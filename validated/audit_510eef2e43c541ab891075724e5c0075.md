### Title
Webhook tenant identity (`shop` header) is not covered by the HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated for a given shop once `Utils::HmacValidator.validate` succeeds, but the HMAC computed by `Request#to_signable_string` only covers the raw request body, not the `shop`, `topic`, or `webhook-id` headers. This breaks the identity binding `hmac(body) == received_hmac ⇒ shop_header is the shop Shopify sent this for`, because the `shop` value that downstream handlers rely on for tenant scoping is never bound into the signed material.

### Finding Description
`Request#hmac`/`#to_signable_string` derive the signable content solely from `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors simply read from unauthenticated headers: [2](#0-1) 

`HmacValidator.validate_signature` only compares the computed HMAC of `to_signable_string` (i.e., the body) against the received signature — it never incorporates `shop`: [3](#0-2) 

`Registry.process` then trusts `request.shop` as the authenticated tenant identifier and forwards it to the handler: [4](#0-3) 

Because `shop` is not part of the signed payload, an attacker who legitimately installs the app on their own store (an unprivileged action available to any merchant for a public app) will receive genuinely-signed webhooks — `hmac == HMAC_SHA256(api_secret_key, raw_body)` — for their own shop. The attacker can then replay the exact same `raw_body` + `hmac` to the app's public webhook endpoint while substituting `x-shopify-shop-domain` (or `shopify-shop-domain`) with any victim shop domain. `HmacValidator.validate` still succeeds, because the check never verifies that the signed body was actually sent by Shopify for that particular shop header value. `Registry.process` then invokes the app's handler with `WebhookMetadata.shop` set to the spoofed victim shop and the attacker's crafted body content.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker-controlled body, wrapped in an attacker-obtained-but-genuine HMAC, can be attributed to any other merchant's shop domain purely by header manipulation. Any host application that uses `WebhookMetadata#shop` (as documented and demonstrated in the test suite) to scope data writes, lookups, or side effects per tenant can be tricked into processing forged/attacker-controlled webhook payloads under a victim's identity — i.e., cross-tenant access, which falls under the Critical impact category.

### Likelihood Explanation
Likelihood is high: webhook endpoints are, by design, publicly reachable HTTP endpoints (that is the entire point of webhooks), and becoming a "sender" of a genuinely-signed webhook only requires installing the app on any shop — including the attacker's own store for a public app, or observing a webhook the attacker's own store received. No access to `api_secret_key`, access tokens, or any privileged account is required; only network access to the app's webhook route and control of one shop's own webhook traffic.

### Recommendation
Do not treat header-supplied `shop`/`topic`/`webhook_id` as authenticated merely because the HMAC over the body is valid. The gem should either (a) bind the shop domain into the value used for the HMAC comparison consistency check by cross-referencing it against a previously-established/authorized session or installation record before invoking the handler, or (b) clearly document that `WebhookMetadata#shop`/`#topic` are **not** cryptographically bound to the payload and require the host application to independently validate the shop against known installed shops before trusting it for tenant-scoped operations. At minimum, `Registry.process` should reject requests where the `shop` header does not correspond to a shop with an active/known session for this app.

### Proof of Concept
1. Install the app (any public app using this gem) on `attacker.myshopify.com`. Shopify sends a real webhook:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <VALID_HMAC_OF_BODY>
x-shopify-shop-domain: attacker.myshopify.com
x-shopify-webhook-id: abc-123

{"id":1,"note":"attacker controlled content"}
```
2. Attacker captures `raw_body` and `x-shopify-hmac-sha256` from this genuine delivery.
3. Attacker resends the identical body and HMAC to the same app endpoint, only changing the shop header:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <SAME_VALID_HMAC_OF_BODY>
x-shopify-shop-domain: victim-shop.myshopify.com
x-shopify-webhook-id: abc-123

{"id":1,"note":"attacker controlled content"}
```
4. `ShopifyAPI::Webhooks::Request.new` accepts the request (only checks header presence), and `Utils::HmacValidator.validate` returns `true` because it only checks `HMAC(raw_body)`. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: {"id":1,"note":"attacker controlled content"}, ...)`, causing the app to process attacker-controlled data attributed to `victim-shop.myshopify.com`.
