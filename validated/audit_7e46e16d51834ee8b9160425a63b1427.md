### Title
Webhook `shop-domain` header used as tenant identity is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from an unauthenticated HTTP header, while the HMAC that `Utils::HmacValidator` checks only covers the raw request body. The `shop` value is then handed to the registered handler as trusted tenant context, breaking the intended binding of `hmac ⟺ (body, shop)`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC solely over `to_signable_string` (the body) and compares it to the `hmac` header: [2](#0-1) 

Meanwhile `Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, a field never included in the signed bytes: [3](#0-2) 

`Registry.process` validates the HMAC and then dispatches the handler using `request.shop` as the tenant identifier, without any additional check that this header matches the shop whose secret validated the HMAC (there is only one global `api_secret_key`, not a per-shop secret, so the HMAC check does not bind to a specific shop at all): [4](#0-3) 

This is exactly the analog class called out in the rules: "a field acted on but not covered by the HMAC." The bytes cryptographically verified (`raw_body`) are not the bytes that determine tenant identity (`shop-domain` header). Any caller who can produce a validly-HMAC'd body for their own shop (which every legitimate merchant/app installation can do, since they know their own webhook payload/signature for their own store) can attach an arbitrary `shopify-shop-domain` header value naming a different tenant, and the gem will pass that spoofed shop straight to the application's webhook handler as `WebhookMetadata#shop`.

### Impact Explanation
Downstream host applications (as documented in `docs/usage/webhooks.md`) are expected to use `WebhookMetadata#shop` to select the merchant's session/access token or scope data updates. Since this value is not bound to the HMAC, an attacker capable of triggering a webhook delivery for their own shop (or replaying a self-generated body+hmac to a public webhook endpoint) can impersonate a different tenant's `shop` value in the metadata passed to the handler, resulting in cross-tenant data confusion — e.g., a handler that revokes access, updates local shop records, or writes GDPR/webhook data keyed by `shop` would act on the wrong tenant. This satisfies the "cross-tenant access" criterion for High/Critical impact given the affected identity is the tenant-selection field.

### Likelihood Explanation
Likelihood is high for any app exposing a single public webhook endpoint: the attacker only needs one valid HMAC for a payload under their own shop's secret (which they have, since app secret is shared across shops for this SDK's single `api_secret_key` model), then can set arbitrary headers when POSTing to the app's own endpoint (the endpoint is a plain HTTP receiver; nothing prevents the caller from setting `shopify-shop-domain` freely alongside a validly-signed body).

### Recommendation
Bind the `shop` (and other identity-relevant headers such as `topic`, `api_version`, `webhook_id`) into the signed payload verification, e.g., by including them in `to_signable_string`, or by requiring the host application to cross-check the header-derived `shop` against an out-of-band verified source (such as the shop associated with the resolved session/access token) rather than trusting the header value directly once the raw-body HMAC passes. At minimum, document prominently that `request.shop` is not authenticated by the HMAC check and must not be used as a sole tenant selector without additional verification.

### Proof of Concept
1. Attacker's own store fires a real Shopify webhook (or attacker crafts any body) and computes `hmac = HMAC-SHA256(api_secret_key, body)` — since `api_secret_key` is the app's shared secret (not per-shop), any legitimate installer of the app already possesses knowledge sufficient to reproduce a valid HMAC for a body of their choosing served through their own store's webhook delivery.
2. Attacker sends `POST /webhooks` with:
   - `x-shopify-hmac-sha256: <valid hmac for body>`
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (arbitrary target tenant)
   - `x-shopify-topic: <any topic>`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the body against the shared secret: [5](#0-4) 
4. The handler executes with `WebhookMetadata.new(... shop: request.shop ...)` set to `victim-shop.myshopify.com`, even though the signed body actually originated from the attacker's own shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
