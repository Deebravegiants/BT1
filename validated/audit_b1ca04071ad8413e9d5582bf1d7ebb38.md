This confirms the vulnerability. The tron `IntentGatewayV2.sol` `placeOrder` function at line 459 (`else` branch, no predispatch) calls `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` for the *nominal* requested amount, but then unconditionally credits `_orders[commitment][token] += reducedInputs[i].amount` — where `reducedInputs[i].amount` is derived from the pre-transfer nominal `order.inputs[i].amount` (minus protocol fee), not from any post-transfer balance measurement.

Compare this to the fixed main EVM contract `evm/src/apps/IntentGatewayV2.sol` (lines 312-329), where the same "no predispatch" branch explicitly measures `balBefore`/`balAfter` and sets `order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore` before computing `reducedInputs` and escrow credit — this fix (and its accompanying `FeeOnTransferToken` regression tests in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`) was never ported to the tron variant. ### Title
Tron IntentGatewayV2.placeOrder credits escrow with nominal amount instead of actual received balance for fee-on-transfer/deflationary tokens - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
In the Tron variant of `IntentGatewayV2.placeOrder`, the non-predispatch escrow path performs `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then credits `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` is computed from the pre-transfer nominal amount rather than the tokens actually received. For any ERC20 with a transfer fee, rebase, or other deflationary transfer mechanic, the contract's actual token balance increase will be less than the amount credited to escrow.

### Finding Description
`placeOrder` first computes `reducedInputs` (nominal amount minus protocol fee) and the order `commitment` hash purely from the caller-supplied `order.inputs[i].amount`, before any tokens move [3](#0-2) . In the branch taken when there is no predispatch call, it then does:
```solidity
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
...
_orders[commitment][token] += reducedInputs[i].amount;
```
with no balance check before/after the transfer [1](#0-0) . If `token` deducts a fee on transfer (or is otherwise deflationary), the gateway's actual balance increases by less than `order.inputs[i].amount`, yet `_orders[commitment][token]` is credited with the full `reducedInputs[i].amount` computed from the pre-fee nominal value.

This is exactly the same bug class as the referenced Cooler `collateralFor`/`transferFrom` report: the contract assumes `transferFrom` moves the exact requested amount and uses that assumption to size an internal accounting/escrow record, without verifying actual balance received.

The upstream, non-Tron `evm/src/apps/IntentGatewayV2.sol` was patched for this exact issue — for the same "no predispatch" branch it snapshots `balBefore = IERC20(token).balanceOf(address(this))`, performs the `safeTransferFrom`, then sets `order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore` before computing protocol fees, the commitment hash, and the escrow credit [2](#0-1) . The presence of dedicated `FeeOnTransferToken` regression tests (`testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, `testPlaceAndFill_FeeOnTransferToken_RoundTrip`, etc.) in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` confirms the project explicitly identified and fixed this class of bug for the mainline contract, but the fix was not carried over to the Tron deployment target.

### Impact Explanation
Every order placed on the Tron IntentGateway using a fee-on-transfer or deflationary ERC20 input token causes `_orders[commitment][token]` to overstate the gateway's actual holdings of that token by the transfer-fee amount. Because escrow accounting is a shared ledger across all orders/solvers for that token, this discrepancy:
- Allows a solver filling this (or any) order, or the user cancelling it, to withdraw against an escrow balance that is not actually backed by real token balance, at the expense of other users' legitimately escrowed funds for the same token, since `_orders[commitment][token]` is used directly to authorize payouts.
- Can lead to insolvency of the contract's token holdings — later legitimate withdrawals for other commitments revert due to insufficient actual balance, i.e., permanent freezing of other users' funds.

This is a direct theft/fund-freezing vector reachable by any unprivileged user simply calling `placeOrder` with a fee-on-transfer token as input, no privileged role required.

### Likelihood Explanation
Likelihood is proportional to how many fee-on-transfer/deflationary tokens are supported as intent inputs on the Tron deployment. Fee-on-transfer tokens are common (e.g., STA-style tokens, some reflection/rebase tokens), and nothing in `placeOrder` restricts input tokens to a fixed allowlist of "safe" ERC20s — any caller can specify an arbitrary `token` address in `order.inputs`. The attack requires only a normal `placeOrder` call with a deflationary token and standard approval, making it trivially reachable.

### Recommendation
Port the balance-delta fix from `evm/src/apps/IntentGatewayV2.sol` to the Tron contract: in the non-predispatch branch, snapshot the token balance before `safeTransferFrom`, compute the actual received amount as the post-transfer balance delta, and use that actual received amount (not the nominal `order.inputs[i].amount`) both for computing `reducedInputs`, the commitment hash, and the `_orders[commitment][token]` escrow credit. The predispatch branch in the Tron contract already computes an actual `balance`/`dust` measurement pattern (lines 416-446) that should similarly gate the escrow credit on actual delivered tokens rather than only the pre-computed `reducedInputs[i].amount`.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 `FOT` with a 1% transfer fee (as in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`'s `FeeOnTransferToken`), and register it as an accepted input token on the Tron `IntentGatewayV2`.
2. User approves `1000 FOT` and calls `placeOrder` with `order.inputs = [{token: FOT, amount: 1000e18}]` and no predispatch.
3. `safeTransferFrom(user, gateway, 1000e18)` executes; due to the 1% fee, the gateway's actual `FOT` balance only increases by `990e18`.
4. Despite this, `_orders[commitment][FOT]` is credited with `reducedInputs[0].amount` derived from `1000e18` (minus any protocol fee), i.e., escrow records ~`1000e18` (or `997e18` with a 30bps protocol fee) instead of the actual `990e18` received.
5. When a solver fills the order or the user cancels it, the contract pays out based on the inflated `_orders[commitment][FOT]` value, drawing down real `FOT` balance that belongs to other orders' escrows, eventually causing a revert (insufficient balance) for some other legitimate order's withdrawal — a permanent fund freeze for that other user.
