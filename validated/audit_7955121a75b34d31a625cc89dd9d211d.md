### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing in `ShopifyAPI::Webhooks::Request` - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw HTTP body of an incoming webhook, while the `shop` identity that `ShopifyAPI::Webhooks::Registry.process` hands to the app's handler is read from an HTTP header that is completely outside the HMAC's coverage. The binding the gem is supposed to enforce — "the HMAC-authenticated bytes equal the bytes the shop identity is derived from" — is broken: `shop == shopify_header("shop-domain")` while `hmac == HMAC(secret, raw_body)`. The two values are never cryptographically tied together.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` verifies `verifiable_query.to_signable_string` (the body) against the received `hmac`, but never touches `shop`: [3](#0-2) 

`Registry.process` gates on that same HMAC check and then trusts `request.shop` as the tenant identifier passed straight to the app's webhook handler: [4](#0-3) 

Contrast this with `Auth::Oauth::AuthQuery#to_signable_string`, where `shop` **is** part of the signed parameter set: [5](#0-4) 

So for OAuth callbacks the gem correctly binds `shop` into the HMAC-protected data, but for webhooks it does not. This is precisely the External Report's bug class translated to this gem: a value that is *acted upon* (`shop`, used to attribute the webhook to a tenant) is disjoint from the value that is *verified* (`raw_body`), exactly as EthRouter sent `msg.value` (unscoped to the loop iteration) while accounting only for the pool's fee (scoped per-change). Here the identity binding that should hold is:

`shop-domain header used by handler == shop bound inside the HMAC-verified payload`

but in truth:

`shop-domain header used by handler != anything covered by HMAC(secret, raw_body)`

An attacker who can obtain any one validly-signed `(raw_body, hmac)` pair for a topic (e.g. by installing the app on their own free development store and triggering an event that produces a generic/attacker-controlled body such as `app/uninstalled`, `shop/update`, or any topic whose payload the attacker fully controls or can predict) can replay that exact `raw_body` + `hmac` to the app's public webhook endpoint while substituting an arbitrary victim `shop-domain` header. `HmacValidator.validate` still passes because it only checks the body, and `Registry.process` forwards `WebhookMetadata.new(... shop: request.shop ...)` with the attacker-chosen shop to the handler — a cross-tenant impersonation entirely inside this gem's trust boundary.

### Impact Explanation
This crosses the tenant boundary the gem is supposed to enforce for webhook processing: the handler is invoked believing the event originates from shop B while the cryptographically-verified content actually originates from (and was authorized for) shop A. Depending on how the host app's registered handler uses `WebhookMetadata#shop` (e.g. to select which merchant record to update/delete, to revoke tokens on `app/uninstalled`, or to fulfil GDPR `shop/redact`/`customers/redact` requests), this enables cross-tenant data corruption or deletion attributed to a merchant who never sent the event — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires no possession of `api_secret_key`, access token, or any privileged credential — only the ability to install the app on a free/unprivileged Shopify store (as any internet user can) to obtain one legitimately-signed `(body, hmac)` pair, plus direct network access to the app's public webhook endpoint to replay it with a modified `shop-domain` header. The gem performs no additional cross-check between the verified body and the header-derived `shop`, so the attack surface is present on every webhook processed via `Registry.process`.

### Recommendation
Include the shop identity (and ideally topic/webhook-id) in the HMAC-covered signable string for `Webhooks::Request`, or otherwise cryptographically bind `shop-domain` to the payload before trusting it in `Registry.process`/`WebhookMetadata`. At minimum, document and enforce that `shop` must never be derived from an unauthenticated header without being part of the verified bytes.

### Proof of Concept
1. Attacker installs the target app on their own (attacker-owned) development store `attacker-shop.myshopify.com` and triggers a webhook topic whose body content is attacker-influenced/predictable (e.g. `app/uninstalled`, which typically has an empty or minimal JSON body `{}`).
2. Attacker captures (or simply reconstructs, since the body is generic/empty and thus reproducible) the raw body and its corresponding valid `X-Shopify-Hmac-Sha256` value produced by Shopify for that request to the app.
3. Attacker POSTs the exact same raw body and `hmac-sha256` header to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) succeeds because it only checks `raw_body` against the secret-derived HMAC.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host app to act on the victim shop's tenant data/session under a forged provenance claim.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
