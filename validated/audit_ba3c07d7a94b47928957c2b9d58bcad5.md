### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify" before invoking the app's handler. In reality, the HMAC signature computed by `Utils::HmacValidator` only covers the raw webhook body, not the `shopify-shop-domain` header that `Registry.process` hands to the handler as the tenant identity. This lets any user who legitimately installs the app on their own store (an unprivileged actor with respect to other tenants) forge the tenant identity of a webhook while keeping a fully valid signature, because the signed bytes and the bytes acted upon by the handler are not the same.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` is read from a separate, unsigned header: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature exclusively from `to_signable_string`, i.e. only the body: [3](#0-2) 

`Registry.process` treats a passing `HmacValidator.validate(request)` check as full authentication of the request, then dispatches the handler using `request.shop` (the unsigned header) as the tenant identity: [4](#0-3) 

The documentation explicitly promises that `process` "will verify the request did indeed come from Shopify," without qualifying that only the body — not the shop identity — is actually verified: [5](#0-4) 

This is the exact bug class flagged in the prompt: a field acted on (`shop`, used to select/attribute the tenant) is not covered by the HMAC that is supposed to bind the whole request to an authentic source. `HmacValidator` proves "this exact body byte-string was produced with the app's secret," it does not prove "this body belongs to this shop." Because a valid `(raw_body, hmac)` pair from any store the attacker controls (any Shopify merchant/developer can install the app on a free/dev store) remains valid regardless of which `shopify-shop-domain` header accompanies it, an attacker can replay their own authentic `(raw_body, hmac)` pair together with a forged `shopify-shop-domain` header naming a victim shop. `Registry.process` will accept the request as authentic and invoke the handler with `shop: <victim-shop>`.

### Impact Explanation
If the host application's webhook handler uses the `shop` field from `WebhookMetadata` to select which tenant's data to mutate (create orders, update inventory, trigger fulfillment, look up and act with that tenant's stored access token, etc.) — which is exactly the intended, documented usage pattern (`ShopifyAPI::Webhooks::Registry.register_all(session: shop_session)` and `WebhookMetadata#shop`) — an attacker can inject cross-tenant events attributed to a shop they do not control, using only their own legitimately-installed shop's valid webhook traffic. This is a cross-tenant access/identity-confusion vulnerability achievable by any unprivileged party who can install the app on any store.

### Likelihood Explanation
Medium-to-high: exploitation requires only (a) installing the target app on any store the attacker controls (freely available to any Shopify developer/merchant), (b) capturing one legitimate webhook delivery (raw body + `x-shopify-hmac-sha256`), and (c) replaying it to the app's webhook endpoint with a forged `shopify-shop-domain`/`x-shopify-shop-domain` header. No access token, `client_secret`, or privileged account for the victim shop is needed.

### Recommendation
Bind the shop identity into the signed material, or otherwise cryptographically tie the `shop` header to the verified body, e.g., include the `shopify-shop-domain` header value in `to_signable_string`, or independently verify that the shop delivering the webhook is one the app actually holds a valid session/webhook subscription for before invoking the handler. At minimum, update the documentation so it does not claim the entire request (including shop attribution) is verified.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`; capture a real webhook delivery: `raw_body = B`, header `x-shopify-hmac-sha256 = H` (valid for `B` under the app secret), `x-shopify-shop-domain: attacker.myshopify.com`.
2. Replay the request to the app's webhook endpoint, keeping `raw_body = B` and `x-shopify-hmac-sha256 = H` unchanged, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` (lib/shopify_api/utils/hmac_validator.rb:12-31) succeeds because it only checks `B` against `H`.
4. `Registry.process` (lib/shopify_api/webhooks/registry.rb:188-200) invokes the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-controlled data under the victim shop's identity.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
