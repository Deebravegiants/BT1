### Title
`messageSigner.signMessage` API accepts an arbitrary `walletAccount` without verifying it is the account the calling origin is authorized/connected to - (File: features/message-signer/src/api/index.ts)

### Summary
The `@exodus/message-signer` public API forwards a caller-supplied `walletAccount` (or account name string) directly into the signing pipeline without any check that the requesting context (e.g., a connected dApp/origin) is actually authorized to sign with that specific wallet account. This is analogous to the reported `BaseTOFT.removeCollateral` bug: the privileged operation (moving/signing on behalf of an account) trusts an attacker/caller-supplied account identifier instead of verifying the caller's actual entitlement to act on that account.

### Finding Description
`messageSignerApiDefinition.factory` exposes `signMessage(params)` as a thin passthrough to the `MessageSigner` module: [1](#0-0) 

`MessageSigner.signMessage` accepts `walletAccount` either as a `WalletAccount` instance or a plain string, resolves it via `#normalizeWalletAccount` by looking it up in `walletAccountsAtom` (i.e., any account existing in the wallet), and then dispatches directly to the seed-based or hardware signer for that account — with no authorization check tying the requested `walletAccount` to the origin/session that issued the call: [2](#0-1) 

The underlying signer then derives the key for that account and produces a valid signature: [3](#0-2) 

Separately, the wallet does maintain a `connected-origins` mechanism that tracks, per dApp origin, which wallet account(s) are connected/trusted (`isTrusted`, `getConnectedAccounts`, `activeWalletAccountAtom`): [4](#0-3) 

However, that authorization/connection state lives in a separate feature module and, based on the available code, is not consulted by `MessageSigner.signMessage` itself. The account-authorization enforcement (if any) would have to happen entirely in a caller/gateway (e.g., a web3-provider RPC handler) *before* invoking `messageSigner.signMessage`. If any such caller passes through a `walletAccount`/address value taken from an untrusted request (dApp postMessage/RPC payload) without first validating it against `connectedOrigins.getConnectedAccounts({ origin })` for that specific origin, a malicious/compromised website could request a signature for an account that was never explicitly connected/approved for it — mirroring the TapiocaOFT flaw where the cross-chain payload's `to`/`from` fields were trusted without an allowance check.

### Impact Explanation
If any RPC/provider entry point calls `messageSigner.signMessage({ walletAccount, ... })` using an account value sourced from the requesting page/dApp/message payload without first verifying it against the origin's actual connected-account grant, this becomes unauthorized cross-account signing: a connected but only lightly-trusted origin (or one that was granted access to `exodus_1`) could request and obtain a valid signature for `exodus_0` or any other wallet account present in `walletAccountsAtom`, without the user ever approving that specific account. Because signatures produced this way are cryptographically valid, this could be leveraged for sign-in spoofing, message-based authentication bypass on other services, or (for chains that support meta-transactions from a signed message) unauthorized actions — a direct account-privilege-bleed matching the report's severity class.

### Likelihood Explanation
The `MessageSigner` module itself does no authorization check and is explicitly the shared signing backend used by all dApp-facing signing flows in this SDK (message-signer README shows it as the primary sign-message entry point for the headless SDK). The likelihood of exploitation depends on whether every RPC/provider adapter that fronts `messageSigner.signMessage` for external/untrusted callers (e.g., browser-extension RPC, WalletConnect, in-app dApp browser) correctly cross-checks the requested account against `connectedOrigins` before calling it — code for those specific bridging layers was not found within the indexed context, so this cannot be fully confirmed as currently exploitable end-to-end, only that the shared signing module itself provides no such safety net and pushes the entire authorization burden onto every caller.

### Recommendation
Add an explicit authorization check inside `MessageSigner.signMessage` (or a required middleware wrapping it) that verifies the requested `walletAccount` is one that the current caller/origin is actually connected to/authorized for (e.g., consulting `connectedOrigins.getConnectedAccounts({ origin })` or an equivalent origin/session-scoped allow-list) before resolving and signing, rather than relying solely on downstream/ad-hoc caller discipline.

### Proof of Concept
Not directly reproducible from the indexed context alone: the vulnerability requires demonstrating that a specific RPC/provider bridge (e.g., the browser-extension RPC or a web3 provider) passes an untrusted, dApp-supplied `walletAccount`/address straight into `messageSigner.signMessage` without checking it against `connectedOrigins`. That bridging code was not found in the available index. Given the index size limits noted in the system instructions, a full trace of every provider-to-`messageSigner` call site should be done in a Devin session with full repository access to confirm whether such an unchecked path exists before treating this as a confirmed, exploitable vulnerability.

  #normalizeWalletAccount = async (
    walletAccount: WalletAccount | string
  ): Promise<WalletAccount> => {
    if (typeof walletAccount === 'string') {
      const walletAccounts = await this.#walletAccountsAtom.get()
      const instance = walletAccounts[walletAccount]
      assert(instance, `wallet account ${walletAccount} not found`)

      return instance
    }

    return walletAccount
  }

  signMessage = async (opts: SignMessageParams) => {
    const { baseAssetName, message, purpose } = opts
    const walletAccount = await this.#normalizeWalletAccount(opts.walletAccount)

    const signer = await this.#getMessageSigner(walletAccount)
    return signer.signMessage({
      baseAssetName,
      walletAccount,
      purpose,
      message,
    })
  }

  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }
