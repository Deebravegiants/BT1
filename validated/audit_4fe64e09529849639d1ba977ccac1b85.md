### Title
Emporium Min-circuit path allows unaccounted arbitrary calls that sweep Emporium's ERC20/ETH balance to the attacker - (File: contracts/CircomDataBuilder.sol, contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
When `externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, which only proves `message == Poseidon(messageSeed)` and carries no root/nullifier/amount constraints. Because `dimensionsCheck` forces every array (`amountChanges`, `slippageValues`, `inputNullifiers`, `onChainCreation`) to also be length 0 when `tokenNumber == 0`, both `Hinkal.transact`'s balance-accounting loop and `EmporiumUpgradeable.runAction`'s balance loop iterate zero times, letting an attacker craft an `EmporiumStack` with `signerAddress == address(0)` (skipping the EIP-712 signature check) whose stateless op calls arbitrary `op.endpoint.call(op.callData)` as Emporium, e.g. `ERC20.transfer(attacker, balance)`, with nothing on-chain checking or accounting for it.

### Finding Description
The broken equality: **assets Emporium can move in a transaction == assets accounted for in `balancesBefore`/`balancesAfter` (Hinkal and Emporium levels)**.

- `formInputForCircom` (`contracts/CircomDataBuilder.sol:134-148`) selects `formInputEmporiumMin` whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`. [1](#0-0) 
- `formInputEmporiumMin` only builds `[emporiumMessage, timeStamp, calldataHash]` as public input, matching `MainEVMCircuitMin`, which proves nothing except `message == Poseidon(messageSeed)` for an attacker-chosen `messageSeed` — no link to any real UTXO, root, or nullifier. [2](#0-1) [3](#0-2) 
- `dimensionsCheck` forces `amountChanges.length == inputNullifiers.length == onChainCreation.length == slippageValues.length == erc20TokenAddresses.length == dimensions.tokenNumber`, so setting `tokenNumber = 0` makes every accounting array empty. [4](#0-3) 
- In `Hinkal.transact`, `oldBalances`/`newBalances` are computed over the (empty) `erc20TokenAddresses` array, and the balance-diff/slippage loop that would otherwise catch unauthorized transfers never executes because it iterates `circomData.erc20TokenAddresses.length` (== 0). [5](#0-4) 
- `_externalTransact` dispatches to `EmporiumUpgradeable.runAction` with `deltaAmountChanges` also empty. [6](#0-5) 
- Inside `runAction`, `balancesBefore`/`balancesAfter` are likewise computed over the empty token array, so the `balanceChange` guard (`BalanceChangeShouldBePositive`) never runs for any token that isn't in that (empty) list. [7](#0-6) 
- `verifyWallet` returns immediately without any signature check when `stack.signerAddress == address(0)`, only marking `emporiumMessage` used. [8](#0-7) 
- With `signerAddress == address(0)`, every op falls into "CASE 2: Stateless Interaction" and is executed as `op.endpoint.call{value: op.value}(op.callData)`, with `msg.sender == Emporium` itself; the only restriction is blocking `callHinkalWallet`/`doSendToRelay` selectors, which is irrelevant to a direct ERC20 `transfer` call. [9](#0-8) 

**Attacker's exact call**: Call `Hinkal.transact` with:
- `circomData.externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalAddress = <registered Emporium address>`
- `circomData.erc20TokenAddresses = []`, and all other dimension-linked arrays `[]`
- `dimensions.tokenNumber = 0`
- `circomData.externalActionData.externalActionMetadata = abi.encode(EmporiumStack{ signerAddress: address(0), ops: [EmporiumOperation{ endpoint: <targetERC20>, invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.transfer.selector, attacker, emporiumBalance) }] })`
- `circomData.emporiumMessage`/`calldataHash` self-computed to satisfy the trivial `getHashedCalldata` integrity check and a legitimately generated `MainEVMCircuitMin` proof for an arbitrary `messageSeed`
- Any existing `rootHashHinkal` (already present in Merkle root history from any prior deposit — no ownership of that root's leaves required, since no nullifier is used)

The circuit and all on-chain guards (`performHinkalChecks`, `verifyProof`, `rootHashExists`, balance/slippage requires, `insertNullifiers`) are bypassed or vacuous because every one of them is either not evaluated (empty loops) or is satisfiable with attacker-chosen, self-consistent data. Since `Emporium` operates using its own funds/identity (not a delegatecall through a per-user wallet), any ERC20 or ETH balance sitting on the Emporium contract (in flight from other users' concurrent transactions, dust, or leftover fee-on-transfer overages) can be swept directly to the attacker with zero accounting.

### Impact Explanation
Direct theft of funds held by the Emporium contract (in-flight user funds mid-multi-step-transaction, or any residual/fee-on-transfer dust) with no balance check, no signature requirement, and no nullifier consumption. This matches the Critical severity category "direct theft of shielded or in-flight user funds," since Emporium routinely and momentarily holds user ERC20/ETH balances as part of legitimate multi-op flows (deposits then swaps then withdraw), and this bug lets an unrelated attacker call `Hinkal.transact` and drain whatever balance Emporium is holding at that moment. The attack is fully repeatable for every transaction where Emporium holds a nonzero balance of a target token.

### Likelihood Explanation
- No privileged role is required; attacker is any EOA.
- Preconditions: Emporium contract must hold a non-zero balance of the targeted token (which is the normal operating condition whenever another user's Emporium operation is in flight, or if a fee-on-transfer token leaves residual dust after a legitimate op).
- Attacker cost: gas plus generating one legitimate, arbitrary "Min" Groth16 proof (trivial off-chain, since `messageSeed` is fully attacker-chosen and unconstrained by any root/nullifier relationship).
- No dependency on relay, oracle, or any other party; fully attacker-executable end-to-end.

### Recommendation
Do not allow `erc20TokenAddresses.length == 0` (i.e., the Min-circuit/"formInputEmporiumMin" path) to be combined with `externalActionMetadata` that can invoke arbitrary `ops`. Specifically:
1. Require that the Emporium Min path can only be used for pure `Emporium` off-chain-message operations that provably touch zero on-chain balances (e.g. forbid non-empty `stack.ops` entirely when `erc20TokenAddresses.length == 0`), or
2. Always require `stack.signerAddress != address(0)` (mandatory signature verification) for any op that performs external calls, removing the unauthenticated `signerAddress == address(0)` bypass path in `verifyWallet`, and
3. Ensure `EmporiumUpgradeable.runAction`'s balance accounting covers every token actually touched by `stack.ops` (e.g., derive the token set from the ops/target contracts rather than trusting `circomData.erc20TokenAddresses`, or forbid `ops` from targeting tokens not present in `erc20TokenAddresses`).

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (registered as `HINKAL_EMPORIUM_ACTION_ID` external action and as an allowed recipient), and a mock/real Groth16 verifier for `MainEVMCircuitMin` registered under `buildVerifierId(Dimensions{tokenNumber:0,...}, HINKAL_EMPORIUM_ACTION_ID)`.
2. Fund `EmporiumUpgradeable` directly with `TOKEN.mint(emporium, 1000e18)` to simulate in-flight/residual balance.
3. As attacker EOA (no prior deposit into Hinkal), generate a valid `MainEVMCircuitMin` proof for an arbitrary `messageSeed`, compute `message`, and build `CircomData` with `erc20TokenAddresses = []`, `dimensions.tokenNumber = 0`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionMetadata = abi.encode(EmporiumStack{signerAddress: address(0), ops: [transfer(attacker, 1000e18) on TOKEN]})`, and a valid `rootHashHinkal` from the tree's initial/empty state.
4. Call `Hinkal.transact(a,b,c,dimensions,circomData)`.
5. Assert:
   - Before: `TOKEN.balanceOf(emporium) == 1000e18`, `TOKEN.balanceOf(attacker) == 0`.
   - After: `TOKEN.balanceOf(emporium) == 0`, `TOKEN.balanceOf(attacker) == 1000e18`.
   - The equality "assets moved by Emporium ops" (1000e18) != "assets accounted in balancesBefore/After arrays" (0, since arrays are empty) is demonstrated broken, and no `require` in `Hinkal.transact` or `EmporiumUpgradeable.runAction` reverts the transaction.
