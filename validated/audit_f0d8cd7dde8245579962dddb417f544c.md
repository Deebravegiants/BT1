### Title
Arbitrary contract call in `EmporiumUpgradeable.runAction` lets an unprivileged prover drain any ERC20 balance stranded on the Emporium contract that isn't in their own declared token list — ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` performs a fully attacker-controlled low-level call (`op.endpoint.call{value: op.value}(op.callData)`) whenever an `EmporiumOperation` is "stateless" (i.e. `invokeWallet == false`, or whenever `stack.signerAddress == address(0)`, since that condition forces every op into the stateless branch). The only accounting safeguard against theft via this call — the `balancesBefore`/`balancesAfter` comparison — is computed **exclusively** over `circomData.erc20TokenAddresses`, an array that the calling prover fully controls and can freely omit the target token from. Any ERC20 balance sitting on the Emporium contract for a token *not* listed in that array can be transferred out with zero balance check, breaking the equality between "tokens Emporium is supposed to account for" and "tokens Emporium actually holds and can move."

### Finding Description
In `runAction`: [1](#0-0) 

- When `stack.signerAddress == address(0)` (a valid, walletless/"proofless" Emporium mode — see the early return in `verifyWallet`), the condition `op.invokeWallet && stack.signerAddress != address(0)` is always false, so **every** op falls into the "stateless" branch and is executed as `op.endpoint.call{value: op.value}(op.callData)` — a raw call to an attacker-chosen address with attacker-chosen calldata, executed with `msg.sender == EmporiumUpgradeable`. [2](#0-1) 

- The only guard against misuse of the arbitrary call is the pre/post-balance diff, but it is computed strictly for `circomData.erc20TokenAddresses`, which is part of the same calldata the attacker submits and signs (via `calldataHash`/ZK proof) for their own transaction — i.e., **the prover chooses which tokens get checked**: [3](#0-2) [4](#0-3) 

- Because Emporium can legitimately hold balances between/after operations — the code even documents this ("the only case when balanceChange can be < 0, when there were some funds on emporium before the call", and `handleOut` simply skips a token if its computed change is `<= 0`, leaving it on the contract) — any dust, rounding leftovers, over-swapped output, unclaimed relay fee, or a prior user's stranded balance for a token can persist on the Emporium contract indefinitely: [5](#0-4) 

- An attacker simply submits their own `Hinkal.transact()` call (valid ZK proof over their own, possibly trivial, shielded balance) with an `EmporiumStack` where `signerAddress == address(0)` and `circomData.erc20TokenAddresses` deliberately omits the token they intend to steal. One `EmporiumOperation` sets `endpoint = <stolen token address>` and `callData = transfer(attacker, strandedBalance)`. This call succeeds unconditionally as `msg.sender` is Emporium itself (Emporium owns the balance, no approval needed for `transfer`), and no balance-equation check ever inspects that token because it isn't in the attacker's declared array.

This is directly analogous to the Tally `fillZrxQuote` bug class referenced in the external report: an arbitrary contract call with attacker-chosen calldata, executed by a contract that can hold tokens belonging to others, with insufficient scoping/whitelisting of the callable target and insufficient accounting of the resulting balance movement.

### Impact Explanation
Any ERC20 (or ETH) balance the Emporium contract accumulates over time — via rounding, output/slippage surplus, delayed relay-fee sweeps, airdrops/rewards sent to the contract, or funds left after `balanceChange <= 0` skips a payout in `handleOut` — is not the attacker's, yet can be unilaterally swept by any unprivileged EOA that can submit a valid Hinkal transaction. This is theft of protocol/other users' in-flight or residual funds held by the contract (High/Critical depending on the token/amount stranded), executed via an asset movement neither the fund owner nor the prover who deposited it ever authorized for the thief.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: Emporium's own accounting model explicitly anticipates and tolerates pre-existing balances on the contract (documented in the `balanceChange < 0` comment), meaning dust/leftover balances are an expected, recurring state rather than a rare edge case. Exploitation requires no privileged role, no signature from another party (the `signerAddress == address(0)` path is a normal, unauthenticated mode), and only a minimal valid proof for the attacker's own shielded state — well within reach of any user of the protocol.

### Recommendation
- Track and check balances for the union of tokens the low-level calls in `stack.ops` could plausibly touch, not just `circomData.erc20TokenAddresses` — or, simpler, restrict the "stateless" arbitrary call (`op.endpoint.call`) to a whitelist of trusted endpoints (e.g., the router/wrapper), similar to the WatchPug recommendation of whitelisting `zrxTo`.
- Alternatively, disallow calls to arbitrary `endpoint` values entirely in the walletless (`signerAddress == address(0)`) mode, or require that any token balance actually held/moved on Emporium during `runAction` (for *any* token, not only the declared list) nets to zero/positive relative to what the transaction is entitled to.
- Add an explicit sweep/accounting mechanism so stranded balances cannot silently accumulate as an unguarded attack surface.

### Proof of Concept
1. Some ERC20 token `T` accumulates a stray balance on `EmporiumUpgradeable` (e.g., swap-output rounding surplus from a legitimate prior `LifiExternalAction`/Emporium op, or an unclaimed relay-fee remainder left because `handleOut` skipped payout when `balanceChange <= 0`).
2. Attacker calls `Hinkal.transact()` with a valid proof for their own trivial shielded operation, setting:
   - `circomData.erc20TokenAddresses` = some other token(s), deliberately excluding `T`.
   - `circomData.externalActionData.externalActionAddress` = Emporium, `externalActionId` = Emporium's id.
   - `externalActionMetadata` decodes to an `EmporiumStack` with `signerAddress = address(0)` and one `EmporiumOperation{ endpoint: address(T), invokeWallet: false, value: 0, callData: abi.encodeWithSignature("transfer(address,uint256)", attacker, strandedAmount) }`.
3. In `runAction`, `verifyWallet` returns immediately (no signature required since `signerAddress == 0`), the op falls into the stateless `else` branch, and `T.transfer(attacker, strandedAmount)` executes with `msg.sender == Emporium`, succeeding because Emporium owns that balance directly (no `transferFrom`/approval needed).
4. The post-loop balance check only iterates `circomData.erc20TokenAddresses`, which does not include `T`, so `strandedAmount` leaving Emporium is never detected or blocked.
5. Result: `strandedAmount` of `T` is transferred to the attacker at zero cost beyond the gas/proof for an otherwise-irrelevant transaction.
