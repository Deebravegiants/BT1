### Title
Webhook HMAC does not bind the `shop-domain` header, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature over the raw request body only, while the `shop` (and `topic`/`webhook_id`) values used by `ShopifyAPI::Webhooks::Registry.process` to identify the tenant are taken from unsigned HTTP headers. Because a single app-wide `api_secret_key` is used to sign webhook bodies for every shop that installs the app, any holder of one validly-signed webhook body/HMAC pair can replay it with a forged `shopify-shop-domain` header to make the host application process it as if it originated from a different, victim shop.

### Finding Description
The equality that should hold is: `shop_the_HMAC_authenticates == shop_the_handler_acts_on`. In this gem it does not.

`Request#to_signable_string` only returns the raw body: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are all pulled straight from attacker-controllable HTTP headers, unrelated to the signed payload: [2](#0-1) 

`HmacValidator.validate` calls `verifiable_query.to_signable_string`, so it only ever verifies the body bytes, never the shop/topic/webhook_id headers: [3](#0-2) 

`Registry.process` verifies the HMAC and then unconditionally trusts `request.shop` and `request.topic` (from headers) to dispatch to the handler and identify the tenant: [4](#0-3) 

Because Shopify signs webhooks with the app's single `client_secret` (`Context.api_secret_key`) — the same secret for every shop that has the app installed — a valid `(body, hmac)` pair captured from any one tenant's webhook delivery (e.g., the attacker's own store, which they fully control and can trigger webhook-triggering events on) remains cryptographically valid when replayed with a different `shopify-shop-domain` header value. The HMAC proves "this body was produced by Shopify for this app," not "this body belongs to this shop." Any consumer of this gem that uses `WebhookMetadata#shop` (built from `request.shop`) as the tenant key to look up sessions/data — the documented and expected usage pattern per `Webhooks::Registry.process` — will misattribute the forged event to the victim shop.

### Impact Explanation
This breaks the tenant-identity binding that HMAC verification is supposed to provide, allowing cross-tenant event injection: an attacker with access to their own shop's webhook traffic can fabricate seemingly-legitimate webhook events "from" a victim shop, since the gem's own `Registry.process` and `Request` treat header-sourced `shop`/`topic`/`webhook_id` as trusted context validated by the HMAC check that immediately precedes it. Applications built on this documented API (`handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))`) inherit this cross-tenant confusion without any misuse of the API.

### Likelihood Explanation
Exploitability requires only: (1) being a legitimate merchant/tenant of the target app (to obtain one validly HMAC-signed webhook body, e.g. by triggering `orders/create` in one's own store), and (2) sending an HTTP request to the app's webhook endpoint with the captured body/HMAC but a rewritten `shopify-shop-domain` (and optionally `shopify-topic`) header. No access to the `client_secret`, access tokens, or the victim's credentials is needed.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signable content (or otherwise cryptographically bind them to the verified body), or require that the host application independently confirm that `request.shop` corresponds to a shop with an active session/installation before trusting the payload as belonging to that tenant. At minimum, document this gap prominently so integrators do not use `WebhookMetadata#shop` as an authenticated tenant identifier.

### Proof of Concept
1. Attacker's own shop `attacker.myshopify.com` triggers a real webhook (e.g., `orders/create`), producing body `B` and header `Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(app_client_secret, B)`.
2. Attacker POSTs to the target app's webhook endpoint with:
   - `shopify-hmac-sha256: H`
   - `shopify-topic: orders/create`
   - `shopify-shop-domain: victim.myshopify.com`
   - body: `B`
3. `HmacValidator.validate` recomputes HMAC over `B` only [3](#0-2)  — validation succeeds because `B` is unchanged.
4. `Registry.process` dispatches the handler with `shop: "victim.myshopify.com"` [5](#0-4) , causing the host application to process attacker-controlled order/webhook data as if it came from the victim's store.
