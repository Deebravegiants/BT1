### Title
`handlePostRequestTimeouts`/`handleGetRequestTimeouts` are blocked by `FrozenStatus.Incoming`, preventing relayer-fee refunds even though timeouts are not "incoming" traffic - (File: `evm/src/core/HandlerV2.sol`)

### Summary
The `notFrozen(host)` modifier in `HandlerV2.sol` is applied uniformly to `handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, and `handleGetRequestTimeouts`, reverting whenever `host.frozen()` returns `FrozenStatus.Incoming` or `FrozenStatus.All`. This mirrors the JOJO bug pattern: an administrative safety switch (`delistReserve`/`setFrozenState(Incoming)`) meant to stop *new* risky activity instead also blocks the wind-down/exit path (repay-and-withdraw/liquidate ≈ timeout-and-refund) that should remain available to users who already committed funds.

### Finding Description
`FrozenStatus.Incoming` is documented as blocking only the *receipt* of new cross-chain messages [1](#0-0) , and `FrozenStatus.Outgoing` is documented as blocking only *dispatch* of new outgoing messages, enforced separately by `EvmHost.notFrozen()` on `dispatch()` [2](#0-1) .

However, `HandlerV2.notFrozen(host)` reuses the same "Incoming" check for `handlePostRequestTimeouts` and `handleGetRequestTimeouts`: [3](#0-2) 

These timeout handlers are invoked by relayers/users on the **source** chain to prove non-membership of a previously *dispatched outgoing* request/response on the destination, in order to trigger `host.dispatchTimeOut(...)` and refund the escrowed relayer fee to the original payer: [4](#0-3) [5](#0-4) 

Because these two functions carry the `notFrozen(host)` modifier (which reverts on `Incoming` or `All`), an admin/handler setting `setFrozenState(FrozenStatus.Incoming)` — a state intended only to stop the host from accepting new incoming requests/responses, e.g. during a suspected consensus/bridge incident — also freezes any in-flight outgoing request whose destination never responds. Users cannot reclaim their escrowed relayer fee via timeout until the admin manually reverts the frozen state to `None` or `Outgoing`. `setFrozenState` is callable by `_hostParams.admin` or `_hostParams.handler` [6](#0-5) , and is a normal operational lever, not a one-off catastrophic event — the docs explicitly describe it as a switch "used to halt specific protocol operations during security incidents or upgrades" [7](#0-6) , meaning this state is expected to be entered/exited routinely, during which window all pending outgoing-request refunds are unable to be claimed.

This is directly analogous to the JOJO finding: `delistReserve` sets flags meant to stop new risky actions (`isDepositAllowed=false`, `isBorrowAllowed=false`) but as a side effect also disables the exit/wind-down actions (withdraw, liquidate) that legitimately should remain open. Here, `FrozenStatus.Incoming` is meant to stop new incoming message acceptance but as a side effect disables the wind-down action (timeout-triggered fee refund) for a user's own already-dispatched outgoing message.

### Impact Explanation
While an admin can eventually flip the frozen state back, during any period the host is set to `Incoming` (a state the docs treat as routine, security-motivated, and reversible but explicitly not requiring the more severe `All`), users who dispatched a `PostRequest`/`GetRequest` whose destination is unresponsive or maliciously non-responding cannot call `handlePostRequestTimeouts`/`handleGetRequestTimeouts` to reclaim their escrowed relayer fee, even though this operation has nothing to do with accepting new incoming messages and is otherwise permissionless-and-safe. This is an unjustified freezing of user funds (relayer fees escrowed in `_requestCommitments`) tied to an operational state that is more restrictive than necessary for the underlying safety goal, contrary to the documented purpose of `Incoming` freezing.

### Likelihood Explanation
`setFrozenState(Incoming)` is a normal admin/handler operational action (not a rare catastrophic emergency-only path) exposed for exactly the routine "security incident" scenarios the docs describe [7](#0-6) . Any time it is active, every user with an outstanding outgoing request past its `timeoutTimestamp` is unconditionally blocked from the refund path, so the condition is trivially reachable by design, not by attacker action.

### Recommendation
Timeout handlers should not be gated by `FrozenStatus.Incoming`. Introduce a distinct check (or simply exempt timeout processing from the `Incoming`/`All` gate, restricting only genuinely new incoming request/response delivery), so that `handlePostRequestTimeouts` and `handleGetRequestTimeouts` remain callable to let users reclaim escrowed fees regardless of the `Incoming` freeze state, consistent with how `FrozenStatus.Outgoing` does not block timeout processing today.

### Proof of Concept
1. Alice dispatches a `PostRequest` via `EvmHost.dispatch`, escrowing a relayer fee in `_requestCommitments` [8](#0-7) .
2. The destination chain never processes the request before `timeoutTimestamp` elapses.
3. Admin/handler calls `host.setFrozenState(FrozenStatus.Incoming)` for an unrelated incident on the incoming path [6](#0-5) .
4. Alice (or a relayer on her behalf) submits a valid non-membership proof to `HandlerV2.handlePostRequestTimeouts` to reclaim her fee; the call reverts with `HostFrozen()` due to the `notFrozen(host)` modifier [9](#0-8) , even though her request has nothing to do with new incoming traffic.
5. Alice's escrowed fee remains locked until the admin reverts the frozen state, with no way for her to force resolution herself.

    function handlePostRequestTimeouts(IHost host, PostRequestTimeoutMessage calldata message)
        external
        notFrozen(host)
    {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            PostRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            // known request? also serves as source check
            bytes32 requestCommitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(requestCommitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(REQUEST_RECEIPTS_STORAGE_PREFIX, requestCommitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(PostRequestTimeout(request, _msgSender()), meta, requestCommitment);
        }
    }
