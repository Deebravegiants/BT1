### Title
Single global `maxOracleAge` staleness bound applied uniformly to all registered token oracles enables stale-price gas payment - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` prices ERC-20 gas payments using Chainlink `latestRoundData()` for both the native asset and the chosen ERC-20 token, staleness-checked against one shared `maxOracleAge` value applied to every oracle in the contract, rather than a per-token bound matched to that token's actual Chainlink heartbeat.

### Finding Description
`Params.maxOracleAge` is a single contract-wide value (governance-settable, capped at `MAX_ORACLE_AGE = 7 days`) used to validate staleness for the native oracle and for every registered token's oracle alike: [2](#0-1) . `TokenConfig` stores only the oracle address/decimals/active flag per token — there is no per-token staleness bound: [3](#0-2) . `_getOraclePrice` enforces exactly this single global bound for whichever oracle is passed in: [4](#0-3) .

Because a permissionless UserOperation sender selects `tokenAddr` from `paymasterData` (mode 0x00/0x02) and this feeds directly into `_fetchDetails`/`_tokenPrice`/`_getOraclePrice` with no per-token staleness override [5](#0-4) , governance is forced to pick one `maxOracleAge` that must simultaneously fit every registered token. If governance sets it loosely to accommodate a slow-heartbeat stablecoin (e.g. up to the documented 24h/86400s heartbeat, as used throughout tests and the deploy script's `MAX_ORACLE_AGE` env default of 90,000s) [6](#0-5) , any other registered token whose Chainlink feed actually updates far more frequently (minutes to an hour, typical of newly-listed or volatile tokens) will still be accepted by the paymaster as "fresh" for up to that same multi-hour/day window even after its feed has silently stalled or the token's market price has diverged sharply from the last reported round.

### Impact Explanation
An attacker who registers, or convinces governance to register, a volatile/thinly-tracked ERC-20 (or simply waits for an already-registered token's price feed to stall or the token's real price to crash) can submit UserOperations paying gas in that token while its Chainlink answer is stale-high relative to the real market price. Because `_tokenPrice` divides by `tokenUsd` [7](#0-6) , an overstated stale `tokenUsd` produces an understated `tokenPrice`, letting the attacker prefund gas with far fewer (and, if the token has crashed, near-worthless) tokens than the true exchange rate requires, directly draining the paymaster's EntryPoint deposit/native reserves for real gas costs against essentially valueless ERC-20 collateral. This is a direct loss-of-funds path reachable by any UserOperation sender, not an admin.

### Likelihood Explanation
Governance is realistically forced into a single global setting that must tolerate the least-frequently-updating registered oracle (documented in the deploy script and `Params` comments as needing to cover up to ~24h heartbeats) [8](#0-7) ; any token registered later with a materially different heartbeat inherits the same lax bound automatically, with no code path to tighten it per-token. Registering a new token happens through ordinary governance `RegisterToken` requests [9](#0-8) , which is a normal, expected operational flow (adding support for a new "trending" token), making the exposure window a routine consequence of expanding token support rather than a rare misconfiguration.

### Recommendation
Add a per-token staleness bound to `TokenConfig` (set at `RegisterToken` time, matching that token's actual Chainlink heartbeat) and check it independently in `_getOraclePrice`/`_tokenPrice`, instead of relying on one contract-wide `maxOracleAge` for every registered oracle including the native feed.

### Proof of Concept
1. Governance registers `TOKEN_X` with a Chainlink feed whose real heartbeat is 1 hour, while `maxOracleAge` is set to `86400` (24h) to accommodate USDC/USDT's slower feeds (per `_registerToken`, `RegisterToken` request kind) [9](#0-8) .
2. `TOKEN_X`'s market price crashes; its Chainlink feed, expected to update hourly, stalls (oracle outage/no deviation trigger) or otherwise reports a stale high price up to 23h59m old.
3. `_getOraclePrice(cfg.tokenOracle, ...)` still passes the staleness check because `block.timestamp - updatedAt <= maxOracleAge (86400)` [10](#0-9) .
4. An attacker submits a UserOperation with `paymasterData` mode 0x00/0x02 selecting `TOKEN_X` [11](#0-10) ; `_fetchDetails`/`_tokenPrice` compute an understated `tokenPrice` from the stale, too-high `tokenUsd`, so `_erc20Cost` charges far fewer `TOKEN_X` units than the token is actually worth.
5. The paymaster's real ETH/native reserve is spent on gas while receiving near-worthless `TOKEN_X`, repeatable across many UserOperations until governance notices and calls `DeactivateToken`.

        tokenConfigs[token] = TokenConfig({

            tokenOracleDecimals: oracle.decimals(),
            tokenDecimals: IERC20Metadata(token).decimals(),
            active: true
        });

        }

    function _tokenPrice(TokenConfig memory cfg) internal view returns (uint256) {
        uint256 nativeUsd = _getOraclePrice(nativeOracle, nativeOracleDecimals);
        uint256 tokenUsd = _getOraclePrice(cfg.tokenOracle, cfg.tokenOracleDecimals);

        return (nativeUsd * (10 ** cfg.tokenDecimals) * (10_000 + markupBps)) / (tokenUsd * 10_000);
    }

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
