### Title
`PoaBridge.describeWithdrawal` misreports status/txHash for batched same-asset withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`findMatchingWithdrawal` matches PoA withdrawal API results purely by `assetId` via `Array.prototype.find`, ignoring `WithdrawalIdentifier.index`. When a batch contains two PoA withdrawals of the same `assetId` to different `destinationAddress`, both `describeWithdrawal` calls resolve to the same matched withdrawal record, so both report identical `(status, txHash)` even though they represent two distinct on-chain transfers.

### Finding Description
The broken equality: `describeWithdrawal({index: 0, assetId: A, destinationAddress: X})` and `describeWithdrawal({index: 1, assetId: A, destinationAddress: Y})` should report the status/txHash of two *different* on-chain transfers, but both resolve to the same object because matching ignores `index` entirely: [1](#0-0) .

`findMatchingWithdrawal` explicitly documents this limitation and returns the first (only) `.find()` match by `nep141:${near_token_id} === assetId`: [2](#0-1) .

Nothing upstream prevents an unprivileged caller from constructing a batch with two `withdrawalParams` sharing the same PoA-routed `assetId`. `createWithdrawalIdentifiers` only tracks a per-bridge-route index counter and does not dedupe or reject same-`assetId` entries: [3](#0-2) . `PoaBridge.supports`/`validateWithdrawal`/`createWithdrawalIdentifier` also perform no cross-withdrawal uniqueness check: [4](#0-3) . The resulting per-index `WithdrawalIdentifier`s are independently polled via `watchWithdrawal`/`createWithdrawalCompletionPromises`, each calling `describeWithdrawal` with its own index but the same `assetId`: [5](#0-4) .

So both polling promises converge on the identical `withdrawal` record returned by `findMatchingWithdrawal`, producing the same `status`/`txHash` for withdrawal index 0 and index 1, even though the PoA bridge backend actually executes two separate transfers to two separate destination addresses.

### Impact Explanation
An integrator relying on `watchWithdrawal`/`createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion` per-index results to attribute a destination `txHash` to a specific `destinationAddress` will attribute the same `txHash` to both withdrawals. This can cause the integrator to believe both destinations were credited via the same transaction (double-credit one destination, or fail to confirm the correct one), matching the "status or hash misreport making an integrator credit or refund twice" High-severity category. This is repeatable on every batch containing duplicate-`assetId` PoA withdrawals with distinct destinations.

### Likelihood Explanation
Preconditions: the batch must route both withdrawals through `RouteEnum.PoaBridge` and share the same `nep141:*.omft.near` `assetId`; this requires no privileged access — a normal user (or a counterparty whose withdrawalParams an integrator forwards) can construct such a batch via `signAndSendWithdrawalIntent`/`processWithdrawal` with `withdrawalParams: [A, B]`. No SDK-side validation rejects this combination, and the code comment confirms the maintainers were aware this scenario is unhandled by design (matching by assetId only, since the POA API itself lacks per-withdrawal disambiguation) [6](#0-5) . Attacker cost is a single normal withdrawal transaction; feasibility is high.

### Recommendation
Either (a) reject/merge batches containing duplicate PoA `assetId`s at `supports()`/`createWithdrawalIdentifiers` time so ambiguous cases cannot be constructed, or (b) disambiguate matches using amount/order heuristics as suggested in the existing code comment (sort both API results and withdrawal params by amount before matching) and throw/return `pending`/an explicit error instead of silently returning the first match when more than one candidate exists for the same `assetId`.

### Proof of Concept
Vitest test in `poa-bridge.test.ts`-style file:
1. Build two `WithdrawalIdentifier`s with identical `withdrawalParams.assetId = "nep141:zec.omft.near"`, `index: 0` and `index: 1`, but different `destinationAddress`/`amount`.
2. Mock `poaBridge.httpClient.getWithdrawalStatus` (only HTTP mocked) to return `{ withdrawals: [{ status: "COMPLETED", data: { near_token_id: "zec.omft.near", transfer_tx_hash: "0xonlyone" } }] }`.
3. Call `poaBridge.describeWithdrawal(wid0)` and `poaBridge.describeWithdrawal(wid1)`.
4. Assert both resolve to `{ status: "completed", txHash: "0xonlyone" }` — i.e., `result0.txHash === result1.txHash` despite `wid0.withdrawalParams.destinationAddress !== wid1.withdrawalParams.destinationAddress`, proving the reported (status, txHash) pair does not distinguish the two distinct on-chain transfers.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
