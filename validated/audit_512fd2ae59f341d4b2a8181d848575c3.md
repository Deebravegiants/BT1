### Title
Webhook shop/topic identity not bound to HMAC allows cross-tenant webhook impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC only over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by `ShopifyAPI::Webhooks::Registry.process` to route and attribute the webhook are read from unauthenticated HTTP headers that are never included in the signed data. This breaks the binding `shop-header == shop-covered-by-hmac` (and the same for `topic`), letting anyone holding one valid `(body, hmac)` pair replay it while freely rewriting the `shop`/`topic` headers to impersonate another tenant or event type.

### Finding Description
`Utils::HmacValidator.validate` verifies that the received `hmac` matches `HMAC-SHA256(secret, verifiable_query.to_signable_string)`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to the HMAC: [3](#0-2) 

`Registry.process` uses exactly these unauthenticated fields for both authorization-equivalent routing (`handler = @registry[request.topic]&.handler`) and tenant attribution (`shop: request.shop` passed into the handler's `WebhookMetadata`): [4](#0-3) 

Equality that should hold but doesn't: `hmac-verified-bytes == bytes-that-determine-tenant/topic`. In reality: `hmac-verified-bytes == raw_body` only, while `tenant/topic-decision-bytes == shop-domain-header / topic-header`, which are disjoint from what the HMAC covers.

Because `api_secret_key` is a single per-app secret shared across every shop that installs the app (not a per-shop secret), any merchant/installer of the app already legitimately receives real webhooks—valid `(body, hmac)` pairs signed with that same app secret. An attacker who has installed the app (an "unprivileged internet user" relative to any *other* tenant) can:
1. Capture one legitimate `(raw_body, x-shopify-hmac-sha256)` pair delivered to their own endpoint for their own shop.
2. Replay that exact body/hmac to the app's public webhook endpoint, but substitute `x-shopify-shop-domain` with a victim shop's domain and/or `x-shopify-topic` with a different registered topic.
3. `Utils::HmacValidator.validate` still succeeds because it only checks the unmodified body against the unmodified hmac.
4. `Registry.process` dispatches to the handler for the attacker-chosen topic, and constructs `WebhookMetadata` with the attacker-chosen `shop`, which is exactly the value host applications use to determine *which tenant's data* the webhook applies to.

### Impact Explanation
This crosses the tenant boundary: the app's webhook consumer will process attacker-supplied body content as if it originated from Shopify for an arbitrary victim shop and/or arbitrary topic, entirely from data whose authenticity guarantee (the HMAC) does not actually cover the fields being trusted. This matches the Critical "cross-tenant access" impact bucket, since any host application relying on `WebhookMetadata#shop` (returned by this gem) to scope data writes/reads per tenant can be tricked into acting on behalf of the wrong shop.

### Likelihood Explanation
Likelihood is high for any multi-tenant app built on this gem: no secret key, access token, or privileged access is required—only possession of one webhook payload the attacker legitimately receives for their own installed shop (trivially obtained by installing the app once) and the ability to send an arbitrary HTTP request to the app's public webhook endpoint with modified headers.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable string used for HMAC computation (or otherwise cryptographically bind them, e.g. via a MAC over `header canonicalization + body`), so any header tampering invalidates the HMAC. At minimum, `Registry.process` should independently validate that `request.shop` matches an expected/enrolled shop for the given install before dispatching, rather than trusting the header value as the sole source of tenant identity.

### Proof of Concept
```ruby
# Attacker legitimately receives one real webhook for their own installed shop:
real_headers = {
  "x-shopify-topic" => "customers/create",
  "x-shopify-hmac-sha256" => real_hmac_base64, # valid for real_body under app secret
  "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
}
real_body = '{"id":1,"email":"a@a.com"}'

# Attacker replays same body/hmac, but forges the tenant + topic headers:
forged_headers = {
  "x-shopify-topic"        => "app/uninstalled",           # different registered topic
  "x-shopify-hmac-sha256"  => real_hmac_base64,             # UNCHANGED, still valid for real_body
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com",  # forged tenant
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: real_body, headers: forged_headers)

# HmacValidator.validate(request) => true, because it only checks real_body against real_hmac.
ShopifyAPI::Webhooks::Registry.process(request)
# => dispatches "app/uninstalled" handler with WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
```
`Utils::HmacValidator.validate` at [5](#0-4)  returns `true` for the forged request because it only re-derives the signature from `raw_body`, never from `shop`/`topic`, confirming the missing binding.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
