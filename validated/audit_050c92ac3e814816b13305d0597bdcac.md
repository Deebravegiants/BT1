### Title
Webhook `shop-domain` header is trusted as tenant identity despite not being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies the webhook HMAC before dispatching to the app's handler, but the HMAC only signs the raw request body. The `shop` value used to identify the tenant for the handler is read from the unauthenticated `X-Shopify-Shop-Domain` HTTP header and is never covered by the signature check, breaking the binding `hmac_verified_bytes == identity_used_bytes`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived purely from the `shopify-shop-domain` / `x-shopify-shop-domain` header, independent of the signed body: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC (which only attests to the body bytes) and then unconditionally forwards `request.shop` — a header value with no cryptographic binding to the verified payload — to the handler as the tenant identity: [4](#0-3) 

Because HTTP headers are attacker-controllable at the transport layer up to the app's own routing/framework (and this gem performs no cross-check between the header and any signed field), an attacker who can produce a validly-signed body for their own shop (e.g., replaying/crafting a webhook payload where the body itself contains no shop identifier, such as `customers/data_request` or generic topics) can pair it with an arbitrary `shop-domain` header. The identity the host application ultimately uses to route/process the webhook (`WebhookMetadata#shop`) is thus not what was actually authenticated by the HMAC.

### Impact Explanation
If the webhook body payload does not itself redundantly encode the shop domain (many Shopify webhook topics do include a shop id inside the JSON body, but this is host-application-dependent and not enforced by this gem), an attacker capable of triggering or replaying a validly-HMAC'd webhook could get the gem to attribute the event to a different shop than the one whose secret validated it, via a `Request` built from attacker-influenced headers. This crosses the cross-tenant boundary the gem's `WebhookMetadata` handoff is meant to preserve.

### Likelihood Explanation
Likelihood is limited: exploitation requires the host application's web framework to expose header values to the attacker at the point `Request.new` is constructed, and requires a scenario where the attacker already possesses (or can replay) a validly-signed payload for their own tenant. This gem does not fetch or normalize headers from a raw socket — it relies entirely on whatever `headers` hash the host application passes in — but the gem itself performs zero validation that the `shop-domain` header is consistent with the signed body, which is the root cause within this gem's own code.

### Recommendation
Bind the `shop` field into the signed payload verification, or explicitly document/require that `Request#shop` must never be trusted for authorization decisions absent additional server-side verification (e.g., comparing against the shop stored for the session/webhook subscription id). At minimum, `Registry.process` should not pass an HMAC-unverified header value as the authoritative tenant identity to `WebhookMetadata` without the host being warned this field is unauthenticated.

### Proof of Concept
1. Host application receives a webhook POST and builds `ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: headers)` per `lib/shopify_api/webhooks/request.rb`.
2. Attacker (with ability to influence `headers` passed to the constructor, e.g. via a misconfigured proxy/framework that forwards attacker headers, or via a topic whose body carries no shop-identifying field) sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` while the body is a validly HMAC-signed payload for the attacker's own shop.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` which only checks `request.to_signable_string` (the raw body) against the HMAC — line `lib/shopify_api/webhooks/registry.rb:190`.
4. Validation passes; `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` is invoked with `shop` read straight from the untrusted header — `lib/shopify_api/webhooks/registry.rb:198-199` — causing the handler to act as though the event belongs to `victim-shop.myshopify.com`.
