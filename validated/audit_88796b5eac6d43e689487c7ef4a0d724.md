### Title
Webhook `shop` (and `topic`) header is not covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from unauthenticated HTTP headers. `Utils::HmacValidator.validate` verifies the HMAC exclusively over that body-only string, so the `shop` value dispatched to the app's handler is never bound to the HMAC that authenticates the webhook.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which returns only `@raw_body`. Meanwhile `shop` is parsed straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the signature: [2](#0-1) 

`HmacValidator.validate` computes and compares the signature only against `verifiable_query.to_signable_string`: [3](#0-2) 

`Registry.process` accepts the request once this body-only HMAC check passes, then forwards the caller-supplied, unauthenticated `request.shop` (and `request.topic`) straight into `WebhookMetadata` given to the app's handler: [4](#0-3) [5](#0-4) 

Because `shop` is never part of the signed payload, the equality the app relies on — "the shop that produced a validly-HMAC'd webhook" == "the shop attributed to the resulting `WebhookMetadata`" — does not hold. An attacker who can obtain any single validly-signed webhook body/HMAC pair for the app (e.g., from their own store's legitimately delivered webhook, which is fully attacker-controlled/observable) can replay that exact `body`+`hmac-sha256` value to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` still succeeds (it only checks the body), and the handler receives `WebhookMetadata` claiming to be from the victim shop.

### Impact Explanation
Any app that uses `WebhookMetadata#shop` to select which tenant's records to create/update/redact (a documented, intended use of this field) can be made to apply another shop's webhook payload under a spoofed shop identity, or apply the same replayed data across multiple shops. This crosses the tenant boundary the gem is documented to protect via HMAC verification, matching the "cross-tenant access" impact bucket.

### Likelihood Explanation
Likelihood is moderate-to-high: exploitation requires the attacker to have at least one legitimately delivered webhook with a matching body/HMAC (trivial to obtain by installing the app on their own development/test store, since bodies and HMACs are visible to the receiving shop), and then to POST that same body/HMAC pair with a forged `shopify-shop-domain` header to the app's public webhook endpoint. No possession of `api_secret_key` or any token is required — only observation of one's own legitimately-received webhook traffic.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signed/verifiable string (or otherwise cryptographically bind them, e.g. by requiring the app to independently verify `shop` against its own session store using a value derived from the HMAC-covered body) so header spoofing cannot decouple the authenticated payload from the attributed shop.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and receives a real webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `client_secret`), `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the exact same `B` and `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Webhooks::Request.new` parses `shop` as `victim.myshopify.com` from the header (`shopify_header("shop-domain")`), while `to_signable_string` still equals `B`.
4. `HmacValidator.validate` recomputes HMAC over `B` and it matches `H`, so validation passes (`Registry.process` proceeds).
5. `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` is delivered to the app's handler, which now processes attacker-controlled data attributed to the victim tenant.
