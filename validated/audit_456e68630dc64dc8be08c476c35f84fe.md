### Title
`update_token`'s `remove_chains` (and chain re-registration in `add_chains`) deletes `ContractToAsset`/`Precisions` with no event and no grace period, permanently freezing in-flight `send()` escrow/burn on timeout - ([File: modules/pallets/hyper-fungible-token/src/lib.rs])

### Summary
`pallet_hyper_fungible_token::update_token` lets `CreateOrigin` add or remove a chain's contract mapping for a registered asset. When a chain is removed (or re-added with a new contract address), the pallet immediately deletes the `ContractToAsset` and `Precisions` entries for that `(StateMachine, asset)` pair, with no event emitted and no delay for in-flight messages to settle. Any `send()` transfer that escrowed or burned tokens against the old configuration, and that later times out, will hit `on_timeout`'s `ContractToAsset::get(dest, &to)` lookup and fail permanently, because the entry no longer exists. The escrowed/burned funds can never be refunded to the original sender.

### Finding Description
`send()` is a fully permissionless, signed extrinsic that escrows the native asset (or burns/transfers a non-native asset) and dispatches a cross-chain `DispatchPost` keyed by the current `TokenContracts`/`Precisions` configuration for the destination chain: [1](#0-0) 

If governance later calls `update_token` to remove that chain (or reassign the chain to a new contract address), the mapping used to resolve the asset on `on_timeout` is deleted immediately, with no event and no waiting period for requests dispatched before the change: [2](#0-1) 

`on_timeout` is the only path that refunds the escrowed/burned funds back to the sender when a previously dispatched `send()` request fails to be delivered in time. It re-derives the asset via the exact same `ContractToAsset` map keyed on `(dest, to)`: [3](#0-2) 

If `ContractToAsset::get(dest, &to)` returns `None` (because the entry was removed by `update_token` after the `send()` was dispatched but before it timed out), `on_timeout` returns `HftError::UnknownContractOnTimeout` and reverts — the ISMP timeout handling is unable to complete, so escrowed native tokens sitting in `Pallet::pallet_account()` or already-burned non-native tokens are never returned to the sender. Even if the lookup succeeds because the same contract bytes are still associated with a *different* asset after a reconfiguration, `Precisions::get` for the removed pairing is also gone, causing `HftError::DecimalsNotConfigured` and the same permanent failure.

This mirrors the reported bug class precisely: an administrative action removes configuration that active in-flight ("in-escrow") state depends on, with no emitted event and no grace period for users to react or unwind their position, and unlike `TokenRegistered`, `update_token` emits no event at all so this state exists silently.

### Impact Explanation
Any user with a `send()` transfer in flight (dispatched, but not yet delivered or timed out) at the moment `update_token` removes or reconfigures that chain permanently loses access to their refund path. The escrowed/burned funds become unrecoverable since `on_timeout` is the only settlement route for a failed/timed-out post and it hard-fails on the missing mapping. This is a permanent freezing of user funds triggered by a routine, non-malicious governance operation (deprecating or migrating a chain's contract address), not requiring any attacker.

### Likelihood Explanation
`update_token` is a normal, expected operational call (e.g., migrating to a new EVM contract deployment or deprecating a chain) that the pallet's own README documents as a supported extrinsic. Any user transaction submitted shortly before such an update is silently exposed, with no on-chain signal (no event) warning them to avoid using the affected chain, and no mechanism to drain or migrate in-flight requests before the mapping disappears.

### Recommendation
- Emit an event (e.g., `TokenChainRemoved { asset_id, chain }`) whenever `update_token` removes or reassigns a chain mapping.
- Do not hard-delete `ContractToAsset`/`Precisions` for a chain while requests dispatched against the old configuration may still be outstanding; instead, retain historical mappings (or a deprecation window keyed by commitment/timeout) so `on_timeout` can still resolve the asset and refund correctly.
- Alternatively, have `on_timeout` fall back to decoding the asset from data embedded in the original request rather than a live, mutable storage lookup, so later administrative changes cannot invalidate already-escrowed funds.

### Proof of Concept
1. Governance registers asset `X` for `StateMachine::Evm(1)` via `register_token`, setting `TokenContracts`, `ContractToAsset`, and `Precisions`.
2. Alice calls `send()` for asset `X` to `StateMachine::Evm(1)`; her tokens are escrowed/burned and a `DispatchPost` is created with a timeout.
3. Before delivery/timeout, governance calls `update_token` with `remove_chains = [StateMachine::Evm(1)]` (a routine, non-malicious chain deprecation). `ContractToAsset` and `Precisions` for `(Evm(1), X)` are deleted; no event is emitted.
4. Alice's request times out. `on_timeout` calls `ContractToAsset::get(dest, &to)`, gets `None`, and returns `HftError::UnknownContractOnTimeout`.
5. Alice's escrowed/burned funds are never refunded — permanently frozen, with no prior warning since no event was emitted at step 3.

	fn on_timeout(&self, request: Request) -> Result<Weight, anyhow::Error> {
		match request {
			Request::Post(PostRequest { body, to, dest, .. }) => {
				let message = Message::abi_decode(&body).map_err(HftError::DecodeError)?;

				// Refund the original sender
				let from_bytes = message.from.as_ref();
				let mut sender_bytes = [0u8; 32];
				if from_bytes.len() == 32 {
					sender_bytes.copy_from_slice(from_bytes);
				} else if from_bytes.len() == 20 {
					sender_bytes[12..].copy_from_slice(from_bytes);
				} else {
					Err(HftError::InvalidSenderLength(from_bytes.len()))?
				}
				let beneficiary: T::AccountId = sender_bytes.into();

				// Look up the asset from the destination contract address
				let local_asset_id = ContractToAsset::<T>::get(dest, &to)
					.ok_or(HftError::UnknownContractOnTimeout)?;

				let decimals = if local_asset_id == T::NativeAssetId::get() {
					T::Decimals::get()
				} else {
					<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(
						local_asset_id.clone(),
					)
				};
				let erc_decimals = Precisions::<T>::get(local_asset_id.clone(), dest)
					.ok_or(HftError::DecimalsNotConfigured(dest))?;
