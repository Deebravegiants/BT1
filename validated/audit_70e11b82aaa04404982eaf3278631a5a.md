Audit Report

## Title
GraphQL `updateUserPassword` mutation allows setting an empty/weak password with no complexity validation - ([File: core/web/resolver/mutation.go])

## Summary
`Resolver.UpdateUserPassword` in `core/web/resolver/mutation.go` validates only that the supplied old password matches, then passes `args.Input.NewPassword` directly to `SetPassword` with no call to `utils.VerifyPasswordComplexity` or `sessions.ValidateAndHashPassword`. The underlying `localauth.orm.SetPassword` simply hashes and stores whatever string is given, so an authenticated user can set their password to an empty string or any trivially weak value via GraphQL, while the equivalent REST endpoint correctly rejects such input.

## Finding Description
`core/web/resolver/mutation.go` lines 934-970 implement the resolver: it authenticates the session, checks the old password with `utils.CheckPasswordHash`, calls `ClearNonCurrentSessions`, and then calls `r.App.AuthenticationProvider().SetPassword(ctx, &dbUser, args.Input.NewPassword)` — no complexity check exists anywhere in this file (confirmed via repo-wide search: `VerifyPasswordComplexity` appears only in `core/web/user_controller.go`, `core/sessions/user.go`, `core/utils/password.go`, `core/cmd/key_store_authenticator.go`, and `core/config/toml/types.go` — never in `core/web/resolver/`). [1](#0-0) 

The GraphQL schema only enforces `newPassword: String!` (non-null), which does not block an empty string. [2](#0-1) 

The local-auth `SetPassword` implementation performs no validation — it hashes and stores the value unconditionally. [3](#0-2) 

By contrast, the REST controller `UserController.UpdatePassword` calls `utils.VerifyPasswordComplexity(request.NewPassword, user.Email)` and returns `422` on failure before ever calling `SetPassword`. [4](#0-3) 

`VerifyPasswordComplexity` enforces a minimum length (`MinRequiredLen`) among other rules, which alone would reject an empty password, but this function is never reached on the GraphQL path. [5](#0-4) 

The existing resolver unit test (`core/web/resolver/user_test.go`, `TestResolver_UpdateUserPassword`) exercises the success/failure paths (old-password mismatch, session-clear failure, `SetPassword` failure) but contains no test case asserting rejection of a short/empty `newPassword`, confirming there is no validation logic to test.

## Impact Explanation
Any authenticated user (any role) who knows their own current password can set their password to an empty string or a trivially weak value through the GraphQL API, bypassing the complexity/length policy enforced elsewhere in the codebase. This weakens account authentication for that account and could facilitate self-lockout or a weaker credential that's easier to brute-force/guess in future attacks. This maps to the "node API authentication" impact category, though the severity is limited to self-inflicted weakening of the actor's own account — it does not by itself allow escalation to another user's account or bypass of another security boundary.

## Likelihood Explanation
Highly reachable: it requires only a valid authenticated GraphQL session and knowledge of the user's own current password — no elevated privileges, race conditions, or special setup. Any node operator user reaching the Operator UI/GraphQL API can trigger it in one mutation call.

## Recommendation
Add the same complexity validation used in the REST controller to `Resolver.UpdateUserPassword` — call `utils.VerifyPasswordComplexity(args.Input.NewPassword, dbUser.Email)` (or reuse `sessions.ValidateAndHashPassword`) before invoking `SetPassword`, and return an `InputErrors` payload on failure, matching the REST behavior in `core/web/user_controller.go`.

## Proof of Concept
1. Authenticate as any existing user and obtain a valid GraphQL session cookie.
2. Send:
```graphql
mutation {
  updateUserPassword(input: { oldPassword: "<correctCurrentPassword>", newPassword: "" }) {
    ... on UpdatePasswordSuccess { user { email } }
    ... on InputErrors { errors { path message code } }
  }
}
```
3. Observe `UpdatePasswordSuccess` is returned and the account's `hashed_password` is now the hash of an empty string, whereas `PATCH /v2/user/password` with the same body returns `422 Unprocessable Entity` due to `VerifyPasswordComplexity`.
4. Add a Go test case to `core/web/resolver/user_test.go` mirroring the existing "success" case but with `newPassword: ""`, asserting the mutation currently succeeds — proving the missing validation.

func VerifyPasswordComplexity(password string, disallowedStrings ...string) (merr error) {
	errMsg := ErrMsgHeader
	var stringErrs []string

	if LeadingWhitespace.MatchString(password) || TrailingWhitespace.MatchString(password) {
		stringErrs = append(stringErrs, ErrWhitespace.Error())
	}

	if len(password) < MinRequiredLen {
		stringErrs = append(stringErrs, fmt.Sprintf("password is less than %d characters long", MinRequiredLen))
	}

	for _, s := range disallowedStrings {
		if strings.Contains(strings.ToLower(password), strings.ToLower(s)) {
			stringErrs = append(stringErrs, fmt.Sprintf("password may not contain: %q", s))
		}
	}

	if len(stringErrs) > 0 {
		for _, stringErr := range stringErrs {
			errMsg = fmt.Sprintf("%s	%s\n", errMsg, stringErr)
		}
		merr = errors.New(errMsg)
	}

	return
}
