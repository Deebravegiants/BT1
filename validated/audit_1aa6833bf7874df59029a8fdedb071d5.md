### Title
Webhook `shop` (and other Shopify headers) are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies only that the raw request *body* matches the HMAC signature; the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers used to attribute the webhook to a specific merchant are never included in the signed payload.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `HmacValidator.validate` computes/compares the HMAC exclusively against that string: [1](#0-0) 

The `shop` accessor used by the registry to build `WebhookMetadata` (the value handed to the app's handler to identify which merchant the payload belongs to) is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed bytes: [2](#0-1) 

`Registry.process` validates the HMAC and then dispatches to the handler using `request.shop` taken from that unverified header: [3](#0-2) 

This breaks the identity binding the rules describe as "a field acted on but not covered by the HMAC": the equality the gem should enforce is `shop_used_by_handler == shop_that_Shopify_actually_sent_the_event_for`, but the gem only proves `hmac_bytes == HMAC(secret, raw_body)`. Because `shop` (and `topic`, `webhook-id`, `api-version`) live outside `raw_body`, any request whose body carries a valid HMAC (e.g. one legitimately issued to the attacker's own shop) can be replayed to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain, and `HmacValidator.validate` will still return `true`.

### Impact Explanation
If the host application (as documented in `docs/usage/webhooks.md` and intended by this gem's API) uses `WebhookMetadata#shop` to look up/update per-tenant records (orders, inventory, customer data, session state, etc.) keyed by shop domain, an unprivileged internet user who is a legitimate merchant of their own installed shop can trigger a valid HMAC-signed webhook body (by performing an action Shopify webhooks fire for, e.g. updating one of their own orders) and then submit that untouched body with a forged `shop-domain` header pointing at a victim shop. The gem accepts it as authentic, causing cross-tenant data confusion/corruption in the host application driven entirely by this gem's verification logic.

### Likelihood Explanation
Exploitation only requires: (1) the attacker's own shop must have the app installed (a normal, unprivileged merchant relationship — no leaked credentials, no access token, no `api_secret_key` needed), and (2) the ability to send an arbitrary HTTP POST with custom headers to the app's public webhook endpoint, which is by definition internet-reachable. No cryptographic secret needs to be obtained; the attacker reuses a signature Shopify itself computed for their own legitimate event.

### Recommendation
Bind the shop identity (and topic/webhook-id) into the value verified by `HmacValidator`, e.g. by having `Webhooks::Request#to_signable_string` incorporate the `shop-domain` header (or otherwise cross-checking that the HMAC-signed body's shop-identifying content matches the header) so a signature valid for one shop's payload cannot be replayed under a different shop's identity.

### Proof of Concept
1. Attacker's own shop `attacker.myshopify.com` has the vulnerable app installed and legitimate webhooks enabled.
2. Attacker performs an action that causes Shopify to POST a real webhook to the app, e.g. body `{"id":1,...}` with header `X-Shopify-Shop-Domain: attacker.myshopify.com` and a correctly computed `X-Shopify-Hmac-Sha256`.
3. Attacker captures this raw request, then re-sends it to the app's webhook endpoint unmodified except for `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, raw_body)`—unaffected by the header change—so validation succeeds (`lib/shopify_api/webhooks/registry.rb:190`).
5. The handler receives `WebhookMetadata(shop: "victim.myshopify.com", body: <attacker's data>, ...)`, and any host logic keyed on `shop` now attributes/mutates attacker-controlled data under the victim tenant.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
