## Analog Vulnerability Found

### Title
Unprivileged front-running of `Initialize2` allows an attacker to permanently squat a market's deterministic pool address and set an arbitrary initial price - (File: `program/src/processor.rs`)

### Summary
Like the CompliFi `Vault.initialize` issue, Raydium's `process_initialize2` is a callable-by-anyone instruction that finalizes a pool's economic state (its initial coin/pc reserve ratio) without any access control tying the call to a specific authorized deployer. Because every AMM-related account (`AmmInfo`, LP mint, coin vault, pc vault, target orders) is derived as a deterministic PDA solely from the `market_account` pubkey, there can only ever be **one** legitimate pool per market. An attacker who front-runs the intended creator's `Initialize2` transaction permanently claims that address and can set the initial `init_coin_amount`/`init_pc_amount` ratio to whatever benefits them.

### Finding Description
`process_initialize2` derives all pool accounts using `get_associated_address_and_bump_seed`, which seeds solely off `program_id` and `market_account.key`: [1](#0-0) 

This is used to compute the addresses for the AMM account, LP mint, coin vault, pc vault, and target orders inside `process_initialize2`: [2](#0-1) 

Any signer supplying their own coin/pc token accounts can call `Initialize2` for any market — there is no check that the caller is the intended/authorized project creator, and no check that `init_coin_amount`/`init_pc_amount` reflect a fair or expected price: [3](#0-2) 

The only economic guard is that the resulting LP amount must exceed the minimum-liquidity lock, which prevents a zero/near-zero share attack but does nothing to prevent an arbitrary, heavily skewed price ratio: [4](#0-3) 

Because the pool address is fully deterministic from the market key, once one caller succeeds, all subsequent `Initialize2` attempts for the same market permanently fail with `AlreadyInUse`/`RepeatCreateAmm`: [5](#0-4) [6](#0-5) 

This exactly mirrors the CompliFi finding: a permissionless, front-runnable "finalize state" call that lets an attacker set the economically meaningful initialization parameter (there: `_underlyingStarts`; here: the initial coin/pc reserve ratio) before the intended, careful creator's transaction lands.

### Impact Explanation
Since the initial reserve ratio directly sets the AMM's starting spot price, an attacker who front-runs `Initialize2` for a known upcoming market can:
- Seed the pool with a heavily skewed price (subject only to the dust-level minimum liquidity check), taking on minimal capital risk while claiming the deterministic pool address permanently for that market.
- Cause the legitimate project's own `Initialize2` transaction to revert (`RepeatCreateAmm`/`AlreadyInUse`), since the account addresses are fixed by the market seed and cannot be recreated elsewhere.
- Leave unsuspecting LPs/swappers who trust "the pool for market X" to deposit or swap against an artificially mispriced pool: depositors get diluted at the wrong ratio (`Deposit` prices new liquidity off the current, attacker-set ratio) and swappers suffer bad execution, directly transferring value to the attacker who holds the (near-)totality of the initial LP supply.
- This is a permanent condition for that market — there is no recovery path since a second, correctly-priced pool cannot be created at that PDA.

### Likelihood Explanation
Any party (bot or MEV searcher) monitoring the mempool for `Initialize2` transactions referencing a not-yet-initialized market can trivially front-run it with their own signer and arbitrary `init_coin_amount`/`init_pc_amount`, using their own token accounts — no special privileges, protocol-config, or non-default configuration are required. Market/pool creation is by design intended to be a public, unprivileged action, so this path is fully within the "pool creator" reachable surface.

### Recommendation
- Bind pool creation to an authorized/whitelisted creator (e.g., via `AmmConfig` sign-off) rather than allowing arbitrary signers to determine the final PDA’s initial price.
- Alternatively, add a price-sanity check against an external reference (oracle or a required minimum ratio bound configured by governance) before allowing `Initialize2` to finalize the pool, so the initial ratio cannot be set arbitrarily by whichever party lands their transaction first.
- Document clearly for integrators that a pool's existence for a market is not proof of a fair-priced pool, and require verification of initial reserves before treating a newly observed pool as canonical for a token pair.

### Proof of Concept
1. Project team broadcasts a transaction calling `initialize2` (per `program/src/instruction.rs` builder) for `market M` with a fair `init_coin_amount`/`init_pc_amount` ratio, signed by their wallet with legitimate token balances.
2. Attacker observes the pending transaction (same `market_info` = `M`), and submits their own `Initialize2` transaction referencing the same market with higher priority fee, but with a heavily skewed `init_coin_amount`/`init_pc_amount` (e.g., depositing dust of coin against a large amount of pc, or vice versa), using their own token accounts.
3. Attacker's transaction lands first: `generate_amm_associated_account`/`generate_amm_associated_spl_mint`/`generate_amm_associated_spl_token` create the PDA-derived `AmmInfo`, LP mint, coin vault, and pc vault (seeded only by `market M`), and `amm.initialize(...)` sets the pool live at the attacker-chosen ratio; attacker receives nearly all initial LP tokens.
4. The legitimate project's transaction now fails with `RepeatCreateAmm`/`AlreadyInUse` since the deterministic accounts already exist and are owned/initialized.
5. The market now has a permanently mispriced canonical pool. Any user who later calls `Deposit`, `SwapBaseIn`, or `SwapBaseOut` against this pool trades or provides liquidity at the attacker's artificial ratio, transferring value to the attacker who holds the dominant LP position.
