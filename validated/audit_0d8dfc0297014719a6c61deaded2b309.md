## Analog Found

### Title
Fixed `per_receipt_storage_proof_size_limit` vs. unbounded account state growth can permanently brick an account's ability to transact - (File: `runtime/runtime/src/lib.rs`)

### Summary
The Sherlock report describes a class of bug where an **immutable, protocol/config-level limit** (`maxSigners`) is checked against a **mutable, growable piece of state** (valid signer count) on every single interaction with the contract. Once normal, unprivileged activity (hat minting) pushes the mutable value past the immutable limit, every subsequent transaction reverts and the contract is permanently bricked, with no way to lower the mutable value because doing so itself requires a transaction that reverts.

The same shape exists in nearcore's `per_receipt_storage_proof_size_limit`: a fixed, protocol-wide constant (not configurable per account) is checked against the storage proof an account's *own* trie subtree generates during execution. Because accounts can grow their own contract state or access-key set through ordinary, unprivileged use, it is possible for the amount of trie proof required merely to touch that account's state to exceed the hard limit, at which point every receipt touching that state — including remedial actions — fails deterministically and permanently.

### Finding Description
`per_receipt_storage_proof_size_limit` is a fixed field of `LimitConfig` [1](#0-0)  baked into the versioned `RuntimeConfig` and not adjustable per account.

During receipt application, `EnforcePerReceiptStorageProofLimit`/`EnforceStorageProofLimitForAllActions` measure the storage proof recorded while executing a receipt's actions and, once it exceeds the fixed limit, fail the receipt with `ReceiptStorageProofSizeExceeded` — the check runs across **all** actions in the receipt, not just the one that pushed the proof over the limit: [2](#0-1) 

This mirrors `reconcileSignerCount`'s `validSignerCount <= maxSigners` check that runs on every `checkTransaction` pre-flight: a hard limit set independently of the account, evaluated on every interaction with the account's own growing state.

The `RecordedStorageCounter` used inside the VM enforces the same fixed limit for `FunctionCall` actions specifically: [3](#0-2) .

Crucially, the amount of proof required to touch an account's own state is a function of that account's own storage footprint (contract data size, access-key subtree depth/width), which grows through ordinary, unprivileged transactions over time (deploying larger contracts, writing more data, adding access keys). Nothing in the design lets a signer or the account owner raise this limit for their account, and — as with `maxSigners` — the value is uniform and immutable once set for the protocol version.

The existing regression test demonstrates the mechanism directly: a receipt that first performs a large legitimate read and then attempts unrelated `AddKey` actions fails the *entire receipt*, including the `AddKey`s, once the cumulative recorded proof exceeds the limit: [4](#0-3) 

The project's own documentation acknowledges that trie removals inflate recorded proof (each removal is estimated at ~2000 extra bytes for accounting purposes), meaning that *shrinking* an account's state (e.g., via `DeleteKey`/`DeleteAccount`) to get back under the limit can itself cost more proof than a normal read of the same size: [5](#0-4) 

If an account's own on-trie footprint is such that even minimal necessary reads (e.g., loading contract code/state to run any method, or walking the access-key subtree to process an `AddKey`/`DeleteKey`) already generate proof close to `per_receipt_storage_proof_size_limit` (4 MB in the current config), **any further receipt touching that account is doomed to fail with `ReceiptStorageProofSizeExceeded` forever**, including receipts meant to reduce that footprint (`DeleteKey`, `DeleteAccount`), because those removal actions run in the same receipt whose earlier actions already consumed most of the budget, and because removals themselves cost proof.

### Impact Explanation
An account whose state naturally grows (through legitimate contract use, adding access keys, or large stored values) past the point where touching its own state generates more than the fixed per-receipt storage proof limit becomes **permanently unable to execute any receipt against it** — the same "safe accounts unable to execute any transaction" impact described in M-13. Because the limit is fixed by protocol version and cannot be raised for a specific account, and because reducing the offending state requires a receipt that is itself subject to the same limit, the account (and any balance locked in it) can become permanently unreachable, a lock of funds/state analogous to bricking the Safe.

### Likelihood Explanation
This requires an account to accumulate enough of its own trie footprint (contract storage or access-key tree) that touching it during normal execution already nears the 4 MB hard limit — a state that is reachable purely through unprivileged, normal transaction activity (deploying/growing a contract's data, adding many access keys), with no malicious node or validator involvement required. It does not require an attacker; it can occur as an unintended consequence of legitimate usage, exactly as in M-13 where the bricking condition arose from ordinary hat-minting activity rather than an attack.

### Recommendation
- Allow receipts that exceed the storage-proof limit to still process actions that reduce the account's footprint (e.g., prioritize/permit `DeleteKey`/`DeleteAccount` even when the proof-size budget for the receipt is exhausted), or split remedial actions into a dedicated, budget-exempt path.
- Alternatively, track storage-proof consumption per *pre-existing* account footprint versus *newly touched* data, so that unavoidable proof needed just to reach an account's own state doesn't count against the same budget as arbitrary reads, preventing a scenario where merely loading an account's necessary state exhausts the entire per-receipt limit.
- Add safeguards/documentation warning contract authors when an account's storage footprint approaches a size where routine calls risk exceeding `per_receipt_storage_proof_size_limit`, and provide an accounts-level escape hatch (e.g., a governance-gated force-delete/reset path) for stuck accounts.

### Proof of Concept
The existing test `test_add_keys_after_large_read_exceed_receipt_storage_proof_limit` already demonstrates the core mechanism: a receipt performing a large (but legitimate) read followed by `AddKey` actions fails the whole receipt, including the `AddKey`s, once the cumulative recorded storage proof crosses the fixed limit [6](#0-5) . Extending this scenario to a `DeleteKey`/`DeleteAccount` action in place of `AddKey`, on an account whose pre-existing state alone already requires proof close to the limit just to be read/traversed, would show that the account can no longer be cleaned up or recovered, matching the "permanently bricked, unable to execute any transaction" impact of M-13.

```rust
    /// Update the latest observed storage proof size and check if it exceeds the limit.
    /// Should be called after every trie operation.
    pub fn observe_size(&mut self, latest_storage_proof_size: usize) -> Result<(), VMLogicError> {
        self.last_observed_storage_size = latest_storage_proof_size;

        let current_size = self.get_storage_size()?;
        if current_size > self.size_limit {
            let limit_u64 = self.size_limit.try_into().map_err(|_| {
                VMLogicError::InconsistentStateError(InconsistentStateError::IntegerOverflow)
            })?;
            return Err(VMLogicError::HostError(HostError::RecordedStorageExceeded {
                limit: ByteSize::b(limit_u64),
            }));
        }

        Ok(())
    }
```

```rust
#[test]
fn test_add_keys_after_large_read_exceed_receipt_storage_proof_limit() {
    const NUM_VALUES: u8 = 4;
    // Part of the limit the values leave free. The read's trie nodes fit in it; the
    // `AddKey` actions that follow do not.
    const RESERVED_UNDER_LIMIT: usize = 1_000;
    // Keys `alice` already holds, enough to fill one branch of the access key subtree. An
    // `AddKey` records the subtree nodes its lookup walks that no earlier one did.
    const NUM_EXISTING_KEYS: usize = 16;
    const NUM_ADDED_KEYS: usize = 6;
    const ACTION_GAS: Gas = Gas::from_teragas(100);

    assert!(ProtocolFeature::EnforceStorageProofLimitForAllActions.enabled(PROTOCOL_VERSION));
    let feature_version = ProtocolFeature::EnforceStorageProofLimitForAllActions.protocol_version();

    let shard_uid = ShardUId::single_shard();
    let existing_signers = (0..NUM_EXISTING_KEYS)
        .map(|i| {
            Arc::new(InMemorySigner::from_seed(
                alice_account(),
                KeyType::ED25519,
                &format!("existing{i}"),
            ))
        })
        .collect();
    let (runtime, tries, root, mut apply_state, signers, epoch_info_provider) =
        setup_runtime_with_keys(
            vec![(alice_account(), existing_signers)],
            Balance::from_near(1_000_000),
            Balance::ZERO,
            Gas::from_teragas(1_000),
        );
    let account = alice_account();
    let signer = signers[0].clone();
    let limit = apply_state.config.wasm_config.limit_config.per_receipt_storage_proof_size_limit;
    let value_size = (limit - RESERVED_UNDER_LIMIT) / NUM_VALUES as usize;

    let apply_receipt = |apply_state: &ApplyState, root: CryptoHash, receipt: &Receipt| {
        let apply_result = runtime
            .apply(
                tries.get_trie_for_shard(shard_uid, root).recording_reads_new_recorder(),
                &None,
                apply_state,
                std::slice::from_ref(receipt),
                SignedValidPeriodTransactions::empty(),
                &epoch_info_provider,
                Default::default(),
            )
            .unwrap();
        let status = apply_result
            .outcomes
            .iter()
            .find(|outcome| outcome.id == *receipt.receipt_id())
            .expect("receipt outcome should be present")
            .outcome
            .status
            .clone();
        (apply_result, status)
    };

    // Setup: deploy the contract, then write the values the receipt reads back.
    let setup_receipt = create_receipt_with_actions(
        account.clone(),
        signer.clone(),
        std::iter::once(Action::DeployContract(DeployContractAction {
            code: near_test_contracts::rs_contract().to_vec(),
        }))
        .chain((0..NUM_VALUES).map(|key| {
            let mut args = vec![key];
            args.extend_from_slice(&(value_size as u32).to_le_bytes());
            Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "write_value_of_size".to_string(),
                args,
                gas: ACTION_GAS,
                deposit: Balance::ZERO,
            }))
        }))
        .collect(),
    );
    let (apply_result, setup_status) = apply_receipt(&apply_state, root, &setup_receipt);
    assert_matches!(setup_status, ExecutionStatus::SuccessValue(_));
    let root = commit_apply_result(&apply_result, &mut apply_state, &tries, shard_uid);

    let read_action = Action::FunctionCall(Box::new(FunctionCallAction {
        method_name: "read_values_in_key_range".to_string(),
        args: vec![0, NUM_VALUES],
        gas: ACTION_GAS,
        deposit: Balance::ZERO,
    }));
    let added_keys: Vec<PublicKey> = (0..NUM_ADDED_KEYS)
        .map(|i| {
            InMemorySigner::from_seed(account.clone(), KeyType::ED25519, &format!("added{i}"))
                .public_key()
        })
        .collect();
    let read_receipt =
        create_receipt_with_actions(account.clone(), signer.clone(), vec![read_action.clone()]);
    let read_and_add_keys_receipt = create_receipt_with_actions(
        account.clone(),
        signer,
        std::iter::once(read_action)
            .chain(added_keys.iter().map(|public_key| {
                Action::AddKey(Box::new(AddKeyAction {
                    public_key: public_key.clone(),
                    access_key: AccessKey::full_access(),
                }))
            }))
            .collect(),
    );

    // The read fills the receipt's allowance and still fits, so a real receipt could do it.
    let (_, read_status) = apply_receipt(&apply_state, root, &read_receipt);
    assert_matches!(read_status, ExecutionStatus::SuccessValue(_));

    // Before the feature version only the `FunctionCall` is bounded, so the keys
    // record past the limit unchecked.
    apply_state.current_protocol_version = feature_version - 1;
    let (_, status_before) = apply_receipt(&apply_state, root, &read_and_add_keys_receipt);
    assert_matches!(status_before, ExecutionStatus::SuccessValue(_));

    apply_state.current_protocol_version = PROTOCOL_VERSION;
    let (apply_result, status_after) =
        apply_receipt(&apply_state, root, &read_and_add_keys_receipt);
    let action_error = assert_matches!(
        status_after,
        ExecutionStatus::Failure(TxExecutionError::ActionError(action_error)) => action_error
    );
    assert_eq!(
        action_error.kind,
        ActionErrorKind::ReceiptStorageProofSizeExceeded { limit: limit as u64 }
    );
    let failed_index = action_error.index.unwrap();
    assert!(failed_index > 0, "receipt should fail on an `AddKey`, not on the read");

    let root = commit_apply_result(&apply_result, &mut apply_state, &tries, shard_uid);
    let state = tries.new_trie_update(shard_uid, root);
    for public_key in &added_keys {
        assert_eq!(get_access_key(&state, &account, public_key).unwrap(), None);
    }
}
```

**File:** docs/misc/state_witness_size_limits.md (L27-32)
```markdown
* `per_receipt_storage_proof_size_limit - 4 MB`
  * Executing a receipt generates storage proof. A single receipt is allowed to generate at most 4MB of storage proof. This is a hard limit, receipts which generate more than that will fail.
* `main_storage_proof_size_soft_limit - 4 MB`
  * This is a limit on the total size of storage proof generated by receipts in one chunk. Once receipts generate more storage proof than this limit, the chunk producer stops processing receipts and moves the rest to the delayed queue.
  * It's a soft limit, which means that the total size of storage proof could reach 8 MB (3.99MB + one receipt which generates 4MB of storage proof)
  * Due to implementation details it's hard to find the exact amount of storage proof generated by a receipt, so an upper bound estimation is used instead. This upper bound assumes that every removal generates additional 2000 bytes of storage proof, so receipts which perform a lot of trie removals might be limited more than theoretically applicable.
```
