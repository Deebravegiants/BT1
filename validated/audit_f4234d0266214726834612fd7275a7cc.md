## Analysis Result

The reachable code confirms an unauthenticated-origin impersonation flaw in `pallet-hyper-fungible-token`'s calldata-execution path, which is the closest analog to the CSWeb "arbitrary path input → access to unintended resources" bug class: an attacker-controlled input field is trusted to select the "identity"/"location" used for a privileged operation, without verifying it actually belongs to the caller.

### Title
Unsigned cross-chain calldata dispatches arbitrary runtime calls as an attacker-chosen origin - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`Pallet::on_accept` executes optional `call_data` attached to an incoming `HyperFungibleToken` transfer. When the attacker omits `substrate_data.signature`, the dispatch origin is derived directly and unconditionally from the message's `from` field (or `EvmToSubstrate::convert` of its low 20 bytes), with no proof that the caller who dispatched the cross-chain `send()` on the source chain controls that account.

### Finding Description
In `on_accept`, after crediting `beneficiary`, optional calldata is decoded and dispatched: [1](#0-0) 

When no signature is supplied, the origin used to sign the runtime call is taken straight from the untrusted `message.from` bytes carried in the POST request body: [2](#0-1) 

The call is then dispatched as `RawOrigin::Signed(origin)` — a fully signed, privileged origin — subject only to the runtime's global `BaseCallFilter`, not to any check that this specific caller is authorized to act as that account: [3](#0-2) 

`message` (including `from` and `data`) is ABI-decoded straight from the POST request body, which originates from the paired `HyperFungibleToken`/`WrappedHyperFungibleToken` contract on the source chain: [4](#0-3) 

On the EVM side, `onAccept`/`send` construct and forward this same `Message.from`/`data` pair through `ICallDispatcher(_dispatcher).dispatch(message.data)` without any binding that ties `from` to a proof of ownership beyond being an arbitrary bytes field chosen by whoever calls the cross-chain send function: [5](#0-4) 

This is directly analogous to the CVE-2025-60946 pattern: an authenticated-but-unprivileged actor supplies a "path"/identifier (`from`) that the receiving system trusts implicitly to select a resource (here, an account origin) it doesn't own, instead of validating that the actor actually controls it — exactly as CSWeb trusted an attacker-supplied path to select arbitrary files instead of restricting to the caller's authorized directory.

### Impact Explanation
An unprivileged sender of a cross-chain `HyperFungibleToken` message (which only needs to be a valid, non-zero-value transfer with attacker-chosen `from` bytes and `data`) can cause `pallet-hyper-fungible-token` to dispatch **any** runtime call as `RawOrigin::Signed(arbitrary_account)`, as long as `BaseCallFilter` does not block that call. This is an "unauthorized app action" analog to arbitrary file access — the attacker can impersonate any substrate account (or any EVM-mapped account) whose 20/32-byte identifier they choose to place in `from`, and drive privileged calls (e.g., `Balances::transfer_allow_death`, asset operations, governance-adjacent extrinsics not blocked by the filter) as that account without ever proving key ownership. Concretely this can drain balances/assets or execute other state-mutating calls on behalf of victims — a form of permanent fund loss / unauthorized app action, satisfying the required impact bar.

### Likelihood Explanation
High. No special privilege is needed: any account able to call `send()` on the counterpart `HyperFungibleToken`/`WrappedHyperFungibleToken` EVM contract (or dispatch the equivalent substrate extrinsic) — i.e., an unprivileged "token bridger" — controls the `Message.from` and `data` fields end-to-end. Reaching the vulnerable branch only requires omitting `substrate_data.signature`; the code has no fallback requirement to prove `from` ownership in that branch, so exploitation is a single crafted cross-chain transfer.

### Recommendation
Require a valid signature (or equivalent proof of key ownership) for any `SubstrateCalldata` execution, or otherwise restrict the un-signed path so the dispatch origin can only ever be `beneficiary` (the token recipient of *this* transfer) rather than an arbitrary `from` value; alternatively, drop support for the unsigned/`from`-derived origin entirely and always require the signature check currently performed only in the `Some(signature)` branch.

### Proof of Concept
1. Attacker deploys/uses the standard `HyperFungibleToken` contract flow and calls `send(...)` with `data` containing a SCALE-encoded `SubstrateCalldata { signature: None, runtime_call: <Balances::transfer_allow_death to attacker, value: victim_balance> }`.
2. The `Message.from` field is set to the victim's 20/32-byte account identifier (attacker fully controls this field; it's just bytes passed into the message, not authenticated to be `msg.sender`).
3. On the destination substrate chain, `pallet_hyper_fungible_token::Pallet::on_accept` decodes the message, sees `signature == None`, and computes `origin = T::EvmToSubstrate::convert(H160::from_slice(victim_bytes))` (or direct 32-byte cast for substrate sources).
4. `runtime_call.dispatch(RawOrigin::Signed(origin))` executes the attacker's chosen call (e.g., transferring the victim's balance) as if the victim had signed it — with `BaseCallFilter` as the only barrier and no proof the attacker controls `origin`'s keys. [6](#0-5)
