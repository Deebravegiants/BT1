### Title
Webhook shop/topic identity is not bound by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC over the raw body only, while the `shop`, `topic`, and `webhook_id` values that the registry hands to the app's handler come from unauthenticated HTTP headers that are never part of the signed content. An attacker who can obtain any one validly-signed webhook payload (trivially achievable by installing the target app on a shop they control) can replay that payload to the app's webhook endpoint with the `shop-domain`/`topic` headers swapped, and the signature check still passes.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by recomputing an HMAC over `to_signable_string` and comparing it to the supplied `hmac`: [1](#0-0) 

For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only the raw request body — none of the Shopify-supplied headers are included: [2](#0-1) 

But `shop`, `topic`, and `webhook_id` — the values actually acted upon by the app — are read straight from unauthenticated headers: [3](#0-2) 

`Registry.process` validates only the body HMAC, then immediately hands the header-derived `shop`/`topic`/`webhook_id` to the app's handler as trusted metadata, with no cross-check that these header values were part of what Shopify signed: [4](#0-3) 

This breaks the intended identity binding: **the shop the HMAC was computed for == the shop the handler is told the event belongs to**. Any unprivileged internet user can become "authorized" to receive one validly-signed webhook simply by installing the target public app on a shop they control (no `api_secret_key`, access token, or privileged account needed). They can then replay that captured `raw_body` + `X-Shopify-Hmac-Sha256` to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header for a victim shop's domain — the signature still validates because those headers are outside the signed content.

The documented usage pattern explicitly relies on `data.shop` to route/attribute webhook processing per tenant: [5](#0-4) 

### Impact Explanation
This is a cross-tenant identity-binding break: an attacker-controlled webhook body can be attributed to an arbitrary victim shop domain that the app trusts for tenant routing (e.g., looking up/updating that shop's records, enqueuing per-shop jobs, or deciding which shop's session/store to touch), since nothing in the HMAC ties the header-derived `shop` to the signed payload. This matches the "Critical - cross-tenant access" bucket, because the app is misled into processing attacker-supplied content under another tenant's identity.

### Likelihood Explanation
The prerequisite — obtaining one validly-signed webhook payload — requires no secret or privileged credential: any user can install a public Shopify app on a free/dev store and trigger a webhook-producing event (e.g., `orders/create`) to capture `raw_body` + `hmac`. Replaying it against the app's public webhook endpoint with a modified `shop-domain` header is a trivial HTTP-level operation. The only gating factor is whether the host application actually keys tenant-sensitive logic off `WebhookMetadata#shop`/`#topic`, which is exactly the pattern this gem's own documentation recommends.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed material verified against the HMAC (or otherwise cryptographically bind them to the raw body before trusting them), for example by having `Registry.process` reject requests where the header-derived `shop`/`topic` cannot be cross-validated, or by deriving these values only from body content that is covered by `to_signable_string`. At minimum, update `docs/usage/webhooks.md` to warn implementers that `data.shop`/`data.topic` are not covered by the HMAC signature and must not be trusted for tenant-routing decisions without additional verification (e.g., confirming the shop exists in the app's own session store before acting).

### Proof of Concept
1. Attacker signs up a free development store `attacker-shop.myshopify.com` and installs the target public app (no privileged credentials needed).
2. Attacker triggers an event (e.g. creates an order) causing Shopify to POST a webhook to the app's endpoint with a body `B`, and headers including `X-Shopify-Hmac-Sha256: H = HMAC-SHA256(client_secret, B)` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures `B` and `H` (e.g. via their own logging proxy in front of their own webhook receiver, or via app debug logs if exposed).
4. Attacker sends a new HTTP request directly to the app's public webhook route with the same body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which only checks `H` against `B` — this passes — and then calls the app handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the app to process attacker-controlled content as if it belonged to `victim-shop`.         def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
