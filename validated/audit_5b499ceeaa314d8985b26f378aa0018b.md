### Title
Message/Transaction signer APIs accept a caller-supplied `walletAccount` with no verification that the requester is authorized to use that account - ([File: features/message-signer/src/module/message-signer.ts])

### Summary
The `@exodus/message-signer` and `@exodus/tx-signer` modules expose public signing APIs that take a `walletAccount` parameter (either a `WalletAccount` instance or a plain string account name) and use it directly to select the signing key, without ever checking that the calling context is actually permitted to sign with that specific account. This is the same bug class as the Hegic `exercise()` finding: a resource identifier (option token ID / wallet account) supplied by the caller is used to perform a privileged action (exercise / sign) without verifying the caller's ownership or authorization over that specific resource.

### Finding Description
`MessageSigner.signMessage` resolves the `walletAccount` argument purely by string lookup against `walletAccountsAtom`, with no authorization check tying the request's origin/session to that account: [1](#0-0) 

The public API layer forwards the caller-supplied value unchanged: [2](#0-1) 

The same pattern exists in the transaction signer: the API resolves a string account name to a `WalletAccount` object purely via an atom lookup and passes it straight into `transactionSigner.signTransaction`: [3](#0-2) [4](#0-3) 

Both `signTransaction`/`signMessage` are marked `public: true` module definitions, meaning they are intended to be reachable from outer layers (UI process / SDK consumers) via the RPC bridge described in the architecture (`sdk-rpc`/`json-rpc`, `browser-extension-rpc`). Separately, the wallet does maintain a permission model for third-party dApps — `@exodus/connected-origins` tracks, per origin, whether it is `trusted`, which `connectedAssetName`/`assetNames` it may use, and computes `getConnectedAccounts` for a given origin: [5](#0-4) 

However, this authorization/ownership model is entirely disjoint from the signing modules. Nothing in `message-signer.ts` or `transaction-signer.ts` consults `connectedOrigins` (or any equivalent origin→account binding) to confirm that the `walletAccount` being signed with is one the requesting origin/session is actually connected to. Any code path that can reach `messageSigner.signMessage({ walletAccount, ... })` or `transactionSigner.signTransaction({ walletAccount, ... })` with an arbitrary account name can obtain a signature for any wallet account known to the instance, exactly mirroring the missing-ownership-check pattern in the reported Hegic `exercise()` bug (any account/token identifier supplied by the caller is trusted without checking it belongs to the caller).

### Impact Explanation
If a compromised or malicious RPC caller (e.g. a UI process bug, a rogue background/RPC message, or any component that can invoke the exposed `messageSignerApi`/`transactionSignerApi`) supplies a `walletAccount` belonging to another account than the one it is authorized for, the wallet will produce a valid signature/signed transaction for that other account without any check. This is a direct wallet-compromise-class impact: unauthorized signing on behalf of another account, which could be used to drain funds or execute arbitrary transactions/messages under another account's identity.

### Likelihood Explanation
The `walletAccount` field accepts a plain string that is resolved via a lookup with no origin/session binding, so the missing check is trivially reachable by anything able to invoke `messageSigner.signMessage` / `transactionSigner.signTransaction` with attacker-controlled parameters — the same low-friction pattern that made the original `exercise()` bug high likelihood.

### Recommendation
Before resolving and signing with a `walletAccount`, verify that the calling context (origin session, connected-origins entry, or equivalent caller identity) is actually authorized to use that specific account — analogous to adding the missing ownership check in the Hegic fix. Concretely, `MessageSigner.signMessage` and `TransactionSigner.signTransaction` (or their API wrappers) should require an explicit authorization check against the caller's permitted account set (e.g. cross-referencing `connectedOrigins.getConnectedAccounts`) rather than trusting the caller-supplied `walletAccount` value unconditionally.

### Proof of Concept
```ts
// Any caller able to invoke the public messageSignerApi/transactionSignerApi
// can request a signature for an account it is not connected to / does not own:
await exodus.messageSigner.signMessage({
  walletAccount: 'exodus_1', // victim account name, not the caller's connected account
  baseAssetName: 'ethereum',
  purpose: 44,
  message: { rawMessage: Buffer.from('attacker-controlled payload') },
})
// message-signer.ts#signMessage -> #normalizeWalletAccount() only checks that
// 'exodus_1' exists in walletAccountsAtom, never that the caller is authorized
// to sign with it, and proceeds to produce a valid signature.

    walletAccount: WalletAccount | string
  ): Promise<WalletAccount> => {
    if (typeof walletAccount === 'string') {

      const instance = walletAccounts[walletAccount]

const createTransactionSignerApi = ({
  transactionSigner,
  walletAccountsAtom,
}: Dependencies): TransactionSignerApi => {
  const getWalletAccount = async (name: string): Promise<WalletAccount> => {
    const walletAccounts = await walletAccountsAtom.get()
    const walletAccount = walletAccounts[name]
    assert(walletAccount, `Unknown wallet account: ${name}`)
    return walletAccount
  }

  return {
    transactionSigner: {
      signTransaction: async (params: SignTransactionApiParams) => {
        const walletAccount =
          typeof params.walletAccount === 'string'
            ? await getWalletAccount(params.walletAccount)
            : params.walletAccount

        return transactionSigner.signTransaction({ ...params, walletAccount })
      },
    },
  }
}

  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }
