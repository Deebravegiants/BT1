## Finding

### Title
Webhook HMAC Does Not Bind the `shop` (or `topic`/`webhook-id`) Header, Enabling Cross-Tenant Webhook Replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body, so the `shopify-hmac-sha256` signature verified by `Utils::HmacValidator` covers the body bytes only. The `shop-domain`, `topic`, and `webhook-id` headers are read directly off the untrusted HTTP headers and are never included in the signed content, yet they are trusted downstream as the tenant identity for the webhook.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook solely via `Utils::HmacValidator.validate(request)` [1](#0-0) , which calls `validate_signature`, computing `HMAC(secret, verifiable_query.to_signable_string)` and comparing it to the `hmac` accessor [2](#0-1) .

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [3](#0-2) , while `shop`, `topic`, and `webhook_id` are parsed straight from HTTP headers with no cryptographic binding to the HMAC [4](#0-3) .

Immediately after HMAC validation succeeds, `Registry.process` passes the unauthenticated `request.shop` value straight into `WebhookMetadata`, which the host app's handler uses as the tenant/shop identity for the event: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [5](#0-4) .

This breaks the identity binding: **verified(body) == acted-upon(shop)** does not hold. The gem verifies "this body was HMAC-signed with the app's `client_secret`" but the app then acts as if it also verified "and it came from shop X," which was never checked.

Critically, the `client_secret` (and thus the webhook HMAC secret) is shared by the app across *all* merchant shops that install it — it is not per-shop. An unprivileged attacker can install the app on their own shop (or intercept any webhook delivered to a shop they control) with no special privileges, thereby obtaining a legitimately-signed `(raw_body, hmac)` pair signed with the app's real `api_secret_key`. Because `shop-domain`/`topic`/`webhook-id` are outside the signed content, the attacker can resend that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting a different, victim shop's `shop-domain` header (and/or a different `topic`/`webhook-id`). `HmacValidator.validate` still succeeds because the signature check only inspects the body [6](#0-5) , and the handler receives the forged `shop` as if Shopify itself vouched for it.

### Impact Explanation
This is a cross-tenant identity-binding bypass: an attacker with no elevated privileges (no access token, no `client_secret`, no leaked credentials — just the ability to install the app on their own store) can cause the host application to process attacker-chosen webhook bodies under the identity of an arbitrary other shop that has installed the app. Any app logic keyed on `data.shop` (order sync, billing/plan updates, uninstall handling, data deletion triggers, etc.) can be triggered against a victim tenant using content the attacker fully controls (their own shop's real event body), achieving cross-tenant access/interference — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for any app author who installs their own app (a completely ordinary, unprivileged step) and relays captured webhook bodies with a modified `shop-domain` header to their own webhook endpoint. No secret material beyond what's already available to any legitimate app installer is required, and the `Webhooks::Request`/`Registry.process` code path performs no additional check to bind `shop` to the signed payload.

### Recommendation
Include the identity fields that the application will act on — at minimum `shop-domain`, and ideally `topic` and `webhook-id` — in the signable string used for HMAC computation, or independently verify that `request.shop` matches an expected/known session shop before dispatching to the handler. Since Shopify's actual wire format signs the body only, the safer fix within this gem is to require callers/handlers to cross-check `request.shop` against a known, previously-established session/shop record (e.g., an existing offline session for that shop) rather than trusting the header value implicitly once the body HMAC passes.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, becoming a legitimate (non-privileged) app user.
2. Shopify sends a real webhook to the app: body `B`, headers include `x-shopify-hmac-sha256: H` (computed with the app's `client_secret`) and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures `(B, H)` and replays it directly to the app's webhook endpoint, replacing the header with `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shopify-shop-domain" => "victim.myshopify.com", "shopify-hmac-sha256" => H})` is constructed; `to_signable_string` still returns `B`, so `HmacValidator.validate` succeeds [3](#0-2) .
5. `Registry.process` calls the registered handler with `WebhookMetadata` whose `shop` is `"victim.myshopify.com"`, even though the body `B` actually belongs to the attacker's own shop event [5](#0-4) .
