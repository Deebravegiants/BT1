Found a concrete identity-binding break in the webhook processing path: the HMAC only covers the raw request body, but the `shop` (tenant identifier) delivered to the app's handler comes from an unauthenticated header.

### Title
Webhook HMAC does not bind the `shop-domain` header, allowing tenant spoofing in delivered webhook data - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `HmacValidator` verifies the HMAC solely against that body string. The `shop` (and `topic`, `api-version`, `webhook-id`) values are read directly from request headers, which are never included in the signed content.

### Finding Description
`Registry.process` verifies the webhook via `Utils::HmacValidator.validate(request)`, which computes `HMAC-SHA256(secret, request.to_signable_string)` and compares it to `request.hmac`. `to_signable_string` is defined as just `@raw_body` [1](#0-0) . Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to the signed body [2](#0-1) .

After a successful HMAC check, `Registry.process` passes `request.shop` (the unauthenticated header value) into `WebhookMetadata` and hands it to the app's handler as the tenant identifier [3](#0-2) .

The binding that should hold is:
`shop authenticated by HMAC == shop delivered to handler`

but the actual binding enforced is only:
`HMAC(secret, raw_body) == received_hmac`, independent of the `shop-domain` header.

Any party who can obtain one valid `(raw_body, hmac)` pair signed by Shopify for their own shop (e.g., by installing the app on a shop they control, or capturing/replaying a real webhook delivery) can resend that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a different (victim) shop domain. The HMAC still validates because it never covered the header, so `Registry.process` will happily invoke the handler with the attacker-chosen `shop` value bound to data/topic that is actually from the attacker's own shop payload — resulting in the app processing webhook data under a spoofed tenant identity.

### Impact Explanation
This crosses a tenant boundary: an unprivileged caller (anyone who controls or has observed one legitimately-signed webhook delivery, which is easy for any developer who installs the app on their own store) can cause the app to attribute webhook payload/topic to an arbitrary victim shop domain of their choosing, since the shop identity is never covered by the signature. Depending on how the host application's webhook handler uses `data.shop` (e.g., looking up sessions/tokens for that shop, updating per-shop records, or triggering per-shop side effects), this can lead to cross-tenant data corruption or actions being executed against the wrong merchant's stored data — matching the "Critical: cross-tenant access" impact category, since the gem's own API (`WebhookMetadata#shop`) is the documented, trusted way apps are told to identify the originating shop and it can be forged without any secret.

### Likelihood Explanation
High. No secrets are required beyond one prior, legitimately observed `(body, hmac)` pair — obtainable by installing the app on any shop, including the attacker's own — and headers are trivially replayable/spoofable by any client hitting the webhook endpoint. The gem performs no header-to-signature binding at all, so the attack is a pure "replay-with-header-substitution."

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, at minimum) in the value that is HMAC-verified, or independently verify that the `shop` reported by the header matches an app-known/expected shop for the delivery (e.g., cross-check against the merchant's registered domain). At minimum, document/enforce that `WebhookMetadata#shop` must not be trusted for tenant-sensitive operations unless additionally corroborated, and consider signing over `topic + shop-domain + raw_body` rather than `raw_body` alone.

### Proof of Concept
1. Attacker installs the target app on a shop they control (`attacker-shop.myshopify.com`) and captures a legitimate webhook delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` with the app's secret) plus `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker sends a new POST to the app's webhook endpoint with the same body `B` and same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Request#hmac`/`#to_signable_string` only checks `B`, so `HmacValidator.validate` returns true [4](#0-3) .
4. `Registry.process` invokes the handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [5](#0-4) , causing the app to process attacker-controlled payload under the victim shop's identity.
