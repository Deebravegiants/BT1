Audit Report

## Title
Non-constant-time bearer token comparison in Prometheus metrics endpoint enables timing side-channel token recovery - ([File: core/web/router.go])

## Summary
`prometheusHandler` in `core/web/router.go` compares the caller-supplied `Authorization` header against the configured `PrometheusAuthToken` using Go's native `!=` string comparison instead of `subtle.ConstantTimeCompare`, which the rest of the codebase consistently uses for secret comparisons (session tokens, bridge tokens, LDAP/OIDC email checks). This is confirmed directly in the source and breaks the codebase's otherwise consistent constant-time-comparison pattern for secret verification.

## Finding Description
The handler is defined as:
```go
func prometheusHandler(token string, h http.Handler) gin.HandlerFunc {
	return func(c *gin.Context) {
		if token == "" {
			h.ServeHTTP(c.Writer, c.Request)
			return
		}
		header := c.Request.Header.Get("Authorization")
		if header == "" {
			c.String(http.StatusUnauthorized, ginprom.ErrInvalidToken.Error())
			return
		}
		bearer := "Bearer " + token
		if header != bearer {
			c.String(http.StatusUnauthorized, ginprom.ErrInvalidToken.Error())
			return
		}
		h.ServeHTTP(c.Writer, c.Request)
	}
}
``` [1](#0-0) 

This is wired into the router via `prometheusUse`, registering an unauthenticated GET route at `p.MetricsPath` (default `/metrics`): [2](#0-1) 

The `header != bearer` comparison is a plain byte-by-byte, short-circuiting Go string comparison, confirmed to differ from the constant-time comparisons used elsewhere for secret verification (`core/sessions/session.go`, `core/bridges/bridge_type.go`, `core/sessions/ldapauth/ldap.go`, `core/sessions/oidcauth/oidc.go`). No other middleware or validation intercepts this comparison before it runs — the check at line 679 (`if token == ""`) only bypasses auth entirely when no token is configured; when a token is configured, the flawed comparison is the sole gate.

## Impact Explanation
If `PrometheusAuthToken` is configured, an attacker able to reach the node's HTTP listener could in principle mount a timing side-channel attack to recover the token byte-by-byte, then use it to authenticate to `/metrics` and read internal Prometheus telemetry data. This is a real, confirmed code defect matching a known bug class (non-constant-time secret comparison), but the practical impact is bounded: the `/metrics` endpoint exposes operational telemetry, not private keys, session credentials, or fund-movement capability, and exploitation requires a network timing attack rather than a direct request-based bypass. Compared to the other in-scope impact categories (authentication/role bypass on core APIs, key/secret exfiltration of high-value secrets, unauthorized job run or fund movement, gateway impersonation), this is a lower-severity, telemetry-scoped disclosure issue.

## Likelihood Explanation
Exploitation requires: (1) the operator to have opted into setting a non-empty `PrometheusAuthToken` (disabled by default), and (2) the attacker to perform a statistical timing attack over the network to recover a secret byte-by-byte — a technique that is far noisier and harder to execute reliably over HTTP/TCP than in the classical local side-channel cases (e.g., password hash comparisons in tight loops). No PoC or benchmark demonstrating actual exploitability over a realistic network path is provided; the report itself acknowledges this uncertainty. The vulnerable code path is real and reachable, but real-world exploitability is unproven and the value of the disclosed secret is limited to metrics-endpoint access.

## Recommendation
Replace the direct string comparison with a constant-time comparison for defense-in-depth consistency with the rest of the codebase:
```go
if subtle.ConstantTimeCompare([]byte(header), []byte(bearer)) != 1 {
    c.String(http.StatusUnauthorized, ginprom.ErrInvalidToken.Error())
    return
}
```
Optionally, hash the token server-side rather than comparing it in plaintext, consistent with the pattern used for user API tokens and bridge tokens.

## Proof of Concept
1. Configure a node with `PrometheusAuthToken` set to a secret value.
2. Send repeated `GET /metrics` requests with `Authorization: Bearer <guess>` headers, incrementally lengthening a correctly-guessed prefix while measuring response latency at the `header != bearer` branch in `prometheusHandler` (`core/web/router.go` line 693).
3. Statistically distinguish longer-matching-prefix guesses (marginally slower rejection) from early-mismatch guesses (faster rejection) across many samples to recover the token.
4. Use the recovered token to authenticate to `/metrics` via `Authorization: Bearer <token>`.

A Go benchmark-based unit test comparing timing distributions for varying-prefix-match inputs against `prometheusHandler` would be the most concrete way to demonstrate measurable timing variance before treating this as more than a theoretical code-quality issue.

// prometheusUse is adapted from ginprom.Prometheus.Use

func prometheusUse(p *ginprom.Prometheus, e *gin.Engine, handlerOpts promhttp.HandlerOpts) {
	var (
		r prometheus.Registerer = p.Registry
		g prometheus.Gatherer   = p.Registry
	)
	if p.Registry == nil {
		r = prometheus.DefaultRegisterer
		g = prometheus.DefaultGatherer
	}
	h := promhttp.InstrumentMetricHandler(r, promhttp.HandlerFor(g, handlerOpts))
	e.GET(p.MetricsPath, prometheusHandler(p.Token, h))
	p.Engine = e
}
