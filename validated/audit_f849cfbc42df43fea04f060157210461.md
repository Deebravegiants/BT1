### Title
Webhook HMAC covers only the request body, allowing shop/topic header forgery for cross-tenant webhook injection - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives its HMAC-signable content solely from the raw request body [1](#0-0) , while the `shop`, `topic`, `webhook_id`, and `api_version` fields used to route and attribute the webhook are read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only the HMAC-over-body via `Utils::HmacValidator.validate(request)` and then trusts `request.shop`/`request.topic` to build `WebhookMetadata` and dispatch to the handler [3](#0-2) .

### Finding Description
The identity binding that should hold is: `shop domain that produced the HMAC-signed body == shop domain trusted by the application as the webhook's tenant`. In this gem that equality is never enforced, because `to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate_signature` compares `HMAC(secret, raw_body)` against the received signature with no reference to the `shop`, `topic`, or `webhook_id` headers [4](#0-3) . `Registry.process` then unconditionally trusts the header-derived `request.shop` and `request.topic` to build the `WebhookMetadata` passed to the app's handler [3](#0-2) .

Because a shared `client_secret` is used to sign webhooks for *every* shop that installs the app, any unprivileged user who installs the app on their own (even free/dev) store can legitimately receive a Shopify-signed webhook whose HMAC is valid for a given `raw_body`. Since that HMAC never covers the `X-Shopify-Shop-Domain` or `X-Shopify-Topic` headers, the attacker can replay the exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with any victim shop domain and/or the `X-Shopify-Topic` header with any topic that has a registered handler. `HmacValidator.validate` still returns `true` because it only checks body bytes, and `Registry.process` routes the forged headers straight into `WebhookMetadata.shop`/`.topic`, which the documented usage pattern feeds directly into tenant-scoped background jobs (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) as shown in the gem's own documentation [5](#0-4) .

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: an app relying on `data.shop` (as instructed by this gem's own docs) to select which merchant record to mutate can be made to act on an attacker-chosen `shop` value with an attacker-supplied `topic`, using a body the attacker legitimately obtained for their own store. This is a cross-tenant confusion vector — e.g. triggering `app/uninstalled`, `customers/redact`, or order-mutation handlers against a victim shop identifier while supplying otherwise-valid signed bytes. This qualifies as Critical (cross-tenant access) under the given impact taxonomy.

### Likelihood Explanation
Exploitation requires only that the attacker can install the app once on a store they control (a routine, unprivileged action any developer/merchant can perform) to obtain one valid `(raw_body, hmac)` pair, and that the app's handler logic uses `data.shop`/`data.topic` for tenant/action routing without independent verification — which is exactly the pattern the gem's documentation recommends. No access to `api_secret_key`, tokens, or privileged accounts is required beyond normal app installation.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signable content (or independently bind/verify them, e.g. by cross-checking `shop`/`topic` against the webhook subscription that Shopify registered and expecting Shopify's delivery to always match), so that `Utils::HmacValidator.validate` fails whenever any of these header fields have been altered relative to what Shopify actually signed for that delivery.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com` and register a webhook (e.g. `orders/create`).
2. Capture a legitimate webhook delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the shared `client_secret`).
3. Replay to the app's webhook endpoint:
```
POST /callback/orders/create
X-Shopify-Topic: customers/redact
X-Shopify-Hmac-Sha256: H
X-Shopify-Shop-Domain: victim-shop.myshopify.com
X-Shopify-Webhook-Id: <any>
X-Shopify-Api-Version: <any>

B
```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because `to_signable_string` only checks `B` against `H` [1](#0-0) .
5. The registered handler for `customers/redact` is invoked with `WebhookMetadata.new(topic: "customers/redact", shop: "victim-shop.myshopify.com", body: <parsed B>, ...)` [3](#0-2) , causing the app to act as if Shopify sent this topic/body combination for `victim-shop.myshopify.com`.
