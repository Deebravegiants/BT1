### Title
Cross-tenant webhook spoofing via unsigned `shop-domain` header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating only the HMAC over the raw request body, then trusts the `shop` value taken from an HTTP header that is never covered by that HMAC. This breaks the identity binding `HMAC-authenticated bytes == bytes used to identify the tenant`, allowing a party who can obtain one genuinely-signed webhook (e.g. by installing the app on their own shop) to replay it with a modified shop-domain header and have the gem accept it as originating from an arbitrary other shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor, however, is read straight from an HTTP header supplied by the caller/host app, with no cryptographic link to the HMAC: [2](#0-1) 

`Registry.process` validates the request purely through `Utils::HmacValidator.validate(request)`, which calls `to_signable_string` (body only) and `hmac` (from the `hmac-sha256` header), and — once that passes — forwards `request.shop` (header-derived, unauthenticated with respect to the signature) directly to the registered handler as the tenant identifier: [3](#0-2) [4](#0-3) 

Because the HMAC covers `@raw_body` only and not the `shop-domain` header, two requests with identical bodies produce identical valid HMACs regardless of which shop-domain header value is attached. An attacker who legitimately installs the target app on their own shop will receive genuine webhooks whose body+HMAC pair is valid for the app's real `client_secret` (Shopify computes this server-side; the attacker never needs to know the secret). The attacker can then replay that exact `(raw_body, hmac)` pair directly against the app's public webhook endpoint while substituting the `shopify-shop-domain` (or `x-shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because it never inspects the header, and `Registry.process` hands the handler a `WebhookMetadata` tagged with the attacker-chosen `shop` value: [5](#0-4) 

If the host application (as is the normal/documented pattern) uses `data.shop` to look up the victim's session/access token and apply the (attacker-controlled) body/topic to that tenant's data, this results in cross-tenant data injection/consumption — the same "field acted on but not covered by the HMAC" identity-binding failure called out in the rules.

### Impact Explanation
This crosses a tenant boundary: an attacker who is themselves a legitimate (even free-tier) merchant of the app can cause the app to process a payload under a different, victim shop's identity, e.g. triggering handler logic (GDPR data requests, order/customer webhooks, uninstall flows) with a spoofed `shop`. Depending on what the host app does in its handler (common pattern: look up stored access token by `shop` and perform admin actions), this can lead to cross-tenant access — rated Critical per the given impact classes.

### Likelihood Explanation
Medium-High: exploitation requires only (a) the attacker be an app user themselves (trivial — free installs are typical for embedded apps) so they can capture one genuinely-signed webhook, and (b) direct network access to the app's public webhook endpoint to replay the request with an altered header, both of which are unprivileged-internet-user actions with no need for `client_secret`, tokens, or social engineering.

### Recommendation
Bind the shop identity into the authenticated material, e.g. include the `shop-domain` (and `topic`) header values in `to_signable_string` for webhook verification, or otherwise cryptographically bind the header-derived tenant identity to the payload before handing it to `handler.handle`. At minimum, document that `request.shop` is unauthenticated w.r.t. the HMAC and must not be trusted for tenant lookup without additional verification (e.g., cross-checking against the shop stored for the topic/webhook_id via the Admin API).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`, triggering a real webhook (e.g. `orders/create`) to the app's webhook endpoint. Shopify sends headers including `x-shopify-hmac-sha256: <validHMAC>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`, with some JSON `raw_body`.
2. Attacker captures `(raw_body, validHMAC)`.
3. Attacker POSTs directly to the app's public webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256: <validHMAC>`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses this; `Utils::HmacValidator.validate(request)` recomputes HMAC over `raw_body` only and it matches, per [6](#0-5) .
5. `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` and the attacker-supplied body, as shown at [7](#0-6) , even though the payload never originated from Shopify for that shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
