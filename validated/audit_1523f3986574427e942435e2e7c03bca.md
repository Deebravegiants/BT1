Audit Report

## Title
JWT replay guard in the Gateway HTTP Trigger handler uses non-atomic check-then-act, allowing concurrent replay of the same signed workflow-trigger request - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

## Summary
`WorkflowMetadataHandler.Authorize` enforces single-use semantics for signed JWTs on the internet-facing HTTP Trigger capability by calling `h.jwtCache.isReplay(claims.ID)` and, only after other checks pass, `h.jwtCache.recordUsage(claims.ID)`. These are two independently mutex-protected operations rather than one atomic check-and-record, so two concurrent requests carrying the same signed JWT can both observe "not replayed" before either commits, both passing authorization and triggering the workflow.

## Finding Description
`Authorize` at [1](#0-0)  calls `isReplay` (RLock/RUnlock) as an early gate, then performs several unrelated checks (workflow ID lookup, authorized-key lookup), and only afterward calls `recordUsage` (Lock/Unlock) at line 105. `isReplay` and `recordUsage` are defined as separate critical sections: [2](#0-1) . Because there is a window between the read and the write where the lock is released, two goroutines handling two concurrent HTTP-trigger requests with the identical signed JWT can both execute `isReplay` and see `false` before either executes `recordUsage`. Both then proceed through `authorizeRequest` and `HandleUserTriggerRequest` at [3](#0-2) , ultimately calling `sendWithRetries` to dispatch the single-use JWT-authorized trigger more than once. In contrast, the Vault capability's equivalent guard, `RequestReplayGuard.CheckAndRecord`, correctly performs the existence check and the record under one held lock, closing this window: [4](#0-3) . The existing regression test only exercises the sequential case, calling `Authorize`/`HandleUserTriggerRequest` twice one after another, which cannot exhibit a TOCTOU race and therefore does not catch this gap.

## Impact Explanation
This breaks the intended single-use guarantee of the HTTP Trigger JWT authentication scheme — the entire mechanism exists so a signed request can be used exactly once by an unprivileged, internet-facing caller. A race allows the identical signed request to authorize more than one workflow execution concurrently, which is an unauthorized/duplicate job run. This maps to the in-scope "unauthorized job run" impact category, and for workflows with on-chain side effects this constitutes a real integrity issue.

## Likelihood Explanation
Exploitability only requires an unprivileged client (or a legitimate client that duplicates a request, e.g. due to a retry) to send the same already-signed JWT-authorized trigger request twice concurrently to the gateway. No special privilege, node compromise, or cryptographic break is needed — just two near-simultaneous requests. Winning the race depends on goroutine interleaving between the `RLock`-protected read and the later `Lock`-protected write, which is plausible under real concurrent load given the gap includes multiple lookups (workflow ID, authorized-key map).

## Recommendation
Merge the check and the record into a single atomic critical section under one lock, mirroring `vault.RequestReplayGuard.CheckAndRecord`:
```go
func (cache *jwtReplayCache) checkAndRecord(jti string) bool {
    cache.mu.Lock()
    defer cache.mu.Unlock()
    if _, exists := cache.cache[jti]; exists {
        return false
    }
    cache.cache[jti] = time.Now()
    return true
}
```
Update `Authorize` to call this single atomic method immediately and reject the request if it returns false, rather than separately calling `isReplay` and `recordUsage`.

## Proof of Concept
1. Create a valid signed JWT for a `WorkflowExecute` request as in the `"JWT replay protection"`/`"duplicate JWT token and request ID"` subtests of `http_trigger_handler_test.go`.
2. Spawn two goroutines that concurrently call `handler.Authorize(workflowID, tokenString, req)` (or `HandleUserTriggerRequest`) with the identical `tokenString`/`req`, synchronized with a `sync.WaitGroup`.
3. Observe that under the current implementation both calls can return success (`nil` error) instead of exactly one succeeding and the other returning "JWT token has already been used," demonstrating the atomicity gap. Running with `go test -race` under repeated iterations should surface the non-deterministic double-success outcome.

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	}
