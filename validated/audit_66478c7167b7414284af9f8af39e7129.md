### Title
Webhook `shop`, `topic`, and `webhook_id` are trusted from unauthenticated headers while only the raw body is HMAC-covered, enabling cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` (and `topic`, `webhook_id`, `api_version`) from HTTP headers that are never included in the HMAC signature computation, yet `Registry.process` trusts those same header values to route the webhook payload to the correct shop's handler once the HMAC check passes.

### Finding Description
The identity binding that should hold is:

`HMAC(secret, bytes_verified) == HMAC(secret, bytes_received)` **and** `bytes_verified` includes the tenant identifier (`shop`) that the application will act on.

In this gem, `to_signable_string` only returns the raw request body: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers with no cryptographic binding to the signed bytes: [2](#0-1) 

`Registry.process` validates only the HMAC over the raw body, then passes the header-derived `shop` straight to the handler: [3](#0-2) 

`HmacValidator.validate` confirms only that `hexdigest(secret, request.to_signable_string) == hmac`, i.e. it authenticates the body bytes, not the shop/topic metadata: [4](#0-3) 

Because the `api_secret_key` used to sign webhooks is the app's single global secret shared across **every** installed shop (not a per-tenant secret), any entity that has received one legitimately-signed webhook body (e.g. a malicious merchant who installs the app on their own store and receives their own real webhooks) possesses a `(raw_body, hmac)` pair that will pass `HmacValidator.validate` regardless of which `shop-domain`/`topic`/`webhook-id` headers accompany it. The header values are parsed, but never re-verified against the signed content, so the equality the code implicitly assumes — "the shop that produced a validly-signed body is the shop named in the header" — does not actually hold.

### Impact Explanation
An attacker who can deliver an HTTP request to the app's webhook endpoint (this is a public endpoint by design) with a captured valid `(raw_body, hmac)` pair and an arbitrary `x-shopify-shop-domain` header can make the application process that payload as belonging to a different, victim shop. Depending on the handler logic (which typically uses `WebhookMetadata#shop` to look up/mutate that shop's stored session, orders, customer data, or to react to `app/uninstalled` by purging shop data), this results in cross-tenant data corruption or cross-tenant state manipulation — an app acting on shop B's session/data because of a forged header on a replayed webhook whose body was only ever legitimately signed for shop A. This matches the Critical/High "cross-tenant access" impact category.

### Likelihood Explanation
Any merchant can install the app on their own store to legitimately receive at least one authentic `(body, hmac)` pair (e.g., `app/installed`, or triggering any subscribed topic). Replaying that exact body with a modified shop header to the same public webhook endpoint requires no credentials beyond network access to the endpoint — well within the "unprivileged internet user" threat model, since the shared `api_secret_key` used for HMAC is not shop-specific.

### Recommendation
Include the tenant-identifying fields (`shop`, `topic`, and ideally `webhook_id`) inside the signed material, or otherwise cryptographically bind them to the raw body before verification — e.g., verify the HMAC over `shop-domain + topic + raw_body` (matching what Shopify actually signs, if it does), or require the caller to independently confirm the resolved `shop` matches a shop with an active session before dispatching to handlers. At minimum, document and enforce that `Registry.process` must not trust `request.shop`/`request.topic` for authorization decisions without additional binding, since only `raw_body` is authenticated by `HmacValidator`.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a real webhook (e.g. `orders/create`) and capture the raw POST body `B` and its header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(api_secret_key, B)`, and `api_secret_key` is the same for all shops).
2. Send a new POST to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256: H` (unchanged)
   - Header `x-shopify-shop-domain: victim.myshopify.com` (forged)
   - Header `x-shopify-topic`/`x-shopify-webhook-id` optionally forged too
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H`.
4. `Registry.process` invokes the app's handler with `shop: "victim.myshopify.com"` and body `B`, causing the app to act as though `victim` produced this data. [5](#0-4)

# typed: strict

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }
      def shopify_header(name)
        @headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]
      end
    end
  end
end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
