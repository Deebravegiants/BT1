Confirmed: the `shop` field passed to `WebhookMetadata` (and to the merchant's `handle` callback) is read from the unauthenticated `shopify-shop-domain` header, while the HMAC only signs `@raw_body`.### Title
Webhook `shop` identity is read from an unauthenticated header while the HMAC only covers the raw body, breaking the tenant binding - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook exclusively via `Utils::HmacValidator.validate(request)`, which computes the HMAC over `request.to_signable_string` — defined in `lib/shopify_api/webhooks/request.rb:35-38` as `@raw_body` only. The `shop` identity used to attribute the event to a tenant is read separately from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header (`lib/shopify_api/webhooks/request.rb:20-23`), a field that is never included in the signed bytes.

### Finding Description
The binding the code is supposed to enforce is: `hmac == HMAC(secret, bytes-that-determine-the-tenant)`. In `HmacValidator.validate_signature` (`lib/shopify_api/utils/hmac_validator.rb:26-31`), `computed_signature = compute_signature(verifiable_query.to_signable_string, secret)` is compared against the `hmac` header. For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`), while `shop` is parsed from the `shop-domain` header (`lib/shopify_api/webhooks/request.rb:20-23`) and never enters the signed string.

`Registry#process` (`lib/shopify_api/webhooks/registry.rb:188-199`) trusts this unauthenticated header directly: after the HMAC check passes, it builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` and hands it to the host application's `WebhookHandler#handle`. The equality the gem is implicitly promising to the host app — "this event's `shop` came from the same origin whose secret produced this valid HMAC" — does not hold, because `shop` is outside the signed payload.

Any actor capable of obtaining one legitimately-signed webhook body+HMAC pair (e.g., by installing the app on their own store, which requires no special privilege beyond normal merchant/developer signup) can replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` will still pass because it only checks the body bytes, but `Registry#process` will hand the handler a `WebhookMetadata` claiming the event belongs to whatever shop domain the attacker put in the header.

### Impact Explanation
This is a cross-tenant identity-binding break: the gem authenticates the *content* of a webhook but not the *attribution* of that webhook to a shop, then still forwards the attacker-controlled shop value to the host application as trusted. Any host app logic that uses `WebhookMetadata#shop` to select a merchant's session/access token, write to shop-scoped storage, or trigger shop-scoped side effects can be made to act against the wrong tenant using data supplied by the attacker's own store. This matches the Critical/High impact class of cross-tenant access driven by a bug in this gem's own verification code, not a host-application misuse of a documented API — the gem provides no signable coverage of `shop` at all, so no correct usage of the public API can close the gap.

### Likelihood Explanation
Likelihood is significant because the prerequisite (running/controlling one's own Shopify dev/partner store and app installation to generate a legitimately HMAC-signed webhook body) is available to any unprivileged internet user via Shopify's free developer program, with no access to the target's `client_secret` or access tokens required. The replay only requires forging an HTTP header, which is trivial once a valid body/HMAC pair is captured.

### Recommendation
Include the `shop` domain (and ideally `topic`/`webhook_id`) as part of the signed material verified for webhooks, or otherwise cryptographically bind the header-derived `shop` to the payload before constructing `WebhookMetadata`. At minimum, `Webhooks::Request#to_signable_string` should not be the sole determinant of authenticity for fields consumed downstream (`shop`) that are not covered by it — the library should document/guard that `shop` from webhook headers must be independently reconciled against the shop that is actually installed/tracked for the given `webhook_id`/topic before being trusted for tenant-scoped logic, since Shopify's real HMAC scheme for webhooks intentionally only signs the body and callers must treat the header-derived shop as merely a hint requiring independent verification (e.g., matching against a known, previously stored shop for that webhook subscription) rather than as an authenticated value.

### Proof of Concept
1. Attacker installs the target app on their own (attacker-controlled) Shopify store `attacker.myshopify.com`, triggering a legitimate webhook. Shopify sends:
   - Headers: `shopify-shop-domain: attacker.myshopify.com`, `shopify-hmac-sha256: <valid HMAC of raw_body>`, `shopify-topic: orders/create`
   - Body: `raw_body` (arbitrary JSON content the attacker fully controls, e.g. crafted order data)
2. Attacker replays the exact same `raw_body` and `shopify-hmac-sha256` value to the app's webhook endpoint, but sets `shopify-shop-domain: victim.myshopify.com`.
3. `Webhooks::Request.new` parses `shop` as `"victim.myshopify.com"` (`lib/shopify_api/webhooks/request.rb:20-23`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` (`lib/shopify_api/webhooks/registry.rb:190`), which recomputes the HMAC only over `raw_body` (`lib/shopify_api/webhooks/request.rb:36-38`) — validation succeeds because `raw_body` and its HMAC are unchanged.
5. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker-controlled parsed body>, ...))` (`lib/shopify_api/webhooks/registry.rb:198-199`), delivering attacker-controlled body content falsely attributed to the victim shop to the host application's webhook handler.
