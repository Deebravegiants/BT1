### Title
Reachable panic (unchecked subtraction underflow) in `SwapBaseOut`/`SwapBaseOutV2` via attacker-controlled `amount_out` - ([File: program/src/processor.rs])

### Summary
In `process_swap_base_out` (and its `_v2` counterpart), the untrusted, attacker-supplied `amount_out` field is passed into `Calculator::swap_token_amount_base_out` *before* the program validates that `amount_out` is smaller than the pool's available liquidity. That calculator function performs `total_pc_without_take_pnl.checked_sub(amount_out).unwrap()` (or the coin-side equivalent), which returns `None` and panics via `.unwrap()` whenever `amount_out` is greater than or equal to the pool reserve. The bounds check that would prevent this (`swap.amount_out >= total_pc_without_take_pnl` / `total_coin_without_take_pnl`) is only performed *after* this calculation, making the panic reachable from a single, permissionless, correctly-signed transaction.

This is the same bug class as CVE-2024-45795: a value that is not validated/implemented against its real constraints reaches an `unwrap`/assertion during normal processing of attacker-controlled input, causing the process to abort (denial of service) rather than returning a graceful error.

### Finding Description
`Calculator::swap_token_amount_base_out` computes the required input amount for a base-out swap: [1](#0-0) 

For `SwapDirection::Coin2PC` it computes `denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap()`; for `SwapDirection::PC2Coin` it computes `denominator = total_coin_without_take_pnl.checked_sub(amount_out).unwrap()`. Both use `.unwrap()` on a `checked_sub`, which panics on underflow (i.e., when `amount_out >= total_{pc,coin}_without_take_pnl`).

`process_swap_base_out` calls this function with the caller-supplied `swap.amount_out` at: [2](#0-1) 

The corresponding sanity check that would reject an out-of-range `amount_out` (`swap.amount_out >= total_pc_without_take_pnl` for `Coin2PC`, `swap.amount_out >= total_coin_without_take_pnl` for `PC2Coin`) is only performed later, inside the transfer-dispatch `match` block, *after* the vulnerable computation has already executed: [3](#0-2) 

Because `swap.amount_out` is fully attacker-controlled instruction data (unpacked directly from the transaction with no range validation) and none of the preceding checks in `process_swap_base_out` (account ownership, PDA authority, vault/mint matching, status permission) constrain its magnitude relative to pool reserves, any unprivileged caller can trigger the panic by simply setting `amount_out` to a value at or above the current pool balance of the requested output token: [4](#0-3) 

The identical pattern exists in `process_swap_base_out_v2`, which reuses the same `Calculator::swap_token_amount_base_out` call ahead of the equivalent bounds check: [5](#0-4) 

### Impact Explanation
On Solana, a Rust panic inside program execution aborts the transaction and consumes the compute/fees for that transaction, but does not persist a corrupted state to the AMM account (SBF/BPF VM catches the panic as a runtime error). The direct impact is therefore reliable transaction failure/denial-of-service for any `SwapBaseOut`/`SwapBaseOutV2` call using an out-of-range `amount_out` against a specific pool, and it demonstrates that a value which should be validated before use (analogous to the unimplemented "unset" dataset option in the Suricata bug) is instead consumed unchecked, reaching an assertion-equivalent (`unwrap`) failure. This does not by itself constitute fund theft or freezing since the transaction reverts atomically without state mutation, keeping severity to denial-of-service rather than fund loss.

### Likelihood Explanation
Trivially reachable: any unprivileged user can submit a single `SwapBaseOut` (or `SwapBaseOutV2`) transaction against any live pool with attacker-chosen `amount_out` greater than or equal to the pool's current reserve of the desired output token, and standard account-binding checks (vault keys, mint matching, signer) are trivially satisfiable with correct, legitimate accounts—no special privilege or race condition is required.

### Recommendation
Move the reserve-sufficiency checks (`swap.amount_out >= total_pc_without_take_pnl` / `total_coin_without_take_pnl`) to occur immediately after `swap_direction` is determined and before calling `Calculator::swap_token_amount_base_out`, in both `process_swap_base_out` and `process_swap_base_out_v2`. Additionally, replace the `.unwrap()` calls inside `swap_token_amount_base_out` (program/src/math.rs) with `checked_sub(...).ok_or(AmmError::CalculationExRateFailure)?` (or equivalent) so that any future unchecked call site fails gracefully with a program error instead of panicking.

### Proof of Concept
1. Identify an existing Raydium AMM pool with `AmmInfo` PDA `amm_info`, valid coin/pc vaults, and a known reserve amount, e.g. `total_pc_without_take_pnl = P` for the desired output side.
2. Build a `SwapBaseOut` instruction (tag `11`, see `AmmInstruction::unpack` case `11`) with `swap.amount_out = P` (or any value `>= P`) and an arbitrary `max_amount_in`, using the legitimate account list expected by `process_swap_base_out` (17 or 18 accounts: token program, amm, authority, open orders, [target orders], coin vault, pc vault, market accounts, user source/destination token accounts, user signer): [4](#0-3) 
3. Submit the transaction signed by the user's own token-account owner (no elevated privilege required).
4. Execution reaches `Calculator::swap_token_amount_base_out(swap.amount_out, total_pc_without_take_pnl, total_coin_without_take_pnl, swap_direction)` at `program/src/processor.rs:2172-2177` before the reserve check at `2212-2216`; since `amount_out >= total_pc_without_take_pnl`, the internal `checked_sub(amount_out).unwrap()` in `program/src/math.rs:341` returns `None` and the `.unwrap()` panics, aborting the transaction with a runtime error rather than a controlled `AmmError`.

        amount_out: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_in;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_in = coin * pc / (pc - amount_out) - coin
                // => amount_in = (coin * pc - pc * coin + amount_out * coin) / (pc - amount_out)
                // => amount_in = (amount_out * coin) / (pc - amount_out)

                amount_in = total_coin_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
