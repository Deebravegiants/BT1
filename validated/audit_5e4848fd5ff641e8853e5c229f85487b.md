### Title
Extreme HyperSwap V2 pre-seed ratio permanently reverts `finalizeGraduation`, freezing curve-raised LT and the 250M LP-reserve tokens - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding._seedUniswapV2Direct` / `_seedRebalancing` / `_pairRebalance` / `_routerDepositAndDispose` assume that capping the rebalance swap at 99% of the available inventory (`_swapBudget`) is sufficient to guarantee a non-zero, mintable LP deposit on `finalizeGraduation`. That assumption is only checked as "remToken > 0 && remLT > 0" — it never checks that the HyperSwap V2 router's `quote()`-based optimal split on those balances actually rounds to a non-zero amount on both legs. An attacker who pre-mints an extreme-ratio (TOKEN, LT) seed into the not-yet-graduated HyperSwap V2 pair can force the capped rebalance to leave the pool at a ratio skewed enough that `IUniswapV2Router02.addLiquidity`'s internal `quote()` rounds one optimal leg to `0`, tripping the router's `amountAMin/amountBMin = 1` floor and reverting `addLiquidity` — and therefore reverting the entire `finalizeGraduation` call, every single time it is retried, because the hostile pair state persists across calls and the whole transaction (including `Router.graduate`'s earlier LT transfer into `Bonding`) rolls back on revert.

### Finding Description
`finalizeGraduation` (`Bonding.sol:1000-1034`) is the only path that can move a token out of `Lifecycle.Graduating`. It calls `_seedUniswapV2Direct` (`Bonding.sol:1201-1234`), which for a pre-seeded ("mint pre-seed") pair takes the `_seedRebalancing` branch (`Bonding.sol:1279-1354`).

`_seedRebalancing` computes a rebalance swap via `_pairRebalance`, capped by `_swapBudget` at 99% of the inventory (`Bonding.sol:1374-1378`): [1](#0-0) 

The natspec on `_swapBudget` explicitly states the goal is to guarantee `_routerDepositAndDispose`'s deposit "always lands AND mints non-zero LP at the post-swap ratio": [1](#0-0) 

But `_routerDepositAndDispose` only checks that both raw balances are non-zero before calling the router, never that the router's internal `quote()`-based optimal split will be non-zero on both legs: [2](#0-1) 

`IUniswapV2Router02.addLiquidity` (canonical V2 logic) computes `amountBOptimal = quote(amountADesired, reserveA, reserveB)`; if that rounds to `0` while `amountBMin = 1` (hard-coded at `Bonding.sol:1470`), the router reverts with an `INSUFFICIENT_*_AMOUNT`-class error. This happens whenever the post-swap pair ratio is skewed enough, relative to the small remaining balances, that integer division in `quote()` truncates to zero — which is straightforward to engineer with a sufficiently extreme pre-seed ratio, since the rebalance swap is capped at 99% of *this graduation's* inventory and cannot fully correct an arbitrarily large pre-existing reserve skew (`_noFeeSwapInput`, `Bonding.sol:1507-1522`, is explicitly bounded by `maxSwap`).

Because `finalizeGraduation` performs `Router.graduate` (which moves the curve's real raised LT out of the curve `Pair` into `Bonding`), the empty-pair/donation skim, the rebalance swap, and the `addLiquidity` call all inside one transaction, any revert inside `_seedUniswapV2Direct` rolls the entire transaction back — `Lifecycle.Graduating` is never advanced, `pendingGraduation` is never deleted, and the hostile pair state (which caused the revert) is untouched. Every subsequent call to `finalizeGraduation` for that token replays the identical computation against the identical pair state and reverts identically. There is no retry path, no alternate seeding function, and — per the `LPLockStorage.isLocker` natspec — no admin rescue mechanism for a token stuck in `Lifecycle.Graduating`.

This is the same bug class as the CVE: a value that can legitimately be zero/degenerate (here, the router's rounded-to-zero optimal deposit leg) is not checked before being fed into an operation that assumes it is well-formed (`addLiquidity`'s `min=1` floor), and the unguarded path is reachable by an untrusted external actor (a pre-seeding trader) rather than a privileged caller — except here the crash is a permanent on-chain revert rather than a node panic.

### Impact Explanation
Once a token enters `Lifecycle.Graduating` (dual-triggered automatically the moment `canGraduate` flips true on any ordinary buy, or via the permissionless `triggerGraduation`), trading on the bonding curve is frozen (`Bonding.buy`/`Bonding.sell` both reject `Lifecycle.Graduating`) and the only exit is `finalizeGraduation`. If `finalizeGraduation` is made to permanently revert:
- All curve-raised LT already pulled into `Bonding` via `Router.graduate` (the entirety of the curve's raised reserve, up to `graduationThresholdUsd` worth) is permanently stranded — it can never reach `LPLock`, never reach the pair, never be swept.
- The 250M (`LP_RESERVE`, i.e. `LP_RESERVE_BPS` of `TOTAL_SUPPLY`) tokens earmarked for the LP are similarly stranded on `Bonding`.
- Every holder of the launched token is frozen out of both the curve (closed) and the V2 pool (never seeded) — total, irreversible loss of liquidity/exit for that token.

This meets the "permanent freezing of trader, creator or LP funds" bar at High severity.

### Likelihood Explanation
Reachable by any unprivileged address: pre-seeding a HyperSwap V2 pair before graduation is explicitly a permitted, realistic attack primitive (an attacker only needs TOKEN, obtained by buying on the curve, and LT, obtained by minting against USDC via the public `IBounceLeveragedToken.mint`), then calling `IUniswapV2Factory.createPair` and `IUniswapV2Pair.mint` directly to bake in an extreme ratio. The existing `_seedRebalancing`/`_swapBudget` defenses were clearly designed with this exact attacker in mind (per the extensive natspec), but the fix only guarantees non-zero raw balances, not a non-zero router-optimal split — an attacker who sizes the pre-seed ratio just outside the `_swapBudget` correction envelope (arbitrarily large-vs-tiny reserve skew) can force the rounding-to-zero condition deterministically.

### Recommendation
In `_routerDepositAndDispose`, before calling `IUniswapV2Router02.addLiquidity`, pre-compute the router's optimal split locally (mirroring `quote()`) against the live pair reserves and confirm both legs are non-zero; if not, fall back to `_seedDirectMint`-style direct `pair.mint` (bypassing the router's `min` floor) instead of reverting the whole transaction. Alternatively, wrap the `addLiquidity` call in a try/catch and fall back to a direct-mint recovery path so a hostile pre-seed can degrade gracefully instead of permanently bricking `finalizeGraduation`.

### Proof of Concept
1. Attacker buys TOKEN on the bonding curve for `tokenAddress` (any small amount) and mints a correspondingly sized amount of `lt` via `IBounceLeveragedToken.mint`.
2. Attacker calls `IUniswapV2Factory(uniswapV2Factory).createPair(tokenAddress, lt)` to pre-create the graduation pair.
3. Attacker transfers a deliberately extreme ratio of TOKEN and LT into the pair (e.g. a large amount of one side, a minimal amount of the other) and calls `pair.mint(attacker)` directly — Regime 3 ("mint pre-seed") in `_seedUniswapV2Direct`'s natspec.
4. Attacker (or anyone) triggers graduation normally via a curve buy that crosses `canGraduate`, or via `Bonding.triggerGraduation(tokenAddress)`.
5. Anyone calls `Bonding.finalizeGraduation(tokenAddress)`. `_seedRebalancing`'s capped `_pairRebalance` cannot fully correct the extreme pre-seed ratio within its 99%-of-inventory budget; `_routerDepositAndDispose`'s `addLiquidity(tokenAddress, lt, remToken, remLT, 1, 1, lpLock_, block.timestamp)` computes an optimal split whose smaller leg rounds to `0` under the router's `quote()`, tripping `amountBMin = 1` (or `amountAMin = 1`) and reverting.
6. The transaction reverts in full; `Lifecycle.Graduating` and `pendingGraduation[tokenAddress]` are unchanged. Every future call to `finalizeGraduation(tokenAddress)` repeats steps 5-6 identically, permanently freezing the token's raised LT and 250M LP-reserve tokens on `Bonding`.

    /// @dev Cap the rebalance swap at 99% of the available side's budget,
    ///      so the subsequent `addLiquidity` always has a non-zero amount
    ///      of BOTH sides to deposit. Without this, an extreme hostile
    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,
    ///      `_pairRebalance` clamps to the full budget, and the swap
    ///      consumes 100% of one side. `_routerDepositAndDispose` then
    ///      skips `addLiquidity` (`remToken == 0` or `remLT == 0`),
    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero
    ///      LP at the post-swap ratio. The 1% comes off the swap, not the
    ///      deposit — for any realistic pre-seed `s_unconstrained` is
    ///      orders of magnitude below `maxSwap`, so the cap doesn't bind
    ///      and behaviour is unchanged. It only kicks in for catastrophic
    ///      pre-seeds beyond our budget capacity, where the alternative
    ///      is bricking.
    function _swapBudget(
        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;
    }

        uint256 remToken = IERC20(tokenAddress).balanceOf(address(this));
