### Title
Webhook `shop-domain`/`topic` headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while the shop identity used by the app (`request.shop`) is read directly from the `x-shopify-shop-domain` header, which is never part of the signed bytes [2](#0-1) . `Registry.process` validates the HMAC over the body only and then unconditionally forwards `request.shop` (and `request.topic`) to the app's handler as the trusted tenant identifier [3](#0-2) . This mirrors the M-2 pattern: a field acted upon (`shop`, used as the tenant/session key by the consuming app) is not bound by the same authentication mechanism (`HMAC`) that gates processing.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC-SHA256(app_secret, verifiable_query.to_signable_string)` and compares it against the `hmac` header [4](#0-3) . For webhooks, `to_signable_string` is exactly `@raw_body` [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors are read straight from headers with no cryptographic linkage to the body or to each other [5](#0-4) .

Because `app_secret` (`Context.api_secret_key`) is the same secret for every shop that installs the app (it is the app's `client_secret`, not a per-shop secret), any two webhook deliveries — regardless of which shop they were generated for — that carry the same body produce the same valid HMAC. `Registry.process` only checks `HmacValidator.validate(request)` [6](#0-5)  — wait see exact citation below — and then trusts `request.shop` as the tenant for the handler call: [3](#0-2) 

The equality the gem implicitly assumes is:
`shop_bound_by_hmac == shop_delivered_to_handler`

but in reality:
`shop_bound_by_hmac = ∅ (HMAC covers body bytes only)`
`shop_delivered_to_handler = header["x-shopify-shop-domain"] (attacker-controlled, unauthenticated)`

### Impact Explanation
An attacker who legitimately installs the app on their own shop (or otherwise legitimately receives one valid webhook delivery for any shop) obtains a `(body, hmac)` pair that is valid under the shared `app_secret`. By replaying that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain, the gem's `HmacValidator` still reports the request as authentic, and `Registry.process` calls the app's handler with `WebhookMetadata#shop` set to the victim's domain. Any host application that follows the documented pattern of trusting `data.shop` from `Registry.process`'s handler callback to select the tenant/session (e.g., updating that shop's local records, revoking access, or triggering shop-scoped side effects) will act on the attacker-controlled data under the victim's identity — a cross-tenant impact.

### Likelihood Explanation
The attacker only needs the ability to install the app once (or otherwise obtain a single legitimate webhook delivery, e.g., via a trial/self-serve install), which is a low bar for most public Shopify apps. No access to `api_secret_key`, access tokens, or TLS interception is required — only a captured, legitimately-signed `(body, hmac)` pair and the ability to POST to the app's public webhook endpoint with modified headers.

### Recommendation
Include the identity fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable content, or otherwise cryptographically bind them (e.g., verify that headers match values embedded in the payload, or require the host app to separately confirm the shop against a previously known/authorized session before trusting the webhook's shop). At minimum, document prominently that `request.shop`/`request.topic` are NOT covered by HMAC verification and must not be trusted as tenant identifiers without additional binding.

### Proof of Concept
1. App owner (attacker) installs their app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw body `B` and the `x-shopify-hmac-sha256` header `H` sent by Shopify (valid because `H = HMAC-SHA256(app_secret, B)`).
2. Attacker sends a forged HTTP POST to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - `x-shopify-hmac-sha256`: `H` (unchanged)
   - `x-shopify-topic`: `orders/create` (unchanged or attacker-chosen)
   - `x-shopify-shop-domain`: `victim-shop.myshopify.com` (forged)
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers (no header integrity check beyond presence) [7](#0-6) .
4. `Registry.process` calls `HmacValidator.validate(request)`, which succeeds because it hashes only `B` [8](#0-7) , and it proceeds to invoke the handler with `shop: "victim-shop.myshopify.com"` [9](#0-8) .
5. The host application's webhook handler processes the (attacker-controlled) payload `B` as if it legitimately originated from `victim-shop.myshopify.com`.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
