Audit Report

## Title
CORS wildcard-origin allowlist bypass via missing subdomain boundary check - (File: core/services/gateway/network/httpserver.go)

## Summary
`isAllowedOrigin` in `core/services/gateway/network/httpserver.go` implements wildcard CORS origin matching (`*.example.com`) using a plain `strings.HasSuffix(originHost, allowedHost)` check after stripping the `*.` prefix, with no verification that the matched suffix begins at a `.` label boundary. This allows an attacker who registers a domain that merely ends with the same character sequence (e.g., `evil-ethereum.org` for an allowlist of `*.ethereum.org`) to be treated as an allowed subdomain and receive a reflected `Access-Control-Allow-Origin` header.

## Finding Description
The vulnerable logic is: [1](#0-0) 
This strips `*.` from the configured allowed host and then performs a raw string suffix comparison against the origin host, rather than checking that the origin is either exactly the allowed host or ends with `.` + allowed host. `splitURL`, used to extract host/scheme/port for both the origin and allowlist entries, does no additional boundary validation: [2](#0-1) 
The result is then reflected directly into the `Access-Control-Allow-Origin` response header for every request to the gateway's public User HTTP server when CORS is enabled: [3](#0-2) 
There is no other subdomain-boundary check anywhere in this file, so any operator who configures a wildcard CORS entry (e.g., `https://*.ethereum.org`, as shown in the integration test config with `CORSAllowedOrigins = ["https://remix.ethereum.org"]`) is exposed to this bypass if a wildcard entry is used.

## Impact Explanation
This is a genuine authority-boundary bug: an attacker-registered domain sharing only a string suffix with the intended wildcard domain (not a true subdomain) can obtain a reflected `Access-Control-Allow-Origin` header, letting a browser on that attacker origin read cross-origin responses from the gateway's user-facing HTTP endpoint. Because `Access-Control-Allow-Credentials` is never set, credentialed/cookie-based requests are not enabled by this bug, which limits impact to non-credentialed response exposure — still a legitimate CORS allowlist bypass affecting gateway request/response confidentiality for any deployment using wildcard CORS entries.

## Likelihood Explanation
Exploitation requires only that (a) the gateway operator configured a wildcard CORS entry (not the default single-origin example shown in the integration test), and (b) an attacker registers/controls a domain sharing the vulnerable suffix and lures a victim's browser to it — no authentication, privileged role, or gateway-side misconfiguration beyond enabling a wildcard entry is needed. This is a plausible, low-effort, repeatable exploitation path for any deployment that uses `*.` wildcard CORS entries.

## Recommendation
Enforce a proper subdomain boundary in the wildcard match, e.g.:
```go
if strings.HasSuffix(originHost, "."+allowedHost) || originHost == allowedHost {
    return true
}
```
or compare `originHost` split on `.` against `allowedHost`'s labels for exact trailing-label equality instead of a raw suffix string comparison.

## Proof of Concept
1. Configure the gateway User HTTP server with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.ethereum.org"]`.
2. Send an HTTP request to the gateway user endpoint with header `Origin: https://evil-ethereum.org`.
3. Observe `isAllowedOrigin` (lines 184-190) returns `true` because `strings.HasSuffix("evil-ethereum.org", "ethereum.org")` is `true`, and `handleRequest` reflects `Access-Control-Allow-Origin: https://evil-ethereum.org` in the response (lines 195-202).
4. A Go unit test calling `httpServer.isAllowedOrigin("https://evil-ethereum.org")` against a config with `CORSAllowedOrigins: []string{"https://*.ethereum.org"}` and asserting `true` demonstrates the bypass directly.
