### Title
Missing size cap before Borsh-deserializing an RPC-submitted transaction enables memory exhaustion - (File: chain/jsonrpc/src/api/transactions.rs)

### Summary
The JSON-RPC transaction submission endpoint decodes an attacker-controlled base64 string and feeds the resulting bytes directly into `SignedTransaction::try_from_slice`, with no upper bound on the input size before deserialization occurs. This is the same bug class described in the external report (uninitialized/unbounded `Vec` allocation driven by attacker-controlled length data during deserialization), and nearcore itself acknowledges and mitigates this exact risk on the P2P network path, but not on the JSON-RPC path.

### Finding Description
`decode_signed_transaction` in `chain/jsonrpc/src/api/transactions.rs` performs: [1](#0-0) 
which base64-decodes the client-supplied string and immediately calls `SignedTransaction::try_from_slice(&bytes)` with no length/size check beforehand. This function is invoked from `RpcSendTransactionRequest::parse`, the entry point for the unprivileged `broadcast_tx_async`, `broadcast_tx_commit`, and `send_tx` JSON-RPC methods: [2](#0-1) 

By contrast, nearcore's own P2P network layer explicitly recognizes and defends against this exact class of bug. The comment and constant in `chain/network/src/network_protocol/proto_conv/peer_message.rs` describe the precise threat: a maliciously inflated transaction payload can exhaust node memory "at decode time" during Borsh deserialization, and a hard cap (`MAX_TRANSACTION_SIZE_BYTES`, 16 MiB) is enforced before decoding: [3](#0-2) 
The associated helper enforces the limit prior to calling into `T::try_from_slice`: [4](#0-3) 

The `serde::Deserialize` impl for `SignedTransaction` used elsewhere (e.g., when a signed transaction is embedded inside JSON RPC params) has the identical gap — it base64-decodes then calls `borsh::from_slice` with no length ceiling: [5](#0-4) 

I was unable to find any HTTP-layer request/body size limit configured for the JSON-RPC server (no `PayloadConfig`, `JsonConfig`, or similar body-size limiting code was found in `chain/jsonrpc`), so the size of the base64 payload accepted at the HTTP layer appears unbounded by nearcore's own code, leaving the Borsh decode step as the only potential backstop — and that step has no cap on this path.

Whether this is actually exploitable in practice ultimately also depends on how the Borsh crate itself allocates buffers for length-prefixed vectors/strings during `try_from_slice` (e.g., whether it pre-allocates `Vec::with_capacity(len)` for an attacker-supplied `len` field before validating that the input actually contains that many bytes). That behavior lives in the external `borsh` dependency, not in nearcore's own code, and per the scoping rules a "dependency-only" bug is out of scope; I could not verify borsh's internal allocation strategy since dependency source isn't part of this index. What is in-scope and verifiable, however, is that nearcore added a size-limiting guard for the network/peer path specifically to close this gap, and did not add the equivalent guard for the JSON-RPC transaction-submission path.

### Impact Explanation
If Borsh's vector/string deserialization pre-allocates capacity based on an attacker-supplied length field before validating it against the actual remaining input length, an attacker (any unprivileged RPC client — no validator or peer status required) could submit a `broadcast_tx_async`/`broadcast_tx_commit`/`send_tx` request whose base64 payload decodes to bytes encoding a huge claimed vector/string length (e.g., within `Transaction.actions`, `FunctionCallAction.args`, or similar variable-length fields), forcing a large allocation attempt on the node before any content or signature validation happens. Repeated requests could exhaust node memory, causing a crash or degraded service (denial of service) on the specific node handling the RPC call.

### Likelihood Explanation
Likelihood is uncertain because it hinges entirely on Borsh's internal allocation strategy, which could not be inspected in this codebase (out of index scope, dependency code). If Borsh itself already bounds vector pre-allocation to a small constant (as `serde`'s `size_hint::cautious` does, referenced in the original report) or validates length against remaining bytes before allocating, this path is not exploitable and the missing RPC-side cap is a defense-in-depth gap rather than an active vulnerability. If Borsh does not bound allocation this way, the missing cap on the JSON-RPC path (in contrast to the explicit, documented cap added for the P2P path) makes this directly reachable by any external, unauthenticated JSON-RPC caller.

### Recommendation
Apply the same mitigation used in `chain/network/src/network_protocol/proto_conv/util.rs` (`try_from_slice_with_limit`) to the JSON-RPC transaction decode path: reject the base64-decoded transaction bytes in `decode_signed_transaction` (`chain/jsonrpc/src/api/transactions.rs`) and in `SignedTransaction`'s `serde::Deserialize` impl (`core/primitives/src/transaction.rs`) if they exceed a size bound (e.g., the existing `MAX_TRANSACTION_SIZE_BYTES` or `max_transaction_size` parameter) before calling `try_from_slice`/`borsh::from_slice`. Additionally, configure an explicit HTTP request body size limit on the JSON-RPC server so oversized payloads are rejected before JSON/base64 parsing even begins.

### Proof of Concept
Not independently verifiable from static analysis alone, since exploitability depends on Borsh's internal deserialization allocation behavior, which is outside this repository's indexed code. The verifiable structural PoC path is:

fn decode_signed_transaction(value: String) -> Result<SignedTransaction, RpcParseError> {
    let bytes = near_primitives::serialize::from_base64(&value)

}

/// enforced before the body is deserialized to mitigate maliciously inflated
/// transactions exhausting node memory at decode time. Set comfortably above
/// the largest valid transaction (`max_transaction_size`, historically 4 MiB)

/// Borsh-deserializes `T` from `bytes`, rejecting inputs larger than `limit`
/// before decoding so a maliciously inflated peer payload cannot force a large
/// allocation at decode time. Use this for any peer-supplied borsh blob whose
/// decoded form can be much larger than its wire size; `limit` must sit above
/// the largest legitimate encoding of `T` and well below the peer-frame cap.
/// Returns `io::Error` so it composes with the borsh-based proto decode sites.
pub fn try_from_slice_with_limit<T: BorshDeserialize>(bytes: &[u8], limit: usize) -> io::Result<T> {
    if bytes.len() > limit {
        return Err(io::Error::new(
            io::ErrorKind::InvalidData,
            format!("encoded size {} exceeds the limit of {limit} bytes", bytes.len()),
        ));
    }
    T::try_from_slice(bytes)
}
