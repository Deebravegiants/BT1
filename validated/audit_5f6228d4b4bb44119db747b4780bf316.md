### Title
Unbounded loop in GRANDPA `AncestryChain::ancestry` allows a relayer-submitted finality proof to hang/OOM a node processing an unsigned consensus message - (File: `modules/consensus/grandpa/primitives/src/justification.rs`)

### Summary
`AncestryChain::ancestry` walks parent-hash pointers from a target block back to a base block using a `while current_hash != base` loop over a `BTreeMap` built directly from the attacker-supplied `finality_proof.unknown_headers` field. There is no cycle detection, no bound on the number of steps taken relative to the number of distinct headers, and no protection against a header whose `parent_hash` field points to another header already present in the same submitted set, forming a loop that never reaches `base`.

### Finding Description
`verify_grandpa_finality_proof` builds an `AncestryChain` from `finality_proof.unknown_headers`, a `Vec<H>` that is fully attacker-controlled and part of the `ConsensusMessage` decoded from an unsigned extrinsic: [1](#0-0) 

The `ancestry` walk itself has no loop-termination guarantee other than eventually hitting a hash missing from the map: [2](#0-1) 

Each `H` in `unknown_headers` is keyed in the `BTreeMap` by its genuinely recomputed hash (`h.hash()`), but its `parent_hash()` field is an independent, attacker-chosen value inside the header body — nothing ties `parent_hash` to any real chain relationship for headers that only need to pass this ancestry-walk / justification check, not full header-validity rules of the origin chain. A relayer can therefore submit two (or more) headers, A and B, in `unknown_headers`, where `A.parent_hash = hash(B)` and `B.parent_hash = hash(A)`. Once `ancestry()` is called on any target that is reachable into this pair (e.g., via `headers.ancestry(from, target.hash())` or `headers.ancestry(base.hash(), consensus_state.latest_hash)`), the walk will alternate between A and B forever: `current_hash` will never equal `base`, and `self.ancestry.get(&current_hash)` will always succeed (both entries are legitimately present in the map), so the loop and the ever-growing `route` vector never terminate.

This is directly analogous to the CVE-2019-2966 bug class: adversary-controlled input (a malformed but structurally valid input, here `unknown_headers`) drives an internal traversal into an unbounded/looping computation, causing a hang (denial of service) rather than a memory-safety violation.

The call is reachable by any relayer without special privilege: `pallet-ismp`'s `handle_unsigned` extrinsic accepts `Message::Consensus` messages from unsigned origin and calls `Self::execute`, which invokes the registered `ConsensusClient::verify_consensus` for GRANDPA: [3](#0-2) [4](#0-3) 

This same code path executes both during `validate_unsigned` transaction-pool validation and during dispatch/execution, so a malicious extrinsic that hits the cycle will hang the node's transaction-pool validation logic and/or block execution, which is a scheduler-level liveness (availability) issue, not merely a wasted transaction fee (there is no fee here since it's unsigned).

### Impact Explanation
An attacker submits a crafted GRANDPA `ConsensusMessage`/`FinalityProof` with a cyclic `unknown_headers` set via the free, unsigned `handle_unsigned` path. When `verify_grandpa_finality_proof` calls `AncestryChain::ancestry`, the traversal never terminates, consuming unbounded CPU and steadily growing memory (`route` vector) until the node hangs or is OOM-killed. Because this runs inside `validate_unsigned`/block execution for the GRANDPA consensus client shared by every parachain and standalone chain tracked with GRANDPA, this can stall transaction-pool validation and/or block production — a chain-wide liveness/availability impact, consistent with a Medium severity DoS.

### Likelihood Explanation
Exploitation requires only constructing two (or more) headers of type `H` whose `parent_hash` fields point to each other while each hashes to a distinct value under the real hash function — trivial to construct off-chain since `parent_hash` is just an arbitrary field, not derived from `hash()`. No signatures, authority membership, or special permissions are needed to reach the `AncestryChain::new`/`ancestry` code path; a relayer just needs `unknown_headers` to include the cyclic pair and the surrounding proof to reach the point where `ancestry()` is invoked on a target/base combination that walks through the cycle before failing validation (e.g., before the justification signature check, on the `headers.ancestry(base.hash(), consensus_state.latest_hash)` and `headers.ancestry(from, target.hash())` calls). This is easily achievable and repeatable.

### Recommendation
Bound the `ancestry` traversal: track visited hashes in a `BTreeSet`/`HashSet` and return an error (`Error::InvalidAncestry` or a new `CyclicAncestry` variant) as soon as a hash is revisited, or cap the number of iterations to `unknown_headers.len() + 1` (the maximum possible chain length given the map's size). Apply the same defensive check to any other place that performs a similar parent-hash walk over relayer-supplied header sets (e.g., in the fraud-proof handling paths that also build `AncestryChain` from proof-supplied headers).

### Proof of Concept
1. Construct header `A` with an arbitrary body such that `hash(A) = H_A`, and set `A.parent_hash = H_B` (a hash you will assign to header `B`).
2. Construct header `B` with `hash(B) = H_B` and `B.parent_hash = H_A`.
3. Submit a `FinalityProof` whose `unknown_headers = [A, B, ...]` (with valid `target`/`block` set to the highest-numbered header so the `LatestBlockMismatch` check passes) and any signed commit/justification structured so that the flow reaches `headers.ancestry(from, target.hash())` or `headers.ancestry(base.hash(), consensus_state.latest_hash)` where the traversal from `target`/`consensus_state.latest_hash` passes through `A`/`B`.
4. Submit this as `Message::Consensus` in a `handle_unsigned` unsigned extrinsic (or via the equivalent `pallet_call_decompressor::decompress_call` path) to a chain running `pallet-ismp` with the GRANDPA consensus client.
5. Observe that `AncestryChain::ancestry` loops indefinitely between `A` and `B`, hanging the extrinsic's `validate_unsigned`/execution and growing `route` without bound, denying service to the node.

impl<H: HeaderT> finality_grandpa::Chain<H::Hash, H::Number> for AncestryChain<H>
where
	H::Number: finality_grandpa::BlockNumberOps,
{
	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}
