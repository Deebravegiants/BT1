### Title
Self-deletable validator accounts can trigger a fatal `StorageInconsistentState` panic in `update_validator_accounts`, halting the chain - (File: `runtime/runtime/src/lib.rs`)

### Summary
The OctoDeFi report describes a push-based fund-distribution routine (`FeeHandler.handleFee()`) that assumes every payee address remains valid/receivable forever; if one payee (e.g. `creator`) becomes unusable, the *entire* future automation reverts, causing a persistent denial of service. nearcore has a structurally identical pattern in `Runtime::update_validator_accounts`, which pushes stake/reward balances to validator accounts recorded up to three epochs earlier, assuming those accounts still exist. If an account that was a validator in one of the last three epochs no longer exists at the moment the pending return-stake is applied, the runtime does not gracefully skip or refund the amount — it returns a **fatal** `StorageError::StorageInconsistentState`, which is nearcore's "this should never happen" invariant-violation path.

### Finding Description
`Runtime::update_validator_accounts` iterates `validator_accounts_update.stake_info`, a map of `account_id -> max_of_stakes` built by `EpochManager::compute_stake_return_info` as the maximum locked stake over the **last three epochs** (`chain/epoch-manager/src/lib.rs:1648-1688`, `max_of_stakes = max(prev_prev_stake, prev_stake, new_stake)`). At the first block of a new epoch, `process_state_update` (`chain/chain/src/runtime/mod.rs:241-273`) constructs this map and passes it to `Runtime::apply`.

This code assumes the invariant "if `max_of_stakes > 0` the account must still exist" always holds. The invariant is enforced only by `check_actor_permissions`/`action_delete_account`, which reject `DeleteAccount` when the account's **current** `locked()` balance is non-zero (per `protocol-model/spec/runtime-execution.md`: "no-stake for delete"). This check only inspects the account's *current* locked balance at deletion time — it has no knowledge of `max_of_stakes`, which looks back over the previous two completed epochs plus the pending one.

Because of the two-epoch lead time in NEAR's staking model (a `Stake`/unstake action submitted in epoch T only fully unlocks the funds after ~2 epochs, and `max_of_stakes` still remembers the stake amount from up to 3 epochs back), an account can:
1. Stake and become a validator.
2. Fully unstake (driving `locked()` to zero as soon as the unstake amount is returned to `amount()`).
3. Self-delete via `DeleteAccount` while `locked() == 0` — which `check_actor_permissions` allows, since it only checks the *current* lock.
4. Still have `max_of_stakes > 0` recorded in `stake_info` for one of the following epoch boundaries (because `compute_stake_return_info` looks back over the last three stake-change snapshots, which can still contain the historical stake even though the account already unstaked and was permitted to delete itself).

When the epoch boundary is later processed, `update_validator_accounts` looks up the now-deleted account, finds `None`, sees `max_of_stakes > 0`, and returns the fatal `StorageInconsistentState` error. `StorageError::StorageInconsistentState` in nearcore is explicitly documented as a corruption-signaling, unrecoverable state (used throughout `lib.rs` for invariants that "must never happen"), and propagating this out of `Runtime::apply` at an epoch boundary is treated as fatal for chunk/block application across every node applying that shard.

### Impact Explanation
This is a chain-halting bug reachable purely through normal, unprivileged account/staking actions (become a validator via `Stake`, unstake, delete account) — no malicious validator collusion or network-layer access is required. Because the failure happens inside deterministic state-transition logic (`update_validator_accounts`, run by every node applying the shard containing the deleted account), it would either:
- crash/panic every node processing that shard at the epoch boundary (matching the report's "reverting recipient blocks all future execution" DoS pattern, but escalated to full node panic / chain stall), or
- otherwise leave the affected shard permanently unable to progress past that epoch boundary, since the same deterministic inputs reproduce the same fatal error on retry.

This directly parallels the reported bug class: a push-style balance-distribution routine that assumes a fixed set of recipients remain valid, and fails catastrophically (rather than degrading gracefully) when one recipient becomes invalid — except in nearcore the blast radius is the entire shard/chain rather than a single DeFi automation.

### Likelihood Explanation
Triggering this requires only standard, permissionless actions available to any account: staking (becoming a validator with even minimal stake, depending on `seat_price`/threshold), then fully unstaking, then self-deleting the account before the "look-back" window (3 epochs) of `max_of_stakes` has fully rolled past the account's stake history. The precise timing window between "current locked() reaches 0" (allowing self-delete) and "`max_of_stakes` for that account reaches 0 in `stake_info`" needs empirical confirmation against `compute_stake_return_info`'s epoch bookkeeping, since I was not able to fully trace every write path that updates `stake_change`/`EpochInfo` per epoch within the available context. This uncertainty is the main open question in an otherwise directly-supported code path.

### Recommendation
- In `update_validator_accounts`, do not treat "recorded `max_of_stakes` account missing" as an unconditional fatal invariant violation. Cross-check against whether the account was permitted to self-delete (i.e., record and honor pending stake-return obligations before allowing `DeleteAccount`, or block deletion until the account's stake fully clears the 3-epoch look-back window used by `compute_stake_return_info`).
- Alternatively, harden `check_actor_permissions`/`action_delete_account` to reject deletion of any account that still has a nonzero `max_of_stakes` obligation pending in `stake_info`, not merely a nonzero *current* `locked()` balance.
- As a defense in depth, avoid modeling this class of invariant violation as an unrecoverable panic; where possible, degrade gracefully (e.g., skip the missing account's stake return and log/alert) rather than aborting shard/block processing entirely.

### Proof of Concept
Conceptual sequence (exact epoch-boundary timing needs test-loop verification against `chain/epoch-manager/src/lib.rs:compute_stake_return_info` and `EpochInfo::stake_change`):
1. Account `victim.near` submits a `Stake` action with enough stake to become a validator.
2. After being selected as validator for epoch T, `victim.near` submits `Stake` with `stake = 0` (full unstake) so that once the stake-return is processed, `account.locked() == 0`.
3. As soon as `locked() == 0`, `victim.near` submits `DeleteAccount` — this passes `check_actor_permissions`'s "no-stake for delete" check since current `locked()` is zero.
4. At a subsequent epoch boundary (within the 3-epoch look-back window used by `compute_stake_return_info`), `EpochManager::compute_stake_return_info` still includes `victim.near` in `stake_info` with `max_of_stakes > 0` (from its earlier stake_change snapshot).
5. `Runtime::update_validator_accounts` looks up `victim.near`, finds no account, and hits the `else if *max_of_stakes > Balance::ZERO` branch, returning `StorageError::StorageInconsistentState`, propagated as a fatal error from `Runtime::apply` for that shard/epoch boundary.
