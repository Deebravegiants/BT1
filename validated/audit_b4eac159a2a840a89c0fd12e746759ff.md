### Title
Permissionless pool creation allows a malicious coin/pc mint with freeze authority to permanently freeze pooled LP funds - (File: program/src/processor.rs)

### Summary
`process_initialize2` lets anyone create a pool for arbitrary `coin_mint`/`pc_mint` accounts, validating only that the newly-created LP mint has no freeze authority. It never checks whether the attacker-supplied `coin_mint` or `pc_mint` itself has a freeze authority.

### Finding Description
In `Processor::process_initialize2`, the coin and pc mints are unpacked with `Self::unpack_mint(&amm_coin_mint_info, spl_token_program_id)` and `Self::unpack_mint(&amm_pc_mint_info, spl_token_program_id)` [1](#0-0)  with no subsequent check on `coin_mint.freeze_authority` or `pc_mint.freeze_authority`. Compare this to the explicit check performed on the LP mint a few lines later:
```
if lp_mint.freeze_authority.is_some() {
    return Err(AmmError::InvalidFreezeAuthority.into());
}
``` [3](#0-2) 

Since `Initialize2` is fully permissionless (any signer can call it, per the account list documented in `AmmInstruction::Initialize2`) [4](#0-3) , a malicious actor can create a token mint that looks legitimate (e.g., matching a well-known token's metadata) while retaining freeze authority, then create an AMM pool using it as `coin_mint` or `pc_mint`. Other users who deposit into this pool via `process_deposit` or perform swaps have their input tokens transferred into the AMM's `coin_vault`/`pc_vault` token accounts, owned by the AMM authority PDA [5](#0-4) . At any later point, the mint's freeze authority (attacker-controlled) can freeze the `amm_coin_vault` or `amm_pc_vault` token account (an SPL Token Program operation available to any freeze authority holder), or freeze depositors' own destination token accounts for that mint. Once the vault account is frozen, `Invokers::token_transfer_with_authority` calls used in `process_withdraw` and the swap paths (`process_swap_base_in`/`process_swap_base_out` and their v2 variants) will fail, since SPL Token disallows transfers from/to frozen accounts [6](#0-5) [7](#0-6) . This permanently locks all LP funds (both coin and pc side, since AMM math requires proportional withdrawal) in the pool for every liquidity provider, not just the party who created the malicious mint.

### Impact Explanation
This is a permanent freezing of user/LP funds: once the malicious mint's freeze authority freezes the vault account, no LP can withdraw or swap through that pool, and there is no path in the program to change/removal the vault's frozen state (only the SPL Token freeze authority can thaw it, and the program is not that authority). This matches the "permanent freezing of user or LP funds" criterion and is analogous to the reported malicious-ERC20 asset-freeze bug class from the Kairos report, translated to Raydium's mint validation at pool creation.

### Likelihood Explanation
Likelihood is high: creating an SPL token mint with a freeze authority and a deceptive name/symbol is trivial and requires no special privilege; `Initialize2` requires only a fee payment and does not require any allow-list or attestation about the mint's freeze authority. Depositors have no on-chain way to detect that the pool's mint carries a freeze authority before depositing, since the program itself performs no such check for `coin_mint`/`pc_mint`.

### Recommendation
Add the same freeze-authority check already applied to `lp_mint` to both `coin_mint` and `pc_mint` in `process_initialize2`, e.g.:
```rust
if coin_mint.freeze_authority.is_some() || pc_mint.freeze_authority.is_some() {
    return Err(AmmError::InvalidFreezeAuthority.into());
}
```
placed immediately after the existing `Self::unpack_mint` calls at [1](#0-0) , rejecting pool creation for any mint that retains a freeze authority.

### Proof of Concept
1. Attacker creates SPL mint `M` with `initialize_mint` specifying itself as `freeze_authority` (and optionally naming/branding it to resemble a well-known token like USDC).
2. Attacker calls `Initialize2` supplying `M` as `pc_mint` (or `coin_mint`), funding the pool with `init_pc_amount`/`init_coin_amount`; `process_initialize2` accepts this because only `lp_mint.freeze_authority` is checked [2](#0-1) .
3. A victim LP calls `Deposit`, transferring token `M` into `amm_pc_vault_info`/`amm_coin_vault_info` via `Invokers::token_transfer` [8](#0-7) .
4. Attacker (freeze authority of `M`) issues an SPL Token `FreezeAccount` instruction against the AMM's vault token account for `M`.
5. The victim (and every other LP) can no longer withdraw or swap through the pool: `process_withdraw`'s `token_transfer_with_authority` call on the frozen vault fails [6](#0-5) , permanently locking pooled funds.
