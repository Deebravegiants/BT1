Webhook shop-domain identity is trusted without HMAC coverage, allowing cross-tenant spoofing of `WebhookMetadata#shop` - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop` attribute consumed by application webhook handlers is read directly from the `x-shopify-shop-domain` HTTP header, which is never included in the signed material. This breaks the intended equality "HMAC-authenticated request == the tenant identity handed to the app," analogous to the axelar-core report's root cause: a value that is trusted/logged/acted upon is not actually covered by the same validation as the rest of the message. Here the un-covered field is `shop`, not a log line, but the structural bug class (verified bytes ≠ trusted field) is the same.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0)  and `Request#hmac` decodes the `hmac-sha256`/`x-shopify-hmac-sha256` header [2](#0-1) . `Request#shop`, however, is read straight from the `shop-domain` header with no cryptographic binding to the signed payload [3](#0-2) .

`Utils::HmacValidator.validate` verifies `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` [4](#0-3) , so only the body is checked; the `shop` header is completely outside this check.

`Registry.process` uses this unauthenticated `shop` value directly when constructing the `WebhookMetadata` passed to the app's handler: it validates the HMAC, then builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` [5](#0-4) . Because `WebhookHandler#handle` receives this `shop` field as part of the trusted `WebhookMetadata` struct [6](#0-5) , any application that uses `data.shop` to select a tenant, session, or database record (a normal and documented usage pattern for multi-tenant Shopify apps) is trusting a value the gem itself never authenticated.

Compare this with the OAuth callback path: `AuthQuery#to_signable_string` explicitly includes `shop` in the signed parameters [7](#0-6) , so that path correctly binds shop identity to the HMAC. The webhook `Request` class does not follow the same pattern, creating an inconsistency where the shop identity binding that exists elsewhere in the gem is absent for webhooks.

### Impact Explanation
This matches the "Critical - cross-tenant access" impact category. An attacker who obtains one genuine, Shopify-signed webhook body+HMAC pair (trivially available to any developer who installs the target app on their own free/trial development store and triggers an event) can replay that exact body and HMAC to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `Utils::HmacValidator.validate` will still pass because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the forged shop. Any app that uses `data.shop` from `WebhookHandler#handle` to look up a session, tenant record, or perform per-shop side effects (the intended and expected use of this field, as it is the only tenant identifier provided by the SDK for this callback) will act on behalf of, or against, a shop the attacker does not own — a cross-tenant identity confusion rooted entirely in this gem's `Request`/`HmacValidator`/`Registry` code.

### Likelihood Explanation
Likelihood is moderate-to-high: the prerequisite (a legitimately signed webhook body from any shop, including a low-privilege trial store the attacker fully controls) is easy for any unprivileged internet user/developer to obtain, and no secret, access token, or privileged account of the *target* tenant is required — only network access to the app's public webhook endpoint and one real webhook from any shop.

### Recommendation
Include the shop-domain header (and any other headers whose values are later trusted by `WebhookMetadata`, e.g. `topic`, `api-version`) in the HMAC-signable string in `Request#to_signable_string`, or otherwise cryptographically bind the shop identity to the signature (e.g., verify it against the shop associated with the currently active session/registration rather than trusting the header verbatim). At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used for tenant selection without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and triggers a webhook event (e.g., `orders/create`), capturing the raw POST body `B` and the valid `x-shopify-hmac-sha256` header `H` that Shopify computed over `B` with the app's shared secret.
2. Attacker sends a POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Request.new` accepts the request (all required headers present) [8](#0-7) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only re-derives the HMAC over `@raw_body` [9](#0-8) .
4. The registered `WebhookHandler#handle` is invoked with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the body/content actually originated from the attacker's own shop — a forged tenant identity accepted as authentic by the gem.
