### Title
Webhook Shop/Topic Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its verifiable signature over the raw HTTP body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values used downstream by `ShopifyAPI::Webhooks::Registry.process` are taken from HTTP headers that are never included in the signed content. Any party who can obtain one legitimately-signed `(raw_body, hmac)` pair — trivially available to anyone who installs the app on a store they control — can replay that exact body/HMAC pair while forging the `X-Shopify-Shop-Domain` (and other) headers to make the library attribute the payload to an arbitrary victim shop.

### Finding Description
The identity binding that should hold is:

`shop used by the handler == shop cryptographically bound to the signed payload`

but the implementation only enforces:

`hmac(raw_body) == received_hmac`

`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read straight from headers that are excluded from the signable string: [2](#0-1) 

`HmacValidator.validate` only ever calls `validate_signature`, which hashes `verifiable_query.to_signable_string` (i.e., the body) and nothing else: [3](#0-2) 

`Registry.process` validates the HMAC, then immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — none of which are covered by the check that just passed — to build the metadata passed to the app's handler: [4](#0-3) 

Because the headers are not part of the signed content, two requests with identical `raw_body`/`hmac` but different `shop-domain` headers both pass `HmacValidator.validate` and are processed identically except for the `shop` value handed to the app's webhook handler.

### Impact Explanation
`Registry.process` hands `request.shop` directly to the app's `WebhookHandler` via `WebhookMetadata`, which host applications commonly use to look up the tenant record to which the webhook body should be applied (e.g., "update order X for shop Y"). Since `shop` is not bound to the HMAC, an attacker who can obtain any single valid `(body, hmac)` pair — for example by installing the app on their own development store and capturing a real webhook delivery — can replay that pair against the app's public webhook endpoint with a forged shop-domain header naming a victim shop. The library will report this as a validly-signed webhook for the victim shop, causing the host application to process attacker-controlled data (order/customer/product payload) under another tenant's identity — a cross-tenant integrity violation reachable by any unprivileged party who has ever received one legitimate webhook from the app.

### Likelihood Explanation
Likelihood is high for any app that installs on more than one shop (i.e., any public or multi-merchant app): obtaining one legitimate `(body, hmac)` sample requires nothing more than installing the app on an attacker-owned store and subscribing to any webhook topic — no access token, no `api_secret_key`, and no privileged account are needed. The webhook endpoint is by design public/unauthenticated (Shopify calls it without any additional caller authentication), so replay with a modified header is a simple HTTP request.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) in the signable content, or otherwise cryptographically bind them to the HMAC check, e.g., by validating that `request.shop` matches an expected/allow-listed value tied to the session/tenant the webhook is being processed for, in addition to verifying the raw-body HMAC. At minimum, document that `request.shop`/`request.topic` must not be trusted as tenant-identifying values unless independently corroborated (e.g., cross-checked against the shop that owns the `webhook_id` via a follow-up API call).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and configures a webhook subscription (e.g. `orders/create`).
2. Attacker triggers the event (creates an order) and captures the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` that Shopify sends — this HMAC is valid because it was produced by Shopify using the app's `api_secret_key` for body `B`.
3. Attacker resends the exact same request to the app's public webhook endpoint, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation passes.
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, causing the host application to apply attacker-chosen data under the victim tenant's identity. [5](#0-4)
