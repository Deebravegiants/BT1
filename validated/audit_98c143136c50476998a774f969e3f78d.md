### Title
Fee-on-Transfer / TRC20-fee tokens break escrow accounting in Tron `IntentGatewayV2.placeOrder`, enabling escrow insolvency and fund freezing/theft on withdrawal - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The main EVM `IntentGatewayV2` (`evm/src/apps/IntentGatewayV2.sol`) has already been hardened against fee-on-transfer (FoT) tokens: it snapshots token balances before/after `safeTransferFrom` and mutates `order.inputs[i].amount` to the *actual received* amount before computing the commitment and crediting escrow [1](#0-0) . The Tron fork of the same contract (`evm/tron/contracts/apps/IntentGatewayV2.sol`) does not have this fix and still exhibits the exact bug class from the original Gitcoin Allo `_fundPool` report.

### Finding Description
In `placeOrder`, the protocol fee is computed from the user-supplied `order.inputs[i].amount` and the commitment/`reducedInputs` are derived from that nominal amount *before* any token transfer occurs: [2](#0-1) 

Then, in the no-predispatch escrow path, the contract calls `safeTransferFrom` with the *nominal* `order.inputs[i].amount` (not the balance actually received) and immediately credits `_orders[commitment][token]` with `reducedInputs[i].amount`, which is derived from the nominal amount, not the actual tokens held: [3](#0-2) 

The predispatch path has the same issue: dust is computed as `balance - requiredAmount` using `order.inputs[i].amount` as `requiredAmount`, but the escrow credit uses `reducedInputs[i].amount` (based on nominal input), not the actually swept `balance`: [4](#0-3) 

If the escrowed token is a fee-on-transfer / deflationary TRC20 (or any token that skims a fee on `transferFrom`), the gateway's actual token balance increase is strictly less than `reducedInputs[i].amount`, yet `_orders[commitment][token]` records the full nominal (minus protocol-fee) amount as if it were fully backed. Since `_orders` is a global per-token/per-commitment ledger against a single shared TRC20 balance, this creates a per-order accounting entry that overstates real backing.

On withdrawal (`withdraw`, called from `onAccept`/`RedeemEscrow`/`RefundEscrow`, or `cancelOrder`), the contract unconditionally transfers the full recorded `amount` from `_orders[commitment][token]`: [5](#0-4) 

Because every order sharing that token draws from the same pooled token balance, the shortfall caused by one FoT-token order is paid for out of other, unrelated orders' legitimately-escrowed balances (first-claimant advantage), or later legitimate redemptions revert due to insufficient contract balance — a straightforward escrow insolvency / fund-freezing vector reachable by any unprivileged user simply placing an order with a fee-on-transfer token.

### Impact Explanation
This is directly reachable by any user submitting a `placeOrder` transaction with a fee-on-transfer token as input — no privileged role required. The result is either:
- Theft: a user/solver who is fast to redeem drains more tokens than were actually deposited for their order, at the expense of other users' escrowed funds sharing that token.
- Freezing of funds: subsequent legitimate `withdraw` calls (RedeemEscrow/RefundEscrow/cancelOrder) fail because the token's actual balance is insufficient to cover all outstanding `_orders[...][token]` entries, permanently locking honest users' funds.

This matches the "concrete theft or permanent freezing of funds" bar for Medium/High severity.

### Likelihood Explanation
Likelihood is moderate: it requires the gateway to be deployed to accept a fee-on-transfer/deflationary token as an escrow input. Given Hyperbridge's Intent Gateway is designed to be permissionless with respect to which ERC20/TRC20 tokens can be used as order inputs (any `TokenInfo.token` address), and the Tron ecosystem includes TRC20 tokens with transfer taxes, this is a realistic configuration rather than a purely theoretical one. The same bug class was already identified and fixed in the mainline EVM contract, confirming the project itself considers FoT tokens an in-scope threat model — the Tron variant was simply not patched in parity.

### Recommendation
Apply the same fix already present in `evm/src/apps/IntentGatewayV2.sol` to the Tron contract: measure the gateway's/dispatcher's actual token balance before and after each `transferFrom`/sweep, mutate `order.inputs[i].amount` to the actually-received amount, and compute `reducedInputs`/`commitment`/escrow credits from that actual amount rather than the user-supplied nominal amount, for both the predispatch and non-predispatch paths.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with a TRC20 token that charges e.g. 1% fee on transfer (`FeeOnTransferToken`, mirroring the test helper already present at `evm/tests/foundry/IntentGatewayV2SameChainTest.sol:2690-2735`).
2. User calls `placeOrder` with `inputs[0] = {token: fot, amount: 1000e18}`, no protocol fee for simplicity.
3. Inside `placeOrder`, `reducedInputs[0].amount = 1000e18` (protocolFeeBps == 0 path uses `order.inputs` directly), commitment is computed with `1000e18`.
4. `IERC20(fot).safeTransferFrom(msg.sender, address(this), 1000e18)` is called; due to the 1% fee, gateway actually receives only `990e18`.
5. `_orders[commitment][fot] += reducedInputs[0].amount` credits `1000e18`, i.e., 10e18 more than the contract actually holds for this order.
6. Any subsequent `withdraw` (fill/refund) for this commitment attempts to `transfer` the beneficiary `1000e18` of `fot`, but the gateway's real balance for this order was only `990e18` — if it's the only order holding that token, the transfer underflows/fails at the TRC20 level or, if other orders share the token, drains their escrowed balance to cover the shortfall.
