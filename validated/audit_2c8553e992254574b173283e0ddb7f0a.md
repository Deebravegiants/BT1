### Title
BSC light client accepts finalized state commitments without verifying continuity to the previously trusted chain, enabling a 51%-style fork/equivocation to forge state roots - (File: `modules/ismp/clients/bsc/src/lib.rs`, `modules/consensus/bsc/verifier/src/lib.rs`)

### Summary
The BSV incident illustrates that a chain-level supermajority attacker can simultaneously produce multiple competing "finalized" chains. `BscClient::verify_consensus` and the underlying `verify_bsc_header` accept any quorum-signed (2/3 BLS) `BscClientUpdate` whose `source_header.number` is strictly greater than the previously stored `finalized_height`, but never check that `source_header` (or its ancestry) actually chains back — via `parent_hash` — to the client's previously accepted `finalized_hash`. A validator supermajority (or any relayer who can obtain/replay two independently-quorum-signed but mutually non-contiguous vote attestations) can therefore get an unrelated fork's header accepted as the new finalized BSC state, exactly analogous to BSV's "large-scale 51% attack" producing three simultaneously mined chain versions.

### Finding Description
`verify_bsc_header` in `modules/consensus/bsc/verifier/src/lib.rs` validates:
- quorum participation (`participant_count >= 2/3`) [1](#0-0) 
- that `target_header` is the direct child of `source_header` (BEP-126 two-consecutive-justified rule) [2](#0-1) 
- the aggregate BLS signature over the vote data [3](#0-2) 

Nowhere in this function, nor in its only caller `BscClient::verify_consensus`, is `source_header.parent_hash` (or any ancestry chain) checked against the client's currently trusted `consensus_state.finalized_hash`. The caller only enforces a height-monotonicity check: [4](#0-3) 

Because `verify_bsc_header` is never given the previous `finalized_hash` as an input, and `verify_consensus` never compares `update.source_header.parent_hash` (or the epoch ancestry chain) to `consensus_state.finalized_hash`, a quorum-signed update whose `source_header` builds on a completely different, non-canonical branch — but whose `number` is merely greater than the stored `finalized_height` — is accepted and overwrites `consensus_state.finalized_hash`/`finalized_height` and the committed `state_root` used for state-membership/non-membership proofs by `pallet-ismp` handlers.

The `verify_fraud_proof` path exists to punish equivocation *after the fact* (same target number, different target hash) [5](#0-4) , but it is a reactive detection mechanism, not a preventive continuity check, and it does nothing to stop the forged state root from being used to unlock ISMP requests/withdrawals in the window before a fisherman submits the fraud proof.

### Impact Explanation
If BSC's validator set is compromised or colludes (the same threat model a 51% attack represents for the source chain), an attacker can get an alternate/forked `state_root` committed as the trusted BSC state on Hyperbridge without any check that it descends from the previously accepted chain. Any `pallet-ismp` handler (`HandlerV2`, `handle_unsigned`) that subsequently accepts state-membership proofs against this forged `state_root` will treat forged storage entries as valid — enabling unbacked mint, forged message delivery, or draining of token-bridge/escrow contracts that rely on BSC state proofs. This is an unsound state commitment vulnerability with direct fund-theft potential, matching the "unsound state commitment" / "forged message delivery" impact categories.

### Likelihood Explanation
Exploitation requires control (or collusion) of a 2/3 BLS supermajority of the then-current BSC validator set — the same precondition as a real-world 51%-style attack — so likelihood is bounded by the security of the underlying chain's validator set, not by any Hyperbridge-side defense, since Hyperbridge's light client provides no additional continuity guard. Given BSC's validator set is smaller/more centralized than PoW chains and BEP-126 justification depends solely on signature quorum (no proof-of-work anti-reorg cost), a colluding/compromised supermajority is a realistic Medium-likelihood scenario, and the missing continuity check removes the one guard that would otherwise prevent Hyperbridge from ingesting the forged chain.

### Recommendation
In `BscClient::verify_consensus`, require and verify that `update.source_header.parent_hash` (directly, or via `epoch_header_ancestry`) equals `consensus_state.finalized_hash` before accepting the update, rejecting any update whose source branch does not chain from the last trusted finalized header. Thread the previous `finalized_hash` into `verify_bsc_header` so this continuity check is enforced at the verifier level rather than solely relying on height ordering.

### Proof of Concept
1. Attacker (controlling/colluding with ≥2/3 of the current BSC validator set) produces two divergent branches at/above the client's current `finalized_height`: branch A (canonical) and branch B (forged, with an attacker-chosen `state_root`).
2. Attacker has validators sign a valid BEP-126 vote attestation for branch B's `source_header`/`target_header` pair (consecutive, quorum-signed, matching `HeaderVoteDataMismatch`/`NonConsecutiveFinalization` checks).
3. Relayer submits this `BscClientUpdate` to `BscClient::verify_consensus`. Since `source_header.number > consensus_state.finalized_height` and BEP-126 adjacency/quorum checks pass, and no check compares `source_header.parent_hash` to `consensus_state.finalized_hash`, the update is accepted: [6](#0-5) 
4. `consensus_state.finalized_hash`/`state_root` now reflects branch B. Attacker crafts state-membership proofs against branch B's forged `state_root` to submit fraudulent ISMP requests/withdrawals before any fraud proof can be raised.
