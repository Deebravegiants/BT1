## Title
Fee token address is read dynamically at settlement time instead of snapshotted at dispatch time, permanently freezing relayer fees and refunds after a `feeToken` governance update - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch()` collects the relayer fee in whatever ERC20 is currently configured as `feeToken()` at the time a request is submitted, but only the fee *amount* is persisted in `FeeMetadata`, not the token address used to collect it. When the request is later settled (timeout refund or relayer reward), the contract calls `feeToken()` again and transfers from that *current* balance. If the host's `feeToken` parameter is updated via governance between dispatch and settlement, the settlement path will attempt to pay out of a token the host never actually collected, causing the transaction to revert and permanently freezing that request's relayer fee/refund.

### Finding Description
`dispatch(DispatchPost)` and `dispatch(DispatchGet)` pull the fee from the caller in the token returned by `feeToken()` at call time and store only `{sender, fee}` in `_requestCommitments`: [1](#0-0) 

Later, when the request times out or is handled, `dispatchTimeOut` and the GET-request handling path read `feeToken()` again — at settlement time — to transfer the refund/reward: [2](#0-1) [3](#0-2) 

`feeToken` is a mutable field of `HostParams`, updatable at any time via `IHostManager.updateHostParams`, which only the `hostManager` (a governance-controlled `IApp` receiving cross-chain governance messages) can invoke: [4](#0-3) 

The Rust-side host param update struct explicitly documents this exact hazard but does not enforce it on-chain: [5](#0-4) 

Because the actual enforcement (draining old fee token funds before rotating `feeToken`) is only a comment/convention and not a contract invariant, any pending request dispatched with the old `feeToken` whose settlement occurs after a `feeToken` rotation will have its refund/reward attempted against the new fee token's balance held by the host — which is zero or insufficient for the old fee amounts, causing `IERC20(feeToken()).safeTransfer(...)` to revert. Since Solidity reverts undo all state changes in the same call, the replay-protection deletion (`delete _requestCommitments[commitment]`) is also rolled back, meaning the request is retried indefinitely and permanently fails to settle — its relayer reward or user refund becomes permanently stuck, unreachable through any legitimate on-chain path.

### Impact Explanation
This breaks a core invariant of the fee/refund accounting for any request in flight at the moment of a legitimate `feeToken` rotation: relayers can never claim their delivery reward, and users can never recover their posted relayer fee on timeout, for outstanding requests submitted before the switch. Funds effectively become permanently frozen in the old fee token's balance held by the host contract, with no code path to release them since every settlement call for the affected commitment will keep reverting. This matches the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
`feeToken` rotation is an explicitly supported governance operation (`updateHostParams`), and the codebase itself acknowledges the risk in commentary, confirming it is a realistic operational scenario rather than a contrived edge case. Any in-flight request (POST/GET with nonzero fee) spanning a `feeToken` update is affected — this can happen from a single relayed governance request without any additional privileged or malicious behavior on the destination path.

### Recommendation
Snapshot the fee token address (not just the amount) into `FeeMetadata` at dispatch time, and use that stored token address — rather than the live `feeToken()` — when refunding or rewarding fees for that specific commitment in `dispatchTimeOut`, `handleGetRequests`, and any other settlement path that pays out from `_requestCommitments`.

### Proof of Concept
1. User dispatches a POST request via `dispatch(DispatchPost)` with `fee = X`, paid in `feeToken_A` (fee pulled via `safeTransferFrom` at [6](#0-5) ).
2. Before the request is delivered or times out, governance sends a `updateHostParams` message rotating `_hostParams.feeToken` to `feeToken_B`.
3. The request later times out; `dispatchTimeOut` is invoked and attempts `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)`, where `feeToken()` now returns `feeToken_B` [7](#0-6) .
4. The host holds no (or insufficient) `feeToken_B` balance corresponding to `X`, so the transfer reverts, the whole transaction (including the state cleanup) reverts, and the fee for this commitment can never be settled.

    function dispatchTimeOut(
        PostRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onPostRequestTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit PostRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }

    function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                post.fee, path, address(this), block.timestamp
            );
        } else if (post.fee > 0) {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
        }

        // adjust the timeout
        uint64 timeoutTimestamp = post.timeout == 0 ? 0 : uint64(block.timestamp) + uint64(post.timeout);
        PostRequest memory request = PostRequest({
            source: host(),
            dest: post.dest,
            nonce: uint64(_nextNonce()),
            from: abi.encodePacked(_msgSender()),
            to: post.to,
            timeoutTimestamp: timeoutTimestamp,
            body: post.body
        });

        // make the commitment
        commitment = request.hash();
        _requestCommitments[commitment] = FeeMetadata({sender: post.payer, fee: post.fee});
