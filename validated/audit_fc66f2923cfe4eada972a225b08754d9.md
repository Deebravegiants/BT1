### Title
Webhook `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook attribution spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, which computes the HMAC over `request.to_signable_string`. For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only the raw body [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` fields are read directly from HTTP headers and are never included in the signed material [2](#0-1) , yet these header-derived values are what get forwarded, as trusted/verified data, into the app's `WebhookHandler#handle` callback.

### Finding Description
The intended binding is: `hmac == HMAC(api_secret_key, entire_request_that_the_shop_field_describes)`. In this gem, the binding actually enforced is `hmac == HMAC(api_secret_key, raw_body_only)`, while `shop` (and `topic`/`webhook_id`/`api_version`) are read from unauthenticated headers [3](#0-2) .

`Registry.process` performs the HMAC check and then immediately trusts `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` to build the `WebhookMetadata` handed to the app: [4](#0-3)  These values are never independently re-validated (e.g., there is no call to `Utils::ShopValidator.sanitize!` on `request.shop` anywhere in this path) despite `ShopValidator` existing elsewhere in the gem specifically to prevent trusting attacker-supplied shop strings [5](#0-4) .

Because the app's `api_secret_key` (a single shared value for the whole app, not per-shop) is used to compute the HMAC over the body only, any party who can obtain one valid `(raw_body, hmac)` pair — for example, from their own shop's webhook deliveries after installing the app, from webhook logs, or from a network intermediary — can replay that exact body and HMAC while substituting an arbitrary `shopify-shop-domain` header. The HMAC validation in `Utils::HmacValidator.validate` recomputes the signature purely from the body and will pass [6](#0-5) , since `AuthQuery`/`Request` both just implement the `VerifiableQuery` interface with `hmac` and `to_signable_string` [7](#0-6) .

### Impact Explanation
This breaks the tenant boundary the app relies on: the `shop` field in `WebhookMetadata`, which host applications use to attribute a webhook payload to a specific merchant (e.g., to look up/update that merchant's record, process a `shop/redact` or `customers/redact` request, or update per-shop state), is not authenticated by the same secret that made the HMAC pass. An attacker with a valid `(body, hmac)` pair for their own tenant can forge delivery of that payload "as" a victim shop, since the app's webhook handler receives an object claiming `shop:` a value it never validated. This is a cross-tenant confusion/attribution issue reachable purely through this gem's own webhook processing code, without needing the app's `client_secret`.

### Likelihood Explanation
Requires an attacker to first obtain one valid `(raw_body, hmac)` pair signed under the app's `api_secret_key` — achievable trivially by installing the app on their own shop (a normal, unprivileged flow for any public/embedded Shopify app) and capturing a webhook delivery, or by controlling the destination endpoint. From there, forging the `shopify-shop-domain` (and other) headers requires only standard HTTP tooling and no cryptographic secret, making the header-substitution step itself low effort.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signed material (or otherwise cryptographically bind them to the body), and/or have `Registry.process` validate `request.shop` through `Utils::ShopValidator.sanitize!` before constructing `WebhookMetadata`. At minimum, document that consumers of `WebhookHandler#handle` must not trust `data.shop` for tenant attribution unless independently verified.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com`, receiving genuine webhook deliveries signed with the app's `api_secret_key`.
2. Attacker captures a legitimate delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `HMAC(api_secret_key, B) == H`).
3. Attacker resends the identical body `B` and header `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is built; `Utils::HmacValidator.validate(request)` calls `to_signable_string` → returns `B` only, computes `HMAC(api_secret_key, B) == H` → validation succeeds: [8](#0-7) 
5. `Registry.process(request)` proceeds and invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, which the app treats as an authenticated event for the victim shop: [9](#0-8)
