### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant shop impersonation - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authentic for a given shop once `Utils::HmacValidator.validate(request)` succeeds, and then hands `request.shop` straight to the app's handler as the trusted tenant identity. However the HMAC only ever covers the raw request body, never the `shop-domain` header, so the "which shop is this event for" field is not bound to the cryptographic signature that authenticates the request.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . `#hmac` decodes the `hmac-sha256` header for comparison [2](#0-1) , and `#shop` simply reads the `shop-domain` header, entirely independent of the signed payload [3](#0-2) .

`HmacValidator.validate` computes `HMAC(api_secret_key, verifiable_query.to_signable_string)` and compares it to the received hmac [4](#0-3) , i.e. it only proves "this body was produced by someone holding `api_secret_key`" — it proves nothing about the `shop-domain` header.

`Registry.process` uses exactly this validator, then forwards `request.shop` (the unauthenticated header) into `WebhookMetadata` for the app-supplied handler to act on: [5](#0-4) .

The identity binding broken is: `shop` acted on by the handler ≠ `shop` covered by the HMAC. Since Shopify signs webhook bodies with the app's shared secret regardless of which store sent them, any store owner (an unprivileged actor who can trivially create a Shopify partner/dev store and install the target app) can capture a legitimate `(raw_body, hmac)` pair generated for *their own* store, then replay that exact pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop. `HmacValidator.validate` will still pass because it only checks the body/HMAC pair, and `Registry.process` will dispatch the handler with `data.shop` set to the attacker-chosen victim domain.

### Impact Explanation
This crosses a tenant boundary: an app relying on `request.shop`/`WebhookMetadata#shop` as the authoritative tenant identifier (a pattern this library's own `Request` class encourages, since it exposes `#shop` as a first-class accessor alongside `#topic` and `#body`) can be made to execute shop-scoped side effects (e.g., data deletion for GDPR "customers/redact"/"shop/redact" mandatory topics, cache invalidation, session teardown, billing state changes) against a shop the attacker does not own, using only a body/HMAC pair legitimately obtained for the attacker's own store. This is a cross-tenant access issue driven directly by a gem-level identity-binding gap, matching the Critical "cross-tenant access" impact class.

### Likelihood Explanation
Likelihood is high for topics whose handling logic does not depend on shop-specific content inside the body (e.g., mandatory compliance topics or topics with largely fixed/empty bodies), because the attacker only needs to obtain one genuine webhook delivery from their own store — something any developer can do for free — and can then forge the header on replay since headers are not authenticated at all by this design. No secret, employee access, or privileged account is required.

### Recommendation
Include the shop identity in the value that is HMAC-verified, or otherwise cryptographically/contextually bind `shop-domain` to the signed body before exposing it to handlers. Concretely:
- Extend `VerifiableQuery`/`Request#to_signable_string` (or add a separate check in `Registry.process`) so the shop-domain header is included in what is authenticated, e.g. by requiring apps to cross-check `request.shop` against a shop that is independently known to have valid, currently-active offline credentials for that exact domain before invoking the handler, and document/enforce this in `Registry.process` itself rather than leaving it entirely to the host app.
- At minimum, update `lib/shopify_api/webhooks/registry.rb` to reject/flag when `request.shop` cannot be correlated to a known installed session, rather than passing an unauthenticated header straight into `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on a store they control, `attacker-shop.myshopify.com`.
2. Shopify delivers a webhook to the app, e.g. `POST /webhooks` with body `{}` and headers:
   - `X-Shopify-Hmac-Sha256: <valid HMAC of "{}" with app's api_secret_key>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - `X-Shopify-Topic: shop/redact`
3. Attacker intercepts/logs this exact request, then replays it to the same endpoint, changing only the header:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - Body and `X-Shopify-Hmac-Sha256` are unchanged (still valid, since HMAC is computed over the unchanged body).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` — this passes because `to_signable_string` only checks `@raw_body`, which is unchanged: [1](#0-0) .
5. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `shop == "victim-shop.myshopify.com"`: [6](#0-5) .
6. The app's handler (which trusts the gem's authenticated-looking `WebhookMetadata#shop`) performs the `shop/redact` action against the victim shop's stored data.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
