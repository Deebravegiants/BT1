### Title
Webhook `shop`, `topic`, and `webhook_id` fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` field (along with `topic`, `webhook_id`, and `api_version`) from raw HTTP headers, but the HMAC signature that `Utils::HmacValidator` verifies is computed only over the request body. This breaks the binding "the shop attributed to a webhook == the shop whose secret produced the HMAC," letting any party who can obtain one legitimately signed webhook body replay it while freely relabeling which shop it came from.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` verifies the signature exclusively against `to_signable_string`, i.e. the body: [2](#0-1) 

Meanwhile, `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from headers that are never part of the signed material: [3](#0-2) 

`Registry.process` validates the HMAC and then trusts `request.shop`/`request.topic` to route and label the event for the handler: [4](#0-3) 

Because the signature only proves "this body was produced with the app's secret," not "this body belongs to shop X," an attacker who legitimately receives (or otherwise obtains) any single valid `(body, hmac)` pair for their own shop can replay that exact body/HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header for a different shop. `HmacValidator.validate` still returns true because it only checks the body, so `Registry.process` will hand the handler a `WebhookMetadata` claiming the event came from the victim shop, even though it was forged.

### Impact Explanation
This breaks the shop-to-signature identity binding required for webhook authenticity: `shop_claimed_in_header != shop_that_actually_produced(hmac, body)`. Any application logic that keys off `WebhookMetadata#shop` (e.g., looking up a merchant's session/store record, processing `app/uninstalled`, `customers/redact`, `shop/redact`, or crediting/state-changing logic per shop) can be triggered for an arbitrary victim shop by a party who only controls one legitimately-webhooked shop of their own — a cross-tenant impact, since the app never had a legitimate webhook from the claimed victim shop for that event.

### Likelihood Explanation
Exploitation requires no access to the app's `client_secret`/`api_secret_key` or any merchant's access token — only the ability to capture one authentic webhook delivery to any shop the attacker controls (trivial for anyone who can install/uninstall the app on their own store, or trigger a mandatory topic like `customers/redact`) and resend it to the app's public webhook endpoint with modified headers.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed material, or otherwise cryptographically bind the header-derived identity fields to the verified body, e.g. incorporate `shop-domain`/`topic`/`webhook-id` into `to_signable_string` used for HMAC verification, or perform an independent authenticated lookup instead of trusting header values post-HMAC check.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and captures a legitimately delivered webhook: body `B`, header `shopify-hmac-sha256: H` (valid HMAC of `B` under the app's secret), `shopify-topic: orders/create`, `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker POSTs the same body `B` and same `shopify-hmac-sha256: H` to the app's webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `shopify-topic`, e.g. `customers/redact`, `webhook_id`).
3. `Utils::HmacValidator.validate` recomputes the HMAC over `B` only and finds it matches `H`, so `Registry.process` proceeds and dispatches `WebhookMetadata.new(topic: "customers/redact", shop: "victim-shop.myshopify.com", body: parsed(B), ...)` to the handler as if this were a genuine event from `victim-shop`.
