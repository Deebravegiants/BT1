### Title
Unbounded native-token spend in `placeOrder`'s fee-token swap enables sandwich extraction from order placers - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder` swaps a user's native ETH for the exact fee-token amount (`order.fees`) via `IUniswapV2Router02.swapETHForExactTokens`, passing the entire remaining `msgValue` as the implicit `amountInMax` (via `{value: msgValue}`) with no price-based cap and no minimum-output/maximum-input check derived from an oracle or quoted rate. [1](#0-0)  This mirrors the reported bug class: a liquidity/swap operation performed with no slippage bound, exposing the caller to sandwich attacks that extract the difference between fair price and the unbounded input ceiling.

### Finding Description
In `placeOrder`, when a user pays the order fee in native ETH, the contract executes:
```solidity
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
    order.fees, path, address(this), block.timestamp
);
msgValue -= amounts[0];
``` [2](#0-1) 

`swapETHForExactTokens` treats `msg.value` as `amountInMax` — the router will accept spending up to the entire `msgValue` to obtain the exact `order.fees` output, and the unspent remainder is refunded to the user via `_sendValue` at the end of `placeOrder`. [3](#0-2)  Unlike the reported `mintUniswapV3`/`mintMarginalV1` case where `amount0Min`/`amount1Min` were hardcoded to zero, here the "slippage cap" is effectively the caller's entire supplied `msgValue`, which is typically sized only slightly above the expected fair-market ETH cost. There is no on-chain reference price (Chainlink oracle, TWAP, or explicit slippage parameter in `receiverParams`/`Order`) bounding how much of the pool's spot price move the swap will tolerate.

A sandwich attacker can:
1. Front-run the `placeOrder` transaction by buying the fee token on the same Uniswap V2 pool, pushing its price up.
2. Let `placeOrder` execute, forcing the contract to spend more ETH (up to the full `msgValue` the user supplied) to obtain the same `order.fees` output.
3. Back-run by selling the fee token back, capturing the price differential as profit.

Because the router call has no independent minimum-output/maximum-input tied to a manipulation-resistant price source, the user's actual ETH cost for the fee swap can be pushed arbitrarily close to their full `msgValue`, and the attacker captures the extracted value. This is the exact reachable analog of the reported issue: a swap/mint operation with slippage protection effectively delegated to a caller-supplied bound that provides no real MEV protection, leading to value extraction rather than reverts. The same pattern exists in the Tron variant, `evm/tron/contracts/apps/IntentGatewayV2.sol`. [4](#0-3) 

### Impact Explanation
Any user placing a cross-chain or same-chain order and paying `order.fees` in native ETH (the `msgValue > 0` branch) is exposed to sandwich extraction on every `placeOrder` call. The stolen amount is bounded only by how much ETH the user supplied beyond the fair-market cost of the fee tokens, which in practice can be a meaningful fraction of the transaction's value since users typically pad `msgValue` to guarantee the swap succeeds. This is a concrete, repeatable value-extraction vector reachable from a single unprivileged `placeOrder` call — it does not require any special permission, and it directly transfers value from users to MEV searchers/LPs rather than to the protocol treasury (unlike the original report's benign "excess funds swept to treasury" outcome).

### Likelihood Explanation
High likelihood: `placeOrder` is a core, permissionless, frequently-invoked entry point of the Intent Gateway, and the vulnerable swap path executes whenever a user opts to pay fees in native ETH with a Uniswap V2 fee-token pool that has any measurable liquidity depth/manipulability. Sandwich bots actively monitor public mempools for router calls exactly like `swapETHForExactTokens`, making exploitation straightforward and economically attractive whenever the extractable spread exceeds gas costs.

### Recommendation
Bound the fee-token swap with a real slippage/price check rather than relying on the caller's full `msgValue` as the implicit ceiling:
- Compute an expected ETH cost for `order.fees` from a manipulation-resistant reference (e.g., a TWAP quote or oracle) and pass a tightly bounded `amountInMax` to `swapETHForExactTokens`, reverting if the router would need to spend beyond an acceptable slippage margin.
- Alternatively, let the caller supply an explicit `maxFeeTokenInNative` parameter (analogous to the report's suggestion to add a slippage parameter to `receiverParams`) so slippage tolerance is set intentionally rather than implicitly equal to the entire remaining `msg.value`.
- Consider using `swapExactETHForTokens` with a computed `amountOutMin` if an exact-fee-amount UX is not required, so slippage is explicit and consistent with the rest of the intents' input/output amount model.

### Proof of Concept
1. User calls `placeOrder` with `order.fees > 0`, `msgValue` set slightly above the current fair-market ETH cost to acquire `order.fees` units of the fee token, and no calldata predispatch.
2. Attacker observes the pending transaction in the mempool and front-runs it with a large buy of the fee token on the same Uniswap V2 pair used in `path = [WETH, feeToken]`, moving the pool price against ETH.
3. `placeOrder` executes `swapETHForExactTokens{value: msgValue}(order.fees, path, address(this), block.timestamp)`; because `amountInMax` is effectively `msgValue`, the swap succeeds at the worse price, consuming ETH up to near the full `msgValue` instead of the fair-market amount.
4. Attacker back-runs by selling the fee token back into the pool, capturing the price differential as profit; the user's refunded `msgValue - amounts[0]` is correspondingly reduced or near zero, versus the anticipated moderate refund.
