### Title
Cross-tenant session hijacking via guessable, unsigned session cookie ID - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
For non-embedded apps (and as a fallback for embedded apps), `ShopifyAPI::Utils::SessionUtils.current_session_id` trusts the raw, attacker-settable `shopify_app_session` cookie value as the lookup key for retrieving a merchant's stored `Session` (including its access token). That cookie value is never a random secret — it is the deterministic, guessable string `Session#id` (`"offline_#{shop}"` or `"#{shop}_#{associated_user.id}"`), derived entirely from public/non-secret data (the shop's `myshopify.com` domain and a merchant user id) rather than from anything cryptographically bound to a completed OAuth flow.

### Finding Description
`ShopifyAPI::Auth::Session.from` builds the session `id` purely from the shop domain and, for online sessions, a numeric associated-user id: [1](#0-0) 

`ShopifyAPI::Auth::Oauth.validate_auth_callback` then uses this predictable `session.id` directly as the **value of the plaintext session cookie** for non-embedded apps (no HMAC, no signature, no server-side random token): [2](#0-1) 

Later, when the host app needs to identify "who is this browser," it calls `ShopifyAPI::Utils::SessionUtils.current_session_id`, which for the non-embedded (and cookie-fallback) path simply echoes back whatever value is in the `shopify_app_session` cookie with **no cryptographic verification that this value actually resulted from a completed OAuth handshake for that shop**: [3](#0-2) [4](#0-3) 

The identity binding this breaks, stated as an equality that the gem fails to enforce:
`cookie_value_presented_by_browser == session_id_created_by_a_genuine_OAuth_completion_for_that_browser`

Instead the gem only enforces:
`cookie_value_presented_by_browser == <any string an attacker can construct from a public shop domain>`

Because `shop` domains (`*.myshopify.com`) are not secret — they are visible in storefront URLs, app listings, and often in the URL of the embedding admin page — and the `offline_#{shop}` format needs no additional secret at all, any unprivileged internet user who knows or guesses a victim merchant's shop domain can construct the exact cookie value the host app expects, set it as their own `shopify_app_session` cookie (this is presentable from a plain browser, no privileged account or TLS interception required), and have `SessionUtils.current_session_id` return the identifier for the victim's session. If the host app then uses that id to fetch the corresponding stored `Session` (as the gem's own documentation instructs apps to do), the attacker's browser ends up associated with the victim shop's persisted `Session` object — which carries the merchant's real `access_token`.

### Impact Explanation
This is a cross-tenant access primitive: the gem-provided session identifier that host applications are told to trust as evidence of "this browser owns this shop's session" carries no unforgeable, unauthenticated-bytes-derived component. Any unprivileged user who knows a target shop's domain can forge the exact lookup key used to retrieve that shop's stored access token, defeating the tenant isolation the gem's session-cookie mechanism is supposed to provide. This matches the Critical impact category: cross-tenant access.

### Likelihood Explanation
High: no credentials, tokens, or privileged access are required — only knowledge of a target's `*.myshopify.com` domain (public information) and, for online sessions, its numeric associated-user id (frequently low/sequential and easy to enumerate). Setting an arbitrary cookie value in one's own browser requires no special capability.

### Recommendation
`SessionCookie`'s value (and by extension `Session#id`) should not be usable on its own as a trust anchor. The cookie value returned to the browser should be an unguessable, high-entropy random token (e.g., `SecureRandom`) that is stored server-side (or otherwise cryptographically bound) and mapped internally to the real `shop`/`associated_user` session — never the deterministic `"offline_#{shop}"` / `"#{shop}_#{user_id}"` string itself. `SessionUtils.cookie_session_id`/`current_session_id` should not treat the raw cookie bytes as an authenticated session identifier without such a binding.

### Proof of Concept
1. Determine any target shop's domain, e.g. `victim-shop.myshopify.com` (public, e.g. from the storefront URL).
2. As an unauthenticated attacker, set a cookie `shopify_app_session=offline_victim-shop.myshopify.com` in your own browser when visiting the vulnerable host app (built with this gem).
3. The host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `"offline_victim-shop.myshopify.com"` unchanged — [4](#0-3) .
4. The host app looks up its session store (as directed by the gem's docs) using this id and retrieves the victim shop's persisted `Session`, including its live `access_token`, and treats the attacker's request as authenticated for that shop — achieving cross-tenant access without ever completing OAuth as that shop.
