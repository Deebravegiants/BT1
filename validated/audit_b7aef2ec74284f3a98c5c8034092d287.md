### Title
OIDC token exchange handler fails to abort on missing email claim, creating an authenticated session despite the detected validation failure - ([File: core/sessions/oidcauth/oidc.go])

### Summary
`oidcAuthenticator.handleTokenExchange` detects that the `email` claim is missing from the verified ID token, logs the error and writes an HTTP 500 response, but does not `return`. Execution falls through and continues to create and persist a fully authenticated session (with the role derived from the OIDC group claims) even though the code explicitly flagged this path as an error condition, mirroring the reported bug class of "detecting a failure but not acting on it."

### Finding Description
In `handleTokenExchange`, after the ID token is cryptographically verified and its claims parsed, the handler attempts to read the `email` claim: [1](#0-0) 

```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims. error: %v", err)
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
}
```

Unlike every other error branch in this same function (e.g. the `id_token` extraction check just above it, or the token-verification/claims-parsing checks), this block is missing a `return` statement. As a result, when the `email` claim is absent or not a string, the function writes an error response but keeps executing with `email` left as its zero value (`""`).

Execution then continues into the session-persistence logic: [2](#0-1) 

```go
clSession := clsessions.NewSession()
_, err = oi.ds.ExecContext(
    ctx,
    "INSERT INTO oidc_sessions (id, user_email, user_role, created_at) VALUES ($1, $2, $3, now())",
    clSession.ID,
    strings.ToLower(email),
    role,
)
...
oi.auditLogger.Audit(audit.AuthLoginSuccessNo2FA, map[string]any{"email": email})
```

A row is inserted into `oidc_sessions` with `user_email = ""` and `user_role` set to whatever role was mapped from the group claims (`oi.IDClaimsToUserRole`, evaluated earlier and independent of the email claim). The handler then saves the session cookie and returns `200 OK`: [3](#0-2) 

Later, this session is fully honored by the authenticator's session-lookup path, which reads role/email directly out of `oidc_sessions` without requiring any correlation to a `users` row: [4](#0-3) 

Because `AuthorizedUserWithSession` trusts the `user_role` stored at session-creation time, the client ends up with a working, role-bearing session cookie — the exact scenario the missing-`email` check was meant to prevent.

### Impact Explanation
This is analogous to the ERC20 `approve` finding: a return/validity check is performed, a failure is detected and even partially reported (HTTP 500 body is written), but the code does not actually enforce the failure — it proceeds as if the operation succeeded. Here the "operation" is authentication/session issuance for the internet-facing gateway handler `handleTokenExchange`. The practical consequences are:
- Any client who completes the OIDC exchange with a token/claims response lacking (or non-string) `email` still receives a valid, working session cookie with a role attached, instead of the intended rejection.
- Multiple such sessions collapse onto the same `user_email = ""` value in `oidc_sessions`, which can cause cross-session/cross-"user" confusion in audit logs and any downstream logic that keys off session email.
- This weakens the security guarantee that a rejected/invalid identity assertion cannot result in a functioning authenticated session.

### Likelihood Explanation
This code path is reachable by any unprivileged client that can drive the OIDC login flow (`handleSignIn` → `handleTokenExchange`), which is part of the browser-facing gateway of the node's HTTP API. Triggering it only requires the identity provider's ID token/claims to omit (or misencode) the `email` field while still passing signature verification and providing the group claim used for role mapping — a state achievable via IdP misconfiguration or a token whose `email` claim is empty/omitted by design (many IdPs treat `email` as optional unless explicitly scoped/required).

### Recommendation
Add the missing `return` after writing the error response in the `email` claim check, matching the pattern used by every other error branch in `handleTokenExchange`:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims")
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
```
More generally, audit all error branches for missing `return` statements after the response is written, since this is the second occurrence of `c.String(...)` without a following `return` in this same function (the `err` inserting into `oidc_sessions` around line 257-260 has a similar but lower-impact issue, since the code continues to set the session cookie even if the DB insert fails).

### Proof of Concept
1. Configure the OIDC provider such that the returned ID token's claims include a valid group claim for role mapping (satisfying `ExtractIDClaimValues`/`IDClaimsToUserRole`) but omit or set a non-string `email` claim.
2. Complete the standard OIDC flow: `GET /sessions/oidc` (state generated and stored) → provider redirect → `POST` to the token exchange endpoint handled by `handleTokenExchange` with the authorization `code`.
3. Observe that although the server logs `"Failed to get email from claims"` and writes an HTTP 500 body, the handler continues, inserts a row into `oidc_sessions` with `user_email = ''` and the mapped `user_role`, sets the session cookie via `ginSession.Save()`, and finally writes `200 OK` with `{"success":true}`.
4. Use the resulting session cookie against any authenticated endpoint; `AuthorizedUserWithSession` ( [5](#0-4) ) returns a valid `User{Role: <mapped role>}`, proving the client obtained a working authenticated session despite the detected validation failure.

// AuthorizedUserWithSession will return the API user associated with the Session ID if it
// exists and hasn't expired
func (oi *oidcAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (clsessions.User, error) {
	if len(sessionID) == 0 {
		return clsessions.User{}, errors.New("session ID cannot be empty")
	}
	var foundUser clsessions.User
	err := sqlutil.TransactDataSource(ctx, oi.ds, nil, func(tx sqlutil.DataSource) error {
		// Query the oidc_sessions table for given session ID, user role and email are saved after the id claims is provided and validated
		var foundSession struct {
			UserEmail string
			UserRole  clsessions.UserRole
			Valid     bool
		}
		if err := tx.GetContext(ctx, &foundSession,
			"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM oidc_sessions WHERE id = $1",
			sessionID, oi.config.SessionTimeout().Duration(),
		); err != nil {
			if errors.Is(err, sql.ErrNoRows) {
				return clsessions.ErrUserSessionExpired
			}
			return err
		}
		if !foundSession.Valid {
			// Sessions expired, purge
			return clsessions.ErrUserSessionExpired
		}
		foundUser = clsessions.User{
			Email: foundSession.UserEmail,
			Role:  foundSession.UserRole,
		}
		return nil
