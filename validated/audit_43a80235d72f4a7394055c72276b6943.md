### Title
Webhook Shop/Topic Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw request body for HMAC verification, while the `shop`, `topic`, `api_version`, and `webhook_id` values that `ShopifyAPI::Webhooks::Registry.process` uses to attribute and dispatch the webhook are read from unauthenticated HTTP headers that are never part of the HMAC computation.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from headers with no cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `verifiable_query.to_signable_string` (i.e., the raw body) against the HMAC: [3](#0-2) 

`Registry.process` calls this validator and then, once it passes, unconditionally trusts `request.shop` and `request.topic` to build the `WebhookMetadata` handed to the app's handler: [4](#0-3) 

The identity binding that should hold is: `HMAC(secret, signed_bytes) == received_hmac` implies `signed_bytes` (and everything derived from it, including which shop/topic the event is attributed to) is authentic. Here, `signed_bytes` is only the JSON body — `shop`, `topic`, `api_version`, and `webhook_id` are *acted on* by `Registry.process` (used to route to a topic-specific handler and stamped into `WebhookMetadata.shop`) but are not covered by the signature that was verified.

Since a single app's `api_secret_key` is shared across every merchant/shop that installs that app, an attacker can install the same target app on their own (unprivileged, free) development/partner store. Shopify will deliver real, validly-signed webhooks to the app's registered endpoint for that attacker-controlled shop — signed with the very same `api_secret_key` used to validate webhooks from every other shop using the app. The attacker can capture one such `(raw_body, X-Shopify-Hmac-Sha256)` pair and replay it to the same endpoint after only changing the `X-Shopify-Shop-Domain` header (and optionally `X-Shopify-Topic`) to point at a victim shop. `HmacValidator.validate` still succeeds because the body bytes and secret are unchanged, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event came from the victim shop/topic.

### Impact Explanation
This breaks the tenant isolation the HMAC signature is meant to provide: an attacker with no privileged credentials can forge webhook events that appear to originate from an arbitrary other shop using the same app, letting them inject attacker-controlled data (e.g., fake `shop/redact`, `app/uninstalled`, order or customer payloads) attributed to a victim tenant. Depending on how the host application's `WebhookHandler` implementations use `WebhookMetadata#shop` (e.g., to look up/update per-shop state, delete data, or trigger de-provisioning), this can result in cross-tenant data corruption or unauthorized actions against a shop the attacker does not control. This matches the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Any internet user can register as a Shopify Partner and install a public/vulnerable app on their own free development store at no cost, then legitimately receive real webhook deliveries signed by the app's shared `api_secret_key`. Capturing and replaying a webhook with a modified shop header requires no special access, no leaked secrets, and no privileged account — only normal use of the app being tested. This is a realistic, low-effort attack path.

### Recommendation
Bind the shop (and ideally topic/api_version) into the signed payload verification, e.g., by including the relevant Shopify headers in the HMAC-signable string, or by cross-checking `request.shop` against a shop the receiving app actually expects/has an active session for before trusting it in `WebhookMetadata`. At minimum, `Registry.process` should not treat `request.shop`/`request.topic` as authenticated simply because the raw-body HMAC passed.

### Proof of Concept
1. Attacker creates a free Shopify partner/development store and installs the target app (same `client_id`/`api_secret_key` as any other install).
2. Shopify delivers a legitimate webhook to the app's endpoint, e.g.:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid-hmac-of-raw-body>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   Body: {...}
   ```
3. Attacker replays the exact same body and `X-Shopify-Hmac-Sha256` value, only changing the header:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` only — unchanged — so validation succeeds.
5. The registered handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, i.e., attacker-controlled event data attributed to a shop the attacker never installed the app on.
