## Finding

### Title
POA bridge withdrawal status matches by `assetId` only, causing status/txHash misreport for batch withdrawals of the same token - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
The SDK explicitly supports batch withdrawals within a single intent (multiple entries in `WithdrawalParams[]`), including withdrawing the same token to different destinations in one batch. However, the code that correlates the destination-chain withdrawal status/tx hash with a specific withdrawal in the batch matches purely by `assetId` (`nep141:<near_token_id>`), not by index, amount, or destination address. When a batch contains two or more withdrawals of the same asset, `describeWithdrawal`/`waitForWithdrawalCompletion` will report the same (first-matched) withdrawal's status and `transfer_tx_hash` for every entry sharing that `assetId`, regardless of which one it actually corresponds to.

### Finding Description
`findMatchingWithdrawal` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` selects a withdrawal record from the POA bridge API purely by asset identity: [1](#0-0) 

This is invoked from `describeWithdrawal`, which is per-`WithdrawalIdentifier` (i.e., per batch index), but the lookup ignores `args.index` entirely: [2](#0-1) 

The identical pattern exists in the internal-utils sibling implementation used by `waitForWithdrawalCompletion`: [3](#0-2) 

The SDK's own test suite documents this as a known limitation, confirming the code intentionally (but insecurely) matches "by assetId, not by index": [4](#0-3) 

The bug is reachable because the SDK's public API explicitly advertises and supports batch withdrawals of arbitrary composition, with each batch item tracked by its own index via `createWithdrawalIdentifiers`: [5](#0-4) 

and the top-level orchestration (`processWithdrawal` → `waitForWithdrawalCompletion`) passes the whole `withdrawalParams` array through to per-item status resolution: [6](#0-5) 

There is no validation anywhere in `sdk.ts`, `signAndSendWithdrawalIntent`, or `createWithdrawalIntents` that rejects or de-duplicates multiple `WithdrawalParams` entries sharing the same `assetId` within one batch (the README's own batch example even shows different assets, but nothing in the code enforces this - the multi-withdrawal signing path in `sdk.signAndSendWithdrawalIntent.test.ts` shows identical `withdrawalParams` repeated 4 times being accepted without error).

**The broken equality:** the withdrawal status/tx hash reported for batch index `i` must correspond to the on-chain withdrawal that was actually created for index `i`'s specific `(assetId, amount, destinationAddress)` tuple. Instead, the code returns whichever withdrawal record from the API response happens to match `assetId` first, which may belong to a *different* index in the same batch.

### Impact Explanation
If a user or integrator submits a batch withdrawal with two or more entries of the same `assetId` (e.g., sending the same token to two different addresses, or splitting an amount across two destinations), `describeWithdrawal`/`waitForWithdrawalCompletion` for both entries resolve to the same underlying withdrawal record - reporting the same `completed` status and the same destination `transfer_tx_hash` for both. An integrator relying on per-index completion tracking (as the SDK's README explicitly recommends for granular batch processing) would incorrectly believe withdrawal B has landed on-chain when only withdrawal A actually has, potentially crediting or releasing funds/records twice for a single on-chain transfer, or failing to notice that the second withdrawal never actually completed. This matches the "status or hash misreport making an integrator credit or refund twice" criterion for High severity.

### Likelihood Explanation
No malicious counterparty action is required - only a benign, protocol-supported usage pattern (two same-token withdrawals in one batch), which the SDK's batch API neither documents as disallowed nor validates against. Any integrator building on the "granular batch withdrawal" feature (the pattern the SDK's own RFC and README promote) is exposed as soon as they process a batch containing a duplicate `assetId`.

### Recommendation
Change `findMatchingWithdrawal` (in both `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) to disambiguate among same-asset withdrawals within a batch - e.g., by tracking which API-returned withdrawal records have already been consumed by earlier indices, or by matching on `(assetId, amount, destinationAddress)` combined, so each batch index is paired to a unique withdrawal record. Alternatively, explicitly validate and reject batches containing duplicate `assetId` entries until the POA API/matching logic supports disambiguation, as suggested in the existing code comment.

### Proof of Concept
1. Submit `processWithdrawal` with `withdrawalParams = [ {assetId: "nep141:btc.omft.near", amount: 100000n, destinationAddress: "addrA", feeInclusive:false}, {assetId: "nep141:btc.omft.near", amount: 50000n, destinationAddress: "addrB", feeInclusive:false} ]`.
2. Both withdrawal intents settle on NEAR under the same `intentTx`; the POA bridge processes both, e.g., withdrawal A completes first with `transfer_tx_hash: "hashA"`, withdrawal B is still `PENDING`.
3. Call `describeWithdrawal` (or `waitForWithdrawalCompletion`) for index 1 (addrB/50000). `findMatchingWithdrawal` filters `withdrawals` by `assetId === "nep141:btc.omft.near"` only and returns the **first** match in the API's (unsorted) list - which is withdrawal A's record, status `COMPLETED`, `transfer_tx_hash: "hashA"`.
4. The SDK reports index 1 (addrB, 50000) as `{status: "completed", txHash: "hashA"}` even though `hashA` is the destination transaction for the *other* withdrawal (addrA, 100000), and B may not have landed at all - confirmed by the code path at [7](#0-6)  and validated by the repo's own test `"matches withdrawal by assetId, not by index"` which demonstrates cross-matching behavior for distinct chains; the same logic applies identically when both entries share the same `assetId`, chain, and near_token_id.

			return { status: "pending" };

				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

	async processWithdrawal(
		args: ProcessWithdrawalArgs<WithdrawalParams | WithdrawalParams[]>,
	): Promise<WithdrawalResult | BatchWithdrawalResult> {
		const withdrawalParams = Array.isArray(args.withdrawalParams)
			? args.withdrawalParams
			: [args.withdrawalParams];

		// Step 1: Estimate fee
		const feeEstimation = await (() => {
			if (args.feeEstimation != null) {
				return Array.isArray(args.feeEstimation)
					? args.feeEstimation
					: [args.feeEstimation];
			}

			return this.estimateWithdrawalFee({
				withdrawalParams,
				logger: args.logger,
			});
		})();

		// Step 2: Sign and send intent
		const { intentHash } = await this.signAndSendWithdrawalIntent({
			withdrawalParams,
			feeEstimation,
			referral: args.referral,
			intent: args.intent,
			logger: args.logger,
		});

		args.logger?.info("Intent published", { intentHash });

		// Step 3: Wait for intent settlement
		const intentTx = await this.waitForIntentSettlement({
			intentHash: intentHash,
			logger: args.logger,
		});

		args.logger?.info("Intent settled", { txHash: intentTx.hash });

		// Step 4: Wait for withdrawal completion
		const destinationTx = await this.waitForWithdrawalCompletion({
			withdrawalParams,
			intentTx,
			logger: args.logger,
		});
