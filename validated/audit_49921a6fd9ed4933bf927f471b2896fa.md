I found a strong analog: a check-then-act race in the gateway's JWT replay guard for HTTP-trigger workflow authorization, structurally identical to the PasswordPusher TOCTOU (check a use-once condition, then record usage, with no atomicity between the two steps).

### Title
Time-of-check-to-time-of-use race in HTTP Trigger JWT replay-guard allows concurrent bypass of one-time-token authorization - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize`, which authenticates unauthenticated HTTP Trigger requests arriving at the gateway from external callers, checks whether a JWT's `jti` claim has already been used via `h.jwtCache.isReplay(claims.ID)` and only *afterward* calls `h.jwtCache.recordUsage(claims.ID)` once the signer/authorization checks pass. [1](#0-0) 

### Finding Description
The replay check and the "mark used" write are two separate, non-atomic operations executed in sequence inside `Authorize`: `isReplay` reads the cache, and only after JWT verification, workflow lookup, and signer-authorization checks succeed does `recordUsage` write the `jti` into the cache. [1](#0-0) 
This is the same bug class as the PasswordPusher CVE: a limit/one-time-use condition is *checked*, work is done, and only afterward is the "already used" state recorded — leaving a window where multiple concurrent requests can all pass the check before any of them records usage. If an attacker sends the same signed JWT to the gateway's HTTP Trigger endpoint concurrently (multiple sockets/goroutines), several requests can observe `isReplay == false` simultaneously and all proceed to `recordUsage`, defeating the intended single-use guarantee of the JWT `jti`.

By contrast, the codebase has a properly-built defense for the same problem class elsewhere: `RequestReplayGuard.CheckAndRecord` in the Vault capability holds a mutex across both the "already seen" check and the write, making the check-and-record atomic and safe under concurrency (verified by a dedicated concurrency test). [2](#0-1) [3](#0-2) 
The HTTP Trigger `jwtReplayCache` used by `Authorize` does not follow this pattern — it exposes `isReplay` and `recordUsage` as two separate calls rather than a single atomic check-and-record, which is the precise anti-pattern that produces TOCTOU races.

### Impact Explanation
A successful race allows an external, unauthenticated caller to reuse a single signed JWT/request to trigger the same workflow execution multiple times concurrently, bypassing the "one JWT per request" / anti-replay guarantee that the HTTP Trigger authorization is supposed to enforce. Depending on the workflow, this could cause duplicate/unauthorized workflow executions triggered from a single authorized signature, which is analogous to the CVE's "bypass single-use limit via concurrent requests" impact. This does not grant credential/secret disclosure, but it does defeat a request-impersonation/replay control that is explicitly documented and tested as enforcing single use.

### Likelihood Explanation
Exploitability requires only unauthenticated network access to the gateway's HTTP Trigger endpoint and the ability to fire concurrent requests with the same valid JWT (which an external caller who legitimately obtained one token could do). No privileged access or protocol-level manipulation is needed beyond ordinary HTTP concurrency, matching the "AV:N/AC:L/PR:N/UI:N" profile of the referenced CVE.

### Recommendation
Make the replay check-and-record atomic, following the existing `RequestReplayGuard` pattern in `core/capabilities/vault/request_replay_guard.go`: acquire a lock (or use a single atomic map operation such as `LoadOrStore`) that performs the "already used?" check and the "mark used" write as one critical section, rejecting the request if the entry already existed, before any other authorization/workflow-lookup work proceeds.

### Proof of Concept
Not independently verified end-to-end due to tool/time limits — I was unable to open the `jwtReplayCache` type definition (`isReplay`/`recordUsage` implementation, and whether it internally uses a mutex/atomic map, e.g. `sync.Map.LoadOrStore`) before the session ended, so the exact concurrency-safety of the cache's internal storage is **unconfirmed**. The finding above is based on the *call pattern* in `Authorize` (separate `isReplay` read followed later by a separate `recordUsage` write, with authorization logic executed in between), which is a textbook TOCTOU shape regardless of the cache's internal locking, unless `recordUsage`/`isReplay` are combined by the caller into one atomic operation — which they are not in `Authorize`. Recommend a Devin session with full repo access to inspect `jwtReplayCache`'s implementation (likely in the same file, lines ~29 onward) and add a concurrency test analogous to `TestRequestReplayGuard_ConcurrentAccess` to confirm/deny exploitability before treating this as fully proven.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}

func TestRequestReplayGuard_ConcurrentAccess(t *testing.T) {
	guard := NewRequestReplayGuard()
	futureExpiry := time.Now().UTC().Unix() + 100

	const goroutines = 100
	results := make([]error, goroutines)
	var wg sync.WaitGroup
	wg.Add(goroutines)

	for i := range goroutines {
		go func(idx int) {
			defer wg.Done()
			results[idx] = guard.CheckAndRecord("same-digest", futureExpiry)
		}(i)
	}
	wg.Wait()

	successCount := 0
	duplicateCount := 0
	for _, err := range results {
		if err == nil {
			successCount++
		} else {
			require.ErrorIs(t, err, ErrRequestAlreadySeen)
			duplicateCount++
		}
	}

	assert.Equal(t, 1, successCount, "exactly one goroutine should succeed")
	assert.Equal(t, goroutines-1, duplicateCount, "all others should be rejected as duplicates")
}
