## Title
Gas Griefing via Unbounded Returndata Copy in `CallDispatcher::dispatch` - (File: `evm/src/utils/CallDispatcher.sol`)

## Summary
`CallDispatcher::dispatch` performs a low-level `call` to an attacker-controlled `to` address and captures the full returndata into a `bytes memory result` local variable regardless of call outcome. Solidity's ABI-decoding of the `(bool, bytes memory)` tuple from a low-level call unconditionally copies all returned bytes into memory before the code can inspect `success`, so an oversized return payload from the target forces a large, gas-costly memory expansion inside the caller — the exact bug class described in the reference report (unbounded `returndatacopy` from an external call consuming the caller's gas budget).

## Finding Description
`CallDispatcher.dispatch` is reachable from `HyperFungibleToken.onAccept`, which is invoked by `EvmHost.dispatchIncoming` whenever a POST request is delivered from a supported source chain: [1](#0-0) [2](#0-1) 

The `message.data` field, decoded from the cross-chain `body`, is attacker-controlled by whoever calls `send()` on the source chain — it encodes an arbitrary array of `Call{to, value, data}` structs that `CallDispatcher.dispatch` executes: [3](#0-2) 

For each call, `(bool success, bytes memory result) = to.call{value: call.value}(call.data);` unconditionally captures the returndata into `result`. Because `to` can be any contract deployed by the attacker, they can make it return an arbitrarily large payload (e.g., tens of KB), forcing the EVM to copy that many bytes into `CallDispatcher`'s memory. Memory expansion cost is quadratic, so this can consume a large, disproportionate share of the gas forwarded to the call — draining gas from `EvmHost.dispatchIncoming`, which forwards essentially all remaining gas to `onAccept` (no `gas:` stipend is set on that outer call).

This mirrors the reported Pancake V4 issue: an external call whose return data is copied into memory without bound, letting the callee dictate how much gas the caller effectively pays via memory-copy cost, independent of any nominal gas cap.

## Impact Explanation
A relayer submitting a legitimate batch of ISMP messages (via `HandlerV2.handlePostRequests`) that includes a POST request destined for `HyperFungibleToken` with attacker-crafted `Call` data can cause `CallDispatcher.dispatch` to burn an outsized amount of gas on the returndata copy. If this exhausts the gas supplied to `dispatchIncoming`'s inner call, `onAccept` fails; `EvmHost.dispatchIncoming` catches that failure and deletes the request receipt so the request can be retried, but the relayer's tx gas for the entire batch is spent handling failed message delivery, and repeated retries against the same malicious target keep failing the same way (denial of message delivery / stuck request requiring manual intervention or blocking the batch's other legitimate messages if the attacker sizes the bomb to consume gas relative to the whole transaction). This is a gas-griefing vector against relayers and a potential route-unable-to-deliver-messages condition for that specific request, satisfying the "route unable to deliver messages" acceptance criterion.

## Likelihood Explanation
Any unprivileged actor can call `HyperFungibleToken.send()` (or any app built on the same pattern) on a source chain with a `data` payload targeting a contract they deploy that returns a large payload on `call`. No special privileges, permissions, or race conditions are required — only a legitimate cross-chain message dispatch and a relayer delivering it, both permissionless operations in the design.

## Recommendation
In `CallDispatcher.dispatch`, avoid capturing return data via the high-level tuple destructuring. Use inline assembly for the external call and either discard returndata entirely (`(bool success,)`-style discard is not sufficient at the Solidity/assembly boundary here since `result` is used in the revert), or bound the copied returndata length (e.g., copy only the first N bytes needed for the revert reason) using `assembly { success := call(...); returndatacopy(ptr, 0, min(returndatasize(), MAX_LEN)) }`. This matches the referenced remediation of encapsulating the call in assembly to prevent automatic copying of the full returndata to memory.

## Proof of Concept
1. Attacker deploys `Bomb.sol`: any function returns e.g. 100,000 bytes of data (via `return(0, 100000)` in a fallback).
2. Attacker calls `HyperFungibleToken.send()` on chain A with `params.data` encoding a `Call[]` where `to = address(Bomb)`.
3. Relayer relays the resulting POST request to chain B; `HandlerV2` invokes `EvmHost.dispatchIncoming`, which calls `HyperFungibleToken.onAccept`, which calls `ICallDispatcher(_dispatcher).dispatch(message.data)`. [4](#0-3) 
4. Inside `CallDispatcher.dispatch`, the call to `Bomb` returns the large payload, which is copied into `result`, consuming a disproportionate amount of the gas forwarded by `dispatchIncoming`, potentially causing `onAccept` to run out of gas and revert — deleting the request receipt and requiring the relayer to retry, repeatedly wasting gas on the same malicious request. [5](#0-4)

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
