### Title
Stale operator session-location reused for user QR-code fraud/geofencing validation - (File: src/plans/mod.rs)

### Summary
The bug class in the report is: a value captured in one context (source chain gas config) is reused unmodified to validate/compute something in a different context (destination chain delivery), and no re-validation is performed, leading to either wasted resources or an unauthorized/failed outcome. In orb-core, the closest reachable unprivileged-user analog is the reuse of the *operator's session location snapshot* — captured once at operator QR-code scan time — as the authoritative location used to validate a user's signup, without ever re-fetching or re-verifying that value for up to `operator_qr_expiration_time` (23 hours by default), even across multiple/different signups.

### Finding Description
When `user_qr_validation_use_only_operator_location` is enabled (`true` by default per `src/config.rs` line 438), the location used to validate a scanned user QR-code is taken from `operator_data.location_data.session_coordinates`, which was captured only once when the operator QR-code was originally validated: [1](#0-0) 

That `operator_data` (including its `location_data` snapshot) is cached in the `OperatorData` struct together with a `timestamp`: [2](#0-1) 

and it is explicitly re-used across the `scan_remaining_qr_codes` loop as long as `operator_data.timestamp.elapsed() < operator_qr_expiration_time` — i.e., the same stale `session_coordinates` value (from the *original* operator scan) is applied to validate potentially different, later user signups, without ever re-querying the operator's current location: [3](#0-2) 

`verify_user_qr_code` then forwards this potentially stale location straight into the backend validation request with no additional freshness check: [4](#0-3) 

This mirrors the report's root cause exactly: a parameter (`baseGas`/`gasPerByte`, here `session_coordinates`) is captured in one context (source chain / initial operator scan) and blindly reused in a different context (destination chain / a later, possibly different signup) that expects a fresh, context-specific value, with no revalidation or fault-tolerant fallback.

### Impact Explanation
If the operator physically moves, or if a malicious/compromised orb operator scans their QR once and then performs multiple user signups over the following hours (the default expiration window is 23 hours), the location-based fraud/geofencing check will keep validating against the original, stale coordinates rather than the operator's true current location. This can defeat the purpose of `user_qr_validation_use_only_operator_location`, which is a fraud-prevention control intended to ensure a signup only proceeds when the operator is physically present at a valid, current location. A user (signup participant) relying on this control being enforced per-signup could be misled into believing their signup was properly geofenced/authorized when it was in fact validated against out-of-date location data.

### Likelihood Explanation
The reuse path is reached through completely normal, unprivileged control flow (`scan_remaining_qr_codes` is invoked on every `do_signup`), and the default configuration (`user_qr_validation_use_only_operator_location: true`, `operator_qr_expiration_time: 23h`) actively favors this stale-reuse behavior rather than treating it as an edge case. No special privileges are required to trigger repeated reuse of `operator_data` across signups within the expiration window.

### Recommendation
Re-fetch (or re-verify freshness of) the operator's location data for each individual signup rather than reusing a session-level snapshot across the full `operator_qr_expiration_time` window, or shrink the effective validity window specifically for the location-based check so that `session_coordinates` cannot be silently reused for unrelated, later signups. At minimum, tie the "operator location" value used in `verify_user_qr_code` to a more recent timestamp check, separate from the general operator QR-code expiration.

### Proof of Concept
1. Configure the orb with defaults (`user_qr_validation_use_only_operator_location = true`, `operator_qr_expiration_time = 23h`).
2. Operator scans their QR code once; `operator_status::request` returns `session_coordinates` reflecting the operator's location at that moment, stored in `OperatorData` with a `timestamp` [2](#0-1) .
3. Operator (or orb) is subsequently moved to a different location, or hours pass, still within the 23-hour expiration window.
4. A new signup is started; `scan_remaining_qr_codes` sees `operator_data.timestamp.elapsed() < operator_qr_expiration_time` and reuses the same cached `operator_data` (including the original `session_coordinates`) without re-scanning/re-validating the operator QR-code [3](#0-2) .
5. `verify_user_qr_code` sends the stale `session_coordinates` to the backend as the operator's "current" location for this new signup [5](#0-4) , causing the location-based fraud check to validate against outdated data rather than the operator's true position at the time of this signup.

async fn do_request(

    use_only_operator_location: bool,

    let request = if use_only_operator_location {

            .get(format!("{}/api/v2/session/{}/status", *SIGNUP_BACKEND_URL, qr_code.user_id,))
            .query(&[

                ("lon", operator_data.location_data.session_coordinates.longitude),
            ])
    } else if use_full_operator_qr {
        super::client()?

    }
