### Title
M-02 accepted-risk: extreme LT-rich/token-rich hostile pre-seeds still open the graduation LP materially off curve-close price - (File: packages/contracts/src/Bonding.sol)

### Summary
The first-depositor share-inflation bug class from the report maps onto alt.fun's HyperSwap V2 LP-seeding at graduation, not an LToken vault. `Bonding._seedUniswapV2Direct` / `_seedRebalancing` / `_pairRebalance` / `_routerDepositAndDispose` defend against an attacker front-running `finalizeGraduation` by pre-creating the TOKEN/LT pair and minting hostile-ratio LP into it. The defense is thorough for moderate pre-seed sizes, but the codebase's own regression tests (`test_hostilePreSeed_budgetCappedSwap_isNotProfitable`, M-02) document and accept a residual case: when the pre-seed is lopsided enough that the required rebalance swap exceeds the per-side budget cap (`_swapBudget`, 99% of the available side), the rebalance only partially corrects the ratio and `_routerDepositAndDispose` deposits the protocol's inventory into a pool that opens materially off the curve-close price (the test asserts a 200x LT-rich pre-seed opens ≥1.2x off curve-close).

### Finding Description
`_seedRebalancing` computes a swap via `_noFeeSwapInput` to rebalance the pool toward the cached `(tokensForLP, ltFromPair)` ratio, then caps it via `_swapBudget` at 99% of the attacker-reachable inventory side: [1](#0-0) 

`_swapBudget` explicitly documents that the 1% reservation only guarantees non-zero deposit amounts, not that the swap reaches the target ratio: [2](#0-1) 

`_routerDepositAndDispose` then deposits whatever remains via `router.addLiquidity(..., 1, 1, lpLock_, ...)` at whatever ratio the (possibly still-skewed) pool sits at post-swap: [3](#0-2) 

The project's own test suite reproduces exactly this: an attacker front-runs `finalizeGraduation` by creating the pair and minting LP at a 200x LT-rich ratio (`reserveToken = tokensForLP/100`, `reserveLt = ltFromPair*200`). The optimal corrective swap exceeds the 99%-of-`tokensForLP` budget, so the rebalance cannot fully correct the ratio, and the pool is asserted to open ≥1.2x off the curve-close price — a materially skewed LP open price, by design accepted rather than prevented: [4](#0-3) 

The maintainers' own comment block frames this as a deliberately *accepted residual* rather than a fix — brick-resistance is prioritized over price integrity: [5](#0-4) 

### Impact Explanation
This satisfies the validation rule's explicit acceptance criterion "an LP seeded away from the curve close price." A permissionless attacker (any unrelated wallet) can, ahead of `finalizeGraduation`, call `factory.createPair(token, lt)` (public HyperSwap V2 factory function), transfer a small amount of TOKEN and a very large multiple of LT to the pair, and call `pair.mint(attacker)`. Because the required corrective swap is bounded by `_swapBudget` at 99% of the protocol's own curve-raised inventory, an attacker who sizes their LT-side pre-seed large enough (e.g. 100–200x `ltFromPair`) can force the resulting HyperSwap TOKEN/LT pool to open at a materially incorrect price relative to the curve's final trading price. This directly distorts the post-graduation trading venue price away from the fair/curve-close value that every other token's LP is guaranteed to open at, harming the token's traders and any arbitrageurs/LPs who rely on the documented zero-gap invariant. While the test suite proves the pre-seeder's own P&L stays non-positive, the pool's mispricing itself is a first-class harm distinct from attacker profit — it is an off-fair-price market open that the protocol's own graduation invariant ("zero-gap LP seeding," `docs/contracts-scope.md` Invariant #1) is designed to prevent and explicitly fails to prevent in this regime.

### Likelihood Explanation
Reachable by any unprivileged EOA with modest capital (needs to acquire/hold LT and TOKEN, both obtainable via `Zap.buy`/`Zap.sell`, and to front-run the permissionless `finalizeGraduation` call, which the protocol expects to be called by a public keeper within ~60 seconds but which anyone can call — an attacker with a bot can win the race). The exact attack shape (200x LT-rich pre-seed) is precisely the shape validated in the maintainers' own M-02 regression test, confirming the mechanism is real and reproducible on the current code, not a theoretical edge case.

### Recommendation
Either (a) increase the per-side swap budget beyond 99% of `tokensForLP`/LT inventory when the computed optimal swap exceeds it, drawing on a wider inventory source (e.g. the LP_RESERVE burn amount) to fully correct the ratio before depositing, or (b) size-limit/detect extreme pre-seed ratios and reject the pre-existing pair by re-creating LP through a fresh pair address (requires deployment flexibility not currently in `_ensureUniswapV2Pair`), or (c) explicitly document and monitor this residual risk with an off-chain alert so operators can compensate affected LPs, since brick-resistance forces the code to proceed regardless.

### Proof of Concept
Using the protocol's own test harness (`packages/contracts/test/TwoPhaseGraduation.t.sol`):
1. Launch a token and drive it to `Graduating` via `_enterGraduating` (reachable by any buy that crosses the graduation threshold, or by `Bonding.triggerGraduation`).
2. Read `(tokensForLP, ltFromPair)` from `bonding.pendingGraduation(tokenAddr)`.
3. As `griefer`, call the public `MockHyperswapFactory.createPair(tokenAddr, lt)`, `deal`/acquire `reserveToken = tokensForLP/100` TOKEN and `reserveLt = ltFromPair*200` LT, `transfer` both to the pair, and call `pair.mint(griefer)` — exactly `_grieferMintPreSeed` in the test helper.
4. Call the permissionless `bonding.finalizeGraduation(tokenAddr)`.
5. Observe (as asserted in `test_hostilePreSeed_budgetCappedSwap_isNotProfitable`) that the resulting HyperSwap pool price is ≥1.2x the curve-close price `ltFromPair/tokensForLP`, confirming the LP opens materially off the fair price on live code paths reachable by any unprivileged address.     /// @dev Cap the rebalance swap at 99% of the available side's budget,
    ///      so the subsequent `addLiquidity` always has a non-zero amount
    ///      of BOTH sides to deposit. Without this, an extreme hostile
    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,
    ///      `_pairRebalance` clamps to the full budget, and the swap
    ///      consumes 100% of one side. `_routerDepositAndDispose` then
    ///      skips `addLiquidity` (`remToken == 0` or `remLT == 0`),
    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero
    ///      LP at the post-swap ratio. The 1% comes off the swap, not the
    ///      deposit — for any realistic pre-seed `s_unconstrained` is
    ///      orders of magnitude below `maxSwap`, so the cap doesn't bind
    ///      and behaviour is unchanged. It only kicks in for catastrophic
    ///      pre-seeds beyond our budget capacity, where the alternative
    ///      is bricking.
    function _swapBudget(
        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;
    }

    /// @notice M-02 reproducer. An LT-rich mint pre-seed so lopsided that the
    ///         TOKEN-side rebalance swap exhausts its full budget (~99% of
    ///         `tokensForLP`) without reaching the cached ratio, so the pool
    ///         deposits materially off curve-close. Finalize must still succeed
    ///         (no brick), the over-funded LT side must be confiscated to the
    ///         owner, and the pre-seeder must end net-negative.
    function test_hostilePreSeed_budgetCappedSwap_isNotProfitable() public {
        (address tokenAddr,) = _launchToken();
        _enterGraduating(tokenAddr);

        (uint256 tokensForLP, uint256 ltFromPair,,) = bonding.pendingGraduation(tokenAddr);

        // Extreme LT-rich shape: TOKEN side at 1% of target, LT side at 200x.
        // The optimal TOKEN-in swap to reach the cached ratio is ~1.4x
        // `tokensForLP`, so the 99%-of-`tokensForLP` budget cap binds and the
        // pool stays ~2x off curve-close after the swap.
        uint256 reserveToken = tokensForLP / 100;
        uint256 reserveLt = ltFromPair * 200;

        // M-02 precondition: the optimal swap exceeds the budget (this is the
        // budget-capped regime, distinct from the swap-rounds-to-zero fallback
        // covered by the dust tests above).
        assertGt(
            _noFeeSwapInputUncapped(reserveToken, reserveLt, tokensForLP, ltFromPair),
            (tokensForLP * 99) / 100,
            "setup: optimal rebalance swap must exceed the per-side budget (M-02 regime)"
        );

        deal(tokenAddr, griefer, reserveToken);
        address hyperPair = _grieferMintPreSeed(tokenAddr, reserveToken, reserveLt);
        uint256 grieferLp = MockHyperswapPair(hyperPair).balanceOf(griefer);
        uint256 ownerLtBefore = lt.balanceOf(bonding.owner());

        bonding.finalizeGraduation(tokenAddr);
        assertTrue(bonding.isGraduated(tokenAddr), "finalize must succeed despite an unrecoverable pre-seed");

        // The accepted residual: no bounded swap can correct a 200x LT-rich
        // pre-seed, so the pool opens materially off curve-close.
        assertGt(
            _poolPriceLtPerToken(hyperPair, tokenAddr),
            (((ltFromPair * 1e18) / tokensForLP) * 12) / 10,
            "M-02 regime: pool opens materially off curve-close"
        );
