## Finding

### Title
Webhook shop identity not bound to HMAC signature enables cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, but the `shop` (and `topic`) values that are handed to application webhook handlers are read from unauthenticated HTTP headers. Because the same app-level `client_secret` is used to sign webhooks for *every* shop that installs the app, any low-privilege merchant who has legitimately installed the app can capture one genuinely-signed webhook body and replay it with a forged `x-shopify-shop-domain` header, causing the host application to process the payload as if it came from a different tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from headers, none of which are part of the signed payload: [2](#0-1) 

`HmacValidator.validate` only verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string` — i.e., the raw body bytes — via `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` passed to the app's handler, with no re-check that the shop is bound to the signed bytes: [4](#0-3) 

The identity binding that should hold is:
```
hmac_verified_bytes == bytes that determine the tenant (shop) acted upon
```
In reality:
```
hmac_verified_bytes = raw_body
tenant_acted_upon    = headers["x-shopify-shop-domain"]  (unauthenticated)
```
Because Shopify signs webhooks for all shops of an app with the same `client_secret` (`Context.api_secret_key`), a merchant who installs the app receives genuinely-HMAC'd webhooks for their own shop. Since the `shop-domain` header is excluded from the signable string, that same valid `(raw_body, hmac)` pair can be replayed with the `shop-domain` header changed to a victim shop's domain, and `HmacValidator.validate` will still return `true`.

### Impact Explanation
This breaks the tenant boundary of the app: a webhook payload can be attributed to any shop's identity while carrying a validly-verified signature, letting an attacker (any merchant with the app installed) inject data or trigger actions (e.g., `orders/create`, `app/uninstalled`, `customers/data_request`) under a different shop's name. This is cross-tenant access via a spoofed identity binding, which falls under the "High/Critical - cross-tenant access" impact category defined in scope.

### Likelihood Explanation
Exploitation requires only that the attacker be a real (even free/low-privilege) install of the app — no access to `api_secret_key`, access tokens, or privileged accounts is needed. The attacker simply needs to capture one legitimate webhook delivered to their own shop (trivial, since they control their own endpoint or can intercept their own traffic) and replay the same body/HMAC pair with a modified `shop-domain` header to the same endpoint. This makes the attack straightforward for any unprivileged multi-tenant user of the host application.

### Recommendation
Include `shop`, `topic`, and other identity-bearing headers in the HMAC-signable string (or independently verify that the shop domain in the header matches a shop-specific expectation), so that `HmacValidator.validate` fails if any of these fields are altered relative to what was actually signed by Shopify.

### Proof of Concept
1. Merchant A installs the app; app receives a legitimate webhook:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of raw_body using shared client_secret>
   x-shopify-shop-domain: shop-a.myshopify.com
   body: {"id": 123, ...}
   ```
2. Attacker (Merchant A) replays the exact same `raw_body` and `x-shopify-hmac-sha256` value, but changes the header:
   ```
   x-shopify-shop-domain: shop-victim.myshopify.com
   ```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the HMAC of `raw_body` — this passes.
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "shop-victim.myshopify.com", body: ...)`, causing the host app to process/store data as if it belongs to `shop-victim`, even though it never sent this webhook.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
