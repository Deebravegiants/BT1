### Title
Webhook shop/topic identity not covered by HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while `shop`, `topic`, and `webhook_id` are read directly from unauthenticated HTTP headers. `Registry.process` verifies the HMAC and then blindly trusts these header-derived fields to identify the tenant (`shop`) for the webhook handler. Because the app's `client_secret`/HMAC key is shared across every shop that installs the app, a valid `(body, hmac)` pair produced for one shop can be replayed with forged `shopify-shop-domain`/`shopify-topic` headers to make the payload appear to originate from a different shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are pulled straight from HTTP headers with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates only the body's HMAC via `Utils::HmacValidator.validate(request)`, then passes the unauthenticated `request.shop`/`request.topic` straight into the handler's `WebhookMetadata`: [3](#0-2) 

`HmacValidator.validate_signature` computes the HMAC using `Context.api_secret_key` (the app's single `client_secret`, shared across all installed shops) and `verifiable_query.to_signable_string`: [4](#0-3) 

The binding that should hold is: `shop-that-produced-the-signed-body == shop-the-handler-attributes-the-event-to`. Because the signature never covers `shop` (or `topic`), this equality is not enforced. Any party that can obtain one genuinely-signed `(raw_body, hmac)` pair for the app (e.g., by installing the app on their own free/test shop and receiving a real webhook) can replay that exact body/HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain (and/or a different `shopify-topic`). `Utils::HmacValidator.validate` will still return `true`, since it only recomputes the HMAC over `@raw_body`, which is unchanged — the forged header is never part of the signable string.

### Impact Explanation
This breaks tenant isolation: the app's webhook handler will process attacker-controlled event data while believing it originated from an arbitrary victim `shop`. Depending on how the host application uses `WebhookMetadata#shop` (e.g., to look up the shop's session/access token, update per-tenant records, trigger `app/uninstalled` cleanup, or sync order/customer data), this can result in cross-tenant data corruption, spoofed uninstall/GDPR events for a shop the attacker doesn't control, or injection of forged business data attributed to another merchant. This matches the "Critical - cross-tenant access" category.

### Likelihood Explanation
Medium-to-High: the attacker only needs the ability to install the app on any shop they control (or otherwise obtain one legitimate signed webhook body for the app) and to send an HTTP POST with forged Shopify headers to the app's public webhook callback URL — no `api_secret_key`, access token, or privileged account is required. The primitive of "HMAC signs body only, not headers used for routing" is entirely inside this gem's `Webhooks::Request`/`Registry` implementation.

### Recommendation
Bind the identity fields into the signed material, or otherwise cryptographically verify them independently of headers:
- Include `shop`, `topic`, and `webhook_id` in the value that is HMAC-verified (this requires cooperation with Shopify's signing scheme, so at minimum the library should not treat an HMAC-body-only check as sufficient proof of the header values), or
- Require the host application to independently confirm `request.shop` is a shop with an active session/installation known to the app before trusting it, rejecting webhooks for shops that never completed OAuth, and
- Document/enforce that `Registry.process` must not be relied upon as the sole authenticity check for the `shop`/`topic` header values, since the current comment/behavior implies "HMAC valid ⇒ headers trustworthy."

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (or otherwise triggers a real webhook delivery to their own controlled endpoint/logging proxy) and captures one legitimate webhook delivery: raw body `B` and header `shopify-hmac-sha256: H`, where `H = HMAC_SHA256(client_secret, B)`.
2. Attacker crafts a new HTTP POST to the app's webhook endpoint with the same body `B` and same `shopify-hmac-sha256: H`, but sets `shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `shopify-topic`).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`) using the same shared `client_secret` — it matches, so validation passes: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` is the attacker-forged `victim-shop.myshopify.com`, even though the body/HMAC were never produced for that shop: [6](#0-5)
