Interesting finding: `CallDispatcher.dispatch(bytes memory encoded)` at `evm/src/utils/CallDispatcher.sol:44-62` is a fully unauthenticated `external` function — anyone can call it directly (not just the intents/wrapped-token contracts that normally invoke it), and it will execute arbitrary `Call{to, value, data}` entries against any contract, forwarding `call.value` from the dispatcher's own native balance.

### Title
Anyone can drain `CallDispatcher`'s native balance via unauthenticated `dispatch()` - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch` has no caller restriction. Since `IntentGatewayV2`/`IntentsBase`/`WrappedHyperFungibleToken` route predispatch/postdispatch calldata and token balances through this same shared dispatcher contract, and the dispatcher holds a `receive() external payable {}` and can accumulate native/token balance transiently during order processing (predispatch value transfers, postdispatch sweep calls), any externally owned account can call `dispatch()` directly with arbitrary `Call[]` entries to move out whatever native balance happens to be sitting in the dispatcher at that moment.

### Finding Description
`dispatch()` is declared `external` with no modifier: [1](#0-0) . It decodes an arbitrary `Call[]` and executes each entry with attacker-controlled `to`, `value`, and `data`, forwarding value from the CallDispatcher's own balance: [2](#0-1) .

The dispatcher is meant to only be invoked by trusted gateway contracts as part of an atomic order flow — e.g. `IntentGatewayV2.placeOrder` sends the predispatch input assets to the dispatcher and immediately calls `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` [3](#0-2) , and `IntentsBase._execute` transiently routes output assets through the dispatcher for postdispatch calldata [4](#0-3) . Because `dispatch()` itself performs no `msg.sender` check, nothing stops any address from calling it directly in the same block (e.g. via a bundled/flash-bot transaction) between the moment assets are forwarded to the dispatcher and the moment the calling gateway's own dispatch call executes, redirecting the dispatcher's transient native balance to an attacker-chosen address using a crafted `Call[]`.

### Impact Explanation
This differs from the Sweepable analog in that the swept value isn't a permanently accumulated treasury balance but transient balances that briefly sit in the shared `CallDispatcher` during order predispatch/postdispatch execution. Still, since multiple production apps (`IntentGatewayV2`, `IntentsBase`/`IntrinsicIntents`/`ExtrinsicIntents`) share one dispatcher instance and route real user/solver funds through it mid-transaction, an attacker able to race or front-run/back-run within the same block can redirect these funds via a directly-submitted `dispatch()` call, causing loss of user or solver funds during order fulfillment. This meets the bar of concrete theft/freezing of funds reachable from an unprivileged transaction.

### Likelihood Explanation
Requires the attacker to time a call to land while the dispatcher briefly holds value forwarded by an in-flight `placeOrder`/`fillOrder` transaction (e.g., via same-block MEV/bundling), so it is not always trivially exploitable but is fully permissionless and requires no privileged role — any address can call `dispatch()` at will.

### Recommendation
Restrict `CallDispatcher.dispatch` to only be callable by an approved set of caller contracts (e.g., an `onlyCaller`/allowlist modifier configured at construction, similar to `onlyHost` in the gateway contracts), so that arbitrary external accounts cannot invoke it directly with attacker-controlled `Call[]` payloads.

### Proof of Concept
1. Attacker monitors the mempool for a `placeOrder`/`fillOrder` call to `IntentGatewayV2` that includes non-empty `predispatch.call`/`output.call`.
2. Before/while that transaction forwards input or output token/native balances to the shared `CallDispatcher`, the attacker submits their own transaction directly calling `CallDispatcher.dispatch(abi.encode(Call[]{ {to: attacker, value: dispatcherBalance, data: ""} }))`.
3. Since `dispatch()` has no access control, the call succeeds, and the dispatcher's native balance (input/output assets in flight) is redirected to the attacker instead of completing the intended order flow. [5](#0-4)

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
