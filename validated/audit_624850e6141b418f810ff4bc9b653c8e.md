### Title
Webhook `shop` (and `topic`/`webhook_id`) headers are trusted without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, never from the `shop-domain`, `topic`, or `webhook-id` headers. `ShopifyAPI::Webhooks::Registry.process` validates only that the body's HMAC is correct, then immediately hands the caller's application-level handler a `WebhookMetadata` object built from those unauthenticated headers, presenting them as if they had been verified alongside the HMAC check.

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively: [2](#0-1) 

`Request#shop`, `#topic`, and `#webhook_id` are read directly from request headers with no cryptographic binding to the signed content: [3](#0-2) 

`Registry.process` validates the HMAC over the body and, on success, dispatches the handler using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`: [1](#0-0) 

The `api_secret_key` used to compute/verify the HMAC is a single, shared per-app secret (`HmacValidator.validate` at [4](#0-3) ), not per-shop. Consequently, any principal who can install the app on any store (an unprivileged action available to any internet user who can create a Shopify dev/partner store) can legitimately receive a real webhook delivery — i.e., obtain a `(raw_body, hmac)` pair that is valid under the app's shared secret. Because the header values (`shop-domain`, `topic`, `webhook-id`) are not part of the signed bytes, that same `(raw_body, hmac)` pair remains valid if replayed to the app's webhook endpoint with a different `shop-domain` header. The gem's `Registry.process` will accept it as authentic and pass the forged shop identity straight to the host application's handler.

This breaks the intended identity binding: `shop asserted to the handler == shop authenticated by the HMAC`. In reality the HMAC only authenticates "these bytes were sent by Shopify for some webhook of the shared app secret," not "this event belongs to this shop/topic/id." This is exactly the "bytes verified versus bytes parsed" analog: the HMAC verifies `raw_body` bytes, but the library parses and forwards `shop`/`topic`/`webhook_id` from unauthenticated header bytes as if they carried the same guarantee.

### Impact Explanation
This enables cross-tenant spoofing: a low-privilege attacker who is a legitimate (but malicious) merchant installer of the target app can capture a valid `(body, hmac)` pair from their own store's webhook delivery, then replay it to the app's public webhook endpoint while substituting a victim shop's domain in the `shop-domain` header (and/or a different `webhook-id`/`topic` if the body content is topic-agnostic, e.g. empty-body mandatory webhooks like `shop/redact`). The host application, trusting `WebhookMetadata#shop` because the HMAC check passed, may act on data intended for the attacker's own shop but attributed to the victim shop — a cross-tenant access primitive, which the rules classify as Critical impact.

### Likelihood Explanation
Exploitability requires no secrets beyond what an ordinary app installer already has (the ability to install the app on a store they control and observe the webhooks Shopify sends them). No `api_secret_key`, access token, or leaked credential is needed. The library provides no additional binding (e.g., re-deriving shop from body content, or documenting that `shop`/`topic` are untrusted) to mitigate this, and its own test suite treats `data.shop`/`data.topic` as trustworthy outputs of `Registry.process` (e.g. [5](#0-4) ), reinforcing that downstream consumers are expected to trust these fields once HMAC validation succeeds.

### Recommendation
Either (a) include `shop-domain`, `topic`, and `webhook-id` header values in the HMAC-signable string alongside the body so they are cryptographically bound to the signature, or (b) clearly document in `WebhookMetadata`/`Request` that `shop`, `topic`, and `webhook_id` are unauthenticated transport metadata and must be independently cross-checked by the host application (e.g., against the body payload or a known-shop allowlist) before being used for any authorization or data-routing decision.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and captures a real webhook delivery, e.g. for `shop/redact` with an empty JSON body `{}`, header `x-shopify-hmac-sha256: <valid-hmac-of-"{}" >`, `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker POSTs the same raw body `{}` and the same valid `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only checks `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`), which is unchanged.
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`) and invokes the app's handler, which now believes this mandatory-redaction event legitimately came from `victim.myshopify.com`.
