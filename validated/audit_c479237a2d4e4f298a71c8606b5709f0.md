## Finding: Webhook `shop` field is not covered by HMAC verification, enabling cross-tenant webhook spoofing

### Title
Webhook shop attribution is trusted from an unauthenticated header while only the body is HMAC-verified - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by checking the HMAC over the request, but the HMAC is computed only over the raw JSON body. The `shop` value that is subsequently handed to the application's webhook handler is read from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is completely outside the signed material. This breaks the identity binding: `hmac_verified(bytes) == shop_used_for_tenant_routing(bytes)` does not hold, because the shop is not part of `bytes`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate_signature` computes the HMAC exclusively over that signable string and compares it to the `hmac` header value: [2](#0-1) 

`Registry.process` validates this HMAC and then immediately trusts `request.shop`, which is parsed straight from the (unsigned) `x-shopify-shop-domain` header, to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`Request#shop` simply reads the header with no cryptographic binding to the body or HMAC: [4](#0-3) 

Because the shop identity is never covered by the signature, any party capable of delivering a validly-HMAC'd body (e.g., a merchant who owns their own shop and can trigger a legitimate webhook for it, or anyone able to record/replay one such legitimate `(body, hmac)` pair) can attach an arbitrary `shop-domain` header value when forwarding that payload to the app's public webhook endpoint. `Registry.process` will accept it as authentic (the HMAC check passes, since it only checks the body) and dispatch it to the handler labeled with an attacker-chosen shop.

### Impact Explanation
This is a cross-tenant identity confusion: the app's webhook handler receives `WebhookMetadata#shop` that it will use to look up per-shop state (uninstall, data deletion, order/customer records, etc.), but that shop value carries no authenticity guarantee. An attacker can cause the receiving application to attribute Shopify-originated (but attacker-relayed) event data to a victim shop, potentially triggering cross-tenant data corruption or unauthorized actions scoped to another merchant's tenant — satisfying the "cross-tenant access" criteria.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one legitimately HMAC-signed `(raw_body, hmac)` pair — trivial for any developer/merchant who can register their own shop and trigger any webhook topic for it — and then relay that same body+HMAC to the target app's public webhook endpoint with a forged `shop-domain` header. No access to the app's `client_secret` or any merchant credential of the victim is required, only network reachability to the webhook endpoint, which is public by design.

### Recommendation
Do not treat the `shop` header as authenticated. Either:
- Include the shop domain (and other identity-relevant headers) as part of the signable payload validated against the HMAC, or
- Cross-check `request.shop` against an independently known/registered value (e.g., the shop associated with the webhook subscription/session store) before dispatching to handlers, and reject the webhook when the header shop cannot be corroborated.

### Proof of Concept
1. Attacker registers webhooks for their own shop `attacker.myshopify.com` and captures a legitimate delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(client_secret, B)`).
2. Attacker POSTs to the victim app's public webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid since HMAC only covers `B`), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` — passes, since only `@raw_body` is verified: [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own shop.
