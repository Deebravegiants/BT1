### Title
Solver value loss on partial fills of `IntrinsicIntents._fillSameChain` when escrow release rounds down to zero - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
In `IntrinsicIntents._fillSameChain`, a solver partially filling an order pays out real output tokens to the beneficiary but the proportional input tokens released to the solver from escrow are computed with integer division that can truncate to zero, with no minimum-amount check before the transfer of value out of the solver's pocket occurs.

### Finding Description
For a partial fill, `escrowedAmount` is computed as: [1](#0-0) 

```solidity
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
```

When `order.inputs[i].amount * fillAmount < totalRequired`, this division floors to `0`. There is no check that `escrowedAmount > 0` before proceeding: the solver has already unconditionally transferred `fillAmount` (plus any surplus) of output tokens to the beneficiary earlier in the same loop iteration: [2](#0-1) 

The `_partialFills` accounting is updated (`amountFilled = alreadyFilled + fillAmount`) and the fill is recorded regardless of whether `escrowedAmount` computed to zero, so the solver has no recourse — they paid the beneficiary but received nothing back from escrow for that fill. This is the same root cause as the reported nToken issue: a proportional-share computation using multiply-then-divide integer math that can round down to zero for small enough fill sizes relative to the total, with no floor/guard enforced on the amount actually credited back to the party providing value.

An order creator (or a solver colluding with themselves across multiple addresses) can construct or steer an order where `order.inputs[i].amount` is small relative to `totalRequired` (e.g. `order.inputs[i].amount = 1` and `totalRequired` large), so that any `fillAmount` under `totalRequired / order.inputs[i].amount` rounds `escrowedAmount` to `0`. A single-transaction partial fill by an unsuspecting solver bidding a small `solverAmount` in `fillOrder`/`_fillSameChain` (an unprivileged, permissionless entry point reachable by any solver) then transfers real output tokens with zero input tokens released in return.

### Impact Explanation
This causes solvers filling small increments of an order to lose the output tokens they transferred, since no escrow is released to them for that fill. Repeated across many small partial fills, this can drain solver funds transaction-by-transaction with the truncated escrow effectively left "stuck" credited to nobody for that increment (it is not double-counted or returned elsewhere in the same call), representing a loss/lock of value analogous to the original nToken finding. This is a concrete, unprivileged, single-transaction-reachable value loss for a legitimate participant (the solver), qualifying as Medium severity.

### Likelihood Explanation
Likelihood is moderate: it requires a specific ratio of `order.inputs[i].amount` to `totalRequired` and a small enough `fillAmount`, all of which are fully attacker-controllable by whoever creates the order (input/output amounts) and by whichever solver chooses to bid a small `solverAmount`. Because `placeOrder` is permissionless and open to any order shape, a malicious order creator can deliberately construct orders that make partial fills round to zero, baiting solvers (especially automated ones bidding proportionally) into value-losing fills.

### Recommendation
After computing `escrowedAmount` for a non-final partial fill, revert (or skip the fill) if `escrowedAmount == 0`, mirroring the guard recommended in the original report: ensure `tokensToWithdraw` (here, `escrowedAmount`) is strictly greater than zero whenever `fillAmount > 0`, e.g.:
```solidity
escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
if (escrowedAmount == 0) revert InvalidInput();
```
Alternatively, require a minimum fill size proportional to `totalRequired / order.inputs[i].amount` so that `fillAmount` can never produce a truncated-to-zero release.

### Proof of Concept
1. Order creator places an order with `order.inputs[0].amount = 1` (e.g., 1 wei of token A) and `order.output.assets[0].amount = 1_000_000` (token B), via `placeOrder`.
2. A solver calls `fillOrder` with `options.outputs[0].amount = 999_999` (i.e., `fillAmount = 999_999`, less than `totalRequired = 1_000_000`), triggering the partial-fill branch in `_fillSameChain`.
3. The solver's `beneficiaryTotal` (999,999 tokens B) is transferred from the solver to the beneficiary at [3](#0-2) .
4. `escrowedAmount = (1 * 999_999) / 1_000_000 = 0` at line 115, so the `WithdrawalRequest` built for `_withdraw` carries `amount = 0` for that token, meaning the solver receives 0 tokens A back (and `_withdraw` even `continue`s on `amount == 0` per [4](#0-3) ).
5. The solver has paid 999,999 units of token B and received 0 units of token A, a direct loss of funds, while the order remains only partially filled (`isFullyFilled = false` since `amountFilled(999,999) < totalRequired(1,000,000)`), so the escrowed token A (1 wei) stays locked in the contract for a subsequent filler to (possibly) claim on the final fill.
