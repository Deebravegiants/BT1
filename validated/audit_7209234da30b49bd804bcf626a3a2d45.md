## Finding

Excess native token sent to `EvmHost.dispatch()` and `EvmHost.fundRequest()` for fee payment is never refunded to the caller, mirroring the reported Allo.sol bug class (msg.value sent above required fee amount is not refunded to the sender).

### Title
Excess native token sent to `EvmHost.dispatch()`/`fundRequest()` for fee-swap is permanently stuck instead of being refunded to the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` all accept `msg.value` and forward the *entire* amount to `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` to buy an exact amount of `feeToken`.

### Finding Description
Uniswap V2's `swapETHForExactTokens` only consumes the ETH actually required to produce the exact output amount and refunds any unused ETH — but that refund is sent to `msg.sender` **of the router call**. Since `EvmHost` itself is the caller of the router (not the end user), any leftover ETH is refunded back to the `EvmHost` contract's own balance, not to the original dispatcher/relayer/user who supplied `msg.value`. [1](#0-0) [2](#0-1) [3](#0-2) 

None of these three functions compute or forward back any leftover value after the swap call, and there is no sweep/withdraw mechanism visible in `EvmHost.sol` to recover the accumulated stray ETH. This is the same root cause as the referenced Allo.sol issue: the contract accepts `msg.value` greater than what is strictly required, uses only the required portion, and never returns the excess to the original payer — except here the excess isn't merely "lost to the treasury," it becomes permanently trapped native token inside the `EvmHost` contract with no accounted recovery path.

This is also inconsistent with the rest of the codebase, where every other native-token payment surface (`IntentGatewayV2.placeOrder`, `ExtrinsicIntents._fillCrossChain`, `WrappedHyperFungibleToken.send`) explicitly tracks `msgValue` and refunds unspent native tokens back to `msg.sender` after the swap/escrow step: [4](#0-3) [5](#0-4) 

`EvmHost.dispatch`/`fundRequest`, which is the lowest-level, most broadly reachable entry point for any application or end-user paying dispatch fees in native token, lacks this refund entirely.

### Impact Explanation
Any user, relayer, or `IDispatcher` consumer (any `HyperApp`, `IntentGatewayV2`, `HyperFungibleToken`, LayerZero endpoint adapter, etc.) that estimates fees off-chain and sends `msg.value` with any buffer/slippage margin above the exact amount consumed by the Uniswap swap will have that excess permanently locked in `EvmHost`. Given the documentation explicitly recommends buffering native-fee estimates (e.g., the LZ endpoint adapter applies a 2x buffer, and the docs warn fee quoting via `quote()` is imprecise and subject to sandwiching), overpayment via `EvmHost.dispatch`/`fundRequest` is an expected, routine occurrence rather than an edge case, causing systematic loss of user/relayer funds. [6](#0-5) 

### Likelihood Explanation
High likelihood: this triggers on every single native-token-funded `dispatch()`/`fundRequest()` call where `msg.value` exceeds the exact swap input needed — a normal outcome of off-chain fee estimation with any safety margin, not a contrived attack scenario. No privileged role or malicious actor is required; the loss occurs for ordinary, honest callers.

### Recommendation
Track the actual ETH consumed by `swapETHForExactTokens` (its return value `amounts[0]`) and refund `msg.value - amounts[0]` back to `_msgSender()` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, mirroring the pattern already used in `IntentGatewayV2.placeOrder`:
```solidity
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
if (msg.value > amounts[0]) {
    payable(_msgSender()).transfer(msg.value - amounts[0]);
}
```

### Proof of Concept
1. Caller estimates the ETH needed for a `fee` of `X` feeToken units via off-chain `quote()`/simulation, adding a safety buffer (as the docs and `HyperbridgeLzEndpoint` recommend) and sends `msg.value = 2 * estimatedCost` to `EvmHost.dispatch(DispatchPost)`.
2. `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` only consumes the exact ETH required to buy `post.fee` feeToken; the router refunds the remainder to `msg.sender` of the call — `EvmHost`, not the original caller. [1](#0-0) 
3. `EvmHost`'s ETH balance permanently increases by the unspent amount; the function returns without forwarding any of it back to the caller.
4. Repeating this across many dispatches/fundRequest calls accumulates stuck ETH in `EvmHost` with no recovery mechanism for the original payers.
