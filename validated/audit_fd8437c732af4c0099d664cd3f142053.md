### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook only by validating the HMAC of the raw request body, then hands the caller-supplied `shop-domain` header straight through to the app's handler as the trusted tenant identifier. The `shop` value is never included in the signed material, so it can be swapped for a different value without invalidating the HMAC.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from an unauthenticated header and exposed as a plain attribute, with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)` — which signs/verifies against `to_signable_string` (body only) — and then immediately constructs `WebhookMetadata` using `request.shop` as the tenant identifier passed to the app's handler: [3](#0-2) 

`HmacValidator.validate_signature` computes the signature purely from `verifiable_query.to_signable_string`, never touching `shop`: [4](#0-3) 

The identity binding the caller relies on is:
`shop authenticated by HMAC == shop delivered to WebhookMetadata.shop used by the app`

but the actual binding enforced by the code is only:
`HMAC(body) == HMAC(body)`

The `shop` field is completely outside that equality. The gem's own documentation instructs handlers to trust `data.shop` as "The shop domain of the webhook" and use it directly (e.g., `shop_domain: data.shop`) for enqueuing/looking up tenant-scoped work: [5](#0-4) 

Because the header is not part of the signed payload, anyone who possesses one valid `(raw_body, hmac)` pair for any topic/shop (e.g., from a webhook legitimately delivered to their own installed shop) can resubmit the identical body and HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value. `HmacValidator.validate` still returns `true` because it never inspects `shop`, and the handler receives `WebhookMetadata.shop` pointing at a different (victim) tenant.

### Impact Explanation
This breaks the tenant-isolation guarantee that Shopify webhook processing is normally assumed to provide: the HMAC is meant to prove "this event genuinely concerns shop X," but the library only proves "this body was produced with the correct secret," leaving `shop` fully attacker-controlled. Any host application that follows the documented pattern of keying per-shop side effects (enqueue jobs, update local records, invalidate caches, trigger shop-scoped webhooks/mutations) off `data.shop` can be tricked into acting on a legitimate payload under a forged tenant identity — a cross-tenant data/action confusion.

### Likelihood Explanation
Exploitation requires the attacker to already control at least one legitimately-registered shop for the app (so they can capture one valid raw body + HMAC from their own webhook deliveries) and knowledge of another tenant's shop domain (public information — every `*.myshopify.com` domain is guessable/enumerable). No possession of `api_secret_key`, access tokens, or privileged accounts is required beyond running the app as an ordinary, unprivileged merchant — exactly the "unprivileged internet user" boundary this analysis targets.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values in the signed material verified against Shopify, or otherwise bind the `shop-domain` header to the merchant's known registered shop before trusting it (e.g., cross-check against the set of shops the app is currently installed on, keyed by something already authenticated). At minimum, document prominently that `WebhookMetadata.shop` is not authenticated by the HMAC and must be independently validated by the host app before being used for tenant-scoped actions.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and receives a legitimate webhook, e.g. body `{"id":1}` with header `x-shopify-shop-domain: attacker.myshopify.com` and a valid `x-shopify-hmac-sha256`.
2. Attacker POSTs the exact same raw body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers; `Utils::HmacValidator.validate(request)` recomputes HMAC over `raw_body` only and it matches, so `Registry.process` proceeds: [3](#0-2) 
4. The registered handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` and — per the documented usage pattern — performs shop-scoped work (e.g., `perform_later(shop_domain: data.shop, ...)`) against the victim shop using data that actually originated from the attacker's own shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
