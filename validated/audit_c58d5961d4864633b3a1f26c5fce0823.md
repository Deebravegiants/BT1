### Title
Webhook `shop` (and `topic`/`webhook_id`) fields are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` only verifies the HMAC over the raw request body; the `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to the app's webhook handler come from HTTP headers that are never included in the signed material, so their authenticity is never checked.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `hmac` is decoded from the `X-Shopify-Hmac-Sha256` header: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e. `@raw_body` only) and compares it against the received signature: [2](#0-1) 

`Registry.process` gates on this HMAC check and then immediately builds `WebhookMetadata` from `request.shop`, `request.topic`, and `request.webhook_id` — all sourced from headers that were never part of the signed payload: [3](#0-2) 

The identity binding that should hold is:
`shop value cryptographically authenticated by Shopify == shop value acted on by the host application's handler`

Because only `raw_body` is signed, this equality is not enforced — the `shop-domain` header can be swapped for any string while a previously-obtained, genuinely-signed `(raw_body, hmac)` pair remains valid. An attacker who operates their own shop and installs the app receives real, validly-signed webhook deliveries for their own store (e.g. `customers/data_request`, `orders/create`, or the mandatory `shop/redact`/`customers/redact` topics). They can replay that exact body+HMAC pair to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` (and, if desired, `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the untouched raw body, and `Registry.process` passes the attacker-chosen shop straight to the registered handler via `WebhookMetadata`.

### Impact Explanation
This breaks the tenant boundary the gem is documented to provide: the `shop` field of `WebhookMetadata` is the primary tenant identifier apps are expected to use inside webhook handlers (e.g., docs/usage/webhooks.md shows handlers keyed only by the processed `WebhookMetadata`). Any app following the documented API can be made to attribute a validly-signed webhook body to an arbitrary victim shop, causing cross-tenant data actions — most severely for mandatory compliance webhooks (`shop/redact`, `customers/redact`, `customers/data_request`), where the handler may execute deletion/redaction logic against the wrong merchant's data based purely on the attacker-controlled header.

### Likelihood Explanation
Any unprivileged internet user can install the app on their own store (or otherwise trigger any webhook topic that is delivered to them) to obtain a legitimately-signed `(raw_body, hmac)` pair, then simply resend it to the app's callback URL with a different `shop-domain` header value. No secret material, access token, or privileged access is required.

### Recommendation
Bind the shop identity into the verified material: require the host application (or the gem itself) to compare the header-derived `shop` against the shop the webhook was registered for/expected, and/or extend the signable string used for verification to include the shop/topic headers so tampering invalidates the HMAC. At minimum, document and enforce that `WebhookMetadata.shop` must be cross-checked against a known/registered shop before any tenant-scoped action is taken.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; wait for (or trigger) a webhook delivery, e.g. `customers/data_request`, capturing the raw body `B` and the genuine `X-Shopify-Hmac-Sha256: H` header, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Send a new POST to the app's webhook endpoint with the same body `B` and same header `X-Shopify-Hmac-Sha256: H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Registry.process` calls `HmacValidator.validate`, which recomputes `HMAC-SHA256(api_secret_key, B)`, matching `H` (body unchanged) — validation passes.
4. `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: parsed_body, ...)` is passed to the handler, which now performs its topic logic (e.g. data redaction) believing it originates from `victim.myshopify.com`, even though Shopify never sent this request for that shop.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
