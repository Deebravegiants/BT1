## Finding: Unlimited router approval + unchecked swap consumption lets a swap caller drain residual token/ETH balances held by the swap action contract [1](#0-0) 

### Summary

`LifiExternalAction`/`ExternalActionSwap` grants the LI.FI router an *unlimited* (`type(uint256).max`) allowance over whatever `inputToken` balance the swap-action contract holds, and then executes arbitrary, user-supplied `externalActionMetadata` against that router without any check that the router only consumes the caller's declared `inputAmount`. Any residual token/ETH balance left in the contract (fee remnants, rounding dust, unswept refunds) becomes drainable by any subsequent Hinkal user performing a swap, because Hinkal's balance equation only tracks *Hinkal's own* balance delta, not the swap-action contract's.

### Finding Description

`ExternalActionSwap.swap()` computes `inputAmount` strictly from the caller's own signed `deltaAmounts[0]` [2](#0-1)  and passes it, along with the fully attacker/user-controlled `externalActionMetadata`, into `callRouter`: [3](#0-2) 

`LifiExternalAction.callRouter` then does:

```solidity
approveUnlimited(inputToken, router);
(bool success, ) = router.call(externalActionMetadata);
```

`approveUnlimited` sets the router's allowance to `type(uint256).max` whenever it drops below half of max [4](#0-3) . Crucially:

- `swappedAmount` is derived only from the *output* token balance diff [5](#0-4) ; nothing checks how much of `inputToken` the router actually pulled via `transferFrom`.
- Because the allowance is unlimited and persistent, the router can pull *any* amount of `inputToken` currently held by the `LifiExternalAction` contract — not just the `inputAmount` that Hinkal transferred in for this specific call.
- Hinkal's own post-action balance equation only compares **Hinkal's** balance before/after the external call to `circomData.amountChanges` / `utxoAmount` [6](#0-5) . Since Hinkal already deducted exactly `inputAmount` from itself *before* invoking `runAction` [7](#0-6) , this equation is fully satisfied regardless of how much extra value the router extracts from the `LifiExternalAction` contract's own token balance.

Any ERC20/ETH left sitting in `LifiExternalAction` — from a prior swap that under-consumed the approved amount (rounding), from `receive() external payable` accepting stray ETH refunds from the router with no sweep function [8](#0-7) , or from any other source — is therefore not protected by any equality Hinkal enforces. A user performing a legitimate, fully-signed swap can craft `externalActionMetadata` (which is only committed to via `calldataHash`/`signedMessageHash`, not restricted in *content*) that instructs the router to consume more `inputToken` than their own declared `inputAmount`, using the pre-existing unlimited allowance to sweep in whatever dust remains, inflating their own `swappedAmount` and thus the `UTXO` they receive back through Hinkal — at the expense of protocol/other-users' residual funds, with none of Hinkal's checks (`balanceDif == amountChanges[i] + utxoAmount`, `balanceDif >= slippageValues[i]`) able to detect it, since those only look at Hinkal's own balance, not the intermediary swap contract's.

### Impact Explanation

This breaks the intended isolation that a swap action should only move exactly the tokens transferred to it for that transaction. Value belonging to the protocol/relay (dust, unswept refunds, rounding remainders) can be siphoned by any subsequent user — a theft of protocol funds not authorized by any signer of those funds, matching the "theft ... of protocol/relay fees" / "temporary freezing... executing calls a wallet owner or prover never authorised" High-severity class.

### Likelihood Explanation

Requires (a) some residual balance to exist in the `LifiExternalAction` contract (plausible from rounding, partial-fill swaps, or unswept native-token refunds since there is no sweep/rescue function and unlimited allowances are never revoked) and (b) a user willing to craft custom router calldata beyond the simple swap encoding the front end would normally produce. Since `externalActionMetadata` is raw arbitrary bytes forwarded verbatim to the router, this is fully within a normal user's control once they sign their own transaction.

### Recommendation

- Do not rely on `approveUnlimited`; approve the router for exactly `inputAmount` before the call and reset to zero afterward (checks-effects pattern already used elsewhere in the codebase, e.g. `unsafeApproveERC20Token`/`approveERC20Token`).
- After `router.call`, assert that the `inputToken` balance decreased by at most `inputAmount` (not just that `outputToken` increased), so any router call that consumes more than the user paid for reverts.
- Add a sweep mechanism (owner-gated) for stray dust/ETH so residual balances don't accumulate as an attack surface, and consider zeroing router allowance to zero when idle.

### Proof of Concept

1. Due to rounding or a partial-fill router execution, `LifiExternalAction` ends up holding e.g. 5 USDC beyond what any pending transaction expects (or ETH refunded to `receive()` from a prior swap sits unswept).
2. `approveUnlimited(USDC, router)` was already invoked in an earlier swap and remains at `type(uint256).max`.
3. A user performs a legitimate signed Hinkal swap withdrawing 100 USDC → ETH, but crafts `externalActionMetadata` for the LI.FI router that requests pulling 105 USDC (still valid because of the unlimited allowance) and swapping the full 105 USDC.
4. `callRouter` returns `swappedAmount` based on the resulting ETH balance increase (covering the full 105 USDC swap), which is larger than what the user actually paid for (100 USDC, as reflected in Hinkal's own balance delta for USDC, which only ever moved 100 out).
5. Hinkal's balance-equation check for USDC passes (it only checks Hinkal's own 100 USDC outflow), and for ETH, the inflated `utxoAmount` matches the inflated `swappedAmount`, so the check passes too — the user receives value corresponding to 105 USDC while only 100 USDC was ever accounted for by Hinkal.
