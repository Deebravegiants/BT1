### Title
Unchecked ERC20 return value in `withdraw()`/`onAccept()` allows silent transfer failure and permanent freezing of escrowed intent funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` uses raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` instead of `SafeERC20.safeTransfer`/`safeTransferFrom` in the escrow-release path (`withdraw()`), the dust-sweep path (`onAccept` → `SweepDust`), and the call-dispatcher transfer path (predispatch), even though the rest of the codebase (`evm/src/apps/intentsv2/ExtrinsicIntents.sol`) consistently uses `SafeERC20`.

### Finding Description
In `withdraw()`, escrowed input tokens are released to the beneficiary/solver via:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [1](#0-0) 

This only checks that the low-level `call` did not revert; it never inspects the ABI-decoded boolean return value. Many non-standard ERC20 tokens (and any token that simply returns `false` on failure rather than reverting) will make the `call` succeed (`success == true`) while the actual transfer silently fails. Because the accounting update `_orders[body.commitment][token] -= amount;` unconditionally follows regardless of whether tokens actually moved, and `_filled[body.commitment]` is already set before the loop, the escrow is marked as settled even though the beneficiary never received the tokens. [2](#0-1) 

The same unchecked-`call` pattern is used for the transaction-fee redemption in the same function: [3](#0-2) 

and for dust-sweeping in `onAccept`: [4](#0-3) 

and for returning input tokens from the `ICallDispatcher` back to the gateway during predispatch handling: [5](#0-4) 

By contrast, the canonical (non-Tron) `ExtrinsicIntents.sol` uses `SafeERC20.safeTransferFrom` throughout for the same escrow flows, confirming this is a regression/inconsistency specific to the Tron deployment: [6](#0-5) 

`withdraw()` is reached from `onAccept()`, which is called by the trusted ISMP host once a relayer delivers a `RedeemEscrow` or `RefundEscrow` post request originating from a peer `IntentGatewayV2` instance on another chain — i.e., it is driven by a normal cross-chain intent settlement flow that any user/solver can trigger by placing and filling an order, then having a relayer deliver the proof. [7](#0-6) 

### Impact Explanation
If the escrowed input token (chosen by the order-placing user at order-creation time) is a non-standard ERC20 that returns `false` instead of reverting on failure (e.g., insufficient allowance edge cases, blacklist/pausable tokens, or tokens with quirky return semantics), a failed transfer during `withdraw()` goes undetected. The escrow accounting is decremented as if the payout succeeded, so the tokens remain stuck in the `IntentGatewayV2` contract with no accounting path to reclaim them — a permanent freezing of user/solver funds. This also affects fee redemption and dust-sweep operations, which can silently fail while leaving stale internal state.

### Likelihood Explanation
Likelihood is moderate: it requires an escrowed token (or fee token) to be a non-reverting-on-failure ERC20 or to fail under specific conditions (e.g., blacklisting, paused state, fee-on-transfer edge cases) at the exact moment of withdrawal/sweep. Because token selection for orders is attacker/user-controlled (any ERC20 can be used as an input/output asset), a malicious or unusual token can be deliberately chosen to trigger this path, and the settlement flow (`onAccept`/`withdraw`) is reached through the normal, unprivileged intent lifecycle once a relayer delivers the message.

### Recommendation
Replace all raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` (in `withdraw()`, the `SweepDust` branch of `onAccept()`, and the predispatch call-dispatcher transfer construction) with OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom`, consistent with the already-imported `SafeERC20` library (`using SafeERC20 for IERC20;`) and with the pattern already used in `evm/src/apps/intentsv2/ExtrinsicIntents.sol`.

### Proof of Concept
1. Deploy an ERC20 token whose `transfer()` returns `false` on failure instead of reverting (e.g., simulate insufficient contract balance due to a prior fee-on-transfer deduction, or a blacklisted recipient).
2. User places a cross-chain order on the source chain (Tron `IntentGatewayV2`) using this token as an input asset, escrowing funds via `_orders[commitment][token] += amount`.
3. A solver fills the order on the destination chain; the relayer delivers the `RedeemEscrow` post request back to the source chain, triggering `onAccept()` → `withdraw()`.
4. If the token's `transfer()` returns `false` (e.g., contract balance insufficient due to some external condition, or recipient blacklisted) without reverting, `token.call(...)` still returns `success = true` at the EVM call level (the low-level call itself succeeds even though the encoded boolean return is `false`).
5. `withdraw()` proceeds to decrement `_orders[body.commitment][token] -= amount` and mark `_filled[body.commitment] = beneficiary`, permanently losing the ability to retry or reclaim the escrowed tokens, which remain locked in the contract.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
