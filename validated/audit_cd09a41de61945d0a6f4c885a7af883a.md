### Title
Webhook `shop`, `topic`, and `webhook_id` fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw body, so the HMAC signature Shopify sends only authenticates the request body content. The `shop-domain`, `topic`, `webhook_id`, and `api-version` values are read directly from HTTP headers and are never included in the signed payload, yet `Registry.process` trusts them and forwards them, unauthenticated, to the app's webhook handler.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then unconditionally trusts the header-derived `shop`, `topic`, and `webhook_id` to route and construct `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The identity binding broken here is: **the bytes verified by HMAC (`raw_body` only) ≠ the bytes the handler acts on (`raw_body` + `shop-domain` + `topic` + `webhook_id` headers)**. Since `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-22`) only checks `verifiable_query.hmac` against `to_signable_string` (the body), an attacker who can obtain any single valid `(raw_body, hmac)` pair signed with the app's secret — e.g. by installing the app on their own store and capturing one of their own genuine webhook deliveries — can replay that exact body+HMAC to the app's webhook endpoint while substituting arbitrary `shop-domain`, `topic`, and `webhook_id` headers. The HMAC check still passes because it never covered those fields, but the handler is invoked believing the event originated from the attacker-chosen shop/topic.

### Impact Explanation
This breaks the shop/topic authenticity guarantee the handler relies on for tenant isolation. A handler that trusts `WebhookMetadata#shop` (e.g., to route updates into the correct tenant's data store, or to determine which merchant's data to update/delete based on `topic`) can be tricked into processing attacker-supplied body content under a victim shop's identity, or under a topic that changes how the body is interpreted (e.g. treating a benign body as `shop/redact` or `orders/create` for another shop). This is a cross-tenant identity spoofing vector reachable by any unprivileged user who can install the app on their own store.

### Likelihood Explanation
Likelihood is moderate: exploitation requires the attacker to obtain at least one legitimate `(raw_body, hmac)` pair produced by the app's secret. Any user able to install the app on a shop they control (a normal unprivileged action) will receive such pairs via real webhook deliveries, satisfying this precondition without needing the app's `client_secret` or any privileged access.

### Recommendation
Extend `VerifiableQuery#to_signable_string` for webhook requests to include the security-relevant headers (`shop-domain`, `topic`, `webhook_id`, `api-version`) in the signed material, or independently verify that the `shop-domain` header matches an expected/registered shop for the session before dispatching to handlers. At minimum, document and enforce that handlers must not trust `WebhookMetadata#shop`/`#topic`/`#webhook_id` as authenticated unless the gem itself binds them into the HMAC computation.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(secret, B)`).
2. Attacker resends a request to the app's webhook endpoint with:
   - `raw_body = B`
   - `x-shopify-hmac-sha256: H` (unchanged — still valid since HMAC only covers `B`)
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: shop/redact` (or any registered topic differing from the original)
3. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because `to_signable_string` only checks `B` against `H`.
4. `Registry.process` looks up the handler for the attacker-chosen topic and invokes it with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "shop/redact", body: JSON.parse(B), ...)`, causing the handler to act as if the event legitimately originated from `victim-shop.myshopify.com`.
