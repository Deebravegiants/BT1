### Title
Webhook `shop-domain` header is trusted for tenant identification but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signable string from only the raw request body, while the `shop` (tenant identifier) is read from an unauthenticated header and passed downstream to application webhook handlers as the trusted tenant. This mirrors the reported bug class: a value that is acted upon (`totalUsers` / here, `shop`) is not bound to the source of truth that is actually verified (the constructor logic / here, the HMAC signature).

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: `lib/shopify_api/webhooks/request.rb:35-38`. The `shop` value returned by `Request#shop` is pulled straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding: `lib/shopify_api/webhooks/request.rb:20-23`.

`Registry.process` validates the HMAC over the body only (`Utils::HmacValidator.validate(request)` at `lib/shopify_api/webhooks/registry.rb:190`), and then immediately builds a `WebhookMetadata` object using `request.shop` — the unauthenticated header value — and hands it to the app's registered handler: `lib/shopify_api/webhooks/registry.rb:198-199`.

This breaks the identity binding: `hmac_verified_bytes == raw_body` but `shop_used_by_handler == header["shop-domain"]`, i.e. the equality that should hold (`shop_bound_by_hmac == shop_trusted_by_app`) does not, because `shop` never enters `to_signable_string`. An unprivileged sender who possesses one legitimate HMAC/body pair signed for shop A (which is trivial to obtain — e.g., by owning a Shopify dev store and receiving your own genuine webhook, since the HMAC key is the app's shared `client_secret` and identical for all shops using the app) can replay that exact body/HMAC pair while substituting the `shop-domain` header to shop B. `HmacValidator.validate` will pass because it only checks the body, and the app's webhook handler will process the payload attributing it to shop B.

### Impact Explanation
This is a cross-tenant data confusion / spoofing primitive: the receiving application is told data (topic, body, webhook_id) belongs to a different merchant (shop) than what was actually verified. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to look up which merchant's data to update, delete, or attribute for GDPR redaction requests such as `customers/redact`), this can lead to writing/deleting/exposing tenant-scoped data under the wrong tenant — a cross-tenant integrity/confidentiality issue reachable without any privileged credential, only knowledge of one previously-observed valid webhook body+HMAC for any shop using the app.

### Likelihood Explanation
Requires the attacker to have received (or otherwise obtained) at least one legitimate raw webhook body and its HMAC for the target app (easily done by installing the app on an attacker-owned dev store, which is normal, low-privilege access), then replay it toward the app's webhook endpoint with a forged `shop-domain` header. No `client_secret`, access token, or victim credential is needed — only a valid captured (body, hmac) pair, which is not secret and is delivered over the wire on every real webhook call.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the HMAC signable string, or otherwise cryptographically bind the header-derived `shop` value before it is trusted, e.g. by validating it against the shop associated with the session/access token that Shopify used to deliver the webhook, rather than trusting the raw header. At minimum, document that `WebhookMetadata#shop` is unauthenticated and must be cross-checked by the host application before performing shop-scoped actions.

### Proof of Concept
1. App registers a webhook handler for topic `customers/redact` via `ShopifyAPI::Webhooks::Registry.add_registration`.
2. Attacker's own store (shop A, legitimately installed) triggers a real webhook; attacker captures the raw POST body and the `x-shopify-hmac-sha256` header — both valid and verifiable with the app's `client_secret`.
3. Attacker resends the exact same body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only signs/verifies `@raw_body` (`request.rb:35-38`), so validation succeeds.
5. `WebhookMetadata.new(... shop: request.shop ...)` is built with `shop = "victim-shop.myshopify.com"` (`registry.rb:198-199`) and passed to the app's handler, which now performs the redact/update action against the wrong tenant. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
