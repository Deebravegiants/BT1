### Title
Webhook `shop` attribution is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for an inbound webhook from an unauthenticated HTTP header, while the HMAC signature that `ShopifyAPI::Utils::HmacValidator` verifies only covers the raw request body. This breaks the intended binding `HMAC-verified bytes == identity used by the handler`, letting an attacker who can obtain one validly-signed webhook payload (e.g., a webhook sent to their own shop) replay it with a forged `shop-domain`/`x-shopify-shop-domain` header to make `ShopifyAPI::Webhooks::Registry.process` dispatch attacker-controlled data under a victim shop's identity.

### Finding Description
`Webhooks::Request` includes `Utils::VerifiableQuery` and defines the bytes that get signed as only the raw body: [1](#0-0) 

Note that `to_signable_string` returns `@raw_body` only — `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from headers and are never included in the signed material: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (the body) using the app's shared `client_secret`, and compares it to the `hmac-sha256` header: [3](#0-2) 

`Webhooks::Registry.process` only checks this body HMAC, and then dispatches the handler using the *unauthenticated* `request.shop` value to build `WebhookMetadata`: [4](#0-3) 

Because Shopify apps share one `client_secret` across all shops that have installed the app, any shop owner (an "unprivileged internet user" from the perspective of any *other* tenant of the same app) can:
1. Trigger a legitimate webhook to be sent to their own endpoint for their own shop (e.g., by placing an order in their own dev/test store, or performing whatever action triggers the topic they want to forge).
2. Capture the raw body and its valid `hmac-sha256` header — this signature is valid for any `shop-domain` value, since `shop` is not part of the signed bytes.
3. Replay the exact same raw body and HMAC to the app's webhook endpoint, but substitute the `X-Shopify-Shop-Domain` header with the victim shop's domain.
4. `HmacValidator.validate` passes (body+HMAC match), and `Registry.process` invokes the registered handler with `shop: <victim-shop>` while `body` is attacker-controlled content that was only ever legitimately produced for the attacker's own shop.

This is exactly the "field acted on but not covered by the HMAC" identity-binding break: the equality that should hold, `hmac_verifies(bytes) => shop_identity_is_authentic`, does not hold, because `shop` is outside `bytes`.

### Impact Explanation
This enables cross-tenant confusion/spoofing for any app using this gem's webhook processing exactly as documented: an attacker (any merchant/tenant of a multi-tenant app, or anyone who can trigger a webhook to fire for a shop they control) can make the app believe attacker-controlled webhook data pertains to a different, victim shop. Depending on how the host app's `WebhookHandler` uses `data.shop` (e.g., updating per-shop state, honoring GDPR mandatory topics like `customers/redact`, `shop/redact`, syncing order/product data, or gating logic on `shop`), this can corrupt or leak another tenant's data — a cross-tenant access impact, which is explicitly in the Critical impact category for this analysis.

### Likelihood Explanation
The attacker only needs to be able to trigger one legitimately signed webhook targeting a shop they control (trivial — install the app on any store, including a free dev store, and perform the triggering action), then can freely relabel the `shop-domain` header on replay since it is unauthenticated. No access token, `client_secret`, or privileged credentials are required — only unprivileged, self-service actions against the same publicly reachable webhook endpoint.

### Recommendation
- Short term: Bind `shop` (and ideally `topic`/`webhook_id`) into the signed material, or alternatively cross-check that `request.shop` corresponds to a shop that actually has an active, expected session/installation before trusting it, rather than trusting the header value implicitly once the body HMAC passes.
- Longer term: Document clearly that `request.shop` is not authenticated by the HMAC and that host applications must independently verify shop identity (e.g., against their own installation records) before acting on webhook data tied to `shop`.

### Proof of Concept
1. App has `client_secret = S`, shared across all installed shops.
2. Attacker installs the app on `attacker.myshopify.com` and triggers topic `orders/create`, causing Shopify to POST body `B` with headers:
   - `X-Shopify-Hmac-Sha256: HMAC(S, B)`
   - `X-Shopify-Shop-Domain: attacker.myshopify.com`
3. Attacker captures `B` and the valid `HMAC(S, B)`.
4. Attacker POSTs the same `B` and same HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` builds a request whose `hmac` field still matches, because `to_signable_string` returns `B` only. [5](#0-4) 
6. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds, then invokes the registered handler with `shop: "victim.myshopify.com"` and the attacker-authored body `B`. [4](#0-3) 
7. The host application processes attacker-controlled data as if it legitimately originated from `victim.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
