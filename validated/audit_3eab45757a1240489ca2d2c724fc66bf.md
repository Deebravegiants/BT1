### Title
Unvalidated swap-route code execution can inject wallet-draining transfers into the caller's authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Severity: High. The controller accepts an opaque caller-supplied route and forwards it to the configured router without venue validation or an allowlist; code reached through that route can add unauthorized-looking token transfers to the caller's simulated authorization tree, which steal wallet assets if the caller signs the resulting tree [1](#0-0) [2](#0-1) [3](#0-2) .

### Finding Description
`swap_collateral` accepts caller-controlled `swap: Bytes` after authenticating the account owner or delegate [4](#0-3) [5](#0-4) . The shared type documents these bytes as the encoded route passed to the router's `execute_strategy` entrypoint [1](#0-0) .

`swap_tokens` checks only that the payload is nonempty, authorizes the controller's exact input-token transfer, and invokes `router.execute_strategy(controller, amount_in, swap)` inside the flash guard [2](#0-1) . Its settlement checks verify only input spend, leftover refunds, and a positive output balance delta; they do not decode the route, constrain named venues, or detect unrelated authorization children [6](#0-5) [7](#0-6) .

The router threat model states that payload-named pool and token addresses are not allowlisted and can place third-party code on the call stack beneath the caller's authorization [8](#0-7) . A malicious venue can call `token.transfer(caller, attacker, amount)`; transaction simulation records it as a child of the caller's `swap_collateral` authorization, and enforcement succeeds if the caller signs that poisoned tree [9](#0-8) [10](#0-9) .

The same opaque-route sink is reachable through `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral` when the input and output assets differ [11](#0-10) [12](#0-11) [13](#0-12) .

### Impact Explanation
A malicious route can execute arbitrary venue code during an otherwise valid account strategy and obtain a caller-signed token transfer outside the routed amount [14](#0-13) [3](#0-2) . The harness demonstrates theft of Alice's entire unrelated wallet-token balance while she still receives the expected swap output, so the controller's measured-output and final-risk checks do not bound the loss [15](#0-14) [6](#0-5) .

### Likelihood Explanation
An attacker can encode a malicious venue in route data and return an economically valid quote, while the opaque `Bytes` argument gives the controller no opportunity to reject the venue [1](#0-0) [2](#0-1) . Exploitation is not fully silent because the rogue transfer must appear in the signed authorization tree; signing an honest root-only tree causes the host to reject it and roll back the transaction [16](#0-15) . The risk remains material where users sign simulation-produced authorization trees without independently decoding every route venue and child invocation [17](#0-16) .

### Recommendation
Decode and validate route destinations at a trust boundary and permit only governance-approved or router-registered venue contracts for strategy execution [18](#0-17) [8](#0-7) . Clients should additionally compare the complete simulated authorization tree against the decoded route and reject any invocation other than the expected strategy root and exact input transfer [17](#0-16) .

### Proof of Concept
The harness deploys a router whose payload names `hop_pool`, invokes that address, and returns a fair output [19](#0-18) . The malicious hop contract stores `(victim, wallet_token, attacker, amount)` and calls `wallet_token.transfer(victim, attacker, amount)` when invoked [20](#0-19) .

A victim with supplied USDC submits `swap_collateral(caller=alice, account_id, current=USDC, amount, new=ETH, swap=route)` where `route` names the malicious pool [21](#0-20) . Simulation records `wallet_token.transfer(alice, attacker, WALLET_BALANCE)` as a child of Alice's `swap_collateral` authorization, Alice's wallet balance becomes zero, and the attacker receives the funds while the strategy still deposits the expected ETH output [9](#0-8) .

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
