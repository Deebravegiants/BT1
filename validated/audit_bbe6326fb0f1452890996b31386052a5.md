### Title
Webhook `shop-domain` and `topic` headers are trusted for tenant identification and handler dispatch without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, `webhook_id`, and `api_version` as plain, unauthenticated HTTP header values, while `to_signable_string` — the only data actually covered by the HMAC signature — returns solely `@raw_body`. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the raw body only, then uses the unauthenticated `topic` header to select the handler and forwards the unauthenticated `shop` header to that handler as the tenant identity, breaking the binding: `shop/topic used for authorization and dispatch == shop/topic covered by the HMAC`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers with no cryptographic binding to the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string`, i.e., the raw body: [3](#0-2) 

`Registry.process` validates that body-only HMAC, then immediately uses the unauthenticated `request.topic` header to look up the handler in `@registry`, and passes the unauthenticated `request.shop` header straight into `WebhookMetadata` as the tenant identity given to the handler: [4](#0-3) 

Because the app's `client_secret`/`api_secret_key` is shared across every shop that installs the app (it is not per-shop), any merchant who installs the app on their own store can legitimately capture a validly-signed webhook delivery (raw body + `x-shopify-hmac-sha256`) from their own shop. They can then replay that exact body/signature pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain, and/or substituting `x-shopify-topic` to select a different registered handler. `HmacValidator.validate` will still return `true` because the signature never covered those headers, and `Registry.process` will dispatch the (attacker-chosen) handler with `WebhookMetadata#shop` set to the victim's shop domain and/or `WebhookMetadata#topic` set to a handler the attacker did not actually trigger.

### Impact Explanation
If the host application's webhook handlers use `WebhookMetadata#shop` to look up a session/access token or otherwise attribute the webhook's side effects to that shop (a common and encouraged pattern, since `shop` is provided precisely for that purpose), an attacker can cause business logic intended for their own shop to be executed against a victim's tenant record with a forged shop identity — a cross-tenant confusion originating from the gem's failure to bind the `shop`/`topic` identity fields into the HMAC-verified data.

### Likelihood Explanation
Medium: the attacker needs to be a legitimate app installer on at least one shop to obtain one validly-signed body/HMAC pair, and needs a webhook whose body content doesn't itself uniquely identify the shop (many topics, e.g. `app/uninstalled`, `shop/redact`, or bodies that are largely boilerplate, satisfy this). No possession of `api_secret_key` or any access token is required — only observation of an ordinary webhook delivery to their own endpoint.

### Recommendation
Bind `shop`, `topic`, `webhook_id`, and `api_version` into the value that is HMAC-verified (or otherwise independently authenticate them, e.g., by cross-checking the `shop` header against a shop for which the app holds an active session/registration before trusting it), rather than relying solely on the raw body for signature verification in `Utils::HmacValidator#validate` while treating the headers as trusted identity in `Registry.process`.

### Proof of Concept
1. App developer installs their own app on `attacker.myshopify.com` and registers a handler for topic `app/uninstalled`.
2. Shopify delivers a legitimate webhook: body `{}` (or any predictable body), headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: app/uninstalled`, `x-shopify-hmac-sha256: <valid signature over body>`.
3. Attacker resends the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request` parses these headers; `Utils::HmacValidator.validate` recomputes the HMAC over the (unchanged) raw body and it matches, so `Registry.process` proceeds.
5. `Registry.process` invokes the `app/uninstalled` handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "app/uninstalled", ...)`, causing the host app to execute uninstall-related logic (e.g., token revocation, data deletion) against the victim shop's tenant record, even though Shopify never sent a webhook for `victim.myshopify.com`.
