### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing in `ShopifyAPI::Webhooks::Request` - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs/verifies only the raw request body, while `shop` (the tenant identity) is read straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header. `Registry.process` accepts the request once the body-only HMAC validates and then dispatches the handler using this unauthenticated `shop` value, breaking the binding `hmac == sign(body, secret)` from ever covering `shop`.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are the two members Shopify's `HmacValidator` uses to verify a webhook: [1](#0-0) 

```
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end
...
def shop
  T.cast(shopify_header("shop-domain"), String)
end
...
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`to_signable_string` returns only `@raw_body`; the `shop-domain` header used by `shop` is never part of the signed material. `HmacValidator.validate` computes `HMAC(api_secret_key, to_signable_string)` and compares it to the supplied `hmac` value, so it only proves the request body is authentic — it says nothing about which shop the header claims to be from: [2](#0-1) 

`Registry.process` then trusts `request.shop` unconditionally once the body HMAC checks out, forwarding it as the tenant identity to the app's handler: [3](#0-2) 

```
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [3](#0-2) 

Because the app's `client_secret` is shared across every shop that installs the app (it is not per-shop), any legitimately signed `(body, hmac)` pair obtained from a webhook sent to the attacker's own shop remains valid when replayed with the `shop-domain` header swapped to a victim shop that has installed the same app. The equality the gem should enforce — `shop (used by handler) == shop that the HMAC-signed body was actually generated for` — never holds; only `hmac == sign(body, secret)` is checked.

### Impact Explanation
An unprivileged user who has installed the app on their own store (a normal, unprivileged tenant relationship, not a leaked credential) can:
1. Trigger any webhook topic on their own shop to obtain a genuinely Shopify-signed `(raw_body, hmac)` pair.
2. Replay that exact body/HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain.
3. `Registry.process` validates the (unchanged) body HMAC successfully and dispatches the handler believing the event originates from the victim shop.

This is cross-tenant identity confusion: the handler executes shop-scoped logic (including compliance-mandatory webhooks such as `customers/redact` or `shop/redact`) attributed to a shop the attacker does not control, potentially causing data loss, incorrect authorization decisions, or state corruption on another merchant's tenant — a cross-tenant access impact.

### Likelihood Explanation
Any app built on this gem that relies on `WebhookMetadata#shop` (as populated by `Request#shop`/`Registry.process`) to scope handler behavior is affected, and the only precondition is that the attacker controls one shop installation of the same app — a normal, unprivileged usage path with no access token, `client_secret`, or admin privilege required.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook_id`, `api_version`) header values in `to_signable_string`, or otherwise independently bind the verified body to the specific shop before trusting `request.shop`, so a captured signature/body pair cannot be replayed under a different shop identity.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic to capture the raw POST body and its `X-Shopify-Hmac-Sha256` header — both are validly signed with the app's `client_secret`.
2. Resend the identical body and HMAC header to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, raw_body)` — unaffected by the header change — and succeeds.
4. The registered handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though the payload never originated from Shopify on behalf of that shop, demonstrating the cross-tenant spoof.
