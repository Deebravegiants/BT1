### Title
Webhook shop-domain spoofing via HMAC binding gap - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, never over the `shop`, `topic`, `webhook_id`, or `api_version` values, which are all taken verbatim from attacker-influenceable HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only that HMAC and then forwards `request.shop` as the trusted tenant identity to the app's webhook handler, breaking the binding `shop_authenticated == shop_acted_on`.

### Finding Description
`to_signable_string` in `lib/shopify_api/webhooks/request.rb:35-38` returns `@raw_body` only: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are pulled from headers via `shopify_header`, entirely outside the signed content: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC and then constructs `WebhookMetadata` (a `T::Struct` with a `shop` field consumed by app handlers) directly from `request.shop`, without any additional binding check between the header value and the signed body: [4](#0-3) [5](#0-4) 

Because a single app-level `client_secret` is shared across every shop that installs the app, any unprivileged user who installs the app on their own (attacker-controlled) shop legitimately receives Shopify-signed webhooks whose HMAC is valid for a body they fully control (e.g. via `orders/create`, `products/update`, etc., with attacker-chosen field values through normal store actions). That attacker can replay the exact `raw_body` + valid `hmac-sha256` header pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `Utils::HmacValidator.validate(request)` still succeeds because the signature only ever covered the body, and `Registry.process` hands the handler a `WebhookMetadata` claiming `shop: <victim-shop>` with attacker-controlled `body`.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: a request that Shopify authenticated for shop A can be relayed and attributed to shop B purely by header substitution, because the shop identity is not part of the authenticated bytes. Any host app that uses `data.shop` from `WebhookMetadata` to key persistence, authorization, or side effects (as shown in the gem's own documentation example, `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) will process attacker-controlled data under a victim tenant's identity — a cross-tenant data-injection vector reachable by any unprivileged app-installing user, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any user can install the target app on their own store for free/trivially and thereby obtain a stream of genuinely Shopify-signed webhook bodies whose content they substantially control by manipulating their own store data (order notes, product fields, metafields, etc.). No secret, token, or privileged access is required — only the ability to capture/replay HTTP requests to the app's public webhook endpoint, which is the intended entry point for this exact operation.

### Recommendation
Bind the tenant/topic identity into the signed material, or otherwise cross-verify header claims cryptographically before trusting them:
- Prefer using the shop verified through the app's separate OAuth/session/API-authenticated relationship (i.e., cross-check `request.shop` against a session or install record the app already trusts) rather than trusting the header value as-is.
- At minimum, document prominently that `WebhookMetadata#shop` is not itself authenticated by the HMAC and must not be used as a sole tenant key without corroboration (e.g., verifying the shop is a known, currently-installed shop for this app before acting on the payload).
- Consider incorporating the `shop` (and `topic`) header into `to_signable_string` if Shopify's outbound signing scheme is extended to support it, or reject/flag requests where the header-derived `shop` cannot be independently corroborated against the app's installed-shop records.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` (this is available to any unprivileged internet user — it's the app's normal install flow).
2. Attacker triggers a webhook topic the app subscribes to (e.g. `orders/create`) with body content of their choosing (order note fields, custom attributes, etc.), causing Shopify to send a legitimately HMAC-signed webhook: `raw_body = B`, `x-shopify-hmac-sha256 = HMAC(client_secret, B)`, `x-shopify-shop-domain = attacker.myshopify.com`.
3. Attacker captures this request and replays it to the same app's public webhook endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com` (topic/webhook-id/api-version headers can also be freely modified since none are signed).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, B)` — matching, since `B` is unchanged — and passes.
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)`, and the host application processes attacker-controlled body content under the victim shop's identity.
