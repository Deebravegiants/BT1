### Title
Webhook `shop` identity field is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authenticated once `Utils::HmacValidator.validate(request)` succeeds, then forwards `request.shop` to the app's handler inside a `WebhookMetadata` struct as if it were verified tenant identity. In fact `Request#to_signable_string` only returns the raw body, so the HMAC signature never covers the `shop-domain` header, breaking the binding `shop authenticated == shop trusted by handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` is defined as: [1](#0-0) 
returning only `@raw_body`. `Utils::HmacValidator.validate` computes the HMAC solely over `verifiable_query.to_signable_string`: [2](#0-1) 
So the `shop` header, parsed unauthenticated in `Request#shop`: [3](#0-2) 
is never part of what is cryptographically checked. Yet `Registry.process` gates entirely on the body HMAC and then passes this unauthenticated `shop` value straight into the handler-facing struct: [4](#0-3) 
The gem's own documentation instructs developers that `process` "will verify the request did indeed come from Shopify" and that `data.shop` is "the shop domain of the webhook": [5](#0-4) [6](#0-5) 
This creates the binding break: `body HMAC valid` is presented to app developers as proof that `shop == the shop that actually triggered the event`, when the gem's own code never checks that equality.

### Impact Explanation
Any actor who controls a shop that is a legitimate tenant of the app (i.e., an ordinary merchant, not a privileged party, and without needing the app's `api_secret_key`) can trigger a real Shopify webhook event on their own store and capture the resulting `(raw_body, hmac)` pair — this is a validly signed pair since Shopify itself computed it. That signed body can then be replayed by any internet-reachable client to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain; `Registry.process`'s only gate (body HMAC) still passes, and the handler receives `WebhookMetadata#shop` pointing at the victim tenant. If the host app follows the gem's documented pattern and uses `data.shop` to select the tenant's session/access token or to attribute/store data (exactly as shown in the gem's own example, `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), this yields cross-tenant data injection/corruption under another merchant's identity — a cross-tenant boundary violation.

### Likelihood Explanation
Likelihood is meaningful rather than purely theoretical because the vulnerable pattern is not a corner case: it is the exact usage pattern the gem's documentation and struct design push developers toward (`docs/usage/webhooks.md`, `webhook_handler.rb`). No knowledge of `api_secret_key` or any credential is required by the attacker beyond running their own shop through the normal signup flow; capturing a legitimate `(body, hmac)` for their own tenant is trivial, and the webhook endpoint is by design internet-reachable.

### Recommendation
Bind the header-derived identity fields into the verified signature domain, or otherwise cryptographically tie `shop`, `topic`, and `webhook_id` to the specific delivery, e.g. by including them in `to_signable_string`, or by having `Registry.process` cross-check `request.shop` against a shop-specific secret/session already known to the app, rather than presenting a body-only HMAC check as full request authentication in the documentation and API surface.

### Proof of Concept
1. App developer follows `docs/usage/webhooks.md` exactly, registering a handler that does `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`.
2. Attacker owns `attacker.myshopify.com`, a legitimate installed tenant, and performs an action that makes Shopify send a real `orders/create` webhook to the app; attacker captures the raw POST body `B` and header `X-Shopify-Hmac-Sha256: H` from that legitimate delivery (e.g. via a proxy they control, since it's their own traffic).
3. Attacker POSTs the same body `B` and same `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` parses `shop` as `victim.myshopify.com`; `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — passes.
5. Handler executes with `data.shop == "victim.myshopify.com"` and `data.body` fully attacker-controlled, causing the app to process/store the attacker's forged order data as if it belonged to the victim tenant.
