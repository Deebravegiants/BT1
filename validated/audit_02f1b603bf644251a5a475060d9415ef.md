### Title
Webhook HMAC Does Not Bind the `shop`/`topic`/`webhook-id` Headers, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The reported bug class is about a validated cryptographic artifact (a Merkle proof) not covering all the data that downstream logic treats as verified, letting an attacker steer identity-bearing fields through an unauthenticated path. The direct analog in this gem is `ShopifyAPI::Webhooks::Request`: the HMAC signature is verified only over the raw request body, while the shop identity (`X-Shopify-Shop-Domain`), the topic, and the webhook id — the very fields `ShopifyAPI::Webhooks::Registry` uses to route data into per-tenant application logic — are taken from unauthenticated HTTP headers that are never part of the signed content.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all parsed straight from headers with no cryptographic binding to the HMAC: [2](#0-1) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e. just the body) and compares it with the received `hmac` header using `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` treats a passing HMAC check as authorization to trust `request.shop` and hand it straight to the app's handler as the tenant identity: [4](#0-3) 

The security invariant the app relies on is: `hmac_valid?(request) == true` implies `request.shop` is the shop Shopify actually sent this payload for. But because `to_signable_string` only covers the body, this equality does not hold — `shop` (and `topic`/`webhook_id`) can be swapped to any value without invalidating the HMAC, as long as the body bytes are unchanged. Anyone who can obtain one legitimate `(body, hmac)` pair signed with the app's real secret (e.g., by installing the app on their own store and capturing any of their own webhook deliveries) can replay that exact body to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. `HmacValidator.validate` still returns `true` because it never inspects the header, so `Registry.process` dispatches the (attacker-supplied) body to the handler under `WebhookMetadata.shop` set to a victim shop of the attacker's choosing: [5](#0-4) 

### Impact Explanation
This breaks the tenant-authentication boundary the webhook subsystem is supposed to enforce: `shop_authenticated_by_hmac == shop_used_by_handler` is assumed but false. Any app that keys business logic (data writes, cache invalidation, order/customer state changes, entitlement checks) off `WebhookMetadata#shop` can be made to apply attacker-supplied data to a shop the attacker does not control — a cross-tenant access/data-integrity violation, matching the "Critical - cross-tenant access" impact bucket.

### Likelihood Explanation
Exploitation requires the attacker to obtain one valid `(raw_body, hmac)` pair produced with the real `api_secret_key` for some topic — trivially achievable by an unprivileged internet user who installs the app on their own store (a normal merchant action requiring no special privilege) and observes any webhook delivery whose body they can reproduce byte-for-byte (many topics, e.g. `app/uninstalled`, `shop/update`, GDPR compliance topics, have small/predictable or attacker-influenced bodies). The webhook endpoint itself is a public HTTP endpoint reachable directly by anyone, bypassing Shopify's delivery infrastructure entirely, since nothing in this gem ties the HMAC or the request to Shopify's IP ranges or TLS session.

### Recommendation
Bind the identity fields into the signed material instead of trusting unauthenticated headers:
- Change `Request#to_signable_string` (or add a companion check in `Registry.process`) to incorporate `shop`, `topic`, and `webhook_id` into the value that is HMAC-verified, or
- Require callers to independently authenticate `shop` (e.g., cross-check against a known/installed-shop allowlist maintained by session storage) before trusting `request.shop` for routing, and
- Document explicitly that `Utils::HmacValidator.validate` only authenticates the byte content of `to_signable_string`, not any other request metadata, so integrators do not implicitly trust headers as verified.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and captures a legitimate webhook delivery, e.g. topic `app/uninstalled` with body `{}` and header `X-Shopify-Hmac-Sha256: <valid_hmac_for_body>`.
2. Attacker POSTs directly to the app's public webhook endpoint with the same body `{}` and the same valid HMAC header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `victim-shop.myshopify.com` from the (unauthenticated) header.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the body against the same valid HMAC: [6](#0-5) 
5. The app's handler receives `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", ...)` and performs whatever tenant-scoped action it implements (e.g., disabling the app, clearing tokens, or other topic-specific logic) against the victim shop's record — despite the attacker never having any credential or relationship with that shop.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
