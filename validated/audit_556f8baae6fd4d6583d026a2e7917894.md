### Title
Webhook `shop` field is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw body, and `HmacValidator.validate` only verifies that body against the app's `client_secret`. The `shop` (and `topic`/`webhook_id`) values are read directly from HTTP headers and are never part of the signed material, yet `Registry.process` passes `request.shop` straight into the `WebhookMetadata` struct delivered to the app's handler as the trusted tenant identifier.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `shop` is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no relation to the signed content [2](#0-1) . `HmacValidator.validate_signature` computes `HMAC-SHA256(client_secret, raw_body)` and compares it to the `hmac` header [3](#0-2) . `Registry.process` only checks this HMAC before forwarding `request.shop` unmodified into `WebhookMetadata`, which the host app's handler treats as the authoritative tenant/shop for the payload [4](#0-3) [5](#0-4) .

Because the app's `client_secret` (`Context.api_secret_key`) is a single shared secret used to validate webhooks for *every* shop that has installed a public app [6](#0-5) , any merchant who installs the app on their own store can capture a genuine `(raw_body, hmac)` pair delivered to their webhook endpoint by Shopify. That attacker (an ordinary, unprivileged internet user with a free Shopify dev/trial store — no special credentials, tokens, or `api_secret_key` access required) can then replay the identical `raw_body` and `hmac` to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds because it never inspects the `shop` header, and `Registry.process` hands the forged `shop` value straight to the handler as if Shopify itself asserted it. This breaks the intended binding: `shop authenticated by HMAC == shop the handler trusts as the data owner`.

### Impact Explanation
This is a cross-tenant identity confusion: the library gives host applications no cryptographic guarantee that `WebhookMetadata#shop` actually corresponds to the shop that produced the HMAC-signed payload. An app that uses `data.shop` to select/update a specific tenant's records (a documented and expected usage pattern per `WebhookMetadata`) can be tricked into applying another shop's webhook body/topic to a different shop's tenant context, resulting in cross-tenant data corruption or disclosure, satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for any multi-tenant public app: obtaining a genuine `(body, hmac)` pair only requires installing the app on a free/attacker-controlled shop and capturing one webhook delivery (e.g., `app/uninstalled`, `orders/create` with attacker-controlled content). Forging the `shop` header on the replayed HTTP request requires no special network position or credentials — it is a standard HTTP request to the app's public webhook endpoint.

### Recommendation
Bind the shop identity into the signed material or otherwise cross-check it against a source of truth: e.g., verify that `request.shop` matches a shop previously known to have installed the app via a stored session, or include the shop-domain header in the HMAC-covered signable string (Shopify's mandatory-webhook validation already treats topic/shop/api-version headers as trusted-but-unverified — the gem should document/require host apps to independently verify shop identity, or the library should reject webhooks whose `shop` cannot be corroborated against an existing session for that HMAC-secret before invoking `handler.handle`).

### Proof of Concept
1. Attacker registers a free/dev shop `attacker.myshopify.com` and installs the target public app, allowing the topic e.g. `customers/data_request`.
2. Attacker's own webhook endpoint (or a network capture) records the exact `raw_body` and `x-shopify-hmac-sha256` header Shopify sent for `attacker.myshopify.com`.
3. Attacker sends a POST to the victim app's real webhook endpoint reusing that same `raw_body` and `hmac` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body normally [7](#0-6) ; `HmacValidator.validate` succeeds because it only hashes `raw_body` with the shared `client_secret` [3](#0-2) .
5. `Registry.process` invokes the host app's `handler.handle` with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker-controlled body>, ...)` [4](#0-3) , causing the host app to process attacker-controlled data under the victim's tenant context.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          received_signature = verifiable_query.hmac
