### Title
Unbounded `handle_unsigned` message/request batches combined with a fixed declared weight enable a network-wide, fee-free denial of service - (File: modules/pallets/ismp/src/lib.rs)

### Summary
`pallet_ismp::Call::handle_unsigned` accepts an unbounded `Vec<Message>`, where each `Message::Request`/`Message::Response` variant itself wraps an unbounded `Vec<PostRequest>`/`Vec<GetRequest>`. This call is dispatched as an **unsigned, fee-free** extrinsic, and its `#[pallet::weight]` annotation is a **fixed constant** regardless of how many messages/requests are packed in. Because `ValidateUnsigned::validate_unsigned` fully executes the batch (`Self::execute(messages.clone())`, including consensus/state proof verification) on every full node that receives the gossiped transaction — before any weight-based admission control applies — an attacker can submit a single, cheaply-crafted extrinsic containing a very large number of messages/requests and force disproportionate CPU/memory work across the entire relayer/validator network for zero cost. This mirrors the CVE-2023-27901 pattern: an externally-reachable, unauthenticated request-processing entry point with no bound on the number of "parts" it will process.

`Vec<Message>` and the per-message `Vec<PostRequest>` / `Vec<GetRequest>` fields carry no `#[max_len]`/bounded-vec constraint: [3](#0-2) [4](#0-3) 

Crucially, `ValidateUnsigned::validate_unsigned` — which every full node runs when it *receives* the extrinsic over the network, prior to block inclusion and prior to any weight-based rejection — unconditionally executes the entire batch to determine validity: [5](#0-4) 

`Self::execute` iterates over every message and, for each, runs full protocol handling (membership-proof verification, consensus-client updates, dedup checks, hashing every request) with no early bound check on batch size: [6](#0-5) 

Within a single `Message::Request`, the handler hashes and verifies membership for every request in `msg.requests` (again unbounded) before any per-item weight is known to the caller: [7](#0-6) 

The documentation itself acknowledges the "free execution" design and pool-level filtering as the *only* stated spam mitigation, without mentioning a batch-size cap: [8](#0-7) 

Because the weight annotation is static, the runtime's weight-based admission control (which is meant to bound how much CPU a single extrinsic may consume relative to the block budget) is defeated: the extrinsic is treated as cheap (300,000,000 ref-time units) no matter how many hundreds/thousands of requests or GET-response storage-proof verifications it actually triggers. Fee-free ("Pays::No"-style unsigned) execution combined with under-declared weight is the direct analog of CVE-2023-27901's root cause: an unbounded amount of attacker-controlled "parts" processed without an enforced limit, at effectively zero cost to the submitter, causing disproportionate resource consumption for everyone who must validate it.

### Impact Explanation
An attacker can:
1. Construct a single `handle_unsigned` call carrying a very large `Vec<Message>` (or a single `RequestMessage`/`ResponseMessage` with a very large inner `Vec<PostRequest>`/`Vec<GetRequest>`), sized only by the generic extrinsic/block-length limit, not by any message-count limit.
2. Broadcast it as an unsigned transaction. Every full node/collator that receives it via gossip must run `validate_unsigned`, which fully executes proof verification and hashing for every request in the batch, for free.
3. Because the declared weight is fixed, the runtime's weight-based scheduling/limits do not throttle this — a collator including it in a block may spend far more actual execution time than the block's declared weight budget implies, and every peer re-validating the same transaction in its transaction pool pays the same CPU cost repeatedly.
4. This can degrade node responsiveness, slow block production/import across the network, and be repeated cheaply and continuously (each variation only needs a different consensus proof/request content to avoid `provides`-tag dedup), producing a sustained denial of service against the parachain/coprocessor's message-dispatch path — the same "unrestricted resource consumption" class flagged as High severity in CVE-2023-27901 (CWE-770).

### Likelihood Explanation
`handle_unsigned` is explicitly permissionless (`ensure_none(origin)`) and reachable by any relayer, dispatcher, or arbitrary network participant — no privileged role, governance, or prior state is required. The only stated defense (`validate_unsigned` "filters out" invalid messages) does not bound batch size, and the fixed weight constant removes the runtime's usual proportional cost signal. This makes the vector trivially reachable from a single submitted extrinsic.

### Recommendation
- Enforce an explicit maximum on `messages.len()` in `handle_unsigned`/`validate_unsigned`, and on the length of nested `requests`/`responses` vectors in `RequestMessage`/`ResponseMessage`/`GetRequestsWithProof` (e.g., via `BoundedVec` with a governance-configurable cap).
- Make the `#[pallet::weight]` for `handle_unsigned` a function of `messages.len()` (and ideally the aggregate nested request count / proof size) rather than a fixed constant, so weight-based admission control accurately reflects the work performed.
- Consider rejecting (at `validate_unsigned`) batches whose declared size exceeds a cheap-to-check bound *before* running any proof verification, so invalid oversized batches are discarded without doing the expensive work.

### Proof of Concept
1. Craft a `pallet_ismp::Call::handle_unsigned` extrinsic where `messages` is a `Vec<Message::Request(RequestMessage { requests, .. })>` with `requests` containing tens of thousands of syntactically well-formed (but ultimately invalid-proof) `PostRequest` entries, staying under the generic block-length/extrinsic-size limit.
2. Submit it as an unsigned transaction to a Hyperbridge/Nexus-type node.
3. Observe that `ValidateUnsigned::validate_unsigned` (`modules/pallets/ismp/src/lib.rs:614`) invokes `Self::execute(messages.clone())`, which loops over every request, hashing each and invoking `verify_membership` (`modules/ismp/core/src/handlers/request.rs:86-93`) before rejecting the whole batch — meaning the full proof-verification cost is paid regardless of the eventual invalid-proof rejection, and the same cost is repeated by every peer that receives the gossiped transaction, at zero cost to the submitter since the extrinsic is unsigned and, in the fixed-weight `weight()` function (`modules/pallets/ismp/src/lib.rs:728-730`), does not scale with the batch's true computational cost.

```rust
	let check_state_machine_client = |state_machine: StateMachine| {
		consensus_clients
			.iter()
			.find_map(|client| client.state_machine(state_machine).ok())
			.is_none()
	};

	let router = host.ismp_router();

	// Reject duplicate requests within the batch. Wire format is `Vec`,
	// so this is the line of defence against an attacker padding a
	// batch with identical requests.
	let wrapped: Vec<Request> = msg.requests.iter().cloned().map(Request::Post).collect();
	dedup_requests::<H>(&wrapped)?;

	for req in msg.requests.iter() {
		let req = Request::Post(req.clone());
		// If a receipt exists for any request then it's a duplicate and it is not dispatched
		if host.request_receipt(&req).is_some() {
			Err(Error::DuplicateRequest { meta: req.clone().into() })?
		}

		// can't dispatch timed out requests
		if req.timed_out(host.timestamp()) {
			Err(Error::RequestTimeout { meta: req.clone().into() })?
		}

		// either the host is a router and can accept requests on behalf of any chain
		// or the request must be intended for this chain
		if req.dest_chain() != host.host_state_machine() && !host.is_router() {
			Err(Error::InvalidRequestDestination { meta: req.clone().into() })?
		}

		let source_chain = req.source_chain();

		// in order to allow proxies, the host must configure the given state machine
		// as it's proxy and must not have a state machine client for the source chain
		let allow_proxy = host.is_allowed_proxy(&msg.proof.height.id.state_id) &&
			check_state_machine_client(source_chain);

		// check if the request is allowed to be proxied
		if source_chain != msg.proof.height.id.state_id && !allow_proxy {
			Err(Error::RequestProxyProhibited { meta: req.clone().into() })?
		}
	}

	// Verify membership proof
	let state = host.state_machine_commitment(msg.proof.height)?;
	let commitments = msg
		.requests
		.iter()
		.map(|post| hash_request::<H>(&Request::Post(post.clone())))
		.collect();
	state_machine.verify_membership(host, commitments, state, &msg.proof)?;
```

```text
## Transaction fees

Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free as unsigned transactions. The upside to this is that it cannot be exploited as a spam vector, since the transaction pool will check if the submitted extrinsics are valid before they are included in the pool. This validity check ensures that the transaction can be successfully executed and contains valid proofs. Malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing and potential network congestion.
```
