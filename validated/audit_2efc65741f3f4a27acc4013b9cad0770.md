### Title
Webhook `shop`, `topic`, `webhook-id` and `api-version` headers are trusted by the handler but excluded from the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, while the merchant/tenant identity (`shop`) and other metadata are read straight from unauthenticated HTTP headers. `Registry.process` validates the HMAC and then dispatches the handler using those unauthenticated header values, so the value the handler trusts as "which shop this event is for" is not the value the signature actually protects.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery`, whose contract is `hmac` + `to_signable_string`. Its `to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all parsed directly from HTTP headers that are not part of the signed input: [2](#0-1) 

`Registry.process` validates the HMAC against the body, then unconditionally trusts `request.shop`, `request.topic`, `request.webhook_id` and `request.api_version` to build the `WebhookMetadata` passed to the app's `handler.handle`: [3](#0-2) 

`WebhookMetadata` carries `shop` as a plain `String` with no further verification: [4](#0-3) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string`, i.e., the body — it never incorporates `shop`, `topic`, or `webhook_id`: [5](#0-4) 

**Binding broken (as an equality):**
`shop_bound_by_hmac == shop_delivered_to_handler` is expected to hold, but in fact `shop_bound_by_hmac = ∅` (the HMAC only binds the raw body) while `shop_delivered_to_handler = request headers["shopify-shop-domain"]`. Any unprivileged internet user who can obtain one genuine `(body, hmac)` pair — trivially available to them if they operate their own store that has installed the same multi-tenant app (Shopify will deliver a validly-signed webhook to the app's public endpoint for their own shop) — can replay that exact body+HMAC to the app's public webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header for a victim tenant's shop domain. The HMAC still validates (it never covered those headers), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop.

This is the same root cause pattern as the analog report: an identity/authorization decision (which tenant a signed payload belongs to) is made using a value that was never bound by the cryptographic guarantee that is supposed to authenticate it — analogous to "a field acted on but not covered by the HMAC."

### Impact Explanation
If the host application's webhook handler uses `data.shop` to select which merchant's session/access token/database record to act on (a standard and documented usage pattern for this gem's webhook framework), an attacker who controls one tenant of a multi-tenant app can forge webhook events that are processed as if they originated from a different, victim tenant. This crosses a tenant boundary using only a validly-signed body obtained from the attacker's own installation — no access token, `client_secret`, or privileged access to the victim is required. This matches the in-scope "cross-tenant access" impact category.

### Likelihood Explanation
Requires the attacker to be a legitimate low-privilege user of the multi-tenant app (i.e., they install the app on their own store to get one authentic `(body, hmac)` pair), which is achievable by any unprivileged internet user. The webhook endpoint is public by design (Shopify webhook delivery is unauthenticated HTTP), and header spoofing on a raw POST request is straightforward. Exploitability additionally depends on the host app trusting `data.shop` for tenant lookups without an independent binding — a common and expected usage per this gem's own webhook framework design (`WebhookMetadata#shop` is the only tenant signal exposed to handlers).

### Recommendation
Include the `shop`, `topic`, and `webhook-id` header values in the HMAC-signed input (or otherwise cryptographically bind them to the body) so that `HmacValidator.validate` fails if any of these values are altered relative to what Shopify actually signed, ensuring `WebhookMetadata#shop` can only ever reflect the tenant the signature was issued for.

### Proof of Concept
1. Attacker installs the target multi-tenant app on their own store `attacker.myshopify.com`.
2. Attacker triggers an event (e.g., creates an order) causing Shopify to deliver a webhook to the app's public webhook endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over body B>`, and body `B`.
3. Attacker captures `(B, HMAC)` (e.g., by running the app's webhook endpoint themselves, or intercepting via a local reverse proxy they control since it's their own server receiving it).
4. Attacker POSTs `B` with the identical `x-shopify-hmac-sha256` value but `x-shopify-shop-domain: victim.myshopify.com` to the app's webhook endpoint.
5. `Utils::HmacValidator.validate` in [6](#0-5)  passes because it only checks the body-derived signature.
6. `Registry.process` in [3](#0-2)  dispatches `handler.handle` with `WebhookMetadata(shop: "victim.myshopify.com", ...)`, causing the host application's handler to process the attacker's event as belonging to the victim tenant.

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
