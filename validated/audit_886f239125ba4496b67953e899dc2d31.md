## Title
Fee-on-transfer output tokens cause under-delivery to order beneficiaries while the intent is marked fully filled and full escrow released to the solver - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`IntrinsicIntents._fillSameChain` and `ExtrinsicIntents._fillCrossChain` pay the order beneficiary using `IERC20.safeTransferFrom(msg.sender, beneficiary, amount)` with the *nominal* required amount, but never verify how much the beneficiary actually received. If the output token charges a transfer fee (deflationary/fee-on-transfer token), the beneficiary receives less than `totalRequired`, yet the code still marks the fill amount as equal to `totalRequired` and proceeds to release 100% of the escrowed input tokens to the solver.

### Finding Description
In `IntrinsicIntents.sol`: [1](#0-0) 
the solver's payment is sent with a fixed `safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal)`. The subsequent accounting (`amountFilled == totalRequired`) assumes the beneficiary received exactly `beneficiaryTotal`/`fillAmount`, ignoring any deduction the token itself applies on transfer. `isFullyFilled` becomes true and the *entire* escrowed input (`_orders[commitment][...]`) is released to the solver via `_withdraw`.

The same pattern exists in the cross-chain path in `ExtrinsicIntents.sol`: [2](#0-1) 
Cross-chain fills are strictly all-or-nothing (`solverAmount < totalRequired` reverts), and once the fixed-amount transfer completes, a `RedeemEscrow` message is dispatched back to the source chain unconditionally releasing the full escrow, with no check that the beneficiary actually received `totalRequired`.

This is inconsistent with how the same codebase treats the *input* side of an order: `IntentGatewayV2.placeOrder` explicitly snapshots balances before and after each `safeTransferFrom` and mutates `order.inputs[i].amount` to the actually-received amount precisely to handle fee-on-transfer tokens: [3](#0-2) 
No equivalent balance-based verification exists on the output/fill side in either `IntrinsicIntents` or `ExtrinsicIntents`.

### Impact Explanation
When an order's output asset is a fee-on-transfer token, the beneficiary permanently receives less than the amount committed to in the order (`totalRequired`), yet:
- The order is marked fully filled (`isFullyFilled = true` / cross-chain unconditional full-fill).
- The solver is credited/released the *entire* escrowed input amount as if the order terms were honored in full.
- Any attached output calldata (`_execute`) may run under the false assumption that the beneficiary/dispatcher holds the full nominal amount.

This results in a permanent, protocol-level loss of funds for the order beneficiary equal to the token's transfer fee on every fill, with no recourse (the order is already finalized/`_filled`).

### Likelihood Explanation
This triggers deterministically any time an order's output token is a fee-on-transfer ERC20 — no special attacker privilege is needed, and it is reachable by any user creating an order and any solver filling it (both are unprivileged, permissionless actors). The codebase already demonstrates it explicitly plans for and tests fee-on-transfer tokens on the input side (`evm/tests/foundry/IntentGatewayV2SameChainTest.sol` FEE-ON-TRANSFER TOKEN TESTS), confirming this is a known token class in scope, but the corresponding protection was not applied to the fill/output side.

### Recommendation
Mirror the balance-snapshot pattern used in `IntentGatewayV2.placeOrder` on the fill paths: measure `beneficiary`'s (and, where relevant, the protocol/dust recipient's) token balance before and after each `safeTransferFrom`, and use the actually-received delta to determine `fillAmount`/`amountFilled` and whether the order can be marked fully filled, rather than trusting the nominal transfer amount.

### Proof of Concept
1. User creates an order with `output.assets[0].token` = a fee-on-transfer ERC20 (e.g., 1% fee) and `amount = totalRequired`.
2. Solver calls `fillOrder` with `options.outputs[0].amount = totalRequired`.
3. `_fillSameChain` (or `_fillCrossChain`) executes `IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired)`; beneficiary actually receives `totalRequired * 0.99`.
4. `amountFilled` is still recorded as `totalRequired`, so `isFullyFilled = true`.
5. `_withdraw` releases 100% of the escrowed input tokens to the solver, while the beneficiary is missing 1% of the promised output — a permanent loss with no mechanism to recover the shortfall.
