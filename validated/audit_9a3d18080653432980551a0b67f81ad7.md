### Title
Missing proxy allowance in GET-response handler permanently blocks delivery through Hyperbridge's proxy route - (File: `modules/ismp/core/src/handlers/response.rs`)

### Summary
The Django CVE-2019-12781 bug class is an inconsistent, configuration-dependent determination of a security-relevant condition (`scheme`/HTTPS) that one code path (redirect) trusted incorrectly while other code paths handled correctly. The same *inconsistency-between-code-paths* bug class exists in `pallet-ismp`'s message handlers: the "allowed proxy" exception that lets a coprocessor state machine relay requests/timeouts on behalf of chains with no direct consensus client is implemented in `handlers/request.rs` and `handlers/timeout.rs`, but is entirely absent from `handlers/response.rs` (the GET-response handler), which enforces a strict, un-relaxed equality check instead.

### Finding Description
`IsmpHost::is_allowed_proxy` and `is_router` exist specifically to let a configured coprocessor state machine (`allowed_proxy`) submit requests/timeouts whose `source_chain`/`dest_chain` differs from the state machine that produced the proof, as long as this host has no direct consensus client for that chain: [1](#0-0) 

`handlers/request.rs` implements this exception before rejecting a mismatched request: [2](#0-1) 

`handlers/timeout.rs` implements the identical exception for post-request timeouts: [3](#0-2) 

However, `handlers/response.rs`, which processes `Message::Response` (GET responses, `ResponseMessage`), performs only a strict equality check with no `allow_proxy`/`is_router` exception: [4](#0-3) 

This means: any GET request dispatched by a module on this host, addressed to a destination chain that only has an indirect connection (i.e., reachable via the configured proxy/coprocessor rather than a direct on-chain consensus client — the exact scenario `allowed_proxy`/`is_router`/`is_allowed_proxy` exist to support), can never receive a valid response through `handle_unsigned`. Any relayer submitting a legitimate response proof produced by the proxy chain will always hit `req.dest_chain() != proof.height.id.state_id` and fail with `Error::RequestProofMetadataNotValid`, because the response path has no equivalent to the `allow_proxy` branch that the request/timeout paths have.

### Impact Explanation
Every GET request dispatched to a state machine that is only reachable through Hyperbridge's proxy topology is permanently undeliverable in its response leg: relayers can never submit a passing `GetResponse`, so the request eventually only resolves via timeout (if configured), and any relayer fee attached is refunded on timeout rather than the intended cross-chain read completing. This is a protocol-level route that is structurally unable to deliver messages for the entire class of proxied destinations for GET semantics — consistent with the "route unable to deliver messages" impact class, and it stems from an inconsistency between sibling code paths that should share the same trust/authorization rule, mirroring the root cause of the Django advisory (one code path trusts/verifies the routing condition, a parallel path doesn't).

### Likelihood Explanation
This is always triggered, not just in an edge case, for any application on a proxy-hosted chain that dispatches ISMP `Get` requests through the coprocessor: the very first legitimate GET response submission from any unprivileged relayer against a proxied destination will fail deterministically. No attacker action is required beyond normal message relaying; the bug manifests for the intended, documented proxy configuration itself.

### Recommendation
Add the same `allow_proxy`/`is_router` exception used in `handlers/request.rs` and `handlers/timeout.rs` to `handlers/response.rs`'s `req.dest_chain() != proof.height.id.state_id` check, so that a `GetResponse` proof produced by the configured `allowed_proxy` state machine is accepted under the same conditions (no direct consensus client for `dest_chain`) as requests and timeouts already are.

### Proof of Concept
1. Configure `T::Coprocessor` (via `allowed_proxy`) to `StateMachine::Kusama(2000)` and register a consensus client only for the proxy chain, not for `StateMachine::Evm(11155111)` (mirroring the existing testsuite setup in `modules/ismp/testsuite/src/lib.rs:449-525`).
2. Dispatch a `Get` request from this host to `StateMachine::Evm(11155111)` via the router.
3. Have any relayer submit `Message::Response(ResponseMessage{ requests: [get], proof: { height: { id: { state_id: Kusama(2000), .. }, .. }, .. } })` — a genuine proof from the proxy chain, exactly analogous to the accepted request in `prevent_request_processing_on_proxy_with_known_state_machine`/`prevent_request_timeout_on_proxy_with_known_state_machine`.
4. `handle` in `handlers/response.rs` rejects with `Error::RequestProofMetadataNotValid` at line 54-56 because `get.dest_chain() (Evm(11155111)) != proof.height.id.state_id (Kusama(2000))`, with no `allow_proxy` branch to permit it — unlike the analogous request/timeout tests which pass through their `allow_proxy` branch and only fail later (`RequestProxyProhibited`) under conditions this scenario doesn't trigger. No test in the testsuite (`modules/ismp/testsuite/src/lib.rs`, `modules/pallets/testsuite/src/tests/pallet_state_coprocessor.rs`) exercises a proxied `Response` message, confirming the gap is untested and unhandled.
