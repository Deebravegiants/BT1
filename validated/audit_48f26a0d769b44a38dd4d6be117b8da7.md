### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so `Utils::HmacValidator.validate` only authenticates the body bytes. The `shop-domain`, `topic`, and `webhook-id` headers used by `Registry.process` to identify the tenant and dispatch the handler are never included in the signed material.

### Finding Description
`Request` exposes `shop`, `topic`, and `webhook_id` purely from unauthenticated HTTP headers: [1](#0-0) 

but the HMAC that is validated only signs `@raw_body`: [2](#0-1) 

`HmacValidator.validate` verifies exactly that signable string against the secret and nothing else: [3](#0-2) 

`Registry.process` trusts `request.shop` (taken from the unauthenticated header) once the body-only HMAC passes, and hands it straight to the app's handler as the tenant identity: [4](#0-3) 

This breaks the intended identity binding: `hmac_valid(body, secret) == true` is treated as proof that `(shop, topic, webhook_id, body)` all originated from Shopify for that specific shop, but the equality that is actually enforced is only `hmac_valid(body, secret) == true`; `shop` is an independent, attacker-controllable value. Concretely: `authenticated_field (raw_body)` ⊄ `field acted upon (shop identity used for tenant routing)`.

Any actor who is themselves an installed merchant of the app (an "unprivileged" party relative to other tenants) will legitimately receive Shopify webhooks with a valid HMAC for their own shop and body. That actor can then POST the same raw body and valid HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with another shop's domain/topic/id. `Utils::HmacValidator.validate` still returns `true` because it only checks the body signature, so `Registry.process` calls the handler with `WebhookMetadata.new(topic: forged_topic, shop: forged_shop, body: attacker_body, ...)`, causing the host application to process attacker-controlled data under another tenant's identity.

### Impact Explanation
This lets an unprivileged app-installing merchant inject arbitrary webhook payloads that the host application will process as if they belong to a different, victim shop (cross-tenant data injection), since the gem's own `Registry.process`/`HmacValidator` contract gives no cryptographic guarantee that the `shop`/`topic`/`webhook_id` values are bound to the signed body. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Any merchant who installs the app can trivially obtain a validly HMAC-signed webhook body/signature pair for their own store (Shopify sends these automatically), and can freely craft an HTTP request to the app's public webhook receiver with arbitrary headers. No secrets, tokens, or privileged access are required beyond normal app installation — this is a realistic, low-effort exploit path.

### Recommendation
Bind the shop, topic, and webhook id into the signed material verified by `HmacValidator`, e.g. by including them (in a canonical, delimiter-safe form) in `Request#to_signable_string`, or by requiring host applications to cross-check `request.shop` against the shop associated with the session/subscription that registered the webhook before trusting it in `Registry.process`.

### Proof of Concept
1. Merchant A installs the app; Shopify sends a legitimate webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: shop-a.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and some `raw_body`.
2. Attacker (Merchant A) captures this request and resends it to the same endpoint, replacing only `X-Shopify-Shop-Domain` with `shop-b.myshopify.com` (victim), keeping `raw_body` and `X-Shopify-Hmac-Sha256` unchanged.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses `shop` as `shop-b.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which passes because it only re-derives the HMAC from `raw_body` [5](#0-4) .
5. The registered handler is invoked with `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: attacker_body, ...)`, causing the host app to process attacker data attributed to shop B.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
