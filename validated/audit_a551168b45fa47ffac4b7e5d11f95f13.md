### Title
Unbounded `open_time` in `Initialize2` can permanently trap pool funds in `WaitingTrade` status - ([File: program/src/processor.rs])

### Summary
`Initialize2` accepts an attacker/creator-chosen `open_time: u64` with no upper-bound (or sanity) check, directly analogous to the reported `challengePeriod` issue where an unbounded, unchecked owner-settable time value can either lock funds indefinitely or make the intended state transition impractical.

### Finding Description
The pool creator supplies `open_time` as raw instruction data in `InitializeInstruction2` [1](#0-0) , which is unpacked directly from user-controlled bytes with no range validation [2](#0-1) .

In `process_initialize2`, this value is stored verbatim into `state_data.pool_open_time` via `amm.initialize(init.nonce, init.open_time, ...)` [3](#0-2) [4](#0-3) , and the pool's initial status is decided purely by comparing it to the current clock:

```
amm.status = if init.open_time > (Clock::get()?.unix_timestamp as u64) {
    AmmStatus::WaitingTrade.into_u64()
} else {
    AmmStatus::SwapOnly.into_u64()
};
``` [5](#0-4) 

There is no upper bound, sanity check, or maximum-delta check against `Clock::get()?.unix_timestamp` (e.g., rejecting values like `u64::MAX` or "100 years from now"). Any value greater than the current timestamp is accepted as-is.

The only path out of `WaitingTrade` is in the swap handler, which requires the real clock to reach `pool_open_time` before flipping the pool to `SwapOnly`:
```
} else if amm.status == AmmStatus::WaitingTrade.into_u64() {
    let clock = Clock::get()?;
    if (clock.unix_timestamp as u64) < amm.state_data.pool_open_time {
        return Err(AmmError::InvalidStatus.into());
    } else {
        amm.status = AmmStatus::SwapOnly.into_u64();
    }
}
``` [6](#0-5) 

Because the initial liquidity deposit (the coin/pc amounts and resulting LP tokens) is executed inside `process_initialize2` itself before this status assignment [7](#0-6) , real user/LP funds are already locked in the vaults at the moment an unreasonably large `open_time` is chosen. If `open_time` is set far enough in the future (e.g. `u64::MAX` or centuries away), the pool remains in `WaitingTrade` state indefinitely: swaps are rejected until the clock passes that timestamp, and no unprivileged instruction path exists to change `pool_open_time` back down (the only mutator, `SetOpenTime` via `process_set_params`, requires the privileged `amm_owner` signer, per `config_feature::amm_owner::ID` check [8](#0-7) , so it's out of scope as an unprivileged remediation path and does not by itself invalidate the bug because the creator, not the owner, causes the condition).

### Impact Explanation
An unprivileged pool creator (or anyone funding/triggering `Initialize2` for a given market/mint pair) can set `open_time` to an astronomically large value. This permanently strands the initial liquidity deposited during `Initialize2` in `WaitingTrade` status: swaps revert until the wall clock reaches that time, which for a large enough value is effectively "never" within any practical timeframe. This matches the reported bug class — no bound check on a time parameter leads to funds being locked indefinitely (the initial LP/coin/pc deposit is frozen) with no unprivileged recovery path, since only the privileged `amm_owner` can call `SetOpenTime`.

### Likelihood Explanation
High reachability: `Initialize2` is a permissionless, single-instruction call reachable by any user with attacker-chosen instruction data (the `open_time` field), and no additional privilege or validator control is needed. The only requirement is supplying a large `u64` for `open_time`, which is trivial.

### Recommendation
Add a sanity bound on `init.open_time` in `process_initialize2` (e.g., reject values further than some maximum reasonable delta, such as a few days/weeks, from `Clock::get()?.unix_timestamp`) before calling `amm.initialize(...)`, mirroring the general recommendation for the analogous `challengePeriod` issue: clamp/validate any owner- or caller-supplied time window to a sane min/max range rather than accepting an arbitrary unchecked value.

### Proof of Concept
1. Attacker (or any pool creator) calls `Initialize2` with `open_time = u64::MAX` (or any value far beyond a realistic pool-open horizon), along with valid `init_pc_amount`/`init_coin_amount` and correctly derived accounts.
2. `process_initialize2` executes the initial token transfers into the vaults and mints LP tokens to the creator [7](#0-6) , then sets `amm.status = WaitingTrade` because `init.open_time > Clock::get()?.unix_timestamp` [5](#0-4) .
3. Any subsequent `SwapBaseIn`/`SwapBaseOut`/V2 call fails with `AmmError::InvalidStatus` because `clock.unix_timestamp < pool_open_time` forever (for a large enough value) [9](#0-8) , leaving the pool's initial liquidity effectively frozen with no unprivileged way to unlock it.
