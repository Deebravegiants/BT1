### Title
Cheap, source-unbounded HRMP notification spam can fill a victim para's `InboundDownwardQueue` to the hard `dmq_max_length` cap, DoS-ing legitimate DMP delivery to that para - (File: polkadot/runtime/parachains/src/dmp.rs)

### Summary
`can_queue_downward_message`/`queue_downward_message` enforce a single, per-para hard cap on queue **length** (`dmq_max_length`, computed only from `MAX_POSSIBLE_ALLOCATION / max_downward_message_size`), independent of the actual size of the messages queued. HRMP-management notifications (`HrmpNewChannelOpenRequest`, `HrmpChannelClosing`) are tiny, cheap to generate, refundable-deposit, and go through the exact same `queue_downward_message` path with no per-sender throttling, so an attacker controlling one or more parachains can repeatedly cycle `hrmp_init_open_channel` + `hrmp_cancel_open_request` against a single victim para to consume queue slots up to the cap and cause subsequent legitimate downward messages to be rejected with `ExceedsMaxQueueSize`.

### Finding Description
`Pallet::can_queue_downward_message` rejects a message only if it exceeds `config.max_downward_message_size` or if `dmq_length(para) > dmq_max_length(max_downward_message_size)`: [1](#0-0) 

`dmq_max_length` is a fixed constant derived purely from the configured `max_downward_message_size`, with no relation to the actual bytes queued so far: [2](#0-1) 

This means every enqueued message — whether a full-size XCM payload or a few-byte HRMP notification — consumes one "slot" toward the same hard cap.

`hrmp_init_open_channel`/`init_open_channel` sends an `HrmpNewChannelOpenRequest` notification to the *recipient* (victim) via `queue_downward_message`, gated only by the *sender's* own outbound-channel-count limits, not by anything protecting the recipient's DMQ: [3](#0-2) 

`hrmp_cancel_open_request` removes the pending request and fully unreserves the sender's deposit, with no notification cost and no cooldown, allowing the same `(origin, recipient)` pair to be reopened immediately: [4](#0-3) 

Because `init_open_channel`'s only check against re-requesting is "no existing entry in `HrmpOpenChannelRequests` for (origin, recipient)" (removed by cancel), an attacker-controlled para can loop `hrmp_init_open_channel(victim) -> hrmp_cancel_open_request(victim)` indefinitely, each cycle producing one downward notification queued to the victim, at the cost of only weight/inclusion fees (the `hrmp_sender_deposit` is reserved then immediately unreserved). `hrmp_close_channel` similarly queues an `HrmpChannelClosing` notification to the opposite party once per established channel: [5](#0-4) 

None of these paths check the recipient's current `dmq_length` or apply any anti-spam throttling specific to protocol notifications, so `queue_downward_message` (dmp.rs:300-326) will happily accept notification messages until `dmq_length(victim) > dmq_max_length(...)`, after which **all** further messages to that para — including governance-neutral protocol messages sent through the same path — are rejected with `ExceedsMaxQueueSize`: [6](#0-5) 

The `DeliveryFeeFactor` mechanism referenced in the module doc only escalates delivery fees charged for *future* UMP sends to discourage growth — it is a soft economic disincentive applied per queued message (including the attacker's own), not a hard rejection of the attacker's spam, and it does not prevent the attacker from continuing to submit notifications, since the attacker pays no per-message fee for these HRMP-triggered system notifications (fees apply to XCM senders paying for delivery, not to the HRMP pallet call itself).

### Impact Explanation
Once `dmq_length(victim)` reaches `dmq_max_length(max_downward_message_size)`, every subsequent `queue_downward_message` call targeting that specific para — regardless of origin (relay-chain system messages, other paras' legitimate XCM, governance-neutral protocol messages) — fails with `ExceedsMaxQueueSize` until the victim's collators process and drain enough of the queue. This is a targeted, per-para denial-of-service of the downward message channel, achievable without any XCM send by the attacker and without governance/relay-chain privileges — only control of one or more parachains capable of invoking `hrmp_init_open_channel`/`hrmp_cancel_open_request`/`hrmp_close_channel`.

### Likelihood Explanation
Preconditions require the attacker to control at least one parachain (sovereign account) capable of dispatching HRMP pallet calls via `ensure_parachain` origin (i.e., via its own UMP/XCM Transact dispatch) — a real, permissionless-enough precondition for any registered parachain/parathread, and easier still with several colluding/attacker-owned paras. The attack is cheap (deposit fully refunded via cancel), repeatable every relay block (bounded only by `max_upward_message_num_per_candidate`/UMP throughput per para, which can allow multiple init/cancel cycles per block if batched), and requires no cooperation from the victim or from relay-chain governance. The number of messages needed to hit `dmq_max_length` scales with `MAX_POSSIBLE_ALLOCATION / max_downward_message_size`, which for realistic `max_downward_message_size` configurations is a bounded, reachable count over a sustained but finite campaign.

### Recommendation
Decouple the DMQ hard-cap enforcement from a pure message-count limit and instead account for cumulative queued bytes (or apply a per-source/per-notification-type rate limit) so that a burst of minimally-sized system notifications cannot occupy the same "slot budget" as full-size messages. Specifically: (1) track and bound total bytes in `InboundDownwardQueue` per para (in addition to/instead of just count) so `dmq_max_length` reflects actual memory pressure; and/or (2) add a per-sender-para or per-notification-type throttle/cooldown for HRMP-channel-management notifications (`hrmp_init_open_channel`/`hrmp_cancel_open_request`/`hrmp_close_channel`) to prevent rapid open/cancel cycling from being used purely to grow another para's DMQ; and/or (3) reserve a portion of the DMQ capacity exclusively for non-notification/system messages so notification spam cannot fully exhaust deliverability to a victim para.

### Proof of Concept
Rust integration test in `polkadot/runtime/parachains/src/hrmp/tests.rs` (or a dedicated dmp/hrmp interaction test):
1. Register a victim para `V` and configure `max_downward_message_size`/`MAX_POSSIBLE_ALLOCATION` such that `Dmp::dmq_max_length(..)` is a small, test-friendly number (e.g. via mock config).
2. Register one (or a small number of) attacker para(s) `A`.
3. In a loop until `Dmp::dmq_length(V)` approaches `dmq_max_length`: call `Hrmp::hrmp_init_open_channel(Origin::A, V, cap, size)` then immediately `Hrmp::hrmp_cancel_open_request(Origin::A, HrmpChannelId{sender:A, recipient:V})`, asserting each call succeeds (`assert_ok!`) and that `Dmp::dmq_length(V)` increments by 1 per cycle via `Dmp::dmq_contents_do_not_call_in_consensus(V)`.
4. Once `Dmp::dmq_length(V) == Dmp::dmq_max_length(config.max_downward_message_size)`, attempt to enqueue a legitimate/benign downward message to `V` via `Dmp::queue_downward_message(&config, V, some_msg)` and assert it returns `Err(QueueDownwardMessageError::ExceedsMaxQueueSize)`, proving the victim's downward channel is DoS'd purely via HRMP-notification side effects.

	pub fn can_queue_downward_message(
		config: &HostConfiguration<BlockNumberFor<T>>,
		para: &ParaId,
		msg: &DownwardMessage,
	) -> Result<(), QueueDownwardMessageError> {
		let serialized_len = msg.len() as u32;
		if serialized_len > config.max_downward_message_size {
			return Err(QueueDownwardMessageError::ExceedsMaxMessageSize);
		}

		// Hard limit on Queue size
		if Self::dmq_length(*para) > Self::dmq_max_length(config.max_downward_message_size) {
			return Err(QueueDownwardMessageError::ExceedsMaxMessageSize);
		}

		// If the head exists, we assume the parachain is legit and exists.
		if !paras::Heads::<T>::contains_key(para) {
			return Err(QueueDownwardMessageError::Unroutable);
		}

		Ok(())
	}

	pub fn queue_downward_message(
		config: &HostConfiguration<BlockNumberFor<T>>,
		para: ParaId,
		msg: DownwardMessage,
	) -> Result<(), QueueDownwardMessageError> {
		let serialized_len = msg.len();
		Self::can_queue_downward_message(config, &para, &msg)?;

		let inbound = InboundDownwardQueue::<T>::push_back(para, msg)
			.map_err(|_| QueueDownwardMessageError::ExceedsMaxQueueSize)?;
		let q_len = InboundDownwardQueue::<T>::len(para).unwrap_or(0);

		// obtain the new link in the MQC and update the head.
		DownwardMessageQueueHeads::<T>::mutate(para, |head| {
			let new_head =
				BlakeTwo256::hash_of(&(*head, inbound.sent_at, T::Hashing::hash_of(&inbound.msg)));
			*head = new_head;
		});

		let threshold =
			Self::dmq_max_length(config.max_downward_message_size).saturating_div(THRESHOLD_FACTOR);
		if q_len > threshold as u64 {
			Self::increase_fee_factor(para, serialized_len as u128);
		}

		Ok(())
	}

	pub fn init_open_channel(
		origin: ParaId,
		recipient: ParaId,
		proposed_max_capacity: u32,
		proposed_max_message_size: u32,
	) -> DispatchResult {
		ensure!(origin != recipient, Error::<T>::OpenHrmpChannelToSelf);
		ensure!(
			paras::Pallet::<T>::is_valid_para(recipient),
			Error::<T>::OpenHrmpChannelInvalidRecipient,
		);

		let config = configuration::ActiveConfig::<T>::get();
		ensure!(proposed_max_capacity > 0, Error::<T>::OpenHrmpChannelZeroCapacity);
		ensure!(
			proposed_max_capacity <= config.hrmp_channel_max_capacity,
			Error::<T>::OpenHrmpChannelCapacityExceedsLimit,
		);
		ensure!(proposed_max_message_size > 0, Error::<T>::OpenHrmpChannelZeroMessageSize);
		ensure!(
			proposed_max_message_size <= config.hrmp_channel_max_message_size,
			Error::<T>::OpenHrmpChannelMessageSizeExceedsLimit,
		);

		let channel_id = HrmpChannelId { sender: origin, recipient };
		ensure!(
			HrmpOpenChannelRequests::<T>::get(&channel_id).is_none(),
			Error::<T>::OpenHrmpChannelAlreadyRequested,
		);
		ensure!(
			HrmpChannels::<T>::get(&channel_id).is_none(),
			Error::<T>::OpenHrmpChannelAlreadyExists,
		);

		let egress_cnt = HrmpEgressChannelsIndex::<T>::decode_len(&origin).unwrap_or(0) as u32;
		let open_req_cnt = HrmpOpenChannelRequestCount::<T>::get(&origin);
		let channel_num_limit = config.hrmp_max_parachain_outbound_channels;
		ensure!(
			egress_cnt + open_req_cnt < channel_num_limit,
			Error::<T>::OpenHrmpChannelLimitExceeded,
		);

		// Do not require deposits for channels with or amongst the system.
		let is_system = origin.is_system() || recipient.is_system();
		let deposit = if is_system { 0 } else { config.hrmp_sender_deposit };
		if !deposit.is_zero() {
			T::Currency::reserve(
				&origin.into_account_truncating(),
				deposit.unique_saturated_into(),
			)?;
		}

		// mutating storage directly now -- shall not bail henceforth.

		HrmpOpenChannelRequestCount::<T>::insert(&origin, open_req_cnt + 1);
		HrmpOpenChannelRequests::<T>::insert(
			&channel_id,
			HrmpOpenChannelRequest {
				confirmed: false,
				_age: 0,
				sender_deposit: deposit,
				max_capacity: proposed_max_capacity,
				max_message_size: proposed_max_message_size,
				max_total_size: config.hrmp_channel_max_total_size,
			},
		);
		HrmpOpenChannelRequestsList::<T>::append(channel_id);

		Self::send_to_para(
			"init_open_channel",
			&config,
			recipient,
			Self::wrap_notification(|| {
				use xcm::opaque::latest::{prelude::*, Xcm};
				Xcm(vec![HrmpNewChannelOpenRequest {
					sender: origin.into(),
					max_capacity: proposed_max_capacity,
					max_message_size: proposed_max_message_size,
				}])
			}),
		);

		Ok(())
	}

	fn cancel_open_request(origin: ParaId, channel_id: HrmpChannelId) -> DispatchResult {
		// check if the origin is allowed to close the channel.
		ensure!(channel_id.is_participant(origin), Error::<T>::CancelHrmpOpenChannelUnauthorized);

		let open_channel_req = HrmpOpenChannelRequests::<T>::get(&channel_id)
			.ok_or(Error::<T>::OpenHrmpChannelDoesntExist)?;
		ensure!(!open_channel_req.confirmed, Error::<T>::OpenHrmpChannelAlreadyConfirmed);

		// Remove the request by the channel id and sync the accompanying list with the set.
		HrmpOpenChannelRequests::<T>::remove(&channel_id);
		HrmpOpenChannelRequestsList::<T>::mutate(|open_req_channels| {
			if let Some(pos) = open_req_channels.iter().position(|x| x == &channel_id) {
				open_req_channels.swap_remove(pos);
			}
		});

		Self::decrease_open_channel_request_count(channel_id.sender);
		// Don't decrease `HrmpAcceptedChannelRequestCount` because we don't consider confirmed
		// requests here.

		// Unreserve the sender's deposit. The recipient could not have left their deposit because
		// we ensured that the request is not confirmed.
		T::Currency::unreserve(
			&channel_id.sender.into_account_truncating(),
			open_channel_req.sender_deposit.unique_saturated_into(),
		);

		Ok(())
	}

	fn close_channel(origin: ParaId, channel_id: HrmpChannelId) -> Result<(), Error<T>> {
		// check if the origin is allowed to close the channel.
		ensure!(channel_id.is_participant(origin), Error::<T>::CloseHrmpChannelUnauthorized);

		// check if the channel requested to close does exist.
		ensure!(
			HrmpChannels::<T>::get(&channel_id).is_some(),
			Error::<T>::CloseHrmpChannelDoesntExist,
		);

		// check that there is no outstanding close request for this channel
		ensure!(
			HrmpCloseChannelRequests::<T>::get(&channel_id).is_none(),
			Error::<T>::CloseHrmpChannelAlreadyUnderway,
		);

		HrmpCloseChannelRequests::<T>::insert(&channel_id, ());
		HrmpCloseChannelRequestsList::<T>::append(channel_id.clone());

		let config = configuration::ActiveConfig::<T>::get();
		let opposite_party =
			if origin == channel_id.sender { channel_id.recipient } else { channel_id.sender };

		Self::send_to_para(
			"close_channel",
			&config,
			opposite_party,
			Self::wrap_notification(|| {
				use xcm::opaque::latest::{prelude::*, Xcm};
				Xcm(vec![HrmpChannelClosing {
					initiator: origin.into(),
					sender: channel_id.sender.into(),
					recipient: channel_id.recipient.into(),
				}])
			}),
		);

		Ok(())
	}
