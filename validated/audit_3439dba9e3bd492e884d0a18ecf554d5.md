### Title
Treasury reserve fee (yield) can be permanently rounded down to zero via frequent accrue() calls - (File: `mainnet/contracts/vault/v0-vault-usdh.clar`, and equivalently `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`)

### Summary
In every Zest vault contract, `accrue()` computes the protocol's reserve/fee share (`reserve-inc`) as a division `debt-delta * fee-reserve / BPS`, truncating (`mul-div-down`) to an integer, and then immediately advances `index` to `next` regardless of whether any reserve was actually minted. Because the reference debt snapshot (`old-debt`) is always taken from the *current* `index` at call time, any fractional reserve amount lost to truncation on one `accrue()` call is not carried forward into the next call — it is permanently discarded, exactly like the C4 finding where a division remainder was dropped from `endEpoch`/reward accounting instead of being carried into the next period.

### Finding Description
`accrue()` in each vault (e.g. `v0-vault-usdh.clar` lines 833-865) computes: [1](#0-0) 

- `old-debt = principal-scaled * idx / INDEX-PRECISION` (rounded down)
- `new-debt = principal-scaled * next / INDEX-PRECISION` (rounded down)
- `debt-delta = new-debt - old-debt`
- `reserve-inc = debt-delta * fee-reserve / BPS` (rounded down via `mul-div-down`)
- `treasury-lp = reserve-inc * total-supply / (total-assets-preview - reserve-inc)` (rounded down)

`index` is then unconditionally set to `next`: [2](#0-1) 

The full-precision multiplier calculation (`calc-multiplier-delta`, `calc-index-next`) means borrower debt itself never loses precision across many small accrual steps — the index compounds correctly. However, the *reserve fee slice* taken out of that accrued interest is computed fresh, from scratch, on every single call, using only the delta since the *last* `index` update. If that delta is small enough that `debt-delta * fee-reserve / BPS` truncates to `0`, the DAO treasury receives no `zft` shares for that period, and — because `old-debt` for the *next* call is derived from the now-updated `idx`/`next` — that lost fraction is never recovered. Repeatedly triggering `accrue()` (via `deposit`, `redeem`, `system-borrow`, `system-repay`, or a bare pass-through call) with very short time deltas between transactions (e.g., back-to-back transactions in the same or nearby blocks) keeps `debt-delta` tiny on every call, causing `reserve-inc` to round to `0` on every accrual instead of a single lump sum that would have produced a non-zero value.

This is a direct analog of the reported bug class: a paired accounting relationship (interest created for the vault vs. the reserve fee actually forwarded to the DAO treasury) is broken by a floor-division that discards a remainder instead of carrying it to the next computation, because the "denominator base" is reset on each call just like `allocatedTokensPerEpoch` division being redone in `depositRewardTokens`/`takeOutRewardTokens`/`setAllocatedTokensPerEpoch` without preserving remainders.

### Impact Explanation
Any unprivileged user who interacts with the vault (deposits, redeems, or simply calls a function that triggers `accrue()`) can fragment interest accrual into many small time-slices, causing the protocol's fee/reserve share (`treasury-lp` minted to `.dao-treasury`) to be permanently and systematically under-collected relative to a single lump-sum accrual over the same period. This constitutes a permanent loss of unclaimed protocol yield (the DAO treasury's fee revenue is diverted, dollar-for-dollar, into higher effective returns for LP token holders because the same accrued interest is retained in `total-assets`/`total-supply` without the corresponding dilution from `treasury-lp` minting). This matches the "fees charged versus fees forwarded" and "interest created versus interest distributed" value identities explicitly in scope, with impact "theft/permanent loss of unclaimed yield."

### Likelihood Explanation
Likelihood is limited by transaction cost/throughput: an attacker (or any regular user acting normally, unintentionally) must generate many separate transactions with short time gaps to keep `debt-delta` below the rounding threshold on each call. Since `debt-delta` scales with `time-delta` and `principal-scaled`, this griefing is easiest on vaults with low utilization/low `fee-reserve` values, or immediately following a fee-reserve update. Because Stacks block times are non-trivial, an attacker would need to call `accrue`-triggering functions on nearly every block to keep deltas minimal, making the accumulated leak per unit time bounded but non-zero and strictly worse than honest lump-sum accrual — a real, provable value leak, though the magnitude per call is small (sub-unit rounding), consistent with the Medium/High classification given to the original C4 finding.

### Recommendation
Track the fractional remainder of `reserve-inc`/`treasury-lp` across `accrue()` calls (carry-forward dust) instead of discarding it on each invocation, or compute the reserve share using a monotonic "total reserve owed to date" checkpoint (analogous to computing `total-debt` from `principal-scaled` and cumulative `index` rather than recomputing per-call deltas) so that truncation cannot compound across many small time-slices. Alternatively, round `reserve-inc` up (`mul-div-up`) so any rounding error favors the protocol reserve rather than being silently dropped, and/or accumulate un-minted dust in a persistent variable that is added into the next `reserve-inc` calculation.

### Proof of Concept
1. Vault has non-zero `fee-reserve` and some outstanding `principal-scaled`.
2. Attacker calls any state-mutating vault function (e.g., `deposit` with a minimal amount) every block (or as frequently as possible), each of which internally calls `accrue()`.
3. On each call, `time-delta` is small, so `debt-delta = new-debt - old-debt` computed at lines 844-846 of `v0-vault-usdh.clar` is a small number; `reserve-inc = debt-delta * fee-reserve / BPS` (line 847) truncates to `0` on every call because `debt-delta * fee-reserve < BPS`.
4. `index` is nonetheless advanced to `next` each call (line 849-851), so the next call's `old-debt` baseline has already absorbed the previous delta — the truncated remainder is unrecoverable.
5. Over many such calls covering the same elapsed time as a single lump-sum accrual, the total `treasury-lp` minted to `.dao-treasury` is strictly less (potentially near-zero) compared to the reserve amount that a single `accrue()` call spanning the same total time-delta would have produced, since a single larger `debt-delta` would not truncate to zero.
