Based on my investigation, I found a genuine analog to the "overwritable mapping key" bug class in the Omni Bridge withdrawal path.

### Title
Caller-controlled `externalId` lets a withdrawal collide with (overwrite the destination of) another withdrawal's storage deposit account - (File: packages/intents-sdk/src/bridges/omni-bridge/omni-withdraw-params.ts)

### Summary
`deriveOmniWithdrawIntentParams` derives the on-chain `storageDepositAccountId` (the account that receives the native-fee `storage_deposit`) via `calculateStorageAccountId`, keyed on a hash of the transfer fields plus an `externalId`. The function accepts a caller-supplied `externalId` instead of always generating a fresh random one, and the code comment itself documents that two withdrawals matching on every other field will "land on one account" unless `externalId` differs.

The type-level documentation explicitly warns that `externalId` is what makes the storage account unique, and reusing it across otherwise-identical transfers routes the native fee to the same intermediate account: [2](#0-1) 

The function signature exposes `externalId` as an optional caller-supplied parameter, defaulting to `crypto.randomUUID()` only when omitted: [3](#0-2) [4](#0-3) 

This mirrors the report's bug class: a value that should make each record (here, the implicit storage account for a pending native-fee deposit) unique is derived from a hash whose input is (partly) attacker/caller-controlled, so two independent withdrawals can be forced onto the same on-chain account/identity, allowing one deposit's storage record to be overwritten or shared with another's.

### Impact Explanation
The tests in `sdk.test.ts` show `storageDepositAccountId`/`implicitAccount` is a distinct near-implicit account that receives the `native_token_fee` `storage_deposit` for a specific withdrawal before the relayer processes the `ft_withdraw`. If a caller (or two overlapping SDK calls) reuses the same `externalId` with the same token/amount/recipient/fee/sender/msg, the derived account collides, meaning the storage_deposit intended to fund withdrawal A's relayer fee lands on/interacts with the same account state as withdrawal B. This could result in one withdrawal's native fee being consumed by, or conflated with, another's — a form of "amount debited/credited to the wrong identity," matching the required Critical/High impact class (funds effectively delivered to a wrong destination/account with no straightforward recovery).

### Likelihood Explanation
This is only reachable if `externalId` is exposed/callable with an attacker-influenced value through the public SDK surface. I was **not able to confirm** any public `IntentsSDK`/`OmniBridge` API path that lets an external caller (as opposed to internal SDK test code) actually set `externalId` — `deriveOmniWithdrawIntentParams` and `OMNI_WITHDRAWAL_EXTERNAL_ID` only appeared referenced in `sdk.test.ts` and `omni-bridge-utils.test.ts` within my search results, and I could not load `omni-bridge.ts`/`omni-bridge-utils.ts` in full within the tool budget to verify whether production code always passes a fixed/random constant or forwards a user-supplied value. This is a genuine gap in my verification.

### Recommendation
Confirm whether `externalId` is ever settable through a public SDK entrypoint reachable by an integrator with attacker-influenced input; if so, either (a) always ignore caller-supplied `externalId` and force `crypto.randomUUID()` for any withdrawal whose native fee will be escrowed via `calculateStorageAccountId`, or (b) bind `externalId` deterministically to an already-unique, non-reusable value (e.g., the intent's own signed nonce/hash) rather than accepting free-form caller input.

### Proof of Concept
Not fully constructible from the indexed code alone — the reachable-from-outside path for a caller-controlled `externalId` could not be confirmed with the available context (see Likelihood). If this repo's public API allows setting `externalId` on a withdrawal call, then:
1. Call withdrawal A with `assetId`, `amount`, `destinationAddress`, fee estimation X, `externalId = "E"`.
2. Call withdrawal B with the same `assetId`, `amount`, `destinationAddress`, and fee estimation X, `externalId = "E"`.
3. Both calls produce the same `storageDepositAccountId` per `calculateStorageAccountId({...}, "E")`, per [5](#0-4) , causing the two withdrawals' native-fee storage deposits to collide on-chain.

```typescript
/**
 * The values an Omni withdrawal computes before it builds the intents.
 *
 * `storageDepositAccountId` is derived from `externalId`, and letter case takes part in that
 * derivation, so recomputing any of these sends the native fee to a different account.
 */
export type OmniWithdrawIntentParams = {
	/** The NEP-141 account of the asset. */
	tokenAccountId: string;
	recipient: OmniAddress;
	/** Empty, except for a UTXO chain. Then it contains `MaxGasFee`. */
	msg: string;
	/**
	 * This value makes the storage account unique. The hash covers the rest of the transfer,
	 * so two withdrawals that match on every field would otherwise land on one account.
	 * `calculateStorageAccountId` throws above 64 UTF-8 bytes.
	 */
	externalId: string;
```
