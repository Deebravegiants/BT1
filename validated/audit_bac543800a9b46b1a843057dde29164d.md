## Title
Mandatory challenge period can force legitimate, non-expired requests to be rejected as timed-out before they can ever be delivered - (File: `evm/src/core/HandlerV2.sol`)

## Summary
`handlePostRequests` (and the analogous Substrate path) enforces the state commitment's `challengePeriod` *before* checking whether the request itself has timed out. Because the challenge period is a mandatory waiting window imposed on the state commitment, it consumes part of the request's own `timeout_timestamp` lifespan. If the delay required to satisfy the challenge period is greater than or equal to the time remaining before the request's `timeout()`, the request becomes fundamentally undeliverable: by the time the message is eligible for processing (challenge period elapsed), `block.timestamp` (or `host.timestamp()`) will already exceed the request's `timeout()`, so delivery always reverts with `MessageTimedOut`, and the only path forward is the timeout/refund path — even though the request was dispatched and its underlying state was committed well before its nominal expiry. This is structurally identical to the referenced Y2K report: a mandatory "grace" delay applied by the protocol can outlast the deadline that the delay is being checked against, causing legitimate transactions to be forced into the "failure"/timeout branch instead of the intended success branch.

## Finding Description
In `evm/src/core/HandlerV2.sol`, `handlePostRequests` first requires the challenge period on the state commitment to have elapsed: [1](#0-0) 

Only after that gate does it check `if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();`. Both checks use `block.timestamp` at the moment of delivery. The `challengePeriod` is a chain-wide/state-machine-wide configuration value (part of `HostParams`/consensus configuration), independent of any individual message's `timeout_timestamp`. A relayer (or the message's own sender when choosing a `timeout_timestamp`) has no way to guarantee that `challengePeriod` will always be smaller than `timeout_timestamp - stateMachineCommitmentUpdateTime`.

The identical ordering exists on the ISMP core (Substrate) side: `validate_state_machine` enforces `verify_delay_passed` (the challenge period check) first: [2](#0-1) 

and only afterward, in `handlers/request.rs`, is the request's own timeout checked against `host.timestamp()`: [3](#0-2) 

The protocol documentation itself confirms relayers are *required* to wait for the challenge period before attempting delivery: [4](#0-3) 

So the enforced sequence for every request is: `state commitment time -> (+ challengePeriod, mandatory wait) -> delivery attempt -> compare against timeout_timestamp`. If `challengePeriod >= timeout_timestamp - commitment_time` for any given request/state-machine pairing, delivery is unconditionally impossible: the request will always appear timed out at the earliest legally-permitted delivery moment, exactly as the Sequencer grace period in the Y2K report could exceed the epoch end and make `triggerDepeg()` permanently unusable for a legitimately-strikeable epoch.

## Impact Explanation
This breaks a core protocol guarantee: that a `PostRequest`/`GetRequest` dispatched with a `timeout_timestamp` in the future is deliverable up until that timestamp. Any application (token bridge, intent settlement, generic cross-chain call) that sets a `timeout_timestamp` shorter than or comparable to the destination's configured `challengePeriod` will have its messages systematically forced down the timeout path instead of the delivery path — even though the underlying state proof exists and is valid. Depending on application logic, this can mean:
- Funds locked/escrowed on the source chain pending delivery are refunded via timeout when the intended cross-chain action (mint, execution, order fill) should have succeeded — an unintended state divergence between what "should" happen (delivery) and what actually happens (timeout), and
- A structural "route unable to deliver messages" condition for any state-machine pair where `challengePeriod` is set too high relative to typical/minimum `timeout_timestamp` values used by apps, effectively freezing/misdirecting all such messages.

This qualifies as a route being unable to deliver messages / permanent freezing of intended cross-chain effects under specific but realistic parameterizations (chain congestion pushing up delivery latency, or an app choosing an aggressive timeout window without accounting for the destination's challenge period).

## Likelihood Explanation
Reachable by any unprivileged relayer or app that dispatches a `PostRequest`/`GetRequest` with a `timeout_timestamp` and by any relayer attempting delivery — no special privileges required. The likelihood of triggering the bad outcome depends entirely on the relationship between the state machine's configured `challengePeriod` and the message's `timeout_timestamp`, both of which are ordinary, attacker/user-influenceable or governance-configured parameters, not edge-case inputs. Since `challengePeriod` is fixed per destination state machine while `timeout_timestamp` is chosen per-message by arbitrary senders, it is straightforward for a sender (accidentally or intentionally) to pick a `timeout_timestamp` that falls within the mandatory challenge window, guaranteeing failure.

## Recommendation
When validating a request/response's timeout, do not compare against the raw current timestamp reachable only after the challenge period has elapsed. Instead:
- Reject dispatch of requests whose `timeout_timestamp` is not comfortably greater than `now + challenge_period(dest)` at the time of `dispatch`, so the invariant is enforced at the source rather than discovered as an unresolvable failure at the destination, or
- When checking `timed_out()` at delivery time, base the comparison on the state commitment's timestamp (the moment the request's inclusion became provable) rather than `block.timestamp` at the delivery attempt, so that the mandatory challenge-period wait does not itself consume the message's timeout budget.

## Proof of Concept
1. Configure/observe a destination state machine with `challengePeriod = C` seconds (e.g., via `IHost.challengePeriod()` / `pallet-ismp` `challenge_periods`).
2. Dispatch a `PostRequest` from the source chain with `timeout_timestamp = T`, where `T - dispatch_time < C` (a perfectly reasonable timeout for an app that isn't aware of the destination's challenge period, e.g., a 60s timeout while `C = 300s`).
3. The request's state commitment gets finalized on the destination at time `S` (`S <= T`, i.e., in time to be delivered).
4. A relayer must wait until `S + C` to satisfy `ChallengePeriodNotElapsed` in `handlePostRequests`: [5](#0-4) 
5. By the time `block.timestamp >= S + C`, since `C > T - S`, it follows that `block.timestamp > T = leaf.request.timeout()`, so the very next check reverts with `MessageTimedOut`: [6](#0-5) 
6. The request can never be delivered through `handlePostRequests`; only `handlePostRequestTimeouts` can process it, forcing the timeout/refund branch of the application logic regardless of the sender's original intent.

    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
        }

pub fn validate_state_machine<H>(
	host: &H,
	proof_height: StateMachineHeight,
) -> Result<Box<dyn StateMachineClient>, Error>
where
	H: IsmpHost,
{
	// Ensure consensus client is not frozen
	let consensus_client_id = host.consensus_client_id(proof_height.id.consensus_state_id).ok_or(
		Error::ConsensusStateIdNotRecognized {
			consensus_state_id: proof_height.id.consensus_state_id,
		},
	)?;
	let consensus_client = host.consensus_client(consensus_client_id)?;
	// Ensure client is not frozen
	host.is_consensus_client_frozen(proof_height.id.consensus_state_id)?;

	// Ensure delay period has elapsed
	if !verify_delay_passed(host, &proof_height)? {
		return Err(Error::ChallengePeriodNotElapsed {
			state_machine_id: proof_height.id,
			current_time: host.timestamp(),
			update_time: host.state_machine_update_time(proof_height)?,
		});
	}

	consensus_client.state_machine(proof_height.id.state_id)
}
