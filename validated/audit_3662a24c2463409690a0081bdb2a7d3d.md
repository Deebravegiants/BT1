## Title
Global `challengePeriod` update retroactively re-applies to already-committed state commitments, allowing bypass of the intended fraud-review window - ([File: evm/src/core/HandlerV2.sol])

### Summary
Hyperbridge's optimistic-bridging security model relies on a `challengePeriod` delay between when a `StateCommitment` is stored on the host and when it may be used to process incoming requests/responses/timeouts, giving fishermen time to detect and veto byzantine or fraudulent commitments. Both the EVM host and the `pallet-ismp` host store `challengePeriod` as a single mutable, global parameter that is re-read live at message-handling time rather than being snapshotted against the specific `StateMachineHeight`/commitment it is meant to protect. A governance update to `challengePeriod` therefore takes immediate effect on all previously-stored, still-pending state commitments — exactly the "Challenge period immediate effect" bug class from the referenced report.

### Finding Description
On the EVM side, `HandlerV2.handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, and `handleGetRequestTimeouts` all compute the elapsed delay as `block.timestamp - host.stateMachineCommitmentUpdateTime(height)` and compare it against `host.challengePeriod()`, which is read fresh on every call: [1](#0-0) [2](#0-1) 

`challengePeriod` itself is stored in `_hostParams` and overwritten wholesale by `updateHostParamsInternal`, which is reachable via cross-chain governance (`HostManager.onAccept` → `IHostManager.updateHostParams`): [3](#0-2) 

There is no mechanism that snapshots the challenge period in effect at the time a given `StateMachineHeight`'s commitment was stored (`storeStateMachineCommitment`); the check always uses whatever `challengePeriod` is configured *now*.

The Rust/Substrate side has the identical pattern. `verify_delay_passed` compares `host.timestamp() - state_machine_update_time` against `host.challenge_period(proof_height.id)`, which is looked up live from `ChallengePeriod` storage rather than being tied to the specific commitment height: [4](#0-3) 

`challenge_period` can be changed at any time via the `update_consensus_state` extrinsic: [5](#0-4) 

This directly parallels the report's root cause: a dynamically-applied duration (`challengePeriod`/`delayPeriod`) is always added/compared against a per-item timestamp (`stateMachineCommitmentUpdateTime`/`state_machine_update_time`) at check-time, so any change to the duration retroactively re-scopes every existing pending item instead of only new ones.

### Impact Explanation
Hyperbridge's own documentation states that the challenge window is the core safety mechanism protecting against eclipse/long-range/byzantine consensus attacks: state commitments are optimistically accepted, and fishermen are given the `challenge_period` to submit fraud proofs before those commitments can be used to process messages. [6](#0-5) 

Because the period is a single global value re-read at processing time rather than pinned to the commitment it governs, a governance-driven decrease of `challengePeriod` immediately shortens (or eliminates) the review window for state commitments that are already stored and still "in flight" under the old, longer period. A relayer could then immediately call `handlePostRequests`/`handleGetResponses`/`handlePostRequestTimeouts`/`handleGetRequestTimeouts` (or the pallet-ismp equivalents) against those commitments before fishermen have had the originally-promised opportunity to veto a fraudulent/byzantine commitment — undermining the "unsound state commitment" safety property the challenge window exists to provide. Conversely, an increase can unexpectedly block previously-eligible requests, causing legitimate in-flight messages to miss their `timeout_timestamp` and be wrongly timed out, i.e. a route temporarily unable to deliver messages it otherwise could have.

### Likelihood Explanation
`updateHostParams`/`update_consensus_state` are standard, expected governance operations (not requiring any malicious actor) that can be triggered at any time — e.g. an ordinary parameter tuning for cost/performance reasons. Because the effect on already-pending commitments is immediate and automatic (no attacker action is needed beyond normal relaying of `handlePostRequests`, `handleGetResponses`, or timeout messages that are always permissionless), the unintended re-exposure of already-stored commitments to a shortened review window occurs as a side effect of ordinary configuration changes, not a contrived attack path.

### Recommendation
Snapshot the challenge period at the time a `StateMachineHeight`'s commitment is stored (alongside `stateMachineCommitmentUpdateTime`), and use that stored value — not the live `challengePeriod()`/`challenge_period()` — when validating delay in `handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, `handleGetRequestTimeouts`, and `verify_delay_passed`. This ensures changes to the configured period only affect state commitments recorded after the change.

### Proof of Concept
1. Governance (via `HostManager`) calls `updateHostParams` to reduce `challengePeriod` from, say, 6 hours to 0 (or a very small value), while a legitimate/byzantine `StateMachineHeight` commitment was stored 1 hour ago under the old 6-hour policy (`evm/src/core/EvmHost.sol` `updateHostParamsInternal`, lines 623-636).
2. A relayer immediately calls `HandlerV2.handlePostRequests` (or `handleGetResponses`) with a proof anchored at that 1-hour-old commitment.
3. `delay = block.timestamp - host.stateMachineCommitmentUpdateTime(height)` (1 hour) is now compared against the newly-lowered `challengePeriod` (0), so `challengePeriod > delay` is false and the check passes (`evm/src/core/HandlerV2.sol`, lines 182-185) — even though fishermen were promised the original 6-hour window to veto that commitment and have not had it.
4. The same pattern applies on the Substrate side: calling `update_consensus_state` to shrink `challenge_periods` immediately changes the outcome of `verify_delay_passed` for existing, not-yet-cleared `StateMachineHeight`s (`modules/ismp/core/src/handlers.rs`, lines 103-114).

pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}

A `StateMachineUpdated` event is emitted to notify network participants (both relayers and fishermen) of some newly available `StateCommitment`s for a given state machine. Relayers will wait for the configured `challenge_period` before attempting to transmit new requests & responses. While fishermen will check if these pending `StateCommitment`s describe valid states on the counterparty network. If the `challenge_period` elapses without any fraud proofs being presented, we can safely conclude that the provided `StateCommitment`s are indeed canonical.
