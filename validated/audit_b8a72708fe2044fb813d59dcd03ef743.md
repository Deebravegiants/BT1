### Title
Consensus relayer rewards (BRIDGE payout + reputation mint + reward watermark) are paid immediately on state-machine update and are never reversed when the underlying commitment is later vetoed or the consensus client is frozen for fraud - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`pallet-consensus-incentives::process_message` pays a relayer BRIDGE and mints a reputation asset for delivering a `ConsensusMessage` the moment `pallet-ismp` emits `StateMachineUpdated`, and it permanently advances a `LastRewardedHeight` watermark for that state machine. None of these three effects (treasury payout, reputation mint, or watermark advance) are reverted if that same state commitment is subsequently proven fraudulent — either vetoed by a fisherman (`StateCommitmentVetoed`) within the challenge period, or the whole consensus client is later frozen via `freeze_client`/`FraudProofMessage`. This is the same bug class as the FrankenDAO `veto` report: an action meant to invalidate a prior submission (veto/fraud-freeze) doesn't claw back the bonus/reward that the prior (malicious) submission already earned.

### Finding Description
`update_client` in `modules/ismp/core/src/handlers/consensus.rs:29-84` verifies a consensus proof and, for every state machine included, stores new `StateMachineHeight` commitments and emits `Event::StateMachineUpdated` as soon as verification succeeds — this happens *before* the configured challenge period elapses and before any fisherman has had a chance to submit a fraud/equivocation proof against it (per `docs/content/protocol/ismp/consensus.mdx:171-233`, challenge period + fishermen vetoes are the safety mechanism, and `StateCommitmentVetoed` explicitly exists to retract a bad commitment: [1](#0-0) ).

`pallet-consensus-incentives` implements `FeeHandler::on_executed`, which is invoked right after message execution. For a `Message::Consensus` it recovers the submitting relayer's account from the signature and, for every `StateMachineUpdated` event in the batch, calls `process_message`: [2](#0-1) .

`process_message` computes a reward proportional to the block span advanced, unconditionally:
1. Transfers `reward` BRIDGE from the treasury to the relayer.
2. Mints `reward` reputation asset to the relayer.
3. Advances `LastRewardedHeight` for that state machine to the new height (a forward-only watermark, by design, so a rolled-back height is never repaid) — but this only prevents *double payment*, it does not undo the *first* payment if that first commitment turns out to be fraudulent: [3](#0-2) 

If the exact same commitment that triggered this reward is later found fraudulent — either:
- vetoed by a fisherman while still in its challenge period (`veto_state_commitment` / `StateCommitmentVetoed`, referenced in `tesseract/messaging/evm/src/byzantine.rs:158-193` and `docs/content/protocol/ismp/consensus.mdx:220-232`), or
- the entire consensus client is frozen via `freeze_client` after a `verify_fraud_proof` (equivocation) succeeds (`modules/ismp/core/src/handlers/consensus.rs:124-145`, `modules/pallets/ismp/src/lib.rs:211-215` `FrozenConsensusClients`),

there is no code path connecting either of those outcomes back into `pallet-consensus-incentives`. The relayer keeps the BRIDGE payout, keeps the minted reputation asset, and the `LastRewardedHeight` watermark for that state machine is not rolled back — so even a legitimate future re-submission of a corrected height range can end up under-rewarded (because the watermark already advanced past the fraudulent height) while the malicious/lying relayer keeps its ill-gotten reward and reputation.

This mirrors the FrankenDAO M-10 bug exactly: `veto()` (the fraud-mitigation function) is supposed to strip a malicious actor of any bonus/accounting benefit earned from the invalidated submission, but the implementation only prevents future double-counting, not retroactive clawback of what was already paid based on the now-invalid commitment.

### Impact Explanation
A relayer (or a colluding validator set) that gets a fraudulent/equivocating consensus update accepted — even briefly, before a fisherman vetoes it or a fraud proof freezes the client — permanently keeps:
- The BRIDGE reward transferred from the treasury (`T::Currency::transfer` from `TreasuryAccount`), and
- The minted reputation asset (`T::ReputationAsset::mint_into`).

Since reputation/relayer-incentive systems typically gate future privileges, allowlist status, or larger reward shares on accumulated reputation (as is common in these incentive pallets), a malicious relayer can repeatedly attempt equivocating/fraudulent consensus submissions, race to have `on_executed` fire (which happens synchronously in the same extrinsic as verification, prior to any challenge-period fishermen check), collect the reward and reputation, and only lose future eligibility to submit (via the frozen client) — with no economic slashing or clawback of what was already collected. This is a direct loss of treasury funds (BRIDGE) with no possibility of recovery once transferred, constituting a fund-drain/unbacked-incentive vector reachable by any relayer submitting a consensus message.

### Likelihood Explanation
The reward and mint happen unconditionally and immediately upon `StateMachineUpdated`, with no dependency on the challenge period elapsing or on fisherman review — this is a normal, permissionless flow triggered by any relayer submitting a `ConsensusMessage` that verifies (verification only proves the header/signature was valid per the trusted consensus state, not that the data isn't part of an equivocation/data-withholding attack, which is exactly what challenge periods and fraud proofs exist to catch after the fact). Any relayer capable of producing a byzantine/equivocating but individually-valid consensus proof (or exploiting a data-withholding attack as described in `docs/content/protocol/interoperability/consensus-proofs.mdx:124-146`) can trigger this reward path before the fraud is detected and the client frozen or the commitment vetoed.

### Recommendation
Track which relayer/reward was associated with each rewarded `StateMachineHeight`/`ConsensusStateId`, and add a clawback path invoked from `veto_state_commitment` and `freeze_client`:
- On veto: if the vetoed height falls within an already-rewarded span, roll back `LastRewardedHeight` to below the vetoed height and burn/reclaim the corresponding reputation mint and/or treasury payout from the offending relayer (a slashing/burn mechanism), similar to the recommended fix pattern of decrementing bonus counters on `veto`.
- On `freeze_client`: iterate any rewards paid for heights on/after the divergence point implied by the fraud proof and reverse them (or at minimum stop counting them toward reputation/eligibility going forward, plus flag the relayer for slashing in whatever staking/bonding mechanism exists for consensus relayers, as referenced in `docs/content/protocol/interoperability/consensus-proofs.mdx:144` "relayers who submit consensus proofs to be staked").
- At minimum, gate the reward/mint in `process_message` behind the challenge period elapsing (i.e., don't pay out for heights still within their challenge window), removing the incentive to front-run fisherman review entirely.

### Proof of Concept
1. A relayer submits a `ConsensusMessage` containing a consensus proof for a byzantine/equivocating update (e.g., a data-withholding attack per `docs/content/protocol/interoperability/consensus-proofs.mdx:124-146`, or two conflicting headers where only one is submitted here) that nonetheless passes `ConsensusClient::verify_consensus` for the submitted branch.
2. `update_client` (`modules/ismp/core/src/handlers/consensus.rs:29-84`) stores the new `StateMachineHeight` commitments and emits `StateMachineUpdated`.
3. `pallet-consensus-incentives::on_executed` fires synchronously (`modules/pallets/consensus-incentives/src/impls.rs:108-157`), recovers the relayer's account from the consensus proof signature, and calls `process_message`, which transfers BRIDGE from the treasury and mints reputation to the relayer, then advances `LastRewardedHeight` (`modules/pallets/consensus-incentives/src/impls.rs:41-75`).
4. A fisherman later detects the fraud and either vetoes the specific `StateCommitment` (`StateCommitmentVetoed`) or submits a `FraudProofMessage` that succeeds in `freeze_client` (`modules/ismp/core/src/handlers/consensus.rs:124-145`), freezing the consensus client.
5. In both cases, the relayer's BRIDGE reward transfer and minted reputation from step 3 are never reversed — no code path in `veto_state_commitment` handling or `freeze_client` touches `pallet-consensus-incentives` storage (`LastRewardedHeight`) or claws back the `T::Currency::transfer`/`T::ReputationAsset::mint_into` already executed.

Note: I was unable to locate the exact implementation of `veto_state_commitment` inside `modules/pallets/fishermen/src/lib.rs` (only match locations were surfaced, not the full function body) due to index size limits; the analysis above is based on the confirmed absence of any cross-pallet call from the fishermen/freeze paths into `pallet-consensus-incentives`, and on the fully-visible `process_message`/`on_executed` reward logic. A Devin session with full repo access could confirm the exact `veto_state_commitment` body to rule out any indirect hook.

	fn process_message(
		state_machine_height: StateMachineHeight,
		state_machine_id: StateMachineId,
		relayer_account: T::AccountId,
	) -> Result<(), Error<T>> {
		if let Some(block_cost) = StateMachinesCostPerBlock::<T>::get(state_machine_id) {
			let reward = Self::calculate_reward(&state_machine_id, block_cost)?;

			if reward.is_zero() {
				return Ok(());
			}

			T::Currency::transfer(
				&T::TreasuryAccount::get().into_account_truncating(),
				&relayer_account,
				reward,
				Preservation::Expendable,
			)
			.map_err(|_| Error::<T>::RewardTransferFailed)?;

			Self::deposit_event(Event::<T>::RelayerRewarded {
				relayer: relayer_account.clone(),
				amount: reward,
				state_machine_height,
			});

			T::ReputationAsset::mint_into(&relayer_account, reward.saturated_into())
				.map_err(|_| Error::<T>::ReputationMintFailed)?;

			LastRewardedHeight::<T>::mutate(state_machine_id, |watermark| {
				*watermark = Some(watermark.unwrap_or_default().max(state_machine_height.height));
			});
		}
		Ok(())
	}

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
				Signature::decode(&mut &consensus_msg.signer[..])
					.ok()
					.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
					.map(|pub_key| pub_key.into())
			} else {
				None::<[u8; 32]>
			}
		});

		if let Some(relayer_account) = maybe_relayer_account {
			// When a batch contains multiple `StateMachineUpdated` events for the
			// same `state_machine_id` (sequential consensus updates for the same
			// chain), `calculate_reward` reads the same persisted
			// `(latest_commitment_height, previous_commitment_height)` pair on
			// every iteration and pays the same block-span reward N times.
			// Collapse the per-state-machine event stream to the single highest
			// `latest_height` so each state machine receives one reward per
			// batch, sized by the actual span of its commitment advance.
			let mut highest_per_state_machine: BTreeMap<StateMachineId, u64> = BTreeMap::new();
			for event in events {
				if let IsmpEvent::StateMachineUpdated(update) = event {
					highest_per_state_machine
						.entry(update.state_machine_id)
						.and_modify(|h| {
							if update.latest_height > *h {
								*h = update.latest_height;
							}
						})
						.or_insert(update.latest_height);
				}
			}

			for (state_machine_id, latest_height) in highest_per_state_machine {
				let state_machine_height =
					StateMachineHeight { id: state_machine_id.clone(), height: latest_height };

				let _ = Self::process_message(
					state_machine_height,
					state_machine_id,
					relayer_account.clone().into(),
				);
			}
		}
