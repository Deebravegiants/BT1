### Title
Withdrawal status matched only by `assetId` misattributes destination tx hash when multiple withdrawals of the same token are batched in one intent - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal()` resolves the on-chain completion status/hash for a specific withdrawal index by calling `findMatchingWithdrawal()`, which matches purely on `assetId` (i.e. `near_token_id`) with `Array.prototype.find`. When a caller batches two or more withdrawals of the **same** token in a single NEAR transaction (which the SDK's public API allows via `withdrawalParams[]`), every index sharing that `assetId` receives the identical matched record — the first one returned by the (explicitly documented as "unsorted") POA API — instead of the record that actually corresponds to that index/destination.

and is invoked per-withdrawal-index from `describeWithdrawal`: [2](#0-1) 

The code comment explicitly acknowledges the gap ("multiple withdrawals of the same token in a single transaction are not supported") but, exactly like the referenced report's `HatsSignerGateFactory.deployHatsSignerGate()` (which silently truncated to 5 modules instead of reverting on a documented unsafe precondition), the SDK does not enforce/guard this precondition in code — it merely notes it in a comment while the calling code paths still allow and process the unsafe case.

`sdk.ts` drives per-index completion tracking for an arbitrary array of `withdrawalParams`, launching one polling promise per index/destination: [3](#0-2) 

There is no validation anywhere in this path rejecting duplicate `assetId` entries within a single batch of `withdrawalParams`, so nothing prevents two withdrawals with different `destinationAddress` (or amounts) but the same `assetId` from being submitted together.

The identical unsorted-list/`.find()`-by-shared-key pattern also exists in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`: [4](#0-3) 

### Impact Explanation
When two withdrawals in the same NEAR tx share an `assetId`, `describeWithdrawal()` for index A and index B will match the **same** withdrawal record (whichever the API returns first). This breaks the equality "status/txHash reported for withdrawal index N" == "actual on-chain outcome of withdrawal index N":
- One destination's withdrawal can be reported `completed` with a `txHash` that actually belongs to the other destination's on-chain transfer, while the correct completion for that index is never separately confirmed.
- An integrator that credits/marks-paid based on the reported `(index, txHash, status)` tuple could credit or acknowledge completion for the wrong withdrawal, or double-report the same `txHash` for two distinct payouts — a status/hash misreport that can cause the integrator to credit or refund twice, matching the "High" impact category.

### Likelihood Explanation
This requires only user/integrator behavior already permitted by the public SDK surface (submitting a batch with duplicate `assetId` withdrawals) — no relayer/bridge-operator/admin misbehavior is needed. It is triggered purely client-side by how withdrawals are batched, i.e., it is reachable by any unprivileged caller of `signAndSendWithdrawalIntent`-style batched withdrawal APIs.

### Recommendation
Enforce the documented precondition in code rather than only in a comment: either (a) reject/validate at withdrawal-submission time that a single batch does not contain multiple withdrawals with the same `assetId`, mirroring the reverting fix pattern from the referenced report, or (b) extend `findMatchingWithdrawal`/the POA API integration to disambiguate matches (e.g., by destination address and amount, consuming matched records so they cannot be reused across indices) before this is relied upon for completion reporting.

### Proof of Concept
1. Call the intents-sdk withdrawal flow with `withdrawalParams = [{assetId: "nep141:btc.omft.near", destinationAddress: A, amount: 100000n}, {assetId: "nep141:btc.omft.near", destinationAddress: B, amount: 50000n}]` in one NEAR transaction.
2. The POA bridge indexer returns both withdrawal records (order unspecified) via `getWithdrawalStatus`.
3. `describeWithdrawal({index:0, assetId:"nep141:btc.omft.near", ...})` and `describeWithdrawal({index:1, assetId:"nep141:btc.omft.near", ...})` both call `findMatchingWithdrawal(withdrawals, "nep141:btc.omft.near")`, which returns the same first-matching record for both calls.
4. Both indices report `status:"completed"` with the identical `txHash`, even though only one of the two on-chain transfers (to A or B) has actually completed — an integrator tracking per-index completion will incorrectly treat both destinations as paid.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});

/**

function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,

	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {

		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
