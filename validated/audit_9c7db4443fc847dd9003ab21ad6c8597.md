### Title
Malicious swap-route gadget can hide an authorized wallet-token transfer inside a victim-signed strategy call - (File: contracts/swap-aggregator/src/execute/mod.rs)

### Summary
A `StrategyPayload` route can name an arbitrary contract as a DEX pool. The router invokes that address during the selected venue adapter without establishing that it is a genuine venue contract. While executing beneath the victim’s `sender.require_auth()` / controller `caller.require_auth()` root, the malicious pool can call `token.transfer(victim, attacker, amount)` on an unrelated wallet token. Soroban simulation records that transfer as a child of the victim’s strategy authorization; if the returned authorization tree is signed, the transaction swaps the intended collateral while also transferring the victim’s wallet token to the attacker.

This is the Soroban analogue of a serialized-payload “gadget”: untrusted route bytes select executable third-party code, and the dangerous call is hidden inside an otherwise valid strategy invocation.

### Finding Description
`execute_strategy` deserializes caller-supplied `swap_xdr` into a `StrategyPayload` and calls `execute::run`. [1](#0-0) 

`run` requires authorization from `sender`, decodes the packed program, and executes every instruction. [2](#0-1) 

For a swap opcode, `execute_op` treats `assets[op.idx_a]` as the pool address and dispatches to it. The structural validator bounds-checks indices and opcodes, but it does not bind a `SwapVenue` to an expected pool implementation or allowlist pool addresses. [3](#0-2) [4](#0-3) 

For example, the Soroswap adapter first invokes the route-selected pool’s `get_reserves` and later invokes its `swap` entrypoint. [5](#0-4)  That pool can use either callback to invoke an unrelated token contract and request `token::transfer(victim, attacker, wallet_balance)`. Because the call occurs below the victim’s authorization root, an honest simulation records it as a child invocation; signing that tree authorizes it. The protocol’s measured-output checks only bound the routed tokens and do not reject unrelated child calls. [6](#0-5) 

The same exposure applies when the router is reached through controller strategies. `swap_tokens` authorizes only the exact routed input transfer from the controller to the configured router, then measures controller balances afterward; unrelated victim-wallet transfers under the caller’s root authorization are outside those measurements. [7](#0-6) 

### Impact Explanation
An attacker can steal arbitrary token balances from the transaction signer, not merely the `amount_in` routed through the strategy. The malicious pool can target any token that implements the normal authorization check for `transfer` and for which the victim has a spendable balance.

For a controller path such as `swap_collateral`, the victim receives a plausible successful strategy result: the pool gadget can return compatible reserves and deliver enough output token for the router’s minimum-output and balance-delta checks, while also performing the unrelated wallet transfer. Thus the protocol reports a valid swap while the victim loses unrelated wallet funds.

This is theft of user funds and is High severity: the route itself is user-controlled, the malicious pool is unprivileged code, and the exploit depends on a victim signing a simulated authorization tree containing an unexpected child call.

### Likelihood Explanation
The attack does not require a privileged role, leaked key, upgrade, malformed token, dishonest oracle, or control of a listed market. The attacker deploys one contract implementing the expected pool-facing functions and constructs a valid packed route naming that contract as the pool.

Likelihood is bounded by the required user interaction: the victim must submit or authorize a transaction using the malicious route and sign the authorization tree containing the extra transfer. Wallets or integrators that display only the root strategy invocation, opaque route bytes, or an incomplete authorization tree make this practical. An honest route produces no unexpected caller-auth child, but the protocol does not enforce that property; integrators are expected to detect it themselves. [6](#0-5) 

### Recommendation
Prevent route-selected contracts from placing unrelated calls beneath the signer’s authorization tree.

1. Bind each venue opcode to governance-approved venue/pool contracts or introduce an explicit venue registry, rather than accepting arbitrary `assets[idx]` values as executable pools.
2. If arbitrary pools remain supported, execute route hops through a separate authorization context that cannot inherit the end user’s root invocation. In practice, this requires separating the user’s signed token pull from the strategy’s external dispatch rather than running both under one `require_auth` tree.
3. For controller-routed swaps, reject routes that produce any authorization children other than the expected router pull and known venue pull. A protocol-level check is preferable to relying on every wallet and integrator to inspect the tree.
4. Publish machine-readable route metadata so clients can verify that the authorization tree contains exactly the expected invocations before signing.

### Proof of Concept
The repository already contains a functional regression-style demonstration in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`.

The test deploys a route-compatible router and an attacker-controlled `RogueHopPool`. The route passes the attacker pool through the serialized swap argument; the router then invokes that pool during `swap_collateral`. [8](#0-7) 

Inside the malicious pool’s `swap` function, the contract calls an unrelated wallet token’s `transfer` with `from = victim`, `to = attacker`, and the victim’s full balance. [9](#0-8) 

Simulation records that unrelated transfer as a child of Alice’s `swap_collateral` authorization, after which Alice’s unrelated wallet balance is zero and the attacker owns the funds. [10](#0-9) 

The enforcing-mode half proves the security boundary precisely: the honest root-only authorization tree rejects the hidden transfer, while signing the poisoned simulation tree authorizes it and moves the wallet token. [11](#0-10)

                panic_with_error!(env, Error::InvalidRouteXdr);
            };

                record[field::POOL] as u32,
                record[field::TOKEN_IN] as u32,
                record[field::TOKEN_OUT] as u32,
            );

            // must have a single output, and that output must be this
            // instruction's input.
            if mode == Mode::Prev {
                if i == 0 {
                    panic_with_error!(env, Error::BrokenTokenChain);
                }
                let previous = self.raw(i - 1);
                let produced = match Opcode::from_u8(previous[field::OPCODE]) {
                    // A swap produces its `token_out`, a mint its share token.
                    Some(Opcode::Swap(_)) => previous[field::TOKEN_OUT],
                    Some(Opcode::Mint) => previous[field::TOKEN_IN],
                    // A burn releases every constituent at once.
                    _ => panic_with_error!(env, Error::BrokenTokenChain),
                };
                if idx_b != produced as u32 {
                    panic_with_error!(env, Error::BrokenTokenChain);

                    panic_with_error!(env, Error::InvalidRouteXdr)

                panic_with_error!(env, Error::InvalidRouteXdr);

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();

#[test]
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
}
