### Title
Webhook shop-domain attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop-domain` (and `topic`/`webhook-id`) header to attribute the webhook to a tenant. This is the same bug class as the reported STETHVault issue: a value used in a critical decision (there, `totalIdleAssets`; here, `shop`) is not covered by the same integrity check that gates the rest of the operation, so an attacker who can obtain one validly-HMAC'd payload can re-bind it to a different identity.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`. For webhooks, `Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` uses this same object to gate execution — it raises `InvalidWebhookError` unless `HmacValidator.validate(request)` succeeds — but then unconditionally forwards `request.shop` (parsed straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, never covered by the HMAC) into the handler as the tenant identifier: [2](#0-1) 

`Request#shop` is read directly from headers with no verification tying it to the signed body: [3](#0-2) 

Because the shared `api_secret_key` used to compute the HMAC is the same for every shop that has installed a given app (it is the app's client secret, not a per-shop secret), any merchant who has installed the app on their own store can capture a validly-signed webhook body (Shopify will send them one for their own store events) and then replay that exact `raw_body` + `hmac-sha256` value to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop that also uses the app. `Registry.process` will validate the HMAC (it only checks the body, which is unmodified and still correctly signed) and will hand `WebhookMetadata` with `shop: <victim-shop>` to the host application's handler: [4](#0-3) 

This breaks the intended binding: `shop-attributed-by-header == shop-that-actually-produced-the-signed-body`. The equality that should hold is `HMAC(raw_body) valid ⇒ (raw_body, shop) both authentic`, but the gem only proves `HMAC(raw_body) valid`, leaving `shop` fully attacker-controlled once one legitimate signed body is captured.

The gem's own documentation instructs consumers to trust `data.shop` directly as "The shop domain of the webhook" and use it to route/attribute business logic (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), with no caveat that `shop` is unauthenticated: [5](#0-4) 

### Impact Explanation
This enables cross-tenant data injection/confusion: an attacker who legitimately installs the target app on a shop they control can forge webhooks that Registry.process will accept as authentic for an arbitrary victim shop (since `shop` isn't part of the signed payload). Depending on how the host app uses `data.shop` (crediting orders, updating inventory, feeding into per-tenant caches/queues, triggering per-tenant side effects), this can result in cross-tenant data corruption or unauthorized actions attributed to a shop the attacker does not control — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Requires only that the attacker be able to install the target app on a shop they control (a normal unprivileged action for any Shopify merchant/developer) and have their webhook endpoint (or a captured payload) resend the exact same raw body/hmac pair with a different `shop-domain` header value to the same processing endpoint. No access token, `client_secret`, or privileged account is required — only ordinary app installation, which is the intended, unprivileged use path for this feature.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or require the host application to cross-check the header `shop` against a known/authorized list of shops for which the given app registered that specific webhook topic before trusting it. At minimum, document prominently that `data.shop` is not covered by the HMAC and must be independently verified against the app's installed-shop registry before being used for tenant attribution.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a normal, unprivileged installation).
2. Shopify sends a legitimately HMAC-signed webhook to the app for a topic (e.g. `orders/create`), with headers `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-hmac-sha256: <valid-hmac-of-body>`, and some `raw_body`.
3. Attacker captures `raw_body` and `shopify-hmac-sha256` value.
4. Attacker crafts a new HTTP POST to the app's webhook endpoint with the same `raw_body` and `shopify-hmac-sha256`, but with `shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers/body: [6](#0-5) 
6. `Registry.process` validates the HMAC (unchanged, still matches the body) and dispatches the handler with `shop: "victim-shop.myshopify.com"`: [2](#0-1) 
7. Any host-app logic keyed on `data.shop` (as shown in the gem's own docs example) now executes as if the event genuinely originated from `victim-shop.myshopify.com`, despite the payload actually belonging to the attacker's own shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
