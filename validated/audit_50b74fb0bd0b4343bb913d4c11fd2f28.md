### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `HmacValidator.validate` computes/compares the HMAC solely over that body. None of the `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, or `shopify-api-version` headers are included in the signed material, yet `Registry.process` forwards the unauthenticated `request.shop` value straight into `WebhookMetadata`, which the app's `WebhookHandler.handle` implementation treats as the authoritative tenant identifier for the event.

### Finding Description
The binding that should hold is: `shop authenticated by HMAC == shop the app acts on`. Instead:

- `Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 
Only `@raw_body` is fed into the signature computation.

- `HmacValidator.validate` / `validate_signature` compute the HMAC purely from `verifiable_query.to_signable_string` (the body) and compare against the `hmac` header: [2](#0-1) 

- `Registry.process` only checks that this body-only HMAC is valid, then immediately trusts `request.shop` (sourced from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed payload) to build the metadata handed to the app's handler: [3](#0-2) 

- `Request#shop` simply reads the header verbatim, with no cross-check against the body or the signature: [4](#0-3) 

Because the `shop` header is completely outside the HMAC's protection, any POST body/HMAC pair that is valid for one shop remains valid (per this gem's check) no matter what `shop-domain` header accompanies it. An attacker who installs the app on their own store (a normal, unprivileged action available to any internet user for a public app) can trigger an event that produces a legitimately-signed webhook body (e.g., by creating a product with attacker-chosen content), capture that `(raw_body, hmac)` pair, and replay it directly to the app's public webhook endpoint with the `x-shopify-shop-domain` header rewritten to an arbitrary victim shop domain. `Utils::HmacValidator.validate` will accept it because the signature only ever certifies the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming this attacker-controlled body belongs to the victim's shop.

### Impact Explanation
This breaks the tenant isolation the gem is expected to provide to consuming apps: `WebhookHandler#handle` receives `data.shop` as a trusted, "verified" tenant identifier (this is explicitly how the library documents the field to app authors), when in fact it is fully attacker-controlled. Any host application that uses `data.shop` to select which merchant's session/data/state to update, enqueue background jobs against, or invalidate caches for, can be made to act on a victim shop's behalf using attacker-supplied body content — a cross-tenant access primitive.

### Likelihood Explanation
Likelihood is moderate-to-high: no `api_secret_key`, access token, or credential leakage is required. The attacker only needs to be able to install the app on a store they control (or trigger any event yielding a webhook to their own tenant) and be able to send an arbitrary HTTP POST to the app's known public webhook path with custom headers — both are standard unprivileged-internet-user capabilities. The only work is capturing one legitimately-signed body/HMAC pair for a chosen payload, which is trivial since the attacker controls their own shop's events.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) in the signed/verified material, or otherwise cryptographically bind them to the payload before trusting them (e.g., derive/verify the shop domain from data embedded and covered by the signed body, or require the consuming app to independently verify the shop matches a known, previously authorized session). At minimum, `HmacValidator`/`Request` should not allow `shop` to be treated as verified when it is excluded from `to_signable_string`.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a webhook-producing event (e.g., `products/create`) with an attacker-chosen body; capture the resulting `raw_body` and the `x-shopify-hmac-sha256` value Shopify computed with the app's shared secret.
3. POST directly to the app's public webhook endpoint with:
   - Same `raw_body` and `x-shopify-hmac-sha256` (unchanged — still valid, since HMAC only covers body).
   - `x-shopify-topic`, `x-shopify-webhook-id`, `x-shopify-api-version` as needed.
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (forged).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` → passes (body/HMAC match), then builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker body>, ...)` and invokes the app's handler, which now acts as if `victim-shop.myshopify.com` produced the attacker's chosen payload.           result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
