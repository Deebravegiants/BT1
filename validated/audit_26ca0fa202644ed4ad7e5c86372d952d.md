### Title
Webhook shop-domain header not covered by HMAC allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body. The shop identity (`shopify-shop-domain` header) that is later handed to the host application's handler as the authoritative tenant identifier is never included in the signed material. Any tenant that can generate one legitimately-signed webhook for their own store (which any merchant installing a multi-tenant app can do) can replay that exact `(body, hmac)` pair while swapping the `shop-domain` header, and the library will report it as coming from an arbitrary victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, and its signable content is only the raw body: [1](#0-0) [2](#0-1) 

The `shop` accessor is read directly from an unauthenticated HTTP header, with no cryptographic binding to the HMAC at all: [3](#0-2) 

`Utils::HmacValidator.validate` computes/verifies the signature exclusively over `to_signable_string` (i.e., the raw body), using the app's single, app-wide `api_secret_key` — the same secret is used for every shop that has installed the app: [4](#0-3) 

`Registry.process` gates entirely on this body-only HMAC check and then forwards the unauthenticated `request.shop` value straight to the host application's webhook handler as the tenant identity for the event: [5](#0-4) 

This exactly mirrors the report's bug class: a value that is *acted on* (the delegate address / here, the shop domain used to attribute and process the webhook payload) is not covered by the integrity check (the vote tally / here, the HMAC signature). The binding the code implicitly assumes — "the shop whose secret validated this HMAC" equals "the shop named in the `shop` field used for downstream processing" — does not actually hold, because the secret is shared across all tenants and the `shop` field is outside the signed scope.

### Impact Explanation
Because the HMAC secret (`api_secret_key`) is identical for every shop that installs a given multi-tenant app, any merchant who has installed the app (an "unprivileged" tenant relative to other merchants) can:
1. Trigger a legitimate webhook from their own store (perfectly valid `(raw_body, hmac)` pair, correctly signed with the app's secret).
2. Replay that exact HTTP request to the app's webhook endpoint, only changing the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to name a victim shop.

`Utils::HmacValidator.validate` still succeeds (it never looks at the header), and `Registry.process` calls the handler with `WebhookMetadata` whose `shop` is the attacker-chosen victim domain. If the host application uses `data.shop` (as documented/intended) to decide which merchant's data/tenant context to update, this enables cross-tenant data injection/confusion — e.g. attributing attacker-controlled order/product/customer payloads to a different merchant's store, corrupting that merchant's data or triggering merchant-scoped side effects under a false identity. This satisfies the Critical "cross-tenant access" impact bucket.

### Likelihood Explanation
Likelihood is High/Low-difficulty: no access to `api_secret_key`, no privileged account, and no TLS interception is required — only the ability to install the app on one's own store (the normal, expected way any merchant uses the app) and issue a normal HTTP request with a modified header, which is standard "unprivileged internet user" capability.

### Recommendation
Bind the shop identity into the verified material, e.g.:
- Require callers to pass the expected/session shop and compare it against `request.shop` before dispatch, or
- Include the shop domain (and other headers actually relied upon downstream) inside the HMAC-signed payload/verification, or use a per-shop-derived secret/session validation in addition to the app-wide HMAC, so that a body signed under one tenant cannot be attributed to another tenant.
- At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted without additional binding.

### Proof of Concept
1. App "Acme App" is installed by both Attacker's store (`attacker.myshopify.com`) and Victim's store (`victim.myshopify.com`), sharing one `api_secret_key`.
2. Attacker triggers any webhook event on their own store, capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent (a fully valid, correctly-signed request for that body).
3. Attacker POSTs the same body + same HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls: [6](#0-5) 
   `Utils::HmacValidator.validate(request)` returns `true` (body/hmac match, since shop isn't part of the signed content), and the handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though the payload actually originated from the attacker's own store.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
