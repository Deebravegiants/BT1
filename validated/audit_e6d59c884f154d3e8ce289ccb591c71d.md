## Vulnerability Found

### Title
Webhook `shop-domain` Header Is Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` entirely from unauthenticated HTTP headers, while the HMAC signature verified by `HmacValidator.validate` only covers the raw request body. `Registry.process` trusts `request.shop` as the tenant identity after HMAC validation succeeds, even though `shop` was never part of the signed payload.

### Finding Description
The identity binding that should hold is: `hmac_valid(raw_body, secret) == true` implies `shop == the shop that actually triggered this event`. In this gem, that equality does not hold, because `to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

`HmacValidator.validate` computes the signature strictly over `verifiable_query.to_signable_string`, i.e. over the body only: [3](#0-2) 

`Registry.process` treats a passing HMAC check as sufficient proof of authenticity for the whole request, and then forwards the attacker-controllable `request.shop` value straight to the app's handler as trusted tenant metadata: [4](#0-3) 

By contrast, the OAuth callback path in this same gem does bind `shop` into the signed payload — `AuthQuery#to_signable_string` explicitly includes `shop`: [5](#0-4) 

This inconsistency confirms `shop` is a security-relevant field elsewhere in the gem, but it was omitted from the webhook signable string.

Because an app's webhook secret (`api_secret_key`, the same `client_secret` used for OAuth) is shared across every shop that installs the app, any merchant who legitimately installs the app can capture a genuine webhook delivery for their own store (valid `raw_body` + valid `hmac-sha256` header, computed with the app's real secret). That attacker-merchant can then replay the exact same body and HMAC header to the app's webhook endpoint while substituting an arbitrary victim shop's domain in the `x-shopify-shop-domain` header. `HmacValidator.validate` still succeeds because it never inspects the shop header, and `Registry.process` dispatches the event with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` to select which tenant's session/data to act on (the documented and expected usage pattern, per `docs/usage/webhooks.md`) can be tricked into applying a genuine, HMAC-verified webhook payload to a shop the attacker does not control. This is a cross-tenant access primitive: an authenticated attacker (a real, if malicious, app installer) can forge events attributed to another merchant's shop, causing the host application's business logic (order processing, inventory sync, data writes, deduplication via `webhook_id`, etc.) to run against the wrong tenant using data the attacker fully controls.

### Likelihood Explanation
Likelihood is High for any app that installs the app on at least one shop (a normal, unprivileged use case, not requiring any secret or elevated access) — installing the app is enough to obtain a valid `raw_body`/`hmac-sha256` pair. Forging the HTTP request to the app's public webhook endpoint with a different `x-shopify-shop-domain` header requires no cryptographic material beyond the attacker's own legitimately received webhook.

### Recommendation
Include the shop-identifying header (`shop-domain`) in the value that is HMAC-verified, or otherwise cryptographically bind the shop domain to the signed webhook payload before trusting `request.shop`/`WebhookMetadata#shop` in `Registry.process`. At minimum, document that `request.shop` is unauthenticated and require host applications to cross-check it against a shop that is independently known to have registered for that `webhook_id`/`topic`.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and lets the app register for, e.g., the `orders/create` webhook.
2. Shopify delivers a webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw_body>`, and some `raw_body`.
3. Attacker captures this raw body and the HMAC header, then sends a new HTTP POST directly to the same app webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256` header, but with `x-shopify-shop-domain` changed to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this successfully (all three required headers present), `Utils::HmacValidator.validate` returns `true` because it only checks `raw_body` against the shared secret, and `Registry.process` invokes the handler with `WebhookMetadata#shop == "victim.myshopify.com"` — a value the attacker fully controls despite passing HMAC validation.

        end
