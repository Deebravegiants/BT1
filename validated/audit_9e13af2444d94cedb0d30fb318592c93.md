## Title
Intent Gateway escrow refunds permanently freeze funds for blacklisted `order.user` addresses on USDC/USDT-style input tokens - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
The Hyperbridge Intent Gateway (`IntentsBase`/`IntrinsicIntents`/`ExtrinsicIntents`) escrows input tokens on order placement and releases them via `_withdraw`, which performs a direct `IERC20(token).safeTransfer(beneficiary, amount)` to a hardcoded beneficiary — either `order.user` (on cancel/refund) or the solver (on fill). There is no pull-based claim path where the beneficiary can redirect funds to an alternate address. If `order.user` is later added to a blacklist by the input token issuer (e.g. USDC/USDT), every refund path for that order permanently reverts, freezing the escrowed funds indefinitely. This mirrors the reported Dinari `BuyOrderIssuer._cancelOrderAccounting()` issue, but is worse here because retries through the ISMP delivery pipeline are deterministic re-executions of the same failing transfer.

### Finding Description
`IntentsBase._withdraw` unconditionally transfers escrowed tokens to a fixed `beneficiary` address decoded from the withdrawal request, with no fallback or alternate-recipient mechanism: [1](#0-0) 

This function is reached from three different refund/settlement paths, all of which use `order.user` as the fixed beneficiary for refunds:

1. **Same-chain cancel** — executes synchronously inside `cancelOrder`: [2](#0-1) 

2. **Cross-chain cancel initiated from destination** — dispatches a `RefundEscrow` POST that is later processed by `onAccept` on the source chain: [3](#0-2) [4](#0-3) 

3. **Cross-chain cancel initiated from source** — dispatches a GET request whose response is processed by `onGetResponse`, which also calls `_withdraw`.

The Tron/EVM-alternate implementation (`evm/tron/contracts/apps/IntentGatewayV2.sol`) has the identical pattern using low-level `IERC20.transfer` calls that revert on `success == false`: [5](#0-4) 

For the cross-chain paths, the failing transfer occurs inside `onAccept`/`onGetResponse`, which are called by `EvmHost.dispatchIncoming`. When the app call reverts, the host simply deletes the request/response receipt "so that it can be retried": [6](#0-5) 

Because the underlying cause (the blacklist status of `order.user` on the input token) does not change between retries, this "retryable" design does not actually recover the funds — every relayer redelivery attempt will deterministically fail in the same way, permanently freezing the escrow for that specific order commitment. The same-chain path is even worse: the `cancelOrder` transaction itself reverts entirely, so the user can never retrieve their escrowed input tokens through the contract at all.

### Impact Explanation
Any order whose `order.user` becomes blacklisted on the escrowed input token (USDC/USDT or any other token with an issuer-controlled blacklist) after placing an order loses the ability to ever recover that escrow through:
- direct same-chain cancellation,
- cross-chain cancellation from the destination chain, or
- cross-chain cancellation from the source chain (GET-based unfilled-order proof).

This is a permanent freezing of user funds, matching a Medium severity finding per the guidelines (concrete permanent freezing of funds reachable from a single order placement + cancellation flow, no privileged actor required). It is worth noting the escrowed funds sit in the `IntentGateway` contract, not a shared pool, so this affects a specific victim order's funds and does not directly threaten other users' orders — but for the affected order, the freeze is total and un-remediable via any contract-level mechanism.

### Likelihood Explanation
Being blacklisted is not attacker-controlled and requires third-party/regulatory action against the address in question, so this is not exploitable at will. However, given USDC/USDT's active and increasingly used blacklist enforcement (including sanctions-driven blacklisting), it is a realistic real-world scenario for any long-lived order or any user later flagged, and it requires no special privileges or race conditions to trigger once the underlying blacklist condition exists.

### Recommendation
Introduce a pull-based recovery mechanism for `_withdraw`/`withdraw`, similar to the sherlock-audit recommendation of a separate user-callable `refund()`/`claim()` function that lets the beneficiary specify an alternate receiving address, or hold failed-transfer amounts in an internal per-user balance that can be withdrawn to any address the caller controls (e.g., `try/catch` around the `safeTransfer` and credit an internal ledger on failure, exposing a `withdrawTo(token, amount, to)` for the affected beneficiary).

### Proof of Concept
1. User places a cross-chain order on the source chain with USDC as the input token, escrowing `inputAmount` in the `IntentGateway` contract.
2. Circle blacklists `order.user`'s address on USDC (independent of the protocol).
3. User (or, post-deadline, any relayer on their behalf) calls `cancelOrder` targeting the destination-chain cancellation path; the destination gateway dispatches `RefundEscrow`.
4. The message is delivered to the source `IntentGateway.onAccept`, which calls `_withdraw(body, true, true)` → `IERC20(usdc).safeTransfer(order.user, refund)` → reverts because `order.user` is blacklisted, per [7](#0-6) .
5. `EvmHost.dispatchIncoming` catches the revert, deletes the receipt to make it "retryable", per [8](#0-7) , but every future relayer redelivery attempt fails identically since the blacklist status is unchanged.
6. The escrowed USDC for this order is now permanently stuck in the `IntentGateway` contract; there is no alternate withdrawal path exposed to the user.

        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];

            unchecked {
                ++i;
            }

        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
