The exact analog exists in the `pallet-hyper-fungible-token` module. The `update_token` extrinsic's `remove_chains` path deletes the `Precisions` and `TokenContracts`/`ContractToAsset` entries for a chain immediately, with no check for outstanding in-flight transfers to that chain — mirroring the reported USSD bug where removing collateral support permanently locks previously-escrowed funds.

### Title
Removing a chain from a registered token via `update_token` permanently locks escrowed/burned funds for in-flight transfers - (File: `modules/pallets/hyper-fungible-token/src/lib.rs`)

### Summary
`update_token` lets `CreateOrigin` remove a destination chain's `TokenContracts`/`ContractToAsset`/`Precisions` entries for a registered asset at any time, with no check for requests already dispatched to that chain that haven't been delivered or timed out yet. Since `on_timeout` depends on `Precisions` to compute the refund amount, removing the chain makes any pending refund permanently unprocessable, stranding user funds that were already escrowed (native asset) or burned (non-native asset) in the `send` call.

### Finding Description
`send()` immediately escrows the native asset into the pallet account (or burns a non-native asset) and dispatches a cross-chain `PostRequest` to `params.destination`, based on `TokenContracts`/`Precisions` state at send time: [1](#0-0) 

Later, if the request times out, `on_timeout` re-reads `ContractToAsset` and `Precisions` for the request's `(dest, to)` pair to determine what to refund: [2](#0-1) 

`update_token`'s `remove_chains` loop unconditionally wipes `TokenContracts`, `ContractToAsset`, and `Precisions` for the given `(asset_id, chain)` pair — it has no guard against outstanding requests still in flight to that chain: [3](#0-2) 

If governance removes a chain from a token's configuration while a `send()` to that chain is still pending (not yet delivered and not yet timed out), the eventual `on_timeout` call fails with `DecimalsNotConfigured(dest)` because `Precisions::<T>::get(local_asset_id, dest)` returns `None`. There is no separate withdrawal/reclaim path for escrowed or burned funds elsewhere in the pallet — `on_accept` only credits inbound transfers, and `send`/`register_token`/`update_token` provide no way to release the escrow account's balance directly. Consequently, the sender's already-escrowed (or burned) tokens can never be recovered: the refund path is the only path back to the user and it is now permanently broken for that request.

### Impact Explanation
This is a permanent freezing-of-funds bug reachable by an ordinary user simply calling `send()` to a chain that governance later delists via `update_token`. For native assets the funds sit forever in the pallet's escrow account (`pallet_account()`); for non-native assets the user's tokens were already burned with no compensating mint, so the loss is total and irreversible. This meets the Medium/High bar for concrete permanent freezing of user funds.

### Likelihood Explanation
Likelihood depends on governance timing (`CreateOrigin` calling `update_token` with `remove_chains` while transfers to that chain are in flight — a plausible real operational action, e.g. delisting a compromised or deprecated destination chain), but the resulting state is permanent and requires no attacker collusion beyond ordinary use of the pallet by a normal user plus a normal governance action.

### Recommendation
Before removing a chain in `update_token`, either (a) disallow removal while `Precisions`/`TokenContracts` are needed for pending timeouts by retaining historical precision/contract data keyed by request rather than deleting it outright (e.g. keep an append-only precision/contract history instead of overwriting/removing), or (b) provide an explicit admin-gated recovery/withdrawal extrinsic that can release escrowed funds for a given request commitment when its `on_timeout` cannot be processed due to missing configuration. At minimum, `on_timeout` should not hard-fail when `Precisions`/`ContractToAsset` are missing — it should fall back to a stored snapshot from the time the request was dispatched.

### Proof of Concept
1. Register a native asset `X` for chain `Evm(1)` via `register_token`, with `Precisions[X, Evm(1)] = 18`.
2. User calls `send(asset_id=X, destination=Evm(1), amount=100, timeout=T)`. The pallet transfers 100 `X` into `pallet_account()` and dispatches a `PostRequest` to `Evm(1)`.
3. Before the request is delivered or times out, governance calls `update_token(asset_id=X, remove_chains=[Evm(1)])`. This removes `TokenContracts[Evm(1), X]`, `ContractToAsset[Evm(1), contract]`, and `Precisions[X, Evm(1)]`.
4. Request times out; `pallet-ismp` invokes `on_timeout`, which calls `Precisions::<T>::get(X, Evm(1))` → `None` → returns `Err(HftError::DecimalsNotConfigured(Evm(1)))`.
5. The refund never executes; the 100 `X` remain locked in `pallet_account()` indefinitely with no extrinsic available to release them.
