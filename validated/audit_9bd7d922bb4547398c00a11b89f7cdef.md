### Title
Webhook HMAC validation only covers the request body, not the `shop-domain` header, allowing cross-tenant shop-identity spoofing in `Webhooks::Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `Utils::HmacValidator.validate` verifies the `X-Shopify-Hmac-SHA256` value against that body alone. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are never covered by the HMAC. `Webhooks::Registry.process` trusts `request.shop` (taken directly from the unauthenticated header) to identify which tenant/shop the webhook belongs to when it invokes the handler. This breaks the identity binding `shop authenticated == shop acted upon`: the HMAC binds the body to the app's secret, but the `shop` value passed to the handler is bytes that were never part of what was verified.

### Finding Description
`Webhooks::Request` exposes: [1](#0-0) 

`shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, while `to_signable_string` (the value that actually gets HMAC-checked) is only `@raw_body`: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`: [3](#0-2) 

`Webhooks::Registry.process` checks only this body-based HMAC, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because `shop-domain` is not part of the signed material, any request whose body+HMAC pair is valid for *some* legitimately-triggered webhook can be replayed with an arbitrary `shop-domain` header substituted, and `Registry.process` will still consider the HMAC valid and hand the handler a `WebhookMetadata` claiming to be from the attacker-chosen shop. The equality the code implicitly assumes — "the shop whose data produced this HMAC" == "the shop passed to the handler" — does not hold, since only the body (not the shop identity) is authenticated.

### Impact Explanation
This directly enables cross-tenant confusion in multi-tenant Shopify apps built on this gem: a party who can trigger (or previously captured) one legitimately-signed webhook delivery for their own shop — a normal, unprivileged event for any merchant/shop installed on the app, not requiring `api_secret_key` — can replay that exact body/HMAC pair to the app's webhook endpoint while swapping the `shop-domain` header to a victim shop. `Registry.process` will accept the HMAC (it never inspected the header) and dispatch the handler as if the payload originated from the victim shop, since `WebhookMetadata.shop` is populated from the unauthenticated header. Depending on how the host app's webhook handler uses `data.shop` (e.g., to select which tenant's records to update/look up), this allows cross-tenant data corruption or disclosure attributed to the wrong shop — squarely a "cross-tenant access" Critical-impact scenario, achieved purely through this gem's own webhook-verification code path, with no access token, secret key, or privileged account needed by the attacker.

### Likelihood Explanation
Likelihood is moderate-to-high in any app where an attacker shop is a legitimate, unprivileged installer of the app: they can capture their own webhook deliveries (body + valid HMAC) via any HTTP intermediary/log they control, then send a forged POST directly to the app's public webhook route with a different `shop-domain` header. No secret material or elevated privilege is required — only the ability to install the app on one's own store and observe/replay one's own webhook traffic, which is standard unprivileged internet-user capability.

### Recommendation
Include the tenant-identifying headers (`shop-domain` at minimum, ideally `topic`/`webhook-id`) in the HMAC-signed material, or otherwise cryptographically bind the shop domain to the verified body (e.g., have `Webhooks::Request#to_signable_string` incorporate the shop domain, or require the host app to independently confirm that the `shop-domain` header corresponds to a shop with a known, previously-established session/webhook registration) before `Registry.process` passes `request.shop` to any handler.

### Proof of Concept
1. App is installed on Attacker's shop `attacker.myshopify.com`; Shopify sends a legitimate webhook (e.g. `orders/create`) to the app's endpoint with body `B` and header `X-Shopify-Hmac-SHA256: H`, where `H = HMAC-SHA256(secret, B)`, and `Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker captures `(B, H)` (e.g., via a proxy under their control, or by simply knowing the content of their own order payload/body since they control the order data).
3. Attacker sends a forged request to the same webhook endpoint with the identical body `B` and header `X-Shopify-Hmac-SHA256: H`, but `Shopify-Shop-Domain: victim.myshopify.com`.
4. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (== `B`, unaffected by header change) and matches `H` — validation passes. [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.shop == "victim.myshopify.com"`, even though the payload never originated from or was authorized by that shop — cross-tenant identity confusion is achieved without any secret, token, or privileged access.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
