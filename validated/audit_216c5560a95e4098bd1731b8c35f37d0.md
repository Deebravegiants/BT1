Audit Report

## Title
PSM permanently DoS's mint/redeem for an external asset if its live decimals metadata changes after registration - (File: `substrate/frame/psm/src/lib.rs`)

## Summary
`pallet-psm` snapshots an external asset's `decimals` into `ExternalAssetInfo::decimals` at `add_external_asset` time, and the internal asset's decimals into `PsmInfo::internal_decimals` at PSM creation time. Every mint/redeem path calls `ensure_decimals_match`, which requires strict equality between these frozen snapshots and the *live* decimals reported by `T::Fungibles::decimals(...)`, an authority controlled entirely by `pallet-assets`' asset `Owner`/`Issuer` (or `Root`), independent of the PSM's own admin roles.

## Finding Description
The `ExternalAssetInfo` struct stores a decimals snapshot taken once, at registration: [1](#0-0) 

`PsmInfo` similarly stores `internal_decimals`, a snapshot from creation time: [2](#0-1) 

Every conversion path calls `ensure_decimals_match`, which compares the live decimals (via `T::Fungibles::decimals`) to the stored snapshots and hard-fails with `Error::DecimalsMismatch` on any divergence — the check exists in the pallet as described in the claim, verified against the corresponding struct/config code in this repository. The metadata backing `T::Fungibles::decimals` (i.e., `pallet-assets` metadata) is mutable after asset creation via that asset's own `Owner`/`Issuer` team or `Root`, a completely different trust domain than the PSM instance's `full_admin`/`emergency_admin`, as verified in `ensure_psm_admin`: [3](#0-2) 

Because the snapshot is taken once and never refreshed, and because the equality check is a hard revert rather than a reconciliation, any decimals metadata update on the underlying asset (whether accidental, corrective, or malicious) by an authority the PSM has no control over permanently blocks all mint/redeem calls for that asset pair on that PSM instance. There is no cross-pallet hook syncing the snapshot to the live value, and no PSM-side path to refresh the cached decimals other than removing and re-adding the asset — which itself requires debt to be zero, a state that may be unreachable if redemptions (the mechanism to drain debt) are also blocked by the very same check.

## Impact Explanation
This is a legitimate logic flaw: the pallet's strict-equality invariant between a point-in-time snapshot and a live, externally-mutable value creates an unsynchronized-state DoS. Once triggered, all `mint`/`redeem` operations for the affected `(internal_asset, external_asset)` pair permanently fail with `DecimalsMismatch`, and if `PsmDebt` is nonzero at the time of the metadata change, the instance can become unrecoverable through normal user-facing paths (mint/redeem blocked, and `remove_external_asset` blocked by nonzero debt). This is a real denial-of-service of core economic functionality for an in-scope pallet.

## Likelihood Explanation
The trigger requires only a legitimate, foreseeable, and independent administrative action: the specific external asset's `Owner`/`Issuer` (or `Root`) calling `set_metadata`/`force_set_metadata` to change `decimals`, an action entirely outside the PSM's own admin's control or visibility. No compromise of the PSM's own privileged roles is needed — the exploit crosses a trust boundary between two independently-administered pallets (`pallet-assets` asset team vs. PSM instance admin), which is a realistic and repeatable operational scenario, not a contrived or privileged-only path.

## Recommendation
- Avoid hard-reverting on live-vs-snapshot decimals mismatch; either recompute conversions using live decimals directly (removing the need for a snapshot/equality check), or
- Provide a way (permissionless or PSM-admin-gated) to refresh the stored decimals snapshot when a live mismatch is detected, unblocking mint/redeem, or
- Track PSM debt/reserve amounts in a decimals-agnostic unit so that a later metadata change cannot invalidate outstanding balances.
- Ensure `remove_external_asset` (or an emergency variant) remains callable even when `ensure_decimals_match` would fail, so an asset pair is never left simultaneously untradeable and unremovable.

## Proof of Concept
1. Asset team creates external asset `USDC` with `decimals = 6` in `pallet-assets`.
2. PSM full-admin calls `add_external_asset(internal_asset, USDC)`; `ExternalAssetInfo.decimals = 6` is stored.
3. Users mint/redeem normally while live decimals (6) match the snapshot (6).
4. `USDC`'s asset `Owner`/`Issuer` (or `Root`) calls `pallet_assets::set_metadata`/`force_set_metadata`, changing `decimals` to `8`.
5. Any subsequent `mint`/`redeem` call on `(internal_asset, USDC)` fails `ensure_decimals_match` with `Error::DecimalsMismatch`, permanently, for all users on that PSM instance, until the asset is removed (blocked if `PsmDebt` remains nonzero) and re-added.

		pub(crate) fn ensure_psm_admin(
			origin: OriginFor<T>,
			internal_asset: &T::AssetId,
			required: impl Fn(PsmManagerLevel) -> bool,
		) -> DispatchResult {
			let admin = PsmAdmin::<T>::get(internal_asset).ok_or(Error::<T>::PsmNotFound)?;
			let caller = <T as Config>::RuntimeOrigin::from(origin).into_caller();
			let level = if caller == admin.full_admin {
				PsmManagerLevel::Full
			} else if caller == admin.emergency_admin {
				PsmManagerLevel::Emergency
			} else {
				return Err(DispatchError::BadOrigin);
			};
			ensure!(required(level), Error::<T>::InsufficientPrivilege);
			Ok(())
		}
