### Title
Webhook `shop`, `topic`, and `webhook_id` are trusted from unauthenticated HTTP headers while the HMAC only covers the raw body, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, `api_version`, and `webhook_id` as plain HTTP header reads, but `to_signable_string` — the value that `Utils::HmacValidator` actually verifies — is defined as only the raw request body. [1](#0-0)  This breaks the identity binding `HMAC(shop, topic, webhook_id, body) == received_hmac`; in reality the gem only checks `HMAC(body) == received_hmac`, so the `shop-domain`/`topic`/`webhook-id` headers can be swapped freely without invalidating the signature.

### Finding Description
`Registry.process` relies solely on `Utils::HmacValidator.validate(request)` to authenticate an inbound webhook, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` handed to the app's handler: [2](#0-1) 

`HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`: [3](#0-2) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — it never mixes in `shop`, `topic`, or `webhook_id`: [4](#0-3) 

Crucially, the `api_secret_key` used to compute this HMAC is the **app's single client secret**, shared across every merchant shop that has installed the app — it is not a per-shop key. Consequently, any unprivileged user who owns a shop that has installed the app can:
1. Trigger a legitimate webhook delivery to their own shop's endpoint (attacker fully controls their own shop's data, e.g. product/customer/order content), capturing a valid `(raw_body, hmac)` pair signed with the app's shared secret.
2. Replay that exact `raw_body` and `hmac` to the same webhook endpoint, but with the `shopify-shop-domain` header rewritten to a victim shop that also uses the app (and optionally alter `shopify-topic`/`shopify-webhook-id`, since these are equally unauthenticated).
3. `HmacValidator.validate` still succeeds because the signature only ever covered `raw_body`, which was not modified.
4. `Registry.process` dispatches the handler with `WebhookMetadata` claiming `shop: "victim-shop.myshopify.com"`, `topic`, and `webhook_id` chosen by the attacker.

This is the analog of the M-4 report's "field acted on but not covered by the signature check" pattern: the router trusted the nominal transferred amount instead of the value actually verified; here the app trusts the header-derived `shop`/`topic` instead of the value actually covered by the HMAC.

### Impact Explanation
Any application built on this gem that keys per-tenant logic (data writes, entitlements, order/customer/inventory sync, etc.) off `WebhookMetadata#shop` is exposed to cross-tenant data injection: an attacker-controlled payload (from their own installed shop) can be attributed to an arbitrary victim shop that also installed the same app, with a validly-passing HMAC check. This satisfies the "Critical – cross-tenant access" impact bar, since a request from tenant A ends up acting on tenant B's data/records inside the host application, solely by manipulating unauthenticated headers.

### Likelihood Explanation
Likelihood is realistic though it requires the attacker to be a legitimate (even free-tier) installer of the vulnerable app on their own shop — no privileged credentials, access tokens, or `client_secret` access are needed. Triggering webhooks on one's own store (e.g., creating orders/products/customers) is a normal, unprivileged action available to any merchant, and replaying the captured `raw_body`+`hmac` with a modified `shop-domain` header is trivial once the header/signature scope mismatch is understood.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the value that is HMAC-verified (or otherwise cryptographically pin them), for example by having `Webhooks::Request#to_signable_string` combine the raw body with the shop/topic/webhook-id headers, and reject the request if those headers are altered relative to what was authenticated. At minimum, `Registry.process` should not trust `request.shop` for cross-tenant dispatch decisions unless it has been independently corroborated (e.g., against the app's own record of shops with active installs, and unless the value is included in what is actually verified).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (unprivileged, self-service).
2. Attacker triggers a real webhook (e.g., `products/create`) on their own shop, capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent — this HMAC is valid because it's signed with the app's shared `client_secret`.
3. Attacker resends the identical raw body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and, if desired, a different `X-Shopify-Topic`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC. [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: attacker_body, ...)`, causing the host application to process attacker-supplied data under the victim's tenant identity. [6](#0-5)
