## Analysis Result

### Title
Webhook shop/topic identity spoofing via unauthenticated headers not covered by HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body, but then trusts the `shop` and `topic` values taken from unauthenticated HTTP headers to route the payload to a handler and to build the `WebhookMetadata` that identifies which merchant the payload belongs to. Because these header values are never part of the signed material, the binding "bytes verified" == "tenant/topic acted on" is broken.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` and `topic` accessors instead read directly from the `x-shopify-shop-domain` / `x-shopify-topic` headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the signature using exactly `verifiable_query.to_signable_string` (i.e. the raw body only) against the app's shared `client_secret`: [3](#0-2) 

`Registry.process` uses this validation, then dispatches purely off the unauthenticated `request.topic` header and hands `request.shop` (also unauthenticated) into `WebhookMetadata` as the tenant identifier for the handler: [4](#0-3) 

All shops that install a given app share the same `client_secret`, so the HMAC only proves "this body was signed by *some* installation of this app," not "this body came from shop X performing topic Y." An unprivileged actor who legitimately installs the app on their own shop can obtain a validly-signed webhook body (e.g. by triggering `orders/create` on their own store), then replay that same raw body to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain (and/or the `x-shopify-topic` header changed). `Utils::HmacValidator.validate` still succeeds because it only checks the untouched raw body, and `Registry.process` will invoke the handler for the victim's tenant with attacker-controlled shop attribution.

Equality that should hold but doesn't: `shop-that-produced-the-signed-body == shop attributed in WebhookMetadata`. The gem only proves the second is *a* valid signer, not that it equals the header-derived value acted upon.

### Impact Explanation
This allows cross-tenant confusion in any application whose webhook handlers key business logic (e.g., data sync, entitlement changes, GDPR redaction processing) off `WebhookMetadata#shop`/`#topic` without independently re-validating them. An attacker with only their own (unprivileged) shop installation can cause the app to process events as if they originated from — or target — a different shop id of the attacker's choosing, and can also relabel the `topic`, causing the payload to be dispatched to the wrong handler (e.g., feeding an `orders/create` body into a `shop/redact` handler or vice versa). This matches the "cross-tenant access" High-impact category.

### Likelihood Explanation
Likelihood is realistic but requires the attacker to have their own valid installation of the target app (an unprivileged, normal merchant relationship, not a privileged internal actor) and network-level ability to POST directly to the app's webhook endpoint with forged headers — both readily available to any internet user who signs up for the app. No knowledge of `api_secret_key` or any credential is needed since the attacker replays a body that Shopify already signed for them.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or otherwise cryptographically bind them) into the HMAC-signable string in `ShopifyAPI::Webhooks::Request#to_signable_string`, or require the caller/host app to only trust `request.shop`/`request.topic` after confirming they match values obtained independently (e.g., from Shopify's IP allowlist and TLS, or from a per-shop secret) rather than solely from HTTP headers accompanying a body-only HMAC.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a real webhook (e.g. `orders/create`), capturing the exact `raw_body` and valid `x-shopify-hmac-sha256` header Shopify sent.
2. Attacker POSTs the identical `raw_body` and `hmac-sha256` header to the app's webhook endpoint, but with `x-shopify-shop-domain: victim.myshopify.com` (and optionally a different `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` (per `to_signable_string`) — this still matches since the body/HMAC pair is untouched.
4. `WebhookMetadata` is built with `shop: "victim.myshopify.com"` and the handler for the (possibly attacker-chosen) topic is invoked, processing attacker-supplied data under the victim shop's identity.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
