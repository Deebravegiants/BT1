Based on my review, I found a concrete identity-binding gap in the webhook processing path.### Title
Webhook `shop` (tenant) identifier is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies the authenticity of an inbound webhook using an HMAC that is computed **only over the raw request body**, while the `shop` (tenant identity) used by webhook handlers is read from an HTTP header that is never included in the signed material.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates the HMAC (over the body only) and then trusts `request.shop`, `request.topic`, and `request.webhook_id` — all header-derived, unsigned fields — when dispatching to the app's handler: [3](#0-2) 

The identity binding the design implicitly assumes is:
`shop authenticated by HMAC == shop the handler acts on`

But because the HMAC is computed only over `raw_body`, this equality does not hold: `hmac` proves "this body was signed with `api_secret_key`" but proves nothing about which header values (topic, shop-domain, webhook-id, api-version) accompanied it. Any of these headers can be swapped after a legitimate webhook delivery (or crafted by anyone who owns a store where the app is installed and can trigger a webhook with attacker-chosen body content) while keeping the same valid `hmac-sha256` value, since the signature never covered them.

### Impact Explanation
A merchant/attacker who controls one shop where the app is installed can capture a legitimate webhook delivery (valid HMAC over a body they control, since the webhook fires for events on their own store) and replay it to the app's webhook endpoint with the `shopify-shop-domain` header changed to a victim shop's domain. `Utils::HmacValidator.validate` will still pass because it only checks the body signature, and `Registry.process` will hand the handler a `WebhookMetadata`/equivalent record claiming `shop: <victim shop>` with attacker-controlled body content. Any app logic that uses `request.shop` to scope writes, cache invalidation, redaction, or other tenant-specific side effects will act on the wrong tenant — a cross-tenant data integrity/confusion issue. This satisfies the "cross-tenant access" impact class.

### Likelihood Explanation
Requires only: (1) the app is installed on an attacker-controlled shop (no privileged credentials or leaked secrets needed — a free/dev store suffices), and (2) the ability to replay an HTTP POST to the app's public webhook endpoint with modified headers, which is trivial for anyone who can trigger a webhook and capture it. No access to `api_secret_key`, access tokens, or the target shop's own credentials is required.

### Recommendation
Include the tenant-identifying and routing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or otherwise cryptographically bind them to the body (e.g., verify `shop-domain` against records already associated with the webhook subscription in the app's own store, and reject if it doesn't match what was registered for that `webhook_id`). At minimum, document that consumers of `Webhooks::Request` must not trust `request.shop`/`request.topic` for tenant-security decisions unless independently corroborated, and consider extending `to_signable_string` (or the HMAC validation step in `Registry.process`) to bind the header values used for dispatch.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger any registered webhook topic (e.g., `orders/create`) with a body the attacker fully controls.
2. Capture the resulting POST request, which includes a valid `x-shopify-hmac-sha256` computed only from the raw body via `Digest.hexencode(Base64.decode64(...))` matching `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`).
3. Replay this exact body + HMAC to the app's webhook endpoint, but replace the `x-shopify-shop-domain` header value with `victim.myshopify.com`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) calls `Utils::HmacValidator.validate(request)` — which still returns `true` (only the body was signed) — then invokes the handler with `shop: request.shop` set to `victim.myshopify.com`, even though Shopify never sent this event for that shop.
