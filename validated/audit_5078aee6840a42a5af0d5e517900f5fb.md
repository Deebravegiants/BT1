### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC signature Shopify sends only authenticates the JSON body bytes. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values are read straight from HTTP headers, which are never included in the signed content, yet `Registry.process` trusts `request.shop` as the tenant identity passed to the app's handler.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received HMAC: [5](#0-4) 

For `Webhooks::Request`, `to_signable_string` is defined as just the raw body: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all sourced from headers and are not part of that signable string: [6](#0-5) 

`Registry.process` validates only the HMAC of the body, then forwards `request.shop` (the unauthenticated header) directly to the app's webhook handler as the tenant identity: [7](#0-6) 

The identity binding that should hold is: `shop header == shop whose secret produced the HMAC`. Because the HMAC is computed only over the body, that equality is never checked — an attacker who intercepts or replays a legitimate webhook body+HMAC pair (e.g., from their own shop, or a captured/leaked webhook payload) can resubmit it with an arbitrary `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header naming a *different* shop. `HmacValidator.validate` still passes (the body signature is unaffected by header changes), and `Registry.process` calls the app's handler with `WebhookMetadata.shop` set to attacker-chosen victim shop domain instead of the shop that actually holds the secret/produced the payload.

### Impact Explanation
This breaks the tenant boundary the gem is documented to enforce for webhook processing: an app relying on `ShopifyAPI::Webhooks::Request#shop` (via `WebhookMetadata#shop`) to determine which merchant's data a webhook body belongs to can be made to attribute another shop's actions/data to a victim shop, or vice versa — effectively cross-tenant data confusion driven purely by an HTTP header the attacker controls. Any downstream logic that keys off `data.shop` (e.g., looking up that shop's session/access token, updating that shop's records) processes attacker-chosen body content under a victim's tenant identity, which satisfies the "cross-tenant access" bar.

### Likelihood Explanation
Exploitation requires only capturing/replaying one valid webhook HMAC+body pair (which the attacker can trivially generate for their own shop by triggering any webhook event, e.g., `orders/create`) and resending it with a different `shop-domain` header value to the app's webhook endpoint — no access token, `client_secret`, or privileged account is needed. This is an unauthenticated network request from any internet user who can reach the app's public webhook callback URL.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook_id`, `api_version`) header values in the signed content that is verified, or otherwise cryptographically bind them to the HMAC — e.g., have `to_signable_string` incorporate the shop domain alongside the raw body, matching the pattern already used for `Oauth::AuthQuery#to_signable_string`, which signs all fields that are later trusted.

### Proof of Concept
1. Attacker owns `attacker-shop.myshopify.com`, installed on the target app, and configured with a real webhook subscription (e.g., `orders/create`).
2. Attacker triggers an order creation, causing Shopify to POST a legitimately-HMAC-signed webhook to the app's endpoint with headers:
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - `X-Shopify-Hmac-Sha256: <valid HMAC of body>`
   - `X-Shopify-Topic: orders/create`
3. Attacker captures this raw body + HMAC pair (trivial since it's their own webhook, no secrets needed).
4. Attacker resends the identical body and HMAC header to the app's public webhook endpoint, but replaces the header with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate(request)` succeeds because it only checks `Digest.hexencode(...)` against `to_signable_string == @raw_body`, which is unchanged.
6. `Registry.process` calls the registered handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker's order body>, ...)`, causing the app to process attacker-controlled data under the victim shop's tenant context.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
