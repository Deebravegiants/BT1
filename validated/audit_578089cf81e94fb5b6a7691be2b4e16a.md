### Title
Stale `ContractToAsset`/`TokenContracts` mapping resolution in `on_timeout`/`on_accept` permanently freezes or misdirects escrowed/burned funds after `update_token` - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token` mirrors the SetToken bug class: a value is locked in at "issuance" time (here, `send()` escrows or burns the local asset and dispatches an ISMP Post whose only durable, on-chain-verifiable link back to an asset is the raw EVM contract address bytes), but resolution of that value at settlement time (`on_timeout`/`on_accept`) is performed against the *current, mutable* `TokenContracts`/`ContractToAsset` storage rather than against a snapshot taken at dispatch time. Because governance's `update_token` can change or remove that mapping at any time — including while a `send()` request is still in flight — the funds locked by that in-flight request can become permanently unresolvable (frozen) or resolved against the wrong asset (misdirected mint), exactly as MaliciousToken's address migration orphaned Alice's SetToken balance in the original report.

### Finding Description
`send()` in [1](#0-0)  escrows (native) or burns (non-native) the caller's local balance, then dispatches a `DispatchPost` whose destination `to` field is `TokenContracts::<T>::get(params.destination, params.asset_id)` — i.e. the current EVM contract address for that asset, looked up once at send time.

Settlement of that same request happens later, driven by `pallet-ismp` calling `on_timeout` (or the counterpart calling `on_accept`) with only the raw request/response bytes (`to`, `from`, `dest`/`source`, `body`). The module re-derives which local asset the request belongs to by looking up the *live* reverse mapping: [2](#0-1) 

and analogously in `on_accept`: [3](#0-2) 

The mapping being dereferenced (`ContractToAsset`, `TokenContracts`, `Precisions`, `NativeAssets`) is fully mutable by `T::CreateOrigin` at any time via `update_token`, with no check for in-flight requests and no per-request snapshot of the asset/decimals/custody-model that were valid at `send()` time: [4](#0-3) 

Two concrete failure modes:

1. **Removal (`remove_chains`)**: once a chain's `TokenContracts`/`ContractToAsset` entry is removed, any Post request already dispatched for the old mapping cannot be resolved when it times out — `ContractToAsset::<T>::get(dest, &to)` returns `None`, and `on_timeout` returns `Err(HftError::UnknownContractOnTimeout)`. The ISMP timeout call for that specific commitment then can never succeed, so the escrowed/burned balance from the original `send()` is **permanently unrecoverable** — the direct analog of "Alice can no longer access her SetToken" once Bob's address migration orphans the original address.

2. **Reassignment (`add_chains` with a reused contract address, or a contract address later reused for a different `local_id`)**: `register_token`/`update_token` place no uniqueness constraint preventing the same EVM contract address bytes from later being associated (for a different `asset_id`) via a subsequent `update_token`/`register_token` call. If this happens while an older request referencing that same address is still in flight, `on_timeout`/`on_accept` will resolve `local_asset_id` to the **new** asset, and mint/transfer/refund using that asset's `Precisions`, `NativeAssets` custody flag and decimals — crediting or minting the wrong asset relative to what was actually escrowed/burned at `send()` time.

### Impact Explanation
Case 1 is a permanent freezing of user funds: assets locked in the pallet's custody account (native case) or already burned (non-native case) at `send()` time become unreachable once the chain-level mapping is deleted, with no path in the module to recover them (no admin re-mint/unlock function keyed by stale commitments). Case 2 allows the pallet to mint/release an asset the user never actually escrowed/burned in that amount, which is an unbacked-mint / asset-confusion condition on the settlement side of the bridge. Both are within the "token bridge mint/burn" analog class and constitute concrete freezing of funds or unauthorized mint, matching High-severity impact criteria.

### Likelihood Explanation
Triggering requires only ordinary, expected pallet operation: a user's normal `send()` (unprivileged, one transaction) combined with a routine `update_token` maintenance/migration call by `CreateOrigin` (which is an expected, non-malicious lifecycle operation — token contract redeployments/migrations are exactly the scenario `update_token` exists to support) occurring while that request is still pending settlement (timeout window is attacker/relayer-influenced via `params.timeout`, and cross-chain finality delay is often minutes-to-hours). Any unprivileged relayer can then submit the timeout/accept message that hits the now-stale mapping. No malicious governance action is required — only a normal token migration racing an in-flight, unprivileged user transaction — so likelihood is realistic during any planned contract migration.

### Recommendation
Snapshot the resolved `local_asset_id`, its custody flag (`NativeAssets`), `Precisions` entry, and decimals into the request's encoded `Message`/commitment state at `send()` time (or into pallet storage keyed by the request commitment), and have `on_accept`/`on_timeout` resolve settlement against that snapshot rather than the live `TokenContracts`/`ContractToAsset` maps. Additionally, `register_token`/`update_token` should reject re-mapping an EVM contract address to a different `asset_id` while any commitments referencing the old mapping are still outstanding, or provide an explicit migration/claim path keyed by commitment hash so orphaned escrowed/burned balances remain recoverable after a mapping change.

### Proof of Concept
1. Governance registers asset `A` with `register_token`, mapping `(StateMachine::Evm(1), A) -> contract_addr = 0xAAA...`.
2. Alice calls `send()` for asset `A` to `StateMachine::Evm(1)`; the pallet burns/escrows her `A` balance and dispatches a `DispatchPost` with `to = 0xAAA...` and a long `timeout`.
3. Before the request is delivered/timed out, governance calls `update_token` and either (a) removes chain `Evm(1)` for asset `A` via `remove_chains`, or (b) re-registers `0xAAA...` under a different asset `B` (e.g. via a fresh `register_token`/`update_token` call for `B`'s `add_chains` on `Evm(1)`), see [5](#0-4) .
4. The request eventually times out and `pallet-ismp` invokes `on_timeout`, calling `ContractToAsset::<T>::get(dest, &to)` [6](#0-5) :
   - In case (a), this returns `None`, the timeout handler errors, and Alice's originally burned/escrowed `A` balance is never refunded — permanently frozen.
   - In case (b), this resolves to asset `B`, and `on_timeout` mints/refunds asset `B` (using `B`'s decimals/custody flag) instead of asset `A` — asset confusion / unbacked mint of `B`.

			>,
		) -> DispatchResult {

			let token_contract =

					.ok_or(Error::<T>::TokenContractNotFound)?;

				.ok_or(Error::<T>::DecimalsNotFound)?;

			// Lock or burn the local asset
			let decimals = if params.asset_id == T::NativeAssetId::get() {

					params.amount,
					ExistenceRequirement::AllowDeath,

			} else {

				} else {

						params.asset_id.clone(),
						&who,
						params.amount.into(),
						Preservation::Expendable,
						Precision::Exact,
						Fortitude::Polite,
					)?;
				}

		pub fn update_token(
			origin: OriginFor<T>,
			update: TokenUpdate<AssetId<T>>,
		) -> DispatchResult {
			T::CreateOrigin::ensure_origin(origin)?;

			let local_decimals = if update.asset_id == T::NativeAssetId::get() {
				T::Decimals::get()
			} else {
				<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(
					update.asset_id.clone(),
				)
			};

			for (chain, config) in update.add_chains {
				// This pallet bridges substrate <-> EVM only; reject non-EVM peers.
				if !matches!(chain, StateMachine::Evm(_)) {
					return Err(Error::<T>::NonEvmPeerChain.into());
				}
				ensure!(
					config.decimals >= local_decimals,
					Error::<T>::ErcDecimalsBelowLocal
				);
				// Remove old reverse mapping if it exists
				if let Some(old_contract) = TokenContracts::<T>::get(chain, update.asset_id.clone())
				{
					ContractToAsset::<T>::remove(chain, old_contract);
				}

				let token_contract = config.token_contract.0.to_vec();
				TokenContracts::<T>::insert(
					chain,
					update.asset_id.clone(),
					token_contract.clone(),
				);
				ContractToAsset::<T>::insert(chain, token_contract, update.asset_id.clone());
				Precisions::<T>::insert(update.asset_id.clone(), chain, config.decimals);
			}

			for chain in update.remove_chains {
				if let Some(old_contract) = TokenContracts::<T>::get(chain, update.asset_id.clone())
				{
					ContractToAsset::<T>::remove(chain, old_contract);
				}
				TokenContracts::<T>::remove(chain, update.asset_id.clone());
				Precisions::<T>::remove(update.asset_id.clone(), chain);
			}
