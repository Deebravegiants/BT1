### Title
Unbounded Message Batching in `pallet-ismp::handle_unsigned` Allows Free-Cost Resource Exhaustion via Validate-Unsigned - (File: `modules/pallets/ismp/src/lib.rs`)

### Summary
`pallet_ismp::Call::handle_unsigned` accepts an unbounded `Vec<Message>` and is dispatched as an **unsigned** extrinsic (no fee, no signature, callable by anyone). The `ValidateUnsigned::validate_unsigned` implementation for this pallet unconditionally calls `Self::execute(messages.clone())` — which runs full cryptographic proof verification (state-machine consensus checks, MMR/child-trie membership/non-membership proofs) for **every message in the batch** — during transaction-pool validation, before any block-weight accounting applies. This mirrors the Saleor GraphQL batching flaw: an unbounded array of operations submitted in one request bypasses the normal per-operation resource/fee gate.

### Finding Description
`handle_unsigned` is defined with no cap on batch size: [1](#0-0) 

The pallet's `ValidateUnsigned::validate_unsigned` runs `Self::execute(messages.clone())` directly against attacker-supplied, arbitrarily large `messages: Vec<Message>` before the extrinsic is weighed or fee-checked, and this same execution happens again during `pre_dispatch`/on-chain apply: [2](#0-1) 

`execute` iterates the full message vector and, per message, invokes `handle_incoming_message`, which performs full state-machine/consensus validation and cryptographic membership-proof verification (MMR proofs, trie proofs) for each entry: [3](#0-2) 

Documentation confirms the pallet intends unsigned messages to be "executed for free" and relies on transaction-pool validity checks alone (not weight/fee limits) to prevent spam: [4](#0-3) 

Because `Vec<Message>` carries no `BoundedVec`/max-length constraint at the type level, and the per-call `weight()` function (used for `#[pallet::weight(weight())]`) is a static/pre-declared weight rather than one computed from `messages.len()` (no evidence found of per-message weight scaling in the searched code), a single unsigned extrinsic can smuggle a very large number of `Message` entries (requests, responses, timeouts, consensus updates) each carrying its own merkle/state proof. Every node that receives this transaction over the network must run `validate_unsigned` — i.e., perform full proof verification for the entire batch — for free, before the transaction is even included in a block, exactly analogous to Saleor evaluating every batched GraphQL operation before batch-size limits could apply.

### Impact Explanation
An unauthenticated party (anyone can submit unsigned extrinsics) can submit a single `handle_unsigned` call containing a huge number of proof-bearing messages. Every honest full node in the network performs expensive cryptographic verification (MMR/trie membership proofs, per-message state-machine checks) on the entire batch during pool validation — for free and with no signer to penalize/slash — repeatedly, as the transaction propagates and is re-validated by each peer. This can exhaust CPU on relayer/validator nodes network-wide, delaying block production and legitimate message delivery (a "route unable to deliver messages" condition), which is the class of impact this scan is scoped to accept.

### Likelihood Explanation
Medium-High. The call is explicitly permissionless and free by design (`ensure_none(origin)`), requiring no stake, fee, or prior relationship. The only current gate is that each individual message's proof must be *valid* (proofs must actually verify) or the extrinsic is rejected as invalid — but there is no evidence of any bound on `messages.len()` before the expensive per-message verification loop runs. An attacker with access to legitimately valid (or replayed/already-processed-but-differently-shaped) proofs for many messages could construct a single oversized batch; even a batch that ultimately fails on one bad message still forces full computation on all prior entries in the iterator before failing (the `.map(...).collect::<Result<_,_>>()` pattern in `execute` stops at first error, but an attacker who can supply many *valid* proofs, e.g. from public request/response streams, pays no cost to force full verification across the whole set repeatedly across the p2p network).

### Recommendation
- Introduce a strict, low `MaxMessagesPerBatch` bound (e.g., a `BoundedVec<Message, MaxMessages>` or an explicit `ensure!(messages.len() <= T::MaxMessages::get())` check) enforced in `validate_unsigned` *before* any proof verification runs.
- Reject unsigned extrinsics failing this check with a cheap early `InvalidTransaction` variant so oversized batches are dropped before expensive cryptographic work.
- Alternatively/additionally make declared weight for `handle_unsigned` scale with `messages.len()` so weight-based block limits actually bound the batch size, and consider a lightweight per-message pre-check (e.g. hash/format sanity) prior to full proof verification in the validation path.

### Proof of Concept
1. Craft an unsigned extrinsic `Ismp::handle_unsigned(messages)` where `messages` is a `Vec<Message>` containing, e.g., thousands of `Message::Request(RequestMessage)` entries, each with a (possibly minimal/valid) membership proof.
2. Submit this extrinsic via RPC to a node (as done in the test harness pattern used elsewhere in the codebase): [5](#0-4) 
3. Every peer node receiving/propagating the transaction runs `ValidateUnsigned::validate_unsigned`, which calls `Self::execute(messages.clone())`, forcing full proof verification over the entire (attacker-sized) batch — for free — before any block inclusion or weight charge occurs: [2](#0-1) 
4. Repeating this from multiple sources / re-broadcasting amplifies CPU load network-wide with no economic cost to the attacker.

**Caveat / uncertainty:** I could not locate the exact implementation of the `weight()` helper function referenced by `#[pallet::weight(weight())]` in `modules/pallets/ismp/src/lib.rs` (it appears to be defined elsewhere or as a constant/closure not captured by the index), so I cannot confirm with certainty whether it already scales with `messages.len()` in a way that would fully mitigate this — if it does scale correctly per message, the block-inclusion weight limit would bound batch size, though the free `validate_unsigned` pass would still run before that weight check is meaningfully enforced (validation happens prior to inclusion). A Devin session with full repo access should verify the `weight()` function definition directly to confirm or rule out this analog with certainty.

```rust
	pub fn execute(messages: Vec<Message>) -> Result<Vec<events::Event>, Error<T>> {
		let host = Pallet::<T>::default();

		let message_results = messages
			.iter()
			.map(|msg| handle_incoming_message(&host, msg.clone()))
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;
```

```text
## Transaction fees

Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free as unsigned transactions. The upside to this is that it cannot be exploited as a spam vector, since the transaction pool will check if the submitted extrinsics are valid before they are included in the pool. This validity check ensures that the transaction can be successfully executed and contains valid proofs. Malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing and potential network congestion.
```
