Confirmed: `freeze_authority` appears only once in `processor.rs`, in the check on `lp_mint` at `process_initialize2` — there is no equivalent check on `coin_mint`/`pc_mint`.

### Title
Missing freeze_authority validation on coin/pc mints allows permanent, program-wide freezing of pool vaults - (File: `program/src/processor.rs`)

### Summary
`process_initialize2` validates that the LP mint has no `freeze_authority` set, but performs no such check on the user-supplied `amm_coin_mint_info`/`amm_pc_mint_info`. Any pool creator can therefore initialize a pool whose underlying coin or pc token is a mint they control with an active `freeze_authority`. After other users deposit or swap into that pool's shared vault account, the pool creator can freeze the vault token account via the SPL Token program's `FreezeAccount` instruction, which permanently DoSes every subsequent instruction that must transfer into/out of that vault.

### Finding Description
`process_initialize2` unpacks and validates the coin/pc mints via `unpack_mint`, but only checks `lp_mint.freeze_authority.is_some()` and rejects it; it never checks the freeze authority of `coin_mint`/`pc_mint`: [1](#0-0) [2](#0-1) 

The `amm_coin_vault`/`amm_pc_vault` are single, fixed-address token accounts shared by all depositors and swappers of the pool, created and owned by the AMM `$authority` PDA: [3](#0-2) 

Every core instruction — Deposit, Withdraw, SwapBaseIn, SwapBaseOut, and WithdrawPnl — performs SPL token transfers directly against these shared vault accounts via `Invokers::token_transfer`/`token_transfer_with_authority`: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

If the coin or pc mint's `freeze_authority` is set (which the program never rejects), the mint's freeze authority (i.e., the malicious pool creator, since they chose/control the mint) can call the SPL Token `FreezeAccount` instruction against the vault. Once the vault token account is frozen, any SPL token instruction referencing it as source or destination returns an error, causing every `invoke_signed` call in `Invokers::token_transfer`/`token_transfer_with_authority` touching that vault to fail, and the entire encompassing Raydium instruction to revert. This is directly analogous to the USDC pause/blacklist scenario in the referenced report: an external token-level restriction on a critical account makes the AMM's core functions permanently revert.

### Impact Explanation
Because the coin/pc vault accounts are shared by all LPs and swappers of the pool (not per-user accounts like the LP mint's ATAs), freezing the vault after liquidity has been deposited permanently locks in all depositors' pooled funds for that pool — Deposit, Withdraw, both swap directions, and WithdrawPnl all revert forever for the affected pool. This is a permanent freezing of user/LP funds, satisfying the High severity bar.

### Likelihood Explanation
This is reachable by any unprivileged actor acting purely as a pool creator through a single `Initialize2` transaction with a self-controlled, attacker-chosen mint (setting `freeze_authority` to themselves is a completely standard, default SPL Token mint feature, not a modified/malicious token program). No privileged signer or off-chain access is required — the attacker only needs to be the mint's freeze authority, which they control by construction, and to wait until legitimate users deposit/swap before freezing the vault.

### Recommendation
In `process_initialize2`, validate that `coin_mint.freeze_authority` and `pc_mint.freeze_authority` are both `None` (`COption::None`), mirroring the existing check already performed on `lp_mint.freeze_authority`, before allowing pool creation to proceed.

### Proof of Concept
1. Attacker creates a new SPL mint `M` with `freeze_authority = Some(attacker)` and mints itself initial supply.
2. Attacker calls `Initialize2` using `M` as `amm_coin_mint` (or `amm_pc_mint`), passing the standard account set; the program does not reject this because it only checks `lp_mint.freeze_authority`, per `process_initialize2` at lines 897-906.
3. Legitimate LPs call `Deposit`, and/or swappers call `SwapBaseIn`/`SwapBaseOut`, transferring `M`-denominated tokens into the shared `amm_coin_vault` (or `amm_pc_vault`).
4. Attacker, as `freeze_authority` of `M`, submits an SPL Token `FreezeAccount` instruction against `amm_coin_vault_info.key`.
5. Any subsequent `Deposit`, `Withdraw`, `SwapBaseIn`, `SwapBaseOut`, or `WithdrawPnl` instruction that transfers into/out of the frozen vault fails at the SPL Token program level, causing the whole Raydium instruction to revert, permanently freezing all previously deposited coin/pc funds in that pool.
