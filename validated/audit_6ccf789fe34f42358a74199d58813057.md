### Title
`_withdraw` finalizes an order and releases the "redeem/refund" fee event even when no escrow tokens are actually transferred - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw` is the shared settlement path for both `RedeemEscrow` and `RefundEscrow` cross-chain messages (and the same-chain fill/cancel paths). When `finalize` is true it unconditionally marks the order filled (`_filled[body.commitment] = beneficiary`) and, if `body.tokens` is empty (or every entry has `amount == 0`), the token-release loop never executes any transfer, yet the function still proceeds to emit `EscrowReleased`/`EscrowRefunded` and pay out any accrued transaction fee — exactly the "operation succeeds/finalizes without doing the thing it claims to have done" pattern from the reported Liquity bug (a "redeem" that completes without any actual redemption).

### Finding Description
`_withdraw` is structured as: [1](#0-0) 

1. `if (finalize) _filled[body.commitment] = beneficiary;` runs first, unconditionally finalizing/permanently closing the order regardless of whether any tokens are actually released.
2. The loop `for (uint256 i; i < len; i++)` that performs the actual `_orders[...]` decrement and token transfer is skipped entirely when `body.tokens.length == 0`, and per-entry `if (amount == 0) continue;` skips any zero-amount entries individually.
3. There is no check anywhere in `_withdraw` that at least one non-zero token was actually released before finalizing and emitting `EscrowReleased`/`EscrowRefunded`.

Both cross-chain entry points construct `body.tokens` from data controlled by the on-chain fill/cancel logic on the *other* chain (`ExtrinsicIntents.sol`'s `_fillCrossChain`, `_cancelSameChain`, and the `RedeemEscrow`/`RefundEscrow` message handlers), and this data is length-checked against `order.inputs.length`, which is itself not enforced to be non-zero at `placeOrder` time in the code paths inspected. If an order is ever placed/relayed with zero inputs (or the derived `escrowedInputs` array collapses to zero live entries, e.g. all `amount == 0` after partial-fill accounting) the settlement message that arrives at `_withdraw` finalizes the order and emits the success event without moving any value — mirroring the reported class of bug (transaction "succeeds" and emits a completion event while no state-relevant work was performed), which can mislead downstream indexers/relayers/solvers that rely on `EscrowReleased`/`EscrowRefunded` as proof that value was actually delivered, and irreversibly closes the order (`_filled` is set) so a legitimate later redemption of any still-escrowed amount is permanently blocked.

### Impact Explanation
Because `_filled[commitment]` is set to non-zero unconditionally on `finalize=true`, once this path is hit the order can never be filled/refunded again (`Filled()` guards elsewhere check `_filled[commitment] != 0`). If real escrow (`_orders[commitment][token] > 0`) still exists on this chain for that commitment when a zero/empty-token `WithdrawalRequest` finalizes it, those funds become **permanently unreachable** — there is no other path in the contract that transfers `_orders[commitment][token]` balances once `_filled` is non-zero. This is a permanent freezing-of-funds condition, satisfying the required impact bar.

### Likelihood Explanation
The likelihood depends on whether an attacker/relayer can force `body.tokens` to be empty or all-zero while real escrow exists for the commitment. The escrow amounts released cross-chain are derived from `order.inputs` on the source chain; if `order.inputs.length == 0` is allowed at placement (not conclusively verified from the sections inspected) a user or malicious placer could place such an order for the sole purpose of demonstrating/triggering this no-op finalize, or a partial-fill accounting edge case (`amountFilled == totalRequired` branch computing `escrowedAmount` from `_orders[commitment][token]`, which could be zero if escrow was already fully drained by a prior partial release) could also produce a zero/empty-token withdrawal that still finalizes the order. Full confirmation requires checking `placeOrder`'s validation of `order.inputs.length` and all call sites that construct `WithdrawalRequest.tokens`, which I could not fully trace within the available search budget.

### Recommendation
In `_withdraw`, require that `finalize` only proceeds (setting `_filled` and emitting the completion event) if at least one non-zero token transfer actually occurred, or explicitly validate at `placeOrder`/message-construction time that `tokens.length > 0` and that all constituent amounts are non-zero when finalize is requested. Add a revert (e.g. `NoEscrowToRelease()`) analogous to the recommended Liquity fix, so a “redemption”/refund message that would move zero value cannot silently finalize and permanently lock any real escrow still associated with the commitment.

### Proof of Concept
Not independently exploitable end-to-end from the code inspected within the available tool budget — the finding is a structural code-path analog (empty/zero-amount `body.tokens` bypassing the transfer loop while still finalizing and emitting success) rather than a demonstrated exploit chain. Confirming full exploitability would require verifying (1) whether `placeOrder` permits `order.inputs.length == 0`, and (2) whether any partial-fill or cross-chain message-construction path can produce a `WithdrawalRequest` with `tokens.length == 0` or all-zero amounts while `_orders[commitment][token]` is still non-zero for that commitment — both of which were not fully traceable in this session and would need direct verification with full repository access (e.g., via a Devin session) before treating this as confirmed rather than a probable analog.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
