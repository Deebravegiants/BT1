### Title
Uncontrolled Resource Consumption via Unbounded, Statically-Weighted `handle_unsigned` Batches - (File: `modules/pallets/ismp/src/lib.rs`)

### Summary
`pallet_ismp::Pallet::handle_unsigned` is a free, unsigned, unprivileged extrinsic that accepts an unbounded `Vec<Message>` and is charged a single, fixed dispatch weight (`Weight::from_parts(300_000_000, 0)`) regardless of how many messages, requests, or how large the accompanying state/consensus proofs are [1](#0-0) . Because it is validated as an unsigned transaction, every full node in the network fully executes `Self::execute(messages.clone())` — including state/consensus proof verification — both at initial submission and on every re-validation while the transaction sits in the pool (`longevity: 25`) [2](#0-1) . This mirrors the Matrix Synapse bug class (CWE-400/772): work proportional to attacker-controlled, effectively unbounded input is performed before any cost-limiting check terminates it, and the "declared cost" (fixed weight here, the 30s timeout there) does not track the real resource consumption.

### Finding Description
`handle_unsigned` takes `messages: Vec<Message>` with no `BoundedVec`/`MaxMessages` constraint [3](#0-2) . Its declared weight is a flat constant used for every call site:

```rust
/// Static weights because these should get overridden by the FeeHandler
fn weight() -> Weight {
	Weight::from_parts(300_000_000, 0)
}
``` [4](#0-3) 

`#[pallet::weight(weight())]` is what `frame_system::CheckWeight` and the block builder use to admit/pack the extrinsic *before* it runs — it does not scale with `messages.len()`, the number of `PostRequest`/`GetRequest` entries inside each message, or the size of the membership/consensus proofs those messages carry. Nested collections such as `RequestMessage.requests: Vec<PostRequest>` and `GetRequest.keys: Vec<Vec<u8>>` are themselves unbounded (tests construct batches of 1000 requests, each with 256 keys, with no rejection at the type level) [5](#0-4) [6](#0-5) .

The `execute` path runs `handle_incoming_message` for every message, which for requests/responses performs full membership/non-membership state proof verification, and for consensus messages performs BEEFY/SP1/GRANDPA/BSC/etc. verification — all CPU/heap-bound by the caller-supplied proof size, not the fixed weight [7](#0-6) .

Crucially, because `handle_unsigned` is validated via `ValidateUnsigned::validate_unsigned`, the *entire batch is fully executed* (all proof verification, all MMR/BEEFY/SP1 checks) just to compute the transaction-pool tag, and this happens again on every block while the transaction remains valid (`longevity: 25`) [8](#0-7) . An attacker (any unprivileged party — no signature or fee required) can submit one or many such unsigned extrinsics with maximal-size proofs/message counts (bounded only by the outer block/extrinsic byte-length limit, not by weight), forcing every full node and collator to repeatedly perform this expensive verification for free, degrading block production and node availability network-wide — the same "attacker-controlled unbounded work with an unrelated fixed cost gate" pattern as CVE-2022-41952.

### Impact Explanation
This is a network-wide availability risk directly reachable from a single unsigned, unauthenticated submission (no signature, no fee) into `pallet-ismp`, which every relayer and collator must process and (during pool revalidation) repeatedly re-execute. Sustained abuse can degrade block production and consensus-message processing across all state machines connected through Hyperbridge, i.e. a route becoming unable to reliably deliver messages, fitting the "route unable to deliver messages" acceptance criterion.

### Likelihood Explanation
Likelihood is high: constructing a large-but-still-valid-looking batch (or a batch that fails only after significant verification work, e.g., a valid membership proof combined with thousands of `PostRequest`/`GetRequest` entries) requires no special privilege, no fee payment, and no prior state — an attacker only needs network access to gossip the unsigned extrinsic. The existing test suite already demonstrates 1000-request / 256-key-per-request batches decoding and dispatching without any batch-size gate at the pallet-ismp level [9](#0-8) .

### Recommendation
Introduce an explicit, benchmarked per-message/per-batch weight function for `handle_unsigned` that scales with `messages.len()` and the size of nested `requests`/`keys` vectors (similar to how `pallet_utility::batch` weighs `c`), and/or bound the batch with a `BoundedVec<Message, T::MaxMessages>` (and bound nested `Vec<PostRequest>`/`Vec<Vec<u8>>` fields) so `CheckWeight`/block-building correctly reject oversized batches before the expensive `execute`/proof-verification path runs, both at initial validation and at every pool revalidation.

### Proof of Concept
1. Construct an unsigned `handle_unsigned` call whose `messages: Vec<Message>` contains a `RequestMessage` with several thousand `PostRequest`s (or a `ResponseMessage`/`GetRequest` with many large `keys`), sized just under the runtime's max extrinsic length.
2. Submit it as an unsigned transaction; `validate_unsigned` executes the full batch (proof verification for every request) to compute `ValidTransaction`, costing far more CPU than the flat 300_000_000 weight implies [2](#0-1) .
3. Because `longevity: 25`, the same expensive validation repeats on subsequent blocks while it sits in the pool, and repeating step 1–2 with multiple concurrent submissions multiplies the effect across all full nodes for zero fee cost.

	pub fn execute(messages: Vec<Message>) -> Result<Vec<events::Event>, Error<T>> {
		let host = Pallet::<T>::default();

		let message_results = messages
			.iter()
			.map(|msg| handle_incoming_message(&host, msg.clone()))
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		let messages_with_weights = message_results
			.iter()
			.zip(messages)
			.map(|(result, message)| MessageWithWeight { message, weight: result.weight() })
			.collect::<Vec<_>>();
