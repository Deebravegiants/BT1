### Title
Fee-on-transfer / burn-on-transfer token accounting mismatch in `placeOrder` causes escrow ledger to exceed actual reserves - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` credits the internal escrow ledger `_orders[commitment][token]` using the *nominal* order amount (reduced only by the protocol fee), instead of measuring the token balance actually received by the contract. Any ERC20 whose `transferFrom` delivers less than the requested amount (fee-on-transfer, deflationary/burn-on-transfer tokens like the BCE token in the referenced incident) causes the contract's bookkeeping to overstate its real token reserves, exactly the "reserve manipulation" root cause described in the external report.

### Finding Description
In `placeOrder`, the non-predispatch branch does: [1](#0-0) 

`IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` is called, but the escrow credit `_orders[commitment][token] += reducedInputs[i].amount` uses the pre-transfer nominal amount (minus protocol fee only), never checking `balanceOf(address(this))` before/after. The predispatch branch has the same flaw — dust is computed only relative to `requiredAmount` (`order.inputs[i].amount`) versus the dispatcher's raw balance, but the amount actually credited to escrow is still `reducedInputs[i].amount`, the nominal pre-fee-on-transfer figure: [2](#0-1) 

Contrast this with the EVM-mainline `IntentGatewayV2.sol`, which explicitly snapshots `balanceOf` before and after every transfer and mutates `order.inputs[i].amount` to the actually-received value before computing the commitment/escrow, precisely to defend against this class of token: [3](#0-2) 

This defensive pattern is missing entirely from the Tron variant.

### Impact Explanation
If a user places (or a malicious user deliberately places, using a fee-on-transfer/burn token as an input asset) an order with such a token, `_orders[commitment][token]` will record an amount greater than what the contract actually holds for that specific escrow entry. Because `_orders` is a shared global mapping across all orders/tokens in the contract, this overstatement lets the corresponding solver (via `fillOrder`/`withdraw`) or the user (via `cancelOrder`/refund) redeem the *nominal* escrowed amount even though the contract's real balance for that token is lower — the shortfall is siphoned from the pooled reserves that back other orders' escrows of the same token. This is a direct analog of the BCE incident: the token's own transfer/burn mechanics are exploited to desynchronize the on-chain accounting from the true reserve, letting an attacker extract more value than was actually deposited, at the expense of the shared pool (concrete theft / permanent freezing of other users' escrowed funds).

### Likelihood Explanation
Any ERC20 that is not a "clean" 1:1 transfer token — deflationary tokens, fee-on-transfer tokens, or tokens with burn-on-transfer logic (as in the BCE case) — placed as an intent input will trigger this immediately on `placeOrder`; no privileged role or complex setup is required, just a standard `placeOrder` call with such a token as input, which is a normal unprivileged user action reachable via the public `placeOrder` entrypoint.

### Recommendation
Apply the same balance-diff safeguard used in the EVM `IntentGatewayV2.sol` (`evm/src/apps/IntentGatewayV2.sol`): snapshot `IERC20(token).balanceOf(address(this))` (or of the dispatcher, for predispatch flows) before and after each `safeTransferFrom`/sweep, and credit `_orders[commitment][token]` (and mutate `order.inputs[i].amount`/`reducedInputs[i].amount` used for the commitment hash) with the actually-received delta rather than the nominal pre-fee amount.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g., 1% burn on transfer, as modeled by `FeeOnTransferToken` in the EVM test suite) and register it as tradeable input.
2. Call `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs[0] = {token: FOT, amount: 1000e18}` and no protocol fee configured.
3. `safeTransferFrom` delivers only 990e18 to the gateway (`balanceOf(gateway)` increases by 990e18), but `_orders[commitment][FOT] += 1000e18` is recorded (`reducedInputs[i].amount` unchanged since `protocolFeeBps == 0`).
4. A solver later fills/withdraws based on the escrow ledger showing 1000e18 available, draining 10e18 more than the contract actually received for this order — funded from other users' pooled FOT-token balances in the same contract. [1](#0-0) [3](#0-2)
