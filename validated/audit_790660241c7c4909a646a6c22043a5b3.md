### Title
`CallDispatcher.dispatch()` has no access control, allowing arbitrary calls from any address while the contract holds escrowed order funds - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch()` is `external` with no caller restriction and executes arbitrary attacker-supplied `Call{to, value, data}` entries via low-level `.call`, using the `CallDispatcher` contract itself as `msg.sender`. [1](#0-0)  This mirrors the reported `JUSDMulticall.multiCall()` pattern: a shared, unauthenticated "do arbitrary calls" entry point on a contract that is documented to temporarily hold real funds.

### Finding Description
`IntentsBase._execute()` transfers order output assets to the `CallDispatcher`, invokes `ICallDispatcher(dispatcher).dispatch(order.output.call)` to run solver-supplied post-fill calldata, and then sweeps residual balances back to the gateway. [2](#0-1)  The documentation for the intent-gateway explicitly states the `CallDispatcher` "holds tokens temporarily during execution," and separately for `predispatch`, assets are transferred to the `CallDispatcher` before its encoded calls execute and the resulting tokens are transferred back for escrow. [3](#0-2) 

Because `dispatch()` itself has no `onlyGateway`/`onlySelf`-style modifier, any external account can call `CallDispatcher.dispatch()` directly (not only via the intent gateway) with an arbitrary `Call[]` targeting any address and value, using the dispatcher's own balance and identity as `msg.sender`. [1](#0-0)  The contract also has a `receive()` function that accepts unsolicited ETH, and there is no way to "own" or gate residual value it accumulates outside of the trusting the atomic in-flight execution during a legitimate order fill. [4](#0-3) 

### Impact Explanation
If the `CallDispatcher` retains any balance between transactions — from dust left by a fee-on-transfer/rebasing token not fully captured by the sweep loop, from unsolicited/mistaken ETH or token transfers to its address (it is a single, publicly known, shared singleton reused across `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` deployments, per the mainnet/testnet contract-address docs) — any unprivileged address can call `dispatch()` directly to route that balance to itself via an arbitrary `to.call{value}(data)`. This is a direct theft of funds vector on a shared, funds-holding contract with a fully public arbitrary-call entry point, analogous in root cause to the reported `multiCall()` finding (unauthenticated arbitrary-call primitive on a contract holding value).

### Likelihood Explanation
The dispatcher's normal design keeps its balance at zero outside of a single atomic transaction (predispatch/postdispatch execute and sweep within the same call), so the exploitable window is not "every transaction" but relies on residual balance accumulating (dust, non-standard tokens, or misdirected transfers) — this is a realistic but conditional scenario given the contract is a long-lived, address-known singleton referenced by multiple production apps, and its `dispatch()` function itself performs no validation of `msg.sender` before making the call.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by the authorized calling app(s) (e.g., an `onlyAuthorizedCaller` allowlist of the `IntentGatewayV2`/`HyperFungibleToken` instances, or require `msg.sender == expected app` set at construction), or make the dispatcher single-use / re-deployed per call rather than a shared singleton that could carry residual balance. At minimum, add a sweep/rescue-only path and disallow arbitrary destinations from being invoked by unauthenticated callers.

### Proof of Concept
1. Attacker observes that `CallDispatcher` (a publicly documented, shared address per docs/content/developers/evm/contract-addresses) is used by `IntentGatewayV2` and `HyperFungibleToken` for predispatch/postdispatch/calldata execution. [5](#0-4) 
2. Attacker sends a small amount of a fee-on-transfer or non-standard ERC20 (or directly sends ETH via `receive()`) to the `CallDispatcher` address, or waits for legitimate dust to accumulate that the gateway's sweep loop (bounded to `order.output.assets`) does not fully capture. [4](#0-3) [6](#0-5) 
3. Attacker calls `CallDispatcher.dispatch(encodedCalls)` directly with `Call{to: token, value: 0, data: transfer(attacker, balance)}` or `Call{to: attacker, value: address(this).balance, data: ""}`, since there is no access check on `dispatch()`. [1](#0-0) 
4. Funds held by the dispatcher are transferred out to the attacker.

Note: I was unable to fully confirm within this session whether the gateway's sweep logic during `predispatch` (in `IntentGatewayV2.sol`/`ExtrinsicIntents.sol`) always leaves zero residual balance in every code path (e.g., partial fills, failed calls, or non-standard tokens); this would need further review of `evm/src/apps/IntentGatewayV2.sol` and `evm/src/apps/intentsv2/ExtrinsicIntents.sol` to fully quantify the realistic residual-balance likelihood.

```text
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```

```text
### Predispatch

The `predispatch` field in `Order` contains calldata to execute *before* escrowing inputs. The predispatch assets specified in `DispatchInfo.assets` are transferred to the `CallDispatcher`, the encoded calls are executed, and the resulting tokens are transferred back to the gateway for escrow. This enables swap-then-escrow patterns — for example, a user sends ETH which the `CallDispatcher` swaps to DAI on Uniswap, and the resulting DAI is escrowed as the order input.
```

```text
### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
```
