### Title
Governance-lowered liquidation threshold is silently never applied to risky accounts — stale threshold blocks liquidation indefinitely - ([File: contracts/controller/src/risk/params.rs])

### Summary
CVE-2019-14870 is a "restriction flag set but not enforced" bug: Samba stored `delegation_not_allowed` but minted forwardable tickets anyway. The analog in XOXNO Lending is the gated restamp of per-position liquidation parameters. Governance can lower `liquidation_threshold` (or raise `liquidation_bonus` / lower `liquidation_fees`) on a spoke asset, and every account carries a cached copy of that tuple in its `AccountPosition`. But `apply_gated_liquidation_params` refuses to apply the new, liquidator-favoring tuple whenever the account has debt and would not clear HF ≥ 1.05 under the new threshold — precisely the accounts that need the tighter threshold. There is no privileged or unprivileged path that forces the restamp, so the reduced protection is never enforced against the riskiest positions.

### Finding Description
Each `AccountPosition` stores its own `liquidation_threshold`, `liquidation_bonus`, and `liquidation_fees`, restamped only via `refresh_supply_risk_params`. The permissionless keeper entrypoint `update_account_threshold(caller, has_risks, account_ids)` reaches `sync_account_thresholds` → `refresh_supply_risk_params` → `apply_gated_liquidation_params` (contracts/controller/src/risk/params.rs:68-93):

```rust
if favors_liquidator(position, effective_config)
    && !account.debt_free()
    && !clears_min_hf(...)
{
    return;   // stale tuple kept, no revert, no alternative path
}
position.liquidation_threshold = effective_config.liquidation_threshold;
```

`favors_liquidator` is true exactly when governance tightened risk (lower threshold, higher bonus, lower fees). For any indebted account whose hypothetical HF under the new threshold is below `THRESHOLD_UPDATE_MIN_HF_RAW` (1.05), the function silently keeps the old, looser threshold forever. The final `hf >= 1.05` assertion in `sync_account_thresholds` (params.rs:221-234) only runs over already-updated positions, so it never forces the skipped tuple through either. Like the Samba bug, the system records a restriction (the new config) and then declines to apply it on the exact path where it matters.

### Impact Explanation
Protocol insolvency. When governance cuts a collateral's `liquidation_threshold` in response to deteriorating risk, all accounts already near the boundary retain the old higher threshold, so their computed health factor stays above 1 and `liquidate` keeps reverting. Interest accrues and prices can drift further while the intended tightening is unenforced — the same shape as Samba honoring `not-delegated` nowhere: a safety parameter exists in storage but is inert for the only population it targets. The delay converts marginal accounts into bad debt that `clean_bad_debt` must socialize against suppliers.

### Likelihood Explanation
Medium. Triggering needs (a) a governance parameter tightening — a routine risk action — and (b) an indebted account sitting in the HF band between 1.0 (new threshold) and 1.05. Any single unprivileged borrower automatically qualifies; no attacker action beyond holding a leveraged position is required, and `update_account_threshold` is permissionless so no keeper neglect is needed to prove the gap — the call itself enforces the gap by design.

### Recommendation
Distinguish "do not push a healthy account under water via parameter refresh" from "never tighten a risky account." Options: allow the restamp whenever the account's HF under the *new* tuple is still ≥ 1.0 (i.e., gate on liquidatability, not on a 1.05 buffer), or add a second, liquidation-only restamp path callable once the account crosses HF < 1 under the stored tuple so the corrected parameters take effect before or at liquidation rather than never.

### Proof of Concept
1. Alice supplies USDC and borrows ETH so her account sits at HF ≈ 1.03 under the current `liquidation_threshold` (e.g., 9000 bps).
2. Governance executes a timelocked `edit_asset_in_spoke` lowering the listing's `liquidation_threshold` to 7000 bps — a liquidator-favoring change (`favors_liquidator` returns true).
3. Any keeper calls `controller.update_account_threshold(anyone, true, [alice_account])`. `clears_min_hf` computes HF with `new_lt = 7000`, gets ~1.03 < 1.05, and `apply_gated_liquidation_params` returns early — Alice's stored threshold stays 9000.
4. Alice's reported HF remains ≥ 1 and `liquidate` reverts. Repeating `update_account_threshold` can never fix this; under the intended 7000-threshold policy the account should already be liquidatable, but the restriction is enforced nowhere — funds that should have been recovered accrue into bad debt borne by suppliers.
