### Title
Relayer-fee transfer in `EvmHost.dispatchIncoming(GetResponse)` can permanently DOS an entire batch of GET-response deliveries - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatchIncoming(GetResponse, address relayer)` pays the accrued relayer fee with a direct, unguarded `IERC20(feeToken()).safeTransfer(relayer, fee)` after a successful `onGetResponse` callback. This function is invoked once per response inside `HandlerV2.handleGetResponses`'s loop over `message.responses`. If the `feeToken` (e.g. a blacklist-capable stablecoin such as USDC) refuses to transfer to `relayer`, the `safeTransfer` reverts, and because this call is not wrapped in a try/catch or low-level call the way `onAccept`/`onGetResponse` invocations are, the revert propagates out of `dispatchIncoming`, out of `handleGetResponses`, and — if bundled via `batchCall` — reverts the whole transaction.

### Finding Description
Compare the two `dispatchIncoming` overloads in `evm/src/core/EvmHost.sol`:

- `dispatchIncoming(PostRequest, ...)` (lines 794-818) makes the callback via low-level `.call`, checks `success`, and on failure simply deletes the receipt and `return`s — so one bad `onAccept` can never block the rest of a batch: [1](#0-0) 

- `dispatchIncoming(GetResponse, ...)` (lines 824-847) also uses a low-level `.call` for `onGetResponse` and correctly isolates *that* failure, but the subsequent relayer-fee payout on the success path is a direct `safeTransfer`, not wrapped in any failure isolation: [2](#0-1) 

This function is called inside a loop by the permissionless `HandlerV2.handleGetResponses`, once per leaf in `message.responses`: [3](#0-2) 

Any relayer address can become blacklisted by the fee token issuer (Circle blacklists addresses that interact with sanctioned protocols such as Tornado Cash), or a fee token could simply be paused/frozen for that address. Once `relayer` is blacklisted for `feeToken`, every subsequent `handleGetResponses` batch that happens to include a response whose `requestCommitments(...).fee != 0` and was originally relayed under this address's incentive path will revert at the fee-payout line, since `relayer` here is `_msgSender()` of the `handlePostRequests`/`handleGetResponses` call, i.e., whoever submits that specific batch. Because the relayer field is fixed once the batch is assembled and reused for every response in that same `handleGetResponses` call, a single blacklisted relayer forces reverting of the entire batch of GET responses (and any consensus update bundled with it via `batchCall`, since `batchCall`'s semantics are "any failure reverts the entire batch": [4](#0-3) ). Other relayers can still resubmit unrelated batches, but any response the blacklisted relayer has already committed to relay (and any batch a relayer submits after becoming blacklisted, even carrying other users' unrelated GET responses) becomes permanently undeliverable, since the fee reward can never be sent and there is no fallback path (no try/catch, no "hold funds for later claim").

This mirrors the CrabNetting root cause precisely: a payment to a single blacklistable recipient is made unconditionally inside code that also processes work belonging to unrelated parties, with no isolation, so one bad recipient blocks everyone sharing the same execution path.

### Impact Explanation
A relayer that becomes blacklisted for the `feeToken` (deliberately or otherwise) can never again have its GET-response deliveries accepted, since the reward payment inside `dispatchIncoming(GetResponse)` unconditionally reverts. Because `handleGetResponses` processes several responses per call and this is composable with `batchCall`, one relayer's blacklisting freezes delivery of every GET response and any bundled consensus update in the same transaction, blocking storage-proof-based flows (e.g., Intent Gateway `cancelOrder` GET-response delivery, `onGetResponse` withdrawals) until a different, non-blacklisted relayer resubmits the exact same response set with itself as `_msgSender()`. While in principle another relayer can always re-relay (GET responses have no relayer field baked into the message itself, only into the call), this still creates griefing/DOS risk and, if `fee` accrual and delivery are otherwise coupled, can also freeze the relayer's own accrued fee balance for the affected requests indefinitely.

### Likelihood Explanation
Getting an address blacklisted by a centralized stablecoin issuer is realistic and low-cost (documented via the Tornado Cash sanctions precedent cited in the source report). Any of Hyperbridge's relayers (permissionless role, `tesseract`) using a fee token capable of blacklisting is exposed; an adversarial relayer operator, or one targeted by third-party sanctions, needs no special contract interaction beyond receiving fee-token transfers to trigger the freeze.

### Recommendation
Isolate the relayer-fee payout in `EvmHost.dispatchIncoming(GetResponse)` the same way `onAccept`/`onGetResponse` failures are isolated — e.g. wrap the `safeTransfer` in a try/catch (or low-level `call`) and, on failure, credit the fee to a claimable balance for the relayer instead of reverting the whole delivery, so a blacklisted relayer's payout failure never blocks the response delivery itself or other responses/consensus updates bundled in the same batch.

### Proof of Concept
1. Relayer `R` accrues a nonzero `fee` for a GET request (`FeeMetadata.fee != 0` in `_requestCommitments`).
2. `feeToken` issuer blacklists `R` (e.g., simulate with a mock ERC20 whose `transfer` reverts for a specific address, mirroring USDC's `blacklist` behavior).
3. Relayer `R` (or anyone submitting on `R`'s behalf as `_msgSender()`) calls `HandlerV2.handleGetResponses(host, message)` with a valid proof for one or more GET responses whose underlying request had `fee != 0`.
4. Execution reaches `EvmHost.dispatchIncoming(GetResponse, relayer=R)`; `onGetResponse` succeeds, then `IERC20(feeToken()).safeTransfer(R, fee)` reverts because `R` is blacklisted.
5. The revert propagates through `handleGetResponses`'s loop and the whole `handleGetResponses` call (and any `batchCall` it was bundled in) reverts, so none of the GET responses in that call — including ones destined for other users' applications (e.g., `IntentGatewayV2.onGetResponse` cancellations) — are delivered until re-submitted by a different `_msgSender()`.

    /**
     * @dev Process a batch of encoded handler calls in a single transaction.
     * Uses delegatecall to self so msg.sender is preserved and storage writes
     * happen in this contract's context. Atomic, any failure reverts the entire batch.
     * @param calls - array of ABI-encoded handler function calls
     */
    function batchCall(bytes[] memory calls) external {
        uint256 len = calls.length;
        for (uint256 i = 0; i < len; ++i) {
            (bool success, bytes memory returnData) = address(this).delegatecall(calls[i]);
            if (!success) revert BatchCallFailed(i, returnData);
        }
    }
