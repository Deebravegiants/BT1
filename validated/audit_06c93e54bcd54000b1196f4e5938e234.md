This confirms the vulnerability pattern. The `Request#hmac` in `lib/shopify_api/webhooks/request.rb` is verified only against `to_signable_string`, which returns `@raw_body` — it does not include the `shop`, `topic`, or `webhook_id` header values in the signed data. `Registry.process` then trusts `request.shop` (from the `x-shopify-shop-domain`/`shopify-shop-domain` header) as the tenant identifier without any cryptographic binding to that value.

### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC over the raw body only, while the `shop` (tenant) identity is read from an unauthenticated header. `ShopifyAPI::Webhooks::Registry.process` passes this unauthenticated `shop` value straight to the host application's handler as the trusted tenant identifier.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is not part of the signed content: [2](#0-1) 

`HmacValidator.validate` verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string` using `OpenSSL.secure_compare`, and for a `Webhooks::Request` this only covers the raw body bytes, not the headers: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identifier passed to the app's webhook handler: [4](#0-3) 

The binding that should hold is: `hmac == HMAC(secret, shop || topic || body)` (or equivalent), so that the `shop` value used for tenant routing is cryptographically tied to the payload that was signed. Instead the gem only checks `hmac == HMAC(secret, body)`, i.e. `shop` is "acted on" (used to route/attribute the event to a tenant) but not "covered by the HMAC". Any two webhooks with identical bodies (e.g., a topic with an empty or predictable body, or a payload the attacker can reproduce byte-for-byte) will produce the *same* valid HMAC for the app's shared `client_secret` regardless of which `shop-domain` header value is attached, because the header is never part of `to_signable_string`.

### Impact Explanation
This breaks the identity binding "shop authenticated versus the shop stored/used as tenant key" analog described in the report: the value used downstream to key persistence, authorization, or session lookups (`request.shop`) is not the value that was actually authenticated by the HMAC (only `raw_body` was authenticated). Since `Registry.process` forwards `request.shop` directly into `WebhookMetadata` for the app's handler without any additional tenant-binding check, an attacker capable of causing (or replaying) any validly-HMAC'd webhook delivery for a body they can predict/reproduce (e.g. an empty-body event, or a captured webhook whose secret-derived HMAC they can compute using a body they control if allowed by Shopify's delivery semantics) can present it with an arbitrary `shop-domain` header, and the gem will process it as belonging to that arbitrary shop — a cross-tenant identity spoof at the library layer. This matches the Critical "cross-tenant access" impact bucket because the vulnerable code is in the gem's own trust boundary (`Registry.process` + `HmacValidator.validate`), not merely the host app's use of the data.

### Likelihood Explanation
Exploitability is bounded by how much control an attacker has over the raw body relative to a target `client_secret`-signed body, but the core defect — that `shop` is never part of the signable string — is deterministic and always present. Any deployment that relies on `request.shop`/`data.shop` from `ShopifyAPI::Webhooks::Registry.process` for tenant-scoped decisions (as the gem's own documentation recommends doing, e.g. `shop_domain: data.shop`) inherits this gap regardless of how carefully the host app is written, since the gem provides no stronger guarantee.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the signable string used for HMAC verification, or otherwise cryptographically bind the header-derived tenant identity to the verified payload before exposing it via `WebhookMetadata`. At minimum, document clearly that `shop` is unauthenticated and must not be used for tenant-keyed decisions without independent verification (e.g., cross-checking against a known registered shop list).

### Proof of Concept
```ruby
require "shopify_api"

ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", host_name: "host",
  scope: "read_products", is_embedded: false, is_private: false, api_version: "2024-01")

raw_body = "{}"
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "secret", raw_body)

# Legit shop's webhook
legit_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",
}

# Attacker swaps only the shop-domain header; HMAC (computed over raw_body only) still validates
spoofed_headers = legit_headers.merge("x-shopify-shop-domain" => "attacker-shop.myshopify.com")

req = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: spoofed_headers)
ShopifyAPI::Utils::HmacValidator.validate(req) # => true, even though shop was changed
```
`HmacValidator.validate` returns `true` for both `legit_headers` and `spoofed_headers` because `to_signable_string` ignores the `shop-domain` header entirely, demonstrating that `shop` is not bound to the HMAC.
