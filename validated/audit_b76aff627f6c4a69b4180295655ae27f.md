### Title
Missing Arbitrum Sequencer-Uptime Check in `SimplexPaymaster` Chainlink Price Reads — (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` prices ERC-4337 gas payments in stablecoins using two Chainlink `AggregatorV3Interface` feeds (native/USD and token/USD), guarded only by a staleness check on `updatedAt`. It is deployed across multiple EVM chains, including Arbitrum per `evm/script/deploy.sh`, but never checks the Arbitrum L2 sequencer-uptime feed (e.g. `0xFdB631F5EE196F0ed6FAa767959853A9F217697D` on Arbitrum One). This mirrors the referenced Sherlock report on `D3Oracle.sol`.

### Finding Description
`_getOraclePrice` reads `latestRoundData()` and only enforces `answer > 0` and `block.timestamp - updatedAt <= maxOracleAge`: [1](#0-0) 

On Arbitrum, when the sequencer is offline, transactions that batch to L1 (via forced inclusion) can be executed with L2 block timestamps that lag real time, while the last Chainlink round pushed before the outage can still look "fresh" relative to that lagging timestamp. There is no `ISequencerUptimeFeed`-style check anywhere in the codebase (`grep` for `L2_SEQUENCER|sequencerUptimeFeed|isSequencerUp` returns no matches), and `AggregatorV3Interface` in `SimplexPaymaster.sol` is a minimal, self-declared interface with no sequencer-feed companion: [2](#0-1) 

The paymaster is confirmed to target Arbitrum among its deployment targets (`evm/script/deploy.sh` references arbitrum multiple times), and pricing directly gates how much of a user's stablecoin is pulled to cover gas: [3](#0-2) [4](#0-3) 

### Impact Explanation
Any unprivileged UserOperation sender ("bandwidth purchaser" paying for gas through this paymaster) can have their token charge computed from a stale-but-passing price during an Arbitrum sequencer outage/recovery window. Depending on which side of the price moved, this either lets a sender underpay for gas (draining the paymaster's stablecoin reserves relative to actual gas cost, a fund-drain against the protocol/treasury) or overcharges senders (fund loss to users). Because `_tokenPrice`/`_getOraclePrice` sit directly in the hot path of every `_fetchDetails`/`_prefund`/`swapAndDeposit` call, this is a direct, unprivileged-reachable accounting flaw, not merely a monitoring gap.

### Likelihood Explanation
Requires an actual Arbitrum sequencer downtime/restart event, which is infrequent but has happened historically; during such an event any user can submit a UserOperation without needing any special privilege, so exploitation only depends on timing, not on any elevated access. `maxOracleAge` is often tuned generously for slow-heartbeat feeds (e.g. the deploy script defaults to 90,000 seconds "buffer over 24h" for stablecoin feeds), widening the exploitable window: [5](#0-4) 

### Recommendation
Add an Arbitrum L2 sequencer-uptime feed check in `_getOraclePrice` (or a wrapper called before it) that reverts if the sequencer feed reports `answer == 1` (down) or if less than a grace period has elapsed since it came back up (`startedAt`), following Chainlink's documented pattern, gated per-chain (e.g. only applied when deployed on Arbitrum/other L2s using Chainlink's sequencer feed).

### Proof of Concept
1. Arbitrum sequencer goes offline; the last Chainlink round for `nativeOracle`/`tokenOracle` was pushed shortly before the outage.
2. During or immediately after the outage, a forced-inclusion (or fast-recovering) UserOperation is processed with an L2 timestamp such that `block.timestamp - updatedAt <= maxOracleAge` still holds even though the true market price has since diverged.
3. `_getOraclePrice` (`evm/src/utils/SimplexPaymaster.sol:662-676`) returns the stale price with no sequencer check, and `_tokenPrice`/`_fetchDetails` uses it to compute the token charge for the UserOperation, allowing an attacker-controlled sender to prefund at a favorable stale rate.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
