### Title
No bounds checking on attacker-controlled scrypt parameters (n, r, p) allows KDF downgrade or resource-exhaustion during backup decryption - (File: libraries/secure-container/src/metadata.js)

### Summary
The `decrypt` flow in `libraries/secure-container/src/index.js` decodes an untrusted backup's metadata (including `scrypt.n`, `scrypt.r`, `scrypt.p`) with no validation, and passes those values straight into `stretchPassphrase`/`scrypt()` via `boxDecrypt`. There is no minimum/maximum bound enforced anywhere in this call chain, so a maliciously crafted backup file can force a drastically weakened (or maliciously oversized) KDF invocation.

### Finding Description
The call chain is: `decrypt(encryptedData, passphrase)` → `conFile.decode` → `conMetadata.decode(fileObj.metadata)` (uses `struct.decode`, raw `UInt32BE` fields for `n`, `r`, `p` with no range constraints, `libraries/secure-container/src/metadata.js:7-17,37-43`) → `conMetadata.decryptBlobKey(metadata, passphrase)` (`libraries/secure-container/src/metadata.js:79-81`) → `boxDecrypt(passphrase, ..., scryptParams)` in `libraries/secure-container/src/crypto.js:41-45`, which merges attacker values over defaults (`scryptParams = { ...createScryptParams(), ...scryptParams }`) and calls `stretchPassphrase` → `scrypt(passphrase, salt, { N: n, r, p, dkLen: 32 }, 'buffer')` (`libraries/secure-container/src/crypto.js:16-19`).

None of `metadata.js`, `crypto.js`, or `index.js` validate `n`, `r`, `p` against a policy floor/ceiling before invoking scrypt. A checksum check (`conFile.computeChecksum`) exists in `decrypt()`, but that checksum is computed over the very same attacker-supplied metadata bytes (`libraries/secure-container/src/index.js:45-46`), so it only verifies internal consistency of the attacker's file — it does not prevent the attacker from choosing arbitrary (weak or extreme) scrypt parameters and self-consistently computing the matching checksum. Because the checksum is not tied to any external secret or trusted source, it provides zero protection against a self-authored malicious backup.

The `decode()` function only warns via `console.warn` if the total metadata blob exceeds `METADATA_LEN_BYTES`, which is unrelated to `n`/`r`/`p` bounds (`libraries/secure-container/src/metadata.js:37-42`).

However, whether this is truly exploitable as "wallet compromise" depends on the actual impact: this weakens/strengthens the passphrase-stretching used to decrypt the `blobKey` that decrypts the backup's own contents — i.e., the attacker controls the very same file's own protection parameters. In a legitimate attack scenario, the attacker would need to get the victim to import a malicious backup file authored by the attacker, using the victim's own real passphrase, in order to benefit from downgraded parameters — but the attacker doesn't know the victim's passphrase and cannot use this to attack an existing, already-encrypted legitimate backup (that backup's `n/r/p` were set at encryption time by the victim's own device with `createScryptParams()` defaults, and are checksummed against the original honest blob). This finding is therefore only relevant if an attacker can substitute or tamper with a backup file in transit/storage after the checksum was computed by a trusted party but before decryption, or if the import flow accepts externally-supplied "restore" files without an independent authenticity check (e.g., HMAC/signature tied to a value not under attacker control) beyond the internal checksum.

### Impact Explanation
If an attacker can substitute a legitimate backup file with a maliciously crafted one that the victim then decrypts with their real passphrase (e.g., during restore from a compromised transport, a malicious import feature, or a supply-chain-tampered backup), the attacker could set `n=1, r=1, p=1` to make offline brute force of a captured/observed ciphertext trivially fast, undermining the confidentiality guarantee that scrypt is meant to provide. Alternatively, absurdly large `n`/`r`/`p` values can cause CPU/memory exhaustion (DoS) on the importing device while it attempts key derivation. This maps to a KDF-strength downgrade / DoS impact class rather than direct signing or key-exfiltration, since the attacker cannot use this to extract secrets from a legitimate untampered backup without also controlling the passphrase used against it.

### Likelihood Explanation
Exploitation requires the attacker to control the content of the backup file being imported (i.e., convince the victim to import an attacker-supplied backup, or tamper with backup content between creation and import without detection by an out-of-band integrity check). The internal SHA-256 checksum in `file.js`/`index.js` is self-consistent and does not prevent an attacker from crafting a coherent malicious file from scratch. Given typical wallet import/restore flows (QR/file import of a backup produced elsewhere), this is a plausible, low-complexity attack surface once such an import entry point is confirmed to accept externally-supplied SECO files.

### Recommendation
Add explicit bounds validation for `scrypt.n`, `scrypt.r`, `scrypt.p` (and possibly `dkLen`) in `metadata.decode()` or immediately before calling `stretchPassphrase`/`boxDecrypt`, rejecting values below a security floor (e.g., `n < 16_384` or `r*p` below policy) and above a sane ceiling (to prevent DoS), throwing rather than silently proceeding. Consider also enforcing that `n` is a power of two and within `[16_384, 1_048_576]`-style bounds consistent with `createScryptParams()` defaults, and reject metadata whose declared KDF cost falls outside this policy window regardless of what the file's internal checksum says.

### Proof of Concept
Unit test plan (extends `libraries/secure-container/src/__tests__/metadata.test.js`):
1. Construct a `metadata` object via `metadata.create({ salt: randomBytes(32), n: 1, r: 1, p: 1 })`.
2. Call `metadata.encryptBlobKey(md, passphrase, blobKey)` then `metadata.decryptBlobKey(md, passphrase)`.
3. Assert current behavior: the call succeeds without error despite `n=1`, demonstrating no policy floor is enforced (`t.doesNotReject` currently passes for `n=1`, which should fail/throw after the fix).
4. Repeat with `n = 2**30` and assert either a bounded execution time/throw (DoS-floor test) instead of unrestricted CPU consumption.
5. After remediation, assert `metadata.decryptBlobKey`/`crypto.stretchPassphrase` throws a validation error for `n`, `r`, or `p` outside the defined policy bounds.
