### Title
Unsafe raw `token.call` in `withdraw()` does not check ERC20 return value - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
In the Tron-specific `IntentGatewayV2` contract, escrow redemption in `withdraw()` uses a raw low-level `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checks that the call itself did not revert (`success`), never decoding/validating the boolean return value encoded in the returned bytes. This is the same class of bug flagged in the referenced report: non-reverting-on-failure ERC20/TRC20 tokens (which return `false` instead of reverting) will be treated as a successful transfer.

### Finding Description
`withdraw()` is the internal function that releases escrowed order tokens to a solver or refunds a user once a cross-chain settlement message (`onAccept`) or GET response (`onGetResponse`) is processed by the ISMP host: [1](#0-0) 

For each escrowed token it does:
```
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
and the same pattern for transaction fee redemption:
```
(bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
if (!success) revert TransferFailed();
``` [2](#0-1) 

`success` here only reflects whether the external call reverted, not whether the token's `transfer` function actually returned `true`. Many tokens (including the canonical non-standard USDT-style token, and any TRC20 token on Tron that follows the same non-reverting convention) return `false` on failure instead of reverting. Because the returndata is discarded (`(bool success,)`), such a failed-but-non-reverting transfer is indistinguishable from a success.

Immediately after the `.call`, the contract unconditionally decrements the internal escrow accounting:
```
_orders[body.commitment][token] -= amount;
``` [3](#0-2) 

so escrow bookkeeping is updated as if funds were delivered even when they were not.

This contrasts with the rest of the Tron `IntentGatewayV2` contract and the main EVM `IntentGatewayV2`/`ExtrinsicIntents.sol`, which consistently use OpenZeppelin's `safeTransferFrom`/`safeTransfer` (via `SafeERC20`) elsewhere for token movement, e.g. in `placeOrder`/`fillOrder`: [4](#0-3) [5](#0-4) 
This makes `withdraw()`'s raw `.call` pattern an inconsistency/regression specifically in the settlement/redemption path.

### Impact Explanation
`withdraw()` is reached via `onAccept` (delivery of a `RedeemEscrow`/refund message relayed through Hyperbridge after cross-chain proof verification) and via `onGetResponse` (cancellation/refund path). If the escrowed token is a non-reverting-on-failure ERC20/TRC20 (e.g. it returns `false` when the beneficiary is blacklisted, when the contract is paused, or under any other soft-failure condition), the solver or user entitled to the escrowed funds receives nothing, while:
- The order/escrow is marked filled/refunded (`_filled[body.commitment] = beneficiary`), and
- Internal escrow accounting is decremented as though funds were paid out.

This is a permanent loss of the escrowed funds for the intended beneficiary (solver or user) — the tokens remain stuck in the `IntentGatewayV2` contract with no accounting path to reclaim them, since the order is already marked filled and escrow already zeroed out.

### Likelihood Explanation
Likelihood depends on whether soft-failing tokens (returning `false` rather than reverting) are used as intent inputs/fee tokens on the Tron deployment. Since `IntentGatewayV2` is a general-purpose intents gateway accepting arbitrary user-specified `TokenInfo.token` addresses for `inputs` and fee tokens (not restricted to a fixed whitelist visible in this snippet), any user placing an order with such a token — or any interaction where the beneficiary account becomes blacklisted/restricted by the token issuer between order placement and settlement — triggers this path. This is a realistic, externally-reachable condition, not a privileged-actor scenario.

### Recommendation
Replace the raw `token.call(...)` / `feeToken.call(...)` patterns in `withdraw()` with `SafeERC20.safeTransfer`, consistent with the rest of the codebase (`IERC20(token).safeTransfer(beneficiary, amount)` and `IERC20(feeToken).safeTransfer(beneficiary, fees)`), so that both call-reversion and false-return failures cause the transaction to revert instead of silently marking the escrow as redeemed.

### Proof of Concept
1. Deploy (or use) a TRC20/ERC20 token whose `transfer` function returns `false` instead of reverting when the transfer cannot be completed (e.g., a blacklist-style token, matching real-world USDT-like semantics).
2. A user places an order on the Tron `IntentGatewayV2` with this token as an input (escrowed).
3. A solver fills the order, and a `RedeemEscrow` message is relayed and delivered via `onAccept`, invoking `withdraw()`.
4. Before delivery, the beneficiary (solver) address becomes restricted by the token contract (or any other condition causing `transfer` to return `false` without reverting).
5. `token.call(...)` returns `success = true` (the call itself didn't revert) even though the encoded return value is `false` and no tokens were moved.
6. `withdraw()` proceeds: `_orders[body.commitment][token] -= amount` executes, `_filled[body.commitment] = beneficiary` is set, and `EscrowReleased` is emitted — yet the beneficiary's token balance is unchanged and the tokens remain locked in the contract with no remaining accounting path to recover them.

Note: I was unable to fully verify whether the main (non-Tron) `evm/src/apps/IntentGatewayV2.sol` composed contract (`IntentsBase`/`ExtrinsicIntents`/`IntrinsicIntents`) contains an equivalent `withdraw()` implementation using `safeTransfer`, since the `withdraw` function name search only matched inside the Tron variant; the composing base contracts were not fully retrieved in this session. The finding above is confirmed specifically for `evm/tron/contracts/apps/IntentGatewayV2.sol`.
