Audit Report

## Title
Fee-on-transfer / non-standard ERC20 tokens cause XCM holding-register accounting mismatch in `ERC20Transactor` - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

## Summary
`ERC20Transactor` is confirmed to be live-wired into `asset-hub-westend`'s XCM configuration as part of the `AssetTransactors` tuple, using the permissionless `ERC20Matcher` [1](#0-0) . Both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus` credit/debit the XCM holding register with the *requested* nominal `amount` based solely on the ERC20 `transfer` call's boolean return value, never verifying the actual balance delta moved by the contract [2](#0-1) [3](#0-2) .

## Finding Description
`withdraw_asset_with_surplus` calls `IERC20::transferCall` to move `amount` to the checking account and, upon a non-reverted call whose ABI-decoded return is `true`, unconditionally credits `AssetsInHolding` with `Erc20Credit(amount)` — the nominal amount, not the amount actually received by `TransfersCheckingAccount` [4](#0-3) . The symmetric `deposit_asset_with_surplus` transfers `amount` from the checking account to the beneficiary and treats the deposit as fully successful as soon as `transfer` returns `true`, without confirming the beneficiary's balance increased by the full `amount` [5](#0-4) . The comment in the file explicitly acknowledges that "the actual balance constraints are enforced by the ERC20 smart contract" rather than by this transactor's own bookkeeping [6](#0-5) , confirming there is no independent balance-delta check as a guard.

Critically, the researcher's stated uncertainty about whether the `Matcher` restricts this to an allow-list is resolved: `ERC20Matcher` is defined as `MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>`, where `IsLocalAccountKey20` matches *any* location of the form `(0, [AccountKey20 { .. }])` — i.e., any local 20-byte address, with no allow-list or registration requirement [7](#0-6) . This confirms the attack surface is genuinely permissionless: any user can deploy an arbitrary `pallet-revive` contract implementing `IERC20` and have it recognized as an XCM-transactable fungible without any privileged registration step.

## Impact Explanation
The accounting mismatch is real and reachable in the live `asset-hub-westend` XCM configuration [8](#0-7) . For fee-on-transfer/deflationary tokens that are genuinely adopted by multiple holders (not merely a throwaway attacker-only contract), the checking account's real on-chain ERC20 balance systematically diverges from the nominal amounts credited/debited through `AssetsInHolding` during withdraw/deposit legs. Since the credited amount always exceeds the amount actually escrowed, this can cause later legitimate `deposit_asset_with_surplus` calls for that token to revert (insufficient real balance in the checking account) or, if float exists from prior transactions, allow a message to withdraw more nominal value than it deposited, degrading the checking account's real backing over time. This is a genuine, concrete accounting-integrity defect in an in-scope Polkadot SDK runtime component, not merely theoretical — it matches the disclosed "fee-on-transfer breaks 1:1 transfer assumption" bug class exactly, with the root cause being the unconditional trust in the boolean return value rather than a measured balance delta.

## Likelihood Explanation
No privileged action is required. `ERC20Matcher`'s `IsLocalAccountKey20` filter accepts any local `AccountKey20` location, so any unprivileged user can deploy a non-standard ERC20 contract on `pallet-revive` and immediately have it recognized by `ERC20Transactor` for XCM transacting [9](#0-8) . The likelihood scales with adoption of non-standard tokens (fee-on-transfer, rebasing, deflationary) that get bridged via XCM using this transactor; this is a common real-world token pattern, making the precondition realistic rather than purely hypothetical.

## Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, query the relevant ERC20 balance (checking account or beneficiary) immediately before and after the `transfer` call, and use the observed balance delta — not the requested `amount` — when constructing `AssetsInHolding` credits or when confirming the deposit succeeded. If the delta is less than requested, fail the operation or credit only the amount actually received.

## Proof of Concept
1. Deploy a Solidity ERC20 contract on `pallet-revive` whose `transfer` function burns/deducts a percentage of `value` on every transfer but returns `true`.
2. Since `ERC20Matcher`'s `IsLocalAccountKey20` matches any local `AccountKey20` location, no registration step is needed for this contract to be recognized by `ERC20Transactor` in `asset-hub-westend`'s `AssetTransactors` tuple.
3. Initiate an XCM `WithdrawAsset` for `amount = 1000` of this token. `withdraw_asset_with_surplus` calls `transfer(checking_account, 1000)`; the contract moves only 900 to the checking account but returns `true`; `AssetsInHolding` is credited with `Erc20Credit(1000)` per lines 197-201 of `erc20_transactor.rs`.
4. A subsequent `DepositAsset` for the same nominal 1000 attempts `checking_account.transfer(beneficiary, 1000)`, which either reverts (if the checking account lacks sufficient real balance) or draws down float accumulated from other users' escrowed funds for the same contract, demonstrating the accounting mismatch and its downstream effect.

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.
pub type ERC20Matcher =
	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
