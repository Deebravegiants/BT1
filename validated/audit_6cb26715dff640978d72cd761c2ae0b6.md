### Title
Webhook shop attribution bypass via unsigned `shop-domain` header enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the `shop` value used to identify the tenant that a webhook belongs to is read from an HTTP header that is never included in that signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Utils::HmacValidator.validate` verifies the HMAC exclusively against that string: [1](#0-0) [2](#0-1) 

Meanwhile, `Request#shop` is parsed straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, with no cryptographic tie to the HMAC-covered bytes: [3](#0-2) 

`Registry.process` validates only the HMAC of the body, then forwards `request.shop` unchecked to the consuming app's handler as the trusted tenant identifier: [4](#0-3) 

The binding that should hold is: `HMAC-verified(shop) == shop passed to handler`. In this implementation, the HMAC only proves `HMAC-verified(raw_body)`, while `shop` is taken from a completely separate, unauthenticated field. Because the webhook signing secret is the app's single, global `api_secret_key` (not a per-merchant secret), any account that can trigger a legitimate webhook from their own shop — which is available to any unprivileged internet user who installs the app — obtains a `(body, hmac)` pair that is valid for that api_secret_key regardless of which shop it is claimed to be about. That valid pair can then be replayed to the app's public webhook endpoint with the `shopify-shop-domain` header changed to any victim shop domain; `Utils::HmacValidator.validate` will still return true because it never inspects the shop header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload came from the victim shop.

### Impact Explanation
This breaks the tenant/session boundary the gem is supposed to guarantee to host applications: the "verified" webhook payload can be attributed to any shop of the attacker's choosing. Host applications that trust `WebhookMetadata#shop` (as returned by this gem) to select which merchant's data/session to update or invalidate can be tricked into writing, deleting, or reacting to data under a victim's tenant using attacker-supplied body content — a cross-tenant data manipulation impact.

### Likelihood Explanation
Exploitation requires only an ability to install the app on any shop (to obtain one legitimate signed body/hmac pair) and public reachability of the app's webhook endpoint — both true for any unprivileged internet user targeting a multi-tenant Shopify app, with no access token, secret, or privileged account required. The only constraint is that the replayed payload's shape/content is whatever the attacker's own shop produced, limiting attacker control over the JSON body content but not over the claimed `shop`.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signable string that the HMAC is computed over, or otherwise cryptographically bind the `shop` header to the verified payload before it is trusted by `Registry.process`/`WebhookMetadata`. At minimum, document that consuming apps must not rely on the header-derived `shop` value as authoritative and must independently authenticate/authorize the tenant (e.g., cross-check against a known list of shops for that specific topic/resource id).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), receiving a request with a valid `shopify-hmac-sha256` computed over the JSON body using the app's global `api_secret_key`.
2. Attacker replays the exact same body and `shopify-hmac-sha256` value to the app's webhook endpoint, but sets `shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the HMAC of the raw body — this passes. [4](#0-3) 
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled JSON>, ...)`, believing this data legitimately originated from the victim's shop, even though it never did.
