### Title
Auto-lock timer can be silently weakened/disabled via `changeLockTimer` with no confirmation, rate-limit, or timelock - (File: `features/application/src/modules/application.ts`)

### Summary
The MarginSwap finding flags that `setLeveragePercent`/`setLiquidationThresholdPercent` are privileged setters for a security-critical parameter that take effect immediately, with no timelock, allowing state to flip from safe to unsafe between one call and the next. The equivalent unprivileged-trust-boundary analog in hydra is the wallet's auto-lock timer: `Application.changeLockTimer` directly mutates the TTL used to decide when the wallet re-locks after inactivity, with no confirmation step, no minimum/rate limiting beyond a static `maxTtl` clamp, and no timelock/cooldown before the new (weaker) value takes effect.

### Finding Description
`changeLockTimer` in the `Application` class immediately delegates to `PassphraseCache.changeTtl`, which sets the new TTL and reschedules the passphrase-clear alarm right away: [1](#0-0) 

`changeTtl` only clamps the value against a static `maxTtl` from config — there is no lower bound enforcement, no re-authentication requirement, and no delay before the change is applied: [2](#0-1) 

The cached passphrase itself is what allows the `#autoUnlock` flow to silently re-unlock the wallet as long as the cached passphrase hasn't expired: [3](#0-2) 

This method is exposed on the public SDK surface as `exodus.application.changeLockTimer` (and its legacy alias `wallet.changeLockTimer`), reachable through the RPC layer that bridges UI/content-script/background boundaries: [4](#0-3) [5](#0-4) 

The RPC exposure mechanism (`exposeMethods`/`callMethod`) performs no origin, permission, or capability check on individual method calls — any caller that can reach the RPC channel can invoke any exposed method by name: [6](#0-5) [7](#0-6) 

I could not find any additional authorization gate (e.g. requiring the current passphrase, a confirmation UI prompt, or a per-origin permission check) between the RPC entry point and the state mutation in `changeTtl`/`autoLockTimerAtom.set`. Given the size limits on the indexed codebase, it's possible such a gate exists in a UI-layer wrapper not captured by the index; this could not be fully confirmed.

### Impact Explanation
If a malicious or compromised caller on the RPC boundary (e.g. an untrusted UI surface, injected script, or compromised companion process reusing the same message channel) can invoke `application.changeLockTimer`, it can silently extend the auto-lock window to an arbitrarily long duration up to `maxTtl` (default configuration commonly ~60 minutes, but configurable higher), or call `restartAutoLockTimer` repeatedly to keep the cached passphrase alive indefinitely. Combined with `#autoUnlock`, this means the wallet will keep re-unlocking itself using the cached passphrase without any further user interaction, directly weakening the "wallet locks after inactivity" security guarantee users rely on — a state change that, unlike a funds-moving action, has no user-visible signal and no delay to allow detection/reaction, mirroring the MarginSwap risk of a position becoming instantly liquidable with no forewarning.

### Likelihood Explanation
Likelihood depends on whether an untrusted caller (dApp page, malicious extension content script, or compromised background/UI channel) can reach the exposed `application`/`wallet` RPC namespace. The RPC/JSON-RPC layer as implemented exposes all methods flatly by name with no per-method authorization, so the likelihood is directly tied to how tightly the transport/channel is scoped to trusted processes in each Exodus product embedding — this scoping is enforced outside the code reviewed here and could not be fully verified with available context.

### Recommendation
- Require re-authentication (current passphrase or biometric) before accepting a `changeLockTimer` call that increases the TTL, and/or gate it behind an explicit user-confirmed UI action rather than a bare RPC call.
- Enforce a reasonable minimum/maximum TTL and rate-limit or add a short cooldown/timelock before a *lengthening* change to the auto-lock timer takes effect, so any unauthorized attempt to weaken the lock policy is not immediately live.
- Restrict which processes/origins may invoke `application.changeLockTimer` and `restartAutoLockTimer` over the RPC transport (origin/capability check at the RPC dispatch layer, not just at the UI).

### Proof of Concept
1. Obtain the ability to call methods on the RPC channel that fronts the `application` API (e.g., via the same transport used by `createBackgroundRpc`/`createUiRpc` in `libraries/browser-extension-rpc/src/index.js`, or any process holding a `createRPCClient` handle to the headless SDK).
2. Call `exodus.application.changeLockTimer({ ttl: <maxTtl> })` (or the deprecated `exodus.wallet.changeLockTimer`) — no passphrase, confirmation, or origin check is required per `features/application/src/api/index.ts:147-157` and `features/application/src/modules/passphrase-cache.ts:87-99`.
3. The auto-lock TTL is immediately updated and the passphrase-clear alarm rescheduled to the new (longer) TTL, per `#scheduleClear`/`changeTtl` in `features/application/src/modules/passphrase-cache.ts:40-48,87-99`.
4. As long as the cached passphrase remains valid under the new TTL, `#autoUnlock` in `features/application/src/modules/application.ts:387-407` will keep silently re-unlocking the wallet on app foreground/start, with no further user interaction — the wallet effectively stops auto-locking despite the user's original setting.

export const flattenObject = <T>(obj: T, path: string[] = []): { [name: string]: Fn } => {
  if (typeof obj === 'function') {
    return { [serializePath(path)]: obj as Fn }
  }

  }, {})
}
