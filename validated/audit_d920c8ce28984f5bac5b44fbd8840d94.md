### Title
Withdraw reverts and permanently freezes LP funds when redeemed token amount rounds to zero - (File: `program/src/processor.rs`)

### Summary
`process_withdraw` unconditionally reverts the entire transaction whenever either of the two computed underlying-token amounts (`coin_amount` or `pc_amount`) evaluates to zero, without any fallback path. Because the underlying pool ratio can be driven arbitrarily skewed through normal swap activity, a small LP holder's proportional share of one side of the pool can floor to zero for every possible withdrawal amount up to their full balance, permanently freezing their LP position with no way to ever redeem it.

### Finding Description
`process_withdraw` computes the coin/pc amounts to return for a given `withdraw.amount` of LP tokens using `InvariantPool::exchange_pool_to_token` with `RoundDirection::Floor`: [1](#0-0) 

Immediately afterward, the function requires both amounts to be non-zero, or it reverts the whole call with `AmmError::InvalidInput`: [2](#0-1) 

The underlying math is a simple floor-division proportional split: [3](#0-2) 

`coin_amount = floor(withdraw.amount * total_coin_without_take_pnl / amm.lp_amount)`. If a holder's LP balance `L` is small relative to `amm.lp_amount` and `total_coin_without_take_pnl` (the pool's coin reserve after pnl accounting) is also small, then `coin_amount` floors to `0` for every value of `withdraw.amount` up to and including the holder's entire balance `L` — there is no amount they can pick that yields a non-zero result. Since this check occurs unconditionally before the token transfer/burn logic, the holder's `withdraw` instruction will always fail, and their LP tokens can never be redeemed.

Crucially, `total_coin_without_take_pnl` (or the pc side, symmetrically) can be driven very low by an ordinary, unprivileged swapper simply performing large one-directional swaps. The swap instructions only forbid the *exact* full drain (`amount_out >= total_..._without_take_pnl`), so the reserve can be pushed down to a very small residual value: [4](#0-3) 

Once one side of the pool reserve is small enough, any LP holder whose share of that reserve rounds to zero is permanently unable to withdraw — this mirrors the reported bug class: an implicit assumption that a computed exit amount can never be zero, embedded as a hard `require`/revert with no error-handling or fallback, which bricks the affected account's ability to ever retrieve its funds.

### Impact Explanation
This freezes actual user-owned LP funds with no recovery path via the on-chain program: the affected liquidity provider can never redeem any coin/pc for their LP tokens through `Withdraw`, regardless of how much (or little) of their balance they specify, because every value floors to zero on at least one side. This is a permanent loss-of-access to real funds, satisfying the "permanent freezing of user or LP funds" criterion.

### Likelihood Explanation
This is reachable by fully unprivileged actors using only in-scope instructions: any swapper can lopsidedly drain one side of the pool through repeated ordinary swaps (`SwapBaseIn`/`SwapBaseOut`), and any small LP holder (or any holder once the ratio is skewed enough) is naturally exposed the moment their proportional share floors to zero. No privileged signer, special build, or off-chain component is required — a single attacker-controlled sequence of swap transactions followed by a withdraw attempt demonstrates the condition.

### Recommendation
Do not hard-revert the entire withdraw when one side floors to zero. Options include: (1) rounding up (ceiling) the smaller side so it is guaranteed non-zero if the LP amount burned is non-zero and adjusting accounting accordingly, (2) allowing a one-sided withdrawal path when the other side legitimately rounds to zero, or (3) enforcing a minimum LP-to-reserve ratio at deposit time so this degenerate state cannot arise. At minimum, provide an alternate code path so `withdraw.amount == user_source_lp.amount` (a full exit of the holder's position) cannot be blocked by this zero-rounding check.

### Proof of Concept
1. Pool starts with reserves `C` (coin) and `P` (pc) and total LP supply `LT`; a small LP holder owns `L` LP tokens such that `L * C / LT < 1` (achievable for a small holder or after `C` shrinks).
2. Attacker executes repeated `SwapBaseIn`/`SwapBaseOut` calls in the `Coin2PC` (or `PC2Coin`) direction, pushing `total_coin_without_take_pnl` (or pc) down toward its practical minimum while respecting the `amount_out < total_..._without_take_pnl` invariant check in `process_swap_base_in`/`process_swap_base_out`.
3. The small LP holder calls `Withdraw` with any `withdraw.amount` up to their full balance `L`.
4. `InvariantPool::exchange_pool_to_token` floors `coin_amount` to `0`.
5. `process_withdraw` hits the check at `program/src/processor.rs:1775-1777` and returns `AmmError::InvalidInput` for every possible `withdraw.amount` the holder can supply, permanently locking their LP tokens.

impl InvariantPool {
    /// Exchange rate
    pub fn exchange_pool_to_token(
        &self,
        token_total_amount: u64,
        round_direction: RoundDirection,
    ) -> Option<u64> {
        Some(if round_direction == RoundDirection::Floor {
            U128::from(token_total_amount)
                .checked_mul(self.token_input.into())
                .unwrap()
                .checked_div(self.token_total.into())
                .unwrap()
                .as_u64()
        } else {
            U128::from(token_total_amount)
                .checked_mul(self.token_input.into())
                .unwrap()
                .checked_ceil_div(self.token_total.into())
                .unwrap()
                .as_u64()
        })
    }
