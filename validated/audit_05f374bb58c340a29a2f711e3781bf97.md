Audit Report

## Title
Authenticated arbitrary command execution via `StandardCapabilities` job spec `command` field - (File: core/services/standardcapabilities/delegate.go)

## Summary
An authenticated user holding only the "Edit" role (not "Admin") can create a `standardcapabilities` job via the GraphQL `createJob` mutation with an arbitrary `command` string. This value is unvalidated beyond a non-empty check and is later passed directly into `exec.Command` when the job starts, allowing an Edit-role user to execute any binary/path reachable by the node process.

## Finding Description
`ValidatedStandardCapabilitiesSpec` only enforces that `Command` is non-empty: [1](#0-0) 

The value flows unmodified into `StandardCapabilities.Start`, which hands `s.command` to `plugins.CmdConfig{Cmd: s.command}` and ultimately `NewCmdFactory`: [2](#0-1) [3](#0-2) 

The delegate's own test explicitly documents that an unrecognized command string bypasses the capability-allowlist check entirely, since `GetCapabilityIDFromCommand` returns nothing to match against for unknown binaries: [4](#0-3) 

On the authorization side, the GraphQL `createJob` mutation is gated by `authenticateUserCanEdit`, which explicitly permits any role other than `View`/`Run` — i.e., it accepts `Edit` role, not just `Admin`: [5](#0-4) [6](#0-5) 

This confirms the exploit path: an Edit-role (non-Admin) authenticated session can submit a `standardcapabilities` TOML spec with `command = "/tmp/evil_binary"`, the spec passes validation, and when the job is started the node spawns that binary as a subprocess with the node's own privileges — no allowlist or path restriction stops it for unrecognized commands.

I was unable to confirm within available context whether the REST route `POST /v2/jobs` (`JobsController.Create`) enforces `Edit` or `Admin` role in `core/web/router.go`; the grep results returned only match counts without resolvable line content. However, the GraphQL path alone is sufficient to demonstrate the vulnerability, since it is independently confirmed to be reachable by Edit-role sessions.

## Impact Explanation
This is a genuine privilege escalation: Chainlink's RBAC model treats `Edit` as a lower tier than `Admin`, intended for configuring bridges/jobs — not raw code execution. Because the `standardcapabilities` job type's `command` field has no allowlist/path restriction for unrecognized binaries, an Edit-role user can achieve arbitrary command execution with the node process's privileges (access to keys, database, network). This maps to the in-scope impact category of "node API authentication or role bypass leading to unauthorized action" / command execution, matching the CVE-2020-26670 bug class cited in the report.

## Likelihood Explanation
Likelihood is high wherever Edit-role credentials exist and are distributed to less-trusted operators, which is an explicit, supported RBAC tier in Chainlink. No additional bypass is required beyond a single crafted GraphQL `createJob` mutation with a valid TOML spec — this is a normal, expected use of the exposed authenticated API, not a misconfiguration or host-level attack.

## Recommendation
- Require `Admin` role for creating/updating `standardcapabilities` job specs, since this job type grants effective code execution.
- Enforce a strict allowlist or fixed directory-based validation for `StandardCapabilitiesSpec.Command`, removing the "unknown command bypasses allowlist" behavior demonstrated in `delegate_test.go`.
- Validate `Command` resolves only to trusted, non-writable binaries within a controlled capabilities directory rather than trusting the LOOP registrar/allowlist to police it post hoc.

## Proof of Concept
1. Authenticate a GraphQL session as a user with role `edit` (not `admin`).
2. Submit:
```graphql
mutation {
  createJob(input: { TOML: "type = \"standardcapabilities\"\nschemaVersion = 1\nname = \"poc\"\nexternalJobID = \"<uuid>\"\nforwardingAllowed = false\ncommand = \"/tmp/evil_binary\"\nconfig = \"\"" }) {
    ... on CreateJobSuccess { job { id } }
  }
}
```
3. Confirm `authenticateUserCanEdit` allows the request to proceed (role check passes for `edit`), and that `ValidatedStandardCapabilitiesSpec` accepts the spec since `Command` is non-empty.
4. Start the job (automatically or via job start API) and observe `StandardCapabilities.Start` → `plugins.NewCmdFactory` → `exec.Command("/tmp/evil_binary")` spawning the attacker-controlled binary under the node process.

// NewCmdFactory is helper to ensure synchronization between the loop registry and os cmd to exec the LOOP
func NewCmdFactory(register func(id string) (*RegisteredLoop, error), lcfg CmdConfig) (func() *exec.Cmd, error) {
	registeredLoop, err := register(lcfg.ID)
	if err != nil {
		return nil, fmt.Errorf("failed to register %s LOOP plugin: %w", lcfg.ID, err)
	}
	return func() *exec.Cmd {
		cmd := exec.Command(lcfg.Cmd) //#nosec G204 -- we control the value of the cmd so the lint/sec error is a false positive
		cmd.Env = append(cmd.Env, lcfg.Env...)
		cmd.Env = append(cmd.Env, registeredLoop.EnvCfg.AsCmdEnv()...)
		return cmd
	}, nil
}

// Authenticates the user from the session cookie and asserts at least 'edit' role.
func authenticateUserCanEdit(ctx context.Context) error {
	session, ok := auth.GetGQLAuthenticatedSession(ctx)
	if !ok {
		return unauthorizedError{}
	}
	switch session.User.Role {
	case sessions.UserRoleView, sessions.UserRoleRun:
		return RoleNotPermittedError{session.User.Role}
	default:
	}
	return nil
}
