### Title
Predictable, unauthenticated session-cookie identifier enables cross-tenant session hijacking - (`lib/shopify_api/utils/session_utils.rb`)

### Finding Description
The broken binding: `SessionUtils.current_session_id(nil, cookies, online)` is expected to equal `session.id` **only when the caller has proven possession of the browser session that Shopify's OAuth flow issued**, i.e. `returned_id == session.id ⟺ requester authenticated via the Set-Cookie issued in `Oauth.validate_auth_callback``. In the non-embedded branch this equality is never checked.

Code path:
- `SessionUtils.current_session_id` (non-embedded branch) only checks that the cookie key exists, then returns the raw value verbatim: [1](#0-0) , via `cookie_session_id`: [2](#0-1) . There is no HMAC, JWT, or any other integrity check on the cookie value in this branch.
- For offline sessions, the value that ends up in this cookie is generated by `offline_session_id`, which is a pure deterministic function of the public shop domain — no secret material, no randomness: [3](#0-2) .
- That exact value is what gets written into the `Set-Cookie` payload after a legitimate OAuth callback: [4](#0-3) .
- The only cryptographic/state checks in the whole OAuth flow (`HmacValidator.validate`, the `state` cookie comparison) occur solely inside `validate_auth_callback` at the time the cookie is minted [5](#0-4) ; they are never re-checked when `current_session_id` reads the cookie back on a later request. `Context.setup?`, `.private?`, `.embedded?` only branch on app configuration and add no authentication to the cookie value itself.

Root cause: the gem uses a **predictable, non-secret string** (`"offline_" + shop_domain`) as both the session-storage lookup key and the entire "authentication" cookie value for non-embedded apps, and `current_session_id` trusts whatever string arrives in the `Cookie` header with zero verification that it was actually issued by this app's own `Set-Cookie` to this same browser session. Because myshopify.com shop domains are public/enumerable, an attacker who never received this cookie can construct it by hand and send it themselves via a raw HTTP request (e.g. `curl -H "Cookie: shopify_app_session=offline_<guessed-victim-shop>.myshopify.com"`). `current_session_id` returns that guessed id unmodified; if the host app follows the documented pattern of using this return value as a session-storage lookup key, the attacker's request is served with the victim shop's stored `Session`, including its `access_token`.

The existing unit test confirms the return-verbatim behavior with no verification call: [6](#0-5) .

### Impact Explanation
If the host app implements the documented pattern (load `Session` from storage by the id returned from `current_session_id`), a successful guess yields the victim merchant's stored offline `access_token`, enabling full cross-tenant API access as that merchant. This is repeatable against any shop domain the attacker can guess (shop names are often derivable from company names/branding and are enumerable), and does not require any credential, secret, or interaction with the victim. This matches the Critical category: theft of a merchant access token and cross-tenant access.

### Likelihood Explanation
Preconditions: the app must be non-embedded (or embedded falling back to cookie auth) and the host app must have a stored offline session for the guessed shop (i.e., that shop previously installed the app) and must use `current_session_id`'s return value directly as a session-storage key, as documented. Attacker cost is a single guessed/enumerated shop domain and one crafted HTTP request — no secrets, no privileged access, fully repeatable against arbitrary victims within the app's install base.

### Recommendation
Do not trust the raw session cookie value as an authenticated session key. Bind the cookie to an unguessable, high-entropy random token (not derived from the shop name) that is looked up server-side to resolve the real session id, and/or sign the cookie value (e.g., HMAC with `Context.api_secret_key`) so `current_session_id` can verify authenticity before returning it, mirroring the JWT verification already done in the embedded branch via `Auth::JwtPayload`.

### Proof of Concept
```ruby
# test/utils/session_utils_test.rb (new test)
def test_non_embedded_current_session_id_accepts_guessed_offline_id_with_no_verification
  ShopifyAPI::Context.stubs(:embedded?).returns(false)
  guessed_victim_shop = "victim-shop.myshopify.com"
  guessed_session_id = "offline_#{guessed_victim_shop}"
  cookies = { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => guessed_session_id }

  # No HMAC/JWT verifier should ever be invoked in this branch
  ShopifyAPI::Utils::HmacValidator.expects(:validate).never
  ShopifyAPI::Auth::JwtPayload.any_instance.expects(:shop).never

  result = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)

  assert_equal(guessed_session_id, result) # returned verbatim, unverified
end
```
This demonstrates that `current_session_id` returns the attacker-guessed id verbatim, with no HMAC/JWT verification method invoked, confirming the broken binding.
