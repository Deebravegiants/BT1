### Title
Stale stored `account.owner` lets the previous NFT owner keep full position control after transfer — (File: contracts/controller/src/account.rs)

### Summary
The controller records `Account.owner` once at account creation and never updates it. All fund-moving entrypoints authorize against that stale stored owner via `require_owner_or_delegate(env, account_id, caller, &account.owner)`, while only `renew_account`/`add_delegate`/`remove_delegate` check the live NFT owner via `require_account_owner`/`storage::account_owner`. After a `position-nft` `transfer`, the seller (and any delegate they registered) remains the recognized owner for `borrow`, `withdraw`, and every account-gated strategy, and can drain the collateral the buyer just acquired.

### Finding Description
- `create_account` writes `Account { owner, spoke_id, mode, .. }` once; the `owner` field is never rewritten on NFT transfer — there is no controller hook invoked by `position-nft` `transfer`/`approve`, and the external NFT surface in `contracts/controller/src/external/position_nft.rs` only exposes `nft_mint_call`, `nft_burn_call`, `nft_renew_call` (no owner-sync call). [1](#0-0) 
- `process_withdraw` and `process_borrow` load the account and call `require_owner_or_delegate(env, account_id, caller, &account.owner)`, which returns success whenever `caller == account.owner` — the *creation-time* owner, not the current NFT holder. Both also accept an arbitrary `to: Option<Address>` recipient. [2](#0-1) [3](#0-2) 
- `is_owner_or_delegate` also honors `Delegates(account_id, owner)` entries, so delegates the old owner granted keep authority after the sale too. [4](#0-3) 
- The codebase itself demonstrates the two notions are distinct: `require_account_owner` exists specifically to check `storage::account_owner` (the live NFT owner) for `renew_account` and delegate management, but that check is not used on any value-moving path. [5](#0-4) 
- `AccountGuard::Migrate`/`AccountGuard::Multiply` in `load_or_create_account` use the same stale `require_owner_or_delegate`, so `flash_position`, `multiply`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, and `migrate_from_blend` are equally reachable by the stale owner. [6](#0-5) 

### Impact Explanation
Theft of user funds. An attacker sells or transfers an account NFT to a victim, then calls `withdraw(caller=attacker, account_id, withdrawals, to=Some(attacker))` — authorization passes against the stale stored owner and pool cash is paid to the attacker. Alternatively, the attacker calls `borrow` up to the account's LTV with `to=attacker`, leaving the buyer holding max debt against collateral they thought they owned, or uses `repay_debt_with_collateral`/`swap_collateral` to the same effect. Post-operation solvency checks (`enforce_post_pool_solvency`) do not help: a borrow or withdraw that keeps HF ≥ 1.0 still passes, and even a liquidatable account transfers the loss to the buyer through the seized collateral/debt asymmetry.

### Likelihood Explanation
Fully unprivileged and single-transaction: the attacker only needs to have owned the account at some point (or to have been added as a delegate via `add_delegate` by a prior owner). NFT transfers are an in-scope, permissionless entrypoint of `position-nft`, and any OTC sale or secondary-market purchase of a position NFT inherits the exposure. No privileged action, oracle manipulation, or timing dependency is required — the stale `owner` field persists indefinitely until the account is emptied and burned. Likelihood is high wherever position NFTs change hands.

### Recommendation
Authorize fund-moving paths against the live NFT owner: replace `require_owner_or_delegate(env, account_id, caller, &account.owner)` in `process_borrow`, `process_withdraw`, `load_or_create_account` (Migrate/Multiply guards), and all strategy entrypoints with a check that resolves `storage::account_owner(env, account_id)` (NFT `owner_of`) and treats that as the owner for both the equality and `Delegates` lookups. Alternatively, make `position-nft` `transfer` call back into the controller to rewrite `Account.owner` and migrate/clear the `Delegates(account_id, old_owner)` set — but the read-live-owner approach is simpler and removes the stale-key class entirely.

### Proof of Concept
1. Alice calls `supply(caller=alice, account_id=0, spoke_id=1, [(hub_asset, X)])`, creating `account_id = N` with `Account.owner = alice` and collateral `X`.
2. Alice calls `position-nft.transfer(alice → bob, N)` (or sells `N` on a marketplace). `Account.owner` still equals `alice`; no controller code updates it.
3. Alice calls `withdraw(caller=alice, account_id=N, withdrawals=[(hub_asset, 0)], to=Some(alice))`. `require_owner_or_delegate` compares `caller == account.owner` → passes; the zero sentinel withdraws the full position and `pool_withdraw_call` pays `alice`.
4. Result: Bob owns an NFT pointing at an emptied account; Alice has stolen the collateral Bob paid for. The same works via `borrow` (leave debt) or by a previously registered `delegate` of Alice. The only mitigations in code are solvency checks, which a partial drain/borrow still satisfies.

*Uncertainty note:* I did not open `position-nft/src/contract.rs` to confirm `transfer` performs no controller callback; this conclusion rests on the absence of any owner-sync call in the controller's NFT interface (`external/position_nft.rs` exposes only mint/burn/renew) and on `Account.owner` being written exactly once at creation. If a transfer hook exists that rewrites `Account.owner`, the finding reduces to the narrower delegate-keyed variant.
