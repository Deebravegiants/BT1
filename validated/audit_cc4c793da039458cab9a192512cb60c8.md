## Title
Global `challengePeriod` update via `updateHostParams` retroactively re-applies to already-elapsed state commitments, blocking message delivery for previously deliverable requests/responses — ([File: evm/src/core/HandlerV2.sol])

### Summary
The reported Blueberry bug is a class of "global config parameter compared against a fixed per-instance timestamp, with the config later changed so that already-qualified instances are unfairly re-subjected to the full window." `EvmHost`'s challenge-period gate for message delivery has the same structural flaw: the delay check reads the *current* `HostParams.challengePeriod` and compares it to the timestamp when a specific state machine height's commitment was stored (`_stateCommitmentsUpdateTime`), rather than snapshotting the challenge period that applied at the time that commitment was accepted.

### Finding Description
`HandlerV2.handlePostRequests` (and the analogous get-response/timeout handlers) gate delivery on the challenge period: [1](#0-0) 

`challengePeriod()` simply returns the live, mutable value in `_hostParams`: [2](#0-1) 

That value can be changed at any time via `updateHostParams`/`updateHostParamsInternal`, which is reachable through cross-chain governance (the `hostManager`, itself an `IApp` invoked by an ISMP `onAccept` from Hyperbridge): [3](#0-2) [4](#0-3) 

Critically, `challengePeriod` is a single global value applied uniformly to **every** whitelisted state machine and **every** stored `StateMachineHeight`, and the update path performs no reconciliation against `_stateCommitmentsUpdateTime` entries already recorded for heights that have already exceeded the old (shorter) challenge period. The identical pattern exists on the Substrate/pallet-ismp side, where `verify_delay_passed` re-derives the pass/fail purely from the live `challenge_period(proof_height.id)` config and the stored `state_machine_update_time`: [5](#0-4) 

As a result: if a state-machine height's commitment was stored at time `T`, and at time `T + old_period` (with `old_period < current_challengePeriod`) it becomes eligible for delivery (relayers can now legally submit `handlePostRequests`/`handleGetResponses` proofs), but governance subsequently raises `challengePeriod` to a larger value before any relayer submits the proof, delivery is retroactively blocked again — the height must now wait until `T + new_period`, exactly mirroring the Blueberry bug where users who had already "passed" the fee window were forced to wait through a newly-restarted window.

### Impact Explanation
This directly matches the rules' accepted impact category "a route unable to deliver messages." A single governance-driven `updateHostParams` call (a legitimate, expected operational action — e.g., rotating the consensus client or admin, which also requires supplying `challengePeriod` in the same struct) can silently and retroactively extend the required wait for **every** pending, already-storable, not-yet-delivered request/response/timeout across every whitelisted state machine on that host — not just newly configured ones. Any post request, get response, or timeout whose underlying state commitment was stored close to (but past) the old challenge period becomes temporarily undeliverable, delaying user-funds-moving cross-chain messages (e.g., IntentGatewayV2 settlement/redeem messages, token bridge deliveries) system-wide until the new, longer period re-elapses. Because the check is baked into every handler path (`handlePostRequests`, get-response handling, timeout handling), this is a protocol-wide liveness regression triggered by a single innocuous parameter change, not an isolated app bug.

### Likelihood Explanation
Medium. `updateHostParams` requires the full `HostParams` struct to be re-supplied on every call (per `updateHostParamsInternal`'s field-by-field copy), so *any* legitimate governance update to unrelated fields (e.g. `consensusClient`, `admin`, `handler`) that also happens to raise `challengePeriod` — intentionally, to tighten security posture, or accidentally due to reusing a stale/incorrect params blob — will trigger this regression. This does not require malicious governance; it only requires a routine parameter change without careful reconciliation of already-in-flight state commitments, which the contract has no mechanism to detect or protect against.

### Recommendation
Snapshot the challenge period applicable to each `StateMachineHeight` at the time its commitment is stored (e.g., store it alongside `_stateCommitmentsUpdateTime` in `storeStateMachineCommitment`), and use that snapshotted value in `handlePostRequests`/`handleGetResponses`/timeout handlers instead of the live `challengePeriod()`. Apply the analogous fix in `modules/ismp/core/src/handlers.rs::verify_delay_passed` for the Substrate host, persisting the delay period at commitment-storage time rather than re-reading the current config.

### Proof of Concept
1. Host `H` has `challengePeriod = 1 hour`. At `T0`, a state commitment for `StateMachineHeight{id=X, height=100}` is stored via `HandlerV2` consensus proof handling, recording `_stateCommitmentsUpdateTime[X][100] = T0`.
2. At `T0 + 30 minutes`, relayer attempts `handlePostRequests` referencing this height — it reverts with `ChallengePeriodNotElapsed` (expected, since 30 min < 1 hour).
3. At `T0 + 90 minutes` (challenge period has legitimately elapsed), before the relayer submits the proof, governance calls `updateHostParams` to rotate `consensusClient` (a routine, unrelated operational change), re-supplying `challengePeriod = 7 days` in the same struct — per [3](#0-2) .
4. Relayer now calls `handlePostRequests` for height 100 at `T0 + 90 minutes`: `delay = 90 minutes`, `challengePeriod = 7 days` → `challengePeriod > delay` → reverts with `ChallengePeriodNotElapsed`, per [6](#0-5) , even though the height had already legitimately cleared its original challenge window.
5. Every other pending, already-elapsed height across every whitelisted state machine on `H` is now blocked for up to 7 days, regardless of how long ago it individually cleared the original 1-hour window.

pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}
