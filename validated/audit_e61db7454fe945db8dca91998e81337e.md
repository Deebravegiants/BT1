This confirms the vulnerability. The `to_signable_string` for `Webhooks::Request` returns only `@raw_body` [1](#0-0) , while the `shop`, `topic`, `api_version`, and `webhook_id` fields are read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only the HMAC over this signable string, then dispatches the handler using `request.shop` as the tenant identifier without any cross-check that the shop header matches the entity the signed body belongs to [3](#0-2) . The `HmacValidator.validate_signature` computation itself only covers `verifiable_query.to_signable_string` against the app's shared `api_secret_key` [4](#0-3) , which is the same secret across every shop that installs the app — this is the same class of "verified bytes vs. parsed/used bytes" gap as the reported missing association check.

### Title
Webhook HMAC Does Not Bind the `shop-domain` Header, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `HmacValidator` verifies the HMAC solely against that body using the app's single, shop-independent `api_secret_key`. The `shop-domain` header — which `Registry.process` trusts as the tenant identity when invoking the webhook handler — is never included in the signed material.

### Finding Description
`Request#to_signable_string` is defined as `@raw_body` [1](#0-0) . `HmacValidator.validate` computes an HMAC-SHA256 over that signable string using `Context.api_secret_key` and compares it to the `hmac` header via `OpenSSL.secure_compare` [5](#0-4) . Because `api_secret_key` is one value shared across every shop that has installed the app (it is not per-shop), a valid `(raw_body, hmac)` pair generated for one shop remains a cryptographically valid pair regardless of which `shop-domain` header accompanies it. `Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching, then builds `WebhookMetadata` using `request.shop`, `request.topic`, etc., which are read straight from attacker-controllable HTTP headers with no binding to the signed body [3](#0-2) . This is exactly the identity-binding break described in the prompt: "a field acted on but not covered by the HMAC" / "the shop authenticated versus the shop stored as a session key."

The equality that should hold but doesn't: `shop_bound_by_hmac == shop_used_by_handler`. In this code, `shop_bound_by_hmac` is undefined (the HMAC binds nothing about shop identity), while `shop_used_by_handler = request.shop` (an unauthenticated header).

### Impact Explanation
An attacker who legitimately installs the app on their own store (a normal, unprivileged action any merchant can take) can trigger a webhook delivery to the app's public webhook endpoint and thereby obtain a valid `(raw_body, hmac)` pair signed with the app's shared secret. Because the signature never covers the `shop-domain` header, the attacker can replay that exact body+HMAC to the app's endpoint while substituting an arbitrary victim shop domain in the `shop-domain` header. The signature check still passes, and the application processes attacker-controlled webhook data as if it originated from the victim's store — a cross-tenant data/state confusion. Depending on how the host application uses `WebhookMetadata#shop` (e.g., updating per-shop records, billing, inventory, or triggering shop-scoped side effects), this can lead to cross-tenant state corruption.

### Likelihood Explanation
Any user who can install the app on their own shop (a trivial, unprivileged action) can obtain a valid `(body, hmac)` pair without needing `api_secret_key`, an access token, or any credential leakage. The webhook endpoint is a public, unauthenticated HTTP endpoint by design, so nothing beyond forging headers on a replayed POST is required.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the HMAC-signable string for webhooks, or otherwise cryptographically bind the reported shop domain to the signed payload, so a signature valid for one shop cannot be replayed against another shop's identity.

### Proof of Concept
1. Install the target app on an attacker-owned development/trial store.
2. Trigger a webhook (e.g., `orders/create`) with attacker-controlled body content; capture the resulting `X-Shopify-Hmac-Sha256` and raw body sent by Shopify to the app's webhook endpoint.
3. Replay an HTTP POST directly to the app's public webhook endpoint using the identical raw body and `X-Shopify-Hmac-Sha256` header, but set `X-Shopify-Shop-Domain` to a victim shop's domain (and any desired `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
4. `HmacValidator.validate` succeeds because it only checks the body against the shared `api_secret_key` [6](#0-5) ; `Registry.process` dispatches the handler with `shop: request.shop` set to the victim's domain [3](#0-2) , causing the app to process attacker-supplied data under the victim shop's identity.
