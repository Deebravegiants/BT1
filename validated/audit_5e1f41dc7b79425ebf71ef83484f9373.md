### Title
Fee-on-Transfer Escrow Over-Crediting in Tron IntentGatewayV2.placeOrder - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron deployment of `IntentGatewayV2` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) credits escrow (`_orders[commitment][token]`) with the *nominal* requested input amount (minus protocol fee), rather than the amount the contract actually received via `safeTransferFrom`/predispatch sweep. For fee-on-transfer (deflationary) ERC-20 tokens, this decouples the accounting map from the contract's real token balance — precisely the same class of bug as the INVISTECH report, where taxed transfers caused the tracked/expected balance to diverge from the actual balance and let an attacker exploit the mismatch.

### Finding Description
In `placeOrder`, the non-predispatch branch does: [1](#0-0) 
It calls `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally credits `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` is derived purely from `order.inputs[i].amount` minus the protocol-fee bps — it is never checked against the gateway's actual token balance before/after the transfer.

The predispatch branch has the same flaw: it computes `balance = IERC20(token).balanceOf(dispatcher)` and sweeps `balance` from the dispatcher to the gateway, but still credits escrow with `reducedInputs[i].amount` (computed from the original nominal `order.inputs[i].amount`), not the amount actually landing in the gateway after the sweep transfer (which itself is subject to the token's transfer tax): [2](#0-1) 

This contrasts directly with the hardened EVM/SDK sibling contracts, which explicitly snapshot balances before and after each transfer and mutate `order.inputs[i].amount` to the *actual received* delta before computing the commitment and crediting escrow: [3](#0-2) [4](#0-3) 

The Tron variant lacks this balance-diff protection entirely, meaning any fee-on-transfer/deflationary ERC-20 token configured as an order input will cause `_orders[commitment][token]` to be credited with more tokens than the gateway actually holds for that order.

### Impact Explanation
Because escrow bookkeeping (`_orders`) is a shared mapping used later to release funds to solvers on fill or refund users on cancel/timeout, over-crediting it with more than the contract's true balance creates an accounting insolvency: the gateway's aggregate liabilities recorded in `_orders` across all orders can exceed its real token holdings. When solvers redeem escrow or users cancel, later claims can fail or drain balances backed by *other* users' escrowed tokens (unrelated orders using the same token), resulting in permanent freezing of funds for some order holders and/or theft-by-first-claimer dynamics — the same "phantom balance / manipulable accounting" root cause seen in the INVISTECH exploit, where the vulnerable contract's on-chain state didn't reflect actual token movement. This is reachable by any unprivileged user placing an order with an arbitrary ERC-20 input token (the taxed/deflationary token doesn't need protocol permission to be listed as an input), satisfying "concrete theft or permanent freezing of funds" from a single submitted transaction.

### Likelihood Explanation
Medium-High. Any user can call `placeOrder` with a fee-on-transfer token as an input with no allowlist gating token choice; nothing in `placeOrder` restricts input tokens to a vetted set. The attack requires only a widely-available deflationary/tax token (common on Tron/TRC20 ecosystems) and no privileged role, flash loans, or governance action — the same low-friction setup as the original INVISTECH bug class.

### Recommendation
Port the balance-snapshot pattern already implemented in `evm/src/apps/IntentGatewayV2.sol` (and `sdk/packages/core/contracts/apps/IntentGatewayV2.sol`) into `evm/tron/contracts/apps/IntentGatewayV2.sol`: measure `balanceOf(address(this))` before and after each `safeTransferFrom`/sweep call, mutate `order.inputs[i].amount` (and thus `reducedInputs[i].amount`) to the actual received delta, and only then compute the commitment hash and credit `_orders[commitment][token]`. Apply the same fix in the predispatch sweep branch by measuring gateway balance immediately before and after the transfer-call sweep rather than trusting `dispatcher.balanceOf` pre-transfer.

### Proof of Concept
1. Deploy/use a fee-on-transfer TRC20 token `T` with e.g. a 5% transfer tax (analogous to `FeeOnTransferToken` used in `IntentGatewayV2SameChainTest.sol`).
2. User calls `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs = [{token: T, amount: 1000}]` and `protocolFeeBps = 0`. [5](#0-4) 
3. `safeTransferFrom(user, gateway, 1000)` moves only 950 `T` into the gateway due to the 5% tax, but `_orders[commitment][T]` is credited with `reducedInputs[0].amount == 1000` (since `protocolFeeBps == 0`, `reducedInputs = order.inputs` unchanged).
4. Repeat with more orders using token `T`; the gateway's real `T` balance is consistently 5% short of the sum of all `_orders[...][T]` entries.
5. When solvers fill orders and redeem escrow (or users cancel/timeout and reclaim), the last claimants under-collateralized by the accumulated shortfall cannot be paid in full from the gateway's real `T` balance — reverting their transactions or requiring an earlier claimant to be paid using tokens that rightfully belong to a later order, freezing/stealing funds. (Full redemption/cancel code paths in this file were not fully retrievable within the tool-call budget; the `_orders` write pattern establishing the over-crediting is directly confirmed above from `placeOrder`.)
