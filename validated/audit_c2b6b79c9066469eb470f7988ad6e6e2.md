Confirmed: `MinWithdrawalAmountError` compares `args.amount < minWithdrawalAmount` as a plain bigint comparison (no `abs()` or clamping), so a negative or zero `actualAmount` is caught the same way as a below-min positive amount, since `minWithdrawalAmount` for real bridge tokens is a positive nonzero value.

### Analysis

**Claimed broken equality:** `sum(debits) == amount + (feeInclusive ? 0 : fee)` and `destination receives amount - (feeInclusive ? fee : 0)`, both non-negative, checked before signing.

**Trace:**
- In `createWithdrawalIntents` (`packages/intents-sdk/src/sdk.ts:342-344`), `actualAmount = feeInclusive ? amount - feeEstimation.amount : amount`. For `feeInclusive: false`, `actualAmount` equals the raw `amount` unmodified — no fee is ever subtracted from it here. [1](#0-0) 
- `bridge.validateWithdrawal` is invoked with `amount: actualAmount` **before** `bridge.createWithdrawalIntents` is called, so the min-amount check always runs first and blocks intent construction if it fails. [2](#0-1) 
- `PoaBridge.createWithdrawalIntents` builds the on-chain intent amount as `withdrawalParams.amount + relayerFee`, where `withdrawalParams.amount` is `actualAmount`. For `feeInclusive:false`, this means the total debited is `amount + relayerFee` (fee charged on top), and the amount that lands on the destination chain is `actualAmount = amount` — exactly what was validated against `min_withdrawal_amount`. [3](#0-2) 
- For `feeInclusive:true`, `actualAmount = amount - feeEstimation.amount`, and this is what gets validated via `MinWithdrawalAmountError` in `validateWithdrawal` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:221-230`) — critically, this check is a plain bigint comparison `args.amount < minWithdrawalAmount`, so it correctly rejects zero, negative, or below-min `actualAmount` as long as `minWithdrawalAmount > 0` (true for all real bridge tokens). [4](#0-3) 
- It is true that `createWithdrawalIntents` in `sdk.ts` lacks the explicit `FeeExceedsAmountError` guard that `_estimateWithdrawalFee` has (`packages/intents-sdk/src/sdk.ts:421-425`), so `actualAmount` could technically become zero or negative when `feeInclusive:true` and `feeEstimation.amount >= amount`. However, this doesn't bypass anything: the very next call, `bridge.validateWithdrawal`, still receives this negative/zero `actualAmount` and unconditionally throws `MinWithdrawalAmountError` before any intent is built, because `skipMinAmountValidation` defaults to `undefined`/falsy in `createWithdrawalIntents` (it's only set conditionally inside `_estimateWithdrawalFee`). [5](#0-4) 

**Both sides of the equality re-checked after the trace:** For `feeInclusive:false`, no fee subtraction ever touches `actualAmount`, so "below min after fee subtraction" doesn't apply — the destination amount checked equals the destination amount used to build the intent. For `feeInclusive:true`, the amount checked (`actualAmount = amount - fee`) is exactly the amount used to build the destination-facing intent, and any value below `min_withdrawal_amount` (including negative/zero) is caught by the plain bigint comparison in `validateWithdrawal`, which runs strictly before `bridge.createWithdrawalIntents` is invoked.

The missing `FeeExceedsAmountError` guard in `createWithdrawalIntents` is a real gap in defense-in-depth (a more descriptive error is skipped in favor of a generic `MinWithdrawalAmountError`), but it does not allow an under-minimum, zero, or negative amount to reach signing — the sequencing of `validateWithdrawal` before `createWithdrawalIntents` and the unconditional comparison in `MinWithdrawalAmountError` close that gap.
