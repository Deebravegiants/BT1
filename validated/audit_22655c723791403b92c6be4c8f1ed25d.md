### Title
Unchecked-length signature copy in BEEFY `Vote` → `SignatureWithAuthorityIndex` conversion causes a WASM trap from a single relayed consensus proof - ([File: evm/rust/src/conversions.rs])

### Summary
The FastNetMon CVE is a classic fixed-buffer overflow: attacker-controlled data of unvalidated length is copied into a fixed-size buffer via `sprintf`. The closest reachable analog in Hyperbridge is `From<Vote> for SignatureWithAuthorityIndex` in `evm/rust/src/conversions.rs:356-366`, which copies an ABI-decoded, attacker-controlled `bytes signature` field into a fixed `[u8; 65]` buffer with `copy_from_slice` and **no length check**, unlike every other analogous conversion in the codebase (which now explicitly guards against exactly this bug class).

### Finding Description
```rust
impl From<Vote> for SignatureWithAuthorityIndex {
    fn from(value: Vote) -> Self {
        let sig_bytes = value.signature.to_vec();
        let mut signature: TSignature = [0u8; 65];
        signature.copy_from_slice(&sig_bytes);   // panics if sig_bytes.len() != 65
        SignatureWithAuthorityIndex {
            signature,
            index: value.authorityIndex.try_into().expect("authority index out of bounds"),
        }
    }
}
``` [1](#0-0) 

`Vote.signature` originates from Solidity's dynamic `bytes` ABI type inside `BeefyConsensusProof` → `RelayChainProof` → `SignedCommitment.votes`, which is exactly the payload processed by the BEEFY consensus-proof pallet (`modules/pallets/beefy-consensus-proofs`), whose `Cargo.toml` pulls in `ismp-abi` with the `substrate` feature that compiles this `beefy` conversions module. Because Solidity ABI-decoding a `bytes` field does not enforce any particular length, an unprivileged relayer can submit a `Vote.signature` of any length (0, 1, 64, 66, …). `copy_from_slice` requires the source and destination slices to have equal length or it panics — there is no length check before the copy, unlike the sibling conversions in the same file (e.g. `RelayChainProof`, `BeefyConsensusProof`) that use `try_into().expect(...)` on scalar fields but still leave this particular byte-copy unguarded.

This is precisely the bug class the codebase's own authors have identified and fixed elsewhere as a production incident:
- `StateMachine::from_str` was hardened with explicit length checks before `copy_from_slice`, with the comment noting an unguarded version "is a wasm trap reachable from untrusted input... so the length is now checked up-front" [2](#0-1) .
- `as_utf8_string`'s deserializer was fixed after it "used to `copy_from_slice` straight from the input, which panics on any length mismatch — and it runs on untrusted RPC input (`consensus_state_id`), so the panic aborted the node's `rpc` worker thread and took the process down," citing `"CERE0"` as "the value that crashed the production node" [3](#0-2) .

The `Vote::signature` copy in `evm/rust/src/conversions.rs` was not covered by that hardening pass and remains vulnerable to the same class of unchecked fixed-buffer write from untrusted, attacker-controlled-length input.

### Impact Explanation
A malformed BEEFY consensus proof (an ordinary relayer-submitted extrinsic, not requiring any privilege) with a `Vote.signature` whose length is not exactly 65 bytes triggers a Rust panic inside runtime/pallet execution during consensus-proof verification. Depending on how the WASM executor handles the panic (`panic = "abort"` is standard for Substrate runtimes), this can trap the runtime call, halting processing of that consensus update and potentially destabilizing the node processing it — since consensus updates gate all subsequent message delivery for that state machine, this can degrade into "a route unable to deliver messages" for the affected consensus client until the runtime/relayer is patched.

### Likelihood Explanation
High: submitting a consensus proof is an ordinary, permissionless relayer action, and Solidity's ABI-encoded dynamic `bytes` type places no constraint on `signature` length, so any relayer (or anyone crafting a raw extrinsic) can trivially set it to a non-65-byte value.

### Recommendation
Add an explicit length check before the copy, mirroring the fix already applied to `StateMachine::from_str` and `as_utf8_string`:
```rust
let sig_bytes = value.signature.to_vec();
if sig_bytes.len() != 65 {
    return Err(/* proper error */);
}
let mut signature: TSignature = [0u8; 65];
signature.copy_from_slice(&sig_bytes);
```
Since `From` cannot fail, convert this to a fallible `TryFrom` and propagate the error through `RelayChainProof`'s conversion instead of panicking.

### Proof of Concept
1. Craft a `BeefyConsensusProof` where `relay.signedCommitment.votes[i].signature` is ABI-encoded as a `bytes` value of length ≠ 65 (e.g., 64 or 66 bytes) — trivial since ABI-encoding a `bytes` field does not enforce byte length.
2. Submit this proof via the consensus-proof submission extrinsic/RPC path handled by `modules/pallets/beefy-consensus-proofs`.
3. During conversion (`BeefyConsensusProof` → `ConsensusMessage` → `RelayChainProof` → `MmrProof` → `Vote::into::<SignatureWithAuthorityIndex>`), `copy_from_slice` panics because source/destination lengths differ, trapping the runtime call. [1](#0-0)
