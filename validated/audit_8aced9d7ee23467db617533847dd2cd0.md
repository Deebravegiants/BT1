### Title
Unrestricted `chain`/`app` targeting in bandwidth `purchase()` lets any buyer forcibly evict a victim app's paid subscriptions - ([File: modules/pallets/bandwidth/src/lib.rs])

### Summary
`pallet-bandwidth`'s subscription ledger is a per-`(app_chain, app)` FIFO list capped at `MAX_SUBSCRIPTIONS` (1024). Any unprivileged caller can invoke `BandwidthManager.purchase()` on any source chain and freely choose the `app` and `chain` fields that determine which `(app_chain, app)` bucket is credited — this is the documented "sponsorship" feature. Because the same push path evicts the oldest entry once a bucket is full, an attacker can flood a victim's bucket with the cheapest configured tier purchases to force-evict the victim's legitimately-purchased, still-unconsumed, higher-value subscriptions before they are drained, permanently destroying prepaid bandwidth the victim paid for. This mirrors the reported bug class: a queue/ledger mechanism intended to serve honest users can be forcibly and repeatedly triggered by any unprivileged party to grief a specific target, causing loss of paid-for resource.

### Finding Description
`push_subscription` unconditionally evicts the oldest subscription in a `(chain, app)` bucket once it reaches `MAX_SUBSCRIPTIONS` (1024), emitting `SubscriptionEvicted` with the lost bytes: [1](#0-0) 

This path is reached identically from a real purchase (`on_accept`) and from `force_credit`. Crucially, the `app_chain`/`app` pair credited by a purchase is taken entirely from the attacker-controlled message body, not from `request.source`: [2](#0-1) 

The docs confirm this is an intentional but unrestricted "sponsorship" design — any buyer on any chain can target any `(chain, app)` pair: [3](#0-2) 

Nothing in `on_accept`/`try_from` validates that the caller has any relationship to the `app` being credited, nor limits how many purchases one caller can direct at the same `(chain, app)` bucket in short order. An attacker who buys the cheapest tier (`TierOne`) 1024 times, targeting the victim's `(app_chain, app)` key, forces `push_subscription` to evict the victim's oldest live subscriptions — which may carry large, mostly-unconsumed `remaining_bytes` and long `expires_at` — one at a time, permanently destroying that prepaid capacity. The gate (`try_consume`) itself performs no compensating check; it drains strictly FIFO from what remains, so evicted subscriptions are simply gone (only logged via the `SubscriptionEvicted` event for post-hoc auditing).

This is structurally analogous to the external report: a shared, capacity-bounded queue mechanism (there: withdrawal queue triggered by exceeding a flow-rate threshold; here: a FIFO subscription list capped at 1024, evicted on overflow) that any unprivileged party can force into an adverse state against a specific victim, degrading or destroying the intended operation/benefit for that victim, using only their own funds and normal, unprivileged calls into the protocol.

### Impact Explanation
A successful attack permanently destroys a victim app's prepaid, unconsumed bandwidth allowance (`remaining_bytes` still live, not yet drained or expired) by evicting it from the FIFO list before the app can use it. Since `pallet-bandwidth` is the enforcement gate for all app dispatches on the ISMP router (`ProxyModule::on_accept` in both `gargantua` and `nexus` runtimes calls `try_consume` on every non-purchase request), destroying a victim's allowance can cause the victim's subsequent legitimate messages to be rejected with `GateError::Insufficient`/`NoAllowance`, i.e., a route becomes temporarily unable to deliver the victim's messages until they re-purchase, and the money already spent on the evicted subscription is permanently lost (a form of fund loss for the victim, since bandwidth was pre-paid and non-refundable). This satisfies "permanent freezing of funds" / "route unable to deliver messages" criteria.

### Likelihood Explanation
Likelihood is Medium: the attack is fully permissionless (no admin/governance privilege required — any address can call `purchase()` on any deployed `BandwidthManager`), reachable from a single class of transactions (repeated `purchase()` calls), and requires no special conditions on the victim's side. The main mitigating factor is cost: an attacker must fund 1024 purchases at the cheapest tier's price to evict a single victim subscription, and must repeat this to keep chasing new victim purchases, which the docs note "in practice only happens under pathological repeat-buy behavior." This raises the cost bar compared to the original report's flow-rate trigger, but for a sufficiently valuable target (e.g., an app that just bought a large, expensive, multi-month tier) the economics can still favor a griefer, especially since MAX_SUBSCRIPTIONS is a small, fixed global constant (1024) unrelated to per-app value.

### Recommendation
- Restrict `push_subscription`/purchase crediting so a subscription can only be evicted early by the same payer/manager pair that funded it, or introduce a value-based (not purely FIFO) eviction policy that never evicts a subscription with materially more remaining value than the one being pushed.
- Consider scoping or rate-limiting how many subscriptions a single source chain/manager can push into another `(chain, app)` bucket within a time window, so sponsorship cannot be abused to force eviction of a bucket's oldest, unrelated entries.
- Alternatively, raise `MAX_SUBSCRIPTIONS` per-app dynamically based on outstanding value, or track/refund evicted `remaining_bytes` value rather than silently discarding it.

### Proof of Concept
1. Victim app `A` purchases a large `TierFour` (8 MB, e.g., 12-month) subscription for `(app_chain, A)`, paying substantial fees; the subscription is inserted at `Allowance::<T>::mutate(app_chain, A, ...)`.
2. Attacker calls `BandwidthManager.purchase()` 1024 times on any registered source chain, each time setting `app = A` and `chain = app_chain` (the sponsorship fields), tier = the cheapest configured `TierOne`, `months = 1`.
3. Each purchase dispatches an ISMP POST to `pallet-bandwidth`; `on_accept` decodes it via `PurchaseMessage::try_from` (`modules/pallets/bandwidth/src/abi.rs`) with no ownership check on `app`/`chain`, and calls `push_subscription(app_chain, A, TierOne, ...)`.
4. Once the FIFO list for `(app_chain, A)` reaches 1024 entries, each subsequent attacker purchase evicts the oldest entry — eventually evicting victim `A`'s large `TierFour` subscription (still containing most of its 8 MB) before it is consumed, emitting `SubscriptionEvicted { app_chain, app: A, tier: TierFour, lost_bytes: <large> }`.
5. Victim `A` has permanently lost the paid-for, unconsumed bandwidth allowance, and if this was its only live subscription, `A`'s subsequent legitimate ISMP dispatches are rejected by `BandwidthGate::try_consume` until it re-purchases. [4](#0-3) [5](#0-4)

```rust
		) -> u64 {

			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});
```

```rust
impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;

		Self::deposit_event(Event::BandwidthConsumed {
			source: *source,
			app: key,
			bytes: need,
			remaining: total - need,
		});
		Ok(())
	}
}
```

```text
## Sponsorship

The purchase message carries its own `chain` (the _credit chain_) which is **independent of the source chain** that sent the message. This means a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`.

The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`. The event `BandwidthCredited` carries both — `app_chain` (where the credit lands) and `paid_from` (where the payment came from) — so the cross-chain payer is auditable.

This is what makes the system multi-tenant friendly: a treasury on a single chain can sponsor bandwidth for an app deployed across many chains, without having to deploy `BandwidthManager` on each chain the app lives on.
```

```rust
/// The 1024-sub cap evicts the oldest entry. force_credit reuses the
/// same push path as purchase, so this also covers the purchase cap.
#[test]
fn subscription_cap_evicts_oldest() {
	new_test_ext().execute_with(|| {
		jump_to(T0);
		let cap = MAX_SUBSCRIPTIONS as u128;

		// Fill the list to exactly the cap. `bytes` encodes the index
		// so we can prove which one got evicted.
		for i in 0..cap {
			Bandwidth::force_credit(
				RuntimeOrigin::root(),
				ForceCreditParams {
					app_chain: APP_CHAIN,
					app: app_key(),
					tier: TIER1,
					bytes: i + 1,
					duration_secs: MONTH_SECS,
				},
			)
			.unwrap();
		}
		assert_eq!(sub_count(APP_CHAIN), cap as usize);
		assert_eq!(sub_at(APP_CHAIN, 0).unwrap().remaining_bytes, 1, "oldest is index 1");

		// One more push: evicts the oldest, appends the new one.
		Bandwidth::force_credit(
			RuntimeOrigin::root(),
			ForceCreditParams {
				app_chain: APP_CHAIN,
				app: app_key(),
				tier: TIER1,
				bytes: cap + 1,
				duration_secs: MONTH_SECS,
			},
		)
		.unwrap();

		assert_eq!(sub_count(APP_CHAIN), cap as usize, "still capped");
		assert_eq!(
			sub_at(APP_CHAIN, 0).unwrap().remaining_bytes,
			2,
			"former second-oldest is now front",
		);
		assert_eq!(
			sub_at(APP_CHAIN, (cap - 1) as usize).unwrap().remaining_bytes,
			cap + 1,
			"new sub is at the back",
		);
	});
}
```
