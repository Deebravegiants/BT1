### Title
Webhook `shop-domain` header is trusted for tenant identification without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, but exposes a separate `shop` accessor that reads the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header. `Registry.process` verifies the HMAC and then hands `request.shop` straight to the host app's webhook handler as the tenant identifier, without that value ever being bound by the signature check.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  This is the only material that `HmacValidator.validate_signature` verifies against the computed HMAC: [2](#0-1) 

Separately, `Request#shop` is derived purely from the `shop-domain` header, which is never included in `to_signable_string` and therefore never covered by the HMAC: [3](#0-2)  The header-parsing logic in `initialize` only checks for the *presence* of `topic`, `hmac-sha256`, and `shop-domain` headers — it never ties their *values* to the signed payload: [4](#0-3) 

`Registry.process` validates the HMAC over the body, then immediately trusts `request.shop` as the tenant key passed to the app's handler: [5](#0-4) 

This breaks the intended identity binding: `hmac == HMAC(secret, raw_body)` should imply `shop == the tenant that produced raw_body`, but the equality actually enforced is only `hmac == HMAC(secret, raw_body)`; `shop` is an independent, attacker-controllable header value with no cryptographic tie to `raw_body` or to the `hmac` header.

### Impact Explanation
An unprivileged internet user who owns any development/test shop that is a legitimate webhook subscriber for the app can obtain a *validly signed* webhook (HMAC computed over their own shop's body). Because the `shop-domain` header is not part of the signed content, the attacker can replay that same signed body while substituting the `shopify-shop-domain` header of a **different, victim shop**. `Utils::HmacValidator.validate` will still pass (it only checks the body against the HMAC), and `Registry.process` will forward `WebhookMetadata.new(topic:, shop: request.shop, body:, ...)` with the victim's shop id to the app's handler. Any host application that uses `WebhookMetadata#shop` to look up per-tenant state (uninstall shop, redact shop data, update shop config, etc.) can be tricked into acting on the wrong tenant — a cross-tenant access/write primitive driven entirely by an unauthenticated header field, despite passing this gem's own HMAC check.

### Likelihood Explanation
The attacker only needs one HTTP request with a modified header and a body/HMAC pair they can legitimately obtain (their own shop's real webhook delivery, since HMAC secrets are per-app not per-shop, any shop installed under the app produces a validly-signed request usable for this substitution). No access token, `client_secret`, or privileged account is required — it only requires the ability to send an HTTP POST to the app's public webhook endpoint, which is unprivileged-internet-reachable by design.

### Recommendation
Include `shop` (and ideally `topic`, `webhook_id`, `api_version`) in the signable string used by `to_signable_string`, or otherwise cryptographically bind the `shop-domain` header value to the HMAC verification, so that `HmacValidator.validate` fails whenever the shop header does not match the shop that actually produced/signed the body.

### Proof of Concept
1. App is subscribed to a webhook topic for two shops: `attacker.myshopify.com` (attacker-controlled) and `victim.myshopify.com`.
2. Shopify sends the attacker a legitimately HMAC-signed webhook for `attacker.myshopify.com` with body `B` and header `X-Shopify-Hmac-Sha256: H` where `H = HMAC(secret, B)`.
3. Attacker replays the request to the app's webhook endpoint, keeping `body = B` and `X-Shopify-Hmac-Sha256 = H`, but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` in `hmac_validator.rb` recomputes the HMAC over `request.to_signable_string` (== `B`) and finds it matches `H` → returns `true`.
5. `Registry.process` (`webhooks/registry.rb` line 190-199) proceeds and calls the app's handler with `shop: "victim.myshopify.com"`, even though the actual signed payload came from the attacker's own shop.

```ruby
      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
```
