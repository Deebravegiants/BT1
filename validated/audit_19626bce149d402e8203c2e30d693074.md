### Title
Publicly scheduled governance parameter changes let any user take borrows/flash loans at stale, more favorable params immediately before permissionless execution - (File: contracts/governance/src/timelock/lifecycle.rs)

### Summary
All market risk and fee changes (e.g. `UpgradeLiquidityPoolParams` raising `flashloan_fee`/`reserve_factor`/rates, `EditAssetInSpoke` lowering `loan_to_value`/`liquidation_threshold`) go through the governance timelock. The pending operation's full payload is visible on-chain for the entire `min_delay` window, and once `Ready`, `execute` with `executor = None` is callable by anyone. A user can therefore observe the scheduled change and submit `flash_loan` / `flash_position` / `multiply` / `borrow` at the old parameters in the ledgers immediately before execution — the exact class as frontrunning `setDivisionFees()`, except here no mempool race is even needed because the change is announced on-chain in advance.

### Finding Description
- `flash::apply` computes the fee from the *current* stored params at call time: `terms(env, amount, cache.params().flashloan_fee, ...)`. [1](#0-0) 
- The same stale-param read exists for strategy fees: `compute_fee` uses `cache.params().flashloan_fee` for `flash_position`/`multiply`-style flows. [2](#0-1) 
- `propose` schedules the op with the full `AdminOperation` payload and returns a deterministic id; state and ready-ledger are publicly queryable via `get_operation_state` / `get_operation_ledger`. [3](#0-2) 
- `execute` marks the op executable once `delay` ledgers pass and imposes no executor restriction when `executor` is `None`. [4](#0-3) [5](#0-4) 
- Param updates are applied only when the op executes (`upgrade_liquidity_pool_params` → `pool_update_params_call`). [6](#0-5) 

So between `propose` and `execute` the protocol continues to serve `flash_loan`, `borrow`, and router strategies under the old `flashloan_fee`, `reserve_factor`, rate curve, LTV, and liquidation threshold — all known to be changing.

### Impact Explanation
- A user takes the maximum flash loan (or a `flash_position`/`multiply` strategy with `charge_fee`) the ledger before a fee-increase op executes: the pool books revenue at the old `flashloan_fee` instead of the new one — direct loss of unclaimed protocol revenue.
- A borrower seeing a scheduled `EditAssetInSpoke` that lowers `loan_to_value`/`liquidation_threshold` can open/max out borrows under the old risk params, leaving the position immediately closer to (or under) liquidation bounds once the op lands — increased insolvency risk borne by suppliers.
- A borrower seeing a scheduled rate-curve or `reserve_factor` increase borrows beforehand, locking principal minted under the cheaper regime (interest accrues forward, but the debt shares are minted at the old index and the protocol loses the intended fee/revenue capture on the transition block actions).

### Likelihood Explanation
- No mempool speculation required: the op payload, id, and ready ledger are public state; execution is permissionless. Any keeper or user can time a transaction into the last ledger(s) before (or even piggyback in the same ledger ordering as) the `execute` call.
- Requires only an unprivileged address calling `controller::flash_loan`, `borrow`, `flash_position`, `multiply`, or `governance::execute` — all in scope.
- Bounded by `MAX_FLASHLOAN_FEE_BPS` and market liquidity; magnitude scales with loan size, so the per-event profit can be material on large flash loans.

### Recommendation
- Treat parameter decreases/increases asymmetrically: apply fee and risk-parameter *tightenings* (higher `flashloan_fee`, `reserve_factor`, lower LTV/threshold) through a path that takes effect sooner, or add a short "effective ledger" embedded in the op so user actions in the gap are priced under the *new* params.
- Alternatively, when a param-change op is `Ready`, have the controller/pool read a "pending params" overlay for fee/risk-relevant fields, or let the proposer include an `effective_ledger` and have `terms`/`compute_fee` use `max(old_fee, pending_fee)` once the pending op is scheduled.
- At minimum, document that scheduled tightenings are griefable during the delay and have the executor bundle `execute` with a guardian `pause`/flag-tightening when the change is economically significant.

### Proof of Concept
1. Governance owner proposes `AdminOperation::UpgradeLiquidityPoolParams` raising `flashloan_fee` from 9 bps to 500 bps for hub asset `(hub_id, USDC)`. The op enters `Waiting`; `get_operation_ledger` exposes the exact ready ledger.
2. Attacker monitors state; when `get_operation_state` flips toward `Ready`, attacker calls `controller::flash_loan(hub_asset, attacker, receiver, cash_balance, data)` with a receiver contract that repays `amount + fee`.
3. `flash::apply` computes `fee = Bps(flashloan_fee).flash_loan_fee_on(amount)` using the still-stored 9 bps and books it via `book_fee` → `interest::add_protocol_revenue`. [7](#0-6) 
4. Next ledger, anyone calls `governance::execute(None, controller, "upgrade_liquidity_pool_params", args, predecessor, salt)`; the new 500 bps applies only to future loans.
5. Result: the protocol captured ~9 bps where ~500 bps was intended on a near-arbitrary-sized loan; equivalently, a borrower front-runs a scheduled `EditAssetInSpoke` LTV cut by calling `borrow` at the old `loan_to_value` one ledger before execution.

/// Computes fee and expected pool balances from the pre-loan token balance.
pub(crate) fn terms(env: &Env, amount: i128, fee_bps: u32, pre_balance: i128) -> FlashTerms {
    let fee = Bps::from(i128::from(fee_bps)).flash_loan_fee_on(env, amount);
    FlashTerms {
        fee,
        total_repayment: amount
            .checked_add(fee)
            .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow)),
        balance_after_payout: pre_balance
            .checked_sub(amount)
            .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow)),
        balance_after_repayment: pre_balance
            .checked_add(fee)
            .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow)),
    }
}

/// Credits cash and mints protocol revenue for the flash-loan fee.
pub(crate) fn book_fee(cache: &mut Cache, fee: i128) {
    let protocol_fee = Ray::from_asset(cache.env(), fee, cache.params().asset_decimals);
    interest::add_protocol_revenue(cache, protocol_fee);
    cache.credit_cash(fee);
}

fn compute_fee(env: &Env, cache: &Cache, amount: i128, charge_fee: bool) -> i128 {

        return 0;
