### Title
Meta-transaction (`DelegateAction`) sender can front-run and grief the relayer by invalidating the shared access-key nonce - (File: `runtime/runtime/src/actions.rs`)

### Summary
NEP-366 meta transactions let an account ("Alice") sign a `DelegateAction` off-chain and hand it to a relayer, who wraps it in a `SignedTransaction`, pays gas for it, and submits it on-chain — a NEAR analog of an ERC-4337 paymaster sponsoring a `UserOperation`. The `DelegateAction`'s validity is gated by the same access-key nonce field used for ordinary transactions signed with that key. Because the nonce check happens only when the relayer's receipt reaches the sender's shard — *after* the relayer has already paid the `SEND` gas cost for it — the sender can front-run their own sponsored meta-transaction with an ordinary self-submitted transaction on the same access key, bumping the nonce and causing the relayer-paid `DelegateAction` to fail with `DelegateActionInvalidNonce`, exactly mirroring the paymaster/`withdraw` nonce race in the source report.

### Finding Description
`DelegateAction` carries a `nonce: Nonce` field documented as sharing the counter of the given `public_key`'s access key: "Nonce to ensure that the same delegate action is not sent twice by a relayer and should match for given account's `public_key`" [1](#0-0) .

The relayer wraps the `SignedDelegateAction` inside its own transaction and pays the `SEND` gas cost for delivering it to the sender's shard immediately at transaction-to-receipt conversion time, before the delegate action itself is validated or executed [2](#0-1) .

The nonce is only checked later, when the receipt reaches the sender's ("Alice's") shard, in `validate_delegate_action_key`, which compares `delegate_nonce.nonce()` against the *current* stored nonce of the same access key and rejects it if the key's nonce has already advanced past it: [3](#0-2) 

That "current" nonce (`access_key.nonce`) is the exact same field advanced by ordinary transaction verification for that account/public_key pair via `verify_nonce`/`verify_and_charge_tx_ephemeral`: [4](#0-3) [5](#0-4) 

Because `NonceMode::Monotonic` only requires `tx_nonce > current_nonce` (not strict sequencing), the sender can submit any ordinary transaction — e.g., a trivial self-transfer — signed with the same access key used for the pending `DelegateAction`, using a nonce equal to or greater than the delegate nonce. If that ordinary transaction is processed first, `access_key.nonce` is bumped, and when the relayer's already-in-flight `DelegateAction` receipt later reaches the sender's shard, `validate_delegate_action_key` finds `delegate_nonce.nonce() <= current_nonce` and rejects it with `DelegateActionInvalidNonce` — at that point the relayer has already irrevocably paid the `SEND` gas fee for delivering the delegate action receipt (docs explicitly separate `SEND` fees, burnt immediately, from `EXEC` fees only burnt on execution start) [6](#0-5) .

This is the direct structural analog of the reported bug: one signature/nonce (the paymaster's `withdrawRequest.nonce`, here the access key's `Nonce`) authorizes two independently-triggerable paths (`validatePaymasterUserOp` vs. direct `withdraw`, here: relayer-submitted `DelegateAction` vs. an ordinary self-submitted transaction on the same key) that race on the same nonce, letting the account owner grief the entity that already committed gas.

### Impact Explanation
The relayer (the paymaster-equivalent, sponsoring gas on the user's behalf) irrevocably burns the `SEND` gas cost of relaying the `DelegateAction`, and possibly further wasted `EXEC`/compute for the delegate-action processing itself, whenever the sender front-runs its own meta transaction. There is no direct fund theft (the inner actions never double-execute, matching the judged "Medium, griefing only" outcome of the original report), but:
- A relayer can be repeatedly griefed by any account it agrees to sponsor, wasting NEAR gas with no revenue, which is directly analogous to a paymaster being drained/DoS'd by revert-triggering front-runs.
- This is documented as an acknowledged trust gap in the codebase's own architecture notes, which flag related nonce-sharing/trust issues for meta transactions but do not describe a mitigation for this specific self-front-run griefing vector [7](#0-6) .

### Likelihood Explanation
Any account that signs a `DelegateAction` for a relayer using a regular (non-gas-key) full-access or function-call access key, and that also independently holds enough balance to submit ordinary transactions on that same key, can perform this attack unilaterally and repeatably — no validator/node compromise, no special privileges, and no cooperation from any other party is required. It only requires racing two transactions to different destinations (the relayer's submission vs. the account's own submission) as in the original PoC.

### Recommendation
Do not let a `DelegateAction`'s nonce alias the account's general-purpose access-key nonce used by ordinary transactions signed with the same key. Options include: (a) maintaining a dedicated nonce/counter namespace for delegate actions per `(sender_id, public_key)` that is independent from the ordinary transaction nonce (similar in spirit to how gas-key nonces are already tracked in separate indexed rows, see `TransactionNonce::GasKeyNonce`/`set_gas_key_nonce`), or (b) requiring relayers to reserve/pre-check the nonce atomically with submission (e.g., via a short-lived on-chain lock or optimistic re-check) before burning `SEND` cost, so an intervening ordinary transaction on the same key cannot retroactively invalidate an already-paid-for delegate action.

### Proof of Concept
1. Alice creates a full-access key `K` with current `access_key.nonce = N0`.
2. Alice signs `DelegateAction { sender_id: Alice, nonce: N0+1, public_key: K, actions: [...] }` and hands it to Relayer.
3. Relayer wraps it into `SignedTransaction` and submits it; the `SEND` cost is burnt on inclusion, per `docs/architecture/how/meta-tx.md` step 2 [8](#0-7) .
4. Before the wrapped receipt reaches Alice's shard, Alice submits an ordinary `SignedTransaction` (e.g., a self-transfer) signed with `K` using nonce `N0+1` (or higher, satisfying `Monotonic` mode's `tx_nonce > current_nonce`), which is processed first and advances `access_key.nonce` to `N0+1`.
5. When the relayer's `DelegateAction` receipt later executes on Alice's shard, `validate_delegate_action_key` computes `delegate_nonce.nonce() (N0+1) <= current_nonce (N0+1)` → true, and rejects it with `ActionErrorKind::DelegateActionInvalidNonce` [9](#0-8) , while the relayer has already paid gas for delivering it.

/// Verify that the transaction nonce is valid.
fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }
    if let Some(height) = block_height {
        let upper_bound = height
            .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
        if tx_nonce >= upper_bound {
            return Err(InvalidTxError::NonceTooLarge { tx_nonce, upper_bound });
        }
    }
    Ok(())
}
