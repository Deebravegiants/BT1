### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that is read directly from the unauthenticated `shop-domain` HTTP header [1](#0-0) , but the HMAC signature that `Utils::HmacValidator` verifies is computed only over the raw request body, never over any header [2](#0-1) . `Registry.process` validates the HMAC and then trusts `request.shop` to identify the tenant when dispatching to the app's webhook handler [3](#0-2) . This breaks the intended identity binding: `shop_value_dispatched_to_handler == shop_value_that_produced_the_verified_HMAC` does not hold, because the `shop` value is never part of the signed material.

### Finding Description
`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the `hmac` field of the object [4](#0-3) . For webhooks, `to_signable_string` returns only `@raw_body` [2](#0-1) . Shopify's own webhook HMAC scheme signs the request body, but the "identity" of the tenant sending the webhook (the `shop-domain` header) is not itself authenticated by this gem — it is read verbatim from headers in `shop` [1](#0-0) .

`Registry.process` does:
1. `raise ... unless Utils::HmacValidator.validate(request)` — verifies only that `@raw_body` was signed by *some* valid Shopify secret owner (i.e., any shop with this app installed, since the same `client_secret`/signing key is shared across all webhooks for the app).
2. Immediately after, it builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` and hands it to the host app's handler, using the unauthenticated `shop` header value to identify which tenant the payload belongs to [3](#0-2) .

Because the `shop-domain` header is never part of the signed payload, a valid `(raw_body, hmac)` pair captured from a genuine webhook delivery to *any* shop that has the app installed (e.g., the attacker's own test/development store, which is a legitimate, credential-free way to obtain a validly-signed webhook) can be replayed to the app's webhook endpoint with the `shop-domain` header swapped to a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` because it only checks `@raw_body`, and the handler receives `shop: <victim-domain>` together with attacker-controlled body content, causing the host app to attribute (and potentially persist/act upon) attacker-controlled data as belonging to a different tenant.

### Impact Explanation
This matches the "Critical – cross-tenant access" impact category: an unprivileged actor who legitimately installs the app on a shop they control can forge webhook deliveries that the app will process as if they came from an unrelated victim shop, without ever possessing the app's `client_secret` or the victim's credentials. This can be used to inject attacker-controlled data (order/customer/product payloads, etc.) into whatever tenant-scoped processing/storage the host app performs keyed off `WebhookMetadata#shop`.

### Likelihood Explanation
Medium-to-High: it only requires the attacker to install the app on a shop they control (a normal, allowed action for any Shopify app), capture one real webhook delivery (HMAC + body), and replay it to the app's public webhook endpoint with a modified `shop-domain` header. No secret material, token theft, or privileged access is required.

### Recommendation
Bind the `shop` identity into the value that is cryptographically verified, e.g. include the `shop-domain` (and other trust-relevant headers such as `webhook-id`/`api-version`) in `Request#to_signable_string`, or otherwise require the host application/gem to cross-check the header-derived `shop` against a shop value independently recoverable from the verified body/session before dispatching to `WebhookHandler#handle`. At minimum, document that `request.shop` is unauthenticated and must not be used as a tenant-identity boundary without additional verification.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` (a shop the attacker legitimately controls) and trigger a webhook (e.g. `orders/create`) so Shopify sends a real request with a valid `X-Shopify-Hmac-Sha256` header, computed over the raw body using the app's shared secret.
2. Capture the raw body and HMAC header from that legitimate delivery.
3. Resend the identical raw body and HMAC header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `@raw_body` against the secret [5](#0-4) ; `Registry.process` then calls the handler with `shop: "victim-shop.myshopify.com"` [6](#0-5) , causing the host app to process attacker-controlled webhook content under the victim tenant's identity.
