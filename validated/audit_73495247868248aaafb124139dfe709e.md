### Title
Password Change Fails to Revoke Existing API Bearer Tokens, Allowing Persistent Account Access - ([File: core/web/user_controller.go])

### Summary
Chainlink's password-change flow (`UserController.UpdatePassword` / GraphQL `UpdateUserPassword`) only revokes cookie-based sessions on password change; it never invalidates the user's existing API bearer token (`X-API-KEY`/`X-API-SECRET` pair). This mirrors the Flarum CVE-2026-39924 root cause: a credential-revocation action (password change) that is assumed by users/operators to "kick out" any attacker, but leaves a separate long-lived credential (Flarum's `access_tokens`/`RememberAccessToken`, here the node's API token) fully valid.

### Finding Description
The `AuthenticationProvider` interface exposes two independent revocation primitives: `ClearNonCurrentSessions` (cookie sessions) and `DeleteAuthToken` (API token) [1](#0-0) .

The password-change handler only calls the former: [2](#0-1) 

The GraphQL mutation resolver has the identical gap — it calls `ClearNonCurrentSessions` then `SetPassword`, never `DeleteAuthToken`: [3](#0-2) 

The API token itself is a long-lived, separately-stored credential (`token_key`/`token_hashed_secret` columns), only removed via the dedicated `DeleteAuthToken` ORM method, which is exclusively invoked from the explicit `DeleteAPIToken` controller action — never from the password-change path: [4](#0-3) 

The CLI's own change-password prompt tells the operator "This will terminate any other sessions," reinforcing the (false) assumption that the API credential is also invalidated: [5](#0-4) 

Because `AuthenticateByToken` validates requests solely against the stored `token_key`/`token_hashed_secret`, independent of the user's password/session state, a token issued before the password change continues to authenticate successfully after the change: [6](#0-5) 

This is the direct chainlink analog of the Flarum bug class: an incident-response action intended to revoke attacker access (password change) fails to clear one class of standing credential (the access token), letting the attacker retain full API access to the node indefinitely.

### Impact Explanation
If a user's API token is leaked/compromised (e.g., via log exposure, phishing, CI misconfiguration, or client-side leakage) and the user responds by changing their account password — the standard remediation step — the attacker's stolen `X-API-KEY`/`X-API-SECRET` pair remains valid. The attacker retains full API access at the victim's role level (potentially `admin`), including bridge management, job management, and other sensitive node operations, until the victim separately and explicitly rotates the API token via `NewAPIToken`/`DeleteAPIToken` — a step most users would not know is necessary since password change is believed to "terminate any other sessions."

### Likelihood Explanation
Any authenticated node user with an API token who has that token compromised, and who follows the natural/documented incident-response step of changing their password, is affected. No special privileges or race conditions are required — this is a straightforward logic gap in the revocation flow reachable by every account holder.

### Recommendation
Call `orm.DeleteAuthToken(ctx, user)` (or equivalent token invalidation) alongside `ClearNonCurrentSessions` in both `UserController.updateUserPassword` (`core/web/user_controller.go`) and the GraphQL `UpdateUserPassword` resolver (`core/web/resolver/mutation.go`), so that password change revokes both session cookies and the API bearer token. Alternatively, at minimum, surface a clear warning/audit event that the API token remains active and must be separately rotated.

### Proof of Concept
1. User creates an API token via `POST /v2/user/token` (`NewAPIToken`), obtaining `AccessKey`/`Secret`.
2. Attacker obtains this token (e.g., via log leak) and authenticates to the API using `X-API-KEY`/`X-API-SECRET` headers, confirmed via `AuthenticateByToken`.
3. Victim, suspecting compromise, changes their password via `PATCH /v2/user/password` (`UserController.UpdatePassword`) or the `updateUserPassword` GraphQL mutation.
4. `updateUserPassword`/`updateUserPassword` internally calls `ClearNonCurrentSessions` (revokes other session cookies) and `SetPassword` (rotates password hash) — but never `DeleteAuthToken`.
5. Attacker re-issues the same API request with the original, unchanged `X-API-KEY`/`X-API-SECRET`; the request still succeeds because `FindUserByAPIToken`/`AuthenticateUserByToken` check only the unmodified token fields, independent of the password change.

```go
func (u *UserController) updateUserPassword(c *gin.Context, user *clsession.User, newPassword string) error {
	ctx := c.Request.Context()
	sessionID, err := getCurrentSessionID(c)
	if err != nil {
		return err
	}
	orm := u.App.AuthenticationProvider()
	if err := orm.ClearNonCurrentSessions(ctx, sessionID); err != nil {
		u.App.GetLogger().Errorf("failed to clear non current user sessions: %s", err)
		return errors.New("unable to update password")
	}
	if err := orm.SetPassword(ctx, user, newPassword); err != nil {
		if errors.Is(err, clsession.ErrNotSupported) {
			return errUnsupportedForAuth
		}
		u.App.GetLogger().Errorf("failed to update current user password: %s", err)
		return errors.New("unable to update password")
	}
	return nil
```

```go
func AuthenticateByToken(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	token := &auth.Token{
		AccessKey: c.GetHeader(APIKey),
		Secret:    c.GetHeader(APISecret),
	}
	if token.AccessKey == "" {
		return auth.ErrorAuthFailed
	}

	if token.Secret == "" {
		return auth.ErrorAuthFailed
	}

	// We need to first load the user row so we can compare tokens using the stored salt
	user, err := authr.FindUserByAPIToken(ctx, token.AccessKey)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) || errors.Is(err, clsessions.ErrUserSessionExpired) {
			return auth.ErrorAuthFailed
		}
		return err
	}

	ok, err := clsessions.AuthenticateUserByToken(token, &user)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionUserKey, &user)

	return nil
}
```
