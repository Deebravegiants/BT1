Audit Report

## Title
Legacy gateway user message handler allows request-ID collision to hijack or deny another user's saved callback - ([File: core/services/gateway/handlers/capabilities/handler.go])

## Summary
`HandleLegacyUserMessage` stores an in-flight callback keyed only by the caller-supplied `msg.Body.MessageID` via an unconditional map write, with no check for an existing, unexpired entry. An unprivileged attacker who sends a legacy request reusing another still-pending request's `MessageID` silently overwrites that entry in `savedCallbacks`, causing the DON's eventual response to be delivered to the attacker instead of the original caller, who instead times out.

## Finding Description
`ProcessRequest` in `core/services/gateway/gateway.go` validates an incoming legacy `Message` via `msg.Validate()` and then calls `h.HandleLegacyUserMessage(ctx, msg, callback)` [3](#0-2) . `Validate()` checks only that `MessageID` is 1–128 bytes and doesn't end in a null byte, plus verifies the ECDSA signature to derive `Sender`—it enforces nothing about ID uniqueness or unpredictability [4](#0-3) . Critically, the signature only proves who signed the message; it places no constraint on what `MessageID` value the signer chooses, so any signer (any legitimate DON participant with signing capability) can pick an ID equal to another in-flight request's ID.

In `HandleLegacyUserMessage`, the pending callback is inserted with a bare map write and no existence check:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageID] = &savedCallback{id: msg.Body.MessageID, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [1](#0-0) 

Later, when a DON node's response arrives, `handleWebAPITriggerMessage` looks up and deletes the callback purely by `MessageID` and forwards the payload to whichever callback is currently registered: [5](#0-4) 

Because the lookup key has no binding to the original `Sender`, a second request with a colliding `MessageID` overwrites the first entry, and the DON's response is delivered to the second (attacker's) caller while the first caller's `callback.Wait(ctx)` in `ProcessRequest` eventually times out [6](#0-5) . The newer v2 `httpTriggerHandler.setupCallback` explicitly rejects a request whose ID is already in-flight, confirming this omission in the legacy handler is a genuine gap rather than intended behavior.

## Impact Explanation
This is a cross-user response corruption / denial-of-service bug reachable by any external, unprivileged caller of the gateway's legacy `/user`-style JSON-RPC endpoint: they can (1) deny another legitimate requester their response by forcing a timeout, and (2) potentially receive a response payload intended for another user's request if the `MessageID`s collide. This falls into the in-scope "gateway request impersonation / cross-user response corruption" impact category.

## Likelihood Explanation
Exploitability requires the attacker to guess or learn a victim's in-flight `MessageID` within the `CallbackMaxAgeSec` window (default 120s) and to be able to produce a validly signed message (any registered signer/workflow owner can craft an arbitrary `MessageID`, since `Validate()` places no constraint on it beyond length/null-byte checks). If `MessageID`s are client-chosen, predictable, sequential, or otherwise observable (e.g., echoed in logs or client apps), the attack is straightforward and repeatable at essentially no cost; if IDs are always high-entropy random values never exposed before completion, the practical likelihood is lower, but the protocol itself provides no defense-in-depth against collision, unlike the v2 handler.

## Recommendation
In `HandleLegacyUserMessage` (core/services/gateway/handlers/capabilities/handler.go), before inserting into `savedCallbacks`, check under the same lock for an existing, non-expired entry keyed by `msg.Body.MessageID` and reject the new request (e.g., respond with a conflict error) instead of overwriting it, mirroring the guard already present in `httpTriggerHandler.setupCallback` (core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go).

## Proof of Concept
1. Caller A sends a validly signed legacy `Message` with `Body.MessageID = "shared-id"` and `Body.Method = "web_api_trigger"` to the gateway; `HandleLegacyUserMessage` stores `savedCallbacks["shared-id"] = <A's callback>` and forwards the request to all DON members [7](#0-6) .
2. Before any DON member responds, caller B sends their own validly signed legacy `Message` also with `Body.MessageID = "shared-id"`; this overwrites `savedCallbacks["shared-id"]` with B's callback.
3. When a DON member later responds with `Body.MessageID == "shared-id"`, `handleWebAPITriggerMessage` looks up and delivers the response to whichever callback is currently stored (B's), while A's original HTTP request in `ProcessRequest` times out via `callback.Wait(ctx)` [5](#0-4) .
4. This can be encoded as a Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go` that calls `HandleLegacyUserMessage` twice with the same `MessageID` and two distinct callbacks, then asserts that `h.savedCallbacks[id]` refers to the second callback and that invoking `handleWebAPITriggerMessage` delivers the response only to the second (attacker) callback.
