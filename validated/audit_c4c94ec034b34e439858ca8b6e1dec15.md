This confirms the vulnerability path. The gem explicitly documents `data.shop` as "the shop domain of the webhook" — an authenticated tenant identifier — intended for host apps to key lookups on (as shown in the doc's own example: `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), yet this value is never covered by the HMAC signature computed in `ShopifyAPI::Webhooks::Request`.

### Title
Webhook `shop` identifier is not covered by HMAC, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC over the raw request body, but the `shop` field that the gem hands to the app's `WebhookHandler` as the authenticated tenant identifier is read from an HTTP header that is excluded from the signed content. Any party able to submit an HTTP request to the app's webhook endpoint can therefore keep a valid `(body, hmac)` pair while substituting an arbitrary `x-shopify-shop-domain` header, causing the gem to report a different, attacker-chosen tenant to the handler while the HMAC check still passes.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, and `to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, independent of the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC of the body via `Utils::HmacValidator.validate(request)`, then immediately forwards `request.shop` to the handler as the trusted tenant identifier, with no cross-check that the signed body actually corresponds to that shop: [3](#0-2) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (i.e., the body only) and compares it with `OpenSSL.secure_compare`: [4](#0-3) 

This breaks the equality the gem implicitly asserts to the host application: `shop authenticated-by-HMAC == shop delivered to handler`. In reality, `shop` is attacker-controllable header data that rides alongside an HMAC that never covers it. The gem's own documentation instructs developers to key application data (e.g., job queues, `shop_domain:`) directly off `data.shop`: [5](#0-4) 

so a mismatch here directly produces cross-tenant data confusion in any host app that follows this documented usage.

### Impact Explanation
An unprivileged internet user who can capture (or is himself the recipient of, e.g. by installing the app on his own shop) any single legitimate `(raw_body, hmac)` pair delivered by Shopify to the app's public webhook endpoint can replay that exact request with the `x-shopify-shop-domain` header changed to a victim shop's domain. `Registry.process` will still validate the HMAC (it only checks the body) and will pass `shop: <victim-shop>` to the handler alongside the attacker's own body content. Any host app relying on the gem's documented pattern of trusting `data.shop` as the authenticated tenant (e.g., to look up the session/store record to update, to route/queue work per-store, or to write data associated with that shop) will process attacker-supplied data under the wrong tenant's identity — a cross-tenant integrity/confidentiality violation.

### Likelihood Explanation
Likelihood is limited by the need for the attacker to first obtain a valid `(body, hmac)` pair, which is trivially achievable by installing the app on the attacker's own (unprivileged) shop and observing the webhook delivery Shopify sends to the public endpoint — no `api_secret_key`, access token, or leaked credential is required. The endpoint is public HTTP infrastructure by design (the whole purpose of webhook delivery). This makes the analog realistically reachable by any unprivileged internet user who has installed, or can install, the app.

### Recommendation
Bind the `shop` (and ideally `topic`/`api_version`) header values into the HMAC-signed content, or otherwise cryptographically tie the asserted `shop` to the verified body (e.g., include the shop domain as part of `to_signable_string`, or require the caller to separately validate `shop` against a known/allow-listed value before trusting it). At minimum, document prominently that `data.shop` is unauthenticated header data and must not be trusted as a tenant boundary without additional verification.

### Proof of Concept
1. Install the app on attacker-owned shop `attacker.myshopify.com`; capture the legitimate webhook POST Shopify sends, including its `raw_body` and `x-shopify-hmac-sha256` header — both fully valid.
2. Replay the exact same HTTP request to the app's webhook endpoint, changing only `x-shopify-shop-domain` (and/or `shopify-shop-domain`) from `attacker.myshopify.com` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the secret, per [1](#0-0)  and [4](#0-3) .
4. The handler is invoked with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker-controlled body>, ...)`, per [6](#0-5) , causing the host app to process attacker data under the victim's tenant identity.
