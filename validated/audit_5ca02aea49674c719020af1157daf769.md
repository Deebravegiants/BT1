Based on my review of the webhook authentication flow, I found a genuine identity-binding gap.

### Title
Webhook HMAC Does Not Cover the `shop-domain` Header, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The HMAC signature Shopify sends with webhooks is verified only against the raw request body. The `shop-domain` header — the field the library uses to identify which merchant/tenant the webhook belongs to — is never included in the signed data. An attacker who legitimately receives one authentic `(body, hmac)` pair (e.g. by installing the app on their own store) can replay that exact body and signature to the app's webhook endpoint while substituting an arbitrary `shop-domain` header, and the library will accept it as authentic for the spoofed shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely outside the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` verifies `computed_signature` against `verifiable_query.to_signable_string`, i.e. the body only: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC and then trusts `request.shop` (the unauthenticated header) to build `WebhookMetadata`, which is handed to the app's handler as the tenant identity for the event: [4](#0-3) 

The identity binding this breaks, stated as an equality that should hold but doesn't:
`shop_covered_by_hmac == shop_used_by_handler` — in this code, `shop_covered_by_hmac` is undefined (the signature covers only the body), while `shop_used_by_handler = request.shop` (an unauthenticated header). Because the signature is independent of the shop header, any `(body, hmac)` pair valid for shop A remains valid when replayed with the `shop-domain` header rewritten to shop B.

### Impact Explanation
This is a cross-tenant confusion vector: an attacker who can obtain one authentic webhook delivery for a shop they control (trivial — install the app on their own store and trigger any webhook topic) can capture the exact `raw_body` and `hmac` header. They can then send that identical body+hmac to the app's public webhook endpoint with the `shop-domain` header changed to a victim shop. `Utils::HmacValidator.validate` still passes (since only the body is checked), and `WebhookMetadata#shop` reports the attacker-chosen victim domain to the host application's handler. Any downstream logic that trusts `data.shop` to select per-tenant credentials, session storage keys, or to perform per-tenant side effects (order fulfillment, inventory updates, GDPR data actions, etc.) will act as though the event originated from the victim's shop, constituting cross-tenant access/confusion.

### Likelihood Explanation
Requires only an app installed by the attacker on any shop (including a free/dev store), which is realistic for most public Shopify apps, plus knowledge of the public webhook endpoint URL (typically discoverable from the app or docs). No secrets, tokens, or privileged access are needed — this is reachable by an unprivileged internet user.

### Recommendation
Bind the `shop` (and ideally `topic`) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived shop to the verified body — e.g., by having `Registry.process` cross-check `request.shop` against a shop that is independently known to be associated with a valid, previously-registered webhook subscription/session for that exact merchant before invoking the handler, rather than trusting the raw header value as the tenant identity solely because the body's HMAC checks out.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`).
2. Attacker captures the raw POST body and the `X-Shopify-Hmac-Sha256` header value from that delivery (both are visible to the receiving endpoint, and can be replayed by the attacker directly since they control the delivery target for their own store, or observe it via their own logging).
3. Attacker sends a new POST request to the app's webhook endpoint with the identical body and `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks the body/hmac pair [3](#0-2) .
5. `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)` [5](#0-4) , causing the host app to act on data intended to represent `attacker.myshopify.com`'s event but attributed to `victim.myshopify.com`.
