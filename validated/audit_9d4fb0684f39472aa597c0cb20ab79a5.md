### Title
Excess native ETH sent to `EvmHost.dispatch()`/`fundRequest()` for fee-token swaps is permanently trapped in the host contract - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` accept `msg.value` and swap it via `IUniswapV2Router02.swapETHForExactTokens` to obtain the exact `feeToken` amount needed for the relayer fee. Any ETH refund that the canonical Uniswap V2 Router returns for unspent input (`msg.value > amountIn`) is sent back to `msg.sender` of the router call, which is the `EvmHost` contract itself — not the original user who called `dispatch`/`fundRequest`. Unlike the analogous `IntentGatewayV2.placeOrder` flow, which explicitly tracks `msgValue -= amounts[0]` and forwards the leftover back to `msg.sender` via `_sendValue`, `EvmHost` has no such refund-forwarding logic.

### Finding Description
In `EvmHost.dispatch(DispatchPost memory post)`: [1](#0-0) 

and identically in `dispatch(DispatchGet memory get)`: [2](#0-1) 

and in `fundRequest`: [3](#0-2) 

each of these calls `swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` with the *entire* `msg.value` as the maximum input, requesting only the exact `fee` output amount. The real Uniswap V2 Router's `swapETHForExactTokens` implementation only pulls in the amount actually required by the swap path and refunds the difference (`msg.value - amounts[0]`) via `TransferHelper.safeTransferETH(msg.sender, ...)`, where `msg.sender` from the router's perspective is `EvmHost` (the caller), not the end user. `EvmHost` never captures or forwards this refund to `_msgSender()`/`post.payer`; there is no `_sendValue`-style refund path as exists in `IntentGatewayV2.placeOrder` (which does perform `msgValue -= amounts[0]` and refunds the caller): [4](#0-3) 

Since `EvmHost`'s deployment ABI has no dedicated "refund" accounting and the contract's only outward-facing ETH exit is the governance-gated `withdraw()` (callable solely by `hostManager` cross-chain governance), the refunded ETH becomes indistinguishable dApp-wide "donated" balance sitting on the host, permanently unrecoverable by the paying user: [5](#0-4) 

Any unprivileged caller of `dispatch()`/`fundRequest()` who overestimates the native amount required (which is expected behavior, since `quote()` is explicitly documented as an approximate off-chain estimate subject to slippage) will have the surplus permanently locked in the contract rather than refunded — this is a straightforward asset freezing bug reachable by any user of the public `dispatch`/`fundRequest` entry points.

### Impact Explanation
This is a direct, permanent loss of user funds. Every call to `dispatch()` (POST/GET) or `fundRequest()` with native-token payment, where the swap consumes less than the full `msg.value` sent, results in the surplus ETH being locked in `EvmHost` with no path for the user to reclaim it — only governance can move it, and only to an address chosen by governance, not the original payer. Given native-token fee payment is an officially documented and encouraged payment method (with explicit warnings that `quote()` is approximate due to slippage, meaning users are expected to send some safety margin), this issue will be triggered in normal operation, not just in an edge case.

### Likelihood Explanation
High. Docs explicitly instruct users to estimate fees off-chain and warn that `quote()` is subject to sandwich-attack slippage, implying that a margin above the exact requirement is a normal and even recommended practice when sending native token payment. Every such transaction that overpays even slightly permanently strands the difference in the host contract.

### Recommendation
Track `amounts[0]` (actual ETH spent) returned from `swapETHForExactTokens` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, and refund `msg.value - amounts[0]` back to `_msgSender()` (or the designated payer), mirroring the pattern already implemented in `IntentGatewayV2.placeOrder`.

### Proof of Concept
1. User calls `dispatch(DispatchPost)` with `post.fee = 10e18` (feeToken units) and sends `msg.value = 1 ether`, expecting the excess above the actual swap cost to be refunded (as documented slippage-safety practice).
2. `EvmHost.dispatch` executes `swapETHForExactTokens{value: 1 ether}(10e18, path, address(this), block.timestamp)`.
3. Suppose the actual ETH required is `0.05 ether`; the Uniswap V2 Router refunds `0.95 ether` to `msg.sender`, i.e., to `EvmHost`.
4. `EvmHost` has no logic to capture or return this `0.95 ether`; it becomes part of the contract's native balance.
5. The user has no function to reclaim this ETH; only `withdraw()`, restricted to `hostManager` via cross-chain governance, can move it — and it would go to whatever beneficiary governance selects, not the original user.
