### Title
Unauthenticated livestream TCP listener discloses in-progress signup's biometric frames to newly connected viewer before any state reset - ([File: src/agents/livestream/mod.rs])

### Finding Description
The livestream `Upstream` binds an unauthenticated TCP listener on port 9201 and accepts any connecting client, immediately emitting `Event::Connected(addr)` with no credential check. [1](#0-0) [2](#0-1) 

In `Agent::run`, on `Event::Connected` the code only constructs a new `Downstream` targeting the attacker's IP on UDP port 9200 — it does not clear or reset any GPU textures, nor does it wait for an `Input::Clear` cycle before allowing the next `gpu.render()` push: [3](#0-2) 

`Gpu`'s camera textures (`camera_ir_eye_texture`, `camera_ir_face_texture`, `camera_rgb_texture`, etc.) are persistent GPU state that is only reset by an explicit `Input::Clear` message or at agent startup (`Gpu::new` → `clear_textures()`); they are continuously overwritten by `Input::IrEyeFrame`/`IrFaceFrame`/`RgbFrame` while a signup is in progress: [4](#0-3) [5](#0-4) [6](#0-5) 

Additionally, `render_egui` uses `LoadOp::Load` for the output render pass, meaning the previously composited output texture (containing whatever camera images were drawn in the last frame) is retained and drawn over, not cleared, each call: [7](#0-6) 

Because the main loop only guards `gpu.render(...)` on `downstream.is_some()` — not on a fresh clear having occurred — the very first `gpu.render()` call after a new `Downstream` is constructed will composite and push whatever camera texture content is already resident from an unrelated, currently in-progress signup directly to the new attacker-controlled UDP destination via `Downstream::push`: [8](#0-7) [9](#0-8) 

No credential, session-token, or IP-allowlist check exists anywhere in the livestream module (`upstream.rs`, `downstream.rs`, `mod.rs`) to bind a viewer connection to an authorized operator or to the specific signup session; the only "gate" is TCP `accept()` itself.

### Impact Explanation
An unprivileged network client that can reach TCP port 9201 on the orb can receive, over UDP, the live IR/RGB face and iris frames of a third party mid-signup — this is unauthorized biometric data disclosure to an arbitrary connecting party, violating the stated invariant that biometric secrets are only sent to backend-authorized destinations. This matches a "sensitive/biometric data disclosure" class impact under the Worldcoin/Orb bounty scope.

### Likelihood Explanation
Feasibility depends entirely on network reachability of TCP port 9201 (and UDP port 9200 for reception) — the prompt states this listener is reachable by any unprivileged client, and the attack requires no credentials, no operator access, and no hardware tampering. The race window (connect exactly when `Event::Connected` fires while another signup's frames are already in the GPU textures) is realistic because camera frame `Input` messages continuously stream in during signup and are processed independently of downstream connection state, and there is no synchronization forcing a clear before the next render/push. This is repeatable on every new connection made while a signup is active.

### Recommendation
On `Event::Connected`, force `gpu.clear_textures()` (and `gpu.app.clear()`) before constructing/attaching the new `Downstream`, and/or gate the first `gpu.render()` push after a new `Downstream` on a completed clear cycle so the first frame sent to any newly connected viewer is guaranteed blank rather than potentially containing another user's in-flight biometric frame. Additionally, consider requiring an authenticated/authorized handshake on the upstream TCP connection (e.g., a shared secret or session token bound to the current signup) before creating a `Downstream`, rather than accepting any TCP client unconditionally.

### Proof of Concept
Integration test plan (to be added near `src/agents/livestream/mod.rs` / a new test harness):
1. Start the livestream `Agent` thread with `Gpu` initialized and simulate an in-progress signup by sending `Input::IrEyeFrame`/`Input::RgbFrame` with non-zero, recognizable pixel data (e.g., all pixels = 0xAA) — simulating signup A's frames already written to GPU textures.
2. Simulate `Event::Connected(addr)` (attacker) arriving on the `Upstream` stream without any preceding `Input::Clear`.
3. Capture the buffer passed into `downstream.push(&buffer)` on the very next `gpu.render()` call (mock/stub `Downstream::push` to record the first buffer instead of opening a real GStreamer pipeline).
4. Assert: the first buffer pushed to the newly created `Downstream` is NOT blank/zeroed and instead contains the previously written signup-A pixel values (0xAA) — demonstrating disclosure of a foreign, in-progress signup frame to a brand-new, unauthenticated downstream client.
5. Expected fix behavior: after applying the recommended reset-on-connect gate, the same test should assert the first buffer pushed is blank/zero (i.e., matches `clear_textures()` output) rather than containing signup-A's data.

    pub fn push(&self, frame: &[u8]) -> Result<()> {
        let mut buffer = gstreamer::Buffer::with_size(self.video_info.size())
            .expect("failed to create a new gstreamer buffer");
        {
            let buffer = buffer.get_mut().unwrap();
            let mut video_frame =
                VideoFrameRef::from_buffer_ref_writable(buffer, &self.video_info).unwrap();
            let plane_data = video_frame.plane_data_mut(0).unwrap();
            unsafe {
                ptr::copy_nonoverlapping(frame.as_ptr(), plane_data.as_mut_ptr(), frame.len());
            }
        }
        self.appsrc.push_buffer(buffer)?;
        Ok(())
    }
