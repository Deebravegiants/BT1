### Title
Hostile-pre-seed direct-mint fallback in graduation LP seeding donates curve-raised LT/tokens to attacker-controlled LP - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding.finalizeGraduation` seeds the post-graduation HyperSwap V2 pair through `_seedUniswapV2Direct` / `_seedRebalancing`, which is explicitly designed to be "brick-resistant" against a pre-existing (mint) pre-seed by rebalancing the pool via a direct `pair.swap` before depositing [1](#0-0) . Whenever `_pairRebalance` cannot execute the corrective swap because its fee-charging quote rounds to zero, the code falls back to `_seedDirectMint`, which unconditionally calls the empty-pair-style `pair.mint(lpLock)` even though the pair's `totalSupply()` is non-zero and its reserves are attacker-controlled [2](#0-1) . Because standard UniswapV2 `mint` uses `min(amount0*supply/reserve0, amount1*supply/reserve1)` once `totalSupply != 0`, depositing the graduation's full `(tokensForLP, ltFromPair)` against a large, ratio-mismatched attacker reserve donates the disproportionate side of the deposit to the attacker's pre-existing (unlocked) LP shares, which the attacker can then redeem for real value.

### Finding Description
`_seedRebalancing` computes the direction and size of a corrective swap needed to bring the pair to the curve-close ratio, then calls `_pairRebalance` [3](#0-2) . `_pairRebalance` returns `false` — signalling "skip, fall back to direct mint" — whenever the computed swap input `s` is zero *or* `getAmountOut(s, tokenIn)` rounds to zero [4](#0-3) . The natspec justifies routing this fallback to `_seedDirectMint` on the assumption that "the reserves are then negligible against this graduation's inventory" [5](#0-4) , but that assumption is only checked earlier for the *small-both-sides* band (`DIRECT_MINT_PRESEED_BPS`, 1 bp) [6](#0-5) . The `_pairRebalance`-returns-`false` fallback at lines 1330-1331 / 1346-1347 is reached from the *general* branch, which is entered whenever reserves are simply off-ratio (`reserveToken * ltFromPair != reserveLT * tokensForLP`), with no upper bound on reserve size [2](#0-1) .

An attacker can permissionlessly pre-create the HyperSwap V2 `TOKEN/LT` pair (via `_ensureUniswapV2Pair`, itself callable by anyone since it's invoked inside the permissionless `finalizeGraduation`, or simply by calling the V2 factory directly ahead of time) and seed it with a *large* liquidity position whose ratio is only fractionally off the eventual curve-close ratio — small enough that the fee-charging `getAmountOut` for the corrective swap size `s` rounds to zero (this is achievable because `s` from `_noFeeSwapInput` shrinks as the pre-seed ratio approaches the target, while `reserveIn`/`reserveOut` can be scaled arbitrarily large by the attacker's own capital) [7](#0-6) . This forces `_pairRebalance` to return `false`, so `_seedDirectMint` is invoked against the pool's real, large, off-ratio reserves [8](#0-7) . `IUniswapV2Pair.mint` on a non-empty pool computes LP output as the *minimum* of the two side ratios relative to existing reserves [9](#0-8) , so whichever side of the graduation's deposit is disproportionately large relative to the attacker's chosen reserve ratio is effectively donated as unclaimed reserve, which increases the value backing the attacker's own (already-minted, unlocked) LP shares. The attacker can then call the V2 router's `removeLiquidity` (as the pair's original minter, holding LP tokens outside `LPLock`) to redeem that donated value, extracting curve-raised LT and/or tokens that should have backed the locked graduation LP.

This mirrors the tar-fs advisory's bug class: a fallback/edge-case code path ("link following") bypasses the primary defensive check ("path restriction") and resolves an operation against attacker-influenced state (an attacker-seeded reserve) instead of the intended isolated target (a fresh/rebalanced pool), resulting in unauthorized value transfer.

### Impact Explanation
Real, permanent loss of curve-raised LT and/or unsold tokens. The protocol's `_prepareGraduationLiquidity` pins `tokensForLP`/`ltFromPair` at the exact curve-close price specifically to guarantee the LP opens at that price for the locked LP in `LPLock` [10](#0-9) . The fallback described above breaks that invariant: a portion of the graduation's deposit is siphoned into an attacker-controlled, unlocked LP position instead of the protocol-locked one, i.e. an LP seeded away from the curve close price with funds extractable by the attacker. `LPLock.recordLock` is one-shot and has no rescue/withdraw path [11](#0-10) , so the protocol/creator cannot recover the diverted value after the fact.

### Likelihood Explanation
Requires only unprivileged, permissionless actions: pre-creating/seeding the HyperSwap V2 pair before a specific token's graduation, and choosing a pre-seed ratio+size such that the rebalance-swap quote rounds to zero. This is squarely within the threat model the contract's own natspec anticipates and attempts to defend against ("hostile pre-seed", "mint pre-seed" regimes) [12](#0-11) , but the specific `getAmountOut`-rounds-to-zero escape hatch is not bounded to "negligible reserves" as the comment claims, making this a realistic, deliberately-triggerable edge case rather than a purely theoretical one. It does require the attacker to correctly size the pre-seed relative to the eventual `(tokensForLP, ltFromPair)`, which depends on curve state at graduation — feasible since `previewLtUntilGraduation`/`getReserves` are public views the attacker can read right up to triggering or observing graduation.

### Recommendation
In `_seedRebalancing`, when `_pairRebalance` returns `false` outside the already-validated `DIRECT_MINT_PRESEED_BPS` band, do not unconditionally fall back to `_seedDirectMint`'s raw `pair.mint`. Instead, route through the router's `quote()`-based balanced-deposit path (`_routerDepositAndDispose`) even when no swap fires, so the mint always uses the optimal-amounts split rather than the raw `min()` formula against arbitrary attacker reserves. Alternatively, explicitly re-check that `reserveToken`/`reserveLT` are within the negligible `DIRECT_MINT_PRESEED_BPS` band before permitting the `_seedDirectMint` fallback triggered by a zero-rounding swap quote, and abort/retry (e.g., widen `maxSwap` or use a minimum-output floor of 1) instead of silently minting against large mismatched reserves.

### Proof of Concept
1. Attacker permissionlessly creates the `TOKEN/LT` HyperSwap V2 pair for a token that is trading on the curve (or waits for `_ensureUniswapV2Pair` to create it).
2. Attacker calls `pair.mint` after transferring a large `(tokenAmt, ltAmt)` position chosen so that its ratio is close to, but not exactly, the token's expected curve-close ratio (observable via `IPair.getReserves()`/`Pair.k()` on the bonding curve pair), such that the eventual `_noFeeSwapInput` result `s`, when fed to `pair.getAmountOut(s, tokenIn)`, rounds to `0`.
3. Attacker (or anyone) drives the curve to graduation (`Bonding.triggerGraduation` / crossing the buy threshold), then calls `Bonding.finalizeGraduation(tokenAddress)`.
4. Inside `_seedRebalancing`, `_pairRebalance` returns `false` due to the zero-rounding quote; `_seedDirectMint` is invoked, transferring the full `tokensForLP`/`ltFromPair` into the pre-seeded pool and calling `pair.mint(lpLock)` against non-zero, attacker-controlled reserves.
5. Because `totalSupply() != 0`, the V2 mint formula's `min()` under-credits `LPLock` on the mismatched side, leaving the excess as reserve value backing the attacker's own (unlocked) LP tokens minted in step 2.
6. Attacker calls the V2 router's `removeLiquidity` with their LP tokens to redeem the donated LT/token value, realizing profit at the expense of the protocol-locked LP.

    function _pairRebalance(
        RebalanceParams memory p
    ) internal returns (bool) {
        uint256 s = _noFeeSwapInput(p.reserveIn, p.reserveOut, p.targetN, p.targetD, p.maxSwap);
        if (s == 0) return false;

        // Quote from the pair so the output tracks its live fee; a value
        // derived from a stale fee rate would trip the pair's K-check.
        uint256 expectedOut = IUniswapV2Pair(p.pair).getAmountOut(s, p.tokenIn);
        if (expectedOut == 0) return false;

        IERC20(p.tokenIn).safeTransfer(p.pair, s);
        (uint256 amount0Out, uint256 amount1Out) = p.tokenInIs0 ? (uint256(0), expectedOut) : (expectedOut, uint256(0));
        IUniswapV2Pair(p.pair).swap(amount0Out, amount1Out, address(this), new bytes(0));
        return true;
    }

    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }

    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }
