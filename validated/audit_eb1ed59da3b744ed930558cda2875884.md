### Title
Webhook HMAC covers only the raw body, allowing shop/topic identity spoofing via unsigned headers - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body via `Utils::HmacValidator.validate(request)`. The signable string used for that check is only `@raw_body` [1](#0-0) . The `shop` (from the `shop-domain` header) and `topic` (from the `topic` header) that the rest of the pipeline treats as authenticated identity are read directly from HTTP headers and are never included in the HMAC-signed material [2](#0-1) .

### Finding Description
This mirrors the reported bug class: a value that downstream code trusts as bound to the signed payload (which liquidity pool a permit applies to) is in fact outside the cryptographically verified region (only owner/spender/value/nonce were signed). Here, the equality that should hold is:

`HMAC(shared_secret, raw_body) valid` ⇒ `(shop, topic) as claimed in headers == (shop, topic) that were actually authorized by Shopify for this exact body`

But the code only proves `HMAC(shared_secret, raw_body)` is valid; it does not bind `shop` or `topic` into that proof. `Registry.process` calls `Utils::HmacValidator.validate(request)`, and only after that check passes does it dispatch based on `request.topic` to look up a handler and pass `request.shop` into `WebhookMetadata` for the app's handler to consume [3](#0-2) . Since the app's webhook secret (`api_secret_key`) is the same shared secret for every shop/topic combination for a given app [4](#0-3) , any legitimately-signed webhook body from Shop A can be replayed with the `shop-domain` header changed to Shop B (or the `topic` header changed to a different topic) and the HMAC check in `HmacValidator.validate` will still pass, because it never inspects those headers.

### Impact Explanation
This is a cross-tenant identity-binding failure: an app processing this replayed/relabeled webhook will invoke the handler registered for the attacker-chosen `topic` and construct `WebhookMetadata` claiming the attacker-chosen `shop`, even though the HMAC only proves the body came from the real secret holder for *some* legitimate webhook, not for this specific shop/topic pairing [5](#0-4) . Depending on how the host application uses `WebhookMetadata#shop`/`#topic` (e.g., to look up which tenant's data to mutate, or to decide GDPR-style `customers/redact`/`shop/redact` handling), this enables cross-tenant data or action confusion — an unprivileged attacker who has observed or replayed one valid webhook delivery (e.g., a low-sensitivity topic for their own shop, or any request whose body they can reconstruct) can cause the app to act as though the traffic belongs to a different shop or a different topic.

### Likelihood Explanation
Requires the attacker to be able to deliver a crafted HTTP request to the app's webhook endpoint with an intercepted/known valid `(raw_body, hmac)` pair and freely-chosen `shop-domain`/`topic` headers — plausible for any actor who receives webhooks for their own shop (a legitimate, unprivileged merchant/app-installer) and can also reach the same endpoint with modified headers, since nothing in this gem's `Webhooks::Request`/`Registry`/`HmacValidator` code prevents it.

### Recommendation
Include `shop`, `topic` (and ideally `webhook_id`/`api_version`) in the HMAC-signable string in `Webhooks::Request#to_signable_string`, or otherwise cryptographically bind the header-derived identity fields to the verified body before they are trusted in `Registry.process`/`WebhookMetadata`.

### Proof of Concept
1. App installs a webhook handler for topic `orders/create` and receives a legitimate webhook for `shop-a.myshopify.com` with body `B` and valid header `X-Shopify-Hmac-Sha256: H = HMAC(secret, B)`.
2. Attacker (who has legitimate access to their own shop's webhook deliveries, or otherwise observes `(B, H)`) sends a new HTTP request to the app's webhook endpoint with the same body `B` and same header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com` and/or `X-Shopify-Topic: customers/redact`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` [6](#0-5) ; since only `raw_body` is signed, validation passes.
4. `request.topic` and `request.shop` are read straight from the attacker-controlled headers and passed to the registered handler via `WebhookMetadata` [5](#0-4) , causing the app to process the event as if it legitimately originated from `shop-b.myshopify.com`/`customers/redact`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
