### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook using an HMAC that only covers the raw request body, while the `shop` field that identifies which tenant the webhook belongs to is taken from an unauthenticated header. This breaks the binding: `HMAC-verified bytes == bytes acted upon`, allowing a holder of a valid webhook signature (all shops share the same app-level `api_secret_key`) to make the handler believe the event belongs to a different, victim shop.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC exclusively over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhook requests, `Webhooks::Request#to_signable_string` returns only the raw HTTP body — it does not include the `shop`, `topic`, or `webhook_id` headers: [2](#0-1) 

`Registry.process` validates the HMAC and then trusts `request.shop` (sourced from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The `shop` field flows straight into `WebhookMetadata`, which is the struct the host application's `WebhookHandler#handle` uses to determine which tenant's data to update: [4](#0-3) 

Because Shopify signs webhooks with the app's single `api_secret_key` (shared across every shop that installs the app, not a per-shop secret), any shop that has legitimately installed the app can produce a body + valid HMAC pair via its own genuine webhook deliveries, then replay that exact `(body, hmac)` pair to the app's webhook endpoint with the `shopify-shop-domain` header swapped to a victim shop's domain. `HmacValidator.validate` will pass — it never inspected `shop` — and `Registry.process` will happily hand the handler a `WebhookMetadata` claiming the event is for the victim shop.

This is the same class of bug as the reported Curve issue: an operation (in this case, "attribute this event to shop X") is executed based on a field (`shop`) that was never covered by the cryptographic binding (HMAC) that was supposed to authenticate the whole message. The equality that should hold — `authenticated bytes == bytes used to select the tenant` — is broken because `shop` is parsed from headers outside the signed payload.

### Impact Explanation
This is a cross-tenant integrity issue: an attacker (any merchant/shop that has installed the app) can cause the host application to process a webhook body under a different, arbitrary shop's identity. Depending on how the host application's `WebhookHandler` implementation uses `data.shop` (e.g., to look up which merchant's records to update, redact, or delete — including the mandatory `shop/redact`, `customers/redact`, `customers/data_request` topics this gem explicitly special-cases), this can lead to cross-tenant data corruption or disclosure keyed off attacker-chosen shop domains. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
High. Any shop that has installed the app already possesses the ability to trigger genuine webhook deliveries and can capture legitimate `(body, hmac)` pairs from its own webhook traffic (e.g. by triggering an order/customer event), since the HMAC secret is the app's single `api_secret_key`, not shop-specific. No privileged credentials, TLS interception, or access to the app's secret are required — only the ability to intercept/replay one's own webhook traffic and forge the `shop`-domain header when re-POSTing to the app's webhook endpoint.

### Recommendation
Bind the tenant identity into the authenticated payload before trusting it:
- Include `shop` (and ideally `topic`, `webhook_id`) in the HMAC-signed material verified by `Webhooks::Request#to_signable_string`/`Utils::HmacValidator`, or
- Cross-check `request.shop` against an independently trusted source (e.g., the shop associated with the stored session/webhook subscription that the `webhook_id` maps to) before dispatching to `WebhookHandler#handle`, and reject mismatches.

### Proof of Concept
1. App has one `api_secret_key` shared by all installed shops.
2. Attacker's own shop (`attacker.myshopify.com`) triggers any webhook event; Shopify sends `POST /webhooks` with body `B` and header `shopify-hmac-sha256: HMAC(secret, B)` and `shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays the exact same body `B` and HMAC header to the app's webhook endpoint, but sets `shopify-shop-domain: victim.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B)` — unaffected by the header change — so validation succeeds: [5](#0-4) 
5. `handler.handle` receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: B, ...)`, causing the app to act as if the event originated from the victim shop.

          received_signature = verifiable_query.hmac
