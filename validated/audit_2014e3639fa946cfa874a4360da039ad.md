## Analog Vulnerability Confirmed

### Title
Unvalidated `shop` parameter in `Oauth.begin_auth` enables forced OAuth completion / session fixation - (`lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the merchant-authorization redirect target directly from the caller-supplied `shop` string with no validation that it is a genuine Shopify domain, while the CSRF `state` nonce is unconditionally minted and handed back to the caller for storage in the visitor's browser cookie before that redirect happens. This breaks the identity binding "the host that receives the CSRF nonce == a trusted Shopify domain," letting an unprivileged caller redirect a victim's browser (carrying the app's `state` nonce) to an attacker-controlled host, enabling forced OAuth completion against a shop the attacker controls.

### Finding Description
`begin_auth` takes `shop:` as a raw `String` and passes it straight into `auth_base_uri(shop)`, which returns `"https://#{shop}/admin"` with no format check: [1](#0-0) 

Before redirecting, the same call generates a random `state` nonce and returns a `SessionCookie` that the host app is instructed to set on the victim's browser, and builds `auth_route = auth_base_uri(shop) + "/oauth/authorize?..."` embedding `state` as a query parameter: [2](#0-1) 

The documented usage pattern takes `shop` straight from an unauthenticated request header (`request.headers["Shop"]`) with no library-side sanitization step: [3](#0-2) 

By contrast, every other credential-issuing flow in this gem was hardened to validate the shop domain against a trusted allow-list via `ShopifyAPI::Utils::ShopValidator.sanitize!`/`sanitize_shop_domain` before it is used to construct any host-facing request or trust boundary, e.g. `TokenExchange`, `ClientCredentials`, and `RefreshToken`: [4](#0-3) 

`Oauth.begin_auth` and `Oauth.validate_auth_callback` are the only OAuth entry points that never call `ShopValidator`, even though the CHANGELOG documents this validator as the fix for exactly this class of shop-domain-trust issue: [5](#0-4) 

The equality that should hold but does not: `host(auth_route) == trusted Shopify domain`. Instead `host(auth_route) == caller-supplied shop` unconditionally, with no `.myshopify.com`/`myshopify.io`/`spin.dev` allow-list check.

### Impact Explanation
Because `auth_base_uri` performs no validation, an attacker who can influence the `shop` value passed into `begin_auth` (e.g., via a crafted deep link into the host app's login route, following the documented `request.headers["Shop"]` pattern) can force the app to:
1. Set the CSRF `state` nonce cookie in the victim's browser (this happens in the app regardless of where the browser is subsequently sent).
2. Redirect the victim's browser to `https://<attacker-domain>/admin/oauth/authorize?...state=<nonce>...`, leaking the app's `client_id`, `redirect_uri`, and the CSRF `state` value to the attacker's server.

The attacker can then complete a legitimate OAuth grant against a Shopify store they themselves control, obtaining a Shopify-signed `code`/`hmac` for a callback with a `shop` of their own choosing, and set `state` to the value stolen from the victim's browser. When replayed against the merchant app's callback route, `validate_auth_callback`'s HMAC and state checks both pass (the HMAC is valid because it was really generated by Shopify for the attacker's real store, and `state == auth_query.state` matches the victim's leaked cookie): [6](#0-5) 

This forces the victim's session/cookie to complete OAuth against the attacker's shop instead of the intended shop — a forced OAuth completion / session-fixation condition matching the High-impact bucket in scope.

### Likelihood Explanation
Any caller of `begin_auth` that follows the gem's own documented pattern (accepting `shop` from a request header/param without a library-enforced allow-list) is exposed; the gem provides no built-in check to prevent it, whereas it does provide and use one (`ShopValidator`) for the equivalent trust decision in `TokenExchange`, `ClientCredentials`, and `RefreshToken`. The inconsistency between these code paths indicates the fix is a straightforward, known remediation that was applied everywhere except the legacy authorization-code-grant entry point.

### Recommendation
Validate `shop` in `Oauth.begin_auth` (and defensively in `validate_auth_callback`) using `ShopifyAPI::Utils::ShopValidator.sanitize!`/`sanitize_shop_domain` before it is used to construct `auth_base_uri`, raising `Errors::InvalidShopError` for any domain outside `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` (or the configured `myshopify_domain`), consistent with the other OAuth flows in this codebase.

### Proof of Concept
1. Host app exposes `/login` per the documented pattern, calling `ShopifyAPI::Auth::Oauth.begin_auth(shop: request.headers["Shop"], redirect_path: "/auth/callback")`.
2. Attacker sends the victim a link that triggers this route with `Shop: attacker.evil.example`.
3. App sets the `state` nonce cookie on the victim's browser, then returns `auth_route = "https://attacker.evil.example/admin/oauth/authorize?client_id=...&state=<nonce>..."`; the host app 307-redirects the browser there per the documented example.
4. Attacker's server captures `state`, `client_id`, `redirect_uri` from the incoming request.
5. Attacker completes a real OAuth grant on their own Shopify store to obtain a genuine `code`/`hmac` pair, then redirects the victim's browser to the app's real callback URL with `shop=attacker-real-store.myshopify.com&code=<real code>&hmac=<real hmac>&state=<stolen nonce>`.
6. `validate_auth_callback` passes HMAC and state checks and completes the OAuth flow, fixating the victim's session onto the attacker's store.

```ruby
      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end
```
