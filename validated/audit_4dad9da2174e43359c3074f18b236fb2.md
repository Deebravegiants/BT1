Based on my investigation, this is a valid analog: the ISMP pallet's bounded state-commitment queue (`MAX_STATE_MACHINE_COMMITMENTS` = 10,240 per chain, with `MAX_COMMITMENT_EVICTIONS_PER_INSERT` = 4 evictions per insert) functions exactly like a rate limiter with a "maximum amount" — and it is fed by a **permissionless** operation (`handleConsensus` / `update_client`), just as the Scroll rate limiters are fed by permissionless deposits/withdrawals.

### Title
Unbounded permissionless consensus updates can evict state commitments still required for pending message delivery, causing permanent message-delivery failure (route DoS) - ([File: modules/pallets/ismp/src/lib.rs])

### Summary
`pallet-ismp`'s per-`StateMachineId` state-commitment store (`BoundedStateCommitments`) is a fixed-capacity FIFO queue (default cap `MAX_STATE_MACHINE_COMMITMENTS = 10_240`, evicting up to `MAX_COMMITMENT_EVICTIONS_PER_INSERT = 4` oldest entries per insertion) [1](#0-0) . Insertions happen via `update_client`, which any relayer can call permissionlessly to submit a valid consensus proof (`handleConsensus` on EVM is explicitly documented as "Access: Permissionless") [2](#0-1) . Anyone can drive this queue to its cap and beyond by rapidly and repeatedly submitting legitimate consensus updates, evicting older — but still needed — commitment heights before pending cross-chain requests/responses that reference them can be proven and delivered.

### Finding Description
`update_client` verifies a consensus proof and then stores every finalized intermediate state height via `host.store_state_machine_commitment`, which in the pallet's `IsmpHost` implementation calls `Pallet::insert_bounded_state_commitment` [3](#0-2) . This is a bounded FIFO: `CommitmentQueueState { head, tail }` tracks live indices, and once the cap is reached, the oldest entries are evicted (up to 4 per insert) as new heights are appended, confirmed by the pallet's own tests (`lowering_the_cap_drains_the_queue_gradually`) [4](#0-3) .

Crucially, `update_client` is reachable by anyone with no fee-token cost gate comparable to a deposit/withdrawal amount limit — it is purely a consensus-proof-verification gate [5](#0-4) , and the EVM-side entrypoint is documented explicitly as permissionless [6](#0-5) . For fast-finalizing chains (BSC's relayer batches up to 8 consensus messages per tx and light-client updates happen roughly every finality event) [7](#0-6) , an attacker with their own relayer/light-client infrastructure could submit many additional valid-but-redundant/fast-successive consensus updates (for any chain whose consensus proof is publicly derivable, i.e., not requiring a private key) at high frequency, purely paying gas/proof cost — mirroring the "only cost is gas fees" abuse pattern from the Scroll report. This inflates queue insertions and evicts old-but-still-needed commitment heights on the `BoundedStateCommitments` FIFO for that `StateMachineId`.

`handlePostRequests` and analogous handlers require the state commitment at a specific proven height to still be present (`host.stateMachineCommitment(request.proof.height)` must resolve, else `StateCommitmentNotFound`) [8](#0-7) . If that height's commitment has been evicted from the bounded queue before a relayer can deliver the pending request/response proven against it, delivery permanently fails for that message (there is no way to regenerate an evicted historical commitment retroactively without re-running consensus from that height, which for BEEFY/GRANDPA/BSC-style clients is generally not re-derivable once superseded).

### Impact Explanation
This is analogous to the Scroll rate-limiter DOS: an unprivileged, adversarial party can exhaust a bounded resource (the fixed-size commitment retention window) purely by paying ordinary transaction/proof-submission costs, with no admin intervention path faster than raising the per-chain cap (`update_commitment_caps`, admin-only) [9](#0-8) . The result is that in-flight, honestly relayed requests/responses whose proofs target an evicted height can never be delivered — a permanent "route unable to deliver messages" condition for affected messages, matching the accepted impact class (route unable to deliver messages / unsound state commitment retention).

### Likelihood Explanation
Medium. The cap (10,240 default) and the small per-insert eviction bound (4) suggest the queue is sized generously for normal finality cadence, so triggering this requires an attacker capable of generating a sustained high rate of *valid* consensus updates for a given light client faster than legitimate relayers can complete pending message deliveries — feasible for chains with fast/cheap finality proofs (e.g., BSC epoch/header updates), less so for slow, expensive consensus proofs (e.g., GRANDPA/BEEFY finality gadgets with larger validator-set proofs). Feasibility depends heavily on per-chain finality-proof cost/frequency, which I was not able to fully quantify for every supported consensus client within the available context.

### Recommendation
- Size `StateMachineCommitmentCap` per chain to comfortably exceed the maximum challenge-period + expected relayer-delivery latency window, and consider dynamically widening it (or refusing to evict) when there exist known pending/unfinished requests/responses whose proof height would be evicted.
- Rate-limit or cost-gate `update_client` per `consensus_state_id` beyond pure gas cost (e.g., minimum interval between accepted updates for the same client) so an attacker cannot force excess churn faster than legitimate relay/delivery cadence.
- Emit an alert/event when eviction is about to remove a commitment height that still has undelivered requests/responses tracked against it, and expose an admin/emergency path (matching the Scroll fix pattern) to raise the cap or pause eviction under attack.

### Proof of Concept
1. Identify a `StateMachineId` (chain) with fast, cheap-to-produce consensus proofs (e.g., a BSC-style client with permissionless `handleConsensus`).
2. Have a pending relayed `PostRequest`/`PostResponse` proven against a specific finalized height `H` that has not yet been delivered.
3. As an attacker, repeatedly submit additional valid consensus proofs advancing the client past `H`, driving more than `(cap - distance_to_H)` new heights into `BoundedStateCommitments` for that chain before the legitimate relayer submits delivery for the message proven at `H`.
4. Once enough insertions occur, `insert_bounded_state_commitment`'s eviction (per `lowering_the_cap_drains_the_queue_gradually` semantics) removes height `H`'s commitment from `BoundedStateCommitments`.
5. The pending delivery transaction referencing `request.proof.height == H` now fails permanently with `StateCommitmentNotFound` (EVM side) or the pallet's equivalent, because `H`'s commitment can never be reinserted.

	let trusted_state = host.consensus_state(msg.consensus_state_id)?;

	host.is_expired(msg.consensus_state_id)?;

		host,
		msg.consensus_state_id,
		trusted_state,
		msg.consensus_proof,

    function handleConsensus(IHost host, bytes calldata proof) external notFrozen(host) {
        uint256 delay = block.timestamp - host.consensusUpdateTime();
        if (delay >= host.unStakingPeriod()) revert ConsensusClientExpired();

        bytes memory previousState = host.consensusState();
        (bytes memory verifiedState, IntermediateState[] memory intermediates, uint256 nextAuthoritySetId) =
            IConsensusV2(host.consensusClient()).verify(previousState, proof);

        if (keccak256(previousState) == keccak256(verifiedState)) return;
        host.storeConsensusState(verifiedState);

        uint256 intermediatesLen = intermediates.length;
        for (uint256 i = 0; i < intermediatesLen; i++) {
            IntermediateState memory intermediate = intermediates[i];
            uint256 latestHeight = host.latestStateMachineHeight(intermediate.stateMachineId);
            if (latestHeight != 0 && intermediate.height > latestHeight) {
                StateMachineHeight memory stateMachineHeight =
                    StateMachineHeight({stateMachineId: intermediate.stateMachineId, height: intermediate.height});
                host.storeStateMachineCommitment(stateMachineHeight, intermediate.commitment);
            }
        }

        // `nextAuthoritySetId` identifies the upcoming set; the relayer that delivered the proof
        // is credited as the relayer for the just-ended epoch (`nextAuthoritySetId - 1`).
        // If `nextAuthoritySetId == 0` no rotation has occurred, so there is nothing to record.
        if (nextAuthoritySetId == 0) return;
        uint256 epoch = nextAuthoritySetId - 1;
        if (epoch > host.currentEpoch()) {
            host.recordEpoch(epoch, _msgSender());
        }
    }
