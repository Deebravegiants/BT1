## Analog Found

### Title
Fee-on-transfer underlying tokens let attackers mint unbacked cross-chain value via `WrappedHyperFungibleToken.send()` - ([File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol])

### Summary
`WrappedHyperFungibleToken.send()` locks the underlying ERC20 via `safeTransferFrom(msg.sender, address(this), params.amount)` and then encodes the *requested* `params.amount` — not the actual amount received — into the cross-chain `Message` that is dispatched to the peer chain. If the underlying token charges a transfer fee (fee-on-transfer, e.g. USDT-style tokens or any upgradeable token that later adds a fee), the contract's escrow balance increases by less than `params.amount`, while the destination chain is told the full `params.amount` arrived and will release/mint that full amount.

### Finding Description
In `send()`:
```solidity
IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
...
DispatchPost memory request = _buildDispatchPost(params); // encodes message.amount = params.amount
``` [1](#0-0) 

`_buildDispatchPost` builds the `Message` body strictly from `params.amount`, with no check against the token's actual balance delta: [2](#0-1) 

There is no `balanceOf` before/after check, and `safeTransferFrom` only reverts on failure — it does not validate that the received amount equals the requested amount. On the destination chain, `onAccept` trusts `message.amount` completely and transfers/unwraps that exact amount to the beneficiary from its own escrow: [3](#0-2) 

The identical pattern exists in the upgradeable variant: [4](#0-3) 

This mirrors the reported Illuminate bug class exactly: the contract trusts the pre-fee transfer amount instead of verifying the actual balance change, letting a fee-on-transfer underlying (or one that becomes fee-on-transfer via upgrade) produce a persistent shortfall between what is escrowed on the source chain and what is promised/released on the destination chain.

### Impact Explanation
Each `send()` call with a fee-on-transfer underlying escrows `params.amount * (1 - fee)` but instructs the peer chain to release/unlock the full `params.amount`. Since the wrapped representation is fully fungible and backed 1:1 by escrow, this systematically drains the shared collateral pool: the destination side pays out more underlying (or credits more value) than was actually locked on the source side. Repeated over time, or exploited deliberately by round-tripping funds through a fee-on-transfer-enabled underlying, this leads to insolvency of the escrow — legitimate holders of the wrapped token/backing asset on either chain will be unable to redeem their full balance, i.e. theft/permanent freezing of other users' funds and an unbacked cross-chain mint of value.

### Likelihood Explanation
Likelihood depends on the underlying token configured via `configure()`; any deployment wrapping a fee-on-transfer ERC20 (common examples: USDT-style fee tokens, some rebasing/tax tokens) or a token that can add a transfer fee via upgrade is directly exploitable by any regular user calling `send()` — no privileged access required. This is a single-transaction, unprivileged attack path reachable exactly as described in the excluded/allowed scope ("token bridge mint/burn").

### Recommendation
Before building the dispatch message, measure the actual amount received:
```solidity
uint256 balBefore = IERC20(_underlying).balanceOf(address(this));
IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
uint256 received = IERC20(_underlying).balanceOf(address(this)) - balBefore;
```
Use `received` (not `params.amount`) when constructing the `Message.amount` that gets dispatched cross-chain, and/or reject configuring `_underlying` tokens with non-standard transfer semantics.

### Proof of Concept
1. Owner configures `WrappedHyperFungibleToken` with `_underlying` = a fee-on-transfer token (e.g. 2% fee).
2. Attacker calls `send({amount: 1000, dest: chainB, to: attacker, ...})`.
3. `safeTransferFrom` pulls 1000 from attacker but contract balance only increases by 980 due to the token fee.
4. `_buildDispatchPost` still encodes `amount: 1000` in the `Message` body; the ISMP request is dispatched with this value.
5. On chain B, the peer `WrappedHyperFungibleToken.onAccept` receives `message.amount = 1000` and calls `IERC20(_underlying).safeTransfer(beneficiary, 1000)` from its own escrow — releasing 1000 units of backing asset even though only 980 were ever actually deposited on chain A.
6. Net effect: 20 units of value are created out of thin air per transfer, paid for by other users' escrowed collateral, and repeatable indefinitely.

    function _buildDispatchPost(HyperFungibleToken.SendParams calldata params) internal view returns (DispatchPost memory) {
        bytes memory dest = _supportedChains[params.dest];
        if (dest.length == 0) revert UnsupportedChain();

        bytes memory body = abi.encode(HyperFungibleToken.Message({
            from: abi.encodePacked(msg.sender),
            to: params.to,
            amount: params.amount,
            data: params.data
        }));

        return DispatchPost({
            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,
            payer: msg.sender
        });
    }

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
