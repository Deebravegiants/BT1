### Title
Unkeyed `restrictConcurrency` on `#getPrivateKey` causes in-flight private-key promise to be shared across different seeds/keys during concurrent calls - ([File: features/cached-sodium-encryptor/module/cached-sodium-encryptor.ts])

### Summary
`CachedSodiumEncryptor#getPrivateKey` is wrapped with the default `make-concurrent` (`restrictConcurrency`) export, which serializes/deduplicates concurrent invocations by function identity only, not by call arguments. As a result, when two `encryptSecretBox`/`decryptSecretBox`/`encryptBox`/`decryptBox` calls for *different* `{seedId, keyId}` values race, the later call can receive the *same in-flight promise* (and thus the same derived private key) as the earlier call, independent of any `getCacheKey` collision.

### Finding Description
`#getPrivateKey` is defined as: [1](#0-0) 

It is wrapped via `restrictConcurrency` (imported as `make-concurrent`'s default export): [2](#0-1) 

The repository itself demonstrates that the plain default export of `make-concurrent` does **not** key by arguments — a separate named export `byArguments` exists specifically for that purpose, and is used elsewhere in the codebase when per-argument isolation is required: [3](#0-2) 

`cached-sodium-encryptor.ts` uses the plain (non-`byArguments`) form on `#getPrivateKey`, so concurrent calls to `#getPrivateKey` — regardless of their `KeySource` (`seedId`/`keyId`) — are subject to the library's default concurrency-restriction behavior, which serializes/reuses in-flight invocations keyed on the wrapped function itself, not on the parameters passed to it. This means that if `encryptSecretBox({ seedId: A, keyId })` and `encryptSecretBox({ seedId: B, keyId })` are both invoked before the first `#getPrivateKey` call settles (e.g., via `Promise.all([...])`), the second call can be resolved using the private key derived for seed A rather than seed B, because `make-concurrent`'s default queuing model does not key on `params`.

This bypasses the intended per-account isolation of `#derivePrivateKey`/`this.#cache`, since the cache-key computation in `getCacheKey` (`features/cached-sodium-encryptor/module/cache.ts`) never even executes for the second racing call under the plain (non-`byArguments`) `make-concurrent` model — the outer concurrency wrapper itself, not `getCacheKey`, is the mechanism causing cross-seed reuse. The `#checkIfAllowed` gate only restricts which `keyId`s (`WALLET_INFO`, `FUSION`) may be cached; it performs no per-`seedId` isolation and does not protect against this race: [4](#0-3) 

### Impact Explanation
If exploited, a caller intending to encrypt/decrypt secret-box data scoped to seed B could transiently receive ciphertext/plaintext produced with seed A's derived private key. This violates SECRET_ISOLATION/STORAGE_INTEGRITY between accounts/seeds sharing the `cachedSodiumEncryptor` module — data tagged as belonging to seed B would actually be encrypted or decrypted using seed A's key material, corrupting or exposing wallet-info/fusion-scoped secrets across account boundaries.

### Likelihood Explanation
Exploitation requires two concurrent invocations of `#getPrivateKey` (via `encryptSecretBox`, `decryptSecretBox`, `encryptBox`, or `decryptBox`) for different `seedId`/`keyId` combinations to race before the first `#derivePrivateKey` promise settles — e.g. via `Promise.all([...])` from within the same process. Whether this is reachable purely from an unprivileged, external dapp/origin/RPC request depends on whether any caller passes an attacker-influenced `seedId` into these APIs; this repository slice does not show such a caller, so full external attacker reachability could not be confirmed with the available context. However, the internal race condition itself is a demonstrable code defect independent of any external trigger, and is fully reproducible with an in-process integration test that races two `KeySource` calls.

### Recommendation
Use the `byArguments` variant of `make-concurrent` (or key the restriction manually using `getCacheKey(params)`) when wrapping `#getPrivateKey`, so that concurrency restriction is scoped per `{seedId, keyId}` rather than globally per function, e.g.:
```ts
import { byArguments as restrictConcurrencyByArguments } from 'make-concurrent'
...
#getPrivateKey = restrictConcurrencyByArguments(async (params: KeySource) => { ... }, getCacheKey)
```

### Proof of Concept
Integration test plan:
1. Instantiate `CachedSodiumEncryptor` with a mock `keychain.exportKey` that returns a distinguishable private key based on `seedId` (e.g., `Buffer.from(seedId.repeat(32))`), with an artificial delay for seed A's resolution longer than seed B's dispatch but still concurrent.
2. Call `Promise.all([instance.encryptSecretBox({ seedId: 'A', keyId: EXODUS_KEY_IDS.FUSION, data }), instance.encryptSecretBox({ seedId: 'B', keyId: EXODUS_KEY_IDS.FUSION, data })])` before the first call's `keychain.exportKey` promise resolves.
3. Decrypt/inspect the resulting ciphertexts (or capture the `encryptionKey` passed to `sodium.encryptSecret`) to assert that seed B's call used a private key derived from `seedId: 'B'`, not `seedId: 'A'`.
4. Expected (failing) result under current code: the second call's derived key equals the first call's key, demonstrating cross-seed key reuse; the fix should make the assertion pass by isolating concurrency per cache key.

  // 'WALLET_INFO' is used for secure storage - everything that's not the seed/private keys. Examples: tx-history, address cache, nfts, etc.
  // for historical reasons, secure storage is unlocked only once during the runtime lifecycle of the application, and never re-locked.

  EXODUS_KEY_IDS.FUSION,
]

export class CachedSodiumEncryptor {
  readonly #keychain: Keychain
  readonly #cache = new Map<string, Buffer>()

  constructor({ keychain }: Dependencies) {
    this.#keychain = keychain
  }

  async #derivePrivateKey({ keyId, seedId }: KeySource) {
    const { privateKey } = await this.#keychain.exportKey({ keyId, seedId, exportPrivate: true })
    return privateKey
  }

  #checkIfAllowed = ({ keyId }: KeySource) => {
    return ALLOWED_KEY_IDS.some((allowedKeyId) => KeyIdentifier.compare(allowedKeyId, keyId))
  }
