Based on the investigation, I found a genuine analog worth reporting: the `hashes.sign` signature in the personal custody package covers only the `hashes.json` digest, while `signup_id` and `signup_reason` — both attacker-reachable-adjacent, security-relevant fields — are only included as *salted-hash entries inside* `hashes.json` rather than being bound to a tamper-evident channel that ties them to the specific signup transaction end-to-end, and more importantly, the `make_signature` used for the separate iris-code corroboration signature in enrollment omits `signup_id`, `distributorId` (operator id), and `signup_reason` entirely.

### Title
Iris-code signature omits `signup_id`, operator id, and signup reason, allowing cross-signup replay/misattribution - (File: `src/plans/enroll_user.rs`)

### Summary
`make_signature()` in `src/plans/enroll_user.rs` computes a Secure-Element-backed signature over the Orb ID, user QR `user_id`, and the iris-code pipeline outputs, but does not include the `signup_id`, the operator/distributor identity, or the `signup_reason` that are transmitted alongside it in the same `signup_post::request()` call. This mirrors the reported bug class: a signature that authenticates some parameters of a request while leaving other security-relevant parameters of the same request unauthenticated, so those excluded fields can be substituted without invalidating the signature.

### Finding Description
`make_signature()` hashes only: [1](#0-0) 

The resulting signature and these unsigned values are sent together in the same multipart form to the backend: [2](#0-1) 

Specifically, `signup_id` (used as the URL path segment `/api/v2/signups/{signup_id}`), `operator_qr_code.user_id` (sent as `distributorId`), `s3_region`, and `signup_reason` are all included in the POST but are outside the signed digest. Only `ORB_ID`, `user_qr_code.user_id`, and the iris pipeline data are covered.

### Impact Explanation
Because `signup_id`, `distributorId`, and `signup_reason` are not bound to the signature, any component or intermediary capable of re-using a captured/valid signature value (e.g., a compromised or misbehaving process that can influence the outgoing HTTP request after signing but before submission) could submit the same signed iris-code payload paired with a different `signup_id` or `distributorId`, causing biometric data to be attributed to the wrong signup session or operator. This is a cross-signup misattribution risk consistent with the reported bug class (signature covering only some parameters of a multi-parameter operation).

### Likelihood Explanation
Exploitation requires an actor with the ability to intercept/modify the request between signature computation and transmission — orb-core sends the signup POST over authenticated HTTPS with `basic_auth(&*ORB_ID, get_orb_token())` [3](#0-2) 
so there is no public "mempool" equivalent to the smart-contract case, and no in-repo evidence of an unprivileged attacker being able to intercept and resubmit with altered `signup_id`/`distributorId` before the legitimate request completes. This substantially reduces likelihood versus the original report and stops short of a fully demonstrable no-privilege exploit path within orb-core alone.

### Recommendation
Include `signup_id`, `distributorId` (operator id), and `signup_reason` in the data hashed by `make_signature()` in `src/plans/enroll_user.rs`, and verify all of them server-side, so the signature binds the entire request context rather than only the biometric payload fields.

### Proof of Concept
Not independently demonstrable as a no-privilege exploit within the orb-core repository alone — the transport layer (authenticated HTTPS to the signup backend) does not expose an analogous public mempool through which an unprivileged attacker could intercept and resubmit with substituted `signup_id`/`distributorId` before the legitimate request lands, unlike the original Sherlock finding's ERC-4337 mempool. Reported as a defense-in-depth signature-completeness gap rather than a fully proven exploit chain.

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());

    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
