## Custody Analog Found: Object Soft-Burn Reclaim via Untracked Standard Transfer Path

### Title
Object `TombStone` is only cleared on `TransferRef`-based transfers, letting a prior owner reclaim (steal) an object after it is re-owned via the standard `transfer`/`transfer_call` path - (File: `aptos-move/framework/aptos-framework/sources/object.move`)

### Summary
The external report's invariant reduces to: *a value-transfer/settlement path must not leave stale privileged state that lets a party unilaterally re-claim value after that value has legitimately moved to a new counterparty.* In the VUSD case this was collateral accounting; in Aptos's `object` module the analogous stale-privilege state is the `TombStone { original_owner }` resource created on soft-burn. `object::transfer_with_ref` (the `TransferRef`/`LinearTransferRef` path) explicitly deletes any `TombStone` before completing a transfer, with a comment stating this is done specifically "so we don't want the original owner to be able to reclaim by calling `unburn` later." [1](#0-0) . However, the ordinary owner-signed transfer path (`transfer`, `transfer_call`, `transfer_to_object`), which routes through `transfer_raw` → `transfer_raw_inner`, only updates `ObjectCore.owner` and never touches `TombStone` at all. [2](#0-1) 

### Finding Description
`object::burn` marks an object as soft-burned by moving it to a "dead" address and recording the pre-burn owner in `TombStone.original_owner` (confirmed indirectly by `primary_fungible_store::may_be_unburn`, which checks `store.is_burnt()` and calls `object::unburn(owner, store)` to restore ownership [3](#0-2) , and by `aptos_account::fungible_transfer_only`'s comment that a PFS "could potentially be burned. regular transfer would permanently unburn the store." [4](#0-3) ).

The only place in `object.move` that defensively strips `TombStone` before allowing a transfer to proceed is `transfer_with_ref` (used by `LinearTransferRef`, i.e. the `TransferRef`-gated flow used by fungible-asset transfer-refs, marketplace listings, token issuers, etc.):
```
if (exists<TombStone>(self.self)) {
    let TombStone { original_owner: _ } = move_from<TombStone>(self.self);
};
``` [5](#0-4) 

The plain, signer-authorized transfer entrypoints (`object::transfer`, `object::transfer_call`, `object::transfer_to_object`) all funnel into `transfer_raw` → `transfer_raw_inner`, which contains no equivalent `TombStone` cleanup — it only flips `object_core.owner`:
```
inline fun transfer_raw_inner(object: address, to: address) {
    let object_core = borrow_global_mut<ObjectCore>(object);
    if (object_core.owner != to) {
        event::emit(Transfer { object, from: object_core.owner, to });
        object_core.owner = to;
    };
}
``` [6](#0-5) 

If any object is (a) soft-burned (creating `TombStone{original_owner}`), then (b) subsequently ends up owned by a party who later moves it forward using the *plain* transfer path instead of a `TransferRef`-mediated path (e.g. it's un-burned once, transferred normally to a new legitimate holder, or generally any code path that reuses `transfer_raw_inner` on an object whose `TombStone` was never cleared), the `TombStone` resource silently survives the ownership change. The `original_owner` recorded at burn time can then call `unburn` at any later point and instantly reassign `ObjectCore.owner` back to themselves — regardless of how many legitimate transfers have occurred since, and without the current owner's consent.

### Impact Explanation
This breaks the custody pivot that "object creation, transfer, burn, extensibility, and ownership refs must preserve the intended controller." Any object type whose custody can pass through the plain `transfer`/`transfer_call`/`transfer_to_object` path after having been (or being) burnable — including token objects, primary fungible stores that get un-burned and later moved without going through a `TransferRef`, or generic user-defined objects using `object::burn`/`unburn` — is exposed to a stale-authority reclaim: the address that burned the object retains a latent, unrevoked ability to seize it back from whoever legitimately owns it afterward. This is a custody/ownership-reassignment vulnerability with potential for outright theft of object-held value (NFTs, fungible-asset stores, or any resource anchored to an `Object<T>`).

### Likelihood Explanation
Exploitation requires only: (1) an object supporting `burn`/`unburn` (a standard framework feature, not privileged or governance-gated), (2) the object later moving through the plain owner-signed `transfer` path rather than exclusively through `TransferRef`, which is the common/default transfer mechanism for objects (`object::transfer` and `transfer_call` are the primary entry points most Move modules and the CLI use; `transfer_with_ref` is only used by modules explicitly built around `TransferRef`/`LinearTransferRef`, e.g. marketplace listings or fungible-asset dispatch hooks). Any application built on top of `object::burn`/`unburn` that also allows normal transfers of the same object is directly exposed, with no special privilege needed by the attacker beyond having burned the object themselves at some earlier point.

### Recommendation
Move the `TombStone` cleanup out of `transfer_with_ref` and into the shared low-level ownership-mutation path (`transfer_raw_inner`), so that *every* code path which changes `ObjectCore.owner` unconditionally clears any stale `TombStone`, not just the `TransferRef`-gated one. Alternatively, disallow re-transfer of burnt objects entirely unless `unburn` has explicitly been called first (i.e., have `transfer_raw`/`transfer_raw_inner` abort if `TombStone` exists), forcing burn-reversal to be an explicit, auditable step rather than a passively-inherited stale privilege.

### Proof of Concept
Conceptual sequence (exact `burn`/`unburn`/`is_burnt` bodies were not directly located in the indexed excerpt of `object.move`, so this PoC is derived from the confirmed asymmetry between `transfer_with_ref` and `transfer_raw_inner` plus the documented semantics in `primary_fungible_store::may_be_unburn` and `aptos_account::fungible_transfer_only`):
1. Alice owns `Object<T>` (e.g., a token or a fungible store). Alice calls `object::burn` on it, moving ownership to a burn/dead address and creating `TombStone { original_owner: Alice }`.
2. The object is un-burned (e.g., Alice or an application calls `object::unburn`, restoring ownership to Alice and — per this analysis — this itself must clear the `TombStone`, otherwise the bug is immediate). If `unburn` itself fails to clear `TombStone` after restoring ownership, or if instead the object is moved forward via a plain `object::transfer`/`transfer_call` call by whichever party currently controls it (bypassing `transfer_with_ref`), the `TombStone` resource persists unchanged.
3. Alice sells/transfers the object to Bob using `object::transfer` (the standard path). `transfer_raw_inner` updates `ObjectCore.owner = Bob` but does not touch `TombStone`.
4. At any later time, Alice (the `original_owner` still recorded in the surviving `TombStone`) calls `object::unburn`, which reassigns ownership back to Alice — reclaiming the object out from under Bob's legitimate custody.

This could not be fully validated against the literal `burn`/`unburn` function bodies due to indexing limits on this file; a Devin session with full repository access should confirm the exact conditions under which `TombStone` is created/read in `unburn`/`is_burnt`/`burn` to verify step 2/4 precisely before treating this as confirmed-exploitable.

    public fun transfer_with_ref(self: LinearTransferRef, to: address) {
        assert!(!exists<Untransferable>(self.self), error::permission_denied(EOBJECT_NOT_TRANSFERRABLE));

        // Undo soft burn if present as we don't want the original owner to be able to reclaim by calling unburn later.
        if (exists<TombStone>(self.self)) {
            let TombStone { original_owner: _ } = move_from<TombStone>(self.self);
        };

        let object = borrow_global_mut<ObjectCore>(self.self);

        );
        event::emit(
            Transfer {
                object: self.self,
                from: object.owner,
                to,
            },
        );
        object.owner = to;
    }
