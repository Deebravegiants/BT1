## Title
Webhook Shop Identity Spoofing via HMAC That Only Covers the Raw Body, Not the Shop-Domain Header - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signable string from the raw request body only, while the `shop` (and `topic`, `api_version`, `webhook_id`) values used by `ShopifyAPI::Webhooks::Registry.process` to attribute the webhook to a specific merchant are taken from unauthenticated HTTP headers. The identity binding the app relies on — "this signed payload belongs to shop X" — is never actually verified, because `shop` is not part of what the HMAC covers.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from request headers, which are not part of the signed material: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then trusts `request.shop` (and `request.topic`) to dispatch the payload to the merchant's handler: [3](#0-2) 

The identity equality the app implicitly relies on is:
`HMAC-verified(raw_body) == authorized-for(shop-domain header)`

This equality does not hold: the HMAC binds only the body bytes to the secret, not the `shopify-shop-domain` header value that the body is subsequently attributed to. This is the same bug class as the reported stable-swap issue — a value used to make a security-relevant decision (`lp_value_after_swap` / here, the `shop` that data gets attributed to) is not actually covered by the check meant to guarantee its integrity (the invariant assertion / here, the HMAC).

### Impact Explanation
Any unprivileged internet user who can install the target app on their own store (a "free"/test installation, requiring no special privilege) receives genuine, validly-signed webhooks for that store. Because the HMAC only signs the body, the attacker can replay that exact body to the app's public webhook endpoint while substituting the `shopify-shop-domain` (and even `shopify-topic`/`shopify-webhook-id`) header with a victim shop's domain. `HmacValidator.validate` still returns true (body + secret are unchanged), and `Registry.process` will hand the attacker-controlled body to the merchant handler tagged as belonging to the victim shop. This lets an attacker inject arbitrary attacker-chosen webhook payloads (e.g., fabricated `orders/create`, `app/uninstalled`, `customers/data_request`, etc.) into the victim tenant's data path — a cross-tenant data-integrity/confusion attack that satisfies the "cross-tenant access" Critical impact bar.

### Likelihood Explanation
Exploitation requires no secrets beyond what an ordinary merchant/attacker already has: install the app on any shop, capture one legitimate webhook (body + `hmac-sha256` header), and replay it to the endpoint with a forged `shop-domain` header for a target shop whose domain is guessable/known (myshopify.com domains are often predictable/enumerable). No `api_secret_key`, access token, or privileged account is needed, matching the "unprivileged internet user" threat model.

### Recommendation
Bind the shop (and topic) identity into the HMAC-verified material, or otherwise independently authenticate them, e.g.:
- Extend `to_signable_string` to include `shop`, `topic`, and `webhook_id` alongside the raw body, and have the receiving app compute/verify the combined signable string (this requires coordinating with how Shopify signs webhooks, so at minimum the gem should document/enforce that the shop attribution is authoritative from a different authenticated source, e.g., cross-checking against the shop of the active/matching session rather than trusting the header alone).
- At minimum, cross-validate `request.shop` against a shop the app has an active install/session for before dispatching, rather than trusting the header value implicitly.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering a real webhook, e.g. `orders/create`, with headers:
   ```
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   ```
2. Attacker captures the raw body and the valid `hmac-sha256` value.
3. Attacker POSTs the identical raw body to the app's webhook endpoint, replacing only the header:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
   keeping the same `x-shopify-hmac-sha256`.
4. `HmacValidator.validate` in [4](#0-3)  succeeds because it only checks the (unchanged) body against the secret.
5. `Registry.process` in [3](#0-2)  dispatches attacker-controlled `orders/create` data to the handler tagged with `shop: "victim-shop.myshopify.com"`, causing the host app to store/process attacker data as if it belonged to the victim tenant.
