### Title
Webhook `shop` (tenant) identifier is not covered by the HMAC signature, allowing cross-tenant webhook forgery via replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` (and `topic`, `webhook_id`, `api_version`) values are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body and then trusts the header-derived `shop` value to build the `WebhookMetadata` passed to the host application's handler. This breaks the intended binding `HMAC(secret, signed_bytes) == HMAC(secret, bytes_the_shop_field_is_taken_from)`: the bytes verified (body) are not the bytes the tenant identity is parsed from (headers).

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` (and `topic`, `webhook_id`, `api_version`) are pulled straight from HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` against the HMAC, so for a `Webhooks::Request` it validates nothing about the headers: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (a header value) to construct the `WebhookMetadata` delivered to the host app's handler: [4](#0-3) 

`WebhookMetadata.shop` is a plain `String` field with no independent verification: [5](#0-4) 

The identity binding that should hold is: **shop-domain header used for tenant dispatch == shop-domain bytes covered by the HMAC signature**. In this code, the verified bytes (body) and the bytes used to determine which tenant the webhook data belongs to (headers) are disjoint. Any party who can obtain one validly-signed `(body, hmac)` pair — e.g., an unprivileged internet user who installs the app on their own shop and receives their own legitimate webhooks — can replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting the `shopify-shop-domain` (or `x-shopify-shop-domain`) header with an arbitrary other shop domain. `HmacValidator.validate` still succeeds because it never inspects the header, and `Registry.process` will hand the host application a `WebhookMetadata` claiming the body belongs to the victim shop.

### Impact Explanation
This is a cross-tenant data-integrity/confusion vulnerability: an attacker who legitimately receives webhooks for their own shop (a completely unprivileged position — they only need the app installed on some shop they control) can cause the app to process attacker-controlled webhook payloads under the identity of a different, arbitrary shop. Depending on how the host application's webhook handler acts on `data.shop` (e.g., writing order/product/customer data keyed by shop, triggering shop-specific side effects, or feeding it into session lookup), this can lead to cross-tenant data corruption or a cross-tenant action — matching the "cross-tenant access" impact category. The vulnerability lives entirely in this gem's `Request`/`Registry`/`HmacValidator` code path and does not require any secret, access token, or privileged account.

### Likelihood Explanation
Likelihood is moderate to high given the low bar to exploit: no `api_secret_key`, access token, or any Shopify-side credential is needed. The only prerequisite is the ability to obtain one valid `(raw_body, hmac)` pair — trivially available to any developer who installs the app to any shop they control and observes their own real webhook deliveries — after which the header can be freely rewritten for replay against the app's public webhook endpoint.

### Recommendation
Include the tenant-identifying value in the HMAC-signed content, or otherwise cryptographically bind the `shop` header to the payload before trusting it. Concretely:
- Have `Request#to_signable_string` incorporate `shop`, `topic`, and `webhook_id` (not just `@raw_body`), matching Shopify's documented webhook verification guidance which signs the full raw request body but expects the app to also independently confirm the shop is one it has an active session/install for.
- At minimum, in `Registry.process`, cross-check `request.shop` against a known/registered shop (e.g., an active session or installed-shops list) before invoking `handler.handle`, rather than trusting the header value unconditionally.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a benign event (e.g., `orders/create`) so Shopify sends a legitimately HMAC-signed webhook to the app's endpoint. Attacker captures the full HTTP request: headers (`x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid_hmac>`, `x-shopify-topic: orders/create`) and raw body `B`.
2. Attacker resends the identical raw body `B` and the identical `x-shopify-hmac-sha256` value, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `@raw_body` (`request.rb:35-38`, `hmac_validator.rb:26-31`) — validation succeeds because the body and secret are unchanged.
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the spoofed `shop` header value (`registry.rb:198-199`) and invokes the host app's handler, which now processes attacker-supplied data as if it originated from `victim-shop.myshopify.com`.
