### Title
Missing sender-authorization check for `RequestState` messages in `orb-relay-client` `PollerAgent::main_loop` - (File: `orb-relay-client/src/client.rs`)

### Summary
`orb-relay-client`'s `PollerAgent::main_loop` validates that incoming relay messages originate from the expected bound peer (`src.id == self.config.dst_id`) before processing them — except for one message type, `self_serve::app::v1::RequestState`, which is handled and answered *before* that check is performed. This is the same bug class as the `ChainlinkLightClient` finding: a handler that is supposed to be reachable only by one specific authorized counterpart lacks the access-control check that every other code path enforces.

### Finding Description
In the connection loop, incoming payloads are matched and dispatched: [1](#0-0) 

Specifically, `self_serve::app::v1::RequestState::matches(&payload)` is checked and answered by resending `self.last_message` immediately, with no verification of `src.id`. Every other payload path first checks `else if src.id != self.config.dst_id` and rejects/logs mismatched senders before calling `self.handle_message(...)`: [2](#0-1) 

The `Config` struct stores the single `dst_id` this client instance is supposed to talk to for a session (the bound app or orb for a given signup): [3](#0-2) 

This client is used by orb-core's self-serve signup flow to gate biometric capture start/end and to exchange signup state with the paired phone app over the relay backend: [4](#0-3) 

Because the `RequestState` branch skips the `src.id`-equality check that guards every other message type, any relay-connected entity that can get a message routed to this client (e.g. due to relay-server-side multiplexing/misrouting, a stale/reused session id, or a bug in the relay backend's own routing enforcement) can force the client to resend its last outgoing state message, bypassing the client-side identity check that is otherwise consistently applied. This mirrors the `ChainlinkLightClient.sol` issue: one specific entrypoint was carved out without the authorization check that protects the rest of the surface.

### Impact Explanation
If the relay backend's server-side authorization has any gap (e.g., stale sessions, replay of `AnnounceOrbId`, or routing bugs), the missing client-side check on `RequestState` means the orb-core relay client itself provides no defense-in-depth: it will hand its `last_message` (which can include signup/session-state payloads such as `CaptureStarted`, `SignupEnded`, etc.) to whatever peer the relay server routed the message from, without independently verifying that peer is the one bound to this signup session (`dst_id`). This creates a possible cross-signup/session state disclosure path, since the check that is meant to enforce "only the paired counterpart can interact with this session" is inconsistently applied only in this code.

### Likelihood Explanation
Likelihood is Low-to-Medium: exploitation depends on a gap in the relay backend's own per-session authorization/routing (this client relies on `TokenAuth`/`ZkpAuth` and server-enforced routing as the primary control). The vulnerability is a concrete, code-level access-control inconsistency (medium confidence, directly analogous to the reported bug class), but its practical exploitability is contingent on the relay server allowing a message to reach a client instance from a source other than its configured `dst_id` — a scenario not fully verifiable from the client-side code alone.

### Recommendation
Move the `src.id != self.config.dst_id` check to run uniformly, before any payload-type-specific handling — including the `RequestState` branch — so that `RequestState` messages are only honored when they originate from the entity this client instance is bound to for the current session, consistent with the enforcement already applied to all other message types.

### Proof of Concept
1. A relay client is instantiated in `Orb` mode with `dst_id = "App-A"` for signup session A.
2. A message is routed to this client whose `payload` matches `self_serve::app::v1::RequestState` but whose `src.id` is `"App-B"` (a different/unrelated session or entity), due to any relay-server-side routing/session-management gap.
3. In `main_loop`, the `if self_serve::app::v1::RequestState::matches(&payload).is_some()` branch (`orb-relay-client/src/client.rs:436-440`) fires first and unconditionally sends `self.last_message` back — the `src.id != dst_id` guard on line 441 is never reached for this message type, so the state is disclosed to `"App-B"` without any binding check.

async fn proceed_with_biometric_capture(orb: &mut Orb) -> Result<bool> {
    let Config {
        self_serve,
        self_serve_app_skip_capture_trigger,
        self_serve_app_capture_trigger_timeout,
        ..
    } = *orb.config.lock().await;
    if !self_serve || self_serve_app_skip_capture_trigger {
        // Biometric capture not gated by a user action. Continue.
        orb.ui.signup_start();
        return Ok(true);
    }

    let orb_relay = orb.orb_relay.as_mut().expect("orb_relay to exist");

    tracing::info!("Waiting for self-serve biometric-capture trigger...");
    if let Err(e) = orb_relay
        .wait_for_msg::<self_serve::app::v1::StartCapture>(self_serve_app_capture_trigger_timeout)
        .await
    {
        if let Err(e) = orb_relay.send(self_serve::orb::v1::CaptureTriggerTimeout {}).await {
            tracing::warn!("failed to send CaptureTriggerTimeout: {e}");
        };
        orb.ui.signup_fail(SignupFailReason::Timeout);
        tracing::warn!("Self-serve biometric-capture start was not triggered: {e}");
        return Ok(false);
    };

    tracing::info!("Self-serve biometric-capture start triggered");
    orb.ui.signup_start();

    tracing::info!("Self-serve: Informing orb-relay that biometric_capture has started");
    orb_relay
        .send(self_serve::orb::v1::CaptureStarted {})
        .await
        .inspect_err(|e| tracing::error!("Relay: Failed to CaptureStarted: {e}"))?;

    Ok(true)
}
