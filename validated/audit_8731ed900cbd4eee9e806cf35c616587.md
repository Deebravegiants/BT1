### Title
Unauthenticated Emporium `runAction` calls via zero-token `MainEVMCircuitMin` proof allow arbitrary calls from the Emporium contract, draining ETH/tokens held by Emporium - (File: `contracts/CircomDataBuilder.sol`, `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
When `circomData.externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `circomData.erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` routes the transaction to a stripped-down "Min" public-input set (`formInputEmporiumMin`) that corresponds to `MainEVMCircuitMin.circom`, a circuit that contains **no signature check, no Merkle-membership check, and no nullifier check** — it only proves knowledge of a `messageSeed` whose Poseidon hash equals the attacker-chosen `emporiumMessage`. Because `messageSeed` is a free private input, this "proof" is trivially forgeable by anyone with no private key or owned UTXO. This path reaches `EmporiumUpgradeable.runAction`, which — when `stack.signerAddress == address(0)` — skips the EIP-712 signature check in `verifyWallet` entirely and executes attacker-supplied stateless calls `op.endpoint.call{value: op.value}(op.callData)` **from the Emporium contract itself**, moving any ETH/tokens the Emporium happens to hold.

### Finding Description
`CircomDataBuilder.formInputForCircom` special-cases the Emporium action with zero declared tokens: [1](#0-0) 

The resulting public-signal vector (`[emporiumMessage, timeStamp, calldataHash]`) matches `MainEVMCircuitMin`, which has no `spendingPublicKey`, no `eddsaSignature`, no `rootHashHinkal`, and no nullifier/commitment logic — only a trivial Poseidon binding of a self-chosen seed to `message`: [2](#0-1) 

By contrast, the normal path (`MainEVMCircuit.circom`) enforces `spendingPublicKey`/`eddsaSignature`/`signedMessageHash` and per-input nullifier/root checks: [3](#0-2) [4](#0-3) 

Because `circomData.erc20TokenAddresses.length == 0` also forces `dimensions.tokenNumber == 0` (enforced in `dimensionsCheck`), every per-token loop in `Hinkal.transact` — including the balance-diff equality check that is supposed to bind `balanceDif == amountChanges[i] + utxoAmount` — iterates zero times and is never evaluated: [5](#0-4) [6](#0-5) 

`Hinkal._externalTransact` then dispatches to `EmporiumUpgradeable.runAction` with an empty `deltaAmountChanges` array: [7](#0-6) 

Inside `runAction`, the attacker-controlled `EmporiumStack` is decoded straight from `externalActionData.externalActionMetadata` (only bound cryptographically via `calldataHash`, never checked against a signer or UTXO owner by the circuit): [8](#0-7) 

`verifyWallet` only performs the EIP-712 signature check when `stack.signerAddress != address(0)`; if it is `address(0)`, verification is skipped completely (only message-replay is checked): [9](#0-8) 

In the stateless branch (`op.invokeWallet == false` or `signerAddress == address(0)`), the only restriction is that the call's selector isn't `callHinkalWallet`/`doSendToRelay`; any other target/selector/value is allowed and executed with `msg.sender == Emporium`: [10](#0-9) 

Since `circomData.erc20TokenAddresses.length == 0`, the post-call balance-accounting loop that would otherwise catch balance changes and mint a corresponding output UTXO never executes: [11](#0-10) 

The code's own comment acknowledges the Emporium contract is expected to sometimes hold residual balances across calls ("there were some funds on emporium before the call"), and it has a `receive()` accepting bare ETH transfers: [12](#0-11) [13](#0-12) 

**Equality broken:** the balance-conservation invariant `balanceDif == amountChanges[i] + utxoAmount` that ties every real fund movement in `transact()` to a ZK-proven, nullifier-consuming statement is never evaluated for this path (zero-length token array), yet `runAction` still executes an arbitrary, attacker-chosen external call carrying `msg.value` and `msg.sender == Emporium`. This is a "value moved by an external action but not counted in the balance equation" case, gated only by a proof that authenticates nothing.

### Impact Explanation
Any unprivileged EOA can:
1. Choose an arbitrary `messageSeed`, compute `emporiumMessage = Poseidon(messageSeed)`.
2. Generate a trivially valid Groth16 proof for `MainEVMCircuitMin` (no secret key, no owned UTXO, no Merkle membership needed).
3. Call `Hinkal.transact` with `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, and `externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)` and a stateless `op` pointing `endpoint`/`callData`/`value` at any target.
4. Have the Emporium contract execute this call as `msg.sender`, moving out any ETH/ERC20 balance the Emporium holds (protocol/relay fees, dust left over from prior swaps, mistakenly-sent tokens) to an address of the attacker's choosing.

This is unauthorized asset movement from a protocol-controlled contract without any valid authorization from a prover or signer — theft of protocol/relay funds held by Emporium (High), and if Emporium is ever left holding meaningfully valuable balances (e.g., during multi-leg swaps or accrued fees before sweep), it could escalate to significant fund loss.

### Likelihood Explanation
High. No privileged role, relayer collusion, or victim action is required — a single unprivileged EOA with a snarkjs proving key for the publicly known `MainEVMCircuitMin` circuit (or any circuit satisfying the trivial constraint) can trigger this at will, and the check that is supposed to gate it (`Invalid Proof`) is satisfied by design for this legitimate-looking "min" circuit path, since it's the intended verifier for zero-token Emporium calls.

### Recommendation
- Do not allow `signerAddress == address(0)` (unsigned) stateless Emporium operations to target arbitrary `endpoint`/`value`; either require `op.value == 0` and a strict allow-list of endpoints for the unsigned path, or remove the unsigned path entirely.
- Ensure the "Min" circuit path cannot be used to authorize movement of protocol-held funds — bind `MainEVMCircuitMin`'s trust to something the sender actually controls (e.g., verify `msg.sender`/`originalSender` against a real secret, or require `stack.signerAddress != address(0)` whenever `erc20TokenAddresses.length == 0` and ops include value-bearing/target-arbitrary calls).
- Sweep/never let the Emporium contract accumulate spendable balances across unrelated transactions; if residual balances are unavoidable, protect them with an owner-only withdrawal path instead of relying on the transact() proof flow.

### Proof of Concept
1. Off-chain: pick any `messageSeed`; compute `message = Poseidon(messageSeed)`; set `circomData.emporiumMessage = message`; generate a Groth16 proof for `MainEVMCircuitMin` with public inputs `[message, timeStamp, calldataHash]` (`circuits/MainEVMCircuitMin.circom`).
2. Build `circomData`: `erc20TokenAddresses = []`, `amountChanges = []`, `inputNullifiers = []`, `outCommitments = []`, `externalActionData = {externalAddress: <Emporium proxy>, externalActionId: HINKAL_EMPORIUM_ACTION_ID, externalActionMetadata: abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation({endpoint: <attacker/target>, invokeWallet: false, value: <ETH held by Emporium>, callData: ""})], maxFee: 0, deadline: type(uint256).max, v:0, r:0, s:0}))}`.
3. Call `Hinkal.transact(a, b, c, dimensions{tokenNumber:0,...}, circomData)` from any EOA.
4. `performHinkalChecks` passes (hash matches, dimensions match zero-length arrays); `verifyProof` passes (circuit is satisfied trivially); `rootHashExists` passes with any valid existing root; balance-diff loop in `Hinkal.transact` is skipped (zero tokens); `_externalTransact` calls `EmporiumUpgradeable.runAction`, which skips signature verification (`signerAddress == address(0)`) and executes the attacker's call from the Emporium contract, transferring `value` ETH (or invoking arbitrary logic) out of the Emporium's balance to the attacker-chosen `endpoint`.
