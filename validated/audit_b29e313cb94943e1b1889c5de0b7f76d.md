### Title
Shared Emporium contract as ERC721 recipient allows any unprivileged user to steal a victim's in-flight Uniswap V3 LP position/fees - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` CASE 2 ("stateless") ops execute `op.endpoint.call(op.callData)` directly as `address(this)` (the shared, singleton Emporium contract), with no signer/owner binding. If a victim's op mints a Uniswap V3 LP NFT with `recipient = address(this)`, the NFT becomes owned by the shared Emporium contract rather than any user-specific address, and any other unprivileged caller can later submit their own `runAction` invoking `positionManager.collect`/`transferFrom` on that same `tokenId`, diverting the victim's fees/position to themselves.

### Finding Description
The claimed equality is: `owner(LP_NFT_before_attacker_tx) == HinkalWallet/stealthAddress(victim)`. In practice this equality never holds for CASE 2 ops, because:

- `runAction` decodes `EmporiumStack` from attacker-controlled `circomData.externalActionData.externalActionMetadata` [1](#0-0) .
- For CASE 2 (`op.invokeWallet=false` or `stack.signerAddress==address(0)`), the call is executed directly by Emporium itself: `op.endpoint.call{value: op.value}(op.callData)` [2](#0-1) . Any external protocol seeing `msg.sender` sees `address(EmporiumUpgradeable)` — a single, shared, non-user-specific address used by *every* Hinkal user routing through this pattern.
- If a victim's op mints a Uniswap NFT with `recipient = address(this)` (Emporium), the NFT is now owned by the shared Emporium contract, not the victim's stealth wallet.
- `verifyWallet` for `stack.signerAddress == address(0)` only marks `usedMessages[circomData.emporiumMessage]` and returns immediately — no signature or ownership binding is required [3](#0-2) .
- `onlyAllowedRecipient` only checks `msg.sender` (i.e., that the caller of `runAction` is Hinkal itself), it does not restrict or authenticate the content of `op.callData`/`op.endpoint` against any prior state or victim identity [4](#0-3) .
- The post-call bookkeeping (`balancesBefore`/`balancesAfter`, `deltaAmountChanges`) only tracks ERC20 balances for tokens explicitly listed in `circomData.erc20TokenAddresses` [5](#0-4) ; there is no accounting whatsoever for ERC721 tokens/NFTs left owned by Emporium. Nothing detects, reverts, or "claims" the leftover NFT for the victim.

Because any unprivileged attacker can generate their own valid proof/CircomData and call `Hinkal.transact()` naming `EmporiumUpgradeable` as the external action, they can freely craft `ops[0]` to call `positionManager.collect(CollectParams{tokenId: victimTokenId, recipient: attacker})` (or even `transferFrom`/`safeTransferFrom` of the NFT itself, since Emporium is the recorded `ownerOf`). Since Emporium is the actual on-chain owner/approved caller for the NFT (as the Uniswap V3 NPM sees `msg.sender == Emporium`), the call succeeds and diverts fees (or the position itself) to the attacker. None of the existing checks (`performHinkalChecks`, proof verification, nullifier/root checks, `onlyAllowedRecipient`) constrain `op.endpoint`/`op.callData` content against the victim's prior transaction or any ownership record, since they only validate the attacker's own deposit/UTXO proof, which is unrelated to the victim's leftover NFT.

### Impact Explanation
Direct theft of a victim's in-flight Uniswap V3 LP position and/or accrued fees by an unrelated, unprivileged attacker — this is Critical severity ("direct theft of shielded or in-flight user funds"). The attack is fully repeatable against any victim tx that leaves any valuable state (ERC721, or any other externally-observable asset/approval) parked on the shared Emporium contract via a CASE 2 op.

### Likelihood Explanation
Requires only that a victim (or victim-facing frontend/integration) constructs a CASE 2 EmporiumStack op that mints/leaves an ERC721 (or other un-tracked asset) with `recipient = address(this)`. `tokenId` and Uniswap position manager address are both publicly observable on-chain. The attacker's cost is a single valid Hinkal deposit/proof plus gas — no special role or victim key material needed. Given that CASE 2 stateless ops are explicitly supported and unrestricted in `endpoint`/`callData` content, this is a straightforward, low-cost, fully deterministic exploit whenever the precondition (an asset type not tracked by the ERC20 balance diff mechanism, like ERC721, is left on Emporium) occurs.

### Recommendation
Do not allow CASE 2 (stateless, unauthenticated) ops to leave any state (especially ERC721/ERC1155 ownership, allowances, or other claimable positions) on the shared `EmporiumUpgradeable` contract. Options:
- Forbid `recipient = address(this)` for stateless ops entirely, or require any minted/received NFTs to be immediately forwarded to `msg.sender`/the user's stealth address within the same `runAction` call, and add ERC721/1155 balance accounting (via `onERC721Received` hooks and end-of-call sweep) analogous to the ERC20 `balancesBefore/After` diff.
- Alternatively, require CASE 1 (`invokeWallet=true` with a per-user `HinkalWallet` as `signerAddress`) for any operation that can leave persistent, claimable state (LP positions, staking receipts, etc.), since `HinkalWallet` is per-user and NFTs left there are not accessible to other users.

### Proof of Concept
Foundry fork test:
1. Deploy a mock/real Uniswap V3 `INonfungiblePositionManager` and `EmporiumUpgradeable`.
2. Victim: call `Hinkal.transact()` with valid proof/CircomData naming Emporium, `EmporiumStack.ops[0] = {endpoint: positionManager, invokeWallet: false, callData: abi.encodeCall(mint, MintParams{..., recipient: address(emporium)})}`.
   - Assert `positionManager.ownerOf(tokenId) == address(emporium)` (not victim's stealth address) after this tx.
3. Attacker: call `Hinkal.transact()` with attacker's own valid proof/CircomData naming Emporium, `EmporiumStack.ops[0] = {endpoint: positionManager, invokeWallet: false, callData: abi.encodeCall(collect, CollectParams{tokenId: victimTokenId, recipient: attacker, amount0Max: type(uint128).max, amount1Max: type(uint128).max})}`.
4. Assert `positionManager.ownerOf(tokenId)` is unchanged (`address(emporium)`) but `token0.balanceOf(attacker)`/`token1.balanceOf(attacker)` increased by the collected fee amounts, i.e. `fees_collected_by(attacker) > 0`, proving `owner(LP_NFT)_before_attacker_tx == address(Emporium) != victim`, and that the attacker successfully extracted value never authorized by the victim.
