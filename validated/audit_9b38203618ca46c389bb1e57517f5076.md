## Title
Zero default reward on hyperbridge-originated system messages removes any economic incentive to deliver them, permanently freezing relayer fee withdrawals and other system state - ([File: docs/outbound-request-incentivization.md], [File: modules/pallets/relayer/src/outbound_request.rs])

### Summary
The DYAD finding shows that when the reward for a beneficial-but-costly action (`CR<1` liquidation) is zero or negative, no rational actor performs it, and the protocol accumulates unresolved bad state. Hyperbridge has a structurally identical situation for **hyperbridge-originated** ISMP requests: `host-executive`, `intents-coprocessor`, `token-governor`, and the relayer pallet's own fee-withdrawal path all dispatch `PostRequest`s with `FeeMetadata { payer: [0u8;32].into(), fee: Default::default() }` — i.e. zero fee. Relayers that deliver these messages incur real gas/verification cost on the destination chain for zero payment.

### Finding Description
The design document explicitly identifies this as "the problem": [1](#0-0)  — hyperbridge-originated system messages dispatch with zero fee and zero payer, so "relayers have no economic reason to pick them up, and the only thing that keeps them flowing today is altruism."

The mitigation implemented is `OutboundRequestDeliveryReward`, a per-`module_id` reward stored in `pallet-relayer`, defaulting to `0` (`StorageMap<..., ValueQuery>`), which the on-chain claim logic explicitly treats as "not on the allowlist" until governance calls `set_outbound_request_delivery_reward`: [2](#0-1) 

Critically, the off-chain relayer's pre-delivery filter (`retain_incentivized_requests`) actively **drops** any hyperbridge-originated `PostRequest` whose `from` module is not in the current non-zero-reward allowlist snapshot, before delivery is even attempted — this is confirmed by the design doc's own description of the filter behavior [3](#0-2) . This mirrors the DYAD pattern exactly: an unincentivized, costly action (delivery / liquidation) is simply never performed by rational actors, and until governance manually whitelists a module with a positive reward, the module's messages are unclaimable/undeliverable by the reference relayer.

The most severe instance of this is the **relayer pallet's own withdrawal path**, called out by name in the design doc as one of the affected system dispatchers alongside `host-executive`, `intents-coprocessor`, and `token-governor` [4](#0-3) . This is the `WithdrawRelayerFees` message documented elsewhere as the mechanism by which relayers redeem fees they already earned on Hyperbridge, dispatched to the module id `b"HYPR-FEE"` and settled by `RefundingRouter` on the destination [5](#0-4) . If governance has not set a non-zero `OutboundRequestDeliveryReward` for this module id (which is the default state, per `ValueQuery`), no relayer has any economic reason to deliver another relayer's own fee-withdrawal request — creating a circular incentive gap identical in structure to "no incentive to liquidate CR<1": the actor who would benefit (the withdrawing relayer) cannot pay enough to make delivery worthwhile for a third party, and the reference implementation's pre-delivery filter actively discards the message rather than delivering it altruistically.

### Impact Explanation
Until governance explicitly enables (sets a non-zero reward for) each system `module_id`, cross-chain system messages — including a relayer's own earned-fee withdrawal, host parameter propagation, and intents-coprocessor/token-governor messages — have zero economic incentive for third-party delivery and are actively filtered out by the reference relayer's `retain_incentivized_requests` gate. This can result in **permanent freezing of relayer-earned fees** (the withdrawal message never gets delivered) and desynchronization of critical host parameters/governance state across chains, since the reference relayer will not deliver these messages without a positive reward once the allowlist filter is active.

### Likelihood Explanation
High under the current default configuration: `OutboundRequestDeliveryReward` defaults to `0` for every `module_id` (`ValueQuery`), so this is not a misconfiguration edge case but the out-of-the-box state for any newly deployed or newly added system module until an explicit governance extrinsic is executed. The design doc itself frames this as the motivating "problem," confirming it is a real, currently-relevant gap rather than a theoretical one [6](#0-5) .

### Recommendation
- Require governance to set a non-zero `OutboundRequestDeliveryReward` for all core system module ids (especially the relayer pallet's own `b"HYPR-FEE"` withdrawal path) as part of runtime genesis/migration, rather than relying on a post-deployment manual `sudo` call, so no window exists where relayer fee withdrawals or other core system messages are undeliverable by design.
- Consider making the off-chain `retain_incentivized_requests` filter fail open (deliver anyway) specifically for the relayer's own fee-withdrawal module, since failing to deliver that message directly harms relayer participation incentives protocol-wide.
- Add a monitoring/alert on `OutboundRequestDeliveryReward` being zero for any module that has pending, unclaimed `RequestCommitments`.

### Proof of Concept
1. Deploy Hyperbridge with the outbound-request-incentivization feature active (as documented in `docs/outbound-request-incentivization.md`) and do **not** call `set_outbound_request_delivery_reward` for the relayer pallet's `b"HYPR-FEE"` module id (the default/undeployed state).
2. Have a relayer accumulate fees on Hyperbridge and dispatch a `WithdrawRelayerFees` request via `RequestCommitments`, using `FeeMetadata { payer: [0u8;32], fee: 0 }` as per the documented dispatch pattern.
3. Observe that the reference tesseract relayer's `retain_incentivized_requests` filter drops this event from delivery because `b"ismp-ast"`-style module id (in this case `b"HYPR-FEE"`) is not present in the `incentivized_outbound_request_modules()` snapshot (reward = 0).
4. The withdrawal request is never delivered to the destination, so `RequestReceipts[commitment]` is never populated and the relayer's earned fees remain permanently unclaimed on Hyperbridge, unless the withdrawing relayer manually self-relays (delivers) its own withdrawal message at its own expense — the same "must act at a loss" dynamic as the CR<1 liquidation bug.

Note: I was unable to directly confirm from the index whether governance has actually configured a non-zero reward for `b"HYPR-FEE"` at genesis in the shipped runtime configs (`parachain/runtimes/*`), since `modules/pallets/relayer/src/lib.rs` content did not fully resolve in the tool output. This should be verified in a live session — if genesis configuration already sets a positive default reward for all core system modules, the practical severity of this finding is substantially reduced.

# Outbound Request Delivery Incentivization

How relayers that deliver a hyperbridge-originated request to a destination chain get paid in BRIDGE from the Hyperbridge treasury.

Tracking issue: [polytope-labs/hyperbridge#532](https://github.com/polytope-labs/hyperbridge/issues/532).

## The problem

A regular cross-chain message that flows *through* hyperbridge has a fee attached at origin (the source chain transfers `fee.payer → RELAYER_FEE_ACCOUNT` and records `RequestPayments[commitment]` in pallet-hyperbridge's child trie). When a relayer delivers and the destination receipt lands back on hyperbridge, the existing `accumulate_fees` flow credits that fee to the relayer. That whole pipeline assumes a *user* paid at origin.

But hyperbridge itself originates requests too: host parameter propagation, host-executive updates, intents-coprocessor responses, token-governor messages, the relayer pallet's withdrawal request. Today these all dispatch with `FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() }` (see `modules/pallets/host-executive/src/lib.rs:228`, `modules/pallets/intents-coprocessor/src/lib.rs:486`, `modules/pallets/relayer/src/lib.rs:638`, and `modules/pallets/token-governor/src/impls.rs`). Zero fee, zero payer. So relayers have no economic reason to pick them up, and the only thing that keeps them flowing today is altruism.

```markdown
1. A pallet on hyperbridge (host executive, intents coprocessor, token governor, the relayer pallet's own withdrawal path) calls `IsmpDispatcher::dispatch_request(post, fee)`. That creates an entry in `pallet_ismp::child_trie::RequestCommitments` keyed by the request commitment hash, and emits an ISMP `Event::PostRequest` with `post.source` set to the hyperbridge nexus state machine.

2. The tesseract outbound task is already subscribed to `proof_accepted_notification` on hyperbridge. When a BEEFY proof advances the dispatch root past the new request, the task wakes up and calls `query_ismp_events(cursor, latest_height)`. The returned vec contains that `Event::PostRequest` alongside everything else hyperbridge emitted in that range.

3. **Pre-delivery filter (off chain, gas saver).** Once per BEEFY notification the outbound loop calls `incentivized_outbound_request_modules()` on hyperbridge to snapshot every `module_id` with a non-zero `OutboundRequestDeliveryReward` into a `BTreeSet<Vec<u8>>`. `submit_for_dest` then runs `retain_incentivized_requests`: any `Event::PostRequest` whose `post.source == coprocessor` is dropped unless `post.from` is in the set. User-originated requests (`source != coprocessor`) are untouched. If the snapshot fetch fails the filter is a no-op for that cycle, so the relayer keeps delivering everything (same risk profile as before the filter existed). Governance updates show up in the next snapshot, so allowlist edits take effect within one BEEFY cycle.

4. `translate_events_to_messages` turns the surviving events into deliverable messages. `dest.submit(batch, coprocessor)` lands the batch on the destination. The returned receipts carry the original `query: Query { source_chain, dest_chain, nonce, commitment }` for each delivered message.

5. **Post-delivery trigger filter (off chain, claim shaping).** `forward_request_delivery_claims` walks `result.receipts`, keeps every `TxReceipt` whose `query.source_chain == coprocessor`, pairs each receipt back to the matching `PostRequest` extracted from the outgoing batch, persists `(commitment, encoded_request, delivery_height)` to the local DB, and pushes the claim onto the request-claim channel via `try_send`. `TxReceipt` only carries requests now (responses were removed from the protocol in #840), so there is nothing to filter out by message type. The pre-delivery filter has already narrowed the population to allowlisted modules, so in steady state every hyperbridge-originated receipt at this point should be claim-eligible.

6. **On-chain enforcement.** When the claim arrives, the pallet hashes the request, confirms `request.source == IsmpHost::host_state_machine()`, confirms `RequestCommitments::get(commitment).is_some()`, then keys the reward lookup by `request.from`. The module must be in the allowlist (non-zero reward set by governance) or the claim is rejected before any state proof verification work runs. This is the only gate that actually matters for correctness; the off-chain stages above just avoid burning destination gas on requests the pallet would reject anyway.

So the relayer never queries a "list of hyperbridge requests" index or treats hyperbridge-originated events as a special class at translation time. Identification is a single equality check on a field already on the wire, narrowed by an on-chain allowlist snapshot for gas, and enforced authoritatively at claim time.
```

## Hyperbridge-initiated relayer fee withdrawals

Relayers accumulate their earned fees on Hyperbridge. When a relayer initiates a withdrawal, Hyperbridge dispatches a POST request back to the source chain. `pallet-ismp`'s [`RefundingRouter`](https://github.com/polytope-labs/hyperbridge/blob/main/modules/pallets/ismp/src/dispatcher.rs) intercepts requests addressed to the built-in module id `b"HYPR-FEE"`, decodes a `WithdrawRelayerFees` payload, and transfers the owed balance from `RELAYER_FEE_ACCOUNT` to the relayer.

No runtime configuration is required to enable this — it ships with `pallet-ismp`.
