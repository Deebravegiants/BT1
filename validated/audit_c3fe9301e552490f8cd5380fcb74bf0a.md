### Title
Tokens pushed to the controller inside `flash_position`'s callback for assets not declared in `collaterals`/`refund_assets` are permanently stranded — (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
Analogous to ETH sent along with an ERC20 `takeOrders` call, `flash_position` accepts arbitrary token transfers into the controller during the receiver callback but only credits assets declared in `collaterals` and only refunds assets declared in `refund_assets`. Any other token balance pushed to the controller — e.g. the receiver returning leftover swap output in a third asset, or pushing a collateral asset whose `HubAssetKey` was omitted — is never credited to the account and never returned. No sweep, rescue, or claim path exists for controller-held balances, so the tokens are frozen permanently.

### Finding Description
`process_flash_position` snapshots controller balances for `collaterals` and `refund_assets` before invoking the receiver (`collateral_before`, `refund_before` at `contracts/controller/src/strategies/flash_position.rs:120-143`). After the callback:

- `collect_collateral_deposits` (`flash_position.rs:325-352`) measures the per-asset delta and deposits it only for assets listed in `collaterals`.
- `refund_listed_assets` (`flash_position.rs:372-384`) returns the delta only for assets listed in `refund_assets`, via `refund_controller_balance_delta` (`contracts/controller/src/payments.rs:41-52`), which explicitly preserves the pre-existing baseline balance and only forwards the delta.

The API docs confirm the gap: "The callback pushes declared collateral to the controller; undeclared controller balances are not credited" (`skills/xoxno-lending-contracts/abi.md:57`). The same measured-delta pattern in `repay_debt_from_controller` (`contracts/controller/src/strategies/legs.rs:60-80`) and the test `test_repay_debt_with_collateral_refund_only_uses_repay_excess` (`tests/test-harness/tests/strategy/edge/rejections.rs:88-108`) show this is deliberate: pre-existing or undeclared controller balances are preserved rather than swept — meaning nothing ever moves them out. A grep of `contracts/controller/src` finds no sweep/recover/rescue function, so a balance that lands in the controller outside the declared sets has no exit path.

### Impact Explanation
Permanent freezing of user funds: any token amount the receiver (or the caller via the receiver) transfers to the controller for a hub-listed asset that was not included in `collaterals` or `refund_assets` is neither deposited nor refunded, and no unprivileged or privileged entrypoint can withdraw stray controller balances.

### Likelihood Explanation
Conditional on a caller mistake, mirroring the original report. The callback pattern makes the mistake plausible: a receiver that swaps flash-proceeds on an external venue will commonly end up holding residual tokens (dust, intermediate route assets, or a collateral token supplied under the wrong hub key) and the natural remediation — transfer them back to `controller` as instructed — strands them if the asset was not pre-declared in `refund_assets`. The function already anticipates residuals via `refund_assets`, but forgetting to list an asset, or listing a `HubAssetKey` with a different `hub_id` (uniqueness is enforced only by token address, `flash_position.rs:189-197`), produces the loss. Reachable by any unprivileged caller running their own receiver contract.

### Recommendation
Reject or reclaim undeclared inbound transfers. Concretely:

- After `refund_listed_assets`, re-snapshot all assets touched (union of `collaterals`, `refund_assets`, and `debt.asset`) and assert each controller balance equals its baseline; or
- Provide a permissionless `sweep(asset, to)` entrypoint that transfers controller balances exceeding tracked obligations, so mistakenly pushed funds are recoverable; or
- Document and enforce at the SDK level that the receiver must return every non-collateral token it holds by listing it in `refund_assets` before the call.

### Proof of Concept
1. Caller invokes `controller.flash_position(caller, account_id, spoke_id, Multiply, debt=(hub, USDC), amount, receiver, data, collaterals=[((hub, XLM), min)], refund_assets=[XLM])`.
2. Inside `execute_flash_position`, the receiver swaps USDC for XLM, pushes XLM to the controller to satisfy the collateral minimum, and also transfers back leftover USDC (or a third token such as EURC) to `controller`.
3. `collect_collateral_deposits` credits only the XLM delta; `refund_listed_assets` iterates only `[XLM]` — since `XLM` was also the collateral and `refund_assets` must exclude collateral assets (`validate_refund_assets`, `flash_position.rs:248-254`), the caller cannot have listed the debt token or the third token redundantly.
4. The leftover USDC/EURC balance remains in the controller. No entrypoint transfers it out; `refund_controller_balance_delta` only forwards deltas above a snapshot baseline, so subsequent calls preserve the stranded balance indefinitely.
