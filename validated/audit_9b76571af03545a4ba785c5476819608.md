## Title
Relayer fee withdrawal dispatches a zero-relayer-fee ISMP message, permanently stranding withdrawn funds if no altruistic relayer delivers it - (File: `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
`Pallet::withdraw` in `pallet-relayer` zeroes out a relayer's accumulated `Fees` balance and dispatches a cross-chain ISMP POST request instructing the destination chain (EVM host manager or `HYPERBRIDGE_MODULE_ID` on Substrate) to disburse the withdrawn amount to the beneficiary — but the dispatch is made with `fee: Default::default()` (zero relayer fee), meaning no Hyperbridge relayer has any economic incentive to actually deliver the message.

### Finding Description
`withdraw()` computes `available_amount`, increments the nonce, immediately zeroes the local `Fees::<T>` entry, and dispatches the payout instruction via `IsmpDispatcher::dispatch_request`: [1](#0-0) 

The `FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() }` used here sets the relayer fee to zero. In `pallet_ismp`'s dispatcher, a zero fee means no escrow transfer happens and, more importantly, no reward exists for a relayer picking up and delivering this request: [2](#0-1) 

This mirrors the exact bug class in the external report: an action that marks internal state as "already settled" (here, `Fees::<T>::insert(..., U256::zero())`, analogous to `_executeClaim()` recording the claim) *before* the cross-chain settlement message is guaranteed to be delivered, while that settlement message itself carries zero incentive for relayers to transmit it (analogous to `_settleClaim()`'s `xcall()` omitting the Connext relayer fee).

The project's own internal engineering notes confirm this is a known, unresolved gap across *all* hyperbridge-originated system dispatches, explicitly including the relayer pallet's withdrawal path: [3](#0-2) 

The `DispatchPost` used for the withdrawal also sets `timeout: 0` (never expires), so there is no automatic timeout/refund path that could restore the relayer's `Fees` balance if the message is never relayed — the withdrawn amount is not credited anywhere else on the source chain once `Fees` is zeroed: [4](#0-3) 

### Impact Explanation
Any relayer that calls `withdraw()` for their earned fees moves their balance out of `Fees::<T>` on the source (hyperbridge) chain in the same transaction that dispatches an unincentivized cross-chain message. If no altruistic third party relays this specific request (there is no reward for doing so, unlike normal user-originated ISMP requests), the destination-chain payout in `WithdrawalRequest`/`WithdrawalParams` never executes, and the relayer's fees are effectively lost — the source-chain accounting has already zeroed the balance with no compensating credit and no timeout-based refund. This directly affects relayer fee and reward accounting, a component explicitly in scope, and results in permanent loss of relayer-earned funds.

### Likelihood Explanation
Likelihood is elevated because: (1) `withdraw()` is a normal, frequently used, unprivileged relayer action, not an edge case; (2) the zero-fee dispatch is present in the shipped code path with no gating on network liveliness of altruistic relayers; (3) the project's own documentation independently identifies this exact zero-fee/zero-payer dispatch pattern (including this withdrawal call site) as lacking any delivery incentive today, corroborating the root cause rather than relying on speculation.

### Recommendation
Attach a non-zero relayer fee (and legitimate `payer`) to the `DispatchPost` used in `Pallet::withdraw`, sourced from a system-owned/treasury account, so `RequestPayments`/relayer-reward accounting is populated and the existing `accumulate_fees` incentive pipeline picks up the delivery. Alternatively, implement the "outbound request delivery incentivization" design already sketched in `docs/outbound-request-incentivization.md` (per-`module_id` treasury-funded reward claimable against a destination delivery proof) before or in place of zeroing `Fees::<T>` optimistically, and consider zeroing `Fees::<T>` only after confirmed delivery, or maintaining a pending-withdrawal record that can be retried/refunded if delivery does not occur within a bounded timeout.

### Proof of Concept
1. A relayer accrues rewards via `accumulate_fees`, populating `Fees::<T>::get(dest_chain, relayer_address)`.
2. Relayer calls `Pallet::withdraw` with a valid signature; nonce increments, `Fees::<T>` is zeroed at line 177, and `dispatch_request` is invoked with `FeeMetadata { payer: [0u8;32].into(), fee: Default::default() }` (line 173).
3. Because `fee == 0`, no relayer has economic incentive to submit the proof needed to execute `WithdrawalRequest`/`WithdrawalParams` on the destination chain's host manager.
4. If no altruistic relayer processes it (and `timeout: 0` means it never expires to trigger any refund logic), the withdrawal is permanently pending on the destination while the source-chain `Fees` balance is already zero — the relayer's earned funds are unrecoverable through any protocol-defined path.

```markdown
## The problem

A regular cross-chain message that flows *through* hyperbridge has a fee attached at origin (the source chain transfers `fee.payer → RELAYER_FEE_ACCOUNT` and records `RequestPayments[commitment]` in pallet-hyperbridge's child trie). When a relayer delivers and the destination receipt lands back on hyperbridge, the existing `accumulate_fees` flow credits that fee to the relayer. That whole pipeline assumes a *user* paid at origin.

But hyperbridge itself originates requests too: host parameter propagation, host-executive updates, intents-coprocessor responses, token-governor messages, the relayer pallet's withdrawal request. Today these all dispatch with `FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() }` (see `modules/pallets/host-executive/src/lib.rs:228`, `modules/pallets/intents-coprocessor/src/lib.rs:486`, `modules/pallets/relayer/src/lib.rs:638`, and `modules/pallets/token-governor/src/impls.rs`). Zero fee, zero payer. So relayers have no economic reason to pick them up, and the only thing that keeps them flowing today is altruism.
```
