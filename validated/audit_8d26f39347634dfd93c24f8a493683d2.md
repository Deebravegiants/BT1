Based on my investigation, I found a genuine analog to the Optimism `move()` re-org vulnerability in orb-core's user QR-code handling flow. The core bug class is: **a commitment/authorization is bound only to a coarse identifier (an index/ID), and if the underlying referent shifts between the moment identification is performed and the moment the identified action is actually consumed, the wrong entity is authorized/credited** — analogous to `attack()`/`defend()` binding only to `parentIndex` instead of the claim hash.

### Title
Operator-authorization reuse without re-binding to the specific signup action allows misattribution of enrollment authorization across a stale QR-code window - (File: `src/plans/mod.rs`)

### Summary
The Orb's signup flow verifies the operator's QR-code once via `verify_operator_qr_code`, producing an `OperatorData { qr_code, location_data, timestamp }` tuple [1](#0-0) . That single verification result is then reused across multiple *subsequent, distinct* authorization-consuming actions (initial user QR-code scanning, resumed scanning after `do_signup` restarts, and ultimately the personal-custody-package attribution `operator_id`) as long as `operator_data.timestamp.elapsed() < operator_qr_expiration_time` [2](#0-1) . The only "identification of target" check is a coarse elapsed-time comparison against a fixed expiration window — there is no re-commitment or re-binding of the specific operator identity to the specific signup/enrollment event that eventually consumes it, mirroring the Optimism bug where `move()` bound only to a `parentIndex` (a slot) rather than the claim's actual content/commitment.

### Finding Description
`scan_remaining_qr_codes` and `scan_initial_qr_codes` treat a previously-validated `OperatorData` as valid "target identification" for a brand-new signup attempt purely based on `Instant` elapsed time [3](#0-2) . The `operator_id` recorded into the signup's attribution/salting logic (`make_info_json`) is taken directly from this reused, time-window-gated `operator_qr_code.user_id` without any fresh cryptographic commitment tying that specific operator authorization to the specific enrollment about to be submitted [4](#0-3) . Just as the Optimism dispute game let an attacker replace the referenced claim in the window between commit and execution because the `move()` only carried a slot index, here the orb only carries a boolean "still within `operator_qr_expiration_time`" check rather than validating that the operator identity is still current/present for *this specific* signup outcome (e.g., after a `MasterPlan::run` loop iteration or a background continuation that reuses `initial_qr_codes` across loop iterations) [5](#0-4) .

### Impact Explanation
If the reused, stale `operator_data` is applied to a signup/enrollment event whose real-world circumstances changed within the expiration window (e.g., attribution, location data, or extension-mode gating tied to `operator_qr_code`), the wrong operator identity/state ends up permanently embedded in the signup's salted attribution hashes and backend records via `signup_post::request`'s `distributorId` field [6](#0-5) . This is a cross-signup state-bleed/misattribution impact analogous to the bond misattribution in the reported bug class, since the identification check is time-based rather than content/commitment-based.

### Likelihood Explanation
Exploitation requires only normal unprivileged timing behavior (no malicious node/peer/hardware access): an operator's QR-code validity window (`operator_qr_expiration_time`) is deliberately kept open across multiple user QR-code scan attempts and loop retries specifically to avoid rescanning, which is the same "don't wait for finality" pressure noted in the original report — the system optimizes for convenience over freshness, creating the same class of window.

### Recommendation
Bind the operator identification to the specific signup/enrollment action being finalized (e.g., include a fresh nonce or short-lived commitment computed at `do_signup` time, or require a fresh backend attestation call at enrollment finalization) rather than relying solely on `Instant::elapsed() < operator_qr_expiration_time` carried over from the initial `verify_operator_qr_code` call.

### Proof of Concept
1. Operator scans QR-code; `verify_operator_qr_code` succeeds, `OperatorData.timestamp` is set to `Instant::now()`.
2. Within `operator_qr_expiration_time`, the loop in `scan_remaining_qr_codes` reuses this same `operator_data` for a new signup attempt without re-verification, purely because `elapsed() < operator_qr_expiration_time` [7](#0-6) .
3. The `operator_qr_code.user_id` from that stale validation flows unchanged into `personal_custody_package::Plan::make_info_json`'s `operator_id` field, permanently attributing the resulting signup to a validation state that is no longer freshly confirmed at the moment of actual enrollment [8](#0-7) .

    /// Checks if `qr_code` is a valid operator QR-code through the backend.
    #[allow(clippy::cast_possible_truncation)]
    async fn verify_operator_qr_code(
        &self,
        orb: &mut Orb,
        qr_code: &qr_scan::user::Data,
        qr_capture_start: Instant,
    ) -> Result<Option<(u64, backend::operator_status::LocationData)>> {
        if qr_code.signup_extension() || self.operator_qr_code_override.is_some() {
            return Ok(Some((0, backend::operator_status::LocationData {
                team_operating_country: "DEV".to_string(),
                session_coordinates: Coordinates { latitude: 0.0f64, longitude: 0.0f64 },
                stationary_location_coordinates: None,
            })));
        }
        let http_start = Instant::now();
        match backend::operator_status::request(qr_code).await {
            Ok(backend::operator_status::Status { valid: true, location_data, reason: _ }) => {
                let location_data = location_data
                    .expect("to always have a result from the backend if valid == true");
                orb.ui.qr_scan_success(QrScanSchema::Operator);
                dd_incr!("main.count.global.distr_code_validated");
                tracing::info!("Operator QR-code validated: {qr_code:?}");
                dd_timing!("main.time.signup.distr_qr_code_capture", qr_capture_start);
                return Ok(Some((http_start.elapsed().as_millis() as u64, location_data)));
            }
            Ok(backend::operator_status::Status { valid: false, .. }) => {
                orb.ui.qr_scan_fail(QrScanSchema::Operator);
                dd_incr!("main.count.signup.result.failure.distr_qr_code", "type:invalid_qr");
            }
            Err(_) => {
                orb.ui.qr_scan_fail(QrScanSchema::Operator);
            }
        }
        Ok(None)
    }
