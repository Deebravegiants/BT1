Audit Report

## Title
NULL Pointer Dereference in `GatewayHandler.handlePublicKeyGet` via missing Params nil-check - (File: `core/capabilities/vault/gw_handler.go`)

## Summary
`HandleGatewayMessage` routes `vaulttypes.MethodPublicKeyGet` directly to `handlePublicKeyGet` without going through `GatewayVaultRequestProcessor.ProcessRequest`, and `handlePublicKeyGet` dereferences `*req.Params` without a nil check, unlike every other vault method path. [1](#0-0) [2](#0-1)  This can panic the goroutine handling the gateway message when `params` is omitted or explicitly `null` in the JSON-RPC request.

## Finding Description
In `HandleGatewayMessage`, `MethodSecretsCreate`/`MethodSecretsUpdate`/`MethodSecretsDelete`/`MethodSecretsList` are all routed through `h.requestProcessor.ProcessRequest`, which internally dispatches to `processCreateSecretsRequest`, `processUpdateSecretsRequest`, `processDeleteSecretsRequest`, and `processListSecretIdentifiersRequest` respectively — each of which explicitly checks `if req.Params == nil` before unmarshaling and returns an `InvalidVaultParamsError` if so. [3](#0-2) [4](#0-3)  Critically, these processing functions also call `marshalVaultParams(req, ...)`, which reassigns `req.Params` to a guaranteed non-nil `*json.RawMessage` before the subsequent `handleSecretsCreate`/`handleSecretsUpdate`/`handleSecretsDelete`/`handleSecretsList` functions dereference it — making those later dereferences safe by construction. [5](#0-4) 

`MethodPublicKeyGet`, however, bypasses this pipeline entirely and calls `h.handlePublicKeyGet` directly from the switch statement. [6](#0-5)  `handlePublicKeyGet` unconditionally executes `json.Unmarshal(*req.Params, r)` with no preceding nil check on `req.Params`. [2](#0-1)  If the incoming JSON-RPC request has `params` omitted or set to `null`, `req.Params` (a `*json.RawMessage`) will be `nil`, and `*req.Params` will panic with a nil pointer dereference.

This confirms the broken security assumption: every other vault method enforces a Params-presence invariant before dereferencing, but `MethodPublicKeyGet` does not, and it also skips the `Authorizer`/`authorizeAndStamp` pipeline used by the others, meaning no authentication gate exists before this code executes.

## Impact Explanation
This is a denial-of-service issue (crash/panic) reachable via the node's Vault gateway connector handler, not a data exfiltration, auth-bypass, or fund-movement issue. The severity depends entirely on whether the panic is recovered somewhere up the call stack (e.g., in the gateway connector's message-dispatch loop) — I was unable to confirm the presence or absence of a `recover()` wrapping the call site that invokes `HandleGatewayMessage` in `core/services/gateway/connector/connector.go` within the available tooling, so the ultimate blast radius (single goroutine crash and reconnect vs. full node crash) is unconfirmed. Regardless, an unhandled panic on an unauthenticated code path is a legitimate node-availability concern, though it maps most closely to a DoS class rather than the higher-severity impact classes explicitly listed in scope (auth bypass, key/secret exfiltration, unauthorized fund movement, gateway request impersonation, allowlist bypass, cross-user response corruption). This finding does not itself grant an attacker any of those higher-severity outcomes.

## Likelihood Explanation
High feasibility: `MethodPublicKeyGet` requires no authorization success and no `Params`-presence validation, so any caller able to reach the gateway (which forwards to the node) can trigger the panic with a single request where `params` is omitted or `null`.

## Recommendation
Add an explicit `if req.Params == nil` check in `handlePublicKeyGet` before dereferencing, returning an `api.UserMessageParseError`/`InvalidVaultParamsError`, consistent with `processCreateSecretsRequest`, `processUpdateSecretsRequest`, `processDeleteSecretsRequest`, and `processListSecretIdentifiersRequest`. Alternatively, route `MethodPublicKeyGet` through a shared pre-check in `HandleGatewayMessage` before any handler dereferences `req.Params`.

## Proof of Concept
1. As a gateway client (no authorization required), send a JSON-RPC 2.0 request to the Vault gateway with `"method": "<value of vaulttypes.MethodPublicKeyGet>"` and `"params": null` (or omit `params` entirely).
2. The gateway forwards the request to the node's `GatewayHandler.HandleGatewayMessage`.
3. Execution reaches the `MethodPublicKeyGet` case, calling `handlePublicKeyGet`, which executes `json.Unmarshal(*req.Params, r)` on a nil `*json.RawMessage`, causing a runtime panic. [1](#0-0) [2](#0-1) 
4. A minimal Go unit test constructing `req := &jsonrpc.Request[json.RawMessage]{Method: vaulttypes.MethodPublicKeyGet, Params: nil}` and calling `gatewayHandler.HandleGatewayMessage(ctx, gatewayID, req)` would reproduce the panic directly against `handlePublicKeyGet`.
