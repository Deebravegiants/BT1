### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signable string from the raw request body only, while the `shop` (and `topic`) fields consumed by the webhook dispatcher are read directly from unauthenticated HTTP headers. This breaks the identity binding `shop verified-by-HMAC == shop acted-upon-by-handler`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` (and `#topic`, `#webhook_id`, `#api_version`) are read straight from the (attacker-controllable, if the request reaches the app) HTTP headers with no cryptographic binding: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string`, i.e. only the body: [3](#0-2) 

`Registry.process` validates the HMAC and then dispatches the handler using `request.shop`, which was never part of the signed material: [4](#0-3) 

Because the signature only certifies "this body was produced with `api_secret_key`", but not "this body belongs to shop X", any two webhook deliveries that share an identical raw body and topic (e.g., an `orders/create` webhook whose JSON body happens to match, or any webhook whose body an attacker can reproduce/predict, or literally a webhook the attacker's own shop received) will validate under a different `shop-domain` header. An unprivileged user who has installed the app on their own shop can capture a legitimately-signed webhook payload (body + valid HMAC, both delivered to them by Shopify for their own tenant) and replay it to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain. `HmacValidator.validate` still returns true (the body and HMAC pair is valid), and `Registry.process` forwards `shop: <victim-domain>` to the handler as `WebhookMetadata`.

This is exactly the "field acted on but not covered by the HMAC" analog: the equality that should hold is `hmac_signed_shop == handler_processed_shop`, but the library never signs or verifies the shop field at all.

### Impact Explanation
If the host application's webhook handler uses `data.shop` (or `WebhookMetadata#shop`) to key persistence/session lookups (a documented, expected usage pattern per this gem's own `WebhookMetadata`), a replayed cross-tenant payload lets one merchant's webhook data be attributed to another merchant's shop record — i.e., cross-tenant data corruption/access, meeting the Critical "cross-tenant access" bar.

### Likelihood Explanation
Any developer who has installed the app on their own store legitimately receives correctly-HMAC'd webhook bodies from Shopify for topics whose payload content is attacker-influenced or predictable (e.g., `app/uninstalled`, `shop/update`, or any webhook where the body is small/fixed or can be engineered by manipulating the attacker's own shop data to match a desired body). They can then re-POST that exact body with a forged `shop-domain` header value to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required — only the attacker's own (unprivileged) app installation and the ability to send an arbitrary HTTP request to the public webhook endpoint.

### Recommendation
Include the shop domain (and ideally topic) in the HMAC-signed material, or otherwise cryptographically bind the shop identity to the signed payload before handing it to `Registry.process`. At minimum, `Utils::HmacValidator`/`Webhooks::Request#to_signable_string` should incorporate `shop` so that a valid signature for one shop cannot be replayed with a different `shop-domain` header.

### Proof of Concept
1. Install the app normally on `attacker-shop.myshopify.com`; Shopify delivers a legitimate webhook `POST` with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and body `B`.
2. Attacker resends the identical request to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body` [1](#0-0) .
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [5](#0-4) , causing the app to process attacker-supplied data under the victim's tenant identity.
