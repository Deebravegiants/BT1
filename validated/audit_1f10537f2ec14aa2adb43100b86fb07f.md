### Title
Webhook `shop`/`topic` identity fields are not covered by the HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable representation solely from the raw request body, while the `shop`, `topic`, and `webhook_id` values that `Registry.process` uses to route and attribute the webhook are taken from HTTP headers that are entirely outside the signed data. This breaks the intended binding `hmac == HMAC(secret, shop || topic || body)` down to `hmac == HMAC(secret, body)`, letting anyone who has captured one valid `(body, hmac)` pair for any shop reuse it under a different `shop-domain`/`topic` header and have it accepted as valid.

### Finding Description
`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it with the `hmac` field of the query object [4](#0-3) . For webhooks, `to_signable_string` is defined as just the raw JSON body:
```ruby
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

Meanwhile, `shop`, `topic`, and `webhook_id` — the identity fields that determine *which tenant* and *which handler* the webhook is attributed to — are pulled straight from request headers with no cryptographic binding to the HMAC:
```ruby
def topic
  T.cast(shopify_header("topic"), String)
end

def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [5](#0-4) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e. body integrity) before dispatching the handler using `request.topic` and constructing `WebhookMetadata` with `request.shop`:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
end
``` [6](#0-5) 

The binding that should hold is: `authenticated(shop, topic, body) == used(shop, topic, body)`. Because only `body` is authenticated, an unprivileged attacker (e.g., someone who installs the app on their own store, an interaction that requires no privileges against the victim) can capture a legitimately-signed `(body, hmac)` pair from a webhook Shopify sent them, then replay that exact body+HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` and/or `X-Shopify-Topic` headers to arbitrary values. The HMAC check still passes because it only re-derives the signature from the untouched body, so the forged request is accepted and dispatched as if it genuinely originated from a different topic/shop.

### Impact Explanation
This is a cross-tenant confusion vector: the app's webhook handler receives `WebhookMetadata` whose `shop` and `topic` are attacker-controlled despite a "valid" HMAC. Any host application that trusts `data.shop` to scope side effects (e.g., updating per-shop records, revoking access, processing "app/uninstalled" or "shop/redact" events, writing order/product data) can be made to apply attacker-supplied body content to a victim shop's tenant context, since the gem gives the caller no signal that the shop/topic were unauthenticated. This matches the Critical "cross-tenant access" category, since the tenant boundary (`shop`) is not actually verified by the primitive the gem exposes as the trust anchor (`HmacValidator.validate`).

### Likelihood Explanation
Obtaining one valid `(body, hmac)` pair requires only installing the target app on any store the attacker controls (a normal, unprivileged app install) and receiving any webhook — something Shopify sends automatically for many topics, including mandatory compliance topics (`shop/redact`, `customers/redact`, `customers/data_request`) that fire without user action. From there, forging the header values and replaying the POST to the app's public webhook endpoint requires no secret material at all.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the value that is HMAC-verified, or otherwise cryptographically authenticate them (e.g., include them in `to_signable_string`, or require the host app to independently confirm the `shop` header corresponds to a store with a known, previously-registered webhook subscription/session before trusting `WebhookMetadata#shop`). At minimum, document prominently that `Request#shop`/`#topic` are not covered by `HmacValidator.validate` so implementers do not treat a passing HMAC check as proof of the header values.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Shopify sends a legitimately signed webhook, e.g. `customers/redact`, to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: customers/redact`, `X-Shopify-Hmac-Sha256: <valid_hmac_for_body>` and some JSON body `B`.
3. Attacker captures `B` and the valid `hmac`.
4. Attacker crafts a new POST to the same public webhook endpoint, keeping body `B` and the `X-Shopify-Hmac-Sha256` header byte-for-byte identical, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` and (optionally) `X-Shopify-Topic` to any topic registered by the app.
5. `Utils::HmacValidator.validate(request)` recomputes the HMAC over `@raw_body` only, which is unchanged, so validation succeeds [7](#0-6) .
6. `Registry.process` dispatches the registered handler with `WebhookMetadata.new(topic: "victim's topic", shop: "victim.myshopify.com", body: B, ...)`, causing the app to act on attacker-supplied body data attributed to `victim.myshopify.com` [8](#0-7) .
