Confirmed: there is no dedup check on `circomData.erc20TokenAddresses` in `dimensionsCheck` or `performHinkalChecks` [1](#0-0) [2](#0-1) , and `runAction` computes per-index balance deltas from the same underlying `balanceOf` without deduplication.

### Title
Duplicate `erc20TokenAddresses` entries let a caller double-claim the same balance increase in `EmporiumUpgradeable.runAction` - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
This is the closest analog to the H-02 pattern reachable in scope: an accumulator (here, a token-balance snapshot) is read/updated per index without accounting for a state that is *shared* across two indices, letting a single caller "claim" the same underlying balance increase twice — analogous to the original bug where an unaccounted-for shared state (total supply/period) let one actor capture value that should have been split or not paid at all.

### Finding Description
`runAction` snapshots `balancesBefore` and `balancesAfter` per element of `circomData.erc20TokenAddresses` using `getBalancesForArray`, which just calls `balanceOf(address(this))` (or ETH balance) for each address in the array [3](#0-2) . Neither `dimensionsCheck` nor any other check in `HinkalHelper.performHinkalChecks` rejects duplicate addresses in `erc20TokenAddresses` [1](#0-0) .

If the same ERC20 address is supplied at two indices `i` and `j` in `circomData.erc20TokenAddresses`, both `balancesBefore[i] == balancesBefore[j]` and `balancesAfter[i] == balancesAfter[j]` (same token, same contract balance), so `balanceChange[i]` and `balanceChange[j]` are computed as the *same* total increase for that token [4](#0-3) . `handleOut` is then called independently for each index and unconditionally transfers `uint256(balanceChange)` of that token to `msg.sender` whenever `balanceChange > 0` [5](#0-4) . This means the same swap/operation output for one token gets paid out to the caller twice (once per duplicated index), draining `2x` the actual increase from the Emporium contract's balance — value that was never actually produced by the operation and is not reflected in the `deltaAmountChanges` / balance equation the circuit is meant to enforce.

### Impact Explanation
This breaks the balance equation the protocol relies on to back UTXOs: the caller receives (and can shield as) more real tokens than the operation actually produced, funded out of the shared Emporium contract's token balance — i.e., theft of protocol/other users' funds sitting in the Emporium contract, or unbacked value extraction. This qualifies as Critical/High under the rubric ("value moved by Hinkal or an external action but not counted in the balance equation").

### Likelihood Explanation
Requires only an unprivileged EOA/relayer submitting a proof/tx where `circomData.erc20TokenAddresses` has a duplicate token entry with a matching `Dimensions.tokenNumber`; no admin/owner/relay privilege is required to trigger the transfer path once such a proof is accepted by the verifier (assuming the circuit does not itself forbid duplicate token addresses in the public input array — this could not be fully confirmed from the in-scope Solidity alone since the circuit constraints for `MainEVMCircuit.circom`'s token-array uniqueness were not located in this pass).

### Recommendation
Add an explicit check (in `dimensionsCheck` or `performHinkalChecks`) that all addresses in `circomData.erc20TokenAddresses` are unique, or make `EmporiumUpgradeable.runAction`'s balance accounting dedupe tokens (aggregate deltas per unique token) before calling `handleOut`.

### Proof of Concept
1. Attacker crafts `circomData` for an Emporium external action with `erc20TokenAddresses = [TOKEN, TOKEN]` (same address twice), with matching `dimensions.tokenNumber = 2` and consistent `deltaAmountChanges`.
2. `verifyWallet`/signature checks pass as normal (stateless path, `signerAddress == address(0)`), and the op list performs one real swap that increases the Emporium contract's `TOKEN` balance by `X`.
3. In `runAction`, `balancesBefore[0] == balancesBefore[1]` and `balancesAfter[0] == balancesAfter[1]`, so `balanceChange[0] == balanceChange[1] == X` (assuming `deltaAmountChanges` for both indices are `>= 0`/deposit-side, or symmetric handling for withdraw-side per lines 136-139).
4. `handleOut` is invoked for both indices, each unconditionally calling `transferERC20TokenOrETH(TOKEN, msg.sender, X)`, sending `2X` to the caller though only `X` was actually generated.
5. Verification of the exact circuit-side constraint that could block duplicate token addresses was not completed due to iteration limits; this should be checked in `circuits/MainEVMCircuit.circom` before treating this as fully confirmed.

    function handleOut(
        int256 balanceChange,
        CircomData calldata circomData,
        uint256 i
    ) internal returns (UTXO memory outUtxo) {
        // total change can be less than zero if there was some balance before the call -> that's why we have <=
        if (balanceChange <= 0) {
            return outUtxo;
        }

        transferERC20TokenOrETH(
            circomData.erc20TokenAddresses[i],
            msg.sender,
            uint256(balanceChange)
        );

        outUtxo = UTXO(
            uint256(balanceChange),
            circomData.erc20TokenAddresses[i],
            circomData.stealthAddressStructure,
            circomData.timeStamp
        );
    }
