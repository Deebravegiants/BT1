### Title
Webhook shop/topic identity not covered by HMAC verification allows cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authorizes and routes an incoming webhook purely on `Utils::HmacValidator.validate(request)`, which verifies the request's HMAC against `request.to_signable_string`. `Request#to_signable_string` returns only the raw body [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values that the gem then hands to the application's handler are taken straight from unauthenticated HTTP headers [2](#0-1) , and `Registry.process` passes `request.shop` (header-derived) into `WebhookMetadata` without ever re-deriving or cross-checking it against anything covered by the HMAC [3](#0-2) .

### Finding Description
The equality that must hold for tenant isolation is:
`shop value the app attributes the event to (WebhookMetadata#shop)` == `shop value that is cryptographically bound to the verified payload`.

Because the HMAC only covers `@raw_body` [4](#0-3) [1](#0-0) , and `shop`/`topic`/`webhook_id` are read from `shopify_header(...)` [5](#0-4) , the "before" state (a genuine webhook: header `shop-domain=A`, body signed for A) and "after" state (attacker resends the same valid `raw_body`/`hmac-sha256` pair but with `shop-domain=B`) are indistinguishable to `HmacValidator.validate`, since it only recomputes/compares the digest of `raw_body` [6](#0-5) . `Registry.process` still succeeds and dispatches `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` to the handler as if `shop` were verified [3](#0-2) .

An unprivileged internet user who can obtain any one genuine `(raw_body, hmac-sha256)` pair — trivially available by installing the app on their own development/trial store and receiving a legitimate webhook — can replay that exact body/HMAC to the app's public webhook endpoint while substituting an arbitrary `shop-domain` (and `topic`/`webhook-id`) header. The signature check still passes because the header fields play no role in the signable string.

### Impact Explanation
This breaks the shop-to-payload identity binding that host applications rely on to scope data per tenant (e.g., looking up a shop's session/store record by `WebhookMetadata#shop` before acting on `body`). An attacker can make the app believe events/data belong to a victim shop they do not control, enabling cross-tenant data injection/confusion — a Critical-tier impact per the defined scope (cross-tenant access).

### Likelihood Explanation
Likelihood is significant: no access token, `client_secret`, or privileged account is required. Obtaining one genuine `(body, hmac)` sample is possible by installing the app on any store the attacker controls (including free/dev stores) and capturing an inbound webhook, then replaying it against the same public endpoint with a spoofed `shop-domain` header. The gem performs no additional check binding the header-derived `shop` to the HMAC-covered content.

### Recommendation
Do not trust header-derived `shop`, `topic`, or `webhook_id` as authenticated identity. Either:
- Include the relevant identity fields (shop domain, topic, webhook id) in the signable string used for HMAC verification, or
- Require the application layer to independently confirm that the `shop-domain` header corresponds to a shop for which this exact webhook subscription/topic was registered (e.g., cross-check against the parsed body's own shop-identifying fields where present), rejecting mismatches before invoking the handler.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body and its `X-Shopify-Hmac-Sha256` header — both valid and Shopify-signed.
2. Attacker sends a new POST to the app's webhook endpoint with the identical `raw_body` and `hmac-sha256` value, but sets `shop-domain: victim.myshopify.com` and any desired `topic`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body successfully [7](#0-6) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and matches, so validation passes [8](#0-7) .
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though the payload was never associated with that shop by Shopify, allowing the app to act on/attribute data to the wrong tenant.

        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
