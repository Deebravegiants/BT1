The documentation explicitly states that the process step "will verify the request did indeed come from Shopify" and presents `data.shop` as a normal, apparently-trusted field of the verified webhook — but that value is never covered by the HMAC that is being validated.

### Title
Webhook `shop` (and `topic`/`api_version`) identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated HTTP headers. `Webhooks::Registry.process` validates the HMAC (which only proves body integrity/authenticity for *some* valid `(body, hmac)` pair produced with the app's secret) and then hands the handler a `WebhookMetadata` whose `shop` attribute is taken straight from the unverified `X-Shopify-Shop-Domain` header.

### Finding Description
The identity binding that should hold is:
`hmac == HMAC(secret, body || shop || topic)`, i.e., the authenticated shop/topic should be cryptographically bound to the same signature that authenticates the payload.

In this gem, the binding is actually:
`hmac == HMAC(secret, body)` only [1](#0-0) 

`shop`, `topic`, `webhook_id`, `api_version` are pulled from headers with zero cryptographic linkage to the HMAC [2](#0-1) .

`Registry.process` validates only the body's HMAC, then dispatches to the handler using the untrusted header-derived `shop`: [3](#0-2) 

Because any body that was ever legitimately signed by Shopify for the attacker's own shop (i.e., any real webhook the attacker received for their own store, which they fully control and can trigger repeatedly, e.g. `orders/create` with attacker-chosen order data) carries a valid HMAC that is *independent of the shop header*, the attacker can replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` with a victim's shop domain. `Utils::HmacValidator.validate` will still succeed because it only recomputes `HMAC(secret, raw_body)` [4](#0-3) , and `Registry.process` will invoke the handler with `shop: request.shop` set to the attacker-chosen victim domain [5](#0-4) .

This mirrors the report's root cause pattern (an identity/entitlement value not properly bound to the operation being authorized) — here, the tenant (`shop`) attribute is not bound to the cryptographic proof that supposedly authenticates the whole webhook.

### Impact Explanation
This crosses a tenant boundary: an attacker who legitimately operates any shop that has installed the app can capture their own genuine webhook deliveries (valid body+HMAC), then send that exact payload to the app's public webhook endpoint claiming it belongs to a different, victim shop. Any app that uses `data.shop` from `WebhookMetadata` to select which merchant's records to create/update/delete (the intended and documented use per `docs/usage/webhooks.md`, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) will process attacker-controlled data under the victim's tenant identity — a cross-tenant data injection/corruption primitive using only the gem's own verification logic, no leaked credentials required. This satisfies the "Critical - cross-tenant access" bar.

### Likelihood Explanation
Moderate-to-high: exploitation requires only that the attacker operate/install the app on any shop they control (a normal unprivileged action for any Shopify merchant/developer), trigger a webhook event, capture the raw body and `X-Shopify-Hmac-Sha256` header, and POST it to the app's public webhook callback URL with a forged `X-Shopify-Shop-Domain` header. No access token, `client_secret`, or other secret is needed — the attacker's own legitimately-issued HMAC for their own shop is sufficient because the HMAC never binds to the shop.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the value that is HMAC-verified, or otherwise cross-check the header-derived `shop` against an independently trusted source (e.g., require the app to verify that the reported `shop` corresponds to a shop for which a webhook was actually registered/has an active session) before trusting it in `WebhookMetadata`. At minimum, update `to_signable_string` to include the shop/topic headers so `HmacValidator.validate` cryptographically ties them to the signature, or add an explicit check in `Registry.process` that only handlers for known-installed shops receive the metadata.

### Proof of Concept
```ruby
# Attacker owns a real installed shop "attacker.myshopify.com"
# and captures a genuine webhook delivery Shopify sent them:
raw_body = '{"id": 1, "note": "hi"}'
real_hmac = "<value from X-Shopify-Hmac-Sha256 header of that genuine delivery>"

# Attacker now replays the exact same body+hmac to the app's public
# webhook endpoint, but swaps the shop-domain header to the victim's shop:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => real_hmac,       # still valid, HMAC only covers raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # forged, not covered by HMAC
  "x-shopify-webhook-id" => "any-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) passes because it only checks HMAC(secret, raw_body).
# handler.handle receives WebhookMetadata with shop: "victim-shop.myshopify.com",
# even though Shopify never sent this webhook for that shop.
```
