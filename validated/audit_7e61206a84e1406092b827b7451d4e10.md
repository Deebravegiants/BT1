### Title
`CallDispatcher.dispatch()` has no caller authorization — any unprivileged address can drive arbitrary calls with the dispatcher's value/token balance - (File: evm/src/utils/CallDispatcher.sol)

### Summary
Flowise's Custom-MCP RCE stems from an execution primitive (`command`/`args` reaching `child_process`) that any unauthenticated caller could invoke with no RBAC gate. The Hyperbridge analog is `CallDispatcher.dispatch()`, a standalone deployed contract used by the IntentGatewayV2 fill flow to make composable calls to DEXes/lending protocols on behalf of a solver. The function is `external` with **no access-control modifier at all** — it does not check `msg.sender` against the gateway, the intents contract, or any allow-list — so any address can call it directly and force it to make arbitrary `to.call{value: call.value}(call.data)` invocations using whatever ETH/token balance happens to sit in the `CallDispatcher` contract at that moment.

### Finding Description
`CallDispatcher` is a shared utility contract referenced from `IntentsBase._execute` via `_params.dispatcher` [1](#0-0) . During a normal fill, the gateway sends the order's output calldata to `dispatcher.dispatch(order.output.call)`, then sweeps back any leftover native/token balance from the dispatcher into itself as "protocol dust" [2](#0-1) .

The problem is that `dispatch()` itself is completely unguarded: [3](#0-2) 

There is no `onlyHost`, `onlyGateway`, or any `msg.sender` check — unlike the rest of the intents/gateway code, which consistently gates privileged paths (e.g. `onlyHost` in `ExtrinsicIntents.setRelayer` [4](#0-3) , or the relayer check in `_checkRelayer` [5](#0-4) ). `CallDispatcher` also has an unconditional `receive() external payable {}` that accepts ETH from anyone [6](#0-5) , and it can also accumulate ERC-20 balances during a fill (before the sweep step reclaims them). Because the contract holds a real balance in between the `dispatch()` call and the sweep, and `dispatch()` accepts an arbitrary, caller-supplied `Call[]` with the `to`/`value`/`data` fields fully attacker-controlled, any unprivileged party — a solver, a filler, or an unrelated third party who is neither the gateway nor the order's beneficiary — can call `CallDispatcher.dispatch()` directly to move whatever native ETH or ERC-20 tokens are currently on the contract to an address of their choosing, i.e. an unauthorized/unsandboxed execution primitive exactly analogous to Flowise's `mcpServerConfig`-driven `child_process` execution reachable without RBAC.

### Impact Explanation
Because `dispatch()` performs unrestricted external calls with the dispatcher's own ETH/token balance and is missing any authorization check (CWE-862, matching the advisory's classification), any address able to observe or induce a nonzero balance on the `CallDispatcher` contract (residual ERC-20 dust from a partially-consumed swap inside `order.output.call`, stray ETH sent to `receive()`, or funds in flight between the `dispatch()` call and the subsequent sweep in `_execute`) can steal it by front-running or simply calling `dispatch()` themselves before the legitimate sweep executes. This is concrete theft of funds reachable from a single unprivileged transaction, matching the required impact bar (theft of funds via an unsandboxed/unauthorized execution path).

### Likelihood Explanation
`CallDispatcher` is meant to be invoked only from `IntentsBase._execute` as part of a fill [1](#0-0) , but nothing on-chain enforces that restriction — the contract is a plain, standalone deployment with a fully public `dispatch()` entry point and a payable fallback that any address can fund or drain. Any solver, filler, or opportunistic MEV searcher monitoring pending fill transactions can trivially construct a competing transaction that calls `dispatch()` on the same dispatcher address before the legitimate transaction's sweep step runs, or immediately after any transaction leaves a nonzero balance on the dispatcher.

### Recommendation
Add an authorization check to `CallDispatcher.dispatch()` restricting the caller to the specific `IntentsBase`/gateway instance(s) that are meant to use it (e.g., an `onlyGateway` modifier configured at deployment, or deploying a fresh, single-use dispatcher per fill instead of a long-lived shared singleton), and ensure the contract never holds residual balance outside of the atomic fill transaction.

### Proof of Concept
1. Any fill of an order whose `order.output.call` swaps through a DEX inside `CallDispatcher` leaves ERC-20 dust or ETH momentarily on the `CallDispatcher` contract before `IntentsBase._execute` sweeps it back [7](#0-6) .
2. An attacker (not the gateway, not a solver, not the beneficiary) calls `CallDispatcher.dispatch(encodedCalls)` directly, where `encodedCalls` decodes to a `Call[]` transferring the dispatcher's current token/ETH balance to the attacker's address: `dispatch(abi.encode([Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, dispatcher.balanceOf(token))})]))`.
3. Since `dispatch()` has no `msg.sender` restriction [3](#0-2) , the call succeeds and the attacker's transfer executes with the dispatcher as `msg.sender`, moving out any balance present — including funds sent directly to `receive()` [6](#0-5)  or dust left from a legitimate fill executed in the same or a prior block.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
