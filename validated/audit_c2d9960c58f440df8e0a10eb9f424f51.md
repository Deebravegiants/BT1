This confirms the finding: `CHANGELOG.md` explicitly documents (PR #1369) "Make `sub` and `sid` jwt claims optional (Checkout ui extension support)" [1](#0-0) , and the test fixtures explicitly distinguish an admin session token (`iss` ending `/admin`) from a checkout UI extension token (`iss` ending `/checkouts`) that is issued to storefront customers, not merchants [2](#0-1) . `JwtPayload` only checks `aud == Context.api_key` and otherwise treats both token types identically except for `shopify_user_id`, which is gated by `admin_session_token?` [3](#0-2) [4](#0-3) . `SessionUtils.session_id_from_shopify_id_token` uses `payload.shop` (the `dest` claim) to compute `offline_session_id(shop)` = `"offline_#{shop}"` without ever checking `admin_session_token?` / `iss` [5](#0-4) , and the docs instruct host apps to feed *any* `shopify_id_token` from the request directly into this method to compute the offline session id used to look up the merchant's persisted offline-access-token session [6](#0-5) .

### Title
Offline (merchant) session ID derived from any valid-`aud` JWT regardless of issuer/surface, letting a checkout/customer-facing session token collide with the shop's offline admin session ID - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
`SessionUtils.session_id_from_shopify_id_token` computes the session-storage key `"offline_#{shop}"` (and `"#{shop}_#{user_id}"` for online) purely from the `dest`/`sub` claims of a JWT that only needs to satisfy `aud == Context.api_key`. It never checks that the JWT is actually an *admin* session token (`iss` ending in `/admin`), even though the library and its own test suite acknowledge that Shopify issues session tokens with the same `aud` and `dest` shape from other surfaces (e.g. checkout UI extensions, `iss` ending in `/checkouts`) that are handed to storefront customers, not the merchant.

### Finding Description
The identity binding that should hold is: `session_id computed by SessionUtils` == `session_id derivable only from a token that Shopify issued specifically for the embedded admin surface of that shop`.

`JwtPayload#initialize` verifies the HS256 signature and `aud`, but it does not bind `iss` (issuer/surface) to any downstream use except the narrow `shopify_user_id` helper: [3](#0-2) 

`admin_session_token?` exists in the class but is only consulted for `shopify_user_id`, not for `shop`/`shopify_domain`: [4](#0-3) 

`SessionUtils.session_id_from_shopify_id_token` (and `current_session_id`, which calls it for embedded apps) derives the storage key exclusively from `payload.shop` and, for offline sessions, ignores the issuer entirely: [5](#0-4) 

Both `test/auth/jwt_payload_test.rb` and the changelog entry for PR #1369 confirm that Shopify-issued, correctly-`aud`-scoped, correctly-signed tokens exist for checkout UI extensions (surface intended for storefront customers, `sub` being a `gid://shopify/Customer/...`), and that this library explicitly supports decoding them the same way as admin tokens: [7](#0-6) [1](#0-0) 

Because `offline_session_id`/`jwt_session_id` are keyed only by `shop`/`shop_user_id` and never gated by `admin_session_token?`, any Shopify-signed JWT for that shop - regardless of which surface issued it - collapses to the exact same session-storage key that the app uses to look up the merchant's OAuth-derived session (which holds the real Admin API access token). The library's own documented usage pattern instructs host apps to feed the raw incoming `shopify_id_token` (from "an embedded Shopify app" request) straight into this method: [6](#0-5) 

Nothing in this call path distinguishes "this token proves I am the embedded admin app for shop X" from "this token proves I am a customer viewing shop X's checkout" - both produce identical session IDs, breaking the binding between the returned session ID and the actual authorization context that the token represents.

### Impact Explanation
An unprivileged actor (any storefront customer, who legitimately receives checkout/customer-account UI extension session tokens for shop X from Shopify) can present that token to a host application built on this gem's documented `current_session_id`/`session_id_from_shopify_id_token` API. If the host app uses the returned `"offline_#{shop}"` id to fetch its persisted session record for shop X (as the docs instruct: "for offline (store) sessions"), the customer ends up resolving to the same session-storage key that holds the merchant's real offline Admin API access token, without ever having gone through OAuth or admin embedding. This maps to cross-tenant/privilege-boundary crossing: a customer-scoped credential is treated as equivalent to a merchant-scoped credential purely because the gem does not bind the issuer/surface into the session id computation.

### Likelihood Explanation
Any app that supports checkout UI extensions or customer-account UI extensions alongside an embedded admin app will receive both types of session tokens from Shopify against the same `api_key`. The gem's documentation directs consumers to funnel "an `HTTP_AUTHORIZATION` header or `id_token` from the request URL params" for embedded requests into this exact function without mentioning any need to check `iss`, making the unsafe usage the *documented default* rather than a corner case.

### Recommendation
In `lib/shopify_api/auth/jwt_payload.rb`, bind the surface into the JWT identity: require and expose an explicit "is this an admin session token" boolean (already computed as `admin_session_token?`) and have `lib/shopify_api/utils/session_utils.rb`'s `session_id_from_shopify_id_token` raise (or take an explicit parameter to opt into non-admin surfaces) when `admin_session_token?` is false, so a checkout/customer-account token can never resolve to the same `offline_#{shop}` / `#{shop}_#{user_id}` key used for the merchant's Admin API session.

### Proof of Concept
1. App X is embedded and also uses checkout UI extensions; both surfaces share `Context.api_key`/`Context.api_secret_key`.
2. A customer visits shop `test-shop.myshopify.io`'s checkout and receives a legitimately Shopify-signed session token with payload `{iss: "https://test-shop.myshopify.io/checkouts", dest: "https://test-shop.myshopify.io", aud: <api_key>, sub: "gid://shopify/Customer/123", ...}` (shape per `test/auth/jwt_payload_test.rb` lines 23-32).
3. The customer (or a script they control that captures this token from network traffic in their own browser) sends this token as `Authorization: Bearer <token>` to any endpoint of App X that calls `ShopifyAPI::Utils::SessionUtils.current_session_id(auth_header, nil, false)`.
4. `session_id_from_shopify_id_token` decodes the token (`aud` matches, signature valid), takes `payload.shop == "test-shop.myshopify.io"`, and returns `"offline_test-shop.myshopify.io"` — identical to the key produced when the real merchant completed OAuth via `lib/shopify_api/auth/oauth.rb`'s `validate_auth_callback`.
5. If App X's session-lookup code uses this id to fetch the stored offline session (as the gem's own docs instruct for "offline (store) sessions"), it retrieves the merchant's real Admin API access token and proceeds to serve the customer's request with merchant-level Admin API privileges.

        def session_id_from_shopify_id_token(id_token:, online:)
          raise Errors::MissingJwtTokenError, "Missing Shopify ID Token" if id_token.nil? || id_token.empty?

          payload = Auth::JwtPayload.new(id_token)
          shop = payload.shop

          if online
            jwt_session_id(shop, T.must(payload.sub))
          else
            offline_session_id(shop)
          end

        end

        end

#### Getting Session ID From Embedded Requests

If your app uses client side rendering instead of server side rendering, you will need to use App Bridge's [authenticatedFetch](https://shopify.dev/docs/apps/auth/oauth/session-tokens/getting-started) to make authenticated API requests from the client.

For *embedded* apps:

If you have an `HTTP_AUTHORIZATION` header or `id_token` from the request URL params , you can pass that as `shopify_id_token` into:
- `ShopifyAPI::Utils::SessionUtils.current_session_id(shopify_id_token, nil, true)` for online (user) sessions or
- `ShopifyAPI::Utils::SessionUtils.current_session_id(shopify_id_token, nil, false)` for offline (store) sessions.

`current_session_id` accepts shopify_id_token in the format of `Bearer this_token` or just `this_token`.

You can also use this method to get session ID:
- `ShopifyAPI::Utils::SessionUtils::session_id_from_shopify_id_token(id_token: id_token, online: true)` for online (user) sessions or
- `ShopifyAPI::Utils::SessionUtils::session_id_from_shopify_id_token(id_token: id_token, online: false)` for offline (store) sessions.

`session_id_from_shopify_id_token` does **NOT** accept shopify_id_token in the format of `Bearer this_token`, you must pass in `this_token`.
