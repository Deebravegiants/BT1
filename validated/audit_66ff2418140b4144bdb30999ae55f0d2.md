### Title
Hostile HyperSwap V2 pre-seed can exceed the fixed graduation rebalance budget, forcing the locked LP to open at an attacker-dictated price instead of the curve-close price - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`finalizeGraduation` seeds the post-graduation HyperSwap V2 pool via `_seedUniswapV2Direct` → `_seedRebalancing` → `_pairRebalance`, which is explicitly designed to "arb away" a hostile pre-seed of the `TOKEN`/`LT` pair before depositing the curve's raised inventory. [1](#0-0)  The corrective swap, however, is capped at 99% of Bonding's own graduation-bound inventory (`ltFromPair` or `tokensForLP`), which is itself a small, fixed amount set at curve close. [2](#0-1)  Any unprivileged address can pre-create the HyperSwap V2 pair and mint an arbitrarily large, arbitrarily skewed `TOKEN`/`LT` ratio into it before `finalizeGraduation` runs, since pair creation and `mint` are fully permissionless on HyperSwap V2 and `_ensureUniswapV2Pair` only creates the pair if it does not already exist. [3](#0-2)  When the skew is large enough that the capped rebalance swap cannot reach the curve-close ratio, `_routerDepositAndDispose` deposits Bonding's remaining inventory at the router's `quote()`-derived split against the still-skewed live reserves rather than the intended curve-close ratio, and the un-matched remainder is burned (TOKEN) or swept to the owner (LT) instead of entering the locked LP. [4](#0-3) 

### Finding Description
`_prepareGraduationLiquidity` pins `tokensForLP` (≤ `LP_RESERVE` = 250M tokens) and `ltFromPair` (bounded by the curve's real raised LT, itself gated near the fixed `graduationThresholdUsd`, e.g. ~$9K worth of LT) at the moment the curve closes. [5](#0-4)  This is the entire USD-denominated "defense budget" available to correct a hostile pre-seed during phase 2.

`_seedRebalancing` computes the no-fee swap size needed to move the live pool ratio to `(tokensForLP, ltFromPair)`, but clamps it with `_swapBudget`, which is hard-capped at 99% of whichever side of Bonding's own graduation inventory is being swapped in (real LT held via `Router.graduate`, or the curve-bound `tokensForLP`). [6](#0-5) [7](#0-6) 

Because pair creation and `mint` on HyperSwap V2 are unrestricted, and both the `TOKEN` (freely tradable on the curve before graduation) and the `LT` (an external, freely transferable asset) are obtainable by any unprivileged actor, an attacker can pre-seed the pair with reserves whose imbalance dwarfs Bonding's fixed, small correction budget. When `_pairRebalance`'s capped swap cannot bring the ratio back to `tokensForLP/ltFromPair`, `_routerDepositAndDispose` deposits at the still-skewed live ratio via `router.addLiquidity(..., 1, 1, lpLock_, ...)`, so the LP that is ultimately minted to `LPLock` — the one-shot, unbypassable `LPLock.recordLock` call in `finalizeGraduation` — opens at a price set by the attacker's pre-seed rather than the curve's actual closing price. [8](#0-7) [9](#0-8)  The unmatched remainder of the honest curve-raised inventory (tokens meant for LP, or real raised LT) is simply burned or swept away instead of reaching the lock. [10](#0-9) 

This mirrors the external report's bug class: a component with a fixed, self-contained budget of "corrective" authority (there: `virt-handler`'s ability to patch node labels; here: Bonding's capped rebalance swap) is abused by an attacker who forces an outcome — a migration/placement decision — onto attacker-controlled territory (there: an attacker node; here: an attacker-dictated LP price) because the correction mechanism's assumed bound on adversarial input turns out to be smaller than what an unprivileged actor can actually inject.

### Impact Explanation
The finalized, locked liquidity pool for the token opens at a price divorced from the curve's actual closing price, and part of the honest curve-raised token/LT inventory that should have backed the LP is instead burned or diverted to the owner rather than entering the lock. This satisfies the "LP seeded away from the curve close price" criterion directly: post-graduation traders transact against a mispriced pool, and the attacker's pre-existing pre-seed captures a share of the deposit/price disproportionate to their contribution, at the expense of the token's creator and every curve buyer whose raised value was supposed to seed the locked LP.

### Likelihood Explanation
The path requires only unprivileged actions reachable by any address: buying tokens on the bonding curve (`Zap.buy`), acquiring LT on the open market, calling the public HyperSwap V2 factory `createPair` + `mint`, and letting/forcing `finalizeGraduation` run afterward (itself permissionless). No admin, upgrade, or off-chain compromise is needed — the attack surface is exactly the "pre-creating or pre-seeding the HyperSwap V2 TOKEN/LT pair before graduation" primitive explicitly reachable in this protocol's design. The natspec on `_swapBudget` and `_seedRebalancing` shows the team reasoned carefully about smaller pre-seeds but bounded the defense budget to Bonding's own small, fixed graduation inventory, leaving large/extreme pre-seeds under-defended.

### Recommendation
Do not bound the correction budget solely to a fraction of the graduation's own bound inventory. Either (a) detect when the pre-seed ratio cannot be corrected within budget and revert/park the graduation instead of depositing at a still-skewed ratio, or (b) size the rebalance swap relative to the pre-seed's own reserves (not just Bonding's fixed inventory) so the post-swap ratio is guaranteed close to `tokensForLP/ltFromPair` regardless of pre-seed magnitude, falling back to a permissionless "reject and retry" path rather than silently depositing off-ratio and burning/sweeping the shortfall.

### Proof of Concept
1. Attacker buys `TOKEN` on the curve (or otherwise acquires a large amount) and separately acquires a small amount of `LT`.
2. Before (or racing) `finalizeGraduation`, attacker calls `IUniswapV2Factory.createPair(token, lt)` directly, then `pair.mint()` after transferring a highly skewed ratio, e.g. a very large `TOKEN` amount against a token-vs-LT ratio wildly divergent from the curve's closing ratio (`tokensForLP/ltFromPair`).
3. `finalizeGraduation(tokenAddress)` is called (by anyone, e.g. the keeper). `_ensureUniswapV2Pair` finds the attacker's pair already exists and reuses it. [3](#0-2) 
4. `_seedUniswapV2Direct` detects `totalSupply() != 0` and enters `_seedRebalancing`, computing the required no-fee swap to correct the ratio, but `_swapBudget` caps it at 99% of Bonding's small fixed inventory (`ltFromPair` or `tokensForLP`). [6](#0-5) 
5. Because the attacker's pre-seed skew exceeds what that capped swap can correct, `_pairRebalance` leaves the pool materially off the curve-close ratio, and `_routerDepositAndDispose` deposits the remaining balances at that skewed live ratio, burning/sweeping the unmatched remainder. [4](#0-3) 
6. `LPLock.recordLock` then permanently locks the resulting under-sized, mispriced LP position, and the token now trades post-graduation at a price the attacker chose rather than the curve's closing price. [9](#0-8)

    function _prepareGraduationLiquidity(
        address tokenAddress
    ) internal returns (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) {
        address pairAddr = _s().tokenInfo[tokenAddress].pair;
        (uint256 tokenReserve, uint256 assetReserve) = IPair(pairAddr).getReserves();

        unsoldBurned = IPair(pairAddr).tokenBalance();
        if (unsoldBurned > 0) {
            Token(tokenAddress).burn(pairAddr, unsoldBurned);
        }

        ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
        if (ltFromPair > 0) {
            _s().router.graduate(tokenAddress, ltFromPair);
        }

        tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
        if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;

        lpBurned = LP_RESERVE - tokensForLP;
        if (lpBurned > 0) {
            Token(tokenAddress).burn(address(this), lpBurned);
        }
    }

    ///           permanently stuck.

    function _seedRebalancing(
        address tokenAddress,
        address lt,
        address pair,
        uint256 tokensForLP,
        uint256 ltFromPair,
        uint256 protectedLT
    ) internal returns (uint256 liquidity) {
        (uint112 r0, uint112 r1,) = IUniswapV2Pair(pair).getReserves();
        bool tokenIs0 = IUniswapV2Pair(pair).token0() == tokenAddress;
        (uint256 reserveToken, uint256 reserveLT) = tokenIs0 ? (uint256(r0), uint256(r1)) : (uint256(r1), uint256(r0));

        // Below the band on BOTH sides, overpower the pre-seed with a direct
        // mint at the cached ratio: the rebalance swap is too coarse to reach
        // the ratio against such small reserves, and the pre-existing LP's
        // claim on the deposit stays bounded by `DIRECT_MINT_PRESEED_BPS`. A
        // side that is large relative to its LP target still takes the
        // rebalance path so it isn't donated under the empty-mint `min()`.
        if (
            reserveToken * BPS_DENOM <= tokensForLP * DIRECT_MINT_PRESEED_BPS
                && reserveLT * BPS_DENOM <= ltFromPair * DIRECT_MINT_PRESEED_BPS
        ) {
            return _seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair);
        }

        // Budget reads `balanceOf(this)` rather than `tokensForLP` /
        // `ltFromPair` so any skim donation contributes to the rebalance
        // and not only to `_routerDepositAndDispose`'s deposit.
        // Direction: pool TOKEN-rich vs target ⇒ swap LT in (TOKEN out).
        // Pool LT-rich ⇒ swap TOKEN in (LT out). Bounded by uint112 reserves
        // and curve-close-shape targets, both products fit in uint256.
        // When `_pairRebalance` returns false the seed is too small for any
        // swap to move the ratio (its fee-charging quote rounds to zero), so
        // the reserves are negligible against this graduation's inventory:
        // overpower them with a direct mint at the cached ratio rather than
        // letting the router deposit at the attacker's ratio. A swap that
        // does fire leaves the pool ≈ at target for the router deposit.
        if (reserveToken * ltFromPair > reserveLT * tokensForLP) {
            // Pool TOKEN-rich. tokenIn = lt, tokenOut = tokenAddress.
            // tokenInIs0 = (lt is token0) = !tokenIs0.
            if (!_pairRebalance(
                    RebalanceParams({
                        pair: pair,
                        tokenIn: lt,
                        tokenInIs0: !tokenIs0,
                        reserveIn: reserveLT,
                        reserveOut: reserveToken,
                        targetN: ltFromPair,
                        targetD: tokensForLP,
                        maxSwap: _swapBudget(_ltSwapInventory(lt, protectedLT))
                    })
                )) {
                return _seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair);
            }
        } else if (reserveToken * ltFromPair < reserveLT * tokensForLP) {
            // Pool LT-rich. tokenIn = tokenAddress, tokenInIs0 = tokenIs0.
            if (!_pairRebalance(
                    RebalanceParams({
                        pair: pair,
                        tokenIn: tokenAddress,
                        tokenInIs0: tokenIs0,
                        reserveIn: reserveToken,
                        reserveOut: reserveLT,
                        targetN: tokensForLP,
                        targetD: ltFromPair,
                        maxSwap: _swapBudget(IERC20(tokenAddress).balanceOf(address(this)))
                    })
                )) {
                return _seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair);
            }
        }

    /// @dev Cap the rebalance swap at 99% of the available side's budget,
    ///      so the subsequent `addLiquidity` always has a non-zero amount
    ///      of BOTH sides to deposit. Without this, an extreme hostile
    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,
    ///      `_pairRebalance` clamps to the full budget, and the swap
    ///      consumes 100% of one side. `_routerDepositAndDispose` then
    ///      skips `addLiquidity` (`remToken == 0` or `remLT == 0`),
    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero
    ///      LP at the post-swap ratio. The 1% comes off the swap, not the
    ///      deposit — for any realistic pre-seed `s_unconstrained` is
    ///      orders of magnitude below `maxSwap`, so the cap doesn't bind
    ///      and behaviour is unchanged. It only kicks in for catastrophic
    ///      pre-seeds beyond our budget capacity, where the alternative
    ///      is bricking.
    function _swapBudget(
        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;
    }

    function _routerDepositAndDispose(
        address tokenAddress,
        address lt,
        uint256 protectedLT
    ) internal returns (uint256 liquidity) {
        BondingStorage storage $ = _s();
        address routerAddr = $.uniswapV2Router;
        address lpLock_ = $.lpLock;
        uint256 remToken = IERC20(tokenAddress).balanceOf(address(this));
        // Subtract `protectedLT` (LT that doesn't belong to this graduation
        // — concurrent escrows or stray dust, snapshotted at the top of
        // `finalizeGraduation`) so the deposit allowance can never pull
        // another graduation's earmark or accidentally absorb dust into a
        // locked LP.
        uint256 ltBal = IERC20(lt).balanceOf(address(this));
        uint256 remLT = ltBal > protectedLT ? ltBal - protectedLT : 0;

        if (remToken > 0 && remLT > 0) {
            IERC20(tokenAddress).forceApprove(routerAddr, remToken);
            IERC20(lt).forceApprove(routerAddr, remLT);
            (,, liquidity) = IUniswapV2Router02(routerAddr)
                .addLiquidity(tokenAddress, lt, remToken, remLT, 1, 1, lpLock_, block.timestamp);
            IERC20(tokenAddress).forceApprove(routerAddr, 0);
            IERC20(lt).forceApprove(routerAddr, 0);
        }

        // Burn off-ratio TOKEN remainder (`Bonding` is the Token owner).
        // Hostile pre-seeds reduce circulating supply by the attacker's
        // wasted-side share, net positive for honest holders.
        uint256 leftoverToken = IERC20(tokenAddress).balanceOf(address(this));
        if (leftoverToken > 0) {
            Token(tokenAddress).burn(address(this), leftoverToken);
        }
        // LT remainder is third-party — we cannot burn it. It stays in
        // this contract until `finalizeGraduation`'s post-bookend sweeps
        // it to the owner. Honest graduations never reach this code path,
        // so the residue is zero outside attack scenarios.
    }
