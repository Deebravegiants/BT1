### Title
Same-chain partial fills round proportional escrow release to zero when `fillAmount * order.inputs[i].amount < totalRequired`, causing solvers to lose their delivered output tokens - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`_fillSameChain` computes the escrow release for a partial fill via integer division `(order.inputs[i].amount * fillAmount) / totalRequired` with no floor/minimum check. When the numerator is smaller than `totalRequired`, this rounds down to `0`, so a solver who transfers real output tokens to the beneficiary receives zero escrowed input tokens in return — the exact "volume/price rounds to zero" bug class described in the external report, here manifesting as `inputs[i].amount * fillAmount / totalRequired`.

### Finding Description
In `_fillSameChain` [1](#0-0) , when a fill does not complete the order, the escrowed amount released to the filling solver is computed as:

```solidity
escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
```

This is a direct structural analog of the reported `volume / price` bug: whenever `order.inputs[i].amount * fillAmount < totalRequired`, the division truncates to `0`. This can happen either because:
- The input token has fewer decimals than the output token (e.g. input is USDC (6 decimals), output is an 18-decimal token), so a modest `fillAmount` relative to `totalRequired` yields a numerator smaller than the denominator, or
- `fillAmount` is simply small relative to `totalRequired` (a legitimate small partial fill).

Crucially, unlike the `_fillSameChain`'s handling of `solverAmount == 0` (which is explicitly skipped at line 75 [2](#0-1) ), there is no check that the *computed* `escrowedAmount` is non-zero before the transfer of `beneficiaryTotal` (the solver's real output tokens) proceeds:

```solidity
IERC20(token).safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal);
...
escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
escrowedInputs[i] = TokenInfo({token: order.inputs[i].token, amount: escrowedAmount});
```

The solver has already paid the beneficiary in full for `fillAmount` before `escrowedAmount` is computed and passed to `_withdraw`. If `escrowedAmount == 0`, the solver transfers real value and receives nothing back from escrow for that fill — the same "transaction accepted, funds unrecoverable" pattern as the H-01 report, just with the solver in the role of the party who loses funds instead of the auction bidder.

The repository does contain a fix for a related but distinct issue ("ROUNDING DUST IN PARTIAL FILLS (Finding #4)"), which ensures the *final* completing fill receives the leftover dust so the escrow is not permanently stuck [3](#0-2) . That fix only addresses cumulative dust loss across multiple fills of the *same* solver-chosen amounts summing near-exactly to `totalRequired`; it does not address (and the test suite does not cover) the case where a *single* fill's `fillAmount` is small enough, or the input/output decimal mismatch large enough, that the per-fill `escrowedAmount` computes to exactly `0` for that fill, in which case the solver pays real tokens and gets a `0`-amount escrow release for that step with no revert.

### Impact Explanation
A solver providing output tokens to a beneficiary in a same-chain partial fill can have its corresponding escrow release computed as `0` due to integer-division truncation, resulting in a complete loss of the value transferred for that fill step — high-severity direct loss of funds for the party executing the fill, with no revert or protection to catch the zero-release case.

### Likelihood Explanation
Medium: this requires either (a) input/output token pairs with sufficiently different decimals (e.g., 6-decimal input vs 18-decimal output, both extremely common — USDC/DAI, USDC/WETH), combined with a modest partial `fillAmount`, or (b) a solver choosing/being forced (e.g. by another concurrent partial filler leaving a small `remaining`) to fill a small remaining amount. Both are realistic conditions in an open, permissionless same-chain solver market where anyone can call `fillOrder` with an arbitrary `fillAmount` for any live order.

### Recommendation
In `_fillSameChain`, after computing `escrowedAmount` for a non-final partial fill, revert (e.g. with a new `ZeroEscrowRelease()`/`InvalidInput()` error) if `escrowedAmount == 0`, mirroring the existing `solverAmount == 0` guard. Alternatively, enforce a minimum fill amount such that `order.inputs[i].amount * fillAmount >= totalRequired` is guaranteed before any output-token transfer to the beneficiary occurs, so a solver can never pay real value for a zero-value escrow release.

### Proof of Concept
1. User places a same-chain order with `inputs[0] = {token: USDC, amount: 1_000_000}` (1 USDC, 6 decimals) and `output.assets[0] = {token: SOME_18_DECIMAL_TOKEN, amount: 10_000_000_000_000_000_000}` (10 tokens, 18 decimals), so `totalRequired = 10e18`.
2. A solver calls `fillOrder` with `outputs[0].amount = 1e11` (a small, non-zero partial fill of the 18-decimal output token — well below `totalRequired` but plausible as a legitimate small partial fill).
3. In `_fillSameChain`, `fillAmount = 1e11`, and `escrowedAmount = (1_000_000 * 1e11) / 10e18 = 1e17 / 1e19 = 0` due to integer truncation.
4. The solver's `safeTransferFrom` sends the full `fillAmount` (1e11 units) of the output token to the beneficiary at line 102 [4](#0-3) , but `escrowedInputs[i].amount = 0` is what gets passed into `_withdraw`, so the solver receives `0` USDC from escrow for a real token transfer — total loss of that fill's inputs for the solver, without any revert.

    /// @notice Verifies that rounding dust from integer division in partial fills
    /// is not permanently locked. The final solver completing the order should
    /// receive the full remaining escrow balance rather than a truncated amount.
    function testPartialFill_RoundingDustReleasedToFinalSolver() public {
        // Choose amounts that produce rounding truncation:
        // input = 100 USDC (100e6), output = 3 DAI (3e18)
        // Each of 3 solvers fills 1 DAI. Proportional release per fill:
        //   100e6 * 1e18 / 3e18 = 33333333 (truncated from 33333333.33...)
        // Without fix: 3 * 33333333 = 99999999, leaving 1 unit locked.
        // With fix: final solver gets remaining balance = 100e6 - 2*33333333 = 33333334
        uint256 inputAmount = 100 * 1e6; // 100 USDC
        uint256 outputAmount = 3 * 1e18; // 3 DAI

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: outputAmount});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        // User places order
        vm.startPrank(user);
        usdc.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;

        uint256 fillPerSolver = 1e18; // Each solver fills 1 DAI
        uint256 truncatedRelease = (inputAmount * fillPerSolver) / outputAmount; // 33333333

        // --- Solver 1 fills 1 DAI ---
        address solver1 = makeCleanAddr("solver1");
        vm.deal(solver1, 1 ether);
        deal(address(dai), solver1, 10 * 1e18);
        uint256 solver1UsdcBefore = usdc.balanceOf(solver1);

        vm.startPrank(solver1);
        dai.approve(address(intentGateway), fillPerSolver);
        TokenInfo[] memory out1 = new TokenInfo[](1);
        out1[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: fillPerSolver});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, validUntil: 0, outputs: out1}));
        vm.stopPrank();

        assertEq(
            usdc.balanceOf(solver1),
            solver1UsdcBefore + truncatedRelease,
            "Solver1 should receive truncated proportional USDC"
        );

        // --- Solver 2 fills 1 DAI ---
        address solver2 = makeCleanAddr("solver2");
        vm.deal(solver2, 1 ether);
        deal(address(dai), solver2, 10 * 1e18);
        uint256 solver2UsdcBefore = usdc.balanceOf(solver2);

        vm.startPrank(solver2);
        dai.approve(address(intentGateway), fillPerSolver);
        TokenInfo[] memory out2 = new TokenInfo[](1);
        out2[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: fillPerSolver});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, validUntil: 0, outputs: out2}));
        vm.stopPrank();

        assertEq(
            usdc.balanceOf(solver2),
            solver2UsdcBefore + truncatedRelease,
            "Solver2 should receive truncated proportional USDC"
        );

        // --- Solver 3 fills final 1 DAI (completes the order) ---
        address solver3 = makeCleanAddr("solver3");
        vm.deal(solver3, 1 ether);
        deal(address(dai), solver3, 10 * 1e18);
        uint256 solver3UsdcBefore = usdc.balanceOf(solver3);

        vm.startPrank(solver3);
        dai.approve(address(intentGateway), fillPerSolver);
        TokenInfo[] memory out3 = new TokenInfo[](1);
        out3[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: fillPerSolver});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, validUntil: 0, outputs: out3}));
        vm.stopPrank();

        // Final solver should receive the remaining balance (truncatedRelease + 1 rounding unit)
        uint256 expectedFinalRelease = inputAmount - (2 * truncatedRelease); // 33333334
        assertEq(
            usdc.balanceOf(solver3),
            solver3UsdcBefore + expectedFinalRelease,
            "Final solver should receive remaining escrow including rounding dust"
        );
        assertGt(expectedFinalRelease, truncatedRelease, "Final release should be larger due to rounding dust");

        // Gateway should have zero USDC — no dust locked
        assertEq(usdc.balanceOf(address(intentGateway)), 0, "Gateway should have zero USDC - no rounding dust locked");
    }
