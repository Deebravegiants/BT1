### Title
Unscoped, client-controlled `requestID` in the HTTP Trigger gateway handler enables cross-caller griefing/DoS analogous to permit front-running - (File: `core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go`)

### Summary
The `httpTriggerHandler` in the internet-facing CRE Gateway keys its in-flight request cache purely by the client-supplied JSON-RPC `req.ID`, with no binding to the caller's identity/signature and no per-owner namespacing. Just as RouterV2's `permit()` call consumes a one-time, unauthenticated identifier (the ECDSA signature/nonce) that any third party can replay ahead of the legitimate submitter to force the victim's follow-on call to revert, this handler treats `req.ID` as a globally unique, unauthenticated token: whoever submits a given ID first "wins" it, and every subsequent legitimate request using the same ID is permanently rejected with `jsonrpc.ErrConflict`.

### Finding Description
`HandleUserTriggerRequest` performs `validatedTriggerRequest` → `resolveWorkflowID` → `authorizeRequest` → `checkRateLimit` → `setupCallback`, in that order: [1](#0-0) 

`setupCallback` registers the request purely by the raw `requestID` string in a single global map (`h.callbacks`), with no scoping by sender, workflow owner, or authorized key: [2](#0-1) 

If an entry for that ID already exists, the handler unconditionally rejects the new (potentially legitimate) request with a conflict error and never re-attempts delivery: [3](#0-2) 

The handler's own test confirms this "second submitter always loses" semantics: [4](#0-3) 

Crucially, `req.ID` itself carries no cryptographic binding — it is not part of the signed JWT payload's identity claim in a way that prevents reuse by a different caller, and `authorizeRequest` only verifies that the caller holds a key authorized for the target `workflowID`, not that the caller "owns" a particular `requestID`: [5](#0-4) 

This is structurally identical to the reported RouterV2 issue: an externally-controllable, single-use identifier is consumed without any fallback/idempotent handling, so anyone able to submit a matching identifier first — whether by observing it, guessing it, or simply colliding with a predictable/reused client-generated ID — can force the legitimate request to fail outright, with no retry-with-fresh-identifier path built into the protocol (the client, not the gateway, must notice the conflict and resubmit with a new ID, burning the original request/attempt in the process).

### Impact Explanation
Any party capable of invoking `HandleUserTriggerRequest` for a workflow that accepts multiple authorized keys (e.g., a shared/public HTTP-triggered workflow with more than one authorized caller) can grief co-tenants sharing that trigger by pre-registering colliding `requestID`s, causing legitimate in-flight requests to be denied with `ErrConflict` and lose their invocation attempt. Because the cache is a single flat map keyed only by the attacker-influenceable string, there is no cross-tenant isolation: one caller's choice of ID can deny another unrelated caller's request to the same workflow purely by timing, exactly mirroring the permit-front-running "attacker consumes the resource first, victim's otherwise-valid call reverts" pattern from the reported issue.

### Likelihood Explanation
Exploitation requires only the ability to submit HTTP trigger requests that pass `authorizeRequest` for a shared/public workflow (i.e., holding any one of the workflow's authorized keys, not administrative privilege) plus knowledge or prediction of another caller's `requestID` (deterministic/sequential/timestamp-derived IDs, or IDs observable through normal client-side logging/telemetry, make this trivially exploitable; fully random UUIDs reduce but do not eliminate the risk of accidental collisions causing the same denial). This is a realistic, unprivileged-caller-triggerable condition reachable purely through the gateway's public HTTP trigger API.

### Recommendation
Scope the in-flight request cache key by `(authorizedKey/sender, workflowID, requestID)` rather than by raw `requestID` alone, so no unrelated caller can collide with or squat another caller's identifier. Additionally, consider deriving or validating `requestID` uniqueness server-side (e.g., requiring it be bound into the signed JWT payload) so it cannot be freely chosen/replayed by a different authorized party, closing the same class of "unauthenticated one-time-identifier consumption" gap called out in the RouterV2 permit finding.

### Proof of Concept
1. Workflow `W` is configured with two independently authorized keys, `keyA` (legitimate user) and `keyB` (attacker), both valid per `workflowMetadataHandler.Authorize` for `resolveWorkflowID`/`authorizeRequest`.
2. Attacker, holding `keyB`, predicts or learns that the legitimate user will submit `requestID = "X"` (e.g., a timestamp-derived or otherwise low-entropy client-generated ID) and submits their own trigger request with `ID = "X"` first; `setupCallback` succeeds, inserting `h.callbacks["X"]`.
3. Legitimate user's request with the same `ID = "X"` arrives afterward and passes `authorizeRequest` normally, but `setupCallback` finds `h.callbacks["X"]` already populated and returns `jsonrpc.ErrConflict` via `handleUserError`, per `core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go` lines 419-426, exactly as exercised by the existing `duplicate request ID` test at `http_trigger_handler_test.go` lines 320-358.
4. The legitimate user's workflow execution never runs for that attempt; they must detect the conflict and resubmit under a new ID, mirroring the gas-loss/failed-transaction outcome described in the permit front-running report.

func (h *httpTriggerHandler) HandleUserTriggerRequest(ctx context.Context, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback, requestStartTime time.Time) error {
	triggerReq, err := h.validatedTriggerRequest(ctx, req, callback)
	if err != nil {
		return err
	}

	workflowID, err := h.resolveWorkflowID(ctx, triggerReq, req.ID, callback)
	if err != nil {
		return err
	}

	key, err := h.authorizeRequest(ctx, workflowID, req, callback)
	if err != nil {
		return err
	}

	if err = h.checkRateLimit(ctx, workflowID, req.ID, callback); err != nil {
		return err
	}

	strippedWorkflowID := strings.TrimPrefix(workflowID, "0x")
	legacyExecutionID, err := workflows.EncodeExecutionID(strippedWorkflowID, req.ID) //nolint:staticcheck // legacy ID kept for observability comparison
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID: " + err.Error())
	}
	// Workflows shouldn't use more than one HTTP trigger. If we ever need to support multiple triggers, we'd need to pass
	// trigger index to the Gateway handler and somehow allow senders to pick. For now, we use trigger index 0.
	// Execution IDs here are used only for logging.
	executionIDWithTriggerIndex, err := workflows.GenerateExecutionIDWithTriggerIndex(strippedWorkflowID, req.ID, 0)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID with trigger index: " + err.Error())
	}
	h.lggr.Debugw("processing request",
		"legacyExecutionID", legacyExecutionID,
		"executionIDWithTriggerIndex", executionIDWithTriggerIndex,
		"requestID", req.ID,
		"workflowID", workflowID)

	reqWithKey, err := reqWithAuthorizedKey(triggerReq, *key)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error marshaling trigger request: " + err.Error())
	}

	doneCh, err := h.setupCallback(ctx, req.ID, callback, requestStartTime, workflowID)
	if err != nil {
		return err
	}

	return h.sendWithRetries(ctx, legacyExecutionID, executionIDWithTriggerIndex, reqWithKey, workflowID, doneCh)

func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}

	// Build one response aggregator per shard the workflow is assigned to.
	assigned := h.workflowMetadataHandler.WorkflowShards(workflowID)
	if len(assigned) == 0 {
		// this shouldn't happen because we checked it in authorizeRequest()
		h.handleUserError(ctx, requestID, jsonrpc.ErrInternal, fmt.Sprintf("Workflow %s is not assigned to any DONs", workflowID), callback)
		return nil, errors.New("workflow is not assigned to any shards")
	}

	aggregators := make(map[string]*aggregation.IdenticalNodeResponseAggregator, len(assigned))
	for _, shard := range assigned {
		// (N+F)//2 + 1 threshold where N = number of nodes, F = number of faulty nodes
		threshold := (len(shard.members)+shard.f)/2 + 1
		agg, err := aggregation.NewIdenticalNodeResponseAggregator(threshold)
		if err != nil {
			return nil, errors.New("failed to create response aggregator: " + err.Error())
		}
		aggregators[shard.donID] = agg
	}

	doneCh := make(chan struct{})
	h.callbacks[requestID] = savedCallback{
		Callback:            callback,
		requestStartTime:    requestStartTime,
		createdAt:           time.Now(),
		responseAggregators: aggregators,
		doneCh:              doneCh,
	}
	return doneCh, nil
}
