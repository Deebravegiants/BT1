### Title
Webhook `shop-domain` header is trusted without HMAC coverage, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw HTTP body for HMAC verification, but downstream code (`Webhooks::Registry.process`) trusts the unauthenticated `shop-domain` header to identify which merchant the webhook belongs to. An attacker who can produce one validly-HMAC-signed webhook body (e.g., by triggering a webhook on their own store, since the app's `client_secret` is shared across every shop that installs the app) can replay that exact body with a forged `x-shopify-shop-domain` header pointing at a victim shop. The gem's HMAC check passes because it never covers the shop header, and the forged shop value is handed straight to the app's webhook handler as authoritative tenant context.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from a separate, unsigned header: [2](#0-1) 

`HmacValidator.validate` computes the signature over `to_signable_string` only: [3](#0-2) 

`Registry.process` validates only that body-derived HMAC, then forwards the header-derived `request.shop` (and `topic`/`webhook_id`/`api_version`, also uncovered) directly to the registered handler as trusted tenant/topic metadata: [4](#0-3) 

The equality the code implicitly assumes is:
`bytes_verified_by_hmac == bytes_used_to_identify_the_tenant`

but in reality:
`bytes_verified_by_hmac (raw_body) != bytes_used_to_identify_the_tenant (shop-domain header)`

Because Shopify apps use a single `client_secret` for HMAC signing across all installed shops, any shop that has the app installed can capture a legitimately-signed webhook payload+HMAC from its own store, then replay that identical body/HMAC pair to the app's webhook endpoint with the `shop-domain` (and/or `topic`/`webhook_id`) header swapped to a different, victim shop. `HmacValidator.validate` will still return `true` because it only checks the body bytes, and `WebhookMetadata.shop` will carry the attacker-chosen value into the handler.

### Impact Explanation
This breaks the tenant-identity binding that webhook processing relies on: the shop value the app uses to look up/act on a specific merchant's data is not the shop value that was actually cryptographically authenticated. A malicious merchant (an "unprivileged" party relative to other tenants) can spoof webhooks as if they originated from a different shop, causing the app to process mandatory or business webhooks (e.g., `customers/data_request`, `shop/redact`, order/product update webhooks) under the wrong tenant. Depending on how the host app's handler uses `WebhookMetadata#shop` (e.g., to fetch/update the session or merchant record), this can result in cross-tenant data confusion/exfiltration or triggering privileged operations against a shop the attacker doesn't own — a cross-tenant access issue.

### Likelihood Explanation
Any user who can install the target app on their own shop meets the only precondition: obtaining one validly-signed webhook body from their own store (trivial, since they control that store's activity), then replaying it to the app's public webhook endpoint with a forged shop header. No secret material, session, or access token is required — only observation of the app's public webhook URL and normal app usage in their own store.

### Recommendation
Bind the header-derived fields (`shop`, `topic`, `webhook_id`, `api_version`) into the signed payload verification, e.g. by including them in `to_signable_string` if Shopify's signing scheme supports it, or — more practically — by having the host application independently confirm that `request.shop` matches the shop associated with the webhook subscription/session before trusting it, rather than relying solely on the raw-body HMAC to authenticate the shop identity. At minimum, document prominently that `Webhooks::Request#shop`/`#topic`/`#webhook_id` are NOT covered by the HMAC and must not be trusted as tenant identifiers without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (app's `client_secret` is shared across all installs).
2. Attacker triggers a webhook (e.g., `orders/create`) on their own shop, capturing `raw_body` and the valid `x-shopify-hmac-sha256` header Shopify sent.
3. Attacker POSTs the identical `raw_body` and `hmac-sha256` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` (called in `Registry.process`, `lib/shopify_api/webhooks/registry.rb:190`) returns `true` because it only checks `raw_body` against the HMAC.
5. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, so the app processes the webhook as if it belongs to `victim-shop.myshopify.com`.

          received_signature = verifiable_query.hmac
