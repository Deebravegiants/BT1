### Title
Webhook `shop-domain` (and `topic`) headers are not covered by the HMAC signature, allowing cross-tenant webhook replay — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate` only authenticates the request body — it never binds the `shop-domain` header (nor `topic`) into the signature [2](#0-1) . Yet `Registry.process` trusts `request.shop` (read straight from the unauthenticated `shop-domain`/`x-shopify-shop-domain` header) as the tenant identity passed to the webhook handler [3](#0-2) . This breaks the intended binding: `hmac_valid ⇒ (body, shop) authentic`, when in fact only `hmac_valid ⇒ (body) authentic`.

### Finding Description
`Request#shop` and `Request#topic` are read from HTTP headers [4](#0-3) , while `hmac` is read from the `hmac-sha256` header and validated against a signature computed purely over `@raw_body` [5](#0-4) [1](#0-0) .

`Registry.process` performs exactly one check — `Utils::HmacValidator.validate(request)` — before dispatching to the topic handler with `shop: request.shop` taken from that same unauthenticated header [3](#0-2) .

Because `shop` (and `topic`) never enter the signable string, an attacker who possesses one valid `(raw_body, hmac)` pair — e.g. from a webhook legitimately delivered to their own install of the app, which they fully control and can trigger at will — can resend that identical body+hmac pair to the app's public webhook endpoint while substituting the `shop-domain` header for a different (victim) shop that also has the app installed. `HmacValidator.validate` will still pass, because it recomputes the HMAC only from `@raw_body`, which is unchanged [6](#0-5) . `Registry.process` then invokes the app's handler with `WebhookMetadata` claiming the forged `shop`, `topic`, and attacker-chosen body [7](#0-6) .

This is the same bug class as the report: a field that is *acted on* by the consuming logic (here, `shop`/tenant identity) is not covered by the authenticity check (here, the HMAC), letting an unprivileged caller present unaccounted-for/mismatched data as trusted.

### Impact Explanation
Most host applications that use `ShopifyApp`-style patterns key their data (orders, products, tokens, uninstall handling, etc.) by the `shop` value from the webhook payload/handler metadata. Since `shop` is not authenticated, any user who can get *any* valid signed webhook body from Shopify (trivially available to any merchant who installs the app on their own store) can forge deliveries that appear to originate from a *different* merchant's shop, and can also spoof the `topic`, causing the wrong handler logic to run against another tenant's identifier. This is a cross-tenant identity confusion at the point where the gem hands data to the app — a Critical-class issue per the rubric ("cross-tenant access").

### Likelihood Explanation
The webhook endpoint is, by design, a public HTTP endpoint reachable by any internet user (Shopify pushes webhooks to it over the open internet). No secret is required by the attacker beyond obtaining one legitimately-signed `(body, hmac)` pair — which any user installing the app on their own store can trivially generate on demand (e.g. by editing a product to trigger a `products/update` webhook). Because the only server-side check (`HmacValidator.validate`) never inspects `shop`/`topic`, replaying with altered headers succeeds unconditionally on the gem side. Likelihood is high for any consumer that dispatches on `WebhookMetadata#shop`/`#topic` without independent verification.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the value that is HMAC-verified (or otherwise cryptographically tie them to the raw body), for example by including them in `to_signable_string`, or by requiring the caller to additionally confirm `request.shop` against a known/allow-listed shop before dispatch. At minimum, document prominently that `shop`/`topic` headers are unauthenticated so consumers do not treat `WebhookMetadata#shop` as a trust boundary.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers any webhook (e.g. edits a product to fire `products/update`). They capture the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` that Shopify sent to the app's webhook endpoint — this pair is valid because Shopify computed `H = HMAC-SHA256(secret, B)`.
2. Attacker crafts a new POST request to the same webhook endpoint using the exact same body `B` and header `H`, but sets `shop-domain: victim-shop.myshopify.com` (a real shop that has the app installed) and, if desired, a different `topic` header.
3. The app constructs `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})`; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC solely from `B` and matches `H` — validation succeeds [8](#0-7) .
4. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` [7](#0-6) , causing the app to process attacker-supplied data under the victim shop's identity.
