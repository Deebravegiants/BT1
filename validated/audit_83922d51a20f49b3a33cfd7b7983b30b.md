Webhook `shop` (and `topic`/`webhook_id`/`api_version`) header values are trusted for tenant dispatch without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` implements the `VerifiableQuery` interface used by `HmacValidator`, but its `to_signable_string` only returns the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers that are never part of the signed material. `Registry.process` trusts `request.shop` as the tenant identity forwarded to the app's webhook handler after only checking that the body's HMAC is valid.

### Finding Description
`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field: [1](#0-0) 

For webhooks, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are pulled directly from HTTP headers, which are completely outside the HMAC: [3](#0-2) 

`Registry.process` only verifies the body HMAC and then dispatches to the handler using `request.shop` (and `request.topic`) as the trusted tenant/topic identity, with no cross-check that these header values are consistent with anything cryptographically bound to the request: [4](#0-3) 

The binding that should hold is: `hmac(raw_body ‖ shop ‖ topic)` verified == `(shop, topic)` delivered to the handler. Instead, only `hmac(raw_body)` is verified, while `(shop, topic)` are taken from unauthenticated headers, i.e. `shop_verified != shop_used_for_dispatch`.

Because Shopify signs webhooks using the app's single shared `api_secret_key` (identical for every shop that has installed the app), any attacker who is themselves a legitimate, unprivileged installer of the target app receives at least one genuine webhook delivery with a valid HMAC over some body. That attacker can then replay the exact same `raw_body` + `hmac-sha256` header to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and/or `X-Shopify-Topic`) with a victim shop's domain. `HmacValidator.validate` still passes because it only checks the body, and `Registry.process` hands the handler a `WebhookMetadata` claiming the victim shop as the source.

### Impact Explanation
This breaks the tenant boundary the webhook receiver is supposed to enforce: an app built on this gem that keys per-shop state, data writes, or redaction/GDPR actions off `WebhookMetadata#shop` can be made to apply another shop's webhook body under a different (victim) shop identity, or vice versa — a cross-tenant confused-deputy condition. This matches the Critical "cross-tenant access" impact category, since the identity binding between the cryptographically-verified content and the tenant used for dispatch is missing.

### Likelihood Explanation
Exploitability requires only that the attacker be able to install the target app on their own store (an unprivileged, low-barrier action for any Shopify merchant/developer) to obtain one genuine, validly-signed webhook body, then replay it against the app's public webhook endpoint with a forged `shop-domain`/`topic` header. No access to `api_secret_key`, access tokens, or victim credentials is needed — likelihood is Medium-to-High for apps that trust `WebhookMetadata#shop`/`#topic` for tenant-scoped side effects, which is the documented intended use.

### Recommendation
Include the `shop`, `topic`, and other webhook-identifying headers in the value that is HMAC-verified (or otherwise cryptographically bind them, e.g. via a compound signable string combining `raw_body` with these header values), so that the same `hmac-sha256` cannot be replayed with substituted headers. At minimum, document/warn that consumers of `WebhookMetadata` must independently verify shop ownership/consistency before performing tenant-scoped actions, and consider validating `shop` format/domain in the gem itself as defense in depth.

### Proof of Concept
1. Attacker installs Target App on their own store `attacker.myshopify.com`, receives a webhook (e.g. `orders/create`) with a valid `X-Shopify-Hmac-Sha256` computed by Shopify over the JSON body using the app's shared `api_secret_key`.
2. Attacker captures the raw body and the `hmac-sha256` value.
3. Attacker POSTs the identical raw body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present).
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body`: [5](#0-4) 
6. The handler is invoked with `WebhookMetadata` reporting `shop: "victim.myshopify.com"`, even though the body actually originated from `attacker.myshopify.com`'s installation — a cross-tenant confused-deputy result.
