### Title
GetResponse relayer-fee payout is an unguarded external call that can revert and permanently stall delivery of the whole `handleGetResponses` batch - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming(GetResponse, address relayer)` mirrors the ERC777 "winner can stall the system" pattern from the PoolTogether audit: after crediting the destination module, it makes a second, un-isolated external call — an ERC20 `safeTransfer` of the relayer fee to the "winner" (the relayer who is being rewarded) — that can revert and take down delivery of every other response bundled in the same transaction.

### Finding Description
In `EvmHost.dispatchIncoming(GetResponse memory response, address relayer)` [1](#0-0) , the module callback to the app (`IApp.onGetResponse`) is invoked defensively with a low-level `.call` and an explicit `success` check; on failure the response receipt is deleted so the response stays retryable and the function returns normally without reverting: [2](#0-1) 

Immediately after that guarded call succeeds, the function unconditionally pays the relayer's fee with a direct (non-try/catch) `safeTransfer` call:
```
uint256 fee = _requestCommitments[commitment].fee;
if (fee != 0) {
    IERC20(feeToken()).safeTransfer(relayer, fee);
}
``` [3](#0-2) 

This is the same architectural mistake as the referenced PoolTogether issue: a reward-crediting step to an externally-controlled/blacklistable address is placed in the mandatory critical path, without the same failure-isolation applied to the sibling module callback just above it. If `feeToken()` is (or becomes) a token that can refuse a transfer to a specific address — e.g. a blacklist-capable stablecoin such as USDC where the relayer's address is later sanctioned/blacklisted, or a paused/rebasing/fee-on-transfer token whose `transfer` reverts under some condition — this `safeTransfer` reverts. Because it is not wrapped in a low-level call/`success` check like the module callback, the revert propagates out of `dispatchIncoming` entirely.

`dispatchIncoming` is called by `IHandlerV2.handleGetResponses`, which processes a batch of `GetResponse`s delivered together, and can itself be included inside `HandlerV2.batchCall`, which delegatecalls sequentially and reverts the entire batch on any single failure [4](#0-3) . Consequently, a single response whose relayer-fee payout reverts poisons the entire batch: every other legitimate `GetResponse` bundled in that transaction (and the same-transaction consensus/POST calls if batched via `batchCall`) fails to be delivered, forcing relayers to identify and exclude the poisoned response by trial and error before resubmission.

This differs materially from the equivalent POST-request path, `dispatchIncoming(PostRequest, address relayer)` [5](#0-4) , which contains no such unguarded post-callback external call and thus cannot be stalled this way — confirming the GetResponse path is the outlier that reproduces the audit's bug class.

### Impact Explanation
Any relayer whose fee-token account becomes untransferable (blacklisted stablecoin, paused token, governance-swapped fee token with quirks) turns every batch containing a response they relayed into a permanently reverting transaction until manually excluded. Because relayers race to batch messages for gas efficiency (`IHandlerV2.batchCall`, `submit_batch_messages` in the tesseract relayer [6](#0-5) ), this can delay/deny delivery of unrelated GetResponses sharing the batch, and — more importantly — permanently denies the relayer their otherwise-earned fee for that GetResponse (the underlying request commitment, response receipt, and reward all roll back together, so the fee can never be paid to that address while still requiring the response to be delivered by that same relayer for the receipt to register them). This is a freezing-of-funds / denial-of-delivery condition reachable by a single relayed transaction, matching the High severity of the referenced finding.

### Likelihood Explanation
Reaching this requires only: (1) `feeToken()` being a token capable of rejecting a transfer to a specific address (governance can change `feeToken` via `HostManager`/`updateHostParams`, and stablecoins with blacklist functionality such as USDC are a realistic choice for a fee token), and (2) a relayer address that becomes blacklisted/restricted, or a malicious relayer intentionally using an address they know will be rejected in order to grief co-batched responses. No privileged role, governance compromise, or off-chain infrastructure fault is needed — an ordinary permissionless relayer submitting `handleGetResponses`/`batchCall` triggers the vulnerable path, matching the "any unprivileged relayer" pattern in scope.

### Recommendation
Isolate the relayer-fee payout from the module-delivery success path, the same way the op above it is isolated:
- Wrap the `IERC20(feeToken()).safeTransfer(relayer, fee)` call in a low-level `call` (or a try/catch on a call-through helper) and, on failure, credit the fee to an internal, pull-based balance for `relayer` instead of reverting the whole `dispatchIncoming` invocation.
- Alternatively, decouple fee accounting entirely from `dispatchIncoming`: emit the fee owed and let relayers withdraw fee balances via a separate, always-successful pull-payment function, so a hostile/blacklisted recipient can never block message delivery or co-batched deliveries.
- Ensure `feeToken()` changes go through the same invariant checks as `CannotChangeFeeToken` and consider disallowing fee tokens with owner-controlled blacklists.

### Proof of Concept
1. Governance configures `feeToken()` to a blacklist-capable ERC20 (e.g., USDC) via `HostManager`/`updateHostParams` [7](#0-6) .
2. Relayer `R` submits `handleGetResponses` for `GetRequest`s whose fee will be paid to `R`; `R`'s address is later blacklisted on the fee token (or `R` is a malicious actor who deliberately uses/derives an address that USDC has already blacklisted).
3. Any relayer bundles that pending response together with other unrelated responses in one `HandlerV2.batchCall`/`handleGetResponses` transaction.
4. Inside `EvmHost.dispatchIncoming(GetResponse, R)`, `IApp.onGetResponse` succeeds (guarded call returns `success = true`), but the subsequent unguarded `IERC20(feeToken()).safeTransfer(R, fee)` reverts because `R` is blacklisted.
5. The revert propagates out of `dispatchIncoming` → `handleGetResponses` → `batchCall`, reverting the entire transaction, including the delivery of every other bundled `GetResponse`, until relayers manually detect and exclude the poisoned response.

    /**
     * @dev Dispatch an incoming GET response to source module
     * @param response - get response
     */
    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
