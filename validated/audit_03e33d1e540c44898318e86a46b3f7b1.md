### Title
Webhook shop/topic identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw HTTP body when validating a webhook's authenticity, while the `shop`, `topic`, `webhook_id`, and `api_version` fields — which `ShopifyAPI::Webhooks::Registry.process` uses to route and attribute the webhook to a specific merchant/tenant — come from HTTP headers that are never included in the HMAC-signed content. This breaks the equality that should hold: `hmac == HMAC(secret, body ‖ shop ‖ topic)`, but the code only ever checks `hmac == HMAC(secret, body)`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated headers with no cryptographic binding to the signed body: [2](#0-1) 

`HmacValidator.validate` only verifies the value returned by `to_signable_string` against the shared `api_secret_key`: [3](#0-2) 

`Registry.process` then trusts `request.shop` and `request.topic` for tenant/handler dispatch after only checking that the body HMAC is valid: [4](#0-3) 

Because `api_secret_key` is the app's single client secret shared across every installed shop (it is not a per-tenant secret), any unauthorized internet user who installs the app on their own shop can legitimately receive a real webhook (body + valid HMAC) for that shop. They can then replay that exact `raw_body`/`hmac-sha256` pair directly against the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for an arbitrary victim shop. `HmacValidator.validate` still passes because it never inspects the headers, and `Registry.process` will hand the attacker-controlled body to the victim's handler tagged with the victim's `shop` value — a shop-authenticated-versus-shop-stored-as-key mismatch.

### Impact Explanation
This allows cross-tenant confusion: an app that keys any state (order processing, idempotency, feature flags, billing, data writes) by `WebhookMetadata#shop` can be made to apply attacker-supplied data to a different, victim tenant's records, since the tenant identifier is never bound to the signed payload. This matches the report's underlying bug class — an identity/authorization field ("which executor"/"which tenant") that is accepted from an unauthenticated channel while a different signed check is treated as sufficient authorization for it.

### Likelihood Explanation
Exploitation requires only (1) installing the target app on a shop the attacker controls (normal, unprivileged self-service action for any public/free app) to obtain one valid `(body, hmac)` pair, and (2) sending a normal unauthenticated HTTP POST to the app's public webhook endpoint with a forged `shop-domain`/`topic` header — no TLS interception, credentials, or leaked secrets are required.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed content (or otherwise cryptographically bind them to the body, e.g. concatenate them before hashing) so any tampering with these header values invalidates the signature. At minimum, `Registry.process`/`VerifiableQuery` implementations should never treat header-derived identity fields as trusted unless they are part of the material verified by `HmacValidator.validate`.

### Proof of Concept
1. Attacker signs up for the target app on their own store `attacker.myshopify.com`, triggering a real webhook delivery, e.g. for `orders/create`. The attacker controls the endpoint that receives it (or can observe the delivery via their own logging proxy that is not the target's TLS channel), obtaining `raw_body` `B` and header `x-shopify-hmac-sha256: H` where `H = HMAC_SHA256(api_secret_key, B)`.
2. Attacker sends a POST request directly to the same app's public webhook route with:
   - Body: `B` (unchanged)
   - `x-shopify-hmac-sha256: H` (unchanged, still valid because only `B` is signed)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - `x-shopify-topic: orders/create` (unchanged or forged to another registered topic)
3. `Utils::HmacValidator.validate(request)` returns `true` since it only checks `HMAC(secret, B) == H`.
4. `Registry.process` dispatches to the registered handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body `B`, causing the app to process attacker data as if it originated from the victim tenant.
