### Title
Webhook `shop` identity field is not covered by the HMAC signature, enabling cross-tenant impersonation via replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body [1](#0-0) , while `shop`, `topic`, and `webhook_id` are read straight from unauthenticated headers [2](#0-1) . `Registry.process` validates only this body-only HMAC and then forwards the header-derived `shop` value directly into the handler as the tenant identity [3](#0-2) . This breaks the binding "shop authenticated == shop acted upon," matching the report's bug class of trusting a value not actually covered by the cryptographic check (there, `wethAddress` vs. actual asset; here, header `shop` vs. HMAC-signed bytes).

### Finding Description
The HMAC that this gem verifies for webhooks is computed solely over the raw JSON body: [1](#0-0) 

But the `shop`, `topic`, and `webhook_id` accessors used downstream come entirely from HTTP headers that are never mixed into the signed string: [4](#0-3) 

`Registry.process` validates the HMAC and then constructs `WebhookMetadata` using `request.shop` — the unauthenticated header value — as the identity that is handed to the application's handler: [5](#0-4) 

Because the signature check `Utils::HmacValidator.validate(request)` only proves the body bytes are untampered [6](#0-5) , it says nothing about which shop the body belongs to. Any body+HMAC pair that is valid for shop A remains "valid" (in the eyes of this gem) when replayed with the `shopify-shop-domain` header changed to shop B, since that header is outside the HMAC's scope.

### Impact Explanation
An unprivileged internet user can install the target app on a shop they control (a normal, free/dev store), and Shopify will deliver at least one genuine webhook — a legitimate `(raw_body, hmac)` pair signed with the app's `client_secret` that the attacker never needs to know or extract. The attacker replays that exact body and HMAC to the app's webhook endpoint, but substitutes the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `Registry.process` will accept the request (`Utils::HmacValidator.validate` passes, since only the body is checked) and will invoke the registered handler with `WebhookMetadata#shop` equal to the victim's domain. Any host application that follows this gem's own intended usage pattern — using `WebhookMetadata#shop` to resolve tenant/session context (e.g., to look up which shop's session/store data to mutate) — will act on the victim's data as if the attacker's payload originated from that shop. This is a cross-tenant access primitive achieved without ever possessing `api_secret_key`, an access token, or any privileged credential.

### Likelihood Explanation
High. Any developer/attacker can freely create a Shopify development store, install the app, and receive at least one real webhook delivery for a topic they control (e.g., `app/uninstalled`, `shop/update`), giving them a valid `(body, hmac)` pair signed by the real `client_secret` without ever learning the secret. Replaying that request with a modified `shop` header requires no cryptographic work — the HMAC check in `hmac_validator.rb` is oblivious to the header change entirely by design of `to_signable_string`.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signed string, or otherwise cryptographically bind them to the payload before HMAC verification, so that the fields acted upon by `Registry.process`/`WebhookMetadata` are the same fields actually covered by the signature check in `Utils::HmacValidator`. At minimum, document prominently that `WebhookMetadata#shop` is NOT authenticated by the HMAC and must not be trusted for tenant resolution without an independent, out-of-band check (e.g., cross-referencing against a shop the app knows it registered a webhook for).

### Proof of Concept
1. Attacker creates `attacker-shop.myshopify.com`, installs the target app, and triggers a webhook (e.g., updates shop settings to fire `shop/update`).
2. Attacker's own endpoint (or intercepted logs, if the host app logs raw webhook deliveries) captures the exact `raw_body` and the `x-shopify-hmac-sha256` header Shopify sent — both valid per `HmacValidator.validate`.
3. Attacker POSTs this identical body and HMAC header to the victim app's webhook route, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` instead of their own domain.
4. `ShopifyAPI::Webhooks::Request.new` parses headers, `Registry.process` calls `Utils::HmacValidator.validate(request)` — which only recomputes over `@raw_body` — and it passes.
5. The handler executes with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own shop, achieving cross-tenant identity confusion in the host application.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
