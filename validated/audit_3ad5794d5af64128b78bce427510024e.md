### Title
Webhook `shop` field is not covered by the HMAC signature, allowing cross-tenant shop-identity spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, `api_version`, and `webhook_id` from unauthenticated HTTP headers, but `to_signable_string` (and thus the HMAC that `HmacValidator` verifies) covers only `@raw_body`. Because the app's `client_secret` (used as the HMAC key) is the same across every shop that installs the app, any actor able to obtain one valid `(body, hmac)` pair — e.g., from their own shop's legitimate webhook delivery — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a different (victim) shop. `Registry.process` will pass HMAC validation and dispatch the handler with `WebhookMetadata.shop` set to the attacker-chosen shop [3](#0-2) , even though the body content was never generated for that shop.

### Finding Description
`Utils::HmacValidator.validate` computes the signature strictly over `verifiable_query.to_signable_string` [4](#0-3) . For webhooks, `to_signable_string` returns only `@raw_body` [5](#0-4) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly, and unauthenticated, from HTTP headers [6](#0-5) . `Registry.process` only checks `Utils::HmacValidator.validate(request)` before trusting `request.shop` to build the `WebhookMetadata` passed to the app's handler [3](#0-2) .

This breaks the intended binding `verified(shop) == shop delivered to handler`: the HMAC only proves the request body was produced by a holder of the app's shared `client_secret` (i.e., Shopify itself, for any shop the app is installed on), not that the body belongs to the specific `shop` header value in that same request. The gem's own documentation instructs developers to treat `data.shop` as the authenticated shop identity of the webhook [7](#0-6) , and to rely on `Registry.process` to "verify the request did indeed come from Shopify" [1](#0-0)  — but it does not verify that the shop header matches the body that was HMAC-signed.

### Impact Explanation
Because the HMAC secret (`client_secret`) is identical for every shop using a given app installation, an attacker who legitimately controls one shop that has the app installed can capture a valid webhook body+HMAC for their own shop, then re-deliver it to the app's webhook endpoint with the `shop` header rewritten to a victim tenant's domain. Handlers that key persistence, authorization, or session lookups off `data.shop` (as the docs instruct) will process attacker-controlled webhook body content under the victim's tenant identity — a cross-tenant data-integrity issue matching the "shop authenticated versus shop used as session/tenant key" binding failure class.

### Likelihood Explanation
Requires the attacker to have legitimate access to at least one shop that has the target app installed (to obtain a valid signed body/HMAC pair), plus the ability to POST to the app's public webhook endpoint with custom headers. Both of these are within reach of an unprivileged actor who installs the app on their own store; no access token, `client_secret`, or privileged Shopify account is required.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the signable string used for the webhook HMAC, or otherwise cryptographically bind the shop domain to the signed payload before dispatching to handlers, so `Registry.process` can reject requests where the claimed shop does not match the one the body was signed for.

### Proof of Concept
1. App has installed on Shop A (attacker-controlled) and Shop B (victim), sharing one `client_secret`.
2. Attacker's own store triggers a webhook (e.g., `orders/create`); attacker captures `raw_body` and the `x-shopify-hmac-sha256` header from the legitimate delivery to Shop A's endpoint — this HMAC is valid because it's computed only over `raw_body` [5](#0-4) .
3. Attacker POSTs the same `raw_body` and `hmac` to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes since it only checks the body's HMAC [8](#0-7) .
5. The handler receives `WebhookMetadata` with `shop: "shop-b.myshopify.com"` and the attacker's body content, spoofing the tenant identity for Shop B.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
