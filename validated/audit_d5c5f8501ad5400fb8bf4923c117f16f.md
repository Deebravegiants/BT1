## Analog Found

### Title
Missing freeze-authority check on `coin_mint`/`pc_mint` in `Initialize2` lets a pool creator permanently freeze all LP funds - (File: `program/src/processor.rs`)

### Summary
`process_initialize2` explicitly rejects a pool whose LP mint has an active freeze authority, but it performs no equivalent check on the `coin_mint` or `pc_mint` supplied by the pool creator. Any unprivileged user can create an AMM pool with a mint they control (with `freeze_authority` set to themselves), let other users deposit/swap normally, and then call the standard SPL Token `FreezeAccount` instruction against the AMM's `coin_vault`/`pc_vault` ATA. Once frozen, every subsequent SPL Token `Transfer`/`Burn` CPI against that vault will fail, permanently blocking `Deposit`, `Withdraw`, and all four swap instructions for that pool and locking in all depositors' funds — the same "evil token locks user funds" bug class as the referenced OpenQ report, just realized via the SPL Token freeze-authority primitive instead of a custom malicious `transfer()` override.

### Finding Description
`Initialize2` unpacks and validates the coin/pc mints only for basic structural correctness: [1](#0-0) 

It then validates the vaults' `delegate`/`close_authority` are unset and checks the **LP mint's** `freeze_authority`: [2](#0-1) 

There is no analogous check that `coin_mint.freeze_authority` or `pc_mint.freeze_authority` is `COption::None`. Since `coin_mint`/`pc_mint` are attacker-supplied accounts (any two arbitrary mints, per the `Initialize2` account list) and the program only enforces `*amm_coin_mint_info.key != *amm_pc_mint_info.key` and that they are valid SPL mints owned by `spl_token_program_id`, an attacker can mint a token with themselves as `freeze_authority`, create a pool via `initialize2`, then after liquidity/deposits accumulate, submit a standard `FreezeAccount` instruction against `amm_coin_vault`/`amm_pc_vault` (the AMM-owned token accounts derived in `generate_amm_associated_spl_token`). Freezing a token account is a normal, unprivileged SPL Token operation available to any mint's `freeze_authority`, and it does not require the AMM authority PDA's signature — it only requires the mint's freeze authority to sign.

Once frozen, every `Invokers::token_transfer`/`token_transfer_with_authority`/`token_burn` call against that vault (used throughout `process_deposit`, `process_withdraw`, and all swap instructions) will fail at the SPL Token program level, since the token account state is frozen: [3](#0-2) [4](#0-3) 

This mirrors the reported bug class exactly: the protocol validates one side (LP mint) against a hazardous authority but omits the equivalent check on the funding/pool token mints, permitting a malicious/hostile mint to be locked into program-controlled state that later becomes permanently unusable.

### Impact Explanation
Freezing the vault(s) permanently locks all coin/pc tokens and LP-redeemable value held by every liquidity provider in that pool — `Withdraw` (LP burn against a frozen vault transfer), `Deposit`, and all four swap instructions become permanently unusable for that pool. This is a permanent freezing of user/LP funds with no on-chain recovery path (the freeze authority is external and the AMM program itself never re-checks or attempts to thaw the account), satisfying the Medium-severity "permanent freezing of user or LP funds" criterion.

### Likelihood Explanation
Likelihood is high for any user who is lured into providing liquidity or swapping into a permissionlessly created pool with an unaudited mint. Pool creation via `Initialize2` is fully unprivileged and reachable in a single transaction with attacker-chosen mint accounts; freezing the vault afterward is also a single, unprivileged transaction requiring only the attacker's own freeze-authority signature on the mint they created.

### Recommendation
In `process_initialize2`, add the same freeze-authority rejection applied to the LP mint to both `coin_mint` and `pc_mint`:
```rust
if coin_mint.freeze_authority.is_some() {
    return Err(AmmError::InvalidFreezeAuthority.into());
}
if pc_mint.freeze_authority.is_some() {
    return Err(AmmError::InvalidFreezeAuthority.into());
}
```
placed alongside the existing checks at [1](#0-0) , mirroring the check already performed for the LP mint at [5](#0-4) .

### Proof of Concept
1. Attacker creates an SPL mint `M` and sets `freeze_authority = attacker`.
2. Attacker mints initial coin/pc supply and calls `initialize2` to create an AMM pool using `M` as `coin_mint` (or `pc_mint`); this succeeds because `process_initialize2` never checks `coin_mint.freeze_authority`/`pc_mint.freeze_authority` (only the LP mint is checked, at [5](#0-4) ).
3. Other users deposit liquidity via `Deposit` and/or swap into the pool, increasing `amm_coin_vault`'s balance.
4. Attacker submits a standard `spl_token::instruction::freeze_account` instruction (signed by `attacker` as freeze authority) targeting `amm_coin_vault_info`, the AMM-owned token account created during initialization.
5. Any subsequent `Deposit`, `Withdraw`, or swap instruction that calls `Invokers::token_transfer`/`token_transfer_with_authority`/`token_burn` against `amm_coin_vault_info` (e.g. [4](#0-3) ) fails at the SPL Token program level because the account is frozen, permanently locking all depositors' coin/pc/LP value in the pool.
