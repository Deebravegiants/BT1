### Title
`force_socialize_bad_debt` skips the documented owner-only identity check, letting any unprivileged address trigger bad-debt cleanup that seizes an account's remaining collateral - (File: contracts/controller/src/positions/liquidation/mod.rs)

### Summary
The bug class in the external report is an authorization gate that performs an authentication step but never binds it to the required identity (a guest JWT passes `authJwt.verify` and reaches the admin surface). The direct analog exists in `contracts/controller/src/positions/liquidation/mod.rs`: `socialize_bad_debt` supports two admission gates, `BadDebtGate::DustCapped` (permissionless) and `BadDebtGate::InsolventOnly`, which is documented as "Owner-only" — but `process_force_socialize_bad_debt`, the entrypoint that selects `InsolventOnly`, performs no `require_auth` and no `require_owner_or_delegate` on the target account at all. The gate that is supposed to enforce *who* may invoke it is silently absent, so the stronger cleanup mode is as permissionless as the weaker one.

### Finding Description
- `process_force_socialize_bad_debt(env, account_id)` only calls `validation::require_not_flash_loaning(env)` before delegating to `socialize_bad_debt(env, account_id, BadDebtGate::InsolventOnly)` (mod.rs:246–249). No `require_auth`, `require_account_owner`, or `require_owner_or_delegate` appears anywhere on this path.
- `socialize_bad_debt` then only checks that borrow positions exist and that `totals.total_debt > totals.total_collateral`, then runs `bad_debt::execute_bad_debt_cleanup` (mod.rs:212–238).
- The enum itself documents the intended split: `DustCapped` is "Permissionless" while `InsolventOnly` is "Owner-only: insolvent alone, with no cap on the collateral left behind" (mod.rs:204–209). The sibling entrypoint `process_clean_bad_debt` correctly performs `caller.require_auth()` before the dust-capped gate (mod.rs:196–200); the owner-only variant performs less authentication than the permissionless one.
- By contrast, every other entrypoint that consumes or destroys a user's position binds the authorized address to the account owner: `process_withdraw` calls `require_owner_or_delegate` before paying out (supply.rs:150), `process_borrow` does the same (debt.rs:43), and `resolve_seize_receiver` binds the credit receiver to the liquidator's own accounts (mod.rs:180). `process_force_socialize_bad_debt` is the only destructive, non-permissionless-gated path with no identity binding — exactly the "authentication without identity inspection" shape of CVE-2026-67443.

### Impact Explanation
An unprivileged address can call `force_socialize_bad_debt(account_id)` on any account whose total debt exceeds total collateral, regardless of how much collateral remains. The dust cap exists precisely to limit permissionless cleanup to accounts whose residual collateral is economically negligible; the owner-only mode intentionally allows an owner to clean up earlier while retaining the right to decide when their remaining collateral is written off. Because the owner check is missing, an attacker can force cleanup on an insolvent account that still holds above-dust collateral — destroying/socializing positions that the owner intended to unwind themselves or that would have been worth more through an ordinary liquidation (which pays the owner-side residual differently and is bounded by the liquidation plan). This is a permanent loss of the account's remaining collateral value, inflicted by a caller with no relationship to the account, and it is reachable via a single controller call with only `account_id` as an argument.

### Likelihood Explanation
Triggering requires only an account that is insolvent (`total_debt > total_collateral`) but whose collateral exceeds the dust threshold — a normal transient state for underwater accounts before liquidation completes. The attacker needs no privileges, no delegation, no NFT ownership, and no funds beyond the transaction fee; the single argument is a `u64` account id, and `require_not_flash_loaning` is satisfied outside any flash callback. The primary uncertainty is the exact destination of the seized collateral inside `execute_bad_debt_cleanup` (whether it is written down via supply index, seized outright, or partially returned), which determines whether the loss lands on the account owner, suppliers, or both — but in all cases value that the owner-only gate was designed to protect is consumed without the owner's consent.

### Recommendation
Authenticate the account owner inside the `InsolventOnly` gate: either have `process_force_socialize_bad_debt` take a `caller: Address` and require `require_account_owner(env, account_id, &caller)` after `caller.require_auth()` (mirroring `set_account_delegate` in `contracts/controller/src/account.rs:249–250`), or fold the identity check into `socialize_bad_debt` so `BadDebtGate::InsolventOnly` asserts `account.owner == caller` in addition to insolvency. Also add `process_force_socialize_bad_debt` to `scripts/permissionless_entrypoints.txt` review and extend `check_access_control.py`'s `ACCOUNT_OWNER_PATTERNS` coverage expectations so an owner-only-gate entrypoint that reaches `get_account` but never `require_account_owner`/`require_owner_or_delegate` fails the static gate.

### Proof of Concept
1. Attacker (fresh address, no NFT, no delegation) observes account `A` where `total_debt > total_collateral` but collateral is above the dust threshold — e.g., a position just crossed below 100% collateralization after a price move, before any liquidator acts.
2. Attacker calls `controller.force_socialize_bad_debt(A)`.
3. `process_force_socialize_bad_debt` passes the flash guard, `socialize_bad_debt` sees `borrow_positions` non-empty and `total_debt > total_collateral` (`InsolventOnly` admits), and `execute_bad_debt_cleanup` runs — with no `require_auth` anywhere on the path and no comparison of any caller identity against `account.owner` (mod.rs:246–249, 212–238).
4. `A`'s remaining collateral is consumed by the cleanup and its debt is written down, a transition the code documents as owner-only but enforces for no one.
