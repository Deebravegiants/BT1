### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`RubiconMarket`'s bug class is: a state/identity field (`_rank`/`_best`) is used by downstream logic (`isOfferSorted`, `_unsort`, `_hide`) without having been consistently established for all code paths, breaking an invariant the protocol relies on. The closest analog in this gem is a broken identity binding in inbound webhook processing: `ShopifyAPI::Webhooks::Request` verifies only the raw request body against the app's shared HMAC secret, but the `shop` field — which downstream `WebhookHandler` implementations use to scope actions to a specific merchant/tenant — is taken verbatim from an unauthenticated HTTP header and is never included in the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e., the body only) using the app-wide `Context.api_secret_key`, which is identical for every shop that has installed the app: [3](#0-2) 

`Registry.process` only checks this body HMAC before dispatching to the handler with the attacker-controlled `shop`: [4](#0-3) [5](#0-4) 

The invariant that should hold is: `signed_bytes == bytes_the_handler_trusts_for_tenant_identity`. Here, `signed_bytes = raw_body` while `bytes_the_handler_trusts_for_tenant_identity = shop header`, and these are disjoint — the equality is broken.

### Impact Explanation
Because the HMAC secret (`api_secret_key`) is the same across all shops that install a given app, any unprivileged merchant who installs the app on their own store receives genuinely-signed webhooks (valid `x-shopify-hmac-sha256` over the body) for their own shop. That merchant can replay the identical raw body/HMAC pair to the app's webhook endpoint while substituting an arbitrary value in the `x-shopify-shop-domain` header. `Utils::HmacValidator.validate` will still pass (it never inspects the shop header), and `WebhookMetadata.shop` handed to the handler will be the forged value. Any host application logic that uses `data.shop` to look up a session/tenant and act on its behalf (e.g., re-fetch data, write to that shop's records, trigger side effects scoped by shop) can be tricked into acting under a different tenant's identity — a cross-tenant confusion condition rooted entirely in this gem's webhook verification code.

### Likelihood Explanation
Exploitation only requires installing the target app on an attacker-controlled shop (a normal, unprivileged action available to any merchant) and replaying one legitimately-received webhook with a modified header — no access to the app's `client_secret`, no privileged account, and no bypass of TLS is required. The vulnerable code path (`Registry.process` → `HmacValidator.validate` → handler) is on the primary, documented webhook-processing flow of the gem.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the HMAC-signed material, or otherwise cryptographically bind `Request#shop` to the verified payload before it is trusted. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must never be used as the sole tenant-identity input without cross-checking it against the shop associated with the specific webhook subscription/session store.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, triggering a legitimate webhook (e.g., `orders/create`) signed with the app's shared `api_secret_key`.
2. Attacker captures the raw body and the `x-shopify-hmac-sha256` header from this legitimate delivery.
3. Attacker POSTs this exact `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint again, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` — it succeeds because the body/HMAC pair is unchanged and the secret is shared across shops.
5. The registered `WebhookHandler#handle` is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing any tenant-scoped logic in the handler to operate as if the (attacker-controlled) payload belongs to `victim-shop.myshopify.com`.
