### Title
Webhook `shop` identity field is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, while the `shop` (tenant) identity used by `ShopifyAPI::Webhooks::Registry.process` to dispatch webhook data is read from an HTTP header that is never included in the signed bytes. Any entity capable of sending a request with a valid `(raw_body, hmac)` pair — i.e., any merchant who has legitimately installed the app and thus regularly receives real, validly-signed webhooks to their own endpoint — can resend that exact `(raw_body, hmac)` pair while substituting the `shop-domain` header to name a different tenant, and the app will process the payload as though it belongs to that other shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`hmac` is likewise derived only from the `hmac-sha256`/`x-shopify-hmac-sha256` header, decoded and hex-encoded, with no dependency on `shop`, `topic`, or `webhook-id`: [2](#0-1) 

The `shop` accessor is read straight from the `shop-domain`/`x-shopify-shop-domain` header, entirely independent of the signed content: [3](#0-2) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)`, which in turn calls `to_signable_string` (i.e. verifies only the body) and then, once that single check passes, forwards `request.shop` — the unauthenticated header value — directly to the app's handler as the tenant identity for that webhook: [4](#0-3) 

`Utils::HmacValidator.validate` / `validate_signature` calls `verifiable_query.to_signable_string` to compute the expected signature and only compares that against the provided `hmac`: [5](#0-4) 

The identity binding that the gem is supposed to enforce is:
`bytes covered by HMAC == bytes the app relies on to attribute the webhook to a tenant (shop)`

Because `shop` is excluded from `to_signable_string`, this equality does not hold: the HMAC only proves the *body* came from Shopify using the app's shared `client_secret`; it proves nothing about which shop the body belongs to. Since a single app's `client_secret` is shared across every shop that installs the app, any one merchant who receives a legitimate webhook (with a fixed, valid `raw_body`/`hmac` pair for a given topic) can replay that identical body+hmac to the app's webhook endpoint while swapping only the `shop-domain` header to a victim shop's domain. `Registry.process` will accept the request (HMAC check passes because the body is unchanged) and hand the handler `WebhookMetadata` stamped with the attacker-chosen `shop`, causing the app to process/store data under the wrong tenant.

### Impact Explanation
This breaks tenant isolation: an unprivileged merchant who has this app installed (and thus legitimately receives its own signed webhooks) can forge webhook deliveries "as" any other shop by replaying a valid `(body, hmac)` pair with a spoofed `shop-domain` header. Depending on how the host application uses `data.shop` in its `WebhookHandler#handle` (e.g., looking up the merchant record, applying the payload to shop-scoped state), this enables cross-tenant data corruption/impersonation — the app cannot distinguish "signed by our secret" from "signed by our secret *for shop X*" because the gem never binds `shop` into the signature check.

### Likelihood Explanation
Exploitation only requires being one of the app's own merchants (unprivileged in relation to other tenants) — no access token, `client_secret`, or credential leakage is needed. The attacker simply needs one legitimately received webhook body/HMAC (which every installed shop receives regularly) and standard HTTP tooling to replay it with a different `shop-domain` header value to the app's public webhook callback route.

### Recommendation
Bind the `shop` (and ideally `topic`) into the value that is HMAC-verified, or otherwise cryptographically/contextually confirm that the `shop-domain` header matches the tenant the app expects for that webhook subscription (e.g., cross-check against the shop for which the webhook was registered) before dispatching `WebhookMetadata` to handlers. At minimum, document to consuming apps that `data.shop` is unauthenticated and must not be trusted for tenant attribution without independent verification — though the safer fix is on the gem side, making `to_signable_string`/HMAC validation shop-aware.

### Proof of Concept
1. App `A` is installed on `shop1.myshopify.com` and `shop2.myshopify.com`, sharing the same `client_secret`.
2. The merchant controlling `shop1` intercepts a legitimate webhook POST to their own endpoint: body `B`, header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(client_secret, B)`), and `x-shopify-shop-domain: shop1.myshopify.com`.
3. The merchant resends the identical request to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `shop2.myshopify.com`. `H` is still a valid HMAC of `B` since the signable string is only `B`:
```ruby
req = ShopifyAPI::Webhooks::Request.new(
  raw_body: B,
  headers: {
    "x-shopify-topic" => "orders/create",
    "x-shopify-hmac-sha256" => H,          # unchanged, still valid for body B
    "x-shopify-shop-domain" => "shop2.myshopify.com", # spoofed
  },
)
ShopifyAPI::Webhooks::Registry.process(req) # passes HMAC check, handler invoked with shop: "shop2.myshopify.com"
```
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) passes HMAC validation (body unchanged) and invokes the registered handler with `WebhookMetadata` claiming `shop2.myshopify.com`, even though the request never originated from Shopify for `shop2`.
