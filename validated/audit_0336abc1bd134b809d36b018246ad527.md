### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook shop-spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats an incoming webhook as authenticated ("did indeed come from Shopify") once `Utils::HmacValidator.validate` succeeds, and then dispatches the handler with the `shop` value taken directly from the `X-Shopify-Shop-Domain` header. That header is never included in the HMAC computation, so the byte range verified by the signature and the value trusted for tenant attribution are not the same data — breaking the identity binding `hmac(bytes) == valid` ⟹ `shop(header) == authenticated_shop`.

### Finding Description
`Request#to_signable_string` returns only the raw request body: [1](#0-0) 

and `shop` is read straight from an HTTP header, entirely outside the signed payload: [2](#0-1) 

`HmacValidator.validate_signature` computes and compares the HMAC only over `to_signable_string` (the body), never over the headers: [3](#0-2) 

`Registry.process` uses this HMAC check as proof the request "did indeed come from Shopify" (per the gem's own docs) and then forwards the unauthenticated `request.shop` value to the app's handler as the identity of the tenant the payload belongs to: [4](#0-3) 

The gem's documentation reinforces that `Registry.process` is expected to fully authenticate the webhook before invoking the handler, and instructs apps to trust `data.shop` as the shop the webhook is for: [5](#0-4) [6](#0-5) 

Because the HMAC secret (`api_secret_key`) is a single per-app secret shared across every shop that installs the app — not a per-shop secret — any shop that legitimately receives a webhook obtains a body+HMAC pair that is valid for that app regardless of which shop it names. An attacker who has installed the app on their own shop can capture a legitimate `(raw_body, hmac)` pair generated for their own store, then replay it to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still returns `true` because it only checks the untouched body bytes, and `Registry.process` passes the attacker-chosen `shop` string straight into `WebhookMetadata`, which the app then uses to route/store per-tenant data.

### Impact Explanation
This lets an unprivileged attacker (any merchant/user capable of installing the app once) forge webhook deliveries that appear to be scoped to an arbitrary victim shop of their choosing, without ever having the app's `api_secret_key` or the victim's access token. Since apps built on this gem key their persistence/workflows on `data.shop` (as directed by the gem's documented handler contract), this enables cross-tenant data injection/confusion (e.g., attacker's order/customer data or actions being attributed to and applied against a different merchant's tenant state).

### Likelihood Explanation
Requires only: (1) the attacker be able to install the target app on a shop they control (the normal, unprivileged path for any Shopify merchant), (2) trigger any registered webhook topic on their own shop, and (3) resend the captured HTTP request to the app's public webhook endpoint with one header field altered. No secrets, tokens, or privileged access are required — this is exploitable entirely from the unauthenticated network path that the webhook endpoint necessarily exposes.

### Recommendation
Bind the shop identity into the value that is HMAC-verified. Either include the shop domain (and other identity-relevant headers) in the signable string used for verification, or independently verify that `request.shop` corresponds to a shop for which the app has an active, previously-established installation/session before trusting it — and document that `Registry.process` only authenticates body integrity, not header-asserted shop identity, so integrators are not misled by the current docs' phrasing ("This will verify the request did indeed come from Shopify").

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" with the app installed.
# Shopify sends a legitimate webhook to the app for a real event on attacker's shop:
raw_body = '{"id":1,"note":"legit order on attacker shop"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_secret, raw_body)
encoded_hmac = Base64.encode64(hmac)

# Attacker captures this (raw_body, encoded_hmac) pair, then replays it to the
# same webhook endpoint but swaps the shop-domain header to the victim's shop:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => encoded_hmac,       # unchanged, still valid for raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (body untouched),
#    handler.handle receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
#    even though this event never occurred on victim-shop.
```

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
