### Title
Deposit slippage control (`other_amount_min`) bounds asset ratio, not LP shares minted (`mint_lp_amount`) - (File: program/src/processor.rs)

### Summary
`process_deposit` lets a depositor bound the ratio between `max_coin_amount`/`max_pc_amount` and, optionally, `other_amount_min`, but never lets the depositor specify a minimum acceptable amount of LP tokens (`mint_lp_amount`) to receive. This mirrors the reported ERC5095 `mint()` bug class: slippage control is expressed in terms of the input/other **assets** rather than the actual **shares** (LP tokens) the caller receives.

### Finding Description
In `Processor::process_deposit` (`program/src/processor.rs`), the deposit's only user-suppliable slippage guards are `deposit.max_coin_amount`, `deposit.max_pc_amount`, and the optional `deposit.other_amount_min` field of `DepositInstruction` [1](#0-0) . These fields only bound the coin/pc exchange ratio used to compute `deduct_coin_amount`/`deduct_pc_amount` [4](#0-3) .

The actual output the depositor receives — `mint_lp_amount`, computed as `deduct_coin_amount / total_coin_without_take_pnl * amm.lp_amount` (or the pc-side equivalent) and then minted directly to the user's LP token account [2](#0-1) [3](#0-2)  — has no corresponding minimum check anywhere in the function. `total_coin_without_take_pnl`/`amm.lp_amount` (i.e., the pool's "price per share") can change between transaction submission and execution — e.g., due to a swap or `WithdrawPnl` sandwiched immediately before the deposit, or direct token transfers into the AMM's SPL vaults ("donation") that inflate `total_coin_without_take_pnl` relative to `amm.lp_amount` — none of which is bounded by `other_amount_min`, since that field only checks the ratio between the two deposited assets, not the coin/lp-share ratio.

### Impact Explanation
A depositor can receive materially fewer LP tokens than expected for the exact same `deduct_coin_amount`/`deduct_pc_amount` they authorized, while every existing on-chain check (`max_coin_amount`, `max_pc_amount`, `other_amount_min`) still passes. Combined with floor rounding in `exchange_token_to_pool`, this enables a classic share-price inflation/dilution pattern where an attacker manipulates `total_coin_without_take_pnl` vs `amm.lp_amount` right before a victim's deposit lands, causing the victim to under-mint LP tokens for their deposited assets — a direct loss of LP value to the victim and a transfer of pool value to other/attacking LPs.

### Likelihood Explanation
This requires only ordinary permissionless actions reachable from a single attacker-controlled transaction: submitting a swap, or `WithdrawPnl`, or a plain SPL token transfer into the (publicly writable) coin/pc vault accounts, immediately ahead of a pending `Deposit` transaction in the same slot/block. No privileged signer or off-chain component is needed, and the `Deposit` instruction itself provides no field to protect against it.

### Recommendation
Add an explicit `min_lp_amount` (or equivalent) parameter to `DepositInstruction`/`process_deposit`, and enforce `mint_lp_amount >= min_lp_amount` (returning `AmmError::ExceededSlippage` otherwise) before minting, so slippage protection is expressed in terms of the shares actually received rather than only the deposited-asset ratio.

### Proof of Concept
1. Pool has `amm.lp_amount = L`, `total_coin_without_take_pnl = C`, so price-per-LP-share (coin side) is `C/L`.
2. Victim submits `Deposit { max_coin_amount = A, max_pc_amount = A * pc/coin_ratio, base_side = 0, other_amount_min = expected_pc }`, expecting `mint_lp_amount ≈ A/C * L`.
3. Attacker, in a preceding transaction in the same block, transfers additional coin and pc tokens directly into `amm_coin_vault`/`amm_pc_vault` (or executes a swap immediately reversed) keeping the coin/pc *ratio* roughly unchanged but increasing `total_coin_without_take_pnl` to `C' > C` without changing `amm.lp_amount`.
4. Victim's deposit still satisfies `deduct_pc_amount <= max_pc_amount` and `deduct_pc_amount >= other_amount_min` because the ratio is unchanged, so no `ExceededSlippage` error is raised at `program/src/processor.rs:1206-1222` or `:1275-1292`.
5. `mint_lp_amount` is now computed as `A/C' * L < A/C * L` at `program/src/processor.rs:1243-1250`, so the victim mints fewer LP tokens than expected for the same deposited assets, with no on-chain check to prevent or detect this.
