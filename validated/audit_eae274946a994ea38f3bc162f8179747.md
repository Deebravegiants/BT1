### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify" before handing the webhook's `shop` field to the app's handler. In reality, the HMAC only signs the raw request body; the `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are never included in the signed material. An attacker who owns any legitimate Shopify store can capture a genuinely-signed webhook and replay it to a victim app's webhook endpoint with a forged `shop-domain` header, and the signature will still validate.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are read directly from unauthenticated HTTP headers: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC solely against `to_signable_string`, i.e. the body, ignoring headers entirely: [3](#0-2) 

`Registry.process` uses this "verified" request to build `WebhookMetadata` and dispatch it to the app's handler, trusting `request.shop` as if it were authenticated: [4](#0-3) 

The identity binding that should hold is:
`shop value covered by the HMAC signature == shop value delivered to the app handler`

In this implementation the equality is broken: the HMAC covers only the body bytes, while the `shop` (and topic/webhook_id/api_version) delivered to the handler come from an entirely separate, unsigned channel (headers). Any attacker who can obtain one genuine `(body, hmac)` pair for their own store — trivial, since anyone can create a free Shopify development store and register a webhook for their own app instance — can replay that exact body+hmac to a different app's webhook endpoint with a different `x-shopify-shop-domain` header. The signature check still passes because it never inspected the header, and `Registry.process` forwards the forged shop value into `WebhookMetadata#shop`.

This directly contradicts the gem's own documentation, which states that `Registry.process` "will verify the request did indeed come from Shopify" and that `data.shop` is "The shop domain of the webhook": [5](#0-4) [6](#0-5) 

### Impact Explanation
Applications built on this gem key their handler logic on `data.shop` (as the documentation itself recommends: `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) after `Registry.process` reports the request as verified. Because `shop` is not bound to the HMAC, an attacker can make the app believe attacker-controlled webhook content originated from an arbitrary victim shop domain, leading to cross-tenant data confusion: fake `orders/create`, `customers/redact`, `app/uninstalled`, etc. events can be injected into another merchant's data pipeline, tenant-scoped caches, or business processes. This matches the "cross-tenant access" Critical impact category, since it lets one tenant's authenticated channel be used to inject data attributed to a different tenant.

### Likelihood Explanation
No merchant credentials, access tokens, or `client_secret` are needed. An attacker only needs their own (or a trial/free) Shopify store with the target app installed to legitimately trigger and capture one signed webhook, then replay the unmodified body+HMAC to the target endpoint with a substituted `shop-domain` header. This is fully unprivileged with respect to the victim tenant and requires no interaction with Shopify's TLS channel — the request is a fresh HTTP POST from the attacker directly to the app's public webhook URL.

### Recommendation
Bind the `shop`, `topic`, `webhook_id`, and `api_version` values into the material verified by `Utils::HmacValidator`, or otherwise cryptographically tie the header values to the signed payload (e.g., include them in `to_signable_string`, or require the host app to cross-check the header shop domain against the shop stored for the resource ids present in the body). At minimum, update `docs/usage/webhooks.md` to stop asserting that `Registry.process` fully verifies "the request did indeed come from Shopify" including its `shop` field, since only the body is covered.

### Proof of Concept
1. Attacker installs the target app on their own Shopify store `attacker-shop.myshopify.com` and registers for a webhook topic (e.g., `orders/create`).
2. Shopify sends a webhook to the app: body `B`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`, header `x-shopify-hmac-sha256: H` where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker resends an HTTP POST to the same public webhook endpoint with the identical body `B` and identical `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which recomputes HMAC over `to_signable_string` (== `B`) and matches `H` — validation succeeds: [7](#0-6) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and body `B`, despite the request never having been produced or endorsed by Shopify for that shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
```
