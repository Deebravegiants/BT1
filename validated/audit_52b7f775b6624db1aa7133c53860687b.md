## Analysis

The reported native-contract-panic bug class ("value trusted after a check doesn't actually verify what it's used for") maps to an HMAC/identity-binding gap in this gem's webhook processing path.

### Root cause

`ShopifyAPI::Webhooks::Request#to_signable_string` returns **only the raw HTTP body**: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes/compares the HMAC exclusively against that signable string: [2](#0-1) 

Yet `Registry.process` treats a successful HMAC check as authorization to trust the entire `Request`, including the `shop` attribute, and hands it straight to the app's handler: [3](#0-2) 

`request.shop` is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is **not** part of `to_signable_string` and therefore never covered by the signature: [4](#0-3) 

### The broken identity binding

`HmacValidator.validate(request) == true` should mean "this exact (body, shop) pair genuinely came from Shopify for this shop," but it actually only proves "this body was signed with the app's shared `api_secret_key`." The shared secret (the app's `client_secret`) is identical across every shop that installs the app — it is not shop-specific. So:

- Equality assumed by `Registry.process`: `shop delivered to handler == shop that produced this signature`
- Equality actually enforced: `hmac(raw_body, api_secret_key) == received_hmac` (shop-independent)

An unprivileged user who installs the app on their own shop receives legitimately-signed webhook deliveries (valid `raw_body` + `hmac` for their shop). Because the shop header sits outside the signed content, they can replay the exact same `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting a different `shopify-shop-domain` header value naming a victim shop. `HmacValidator.validate` still returns `true` (the body/secret pair is valid), and `Registry.process` passes the forged `shop` straight into `WebhookMetadata`, which the host application uses to key data updates/deletions (e.g. `app/uninstalled`, `shop/redact`, `customers/data_request`, subscription state, etc.).

### Impact

Cross-tenant impersonation of webhook events: an attacker with any installation of the app (even a free/trial one) can produce webhook payloads that a downstream `ShopifyAPI::Webhooks::Registry` handler will treat as authentic events for a shop they don't control, because this gem exposes an unauthenticated field (`shop`) as if it were covered by the HMAC guarantee it just performed.

### Recommendation

`ShopifyAPI::Webhooks::Request#to_signable_string` (or `HmacValidator`) should bind the shop domain (and/or webhook id/topic) into the value being verified, or `Registry.process`/`WebhookMetadata` should independently verify that `request.shop` corresponds to a shop session/installation known to the app before dispatching to the handler, rather than implicitly treating a body-only HMAC pass as validating the shop header.

### Title
Webhook `shop` header trusted as HMAC-verified though it is excluded from the signed payload, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/utils/hmac_validator.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` gates webhook processing on `Utils::HmacValidator.validate(request)`, but the HMAC only covers `raw_body` (`Request#to_signable_string`), never the `shopify-shop-domain` header exposed via `Request#shop`. Since the HMAC secret (`Context.api_secret_key`) is shared across all shops that install the app, any installer can capture a legitimately-signed webhook and replay it with a forged shop header, passing validation while impersonating another tenant.

### Finding Description
See root cause analysis above: `to_signable_string` = raw body only [1](#0-0) , `shop` sourced from an unsigned header [4](#0-3) , and `Registry.process` dispatching to handlers immediately after the HMAC check succeeds without any further shop verification [3](#0-2) .

### Impact Explanation
Cross-tenant access: a downstream application relying on `WebhookMetadata#shop` (populated straight from the unauthenticated header) to identify which merchant a webhook pertains to can be tricked into acting on another shop's behalf using a replayed, re-labeled payload.

### Likelihood Explanation
Requires only that the attacker be an app installer (any Shopify merchant can install a public app) capable of sending arbitrary HTTP requests to the app's public webhook endpoint with a captured, previously-valid `raw_body`/`hmac-sha256` pair and a forged `shop-domain` header — no privileged credentials or the app's `client_secret` needed.

### Recommendation
Bind the shop domain (and ideally webhook id/topic) into the HMAC-covered content, or have `Registry.process`/the consuming app cross-check `request.shop` against a known/expected installation before trusting it, rather than relying solely on the body-only HMAC result.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`; app registers a webhook (e.g. `orders/create`).
2. Shopify delivers a webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid hmac of raw_body>`, and some `raw_body`.
3. Attacker captures `raw_body` and `hmac-sha256` value.
4. Attacker sends a new HTTP POST to the same endpoint with the identical `raw_body`/`hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `raw_body` — validation succeeds.
6. The handler receives `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` and performs whatever shop-scoped action the host app implements, attributing attacker-controlled data to the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
