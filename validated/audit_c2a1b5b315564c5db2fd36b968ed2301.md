### Title
Stranded/residual token balances in `ExternalActionSwap`/`LifiExternalAction` can be drained by any caller via attacker-controlled router call data - (File: `contracts/external-actions/swaps/ExternalActionSwap.sol`, `contracts/external-actions/swaps/LifiExternalAction.sol`)

### Summary
`ExternalActionSwap.swap` computes the amount forwarded to the caller (`amountToSendToHinkal`) purely from the *output-token balance delta* observed around an attacker-supplied `externalActionMetadata` call to `router`, and never verifies that the `inputAmount` transferred to it that same transaction was fully consumed. Combined with `approveUnlimited(inputToken, router)` in `LifiExternalAction.callRouter`, this lets any unprivileged caller direct the router to pull more input tokens than `-deltaAmountChanges` for that transaction (e.g. leaving unconsumed input-token dust behind on a prior call, or, symmetrically, sweeping a pre-existing/stranded balance on a later call) and package the extra output as their own UTXO.

### Finding Description
The invariant that should hold is: *tokens leaving the external action contract in transaction T == `-deltaAmountChanges` Hinkal transferred to it in T*. This is violated because `swap()`'s accounting is balance-diff based and untethered from `inputAmount`:

```solidity
// contracts/external-actions/swaps/ExternalActionSwap.sol
address inputToken = circomData.erc20TokenAddresses[0];
uint256 inputAmount = uint256(-deltaAmounts[0]);
...
uint256 swappedAmount = callRouter(inputToken, inputAmount, outputToken, circomData.externalActionData.externalActionMetadata);
...
uint256 amountToSendToHinkal = swappedAmount - totalFee;
transferERC20TokenOrETH(outputToken, msg.sender, amountToSendToHinkal);
utxoSet[0] = UTXO({ amount: amountToSendToHinkal, erc20Address: outputToken, ... });
``` [1](#0-0) [2](#0-1) 

`callRouter` never checks that `inputAmount` of `inputToken` was consumed by the router; it only measures the *output* token's balance change, and it grants the router an unlimited allowance over the whole contract's `inputToken` balance, not just the amount just transferred in:
```solidity
approveUnlimited(inputToken, router);
(bool success, ) = router.call(externalActionMetadata);
...
swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
``` [3](#0-2) 

Because `externalActionMetadata` is 100% attacker-controlled (it is passed through raw from `circomData.externalActionData.externalActionMetadata`, only checked for proof validity of the attacker's own circuit inputs, never validated on-chain against `inputAmount`), the attacker can craft a router call that intentionally consumes less than `inputAmount` of `inputToken`, leaving a residual balance parked in the shared `LifiExternalAction` contract (this contract is not per-transaction isolated - it persists state/balances across all users' calls). Nothing in `swap()` verifies the leftover `inputToken` balance returns to zero, and no UTXO or refund is created for it, so this leftover silently becomes an unaccounted, un-owned balance sitting in the action contract.

In a subsequent transaction (same or different unprivileged attacker), the attacker calls `Hinkal.transact` again with `erc20TokenAddresses[0] = inputToken` (matching the stranded token) and crafts `externalActionMetadata` so the router pulls (via the pre-existing unlimited allowance) both the fresh `inputAmount` for this tx *and* the stranded residual. `swappedAmount` (measured only via output-token balance diff) is therefore inflated by exactly the stranded amount, and the whole inflated `amountToSendToHinkal` is transferred to `msg.sender` (Hinkal) and packaged into `utxoSet[0]`, whose `stealthAddressStructure` is fully attacker-chosen (`circomData.stealthAddressStructure`).

`Hinkal.transact`'s balance-diff/equality check does not catch this because the check only verifies Hinkal's own balance change matches `amountChanges[i] + utxoAmount` for the *output* token, and both sides move together: the entire inflated amount arrives at Hinkal and is entirely represented by the single UTXO the attacker creates (`utxoAmount = amountToSendToHinkal`) with `amountChanges[1] = 0`. Nothing in `_externalTransact`/`transact` cross-checks that the output amount is proportional to what was actually sent to the action for that specific transaction versus a residual accumulated over multiple transactions:
```solidity
for (uint64 i; i < circomData.erc20TokenAddresses.length; i++) {
    ...
    require(balanceDif == (circomData.onChainCreation[i] ? int256(0) : circomData.amountChanges[i]) + int256(utxoAmount), ...);
}
``` [4](#0-3) 

### Impact Explanation
Any unprivileged attacker can extract stranded/residual token balances from the shared `ExternalActionSwap`/`LifiExternalAction` contract and claim them as their own shielded UTXO, i.e. direct theft of in-flight/protocol-parked funds that were never backed by that transaction's `-deltaAmountChanges`. This is repeatable: any time a leftover balance exists in the action contract (self-seeded by the attacker in a prior call, or accumulated from any other source such as router dust/refunds), the next call can sweep it. This matches the Critical category "direct theft of shielded or in-flight user funds."

### Likelihood Explanation
The attacker needs only: (1) the ability to call `Hinkal.transact` with their own valid proof/UTXOs (fully permitted for an unprivileged user), and (2) full control of `externalActionMetadata`, which is already an explicit attacker-controlled field per the threat model. Seeding a residual costs the attacker only gas and the ability to craft a router call that leaves funds behind (feasible against a real or mock LI.FI router, e.g. a partial-fill call), and reclaiming it is a normal `swap()` call. No privileged role or race condition is required, making this highly likely to be exploitable in practice.

### Recommendation
Track and enforce exact consumption of `inputAmount` in `callRouter`/`swap`: require `getERC20OrETHBalance(inputToken)` returns to (pre-call balance − inputAmount) after the router call, refund any leftover input token back to `msg.sender` (Hinkal) as part of the returned `utxoSet` instead of leaving it in the contract, and replace `approveUnlimited` with an approval scoped exactly to `inputAmount` for that call.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `LifiExternalAction` (with a mock LI.FI router), register the action.
2. Tx1 (attacker A): call `transact` with `erc20TokenAddresses=[tokenX, tokenY]`, valid proof/UTXOs such that `deltaAmountChanges[0] = -1000`. Craft `externalActionMetadata` so mock router only pulls `900` of `tokenX` via `transferFrom`, leaving `100` `tokenX` stuck in `LifiExternalAction`. Assert `tokenX.balanceOf(LifiExternalAction) == 100` after Tx1.
3. Tx2 (attacker A or B): call `transact` with `erc20TokenAddresses=[tokenX, tokenZ]`, `deltaAmountChanges[0] = -500`. Craft `externalActionMetadata` so mock router pulls `600` (`500` fresh + `100` residual) of `tokenX`, returning proportional `tokenZ`. Assert `utxoSet[0].amount` (and thus the attacker's claimable output UTXO) reflects the `600`-input swap output rather than the `500` legitimately funded that transaction, and assert `tokenX.balanceOf(LifiExternalAction) == 0` (residual fully drained) while `circomData.amountChanges` for Tx2 only accounted for `500`.
4. Equality to assert broken: tokens leaving the action in Tx2 (`600` `tokenX` pulled by router) != `-deltaAmountChanges` Hinkal sent the action in Tx2 (`500`).

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
