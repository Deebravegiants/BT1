## Title
Webhook `shop` (and `topic`/`api-version`/`webhook-id`) headers are trusted for tenant identification but are not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates incoming webhooks by validating an HMAC that is computed over the raw request body only, yet the `shop` (and `topic`, `webhook_id`, `api_version`) values used to route and attribute the webhook to a tenant are taken from unauthenticated HTTP headers that the signature never covers.

### Finding Description
`Utils::HmacValidator.validate` computes the signature strictly from `verifiable_query.to_signable_string`: [1](#0-0) 

For a webhook `Request`, `to_signable_string` is defined to be just the raw HTTP body: [2](#0-1) 

But the `shop`, `topic`, `webhook_id`, and `api_version` accessors used by `Registry.process` to identify and route the event are all pulled from separate HTTP headers that play no part in the signed material: [3](#0-2) 

`Registry.process` validates only the HMAC, then hands the header-derived, unauthenticated `shop`/`topic`/`webhook_id` straight to the app-registered handler as `WebhookMetadata`: [4](#0-3) 

This is precisely the "field acted on but not covered by the HMAC" pattern: `Utils::HmacValidator.validate(request) == true` only proves `raw_body` bytes are authentic; it proves nothing about `shop`, `topic`, or `webhook_id`, yet the library treats a successful `validate` call as license to hand all four values, including `shop`, to the handler as trustworthy tenant-identifying metadata.

An attacker who controls any shop that has the target app installed (a normal, unprivileged merchant/dev-store scenario) receives real, validly-signed webhooks for their own shop. Because only the body is signed, the attacker can capture one `(raw_body, hmac)` pair and resubmit it to the app's public webhook endpoint with the `shop-domain` (and/or `topic`/`webhook-id`) header rewritten to name a different, victim shop. `HmacValidator.validate` still succeeds (body untouched), so `Registry.process` calls the app's handler with `WebhookMetadata#shop` equal to the attacker-chosen victim shop domain while the body content actually belongs to the attacker's own shop.

### Impact Explanation
Any handler that uses `WebhookMetadata#shop` as the tenant key (the field the library itself surfaces for exactly that purpose) can be tricked into writing/processing data under, or associated with, a shop the attacker does not own — a cross-tenant data injection through a forged identity binding. This satisfies the "cross-tenant access" High-impact category: the shop identity asserted to the application is not the shop that actually authenticated the payload.

### Likelihood Explanation
Likelihood is significant: the attacker only needs their own (or a trial) Shopify store with the target app installed to obtain one legitimately-signed webhook body/HMAC pair, and the webhook endpoint is a plain public HTTP endpoint that accepts attacker-controlled headers. No access token, `client_secret`, or privileged account is required — only a self-service shop install, which matches the "unprivileged internet user" threat model.

### Recommendation
Bind the routing metadata into the signed material, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the verified body, e.g. include the canonical shop domain (as delivered by Shopify) in the value that is HMAC-verified, or require host applications to reject any webhook whose header-asserted `shop` is not already a known, previously-OAuth-authenticated shop before trusting `WebhookMetadata#shop` — and document this requirement explicitly in `Webhooks::Registry.process`/`WebhookMetadata`, since currently a successful `HmacValidator.validate` return is easy to mistake for full authentication of the shop identity.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives (or triggers, e.g. via `orders/create`) a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid for `B` under the app's `api_secret_key`), `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays the exact same request to the app's public webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the crafted headers; `Utils::HmacValidator.validate(request)` recomputes HMAC over `B` only and it matches `H`, so validation succeeds.
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)`, even though `B` never originated from `victim.myshopify.com`, demonstrating the identity-binding break between the authenticated bytes (`B`) and the trusted tenant field (`shop`).
