### Title
Webhook `shop-domain` (and `topic`) headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` and `topic` identifiers used to route and process the webhook come from unauthenticated HTTP headers. This breaks the binding `shop authenticated == shop the webhook is processed for`, letting an attacker who possesses one valid `(body, hmac)` pair replay it while forging a different `shop-domain` header, so the payload is accepted and processed as belonging to a different merchant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  The `shop`, `topic`, and `webhook_id` accessors are read straight from client-supplied HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which only checks `to_signable_string` (the body) against the HMAC: [3](#0-2)  `HmacValidator.validate_signature` hashes `verifiable_query.to_signable_string` (the raw body) and compares it to the received HMAC — the `shop` header plays no role in the signature at all: [4](#0-3) 

Once `process` validates the HMAC, it immediately trusts `request.shop` as the tenant identity and forwards it, unverified, to the app's webhook handler: [5](#0-4) 

The broken identity binding is:
`HMAC-covered bytes (raw body) != identity bytes acted on (shop header used for tenant routing)`

Because the signature only proves "this body was produced with the app's secret for *some* webhook," not "this body belongs to *this* shop," a valid `(body, hmac)` pair captured from one tenant can be replayed with a different `shop-domain` header value, and `HmacValidator.validate` will still return `true`.

### Impact Explanation
This is a cross-tenant confusion primitive: an attacker who controls (or has access to) one shop that has the app installed can trigger genuine, validly-signed webhooks for their own shop (e.g., by creating an order or updating a product), capture the `(raw_body, hmac)` pair, and replay it to the app's public webhook endpoint with a forged `shopify-shop-domain` (or `x-shopify-shop-domain`) header naming a victim shop. The HMAC check still passes because only the body is hashed, so `Registry.process` calls the app's handler with `shop: <victim shop>` and attacker-controlled body content. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to select the tenant's data store, update per-shop state, or key a session), this can lead to cross-tenant data corruption/injection — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Webhook endpoints are internet-reachable by design (Shopify posts to them from the internet), and nothing in this gem restricts the source IP or otherwise authenticates the sender beyond the body HMAC. Any unprivileged user who can install the app on a shop they control (e.g., a free/dev store) can generate valid `(body, hmac)` pairs for arbitrary webhook topics/bodies at will, then replay them with a spoofed shop header — no access to `api_secret_key` or any credential is required beyond triggering normal webhook delivery to their own store.

### Recommendation
Bind the shop (and ideally topic) identifier into the authenticated material. Either include the `shop-domain`/`topic` header values in the HMAC-signable string used by `Request#to_signable_string` (mirroring `Oauth::AuthQuery`, which signs `shop` as part of the OAuth signable string: [6](#0-5) ), or otherwise cryptographically bind the shop identity so that a captured `(body, hmac)` pair cannot be replayed under a different shop header and still validate.

### Proof of Concept
1. Attacker installs the target app on their own dev store (`attacker-shop.myshopify.com`).
2. Attacker performs an action that triggers a real webhook (e.g., `orders/create`); Shopify POSTs to the app's webhook endpoint with headers `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-topic: orders/create`, `shopify-hmac-sha256: H`, and body `B`, where `H = HMAC_SHA256(client_secret, B)`.
3. Attacker records `(B, H)`.
4. Attacker sends a new POST to the same public webhook endpoint with the *same* body `B` and HMAC `H`, but with `shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate` calls `Request#to_signable_string`, which returns `@raw_body` (`B`) — unaffected by the header change — so `OpenSSL.secure_compare(compute_signature(B, secret), H)` still succeeds: [7](#0-6) 
6. `Registry.process` proceeds and calls the app's handler with `shop: "victim-shop.myshopify.com"` and attacker-controlled body `B`, even though this webhook was never issued for `victim-shop`: [8](#0-7)

          received_signature = verifiable_query.hmac
