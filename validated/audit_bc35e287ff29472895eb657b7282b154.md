### Title
Missing IDNA/punycode host normalization in the WHATWG-style URL parser causes host/origin differential vs. standards-compliant browsers - ([File: modules/networking-mobile/src/url/helpers/host.ts])

### Summary
`domainToASCII` in the state-machine URL parser used by `modules/networking-mobile/src/url/url.ts` (and re-exported behind `@exodus/networking-common/url` types) does not perform IDNA/punycode conversion — the `tr46.toASCII` call is commented out and replaced with a bare `.toLowerCase()`. This causes `.host`/`.origin` for any URL containing non-ASCII/Unicode hostname labels to differ from what Chrome/Firefox/Safari (and the reference `whatwg-url`/`tr46` implementation this code is derived from) would produce for the same string.

### Finding Description
`parseHost` in `modules/networking-mobile/src/url/helpers/host.ts` calls `domainToASCII(domain)` to canonicalize a host label before further validation: [1](#0-0) 

`domainToASCII` itself is a stub: [2](#0-1) 

A standards-compliant browser applies full IDNA processing (Unicode NFC normalization, bidi/joiner checks, and Punycode (`xn--`) transcoding) via `tr46.toASCII`, per the WHATWG URL spec's "domain to ASCII" algorithm. This implementation skips that entirely and only lowercases the string, then runs `containsForbiddenDomainCodePoint`, which forbids most syntactically dangerous characters but does not forbid ordinary Unicode letters. As a result, non-ASCII host labels pass through into `URLRecord.host` and are later returned verbatim by `URL.prototype.host`/`.hostname` and used to build `.origin` via `serializeURLOrigin`/`serializeOrigin` (`modules/networking-mobile/src/url/url.ts:56-58`, `modules/networking-mobile/src/url/helpers/serializer.ts:55-63`).

Consequences of this gap:
- Two visually/semantically different Unicode host strings (e.g. containing different codepoints that a real IDNA/punycode pass would either normalize to the same ASCII label or reject) are preserved as distinct, un-normalized strings by this parser, while a real browser/webview would canonicalize them to Punycode ASCII labels before navigation and before exposing `location.origin` to page scripts.
- Because origin/host comparisons in the wallet (e.g. `#getOrigin` in `features/connected-origins/module/connections.js:66-68`, used by `isTrusted`/`isAutoApprove`/`getConnectedAccounts`) are plain strict string equality against a stored `origin` string, any place where this custom URL parser (rather than the platform's native `URL`) is used to derive that origin string from an attacker-controlled input (dapp request, deeplink) can produce an origin token that does not match what the actual WebView/native `URL` implementation computes for identical navigation — i.e., a parser/origin-derivation differential between this library and the real rendering surface.
- This is the classic root cause behind known "URL parser confusion" (IDNA-mismatch) bug classes: since canonicalization is skipped, homograph/IDN-based lookalike hosts are not reduced to their true Punycode form here, whereas the WebView that ultimately renders/dispatches postMessage does apply full IDNA — creating exactly the kind of parser-vs-runtime origin disagreement the question is probing for.

I was not able to conclusively locate, within the indexed portion of the repo, the exact call site where this specific `networking-mobile` `URL` class's `.origin` is fed directly into the `connected-origins` trust check (the `connected-origins` module receives a plain `origin` string argument from its caller, and I could not find that caller in the indexed code — it may live in a dapp-provider/RPC-bridge module not covered by the available index). This limits the finding to a confirmed parser-level implementation bug with a plausible, but not fully traced end-to-end, path into the trust/auto-approve gate.

### Impact Explanation
If any wallet-side origin derivation for dapp/webview/deeplink requests uses this custom parser instead of the platform-native `URL`, an attacker could craft a Unicode hostname whose un-normalized string representation collides with, or is treated inconsistently against, the origin the actual WebView navigates to and reports via `postMessage`/`location.origin`. Given that `connectedOrigins.isTrusted`/`isAutoApprove`/`getConnectedAccounts` gate auto-approval and account address exposure purely on strict string equality of the `origin` field, an origin-derivation mismatch of this kind could enable wrong-origin trust/auto-approve or inconsistent treatment of look-alike domains — matching Hydra's "origin confusion enabling auto-approve or account exposure" impact category. The severity is bounded by not being able to confirm the exact production call site that feeds attacker-controlled Unicode hostnames through this specific parser into the trust check.

### Likelihood Explanation
Preconditions: the vulnerable code path (this custom `URL`/`parseHost` implementation) must be the one used to compute the origin that is compared against `connectedOrigins`, and the attacker must be able to supply a URL/host string with non-ASCII characters (achievable via any dapp URL, deeplink, or QR-derived link, all attacker-controlled per the threat model). The parser bug itself is 100% reproducible and deterministic — it is not conditional on the state machine's control flow being fuzzed, it's a straightforward missing-normalization defect. However, whether it is reachable from the specific origin-trust gate could not be confirmed from the indexed code, which is why likelihood cannot be assessed as "confirmed exploitable end-to-end" — it is a confirmed library bug with unconfirmed full reachability into `connected-origins`.

### Recommendation
Restore proper IDNA/Punycode canonicalization in `domainToASCII` (uncomment/enable the `tr46.toASCII` call with `checkBidi: true`, `checkJoiners: true`, and reject invalid domains rather than silently passing Unicode through) so that `.host`/`.hostname`/`.origin` match the WHATWG spec and native browser/WebView behavior. Additionally, audit all call sites that derive an "origin" string used for trust/auto-approve decisions to ensure they use the platform-native `URL`/`origin` (from the WebView's `postMessage` event or native `URL` API) rather than this bundled parser, or ensure this parser is spec-complete before being used for any security-relevant origin comparison.

### Proof of Concept
Unit/differential test plan (Jest):
```js
import URL from 'modules/networking-mobile/src/url/url'

test('non-ASCII host is not IDNA/punycode-normalized, diverging from browser URL', () => {
  const u = new URL('https://xn--e1aybc.tld/') // reference: real 'аbc.tld'-style punycode host
  // A standards-compliant parser normalizes any equivalent Unicode input to this exact xn-- form.
  const unicodeInput = new URL('https://\u0430bc.tld/') // Cyrillic 'а' (U+0430) look-alike of Latin 'a'
  // EXPECT (browser-compliant behavior): unicodeInput.host === u.host (both normalize to same xn-- label)
  // ACTUAL (this implementation): unicodeInput.host retains raw Unicode codepoints, lowercased only
  expect(unicodeInput.host).not.toBe(u.host) // demonstrates the differential
})
```
Fuzz/invariant plan: generate a corpus of Unicode hostnames (mixed scripts, look-alike letters, combining marks, trailing dots) and assert `parseURL(...).host` equals the ASCII/punycode form produced by Node's native `URL` or the `tr46`/`whatwg-url` reference library for the same input string; any mismatch is a confirmed origin-derivation differential.

export function parseHost(input: string, isNotSpecialArg = false) {
  if (input[0] === '[') {
    if (input[input.length - 1] !== ']') {
      return FAILURE
    }

    return parseIPv6(input.slice(1, -1))
  }

  if (isNotSpecialArg) {
    return parseOpaqueHost(input)
  }

  const domain = utf8DecodeWithoutBOM(percentDecodeString(input))
  const asciiDomain = domainToASCII(domain)
  if (asciiDomain === FAILURE) {
    return FAILURE
  }

  if (containsForbiddenDomainCodePoint(asciiDomain)) {
    return FAILURE
  }

  if (endsInNumber(asciiDomain)) {
    return parseIPv4(asciiDomain)
  }

  return asciiDomain
