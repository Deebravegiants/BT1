### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `Webhooks::Registry.process` validates only the body HMAC and then forwards the header-derived `shop` value to the app's handler as the tenant identifier, without any binding between the verified body and the claimed shop.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 
as the signable string — i.e., only `@raw_body` is HMAC-signed.

Meanwhile, `shop` (tenant identity) is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`: [3](#0-2) 

`Registry.process` calls this validator and, on success, immediately hands the unauthenticated `request.shop` value to the app's handler as the tenant identity: [4](#0-3) 

Because the `client_secret`/`api_secret_key` is shared across all shops that install a given app (it is per-app, not per-shop), an attacker can install the target app on their own store, receive a genuine, correctly-signed webhook (HMAC computed by Shopify over a body they control indirectly, e.g. via `orders/create` on their own shop), and then replay that exact raw body to the app's webhook endpoint while swapping the `shopify-shop-domain` header to a victim shop's domain. The binding broken is:

`shop authenticated (the shop whose secret produced the HMAC over this body) != shop stored/acted upon (request.shop, taken from an unauthenticated header and passed to the handler as WebhookMetadata#shop)`

`HmacValidator.validate` returns `true` because the body HMAC is unaffected by header changes, and `Registry.process` never checks that the claimed `shop` corresponds to a shop the app actually expects for this specific webhook delivery.

### Impact Explanation
This is a High-severity cross-tenant authentication/binding bypass: any app built on this gem that uses `WebhookMetadata#shop` (or `Request#shop`) to select which merchant's data/session to update, without an independent verification, can be tricked into writing/deleting data or triggering business logic under an arbitrary victim shop's identity, using only a webhook the attacker legitimately received for their own (attacker-controlled) shop. This crosses tenant boundaries using only an attacker's own installation, no leaked credentials or access tokens required — matching the "Critical - cross-tenant access" impact bucket.

### Likelihood Explanation
Likelihood is moderate-to-high: the attacker needs only to install the target Shopify app on their own store (unprivileged, self-service action available to any internet user via the Shopify App Store or a dev store), trigger any inbound webhook event, capture the raw body and its valid HMAC, and replay it to the app's public webhook endpoint with a forged `shop-domain` header. No secret material, TLS interception, or privileged access is required — the gem itself provides no protection against this because it does not bind `shop` into the signed material.

### Recommendation
Bind the shop domain (and ideally topic/webhook id) into the value that is HMAC-verified, or otherwise require the host application to independently confirm that `request.shop` matches a shop for which this exact webhook subscription/callback address was registered before trusting it. At minimum, document prominently that `Request#shop` is unauthenticated and must not be used as a tenant-scoping key without additional verification (e.g., cross-referencing against the shop associated with the currently stored webhook registration or session).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, granting the app the standard webhook subscriptions (e.g., `orders/create`).
2. Shopify sends a webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw body>`, and a JSON body the attacker fully or partially controls (e.g., via placing a crafted order).
3. Attacker intercepts/records this raw body and the exact valid `x-shopify-hmac-sha256` value (both are visible to them as the shop owner / can be observed via their own endpoint logs).
4. Attacker replays an HTTP POST directly to the app's public webhook endpoint with the same raw body and HMAC header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Webhooks::Request.new` builds a request object where `hmac` and `to_signable_string` (body) still match, so: [5](#0-4) 
`Utils::HmacValidator.validate(request)` returns `true`.
6. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)`, causing the host application to act as if the data originated from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
