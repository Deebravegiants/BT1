### Title
Webhook `shop` identity field is not covered by HMAC verification, enabling cross-tenant data spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying the HMAC over the raw request body, but the `shop` field that is subsequently trusted and handed to the app's webhook handler is read from an HTTP header that is never included in the HMAC computation. This breaks the identity binding `shop authenticated == shop acted upon`.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`. For webhooks, `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is derived purely from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is never part of the signed bytes: [2](#0-1) 

`Registry.process` validates only the HMAC (covering the body) and then forwards `request.shop` — the unauthenticated header value — directly into `WebhookMetadata`, which is passed to the app's registered handler as trusted identity data: [3](#0-2) [4](#0-3) 

Root cause: `bytes verified` (raw_body) != `bytes parsed for identity` (shop header). The equality that should hold — `verified(HMAC) ⊇ {shop, body}` — does not; only `{body}` is covered.

### Impact Explanation
Any internet user who can obtain one genuine, validly-signed webhook delivery for a shop they control (trivial: install the app on a free Shopify development/trial store, which is unprivileged and requires no special credential) possesses a `(raw_body, hmac)` pair that is valid forever for that exact body under the app's `api_secret_key`, without ever learning the secret itself. Because the `shop` header is excluded from the signature, the attacker can replay that same `raw_body` + `hmac` header directly to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with an arbitrary victim shop domain. `Registry.process` will pass HMAC validation (it only checks the body) and will invoke the handler with `WebhookMetadata#shop` set to the victim's domain while `body` is attacker-controlled content. Any host application that uses `data.shop` as a tenant/session key to attribute the payload (a normal and expected usage pattern, e.g. looking up the merchant's `Session`/access token by `shop` before acting on `body`) will process attacker-supplied data under a different tenant's identity — a cross-tenant data-integrity/confusion issue.

### Likelihood Explanation
The webhook HTTP endpoint is internet-facing by design (that is the entire point of HTTP webhook delivery), requires no credential to reach, and the attacker only needs to run one unprivileged Shopify store to obtain a legitimately signed `(body, hmac)` sample. No `api_secret_key`, access token, or TLS interception is required — the attacker never forges an HMAC, they replay a genuine one with a swapped, unauthenticated header.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the signed material, or otherwise cryptographically bind them to the HMAC before trusting them — e.g., include the shop-domain header in the string that is HMAC-verified, or require callers to independently confirm the `shop` domain is one currently authorized/installed for the app before dispatching to the handler, rather than trusting the header. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as a trust boundary/tenant key without independent verification.

### Proof of Concept
1. Attacker installs the target app on their own Shopify development store `attacker.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Shopify delivers a genuine webhook to the app's endpoint with headers including `x-shopify-hmac-sha256: <H>` and `x-shopify-shop-domain: attacker.myshopify.com`, and raw body `B`. The attacker captures this exact `(B, H)` pair from their own store's outgoing traffic (their own dev tools / logging — no interception of others' traffic needed).
3. Attacker sends a new POST directly to the app's public webhook endpoint with the identical raw body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)`, causing any host logic keyed on `data.shop` to associate attacker-controlled data with the victim tenant.
