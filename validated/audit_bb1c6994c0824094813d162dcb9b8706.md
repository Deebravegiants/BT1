### Title
Unvalidated `hop.pool` in the swap route lets attacker-deployed code run under the caller's auth and steal wallet tokens - (File: contracts/swap-aggregator/src/venues/mod.rs)

### Summary
The Furucombo "evil contract" class — a protocol delegating calls to an attacker-chosen address — maps onto XOXNO Lending's router strategies. Every swap hop's `pool` address comes from the caller-supplied `StrategyPayload.assets` registry and is invoked directly with no allowlist (`dispatch_hop`, `soroswap::swap` → `env.invoke_contract(&ctx.hop.pool, "swap", ...)`). When a victim signs a `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, or direct `execute_strategy` transaction carrying a route whose hop points at an attacker-deployed contract, that contract executes inside the victim's authorization context. From there it can call `token.transfer(victim, attacker, amount)` on any token the victim holds; Soroban records the transfer as a child of the victim's `require_auth` entry, and if the victim signs the tree simulation produced, the transfer succeeds. The repo's own test `rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates exactly this: Alice signs a `swap_collateral` route, the rogue pool drains her entire unrelated wallet balance, and the swap still completes with a fair output.

### Finding Description
`SwapHop.pool` is resolved from the payload's `assets` registry by `u8` index; neither `dispatch_hop` nor any venue adapter checks the pool address against a registry, code hash, or token-pair binding. `soroswap::swap` calls `get_reserves` and `swap` on `ctx.hop.pool` unconditionally, and `HopContext::authorize_pool_pull`/`authorize_token_transfer` registers the router's own pull — but nothing constrains what the pool contract itself does while on the stack. Because the controller's `caller.require_auth()` (and `sender.require_auth()` in `execute_strategy`) produces a single auth entry covering the whole call, any `require_auth` the rogue pool triggers against the victim attaches beneath it. The controller-side guard in `contracts/controller/src/strategies/swap.rs` (`RouterOverspend`, `NoSwapOutput`, balance-delta checks) only bounds the *routed* tokens; it does not observe or bound arbitrary victim-spending calls made by route-selected code.

### Impact Explanation
Theft of user funds. A single signed `swap_collateral` (or `execute_strategy`) transaction can transfer the signer's entire balance of any unrelated token to the attacker, with the loss unbounded by the route amount, the `min_out` check, or the controller's measured-output verification. The test shows `WALLET_BALANCE` fully drained while the swap returns a legitimate fill.

### Likelihood Explanation
Reachable by any unprivileged attacker who can get a victim to sign one transaction: the attacker deploys a `RogueHopPool`-style contract, embeds its address in the route payload, and serves the poisoned route through any channel that produces signed routes (malicious quote, phishing frontend, or crafted `swap_xdr` handed to the victim). Simulation records the theft as a child auth entry, so it only requires the victim to sign what simulation returns — the standard signing flow. No privileged role, oracle manipulation, or reentrancy is needed.

### Recommendation
Pin hop targets to a governance-maintained allowlist of pool addresses (or verify pool code hash / factory provenance) inside `dispatch_hop` before any `invoke_contract`. Additionally, the controller should present swaps to users through a route format that cannot reference foreign addresses, and clients must reject authorization trees containing any child invocation beyond the expected input `transfer`.

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` implements the full exploit: `RogueHopPool::swap` calls `token.transfer(victim → attacker, WALLET_BALANCE)`; `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` shows the signed-tree path drains Alice's wallet to zero while crediting her `FAIR_OUT_ETH` output. Contract support: `contracts/swap-aggregator/src/venues/mod.rs` (`dispatch_hop`, `authorize_pool_pull`), `contracts/swap-aggregator/src/venues/soroswap.rs` (`invoke_contract(&ctx.hop.pool, "swap", ...)`), `contracts/controller/src/strategies/swap.rs` (`swap_tokens` granting router execution under the caller's auth).
