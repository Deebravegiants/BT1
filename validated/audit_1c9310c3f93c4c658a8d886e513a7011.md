### Title
Webhook `shop` identity field is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's HMAC over the raw request body only, but the `shop` value that is handed to the app's `WebhookHandler` (and documented as "the shop domain of the webhook") is read from an HTTP header that is never included in the signed bytes. This breaks the intended binding: `hmac(bytes verified) == bytes trusted for tenant identity`. An attacker who controls the raw HTTP request to the app's webhook endpoint can pair a previously-obtained, validly-signed body with an arbitrary `shop-domain` header and have the app process/attribute that data to a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` (and `topic`, `api_version`, `webhook_id`) are read straight from HTTP headers, which are not part of the signable string: [2](#0-1) 

`Registry.process` validates the HMAC (which only covers `raw_body`) and then passes `request.shop`, taken from the unauthenticated header, directly into `WebhookMetadata` given to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature only over `to_signable_string` (i.e., the body), never mixing in `shop`: [4](#0-3) 

The library explicitly documents `shop` as a trusted field surfaced to the handler after "the request did indeed come from Shopify" is verified: [5](#0-4) [6](#0-5) 

This is the exact bug class named in the rules: "a field acted on but not covered by the HMAC." The identity-binding equality the protocol needs is:
`hmac_valid(raw_body, api_secret_key) == true` implies `shop == origin_shop_of(raw_body)`

But in this implementation:
`hmac_valid` only proves `raw_body` was produced by someone possessing `api_secret_key` for *some* shop at *some* time — it proves nothing about the `shop-domain` header value. Any party who has ever received one legitimately signed webhook body (e.g., the operator of their own installed shop, which requires no privileged credentials) can replay that exact `raw_body` with its unchanged, still-valid `hmac-sha256` header, but substitute the `shop-domain` header for any other shop domain, directly to the app's webhook endpoint (bypassing Shopify's servers entirely, since nothing in this gem confirms the request path came from Shopify beyond the body HMAC).

### Impact Explanation
This crosses a tenant boundary: an attacker (a normal merchant with app access to their own store, not privileged, no leaked secret) can make the host application process a webhook event and durably attribute it to a shop they do not own, since the gem hands the (spoofable) shop identity to the handler as if it were verified alongside the HMAC. Applications typically key their per-tenant data (orders, GDPR redaction requests such as `shop/redact`, `customers/redact`, `customers/data_request`) by this `data.shop` value, exactly as shown in the gem's own documented handler example (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`). This enables cross-tenant data injection/confusion — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is bounded by the fact that the attacker needs at least one legitimately signed webhook body/HMAC pair, which any merchant who installs the app can obtain by simply having the app installed on their own store (no privileged account, no leaked `api_secret_key`, no access token needed). From there, forging the header is trivial since HTTP headers are fully attacker-controlled when sending directly to the endpoint. The main constraint is that the replayed body content itself is fixed (can't forge arbitrary body content without the secret), but the `shop` attribution can be freely chosen, and combined with mandatory topics like `customers/redact`/`shop/redact` this is a meaningful and readily reachable primitive.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook_id`) header values in the HMAC-signed material that `Utils::HmacValidator` checks, or otherwise cryptographically bind the shop identity to the verified payload before exposing it as `WebhookMetadata#shop`. At minimum, document loudly that `data.shop` is unauthenticated header data and must not be trusted for tenant attribution without additional verification (e.g., cross-checking against a `shop` value embedded in the JSON body, or validating against a known set of shops the app is installed on with a matching session).

### Proof of Concept
1. App legitimately installs on `victim-or-attacker-owned-shop.myshopify.com` and registers a webhook (e.g., `customers/data_request`) to `POST /callback/customers/data_request`.
2. Shopify sends a real webhook: `raw_body = B`, headers include `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` with `api_secret_key`) and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures this request (they own the shop, so this is not privileged access) and replays it directly to the app's webhook endpoint, keeping `raw_body = B` and `X-Shopify-Hmac-Sha256: H` unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` builds successfully; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (`B` only) and it matches `H`, so validation passes. [3](#0-2) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the request never actually originated from that shop, and the app processes/stores the data under the victim shop's tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
