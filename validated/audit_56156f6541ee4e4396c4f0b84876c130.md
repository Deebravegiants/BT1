### Title
Unauthenticated Disclosure of a User's MFA/WebAuthn (2FA) Enrollment Status via `SessionsController.Create` - ([File: core/web/sessions_controller.go])

### Summary
The `/sessions` login endpoint queries WebAuthn (2FA) enrollment data for any submitted email **before** any credential validation occurs, letting an unauthenticated caller determine whether an arbitrary account has 2FA enabled — the same bug class as CVE-2022-1963 (GitLab revealing 2FA enrollment status to unauthenticated users).

### Finding Description
`SessionsController.Create` is the handler for the unauthenticated `POST /sessions` login route. It immediately calls: [1](#0-0) 

`sc.App.AuthenticationProvider().GetUserWebAuthn(ctx, sr.Email)` using the raw, attacker-supplied `sr.Email` from the JSON body — no password, session, or any authentication is required to reach this call. The underlying implementation directly queries the `web_authns` table keyed only on the (case-insensitive) email: [2](#0-1) 

This is functionally the identical database lookup that `orm.CreateSession` performs internally, but that internal call is explicitly ordered *after* email/password validation, specifically to prevent this exact leak — as stated in the code comment: [3](#0-2) 

"Do email and password check first to prevent extra database look up for MFA tokens leaking if an account has MFA tokens or not."

However, `SessionsController.Create` bypasses this protection entirely by performing the same `GetUserWebAuthn` lookup unconditionally and unauthenticated, before `CreateSession` (and its password check) is ever invoked: [4](#0-3) 

The result (`len(userWebAuthnTokens) > 0`) drives observable behavioral differences: an extra DB round-trip is performed for every submission, and it also directly determines whether `sr.SessionStore`/`sr.WebAuthnConfig` are populated, which in turn changes the downstream code path taken inside `CreateSession` (whether a WebAuthn challenge branch is reachable at all) and the query volume/timing associated with the request. Because this all happens before any credential check, an attacker needs no valid password and no valid account — only an email address — to trigger a per-account differential in server behavior tied to 2FA enrollment, mirroring the GitLab flaw of exposing 2FA status to unauthenticated users.

### Impact Explanation
This enables an unauthenticated attacker to enumerate which accounts have 2FA/WebAuthn enabled purely from timing/behavioral side channels on the public login endpoint, without needing valid credentials. This is a targeting/reconnaissance primitive: attackers can prioritize credential-stuffing or password-spraying against accounts confirmed to lack 2FA, increasing the practical risk of account takeover on a node's Operator UI. It does not by itself grant authentication bypass or fund movement, keeping severity at the same class GitLab assigned (Medium).

### Likelihood Explanation
The `/sessions` endpoint is intentionally internet/network-reachable and unauthenticated by design (it's the login endpoint), and the vulnerable code path is hit on every login attempt regardless of the emailed account's validity or the submitted password — no rate-limit bypass or special conditions are required. This makes exploitation straightforward for any actor who can reach the node's web server.

### Recommendation
Move the `GetUserWebAuthn` lookup used to decide whether to attach `sr.SessionStore`/`sr.WebAuthnConfig` so that it only occurs after `CreateSession`'s internal email/password validation succeeds (i.e., let `CreateSession` be the sole place that queries `web_authns`, as its internal comment already intends), or otherwise ensure the pre-check query executes with constant timing/behavior regardless of email/account validity.

### Proof of Concept
1. Register (or know) two accounts on a node: `no2fa@example.com` (no WebAuthn credentials) and `has2fa@example.com` (WebAuthn credential registered).
2. Send unauthenticated `POST /sessions` requests with invalid passwords for both emails.
3. Measure request latency / DB query counts (e.g., via server-side logging or timing) for each: the `has2fa@example.com` request triggers `GetUserWebAuthn` returning non-empty rows and additional branch logic in `SessionsController.Create`, while `no2fa@example.com` returns an empty slice — producing a consistent, measurable behavioral distinction attributable solely to 2FA enrollment status, without any valid password.

```go
// GetUserWebAuthn will return a list of structures representing all enrolled WebAuthn
// tokens for the user. This list must be used when logging in (for obvious reasons) but
// must also be used for registration to prevent the user from enrolling the same hardware
// token multiple times.
func (o *orm) GetUserWebAuthn(ctx context.Context, email string) ([]sessions.WebAuthn, error) {
	var uwas []sessions.WebAuthn
	err := o.ds.SelectContext(ctx, &uwas, "SELECT email, public_key_data FROM web_authns WHERE LOWER(email) = $1", strings.ToLower(email))
	if err != nil {
		return uwas, err
	}
	// In the event of not found, there is no MFA on this account and it is not an error
	// so this returns either an empty list or list of WebAuthn rows
	return uwas, nil
}
```
