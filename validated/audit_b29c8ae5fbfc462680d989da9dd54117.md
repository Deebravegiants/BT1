### Title
Tokens sent directly to the pool contract are permanently frozen — the pool has no rescue/sweep mechanism (File: contracts/pool/src/lib.rs)

### Summary

The pool tracks reserves in a `cash` bookkeeping field that is only credited through owner-gated, measured-receipt paths (`supply`, `repay`, `recapitalize`, `flash_loan`). A raw `token.transfer(..., pool_address, ...)` raises the contract's real token balance but never `cash`, and no entrypoint — privileged or otherwise — can move the unbooked surplus. Unlike the swap-aggregator, which exposes `sweep_balance` for exactly this case, the pool (and its owner, the controller) exports no equivalent, so any token balance above the sum of all markets' booked `cash` is locked forever.

### Finding Description

Every mutating pool entrypoint is `#[only_owner]` (the controller), and the complete mutation surface is: `supply`, `borrow`, `withdraw`, `repay`, `recapitalize`, `flash_loan`, `create_strategy`, `seize_positions`, `net_settle`, `claim_revenue`, `create_market`, `update_params`, `update_indexes`, `upgrade` — none of which can transfer out an arbitrary token surplus. [1](#0-0) [2](#0-1) 

The design deliberately decouples the token balance from the book: `cash` is the only reserve quantity, and "incidental token donations do not increase" it — the codebase even ships a test asserting a 7-unit donation to the pool never appears in any market's `cash` and simply inflates `token.balance(pool)`. [3](#0-2) [4](#0-3) [5](#0-4) 

The closest exits are all bound to the book, not the balance:

- `claim_revenue` pays `min(cash, floor(revenue))` — it cannot touch the unbooked surplus even for a fully liquid market.
- `recapitalize` credits at most the backing shortfall and refunds the excess to the payer; it does not sweep pre-existing balance.
- `withdraw`/`borrow`/`flash_loan` transfer out only amounts debited from `cash`. [6](#0-5) [7](#0-6) [8](#0-7) 

The controller — the pool's owner — likewise exports no sweep/rescue entrypoint, and governance operations are typed proposals with no arbitrary token-transfer primitive against the pool. The surplus therefore can only ever leave through a WASM `upgrade` that adds a rescue function, i.e., it is unrecoverable under the deployed code. The contrast is stark with the swap-aggregator, whose `sweep_balance` sends the owner exactly `balance - reserved_fee_total` — the codebase authors clearly recognize the bug class but implemented the fix only in the router. [9](#0-8) [10](#0-9) 

The frozen amount is not merely dormant: because one physical pool balance is shared by every `(hub, token)` market of that token, donations of a listed token commingle across hub books while remaining payable to no one, and donations of an unlisted token have no associated market at all.

### Impact Explanation

Permanent freezing of user funds. Any user (or contract, or an accidental `transfer`) that sends a supported or arbitrary token to the pool address loses it with no recourse: the tokens cannot be credited to a position (supply requires controller mediation and measured credit to a specific account), cannot be claimed as revenue, cannot be swept by the owner, and cannot be returned. For the flash_position path, "Neither category sweeps prior balances" — positive balances already sitting on the controller from prior transfers are likewise never refunded and have no exit. [11](#0-10) 

### Likelihood Explanation

Low, mirroring the reference issue. It requires someone to send tokens directly to the pool or controller contract address outside the intended flows. Realistic triggers include users copying the contract address from a block explorer instead of calling `supply`, third-party protocol integrations pushing tokens (e.g., venue rewards — Aquarius LP rewards can already be pushed into the pool as unbooked donations per the threat model), or airdrops. The class is identical to the Medium-severity reference finding, and the loss is total once it happens.

### Recommendation

Add a bounded rescue mechanism to the pool, mirroring the swap-aggregator's `sweep_balance` pattern:

```rust
// contracts/pool/src/lib.rs — owner-only, or permissionless to a fixed recipient
fn sweep_balance(env: Env, recipient: Address, token: Address, hub_asset: HubAssetKey) {
    let balance = token::Client::new(&env, &token).balance(&env.current_contract_address());
    let surplus = balance - total_cash_for_token(&env, &token); // sum of cash across all (hub, token) markets
    if surplus > 0 { transfer(recipient, surplus); }
}
```

Key constraints: the reserved amount must be the sum of `cash` over every market sharing the token's physical balance (hub/spoke books share custody, per `docs/reference/architecture.md`), the function should refuse tokens with any market that has outstanding `borrowed` claims beyond cash, and routing through governance's delayed operation or a fixed treasury recipient preserves decentralization as the reference issue's timelock suggestion intends. For tokens with no market at all, the full balance is safely sweepable.

### Proof of Concept

1. Deploy controller + pool, create market `key = (hub_id, USDC)`, and supply 1,000 USDC through `controller.supply` so `cash = 1_000`.
2. Call `token.transfer(alice, pool_address, 500)` directly — permissionless, exactly the accidental-send scenario.
3. Observe `token.balance(pool) == 1_500` while `get_reserves(key) == 1_000`; the extra 500 belongs to no market, mints no shares, and accrues to no revenue bucket.
4. Exhaust the exit set: `claim_revenue` caps at `min(cash, revenue)` (500 untouchable), `withdraw` debits only booked cash, `recapitalize` only fills a shortfall and refunds overage — there is no call any address can make that returns Alice's 500 USDC.
5. Repeat with an unlisted token: `balance(pool)` increases but no market exists, so the tokens are inert forever absent a Wasm upgrade adding a rescue function.

    /// Transfers each token's balance above its reserved fee total to `recipient`. Owner only.
    #[only_owner]
    fn sweep_balance(env: Env, recipient: Address, tokens: Vec<Address>) {
        renew_instance(&env);
        let router = env.current_contract_address();
        let n = tokens.len();
        for i in 0..n {
            // `i < n == tokens.len()`, so the index is in range by construction.
            let token = tokens.get_unchecked(i);
            let client = token::Client::new(&env, &token);
            let balance = client.balance(&router);
            let reserved = storage::reserved_fee_balance(&env, &token);
            if balance > reserved {
                client.transfer(&router, &recipient, &(balance - reserved));
            }
        }
    }

cannot be claimed at all. Suppliers of LP collateral should expect no venue
rewards; this is forgone yield, not a loss of principal.
