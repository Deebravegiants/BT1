## Analysis

I found a concrete, code-supported analog. The XWiki bug class is: **unprivileged, attacker-supplied content is later executed with a context/privilege it should never have** (a blog post body ran with the page's elevated rights instead of the actual author's). The closest reachable analog in Hyperbridge is the shared `CallDispatcher` contract, which every unprivileged actor can invoke directly to spend whatever balance or approvals it happens to be holding on behalf of *other* users' in-flight cross-chain settlements or orders.

### Title
Unrestricted `CallDispatcher.dispatch()` lets any caller weaponize the shared dispatcher's residual token approvals/balances to steal funds - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a single, shared, permissionless utility contract referenced by `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `IntentGatewayV2`/`IntentsBase` to execute attacker-defined `Call[]` payloads attached to cross-chain messages and orders. `dispatch()` has no caller restriction whatsoever, so any unprivileged EOA can call it directly with an arbitrary `Call[]`, using whatever ETH/ERC-20 balance or lingering token approvals the dispatcher currently holds — including approvals or dust left behind by a completely unrelated user's earlier calldata execution.

### Finding Description
`CallDispatcher.dispatch()` is declared with no access-control modifier: [1](#0-0) 

It is intended to be invoked only as an internal step of `onAccept()`/`_execute()` flows in `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `IntentsBase`, immediately after tokens are minted/unlocked/escrowed to the dispatcher: [2](#0-1) [3](#0-2) 

However, because `dispatch()` is a bare `external` function with no `msg.sender` check, nothing stops an attacker from calling it directly, out-of-band from any legitimate mint/fill flow. The protocol's own documentation acknowledges that `Call[]` entries commonly perform ERC-20 `approve()` calls from the dispatcher to spender contracts (e.g., Uniswap routers) as part of composable swap patterns, and explicitly warns to use exact amounts rather than unlimited allowances "since the dispatcher contract holds tokens temporarily during execution": [4](#0-3) 

If any single call across the protocol's lifetime leaves a non-zero standing approval from the dispatcher to a spender (an uncapped `approve()`, or one where the paired swap/action reverts or is only partially consumed), that approval is a durable liability: any address can subsequently call `CallDispatcher.dispatch()` with a `Call` that invokes the approved spender (e.g., a DEX router) in a way that pulls the dispatcher's approved tokens and routes the output to an attacker-controlled address. Because the dispatcher is a single shared singleton address referenced across `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `IntentGatewayV2` on each chain, this residual state is not scoped to one order or one user — any user's leftover approval becomes a shared attack surface for every other unprivileged caller.

This mirrors the XWiki root cause precisely: content supplied by one actor (a `Call[]` embedded in a cross-chain message or order by user A) is executed later in a context (the dispatcher's own approvals/balance) that an unrelated, unprivileged actor (attacker B) can directly trigger and redirect, rather than being scoped to the rights of the actor who created it.

### Impact Explanation
An attacker who identifies (or produces, via a low-cost order/transfer of their own) a non-zero standing approval or balance on the shared `CallDispatcher` can call `dispatch()` directly to redirect those funds to themselves — concrete theft of funds belonging to unrelated bridge users/orders. Given `CallDispatcher` is shared infrastructure across `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `IntentGatewayV2`, the blast radius spans every app configured to use the same dispatcher deployment on a chain.

### Likelihood Explanation
Reachable by a single unprivileged transaction from any EOA — no relayer, proof, consensus, or governance privilege is required; only a call to `CallDispatcher.dispatch()`. The trigger condition (a non-zero standing approval or un-swept balance on the dispatcher) is plausible whenever any user's `Call[]` performs an `approve()` to a spender that doesn't fully consume the allowance in the same call, or when a batch involving dispatcher-held tokens reverts/partially executes and leaves dust before a sweep call is made.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by an allow-listed set of app contracts (e.g., an `onlyAuthorizedCaller` modifier configured per-app), or deploy an ephemeral/ per-call dispatcher (e.g., via `CREATE2`/minimal proxy scoped to the single call) so no address-level standing approvals or balances can persist between invocations from different, unrelated users.

### Proof of Concept
1. User A's order/message includes an output `Call[]` that has the shared `CallDispatcher` `approve()` a DEX router for `type(uint256).max` of `TOKEN`, intending a swap that (due to slippage or partial revert-tolerant design) doesn't consume the full allowance.
2. Once that order settles, the residual approval `TOKEN.allowance(callDispatcher, router) > 0` persists on-chain.
3. Attacker calls `CallDispatcher.dispatch()` directly (bypassing `HyperFungibleToken`/`IntentGatewayV2` entirely, since `dispatch()` has no caller restriction) with a `Call` invoking the router's swap/transfer function that pulls `TOKEN` from `callDispatcher` using the standing approval and routes the output to the attacker's own address.
4. Attacker profits from tokens that belonged to the dispatcher's residual state from User A's unrelated transaction. [5](#0-4)

     *  @dev reverts if the target is not a contract or if any of the calls reverts.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
