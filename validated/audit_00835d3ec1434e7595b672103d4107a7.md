### Title
`describeWithdrawal()` misreports status for same-token multi-withdrawals in one NEAR tx due to assetId-only matching - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal()` fetches all withdrawal records for a shared NEAR `tx.hash` via `getWithdrawalStatusWithRetry()`, then selects one using `findMatchingWithdrawal()`, which matches solely on `nep141:${w.data.near_token_id} === assetId`. When a single NEAR intents transaction contains two or more PoA withdrawals of the same token (a legitimate batch use case), `.find()` deterministically returns the same first-matching record for every `WithdrawalIdentifier` with that `assetId`, regardless of `index`, `destinationAddress`, or `amount`.

### Finding Description
The claimed equality is: `describeWithdrawal({index: i, tx, withdrawalParams}).status/txHash` must equal the true on-chain outcome of the i-th withdrawal specifically, not of "some withdrawal of this token in this tx."

Tracing the path: `getWithdrawalStatusWithRetry()` keys the PoA API query only by `{ withdrawal_hash: args.tx.hash }` [1](#0-0)  — identical for every withdrawal in the same NEAR tx, since `WithdrawalIdentifier.tx` is the shared intent transaction [2](#0-1) . The result list is then filtered by `findMatchingWithdrawal()`, which only compares `nep141:${w.data.near_token_id} === assetId` [3](#0-2) , ignoring `destinationAddress`, `amount`, and `index` entirely. The code comment explicitly documents this as a known, unresolved limitation: "multiple withdrawals of the same token in a single transaction are not supported" [4](#0-3) .

`describeWithdrawal()` itself does nothing with `args.withdrawalParams.amount`, `destinationAddress`, or `args.index` — it only forwards `assetId` into the matcher [5](#0-4) . `createWithdrawalIdentifier()` similarly does not encode any per-withdrawal disambiguator beyond the raw `withdrawalParams` and an `index` that is never consulted by the status-matching logic [6](#0-5) . `createWithdrawalIdentifiers()` in the orchestration layer assigns sequential per-bridge `index` values, but this index is only for bookkeeping, not for status disambiguation [7](#0-6) . `watchWithdrawal()` (used for polling until completion) calls `describeWithdrawal` per `wid` and trusts the returned status/txHash directly [8](#0-7) .

No existing guard (`validateAddress`, `compareAddresses`, `validateWithdrawal`, `supports()`, `assert` checks) touches this matching logic — those all operate at request-validation time, before the NEAR tx is even sent, and have no visibility into post-hoc status disambiguation between two API-returned withdrawal records with the same token.

Exploit flow: an ordinary user submits a NEAR intents tx containing two POA withdrawal intents of the same `nep141:zec.omft.near` asset to the same destination address but different amounts (e.g., splitting a large withdrawal into two batches to their own exchange deposit address, which the PoA bridge and this SDK impose no restriction against). If the PoA bridge processes and completes only one of the two on-chain transfers (which occurs at different times), calling `describeWithdrawal` for both `WithdrawalIdentifier`s (index 0 and 1) returns the exact same `{status: 'completed', txHash}` record — because `.find()` returns the first array match regardless of which logical withdrawal is queried — causing an integrator relying on per-index status to treat the still-pending withdrawal as completed.

### Impact Explanation
An integrator building a payout/credit ledger on top of `describeWithdrawal`/`watchWithdrawal` per `WithdrawalIdentifier` will either double-credit the single completed transfer (both indices report the same `txHash`) or falsely conclude a withdrawal is finished/failed when it is not. This is a status/hash misreport enabling a double-credit/refund, matching the "status or hash misreport making an integrator credit or refund twice" High-severity category (bordering on Critical per the question's framing, since funds could be double-released against a single actual on-chain transfer). The affected parties are the recipient of the still-pending withdrawal and the integrator's own payout accounting.

### Likelihood Explanation
Preconditions are simple and require no privilege beyond normal SDK usage: a user (or integrator forwarding user-controlled `withdrawalParams`) submits ≥2 same-`assetId` PoA withdrawals in a single `signAndSendWithdrawalIntent`/batch call, landing in one NEAR tx. This is a fully legitimate, unprivileged, repeatable action — no malicious relayer, RPC, or bridge API misbehavior is required; the PoA bridge API's normal, documented response format (return all withdrawal records tied to a `withdrawal_hash`) is sufficient to trigger the mismatch. The bug is deterministic and reproducible on every same-token multi-withdrawal batch, not merely theoretical, and is explicitly acknowledged as unhandled in the source comment.

### Recommendation
Disambiguate withdrawals within `findMatchingWithdrawal()` beyond `assetId` — incorporate `destinationAddress` and, where the PoA API allows, `amount`/ordinal position matched against sorted local `withdrawalParams` (as the existing comment suggests: sort both API results and local params by amount, since relayer fees are equal for same-token batches). Until the PoA API supports index-level disambiguation, either throw/refuse when `createWithdrawalIdentifiers` would produce more than one same-`assetId` PoA withdrawal in a single tx, or document and reject batches that cannot be reliably individually tracked, rather than silently returning a possibly-wrong shared result.

```typescript
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
```

```typescript
export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
```
