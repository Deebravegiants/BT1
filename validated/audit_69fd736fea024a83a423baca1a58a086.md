### Title
Webhook shop identity spoofing — HMAC binds only the request body, not the `shop`/`topic`/`webhook-id` headers ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw body, then trusts the unauthenticated `shop-domain` (and `topic`, `webhook-id`, `api-version`) headers when building the `WebhookMetadata` passed to the app's handler. Because the shop identity is never bound into the signed material, any unprivileged internet user who can obtain one valid `(hmac, body)` pair — trivially done by installing the same (often public/free) app on their own development store and capturing a real webhook delivery — can replay that exact body/HMAC to the victim app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. The signature still validates because it never covered the shop field, so the app processes attacker-controlled event data under the identity of a shop chosen by the attacker.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers, none of which participate in the signable string: [2](#0-1) 

`HmacValidator.validate` verifies only `to_signable_string` (i.e., the body) against the shared `api_secret_key`: [3](#0-2) 

`Registry.process` accepts the request once the body HMAC checks out, then forwards the unauthenticated `request.shop` header straight into the app's handler as the shop identity: [4](#0-3) 

The equality that should hold but does not: `shop authenticated by HMAC == shop delivered to the handler`. In this implementation, `shop delivered to the handler` is sourced from `X-Shopify-Shop-Domain`, a field entirely outside the HMAC's coverage. Any attacker with access to one legitimate `(hmac, body)` pair for a body they crafted on their own store (e.g., by controlling product/order content on their own trial installation, or simply capturing a webhook and reusing its body verbatim) can present that same signed body to the target app's webhook endpoint with a forged `shop-domain` header pointing at any victim shop the app has installed, since the shared `api_secret_key` is the same across all shops using the same app.

### Impact Explanation
This crosses a tenant boundary: the webhook handler is invoked believing the event originates from shop B while the attacker actually controls the (validly-signed) payload content, potentially triggering shop-specific side effects (data updates, uninstall handling, order/customer processing, etc.) against a shop the attacker does not control. This matches the "cross-tenant access" critical-impact category, since the shop binding that the HMAC is supposed to guarantee is not actually enforced.

### Likelihood Explanation
Any unprivileged internet user can obtain a valid `(hmac, body)` pair by installing the target app on their own store (most Shopify apps allow free trial installs) and capturing any inbound webhook, then replaying it against the app's public webhook endpoint with a modified `shop-domain` header. No credentials, access tokens, or `api_secret_key` knowledge are required — only the ability to generate one legitimate webhook for a shop the attacker controls, which is standard, unprivileged behavior.

### Recommendation
Bind the shop (and, ideally, topic/webhook id) into the value that is authenticated, or cross-check the header-derived `shop` against a lookup of an active, installed session for that shop before trusting it as the handler's shop identity. At minimum, document and enforce that consuming applications must verify `request.shop` corresponds to a shop with an existing session/installation before acting on the payload, rather than passing the raw header through `WebhookMetadata` unchecked.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Attacker triggers (or waits for) any webhook delivery, capturing the exact `raw_body` and the corresponding `X-Shopify-Hmac-Sha256` value — both valid because they were generated by Shopify using the app's real `api_secret_key`.
3. Attacker POSTs the same `raw_body` and `hmac` to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and any desired `X-Shopify-Topic`).
4. `Utils::HmacValidator.validate` succeeds because it only checks the body signature: [5](#0-4) 
5. `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"` and attacker-controlled body content, as shown in the metadata construction: [6](#0-5)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
