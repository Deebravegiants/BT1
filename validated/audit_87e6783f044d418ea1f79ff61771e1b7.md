Webhook shop-domain identity is not covered by HMAC, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC signature validated by `Utils::HmacValidator` binds solely to the JSON body. The `shop` identity used to attribute the webhook to a tenant is read from the unauthenticated `x-shopify-shop-domain` HTTP header and is never part of the signed content.

### Finding Description
The binding that should hold is:

`hmac == HMAC(secret, body || shop || topic)` such that the tuple `(shop, body)` delivered to the handler is authenticated as a unit.

Instead the gem implements:

`hmac == HMAC(secret, body)` while `shop = header("x-shopify-shop-domain")` (unauthenticated) [1](#0-0) [2](#0-1) 

`Registry.process` validates the HMAC using only this signable string, then constructs `WebhookMetadata` — including `shop: request.shop` from the header — and dispatches it directly to the app's handler: [3](#0-2) 

`WebhookMetadata` treats `shop` as a trusted const passed straight to the app-defined `WebhookHandler#handle`: [4](#0-3) 

Because the shop domain is never mixed into the HMAC computation, the signature that is valid for `(body)` remains valid for `(body, any-shop-domain)`. Any party that can obtain one validly-HMAC-signed body/signature pair for their own shop (e.g., a merchant who has installed the app and receives genuine webhook deliveries from Shopify for their own store) can replay that exact body + hmac while substituting the `x-shopify-shop-domain` header with an arbitrary victim shop domain. `HmacValidator.validate` will still succeed because `to_signable_string` ignores the header entirely, and the handler will process the forged event believing it originated from the victim tenant.

### Impact Explanation
This breaks the tenant-identity binding between the cryptographically-authenticated payload and the shop it is attributed to, letting an attacker impersonate arbitrary shops to any app built on this gem's webhook handling, causing cross-tenant data confusion/access in the host application (e.g., an app that keys its access-token/session lookup or writes data by `data.shop` from `WebhookMetadata`, as documented for consumers of this gem). This matches the Critical "cross-tenant access" category since the shop-scoping guarantee the gem is supposed to provide via `HmacValidator` is not actually enforced for the shop field.

### Likelihood Explanation
Likelihood is realistic in the standard use case: any developer/merchant able to install the target app on their own store legitimately receives real, validly signed webhook deliveries (mandatory topics `shop/redact`, `customers/redact`, `customers/data_request` are always deliverable, and any topic the app registers is deliverable to any installer). They can capture the raw body + `x-shopify-hmac-sha256` header from a delivery to their own shop and replay it against the app's webhook endpoint with a spoofed `x-shopify-shop-domain` header (or forge a request entirely if no other authentication/IP allowlisting is layered on top, which is outside this gem's control) — no secret key, access token, or victim credential is required.

### Recommendation
Bind the shop identity (and ideally the topic) into the signable string used by `HmacValidator`, e.g. include `shop-domain` and `topic` header values in `Webhooks::Request#to_signable_string` (matching how Shopify actually signs these values), or otherwise cryptographically verify that the delivered `shop` header matches an expected/authorized value before dispatching to the handler.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, triggering a legitimate webhook delivery for a registered topic (or a mandatory GDPR topic).
2. Attacker records the raw JSON body `B` and the valid `x-shopify-hmac-sha256: H` header Shopify sent, where `H = HMAC_SHA256(secret, B)` per [2](#0-1) .
3. Attacker replays a request to the app's webhook endpoint with the same body `B` and header `H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the signature from `to_signable_string` (only `B`) and succeeds because the shop header was never part of the signed content: [5](#0-4) .
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)` and processes the attacker-controlled body as if it belongs to `victim.myshopify.com`, achieving cross-tenant forgery.
