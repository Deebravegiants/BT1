### Title
Unprivileged users can permanently freeze a market by pushing accrued debt value past the i128 RAY ceiling, panicking every subsequent accrual - ([File: common/src/rates/index.rs])

### Summary
Every pool mutation runs `global_sync` accrual before executing the requested action. The accrual step multiplies `borrowed` (scaled debt shares, a RAY-fixed-point `i128`) by `borrow_index` via `scaled_to_original`/`Ray::mul`, which panics with `GenericError::MathOverflow` when the product exceeds `i128::MAX`. Because the borrow index grows monotonically and shares never shrink, once `borrowed * borrow_index > i128::MAX` the panic is permanent: no repay, withdraw, liquidate, supply, or `update_indexes` call on that market can ever succeed again. The market - and all user funds in it - is frozen forever, analogous to the CVE-2021-2201 class (a reachable path that crashes/halts the system).

### Finding Description
The accrual path is:

- `contracts/pool/src/interest.rs::global_sync` runs on every pool op and calls `accrue_step` per chunk.
- `accrue_step` calls `calculate_supplier_rewards` (`common/src/rates/index.rs:73`), which computes `borrowed.mul(env, old_borrow_index)` and `borrowed.mul(env, new_borrow_index)` at lines 80-81.
- `Ray::mul` uses `mul_div` over `RAY` and panics on overflow; `scaled_to_original` (`common/src/rates/scaling.rs:14`) does the same for utilization at `contracts/pool/src/cache/scale.rs:19-27`.

The caps and the index ceiling do not prevent this. `update_borrow_index` caps the *index* at `MAX_BORROW_INDEX_RAY = 1e36` (`common/src/rates/index.rs:13-19`), but the *product* `borrowed × index` must also fit in `i128`. Per `docs/reference/formulas.md:432-437`, "valid caps and bounded indexes do not guarantee that future accrual fits. Value overflow can occur before the index ceiling and block repayment/withdrawal because those operations accrue first."

The repository's own test suite proves the reachable permanent freeze. `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-360` (`a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`) shows that after sustained ~98% utilization, `update_indexes` fails with `MATH_OVERFLOW`, the borrow index is still below `MAX_BORROW_INDEX_RAY` (the cap never engaged), and every subsequent `withdraw` and `repay` reverts with the same error: "The market is frozen: exits and repayments accrue first and hit the same panic."

An unprivileged address can drive a market into this state through ordinary entrypoints: `supply` and `borrow` to establish high utilization at the steep curve segment (up to 200% APR `max_borrow_rate`), then `update_indexes` (permissionless) to trigger accrual. No role, upgrade, or parameter manipulation is required - only listed-market caps sized near the admitted token maximum (`~170B` whole tokens per `formulas.md:429`), which governance-set caps explicitly allow.

### Impact Explanation
Permanent freezing of funds for an entire market. Once `borrowed × borrow_index` exceeds `i128::MAX`, `global_sync` panics inside every op that accrues first - `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `flash_loan`, `claim_revenue`, `update_indexes` - so all suppliers' deposits, borrowers' collateral backing, and protocol revenue on that market become unrecoverable. There is no escape hatch: the panic is monotone because the borrow index only grows and debt shares cannot be burned without first accruing.

### Likelihood Explanation
Requires a large, high-utilization market sustained near the 200% APR curve segment and enough inactivity for the index to compound toward the value ceiling (in the harness test, reached within tens of years-equivalent ledger time at ~98% utilization; faster at higher effective index growth or larger `borrowed`). The caps admit up to ~170 billion whole tokens, so the condition is within configured bounds rather than hypothetical. Severity is Medium: the outcome is catastrophic for the affected market but the setup cost (capital locked at high utilization over a long horizon) is high and early repayment/withdrawal pressure from other users can delay reaching the cliff.

### Recommendation
- Bound the accrual product, not just the index: cap `borrowed` shares or clamp accrual when `borrowed * borrow_index` approaches `i128::MAX` (e.g., treat further accrual as a no-op once the value ceiling is hit, similar to the index cap at `common/src/rates/index.rs:15-17`).
- Alternatively, use saturating/`I256` arithmetic in `calculate_supplier_rewards` (`common/src/rates/index.rs:80-83`) and `scaled_to_original` (`common/src/rates/scaling.rs:14`) and clamp the resulting value, so ops continue instead of trapping.
- Add a checked pre-condition in `global_sync` (`contracts/pool/src/interest.rs:39-53`) that stops accrual gracefully when the next step would overflow, keeping repay/withdraw/liquidate usable.
- Emit an alarm event as indexes approach the ceiling (`formulas.md:437` notes none exists today).

### Proof of Concept
Existing test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-360`:

```rust
t.supply_raw(BOB, "BIG18", principal);            // unprivileged supply
t.borrow_raw(ALICE, "BIG18", debt);               // ~98% utilization
// advance time; update_indexes eventually reverts with MATH_OVERFLOW
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
// borrow_index < MAX_BORROW_INDEX_RAY: the cap never engaged
```

Root cause: `common/src/rates/index.rs:80-81` (`borrowed.mul(env, index)` on `i128` RAY values) inside `accrue_step`, invoked unconditionally by `global_sync` before every market operation.
