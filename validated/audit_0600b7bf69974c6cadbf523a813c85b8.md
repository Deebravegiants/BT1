## Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header not covered by HMAC - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating the HMAC over the raw request body only, then hands the handler a `shop` value read from an HTTP header that is never covered by that HMAC. This breaks the intended binding `shop_authenticated == shop_that_produced_the_signed_bytes`: the signature only proves "this body was HMAC-signed with the app's secret," not "this body came with this shop domain." An unprivileged internet user who controls any shop where the app is installed can capture a genuinely-signed body+HMAC pair and replay it to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header, since the secret (`Context.api_secret_key`) is shared by the app across every installed shop, not scoped per tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is instead read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no relation to the signed bytes: [2](#0-1) 

`HmacValidator.validate_signature` computes and compares the HMAC exclusively against `verifiable_query.to_signable_string` (i.e. the body): [3](#0-2) 

`Registry.process` validates that HMAC, then immediately trusts `request.shop` — the unsigned header — and forwards it to the application's webhook handler as the identity of the sending tenant: [4](#0-3) 

Because the API secret (`Context.api_secret_key`) is a single per-app secret shared across every shop that installs the app (it is not shop-specific — see how it's used identically for all shops in `ClientCredentials.client_credentials` and `Auth::Oauth`), any shop owner who installs the app can trigger a real webhook, capture the exact `(raw_body, hmac)` pair Shopify sent them (valid because it's HMAC'd with the same shared secret), and replay that identical body+HMAC to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim's `myshopify.com` domain. `HmacValidator.validate` still returns `true` (it never looked at the shop header), and `Registry.process` calls the handler with `WebhookMetadata` claiming the payload originated from the victim shop.

This is exactly the report's bug class: a field that is *acted on* (here, the tenant identity used by the handler to route/attribute the payload) is not covered by the authentication check (the HMAC), so the two values that should be bound together — "shop whose secret validated this request" and "shop the handler believes sent it" — can diverge.

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged shop owner (attacker) can make the host application process attacker-chosen webhook body content while it is attributed to an arbitrary other merchant's shop domain. Any app logic that uses `WebhookMetadata#shop` to look up that shop's session/access token, update per-shop state, or take shop-scoped action will act on attacker-controlled data under another tenant's identity — a cross-tenant access issue.

### Likelihood Explanation
Likelihood is realistic but requires the attacker to have some shop where the target app is installed (a normal, unprivileged step — any merchant can install a public app), and to be able to reach the app's public webhook endpoint directly with a crafted HTTP request (webhook endpoints are plain HTTP(S) endpoints, not restricted to Shopify's IP ranges by this gem). No access token, `client_secret`, or privileged credential is needed — only a body/HMAC pair the attacker already legitimately received for their own shop.

### Recommendation
Bind the shop identity into the authenticated data instead of trusting an unsigned header:
- Require the consuming application (or the gem itself) to cross-check `request.shop` against a shop domain independently known/stored for that installation before acting on the payload, or
- Where the raw body already contains an authoritative shop identifier (e.g. Shopify's webhook payloads generally include shop-scoped IDs), validate consistency between the signed body content and the header-derived shop before dispatching to handlers.
At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as a trust boundary by consuming apps.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers any webhook topic the app subscribes to (e.g. `orders/create`), receiving a request with `raw_body` `B` and header `x-shopify-hmac-sha256` = `HMAC(secret, B)` = `H`.
2. Attacker replays an HTTP POST to the app's webhook endpoint with the same body `B`, same `x-shopify-hmac-sha256: H`, and header `x-shopify-shop-domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` — this returns `true` because it only checks `B` against `H`, per `HmacValidator#validate_signature` / `Request#to_signable_string`.
4. `Registry.process` builds `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim.myshopify.com"` and dispatches it to the registered handler, which now processes attacker-controlled data believing it originated from the victim shop. [4](#0-3) [5](#0-4)
