### Title
Webhook `shop-domain` header is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC only over the raw request body, while the `shop` (tenant) identifier is read from a separate, unsigned header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then hands the unauthenticated `shop` value straight to the application's webhook handler. This breaks the identity binding `shop verified by HMAC == shop acted on by the handler`, letting anyone who can obtain one valid `(body, hmac)` pair from the app's own secret (e.g. by installing the app on their own store and receiving a legitimate webhook) replay that pair while claiming an arbitrary target shop domain.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, completely independent of the signed content: [2](#0-1) 

`Registry.process` validates the HMAC against the body only, and then immediately trusts `request.shop` to build `WebhookMetadata` passed to the app's handler, with no check that `shop` was part of what was signed: [3](#0-2) 

`Utils::HmacValidator.validate` re-derives the signature purely from `verifiable_query.to_signable_string` (the body, in this case) and the app's `api_secret_key`, so the check cannot detect that the `shop` header has been altered: [4](#0-3) 

This is a direct architectural inconsistency compared to how the gem handles the analogous OAuth callback flow, where `shop` **is** explicitly included in the signed string, proving the maintainers understand and normally enforce this binding: [5](#0-4) 

Because Shopify signs webhooks with a per-app secret (`api_secret_key`) rather than a per-shop secret, the same HMAC key is valid across every shop that has installed the app. An attacker only needs a legitimate `(raw_body, hmac)` pair produced by Shopify for *any* shop under the app (trivially obtained by installing the app on their own development/test store and capturing one real webhook delivery) to then resend the exact same body/HMAC to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop. `HmacValidator.validate` still returns true (body unchanged), and `Registry.process` will call the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

### Impact Explanation
Applications built on this gem are documented to key their per-tenant business logic off `WebhookMetadata#shop` (e.g., looking up the victim's stored session/access token to act on their behalf, or writing data under the victim's tenant record). Spoofing this field lets an unprivileged attacker who merely has one legitimate webhook from their own shop cause writes/actions to be attributed to another merchant's tenant — a cross-tenant access break, matching the report's identity-binding failure pattern (a field acted upon, here `shop`, is not covered by the integrity check, here the HMAC).

### Likelihood Explanation
Likelihood is High for any attacker capable of installing the target app on a shop they control (a normal, unprivileged action for any Shopify App Store app) — no leaked secrets, tokens, or privileged access are required, only replaying a legitimately received webhook body with a forged header.

### Recommendation
Include the shop identifier (or another tenant-binding value delivered inside the signed body/payload, e.g. verifying `shop` against the JSON payload rather than the header) in the value that is HMAC-verified, or independently confirm that the `shop` header matches an authenticated field derived from data covered by the signature, mirroring the pattern already used in `Auth::Oauth::AuthQuery#to_signable_string`.

### Proof of Concept
1. Install the target Shopify app on attacker-owned shop `attacker-shop.myshopify.com`; trigger any webhook topic and capture the raw POST body and its `x-shopify-hmac-sha256` header — this is a validly signed `(body, hmac)` pair under the app's real `api_secret_key`.
2. Replay an HTTP POST to the app's webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256`, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` succeeds because it only checks `raw_body` against the secret [1](#0-0) .
4. `Registry.process` invokes the registered handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"` [6](#0-5) , causing the host application to act on the victim shop's tenant data using attacker-supplied payload content.

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
