**Reasoning:**

The eviction loop in `HotStateLRU::maybe_evict` cannot evict a just-inserted key while the true LRU tail is still non-evicted, for two independent reasons:

1. **Algorithmic correctness of the doubly-linked list.** `insert` always places a new/updated slot at `head` via `insert_as_head`, and never touches `tail` unless the list was previously empty [1](#0-0) . `maybe_evict` starts from `self.tail` and walks toward `head` strictly via `prev` pointers, evicting one node per loop iteration and decrementing `num_items` [2](#0-1) . The loop condition `self.num_items > self.capacity.get()` guarantees the loop stops exactly when `num_items == capacity`, i.e., after evicting precisely the excess count of entries — no more. Since `capacity` is a `NonZeroUsize` (enforced at the type level, line 15), at least one entry always survives, and that surviving entry is guaranteed to be the most-recently-inserted `head` (the just-written slot), because eviction proceeds tail→head and stops before reaching it as long as `num_items` after insertion exceeds `capacity` by no more than the number of pre-existing entries minus one. In the boundary case cited by the question (fill to `capacity`, then insert one more), only a single eviction occurs, and it removes the original tail (the true oldest entry) — not the newly inserted head — as walked through explicitly above for `capacity == 1`.

2. **This behavior is already exhaustively verified.** The file's own property-based tests (`test_empty_overlay`, `test_nonempty_overlay`) compare `HotStateLRU` behavior against the `lru` crate's reference `LruCache` implementation across randomized insert/evict sequences and capacities, asserting exact equality of evicted keys [3](#0-2) . This is strong evidence the LRU tail-eviction invariant holds as implemented.

3. **Even hypothetically, no custody impact.** The hot/cold state distinction is a caching/performance optimization layer over state storage — moving a slot from "hot" to "cold" via `slot.to_cold()` does not alter the state value, balance, or ownership encoded in the slot [4](#0-3) ; it only affects where/how fast the slot is subsequently read. This is not a custody surface — it does not change controller, holder, supply, or authority of any asset, which the review's Custody Impact Gate requires.

    pub fn maybe_evict(&mut self) -> Vec<(HashValue, StateSlot)> {
        let mut current = match self.tail {
            Some(tail) => tail,
            None => {
                assert_eq!(self.num_items, 0);
                return Vec::new();
            },
        };

        let mut evicted = Vec::new();
        while self.num_items > self.capacity.get() {
            let slot = self
                .delete(&current)
                .expect("There must be entries to evict when current size is above capacity.");
            let prev_key_hash = *slot
                .prev()
                .expect("There must be at least one newer entry (num_items > capacity >= 1).");
            self.total_value_bytes -= slot.size();
            evicted.push((current, slot.clone()));
            self.pending.insert(current, slot.to_cold());
            current = prev_key_hash;
            self.num_items -= 1;
        }
