### Title
Webhook shop attribution not bound to HMAC signature allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` value used by `ShopifyAPI::Webhooks::Registry.process` to attribute the event to a tenant is read from an unauthenticated header. Any party that can obtain one validly-signed webhook body (e.g. a merchant who has installed the app on their own store) can re-send that body to the app's public webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header, and the HMAC check will still pass because the shop value is never part of the signed content.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

but `#shop` (and `#topic`, `#webhook_id`, `#api_version`) are pulled straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate`, which calls `to_signable_string` (body only) against `request.hmac`: [3](#0-2) [4](#0-3) 

Once the HMAC check passes, the unauthenticated `request.shop` value is forwarded verbatim into `WebhookMetadata`, which host applications use to route/attribute the update to a specific merchant: [5](#0-4) 

The Shopify webhook HMAC is computed using the app's single shared `client_secret` across every shop that installs the app, not a per-shop secret. Consequently, a merchant who installs the app on their own store (an unprivileged party with respect to any other tenant) legitimately receives Shopify-signed webhook bodies whose HMAC is valid for that same shared secret. Because the `X-Shopify-Shop-Domain` / `x-shopify-shop-domain` header is not part of the signed content, that same attacker can resend the identical signed body to the app's public webhook endpoint while substituting an arbitrary victim shop domain in the header. `HmacValidator.validate` will still succeed because it only checks the body bytes, and `Registry.process` will dispatch to the handler with `shop: <victim's domain>`.

The binding this breaks (as an equality):
`shop value bound by HMAC` (∅, not included in `to_signable_string`) ≠ `shop value acted on by Registry.process` (`request.shop`, read from an unauthenticated header).

### Impact Explanation
Any host application that trusts `WebhookMetadata.shop` as an authenticated tenant identifier (as the gem's own documentation instructs — see `docs/usage/webhooks.md`, which shows `data.shop` being used directly to key/update per-shop records) can be made to apply another shop's webhook payload against a completely different, victim shop's data. This is a cross-tenant integrity break: an attacker with a legitimate (non-privileged) installation of the app can inject fabricated events attributed to any other shop by domain, since only the domain string, not any secret, is required to target a victim. This qualifies as Critical — cross-tenant access — under the stated impact categories.

### Likelihood Explanation
Likelihood is high for any app that has installed the gem's webhook processing exactly as documented: the attacker only needs to be a legitimate (even free/trial) merchant of the app to obtain a validly HMAC-signed webhook body, then replay it with a modified `X-Shopify-Shop-Domain` header to the app's public webhook endpoint. No access to `api_secret_key`, access tokens, or the target shop's credentials is required.

### Recommendation
Include the shop domain (and ideally the topic and webhook id) in the HMAC-signed material, or otherwise cryptographically bind the shop attribution to the verified request — e.g., only trust `request.shop` after confirming it corresponds to a shop with a known active session in the app's own session storage, and document explicitly that host apps must independently verify `data.shop` is an installed/authorized shop before processing. At minimum, update `docs/usage/webhooks.md` to make this cross-tenant risk explicit, since the current example code trusts `data.shop` outright.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Shopify delivers a webhook to the app's endpoint with body `B`, header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`, and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures this request (they control their own endpoint/proxy) and re-issues an HTTP POST to the same public webhook endpoint with the identical body `B` and identical `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is constructed; `Registry.process` calls `Utils::HmacValidator.validate`, which recomputes `HMAC(secret, B)` — this matches because `to_signable_string` only ever returns the body. [3](#0-2) 
5. The handler is invoked with `WebhookMetadata.shop == "victim.myshopify.com"`, even though Shopify never sent an event for that shop — demonstrating the cross-tenant spoof.
