### Title
Webhook `shop-domain` header is trusted for tenant identification without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signable content from the raw body only, while the shop identity (`shop-domain` header) that the registry hands to app webhook handlers is taken from an unauthenticated header. This breaks the intended identity binding `HMAC-covered bytes == data acted upon`, allowing a forged shop identity to accompany a legitimately-signed body.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 
`to_signable_string` returns only `@raw_body`. None of the HTTP headers — including `shop-domain`, `topic`, `webhook-id`, or `api-version` — are part of the signed material.

`Webhooks::Registry.process` validates the HMAC over that signable string, then immediately trusts the unauthenticated `request.shop` header to build the metadata dispatched to the app's handler: [2](#0-1) 

`Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cross-check against the HMAC or against any allow-list of installed shops: [3](#0-2) 

Because a single app uses one shared `client_secret` (`Context.api_secret_key`) across every merchant that installs it, HMAC validation in `Utils::HmacValidator.validate` only proves that *some* installer of this app produced this body — it proves nothing about which shop the body belongs to: [4](#0-3) 

**Broken identity binding (as an equality):**
`shop_used_by_handler (request.shop, from unauthenticated header)` should equal `shop_that_produced_the_HMAC-signed_body`, but the gem enforces only `HMAC(raw_body) == expected`, never `shop ∈ signable material`. An attacker who controls their own shop can receive a legitimately-signed webhook body from Shopify (any topic they can trigger, e.g. `app/uninstalled`, `orders/create` on a low-effort resource they create in their own dev store), capture the valid `(raw_body, hmac)` pair, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop that has also installed the same app. `HmacValidator.validate` still succeeds (it never looked at the header), and `Registry.process` calls the handler with `WebhookMetadata.new(shop: <victim-shop>, body: <attacker-controlled-but-Shopify-signed>, ...)`.

### Impact Explanation
This is a cross-tenant confusion: the app's business logic (built on `WebhookMetadata#shop`, as returned to handlers) will act as if the webhook came from the victim's store while the payload/topic was actually authored by the attacker's own store. Depending on the handler's use of `data.shop` (e.g., looking up an `Auth::Session` for that shop to make authenticated API calls, or writing/mutating per-shop records), this can lead to cross-tenant data corruption or actions being taken against a shop the attacker does not control, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
The attacker needs: (1) their own shop installed on the same app (any unprivileged internet user with a dev/trial store can do this) to legitimately trigger and capture a signed webhook payload, and (2) network access to POST to the app's public webhook endpoint with attacker-chosen headers. Both requirements are trivially satisfiable by an unprivileged internet user; no access token, `api_secret_key`, or privileged account is required.

### Recommendation
Bind the trusted shop identity to the signed material, or otherwise cryptographically verify it, before trusting `request.shop`:
- Include `shop`, `topic`, and `webhook-id` in the HMAC-signable string (mirroring what OAuth's `AuthQuery#to_signable_string` already does for `shop`/`host`), or
- Require callers to independently confirm the resolved shop is an installed/known shop (e.g., cross-check against a stored session/shop registry) before invoking the handler, rather than trusting the header value alone.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a webhook (e.g., `app/uninstalled`) and capture the raw POST: body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
3. Send a new POST to the app's webhook endpoint with the same body `B` and header `H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` passes because it only checks `B` against `H` via `to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-22`).
5. `Registry.process` dispatches to the handler with `shop: "victim.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:188-200`), even though the payload was authored by the attacker's own shop, not Shopify acting on behalf of the victim.
