### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body. The `shop` (and `topic`/`webhook_id`) values, which are taken from HTTP headers, are never included in the signed material, yet `shop` is subsequently treated as the trusted tenant identifier and handed to the app's webhook handler.

### Finding Description
`Webhooks::Registry.process` verifies authenticity with: [1](#0-0) 

`Utils::HmacValidator.validate(request)` calls `request.to_signable_string`, which for a webhook `Request` returns only the raw body: [2](#0-1) 

The `shop` accessor, however, is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header and is never part of the signed bytes: [3](#0-2) 

After HMAC validation passes, `request.shop` is passed straight into `WebhookMetadata` and delivered to the app's handler as the authenticated tenant identifier: [1](#0-0) 

This is the same class of bug as the report's shadowed variable: the value that is *verified* (the raw body bytes, under the app's single `client_secret` shared across every merchant that installed the app) is not the same as the value that is *acted upon* (the `shop` header used to identify which tenant the webhook belongs to). The broken identity binding is:

`HMAC-verified(body) == shop-attributed-to(body)`

which does not hold, because `shop` can be swapped independently of the signed body without invalidating the signature.

### Impact Explanation
Any merchant who has legitimately installed the app receives real webhooks signed with the app's single, shared `client_secret`. That merchant (an unprivileged, non-victim tenant) can capture one of their own valid `(body, hmac)` pairs and replay it against the app's webhook endpoint with the `shopify-shop-domain` header changed to a victim shop's domain. `HmacValidator.validate` will still succeed because it only checks the body against the shared secret, and `Registry.process` will dispatch the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain. If the host application uses `WebhookMetadata#shop` to look up the victim's session/access token or to write data into the victim's tenant record (the documented and expected usage pattern of this field), this results in cross-tenant data injection/access — a Critical-impact cross-tenant boundary violation achievable by any user who can install the app once, without needing the victim's or the app's `client_secret`, access token, or any privileged access.

### Likelihood Explanation
Likelihood is high for apps that follow the library's own contract of trusting `WebhookMetadata#shop` as the tenant identifier once `HmacValidator.validate` passes — nothing in the gem hints that the shop header is unauthenticated, and the API guarantees only "HMAC valid" without qualifying which fields that covers. An attacker needs only a normal, one-time app installation on any shop (unprivileged internet-user access) to obtain a valid `(body, hmac)` pair signed with the shared secret, then replay it with a forged shop header.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the signable content used by `Webhooks::Request#to_signable_string`, or independently verify that the `shop` header matches a shop actually known/registered by the host app before trusting it — however, since Shopify's real webhook HMAC scheme signs only the body (this mirrors Shopify's actual on-the-wire webhook protocol), the safer mitigation within this gem is to document/enforce that consumers must independently authenticate `WebhookMetadata#shop` against their own installed-shop registry rather than treat it as verified by `Utils::HmacValidator.validate`. At minimum, `Registry.process`/`WebhookMetadata` documentation should not imply `shop` is authenticated by the HMAC check.

### Proof of Concept
1. Legitimately install the target app on `attacker-shop.myshopify.com`; Shopify sends a real webhook: body `B`, header `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-hmac-sha256: HMAC(secret, B)`.
2. Attacker replays the identical `B` and `HMAC(secret, B)` to the app's webhook endpoint but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because only `B` is checked.
4. `Registry.process` in `lib/shopify_api/webhooks/registry.rb:188-199` dispatches the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the app to act on/for the victim tenant using attacker-supplied body content.
