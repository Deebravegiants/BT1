### Title
Order withdrawal permanently reverts for beneficiaries lacking a payable fallback, freezing escrowed ETH - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._sendValue` and the `_withdraw`/`_sweepDust` functions that use it push native ETH to a `beneficiary` address via a low-level `.call{value: amount}("")` and revert the entire transaction (`InsufficientNativeToken`) if the push fails. If the beneficiary is a smart contract without a `receive()`/payable `fallback()`, the ETH transfer will always fail, permanently blocking release of the escrowed funds for that order, mirroring the referenced Footium `claimETHPrize()` bug class.

### Finding Description
`_sendValue` is a hard-revert-on-failure native transfer helper: [1](#0-0) 

It is used inside `_withdraw`, the function that releases escrowed order tokens (including native ETH, `token == address(0)`) to a `beneficiary` derived purely from order data supplied at order-placement time: [2](#0-1) 

The `beneficiary` is decoded directly from `body.beneficiary`, an address chosen by the order creator (or, for solver fills, the order's `output.beneficiary`) — a value the protocol does not validate for payable-ability: [3](#0-2) 

The same pattern (revert-on-failed push) also appears directly in `IntrinsicIntents.sol`'s same-chain fill path, where the beneficiary receives native ETH inline: [4](#0-3) 

and in `ExtrinsicIntents.sol`'s cross-chain fill path via `_sendValue`: [5](#0-4) 

Unlike `WrappedHyperFungibleToken.onAccept`/`onPostRequestTimeout`, which explicitly guard against exactly this failure mode by re-wrapping to WETH and delivering an ERC-20 transfer if the native push fails (`if (!sent) { IWETH(_underlying).deposit{value: message.amount}(); IERC20(_underlying).safeTransfer(beneficiary, message.amount); }`): [6](#0-5) 

the intents contracts have no fallback path — a failed native push simply reverts the whole withdrawal/fill/refund.

### Impact Explanation
When `_withdraw` is called with `token == address(0)` for a beneficiary contract lacking a payable fallback:
- For `fillOrder`/`RedeemEscrow`, the solver's fill transaction always reverts, so the order can never be filled and the escrowed input tokens are permanently stuck for both the order creator and any solver.
- For `RefundEscrow` (cancellation), the refund can never be delivered, permanently freezing the original user's escrowed input tokens, since the same `beneficiary`-derived address (the order creator, unless a different refund beneficiary is set) is used.
- `_sweepDust` has the same issue for governance dust sweeps, but that is a privileged/governance path and out of scope; the unprivileged order-creator/solver-driven paths (`fillOrder`, `cancel`) are in scope and directly reachable by any unprivileged order submitter or solver.

This results in permanent freezing of escrowed ETH funds with no recovery mechanism, matching the "Accept... permanent freezing of funds" validation criterion.

### Likelihood Explanation
Any user can place a cross-chain or same-chain order specifying a `beneficiary`/`output.beneficiary` that is a contract address without payable capability (either accidentally, e.g. a multisig/vault contract that rejects plain ETH, or maliciously to grief a solver by making the order unfillable while still locking the solver's committed liquidity attempt). No special privileges are required — an unprivileged order placer or the order's own beneficiary field decides the outcome, so likelihood is realistic in normal usage (many smart-contract wallets/vaults do not implement a payable fallback) and easily triggerable deliberately.

### Recommendation
Apply the same defensive pattern already used in `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable`: on a failed native ETH push in `_sendValue` (or specifically within `_withdraw`), fall back to wrapping the ETH (e.g., into WETH) and delivering it as an ERC-20 transfer instead of reverting, or maintain a pull-based claim mechanism (escrow accounting keyed by beneficiary that can be withdrawn later) so a non-payable beneficiary does not permanently block the fill/refund of the entire order.

### Proof of Concept
1. Order creator places a same-chain or cross-chain order via `IntentGatewayV2`/`IntrinsicIntents`/`ExtrinsicIntents`, setting `order.output.beneficiary` (or refund beneficiary) to a deployed contract that has no `receive()`/payable `fallback()` and requesting a native-ETH (`token == address(0)`) output.
2. A solver calls `fillOrder`, which in `IntrinsicIntents._fillOrder`/`ExtrinsicIntents._fillCrossChain` attempts `beneficiary.call{value: beneficiaryTotal}("")` (or `_sendValue`) at [7](#0-6) .
3. The call fails since the beneficiary contract rejects plain ETH transfers; the function reverts with `InsufficientNativeToken`, so the fill transaction can never succeed.
4. Similarly, if the order later needs to be cancelled/refunded, `_withdraw` at [8](#0-7)  reverts for the same reason, permanently freezing the escrowed input tokens with no way to release them.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
