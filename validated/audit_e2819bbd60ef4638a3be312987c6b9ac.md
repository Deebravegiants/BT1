Based on my investigation, the codebase already has explicit zero-price guards in exactly the places the report warns about, but one path in the FX solver's fill computation lacks that guard.

### Title
Missing zero-output check in `computeLegPolicyOutput` lets an extreme-price leg consume budget while paying nothing - ([File: sdk/packages/simplex/src/strategies/fx.ts])

### Summary
`FXFiller.computeLegPolicyOutput` converts a leg's token0 notional into a token1 (or token0) output using a floating `Decimal` rate, then floors it into an on-chain integer. It only guards against the *input* notional being non-positive (`token0ForLeg.lte(0)`) — it never checks whether the resulting `policyMaxOutput` itself rounds down to zero, which is exactly the failure mode described in the referenced report (extreme price ratios rounding a quoted price to zero).

### Finding Description
`computeLegPolicyOutput` computes: [1](#0-0) 
Only `token0ForLeg.lte(0)` returns `null`; `policyMaxOutput` can legitimately floor to `0n` (e.g., a token1-denominated input divided by a very large `rate`, or a very small input multiplied by a very small `rate`) while `token0ForLeg` stays positive. When that happens `legResult` is non-null and the caller treats it as a normal, successful leg.

In the real-fill path (`evaluateOrder`), this zero-output leg still consumes the pair's exposure budget: [2](#0-1) 
`remainingByPair` is debited by `token0Used` even though the paid-out `policyMaxOutput` is `0`. The subsequent `policyMaxOutput < desiredOutput` check would normally reject an underpriced leg, but if `desiredOutput` is also `0` (e.g., a proportionally tiny capped slice) the leg can slip through with a payout of `0` while consuming real budget — silently degrading the pair's remaining capacity for other orders without delivering value, and doing so without any log or error signal, unlike the explicit `policyMaxOutput < desiredOutput` "price" skip path that exists for the ordinary underpricing case.

In the phantom-probe path (`quotePhantomFill`), the same unguarded zero is pushed directly into the published price feed: [3](#0-2) 
That zero amount becomes a solver bid (`quotes.push({ price: 0, weight })`), can be selected by `weightedMedian`, and would be written as `PhantomOrderPriceSnapshotV2.medianPrice = 0`, exactly the "0 price could occur as an intermediate step" scenario the report warns about.

### Impact Explanation
On the consumer side, the SDK strategies (`phantomSnapshot.ts` and `indexedRates.ts`) *do* already guard against a zero-priced quote: [4](#0-3) [5](#0-4) 
so a *quote* built from a zero-priced snapshot fails loudly rather than letting a user construct a free-theft order. This substantially limits exploitability of the report's classic "steal all of a user's tokens" scenario through the intent-quoting surface.

However, the missing guard inside `computeLegPolicyOutput` itself still allows the filler to (a) silently degrade a pair's `remainingToken0` budget for zero real output in a live fill, and (b) publish a `medianPrice = 0` phantom snapshot that corrupts the indexer's published rate for that pair (`poolRateFromQuote` would compute a rate of `0`, later consumed by `indexed_rates` quotes on other orders unless the downstream `readIndexedRate`/`amountOut <= 0n` checks catch it). This is budget/accounting corruption and a false-zero price signal into the shared oracle infra — not a directly demonstrated fund-theft path given the downstream `<= 0` guards, so I classify it as Medium.

### Likelihood Explanation
This requires a pair configured with a token0/token1 decimals/rate combination extreme enough to floor to zero at the leg's actual notional — analogous to the `BTC/SHIB`-style disparity in the report. Given Hyperbridge's currently configured pairs (stablecoins, cNGN) this is unlikely today, but the code has no structural protection if a new pair with a large decimal/price disparity is added, and the root cause (missing `price != 0` / `policyMaxOutput != 0` check) mirrors the exact bug class validated and fixed upstream in splits-oracle.

### Recommendation
Add an explicit check in `computeLegPolicyOutput` that returns `null` (treated the same as "cannot fill this leg") when `policyMaxOutput === 0n`, mirroring the `price != 0` check the referenced fix applied:
```ts
if (policyMaxOutput === 0n) {
  return null
}
```
This ensures a leg that floors to a zero payout is treated as unfillable (triggering the existing `partialEligible()` / skip-order logic) rather than silently consuming exposure budget or being published as a `0` phantom price.

### Proof of Concept
1. Configure (or have configured in the future) a pair whose `token0Decimals`/`token1Decimals` and curve `rate` combination is extreme enough that a legitimate, positive `input.amount` converts, via `token0ForLeg.mul(rate)` (or `.div(rate)`), to a `Decimal` value that floors to `0` when scaled by `10 ** token1Decimals` (or `token0Decimals`).
2. Call `quotePhantomFill(order)` for that pair: `computeLegPolicyOutput` returns `{ token0Used: <positive>, policyMaxOutput: 0n }`, which is pushed into `outputs` as `{ token: output.token, amount: 0n }`. [6](#0-5) 
3. That `0` output is submitted as this solver's bid; if it wins the weighted median (e.g., this solver dominates the destination-token balance weight), `PhantomOrderPriceSnapshotV2.medianPrice` is written as `0`, corrupting `updateLiquidityPools`'s published rate for the pair via `poolRateFromQuote(0n, ...) === 0n`.
4. Separately, in `evaluateOrder`, the same zero-output leg debits `remainingByPair` by `token0Used` while paying `finalOutputAmount = 0`, degrading the pair's live exposure budget for subsequent orders with no compensating output or log entry.
