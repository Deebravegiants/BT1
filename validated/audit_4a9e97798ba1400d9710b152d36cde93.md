### Title
Assets/ERC20s created by an Emporium CASE 2 op but omitted from `circomData.erc20TokenAddresses` are never diffed or swept, permanently stranding value at the Emporium proxy and letting any later transaction silently drain it - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` only measures `balancesBefore`/`balancesAfter` for the tokens explicitly listed in `circomData.erc20TokenAddresses`, and `handleOut` only sweeps back tokens at those same indices. Any asset produced by a CASE 2 op (raw, attacker-controlled `op.endpoint.call(op.callData)`) whose address is not included in that array is left sitting on the Emporium contract with no accounting, no UTXO created for it, and no enforcement preventing an unrelated later transaction from moving it out unconstrained.

### Finding Description
Broken equality: for token `T` not present in `circomData.erc20TokenAddresses`, the code should still guarantee `value created by the op for T == value swept back via handleOut to msg.sender`. Instead, the `runAction` loop: [1](#0-0) 

only iterates `i` over `circomData.erc20TokenAddresses`, computing `balanceChange = balancesAfter[i] - balancesBefore[i]` and calling `handleOut` per listed index. `handleOut` transfers `balanceChange` of `circomData.erc20TokenAddresses[i]` to `msg.sender` (Hinkal.sol): [2](#0-1) 

Because `circomData.erc20TokenAddresses` is fully attacker-supplied (part of their own proof/`CircomData`), an attacker constructs a valid transaction whose CASE 2 op (`op.invokeWallet == false`, so it's an arbitrary `op.endpoint.call{value: op.value}(op.callData)` with no endpoint allow-list beyond blocking two specific selectors): [3](#0-2) 

calls `MockVault.deposit(...)` which pulls an already-tracked deposit token from Emporium and mints vault shares to `address(this)` (Emporium). Since the vault-share token address is deliberately absent from `erc20TokenAddresses`, no `balanceChange` is ever computed for it, `handleOut` never runs for it, and the shares remain on Emporium's balance sheet forever. `Hinkal.sol`'s outer balance-diff loop (which creates the actual UTXOs returned to the user) is likewise scoped only to `circomData.erc20TokenAddresses`: [4](#0-3) 

so the shares never receive a corresponding UTXO/commitment - the value is simply orphaned in the Emporium contract, unbacked by any nullifier/commitment accounting.

This is worse than a self-inflicted mistake: because `EmporiumUpgradeable` is a shared, persistently-funded proxy, in a **later, unrelated** transaction any unprivileged attacker (the original depositor or anyone else) can submit a fresh valid proof for their own trivial action and simply append a CASE 2 op such as `vaultShareToken.transfer(attacker, staticBalance)`. As long as `vaultShareToken` is again omitted from that transaction's `erc20TokenAddresses`, the `runAction` balance loop never inspects it, so the raw transfer succeeds with zero checks (no slippage requirement, no `BalanceChangeShouldBePositive` revert, since that guard only fires for indices present in the array): [5](#0-4) 

If the attacker instead tried to list the token in `erc20TokenAddresses` to withdraw it "properly," the negative `balanceChange` with no matching negative `deltaAmountChanges[i]` would hit `revert BalanceChangeShouldBePositive()` — so the *only* way to move the stranded asset at all is via the unaccounted, silent path, confirming this is a structural drain vector, not an accounting nuance.

None of the existing guards catch this: `performHinkalChecks`/`dimensionsCheck`/`checkOnchainCreation` (`contracts/HinkalHelper.sol`) only constrain array-length consistency and onchain-creation semantics for tokens that ARE listed; the calldata-hash check binds the attacker to their own self-chosen `erc20TokenAddresses` and op bytes, but does not force them to enumerate every asset their own arbitrary call touches. The circuit's `inTotal + amountChanges === outTotal` constraint likewise only reasons about the enumerated token dimension — it has no visibility into arbitrary CASE 2 side effects on unlisted tokens.

### Impact Explanation
Two coupled harms, both matching the Critical bar:
1. Permanent freezing of the depositing user's own funds: the underlying deposit is consumed (accounted for via `deltaAmountChanges`/nullifiers) but the resulting vault-share value is never returned as a UTXO — it is unrecoverable through the intended shielded-balance mechanism.
2. Direct theft: because the stray balance sits on a shared, always-live proxy contract, any other unprivileged attacker can later drain it via an unrelated CASE 2 raw `transfer` call that also omits the token from `erc20TokenAddresses`. This is "moving assets a wallet owner or prover never authorised" at minimum, and constitutes theft of another party's stranded value.

### Likelihood Explanation
No privileged role is required. The attacker fully controls `CircomData` (including `erc20TokenAddresses`, `externalActionData.externalActionMetadata`/`EmporiumStack.ops`) for their own proof, and can deploy their own `MockVault`-style endpoint or target any existing ERC20/vault. The only cost is gas plus one legitimate Hinkal transaction to seed the Emporium balance and a second (from anyone) to drain it. Fully repeatable against any token/asset kind (LP tokens, ERC4626 shares, NFTs via `safeTransferFrom`, Permit2 allowances) that a CASE 2 op can create or approve without being listed.

### Recommendation
Require the circuit/on-chain check to enumerate every asset touched by CASE 2 calls (or ban truly open-ended `op.endpoint`/`op.callData` in favor of an allow-listed, parameterized set of DeFi adapters whose token outputs are always included in `erc20TokenAddresses`). At minimum, after executing all ops, verify Emporium's balance of any token not in `erc20TokenAddresses` is unchanged (e.g., via a generic sweep-and-revert check, or by disallowing arbitrary `call` targets/selectors entirely for CASE 2 and only permitting whitelisted adapter contracts that are required to report their output token to the accounting loop).

### Proof of Concept
Foundry fork test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, a real ERC20 `USDC`, and a `MockERC4626Vault(USDC)` whose `deposit()` mints shares to `msg.sender` (Emporium).
2. As `attacker`, deposit `USDC` into Hinkal normally (creating a valid UTXO), then submit a `transact` call with `externalActionId` = Emporium, `erc20TokenAddresses = [USDC]` only, and an `EmporiumStack` CASE 2 op: `MockVault.deposit(amount)`. `deltaAmountChanges[0] = -amount` (USDC consumed), vault shares minted to Emporium but never enumerated.
   - Assert `vault.balanceOf(address(emporium)) > 0` immediately after the tx.
3. Have `attacker` (or a second unrelated `attacker2`) submit any other trivial valid Hinkal/Emporium transaction (e.g., a no-op deposit of 1 wei of an unrelated token) with a CASE 2 op `vault.transfer(attacker2, sharesAmount)`, again with `vault` omitted from `erc20TokenAddresses`.
   - Assert this transaction succeeds (no revert), and `vault.balanceOf(address(emporium))` drops to 0 while `vault.balanceOf(attacker2) == sharesAmount`, proving unauthorized extraction of value never accounted for by `handleOut`/`balancesBefore`/`balancesAfter`, and never backed by any nullifier/UTXO.

        int256 balanceChange,
        CircomData calldata circomData,
        uint256 i
    ) internal returns (UTXO memory outUtxo) {
        // total change can be less than zero if there was some balance before the call -> that's why we have <=
