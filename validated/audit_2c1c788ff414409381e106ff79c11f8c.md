Audit Report

## Title
CORS wildcard-origin matching in the Gateway HTTP server accepts non-subdomain hosts sharing a suffix, allowing Origin allowlist bypass - (File: `core/services/gateway/network/httpserver.go`)

## Summary
The `isAllowedOrigin` function in `core/services/gateway/network/httpserver.go` strips the `*.` prefix from a configured wildcard CORS origin and then performs a raw `strings.HasSuffix` comparison against the client-supplied `Origin` header, without requiring a `.` label boundary. This lets an attacker whose domain merely ends with the same character sequence (e.g. `evilexample.com` against an allowlisted `*.example.com`) be treated as an authorized subdomain, bypassing the intended CORS origin restriction.

## Finding Description
The vulnerable code is: [1](#0-0) . Once `*.` is stripped from `allowedHost`, the remaining check `strings.HasSuffix(originHost, allowedHost)` is satisfied by any string ending in that suffix, not just true subdomains delimited by a dot — e.g. `evilexample.com` satisfies `HasSuffix("evilexample.com", "example.com")`.

This function directly gates the `Access-Control-Allow-Origin`/`Access-Control-Allow-Methods`/`Access-Control-Allow-Headers` response headers in `handleRequest`, using the raw, attacker-controlled `Origin` header value: [2](#0-1) . No other validation of the Origin value's domain boundary exists elsewhere in the file.

I confirmed the existing unit tests exercise wildcard matching but do not cover this exact boundary-bypass scenario: [3](#0-2)  only tests a different-suffix host (`ethereum.remix.org` vs `*.ethereum.org`), a scheme mismatch, and a missing port — none of which exercise a suffix-sharing but non-subdomain host like `notethereum.org` or `evilethereum.org` against `*.ethereum.org`. The bug is present and untested/unfixed in the current code.

## Impact Explanation
This is an allowlist-bypass in the Gateway's CORS handling. An operator who configures `CORSAllowedOrigins = ["https://*.example.com"]`, intending to permit only their own subdomains, will unintentionally also authorize any attacker-controlled domain that merely shares the trailing byte sequence (e.g. `evilexample.com`). A malicious site can then issue browser-based, CORS-authorized requests against the Gateway's HTTP endpoint, which maps to the in-scope "allowlist bypass" / "cross-user response corruption" impact class.

## Likelihood Explanation
Exploitability requires only a documented, supported configuration pattern (`CORSEnabled = true` with a wildcard entry in `CORSAllowedOrigins`, as shown in `sample_config.toml`) and an attacker registering/controlling a domain sharing the allowed suffix — no privileged, host, or operator access is needed by the attacker. Reachable purely via a crafted `Origin` header from any unprivileged web client.

## Recommendation
Enforce a proper label boundary in the wildcard match, e.g. verify `originHost` equals the base domain or ends with `"."+allowedHost` (with the leading dot preserved), rather than a bare suffix comparison.

## Proof of Concept
1. Configure `CORSEnabled = true`, `CORSAllowedOrigins = ["https://*.example.com"]`.
2. Send `POST` to the Gateway's configured path with header `Origin: https://evilexample.com`.
3. `isAllowedOrigin` strips to `allowedHost = "example.com"`; `strings.HasSuffix("evilexample.com", "example.com")` returns `true`.
4. Response includes `Access-Control-Allow-Origin: https://evilexample.com`, despite `evilexample.com` not being a subdomain of `example.com` — extendable to a Go unit test analogous to `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards` in `core/services/gateway/network/httpserver_test.go` asserting the header is empty for such an origin (it currently would not be, once such a case is added).
