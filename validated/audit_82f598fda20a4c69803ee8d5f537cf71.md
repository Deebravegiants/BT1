### Title
Webhook shop-domain identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC over the raw request body, but the `shop` (and `topic`/`webhook_id`) values that are handed to the app's handler as the trusted tenant identity come from unauthenticated HTTP headers that are never included in the HMAC-signed material. This breaks the intended binding: `HMAC-verified bytes == bytes acted upon as the tenant identity`.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only `@raw_body`, deliberately excluding all headers: [2](#0-1) 

However, `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from HTTP headers, which are attacker-controllable at the transport layer (any HTTP client hitting the app's public webhook route can set arbitrary header values), and are not cryptographically bound to the signed body: [3](#0-2) 

`Registry.process` validates only the HMAC and then immediately trusts `request.shop` and `request.topic` as the tenant/topic identity passed to the app's handler: [4](#0-3) 

The documented handler contract explicitly tells integrators to treat `data.shop` as the authenticated shop for that webhook, e.g. to route/store per-tenant work: [5](#0-4) 

Because the signature covers only the body and not the shop-domain header, two different header sets can produce the *same valid* HMAC as long as the body bytes are unchanged, i.e.:
`HMAC(secret, body) == HMAC(secret, body)` regardless of `shop-domain header A` vs `shop-domain header B`.
This equality that the code relies on for authorization — "the shop the HMAC was computed for" == "the shop passed to the handler" — does not actually hold, since the HMAC was never computed "for" any shop at all.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker who owns any shop that installs the app (a trivial, low-privilege action — no `api_secret_key`, access token, or leaked credential required) receives genuinely-Shopify-signed webhook deliveries for their own shop. Because the HMAC only covers the body, the attacker can capture one such valid `(body, hmac)` pair and replay it to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and freely also `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header for a victim shop. The HMAC validation still succeeds (it never looked at those headers), and the app's `WebhookHandler#handle` is invoked believing the payload originated from the victim shop. If the host application uses `data.shop` to look up the merchant's session/access token or to perform per-tenant side effects (exactly as documented), this enables cross-tenant data manipulation/exfiltration through the app acting on behalf of the wrong tenant — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for any app that: (1) uses this gem's built-in `Webhooks::Registry.process`/`Request` as documented, and (2) is installed on at least one shop controlled by the attacker (a normal, unprivileged action available to any internet user via the Shopify app install flow) so they can harvest one legitimate `(raw_body, hmac)` pair to replay with a forged shop header. No secrets, tokens, or elevated access are needed — only a normal merchant/developer relationship with Shopify plus the ability to send arbitrary HTTP headers to the app's public webhook route.

### Recommendation
Include the shop-identifying header(s) (`X-Shopify-Shop-Domain` and, ideally, topic/webhook-id) in the material that is HMAC-verified, or otherwise cryptographically bind them to the signed payload before trusting them. Concretely, `Webhooks::Request#to_signable_string` should incorporate the shop-domain (and other headers currently used to construct `WebhookMetadata`) rather than only the raw body, so an attacker cannot swap tenant-identifying headers on a replayed-but-still-validly-signed body.

### Proof of Concept
1. Attacker creates/owns Shop A and installs the target app; the app registers webhooks via `ShopifyAPI::Webhooks::Registry.register_all`.
2. Shopify delivers a legitimate webhook to the app for Shop A with headers `X-Shopify-Shop-Domain: shop-a.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid hmac over raw body>`, and some `raw_body` (e.g., `{}` or any predictable/attacker-influenced payload such as a store setting the attacker controls).
3. Attacker captures this `(raw_body, hmac)` pair (they own Shop A, so they can trivially observe their own webhook deliveries, e.g. via a debugging proxy on their own callback endpoint).
4. Attacker sends a new HTTP request directly to the app's public webhook route with the **same** `raw_body` and `X-Shopify-Hmac-Sha256`, but with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only, which matches, so `Registry.process` proceeds and invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` — as shown in [4](#0-3) , causing the host app to act as if the (attacker-chosen) payload legitimately originated from the victim shop.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```
