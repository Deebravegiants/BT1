### Title
Webhook `shop` (tenant) identifier is not covered by the HMAC signature, allowing cross-tenant shop spoofing on replayed webhooks - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the handler a `shop` value that is read from an HTTP header and never included in the signed material. Because a single `api_secret_key` is shared across every shop that installs a multi-tenant app, an attacker who legitimately installs the app on their own shop can capture a genuine, validly-signed webhook delivery and replay it to the app's webhook endpoint with the `shop-domain` header changed to a victim shop, producing a webhook that passes HMAC validation while claiming to originate from a different, arbitrary tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read independently from the `shopify-shop-domain` (or `x-shopify-shop-domain`) header and is not part of the signable string: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which computes the HMAC only over `to_signable_string` (i.e., the body) and compares it with `OpenSSL.secure_compare`: [3](#0-2) [4](#0-3) 

After the HMAC check succeeds, `request.shop` is forwarded unmodified into `WebhookMetadata` and passed to the app's handler as the trusted tenant identifier: [5](#0-4) 

The equality the gem implicitly relies on is: `shop-header == shop-that-signed-the-body`. In reality only `raw_body == HMAC⁻¹(secret, hmac-header)` is checked; the `shop` header is never bound to the HMAC. Since `api_secret_key` is the same for every shop using the app (it's the app's client secret, not a per-shop secret), any unprivileged user who installs the app on their own store receives legitimate webhook deliveries with a valid HMAC computed under that shared secret. They can replay the exact `raw_body`/`hmac` pair to the app's public webhook endpoint while substituting an arbitrary victim `shop-domain` header. `HmacValidator.validate` still returns `true` (it never looks at the shop header), so `Registry.process` invokes the handler believing the payload belongs to the victim shop.

### Impact Explanation
Apps built on this gem commonly use `WebhookMetadata#shop` to decide which merchant's data record to create, update, or delete (per the gem's own webhook usage docs). Because the shop identity is trusted without being cryptographically bound to the payload, an attacker-controlled webhook body can be attributed to any shop of the attacker's choosing, letting them inject or corrupt data under a victim tenant's identity — a cross-tenant access/write primitive, which the rules classify as Critical/High impact.

### Likelihood Explanation
Exploitation only requires: (1) the ability to install the app on an attacker-owned development/trial store to receive one legitimate webhook (standard, unprivileged action available to any developer/merchant), and (2) sending a single crafted HTTP POST to the app's public webhook endpoint with a substituted `shop-domain` header — no access token, `api_secret_key`, or privileged credential is needed.

### Recommendation
Include the shop domain (and other identifying headers such as `topic`/`webhook-id`) as part of the signable material verified in `to_signable_string`, or otherwise require applications to cross-check `request.shop` against a shop already known/authorized for the app before trusting it, rather than accepting the header value as-is post-HMAC-check.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and triggers/receives a genuine webhook, capturing `raw_body` (e.g. `{"id":123,...}`) and header `x-shopify-hmac-sha256: <validHmac>` (valid because `Utils::HmacValidator` only signs `raw_body` with the shared `api_secret_key`).
2. Attacker POSTs to the app's webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the HMAC — see `lib/shopify_api/utils/hmac_validator.rb` lines 26-31 and `lib/shopify_api/webhooks/request.rb` lines 35-43.
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, causing the app to process/store attacker-controlled data under the victim shop's tenant identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
