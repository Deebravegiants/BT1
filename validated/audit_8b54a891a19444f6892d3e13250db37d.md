### Title
Webhook `shop-domain` (and `topic`/`api-version`/`webhook-id`) headers are trusted for tenant identity but are not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw request body only, while the `shop`, `topic`, `api_version`, and `webhook_id` fields are read from unauthenticated HTTP headers and forwarded, unchecked, to the app's webhook handler as the tenant/context identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all pulled directly from HTTP headers with no cryptographic binding: [2](#0-1) 

`Utils::HmacValidator.validate` signs/verifies only `verifiable_query.to_signable_string`, i.e., only the raw body for webhook requests: [3](#0-2) 

`Registry.process` validates the HMAC and then, without any additional check that `request.shop` matches an expected/authorized shop, constructs `WebhookMetadata` directly from the unauthenticated `shop` header and hands it to the app's handler: [4](#0-3) 

Because the HMAC is computed with the app's single `client_secret`/`api_secret_key` shared across every shop that installs the app (not a per-shop secret), any body+HMAC pair that is valid for one shop is valid for every shop. An attacker who controls a shop that has installed the target app (a normal, unprivileged action) can capture one of their own legitimately signed webhook deliveries (same body, valid HMAC) and replay it to the app's webhook endpoint after substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header value with an arbitrary victim shop domain. `HmacValidator.validate` still passes (it only checks the body signature), so `Registry.process` dispatches the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain, spoofing the tenant identity the host application relies on to select/authorize per-shop data.

This breaks the identity binding: `shop reported to handler == shop attested by HMAC`. The HMAC attests "this body came from an app-holder using this app's secret", not "this body/shop pair came from Shopify for this specific shop", yet the gem returns the header-derived `shop` as if it were verified alongside the HMAC.

### Impact Explanation
The webhook handler receives a `shop` value that is not bound to the cryptographic proof (HMAC) at all. If the host application uses `WebhookMetadata#shop` to select which merchant's session/access token/data to act upon (a common integration pattern, and the only shop-identifying field the gem exposes from `process`), an attacker can inject arbitrary body content into another tenant's data pipeline under a forged shop identity — a cross-tenant access/data-injection primitive achieved purely by replaying a self-triggered request with a modified header, no credentials or victim access token required.

### Likelihood Explanation
Likelihood is moderate-to-high for any app that installs on multiple shops: the attacker needs only to install the target app on their own store (unprivileged), capture one webhook delivery to their own endpoint, and replay it with a modified `shop-domain` header — no secret, access token, or privileged account is needed, satisfying the "unprivileged internet user" constraint. The only mitigating factor is that success depends on the host app trusting `WebhookMetadata#shop` as an authorization boundary, which is exactly the value/shape this gem hands back from `process`.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`) claim in the HMAC-signable string for webhook requests, or otherwise verify the header-derived `shop` against an app-maintained allowlist/registration record before dispatching to the handler, so the identity asserted to handlers is provably bound to the signature that authenticated the request.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (legitimate, unprivileged action).
2. Shopify delivers a webhook to the app; attacker captures the raw body `B` and the valid `X-Shopify-Hmac-Sha256` header `H` (computed over `B` with the app's shared secret).
3. Attacker replays the exact same `B`/`H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only — passes, since `B`/`H` are unchanged: [5](#0-4) 
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, believing the (attacker-controlled) body legitimately originated from the victim shop.

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
