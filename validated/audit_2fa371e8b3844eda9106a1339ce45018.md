### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` extracts the `shop` field from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, but the HMAC signature that `Utils::HmacValidator` verifies is computed only over the raw request body. The `shop` value is never part of the signed material, so an attacker who can reuse or replay a validly-signed webhook body can attach an arbitrary `shop-domain` header and have it pass HMAC verification, causing the host application to attribute the payload to the wrong tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` header: [2](#0-1) 

Meanwhile, `Request#shop` is read straight from the header with no cryptographic binding to the body or the HMAC: [3](#0-2) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., body signature validity) before dispatching to the handler with `shop: request.shop` taken from the same untrusted header: [4](#0-3) 

The identity binding that should hold is: `shop-domain header == shop that the secret used to compute the HMAC belongs to`. Because the signable string never includes the shop domain, this equality is never enforced by the gem. Any two shops share the same `Context.api_secret_key` app-level secret (a single app's secret signs webhooks for all installed shops), so a body correctly signed with the app's secret for shop A will also verify successfully with a forged `shop-domain: shopB.myshopify.com` header. The `WebhookMetadata` passed to the handler will report `shop: "shopB.myshopify.com"` even though the payload/HMAC was generated for shop A, and host applications are documented to trust `data.shop` as the tenant identifier without any additional binding, since the gem provides no such check itself.

This matches the reported bug class pattern: a field ("shop-domain") that is acted upon (used to select the tenant record/session) but is not covered by the HMAC that is supposed to authenticate the whole request.

### Impact Explanation
This allows an attacker who obtains one legitimately-signed webhook body (e.g., by triggering an event on their own installed test store, which merchants routinely control) to relabel it as belonging to a different merchant shop by simply changing the `shop-domain` header before replaying/forwarding it to the app's webhook endpoint. Because `Registry.process` treats HMAC-body-validity as sufficient authentication and forwards the attacker-controlled `shop` value to the handler, the host application's webhook handler will process (and likely persist/act on) data under the wrong tenant's identity — a cross-tenant data-integrity/confidentiality breach (e.g., writing attacker-supplied order/customer data into another merchant's records, or triggering shop-scoped side effects for a shop the attacker does not control).

### Likelihood Explanation
Exploitability requires: (1) the app's webhook endpoint is exposed to raw HTTP requests (standard deployment), (2) the attacker can generate at least one validly HMAC-signed body under the app's shared secret — trivially possible if the attacker's own shop has the app installed and receives real webhooks, and (3) the attacker can replay/forge the header. Because `api_secret_key` is a single per-app secret shared across all installed shops (not a per-shop secret), any merchant using the app can produce a validly-signed request and merely swap the shop header to target another tenant. No access token or victim credentials are required. This is a High-likelihood, low-effort exploitation path fully within the unprivileged-internet-user threat model, since the only "privilege" needed is installing the app on one's own store.

### Recommendation
Include the trusted shop-domain header (and other identity-bearing headers such as `topic`/`webhook-id` if relevant) as part of the signable string in `Request#to_signable_string`, or otherwise cryptographically bind `shop` to the payload before it is trusted downstream (e.g., require host apps to cross-check `shop` against a shop known to be currently installed via a separately verified channel, or extend `HmacValidator` to fail verification when the header-derived shop does not match an expected/allow-listed set). At minimum, document loudly that `data.shop` from `WebhookMetadata` is not authenticated and must not be used as the sole tenant selector without additional verification (e.g., cross-referencing against an active `Session` keyed by an independently-authenticated shop domain).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the valid raw body `B` and its correctly computed `hmac-sha256` header `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker sends a POST to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256`: `H` (unchanged, still valid because `to_signable_string` only depends on `B`)
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com` (forged)
3. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `HMAC(secret, B) == H`, which is unaffected by the header change: [5](#0-4) 
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb`, lines 188-199) dispatches to the app's handler with `shop: "victim-shop.myshopify.com"`, even though the payload was never generated for or by that shop, resulting in cross-tenant data being processed under the wrong tenant identity.
