### Title
PoA bridge withdrawal status matches only by `assetId`, causing cross-withdrawal txHash misreporting for batched same-asset withdrawals to different destinations - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` resolves the destination-chain status of a specific withdrawal solely via `findMatchingWithdrawal`, which matches API entries only by `nep141:${w.data.near_token_id} === assetId`, completely ignoring `WithdrawalIdentifier.index`, `withdrawalParams.amount`, and `withdrawalParams.destinationAddress`. When a single NEAR intent transaction contains two or more PoA withdrawals of the same token to different destinations/amounts, every `watchWithdrawal` call for that token returns the array's first matching entry, so distinct withdrawals can be reported as sharing the same (wrong) destination txHash.

### Finding Description
The equality the code is supposed to guarantee is: for withdrawal `i` with `wid.index = i`, `wid.withdrawalParams.amount = A_i`, `wid.withdrawalParams.destinationAddress = D_i`, the returned `withdrawal.data.transfer_tx_hash` must correspond to the on-chain transfer that actually paid `A_i` to `D_i`. Instead, `findMatchingWithdrawal` in [1](#0-0)  only checks `nep141:${w.data.near_token_id} === assetId` and returns `withdrawals.find(...)`, i.e. the first array entry with the same token, with no participation of `amount`, `destinationAddress`, or `index`. `describeWithdrawal` then directly returns that entry's `transfer_tx_hash` as the completed status: [2](#0-1) .

`watchWithdrawal` in `withdrawal-watcher.ts` calls `describeWithdrawal` per `WithdrawalIdentifier` independently, with no shared consumption/removal state across calls, so multiple calls for the same `assetId` but different `index`/`amount`/`destinationAddress` can all resolve against the same first-matching API entry: [3](#0-2) .

The batching path that constructs these identifiers, `createWithdrawalIdentifiers`, assigns `index` per-bridge in array order but performs no validation rejecting duplicate `assetId` entries with distinct destinations/amounts within the same batch: [4](#0-3) . The public batch withdrawal API (`sdk.processWithdrawal`/`signAndSendWithdrawalIntent`/`waitForWithdrawalCompletion`) explicitly documents and tests arbitrary batches of `WithdrawalParams[]`, including duplicated params, without asset-uniqueness constraints: [5](#0-4) .

The bug is explicitly acknowledged in the code's own comment ("multiple withdrawals of the same token in a single transaction are not supported") but this is only a comment — there is no runtime guard, validation, or rejection preventing an unprivileged user from constructing exactly such a batch, and no code sorts/reconciles by amount as the comment suggests a fix might: [6](#0-5) . The identical unmitigated pattern also exists in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`: [7](#0-6) .

None of `validateAddress`, `compareAddresses`, or `validateWithdrawal` (in `poa-bridge.ts`) prevent this, because they validate each withdrawal individually before submission — they do not check for cross-withdrawal collisions on `assetId` within a batch, and they run before the intent is even signed, long before `describeWithdrawal` executes.

### Impact Explanation
An integrator that relies on the SDK's per-withdrawal `txHash`/`status` result to reconcile which destination address was paid can be given a `txHash` that actually corresponds to a different destination/amount within the same batch. This is a status/hash misreport that can cause an integrator to credit the wrong account, or credit/refund based on incorrect proof-of-payment, matching the High-severity category "a status or hash misreport making an integrator credit or refund twice." It does not itself move funds to the wrong destination (that's determined by the intent itself, and the actual on-chain PoA transfer still pays the correct amounts to the correct addresses) — the flaw is purely in the SDK's reporting/reconciliation of which address's payment corresponds to which watcher's result.

### Likelihood Explanation
Preconditions: (1) an integrator uses batch withdrawals of the same `assetId` (same token) to different destination addresses/amounts within one intent — a supported, documented, tested SDK feature; (2) the PoA bridge backend actually processes and returns multiple entries for the same NEAR tx hash and token. The code comment states the POA API "doesn't currently support this case either," meaning it's uncertain whether the backend, in practice, returns multiple distinct entries for same-token batched withdrawals today — this is an external precondition outside SDK control and not verifiable from this repo alone. If the backend does start supporting or already partially supports multi-entry same-token responses, the SDK-side matching bug is immediately and repeatably exploitable by any ordinary user, at zero additional cost, on every batch of same-token withdrawals to different destinations.

### Recommendation
Extend `findMatchingWithdrawal` to disambiguate among same-`assetId` entries using additional discriminators returned by the POA API (e.g. `amount`, `destination_address`, or an ordering key), or track already-consumed entries across sibling `describeWithdrawal` calls in the same batch (e.g. pass previously-matched entries as an exclusion set) so that two `WithdrawalIdentifier`s with the same `assetId` cannot resolve to the same API entry. Until the backend supports disambiguation, either reject/validate against constructing batches with duplicate `assetId`+different destination/amount combinations for the PoA route in `createWithdrawalIdentifiers`/`supports`/`validateWithdrawal`, or surface an explicit unsupported-batch error rather than silently returning a possibly-wrong `txHash`.

// vitest, mocking only the HTTP call poaBridge.httpClient.getWithdrawalStatus
it("misreports txHash across duplicate-assetId batched withdrawals", async () => {
  vi.spyOn(poaBridge.httpClient, "getWithdrawalStatus").mockResolvedValue({
    withdrawals: [
      { status: "COMPLETED", data: { near_token_id: "btc.omft.near", transfer_tx_hash: "hashB", amount: "50000", address: "B" } },
      { status: "COMPLETED", data: { near_token_id: "btc.omft.near", transfer_tx_hash: "hashA", amount: "100000", address: "A" } },
    ],
  });

  const bridge = new PoaBridge({ envConfig, xrplRpcUrls: [] });

  const statusIndex0 = await bridge.describeWithdrawal({
    landingChain: Chains.Bitcoin,
    index: 0,
    withdrawalParams: { assetId: "nep141:btc.omft.near", amount: 100000n, destinationAddress: "A", feeInclusive: false },
    tx: { hash: "shared-tx", accountId: "user.near" },
  });

  const statusIndex1 = await bridge.describeWithdrawal({
    landingChain: Chains.Bitcoin,
    index: 1,
    withdrawalParams: { assetId: "nep141:btc.omft.near", amount: 50000n, destinationAddress: "B", feeInclusive: false },
    tx: { hash: "shared-tx", accountId: "user.near" },
  });

  // Broken equality: both resolve to the FIRST array entry (hashB, amount=50000, address=B),
  // even though index 0's params specify amount=100000/address=A.
  expect(statusIndex0).toEqual({ status: "completed", txHash: "hashB" }); // WRONG: should be hashA
  expect(statusIndex1).toEqual({ status: "completed", txHash: "hashB" }); // both collide on same entry
});

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
