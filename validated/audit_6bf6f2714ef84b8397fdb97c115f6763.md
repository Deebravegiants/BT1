### Title
Webhook Shop/Topic Identity Not Covered by HMAC Signature Allows Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC of the raw request body, but then dispatches the webhook using the `shop`, `topic`, `webhook_id`, and `api_version` values taken straight from unauthenticated HTTP headers. Because the HMAC signature only covers `raw_body` and not these headers, any party capable of producing (or capturing) one validly-signed webhook body can re-submit it with a forged `shop-domain` header, causing the host application to process the webhook as if it originated from a different, victim tenant.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors read directly from HTTP headers that are never part of the signed data: [2](#0-1) .

`Registry.process` validates only this body HMAC via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.topic` to select the handler and `request.shop` to build the `WebhookMetadata` passed to the handler: [3](#0-2) .

`HmacValidator.validate` computes/compares the signature only against `verifiable_query.to_signable_string`, i.e., the raw body: [4](#0-3) .

This breaks the intended binding: **shop-that-signed-the-body == shop-attributed-to-the-webhook**. The HMAC only proves "this body was produced by someone who knows `api_secret_key`," it proves nothing about which shop header should accompany that body. The `shop-domain`, `topic`, and `webhook_id` headers are fully attacker-controlled bytes that are "verified" only in the sense that they exist (presence check), not that they are authentic: [5](#0-4) .

### Impact Explanation
An attacker who operates their own legitimate installed shop (an unprivileged actor with respect to any other merchant's tenant) receives real Shopify webhooks with valid HMAC signatures for their own shop's events. Because the signature covers only the JSON body, the attacker can replay that exact body to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with a victim shop's domain. `Registry.process` will validate the (still-correct) body HMAC and then hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop — a cross-tenant confusion where actions, side effects, or stored state end up attributed to a shop the attacker does not control and has no authorization over. This crosses the tenant boundary the gem is meant to enforce, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires: (1) the attacker's own legitimate app installation (any merchant/dev store can obtain this), (2) capturing one webhook delivery to their own endpoint or proxy, and (3) resending it with a modified header field, which is trivial HTTP tampering. No knowledge of `api_secret_key` or any victim credential is required.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed material, or otherwise verify it out-of-band before trusting it: e.g., include the `shop-domain` header value in the signable string that is HMAC-verified, or require the caller to independently confirm that `request.shop` corresponds to a shop with a currently valid, previously-established session before invoking the handler. At minimum, document loudly that `request.shop`/`request.topic` are unauthenticated and must not be trusted for authorization decisions — but since this gem is precisely the trust boundary consumers rely on, the safer fix is to cover these fields with the HMAC check.

### Proof of Concept
1. Attacker's own shop `attacker.myshopify.com` has the app installed; Shopify delivers a legitimate webhook, e.g. `orders/create`, to the app's endpoint with headers:
   - `x-shopify-hmac-sha256: <valid-signature-of-raw-body>`
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-topic: orders/create`
   - body: `{"id":123,...}`
2. Attacker intercepts/replays this exact request but changes only the header:
   - `x-shopify-shop-domain: victim.myshopify.com`
   (raw body and HMAC signature are left untouched, since they don't depend on the header)
3. The app's endpoint calls `ShopifyAPI::Webhooks::Registry.process(request)`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks `raw_body` against `api_secret_key` — the signature is unaffected by the header swap: [6](#0-5) .
5. `request.shop` now returns `"victim.myshopify.com"`, and the handler receives `WebhookMetadata` attributing the attacker's order payload to the victim shop: [7](#0-6) .

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

          end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
