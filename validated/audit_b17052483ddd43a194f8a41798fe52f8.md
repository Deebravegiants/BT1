### Title
Webhook `shop` (and `topic`) identity is trusted without being covered by the HMAC signature, enabling cross-tenant webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` authenticates nothing but the byte content of `@raw_body`. The `shop` (and `topic`) values that `Webhooks::Registry.process` subsequently hands to the host application's handler are read straight from unauthenticated HTTP headers and are never bound into the HMAC check.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
returning only `@raw_body`. `Request#shop` and `Request#topic` are pulled from the `shopify-shop-domain` / `shopify-topic` headers: [2](#0-1) 

`HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e. body only) and compares it with `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` uses this body-only HMAC check as the sole authentication gate, then immediately trusts the header-derived `shop`/`topic` and forwards them to the app's handler: [4](#0-3) 

The binding that should hold is:
`hmac_valid(body) == true` should imply `shop == the shop the body actually belongs to`.
Instead the code only proves `hmac_valid(body) == true`; `shop` is an independent, attacker-controlled header value never mixed into the signed material. Because Shopify's webhook payloads for many topics are small and often identical in content across different shops for the same topic/state (e.g. minimal `{}` or template-shaped bodies for topics such as `app/uninstalled`), an attacker who owns *any* shop (including a free/dev store) can legitimately receive a Shopify-signed `(body, hmac)` pair for that topic, then replay the identical bytes to the app's webhook endpoint while substituting a victim shop's domain in the `shopify-shop-domain` header. `HmacValidator.validate` still returns `true` (the body bytes and secret are unchanged), and `Registry.process` calls the handler with `shop: <victim-shop>`, causing the host application to perform shop-scoped side effects (e.g. mark the victim shop uninstalled, wipe/cancel data, invalidate sessions) attributed to a tenant the attacker does not control.

### Impact Explanation
This breaks the tenant boundary the HMAC check is supposed to enforce: an unprivileged actor who can trigger any legitimately-signed webhook for their own shop can cause the same signed payload to be processed as if it belonged to a different, victim shop, since `shop` is not bound to the signature. This is a cross-tenant access primitive achieved without possession of the app's `client_secret`/`api_secret_key`, satisfying the "cross-tenant access" High/Critical impact bar.

### Likelihood Explanation
Requires only: (1) an attacker-controlled/free Shopify store capable of installing the target app to generate one legitimately HMAC-signed webhook, and (2) the ability to send an arbitrary HTTP POST to the target app's public webhook endpoint with a modified `shopify-shop-domain` header (trivial for any internet client, no credentials needed). Success additionally depends on the webhook body being identical/predictable across shops for a chosen topic, which is plausible for several low-cardinality topics.

### Recommendation
Bind the `shop` (and `topic`, `webhook_id`) values into the material that is HMAC-verified, or otherwise cryptographically tie the claimed shop to the signed body (e.g., include shop domain in the signable string, or validate that the shop domain in the header matches a shop known to have installed the app and require additional shop-specific verification) before dispatching to handlers.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook topic whose body is constant/predictable (e.g. `app/uninstalled`, body `{}`).
2. Attacker's endpoint captures the legitimate headers, including `x-shopify-hmac-sha256: <H>` computed by Shopify over body `{}`.
3. Attacker replays a POST to the same webhook endpoint with body `{}`, header `x-shopify-hmac-sha256: <H>` unchanged, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which returns `true` because it only checks `H` against `HMAC(secret, "{}")`, per [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and performs the topic's associated action against the victim tenant.
