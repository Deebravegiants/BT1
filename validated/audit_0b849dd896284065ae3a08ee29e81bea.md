### Title
Fee-on-transfer input tokens inflate escrow accounting in the Tron `IntentGatewayV2.placeOrder`, causing escrow insolvency - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron fork of `IntentGatewayV2.placeOrder` escrows input tokens by writing `reducedInputs[i].amount` (derived from the user-specified `order.inputs[i].amount` minus protocol fee) into `_orders[commitment][token]`, without ever measuring the actual token balance the contract received from the `safeTransferFrom` call. For fee-on-transfer ERC20 input tokens, the contract will hold strictly less than the amount it records as escrowed, exactly analogous to the reported Allo.sol `poolAmount` mismatch.

### Finding Description
In the direct (no-predispatch) escrow path: [1](#0-0) 
the contract calls `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally credits `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` is computed from the nominal `order.inputs[i].amount` at lines 362-370, not from any observed balance delta.

The predispatch-sweep path has the same defect: it uses `balance = IERC20(token).balanceOf(dispatcher)` before the sweep, transfers that "balance" out via a raw `transfer` call, but never re-checks what `address(this)` actually received after the sweep transfer — and still credits escrow with `reducedInputs[i].amount` (nominal), not the post-sweep observed balance: [2](#0-1) 

This is a functional regression relative to the primary (non-Tron) `IntentGatewayV2.sol`, which was explicitly hardened against this exact bug class by measuring `balanceOf` before/after every transfer and mutating `order.inputs[i].amount` to the actually-received amount before computing fees/commitment/escrow: [3](#0-2) 
That the project has dedicated regression tests (`testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, `testPlaceOrder_FeeOnTransferToken_WithProtocolFee`) confirms fee-on-transfer input tokens are an anticipated, in-scope threat model for `IntentGatewayV2`: [4](#0-3) 
The Tron variant, however, has no equivalent balance-delta measurement or corresponding tests, so it silently reintroduces the vulnerability for that deployment target.

### Impact Explanation
`_orders[commitment][token]` is the ledger the contract relies on to know how much of a given token is escrowed for a commitment; withdrawal/refund/redemption logic pays out based on this stored value (see the shared `_withdraw` pattern in `IntentsBase.sol` which decrements `_orders[body.commitment][token]` and transfers `amount` to the beneficiary): [5](#0-4) 
If the recorded escrow for a commitment exceeds the tokens the contract actually received (due to a fee-on-transfer input token), the contract's real token balance becomes insufficient to honor all outstanding escrow claims across all commitments sharing that token. This can cause reverts (denial of service on legitimate cancellations/redemptions) once the shared token pool is depleted, and in the worst case allows one inflated-escrow commitment to be paid out using tokens that were actually deposited by other users' orders, since ERC20 balances are fungible and not segregated per commitment on-chain — a cross-order fund-safety/insolvency issue.

### Likelihood Explanation
Any user or solver can trigger this by placing an order (`placeOrder`) whose input token is a fee-on-transfer (or otherwise deflationary/rebasing-on-transfer) ERC20 — no privileged role is required, and the path is reachable from a single ordinary transaction. Given intents/solver systems commonly need to support arbitrary listed ERC20s, this is a realistic, unprivileged attack surface for the Tron deployment.

### Recommendation
Mirror the fix already applied in `evm/src/apps/IntentGatewayV2.sol`: measure `IERC20(token).balanceOf(address(this))` (or `balanceOf(dispatcher)` for the predispatch sweep) before and after each transfer, use the actual received delta to compute `reducedInputs`/escrow amounts and the commitment hash, and only credit `_orders[commitment][token]` with the amount actually held by the contract.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g., 1% fee, as in `FeeOnTransferToken` used in the same-chain tests) and use it as `order.inputs[0].token` with `amount = 1000e18`.
2. Call `placeOrder` on the Tron `IntentGatewayV2`: `safeTransferFrom(msg.sender, address(this), 1000e18)` executes, but the contract only receives `990e18` due to the token's transfer fee.
3. `_orders[commitment][token]` is nonetheless credited with `reducedInputs[0].amount` computed from the nominal `1000e18` (minus protocol fee if any) — e.g., `1000e18` (or `997e18` with a 30bps protocol fee) — while the actual contract balance for that token increased by only `990e18`.
4. Repeat with additional orders sharing the same fee-on-transfer token; the aggregate `_orders[...][token]` values across commitments will exceed the contract's actual token balance, so a later `RedeemEscrow`/refund `safeTransfer` will fail with insufficient balance for the last claimant(s), or, depending on redemption order, allow one commitment's payout to consume tokens that were actually contributed by another commitment.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
