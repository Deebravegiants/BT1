## Analog Found

### Title
Relayer fees permanently locked when accrued to a contract-controlled delivery address that cannot produce the private-key signature `withdraw_fees`/`accumulate_fees` require - (File: `modules/pallets/relayer/src/withdrawal.rs`, `modules/pallets/relayer/src/accumulate.rs`)

### Summary
`pallet-ismp-relayer` credits delivery fees to whatever raw address is proven to have delivered a message on the destination chain (`RequestReceipts[commitment]`), exactly the way the Footium report ties prizes to "whoever holds the asset at snapshot time." The only way to ever move that balance — `withdraw_fees`, or the beneficiary-redirect path inside `accumulate_fees` — requires a raw ECDSA/sr25519/ed25519 signature that recovers to that exact credited address. If the credited address is a smart contract (multisig, relayer-automation contract, forwarder/proxy used to submit `handlePostRequests`) rather than an EOA, no such signature can ever be produced, and the accrued fee balance is permanently frozen with no rescue path.

### Finding Description
Fees are accrued per delivering address, not per any reassignable/ownable entity: [1](#0-0) 

`decode_receipt_relayer` pulls this address straight out of the destination chain's on-chain receipt — for EVM, the RLP-encoded `msg.sender` recorded by `EvmHost.dispatchIncoming(request, _msgSender())`: [2](#0-1) 

That `_msgSender()` is simply whoever called `HandlerV2.handlePostRequests`/`handleGetResponses` — `batchCall` even uses `delegatecall` to preserve the original caller, so a relayer operating through any contract wallet (multisig, gas-abstraction forwarder, automation bot contract) becomes the credited "relayer" address: [3](#0-2) 

The fee then accumulates into `Fees::<T>` keyed by that contract's raw address bytes: [4](#0-3) 

The **only** two exits for that balance both require a raw private-key signature recovering to exactly that credited address, with no EIP-1271/owner/multisig fallback:

- `withdraw()` verifies `Signature::Evm/Sr25519/Ed25519` against `address` before ever looking at the beneficiary: [5](#0-4) 

- The in-`accumulate` "beneficiary redirect" also requires a signature that must recover to `delivery_address` (i.e. still requires the contract to sign): [6](#0-5) 

A contract address has no private key, so `signature.verify(...)` can never recover to it. There is no admin/governance rescue function anywhere in `pallet-ismp-relayer` for a stuck per-address `Fees` balance (only per-chain config knobs like `MinimumWithdrawalAmount`/`OutboundConsensusDeliveryReward` exist) — this exactly mirrors the reported class: an entitlement is bound to a fixed "account" observed on-chain at accrual time, that account can legitimately be a contract without any way to invoke the claim function, and the protocol never anticipated that possibility, so the funds are permanently locked.

### Impact Explanation
Relayer fees legitimately earned for real message deliveries become permanently unclaimable and stuck in `pallet-ismp-relayer` storage forever, with no recovery mechanism. This is a direct freezing-of-funds bug reachable purely by normal relayer operation (submitting a delivery transaction from a smart-contract-controlled account), not by any admin/governance misbehavior.

### Likelihood Explanation
Running relay infrastructure behind a contract wallet (Safe multisig for key custody, Gelato/Defender-style relayer forwarders, or any automation/batching contract) is a common, entirely non-malicious operational pattern for relayer operators, and nothing in the dispatch/accrual path checks whether the credited address is an EOA before crediting fees to it. The freeze triggers the first time such an operator relays even a single message.

### Recommendation
Support an EIP-1271-style / owner-authorization claim path for contract-controlled delivery addresses (verify a signature from the contract's designated owner/signer against the contract, similar to how `SolverAccount.isValidSignature` is handled elsewhere in this codebase), or require/validate at accrual time that the delivering address is capable of later authorizing a withdrawal, or add a governance-gated rescue extrinsic for balances stuck under a non-EOA `Fees` key.

### Proof of Concept
1. Relayer operator deploys/uses a smart-contract wallet `C` (e.g. a Safe) as the transaction sender for destination-chain delivery.
2. `C` calls `HandlerV2.handlePostRequests` (directly or via `batchCall`, which delegatecalls and preserves `msg.sender == C`); `EvmHost.dispatchIncoming` records `C` as the relayer in `RequestReceipts[commitment]`.
3. Anyone later calls `pallet-ismp-relayer::accumulate_fees` with the source/dest proofs; `decode_receipt_relayer` extracts `C`'s address; `Fees::<T>::insert(state_machine, C, fee)` credits `C`.
4. No one can now call `withdraw_fees` (or the `accumulate_fees` beneficiary-redirect) successfully for `C`, because `Signature::verify` can never recover `C`'s address from any ECDSA/sr25519/ed25519 signature — `C` has no private key.
5. The fee balance under `Fees::<T>::get(state_machine, C)` remains permanently non-zero and unspendable; there is no other extrinsic in the pallet that can move it out.

		match state_id {
			s if crate::is_pharos(&s) =>
				if raw.len() == 32 {
					Ok(Address::from_slice(&raw[12..]).0.to_vec())
				} else {
					Err(Error::<T>::ProofValidationError)
				},
			s if s.is_evm() => {
				use alloy_rlp::Decodable;
				Ok(Address::decode(&mut &*raw)
					.map_err(|_| Error::<T>::ProofValidationError)?
					.0
					.to_vec())
			},

						.map_err(|_| Error::<T>::SignatureDecodingError)?
						.signer()
				} else {
					bytes
				})
			},
			_ => Err(Error::<T>::MismatchedStateMachine),
		}
