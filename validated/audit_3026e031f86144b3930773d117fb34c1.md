## Title
Webhook shop/topic attribution is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw body only, while the shop domain, topic, and webhook id are read from unauthenticated HTTP headers and then handed to the app's webhook handler as trusted identity data. The equality the code assumes — `hmac_signature == HMAC(shop || topic || body)` — actually only holds for `HMAC(body)`; `shop` and `topic` are never covered.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read straight from headers, unauthenticated: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then forwards `request.shop` and `request.topic` (both header-derived) into `WebhookMetadata` for the app's handler to act on: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`, i.e. the body, using the shared `api_secret_key` (which is the same for every shop that installs the app): [4](#0-3) 

Because the same `api_secret_key` signs webhooks for every merchant that installs the app, and the signature never covers `shop-domain`/`topic`, any party who can obtain one valid `(raw_body, hmac)` pair — trivially, by installing the app on their own store and capturing a webhook Shopify sends them — can replay that exact body to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for a victim shop. `HmacValidator.validate` will report the request as authentic, and `Registry.process` will hand the attacker-chosen `shop` value to the app's handler as if it were verified. This breaks the identity binding `verified_bytes == acted_upon_bytes`: only the body is verified, but `shop`/`topic` are acted upon.

### Impact Explanation
This is a cross-tenant boundary break: an unprivileged attacker who is merely a legitimate (or trial) installer of the app on their own shop can forge webhook deliveries that the app attributes to any other shop of their choosing, since the shop identifier used for tenant routing/storage is never included in the authenticated payload. Any host application that uses `WebhookMetadata#shop` to key persistence, trigger shop-scoped side effects, or make trust decisions is exposed to injected/misattributed data for a shop the attacker does not control.

### Likelihood Explanation
Any developer account can install the app to receive real, validly-signed webhooks and observe `(body, hmac)` pairs for their own store. Because the HMAC secret (`api_secret_key`) is shared across all shops using that app, no shop-specific secret exists to prevent this replay-with-relabeled-header trick, and the gem does no cross-check between the header-provided `shop`/`topic` and the signed content. This requires no credential theft or privileged access — only that the attacker install the app once.

### Recommendation
Bind the trust-relevant identifiers into the verified data before acting on them: either have `to_signable_string` incorporate `shop`, `topic`, and `webhook_id`, or independently verify (e.g., against known-registered shop sessions before accepting) that the header-derived `shop` in `WebhookMetadata` matches expectations before dispatching to handlers. At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are not covered by the HMAC and must not be trusted for tenant attribution without additional verification (e.g., cross-checking against an existing, previously-authenticated session for that shop).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Shopify sends a real webhook to the app: body `B`, headers include `x-shopify-hmac-sha256: H` (computed as `HMAC(secret, B)`), `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`.
3. Attacker replays the exact same request to the app's webhook endpoint but changes `x-shopify-shop-domain` to `victim.myshopify.com` (and/or changes `x-shopify-topic`), leaving `B` and `H` untouched.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — this still passes. [5](#0-4) 
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: B, ...)` as if Shopify itself had certified this data for `victim.myshopify.com`, even though the victim shop never sent or received this webhook.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
