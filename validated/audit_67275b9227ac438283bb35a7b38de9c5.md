Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before invoking the app's handler with `WebhookMetadata`, whose `shop` field is documented as "The shop domain of the webhook." [1](#0-0)  In practice, the HMAC signature only ever covers the raw request body, while `topic`, `shop`, `api_version`, and `webhook_id` are all read directly from unauthenticated HTTP headers.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [2](#0-1)  and `#shop`, `#topic`, `#api_version`, `#webhook_id` are all pulled straight from the `shopify-*`/`x-shopify-*` HTTP headers with no cryptographic binding to that value: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature purely over `verifiable_query.to_signable_string` (i.e., only the body) and compares it to the `hmac-sha256` header: [4](#0-3)  `Registry.process` calls this validator, and on success forwards `request.shop` (the unauthenticated header value) into `WebhookMetadata`, which the app handler is expected to trust as the tenant identity: [5](#0-4) [6](#0-5) 

This breaks the identity binding: `shop_verified_by_HMAC` (nothing — the shop is never part of the signed content) should equal `shop_used_as_tenant_key` (`request.shop`, from the `shopify-shop-domain` header). Since the header is entirely outside the signed payload, `HMAC-valid(body)` does not imply `shop-domain-authentic`.

### Impact Explanation
An unprivileged internet user can install the app on their own attacker-controlled shop, receive one legitimately Shopify-signed webhook (valid `hmac-sha256` over the body, generated using the real `api_secret_key` they never need to know), and then replay that exact same `raw_body` + `hmac-sha256` header pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` will still pass, because it never inspects the domain header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the (forged) victim shop. Any app that uses `data.shop` (as shown in the gem's own recommended handler example, `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) to select which tenant's records to update, delete, or redact — including the mandatory `customers/redact` / `shop/redact` topics — will act on the wrong tenant, producing cross-tenant data corruption or exposure. This qualifies as Critical (cross-tenant access) since the platform's own documented model presents `WebhookMetadata.shop` as reliable and authenticated.

### Likelihood Explanation
Reasonably likely to be exploitable, but not trivial: the attacker needs at least one webhook delivered for a topic/body of interest that is also relevant/replayable against a victim (e.g., generic topics like `app/uninstalled` or a `products/update` whose body doesn't reference shop-specific IDs would be easiest; topics whose body content embeds shop-identifying data are harder to abuse for meaningful impact). The attacker fully controls when to trigger webhooks on their own shop (e.g., by installing the app and performing actions), giving them practically unlimited opportunities to harvest valid `(body, hmac)` pairs and replay them with a forged domain header, requiring no secrets and no privileged account.

### Recommendation
Bind the `shop` (and ideally `topic`/`api_version`/`webhook-id`) into the HMAC-verified payload, or independently verify that the shop advertised in the header corresponds to a shop that is actually known/installed and matches session state expected for that webhook_id. At minimum, document prominently that `WebhookMetadata.shop` is NOT covered by the HMAC check and must not be used as a sole tenant-authorization signal without additional server-side verification (e.g., cross-checking against the shop stored for a previously issued `webhook_id`/subscription, or validating shop format/installation state before trusting it).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and registers/receives a webhook (e.g., `products/update`) for a resource whose JSON body carries no attacker-identifying data.
2. Attacker captures the full raw HTTP request, including `raw_body`, `X-Shopify-Hmac-Sha256`, `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, and `X-Shopify-Api-Version` headers.
3. Attacker replays the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value to the same app endpoint, but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses this as valid (`to_signable_string` returns the unmodified `raw_body`), `Utils::HmacValidator.validate` succeeds because the body/hmac pair is untouched, and `Registry.process` invokes the app handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`.
5. Any handler logic keyed off `data.shop` (per the gem's own documented example) now operates as if this event genuinely originated from the victim shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
