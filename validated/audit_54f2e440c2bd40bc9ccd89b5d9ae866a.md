### Title
Crafted swap route can add an unauthorized token transfer to the caller’s signed authorization tree - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
Controller swap strategies accept caller-supplied opaque `swap` bytes and execute them through the configured router after authorizing only the controller’s own input-token transfer. Because route-selected third-party code runs below the caller-authorized controller invocation, a malicious route can cause simulation to record an additional `token.transfer(caller, attacker, amount)` as a child of the caller’s authorization. If the caller signs that poisoned tree, unrelated wallet funds are transferred while the controller still observes a valid swap result.

### Finding Description
`swap_tokens` validates only that `swap` is non-empty, snapshots controller balances, authorizes one exact `token_in.transfer(controller, router, amount_in)`, invokes `router.execute_strategy`, then checks controller-side spend and output deltas. It does not validate which contracts the route may invoke or constrain the caller’s resulting authorization tree to the expected strategy flow. [1](#0-0) [2](#0-1) 

An attacker can provide a victim with a crafted route containing a malicious venue contract. During simulation, that venue calls `transfer(victim, attacker, amount)` on an unrelated token held by the victim. Soroban records the transfer beneath the victim’s controller authorization entry. A wallet or integration that signs the simulated tree without rejecting unexpected children authorizes the theft. The regression test demonstrates this exact behavior through `swap_collateral`: recording mode produces a `swap_collateral` root containing the rogue token transfer, and enforced auth succeeds only when that malicious child is signed. [3](#0-2) [4](#0-3) 

### Impact Explanation
Theft of user funds. The stolen amount is not limited to the strategy input, collateral position, or protocol-listed assets; any token spendable by the victim can be transferred if the malicious child authorization is signed. The test steals an unlisted wallet-token balance while leaving the victim with the expected swap output, showing that output and health checks do not bound the loss. [5](#0-4) 

### Likelihood Explanation
Likelihood is Medium. Exploitation requires delivering a crafted route to a victim and having the victim’s signing path accept the extra authorization child. The victim must authorize a reachable strategy such as `swap_collateral`, but no privileged role, compromised key, oracle manipulation, or protocol upgrade is required. The issue specifically affects signing flows that trust simulation output rather than independently enforcing that the authorization tree contains only expected calls. [6](#0-5) [7](#0-6) 

### Recommendation
Constrain route execution or authorization shape so route-selected code cannot add caller-authenticated sub-invocations. At minimum, document and enforce in all client paths that a controller strategy authorization must contain no unexpected child entries; reject any simulated tree containing token transfers other than the explicitly expected user-to-protocol pulls. Prefer a router/venue allowlist or route commitment that prevents arbitrary contracts from executing under the caller’s authorization context.

### Proof of Concept
The repository contains a deterministic proof in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

1. `UnlistedPoolRouter::execute_strategy` decodes the route and invokes the route-selected `hop_pool`. [8](#0-7) 
2. `RogueHopPool::swap` calls `wallet_token.transfer(victim, attacker, amount)`. [9](#0-8) 
3. The victim calls `swap_collateral` with that route. [10](#0-9) 
4. Simulation records the malicious token transfer under the victim’s `swap_collateral` authorization root and moves the victim’s entire unrelated wallet balance. [11](#0-10) 
5. Under enforcing auth, the same transfer succeeds when the poisoned simulated child is signed. [4](#0-3)
