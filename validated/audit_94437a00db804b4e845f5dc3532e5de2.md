### Title
Direct token transfers to `amm_coin_vault`/`amm_pc_vault` allow a deposit/withdraw sandwich that steals value from existing LPs - (File: `program/src/processor.rs`)

### Summary
`process_deposit` and `process_withdraw` compute the pool's true reserves via `Calculator::calc_total_without_take_pnl_no_orderbook`, which is fed the *live* SPL token balances of `amm_coin_vault` and `amm_pc_vault` read straight off-chain state, not an internally tracked, donation-resistant ledger. Because these vault accounts are ordinary SPL token accounts, anyone can `Transfer` tokens into them directly, instantly inflating the reserves used to price LP shares — this is functionally identical to `LendingPool.sol::donateToTranche()` bumping `realisedLiquidityOf[tranche]` directly. An attacker can sandwich any such balance-increasing transfer with a `Deposit` immediately before and a `Withdraw` immediately after to capture a disproportionate share of the injected value at the expense of existing LPs.

### Finding Description
In `process_deposit`, reserves are computed from the vaults' current SPL balances: [1](#0-0) 
and this `total_coin_without_take_pnl` / `total_pc_without_take_pnl` value directly determines the deposit exchange rate and minted LP amount: [2](#0-1) 

In `process_withdraw`, the same live-balance recomputation is used to price the LP redemption: [3](#0-2) 
and the payout is a straight pro-rata share of that (now inflated) total: [4](#0-3) 

Because `amm_coin_vault`/`amm_pc_vault` are regular SPL token accounts owned by the program's `$authority` PDA (no deposit-only gate on the destination), any signer can execute a standard SPL `Transfer` instruction that credits tokens to these vaults outside of the `Deposit` instruction path — exactly the "donation" primitive described in the report, except here it requires no bespoke `donateToTranche`-style function at all; a bare token transfer suffices. Since neither `process_deposit` nor `process_withdraw` distinguishes tokens that arrived via the sanctioned `Deposit` flow from tokens that arrived via a raw transfer, an attacker can:
1. Front-run: call `Deposit` to acquire LP tokens at the pre-injection exchange rate.
2. Wait for (or itself trigger, in a two-transaction sequence) tokens landing directly in the vault (e.g., fee sweeps, external settlements, or any other party's transfer).
3. Back-run: call `Withdraw`, redeeming LP tokens; `calc_total_without_take_pnl_no_orderbook` now reflects the inflated vault balance, so the attacker's redemption includes a pro-rata slice of value it never contributed, diluting all other LP holders — the direct analog of the sandwiched `donateToTranche()` call increasing `realisedLiquidityOf[tranche]` just before an attacker's `redeem()`.

### Impact Explanation
Existing LP holders lose a portion of any funds credited to the pool vaults outside the standard `Deposit` accounting, because reserve calculations in both `Deposit` and `Withdraw` (and the swap PNL-taking path, which uses the identical `calc_total_without_take_pnl_no_orderbook` call) trust the vault's raw SPL balance. Any legitimate value added to the vaults (e.g., manual reconciliation, protocol operations, or accidental transfers) becomes a target for immediate extraction by a sandwiching attacker, resulting in a direct, unauthorized transfer of value from passive LPs to the attacker — meeting the "concrete theft of LP funds" bar.

### Likelihood Explanation
The attack requires only two ordinary, permissionless instructions (`Deposit` then `Withdraw`) that any user can already submit with attacker-chosen accounts and amounts, plus the ability to observe (via mempool/slot monitoring) an upcoming balance-increasing transfer to the vault. No privileged role, off-chain component, or SPL-token-program bug is needed — the vault accounts are open destinations for standard token transfers, and the AMM's own accounting logic (in-scope: `AmmInfo`/vault loading and PNL accounting in `processor.rs`) is what fails to distinguish sanctioned deposits from unsanctioned balance increases.

### Recommendation
Track pool reserves internally (e.g., cumulative `amm.lp_amount`-backed reserve counters updated only through `Deposit`/`Withdraw`/`Swap` code paths) instead of trusting the vault's live SPL balance for pricing, or reconcile any balance surplus into `target_orders.calc_pnl_x`/`calc_pnl_y` gradually (vesting) rather than atomically folding it into `total_*_without_take_pnl` on the very next `Deposit`/`Withdraw` call.

### Proof of Concept
1. Attacker observes (or independently causes) a token transfer that will land directly in `amm_coin_vault` or `amm_pc_vault` (destination is a normal SPL token account, no special authorization required to be the recipient of a transfer).
2. Attacker submits `Deposit` (`program/src/processor.rs` `process_deposit`, ix in `program/src/instruction.rs:171-188`) with proportional `max_coin_amount`/`max_pc_amount`, minting LP tokens at the pre-injection ratio computed at [1](#0-0) .
3. The balance-increasing transfer lands in the vault(s).
4. Attacker submits `Withdraw` (ix in `program/src/instruction.rs:190-212`); `process_withdraw` recomputes reserves from the now-inflated vault balances at [3](#0-2)  and pays out coin/pc proportional to the attacker's LP share at [4](#0-3) , giving the attacker a pro-rata cut of value it never deposited, at the expense of other LP holders.
