This confirms the vulnerability: the gem's own documentation (`docs/usage/webhooks.md:125`) explicitly states that `Registry.process` "will verify the request did indeed come from Shopify," and instructs developers to trust `data.shop` from `WebhookMetadata` (`docs/usage/webhooks.md:12-17`) without any additional shop-binding check. This is not "the host application ignoring documented API" — it's the documented API itself failing to bind `shop` to the HMAC it validates.

### Title
Webhook shop-domain spoofing due to HMAC not covering the `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , and `HmacValidator.validate` computes/verifies the HMAC solely over that signable string [2](#0-1) . The `shop`, `topic`, and `webhook_id` values are read directly from unauthenticated HTTP headers [3](#0-2) . `Registry.process` validates only the HMAC, then unconditionally routes/attributes the request using these unauthenticated fields [4](#0-3) .

### Finding Description
The identity binding that should hold is: `hmac_valid(body) == true` should imply `shop_in_metadata == shop_that_actually_sent_this_body`. In this gem, that equality is broken — the HMAC only binds the body, not the `shop-domain` header that `Registry.process` uses to construct `WebhookMetadata.shop` and pass to the app's handler [5](#0-4) .

Because a single app has one `api_secret_key` shared across all its installed shops (`Context.api_secret_key`, used identically in `HmacValidator.validate` regardless of shop), any merchant who installs the app can legitimately trigger a webhook for their own store (e.g., `orders/create`) and receive a body + valid HMAC signed with the app's shared secret. Nothing in `HmacValidator` or `Webhooks::Request` binds that HMAC to the specific shop that triggered it — the developer-facing documentation confirms this by stating that `Registry.process` "will verify the request did indeed come from Shopify" (implying `shop` is trustworthy) [6](#0-5) , while the header used to populate `WebhookMetadata#shop` is never included in the signed bytes [7](#0-6) .

An unprivileged internet user who can install the app on any store (a normal, no-privilege action) can capture a genuinely-signed `(body, hmac)` pair from their own shop's webhook delivery, then resend it to the app's public webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop's domain (and, since `topic` is likewise unsigned, potentially the `topic` header rewritten too). `Registry.process` will still pass `Utils::HmacValidator.validate(request)` because the HMAC only covers `@raw_body`, and will invoke the handler with `shop: <attacker-chosen victim domain>` [8](#0-7) .

### Impact Explanation
This is a cross-tenant identity confusion: attacker-controlled webhook data is delivered to the app's handler tagged with an arbitrary victim shop identity, despite passing the gem's own HMAC "authenticity" check. Any host application that trusts `WebhookMetadata#shop` (as the gem's docs instruct) to key its persistence/business logic (e.g., updating "victim-shop"'s local order/product records, or firing tenant-scoped side effects) can have its per-tenant data corrupted or its per-tenant workflows triggered by an attacker who only controls their own shop's installation — meeting the cross-tenant access bar.

### Likelihood Explanation
Likelihood is meaningful but not trivial: it requires the attacker to (a) install the target app on a shop they control (no special privilege needed — any Shopify Partner/dev store or public app install), (b) trigger a webhook topic that is registered by the app, and (c) intercept/replay the raw POST with a modified `shop-domain` header, which requires no cryptographic secret since the signed bytes are unaffected by header changes.

### Recommendation
Bind the identity used for routing to the signed content, not to an unauthenticated header. Options: (1) include `shop`, `topic`, and `webhook_id` in the HMAC-signable string (this would be a breaking protocol change vs. Shopify's real signing scheme, so likely infeasible unilaterally), or (2) require host applications to cross-check `WebhookMetadata#shop` against a shop that is independently known to be associated with the unique registered webhook `path`/callback URL, and document this requirement prominently rather than implying `process` fully "verifies the request did indeed come from Shopify" for the `shop` field specifically. At minimum, update `docs/usage/webhooks.md` to explicitly warn that `data.shop`, `data.topic`, and `data.webhook_id` are NOT covered by the HMAC and must not be trusted for tenant-scoping without additional verification (e.g., validating against the shop tied to the specific registered callback path).
