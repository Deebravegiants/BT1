### Title
Personal Custody Package (biometric data) is uploaded to the backend even when fraud is detected, without any gating or rollback - (File: `src/plans/mod.rs`)

### Summary
`do_signup()` computes `fraud_detected` and derives a `signup_reason` of `SignupReason::Fraud` when the on-device fraud checks flag a capture, but this `signup_reason` is only used as metadata embedded in the personal custody package (PCP) — it never gates whether the PCP (iris codes, iris images, face embeddings/thumbnail) is actually built and uploaded to the backend. The upload happens unconditionally as long as a `pipeline` was produced, before the actual enrollment decision (`enroll_user`) is made. This is the same bug class as the reported `insertValidatorSet()` issue: data is persisted (uploaded/inserted) speculatively before all validation gates have passed, and once persisted it is never retracted if the later validation (fraud/enrollment) fails.

### Finding Description
In `src/plans/mod.rs`, `do_signup()`: [1](#0-0) 

computes `fraud_detected`/`signup_reason` and then, regardless of whether `signup_reason == SignupReason::Fraud`, proceeds to call `self.build_pcp(...)` and, on success, immediately calls `self.upload_pcp_tier_0(...)` and sends tier1/tier2 packages to the `data_uploader` agent. There is no check such as `if signup_reason != SignupReason::Fraud` guarding this block.

`build_pcp` itself only validates that the `pipeline` bundle fields are present — it has no awareness of `signup_reason` other than embedding it as a string field in the resulting package: [2](#0-1) [3](#0-2) 

The actual enrollment/success determination (which is what should decide whether a signup, and therefore its biometric data, is legitimate) only happens afterwards: [4](#0-3) 

By the time `enroll_user`/`report_signup_reason` runs and marks the signup as `SignupReason::Fraud`, the iris codes, normalized iris images, and face embeddings/thumbnail have already been packaged, encrypted, and uploaded to the backend via presigned URL (`backend::upload_personal_custody_package::request` / the `data-uploader` agent queue), with no code path that deletes or invalidates the already-uploaded package.

This mirrors the `insertValidatorSet()` root cause: an entity (biometric package) is written into a persistent store (S3 back end via presigned URL) before the validation result that should gate its existence is checked, and no compensating removal exists when that validation later fails.

### Impact Explanation
If the on-device fraud detection determines a capture is fraudulent (or otherwise flags `SignupReason::Fraud`), the user's biometric data (iris codes/images, face embeddings and thumbnail) is nevertheless uploaded to the backend under that `signup_id`/`user_id`. This is an unauthorized disclosure/persistence of biometric data for a signup attempt that the system itself has judged should not be trusted — data that should have been blocked from leaving the device is instead exfiltrated to the backend, with the "fraud" designation only recorded as a benign string tag on the same package rather than as a gate preventing the upload.

### Likelihood Explanation
The upload path is on the standard, unprivileged signup flow (`do_signup`) reachable by any user performing a normal signup; no special access is required to trigger `fraud_detected`. In the current FOSS build the concrete fraud rule implementations have been stripped out (`detect_fraud` always returns `Ok(false)`, per the `// FOSS: WE HAVE DELETED ALL FRAUD CHECKS` comment), so the condition is not exercised today, but the structural gap — no gating of `build_pcp`/`upload_pcp_tier_0` on `signup_reason` — remains present in the control flow and will re-activate as soon as fraud checks are reinstated (e.g. in a non-FOSS build), exactly as with the analog bug where the flawed insertion path exists regardless of whether the triggering bad input currently occurs in practice. [5](#0-4) 

### Recommendation
Gate the `build_pcp`/`upload_pcp_tier_0` (and tier1/tier2 upload) calls on `signup_reason != SignupReason::Fraud` (and `!= SignupReason::Failure`), mirroring the recommendation in the analog report to "perform checks before inserting" — i.e., validate/finalize the fraud and enrollment decision before any biometric package is built or uploaded, not after. If packaging must occur before the decision for latency reasons, add an explicit abort/no-op path that skips the upload entirely when `signup_reason == SignupReason::Fraud`.

### Proof of Concept
1. In `do_signup` (`src/plans/mod.rs:562-571`), force `fraud_detected = true` (e.g., re-enable a fraud check rule) so `signup_reason = SignupReason::Fraud`.
2. Continue execution: `qr_codes.try_into()` succeeds, `self.build_pcp(...)` is called with `signup_reason = SignupReason::Fraud` (`src/plans/mod.rs:580-598`) — it does not check `signup_reason` and returns `Ok(Some(packages))` as long as the pipeline bundle is populated.
3. `self.upload_pcp_tier_0(...)` (`src/plans/mod.rs:600-612`, implementation at `src/plans/mod.rs:1778-1839`) uploads tier0 data via `backend::upload_personal_custody_package::request`, and tier1/tier2 are queued to `data_uploader` (`src/plans/mod.rs:613-636`) — all before `enroll_user` is ever invoked.
4. Only afterward does `report_signup_reason` (`src/plans/mod.rs:665-683`) record the signup as fraudulent — by which point the biometric package has already left the device and reached the backend.
