### Title
Webhook `shop` identity is trusted from an unauthenticated header while the HMAC signature only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, but the `shop` (and `topic`/`api_version`) values that are handed to the app's `WebhookHandler` are read from HTTP headers that are **not** included in that HMAC computation. Because the HMAC secret (`api_secret_key`) is shared by the app across every shop that installs it, any shop that can generate one legitimate webhook can reuse its valid `(body, hmac)` pair while forging the `shop-domain` header to impersonate a different tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor used elsewhere is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, independent of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC only over `to_signable_string`, i.e. only the body: [3](#0-2) 

`Registry.process` uses this HMAC check as the sole authentication gate, then forwards `request.shop` (the unauthenticated header value) straight into the `WebhookMetadata` that is delivered to the host app's handler: [4](#0-3) 

`WebhookMetadata.shop` is a plain `String` field with no further validation, and is documented/relied upon by host apps as the tenant identifier for the webhook: [5](#0-4) 

The identity binding broken is: `hmac == HMAC(secret, signable_string)` should equal `hmac == HMAC(secret, signable_string_including_shop)`, but the actual binding is `hmac == HMAC(secret, body_only)` while `shop` is trusted unconditionally afterward. Since `api_secret_key` is a single app-level secret shared across all shops (not shop-specific), any installer of the app can obtain a `(body, hmac)` pair that is valid for the app as a whole, then replay that exact body+HMAC to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header pointing at a victim shop. `Utils::HmacValidator.validate` will still pass (it never looks at the shop header), and the handler will process attacker-controlled data under the victim shop's identity.

### Impact Explanation
This crosses the tenant boundary that the report's bug class targets ("shop authenticated versus the shop stored/used as identity"): the value driving which shop's session/data the host application acts on is not bound to the cryptographic proof of authenticity. This enables cross-tenant confusion/spoofing — an attacker-controlled webhook payload can be attributed to an arbitrary victim shop domain, which typically drives session lookup, order/customer processing, or app-uninstall handling keyed by `shop` in host applications built on this gem's documented `WebhookMetadata` contract.

### Likelihood Explanation
Requires only that the attacker be an unprivileged user who can install the app on their own shop (to generate one legitimate webhook with a valid HMAC), then send an HTTP POST to the app's public webhook endpoint with a modified `shop-domain` header — no access token, secret, or privileged account needed.

### Recommendation
Bind `shop` (and ideally `topic`/`api_version`) into the signed material verified against the HMAC, or otherwise cryptographically tie the shop identity to the signature (e.g. include headers in the signable string, or require the caller to separately verify shop against a known/expected value before trusting `request.shop`).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering a real webhook (e.g. `orders/create`) with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC(api_secret_key, B)`.
2. Attacker replays the exact same body `B` and HMAC header `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks `HMAC(api_secret_key, B) == H`, per `lib/shopify_api/utils/hmac_validator.rb:26-31` and `lib/shopify_api/webhooks/request.rb:35-38`.
4. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` from the forged header, per `lib/shopify_api/webhooks/registry.rb:198-199`, and invokes the host app's handler as if the event genuinely originated from `victim-shop.myshopify.com`.
