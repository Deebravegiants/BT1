### Title
Webhook `shop`/`topic`/`webhook_id` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-authenticated signable content from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to dispatch and attribute the webhook are read from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only the body's HMAC and then trusts these header-derived fields to route the event and construct `WebhookMetadata`, breaking the binding between "the shop whose bytes were authenticated" and "the shop the event is attributed to."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`HmacValidator.validate_signature` verifies the received HMAC strictly against `verifiable_query.to_signable_string` (i.e. the raw body): [3](#0-2) 

`Registry.process` performs exactly one authentication check — the body HMAC — and then unconditionally trusts `request.topic` and `request.shop` (both header-derived, unauthenticated) to select the handler and build the `WebhookMetadata` object passed into the app's business logic: [4](#0-3) 

The identity binding the code implicitly assumes is:
`shop_authenticated_by_hmac(raw_body) == shop_used_for_dispatch(request.shop)`

That equality does not hold, because `request.shop` (and `request.topic`/`request.webhook_id`) are never part of the bytes HMAC covers. The `client_secret` used to compute the HMAC is shared across all shops that have installed the same app (it is an app-level secret, not shop-scoped), so any body that legitimately validates for one shop's event will validate identically for a forged request that swaps in an arbitrary `x-shopify-shop-domain` / `x-shopify-topic` / `x-shopify-webhook-id` header.

### Impact Explanation
An attacker who is nothing more than an unprivileged merchant/installer of the target app (or anyone who otherwise obtains one legitimately-signed `(body, hmac)` pair for the app, e.g. from their own store's webhook traffic, an app's own webhook debug/log feature, or any topic whose body is fixed/generic such as an empty-body event) can replay that exact body+HMAC to the app's public webhook endpoint while freely rewriting the `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` headers. `Registry.process` will accept it as valid (HMAC check passes) and dispatch it as if it were an authentic event from an arbitrary victim shop and topic of the attacker's choosing. This is cross-tenant identity spoofing: the app's downstream logic (order/customer/shop data handlers, webhook-driven billing, GDPR redaction, etc.) will act on attacker-controlled `shop`/`topic` metadata that was never actually verified.

### Likelihood Explanation
This is reachable by any internet-facing caller of the app's public webhook endpoint (which must be internet-reachable for Shopify to deliver to it) without any privileged credential, access token, or TLS interception — only a single previously-observed valid `(body, hmac)` pair for the app is needed, which is trivially obtainable by an app user for their own account's traffic or for any topic with static/generic body content (e.g. `app/uninstalled`'s empty `{}` payload).

### Recommendation
Include the identity-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the signed payload before `Registry.process` uses them for dispatch/attribution, so that the authenticated shop/topic cannot diverge from the shop/topic acted upon.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and triggers (or otherwise obtains) one webhook delivery, e.g. `app/uninstalled`, whose body is the fixed JSON `{}`. They capture the `x-shopify-hmac-sha256` value delivered with it (e.g., via the app's own webhook logging feature).
2. Using the same raw body `{}` and the same captured HMAC, the attacker sends a direct HTTP POST to the app's public webhook endpoint with headers:
   ```
   x-shopify-topic: orders/paid
   x-shopify-hmac-sha256: <captured value>
   x-shopify-shop-domain: victim-shop.myshopify.com
   x-shopify-webhook-id: <arbitrary>
   ```
3. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks the HMAC of the body `{}` (`lib/shopify_api/webhooks/request.rb` line 37, `lib/shopify_api/utils/hmac_validator.rb` lines 26-31).
4. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb` lines 188-199) dispatches to the `orders/paid` handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: "orders/paid", ...)`, even though no such event was ever authenticated by Shopify for `victim-shop.myshopify.com`.
