## Analysis

The `spread()` view function in `VWAPOracle.sol` computes a volume-weighted average spread for cross-chain intent fills by dividing a signed cumulative sum by an unsigned total volume: [1](#0-0) 

Solidity's `/` operator truncates toward zero, not toward negative infinity. When `data.weightedSpreadSum` is negative (i.e., fillers have on average captured a negative spread from users) and does not evenly divide `data.totalVolume`, the result is rounded up (toward zero) rather than down, exactly the same class of error described in the external report for `callUniswapObserve`'s `(tickCumulatives[1] - tickCumulatives[0]) / secondsAgo` division.

This is populated by `recordSpread`, which is called by the `IntentGateway` on every order fill with attacker/filler-influenced `inputs`/`outputs` amounts: [2](#0-1) 

and the underlying accumulator update is a simple running sum with no floor-rounding correction: [3](#0-2) 

### Title
Incorrect (rounded-toward-zero) VWAP spread reading due to lack of round-down for negative cumulative sums - (File: `evm/src/utils/VWAPOracle.sol`)

### Summary
`VWAPOracle.spread()` divides a signed `weightedSpreadSum` by an unsigned `totalVolume` using Solidity's default division, which truncates toward zero instead of flooring. When the accumulated weighted spread is negative and not an exact multiple of total volume, the reported spread is biased upward (less negative than the true VWAP), analogous to the Uniswap TWAP tick truncation bug in the referenced report.

### Finding Description
`spread()` at [1](#0-0)  performs `data.weightedSpreadSum / int256(data.totalVolume)` without the "round to negative infinity" correction that Uniswap's own `OracleLibrary::consult()` applies (`if (tickCumulativesDelta < 0 && (tickCumulativesDelta % secondsAgo != 0)) arithmeticMeanTick--;`). Every intent fill routed through the `IntentGateway` feeds `recordSpread()` with filler-controlled `inputs`/`outputs` token amounts, which directly determine the sign and magnitude of `weightedSpread` accumulated into storage. Since fillers routinely provide slightly fewer output tokens than input tokens (capturing a small negative spread as their margin), `weightedSpreadSum` is very commonly negative in normal operation, making the rounding bias a persistent, not edge-case, occurrence.

### Impact Explanation
The rounded-up (less negative) spread value understates how much value fillers have historically captured from users on a given (source-chain, token) pair. Any downstream consumer of `IIntentPriceOracle.spread()` that uses this value to validate that a filler's fill price stays within an acceptable band, or to compute expected outputs, will accept fills that are marginally worse for users than the true historical VWAP indicates, or admit a filler-favorable pricing decision by up to one bps unit per query. Because this occurs on every read and the bias is directional (always toward tolerating more filler value-extraction, never less), it can be systematically exploited by fillers to skew the oracle's tolerance band over time.

### Likelihood Explanation
High: `weightedSpreadSum` is negative under ordinary operation (fillers profit by giving out less than they take in), and `weightedSpreadSum % totalVolume != 0` is the common case for arbitrary token amounts, so the rounding error is triggered by essentially every fill/read rather than requiring adversarial setup.

### Recommendation
Apply the same "round to negative infinity" correction used in Uniswap's `OracleLibrary`:
```solidity
function spread(bytes memory sourceChain, address token) external view returns (int256) {
    bytes32 chainHash = keccak256(sourceChain);
    CumulativeSpreadData memory data = _tokenSpreads[chainHash][token];
    if (data.totalVolume == 0) return 0;

    int256 totalVolume = int256(data.totalVolume);
    int256 result = data.weightedSpreadSum / totalVolume;
    if (data.weightedSpreadSum % totalVolume != 0 &&
        (data.weightedSpreadSum < 0) != (totalVolume < 0)) {
        result--;
    }
    return result;
}
```

### Proof of Concept
1. Filler fills two orders on the same `(sourceChain, inputToken)` pair such that `weightedSpreadSum = -7` and `totalVolume = 2` (e.g., via `recordSpread` calls with normalized amounts producing those weighted contributions).
2. Correct floor division: `-7 / 2 = -3.5` → floors to `-4`.
3. Solidity's truncating division: `-7 / 2` evaluates to `-3` (rounded toward zero).
4. `spread()` returns `-3` instead of the correct `-4`, understating filler value-extraction by one unit on every such query.

```text
    function recordSpread(
        bytes32 commitment,
        bytes memory sourceChain,
        TokenInfo[] calldata inputs,
        TokenInfo[] calldata outputs
    ) external restrict(_intentGateway) {
        // Validate inputs and outputs have the same length
        if (inputs.length != outputs.length || inputs.length == 0) {
            return;
        }

        bytes32 sourceChainHash = keccak256(sourceChain);
        uint256 tokensLen = inputs.length;
        for (uint256 i = 0; i < tokensLen; i++) {
            address inputToken = address(uint160(uint256(inputs[i].token)));
            address outputToken = address(uint160(uint256(outputs[i].token)));

            // Get decimals for input token from storage (remote chain)
            // Native tokens (address(0)) use 18 decimals
            uint8 inputDecimals = inputToken == address(0) ? 18 : _tokenDecimals[sourceChainHash][inputToken];
            if (inputDecimals == 0) continue; // Skip if decimals not configured

            // Get decimals for output token directly from contract (local chain)
            // Native tokens (address(0)) use 18 decimals
            uint8 outputDecimals = outputToken == address(0) ? 18 : IERC20Metadata(outputToken).decimals();

            // Normalize both amounts to 18 decimals for comparison
            uint256 inputAmountNormalized = _normalizeAmount(inputs[i].amount, inputDecimals);
            uint256 outputAmountNormalized = _normalizeAmount(outputs[i].amount, outputDecimals);

            // Calculate spread for this token: (output - input) / input * 10000
            // Positive spread = filler provided more tokens (good for user)
            // Negative spread = filler provided fewer tokens (filler captured spread)
            int256 spreadBps = 0;
            if (inputAmountNormalized > 0) {
                int256 amountDiff = int256(outputAmountNormalized) - int256(inputAmountNormalized);
                spreadBps = (amountDiff * int256(BPS_DENOMINATOR)) / int256(inputAmountNormalized);
            }

            // Update cumulative spread data for this token (weighted by volume)
            int256 weightedSpread = spreadBps * int256(inputAmountNormalized);
            _updateCumulativeSpread(_tokenSpreads[sourceChainHash][inputToken], weightedSpread, inputAmountNormalized);

            // Emit event for each token
            emit SpreadRecorded(commitment, outputToken, spreadBps);
        }
    }
```

```text
    function _updateCumulativeSpread(CumulativeSpreadData storage data, int256 weightedSpread, uint256 volume) private {
```
