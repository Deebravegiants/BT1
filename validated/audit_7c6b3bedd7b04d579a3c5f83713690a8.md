### Title
`redeem` (and other user-supplied recipient paths) in Zest vaults lack the self-address guard present in `transfer`, allowing user principal to be permanently trapped in the vault contract - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
The Zest vault contracts (`v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, and their `local-testing` equivalents) implement a SIP-010 `transfer` that explicitly forbids sending zTokens to the vault's own address: [1](#0-0) 
but the `redeem` function, which accepts an unrestricted user-supplied `recipient principal` and then burns shares and sends underlying to that address, has no equivalent check: [2](#0-1) 
This is the same bug class as the Origin Marketplace report: an unprivileged, user-controlled destination address is never validated against the contract's own principal before value is irrevocably moved/burned, so specifying the vault (or another contract with no sweep/recovery function) as the destination permanently strands the underlying that the caller's burned shares represented.

### Finding Description
`redeem(amount, min-out, recipient)` burns the caller's shares and decrements the internal `assets` ledger *before/simultaneously* sending the underlying to `recipient`: [3](#0-2) 
There is no `(asserts! (not (is-eq current-contract recipient)) ...)` guard, unlike `transfer`, which explicitly blocks `to = current-contract`: [4](#0-3) 

The value identity being broken is: **shares burned == underlying delivered to the redeemer**. If `recipient` is set to the vault's own principal (or to `market.clar`/another vault contract that has no code path to credit or forward an unsolicited incoming balance), `send-underlying` moves the token balance internally while the `assets` accounting variable is still decremented by `inkind`: [3](#0-2) 
The caller's zToken shares are gone (burned), yet no external party ends up holding the redeemed underlying — it is deposited into a contract balance that is never credited to any user's collateral map or debt ledger and for which no `recipient == current-contract` guard, sweep, or `acceptCommission`-style claim function exists anywhere in the vault or market contracts. This mirrors exactly the root cause described in the reference report: `makeOffer`/`payCommission` validated only against the zero address, never against the contract's own address, so funds sent to a self-referential/uncontrolled address become permanently unclaimable.

The same unguarded-recipient pattern recurs at every place a principal is threaded through as a destination without a self-address check, e.g. `system-borrow`'s `receiver`: [5](#0-4) 
and `market.clar`'s `borrow`, `collateral-remove-redeem`, and `liquidate-redeem`, all of which forward an optional `receiver`/`funds-receiver` to `vault-redeem`/`send-underlying` without checking it against `current-contract`: [6](#0-5) [7](#0-6) 

### Impact Explanation
Once a redeemer's shares are burned and the underlying lands in the vault's/market's own balance with no accounting entry crediting any account, that value is permanently unrecoverable by the depositor and is not distributed to any other party either (the `assets` ledger, which governs `convert-to-shares`/`convert-to-assets` pricing and thus everyone else's redemption rate, is decremented as if the tokens left the contract). This is a **permanent freezing of user funds**: the depositor's principal is stranded in the contract with no function anywhere in the codebase to reclaim a balance that exceeds the tracked `assets`/`total-borrowed` state.

### Likelihood Explanation
The likelihood is comparable to the original report: it requires an unprivileged caller (or a third-party front-end/integration bug) to pass the vault's own contract principal as `recipient`/`receiver`/`funds-receiver`. This can happen through user error, a buggy integrator, or a malicious actor deliberately convincing/tricking another party's tooling into redeeming to the vault address (e.g., copy-pasted contract address instead of wallet address, or a compromised/misconfigured front-end default). Unlike the flashloan `funds-receiver-resolved`, which is explicitly checked with `(asserts! (is-standard funds-receiver-resolved) ERR-INVALID-ADDRESS)`: [8](#0-7) 
`redeem` has no such standard-principal or self-address check at all, making this comparatively easier to trigger than the flashloan path (which is out of scope here anyway).

### Recommendation
- **Short term:** Add `(asserts! (not (is-eq current-contract recipient)) ERR-INVALID-ADDRESS)` to `redeem` in every vault contract, mirroring the guard already present in `transfer`. Apply the same check to `deposit`'s `recipient` (share minting), `system-borrow`'s `receiver`, and to every `receiver`/`funds-receiver` parameter accepted by `market.clar` (`borrow`, `collateral-remove-redeem`, `liquidate-redeem`), excluding only the internal cases where `current-contract` (market) is intentionally used as an intermediate holder before a subsequent internal redeem step.
- **Long term:** Introduce a generic "reject self-address as external recipient" helper shared across vault and market contracts, and add a DAO-gated sweep/rescue function to recover any underlying balance in a vault/market that exceeds its tracked `assets`/`total-borrowed` accounting, so accidental self-sends do not result in permanently unrecoverable funds.

### Proof of Concept
1. Alice deposits `amount` underlying into `vault-stx`, receiving `inkind` zSTX shares via `deposit`, minted to her account: [9](#0-8) 
2. Alice (or a buggy client acting on her behalf) calls `redeem(amount, min-out, .vault-stx)` — i.e., passes the vault's own contract principal as `recipient`.
3. `redeem` burns Alice's zSTX shares (`ft-burn? zft amount account`), decrements `(var-set assets (- current-assets inkind))`, and calls `(send-underlying inkind recipient)` with `recipient = .vault-stx`: [3](#0-2) 
4. The underlying ends up (or remains) in the vault's own token balance, uncredited to any collateral/debt entry, while Alice's shares are irreversibly destroyed and the `assets` ledger no longer reflects the true available balance.
5. No function in `vault-stx.clar` or `market.clar` allows Alice, the DAO, or anyone else to reclaim this specific stranded amount — it is permanently frozen, exactly as OGN commission was permanently frozen in the Origin Marketplace when the affiliate address equaled the Marketplace's own address.

(define-public (collateral-remove-redeem (ft <ft-trait>) (amount uint) (min-underlying uint) (receiver (optional principal)) (price-feeds (optional (list 3 (buff 8192)))))
  (let ((ft-address (contract-of ft))
        (asset (try! (get-asset ft-address)))
        (ztoken-id (get id asset))
        (underlying-id (if (is-eq ztoken-id zSTX) STX
                       (if (is-eq ztoken-id zsBTC) sBTC
                       (if (is-eq ztoken-id zstSTX) stSTX
                       (if (is-eq ztoken-id zUSDC) USDC
                       (if (is-eq ztoken-id zUSDH) USDH
                       (if (is-eq ztoken-id zstSTXbtc) stSTXbtc
                       u100)))))))  ;; invalid sentinel for non-ztoken
        (funds-receiver (match receiver recv recv contract-caller)))

    (asserts! (<= underlying-id stSTXbtc) ERR-UNKNOWN-VAULT)
    
    ;; Step 1: Remove collateral - sends zTokens to THIS contract (market)
    ;; receiver=current-contract so market holds the zTokens

    ;; Since market now holds the zTokens, this succeeds
    ;; Underlying tokens are sent to the specified receiver
    (vault-redeem underlying-id amount min-underlying funds-receiver)))
