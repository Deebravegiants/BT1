### Title
Webhook `shop-domain` and `topic` headers are excluded from HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request **body**. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values that the gem then hands to the application's handler as the authoritative tenant/topic identity are read straight from unauthenticated HTTP headers and are never included in the signed material, breaking the equality `hmac_verified_bytes == bytes_the_handler_trusts_for_tenant_and_topic_attribution`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors instead read directly from HTTP headers without any cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates only that the body's HMAC matches, then dispatches to the handler using the unauthenticated `request.shop` and `request.topic`: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature purely over `verifiable_query.to_signable_string`, i.e. body bytes only, with no involvement of the headers: [4](#0-3) 

Because the signature covers the body but not `shop`/`topic`, an entity that has captured any single legitimate `(body, hmac)` pair emitted by Shopify for this app's endpoint (webhook bodies are delivered over plain HTTP callback URLs and are not treated as secret by Shopify's own model — the security boundary is the HMAC, not body secrecy) can resend that exact body/HMAC pair to the same public webhook endpoint while freely rewriting the `X-Shopify-Shop-Domain` and `X-Shopify-Topic` headers. The gem will accept it as authentic and hand the application a `WebhookMetadata` object claiming an attacker-chosen `shop` and `topic`, even though those values were never authenticated.

### Impact Explanation
This breaks the tenant-attribution binding webhook consumers rely on. An application that persists or acts on webhook data keyed by `WebhookMetadata#shop` (e.g., updating shop-specific records, provisioning, billing state, uninstall/GDPR handlers) can be made to apply another shop's payload to an arbitrary victim shop identifier, or process a payload under the wrong topic handler, resulting in cross-tenant data corruption/misattribution — a data integrity and cross-tenant access issue in a multi-tenant app built on this gem's documented webhook processing API.

### Likelihood Explanation
Exploitation requires an attacker to obtain a single legitimate `(body, hmac)` pair for the target app (e.g., via replay of network traffic to the endpoint, a shared/leaked webhook body from a topic with predictable/non-sensitive contents, or their own shop's webhook whose body content is attacker-influenced, such as `app/uninstalled` or a custom order note) and to be able to POST directly to the app's public webhook endpoint with modified headers — no `api_secret_key`, access token, or other privileged material is required, since the headers sit entirely outside the HMAC's protection.

### Recommendation
Include the `shop-domain`, `topic`, and `webhook-id` header values in the signed/verified material (e.g., verify them against an out-of-band trusted mapping, or require the host application to independently validate `shop` against a known/installed-shop registry) before constructing `WebhookMetadata`, rather than trusting them as co-equal with the HMAC-verified body.

### Proof of Concept
1. Capture one legitimate webhook delivery to the app's public endpoint: body `B` with header `shopify-hmac-sha256: H` (valid because `H = HMAC(secret, B)`), originally sent for `shopify-shop-domain: victim-a.myshopify.com`, `shopify-topic: orders/create`.
2. Replay a POST to the same endpoint with identical body `B` and header `shopify-hmac-sha256: H`, but set `shopify-shop-domain: victim-b.myshopify.com` and/or `shopify-topic: app/uninstalled`.
3. `Utils::HmacValidator.validate` succeeds (only `B` and `H` are checked) — [5](#0-4)  — and `Registry.process` invokes the handler registered for the attacker-chosen topic with `shop: "victim-b.myshopify.com"`, even though that shop never sent this webhook.
