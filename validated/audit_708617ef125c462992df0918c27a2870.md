### Title
Session cookie value is trusted as a storage key without cryptographic verification, enabling cross-tenant offline session theft - (File: lib/shopify_api/utils/session_utils.rb)

### Finding Description
The broken binding: `SessionUtils.cookie_session_id(cookies)` returns `cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]` verbatim [1](#0-0) . There is no HMAC/signature check anywhere in this method or in `current_session_id` before this value is handed to the host app's session storage as a lookup key [2](#0-1) . The intended binding should be `session_id_returned == HMAC_verify(Context.api_secret_key, cookie)`, but the actual code enforces only `session_id_returned == cookies['shopify_app_session']`, i.e. whatever bytes the caller supplies in the `Cookie` header.

Compounding this, for offline (non-online) sessions the session ID format is fully deterministic and derived only from public information: `offline_session_id(shop) = "offline_#{shop}"` [3](#0-2) . A shop's `myshopify.com` domain is not a secret — an attacker can trivially learn or guess a target's domain. Because the cookie value equals this deterministic string, no signature, nonce, or randomness protects it. An attacker does not need to steal a cookie from a victim's browser; they can construct the value themselves and send it directly in an HTTP request's `Cookie` header, since HTTP requests are attacker-controlled and cookies are just headers with no origin enforcement on the server side.

For non-embedded apps (`Context.embedded?` false, the default/host-configured case in this scenario), `current_session_id` unconditionally falls back to `cookie_session_id(cookies)` with no JWT/id-token check at all [4](#0-3) . This means the only gate that exists is "does a cookie by this name exist," not "was this cookie value issued through a completed, verified OAuth flow for this shop."

Exploit flow: attacker sends `GET /callback` (or whatever route in the host app calls `current_session_id`) with header `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`. `current_session_id(nil, cookies, false)` returns `"offline_victim-shop.myshopify.com"` unchanged. The host app then calls its `SessionStorage#load_session("offline_victim-shop.myshopify.com")`, which — if the victim shop previously completed OAuth — returns the victim's real `Session` object, including `access_token`. The app can then build a `ShopifyAPI::Clients::HttpClient` using that stolen session and access the victim shop's Admin API on the attacker's behalf.

No existing guard in this gem intercepts this: `HmacValidator.validate` only applies to OAuth callback/webhook HMAC params, not to this cookie read path; `ShopValidator.sanitize!` only validates shop domain format, not authenticity of the session lookup; `JwtPayload`'s checks are bypassed entirely because the non-embedded branch never touches the JWT code path; Sorbet's `T.nilable(String)` typing only constrains the type, not the semantic trust of the value.

### Impact Explanation
Any unprivileged attacker who knows (or guesses) a target merchant's `myshopify.com` domain can, with a single crafted request, retrieve the victim shop's stored offline session and its `access_token` from the host app's session storage. This is a Critical cross-tenant access vulnerability: the access token grants full API access equivalent to the merchant's installed app scopes, is repeatable against any victim shop, and requires no interaction from the victim, no prior attacker OAuth flow against the victim, and no leaked credentials.

### Likelihood Explanation
Preconditions are minimal and match common real-world deployments: a non-embedded app (`Context.embedded?` false, a normal/default deployment mode for many Shopify apps, e.g., POS or backend-only integrations), and any victim shop that has previously completed OAuth (a normal operating state for an installed app). The attacker's cost is a single HTTP request with a guessed/known shop domain — no rate limiting bypass, no secret material, no timing attack needed. This is highly feasible and trivially repeatable across arbitrary victim shops known to have installed the app.

### Recommendation
Do not use a deterministic, unsigned value (`offline_#{shop}` / `#{shop}_#{user_id}`) as both the session-storage key and the bearer credential handed back by the browser. Either (a) sign the cookie value with an HMAC keyed by `Context.api_secret_key` and verify that HMAC in `cookie_session_id` before returning the ID, or (b) store an unguessable random token in the cookie that maps to the deterministic session ID server-side (session storage indirection), rather than exposing the deterministic ID directly as the trusted cookie value.

### Proof of Concept
```ruby
# test/utils/session_utils_test.rb (new test)
class SessionUtilsCrossTenantTest < Minitest::Test
  def test_cookie_session_id_accepts_attacker_forged_cookie_without_signature
    ShopifyAPI::Context.expects(:embedded?).returns(false)

    forged_cookie_value = "offline_victim-shop.myshopify.com"
    cookies = { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => forged_cookie_value }

    returned_id = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)

    # Broken binding: returned_id == attacker-supplied bytes, not HMAC-verified
    assert_equal forged_cookie_value, returned_id

    # Show that this ID, unverified, is used directly to load a real session/token
    fake_storage = mock("SessionStorage")
    fake_storage.expects(:load_session).with(forged_cookie_value).returns(
      ShopifyAPI::Auth::Session.new(id: forged_cookie_value, shop: "victim-shop.myshopify.com", access_token: "victim-secret-token")
    )
    session = fake_storage.load_session(returned_id)
    assert_equal "victim-secret-token", session.access_token
  end
end
```
This demonstrates that no HMAC or origin check is performed anywhere in `current_session_id`/`cookie_session_id`, and the attacker-chosen cookie string is passed straight through to session storage lookup.
