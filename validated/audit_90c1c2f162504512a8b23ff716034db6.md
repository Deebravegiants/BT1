### Title
Stale `account.owner` field used for authorization lets a previous NFT holder keep full control of a transferred account - ([File: contracts/controller/src/account.rs])

### Summary
The controller tracks two different notions of account identity: the `owner` field stored in the `Account` struct at creation time, and the live owner resolved from the position-NFT (`storage::account_owner` → `nft.owner_of`). The authorization gate `is_owner_or_delegate` compares `caller == owner` where `owner` is passed as `&account.owner` — the stale stored field, not the NFT owner. A caller who transfers their account NFT keeps matching the stored field and retains full borrow/withdraw power over collateral that now belongs to the buyer/new holder.

### Finding Description
`create_account_with` mints the NFT and stores `owner: owner.clone()` into the `Account` struct (contracts/controller/src/account.rs, lines 62-70). Nothing in the NFT `transfer`/`transfer_from` path flows back into the controller to update this stored field — position-nft is the stock OpenZeppelin enumerable NFT and only `mint`/`burn`/`upgrade` are controller-authenticated calls into it.

Both fund-moving entrypoints authorize against the stored field:

- `process_withdraw` calls `require_owner_or_delegate(env, account_id, caller, &account.owner)` (contracts/controller/src/positions/supply.rs, line 150).
- `process_borrow` calls `require_owner_or_delegate(env, account_id, caller, &account.owner)` (contracts/controller/src/positions/debt.rs, line 43).
- `is_owner_or_delegate` short-circuits on `caller == owner` before checking the delegate set (contracts/controller/src/account.rs, lines 121-127).

Meanwhile owner-only maintenance paths correctly resolve the NFT owner: `require_account_owner` uses `storage::account_owner(env, account_id)` (contracts/controller/src/account.rs, lines 143-148), which calls `nft_try_owner_of_call` (contracts/controller/src/storage/account.rs, lines 35-44). So the codebase itself treats NFT ownership as canonical for identity, but the money paths consult the stale snapshot — the same class as the OpenClaw advisory, where an allowlist decision was made against a non-canonical, sender-derived identity instead of the canonical identifier.

Result after a transfer:
- Old owner: `caller == account.owner` still true → can `borrow` (pulling debt assets to any `to` recipient) and `withdraw` every supply position, i.e. drain the account they just sold.
- New owner: `caller != account.owner`, and `get_delegates(env, account_id, owner)` is keyed under the stored owner, so they are neither owner nor delegate → cannot withdraw their own collateral; they can only `repay`.

Note on verification: I could not exhaustively confirm the absence of a controller-side owner resync on NFT transfer within the available search iterations; if such a sync exists (e.g., invoked inside `storage::get_account` or a transfer hook), this finding does not apply. The code paths shown are the strongest match for the advisory's bug class in this codebase.

### Impact Explanation
Theft of user funds. An attacker sells or gift-transfers their account NFT to a victim (or receives payment for it), then calls `borrow` against the victim's collateral and `withdraw` on all remaining supply, receiving tokens directly. The stored `owner` field being attacker-legacy data means the protocol authorizes an identity the NFT no longer names. Severity: High — direct unauthorized extraction of collateral from an account the caller no longer owns.

### Likelihood Explanation
Reachable by any unprivileged address: `position-nft::transfer` is a permissionless holder call, and `withdraw`/`borrow` only require `caller.require_auth()` plus the stale-owner check. No privileged action, timing window, or external condition is needed — the divergence exists from the moment of transfer until account deletion.

### Recommendation
In `is_owner_or_delegate` / `require_owner_or_delegate`, resolve the canonical owner via `storage::account_owner(env, account_id)` (NFT `owner_of`) instead of trusting `account.owner`, or keep `account.owner` synchronized by updating it in every path where NFT ownership can change. Alternatively, drop the stored `owner` field entirely and treat the NFT as the single identity source, mirroring what `require_account_owner` already does.

### Proof of Concept
1. Alice calls `supply` (account_id 0) creating account A owned by her; `account.owner = Alice`.
2. Alice supplies collateral and optionally borrows.
3. Alice calls `position-nft::transfer(Alice → Bob, token_id = A)`.
4. Bob now owns the NFT: `storage::account_owner` returns Bob; `require_account_owner` accepts only Bob.
5. Alice calls `controller::withdraw(caller=Alice, account_id=A, withdrawals=[all], to=Some(Alice))`. `process_withdraw` loads `account` (`account.owner == Alice`), `require_owner_or_delegate` sees `caller == owner` → authorized. Pool pays Alice.
6. Alice calls `borrow` similarly to extract any remaining borrow capacity before withdrawing the freed collateral.
7. Bob, the NFT owner, is rejected by `require_owner_or_delegate` on `withdraw` — his collateral and the new debt are stranded under Alice's stale `owner` field.
