### Title
Attacker-Sized HyperSwap V2 Pre-Seed Defeats `_pairRebalance`'s Budget Cap, Graduating the LP Away From Curve-Close Price - (File: `packages/contracts/src/Bonding.sol`)

### Summary
The Traefik advisory shows a bounded defense (`readTimeout`) that a protocol-detection fast path silently disables once the attacker's input exceeds the assumption the fast path was built for, letting the attacker stall past the intended limit indefinitely. `Bonding`'s hostile-pre-seed defense for graduation LP seeding has the same failure shape: the rebalance swap that is supposed to force the HyperSwap V2 pool back to the curve-close ratio is capped by `_swapBudget`, whose cap is sized off *this graduation's own* LT/token inventory rather than off what is actually needed to correct an attacker-chosen pre-seed ratio. An attacker who pre-seeds the pool with reserves large enough that the required corrective swap exceeds that budget causes the defense to silently give up and deposit at the still-skewed, attacker-controlled ratio.

### Finding Description
`_seedRebalancing` (regime 3, "mint pre-seed") is the code path Bonding uses when an attacker has already called `pair.mint()` on the HyperSwap V2 TOKEN/LT pair before `finalizeGraduation` fires: [1](#0-0) 

It computes the required corrective swap via `_noFeeSwapInput`, which is explicitly capped at `maxSwap`: [2](#0-1) 

`maxSwap` comes from `_swapBudget`, which is 99% of *Bonding's own* LT/token inventory for this graduation (`ltFromPair` / `tokensForLP` scale, not the pre-seed's reserve scale): [3](#0-2) 

`_noFeeSwapInput` derives the ideal input as `sqrt(reserveIn * reserveOut * targetN / targetD) - reserveIn`, which scales with the *pre-seed's* reserve magnitudes, not with Bonding's inventory: [4](#0-3) 

If the attacker pre-seeds the pool with reserves large enough that the ideal corrective swap exceeds `maxSwap`, `_pairRebalance` simply executes a swap capped at the budget — nowhere near enough to move a large pool back to the target ratio — and returns `true` (a swap did execute, just an inadequate one). The natspec's stated fallback ("`_pairRebalance` returns false → direct mint overpowers") only fires when the *ideal* swap size is zero or the quoted output is zero; it does **not** fire when the swap is merely budget-capped, because the function still returns `true` in that case: [5](#0-4) 

Consequently `_routerDepositAndDispose` then deposits Bonding's remaining LT/token inventory via `addLiquidity(min0=1, min1=1)` at whatever ratio the (inadequate) swap left the pool at — still dominated by the attacker's pre-seed ratio, not the curve-close ratio: [6](#0-5) 

The natspec on `_swapBudget` explicitly acknowledges the cap only guarantees a *non-zero* deposit, not a *correctly priced* one: [7](#0-6) 

`LPLock` has no withdrawal path in v1 ("No withdraw in v1"), so once `finalizeGraduation` calls `recordLock` the mis-priced LP position is permanently locked with no on-chain recovery: [8](#0-7) [9](#0-8) 

### Impact Explanation
The protocol permanently seeds and locks 25% of the token's total supply (`LP_RESERVE`) plus all curve-raised LT into a HyperSwap V2 pool whose price the attacker dictated, rather than the curve's actual close price: [10](#0-9) 

Because the LP is minted straight to `LPLock` with no rescue mechanism, this is a permanent freezing/misallocation of protocol- and creator-controlled LP value at a wrong price. Simultaneously, the attacker's own pre-existing LP position (which they funded to create the imbalance) can be unwound/arbitraged immediately after `finalizeGraduation` against the freshly and incorrectly seeded reserves, extracting real value (curve-raised LT and reserve tokens) that belonged to the protocol/creator/holders. This satisfies the explicitly accepted impact class "an LP seeded away from the curve close price" together with permanent freezing of LP funds.

### Likelihood Explanation
This is reachable by any unprivileged wallet: token buys on the curve (`Zap.buy`) are permissionless, LT minting through BounceTech is permissionless, and creating/seeding a HyperSwap V2 pair via `pair.mint()` (or the V2 router) before `Bonding.finalizeGraduation` runs is explicitly one of the reachable analog surfaces (pre-seeding the HyperSwap V2 pair before graduation). The only constraint is that the attacker must fund a pre-seed large enough that the required corrective swap exceeds Bonding's own `ltFromPair`/`tokensForLP` inventory for that specific token — feasible for any token whose curve raise (and hence LP budget) is modest relative to capital the attacker is willing to commit temporarily (the pre-seed capital is largely recoverable by the attacker via their own LP share and post-graduation arbitrage). This does not require any privileged role, upgrade, or off-chain component — it's fully triggerable via ordinary transactions plus the existing permissionless `triggerGraduation`/buy flow.

### Recommendation
Size the rebalance swap budget (and/or reject the deposit) based on the *pre-seed reserve magnitude relative to the target ratio*, not solely on Bonding's own graduation-scoped inventory. If the ideal corrective swap (uncapped) exceeds the available budget, the contract should fall back to the direct-mint-overpower path (as it already does for the zero/degenerate cases) rather than depositing at a partially-corrected, still-skewed ratio. Alternatively, cap the pre-seed's influence by measuring the resulting post-swap price deviation from the cached curve-close ratio and reverting/deferring `finalizeGraduation` (with a permissionless retry) if the deviation exceeds a safe tolerance, instead of unconditionally depositing via `addLiquidity(min=1, min=1)`.

### Proof of Concept
1. Attacker identifies a curve token close to `canGraduate` (via `Bonding.previewLtUntilGraduation`).
2. Attacker buys some amount of the launched `Token` via `Zap.buy`, and separately mints a large amount of the paired LT via BounceTech's permissionless `mint`.
3. Attacker calls HyperSwap V2 factory `createPair(token, lt)` (or lets `Bonding._ensureUniswapV2Pair` create it) and calls `pair.mint(attacker)` after transferring a large, deliberately imbalanced amount of `token`/`lt` into the pair — sized so that the ideal corrective swap `sqrt(reserveIn*reserveOut*targetN/targetD) - reserveIn` computed in `Bonding._noFeeSwapInput` exceeds `_swapBudget(ltFromPair)` / `_swapBudget(tokensForLP)` for this token's expected graduation amounts.
4. Attacker (or anyone) triggers graduation, e.g. via a curve buy that crosses the threshold, or `Bonding.triggerGraduation(tokenAddress)`.
5. `finalizeGraduation` → `_seedUniswapV2Direct` → `_seedRebalancing` → `_pairRebalance` executes a swap capped at `maxSwap`, insufficient to bring the pool back to the `tokensForLP/ltFromPair` ratio.
6. `_routerDepositAndDispose` deposits the remaining inventory via `addLiquidity(min=1, min=1)` at the still-skewed post-swap ratio; `LPLock.recordLock` permanently locks this mis-priced LP with no withdrawal path.
7. Attacker swaps against the mispriced pool (or removes their pre-existing LP share) to realize arbitrage profit extracted from the protocol's curve-raised LT and reserved token supply.

    function _pairRebalance(
        RebalanceParams memory p
    ) internal returns (bool) {
        uint256 s = _noFeeSwapInput(p.reserveIn, p.reserveOut, p.targetN, p.targetD, p.maxSwap);
        if (s == 0) return false;

        // Quote from the pair so the output tracks its live fee; a value
        // derived from a stale fee rate would trip the pair's K-check.
        uint256 expectedOut = IUniswapV2Pair(p.pair).getAmountOut(s, p.tokenIn);
        if (expectedOut == 0) return false;

        IERC20(p.tokenIn).safeTransfer(p.pair, s);
        (uint256 amount0Out, uint256 amount1Out) = p.tokenInIs0 ? (uint256(0), expectedOut) : (expectedOut, uint256(0));
        IUniswapV2Pair(p.pair).swap(amount0Out, amount1Out, address(this), new bytes(0));
        return true;
    }

    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }

    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }
