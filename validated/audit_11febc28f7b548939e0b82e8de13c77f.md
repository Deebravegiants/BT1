Found it. `Webhooks::Request` verifies the HMAC only over the raw request body (`to_signable_string` returns `@raw_body`), while `shop` and `topic` are read straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`) that are never covered by the HMAC computation. This breaks the identity binding: `shop` (used to authorize/attribute the webhook to a tenant) ≠ `shop` (bytes actually verified by the HMAC).

### Title
Webhook `shop`/`topic` identity spoofing via unauthenticated HTTP headers not covered by HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates the HMAC exclusively over the raw JSON body (`to_signable_string` → `@raw_body`), but the `shop` (`shop-domain` header) and `topic` values that a host application uses to route/authorize the webhook to a specific merchant are pulled directly from HTTP headers that are never part of the signed payload.

### Finding Description
`Webhooks::Request` includes `Utils::VerifiableQuery` and defines: [1](#0-0) 
`to_signable_string` returns only `@raw_body`: [2](#0-1) 
`shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header via `shopify_header`, entirely independent of the HMAC computation: [3](#0-2) [4](#0-3) 
`HmacValidator.validate` computes the HMAC of `to_signable_string` against `Context.api_secret_key` and compares it to the `hmac` accessor using `OpenSSL.secure_compare`: [5](#0-4) 

Because HMAC validation only proves that `@raw_body` was produced by someone holding `api_secret_key` (i.e., Shopify), it says nothing about the `shop-domain` or `topic` headers. Any consumer of this gem that calls `Webhooks::Request#shop` to look up which merchant/tenant the payload belongs to (a documented, expected usage pattern per `docs/usage/webhooks.md`) is binding tenant identity to a value that carries no cryptographic guarantee.

The identity-binding equality this breaks is:
`shop used for tenant authorization` (header, attacker-controlled) ≠ `shop bytes covered by the verified HMAC` (none — the shop is not in the signed string at all).

### Impact Explanation
An unprivileged attacker who can deliver an HTTP request to the app's webhook endpoint (the endpoint is, by design, a public unauthenticated route awaiting Shopify's POST) can replay any legitimately-obtained webhook body (e.g., a request the attacker's own store's webhook produced, which they legitimately received and whose HMAC is valid for that body) while substituting an arbitrary `shopify-shop-domain` header value naming a *different* victim shop. Because `shop` is never part of `to_signable_string`, `HmacValidator.validate` still returns `true`. If the host application trusts `request.shop` to select which merchant's session/access token/data to update in response to the payload (a common and encouraged pattern in Shopify webhook handling), this results in cross-tenant data processing — the attacker's payload (with attacker-chosen `topic`/body content, up to whatever body they can get legitimately HMAC-signed, e.g. from their own store) is attributed to and processed against an arbitrary victim shop record.

### Likelihood Explanation
High likelihood of reachability: the webhook endpoint is inherently exposed to the internet (Shopify posts to it without any session/cookie context), and `Webhooks::Request` is the gem's documented interface for validating and reading webhook data — an attacker need only possess one validly-signed webhook body (trivially obtainable by installing the app on their own free development store and capturing a real webhook) and can then relay it with a forged `shop-domain` header to any endpoint that uses `request.shop` post-validation.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the HMAC-covered signable material, or otherwise cryptographically bind them (e.g., validate `shop` against the session/shop the webhook route is scoped to, not from an unauthenticated header) before using them for tenant attribution. At minimum, the gem's `Webhooks::Request` should not present `shop`/`topic` as "validated" alongside a passing `HmacValidator.validate?` call without documenting that these header-derived fields are unauthenticated.

### Proof of Concept
```ruby
# 1. Attacker installs the target app on their own (attacker-owned) store and
#    captures one legitimate webhook delivery, e.g.:
raw_body = '{"id": 1, "note": "hello"}'
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => "<valid base64 HMAC computed by Shopify over raw_body with the real api_secret_key>",
  "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
}

# 2. Attacker replays the identical body/HMAC to the app's public webhook
#    endpoint, substituting the shop-domain header to name the victim:
forged_headers = headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Utils::HmacValidator.validate(request) # => true, because to_signable_string == raw_body only

request.shop  # => "victim-shop.myshopify.com"  (unauthenticated, attacker-controlled)
# A host app that does `Merchant.find_by(shop: request.shop).process(request.parsed_body)`
# after seeing `validate == true` now processes attacker-controlled data against the victim's record.
```
