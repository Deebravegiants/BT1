## Analysis

The JOJO report's core bug class is: **a shared, no-access-control contract that executes attacker-supplied `to`/`data` calls, combined with funds/approvals transiently or accidentally sitting on that contract, letting anyone drain them.**

The closest analog in Hyperbridge is `CallDispatcher`, the shared executor used by `IntentGatewayV2`'s predispatch/postdispatch calldata feature.

### Title
Unrestricted `CallDispatcher.dispatch()` lets anyone drain any token/ETH dust left on the shared dispatcher from incomplete sweeps - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher.dispatch()` has no access control - any address can call it with arbitrary `Call[]{to, value, data}` and force the dispatcher to execute them using whatever balance/allowances the dispatcher currently holds. [1](#0-0)  `IntentGatewayV2` and `IntentsBase` route both `predispatch` and `postdispatch` (`order.output.call`) arbitrary, order-creator-controlled calldata through this single shared dispatcher instance, temporarily transferring user/solver funds into it before sweeping the balance back. [2](#0-1) 

### Finding Description
The sweep logic after `dispatch()` only recovers balances for tokens explicitly declared in `order.inputs` (predispatch) or `order.output.assets` (postdispatch) - it iterates only over those enumerated tokens. [3](#0-2)  If a predispatch/postdispatch call chain (fully controlled by the order creator, e.g. a multi-hop swap through an intermediate token, or a native-ETH-refunding router call) leaves residual balance in a token or in native ETH that is *not* one of the declared input/output assets, that balance is never swept and permanently accumulates on the `CallDispatcher` contract. Because `dispatch()` is public and unauthenticated (no `onlyGateway`/`onlyOwner` modifier), any unrelated third party can later call `CallDispatcher.dispatch()` directly with a `Call` that transfers that stranded token/ETH balance to themselves - exactly the "no access control lets an attacker steal funds sitting in a shared pass-through contract" pattern from the JOJO report, just substituting stranded intermediate-swap dust/native refunds for the JOJO contract's approved-but-unswept USDC.

Additionally, because postdispatch/predispatch calldata routinely issues standing ERC20 `approve()` calls from the dispatcher to routers (e.g. `token.approve(uniswapRouter, type(uint256).max)`, as exercised in `IntentGatewayV2Test.sol`), any malicious order creator can grant themselves (instead of a router) a standing infinite allowance from the shared `CallDispatcher` for an arbitrary token. [4](#0-3)  This allowance is never revoked and persists indefinitely in the dispatcher's storage, ready to be exercised the moment that token's balance on the dispatcher becomes non-zero for any reason.

### Impact Explanation
Any ETH or ERC20 tokens left over from swap slippage/refunds in a token not covered by the sweep enumeration are permanently and trivially stealable by any address, since `dispatch()` performs no caller check. This is a direct, unbacked-mint-adjacent loss of funds vector reachable from a single unprivileged transaction (no governance, no relayer, no proof required) - qualifying as Medium/High per the loss-of-funds bar.

### Likelihood Explanation
Likelihood is moderate to high: predispatch/postdispatch calldata routinely performs multi-step swaps (wrap/approve/swap) where slippage or exact-output semantics leave dust in an intermediate token not declared in `order.inputs`/`order.output.assets`, and the dispatcher's `receive()` accepts arbitrary ETH. Any user (or bot) monitoring the dispatcher's balance can immediately call `dispatch()` to sweep any stray balance to themselves, since there is no cooldown, and no privileged caller check gates the function.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by the registered `IntentGatewayV2` instance(s) (an `onlyGateway`/allow-list modifier), and/or have the gateway sweep *all* non-declared token balances (not just the ones in `order.inputs`/`order.output.assets`) back to itself or to a protocol-controlled recipient after every `dispatch()` call so no dust or stray ETH can persist on the shared dispatcher between transactions.

### Proof of Concept
1. A user places (or fills) an order whose `predispatch.call`/`output.call` performs a multi-hop swap, e.g. wraps ETH to WETH, swaps WETH → USDC for the declared `order.inputs`, but the swap path leaves residual WETH (an intermediate token not declared in `order.inputs`) on the `CallDispatcher`.
2. `IntentsBase._execute`/`IntentGatewayV2`'s predispatch sweep only iterates `order.inputs`/`order.output.assets`, so the leftover WETH is never transferred back and remains on `CallDispatcher`. [5](#0-4) 
3. Any attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: WETH, value:0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, dustAmount)})]))` directly - this succeeds because `dispatch()` has no caller restriction. [6](#0-5) 
4. The attacker receives the stranded WETH dust that rightfully belonged to the order's input/escrow accounting.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
