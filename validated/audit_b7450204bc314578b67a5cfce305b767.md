## Title
Webhook Shop-Domain Header Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's authenticity by checking the HMAC-SHA256 signature, but the signature is computed only over the raw request body. The `shop` value that identifies which merchant/tenant the webhook belongs to is read from the `x-shopify-shop-domain` HTTP header, which is never included in the signed payload. Because the same `client_secret` is shared across every shop that installs a given app, an attacker who controls one legitimately-installed shop can capture a genuinely-signed webhook delivery for their own store and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to point at a victim shop. The signature check still passes (it only checks the body), so the forged event is dispatched to the app's webhook handler as if it originated from the victim tenant.

### Finding Description
The webhook request wrapper only signs the body: [1](#0-0) 

`shop` is parsed straight from the (unsigned) header: [2](#0-1) 

The registry validates the HMAC against `to_signable_string` (the raw body) and, once it passes, immediately forwards `request.shop` — the unauthenticated header value — to the handler as the tenant identifier, with no additional binding check: [3](#0-2) 

The HMAC verification itself confirms this: it only ever operates on `verifiable_query.to_signable_string` (for `Request`, the raw body) and the app's shared `api_secret_key`: [4](#0-3) 

The broken identity binding, as an equality that should hold but doesn't:

`shop_bound_by_hmac == shop_delivered_to_handler`

is actually:

`shop_bound_by_hmac == "" (nothing) ; shop_delivered_to_handler == request.shop (attacker-controlled header)`

Since the `client_secret` used to compute the HMAC is per-app (not per-shop), any shop that installs the app can produce a validly-signed body/HMAC pair for events in its own store, then relabel that payload as belonging to any other shop by changing only the unsigned `x-shopify-shop-domain` header — the check in `Registry.process` cannot detect this tampering.

### Impact Explanation
This breaks the tenant boundary the whole webhook subsystem is meant to enforce: a merchant/attacker with any legitimate install of the app can inject fabricated webhook events (order data, GDPR/compliance topics, uninstall notices, etc.) attributed to a shop they do not own. Any host application that trusts `WebhookMetadata#shop` returned by `Registry.process` (which is the whole point of exposing it) will act on data for the wrong tenant — this is a cross-tenant access/data-injection primitive, matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is Medium-to-High: the attacker only needs their own legitimate install of the app (unprivileged relative to other tenants) to obtain one validly-HMAC-signed webhook body, and standard HTTP tooling to replay it with a modified header — no knowledge of `client_secret`, access tokens, or other tenants' credentials is required.

### Recommendation
Bind the `shop` identity to the signed payload rather than trusting the header alone: include `x-shopify-shop-domain` (and ideally topic/api-version) in the signable string that is HMAC-verified, or independently verify the shop domain against a known/installed-shop list (e.g., a stored session for that shop) before dispatching to the handler in `ShopifyAPI::Webhooks::Registry.process`.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; the attacker triggers/observes a real webhook delivery, capturing `raw_body`, `x-shopify-hmac-sha256`, and other headers.
2. Attacker resends the exact same HTTP request to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com` (HMAC header unchanged).
3. `ShopifyAPI::Webhooks::Request.new` parses the tampered headers; `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the (unchanged) signature.
4. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host app to process/store attacker-supplied data under the victim tenant's identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
