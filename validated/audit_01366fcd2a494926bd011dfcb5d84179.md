### Title
Unrecognized HOT Bridge withdrawal status is misreported as "completed" - ([File: packages/intents-sdk/src/bridges/hot-bridge/hot-bridge.ts])

### Summary
`HotBridge.describeWithdrawal` treats any non-hex string status value returned by the HOT SDK contract-view fallback as a completed withdrawal with no transaction hash, instead of treating it as pending or unknown. This breaks the equality "reported status == actual on-chain outcome" and can cause callers to treat an unfinished/failed withdrawal as done.

### Finding Description
For non-EVM/non-Stellar/non-TON chains, `describeWithdrawal` falls back to the on-chain "gasless withdraw status" view. The code expects only two possible statuses: `HotWithdrawStatus.Completed`/`HotWithdrawStatus.Canceled` (enum sentinels), or a raw hex string representing a destination tx hash: [1](#0-0) 

If the contract/API ever returns a string value that is not hex-encoded (and not equal to the `Completed`/`Canceled` sentinels), the code does **not** treat it as pending or unrecognized — it logs a warning and returns `{ status: "completed", txHash: null }`: [2](#0-1) 

This `completed` status is then consumed by `watchWithdrawal`, which immediately resolves the polling promise with `{ hash: null }` as soon as `status.status === "completed"`, without any independent verification that funds were actually delivered on the destination chain: [3](#0-2) 

This is structurally the same bug class as the referenced report: a status/sentinel value that does not actually correspond to the real state (there, `type(int128).max` was conflated with "canceled"; here, any non-hex non-enum string is conflated with "completed"). The equality broken is: *status reported by the SDK == actual on-chain settlement outcome*.

### Impact Explanation
`waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` are the SDK's primary APIs for integrators to determine when a withdrawal has landed on the destination chain (per the SDK README's documented usage). If an integrator uses the resolved "completed" result to credit a user's balance, mark an off-chain ledger entry as settled, or release a paired obligation, they can do so for a withdrawal that never actually completed — because the misreport came from an unexpected/garbage status string rather than confirmed on-chain settlement. This matches the High-severity category "a status or hash misreport making an integrator credit or refund twice," since the integrator may credit based on this false completion and later have to also handle the real completion or a retried withdrawal, or worse, refund erroneously since `txHash: null` gives no way to verify the claim.

### Likelihood Explanation
This path only triggers when the underlying HOT SDK's `getGaslessWithdrawStatus` view returns a string that is neither the two known sentinel values nor valid hex — e.g., an unexpected value shape from a HOT SDK/contract change, an error string leaking through, or any future status value the SDK author didn't anticipate. This is plausible without any malicious actor: it only requires the external HOT bridge/contract to return an unanticipated but syntactically valid string, which is explicitly acknowledged as an "incorrect destination tx hash" scenario in the existing log message, showing the author was already aware such values can occur but chose to treat them as "completed" rather than "pending"/"unknown."

### Recommendation
Do not default to `completed` when the status string fails the `isHex` check. Instead:
- Return `{ status: "pending" }` (matching the same fallback used elsewhere in the function for `null`/unknown states) when the value is neither a recognized enum sentinel nor a valid hex tx hash.
- Reserve "completed" exclusively for cases where a real destination transaction hash (or the explicit `HotWithdrawStatus.Completed` enum with corroborating hash lookup) is present, mirroring the `AuctionStorage.Status`-style recommendation of relying on explicit state rather than inferring status from ambiguous sentinel/format checks.

### Proof of Concept
1. A withdrawal on a non-EVM/non-Stellar/non-TON chain (e.g., a chain in the final `else` branch) is in progress.
2. `hotSdk.getGaslessWithdrawStatus(nonce)` returns some string value that is not `"COMPLETED"`, not `"CANCELED"`, and not valid lowercase/uppercase hex (e.g., due to an API quirk, encoding difference, or partial/garbled response).
3. `describeWithdrawal` executes the `!isHex(status)` branch and returns `{ status: "completed", txHash: null }`. [2](#0-1) 
4. `watchWithdrawal` sees `status.status === "completed"` and immediately resolves the caller's promise with `{ hash: null }`, even though the withdrawal has not actually been confirmed on the destination chain. [3](#0-2) 
5. An integrator relying on `sdk.waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` credits the user or closes out the withdrawal based on this false "completed" signal.
