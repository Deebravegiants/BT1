### Title
Webhook `shop`, `topic`, and `webhook_id` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate` only proves the request body was signed by the app's `client_secret` — it never binds the `shop-domain`, `topic`, or `webhook-id` headers into that proof. Yet `Registry.process` trusts those same unauthenticated headers to build the `WebhookMetadata` handed to the app's handler [2](#0-1) , and the documented handler contract tells app developers to use `data.shop` as the tenant identifier for follow-up work (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [3](#0-2) .

### Finding Description
The identity binding that should hold is:
`shop header trusted by Registry.process == shop bound inside the HMAC-verified bytes`

This equality does not hold. `Request#hmac` decodes the `hmac-sha256` header and `to_signable_string` returns the raw body verbatim [4](#0-3) ; `HmacValidator.validate_signature` recomputes `HMAC-SHA256(client_secret, to_signable_string)` and compares it to the received signature [5](#0-4) . Neither `shop`, `topic`, nor `webhook_id` participate in that computation — they are read straight from attacker-controllable HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) via `shopify_header` [6](#0-5) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., body authenticity) before dispatching to the handler with `request.shop`, `request.topic`, and `request.webhook_id` taken as ground truth [2](#0-1) . Because the app's `client_secret` (and thus the HMAC key) is the same for every shop that installs the app, any successfully captured `(raw_body, hmac)` pair — for example from a webhook the attacker's own store legitimately receives after installing the app — remains a valid HMAC for that exact body regardless of which `shop-domain` header accompanies it. An attacker can therefore resubmit that same body+HMAC to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop, and `Registry.process` will accept it and hand the handler a `WebhookMetadata` whose `shop` field impersonates the victim tenant.

### Impact Explanation
This breaks the tenant boundary the whole webhook subsystem is supposed to enforce: HMAC validity is meant to prove "this event is authentic for this shop," but it only proves "this exact body byte-string was signed once by this app." Host applications following this gem's documented contract (`data.shop` used to route webhook data to per-shop records/queues) will attribute attacker-supplied event data to an arbitrary victim shop of the attacker's choosing — a cross-tenant data-injection/confusion primitive reachable by any unprivileged internet user who can install the app once (public apps) or otherwise obtain one valid body+HMAC pair, without needing the app's `client_secret`, an access token, or any privileged account.

### Likelihood Explanation
Webhook HTTP endpoints are, by design, unauthenticated public endpoints — the HMAC is the *only* authentication mechanism this gem provides, and the gem's own header-parsing code accepts whatever `shopify-shop-domain`/`x-shopify-shop-domain` value is present, with no cross-check against the signed payload. Any consumer of this gem that follows the documented pattern of trusting `data.shop` is exposed; no special network position, TLS interception, or credential theft is required — just the ability to POST to the app's public webhook route with a previously-observed valid body+HMAC and a forged shop header.

### Recommendation
Bind the tenant identity into the signature-verified surface, e.g. include `shop-domain`, `topic`, and `webhook-id` in `to_signable_string` (or otherwise cryptographically bind them, since Shopify's own webhook signature does not cover headers), or independently corroborate `request.shop` against a value obtained through an authenticated channel (such as a previously stored session/shop record keyed by an app-generated identifier) before trusting it for tenant routing. At minimum, document prominently that `data.shop` is unauthenticated header data and must not be used as a sole tenant key without additional verification.

### Proof of Concept
1. Attacker installs the (public) app on their own store `attacker.myshopify.com`, triggers an event (e.g. `orders/create`), and captures the legitimate webhook POST: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC-SHA256(client_secret, B)`).
2. Attacker replays the request to the app's webhook endpoint, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` builds successfully (all required headers present) [7](#0-6) .
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(client_secret, B)` and matches `H` — validation succeeds because `shop` was never part of the signed content [8](#0-7) [9](#0-8) .
5. The registered handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ..., ...)` [10](#0-9)  and, per the documented usage pattern, processes/queues the attacker's data under the victim's tenant identity [11](#0-10) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
