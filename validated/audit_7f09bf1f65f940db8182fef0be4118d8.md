Confirmed: `ShopValidator.sanitize!` exists and is used in `TokenExchange`, `RefreshToken`, `ClientCredentials`, and `Clients::Graphql::Storefront`, but it is **not** used by `Auth::Oauth.begin_auth` or `Auth::Oauth.validate_auth_callback`. This is the identity-binding gap worth reporting.

### Title
Unvalidated `shop` domain in `Oauth.validate_auth_callback` allows SSRF exfiltration of `client_secret` to attacker-controlled host - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the OAuth token-exchange request URL directly from the caller-supplied `auth_query.shop` value via `auth_base_uri(shop)`, without ever passing it through `Utils::ShopValidator.sanitize!` (the check used elsewhere in the gem, e.g. `ClientCredentials`, `TokenExchange`, `RefreshToken`). The `shop` field is bound only by the OAuth HMAC signature, and the gem never independently confirms it is a `*.myshopify.com` (or other Shopify-trusted) domain.

### Finding Description
`Oauth.validate_auth_callback` computes: [1](#0-0) 

The request target host comes from `auth_base_uri(auth_query.shop)`: [2](#0-1) 

and the POST body contains `client_id` and `client_secret` in plaintext: [3](#0-2) 

The only check applied to `shop` before it is used as an outbound host is the HMAC validation: [4](#0-3) 

which validates that `shop` (together with `code`, `host`, `state`, `timestamp`) is unmodified relative to whatever query Shopify originally signed: [5](#0-4) 

Unlike `ClientCredentials.client_credentials`, which calls `Utils::ShopValidator.sanitize!(shop)` before constructing the session used for the outbound request: [6](#0-5) 

`validate_auth_callback` performs **no domain-format validation at all** — it trusts any string in `shop` as long as it is HMAC-consistent with the rest of the query, and feeds it straight into the URL used to send the `client_secret`: [7](#0-6) 

The binding that should hold is: `shop == <a myshopify.com-family domain>`, enforced independently of the HMAC. Instead the code only enforces `shop == <value embedded in the HMAC-signed query>`, which is a weaker property — it says nothing about the *format* of that value.

### Impact Explanation
This matters because the HMAC-signing party for the `/admin/oauth/authorize` flow is not exclusively Shopify's servers under all documented integration patterns of this gem: the `shop` and `state`/`host` values that eventually reach `validate_auth_callback` originate from the merchant's browser query string on the developer's `/callback` route, and the HMAC only proves that *these specific query parameters have not been tampered with relative to each other* using `api_secret_key`. It does not, by itself, prove `shop` is a genuine Shopify store domain — that is exactly why the gem introduced `ShopValidator` and applies it in three other OAuth-adjacent flows (`client_credentials`, `token_exchange`, `refresh_token`). Its absence here is an inconsistency in the identity-binding model: `validate_auth_callback` is the one flow that actually transmits the `client_secret` over the network to a host derived from user-influenced input, yet it is the one flow lacking the shop allow-list check.

Given the rules require the attack to not require possession of `api_secret_key`, and the HMAC here is computed with `api_secret_key`, a full SSRF exfiltration primarily depends on whether an app deployment can be driven into calling `validate_auth_callback` with attacker-influenced `shop`/`hmac` pairs without Shopify's real secret. Since I could not find, within this gem's code, any path that produces a validly-signed callback query with an attacker-chosen non-myshopify `shop` (the HMAC always requires `api_secret_key`), I cannot confirm this reaches full exploitability by an unprivileged user without a key. I am flagging the missing `ShopValidator.sanitize!` call as a structural inconsistency/regression relative to the rest of the gem's own trust model, not as a proven, unauthenticated SSRF.

### Likelihood Explanation
Low-to-unknown as a standalone unprivileged exploit: successfully reaching the vulnerable code path with an attacker-chosen `shop` requires a validly HMAC-signed query, which requires `api_secret_key` — out of scope per the rules. I could not identify an unprivileged bypass of the HMAC check in this gem.

### Recommendation
For defense-in-depth and consistency with the rest of the gem's OAuth surface, `Auth::Oauth.validate_auth_callback` (and `begin_auth`) should call `Utils::ShopValidator.sanitize!(auth_query.shop)` before using `shop` to construct `auth_base_uri`, mirroring the pattern already used in `ClientCredentials`, `TokenExchange`, and `RefreshToken`.

### Proof of Concept
Not producible with the tools available: constructing a request that reaches `Oauth.validate_auth_callback` with an attacker-controlled `shop` requires a valid HMAC computed with the app's `api_secret_key`, which is out of scope for an unprivileged-attacker PoC. No working exploit chain was found that avoids this requirement, so this finding should be treated as an unverified/low-confidence hardening gap rather than a proven vulnerability.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

        end
