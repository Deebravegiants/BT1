### Title
Simplex Uniswap V4 venue pricing reads raw spot `sqrtPriceX96` with no TWAP/staleness protection, letting a manipulated pool price size solver fills - (File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts)

### Summary
`UniswapV4FundingPlanner.getExoticTokenPrice` and its helper `computeDirectPoolPriceUsd` price the exotic token directly from the pool's current `slot0`-derived `sqrtPriceX96` (via `sdkPool.token0Price`/`token1Price`), exactly the faulty pattern the external report flags for `VeloOracle.getOraclePrice`: an instantaneous AMM spot price is trusted with no time-weighting and no default sanity check against manipulation.

### Finding Description
`getExoticTokenPrice` refreshes on-chain pool state and computes price straight from `sdkPool.token0Price`/`token1Price`, which are derived from the pool's live `sqrtPriceX96`: [1](#0-0) [2](#0-1) 

This price feeds `resolveLegRates`/`checkPriceGuard` in the FX strategy used to decide fills. As the project's own flow documentation states, `computeDirectPoolPriceUsd` returns the "raw pool mid derived from sqrtPriceX96" with no TWAP, no size/impact term, and `checkPriceGuard` is the *only* defense on this path — and it only checks deviation from a static reference price, not whether the price is a manipulated instantaneous quote: [3](#0-2) 

Crucially, the guard is optional and configuration-dependent — a pair/chain configured without `referencePrice`/`maxDeviationBps` is priced with zero manipulation protection: [4](#0-3) [5](#0-4) 

This mirrors the reported `VeloOracle` bug class exactly: both trust the pool's current tick/`sqrtPriceX96` state as if it cannot be manipulated within the same block/transaction, with no minimum elapsed-time or TWAP check to force the price through an update that costs an attacker capital across multiple blocks.

### Impact Explanation
An unprivileged actor placing an intent/order that Simplex is configured to fill from a Uniswap V4-priced pair can manipulate the referenced pool's spot price (e.g., via a swap immediately preceding order settlement, or by bundling the order with a manipulating swap in the same block) to shift `sqrtPriceX96` favorably. Since `getExoticTokenPrice` reads this manipulated value directly and (absent an explicit `referencePrice`/`maxDeviationBps` guard) applies no bound, the resulting quote used to size the solver's LP withdrawal/fill is distorted. This lets the attacker extract more of the exotic token from the solver's LP position than the honest USD amount warrants, or force an unprofitable fill — a direct value-extraction/loss-of-solver-funds outcome triggered by a single attacker-controlled order/transaction.

### Likelihood Explanation
Medium. Exploitation requires the pair to be configured for pool-based (curveless) pricing without a configured price guard, or with a guard band wide enough to still allow profitable manipulation, and requires sufficient capital/liquidity access to move the specific pool's `sqrtPriceX96` momentarily. This is realistic for exotic/thin pools (the intended use case for this feature, e.g., cNGN), where manipulation cost is lower than for deep pools — matching the same conditions that made the original `VeloOracle` bug medium risk.

### Recommendation
Do not price fills from the pool's raw instantaneous `sqrtPriceX96`. Use a Uniswap V4 TWAP/observation-based price (or require a minimum time delta since the last pool-state change before trusting a quote), and make the `referencePrice`/`maxDeviationBps` guard mandatory (not optional) for any pair using pool-based venue pricing, so no chain/pair can be left unguarded.

### Proof of Concept
1. Configure a pair (e.g., USDC/EXOTIC) with `[vault.uniswapV4]` pool-based pricing and no `referencePrice`/`maxDeviationBps` set for that chain (permitted per `docs/content/developers/evm/simplex/pricing.mdx` lines 68–84 and `fx.ts` lines 428–431, where `checkPriceGuard` returns `true`/no-op when unconfigured).
2. Attacker submits a large swap against the exotic/USDC Uniswap V4 pool used by the solver's LP position, shifting `slot0.sqrtPriceX96` sharply in the attacker's favor.
3. In the same block (or immediately after), attacker submits/dispatches the cross-chain intent/order to be filled by the Simplex solver against that pair.
4. `UniswapV4FundingPlanner.getExoticTokenPrice` (`UniswapV4FundingPlanner.ts` lines 206–240, `computeDirectPoolPriceUsd` lines 246–275) reads the manipulated `sqrtPriceX96` and returns a distorted USD price; `resolveLegRates` sizes the fill/withdrawal from this price with no guard rejecting it.
5. The solver withdraws/pays out based on the manipulated price, and the attacker reverses their manipulating swap, netting the price difference at the solver's expense.

	async getExoticTokenPrice(chain: string, exoticToken: string): Promise<Decimal | null> {
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}

	private computeDirectPoolPriceUsd(
		pos: HydratedV4Position,
		sdkPool: V4Pool,
		chain: string,
	): { exoticToken: string; priceUsd: Decimal } | null {
		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {
				exoticToken: c1,
				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

		if (c1 === usdc || c1 === usdt) {
			// currency1 is stable → exotic is currency0
			// token0Price = "token1 per token0" = USD per exotic
			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),
			}
		}

		return null
	}

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

```toml lineNumbers
[vault.uniswapV4]
# referencePrice is the expected cNGN per USD;
# reject if the quote is more than 2% off.
# The two go together — one without the other is rejected.
[[vault.uniswapV4.positions]]
chain           = "EVM-8453"
tokenId         = "2087350"
referencePrice  = "1575"
maxDeviationBps = 200
```
