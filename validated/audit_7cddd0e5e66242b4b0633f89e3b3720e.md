Based on my review of the ledger pruner architecture:

**No vulnerability found for this question.**

Rationale:

1. **No independent pruning in practice.** The `TransactionAuxiliaryDataPruner` and `TransactionInfoPruner` are both sub-pruners driven by a single `LedgerPruner::prune` loop that computes one `current_batch_target_version` per iteration and invokes every sub-pruner with the exact same `(progress, current_batch_target_version)` pair via `sub_pruners.par_iter().try_for_each(...)` [1](#0-0) . They are not driven by independent schedules; they advance in lockstep by construction.

2. **Startup catch-up reconciles any divergence.** Each sub-pruner (e.g. `TransactionAuxiliaryDataPruner::new`, `TransactionInfoPruner::new`) reads its own persisted progress via `get_or_initialize_subpruner_progress` and immediately calls `myself.prune(progress, metadata_progress)` to catch itself up to the shared `ledger_metadata_pruner` progress before the pruner is even usable [2](#0-1) [3](#0-2) . Any transient divergence (e.g. from a crash mid-batch between per-CF `write_schemas` calls) is only possible as a crash-consistency edge case in storage internals, not something an unprivileged transaction, package, or view can trigger or influence.

3. **No connection to dispatchable FA hooks.** Pruning progress is purely a function of ledger commit progress and pruning configuration/time; it has no dependency on transaction content, abort codes, or `detail_error_message` from a dispatchable fungible-asset withdraw hook. There is no code path by which invoking or aborting a dispatch hook could accelerate or desynchronize the `transaction_auxiliary_data_db` pruner relative to the `transaction_info_db` pruner.

4. **No custody impact even if achieved.** Per the Custody Impact Gate, only impacts changing who can own, move, mint, burn, freeze, upgrade, or recover value qualify. A hypothetical mismatch between pruned auxiliary data and transaction info would at most cause an API read to return stale/missing data or an error — it does not touch fungible-asset stores, dispatchable hook authority, object ownership refs, or any transfer/freeze/mint/burn logic. This is a data-availability/API-consistency concern, not a custody boundary violation, and it does not originate from unprivileged transaction input as required by the Review Path.

    fn prune(&self, max_versions: usize) -> Result<Version> {
        let mut progress = self.progress();
        let target_version = self.target_version();

        while progress < target_version {
            let current_batch_target_version =
                min(progress + max_versions as Version, target_version);

            info!(
                progress = progress,
                target_version = current_batch_target_version,
                "Pruning ledger data."
            );
            self.ledger_metadata_pruner
                .prune(progress, current_batch_target_version)?;

            THREAD_MANAGER.get_background_pool().install(|| {
                self.sub_pruners.par_iter().try_for_each(|sub_pruner| {
                    sub_pruner
                        .prune(progress, current_batch_target_version)
                        .map_err(|err| anyhow!("{} failed to prune: {err}", sub_pruner.name()))
                })
            })?;

            progress = current_batch_target_version;
            self.record_progress(progress);
            info!(progress = progress, "Pruning ledger data is done.");
        }

        Ok(target_version)
    }
