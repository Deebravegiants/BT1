This is a genuine analog to the constant-sum AMM unlimited-arbitrage bug class: a fixed/curve price with no bound tied to reserves or execution cost, reachable by anyone who places an IntentGateway order. I have enough evidence to write the final answer now.

### Title
Disabled overfill clamp lets a manipulated/stale Uniswap V4 venue price drain the FXFiller solver's inventory - (File: `sdk/packages/simplex/src/strategies/fx.ts`)

### Summary
`FXFiller` prices intent-gateway orders either from static curves or, for venue-priced pairs, directly from the live Uniswap V4 pool mid-price (`resolveLegRates` / `UniswapV4FundingPlanner.getExoticTokenPrice`). Like the `CCFrax1to1AMM` finding, the solver commits to paying out `policyMaxOutput` — a rate computed against an external, unbounded price source — with the only defense being an optional, per-chain static reference band (`checkPriceGuard`). The one hard, universal safety bound that existed (`maxOverfillBps`, capping payout to at most 105% of what the user requested) has been explicitly turned into a no-op: the code computes the ceiling, logs a warning if it's exceeded, and then pays the full unclamped amount anyway.

### Finding Description
In `calculateProfitability`, once a leg's output is priced (`computeLegPolicyOutput` → `rawPolicyMaxOutput`), the code computes an overfill ceiling and explicitly ignores it: [1](#0-0) 

```
// Overfill detection is warn-only: the clamp is DISABLED, so the filler
// fills the full computed amount even when it exceeds
// (1 + maxOverfillBps) × user-requested — including venue-priced legs
// (e.g. Uniswap V4). ...
const policyMaxOutput = rawPolicyMaxOutput
if (rawPolicyMaxOutput > overfillCeiling) {
    this.logger.warn(...) // "Overfill ceiling exceeded — clamp disabled, filling unclamped amount"
}
```

`targetOutput = policyMaxOutput` is then paid straight out of the solver's wallet/vault, funded via `fundingVenues` if the wallet balance is short.

For pairs priced off Uniswap V4 (`resolveLegRates`), the price comes from the pool's raw mid (`computeDirectPoolPriceUsd`), which itself is documented as having no size/impact term and only optionally checked against a static `referencePrice`/`maxDeviationBps` guard: [2](#0-1) 

That guard is opt-in ("omit both to leave the chain unguarded") per the docs: [3](#0-2) 

The design decision explicitly acknowledges the removed protection was never re-armed: [4](#0-3) 

This is structurally the same failure mode as the `CCFrax1to1AMM` report: a party that controls or observes a price divergence between the solver's pricing source (curve or thin/manipulated Uniswap V4 pool) and the true market price can place — or wait for — an IntentGateway order sized to extract the full available inventory at the stale/manipulated rate, with no reserve-dependent slippage and no hard ceiling stopping the payout, because the one bound that would have capped the loss (`maxOverfillBps`) is dead code.

### Impact Explanation
Any unprivileged user who places an intent-gateway order (the "unprivileged intent solver counterpart," an order placer) that this filler evaluates can, when the venue price is thin, stale, or manipulated (e.g., a low-liquidity Uniswap V4 pool, or a misconfigured/missing `referencePrice` guard), cause the solver to pay out its entire deliverable inventory of a token per fill, well beyond the 5% (`maxOverfillBps` default 500) ceiling that operators are told exists. This is a direct theft-of-funds vector against solver capital that Simplex operators believe is bounded by `maxOverfillBps`, but is not.

### Likelihood Explanation
Medium-High: exploitation requires either (a) manipulating a thin Uniswap V4 pool used for venue pricing (a single flash-loan-funded swap to move the tick, then placing an order priced off it) when no `referencePrice`/`maxDeviationBps` guard is configured for that chain (documented as an optional, frequently-omitted setting), or (b) waiting for a stale/misconfigured static curve or a decimals-misread bug (a related, separately-documented incident) to diverge from market. No special privilege is needed — placing an order through `IntentGatewayV2.placeOrder` is fully permissionless.

### Recommendation
Re-enable the `maxOverfillBps` clamp so `targetOutput` is capped at `min(policyMaxOutput, output.amount * (1 + maxOverfillBps) / 10000)` for venue-priced (and ideally all) legs, restoring the loss bound the configuration and documentation already advertise. Additionally make the Uniswap V4 `referencePrice`/`maxDeviationBps` price guard mandatory rather than optional for venue-priced pairs, and incorporate pool depth/size impact into `computeDirectPoolPriceUsd` rather than extending the raw mid linearly across the whole quantity.

### Proof of Concept
1. Operator configures a venue-priced pair (`token0` = USDC, `token1` = an exotic token) funded from a Uniswap V4 LP position, without setting `referencePrice`/`maxDeviationBps` (an allowed, documented configuration — "omit both to leave the chain unguarded"). [3](#0-2) 
2. Attacker performs a large swap in the underlying thin Uniswap V4 pool (optionally via flash loan) to move the tick so the pool's mid price overstates `token1`'s USD value.
3. Attacker places an IntentGateway order requesting a modest amount of `token1` for USDC; `resolveLegRates`/`computeDirectPoolPriceUsd` prices the leg off the manipulated mid, producing a `rawPolicyMaxOutput` far above what the user requested.
4. `calculateProfitability` logs the "Overfill ceiling exceeded — clamp disabled" warning but sets `policyMaxOutput = rawPolicyMaxOutput` unconditionally and pays it out via `executeOrder`, draining the solver's `token1` inventory (and any connected funding-venue withdrawals) at the manipulated rate. [5](#0-4) 
5. Attacker reverses the pool manipulation and captures the difference between the manipulated fill price and the true market price.

```text
## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
```
