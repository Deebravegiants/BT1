### Title
Webhook `shop` identity is taken from an unauthenticated header while the HMAC only covers the raw body, allowing cross-tenant shop-spoofing replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` validates only covers the raw request body, not the header. Because the webhook secret (`api_secret_key`) is shared by the app across *all* shops that install it, any merchant who installs the app (an unprivileged tenant from the app's perspective) can capture a validly-signed webhook delivery for their own shop and replay it to the app's endpoint with the `shop-domain` header changed to a victim shop, producing a request that still passes HMAC validation but is attributed to the wrong tenant.

### Finding Description
`Request#hmac` reads the signature from the header and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

`Request#shop`, by contrast, is read straight from an HTTP header with no cryptographic binding to the signed body: [3](#0-2) 

`HmacValidator.validate` computes the HMAC purely over `to_signable_string` (the raw body) and compares it to the header-supplied signature: [4](#0-3) 

`Registry.process` accepts any request whose body/HMAC pair validates, then unconditionally trusts `request.shop` as the tenant identity when dispatching to the handler: [5](#0-4) 

This is the identity-binding gap described in the rules: "a shop authenticated versus the shop stored as a session key." The cryptographic proof (`hmac` over `@raw_body`) authenticates only "a request signed with this app's secret," not "this specific body came from this specific shop." Since the same `api_secret_key` is used for every shop that installs the app, any tenant that can legitimately trigger a webhook (e.g., by performing an action on their own store that Shopify webhooks) obtains a `(raw_body, hmac)` pair that remains valid regardless of which `shop-domain` header accompanies it.

### Impact Explanation
An attacker who installs the app on their own store (a normal, unprivileged action) can:
1. Trigger any webhook topic the app subscribes to (e.g., `app/uninstalled`, `customers/data_request`, `shop/update`) on their own shop and capture the raw body + valid `X-Shopify-Hmac-Sha256` value.
2. Replay that exact body/HMAC pair to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) with a victim shop's domain.
3. Because `Registry.process` only checks the HMAC against the body and never binds it to the header-derived shop, the request passes validation and the handler executes `WebhookMetadata.new(shop: victim_shop, body: attacker_controlled_body, ...)`.

Depending on how the host application's webhook handlers use `shop`/`body` (e.g., deleting sessions on `app/uninstalled`, updating per-shop settings, purging or exporting data on GDPR topics), this enables cross-tenant data corruption or a forced deauthorization of a victim shop's session — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is moderate to high: no privileged credentials, access tokens, or knowledge of the app's `client_secret` are required — only the ability to install the app on an attacker-controlled store to legitimately obtain one valid `(body, hmac)` pair, plus the ability to send arbitrary HTTP requests to the app's public webhook endpoint (which is inherently internet-facing). The library itself performs no additional binding between the signed bytes and the tenant identity, so every host application built on this gem's `Registry.process`/`Request` API inherits the gap by default.

### Recommendation
Bind the shop identity to the signed payload instead of trusting the header in isolation:
- Where the webhook payload includes shop-identifying fields (e.g., `admin_graphql_api_id`, or embedding the expected shop in `to_signable_string`), include the header value in the signable string so it is covered by the HMAC, or
- Cross-check `request.shop` against an existing, already-authenticated session/shop record before dispatching, rejecting webhook payloads whose header-derived shop was never provisioned/expected, and
- Document to consumers of `ShopifyAPI::Webhooks::Registry` that `WebhookMetadata#shop` is not cryptographically authenticated and must not be used as the sole tenant key for state-changing operations without additional verification.

### Proof of Concept
```ruby
# Attacker installs the app on their own store "attacker.myshopify.com"
# and triggers, e.g., an app/uninstalled webhook, capturing:
raw_body = '{"id":123}'
hmac_b64 = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, raw_body)
)
# APP_SECRET here is not known to the attacker directly, but Shopify computed
# it for them because the app is genuinely installed on their own shop.

# Attacker now replays the same body/hmac to the app's public webhook URL,
# but swaps the shop-domain header to the victim:
headers = {
  "x-shopify-topic"       => "app/uninstalled",
  "x-shopify-hmac-sha256" => hmac_b64,
  "x-shopify-shop-domain" => "victim.myshopify.com",  # forged, unauthenticated
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) succeeds because it only checks raw_body,
# and the handler is invoked with shop: "victim.myshopify.com".
``` [6](#0-5)
