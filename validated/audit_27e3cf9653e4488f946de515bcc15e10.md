## Finding

### Title
Webhook `shop` (tenant identity) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, while the `shop` (tenant identifier) consumed by handlers comes from an HTTP header that is never included in that signed content. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then trusts the header-derived `shop` value to route data to the application's per-tenant handler logic, breaking the binding between "the shop the HMAC actually authenticates" and "the shop the application acts on."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read directly from the `shop-domain`/`x-shopify-shop-domain` header, completely independent of the signed body: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, and then forwards `request.shop` (from the unsigned header) straight into `WebhookMetadata`, which is handed to the app's registered handler as the trusted tenant identity: [3](#0-2) 

The `VerifiableQuery` interface only requires `hmac` and `to_signable_string`, so there is no structural guarantee that all security-relevant fields (like `shop`) are part of the signed content: [4](#0-3) 

This is the exact bug class from the reference report generalized to an equality-breaking identity binding: the gem verifies `hmac == HMAC(secret, raw_body)`, but then acts on `shop = header["x-shopify-shop-domain"]`, a value that is never part of the equality being checked. Anything that can supply a body/HMAC pair that passes validation (e.g., an app's own tenant replaying its own genuine webhook, since the same `client_secret`/`api_secret_key` is shared across all shops installed on a single app) can attach an arbitrary `shop-domain` header and have the library report it as an authenticated webhook "from" any other shop.

### Impact Explanation
Because a single app-wide `api_secret_key` signs webhooks for every shop that installs the app, and the shop identity is excluded from the signed bytes, a malicious merchant/tenant of the app can take a validly-signed webhook body from their own shop and resubmit it with a forged `shop-domain` header naming a victim shop. The library will report `HmacValidator.validate` as `true` and hand the handler a `WebhookMetadata` claiming the victim's shop, causing the host application to process attacker-controlled data as if it originated from another tenant — a cross-tenant access/data-integrity breach entirely enabled by this gem's signing/verification boundary.

### Likelihood Explanation
Any app built on this gem that uses `Webhooks::Registry.process` for webhook ingestion is affected, since the vulnerable code lives in the shared `Request`/`Registry` classes rather than being an app-specific mistake. Exploitation only requires possession of one genuinely signed webhook body (trivially available to any merchant who installs the app on their own store, since Shopify delivers real signed webhooks to every installer) plus the ability to set the `shop-domain` HTTP header when re-posting to the app's webhook endpoint — no `api_secret_key`, access token, or privileged account is needed.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) in the HMAC-signable content, or otherwise cryptographically bind them to the body before verification, so `Utils::HmacValidator.validate` cannot succeed if the header-derived tenant identity has been altered independently of the signed payload.

### Proof of Concept
1. App merchant installs the target app on `attacker.myshopify.com` and receives a real webhook delivery with body `raw_body` and header `x-shopify-hmac-sha256: H` (valid for `raw_body` under the app's shared `api_secret_key`).
2. Attacker resends the same `raw_body` and `H` to the app's webhook endpoint, replacing `x-shopify-shop-domain: attacker.myshopify.com` with `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, `Registry.process` calls `Utils::HmacValidator.validate(request)` which only checks `HMAC(api_secret_key, raw_body) == H` — this succeeds because `raw_body`/`H` are unchanged. `request.shop` returns `"victim.myshopify.com"`.
4. The handler receives `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: ..., ...)` and the host app processes attacker-controlled data attributed to the victim tenant. [3](#0-2)
