### Title
Unauthorized cross-account signing via unchecked `walletAccount` parameter in `messageSigner`/`transactionSigner` APIs - (File: `features/message-signer/src/api/index.ts`, `features/tx-signer/src/api/index.ts`)

### Summary
The H-01 report's root cause is that a privileged operation (minting) trusted a piece of externally-observable/attacker-influenced state (the vault's token balance) instead of verifying that the caller actually supplied/owns the funds being credited. The structural analog in `hydra` is that the core signing APIs — `messageSignerApi.signMessage` and `transactionSignerApi.signTransaction` — accept a caller-supplied `walletAccount` (string name or object) and use it directly to select which account's private key signs the payload, with no verification anywhere in this call chain that the requesting party (e.g., an RPC caller / connected dapp origin) is actually authorized to use that specific `walletAccount`.

### Finding Description
`messageSignerApi.signMessage` forwards `params` (including the caller-supplied `walletAccount`) straight into `messageSigner.signMessage`: [1](#0-0) 

`MessageSigner#signMessage` resolves the `walletAccount` string against `walletAccountsAtom` and dispatches to the seed-based or hardware signer based solely on `walletAccount.source` — with no check of *who is calling*: [2](#0-1) 

Similarly, `transactionSignerApi.signTransaction` resolves a string `walletAccount` from `walletAccountsAtom` and passes it into `transactionSigner.signTransaction`, again with no authorization check tied to the caller: [3](#0-2) [4](#0-3) 

Separately, `hydra` has a `connected-origins` module that is explicitly responsible for tracking which wallet accounts/addresses have been exposed to a given dapp `origin`, and gating account exposure behind `isTrusted`/`getConnectedAccounts`: [5](#0-4) 

However, none of that origin/connection state is consulted anywhere in the `messageSigner`/`transactionSigner` module or API code — the signing modules only depend on `walletAccountsAtom` (all wallet accounts), not on `connectedAccountsAtom`/`connectedOriginsAtom`: [6](#0-5) [7](#0-6) 

These APIs are ultimately exposed over the RPC bridge that connects the untrusted UI/dapp-facing process to the privileged background wallet process (`sdk-rpc`/`browser-extension-rpc` deep-flatten and expose every API method by path, e.g. `messageSigner!signMessage`, `transactionSigner!signTransaction`): [8](#0-7) [9](#0-8) 

I was unable to locate (within the indexed content) the specific web3-provider background handler code (e.g., the Ethereum/Solana provider's `eth_sendTransaction`/`signTransaction` background implementation) that translates a dapp's RPC call into a `transactionSigner.signTransaction`/`messageSigner.signMessage` call, so I cannot confirm with certainty whether that intermediate provider layer enforces the origin-to-account binding before calling these APIs, or whether it also forwards a caller/dapp-chosen `walletAccount` unchecked. This is a gap in the available index and would need direct code inspection in a full Devin session to confirm end-to-end exploitability from a connected dapp.

### Impact Explanation
If any caller reachable through the RPC layer (e.g., a malicious or compromised dapp/content script, or a bug in a provider bridge that passes through a `walletAccount` parameter from dapp input) can supply an arbitrary `walletAccount` value to `messageSigner.signMessage` or `transactionSigner.signTransaction`, it can obtain a valid signature from an account it was never connected to / never authorized for, potentially exposing another account's ability to sign transactions or messages to an unrelated origin. This is directly analogous to the original finding's core defect: a privileged state-mutating operation is driven by attacker-influenced input without validating that the requester is entitled to act on that specific account/asset.

### Likelihood Explanation
Likelihood is **uncertain/moderate** rather than confirmed. The vulnerability pattern (accepting an unauthenticated `walletAccount` identity parameter at the signer-module boundary) is real and verifiable in the code cited above. What is *not* verified from the available index is whether any actually-reachable, less-trusted caller path (browser extension content script → background, or dapp provider RPC) passes a caller-controlled `walletAccount` into these APIs without an intervening origin-authorization check (such as `connectedOrigins.isTrusted`/`getConnectedAccounts`). Without that missing link confirmed, this should be treated as a defense-in-depth gap that needs verification against the concrete provider/background call sites rather than a proven live exploit.

### Recommendation
- In `messageSigner`/`transactionSigner` modules (or in the layer that exposes them over RPC to dapp-originated requests), require an explicit, verified binding between the calling origin/session and the target `walletAccount`, using the existing `connectedOrigins`/`connectedAccountsAtom` primitives (`isTrusted`, `getConnectedAccounts`) before allowing `walletAccount` to be resolved and used for signing.
- Avoid accepting `walletAccount` as a raw external-facing parameter for any RPC method reachable from dapp/content-script contexts; instead derive it server-side from the authenticated/connected-origin state, only allowing selection among the origin's already-approved accounts.
- Audit all web3-provider background handlers (ethereum, solana, bitcoin, algorand, etc.) that ultimately call `transactionSigner.signTransaction` / `messageSigner.signMessage` to confirm the `walletAccount` used is always derived from the connected/approved account for that origin, never from unauthenticated request parameters.

### Proof of Concept
Not directly demonstrable from the indexed code alone, since the concrete dapp-facing provider handler that would supply a caller-controlled `walletAccount` was not found in this pass. Conceptually:
1. A connected/trusted origin is authorized only for `walletAccount: 'exodus_0'` via `connectedOrigins`.
2. If any RPC-reachable path (background message handler, provider bridge, or a debugging/dev API left exposed) calls `exodus.transactionSigner.signTransaction({ walletAccount: 'exodus_1', ... })` or `exodus.messageSigner.signMessage({ walletAccount: 'exodus_1', ... })` using an attacker-influenced `walletAccount` string, the code in `features/tx-signer/src/api/index.ts:33-38` and `features/message-signer/src/module/message-signer.ts:40-52` will happily resolve `'exodus_1'` from `walletAccountsAtom` and sign with it — with no check against `connectedAccountsAtom`/`connectedOriginsAtom` for that origin.
Confirming actual reachability from a dapp requires source access to the provider background handlers (ethereum-plugin/solana-plugin/etc. background implementations), which were not retrievable from the current index.

      signTransaction: async (params: SignTransactionApiParams) => {
        const walletAccount =

            ? await getWalletAccount(params.walletAccount)
            : params.walletAccount

        return transactionSigner.signTransaction({ ...params, walletAccount })
      },
    },
  }
}

  /**
   * Returns the connected accounts for a given origin with the active wallet account sorted first. Can be used while
   * the wallet is locked
   */
  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }

export const flattenObject = <T>(obj: T, path: string[] = []): { [name: string]: Fn } => {
  if (typeof obj === 'function') {
    return { [serializePath(path)]: obj as Fn }
  }

  if (typeof obj !== 'object' || !obj) return {}

  return Object.keys(obj).reduce((acc, key) => {
    return { ...acc, ...flattenObject(obj[key as keyof T], [...path, key]) }
  }, {})
}

export const createRPCProxy = ({ extensionName, channelName }) => {
  if (typeof extensionName !== 'string' || typeof channelName !== 'string') {
    throw new TypeError(`Unable to create RPC because channelName or extensionName are missing`)
  }

  const channel = channels[channelName]
  const transport = createWindowRpcTransport({
    name: `${extensionName}-${channelName}`,
    target: `${extensionName}-${channelName}-window`,
  })

  transport.on('data', async (event) => {
    const isResponse = !JSON.parse(event).method
    const senderMetadata = await metadata
    const options = { senderMetadata }

    if (isResponse) {
      channel.sendMessage(event, options)
    } else {
      channel.call(event, options).then(transport.write)
    }
  })

  channel.onMessage((message, sender) => {
    if (sender.tab) return
    transport.write(message)
  })
}
