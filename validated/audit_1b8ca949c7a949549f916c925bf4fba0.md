### Title
`Webhooks::Request#hmac` / `HmacValidator.validate` bind trust to `@raw_body` only, letting unauthenticated `x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id` headers ride along with any valid signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`to_signable_string` returns only `@raw_body`, and `HmacValidator.validate_signature` computes/compares the HMAC over that string alone, never over `topic`, `shop`, `api_version`, or `webhook_id`. `Registry.process` still uses those same unauthenticated header values to select the handler and to build `WebhookMetadata` passed to app code, so a validly-signed body from one shop can be replayed with forged identity headers and pass `HmacValidator.validate`.

### Finding Description
The intended binding is: `HmacValidator.validate(request) == true` implies the whole webhook delivery — including `request.shop`, `request.topic`, `request.webhook_id`, `request.api_version` — is authentic for that specific delivery. The actual binding enforced by the code is much narrower:

- `Webhooks::Request#hmac` just decodes the `x-shopify-hmac-sha256` header value: `Digest.hexencode(Base64.decode64(...))` [1](#0-0) .
- `Webhooks::Request#to_signable_string` returns `@raw_body` and nothing else [2](#0-1) .
- `HmacValidator.validate_signature` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the received signature — i.e. `HMAC(secret, @raw_body)` only [3](#0-2) .
- `Registry.process` then trusts `request.topic` to pick a handler, and forwards `request.shop`, `request.webhook_id`, `request.api_version` straight into `WebhookMetadata` handed to the app's handler, with the only gate being the body-only HMAC check [4](#0-3) .

So `topic`, `shop`, `api_version`, and `webhook_id` are unauthenticated input that travels alongside a valid signature — nothing in the gem ties them to the signed payload, and nothing tracks previously-seen `webhook_id` values either.

Exploit path: an app's `api_secret_key`/`client_secret` is shared across every shop that installs the app (this is Shopify's own model, not something the app developer controls per-tenant). An attacker can install the target app on their own development shop (explicitly permitted attacker capability) and thereby receive a real, validly-signed webhook: a `(raw_body, hmac)` pair computed with the app's actual secret, without ever learning the secret itself. The attacker then POSTs that exact `raw_body` and `x-shopify-hmac-sha256` value directly to the app's public webhook endpoint, but substitutes `x-shopify-shop-domain` with a victim shop's domain, `x-shopify-topic` with any topic the app has registered a handler for, and any `x-shopify-webhook-id` (including a value already used, since nothing tracks delivery ids). `HmacValidator.validate` still returns `true` because it only checks `raw_body` against the secret, and `Registry.process` calls the handler with `WebhookMetadata` carrying the attacker-chosen `shop`/`topic`/`webhook_id` as if they were authenticated. No other guard exists in this path — `ShopValidator`, `JwtPayload`, and `HttpRequest#verify` apply to OAuth/session-token flows, not to `Webhooks::Request`.

### Impact Explanation
The app's webhook handler receives a forged shop identity, forged topic, and forged webhook id together with a cryptographically "valid" signature. For mandatory compliance webhooks (`shop/redact`, `customers/redact`, `customers/data_request`) or any handler that keys business logic off `data.shop`/`data.topic` (as the gem's own `WebhookMetadata` exposes them), this lets one attacker-controlled installation forge events attributed to an arbitrary victim shop domain — a cross-tenant authentication bypass, matching the Critical "forged webhook accepted as authentic" category. It is repeatable against any victim shop domain the attacker chooses, for any topic the app has registered.

### Likelihood Explanation
Preconditions are minimal and match the stated attacker model: attacker installs the target app on their own free development shop, receives one genuinely signed webhook (any topic), and then crafts arbitrary HTTP POSTs to the app's public webhook endpoint with that same body/signature but forged headers. No access to `api_secret_key` or TLS interception is needed. Cost is a single legitimate webhook delivery to bootstrap a reusable `(body, hmac)` pair; the attack is then repeatable at will against any shop domain string.

### Recommendation
Include `topic`, `shop`, `api_version`, and `webhook_id` (or at minimum `shop` and `topic`) in the string that is HMAC-verified, or otherwise cryptographically bind the header identity to the signed payload before trusting it in `Registry.process`/`WebhookMetadata`. Alternatively, require handlers to independently authenticate `shop` (e.g., via the JSON body's own shop identifier for mandatory webhooks) rather than exposing the raw unauthenticated header value as if it were verified.

### Proof of Concept
```ruby
# test/webhooks/registry_test.rb (new test)
def test_hmac_only_covers_body_shop_header_is_unauthenticated
  raw_body = "{}"
  valid_hmac = Base64.encode64(OpenSSL::HMAC.digest(
    OpenSSL::Digest.new("sha256"),
    ShopifyAPI::Context.api_secret_key,
    raw_body,
  ))

  received_shops = []
  handler = TestHelpers::FakeWebhookHandler.new(
    lambda { |data| received_shops << data.shop },
  )
  ShopifyAPI::Webhooks::Registry.add_registration(
    topic: "some/topic", path: "path", delivery_method: :http, handler: handler,
  )

  headers_a = {
    "x-shopify-topic" => "some/topic",
    "x-shopify-hmac-sha256" => valid_hmac,
    "x-shopify-shop-domain" => "attacker-dev-shop.myshopify.com",
    "x-shopify-webhook-id" => "same-id",
  }
  headers_b = headers_a.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

  ShopifyAPI::Webhooks::Registry.process(
    ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers_a),
  )
  ShopifyAPI::Webhooks::Registry.process(
    ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers_b),
  )

  # Same body + same signature, but the handler received two different, unauthenticated shop identities.
  assert_equal(["attacker-dev-shop.myshopify.com", "victim-shop.myshopify.com"], received_shops)
end
```
Both calls pass `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb` lines 26-31) because only `raw_body` is checked; the assertion shows one valid signature is accepted for two distinct, attacker-chosen shop identities, proving the signature does not cover the values acted on downstream.           if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
