### Title
Unbounded cycle traversal in `AncestryChain::ancestry` causes infinite loop / permanent DoS of the GRANDPA consensus client - ([File: modules/consensus/grandpa/primitives/src/justification.rs])

### Summary
`AncestryChain::ancestry()` walks backward from a `block` hash to a `base` hash purely by following attacker-supplied `parent_hash` fields inside a `BTreeMap` built from `finality_proof.unknown_headers`. The loop has no visited-set / iteration bound and no requirement that the walk strictly decreases toward a known terminus. A relayer can submit two (or more) forged header structs whose `parent_hash` fields point at each other, forming a cycle that is fully contained in the attacker-supplied `unknown_headers` set. When the traversal enters that cycle it never reaches `base` and never hits a `None` lookup (both cycle members are present in the map), so it loops forever. This is architecturally the same bug class as CVE-2020-17444: a length/pointer-advance invariant that is silently violated by attacker input, turning bounded-looking header traversal into an infinite loop.

### Finding Description
`AncestryChain::ancestry` implements `finality_grandpa::Chain`: [1](#0-0) 

```rust
fn ancestry(&self, base: H::Hash, block: H::Hash) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
    let mut route = vec![block];
    let mut current_hash = block;
    while current_hash != base {
        match self.ancestry.get(&current_hash) {
            Some(current_header) => {
                current_hash = *current_header.parent_hash();
                route.push(current_hash);
            },
            _ => return Err(finality_grandpa::Error::NotDescendent),
        };
    }
    Ok(route)
}
```

The `self.ancestry` map is built directly from the untrusted `unknown_headers` field of a relayed `FinalityProof`: [2](#0-1) 

Nothing validates that these headers form an acyclic chain rooted at a genuinely known ancestor before `ancestry()` is called. In `verify_grandpa_finality_proof`, `ancestry()` is invoked twice **before any GRANDPA signature/justification is verified**: [3](#0-2) 

```rust
if base.number() < &consensus_state.latest_height {
    headers
        .ancestry(base.hash(), consensus_state.latest_hash)
        .map_err(|_| Error::InvalidAncestry)?;
}

let finalized = headers.ancestry(from, target.hash()).map_err(|_| Error::InvalidAncestry)?;

// 2. verify justification.
justification
    .verify(consensus_state.current_set_id, &consensus_state.current_authorities)
    .map_err(|e| Error::JustificationVerify(e.to_string()))?;
```

An attacker crafts two fake header objects `H1`, `H2` with arbitrary field values (they need not correspond to any real chain state), setting `H1.parent_hash = hash(H2)` and `H2.parent_hash = hash(H1)`. Both are placed in `unknown_headers`; one is given the largest `number` (becomes `target`), satisfying the `target.hash() == finality_proof.block` check trivially by construction. When `headers.ancestry(from, target.hash())` walks backward from `H1`→`H2`→`H1`→`H2`→…, the map lookup always succeeds for both nodes and `current_hash` never equals `from` (the real trusted hash), so the `while` loop never terminates — before the justification/BLS/GRANDPA-vote check (`justification.verify`) is ever reached, i.e., **no valid signatures are required to trigger the infinite loop**.

This function is reachable via the standard unsigned/permissionless ISMP message path: any relayer submits a `ConsensusMessage` containing this crafted `FinalityProof` through `handle_unsigned`, which calls `Pallet::execute` → `handle_incoming_message` → the GRANDPA `ConsensusClient::verify_consensus` → `verify_grandpa_finality_proof`: [4](#0-3) [5](#0-4) 

Because `handle_unsigned` requires no signature (`ensure_none(origin)?`) and is also executed during `ValidateUnsigned::validate_unsigned` (mempool validation) as well as on-chain block execution, the infinite loop can hang both transaction-pool validation and block execution.

### Impact Explanation
This is a High/Critical-severity denial-of-service against the GRANDPA-based state-machine route: a single crafted, unsigned, permissionless transaction can hang the node's runtime execution (both in mempool validation and in block-authoring/import), because the vulnerable loop is a plain Rust `while` loop with no gas/weight metering internal to it. In a Substrate/parachain context this can stall block production entirely for validators that attempt to include or validate the malicious extrinsic — effectively making the corresponding GRANDPA route permanently unable to deliver messages (satisfying the "route unable to deliver messages" impact criterion), and potentially halting the chain for any collator/validator that processes it.

### Likelihood Explanation
High. The attack requires only:
1. Constructing two arbitrary fake header structs (no real chain data, no signatures, no authority-set knowledge) whose `parent_hash` fields reference each other.
2. Wrapping them in a `FinalityProof.unknown_headers` and submitting via the standard unsigned `handle_unsigned` extrinsic (which pallet-ismp explicitly documents as executable "for free" by anyone with any well-formed message).
3. No cryptographic material or privileged role is needed, and the vulnerable code runs before signature verification.

### Recommendation
Harden `AncestryChain::ancestry` against cycles and unauthenticated header sets:
- Maintain a `visited` set of hashes during traversal and return `Error::NotDescendent` (or a new cycle-detected error) if a hash is revisited before hitting `base`.
- Alternatively/additionally bound the loop by `unknown_headers.len() + 1` iterations, erroring out if exceeded.
- Validate that `unknown_headers` forms a well-ordered, strictly-decreasing-by-number chain before building the `AncestryChain`, rejecting duplicate/cyclical parent references up front.

### Proof of Concept
1. Construct fake headers `H1` and `H2` (arbitrary `number`, `state_root`, `extrinsics_root`, `digest`), setting `H1.parent_hash = H2.hash()` and `H2.parent_hash = H1.hash()`.
2. Set `H1.number` to the maximum among `unknown_headers = [H1, H2]`, and set `finality_proof.block = H1.hash()`.
3. Provide any (even garbage/undecodable-but-non-erroring, or simply any) `justification` bytes — irrelevant, since the loop triggers first — and submit `Message::Consensus(ConsensusMessage { consensus_proof: <encoded FinalityProof>, consensus_state_id, .. })` inside `pallet_ismp::Call::handle_unsigned { messages: vec![msg] }` as an unsigned extrinsic.
4. `verify_grandpa_finality_proof` calls `headers.ancestry(from, target.hash())`, which cycles between `H1` and `H2` forever, hanging the node during transaction-pool validation and/or block execution.
