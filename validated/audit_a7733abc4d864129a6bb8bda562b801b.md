### Title
Unguarded `assetReserve - virtualLtReserve` subtraction in `canGraduate`/`previewLtUntilGraduation` underflow-reverts once rounding drift drains the curve below its virtual floor, permanently freezing curve trading — ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.canGraduate()` and `Bonding.previewLtUntilGraduation()` both compute the USD-leg of the graduation trigger as `realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair)` without ever checking that `assetReserve >= virtualLtReserve` first [1](#0-0) [2](#0-1) . This mirrors the CVE's root cause of reading/using a value before validating it is within the assumed bound: here the code assumes `assetReserve` (the pair's stored LT reserve) can never legitimately fall below the launch-time virtual reserve, but that assumption is not enforced anywhere on the trade path.

### Finding Description
`Router._computeBuy` and `Router._computeSell` both derive the traded-out amount via floor division of `k` and subtract it from the reserve:
- Buy: `tokensOut = reserveToken - (k / newReserveAsset)` [3](#0-2) 
- Sell: `assetOut = reserveAsset - (k / newReserveToken)` [4](#0-3) 

Flooring `k / newReserve` in both directions rounds the *subtracted* term down, which rounds the *output given to the trader* (`tokensOut`, `assetOut`) up. Both formulas therefore round in favor of the trader on every single trade, never in favor of the pool. There is no compensating fee taken by the curve itself (per `docs/contracts-scope.md`: "No fees here — `Zap` handles fees"), so a trader who buys and immediately sells back (a round trip) walks away, on average, with a small net LT profit extracted directly from `assetReserve`, wei by wei, with no mechanism ever pushing value the other way.

Because this bias is one-directional and unbounded, a sufficiently long sequence of permissionless buy/sell round trips through `Bonding.buy` / `Bonding.sell` (reachable by any unprivileged wallet, no special role needed beyond being a registered router/caller of `Bonding`) can drive the pair's stored `assetReserve` strictly below the launch-time virtual reserve (`_launchTimeVirtualLtReserve`, defined as `Pair.k() / Token.TOTAL_SUPPLY()`, which — since `tokenReserve == TOTAL_SUPPLY` at mint — equals the pair's *initial* `assetReserve` exactly).

Once `assetReserve < virtualLtReserve`, the unchecked subtraction:
```solidity
uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
```
underflows and reverts in Solidity 0.8's checked-arithmetic semantics [5](#0-4) . The identical unguarded subtraction also appears earlier in `previewLtUntilGraduation`, *before* that function's own supply-leg donation guard (`if (realBalance >= reserveToken) return ltUntilThreshold;`) [6](#0-5) . `previewLtUntilGraduation` is called on every non-graduated `Zap.buy` to pre-size the LT mint [7](#0-6) , so once the underflow condition is reached, **every subsequent `Zap.buy` on that token reverts unconditionally** — there is no remaining code path that can push `assetReserve` back up except another buy, which itself reverts before it can execute.

This is the direct structural analog of the CVE: a bound (`assetReserve ≥ virtualLtReserve`) is assumed but never validated before the arithmetic that depends on it, and an attacker-reachable, unprivileged input sequence (repeated tiny buy/sell round trips) can violate that bound.

### Impact Explanation
Once triggered, the affected token's curve becomes permanently stuck:
- `Zap.buy` reverts for all traders (via `previewLtUntilGraduation`), freezing all further curve-side purchases.
- `Bonding.canGraduate` also reverts, so the token can never naturally cross the USD graduation trigger, and any code path relying on `canGraduate` (e.g. the post-buy graduation check in `_executeBuy` per `docs/contracts-scope.md`) breaks too.
- All LT and tokens already locked in the `Pair` for that token become permanently unreachable through the intended buy/graduation flow — a freeze of trader, creator, and protocol funds tied to that token's future trading and eventual graduation/LP seeding.
- Sells (`Bonding.sell` → `Router._computeSell`) do not call the underflowing functions directly and may remain the only exit, but the token is permanently stuck at the pre-graduation stage with no route to `Zap.buy` or graduation.

### Likelihood Explanation
The rounding bias is deterministic and always favors the trader on both buy and sell legs — there is no mitigating fee or rounding-toward-pool anywhere in `Router.sol`. Any unprivileged wallet can permissionlessly execute an arbitrary number of buy/sell round trips against `Bonding.buy`/`Bonding.sell` on a token they choose (self-funded, no cooperation needed), so the attack is fully reachable without any privileged role. The number of round trips needed to accumulate a full-unit drift depends on the token's virtual reserve size and the LT's decimal scale, but the drift is strictly monotonic in one direction with no offsetting mechanism, so the underflow condition is guaranteed to be reachable given enough transactions — this is a systemic design gap rather than a probabilistic one.

### Recommendation
- Round the subtracted `k / newReserve` term in `_computeBuy`/`_computeSell` in favor of the pool (round the quotient up, not down) so every trade leaves reserves at or above the ideal constant-product curve, eliminating the drift.
- Independently, harden `canGraduate` and `previewLtUntilGraduation` by guarding the `assetReserve - virtualLtReserve` subtraction the same way the supply leg already guards `reserveToken - realBalance` (`if (realBalance >= reserveToken) ...`), e.g. `if (assetReserve <= virtualLtReserve) { realLtRaised = 0; }` instead of letting it underflow-revert.

### Proof of Concept
1. Launch a token via `Bonding.launch`, creating a `Pair` with `tokenReserve = TOTAL_SUPPLY`, `assetReserve = ASSET_RESERVE` (virtual), `k = TOTAL_SUPPLY * ASSET_RESERVE`.
2. An unprivileged wallet repeatedly:
   a. Calls `Bonding.buy(smallLtAmount, token, self)` → `Router._computeBuy` returns `tokensOut = reserveToken - floor(k/newReserveAsset)`, rounded up in the buyer's favor.
   b. Immediately calls `Bonding.sell(tokensOut, token, self)` → `Router._computeSell` returns `assetOut = reserveAsset - floor(k/newReserveToken)`, again rounded up in the seller's favor.
   Each full round trip nets the caller a small LT profit extracted from `_pool.assetReserve`, with `Pair.swap`'s `(x+1)(y+1) ≥ k` check never blocking it since the Router's own computed amounts already satisfy the tightened invariant.
3. After enough iterations, `_pool.assetReserve` in `Pair.sol` drops below `_launchTimeVirtualLtReserve(token, pair)`.
4. The next call to `Bonding.canGraduate(token)` or `Bonding.previewLtUntilGraduation(token)` — including the one invoked internally by `Zap.buy` — reverts with a `uint256` underflow (`Bonding.sol:691-693` / `Bonding.sol:722`), and every subsequent `Zap.buy` for that token reverts identically, freezing the curve.
