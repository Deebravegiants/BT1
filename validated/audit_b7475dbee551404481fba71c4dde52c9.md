### Title
Floor-rounding asymmetry between curve buy/sell lets an unprivileged trader drive `Pair.assetReserve` below the recovered launch-time virtual reserve, causing a permanent underflow revert in `canGraduate` that bricks all trading and graduation on the token - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.canGraduate` recovers the launch-time virtual LT reserve via `Pair.k() / TOTAL_SUPPLY` and subtracts it from the pair's live stored `assetReserve` with an unchecked Solidity subtraction. `Router._computeBuy`/`_computeSell` use asymmetric floor/ceil rounding when updating the pair's stored reserves, which lets a buy immediately followed by a sell of the same size return the pool to a `tokenReserve`/`assetReserve` pair whose product is *below* `k`, and specifically an `assetReserve` that is 1+ wei *lower* than the original virtual seed. Because `_launchTimeVirtualLtReserve` never changes, this drives `assetReserve - virtualLtReserve` negative, and the subtraction reverts with a Solidity arithmetic-underflow panic. `canGraduate` is called from `Bonding.buy`, `Bonding.sell`, and `Bonding.triggerGraduation` — once it panics, every one of those entry points reverts for that token forever, freezing the curve-held tokens and LT with no owner-only escape hatch.

### Finding Description
`canGraduate` computes: [1](#0-0) 

`_launchTimeVirtualLtReserve` is fixed forever (`Pair.k()` never changes after `mint`), so this is effectively `liveAssetReserve - constant`. The natspec explicitly assumes `assetReserve` only ever grows relative to the virtual seed ("recoverable ... donation-immune raised-LT"), i.e. it assumes `assetReserve >= virtualLtReserve` always holds.

That assumption is broken by the router's rounding:

- Buy floors `tokensOut` (rounds in the pool's favor on the token side): [2](#0-1) 

- Sell floors `k / newReserveToken` when computing the *remaining* `assetReserve`, which is equivalent to rounding `assetOut` *up* (in the seller's favor): [3](#0-2) 

Doing a buy of `amountIn = Δ` and then immediately selling back exactly `tokensOut` tokens can land the post-sell `tokenReserve` one unit above its pre-buy value (`T+1` instead of `T`) due to the ceil/floor mismatch between the two paths. Because `floor(k/T) == A` exactly (as `k = T*A`), but `floor(k/(T+1)) < A`, the seller receives `assetOut` slightly larger than `Δ`, so the resulting `assetReserve` ends up strictly below the pre-buy value — i.e. below `virtualLtReserve` if done as the very first trade on a fresh curve (`assetReserve` starts exactly at `virtualLtReserve` after `Router.addInitialLiquidity`/`Pair.mint`): [4](#0-3) 

`Pair.swap`'s invariant check does not prevent this, because the `+1` slack is derived from the very same floor identity and is always satisfied by construction: [5](#0-4) 

Once `assetReserve < virtualLtReserve`, `canGraduate`'s subtraction underflows and every caller reverts: [6](#0-5) [7](#0-6) [8](#0-7) 

`buy`, `sell`, and `triggerGraduation` are the only ways to move the token forward on the curve or into graduation, and all three unconditionally call `canGraduate`. With `canGraduate` permanently reverting, the token can never trade, never graduate, and never reach `finalizeGraduation`/`LPLock.recordLock`, so the tokens and any real LT already sitting in `Pair` are permanently stranded there — no admin function can recover them (`Router.graduate`/`transferAsset` is only reachable from `_prepareGraduationLiquidity`, which is itself unreachable once `canGraduate` reverts).

### Impact Explanation
This is a permanent freeze of protocol funds reachable by any single unprivileged trader (via `Zap.buy`/`Zap.sell` → `Bonding.buy`/`sell` → `Router.buy`/`sell` → `Pair.swap`), with no privileged recovery path. It matches the "permanent freezing of trader, creator or LP funds" impact class and is structurally the same bug class as the external report: an unchecked, attacker-influenceable arithmetic operation (hex.Decode's length assumption vs. Solidity's reserve-ordering assumption) that panics/reverts and cannot be worked around once triggered, and is trivially and cheaply repeatable against any freshly-launched token.

### Likelihood Explanation
High. The trigger requires only one buy followed by one sell on a freshly-launched curve (before any other trading has padded `assetReserve` above `virtualLtReserve`), sized so the floor/ceil rounding lands the post-sell `tokenReserve` one unit above the pre-buy value. This is a pure integer-rounding property of `_computeBuy`/`_computeSell` and is independent of the external LT's price or any oracle behavior; an attacker can brute-force `amountIn` values off-chain (or simulate) to find one that produces the unfavorable rounding case, then execute the two-transaction (or same-tx) attack against any freshly launched token for the cost of two curve trades.

### Recommendation
- In `canGraduate` (and `previewLtUntilGraduation`), clamp the subtraction: `uint256 realLtRaised = assetReserve > virtual_ ? assetReserve - virtual_ : 0;` instead of letting it underflow.
- More fundamentally, fix the rounding asymmetry in `Router._computeSell`/`_computeBuy` so that round-trip buy+sell sequences cannot reduce the stored `assetReserve` below the value it started at (e.g., round `assetOut` down instead of effectively rounding it up, mirroring the floor used on the buy side for `tokensOut`), and add an explicit invariant assertion in `Pair.swap` that rejects any update where the *un-padded* product falls below the previous un-padded product beyond the documented single-wei buy-side slack.

### Proof of Concept
1. Attacker launches (or waits for) a fresh token; immediately after `Bonding.launch`/seed buy, `Pair`'s reserves are `(tokenReserve = T, assetReserve = A = virtualLtReserve)`, `k = T*A`.
2. Attacker calls `Zap.buy(token, usdcAmount, 0, address(0))` with a `usdcAmount` chosen (via off-chain simulation of `Router._computeBuy`) so that after minting LT and buying `Δ` LT worth of tokens, `tokensOut = T - floor(k/(A+Δ))`.
3. Attacker immediately calls `Zap.sell(token, tokensOut, 0)` to sell exactly the tokens just bought. `Router._computeSell` computes `newReserveToken = reserveToken' + tokensOut`; for the chosen `Δ`, this lands on `T+1` instead of `T`, so `assetOut = reserveAsset' - floor(k/(T+1))`, which exceeds `Δ` by at least 1 wei.
4. Net effect: stored `_pool.assetReserve` after the sell is `A - 1` (or lower), strictly below `virtualLtReserve`. `Pair.swap`'s `(newTokenReserve+1)*(newAssetReserve+1) >= k` check passes trivially (proven above) so the transaction does not revert.
5. Any subsequent call to `Bonding.buy`, `Bonding.sell`, or `Bonding.triggerGraduation` on this token now reverts with a Solidity Panic(0x11) inside `canGraduate`'s `assetReserve - _launchTimeVirtualLtReserve(...)` subtraction, permanently bricking the token's curve and graduation path while any tokens/LT already in `Pair` remain stuck.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
