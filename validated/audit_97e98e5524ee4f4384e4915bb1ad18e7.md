The docs explicitly present `ShopifyAPI::Webhooks::Registry.process` as verifying "the request did indeed come from Shopify," and hand developers `data.shop` as the trusted tenant identifier — but the code only proves the raw body is untampered, not which shop it came from.

## Title
Cross-tenant webhook impersonation via `shop` field not covered by HMAC - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies webhook authenticity by checking only that the HMAC over the raw request body matches, then trusts the unauthenticated `shopify-shop-domain` header to identify the tenant shop passed to the app's handler. Because the `shop` value is never included in the signed bytes, an attacker who obtains one valid `(body, hmac)` pair signed by the app's shared `client_secret` (e.g. by installing the app on their own free/dev store and capturing a legitimate webhook) can replay that exact body+HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header of any victim shop. The HMAC check still passes, and the app processes attacker-controlled data as if it originated from the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, independent of anything covered by the signature: [2](#0-1) 

`Registry.process` validates only the HMAC over the body via `Utils::HmacValidator.validate(request)`, and then immediately forwards `request.shop` — the unauthenticated header value — to the app's handler as the tenant identity: [3](#0-2) 

`HmacValidator.validate` only calls `verifiable_query.to_signable_string`, which for `Request` is the raw body, so the `shop` never enters the equality being checked: [4](#0-3) 

The identity binding the library implicitly claims to enforce is `shop_header == shop_that_produced(hmac(body))`. In reality, the check only proves `hmac == HMAC(client_secret, body)`; it never proves the `shop` header corresponds to the shop that triggered that specific webhook. Since Shopify signs webhooks for *all* shops of an app with the same `client_secret`, any legitimately obtained `(body, hmac)` pair — even one generated by the attacker's own store — remains valid regardless of which `shop` header accompanies it. The documentation in `docs/usage/webhooks.md` explicitly tells developers that `Registry.process` "will verify the request did indeed come from Shopify," reinforcing that `data.shop` is meant to be a trusted, verified value, which it is not.

### Impact Explanation
This breaks the tenant/shop boundary that this library's `Webhooks::Request`/`Registry.process` API is designed to protect. An app that uses `data.shop` (per the documented usage pattern) to decide which merchant's records to update, which merchant's session/access token to load, or which merchant's data to expose, can be made to act on a victim shop's identity using attacker-supplied body content. This is a cross-tenant confusion vulnerability: any actor who can install the app on any shop (including their own) — an unprivileged action — can spoof webhooks purportedly from a different, victim shop.

### Likelihood Explanation
Likelihood is limited by the fact that the attacker needs at least one legitimately signed `(body, hmac)` pair, which they can trivially obtain by installing the target app on their own store (a normal, low-privilege action any internet user can perform for a public app) and capturing the resulting webhook. Replaying that captured request with a modified `shopify-shop-domain` header requires no secret knowledge and is unauthenticated.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value verified against the HMAC, or independently corroborate the `shop` header against an out-of-band source of truth (e.g., only accept a `shop` for which the app has a known, previously stored session/installation) before trusting it in `WebhookMetadata`. At minimum, document prominently that `data.shop` is not authenticated by the HMAC check and must be cross-validated by the host application against known installed shops.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw body `B` and the resulting `shopify-hmac-sha256` header `H` — both are legitimately produced using the app's real `client_secret`.
2. Attacker sends a POST to the app's webhook endpoint with the same raw body `B`, the same `H` in `shopify-hmac-sha256`, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, B)` and compares to `H` — this matches, since `shop` is not part of `to_signable_string`.
4. The app's `WebhookHandler#handle` is invoked with `data.shop == "victim-shop.myshopify.com"` and `data.body` fully attacker-controlled, even though this data never came from the victim shop.
