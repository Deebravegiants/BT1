Confirmed: `WebhookMetadata.shop` is passed directly to the app's handler and is exactly the header-derived `request.shop`, which is not part of `to_signable_string`. This confirms the vulnerability.

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-identity spoofing on replayed webhooks - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity solely by checking the HMAC over the raw request body, but the `shop` value that gets handed to the host application's handler is read from an HTTP header that is never included in that HMAC computation. This breaks the identity binding `HMAC(body, secret) == valid ⇒ shop header is trustworthy`, which the library implicitly assumes but does not enforce.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`. Its `to_signable_string` returns only the raw body: `@raw_body` [1](#0-0) . The `shop` accessor, however, is derived purely from the `shopify-shop-domain` (or `x-shopify-shop-domain`) header, which is attacker-controlled and completely outside the signed material: [2](#0-1) .

`Registry.process` verifies authenticity by calling `Utils::HmacValidator.validate(request)`, which only recomputes and compares the HMAC of `to_signable_string` (i.e., the raw body) against the `hmac` header: [3](#0-2)  and [4](#0-3) . After this check passes, `request.shop` is forwarded verbatim into `WebhookMetadata`, which is passed to the app-defined handler as the authoritative tenant identifier: [3](#0-2)  and [5](#0-4) .

Because the shop domain is never part of the signed payload, `HMAC(body)` being valid says nothing about which shop the header claims to be from. Concretely, the equality the code needs but never checks is:
`shop_bound_by_hmac == shop_used_by_handler`
but instead what holds is only:
`hmac(body, secret) == received_hmac` while `shop` is read independently and unauthenticated.

An attacker who legitimately owns any Shopify store (e.g., a free development store) can install the target app on that store, causing Shopify to send a validly-HMAC-signed webhook (signed with the app's real secret) for their own shop. The attacker captures this raw body + valid HMAC pair (both are delivered to their own server/endpoint if they configure the webhook delivery URL, or observable through their own infrastructure — no interception of the victim's traffic or the app's secret is needed since Shopify sends it to whatever callback URL is registered for the attacker's own shop). The attacker then replays the exact same body and HMAC value to the target app's webhook endpoint, only substituting the `shopify-shop-domain` header with a victim shop's domain. Since the header is not covered by the HMAC, the signature still validates, and the handler processes the payload as if it came from the victim shop — a cross-tenant identity confusion.

### Impact Explanation
This crosses the tenant boundary the library is meant to enforce: a webhook payload legitimately generated for shop A can be replayed and attributed to shop B purely by editing an unsigned header, with the HMAC check still passing. Any host application logic that uses `WebhookMetadata#shop` to scope database writes, cache invalidation, order/inventory updates, or trigger per-merchant side effects can be manipulated by an attacker who only needs to control one legitimate (even free) Shopify store where the app is installed. This matches the Critical bar of cross-tenant access.

### Likelihood Explanation
Exploitation requires only: (1) the attacker installs the target app on a shop they control (a normal, unprivileged action any Shopify merchant can do, including via a free dev store), (2) capture one webhook delivery for their own shop, and (3) replay it against the app's public webhook endpoint with the `shop-domain` header rewritten. No access to the app's `client_secret`/`api_secret_key`, no TLS interception, and no privileged account is required — the attacker only ever interacts with data addressed to their own shop.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the HMAC-signed material, or otherwise bind the verified body to the specific shop before handing control to `WebhookHandler#handle`. Concretely, `Request#to_signable_string` should incorporate `shop` (and other Shopify-supplied identity headers relied upon by handlers) so that `HmacValidator.validate` fails if any of these are tampered with, restoring the equality `hmac(body) valid ⇒ shop header authentic`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers/receives a webhook, e.g. `orders/create`, capturing:
   - raw body `B`
   - header `shopify-hmac-sha256: H` (valid HMAC of `B` under the app's real secret)
2. Attacker sends a POST to the app's webhook endpoint with:
   - `raw_body: B`
   - headers: `shopify-hmac-sha256: H`, `shopify-topic: orders/create`, `shopify-shop-domain: victim.myshopify.com`
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and finds it matches `H` — validation succeeds despite the shop header being forged [6](#0-5) .
4. `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ..., ...))` is invoked, and the host application processes attacker-supplied order data as belonging to `victim.myshopify.com`.
