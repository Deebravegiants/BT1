### Title
Native ETH (and any untracked token) moved by Emporium operations is not included in the balance-accounting loop, allowing theft of stray/leftover funds held by the `EmporiumUpgradeable` contract - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` executes arbitrary calls (including sending native ETH via `op.endpoint.call{value: op.value}(op.callData)`) but only verifies the resulting balance change for the tokens explicitly listed in `circomData.erc20TokenAddresses`. When the stateless path is used (`stack.signerAddress == address(0)`), `verifyWallet` performs no per-op authorization at all beyond marking the `emporiumMessage` used. Any user who can produce a valid ZK proof for their own (unrelated) shielded UTXO can therefore craft `externalActionMetadata` whose ops send any ETH (or ERC-20 token) balance currently held by the Emporium contract to an address of their choosing, as long as that asset is simply omitted from `circomData.erc20TokenAddresses` for that call. This mirrors the reported class of bug: a value transfer performed through an arbitrary call that is not accounted for in the contract's balance/value equation.

### Finding Description
In `runAction`, the only funds that are checked for correct accounting are the ones in `circomData.erc20TokenAddresses`: [1](#0-0) 

Each `EmporiumOperation` can target an arbitrary `endpoint` with arbitrary `callData` and `value` (including native ETH): [2](#0-1) 

After the ops execute, the contract only diff-checks balances for the addresses in `circomData.erc20TokenAddresses`: [3](#0-2) 

If native ETH (`address(0)`) — or any other token that the Emporium contract happens to be holding — is not included in this array, any amount of it moved out via the op loop is completely invisible to the balance-diff/`BalanceChangeShouldBePositive` check. Unlike `Hinkal.sol`, which explicitly special-cases `address(0)` by adding `msg.value` to the balance-diff computation: [4](#0-3) 

`EmporiumUpgradeable` has no equivalent native-asset accounting at all — `getBalancesForArray` is only ever called with `circomData.erc20TokenAddresses`, so if a caller simply excludes `address(0)` (or any other token the contract is holding) from that array, moving it via an op is entirely unchecked.

Critically, when `stack.signerAddress == address(0)` (the "stateless" path), `verifyWallet` performs no signature check on the ops whatsoever — it just marks the `emporiumMessage` as used and returns: [5](#0-4) 

The only binding of `externalActionMetadata` (which encodes the `EmporiumStack`/ops) is via `circomData.calldataHash`, which is checked purely against `msg.data` of the current call: [6](#0-5) 

and is fixed by whoever generates the ZK proof (i.e., the caller themselves, using their own valid UTXO nullifiers) — it does not prove that the ops only touch assets that caller is entitled to. Any unprivileged EOA that owns any spendable shielded UTXO (of any token, even a trivial one) can therefore generate a valid proof, set `externalActionData.externalActionId` to the Emporium action, choose `erc20TokenAddresses` that excludes whichever asset the Emporium contract happens to be holding (e.g., stray/leftover ETH from a prior swap-style op that refunded unused value back to the contract), and include a stateless op `{endpoint: attacker, value: <Emporium's ETH balance>, callData: ""}` to drain it — all while satisfying the in-circuit balance equation for the (unrelated) tokens actually declared.

### Impact Explanation
This allows unauthorized draining of any native ETH (or other untracked token) balance held by the `EmporiumUpgradeable` contract — funds that may be residual/in-flight value belonging to the protocol or to other users (e.g., leftover ETH from swap refunds performed through earlier Emporium ops), moved to an address never authorized by the actual owner of those funds. This falls under "theft or permanent freezing of protocol/relay fees" / "temporary freezing of user funds" / "moving assets... a prover never authorised" (the attacker's own proof only authorizes spend of their own UTXO, not the third-party residual balance sitting in the Emporium contract).

### Likelihood Explanation
Exploitability depends on the Emporium contract actually holding an unaccounted balance (e.g., ETH change/refund from a prior op-based swap, or dust from partial fills) at the time of the attack. This is a realistic but not always-available condition, since well-behaved ops typically sweep balances for tracked tokens back to `msg.sender` via `handleOut`, but nothing sweeps balances for tokens not included in a given call's `erc20TokenAddresses`. Any EOA holding a spendable shielded UTXO of any denomination can attempt this at will, so likelihood scales with how often the Emporium accumulates untracked native/ERC-20 balance in practice.

### Recommendation
- Include native ETH (and ideally any token actually held by the Emporium contract as a result of the ops) in the pre/post balance accounting loop of `runAction`, analogous to how `Hinkal.sol` folds `msg.value` into the `address(0)` balance diff.
- Require that every `EmporiumOperation.value > 0` correspond to an entry in `circomData.erc20TokenAddresses` (i.e., `address(0)` must be declared whenever any op sends ETH), and revert otherwise.
- Consider disallowing/limiting stateless ops (`signerAddress == address(0)`) from sending native value at all, or require an explicit `receive`/sweep step so that no asset can leave the contract without being reflected in the balance-diff check.

### Proof of Concept
1. Prior legitimate transaction leaves stray ETH in `EmporiumUpgradeable` (e.g., an Emporium op performing a DEX swap gets partial ETH refund from the router back to the Emporium contract, and that transaction's `circomData.erc20TokenAddresses` did not include `address(0)`).
2. Attacker (any EOA with a spendable shielded UTXO for any token, e.g. a trivial dust deposit) generates a valid ZK proof for their own UTXO spend, with:
   - `externalActionData.externalActionId` = Emporium action id
   - `externalActionData.externalActionMetadata` = ABI-encoded `EmporiumStack{ signerAddress: address(0), ops: [{endpoint: attacker, invokeWallet: false, value: <emporium ETH balance>, callData: "0x"}], maxFee: 0, deadline: <future> }`
   - `circomData.erc20TokenAddresses` = attacker's own dust token only (no `address(0)`)
3. `Hinkal.transact` verifies the proof and calls `EmporiumUpgradeable.runAction`.
4. `verifyWallet` short-circuits (signerAddress == 0), no signature check on the op is performed.
5. The op `attacker.call{value: emporium's ETH balance}("")` executes, draining the ETH to the attacker.
6. `balanceChange` accounting only loops over the attacker's declared dust token, so the missing ETH is never detected and the transaction succeeds.
