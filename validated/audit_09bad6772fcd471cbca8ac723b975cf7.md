### Title
Webhook `shop` identity is taken from an unauthenticated header that the HMAC signature never covers - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the webhook signature over the raw body only, while the `shop`, `topic`, `api_version`, and `webhook_id` fields used downstream to identify the tenant and dispatch the handler are read straight from HTTP headers that are never included in the HMAC-signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled directly from request headers with no cryptographic binding to the signed body: [2](#0-1) [3](#0-2) 

`ShopifyAPI::Webhooks::Registry.process` validates only the body's HMAC and then trusts `request.shop` (and `request.topic`) as the tenant identity passed into the handler: [4](#0-3) 

`ShopifyAPI::Utils::HmacValidator.validate` confirms this: it calls `verifiable_query.to_signable_string` (the raw body) and HMAC-compares it against `verifiable_query.hmac`, never touching `shop`, `topic`, or any other header: [5](#0-4) 

The identity binding that should hold is: `shop authenticated by HMAC == shop used by the handler for tenant-scoped side effects`. Because the HMAC only signs the body bytes, this equality is not enforced — the `shop-domain` header (and `topic`/`webhook_id`) can be swapped freely by anyone who can present *any* previously-observed valid `(body, hmac)` pair for the merchant's shared secret, without invalidating the signature check. The webhook's tenant identity is effectively derived from bytes that were never verified.

### Impact Explanation
An attacker who can capture or otherwise obtain one legitimate `(raw_body, hmac)` pair generated by Shopify for the app (e.g., by intercepting a webhook delivery, or via a shop they control receiving their own legitimate webhooks) can replay that exact body+HMAC to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` header. `Registry.process` will accept it (HMAC still validates against the unchanged body) and dispatch the handler with `WebhookMetadata.shop` set to the attacker-chosen shop, causing the host application's handler to associate the replayed body's contents (e.g., order/customer data) with the wrong tenant. This is a cross-tenant identity-confusion vector caused entirely by this gem's failure to bind the header-derived shop to the HMAC-verified payload.

### Likelihood Explanation
Exploitation requires the attacker to already possess at least one valid `(body, hmac)` pair — for example from a shop they legitimately operate, or by intercepting webhook traffic to the app. Given that, no possession of `api_secret_key` is needed to perform the header-swap replay, since the check never inspects the header at all. This is a plausible, low-effort attack once a single valid webhook sample is obtained, and is a design flaw purely internal to this gem's `Webhooks::Request`/`Registry` implementation rather than a host-application misuse issue.

### Recommendation
Bind the tenant-identifying fields to the HMAC verification: either include `shop`, `topic`, and `webhook_id` in the signed string (`to_signable_string`) so any header tampering invalidates the signature, or require host applications to cross-validate `request.shop` against an independently-known registered shop for that webhook subscription before trusting it in `WebhookHandler#handle`. At minimum, `docs/` should explicitly warn that `WebhookMetadata#shop`/`#topic` are not cryptographically bound to the HMAC and must not be trusted as an authenticated tenant identifier by themselves — though per scope, doc-only fixes are out of scope for a code-level fix.

### Proof of Concept
```ruby
# Attacker has previously observed (or generated via their own shop) one legitimate
# (raw_body, hmac) pair delivered by Shopify to the app's webhook endpoint:
raw_body = '{"id": 12345, "note": "legit order payload"}'
valid_hmac_b64 = "..."   # captured from a real Shopify webhook delivery

# Replay it, but claim it belongs to a *different* shop:
forged_headers = {
  "x-shopify-topic"       => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac_b64,      # unchanged, still verifies against raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # attacker-controlled value
  "x-shopify-webhook-id"  => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate passes (only raw_body is checked),
#    handler.handle is invoked with data.shop == "victim-shop.myshopify.com",
#    even though that shop never sent this webhook.

# typed: strict
# frozen_string_literal: true

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }
      def shopify_header(name)
        @headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]
      end
    end
  end
end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
