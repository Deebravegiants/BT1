## Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` (tenant identity) is read from an HTTP header that is never included in the signed bytes. `ShopifyAPI::Webhooks::Registry.process` trusts this header value as the authenticated shop when dispatching to the app's webhook handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers, none of which are part of `to_signable_string`: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. against the raw body bytes exclusively: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (the unsigned header) as the tenant identity passed to the app's handler: [4](#0-3) 

The binding that should hold is: `shop header == shop that produced/authorized this exact body`. Because the header is excluded from the HMAC input, that equality is never checked. Since the HMAC key is the app's single `client_secret` — identical across every shop that has the app installed — any body+HMAC pair that is genuinely produced for **one** shop remains a valid HMAC for the **same bytes** regardless of which `shop-domain` header accompanies it. An attacker who operates their own store with the app installed can trigger a webhook (e.g. by performing an action that produces a predictable/attacker-controlled body, or by simply capturing any webhook delivery to their own endpoint), then replay the exact `raw_body` + `X-Shopify-Hmac-Sha256` header to the target app's webhook endpoint while substituting `X-Shopify-Shop-Domain` with a victim shop that also has the app installed. `HmacValidator.validate` will pass (body bytes/signature match), and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop:` is the victim's domain.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: an unprivileged user who merely has their own install of the app can inject an HMAC-“valid” webhook that the app processes as belonging to a different, victim shop. Depending on the app's webhook handler logic, this enables cross-tenant data corruption/injection (e.g. mandatory `shop/redact`, `customers/redact`, `app/uninstalled`, or business webhooks acting on the wrong tenant's records) — a cross-tenant access vulnerability.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate (even free-tier) merchant with the app installed on their own store, so they can obtain at least one raw body whose HMAC they can capture and replay; no access token, `client_secret`, or victim credentials are needed. The only extra step is delivering an HTTP POST with a forged header to the target's public webhook endpoint, which is standard for any app exposing a webhook receiver built on this gem.

### Recommendation
Include the shop domain (and ideally topic/webhook id/api version) in the HMAC-signed content, or otherwise cryptographically bind the `shop-domain` header to the payload (e.g., derive/verify shop identity from a per-shop secret or from the registered webhook subscription rather than trusting an unsigned header). At minimum, document and enforce that handlers must independently verify `data.shop` corresponds to a shop with an active session/installation before acting on webhook content.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers/captures a legitimate webhook delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(client_secret, B)`).
2. Attacker POSTs to the app's webhook endpoint with the same body `B`, the same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (a shop that also installed the app).
3. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate(request)`, which passes because only `B` and `H` are checked.
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` and processes attacker-supplied data under the victim's tenant identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
