### Title
Unauthenticated `RequestState` handler bypasses source-identity validation and replays last signup message to any sender - ([File: orb-relay-client/src/client.rs])

### Summary
In `PollerAgent::main_loop`, every inbound relay message that matches `self_serve::app::v1::RequestState` is answered by replaying `self.last_message` **before** the code checks whether the message actually came from the configured counterpart (`src.id == self.config.dst_id`). That identity check is only applied to the `else if` branch that handles all other payload types. This mirrors the reported bug class: a security-relevant "is this identifier in the allowed/expected set" check (there: `_reward` vs `rewardTokens`; here: `src.id` vs `config.dst_id`) is skipped for one specific code path, letting anyone who can put a `RequestState` payload on the stream extract cached state without being validated as the legitimate remote party.

### Finding Description
`Client` is orb-core's wrapper around the bidirectional Orb-Relay gRPC stream used during self-serve signup flows (`src/plans/mod.rs`, `src/brokers/orb.rs` reference this client). In the main receive loop: [1](#0-0) 

every message received from the relay server is matched:
- If the payload matches `self_serve::app::v1::RequestState`, the agent immediately sends back `self.last_message.clone()` to the peer — with **no check at all** on `src.id`.
- Only in the `else if` branch (for every other payload type) is `src.id != self.config.dst_id` verified, and mismatched senders are rejected and logged as "unexpected source".

`self.last_message` is set on every outgoing send to whatever payload the orb/app most recently transmitted over that relay session (e.g., `AnnounceOrbId`, `SignupEnded`, or other signup-state payloads): [2](#0-1) 

Because the source-identity check that legitimately gates all other inbound traffic is structurally excluded from the `RequestState` branch, the mechanism designed to ensure only the expected counterpart (matching `config.dst_id`) can interact with a session is defeated for this one message type — the same class of omission as the reported DeFi bug, where a per-type/per-token validity check was missing on one specific entry point (`distributeRewards`/`claimRewards`) while being present elsewhere in the same contract family.

### Impact Explanation
If the relay transport or its authorization model allows a party other than the intended orb/app counterpart to place a `RequestState` payload with an arbitrary claimed `src` onto the stream for a given session/queue, that party can trigger a replay of the last signup-flow protocol message (which can include signup completion/session state) without passing the same source-authentication gate applied to every other message type. This is a state-disclosure / cross-session-bleed risk in the signup relay channel: state intended for one authenticated party is releasable to an unauthenticated requester purely by sending the special `RequestState` message, bypassing the very check that exists to enforce this boundary.

### Likelihood Explanation
The vulnerable code path is on the primary receive loop of every relay-based session (`main_loop`), which is exercised for every signup session that uses the Orb-Relay client (referenced from `src/plans/mod.rs` and `src/brokers/orb.rs`). The bypass requires no special privilege beyond being able to deliver a `RequestState`-typed payload into the stream that the poller reads — it does not require compromising the reward/token contract analogs (hardware access, malicious operator, etc., which are out of scope) — making it a reachable, low-effort trigger once a message with the right type reaches the client's response stream handling.

### Recommendation
Apply the same source-identity validation uniformly, regardless of payload type: check `src.id == self.config.dst_id` before branching on payload type, and only then decide whether to answer `RequestState` requests. Concretely, restructure the match so the source check happens first, e.g.:

```rust
Some(Ok(RelayConnectResponse {
    msg: Some(relay_connect_response::Msg::Payload(RelayPayload {
        src: Some(src), dst, seq, payload: Some(payload),
    })),
})) => {
    if src.id != self.config.dst_id {
        tracing::error!("Skipping received message from unexpected source: {:?}", src.id);
    } else if self_serve::app::v1::RequestState::matches(&payload).is_some() {
        sender_tx.send(self.last_message.clone()).await.wrap_err("Failed to send outgoing message")?;
    } else {
        self.handle_message(RelayPayload { src: Some(src), dst, seq, payload: Some(payload) }, message_buffer).await?;
    }
}
```

### Proof of Concept
1. Establish (or otherwise gain the ability to inject into) a relay stream targeting a given `orb_id`/`session_id` pair used by an active `Client` (as configured via `Client::new_as_orb`/`new_as_app`). [3](#0-2) 
2. Send a `RelayConnectResponse` payload whose `payload` matches `self_serve::app::v1::RequestState`, with an arbitrary/spoofed `src` (not equal to `config.dst_id`).
3. Observe that `main_loop` responds with `self.last_message.clone()` — the most recently sent signup-flow message — without ever evaluating or enforcing `src.id != self.config.dst_id`, unlike the handling for every other payload type. [4](#0-3)
