### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) headers are trusted for tenant identity without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the raw request body against the `X-Shopify-Hmac-Sha256` header, but the `shop-domain`, `topic`, and `webhook-id` values that identify *which tenant* the webhook belongs to are read from separate HTTP headers that are never included in the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors instead read directly from caller-supplied headers, independent of the signed body: [2](#0-1) [3](#0-2) 

`Registry.process` validates only the body/HMAC pair via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

`HmacValidator.validate` computes the signature exclusively from `verifiable_query.to_signable_string`, i.e., the body: [5](#0-4) 

The binding that should hold is: `hmac == HMAC(secret, body || shop || topic)`. In this implementation the equality actually enforced is `hmac == HMAC(secret, body)`, while `shop`/`topic`/`webhook_id` are unauthenticated fields acted upon (used to build tenant-identifying `WebhookMetadata`) but never bound into the signature. `WebhookMetadata.shop` is a plain `String`, and downstream handlers (per the gem's documented contract) use `data.shop` as the tenant key to persist/act on data.

### Impact Explanation
Because any request satisfying `HMAC(secret, body) == signature` is accepted regardless of the `shop-domain` header value, a party who has ever observed one legitimate webhook body+HMAC pair for their own shop (a normal, unprivileged tenant/merchant of a multi-tenant app — webhook bodies for many topics, e.g. `app/uninstalled`, `shop/redact`, contain no shop-specific secret and the HMAC value itself is visible to anyone who can see the request, e.g. via logs, a browser devtools proxy, or by simply being the recipient of their own shop's webhook) can resend that exact `(body, hmac)` pair to the app's webhook endpoint with the `shop-domain` header changed to a different shop. The signature still validates (it only checks the body), and the registry hands the forged shop identity straight to the app's handler as `WebhookMetadata.shop`, `topic`, and `webhook_id`. Any application that uses `data.shop` to select/mutate per-tenant data or trigger tenant-scoped side effects (e.g. mandatory GDPR topics `customers/redact`, `shop/redact`, `customers/data_request` are always registered per `Registry::MANDATORY_TOPICS`) can be tricked into applying another tenant's payload against a different shop's records — a cross-tenant boundary break driven entirely by an unauthenticated header field.

### Likelihood Explanation
The attacker needs no `api_secret_key`, no access token, and no privileged account — only the ability to send an HTTP POST to the app's public webhook endpoint and knowledge of one previously-received `(body, hmac)` pair for their own tenant, which is inherently visible to the shop that received it. The gem's own design silently reuses this weakly-scoped verification for all webhook topics, including the mandatory redact/data-request topics that every embedded app must implement.

### Recommendation
Bind the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`) into the HMAC-signed material (e.g., include them in `to_signable_string`, or require the caller to separately re-verify `shop` against session/install records before trusting `WebhookMetadata.shop`), rather than relying on body-only HMAC verification while treating header-derived fields as trusted identity.

### Proof of Concept
1. App merchant "shop-a.myshopify.com" receives a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid because `H == HMAC(secret, B)`), `X-Shopify-Shop-Domain: shop-a.myshopify.com`.
2. Attacker (the same merchant, or anyone who can observe that request, e.g. via a debugging proxy on their own store) resends the identical body `B` and HMAC header `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com` (and/or a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and matches `H` — validation succeeds: [6](#0-5) 
4. The handler receives `WebhookMetadata.new(topic: request.topic, shop: "shop-b.myshopify.com", body: parsed(B), ...)` and performs its tenant-scoped action against `shop-b` using data intended for `shop-a`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
