### Title
Source Identity Check Bypassed for `RequestState` Messages in Orb-Relay Client - ([File: orb-relay-client/src/client.rs])

### Summary
The `orb-relay-client` enforces a source-identity check (`src.id != self.config.dst_id`) before processing any inbound relay message, intended to reject messages that do not originate from the paired peer (orb or app) for the current signup session. However, this check is completely skipped for messages matching the `self_serve::app::v1::RequestState` payload type, which are unconditionally accepted and acted upon regardless of the `src` field. This mirrors the `BribeRewarder::deposit()` root cause pattern from the referenced report: a security/identity check exists in the code path, but a specific call/message pattern bypasses it entirely, breaking the intended trust boundary between session peers.

### Finding Description
In `PollerAgent::main_loop`, every incoming `RelayPayload` is supposed to be validated against the expected peer identity before being handed to application logic: [1](#0-0) 

Specifically:
```rust
if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx.send(self.last_message.clone()).await...
} else if src.id != self.config.dst_id {
    tracing::error!("Skipping received message from unexpected source: ...");
} else {
    self.handle_message(...).await?;
}
```
The `else if src.id != self.config.dst_id` branch is the trust-boundary check that discards messages whose `src` does not match the configured peer (`dst_id`) for this session — this is the analog of `BribeRewarder`'s `onlyVoter`/`ownerOf` check that is supposed to gate who may drive state transitions. But the `RequestState` branch is evaluated first and unconditionally re-sends `self.last_message` (the last outgoing message for this client/session) without ever checking `src.id`. Any relay message whose payload matches `RequestState` — irrespective of which `src` entity it claims to be from — triggers a resend of the client's last message.

This is structurally identical to the reported bug class: a security check exists (`src.id != dst_id`), but one specific call path (here, `RequestState` payloads) is routed around it entirely, so the identity/authorization boundary does not apply uniformly across all reachable code paths.

### Impact Explanation
Because the relay server multiplexes different session entities and the orb/app client only trusts `src.id == dst_id` as the peer-identity boundary, an attacker able to inject or replay a `RequestState`-shaped payload (e.g., a malicious or compromised peer on the relay, or cross-session message leakage) can force the orb-relay client to retransmit its last message (`self.last_message`) without any verification that the request actually came from the legitimate paired session peer. This undermines the identity binding between the physical Orb session and the App session that self-serve signup flow relies on (`self_serve` mode, `orb_relay_app_id` binding in `src/plans/mod.rs`), and could be leveraged to trigger cross-signup state bleed — causing the orb to re-emit session state (e.g., `SignupEnded`/status messages) toward a party that never proved it is the correct session counterpart. [2](#0-1) 

### Likelihood Explanation
This requires an attacker to be able to submit a message on the relay channel matching `RequestState` with an arbitrary/spoofed `src` — a capability an unprivileged app-side or relay-connected peer could plausibly have, since the check that would normally reject foreign sources is the exact mechanism disabled for this payload type. No privileged/relay-server-operator access is required; only the ability to send a `RequestState`-typed message is needed. Full end-to-end exploitability (e.g., confirming the relay server does not itself filter by `src` before delivery) could not be verified from the indexed code alone.

### Recommendation
Move the `src.id != self.config.dst_id` check ahead of the `RequestState` special case so that source-identity validation applies uniformly to all payload types, including `RequestState`. Only after confirming the message's `src` matches the expected session peer should the client resend `self.last_message`.

### Proof of Concept
1. Establish (or intercept) a relay connection such that the orb-relay client is running `main_loop` for a given session (`dst_id` = expected peer).
2. Send a `RelayConnectResponse` containing a `RelayPayload` whose `payload` matches `self_serve::app::v1::RequestState`, but whose `src.id` does **not** equal `self.config.dst_id` (i.e., spoofed/foreign source).
3. Observe that the `else if src.id != self.config.dst_id` branch is never reached for this payload — the client unconditionally executes `sender_tx.send(self.last_message.clone())`, resending the last outgoing message regardless of the sender's true identity. [3](#0-2) 

**Uncertainty note:** I was unable to fully verify from the indexed code whether the relay server itself performs additional server-side source authentication that would prevent an attacker from delivering a payload with an arbitrary `src` to this client (this would affect real-world exploitability). The `orb-relay-client` crate's server-facing connection/auth logic and the relay server implementation were not available in the indexed context; a full assessment would require inspecting the relay server's routing/auth code, which may not be part of this repository.
