## Finding

The `pallet-ismp-relayer` pallet has the same root-cause bug class as the reported `SolverVaults::setDepositLimit` issue: a governance-set threshold is written to storage without validating it against the current value of the state it gates, retroactively freezing legitimate holders who are below the new threshold with no way to fix it if their activity has stopped.

### Title
`set_minimum_withdrawal` can permanently freeze already-accumulated relayer fees below the new minimum - ([File: modules/pallets/relayer/src/lib.rs])

### Summary
`Pallet::set_minimum_withdrawal` overwrites `MinimumWithdrawalAmount[state_machine]` with an arbitrary new value with no check against relayers' currently accumulated `Fees[state_machine][relayer]` balances. `Pallet::withdraw` (the only unprivileged, permissionless path to redeem fees) hard-reverts with `NotEnoughBalance` whenever `available_amount < min_withdrawal_amount`, and there is no partial-withdrawal path. A relayer whose already-accumulated balance sits below a newly raised minimum is locked out of withdrawing it until they accumulate more fees on that exact `(state_machine, address)` pair — which is impossible if that destination is deprecated, low-traffic, or the relayer simply stops delivering to it.

### Finding Description
`set_minimum_withdrawal` is a privileged call, but it mutates a threshold that gates an unprivileged, permissionless action (`withdraw_fees`, dispatched via `ensure_none`): [1](#0-0) 

It performs an unconditional `insert`, with no comparison to any relayer's outstanding `Fees` balance for that `state_machine`: [2](#0-1) 

`withdraw` reads `available_amount` from `Fees` and reverts outright if it is below the configured minimum — there is no fallback to withdraw a smaller amount, and no other extrinsic exists to redeem a sub-minimum balance: [3](#0-2) 

The only way to increase a specific `(state_machine, address)` `Fees` entry is via `accumulate`, which requires proving a *new* fee-delivery on that exact destination: [4](#0-3) 

If governance raises `MinimumWithdrawalAmount` for a state machine after relayers have already accrued balances below the new value — analogous to `SolverVaults::setDepositLimit` being lowered below `currentDeposit` — those relayers cannot withdraw their existing balance. Unlike the original report where only *future* deposits are blocked (existing funds stay safe), here the *already-earned* funds themselves become stuck: the only unlock path is delivering more messages to that same destination, which is not guaranteed to ever happen again (e.g., destination chain deprecation, relayer retirement, or a governance-set minimum simply too high for that chain's typical fee volume).

### Impact Explanation
Relayer fees already earned and recorded in `Fees[state_machine][address]` become permanently unwithdrawable whenever the relayer cannot generate further deliveries to raise the balance past the new minimum. This is a direct freezing of legitimately earned funds belonging to an unprivileged actor (the relayer), triggered by an ordinary, non-malicious governance parameter update that never accounts for existing state — the same class of defect as the reported High-severity `setDepositLimit` bug.

### Likelihood Explanation
`set_minimum_withdrawal` is a normal governance operation expected to be called over the life of the protocol (e.g., to adjust for token price changes), exactly like `SolverVaults::setDepositLimit`. No malicious intent is required — a routine increase of the minimum for a state machine that also has slow-accruing or dormant relayers is sufficient to trigger the freeze, making this a realistic operational scenario rather than a contrived edge case.

### Recommendation
Either (a) let `withdraw` redeem the full `available_amount` whenever it is nonzero but below the configured minimum instead of reverting outright (i.e., treat the minimum only as a batching/dust threshold rather than an absolute floor that can trap funds), or (b) add a dedicated always-available "sweep remaining balance" extrinsic that bypasses `MinimumWithdrawalAmount`, or (c) require `set_minimum_withdrawal` to only apply to newly-accumulated balances going forward, e.g., via a grandfathering/snapshot mechanism, so no relayer's currently accrued balance is ever retroactively made unwithdrawable.

### Proof of Concept
1. Relayer `R` delivers requests to destination chain `D` and calls `accumulate_fees`, building `Fees[D][R] = 8 * 10^18` (8 tokens).
2. Governance calls `set_minimum_withdrawal(D, 10 * 10^18)` (a routine bump, e.g. tracking a price increase) — no check is made against `Fees[D][R]`. [2](#0-1) 
3. `R` calls `withdraw_fees(D, ...)`; `available_amount (8e18) < min_withdrawal_amount (10e18)` so the call reverts with `NotEnoughBalance`. [3](#0-2) 
4. If `D` is a low-traffic or soon-to-be-deprecated destination, `R` may never accumulate the additional `2e18` needed on that specific `(D, R)` key, leaving the 8 tokens permanently stuck with no extrinsic able to redeem them.

			origin: OriginFor<T>,
			state_machine: StateMachine,
			amount: u128,
		) -> DispatchResult {
			T::RelayerOrigin::ensure_origin(origin)?;
			MinimumWithdrawalAmount::<T>::insert(state_machine, U256::from(amount));
			Ok(())
