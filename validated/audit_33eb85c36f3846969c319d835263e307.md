### Title
`EmporiumUpgradeable.runAction`'s `stack.ops` loop allows arbitrary calls into any `IExternalActionV2` endpoint, enabling theft of another action contract's residual balance via forged nested `CircomData` - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction`'s ops loop (lines 91-118) places no restriction on `op.endpoint`, so it can freely call any address registered as an allowed recipient of another `IExternalActionV2` contract such as `LifiExternalAction`, including passing a fully attacker-forged, unverified `CircomData`/`deltaAmounts` pair as `op.callData`. Because `LifiExternalAction.runAction` only gates on `msg.sender` (the caller, here `EmporiumUpgradeable`) via `onlyAllowedRecipient`, and never re-validates that the `circomData` it receives is bound to any Hinkal proof, an attacker can trigger a real token swap of `LifiExternalAction`'s existing balance and redirect the proceeds to `EmporiumUpgradeable`, which the outer accounting loop then happily mints back to the attacker as a new UTXO.

### Finding Description
**Broken equality:** tokens leaving `LifiExternalAction` through its `runAction`/`swap` path must equal `-deltaAmountChanges` that were provably supplied by a Hinkal-verified deposit for *that specific* action call. In the exploit, the `deltaAmounts` and `circomData` passed to `LifiExternalAction.runAction` are decoded from `op.callData`, itself decoded from `circomData.externalActionData.externalActionMetadata` of the *outer*, unrelated Emporium call — an opaque byte blob that the circuit only ever commits to as a hash, never parses or semantically constrains. So the inner `forgedCircomData`/`deltaAmounts` have no relationship to any proof-verified UTXO.

**Code path:**
- `EmporiumUpgradeable.runAction` (gated by `onlyAllowedRecipient`, i.e. callable by Hinkal after proof verification of the attacker's own genuine deposit) decodes `stack` from `circomData.externalActionData.externalActionMetadata` [1](#0-0) .
- The ops loop performs `op.endpoint.call{value: op.value}(op.callData)` with the only checks being that `invokeWallet` selector abuse (`callHinkalWallet`/`doSendToRelay`) is blocked; there is **no allowlist/registry check restricting `op.endpoint`** to anything other than another `IExternalActionV2` contract [2](#0-1) .
- `LifiExternalAction` inherits `ExternalActionSwap.runAction`, gated only by `onlyAllowedRecipient` on `msg.sender` (which will be `EmporiumUpgradeable` in this low-level `.call`), and then executes `swap()` using whatever `circomData`/`deltaAmounts` were passed — no re-derivation from any Merkle root, nullifier, or proof [3](#0-2) .
- `swap()` uses `inputAmount = uint256(-deltaAmounts[0])` against `LifiExternalAction`'s own token balance (via `callRouter`/`approveUnlimited`), and sends `amountToSendToHinkal` of the swapped `outputToken` to `msg.sender` (`EmporiumUpgradeable`) [4](#0-3) [5](#0-4) .
- Back in `EmporiumUpgradeable.runAction`, if the attacker's outer `circomData.erc20TokenAddresses` also lists that `outputToken`, the resulting `balanceChange` (real balance delta caused by the nested swap) is credited via `handleOut`, transferring it to `msg.sender` (the Hinkal contract on behalf of the attacker) and minting a fresh UTXO to the attacker's `stealthAddressStructure` [6](#0-5) [7](#0-6) .

**Why guards fail:** `onlyAllowedRecipient` on both contracts only checks `msg.sender`, which is satisfied by the legitimate call chain (Hinkal → EmporiumUpgradeable → LifiExternalAction). Neither `verifyWallet` (EIP-712 signature over `stack.ops` only binds `endpoint/invokeWallet/value/callData` as opaque bytes, it never inspects nested calldata semantics) nor the circuit (which only constrains the outer `circomData`'s own public inputs, not the opaque `externalActionMetadata` payload's semantic content) prevents an attacker from embedding an arbitrary nested `CircomData` targeting a different, unrelated action contract's balance.

### Impact Explanation
This allows direct theft of another user's/protocol's stranded balance held in `LifiExternalAction` (or any other `IExternalActionV2` implementer that lists `EmporiumUpgradeable` as an allowed recipient), converted into a legitimately-minted shielded UTXO for the attacker with no corresponding backing deposit. This matches Critical severity: theft of in-flight/stranded funds and effectively minting shielded value without backing, since the attacker's real proof only covers their own trivial deposit while the stolen value flows in through the unconstrained nested call.

### Likelihood Explanation
Requires: (1) `LifiExternalAction.isAllowedRecipient[EmporiumUpgradeable] == true` — a configuration decision made by the (non-attacker) owner, plausible since Emporium's stated purpose is composing calls to other external actions; (2) a residual/stranded ERC20 balance sitting in `LifiExternalAction` (e.g., dust from a prior swap or a failed downstream transfer). Given these two preconditions, the attack costs only the gas and proof-generation for the attacker's own trivial genuine deposit and is repeatable each time a new residual balance accrues in a reachable external action contract.

### Recommendation
In `EmporiumUpgradeable.runAction`, explicitly disallow `op.endpoint` from being any address registered as an `IExternalActionV2`/allowed-recipient endpoint of another Hinkal external action (or maintain an explicit endpoint allowlist for Emporium ops, separate from the swap/action allowlists), and/or forbid endpoints whose selector matches `runAction`/`IExternalActionV2.runAction` unless invoked through the properly proof-verified `Hinkal` dispatch path rather than via a raw `.call` from within another action.

### Proof of Concept
Foundry test plan:
1. Deploy `LifiExternalAction`, `EmporiumUpgradeable`, and a mock router; set `LifiExternalAction.isAllowedRecipient[EmporiumUpgradeable] = true` via owner call.
2. Seed `LifiExternalAction` with a residual ERC20 balance (e.g., transfer tokens directly to it, simulating dust from a prior swap).
3. Attacker generates a real proof for their own trivial UTXO deposit, with `circomData.externalActionData.externalActionMetadata` encoding an `EmporiumStack` whose `ops[0] = {endpoint: LifiExternalAction, invokeWallet: false, value: 0, callData: abi.encodeWithSelector(runAction.selector, forgedCircomData, forgedDeltaAmounts)}`, where `forgedCircomData` targets swapping `LifiExternalAction`'s residual balance to an attacker-chosen `outputToken` matching the attacker's real outer `circomData.erc20TokenAddresses`.
4. Call `Hinkal`'s external-transact entrypoint with the real proof, routing into `EmporiumUpgradeable.runAction`.
5. Assert: `LifiExternalAction` balance of the seeded token drops by exactly the swapped amount, and a new UTXO of `outputToken` is minted to the attacker equal to that amount, while `deltaAmountChanges` supplied by the attacker's real proof never authorized moving `LifiExternalAction`'s balance (i.e., `sum(-deltaAmountChanges)` for the attacker's real deposit is negligible/zero compared to the value received).

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
