### Title
Redundant per-item Merkle-Patricia proof re-verification in `HandlerV2.handlePostRequestTimeouts`/`handleGetRequestTimeouts` causes quadratic gas costs (DoS risk) - (File: `evm/src/core/HandlerV2.sol`)

### Summary
`HandlerV2.handlePostRequestTimeouts` and `HandlerV2.handleGetRequestTimeouts` iterate over a batch of timed-out requests and, on every single iteration, call `PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)` with a single-element `keys` array, instead of collecting all keys once and verifying them in one call outside the loop. Because `VerifyProof` decodes and `keccak256`-hashes the *entire* set of trie proof nodes on every invocation (as documented in `docs/content/protocol/cryptography/merkle-trees/patricia-trie.mdx`), this pattern re-does the same expensive proof-node hashing work once per timeout item in the batch, turning what should be O(proof_nodes + keys) work into O(proof_nodes × keys). This mirrors the reported bug class of "expensive looping" where multiple calls to the same routine within a loop should be consolidated into a single call with cached/batched inputs.

### Finding Description
In `evm/src/core/HandlerV2.sol`, `handlePostRequestTimeouts`: [1](#0-0) 
and `handleGetRequestTimeouts`: [2](#0-1) 

both loop over `message.timeouts` and, for each element, construct a single-key `bytes[]` array and call `PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)`. The same `message.proof` (the same set of trie nodes) is passed unchanged on every call. As documented in the protocol's own description of the verification algorithm, `VerifyProof`/`VerifySubstrateProof` first decodes and hashes every node in the supplied proof array before walking it once per key: [3](#0-2) 

This proof-node decode/hash step (`keccak256` over every proof node) is designed to be amortized across *all* keys in a single call — the algorithm explicitly accepts a `keys` array so the node table is built once and reused for each key lookup. By calling `VerifyProof` once per timeout with a 1-element key array, `HandlerV2` pays the full node-decoding cost N times for a batch of N timeouts, rather than once. Other handlers in the same contract correctly batch: `handlePostRequests` and `handleGetResponses` build one `leaves` array and call `MerkleMountainRange.VerifyProof` a single time for the whole batch: [4](#0-3) 

`handlePostRequestTimeouts`/`handleGetRequestTimeouts` do not follow this pattern, which is the exact "consolidate multiple subsequent calls to the same [proof-verification] routine into a single call" issue the external report describes for `Accounts.getBorrowETH`.

### Impact Explanation
`handlePostRequestTimeouts` and `handleGetRequestTimeouts` are permissionless, relayer-callable dispatch entry points (reachable via `IHandlerV2`/`batchCall`) that process an attacker- or relayer-controlled-size batch (`message.timeouts`) against a single shared non-membership proof. Because the per-key hashing cost of the proof node array is repeated for every timeout instead of amortized once, gas cost scales multiplicatively with `(proof_nodes × timeouts_in_batch)` rather than `(proof_nodes + timeouts_in_batch)`. For proofs with many nodes (deep/large tries) and large timeout batches, this can push a legitimate batch timeout-processing transaction over the block gas limit, making it impossible to deliver timeout messages for a legitimate batch in one transaction — a route/message unable to be delivered without splitting into much smaller (and costlier for relayers) batches. This degrades the "timeout" leg of ISMP request delivery, which is a core dispatch/delivery function of the protocol.

### Likelihood Explanation
This code path executes on every timeout batch submitted by any relayer; the inefficiency is structural (in the loop, not just triggerable by a rare edge case), so it is always present, and its severity scales directly with the size of the relayer-chosen batch and the depth of the supplied trie proof — parameters fully controlled by the transaction submitter. No special privileges are required to trigger the worst case; a relayer (or anyone racing to submit a timeout message) simply needs to submit a batch with many timeouts backed by a proof with many shared nodes.

### Recommendation
Refactor `handlePostRequestTimeouts` and `handleGetRequestTimeouts` to collect all request-receipt (or response-receipt) storage keys into a single `bytes[]` array before the loop, and call `PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)` exactly once, then iterate over the returned `StorageValue[]` array to check each entry's non-membership and dispatch the timeout — mirroring the batching pattern already used in `handlePostRequests`/`handleGetResponses` for `MerkleMountainRange.VerifyProof`.

### Proof of Concept
1. A relayer submits `handlePostRequestTimeouts` with a `message.proof` containing a moderately deep/large non-membership proof (e.g., hundreds of trie nodes) and a large `message.timeouts` array (e.g., 50–100 timed-out requests), all provable via the same shared state root.
2. For each of the N timeouts, `PolkadotTrie.VerifyProof` is invoked, and internally decodes and `keccak256`-hashes every one of the M proof nodes again (see `VerifySubstrateProof` in `docs/content/protocol/cryptography/merkle-trees/patricia-trie.mdx`), costing O(M) work per call.
3. Total gas for proof verification alone scales as O(N × M) instead of O(N + M), and as N and M grow (both attacker/relayer-controlled up to protocol limits), the transaction can exceed the block gas limit, preventing legitimate large timeout batches from ever being delivered in a single call.
