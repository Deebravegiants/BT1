### Title
Webhook shop identity spoofing via HMAC-unbound `shop-domain` header enables cross-tenant webhook injection - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating the HMAC over the raw request body only, but the tenant identifier (`shop`) delivered to the app's handler is taken from an HTTP header that is never covered by that signature. This breaks the intended binding `shop authenticated == shop acted on`, letting an attacker who possesses one valid `(body, hmac)` pair replay it while asserting an arbitrary `shop-domain`, causing the app to process/attribute the payload to a different tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cryptographic tie to the signed payload: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC (over body only) and then hands the caller-supplied `request.shop` straight into `WebhookMetadata`, which the app handler uses as the tenant key: [4](#0-3) 

`Utils::HmacValidator.validate` and `validate_signature` confirm the signature check operates purely on `verifiable_query.to_signable_string` (the body) against `verifiable_query.hmac`, never incorporating `shop`: [5](#0-4) 

**Equality that should hold but doesn't**: `shop` bound by HMAC == `shop` acted on by the handler. In reality, HMAC binds only `body` == `body` acted on; `shop` is fully attacker-controlled at the transport layer and unauthenticated. Any party capable of capturing one genuine, HMAC-valid webhook delivery for their own shop (which the app itself sends them via legitimate app behavior, logs, browser dev tools, or a compromised low-privilege proxy in front of the endpoint) can resend that exact `(body, hmac)` pair with a different `shop-domain` header value. The signature still validates because it never inspected the header, and `Registry.process` dispatches the handler believing the payload originates from the spoofed shop.

### Impact Explanation
This is a cross-tenant integrity/confidentiality issue: an unprivileged actor with access to only their own shop's legitimate webhook traffic can inject/attribute another merchant's webhook events, or worse, replay their own event data (e.g., `orders/create`, `app/uninstalled`, `customers/data_request`) under an arbitrary target shop domain. Depending on how the host handler keys off `WebhookMetadata#shop` (most `shopify_app`-style integrations look up/act on merchant records keyed by this value), this enables cross-tenant data corruption, unauthorized state changes (e.g., forcing an uninstall/GDPR flow against a shop that never sent it), or misattributed business events — matching the "cross-tenant access" impact class.

### Likelihood Explanation
Likelihood is constrained by the fact that the attacker must first obtain one valid `(body, hmac)` pair, which normally only Shopify can produce for a given secret. However, no secret knowledge is required to reuse that pair against a different shop — only network access to the app's public webhook endpoint and the ability to alter the `shop-domain` header of an HTTP request, both trivially available to any unprivileged actor who has ever seen one legitimate delivery (e.g., from their own store's install, or a captured request). This differs materially from the false denial-of-service report cited, but the underlying bug class — an identity field (`shop`) not covered by the same authentication check that gates the rest of the payload — is directly analogous and reachable purely through this gem's own webhook-processing code path.

### Recommendation
Bind `shop` (and ideally `topic`, `webhook_id`, `api_version`) into the signed material, or independently verify that `request.shop` corresponds to a shop with an active, known session/installation before invoking the handler, rather than trusting the header as authoritative purely because the body's HMAC passed. At minimum, document that `WebhookMetadata#shop` is not authenticated by `HmacValidator.validate` so host applications don't assume it is trustworthy for authorization decisions.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a real event (e.g., updates a product), causing Shopify to deliver a legitimate webhook with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some `raw_body`.
2. Attacker captures this full HTTP request (trivial via a proxy they control in front of their own endpoint, or via app logs they have access to).
3. Attacker replays the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (only checks presence, not correspondence) at [6](#0-5) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC solely from `raw_body` and finds it matches (since body/hmac were untouched), at [7](#0-6) .
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker's event body, processing it as though it originated from the victim shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
