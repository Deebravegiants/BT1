### Title
Direct LT donations to a curve `Pair` become permanently unretrievable once the token graduates - ([File: packages/contracts/src/Router.sol])

### Summary
Any unprivileged wallet can `IERC20(lt).transfer(pairAddress, amount)` directly to a bonding-curve `Pair` before graduation. That donated LT is deliberately excluded from `ltFromPair`/LP seeding (donation resistance) and is documented as remaining "locked in the curve pair" — but the only function capable of moving asset out of the `Pair` (`Router.graduate`, gated `BONDING_ROLE`) is invoked exactly once per token, during phase 1 of graduation. After the token's lifecycle advances past `Curve`, there is no remaining code path that can ever call `Pair.transferAsset` for that token again, so any LT sitting in the pair beyond the amount already drained becomes permanently stranded with no rescue function anywhere in `Pair`, `Router`, `Bonding`, or the rest of the protocol.

### Finding Description
`Pair.transferAsset` is the only function that can move the reserve asset (LT) out of a `Pair`, and it is gated `onlyRouter`: [1](#0-0) 

`Router` exposes `transferAsset` through exactly two paths: `sell` (requires `BONDING_ROLE`, and only fires while `Bonding.sell` is reachable, i.e. `Lifecycle.Curve`) and `graduate` (also `BONDING_ROLE`): [2](#0-1) 

`Router.graduate` is only ever called once, from `Bonding._prepareGraduationLiquidity`, which runs exactly once per token as part of phase-1 (`_enterGraduating`), flipping the token's lifecycle from `Curve` to `Graduating`: [3](#0-2) [4](#0-3) 

`ltFromPair` is computed strictly from the pair's *stored* `assetReserve` minus the recovered launch-time virtual reserve (`assetReserve - _launchTimeVirtualLtReserve(...)`) — a live `transfer` to the pair that never goes through `Router.swap`/`sell` does not change `assetReserve`, so it is excluded from `ltFromPair` and left behind in the pair after `Router.graduate` drains only the accounted amount. The project's own documentation and inline comments confirm this is understood behavior, not accidental: [5](#0-4) 

"`Bonding` in turn only calls `graduate` from `_prepareGraduationLiquidity` — which is unreachable once the token's lifecycle has flipped past `Curve`. So the leftover is unreachable..." — the protocol itself states this is only a trust-assumption, not an on-chain guarantee, and that donated LT stays trapped in the pair indefinitely once graduation phase 1 has fired. There is no `Pair.rescue`/`sweep`/`skim`-equivalent for the reserve asset, no owner-only recovery path in `Bonding`, and once lifecycle is `Graduating`/`Graduated`, `Bonding.buy`/`sell` (the only callers that could route through `Router.sell`) permanently revert for that token, so `Router.sell`'s `transferAsset` call is likewise unreachable.

Because this "leftover is unreachable" is stated as an accepted design property rather than a mitigated bug, the donated LT is genuinely and permanently locked — matching the report's bug class of "deposits into the contract have no corresponding claim mechanism."

### Impact Explanation
Any LT balance donated directly to a `Pair` (by mistake, by a third-party integration, or intentionally, e.g. someone trying to "top up" a bonding curve believing it aids the project) is permanently frozen the moment that token's curve reaches `Lifecycle.Graduating`/`Graduated`. There is no function in the entire contract surface (`Pair`, `Router`, `Bonding`, `Factory`, `Zap`, `FeeVault`, `LPLock`) that can move that residual LT out of a graduated `Pair` ever again. This is a permanent freeze of funds belonging to an unrelated/depositing wallet, satisfying the "permanent freezing of funds" impact bar even though the donor's action is voluntary — the protocol accepts the deposit into its contract surface (the `Pair` has no `receive`/rejection logic for the LT ERC20) with no corresponding claim/rescue mechanism, precisely the bug class in the external report.

### Likelihood Explanation
Likelihood of the underlying action (a plain `IERC20.transfer` to a known, publicly-derivable `Pair` address) is trivial for any unprivileged wallet at any time before that token's `finalizeGraduation`/`_enterGraduating` fires — no special permissions, front-running, or unusual state is required. The freeze becomes irreversible as soon as the curve crosses either graduation trigger (USD or supply), which happens for essentially all successful tokens. The severity is bounded by donor behavior being non-adversarial/accidental in the common case, but the loss is complete and permanent whenever it occurs.

### Recommendation
Add an owner-gated (or otherwise permissioned) rescue function on `Pair` (or exposed via `Router`/`Bonding` under `BONDING_ROLE`) that can sweep any LT (`assetToken`) balance in excess of the pair's live `assetReserve` after a token has left `Lifecycle.Curve`, similar in spirit to `Bonding._sweepLTToOwner` used for the HyperSwap-side pre-seed residue. At minimum, document and surface an explicit "post-graduation curve-pair donation is permanently unrecoverable" warning in user-facing docs/UI so third parties never send LT directly to a `Pair` address, and consider adding a `skim`/`rescue` entry point mirroring the HyperSwap-side `_sweepLTToOwner` pattern that is already used to avoid exactly this kind of permanent loss for the graduated LP pair.

### Proof of Concept
1. Token `T` launches on `Bonding`, pair `P` created against LT `L` (`Bonding.launch` → `Router.addInitialLiquidity`).
2. Any wallet `W` (no special role) directly calls `L.transfer(P, X)` — a bare ERC20 transfer to the pair address, bypassing `Zap`/`Bonding`/`Router` entirely.
3. Trading continues normally; eventually a buy crosses the USD or supply graduation trigger and `Bonding._executeBuy` calls `_enterGraduating(T)` → `_prepareGraduationLiquidity(T)`.
4. `_prepareGraduationLiquidity` computes `ltFromPair = storedAssetReserve - virtualLtReserve` (excludes `X`, since `X` was a raw transfer that never updated `_pool.assetReserve`) and calls `Router.graduate(T, ltFromPair)`, draining only that amount via `Pair.transferAsset`.
5. `finalizeGraduation(T)` completes, flipping lifecycle to `Graduated`. `X` LT remains sitting in `P`'s token balance (`assetBalance() > 0` even though `_pool.assetReserve` may now be stale/irrelevant post-graduation).
6. No function anywhere (`Pair`, `Router`, `Bonding`, `Zap`, `FeeVault`) can ever call `Pair.transferAsset` for `T` again — `Router.graduate` is single-shot per token and `Router.sell`/`Bonding.sell` are permanently gated off `Lifecycle.Curve`. `W`'s `X` LT is unrecoverable forever.

*Note: I was unable to fully verify from the index whether any as-yet-undiscovered admin/owner function elsewhere in `Bonding.sol` (outside the ranges retrieved) might expose a generic ERC20 rescue on arbitrary pairs; the documentation and every code path found explicitly state the donated LT is unreachable, but a full file read of `Bonding.sol` was not completed due to tool-call limits.*

```text
        address token,
```

```text
    function _prepareGraduationLiquidity(
        address tokenAddress
    ) internal returns (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) {
        address pairAddr = _s().tokenInfo[tokenAddress].pair;
        (uint256 tokenReserve, uint256 assetReserve) = IPair(pairAddr).getReserves();

        unsoldBurned = IPair(pairAddr).tokenBalance();
        if (unsoldBurned > 0) {
            Token(tokenAddress).burn(pairAddr, unsoldBurned);
        }

        ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
        if (ltFromPair > 0) {
            _s().router.graduate(tokenAddress, ltFromPair);
        }

        tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
        if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;

        lpBurned = LP_RESERVE - tokensForLP;
        if (lpBurned > 0) {
            Token(tokenAddress).burn(address(this), lpBurned);
        }
    }
```
