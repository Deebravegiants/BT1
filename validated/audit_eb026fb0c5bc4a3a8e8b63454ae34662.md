## Title
Webhook `shop` field is not covered by HMAC verification, enabling cross-tenant impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook exclusively by validating the HMAC over the raw request body, while the `shop` (and `topic`, `webhook_id`, `api_version`) values are taken from unauthenticated HTTP headers and handed to the app's handler as trusted identity data. This breaks the equality that should hold between "bytes covered by the HMAC" and "bytes the handler treats as authenticated shop identity," allowing any user with a legitimate app installation to forge webhook deliveries that claim to originate from a different (victim) shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, and its `to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` values are all pulled from HTTP headers (e.g. `x-shopify-shop-domain`), which are never included in the signable string and are therefore never covered by the HMAC: [2](#0-1) 

`Registry.process` validates only the HMAC (i.e. only the body) and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to construct `WebhookMetadata`, which is passed directly to the application's registered handler: [3](#0-2) 

The `HmacValidator.validate` call only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string` (the raw body) — it has no visibility into, and provides no guarantee about, the `shop` header: [4](#0-3) 

The gem's own documentation instructs developers to key downstream work directly off `data.shop` from the webhook handler, reinforcing that this field is treated as an authenticated tenant identifier by design: [5](#0-4) 

**Binding broken:** `shop authenticated (bytes covered by HMAC) == shop used as the tenant/session key by the handler`. In reality, `bytes verified by HMAC (raw_body)` ≠ `bytes used to key tenant identity (shop-domain header)`.

### Impact Explanation
Any user who can install the app on a shop they control (an "unprivileged internet user" with respect to any other merchant's data) receives genuine Shopify webhook deliveries whose HMAC is computed with the app's single, shared `client_secret` over the body only. Because the `shop-domain` header is not part of the signed material, that same attacker can replay/forge a request to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` value naming a victim shop, while keeping the HMAC valid (since it only checks the body they legitimately received). Any application built per this gem's documented pattern — trusting `WebhookMetadata#shop` as an authenticated tenant key to look up sessions, queue jobs "for that shop," or perform data mutations — can be tricked into acting as if the event came from a different, arbitrary tenant. This constitutes cross-tenant impact (High severity per the impact categories), since data or actions attributable to shop A can be attributed to/affect shop B purely by header manipulation.

### Likelihood Explanation
Likelihood is high for any application that follows the documented handler pattern literally (using `data.shop` to select the tenant context) without independently maintaining a list of shops that installed the app to cross-check the header. No secrets, tokens, or privileged access are required beyond a normal app installation, which is available to any internet user for most public apps.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the authenticated material, or otherwise require the application to verify the incoming `shop` against a known, previously stored list of shops with valid sessions/access tokens for this app before trusting it. At minimum, update `ShopifyAPI::Webhooks::Registry.process` and its documentation to explicitly warn that `shop` is unauthenticated and must be independently validated by the host application against its own session/shop store before being used as a tenant key.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, receiving genuine webhook deliveries (e.g. `orders/create`) signed by Shopify with the app's `client_secret` over the JSON body.
2. Attacker captures such a delivery, keeping `x-shopify-hmac-sha256` and the raw body untouched (so `HmacValidator.validate` still passes, since it only checks the body per `lib/shopify_api/utils/hmac_validator.rb#L26-L31` and `lib/shopify_api/webhooks/request.rb#L35-L38`).
3. Attacker replays the request to the app's webhook endpoint, changing only the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb#L188-L200`) validates the HMAC successfully (body unchanged) and invokes the handler with `WebhookMetadata` whose `shop` is `victim-shop.myshopify.com`.
5. Any handler logic keyed on `data.shop` (as shown in the gem's own docs) now performs actions or data lookups as though the event genuinely originated from the victim shop, achieving cross-tenant impersonation without ever needing the victim's credentials.
