This confirms the vulnerability: the webhook HMAC in `lib/shopify_api/webhooks/request.rb` is computed only over `@raw_body` (`to_signable_string` returns `@raw_body` alone, line 36-38), while `shop` is read independently from the `x-shopify-shop-domain`/`shopify-shop-domain` header (`request.rb` lines 20-23, 68-70) and is never included in the signed bytes. `Registry.process` (`lib/shopify_api/webhooks/registry.rb` lines 188-199) validates only `Utils::HmacValidator.validate(request)` (which checks the body signature) and then hands `request.shop` straight to the handler via `WebhookMetadata`, with no cross-check that the header's shop matches anything cryptographically bound to the payload.

### Title
Webhook shop-domain identity binding bypass allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
The Shopify webhook HMAC verification in this gem authenticates only the raw request body, not the `shop-domain` header that host applications rely on to attribute the payload to a specific merchant/tenant. Any user who can install the app on a shop they control (e.g. a free developer store) can capture a validly-signed webhook from their own store and replay it against the app's webhook endpoint with the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header swapped to point at a victim shop, causing the app to process legitimate, HMAC-valid data under the wrong tenant's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is derived independently from a header that is never part of the signed bytes: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC over the request (i.e. only the body) and then dispatches the handler using the unauthenticated `request.shop` value with no additional binding check: [4](#0-3) 

`Utils::HmacValidator.validate` performs a constant-time comparison of the computed HMAC against the presented one, but the comparison is entirely a function of `verifiable_query.to_signable_string`, which for webhooks is body-only: [5](#0-4) 

The identity binding broken here is: `shop attributed to webhook data (WebhookMetadata.shop, from the unauthenticated header)` ≠ `shop cryptographically bound by the HMAC (none — only the body is signed)`. Because Shopify uses the same `client_secret`/`api_secret_key` to sign webhooks across every shop that has installed a given public app, a validly-signed webhook body obtained from *any* shop installation (including one the attacker fully controls) remains HMAC-valid regardless of which shop-domain header is attached to it upon replay.

### Impact Explanation
An attacker who controls their own shop installation (a normal unprivileged action for any developer using a public app, requiring no leaked secrets or privileged access) can replay their own genuinely-signed webhook body to the app's webhook endpoint while forging the `shop-domain` header to name a victim shop. The host application, trusting `WebhookMetadata.shop` because `HmacValidator.validate` succeeded, will process/store that data as if it originated from the victim tenant — a cross-tenant data confusion/spoofing primitive. Depending on the webhook topic and how the host app persists it (e.g. `customers/data_request`, `app/uninstalled`, order or fulfillment webhooks), this can corrupt or exfiltrate victim-tenant records, trigger tenant-scoped side effects (like data deletion flows for GDPR topics) against the wrong shop, or desynchronize the victim's application state — a cross-tenant access violation.

### Likelihood Explanation
Likelihood is high for any attacker with legitimate access to at least one shop installation of the target public app (a trivial, free, unprivileged action via a development store), since no `api_secret_key`, access token, or privileged credentials are required — only capturing one's own valid webhook delivery and replaying it with a modified header.

### Recommendation
Bind the shop identity into the authenticated material used for tenant attribution: require the host application (and ideally this gem) to look up the merchant's stored HMAC/session using the `shop-domain` header itself as a lookup key against known/registered shops rather than trusting it implicitly once body-HMAC succeeds, and/or document and enforce that the `shop` value must be independently cross-checked against the app's own registered/installed-shop list before webhook data is processed for that shop. At minimum, surface this gap explicitly in `Webhooks::Registry.process`/`WebhookMetadata` documentation so host apps do not conflate "HMAC valid" with "shop header trustworthy."

### Proof of Concept
1. Attacker installs the target public app on their own development store `attacker-shop.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Shopify delivers a webhook to the app with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some JSON body.
3. Attacker captures this raw HTTP request, changes only `x-shopify-shop-domain` to `victim-shop.myshopify.com`, and replays it to the same webhook endpoint.
4. `ShopifyAPI::Webhooks::Request.new` parses the tampered headers and body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only — this matches because the body is unchanged, so validation succeeds.
5. The handler receives `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` even though the payload actually originated from the attacker's shop, and the host app processes/stores it under the victim's tenant.
