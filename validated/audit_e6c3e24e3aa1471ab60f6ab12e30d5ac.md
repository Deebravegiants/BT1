Webhook `Registry.process` authenticates request body but trusts the unauthenticated `shop-domain` header for tenant identity - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns `@raw_body`, so the HMAC that `ShopifyAPI::Webhooks::Registry.process` validates via `Utils::HmacValidator.validate(request)` covers exclusively the JSON body. The `shop` value that the gem hands to the app's webhook handler (`request.shop`, used to build `WebhookMetadata`) comes straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header and is never included in the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` with: [1](#0-0) 
`hmac` is derived from the `hmac-sha256` header, and `to_signable_string` returns only `@raw_body` - the `shop` (from the `shop-domain` header), `topic`, `webhook_id`, and `api_version` headers are not part of the signed data at all.

`Registry.process` verifies the HMAC and then dispatches to the registered handler using `request.shop` as the tenant identifier, with no independent verification that the signed body actually originated for that shop: [2](#0-1) 

The identity binding that should hold is: `HMAC(secret, signed_bytes) == received_hmac` should imply `signed_bytes` uniquely determines the tenant (`shop`) that the app acts on. Here the equality actually enforced is only over `raw_body`, while `shop` is an independent, unauthenticated header value copied verbatim into `WebhookMetadata#shop`, which the app's handler is expected to trust to attribute the event to a tenant (per `docs/usage/webhooks.md`, `data.shop` is documented as "The shop domain of the webhook").

Since the HMAC secret (`Context.api_secret_key`) is the same for every shop that installs a given app, any HTTP request bearing a **previously observed valid `(body, hmac)` pair for the app** (e.g. a webhook payload the attacker's own shop received, or one leaked/logged/replayed) will pass `Utils::HmacValidator.validate` regardless of what `shop-domain` header is attached, because that header is never part of the signed material.

### Impact Explanation
An attacker who controls one shop that has the app installed (or who otherwise obtains one genuine `(body, hmac)` pair for this app - e.g. from logs, network capture, or a second app instance) can replay that exact body against the app's webhook endpoint with an arbitrary `shop-domain` header. `Registry.process` will accept it as authentic (`Utils::HmacValidator.validate` passes) and invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen shop. If the host app trusts `data.shop` to select which tenant's session/data to update (the documented and expected usage pattern), this enables cross-tenant data injection/corruption using another merchant's identity, without the attacker ever needing that merchant's credentials.

### Likelihood Explanation
Exploitation requires the attacker to already possess one legitimate `(body, hmac)` pair generated by the app (trivial if the attacker's own shop is a tenant of the app, since they can request/observe genuine webhooks for topics they control, e.g. `app/uninstalled`, `shop/update`, or any topic whose body content doesn't itself embed a shop-specific value the app separately validates). This is a realistic path for any developer/multi-tenant SaaS app on this gem and requires no privileged credentials, matching the "unprivileged internet user" threat model.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, and ideally `topic`/`webhook_id`) in the signed payload used for HMAC verification, or have `Registry.process`/the host app cross-check the shop header against a shop value embedded in the verified body (where available) or against a shop known to be associated with the specific `webhook_id`/subscription before dispatching to handlers. At minimum, document prominently that `shop` is unauthenticated and must not be trusted for authorization decisions without additional verification (e.g., confirming an active, stored session/install record for that shop).

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; attacker receives (or triggers) a genuine webhook for topic `T` with raw body `B`, and Shopify's valid header `shopify-hmac-sha256: H` (computed as `HMAC-SHA256(api_secret_key, B)`).
2. Attacker sends a POST to the app's webhook endpoint with the exact same body `B` and header `H`, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shopify-hmac-sha256" => H, "shopify-shop-domain" => "victim-shop.myshopify.com"})` is constructed.
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and compares to `H` - this matches because the shop header is not part of `to_signable_string`: [3](#0-2) 
5. The handler is invoked with `WebhookMetadata.new(topic: T, shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to act on/attribute data to `victim-shop` using content the attacker fully controls (limited to whatever body content they can legitimately obtain a signature for).
