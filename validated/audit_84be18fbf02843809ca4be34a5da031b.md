## Title
Unbounded cycle in `AncestryChain::ancestry` allows a permanently non-terminating loop when processing untrusted GRANDPA finality proofs - (File: `modules/consensus/grandpa/primitives/src/justification.rs`)

### Summary
`AncestryChain::ancestry` walks a hash→header map by following `parent_hash` pointers until it reaches a target `base` hash, with no visited-set/cycle detection and no iteration bound — the same bug class as CVE-2018-7174, where `XRef::Xref` walks a chained structure and only guards against cycles for one representation (tables) but not another (streams). Here, the ancestry-walk guard against cycles is entirely absent for attacker-supplied header chains.

### Finding Description
`AncestryChain::ancestry` is implemented as: [1](#0-0) 

```
fn ancestry(&self, base, block) -> Result<Vec<H::Hash>, ...> {
    let mut route = vec![block];
    let mut current_hash = block;
    while current_hash != base {
        match self.ancestry.get(&current_hash) {
            Some(current_header) => {
                current_hash = *current_header.parent_hash();
                route.push(current_hash);
            },
            _ => return Err(finality_grandpa::Error::NotDescendent),
        };
    }
    Ok(route)
}
```

`self.ancestry` is a `BTreeMap<Hash, Header>` built directly from the untrusted, relayer-supplied `finality_proof.unknown_headers` vector via `AncestryChain::new`: [2](#0-1) . Because the headers, including their `parent_hash` fields, are fully attacker-controlled SCALE-decoded structs, an attacker can craft two or more headers whose `parent_hash` fields point at each other, forming a cycle that never includes `base`. Since `current_hash` only ever takes values inside that finite cyclic set, `self.ancestry.get(&current_hash)` always returns `Some`, and the `while current_hash != base` condition is never satisfied — the loop never terminates.

Critically, this call happens **before** any GRANDPA signature/justification verification in `verify_grandpa_finality_proof`: [3](#0-2) 

The `headers.ancestry(base.hash(), consensus_state.latest_hash)` and `headers.ancestry(from, target.hash())` calls execute purely against attacker-supplied `unknown_headers`, and only afterward does the code call `justification.verify(...)`. This is reachable from the top-level `ConsensusClient::verify_consensus` entrypoint used by any relayer submitting a GRANDPA `ConsensusMessage`: [4](#0-3) 

The equivalent `AncestryChain::ancestry` usage in the fraud-proof path (`verify_fraud_proof`) is similarly exposed: [5](#0-4) .

### Impact Explanation
Any unprivileged relayer can submit a consensus-update message that reaches `GrandpaConsensusClient::verify_consensus` with crafted `unknown_headers` forming a parent-hash cycle. The resulting infinite loop occurs inside runtime/pallet execution, before any authentication (justification signature check) is performed, causing that execution context to hang indefinitely. Because GRANDPA consensus updates gate all state/message proofs relayed from Polkadot/Kusama to Hyperbridge, blocking this code path permanently freezes the route: no further consensus updates, parachain header proofs, or cross-chain messages can be delivered through this consensus client — a "route unable to deliver messages" condition and denial of service to the bridge.

### Likelihood Explanation
High: crafting two or more headers with mutually-referencing `parent_hash` fields requires no privileged access, no valid GRANDPA signatures, and no special timing — it is pure client-side proof construction. The vulnerable calls execute prior to signature verification, so the attacker does not need a genuine finalized chain state to trigger the loop; only that `base.number() < consensus_state.latest_height` (easily satisfiable) or that the ancestry walk from `from` to `target.hash()` traverses the crafted cycle.

### Recommendation
Add cycle detection to `AncestryChain::ancestry` (e.g., a bounded iteration count equal to `self.ancestry.len()`, or a `visited: BTreeSet<Hash>` that aborts with `Error::NotDescendent` once a hash is revisited), mirroring the fix pattern used for `XRef::Xref` in xpdf (track visited entries regardless of whether the walk originates from a table-like or stream-like source). Apply the fix once in `AncestryChain::ancestry` so both `verify_grandpa_finality_proof` and `verify_fraud_proof` are protected.

### Proof of Concept
1. Attacker constructs `unknown_headers = [H_target, H_a, H_b]` where `H_a.parent_hash = H_b.hash()` and `H_b.parent_hash = H_a.hash()` (a 2-cycle), and `H_target` has the highest block number with `H_target.hash() == finality_proof.block`.
2. Attacker sets `H_a`/`H_b` block numbers such that the minimum-numbered header (`base`) satisfies `base.number() < consensus_state.latest_height`.
3. Attacker submits a `ConsensusMessage::Polkadot` (or the relevant GRANDPA consensus message) extrinsic carrying this `FinalityProof`.
4. `verify_grandpa_finality_proof` calls `headers.ancestry(base.hash(), consensus_state.latest_hash)`; since `consensus_state.latest_hash` is never reached via the crafted cycle, the `while current_hash != base` loop in `AncestryChain::ancestry` never terminates, hanging the runtime call before any signature check occurs.
