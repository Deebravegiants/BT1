### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant impersonation via header replay - ([File: lib/shopify_api/webhooks/registry.rb], [File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then hands the handler the shop identity taken from an unsigned, attacker-controllable HTTP header. The equality the code implicitly relies on — "the shop that produced this signed body" == "the shop named in the `shop-domain` header" — is never actually checked, because the header is outside the HMAC's coverage.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC and, on success, forwards the header-derived `request.shop` (and `request.topic`) to the app's handler as trusted tenant identity, without ever re-deriving or cross-checking `shop` against anything the signature actually covers: [4](#0-3) 

`HmacValidator.validate`/`validate_signature` only compares the HMAC computed from `to_signable_string` (i.e., the raw body) against the received `hmac`: [5](#0-4) 

Because the signature covers only the body, two different `(shop-domain header, hmac)` combinations can be valid for the exact same body/hmac pair. Concretely: a merchant who has legitimately installed the app (an unprivileged, no-special-access actor from the app's perspective) receives real webhooks addressed to their own store, each with a body and a correctly computed `x-shopify-hmac-sha256`. That merchant can capture one such `(raw_body, hmac)` pair and replay it to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a different, victim shop's domain. `Registry.process` will still find the HMAC valid (it only checks the body) and will invoke the handler with `WebhookMetadata#shop` set to the victim's domain, even though the body was never actually produced for that shop.

### Impact Explanation
This breaks the identity binding `shop-bound-to-signature == shop-acted-upon`. Any host application that uses `data.shop` from the handler to select which merchant's session/data to act on (the officially documented pattern in `docs/usage/webhooks.md`, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) will process attacker-influenced webhook content under a victim shop's identity. Depending on the host app's downstream logic, this enables cross-tenant data confusion/corruption (e.g., an attacker forcing a job to run "as" another merchant's shop using their own arbitrary — but validly-HMAC'd — payload content). This falls under cross-tenant access impact.

### Likelihood Explanation
Medium. The prerequisite is that the attacker be a legitimate, low-privilege actor able to install the app on at least one shop (a very common threat model for public/multi-tenant Shopify apps — anyone can install a public app on a free dev store) so they can obtain at least one genuine `(body, hmac)` pair from a real webhook delivery. No access to `api_secret_key` or any elevated credential is required; only observation of one's own legitimately-received webhook traffic. The main constraint is that the attacker is limited to reusing bodies they've already received (they cannot forge arbitrary new bodies without the secret), but for topics where the body content is attacker-influenced (e.g., `orders/create`, `products/update` on their own shop) this is a low bar.

### Recommendation
Bind the shop identity to the HMAC-verified content rather than trusting the unauthenticated header:
- Include the shop domain (and ideally topic/webhook id) in the signable string used for the HMAC computation, if Shopify's delivered signature scheme is going to be relied upon this way, or
- Require the host application to independently verify that the `shop` on the webhook request matches an existing, previously-established session/shop record before trusting `data.shop` for tenant-scoped actions, and document this requirement prominently, or
- At minimum, document explicitly in `docs/usage/webhooks.md` that `data.shop`/`data.topic` are not covered by HMAC verification and must not be trusted as authenticated without additional application-level checks (e.g., correlating with `webhook_id` uniqueness tracking per shop and an existing stored session for that shop).

### Proof of Concept
1. App installs `WebhookHandler` per `docs/usage/webhooks.md`, whose `handle` uses `data.shop` to select which shop's records to update (the documented pattern).
2. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers a real webhook (e.g. `products/update`) with body content of their choosing (e.g., a product title containing a payload relevant to the target flow). Attacker records the exact raw body and the resulting `x-shopify-hmac-sha256` header Shopify sent.
3. Attacker POSTs to the app's webhook endpoint reusing that exact raw body and HMAC, but sets `x-shopify-shop-domain: victim.myshopify.com` and `x-shopify-topic: products/update`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers (all required headers present) — [6](#0-5) .
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `raw_body` — [7](#0-6) .
6. The handler is invoked with `WebhookMetadata.new(topic: "products/update", shop: "victim.myshopify.com", body: attacker_controlled_body, ...)` — [8](#0-7) , causing the app to act on `victim.myshopify.com`'s behalf using attacker-supplied content.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
