### Title
Stale-rate reward calculation in `pallet-consensus-incentives::calculate_reward` overpays/underpays relayers when `CostPerBlock` changes between reward payouts - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
The reported `EscrowManager.getPastVotes()` bug is a general "current rate applied over a historical elapsed interval" bug class: a rate stored/read *at settlement time* is multiplied by a span of time/height that occurred *before* that rate was set, so any rate change silently mispays the whole unpaid span rather than only the portion under the new rate. `pallet-consensus-incentives::calculate_reward` reproduces the same pattern for relayer rewards.

### Finding Description
`Pallet::calculate_reward` computes the reward for a consensus update as: [1](#0-0) 

```
let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);
let blocks = latest_height.saturating_sub(baseline);
let reward = blocks_as_balance.saturating_mul(block_cost);
```

`block_cost` is read fresh from `StateMachinesCostPerBlock` at the moment `process_message` runs [2](#0-1) , i.e. it is the *current* configured cost, exactly like `EscrowManager` reading the *current* decay rate. The `blocks` span, however, is `latest_height - baseline`, which can straddle any number of prior, unpaid heights that accrued while a *different* `cost_per_block` was in effect (governance can update it at any time via the unsigned, no-history `update_cost_per_block` extrinsic [3](#0-2) ). There is no per-height or per-rate-epoch accounting; `StateMachinesCostPerBlock` only ever holds a single current value [4](#0-3) .

Because rewards are watermark-based and can legitimately batch a large unpaid span (the `reward_covers_only_unpaid_heights_after_rollback` test shows a single settlement covering many blocks at once, and settlements can be delayed arbitrarily long since relayers only pay when they submit a `ConsensusMessage`) [5](#0-4) , any rate change that happens between the baseline height and the settlement height applies the wrong rate to part of the span:

- If governance raises `cost_per_block` after a large unpaid backlog accrues, the very first relayer to submit a proof afterward is overpaid for the *entire* backlog at the new, higher rate.
- If governance lowers `cost_per_block`, relayers who already earned the right to be paid at the old rate for blocks that occurred before the change are underpaid — the treasury effectively retroactively cuts pay for work already done.

This is triggered by an ordinary, unprivileged action — a relayer submitting a `ConsensusMessage` via `pallet_ismp::handle_unsigned` (an unsigned inherent-style extrinsic) [6](#0-5)  — combined with a routine, non-malicious governance parameter update. No malicious admin action is required for the miscalculation to occur; the vulnerability is in the reward math itself, not in governance intent.

### Impact Explanation
`calculate_reward` moves real treasury funds (`T::Currency::transfer` from `TreasuryAccount` to the relayer) and mints a corresponding `ReputationAsset` amount based on the miscalculated reward [7](#0-6) . A stale-rate span produces either:
- unbacked over-minting of funds/reputation from the treasury to a single relayer for a large backlog priced at a rate that was never in effect during most of that backlog (funds loss to the treasury / other relayers), or
- an unfair underpayment that reduces relayer incentive to keep the consensus client fresh, which can degrade Hyperbridge's liveness for that state machine (a delivery/economic-security concern, not merely cosmetic).

Because the backlog size (`blocks`) is fully attacker-influenceable by simply waiting to submit a proof until after a rate change and because any relayer can trigger settlement by submitting a valid consensus message, the miscalculation is reachable from a single unprivileged relayer transaction.

### Likelihood Explanation
Medium. It requires two things to align: (1) a `cost_per_block` update via the standard governance extrinsic, and (2) an unpaid height backlog spanning that update. Given that watermark rewards are explicitly designed to batch large spans (as shown by the rollback test paying `5 * BLOCK_COST` for one settlement) and that `cost_per_block` values are expected to be tuned as market conditions/chain costs change, this is a realistic, not merely theoretical, operational scenario — every cost-per-block adjustment made while any state machine has outstanding unpaid heights corrupts that settlement.

### Recommendation
Do not apply a single current `block_cost` to a historical span that may straddle rate changes. Options:
- Snapshot `(rate, effective_from_height)` and require `calculate_reward` to sum contributions per rate-epoch across the `[baseline, latest_height]` span (mirrors "accurately accounting for past rate changes" from the original report).
- Alternatively, force settlement (or at least record a checkpoint of `LastRewardedHeight`/pending reward) whenever `update_cost_per_block` changes a value that has an outstanding, un-rewarded backlog, so a rate change can never retroactively reprice already-elapsed blocks.

### Proof of Concept
Conceptual PoC building on the existing test harness style (`reward_covers_only_unpaid_heights_after_rollback`) [8](#0-7) :

1. Set `cost_per_block = 100` for `state_machine_id` via `update_cost_per_block`.
2. Advance the state machine height from 0 to 1000 with no relayer ever submitting a `ConsensusMessage` (so `LastRewardedHeight` stays at its baseline and the 1000-block span remains unpaid).
3. Governance calls `update_cost_per_block` again, raising `cost_per_block` to 10,000.
4. A relayer submits a single `ConsensusMessage` advancing to height 1000 (or any height above the backlog). `calculate_reward` computes `reward = 1000 * 10_000`, i.e. the entire 1000-block backlog priced at the new rate, even though 999 of those blocks accrued while the rate was 100 — a 100x overpayment relative to what should have been owed under the rates actually in effect at each height.

Note: This is presented as an analog derived from the reported bug class (current-rate-applied-to-past-elapsed-interval) and the `calculate_reward` code path; it has not been executed against a live test harness in this session, so exact numeric outputs should be confirmed by running the described scenario in the existing `pallet_consensus_incentives` test module.

// A relayer is paid once for advancing a state machine across a span of heights. When the latest
// height is rolled back and later resubmitted, the reward should still only cover the new blocks.
// The `LastRewardedHeight` watermark keeps each payout scoped to the span that has not been paid.
#[test]
fn reward_covers_only_unpaid_heights_after_rollback() {
	let mut ext = new_test_ext();
	ext.execute_with(|| {
		const BLOCK_COST: u128 = 100;
		let host = Ismp::default();
		let state_machine_id = setup_state_machine();
		let treasury_account: AccountId32 = PalletId(*b"treasury").into_account_truncating();

		pallet_consensus_incentives::Pallet::<Test>::update_cost_per_block(
			RuntimeOrigin::root(),
			state_machine_id,
			BLOCK_COST,
		)
		.unwrap();

		let (consensus_message, relayer_account) = setup_host_and_message(&host);
		let message = MessageWithWeight { message: consensus_message, weight: Weight::zero() };
		let updated = |height: u64| {
			vec![IsmpEvent::StateMachineUpdated(StateMachineUpdated {
				state_machine_id,
				latest_height: height,
			})]
		};

		// The chain has already advanced to 1025 and every block up to it has been rewarded once.
		host.store_state_machine_commitment(
			StateMachineHeight { id: state_machine_id, height: 1024 },
			commitment(),
		)
		.unwrap();
		host.store_latest_commitment_height(StateMachineHeight {
			id: state_machine_id,
			height: 1024,
		})
		.unwrap();
		host.store_state_machine_commitment(
			StateMachineHeight { id: state_machine_id, height: 1025 },
			commitment(),
		)
		.unwrap();
		host.store_latest_commitment_height(StateMachineHeight {
			id: state_machine_id,
			height: 1025,
		})
		.unwrap();

		let treasury_before_first = Balances::balance(&treasury_account);
		<pallet_consensus_incentives::Pallet<Test> as FeeHandler>::on_executed(
			vec![message.clone()],
			updated(1025),
		)
		.unwrap();

		assert_eq!(Balances::balance(&treasury_account), treasury_before_first - BLOCK_COST);
		assert_eq!(
			pallet_consensus_incentives::LastRewardedHeight::<Test>::get(state_machine_id),
			Some(1025)
		);

		// The previous-height pointer references an older height whose commitment is no longer
		// retained in the bounded map.
		pallet_ismp::PreviousStateMachineHeight::<Test>::insert(state_machine_id, 1);

		// Deleting the latest commitment rolls the latest height back to that previous pointer.
		host.delete_state_commitment(StateMachineHeight { id: state_machine_id, height: 1025 })
			.unwrap();
		assert_eq!(host.latest_commitment_height(state_machine_id).unwrap(), 1);

		// The next honest consensus update advances to 1030, carrying the stale pointer forward as
		// the new previous height.
		host.store_state_machine_commitment(
			StateMachineHeight { id: state_machine_id, height: 1030 },
			commitment(),
		)
		.unwrap();
		host.store_latest_commitment_height(StateMachineHeight {
			id: state_machine_id,
			height: 1030,
		})
		.unwrap();
		assert_eq!(host.previous_commitment_height(state_machine_id), Some(1));

		let treasury_before_second = Balances::balance(&treasury_account);
		<pallet_consensus_incentives::Pallet<Test> as FeeHandler>::on_executed(
			vec![message],
			updated(1030),
		)
		.unwrap();

		// The real advance is 1025 -> 1030, so only the 5 new blocks are paid rather than the full
		// span back to the previous pointer.
		assert_eq!(Balances::balance(&treasury_account), treasury_before_second - 5 * BLOCK_COST);
		assert_eq!(
			pallet_consensus_incentives::LastRewardedHeight::<Test>::get(state_machine_id),
			Some(1030)
		);
	})
}
