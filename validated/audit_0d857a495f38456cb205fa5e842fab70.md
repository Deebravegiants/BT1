### Title
Missing validation on `changePassphrase` allows silent removal of wallet passphrase protection - ([File: features/wallet/module/wallet.js])

### Summary
The external report describes `Staking.sol` admin functions (e.g. `setOwner`) that accept sensitive parameters without validating them against zero/empty values, which can silently and irrevocably degrade the security configuration of the contract. The analogous pattern exists in `Wallet#changePassphrase` in `features/wallet/module/wallet.js`, where the `newPassphrase` argument is passed straight through to `#setSeed` without any check that it is non-empty, allowing a falsy value to silently strip passphrase protection from the wallet's stored seed.

### Finding Description
`changePassphrase` verifies the current passphrase, then re-stores the seed under `newPassphrase` with no validation of that value: [1](#0-0) 

The re-storage is done via `#setSeed`, which branches purely on JS truthiness of `passphrase`: [2](#0-1) 

If `newPassphrase` is `''`, `null`, or `undefined` (e.g., due to a caller bug, a stripped/blank form field, or any unvalidated input reaching this API), the `if (passphrase)` branch at line 96 is skipped, and the wallet falls into the "no user passphrase" branch: it marks `HAS_USER_SET_PASSPHRASE_KEY` as `false`, optionally substitutes an auto-generated password, and persists the seed with no user-supplied passphrase — exactly mirroring the `setOwner`/`root`/`nonce` zero-value class of bug where a sensitive administrative/security parameter is accepted without a non-empty/non-zero check, silently and irrevocably reconfiguring the security posture (here: disabling password-based encryption of the mnemonic) instead of failing loudly.

This function is exposed to the top-level SDK/API surface (`exodus.wallet.changePassphrase` / `exodus.application.changePassphrase`), so it is reachable by unprivileged application/UI code: [3](#0-2) [4](#0-3) 

### Impact Explanation
Since `seedStorage.set(value, { passphrase })` is documented as the mechanism providing passphrase-based encryption of the mnemonic (`features/wallet/README.md`), silently accepting an empty `newPassphrase` causes the wallet's seed to be persisted without the user-intended passphrase-derived encryption. This is a direct wallet-compromise vector: any caller (buggy UI, malformed API/RPC call, or otherwise) that invokes `changePassphrase` with an empty string instead of throwing/rejecting will downgrade the encryption protecting the mnemonic without any explicit signal to the user, and there is no re-prompt or confirmation step at this layer to catch it.

### Likelihood Explanation
The function has no built-in guard against empty-string/undefined input, and the type signature only requires a `string`, not a non-empty string, at any layer (module, API façade, or headless API): [3](#0-2) [5](#0-4) 
Any bug in a calling UI (e.g., a form that can submit before validation, or programmatic/automation misuse) that produces an empty string reaches this code path directly, with no server-side/module-side rejection.

### Recommendation
Add explicit validation in `changePassphrase` (and ideally in `#setSeed`) to require `newPassphrase` be a non-empty string whenever `#usePassword` is enabled and the caller intends to keep passphrase protection, e.g.:
```js
changePassphrase = async ({ currentPassphrase, newPassphrase }) => {
  if (this.#usePassword) {
    assert(newPassphrase, 'newPassphrase must not be empty')
    ...
```
This mirrors the report's short-term recommendation to validate non-zero/non-empty values for security-critical parameters, and long-term, add explicit unit tests asserting that `changePassphrase({ newPassphrase: '' })` throws rather than silently disabling passphrase protection.

### Proof of Concept
```js
// Given a wallet created with password support (usePassword: true) and an existing passphrase:
await exodus.wallet.create({ passphrase: 'correct horse battery staple' })
await exodus.wallet.unlock({ passphrase: 'correct horse battery staple' })

// Caller intends to set a new passphrase but an empty string reaches the function
// (e.g. due to a UI validation bug, or a malformed automated/API call):
await exodus.wallet.changePassphrase({
  currentPassphrase: 'correct horse battery staple',
  newPassphrase: '',
})

// Result: HAS_USER_SET_PASSPHRASE_KEY is now false, and the seed is re-persisted
// without the user's intended passphrase-based encryption -- no error is thrown.
await exodus.wallet.hasPassphraseSet() // => false, protection silently removed
```
