### Title
Permissive `instance()` fallback in the Tron `IntentGatewayV2` lets any unregistered source chain forge messages that authenticate as the gateway itself - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2` implements `instance()` differently from the canonical EVM `IntentsBase._instance()`. The canonical version reverts with `UnknownInstance` when a state machine has no registered peer gateway [1](#0-0) . The Tron port instead silently falls back to `address(this)` for any unregistered `stateMachineId`: [2](#0-1) 

This fallback is used directly in `authenticate(request)`, which is the sole gate protecting the escrow-redeeming and governance-processing branches of `onAccept` (RedeemEscrow, RefundEscrow, and — per the doc comment in `evm/src/apps/intentsv2/ExtrinsicIntents.sol` lines 310-330 — potentially other request kinds ported to the same pattern).

### Finding Description
Cross-chain modules in this codebase authenticate `IsmpModule::on_accept`/`onAccept` deliveries by checking that `request.from` matches the module address registered for `request.source`. This pattern appears consistently: `HyperFungibleToken.onAccept` reverts with `UnauthorizedSource` for any chain without a registered peer [3](#0-2) , and the canonical `IntentGatewayV2`/`ExtrinsicIntents._authenticate` reverts with `Unauthorized` when `_instance(request.source) != module`, and `_instance` itself reverts with `UnknownInstance` for unregistered chains [4](#0-3) [5](#0-4) .

The Tron deployment breaks this invariant: `instance()` returns `address(this)` instead of reverting when the chain is unregistered [6](#0-5) . Since `authenticate()` compares `instance(request.source)` against `address(bytes20(request.from))` [7](#0-6) , any message whose declared `source` is a state machine that has never had a peer gateway registered will authenticate successfully as long as the attacker sets `request.from = address(thisIntentGateway)` — the attacker fully controls both fields when they are the module dispatching from their own (unregistered/arbitrary) chain, since ISMP only proves that a given source chain's consensus produced a given commitment, not that the `from` address is meaningful on that chain.

This is structurally analogous to CVE-2021-22229: a data-scoping/authentication check that has a permissive default path (there: fork inheriting internal-repo visibility; here: `instance()` "inheriting" the identity of the gateway contract itself for any un-configured chain) lets an entity with no privileged relationship to the target (an unprivileged relayer/dispatcher on any unregistered state machine) satisfy an access check meant to restrict a privileged/internal actor (the gateway's own peer instance / Hyperbridge governance channel).

### Impact Explanation
`onAccept` routes `RequestKind` values including `RedeemEscrow` (releases escrowed input tokens to a solver) and `RefundEscrow` (refunds escrow to a user) to the `authenticate()`-gated branch, per the documented behavior in the sibling `ExtrinsicIntents.onAccept` [8](#0-7) . If the Tron contract mirrors this dispatch (which its shared `IntentsBase`/`ExtrinsicIntents` ancestry strongly suggests), an attacker who dispatches a forged `PostRequest` from any state machine that is not an explicitly registered `instance` — trivially satisfiable since new/arbitrary state machine identifiers are attacker-choosable bytes — with `from = address(intentGateway)` can pass authentication and drain escrowed order funds (`_orders`/`_filled`) to an address of their choosing. This is concrete theft of escrowed user/solver funds, reachable by a single relayed cross-chain message from an unprivileged dispatcher, matching the required impact bar (concrete theft / unauthorized app action).

### Likelihood Explanation
Likelihood is high if the Tron gateway is deployed with any state machines left unregistered (the common case — new deployments only register a handful of known peer chains, per `initialize`'s `peerChains` parameter pattern seen in the EVM gateway [9](#0-8) ). Any relayer capable of delivering an ISMP message through Hyperbridge from a chain the gateway has not registered as a peer can trigger this — no governance, admin, or validator compromise is required, only a standard relayed request through the normal dispatch path (`onlyHost` on `onAccept` is satisfied by the legitimate host delivering any proven message; the flaw is purely in the module-level `authenticate()` check, not in host-level proof verification).

### Recommendation
Change `IntentGatewayV2.sol` (Tron) `instance()` to match the canonical `IntentsBase._instance()` behavior: revert with an `UnknownInstance`/`Unauthorized`-style error when no peer gateway is registered for the given state machine, rather than defaulting to `address(this)`. Audit all callers of `instance()`/`authenticate()` in the Tron contract to confirm none rely on the permissive fallback for legitimate functionality (e.g., self-referential registration), and add a regression test mirroring `IntentGatewayV2Test.sol`'s `testInstance`/`testOnAcceptRejectsAnotherPalletOnNexus`-style negative cases, asserting that a forged message from an unregistered chain claiming `from = address(this)` is rejected.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with peers registered only for the chains it actually integrates with (e.g., Ethereum, Nexus) — state machine `"ARBITRARY_CHAIN"` is never registered.
2. A user places an order on the Tron gateway; solver fills it, escrow accumulates in `_orders`/`_filled` as usual.
3. Attacker crafts (or relays) a `PostRequest` with `source = "ARBITRARY_CHAIN"`, `from = abi.encodePacked(address(intentGateway))`, `to = abi.encodePacked(address(intentGateway))`, and `body` encoding `RequestKind.RedeemEscrow` for the target commitment and an attacker-controlled beneficiary/solver address.
4. Since `"ARBITRARY_CHAIN"` has no registered `_instances` entry, `instance("ARBITRARY_CHAIN")` returns `address(this)` (the gateway's own address) instead of reverting.
5. `authenticate(request)` computes `module = address(bytes20(request.from)) == address(intentGateway)`, which equals `instance(request.source)`, so the check passes.
6. The forged request is processed as if it came from a legitimate peer gateway, releasing the escrowed tokens to the attacker's chosen address — theft of escrowed funds.

Note: I could not directly view the full `onAccept` function body of `evm/tron/contracts/apps/IntentGatewayV2.sol` in this session (index truncation prevented retrieving lines beyond what's shown above) to confirm verbatim that `RedeemEscrow`/`RefundEscrow` dispatch uses `authenticate()` in the Tron file specifically, though its imports, `authenticate()` definition, and shared inheritance from `IntentsBase` strongly indicate it does. A Devin session with full file access should confirm the exact `onAccept` dispatch table in that file before treating this as fully verified.

     * @dev Resolves the IntentGateway instance address for a given state machine.
     * Reverts with `UnknownInstance` if no remote deployment has been registered for that chain.
     * @param stateMachineId The raw state machine identifier bytes.
     * @return The gateway address for the given state machine.
     */
    function _instance(bytes calldata stateMachineId) internal view returns (address) {
        address gateway = _instances[keccak256(stateMachineId)];
        if (gateway == address(0)) revert UnknownInstance();
        return gateway;
    }

    function instance(bytes calldata stateMachineId) public view returns (address) {

    /**
     * @dev Checks that the request originates from a known instance of the IntentGateway.
     */
    function authenticate(PostRequest calldata request) internal view {
        if (request.from.length != 20) revert InvalidInput();
        address module = address(bytes20(request.from));
        // IntentGateway only accepts incoming assets from itself or known instances
        if (instance(request.source) != module) revert Unauthorized();
    }
