### Title
Webhook `shop-domain` header not covered by HMAC signature, allowing cross-tenant webhook replay - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers used to dispatch and process that webhook are never included in the signed payload. This breaks the identity binding between "the shop the HMAC signature attests to" and "the shop the handler is told the data belongs to," letting a request with a validly-signed body but an attacker-controlled shop header be processed as if it originated from an arbitrary shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Utils::HmacValidator.validate` computes and compares the HMAC exclusively over that signable string: [2](#0-1) 

`Registry.process` treats a passing HMAC check as proof the whole request "did indeed come from Shopify" (per the gem's own docs), then immediately trusts the unauthenticated `shop`, `topic`, `webhook_id`, and `api_version` header values pulled straight off the request object to build the data handed to the app's handler: [3](#0-2) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are simple header reads with no cryptographic binding to the body or to each other: [4](#0-3) 

Because Shopify signs webhooks per-app (using the app's single `api_secret_key`), not per-shop, a valid `hmac-sha256`/body pair obtained from any shop that has installed the app (including a shop the attacker fully controls, e.g. their own free development store) remains valid for that same body regardless of which `shop-domain` header accompanies it. An attacker can capture one authentic `(raw_body, hmac)` pair from a webhook fired on their own store, then replay the request to the app's public webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop. `HmacValidator.validate` still returns `true` because it never inspects the shop header, and `Registry.process` dispatches the handler with `shop: request.shop` set to the victim's domain — a value that was never authenticated at all.

This is the same class of bug as the reported issue: a downstream security-relevant field (`_admin`/`shop`) is consumed without validation, even though a sibling code path (`changeAdmin`/`HmacValidator.validate`) shows the correct check exists elsewhere but simply isn't applied to this field. Here the "sibling correct check" is the body HMAC itself — proving the correct mechanism (HMAC binding) exists in the codebase, but it is not extended to cover the tenant-identifying header.

### Impact Explanation
Handlers built on top of `Registry.process` receive `WebhookMetadata` whose `shop` field is attacker-controlled despite HMAC validation having passed. Any app that uses `data.shop` to select which merchant's records to update, uses it as a cache/session key, or otherwise trusts it as the authenticated tenant identifier can be tricked into writing/reading data under the wrong shop — a cross-tenant access/data-integrity issue, one of the explicitly listed Critical impacts for this scan (cross-tenant access).

### Likelihood Explanation
Exploitation requires no privileged credentials from the app: any unprivileged internet user can install the target app on their own (free) development store to legitimately trigger a webhook and obtain one valid `(body, hmac)` pair signed with the app's shared secret, then replay that exact HTTP request to the app's public webhook URL with a forged `shop-domain` header. The webhook endpoint is typically internet-reachable by design (that's how Shopify delivers webhooks), so likelihood is realistic wherever an app's handler logic relies on `WebhookMetadata#shop` for tenant scoping — which the gem's own documentation encourages ("register to receive webhooks for a shop... process a webhook... this will verify the request did indeed come from Shopify").

### Recommendation
- Short term: Include the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or otherwise cryptographically bind them to the request (e.g., verify `shop` against the shop associated with the currently active/expected session before invoking the handler), and document that `WebhookMetadata#shop` must not be trusted as authenticated unless independently verified.
- Long term: Audit all places where header/query values are used as authorization or tenant-scoping inputs without being part of a signed payload, and add property-based tests (e.g., Echidna-style fuzzing/replay tests) asserting the invariant that any field influencing tenant-scoped behavior is bound to the signature that authenticates the request.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled development store (`attacker-shop.myshopify.com`) — no special privilege required beyond normal app installation.
2. Trigger a webhook event (e.g., `orders/create`) on `attacker-shop`, capturing the exact `raw_body` and the `x-shopify-hmac-sha256` header Shopify sends — this HMAC is valid because it is computed with the app's `api_secret_key` shared across all installs.
3. Replay the captured request to the app's public webhook endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` unchanged but rewriting `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the (unchanged) body/HMAC pair and returns `true`: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though nothing about the request was ever authenticated as coming from that shop, allowing the attacker to inject events under an arbitrary tenant identity.
