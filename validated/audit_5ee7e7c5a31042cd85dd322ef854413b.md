### Title
Non-embedded cookie-based session resolution trusts unauthenticated, guessable `session.id` as a bearer credential - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
For non-embedded apps (`Context.embedded? == false`), `SessionUtils.current_session_id` unconditionally returns the raw `Cookie: shopify_app_session=...` value with zero HMAC/JWT verification, and that value is the fully predictable, publicly-derivable `offline_#{shop}` (or `#{shop}_#{user_id}`) string. An attacker can therefore forge this cookie for any victim shop domain (which is public knowledge) and, if the host app's `SessionStorage` resolves the id to a stored `Auth::Session`, obtain that merchant's `access_token`.

### Finding Description
The claimed binding — "session id == bytes authenticated under `Context.api_secret_key`" — never holds on the cookie path. It only holds for the embedded/JWT path, where `session_id_from_shopify_id_token` derives the id from a JWT verified via `Auth::JwtPayload` (HS256 signed with `api_secret_key`). For `Context.embedded? == false`, `current_session_id` skips JWT entirely and calls `cookie_session_id(cookies)`, which is just `cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]` — a straight hash lookup returning the raw client-supplied string, verbatim, with no signature or MAC check [3](#0-2) , [4](#0-3) .

Compounding this, the value that legitimately ends up in that cookie is not a random opaque secret: `Session.from` sets `id = "offline_#{shop}"` for offline sessions [5](#0-4) , and `validate_auth_callback` writes exactly `session.id` into the `SessionCookie` value for non-embedded apps [6](#0-5) . Since a shop's `*.myshopify.com` domain is public, any attacker can compute the exact valid cookie value for any target shop without ever observing real traffic. `SessionCookie` itself is a plain `T::Struct` carrying `name`/`value`/`expires` only [7](#0-6)  — it encodes no `HttpOnly`/`Secure`/`SameSite` attributes or any cryptographic binding; those are entirely up to the host framework, and the gem's own test suite explicitly documents/asserts that an arbitrary cookie value is returned unchanged as the session id (`test_non_embedded_app_current_session_id_returns_id_from_cookie`) [8](#0-7) .

None of the existing guards intercept this: `HmacValidator.validate` and the `state`/`auth_query.state` check only apply during the OAuth callback itself, not to subsequent API requests; `JwtPayload`'s `aud`/signature check is bypassed entirely because the embedded branch is never taken when `Context.embedded? == false`; `HttpRequest#verify` and `Context.setup?`/`private?` do not touch session-id derivation at all. The exploit request is simply any HTTP call to a host-app endpoint that calls `current_session_id(nil, request.cookies, false)` with header `Cookie: shopify_app_session=offline_victim-shop.myshopify.com` — no TLS interception, no secret, no browser needed, since HTTP servers don't verify that a Cookie header actually originated from a legitimate Set-Cookie exchange.

### Impact Explanation
If the host app's session storage does a bare id→`Auth::Session` lookup (as the gem's documented API implies is sufficient — `docs/getting_started.md` describes passing raw `cookies` directly into `current_session_id` with no mention of needing a signed/encrypted cookie jar) [9](#0-8) , the attacker is treated as the victim merchant and gains use of that merchant's `access_token` for all subsequent REST/GraphQL calls made through `Clients::HttpClient`, which injects `X-Shopify-Access-Token` from whatever session it's given [10](#0-9) . This is repeatable against any victim shop that has previously completed offline OAuth with the app, requires only knowledge of the shop's public domain, and constitutes cross-tenant access — Critical severity.

### Likelihood Explanation
Preconditions: app configured non-embedded, host app's session storage does a plain id-keyed lookup without additional cookie signing/verification beyond what this gem provides (which is exactly the scenario the gem's own docs and tests describe/exercise) [8](#0-7) , and the victim shop has completed OAuth at least once. Attacker cost is trivial: no credentials, no timing, no crypto — just the target's `.myshopify.com` domain string. Fully repeatable per shop.

### Recommendation
Do not treat the raw `shopify_app_session` cookie value as an authenticated bearer identifier. Either (a) require the host app to store the session cookie only via a cryptographically signed/encrypted cookie jar (and document this as a hard requirement, not an implementation detail left to the host), or (b) have `SessionCookie`/`cookie_session_id` embed and verify an HMAC over the session id keyed by `Context.api_secret_key`, mirroring the `state` HMAC-like binding already used in the OAuth callback flow, so that `cookie_session_id` rejects any cookie whose value wasn't produced and signed by this gem's own OAuth completion step.

### Proof of Concept
```ruby
# test/utils/session_utils_forged_cookie_test.rb
require_relative "../test_helper"

module ShopifyAPITest
  module Utils
    class ForgedCookieSessionIdTest < Test::Unit::TestCase
      def test_forged_offline_cookie_is_trusted_verbatim_for_non_embedded_apps
        ShopifyAPI::Context.stubs(:embedded?).returns(false)

        victim_shop = "victim-shop.myshopify.com"
        forged_session_id = "offline_#{victim_shop}"  # attacker computes this with zero secrets
        forged_cookies = { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => forged_session_id }

        resolved_id = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, forged_cookies, false)

        # Binding under test: resolved_id should equal only bytes authenticated under Context.api_secret_key.
        # It instead equals the raw attacker-supplied cookie string, unauthenticated.
        assert_equal(forged_session_id, resolved_id)

        # Simulate a host SessionStorage keyed by exact string, seeded by the *real* victim session
        # created during legitimate OAuth (access token unknown to attacker).
        victim_session = ShopifyAPI::Auth::Session.new(
          shop: victim_shop, id: forged_session_id, access_token: "real-victim-secret-token",
        )
        fake_storage = { forged_session_id => victim_session }

        resolved_session = fake_storage[resolved_id]
        assert_equal(victim_session, resolved_session)
        assert_equal("real-victim-secret-token", resolved_session.access_token)
        # The attacker never supplied or derived this token from any signed value —
        # it was obtained purely by guessing a deterministic id from a public shop domain.
      end
    end
  end
end
```

#### Cookie
Cookie based authentication is not supported for embedded apps due to browsers dropping support for third party cookies due to security concerns. Non-embedded apps are able to use cookies for session storage/retrieval.

For *non-embedded* apps, you can pass the cookies into:
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, true)` for online (user) sessions or
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` for offline (store) sessions.
