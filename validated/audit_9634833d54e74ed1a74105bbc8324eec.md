### Title
Webhook shop-domain (and topic/webhook-id/api-version) header spoofing bypasses HMAC binding, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body, but the `shop` (and `topic`, `webhook_id`, `api_version`) values used to identify the tenant are read from unsigned HTTP headers that are never included in the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from the `x-shopify-*`/`shopify-*` headers, none of which are part of the signed string: [2](#0-1) 

`Utils::HmacValidator.validate` computes/compares the signature over `to_signable_string` only — i.e. body bytes — never binding the `shop-domain` header to the signature: [3](#0-2) 

`Webhooks::Registry.process` then accepts the request purely on that body-only HMAC check and forwards `request.shop` (from the unsigned header) directly to the app's handler as the tenant identifier, with no further tie back to the HMAC: [4](#0-3) 

The identity binding that should hold is: `hmac(body, api_secret_key) == received_hmac` AND `shop-header == shop-that-sent-body`. The gem only enforces the first equality; the second is entirely attacker-controlled. Any client capable of observing a genuine `(raw_body, hmac)` pair delivered to their own store's endpoint (they own that store/server, so they legitimately receive it) can replay that exact pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header for a different (victim) shop. `HmacValidator.validate` still succeeds because it never looks at the header, and `Registry.process` hands the handler `WebhookMetadata.new(..., shop: request.shop, ...)` claiming the payload originated from the victim shop.

### Impact Explanation
Host applications are documented to key persistence/business logic off `data.shop` (per `docs/usage/webhooks.md`, e.g. `perform_later(shop_domain: data.shop, webhook: data.body)`), trusting it as the authenticated tenant identity because the request "passed HMAC validation." Because `shop` is not bound to the HMAC, an attacker who legitimately receives a real signed webhook for their own shop can relabel it as belonging to any other shop, causing the app to process attacker-controlled webhook content under a victim shop's identity — a cross-tenant confusion/spoofing vector (e.g. misattributing `app/uninstalled`, `customers/data_request`, or resource-update events to the wrong tenant).

### Likelihood Explanation
Exploitation requires only that the attacker (any unprivileged party who can install the app on their own store, which is normal, unprivileged app usage) capture a body+HMAC pair delivered to their own endpoint and replay it with a forged shop header to the app's public webhook URL — no access token, `client_secret`, or privileged credential is required, and no interaction with Shopify's own systems is needed after the initial legitimate delivery.

### Recommendation
Bind the shop (and topic/webhook_id) into the value that is actually verified — either by requiring the host application to independently confirm `shop` against a value derived from a signed source (e.g. cross-check with the shop tied to the webhook subscription/session), or by including the identifying headers in the HMAC computation before trusting `request.shop` downstream. At minimum, document prominently that `Request#shop` is unauthenticated header data and must not be trusted for tenant-scoping decisions without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets the app register for a webhook topic (e.g. `orders/create`).
2. Shopify delivers a legitimate webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`, plus `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures `(B, H)` from their own server logs (they own that endpoint's traffic in a self-hosted/dev scenario, or via a proxy they control).
4. Attacker sends a new HTTP POST directly to the app's webhook route with the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `Webhooks::Request#hmac`/`#to_signable_string` only look at `B`; `Utils::HmacValidator.validate` recomputes `HMAC(client_secret, B)` and it matches `H` — validation passes.
6. `Registry.process` invokes the handler with `WebhookMetadata(shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled content as if it came from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
