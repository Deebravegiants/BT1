### Title
`TokenExchange.exchange_token` sends the app's `client_secret` to a host derived from an unsanitized JWT `dest` claim - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds the request host that receives the app's `client_id`/`client_secret` directly from the session token's `dest` claim (`jwt_payload.shop`), without ever passing it through `Utils::ShopValidator.sanitize!`. Every other credential-sending path in this module (`migrate_to_expiring_token`, and `ClientCredentials.client_credentials`) explicitly calls `Utils::ShopValidator.sanitize!(shop)` before using the value as a request host. `exchange_token` is the one exception.

### Finding Description
`JwtPayload#shop` is computed as `@dest.gsub("https://", "")` [1](#0-0)  with no format/domain restriction — it only strips the `https://` prefix and returns whatever string was in the `dest` claim.

`exchange_token` takes this raw value and uses it as the `shop` for the session used to build the HTTP request host, sending the app's `client_secret` to it: [2](#0-1) 

By contrast, `migrate_to_expiring_token` in the very same file validates the shop before use: [3](#0-2) 
and `ClientCredentials.client_credentials` does the same: [4](#0-3) 

The `HttpClient` uses `session.shop` directly to construct the request URI host that will receive the POST body containing `client_id`/`client_secret`: [5](#0-4) 

The binding this breaks (expressed as an equality that should hold but doesn't): `host_receiving(client_secret) == ShopValidator.sanitize!(dest_claim)`. Instead the code enforces only `host_receiving(client_secret) == dest_claim` (unsanitized), diverging from the pattern used everywhere else credentials are sent to a shop-derived host in this same gem.

However, the exploitability of this gap depends on whether an unprivileged attacker can produce a `dest` claim value that is not a legitimate `*.myshopify.com` (or otherwise trusted) domain while still passing `JwtPayload` signature verification. `JwtPayload` verifies the JWT via `JWT.decode(token, api_secret_key, true, ..., algorithm: "HS256")` [6](#0-5)  — a valid signature requires knowledge of the app's `api_secret_key` (or `old_api_secret_key`), which under this exercise's rules is explicitly out of scope ("anything requiring `api_secret_key`... a leaked credential"). Session tokens with attacker-controlled `dest` values are only mintable by parties holding that secret (normally only Shopify and the app itself), so there is no demonstrated way for an unprivileged internet user, without already possessing the app's `api_secret_key`, to make `exchange_token` send the `client_secret` to an attacker-controlled host.

### Impact Explanation
If this path were reachable without the secret, the impact would be Critical/High (SSRF carrying the app's `client_secret` to an attacker-controlled host, i.e., credential exfiltration). As found, however, exploitation requires forging a validly-signed session token, which requires the `api_secret_key` — a prerequisite explicitly excluded from scope for this analysis.

### Likelihood Explanation
Low/unproven. The missing `ShopValidator.sanitize!` call is a genuine inconsistency relative to sibling methods in the same file and module, and is worth hardening defensively (defense-in-depth against secret rotation edge cases, misconfigured `Context.old_api_secret_key`, or future signature-verification regressions). But under the stated rules, no concrete unprivileged-attacker path to control the `dest` claim was found.

### Recommendation
For defense in depth and consistency with `migrate_to_expiring_token` and `ClientCredentials.client_credentials`, validate `dest_shop` through `Utils::ShopValidator.sanitize!` before constructing `shop_session` in `exchange_token`, so all three credential-sending call sites enforce the same trusted-domain invariant regardless of upstream JWT verification correctness.

### Proof of Concept
Not demonstrable without possession of the app's `api_secret_key` (out of scope per the rules). No further PoC is provided since a concrete unprivileged-attacker exploit path could not be constructed.
