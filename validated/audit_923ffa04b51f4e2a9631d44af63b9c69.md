### Title
Unprivileged bandwidth purchase spam evicts victim apps' paid subscriptions, permanently destroying prepaid bandwidth - (File: modules/pallets/bandwidth/src/lib.rs)

### Summary
`pallet-bandwidth` credits a `(app_chain, app)` FIFO subscription list on every purchase message, capped at 1024 entries, and evicts the oldest entry once the cap is reached. Any address on any registered EVM source chain can call `BandwidthManager.purchase()` targeting an arbitrary victim `(app_chain, app)` pair (the sponsorship model explicitly allows crediting any app on any chain from any payer chain). Because the FIFO cap is shared per key and eviction always removes the head regardless of remaining value, an attacker can spam the cheapest tier 1024+ times against a victim's key to evict all of the victim's legitimately paid, unconsumed bandwidth — a dust-cost, no-privilege DoS/fund-freezing attack directly analogous to the referenced Blueberry report, where dust-value `execute()` calls exhausted a shared, capacity-limited resource to deny service to legitimate users.

### Finding Description
- `Allowance<T>` is a `StorageDoubleMap<StateMachine, AppKey, SubscriptionList>` where `SubscriptionList = BoundedVec<Subscription, 1024>`. [1](#0-0) 
- `push_subscription` appends a new subscription for every accepted purchase; if the list is already at the 1024 cap, it evicts index 0 (the oldest entry) unconditionally — even if that entry still has a large `remaining_bytes` balance — and emits `SubscriptionEvicted` with the lost bytes. [2](#0-1) 
- The purchase path is reachable by anyone: `is_purchase_message` only checks that `request.from` matches the *registered manager contract* for `request.source` — not that the caller is the app owner. Any EOA can call `purchase()` on the public `BandwidthManager.sol` contract for any `(chain, app)` pair, because the purchase message's `app` and `app_chain` fields are attacker-supplied payload data, and "a buyer on Ethereum can credit an app on Base" is a documented, intended feature (sponsorship). [3](#0-2) [4](#0-3) 
- There is no per-purchaser rate limit, no minimum-value protection against dust tiers relative to the victim's balance, and no restriction preventing a third party from purchasing (and thus writing) against a key it doesn't own. [5](#0-4) 

This mirrors the referenced Blueberry bug class: a shared, capacity-bounded resource (there: a single global `execute()` lock via `inExec()`; here: the 1024-slot per-app FIFO) can be exhausted/manipulated by an unprivileged actor paying only the cheapest available unit cost (dust `amount`/cheapest tier), denying/damaging legitimate use.

### Impact Explanation
An attacker who has legitimately purchased or funded 1024 cheap-tier subscriptions targeting a victim `(app_chain, app)` key can evict every one of the victim's real, paid, unconsumed subscriptions from the FIFO list before they are drained by the gate. This is a permanent, on-chain-irreversible loss of prepaid bandwidth funds for the victim app (the docs themselves state "lost_bytes ... is what the user paid for and won't get to use"), and simultaneously denies the victim's application any bandwidth allowance (since the gate is the sole enforcement point for all non-purchase POST requests routed through Hyperbridge for that app) — meeting both the "permanent freezing of funds" and "route unable to deliver messages" criteria (the app's dispatch traffic becomes rejected with `GateError::NoAllowance`/`Insufficient` after eviction). [6](#0-5) [7](#0-6) 

### Likelihood Explanation
The attack requires only the cheapest configured tier price ($50/tier per the documented plan table) repeated up to 1024 times, entirely from an unprivileged EOA, with no special timing or race condition needed — this is comparable in cost/complexity to the dust-amount spam in the original Blueberry report. Given the pallet is designed for open cross-chain sponsorship (anyone can credit any app on any chain), the barrier to targeting an arbitrary victim key is zero beyond gas/tier cost.

### Recommendation
- Restrict `push_subscription`/purchase crediting so that only the app owner (or an explicitly authorized sponsor list) can append to a given `(app_chain, app)` subscription list, or
- Change eviction policy to refuse pushing (reject the purchase) rather than silently evicting existing unconsumed value when the list is full, and/or
- Track eviction loss per-purchaser vs. per-owner so that a purchaser cannot destroy another party's unconsumed balance, e.g. require an explicit `min_remaining_bytes` guard before evicting, or increase/parametrize the cap and charge deposit-scaled costs to make griefing economically prohibitive.

### Proof of Concept
1. Governance registers a `BandwidthManager` for `EVM-<chainId>` and configures `TierOne` as the cheapest tier ($50 / 100 KB).
2. Victim app `V` purchases a large, expensive tier (e.g., `TierFour`, $1000/8MB) via `BandwidthManager.purchase()`, crediting `Allowance[V.app_chain][V.app]` with one `Subscription { remaining_bytes: 8MB, ... }`.
3. Attacker `A` repeatedly calls `BandwidthManager.purchase()` 1024 times with `TierOne` and the payload's `app`/`app_chain` fields set to `V`'s app key/chain (sponsorship allows crediting any app), each dispatched as an ISMP POST to `pallet-bandwidth`.
4. Each purchase runs `on_accept` → `push_subscription`, which appends a `Subscription` for `(V.app_chain, V.app)`; once the list reaches 1024 entries, each subsequent attacker purchase evicts the oldest entry from the head — eventually evicting `V`'s legitimate 8MB subscription with `SubscriptionEvicted { lost_bytes: 8_000_000 }` before the gate ever drained it. [2](#0-1) 
5. `V`'s prepaid bandwidth is permanently lost, and `V`'s subsequent dispatches through the `BandwidthGate::try_consume` hook are rejected (`NoAllowance`/`Insufficient`) once the attacker's cheap entries (which absorbed the queue) are also consumed or expired, denying `V` service until it pays again. [7](#0-6)

```rust
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}
```

```rust
impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;

		Self::deposit_event(Event::BandwidthConsumed {
			source: *source,
			app: key,
			bytes: need,
			remaining: total - need,
		});
		Ok(())
	}
```

```text
## Subscription Lifecycle

Each `(chain, app)` row holds a FIFO list of subscriptions, capped at **1024** entries. Every purchase appends a new subscription — same-tier repurchases don't stack, they queue.

A subscription is immutable across its lifetime:

| Field             | Behavior                                                                       |
| ----------------- | ------------------------------------------------------------------------------ |
| `tier`            | Recorded at purchase time. Used for events and analytics, not for gating.      |
| `remaining_bytes` | Drains as the gate consumes messages. Pops once it hits zero.                  |
| `expires_at`      | Fixed at purchase. Never extends — a repurchase is a _new_ row, not a renewal. |
| `purchased_at`    | Insertion timestamp. Fixes FIFO order under same-block buys.                   |

### Drain order

The gate drains from the **head** of the list. Once the head is fully consumed it pops and continues into the next. If the next entry is expired it's swept silently — what you paid for is yours only until it expires.

This matters when you queue multiple tiers: the cheapest/oldest entry is consumed first regardless of which tier it came from. Plan top-ups so a higher tier doesn't sit behind a soon-to-expire lower tier you'd rather burn last.

### Eviction

Pushing onto a full list (1024 entries) evicts the **oldest** entry and emits `SubscriptionEvicted` with the lost bytes so the loss is auditable on-chain. In practice this only happens under pathological repeat-buy behavior — at the default of one purchase per cycle, 1024 buys is years of headroom.
```

```text
## Sponsorship

The purchase message carries its own `chain` (the _credit chain_) which is **independent of the source chain** that sent the message. This means a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`.

The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`. The event `BandwidthCredited` carries both — `app_chain` (where the credit lands) and `paid_from` (where the payment came from) — so the cross-chain payer is auditable.

This is what makes the system multi-tenant friendly: a treasury on a single chain can sponsor bandwidth for an app deployed across many chains, without having to deploy `BandwidthManager` on each chain the app lives on.
```
