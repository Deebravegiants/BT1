Based on my investigation, I found a legitimate analog in the codebase. The external report's root cause is "unchecked return value from a transfer, causing the calling contract to update internal accounting as if the transfer succeeded, even when it didn't." The NEAR-native analog of an ERC-20 return-value check is checking the outcome of an outgoing `Promise` via a callback (`is_promise_success()`), and the `staking-pool` contract has exactly one place where a native NEAR transfer is fired without any such confirmation.

### Title
Unchecked Promise Result on NEAR Transfer in `StakingContract::withdraw`/`withdraw_all` Leads to Permanent Loss of Funds - (File: staking-pool/src/internal.rs)

### Summary
`internal_withdraw()`, invoked by the public `withdraw()` and `withdraw_all()` entry points, permanently decrements the caller's `unstaked` balance and the contract's `last_total_balance` and then fires an outgoing `Promise::new(account_id).transfer(amount)` **without ever attaching a `.then()` callback** to confirm the transfer succeeded. [1](#0-0)  This is the direct NEAR analog of the reported issue: the contract "trusts" that the outgoing transfer will succeed and commits state changes based on that untrusted assumption, exactly like unconditionally trusting an ERC-20 `transfer()`'s return value.

### Finding Description
Every other outgoing cross-contract/staking action in this codebase (`internal_restake`/`on_stake_action`, and the entire `lockup` contract's staking interactions) follows the pattern of firing a `Promise`, chaining `.then(ext_self::on_X_callback(...))`, and only finalizing state changes after checking `is_promise_success()` in the callback. [2](#0-1) [3](#0-2) 

In contrast, `internal_withdraw` in `staking-pool/src/internal.rs` decrements `account.unstaked` and `self.last_total_balance` synchronously, then calls `Promise::new(account_id).transfer(amount)` and returns, with no `.then()` and no callback verifying `is_promise_success()`: [4](#0-3) 

The public methods `withdraw()` and `withdraw_all()` call this function directly with no follow-up verification: [5](#0-4) 

If the transfer receipt fails for any reason (e.g., the account no longer exists at execution time, or any other native-transfer failure condition), the NEAR runtime does not automatically roll back the state already committed in the sending contract's function — that only happens if the contract explicitly checks the promise result in a callback and reverts/re-credits the accounting. Since no such callback exists here, the internal ledger permanently reflects the withdrawal as successful (balance decremented) while the actual NEAR was never delivered, and is not deducted from the contract's own balance either. There is no method to re-credit the account, so the funds become stuck/unaccounted for.

### Impact Explanation
This falls under: "Critical. Permanent freezing, unrecoverable lock, or irrevocable loss of user or protocol funds in ... unstake-withdraw ... flows." A user's rightfully unstaked, withdrawable NEAR can become permanently unrecoverable through the contract's own accounting once a withdraw transfer fails post-state-update, with no compensating callback logic to detect and reverse the failure.

### Likelihood Explanation
The withdraw path is a normal, frequently-used entry point (`withdraw`/`withdraw_all`) reachable by any unprivileged delegator with a nonzero unstaked balance — no special privilege is required. [6](#0-5)  While simple NEAR transfers to an existing account rarely fail, the contract provides no defense-in-depth against the failure case that every other transfer-related flow in the same codebase (staking, unstaking, restaking, and all of lockup's staking interactions) explicitly guards against via `is_promise_success()` callbacks. The asymmetry itself indicates this is an overlooked gap rather than an accepted design tradeoff.

### Recommendation
Mirror the pattern used elsewhere in the codebase (e.g., `on_stake_action`, `on_staking_pool_withdraw`): chain a `.then()` callback on the `Promise::new(account_id).transfer(amount)` in `internal_withdraw`, and only finalize (or conversely, re-credit `account.unstaked` and `last_total_balance` on failure) based on `is_promise_success()` in that callback, rather than committing state unconditionally before the transfer outcome is known.

### Proof of Concept
1. User deposits and later unstakes funds, waiting the required epochs so `unstaked_available_epoch_height` is reached.
2. User calls `withdraw(amount)` (or `withdraw_all()`).
3. `internal_withdraw` immediately decrements `account.unstaked` and `self.last_total_balance`, then issues `Promise::new(account_id).transfer(amount)` with no callback. [4](#0-3) 
4. If that transfer receipt fails (e.g., the target account was removed/became invalid between call submission and receipt execution), the NEAR is never delivered, yet the contract's internal ledger already shows the balance as withdrawn with no code path to detect the failure or restore the account's `unstaked` balance.

    pub(crate) fn internal_withdraw(&mut self, amount: Balance) {
        assert!(amount > 0, "Withdrawal amount should be positive");

        let account_id = env::predecessor_account_id();
        let mut account = self.internal_get_account(&account_id);
        assert!(
            account.unstaked >= amount,
            "Not enough unstaked balance to withdraw"
        );
        assert!(
            account.unstaked_available_epoch_height <= env::epoch_height(),
            "The unstaked balance is not yet available due to unstaking delay"
        );
        account.unstaked -= amount;
        self.internal_save_account(&account_id, &account);

        env::log(
            format!(
                "@{} withdrawing {}. New unstaked balance is {}",
                account_id, amount, account.unstaked
            )
            .as_bytes(),
        );

        Promise::new(account_id).transfer(amount);
        self.last_total_balance -= amount;
