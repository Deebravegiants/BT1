## Finding

The webhook processing path in this gem trusts an unauthenticated `shop` field while only the request body is covered by the HMAC signature, breaking the identity binding: **HMAC-covered bytes (`raw_body`) ≠ shop identity used for handler dispatch (`X-Shopify-Shop-Domain` header)**.

### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` verifies the HMAC exclusively over the JSON body. The `shop` (from the `x-shopify-shop-domain`/`shopify-shop-domain` header), along with `topic`, `webhook_id`, and `api_version`, are read straight from HTTP headers with no cryptographic binding to the signature and no domain sanitation (`Utils::ShopValidator` is never invoked here). [1](#0-0) [2](#0-1) 

### Finding Description
`Webhooks::Registry.process` validates only the HMAC of the request and then forwards `request.shop` (an unauthenticated header value) directly into the `WebhookMetadata` struct that is handed to the app's registered handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes/compares the HMAC solely against `verifiable_query.to_signable_string`, which for a webhook `Request` is `@raw_body` — headers are never part of the signable content: [4](#0-3) 

Because a single app has one `api_secret_key` shared across all merchants that installed it, an attacker who controls (or has previously captured) a legitimate `(raw_body, hmac)` pair for any shop — e.g. by installing a free/dev store and triggering a webhook for a body they fully control — can replay that exact body and its valid HMAC to the app's webhook endpoint while swapping the `x-shopify-shop-domain` (and `topic`/`webhook_id`) headers to point at an arbitrary victim shop. `HmacValidator.validate` will still return `true` because it only checks the body bytes, and `Registry.process` will dispatch the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

This differs from the OAuth callback path in the same gem, where `Auth::Oauth::AuthQuery#to_signable_string` explicitly includes `shop` in the signed parameters, so shop-spoofing is not possible there: [5](#0-4) 

### Impact Explanation
Host applications are expected to use `WebhookMetadata#shop` (the gem's own documented struct returned from `Registry.process`) to look up the merchant/session the webhook body should be applied to. Since this field is not bound to the HMAC, an attacker can forge the shop identity on an otherwise-valid webhook request, causing the receiving application to apply attacker-controlled webhook data (order data, product data, GDPR payloads, etc.) under a different tenant's identity — a cross-tenant integrity/confidentiality breach rooted entirely in this gem's `Webhooks::Request`/`Registry` implementation, not in host-app misuse.

### Likelihood Explanation
Exploitation requires only: (1) knowledge of one valid `(raw_body, hmac)` pair for the target app (trivially obtainable by installing the app on an attacker-owned store and capturing its own genuine webhook), and (2) the ability to send an HTTP POST with attacker-chosen headers to the app's public webhook endpoint. No access token, `api_secret_key`, or privileged account is required, making this reachable by an unprivileged internet user.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signable content for webhooks (or otherwise cryptographically bind them, e.g., by deriving shop identity only from a value included inside the signed body), and/or validate the header-derived `shop` domain via `Utils::ShopValidator.sanitize!` before constructing `WebhookMetadata`, rejecting mismatches between the claimed shop and any shop-identifying data inside the verified body.

### Proof of Concept
1. Attacker installs the target app on their own `attacker-shop.myshopify.com` and captures a genuine webhook delivery: raw body `B` and its valid `X-Shopify-Hmac-Sha256` header `H` (computed by Shopify over `B` using the app's shared `api_secret_key`).
2. Attacker replays the request to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `H` against `HMAC(secret, B)` — this passes.
4. `Registry.process` dispatches the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-controlled data as if it originated from `victim-shop.myshopify.com`. [6](#0-5)
