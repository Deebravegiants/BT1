### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` (tenant identifier) is taken from an unsigned HTTP header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then unconditionally trusts `request.shop` to route the webhook payload to the host app's per-merchant handler. Any actor who can obtain one authentic, validly-signed webhook (e.g. by installing the app on their own store) can replay that same body/HMAC pair while substituting a different `shop-domain` header, causing the webhook to be processed as if it belonged to another merchant.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed content: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` (which only checks `to_signable_string`, i.e. the body) and then dispatches to the handler using `request.shop` taken straight from the unauthenticated header, with no cross-check against the signed body: [3](#0-2) 

`Utils::HmacValidator.validate_signature` confirms only that the HMAC matches the (secret, body) pair — it never verifies that the `shop` header is bound to that signature: [4](#0-3) 

The identity binding broken is: `hmac == HMAC(secret, body)` should imply `shop == tenant_that_produced(body)`, but the code only enforces `hmac == HMAC(secret, body)` while `shop` is read from a separate, unauthenticated header. Since the same `api_secret_key` is shared by the app across all of its installed shops, an unprivileged internet user who has installed the target app on any shop they control can capture a genuine webhook delivery (valid body + valid HMAC) and resend it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim merchant's domain. `Registry.process` will validate successfully (the HMAC only covers the body) and hand the handler a `WebhookMetadata` claiming to be from the victim shop: [5](#0-4) 

Any host application that uses `data.shop` to select the tenant record to update (the documented and expected usage pattern) will apply the attacker-controlled body under the wrong tenant.

### Impact Explanation
This breaks the tenant boundary the webhook HMAC is supposed to enforce: an attacker who legitimately controls one shop's webhook stream can inject/replay events attributed to a different merchant's shop, corrupting or forging data on the victim tenant (cross-tenant access), without ever needing the app's `api_secret_key`, an access token, or any privileged credentials — only the ability to install the app on their own store and send HTTP requests to the app's public webhook endpoint.

### Likelihood Explanation
Likelihood is realistic for any publicly-installable app: obtaining a legitimate webhook delivery only requires installing the app (a normal, unprivileged action), and forging the `shop-domain` header on a replayed HTTP request requires no special access. The HMAC validation as implemented cannot detect the header substitution because it never covers the `shop` field.

### Recommendation
Include the shop domain (and ideally the webhook id / topic / api-version) inside the value covered by the HMAC verification — either by requiring the host app to independently validate that `request.shop` corresponds to a shop with an active app installation before trusting it, or by having `Request#to_signable_string` incorporate the shop header alongside the body so that tampering with `shop-domain` invalidates the signature. At minimum, document prominently that `request.shop` is unauthenticated with respect to the HMAC and must be cross-checked by the consuming application against its own installed-shop records.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, obtaining a legitimate webhook delivery: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, header `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the identical body `B` and identical HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Webhooks::Request.new` accepts the headers (only checks presence, not shop-binding): [6](#0-5) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the HMAC still matches `HMAC(secret, B)`: [7](#0-6) 
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and processes the attacker's body `B` as belonging to the victim's tenant.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
