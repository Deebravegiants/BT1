### Title
Webhook HMAC does not bind `shop-domain` header, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates only the raw request body via HMAC and never authenticates the `shop-domain` header, so an attacker who possesses one validly-signed `raw_body`+`hmac` pair from their own shop install can replay it against the app's public webhook endpoint with an arbitrary `shop-domain` header value. The handler receives `data.shop` equal to the attacker-chosen value while `HmacValidator.validate` still returns `true`, giving the attacker full control over which tenant the webhook body is attributed to.

### Finding Description
The binding that must hold is: `shop authenticated by HMAC == shop the handler acts on (request.shop)`. Tracing the code shows this binding is broken by construction.

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`request.shop` is read straight from the unsigned `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against anything cryptographically bound: [2](#0-1) 

`Utils::HmacValidator.validate_signature` computes the HMAC purely over `verifiable_query.to_signable_string` (i.e., `@raw_body`), and compares it to the received `hmac` header value — the shop-domain header plays no role in the signature: [3](#0-2) 

`Registry.process` calls `HmacValidator.validate(request)` (validates body+hmac only), then immediately forwards `request.shop` (the unauthenticated header) to the handler with no shop sanitization/binding check: [4](#0-3) 

Attack flow: the attacker installs the app on their own development shop (a normal, unprivileged action), receives a real webhook (any topic) with a legitimately signed `raw_body` + `x-shopify-hmac-sha256`, captures both, then POSTs directly to the app's public webhook URL setting `shop-domain` (or `x-shopify-shop-domain`) to any victim shop domain string of their choosing while keeping the same `raw_body`/`hmac`. `HmacValidator.validate` still returns `true` because it only checks the raw body against the secret; `request.shop` now returns the attacker-chosen victim string. The handler's `WebhookMetadata.shop` is populated with that spoofed value: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))`. No component in the gem (`Context.setup?`, `ShopValidator.sanitize!`, etc.) is invoked in this path to reconcile the header shop against anything authenticated — `ShopValidator` is not called anywhere in `Registry.process`.

### Impact Explanation
Any host app that trusts `data.shop` from the webhook handler as the tenant identifier for shop-scoped work (e.g., looking up the shop's session/access token, writing tenant data, triggering shop-specific side effects) can be made to act on an attacker-chosen shop identifier using a body that only reflects the attacker's own data. This is a cross-tenant / authentication-bypass class issue: the party actually authenticated (the raw body's signer, i.e., the attacker's own installed shop) diverges from the party the code believes it is acting for (whatever shop string the attacker puts in the header). It is fully repeatable — the attacker can replay any number of captured signed bodies against any victim shop-domain string they choose, for as long as `api_secret_key` doesn't rotate.

### Likelihood Explanation
Preconditions are trivial and match "unprivileged attacker" capabilities exactly: create/install on an attacker-owned development shop (a mandatory, self-service Shopify capability), register at least one webhook topic, capture one real signed callback, then issue a direct HTTP POST to the app's public webhook endpoint with a modified `shop-domain` header. No secrets, tokens, or elevated access are required. This is inherent to how the gem's own `Request`/`HmacValidator`/`Registry.process` are wired, not an app misconfiguration.

### Recommendation
Bind the `shop` to something authenticated: either include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) in the signed content that `to_signable_string` covers (this would require Shopify to change what's HMAC'd, which the app doesn't control), or — more practically within this gem — require host apps to reconcile `request.shop` against a shop known to be legitimately registered/installed (e.g., verify the shop has an active, previously-established session/webhook registration) before dispatching to the handler, and run the shop value through `Utils::ShopValidator.sanitize!` at minimum to reject malformed/non-Shopify domains. Document prominently that `request.shop` is NOT authenticated by the HMAC and must not be trusted as a tenant identifier without additional verification.

### Proof of Concept
```ruby
# test/webhooks/registry_shop_spoof_test.rb
require_relative "../test_helper"

module ShopifyAPITest
  module Webhooks
    class RegistryShopSpoofTest < Test::Unit::TestCase
      def test_hmac_valid_but_shop_header_is_unauthenticated_and_attacker_controlled
        raw_body = '{"id":1}'
        hmac = OpenSSL::HMAC.digest(
          OpenSSL::Digest.new("sha256"),
          ShopifyAPI::Context.api_secret_key,
          raw_body,
        )
        signed_hmac_header = Base64.encode64(hmac)

        # Attacker's own shop legitimately received this signed body+hmac.
        attacker_headers = {
          "x-shopify-topic" => "orders/create",
          "x-shopify-hmac-sha256" => signed_hmac_header,
          "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
        }
        attacker_request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: attacker_headers)
        assert(ShopifyAPI::Utils::HmacValidator.validate(attacker_request))
        assert_equal("attacker-shop.myshopify.com", attacker_request.shop)

        # Attacker replays the SAME raw_body+hmac but swaps shop-domain to a victim shop.
        spoofed_headers = attacker_headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")
        spoofed_request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: spoofed_headers)

        # HMAC validation still passes: shop is not covered by the signature.
        assert(ShopifyAPI::Utils::HmacValidator.validate(spoofed_request))
        # But the shop acted on is now attacker-chosen, not the shop that produced the signed body.
        assert_equal("victim-shop.myshopify.com", spoofed_request.shop)

        handled_shop = nil
        handler = TestHelpers::FakeWebhookHandler.new(lambda { |data| handled_shop = data.shop })
        ShopifyAPI::Webhooks::Registry.add_registration(
          topic: "orders/create", path: "path", delivery_method: :http, handler: handler,
        )

        ShopifyAPI::Webhooks::Registry.process(spoofed_request)

        # The handler processed the attacker's body under the victim's shop identity.
        assert_equal("victim-shop.myshopify.com", handled_shop)
      end
    end
  end
end
```
