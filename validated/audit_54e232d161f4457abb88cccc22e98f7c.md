This is a confirmed access-control gap in the Tron variant of `IntentGatewayV2`, which lacks the relayer-authorization gate that the mainline `ExtrinsicIntents.sol`/`IntentGatewayV2` contract enforces on every governance-carrying `onAccept` action.

### Title
Missing relayer authorization gate in Tron `IntentGatewayV2.onAccept` allows any relayer to forge governance actions (NewDeployment/UpdateParams/SweepDust) and escrow releases - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The mainline EVM intents implementation (`ExtrinsicIntents.sol`) enforces `_checkRelayer(incoming.relayer)` as the very first statement of `onAccept`, before the request body's discriminator byte is even read [1](#0-0) . This ensures that once a relayer is configured, only that authorized relayer's proof-delivered messages can reach any privileged branch (escrow redemption, `NewDeployment`, `UpdateParams`, `SweepDust`, `Execute`/upgrade). Foundry tests explicitly confirm "the gate runs before the body is decoded, so every kind is covered" [2](#0-1) .

The Tron port of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, has no such relayer field, no `_checkRelayer`/`_relayer` state, and no call to any relayer-authorization function anywhere in the file. Its `onAccept` only enforces `onlyHost` and then dispatches purely on the message's `RequestKind` and `source` checks [3](#0-2) .

### Finding Description
`EvmHost.dispatchIncoming`/`HandlerV2` deliver an incoming ISMP message to `onAccept` along with the `relayer` address that *submitted the proof to the handler* — this is untrusted, attacker-controlled input (any address can call the handler and pay gas to relay any correctly-proven message) [4](#0-3) . The documented security model of Hyperbridge's intent-gateway apps is that once a gateway is armed with an authorized relayer, `onAccept`/`onGetResponse` must reject any other relayer *before* interpreting the body, precisely so an unauthorized submitter cannot race to deliver forged or manipulated cross-chain governance/escrow messages [5](#0-4) .

`ExtrinsicIntents._checkRelayer` implements this: "Once a relayer is set, rejects deliveries from anyone else before the body is read... While unset, every delivery passes" [6](#0-5) .

The Tron `IntentGatewayV2.onAccept` omits this gate entirely: it reads `RequestKind` from `incoming.request.body[0]` unconditionally, then for `RedeemEscrow`/`RefundEscrow` only checks `authenticate()` (source-instance check, not relayer) [7](#0-6) , and for `NewDeployment`/`UpdateParams`/`SweepDust` only checks that `request.source == hyperbridge` [8](#0-7) . Neither check constrains *who submitted the proof* (`incoming.relayer`) — this is the missing dimension of authorization. This is directly analogous to the OpenCMS bug class: a privileged/administrative code path (`NewDeployment`, `UpdateParams`, `SweepDust` — cross-chain governance actions equivalent to "admin functions") is reachable by any unprivileged actor (any relayer) who can supply a syntactically valid, correctly-sourced message, because the function-level access-control check that should gate the action based on the caller's identity/role is missing, mirroring `admin-main.jsp`'s failure to restrict admin sub-functions reachable via a request parameter.

### Impact Explanation
Since `source == hyperbridge` is a bytes-string comparison the attacker cannot forge on their own (it depends on the request actually originating from the Hyperbridge parachain, verified by the handler's consensus proof), the practical severity centers on the escrow paths and on race/DoS conditions:
- Any relayer (not just the intended/authorized one) can be first to deliver a legitimately-sourced but sensitive governance message (`NewDeployment`, `UpdateParams`, `SweepDust`) or an escrow release (`RedeemEscrow`/`RefundEscrow`), bypassing the intended single-relayer trust model that the rest of the protocol relies on (see the mainline `_checkRelayer` design intent and its tests around `testOnAcceptRejectsUnlistedRelayer` / `testOnAcceptGovernanceRejectsUnlistedRelayer`) [9](#0-8) .
- `SweepDust` sends arbitrary native/token balances to a `beneficiary` decoded from the message body with no relayer check — if the relayer-authorization model is depended on elsewhere in the fee/dust-sweeping trust assumptions, an unauthorized relayer front-running delivery undermines that assumption.
- This breaks parity/consistency guarantees between the mainline and Tron deployments of the same protocol, and removes a defense-in-depth layer explicitly present and tested everywhere else in the codebase, directly matching the CWE-862 (Missing Authorization) / CWE-284 (Improper Access Control) class cited in the report.

### Likelihood Explanation
High reachability: any account that can call `HandlerV2`/deliver a valid ISMP proof to the Tron host can set `incoming.relayer` to itself and reach `onAccept`'s privileged branches with no additional check, requiring no special privilege beyond being able to relay a message — the same "unprivileged, single submitted...relayed proof" access class explicitly in scope.

### Recommendation
Port the `_relayer`/`_checkRelayer` gate from `evm/src/apps/intentsv2/ExtrinsicIntents.sol` (and the pattern used consistently in `HostManager.sol`, `BandwidthManager.sol`, `SimplexPaymaster.sol`) into the Tron `IntentGatewayV2.sol`: add relayer state, a setter reachable only via governance, and invoke the relayer check as the first statement of both `onAccept` and `onGetResponse`, before any `RequestKind` branching or body decoding.

### Proof of Concept
1. Deploy/observe the Tron `IntentGatewayV2` with orders escrowed and a `NewDeployment`/`SweepDust` message legitimately dispatched from Hyperbridge (`source == hyperbridge`).
2. Any address (`attackerRelayer`) submits the proof through the handler such that `HandlerV2` calls `host.dispatchIncoming(request, attackerRelayer)`.
3. `EvmHost.dispatchIncoming` (restricted only to `handler`) calls `IApp.onAccept(IncomingPostRequest(request, attackerRelayer))` [4](#0-3) .
4. Tron `IntentGatewayV2.onAccept` accepts the delivery from `attackerRelayer` with no relayer check, decodes `RequestKind`, and executes `NewDeployment`/`UpdateParams`/`SweepDust`/escrow-release logic exactly as if the designated/authorized relayer had delivered it [10](#0-9) .
5. Compare against the equivalent EVM test `testOnAcceptRejectsUnlistedRelayer`, which shows the mainline contract reverts with `Unauthorized` for exactly this scenario until the correct relayer submits it [11](#0-10)  — the Tron contract has no equivalent test or check, confirming the gap.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            authenticate(incoming.request);
            WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
            return withdraw(body, kind == RequestKind.RefundEscrow);
        }

        // only hyperbridge is permitted to perfom these actions
        if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
        if (kind == RequestKind.NewDeployment) {
            NewDeployment memory body = abi.decode(incoming.request.body[1:], (NewDeployment));
            _instances[keccak256(body.stateMachineId)] = body.gateway;

            emit NewDeploymentAdded({stateMachineId: body.stateMachineId, gateway: body.gateway});
        } else if (kind == RequestKind.UpdateParams) {
            // Decode the body which includes optional destination-specific protocol fee updates
            ParamsUpdate memory update = abi.decode(incoming.request.body[1:], (ParamsUpdate));
            emit ParamsUpdated({previous: _params, current: update.params});
            _params = update.params;

            // Update destination-specific protocol fees if provided
            for (uint256 i; i < update.destinationFees.length;) {
                bytes32 stateMachineId = update.destinationFees[i].stateMachineId;
                uint256 feeBps = update.destinationFees[i].destinationFeeBps;
                _destinationProtocolFees[stateMachineId] = feeBps;

                unchecked {
                    ++i;
                }
                emit DestinationProtocolFeeUpdated(stateMachineId, feeBps);
            }
        } else if (kind == RequestKind.SweepDust) {
            SweepDust memory req = abi.decode(incoming.request.body[1:], (SweepDust));

            uint256 outputsLen = req.outputs.length;
            for (uint256 i; i < outputsLen;) {
                TokenInfo memory info = req.outputs[i];
                address token = address(uint160(uint256(info.token)));
                uint256 amount = info.amount;

                if (token == address(0)) {
                    (bool sent,) = req.beneficiary.call{value: amount}("");
                    if (!sent) revert InsufficientNativeToken();
                } else {
                    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, req.beneficiary, amount));
                    if (!success) revert TransferFailed();
                }
                unchecked {
                    ++i;
                }
                emit DustSwept(token, amount, req.beneficiary);
            }
        }
    }
