## Analog Found

### Title
Precision Truncation in `convert_to_balance` Causes Silent Loss of Bridged Funds for Low-Precision Destination Assets - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
The `hyper-fungible-token` pallet's `convert_to_balance` function truncates cross-chain token amounts via integer division without any decimals validation or minimum-amount check, mirroring the `USSDRebalancer` bug class: small-but-legitimate amounts round down to zero, and the pallet proceeds to mint/transfer that zero amount to the beneficiary even though the source chain has already burned or escrowed the user's real, non-zero tokens.

### Finding Description
`convert_to_balance` converts an incoming ERC20 (source-chain) `U256` amount into the local balance type by dividing by `10^(erc_decimals - local_decimals)`: [1](#0-0) 

This is called from `on_accept` (and identically from `on_timeout` for refunds) in `module.rs`, immediately followed by an unconditional mint/transfer of the resulting `amount` to the beneficiary with no zero-amount or dust guard: [2](#0-1) 

When the local asset has fewer decimals than the source chain's ERC20 (e.g. a local asset with 6 decimals receiving a message from an 18-decimal ERC20), any incoming raw amount smaller than `10^(erc_decimals - local_decimals)` (e.g. below `1e12` wei for an 18→6 decimals pair) integer-divides to `0`. This is exactly the same failure mode as the `USSDRebalancer` bug: a legitimate non-zero value is silently discarded by truncating division, and the code proceeds as if the computed (zero) result were correct, rather than reverting or accounting for the dust.

Critically, this is reachable from the user-facing `send()` extrinsic on the source chain, which performs the corresponding burn/escrow via `convert_to_erc20` (multiplication, no truncation issue there) before dispatching the cross-chain message: [3](#0-2) 

So a user can burn/escrow a real (small) amount of the local asset on the source chain, dispatch the ISMP request, and have the destination chain's `on_accept` mint/transfer `0` tokens to the beneficiary due to the truncation — a straightforward path to permanent loss of user funds with a single unprivileged cross-chain `send()`.

### Impact Explanation
Any user bridging a small amount between a higher-decimals asset (e.g., 18-decimal token) and a chain/asset pair configured with fewer decimals (e.g., 6-decimal local asset) can have their tokens burned/escrowed on the source side while receiving nothing on the destination side. This is a direct, unrecoverable loss of user funds (High severity), analogous to the reported collateral-sale truncation bug's core defect: an integer-division-based unit conversion that silently degrades to zero without any safeguard, and the caller code trusts the computed value unconditionally.

### Likelihood Explanation
Likelihood is high in practice for any asset pair where `erc_decimals - local_decimals` is large (e.g. 12+, common for USDC/USDT-style 6-decimal locals bridged against 18-decimal EVM ERC20 representations) and a user sends a small amount (dust, fee remainders, or accidental small transfers) — no configuration guard prevents this, and no minimum-transfer-amount enforcement exists in `send()`.

### Recommendation
- Add an explicit check in `convert_to_balance` (or its callers) that rejects/reverts when the computed local `amount` is `0` for a non-zero input `value`, rather than silently minting/transferring zero.
- Alternatively, enforce a minimum bridgeable amount on the `send()` path (e.g., in `lib.rs`'s `send` extrinsic) proportional to the decimals delta so that any dispatched message is guaranteed to resolve to a non-zero destination amount.
- Consider rounding/remainder handling (e.g., refuse fractional dust below one destination unit) instead of pure truncation.

### Proof of Concept
1. Configure `hyper-fungible-token` with a local asset `X` having 6 decimals, and register its EVM counterpart contract's `Precisions` entry for the destination chain as `erc_decimals = 18` (a plausible real-world setup, e.g., local 6-decimal stablecoin ↔ 18-decimal wrapped ERC20).
2. On the EVM side, a user (or the pallet's own `send()`, symmetric logic) triggers a cross-chain transfer with `message.amount` set to e.g. `500_000_000_000` (0.5 * 1e12, i.e. less than `1e12 = 10^(18-6)`), a legitimate non-zero amount of the 18-decimal ERC20.
3. Destination pallet's `on_accept` calls `convert_to_balance(value=5e11, erc_decimals=18, local_decimals=6)`, computing `5e11 / 10^12 = 0` (integer division truncates).
4. `mint_into`/`transfer` is called with `amount = 0`; the beneficiary receives nothing, while the source chain already burned/escrowed the corresponding real value. Funds are permanently lost with no error, revert, or event indicating failure — only a `TokenReceived` event with `amount: 0`.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
