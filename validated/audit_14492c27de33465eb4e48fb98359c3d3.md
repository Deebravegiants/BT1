### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw HTTP body when verifying a webhook's HMAC, while `shop`, `topic`, `webhook_id`, and `api_version` come from unauthenticated HTTP headers and are trusted directly by `Registry.process`. This is the same class of bug as the analog report: a value that is *used* by the application (`shop`) is not part of the data that is cryptographically bound by the signature check (`hmac`), so the binding `verified(shop) == acted_upon(shop)` does not hold.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

All the other webhook identity fields are pulled straight from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which only checks `to_signable_string` (i.e. the body) against the secret: [3](#0-2) 

Immediately after that check passes, `Registry.process` trusts `request.topic` to select the handler and `request.shop` to build `WebhookMetadata`, both taken from headers that were never included in the signed bytes: [4](#0-3) 

Because the HMAC secret (`Context.api_secret_key`) is shared by the app across **all** installed shops, any shop that has installed the app can legitimately capture a valid `(body, hmac)` pair for its own webhook traffic (e.g. by editing its own store data to control the body of a `products/update`, or by simply calling its own confirmed webhook endpoint's request log). The attacker can then replay that exact body and HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop, and optionally the `x-shopify-topic`/`x-shopify-webhook-id`/`x-shopify-api-version` headers. `HmacValidator.validate` still succeeds (it only checked the body), and `Registry.process` will invoke the registered handler with `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
This breaks the tenant isolation guarantee the HMAC check is supposed to provide: `verified_shop == acted_upon_shop` no longer holds. An app's webhook handler (which typically updates or redacts per-shop data, e.g. `customers/redact`, `shop/redact`, `orders/*`, `products/*`) can be tricked into processing attacker-supplied payloads under an arbitrary victim shop identity, i.e. cross-tenant data injection/spoofing — matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation requires only that the attacker control (or previously install on) any shop using the target app to obtain one valid `(body, hmac)` pair — no access to `api_secret_key`, access tokens, or the victim's credentials is needed. This is a realistic step for any unprivileged app-installing user and does not depend on host-application misuse of documented APIs; the gem itself does not bind these header fields to the signature.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the bytes that are HMAC-verified (or otherwise cryptographically bind them to the signed payload), so that tampering with any of these header values invalidates the signature. At minimum, `to_signable_string` should incorporate the shop domain and topic, matching how `AuthQuery#to_signable_string` binds `shop`/`host` into its signable string.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (or otherwise gets one legitimate webhook delivery for a topic the app handles).
2. Attacker captures the `raw_body` and `X-Shopify-Hmac-Sha256` header of that legitimate webhook request (or crafts body content on their own store so its outbound webhook body is attacker-chosen).
3. Attacker sends a forged HTTP POST to the app's webhook endpoint with:
   - Body = the same `raw_body`
   - `X-Shopify-Hmac-Sha256` = the same valid HMAC
   - `X-Shopify-Shop-Domain` = `victim-shop.myshopify.com`
   - `X-Shopify-Topic` = any handled topic (e.g. `customers/redact`)
4. `Utils::HmacValidator.validate(request)` passes because only the body was checked (`lib/shopify_api/webhooks/request.rb` `to_signable_string`, `lib/shopify_api/utils/hmac_validator.rb` `validate_signature`).
5. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "customers/redact", body: attacker_body, ...)`, causing the app to act on data attributed to the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
