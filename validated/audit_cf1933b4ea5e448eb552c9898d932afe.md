Confirmed. This is a genuine analog to the missing-`chainID` bug class: a value that is *acted upon* (the `shop` tenant identifier) is not covered by the cryptographic authentication (`hmac`) that is supposed to bind the message.

### Title
Webhook `shop` (tenant) field is not covered by HMAC authentication, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable payload from the raw HTTP body only, while the `shop` (and `topic`/`webhook_id`) values are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC against the body, then trusts `request.shop` to build the `WebhookMetadata` passed to the host application's handler. Exactly like the ERC20Permit bug (where `chainID` was omitted from the signed struct, letting a signature be replayed on a different chain), the tenant-identifying field here is omitted from the signed struct, letting a validly-signed webhook body be replayed under a different tenant identity.

### Finding Description
`to_signable_string` in `Request` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, and `webhook_id` are read straight from HTTP headers without being part of the signed material: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `verifiable_query.to_signable_string` (i.e., the body) against the HMAC: [3](#0-2) 

`Registry.process` validates the HMAC over the body and, once that passes, unconditionally trusts `request.shop` — the identity binding claimed by an unauthenticated header — to construct the metadata handed to the app's webhook handler, which apps use to select the tenant/session to act on: [4](#0-3) 

The equality the gem is supposed to guarantee is: `shop authenticated by HMAC == shop acted on by the handler`. Because the HMAC secret (`api_secret_key`, i.e. `client_secret`) is the same for every shop that installs a given app, and the `shop-domain` header is not part of the signed bytes, an attacker who installs the app on their own (attacker-controlled) shop can obtain a legitimately HMAC-signed webhook (body + valid signature) for their own shop, then resend the exact same body/signature pair to the app's webhook endpoint with the `shopify-shop-domain` (or `x-shopify-shop-domain`) header changed to a victim shop. `HmacValidator.validate` still returns `true` because it only checks the body bytes, and `Registry.process` passes the attacker-chosen `shop` value straight through to the handler.

### Impact Explanation
This breaks the tenant boundary between shops using the same app (cross-tenant access), matching the Critical impact bucket ("cross-tenant access"). Any host application that uses `WebhookMetadata#shop` from `ShopifyAPI::Webhooks::Registry.process` to select which shop/session/data to update (the documented and intended use, per `docs/usage/webhooks.md`) can be tricked into applying a webhook payload crafted (or replayed) by one tenant against another tenant's data, without needing that tenant's access token or credentials.

### Likelihood Explanation
Any developer/merchant who can install the app on their own store already possesses a channel to generate arbitrarily-shaped, validly-HMAC-signed bodies (Shopify will sign whatever payload the event produces, and for many topics the body content is attacker-influenceable, e.g. metafields, product data, order notes). Constructing the forged request only requires re-issuing the same body/HMAC with a different header value, which any HTTP client can do — no secrets, tokens, or advanced capabilities are required beyond controlling one shop that has the app installed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed material used for HMAC verification, or otherwise cryptographically/authoritatively verify that the `shop-domain` header corresponds to the shop the webhook subscription was registered for (e.g., cross-check against a shop-specific webhook id/secret recorded at registration time, analogous to including `chainID` in the signed struct to prevent cross-context replay). Document that consuming applications must not use the `shop` header value as a trust boundary unless this binding is fixed within the gem.

### Proof of Concept
```ruby
# Attacker owns "attacker.myshopify.com" and has the app installed there.
# Shopify sends a legitimately signed webhook for the attacker's own shop:
body = '{"id": 1, "note": "hijack payload"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)

# Attacker replays the same body+hmac but swaps the shop-domain header to the victim:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) returns true (body/hmac match)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# The host app now believes this payload legitimately came from "victim-shop.myshopify.com".
```
