### Analysis

The premise assumes the intents.near contract "only checks the nonce deadline," but that assumption is unsupported and contradicted by the SDK's own design intent. `defaultIntentPayloadFactory` deliberately sets the nonce's embedded deadline to `deadline + DEFAULT_NONCE_DEADLINE_OFFSET_MS` (60s), separate from the intent payload's own `deadline` field, which is set independently and is the value actually enforced by the contract's execution-time expiry check. [1](#0-0) 

The CHANGELOG entry for this exact behavior explicitly documents the purpose of the offset: it exists "so solvers can reliably invalidate soon-to-expire quotas" — i.e., to give a grace window for nonce bookkeeping/invalidation, not to extend the executable lifetime of a signed intent. [2](#0-1) 

Both `IntentPayloadBuilder.buildWithSalt` and `invalidateNonces` follow this same separation: the intent's `deadline` field (checked by the contract at execution time) is set independently from the nonce's internal deadline (used by the contract for nonce garbage-collection/storage cleanup after the point at which the corresponding intent could no longer be valid). [3](#0-2) [4](#0-3) 

The claimed exploit requires that the intents.near contract's own deadline/nonce verification logic be broken — specifically that it fails to reject a payload whose own `deadline` has passed, relying instead only on the nonce's later embedded deadline. That is a claim about the on-chain `intents.near` contract's signature/deadline verification, which is explicitly out of scope per the rules ("defects inside intents.near, bridge contracts... with no path through this repo"). Nothing in this SDK repository causes divergence between the signed `deadline` field and what gets enforced; the SDK correctly signs both fields, and `verifying_contract` is always taken from `envConfig.contractID`, preventing cross-contract replay from the SDK side. [5](#0-4) 

Additionally, `invalidateNonces` produces empty-intent (`intents: []`) payloads — there is no fund movement to replay even if the underlying nonce/deadline mechanics were somehow abused, so the "funds executed twice" impact does not apply to this code path regardless. [6](#0-5)
