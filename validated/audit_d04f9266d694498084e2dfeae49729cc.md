### Title
Webhook `shop-domain` header is trusted by handlers but excluded from HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `api_version`, and `webhook_id` are read from unauthenticated HTTP headers that are never included in the HMAC-signed content. `Registry.process` validates the HMAC and then forwards `request.shop` directly to the app's `WebhookHandler` as trusted tenant identity, without any binding between the signed bytes and the shop claim.

### Finding Description
`ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` compute/verify the signature purely from `@raw_body`: [1](#0-0) 

Meanwhile `#shop`, `#topic`, `#api_version`, and `#webhook_id` are pulled from headers (`shopify-shop-domain`/`x-shopify-shop-domain`, etc.) that are not part of `to_signable_string`: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` against the HMAC — for a `Request`, that means only the body bytes are authenticated, not the shop header: [3](#0-2) 

`Registry.process` then passes the *unauthenticated* `request.shop` straight into `WebhookMetadata`, which is delivered to the host app's handler as the trusted tenant identifier: [4](#0-3) [5](#0-4) 

The gem's own documentation confirms host apps are expected to trust `data.shop` as the shop the webhook body belongs to, using it to key job queues, lookups, and enqueueing of shop-scoped work: [6](#0-5) 

**Binding broken (as an equality):** the gem asserts `shop_header == shop_that_produced_the_signed_body`, but the HMAC only proves `raw_body == HMAC(raw_body, api_secret_key)`; it proves nothing about which shop header accompanied that body. Any request whose body+HMAC pair is valid for the app's shared `api_secret_key` (i.e., a webhook genuinely delivered for the attacker's own shop, which the attacker fully controls and can trigger and capture) will pass `HmacValidator.validate` regardless of which `shop-domain` header value is attached to it, because that header is never part of the signed bytes.

### Impact Explanation
Because the app's `api_secret_key` is shared across all installed shops, an unprivileged merchant (attacker) can:
1. Install the app on their own shop and trigger a webhook event (e.g. `orders/create`) they fully control the content of, capturing the exact `raw_body` and its valid `X-Shopify-Hmac-Sha256` value that Shopify computed for their own tenant.
2. Replay that identical `raw_body` + HMAC pair to the app's webhook endpoint, but substitute the `X-Shopify-Shop-Domain` header with a victim shop's domain.
3. `HmacValidator.validate` still returns `true` (it never looked at the header), so `Registry.process` calls the host handler with `data.shop == "victim-shop.myshopify.com"` while `data.body` is attacker-controlled content.

This crosses the tenant boundary: data attributed to and processed under the victim's shop context originates from, and is fully controlled by, the attacker — a cross-tenant integrity/confidentiality violation of exactly the kind called out in scope (cross-tenant access via an identity binding that is checked/verified on one side but not enforced against the field actually consumed).

### Likelihood Explanation
The attacker needs no credentials beyond a free/trial Shopify shop that installs the target app (an unprivileged internet user action), and no access to `api_secret_key`, TLS interception, or social engineering — they merely observe a webhook legitimately sent to their own endpoint (which they control) and replay it with one header changed. This is a low-effort, easily automatable attack once identified.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the signed/verified content, or otherwise cryptographically bind them to the request (e.g., have `to_signable_string` incorporate the shop header, or require callers to independently verify the `shop-domain` header against a shop they already have an active session/webhook registration for) before trusting `request.shop` in `Registry.process`.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and installs the target app.
# Shopify sends a genuine webhook for the attacker's own shop:
raw_body = '{"id":1,"note":"malicious payload"}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, raw_body)
)

# Attacker replays the exact same body/HMAC to the app's webhook endpoint,
# but swaps the shop header to a victim shop they do not control:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,           # still valid! only signs raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, unauthenticated
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (body/HMAC pair is genuine)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker_body, ...))
```
