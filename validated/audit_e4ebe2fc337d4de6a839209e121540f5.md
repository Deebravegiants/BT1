### Title
Webhook shop-domain identity not covered by HMAC signature enables cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC verification performed in `Utils::HmacValidator.validate` never covers the `shopify-shop-domain` header. This is the same class of bug as the ERC1155 report: a value that is trusted and acted upon (`shop`) is not the value that was actually authenticated (the raw body bytes only).

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 
`shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, but `to_signable_string` returns only `@raw_body`, excluding `shop`, `topic`, and `webhook_id` entirely from the signed content.

`Registry.process` validates the request purely via this HMAC check and then dispatches the handler using the unauthenticated `request.shop` and `request.topic` values: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature strictly over `verifiable_query.to_signable_string`: [3](#0-2) 

So the equality that should hold is: `shop_used_by_handler == shop_covered_by_hmac`. In fact, `shop_used_by_handler` comes from an HTTP header, while `shop_covered_by_hmac` is the empty set — the HMAC only authenticates the JSON body bytes, not which shop the body belongs to.

By contrast, the OAuth `AuthQuery#to_signable_string` correctly includes `shop` in the signed parameters: [4](#0-3) 
This confirms `shop` binding into the HMAC is the intended pattern elsewhere in the gem, but it was not carried over to the webhook `Request` class.

### Impact Explanation
Because Shopify computes the webhook HMAC only over the raw body (this is documented Shopify behavior and mirrored faithfully by the gem's `to_signable_string`), any attacker who controls or can trigger a webhook for **their own store** (e.g., a dev/test store they own, or a store where they install the same app) obtains a body + HMAC pair that is valid for that exact body. If the app's handler logic keys any per-tenant behavior off `WebhookMetadata#shop` without independently cross-checking that the shop is a store the app has installed/authorized data for, an attacker can replay that same signed body to the app's webhook endpoint while forging the `shopify-shop-domain` header to name a victim shop. `Utils::HmacValidator.validate` will report success because the signature check never touches the header, and `Registry.process` will hand the forged `shop` straight to the handler as trusted `WebhookMetadata.shop`, resulting in a cross-tenant confused-identity condition (data written/attributed to the wrong tenant, or triggering shop-specific logic — e.g., uninstall/GDPR/order webhooks — against a shop the attacker doesn't control).

This matches the report's "Critical - cross-tenant access" impact category: the shop identity binding that host applications rely on when trusting `WebhookMetadata.shop` is broken at the gem's HMAC-verification layer.

### Likelihood Explanation
Exploitation requires the attacker to be able to generate at least one legitimately-HMAC-signed webhook body (trivial: install the app on any store they control, including a free/dev store, and observe/trigger a webhook), and requires the host app to treat `WebhookMetadata.shop` as trustworthy for tenant-scoping without additional verification (e.g., checking the shop is one it has a session/access-token for) — a very common integration pattern since the gem's own documentation and `WebhookMetadata` struct present `shop` as the authenticated origin of the event. No access token, `client_secret`, or privileged credentials are required by the attacker.

### Recommendation
Include the shop domain (and ideally the topic and webhook id) in the signable content checked against the HMAC, or — since Shopify itself does not sign these header values — require `Registry.process`/`WebhookMetadata` callers to independently verify that `request.shop` corresponds to a shop for which the app currently holds a valid session/access token before trusting it for tenant-scoped operations. At minimum, update the documentation for `ShopifyAPI::Webhooks::Registry.process` to explicitly warn that `shop` is unauthenticated header data and must be cross-validated against known installed shops before being used for any tenant-identifying decision.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (a store the attacker owns) and triggers a webhook (e.g., `orders/create`) with a chosen JSON body `B`.
2. Shopify signs `B` and delivers headers including `x-shopify-hmac-sha256: HMAC(secret, B)` and `x-shopify-shop-domain: attacker-shop.myshopify.com` to the app's callback URL.
3. Attacker captures this valid `(B, HMAC)` pair and replays it directly to the same callback URL, but rewrites the header to `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully; `Utils::HmacValidator.validate(request)` returns `true` because `to_signable_string` returns only `B`, unaffected by the header change.
5. `Registry.process(request)` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, causing the host app to act on data mislabeled as belonging to `victim-shop.myshopify.com`.

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
