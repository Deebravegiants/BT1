### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature over the raw request body only, while the `shop`, `topic`, and `webhook_id` values used by `ShopifyAPI::Webhooks::Registry.process` to route and attribute the webhook are read from unsigned HTTP headers. Because a single `api_secret_key` is shared across every shop installed on a multi-tenant app, any merchant who has installed the app can capture one of their own genuine webhook deliveries and replay it with a modified `shop-domain` (and/or `topic`/`webhook-id`) header. The HMAC check still passes (it only re-hashes the unchanged body), so the app processes attacker-controlled body content as if it originated from an arbitrary other shop — breaking the binding between "authenticated payload" and "the shop the payload is attributed to."

### Finding Description
`HmacValidator.validate` verifies authenticity by re-computing the HMAC over `verifiable_query.to_signable_string` and comparing it to the `hmac` field: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

However, `shop`, `topic`, and `webhook_id` — the fields that identify *which tenant* the event belongs to — are pulled straight from HTTP headers that are entirely outside the signed content: [3](#0-2) 

`Registry.process` only checks the HMAC of the body, then immediately trusts `request.shop`/`request.topic`/`request.webhook_id` to dispatch the event to the app's handler: [4](#0-3) 

The equality that should hold is:
`shop attested by the HMAC-signed content == shop the app attributes the event to`

Here that equality is broken: the HMAC only proves `body == HMAC(body, api_secret_key)`; it says nothing about which shop the header claims the event came from. Since `api_secret_key` is a single per-app secret shared by all tenants (not a per-shop secret), any tenant that can produce one valid `(body, hmac)` pair for their own shop can pair that same valid `(body, hmac)` with a different `shop-domain` header value, and the app has no way to detect the substitution.

### Impact Explanation
This is a cross-tenant identity-binding break: a merchant who installed the app on Shop A (an unprivileged, non-privileged tenant with no access to `api_secret_key`, access tokens, or other merchants' data) can cause the app's webhook handler to execute with `data.shop` equal to Shop B while the body content is attacker-controlled (their own genuine webhook body from Shop A, replayed). Depending on what the handler does with `data.shop` (e.g., look up Shop B's session/store record and apply the attacker's body data to it), this can lead to cross-tenant data corruption or unauthorized actions being attributed to/executed against a shop the attacker does not control.

### Likelihood Explanation
Likelihood is realistic in any multi-tenant deployment of this gem: the attacker only needs to be a legitimate but malicious installer of the app on their own shop (i.e., an "unprivileged internet user" relative to other tenants) and the ability to replay an HTTP POST with modified headers to the app's public webhook endpoint — no access token, `api_secret_key`, or TLS interception is required, since the HMAC and body are taken verbatim from a webhook the attacker legitimately received for their own shop.

### Recommendation
Bind the tenant-identifying fields (`shop`, `topic`, `webhook_id`) into the signed content that `HmacValidator` verifies, or independently re-derive/verify the shop identity from data inside the signed body (e.g., cross-check the header's shop domain against a shop identifier embedded in the payload, or maintain a per-shop secret/session lookup keyed by a value that is itself covered by the signature) before dispatching to `handler.handle`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and subscribes to a webhook topic (e.g., `orders/create`).
2. Shopify delivers a legitimate webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid hmac of body>`, and some `raw_body`.
3. Attacker captures this request and replays it to the same endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and/or `x-shopify-topic`), leaving `raw_body` and `x-shopify-hmac-sha256` untouched.
4. `HmacValidator.validate` re-computes the HMAC over the unchanged `raw_body` with the shared `api_secret_key` and it matches, so `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) proceeds and calls the handler with `WebhookMetadata` whose `shop` is `victim-shop.myshopify.com`, even though the payload actually originated from `attacker-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
