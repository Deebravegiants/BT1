Audit Report

## Title
Missing `return` after failed email-claim extraction and after failed session DB insert allows creation of an authenticated session with an empty/incorrect email - (File: core/sessions/oidcauth/oidc.go)

## Summary
In `oidcAuthenticator.handleTokenExchange`, the error branch for the `email` type assertion (lines 226-230) and the error branch for the `oidc_sessions` DB insert (lines 257-260) both write an HTTP error response but omit the `return` statement, letting execution fall through to session creation, cookie-setting, and a `200 OK` success response.

## Finding Description
At [1](#0-0)  the code does `email, ok := claims["email"].(string)`; on failure it logs and calls `c.String(http.StatusInternalServerError, ...)` without `return`. Execution proceeds to role mapping via `IDClaimsToUserRole` and then to session creation at [2](#0-1) , which inserts a row into `oidc_sessions` using the (empty) `email` value. If that `ExecContext` call itself fails, the same missing-`return` pattern repeats. In both cases, execution reaches [3](#0-2) , which audits a "successful" login, sets the session cookie via `ginSession.Set`/`ginSession.Save()`, and responds `200 OK` with `{"success": true}`. `AuthorizedUserWithSession`, used on every subsequent authenticated request, trusts whatever row exists for the session ID at [4](#0-3)  without validating that `user_email` is non-empty, so downstream role-based authorization checks such as those in [5](#0-4)  operate on a session whose creation was flagged as an internal error to the client but not aborted server-side.

I confirmed via direct file read that the code matches the claim exactly — both `if !ok { ... c.String(...) }` and `if err != nil { ... c.String(...) }` blocks at these exact locations lack a trailing `return`, unlike every other error branch in this function which does include `return` after writing an error response.

## Impact Explanation
This is a genuine logic bug that can result in an authenticated session cookie being issued to the client with `200 OK`/`success: true` even though the server has already signaled (via the 500 response body, which is overwritten by the later `c.JSON` call) that email-claim extraction or session persistence failed. In the email-claim-empty case, this creates a session in `oidc_sessions` keyed to `user_email = ""` with a role derived from group claims, which is a form of cross-user identity confusion (multiple failed logins could collapse to the same empty-email identity) impacting per-user audit trails and any code path that looks up users by email. In the DB-insert-failure case, the client receives a working session cookie for a session ID that may have no corresponding row (or a stale one), an integrity issue in the authentication state. These map to the in-scope "node API authentication or role bypass" / "cross-user response corruption" impact categories.

## Likelihood Explanation
The email-claim branch requires only that the configured OIDC provider's ID token/UserInfo response is missing or mistypes the `email` field — reachable by any client completing the standard, unprivileged OIDC login flow when using such a provider, or by an attacker able to influence/spoof provider responses in a way that fails the type assertion while still passing the earlier `ExtractIDClaimValues`/role-claim checks. The DB-insert-failure branch requires an ordinary transient DB error, not attacker-controlled input, making it less directly attacker-triggerable but still a real defect that can be hit under load or connectivity issues, and it is part of the same code-quality/security-relevant flaw (unchecked error not aborting execution).

## Recommendation
Add `return` immediately after:
- `c.String(http.StatusInternalServerError, "Failed to get email from claims")` (line 229-230).
- `c.String(http.StatusInternalServerError, "Error creating session")` (line 259-260).

Additionally, validate that `email` is non-empty before proceeding to session creation, and ensure the audit log call only fires after a confirmed successful `oidc_sessions` insert.

## Proof of Concept
1. Configure or point the authenticator at an OIDC provider whose token/claims response omits the `email` field but includes group claims that satisfy `IDClaimsToUserRole`.
2. Complete the OAuth2 authorization code flow and `POST` the resulting code/state to the token-exchange endpoint served by `handleTokenExchange`.
3. Observe: despite the failed `claims["email"].(string)` assertion and the `500` body written via `c.String`, the handler continues, inserts an `oidc_sessions` row with `user_email = ''` and the role from group claims, sets the session cookie, and finally responds `200 OK` with `{"success": true}` — a Go handler/integration test asserting the final HTTP status/body and inspecting the `oidc_sessions` table row after posting a claims payload without `email` would confirm this deterministically.
4. Separately, inject a DB error from `oi.ds.ExecContext` during a valid login (e.g., via a mock `DataSource` in a unit test) and confirm the same `200 OK`+cookie result is returned even though no row was inserted.

// AuthorizedUserWithSession will return the API user associated with the Session ID if it
// exists and hasn't expired
func (oi *oidcAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (clsessions.User, error) {
	if len(sessionID) == 0 {
		return clsessions.User{}, errors.New("session ID cannot be empty")
	}
	var foundUser clsessions.User
	err := sqlutil.TransactDataSource(ctx, oi.ds, nil, func(tx sqlutil.DataSource) error {
		// Query the oidc_sessions table for given session ID, user role and email are saved after the id claims is provided and validated
		var foundSession struct {
			UserEmail string
			UserRole  clsessions.UserRole
			Valid     bool
		}
		if err := tx.GetContext(ctx, &foundSession,
			"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM oidc_sessions WHERE id = $1",
			sessionID, oi.config.SessionTimeout().Duration(),
		); err != nil {
			if errors.Is(err, sql.ErrNoRows) {
				return clsessions.ErrUserSessionExpired
			}
			return err
		}
		if !foundSession.Valid {
			// Sessions expired, purge
			return clsessions.ErrUserSessionExpired
		}
		foundUser = clsessions.User{
			Email: foundSession.UserEmail,
			Role:  foundSession.UserRole,
		}
		return nil
	})
	if err != nil {
		if errors.Is(err, clsessions.ErrUserSessionExpired) {
			if _, execErr := oi.ds.ExecContext(ctx, "DELETE FROM oidc_sessions WHERE id = $1", sessionID); execErr != nil {
				oi.lggr.Errorf("error purging stale OIDC session: %v", execErr)
			}
		}
		return clsessions.User{}, err
	}
	return foundUser, nil
}

// Authenticates the user from the session cookie and asserts at least 'run' role.
func authenticateUserCanRun(ctx context.Context) error {
	session, ok := auth.GetGQLAuthenticatedSession(ctx)
	if !ok {
		return unauthorizedError{}
	}
	if session.User.Role == sessions.UserRoleView {
		return RoleNotPermittedError{session.User.Role}
	}
	return nil
}

// Authenticates the user from the session cookie and asserts at least 'edit' role.
func authenticateUserCanEdit(ctx context.Context) error {
	session, ok := auth.GetGQLAuthenticatedSession(ctx)
	if !ok {
		return unauthorizedError{}
	}
	switch session.User.Role {
	case sessions.UserRoleView, sessions.UserRoleRun:
		return RoleNotPermittedError{session.User.Role}
	default:
	}
	return nil
}

// Authenticates the user from the session cookie and asserts has 'admin' role
func authenticateUserIsAdmin(ctx context.Context) error {
	session, ok := auth.GetGQLAuthenticatedSession(ctx)
	if !ok {
		return unauthorizedError{}
	}
	if session.User.Role != sessions.UserRoleAdmin {
		return RoleNotPermittedError{session.User.Role}
	}
	return nil
}
