### Title
Webhook `shop` (tenant) identity is trusted from an unauthenticated header while the HMAC only covers the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `api_version`, and `webhook_id` fields entirely from HTTP headers, but `to_signable_string` — the value that the HMAC is computed over — returns only `@raw_body`. `Registry.process` validates the HMAC and then dispatches to the app's handler using `request.shop` as the tenant identifier, without that value ever having been bound to the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

The `shop` accessor is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no relation to the HMAC-signed bytes: [2](#0-1) 

`Registry.process` validates only the HMAC over the signable string (the body) and then builds `WebhookMetadata` using `request.shop` taken from the header, which is passed unchanged to the app's handler as the tenant identifier for the event: [3](#0-2) 

`WebhookMetadata.shop` is a plain `String` const with no further validation, and is exactly what handler implementations use to know which merchant/shop the event belongs to: [4](#0-3) 

The binding that should hold is: `shop used to attribute/authorize the webhook event == shop cryptographically bound to the HMAC-verified bytes`. In this gem that equality does not hold — the HMAC only authenticates `@raw_body`; the `shop-domain` header is authenticated by nothing. `HmacValidator.validate_signature` confirms the HMAC covers only `verifiable_query.to_signable_string`: [5](#0-4) 

Because Shopify's own webhook body payloads frequently do not embed the originating shop domain (many topics only include resource IDs, e.g. order/customer IDs, scoped implicitly to the shop that fired the webhook), an attacker who owns/controls their own installed shop can capture one of their own legitimate, correctly-signed webhook deliveries (raw body + `X-Shopify-Hmac-Sha256`) and replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value naming a different merchant. `HmacValidator.validate` will pass, since it only checks the (unchanged) body against the (unchanged) HMAC, and `Registry.process` will hand the forged `shop` to the app's handler as if the event originated from that shop.

### Impact Explanation
This breaks the tenant-identity binding at the boundary the gem's webhook API is supposed to enforce (an unprivileged internet user needs no `access_token`/`client_secret`/API key — only a body+HMAC pair they can legitimately obtain from their own installed instance of the app). Downstream, any host application that trusts `WebhookMetadata#shop` to select/mutate per-tenant state (e.g., to look up or clear that shop's stored access token during a `shop/redact` or `app/uninstalled` webhook, or to record data against a given shop) can be made to act on a shop the attacker does not control — a cross-tenant impact. This falls under the "cross-tenant access" bucket of the rubric.

### Likelihood Explanation
Requires only: (1) attacker installs the app on their own store (a normal, unprivileged action any Shopify merchant can perform) to receive a legitimately HMAC-signed webhook from Shopify, and (2) attacker replays that raw body/HMAC to the app's public webhook endpoint with a substituted `shop-domain` header. No secrets, tokens, or elevated permissions are needed to mount the request against a target app; only the topic's body needing to be shop-domain-agnostic (true for many topics, e.g. compliance/uninstall/generic resource events) is required for the impersonation to be effective.

### Recommendation
Bind the `shop` (and ideally `topic`/`api_version`) to the HMAC-verified material instead of trusting it purely from headers: e.g., include the shop domain header value as part of `to_signable_string` (matching whatever Shopify actually signs) or, at minimum, require host applications/this gem to independently validate that `request.shop` corresponds to a shop with an active installation/session for this app before invoking the handler. If Shopify's real webhook signature genuinely does not cover headers, the gem should document this trust boundary explicitly and encourage handlers to cross-check `shop` against known installed shops before acting, rather than silently treating the header as authenticated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers/receives a webhook for a topic whose body does not embed the shop (e.g. `app/uninstalled` or a generic compliance topic), capturing the raw POST body and its `X-Shopify-Hmac-Sha256` header — both valid and provided by Shopify itself.
2. Attacker replays this exact `{raw_body, hmac}` pair to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body successfully: [6](#0-5) 
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which only recomputes/compares the HMAC of `@raw_body` — unaffected by the header change — so validation succeeds: [7](#0-6) 
5. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)`, where `request.shop == "victim-shop.myshopify.com"`, even though nothing about that value was ever verified by Shopify's signature: [8](#0-7)

```ruby
      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
```

```ruby
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
```
