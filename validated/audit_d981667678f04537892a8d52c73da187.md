### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` from HTTP headers that are never included in the HMAC-signed payload. `Utils::HmacValidator` only verifies the raw request body, so an attacker who can obtain one validly-signed webhook body (e.g., by installing the app on their own free/dev store and capturing the webhook Shopify sends them) can replay that same body while rewriting the `shop-domain`/`topic`/`webhook-id` headers to arbitrary values, and the HMAC check will still pass.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes the HMAC over exactly that signable string: [2](#0-1) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are read straight from attacker-controllable HTTP headers, with no cryptographic binding to the body at all: [3](#0-2) 

`Registry.process` validates only the HMAC of the body, then dispatches to the handler using the unauthenticated `request.shop`/`request.topic`/`request.webhook_id` values as the tenant/topic identity for the callback: [4](#0-3) 

This is the same class of bug as the reported issue: bytes are cryptographically verified (the body), but the identity fields the application actually acts on (`shop`, `topic`) are parsed from a completely different, unverified channel (headers) and trusted anyway. The equality that should hold — "shop bound by the signature" == "shop the handler processes the webhook for" — does not hold, since the signature only proves the body originated from Shopify for *some* registered app/shop pair, not for the specific shop asserted in the header.

### Impact Explanation
Because the API secret key (`client_secret`) is shared by the app across every installing shop, any attacker can:
1. Install the target app on their own (attacker-controlled) shop.
2. Trigger a webhook delivery to capture a validly HMAC-signed request (body + signature).
3. Replay that exact body/HMAC pair to the app's webhook endpoint while swapping the `shopify-shop-domain` header to a victim shop's domain (and/or the `shopify-topic`/`shopify-webhook-id` headers).
4. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` dispatches the handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain.

Any host application logic that trusts `WebhookMetadata#shop` to select which merchant's records to update (a very common integration pattern, e.g., "insert this order data for this shop") can be tricked into writing or acting on data under a different tenant's identity — a cross-tenant access/data-confusion vulnerability rooted entirely in this gem's webhook verification.

### Likelihood Explanation
Any unprivileged internet user can obtain a developer/free Shopify store, install a target app, and capture one legitimately-signed webhook body without needing the app's `client_secret`, an access token, or any other privileged credential. Only network access to the app's webhook endpoint is required afterward, satisfying the "unprivileged internet user" bar.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signable string (as Shopify's own HMAC of the raw payload is meant to be scoped to a specific delivery), or otherwise cryptographically bind the shop/topic to the signed body before `Registry.process` uses them to select the handler and construct `WebhookMetadata`. At minimum, document that consumers of `WebhookMetadata#shop` must independently confirm the shop context (e.g., correlate the webhook with an existing, known-good session/shop record) before using it as a tenant key.

### Proof of Concept
1. App with secret `S` is installed on attacker's own shop `evil.myshopify.com`. Shopify sends a webhook with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(S, B)`.
2. Attacker POSTs the same `B` and same HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...changed shop...})` is constructed; `hmac` is unchanged since it comes from the untouched HMAC header, and `to_signable_string` still returns `B`.
4. `Utils::HmacValidator.validate(request)` returns `true` (body/HMAC pair is valid), and `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, even though Shopify never sent this webhook for `victim.myshopify.com`.
