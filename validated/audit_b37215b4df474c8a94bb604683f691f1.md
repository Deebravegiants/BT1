### Title
Zero-rounded `tokensForLP` at graduation permanently bricks `finalizeGraduation` and freezes curve-raised LT — ([File: packages/contracts/src/Bonding.sol])

### Summary
`_prepareGraduationLiquidity` computes the LP-side token amount for graduation as an integer division that can round down to `0` while the real LT raised (`ltFromPair`) is still positive. That `0` is cached in `pendingGraduation[token]` at phase 1 and replayed verbatim by the permissionless phase-2 `finalizeGraduation`, which feeds it straight into `IUniswapV2Pair.mint`. A first mint on an empty pair with one side equal to `0` computes `liquidity = sqrt(0 * ltFromPair) - MINIMUM_LIQUIDITY`, which is `0 - 1000` and reverts (Solidity 0.8 underflow / V2's `INSUFFICIENT_LIQUIDITY_MINTED`). Since the cached inputs never change, every future call to `finalizeGraduation(token)` reverts identically, permanently trapping the token in `Lifecycle.Graduating` and freezing both the curve-raised LT and the reserved 250M LP tokens.

### Finding Description
`_prepareGraduationLiquidity` in `Bonding.sol` computes: [1](#0-0) 

```
ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
...
tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;
```

`assetReserve` is dominated by the launch-time virtual LT reserve (`VIRTUAL_LIQUIDITY_USD = 3000 ether` worth of LT, recovered via `Pair.k() / Token.TOTAL_SUPPLY()`), while `ltFromPair` is only the *real* LT actually raised by the curve so far. Graduation can fire on the **USD trigger** — `(storedAssetReserve - virtualLtReserve) × exchangeRate ≥ $9K` — the moment real LT raised times the LT's `exchangeRate()` crosses the threshold. Because `exchangeRate()` is an externally-controlled, live-appreciating value on a BounceTech leveraged token (by design, LTs can carry high leverage/appreciation), a token creator can pick (or an existing curve can end up paired with) an LT whose `exchangeRate()` is high enough that the USD threshold is crossed while `ltFromPair` (in LT-wei) is still tiny relative to `assetReserve` (which still includes the large virtual seed). In that case the integer division `(ltFromPair * tokenReserve) / assetReserve` rounds down to `0`, even though `ltFromPair > 0`.

This `(tokensForLP=0, ltFromPair>0)` pair is pinned into `pendingGraduation[token]` at phase 1 (`_enterGraduating`), which is fired inline by any ordinary trader's buy that crosses the threshold — no privilege required: [2](#0-1) 

Phase 2, `finalizeGraduation`, is permissionless and replays the cached values verbatim into `_seedUniswapV2Direct` → `_seedDirectMint` (the empty-pair regime, since the HyperSwap pair has no LP yet): [3](#0-2) [4](#0-3) 

`_seedDirectMint` transfers `tokensForLP` (=0) tokens and `ltFromPair` (>0) LT to the pair and calls `pair.mint(lpLock)`. Uniswap-V2-style `mint` on a virgin pool computes `liquidity = sqrt(amount0 * amount1) - MINIMUM_LIQUIDITY`; with `amount0 = 0`, `sqrt(0) = 0`, so `0 - 1000` underflows/reverts (`INSUFFICIENT_LIQUIDITY_MINTED` on canonical V2, an arithmetic-underflow panic on the project's own mock, both of which revert the whole `finalizeGraduation` call): [5](#0-4) 

Because `pendingGraduation[token]` is deleted only on a *successful* `finalizeGraduation`, and the cached `(tokensForLP, ltFromPair)` are pure pair-state arithmetic that "never reads `exchangeRate()`" and are explicitly designed to be replayed byte-identically on every retry (per the contract's own natspec on `finalizeGraduation`), there is no path that ever changes the value — every future `finalizeGraduation(token)` call reverts identically forever. [6](#0-5) 

Once stuck in `Lifecycle.Graduating`, `Bonding.buy`/`sell` (and `Zap.buy`/`sell`) revert with `TokenIsGraduating`, so no one can trade the token either — the real LT raised by the curve (already drained into `Bonding` via `Router.graduate` in phase 1) and the 250M reserved LP tokens are permanently unreachable, with no rescue path (the codebase's own `AGENTS.md` explicitly notes `LPLock` has no withdrawal path in v1, and there is no owner escape hatch for a `pendingGraduation` entry stuck at zero).

### Impact Explanation
This permanently freezes: (1) all real LT raised by traders on the bonding curve up to the point of graduation (drained via `Router.graduate` into `Bonding` in phase 1 and never returned), (2) the 250M `LP_RESERVE` tokens reserved for that specific token, and (3) all trading for that token, since `Lifecycle.Graduating` blocks both `Bonding.buy` and `Bonding.sell`. This is a direct, unrecoverable loss of trader/curve funds for that token — no privileged action, upgrade, or off-chain intervention can un-stick it because the cached inputs are immutable and always reproduce the same revert. This matches the CVSS-availability class of the reference CVE (a reachable operation triggers a permanent "hang"/failure of a load-bearing code path), mapped onto alt.fun's own graduation math rather than MySQL's optimizer.

### Likelihood Explanation
Reachable by a single unprivileged trader: any `Zap.buy` (or `Bonding.buy` through an allowlisted router) that pushes `realLtRaised × exchangeRate()` across `graduationThresholdUsd` while `realLtRaised` (in LT-wei) is small relative to the launch-time virtual LT reserve (`VIRTUAL_LIQUIDITY_USD = 3000 ether`) triggers phase 1 inline, with no additional gating. This requires only that the token be paired with (or grow paired with, via LT price appreciation) an LT whose `exchangeRate()` is high enough — an ordinary, expected state for a leveraged token, not an attack on BounceTech itself. The rounding-to-zero condition depends purely on the ratio `ltFromPair / assetReserve`, which narrows toward zero as `exchangeRate()` rises; the bug is deterministic pure-integer-math, not probabilistic, once that ratio is small enough.

### Recommendation
In `_prepareGraduationLiquidity`, guard against `tokensForLP` rounding down to `0` (or generally becoming small enough that `sqrt(tokensForLP * ltFromPair) <= MINIMUM_LIQUIDITY` on the target V2 fork) whenever `ltFromPair > 0`. Either floor `tokensForLP` to a value that guarantees a non-degenerate first mint (e.g. `Math.max(tokensForLP, MINIMUM_TOKENS_FOR_LP)`, capped as today at `LP_RESERVE`), or detect the degenerate case in `finalizeGraduation`/`_seedDirectMint` and fall back to minting with a minimum viable token amount pulled from the reserved `LP_RESERVE`, so the pool always opens with a valid non-zero liquidity mint regardless of how skewed the real-LT-to-virtual-LT ratio is at graduation time. Add a regression test that graduates a curve against a high-`exchangeRate()` LT with `ltFromPair` deliberately tiny, asserting `finalizeGraduation` still succeeds.

### Proof of Concept
1. Launch a token via `Bonding.launch` / `Zap.createToken` paired with an LT whose `exchangeRate()` is set (or appreciates) to a large value relative to `VIRTUAL_LIQUIDITY_USD = 3000 ether` (e.g., in tests, `lt.setExchangeRate(...)` to a very large multiplier, mirroring the existing `test_canGraduate_returnsTrueWhenThresholdMet` / `_ratePumpForStagedGraduation` test helpers already used in `test/Bonding.t.sol` and `test/GraduationInvariants.t.sol`).
2. Perform a minimal `Bonding.buy` (or `Zap.buy`) that raises `realLtRaised` by only a tiny amount of LT-wei — just enough that `realLtRaised × exchangeRate() ≥ graduationThresholdUsd` — while `realLtRaised` stays orders of magnitude smaller than `assetReserve` (which is dominated by the `3000 ether`-equivalent virtual LT reserve).
3. Observe `_enterGraduating` fires inline, caching `pendingGraduation[token] = {tokensForLP: 0, ltFromPair: <tiny nonzero>, ...}` because `(ltFromPair * tokenReserve) / assetReserve` rounds to `0`.
4. Call the permissionless `Bonding.finalizeGraduation(token)`. It creates the HyperSwap pair (empty), calls `_seedDirectMint` with `tokensForLP = 0`, transfers `0` tokens + `ltFromPair` LT to the pair, and calls `pair.mint(lpLock)`, which reverts (`sqrt(0) - MINIMUM_LIQUIDITY` underflow / `INSUFFICIENT_LIQUIDITY_MINTED`).
5. Retry `finalizeGraduation(token)` — it reverts identically every time since `pendingGraduation[token]` is unchanged. The token is permanently stuck in `Lifecycle.Graduating`; `Bonding.buy`/`sell` and `Zap.buy`/`sell` all revert with `TokenIsGraduating`; the LT drained via `Router.graduate` in phase 1 and the 250M `LP_RESERVE` tokens are unrecoverable.

    function finalizeGraduation(
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }

    function _seedDirectMint(
        address tokenAddress,
        address lt,
        address pair,
        uint256 tokensForLP,
        uint256 ltFromPair
    ) internal returns (uint256 liquidity) {
        IERC20(tokenAddress).safeTransfer(pair, tokensForLP);
        IERC20(lt).safeTransfer(pair, ltFromPair);
        liquidity = IUniswapV2Pair(pair).mint(_s().lpLock);
        uint256 leftoverToken = IERC20(tokenAddress).balanceOf(address(this));
        if (leftoverToken > 0) {
            Token(tokenAddress).burn(address(this), leftoverToken);
        }
