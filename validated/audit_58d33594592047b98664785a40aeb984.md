### Title
Unbounded `Topics` array in Web API trigger request causes O(N×M) DoS in `processTrigger()` - ([File: core/capabilities/webapi/trigger/trigger.go])

### Summary
The `processTrigger` function in the `web-api-trigger` capability's gateway handler iterates over every registered workflow and, for each workflow, iterates over every element of the attacker-supplied `payload.Topics` slice, with no upper bound on the size of that slice. An unprivileged external caller sending a gateway request can submit an arbitrarily large `Topics` array, forcing the node to perform O(registeredWorkflows × len(topics)) work — including rate-limiter checks, execution-ID generation, and event emission — for a single inbound message, analogous to the unbounded-array DoS pattern in the external report where an ever-growing set drove excessive work inside a critical loop.

### Finding Description
`HandleGatewayMessage` decodes an untrusted JSON payload from the gateway into `webapicap.TriggerRequestPayload` and passes it straight to `processTrigger` without validating the size of `payload.Topics`: [1](#0-0) 

Inside `processTrigger`, the code takes a snapshot of all currently registered workflows and then runs a nested loop: for every registered workflow, for every topic in the caller-controlled `topics` slice, it does a map lookup (`trigger.allowedTopics[topic]`), and on a match performs a sender check, a rate-limiter check, execution-ID generation (`events.GenerateExecutionID`), and an event emission (`events.EmitTriggerExecutionStarted`): [2](#0-1) 

There is no limit anywhere in this path on `len(payload.Topics)` — only a check that it is non-empty: [3](#0-2) 

Because the outer loop count (number of registered workflows) grows with legitimate workflow registrations over time, and the inner loop count is entirely attacker-controlled per request, a single malicious or malformed request can multiply the cost of handling every subsequent (and the current) trigger message, matching the report's root cause: an unbounded, caller-influenced collection driving unchecked iteration inside a function that must complete for the system to function correctly (here, trigger dispatch to workflows).

### Impact Explanation
A crafted `web_api_trigger` gateway message with a very large `Topics` array can consume disproportionate CPU/memory on the node processing the request, since the work is proportional to `registeredWorkflows × len(topics)` and includes per-match calls such as `events.EmitTriggerExecutionStarted`. As more workflows register triggers over time (a normal, expected operational growth, not attacker-controlled), the multiplier effect increases, so requests that were cheap before become expensive later — closely mirroring the original report where an ever-growing collection eventually made a critical function too expensive to execute reliably. In the worst case this can degrade or block timely trigger delivery to legitimate workflows sharing the same `triggerConnectorHandler`, delaying or dropping workflow executions.

### Likelihood Explanation
The request path is reachable from an unprivileged external caller via the gateway (`HandleGatewayMessage` → `MethodWebAPITrigger`), and nothing enforces a maximum size on `payload.Topics` before it reaches the nested loop. I could not find any external boundary validation of `Topics` length in the gateway HTTP handler layer that forwards such messages to this capability handler based on the code visible in the index. This makes the likelihood plausible but not fully confirmed — a full assessment would require checking the gateway's inbound HTTP request/JSON-RPC size limits, which may or may not bound the number of array elements versus just total payload byte size.

### Recommendation
Enforce an explicit, reasonably small upper bound on `len(payload.Topics)` (and consider bounding `AllowedTopics`/`AllowedSenders` sizes at registration time too) before entering the nested loop in `processTrigger`, rejecting oversized requests early with an error response rather than performing the O(N×M) work. Additionally, consider indexing workflows by topic (e.g., `map[topic] -> []*webapiTrigger`) instead of iterating all registered workflows per topic, to avoid the multiplicative cost entirely.

### Proof of Concept
1. Register one or more workflows via `RegisterTrigger` with non-trivial `AllowedTopics`/`AllowedSenders` sets (standard, legitimate operation) — see `core/capabilities/webapi/trigger/trigger.go:212-269`.
2. As an unprivileged caller, send a `web_api_trigger` gateway message whose JSON body decodes into `webapicap.TriggerRequestPayload` with `Topics` containing a very large number of entries (e.g., 10^5+ strings), which passes the only check present (`len(topics) == 0`) at `core/capabilities/webapi/trigger/trigger.go:94-96`.
3. `HandleGatewayMessage` (`core/capabilities/webapi/trigger/trigger.go:167-188`) invokes `processTrigger`, which executes the nested loop over `triggers × topics` (`core/capabilities/webapi/trigger/trigger.go:106-156`), performing map lookups, rate-limit checks, and event emission proportional to the attacker-chosen `Topics` size — demonstrating the unbounded-work DoS vector for a single unprivileged request.
