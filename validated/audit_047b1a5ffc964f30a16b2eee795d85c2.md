### Title
Single reverting/malicious ERC-20 in a multi-asset order permanently freezes all escrowed funds via unprotected loop in `_withdraw` - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._withdraw` iterates over an order's token list and calls `safeTransfer`/`_sendValue` on each token inside an unprotected loop. This function is invoked from `onAccept` when a `RedeemEscrow` or `RefundEscrow` cross-chain message is delivered. Because `EvmHost.dispatchIncoming` only catches the *outer* call to `onAccept` and retries the whole delivery, a single token in the order's `inputs` array that reverts on transfer (blacklist, pause, malicious/rugged token, etc.) permanently blocks release of *every* token in that order, with no path to recovery once the order has already been finalized (`_filled` set) on the counterpart chain.

### Finding Description
`_withdraw` loops over `body.tokens` and transfers each one with no try/catch or per-token failure isolation: [1](#0-0) 

This function is reached from `ExtrinsicIntents.onAccept`-driven flows for `RedeemEscrow` (paid to the solver after a cross-chain fill) and `RefundEscrow` (paid to the user after cancellation) — both dispatched via Hyperbridge as `PostRequest`s and delivered by `EvmHost.dispatchIncoming`: [2](#0-1) 

`dispatchIncoming` only guards the top-level `onAccept` call: if it reverts, the receipt is deleted "so that it can be retried" — but a retry re-executes the exact same loop with the exact same poisoned token and will revert identically every time. There is no mechanism to skip, isolate, or partially settle the non-reverting tokens in `body.tokens`.

The order's input tokens are attacker/user-controlled at order-placement time (`placeOrder`/`_escrow`), and the destination-side order is marked filled (`_filled[commitment] = msg.sender`) *before* the cross-chain `RedeemEscrow` message even reaches the source chain: [3](#0-2) 

So once a solver has filled a cross-chain order whose `order.inputs` includes any token that can be made to revert on transfer to the beneficiary (e.g., a USDC-style token that blacklists the solver's or user's address after order placement, a token that self-destructs/pauses, or a bespoke malicious ERC-20 the order creator deliberately includes alongside a legitimate valuable token), the source-chain escrow release can never succeed — freezing not just the bad token but every other legitimately-escrowed token bundled in the same order, permanently.

### Impact Explanation
This is a direct instance of the reported bug class (SWC-113, calls-in-loop) but with materially higher impact than the original Cudos finding, because:
- It causes **permanent freezing of funds**, not just delivery griefing — there is no governance/sweep path back to escrow once `_orders[commitment][token]` balances are stuck behind a permanently-reverting sibling token in the same withdrawal batch.
- The destination side has already advanced (order marked filled/cancelled), so there is no way to re-trigger a different withdrawal path for the order; the withdrawal loop must succeed atomically for the entire `TokenInfo[]` array or not at all.
- Reachable by any unprivileged user/solver placing or filling a cross-chain order (`placeOrder`/`fillOrder` on `IntentGatewayV2`), i.e., a single submitted transaction can create a permanently unrecoverable escrow state.

### Likelihood Explanation
Likelihood is realistic: blacklistable stablecoins (USDC, USDT) are exactly the kind of token expected to be used as order inputs/outputs, and blacklisting of a counterparty address between order placement/fill and cross-chain settlement is a known real-world occurrence, not a purely theoretical attacker capability. An order creator can also deliberately construct a multi-token order pairing a valuable legitimate asset with a token they control and can pause/revert, weaponizing this to grief solvers or permanently lock protocol-adjacent escrow.

### Recommendation
Do not let a single failing transfer abort the whole `_withdraw` batch:
- Wrap each per-token transfer in `_withdraw` (and similarly in `_sweepDust`) in a low-level `call`/try-catch, and if a transfer fails, credit the amount to a per-(commitment, token, beneficiary) claimable balance instead of reverting the loop, so remaining tokens still settle and the failed one can be retried or swept independently.
- Alternatively, disallow reverting/exotic tokens in `order.inputs`/`order.output.assets` at order-placement/fill time via a safe-transfer probe, or cap the blast radius by requiring one token per order.

### Proof of Concept
1. User places a cross-chain order via `IntentGatewayV2.placeOrder` with `order.inputs = [GOOD_TOKEN, EVIL_TOKEN]`, where `EVIL_TOKEN` is an ERC-20 whose `transfer` to a specific address (e.g., any solver) always reverts (blacklist-style logic, or trivially `revert()` unconditionally after a delay/condition the creator controls).
2. Escrow succeeds normally: `_escrow` loops through `order.inputs` doing `safeTransferFrom` — both tokens escrow fine (no revert on `transferFrom` into the gateway).
3. A solver fills the order cross-chain via `fillOrder` → `_fillCrossChain`, providing outputs and paying the solver-side beneficiary; `_filled[commitment] = msg.sender` is set, and a `RedeemEscrow` post request is dispatched back to the source chain.
4. On the source chain, the relayer delivers the request; `EvmHost.dispatchIncoming` calls `onAccept`, which calls `_withdraw(body, false, true)` with `body.tokens = order.inputs = [GOOD_TOKEN, EVIL_TOKEN]`.
5. The loop in `_withdraw` transfers `GOOD_TOKEN` successfully, then attempts `EVIL_TOKEN.safeTransfer(solver, amount)`, which reverts, reverting the entire `onAccept` call (including the successful `GOOD_TOKEN` state change, since it's all one transaction).
6. `EvmHost.dispatchIncoming` catches this, deletes the request receipt "for retry," but every subsequent relayer retry hits the exact same revert on `EVIL_TOKEN`. `GOOD_TOKEN` and `EVIL_TOKEN` both remain locked in `_orders[commitment]` forever, with the order already marked filled on the destination chain (no cancellation path available).     function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
