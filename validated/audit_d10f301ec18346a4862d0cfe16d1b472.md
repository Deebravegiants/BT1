### Title
Unsanitized route payload lets a swap hop invoke attacker code that drains the signer's wallet under their own authorization - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller's strategy verbs (`swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`) accept a fully attacker-supplied `swap_xdr` route. The router resolves the `pool`/`token_in`/`token_out` addresses straight out of that payload's `assets` registry and keeps no allowlist of them, so a route can place an arbitrary attacker-deployed contract on the call stack *below* the victim's `require_auth` entry. That contract can then call `token.transfer(victim, attacker, amount)` on any token in the victim's wallet; the host records the transfer as a child of the victim's `swap_collateral` authorization, and a signature on the simulated tree authorizes it. This is the direct analog of the CVE-2023-38692 command injection class: untrusted input (the route) reaching an execution primitive (arbitrary contract invocation under the caller's auth).

### Finding Description
- `contracts/swap-aggregator/src/types.rs:41` — `StrategyPayload.assets` is a caller-controlled `Vec<Address>` of tokens, pools, and LP tokens; instructions index into it by `u8`.
- `contracts/swap-aggregator/src/venues/mod.rs:23` — `dispatch_hop` routes each hop to a venue adapter that calls `hop.pool`, an address taken verbatim from the payload. The router "calls the pool and token addresses its payload names and keeps no allowlist of them" (`docs/explanation/threat-model.md:154-165`).
- `contracts/controller` strategy path: the controller is `sender` for composed swaps and grants "one exact input-transfer invocation" via `authorize_transfer_as_current` before `execute_strategy` (documented in `skills/xoxno-swap-aggregator/payload.md:111-115`), but for the *direct* `execute_strategy` path the sender is the user, and for `swap_collateral` the user's auth entry roots the whole tree.
- The proof test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates the mechanism end to end: `UnlistedPoolRouter::execute_strategy` invokes `route.hop_pool` (`:44`), `RogueHopPool::swap` calls `token.transfer(victim, attacker, WALLET_BALANCE)` (`:69`), simulation records that transfer as a child of the victim's `swap_collateral` entry (`:206-222`), and signing that tree executes the theft — `assert_eq!(s.wallet(&s.alice), 0)` (`:224, :267-268`).

### Impact Explanation
Theft of user funds beyond the routed amount. The stolen transfer is not bounded by the route's `min_out`, the router's measured-delta checks, or the controller's post-swap risk gate — it touches any token the victim holds, in any amount, because it executes under the victim's own signed authorization tree. The test drains Alice's entire unrelated-token wallet (77,770 units) while her protocol position settles cleanly (`tests/.../rogue_hop_pool_transfer_joins_caller_auth_tree.rs:224-226`).

### Likelihood Explanation
A single unprivileged attacker deploys a malicious "pool" contract, publishes or injects a poisoned `routeXdr` (phishing frontend, compromised quote channel, or malicious route builder), and gets the victim to sign the simulated transaction. Simulation presents the theft only as an extra child node in the auth tree — indistinguishable from a legitimate nested transfer to any wallet that does not decode it. The contracts themselves provide the injection surface; no admin action, oracle manipulation, or protocol state is required.

### Recommendation
The router should resolve hop pools and hop tokens against an on-chain venue/pool registry (or at minimum verify the pool address against a venue-published factory/registry) rather than trusting payload-supplied addresses, so that only recognized venue contracts can sit under the caller's auth. Until then, clients must refuse any authorization tree whose children contain anything other than the single expected `token_in.transfer` (direct swaps) or the controller's input grant (composed strategies) — as the threat model already instructs (`docs/explanation/threat-model.md:160-165`).

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` is a working PoC:
1. Attacker registers `RogueHopPool` with plan `(victim, wallet_token, attacker, WALLET_BALANCE)` (`:56-60`).
2. Route names the rogue pool as the hop (`:111-125`); `execute_strategy` invokes it mid-route (`:44`).
3. `RogueHopPool::swap` executes `token.transfer(alice, attacker, WALLET_BALANCE)` (`:69`).
4. Simulation attaches that transfer beneath Alice's `swap_collateral` auth entry (`:214-222`); signing the recorded tree executes the theft (`:265-268`).
