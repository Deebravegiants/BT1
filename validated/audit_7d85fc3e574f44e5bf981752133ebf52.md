### Title
Unregistered-chain fallback in `IntentGatewayV2.instance()` lets a forged cross-chain message authenticate as a trusted gateway instance and drain escrow — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` resolves the trusted peer-gateway address for a source chain with a fail-open default: when no deployment has been registered for a `stateMachineId`, `instance()` returns `address(this)` instead of reverting. `authenticate()` uses this value to gate `onAccept`, so any relayed `PostRequest` whose `source` is a chain that was never explicitly configured as a peer, and whose `from` field is set to the local contract's own address, passes authentication as if it came from a legitimate, registered `IntentGatewayV2` instance.

### Finding Description
`instance()` in the Tron contract: [1](#0-0) 
```
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    return gateway == address(0) ? address(this) : gateway;
}

function authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    // IntentGateway only accepts incoming assets from itself or known instances
    if (instance(request.source) != module) revert Unauthorized();
}
```
For any `stateMachineId` that has never been registered via `NewDeployment`/`_instances[...]`, `_instances[keccak256(stateMachineId)]` is the storage default, `address(0)`. Instead of treating an unset mapping entry as "unknown, reject" (as the correct/non-Tron implementation does), the Tron implementation substitutes `address(this)` — the local contract's own address — as the trusted counterpart for that source chain.

Compare to the fail-closed EVM implementation: [2](#0-1) 
```
function _instance(bytes calldata stateMachineId) internal view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    if (gateway == address(0)) revert UnknownInstance();
    return gateway;
}
```
This mirrors the external report's bug class precisely: a root/authorization check ("is this the trusted media root / trusted peer instance?") that is supposed to constrain reads/actions to a configured value instead defaults to an *open* value when the config is unset, because the "unset" case was implemented as "trust everything" rather than "trust nothing."

Since ISMP's message-handler layer (`HandlerV2`/`EvmHost`) only verifies that a `PostRequest` genuinely originated from the claimed `source` state machine via consensus/state proofs — it does not know or enforce which *module* on that chain is a legitimate `IntentGatewayV2` peer — that module-level trust decision is entirely delegated to `authenticate()`. Any state machine (chain/rollup id) that Hyperbridge supports as a destination but for which this specific `IntentGatewayV2` deployment has not yet registered a peer (a very common, expected operational state — new chains are onboarded to Hyperbridge before every app registers all peers) is wide open: an attacker who can dispatch a genuine ISMP `PostRequest` from that chain (e.g., by deploying an arbitrary contract on that unconfigured chain and calling the local chain's real dispatch/host contracts, which is unprivileged) sets `from = address(this)` (the known, deployed address of the victim `IntentGatewayV2`) and the message authenticates.

### Impact Explanation
`authenticate()` gates `onAccept`, which dispatches `RequestKind` actions including `RedeemEscrow` (release escrowed tokens to a solver) and `RefundEscrow` (refund escrowed tokens to a user) — both of which move real, escrowed user/solver funds out of the contract. A forged message that passes `authenticate()` from an unconfigured source chain can trigger `RedeemEscrow`/`RefundEscrow` for arbitrary commitments/amounts controlled by the attacker, i.e., unauthorized withdrawal of escrowed funds — concrete theft of funds, reachable by an unprivileged actor from a single relayed cross-chain message. This satisfies "unauthorized app action" / "theft of funds" impact criteria and is High severity, matching the class and severity of the referenced advisory (an authorization boundary silently disabled when a config value is unset).

### Likelihood Explanation
Likelihood is high in practice: every chain onboarded to Hyperbridge that this `IntentGatewayV2` deployment has not yet peered with (a normal transient/operational state during rollout, or any chain the operator simply never registers) is affected by default — no misconfiguration beyond "haven't called `NewDeployment` for that chain yet" is required. The attacker only needs the ability to dispatch a genuine ISMP `PostRequest` from that unregistered source chain (deploying a contract there is unprivileged) with `from` set to the victim gateway's own address, which is knowable from the chain's deployment records/CREATE2 address.

### Recommendation
Change `instance()` to fail closed, mirroring the non-Tron implementation: revert (e.g., `UnknownInstance`) when `_instances[keccak256(stateMachineId)] == address(0)`, rather than substituting `address(this)`. If self-authentication is intentionally desired for the local chain's own state-machine id, gate that explicitly (e.g., `stateMachineId == host().hostStateMachine()`) instead of using the zero-address sentinel as a wildcard "trust local address" fallback.

### Proof of Concept
1. Deploy Hyperbridge support for a new destination/source chain `C` that the target `IntentGatewayV2` (Tron variant) has not yet registered a peer deployment for (`_instances[keccak256(C)] == address(0)`), which is expected during normal onboarding.
2. On chain `C`, dispatch (via the standard ISMP host/dispatcher on `C`, unprivileged) a `PostRequest` with:
   - `source = C`
   - `to = <victim IntentGatewayV2 address>`
   - `from = abi.encodePacked(<victim IntentGatewayV2 address>)` (20 bytes, matching the victim's own deployed address)
   - `body = 0x00 || abi.encode(WithdrawalRequest{commitment: <attacker-chosen>, tokens: ..., beneficiary: <attacker>})` (`RequestKind.RedeemEscrow`)
3. Relay the message through the normal ISMP consensus/message pipeline to the victim chain; `HandlerV2`/`EvmHost` verifies only that it truly came from `C`, then calls `IntentGatewayV2.onAccept`.
4. Inside `onAccept`, `authenticate(request)` computes `instance(C)`. Since `_instances[keccak256(C)] == address(0)`, `instance()` returns `address(this)`, which equals `module` (the forged `from`), so authentication passes.
5. `RedeemEscrow` executes, releasing escrowed tokens to the attacker-controlled beneficiary for a commitment the attacker chose — funds theft with no legitimate order fill.
