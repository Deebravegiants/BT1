### Title
Users permanently lose excess ETH sent to `EvmHost.dispatch()`/`fundRequest()` because Uniswap refunds are returned to the Host contract, not the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` accept `msg.value` and swap it via `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`. Uniswap's router only spends the ETH needed to buy the exact `feeToken` amount and refunds any unused ETH — but the refund is sent to `msg.sender` of the router call, which is the `EvmHost` contract itself, not the end user who originally supplied `msg.value`. `EvmHost.sol` has no logic to forward this refund back to the caller and no `receive`/`withdraw` sweep mechanism, so any ETH sent in excess of the exact amount needed is permanently stuck.

### Finding Description
In `dispatch(DispatchPost memory post)`: [1](#0-0) 

the full `msg.value` is forwarded to `swapETHForExactTokens`, requesting exactly `post.fee` tokens out. Uniswap V2's router computes the minimum ETH input (`amountIn`) needed and refunds `msg.value - amountIn` to its caller — which here is `EvmHost`, not the original transaction sender. The same pattern repeats in `dispatch(DispatchGet)` and in `fundRequest()`: [2](#0-1) 

Nowhere in `EvmHost.sol` is there a step that measures the ETH actually spent and refunds the remainder to `_msgSender()`. By contrast, other contracts in the same codebase that perform the identical Uniswap ETH-for-fee-token swap explicitly compute and refund unspent native tokens to the caller, e.g. `IntentGatewayV2.sol`: [3](#0-2) 

This confirms the expected/safe pattern (track `amounts[0]` spent, refund the delta) exists elsewhere but is missing in `EvmHost.dispatch`/`fundRequest`. Any dApp or SDK caller who does not supply an exact-to-the-wei `msg.value` (which is unavoidable since the exact Uniswap price at execution time cannot be predicted precisely off-chain, and the docs explicitly warn against calling `quote()` on-chain due to sandwich risk) will overpay and lose the difference, which accumulates unrecoverably inside `EvmHost`.

### Impact Explanation
Every dispatcher of a POST/GET request or `fundRequest` call using native-token payment loses the ETH difference between the `msg.value` sent and the exact amount Uniswap consumes. Given typical slippage buffers recommended for such swaps (to avoid revert on price movement), this is a systematic, ongoing loss across all cross-chain messaging traffic through `EvmHost`, not a rare edge case, and the funds have no recovery path since `EvmHost` holds them with no accounting or withdrawal function tied to the correct recipient. This matches the "medium" classification in the referenced report — no protocol solvency risk, but real, direct and unrecoverable user fund loss.

### Likelihood Explanation
High likelihood: any caller supplying `msg.value` slightly above the exact swap requirement (the normal/expected way to avoid slippage-induced reverts, since callers cannot know the exact on-chain price at execution time) triggers the loss on every dispatch. This is the default, unprivileged, single-transaction path exercised by ordinary users and integrating apps (e.g., `HyperApp.dispatchWithFeeToken`/native dispatch helpers documented for developers).

### Recommendation
In `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, capture the actual ETH spent from `swapETHForExactTokens`'s returned `amounts[0]` (or track `address(this).balance` deltas) and refund the unspent portion of `msg.value` back to `_msgSender()`, mirroring the pattern already implemented in `IntentGatewayV2.sol`.

### Proof of Concept
1. A user calls `EvmHost.dispatch(DispatchPost)` with `msg.value` set higher than the exact ETH needed to buy `post.fee` feeTokens (necessary in practice to tolerate price movement between quote and execution).
2. `swapETHForExactTokens` spends only the minimal ETH required and refunds the excess to `msg.sender`, i.e., the `EvmHost` contract address.
3. `EvmHost` has no code to detect or forward this refund to the original caller.
4. The excess ETH remains locked in the `EvmHost` contract balance indefinitely, representing a direct, unrecoverable loss for the user.
