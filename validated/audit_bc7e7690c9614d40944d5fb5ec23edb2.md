### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, excluding the `shop-domain` header from the HMAC-signed content. `Registry.process` verifies the HMAC over the body only, then trusts `request.shop` (read straight from the unauthenticated header) as the tenant identifier passed to the app's webhook handler. This breaks the identity binding `hmac(signed_bytes) == hmac(bytes_acted_on)`, since `shop` is part of the bytes acted on but not part of the bytes verified.

### Finding Description
`Utils::HmacValidator.validate` computes the signature strictly from `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw HTTP body: [2](#0-1) 

Meanwhile, `shop` is derived directly and solely from the `shop-domain` header, with no cryptographic tie to the signed body: [3](#0-2) 

`Registry.process` validates the HMAC (which only covers `@raw_body`) and then forwards `request.shop` — the unauthenticated header value — to the app's handler as the trusted tenant identity: [4](#0-3) 

The equality that should hold is: `shop_bound_by_hmac == shop_delivered_to_handler`. In this implementation, `shop_bound_by_hmac` is undefined (the field isn't in the signable string at all), so any value can be substituted in `shop_delivered_to_handler` without invalidating the signature — provided the attacker can produce *some* body+HMAC pair signed with the app's `api_secret_key`.

An unprivileged internet user can obtain such a pair without ever touching `api_secret_key`, an access token, or any of the app's credentials: they simply install the target app on their own (attacker-controlled) Shopify development/trial store. Shopify's genuine webhook delivery to the app's endpoint will include a body and an `X-Shopify-Hmac-Sha256` value computed by Shopify using the app's real `api_secret_key`, plus an `X-Shopify-Shop-Domain` header equal to the attacker's own shop. Because the shop header sits outside the signed payload, the attacker can capture that legitimate delivery and replay it to the app's public webhook endpoint after swapping only the `shop-domain` header to a victim's `*.myshopify.com` domain. `HmacValidator.validate` still succeeds (body unchanged), `Registry.process` proceeds, and the handler executes business logic (e.g., data sync, uninstall handling, order/customer updates) believing it originated from the victim shop.

### Impact Explanation
This is a cross-tenant access vulnerability: an attacker who only controls their own store can cause the app to process webhook events as if they belong to a different, victim shop, without needing the app's `client_secret`, any access token, or privileged credentials. Depending on the app's webhook handlers (e.g., `app/uninstalled`, order or customer webhooks), this can lead to data being written/read/deleted under the wrong tenant, satisfying the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is realistic: creating a free/development Shopify store and installing the target app is trivial and requires no special privilege beyond normal internet access. Capturing one's own legitimate webhook request (body + valid HMAC) and replaying it against the public webhook endpoint with a modified header is straightforward, since the library performs no additional binding between the signed body and the shop identity.

### Recommendation
Include the shop domain (and ideally other Shopify-supplied identifying headers, e.g., `api-version`, `webhook-id`) in the HMAC-signed content, or otherwise cryptographically bind `shop` to the verified payload before it is handed to `WebhookMetadata`/handlers. At minimum, `Webhooks::Request#to_signable_string` should incorporate the `shop-domain` header value so that tampering with it invalidates the HMAC check in `Registry.process`.

### Proof of Concept
1. Register a webhook handler with `ShopifyAPI::Webhooks::Registry` for a topic your app cares about (e.g., `app/uninstalled`).
2. As an attacker, install the app on your own store `attacker-shop.myshopify.com`; Shopify delivers a genuine webhook to the endpoint with headers:
   - `X-Shopify-Topic: app/uninstalled`
   - `X-Shopify-Hmac-Sha256: <valid HMAC over raw body, computed with the real api_secret_key>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
3. Capture this raw request (body + `hmac-sha256` header untouched).
4. Replay the identical body/HMAC to the app's webhook endpoint, but change `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body’s HMAC — validation succeeds.
6. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and executes tenant-scoped logic against the victim shop, even though the payload and signature never originated for/from that shop. [5](#0-4)
