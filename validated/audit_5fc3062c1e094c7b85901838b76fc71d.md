### Title
`block.timestamp` as Uniswap swap deadline in `EvmHost.dispatch()` provides no MEV/delay protection when paying fees in native tokens - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` allow any unprivileged caller to pay the protocol's dispatch fee in native token, which triggers an on-chain `swapETHForExactTokens` call through a configured Uniswap V2 router. Both calls pass `block.timestamp` as the swap `deadline` [1](#0-0) , [2](#0-1) . As documented in the referenced report, `block.timestamp` used this way is always equal to whatever block the transaction eventually lands in, so it enforces no real time bound — a transaction can be withheld and included arbitrarily later at a materially worse market price, and it will still pass the deadline check.

### Finding Description
Both `dispatch(DispatchPost memory post)` and `dispatch(DispatchGet memory get)` in `EvmHost.sol` perform an internal swap when the caller sends native ETH to cover the request fee:

```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
``` [1](#0-0) 

The same pattern exists for `GetRequest` dispatch:
```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    get.fee, path, address(this), block.timestamp
);
``` [2](#0-1) 

`swapETHForExactTokens` requests an exact amount of `feeToken()` out (`post.fee`/`get.fee`), spending up to the full `msg.value` sent by the caller and refunding any unspent ETH. Because the `deadline` parameter always equals the timestamp of whichever block ultimately executes the transaction, it can never actually expire — a block producer (or any actor able to delay inclusion, e.g. via private mempool/MEV relays) can hold the signed transaction and choose to include it at a later, more favorable-to-them block where the ETH/feeToken price has moved unfavorably for the user. The swap will still succeed (as long as the price stays within the implicit `msg.value` cap), consuming more of the user's ETH than intended for the same fixed `post.fee`/`get.fee` output, with any leftover simply not being refunded because it was consumed by the worse execution price.

This is the exact bug class described in the external report: using `block.timestamp` for a swap deadline is not a meaningful protection because it always reflects the actual execution block, not the block the user intended.

### Impact Explanation
Any unprivileged user who calls `EvmHost.dispatch()` (for either POST or GET ISMP requests) and pays the request fee in native ETH is exposed. A malicious block producer/relayer/searcher can delay inclusion of the dispatch transaction to a block where ETH/feeToken price has moved against the user, causing the swap to consume materially more of the user's supplied ETH than the fair-market amount required to obtain `post.fee`/`get.fee` worth of the fee token — a direct value-extraction/fund-loss vector on the dispatch path, bounded only by the `msg.value` the caller sent. Since `EvmHost.dispatch()` is the core message-dispatch entrypoint used by any app/user submitting a cross-chain request, this is reachable from a single unprivileged transaction and affects normal message senders, not just governance/admin actors.

### Likelihood Explanation
Likelihood is moderate: it requires an actor with power to delay/reorder transaction inclusion (a validator/block-builder or sophisticated MEV searcher with private-order-flow access) and a native-ETH-fee-paying dispatch call, but no special privileges on the protocol itself are needed — this is exactly the scenario the referenced report calls out for PoS chains, where proposers can know in advance whether they will propose sequential blocks and withhold transactions accordingly.

### Recommendation
Add an explicit `deadline` (or equivalent max-delay) parameter to `DispatchPost`/`DispatchGet` (or to the `dispatch` functions) that the caller sets off-chain when paying fees in native token, and pass that caller-supplied value to `swapETHForExactTokens` instead of `block.timestamp`, reverting if the swap is not executed before it elapses.

### Proof of Concept
1. User calls `EvmHost.dispatch(DispatchPost)` sending `msg.value` in ETH to cover `post.fee` worth of `feeToken`, signing the transaction and broadcasting it.
2. A validator/searcher able to control transaction ordering observes the transaction in the mempool but does not include it immediately; instead it is withheld across several blocks while the ETH/feeToken market price shifts unfavorably to the user (e.g., via manipulation or natural volatility).
3. The validator eventually includes the transaction. Because `deadline == block.timestamp` at execution time, the deadline check in `swapETHForExactTokens` trivially passes regardless of how long the transaction was delayed [3](#0-2) .
4. The swap executes at the now-worse price, consuming a larger portion of the user's `msg.value` to obtain the same fixed `post.fee` amount of `feeToken`, refunding less ETH than the user would have received had the swap executed promptly at the price observed when they signed.
