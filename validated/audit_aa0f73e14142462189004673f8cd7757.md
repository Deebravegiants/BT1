## Finding

### Title
Missing shop-domain validation in `TokenExchange.exchange_token` allows the app's `client_secret` to be sent to an attacker-influenced host - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the destination host for the token-exchange HTTP request directly from the unvalidated `dest` claim of the caller-supplied session token, and then POSTs the app's `client_id`/`client_secret` to that host. Every sibling credential-exchange method in this gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`) explicitly runs the shop value through `Utils::ShopValidator.sanitize!` before using it to build the request host — `TokenExchange` is the one path that skips this check.

### Finding Description
`JwtPayload#initialize` cryptographically verifies the token's signature against `Context.api_secret_key` and checks that `aud == Context.api_key`, but it performs **no validation of the `dest`/`iss` claim's domain** against the trusted Shopify domain list: [1](#0-0) 

`SessionUtils`/tests confirm `dest` is free-form and not restricted to `*.myshopify.com` — the test fixtures show `dest` values such as `https://test-shop.other.spin.dev`: [2](#0-1) 

`TokenExchange.exchange_token` takes this unvalidated `shop`/`dest` value and uses it verbatim to construct the session/host that receives the request containing the app's `client_secret`: [3](#0-2) 

Contrast this with the two other credential-exchange flows in the same module, both of which call `Utils::ShopValidator.sanitize!(shop)` — enforcing the domain equals one of `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) — before building the request: [4](#0-3) [5](#0-4) 

`HttpClient` builds the request host straight from `session.shop`: [6](#0-5) 

The identity binding that is broken is: **the host that is cryptographically authenticated by the JWT signature (i.e., "a genuine Shopify-issued token") is not the same as the host that is validated to be a trusted Shopify domain before the app's secret is sent to it.** The `HmacValidator`/OAuth flow always pairs an authenticity check with a `ShopValidator.sanitize!` domain check (`client_credentials.rb`, `refresh_token.rb`); `token_exchange.rb` only performs the former.

### Impact Explanation
If a session token's `dest` claim can ever reflect a value that is not on `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` (e.g., a merchant-configured custom domain, a differently-formatted host, or any value Shopify includes verbatim in the claim), calling `exchange_token` will cause this gem to issue an HTTP POST containing `client_id` and `client_secret` — the app's most sensitive secret — to that host. This is SSRF carrying the app's own credentials to a host outside the gem's declared trust boundary, matching the High-impact category "SSRF with the app's credentials ... or credential leakage."

### Likelihood Explanation
Exploitation requires no secrets, tokens, or privileged access from the attacker — only the ability to cause a session token to be minted with a `dest`/`iss` value pointing away from the `myshopify.com`/`spin.dev`/`shop.dev` family (e.g., through a merchant's custom domain configuration flowing into a checkout/session-token `dest`, which the code's own test fixtures show is not constrained to a fixed suffix). This is a straightforward, code-provable gap rather than a theoretical one: the inconsistency between `token_exchange.rb` and its sibling methods (`client_credentials.rb`, `refresh_token.rb`) is visible directly in the diff of intent between these three near-identical functions.

### Recommendation
In `ShopifyAPI::Auth::TokenExchange.exchange_token`, validate `dest_shop` with `Utils::ShopValidator.sanitize!(dest_shop)` (mirroring `client_credentials.rb`/`refresh_token.rb`) before constructing `shop_session`/`Clients::HttpClient`, and raise `Errors::InvalidShopError` if it does not resolve to a trusted Shopify domain.

### Proof of Concept
1. Obtain (or cause to be minted) a validly-signed session token whose `dest` claim is `https://attacker-controlled-host.example`.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe (per `token_exchange.rb` lines 39-65 and `http_client.rb` lines 11-19) that the gem builds `shop_session = Session.new(shop: "attacker-controlled-host.example")` and POSTs a body containing `client_id`/`client_secret` to `https://attacker-controlled-host.example/admin/oauth/access_token`, with no call to `Utils::ShopValidator.sanitize!` anywhere in the method — unlike `client_credentials.rb`/`refresh_token.rb`, which would reject this same `shop` value with `Errors::InvalidShopError`.
