### Title
Webhook `shop` identity is never covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before invoking the app's handler. In reality, the HMAC only authenticates the raw request body — the `shop` identity that the handler uses to route/attribute the webhook to a tenant is read from an unsigned HTTP header and is never bound to that signature. This is the exact analog to the report's root cause: a field that is acted upon (here, tenant routing via `shop`) is not covered by the cryptographic check that is supposed to guarantee its authenticity (the HMAC).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop` is pulled straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes and compares the signature over `verifiable_query.to_signable_string` (i.e., the body): [3](#0-2) 

`Registry.process` performs this HMAC check and then, without any further validation, forwards `request.shop` (the unverified header) straight into the `WebhookMetadata` object passed to the app's handler: [4](#0-3) 

The gem's own documentation tells integrators that `Registry.process` "will verify the request did indeed come from Shopify," and shows the intended usage pattern where the handler trusts `data.shop` to route/attribute work to the correct tenant: [5](#0-4) [6](#0-5) 

This breaks the identity binding: `shop used for tenant routing == shop authenticated by the HMAC`. In fact the HMAC authenticates only the body bytes; the tenant identity is unauthenticated. Since one HMAC secret (the app's `client_secret`) is shared across every shop that installs the app, any shop that legitimately installs the app receives real, correctly-signed webhooks addressed to its own domain. That installer — an unprivileged internet user with respect to any *other* tenant — can capture one such `(raw_body, hmac)` pair from a webhook Shopify sent to their own endpoint, then replay it to the app's webhook endpoint with the `shopify-shop-domain` header changed to a different, victim shop that also uses the app. `HmacValidator.validate` still passes (it only checks the body), and `Registry.process` hands the handler a `WebhookMetadata` claiming the victim shop, causing the app to attribute attacker-controlled webhook data to another tenant's records — a cross-tenant data-integrity/confusion vulnerability.

### Impact Explanation
This crosses a tenant boundary: an app built on this gem, following its documented usage exactly as shown in `docs/usage/webhooks.md`, will process attacker-forged webhook data under an incorrect (victim) shop identity, because the library asserts authenticity ("verify the request did indeed come from Shopify") for a field it never actually signs. This matches the Critical "cross-tenant access" impact category, since data intended for one tenant can be injected/attributed to another tenant purely by modifying an unauthenticated header.

### Likelihood Explanation
Exploitation only requires the attacker to be a normal, unprivileged user who can install the target app on a shop they control (no leaked credentials, no privileged account, no TLS interception) — this is the same low bar as any legitimate app installation. Once installed, the attacker fully controls the header replay because they simply intercept and modify their own inbound webhook traffic before resending it to the app's public webhook endpoint.

### Recommendation
Bind the `shop` (and other routing-relevant fields such as `topic`, `webhook_id`, `api_version`) into the HMAC-signable material, or otherwise cryptographically bind the header claims to the signed payload, before trusting them for tenant identification in `Registry.process`. At minimum, update `to_signable_string` in `lib/shopify_api/webhooks/request.rb` to include the shop domain, and update `docs/usage/webhooks.md` to stop asserting that `process` fully "verifies the request did indeed come from Shopify" when only the body is actually authenticated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (normal, unprivileged installation).
2. Shopify sends a legitimate webhook to the app's endpoint:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw_body>`, `x-shopify-topic: orders/create`
   - Body: `raw_body` (order data belonging to attacker-shop)
3. Attacker captures this exact `(raw_body, hmac header)` pair from their own traffic.
4. Attacker POSTs the same `raw_body` and `x-shopify-hmac-sha256` value to the same webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses this successfully; `HmacValidator.validate` recomputes the HMAC only from `raw_body` and it matches, so `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`.
6. The app, following the documented pattern (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), now processes attacker-controlled webhook data under the victim shop's tenant context.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
