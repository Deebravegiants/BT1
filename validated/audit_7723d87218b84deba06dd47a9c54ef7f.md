## Finding

### Title
Webhook shop identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-verifiable signable string from the raw request body only, while the `shop` (and `topic`/`webhook_id`) values that are dispatched to the host application's webhook handler are read directly from unauthenticated HTTP headers. This breaks the equality `shop bound by HMAC == shop delivered to handler`, letting anyone who possesses one validly-signed webhook body/HMAC pair replay it under an arbitrary shop identity.

### Finding Description
`Request#to_signable_string` returns only the raw POST body: [1](#0-0) 

`Request#shop` (and `topic`, `webhook_id`, `api_version`) are parsed straight from HTTP headers with no relation to the signed content: [2](#0-1) 

`HmacValidator.validate` verifies the HMAC only against `verifiable_query.to_signable_string`, i.e. only the body, using the app's `api_secret_key`: [3](#0-2) 

`Registry.process` validates that body-only HMAC and then trusts the header-derived `shop` for dispatch to the handler: [4](#0-3) 

Because the signature never binds `shop` (or `topic`/`webhook_id`), the identity used for tenant routing (`WebhookMetadata#shop`) is disjoint from the identity actually authenticated by the HMAC (the body's origin). Any entity capable of obtaining one genuine `(raw_body, hmac)` pair signed with the app's secret — trivially available to any merchant who installs the app and receives their own webhooks — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value. The HMAC check in `HmacValidator.validate` still passes because it never inspects the shop header, yet `Registry.process` forwards the attacker-chosen `shop` to the handler as if it were authenticated.

### Impact Explanation
This is a cross-tenant identity-binding bypass carried through this gem's own webhook-processing API: the library asserts that a webhook request passed HMAC validation and hands the host application a `shop` value implying that assertion also covers the shop, when it does not. Any host app that uses `WebhookMetadata#shop` from `ShopifyAPI::Webhooks::Registry.process` to key persistence/tenant logic (the documented and intended use of this field) can be made to apply another shop's legitimately-signed payload data under an attacker-chosen shop identity — i.e., cross-tenant access without needing the target's credentials.

### Likelihood Explanation
Any unprivileged party can install the app on their own shop (or otherwise obtain one valid webhook delivery) to acquire a body + HMAC pair signed with the target app's `api_secret_key`. Replaying that exact body while forging only the `shop-domain` header is a simple HTTP-level manipulation requiring no secret material, no privileged account, and no interaction with Shopify's servers beyond the attacker's own legitimate webhook subscription.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the signable content that is verified, or otherwise cryptographically bind them to the authenticated request (e.g., verify the shop domain returned by `Request#shop` against a shop known to be associated with the currently active app installation before dispatching to a handler), rather than trusting header fields that lie outside the HMAC-protected payload.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com" and
# receives a legitimate webhook, e.g. for orders/create, with body B and a
# valid HMAC H = HMAC-SHA256(api_secret_key, B).

headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => H,                     # captured from the real webhook
  "x-shopify-shop-domain" => "victim.myshopify.com", # forged - not covered by H
  "x-shopify-webhook-id" => "any-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: headers)

# HMAC check passes because to_signable_string only covers B:
ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle receives WebhookMetadata(shop: "victim.myshopify.com", ...)
# even though the signature never authenticated that shop value.
```

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
