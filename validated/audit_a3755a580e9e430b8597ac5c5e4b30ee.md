### Title
Checks-Effects-Interactions violation in `IntentGatewayV2.withdraw()` allows reentrant double-redemption of escrowed funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of the intent gateway, `evm/tron/contracts/apps/IntentGatewayV2.sol`, performs the external token transfer for an escrow withdrawal *before* decrementing the escrow accounting variable `_orders[commitment][token]`. This is the same class of bug as CVE-2022-49287: a bookkeeping value that is supposed to gate reuse of a resource (there, `struct tpm_chip`'s refcount; here, the remaining escrowed balance) is updated too late relative to the operation that depends on it, leaving a window in which the "already consumed" resource can be reused. The parallel, hardened implementation used by the primary EVM contracts (`evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`) already fixes exactly this ordering, decrementing state before the transfer — confirming this is a known bug class in this codebase that was not uniformly back-ported.

### Finding Description
`withdraw()` in the Tron contract is: [1](#0-0) 

For each token in the withdrawal batch it: (1) checks only `_orders[commitment][token] == 0` (not whether the escrowed amount actually covers `amount`), (2) makes a raw, unrestricted `token.call(...)` to whatever address is encoded as `token`, and only afterwards (3) decrements `_orders[commitment][token] -= amount`. Because `token` is attacker-influenced order data (any address can be placed as an "input token" at `placeOrder` time) and the call is a bare low-level `.call`, the callee fully controls execution before the escrow counter is ever reduced.

Contrast with the hardened, in-scope reachable path used by the mainline EVM contracts, where the equivalent function decrements the escrow map before performing the transfer: [2](#0-1) 

The project's own regression tests demonstrate that this exact ordering (effects before interaction) is what closes a real, previously-exploitable escrow-theft reentrancy in the same intents subsystem: [3](#0-2) 

The Tron `withdraw()` was not updated to match, so it retains the pre-fix ordering: state that is supposed to record "this escrow slot has already been paid out" is written only after control has been handed to an externally-supplied address.

### Impact Explanation
An escrow accounting variable that functions as the resource's "remaining balance/refcount" is mutated after, rather than before, the external interaction that consumes it. If the callee (an attacker-supplied `token` address, or a malicious ERC-20/near-ERC20-shaped contract used as an order input) can re-enter any code path that reads `_orders[commitment][token]` before the decrement lands, escrowed funds can be paid out more than once for the same commitment, i.e. concrete theft/permanent freezing-class impact on escrowed user/solver funds — matching the CWE-class of the underlying kernel bug (use of a resource whose accounting update was skipped/delayed).

### Likelihood Explanation
Exploitability depends on finding a reachable re-entry point into `withdraw()`/its callers (`onAccept`, `onGetResponse`) that is not gated by `_filled[commitment]` being already set, since `_filled` is written at the very top of `withdraw()`. Both `onAccept` and `onGetResponse` are `onlyHost`-restricted, which narrows the practical re-entry surface to logic reachable purely through the malicious token's callback within the same transfer call. This is the same reason the equivalent contract was hardened rather than left as "theoretically fine" — the project's own history shows this exact ordering was previously weaponized into a full escrow-theft exploit in the sibling contract, which is strong evidence the pattern is unsafe once any additional reentry surface (e.g. a future integration, an unprotected helper, or a token with a non-standard callback) is present.

### Recommendation
Apply the same Checks-Effects-Interactions fix already used in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`: decrement `_orders[commitment][token]` by `amount` (and validate `amount <= escrowed`, not just `!= 0`) before performing the token transfer or native value send. Audit `evm/tron/contracts/apps/IntentGatewayV2.sol` for other instances of the state-after-interaction pattern and bring it to parity with the hardened `evm/src/apps/intentsv2/` implementation, including the duplicate-input-token protections referenced by `testRevert_PlaceOrder_DuplicateInputTokens`.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` and place an order whose `inputs[]` includes a malicious "token" contract address controlled by the attacker (or a legitimate token with a transfer-hook, e.g. ERC-777-style) alongside a real escrowed token.
2. Trigger settlement so `onAccept`/`onGetResponse` calls `withdraw()` for that commitment.
3. In `withdraw()`'s loop, when the call reaches the malicious token's `transfer`-selector handler, the escrow counter `_orders[commitment][token]` for that token has not yet been decremented.
4. If the malicious token's callback can reach any code path that re-reads/re-consumes `_orders[commitment][...]` (directly, or via a future/alternate entry point not covered by the `_filled` guard) before the pending decrement executes, it can cause a double payout of the same escrowed funds.
5. Compare against `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`, which shows the identical pre-decrement-external-call pattern was previously exploitable for escrow theft in the sibling `IntrinsicIntents.sol` contract before the CEI fix was applied there.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);

        }
