### Title
Unbounded `GetRequest.keys` / message batch size lets an unsigned `handle_unsigned` extrinsic force unbounded state-proof verification work under a fixed declared weight - ([File: modules/pallets/ismp/src/lib.rs])

### Summary
`pallet_ismp::Call::handle_unsigned` accepts an arbitrary `Vec<Message>`, and each `Message` (Request/Response) may carry `GetRequest.keys: Vec<Vec<u8>>` with no upper bound anywhere in the type or in the handlers. The extrinsic's declared weight is a fixed constant (`weight()`), and it is a free, unsigned call whose full execution (`Self::execute(messages)`) runs inside `validate_unsigned` — i.e., on every submission/propagation attempt, not just on inclusion. Because there is no cap on the number of keys per `GetRequest`, the number of `GetRequest`s per message, or the number of messages per batch, a single crafted extrinsic can force the node to perform a very large amount of Merkle/Patricia trie proof verification work (cloning per-contract account proofs, rebuilding tries, hashing every key) while being charged a constant, and in this case zero, fee — the same "no limit on the size of the request" class of bug as CVE-2022-23837 in sidekiq.

### Finding Description
`handle_unsigned` is declared with a static weight independent of message content: [1](#0-0) 
and is dispatched as an unsigned call that anyone can submit for free, per the design docs: [2](#0-1) 

`ValidateUnsigned::validate_unsigned` fully executes the batch (`Self::execute(messages.clone())`) just to accept the transaction into the pool, before it is ever included in a block: [3](#0-2) 

`GetRequest.keys` is an unbounded `Vec<Vec<u8>>` with no declared maximum length anywhere in the router type: [4](#0-3) 

Every `verify_state_proof` implementation loops over the full, caller-supplied `keys` with no cap, and for EVM state machines even clones the whole per-contract account proof and rebuilds a trie for each contract touched: [5](#0-4) [6](#0-5) 

The response handler processes every `GetRequest` in the batch, invoking `verify_state_proof` once per request — with no bound on how many `Get` requests can be batched into one `ResponseMessage`: [7](#0-6) 

The same unbounded per-key loop exists in the coprocessor's `handle_get_requests`, which is also reachable via an unsigned `handle_unsigned` call on chains using `pallet-state-coprocessor`: [8](#0-7) 

Nowhere in this call graph is there a check analogous to the caps seen elsewhere in the codebase (e.g. `MAX_STATE_MACHINE_COMMITMENTS`, `MAX_COMMITMENT_EVICTIONS_PER_INSERT`, `MAX_PROOF_DEPTH` in the Pharos SPV verifier) that bounds the number of keys per `GetRequest`, the number of requests per message, or the number of messages per `handle_unsigned` batch. The only practical limit is the extrinsic/block-length limit, which still permits thousands of 32/52-byte keys and correspondingly thousands of trie-proof verifications per submitted transaction — all performed during (free, unpaid) `validate_unsigned`.

### Impact Explanation
Because `handle_unsigned` executes for free and its declared weight does not scale with the actual number of keys/requests/messages, an attacker can submit (or repeatedly propagate) extrinsics whose real CPU/memory cost in `validate_unsigned` vastly exceeds the weight accounted for block-production limits and transaction-pool throttling. This can be used to overload validating/collator nodes' transaction-pool validation loop and general availability, matching the "unbounded resource consumption from an unbounded request size" bug class and the rule's "route unable to deliver messages" impact criterion — a saturated node cannot validate or relay legitimate ISMP messages, degrading or halting message delivery on the affected route.

### Likelihood Explanation
`handle_unsigned` is explicitly designed to be callable by anyone with no signature and no fee (see overview.mdx), so the attack requires no privileges, funds, or state — only crafting a batch with many `GetRequest.keys`/requests and submitting/gossiping it. Nodes must run tx-pool validation (`validate_unsigned`) on every submission attempt for messages naming state machines they track, so repeated submission (or gossip amplification) directly repeats the costly verification work.

### Recommendation
Bound the attacker-controlled dimensions before any proof verification work is performed:
- Add a `MaxKeys`-style bound (or explicit runtime-configured maximum) on `GetRequest.keys.len()`, enforced in `validate_unsigned`/`execute` before calling `verify_state_proof`.
- Bound the number of `Get` requests allowed per `ResponseMessage`/`RequestMessage` and the number of `Message`s allowed per `handle_unsigned` batch.
- Make the declared `#[pallet::weight(...)]` for `handle_unsigned` (and `pallet-state-coprocessor::handle_unsigned`) a function of the actual message content (number of keys, requests, and messages) rather than a fixed constant, so oversized batches are rejected by weight limits rather than executed for free.

### Proof of Concept
1. Construct a `Message::Response(ResponseMessage)` (or `Message::Request(RequestMessage)`) whose `requests` field contains many `GetRequest` entries, each with `keys` populated up to the block-length limit (e.g., thousands of 52-byte EVM storage keys spread across many distinct contract addresses to maximize distinct trie rebuilds), following the same shape used in the existing test fixtures that build 100–1000 requests with 256 keys each: [9](#0-8) 
2. Wrap it in `pallet_ismp::Call::handle_unsigned { messages: vec![message] }` and submit it as an unsigned extrinsic to a Hyperbridge/ISMP node's transaction pool.
3. `validate_unsigned` calls `Self::execute(messages.clone())`, which for each `Get` invokes `verify_state_proof`, which loops over every key, clones/rebuilds a trie per distinct contract, and performs proof verification — all before the transaction is accepted into the pool and regardless of whether it is ever included in a block.
4. Repeating step 2 from multiple peers (the call is free and requires no valid state, only a syntactically well-formed proof structure that fails late) forces repeated expensive validation work on every node validating unsigned transactions for the targeted state machine, since the declared static weight in `weight()` does not reflect or limit this cost.

## Transaction fees

Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free as unsigned transactions. The upside to this is that it cannot be exploited as a spam vector, since the transaction pool will check if the submitted extrinsics are valid before they are included in the pool. This validity check ensures that the transaction can be successfully executed and contains valid proofs. Malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing and potential network congestion.

pub fn verify_state_proof<H: Keccak256 + Send + Sync>(
	keys: Vec<Vec<u8>>,
	root: H256,
	proof: &Proof,
	ismp_address: H160,
) -> Result<BTreeMap<Vec<u8>, Option<Vec<u8>>>, Error> {
	// Reject repeats before doing any work at all. They are already an error — repeats collapse
	// in the map returned below, so the caller's key-count check fails — but reaching that
	// check means every repeat has been verified first, and for account queries that is a
	// clone of the whole contract proof each time.
	let mut seen_keys = BTreeSet::new();
	for key in &keys {
		if !seen_keys.insert(key.as_slice()) {
			return Err(EvmStateMachineError::DuplicateKey.into());
		}
	}

	let evm_state_proof = decode_evm_state_proof(proof)?;
	let mut map = BTreeMap::new();
	let mut contract_to_keys = BTreeMap::new();
	let mut contract_account_queries = Vec::new();

	// Group keys by the contract address they belong to
	for key in keys {
		// For keys that are 52 bytes we expect the first 20 bytes to be the contract address and
		// the last 32 bytes the slot hash.
		// For keys that are 20 bytes we expect that to the
		// contract or account address.
		// For keys that are 32 bytes we expect that to be a slothash in
		// the Ismp EVM host
		let contract_address = if key.len() == 52 {
			H160::from_slice(&key[..20])
		} else if key.len() == 32 {
			ismp_address
		} else if key.len() == 20 {
			contract_account_queries.push(H160::from_slice(&key));
			continue;
		} else {
			return Err(EvmStateMachineError::UnsupportedKeyLength.into());
		};
		let entry = contract_to_keys.entry(contract_address.0.to_vec()).or_insert(vec![]);

		let slot_hash = if key.len() == 52 {
			H::keccak256(&key[20..]).0.to_vec()
		} else {
			H::keccak256(&key).0.to_vec()
		};

		entry.push((key, slot_hash));
	}
