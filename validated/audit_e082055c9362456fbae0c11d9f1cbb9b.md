### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated once `Utils::HmacValidator.validate(request)` succeeds, then immediately trusts `request.shop` (and `request.topic`/`request.webhook_id`) to build the `WebhookMetadata` passed to the app's handler. However, the HMAC signable content is only the raw body — the shop-identifying header is never covered by that signature. This is the same bug class as the Beanstalk report: a value the code treats as verified (`amountIn`/here, the tenant identity) is not the value that was actually checked (`receiveToken` return/here, the HMAC digest), letting an attacker substitute a different identity after the check passes.

### Finding Description
`Registry.process` gates all processing on the HMAC check and then trusts `request.shop`: [1](#0-0) 

`Utils::HmacValidator.validate` recomputes the signature only from `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`; `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from separate HTTP headers that are outside the HMAC digest: [3](#0-2) 

So the equality the gem implicitly asserts is:
`HMAC_valid(raw_body) == true` implies `shop header == the tenant that produced raw_body`

That equality does not hold: `shop` is a header, not part of the signed material, so it can be swapped independently of the (still-valid) body/HMAC pair. Concretely: a merchant/app-install that legitimately receives a real Shopify webhook for their own shop (with a valid `x-shopify-hmac-sha256` computed by Shopify over that body) can replay the identical body/HMAC to the app's webhook endpoint while substituting `x-shopify-shop-domain` for a victim shop. `HmacValidator.validate` still returns `true` (it never inspects the shop header), and `Registry.process` dispatches to the handler with `WebhookMetadata.new(shop: request.shop, ...)` set to the attacker-chosen victim shop.

### Impact Explanation
If the host application uses `data.shop` from `WebhookMetadata` (as documented/intended by this gem, see `test_process_with_new_format_headers` asserting `data.shop` is trusted) to select which tenant's records to create/update/delete, an attacker who controls one legitimately-installed shop can inject webhook-triggered side effects (order/customer/app-data mutations) under an arbitrary victim shop's identity — a cross-tenant access vulnerability, which the rules classify as Critical impact.

### Likelihood Explanation
Exploitation requires the attacker to control (or install) any single instance of the app producing normal webhook traffic to capture one valid `body`+`hmac` pair for their own shop, and to replay that exact request with a forged `shop-domain` header. No secrets, tokens, or privileged access are needed — HTTP-level header manipulation against the app's own public webhook endpoint is sufficient, which is achievable by any unprivileged internet user who is or becomes an installed shop for the target app.

### Recommendation
Bind the shop identity into the material that is HMAC-verified (or otherwise cryptographically bind it), for example:
- Include the `shop` (and `topic`) header value as part of `to_signable_string` so it becomes part of the HMAC-verified payload, or
- Cross-check `request.shop` against the shop embedded in the JSON body (most Shopify webhook payloads do not carry shop domain in-body, so this may not be sufficient), or
- Require host applications to independently authenticate the tenant (e.g., look up an existing session/installation keyed by an out-of-band verified shop identifier) before trusting `WebhookMetadata#shop` for any tenant-scoped operation, and document explicitly in this gem that `shop`/`topic`/`webhook_id` headers are **not** authenticated by `HmacValidator.validate` — only the raw body is.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets Shopify deliver a legitimate webhook (e.g., `orders/create`) to the app's webhook endpoint. Capture the full raw body and the `x-shopify-hmac-sha256` header value — both valid and Shopify-signed.
2. Replay the identical HTTP POST to the same endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` unchanged, but changing `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` (per `hmac_validator.rb:12-31`) recomputes the HMAC purely from the unchanged raw body and secret, so it returns `true`.
4. `Registry.process` (`registry.rb:189-200`) proceeds and calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host application to act as though this webhook (and its body/content) genuinely originated from the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
