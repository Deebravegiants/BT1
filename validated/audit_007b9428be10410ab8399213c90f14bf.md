### Title
A stale per-invocation asset configuration survives a governance state change inside `flash_position`, allowing collateral to be deposited and evaluated under retired risk parameters - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
`flash_position` loads spoke/asset configuration and prices into `Context` before invoking the caller-selected receiver. The receiver can execute an already-ready governance operation that changes that same collateral’s risk configuration, then return collateral to the controller. Because `Context` intentionally retains already-cached values, post-callback deposit stamping and solvency checks can use the obsolete configuration.

### Finding Description
`process_flash_position` creates one `Context`, validates the requested collateral legs, prefetches prices, and only then calls `mint_and_forward` and `invoke_receiver` inside the flash guard. [1](#0-0) 

`Context::cached_spoke_asset`, `require_spoke_asset_config`, `spoke_config`, `require_hub_active`, `fetch_prices`, and `fetch_market_indexes` all retain the first loaded value for the remainder of the invocation. [2](#0-1) [3](#0-2) [4](#0-3) 

The untrusted receiver can therefore execute a governance-ready operation between configuration lookup and final account evaluation. After callback return, `collect_collateral_deposits` only measures the token balance increase, `process_deposit` records the collateral, and `strategy_finalize` evaluates the account through the same stale `Context`. [5](#0-4) [6](#0-5) 

This matches the report’s lifetime bug class: state that should be ephemeral to the pre-callback authorization/evaluation phase is retained by a longer-lived object and consulted after the trusted condition has changed.

### Impact Explanation
A caller can use a ready governance operation that lowers a collateral asset’s LTV/liquidation threshold, disables supply, deprecates the spoke, or otherwise tightens its risk configuration. The callback changes the authoritative storage state, while the open `flash_position` still stamps and evaluates the deposit using the old cached configuration.

If the stale parameters are sufficiently more favorable, the resulting account can pass `ltv_collateral >= total_debt`, `health_factor >= Wad::ONE`, and the collateral floor even though it would fail under the current parameters. [7](#0-6) 

The borrowed assets have already left the pool through `mint_and_forward`, so the protocol can be left with debt collateralized only under obsolete risk parameters. Depending on the governance transition and market movement, this can create immediate bad debt or leave insufficient collateral to repay the minted debt.

### Likelihood Explanation
The path is reachable by an unprivileged account: `flash_position` is callable with `account_id = 0`, a caller-controlled Wasm receiver, selected collateral minimums, and selected refund assets. [8](#0-7) 

The governance operation must already be ready and the receiver must be able to produce the required collateral return. The attacker can time `flash_position` specifically for the ledger in which such an operation becomes executable, avoiding the need to control governance itself.

No host re-entry into the controller is needed: the callback invokes governance, not the controller, and then returns collateral directly.

### Recommendation
Do not retain spoke, asset, hub-active, price, or pool sync snapshots across an untrusted callback when post-callback accounting depends on them.

After `invoke_receiver` returns, construct a fresh `Context` or explicitly invalidate `spoke_usage`, `spoke_config`, `spoke_assets`, `verified_hubs`, `pool_sync_data`, `market_indexes`, and `token_prices` before calling `process_deposit` and `strategy_finalize`. At minimum, re-read the collateral’s `SpokeAssetConfig` and hub/spoke activity immediately before stamping its stored LTV and liquidation parameters.

Alternatively, execute the callback before collateral validation and then perform all market/configuration loading after the callback, so no privileged or external state transition can be interposed between validation and settlement.

### Proof of Concept
1. Governance schedules and reaches the execution window for an operation that changes collateral `C` from `ltv = 8000` to `ltv = 0`, or marks `C` not supplyable/deprecated.
2. Attacker deploys a Wasm receiver and calls:

```text
controller.flash_position(
    caller = attacker,
    account_id = 0,
    spoke_id = S,
    mode = Multiply,
    debt = D,
    amount = 1_000_D,
    receiver = attacker_receiver,
    data = encoded_governance_operation_id,
    collaterals = [(C, minimum_C)],
    refund_assets = []
)
```

3. Before the callback, `process_flash_position` caches active spoke state, `C`’s old `SpokeAssetConfig`, and relevant prices/indexes.
4. Inside `execute_flash_position`, the receiver calls `governance.execute(ready_operation_id)`, which writes the new zero-LTV or disabled configuration for `C`.
5. The receiver sends enough `C` to the controller to satisfy `minimum_C`.
6. `collect_collateral_deposits` accepts the measured `C` receipt, but `process_deposit` and `strategy_finalize` continue through the original `Context`, whose cached `C` configuration still reflects the old `8000` LTV and supplyable state.
7. The account passes the post-pool solvency checks using retired parameters, while the debt remains owed by the attacker’s new account.

pub(crate) fn process_flash_position(
    env: &Env,
    caller: &Address,
    params: FlashPositionParams<'_>,
) -> u64 {
    require_authorized_caller(env, caller);

    let FlashPositionParams {
        account_id,
        spoke_id,
        mode,
        debt,
        amount,
        receiver,
        data,
        collaterals,
        refund_assets,
    } = params;

    require_positive_amount(env, amount);
    config::require_hub_active(env, debt.hub_id);
    assert_with_error!(
        env,
        matches!(
            mode,
            PositionMode::Multiply | PositionMode::Long | PositionMode::Short
        ),
        CollateralError::InvalidPositionMode
    );
    require_wasm_receiver(env, receiver);

    let controller = env.current_contract_address();
    assert_with_error!(
        env,
        *receiver != controller,
        FlashLoanError::InvalidFlashloanReceiver
    );

/// Requires debt coverage by LTV-weighted collateral, health factor >= 1, and
/// the configured collateral floor. Debt-free accounts skip all three checks.
pub(crate) fn require_post_pool_risk_gates(env: &Env, cache: &mut Context, account: &Account) {
    if account.debt_free() {
        return;
    }

    let totals = risk::calculate_account_risk_totals(
        env,
        cache,
        &account.supply_positions,
        &account.borrow_positions,
    );

    assert_with_error!(
        env,
        totals.ltv_collateral >= totals.total_debt,
        CollateralError::InsufficientCollateral
    );

    spec_hooks::solvency_gate_checked(account);

    assert_with_error!(
        env,
        totals.health_factor >= Wad::ONE,
        CollateralError::InsufficientCollateral
    );

    let floor = storage::get_min_borrow_collateral_usd_wad(env);
    if floor != 0 && totals.ltv_collateral.raw() < floor {
        panic_with_error!(env, CollateralError::MinBorrowCollateralNotMet);
    }

    require_whole_unit_collateral_floor(env, cache, account);
}
