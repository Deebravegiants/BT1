## Title
Webhook Shop-Domain Spoofing via HMAC That Only Covers the Raw Body - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
The webhook HMAC verification in this gem authenticates only the raw request body, while the shop identity (`x-shopify-shop-domain` header) that the host application uses to attribute the webhook to a tenant is never covered by that signature. Because the same `api_secret_key` is used to sign webhooks for every shop that has installed the app, an attacker who controls their own (free) shop installation can obtain a validly-signed webhook body and replay it against the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop, producing a webhook that passes `HmacValidator.validate` and is dispatched to the app's handler as if it originated from the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read directly from an attacker-controllable HTTP header and is never included in the signed material: [2](#0-1) 

`Registry.process` validates the HMAC over the request (i.e., over the body only) and then trusts `request.shop` unconditionally to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`, i.e., the raw body, and the secret — it has no notion of which shop the request claims to be for: [4](#0-3) 

The binding that is expected to hold is:
`shop authenticated by HMAC == shop delivered to the handler as WebhookMetadata.shop`

In reality the equality is broken: the HMAC only proves "this body was signed with the app's `api_secret_key`" — it says nothing about which shop the body is "for." Since the same `api_secret_key` is shared by the app across every merchant that installs it, any merchant (including an attacker who freely installs the app on their own development/trial shop) can legitimately receive a webhook with a valid `hmac-sha256` value for a body they fully control (or a body Shopify sends them, e.g., an empty-payload topic). The attacker can then replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with any victim shop's domain. `HmacValidator.validate` still returns `true` because it never looks at the shop header, and `Registry.process` passes the spoofed `shop` straight into the handler.

### Impact Explanation
This is a cross-tenant access vector: an attacker-controlled webhook payload is delivered to the host application labeled as belonging to a victim merchant. Any host application logic that trusts `WebhookMetadata#shop` (e.g., to load the correct shop's session/access token, apply state changes, or route to per-tenant logic) will act on attacker-supplied data under the victim's tenant identity, meeting the "cross-tenant access" criterion.

### Likelihood Explanation
Likelihood is high for any developer using this gem's default `Webhooks::Registry`/`Webhooks::Request` machinery as documented: the attacker needs no privileged credentials — only a self-service Shopify development/trial store to obtain a validly HMAC'd webhook body, and the ability to POST an HTTP request with a forged shop-domain header to the app's public webhook endpoint.

### Recommendation
Bind the shop identity into the verified signature material, or otherwise cryptographically tie the `shop-domain` header to the HMAC, so that the shop the payload is delivered "for" cannot be altered without invalidating the signature — e.g., include the `shop-domain` (and/or `topic`, `webhook-id`) header value as part of `to_signable_string`'s input, or have `Registry.process` cross-check the request's shop against a separately authenticated channel (such as verifying the webhook via Shopify's per-shop signing if available) before trusting `request.shop`.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`.
2. Shopify delivers a legitimate webhook to the attacker's registered endpoint with body `B` and a valid `x-shopify-hmac-sha256` computed with the app's `api_secret_key`.
3. Attacker captures `B` and the valid HMAC, then sends a POST to the app's public webhook endpoint with the same body `B`/HMAC but header `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the HMAC.
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though the payload never touched the victim's store, as shown by: [5](#0-4)
