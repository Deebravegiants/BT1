Audit Report

## Title
Plaintext `AccessKey` and `OutgoingToken` for External Initiators permanently exposed to any authenticated (including `view`-role) user via `GET /v2/external_initiators` - (File: core/web/presenters/external_initiators.go)

## Summary
The `ExternalInitiatorResource` presenter used by the `GET /v2/external_initiators` index route unconditionally serializes the long-lived `AccessKey` and `OutgoingToken` fields in plaintext with no `omitempty` or redaction, and the route itself is registered with no role restriction beyond generic authentication. Any user with the lowest-privilege `view` role can repeatedly harvest these standing webhook credentials for every configured External Initiator.

## Finding Description
`ExternalInitiator.AccessKey` and `OutgoingToken` are long-lived credentials that authenticate inbound job-run trigger requests and outbound callbacks between the node and external initiator services [4](#0-3) . The one-time `Secret` is intentionally returned only at creation via `ExternalInitiatorAuthentication` [5](#0-4) , but the separate read/list presenter `ExternalInitiatorResource` always includes `AccessKey` and `OutgoingToken` without `omitempty`, unlike the analogous `BridgeResource.IncomingToken` field which is deliberately `omitempty` and left unset on normal reads [6](#0-5) [7](#0-6) . The `Index` handler builds this resource straight from ORM-loaded records with no filtering [8](#0-7) , and this is confirmed by the controller test asserting `AccessKey`/`OutgoingToken` round-trip through the index response [9](#0-8) .

Critically, the route registration confirms there is no role gate on this GET route: `authv2.GET("/external_initiators", paginatedRequest(eia.Index))` has no `auth.RequiresEditRole`/`RequiresAdminRole` wrapper, whereas the `POST`/`DELETE` variants on the same resource do (`auth.RequiresEditRole(eia.Create)`, `auth.RequiresEditRole(eia.Destroy)`) [10](#0-9) . The codebase has a real, enforced `view` role that is the lowest privilege tier and is explicitly excluded from run/edit/admin actions elsewhere (`RequiresRunRole`, `RequiresEditRole`, `RequiresAdminRole` all reject `UserRoleView`) [2](#0-1) [3](#0-2) . Because the index route has no such wrapper, a `view`-role user — who cannot create/delete external initiators, run jobs, or export keys — can still list every External Initiator's plaintext `AccessKey` and `OutgoingToken` in perpetuity via ordinary paginated GET requests.

## Impact Explanation
This is a genuine, in-scope key/secret exfiltration vulnerability: standing webhook-authentication credentials (`AccessKey`, `OutgoingToken`) used to authenticate inbound job-run triggers and outbound node callbacks are readable by the lowest-privilege authenticated role (`view`), which by design is meant to have read-only, non-privileged access. This enables a low-privileged account to obtain credentials that could be used to impersonate the external initiator's authorized calls to the node or forge outbound-callback trust, exceeding the intended privilege boundary enforced everywhere else in the router via `RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole`.

## Likelihood Explanation
High likelihood in any deployment with External Initiators enabled and more than one user role in use (a common practice — creating `view`-role accounts for dashboards/monitoring/read-only integrations). No misconfiguration, timing, or special access is needed: a single ordinary `GET /v2/external_initiators` call by a `view`-role user reproduces the leak every time, as shown by the existing test asserting the fields are always populated in list responses.

## Recommendation
Add a role guard (at minimum `auth.RequiresEditRole`, consistent with `POST`/`DELETE`) to `GET /v2/external_initiators` in `core/web/router.go`, and/or strip `AccessKey`/`OutgoingToken` from `ExternalInitiatorResource` (mirroring `BridgeResource.IncomingToken`'s `omitempty` treatment), only exposing them once via `ExternalInitiatorAuthentication` at creation time.

## Proof of Concept
1. Enable External Initiators (`JobPipeline.ExternalInitiatorsEnabled = true`).
2. As an `admin`/`edit` user, `POST /v2/external_initiators` to create an initiator.
3. Create a second user with `UserRoleView` (the lowest-privilege role).
4. As the `view`-role user, call `GET /v2/external_initiators?size=50` — this succeeds since the route has no `RequiresEditRole`/`RequiresAdminRole` wrapper.
5. Observe the response includes `accessKey` and `outgoingToken` in cleartext for every initiator, matching `TestExternalInitiatorsController_Index`'s assertions at core/web/external_initiators_controller_test.go:104-126.
