## Title
Verifier signature replay across crowdloan fund lifecycles due to missing `fund_index` in signed payload - (File: `polkadot/runtime/common/src/crowdloan/mod.rs`)

## Summary
`Pallet::do_contribute` verifies KYC/verifier signatures against the payload `(index, &who, old_balance, value)`, where `index` is the `ParaId` and `old_balance` is read from the current fund's child-trie via `contribution_get(fund.fund_index, &who)`. Since the payload never includes `fund.fund_index`, and `old_balance` resets to `0` in a freshly created fund's child-trie, a signature originally authorized for a contributor's first contribution to one fund can be replayed verbatim as the first contribution to a subsequent fund created for the same `ParaId` after a dissolve/recreate cycle.

## Finding Description
In `do_contribute`, the signed payload is constructed and verified as: [1](#0-0) 

`old_balance` comes from the current fund's child-trie, keyed by `fund.fund_index`: [2](#0-1) 

`fund_index` is assigned monotonically at `create` time and is not part of the signed payload: [3](#0-2) 

`dissolve` removes the `Funds` entry for a `ParaId` once `raised` is zero, permitting a brand-new `create` for the same `ParaId` later, which allocates a fresh `fund_index` and thus a fresh, empty child-trie. This means a new fund for the same `ParaId` will again produce `old_balance == 0` for any contributor's first contribution — identical to the `old_balance` used in the very first, already-broadcast signed payload from the prior (now-dissolved) fund. Because `index` (the `ParaId`), `who`, `old_balance` (0), and `value` can all coincide across the two funds, the exact same `MultiSignature` remains valid for `signature.verify` in the new fund. None of the other checks in `do_contribute` (cap, period, VRF delay, auction status) reference `fund_index` or otherwise scope the signature to a specific fund lifecycle, so this replay is not caught by any existing guard.

## Impact Explanation
This breaks the intended one-time-use / per-event authorization semantics of the verifier signature scheme: a KYC/whitelist signature meant to authorize exactly one contribution event in one specific fund can instead authorize a contribution to a different, later fund tied to the same `ParaId`, bypassing the organizer's fresh-authorization requirement (e.g., updated KYC status, jurisdictional restriction, or accredited-investor gating for the new fundraising round). This is a real, in-scope logic flaw in the crowdloan pallet's signature verification, not a node/governance/privileged-only issue.

## Likelihood Explanation
The exploit requires no privileged access and no cryptographic forgery — only replaying a previously observed, valid, publicly-visible extrinsic. Required conditions are realistic: (1) a verifier-gated fund exists for a `ParaId`; (2) a contributor makes a first contribution (`old_balance == 0`), and the extrinsic (including its signature) becomes public on-chain; (3) the fund is dissolved once `raised` returns to zero (a normal, permissionless outcome after `refund` for an unsuccessful/expired crowdloan, dissolvable by the depositor or by anyone after `fund.end`); (4) a new fund is later created for the same `ParaId` (plausible for repeated crowdloan attempts for the same parachain across lease periods/auctions). The attacker is simply the original contributor resubmitting their own old signed extrinsic, which is fully attacker-controlled and requires no victim mistake beyond the organizer's assumption that verifier signatures are single-use per fund lifecycle.

## Recommendation
Bind the signed payload to the specific fund instance by including `fund.fund_index` (or another value unique per fund lifetime, e.g., a nonce incremented per fund) in the payload, e.g., `(fund.fund_index, index, &who, old_balance, value)`, so that signatures cannot be replayed across dissolve/recreate cycles for the same `ParaId`.

## Proof of Concept
1. `create` fund `F1` for `ParaId(1)` with `verifier = Some(pubkey)`.
2. Verifier signs payload `(ParaId(1), who=1, old_balance=0, value=100)` → `sig`.
3. `contribute(who=1, index=1, value=100, Some(sig))` succeeds; `Contributed` event emitted; extrinsic and `sig` are now public.
4. `refund` the fund (contribution removed, `raised` returns to `0`), then `dissolve(index=1)` (removes the `Funds` entry; `fund_index` counter has already advanced from `create`'s `NextFundIndex` logic).
5. `create` a new fund `F2` for the same `ParaId(1)` (fresh `fund_index`, fresh empty child-trie).
6. Call `contribute(who=1, index=1, value=100, Some(sig))` reusing the same `sig` from step 2, with no new signing.
7. Because `old_balance` in `F2`'s child-trie is `0` (matching the signed payload) and `index`/`who`/`value` are unchanged, `signature.verify` succeeds and the contribution is accepted — demonstrating the signature replay across fund lifecycles for the same `ParaId`.
