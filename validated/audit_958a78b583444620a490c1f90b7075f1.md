Audit Report

## Title
Response cache key omits `WorkflowID`, causing cross-workflow HTTP response confusion in the CRE HTTP gateway's outbound-action cache - (File: `core/services/gateway/handlers/capabilities/v2/response_cache.go`)

## Summary
`responseCache.Fetch` and `responseCache.Set` key cached HTTP action responses solely by `OutboundHTTPRequest.Hash()`, which is computed from method, URL, headers, body, and `WorkflowOwner` — but not `WorkflowID`. This contradicts the package's own documented "Workflow Isolation" guarantee and allows two distinct workflows owned by the same address to transparently share cached HTTP responses when they issue requests with identical method/URL/headers/body.

## Finding Description
The cache lookup in `responseCache.Fetch` uses `req.Hash()` as the sole key: [1](#0-0) , and `Set` stores under the same key: [2](#0-1) . This is invoked directly in the HTTP action request-handling path for any workflow node's outbound request: [3](#0-2) .

The package README explicitly documents that cache entries are "scoped by workflow ID to prevent cross-workflow data leakage" and that the cache key is "Generated from workflow ID and request hash": [4](#0-3) . However, the shipped test suite directly disproves this: a dedicated subtest named "having different workflowID results in same Hash" asserts `hash1 == hash2` for requests differing only in `WorkflowID`: [5](#0-4) , while a separate subtest confirms `WorkflowOwner` is the actual (coarser) differentiator: [6](#0-5) .

No other check in `Fetch`, `Set`, or the calling code in `http_handler.go` reintroduces per-workflow scoping — the cache map is a flat `map[string]*cachedResponse` keyed only by this hash: [7](#0-6) .

## Impact Explanation
An owner (single onboarded address) running two or more distinct workflows that issue outbound HTTP Action requests with identical method/URL/headers/body will have one workflow's cached response transparently served to another workflow, in direct violation of the documented workflow-isolation invariant. This is a concrete cross-workflow response confusion/data leakage within the CRE HTTP gateway's caching layer — the response an unrelated workflow consumes (and potentially feeds into consensus aggregation) is not the one it requested, but a stale or foreign one cached by a sibling workflow under the same owner.

## Likelihood Explanation
This is directly reachable by any unprivileged, onboarded workflow owner through the standard HTTP Action capability flow with `CacheSettings.MaxAgeMs > 0` / `Store: true` — a normal, non-adversarial configuration (e.g., two workflows hitting the same third-party API with a shared template). No authentication bypass, host access, or privileged role is required; only that two workflows under one owner produce identical request hashes.

## Recommendation
Include `WorkflowID` in the `Hash()` computation used to key `responseCache` entries, so that cache entries are truly scoped per-workflow as documented, and update `TestRequestHash` to assert that different `WorkflowID`s produce different hashes instead of asserting equality.

## Proof of Concept
1. Workflow A (owner `X`, `WorkflowID=wf-A`) issues `GET https://api.example.com/data` with `CacheSettings{Store:true, MaxAgeMs:60000}`; `responseCache.Fetch` executes the request and stores it under `req.Hash()` (independent of `wf-A`).
2. Workflow B (same owner `X`, `WorkflowID=wf-B`) issues the identical `GET https://api.example.com/data` with `CacheSettings.MaxAgeMs>0` within the TTL window.
3. `responseCache.Fetch` for workflow B computes the same `cacheKey` as workflow A (per `TestRequestHash`'s "having different workflowID results in same Hash" case) and returns workflow A's cached response instead of executing workflow B's own request — reproducible directly via the existing unit test in `response_cache_test.go` lines 139-149, plus an integration test exercising two `Fetch` calls with different `WorkflowID` but identical method/URL/headers/body/owner and asserting the second call returns the first's cached response.

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}
