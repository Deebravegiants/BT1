### Title
Webhook shop-domain header is trusted for tenant routing despite not being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature that `Utils::HmacValidator` verifies only covers the raw request body, never the headers. `Registry.process` treats a successful HMAC check as proof of authenticity for the whole request and then hands `request.shop` straight to the app's webhook handler, so the tenant identity is trusted without being bound to what was actually signed.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `HmacValidator.validate_signature` computes/compares the HMAC exclusively over that signable string: [2](#0-1) 

`Request#shop`, however, is pulled from the `shop-domain` header, which is not part of `to_signable_string`: [3](#0-2) 

`Registry.process` only checks the HMAC before dispatching, and then constructs the metadata (including `shop`) passed to the app's handler purely from the request object: [4](#0-3) 

Because the `api_secret_key` used to sign webhooks is the single shared secret for the whole app (identical for every shop that installs it), any shop that has legitimately installed the app receives real webhooks with a valid HMAC for its own body. That same body + HMAC pair remains valid no matter what the accompanying `shop-domain` header says, since the header is never part of the signed material. An attacker who controls one tenant (their own shop, a legitimate app install) can therefore replay one of their own genuinely-signed webhook deliveries to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still returns `true` (the body/secret pair matches), and `Registry.process` invokes the handler with `WebhookMetadata#shop` set to the victim's domain while the body content is the attacker's own data.

This breaks the intended binding:
`shop header used for tenant routing` == `shop cryptographically bound inside the HMAC-signed payload`

which does not hold here, since the equality is never enforced — the header is unauthenticated relative to the signature.

### Impact Explanation
Any handler that uses `WebhookMetadata#shop` to look up a session/access token, write data, or trigger shop-scoped side effects can be made to act on/inject data for a shop the attacker does not control, using only data derived from their own legitimate app install. This is a cross-tenant confusion vulnerability directly enabled by the gem's webhook verification design (the identity field is not covered by the same signature that authenticates the payload), matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation only requires the attacker to be a real, unprivileged merchant who has installed the target app (a normal, low-privilege position for anyone able to install a public/embedded Shopify app), then replay one of their own webhook deliveries with a modified shop header to the app's public webhook endpoint. No access to the app's `api_secret_key`, access tokens, or any other merchant's credentials is required.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed material, or otherwise cryptographically bind the header-derived `shop` value to the signed body before it is trusted for routing/tenant identification in `Registry.process`. At minimum, `Request#to_signable_string` should incorporate the shop domain so `HmacValidator.validate` fails when the header is altered independently of the body.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com` and receives a legitimate webhook delivery: body `B`, header `X-Shopify-Shop-Domain: attacker.myshopify.com`, header `X-Shopify-Hmac-Sha256: H` (computed by Shopify using the app's shared `api_secret_key` over `B`).
2. Attacker resends the exact same body `B` and the exact same `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the request; `Utils::HmacValidator.validate` recomputes the HMAC over `B` (the header is irrelevant to `to_signable_string`) and it matches `H`, so validation succeeds.
4. `Registry.process` dispatches to the registered handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled data under the victim shop's identity.
