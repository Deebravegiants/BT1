### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature validated by `Utils::HmacValidator` proves nothing about the `x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`, or `x-shopify-api-version` headers. `Webhooks::Registry.process` nonetheless passes the unauthenticated `shop` header straight into the handler as the tenant identity. Any party who can obtain one valid `(body, hmac)` pair signed with the app's secret (e.g. by triggering a webhook on their own shop where the app is installed) can replay that exact body/HMAC combination while substituting an arbitrary victim `shop` header, causing the host application to process the payload as if it originated from a different, unrelated merchant.

### Finding Description
The webhook signature verification chain is: [1](#0-0) 

`hmac` is read from the `hmac-sha256` header and `to_signable_string` returns `@raw_body` — nothing else. `Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the received HMAC: [2](#0-1) 

`Registry.process` calls this validator and, if it passes, immediately trusts `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` — none of which are part of the signed bytes — to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

The identity binding the gem is supposed to enforce is:
`HMAC-verified bytes == bytes used to establish tenant/shop identity`

In reality the equality is:
`HMAC-verified bytes == raw_body only` ≠ `shop header trusted for tenant identity`

Because the `shop` header sits entirely outside the signed payload, it is fully attacker-controllable independent of HMAC validity, as long as the attacker supplies *some* `(body, hmac)` pair that is valid for the shared `api_secret_key`. This is straightforward for any developer/merchant who has the app installed on their own store — they legitimately receive real webhook deliveries (valid body + valid HMAC) and can then replay that exact `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while swapping in a victim shop's domain in `x-shopify-shop-domain`.

### Impact Explanation
This breaks the tenant boundary the gem is expected to preserve: `Registry.process` will successfully validate ("Invalid webhook HMAC" is not raised) and dispatch the payload to the handler tagged with an attacker-chosen `shop`, even though that shop never sent or authorized the event. Any host application that uses `WebhookMetadata#shop` to select which merchant's records to update (a standard, documented usage per `docs/usage/webhooks.md`) can be made to write/act on data under the wrong tenant — a cross-tenant integrity/confidentiality violation driven entirely by this gem's failure to bind the `shop` field to the HMAC it validates.

### Likelihood Explanation
Exploitation only requires an attacker to have (or obtain) one legitimate `(raw_body, hmac-sha256)` pair produced by the target app's own `api_secret_key` — e.g. by installing the app on their own shop and capturing one of their own webhook deliveries. No knowledge of `api_secret_key` itself, no access token, and no privileged account beyond ordinary app installation is required, and the header substitution can be done with a simple HTTP replay.

### Recommendation
Include the header fields the application relies on for identity (`shop`, `topic`, `api_version`, `webhook_id`) in the HMAC-signable content, or otherwise cryptographically bind them (e.g., verify the `shop` value against a registration/subscription record fetched via an authenticated GraphQL call keyed by `webhook_id`) before exposing them through `WebhookMetadata`. At minimum, `docs/usage/webhooks.md` and the `Request`/`Registry` API should explicitly warn integrators that only the raw body is HMAC-verified and that `shop`/`topic`/`webhook_id` headers must not be trusted for tenant selection without additional server-side verification (e.g., cross-checking against `Registry.get_webhook_id` results or a stored shop/webhook mapping).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and receives a legitimate webhook delivery, capturing:
   - `raw_body = '{"id":123,...}'`
   - `x-shopify-hmac-sha256 = <valid HMAC of raw_body with the app's api_secret_key>`
2. Attacker POSTs to the app's webhook endpoint with the same `raw_body` and same `x-shopify-hmac-sha256`, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `Registry.process` computes:
   ```ruby
   Utils::HmacValidator.validate(request) # => true, because only raw_body is signed
   ``` [4](#0-3) 
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: <attacker's captured body> ...)`, causing the host app to process attacker-controlled data as if it belongs to `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
