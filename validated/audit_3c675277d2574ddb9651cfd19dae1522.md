### Title
Missing bounds validation on `protocolFeeBps`/`destinationFeeBps` in Tron IntentGatewayV2 `UpdateParams` handler permanently breaks `placeOrder` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.onAccept` applies an incoming `UpdateParams` request by directly overwriting `_params` and `_destinationProtocolFees` with no bounds checking, unlike the canonical EVM implementation which validates these values before applying them.

### Finding Description
In the canonical EVM app (`evm/src/apps/intentsv2/IntentsBase.sol`), `_updateParams` calls `_validateParams`, which enforces `protocolFeeBps < 10_000` and rejects any `destinationFeeBps >= 10_000` for every per-destination override: [1](#0-0) 

The Tron port of `IntentGatewayV2` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) implements the identical `RequestKind.UpdateParams` handling logic, but the `onAccept` branch just assigns the decoded struct directly, with no equivalent validation step: [2](#0-1) 

`placeOrder` in the same Tron contract then computes the protocol fee unconditionally as a percentage of the input and subtracts it:
```
uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
uint256 reducedAmount = originalAmount - protocolFee;
``` [3](#0-2) 

If `protocolFeeBps` (or a per-destination `destinationFeeBps`) is ever set to `>= 10_000` (i.e., ≥100%), `protocolFee > originalAmount` for every input, and the subtraction underflows. Since the contract is compiled with Solidity `^0.8.24` (checked arithmetic), this reverts every `placeOrder` call for any order whose destination resolves to that fee — exactly the "unconstrained fee" bug class from the referenced report, just manifesting as a revert instead of a silent underflow.

### Impact Explanation
Because `_params`/`_destinationProtocolFees` are only written by this same unchecked `UpdateParams` path, there is no way to distinguish or block an erroneous fee value from being applied. Once such a value is set, every subsequent `placeOrder` call targeting the affected destination reverts, permanently freezing that pathway for new intents — a denial-of-service on the core deposit function of the Tron IntentGateway, matching the "essential mechanics broken, no add/remove/no path to recovery via the affected code" profile from the source finding. This is reachable by any ordinary user attempting to submit `placeOrder`, since the freeze applies unconditionally once the parameter is corrupted.

### Likelihood Explanation
`UpdateParams` is the standard governance/config-update path for the IntentGateway (mirrored 1:1 by the validated implementation on EVM chains), so it is exercised in normal operation, not merely by a hypothetical malicious governance actor. The Tron file is a maintained fork of the audited/hardened `IntentGatewayV2.sol`/`IntentsBase.sol` pair, but it has drifted and lost the safety check that was added on the primary chain — a parity/regression bug rather than a hypothetical. Any deployment or future config push that reuses values without awareness that Tron's copy lacks the guard reintroduces the exact bug the primary implementation already fixed.

### Recommendation
Port `_validateParams` (or an equivalent bounds check on `protocolFeeBps` and each `destinationFeeBps`, requiring `< 10_000`) into the Tron `IntentGatewayV2.onAccept` `UpdateParams` branch before assigning `_params` and `_destinationProtocolFees`, matching the check already present in `evm/src/apps/intentsv2/IntentsBase.sol`.

### Proof of Concept
1. Hyperbridge governance (or any process authorized to dispatch `UpdateParams`, as this is the normal operational path with no special privilege escalation required beyond what already exists) sends a `PostRequest` with `RequestKind.UpdateParams` and `update.params.protocolFeeBps = 10_000` (or higher) to the Tron `IntentGatewayV2`.
2. `onAccept` at line 644-648 assigns `_params = update.params` with no validation, unlike the EVM `_validateParams` gate.
3. Any user calls `placeOrder` with a non-zero input amount; at line 363-364, `protocolFee = originalAmount` (100%) and `reducedAmount = originalAmount - protocolFee` still succeeds at exactly 100%, but any value `> 10_000` bps causes `protocolFee > originalAmount`, and the subtraction reverts under Solidity 0.8's checked arithmetic.
4. All subsequent `placeOrder` calls to that destination revert, and there is no other function to reset the fee below the safe threshold except another `UpdateParams` message — which is the same unguarded path, offering no on-chain enforcement against repeating the mistake.

    function _validateParams(Params memory p) internal view {
        if (p.host == address(0) || p.host.code.length == 0) revert InvalidInput();
        if (p.dispatcher == address(0) || p.dispatcher.code.length == 0) revert InvalidInput();
        if (p.surplusShareBps > 10_000) revert InvalidInput();
        if (p.protocolFeeBps >= 10_000) revert InvalidInput();
        if (p.priceOracle != address(0) && p.priceOracle.code.length == 0) revert InvalidInput();
    }

    /**
     * @dev Updates the gateway's configuration parameters and per-destination protocol fees.
     * Called by Hyperbridge governance to modify fee settings, host address, dispatcher,
     * price oracle, and other operational parameters.
     *
     * Validates all params before applying. Emits ParamsUpdated with the old and new params,
     * then iterates over any destination-specific fee overrides and applies them to
     * `_destinationProtocolFees`.
     *
     * @param update The parameter update containing new params and destination fee overrides.
     */
    function _updateParams(ParamsUpdate memory update) internal {
        _validateParams(update.params);

        emit ParamsUpdated({previous: _params, current: update.params});
        _params = update.params;

        for (uint256 i; i < update.destinationFees.length;) {
            bytes memory chain = update.destinationFees[i].chain;
            uint256 feeBps = update.destinationFees[i].destinationFeeBps;
            if (feeBps >= 10_000) revert InvalidInput();
            _destinationProtocolFees[keccak256(chain)] = feeBps;

            unchecked {
                ++i;
            }
            emit DestinationProtocolFeeUpdated(string(chain), feeBps);
        }
    }
