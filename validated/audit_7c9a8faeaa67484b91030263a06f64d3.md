This confirms the root cause: `to_signable_string` in `lib/shopify_api/webhooks/request.rb:36-38` returns only `@raw_body`, so the HMAC computed in `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:27-31`) covers exclusively the request body bytes. The `shop`, `topic`, `webhook_id`, and `api_version` fields are pulled directly from HTTP headers via `shopify_header` in `lib/shopify_api/webhooks/request.rb:67-70` and are never part of the signed material.

`Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) validates only the HMAC over the body, then trusts `request.shop` unconditionally when constructing `WebhookMetadata` handed to the host app's handler — the tenant identity is taken from an unauthenticated header while only the body content is cryptographically bound.

### Title
Webhook shop-domain header is not covered by HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw body, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers with no binding to the HMAC. `Registry.process` accepts any HMAC-valid body and forwards the caller-supplied `shop` header to the app's webhook handler unchecked, breaking the identity binding `shop_verified_by_hmac == shop_delivered_to_handler`.

### Finding Description
`HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:27-31`) computes `HMAC(secret, signable_string)` and compares it to the `hmac` header. `signable_string` for a webhook is defined as just `@raw_body` (`lib/shopify_api/webhooks/request.rb:36-38`). The `shop` accessor (`lib/shopify_api/webhooks/request.rb:20-23`) reads the `shopify-shop-domain`/`x-shopify-shop-domain` header directly, with no cryptographic tie to the signature.

`Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) does:
```
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))
```
Any request whose body+hmac pair is valid for the app's secret will pass validation regardless of what `shop-domain` header is attached, and that attacker-chosen `shop` value is what gets delivered to the host application's business logic (e.g., to look up which merchant record to update).

Because installing a Shopify app on one's own store is unprivileged (any internet user can install a public/dev app), an attacker can legitimately receive genuine `(raw_body, hmac)` pairs for their own shop's webhooks, then replay that exact body/HMAC to the app's webhook endpoint while substituting the `shop-domain` (and `topic`/`webhook-id`) headers to impersonate a different, victim shop. `HmacValidator` still validates because it never inspected those headers, and `Registry.process` will invoke the handler believing the payload originated from the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: data that is cryptographically authenticated as coming "from Shopify" (valid HMAC) can be attributed to an arbitrary shop of the attacker's choosing, since the shop identity is never part of the signed bytes. Any host application that trusts `WebhookMetadata#shop` to select which merchant's records to mutate (e.g., processing `app/uninstalled`, `shop/update`, order/customer topics) can be tricked into applying attacker-controlled data under a victim shop's identity — a cross-tenant access/data-poisoning primitive.

### Likelihood Explanation
Requires the attacker to install the target app on a shop they control (unprivileged, self-service in Shopify's ecosystem) to harvest one valid `(body, hmac)` pair per topic, then a single crafted POST to the app's public webhook endpoint with forged headers. No access to `api_secret_key` or any merchant's access token is needed.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the signed material, or otherwise cryptographically bind `request.shop` to the HMAC before trusting it — e.g., validate that the `shop-domain` header matches an expected/registered shop for that HMAC-body pairing, or require host apps to cross-check `request.shop` against session/install records before acting, and document this gap prominently since `to_signable_string` currently omits all headers.

# Attacker replays the exact body + hmac against the app's public webhook endpoint,
# but forges the shop-domain header to claim it's from the victim shop:

ShopifyAPI::Webhooks::Registry.process(request)

# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body, ...))
