### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The library's webhook HMAC verification computes the signature only over the raw request body, while the `shop` field that downstream handler code uses to identify the tenant is read from an unauthenticated HTTP header. This breaks the identity binding `shop verified-by-HMAC == shop acted-on-by-handler`, mirroring the reported bug class of "a field acted on but not covered by the HMAC."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the signature over exactly that signable string and compares it against the `hmac-sha256` header: [2](#0-1) 

`Request#shop`, however, is pulled straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never part of `to_signable_string` and therefore never covered by the HMAC: [3](#0-2) [4](#0-3) 

`Registry.process` validates the HMAC over the body, then forwards `request.shop` — the unauthenticated header value — into `WebhookMetadata`, which is passed to the host application's handler as the tenant identity: [5](#0-4) [6](#0-5) 

Because only the body bytes are authenticated, an attacker who can obtain one valid `(raw_body, hmac)` pair signed with the app's shared secret for *any* shop (e.g. by installing the app on a shop they control and capturing the webhook Shopify sends them) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary value in the `x-shopify-shop-domain` header. `HmacValidator.validate` will still pass because it never inspects the header, and `Registry.process` will invoke `handler.handle` with `WebhookMetadata#shop` set to the attacker-chosen shop instead of the shop the body actually originated from.

### Impact Explanation
Host applications built on this gem are documented to trust `WebhookMetadata#shop` as the tenant key for locating/mutating merchant data (sessions, orders, product records, uninstall processing, GDPR data-erasure webhooks, etc.). Since the shop identity is not bound to the HMAC-verified bytes, an attacker who owns even one shop that installs the target app can forge webhook deliveries "as" a different shop, letting them inject attacker-controlled but validly-signed data into another tenant's data path — a cross-tenant access/data-integrity break rooted entirely in this gem's verification logic.

### Likelihood Explanation
Exploitation only requires being an unprivileged internet user who can install the app on a shop they control (a normal, low-privilege action) to obtain one legitimately-signed `(body, hmac)` pair, then send a crafted HTTP request with the same body/HMAC but a different `shop-domain` header directly to the app's public webhook endpoint. No access to `api_secret_key`, tokens, or Shopify infrastructure is required, making this readily reachable by an external attacker.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-signed material, or otherwise cryptographically bind `Request#shop` to the verified payload before constructing `WebhookMetadata`, so that `HmacValidator.validate` fails whenever the `shop-domain` header does not correspond to the shop that actually produced the signed body.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com`; trigger any webhook topic the app subscribes to and capture the raw POST body plus its `x-shopify-hmac-sha256` header (both are valid, since the signature only depends on the body and the shared `api_secret_key`).
2. Send a new HTTP request to the app's webhook endpoint with the identical body and `x-shopify-hmac-sha256` header, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `@raw_body` against the HMAC (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host application to process attacker-controlled webhook content under the victim shop's identity.
