The webhook handling path in this gem breaks an identity binding matching the reported bug class: the `shop` field used to route/attribute webhook data is not covered by the HMAC signature that is used to authenticate the ingoing webhook request.

### Title
Webhook shop attribution not covered by HMAC signature allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the shop identity from the `x-shopify-shop-domain` (or `shopify-shop-domain`) HTTP header, while the HMAC signature verified by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then hands `request.shop` straight to the registered handler as the tenant identifier, without that value ever being bound by the signature that authenticates the request.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is read verbatim from an attacker-controllable HTTP header with no cryptographic binding to that value: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely from `to_signable_string` (the raw body) against `Context.api_secret_key`: [3](#0-2) 

`Webhooks::Registry.process` treats a passing HMAC check as full authentication of the request, then forwards `request.shop` (the unauthenticated header value) into `WebhookMetadata`, which the app's handler uses to attribute/act on the webhook: [4](#0-3) 

The broken identity binding, stated as an equality that the gem implicitly assumes but does not enforce:
`hmac_valid(raw_body, api_secret_key) == true` is treated as implying `request.shop == "the shop that this raw_body actually belongs to"`. In reality the HMAC only proves "this raw body was produced/known by holder of `api_secret_key`" — it says nothing about which shop the header claims the body belongs to.

An unprivileged holder of a genuine, signed webhook payload (e.g., obtained from their own store the app is installed on, since any merchant can install a public app and receive correctly-HMAC-signed webhooks for their own shop) can replay that exact raw body to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` still succeeds because it never inspects the header, and `Registry.process` calls the handler with `shop: <victim shop>`.

### Impact Explanation
This directly breaks a tenant boundary: an app's own webhook-processing handler (which typically looks up the victim's stored session/access token via `WebhookMetadata#shop` to act on their behalf, e.g., to fetch or mutate data, or to trigger uninstall/GDPR-type flows) executes with attacker-supplied body content while wrongly believing it originates from the victim shop. This is a cross-tenant access primitive per the impact classification (Critical: cross-tenant access) — the attacker forges a request that the host application will process as authentic data belonging to a different merchant.

### Likelihood Explanation
No secrets are required beyond something obtainable by any unprivileged actor: install the target app (or use a webhook endpoint the attacker's own shop legitimately received) to obtain one valid `(raw_body, hmac)` pair for any subscribed topic, then POST that same body to the app's public webhook endpoint with a forged shop-domain header. This requires no `client_secret`, no access token, and no privileged role — only the ability to send an HTTP request to the app's publicly reachable webhook URL, which is inherent to how webhook endpoints work.

### Recommendation
Bind the shop identity into the value verified by the HMAC, e.g., include the `shop-domain` header (and ideally `topic`/`webhook-id`) in `to_signable_string`, or independently verify that the `shop` header matches an expected/registered shop for the given `webhook_id`/subscription before dispatching to the handler. At minimum, document/require host apps to cross-check `request.shop` against their own webhook subscription registry rather than trusting the header outright.

### Proof of Concept
1. Register the app on `attacker-shop.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw POST body and its `x-shopify-hmac-sha256` value — both valid since they were computed by Shopify with the app's real `api_secret_key`.
2. Replay the exact same body and HMAC header to the app's webhook endpoint, but replace `x-shopify-shop-domain: attacker-shop.myshopify.com` with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds successfully; `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `raw_body`.
4. The handler executes with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, causing the app to process attacker-controlled data under the victim's tenant identity.
