### Title
Zero `tokensForLP` (or `ltFromPair`) permanently bricks `finalizeGraduation` via an uninitialized `pair.mint()` call - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding._prepareGraduationLiquidity` computes `tokensForLP` and `ltFromPair` by integer division with no floor/non-zero guard, and `_seedDirectMint`/`_routerDepositAndDispose` never validate that the amounts they hand to the HyperSwap pair are non-zero before minting. If either amount is/rounds to `0`, the resulting LP mint returns `liquidity == 0`, which `finalizeGraduation` then feeds straight into `LPLock.recordLock`, which explicitly reverts on a zero amount — permanently bricking that token in `Lifecycle.Graduating`.

### Finding Description
`_prepareGraduationLiquidity` computes the LP-bound amounts with plain integer division and no non-zero assertion: [1](#0-0) 

`tokensForLP = (ltFromPair * tokenReserve) / assetReserve` can round down to `0` whenever `ltFromPair` (the real LT raised, net of the launch-time virtual reserve) is small relative to `assetReserve`. This value, together with `ltFromPair`, is cached verbatim in `pendingGraduation[token]` at end of phase 1 and consumed unconditionally by phase 2: [2](#0-1) 

In phase 2, on the common "no LP minted yet" path, `_seedDirectMint` transfers whatever amounts were cached — including a possible `0` — straight to the pair and mints: [3](#0-2) 

With a first mint against a totally empty pair, minting with one side at `0` produces `liquidity == 0` (or reverts inside the pair depending on its guard). Either way, `finalizeGraduation` proceeds to hand that `0` straight to `LPLock.recordLock`: [4](#0-3) 

`LPLock.recordLock` explicitly rejects a zero amount: [5](#0-4) 

Because Solidity transactions revert atomically, this revert unwinds the entire `finalizeGraduation` call — the `lifecycle` flip to `Graduated`, `graduatedPair` write, and `delete $.pendingGraduation[tokenAddress]` never happen. The token is left permanently stuck in `Lifecycle.Graduating`: trading is frozen (`buy`/`sell` both revert `TokenIsGraduating` while graduating), and every subsequent call to `finalizeGraduation` recomputes the exact same cached `(tokensForLP, ltFromPair)` and fails identically — there is no retry path or admin recovery function. This is the same bug class as CVE-2016-4470: a value that should be validated/non-degenerate before being consumed downstream is allowed through unchecked, and the resulting malformed/zero state causes a hard failure (there, a kernel crash; here, a permanently reverting critical state-transition function) instead of being defused earlier.

The comment on `_swapBudget` (packages/contracts/src/Bonding.sol:1356-1378) shows the team is aware of, and has partially guarded against, a related "zero-sized `recordLock`" failure mode for the *hostile-pre-seed rebalance* path (regime 3) by reserving 1% of the swap budget so both deposit sides stay non-zero. That guard, however, only protects `_routerDepositAndDispose`'s router deposit; it does nothing for the much more common regime-1 "empty pair" path (`_seedDirectMint`), which has no equivalent non-zero check on `tokensForLP`/`ltFromPair` before calling `pair.mint`.

### Impact Explanation
Once bricked, all LT raised by the curve (`ltFromPair`) and the reserved 250M `LP_RESERVE` tokens (minus any already-burned `lpBurned`) are permanently parked inside `Bonding` with no code path to ever complete graduation, and the curve itself stays frozen (no buys/sells) forever. This is a permanent freezing of creator/trader funds — both the raised LT and the token supply meant to seed the LP become unrecoverable, matching the "permanent freezing of trader, creator, or LP funds" impact bar in the validation rules.

### Likelihood Explanation
The trigger requires only that `tokensForLP` (or, symmetrically, `ltFromPair`) round to zero at the moment phase 1 (`_enterGraduating`/`triggerGraduation`) fires — a pure integer-division edge case in `_prepareGraduationLiquidity` driven by the ratio of `ltFromPair` to `tokenReserve`/`assetReserve` at graduation time. Since `triggerGraduation` is permissionless and callable by anyone once `canGraduate` is true, and the USD/supply thresholds and the LT's `exchangeRate()` are both attacker/market-influenceable inputs to that ratio, an attacker (or even organic trading against a low-liquidity or extreme-exchange-rate LT) can engineer the reserves so this rounding-to-zero condition holds at the exact moment of the threshold-crossing buy or `triggerGraduation` call.

### Recommendation
In `_prepareGraduationLiquidity`, explicitly guard against `tokensForLP == 0` or `ltFromPair == 0` (e.g., revert with a dedicated error, or floor them to `1`) before caching the `PendingGraduation` snapshot, so a degenerate zero value can never be baked into phase 1's cache and consumed unconditionally by phase 2. Additionally, add an explicit non-zero check on both amounts inside `_seedDirectMint` before calling `pair.mint`, mirroring the defensive posture already taken for the `_routerDepositAndDispose` path via `_swapBudget`.

### Proof of Concept
Not runnable from the indexed context alone — reproducing the exact reserve ratio that drives `tokensForLP` (or `ltFromPair`) to `0` requires stepping through `_prepareGraduationLiquidity`'s arithmetic with a concrete `exchangeRate()`/reserve sequence in a Foundry test (e.g., a `MockBounceLeveragedToken` with an extreme `exchangeRate()` combined with a minimal `_ltGraduationTrigger()` buy), which is best driven interactively in `packages/contracts/test/TwoPhaseGraduation.t.sol` rather than derived purely from the indexed snippets.

    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }
