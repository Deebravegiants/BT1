### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header is trusted by the handler without being covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` authenticates the *body bytes* alone. The `shop-domain`, `topic`, `api-version`, and `webhook-id` values are read from unauthenticated HTTP headers and passed straight into `WebhookMetadata`, which the host app's `WebhookHandler#handle` uses to key its tenant-scoped logic. Nothing binds the `shop` field to the HMAC that "proves" the request is genuine, breaking the equality `shop-that-produced-the-valid-HMAC == shop-attributed-to-the-processed-event`.

### Finding Description
`Registry.process` only gates on the HMAC of the body: [1](#0-0) 

The HMAC is computed with `Utils::HmacValidator.validate_signature`, which hashes `verifiable_query.to_signable_string` with `Context.api_secret_key`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns `@raw_body` exclusively: [3](#0-2) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled directly from attacker-controllable HTTP headers with no cryptographic tie to the signature: [4](#0-3) 

These unauthenticated fields are then forwarded verbatim into `WebhookMetadata`, the struct the host application's handler uses to decide which tenant/shop the event belongs to: [1](#0-0) [5](#0-4) 

This is the same identity-binding class of bug as the referenced report: a value that is *acted on* (there, the cancelled signer's signature and address binding; here, the `shop` tenant identifier) is not the value that the cryptographic check actually covers (there, the malleable ECDSA bytes; here, the HMAC-signed body). An attacker who legitimately owns any single shop that has this app installed (an ordinary, unprivileged merchant — no `api_secret_key`, access token, or privileged account required) can:

1. Trigger (or simply record) any legitimate webhook delivery for their own shop, obtaining a body `B` and its correctly-computed `hmac-sha256` value `H` (both are visible to the shop owner since Shopify delivers webhooks over plain HTTP(S) POST to the app's public endpoint).
2. POST directly to the app's webhook endpoint with body `B`, HMAC header `H` (unchanged — HMAC validation still passes because it only checks `B`), but with `shopify-shop-domain` set to a victim shop's `myshopify.com` domain, and/or an arbitrary `shopify-webhook-id`/`shopify-topic`.
3. `Utils::HmacValidator.validate` returns `true` because it only ever checks `B` against `H`. `Registry.process` then dispatches `handler.handle(data: WebhookMetadata.new(topic: <attacker-chosen>, shop: <victim-shop>, body: parsed(B), ...))`.

The handler (host app code, but driven entirely by this gem's trusted `WebhookMetadata`) will act as though the event genuinely originated from the victim shop — e.g., updating the victim's app-side records, deleting installed data (`shop/redact`), or performing shop-specific side effects, based on data the attacker actually controls.

### Impact Explanation
This crosses a tenant boundary: an attacker with no privileged access to the app's secret key or any specific victim credential can make the library assert that an event body of their choosing belongs to an arbitrary shop. Any host handler that trusts `WebhookMetadata#shop` as an authenticated tenant identifier (the documented, intended usage pattern) is exposed to cross-tenant data corruption or forged mandatory-compliance webhooks (e.g. spoofing `customers/redact` or `shop/redact` against a victim). This matches the Critical "cross-tenant access" impact category, since the shop-to-body binding the handler relies on is not actually enforced by the gem.

### Likelihood Explanation
No secret, access token, or privileged account is required — the attacker only needs to be a normal merchant with the app installed (able to generate one legitimate HMAC/body pair) and network access to POST to the app's public webhook route, which by design is an unauthenticated internet-facing endpoint (that's the entire point of HMAC verification here). Reproducing a valid `(body, hmac)` pair is trivial via the attacker's own shop's real webhook traffic, so the only work is replaying it with a modified `shop-domain` (and optionally `webhook-id`/`topic`) header, which the gem does nothing to prevent.

### Recommendation
Bind the trusted request metadata into the HMAC-signed material, or otherwise cryptographically tie `shop`, `topic`, and `webhook_id` to the verified payload before they are trusted, e.g.:
- Include the `shop-domain` (and ideally `topic`/`webhook-id`) values in `to_signable_string`, matching them against a canonical signed representation, or
- After HMAC validation, cross-check `request.shop` against the session/shop that is expected to have triggered the topic/registration (e.g., compare with a known-installed shop store) before constructing `WebhookMetadata`, and document to consumers that these header-derived fields must not be treated as authenticated unless independently revalidated.

### Proof of Concept
1. Install the app on shop `attacker.myshopify.com`; capture (or trigger) a legitimate webhook delivery, e.g. `orders/create`, with body `B = "{}"` and header `shopify-hmac-sha256: H` (a valid Base64 HMAC-SHA256 of `B` under the app's `api_secret_key`, which the attacker can obtain simply by receiving their own webhook).
2. POST directly to the app's webhook receiver endpoint with:
   - `shopify-topic: shop/redact`
   - `shopify-hmac-sha256: H` (reused, unchanged)
   - `shopify-shop-domain: victim-shop.myshopify.com`
   - `shopify-webhook-id: <arbitrary>`
   - body `B`
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed and passed to `ShopifyAPI::Webhooks::Registry.process`.
4. `Utils::HmacValidator.validate(request)` returns `true` (validated in `lib/shopify_api/utils/hmac_validator.rb:26-31`, which only ever compares against `to_signable_string` = `B`).
5. `Registry.process` invokes the registered handler for `shop/redact` with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: "shop/redact", body: {}, ...)`, even though the request never actually originated from Shopify on behalf of that victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        sig { params(signable_string: String, secret: String).returns(String) }
        def compute_signature(signable_string, secret)

            secret,

          )
        end
