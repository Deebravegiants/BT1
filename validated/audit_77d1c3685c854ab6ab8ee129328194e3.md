Audit Report

## Title
Missing allowlist and rate-limiting enforcement on legacy `HandleLegacyUserMessage` path in `core/services/gateway/handlers/capabilities/handler.go`

## Summary
The `capabilities.handler.HandleLegacyUserMessage` function, reachable from `gateway.ProcessRequest` for any legacy DON-ID-keyed JSON-RPC request, contains a `// TODO: apply allowlist and rate-limiting here` comment followed only by a method-name check, with no actual allowlist or per-caller rate limiting before the request payload is broadcast to every node in the target DON. The only control present is a signature-validity check (`msg.Validate()` / `common.ValidatedRequestFromMessage`), which proves the message wasn't tampered with and recovers a signer address, but performs no authorization decision against that signer — any holder of an arbitrary ECDSA keypair can sign and send a well-formed request.

## Finding Description
`gateway.ProcessRequest` dispatches legacy (DON-ID-keyed) messages directly to `h.HandleLegacyUserMessage(ctx, msg, callback)` after only structural validation via `msg.Validate()` [1](#0-0) . `Message.Validate()` checks field lengths and recovers the signer from the signature (`ExtractSigner`), but does not check the signer against any allowlist or registry [2](#0-1) .

In `HandleLegacyUserMessage`, after payload decoding and staleness checks, the code has the TODO comment and only verifies `msg.Body.Method == MethodWebAPITrigger` before unconditionally forwarding the request to every DON member via `don.SendToNode` [3](#0-2) . The only rate limiter in this handler, `nodeRateLimiter`, is applied to node→gateway responses in `handleWebAPIOutgoingMessage`, not to the ingress path from clients [4](#0-3) . This confirms the exact code path and absence of control as claimed.

However, this legacy handler is not the only, and appears not to be the current, code path for web API triggers in this codebase. A newer `v2` package (`core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go`) implements `httpTriggerHandler.HandleUserTriggerRequest`, which explicitly performs `h.authorizeRequest` (workflow-scoped authorized-key check via `workflowMetadataHandler.Authorize`) and `h.checkRateLimit` (per-workflow rate limiting via `userRateLimiter.AllowErr`) before dispatching to DON nodes [5](#0-4) [6](#0-5) . This indicates the project is aware of, and has already solved, the exact control gap described in the TODO — via a parallel, newer implementation — while the older legacy handler with the TODO remains present, presumably for backward compatibility with older-style DON-ID-addressed requests.

I was not able to fully confirm within the available tool budget whether the legacy `capabilities` handler (with the TODO) is still registered/reachable in current production job/gateway configurations, or whether it is retained only for backward compatibility with DONs that have not migrated to the v2 authorization flow. `core/services/gateway/handler_factory.go` does reference the legacy `capabilities` package, so the code path is not dead code, but I could not verify the exact conditions (DON config / job spec) under which it is selected versus the v2 handler.

## Impact Explanation
If the legacy handler is reachable in a live deployment for a DON configured to use it, an unauthenticated-in-the-authorization-sense client (anyone able to produce a valid ECDSA signature, which requires no special privilege) could trigger `web_api_trigger` messages fanned out to every node of that DON without any allowlist or per-caller rate limit, matching the impact class of unauthorized workflow triggering / potential DoS via broadcast fan-out described in the report. This would map to the "unauthorized job run" / "allowlist bypass" impact category if reachable in practice.

## Likelihood Explanation
Likelihood is uncertain rather than clearly "High" as originally claimed, because the report does not establish whether the legacy handler is actually the active/default code path in current deployments versus the properly-authorized v2 `httpTriggerHandler`, which already implements the exact allowlist and rate-limiting controls that the TODO in the legacy handler describes as missing. Without confirming that a production DON is actually configured to route through the legacy `capabilities.handler` rather than v2, the claim of "High, directly reachable from the internet-facing gateway" is not fully substantiated — it may describe a superseded/legacy code path that is not used by current in-scope deployments.

## Recommendation
- Confirm whether any in-scope/production DON configuration still routes through `capabilities.handler.HandleLegacyUserMessage` rather than the v2 `httpTriggerHandler`.
- If the legacy path is still reachable, port the same allowlist (`Authorizer`/`workflowMetadataHandler.Authorize`-style) and rate-limiting (`userRateLimiter`/per-workflow) logic already implemented in `v2/http_trigger_handler.go` into `HandleLegacyUserMessage` before the `don.SendToNode` fan-out, resolving the TODO.
- If the legacy path is deprecated and unreachable in current configurations, remove it or gate it behind an explicit deprecation flag to eliminate the dead/vulnerable code path and its stale TODO.

## Proof of Concept
Not independently reproduced. The originally proposed PoC (send a well-formed `web_api_trigger` JSON-RPC request with a valid signature and non-zero timestamp to the gateway's legacy DON-ID endpoint, and observe fan-out to all DON members without allowlist/rate-limit checks) is consistent with the code as read: `gateway.ProcessRequest` → `HandleLegacyUserMessage` → unconditional `don.SendToNode` loop [1](#0-0) [3](#0-2) . Confirming real-world exploitability requires verifying, via a running node/DON configuration or integration test, that a target DON is actually wired to this legacy handler rather than the v2 authorized handler — this could not be established from static code search alone within the available tool budget.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageID) == 0 || len(m.Body.MessageID) > MessageIDMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageID, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonID) == 0 || len(m.Body.DonID) > MessageDonIDMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonID, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}

func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}

// resolveOrgID resolves the organization ID for owner, or returns "" if it can't be resolved
func (h *httpTriggerHandler) resolveOrgID(ctx context.Context, owner string) string {
	if h.orgResolver == nil {
		h.lggr.Warnw("OrgResolver is nil, continuing without an orgID", "workflowOwner", owner)
		return ""
	}
	orgID, err := h.orgResolver.Get(ctx, owner)
	if err != nil {
		h.lggr.Warnw("Failed to resolve organization ID, continuing without it", "workflowOwner", owner, "err", err)
		return ""
	}
	return orgID
}

func (h *httpTriggerHandler) checkRateLimit(ctx context.Context, workflowID, requestID string, callback handlers.Callback) error {
	workflowRef, found := h.workflowMetadataHandler.GetWorkflowReference(workflowID)
	if !found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "workflow reference not found", callback)
		return errors.New("workflow reference not found")
	}

	orgID := h.resolveOrgID(ctx, workflowRef.workflowOwner)
	ctx = contexts.WithCRE(ctx, contexts.CRE{Owner: workflowRef.workflowOwner, Org: orgID, Workflow: workflowID})
	if err := h.userRateLimiter.AllowErr(ctx); err != nil {
		lggr := logger.With(h.lggr, platform.KeyWorkflowID, workflowID, platform.KeyWorkflowOwner, workflowRef.workflowOwner, "requestID", requestID, "err", err)
		if errLimited, ok := errors.AsType[limits.ErrorRateLimited](err); ok {
			switch errLimited.Scope {
			case settings.ScopeWorkflow:
				lggr.Errorf("failed to start execution: per workflow rate limit exceeded")
				h.metrics.IncrementWorkflowThrottled(ctx, h.lggr)
			default:
				lggr.Errorf("failed to start execution: unexpected rate limit for scope %s", errLimited.Scope)
			}
			h.handleUserError(ctx, requestID, jsonrpc.ErrLimitExceeded, "rate limit exceeded", callback)
			return err
		}
		return fmt.Errorf("failed to check rate limit: %w", err)
	}
	return nil
}
