## Analysis

I found a concrete decimals-conversion bug in `convert_to_balance` that is directly analogous to the reported bug class (incorrect price/ratio arithmetic causing an incorrect minted/transferred amount, reachable by an unprivileged cross-chain message).

### Title
Incorrect ERC20-to-local decimals conversion in `convert_to_balance` silently mints/refunds the wrong amount when local decimals exceed ERC20 decimals - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`convert_to_balance` is supposed to rescale an ERC20 `U256` amount (posted from an EVM chain, at `erc_decimals` precision) down to the pallet's local asset precision (`local_decimals`). It always computes the scaling exponent as `erc_decimals.saturating_sub(local_decimals)` and always *divides* by `10^exponent`, silently assuming `erc_decimals >= local_decimals`. [1](#0-0) 

### Finding Description
`convert_to_balance` and `convert_to_erc20` both use `saturating_sub`:

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
``` [2](#0-1) 

When `local_decimals > erc_decimals` (e.g. an asset registered with 18 local decimals but bridged from an 8-decimal EVM ERC20, or 6 vs 18 the other direction than assumed), `erc_decimals.saturating_sub(local_decimals)` saturates to `0`, so the division becomes a no-op (`value / 10^0 = value`). The raw ERC20 integer is then interpreted directly as the local balance, which is off by a factor of `10^(local_decimals - erc_decimals)` — the same class of "denominator/scaling direction" error as the report's `stethPerEth` being multiplied instead of divided: the code silently assumes one direction of the decimals relationship and produces a badly wrong output magnitude instead of an error.

This function is invoked directly on `on_accept` (inbound cross-chain mint/transfer path, reachable by any relayer delivering a `PostRequest` whose body is attacker/user-controlled `Message.amount`) and on `on_timeout` (refund path):

```rust

    <T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(local_asset_id.clone())
};
let erc_decimals = Precisions::<T>::get(local_asset_id.clone(), source)
    .ok_or(HftError::DecimalsNotConfigured(source))?;
let amount = convert_to_balance::<...>(
    U256::from_big_endian(&message.amount.to_be_bytes::<32>()),
    erc_decimals,
    decimals,
).map_err(...)?;
...
<T as Config>::Assets::mint_into(local_asset_id, &beneficiary, amount.into())
``` [3](#0-2) 

`erc_decimals` here is a per-`(local_asset_id, source)` value set by an admin via `Precisions` storage (config, not attacker-controlled), so the bug does not require malicious governance — it is triggered purely by a legitimate configuration where the local asset's decimals exceed the source ERC20's decimals (a normal, foreseeable configuration, e.g. a Substrate asset minted at 18 decimals bridging a 6- or 8-decimal ERC20). Any message that crosses the bridge for such a pair is unconditionally mis-scaled — no malicious relayer or admin action needed to trigger the loss, only a plausible decimals configuration plus a normal user-submitted bridge message.

### Impact Explanation
If `local_decimals > erc_decimals` for a configured pair, every inbound mint/transfer (`on_accept`) and every timeout refund (`on_timeout`) computes `amount` as the *raw* ERC20 integer instead of the correctly rescaled-up amount, minting/crediting far less than intended (under-crediting by `10^(local_decimals - erc_decimals)`) while the source chain's escrow/burn already accounted for the full value — a permanent, protocol-level loss of funds for the bridging user, and a systemic accounting break for the asset (mismatched effective peg between the EVM and Substrate representations of the "same" token). This is a fund-loss/broken-accounting bug reachable from ordinary token-bridge usage, not a privileged action.

### Likelihood Explanation
High for any deployment where an admin configures a pair with `local_decimals > erc_decimals` (very plausible: Substrate assets are commonly created at 18 decimals in modern configs while the EVM ERC20 counterpart may use 6 or 8 decimals). No malicious actor is needed — the bug fires automatically and silently on every bridge message for such a pair, and there is no compensating check or test elsewhere in the pallet catching the saturating case (only the `erc_decimals >= local_decimals` direction is exercised in the comment and doc, "scale down from ERC20 precision").

### Recommendation
Do not assume a fixed direction. Compute the decimal difference as a signed value and either divide or multiply accordingly (mirroring `adjustDecimals`/`adjustDecimalsFloor` patterns already used elsewhere in the codebase, e.g. `sdk/packages/sdk/src/utils.ts`'s `adjustDecimals`):

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256,
    erc_decimals: u8,
    local_decimals: u8,
) -> Result<B, B::Err> {
    let scaled = if erc_decimals >= local_decimals {
        value / U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        value * U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    };
    scaled.to_string().parse::<B>()
}
```
and symmetrically fix `convert_to_erc20`. Add regression tests for both decimal-relationship directions (erc > local and erc < local), not just the currently-assumed one.

### Proof of Concept
1. Admin configures a bridged pair where the EVM ERC20 uses 6 decimals (`erc_decimals = 6`) and the local Substrate asset uses 18 decimals (`local_decimals = 18`), setting `Precisions::<T>::insert(asset_id, source, 6)`.
2. A user on the EVM side bridges `1_000_000` raw units (i.e. `1.0` token at 6 decimals) via the ERC20 contract; this is encoded as `message.amount = 1_000_000` in the `PostRequest` body.
3. On the Substrate side, `on_accept` computes `erc_decimals.saturating_sub(local_decimals) = 6.saturating_sub(18) = 0`, so `convert_to_balance` returns `1_000_000 / 10^0 = 1_000_000`.
4. The pallet mints `1_000_000` local-asset units to the beneficiary — but at 18 local decimals, `1_000_000` units is `0.000000000000000001` × `1_000_000` = a vanishingly small fraction of one whole token, instead of the intended `1_000_000 * 10^12 = 10^18` units (one whole token). The user's bridged value is destroyed (under-minted by `10^12`), a permanent loss of funds, purely from normal bridge usage with a plausible (18 local vs 6 ERC20) decimals configuration.
