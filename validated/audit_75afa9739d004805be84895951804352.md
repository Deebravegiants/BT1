### Title
Unprivileged accounts can grief any account's gas key by donating balance via `TransferToGasKey`, permanently blocking key/account deletion - (File: `runtime/runtime/src/access_keys.rs`)

### Summary
`action_transfer_to_gas_key` lets **any** predecessor account top up the balance of a `GasKeyInfo` attached to an arbitrary target account's public key, with no check that the caller owns or controls that account. `delete_gas_key` (used by both `DeleteKey` on a gas key and `DeleteAccount`) unconditionally rejects deletion once `gas_key_info.balance > GasKeyInfo::MAX_BALANCE_TO_BURN`. An attacker can therefore "donate" funds to push a victim's gas key balance above this threshold, after which the victim can never delete that key (or, if the account relies on it, the whole account), reproducing the WagmiLeverage pattern where an unprivileged, unsolicited balance donation broke a downstream exact/threshold check and caused a denial of service.

### Finding Description
`action_transfer_to_gas_key` only checks that the target `public_key` exists on `account_id` and is a gas key; it performs no authorization check tying the predecessor of the receipt to the account being funded: [1](#0-0) 

Because this is a normal action executed against `receipt.receiver_id()`, any signer can construct a transaction/receipt whose receiver is the victim account and whose action list contains `TransferToGasKey { public_key: <victim's known gas key>, deposit: <arbitrary> }`, exactly like anyone can send a plain `Transfer` to any account. The victim's gas-key public key is public on-chain data (queryable via access-key views), so it is always discoverable.

Later, when the victim (or the protocol, via account deletion) tries to remove that gas key, `delete_gas_key` enforces a hard ceiling: [2](#0-1) 

If `gas_key_info.balance > GasKeyInfo::MAX_BALANCE_TO_BURN`, the action fails with `ActionErrorKind::GasKeyBalanceTooHigh` instead of succeeding — this is the same class of bug as the report: a check that assumes the balance was only ever set by the account's own legitimate operations is subverted by an unrelated, attacker-controlled inbound "donation" performed before the legitimate operation executes.

This affects not only single-key deletion but also whole-account deletion, since account deletion sums all gas-key balances against the same `MAX_BALANCE_TO_BURN` threshold, as documented: [3](#0-2) 

### Impact Explanation
An unprivileged attacker can send a single cheap transaction to permanently prevent a victim from deleting a targeted gas key, and — if the gas key's balance dominates the account deletion path — from deleting their entire account. This is a griefing/denial-of-service vector reachable from any account with no special privilege, directly caused by protocol-level action-execution logic (not a user contract), and it produces a persistent, unauthorized state effect on the victim's account (an access key/account that cannot be cleaned up, contrary to the account owner's intent) purely because of unsolicited funds sent by a third party.

### Likelihood Explanation
Likelihood is moderate: the attacker needs only to know the victim's account id and the target public key (both are public), and the cost is bounded by however much above `MAX_BALANCE_TO_BURN` they choose to send (this value is burned, not returned to the attacker, but is cheap relative to the guaranteed, permanent griefing effect it causes on the victim, especially against high-value or automated accounts that periodically rotate/delete gas keys).

### Recommendation
Do not let inbound `TransferToGasKey` deposits alone determine whether a key can be deleted. Options include: (1) refunding/rejecting deposits that would push `gas_key_info.balance` above `MAX_BALANCE_TO_BURN` at `action_transfer_to_gas_key` time rather than only checking at deletion time, (2) allowing deletion of a gas key regardless of balance by refunding the balance (up to `MAX_BALANCE_TO_BURN`) to the account/predecessor instead of erroring out, or (3) requiring authorization (predecessor must equal `account_id`, or the action must be routed through the key owner) before crediting a gas key's balance.

### Proof of Concept
1. Victim account `victim.near` has an access key `pk_gas` configured as a gas key (`AccessKeyPermission::GasKey*`), balance `b < MAX_BALANCE_TO_BURN`.
2. Attacker (any unrelated account) submits a transaction with receiver `victim.near` and action `TransferToGasKey { public_key: pk_gas, deposit: MAX_BALANCE_TO_BURN - b + 1 }`. This succeeds in `action_transfer_to_gas_key` (no ownership check) and sets `gas_key_info.balance > MAX_BALANCE_TO_BURN`.
3. `victim.near` (or any relayer acting for it) later submits `DeleteKey { public_key: pk_gas }`. `delete_gas_key` now returns `ActionErrorKind::GasKeyBalanceTooHigh`, and the key can never be deleted while the balance exceeds the threshold.
4. If `victim.near` attempts `DeleteAccount`, the same threshold check (summed over gas keys, per `protocol-model/spec/accounts-keys.md:109`) blocks account deletion as well.

```rust
pub(crate) fn action_transfer_to_gas_key(
    state_update: &mut TrieUpdate,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &TransferToGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "gas key balance integer overflow".to_string(),
        ))
    })?;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
}
```
