## Title
`update_token` decimals reconfiguration corrupts in-flight cross-chain transfer amounts, causing unbacked mint or fund loss - (File: `modules/pallets/hyper-fungible-token/src/lib.rs`, `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token`'s `Precisions` storage (per `(AssetId, StateMachine)` EVM decimals) is read **live** at settlement time (`on_accept` / `on_timeout`) rather than being pinned to the value that was in effect when the corresponding `send` was originally dispatched. If `update_token` changes an existing chain's `decimals` while a message is in flight, the amount-scaling math on delivery/timeout uses a different scale factor than the one used to encode the amount on dispatch, corrupting the settled amount.

### Finding Description
`update_token` lets `CreateOrigin` add (or overwrite) a chain's `decimals` for an already-registered asset: [1](#0-0) 

This directly overwrites `Precisions::<T>::insert(asset_id, chain, config.decimals)` for a chain that may already have in-flight requests dispatched under the old decimals value.

`send` computes the outbound ERC20-scaled amount using the *current* `Precisions` value at dispatch time and embeds it in the ISMP request body: [2](#0-1) 

But `on_timeout` (refund path for that same outbound request) re-reads `Precisions` at **processing** time, not the value pinned at dispatch time, and uses it to convert the embedded ERC20 amount back to local balance: [3](#0-2) 

Likewise `on_accept` (inbound delivery from the EVM-side contract) reads `Precisions` at delivery time to interpret the incoming ERC20-scaled `message.amount`: [4](#0-3) 

`convert_to_balance` / `convert_to_erc20` scale using `10u128.pow(erc_decimals.saturating_sub(local_decimals))` (or the reverse), so any mismatch between the decimals used to *encode* an amount and the decimals used to *decode* it multiplies/divides the settled amount by an arbitrary power of 10: [5](#0-4) 

This is directly analogous to the reported `CrosschainDistributor._setToken` bug: an admin/governance action that mutates a stored config value (token address / decimals) is applied retroactively to already-outstanding accounting (`claimed` / in-flight escrowed amount), producing incorrect arithmetic against state that was computed under the old configuration. Here it's worse than the original report's simple revert — because `saturating_sub` prevents a panic, the pallet silently computes a wrong scaled amount instead of reverting, so mismatches can mint far more or far less than intended.

### Impact Explanation
- If decimals are decreased for a chain while an outbound `send` is pending timeout, `on_timeout`'s conversion divides by a smaller factor than was used to multiply on `send`, refunding the sender **far more** local balance than was escrowed/burned — an unbacked mint / over-refund out of the pallet's custody or via fresh minting for non-native assets.
- If decimals are increased, the refund divides by a much larger factor, permanently freezing the bulk of the user's original funds (the on-chain escrow/burn already happened; the refund credited is a fraction of what's owed).
- Symmetrically, on the `on_accept` inbound path, a decimals change between EVM-side dispatch and substrate-side delivery causes the pallet to mint (non-native) or release-from-escrow (native) an amount scaled by the wrong power of ten relative to what the EVM contract actually locked/burned, again producing unbacked mint or fund loss.

This satisfies "unbacked mint" / "permanent freezing of funds" impact criteria, triggered by a normal, non-malicious governance reconfiguration (e.g., correcting or updating a chain's registered ERC20 decimals) combined with any unprivileged user's `send` extrinsic that happens to be in flight at that moment.

### Likelihood Explanation
Any legitimate reason to call `update_token` (fixing a misconfigured `decimals` value, deploying a new contract version with different decimals, migrating a chain) while there are outstanding in-flight transfers (which can take a nontrivial time to finalize/timeout across chains) will trigger this. No malicious intent is required from the `CreateOrigin`; it's a race between an ordinary config update and any user's pending `send`. Given cross-chain finality windows are typically minutes to hours, the window for landing this race is realistic in production operation.

### Recommendation
Do not read `Precisions` live at settlement time. Either:
1. Pin the `erc_decimals` used for a given `send` into the request body / an auxiliary storage item keyed by the request commitment, and have `on_timeout` (and any settlement path) use that pinned value instead of the live `Precisions` lookup, or
2. Disallow overwriting `decimals` for a chain that already has a registered asset (only allow decimals to be set once, or require a dedicated migration path that first ensures no in-flight requests exist for that `(asset, chain)` pair before changing precision), mirroring the recommendation in the original report to convert stale state to the new precision before applying it, rather than blindly reusing storage from before the update.

### Proof of Concept
1. Register asset `X` (non-native) with chain `Evm(1)` at `decimals = 6`.
2. User calls `send` with `amount = 100 * 10^local_decimals`; pallet burns the local amount and encodes `erc20_amount = convert_to_erc20(100, 6, local_decimals)` into the dispatched `Message`, e.g. yielding a small ERC20-scaled value.
3. Before the request times out, `CreateOrigin` calls `update_token` with `add_chains` containing `Evm(1)` again but `decimals = 18` (e.g., correcting a genuine misconfiguration), overwriting `Precisions::<T>::insert(X, Evm(1), 18)`.
4. The request times out; `on_timeout` reads `Precisions::<T>::get(X, Evm(1))` == 18 (not the 6 used at dispatch) and calls `convert_to_balance(erc20_amount, 18, local_decimals)`, dividing by `10^(18-local_decimals)` instead of `10^(6-local_decimals)` — a mismatch of `10^12`, producing a refund that is either negligible (fund freeze) or, in the reverse decimals-change scenario, wildly inflated (unbacked mint), depending on the direction of the decimals change.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
