### Title
`Oauth.validate_auth_callback` uses the HMAC-verified but unsanitized `shop` domain to build the token-exchange request host — ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` takes the `shop` value from the caller-supplied `AuthQuery`, verifies it only via `Utils::HmacValidator.validate` (an HMAC computed over `code/host/shop/state/timestamp`), and then uses that raw `shop` string directly to build the `null_session` whose `shop` attribute becomes the HTTP host that receives the OAuth `code`, `client_id`, and `client_secret`.

### Finding Description
In `lib/shopify_api/auth/oauth.rb`, `validate_auth_callback` does: [1](#0-0) 
`null_session = Auth::Session.new(shop: auth_query.shop)` is passed straight to `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")`, and `HttpClient#initialize` builds the request host directly from `session.shop`: [2](#0-1) 

Unlike every other code path that turns caller/user input into the host used for a token request — `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`, which both call `Utils::ShopValidator.sanitize!(shop)` before constructing the session/host — `Oauth.validate_auth_callback` never calls `ShopValidator`: [3](#0-2) [4](#0-3) 

The only check applied to `auth_query.shop` is that it is one of the fields covered by the request HMAC: [5](#0-4) [6](#0-5) 

However, that HMAC is generated by Shopify's own OAuth redirect using the app's `client_secret`, and the value it signs is *whatever `shop` string Shopify put in the query string* — the gem never independently confirms this value is a well-formed `*.myshopify.com` (or otherwise trusted) domain. The `ShopValidator.sanitize!` trusted-domain allowlist exists precisely for this purpose elsewhere in the codebase: [7](#0-6) 

The binding this breaks (stated as an equality that should hold but doesn't): `shop authenticated-by-HMAC == shop validated-as-trusted-domain-used-as-request-host`. HMAC validity only proves the query was signed by an entity holding the secret; it does not prove the `shop` value is a legitimate/trusted API host. Because `ShopValidator.sanitize!` is applied everywhere else this trust boundary matters, its absence here is an inconsistency in this gem's own code, not a host-app misuse of a documented API.

### Impact Explanation
If Shopify's own callback (or any environment producing a HMAC-valid `AuthQuery`, e.g. a compromised/duplicated frontend, replay from a different context, or a testing/staging flow that reuses secrets) ever supplies a non-`myshopify.com` `shop` string, this code will send the OAuth authorization `code` together with the app's `client_id` and `client_secret` to `https://<attacker-controlled-shop-value>/admin/oauth/access_token` — i.e., SSRF carrying the app's `client_secret` and the authorization code to an arbitrary host. This matches the report's "High: SSRF with the app's credentials" impact class.

### Likelihood Explanation
Exploitability is constrained: an outside, unprivileged attacker cannot forge the HMAC without knowing `api_secret_key`, so this cannot be triggered purely by a malicious internet client crafting query parameters (unlike the webhook/HMAC bug class the report describes). It requires a scenario in which a validly-HMAC'd query string can carry an untrusted `shop` value (e.g., a shop-domain confusion/edge case not covered by the current allowlist, or if the app itself computes a matching signature in an internal replay/testing utility). This lowers likelihood significantly compared to a fully attacker-forgeable case, but the root cause — missing `ShopValidator.sanitize!` call before using `shop` as the outbound request host — is a genuine and demonstrable code defect distinct from any documented misuse by the host app.

### Recommendation
In `lib/shopify_api/auth/oauth.rb#validate_auth_callback`, after the HMAC check, sanitize `auth_query.shop` the same way `ClientCredentials` and `RefreshToken` do:
```ruby
validated_shop = Utils::ShopValidator.sanitize!(auth_query.shop)
null_session = Auth::Session.new(shop: validated_shop)
...
session = Session.from(shop: validated_shop, access_token_response: ...)
```
This ensures the value used to construct the outbound request host (and to receive `client_secret`) is confirmed to be a trusted Shopify domain, not merely "some string that was HMAC-signed."

### Proof of Concept
1. Construct an `AuthQuery` with `shop` set to a value that is not a genuine `myshopify.com` domain but for which a valid HMAC can be produced over `code/host/shop/state/timestamp` using the app's `api_secret_key` (this requires either secret compromise or a code path — e.g., an internal replay/test harness — that legitimately re-signs attacker-influenced data).
2. Call `ShopifyAPI::Auth::Oauth.validate_auth_callback(cookies:, auth_query:)`.
3. Observe that `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")` builds `@base_uri = "https://#{session.shop}"` from the unsanitized `shop`, per `lib/shopify_api/clients/http_client.rb` lines 16-19, and the POST containing `client_id`, `client_secret`, and `code` is sent to that host — with no `ShopValidator` check anywhere in `Oauth.validate_auth_callback`, unlike `ClientCredentials#client_credentials` and `RefreshToken#refresh_access_token`.
