### Title
Unvalidated `VirtualChain` route + unconditional "completed" status let `nep141:bch.omft.near` be `ft_withdraw`n to an arbitrary caller-named contract while `AuroraEngineBridge.describeWithdrawal` always reports success - (File: `packages/intents-sdk/src/bridges/aurora-engine-bridge/aurora-engine-bridge.ts`)

### Summary
`AuroraEngineBridge.supports()` accepts *any* `nep141:*` asset as long as `routeConfig.route === RouteEnum.VirtualChain`, with no check that the asset is actually redeemable through the caller-supplied `auroraEngineContractId`/`proxyTokenContractId`. Because `AuroraEngineBridge` is registered before `PoaBridge` in `IntentsSDK.bridges`, a `nep141:bch.omft.near` withdrawal routed with `createVirtualChainRoute(auroraEngineContractId, proxyTokenContractId)` is diverted from the real PoA custodian into an `ft_withdraw` intent whose `receiver_id` is the caller-named contract. `AuroraEngineBridge.describeWithdrawal()` then unconditionally returns `{status: "completed", txHash: null}`, so the SDK reports success regardless of what actually happened on-chain.

### Finding Description
The claimed equality: the bridge contract/chain named by the produced intent (`receiver_id` = `auroraEngineContractId` or `proxyTokenContractId`, msg encodes destination) must equal the real custodian of `nep141:bch.omft.near` (the PoA bridge) and the chain the caller actually intended.

Trace:
- `IntentsSDK.bridges` order places `AuroraEngineBridge` (VirtualChain) ahead of `PoaBridge`: [1](#0-0) 
- `createWithdrawalIntents` iterates bridges and picks the first one whose `supports()` resolves true: [2](#0-1) 
- `AuroraEngineBridge.supports()` only checks `routeConfig.route === VirtualChain` and `standard === "nep141"` — it never checks that the specific token (`bch.omft.near`) is redeemable via the supplied `auroraEngineContractId`/`proxyTokenContractId`: [3](#0-2) 
- `createWithdrawIntentPrimitive` builds `ft_withdraw` with `receiver_id` set directly from the caller-supplied `auroraEngineContractId`/`proxyTokenContractId`, and `msg` built purely from `destinationAddress`, with no cross-check against the token's actual bridge/custodian: [4](#0-3) 
- `validateWithdrawal()` for this bridge only checks that `destinationAddress` looks like an EVM address; it does not throw on token/contract mismatch: [5](#0-4) 
- `describeWithdrawal()` for this bridge is a hard-coded stub that always reports success, with no verification of the NEAR transaction, receipts, or destination-chain settlement: [6](#0-5) 

Contrast this with every other bridge, which verifies actual on-chain/off-chain settlement before reporting `completed`: `PoaBridge.describeWithdrawal` polls the PoA API and matches asset/status [7](#0-6) , `OmniBridge.describeWithdrawal` fetches transfer status and destination hash [8](#0-7) , and `HotBridge.describeWithdrawal` polls nonces and indexer hashes [9](#0-8) . Only `AuroraEngineBridge` skips this entirely.

Root cause: the SDK trusts `routeConfig` completely for `VirtualChain` withdrawals — neither `supports()` nor `validateWithdrawal()` nor `createWithdrawalIntents()` verifies that `assetId` is actually bridgeable through the named `auroraEngineContractId`/`proxyTokenContractId`, and no bridge throws to reject the mismatch; execution falls straight through to intent construction and signing. There is no allowlist of valid Aurora Engine contract IDs anywhere in the codebase (confirmed by grep for `VIRTUAL_CHAIN`/`AURORA_ENGINE` constants — none exist outside README prose).

### Impact Explanation
An integrator that forwards a counterparty/attacker-controlled `routeConfig` (`createVirtualChainRoute(auroraEngineContractId, proxyTokenContractId)`) together with `assetId: "nep141:bch.omft.near"` will have the SDK sign and publish an `ft_withdraw` intent whose `receiver_id` is that attacker-named NEAR account rather than the actual bch custodian, and whose `msg` encodes an attacker-chosen EVM address rather than a validated BCH destination. Because `describeWithdrawal()` for this route always returns `{status: "completed"}`, the integrator's `waitForWithdrawalCompletion`/`processWithdrawal` will report the withdrawal as successfully completed even if the tokens were misrouted, rejected by the target contract, or stuck. This matches: funds delivered to a wrong contract/chain with no recovery (Critical), and a status misreport that could cause an integrator to credit/refund a user based on a false "completed" signal (High). This is repeatable on every call for any `nep141` asset routed through `VirtualChain`.

### Likelihood Explanation
Preconditions: the caller (or an integrator blindly forwarding caller-supplied `routeConfig`) must choose `createVirtualChainRoute(auroraEngineContractId, proxyTokenContractId)` for an asset (e.g. `nep141:bch.omft.near`) that is not actually an Aurora-Engine-bridged asset. No special privilege is required — `routeConfig`, `assetId`, and `destinationAddress` are all attacker-controllable per the threat model. The SDK performs zero validation tying the asset to the named Aurora Engine contract, so the call succeeds and signs/publishes without any bridge throwing. This is entirely feasible via the public `processWithdrawal`/`createWithdrawalIntents`/`estimateWithdrawalFee` APIs.

### Recommendation
1. In `AuroraEngineBridge.supports()`/`validateWithdrawal()`, validate that `assetId` is actually associated with the given `auroraEngineContractId` (e.g., via an allowlist/registry mapping virtual chains to their supported base/proxy tokens) and throw if it isn't, rather than accepting any `nep141` token unconditionally.
2. Replace the `AuroraEngineBridge.describeWithdrawal()` stub with a real on-chain check (e.g., verify the `ft_withdraw` receipt succeeded, and where possible confirm the destination-chain deposit), following the pattern used by `PoaBridge`/`OmniBridge`/`HotBridge`.

```ts
// packages/intents-sdk/src/bridges/aurora-engine-bridge/aurora-engine-bridge.poc.test.ts
import { describe, it, expect } from "vitest";
import { configsByEnvironment } from "@defuse-protocol/internal-utils";
import { AuroraEngineBridge } from "./aurora-engine-bridge";
import { createVirtualChainRoute } from "../../lib/route-config-factory";

describe("PoC: route confusion for nep141:bch.omft.near", () => {
  it("supports() accepts a PoA-native BCH token under an attacker-named VirtualChain route", async () => {
    const bridge = new AuroraEngineBridge({
      envConfig: configsByEnvironment.production,
      nearProvider: {} as any,
    });

    const attackerContract = "attacker-controlled.near";
    const routeConfig = createVirtualChainRoute(attackerContract, null);

    // Equality under test: receiver named by produced intent must equal the real
    // custodian of nep141:bch.omft.near (the PoA bridge), not an arbitrary contract.
    await expect(
      bridge.supports({ assetId: "nep141:bch.omft.near", routeConfig }),
    ).resolves.toBe(true); // never throws -> no rejection of mismatch

    const intents = await bridge.createWithdrawalIntents({
      withdrawalParams: {
        assetId: "nep141:bch.omft.near",
        amount: 100000n,
        destinationAddress: "0x000000000000000000000000000000000000dEaD",
        feeInclusive: false,
        routeConfig,
      },
      feeEstimation: {
        amount: 0n,
        quote: null,
        underlyingFees: { virtual_chain: { storageDepositFee: 0n } },
      },
    });

    // receiver_id equals the attacker-supplied contract, NOT bch.omft.near's real custodian
    expect(intents[0]).toMatchObject({
      intent: "ft_withdraw",
      token: "bch.omft.near",
      receiver_id: attackerContract,
    });

    // describeWithdrawal always reports completed, regardless of what happened on-chain
    const status = await bridge.describeWithdrawal();
    expect(status).toEqual({ status: "completed", txHash: null });
  });
});
```

```typescript
export function createWithdrawIntentPrimitive(params: {
	assetId: string;
	auroraEngineContractId: string;
	proxyTokenContractId: string | null;
	destinationAddress: string;
	amount: bigint;
	storageDeposit: bigint;
}): IntentFtWithdraw {
	const { contractId: tokenAccountId, standard } = utils.parseDefuseAssetId(
		params.assetId,
	);
	assert(standard === "nep141", "Only NEP-141 is supported");

	// Most cases
	if (params.proxyTokenContractId == null) {
		return {
			intent: "ft_withdraw",
			token: tokenAccountId,
			receiver_id: params.auroraEngineContractId,
			amount: params.amount.toString(),
			msg: makeAuroraEngineDepositMsg(params.destinationAddress),
			storage_deposit:
				params.storageDeposit > 0n
					? params.storageDeposit.toString()
					: undefined,
			min_gas: MIN_GAS_AMOUNT,
		};
	}

	//  Flow for transferring a base token to a virtual chain with a non-standard (non-ETH) base token
	return {
		intent: "ft_withdraw",
		token: tokenAccountId,
		receiver_id: params.proxyTokenContractId,
		amount: params.amount.toString(),
		msg: `${params.auroraEngineContractId}:${makeAuroraEngineDepositMsg(params.destinationAddress)}`,
		storage_deposit:
			params.storageDeposit > 0n ? params.storageDeposit.toString() : undefined,
		min_gas: MIN_GAS_AMOUNT_NON_STANDARD_DECIMALS,
	};
}
```

```typescript
	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const transfer = (
			await this.omniBridgeAPI.getTransfer({
				transactionHash: args.tx.hash,
			})
		)[args.index];

		if (transfer == null || transfer.recipient == null) {
			return { status: "pending" };
		}

		const destinationChain = getChain(transfer.recipient as OmniAddress);
		let txHash = null;
		if (
			isEvmChain(destinationChain) ||
			destinationChain === ChainKind.Sol ||
			destinationChain === ChainKind.Fogo ||
			destinationChain === ChainKind.Strk ||
			destinationChain === ChainKind.Aptos
		) {
			txHash = transfer.finalised?.transaction_hash;
		} else if (isUtxoChain(destinationChain)) {
			// pending_sign_id is not the finalised tx hash. In rare cases, the hash may
			// change if the BTC transfer fails to be submitted. We return fast hash for FE and
			// wait for final one (transfer.finalised?.transaction_hash) for BE.
			txHash =
				typeof window !== "undefined"
					? transfer.utxo_meta?.pending_sign_id
					: transfer.finalised?.transaction_hash;
		} else {
			return { status: "completed", txHash: null };
		}

		if (!txHash) {
			return { status: "pending" };
		}

		return { status: "completed", txHash };
	}
```

```typescript
	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const cacheKey = this.getNoncesCacheKey(args.tx);
		const nonces = await this.noncesCache.fetch(cacheKey, { context: args.tx });
		if (nonces == null) {
			throw new HotWithdrawalNotFoundError(args.tx.hash, args.index);
		}

		const nonce = nonces[args.index];
		if (nonce == null) {
			throw new HotWithdrawalNotFoundError(args.tx.hash, args.index);
		}

		const status: unknown = await this.hotSdk.getGaslessWithdrawStatus(
			nonce.toString(),
		);
		// stop polling in case withdrawal is cancelled
		if (status === HotWithdrawStatus.Canceled) {
			return {
				status: "failed",
				reason: "Withdrawal was cancelled",
			};
		}

		const isEvm = args.landingChain.startsWith("eip155:");
		const isTon = args.landingChain === Chains.TON;
		// Bridge indexer is the source of truth for destination hashes on these chains.
		// TON does not fall back to HOT API hashes because they can refer to trace roots instead of CEX-visible transfers.
		if (isEvm || args.landingChain === Chains.Stellar || isTon) {
			try {
				args.logger?.info("Fetching withdrawal hash from bridge indexer", {
					nearTxHash: args.tx.hash,
					nonce: nonce.toString(),
				});
				const bridgeIndexerHash = await this.fetchWithdrawalHashBridgeIndexer(
					args.tx.hash,
					nonce.toString(),
					args.logger,
				);
				if (bridgeIndexerHash !== null) {
					args.logger?.info("Bridge indexer found withdrawal hash", {
						withdrawalHash: bridgeIndexerHash,
						nearTxHash: args.tx.hash,
						nonce: nonce.toString(),
					});
					return {
						status: "completed",
						txHash: bridgeIndexerHash,
					};
				}
			} catch (error) {
				if (isTon) {
					args.logger?.error(
						"Bridge indexer failed unexpectedly, keeping TON withdrawal pending",
						{
							nearTxHash: args.tx.hash,
							nonce: nonce.toString(),
							error,
						},
					);
					return { status: "pending" };
				}

				// Bridge indexer failed, fallback to HOT API
				args.logger?.error(
					"Bridge indexer failed unexpectedly, trying HOT API fallback",
					{
						nearTxHash: args.tx.hash,
						nonce: nonce.toString(),
						error,
					},
				);
				const apiHash = await this.fetchWithdrawalHashFromApi(
					args.tx.hash,
					nonce,
					args.logger,
				);
				if (apiHash != null) {
					args.logger?.info("HOT API fallback found withdrawal hash", {
						withdrawalHash: apiHash,
						nearTxHash: args.tx.hash,
						nonce: nonce.toString(),
					});
					return {
						status: "completed",
						txHash: formatTxHash(apiHash, args.landingChain),
					};
				}
			}
		} else {
			// Fallback for other non EVM networks
			// Primary source: contract view method
			if (status === HotWithdrawStatus.Completed) {
				return { status: "completed", txHash: null };
			}
			if (typeof status === "string") {
				// HOT returns hexified raw bytes without 0x prefix, any other value should be ignored.
				if (!isHex(status)) {
					args.logger?.warn(
						"HOT Bridge incorrect destination tx hash detected",
						{
							value: status,
						},
					);
					return { status: "completed", txHash: null };
				}
				return {
					status: "completed",
					txHash: formatTxHash(status, args.landingChain),
				};
			}

			// Fallback: API indexer (when contract returns null/pending)
			const apiHash = await this.fetchWithdrawalHashFromApi(
				args.tx.hash,
				nonce,
				args.logger,
			);
			if (apiHash != null) {
				return {
					status: "completed",
					txHash: formatTxHash(apiHash, args.landingChain),
				};
			}
		}

		return { status: "pending" };
	}
```
