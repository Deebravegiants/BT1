### Title
Accrued market-value overflow permanently freezes repayment, withdrawal, and liquidation - (File: common/src/rates/simulate.rs)

### Summary
`accrue_step` converts total scaled debt and supply back to RAY-denominated asset values before calculating utilization, and `scaled_to_original` panics when that representable value exceeds `i128::MAX`. [1](#0-0) [2](#0-1) 

### Finding Description
`scaled_to_original` computes `scaled * index / RAY` through `Ray::mul`; intermediate arithmetic is widened to `I256`, but a result larger than `i128::MAX` returns `None` from `to_i128` and is converted into `MathOverflow`. [3](#0-2) [4](#0-3) 

This boundary is separate from `MAX_BORROW_INDEX_RAY`: the index cap is applied only after `borrowed_original` has already been calculated, so a sufficiently large `borrowed` position can overflow while `borrow_index` remains below the configured cap. [5](#0-4) [6](#0-5) 

Every pool position leg first loads a synced market through `load_leg`, which invokes `interest::global_sync`. [7](#0-6)  Consequently, once the stored scaled balances and index cross the representable-value boundary, `repay`, `withdraw`, liquidation withdrawals, and subsequent `update_indexes` calls all re-execute the same overflowing accrual before their mutation logic. [8](#0-7) [9](#0-8) 

The existing regression test demonstrates this exact state transition: after large-scale supply and borrow positions remain at high utilization, `update_indexes` returns `MathOverflow`, the borrow index is still below `MAX_BORROW_INDEX_RAY`, and both repayment and withdrawal subsequently fail with the same error. [10](#0-9) 

### Impact Explanation
This is a permanent freezing-of-funds condition for the affected market: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot execute liquidation legs, and index updates cannot progress once the accrual calculation overflows. [7](#0-6) [11](#0-10) 

### Likelihood Explanation
The trigger requires an exceptionally large market: for an 18-decimal asset, the representable RAY value limit is approximately 170.14 billion whole tokens, and utilization must remain high long enough for the index to push `borrowed * borrow_index / RAY` above `i128::MAX`. [12](#0-11)  A single unprivileged address can nevertheless construct the state by supplying liquidity through `supply`, borrowing through `borrow` from another account it owns, and later invoking the permissionless `update_indexes(caller, assets)` entrypoint. [13](#0-12) [14](#0-13) 

### Recommendation
Before unscaling total debt or supply during accrual, detect an unrepresentable result and clamp accrual or cap the index without reverting. Alternatively, track a per-market value ceiling based on `i128::MAX / current_index`, enforce it before minting additional debt or supply shares, and provide a recovery path that permits repayments, withdrawals, or bad-debt settlement without requiring the overflowing utilization calculation.

### Proof of Concept
The repository already contains a harness proof at `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs`. [10](#0-9) 

Transaction sequence:

1. Account A calls `supply(caller=A, account_id=0, spoke_id, [(debt_asset, principal)])`, creating the liquidity-supply account.
2. Account A calls `supply(caller=A, account_id=0, spoke_id, [(collateral_asset, collateral)])`, creating a borrowing account.
3. Account A calls `borrow(caller=A, account_id=<borrow_account>, [(debt_asset, debt)], Some(A))`, bringing utilization near the tested 98% condition.
4. After sufficient ledger time passes, call `update_indexes(caller=A, [debt_asset])`.
5. `accrue_step` evaluates `scaled_to_original(borrowed, borrow_index)`, receives a quotient greater than `i128::MAX`, and aborts with `MathOverflow`.
6. Calls to `repay`, `withdraw`, or liquidation paths for that market call `load_leg`, execute the same accrual first, and continue reverting, leaving the market frozen.

fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);

| Asset decimals 0..=18 | Exact token-to-RAY upscaling. Below 3: collateral only, no flash loans, no liquidation fee, its account's only supply position, at least 2 whole units while in debt |
| Both indexes initially RAY; ceiling 10^36 | 10^9 times initial index; protocol constants |
| Supply-index floor 10^24 | At most 1,000 times the shares minted at index one for the same deposit |
| Borrow APR maximum 2 RAY | 200% annual rate; not a bound on balance growth alone |
| Token-to-RAY input maximum `i128::MAX / 10^(27-d)` | About 170.14 billion whole tokens, before other limits |
| Deposit conversion at the supply-index floor | About 170.14 million whole tokens before scaled-share overflow |

The token-to-RAY maximum is also the admitted cap maximum. Accrued position
values and market totals must independently fit the RAY domain; valid caps and
bounded indexes do not guarantee that future accrual fits. Value overflow can
occur before the index ceiling and block repayment/withdrawal because those
operations accrue first. At the borrow-index ceiling, further accrual produces
