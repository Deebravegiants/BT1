### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop` value taken from an HTTP header that is never included in that signed content. This breaks the intended binding `HMAC-authenticated bytes == bytes used to identify the tenant`, letting anyone who possesses one validly-signed webhook delivery (e.g. from their own store where the app is installed) relabel it as belonging to any other shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, completely independent of the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC (which only covers `@raw_body`) and then forwards `request.shop` — the unauthenticated header value — straight to the merchant's handler as the tenant identity for the payload: [3](#0-2) 

The HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is shared across *every* shop that has the app installed — it is not shop-specific. Consequently, any body+HMAC pair that is valid for one shop is valid, byte-for-byte, for every other shop, because `shop` was never part of what was signed. This is exactly the class of bug in the report: an identity field (`targetAccount`/`shop`) is acted upon by the authorization/authentication layer without being covered by the thing that was actually cryptographically verified (the calldata/the HMAC).

### Impact Explanation
An entity that legitimately installs the app on their own store (an "unprivileged" tenant relative to other merchants) receives genuine webhook deliveries from Shopify with a valid `x-shopify-hmac-sha256` for a given `@raw_body`. Because `shop` is excluded from the signed content, that entity can replay the identical `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` value for a different, victim merchant. `Registry.process` will accept the HMAC as valid and hand the handler a `WebhookMetadata` claiming the body originated from the victim shop. Any app logic that uses `webhook.shop` to select which merchant's records/session to update, credit, or fulfill (a very common pattern, e.g. `orders/create`, `app/uninstalled`, `shop/redact`) can be tricked into cross-tenant data corruption or disclosure — this matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
No `api_secret_key`, access token, or `client_secret` needs to be recovered — the attacker simply needs one webhook body/HMAC pair that Shopify legitimately delivered to their own store (trivial to obtain by installing the app once), and the ability to POST to the app's public webhook route with a modified header, which by design must be internet-reachable. This requires no privileged access and no interception of TLS traffic.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC-signed material used for verification, or independently authenticate the shop identity against a shop known to be installed/authorized for this app (e.g., cross-check `request.shop` against the app's own session store) before trusting it, rather than accepting it as an unauthenticated header value once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the target app on their own development store `attacker.myshopify.com`.
2. Attacker triggers an event (e.g. updates a product) causing Shopify to POST a webhook to the app's callback URL with body `B` and a valid header `x-shopify-hmac-sha256: H = HMAC-SHA256(client_secret, B)`.
3. Attacker captures `(B, H)` and resends the exact same POST to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `HmacValidator.validate` in `Utils::HmacValidator` succeeds because `to_signable_string` only checks `B` against `H`: [4](#0-3) 
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(... shop: "victim.myshopify.com", body: parsed(B) ...)`, causing the app to process attacker-controlled data as if it came from `victim.myshopify.com`.
