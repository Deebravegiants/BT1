### Title
Webhook `shop` field is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop` is read from an HTTP header that is never included in the HMAC-signed payload. `Registry.process` validates the HMAC over the body alone and then forwards the header-derived `shop` value to the app's webhook handler as an authenticated tenant identifier. Any actor who can obtain one valid `(body, hmac)` pair signed with the app's shared `client_secret` — for example a merchant who has installed the app on their own store and can trigger webhooks with attacker-influenced body content — can replay that exact body+hmac while substituting an arbitrary `shopify-shop-domain` / `x-shopify-shop-domain` header. The signature check still passes because the header is not part of the signed string, so the app receives attacker-controlled body data falsely attributed to a victim shop.

### Finding Description
The binding that should hold is: `hmac == HMAC(client_secret, body ++ shop)`, i.e. the tenant identity should be cryptographically bound to the signed content. Instead the gem implements: `hmac == HMAC(client_secret, body)` only. [1](#0-0) 

- `hmac` is derived from the `hmac-sha256` header.
- `shop` is derived from the `shop-domain` header — a completely separate, unauthenticated field.
- `to_signable_string` returns `@raw_body` only. [2](#0-1) 

`Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, request.to_signable_string)` against `request.hmac`: [3](#0-2) 

Since `client_secret` (the app's `api_secret_key`) is shared across every merchant that installs the app, a valid `(body, hmac)` pair generated for one shop's webhook is cryptographically valid for **any** shop domain. `Registry.process` then builds `WebhookMetadata` directly from the unverified header field and hands it to the app's handler as the trusted tenant context: [4](#0-3) 

The documentation reinforces that host apps are meant to trust this value as the "shop domain of the webhook" once `process` has "verif[ied] the request did indeed come from Shopify": [5](#0-4) [6](#0-5) 

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing. An attacker who is a legitimate merchant for their own shop (unprivileged relative to any other tenant) can:
1. Install the app on their own store.
2. Trigger a webhook whose body contains attacker-influenced content (e.g. `orders/create` with a crafted `note`, `products/update` with a crafted title/body_html, etc., depending on which fields are forwarded).
3. Capture the resulting genuine `(raw_body, hmac-sha256 header)` pair sent by Shopify — this is signed with the app's shared `client_secret`, not a value scoped to that merchant.
4. Replay that exact body and HMAC header to the app's public webhook endpoint while setting the `shopify-shop-domain` (or `x-shopify-shop-domain`) header to a victim shop's domain.
5. `Utils::HmacValidator.validate` passes because it never inspected the shop header, and the app's handler receives `WebhookMetadata` claiming the victim shop as the source, with attacker-controlled body data.

Any host app that uses `data.shop` to select which merchant's records to update (which is the documented/expected usage pattern) will apply attacker data to the wrong tenant — a cross-tenant data-integrity/confusion vulnerability that only requires the gem's own documented API surface, no `api_secret_key`, no access token, and no TLS interception.

### Likelihood Explanation
Moderate-to-high. It requires the attacker to be able to install the app on a shop they control (a normal, low-privilege action for any merchant using a public app) and to influence some body content that the app registers a webhook for. No credential theft, MITM, or insider access is required — only sending a crafted HTTP request to the app's already-public webhook callback URL.

### Recommendation
Bind the shop identity to the signed payload before trusting it: parse `shop` from the JSON body (Shopify webhook payloads for shop-scoped topics generally include shop-identifying data) rather than solely from the header, or otherwise cryptographically bind the header value into the HMAC computation (e.g., verify it against a shop domain provided by the app's own webhook subscription record for that specific delivery, not from request headers alone). At minimum, document prominently that `data.shop` is **not** covered by the HMAC and must not be trusted as an authenticated tenant identifier without additional verification (e.g., cross-checking it against shops known to have the app installed, or against a per-shop webhook secret if using per-shop signing).

### Proof of Concept
1. App registers a handler for `orders/create` for two installed shops, `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`.
2. Attacker (merchant of `attacker-shop`) creates an order with a crafted `note` field designed to be misinterpreted by the app's handler (e.g., an identifier that the app associates with a resource belonging to the victim, if the handler keys off both `shop` and body content).
3. Shopify sends the webhook to the app's endpoint with headers:
   ```
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of body using app's client_secret>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   ```
4. Attacker captures this raw request (body + `hmac-sha256` header) via any HTTP intercept tool they control on their own outbound testing, or simply by having their own server receive it directly if they can point the app's webhook endpoint URL at a proxy they observe.
5. Attacker resends the identical body and `x-shopify-hmac-sha256` header to the same endpoint, replacing the header with `x-shopify-shop-domain: victim-shop.myshopify.com`.
6. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which recomputes `HMAC(client_secret, body)` and matches the replayed header, so validation succeeds.
7. `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's order data>, ...)` is delivered to the app's handler, which processes attacker-controlled content under the victim shop's identity. [7](#0-6) [8](#0-7)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

        end
