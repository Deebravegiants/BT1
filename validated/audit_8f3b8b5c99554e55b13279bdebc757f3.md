### Title
Attacker-crafted `swap` route bytes deserialize into arbitrary contract calls that smuggle token drains into the victim's signed auth tree — (`contracts/controller/src/strategies/swap.rs`)

### Summary
The bug class from the external report — an unauthenticated endpoint deserializing attacker-controlled bytes into executable behavior (`pickle.loads`) — maps onto XOXNO Lending's strategy-swap path. `swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` accept a `Bytes`/`StrategySwap` payload from the caller and hand it verbatim to the configured swap aggregator, which decodes it as XDR (`from_xdr`) and invokes whichever `hop_pool` addresses the payload names via `env.invoke_contract`. A rogue hop contract can then call `token.transfer(victim, attacker, amount)` on any token the victim holds; because the call happens inside the victim's `swap_collateral` invocation, Soroban attaches that `require_auth` to the victim's authorized-invocation tree. When the victim simulates and signs the recorded auth tree (the standard wallet flow), the rogue hop executes and drains the victim's entire unrelated wallet balance — the on-chain equivalent of deserialized untrusted bytes producing arbitrary code execution.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs` snapshots balances, authorizes one exact input transfer to the router, calls `router.execute_strategy(&controller, &amount_in, swap)`, and only checks that the controller's input did not overspend and that output was received (`RouterOverspend`, `NoSwapOutput`). Nothing validates the contents of `swap`: the venue addresses embedded in the XDR are fully attacker-controlled, and the router calls them while the victim's authorization tree is live. The harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates this end-to-end: `RogueHopPool::swap` calls `token.transfer(&victim, &to, &amount)` (lines 62-71), the router double invokes it via `env.invoke_contract(&route.hop_pool, ...)` after `RoutedSwap::from_xdr` (lines 39-47), and enforcing-mode execution succeeds when the tree containing the steal transfer is signed (lines 322-368). The victim's `WALLET_BALANCE` of a token the protocol never listed moves to the attacker while the swap itself returns a fair output (`FAIR_OUT_ETH`), so every controller-side invariant passes.

### Impact Explanation
Theft of user funds: any tokens in the victim's wallet — assets never supplied to the protocol — can be transferred to the attacker inside a single signed `swap_collateral`/`swap_debt`/`multiply`/`repay_debt_with_collateral` call. The protocol's own checks (input cap, output receipt, health factor) all pass because the drain is orthogonal to position accounting; it rides the victim's authorization tree.

### Likelihood Explanation
The route bytes are opaque XDR to the victim and are normally produced by an off-chain quote service or attacker-supplied quote; the signer sees only a `swap_collateral` root with a nested tree they are trained to accept after simulation. The malicious hop returns a fair swap output, so simulation shows a successful trade and there is no on-chain signal distinguishing the poisoned tree from a benign multi-hop route. Any unprivileged address can deploy the rogue pool and construct the payload.

### Recommendation
Treat `swap`/`route` bytes as untrusted executable input: restrict venues to a governance-allowlisted set, decode and validate route structure in the controller (or pin the aggregator to a strict schema), and/or bound the authorization surface — e.g., have the router require only the controller's contract auth for the exact input transfer and refuse any nested `require_auth` on the caller's address beyond the declared input/output tokens. Document a client-side check that rejects simulated auth trees containing `transfer` entries whose `from` is the caller and whose `to` is an unexpected address.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

1. Attacker deploys `RogueHopPool` with `PLAN = (victim=alice, wallet_token, to=attacker, amount=WALLET_BALANCE)` (lines 56-71).
2. Attacker encodes `RoutedSwap { hop_pool: rogue, min_out: FAIR_OUT_ETH, token_in: USDC, token_out: ETH }` to XDR and supplies it as the `route` argument; victim calls `swap_collateral(alice, account_id, USDC, SWAP_IN_USDC, ETH, route)` (lines 111-157).
3. The router deserializes the bytes (`RoutedSwap::from_xdr`, line 41) and invokes `hop_pool.swap`, which executes `token.transfer(alice, attacker, WALLET_BALANCE)`; recording mode shows the steal nested under the victim's `swap_collateral` entry (lines 194-227), and enforcing mode with source-account credentials executes it when the child is present in the signed tree (lines 322-368).
4. Assertions confirm `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`, and the position still receives `FAIR_OUT_ETH` — the swap "succeeds" while the wallet is drained.
