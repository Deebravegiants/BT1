### Title
Webhook shop/topic identity spoofing via HMAC that only covers the request body, not the identifying headers - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its `hmac` signature over the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to route and process the webhook are read directly from unauthenticated HTTP headers. `Registry.process` trusts `request.shop` from these headers when dispatching to the app's handler, breaking the identity binding `hmac-verified bytes == bytes acted on`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all derived from headers that are never included in the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `hmac` against `to_signable_string` (the body), so it cannot detect tampering with any header: [3](#0-2) 

`Registry.process` validates the HMAC and then unconditionally trusts `request.shop` and `request.topic` to route and label the event to the app's handler: [4](#0-3) 

This is the same identity-binding failure class as the referenced report: a value that is *acted on* (`shop`) is not covered by the same authentication mechanism (HMAC) that is checked before acting. Any unprivileged actor who has ever received a single legitimate webhook for their own shop (trivial: install the app on a free dev/test shop and let one webhook fire) obtains a `(raw_body, hmac)` pair that is valid for the app's `client_secret`. Because the signature never covers headers, that captured `(raw_body, hmac)` pair can be replayed to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to any victim shop domain, and/or the `X-Shopify-Topic` header rewritten to any topic (e.g. `app/uninstalled`, `shop/redact`, `customers/data_request`). `Utils::HmacValidator.validate` still returns `true` because it only re-hashes the body, and `Registry.process` hands `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` straight to the app's handler as if it were an authentic Shopify-originated event for that shop.

### Impact Explanation
This crosses a tenant boundary: an attacker who is a legitimate (even free/trial) merchant of the app can make the app believe an arbitrary, victim shop-domain sent a webhook of an arbitrary topic with attacker-chosen body content, without ever compromising the victim or obtaining the app's `client_secret`. Depending on the handler logic the host app registers (data sync, uninstall cleanup, GDPR redact handling, order/customer processing keyed by `shop`), this enables cross-tenant data corruption, spoofed mandatory compliance events, or forced processing of attacker-controlled payloads attributed to a victim shop - satisfying the "Critical: cross-tenant access" bar.

### Likelihood Explanation
Likelihood is high for any app that exposes its webhook endpoint publicly (as required by Shopify) and relies on the gem's `Registry.process`/`HmacValidator` as the sole authenticity check, since only knowledge of one's own valid `(body, hmac)` pair - trivially obtainable by installing the app - is needed; no access token, `client_secret`, or victim interaction is required.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed/verifiable content, or otherwise cryptographically bind them to the HMAC-covered body (e.g., verify them against Shopify's canonical webhook envelope conventions) before `Registry.process` trusts `request.shop`/`request.topic`. At minimum, document that host apps must independently corroborate the `shop` header against a known/registered shop before acting, since the gem's own validation does not do so.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers/captures one legitimate webhook delivery, e.g. `orders/create`, recording `raw_body` and the `X-Shopify-Hmac-Sha256` header value `H`.
2. Attacker replays a POST to the app's webhook endpoint with the same `raw_body` and same `hmac-sha256` header `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and/or `X-Shopify-Topic: app/uninstalled`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only and matches `H`, so validation passes. [5](#0-4) 
4. The handler for the topic is invoked with `WebhookMetadata` whose `shop` field is `victim.myshopify.com`, despite the payload never having been produced by Shopify for that shop. [6](#0-5)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
