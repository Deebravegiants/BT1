## Analysis Result

### Title
Unprivileged `CallDispatcher.dispatch()` lets any user-supplied order calldata leave standing approvals that drain funds routed through the shared dispatcher for *other* orders - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher` is a single, shared, unauthenticated utility contract reused across every `IntentGatewayV2` order (predispatch and postdispatch calldata) and across other apps in the repo. Its `dispatch()` entrypoint has no caller restriction and executes fully attacker-controlled `Call[]` arrays with the dispatcher's own token balances/allowances as the execution context.

### Finding Description
`CallDispatcher.dispatch(bytes memory encoded)` is `external` with no access-control modifier at all — any address can call it, and it will `to.call{value: call.value}(call.data)` for every entry in the caller-supplied `Call[]`: [1](#0-0) 

This same singleton dispatcher instance is used by `IntentGatewayV2.placeOrder()` for `order.predispatch.call` and by `IntentsBase._execute()` for `order.output.call` — both of which embed **arbitrary calldata chosen by whoever places/fills the order**: [2](#0-1) [3](#0-2) 

Because `dispatch()` performs raw low-level calls to any target with any calldata, an order author can embed a call such as `token.approve(attacker, type(uint256).max)` in their own `predispatch.call`/`output.call`. This grants the shared `CallDispatcher` contract's balance an unlimited standing allowance to an attacker-controlled address — a state that persists indefinitely, unlike the per-transaction escrow flow the gateway assumes. Since the dispatcher is shared across *every* order/app that routes tokens through it, any token dust or transiently-held balance left on the dispatcher during a *different, unrelated* user's predispatch/postdispatch flow (fee-on-transfer remainders, rounding dust, or any token the sweep logic doesn't fully account for) is later reachable by the earlier attacker via the standing allowance — with no further authorization needed, since `dispatch()` itself has no owner check to prevent this in the first place, and the attacker doesn't even need `dispatch()` again: they can call `transferFrom` directly using their pre-granted allowance.

The developer documentation itself flags this exact hazard as a known caveat rather than a hard invariant enforced on-chain: [4](#0-3) 

This mirrors the report's root cause: a function reachable by an unprivileged party ends up controlling/consuming token allowances that belong to funds not authorized by their rightful owner for that purpose — here, the "victim" is the shared dispatcher's balance/allowance state instead of a single borrower's wallet, but the mechanism (an open entrypoint letting one user's transaction commit resources that get misused for another user's flow) is structurally the same.

### Impact Explanation
Any account can plant a persistent unlimited approval from the shared `CallDispatcher` to itself via ordinary order placement (no special privilege required), then later drain any token balance the dispatcher subsequently holds for unrelated orders/users routed through `IntentGatewayV2` (or other hyperbridge apps sharing the same dispatcher deployment). This is a fund-theft vector against protocol dust/leftover balances that is not bounded by governance or per-order controls — a route for unauthorized transfer of value that was never intended to be reachable by the attacker.

### Likelihood Explanation
Placing an order with arbitrary `predispatch.call`/`output.call` bytes requires no special permission — any user can craft such an order today. The only precondition for exploitation is that the shared `CallDispatcher` at some point (across any order, any user, any token) holds a non-zero balance of the approved token that isn't perfectly swept (fee-on-transfer tokens, rounding, or any residual token not part of the declared `inputs`/`outputs` list are explicitly acknowledged as "dust" in the code/comments), which the documentation itself already warns integrators about.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by the specific gateway/app instance associated with the current in-flight order (e.g., an `onlyAuthorizedCaller` allowlist set at deployment, or better, deploy a scoped, single-use, ephemeral dispatcher per order instead of one shared singleton), and explicitly disallow/neutralize `approve` calls to arbitrary spenders from within dispatched `Call[]`, or force-reset any approvals the dispatcher grants at the end of every `dispatch()` invocation so no allowance persists past the originating transaction.

### Proof of Concept
1. Attacker calls `IntentGatewayV2.placeOrder()` with `predispatch.assets = [{tokenX, 1}]` and `predispatch.call` encoding a single `Call{ to: tokenX, data: approve(attacker, type(uint256).max) }`.
2. This routes through `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` at [5](#0-4) , granting `CallDispatcher` → `attacker` an unlimited `tokenX` allowance that is never revoked.
3. At any later point, any other order (fee-on-transfer token flow, or any predispatch/postdispatch call leaving tokenX dust on the dispatcher per the docs' own caveat) causes `tokenX` to sit, even momentarily, in `CallDispatcher`'s balance.
4. Attacker calls `tokenX.transferFrom(dispatcher, attacker, amount)` directly (no further interaction with `dispatch()` needed) to steal the balance, since the approval from step 2 never expires and `dispatch()`'s lack of access control was what allowed the malicious approval to be planted in the first place.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

        ICallDispatcher(dispatcher).dispatch(order.output.call);

        Call[] memory sweepCalls = new Call[](outputsLen);
        uint256 sweepCount = 0;

        for (uint256 i; i < outputsLen;) {
            address token = address(uint160(uint256(order.output.assets[i].token)));

            if (token == address(0)) {
                uint256 balance = dispatcher.balance;
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({to: address(this), value: balance, data: ""});
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            } else {
                uint256 balance = IERC20(token).balanceOf(dispatcher);
                if (balance > 0) {

                        to: token,
                        value: 0,

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
