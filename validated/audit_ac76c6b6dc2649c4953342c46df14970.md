The docs explicitly state that `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" [1](#0-0)  and that `data.shop` is "The shop domain of the webhook" [2](#0-1) , positioning `shop` as a value verified by that same call — but the HMAC only ever signs the raw body.

### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity solely by checking the `hmac-sha256` header against the raw request body [3](#0-2) . The `shop` (and `topic`, `webhook_id`, `api_version`) values that are then forwarded to the app's handler as trusted, "verified" data are taken directly from HTTP headers that are never part of the signed payload [4](#0-3) . Since the HMAC secret (`api_secret_key`) is the app's single client secret shared across every shop that installs the app — not a per-shop secret — anyone with a legitimate install of the app can obtain a validly-signed `(body, hmac)` pair from their own shop's webhook deliveries and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop that also uses the same app. `Registry.process` will report the request as authenticated and hand the attacker-chosen `shop` value to the handler as if it were verified.

### Finding Description
The identity binding that should hold is: `hmac == HMAC(api_secret_key, bytes_that_determine_the_acted_upon_shop)`. Instead the binding actually enforced is: `hmac == HMAC(api_secret_key, raw_body)` while `shop` is read from an unrelated, unauthenticated header.

- `VerifiableQuery#to_signable_string` for a webhook `Request` returns only `@raw_body` [5](#0-4) .
- `HmacValidator.validate` computes the signature over exactly that signable string and constant-time-compares it to the `hmac` header [6](#0-5) .
- `Registry.process` treats a passing HMAC check as proof the whole request "did indeed come from Shopify" (per the gem's own docs) and then builds `WebhookMetadata` using `request.shop`, which is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the HMAC [7](#0-6) [8](#0-7) .

Because Shopify's `api_secret_key` (the app's client secret) is identical for all shops that have installed a given app, any of those shops can legitimately receive a webhook with a valid HMAC over some body they control the timing/content of (e.g. by triggering an order update in their own store). Capturing that `(raw_body, hmac)` pair and re-POSTing it to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header pointing at a different, victim shop using the same app passes `Registry.process` unchanged, because `shop` is never part of what's hashed.

### Impact Explanation
This breaks the tenant boundary the gem is documented to guarantee: an app author is told that after `Registry.process` succeeds, `data.shop` is a verified attribute of an authentic Shopify request [9](#0-8) . In practice a malicious merchant/installer of the same app can spoof webhook events "from" any other merchant that installed the app, causing the host application to attribute attacker-controlled data/state changes to the victim shop (cross-tenant data injection), satisfying the Critical "cross-tenant access" impact bucket.

### Likelihood Explanation
Exploitation only requires installing the target app on any shop the attacker controls (a normal, unprivileged action for any Shopify merchant/developer) and being able to send arbitrary HTTP requests to the app's public webhook URL — no access token, `api_secret_key` leak, or privileged account is needed. The `api_secret_key` never needs to be known by the attacker since they reuse a signature Shopify itself produced for their own shop's event.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-covered signable string, or independently verify `request.shop` against a shop known to have a valid, currently-registered session/installation for this app before trusting it in the handler. At minimum, document prominently that `data.shop` is not covered by the HMAC and must be revalidated by the host app against its own store of installed shops.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`) for their own shop, capturing the raw POST body and the `x-shopify-hmac-sha256` header value Shopify computed.
2. Attacker POSTs that exact `raw_body` to the app's webhook endpoint, keeping the same `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `HmacValidator.validate` recomputes `HMAC(api_secret_key, raw_body)` — identical to before — and returns `true` [10](#0-9) .
4. `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, and the host app processes/stores attacker-controlled data as if it came from the victim shop [11](#0-10) .

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
