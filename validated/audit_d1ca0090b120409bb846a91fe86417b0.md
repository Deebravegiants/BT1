### Title
Webhook shop binding bypass via unsigned `x-shopify-shop-domain` header - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`Registry.process` validates the HMAC of a webhook via `Utils::HmacValidator.validate(request)`, but the signable string returned by `Webhooks::Request#to_signable_string` is only the raw request body [1](#0-0) , while `request.shop` is read straight from the unsigned `x-shopify-shop-domain`/`shopify-shop-domain` header [2](#0-1) . This lets an attacker who controls a real, validly-signed webhook payload (received on their own dev shop's registered endpoint) replay that exact body+HMAC to the app's webhook endpoint with the shop-domain header swapped to a victim shop, and `Registry.process` will pass the forged shop into `handler.handle(data: WebhookMetadata.new(... shop: request.shop ...))` [3](#0-2) .

### Finding Description
The binding that should hold is: `shop_covered_by_hmac == shop_acted_on`, i.e. the value of `request.shop` used to build `WebhookMetadata` must be part of what `HmacValidator.validate` cryptographically authenticates. Tracing the code:

- `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` header via `OpenSSL.secure_compare` [4](#0-3) .
- `Webhooks::Request#to_signable_string` returns `@raw_body` only — no headers, including `shop-domain`, are part of the signed string [1](#0-0) .
- `Webhooks::Request#shop` is read directly from the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with no cross-check against the body or the HMAC [2](#0-1) .
- `Registry.process` only checks `HmacValidator.validate(request)` returns true, then immediately trusts `request.shop` to build `WebhookMetadata`, handing it to the host app's handler [3](#0-2) .

This matches Shopify's actual, documented webhook HMAC scheme (HMAC over raw body only, using the app's `client_secret`), which is shared across every shop that installs the app. Because the secret is app-wide rather than per-shop, and only the body is signed, a validly-signed request signed for the attacker's own shop remains validly-signed after the (unsigned) shop-domain header is altered. An attacker who installs the app on their own development shop and registers a webhook endpoint receives genuine, correctly-HMAC'd callbacks from Shopify. Since they control the server receiving those callbacks, they can capture the raw body + `hmac-sha256` header pair and re-POST it to the app's public webhook endpoint with `x-shopify-shop-domain` rewritten to a victim shop's domain. `HmacValidator.validate` still returns `true` because it never inspected the shop header, and `Registry.process` hands the handler a `WebhookMetadata` claiming `shop: "victim.myshopify.com"` while the actual body content originates from the attacker's own shop.

No other guard in this gem closes the gap: `ShopValidator`, `Context.setup?`/`private?`/`embedded?`, and Sorbet typing are not involved in this path, and there is no secondary check anywhere in `registry.rb` or `request.rb` that ties `shop` to the signed payload.

### Impact Explanation
Any host app that uses `request.shop` from `WebhookMetadata` to key per-tenant state (e.g., "update this record for `shop`", "mark GDPR redaction complete for `shop`", billing/plan updates, mandatory-webhook side effects) can be made to apply attacker-controlled webhook data to an arbitrary victim shop's tenant context. This is a cross-tenant impact: one tenant's (the attacker's) webhook event is misattributed to another tenant (the victim) purely by altering an unauthenticated header. It is repeatable against arbitrary victim shop domains at will, for every webhook topic the attacker can trigger on their own shop (e.g. by installing the app, creating orders/customers/products on their own dev store, or by triggering mandatory `customers/redact`, `shop/redact`, `customers/data_request` topics), with no additional secrets required.

### Likelihood Explanation
Preconditions are exactly what's granted to an "unprivileged attacker" in scope: they need only their own dev shop with the app installed, a webhook subscription with a self-controlled receiving endpoint (or the ability to observe/replay a delivered payload), and the ability to send arbitrary HTTP requests to the app's public webhook endpoint (which is, by design, a public unauthenticated-by-caller-identity endpoint that Shopify itself POSTs to). No `api_secret_key`, access token, or victim credentials are needed. This is low-cost and fully repeatable.

### Recommendation
Do not trust `x-shopify-shop-domain` as authenticated identity. Either:
1. Bind the shop domain into the signed material used for verification (not possible unilaterally since Shopify controls the signature format), or, practically,
2. Require host apps to independently correlate `request.shop` against an application-level fact that is authenticated separately (e.g., verify the shop has a known/valid installed session/access token on record, and treat the webhook purely as a trigger rather than as authoritative proof of which shop generated it), and
3. At minimum, document prominently in this gem that `request.shop` is unauthenticated and must not be trusted for authorization decisions without additional verification (e.g., confirming an active `Session` exists for that shop, or using per-shop webhook endpoint paths that the host app maps out-of-band), since the gem's `HmacValidator` cannot itself strengthen the binding beyond what Shopify's own HMAC scheme covers.

### Proof of Concept
Minitest + WebMock/Mocha plan (would live under `test/`, out of scope to write here, but for reference):
1. Set `Context.api_secret_key` to a known test secret.
2. Compute `body = '{"id":123,"shop_data":"attacker-owned"}'` and `sig = OpenSSL::HMAC.hexdigest("sha256", secret, body)`.
3. Build `request = Webhooks::Request.new(raw_body: body, headers: {"x-shopify-hmac-sha256" => Base64.strict_encode64([sig].pack("H*")), "x-shopify-topic" => "orders/create", "x-shopify-shop-domain" => "victim-shop.myshopify.com", "x-shopify-api-version" => "2023-10", "x-shopify-webhook-id" => "1"})`.
4. Assert `Utils::HmacValidator.validate(request) == true`.
5. Assert `request.shop == "victim-shop.myshopify.com"` while the signed string (`request.to_signable_string == body`) contains no reference to `"victim-shop.myshopify.com"` (only `"attacker-owned"`), demonstrating `shop_covered_by_hmac != shop_acted_on`.
6. Stub a `WebhookHandler` registered for `orders/create` and call `Registry.process(request)`, asserting the handler's `handle` receives `data.shop == "victim-shop.myshopify.com"` — proving the forged shop flows unchecked into the host app despite HMAC validation succeeding.
