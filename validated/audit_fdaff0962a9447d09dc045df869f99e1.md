### Title
Zero-length `erc20TokenAddresses` with `MainEVMCircuitMin` bypasses ALL balance-conservation checks in `EmporiumUpgradeable.runAction`, allowing unbacked drain of pooled ERC20 balances - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`CircomDataBuilder.formInputForCircom` intentionally routes any call with `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0` to `MainEVMCircuitMin`, a circuit with no `rootHashHinkal`, no nullifiers, and no `amountChanges` constraints. Both `Hinkal.transact`'s balance-conservation loop and `EmporiumUpgradeable.runAction`'s balance-conservation loop iterate over `circomData.erc20TokenAddresses`, so with length 0 they execute zero times, leaving arbitrary attacker-supplied `ops` free to move the Emporium contract's real ERC20 balance with no accounting whatsoever.

### Finding Description
Equality that should hold: for any Emporium call, `sum(balanceChange per token accounted in the loop) == sum(deltaAmountChanges + UTXO outputs)` (`EmporiumUpgradeable.sol:132-151`), and Hinkal's own post-check `balanceDif == amountChanges[i] + utxoAmount` (`Hinkal.sol:97-147`). Both loops are indexed by `circomData.erc20TokenAddresses.length`.

`CircomDataBuilder.formInputForCircom` (`contracts/CircomDataBuilder.sol:134-148`) selects `formInputEmporiumMin` — feeding only `emporiumMessage`, `timeStamp`, `calldataHash` to the circuit — precisely when `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`. `MainEVMCircuitMin` (`circuits/MainEVMCircuitMin.circom:1-18`) has no `rootHashHinkal`, no nullifier/commitment signals, and does not constrain `amountChanges` at all — it only checks `message == Poseidon(messageSeed)`.

`dimensionsCheck` (`contracts/HinkalHelper.sol:64-90`) only requires `erc20TokenAddresses.length == dimensions.tokenNumber`; nothing prevents `dimensions.tokenNumber = 0`. `performHinkalChecks` never re-derives or ties `rootHashHinkal`/balance state to the `stack` (`EmporiumStack`) content.

In `EmporiumUpgradeable.runAction` (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:76-160`):
- `stack` is decoded straight from attacker-supplied `circomData.externalActionData.externalActionMetadata`.
- `verifyWallet` only checks an EIP-712 signature when `stack.signerAddress != address(0)`; the attacker can set `signerAddress = address(0)` to skip signature verification entirely and still pass (it only records `usedMessages`).
- The ops loop (lines 91-118) executes `EmporiumOperation[] ops` via CASE 2 ("Stateless Interaction"): `op.endpoint.call{value: op.value}(op.callData)`, filtering only `callHinkalWallet`/`doSendToRelay` selectors — any other target/selector is permitted, including a direct call to an ERC20 token's `transfer(attacker, amount)`, which executes with `msg.sender == address(EmporiumUpgradeable)`.
- The balance-conservation loop (lines 132-151), which would normally require `balanceChange >= 0` per token and mint an offsetting UTXO for any positive change, is driven by `circomData.erc20TokenAddresses.length`. With length 0 this loop runs zero times, so a negative balance change (funds leaving Emporium) is never detected or reverted.
- `Hinkal.sol`'s own outer balance loop (lines 97-147) is likewise indexed by the same empty array and also performs zero checks.

Attacker's call: submit `Hinkal.transact` with a valid `MainEVMCircuitMin` proof (only needs `messageSeed` known to the caller — no UTXOs, no merkle root, no nullifiers required), `dimensions.tokenNumber = 0`, `circomData.erc20TokenAddresses = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, and `externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)` and `ops = [{endpoint: pooledToken, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, poolBalance))}]`. `calldataHash` is separately checked on-chain via `getHashedCalldata` (`CircomDataBuilder.sol`), but the attacker fully controls their own calldata, so this hash check is trivially satisfiable and does not constrain what the ops actually do.

Existing guards do not stop this: `performHinkalChecks` (`dimensionsCheck`, `checkOnchainCreation`) never requires `tokenNumber > 0` for Emporium calls; `rootHashExists` is not even reached in the Min-circuit's constraints (the circuit doesn't use it, and `rootHashHinkal` in `CircomData` can be set to any value on-chain valid root since `rootHashHinkal`/`rootHashHinkalIndex` are still checked by `Hinkal.transact` against the on-chain tree, but that check is orthogonal to whether ERC20 balance movements are tallied); `insertNullifiers` inserts zero nullifiers (dimension-consistent with `tokenNumber=0`), so SINGLE SPEND is not violated by a double-spend, but VALUE CONSERVATION is broken outright since no spend is required at all to justify a real balance outflow.

### Impact Explanation
Direct theft of the Emporium contract's pooled ERC20 balance — funds belonging to other users who have deposited into Emporium via prior legitimate `transact` calls and hold unredeemed UTXOs backed by that balance. An unprivileged attacker can transfer out the entire balance of any ERC20 token held by the Emporium contract to themselves, with zero UTXOs spent and zero balance-conservation checks applied, matching the "Critical - direct theft of shielded or in-flight user funds" category. The attack is repeatable for every token/ balance accumulated in the Emporium contract and for every fresh `emporiumMessage` (bounded only by `usedMessages` per message value, which is trivially incremented by the attacker).

### Likelihood Explanation
Preconditions: the Emporium external action must be registered (`Hinkal.registerExternalAction`) and must hold a non-zero balance of at least one ERC20 token (a normal, expected operating state for the Emporium pooled-balance design). The attacker needs no special role — any EOA can call `Hinkal.transact` after generating a `MainEVMCircuitMin` proof locally (trivial: only needs a `messageSeed`; no tree state, no UTXOs). Cost is a single transaction plus proof generation. This is fully within the declared unprivileged attacker capability and is highly feasible/repeatable.

### Recommendation
Do not allow the "Min circuit"/`erc20TokenAddresses.length == 0` fast path to reach `EmporiumUpgradeable.runAction` when `stack.ops` can perform value-moving stateless calls. At minimum: (1) require `stack.ops.length == 0` (or restrict CASE 2 targets to a strict allowlist unrelated to token contracts) whenever `erc20TokenAddresses.length == 0`; (2) make the balance-conservation check in both `Hinkal.transact` and `EmporiumUpgradeable.runAction` unconditional on the *actual* set of tokens touched by `ops` (e.g., snapshot balances of all tokens the ops interact with, not just `circomData.erc20TokenAddresses`), rather than trusting the circuit-selected empty array; (3) require `verifyWallet` to always validate a signature (disallow `signerAddress == address(0)` bypass) for any op that isn't a pure state-invoking wallet call.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `VerifierFacade`, register the real `mainEVMCircuitMin0v4` verifier for the verifierId computed from `buildVerifierId(dimensions{tokenNumber:0,...}, HINKAL_EMPORIUM_ACTION_ID)`.
2. Deploy `EmporiumUpgradeable`, register it as `externalActionMap[HINKAL_EMPORIUM_ACTION_ID]`, mark the `Hinkal` address as an allowed recipient.
3. Seed Emporium with a pooled ERC20 balance (simulate a prior legitimate deposit by another user, e.g., `token.mint(address(emporium), 1000e18)`).
4. As attacker EOA (no deposits, no UTXOs), generate a valid `MainEVMCircuitMin` proof off-chain via snarkjs for arbitrary `messageSeed`, `outTimeStamp`, `calldataHash`.
5. Build `CircomData` with `erc20TokenAddresses = []`, `dimensions.tokenNumber = 0`, `inputNullifiers = []`, `outCommitments = []`, `externalActionData = {externalAddress: emporium, externalActionId: HINKAL_EMPORIUM_ACTION_ID, externalActionMetadata: abi.encode(EmporiumStack{signerAddress: address(0), ops: [{endpoint: address(token), invokeWallet:false, value:0, callData: abi.encodeCall(IERC20.transfer,(attacker, 1000e18))}], ...}}`; compute `calldataHash` via `CircomDataBuilder.getHashedCalldata` locally to match.
6. Call `hinkal.transact(a,b,c,dimensions,circomData)` from attacker.
7. Assert: call succeeds (no revert), `token.balanceOf(attacker) == 1000e18`, `token.balanceOf(emporium) == 0`, and assert the equality `balanceChange (== -1000e18 actual) != 0` while `deltaAmountChanges.length == 0` and the conservation loop never executed (i.e., no `BalanceChangeShouldBePositive` revert occurred despite balance going negative), proving the balance-conservation invariant was skipped entirely.
