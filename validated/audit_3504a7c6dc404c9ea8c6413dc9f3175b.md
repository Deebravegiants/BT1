This is the key finding. `Webhooks::Request` computes the HMAC over `@raw_body` (`to_signable_string` returns the raw, unparsed request body), but every field the caller subsequently trusts — `shop`, `topic`, `api_version`, `webhook_id` — is read exclusively from HTTP headers (`shopify_header`), which are never covered by the HMAC computation at all. The "bytes verified" (the raw body) are disjoint from the "bytes parsed and trusted for tenant identity" (the headers). This maps directly onto the analog category "bytes verified versus bytes parsed" / "a shop authenticated versus the shop stored as a session key." [1](#0-0) 

### Title
Webhook HMAC only signs the request body while `shop`/`topic` identity is taken from unauthenticated headers - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `HmacValidator.validate` computes/verifies the signature purely against that raw body string. However, `shop`, `topic`, `api_version`, and `webhook_id` — the values a host application relies on to route the webhook and identify the tenant — are pulled straight from HTTP headers via `shopify_header`, which are never included in the signed material. [2](#0-1) [3](#0-2) 

### Finding Description
The equality this code is supposed to enforce is: `hmac_verify(body) == true` implies `shop header == the tenant that actually sent this webhook`. But because the HMAC only binds the body bytes, an unprivileged internet user who can replay/forward a previously observed, validly-signed webhook body (e.g. one obtained from a public/test endpoint, a proxy log, or a shared body across two apps using the same API secret in dev/staging, or simply from another shop's genuinely delivered webhook whose body they can read) can attach **arbitrary `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, and `X-Shopify-API-Version` headers** to that same body and resubmit it to the app's webhook endpoint. `HmacValidator.validate` will still report success because it only recomputes HMAC over `@raw_body`, which is unchanged. The application, trusting `request.shop` to decide which merchant's data record to update, will act on the attacker-chosen `shop` value paired with a body that Shopify never associated with that shop.

### Impact Explanation
This breaks the tenant-identity binding at the heart of webhook processing: HMAC validity is supposed to prove "this exact (shop, topic, body) tuple came from Shopify for this shop," but the gem only proves "this body came from Shopify for *some* shop." Any host application that follows this gem's documented pattern (validate via `HmacValidator.validate(request)`, then trust `request.shop`/`request.topic` to look up/update per-tenant records) is exposed to cross-tenant data confusion — an attacker-controlled `shop` header paired with a valid signature lets an attacker force the app to process/attribute another shop's payload as belonging to a shop of the attacker's choosing. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires no possession of `api_secret_key`, access token, or any credential — only the ability to observe one valid webhook delivery's raw body (which is not itself secret; only the HMAC and header identity are meant to establish trust) and the ability to re-POST it with modified headers to the target's public webhook endpoint. This is exploitable by any unprivileged internet user who can capture/replay one legitimately signed payload.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string, or otherwise cryptographically bind them to the raw body before computing/validating the HMAC, so that changing any header invalidates the signature.

### Proof of Concept
1. Attacker captures one valid webhook delivery (raw JSON body `B` with headers `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Shop-Domain: victim-shop.myshopify.com`) sent to the app's webhook endpoint — e.g., from a publicly logged request, a shared error tracker, or a shop the attacker also controls that happens to receive a delivery.
2. Attacker resends the identical body `B` with header `X-Shopify-Hmac-Sha256: H` unchanged, but sets `X-Shopify-Shop-Domain: target-shop.myshopify.com` (a different tenant) and/or a different `X-Shopify-Topic`.
3. Application calls:
```ruby
request = ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: attacker_headers)
ShopifyAPI::Utils::HmacValidator.validate(request) # => true, because validate() only hashes @raw_body
request.shop   # => "target-shop.myshopify.com" (attacker-controlled, unauthenticated)
```
4. `HmacValidator.validate` returns `true` because `to_signable_string` never included the header values, so the app processes the payload as if Shopify itself sent it for `target-shop.myshopify.com`.
