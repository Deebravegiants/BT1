### Title
Permissionless `CallDispatcher.dispatch` lets anyone steal tokens/ETH left in the shared dispatcher by `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata delivery - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` has no caller restriction whatsoever — any address can invoke it to force the `CallDispatcher` to execute arbitrary `Call[]` against any contract, using the `CallDispatcher`'s own balance and identity as `msg.sender`. [1](#0-0)  This mirrors the report's bug class ("an unrestricted, arbitrary-call-forwarding contract whose funds/identity can be hijacked by anyone") except no factory/whitelist bypass is even needed here — the entry point is public by design. Several Hyperbridge apps route bridged assets through this single shared `CallDispatcher` and then invoke attacker/sender-supplied calldata on it, but at least one of them (`HyperFungibleToken`/`WrappedHyperFungibleToken`/their upgradeable variants) never sweeps back whatever balance remains on the dispatcher after that calldata runs.

### Finding Description
`CallDispatcher` is a single, shared, chain-wide utility contract (one deployment referenced from many app instances) used to execute user-supplied `Call[]` on behalf of `IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken` and their upgradeable variants. [2](#0-1) 

Its `dispatch` function is `external` with no access control (no `onlyOwner`, no caller allow-list, only a check that the *target* has code): [1](#0-0) 

Multiple flows route bridged assets through it:
- `HyperFungibleToken.onAccept` mints tokens to `message.to` (which, per the documented pattern, is often set to the `CallDispatcher` address itself so the calldata can spend the minted tokens) and then calls `ICallDispatcher(_dispatcher).dispatch(message.data)` with **no subsequent sweep of leftover balance**. [3](#0-2) 
- The equivalent unlock path in `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` has the same shape: transfer/unwrap to beneficiary, then `dispatch(message.data)`, again with no residual-balance sweep. [4](#0-3) 
- By contrast, `IntentGatewayV2`/`IntentsBase._execute` does implement an explicit post-dispatch sweep of the dispatcher's remaining balances back to the gateway, which shows the maintainers are aware residual funds can be left on the shared dispatcher and must be reclaimed. [5](#0-4) 

Because `dispatch()` is callable by anyone, any leftover balance left on the `CallDispatcher` — from a swap that doesn't consume 100% of the minted/unlocked tokens (slippage, fee-on-transfer tokens, partial fills, output token not fully swept, native ETH dust from `Call.value`, or calldata that targets a token not accounted for by whichever caller built it) — is immediately up for grabs by any third party. An attacker simply calls `CallDispatcher.dispatch(...)` with a `Call` such as `{to: token, value: 0, data: transfer(attacker, balance)}` (the `to` check only requires the target have code, so calling the ERC20 token contract itself trivially satisfies it) to sweep the dust to themselves.

This is functionally the same primitive misuse as the report: a contract meant to forward calls on behalf of a trusted flow can be driven directly by anyone, and funds that transiently sit inside it (analogous to the swapper's escrowed payback/approval state in the original report) are stolen through that unrestricted forwarding capability.

### Impact Explanation
Any tokens/ETH left un-swept on the shared `CallDispatcher` after an `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata-bearing delivery are permanently stealable by any address that notices the balance, since `dispatch()` performs no caller check and can direct the dispatcher to transfer out any asset it currently holds. Given the `CallDispatcher` is shared across all HFT/WrappedHFT instances (and possibly `IntentGatewayV2`) on a chain, this is a cross-application, direct-theft-of-funds primitive reachable by a single unprivileged transaction — no relayer collusion, governance compromise, or malicious node required.

### Likelihood Explanation
Likelihood is driven by how often calldata-bearing sends leave a non-zero balance on the dispatcher. Any of the following can trigger it in a legitimate, non-malicious flow: fee-on-transfer output tokens, slippage from a `swapExactTokensForTokens`-style call, native ETH dust from `Call.value`, or a sender-authored `Call[]` that (accidentally or otherwise) doesn't fully spend the minted amount. Since `HyperFungibleToken`/`WrappedHyperFungibleToken` never checks or sweeps the dispatcher's post-call balance (unlike `IntentsBase`, which explicitly does), any such residue is an open bounty for MEV bots watching the mempool/chain state. This makes exploitation opportunistic and cheap (a single `dispatch()` call), and given cross-chain bridging volumes and the many ways slippage/dust can occur, realistically likely over time.

### Recommendation
- Restrict `CallDispatcher.dispatch` to a caller allow-list (e.g., only the registered `HyperFungibleToken`/`WrappedHyperFungibleToken`/`IntentGatewayV2` instances that are expected to use it), or make the dispatcher per-caller/ephemeral (deployed or cleared per invocation) so no shared, permissionlessly-drainable balance persists.
- Add an explicit sweep step in `HyperFungibleToken.onAccept` and `WrappedHyperFungibleToken.onAccept` (and their upgradeable variants) mirroring `IntentsBase._execute`'s dust-collection pattern, transferring any residual token/ETH balance off the `CallDispatcher` back to the beneficiary or protocol treasury within the same transaction.
- At minimum, ensure the dispatcher never carries value across transaction boundaries by validating post-dispatch balance is zero for all tokens/ETH involved in the message, reverting otherwise so the request can be retried with corrected calldata.

### Proof of Concept
1. A relayer delivers an ISMP POST to `HyperFungibleToken.onAccept` with `message.to = CALL_DISPATCHER` and `message.data` encoding a `Call[]` that swaps the minted tokens on a DEX but, due to slippage tolerance or fee-on-transfer behavior, leaves a nonzero residual balance of the output token (or leftover native ETH from `Call.value`) sitting on the `CallDispatcher` after execution — `onAccept` mints, dispatches, and returns without checking or sweeping any remaining balance. [3](#0-2) 
2. An unrelated attacker observes the `CallDispatcher`'s balance increase (e.g., by monitoring `Transfer`/`Received` events or simply polling `balanceOf(dispatcher)`/`dispatcher.balance`).
3. The attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: residualToken, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, residualBalance)})]))` directly — this passes the `extcodesize(to) > 0` check (the token contract has code) and requires no special permission. [1](#0-0) 
4. The residual tokens/ETH are transferred to the attacker, permanently, with no way for the original sender/beneficiary to reclaim them.

**Note on verification limits:** I was unable to fully confirm from the indexed code whether every deployment of `CallDispatcher` is a single chain-wide singleton shared across app instances (versus per-app deployments), and I could not locate a persistent-balance sweep anywhere in `HyperFungibleToken`/`WrappedHyperFungibleToken` beyond what's shown above — a Devin session with full repository access should confirm deployment topology (via `evm/tests/foundry/MainnetForkBaseTest.sol` and any deployment scripts) before treating this as fully proven.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

            to: beneficiary,
