### Title
Webhook shop, topic, and delivery-metadata headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` (used by `Registry.process`) authenticates the *body bytes* alone. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values that `Registry.process` hands to the app's webhook handler as trusted, tenant-identifying metadata are read straight from HTTP headers that are excluded from the signed payload.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
only the `@raw_body` is included. `HmacValidator.validate_signature` computes the HMAC exclusively over that signable string: [2](#0-1) 

`Registry.process` then trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all header-derived — to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 
and those accessors read directly from unauthenticated headers: [4](#0-3) 

Shopify signs classic webhooks with the single app-wide `api_secret_key`, not a per-shop secret, so the same HMAC secret is valid across every shop that has the app installed. Consequently a valid `(raw_body, hmac)` pair obtained from a webhook delivered to one shop (e.g. the attacker's own store, or any store where the attacker can trigger a webhook of their choosing) is a valid HMAC for that exact body **regardless of which `shop-domain`, `topic`, or `webhook-id` header accompanies it**, because none of those fields are part of `to_signable_string`. The equality this breaks is:

`shop authenticated by HMAC == shop attributed to the processed webhook (request.shop)`

The gem verifies the former is "byte-identical, HMAC-authentic body" but the latter is taken from an arbitrary, unauthenticated header value that the receiving application (and this gem's `WebhookMetadata`) treats as the trusted tenant identifier.

### Impact Explanation
Any party capable of triggering a legitimate webhook delivery for one shop (including their own shop, which any merchant/unprivileged installer of a public app can do) obtains a valid `(body, hmac)` pair. They can replay that exact body with a modified `shopify-shop-domain` (and/or `shopify-topic`) header pointed at a different, victim tenant. `Registry.process` will pass HMAC validation and hand the handler a `WebhookMetadata` claiming to originate from the victim shop, with attacker-chosen body content. Any downstream logic that uses `data.shop` as a tenant key (updating per-shop records, revoking data, writing state keyed by shop) can be corrupted with attacker-supplied data attributed to another tenant — a cross-tenant integrity/confidentiality break.

### Likelihood Explanation
Obtaining a valid webhook body/HMAC pair requires only an app installation an attacker controls (any merchant who installs a public app can trigger events such as `app/uninstalled`, `shop/update`, etc.), no secret material, TLS interception, or privileged access is needed. Only the HTTP headers of the replayed request need to be modified, which is possible without any credentials since headers are not authenticated by the gem at all.

### Recommendation
Bind the identifying headers into the signed material, or otherwise cryptographically tie `shop`, `topic`, and `webhook_id` to the HMAC before trusting them in `WebhookMetadata`. At minimum, `Registry.process` should independently verify that `request.shop` corresponds to a shop that is actually expected/known to the app (e.g., cross-check against stored sessions) rather than trusting the header value implied to be authenticated merely because the body's HMAC validated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any webhook subscription (e.g. `shop/update`) to receive a legitimate delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker sends a POST to the app's webhook endpoint with the same body `B` and the same header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and/or a different `X-Shopify-Topic`.
3. `Utils::HmacValidator.validate` (via `Request#to_signable_string`, only body `B`) succeeds because the body/HMAC pair is legitimate. [5](#0-4) 
4. `Registry.process` invokes the handler with `WebhookMetadata` where `shop == "victim-shop.myshopify.com"`, even though that shop never sent this data — the app processes attacker-controlled content under the victim's tenant identity.
