### Title
Emporium's `isAllowedRecipient` grant lets any user drain another external action's residual balance via forged `deltaAmounts` in `runAction` - (File: contracts/external-actions/swaps/ExternalActionSwap.sol / contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`ExternalActionSwap.swap()` (used by `LifiExternalAction`) trusts the caller-supplied `deltaAmounts[0]` as the exact amount to swap, and `onlyAllowedRecipient` only checks `msg.sender`, not that the funds were actually just transferred in by `Hinkal._externalTransact`. Because `EmporiumUpgradeable.runAction()` executes attacker-defined "stateless" ops (`op.endpoint.call(op.callData)`) with `isAllowedRecipient[Emporium] == true` on `LifiExternalAction`, any unprivileged user who can get a valid Emporium proof for their own UTXO can make Emporium call `LifiExternalAction.runAction(forgedCircomData, forgedDeltaAmounts)` directly and sweep any pre-existing residual balance sitting in `LifiExternalAction` into their own new Hinkal UTXO.

### Finding Description
Equality that should hold: **tokens leaving `LifiExternalAction` during a swap == `-deltaAmounts[0]`, where `deltaAmounts[0]` is derived from `Hinkal._calculateDeltaAmount` for a legitimate UTXO's declared amount** [1](#0-0) . This equality is broken because `deltaAmounts` reaching `LifiExternalAction.runAction()` is not derived from `Hinkal` at all when the call originates from `EmporiumUpgradeable.runAction()`'s stateless-op loop instead of from `Hinkal._externalTransact`.

Path:
1. `ExternalActionBaseV2.onlyAllowedRecipient` only checks `isAllowedRecipient[msg.sender]` [2](#0-1) . It does not verify that `msg.sender` is `Hinkal` itself or that the call is part of a genuine `_externalTransact` flow.
2. `EmporiumUpgradeable.runAction()` iterates attacker-supplied `stack.ops`, and for "Stateless Interaction" ops performs `op.endpoint.call{value: op.value}(op.callData)` with arbitrary attacker-chosen `endpoint`/`callData` [3](#0-2) .
3. If `LifiExternalAction.isAllowedRecipient[Emporium] == true` (stated precondition), an attacker sets `endpoint = LifiExternalAction`, `callData = runAction(forgedCircomData, forgedDeltaAmounts)`. `onlyAllowedRecipient` passes because `msg.sender == Emporium`.
4. `ExternalActionSwap.swap()` computes `inputAmount = uint256(-deltaAmounts[0])` purely from the forged calldata [4](#0-3) , with no check that this amount was ever transferred into `LifiExternalAction` by `Hinkal`. It then calls `callRouter`, which spends `LifiExternalAction`'s *existing* balance (the residual dust) via `router.call{value: inputAmount}(...)` or `approveUnlimited` + `router.call(...)` [5](#0-4) , and sends the swap output to `msg.sender` (Emporium) via `transferERC20TokenOrETH(outputToken, msg.sender, amountToSendToHinkal)` [6](#0-5) . Choosing `feeStructure.feeToken` different from both tokens (or matching parameters that zero the fee) avoids the flat fee.
5. Back in `EmporiumUpgradeable.runAction()`, if the attacker includes `outputToken` in the outer `circomData.erc20TokenAddresses` with `deltaAmountChanges[i] == 0` (a legitimate zero-value deposit/withdraw declaration for their own UTXO), the observed `balanceChange = balancesAfter[i] - balancesBefore[i]` (the drained amount just received from `LifiExternalAction`) is treated as genuine swap output and forwarded via `handleOut()` to `msg.sender` (Hinkal) and packaged into a `UTXO` keyed to the attacker's own `circomData.stealthAddressStructure` [7](#0-6) .
6. The top-level `Hinkal.transact()` reconciliation only checks that Hinkal's own balance delta equals `amountChanges[i] + utxoAmount` [8](#0-7) ; this holds trivially because both sides reflect the same drained amount now flowing through the accounting — the check never verifies the *origin* of the funds is a genuine, previously-accounted deposit.

The root cause is that `onlyAllowedRecipient` is a coarse allow-list keyed only on `msg.sender`, and `ExternalActionSwap.swap`/`LifiExternalAction.callRouter` never validate that `deltaAmounts` corresponds to a balance actually just pushed in by `Hinkal`. Granting Emporium generic "call any endpoint" composability combined with being a trusted `isAllowedRecipient` on other actions turns any of those actions' residual balances into drainable funds for any Emporium user.

### Impact Explanation
Any residual ERC20/ETH balance stranded in `LifiExternalAction` (or any other external action listing Emporium as an allowed recipient) — arising from LI.FI router slippage/partial-fill refunds — can be stolen by an unprivileged attacker and minted as a legitimate-looking new Hinkal UTXO under their control. This is theft of protocol-held funds with no corresponding depositor accounting removed, i.e., value created/captured without being backed by a genuine prior nullifier spend — matching the Critical category (theft of shielded/in-flight funds / minting value without backing).

### Likelihood Explanation
Preconditions: `LifiExternalAction.isAllowedRecipient[Emporium] == true` (a plausible/expected configuration to enable Emporium-driven swaps) and `LifiExternalAction` holding a nonzero residual balance from a prior swap's slippage. The attacker needs only their own valid Emporium proof/UTXO (even a zero-value one), full control over `EmporiumStack.ops[].callData`, and knowledge of a valid LI.FI router calldata directing output back to `LifiExternalAction`. No special privileges are required. The attack is repeatable each time dust accumulates.

### Recommendation
Restrict `onlyAllowedRecipient`/`runAction` on swap-style actions so they can only be invoked as part of a genuine `Hinkal._externalTransact` flow (e.g., require `msg.sender == Hinkal` directly, not indirectly via Emporium's generic call-forwarding), or have `ExternalActionSwap.swap` verify that `inputAmount` was actually just received in the same call rather than trusting `deltaAmounts` blindly. Separately, Emporium's stateless-op call target should be restricted (allow-list/deny-list) from being able to call other Hinkal external actions' `runAction` entry points at all.

### Proof of Concept
Foundry fork test:
1. Deploy `LifiExternalAction` with `Emporium` in `_allowedRecipients`; seed it with a residual ERC20 (or ETH) balance by performing one legitimate `Hinkal.transact()` swap that leaves dust (mock LI.FI router to refund partial input).
2. As attacker, generate a valid proof for a minimal/zero-value Emporium action UTXO (using `formInputEmporiumMin` since `erc20TokenAddresses.length==0` is allowed, or non-zero with `deltaAmountChanges[i]=0` for `outputToken`).
3. Craft `EmporiumStack.ops[0] = { endpoint: LifiExternalAction, invokeWallet: false, callData: abi.encodeCall(runAction, (forgedCircomData, forgedDeltaAmounts)) }` with `forgedDeltaAmounts[0] = -int256(residualBalance)`.
4. Call `Hinkal.transact(...)` with this Emporium circomData.
5. Assert: `LifiExternalAction` balance before == residualBalance, after == 0 (or near-0); attacker's new UTXO commitment amount == drained amount minus router/hinkal fees; no nullifier was spent corresponding to that amount (`inputNullifiers` for that token is empty/unrelated).
