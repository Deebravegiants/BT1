## Analog Found

### Title
Missing allowlist/rate-limit enforcement on legacy WebAPI trigger messages allows unauthenticated triggering of workflow runs on all DON nodes - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The Kakarot report describes a case where a boundary/precondition check that looks sufficient on the surface actually skips a required validation step for a specific code path (`CREATE`/creation-code jumps), allowing an unprivileged caller to reach a downstream operation that should never be reachable without a prior authorization/validity check. The chainlink analog is `handler.HandleLegacyUserMessage` in the gateway's capabilities handler, which processes messages from unauthenticated HTTP clients and forwards them to every DON node without applying the allowlist/rate-limit check that the equivalent JSON-RPC/vault gateway path enforces.

### Finding Description
`HandleLegacyUserMessage` is the gateway-side entry point for legacy (non JSON-RPC v2, "message envelope") user requests. It validates payload structure, a non-zero timestamp, and message staleness, but the code contains an explicit TODO marking a missing authorization step: [1](#0-0) 

Right after this TODO, the method only checks that `msg.Body.Method == MethodWebAPITrigger`, converts the message to a request, and then, without any allowlist/subscription or rate-limit check, broadcasts it to every member of the DON: [2](#0-1) 

This is structurally identical to the Kakarot bug class: a precondition (here, "is this sender allowlisted to trigger this DON/workflow") that the surrounding code implies should be checked (as evidenced by the TODO and by the comment in `handleWebAPIOutgoingMessage` explicitly stating the trust model relies on "DON-side and Gateway-side allowlist" enforcement), but is actually skipped for this specific code path — letting an attacker's crafted-but-structurally-valid message flow through to a sensitive downstream action (`don.SendToNode` for every member) before authorization is performed.

By contrast, the newer JSON-RPC/vault gateway path explicitly performs `AuthorizeRequest`/allowlist checks before dispatching to nodes or acting on payloads (see `GatewayHandler.HandleGatewayMessage`/`GatewayVaultRequestProcessor.ProcessRequest`): [3](#0-2) 

The legacy capabilities `HandleLegacyUserMessage` path has no equivalent gate.

### Impact Explanation
Any unauthenticated/unprivileged client that can reach the gateway's public legacy message endpoint can submit a `web_api_trigger` message with an arbitrary (non-zero, non-stale) timestamp and have it broadcast to every node in the target DON, causing those nodes to process/execute the corresponding workflow trigger. This is an allowlist bypass leading to unauthorized job/workflow triggering on the DON — precisely the "unauthorized job run" / "allowlist... bypass" impact category. It also allows an attacker to consume gateway/DON resources (each request fans out to all DON members) without being subject to the intended per-sender allowlist/rate controls, unlike the analogous, already-hardened JSON-RPC vault path.

### Likelihood Explanation
The vulnerable code path is directly reachable from any client able to send a legacy-format message to the gateway HTTP endpoint (`Gateway.ProcessRequest` → `HandleLegacyUserMessage`), requires only a well-formed JSON payload with `method=web_api_trigger` and a recent timestamp, and needs no credentials, signature check, or allowlist membership. The missing check is explicitly flagged as a TODO in the code, confirming it was never implemented for this handler, making this a straightforward, low-effort exploitation path for any unprivileged actor.

### Recommendation
Add allowlist/subscription and rate-limiting enforcement in `HandleLegacyUserMessage` before dispatching to DON members — mirroring the `Authorizer`/allowlist gate used in the vault gateway path (`GatewayVaultRequestProcessor.ProcessRequest` → `AuthorizeRequest`) — so that only senders permitted for the target DON/workflow can trigger `web_api_trigger` messages, and so repeated/unauthorized attempts are rate-limited per sender.

### Proof of Concept
1. Craft a legacy-format `api.Message` with `Body.Method = "web_api_trigger"`, a valid non-zero `Timestamp` within `MaxAllowedMessageAgeSec`, and an arbitrary `Sender`/payload (no valid signature or allowlist membership required for this handler, since `HandleLegacyUserMessage` performs no such check before dispatch).
2. Submit it to the gateway's legacy message endpoint (`Gateway.ProcessRequest`) as demonstrated in existing tests such as `TestGateway_LegacyRequest_HandlerResponse` in `core/services/gateway/gateway_test.go`, which shows the legacy flow calling `HandleLegacyUserMessage` directly with no authorization mock configured.
3. Observe that `handler.HandleLegacyUserMessage` proceeds past the `// TODO: apply allowlist and rate-limiting here` comment and calls `don.SendToNode` for every DON member, dispatching the trigger to all nodes despite the sender never having been checked against any allowlist.
