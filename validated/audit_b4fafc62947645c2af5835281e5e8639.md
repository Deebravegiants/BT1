### Title
Unchecked multiplication in transaction fee burn calculation - (File: `runtime/src/bank/fee_distribution.rs`)

### Summary
`Bank::calculate_reward_and_burn_fee_details` computes the amount of collected transaction fees to burn using a raw `*` multiplication instead of a checked or saturating operation, mirroring the exact bug class described in the referenced RubiconMarket finding (raw `*` used for percentage/scaling math instead of a safe-math helper).

### Finding Description
The burn amount is computed as: [1](#0-0) 

```rust
let burn = fee_details.transaction_fee * self.burn_percent() / 100;
```

`self.burn_percent()` returns a constant 50 (`DEFAULT_BURN_PERCENT`), so this is functionally `transaction_fee * 50 / 100`, a raw unchecked multiply, unlike the rest of the same function which uses `saturating_add`/`saturating_sub` for the sibling `deposit` calculation: [2](#0-1) 

`fee_details.transaction_fee` is a `u64` field of `CollectorFeeDetails` that accumulates the base (non-prioritization) signature fee for every transaction processed in the slot via `accumulate`, which itself uses `saturating_add`: [3](#0-2) 

Because `accumulate` saturates on overflow, `transaction_fee` can, in principle, reach values up to `u64::MAX` after enough calls within a slot (each add saturates rather than reverting/erroring). Once `transaction_fee` exceeds `u64::MAX / 50` (~3.69 × 10^17), the raw multiplication `transaction_fee * self.burn_percent()` overflows. In a debug build this panics (`attempt to multiply with overflow`), and in a release build it silently wraps, producing an arbitrary, incorrect `burn` value. This function is invoked from the bank-commit path `distribute_transaction_fee_details`, which subtracts `burn` from `capitalization`: [4](#0-3) 

An incorrect `burn` value directly corrupts the `deposit` (leader reward) and the `capitalization.fetch_sub` amount — i.e., miscounted "burned" vs "rewarded" lamports, which is the direct analog of the original report's "improper tracking of sold out / bought out" impact.

### Impact Explanation
If triggered, this would either:
- Panic the validator during bank freeze/commit in debug builds (a deterministic path executed by every validator, so it would be a network-wide halt rather than a single-node crash), or
- In release builds, silently produce an incorrect `burn`/`deposit` split, corrupting `capitalization` and misallocating collected fees between burning and the leader reward — a form of miscounted value creation/loss in a bank-commit accounting path.

Since `distribute_transaction_fee_details` runs identically on every replaying node from the same accumulated `CollectorFeeDetails`, the corrupted result would be consistent across nodes (not a consensus divergence by itself), but it does represent concrete, incorrect on-chain fee/capitalization accounting.

### Likelihood Explanation
This requires `fee_details.transaction_fee` (the sum of `lamports_per_signature * signature_count` across all transactions in a single slot) to exceed roughly `u64::MAX / 50 ≈ 3.69 × 10^17` lamports. Given `lamports_per_signature` is governed by the cluster's fee schedule (typically in the low thousands of lamports) and slots are bounded by block-cost limits (limiting the number of transactions/signatures processable per slot), reaching this magnitude under realistic operating conditions is not feasible today. This mirrors the original report's own judge assessment that "in order to overflow... highly unlikely with majority of tokens" — likelihood here is similarly low under current fee-schedule and cost-model constraints, but the pattern remains a latent, unguarded raw-multiplication code path with no explicit upper bound enforced against `burn_percent()` scaling, unlike the parallel `deposit` computation in the same function which does use saturating arithmetic.

### Recommendation
Replace the raw multiplication with `checked_mul`/`saturating_mul` (consistent with the neighboring `deposit` calculation in the same function) to guarantee no silent wraparound or panic, e.g.:
```rust
let burn = fee_details.transaction_fee
    .saturating_mul(self.burn_percent())
    .saturating_div(100);
```

### Proof of Concept
Root cause is deducible directly by inspecting `calculate_reward_and_burn_fee_details`: [5](#0-4) 
combined with the saturating accumulation of `transaction_fee` in `CollectorFeeDetails::accumulate`: [6](#0-5) 
which together allow `transaction_fee` to reach magnitudes where the subsequent raw `*` in the burn calculation overflows (panicking in debug builds, wrapping in release builds), unlike the adjacent `deposit` computation which is fully saturating-safe.

        &self,
        fee_details: &CollectorFeeDetails,
    ) -> FeeDistribution {
        let burn = fee_details.transaction_fee * self.burn_percent() / 100;

#[derive(Clone, Debug, Default, PartialEq)]
pub struct CollectorFeeDetails {
    transaction_fee: u64,
    priority_fee: u64,
}

impl CollectorFeeDetails {
    pub(crate) fn accumulate(&mut self, fee_details: &FeeDetails) {
        self.transaction_fee = self
            .transaction_fee
            .saturating_add(fee_details.transaction_fee());
        self.priority_fee = self
            .priority_fee
            .saturating_add(fee_details.prioritization_fee());
    }

    pub fn total_transaction_fee(&self) -> u64 {
        self.transaction_fee.saturating_add(self.priority_fee)
    }

    pub fn total_priority_fee(&self) -> u64 {
        self.priority_fee
    }
}
