## Title
JWT replay-guard check-then-act race breaks single-use nonce mutual exclusion, allowing JWT reuse under concurrent requests - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
`WorkflowMetadataHandler.Authorize` implements JWT single-use (`jti`) replay protection with a check (`isReplay`) and a subsequent, separately-locked write (`recordUsage`), rather than one atomic check-and-set operation. Two concurrent calls to `Authorize` carrying the identical signed JWT can both pass `isReplay` before either calls `recordUsage`, allowing the same one-time JWT to be accepted more than once.

## Finding Description
`Authorize` calls `h.jwtCache.isReplay(claims.ID)` (which takes `cache.mu.RLock()`, checks, and releases) and later, after unlocked map lookups and signer-authorization checks, calls `h.jwtCache.recordUsage(claims.ID)` (which takes `cache.mu.Lock()` and writes): [1](#0-0) 
`isReplay` and `recordUsage` are independent critical sections with no shared lock spanning both: [2](#0-1) 
This is a genuine check-then-act (TOCTOU) gap: two goroutines can both observe `exists == false` from `isReplay` before either executes `recordUsage`, so both proceed past the replay check for the same `jti`. This contrasts with the vault package's `RequestReplayGuard.CheckAndRecord`, which performs the check and the write under a single lock: [3](#0-2) 
and is proven race-safe by `TestRequestReplayGuard_ConcurrentAccess`, which fires 100 goroutines with the identical digest and asserts exactly one succeeds — an equivalent test does not exist for `jwtReplayCache`. The existing `WorkflowMetadataHandler` test only exercises sequential, non-concurrent reuse: [4](#0-3) 
which does not touch the race window at all.

However, `VerifyRequestJWT` binds the JWT's `digest` claim to the specific JSON-RPC request being authorized (`req.Digest()`), and rejects mismatches: [5](#0-4) 
This means a replayed/duplicated JWT is only useful to re-authorize the *exact same* request content it was originally bound to (same digest) — it cannot be repurposed to authorize a different action. Additionally, at the `http_trigger_handler.go` call site, a separate in-flight-request-ID de-duplication mechanism exists and is exercised in `TestHttpTriggerHandler_HandleUserTriggerRequest`'s "duplicate request ID" and "duplicate JWT token and request ID" subtests, which reject concurrent duplicate `Request.ID`s with an "in-flight request" conflict error before/around the authorization path: [6](#0-5) 
I was not able to fully trace, within the remaining tool budget, the exact ordering between this in-flight-request de-duplication and the `Authorize` call inside `http_trigger_handler.go` (i.e., whether the in-flight guard fully closes the race window for this specific handler, or only reduces it). This is a material gap in verifying real-world exploitability of the race for the reachable gateway path.

## Impact Explanation
The underlying concurrency bug (check-then-act split between `isReplay` and `recordUsage`) is real and confirmed by direct code reading — it is not a false claim about the code's structure. However, the actual security impact is significantly narrower than "request impersonation / duplicate authorized workflow trigger" as claimed, because: (1) the JWT digest binds it to one specific request payload, so a "duplicate use" only re-authorizes the identical, already-issued request rather than an arbitrary new action; and (2) the gateway's HTTP trigger path has an independent in-flight-request-ID guard that appears to reject concurrent duplicate submissions of the same request ID, which is the exact scenario needed to exploit this race in practice. Given the request-digest binding, worst-case impact of winning this race is processing the same, already-signed single request twice rather than gaining any new privilege or forging a different action.

## Likelihood Explanation
Exploiting the race requires an attacker (or racing legitimate client) to fire two requests with byte-identical JWTs (hence identical underlying request content, per the digest binding) at the gateway within the narrow window between the RLock-protected check and the Lock-protected write. Whether this is practically exploitable at the reachable `http_trigger_handler.go` call site is unresolved because of the separate in-flight-request de-duplication logic observed in that handler's test suite, which appears to reject concurrent duplicate request IDs — a scenario that substantially overlaps with (and may fully preempt) the race window being described. This overlap was not fully resolved due to running out of available tool iterations, and is the deciding uncertainty for whether this claim maps to a genuinely triggerable end-to-end impact versus a latent internal-code race that is masked by an outer guard.

## Recommendation
Merge `isReplay` and `recordUsage` into a single atomically-locked check-and-record operation, mirroring `RequestReplayGuard.CheckAndRecord`, so the replay check and the marking of the `jti` as used occur under one critical section with no intervening unlocked logic. Add a concurrency test analogous to `TestRequestReplayGuard_ConcurrentAccess` that fires many goroutines with an identical `jti`/token against `WorkflowMetadataHandler.Authorize` and asserts exactly one succeeds, and separately verify (in the same test) whether `http_trigger_handler.go`'s in-flight-request-ID guard already prevents this race from being reachable in practice, to properly scope remediation priority.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
