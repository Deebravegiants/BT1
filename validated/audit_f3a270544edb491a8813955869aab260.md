### Title
Unchecked `copy_from_slice` into fixed-size signature buffer causes deterministic panic on attacker-controlled BEEFY vote data - (File: `evm/rust/src/conversions.rs`)

### Summary
`evm/rust/src/conversions.rs` implements `From<Vote> for SignatureWithAuthorityIndex`, which copies an ABI-decoded, attacker-controlled `bytes` field (`Vote.signature`) into a fixed `[u8; 65]` array with `copy_from_slice` without first checking that the source length equals 65 bytes. [1](#0-0) 

### Finding Description
`Vote` is an ABI type (`Beefy::Vote`) whose `signature` field is a Solidity `bytes` (arbitrary length), decoded from calldata/witness data supplied by whoever submits a BEEFY consensus proof. The conversion into the native `SignatureWithAuthorityIndex` type used by `beefy_verifier_primitives` does:
```
let sig_bytes = value.signature.to_vec();
let mut signature: TSignature = [0u8; 65];
signature.copy_from_slice(&sig_bytes);
``` [2](#0-1) 
`copy_from_slice` panics if `sig_bytes.len() != 65`. Unlike other conversions in the same file (e.g., `WithdrawParamsAbi::try_from`, `ModuleId::from_bytes`) that explicitly validate lengths before doing fixed-size copies/`from_slice` calls, this conversion has no such length guard. [3](#0-2) [4](#0-3) 

This is the same bug class as the OpenEXR CVE: a public entry point validates the outer container but not the length/content of a nested, attacker-controlled buffer before performing an unchecked copy into a fixed destination, producing a deterministic crash reachable from untrusted input.

The `SignatureWithAuthorityIndex` type this conversion produces feeds the BEEFY consensus-proof verification path used by `beefy_verifier_primitives`/`pallet-ismp-beefy`, exercised by `modules/consensus/beefy/prover/src/lib.rs`, `modules/consensus/beefy/primitives/src/lib.rs`, and tested against the pallet path in `modules/pallets/testsuite/src/tests/pallet_ismp_beefy.rs` and `parachain/simtests/src/pallet_beefy_consensus_proofs.rs`. [5](#0-4) 

### Impact Explanation
Any unprivileged relayer submitting a BEEFY consensus proof / vote whose `signature` bytes are not exactly 65 bytes triggers a Rust panic during the ABI-to-native conversion. Depending on the runtime context in which this conversion executes (extrinsic handling vs. off-chain worker/prover), this can abort the current call or crash the process handling consensus-proof submission, denying service to the BEEFY consensus verification route until restarted — a route-unable-to-deliver-messages condition for state/consensus updates that gate cross-chain message delivery.

### Likelihood Explanation
High: `Vote.signature` originates from externally supplied ABI-encoded `bytes`, which has no length constraint at the ABI level; producing an off-length signature requires no special privilege — any party capable of submitting/relaying a BEEFY proof can trigger it.

### Recommendation
Validate `sig_bytes.len() == 65` before `copy_from_slice`, returning a typed conversion error (mirroring the pattern already used by `WithdrawParamsAbi::try_from` and `ModuleId::from_bytes`) instead of panicking, and propagate that error through `TryFrom` rather than an infallible `From`. [1](#0-0) 

### Proof of Concept
1. Construct a `Beefy::Vote` ABI value with `signature` set to any byte string whose length is not 65 (e.g., 0 or 64 bytes) and an arbitrary `authorityIndex`.
2. Submit it as part of a BEEFY consensus proof through the path that invokes `From<Vote> for SignatureWithAuthorityIndex` (e.g., pallet-ismp-beefy `submit_proof` handling or the SP1/ECDSA BEEFY witness-construction path).
3. `signature.copy_from_slice(&sig_bytes)` panics because the source slice length does not match the fixed 65-byte destination, aborting/crashing the handling process.
