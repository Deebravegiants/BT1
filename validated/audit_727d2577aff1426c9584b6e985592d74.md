Audit Report

## Title
Cross-user response hijacking via attacker-controlled `MessageID` collision in `WebAPIHandler.HandleLegacyUserMessage` - ([File: core/services/gateway/handlers/capabilities/handler.go])

## Summary
`handler.HandleLegacyUserMessage` stores each incoming request's callback in the shared `h.savedCallbacks` map keyed solely by the client-supplied `MessageID`, with no check for an existing in-flight entry and no binding to the message's authenticated sender. Any client that can produce a validly signed message (which requires only its own private key, not any special privilege) can pick a `MessageID` already in use by another sender and silently overwrite that sender's callback registration, causing the eventual DON response for that ID to be delivered to the wrong caller.

## Finding Description
`gateway.ProcessRequest` routes legacy DON-ID requests to `h.HandleLegacyUserMessage(ctx, msg, callback)` after only calling `msg.Validate()` [1](#0-0) . `Validate()` checks signature length/format and message-field length constraints and extracts the signer into `m.Body.Sender`, but it performs no check that `MessageID` is unique or tied to a particular sender across requests [2](#0-1) .

Inside `HandleLegacyUserMessage`, the callback is registered unconditionally into the shared map keyed only by `msg.Body.MessageID`:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageID] = &savedCallback{id: msg.Body.MessageID, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [3](#0-2) 

There is no existing-entry/conflict check here, unlike the newer `httpTriggerHandler.setupCallback`, which explicitly rejects a duplicate `requestID` with `jsonrpc.ErrConflict` before registering a callback [4](#0-3) . There's even an unaddressed `// TODO: apply allowlist and rate-limiting here` comment right above the method dispatch in the legacy handler, confirming this path lacks additional protections [5](#0-4) .

When a DON node later responds, routing is purely by `MessageID`, with whichever callback is currently registered for that key receiving the response:
```go
h.mu.Lock()
savedCb, found := h.savedCallbacks[msg.Body.MessageID]
delete(h.savedCallbacks, msg.Body.MessageID)
h.mu.Unlock()
if found {
    codec := api.JSONRPCCodec{}
    return savedCb.SendResponse(...)
}
``` [6](#0-5) 

Signature verification in `Validate()` only proves that the request was signed by the sender presenting it — it does not prevent two different signers from independently choosing the same `MessageID` value. Because the map is shared across all senders and keyed only by this attacker-chosen string, the second signer's request silently overwrites the first signer's callback entry, and the eventual node response is delivered to the second (attacker) sender's callback rather than the original requester's.

## Impact Explanation
This maps to the explicit in-scope "cross-user response confusion" impact class. An attacker able to guess or collide on a `MessageID` in use by another user can: (1) cause the victim's in-flight request to never resolve correctly (its callback is evicted, resulting in denial of service until timeout), and (2) receive the DON's response payload that was intended to resolve the victim's request, disclosing another user's job/capability result data through the gateway.

## Likelihood Explanation
The attacker needs only to be an unprivileged client capable of signing and submitting a legacy JSON-RPC/DON-ID request with their own key — no operator, admin, or host access is required. Exploitability depends on the attacker knowing or predicting a victim's `MessageID` within the callback TTL window (`defaultCallbackMaxAgeSec = 120`) [7](#0-6) ; if client applications derive `MessageID`s predictably (e.g., from `WorkflowExecutionID` and method name as in `getMessageID`), collision is straightforward. Even absent prediction, nothing in the code prevents two callers from colliding on the same ID, whether accidentally or intentionally.

## Recommendation
- In `HandleLegacyUserMessage`, reject requests whose `MessageID` already has an active entry in `h.savedCallbacks`, mirroring the conflict check in `httpTriggerHandler.setupCallback` (`jsonrpc.ErrConflict`).
- Key `savedCallbacks` by a composite of `(Sender, MessageID)` rather than `MessageID` alone, since `Validate()` already populates `m.Body.Sender` from the signature.
- Consider migrating the legacy WebAPI trigger path onto the newer `httpTriggerHandler` model, which already implements per-request-ID conflict protection.

## Proof of Concept
1. Attacker A signs and sends a legacy JSON-RPC request to the gateway's DON-ID endpoint with `MessageID = "X"`, method `web_api_trigger`; `HandleLegacyUserMessage` stores `savedCallbacks["X"] = callbackA` and fans the request out to DON nodes.
2. Before the DON responds, attacker/victim B, signing with a different private key, sends another request also using `MessageID = "X"`; since `Validate()` and `HandleLegacyUserMessage` do not check for an existing entry, `savedCallbacks["X"]` is overwritten with `callbackB`.
3. When a DON node responds for `MessageID = "X"`, `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds `callbackB`, and delivers the response to B instead of A — demonstrable via a Go unit test that calls `HandleLegacyUserMessage` twice with distinct signers/callbacks but identical `MessageID`, then invokes `handleWebAPITriggerMessage` and asserts which callback receives the response.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageID) == 0 || len(m.Body.MessageID) > MessageIDMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageID, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonID) == 0 || len(m.Body.DonID) > MessageDonIDMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonID, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
