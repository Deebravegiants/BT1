### Title
Shared `msg.sender` identity in `EmporiumUpgradeable.runAction` CASE 2 lets any user hijack another user's Uniswap V3 NFT position - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
In `EmporiumUpgradeable.runAction`, CASE 2 ("Stateless Interaction") executes `op.endpoint.call{value: op.value}(op.callData)` directly from the `EmporiumUpgradeable` contract itself, so any external contract that records `msg.sender` as an owner/authority (e.g., Uniswap V3 `NonfungiblePositionManager.mint`) will record the shared `Emporium` contract address as owner, not the depositing user. Because CASE 2 requires no signature when `stack.signerAddress == address(0)`, and `op.endpoint`/`op.callData` are entirely attacker-controlled with only a check against `callHinkalWallet`/`doSendToRelay` selectors, any unprivileged user can later submit their own `transact()` targeting that same `NonfungiblePositionManager` to `decreaseLiquidity`/`collect`/`burn` a victim's `tokenId`, since the position manager only checks `msg.sender == owner`, and `msg.sender` will again be the shared `Emporium` contract.

### Finding Description
The claimed broken equality: `ownerOf(tokenId)` recorded by `NonfungiblePositionManager` should equal the depositing user's stealth address / `HinkalWallet`, but instead equals `EmporiumUpgradeable`'s own address, an identity shared by every user of the protocol.

Code path:
- `Hinkal.sol._externalTransact` routes to `IExternalActionV2(...).runAction(circomData, deltaAmountChanges)` [1](#0-0) .
- `EmporiumUpgradeable.runAction` is guarded only by `onlyAllowedRecipient`, which checks that `msg.sender` (i.e., `Hinkal.sol`) is a globally-allowed recipient - it does not authenticate or scope actions per depositing user [2](#0-1) .
- `EmporiumStack` (including `ops`, each an `EmporiumOperation{endpoint, invokeWallet, value, callData}`) is decoded straight from `circomData.externalActionData.externalActionMetadata`, which is attacker-supplied for their own `transact()` call [3](#0-2) .
- `verifyWallet` only enforces a signature when `stack.signerAddress != address(0)`; when `signerAddress == address(0)` (CASE 2, stateless) it returns immediately after marking `emporiumMessage` used - no cryptographic binding of `op.endpoint`/`op.callData` to the caller beyond the caller submitting a valid Hinkal proof for their own token deltas [4](#0-3) .
- In the loop, CASE 2 performs `(success, err) = op.endpoint.call{value: op.value}(op.callData);` directly from `EmporiumUpgradeable`'s own execution context, so `msg.sender` as seen by `op.endpoint` is the `EmporiumUpgradeable` contract address itself [5](#0-4) .

Root cause: `EmporiumUpgradeable` is a single shared contract instance used by all users of the protocol for CASE 2 stateless calls, and any state that an external contract associates with `msg.sender` (such as Uniswap V3's `ownerOf(tokenId)` set during `mint`) is therefore associated with `EmporiumUpgradeable`'s address, not with any specific depositor. Because CASE 2 does not require any specific signer or additional binding when `signerAddress == address(0)`, and `op.endpoint`/`op.callData` can be freely chosen per-call (only the wallet-hijack selectors `callHinkalWallet`/`doSendToRelay` are blocked), a completely different, unprivileged attacker can submit their own `transact()` with `op.endpoint == NonfungiblePositionManager` and `op.callData` set to `decreaseLiquidity`, `collect`, or `burn` for the victim's `tokenId`. `NonfungiblePositionManager` will authorize this because `msg.sender` (`EmporiumUpgradeable`) matches the position's recorded owner - it has no way to know that the actual economic owner is a different Hinkal user.

The balance-diffing logic in `runAction` (`balancesBefore`/`balancesAfter` over `circomData.erc20TokenAddresses`, `handleOut`) only tracks the ERC20 tokens explicitly listed by the caller; it does not prevent or detect that the underlying liquidity/fees released by `collect`/`decreaseLiquidity`/`burn` originated from someone else's LP position [6](#0-5) . The attacker simply lists the underlying tokens (e.g., WETH/USDC) in their own `circomData.erc20TokenAddresses`, and `handleOut` will transfer the resulting positive `balanceChange` straight to `msg.sender` (the attacker) via `transferERC20TokenOrETH` [7](#0-6) .

None of the existing guards prevent this: `onlyAllowedRecipient` only checks that the caller is `Hinkal.sol`; `verifyWallet` skips signature checks entirely for CASE 2; nullifier/root/proof checks in `Hinkal.sol` only validate the attacker's own UTXO spend/deposit, not the ownership of arbitrary external protocol state created by a previous, unrelated call.

### Impact Explanation
This is direct theft of a victim's Uniswap V3 LP position and its underlying liquidity/accrued fees by an unrelated, unprivileged attacker, matching the Critical category ("direct theft of shielded or in-flight user funds"). The attack is repeatable against any LP position (or any other stateful external protocol interaction) minted/created via CASE 2 through `EmporiumUpgradeable`, since the shared contract identity issue applies to every such interaction, not just one victim.

### Likelihood Explanation
Preconditions are modest: a victim must have used CASE 2 (`invokeWallet == false`/`signerAddress == address(0)`) to mint a Uniswap V3 position (or any operation where the callee records `msg.sender` as an authority) through `EmporiumUpgradeable`. The attacker needs only to know the resulting `tokenId` (observable on-chain via the `Transfer`/`IncreaseLiquidity` events from `NonfungiblePositionManager`) and craft their own valid `transact()` call with legitimate proof/UTXO data for their own funds - no privileged role, victim key, or victim cooperation is required. This is fully within the "unprivileged attacker" threat model.

### Recommendation
For CASE 2 stateless calls that interact with external protocols expected to track ownership/authority by `msg.sender` (e.g., NFT position managers), route the call through a per-user proxy/wallet contract (similar to `HinkalWallet` used in CASE 1) instead of executing it directly from the shared `EmporiumUpgradeable` contract, so that `msg.sender` as seen by the external protocol is unique to the depositing user rather than shared across all Hinkal users. Alternatively, restrict CASE 2 `op.endpoint` calls to an explicit allowlist of stateless-only functions/contracts that are known not to persist caller-scoped authority state.

### Proof of Concept
Foundry fork test plan:
1. Deploy/fork with real `NonfungiblePositionManager` and `EmporiumUpgradeable` wired as an allowed recipient of `Hinkal.sol`.
2. Victim calls `Hinkal.transact()` with valid proof/UTXO data whose `CircomData.externalActionData` targets `EmporiumUpgradeable`, with an `EmporiumStack` containing one CASE 2 op: `endpoint = NonfungiblePositionManager`, `callData = mint(...)`, `invokeWallet = false`, `signerAddress = address(0)`.
3. Assert `NonfungiblePositionManager.ownerOf(tokenId) == address(EmporiumUpgradeable)` (equality broken: expected victim's stealth address/wallet, actual is `Emporium`).
4. Attacker (unrelated account, own funds/UTXOs) calls `Hinkal.transact()` with their own valid proof, `CircomData.erc20TokenAddresses = [token0, token1]`, and an `EmporiumStack` with CASE 2 ops for `decreaseLiquidity`, `collect`, and `burn` on the victim's `tokenId`.
5. Assert the calls succeed (no revert), and assert attacker's ERC20 balances of `token0`/`token1` increase by the victim's deposited liquidity/fees, while the victim's position (`tokenId`) is now burned/drained - demonstrating theft without any authorization from the victim.
