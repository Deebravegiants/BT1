## Title
Tron `IntentGatewayV2.onAccept` lacks the relayer allowlist gate that the canonical EVM gateway enforces, allowing any relayer to forge escrow settlement - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The canonical EVM `IntentGatewayV2`/`ExtrinsicIntents.onAccept` requires `_checkRelayer(incoming.relayer)` before processing any `RedeemEscrow`/`RefundEscrow`/governance action, restricting escrow-affecting deliveries to a single authorised relayer. [1](#0-0)  The Tron fork of the same contract implements `onAccept` with the identical `RequestKind` dispatch and `authenticate()` gateway-instance check, but never calls any relayer allowlist check before releasing or refunding escrow. [2](#0-1) 

### Finding Description
This mirrors the RustFS bug class: a privileged action (`create_bucket` / here, escrow release) is exposed on an alternate, less-audited code path (FTPS MKD / here, the Tron variant of the same app) that omits an authorization check (`authorize_operation` for `s3:CreateBucket` / here, `_checkRelayer`) that the primary, canonical path enforces.

On the canonical EVM `IntentGatewayV2` (via `ExtrinsicIntents.onAccept`), every `onAccept` delivery — including `RedeemEscrow` and `RefundEscrow`, which move escrowed user/solver funds — is gated by `_checkRelayer(incoming.relayer)` before the request kind is even decoded: [1](#0-0) 
This was added specifically because the `IApp.onAccept` interface lets the host forward `incoming.relayer` as an arbitrary attacker-controlled value (any relayer that submitted a valid state/consensus proof), and the intent gateway's escrow settlement is high value enough that only one designated relayer is trusted to submit governance/settlement messages, per the accompanying changelog. [3](#0-2) 

The Tron deployment of `IntentGatewayV2`, however, retains the pre-fix `onAccept`: it checks `onlyHost`, decodes the `RequestKind`, and for `RedeemEscrow`/`RefundEscrow` only calls `authenticate(incoming.request)` (which validates the message's `source`/`from` against the registered peer gateway instance) — with no check at all on `incoming.relayer`: [2](#0-1) 

Because `authenticate()` only verifies the cross-chain *source* of the message (that it really came from the registered peer `IntentGatewayV2` instance on the counterparty chain), and not *who relayed it*, any relayer capable of submitting a valid ISMP proof to the Tron host can trigger `withdraw()` for a legitimately-sourced `RedeemEscrow`/`RefundEscrow` message. This defeats the entire point of the relayer allowlist that the canonical implementation added, on Tron specifically — an unprivileged actor (any relayer) can deliver/replay-order settlement messages there without being the authorised relayer, once the message itself is otherwise valid.

### Impact Explanation
An unauthorised relayer can force `withdraw()` execution paths (release of escrowed input tokens to a solver, or refund to a user) on the Tron `IntentGatewayV2` deployment without being the single relayer Hyperbridge governance intended to trust for this app. Since `authenticate()` is source-only, this weakens the intended defense-in-depth specifically added to stop a relayer from front-running/timing/tampering with settlement delivery (e.g. racing an admin-intended relayer, or -- combined with any future compromise of the proof/consensus path on Tron -- becoming the sole gate standing between escrow funds and an attacker). This is a real deviation from the security model documented and enforced on every other chain's gateway, constituting an unauthorized-app-action / permanently-weakened-authorization class bug reachable by any relayer, satisfying the "unauthorized app action" acceptance criterion.

### Likelihood Explanation
Medium-High reachability: any party that can act as a relayer for the Tron chain (an unprivileged role by design — Hyperbridge relaying is permissionless) can exploit this immediately once they can produce/relay a validly-sourced settlement message; no special privilege beyond being a relayer is required, and the bug is a straightforward omission relative to the fixed, canonical implementation that already exists in the same codebase.

### Recommendation
Add the same relayer allowlist enforcement used in `evm/src/apps/intentsv2/ExtrinsicIntents.sol` (`_relayer` storage slot, `setRelayer`, and a `_checkRelayer(incoming.relayer)` call at the top of `onAccept` before any request kind is processed) to `evm/tron/contracts/apps/IntentGatewayV2.sol`, and audit any other chain-specific forks of `IntentGatewayV2` for the same drift from the canonical, patched implementation.

### Proof of Concept
1. Deploy/observe the Tron `IntentGatewayV2` with a peer gateway registered for `SOURCE_CHAIN`.
2. An order is placed and filled cross-chain, producing a legitimate `RedeemEscrow` `PostRequest` from the registered peer instance.
3. Any relayer (not the chain's designated/authorised relayer) submits the proof and calls `host.dispatchIncoming(...)`, which invokes `IntentGatewayV2.onAccept(IncomingPostRequest({relayer: attackerRelayer, request: redeemEscrowRequest}))`.
4. `onAccept` calls only `authenticate(incoming.request)` (source check) — no `incoming.relayer` check exists — so `withdraw()` executes and escrow is released, exactly as it would if the canonical relayer had submitted it. Compare against `evm/tests/foundry/IntentGatewayV2Test.sol`'s `testOnAcceptRejectsUnlistedRelayer`, which shows the canonical EVM contract reverts with `IntentsBase.Unauthorized` for the same scenario — behavior absent from the Tron contract. [4](#0-3)
