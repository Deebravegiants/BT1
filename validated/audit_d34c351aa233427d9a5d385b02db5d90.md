This confirms the vulnerability: the webhook HMAC only covers `raw_body` (`to_signable_string` returns `@raw_body` only, `lib/shopify_api/webhooks/request.rb:35-38`), while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers (`lib/shopify_api/webhooks/request.rb:15-33`) and passed straight into `WebhookMetadata` after only a body-HMAC check in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`).

### Title
Webhook `shop` identity is not covered by HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw body only [1](#0-0) , while the `shop`, `topic`, `webhook_id`, and `api_version` fields used by the application are read verbatim from HTTP headers that are never included in the HMAC computation [2](#0-1) . `Registry.process` only checks `Utils::HmacValidator.validate(request)` (which validates the body against the shared `api_secret_key`) before constructing `WebhookMetadata` with the unauthenticated `shop` header value and dispatching it to the app's handler [3](#0-2) .

### Finding Description
This breaks the identity binding: **shop authenticated by the HMAC** should equal **shop the handler acts on**. `HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, api_secret_key, signable_string)` and compares against the `hmac-sha256` header [4](#0-3) , but `signable_string` is `@raw_body` alone [1](#0-0) . The `shop-domain` header is never part of that signed payload — it is read separately via `shopify_header("shop-domain")` [5](#0-4) .

Because `client_secret`/`api_secret_key` is shared across **all** merchant shops that install a given app (it is not per-shop), any unprivileged user who installs the target app on their own store will receive a legitimately HMAC-signed webhook whose body+HMAC pair is valid under that same shared secret. That user can then replay the exact same `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because the body and HMAC weren't modified, and `Registry.process` forwards the forged `shop` value into `WebhookMetadata`, so the host application's handler processes/stores the payload as if it originated from the victim tenant [6](#0-5) .

### Impact Explanation
This is a cross-tenant confusion vulnerability: an attacker controlling one tenant's webhook traffic can inject data attributed to (or trigger tenant-scoped side effects for) a different, victim merchant, because the gem's own signature validation does not bind the shop identity to the signed bytes. Depending on how the host app uses `WebhookMetadata#shop` (e.g., looking up/creating records, syncing inventory, granting entitlements per shop), this can lead to cross-tenant data corruption or unauthorized actions performed against a victim shop's data with attacker-controlled body content limited to whatever legitimate webhook topic the attacker owns.

### Likelihood Explanation
Any user can become an "unprivileged" attacker simply by installing the target app as a merchant, which is normal and requires no privileged access, no leaked token, and no `api_secret_key`/`client_secret` exposure. They only need to capture their own legitimate webhook delivery (raw body + `hmac-sha256` header) and resend it with a modified `shop-domain` header, since the gem performs no binding between the two.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values in the HMAC-signed payload verification (e.g., bind the shop domain into `to_signable_string`, or independently verify/authorize the `shop` header against a known, previously-established relationship such as an app-installed session before trusting it), rather than validating only the raw body while trusting unauthenticated headers for tenant identity.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers a webhook subscription (e.g., `orders/create`).
2. Attacker triggers the webhook (e.g., creates an order) and captures the raw POST body and the `x-shopify-hmac-sha256` header sent by Shopify to the app's webhook endpoint.
3. Attacker resends the identical raw body and `x-shopify-hmac-sha256` value to the same webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com` (and optionally spoofs `x-shopify-webhook-id`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the untouched raw body against the shared `api_secret_key` [7](#0-6) .
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ..., ...)` [8](#0-7)  and processes attacker-supplied data as if it came from the victim's shop.
