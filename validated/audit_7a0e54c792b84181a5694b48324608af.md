### Title
`EvmHost.dispatch()`/`fundRequest()` swap native fees via raw Uniswap V2 spot price with a `block.timestamp` deadline, trapping victim ETH on manipulation - ([File: evm/src/core/EvmHost.sol])

### Summary
When a caller pays Hyperbridge dispatch/relayer fees in native token, `EvmHost` swaps the supplied ETH for an exact amount of `feeToken()` directly against a Uniswap V2 pool's current spot reserves, with no TWAP, no minimum-output/maximum-slippage guard beyond `msg.value`, and a `deadline` set to `block.timestamp` (i.e. no real deadline protection). This mirrors the audited USSD issue of using an unprotected AMM spot price for a financially consequential on-chain calculation.

### Finding Description
`dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` in `EvmHost.sol` all follow the same pattern: [1](#0-0) [2](#0-1) [3](#0-2) 

Each calls `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. This is an exact-output swap priced entirely off the pool's instantaneous reserves (spot price) — there is no TWAP oracle, no `referencePrice`/`maxDeviationBps`-style guard (unlike the Uniswap V4 guard the Simplex solver implements, see `docs/content/developers/evm/simplex/pricing.mdx`), and the "deadline" parameter is `block.timestamp`, which imposes no real time bound since it is evaluated at execution.

The Uniswap V2 router's `swapETHForExactTokens` refunds any leftover ETH (the difference between `msg.value` and the actual amount needed at execution-time spot price) to `msg.sender` of the router call. Because `EvmHost` itself calls the router, `msg.sender` from the router's perspective is `EvmHost`, not the original external caller who supplied the ETH. Any refund is therefore captured by the `EvmHost` contract rather than returned to the depositor.

The SDK's own documentation flags this exact class of risk for the off-chain `quote()`/`quoteNative()` helpers: "Do not call `quote()` in smart contract transactions. It uses Uniswap's `getAmountsIn`, making it vulnerable to sandwich attacks." [4](#0-3)  That warning only covers the off-chain estimator, but the actual on-chain swap executed inside `dispatch()`/`fundRequest()` has the identical unprotected-spot-price exposure and is reachable by any unprivileged caller in a single transaction.

### Impact Explanation
Because the amount of native token needed is priced purely off the pool's spot reserves at execution time, an attacker can manipulate the WETH/feeToken pool immediately before a victim's `dispatch`/`fundRequest` transaction (a classic sandwich): by pushing the price down (adding feeToken liquidity / removing WETH from the pair or executing an opposite-direction swap) the exact-output swap consumes less ETH than the victim intended, and the difference is refunded to `EvmHost` itself instead of the victim — a real, permanent loss of the victim's native token with no recovery path, since `EvmHost` has no sweep/refund-to-sender mechanism for this residual balance shown in this contract. Because this fee-payment path is on every `dispatch()`/`fundRequest()` call — the core, unprivileged entry point for sending cross-chain messages and topping up relayer fees — this is reachable from a single submitted transaction by any user of the protocol, satisfying the "concrete...freezing of funds" bar.

### Likelihood Explanation
Any Hyperbridge deployment on a chain where the fee-token/WETH pair is a shallow or thinly-traded Uniswap V2 pool is exploitable with a standard sandwich/flashloan front-run, requiring no special privilege — only capital to move the spot price within one block, which is cheap on most V2 pools with modest liquidity. The bug triggers on the ordinary, expected usage path (paying dispatch fees in native token), so it does not require any unusual victim behavior.

### Recommendation
- Do not swap native fees on-chain against a raw spot price; require callers to pre-swap to `feeToken()` off-chain (already supported via `feeToken` payment path) or add explicit minimum-in/maximum-slippage bounds passed by the caller (`swapETHForExactTokens` return value checked against a caller-supplied `amountInMax`, reverting rather than silently keeping the difference).
- Set an actual deadline (e.g., `block.timestamp + X`) rather than `block.timestamp`.
- Refund any leftover ETH explicitly to the original `_msgSender()` (not `address(this)`), or expose a `sweepExcessEth`/refund function callable by the original payer.
- Consider adopting the same `referencePrice`/`maxDeviationBps` price-guard pattern already used for Uniswap V4 solver pricing (`docs/content/developers/evm/simplex/pricing.mdx`) to bound the acceptable spot price before the on-chain swap executes.

### Proof of Concept
1. Attacker observes a pending `dispatch(DispatchPost{...})` (or `fundRequest`) transaction from a victim, sent with `msg.value` computed off-chain via `quoteNative()`/`quote()` against the pre-attack spot price.
2. Attacker front-runs with a swap that shifts the WETH/feeToken pool's spot price so that `feeToken()` becomes cheaper in ETH terms (e.g., attacker sells feeToken into the pool, or buys WETH out of it, depending on `path` direction).
3. Victim's `dispatch()` executes `swapETHForExactTokens{value: msg.value}(post.fee, [WETH, feeToken()], address(this), block.timestamp)`. Because the price is now cheaper, the router only consumes a fraction of `msg.value` to produce `post.fee` tokens and refunds the remainder ETH to `msg.sender`, which resolves to `EvmHost`, not the victim.
4. Attacker (optionally) back-runs to restore the pool to its original price, pocketing arbitrage profit from steps 2–4, while the victim's excess ETH remains stranded inside `EvmHost` with no recovery mechanism exposed in this contract.

Note: I was unable to fully verify within the available iterations whether any other contract-level sweep/refund function exists elsewhere in the codebase that could recover ETH accidentally sent to `EvmHost` in this way (e.g., an admin-only sweep), so this should be confirmed against the full `EvmHost.sol` and its inherited `HostManager`/ownership contracts before treating the freeze as strictly permanent; a Devin session with full repository access would be needed to check `evm/src/core/HostManager.sol` and related admin functions exhaustively.
