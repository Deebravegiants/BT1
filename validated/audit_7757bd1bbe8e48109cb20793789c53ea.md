### Title
Missing checks-effects-interactions / reentrancy guard in Tron `IntentGatewayV2.withdraw` allows escrow drain via malicious beneficiary callback - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron port of the intents gateway, `evm/tron/contracts/apps/IntentGatewayV2.sol`, declares the contract as `contract IntentGatewayV2 is HyperApp, EIP712` [1](#0-0) , with **no `ReentrancyGuard`/`ReentrancyGuardTransient` inherited or `nonReentrant` modifier anywhere**, unlike the canonical EVM `IntentGatewayV2.sol`, which explicitly inherits `ReentrancyGuardTransient` and guards `fillOrder` with `nonReentrant` [2](#0-1) [3](#0-2) .

In the Tron variant's internal `withdraw` function, the token/ETH transfer (external interaction) is performed **before** the escrow accounting is decremented — a direct checks-effects-interactions violation and functionally the same bug class as the referenced `BvbProtocol.withdrawToken` report (external transfer that can trigger attacker code prior to state finalization, with no reentrancy protection anywhere in the call graph).

### Finding Description
In `withdraw`, for every token in `body.tokens`, the contract performs the transfer first, and only decrements the escrow mapping afterward: [4](#0-3) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;
    ...
    if (token == address(0)) {
        (bool sent,) = beneficiary.call{value: amount}("");
        if (!sent) revert InsufficientNativeToken();
    } else {
        (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
        if (!success) revert TransferFailed();
    }

    _orders[body.commitment][token] -= amount;   // <-- state update AFTER external call
    ...
}
```

The same pattern repeats for the transaction-fee redemption a few lines below: the `feeToken.call(...)` transfer happens, and only afterward is `_orders[body.commitment][TRANSACTION_FEES]` deleted [5](#0-4) .

Contrast this with the fixed, canonical EVM implementation in `IntentsBase._withdraw`, where the escrow mapping is decremented **before** the external transfer is made: [6](#0-5) 

The `beneficiary` address in a `WithdrawalRequest` originates from the order itself (`order.user`, i.e. attacker-controlled for a self-placed order that is later cancelled/refunded, or from the destination-chain `RedeemEscrow` message forwarded by the counterpart gateway) [7](#0-6) . `withdraw` is reached from `onAccept` for `RedeemEscrow`/`RefundEscrow` kinds and from `onGetResponse`, both of which are `onlyHost`-restricted [8](#0-7) , but the trigger is an unprivileged relayed cross-chain message that any relayer can deliver once the underlying request/response is available — the beneficiary/attacker does not need any special privilege to have this code execute with itself as the receiving contract.

Because there is no reentrancy guard anywhere in this contract (unlike the hardened `evm/src/apps/IntentGatewayV2.sol`, which was specifically patched for this exact class of bug, as documented and tested in `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`), a malicious `beneficiary` contract can, inside its `receive()`/token-transfer callback triggered during the `.call` in `withdraw`, re-enter other public entry points of the same contract (e.g. `placeOrder`, `select`, `cancel`, or the multi-token loop's not-yet-decremented `_orders[commitment][token]` state for the remaining tokens in the same `body.tokens` array) while the escrow accounting for the just-transferred token(s) is still stale. This reopens exactly the "escrow theft" / "fee theft" attack classes that the sibling EVM contract's regression tests (`testReentrancy_FeeTheft`, `testReentrancy_EscrowTheft_MultiOutput`) were written specifically to prevent by moving `_filled`/`_orders` updates before external calls and adding `nonReentrant`.

### Impact Explanation
This is a High severity finding: the Tron `IntentGatewayV2.withdraw` (and its fee-redemption tail) transfers value/tokens before finalizing internal escrow accounting and has zero reentrancy protection at the contract level. An attacker who controls the withdrawal `beneficiary` (a normal, unprivileged position for a solver/order-placer in the intents flow) can deploy a malicious receiving contract to exploit the stale accounting window during multi-token or fee withdrawals, resulting in theft of escrowed input/output tokens or fee-token funds beyond what is legitimately owed — a direct loss of user/protocol funds.

### Likelihood Explanation
Likelihood is high given the code as written: no reentrancy guard exists on this contract, transfers use raw low-level `.call`/ERC20 `.call(transfer.selector,...)` (both of which can trigger attacker-controlled code — a contract `receive()` for native transfers, or a malicious/ERC777-style token for the ERC20 branch), and CEI ordering is violated in exactly the pattern the sibling hardened contract's test suite was built to catch. Any order whose destination-chain beneficiary is attacker-controlled (which is the normal, permissionless case for solvers/order placers) can trigger the vulnerable path once the corresponding `RedeemEscrow`/`RefundEscrow` message is relayed.

### Recommendation
Apply the same fix already implemented in the canonical EVM `IntentGatewayV2`/`IntentsBase`:
1. Decrement `_orders[body.commitment][token]` (and delete the `TRANSACTION_FEES` entry) **before** performing the corresponding native/ERC20 transfer in `withdraw`.
2. Inherit `ReentrancyGuardTransient` (or an equivalent nonReentrant guard) in the Tron `IntentGatewayV2` contract and apply it to all externally reachable entry points that can trigger `withdraw`/`onAccept`/`onGetResponse` transfer paths, mirroring the protections already validated by `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`.
3. Replace raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` with `SafeERC20.safeTransfer`, consistent with the rest of the codebase.

### Proof of Concept
1. Attacker places a same-chain or cross-chain order via the Tron `IntentGatewayV2`, escrowing multiple tokens (e.g. native + ERC20) under a commitment where they control the eventual `beneficiary` (e.g. by cancelling their own order to trigger a `RefundEscrow`, per `_cancel` setting `beneficiary: order.user` [7](#0-6) ).
2. `beneficiary` is a malicious contract with a `receive()`/token-receive hook.
3. Once relayed, `onAccept` invokes `withdraw(body, isRefund)`. In the token loop, the first native transfer `beneficiary.call{value: amount}("")` triggers the attacker's `receive()` **before** `_orders[body.commitment][token] -= amount` executes for that token, and before the loop has reached/decremented the escrow entries for subsequent tokens.
4. Inside `receive()`, since no `nonReentrant` guard exists anywhere in the contract, the attacker re-enters a public function of `IntentGatewayV2` (e.g. re-triggers a flow that reads/relies on `_orders[commitment][...]`) while the stale (not-yet-decremented) escrow balances are still visible, allowing the attacker to extract more value than is legitimately owed for that commitment before the original `withdraw` call finishes zeroing out the accounting.
