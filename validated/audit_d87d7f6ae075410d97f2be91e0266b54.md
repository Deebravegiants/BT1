### Title
Webhook shop-domain spoofing via un-authenticated header outside HMAC scope - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC that `Utils::HmacValidator.validate` checks in `Registry.process` never covers the `X-Shopify-Shop-Domain` / `shopify-shop-domain` header. `Registry.process` nevertheless takes `request.shop` straight from that unauthenticated header and hands it to the webhook handler as the tenant identifier, breaking the binding: `shop attributed to the payload == shop that produced/authenticated the payload`.

### Finding Description
`Request#hmac` is computed by Shopify over the raw JSON body only, and `Request#to_signable_string` reflects that scope: [1](#0-0) [2](#0-1) 

`Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed material: [3](#0-2) 

`Registry.process` validates only the body HMAC, then immediately trusts `request.shop` to build `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because a single `client_secret` is shared across every shop that installs the app, any merchant who has that app installed on their own store legitimately receives correctly-HMAC-signed webhook deliveries for their own shop. Nothing in this gem binds the verified body to a specific shop identity — the equality that should hold, `HMAC-authenticated body ⇔ shop attributed by Registry.process`, does not hold, since the `shop` header is bytes parsed but never bytes verified.

### Impact Explanation
An attacker who controls one legitimately-installed shop (no `client_secret`, no victim access token, no privileged account needed) can capture a genuine webhook body/HMAC pair delivered to their own store, then replay that exact body/HMAC to the app's webhook endpoint while swapping the `shop-domain` header to any other shop that has the app installed. `HmacValidator.validate` still passes (it only checks the body), and `Registry.process` forwards the forged `shop` value to the host application's handler, letting the attacker inject data (e.g. spoofed order/customer/redact events) attributed to a shop they do not control — a cross-tenant identity-binding bypass rooted in this gem's own `Request`/`Registry` code, not in host misuse.

### Likelihood Explanation
Requires only that the attacker run the target app on one shop they legitimately control (a normal, unprivileged app installation) and know/guess another shop's `myshopify.com` domain (public information) — no secret material or victim credentials are needed, making this readily reachable.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com` and lets Shopify deliver a real webhook, capturing `raw_body` and the `X-Shopify-Hmac-Sha256` header (valid, since it's the genuine Shopify-signed body for that app's `client_secret`).
2. Attacker POSTs the identical `raw_body` and `X-Shopify-Hmac-Sha256` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because `to_signable_string` only checks `@raw_body`.
4. `Registry.process` builds `WebhookMetadata.new(shop: request.shop, ...)` using the forged header value and invokes the registered handler as if the event genuinely originated from `victim-shop.myshopify.com`.

### Recommendation
Have `Registry.process` (or `Request`) cross-check `request.shop` against an independently trusted source (e.g., the shop associated with the session/webhook subscription that was registered, or a list of shops known to have the app installed) before dispatching to handlers, rather than trusting the unauthenticated `shop-domain` header outright.
