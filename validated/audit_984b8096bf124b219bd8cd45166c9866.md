Based on my research, I found a strong analog. The `hyper-fungible-token` module's `on_accept` handler slices `message.from` with subtraction-based offset arithmetic that is not length-checked before use — the same bug class as the ksmbd `parse_sec_desc()` CVE (offsets/lengths taken from untrusted input used to index a buffer without validating the buffer is large enough).

### Title
Unchecked length subtraction on relayed message sender bytes causes panic/DoS in HFT `on_accept` - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`Pallet::on_accept` (or the equivalent inbound-message handler) in the `hyper-fungible-token` pallet derives the calldata-dispatch origin from `message.from` when no explicit signature is supplied. For EVM sources it computes `&from_bytes[from_bytes.len() - 20..]` to extract a 20-byte EVM address, exactly mirroring the unchecked offset arithmetic pattern in the kernel's `parse_sec_desc()` (`osidoffset`/`gsidoffset`/`dacloffset` subtracted/indexed without checking they are ≤ the buffer length).

### Finding Description [1](#0-0) 
```rust
} else {
    let from_bytes = message.from.as_ref();
    if source.is_evm() {
        T::EvmToSubstrate::convert(H160::from_slice(
            &from_bytes[from_bytes.len() - 20..],
        ))
    } else {
        let mut account = [0u8; 32];
        account.copy_from_slice(from_bytes);
        account.into()
    }
};
```
`message.from` originates from an ISMP `PostRequest` delivered by a relayer after proof verification, i.e. it is attacker-influenced application-layer payload data rather than protocol-verified metadata — the `from` field is set by the sending module on the source chain and is not length-constrained by the ISMP core codec (`PostRequest.from: Vec<u8>` — see `modules/ismp/core/src/router.rs`). If `from_bytes.len() < 20`, the expression `from_bytes.len() - 20` underflows in `usize` arithmetic, which panics in debug builds and, more importantly, panics in `no_std`/WASM runtime execution (checked arithmetic is enabled by default in Substrate runtimes), aborting the extrinsic. In the `else` branch, `account.copy_from_slice(from_bytes)` will also panic if `from_bytes.len() != 32`.

This is structurally identical to the CVE-2025-21946 pattern: an offset (`from_bytes.len() - 20`) is computed from attacker-controlled input length and used to index/slice a buffer without first validating that the buffer is large enough to satisfy the offset, causing an out-of-bounds condition (here, a `usize` underflow panic rather than a raw memory read, since Rust panics instead of reading OOB memory — but the runtime-halting effect is the direct analog).

### Impact Explanation
A malicious or misconfigured module on a connected chain (or a malicious relayer forging any part of the payload outside the merkle/commitment-verified request contents that ISMP does authenticate — the `from` field's *content* is not otherwise constrained) can craft a cross-chain POST request whose `from` field is shorter than 20 bytes (for an EVM source) or not exactly 32 bytes (for a substrate source) while carrying non-empty `data`. Dispatch of `on_accept` for this message panics, which in a Substrate runtime aborts the current transaction/block execution path for that inbound message handling, causing a denial of service for the HFT pallet's message processing (an unauthorized/uncontrolled halt reachable from a single relayed ISMP message) — this can also be used to grief relayers who submit the message, since delivering it triggers a runtime panic instead of a graceful `Err`.

### Likelihood Explanation
High likelihood: `message.from` is fully attacker/source-module controlled data forwarded through a relayer; ISMP's core commitment/consensus verification proves the request was included in the source chain's state, but does not constrain the *length* of arbitrary `Vec<u8>` fields like `from`. Any actor able to dispatch a cross-chain message to the HFT module from a connected chain (including a malicious dApp on that chain) can trigger this with zero extra privilege, and the check is trivially satisfiable (just send an empty or short `from`).

### Recommendation
Replace the unchecked slicing/copy with explicit length checks that return a typed `HftError` instead of panicking, e.g.:
```rust
if source.is_evm() {
    let addr_bytes = from_bytes
        .len()
        .checked_sub(20)
        .and_then(|start| from_bytes.get(start..))
        .ok_or(HftError::InvalidFromLength)?;
    T::EvmToSubstrate::convert(H160::from_slice(addr_bytes))
} else {
    let account: [u8; 32] = from_bytes
        .try_into()
        .map_err(|_| HftError::InvalidFromLength)?;
    account.into()
}
```

### Proof of Concept
1. On a connected EVM-source chain, dispatch an ISMP POST request targeting the HFT module's destination pallet, with `from` set to fewer than 20 bytes (e.g., `vec![0x01]`) and non-empty `data` containing valid `SubstrateCalldata` bytes (so the `!message.data.is_empty()` branch is entered) and no `signature` (so the vulnerable branch at lines 176-187 executes).
2. Relay the message through the standard relaying flow; ISMP core verifies the commitment/inclusion proof of the request but does not validate `from.len()`.
3. On delivery, `on_accept` computes `from_bytes.len() - 20` (e.g., `1 - 20`), underflowing `usize` and panicking, aborting execution of the inbound message dispatch. [2](#0-1)
