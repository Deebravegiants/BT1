### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant webhook impersonation - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body (`to_signable_string` returns `@raw_body`), while the shop identity (`shop-domain` header) that `ShopifyAPI::Webhooks::Registry.process` hands to the app's handler is read from an HTTP header that is never included in the signed bytes.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`HmacValidator.validate` verifies the signature strictly against `verifiable_query.to_signable_string` (the body), never touching headers: [3](#0-2) 

`Registry.process` trusts this unauthenticated `shop` value and forwards it directly to the app's webhook handler as the tenant identifier, immediately after the HMAC check passes: [4](#0-3) 

This is the exact "field acted on but not covered by the HMAC" pattern: the equality the gem implicitly promises is `hmac_verified_bytes == identity_bytes_used_for_tenant_scoping`, but in reality `hmac_verified_bytes` = `raw_body` while `identity_bytes_used_for_tenant_scoping` = `shop-domain header`, which are disjoint. Anyone who has ever legitimately received one authentic webhook delivery (e.g., by installing the app on any shop, including their own free/dev shop) possesses a valid `(raw_body, hmac)` pair signed with the app's real secret. Because the header is not part of the signed material, they can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` value for a different (victim) shop. `Registry.process` will validate the HMAC successfully (it only checks the body) and will call the handler with `WebhookMetadata` claiming the attacker-chosen shop, even though no valid signature for that shop/body combination was ever produced by Shopify.

### Impact Explanation
This breaks the tenant-scoping identity binding the gem is trusted to provide: an app that keys per-shop side effects (e.g., data deletion, GDPR redaction handling, subscription/billing state changes, cache invalidation, order/customer processing keyed by `shop`) off `WebhookMetadata#shop` as delivered by `Registry.process` can be made to apply body content sent for shop A to shop B's data, since the gem presents the `shop` field as coming from a "verified webhook" call. This is a cross-tenant identity-binding bypass reachable purely from a normal internet-facing webhook endpoint, without needing the app's `client_secret`, an access token, or any privileged account — only possession of one legitimately received webhook body/signature pair (which any user who installs the app for any shop can obtain).

### Likelihood Explanation
The attack requires no secrets beyond one authentic `(body, hmac)` pair the attacker already legitimately possesses (trivially obtainable by installing the target app on a shop they control, or observing any webhook delivery to their own endpoint), and no cryptographic breaking of HMAC-SHA256 — only exploiting that the header is unauthenticated. The only gem-level control is `Registry.process`, and it performs no cross-check between the header-derived `shop` and anything bound to the signed body.

### Recommendation
Bind the shop identity into the signed material, or otherwise cryptographically authenticate the `shop-domain` header before trusting it in `Registry.process`/`WebhookMetadata`. At minimum, since Shopify's genuine webhook delivery always sends the shop domain as a header alongside the HMAC that only covers the body, the gem should document this limitation explicitly and/or provide a mechanism (e.g., requiring apps to compare the delivered `shop` against a shop they have an active, verified session/access token for) rather than exposing `WebhookMetadata#shop` as if it were part of the verified payload. If Shopify's webhook protocol allows it, incorporate the shop domain into the HMAC signable string.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic (e.g. `orders/create`) to capture a genuine `(raw_body, shopify-hmac-sha256)` pair signed by the app's real `client_secret`.
2. Replay the captured request to the app's webhook endpoint, keeping `raw_body` and `shopify-hmac-sha256` unchanged, but setting `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds successfully (all required headers present); `Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates because the signature only covers `raw_body`.
4. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: <attacker's original body>, ...)`, causing the app to process attacker-controlled data attributed to the victim shop. [4](#0-3)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
