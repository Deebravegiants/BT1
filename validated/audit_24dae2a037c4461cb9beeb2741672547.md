### Title
Webhook shop identity is not authenticated by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, while the `shop` (and `topic`) that the handler subsequently trusts as the tenant identity are taken from HTTP headers that are excluded from that HMAC. An attacker who controls any legitimately installed shop (a "trial"/attacker-owned store, i.e. an unprivileged holder of a valid webhook body+HMAC pair) can take a webhook body that Shopify legitimately signed for their own shop and replay it with the `shop-domain` header swapped to a victim shop, causing the host application to process attacker-controlled data as if it originated from the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request` mixes in `Utils::VerifiableQuery` and defines the signable content as only the raw body: [1](#0-0) 

The `shop` and `topic` fields used later are parsed straight from headers, entirely outside the HMAC computation: [2](#0-1) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (the body only) and compares it with the value from the `hmac-sha256` header: [3](#0-2) 

`Registry.process` only calls this HMAC check, then immediately forwards `request.shop` (an unauthenticated header) and `request.topic` to the handler as the tenant/topic identity: [4](#0-3) 

Because `shop-domain` (and `topic`, `webhook-id`, `api-version`) are never bound to the HMAC, the equality the application implicitly relies on — `authenticated_shop == shop_used_by_handler` — does not hold. Any actor who possesses one valid `(raw_body, hmac)` pair generated by Shopify for their own shop (trivial: install the app on any shop and trigger a webhook) can resend that exact body/HMAC pair to the host app's webhook endpoint with the `x-shopify-shop-domain` header set to an arbitrary victim shop. `HmacValidator.validate` still succeeds because it never inspects the shop header, and `WebhookMetadata.shop` handed to the handler is the attacker-chosen value.

### Impact Explanation
Host applications built on this gem are expected to trust `WebhookMetadata#shop` (passed from `request.shop`) to select the tenant record/session to operate on, per the documented processing flow: [5](#0-4) 

Since the shop identity is unauthenticated, an attacker holding only credentials for their own (or any) shop can cause the host application to attribute attacker-controlled webhook data (order events, GDPR/compliance topics, uninstall notifications, etc.) to a different, victim tenant, i.e. cross-tenant access/data confusion in any consumer of this gem that keys business logic off `WebhookMetadata#shop`.

### Likelihood Explanation
Exploitation requires no secrets beyond having ever received one legitimate webhook (obtainable by installing the target app on any shop, including the attacker's own trial store), and no interaction with the victim shop. The header can be freely modified because HTTP request headers are entirely attacker-controlled on the wire before reaching the host server. This is a low-effort, repeatable spoof.

### Recommendation
Bind the shop (and ideally topic/webhook-id/api-version) into the HMAC-covered content, or otherwise cryptographically bind them before use — e.g. verify `shop-domain` against the session/shop associated with the currently registered webhook subscription, or include the header values in `to_signable_string` mirrored against a value independently confirmed via a GraphQL lookup, matching how Shopify's own webhook signature is scoped. At minimum, document loudly that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant selection without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any webhook topic the app is registered for; Shopify delivers a request with a valid `x-shopify-hmac-sha256` computed over the raw body using the app's `api_secret_key`.
2. Attacker captures `raw_body` and the `hmac-sha256` header value.
3. Attacker resends the identical `raw_body`/HMAC pair directly to the host app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body-derived HMAC and passes: [6](#0-5) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload actually originated from the attacker's own shop, letting the attacker inject/confuse data cross-tenant.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
