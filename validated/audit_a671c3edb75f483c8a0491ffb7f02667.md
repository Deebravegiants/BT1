### Title
Webhook Shop/Topic/Webhook-ID Headers Not Covered by HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by application handlers are read directly from unauthenticated HTTP headers. This is the exact bug class described in the report — a field that is *acted on* (the shop/tenant identifier) is not *covered* by the signature that is supposed to authenticate the request.

### Finding Description
`Utils::HmacValidator.validate` verifies a request by comparing a computed HMAC against the object's `hmac` accessor, using `to_signable_string` as the signed payload: [1](#0-0) 

For webhooks, `Webhooks::Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

But the `shop`, `topic`, `webhook_id`, and `api_version` values used everywhere else in the request object — and passed straight through to the application's webhook handler — come from HTTP headers that are never part of the signed content: [3](#0-2) 

`Webhooks::Registry.process` validates only the HMAC of the body, then forwards the unauthenticated `shop`, `topic`, and `webhook_id` header values straight to the registered handler as tenant-identifying metadata: [4](#0-3) 

The equality the gem is implicitly claiming to guarantee is:
`HMAC_valid(raw_body) == true` implies `shop_header is authentic`

But the actual guarantee provided is only:
`HMAC_valid(raw_body) == true` implies `raw_body is authentic` (regardless of `shop_header`, `topic_header`, `webhook_id_header`)

Because the app's `api_secret_key` is a single, shop-independent secret (the same key signs webhooks for every shop the app is installed on), any `(raw_body, hmac)` pair that is valid for one shop is also a syntactically valid pair for every other shop the app serves. Since `shop-domain`, `topic`, and `webhook-id` headers are never included in the signed bytes, an attacker who has legitimately received one real webhook from Shopify (e.g., by triggering an event, such as placing/cancelling an order, on their own store where the app is installed) can capture that exact `raw_body` + `hmac-sha256` header pair and POST it to the app's webhook endpoint again with the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header values swapped to point at a different shop that has the app installed. `Utils::HmacValidator.validate` still succeeds, since it only checks `raw_body` against the HMAC, and `Registry.process` will dispatch to the handler claiming the event originated from the victim shop.

### Impact Explanation
This breaks the tenant-identity binding the webhook subsystem is relied upon to provide. Any app handler that trusts `WebhookMetadata#shop` (built directly from the unauthenticated header) to select which tenant's data to read or mutate can be made to act on behalf of, or write data attributed to, a shop the attacker does not control — a cross-tenant access primitive achievable by an ordinary merchant/user of the app, without needing the `api_secret_key`, an access token, or any privileged account.

### Likelihood Explanation
Exploitability requires only: (1) the app is installed on any shop the attacker controls (a normal unprivileged merchant), (2) the attacker can trigger and capture one legitimate webhook delivery for their own shop (trivial — e.g., place a test order), and (3) the app has at least one other shop installed for a target tenant. No secrets, tokens, or elevated access are required beyond normal merchant use of the app — this fits an "unprivileged internet user" threat model. The only constraint is that the raw body content itself must be something the handler will still act on meaningfully when relabeled to a different shop (e.g., generic body shapes like order/product payloads are commonly reusable across shops).

### Recommendation
Include the tenant-identifying fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed content, or otherwise cryptographically bind them to the HMAC (e.g., compute the signature over `shop + topic + webhook_id + raw_body` rather than `raw_body` alone) in `Webhooks::Request#to_signable_string`, and reject any webhook whose header-derived identifiers were not part of the verified signature.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com` and on `victim-shop.myshopify.com` (both real, unprivileged merchant installs).
2. Trigger a webhook event on `attacker-shop.myshopify.com` (e.g., `orders/create`) and capture the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent to the app's webhook endpoint.
3. Replay that exact captured body and `X-Shopify-Hmac-Sha256` value to the same webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally spoof `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only checks the untouched raw body.
5. The registered handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, processing attacker-controlled/attacker-originated data as if it came from the victim tenant.

          received_signature = verifiable_query.hmac
