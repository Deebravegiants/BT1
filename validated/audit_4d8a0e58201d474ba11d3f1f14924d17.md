Attacker-crafted `swap_xdr` route loads arbitrary pool code that drains the signer's wallet under their own auth tree - ([File: contracts/swap-aggregator/src/venues/dispatch / controller/src/strategies/swap.rs])

### Summary
The swap aggregator decodes a caller-supplied `swap_xdr` byte payload into a program whose hop records name `pool` and token addresses by registry index. No venue allowlist exists: `dispatch_hop`/`invoke_contract` calls whatever contract the payload names (`contracts/swap-aggregator/src/venues/comet.rs:30-34`, `phoenix.rs:23-25`, `sushi.rs:48-50`). A rogue "pool" contract on that call stack can call `token.transfer(victim, attacker, …)` on any token the victim holds. Because `execute_strategy` only requires `sender.require_auth()` and Soroban simulation records the rogue transfer as a child of the caller's authorization entry, signing the simulated transaction executes the theft. This is the on-chain analog of CVE-2026-24152: convincing a user to load a maliciously crafted file (here, a crafted route payload) achieves code execution in the victim's security context.

### Finding Description
- `execute_strategy(sender, total_in, swap_xdr)` authenticates only `sender.require_auth()` once, then runs payload-named contracts under invoker auth. The router "calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization" (`docs/explanation/threat-model.md:154-165`).
- The controller path grants the router exactly one input transfer (`authorize_transfer_as_current`, `contracts/controller/src/strategies/swap.rs:34`) before `router.execute_strategy` (`swap.rs:37`), so a malicious route enters from `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, or direct `execute_strategy`.
- The harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates the full kill chain: `RogueHopPool::swap` calls `token::Client::new(env, &wallet_token).transfer(&victim, &to, &amount)` (lines 62-71); simulation records that transfer as a child of Alice's `swap_collateral` entry (lines 206-222); enforcing mode executes it once signed, leaving `wallet(alice) == 0` and `wallet(attacker) == WALLET_BALANCE` for a token "the protocol never listed" (lines 224-225).

### Impact Explanation
Theft of user funds. The stolen amount is unbounded by the routed input, `min_out`, or the controller's post-swap risk gates — the payload minimum and final health check bound only the swap itself. Any token balance in the signer's wallet (including unrelated, never-listed assets) can be transferred to the attacker in the same transaction that delivers a "fair" swap, so the victim sees a successful operation while losing their wallet. Both the composed path (`swap_collateral` et al., where the signer is the account owner) and the direct router path (`execute_strategy`) expose this.

### Likelihood Explanation
Reachable by a single unprivileged address: the attacker deploys a rogue pool contract, crafts `swap_xdr` naming it as a hop pool, and serves the quote (e.g., via a malicious or compromised route source). The victim signs whatever auth tree simulation produces; clients that don't decode and reject foreign child invocations sign the poisoned tree. The threat model itself states "an honest swap strategy gives the caller no child entry, and a direct router swap gives exactly one input transfer. A client must decode the route it signs and refuse an authorization tree with any other child" — i.e., safety currently depends entirely on client-side verification, not on any contract-side constraint.

### Recommendation
Constrain the trust surface contract-side: maintain a venue/pool allowlist on the router (or require hop pools to be registered and governance-approved), so payloads cannot place arbitrary code inside the caller's auth tree. Short of that, pin each hop's authorization to a fixed function/argument shape so a payload-named contract cannot inject additional `transfer` sub-invocations into the caller's tree; document and enforce in the SDK/quote path that any signed auth tree containing children beyond the single input `transfer` is rejected.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:
1. Alice supplies 10,000 USDC; attacker registers `RogueHopPool` with plan `(alice, wallet_token, attacker, WALLET_BALANCE)` (lines 111-125).
2. Route `swap_xdr` names the rogue pool; Alice calls `try_swap_collateral` — recording mode shows the rogue `wallet_token.transfer(alice → attacker)` attached under her `swap_collateral` auth entry (lines 195-227).
3. Signing that tree executes the theft: `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`, while the swap itself returns the fair ETH output (line 226).
