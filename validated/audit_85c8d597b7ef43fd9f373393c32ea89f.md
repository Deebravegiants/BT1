## Title
Webhook Shop-Domain Header Is Not Covered by HMAC, Allowing Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `ShopifyAPI::Utils::HmacValidator` verifies the HMAC solely against that body. The `shop-domain` header — which is the very field the library hands to the app's webhook handler as the tenant identifier — is never part of the signed material. Because a single Shopify app uses one `api_secret_key` shared across every installed shop, a valid HMAC for shop A's webhook body remains valid when replayed with shop B's `shop-domain` header, letting an attacker who controls one tenant impersonate another tenant's webhook traffic.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `shop` is read straight from an unauthenticated header: [2](#0-1) 

`Registry.process` validates only the HMAC over that body, then immediately trusts `request.shop` to build the metadata passed to the app's handler, with no cross-check against the shop that actually owns the signature: [3](#0-2) 

`HmacValidator.validate` computes the signature only from `to_signable_string` (the body) and the app's `api_secret_key`/`old_api_secret_key`, never mixing in the shop domain: [4](#0-3) [5](#0-4) 

The identity binding that should hold is:
`shop_domain_verified_by_HMAC == shop_domain_delivered_to_handler`

In this implementation the left side doesn't exist at all — the HMAC binds only the body — while the right side (`data.shop`) is exactly what the gem's own documentation tells integrators to trust for tenant routing: [6](#0-5) 

Because the `api_secret_key` is shared across all shops installed on one app (multi-tenant), any legitimate merchant/tenant who has the app installed can capture a genuinely Shopify-signed webhook delivered to their own endpoint (raw body + valid `x-shopify-hmac-sha256`), then POST that exact body/HMAC pair to the app's public webhook endpoint again, substituting the `shopify-shop-domain` / `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it never looked at the header), and `Registry.process` hands the handler a `WebhookMetadata` claiming the (attacker-chosen) victim shop, with attacker-controlled `body`.

### Impact Explanation
This breaks the tenant boundary the app relies on: the receiving application processes attacker-supplied webhook content as if it belongs to a shop the attacker does not control. Per the library's documented usage pattern (`perform_later(topic:, shop_domain: data.shop, webhook: data.body)`), this can be used to inject or overwrite data keyed by the victim shop's identifier — a cross-tenant access/data-injection primitive, which the rules classify as Critical impact.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate (even low-tier/trial) merchant with the target app installed, so they can trigger and capture one authentic HMAC-signed webhook, then replay it with a forged shop header directly to the app's public HTTP endpoint. No access to the app's `api_secret_key`, access tokens, or any privileged account is required — this is exploitable by any unprivileged internet user who can install the app on their own store.

### Recommendation
Bind the shop identity into the verified material, e.g., include the `shop-domain` header (and/or `webhook_id`/`topic`) in `to_signable_string`, or have `Registry.process` cross-validate `request.shop` against an independently trusted source (such as the shop tied to the webhook subscription that generated the signature) before constructing `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`) that is delivered to the app's public webhook endpoint with a valid `x-shopify-hmac-sha256` computed over the raw body using the app's shared `api_secret_key`.
2. Attacker captures the raw body and the valid HMAC value.
3. Attacker re-sends an HTTP POST to the same public webhook endpoint with the identical raw body and HMAC header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which validates successfully because it only checks the body.
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, causing the app to act on victim-shop's tenant data using attacker-supplied content.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
