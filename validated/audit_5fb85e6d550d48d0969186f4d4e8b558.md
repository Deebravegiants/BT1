### Title
Webhook `shop` (and `topic`) identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw HTTP body of an incoming webhook, while the `shop` (tenant identity), `topic`, `api_version`, and `webhook_id` values — all taken from unauthenticated HTTP headers — are used unverified by `Registry.process` to route data to the app's handler. This breaks the intended binding: `hmac_verified_bytes == identity_used_downstream`. Since Shopify signs all webhooks for an app installation with the app's single shared `client_secret` (the same value used for every shop that installs the app), any actor who legitimately installs the app on their own store can capture a validly-signed webhook body and replay it against the app's webhook endpoint while forging the `shopify-shop-domain` (and/or `shopify-topic`) header to point at a different, victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all pulled straight from HTTP headers, with no cryptographic tie to the body or its signature: [2](#0-1) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)` (which checks `to_signable_string`, i.e. the body) and then unconditionally trusts `request.shop` and `request.topic` when dispatching to the handler: [3](#0-2) 

`Utils::HmacValidator` computes/compares the signature purely from `verifiable_query.to_signable_string`, i.e. the body for webhooks — it never mixes in `shop`, `topic`, or any other header: [4](#0-3) 

Because Shopify apps use one shared `api_secret_key` (`client_secret`) to sign webhooks for *every* installed shop, a signature that is valid for one tenant's body is valid HMAC-wise regardless of which shop the body is attributed to. An attacker who installs the app on their own (attacker-controlled) shop can:
1. Trigger a real webhook from Shopify to the app (e.g. by creating an order/customer on their own store), obtaining a body + valid `X-Shopify-Hmac-SHA256` signature from Shopify.
2. Replay that exact `raw_body`/HMAC pair to the app's webhook endpoint, but substitute the `shopify-shop-domain` header (and optionally `shopify-topic`) with the victim shop's domain / desired topic.
3. `Utils::HmacValidator.validate` still returns `true` because it only checks the (unmodified) body against the signature.
4. `Registry.process` builds a `WebhookMetadata` with `shop: <victim-domain>` and dispatches attacker-controlled body content to the handler as if it originated from the victim tenant. [5](#0-4) 

Any host application that uses `data.shop` (as documented) to decide which tenant's records to update/create — the pattern the gem's own docs recommend — will act on attacker-controlled data under a false tenant identity.

### Impact Explanation
This breaks the equality `bytes_covered_by_HMAC == shop_identity_used_by_handler`, letting a low-privileged actor (anyone who can install the app on any store) inject or manipulate data attributed to a different, victim shop/tenant inside the merchant application — i.e. cross-tenant access/write, matching the Critical impact category defined in scope.

### Likelihood Explanation
Requires only that the app be publicly installable (or that the attacker has any shop where they can trigger a webhook) — no leaked credentials, TLS interception, or privileged access needed; the whole class of `shop`/`topic` header being outside HMAC coverage is inherent to how `Request`/`HmacValidator` are implemented in this gem.

### Recommendation
Bind the shop/topic identity into the value being authenticated (e.g., verify `X-Shopify-Shop-Domain` corresponds to a shop that legitimately has this app installed via server-side session lookup before trusting it, and/or reject processing unless the resolved shop from an authenticated source, such as a stored offline session, matches the header), rather than trusting the `shop`/`topic` headers purely because the raw body's HMAC validates.

### Proof of Concept
1. Install the target app on an attacker-owned shop `attacker.myshopify.com`.
2. Trigger a webhook (e.g., `orders/create`) from Shopify to the app; capture `raw_body` and `X-Shopify-Hmac-Sha256`.
3. POST to the app's webhook route with the same `raw_body`/HMAC but `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` (verifies only `raw_body`), so `ShopifyAPI::Webhooks::Registry.process` dispatches the attacker's body to the handler tagged as belonging to `victim.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
