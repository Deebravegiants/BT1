### Title
Withdrawal status misattribution when matching by `assetId` instead of a unique per-withdrawal identifier - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain completion status of a specific withdrawal by matching entries returned by the POA Bridge indexer using only the withdrawal's `assetId`, instead of a per-withdrawal unique identifier (e.g., index, destination address, or amount). When a single NEAR transaction contains multiple `ft_withdraw` intents for the same asset (a supported use case per `createWithdrawalCompletionPromises` in `sdk.ts`, which handles arrays of `WithdrawalParams`), the matching logic can return the status/`txHash` of a different withdrawal than the one being queried.

### Finding Description
`describeWithdrawal` explicitly documents the risk in its own comment: [1](#0-0) 

```
async describeWithdrawal(...) {
	const response = await this.getWithdrawalStatusWithRetry(args);
	// Response list is unsorted, so we match by assetId instead of index
	const withdrawal = findMatchingWithdrawal(
		response.withdrawals,
		args.withdrawalParams.assetId,
	);
	...
	if (withdrawal.status === "COMPLETED") {
		return { status: "completed", txHash: withdrawal.data.transfer_tx_hash };
	}
	...
}
```

The equality this logic is supposed to preserve is: *the `txHash`/`status` reported for withdrawal N corresponds to the actual on-chain settlement of withdrawal N*. Because the match key is only `assetId` (not index, destination address, or amount), if two or more withdrawals of the same asset are in flight from the same NEAR transaction — a scenario explicitly supported by `IntentsSDK.createWithdrawalCompletionPromises` (`packages/intents-sdk/src/sdk.ts:557-609`), which maps an array of `withdrawalParams` to one `watchWithdrawal` promise per index — `findMatchingWithdrawal` can return the wrong entry from the unsorted `response.withdrawals` list for a given index. This breaks the binding between the queried withdrawal identity and the reported completion outcome.

The internal-utils equivalent path (`packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts:35-84`) has the same limitation: `WithdrawalCriteria` is `{ assetId: string }` only, so `findMatchingWithdrawal` there is likewise unable to distinguish between multiple concurrent withdrawals of the same asset. [2](#0-1) 

### Impact Explanation
If an integrator relies on `watchWithdrawal`/`waitForWithdrawalCompletion` per-index promises (as the SDK's own `createWithdrawalCompletionPromises` API encourages for batched withdrawals) to decide when to credit a user or finalize a withdrawal record, a same-asset multi-withdrawal batch can cause one withdrawal's promise to resolve with another withdrawal's `txHash`, or resolve as "completed" prematurely while the actually-intended withdrawal is still pending. This matches the "status or hash misreport making an integrator credit or refund twice" High-impact category, since downstream systems keying off the reported hash/index could mark the wrong withdrawal as done or double-count settlement.

### Likelihood Explanation
This requires no malicious actor — it is triggered by the SDK's own supported feature of batching several `withdrawalParams` (potentially of the same `assetId`) into a single call, which is explicitly documented and handled in `sdk.ts`. Any integrator issuing two or more withdrawals of the same token in one intent/transaction and using the per-index completion tracking is exposed. However, I could not locate the exact body of `findMatchingWithdrawal` (only its call sites), so I cannot confirm whether it also considers `destinationAddress`/`amount` in some deduplicated form, which would reduce or eliminate the risk — this uncertainty should be verified before treating this as fully confirmed.

### Recommendation
Extend the matching key used in `findMatchingWithdrawal` (both in `poa-bridge.ts` and `internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) to include the withdrawal's index/nonce, destination address, and amount — not `assetId` alone — so each per-withdrawal completion promise is guaranteed to resolve with the outcome of the exact withdrawal that was requested, especially for batches containing multiple withdrawals of the same asset.

### Proof of Concept
Not independently reproducible from the indexed context because the body of `findMatchingWithdrawal` was not retrievable within the tool budget — the finding is based on the explicit comment and matching signature `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` at `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:319-322`, combined with `IntentsSDK.createWithdrawalCompletionPromises` supporting arrays of withdrawals (`packages/intents-sdk/src/sdk.ts:557-609`). Confirming exploitability requires inspecting the full `findMatchingWithdrawal` implementation to verify whether `assetId` is indeed the sole disambiguator when the same asset is withdrawn twice in one batch.

export async function waitForWithdrawalCompletion({
	txHash,
	withdrawalCriteria,
	signal,
	baseURL,
	retryOptions = RETRY_CONFIGS.TWO_MINS_GRADUAL,
	logger,
}: {
	txHash: string;
	withdrawalCriteria: WithdrawalCriteria;
	signal: AbortSignal;
	baseURL?: string;
	retryOptions?: RetryOptions;
	logger?: ILogger;
}): Promise<WaitForWithdrawalCompletionOkType> {
	return retry(
		async () => {
			const result = await getWithdrawalStatus(
				{ withdrawal_hash: txHash },
				{ baseURL, fetchOptions: { signal }, logger },
			);

			const withdrawal = findMatchingWithdrawal(
				result.withdrawals,
				withdrawalCriteria,
			);
			if (withdrawal == null) {
				throw new PoaWithdrawalInvariantError(
					"POA Bridge didn't return withdrawal matching criteria",
					result,
					txHash,
					withdrawalCriteria,
				);
			}

			if (withdrawal.status === "COMPLETED") {
				if (withdrawal.data.transfer_tx_hash == null) {
					throw new PoaWithdrawalInvariantError(
						"POA Bridge didn't return transfer_tx_hash for COMPLETED withdrawal",
						result,
						txHash,
						withdrawalCriteria,
					);
				}

				return {
					destinationTxHash: withdrawal.data.transfer_tx_hash,
					chain: withdrawal.data.chain,
				};
			}
