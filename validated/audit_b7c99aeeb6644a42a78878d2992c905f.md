### Title
SSRF/`client_secret` exfiltration via unvalidated `dest` claim in `TokenExchange.exchange_token()` - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`TokenExchange.exchange_token()` builds the OAuth request host directly from the session token's `dest` claim without passing it through `Utils::ShopValidator.sanitize!`, unlike every other credential-issuing flow in the same file and module (`migrate_to_expiring_token`, `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`), which all call `ShopValidator.sanitize!` before constructing the request host.

### Finding Description
`exchange_token` decodes the caller-supplied `session_token` with `JwtPayload.new(session_token)` [1](#0-0) , then takes `dest_shop = jwt_payload.shop` (the `dest` claim, stripped of `https://`) and uses it, unsanitized, both to build the `Session` used as the HTTP client's host and as the returned session's `shop`: [2](#0-1) 

Contrast this with the sibling method in the very same file, `migrate_to_expiring_token`, and with `ClientCredentials.client_credentials` / `RefreshToken.refresh_access_token`, all of which call `Utils::ShopValidator.sanitize!(shop)` before building the session/host: [3](#0-2) [4](#0-3) [5](#0-4) 

`ShopValidator.sanitize!` is exactly the boundary that is supposed to guarantee "host == trusted Shopify domain" before the app's `client_secret` is sent anywhere [6](#0-5) . In `exchange_token`, this equality (`request host == a domain in TRUSTED_SHOPIFY_DOMAINS`) is never established for the `dest` claim; the value only has to pass `JwtPayload`'s own checks, which are limited to signature validity, expiry/nbf leeway, and `aud == Context.api_key` — there is no check that `dest` is a myshopify/shopify.com/spin.dev/shop.dev host: [7](#0-6) 

The `client_secret` and `client_id` are then sent in the POST body to `https://#{dest_shop}/admin/oauth/access_token` [8](#0-7) .

### Impact Explanation
If `dest_shop` can be influenced to an attacker-controlled host, the app's `client_secret` and `client_id` — high-value credentials — would be sent to that attacker-controlled host (SSRF carrying the app's credentials, High severity per the given impact categories). This directly mirrors the analog class called out in scope: "a host validated versus the host that receives the access token or `client_secret`."

### Likelihood Explanation
Exploitability is bounded by the fact that `dest` sits inside a JWT that must still pass HMAC-SHA256 verification against `Context.api_secret_key` (or `old_api_secret_key`) in `JwtPayload#decode_token` [9](#0-8) . I could not find any path in this gem by which an unprivileged, unauthenticated internet user forges or otherwise obtains a session token with an arbitrary `dest` value without already possessing the app's `api_secret_key` — which the scope rules explicitly exclude ("anything requiring `api_secret_key`... is out of scope"). Session tokens are normally minted and signed exclusively by Shopify for the actual store origin, so under Shopify's real token-issuance behaviour `dest` should always be a genuine `*.myshopify.com`/`*.spin.dev` host. The missing `ShopValidator.sanitize!` call is a real inconsistency and defense-in-depth gap relative to every sibling method, but I cannot demonstrate a concrete unauthenticated exploitation path with the code available in this gem's scope — proving actual exploitability would require confirming whether any host application/Shopify token-issuance behavior could ever produce a `dest` outside the trusted domain list, which is outside what `lib/shopify_api/**` can show.

### Recommendation
Apply `Utils::ShopValidator.sanitize!(dest_shop)` to the `dest` claim in `TokenExchange.exchange_token()` before constructing `shop_session`, exactly as is already done in `migrate_to_expiring_token`, `ClientCredentials.client_credentials`, and `RefreshToken.refresh_access_token`, so the "host receiving `client_secret` is a trusted Shopify domain" invariant is enforced uniformly across all credential-exchange code paths.

### Proof of Concept
Not reproducible as a concrete unauthenticated exploit from this gem's code alone: doing so would require a validly HMAC-signed session token whose `dest` claim is an attacker-controlled host, and no path to forge such a token without the app's `api_secret_key` was found within `lib/shopify_api/**`. The finding is reported as a structural inconsistency/missing defense-in-depth check (`ShopValidator.sanitize!` omitted only in `exchange_token`, present in all sibling credential-issuing methods) rather than a demonstrated end-to-end attack.

        [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
