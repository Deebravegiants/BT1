### Title
Webhook Shop-Domain Header Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (tenant) attribute from the unauthenticated `X-Shopify-Shop-Domain` / `shopify-shop-domain` HTTP header, while the HMAC signature verified by `ShopifyAPI::Webhooks::Registry.process` only covers the raw request body. Because the app's `client_secret` (and therefore the HMAC key) is identical for every shop that installs the app, any party who can obtain one valid `(body, hmac)` pair — e.g., by triggering a webhook event on their own store — can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header, and the request will still pass validation. The tenant identity is never actually bound to the signature.

### Finding Description
`Request#hmac` and `Request#to_signable_string` only expose/sign the raw body: [1](#0-0) [2](#0-1) 

`shop` is read directly from a header that is never part of the signed payload: [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then hands `request.shop` straight to the host application's handler as the tenant identity, with no additional check that the shop matches the signed content: [4](#0-3) 

`HmacValidator.validate_signature` confirms the check is a pure body/secret HMAC compare with no shop binding: [5](#0-4) 

Because `client_secret` (the HMAC key) is the same across every shop that has installed a given app (there is no per-shop signing key), `HMAC(secret, body)` is identical no matter which shop actually generated the event. This breaks the intended identity binding `shop_signed == shop_used`, analogous to the reported bug class where a field is *acted upon* but not *covered* by the authenticating computation — here `shop` is the identity used to route/attribute webhook data, while the HMAC only authenticates `body`.

### Impact Explanation
This is a cross-tenant identity confusion: a request can be crafted (replaying a legitimately observed `body`+`hmac` pair from any shop that shares the app's `client_secret`, i.e., any installer of the same app) with a forged `shop-domain` header pointing at a *different* merchant. The host application's `WebhookHandler#handle` receives `WebhookMetadata` with the attacker-chosen `shop` value alongside a validly-signed `body`, and will attribute/store/process that webhook data under the wrong tenant. This meets the Critical bar of cross-tenant access, since data intended for/about one merchant can be injected into another merchant's tenant scope purely by manipulating an unauthenticated header.

### Likelihood Explanation
Exploitation requires the attacker to have at least one valid `(body, hmac)` pair signed with the same app `client_secret` used across all of the app's installations — obtainable by any legitimate merchant who installs the app on their own store and triggers a webhook event (a routine, unprivileged action for an "unprivileged internet user" in the sense of not needing the target's credentials). No access to the victim's token, secret, or account is needed; only the shared app secret's signing behavior over the fixed body content and the ability to replay an HTTP request with a modified header.

### Recommendation
Bind the tenant identity into the signed material, or otherwise cryptographically tie `shop` to the verified payload, e.g.:
- Require and verify that the `X-Shopify-Shop-Domain` header matches a shop domain independently known to be associated with the specific webhook subscription/topic (e.g., cross-check against registrations stored server-side per shop), rather than trusting the header at face value.
- Where possible, include the shop domain in the signable string used for HMAC verification (if Shopify's delivery format allows binding headers into the signature) or perform an out-of-band verification (e.g., re-fetch webhook/shop identity via the Admin API using a session tied to the claimed shop) before trusting `request.shop` for tenant attribution.
- At minimum, document/enforce in `Registry.process` that consuming applications must not treat `request.shop` as authenticated without additional verification.

### Proof of Concept
1. App "X" is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`; both share the same `client_secret` (per Shopify's per-app, not per-shop, secret model).
2. Attacker triggers an event on `attacker-shop.myshopify.com` (e.g., updates a product) and captures the resulting legitimate webhook `raw_body` and its `X-Shopify-Hmac-Sha256` value — both fully within their control as the store owner.
3. Attacker POSTs this exact `raw_body` and `hmac` to the app's webhook endpoint, but replaces the header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(client_secret, raw_body)` — this still matches because `raw_body` and the secret are unchanged.
5. `handler.handle(data: WebhookMetadata.new(topic: ..., shop: request.shop, body: request.parsed_body, ...))` is invoked with `shop == "victim-shop.myshopify.com"`, causing the host application to process/store attacker-controlled data under the victim tenant. [4](#0-3)
