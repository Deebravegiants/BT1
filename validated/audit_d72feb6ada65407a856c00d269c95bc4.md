### Title
Attacker-controlled `timeStamp` in `DepositOnChainUtxosExternalAction` allows duplicate on-chain UTXO commitments, permanently freezing a victim's shielded funds - (File: `contracts/external-actions/DepositOnChainUtxosExternalAction.sol`)

### Summary
`DepositOnChainUtxosExternalAction.runAction` builds on-chain UTXOs whose commitment preimage is `(amount, erc20Address, stealthAddress, timeStamp)`, where `timeStamp = circomData.timeStamp + utxoIndex` is taken verbatim from unverified user calldata instead of `block.timestamp`. Because the nullifier used to spend a leaf is a deterministic function of only the commitment value and the owner's private key (not of the leaf's tree index), an attacker can repeat the exact same `(amount, token, stealthAddress, timeStamp)` tuple across two separate deposit transactions targeting the same victim stealth address, producing two Merkle leaves with an identical commitment. Once the victim spends the first one, the second becomes permanently unspendable because it collapses to the same nullifier, which is already marked used.

### Finding Description
Commitments for these on-chain deposits are computed in `HinkalBase.createOnchainCommitment`: [1](#0-0) 

The `timeStamp` field of the UTXO struct is not derived from `block.timestamp` for this action (unlike the analogous proofless-deposit path, which explicitly does `timeStamp: block.timestamp`): [2](#0-1) 

Instead, `DepositOnChainUtxosExternalAction` sets it from fully caller-supplied `circomData.timeStamp` (documented in the contract's own NatSpec as intentionally caller-determined): [3](#0-2) [4](#0-3) 

There is no per-transaction randomness/nonce tied to the block or to a unique counter enforced on-chain — `circomData.timeStamp` is arbitrary, and `checkOnchainCreation`/`performHinkalChecks` in `HinkalHelper.sol` never validate its freshness or uniqueness, they only check `amountChanges`/`inputNullifiers` are zero when `onChainCreation` is set: [5](#0-4) 

Nullifier derivation in the proof circuit depends only on the commitment value and the spender's `nullifyingPrivateKey` — not on the leaf's Merkle index: [6](#0-5) 

If two leaves carry the identical commitment (same `amount`, `erc20Address`, `stealthAddress`, `timeStamp`), they necessarily produce the identical nullifier for the true owner. The on-chain nullifier registry enforces global uniqueness: [7](#0-6) 

Thus after the victim spends the first duplicate leaf, `nullifiers[N] = true` is set; any later attempt to spend the second, otherwise legitimate, value-bearing leaf reverts with `"Nullifier cannot be reused"`, even though that leaf's funds were never spent. This breaks the (leaf, spendability) invariant: a leaf the tree/circuit accepted as valid and value-bearing becomes permanently unspendable.

### Impact Explanation
This is a permanent freezing of user (victim) shielded funds — a Critical-severity outcome per the rules ("permanent freezing of user funds"). An attacker (any unprivileged EOA who can call `Hinkal.transact` with `externalActionId` routed to `DepositOnChainUtxosExternalAction`) can deposit into a victim's known stealth meta-address twice using the same `circomData.timeStamp`/`amount`/token, silently duplicating a commitment the victim believes represents two independent, spendable UTXOs. One of the two amounts becomes permanently frozen the moment the victim spends the other.

### Likelihood Explanation
The attack requires no privileged role, no relayer collusion, and no admin key — only the ability to call `transact` targeting the whitelisted `DepositOnChainUtxosExternalAction` with attacker-chosen `circomData.timeStamp`/metadata and knowledge of the victim's public stealth address components (which are necessarily public/derivable to allow anyone to deposit to a stealth address, per the design of `DepositOnChainUtxosExternalAction`). The attacker only needs to fund the token amount being deposited (which can even be the attacker's own funds sent "as a gift"/probe, or performed against amounts a victim is expected to receive from a third party), making this straightforward and reproducible.

### Recommendation
Derive the on-chain UTXO `timeStamp` from `block.timestamp` (as already done in `Hinkal._createProoflessDepositCommitments`) or, if a caller-chosen per-UTXO timestamp is required for offline-generation reasons, incorporate an on-chain enforced strictly-increasing nonce or a chain-side randomness/hash of `keccak256(msg.sender, block.number, blockhash)` mixed into the commitment preimage so identical `(amount, token, stealthAddress)` tuples cannot ever produce identical commitments/nullifiers across two separate deposits.

### Proof of Concept
1. Attacker learns victim's public `stealthAddressStructure` components (needed publicly so third parties can deposit to the victim, per this contract's stated purpose).
2. Attacker calls `Hinkal.transact` with `externalActionId` pointing at `DepositOnChainUtxosExternalAction`, `circomData.onChainCreation[i] = true`, `circomData.amountChanges[i] = 0`, `circomData.timeStamp = T`, `externalActionMetadata` encoding `utxoAmounts[i][0] = X`, and `circomData.stealthAddressStructure` = victim's structure. This creates leaf L1 with `commitment = hash4(X, token, victimStealthAddress, T)`.
3. Attacker repeats step 2 identically (same `T`, `X`, token, stealth structure) in a second transaction. This creates leaf L2 with the identical `commitment` value as L1, at a different Merkle index.
4. Victim later spends L1 normally: the circuit computes `nullifier = f(commitment, signature(nullifyingPrivateKey, commitment))` and `HinkalBase.insertNullifiers` marks it used.
5. Victim attempts to spend L2 (a distinct, still-unspent, value-bearing leaf): the circuit computes the same `commitment` → same `nullifier`, and `Hinkal.transact` reverts with `"Nullifier cannot be reused"`, permanently locking the funds represented by L2.

    function insertNullifiers(
        uint256[][] calldata inputNullifiers,
        bool[] calldata onChainCreation
    ) internal {
        for (uint256 i = 0; i < inputNullifiers.length; i++) {
            for (uint256 j = 0; j < inputNullifiers[i].length; j++) {
                if (onChainCreation[i] == true) break;
                if (inputNullifiers[i][j] != 0) {
                    require(
                        !nullifiers[inputNullifiers[i][j]],
                        "Nullifier cannot be reused"
                    );
                    nullifiers[inputNullifiers[i][j]] = true;
                    emit Nullified(inputNullifiers[i][j]);
                }
            }
        }
    }
