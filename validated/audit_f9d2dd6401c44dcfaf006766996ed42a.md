### Title
Webhook `shop`/`topic` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, while the tenant-identifying `shop-domain` header (and `topic`) are read straight from unauthenticated HTTP headers and later trusted by `Registry.process` to route the webhook to a handler and populate `WebhookMetadata.shop`. This is the exact bug class from the report: a field that is *acted on* (`shop`, used as the tenant identity for downstream processing) is not bound by the cryptographic check (`hmac`), which only covers `@raw_body`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` and `Request#topic` are pulled directly from HTTP headers with no cryptographic binding to the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string` (i.e. the body) — it never validates `shop` or `topic`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.topic` and `request.shop` — values that were never part of the signed material — to select the handler and construct `WebhookMetadata` for the app's business logic: [4](#0-3) 

The broken identity binding, expressed as an equality that should hold but doesn't:

`shop_that_produced_the_HMAC-valid_body == shop_header_trusted_by_Registry.process_as_the_tenant`

Because the HMAC is computed only over `@raw_body`, any request whose body is byte-identical to a previously-observed, legitimately-signed webhook (e.g., one the attacker received for their own store, which they fully control and can trigger arbitrarily many events on) keeps a valid signature even if the `X-Shopify-Shop-Domain` / `X-Shopify-Topic` headers are swapped for a different (victim) shop before being replayed to the host app's webhook endpoint. `Utils::HmacValidator` will report `true` because it never inspects those headers, and `Registry.process` will hand the forged `shop` value straight into the handler as if it were the authenticated tenant.

### Impact Explanation
This crosses the "cross-tenant access" boundary explicitly listed as Critical impact: an unprivileged internet user who legitimately controls one Shopify store (attacker's own tenant, easily obtainable via a free/dev store) can produce genuine HMAC-valid webhook bodies, then relabel the `shop-domain` header to a victim shop and have the host application's `WebhookHandler` process business logic (e.g., `customers/redact`, order/customer updates, GDPR flows) under the victim's identity. Any app that keys per-tenant state, redaction, or side effects off `WebhookMetadata#shop` inherits this cross-tenant confusion, because the gem provides no protection for that field.

### Likelihood Explanation
Likelihood is High: the webhook endpoint is a standard, internet-reachable ingress with no additional secrets required beyond an attacker's own legitimate app-install/store (routinely available), and the header manipulation (changing `shop-domain`) requires no privileged access, TLS interception, or knowledge of `api_secret_key`. This satisfies the "unprivileged internet user" and no-credential-required constraints in the rules.

### Recommendation
Include the identity fields (`shop`, `topic`, and ideally `webhook_id`/timestamp) in the signed material, or otherwise cryptographically bind them, e.g. by having `to_signable_string` concatenate `shop`, `topic`, and the body, mirroring how `AuthQuery#to_signable_string` binds `shop`/`host`/`state` for OAuth. At minimum, `HmacValidator`/`Registry.process` should refuse to trust `request.shop` for anything beyond logging unless it can be tied to the signature, or the host app should be required to cross-check `request.shop` against a known/installed shop list before dispatch.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook event (e.g., `orders/create`), receiving a genuine POST with body `B` and header `X-Shopify-Hmac-Sha256: H` where `H = HMAC(secret, B)`.
2. Attacker resends the identical body `B` (or a body with attacker-desired content but reusable across shops, since `to_signable_string` is body-only) to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)`, which still equals `H`, so validation passes: [5](#0-4) 
4. `Registry.process` dispatches to the handler with `WebhookMetadata.new(... shop: request.shop ...)` set to `victim.myshopify.com`, even though the signature never authenticated that value: [6](#0-5) 
5. Any host-app logic that trusts `data.shop` for tenant-scoped operations now executes against the victim tenant using attacker-supplied timing/content.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
