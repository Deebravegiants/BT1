## Analysis Result

Chainlink does not use the npm `ldapauth`/`ldapauth-fork` package referenced in the advisory — its LDAP integration is a native Go implementation using `github.com/go-ldap/ldap/v3`. [1](#0-0)  However, the same underlying bug class (unsanitized user input concatenated into an LDAP query/bind string) is reachable in this Go code.

### Title
LDAP Injection via unsanitized Bind DN construction in `CreateSession`/`TestPassword` (LDAP filter-escaping used where DN-escaping is required) - (File: core/sessions/ldapauth/ldap.go)

### Summary
The LDAP authentication driver builds the bind Distinguished Name (DN) for user login by string-concatenating the user-supplied, attacker-controlled `sr.Email` value after passing it only through `ldap.EscapeFilter`, which escapes characters meaningful in LDAP *search filters* (RFC 4515) but not characters meaningful in a *DN* (RFC 4514), such as `,`, `+`, `"`, `;`, `<`, `>`. This is functionally the same root cause as the reported `ldapauth`/`ldapauth-fork` CVE-2015-7294: unsanitized username input flowing into an LDAP identity operation.

### Finding Description
In `CreateSession`, the login endpoint's email field is lower-cased and passed through `ldap.EscapeFilter`, then embedded directly into a bind DN string: [2](#0-1) 

The identical pattern is repeated in `TestPassword`: [3](#0-2) 

`ldap.EscapeFilter` only escapes NUL, `(`, `)`, `\`, `*`, and non-ASCII bytes — it does not escape DN metacharacters like `,`/`+`/`"`/`;`/`<`/`>`. Because the value is used to build a *DN* (`BaseUserAttr=<email>,UsersDN,BaseDN`) rather than a *filter*, this is the wrong escaping function for the context, and the input remains attacker-influenceable in DN structure.

The `sr.Email` value reaching this code is not required to be a validated email address at login time — the `/sessions` endpoint binds the raw JSON body directly to `sessions.SessionRequest` and calls `CreateSession` without calling `ValidateEmail` (that validator is only used for local admin user *creation*, in `NewUser`): [4](#0-3) [5](#0-4) 

This means any unauthenticated caller of the `/sessions` login endpoint can submit an arbitrary string as `Email`, which is then woven into the LDAP bind DN.

### Impact Explanation
An attacker who controls the `Email` field of a login request can inject DN-structural characters (e.g., `,`) into the bind DN sent to the upstream LDAP server. Depending on the target directory's structure and any permissive/anonymous binds, this can allow the request to resolve to a different DN than intended by the operator's config (`BaseUserAttr`, `UsersDN`, `BaseDN`), which is a form of authentication request manipulation/impersonation against the identity backend — directly matching the "request impersonation" / "authentication bypass" impact classes called out for this bug class.

### Likelihood Explanation
Exploitability is conditional on the specific LDAP directory's tree layout and object contents (i.e., whether an attacker-crafted DN suffix resolves to an existing bindable object), so this is not a universally-exploitable bypass. It requires the `AuthenticationMethod = 'ldap'` deployment mode to be enabled, per the config validation gating this code path. [6](#0-5)  Still, the request path is reachable by any unauthenticated client hitting the `/sessions` endpoint, and the code uses the semantically wrong escaping primitive for a DN context, which is the exact defect class flagged by the reference advisory.

### Recommendation
Do not build DN strings via raw string concatenation of user input. Either use the `go-ldap` DN-escaping helper for DN components (escape `,`, `+`, `"`, `\`, `<`, `>`, `;`, leading/trailing spaces, and leading `#`), or preferably avoid constructing the login bind DN from user input entirely — first resolve the user's DN via a filtered `Search` (using `ldap.EscapeFilter`, which is appropriate there) and then `Bind` using the DN returned by the directory server, never a client-supplied value. Apply the same fix to `CreateSession`, `TestPassword`, `FindUser`'s filter construction, and `sync.go`'s bind construction that reuses similar patterns. [7](#0-6) 

### Proof of Concept
1. Deploy a Chainlink node with `AuthenticationMethod = 'ldap'` and a configured `BaseDN`/`UsersDN`/`BaseUserAttr`.
2. POST to `/sessions` with a JSON body such as `{"email": "<attacker-controlled-string-with-comma-and-RDN-components>", "password": "<guessed-or-blank>"}`.
3. Observe that the resulting bind DN sent to the upstream LDAP server, built at [8](#0-7) , contains attacker-controlled DN structure rather than a single validated RDN value, since `ldap.EscapeFilter` does not neutralize DN metacharacters.

	// Does this user have 2FA enabled?

		return
	}

	// required for successful WebAuthn authentication

		sr.WebAuthnConfig = sc.App.GetWebAuthnConfiguration()
	}

	if err != nil {
		jsonAPIError(c, http.StatusUnauthorized, err)
		return
	}

// NewUser creates a new user by hashing the passed plainPwd with bcrypt.
func NewUser(email string, plainPwd string, role UserRole) (User, error) {
	if err := ValidateEmail(email); err != nil {
		return User{}, err
	}

	pwd, err := ValidateAndHashPassword(plainPwd)
	if err != nil {
		return User{}, err
	}

	return User{
		Email:          email,
		HashedPassword: *config.NewSecretString(pwd),
		Role:           role,
	}, nil
}

// ValidateEmail is the single point of logic for user email validations
func ValidateEmail(email string) error {
	if len(email) == 0 {
		return pkgerrors.New("Must enter an email")
	}
	_, err := mail.ParseAddress(email)
	return err
}
