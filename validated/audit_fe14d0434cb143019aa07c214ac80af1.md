### Title
Webhook shop/topic identity spoofing via HMAC that only covers the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches to a handler using the `shop` and `topic` values taken from HTTP headers that are **not** part of the signed data. This breaks the binding: `shop/topic acted on == shop/topic covered by HMAC`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from headers, entirely outside the signed payload: [2](#0-1) 

`Registry.process` validates only this body-based HMAC and then trusts the unsigned `shop`/`topic` headers to select the handler and construct `WebhookMetadata`, which is handed to app code as the tenant/topic identity of the event: [3](#0-2) 

`HmacValidator.validate` (used by `process`) only checks `verifiable_query.hmac` against `to_signable_string`, i.e., the body — it never incorporates `shop` or `topic`: [4](#0-3) 

**Binding broken:** `shop_acted_on == shop_covered_by_hmac` and `topic_acted_on == topic_covered_by_hmac` do not hold. The HMAC only proves "this body was signed with the app's secret at some point," not "this body was delivered for this shop/topic."

Since a single app typically shares one `api_secret_key` across all installed shops (multi-tenant), any merchant who installs the app on their own store legitimately receives real webhook deliveries — each a valid `(raw_body, hmac)` pair signed with the app's shared secret. That merchant can replay the exact same `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` and/or `X-Shopify-Topic` headers to name a different (victim) shop or a different topic. `HmacValidator.validate` still succeeds because it never inspected those headers, and `Registry.process` will hand the forged `shop`/`topic` straight to the handler as if Shopify itself asserted them.

### Impact Explanation
This is a cross-tenant identity-spoofing primitive reachable by any unprivileged actor who can install the app on their own store (no `api_secret_key`, access token, or leaked credential needed):
- An attacker can make the host application execute webhook business logic (e.g., data updates, GDPR compliance actions in `MANDATORY_TOPICS`, order/customer state changes) **attributed to a shop the attacker does not control**, because `WebhookMetadata#shop` is forged.
- An attacker can also relabel a benign topic's payload as a different, more sensitive topic (`customers/data_request`, `customers/redact`, `shop/redact`, etc.), tricking handler dispatch logic (`@registry[request.topic]&.handler`) into running the wrong handler on attacker-supplied body content.

This maps to the report's bug class ("a shop authenticated versus the shop stored/acted on") and satisfies the Critical impact bar of **cross-tenant access**, since the shop identity used to key downstream data operations is forgeable by any party who has ever received one legitimate webhook from the shared-secret app.

### Likelihood Explanation
Likelihood is high for any multi-tenant app built on this gem: obtaining one valid `(body, hmac)` pair only requires being an ordinary merchant who installs the app (a routine, unprivileged action), and replaying it with modified headers requires no cryptographic work — the HMAC is untouched because it never covered the headers in the first place.

### Recommendation
Bind the `shop` (and ideally `topic`) into the value that is HMAC-verified, or independently authenticate them, e.g.:
- Require the `shop` domain to also be verified against the currently active/known session for that shop before dispatch, or
- Include `shop`/`topic`/`webhook_id` in the signable string (if Shopify's webhook signing scheme supports this) or otherwise cryptographically bind them, or
- At minimum, document and enforce that `WebhookMetadata#shop`/`#topic` must not be trusted as authenticated identifiers unless cross-checked against out-of-band session/shop records before use in tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`. The app's shared `api_secret_key` is used to sign every webhook, including ones sent to the attacker's own endpoint (if attacker controls their own installed app's callback URL in a self-hosted testing scenario) or the attacker simply captures a legitimate webhook delivery aimed at their own store.
2. Attacker captures a legitimate webhook delivery: `raw_body = '{"id":123,...}'`, header `X-Shopify-Hmac-Sha256: <valid_hmac_for_body>`, `X-Shopify-Topic: orders/create`, `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker resends the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com` (and/or changes `X-Shopify-Topic` to `customers/redact`).
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body successfully (all required headers present): [5](#0-4) 
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and compares — it matches, because the body is unchanged: [6](#0-5) 
6. The handler for the (forged) topic is invoked with `WebhookMetadata.new(topic: "customers/redact", shop: "victim.myshopify.com", body: ..., ...)`, i.e., the app processes attacker-supplied content as an authentic event for `victim.myshopify.com` — a cross-tenant forgery with no valid credential for the victim shop ever presented.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
