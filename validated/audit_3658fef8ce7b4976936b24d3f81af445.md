Based on my investigation, I found a legitimate finding matching the specified bug class: a field (`shop`) is acted upon by the application but is not covered by the HMAC signature.

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook data misattribution - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator.validate` is computed only over the raw request body via `to_signable_string`, never over the shop header. Any party holding one valid `(raw_body, hmac)` pair signed with the app's `client_secret` (e.g., a merchant who has legitimately installed the app on their own store and receives real webhooks) can resend that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header, and it will pass validation.

### Finding Description
`Utils::HmacValidator.validate` computes the signature exclusively from `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only `@raw_body`, and the `shop`, `topic`, `api_version`, and `webhook_id` accessors are read straight from unauthenticated HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., body-vs-HMAC) before dispatching to the handler with `request.shop` taken as ground truth: [3](#0-2) 

The identity binding that should hold is: `shop asserted to the handler == shop that produced/authorized this exact signed payload`. Because the header is outside the signed bytes, an attacker who obtains any one valid `(raw_body, hmac)` pair for the app (trivially available to them by installing the app on their own store and capturing a real webhook delivery, since Shopify signs webhooks with the app-wide `client_secret`, not a per-shop secret) can replay that pair with a forged `shop-domain` header pointing at a victim shop. The handler then processes attacker-controlled/attacker-known body content under the victim shop's identity.

### Impact Explanation
This breaks the tenant boundary the gem is documented to enforce for webhook handlers: `WebhookMetadata.shop` is meant to reliably identify which store the payload is about, and app code (e.g., `shopify_app` and custom handlers) commonly branches on `data.shop` to decide which merchant's records to create/update/delete. An attacker can cause the app to process crafted (but validly-HMAC'd, since it's the attacker's own legitimate webhook data) content while claiming it belongs to another merchant's shop, leading to cross-tenant data confusion/corruption in host applications that trust `WebhookMetadata.shop` — satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Requires only that the attacker install the target app on a store they control (no special access needed) and be able to send arbitrary HTTP requests to the app's public webhook endpoint — both trivially available to "any unprivileged internet user." No `api_secret_key`, access token, or other privileged credential of the app/victim is needed.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signable string alongside the raw body, or independently verify that the `shop-domain` header matches an already-authenticated session/shop associated with the delivery, so the HMAC binds the full set of fields the handler relies on, not just the body bytes.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com`; trigger any webhook (e.g. `orders/create`) and capture the raw POST body and the `x-shopify-hmac-sha256` header value — both signed validly by the app's `client_secret`.
2. Send a new HTTP request to the app's webhook endpoint with the same captured body and HMAC header, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the body against the HMAC; `request.shop` returns the forged `victim-shop.myshopify.com`.
4. The registered handler executes with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, even though the payload actually originated from and was authorized by `attacker-shop.myshopify.com`.
