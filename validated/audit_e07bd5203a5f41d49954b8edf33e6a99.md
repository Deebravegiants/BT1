### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop` (from the `X-Shopify-Shop-Domain` header) is read unauthenticated and passed straight through to the app's webhook handler as the trusted tenant identifier. This breaks the identity binding `hmac_valid(body) == trusted(shop, body)`: the signature only proves the body wasn't tampered with, not which shop it belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop` is parsed directly from an HTTP header with no cryptographic binding to that body: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates the request solely via `Utils::HmacValidator.validate(request)`, which in turn calls `validate_signature` against `verifiable_query.to_signable_string` — i.e., the raw body only — and then immediately hands `request.shop` to the handler as the authoritative tenant identity: [3](#0-2) [4](#0-3) 

Crucially, the app's `api_secret_key` is a single shared secret for *all* shops that install the app (not shop-specific), so an HMAC that is valid for one shop's webhook body is equally "valid" for any other shop's webhook, since the shop identity is never part of what's signed.

The gem's own documentation instructs developers to treat `data.shop` from the handler as the trusted per-tenant key, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`: [5](#0-4) 

This is the gem's documented contract, so any host application following it inherits this gap — it is not a case of the host app ignoring the gem's API.

### Impact Explanation
An attacker who has installed the app on their own (unprivileged) Shopify store receives genuine, correctly-HMAC-signed webhook deliveries for that store. Because the HMAC covers only the body and the shared secret is identical across all shops, the attacker can resend that exact same body/HMAC pair to the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` header to a victim shop's domain. `Registry.process` will accept it as valid (`HmacValidator.validate` only checks the body signature) and invoke the handler with `WebhookMetadata(shop: <victim-shop>, body: <attacker-controlled-data>)`. Any app logic that uses `data.shop` to select per-tenant state, sessions, or storage (as the docs instruct) can be tricked into associating attacker-supplied data with an arbitrary victim shop — i.e., cross-tenant data injection/corruption without ever possessing the victim's credentials.

### Likelihood Explanation
Medium: it requires the attacker to be an app-installing merchant (unprivileged internet user, no special credentials needed beyond installing the app themselves) and to know/guess a victim shop domain (which is often public, e.g. `victim.myshopify.com`). No access to `api_secret_key`, tokens, or the victim's account is required — only standard install access that any Shopify Partner/developer can obtain.

### Recommendation
Bind the shop identity into the webhook's signed content, e.g. include `shop-domain` (and ideally `topic`/`webhook-id`) as part of `to_signable_string`, or independently verify that the shop asserted in the header matches an app-side record (installed session) that was itself established through a shop-bound flow before trusting `request.shop` in `WebhookMetadata`. At minimum, document that `data.shop` must not be treated as authenticated identity, or change the implementation so the HMAC computation incorporates the shop domain, closing the gap between "bytes verified" (body) and "identity trusted" (shop).

### Proof of Concept
1. Attacker installs the app for `attacker-shop.myshopify.com` and configures webhooks so Shopify sends real webhook deliveries to the app's endpoint, each with a valid `X-Shopify-Hmac-Sha256` computed over the raw body using the app's shared `api_secret_key`.
2. Attacker captures one such request: `raw_body = B`, `X-Shopify-Hmac-Sha256 = H`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker resends the identical `raw_body = B` and `X-Shopify-Hmac-Sha256 = H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`) and successfully matches `H` — the forged shop header is never checked.
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, letting the attacker inject data attributed to `victim-shop.myshopify.com` into any per-tenant logic that trusts `data.shop`.
