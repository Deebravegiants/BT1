Based on my research, I found a valid analog in `FeeVault.claim()`.

### Title
Blacklisted creator address permanently freezes accrued creator fees in FeeVault with no rescue path - (File: packages/contracts/src/FeeVault.sol)

### Summary
`FeeVault.claim()` always pays out the caller's own `creatorBalance[msg.sender]` and provides no `recipient` parameter, mirroring the exact shape of the reported `Pool.removeCollateral()` bug: a hardcoded transfer to a single, non-redirectable address using a real-world blacklistable stablecoin (USDC).

### Finding Description
`FeeVault.claim()` reads `$.creatorBalance[msg.sender]`, zeroes it, and calls `$.usdc.safeTransfer(msg.sender, amount)` [1](#0-0) . There is no way to specify an alternate recipient — the payout destination is hardcoded to `msg.sender`. If USDC (the vault's underlying asset, per `FeeVaultStorage.usdc`) blacklists that creator's address (e.g., OFAC/Circle freeze), every future `claim()` call from that address reverts inside `safeTransfer`, permanently trapping the creator's already-accrued `creatorBalance[msg.sender]`. Fees continue to accrue into this balance via `Zap._accrueFee` → `FeeVault.accrue` on every buy/sell of that creator's token [2](#0-1) , so the trapped amount grows over time with no way to redirect it.

Critically, `Bonding.transferCreator` (mentioned as reassigning `tokenInfo.creator` for future fee attribution, per `docs/contracts-scope.md` line 117: "Creator attribution comes from `Bonding.tokenInfo(token).creator` ... updatable via `transferCreator`") only affects the forward-looking `creatorOf(token)` lookup used by `Zap._accrueFee` for *new* accruals. It does not — and structurally cannot, since `FeeVault.creatorBalance` is keyed by address, not by token — migrate the *already-accrued* `creatorBalance[oldAddress]` to the new address. This is the same root defect as the reported bug: irreversible state (accrued balance / collateral) tied to one specific address, and that address's own blacklist status is a single point of failure with no owner-level override, sweep, or admin rescue function for `creatorBalance`.

### Impact Explanation
Any accrued, unclaimed USDC balance under a creator address that later becomes blacklisted by USDC is permanently frozen — it can never be claimed by that address, and no admin function exists to redirect or force-pay it elsewhere. `FeeVault.claimProtocol()` similarly pays only the admin-set `feeTo` [3](#0-2) , though that address is owner-controlled and rotatable via `setFeeTo`, so the protocol side has a mitigation the creator side lacks. This satisfies "permanent freezing of creator... funds" from the validation criteria.

### Likelihood Explanation
Requires only that a creator's wallet be added to USDC's blacklist (a real, externally-triggerable event independent of the protocol) while they hold an unclaimed `creatorBalance`. No privileged action, upgrade, or malicious actor within alt.fun is needed — the trigger is entirely external (Circle/USDC issuer action), same trust model as the original Sherlock report.

### Recommendation
Add a `recipient` parameter to `claim()` (analogous to the original report's fix for `removeCollateral`), gated to `msg.sender` as claimant but allowing an arbitrary payout address, e.g. `claim(address recipient)`. Additionally, provide an owner-gated rescue path (e.g., a timelocked `adminRedirectClaim(creator, newRecipient)`) so balances belonging to a blacklisted address are not permanently unrecoverable.

### Proof of Concept
1. Creator `C` accrues `creatorBalance[C] = X` USDC via normal buy/sell activity on their launched token (`Zap._accrueFee` → `FeeVault.accrue`).
2. USDC issuer blacklists `C` (independent of alt.fun).
3. `C` calls `FeeVault.claim()` — `$.usdc.safeTransfer(C, X)` reverts because USDC's `transfer`/`transferFrom` checks the blacklist and reverts for a blacklisted recipient.
4. `C` calls `Bonding.transferCreator(token, D)` to reassign future accrual attribution to a clean address `D`.
5. `D` calls `FeeVault.claim()` — but `creatorBalance[D] == 0` since the historically accrued `X` is keyed to `C`, not `D`. The `X` USDC remains permanently stuck in `FeeVault`, unclaimable by anyone. [1](#0-0) [4](#0-3)

        address token,

            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }

    function claim() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        amount = $.creatorBalance[msg.sender];
        if (amount == 0) revert NothingToClaim();
        $.creatorBalance[msg.sender] = 0;
        $.totalAccruedCreator -= amount;
        $.usdc.safeTransfer(msg.sender, amount);
        emit CreatorFeesClaimed(msg.sender, amount);
    }
