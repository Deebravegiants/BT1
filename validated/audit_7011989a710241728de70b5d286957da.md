### Title
BSC consensus client epoch/rotation math breaks when `epoch_length` is changed while a validator-set rotation is pending - (File: modules/ismp/clients/bsc/src/pallet.rs)

### Summary
The reported bug class is: a scheduling/duration computation assumes a fixed cycle length across several future periods, but silently becomes wrong once an already-queued config change alters that length mid-flight. The BSC light client reproduces this exact pattern: it stages a validator-set rotation (`next_validators.rotation_block`, computed against the epoch length in effect at staging time) and later re-derives epoch boundaries for that pending rotation using whatever `epoch_length` happens to be stored *at verification time*, rather than the length that was actually in effect when the rotation was staged.

### Finding Description
`ismp_bsc::pallet::Pallet::set_epoch_length` lets `AdminOrigin` overwrite the global `EpochLength<T>` storage value at any time, with no check for an in-flight validator-set rotation: [1](#0-0) 

`verify_consensus` in the client always re-reads this single, mutable, global value and uses it to reinterpret the previously staged `next_validators.rotation_block` (an absolute BSC block number computed once, under the epoch length that was current at the time it was staged): [2](#0-1) 

`rotation_block` itself is derived once from the epoch length in effect at staging time and never re-anchored: [3](#0-2) 

`compute_epoch` is a pure division by whatever `epoch_length` is passed in: [4](#0-3) 

and the anti-stall invariant `ensure_finalized_epoch_consistent`, which every `verify_consensus` call runs, also recomputes `finalized_epoch`/`rotation_epoch` boundaries with the current `epoch_length`: [5](#0-4) 

Nothing in `ConsensusState` (`current_validators`, `next_validators`, `finalized_height`, `current_epoch`) records which `epoch_length` the staged `rotation_block`/`current_epoch` were computed under: [6](#0-5) 

`set_epoch_length` exists precisely because BSC has changed its epoch length via hard fork before (BEP-341/Lorentz), so calling it while a rotation is pending is a realistic operational sequence, not a contrived adversarial input — directly analogous to the withdrawal-manager report's "queuing a config update while an earlier one is already scheduled."

Once `epoch_length` changes while `next_validators` is `Some`, all of the following become inconsistent relative to the real BSC chain, which still rotates on its actual protocol-defined boundary:
- `rotation_epoch = compute_epoch(next_validators.rotation_block, new_epoch_length)` no longer identifies the real epoch in which the staged set should activate.
- `ensure_finalized_epoch_consistent` recomputes `finalized_epoch` against the new length and can start rejecting every subsequent legitimate update as `StaleValidatorSet`, or `SourceHeaderEpochMismatch` triggers on every promotion attempt.
- Because the pending set can never cleanly promote (or promotes against the wrong header epoch), the on-chain BSC consensus client stops accepting new state commitments.

### Impact Explanation
A permanently stuck BSC consensus client means `stateMachineCommitment` for BSC state machines stops advancing. Every ISMP request/response/timeout routed through this consensus client (`HandlerV2` message delivery, state membership/non-membership proofs) becomes permanently undeliverable — the exact "route unable to deliver messages" outcome the validation criteria call out. This is not a transient DoS: without a fresh `create_client` (frozen clients "cannot be unfrozen", and here the client isn't even frozen by design, it's just stuck on a stale rotation) recovery requires manual intervention, i.e., a permanent freeze of the BSC message route.

### Likelihood Explanation
`set_epoch_length` is an intended, documented governance action (it exists specifically to follow BSC hard forks that change epoch length), so it will be exercised in normal operation, not only by a hypothetical malicious actor. The bug is triggered whenever such an update happens to land while a validator-set rotation is staged (`next_validators.is_some()`), which is a routine, recurring state for this client (BSC rotates validators every epoch). The relayer/verifier code that subsequently trips the invariant is exercised by ordinary, unprivileged relayer message submission (`verify_consensus` runs on every consensus message any relayer submits), matching the "message dispatcher / relayer" reachability requirement.

### Recommendation
Store the `epoch_length` that was in effect when `next_validators`/`rotation_block` were staged as part of `ConsensusState` (or re-derive `rotation_block` in terms of an epoch-length-independent anchor), and use that stored value — not the live `EpochLength<T>` — when deciding whether to promote a pending validator set or when checking `ensure_finalized_epoch_consistent` against a still-pending rotation. Alternatively, reject `set_epoch_length` (or force an immediate, safe re-staging/consensus-state reset) whenever `next_validators` is currently `Some`, so an epoch-length change can never straddle an in-flight rotation.

### Proof of Concept
1. BSC client is live with `EpochLength = 1000`. A sync update stages `next_validators` with `rotation_block = 5010` (epoch 5 boundary + `validator_size/2`), per `verify_bsc_header`'s `NextValidators` construction (`modules/consensus/bsc/verifier/src/lib.rs:169-205`).
2. Before that rotation is enacted, `AdminOrigin` calls `set_epoch_length` with `epoch_length = 500` to follow a real BSC hard fork, without also resupplying a `consensus_state` that clears/re-stages `next_validators` (`modules/ismp/clients/bsc/src/pallet.rs:79-94`).
3. A relayer submits the next legitimate consensus update. `verify_consensus` reads the new `epoch_length = 500` and computes `rotation_epoch = compute_epoch(5010, 500) = 10`, while `attested_epoch` for blocks actually following the real chain lands elsewhere (`modules/ismp/clients/bsc/src/lib.rs:95-124`).
4. The promotion condition `attested_epoch == rotation_epoch && attested_number >= rotation_block` never lines up correctly against the real chain's post-fork block cadence, and/or `ensure_finalized_epoch_consistent` (`modules/consensus/bsc/verifier/src/lib.rs:228-244`) starts rejecting updates as `StaleValidatorSet` because `finalized_epoch` computed with the new length races ahead of `current_epoch`.
5. No subsequent BSC consensus update can be accepted; the state machine commitment freezes, permanently blocking delivery of BSC-routed ISMP messages.

```rust
pub fn ensure_finalized_epoch_consistent(
	finalized_height: u64,
	current_epoch: u64,
	next_validators_staged: bool,
	epoch_length: u64,
) -> Result<(), Error> {
	let finalized_epoch = compute_epoch(finalized_height, epoch_length);
	let max_finalized_epoch = current_epoch + next_validators_staged as u64;
	if finalized_epoch > max_finalized_epoch {
		return Err(Error::StaleValidatorSet {
			finalized_epoch,
			current_epoch,
			next_validators_staged,
		});
	}
	Ok(())
}
```
