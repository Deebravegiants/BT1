### Title
Webhook shop/topic/id headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying the HMAC over the raw request body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers — which the gem hands to the app's `WebhookHandler` as trusted, verified metadata (`WebhookMetadata#shop`, `#topic`, etc.) — are never included in the signed data. Anyone who possesses one genuine `(raw_body, hmac)` pair for the app (e.g., a real merchant who installed the app and received a legitimate webhook, or a test webhook triggered from the Partner Dashboard) can resend that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. The HMAC check still passes because the header is never part of the signed string, yet the handler receives `data.shop` claiming to be a different, victim merchant.

### Finding Description
- `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated headers with no relation to the signed payload: [2](#0-1) 
- `Utils::HmacValidator.validate` computes and compares the HMAC only over `verifiable_query.to_signable_string` (i.e., the raw body for webhooks): [3](#0-2) 
- `Registry.process` gates on that same HMAC check and then forwards the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` straight into `WebhookMetadata`, which is the only data the app's handler ever sees: [4](#0-3) [5](#0-4) 

The identity binding that should hold is:
`hmac_signed_bytes == bytes_that_determine_which_tenant(shop) the handler acts on`

but it actually holds:
`hmac_signed_bytes == raw_body_only`, while `shop` (the tenant identity) is taken from an independently-controllable header.

Because the `shop` header sits outside the MAC, any party who can obtain one valid `(body, hmac)` pair — which does not require knowledge of `api_secret_key` — can freely re-attribute that payload to any other shop by editing the `shopify-shop-domain` header before resubmitting the HTTP request to the app's public webhook endpoint. This is exactly the "field acted on but not covered by the HMAC" analog: the HMAC verifies body integrity but not the tenant binding the app relies on.

### Impact Explanation
This breaks the shop/tenant boundary the whole SDK is built around. A handler that keys any state, entitlement, or side effect off `WebhookMetadata#shop` (which is the documented and intended use, per `docs/usage/webhooks.md`) can be tricked into performing that action against a victim shop it never actually received a webhook for — e.g., an `app/uninstalled` or `shop/redact` replay causing deletion/deactivation of a different merchant's data, or a `orders/create`/billing-related webhook being falsely attributed to a shop that never placed that order. This is a cross-tenant impact, i.e., Critical severity per the given scale.

### Likelihood Explanation
Any user of the app who is themselves a legitimate merchant (unprivileged relative to other tenants) can trivially capture one genuine webhook delivery for their own shop (from real usage or Shopify's "Send test notification" feature) and replay it with a modified `shop` header using a simple HTTP client — no secret, token, or elevated access required. The only prerequisite is that the target app exposes its webhook endpoint publicly, which is required by design for Shopify to deliver webhooks.

### Recommendation
Bind the tenant-identifying headers into the signed material, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the HMAC-verified body before constructing `WebhookMetadata`. At minimum, `VerifiableQuery#to_signable_string` for `Webhooks::Request` should incorporate `shop`, `topic`, and `webhook_id` (e.g., a canonical concatenation) so `HmacValidator.validate` fails if any of these headers are altered relative to the original signed delivery. Alternatively, cross-check `request.shop` against session/shop state already known to the app for the given webhook subscription before dispatching to the handler.

### Proof of Concept
1. Legitimate merchant `shop-a.myshopify.com` installs the app and receives (or triggers, via Partner Dashboard "Send test notification") a real webhook delivery:
   ```
   POST /webhooks HTTP/1.1
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC for BODY>
   x-shopify-shop-domain: shop-a.myshopify.com
   x-shopify-webhook-id: wh-123

   BODY
   ```
2. The attacker (the merchant behind `shop-a`) captures this exact `BODY` and `x-shopify-hmac-sha256` value.
3. The attacker resends the identical request to the same app endpoint, changing only the shop header:
   ```
   POST /webhooks HTTP/1.1
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <same valid HMAC for BODY>
   x-shopify-shop-domain: victim-shop.myshopify.com
   x-shopify-webhook-id: wh-123

   BODY
   ```
4. `Utils::HmacValidator.validate` recomputes the HMAC over `BODY` only — it still matches — so `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, even though `victim-shop` never sent this event. [4](#0-3)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
