### Title
Excess native token from `EvmHost.dispatch()` / `fundRequest()` Uniswap swap is not refunded to caller - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)` and `EvmHost.fundRequest()` accept `msg.value` and forward the *entire* amount to `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(post.fee, ...)`, but never capture or forward back any leftover native token that the swap returns to the caller (`EvmHost` itself).

### Finding Description
`dispatch(DispatchPost)` swaps the full `msg.value` for an exact amount of fee token and never checks for/refunds the difference: [1](#0-0) 

The same pattern repeats in `fundRequest`: [2](#0-1) 

The real Uniswap V2 Router's `swapETHForExactTokens` refunds unused ETH to `msg.sender` — but in this call chain, `msg.sender` (from the router's perspective) is `EvmHost`, not the original transaction sender (`_msgSender()`), since `EvmHost` is the one invoking the router with `{value: msg.value}`. The custom wrapper used in some deployments (`UniV3UniswapV2Wrapper.swapETHForExactTokens`) makes this explicit — it computes `spent`, and refunds `msg.value - spent` back to `msg.sender`, i.e., back to `EvmHost`: [3](#0-2) 

`EvmHost.dispatch()` and `fundRequest()` take no action to receive/track/forward this refund to the original caller. Any leftover native token becomes stranded in the `EvmHost` contract balance permanently, indistinguishable from other host funds, with no code path that returns it to the depositor. This is the same root cause as the referenced Gitcoin finding: a function accepts more native value than it consumes internally, and the excess is silently absorbed by the contract instead of being refunded to the sender.

By contrast, the newer `IntentGatewayV2.placeOrder` / `fillOrder` code paths in this same repository correctly track `msgValue` and refund unspent native tokens at the end of the function: [4](#0-3) [5](#0-4) 

This confirms the codebase's own established pattern (refund unspent `msg.value`) is missing specifically from `EvmHost.dispatch`/`fundRequest`.

### Impact Explanation
Users dispatching POST/GET requests or funding a request with native token overestimate the exact ETH needed (since the swap output amount is fixed and slippage/price movement is unpredictable client-side, and the docs themselves warn that on-chain `quote()` is unsafe due to sandwich risk, pushing users toward sending a buffer of native value). Any surplus beyond what the swap consumes is permanently lost by the sender and accumulates, unrecovered, in `EvmHost`. This is a direct loss of user funds on every over-estimated native-token dispatch call — not a rare edge case, since off-chain fee estimation combined with price volatility between quote-time and execution-time will regularly cause overpayment.

### Likelihood Explanation
High likelihood: `dispatch()` and `fundRequest()` are the primary, unprivileged, permissionless entry points used by every app dispatching a cross-chain POST/GET request or topping up a relayer fee with native token, and the docs explicitly instruct developers to call `dispatch{value: msg.value}(...)` with a native-token buffer since exact fee cost can't be safely computed on-chain (`get-requests.mdx`/`post-requests.mdx` snippets shown above). Every such call that overshoots the exact swap cost permanently loses the difference.

### Recommendation
Track the actual amount consumed by the Uniswap swap (or the caller's `IUniswapV2Router02` implementation) and refund the difference to `_msgSender()` (or `post.payer`) at the end of `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, mirroring the pattern already used in `IntentGatewayV2.placeOrder`/`fillOrder`:
```solidity
uint256 balanceBefore = address(this).balance - msg.value;
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp);
uint256 refund = address(this).balance - balanceBefore;
if (refund > 0) {
    (bool ok, ) = payable(_msgSender()).call{value: refund}("");
    require(ok);
}
```

### Proof of Concept
1. User calls `EvmHost.dispatch{value: 5 ether}(post)` with `post.fee = 100 DAI`, expecting the swap to only use a fraction of the 5 ETH (as `quote()`/off-chain estimation is imprecise and users are advised to send buffer ETH per the docs).
2. `swapETHForExactTokens{value: 5 ether}(100e18, path, address(this), block.timestamp)` executes, consuming e.g. 0.3 ETH and (per Uniswap V2 Router semantics, or explicitly per `UniV3UniswapV2Wrapper.sol#L143-149`) refunding the remaining 4.7 ETH to `msg.sender`, i.e., to the `EvmHost` contract itself.
3. `EvmHost.dispatch()` returns normally; the 4.7 ETH refund is now sitting in `EvmHost`'s balance with no accounting or path back to the user.
4. Repeat across many dispatches — leftover ETH accumulates in `EvmHost`, permanently unavailable to the users who overpaid, exactly analogous to the excess-ETH-stuck scenario described in the referenced report.
