## Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) identity fields are trusted by the handler dispatch without being covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely via `Utils::HmacValidator.validate(request)`, but the HMAC is computed only over the raw request body. The `shop` field that is handed to the app's webhook handler — and that host applications use to select the tenant whose data should be mutated — comes from the `x-shopify-shop-domain` HTTP header, which is never included in the signed material. Any party capable of producing a validly-signed body (e.g., a merchant who has installed the app and thus legitimately receives HMAC-signed webhooks for their own shop) can replay that same body while swapping the `shop-domain` header to a different, victim tenant, and the library will report it to the handler as an authenticated event for the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from unauthenticated headers with no cross-check against the signed body: [2](#0-1) 

`Registry.process` verifies the HMAC (which, per the above, only binds the body) and then immediately trusts `request.shop` as the tenant identity forwarded to the app-level handler: [3](#0-2) 

`Utils::HmacValidator.validate` simply compares the received HMAC against a signature computed from `verifiable_query.to_signable_string` (the body, in the webhook case) — it has no notion of the `shop` header at all: [4](#0-3) 

Because a single `api_secret_key` is shared across every shop that has installed the app (that is how Shopify signs webhooks for a given app), any merchant who legitimately installed the app receives an authentic `(body, hmac)` pair for their own shop. Nothing stops that merchant from POSTing that exact `(body, hmac)` pair back to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to name a different (victim) shop. `HmacValidator.validate` will accept it, because it never inspects the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event is for the victim shop. This is precisely the "field acted on but not covered by the HMAC" identity-binding break called out in the report's bug class: the equality that should hold — `shop asserted in the authenticated bytes == shop used to select the tenant` — does not hold, because the signature covers only the body while the tenant-selecting `shop` value is taken from an unauthenticated header.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` (as returned by `Registry.process`) to pick which tenant's records to update, credit, or otherwise mutate is exposed to cross-tenant data injection: a legitimate but malicious merchant of the app can forge webhook events that other tenants will accept as their own. This matches the "cross-tenant access" Critical impact category, since the identity boundary between tenants is broken purely through this gem's own verification logic — the caller performs no extra work beyond supplying the header, no credentials belonging to the victim are required.

### Likelihood Explanation
Likelihood is elevated because the attacker only needs to be a legitimate app user (any merchant who installed the app) to obtain a genuinely-signed `(body, hmac)` pair, and no access token, secret, or privileged account is needed. The webhook endpoint URL is typically public/predictable (e.g., `/webhooks`), and forging the `x-shopify-shop-domain` header on a normal HTTP POST requires no special access.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the HMAC-verified material, e.g. by including relevant headers in `to_signable_string`, or by requiring the caller to additionally verify that the shop asserted in the header corresponds to a shop the app has installed for *and* that no cross-tenant replay has happened (e.g., via webhook-id uniqueness tied to a registered shop). At minimum, document prominently that `request.shop` is not authenticated by the HMAC and that host applications must independently corroborate it (e.g., cross-referencing against the shop that owns the specific `webhook_id`) before trusting it for tenant selection.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and registers a webhook handler pointing at the same endpoint the target app uses.
2. Shopify sends the attacker a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, header `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker resends the exact same request to the app's webhook endpoint, but changes only the header to `x-shopify-shop-domain: victim.myshopify.com`, leaving body `B` and the HMAC untouched.
4. `ShopifyAPI::Webhooks::Request#to_signable_string` and `HmacValidator.validate` only check `B` against the same signature — validation succeeds.
5. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, letting the attacker inject/replay data as if it originated from the victim's shop.

          received_signature = verifiable_query.hmac
