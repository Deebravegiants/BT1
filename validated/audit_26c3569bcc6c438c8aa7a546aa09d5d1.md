## #Vulnerability found for this question.

### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that is read directly from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, while the HMAC signature verified by `ShopifyAPI::Webhooks::Registry.process` only covers the raw request body. Any unprivileged internet user who legitimately owns a Shopify store (a free/dev store is trivial to obtain) can capture a validly-signed webhook payload from their own shop and replay it against a target app's webhook endpoint with a forged `shop-domain` header, causing the app to process the event as if it originated from a victim merchant's shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#shop` reads the shop identity straight from a header that is never included in the signable content: [1](#0-0) 

The signable string used for HMAC verification is only the raw body: [2](#0-1) 

`HmacValidator.validate` recomputes the HMAC over `to_signable_string` (the body) and compares it to the `hmac` header — it never touches `shop`: [3](#0-2) 

`Registry.process` accepts the request purely based on that body-only HMAC check, then hands the unauthenticated `request.shop` straight to the app's handler as the identity of the shop the event belongs to: [4](#0-3) 

The binding that should hold is: `shop-domain header == identity Shopify HMAC-signed for`. In this design that equality is never enforced — the HMAC signs `body` only, so `hmac_valid(body, secret) == true` says nothing about which shop the `shop-domain` header claims. An attacker who owns any legitimate Shopify store (installable by any internet user, requiring no special access to the target app, no `api_secret_key`, no leaked credentials) receives real, validly-signed webhook deliveries from Shopify for their own store. They can capture one such delivery (raw body + valid `x-shopify-hmac-sha256`) and resend it to the same app's webhook endpoint while swapping only the `x-shopify-shop-domain` header to a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` because it never inspects the shop header, and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the spoofed victim domain.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to guarantee for webhook consumers: host applications reasonably treat `WebhookMetadata#shop` (built from `request.shop`) as an authenticated tenant identifier, since it comes from a request that passed HMAC verification. Because the header is unauthenticated, an attacker with a legitimate (even free/trial) store can cause the app to execute webhook handler logic (e.g., updating records, triggering actions, invalidating data, writing to a database keyed by shop) attributed to an arbitrary victim shop domain that they do not control — a cross-tenant access issue.

### Likelihood Explanation
Any internet user can create a Shopify partner/dev store for free and install any public app that registers webhooks, giving them a source of validly HMAC-signed payloads. Capturing one webhook body+HMAC pair and replaying it with a modified `shop-domain` header requires no cryptographic secret and no special privileges — only the ability to send an HTTP request to the target app's public webhook endpoint. The attack is straightforward to execute repeatedly for any topic the app subscribes to.

### Recommendation
Bind the `shop` identity into the material that is HMAC-verified (or otherwise re-derive/cross-check it from a value Shopify actually signs), e.g.:
- Include the `shop-domain` (and `topic`) header value as part of `to_signable_string`/the value used to compute/verify the HMAC, matching how Shopify itself associates the delivery with a specific shop, or
- Require host apps to independently confirm that `request.shop` corresponds to a shop with an active, previously-established session/installation before trusting it, and document clearly that `Webhooks::Request#shop` is not currently covered by the HMAC.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a free dev store), enabling webhook delivery for a subscribed topic (e.g. `orders/create`).
2. Shopify sends a legitimately signed webhook to the app's endpoint:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid_hmac_for_body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   Body: {"id": 123, ...}
   ```
3. Attacker captures this exact `Body` and `x-shopify-hmac-sha256` value (they own the store, so they can trivially observe their own webhook deliveries, e.g. via a proxy/ngrok endpoint they control instead of the real app URL, or via app logs if they operate a similar test app).
4. Attacker replays the request directly to the target app's public webhook endpoint, keeping `Body` and `x-shopify-hmac-sha256` identical but replacing the header:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over the (unchanged) body only and succeeds, per [5](#0-4) .
6. The handler is invoked with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, per [6](#0-5) , even though the payload actually originated from, and was signed for, the attacker's own store.
