Confirmed: each app deployment (HFT, WrappedHFT, IntentGatewayV2) deploys its **own dedicated `CallDispatcher` instance** [1](#0-0) , and that dispatcher address is wired in via configuration into the app [2](#0-1) . The `CallDispatcher.dispatch` function itself has zero access control — it is a bare `external` function that decodes an arbitrary `Call[]` and executes each one with `to.call{value: call.value}(call.data)`, using whatever ETH/ERC20 balance the dispatcher happens to hold at call time [3](#0-2) . It also has a public `receive()` that accepts ETH from anyone [4](#0-3) .

### Title
Unprotected `CallDispatcher.dispatch()` allows any address to drain assets left transiently on the dispatcher during order/token execution flows - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch(bytes memory encoded)` is `external` with no caller restriction (no `onlyOwner`, no `msg.sender == app` check). Any account can call it directly, at any time, to force the dispatcher to execute arbitrary `Call{to, value, data}` entries against whatever native ETH or ERC20 balance the dispatcher currently holds.

### Finding Description
`CallDispatcher` is deployed once per application (`IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`) and is configured as the trusted executor of "untrusted" calldata that solvers/senders embed in orders or cross-chain transfer messages [2](#0-1) [5](#0-4) . The intended flow is: assets are transferred to the dispatcher, `dispatch()` executes the caller-supplied `Call[]`, and the app then sweeps back any resulting balance.

`CallDispatcher.dispatch` itself is completely permissionless:
```solidity
function dispatch(bytes memory encoded) external {
    Call[] memory calls = abi.decode(encoded, (Call[]));
    ...
    (bool success, bytes memory result) = to.call{value: call.value}(call.data);
    if (!success) revert CallFailed(to, result);
}
```
There is no check that `msg.sender` is the configured app (`IntentGatewayV2`/`HyperFungibleToken`/`WrappedHyperFungibleToken`) [6](#0-5) . The `receive()` function also accepts ETH from anyone unconditionally [4](#0-3) .

Because the dispatcher can transiently or persistently hold funds — dust from `_execute`/predispatch sweeps that misses unlisted tokens received during solver-supplied calldata execution, ERC20 tokens left over from an incomplete `transferCalls` step, or ETH sent directly via `receive()` — any of that balance is exposed to theft. Since `dispatch()` performs a raw low-level `call` to any address with any value drawn from the dispatcher's own balance, and enforces no sender restriction, any third party can front-run or simply call `CallDispatcher.dispatch()` directly with a `Call[]` that sweeps the dispatcher's ERC20/ETH balance to themselves — e.g. `Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, balance)})` or `Call({to: attacker, value: address(dispatcher).balance, data: ""})`.

This mirrors the reported bug class exactly: an unprotected function that executes arbitrary calls to arbitrary targets with arbitrary data and no input/caller validation, reachable here by any unprivileged EOA rather than a privileged owner.

### Impact Explanation
Any ETH or ERC20 balance held by a `CallDispatcher` instance — whether from legitimate dust left after an intent fill/predispatch calldata execution, an ERC20's fee-on-transfer/rebasing residue, or ETH sent to the dispatcher's `receive()` — can be stolen by any unprivileged address. Because `IntentGatewayV2`/HFT/WrappedHFT route order/token calldata execution and asset transfers through this same dispatcher, and the dust-sweep logic in `_execute`/`placeOrder` only accounts for known `order.output.assets`/`order.inputs` tokens [7](#0-6) , any token balance outside that enumerated set (e.g. bonus/reward tokens returned by a swap router, rounding remainders, or a second ETH transfer during a multi-call `predispatch`) is left stranded on the dispatcher and permanently stealable by anyone who calls `dispatch()` first. This is concrete theft of user/protocol funds.

### Likelihood Explanation
High reachability: `dispatch()` is a public, permissionless entrypoint on a contract that legitimately and routinely holds funds mid-transaction as part of the core intent-filling and cross-chain-token-delivery flows used by ordinary users and solvers. No privileged role, governance action, or malicious insider is required — any address monitoring the dispatcher's balance (e.g., watching for `DustCollected` events that under-report a leftover token, or any pending ETH sent to `receive()`) can immediately call `dispatch()` to exfiltrate the balance before the legitimate sweep transaction executes.

### Recommendation
Restrict `CallDispatcher.dispatch()` to the configured owning application (e.g. an immutable `owner`/`caller` address set at construction, enforced via a `require(msg.sender == owner)` or equivalent modifier), so that only the app contract that deposited assets into the dispatcher can trigger execution of the queued `Call[]`. Additionally consider removing the unconditional public `receive()` or restricting/sweeping ETH deposits, and ensure sweep logic in `IntentsBase._execute`/`placeOrder` accounts for arbitrary residual token balances (not just the enumerated `order.output.assets`/`order.inputs`) before any external call is possible.

### Proof of Concept
1. A solver fills an order via `IntentGatewayV2.fillOrder`, whose `output.call` (attacker/solver-controlled calldata, since solvers construct the fill) is dispatched through the configured `CallDispatcher` and results, e.g. via a DEX swap with slippage, in a bonus/extra ERC20 token landing on the dispatcher that is not present in `order.output.assets` [7](#0-6) .
2. Because the sweep in `_execute` only iterates over `order.output.assets` (`outputsLen`), the unexpected token balance is never swept and remains on the `CallDispatcher`.
3. Any third-party attacker (not the `IntentGatewayV2` contract) directly calls:
   `CallDispatcher.dispatch(abi.encode([Call({to: unexpectedToken, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, balance)})]))`
4. Since `dispatch()` has no sender check [6](#0-5) , the call succeeds and the attacker receives the stranded tokens, which rightfully belonged to the protocol/order beneficiary as dust.

        if (order.output.call.length == 0) return;

        address dispatcher = _params.dispatcher;
        ICallDispatcher(dispatcher).dispatch(order.output.call);

        Call[] memory sweepCalls = new Call[](outputsLen);
        uint256 sweepCount = 0;

        for (uint256 i; i < outputsLen;) {
            address token = address(uint160(uint256(order.output.assets[i].token)));

            if (token == address(0)) {
                uint256 balance = dispatcher.balance;
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({to: address(this), value: balance, data: ""});
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            } else {
                uint256 balance = IERC20(token).balanceOf(dispatcher);
                if (balance > 0) {

                        value: 0,
                        data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
                    });
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            }

            unchecked {
                ++i;
            }
        }

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
