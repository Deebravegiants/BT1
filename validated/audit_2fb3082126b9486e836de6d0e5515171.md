### Title
Webhook shop identity spoofing via HMAC that only signs the request body, not the `shop-domain` header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) purely from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, while `Utils::HmacValidator.validate` (invoked in `Registry.process`) only verifies the HMAC over `to_signable_string`, which returns `@raw_body` alone. The shop field that identifies which tenant a webhook event belongs to is never bound by the signature, allowing a valid HMAC computed for one shop's payload to be replayed with an attacker-chosen `shop-domain` header for a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#hmac` reads the signature from the `hmac-sha256` header and `#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`#shop` is read straight from the `shop-domain` header, with no relation to the signed bytes: [2](#0-1) 

`Registry.process` validates the webhook exclusively via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop` as the tenant identity passed to the handler: [3](#0-2) 

`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received HMAC — it never incorporates `shop`, `topic`, or any other header into the signed string: [4](#0-3) 

The binding that should hold is:
`shop used by the app to select/act on tenant data == shop cryptographically authenticated by the HMAC`

Instead, the actual binding is:
`shop used by the app == shop declared in an unauthenticated header`, while `HMAC-authenticated bytes == raw_body only`.

Because every shop that installs the app shares the same app `api_secret_key` (Shopify signs each shop's own webhooks with the app's single client secret, not a per-shop secret), any shop that has installed the app can legitimately trigger a webhook delivery to its own endpoint (e.g., by performing an action that fires `orders/create`, `app/uninstalled`, etc.), capture the resulting `(raw_body, hmac)` pair from a delivery it controls (e.g. via a webhook proxy it operates, or by simply observing its own endpoint logs), and then resend that exact `raw_body` + `hmac` to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still succeed because the signature only covers `raw_body`, and `Registry.process` will hand the handler a `WebhookMetadata` object whose `shop` is the attacker-controlled victim domain, with `Registry.process` passing `request.shop` straight into the handler without any correlating check against the signed content: [5](#0-4) 

The app-level webhook handler will then process/act on data (e.g., update stored session/app state, deauthorize, sync data) attributing it to the victim shop, when the payload actually originated from the attacker's own shop.

### Impact Explanation
This crosses a tenant boundary: an unprivileged actor (a merchant who has installed the app on their own shop, and thus is otherwise scoped only to their own tenant) can cause the app to process arbitrary shop-scoped webhook events under a different merchant's identity. Depending on the app's handler logic, this can be used to inject falsified data, trigger cross-tenant side effects (e.g., calling `app/uninstalled` cleanup logic, or `customers/redact`/`shop/redact` mandatory topics) against a shop the attacker does not control, satisfying the "cross-tenant access" criteria for Critical impact.

### Likelihood Explanation
Likelihood is high for any app that relies on `ShopifyAPI::Webhooks::Registry.process` / `Request#shop` to select the tenant context in its handler: no secret material beyond a normal app installation is required, only the ability to trigger one legitimate webhook to capture a valid `(body, hmac)` pair for replay with a forged header.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed content used for HMAC verification, or otherwise verify the header-derived `shop` value against an independently authenticated source (e.g., cross-check that the shop has an active, previously stored session/webhook registration correlated to the specific delivery, or require Shopify's newer webhook verification that binds headers). At minimum, `to_signable_string` should not be the sole basis for trusting `Request#shop`; the shop identity must not be accepted from an unauthenticated header when it drives tenant-scoped business logic.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, receiving a legitimately Shopify-signed webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H` (computed by Shopify using the app's `api_secret_key`, since the same secret signs every installed shop's webhooks).
2. Attacker crafts a new HTTP request to the app's webhook endpoint containing the same raw body `B`, the same `x-shopify-hmac-sha256: H` header, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. The app's controller builds `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim.myshopify.com", "x-shopify-hmac-sha256" => H})` and calls `ShopifyAPI::Webhooks::Registry.process(request)`.
4. `Utils::HmacValidator.validate(request)` recomputes `HMAC(secret, B)` and matches `H`, so validation passes (per `lib/shopify_api/utils/hmac_validator.rb` lines 12-31, since it only ever signs `raw_body`).
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body, ...)`, causing the app to process attacker-supplied order/event data as if it belonged to `victim.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
