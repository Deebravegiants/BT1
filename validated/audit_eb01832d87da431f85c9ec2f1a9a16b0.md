### Title
System-originated messages carry a static, gas-price-blind incentive — undelivered relayer withdrawals and host-param updates permanently strand funds/state - ([File: modules/pallets/relayer/src/withdrawal.rs])

### Summary
Hyperbridge-originated requests (relayer fee withdrawals, host-executive parameter updates, intents-coprocessor responses, token-governor messages) are dispatched with `FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() }` — i.e. zero relayer fee — and rely either on relayer altruism or on a governance-configured flat `OutboundRequestDeliveryReward` per `module_id`. Because the reward is a fixed, governance-set value rather than one scaled to the destination's real-time gas cost, exactly the same economic failure mode described in the external report applies: whenever the flat reward (or "$0" default) falls below what it costs a relayer to actually submit the delivery transaction on the destination chain, no rational relayer will deliver the message, and the underlying action (e.g. paying out a relayer's already-earned fees) never completes.

### Finding Description
`Pallet::withdraw` in [1](#0-0)  dispatches a `WithdrawRelayerFees`/`WithdrawalParams` POST request to the destination chain's fee-holding contract/module, but pays for delivery with `FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() }` — a hard-coded zero fee, not derived from destination gas price at all.

The same zero-fee pattern is used for host-executive parameter updates in [2](#0-1) , and is documented as also applying to `intents-coprocessor` and `token-governor` dispatches in [3](#0-2) .

The "fix" shipped for this is an opt-in reward layer: `Pallet::process_outbound_request_delivery_claim` in [4](#0-3)  pays a relayer a flat `OutboundRequestDeliveryReward[module_id]` amount from the treasury, but that amount is a static governance-set balance ("0 (the default) means both 'no reward' and 'module not on the allowlist'" per the doc, [5](#0-4) ). Nothing ties this flat reward to the live destination gas price the way `pallet-ismp`'s user-fee based incentive is (see `return_successful_queries`'s profitability check in [6](#0-5) , which explicitly compares `fee_metadata` to `total_gas_to_be_expended_in_usd + profit` and skips unprofitable messages).

Consequently, for any module whose reward is unset (default 0) or set too low relative to the destination chain's prevailing gas price, the Tesseract relayer's own profitability gate (`return_successful_queries`) will always classify the delivery as unprofitable and skip it — exactly mirroring the DSCEngine liquidation-report's "gas cost outweighs profit incentive, so nobody performs the required call" pattern, except here the un-relayed call is a relayer-fee withdrawal or a host-param update rather than a liquidation.

### Impact Explanation
If a relayer's accumulated `Fees` balance is small (analogous to the report's "$5 undercollateralized position"), or if destination gas prices rise after `OutboundRequestDeliveryReward` was set, no relayer will have an economic reason to submit the delivery transaction:
- The relayer's `withdraw` extrinsic zeroes `Fees::<T>` immediately at dispatch time ( [7](#0-6) ) before the destination-side payout is confirmed, so if the message is never delivered, the relayer's earned fee is permanently lost — a real freezing/loss of funds, not merely a stuck retry.
- Host-executive parameter updates that are never delivered leave the destination `EvmHost`/manager permanently out of sync with Hyperbridge's intended configuration, which can block subsequent legitimate operations that depend on that parameter being current.

This satisfies "permanent freezing of funds" / "route unable to deliver messages" from the validation criteria, reachable from a normal, unprivileged relayer calling `withdraw` (a single extrinsic) with no attacker or governance action required.

### Likelihood Explanation
Moderate-to-high: the zero-fee default is the as-shipped behavior for these system dispatches, and the governance-configured reward is a static value that is not automatically re-priced as destination gas costs fluctuate (unlike the ordinary user-fee path, which is checked against real-time gas estimates by the relayer's `return_successful_queries`). Any relayer with a small accumulated fee balance, or any period of elevated destination gas prices, triggers the condition without any special conditions or malicious actor.

### Recommendation
Tie `OutboundRequestDeliveryReward` (and the withdrawal/host-executive dispatch fee) to a periodically-updated, gas-price-aware minimum rather than a flat governance constant — e.g., require the reward to exceed `destination_gas_cost_usd + margin` at claim time (reusing the same profitability formula already used in `return_successful_queries`), or allow permissionless top-ups of the reward (similar to `fundRequest` for user-attached fees) so it can be bumped if gas prices rise, and ensure `Fees::<T>` is only decremented after delivery is confirmed rather than at dispatch time.

### Proof of Concept
1. Relayer accumulates a `Fees` balance for `dest_chain = D` (e.g. via `accumulate_fees` after several deliveries).
2. Relayer calls `Pallet::withdraw`, which zeroes `Fees::<T>::insert(D, address, 0)` and dispatches a `WithdrawRelayerFees`/`WithdrawalParams` POST with `fee: Default::default()` ( [8](#0-7) ).
3. Meanwhile `OutboundRequestDeliveryReward[MODULE_ID]` is either unset (0, default) or was set months earlier when gas on `D` was cheap.
4. Tesseract's `return_successful_queries` estimates the current gas cost on `D`, compares it against the (zero or stale) reward, finds it unprofitable, and adds the message to `retriable_messages` instead of relaying it ( [9](#0-8) ).
5. No relayer ever submits the delivery; the relayer's fee balance was already zeroed in step 2 and is never paid out on `D` — permanent loss for that relayer, and the withdrawal request sits undelivered indefinitely.

**Note:** I could not fully verify whether `MODULE_ID` (the relayer pallet's own withdrawal module id) is pre-registered with a non-zero `OutboundRequestDeliveryReward` in production runtime genesis/configuration (`parachain/runtimes/*`), since the file read for `modules/pallets/relayer/src/lib.rs` around the extrinsic/genesis config did not return content before the tool budget was exhausted. If it is pre-registered with a reward that auto-scales or is routinely governance-updated to track gas prices, the practical severity is reduced to "requires governance neglect" rather than being always-live; a Devin session with full repo access should confirm the genesis/runtime configuration for `OutboundRequestDeliveryReward` before this is treated as unconditionally exploitable.

A regular cross-chain message that flows *through* hyperbridge has a fee attached at origin (the source chain transfers `fee.payer → RELAYER_FEE_ACCOUNT` and records `RequestPayments[commitment]` in pallet-hyperbridge's child trie). When a relayer delivers and the destination receipt lands back on hyperbridge, the existing `accumulate_fees` flow credits that fee to the relayer. That whole pipeline assumes a *user* paid at origin.

But hyperbridge itself originates requests too: host parameter propagation, host-executive updates, intents-coprocessor responses, token-governor messages, the relayer pallet's withdrawal request. Today these all dispatch with `FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() }` (see `modules/pallets/host-executive/src/lib.rs:228`, `modules/pallets/intents-coprocessor/src/lib.rs:486`, `modules/pallets/relayer/src/lib.rs:638`, and `modules/pallets/token-governor/src/impls.rs`). Zero fee, zero payer. So relayers have no economic reason to pick them up, and the only thing that keeps them flowing today is altruism.

	pub fn process_outbound_request_delivery_claim(
		claim: OutboundRequestDeliveryClaim,
	) -> DispatchResult {
		let OutboundRequestDeliveryClaim { request, state_proof, payee, signature } = claim;
		let destination = state_proof.height.id.state_id;

		let commitment = hash_request::<<T as Config>::IsmpHost>(&Request::Post(request.clone()));

		let host = <T as Config>::IsmpHost::default();
		ensure!(
			request.source == host.host_state_machine(),
			Error::<T>::OutboundRequestSourceNotHyperbridge,
		);

		ensure!(
			RequestCommitments::<T>::get(commitment).is_some(),
			Error::<T>::OutboundRequestNotKnown,
		);

		ensure!(
			!OutboundRequestsClaimed::<T>::contains_key(commitment),
			Error::<T>::OutboundRequestAlreadyClaimed,
		);

		let module_id: BoundedVec<u8, ModuleIdBound> = request
			.from
			.clone()
			.try_into()
			.map_err(|_| Error::<T>::OutboundRequestModuleIdTooLong)?;
		let reward = OutboundRequestDeliveryReward::<T>::get(&module_id);
		ensure!(reward > BalanceOf::<T>::default(), Error::<T>::OutboundRequestNoRewardConfigured);
