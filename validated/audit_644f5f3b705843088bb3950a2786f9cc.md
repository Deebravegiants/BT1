### Title
Panic-inducing fixed-size buffer copy in BEEFY `Vote` signature conversion - (File: evm/rust/src/conversions.rs)

### Summary
`impl From<Vote> for SignatureWithAuthorityIndex` in `evm/rust/src/conversions.rs` copies an attacker-controlled, variable-length `bytes signature` field from the Solidity `Vote` struct into a fixed 65-byte array using `copy_from_slice` with no length check, exactly the bug class fixed in CVE-2024-54456 (fixed `char[64]` buffer filled via `strcat`/`strcpy` without checking the source length). Here the destination is a fixed `[u8; 65]` (`TSignature`) and the source is `Vote.signature: bytes`, whose length is fully controlled by whoever submits a BEEFY consensus proof.

### Finding Description
`Vote` is defined in `evm/src/consensus/Types.sol`: [1](#0-0) 
as an unconstrained `bytes signature` plus an authority index. This struct is embedded in `SignedCommitment.votes[]`, itself embedded in `RelayChainProof`, which is the payload submitted by a relayer to update the BEEFY consensus client (`ConsensusMessage`/`BeefyConsensusProof`).

The conversion that turns this Solidity-decoded `Vote` into the internal `SignatureWithAuthorityIndex` type used by the BEEFY verifier is: [2](#0-1) 

`sig_bytes` is `value.signature.to_vec()` — its length is whatever the caller supplied on-chain, not necessarily 65. `signature.copy_from_slice(&sig_bytes)` requires the source and destination slices to have *exactly* equal length; if `sig_bytes.len() != 65`, Rust's `copy_from_slice` panics/traps immediately, with no bounds check performed beforehand (unlike every other `TryInto`/length-sensitive conversion in the same file, which either use `.expect()` on numeric truncation or perform explicit length checks, e.g. `WithdrawalParamsError::InvalidBeneficiaryAddressLength` in `evm/rust/src/host_params.rs`).

This is the same root-cause class the project has already identified and fixed in multiple other locations: `modules/ismp/core/src/host.rs`, `modules/utils/serde/src/lib.rs`, `parachain/node/fisherman/src/lib.rs`, and `tesseract/consensus/parachain/src/lib.rs` all contain comments and dedicated regression tests explicitly stating that "`copy_from_slice` traps on a length mismatch" and that this is a real, previously-exploited crash vector reachable from untrusted/relayed input: [3](#0-2) [4](#0-3) 

The `Vote -> SignatureWithAuthorityIndex` conversion was missed and still performs the unchecked copy.

### Impact Explanation
This code path processes BEEFY consensus proofs (`RelayChainProof`/`BeefyConsensusProof`), which is precisely the "consensus verification (BEEFY...)" surface called out as in-scope and reachable by a single relayed proof. A malformed `Vote.signature` (any length other than 65 bytes) forces a panic/trap at the point this conversion runs. Depending on where this Rust conversion executes (a native precompile/FFI helper invoked as part of on-chain BEEFY verification, or the SP1 guest program that produces/consumes BEEFY proofs), this either crashes the verifying process or aborts proof generation/verification for that consensus update — a denial of service against the BEEFY consensus-update route, matching the "route unable to deliver messages" impact category.

### Likelihood Explanation
`Vote.signature` is a plain `bytes` field decoded straight from calldata/proof input supplied by whoever submits the consensus update; there is no evidence in the reviewed code that its length is validated to be exactly 65 bytes before reaching this conversion. Constructing a `SignedCommitment` with an off-length vote signature requires no privilege beyond being able to submit a consensus proof (an unprivileged relayer action), so likelihood is high assuming this conversion is invoked on the message-processing path rather than purely in isolated unit tests. I was not able to fully trace, within the available tool budget, the exact caller (native precompile vs. off-chain-only prover tooling) that invokes `From<Vote> for SignatureWithAuthorityIndex`, so the precise blast radius (node crash vs. isolated relayer-only failure) could not be fully confirmed from the indexed code and should be verified directly in the repository.

### Recommendation
Validate `value.signature.len() == 65` before the `copy_from_slice` and return a typed conversion error (mirroring the pattern already used for `WithdrawalParamsError::InvalidBeneficiaryAddressLength` and the `consensus_state_id_from_str`/`as_utf8_string` fixes) instead of allowing the panic to propagate. Add a regression test analogous to the `from_str_rejects_non_four_byte_consensus_ids` / `as_utf8_string_rejects_non_four_byte_input` tests already present elsewhere in this codebase, feeding a non-65-byte `Vote.signature` through the conversion and asserting a graceful error.

### Proof of Concept
1. Craft a `SignedCommitment` containing a `Vote` whose `signature` field is, e.g., 64 or 66 bytes instead of 65 (trivial ABI encoding change).
2. Submit this as part of a `RelayChainProof`/`BeefyConsensusProof` through the normal BEEFY consensus-update submission path (open to any relayer).
3. When the proof is converted via `From<Vote> for SignatureWithAuthorityIndex`, `signature.copy_from_slice(&sig_bytes)` panics because `sig_bytes.len() != 65`, aborting/crashing the process handling the conversion instead of returning a decode error. [2](#0-1) [5](#0-4)

		fn from(value: Vote) -> Self {
