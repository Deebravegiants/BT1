Audit Report

## Title
JWT Replay Protection Bypass via Check-Then-Record Race (TOCTOU) - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
`WorkflowMetadataHandler.Authorize` performs JWT replay detection and replay recording as two separate, non-atomic critical sections with authorization logic executed in between, allowing concurrent requests carrying an identical signed JWT to both pass the replay check before either marks the JTI as used.

## Finding Description
`Authorize` is reachable from any unprivileged HTTP Trigger client via `HandleUserTriggerRequest` → `authorizeRequest` → `WorkflowMetadataHandler.Authorize` [1](#0-0) . Inside `Authorize`, the replay check `h.jwtCache.isReplay(claims.ID)` takes an `RLock`, reads, and releases immediately [2](#0-1) , and only after workflow-ID lookup and signer-authorization checks complete does the code call `h.jwtCache.recordUsage(claims.ID)`, which takes the write `Lock` in a separate critical section [3](#0-2) [4](#0-3) . This is a classic TOCTOU: two concurrent goroutines using the identical `jti` can both observe `exists == false` in `isReplay` before either writes to the map in `recordUsage`.

Crucially, this race is not neutralized by the request-level dedup logic elsewhere in the handler: `setupCallback` only rejects duplicate *user-supplied* `requestID`s, which are attacker-controlled and unrelated to the JWT's `jti` claim [5](#0-4) . An attacker can send two `HandleUserTriggerRequest` calls with the same JWT/`jti` but two different `requestID`s, bypassing the `callbacks` map uniqueness check entirely while still racing through `Authorize`'s replay guard.

## Impact Explanation
An unprivileged HTTP Trigger client holding a single valid signed JWT can fire it concurrently (with distinct `requestID`s to avoid the unrelated callback dedup) to have the same authorization accepted more than once, causing multiple workflow trigger executions to be dispatched to the DON from what should be a single-use token, defeating the anti-replay guarantee documented for `JWTReplayPeriodMs`. This maps to unauthorized job/workflow execution triggered via the gateway — an in-scope impact (unauthorized job run / gateway request impersonation-style bypass).

## Likelihood Explanation
The exploit requires only ordinary network-level concurrency from an external, unprivileged caller (firing the same signed JWT in two near-simultaneous HTTP trigger requests) — no node compromise, peer collusion, or elevated privilege is needed. The window is narrow but real, and is repeatable by any client capable of concurrent HTTP requests.

## Recommendation
Merge `isReplay` and `recordUsage` into a single atomic check-and-set operation performed under one write-lock acquisition (e.g., `cache.mu.Lock(); if _, exists := cache.cache[jti]; exists { return true }; cache.cache[jti] = time.Now(); return false`), or use a concurrency-safe `LoadOrStore`-style primitive, so that a given `jti` cannot pass the replay check more than once concurrently.

## Proof of Concept
1. Obtain one valid signed request JWT (`jti = X`) authorized for a workflow's `MethodWorkflowExecute` trigger.
2. Construct two `HandleUserTriggerRequest` calls using the same JWT/`Auth` header but two distinct `id` (`requestID`) values (to avoid the unrelated `callbacks` map dedup in `setupCallback`).
3. Fire both concurrently (e.g., via `go` routines or two near-simultaneous HTTP POSTs to the gateway).
4. Both goroutines call `h.jwtCache.isReplay(X)` before either calls `h.jwtCache.recordUsage(X)` (workflow_metadata_handler.go lines 87 and 105), so both pass the `Authorize` replay check, resulting in two dispatched workflow executions from a single JWT instead of one. This can be demonstrated in a Go unit test with two goroutines invoking `Authorize` concurrently on a `WorkflowMetadataHandler` instance with the same `claims.ID`, asserting both return `nil` error.

	}
	return key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {

}
