### Title
Webhook `shop`/`topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing via header substitution - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` fields used to route and label a webhook to a tenant are read directly from unauthenticated HTTP headers. `Registry.process` only validates the body's HMAC and then dispatches the handler using these unauthenticated header values, breaking the binding: `shop authenticated by HMAC` ≠ `shop used to key tenant-scoped handling`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC over the body via `Utils::HmacValidator.validate(request)`, and then immediately dispatches the handler using the unauthenticated `request.shop` and `request.topic`: [3](#0-2) 

`Utils::HmacValidator.validate_signature` confirms the signature is computed only from `verifiable_query.to_signable_string` (the raw body for webhooks), never incorporating header values: [4](#0-3) 

Because the `X-Shopify-Shop-Domain` and `X-Shopify-Topic` headers sit entirely outside the signed payload, any request with a **previously valid** `(body, hmac)` pair remains "HMAC valid" regardless of which `shop-domain`/`topic` headers are attached to it. An unprivileged internet user who can obtain one legitimate `(body, hmac)` pair — e.g., by installing the app on their own store (a normal, unprivileged action any merchant can take) and capturing the webhook their own store legitimately receives — can replay that exact body+HMAC to the app's public webhook endpoint while substituting the `shop-domain` header with a **victim shop's domain**. `Registry.process` will accept the HMAC as valid (it only checks the body) and will invoke the handler with `WebhookMetadata` labeled as belonging to the victim shop: [5](#0-4) 

### Impact Explanation
This breaks the identity binding `shop verified via signature == shop the handler acts on`, allowing cross-tenant event injection: an attacker-controlled webhook body (from their own store) can be attributed to any other merchant's shop domain. Depending on how the host application uses `WebhookMetadata#shop` (e.g., GDPR `customers/redact`, `shop/redact`, `app/uninstalled` handling that deletes/updates records keyed by shop), this can trigger unauthorized actions against another tenant's data/records — i.e., cross-tenant access/integrity impact, without ever possessing the app's `client_secret` or the victim's access token.

### Likelihood Explanation
Any user can become a legitimate merchant that installs the app and thus obtain at least one genuine `(body, hmac)` pair for a webhook topic of their choosing (e.g. `app/uninstalled`, which fires with a predictable/empty body). The webhook HTTP endpoint is by definition internet-reachable and headers are fully attacker-controlled when crafting the replayed request; no interception of Shopify-to-app traffic is required for topics whose bodies are static/predictable across shops.

### Recommendation
Bind the tenant-identifying fields into the signed payload verification, not just raw body bytes:
- Include `shop`, `topic`, and other dispatch-relevant headers in the HMAC-covered signable string, or
- Cross-check `shop`/`topic` against an out-of-band authenticated source (e.g., confirm the shop has a stored, valid session/access token and that the topic is one the app registered for that shop) before treating the request as originating from that shop, or
- Reject/flag any topic whose registered webhook allows trivial cross-shop body reuse (e.g. static-body topics) by additionally requiring shop-specific nonce/timestamp binding.

### Proof of Concept
1. Attacker installs the target app on their own development/free store `attacker-shop.myshopify.com`.
2. App registers, e.g., the `app/uninstalled` webhook; attacker uninstalls the app, capturing the genuine POST request Shopify sends to the app's webhook endpoint, including headers `X-Shopify-Hmac-Sha256: <valid_hmac>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: app/uninstalled`, and body `B`.
3. Attacker resends the identical body `B` and `X-Shopify-Hmac-Sha256` header to the same webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` recomputes HMAC over `B` only and it matches — validation succeeds.
5. `Registry.process` dispatches the handler with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", ...)`, causing the host app to process an uninstall/cleanup event for the victim's shop that never actually occurred.

Note: This analysis is based on the gem's own code paths (`lib/shopify_api/webhooks/*`, `lib/shopify_api/utils/hmac_validator.rb`); actual exploitability/severity depends on how a specific host application consumes `WebhookMetadata#shop` in its handler, which is outside this gem's index.
