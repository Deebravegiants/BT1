### Title
Unauthorized theft of Emporium-held funds via `HINKAL_EMPORIUM_ACTION_ID` "Min" path bypassing both signature check and balance-equation enforcement - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
The Chakra report's root cause is that a value that should be bound inside a verified equality (the `to_chain` field inside the signed hash) is instead checked *outside* that equality, letting an attacker satisfy the check with a mismatched context. The same bug class exists in Hinkal: when `CircomData.erc20TokenAddresses.length == 0` and `externalActionId == HINKAL_EMPORIUM_ACTION_ID`, the contracts switch to a "Min" code path whose SNARK proof and on-chain balance-equation checks are entirely decoupled from the actual value moved by the `EmporiumOperation` calls, and whose wallet-authorization check is skippable by simply setting `signerAddress = address(0)`. This lets any unprivileged EOA execute arbitrary calls that move Emporium-held ETH/ERC20 funds with no cryptographic authorization at all.

### Finding Description
`CircomDataBuilder.formInputForCircom` selects a minimal public-input set when the transaction is an Emporium action with no tokens declared: [1](#0-0) 

`formInputEmporiumMin` only exposes `emporiumMessage`, `timeStamp`, and `calldataHash` as public signals — it omits `rootHashHinkal`, `chainId`/`verifyingContract` binding (present in `getSignedMessageHash`), and any nullifier/commitment/ownership signals. The circuit verified for this input set, `MainEVMCircuitMin`, only proves `message == Poseidon(1)([messageSeed])`: [2](#0-1) 

This is trivially satisfiable by any party who picks an arbitrary `messageSeed` — it proves no ownership of a spending key, no nullifier/commitment relationship, and (unlike the normal `MainEVMCircuit`) contains no `SignatureVerifier` component at all.

Because `dimensions.tokenNumber == 0` for this path, `Hinkal.transact()`'s balance-equation loop (lines 97-147) never executes for any token — it is indexed by `circomData.erc20TokenAddresses.length`, which is 0: [3](#0-2) 

The same applies inside `EmporiumUpgradeable.runAction`: `balancesBefore`/`balancesAfter` are computed only over `circomData.erc20TokenAddresses` (empty), so the "balance change must not be negative" invariant never fires for this branch: [4](#0-3) 

Finally, `verifyWallet` skips *all* ECDSA/EIP-712 signature verification whenever `stack.signerAddress == address(0)`, only marking the self-chosen `emporiumMessage` as used: [5](#0-4) 

With `signerAddress == address(0)`, `runAction` executes each `EmporiumOperation` as `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract's own context/balance: [6](#0-5) 

Putting this together: an attacker can call `Hinkal.transact()` with `dimensions.tokenNumber = 0`, `erc20TokenAddresses = []`, `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, a self-forged trivial proof for `MainEVMCircuitMin`, a `rootHashHinkal`/`rootHashHinkalIndex` pair copied from any historically valid root (unconstrained by the proof since it is not a public input in this branch), and `externalActionMetadata` decoding to an `EmporiumStack` with `signerAddress = address(0)` and `ops` = `[{endpoint: token, invokeWallet:false, value:0, callData: token.transfer(attacker, token.balanceOf(Emporium))}]`. No signature, no nullifier, no balance-equation check gates this call.

### Impact Explanation
This breaks the balance equation the rules require: value is moved by an external action (`EmporiumUpgradeable.runAction`'s `op.endpoint.call`) that is never counted anywhere in Hinkal's or Emporium's own balance-conservation checks, and it is a wallet/transfer operation not authorized by any prover or signer (the ZK proof proves nothing about ownership, and the ECDSA check is skipped for `signerAddress == address(0)`). Any ETH or ERC20 balance held by the `EmporiumUpgradeable` contract (e.g., accumulated relay fees, or funds transiently held between multi-op Emporium sequences) can be stolen by an arbitrary unprivileged EOA. This is Critical: direct theft of protocol/relay funds and unauthorized movement of assets never approved by their owner/signer.

### Likelihood Explanation
High. No privileged role, relayer collusion, or admin key is required — a normal EOA can call `Hinkal.transact()` directly (payable, public function) and self-generate the trivial `MainEVMCircuitMin` proof off-chain with any tooling that has the circuit's proving key. The only preconditions are that the Emporium contract holds a non-zero balance of some asset at the time of the call, which is a realistic and recurring protocol state (fees, in-flight balances).

### Recommendation
- For the Emporium "Min" path, do not allow `signerAddress == address(0)` to skip signature verification when `op.value > 0` or when the call could move any asset out of the Emporium's own balance; require an explicit relay/self-authorization binding.
- Ensure the `MainEVMCircuitMin` proof (or an equivalent constraint enforced in `formInputEmporiumMin`/`Hinkal.transact`) actually binds and constrains any value that can be moved through `EmporiumOperation.value`/`callData`, not just an arbitrary self-chosen `messageSeed`.
- Add a global balance-conservation check in `EmporiumUpgradeable.runAction` and `Hinkal.transact()` that is not conditioned on `circomData.erc20TokenAddresses.length`, so that ETH/ERC20 balance changes caused by `ops` are always measured and constrained regardless of the declared token array length.

### Proof of Concept
1. Attacker (any EOA, no prior deposit) picks `messageSeed`, computes `message = Poseidon(1)([messageSeed])`, and generates a valid Groth16 proof for `MainEVMCircuitMin` with public inputs `outTimeStamp`, `calldataHash` of their choice.
2. Attacker builds `CircomData` with: `erc20TokenAddresses = []`, `amountChanges = []`, `inputNullifiers = []`, `outCommitments = []`, `dimensions.tokenNumber = 0`, `externalActionData = {externalActionId: HINKAL_EMPORIUM_ACTION_ID, externalAddress: EmporiumUpgradeable, externalActionMetadata: abi.encode(EmporiumStack({signerAddress:address(0), ops:[{endpoint: victimToken, invokeWallet:false, value:0, callData: abi.encodeCall(IERC20.transfer,(attacker, victimToken.balanceOf(EmporiumUpgradeable)))}], maxFee:0, deadline:0, v:0,r:0,s:0}))}`, `rootHashHinkal`/`rootHashHinkalIndex` = any historically valid root/index pair on this chain, `calldataHash` computed self-consistently via `getHashedCalldata`.
3. Attacker calls `Hinkal.transact(a, b, c, dimensions, circomData)`. `verifyProof` succeeds (trivial circuit), `rootHashExists` succeeds (any valid root works), `calldataHash` self-check passes, and `_externalTransact` → `EmporiumUpgradeable.runAction` executes the crafted `ops` with `signerAddress == address(0)`, skipping `verifyWallet`'s ECDSA check entirely, and transferring the Emporium's full token balance to the attacker with no balance-equation check anywhere in the call path.

        );

        verifyWallet(stack, circomData);

        for (uint256 i = 0; i < stack.ops.length; i++) {
            EmporiumOperation memory op = stack.ops[i];

            bool success;
            bytes memory err;

            // CASE 1: Stateful Interaction
            if (op.invokeWallet && stack.signerAddress != address(0)) {
                (success, err) = IHinkalWallet(stack.signerAddress)
                    .callHinkalWallet(op.endpoint, op.callData, op.value);
            }
            // CASE 2: Stateless Interaction

                    revert UnauthorizedWalletCall();

                (success, err) = op.endpoint.call{value: op.value}(op.callData);
            }

            if (!success) {
                revert CallFailed(err);
            }

            circomData.erc20TokenAddresses
