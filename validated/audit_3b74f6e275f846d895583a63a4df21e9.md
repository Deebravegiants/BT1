### Title
Webhook `shop-domain` header trusted for tenant identity without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates a webhook exclusively by HMAC-signing the raw request body, but exposes `shop` (tenant identity) by reading it from an HTTP header that is never included in the signed material.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate`/`validate_signature` computes the HMAC purely over that signable string and compares it against the `hmac-sha256` header [2](#0-1) . Meanwhile `Request#shop`, used by the host app to identify which tenant/shop the webhook belongs to, is read straight from the `shop-domain` header without any cryptographic binding to the signed body: `T.cast(shopify_header("shop-domain"), String)` [3](#0-2) . The constructor only checks for the header's *presence*, not that its value is bound to the signature: `["topic", "hmac-sha256", "shop-domain"].each { ... unless headers.key?(...) }` [4](#0-3) .

This mirrors the reported bug class exactly: "a field acted on but not covered by the HMAC." The equality that should hold is:
`shop identity used by the application == shop identity cryptographically verified by the HMAC`.
In this gem, the left side is `Request#shop` (header-derived), and the right side is `Request#topic`/body only — `shop` is never part of `to_signable_string`, so the equality does not hold structurally.

### Impact Explanation
Any consumer of `ShopifyAPI::Webhooks::Request#shop` (the documented API for identifying the source shop of an inbound webhook) is trusting an HMAC-authenticated request's body/topic while accepting an arbitrary, attacker-controlled `shop-domain` header value as the tenant identity. Since Shopify's HMAC only covers the raw body, an attacker who can replay or forward any validly-signed webhook payload (e.g., one they legitimately received for shop A, since apps receive webhooks for every shop that installs them) can resubmit it with a forged `X-Shopify-Shop-Domain` header set to shop B. If the host application uses `Request#shop` (as the gem intends and documents) to route/attribute webhook data to a tenant/session without independently re-verifying the shop against installed/known shops, this enables cross-tenant data injection/attribution — i.e., processing shop A's authentic, signed event as if it belongs to shop B.

### Likelihood Explanation
Moderate-to-high: an app receives legitimately-signed webhooks for its own shop under normal operation, giving an attacker (any merchant that installs the app) a source of validly HMAC-signed raw bodies. The `shop` header is not part of what's verified, so swapping it costs nothing and is not out-of-scope (it does not require `api_secret_key`, a leaked token, or TLS interception — only a webhook payload the attacker already legitimately possesses from their own installation).

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the HMAC-signed material, or otherwise cryptographically bind them (e.g., by having the gem cross-check `shop` against the tenant associated with the session/API key context before exposing it), so `Request#shop` cannot diverge from the value Shopify actually authenticated.

### Proof of Concept
1. App receives a legitimately Shopify-signed webhook for `attacker-shop.myshopify.com` (attacker installs the app on their own dev store to obtain one).
2. Attacker replays the exact `raw_body` and `hmac-sha256` header (both unchanged, so `HmacValidator.validate` still returns `true`) but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:).shop` returns `"victim-shop.myshopify.com"` while `Utils::HmacValidator.validate(request)` still returns `true`, because `shop` is outside `to_signable_string`.
4. A host application that trusts `request.shop` after HMAC validation (the gem's documented usage pattern) will process/attribute the payload to the wrong tenant.
