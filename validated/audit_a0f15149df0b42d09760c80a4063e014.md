### Title
Multi-token escrow withdrawal permanently reverts and locks all escrowed assets if any single token transfer to the beneficiary fails (blocklist/pause) - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw()` iterates over all output/input tokens of an intent order and transfers each to a single `beneficiary` in one atomic loop. If any one token in that array cannot be transferred to the beneficiary — because the token is paused, or the beneficiary is blocklisted by that token's issuer (e.g. USDC/USDT-style freeze) — the whole function reverts, and since the loop is atomic there is no way to skip the bad token and settle the others. This mirrors the reported analog's bug class ("Funds may become locked if a plugin is blocklisted, or LINK is paused"): a single unreachable asset/address inside an iteration blocks recovery of everything else in that batch.

### Finding Description
`_withdraw` loops over `body.tokens`, transferring each escrowed asset to `beneficiary` via `_sendValue`/`safeTransfer`, and only after the loop succeeds does it release transaction fees and emit the finalize event: [1](#0-0) 

The same unconditional, all-or-nothing pattern exists in the Tron variant of the gateway: [2](#0-1) 

This function is invoked from `onGetResponse` (cross-chain escrow settlement) and from same-chain fill/refund paths, which are themselves reached through `EvmHost.dispatchIncoming`. Critically, `EvmHost.dispatchIncoming` is designed to gracefully absorb a failing module call so the rest of an incoming batch is unaffected and the specific message stays retryable: [3](#0-2) 

That graceful-failure design (delete receipt, return without reverting) protects the *batch*, but it does nothing for the *stuck order itself*: every retry of the same `WithdrawalRequest` re-runs the identical loop over the identical token set and beneficiary, so if one token in that order is permanently blocklisted for that beneficiary (or paused indefinitely), `_withdraw` will revert on every single attempt, forever. There is no per-token skip/partial-settlement path, and no admin/recovery function that can force-release the unaffected tokens or change the stuck token's recipient.

This is structurally identical to the reported `Vault._ensureLinkAmount()` bug: an atomic loop over a resource list where a blocklist/pause on one element makes the whole withdrawal permanently un-satisfiable, with no mechanism to isolate and bypass the bad element.

### Impact Explanation
For a multi-asset intent order (e.g., an order whose output/input contains both USDC and DAI to the same beneficiary), if the beneficiary is later blocklisted on USDC (or USDC/any output token is paused) before `_withdraw` executes successfully:
- The escrowed DAI (and any other unaffected tokens in the same order) becomes permanently unwithdrawable, even though nothing is wrong with DAI itself, because the atomic loop always reverts on the blocked USDC leg first.
- Any accrued Hyperbridge relayer transaction fees tied to that commitment (`_orders[commitment][TRANSACTION_FEES]`) are also permanently stuck, since fee release happens only after the token loop completes.
- Unlike the sender-refund design used elsewhere in the repo (e.g. `HyperFungibleToken`/`WrappedHyperFungibleToken`, whose timeout refund path pays back the *original sender*, a different address than a potentially-blocked beneficiary), `IntentsBase._withdraw` always pays the *same* `beneficiary` for every token in the order — there is no fallback path that redirects to an unaffected address. This makes the freeze permanent rather than a temporary externally-resolved condition, which is the "locked forever" branch of the Medium severity described in the analog report.

### Likelihood Explanation
Reachability requires no privileged action: any solver/filler/user can be the `beneficiary` of an order, and token issuers such as Circle (USDC) routinely blocklist addresses under sanctions/compliance actions, or pause the token contract, entirely outside Hyperbridge's control. A relayer delivering a `RedeemEscrow`/withdrawal message for such an order will always trigger the atomic revert. Given production usage of blocklistable stablecoins as intent assets, this is a realistically reachable, not merely theoretical, freeze condition.

### Recommendation
Make `_withdraw` resilient to a single failing token leg:
- Wrap each per-token transfer in a low-level call and, on failure, skip that token (leaving its escrow balance untouched) instead of reverting the entire function, then finalize/emit for the successfully transferred tokens.
- Provide a per-token retry/claim function so a still-stuck token's escrow can be withdrawn later (e.g., once unblocked) without blocking the already-successful legs.
- Consider allowing the affected token's balance to be redirected to a caller-specified alternate address (analogous to a refund-to-sender fallback) if the beneficiary remains blocked past a grace period, so funds are not held hostage indefinitely by a third-party blocklist decision.

### Proof of Concept
1. User places a cross-chain order whose output assets are `[USDC: 1000, DAI: 1000]`, filled by solver `S`.
2. Before the settlement message (`RedeemEscrow`/`withdraw`) is delivered, Circle blocklists `S`'s address on USDC (external, unprivileged-to-Hyperbridge event).
3. Relayer delivers the GET response / redeem request; `EvmHost.dispatchIncoming` calls `onGetResponse` → `withdraw(body, true)` → `_withdraw`.
4. The loop's `IERC20(USDC).safeTransfer(S, 1000)` reverts because `S` is blocklisted; the whole `_withdraw` call reverts.
5. `EvmHost.dispatchIncoming` catches this, deletes the response receipt, and returns — the request is "retryable" per design, but every retry re-executes the same reverting USDC transfer.
6. Both the 1000 DAI and the 1000 USDC (plus any pending relayer fee) tied to this commitment remain escrowed in the gateway indefinitely, with no function able to release the DAI alone or redirect it to an unblocked address. [1](#0-0) [4](#0-3)

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;

                ++i;
            }
        }

     * @dev Dispatch an incoming POST request to destination module

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
