### Title
Webhook `shop`/`topic` identity is not covered by HMAC, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` (and the underlying `Utils::HmacValidator`) verifies only the raw request *body* against the app's `client_secret`, but the shop identity and topic used for all downstream business logic are read from unauthenticated HTTP headers. Because the HMAC secret is shared across every shop that installs the app (it's the app's own `client_secret`, not a per-shop secret), a valid signature computed for one shop's webhook remains valid when replayed with different `shop-domain`/`topic` headers attached to the same body. This breaks the intended binding: **shop authenticated (via HMAC) == shop attributed to the event (`request.shop`)**.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from headers, which are never included in the signable content: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `to_signable_string` (i.e. the body only) using the app's `Context.api_secret_key`/`old_api_secret_key`, and simply secure-compares it to the received signature: [3](#0-2) 

`Registry.process` treats a passing HMAC check as full authentication of the request, then immediately trusts the header-derived `request.shop` and `request.topic` to build `WebhookMetadata` handed to the app's handler: [4](#0-3) 

Because the same `api_secret_key` signs webhooks for *every* shop that has installed the app (there is no per-shop key or nonce tying the signature to a specific `shop-domain`), an attacker who legitimately installs the app on a shop they control can capture one of their own real, correctly-signed webhook deliveries (body + `x-shopify-hmac-sha256`), then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and optionally `x-shopify-topic`) header for a victim shop. `HmacValidator.validate` still succeeds, because it never inspects the headers, and `Registry.process` will invoke the handler believing the event is authentic and belongs to the victim shop.

This is exactly the class of flaw described in the analog: a value acted upon by the application (`shop`) is not covered by the cryptographic binding (`hmac` over body only), so the "authenticated" side (HMAC valid for *some* shop under the app's secret) and the side trusted by business logic (`shop` header) diverge and can be made inconsistent by an attacker.

### Impact Explanation
Applications built on this gem drive tenant-scoped side effects (job enqueueing, database writes, order/customer/inventory processing, session/store lookups) keyed off `WebhookMetadata#shop` as documented in `docs/usage/webhooks.md`. An attacker who is merely a legitimate merchant on their own shop can forge webhook events that the receiving app will process as if they came from an arbitrary other shop (victim), with body content substantially influenced by the attacker (they trigger the topic on their own store). This is a cross-tenant integrity/data-injection primitive: a low-privilege user of the app can inject fabricated events attributed to another tenant, bypassing the sole authentication mechanism (`Registry.process`'s HMAC gate) that the app is documented to rely on ("This will verify the request did indeed come from Shopify"). This satisfies the "cross-tenant access" bar for Critical severity, since the gem's own guarantee ("verify the request did indeed come from Shopify" for *that* shop) does not hold.

### Likelihood Explanation
Exploitation requires only: (1) the attacker installs the target app on a shop they control (a normal, unprivileged step available to any merchant/developer), (2) they trigger a webhook topic they want to forge and capture the raw POST body + `x-shopify-hmac-sha256` header, (3) they replay it to the app's public webhook endpoint with a modified `x-shopify-shop-domain` header. No access to `api_secret_key`, access tokens, or any privileged credential is needed — the value of the exploit is precisely that the attacker never needs the secret because they simply reuse a signature that was legitimately produced for a different (their own) shop's payload. Likelihood is high for any app that keys business logic off `WebhookMetadata#shop`/`#topic` as directed by the gem's own documentation.

### Recommendation
Bind the header-derived identity fields into the HMAC-covered signable content, or otherwise authenticate them independently of the raw body. Concretely, `Request#to_signable_string` should incorporate `shop-domain` (and ideally `topic`/`webhook_id`) into the signed material (mirroring how the OAuth `AuthQuery#to_signable_string` — [5](#0-4)  — includes `shop` in what gets signed), so that a signature computed for shop A's payload cannot be replayed for shop B. At minimum, document prominently that `Registry.process`'s HMAC check does not bind the shop/topic headers, and require host applications to independently verify that `request.shop` corresponds to a shop with an active, known session/installation for the topic being processed before trusting it.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and configures a webhook for `orders/create`.
2. Attacker creates an order in their own shop, causing Shopify to POST a correctly-signed webhook to the app:
   ```
   POST /callback/orders/create
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of raw_body under app's client_secret>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   Body: {"id":1,"note":"forged payload attacker controls"}
   ```
3. Attacker replays the identical raw body and `x-shopify-hmac-sha256` value to the same endpoint but changes the shop header:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which recomputes the HMAC over the (unchanged) body and matches the (unchanged) signature — validation passes.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: ...)`, causing the app to process attacker-controlled data as though it originated from the victim's store.

Note: I was unable to find any additional per-shop or per-topic binding value elsewhere in `lib/shopify_api/webhooks/**` or `lib/shopify_api/utils/**` that would mitigate this replay; the index did not surface any nonce/timestamp/shop-scoped secret used for webhook signing.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
