### Title
Stale `TombStone.original_owner` allows a prior owner to reclaim an object that a later, legitimate owner intentionally sent to `BURN_ADDRESS` - ([File: aptos-move/framework/aptos-framework/sources/object.move])

### Summary
The soft-burn mechanism in `object.move` (`burn`/`unburn`) marks an object with a `TombStone { original_owner }` without transferring ownership, and only clears that tombstone when ownership is later moved via `TransferRef`/`LinearTransferRef::transfer_with_ref`. Ordinary owner-signed transfers (`transfer`, `transfer_call`, `transfer_raw`, `transfer_to_object`) do **not** clear a pre-existing `TombStone`. This lets a stale, unrelated `original_owner` reclaim an object out from under its current legitimate owner once that owner sends it to `BURN_ADDRESS`.

### Finding Description
`burn<T>()` [1](#0-0)  does not move the object to `BURN_ADDRESS`; it just attaches `TombStone { original_owner: signer }` to the object address, and aborts if a `TombStone` already exists.

`unburn<T>()` [2](#0-1)  has two reclaim branches:
- If the *current* owner equals `original_owner`, it simply clears the tombstone.
- If the current owner is `BURN_ADDRESS`, it transfers the object back to whatever address is stored in `TombStone.original_owner`, without requiring that this original owner be the one who actually sent the object to `BURN_ADDRESS`.

Normal ownership transfers do **not** clear the tombstone. `transfer_raw_inner` (used by `transfer`, `transfer_call`, `transfer_raw`, `transfer_to_object`) only updates `ObjectCore.owner` and emits a `Transfer` event — it never touches `TombStone`: [3](#0-2) 

By contrast, `transfer_with_ref` (the `TransferRef`/`LinearTransferRef` path) explicitly removes a pre-existing tombstone before transferring: [4](#0-3) 

This asymmetry means the tombstone's `original_owner` field is stale custody state that is only correctly reset on one of the two transfer code paths.

### Impact Explanation
Exploit sequence:
1. Owner A creates/owns object O, calls `object::burn(A, O)`. `TombStone{original_owner: A}` is attached; O is still owned by A (ungated transfer not disabled by `burn`).
2. A sells/transfers O to B via the ordinary signer-based `object::transfer` (or `transfer_call`). `ObjectCore.owner` becomes B; `TombStone{original_owner: A}` is left untouched because `transfer_raw_inner` never inspects/clears `TombStone`.
3. B is unaware of the stale tombstone (it's invisible via normal `owner()`/`is_owner` checks) and later performs a genuine burn by transferring O to `BURN_ADDRESS` using the same ordinary `transfer`/`transfer_call` function (B cannot call `object::burn` again since `TombStone` already exists, so B naturally uses the raw transfer to actually destroy/burn it).
4. A calls `unburn(A, O)`. Since `ObjectCore.owner == BURN_ADDRESS` and `TombStone.original_owner == A`, the check `original_owner_addr == signer::address_of(original_owner)` passes, and `transfer_raw_inner(O, A)` sends the object back to A — the *former* owner, not B who was the legitimate owner at time of burn.

This is a genuine custody-control break: ownership reassignment of an object (and everything held by/under it — e.g., a `FungibleStore`, token, or other custody-bearing resource nested under the object) is redirected to an unauthorized, unprivileged party (A) instead of preserving B's recovery rights or leaving the asset permanently burned as B intended. This can result in outright theft of object-held value by a prior owner, or denial of B's legitimate burn/recovery semantics — satisfying the "unauthorized owner reassignment" and "custody accounting corruption moves value to wrong holder" impact classes.

### Likelihood Explanation
The preconditions are fully permissionless and require no privileged assumptions: any object owner can call `burn`, transfer the object normally afterward (a very ordinary user action, since `burn` does not disable `allow_ungated_transfer`), and any subsequent owner can trigger the vulnerable state simply by using the standard `transfer`/`transfer_call` entry functions to move the object to `BURN_ADDRESS` (a well-known, hardcoded constant) instead of the `TransferRef`-based path. Given `transfer`/`transfer_call` are the default, most commonly used transfer entry points (used far more often than `TransferRef`-driven flows for plain owner-to-owner or owner-to-burn transfers), likelihood of accidental or intentional triggering is high.

### Recommendation
Clear any existing `TombStone` whenever ownership changes through *any* transfer path, not just `transfer_with_ref`/`LinearTransferRef`. The simplest fix is to move the tombstone-clearing logic into the shared `transfer_raw_inner` function (or equivalently call it from `transfer_with_ref` too, since both paths converge there), so a stale burn record can never survive a legitimate ownership transfer. Alternatively, `unburn`'s `BURN_ADDRESS` branch should require that the caller be the address that most recently transferred the object into `BURN_ADDRESS`, not merely whoever happened to create the (potentially stale) tombstone.

### Proof of Concept
```
// Pseudocode illustrating the exploit using object.move's own API
let ctor = object::create_object(@A);
let obj: Object<ObjectCore> = object::object_from_constructor_ref(&ctor);

// Step 1: A soft-burns
object::burn(&signer_A, obj); // TombStone{original_owner: A} attached, A still owner

// Step 2: A sells obj to B via ordinary transfer (ungated transfer still enabled)
object::transfer(&signer_A, obj, @B); // owner becomes B; TombStone untouched

// Step 3: B genuinely wants to burn the (now theirs) object -- can't call object::burn again
// (would abort EOBJECT_ALREADY_BURNT), so uses raw transfer to BURN_ADDRESS instead
object::transfer_call(&signer_B, object::object_address(&obj), BURN_ADDRESS);

// Step 4: A reclaims what should be permanently burned / owned in B's burn flow
object::unburn(&signer_A, obj); // succeeds: owner==BURN_ADDRESS && tombstone.original_owner==A
// obj is now transferred back to A, bypassing B's intended burn / ownership.

    /// Add a TombStone to the object.  The object will then be interpreted as hidden via indexers.
    /// This only works for objects directly owned and for simplicity does not apply to indirectly owned objects.
    /// Original owners can reclaim burnt objects any time in the future by calling unburn.
    /// Please use the test only [`object::burn_object_with_transfer`] for testing with previously burned objects.
    public entry fun burn<T: key>(owner: &signer, object: Object<T>) {
        let original_owner = signer::address_of(owner);
        assert!(is_owner(object, original_owner), error::permission_denied(ENOT_OBJECT_OWNER));
        let object_addr = object.inner;
        assert!(!exists<TombStone>(object_addr), EOBJECT_ALREADY_BURNT);
        move_to(&create_signer(object_addr), TombStone { original_owner });
    }

    /// Allow origin owners to reclaim any objects they previous burnt.
    public entry fun unburn<T: key>(
        original_owner: &signer,
        object: Object<T>,
    ) {
        let object_addr = object.inner;
        assert!(exists<TombStone>(object_addr), error::invalid_argument(EOBJECT_NOT_BURNT));

        // The new owner of the object can always unburn it, but if it's the burn address, we go to the old functionality
        let object_core = borrow_global<ObjectCore>(object_addr);
        if (object_core.owner == signer::address_of(original_owner)) {
            let TombStone { original_owner: _ } = move_from<TombStone>(object_addr);
        } else if (object_core.owner == BURN_ADDRESS) {
            // The old functionality
            let TombStone { original_owner: original_owner_addr } = move_from<TombStone>(object_addr);
            assert!(
                original_owner_addr == signer::address_of(original_owner),
                error::permission_denied(ENOT_OBJECT_OWNER)
            );
            transfer_raw_inner(object_addr, original_owner_addr);
        } else {
            abort error::permission_denied(ENOT_OBJECT_OWNER);
        };
    }
