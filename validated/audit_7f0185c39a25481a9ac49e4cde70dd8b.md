### Title
Unbounded O(n) trie scan in `bootstrap_congestion_info` runs synchronously on the chunk-apply hot path and is exploitable by pre-upgrade receipt-queue spam - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`bootstrap_congestion_info` fully iterates the `DelayedReceiptQueue` and every shard's `ShardsOutgoingReceiptBuffer` to reconstruct `CongestionInfo` from scratch, and it is explicitly documented as "IO intensive" [1](#0-0) . It is invoked synchronously inside `ApplyState::own_congestion_info`, which is called during normal chunk apply whenever no `CongestionInfo` is yet present for the shard (e.g., the block where the CongestionControl protocol feature first activates, or after a resharding event) [2](#0-1) . Because pre-upgrade receipt admission is bounded only by ordinary per-chunk compute/gas limits and not by congestion-based backpressure (which does not exist before the feature activates), an attacker can spend many blocks submitting cheap transactions to inflate the delayed and outgoing-buffer queues before the known upgrade height, making the one mandatory bootstrap chunk expensive for every validator applying that shard at that exact height.

### Finding Description
`bootstrap_congestion_info` loads the `DelayedReceiptQueue` and loops over every item calling `receipt_congestion_gas`/`receipt_size` for each, then loads `ShardsOutgoingReceiptBuffer` and does the same for every receiver shard's buffer [3](#0-2) . This is triggered from `ApplyState::own_congestion_info`, called inline during chunk application whenever `self.congestion_info.get(&self.shard_id)` is `None` [4](#0-3) . This condition is true exactly at the chunk height where a shard first needs congestion accounting (protocol-feature activation or resharding split), which is a publicly-known, deterministic block height.

Prior to this activation, admission into the delayed queue is governed only by the pre-congestion-control per-chunk compute/proof-size limits in `process_incoming_receipts`/`process_delayed_receipts` [5](#0-4)  — there is no `shard_accepts_transactions`/`reject_tx_congestion_threshold` backpressure yet, since that mechanism itself depends on `CongestionInfo` existing. An attacker submitting many cheap low-fee transactions over the blocks leading up to the known upgrade height can therefore accumulate a large delayed queue and/or large outgoing buffers (subject only to the aggregate per-chunk gas/compute ceiling over many blocks, and the gas cost of generating each receipt). At the upgrade block, every validator applying that shard's chunk must synchronously perform the full O(n) trie scan before it can process anything else in that chunk, so the cost is incurred simultaneously and identically by all validators tracking the shard rather than being amortized — this differs from an ordinary "just a slow chunk" scenario because it is deterministically correlated across the whole validator set for that shard at a single, attacker-predictable block height.

The code authors are aware this is expensive ("this might take a while", and comment "IO intensive operation! Only do it to bootstrap") [6](#0-5) [7](#0-6) , and there is tooling (`tools/state-viewer/src/congestion_control.rs`) specifically to benchmark this bootstrap cost, confirming it is a recognized, non-trivial operational risk [8](#0-7) . However, there is no cap in `bootstrap_congestion_info` itself, nor any chunked/incremental/async execution — the whole scan runs within the block's apply budget with no early-exit or resumability.

### Impact Explanation
This falls under liveness/chunk-application-stall (bounded resource use violation): a correlated, attacker-timed slowdown of chunk application across all validators of a shard exactly at a protocol-upgrade or resharding boundary. In the worst case this could push chunk-apply time past block/chunk production timeouts for that shard at that height, causing missed chunks or a stall that must be absorbed network-wide at a single, adversary-influenced moment (the attacker chooses how much to pre-load before the known, deterministic activation height).

### Likelihood Explanation
Preconditions are attacker-feasible without any privilege: only ordinary transactions that create action receipts routed to a congested/foreign shard (to grow `ShardsOutgoingReceiptBuffer`) or that exceed the chunk's compute budget (to grow `DelayedReceiptQueue`) are needed, and protocol-upgrade/resharding activation heights are public and predictable well in advance, giving the attacker many blocks to accumulate volume. The magnitude of achievable queue depth is bounded by total gas spent over that period and per-chunk limits, so the severity depends on economic cost vs. achievable scan-time increase — this requires empirical benchmarking (as the repo's own `PrepareBenchmark`/`Bootstrap` tooling suggests) to determine whether achievable queue sizes actually push apply time into problematic territory, which is not established purely from static code reading.

### Recommendation
Bound or amortize `bootstrap_congestion_info`: either (a) cap/pre-limit delayed and buffered queue growth even before congestion-control activation (e.g., apply a hard queue-length ceiling independent of the feature flag), or (b) make the bootstrap computation incremental/resumable across multiple chunks rather than a single synchronous full scan, or (c) precompute/checkpoint the aggregate congestion values incrementally as receipts are pushed even before the feature activates, so no O(n) catch-up scan is ever required on the hot path.

### Proof of Concept
Integration test plan (extending existing benchmarking tools):
1. Using `tools/state-viewer/src/congestion_control.rs`'s `PrepareBenchmark` path (or an equivalent test harness), populate `DelayedReceiptQueue` and `ShardsOutgoingReceiptBuffer` with receipt counts achievable via N blocks of maximal cheap-transaction spam under current gas/compute limits (e.g., simulate several thousand blocks at the per-chunk compute ceiling).
2. Call `bootstrap_congestion_info` (as exercised in `tools/state-viewer/src/congestion_control.rs::BootstrapCmd`) and measure wall-clock time and trie IO reads.
3. Assert that time stays within an acceptable bound (e.g., under the block time budget) for the maximum attacker-achievable queue depth; if it exceeds the bound, this demonstrates the liveness risk in `ApplyState::own_congestion_info`'s synchronous call path [9](#0-8) .

impl ApplyState {
    fn own_congestion_info(&self, trie: &dyn TrieAccess) -> Result<CongestionInfo, RuntimeError> {
        if let Some(congestion_info) = self.congestion_info.get(&self.shard_id) {
            return Ok(congestion_info.congestion_info);
        }

        tracing::warn!(target: "runtime", "starting to bootstrap congestion info, this might take a while");
        let start = std::time::Instant::now();
        let result = bootstrap_congestion_info(trie, &self.config, self.shard_id);
        let time = start.elapsed();
        tracing::warn!(target: "runtime", ?time, "bootstrapping congestion info done");
        let computed = result?;
        Ok(computed)
    }
