### Title
Webhook shop-domain header is not covered by HMAC, enabling cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` (tenant identifier) is read from a separate, unsigned HTTP header. `Registry.process` validates the HMAC and then hands the attacker-controllable `shop` value straight to the app's `WebhookHandler` as the authoritative tenant identity. This is the exact bug class described in the external report — a field that is acted upon (used as an identity/tenant binding) but not covered by the integrity check that is supposed to authenticate the message.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is completely independent of the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which calls `to_signable_string` (i.e., checks only the raw body against the secret) and, once that passes, immediately trusts `request.shop` as the tenant for dispatch: [3](#0-2) [4](#0-3) 

The `shop` value flows unchecked into `WebhookMetadata`, the struct passed to the app-defined handler as the source of truth for which merchant/tenant the event belongs to: [5](#0-4) 

The identity binding that is broken: `hmac == HMAC(secret, raw_body)` is verified, but the equality that the application actually needs — `shop_header == shop_that_produced(raw_body)` — is never checked. Any bytes can be placed in the `shop-domain` header without invalidating the HMAC, because the header is outside the signed content.

### Impact Explanation
This is a cross-tenant identity confusion vulnerability. An unprivileged attacker who operates their own Shopify store can:
1. Configure the app's webhook endpoint to receive a webhook for an event they trigger in their own shop, capturing a genuine `(raw_body, hmac-sha256, other headers)` tuple signed by Shopify with the app's real `client_secret` (the attacker never needs to know the secret — Shopify computes and delivers it).
2. Replay that exact `raw_body`/HMAC pair to the app's public webhook endpoint, but substitute the `X-Shopify-Shop-Domain` header with a victim shop's domain.
3. `HmacValidator.validate` still succeeds because it only checks the untouched `raw_body`.
4. `Registry.process` dispatches to the handler with `WebhookMetadata#shop` equal to the victim's domain, causing the host application to process/attribute the (attacker-controlled) webhook payload as if it originated from the victim tenant.

Depending on how the host app uses `shop` (e.g., to look up per-shop settings, write records, or trigger per-tenant side effects), this enables cross-tenant data injection/confusion — writing or triggering actions under a victim shop's identity without ever touching that shop's real access token or credentials. This matches the Critical impact category (cross-tenant access) defined in scope.

### Likelihood Explanation
Likelihood is realistic: it requires no privileged access, no leaked secret, and no TLS interception — only (a) the ability to run/own a Shopify store to obtain one genuine signed webhook body, and (b) the ability to POST an HTTP request with custom headers to the app's publicly reachable webhook endpoint, which is normal, expected usage of the gem's documented `Registry.process` entry point.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the HMAC-covered signable content, or otherwise independently verify that the `shop-domain` header matches metadata embedded in the verified `raw_body`/payload before trusting it for dispatch. At minimum, `Request#to_signable_string` should include the shop-domain header value so that any tampering invalidates the signature, e.g. combine `raw_body` with the shop header before hashing/verifying, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` includes `shop` in its signed parameters.

### Proof of Concept
```ruby
# Attacker triggers an event in their own shop and captures the genuine webhook
# Shopify sends (raw_body, headers) where headers include:
#   "x-shopify-hmac-sha256" => <valid HMAC over raw_body computed with app's real secret>
#   "x-shopify-shop-domain" => "attacker-shop.myshopify.com"
#   "x-shopify-topic"       => "orders/create"
raw_body = captured_body
valid_hmac_header = captured_headers["x-shopify-hmac-sha256"]

# Attacker replays the same body/HMAC to the app's public webhook endpoint,
# but swaps the shop-domain header to the victim's shop
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac_header,   # unchanged, still matches raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, unsigned
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# HMAC validation succeeds because only raw_body is checked:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...))
# The app now processes attacker-controlled data as if it belongs to victim-shop.myshopify.com
```
