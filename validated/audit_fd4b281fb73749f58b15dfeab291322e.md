### Title
Fee-on-transfer tokens desync `_orders` escrow accounting from actual contract balance in the Tron `IntentGatewayV2.placeOrder` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` credits the `_orders` escrow mapping using the nominal, pre-transfer input amount (minus protocol fee), but pulls the token via a plain `safeTransferFrom` without verifying how much the contract actually received. For fee-on-transfer (FOT) ERC-20s, the gateway's on-chain balance ends up lower than what `_orders` records, exactly mirroring the Allo `_fundPool` M-02 report.

### Finding Description
In `placeOrder`, the escrow credit for each input token is computed purely from the caller-supplied `order.inputs[i].amount`: [1](#0-0) 

For the common case with no predispatch call, the tokens are then pulled with a bare `safeTransferFrom` and the escrow is credited with `reducedInputs[i].amount` — a value derived solely from `originalAmount` and has no relation to what the contract actually received: [2](#0-1) 

For a fee-on-transfer token, `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` (line 459) delivers less than `order.inputs[i].amount` to the gateway, yet `_orders[commitment][token]` (line 463) is still credited with the fee-reduced (but not FOT-reduced) amount. This is the exact root cause pattern reported in Allo's `_fundPool`: the internal accounting variable is derived from the nominal transfer amount instead of the measured balance delta.

This is confirmed to be a real regression by comparing to the main EVM contract `evm/src/apps/IntentGatewayV2.sol`, which was explicitly hardened against this class of bug — it snapshots balances before/after each transfer and mutates `order.inputs[i].amount` to the actually-received amount before computing fees/commitment/escrow: [3](#0-2) [4](#0-3) 

This balance-based reconciliation (also with dedicated `FeeOnTransferToken` regression tests, e.g. [5](#0-4) ) is absent in the Tron contract's non-predispatch path, and the predispatch path (lines 389-446) also credits escrow from `reducedInputs[i].amount` (nominal-fee-adjusted) rather than the measured `balance` swept from the dispatcher, so a second layer of transfer fee (dispatcher → gateway) is likewise not reconciled into `_orders`.

Later, `withdraw()` pays out exactly the `_orders[commitment][token]` amount recorded at placement time via a raw low-level `token.call(...transfer...)`: [6](#0-5) 

Since the escrow ledger overstates the actual token balance held by the gateway, cumulative use of an FOT token across multiple orders will make the contract's real balance run below the sum of outstanding `_orders` entries.

### Impact Explanation
Once the gateway's actual FOT-token balance falls short of the aggregate `_orders` ledger, a subsequent legitimate `withdraw()` call (solver claiming escrow after fill, or a user reclaiming via cancellation/refund) for that token will fail — the `token.call` transfer will revert if the contract balance is insufficient, or (depending on the specific FOT token's transfer semantics) silently under-deliver, leaving the beneficiary permanently short of the tokens they are entitled to per `_orders`. Because `_orders[body.commitment][token]` is decremented by the full nominal `amount` regardless of what was actually transferred, this can permanently freeze/lose funds for the user or solver whose order can no longer be satisfied from the contract's real balance — a permanent freezing/loss-of-funds condition of Medium severity, consistent with the Sherlock report's classification.

### Likelihood Explanation
Any order placed with a fee-on-transfer or deflationary ERC-20 as an input token triggers this desync automatically — no special conditions, front-running, or privileged access are required; a single unprivileged `placeOrder` call from any user reaches this vulnerable code path. Given that the sibling contract (`evm/src/apps/IntentGatewayV2.sol`) was already patched for this exact scenario with dedicated tests, it indicates FOT-token compatibility is an intended/expected use case for the IntentGateway, making exploitation via ordinary usage (not adversarial manipulation) plausible.

### Recommendation
Apply the same fix used in `evm/src/apps/IntentGatewayV2.sol` to the Tron contract: measure the gateway's (and, for the predispatch path, dispatcher's) token balance before and after each `transferFrom`/sweep, and use the measured delta — not the nominal `order.inputs[i].amount` — as the basis for protocol-fee calculation, commitment hashing, and `_orders` escrow crediting.

### Proof of Concept
1. Deploy a 1% fee-on-transfer ERC-20 (e.g., the `FeeOnTransferToken` test helper already present in the repo at [7](#0-6) ) and use it as `order.inputs[0].token` with `amount = 1000e18` when calling `IntentGatewayV2.placeOrder` (Tron variant).
2. `safeTransferFrom` at line 459 delivers only 990e18 to the gateway (1% fee burned/retained by the token), but `_orders[commitment][token]` at line 463 is credited with `reducedInputs[0].amount` computed from the nominal 1000e18 (minus only the protocol fee, if any) — i.e., it records more than the contract actually holds.
3. Repeat placement with the same FOT token from other users; each order under-delivers 1% relative to what is recorded in `_orders`.
4. When a solver later calls `fillOrder`/triggers `withdraw()` to claim an early order's escrow in full, the contract's real balance of the FOT token is insufficient to cover all outstanding `_orders` entries for that token, causing `withdraw()`'s `token.call` transfer to fail for a legitimate claimant — permanently freezing that user's/solver's entitled funds.

contract FeeOnTransferToken {
    string public name = "FeeOnTransferToken";
    string public symbol = "FOT";
    uint8 public decimals = 18;
    uint256 public totalSupply;
    uint256 public feeBps;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    constructor(uint256 _feeBps) {
        feeBps = _feeBps;
    }

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        totalSupply += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        return _transfer(msg.sender, to, amount);
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
        // fee is burned
        totalSupply -= fee;
        return true;
    }
}
