Confirmed: `finalizeGraduation` calls `_seedUniswapV2Direct` to compute `liquidity`, and in the Regime‑3 hostile-pre-seed path (`_seedRebalancing` → `_routerDepositAndDispose`), `liquidity` stays `0` whenever `remToken == 0 || remLT == 0` at line 1466 in `packages/contracts/src/Bonding.sol` — that branch is skipped entirely and `liquidity` keeps its zero-initialized value [1](#0-0) . `finalizeGraduation` then unconditionally calls `LPLock.recordLock(tokenAddress, lpPair, liquidity)` [2](#0-1) , and `recordLock` hard-reverts with `ZeroAmount()` whenever `amount == 0` [3](#0-2) .

### Title
Zero-liquidity hostile-pre-seed causes `LPLock.ZeroAmount` revert, permanently bricking `finalizeGraduation` and freezing curve-raised LT + 250M reserve tokens — ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.finalizeGraduation` is a permissionless, one-shot state transition (`Graduating → Graduated`) that must succeed exactly once per token. Its hostile-pre-seed defense (`_seedRebalancing`/`_pairRebalance`/`_routerDepositAndDispose`) is explicitly documented by the contract's own comments as being able to drive `liquidity` to `0` under a sufficiently extreme attacker-controlled HyperSwap pre-seed, and the code passes that `0` straight into `LPLock.recordLock`, which unconditionally reverts on `amount == 0`. This is analogous to CVE‑2021‑3119: an unchecked edge-case input (a NULL/zero condition the calling code assumed couldn't occur) reaches a downstream function that dereferences/rejects it, crashing the operation. Here the "crash" is a permanent revert of the only path that can advance the token out of `Lifecycle.Graduating`.

### Finding Description
`_swapBudget` reserves 1% of the rebalance-swap budget specifically "so the subsequent `addLiquidity` always has a non-zero amount of BOTH sides to deposit," and the surrounding comment explicitly states the failure mode this is meant to prevent: *"the swap consumes 100% of one side. `_routerDepositAndDispose` then skips `addLiquidity` (`remToken == 0` or `remLT == 0`), `finalizeGraduation` returns `liquidity = 0`, and `LPLock.recordLock(...)` records a zero-sized lock"* [4](#0-3) .

However, the fix only clamps the *swap* input; it does not guarantee `remToken > 0 && remLT > 0` after the swap in all cases:
- `_seedRebalancing`'s direct-mint short-circuit (`reserveToken * BPS_DENOM <= tokensForLP * DIRECT_MINT_PRESEED_BPS && reserveLT * BPS_DENOM <= ltFromPair * DIRECT_MINT_PRESEED_BPS`) only fires when *both* sides are small relative to target; an attacker can pre-seed one side of the HyperSwap pair to be disproportionately large on just one axis (e.g., `reserveToken` enormous, `reserveLT` tiny) so the rebalancing path is taken instead of the direct-mint fallback [5](#0-4) .
- `_pairRebalance` caps the swap at `maxSwap = _swapBudget(inventory)`, i.e. 99% of `Bonding`'s own inventory of the input side — not 99% of the *pair's* reserve. If the graduation's `tokensForLP`/`ltFromPair` amounts are themselves small (e.g., a token graduating with a tiny curve-raise, or via the supply trigger on a token with a very small `LP_RESERVE` slice), `_noFeeSwapInput`'s computed `s` needed to reach the target ratio can legitimately consume the entire relevant-side inventory even after the 99% cap, especially since `maxSwap` is derived from Bonding's balance, not from a floor that guarantees post-swap non-zero remainder on both sides [6](#0-5) .
- `_routerDepositAndDispose` silently skips `addLiquidity` and returns `liquidity = 0` whenever either `remToken == 0` or `remLT == 0` post-swap — there is no fallback to `_seedDirectMint` at this point, and no revert to signal the failure; it returns cleanly to `finalizeGraduation` [7](#0-6) .
- `finalizeGraduation` has no guard for `liquidity == 0` before calling `LPLock.recordLock`, and `recordLock` is a strict `if (amount == 0) revert ZeroAmount();` check with no way to bypass or retry with a corrected amount, since the whole call reverts atomically [8](#0-7) .

Because `finalizeGraduation` is atomic, a revert on `recordLock` unwinds everything — including `info.lifecycle = Lifecycle.Graduated` and `delete $.pendingGraduation[tokenAddress]` — so the token stays stuck in `Lifecycle.Graduating` forever with no retry that changes the outcome: `pendingGraduation` is immutable cached data from phase 1, `p.tokensForLP`/`p.ltFromPair` never change, and the hostile pre-seed on the HyperSwap pair is already locked in by the time `finalizeGraduation` is first attempted. Every subsequent call to `finalizeGraduation` reproduces the identical zero-liquidity outcome and reverts identically. `AGENTS.md`'s own "brick resistance" claim ("Phase 2 must never revert under any pre-seed shape") is therefore not fully substantiated by the code as written — the documented fix (`_swapBudget`'s 1% reserve) addresses one specific extreme but does not close the gap for all pre-seed shapes, particularly asymmetric ones where only one side of the target ratio is starved.

### Impact Explanation
If triggered, the token permanently freezes in `Lifecycle.Graduating`:
- All curve-raised LT (`p.ltFromPair`) and the `tokensForLP` slice of the 250M `LP_RESERVE` tokens, already transferred out of the curve `Pair` by phase 1 (`_prepareGraduationLiquidity` / `Router.graduate`), sit unreachable inside `Bonding` — there is no rescue function for LP-bound token/LT inventory pinned to a specific `pendingGraduation[tokenAddress]` entry.
- Traders who bought into the curve up to the graduation trigger lose the ability to trade the token at all (curve trading is frozen at `Lifecycle.Graduating`, and HyperSwap trading never opens because the LP never locks).
- This is a permanent freeze of trader/creator funds tied to that token, matching the "Validate" bar (concrete, permanent freezing of funds), though it is scoped to the specific token that was hostile-pre-seeded — it does not cascade to other tokens or drain the FeeVault.

### Likelihood Explanation
Exploitation requires an attacker to pre-create the HyperSwap V2 TOKEN/LT pair for a specific not-yet-graduated token and mint into it with a deliberately asymmetric ratio (in scope per the rules: "pre-creating or pre-seeding the HyperSwap V2 TOKEN/LT pair before graduation"), then wait for or trigger graduation. This is a moderately sophisticated but fully unprivileged and permissionless attack — it requires no special role, only capital to seed the hostile pair and gas to call `pair.mint`. The severity of the pre-seed asymmetry needed depends on the specific token's `tokensForLP`/`ltFromPair` cached values and `Bonding`'s LT/token inventory at finalize time, so it is not universally triggerable on every token, but the code path exists and the contract's own comments acknowledge the zero-liquidity failure mode as a real (if partially mitigated) possibility.

### Recommendation
In `_routerDepositAndDispose` / `_seedRebalancing`, guarantee non-zero `liquidity` on every path — e.g., fall back to `_seedDirectMint` (or an explicit "escrow and allow permissionless recovery" path) whenever the post-swap `remToken == 0 || remLT == 0`, rather than silently returning `liquidity = 0`. Additionally, add an explicit `require(liquidity > 0)` guard inside `finalizeGraduation` before calling `LPLock.recordLock`, so a zero-liquidity condition fails fast with a clear, auditable revert reason rather than surfacing as an opaque, permanent `LPLock.ZeroAmount()` brick — and pair that guard with a redesigned fallback that can never itself return zero liquidity for a non-degenerate `(tokensForLP, ltFromPair)` pair.

### Proof of Concept
1. Attacker identifies a token still trading on the curve, close to its graduation threshold, whose cached (once graduation triggers) `tokensForLP`/`ltFromPair` will be small relative to what can be pre-seeded on HyperSwap.
2. Attacker calls the HyperSwap V2 factory to create the TOKEN/LT pair for that token (uncontested, since `_ensureUniswapV2Pair` in `finalizeGraduation` only creates the pair if it doesn't already exist).
3. Attacker mints into the pair with a heavily asymmetric ratio, sized so `reserveToken` is large relative to `tokensForLP` but `reserveLT` is not proportionally small enough to trip `_seedRebalancing`'s direct-mint short-circuit (`DIRECT_MINT_PRESEED_BPS` band).
4. Attacker (or anyone) triggers the curve buy/sell that crosses the graduation threshold, firing `_enterGraduating` and caching `pendingGraduation[token]`.
5. Anyone calls `finalizeGraduation(token)`. `_seedRebalancing` computes a rebalance swap capped by `_swapBudget(inventory)` that, given the crafted pre-seed ratio, still exhausts one side of `Bonding`'s inventory post-swap, so `_routerDepositAndDispose` sees `remToken == 0` (or `remLT == 0`) and skips `addLiquidity`, returning `liquidity = 0`.
6. `finalizeGraduation` calls `LPLock.recordLock(token, lpPair, 0)`, which reverts with `ZeroAmount()`. The entire `finalizeGraduation` call reverts, and since `pendingGraduation[token]` and the hostile pair state are unchanged, every future call to `finalizeGraduation(token)` reproduces the same revert — the token is permanently stuck in `Lifecycle.Graduating`.

    /// @dev Cap the rebalance swap at 99% of the available side's budget,
    ///      so the subsequent `addLiquidity` always has a non-zero amount
    ///      of BOTH sides to deposit. Without this, an extreme hostile
    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,
    ///      `_pairRebalance` clamps to the full budget, and the swap
    ///      consumes 100% of one side. `_routerDepositAndDispose` then
    ///      skips `addLiquidity` (`remToken == 0` or `remLT == 0`),
    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero
    ///      LP at the post-swap ratio. The 1% comes off the swap, not the
    ///      deposit — for any realistic pre-seed `s_unconstrained` is
    ///      orders of magnitude below `maxSwap`, so the cap doesn't bind
    ///      and behaviour is unchanged. It only kicks in for catastrophic
    ///      pre-seeds beyond our budget capacity, where the alternative
    ///      is bricking.
    function _swapBudget(
        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;
    }

    function _routerDepositAndDispose(
        address tokenAddress,
        address lt,
        uint256 protectedLT
    ) internal returns (uint256 liquidity) {
        BondingStorage storage $ = _s();
        address routerAddr = $.uniswapV2Router;
        address lpLock_ = $.lpLock;
        uint256 remToken = IERC20(tokenAddress).balanceOf(address(this));
        // Subtract `protectedLT` (LT that doesn't belong to this graduation
        // — concurrent escrows or stray dust, snapshotted at the top of
        // `finalizeGraduation`) so the deposit allowance can never pull
        // another graduation's earmark or accidentally absorb dust into a
        // locked LP.
        uint256 ltBal = IERC20(lt).balanceOf(address(this));
        uint256 remLT = ltBal > protectedLT ? ltBal - protectedLT : 0;

        if (remToken > 0 && remLT > 0) {
            IERC20(tokenAddress).forceApprove(routerAddr, remToken);
            IERC20(lt).forceApprove(routerAddr, remLT);
            (,, liquidity) = IUniswapV2Router02(routerAddr)
                .addLiquidity(tokenAddress, lt, remToken, remLT, 1, 1, lpLock_, block.timestamp);
            IERC20(tokenAddress).forceApprove(routerAddr, 0);
            IERC20(lt).forceApprove(routerAddr, 0);
        }

        // Burn off-ratio TOKEN remainder (`Bonding` is the Token owner).
        // Hostile pre-seeds reduce circulating supply by the attacker's
        // wasted-side share, net positive for honest holders.
        uint256 leftoverToken = IERC20(tokenAddress).balanceOf(address(this));
        if (leftoverToken > 0) {
            Token(tokenAddress).burn(address(this), leftoverToken);
        }
        // LT remainder is third-party — we cannot burn it. It stays in
        // this contract until `finalizeGraduation`'s post-bookend sweeps
        // it to the owner. Honest graduations never reach this code path,
        // so the residue is zero outside attack scenarios.
    }

    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }
