### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate` only authenticates the byte content of the body, never the `shop`, `topic`, `webhook_id`, or `api_version` values, which are all read straight from unauthenticated HTTP headers [2](#0-1) . `Registry.process` passes these unauthenticated header values directly to the app's handler as trusted identity data after only checking the body HMAC [3](#0-2) .

### Finding Description
This is the direct analog of the reported bug class: a control is supposed to bind one value (the "reward token" address / here, the webhook's claimed shop) but the actual check covers a different value (the ETH address constant / here, only the raw JSON body bytes), breaking the equality that the caller relies on:

`hmac-verified bytes (raw_body)` ⟺ `identity used by the handler (request.shop)`

Before the attacker's request: a merchant installs the app on their own store (an "unprivileged internet user" can trivially do this on their own dev/test store) and receives a legitimately-signed webhook — valid `raw_body` + valid `X-Shopify-Hmac-Sha256` for their own shop.

Attacker's request sequence: the attacker replays that exact `raw_body` and `hmac` header to the app's webhook endpoint, but substitutes the `X-Shopify-Shop-Domain` header (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) with a victim shop's domain or an arbitrary value.

After the attacker's request: `HmacValidator.validate` recomputes the signature over `to_signable_string` (`@raw_body` only) using `Context.api_secret_key` and it matches, because the body was untouched [4](#0-3) . `Registry.process` therefore proceeds and constructs `WebhookMetadata` with `shop: request.shop` taken from the now-forged header, and dispatches it to the app's `WebhookHandler#handle` as if it were an authentic event for that shop [5](#0-4) . The gem's own documentation instructs developers that calling `Registry.process` "will verify the request did indeed come from Shopify" [6](#0-5)  and shows the `shop` field being used directly to key background work (`shop_domain: data.shop`) [7](#0-6) , so the documented contract implies `shop` is authenticated — but it is not.

### Impact Explanation
This breaks the shop/tenant identity binding that host applications are expected to rely on for the `shop` field returned by `Registry.process`/`WebhookMetadata`. An attacker who can obtain any one validly-signed webhook body (trivial via their own store's installation) can relabel it to any target shop domain, causing the host app to process/store/queue data under the wrong tenant's identity — a cross-tenant confusion at the point where the gem is the trust boundary for webhook authenticity. This matches the "cross-tenant access" Critical impact category, since the vulnerability lives entirely in this gem's `HmacValidator`/`Webhooks::Request`/`Registry` code path, not in host-application misuse of an undocumented contract.

### Likelihood Explanation
Likelihood is high for any app that uses `data.shop` from `WebhookMetadata` (as the gem's own documented example does) to select tenant context for processing, since no additional binding of `shop` to the HMAC exists anywhere in `Request`, `HmacValidator`, or `Registry`. The only requirement is possession of one legitimately-signed webhook body+HMAC pair, which is trivially obtainable by installing the app on an attacker-controlled store.

### Proof of Concept
1. Attacker installs the victim's Shopify app on their own store `attacker.myshopify.com` and registers a webhook (e.g., `orders/create`).
2. Shopify sends a legitimately signed webhook: `raw_body = B`, headers include `X-Shopify-Hmac-Sha256: H` (valid for `B` and the app's `api_secret_key`), `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker replays this exact request to the same app endpoint, changing only `X-Shopify-Shop-Domain` to `victim.myshopify.com` (and/or spoofing `X-Shopify-Webhook-Id` to avoid dedupe):
   ```
   POST /callback/orders/create
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: H
   X-Shopify-Shop-Domain: victim.myshopify.com
   X-Shopify-Webhook-Id: <new-uuid>

   B
   ```
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is built; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and succeeds [8](#0-7) .
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: JSON.parse(B), ...)` and processes it as an authentic event for `victim.myshopify.com`, even though Shopify never sent anything for that shop.

### Recommendation
Bind the shop (and other identity headers) into the value that is actually HMAC-verified, or verify them out-of-band against Shopify's known/registered shop list before trusting `request.shop`:
- Have `Registry.process` cross-check `request.shop` against the shop associated with the session/webhook subscription that was registered (e.g., require the caller to supply the expected shop and compare), and/or
- Extend `to_signable_string`/validation to incorporate `shop`, `topic`, and `webhook_id` so header tampering invalidates the signature, matching the reported fix pattern of covering every value the check is meant to protect rather than leaving some values unchecked.
