Audit Report

## Title
Malicious collator can permanently censor specific DMP messages by exploiting the weak `check_enough_messages_included_basic` advancement rule used for the DMQ path - ([File: cumulus/pallets/parachain-system/src/lib.rs])

## Summary
`enqueue_inbound_downward_messages` validates the collator-submitted `AbridgedInboundDownwardMessages` split using only `check_enough_messages_included_basic`, which merely requires at least one full message be present when any hashed message exists, without verifying that hashing was actually necessary due to size constraints. The HRMP path, by contrast, uses the strictly stronger `check_enough_messages_included_advanced`, which requires that the total size of full messages plus the worst-case size of the first hashed message actually exceed the size budget. This asymmetry lets a malicious collator hash (and thus suppress dispatch of) any specific DMP message that would otherwise fit, while satisfying the weak check with an unrelated trivial full message.

## Finding Description
`into_abridged` at [1](#0-0)  is the honest algorithm invoked from `do_create_inherent` at [2](#0-1) , but a collator constructing its own PoV is free to submit any `InboundMessagesData` directly through the unsigned `set_validation_data` extrinsic (`ensure_none(origin)?`) at [3](#0-2) .

The DMQ ingestion path only calls the weak check: [4](#0-3) 

`check_enough_messages_included_basic` only asserts `full_messages.len() >= 1` when `hashed_messages` is non-empty, with no relation to actual message sizes: [5](#0-4) 

By contrast, HRMP uses `check_enough_messages_included_advanced`, which requires `full_messages_size + first_hashed_msg_max_size > max_full_messages_size` — i.e., hashing is only legal when the size budget was genuinely exceeded: [6](#0-5) [7](#0-6) 

The only other guard on the DMQ split is the MQC head assertion, which is agnostic to whether a message was submitted full or hashed — both `extend_downward` and `extend_with_hashed_msg` feed the same hash chain, and since DMP messages are public on the relay chain, a collator can always compute the correct hash for a message it chooses to suppress. Only `full_messages` are dispatched via `bounded_msgs_iter`/`T::DmpQueue::handle_messages`, while hashed messages only advance `LastProcessedDownwardMessage` and the MQC head without executing their payload: [8](#0-7) [9](#0-8) 

Since the message is marked processed via the advancing MQC pointer, there is no re-delivery mechanism — the censorship is permanent for that message.

The existing test suite confirms the exact asymmetry: `check_enough_messages_included_basic_works` shows the basic check passes with any full message present regardless of size [10](#0-9) , while `check_enough_messages_included_advanced_works` shows the advanced check rejects a hashed message when the full-messages size does not actually approach the budget [11](#0-10) .

## Impact Explanation
A malicious or colluding collator can selectively and permanently suppress the execution of any specific DMP message (e.g., governance dispatches, XCM `Transact` calls, or reserve-transfer completions targeted at the parachain) while still producing a `set_validation_data` inherent that satisfies all current on-chain assertions (MQC head match and the basic advancement check). This matches exactly the censorship risk the code comment on `check_enough_messages_included_advanced` describes, but that mitigation was applied only to HRMP, per the same code's own explicit warning: "A malicious collator can provide a collection that contains no full messages or fewer full messages than possible, leading to censorship" [12](#0-11) .

## Likelihood Explanation
This requires only an unprivileged, malicious/colluding collator with the ability to author blocks for the target parachain — a standard, explicitly acknowledged threat model in this codebase (collators are untrusted actors that construct their own PoV and submit unsigned inherents). No relay-chain collusion, privileged keys, or unusual protocol behavior is needed; the message data being hashed is public relay-chain data, so the correct hash is always computable. The attack is repeatable every block for any DMP message the collator wants to suppress.

## Recommendation
Apply an equivalent size-based advancement check to the DMQ path in `enqueue_inbound_downward_messages`, replacing/supplementing `check_enough_messages_included_basic("DMQ")` with `check_enough_messages_included_advanced("DMQ", ...)`, using `messages_collection_size_limit()` as `max_full_messages_size` and an appropriate max DMP message size (analogous to HRMP's `channel.max_message_size`) as `first_hashed_msg_max_size`.

## Proof of Concept
Extend the existing test module in `cumulus/pallets/parachain-system/src/parachain_inherent.rs`:
```rust
#[test]
fn dmq_basic_check_allows_censorship_of_large_fitting_message() {
    let small = InboundDownwardMessage { sent_at: 0, msg: vec![1; 1] };
    let large = InboundDownwardMessage { sent_at: 0, msg: vec![1; 900] };

    let crafted = AbridgedInboundDownwardMessages {
        full_messages: vec![small.clone()],
        hashed_messages: vec![(&large).into()],
    };

    // Passes trivially -- this is the only check applied to DMQ in
    // enqueue_inbound_downward_messages.
    crafted.check_enough_messages_included_basic("DMQ");

    // The stronger check applied to HRMP would reject this exact split.
    let result = std::panic::catch_unwind(|| {
        crafted.check_enough_messages_included_advanced(
            "DMQ",
            AbridgedInboundMessagesSizeInfo {
                max_full_messages_size: 1000,
                first_hashed_msg_max_size: 900,
            },
        )
    });
    assert!(result.is_err());
}
```
This demonstrates that a collator relying on the DMQ code path (governed solely by `check_enough_messages_included_basic` at `cumulus/pallets/parachain-system/src/lib.rs:1323`) can hash a large, otherwise-fitting DMP message and have it accepted on-chain, preventing its dispatch while advancing `LastProcessedDownwardMessage` past it.

	pub fn into_abridged(
		self,
		size_limit: &mut usize,
	) -> AbridgedInboundMessagesCollection<Message> {
		let mut messages = self.messages;

		let mut split_off_pos = messages.len();
		for (idx, message) in messages.iter().enumerate() {
			if *size_limit < message.data().len() {
				break;
			}
			*size_limit -= message.data().len();

			split_off_pos = idx + 1;
		}

		let extra_messages = messages.split_off(split_off_pos);
		let hashed_messages = extra_messages.iter().map(|msg| msg.to_compressed()).collect();

		AbridgedInboundMessagesCollection { full_messages: messages, hashed_messages }
	}

	pub fn check_enough_messages_included_advanced(
		&self,
		collection_name: &str,
		size_info: AbridgedInboundMessagesSizeInfo,
	) {
		// We should check that the collection contains as many full messages as possible
		// without exceeding the max expected size.
		let AbridgedInboundMessagesSizeInfo { max_full_messages_size, first_hashed_msg_max_size } =
			size_info;

		let mut full_messages_size = 0usize;
		for msg in &self.full_messages {
			full_messages_size = full_messages_size.saturating_add(msg.data().len());
		}

		// The worst case scenario is that were the first message that had to be hashed
		// is a max size message.
		assert!(
			full_messages_size.saturating_add(first_hashed_msg_max_size) > max_full_messages_size,
			"[{}] Advancement rule violation: full messages size smaller than expected. \
			full msgs size: {}, first hashed msg max size: {}, max full msgs size: {}",
			collection_name,
			full_messages_size,
			first_hashed_msg_max_size,
			max_full_messages_size
		);
	}

	fn do_create_inherent(data: ParachainInherentData) -> Call<T> {
		let (data, mut downward_messages, mut horizontal_messages) =
			deconstruct_parachain_inherent_data(data);
		let last_relay_block_number = LastRelayChainBlockNumber::<T>::get();

		let messages_collection_size_limit = Self::messages_collection_size_limit();
		// DMQ.
		let last_processed_msg = LastProcessedDownwardMessage::<T>::get()
			.unwrap_or(InboundMessageId { sent_at: last_relay_block_number, reverse_idx: 0 });
		downward_messages.drop_processed_messages(&last_processed_msg);
		let mut size_limit = messages_collection_size_limit;
		let downward_messages = downward_messages.into_abridged(&mut size_limit);

		// HRMP.
		let last_processed_msg = LastProcessedHrmpMessage::<T>::get()
			.unwrap_or(InboundMessageId { sent_at: last_relay_block_number, reverse_idx: 0 });
		horizontal_messages.drop_processed_messages(&last_processed_msg);
		size_limit = size_limit.saturating_add(messages_collection_size_limit);
		let horizontal_messages = horizontal_messages.into_abridged(&mut size_limit);

		let inbound_messages_data =
			InboundMessagesData::new(downward_messages, horizontal_messages);

		Call::set_validation_data { data, inbound_messages_data }
