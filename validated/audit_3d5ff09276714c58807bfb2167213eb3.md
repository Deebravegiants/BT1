Based on the investigation, there is a valid on-chain analog to this bug class in `Bonding.sol`'s graduation-seeding logic, and it is already characterized (but not eliminated) as the "M-02" residual in the test suite.

### Title
Budget-capped rebalance swap lets a front-run pre-seed permanently lock the graduated LP at a price far from curve-close - (File: `packages/contracts/src/Bonding.sol`)

### Summary
The external report's root cause is that an unprivileged actor's *first* on-chain interaction (a direct deposit-contract call setting withdrawal credentials) permanently fixes state that the later, "canonical" flow (Swell's `stake()`) cannot correct, because the Beacon chain only honors the first-seen withdrawal credentials for a given validator key. The alt.fun analog is `Bonding`'s two-phase graduation: an unprivileged trader can act *first* against the permissionless HyperSwap V2 `TOKEN/LT` pair (`factory.createPair` + `transfer` + `pair.mint`) before `finalizeGraduation` runs, and the protocol's correction mechanism (`_pairRebalance`) is capped at a fixed swap budget, so an extreme pre-seed ratio cannot be fully corrected — the graduated LP, which is then irreversibly locked via `LPLock.recordLock` (a one-shot, no-withdraw-in-v1 lock), opens materially away from the curve-close price.

### Finding Description
`finalizeGraduation` (`Bonding.sol:1000-1034`) seeds the HyperSwap pair via `_seedUniswapV2Direct` → `_seedRebalancing` (`Bonding.sol:1279-1354`). When an attacker has already minted LP into the pair at a hostile ratio ("Regime 3"), `_seedRebalancing` computes a rebalancing swap via `_pairRebalance`, but the swap input is capped at `_swapBudget` = 99% of the available inventory on one side (`Bonding.sol:1374-1378`, `1328`, `1344`): [1](#0-0) 

For a sufficiently lopsided pre-seed (e.g. LT reserve 200× the target ratio), the no-fee optimal swap that would be required to restore the curve-close ratio exceeds this budget, so `_pairRebalance` clamps the swap and the pool is left off-ratio when `_routerDepositAndDispose` deposits the remaining inventory: [2](#0-1) 

The over-funded side is then confiscated (burned/swept to owner) rather than restoring the price, and `finalizeGraduation` proceeds to call `LPLock.recordLock` unconditionally (`Bonding.sol:1031`), which is a one-shot function that `finalizeGraduation` cannot skip or redo (`LPLock.sol:70-85`, `AlreadyLocked` guard). Once locked, `LPLock` has no withdraw path in v1, so the mispriced LP position is permanent.

This is precisely tested and acknowledged in the repo's own test suite as the "M-02" regime: [3](#0-2) 

The comment `_swapBudget`'s natspec even frames this as an accepted trade-off "for catastrophic pre-seeds beyond our budget capacity, where the alternative is bricking" — i.e., the protocol deliberately chose "mispriced but not bricked" over "reverts."

### Impact Explanation
An unprivileged actor who buys tokens on the curve (permissionless, via `Bonding.buy`/`Zap.buy`) can accumulate token inventory, then front-run `finalizeGraduation` by calling HyperSwap's permissionless `factory.createPair` + `transfer` + `pair.mint(self)` with an extreme LT-rich or token-rich ratio (e.g. 200× off target). Because the correction swap is budget-capped at 99% of one side's inventory, the final locked LP opens at a price that can be off the curve-close price by >20% (per the test's own assertion, `_poolPriceLtPerToken(...) > 1.2×` target). This permanently misprices the protocol's own locked LP position (which cannot be withdrawn or corrected, per `LPLock`'s no-rescue-in-v1 design) and exposes every post-graduation trader/arbitrageur to a stale opening price, i.e., an LP seeded away from the curve-close price with no on-chain remedy — matching the "LP seeded away from the curve close price" impact criterion.

### Likelihood Explanation
The precondition (an extreme, lopsided pre-seed) requires only permissionless calls any wallet can make: buying tokens on the curve, creating the HyperSwap pair, transferring tokens/LT to it, and calling `pair.mint`. No privileged role, no protocol cooperation, and no timing race against the keeper beyond simply acting during the (multi-second) window between `_enterGraduating` (phase 1) and `finalizeGraduation` (phase 2) — the same window the report's off-chain-bot mitigation exists to narrow but not eliminate for the analogous scenario. The repo's own fuzz test (`testFuzz_hostilePreSeed_neverProfitable_neverBricks`) confirms the budget-capped regime is reachable across a wide range of seed multiples.

### Recommendation
Either (a) remove the fixed 99% swap-budget ceiling and instead size the rebalance swap dynamically so it always reaches the cached target ratio regardless of pre-seed extremity (accepting a larger, but ratio-correct, disposal of the off-side remainder), or (b) add a maximum-deviation guard in `finalizeGraduation` that reverts (or defers via a retry path) if the post-rebalance pool price would land beyond an acceptable bps tolerance of the cached curve-close ratio, paired with a recovery mechanism so a stuck graduation is not equivalent to a permanent brick. Given `LPLock` has no withdraw path, any accepted "mispriced but locked" residual should at minimum be bounded much tighter than the current ~2× worst case demonstrated by `test_hostilePreSeed_budgetCappedSwap_isNotProfitable`.

### Proof of Concept
Adapted directly from the repo's own regression test, `packages/contracts/test/TwoPhaseGraduation.t.sol::test_hostilePreSeed_budgetCappedSwap_isNotProfitable` (`TwoPhaseGraduation.t.sol:864-917`):
1. Launch a token and drive it into `Lifecycle.Graduating` via `_enterGraduating`.
2. Read `(tokensForLP, ltFromPair)` from `bonding.pendingGraduation(tokenAddr)`.
3. As an unprivileged griefer, create the HyperSwap pair and pre-seed it with `reserveToken = tokensForLP / 100` and `reserveLt = ltFromPair * 200`, then call `pair.mint(griefer)`.
4. Call `bonding.finalizeGraduation(tokenAddr)` (permissionless) — it succeeds (no brick) but the resulting pool price is >1.2× the curve-close price, and the LP is irrevocably locked in `LPLock` at that mispriced ratio. [4](#0-3)

        (address tokenAddr,) = _launchToken();
        _enterGraduating(tokenAddr);

        // Extreme LT-rich shape: TOKEN side at 1% of target, LT side at 200x.
        // The optimal TOKEN-in swap to reach the cached ratio is ~1.4x
        // `tokensForLP`, so the 99%-of-`tokensForLP` budget cap binds and the
        // pool stays ~2x off curve-close after the swap.
        uint256 reserveToken = tokensForLP / 100;
        uint256 reserveLt = ltFromPair * 200;

        // M-02 precondition: the optimal swap exceeds the budget (this is the
        // budget-capped regime, distinct from the swap-rounds-to-zero fallback
        // covered by the dust tests above).
        assertGt(
            _noFeeSwapInputUncapped(reserveToken, reserveLt, tokensForLP, ltFromPair),
            (tokensForLP * 99) / 100,
            "setup: optimal rebalance swap must exceed the per-side budget (M-02 regime)"
        );

        deal(tokenAddr, griefer, reserveToken);
        address hyperPair = _grieferMintPreSeed(tokenAddr, reserveToken, reserveLt);
        uint256 grieferLp = MockHyperswapPair(hyperPair).balanceOf(griefer);
        uint256 ownerLtBefore = lt.balanceOf(bonding.owner());

        bonding.finalizeGraduation(tokenAddr);
        assertTrue(bonding.isGraduated(tokenAddr), "finalize must succeed despite an unrecoverable pre-seed");

        // The accepted residual: no bounded swap can correct a 200x LT-rich
        // pre-seed, so the pool opens materially off curve-close.
