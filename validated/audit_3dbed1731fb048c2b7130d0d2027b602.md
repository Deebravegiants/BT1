### Title
`Wallet#getMnemonic` never checks `#isLocked` before decrypting and returning the seed - ([File: features/wallet/module/wallet.js])

### Finding Description
`Wallet#addSeed` and `Wallet#removeManySeeds` both explicitly call `await this.#assertWalletIsUnlocked()` before touching wallet storage [1](#0-0) , [2](#0-1) . `Wallet#getMnemonic`, however, contains no such check - it calls `#getSeed({ passphrase })` directly and returns the decrypted mnemonic [3](#0-2) . `#getSeed` itself performs no lock check either; it only conditionally auto-fills a stored generated passphrase and calls `this.walletStorage.get(SEED_KEY, { passphrase })` [4](#0-3) .

The `#isLocked` flag only gates the in-memory keychain state via `lock()`/`unlock()` [5](#0-4) ; it is not consulted anywhere in the `#getSeed`/`getMnemonic` path. When `usePassword` is `false`, or when `useAutoGeneratedPassword` is enabled (so the passphrase is transparently fetched from `walletStorage.get(GENERATED_PASSPHRASE_KEY)`), `#getSeed` will successfully decrypt and return the seed/mnemonic with **no passphrase from the caller and no lock check**, regardless of `this.#isLocked`. `getMnemonic` is exposed directly and unguarded through the wallet API surface: `wallet.getMnemonic: wallet.getMnemonic` [6](#0-5) .

Thus, any caller that can invoke the `wallet` API's `getMnemonic` method (e.g., via RPC/host bridge exposing the wallet API to the app UI/headless SDK) can retrieve the mnemonic while the wallet is in a locked state, as long as password protection is disabled or auto-generated-password mode is active - both of which are legitimate, supported configurations (`config.usePassword`, `config.useAutoGeneratedPassword`), not privileged/test-only states.

### Impact Explanation
This breaks the "locked means locked" invariant: an attacker or malicious surface that can reach the `getMnemonic` API call (without needing to go through `unlock()`) obtains the raw seed phrase, which is full wallet compromise (root secret disclosure enabling total fund theft across every account derived from the seed).

### Likelihood Explanation
Preconditions: the wallet instance must be configured with `usePassword: false`, or `usePassword: true` with `useAutoGeneratedPassword: true` (the passphrase is then silently retrieved from storage) - both are supported, real configuration paths, not test-only mocks. Given such a config, the exploit requires only calling the exposed `getMnemonic()` API method with no unlock step; this is directly reachable since the API module wires `wallet.getMnemonic` unguarded [7](#0-6) .

### Recommendation
Add an explicit lock check at the start of `getMnemonic` (and any other seed-returning method), mirroring `addSeed`/`removeManySeeds`:
```js
getMnemonic = async ({ passphrase, seedId } = {}) => {
  await this.#assertWalletIsUnlocked()
  ...
}
```
Alternatively/also enforce the check inside `#getSeed` itself so every caller benefits uniformly.

```js
  await wallet.create({ mnemonic: TEST_MNEMONIC })
  await wallet.lock()
  expect(await wallet.isLocked()).toBe(true)

  // Expected (secure) behavior: should throw 'wallet is locked'
  await expect(wallet.getMnemonic()).rejects.toThrow('wallet is locked')

  // Actual (current) behavior: resolves with the real mnemonic despite lock
})
```
This test currently fails (the call resolves with the mnemonic) instead of throwing, demonstrating the missing `#assertWalletIsUnlocked` guard in `getMnemonic`.
