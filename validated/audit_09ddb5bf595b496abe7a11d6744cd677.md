### Title
`recapitalize` credits the cash book without measuring actual tokens received, letting an unfunded payer drain custody while withdrawals later fail — ([File: contracts/pool/src/ops/recapitalize.rs])

### Summary
Analogous to OpenQ's "refund after `fundingTotals` was frozen breaks later claims", the pool's `recapitalize` settles against the internal `cash` book rather than the measured token balance. An unprivileged `payer` can invoke `pool.recapitalize(hub_asset, payer, offered)` with an `offered` amount covering the perceived shortfall; the pool releases `shortfall` tokens to `payer` from custody while the `cash` book is left overstating real holdings. Subsequent supplier withdrawals pass the pool's own `require_reserves` liquidity guard (which reads the book) and then revert inside the SAC token transfer for lack of custody — exactly the OpenQ pattern where a stale accounting figure outlives the funds it was meant to represent.

### Finding Description
`contracts/pool/src/lib.rs` exposes `recapitalize` → `ops::recapitalize`. The regression test in `contracts/pool/tests/flows.rs` (`test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody`, lines 3405–3483) documents the reachable sequence:

1. A supplier deposits; `cash` book equals token custody (asserted at 3424–3428).
2. `client().recapitalize(&hub(&t.asset), &payer, &custody)` is called by an arbitrary `payer` with **no prior token transfer**; after the call `token.balance(&t.pool) == 0` (3430–3433) while `cash >= deposit` (3435–3439).
3. The supplier's `withdraw` call passes `require_reserves`/`PoolInsolvent` guards — the test asserts neither `InsufficientLiquidity` nor `PoolInsolvent` fired — and fails only inside the SAC `transfer` with balance error 10 (3443–3473).

Root cause mirrors the OpenQ bug: accounting state (`cash` book / `fundingTotals`) is treated as frozen truth while a side exit path (`recapitalize` payout / `refundDeposit`) moves real tokens without being bound by, or reconciled against, that snapshot.

### Impact Explanation
Permanent freezing of user funds and protocol insolvency per (hub, token) book: the payer extracts the market's entire custody while the book still advertises solvency, so every honest supplier's withdrawal either silently mis-splits remaining cash or reverts at the token transfer. Any later depositor's funds become the de facto backing for the overstated book.

### Likelihood Explanation
Reachable by any unprivileged address: `recapitalize` is on the allowed entrypoint list and takes an arbitrary `payer` and `offered` — no auth, collateral, or health-factor precondition gates it. The precondition is only an outstanding perceived shortfall/cash in the market, which exists in any live market.

### Recommendation
In `recapitalize`, measure the actual token receipt via balance-delta (`balance` after pull minus `balance` before) or require the funds via an explicit `token.transfer_from(payer → pool)` before crediting `cash` and computing `shortfall`; never release custody to `payer` based solely on the declared `offered` amount. Treat the cash book as claims against verified custody, matching the fix direction of the source report ("don't allow the exit path after the accounting snapshot").

### Proof of Concept

```rust
// Supplier deposits; book == custody.
token_admin.mint(&t.pool, &deposit);
let supplied = t.client().supply(&t.sup(0, deposit))...scaled_amount;

// Unprivileged payer drains all custody with an unfunded recapitalize.
t.client().recapitalize(&hub(&t.asset), &payer, &token.balance(&t.pool));
assert_eq!(token.balance(&t.pool), 0);
assert!(t.state_snapshot().cash >= deposit); // book still claims solvency

// Supplier's withdraw passes pool guards, fails in the SAC transfer.
let outcome = t.client().try_withdraw(&receiver, &false, &t.wdr(supplied, i128::MAX, 0));
// => SAC BalanceError (10), not InsufficientLiquidity / PoolInsolvent
```
