### Title
`Registry.process` trusts the `shopify-shop-domain` webhook header for tenant attribution while the HMAC only covers the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
This is the same identity-binding failure pattern as the reported `L1MessageServiceV1` bug: an attribute that downstream code treats as authenticated (the message sender / here, the shop tenant) is not actually covered by the cryptographic check that is supposed to guarantee its authenticity (transient storage set from the proof / here, the HMAC signature).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The HMAC that `Registry.process` verifies is computed only over that raw body: [2](#0-1) [3](#0-2) 

However, the `shop` value that is handed to the app's handler as the tenant identifier is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never part of the signed bytes: [4](#0-3) [5](#0-4) 

`Registry.process` validates the HMAC over the body, then immediately constructs a `WebhookMetadata` using `request.shop` (the unauthenticated header) and dispatches it to the app's handler as the authoritative tenant: [6](#0-5) [7](#0-6) 

The identity binding that should hold is: `authenticated(shop) == shop used for tenant-scoped processing`. In this gem it instead holds: `authenticated(body bytes) ≠ shop header used for tenant-scoped processing`. Because `hmac-sha256` is computed by Shopify over the request body only (per Shopify's documented webhook signing scheme) and this gem's `to_signable_string` mirrors that, `shop-domain` is never covered by the signature at any point in this code path.

### Impact Explanation
An unprivileged actor who can capture or replay one legitimate, validly-signed webhook delivery (e.g., a webhook sent to their own store, which any merchant/developer can generate) can resend the same body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a different shop domain. Because `Registry.process` only validates the HMAC against the body and trusts the header for `shop`, the app's `WebhookHandler#handle` will process data under the wrong tenant identity (`WebhookMetadata#shop`), i.e. actions/state changes get attributed to a shop the attacker does not own. This is a cross-tenant identity-binding bypass reachable purely through this gem's `Registry.process`/`Request` API with no access token, `client_secret`, or privileged account required — only a previously delivered legitimate webhook body of the attacker's own shop.

### Likelihood Explanation
Requires the attacker to already possess one legitimately-signed webhook (trivial: install their own free app/dev store and trigger any webhook event), then replay it with a forged shop header to the target app's public webhook endpoint. No secret material is needed. This is a realistic, low-effort attack path for any external actor targeting an app built on this gem.

### Recommendation
Bind the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) header values into the signed payload verification, e.g., include them in `Request#to_signable_string`, or otherwise have `Registry.process` re-derive/verify `shop` from a source that is covered by the HMAC rather than trusting the raw header value used for tenant dispatch.

### Proof of Concept
1. Attacker owns/controls `attacker-shop.myshopify.com` and installs the target app, or otherwise triggers/observes one legitimate webhook delivery to the app (`raw_body`, `X-Shopify-Hmac-Sha256`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic`, `X-Shopify-Webhook-Id`).
2. Attacker resends the exact same raw body and `X-Shopify-Hmac-Sha256` value to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (the raw body only) and succeeds because the body/HMAC pair is unchanged — see `HmacValidator.validate_signature`: [8](#0-7) 
4. `Registry.process` builds `WebhookMetadata.new(..., shop: request.shop, ...)` using the forged header, and calls the app's `handler.handle(data: ...)` with `shop == "victim-shop.myshopify.com"` even though the payload was never authenticated for that shop: [9](#0-8) 
5. The app processes/stores data as if it originated from `victim-shop`, achieving cross-tenant data confusion/attribution without any credential belonging to the victim.

        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
