### Title
Uniswap V4 spot-price venue pricing with disabled overfill clamp lets a flash-loan-manipulated pool drain solver funds - ([File: sdk/packages/simplex/src/strategies/fx.ts])

### Summary
The Simplex intent-solver's `FXFiller` prices curveless (venue-priced) legs directly from a live Uniswap V4 pool's instantaneous mid price (`sqrtPriceX96`), the same class of manipulable, single-block price source flagged in the reference report's `UniswapV2Oracle.getPrice`. The only defense (`checkPriceGuard`) is optional, checks a static-reference deviation band rather than execution cost, and — critically — the per-leg overfill clamp that would otherwise bound the blast radius of a bad quote has been explicitly disabled, so a manipulated pool price can cause the filler to pay out an unbounded excess amount when filling a real `IntentGatewayV2` order.

### Finding Description
`resolveLegRates` prices any curveless pair whose `token0` is a USD stablecoin directly from `getVenueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice` → `computeDirectPoolPriceUsd`, which returns the pool's raw spot mid derived from `sqrtPriceX96` with no TWAP, no size/impact term, and no liquidity-depth weighting: [1](#0-0) [2](#0-1) 

The only mitigation is `checkPriceGuard`, which is optional per-chain configuration and only rejects quotes that deviate from a static `referencePrice` by more than `maxDeviationBps` — it does not model execution/impact cost and, per the maintainers' own note, "trusts the live pool": [3](#0-2) [4](#0-3) 

Even where the guard is configured, an attacker can move the pool price to just inside the allowed deviation band via a flash loan, still skewing the rate used to size the fill. Worse, the per-leg overfill clamp that would cap losses from exactly this kind of manipulated venue price has been intentionally disabled, with an explicit comment acknowledging the removed protection: [5](#0-4) 

The resulting `policyMaxOutput`/`targetOutput` is the actual amount the filler pays out on-chain via `fillOrder` against a real `IntentGatewayV2` order escrow, so a manipulated rate translates directly into an over-payment of real funds by the solver: [6](#0-5) 

### Impact Explanation
This is a direct analog of the reported bug class: pricing derived from a spot AMM state that a flash loan can move within a single transaction, with a downstream consumer (here, an intent solver filling a `IntentGatewayV2` order) that pays out real assets at that price. Because the overfill clamp is disabled, there is no hard ceiling on how much a manipulated price can cause the filler to overpay per fill, resulting in concrete theft/loss of solver funds — an unprivileged party (an order placer or anyone able to flash-loan the referenced Uniswap V4 pool) can trigger it.

### Likelihood Explanation
Reachable by any unprivileged intent placer: submit an `IntentGatewayV2` order on a curveless, venue-priced pair while manipulating the referenced Uniswap V4 pool via a flash loan in the same transaction/bundle, then have the solver's `FXFiller` bid/fill against the skewed quote. Likelihood is higher for pools without a configured price guard (guard is optional), and non-zero even when a guard is configured because the guard only bounds deviation from a static reference, not manipulation within that band, and the removed overfill clamp means no compensating control exists downstream.

### Recommendation
- Re-enable and enforce the overfill clamp for venue-priced legs, or otherwise bound per-fill exposure to venue-priced pairs independent of the (optional) price guard.
- Replace or supplement the instantaneous `sqrtPriceX96` mid with a manipulation-resistant source (e.g., a TWAP over multiple blocks, or a cross-referenced external oracle) for venue pricing.
- Make the price guard (`referencePrice` + `maxDeviationBps`) mandatory for any venue-priced pair rather than optional, and consider tightening bands based on the pool's realistic flash-loan-manipulation range rather than a static business-driven tolerance.

### Proof of Concept
1. Operator configures a curveless pair priced via `[vault.uniswapV4]` with no `referencePrice`/`maxDeviationBps` guard (or a wide one) as shown in the example config: [7](#0-6) 
2. Attacker takes a flash loan and swaps heavily against the configured Uniswap V4 pool to move `sqrtPriceX96` far from the fair market mid.
3. In the same or immediately following transaction, attacker submits an `IntentGatewayV2` order on the venue-priced pair, sized so `FXFiller.calculateProfitability` → `resolveLegRates` → `getVenueUsdPrice` reads the manipulated pool price.
4. `checkPriceGuard` either is not configured or the manipulated price is kept within the allowed deviation band; `computeLegPolicyOutput` computes an inflated `policyMaxOutput` from the skewed rate.
5. Because the overfill clamp is disabled (`sdk/packages/simplex/src/strategies/fx.ts:678-701`), the filler pays the unclamped inflated `targetOutput` to fill the order, delivering excess value to the attacker at the solver's expense.
6. Attacker reverses the flash-loan swap, restoring the pool price and repaying the loan, keeping the excess extracted from the solver as profit.

	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}

	private computeDirectPoolPriceUsd(
		pos: HydratedV4Position,
		sdkPool: V4Pool,
		chain: string,
	): { exoticToken: string; priceUsd: Decimal } | null {
		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {
				exoticToken: c1,
				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

		if (c1 === usdc || c1 === usdt) {
			// currency1 is stable → exotic is currency0
			// token0Price = "token1 per token0" = USD per exotic
			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),
			}
		}

		return null
	}

**File:** docs/content/developers/evm/simplex/pricing.mdx (L68-72)
```text
## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
```
