### Title
Webhook HMAC Does Not Cover `shop-domain`/`topic`/`webhook-id` Headers, Allowing Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature validated by `Utils::HmacValidator` binds solely to the JSON payload bytes. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values that `ShopifyAPI::Webhooks::Registry.process` uses to select the handler and attribute the event to a merchant are read from HTTP headers that are completely outside the HMAC's coverage.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled from headers via `shopify_header`, none of which are part of `to_signable_string`: [2](#0-1) 

`Registry.process` validates the HMAC and then trusts the header-derived `topic` and `shop` for dispatch and tenant attribution without any additional binding: [3](#0-2) 

Because Shopify signs every shop's webhooks with the app's single shared `client_secret` (the same `api_secret_key` used across all shops that install the app), any shop that has legitimately installed the app can trigger a webhook event in their own store and legitimately receive a `(raw_body, hmac)` pair that is valid for that body under the shared secret. Since the HMAC never binds to `shop-domain`, `topic`, or `webhook-id`, that shop-controlled attacker can replay the same body/HMAC pair to the app's public webhook endpoint while substituting the `shop-domain` header for a different (victim) shop, or substituting the `topic`/`webhook-id` header to redirect the payload to a different handler. This breaks the identity binding: `hmac-verified bytes == raw_body` but the values *acted upon* (`shop`, `topic`) are unauthenticated, unlike the OAuth flow's `AuthQuery`, which explicitly folds `shop`, `host`, `state`, `code`, and `timestamp` into `to_signable_string` before computing the HMAC: [4](#0-3) 

The webhook path has no equivalent binding for its routing/attribution fields.

### Impact Explanation
This qualifies as Critical (cross-tenant access): an app that keys webhook side-effects (e.g., data updates, mandatory GDPR compliance handlers like `customers/redact`, `customers/data_request`, `shop/redact`) off `WebhookMetadata#shop`/`#topic` as forwarded by `Registry.process` can be made to apply another shop's webhook data to the wrong tenant's records, or to invoke a different handler than the one Shopify actually intended, purely by an attacker who controls their own (legitimately installed) shop and can therefore generate valid signed bodies at will.

### Likelihood Explanation
Any merchant who installs the app is, from the app's perspective, an "unprivileged" webhook sender relative to other tenants, and can trigger webhook events in their own store to obtain valid `(body, hmac)` pairs at will. Forging the `shop-domain`/`topic` headers on a raw HTTP POST to the app's public webhook endpoint requires no secret knowledge beyond the already-obtained valid HMAC for their own payload, making this straightforward to exploit for any app that relies on this gem's `Webhooks::Registry`/`Request` for authentication of webhook origin and routing.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in `Request#to_signable_string` (or otherwise cryptographically bind them, e.g., by validating them against Shopify's out-of-band webhook metadata/GraphQL confirmation) so that the HMAC check in `Utils::HmacValidator.validate` fails if any of these header values are altered relative to what Shopify actually signed for that event.

### Proof of Concept
1. App developer registers a webhook handler for `orders/create` and a separate mandatory handler for `customers/redact`.
2. Attacker installs the app on `attacker-shop.myshopify.com` and triggers an `orders/create` webhook, capturing the legitimate `raw_body` and its `x-shopify-hmac-sha256` value (valid because it's computed with the app's real, shared `api_secret_key`).
3. Attacker POSTs to the app's public webhook endpoint reusing that exact `raw_body`/`hmac`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and/or `x-shopify-topic: customers/redact`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks `raw_body` against the HMAC (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. `Registry.process` dispatches to the `customers/redact` handler (or whichever topic was spoofed) with `WebhookMetadata#shop` set to `victim-shop.myshopify.com`, causing the app to act on the wrong tenant/topic despite the request never actually originating from Shopify for that shop/topic combination.
