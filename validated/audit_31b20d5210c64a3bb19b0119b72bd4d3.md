Audit Report

## Title
Unauthenticated LOOP Plugin Debug/Metrics/PPROF Endpoints Bypass the Node's Authentication Layer - (File: core/web/router.go)

## Summary
`loopRoutes` is registered directly on the bare `api` group in `NewRouter` with no `auth.Authenticate(...)` wrapper, unlike the functionally equivalent `debugRoutes` and `metricRoutes` groups which are explicitly gated behind session/token authentication. This exposes `/discovery`, `/plugins/:name/metrics`, `/plugins/:name/debug/pprof/*profile`, and `/plugins/:name/debug/pprof/symbol` to any unauthenticated client able to reach the node's HTTP listener.

## Finding Description
`NewRouter` builds the `api` gin group with only CORS/rate-limit/session-cookie middleware, no authentication [1](#0-0) . Individual sub-route builders are expected to explicitly wrap themselves with `auth.Authenticate`: `debugRoutes` does so for `/debug/vars` [2](#0-1) , and `metricRoutes` (the node's own pprof surface) is only ever mounted inside `authv2`, which requires `auth.Authenticate(..., auth.AuthenticateByToken, auth.AuthenticateBySession)`, explicitly commented "Debug routes accessible via authentication" [3](#0-2) .

In contrast, `loopRoutes(app, api)` is called directly on the unauthenticated `api` group [4](#0-3) , and the `loopRoutes` function itself applies no authentication middleware whatsoever before registering `/discovery`, `/plugins/:name/metrics`, `/plugins/:name/debug/pprof/*profile`, and `/plugins/:name/debug/pprof/symbol` [5](#0-4) . Reviewing the handler implementations in `core/web/loop_registry.go` confirms none of `discoveryHandler`, `pluginMetricHandler`, `pluginPPROFHandler`, or `pluginPPROFPOSTSymbolHandler` perform any internal authentication or authorization check — they only validate that the named plugin exists in the registry before proxying the request to the plugin's internal metrics/pprof port [6](#0-5) [7](#0-6) . This confirms the claim's root cause precisely as described: a second, parallel debug/pprof surface exists that silently omits the authentication policy applied to the equivalent `metricRoutes`/`debugRoutes` surface.

The existing RBAC regression test suite (`routesRolesMap` in `core/web/auth/auth_test.go`) enumerates all `/v2/*` and other protected routes but contains no entries for `/discovery` or `/plugins/:name/*`, confirming these routes are untested and outside the existing auth-verification harness.

## Impact Explanation
`/plugins/:name/debug/pprof/*profile` and `/plugins/:name/debug/pprof/symbol` proxy directly to the LOOP plugin's `net/http/pprof` handlers, and `/plugins/:name/metrics` proxies to the plugin's Prometheus `/metrics` endpoint — all without any credential check. An unauthenticated remote client can:
- Enumerate all registered LOOP plugins and their scrape targets via `/discovery`.
- Pull CPU/heap/goroutine/mutex/block profiles and full stack traces of any named plugin process, potentially leaking in-memory secrets, config, or internal state.
- Repeatedly trigger expensive profiling operations (e.g., `profile?seconds=N`) against the plugin's internal endpoint, causing resource exhaustion/availability degradation.

This is a genuine authentication-bypass on the node's HTTP API surface, matching the in-scope "node API authentication bypass" impact category, since it's directly reachable and requires no session/token/role, in contrast to the correctly-gated `metricRoutes`.

## Likelihood Explanation
Likelihood is high wherever the node's HTTP API port is reachable by any party other than the trusted operator — a common deployment topology, since `/discovery`, `/plugins/...` share the same listener/port as the authenticated `/v2` API. No credentials or special network position are needed; a single unauthenticated GET/POST request triggers the flow. The precondition is that at least one LOOP plugin is registered via `app.GetLoopRegistry()`, which is standard for OCR2-based EVM/non-EVM job types.

## Recommendation
Wrap `loopRoutes` in the same authentication middleware used for `debugRoutes`/`metricRoutes` — e.g., mount it inside a group gated by `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateByToken, auth.AuthenticateBySession)`, and consider `auth.RequiresAdminRole` for the pprof/profile endpoints specifically — rather than passing the unauthenticated `api` group into `loopRoutes` in `NewRouter`. Add entries to `routesRolesMap` in `core/web/auth/auth_test.go` for `/discovery`, `/plugins/:name/metrics`, `/plugins/:name/debug/pprof/*`, and `/plugins/:name/debug/pprof/symbol` asserting 401/403 for unauthenticated/non-admin callers.

## Proof of Concept
Against a running node with at least one LOOP plugin registered:
```
curl -s http://NODE_HOST:6688/discovery
curl -s http://NODE_HOST:6688/plugins/<plugin-name>/metrics
curl -s http://NODE_HOST:6688/plugins/<plugin-name>/debug/pprof/goroutine?debug=2
curl -s http://NODE_HOST:6688/plugins/<plugin-name>/debug/pprof/profile?seconds=30
```
No `Authorization` header or session cookie is sent. On the current code, these return HTTP 200 with plugin discovery/metrics/pprof data (subject only to the plugin name existing in the registry), while the equivalent `/v2/debug/pprof/*` route correctly returns 401 without a valid session/token, per `metricRoutes`'s placement inside `authv2` [3](#0-2) . A Go integration test using `gin`'s test recorder against `NewRouter`'s output, sending unauthenticated requests to these four routes and asserting non-2xx, would concretely demonstrate the bypass.

func (l *LoopRegistryServer) pluginMetricHandler(gc *gin.Context) {
	pluginName := gc.Param("name")
	p, ok := l.registry.Get(pluginName)
	if !ok {
		gc.Data(http.StatusNotFound, "text/plain", fmt.Appendf(nil, "plugin %q does not exist", html.EscapeString(pluginName)))
		return
	}

	// unlike discovery, this endpoint is internal btw the node and plugin
	pluginURL := fmt.Sprintf("http://%s:%d/metrics", l.loopHostName, p.EnvCfg.PrometheusPort)
	req, err := http.NewRequestWithContext(gc.Request.Context(), http.MethodGet, pluginURL, nil)
	if err != nil {
		gc.Data(http.StatusInternalServerError, "text/plain", fmt.Appendf(nil, "error creating plugin metrics request: %s", err))
		return
	}
	res, err := l.promClient.Do(req)
	if err != nil {
		msg := "plugin metric handler failed to get plugin url " + html.EscapeString(pluginURL)
		l.logger.Errorw(msg, "err", err)
		gc.Data(http.StatusInternalServerError, "text/plain", fmt.Appendf(nil, "%s: %s", msg, err))
		return
	}
	defer res.Body.Close()
	b, err := io.ReadAll(res.Body)
	if err != nil {
		msg := fmt.Sprintf("error reading plugin %q metrics", html.EscapeString(pluginName))
		l.logger.Errorw(msg, "err", err)
		gc.Data(http.StatusInternalServerError, "text/plain", fmt.Appendf(nil, "%s: %s", msg, err))
		return
	}

	gc.Data(http.StatusOK, "text/plain", b)
}

func (l *LoopRegistryServer) pluginPPROFHandler(gc *gin.Context) {
	pluginName := gc.Param("name")
	p, ok := l.registry.Get(pluginName)
	if !ok {
		gc.Data(http.StatusNotFound, "text/plain", fmt.Appendf(nil, "plugin %q does not exist", html.EscapeString(pluginName)))
		return
	}

	// unlike discovery, this endpoint is internal btw the node and plugin
	pluginURL := fmt.Sprintf("http://%s:%d/debug/pprof/"+gc.Param("profile"), l.loopHostName, p.EnvCfg.PrometheusPort)
	urlVals, timeout := pprofURLVals(gc)
	if s := urlVals.Encode(); s != "" {
		pluginURL += "?" + s
	}
	l.logger.Infow("Forwarding plugin pprof request", "plugin", pluginName, "url", pluginURL)
	l.doRequest(gc, "GET", pluginURL, nil, timeout, pluginName)
}
