### Title
Unchecked ERC20 return value in `IntentGatewayV2.withdraw()`/`SweepDust` on Tron allows silent transfer failure and permanent freezing of escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`evm/tron/contracts/apps/IntentGatewayV2.sol` imports and elsewhere consistently uses `SafeERC20` (`using SafeERC20 for IERC20;` and `safeTransferFrom` throughout the fill/open paths), but the escrow-release path in `withdraw()` and the `SweepDust` handling in `onAccept()` instead perform a raw low-level call with the `transfer` selector and only check that the external call itself did not revert, never validating the ABI-decoded boolean return value. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
In `withdraw()`, both the per-token payout loop and the transaction-fee payout use:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [2](#0-1) 

`success` here only reflects whether the low-level call reverted, not what `transfer()` returned. A standards-compliant but non-strictly-behaving ERC20 (or a TRC20 token on Tron, which is what this file specifically targets) can return `false` on a failed transfer instead of reverting. In that case `success` is still `true` because the call itself completed without reverting, so the check passes even though no tokens were actually moved.

Despite this false "success", the function unconditionally decrements the escrow accounting immediately after:
```solidity
_orders[body.commitment][token] -= amount;
```
and marks the order as filled/refunded via `_filled[body.commitment] = beneficiary;` before the loop even begins. Because `withdraw()` is invoked from `onAccept()` for `RequestKind.RedeemEscrow`/`RequestKind.RefundEscrow` — a path reachable by any relayer that proves delivery of a cross-chain message — a token that returns `false` on failure causes the protocol to believe the beneficiary was paid while the escrowed balance is deducted and the order is marked filled, with no facility to retry or reclaim. The same unchecked-`success`-only pattern is repeated in the `SweepDust` branch of `onAccept()`. [4](#0-3) 

This directly matches the reported bug class (not validating the boolean return of `transfer`/not using `safeTransfer`), but the impact here is stronger than in the original report: it is not merely a revert-and-retry DoS, it is silent fund loss/permanent freezing because the escrow bookkeeping is updated regardless of whether the transfer actually succeeded, and there is no other code path to re-claim the un-transferred tokens for that commitment.

### Impact Explanation
Any token used with `IntentGatewayV2` on Tron that follows the "return false rather than revert" failure convention causes escrowed user or protocol funds to be permanently unrecoverable: the beneficiary never receives the tokens, yet the contract's internal accounting (`_orders`, `_filled`) treats the withdrawal as complete. This is a permanent freezing/loss-of-funds condition on escrowed assets, triggerable by ordinary relayer-driven message delivery with no privileged role required.

### Likelihood Explanation
The trigger requires only that one of the escrowed input tokens used in an order is a token that can return `false` instead of reverting on transfer failure (e.g., due to insufficient balance from fee-on-transfer/blacklist/pausable mechanics common on TRC20/ERC20-like tokens), combined with a relayer delivering the `RedeemEscrow`/`RefundEscrow` message — both of which are routine, permissionless occurrences in normal protocol operation, not requiring any malicious privileged actor.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and in the `SweepDust` branch of `onAccept()` with `SafeERC20.safeTransfer`, which is already imported and used elsewhere in this file (e.g. `safeTransferFrom` in the escrow-input path), so that both revert-based and false-return failure modes are handled correctly.

### Proof of Concept
1. Deploy an ERC20/TRC20-style token whose `transfer()` implementation returns `false` (rather than reverting) when the sender's balance is insufficient or the recipient is blacklisted (a common pattern for compliance-oriented stablecoins).
2. Create and fill an order on the source chain escrowing this token via `IntentGatewayV2`, so `_orders[commitment][token]` records the escrowed amount.
3. Arrange for the contract's token balance to be insufficient at redemption time (e.g., through fee-on-transfer skimming, a blacklist added by the token issuer after escrow, or any other in-token business logic causing `transfer` to return `false`) and have a relayer deliver the `RedeemEscrow` message, invoking `onAccept` → `withdraw`.
4. Observe that `token.call(...)` succeeds (returns `success = true`) because the low-level call did not revert, even though the token's internal `transfer` logic returned `false` and moved no tokens; `_orders[commitment][token]` is decremented and `_filled[commitment]` is set, permanently marking the order as paid out while the beneficiary received nothing and has no path to reclaim the escrowed tokens.
