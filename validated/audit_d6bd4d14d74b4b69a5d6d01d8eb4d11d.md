### Title
Webhook shop-domain header is not covered by HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature validated by `Utils::HmacValidator` covers the body's bytes but not the `shop-domain` header. `Registry.process` trusts `request.shop` (read straight from the header) and forwards it, unauthenticated, into the app's webhook handler.

### Finding Description
`HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, verifiable_query.to_signable_string)` and compares it to the `hmac` value. [1](#0-0) 
For webhook requests, `to_signable_string` is defined as just `@raw_body`, while `shop` is read independently from the `shop-domain` header, entirely outside the signed material. [2](#0-1) 
`Registry.process` validates the HMAC of the body, then immediately uses `request.shop` — never cross-checked against anything derived from the signature — to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

Because Shopify apps share a single `api_secret_key` across all installed shops (it's not per-tenant), any legitimate merchant that has installed the app can legitimately receive a validly-signed webhook (body + HMAC) for their own store. That same `(raw_body, hmac)` pair remains a "valid" signature for the app's endpoint regardless of what `shop-domain` header accompanies it, because the header plays no role in signature computation. A malicious merchant can therefore replay their own valid body/HMAC pair while substituting a different shop's `x-shopify-shop-domain` (or `shopify-shop-domain`) header value. `Registry.process` will pass `Utils::HmacValidator.validate`, and the handler will receive `WebhookMetadata` claiming the data belongs to the victim shop.

This breaks the identity binding: **shop authenticated (via the request's validated HMAC) ≠ shop attributed to the resulting data** (`request.shop`, an unauthenticated header). The library's `HmacValidator` only proves "this body was generated by someone holding the app secret" — it says nothing about which of the app's many tenants it applies to.

### Impact Explanation
This is a cross-tenant integrity attack: a merchant who is an unprivileged (from the perspective of other tenants) but legitimate app installer can forge webhook deliveries that the host application will attribute to a different merchant's shop. Depending on how the host app's `WebhookHandler` implementations use `data.shop` (e.g., to look up which tenant's database row to update, or to trigger `app/uninstalled`, `customers/redact`, `shop/redact` type side effects), this can result in cross-tenant data corruption, spoofed lifecycle events for another shop, or forced data-deletion/redaction actions against a victim tenant — all without needing the victim's credentials or the app's `client_secret`.

### Likelihood Explanation
Exploitability requires only: (1) being a legitimate installer of the target Shopify app (an "unprivileged" position relative to other tenants of the same app) and (2) capturing one's own valid webhook delivery (body + `x-shopify-hmac-sha256`), which is trivially observable by any merchant who can inspect their own app's traffic or webhook endpoint logs, or who runs their own reachable relay/proxy. No knowledge of `api_secret_key` or another shop's access token is needed. The replay itself is a simple HTTP POST with a substituted `shop-domain` header.

### Recommendation
Bind the declared shop to the signed payload, or otherwise re-authenticate the shop independently of the client-supplied header — e.g., look up the shop from the store's own registered session/access-token instead of trusting the header value, or require the host application to cross-check `webhook_id`/topic against a per-shop webhook registration record before processing. At minimum, document prominently that `WebhookMetadata#shop` is not cryptographically bound and must not be used as the sole tenant-selection key without additional verification (such as confirming the shop has an active, matching session in the app's own session store before acting on the payload).

### Proof of Concept
1. App installs on `shop-a.myshopify.com`. Shopify sends a legitimate webhook to the app's endpoint:
   - Headers: `x-shopify-topic: app/uninstalled`, `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body B computed with the app's shared api_secret_key>`
   - Body: `B`
2. The merchant operating `shop-a` (an unprivileged actor with respect to other tenants) captures this `(B, hmac)` pair from their own inbound traffic.
3. The merchant crafts a new POST to the same app endpoint, reusing body `B` and the same `hmac`, but sets `x-shopify-shop-domain: shop-b.myshopify.com` (a victim shop also using the app).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(api_secret_key, B) == hmac` — true, `shop` header is irrelevant to this check: [4](#0-3) 
5. Validation passes; `handler.handle` is invoked with `WebhookMetadata.new(..., shop: "shop-b.myshopify.com", ...)`, so the app processes an `app/uninstalled` (or any other topic) event as if it originated from `shop-b`, even though `shop-b` never sent it. [5](#0-4)
