### Title
Wrapped HFT lock accounting trusts requested amount instead of actual tokens received, enabling under-collateralized cross-chain mint/unlock for fee-on-transfer or deflationary tokens - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol)

### Summary
`WrappedHyperFungibleToken.send()` locks the underlying ERC20 via `safeTransferFrom(msg.sender, address(this), params.amount)` and then dispatches a cross-chain message that always encodes the full `params.amount`, regardless of how much the contract actually received [1](#0-0) .

### Finding Description
For any underlying ERC20 that charges a transfer fee, rebases, or otherwise delivers less than the nominal `amount` on `transferFrom` (fee-on-transfer, deflationary, or rebasing tokens), the wrapper will:
1. Lock less than `params.amount` in actual token balance.
2. Still build and dispatch a `Message` with `amount: params.amount` (the full nominal amount) via `_buildDispatchPost` [3](#0-2) .

On the destination side (a peer `WrappedHyperFungibleToken` or `HyperFungibleToken` deployment), `onAccept` mints/unlocks exactly `message.amount` to the beneficiary [4](#0-3) , i.e. the full nominal amount, which now exceeds what was actually escrowed on the source chain. Over repeated sends this creates a structural shortfall: the wrapper's real token balance backing outstanding cross-chain liabilities becomes permanently less than the sum of unlock/refund obligations it has committed to, so a later legitimate unlock or timeout-refund can fail or, if the peer is a lock/unlock pair, effectively siphon tokens deposited by other users. This is the direct analog to the BetaProvider report: an untrusted assumption that a `transferFrom` delivers exactly the requested amount, but here it corrupts a cross-chain balance commitment rather than merely reverting.

By contrast, `IntentGatewayV2.placeOrder` was specifically hardened against this exact issue: it snapshots balances before and after `safeTransferFrom`/sweep calls and mutates `order.inputs[i].amount` to the actually-received amount before computing the commitment and escrow [5](#0-4) , and this behavior is explicitly tested for fee-on-transfer tokens [6](#0-5) . `WrappedHyperFungibleToken` has no equivalent check.

### Impact Explanation
This is a fund-integrity issue for the wrapper's escrow: the destination chain will unlock/mint more of the underlying (or trigger over-large refunds on timeout) than was actually locked on the source chain, permanently under-collateralizing the wrapper and threatening the funds of other users who legitimately locked tokens in the same contract. Because `WrappedHyperFungibleToken` is designed as a generic, owner-deployable wrapper for "existing ERC20 tokens" (per its own documentation, which does not restrict callers to a known safe-token allowlist), it is reasonably foreseeable that a fee-on-transfer or deflationary token could be configured as `_underlying`.

### Likelihood Explanation
Likelihood depends on whether the deploying owner configures the wrapper with a fee-on-transfer/deflationary/rebasing ERC20 as `_underlying`. Since `configure()` places no restriction on token type [7](#0-6) , and the contract is a generic wrapper meant to be reused for arbitrary ERC20s, this is a plausible deployment scenario, especially since the codebase elsewhere (IntentGatewayV2) explicitly anticipates and tests fee-on-transfer tokens as a first-class case.

### Recommendation
In `send()`, measure the underlying balance of `address(this)` before and after `safeTransferFrom`, and use the delta (actual received amount) both for the amount encoded in the dispatched `Message` and in the `Sent` event, mirroring the pattern already implemented in `IntentGatewayV2.placeOrder` (see `evm/src/apps/IntentGatewayV2.sol:291-329`). Apply the identical fix to `WrappedHyperFungibleTokenUpgradeable.sol` and any Tron/L2 variants of this contract.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` with `_underlying` set to a token that takes a 1% fee on transfer (e.g., the `FeeOnTransferToken` test helper already present in the repo's test suite [8](#0-7) ).
2. User calls `send({ amount: 1000e18, ... })`. `safeTransferFrom` pulls 1000e18 from the user but the wrapper only receives 990e18 due to the fee.
3. `_buildDispatchPost` still encodes `amount: 1000e18` in the `Message` body, and the commitment/dispatch reflects 1000e18 [1](#0-0) .
4. On the destination chain, `onAccept` unlocks/mints 1000e18 to the beneficiary [4](#0-3) , a 10e18 (1%) surplus versus what was actually escrowed on the source chain — repeatable per transaction, draining the wrapper's real backing over time.

    function _buildDispatchPost(HyperFungibleToken.SendParams calldata params) internal view returns (DispatchPost memory) {
        bytes memory dest = _supportedChains[params.dest];
        if (dest.length == 0) revert UnsupportedChain();

        bytes memory body = abi.encode(HyperFungibleToken.Message({
            from: abi.encodePacked(msg.sender),
            to: params.to,
            amount: params.amount,
            data: params.data
        }));

        return DispatchPost({
            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,
            payer: msg.sender
        });

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }

contract FeeOnTransferToken {
    string public name = "FeeOnTransferToken";
    string public symbol = "FOT";
    uint8 public decimals = 18;
    uint256 public totalSupply;
    uint256 public feeBps;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    constructor(uint256 _feeBps) {
        feeBps = _feeBps;
    }

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        totalSupply += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        return _transfer(msg.sender, to, amount);
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
        // fee is burned
        totalSupply -= fee;
        return true;
    }
}
