### Title
Division-by-zero panic in `calc_take_pnl` when decimal-normalized pool reserves round to zero - (File: `program/src/processor.rs`, `program/src/math.rs`)

### Summary
`Calculator::normalize_decimal_v2` performs an integer-division decimal conversion that silently rounds small raw token amounts down to `0`. `Processor::calc_take_pnl`, which is invoked unconditionally from `process_deposit`, `process_swap_base_in`/`_out`, `process_swap_base_in_v2`/`_out_v2`, and `process_withdraw` (unless the pool is in `WithdrawOnly` status), then uses one of these normalized values as a divisor without checking it for zero, causing an unrecoverable panic (`.unwrap()` on `None` from `checked_div`).

### Finding Description
`normalize_decimal_v2` converts a raw vault amount into "system decimal" units: [1](#0-0) 
Because this is plain integer division, whenever `total_pc_without_take_pnl` (or `total_coin_without_take_pnl`) is small relative to `10^native_decimal / sys_decimal_value`, the normalized value `x1`/`y1` is truncated to exactly `0`, even though the raw pool balance is non-zero.

`total_pc_without_take_pnl`/`total_coin_without_take_pnl` are derived directly from live vault balances minus the pending `need_take_pnl_*` amounts: [2](#0-1) 

These `x1`/`y1` values are then fed into `Processor::calc_take_pnl`, which is called from every swap/deposit path: [3](#0-2) 
When the branch condition is satisfied, `calc_x_power` computes `x2_power` and then the code divides by `x1` unconditionally: [4](#0-3) 
`checked_div` returns `None` on division by zero; the subsequent `.unwrap()` panics the whole transaction instead of returning a handled `ProgramError`.

An unprivileged swapper can reach this state without any privileged action. A `swap_base_out`/`swap_base_in` call is only prevented from draining the pool down to *exactly* zero remaining tokens on one side: [5](#0-4) 
An attacker can therefore submit a swap that leaves only a residual `1` (or a few) raw units of `total_pc_without_take_pnl` (or `total_coin_without_take_pnl`) in the pool. If the mint's decimals are large relative to `amm.sys_decimal_value` (e.g. a 9-decimal token with the common `sys_decimal_value = 10^6`), that residual normalizes to `0` via `normalize_decimal_v2`, and the very next call into `calc_take_pnl` (via `process_deposit`, `process_swap_base_in[_v2]`, `process_swap_base_out[_v2]`, or `process_withdraw` while not in `WithdrawOnly`) panics on the zero-division.

This mirrors CVE-2021-32282's bug class: a NULL/undefined dereference caused by a missing check before consuming a value, reachable from ordinary user-controlled input, producing an unhandled crash (panic) rather than a graceful error.

### Impact Explanation
Once the residual reserve is driven into the rounding-to-zero range, every subsequent `Deposit`, `SwapBaseIn`/`SwapBaseOut` (v1 and v2) instruction against that pool will panic and abort, because `calc_take_pnl` is invoked unconditionally in those code paths. `Withdraw` is only exempted from the crash if the pool's `status` has separately been switched to `WithdrawOnly` by an admin (`process_set_params`), which an ordinary user cannot do. Consequently, an unprivileged attacker can permanently freeze normal trading/liquidity operations on the pool (denial of service / freezing of LP and swap functionality) until an administrator intervenes, satisfying the "permanent freezing of user or LP funds" impact bar.

### Likelihood Explanation
Reaching the residual-balance state requires only a single or a few ordinary `SwapBaseIn`/`SwapBaseOut` transactions with attacker-chosen `amount_in`/`amount_out`, no special privileges, no leaked keys, and no validator collusion — well within the reach of any swapper. The precise likelihood of hitting the zero-normalization threshold depends on the specific mint's decimals and `sys_decimal_value`, but for pools involving standard 9-decimal SPL tokens paired with `sys_decimal_value = 10^6` (a common Raydium configuration), the "rounds to zero" band covers up to 999 raw units, which is trivially reachable by design (a swap can always be sized to leave `1` unit remaining).

### Recommendation
- In `Calculator::normalize_decimal_v2`/`normalize_decimal`, do not silently truncate a non-zero raw amount to `0`; either round up when the raw remainder would otherwise be lost, or explicitly propagate an error/sentinel when the normalized quantity underflows to zero.
- In `Processor::calc_take_pnl` (and `Calculator::calc_x_power`), replace the unchecked `.checked_div(x1).unwrap()` pattern with a proper zero-check that returns `AmmError::CalcPnlError` (or similar) instead of panicking, so a degenerate reserve state fails gracefully rather than permanently DoS'ing the instruction.

### Proof of Concept
1. Create/target a pool where the pc (or coin) mint has native decimals higher than `log10(amm.sys_decimal_value)` (e.g. 9-decimal pc mint with `sys_decimal_value = 1_000_000`).
2. As any user, submit a `SwapBaseOut` (or `SwapBaseIn`) transaction sized so that `swap_amount_out = total_pc_without_take_pnl - 1` (respecting the existing `swap_amount_out >= total_pc_without_take_pnl` guard at `program/src/processor.rs:2404`), draining the pc side of the pool down to `1` raw unit.
3. Submit any subsequent `Deposit`, `SwapBaseIn`, or `SwapBaseOut` instruction. `calc_total_without_take_pnl_no_orderbook` returns `total_pc_without_take_pnl = 1`; `normalize_decimal_v2(1, 9, 1_000_000)` computes `1 * 1_000_000 / 10^9 = 0`, so `x1 = 0`.
4. `Processor::calc_take_pnl` is invoked with `x1 = 0`; if the pnl-branch condition (`pool_pc*pool_coin >= calc_pc*calc_coin`) is met, `y2 = x2.checked_mul(y1).unwrap().checked_div(x1).unwrap()` divides by zero and panics, aborting the transaction and leaving the pool permanently stuck at the degenerate reserve level for all future callers of that path.
