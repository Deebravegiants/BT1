## Finding

### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, while the `shop`, `topic`, `api_version`, and `webhook_id` values are read directly from unauthenticated HTTP headers. `Registry.process` accepts any request whose body matches a valid HMAC and then dispatches the handler using the header-derived `shop`, without any cryptographic binding between the two. Since Shopify signs webhooks with a single app-wide `api_secret_key` (not a per-shop secret), any shop that has installed the app can capture one of its own genuine webhooks and replay the identical body/HMAC pair while substituting a victim shop's domain in the `X-Shopify-Shop-Domain` header, causing the app to process attacker-controlled data under another tenant's identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from HTTP headers, which are not part of the signed payload: [2](#0-1) 

`Registry.process` validates only the HMAC of the request (i.e., the body) and then trusts `request.shop` to build the metadata passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature over `to_signable_string` (the body) using the app's single `Context.api_secret_key`, which is the same secret for every shop that installs the app: [4](#0-3) 

Test fixtures confirm the HMAC is computed only over the JSON body, independent of shop-identifying headers: [5](#0-4) 

The broken identity binding is:
`hmac_verified(raw_body, api_secret_key) == true` should imply `shop header == shop that produced this body`, but instead `shop` is accepted from an unsigned header while only `raw_body` is authenticated. Because the signing secret (`api_secret_key`) is shared across all shops that install the app (not shop-specific), any installed shop can generate a validly-signed body/HMAC pair and pair it with an arbitrary victim `shop-domain` header.

### Impact Explanation
This breaks tenant isolation: an unprivileged party who has merely installed the app on their own shop (no special access, no leaked credentials) can forge webhook deliveries that the app attributes to a different, victim shop. Depending on what the app's webhook handlers do with `WebhookMetadata#shop` (e.g., updating billing/subscription state, order records, product data, or triggering shop-scoped side effects), this enables cross-tenant data injection/corruption — matching the "Critical: cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for apps that use this gem's `Webhooks::Registry`/`Request` as documented: the attacker needs only to install the app (a normal, permitted action for any Shopify merchant) to receive at least one genuine webhook with a valid HMAC, then replay the exact body while changing the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header value. No secret, token, or privileged access is required beyond ordinary app installation.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed material, or otherwise cryptographically tie the header-derived shop to the verified body — e.g., require the consuming application to cross-check `request.shop` against a shop it already has a stored, verified session/access token for before processing, and document this requirement prominently. At minimum, the library should warn integrators that `request.shop`/`request.topic` are not authenticated by the HMAC check and must not be trusted for tenant attribution without additional verification against known installed shops.

### Proof of Concept
1. App merchant "attacker.myshopify.com" installs the target app and triggers a benign webhook (e.g., `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header sent by Shopify.
2. Attacker resends the exact same body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `HmacValidator.validate` in [6](#0-5)  passes because it only checks the (unchanged) body against the (unchanged) HMAC, using the app-wide secret.
4. `Registry.process` in [3](#0-2)  invokes the app's handler with `shop: "victim.myshopify.com"`, causing the app to process attacker-supplied data as if it came from the victim shop.

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
