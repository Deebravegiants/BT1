Based on the codebase, there is a valid analog: the Shopify webhook HMAC only covers the raw request body, while critical identity-binding fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) are read directly from unauthenticated HTTP headers and passed straight to the app's handler.

### Title
Webhook shop/topic identity spoofing via HMAC that only covers the request body, not headers - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but its `to_signable_string` returns only `@raw_body`, excluding the `shop-domain`, `topic`, `webhook-id`, and `api-version` header values from the signed material. [1](#0-0) 
`Utils::HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string`, so it verifies only the body bytes and never binds the header-derived identity fields to the signature. [2](#0-1) 
`Webhooks::Registry.process` accepts the request once HMAC validation succeeds and then forwards `request.shop` and `request.topic` — both taken straight from unauthenticated headers — to the app-provided handler as trusted identity metadata. [3](#0-2) 

### Finding Description
The binding that should hold is: `bytes authenticated by HMAC == bytes used to identify the tenant (shop) and event (topic)`. Here that equality is broken: the HMAC covers only `raw_body`, while `shop`, `topic`, `webhook_id`, and `api_version` come from `shopify-*` / `x-shopify-*` headers that are never included in `to_signable_string`. [4](#0-3) 
Because `OpenSSL::HMAC.hexdigest` is computed only over the body, an attacker who has ever legitimately received one valid `(raw_body, hmac)` pair from Shopify — trivially obtainable by installing the app on their own free/dev store and capturing one webhook delivery — can replay that exact `raw_body`/`hmac` pair to the app's public webhook endpoint while substituting the `shop-domain` header for a victim shop and/or the `topic` header for a different registered topic. `HmacValidator.validate` will still return `true` because it only re-derives the HMAC from `raw_body`, which is unchanged. [5](#0-4) 
`Registry.process` then dispatches to the topic handler using the attacker-forged `shop` and `topic`, without any secondary check that the shop actually owns/received that webhook. [3](#0-2) 

### Impact Explanation
Because host applications typically use `WebhookMetadata#shop` to select which tenant's records to read or write (e.g., in the reference `shopify_app` pattern), this is a cross-tenant boundary violation — an unprivileged attacker can cause the app to act on a victim shop's identity using content the attacker fully controls (their own captured webhook body), which is well documented as a Critical class of finding (cross-tenant access) in this assessment's rules.

### Likelihood Explanation
The prerequisite is trivial for any unprivileged internet user: install the target app on their own shop (or use any shop that already has the app installed) to legitimately receive one valid `(raw_body, hmac)` pair for any topic, then POST that unchanged body/HMAC to the app's public webhook endpoint with modified `shopify-shop-domain`/`shopify-topic` headers. No secret, access token, or privileged access is required.

### Recommendation
Include the header-derived identity fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the request before dispatching to handlers, so `Utils::HmacValidator.validate` authenticates the full set of fields that `Registry.process` and downstream handlers rely on for tenant/topic identification.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger any webhook topic (e.g. `customers/create`) and capture the raw POST body `B` and header `x-shopify-hmac-sha256: H` sent to the app's webhook endpoint.
2. Replay: `POST /webhooks` with body `B` unchanged, headers:
   - `x-shopify-hmac-sha256: H` (unchanged)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - `x-shopify-topic: customers/create` (unchanged or forged to another registered topic)
3. `ShopifyAPI::Webhooks::Request.new` parses these headers; `Utils::HmacValidator.validate(request)` succeeds because `to_signable_string` returns only `B`, matching `H`. [6](#0-5) 
4. `Registry.process` looks up the handler for `customers/create` and invokes it with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: "customers/create", body: parsed_body_of_B, ...)`, causing the app to process attacker-controlled data attributed to the victim shop. [7](#0-6)
