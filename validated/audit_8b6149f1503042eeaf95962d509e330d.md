### Title
Missing `FeeExceedsAmountError` guard in `createWithdrawalIntents` allows negative `actualAmount` to be signed into `ft_withdraw`/`mt_withdraw` intents - (File: packages/intents-sdk/src/sdk.ts)

### Summary
`IntentsSDK.createWithdrawalIntents` (sdk.ts:334-372) recomputes `actualAmount = withdrawalParams.amount - feeEstimation.amount` for `feeInclusive` withdrawals but, unlike `_estimateWithdrawalFee` (sdk.ts:408-453), never checks that `amount > fee.amount` before using it. A caller who supplies any `feeEstimation` object (not necessarily one returned by `estimateWithdrawalFee`) with `feeEstimation.amount >= withdrawalParams.amount` causes `actualAmount` to underflow to zero/negative before it is fed into `bridge.validateWithdrawal` and `bridge.createWithdrawalIntents`.

### Finding Description
Equality claimed broken: `sum(debits in produced intents) == withdrawalParams.amount` (fee-inclusive accounting).

In `_estimateWithdrawalFee`:
```
if (args.withdrawalParams.feeInclusive) {
  if (args.withdrawalParams.amount <= fee.amount) {
    throw new FeeExceedsAmountError(fee, args.withdrawalParams.amount);
  }
}
const actualAmount = ... amount - fee.amount ...
``` [1](#0-0) 

In `createWithdrawalIntents` the identical subtraction is performed but the `FeeExceedsAmountError` check is absent:
```
const actualAmount = args.withdrawalParams.feeInclusive
  ? args.withdrawalParams.amount - args.feeEstimation.amount
  : args.withdrawalParams.amount;

await bridge.validateWithdrawal({ ... amount: actualAmount ... });
return bridge.createWithdrawalIntents({ withdrawalParams: { ...args.withdrawalParams, amount: actualAmount }, feeEstimation: args.feeEstimation, ... });
``` [2](#0-1) 

`createWithdrawalIntents` is a public method that takes `feeEstimation: FeeEstimation` as a plain, unauthenticated data parameter — there is no cryptographic or structural binding tying it to a prior `estimateWithdrawalFee` call for the same `withdrawalParams`. Nothing in `sdk.ts` prevents an integrator (or code path controlled by data the integrator forwards) from calling `createWithdrawalIntents` directly with a `feeEstimation.amount` that is equal to or greater than `withdrawalParams.amount` — e.g., a quote/fee estimate copied from a different, larger route — bypassing the `FeeExceedsAmountError` throw that exists only in the sibling method.

Whether this reaches a genuinely negative signed value inside the intent, or is instead caught downstream by `bridge.validateWithdrawal`'s own minimum/positive-amount checks, could not be fully confirmed: I was only able to confirm the guard asymmetry inside `sdk.ts` itself; I was not able to fully inspect every bridge's `validateWithdrawal` implementation (poa-bridge, omni-bridge, hot-bridge, direct-bridge, aurora-engine-bridge, intents-bridge) within the available tool budget to determine definitively whether all of them independently reject `amount <= 0n` before intent construction. This is the key open question for confirming end-to-end exploitability.

### Impact Explanation
If any bridge's `validateWithdrawal` does not itself reject a zero/negative `amount` (which is plausible since that check was apparently centralized in `_estimateWithdrawalFee` rather than duplicated per-bridge), a caller-supplied oversized `feeEstimation.amount` would flow into `bridge.createWithdrawalIntents` as a negative `actualAmount`, and get serialized into the produced `ft_withdraw`/`mt_withdraw` intent. This would break the fee-inclusive equality (`debits == withdrawalParams.amount`) and could result in either a malformed intent that is rejected on-chain after signing (stranding the flow) or, in the worst case, funds movement inconsistent with what the caller displayed/authorized — matching the "fee error draining a material share of the amount" Critical category.

### Likelihood Explanation
The precondition is narrow: the caller (an SDK integrator or code that forwards a stale/foreign `feeEstimation`) must invoke `createWithdrawalIntents` directly with a `feeEstimation.amount` it did not obtain from a matching `estimateWithdrawalFee` call for the same `withdrawalParams`/route. Since `feeEstimation` is a plain object parameter with no route/asset binding enforced by `sdk.ts`, this is inexpensive and repeatable per call. However, real-world exploitability hinges on whether the bridge-level `validateWithdrawal` implementations independently reject non-positive amounts — this could not be conclusively verified in this session.

### Recommendation
Add the same `FeeExceedsAmountError` guard used in `_estimateWithdrawalFee` to `createWithdrawalIntents` before computing `actualAmount`:
```ts
if (args.withdrawalParams.feeInclusive && args.withdrawalParams.amount <= args.feeEstimation.amount) {
  throw new FeeExceedsAmountError(args.feeEstimation, args.withdrawalParams.amount);
}
```
Additionally, consider binding `feeEstimation` to the specific `withdrawalParams` (e.g., via a hash/signature or by requiring `estimateWithdrawalFee` to return an opaque token consumed by `createWithdrawalIntents`) so a fee estimate for one route/asset cannot be replayed against another.

### Proof of Concept
```ts
// vitest, mocks only HTTP layer used by bridge.supports/validateWithdrawal
it("rejects feeEstimation.amount >= withdrawalParams.amount without calling estimateWithdrawalFee", async () => {
  const foreignFee: FeeEstimation = { amount: 1_000_000n, ... }; // taken from a different asset/route's quote
  const withdrawalParams: WithdrawalParams = {
    amount: 500_000n, // smaller than the foreign fee
    feeInclusive: true,
    assetId: "...",
    destinationAddress: "...",
    routeConfig: { ... },
  };

  await expect(
    sdk.createWithdrawalIntents({ withdrawalParams, feeEstimation: foreignFee })
  ).rejects.toThrow(FeeExceedsAmountError); // currently FAILS: no such throw exists in createWithdrawalIntents

  // Assert both sides of the claimed equality diverge if the call is allowed to proceed:
  // LHS: sum of debits in intents produced == withdrawalParams.amount (500_000n)
  // RHS (observed): actualAmount = 500_000n - 1_000_000n = -500_000n serialized into ft_withdraw.amount
});
```
