### Title
Missing check on actual tokens received in `WrappedHyperFungibleToken.send()` / `WrappedHyperFungibleTokenUpgradeable.send()` when locking underlying ERC20 - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.send()` (and its upgradeable twin) locks the underlying ERC20 via `safeTransferFrom` and then dispatches a cross-chain message committing to `params.amount` as the locked balance, without verifying that the contract actually received `params.amount` of tokens. If the underlying token is fee-on-transfer, deflationary, or otherwise rebasing/non-standard, the contract will hold less than the committed amount while still promising `params.amount` to be minted/unlocked on the destination chain, creating an unbacked liability against the escrow.

### Finding Description
In `send()`:
```solidity
function send(HyperFungibleToken.SendParams calldata params) external payable whenNotPaused {
    uint256 msgValue = msg.value;
    if (_isWeth && msgValue >= params.amount) {
        msgValue = msgValue - params.amount;
        IWETH(_underlying).deposit{value: params.amount}();
    } else {
        IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
    }

    DispatchPost memory request = _buildDispatchPost(params);
    ...
}
``` [1](#0-0) 

`_buildDispatchPost` encodes the cross-chain `Message` using `params.amount` verbatim, not the actual balance delta observed after the transfer: [2](#0-1) 

This is the same bug class described in the external report for `LSSVMPairERC20._validateTokenInput()`: the direct-transfer branch (`safeTransferFrom`) is trusted blindly, with no `balanceOf` before/after check, unlike the router branch in that codebase's analog. Notably, this exact codebase already recognizes and defends against this class of bug elsewhere: `IntentGatewayV2.placeOrder()` explicitly snapshots `balanceOf` before and after `safeTransferFrom` and uses the *actual received* amount (`order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;`) to build the commitment/escrow, precisely to protect against fee-on-transfer tokens: [3](#0-2) 

`WrappedHyperFungibleToken.send()` and `WrappedHyperFungibleTokenUpgradeable.send()` do not apply this same protection, so any home-chain deployment of the wrapper over a non-standard ERC20 (fee-on-transfer, deflationary, rebasing) will commit and dispatch a `Message.amount` larger than what was actually locked in the contract.

On the remote-chain side, `HyperFungibleToken.onAccept()` mints `message.amount` unconditionally: [4](#0-3) 

and when tokens are sent back to the home chain, `WrappedHyperFungibleToken.onAccept()` releases `message.amount` of the underlying via `safeTransfer`: [5](#0-4) 

Since minted supply on remote chains is always assumed backed 1:1 by the home-chain escrow (per the contract's own documented invariant, e.g. `BridgeToken.sol`'s comment "the supply of this token is always backed by the pallet's escrow account"), any shortfall introduced at `send()` breaks this invariant permanently.

### Impact Explanation
Each `send()` call on a deflationary/fee-on-transfer underlying causes the wrapper's actual escrowed balance to fall short of the sum of all committed/minted amounts across destination chains. Because remote-chain contracts mint the full `message.amount` unconditionally, total remote-side minted supply becomes unbacked by real collateral. When holders later attempt to bridge back and unlock/withdraw the underlying via `onAccept`, the home-chain contract's underlying balance can be insufficient to fully honor all outstanding claims, leading to some users being permanently unable to redeem their share (freezing of funds) — a direct violation of the token's core custody guarantee. This is a Medium-severity risk gated on the token deployer choosing a non-standard ERC20 as the underlying, mirroring the acknowledged risk profile of the referenced Sudoswap finding.

### Likelihood Explanation
Exploitability is deterministic once a `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` instance is deployed over a fee-on-transfer, deflationary, or rebasing ERC20 — every `send()` call reachable by any unprivileged user silently under-collateralizes the bridge with no code path resisting it. The codebase itself demonstrates awareness of this exact bug class (the balance-diff pattern implemented in `IntentGatewayV2.placeOrder()` and covered by dedicated `FeeOnTransferToken` tests), but the fix was not propagated to the `WrappedHyperFungibleToken` family, indicating an inconsistent/incomplete mitigation rather than a deliberately accepted risk.

### Recommendation
In `send()`, snapshot `IERC20(_underlying).balanceOf(address(this))` before and after `safeTransferFrom`, and use the actual delta (not `params.amount`) both for escrow accounting and for the `Message.amount` field encoded in the dispatched request — mirroring the pattern already used in `IntentGatewayV2.placeOrder()`. Apply the same fix to `WrappedHyperFungibleTokenUpgradeable.send()`.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` with `_underlying` set to a fee-on-transfer ERC20 that takes, e.g., a 1% fee on `transferFrom` (as modeled by the `FeeOnTransferToken` test helper used in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`).
2. User calls `send({ amount: 1000e18, ... })`. `safeTransferFrom` moves only 990e18 into the contract (1% fee burned/redirected), but `_buildDispatchPost` encodes `Message.amount = 1000e18` and dispatches the ISMP POST. [1](#0-0) 
3. On the destination chain, `HyperFungibleToken.onAccept()` mints the full 1000e18 to the beneficiary — 10e18 more than what is actually escrowed on the home chain. [4](#0-3) 
4. Repeating this across multiple sends accumulates an unbacked balance; eventually a user bridging back cannot be paid out in full by `WrappedHyperFungibleToken.onAccept()`'s `safeTransfer`, reverting or leaving other holders unable to redeem — funds are permanently frozen for the shortfall amount.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }
