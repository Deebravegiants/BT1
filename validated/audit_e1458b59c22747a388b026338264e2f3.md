### Title
Webhook shop/topic identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates the webhook HMAC over the raw JSON body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values that `ShopifyAPI::Webhooks::Registry.process` hands to the app's `WebhookHandler` are read straight from unauthenticated HTTP headers. Any caller who can produce one valid `(body, hmac)` pair (e.g. by receiving a real webhook for their own store) can replay that exact pair to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header, and the gem will accept it and hand the attacker's body to the handler tagged as belonging to the victim shop.

### Finding Description
`Request#hmac` reads the signature from the header: [1](#0-0) 

but `to_signable_string`, the value that is actually signed/verified, is only the raw body: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled directly from attacker-controllable headers, entirely outside the signed data: [3](#0-2) 

`HmacValidator.validate` only checks `computed_signature == received_signature` against `verifiable_query.to_signable_string` (the raw body): [4](#0-3) 

`Registry.process` uses this single check as the sole gate before trusting `request.shop`/`request.topic` and forwarding them to the handler as authoritative identity fields: [5](#0-4) 

The gem's own documentation instructs apps to treat `data.shop` as the trusted shop identifier for the webhook, with no caveat that it is unauthenticated: [6](#0-5) 

The broken identity binding is:
```
verified: HMAC(api_secret_key, raw_body) == received_hmac
assumed:  shop_header == shop_that_actually_generated(raw_body)
```
These two are independent. The HMAC proves the body bytes were signed by someone holding `api_secret_key` (i.e., Shopify, for *some* webhook event), but it proves nothing about which shop that event belongs to, because `shop` never enters `to_signable_string`.

### Impact Explanation
An unprivileged internet user who legitimately installs the target app on their own (attacker-controlled) store will receive genuine webhooks with a valid `(body, hmac)` pair for their own shop. They can then POST that exact `body` + `hmac` header directly to the app's public webhook endpoint while setting `shopify-shop-domain` (or `x-shopify-shop-domain`) to an arbitrary victim shop domain. `Registry.process` will pass HMAC validation (since it only checks the body) and invoke the app's handler with `WebhookMetadata#shop` set to the victim's domain and `body` set to attacker-chosen content (e.g., a crafted order/product payload created on the attacker's own store). Any app that uses `data.shop` to key data writes, trigger tenant-scoped side effects, or select which merchant's records to update will perform those actions against the victim tenant using attacker-supplied data — a cross-tenant data/action injection facilitated entirely through this gem's documented webhook API.

### Likelihood Explanation
Likelihood is realistic but not trivial: the attacker needs at least one genuine `(body, hmac)` pair, which they can always obtain by installing the app on a store they control (an unprivileged action) and capturing any webhook Shopify sends them. From there, forging the header is a simple direct HTTP request to the app's public callback endpoint — no secret material or privileged access is required.

### Recommendation
- Bind the shop (and ideally topic/webhook id) into the signed material, or otherwise cryptographically tie the header-provided `shop` to the specific webhook delivery, rather than trusting `shopify-shop-domain` unconditionally.
- At minimum, update `Webhooks::Request`/`Registry.process` and the accompanying documentation to make explicit that `shop`, `topic`, `webhook_id`, and `api_version` are **not** covered by the HMAC and must not be used by host apps as an authorization/tenant boundary without independent verification (e.g., cross-checking against the shop's registered webhook subscriptions or session storage).
- Consider exposing a method that also validates the `topic`/`webhook_id` are internally consistent with an app-side webhook registry entry (e.g., matching a previously registered/expected callback address per shop) before dispatch.

### Proof of Concept
```ruby
# Attacker step 1: install target app on their own shop "attacker-shop.myshopify.com"
# and capture a real webhook, e.g. for "orders/create":
raw_body = '{"id":1,"note":"attacker-controlled content"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, raw_body)
# (APP_SECRET unknown to attacker, but Shopify signs it correctly and delivers
#  both raw_body and the hmac header to the attacker's own endpoint/logs)

# Attacker step 2: replay the exact same body + hmac to the target app's
# public webhook endpoint, but with a forged shop header pointing at the victim:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, unsigned
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) succeeds (it only checks raw_body),
# and the app's WebhookHandler#handle receives:
#   data.shop == "victim-shop.myshopify.com"
#   data.body == {"id"=>1,"note"=>"attacker-controlled content"}
# even though this event never occurred on the victim's store.
```

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
