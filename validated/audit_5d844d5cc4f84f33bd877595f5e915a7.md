### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) attribution is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` implements the `Utils::VerifiableQuery` interface used by `HmacValidator`, but its `to_signable_string` method returns only the raw HTTP body, never the `shop`, `topic`, `api-version`, or `webhook-id` values that are read from unauthenticated HTTP headers. `Registry.process` accepts a request as authentic as soon as the HMAC over the body validates, then dispatches to the handler using `request.shop` taken straight from the header, with no cryptographic binding between the validated bytes (body) and the tenant-identifying field (`shop`) acted upon.

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read straight from client-supplied headers with no signature coverage: [2](#0-1) 

`HmacValidator.validate` only ever hashes `verifiable_query.to_signable_string` (the body) against the app's `api_secret_key`, and never incorporates the headers into the signature check: [3](#0-2) 

`Registry.process` treats a valid HMAC as proof the whole request (including `request.shop`) is authentic, and hands the unauthenticated `shop` value straight to the merchant's webhook handler: [4](#0-3) 

This breaks the identity binding: **shop that produced the HMAC-covered bytes (body) ≠ shop attributed to those bytes for business logic (header)**. Because the app's `api_secret_key` is shared across every merchant that installs the app, any merchant can legitimately trigger a real webhook delivery to capture a `(body, hmac)` pair that is valid under the shared secret. Since the header carrying `shop` is excluded from the signed content, that same valid `(body, hmac)` pair can be replayed to the app's public webhook endpoint with an arbitrary `x-shopify-shop-domain` header substituted for a victim shop. `HmacValidator.validate` still returns `true` (it only checks the body/secret pairing), so `Registry.process` will happily invoke the registered handler with `WebhookMetadata.new(..., shop: <attacker-chosen-value>, body: <replayed-body>, ...)`.

### Impact Explanation
Any app built on this gem that uses the `shop` field from `Webhooks::Request`/`WebhookMetadata` to select which merchant's tenant record to update (the intended, documented use of `Registry.process`) can be tricked into applying a genuine merchant's webhook payload to a different merchant's tenant data, since the gem itself provides no assurance that `shop` is bound to the HMAC-validated bytes. This is a cross-tenant access primitive supplied by the gem's own webhook-verification API.

### Likelihood Explanation
Exploitation requires only: (1) the attacker installs the app on their own shop (an unprivileged/normal merchant action, not a privileged credential), (2) they trigger a webhook with a body they can predict or replay (e.g., topics with an empty/predictable body, or by capturing a real delivery), and (3) they replay that exact body+HMAC to the app's webhook receiver with a spoofed `shop`-domain header. No access to `api_secret_key`, access tokens, or the target merchant's credentials is needed.

### Recommendation
Include the identity-relevant headers (`shop`, `topic`, `api_version`, `webhook_id`) in the signed material that `to_signable_string` returns, or otherwise verify `request.shop` against an independently authenticated value (e.g., cross-check against the shop registered for the delivery, as Shopify's platform does via mTLS/IP allow-listing) before passing it to `Registry.process`'s handler. At minimum, document explicitly that `request.shop` is unauthenticated and must not be trusted to select tenant data without additional verification.

### Proof of Concept
1. Install the app on shop `attacker.myshopify.com`; trigger a webhook topic whose delivered body is empty/predictable, e.g. `{}"`.
2. Capture the delivered `x-shopify-hmac-sha256` header for that body (valid under the app's shared `api_secret_key`, per `HmacValidator.compute_signature` in `lib/shopify_api/utils/hmac_validator.rb`).
3. Send a forged HTTP POST to the app's webhook endpoint with the same raw body `{}"`, the same captured `hmac-sha256` header, `x-shopify-topic` set to the target topic, and `x-shopify-shop-domain` set to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` (lib/shopify_api/webhooks/registry.rb:189-199) calls `Utils::HmacValidator.validate`, which passes because only the body is checked (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, letting the attacker inject data attributed to a shop they do not control.
