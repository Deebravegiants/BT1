This confirms the exploit path. The gem's docs explicitly state that `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" (docs/usage/webhooks.md line 125), and the documented handler pattern uses `data.shop` as the authoritative tenant identifier passed straight into application logic (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`, docs/usage/webhooks.md line 26) — yet that `shop` value is never covered by the HMAC.

### Title
Webhook shop-domain header is not covered by the HMAC, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `ShopifyAPI::Webhooks::Registry.process` uses the unauthenticated `shop-domain` header to identify the tenant that the webhook payload is dispatched to application handlers under. Any actor who can obtain one genuinely-signed webhook (e.g. by installing the app on their own store) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header, causing the host application to process attacker-controlled data under a victim shop's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request` parses `shop`, `topic`, `webhook_id`, and `api_version` from HTTP headers [1](#0-0) , but the HMAC signature that authenticates the request is computed and verified only over `@raw_body`: [2](#0-1) 

`Utils::HmacValidator.validate` calls `to_signable_string` to build the signable payload and compares it against the `hmac-sha256` header using the app's shared `api_secret_key`: [3](#0-2)  — the `shop` header plays no role in this computation or in the constant-time comparison.

`Registry.process` treats a passing HMAC check as proof the whole request (including its shop identity) is legitimate, then immediately forwards the unauthenticated `request.shop` value to the app's handler as the tenant identifier: [4](#0-3) 

The identity binding that should hold is: `shop header used for tenant routing == shop cryptographically bound by the HMAC`. In reality the equation is `shop header (attacker-controlled, unauthenticated) != bytes actually covered by HMAC (raw_body only)`. Because the app's `api_secret_key` is the same for every shop that installs the app, any user who installs the app on their own store receives real, validly-signed webhooks from Shopify. That user can capture one such `(raw_body, hmac-sha256)` pair and replay it to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header changed to name a different, victim shop. `HmacValidator.validate` still returns `true` (the body/HMAC pair is genuine and matches the shared secret), so `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(... shop: request.shop ...)` reporting the victim's domain [5](#0-4) .

The gem's own documentation reinforces that host apps are expected to trust this value as authenticated: it states `Registry.process` "will verify the request did indeed come from Shopify" and shows the canonical handler using `data.shop` directly to route/queue tenant-scoped work.

### Impact Explanation
This breaks the tenant/shop identity binding that `Registry.process` is documented to guarantee, allowing an attacker who has installed the app on any (even their own, free) shop to forge webhook events that the host application will process as if they belonged to an arbitrary other shop/tenant — a cross-tenant integrity/confusion attack carried out purely through the gem's own webhook verification API, matching the required "cross-tenant access" impact category.

### Likelihood Explanation
Moderate-to-high: the attacker only needs to install the target app on any Shopify store (a normal, unprivileged action — free dev stores are trivial to create) to obtain a genuinely signed webhook body/HMAC pair, then replay it with a modified shop header to the app's public webhook URL. No access to the app's `client_secret`/access tokens or the victim's store is required.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signable payload, or otherwise cryptographically bind the `shop-domain` header to the verified body (e.g., require host applications receiving a webhook to cross-check `request.shop` against a shop that is known to have a valid, stored session/registration before trusting it as tenant identity), rather than only signing the raw body.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, triggering Shopify to POST a real webhook with a valid `X-Shopify-Hmac-Sha256` header computed over that body using the app's `api_secret_key`.
2. Attacker captures `raw_body` and the corresponding `hmac-sha256` value.
3. Attacker sends a new HTTP POST to the app's webhook endpoint with the identical `raw_body`/`hmac-sha256`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged shop header; `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` [2](#0-1) .
5. `Registry.process` calls the registered handler with `shop: "victim-shop.myshopify.com"` [4](#0-3) , causing the host app to act on forged data under the victim's tenant identity.
