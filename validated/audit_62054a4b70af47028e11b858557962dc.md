### Title
Deposit/Withdraw LP-share pricing relies on instantaneous, single-transaction-manipulable vault balances instead of a time-weighted price - (File: `program/src/processor.rs`)

### Summary
`process_deposit` and `process_withdraw` (and `process_withdrawpnl`) determine the exchange rate between deposited/withdrawn tokens and LP tokens exclusively from the current SPL token vault balances (`amm_coin_vault.amount`, `amm_pc_vault.amount`), fetched via `Calculator::calc_total_without_take_pnl_no_orderbook` <cite repo="AYontt/raydium-amm--009" path="program/src/processor.rs" start="1147="1153"/> [1](#0-0) . This is the same class of issue as the reported `slot0` bug: the pool's "current price" state used for LP-share accounting is a single, spot-in-time on-chain value that a caller can shift arbitrarily within the same atomic transaction via `SwapBaseIn`/`SwapBaseOut`/`SwapBaseIn2`/`SwapBaseOut2`, and there is no TWAP, weighted-average, or price-deviation check anywhere in the program (confirmed: no `twap`/`oracle`/`deviation` guard exists in `program/src/`).

### Finding Description
- `process_deposit` reads the live vault balances and computes `total_pc_without_take_pnl`/`total_coin_without_take_pnl` from them [2](#0-1) .
- It then builds an `InvariantToken`/`InvariantPool` exchange rate directly from these spot totals to compute `deduct_pc_amount`/`deduct_coin_amount` and `mint_lp_amount` [3](#0-2) .
- `process_withdraw` (and `process_withdraw2`) does the symmetric computation for redemption using `total_pc_without_take_pnl`/`total_coin_without_take_pnl` derived the same way [4](#0-3) .
- The swap instructions (`process_swap_base_in`, `process_swap_base_in_v2`, `process_swap_base_out`, `process_swap_base_out_v2`) mutate these same vault balances directly through the constant-product formula, with no cool-down, no minimum elapsed slots, and no averaging over multiple observations [5](#0-4) .
- Because Solana composes multiple instructions atomically in one transaction, an attacker fully controls: (1) a swap that skews the coin/pc ratio, (2) a deposit or withdrawal priced off that skewed ratio, and (3) a reverse swap restoring the original ratio — all with attacker-chosen accounts/amounts in a single submitted transaction, paying only the swap fee.
- Unlike the fix adopted by Real Wagmi (`_checkPriceDeviation`, which rejects operations when the spot price diverges too far from a weighted-average reference), Raydium's `Calculator`/`InvariantPool`/`InvariantToken` code paths perform no analogous sanity check against a longer-window reference price.

### Impact Explanation
By skewing the pool ratio immediately before a deposit and reversing it immediately after, an attacker can mint LP tokens at a rate more favorable than the pool's fair long-term value, diluting the LP share value held by existing liquidity providers (unbacked/under-collateralized LP minting relative to the pool's true value). The symmetric operation around a withdrawal lets an attacker extract a disproportionate amount of one token relative to their true LP share, at the expense of remaining LPs. This directly matches the "Impact" criterion of unbacked LP minting / insolvent pool accounting from a single attacker-controlled transaction.

### Likelihood Explanation
The attack requires only funds sufficient to move the pool price temporarily (a flash loan or the attacker's own capital) and a single transaction combining swap + deposit/withdraw + reverse-swap instructions, all publicly available to any unprivileged caller (`Deposit`, `Withdraw`, and the four swap instructions are explicitly in scope and reachable without any privileged signer). No off-chain component, validator collusion, or non-default configuration is required, making this practically exploitable whenever pool liquidity is not deep enough to absorb the attacker's capital without materially moving price within slippage tolerance (`other_amount_min`/`max_coin_amount`/`max_pc_amount` bound the attacker's own slippage, not the fairness of the price used for share accounting).

### Recommendation
Introduce a time-weighted or multi-observation reference price (e.g., accumulate normalized `total_pc`/`total_coin` over a minimum number of slots) and reject `Deposit`/`Withdraw` operations when the instantaneous vault-balance-derived price deviates from that reference by more than a configurable threshold, mirroring the `_checkPriceDeviation` mitigation referenced in the report. At minimum, disallow deposit/withdraw and swap instructions from being combined in the same transaction/slot for the same pool, or require deposits/withdrawals to also satisfy the same-block reserve ratio recorded at the start of the slot.

### Proof of Concept
1. Attacker submits a single transaction containing three instructions against the same AMM pool: 
   a. `SwapBaseIn`/`SwapBaseIn2` with a large `amount_in` of `coin`, driving `total_coin_without_take_pnl` up and `total_pc_without_take_pnl` down per `Calculator::swap_token_amount_base_in` [6](#0-5) .
   b. `Deposit` with `base_side = 0` (base coin), so `deduct_pc_amount` is computed from the now-skewed `InvariantToken` built off `total_pc_without_take_pnl`/`total_coin_without_take_pnl` [7](#0-6) , letting the attacker mint `mint_lp_amount` LP tokens for less pc than a fairly-priced deposit would require.
   c. A reverse `SwapBaseIn`/`SwapBaseOut` restoring the original ratio, paying only swap fees.
2. Because `calc_take_pnl`/`InvariantPool`/`InvariantToken` never validate the vault-balance ratio against any independent or time-averaged reference, the deposit instruction accepts the skewed price unconditionally, and the attacker's LP tokens are backed by less value than the LP tokens of the pool's other depositors, diluting them.

    }

    pub fn swap_token_amount_base_in(
        amount_in: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_out;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_out = pc - coin * pc / (coin + amount_in)
                // => amount_out = ((pc * coin + pc * amount_in) - coin * pc) / (coin + amount_in)
                // => amount_out =  pc * amount_in / (coin + amount_in)
                let denominator = total_coin_without_take_pnl.checked_add(amount_in).unwrap();
                amount_out = total_pc_without_take_pnl
                    .checked_mul(amount_in)
                    .unwrap()
                    .checked_div(denominator)
                    .unwrap();
            }
            SwapDirection::PC2Coin => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)
                // => amount_out = coin * amount_in / (pc + amount_in)
                let denominator = total_pc_without_take_pnl.checked_add(amount_in).unwrap();
                amount_out = total_coin_without_take_pnl
                    .checked_mul(amount_in)
                    .unwrap()
                    .checked_div(denominator)
                    .unwrap();
            }
        }
        return amount_out;
    }
