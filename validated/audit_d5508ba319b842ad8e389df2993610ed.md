### Title
Token Exchange sends `client_secret` to an unvalidated host derived from the JWT `dest` claim - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds the token-exchange request host directly from the session token's `dest` claim without passing it through `Utils::ShopValidator`, unlike every sibling OAuth flow (`refresh_access_token`, `migrate_to_expiring_token`, `client_credentials`) which all call `Utils::ShopValidator.sanitize!(shop)` before using the value as a request host. This breaks the identity binding: `host that receives Context.api_secret_key == ShopValidator-approved Shopify domain`.

### Finding Description
In `exchange_token`, the shop used to build the outbound HTTP request is taken unvalidated from the JWT payload: [1](#0-0) 

```
jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
dest_shop = jwt_payload.shop
...
shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)
...
client = Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")
```

`jwt_payload.shop` simply strips the `https://` prefix off the `dest` claim: `@dest.gsub("https://", "")` [2](#0-1) . `JwtPayload#initialize` only checks signature validity and `aud == Context.api_key`; it never checks that `dest`'s host is a `*.myshopify.com`/trusted Shopify domain [3](#0-2) .

`Clients::HttpClient#initialize` uses `session.shop` directly as the request hostname with no further validation: [4](#0-3) 

The POST body sent to that host includes the app's `client_secret`: [5](#0-4) 

By contrast, `RefreshToken.refresh_access_token` and `TokenExchange.migrate_to_expiring_token` and `ClientCredentials.client_credentials` all run the `shop` parameter through `Utils::ShopValidator.sanitize!` — which restricts the destination host to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) — before it is used to build the request host that will receive `client_secret`: [6](#0-5) [7](#0-6) 

`exchange_token` is the one code path in this family that skips this sanitization step entirely, relying solely on the JWT signature to "trust" the `dest` value as a hostname, without confirming that hostname is actually a Shopify domain. This mirrors the analog bug class described in the report: a value that passes one check (cryptographic signature over the token) is used for a purpose (selecting the network destination for a secret) that a parallel/sibling code path protects with an additional, stricter check (`ShopValidator`) that this path omits — i.e., the byte range "verified" (signature over claims) does not equal the byte range "acted on" (the destination host string used for the HTTP request).

### Impact Explanation
If the `dest` claim can ever contain a non-Shopify host (e.g., through a malformed/compromised token issuance surface, or any future change to how session tokens are minted for extensions/other surfaces), `exchange_token` would POST `client_id` and `client_secret` — the app's OAuth credentials — to that host. This is SSRF carrying the app's credentials, matching the "High" impact category defined in scope (SSRF with the app's credentials / credential leakage). The other three sibling methods in this same file/module are hardened against exactly this risk via `ShopValidator.sanitize!`, which strongly suggests the omission here is an inconsistency/gap rather than an intentional design decision.

### Likelihood Explanation
Exploitability depends on an attacker's ability to influence the `dest` claim of a session token that still passes `JwtPayload`'s signature/`aud` check. Under normal operation this requires the shared `api_secret_key`, so a full external exploit is not immediately achievable purely as an unprivileged internet user without further conditions (e.g., a bug in token issuance, or reuse of the JWT signing key across environments/apps). Likelihood is therefore moderate-to-low on its own, but the missing defense-in-depth check is a real, code-verifiable regression relative to the rest of the module's threat model, which explicitly treats "shop host" as untrusted input needing validation before use as a network destination for credentials.

### Recommendation
Apply `Utils::ShopValidator.sanitize!` (or an equivalent allow-list check against `TRUSTED_SHOPIFY_DOMAINS`) to `dest_shop` in `TokenExchange.exchange_token` before constructing `shop_session`/`HttpClient`, exactly as done in `refresh_access_token`, `migrate_to_expiring_token`, and `client_credentials`. This ensures the host that receives `client_id`/`client_secret` is always bound to a validated Shopify domain, independent of what the JWT `dest` claim contains.

### Proof of Concept
1. Obtain/produce a session token whose `dest` claim resolves (after `JwtPayload#shop`'s `gsub("https://", "")`) to an arbitrary host string that still satisfies `JWT.decode` and `aud == Context.api_key` (e.g., via any issuance-path anomaly, misconfigured shared secret across environments, or a future extension surface that mints its own `dest`).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe that `Clients::HttpClient` builds `@base_uri = "https://#{dest_shop}"` (no `ShopValidator` check) and issues `POST https://#{dest_shop}/admin/oauth/access_token` with body containing `client_id` and `client_secret` — sending the app's OAuth secret to whatever host `dest_shop` resolves to, unlike the validated sibling flows.

      TRUSTED_SHOPIFY_DOMAINS = T.let(
        [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],
      )

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
