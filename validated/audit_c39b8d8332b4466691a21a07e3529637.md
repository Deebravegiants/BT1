### Title
Webhook `shop` (and topic/webhook-id/api-version) headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` from HTTP headers, but `to_signable_string` returns only the raw body [1](#0-0) . `Utils::HmacValidator.validate` verifies the HMAC solely over that signable string [2](#0-1) , so the `shop` header is never part of what is authenticated. `Registry.process` checks only `Utils::HmacValidator.validate(request)` and then trusts `request.shop` unconditionally when building `WebhookMetadata` and dispatching to the host app's handler [3](#0-2) .

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, shop || body)`, i.e. the shop the app acts on should be cryptographically bound to the signature. Instead the actual binding is `hmac == HMAC(secret, body)` while `shop = header("shopify-shop-domain")` is read and trusted independently [4](#0-3) .

Because the app's `client_secret` is shared across every shop that has the app installed (it is not a per-shop secret), any merchant who installs the app on their own store legitimately receives real webhook deliveries with a valid `x-shopify-hmac-sha256` for a given raw body. That attacker-controlled merchant can then re-POST the exact same `raw_body` (and therefore the same valid HMAC) to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value naming a different, victim tenant. `Utils::HmacValidator.validate` will still return `true` because it only checks the body against the shared secret [5](#0-4) , and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event is from the victim shop [6](#0-5) .

Any host application logic that looks up the victim's stored session/access token by `data.shop` and performs actions (e.g., updating orders, creating fulfillments, redacting data for GDPR topics) based on the forged event now operates against the wrong tenant using the attacker's chosen payload — a cross-tenant confusion driven entirely by an unauthenticated field.

### Impact Explanation
This breaks the shop-identity binding of the webhook subsystem and lets an unprivileged internet user (any merchant who can install the app on their own store to harvest a valid `raw_body`/HMAC pair) inject attacker-chosen webhook bodies attributed to an arbitrary victim shop. Depending on the host app's handler logic this enables cross-tenant data manipulation, which maps to the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation only requires: (1) installing the target app on an attacker-controlled development/test store to observe one legitimate webhook body+HMAC pair, and (2) replaying that exact body with a forged `shop-domain` header to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is needed — only network access to the endpoint the gem's `Registry.process` exposes.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed material, or independently authenticate the `shop` header against a value not attacker-controlled (e.g., cross-check it against the shop associated with the session/store that the app already trusts), rather than trusting `request.shop` solely because the raw body's HMAC validates. At minimum, document that `data.shop` must be validated against a known/installed shop list before use, and consider rejecting requests whose `shop` was not part of an app-known installation.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body and the `x-shopify-hmac-sha256` header sent by Shopify.
2. Attacker sends a new HTTP POST to the app's webhook endpoint with the identical raw body and HMAC header, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. The endpoint calls `ShopifyAPI::Webhooks::Registry.process(request)` [7](#0-6) ; `Utils::HmacValidator.validate(request)` returns `true` since only the body is checked against the shared app secret.
4. `handler.handle` receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` [6](#0-5) , and the host app processes the attacker's payload as if it originated from the victim's store.
