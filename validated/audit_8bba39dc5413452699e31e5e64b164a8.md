### Title
Webhook HMAC does not bind the `shop-domain` header, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` verifies solely that the request body was signed with the app's `api_secret_key` — it never binds the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers into that signature.

### Finding Description
`Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, secret, verifiable_query.to_signable_string)` and compares it against the `hmac` value the caller supplies [4](#0-3) . For webhooks, `to_signable_string` is defined as just the raw JSON body [5](#0-4) , while `shop`, `topic`, and `webhook_id` are pulled straight from HTTP headers with no cryptographic binding to the body or the signature [6](#0-5) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: ..., ...)` to the registered handler [2](#0-1) . Because the header-derived `shop` is outside the signed content, the identity binding the library implicitly promises — `hmac == HMAC(secret, body) ⇒ (body, shop) is authentic` — does not hold; only `HMAC(secret, body) ⇒ body is authentic` holds. `shop` is trusted without being covered by the same proof.

### Impact Explanation
An unprivileged internet user who can obtain one valid `(body, hmac)` pair for the app's `api_secret_key` (e.g., by installing the app on their own store and capturing a legitimately delivered webhook whose body is not shop-specific, such as certain lifecycle/topic payloads) can replay that exact body+HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain`/`shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still passes because the signature only covers the body. The handler then executes with `shop` set to the victim's domain, potentially causing the host application to act on/against the victim tenant's stored offline session/access token, corrupt victim tenant data, or otherwise cross the tenant boundary — this is a cross-tenant access impact.

### Likelihood Explanation
Requires only network access to the app's webhook endpoint and possession of one signed `(body, hmac)` pair, obtainable by installing the app on an attacker-owned store (a standard, unprivileged action) — no `api_secret_key`, access token, or privileged account is needed. The bug is fully within this gem's own signing/verification logic (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`), not a host-application misuse.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed content used by `to_signable_string`, or otherwise cryptographically bind them to the payload the HMAC covers, so that `HmacValidator.validate` proves the authenticity of the (shop, topic, body) tuple as a whole rather than the body alone.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook whose JSON body carries no shop-specific data (e.g. `{}` for certain topics), capturing the raw body `B` and the resulting `x-shopify-hmac-sha256` header `H` — both legitimately produced by Shopify using the app's real `api_secret_key`.
2. Attacker sends `POST` to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` unchanged, `x-shopify-topic` unchanged, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and compares to `H` — it matches, since `B` and `H` are unmodified [7](#0-6) .
4. The handler is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, letting the attacker-controlled body be processed under the victim tenant's identity.
