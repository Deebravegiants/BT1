### Title
Webhook shop/topic identity is not bound to the HMAC, allowing cross-tenant webhook forgery via header substitution - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the HMAC exclusively over the raw request body [1](#0-0) , while the `shop`, `topic`, `webhook_id`, and `api_version` values used to route and attribute the webhook are read straight from HTTP headers that are never included in that signed content [2](#0-1) . `Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching `request.shop` and `request.topic` straight to the app's handler [3](#0-2) . This breaks the identity binding `shop-that-produced-the-signed-bytes == shop-attributed-to-the-event`.

### Finding Description
`HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header using a constant-time comparison [4](#0-3) . For webhooks, `to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop`, `topic`, `webhook_id` and `api_version` accessors pull their values from `shopify-*`/`x-shopify-*` HTTP headers, none of which are covered by that signature [2](#0-1) . `Registry.process` validates only the HMAC and then forwards `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` unchanged into `WebhookMetadata`, which is delivered to the host app's handler as the trusted tenant/topic identity [3](#0-2) . The gem's own documentation instructs apps to key their downstream processing directly off `data.shop` and `data.topic` without any additional verification [5](#0-4) .

Because the identity fields live outside the signed bytes, any party who can obtain one genuine `(raw_body, hmac)` pair from Shopify — e.g., a merchant who installs the app on their own store and receives a legitimate webhook for a topic they registered — can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers. The HMAC check still succeeds (it only re-derives the digest from the unchanged body), yet the app now processes attacker-supplied body content as if it were an authentic event for an arbitrary victim shop and/or an arbitrary registered topic — a cross-tenant identity spoof, matching the same class of bug as the reported analog ("a field acted on but not covered by the HMAC").

### Impact Explanation
This is a Critical-class cross-tenant issue: an unprivileged (but app-installing) attacker can make the library attribute an event to a different merchant's shop domain and/or a different webhook topic than the one Shopify actually signed for, without needing the app's `api_secret_key`. Any host application that uses `data.shop` from `WebhookMetadata` to key database writes, trigger merchant-specific business logic, or select an access token/session (as the gem's own docs recommend) can be tricked into updating or acting on the wrong tenant's data, or invoking a handler for a topic whose payload schema wasn't actually validated for that topic.

### Likelihood Explanation
Likelihood is moderate: the attacker must first obtain one legitimate `(raw_body, hmac)` pair, which is trivial if the attacker installs the app on their own store (a normal, unprivileged action) and lets it deliver at least one real webhook. From there, forging a POST to the fixed, publicly known webhook endpoint with modified `shop-domain`/`topic` headers requires no cryptographic knowledge, only knowledge of the (documented) fixed request format.

### Recommendation
Bind the shop/topic identity into the signed content, e.g., include `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` in `to_signable_string` (or verify them independently against Shopify, such as looking up the webhook by `webhook_id` via the Admin API before trusting the `shop` header), rather than relying purely on a body-only HMAC to authenticate header-derived identity fields.

# Attacker step 2: replay same body/hmac, but swap identity headers

ShopifyAPI::Webhooks::Registry.process(request)

# handler.handle is invoked with data.shop == "victim-shop.myshopify.com"
