### Title
Webhook tenant identity (`shop`) is not covered by HMAC verification, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-verifying the raw request body against the app's `client_secret`. The `shop` (tenant) identifier that the library hands to the app's handler is read from an HTTP header and is never included in the HMAC-signed material, so the signature proves only "this body was signed by Shopify for some shop," not "this body belongs to the shop named in this header."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `shop` is parsed independently from a header, not from the signed body: [2](#0-1) 

`Registry.process` verifies the request using `Utils::HmacValidator.validate(request)` — which calls `verifiable_query.to_signable_string` (the raw body) — and then, once that single check passes, forwards the header-derived `request.shop` straight to the app's handler as the authoritative tenant identifier: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` compute the HMAC purely over `verifiable_query.to_signable_string` (the body) using `Context.api_secret_key`: [4](#0-3) 

The identity binding that should hold is: `shop covered by the verified signature == shop delivered to the app's handler`. In this implementation that equality does not hold — the signature covers only the body, while `shop` is taken from an independent, unsigned `x-shopify-shop-domain`/`shopify-shop-domain` header. Documentation confirms apps are expected to trust `data.shop` as the tenant for downstream processing (e.g., enqueuing jobs keyed by `shop_domain`): [5](#0-4) 

Because Shopify's own webhook signing (and this library's replication of it) never binds the `shop` header into the signed payload, any request that carries a body/HMAC pair that was legitimately produced for shop A (something an attacker can obtain simply by owning a development/trial store that receives real webhooks from Shopify) remains HMAC-valid if replayed with the `shop-domain` header changed to shop B. The library will accept it and hand the app a `WebhookMetadata` claiming the data belongs to shop B.

### Impact Explanation
This breaks the tenant boundary the gem is responsible for establishing before invoking app code: an unprivileged internet user who controls (or has captured a webhook from) one Shopify store can cause the app to process attacker-supplied body content under the identity of a different, victim shop, since the only integrity check (HMAC) never covers the shop identifier. Depending on how the host app uses `data.shop`, this enables cross-tenant data injection/confusion — writing or associating webhook data to another merchant's account within the app's own data model. This matches the "cross-tenant access" class of impact.

### Likelihood Explanation
Exploitation requires only network access to the app's public webhook endpoint plus possession of one valid (body, HMAC) pair for any shop — trivial for an attacker who installs the app on their own (attacker-controlled) development store, since Shopify will deliver real signed webhooks to it. No access to `api_secret_key`, tokens, or privileged accounts is needed; the header is not authenticated at all.

### Recommendation
Bind the tenant identifier into the verified material before trusting it, e.g.:
- Include `shop-domain` (and ideally `topic`, `webhook-id`) in the signable string used by `HmacValidator`, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop` into its signed query, or
- Cross-check the header `shop` against an expected/known set of shops (e.g., shops with an active session/installation) before invoking the handler, rejecting webhooks for shops with no corresponding validated session, and clearly document that `WebhookMetadata#shop` must not be trusted as authenticated identity absent this additional check.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets Shopify deliver a real webhook, e.g. `orders/create`, to the app's webhook endpoint. Attacker captures the raw body `B` and its `x-shopify-hmac-sha256` value `H` (valid for `B` under the app's secret).
2. Attacker crafts a new HTTP POST to the same webhook endpoint reusing body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {... "x-shopify-shop-domain" => "victim.myshopify.com", "x-shopify-hmac-sha256" => H ...})` is constructed; `to_signable_string` returns `B`, so `Utils::HmacValidator.validate` succeeds (the signature never referenced the shop header).
4. `ShopifyAPI::Webhooks::Registry.process` proceeds to call the registered handler with `WebhookMetadata.new(... shop: "victim.myshopify.com", body: parsed B ...)`, i.e., the app processes attacker-controlled data as if it came from the victim's store.

```ruby
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
```

```ruby
        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
```

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
```
