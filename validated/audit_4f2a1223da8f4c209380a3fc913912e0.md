### Title
Interest-accrual multiplication can permanently freeze an oversized market - ([File: `common/src/rates/simulate.rs`])

### Summary

A market whose scaled balances and interest indexes remain individually representable can nevertheless make `scaled × index` exceed `i128::MAX`. Because every mutation runs interest accrual before processing the requested action, reaching that arithmetic ceiling permanently blocks repayment, withdrawal, liquidation, and further index updates for the market.

### Finding Description

`Controller::update_indexes(caller, assets)` is callable by any authenticated caller and invokes the pool’s `update_indexes` entrypoint for each supplied `HubAssetKey`. [1](#0-0) [2](#0-1) 

The pool accrual path calls `interest::global_sync`, which repeatedly invokes `accrue_step`. [3](#0-2) [4](#0-3) 

`accrue_step` first computes the current debt and supply values with `scaled_to_original`. [5](#0-4)  `scaled_to_original` delegates to `Ray::mul`, which panics with `MathOverflow` when the exact product does not fit in `i128`. [6](#0-5) [7](#0-6) 

The configured borrow-index cap does not prevent this: `update_borrow_index` multiplies by the interest factor first and only then clamps the resulting index. [8](#0-7)  More importantly, the failure can occur on `borrowed × borrow_index` before a new index is even calculated.

All ordinary pool mutations synchronize interest first through `synced_market`, so once accrual overflows, later transactions cannot bypass the failing calculation. [9](#0-8) 

### Impact Explanation

The result is permanent freezing of all funds in the affected `(hub_id, asset)` market: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot force resolution, and `update_indexes` itself cannot advance `last_timestamp`. [9](#0-8) [10](#0-9) 

The repository contains an executable reproduction demonstrating that a one-billion-token, 18-decimal market at sustained 98% utilization hits the RAY-value ceiling before `MAX_BORROW_INDEX_RAY`; subsequent withdrawal and repayment attempts both fail with `MATH_OVERFLOW`. [11](#0-10) 

### Likelihood Explanation

Likelihood is constrained by the very large market size and sustained high-utilization period required: the test fixture uses `1e27` base units, equivalent to `1e36` in RAY terms, and requires the effective index exposure to exceed roughly 170× that value. [12](#0-11) 

Nevertheless, the condition arises from allowed supply, borrow, and time progression rather than privileged state corruption; after it is reached, any authenticated user can trigger the fatal `update_indexes` call. [2](#0-1) 

### Recommendation

Do not let index accrual evaluate an unrepresentable aggregate value. Before `scaled_to_original`, detect whether `scaled` or `index` exceeds a product-domain bound and cap, split, or otherwise handle the aggregate deterministically. The borrow-index cap should also be applied before deriving `new_total_debt`, and repayment/withdrawal should have a recovery path that does not require a successful next accrual step. Relevant locations are `common/src/rates/simulate.rs`, `common/src/rates/index.rs`, and `contracts/pool/src/ops/mod.rs`. [13](#0-12) [14](#0-13) 

### Proof of Concept

1. Create an 18-decimal market using the high-rate XLM curve and a separate collateral market, with utilization caps disabled as in the checked-in fixture. [15](#0-14) 
2. Supply `1_000_000_000 * 10^18` base units to the target market and borrow 98% of it against sufficient collateral in the collateral market. [16](#0-15) 
3. Advance ledger time in yearly intervals and call controller `update_indexes` with `assets = vec![HubAssetKey { hub_id, asset }]` for the target market. [17](#0-16) 
4. Once `borrowed × borrow_index` exceeds the `i128` result domain, `scaled_to_original` panics with `MathOverflow` before the borrow-index cap can engage. [6](#0-5) [18](#0-17) 
5. Subsequent `withdraw` and `repay` calls fail with the same `MATH_OVERFLOW`, because both routes synchronize interest before mutating the position. [9](#0-8) [19](#0-18)

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
