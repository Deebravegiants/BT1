### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) identity headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the shop identity delivered to the app's webhook handler is read from an HTTP header that is never included in that signature. This breaks the binding "bytes verified == bytes the shop identity is derived from," allowing an attacker who obtains one legitimately-signed webhook body to replay it while asserting a different shop.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` verifies a `VerifiableQuery` by computing an HMAC over `to_signable_string` and comparing it to the `hmac` value: [1](#0-0) 

For webhooks, `ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [2](#0-1) 

However, `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`), which are **not** part of the signed payload: [3](#0-2) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)` — which only proves the raw body wasn't tampered with — and then unconditionally trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The equality that should hold is: `shop asserted to the handler == shop the signature was computed for`. Because the signature covers only the body bytes and not the `shop-domain` header, this equality is never checked. An attacker who has captured/received one validly-signed webhook delivery (e.g., a webhook Shopify sent for the attacker's own shop where the app is installed) can resend that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header with a victim shop's domain. `HmacValidator.validate` will still return `true` because it only checks the (unchanged) body against the (unchanged) HMAC — the header substitution is invisible to the signature check. The app's handler then receives `WebhookMetadata` claiming the event is for the victim shop, when it is in fact attacker-controlled data for the attacker's own shop.

### Impact Explanation
This is a High-severity issue: it is a case of "a field acted on but not covered by the HMAC," directly matching an accepted analog for identity-binding failures. It allows cross-tenant confusion of webhook events — an attacker can make the app process/act on their own submitted body/topic combination while pretending it originates from an arbitrary other shop domain that has previously installed the app. Any app whose webhook handler makes trust decisions based on `WebhookMetadata#shop` (e.g., updating per-shop records, triggering actions scoped to a shop, or granting behavior based on which shop sent the event) can be manipulated into acting on behalf of, or against, a different tenant than the one that actually produced the signed payload — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires the attacker to first obtain one validly-HMAC-signed webhook body. This is trivially achievable by any unprivileged internet user who installs the target app on their own development/trial shop (standard, unprivileged action — no special credentials, access tokens, or `client_secret` needed) and captures a webhook Shopify sends them. They can then replay that captured body to the app's public webhook endpoint with a forged `shop-domain` header pointing at any other shop. No secrets are needed for the forgery step itself since the signature check never inspects the header being changed.

### Recommendation
Include the shop domain (and topic, if used for routing/authorization decisions) in the signed material verified against the HMAC, or independently bind the header value to the signature, e.g.:
- Verify that `request.shop` matches a shop known to be associated with an active app installation before trusting it, and/or
- Compute/verify the HMAC over a canonical string that includes the `shop-domain` and `topic` headers in addition to the raw body, rejecting the webhook if any of these fields were altered relative to what was signed.

At minimum, document/guard so that `WebhookMetadata#shop` is never treated as authenticated/trusted purely because `HmacValidator.validate` passed, since the validator currently only guarantees body integrity, not header integrity.

### Proof of Concept
```ruby
# Step 1: Attacker installs the target app on their own shop "attacker-shop.myshopify.com"
# and receives a legitimately Shopify-signed webhook, e.g. for topic "orders/create":
#   Headers:
#     X-Shopify-Topic: orders/create
#     X-Shopify-Hmac-Sha256: <valid_hmac_for_body>
#     X-Shopify-Shop-Domain: attacker-shop.myshopify.com
#   Body: '{"id": 123, "note": "hello"}'

# Step 2: Attacker replays the exact same body + hmac header to the app's
# public webhook endpoint, but swaps the shop-domain header:
POST /webhooks HTTP/1.1
X-Shopify-Topic: orders/create
X-Shopify-Hmac-Sha256: <same_valid_hmac_for_body>   # unchanged, still matches body
X-Shopify-Shop-Domain: victim-shop.myshopify.com    # forged
Content-Type: application/json

{"id": 123, "note": "hello"}

# Step 3: In the gem:
request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Utils::HmacValidator.validate(request)  # => true (body/hmac still match)
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(topic: "orders/create",
#                                              shop: "victim-shop.myshopify.com",  # attacker-controlled!
#                                              body: {"id"=>123, "note"=>"hello"}, ...))
```
The app's handler now believes attacker-supplied data pertains to `victim-shop.myshopify.com`, despite the HMAC never having validated that association.
