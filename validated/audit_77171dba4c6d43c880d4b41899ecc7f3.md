## Title
Webhook Shop/Topic Identity Spoofing via HMAC That Only Covers the Body — (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking `Utils::HmacValidator.validate(request)`, and `Request#to_signable_string` returns only the raw request body — none of the identity-bearing headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) are part of the signed material. Yet those exact unverified fields are what get handed straight to the app's handler as trusted identity data.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
It returns only `@raw_body`. The `hmac`, `topic`, `shop`, `api_version`, and `webhook_id` accessors all read directly from unauthenticated HTTP headers: [2](#0-1) 

`Registry.process` only calls `HmacValidator.validate`, which computes `HMAC(secret, raw_body)` and compares it to the `hmac` header — it never binds `shop`, `topic`, `api_version`, or `webhook_id` into that computation: [3](#0-2) [4](#0-3) 

After this "verification," the unauthenticated `shop`, `topic`, `api_version`, and `webhook_id` headers are passed straight into `WebhookMetadata` and given to the app's registered handler as trusted fields: [5](#0-4) 

This is exactly the identity-binding gap described in the report's bug class: a field that is *acted on* (`shop`, used by host apps to select which tenant's data the webhook applies to) is not covered by the cryptographic proof (the HMAC only proves the body bytes are unmodified from *some* genuine Shopify webhook signed with this app's secret — it says nothing about which shop or topic that body was originally sent for).

Because every shop installing the same app shares the single `api_secret_key`, any tenant of a multi-tenant app can legitimately receive an authentically HMAC-signed webhook for their **own** shop, then replay that exact `raw_body`/`hmac` pair against the app's shared webhook endpoint while altering the `x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`, or `x-shopify-api-version` headers. `Registry.process` will accept it as valid (the body-only HMAC still matches) and hand the forged `shop`/`topic` to the handler as if Shopify itself had asserted them.

The library's own documentation reinforces the false sense of completeness: "This will verify the request did indeed come from Shopify and then call the specified handler for that webhook" — but it only verifies the body came from Shopify at some point, not that the accompanying shop/topic headers are authentic. [6](#0-5) 

### Impact Explanation
Any unprivileged user who can install the app on their own store (a normal, no-privilege onboarding flow) can obtain authentic `(raw_body, hmac)` pairs and replay them with a spoofed `shop-domain` header to impersonate another tenant to the webhook handler. Applications that use `WebhookMetadata#shop` to key data lookups/writes (the pattern this library encourages, per its own docs) can be tricked into associating attacker-controlled webhook content with a victim shop's record, or into re-triggering a handler under a different `topic`/`webhook_id` than actually occurred — a cross-tenant identity confusion in a multi-tenant application context.

### Likelihood Explanation
Requires only that the attacker be a legitimate installer of the target multi-tenant app on their own shop (no leaked credentials, no TLS interception, no social engineering) — well within "unprivileged internet user." Capturing a genuine webhook to a self-controlled endpoint is trivial (webhook `path` is attacker-configurable during their own installation/registration), and replaying to the shared processing endpoint with modified headers is a simple HTTP request.

### Recommendation
Bind the identity headers into the signed material verified by `HmacValidator`, or otherwise require the host application to independently correlate `request.shop` against a known, previously-established session/tenant before trusting it — e.g., include `shop`, `topic`, and `webhook_id` in `to_signable_string`, or document/enforce that `Registry.process` callers must verify `request.shop` corresponds to an existing stored session before acting on the payload, rather than implying the current HMAC check is sufficient identity proof.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers a webhook (e.g., `orders/create`) pointing at a URL they control, capturing the raw POST: headers include `x-shopify-hmac-sha256: <H>`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`, body `B`. `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker replays the exact same body `B` and `x-shopify-hmac-sha256: <H>` to the app's real, shared webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` and finds it matches `H` — validation passes, since `shop` is never part of the signed string: [7](#0-6) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-supplied body content, believing it is an authentic event from the victim's store.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
