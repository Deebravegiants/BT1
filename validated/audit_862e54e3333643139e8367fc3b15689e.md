Audit Report

## Title
Gateway CORS wildcard allowlist uses unanchored suffix matching, letting attacker-registered domains impersonate trusted origins - ([File: core/services/gateway/network/httpserver.go])

## Summary
`isAllowedOrigin` in `core/services/gateway/network/httpserver.go` matches wildcard CORS allowlist entries (e.g. `*.example.com`) using unanchored `strings.HasSuffix(originHost, allowedHost)`, which is satisfied by any domain that merely ends with the allowed suffix (e.g., `evilexample.com` matches `*.example.com`) rather than only true subdomains. This allows an attacker who registers such a domain to have the gateway reflect their `Origin` back in `Access-Control-Allow-Origin`, letting attacker-controlled pages read the gateway's JSON-RPC responses cross-origin.

## Finding Description
In `isAllowedOrigin` [1](#0-0) , wildcard entries strip the `*.` prefix and then check `strings.HasSuffix(originHost, allowedHost)` with no requirement that the match occur on a domain-label boundary (i.e., no check for a preceding `.` or exact equality). Given `allowedHost = "example.com"`, `strings.HasSuffix("evilexample.com", "example.com")` returns `true`, incorrectly treating an unrelated attacker-controlled domain as a subdomain.

This function is called from `handleRequest`, which reflects the attacker's `Origin` value into `Access-Control-Allow-Origin` along with permissive `Access-Control-Allow-Methods`/`Access-Control-Allow-Headers` whenever the check passes [2](#0-1) , and then forwards the response from `ProcessRequest` to the caller [3](#0-2) . There is no other validation layer that anchors the wildcard match to a proper subdomain boundary — the existing test suite in `httpserver_test.go` only exercises true-subdomain and clearly-mismatched cases (e.g., `another.valid.domain.com` vs `ethereum.remix.org`), and does not cover the boundary-adjacent case (`evilexample.com` vs `*.example.com`), so the flaw is not caught by current tests [4](#0-3) .

## Impact Explanation
When an operator enables CORS with a wildcard allowlist entry (a supported, documented, and tested configuration), an unprivileged external attacker can register a domain sharing the allowed suffix without a dot separator and have the gateway trust it as an allowed origin. This lets attacker JavaScript, once a victim visits the attacker's page, make cross-origin requests to the gateway's user-facing endpoint and read JSON-RPC responses that would otherwise be same-origin-protected, corresponding to a cross-user/cross-origin response-disclosure class issue (allowlist bypass) in the gateway.

## Likelihood Explanation
Exploitation requires only that the operator use a wildcard `CORSAllowedOrigins` entry (an intended, tested feature) and that the attacker register an inexpensive domain name ending in the same suffix — no operator/admin credentials, host access, or privileged role are needed by the attacker, and the victim only needs to visit a page in a normal browser (standard CORS-triggering behavior, not exotic social engineering).

## Recommendation
Anchor wildcard matching to a proper subdomain boundary, e.g. require `originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost)`, so that `evilexample.com` cannot satisfy `*.example.com`.

## Proof of Concept
1. Configure the gateway with `CORSEnabled = true`, `CORSAllowedOrigins = ["https://*.example.com"]`.
2. Send a request to the gateway's user-facing endpoint with header `Origin: https://evilexample.com`.
3. Observe `isAllowedOrigin` strips `*.` to get `allowedHost = "example.com"` and evaluates `strings.HasSuffix("evilexample.com", "example.com")` as `true`.
4. Observe the response includes `Access-Control-Allow-Origin: https://evilexample.com`, confirming the bypass. This can be verified as a unit test analogous to `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards`, but using origin `https://evilexample.com` against allowlist `https://*.example.com`, asserting `Access-Control-Allow-Origin` is unexpectedly set.
