### Title
Escrow withdrawals in `IntentGatewayV2` (Tron) use unchecked low-level `transfer()` calls instead of `safeTransfer()`, silently marking failed ERC20 transfers as successful - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.sol` releases escrowed order funds and sweeps dust by issuing a raw low-level `.call()` encoding `IERC20.transfer.selector` and only checking that the **outer call did not revert** (`success`). It never decodes/validates the ABI-encoded boolean return value that `transfer()` is supposed to return. For any ERC20/TRC20 token that returns `false` on failure instead of reverting (non-compliant tokens are common on Tron/TRC20), the contract will treat the transfer as successful even though no tokens moved.

and identically for fee redemption: [2](#0-1) 
and for `SweepDust`: [3](#0-2) 

These are called from `onAccept`, which is invoked by the host when a cross-chain `RedeemEscrow`/`RefundEscrow`/`SweepDust` POST request is delivered by any relayer submitting a valid proof: [4](#0-3) 

Immediately after the unchecked `token.call(...)`, the accounting is unconditionally decremented as if the transfer succeeded: [5](#0-4) 

This differs from the rest of the codebase, which consistently uses OpenZeppelin's `safeTransfer`/`safeTransferFrom` for escrow-affecting ERC20 movements, e.g. in `WrappedHyperFungibleToken.sol` and the EVM `IntentGatewayV2.sol` predispatch/input logic: [6](#0-5) [7](#0-6) 

`token.call(...)` only reverts (`success == false`) if the target address has no code or the call itself throws; a contract that returns `abi.encode(false)` without reverting (a legitimate ERC20 behavior per EIP-20, and common among non-compliant tokens) will make `success == true` while the beneficiary receives nothing.

### Impact Explanation
Because `_orders[body.commitment][token]` (and the transaction-fee escrow) is decremented unconditionally after this unchecked call, a token that returns `false` instead of reverting causes:
- The escrowed balance is deleted/reduced as if funds were paid out, but the beneficiary/solver never actually receives the tokens — a **permanent freeze of funds** (the tokens remain locked in the `IntentGatewayV2` contract with no accounting path to reclaim them, since `_orders[...]` has already been decremented).
- Any relayer/solver interacting with intents that use such a token on the Tron deployment is directly affected, since escrow release, refund, dust sweep, and fee redemption all share this pattern.

This satisfies the "permanent freezing of funds" acceptance criterion for the analog.

### Likelihood Explanation
Reachability requires only a normal, permissionless flow: a user places an order with a non-standard ERC20/TRC20 token (or a relayer/solver fills/cancels the order), and the relayer delivers the corresponding `RedeemEscrow`/`RefundEscrow`/`SweepDust` message via the standard ISMP delivery path to `onAccept`. No privileged role is required to trigger the vulnerable code path — any token that follows the EIP-20 spec of returning `false` instead of reverting will trigger the bug on ordinary escrow settlement, making this highly likely to be hit in production usage of the Tron intent gateway with such tokens.

### Recommendation
Replace all `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` (in `withdraw()` and the `SweepDust` handler) with OpenZeppelin's `SafeERC20.safeTransfer()`, matching the pattern already used elsewhere in the codebase (`WrappedHyperFungibleToken.sol`, EVM `IntentGatewayV2.sol`). This ensures a non-compliant token's `false` return value causes a revert rather than being silently accepted as success.

### Proof of Concept
1. Deploy (or use) a TRC20/ERC20 token whose `transfer()` implementation returns `false` on failure instead of reverting (e.g., insufficient balance/blacklist check that returns false), and register it as a valid input/output token for an order.
2. A user places an order using this token; funds get escrowed into `_orders[commitment][token]`.
3. Cause the token transfer inside `withdraw()` to fail in a way that returns `false` (e.g., beneficiary is blacklisted by the token, or contract balance manipulated so the token's internal check returns false rather than reverting).
4. A relayer delivers the `RedeemEscrow`/`RefundEscrow` message; `onAccept` → `withdraw()` executes `token.call(...)`, which returns `success == true` (call succeeded) even though the encoded return data is `false`.
5. `_orders[body.commitment][token] -= amount;` executes, permanently erasing the escrow record while the beneficiary received zero tokens — funds are now stuck in the contract with no future accounting path to withdraw them.
