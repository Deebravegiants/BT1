### Title
Webhook shop-tenant attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by HMAC-signing only the raw request body, while the `shop-domain` header — used by handlers to attribute the event to a tenant — is read from an unauthenticated header and never included in the signed material.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is pulled straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the body or the HMAC: [2](#0-1) 

`Registry.process` validates the request solely via `Utils::HmacValidator.validate(request)` (which signs/verifies `to_signable_string`, i.e. only the body) and then hands the *unauthenticated* `request.shop` straight to the handler as the tenant identifier: [3](#0-2) 

`HmacValidator.validate_signature` confirms this: it signs/compares only `verifiable_query.to_signable_string`: [4](#0-3) 

The identity binding that should hold is: **shop-domain used to attribute the event == shop-domain covered by the HMAC**. Instead, only the body is authenticated; the shop attribution is a bare, unauthenticated header value. Because the HMAC key (`api_secret_key`) is a single, app-wide secret shared across *all* installed shops (not per-tenant), any legitimately installed merchant who receives a real, validly-HMAC'd webhook for their own shop can capture that raw body + HMAC and replay it to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. The signature still validates (it only covers the body), and `Registry.process` will invoke the handler with `WebhookMetadata` (topic/shop/body) attributing the event to whatever shop the attacker names.

This directly matches the identity-binding class called out in scope: "a field acted on (shop) but not covered by the HMAC."

### Impact Explanation
This is a cross-tenant attack: an unprivileged (but legitimately installed) merchant can, without ever touching `api_secret_key` or any other shop's credentials, forge webhook events that the app will process as originating from a victim shop. Depending on the host app's webhook handlers, this can be used to poison another shop's data, trigger fulfillment/inventory/order side effects attributed to a different tenant, or otherwise cross the tenant boundary the whole webhook system is meant to enforce — this is exactly the "cross-tenant access" impact category.

### Likelihood Explanation
Moderate-to-high. The only prerequisite is being a real, installed (unprivileged) merchant of the app — no secret material, access token, or social engineering is required. The attacker only needs one legitimately delivered webhook (with a body and valid HMAC for their own store) to replay against the same public endpoint with a different `shop-domain` header, since headers are not part of what the HMAC verifies.

### Recommendation
Bind the shop identity into the authenticated material: either include `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) in the value covered by the HMAC signature computation, or otherwise cryptographically verify that the `shop-domain` header matches the tenant that the caller/session is authorized for before dispatching to `WebhookMetadata`/handlers. At minimum, document that consuming applications must independently authenticate the shop (e.g. against a known list of installed shops) rather than trusting `WebhookMetadata#shop` as tenant-authenticated.

### Proof of Concept
1. Attacker installs the app on their own shop (`attacker.myshopify.com`) — this is a normal, unprivileged installation flow.
2. Shopify sends a legitimate webhook to the app's endpoint for `attacker.myshopify.com`, e.g.:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of raw_body under the app's single api_secret_key>
   x-shopify-shop-domain: attacker.myshopify.com
   {"id": 1, ...order json...}
   ```
3. Attacker captures this exact raw body and HMAC value (both are visible to them as the receiving party, or replayable via a proxy in front of their own endpoint).
4. Attacker replays the identical request to the same public webhook endpoint but with the header changed:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
   Same raw body, same `x-shopify-hmac-sha256`.
5. `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the shared `api_secret_key`. `Registry.process` proceeds and invokes the registered handler with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)` [5](#0-4) , causing the app to process/store the attacker's data as if it belonged to the victim shop.
