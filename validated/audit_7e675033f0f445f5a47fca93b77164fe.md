## Finding: Omni Bridge withdrawal status is matched by raw array index instead of by withdrawal identity, unlike the sibling PoA Bridge implementation

### Title
Omni Bridge `describeWithdrawal()` reports completion of the wrong withdrawal by indexing an unvalidated transfer array — (File: packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts)

### Summary
`OmniBridge.describeWithdrawal()` fetches all transfers for a NEAR transaction hash and picks the one at `args.index` with no check that the transfer's recipient, asset, or amount actually corresponds to the withdrawal being described. When multiple Omni Bridge withdrawals are batched in a single NEAR intent (a supported and documented SDK flow), the SDK can report `status: "completed"` with a `txHash` belonging to a *different* withdrawal in the batch, if the bridge API returns transfers in an order that doesn't match submission order.

### Finding Description
`describeWithdrawal` does: [1](#0-0) 

```ts
const transfer = (
    await this.omniBridgeAPI.getTransfer({ transactionHash: args.tx.hash })
)[args.index];

if (transfer == null || transfer.recipient == null) {
    return { status: "pending" };
}
const destinationChain = getChain(transfer.recipient as OmniAddress);
```

No field of `transfer` (recipient address, amount, token) is compared against `args.withdrawalParams` before the function returns `{ status: "completed", txHash }`.

Compare this to the sibling `PoaBridge.describeWithdrawal`, which explicitly documents and fixes this exact class of bug: [2](#0-1) [3](#0-2) 

```ts
// Response list is unsorted, so we match by assetId instead of index
const withdrawal = findMatchingWithdrawal(
    response.withdrawals,
    args.withdrawalParams.assetId,
);
```

This fix was introduced specifically because index-based matching against an unordered API response is unsafe — see the changelog entry: "Fix POA bridge withdrawal matching to use assetId instead of index" [4](#0-3) . The same defensive matching was never applied to `OmniBridge`.

Batch withdrawals through the same bridge route are a supported, documented scenario — `createWithdrawalIdentifiers` assigns a strictly incrementing `index` per bridge route across multiple withdrawal params in one intent/tx: [5](#0-4) 

and the design RFC explicitly calls out multi-asset batches like "USDC to Solana + BTC refund to Bitcoin" in one NEAR tx [6](#0-5) .

### Impact Explanation
If `omniBridgeAPI.getTransfer()` ever returns the underlying chain-recorded transfers for a multi-withdrawal NEAR tx in an order that does not match submission order (which is exactly the failure mode the PoA sibling code was patched to defend against), `describeWithdrawal` will:
- Report `withdrawal[0]` as `completed` with the `txHash`/chain that actually belongs to `withdrawal[1]` (a different destination address, asset, or amount).
- An integrator relying on `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` to know when to credit a user or mark a withdrawal settled would credit/finalize the wrong withdrawal, using a transaction hash and completion signal that does not correspond to the actual on-chain outcome of that specific withdrawal — a status/hash misreport that can cause double-crediting or premature release tied to the wrong destination.

This falls under the accepted High-impact category: "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
This requires no attacker action beyond using the SDK's own documented batch-withdrawal feature with the Omni Bridge route for two or more withdrawals in a single intent; correctness then depends entirely on an assumption (stable, submission-order-matching indices from a third-party API) that the codebase itself has already proven unreliable and patched for the PoA route.

### Recommendation
Apply the same defensive, identity-based matching used in `PoaBridge.describeWithdrawal` to `OmniBridge.describeWithdrawal`: instead of indexing the transfers array directly, match the transfer whose recipient/asset/amount corresponds to `args.withdrawalParams`, and only fall back to positional index when no better identifier is available and multiplicity is disambiguated (e.g., by asset + amount similar to the PoA bridge's noted future improvement).

### Proof of Concept
1. Submit `processWithdrawal` with `withdrawalParams` containing two Omni Bridge withdrawals in one batch intent, e.g. `[{assetId: USDC, destinationAddress: A}, {assetId: BTC, destinationAddress: B}]`.
2. Assume (as already documented as a real risk for the PoA bridge) that `BridgeAPI.getTransfer(txHash)` returns the underlying transfers in an order not guaranteed to match submission order.
3. `describeWithdrawal` for `index=0` picks `transfers[0]`, which may be the BTC-to-B transfer, and returns `{status: "completed", txHash: <BTC tx>}` as the result for the USDC-to-A withdrawal.
4. An integrator using `createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion` sees withdrawal index 0 (USDC/A) reported completed with a transaction hash/chain that actually paid destination B, and credits/settles based on incorrect data.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
