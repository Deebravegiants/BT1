### Title
`TokenExchange.exchange_token` sends `client_secret` to an unvalidated host derived from the JWT `dest` claim - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`JwtPayload#shop` simply strips `"https://"` from the `dest` claim with no domain allow-listing [4](#0-3) , and `TokenExchange.exchange_token` feeds that raw value directly into `Auth::Session.new(shop: dest_shop)` and then into `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")`, which builds the outbound request host from `session.shop` and posts a body containing `client_id`/`client_secret` to it.

### Finding Description
Every other OAuth grant helper in this gem — `ClientCredentials.client_credentials` [5](#0-4) , `RefreshToken.refresh_access_token` [6](#0-5) , and even `TokenExchange.migrate_to_expiring_token` [7](#0-6)  — pass the shop string through `Utils::ShopValidator.sanitize!`, which enforces the value resolves to one of the `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) [8](#0-7) .

`TokenExchange.exchange_token`, however, takes `dest_shop = jwt_payload.shop` straight from the decoded JWT and skips this validation entirely before constructing the credential-bearing request [9](#0-8) . The `dest` claim is only checked for `aud == Context.api_key` and standard JWT time bounds (`exp`/`nbf`) inside `JwtPayload#initialize` [10](#0-9)  — there is no check that `dest`/`iss` is actually a `*.myshopify.com`/`*.myshopify.io`/etc. host. This breaks the intended binding: `shop the token authenticates for == shop that is trusted to receive the client_secret`. Any signer of a validly-signed session token (i.e., Shopify itself in the normal flow, or the app's own test/dev harness that signs JWTs with the shared `api_secret_key`) can set `dest` to an arbitrary hostname, and this gem will send the app's `client_id`/`client_secret` to that host in an HTTP POST — a credential-exfiltration/SSRF vector that the parallel `ShopValidator.sanitize!` calls in the sibling grant flows are specifically designed to prevent.

### Impact Explanation
If `dest_shop` can be influenced to a non-Shopify host, the gem performs an outbound POST containing the app's `client_secret` (and `subject_token`, itself a bearer-equivalent session token) to that host — directly matching the "High: SSRF with the app's credentials" / "credential leakage" impact categories. This is a straightforward inconsistency versus the gem's own established pattern (`sanitize!` used everywhere else a `shop` value reaches an HTTP client).

### Likelihood Explanation
Exploitation is gated on being able to produce, or otherwise obtain, a JWT whose `dest` claim differs from a legitimate merchant domain while still passing `aud`/`exp`/`nbf`/signature checks in `JwtPayload`. In the fully-legitimate flow, `dest` is set by Shopify itself, so a purely-remote unprivileged attacker cannot forge this without the `api_secret_key`. However, unlike the OAuth-callback HMAC (which independently binds the `shop` value the app already trusts), this path has zero defense-in-depth: it relies entirely on trusting the claim value's format, with no allow-list check that the rest of the codebase applies uniformly. This is best treated as a missing defense-in-depth control rather than a directly exploitable-by-outsider bug, since forging the JWT itself still requires the shared secret.

### Recommendation
Apply `Utils::ShopValidator.sanitize!(dest_shop)` to the value returned by `jwt_payload.shop` in `TokenExchange.exchange_token` before using it to build `shop_session`/the outbound request, matching the pattern already used in `ClientCredentials`, `RefreshToken`, and `TokenExchange.migrate_to_expiring_token`.

### Proof of Concept
Not independently reproducible as a remote, credential-free attack: exploitation requires a validly HMAC-signed JWT (signed with the app's `api_secret_key`) whose `dest` claim points to an attacker-controlled host, which is outside the threat model of an unprivileged internet user with no credentials. This is reported as a code-consistency / defense-in-depth gap rather than a confirmed end-to-end exploit.
