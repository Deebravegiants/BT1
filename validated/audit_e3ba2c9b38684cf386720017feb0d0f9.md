### Title
Unchecked ERC20 return value on token payouts allows silent transfer failure / fund freeze in Tron IntentGatewayV2 - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The `IntentGatewayV2` contract deployed for Tron (`evm/tron/contracts/apps/IntentGatewayV2.sol`) uses raw low-level `.call()` invocations of the ERC20 `transfer` selector to pay out escrowed funds in `withdraw()` and `SweepDust` handling, instead of `SafeERC20.safeTransfer` (which the rest of the codebase, including the EVM `IntentGatewayV2.sol` and `IntentsBase.sol`, consistently uses). This mirrors the reported `ERC20Wrapper.checkSuccess` bug class: it only checks the boolean `success` returned by the low-level `call` (i.e., that the callee didn't revert), but never inspects/decodes the actual ABI-encoded return data to confirm the token itself reported `true`.

### Finding Description
In `withdraw()`: [1](#0-0) 

and in the `SweepDust` request handler: [2](#0-1) 

Both sites do:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
This checks only that the external call did not revert. It never decodes the return data to verify that the ERC20 `transfer` actually returned `true`. Per the reported bug class, this is exactly the risk the external report warns about: non-conforming/edge-case tokens (e.g., tokens that return `false` on failure instead of reverting — common among various TRC20/legacy ERC20 tokens, which is precisely why this Tron-specific fork exists) will make the call succeed (`success == true`) while the token transfer itself silently fails.

Critically, the internal escrow accounting in `withdraw()` unconditionally decrements `_orders[body.commitment][token] -= amount;` regardless of whether the token's own return value indicated success: [3](#0-2) 

So if the token returns `false` without reverting, the contract believes the beneficiary was paid and finalizes/decrements escrow (`_filled[body.commitment] = beneficiary` is also set unconditionally at the top of `withdraw`), but the beneficiary never received the tokens. The escrowed value becomes permanently unaccounted for — the accounting says it's gone, but the tokens are still stuck in the contract with no order left to reclaim them (the order is marked filled/refunded already), a permanent freeze of funds from the beneficiary's perspective.

Note the EVM-mainline `IntentsBase.sol._withdraw` (used by `IntentGatewayV2.sol` on standard EVM chains) correctly uses `SafeERC20.safeTransfer`, which decodes and validates the return value: [4](#0-3)  The Tron variant deviates from this pattern specifically at the payout sites, reintroducing the exact `checkSuccess`-style validation gap the external report describes.

### Impact Explanation
`withdraw()` is reached via `onAccept` for `RedeemEscrow`/`RefundEscrow` requests (relayed cross-chain fill/cancel messages) and via `onGetResponse` for cancellation-by-proof — both are triggered by ordinary relayers delivering ISMP messages, not privileged actors. A solver/user whose order is filled or refunded against a non-conforming token (returns `false` instead of reverting on failure, e.g., insufficient balance/allowance edge cases in some TRC20 tokens) will have their escrow silently zeroed out and marked filled while the tokens remain trapped in the contract — a permanent loss/freeze of escrowed user or solver funds. The same gap applies to protocol `SweepDust` payouts and fee redemption at [5](#0-4) .

### Likelihood Explanation
Likelihood is elevated specifically because this is the Tron deployment: Tron's TRC20 ecosystem is known for tokens with non-standard `transfer` return semantics (some historically return no data or `false` under overflow/failure conditions rather than reverting, which is the entire reason `checkSuccess`/wrapper patterns exist). Any whitelisted token with such behavior, or any future integration of a non-conforming token, triggers this path with a single ordinary relayed fill/refund/cancel — no attacker privilege needed beyond normal solver/relayer participation.

### Recommendation
Replace all `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` payout sites in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw`'s escrow payout, the fee redemption, and the `SweepDust` handler) with `SafeERC20.safeTransfer`, which is already imported and used elsewhere in the same file (`using SafeERC20 for IERC20;`), so that a token's actual boolean return value (when present) is decoded and validated, consistent with `IntentsBase.sol`'s implementation on standard EVM chains.

### Proof of Concept
1. Whitelist/accept an ERC20-like token on Tron whose `transfer` function returns `false` (does not revert) when the internal transfer condition fails (e.g., a fee-charging or pausable token variant, or one hitting an edge-case branch that returns `false`).
2. A user places an order and escrows this token via `placeOrder`; a solver fills it, or the order times out/cancels.
3. The corresponding `RedeemEscrow`/`RefundEscrow` message is relayed and delivered to `onAccept`, invoking `withdraw(body, ...)`.
4. `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` (call didn't revert) but the token's internal logic returned `false` and moved no funds.
5. `_orders[body.commitment][token] -= amount` executes and `_filled[body.commitment] = beneficiary` is set — escrow accounting shows the order settled, `EscrowReleased`/`EscrowRefunded` is emitted — yet the beneficiary's balance is unchanged and the tokens remain stuck in the contract with no reachable code path to reclaim them.
