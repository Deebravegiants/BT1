## Title
Missing zero-shares-minted validation in vault `deposit` allows depositor principal to be donated to existing shareholders after debt socialization drains a vault's assets — (File: `contracts/vault/vault-stx.clar` and equivalent vault contracts)

### Summary
Every Zest vault contract (`vault-stx`, `vault-sbtc`, `vault-ststx`, `vault-usdc`, `vault-usdh`, `vault-ststxbtc`, present in both `local-testing/contracts/vault/*.clar` and `mainnet/contracts/vault/v0-vault-*.clar`) implements a share-minting `deposit` function and a share-burning `redeem` function that are supposed to be symmetric with respect to zero-output validation. `redeem` explicitly rejects a zero-value conversion result, but `deposit` does not, even though both rely on the exact same conversion helper that can legitimately return `u0`.

### Finding Description
`convert-to-shares-preview` returns `u0` whenever total-supply (`ts`) is non-zero but total-assets (`ta`) is zero: [1](#0-0) 

`total-assets`/`total-assets-preview` is derived from the internal `assets` ledger variable plus unrealized interest: [2](#0-1) 

The `assets` variable can be driven to `u0` by `socialize-debt` (invoked when bad debt is written off) without burning any outstanding `zft` shares — it only zeroes the backing, leaving `total-supply` (`ts`) untouched: [3](#0-2) 

Once `ta == 0` and `ts > 0`, any subsequent `deposit` computes `inkind` (shares to mint) as `u0`. `deposit` checks `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` — trivially satisfied if the caller/UI supplies `min-out = 0` — but, unlike `redeem`, never asserts `inkind > 0`: [4](#0-3) 

Contrast this with `redeem`, which explicitly guards the same class of failure with `ERR-OUTPUT-ZERO`: [5](#0-4) 

This is structurally the same bug class as the Trail of Bits `LoanState`/`LoanFactoryBase` finding: a validation invariant ("the conversion output must be non-zero") is enforced in one code path (`redeem`) via an explicit check, and the codebase implicitly assumes it is enforced everywhere the shared helper (`convert-to-shares-preview`/`convert-to-assets-preview`) is used — but the symmetric path (`deposit`) forgot to call/assert it. The identity that breaks is:

```
ΔtotalSupply(shares minted) * (ta / ts) == ΔtotalAssets(amount deposited)
```

When `inkind = 0` but `amount > 0`, `var-set assets (+ current-assets amount)` still increases backing assets while `ft-mint? zft inkind recipient` mints zero shares to the depositor: [6](#0-5) 

The depositor's real underlying tokens are absorbed into the vault's `assets` ledger, silently increasing the per-share backing (`ta`) for every pre-existing `zft` holder, while the depositor receives nothing in return — an unrecoverable transfer of the depositor's principal to other shareholders.

### Impact Explanation
This is direct theft of a user's principal: the depositor transfers real underlying tokens into the vault (`receive-underlying`) and permanently receives zero shares (no `zft` minted), while the value is retained by the vault and accrues to other, unrelated shareholders. This meets the Critical bar of "direct theft of user funds at rest or in motion."

### Likelihood Explanation
The precondition (`ta == 0`, `ts > 0`) is reachable through the protocol's own permissioned bad-debt socialization flow (`socialize-debt`), which is a normal, expected liquidation/insolvency-handling mechanism rather than a DAO compromise or an oracle failure caused externally — it only requires that the vault's tracked assets be fully written down while shares remain outstanding. From that point, any ordinary, unprivileged user calling `deposit` (particularly if their client/UI passes `min-out = 0`, which is a common default for a "no slippage protection" call) will silently lose their entire deposited amount. No special privileges or governance action are required to trigger the loss once the precondition exists.

### Recommendation
Add an explicit zero-output check to `deposit`, symmetric to the one already present in `redeem`:
```clarity
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
in `deposit` for every vault contract (`vault-stx.clar`, `vault-sbtc.clar`, `vault-ststx.clar`, `vault-usdc.clar`, `vault-usdh.clar`, `vault-ststxbtc.clar`, and their `mainnet/contracts/vault/v0-vault-*.clar` counterparts), immediately after computing `inkind`. More generally, keep the "non-zero conversion output" validation co-located with every call site of `convert-to-shares-preview`/`convert-to-assets-preview` rather than relying on it being enforced only in some of the functions that use it.

### Proof of Concept
1. Vault `V` has non-zero `total-supply` (some LPs hold `zft`) and non-zero outstanding debt.
2. The associated market fully socializes bad debt for `V` via `socialize-debt`, driving `current-assets` (and hence `total-assets-preview`) to `u0` while `total-supply` remains `> 0` (see `local-testing/contracts/vault/vault-stx.clar:944-967`).
3. A user (Alice) calls `deposit(amount, min-out=0, recipient=Alice)` with `amount > 0`.
4. `convert-to-shares-preview` computes `ts != 0` and `ta == 0`, returning `inkind = u0` (`local-testing/contracts/vault/vault-stx.clar:308-315`).
5. `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` passes since `0 >= 0`.
6. `receive-underlying` pulls `amount` of Alice's tokens into the vault; `ft-mint? zft inkind recipient` mints `0` shares to Alice; `var-set assets (+ current-assets amount)` increases the vault's backing by `amount` (`local-testing/contracts/vault/vault-stx.clar:779-783`).
7. Alice has permanently lost `amount` of principal with no shares to redeem it, while all other `zft` holders now have a higher per-share backing.

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)
