### Title
Webhook `shop` field is not covered by the HMAC signature, allowing forged/replayed webhooks to be attributed to an arbitrary shop - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the request body's HMAC signature, but the `shop` domain that identifies which tenant the webhook belongs to is taken from an unsigned HTTP header. Because the HMAC secret (`Context.api_secret_key`) is a single, app-wide secret shared across every shop that has the app installed, any merchant who installs the app can obtain a validly-signed webhook body for their own shop and replay it against the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header changed to point at a victim shop. The equality the code should enforce — "shop the HMAC was computed for" == "shop the handler acts on" — is never checked.

### Finding Description
`Request#to_signable_string` returns only the raw request body: [1](#0-0) 

The `shop` accessor instead reads directly from an HTTP header that is never included in that signable string: [2](#0-1) 

`HmacValidator.validate` only verifies `verifiable_query.to_signable_string` (the body) against the secret — it has no knowledge of, and does not bind, the `shop` header: [3](#0-2) 

`Registry.process` performs exactly this check-then-use pattern: it validates the HMAC of the body, then immediately trusts `request.shop` (the unauthenticated header) to build the data handed to the app's handler: [4](#0-3) 

`WebhookMetadata.shop` is documented and typed as a trusted field passed straight to the app's handler: [5](#0-4) 

Since `Context.api_secret_key` is one value shared by the app across all installed shops (it is not derived per-shop), any tenant that has legitimately received one signed webhook body can replay that exact body/HMAC pair while substituting a different `shop` header value. `HmacValidator.validate` will still return `true` because it never inspects the `shop` header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload originated from an arbitrary victim shop.

This is the same bug class flagged in the external report (a value that drives processing — there the number of requests/withdrawal id, here the tenant identity — is not the value that is actually authenticated), mapped onto this gem's identity-binding surface: "a field acted on but not covered by the HMAC."

### Impact Explanation
This breaks the tenant boundary the gem is responsible for enforcing at the webhook ingestion point: `hmac-authenticated shop == shop acted upon` does not hold. A merchant who installs the app on their own store (an unprivileged actor with respect to other merchants) can forge webhook events that the app's handler will process as if they came from a different, victim shop — i.e., cross-tenant data injection/corruption at the boundary this gem is expected to guard, since apps rely on `data.shop` from `WebhookMetadata` to route webhook processing to the correct tenant record.

### Likelihood Explanation
Exploitation only requires: (1) installing the app on an attacker-controlled shop to receive at least one legitimately signed webhook (trivial, since app installation is generally open to any Shopify merchant), and (2) POSTing the captured raw body and HMAC header to the app's public webhook endpoint with a modified shop-domain header. No access to `api_secret_key`, access tokens, or any privileged credential is required.

### Recommendation
Include the shop domain in the value that is HMAC-verified, or otherwise cryptographically bind the shop claim to the specific delivery — for example, require the caller to supply a shop identity that is cross-checked against a value carried inside the authenticated payload (Shopify webhook bodies include the shop's numeric ID), or maintain a per-shop webhook secret/registration record and validate that the delivered `webhook_id`/topic combination was actually registered for the shop claimed in the header before invoking the handler.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook delivery:
   - `x-shopify-hmac-sha256: <valid-hmac-of-body>`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - body: `{"id":123, ...}`
2. Attacker replays the exact same body and HMAC header to the app's public webhook endpoint, only changing:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `request.to_signable_string` (the untouched body) against `Context.api_secret_key`.
4. `WebhookMetadata.new(topic:, shop: request.shop, ...)` is constructed with `shop == "victim-shop.myshopify.com"`, and the app's handler processes it as a legitimate event for the victim shop.
