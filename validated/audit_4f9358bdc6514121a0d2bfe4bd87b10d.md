### Title
Webhook shop/topic/webhook_id headers are trusted without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking `Utils::HmacValidator.validate(request)` against `request.to_signable_string`, which returns only the raw request body. The `shop-domain`, `topic`, and `webhook-id` headers that the handler subsequently trusts as the authenticated origin of the event are never included in the signed bytes, so they can be freely substituted by anyone who can supply a body/HMAC pair.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns `@raw_body` only [1](#0-0) . `HmacValidator.validate` computes `HMAC-SHA256(client_secret, to_signable_string)` and compares it to the `hmac` accessor, which reads the `hmac-sha256` header [4](#0-3) [5](#0-4) . The `shop`, `topic`, and `webhook_id` accessors read separate, unsigned headers (`shop-domain`, `topic`, `webhook-id`) [2](#0-1) .

`Registry.process` only calls `Utils::HmacValidator.validate(request)` before dispatching to the handler, and then builds `WebhookMetadata` using `request.shop`, `request.topic`, and `request.webhook_id` taken directly from those unsigned headers [3](#0-2) . The identity binding that should hold is: `shop/topic/webhook_id verified by HMAC == shop/topic/webhook_id acted on by the handler`. Because only the body bytes are covered, this binding never actually holds — any request whose body+HMAC pair is valid for *some* topic/shop will pass validation regardless of which shop-domain, topic, or webhook-id headers are attached to it.

Concretely, since the HMAC is computed over the raw body only, and many webhook payloads for different shops/topics can have identical or attacker-influenced bodies (e.g., an app's own installed dev/test shop can trigger a webhook with a body the attacker fully controls, such as a metafield or order note field), an attacker who receives one legitimate `(body, hmac)` pair from Shopify for their own shop can replay that exact body and HMAC to the app's webhook endpoint while swapping the `shop-domain` header to the victim's shop domain and/or the `topic`/`webhook-id` headers. `HmacValidator.validate` still succeeds since it only checks the (unchanged) body, and the handler will process the forged request as if it authentically originated from the victim shop/topic.

### Impact Explanation
This breaks the shop-identity binding relied upon by any host application that keys per-shop side effects (data writes, redact/GDPR actions, order processing, tag updates, etc.) off `WebhookMetadata#shop`/`#topic`. An attacker can inject events attributed to a shop they do not operate, causing cross-tenant data confusion — the handler operates on data believed to belong to shop A while it was actually forged by an unrelated attacker controlling shop B. This matches the "cross-tenant access" impact category since the shop identity used for authorization/attribution of the webhook is not actually authenticated by the cryptographic check.

### Likelihood Explanation
Exploitation requires the attacker to control an app installation on some shop (any developer can create a free/dev Shopify store) and to have some influence over the body content of a webhook (many webhook topics carry attacker-writable fields such as order notes, product/metafield content, or customer fields). No access to the app's `client_secret` or existing merchant credentials is required — this is achievable by any unprivileged internet user with a Partner/dev account. This is a moderate-effort but realistic attack path.

### Recommendation
Include the authenticating headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or independently verify that the shop/topic in the request correspond to the shop/topic the app expects for that webhook subscription (e.g., by validating them against Shopify's registered webhook metadata rather than trusting client-supplied headers). At minimum, document that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are unauthenticated and must not be used for tenant-sensitive authorization decisions without additional verification.

### Proof of Concept
```ruby
# Attacker operates dev-shop.myshopify.com and receives a legitimate webhook
# for a topic whose body they control, e.g. "orders/create" with a note field.
# Shopify computes: hmac = HMAC-SHA256(client_secret, raw_body)
# and sends headers: x-shopify-shop-domain: dev-shop.myshopify.com
#                    x-shopify-topic: orders/create
#                    x-shopify-hmac-sha256: <valid hmac>

# Attacker replays the same raw_body + hmac to the target app's webhook
# endpoint, only changing the shop-domain header:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => captured_valid_hmac, # unchanged
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
  "x-shopify-webhook-id" => "forged-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_raw_body, headers: headers)

# HmacValidator.validate only checks captured_raw_body against captured_valid_hmac,
# which still matches -> validation passes.
ShopifyAPI::Webhooks::Registry.process(request)
# Handler is invoked with shop: "victim-shop.myshopify.com", believing the event
# genuinely originated from the victim shop.
```
