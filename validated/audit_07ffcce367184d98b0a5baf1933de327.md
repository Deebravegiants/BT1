### Title
Local success determination in `user_centric_signup` path bypasses backend enrollment verification - (File: `src/plans/mod.rs`)

### Summary
The reported `withdrawRedundant` bug class is: a conditional was written so that an "else"/fallback branch performs a broad, unguarded action instead of the narrower guarded action the code was intended to enforce. In `orb-core`, `MasterPlan::do_signup` contains a structurally analogous branch: when a signup is flagged `user_centric_signup`, the orb determines signup success **locally**, purely from its own `signup_reason` enum, instead of going through the same backend confirmation path (`enroll_user`/`signup_post`/`signup_poll`) used for all other signups.

### Finding Description
In `do_signup`, after the biometric pipeline and fraud pipeline run, the code branches on `user_centric_signup`: [1](#0-0) 

- If `user_centric_signup && !ignore_user_centric_signups`, the orb sets `enrollment_status` and computes `success` purely from the in-process `signup_reason` (`Normal`/`Fraud`/`Failure`) — it never calls `enroll_user::Plan::run`, i.e., it never contacts the signup backend (`signup_post`/`signup_poll`) to get server-side confirmation.
- Otherwise (the `else` branch), it calls `self.enroll_user(...)`, which posts to the backend and polls `signup_poll::request` for the authoritative completion/duplicate/fraud verdict (`Status::Success` requires `signup_poll::Response { success: true, error: None, status: Completed }`). [2](#0-1) 

This mirrors the `withdrawRedundant` bug pattern: instead of nesting the "safe" narrow condition *inside* the guard, the code created two disjoint top-level branches, and one of them (`user_centric_signup`) skips the check that the rest of the system relies on (server-side confirmation of uniqueness/fraud/liveness for that signup id) and substitutes a locally-derived boolean.

`signup_reason` itself is computed from `pipeline`/`detect_fraud` results: [3](#0-2) 

and in this build the fraud-detection engine has been stripped out entirely (`detect_fraud` always returns `Ok(false)`): [4](#0-3) 

so for a `user_centric_signup`, `fraud_detected` is always `false`, and `signup_reason` collapses to `Normal` as long as the pipeline produced a result — meaning `success` in the `user_centric_signup` branch is effectively determined by "did the biometric pipeline run," with no backend-side duplicate/fraud/liveness confirmation at all, unlike the non-user-centric path.

### Impact Explanation
If `user_centric_signup` is set for a signup, the orb self-certifies enrollment success without validating with the backend (`signup_post`/`signup_poll`), which is the system's actual source of truth for duplicate detection ("Backend duplicates", "Backend inflight matches", "Backend detected fraud" — see the comment block in `enroll_user.rs`): [5](#0-4) 
This is a state/authorization bleed: the orb-side `debug_report.enrollment_status`/`success` (used for reporting "successful signup" telemetry and UI flow) is decoupled from the backend's actual acceptance of that identity, and — combined with the fact that fraud checks are compiled out in this build — the "fraud" branch of `signup_reason` can never actually be reached, so the `user_centric_signup` path always reports success on pipeline completion. This can result in misattributed/unverified signups being marked successful without the backend-side enforcement that governs every other code path.

### Likelihood Explanation
`user_centric_signup` is populated from `authenticated_app_data.user_centric_signup` returned by the backend and is verified against a hash embedded in the user's QR code via `user_data.verify(user_data_hash)`: [6](#0-5) 
This makes the flag part of the normal, reachable user-signup flow (not a test-only or admin-only path) — every signup where the backend/app opts into user-centric mode takes this branch, and the branch is reached unconditionally whenever `!ignore_user_centric_signups` (the default posture is not verifiable from the indexed files, but the branch exists in production code paths, gated only by ordinary config, not a privileged/test feature flag).

### Recommendation
Restructure the logic so that the "user-centric" determination is nested inside the same server-verification path rather than being a parallel branch that skips it — analogous to the report's fix for `withdrawRedundant`:
```rust
let success = Box::pin(self.enroll_user(orb, debug_report, &capture, pipeline.as_ref(), signup_reason))
    .await
    .is_success();
if user_centric_signup && !orb.config.lock().await.ignore_user_centric_signups {
    // adjust reporting/UI behavior only, but still require backend confirmation
}
```
At minimum, ensure that any locally-derived `success`/`enrollment_status` for `user_centric_signup` signups cannot short-circuit the backend duplicate/fraud verification that the non-user-centric path enforces, and re-enable/restore the fraud-detection pipeline (`detect_fraud`) so `signup_reason` cannot trivially collapse to `Normal`.

### Proof of Concept
1. Complete a biometric capture/pipeline normally so `pipeline.is_some()`.
2. Have the backend/app mark the signup as `user_centric_signup = true` (verified via the QR `user_data_hash`, a normal unprivileged user/app flow).
3. Because `detect_fraud` unconditionally returns `false` in this build (`src/plans/mod.rs:1390-1406`), `signup_reason` becomes `SignupReason::Normal`.
4. In `do_signup`, the `user_centric_signup` branch sets `success = (signup_reason == SignupReason::Normal) = true` without ever calling `enroll_user`/contacting the backend for confirmation (`src/plans/mod.rs:639-656`).
5. The orb reports `signup_successful` / increments `main.count.signup.result.success.successful_signup` even though the backend never confirmed uniqueness, liveness, or fraud status for this signup.
