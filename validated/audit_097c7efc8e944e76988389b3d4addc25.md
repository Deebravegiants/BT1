### Title
Multi-token escrow withdrawal reverts atomically on a single bad token, permanently freezing all other escrowed funds - (File: `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The IntentGateway's escrow-release path (`_withdraw` in `IntentsBase.sol` and `withdraw` in the Tron `IntentGatewayV2.sol`) settles an order's multiple input tokens in a single loop with no isolation between transfers. If a single one of the order's input tokens fails to transfer (blacklisted beneficiary, paused/frozen token, non-standard revert-on-condition ERC20), the entire withdrawal reverts, permanently blocking release of *all* other tokens escrowed for that order as well.

### Finding Description
`_withdraw` iterates `body.tokens` and calls `IERC20(token).safeTransfer(beneficiary, amount)` for each token in the withdrawal request, decrementing escrow before each transfer: [1](#0-0) 

The Tron variant does the same with a raw low-level `.call` that still reverts (`TransferFailed()`) if the token's `transfer` returns false or the call fails: [2](#0-1) 

This function is invoked from `onAccept()` when Hyperbridge delivers a `RedeemEscrow` or `RefundEscrow` cross-chain message (reachable by any relayer submitting a proof for a message that originated from an ordinary user's `fillOrder`/`cancelOrder` call), and from `onGetResponse()` for the same-chain cancel-from-source flow: [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

Orders can escrow multiple distinct input tokens (`order.inputs` is an array), all committed to the same `commitment` and released atomically in a single `_withdraw`/`withdraw` call. If the beneficiary address (the order's `user` for refunds, or the filling solver for redemptions) becomes non-compliant for even one of these tokens — e.g. added to a USDC/USDT blacklist, the token contract is paused, or the token simply reverts under some condition specific to that account — the single failed `transfer` call reverts the *whole* function, since there is no per-token isolation (no try/catch, no partial success accounting). Because the escrow decrement (`_orders[...] -= amount`) happens in the same loop iteration as the transfer, a reattempt of the same message delivery will hit the identical revert every time, since neither the blacklist status nor the escrowed balance changes between retries.

This is the direct analog of the reported issue: in the original report, `MintingHub.sol#end()` bundles several unrelated fund movements (challenger collateral return, reward, bidder refund, owner refund) in one call, so one failing leg (e.g., 0-amount ERC20 revert, `transfer` to `address(0)`) blocks all the others. Here, the equivalent bundling failure point is the per-order, multi-token settlement loop in `_withdraw`/`withdraw`, reached through the ISMP message-delivery path (`onAccept`) rather than a single hub call, but with the same root cause: one non-compliant token asset dooms the settlement of every other unrelated token in the same order.

### Impact Explanation
Because escrow decrement and transfer happen together per token and the whole call reverts on any single failure, and because a relayer/host retry of the same message will deterministically hit the same revert, the order's cross-chain settlement message (`RedeemEscrow`/`RefundEscrow`) becomes permanently undeliverable. All tokens escrowed for that order — not just the problematic one — are permanently frozen: they can never be released to the solver on a fill, nor refunded to the user on a cancellation, since both paths go through the same atomic `_withdraw`/`withdraw`. This is a permanent freezing-of-funds condition and, from the ISMP perspective, a route that becomes unable to deliver a specific message indefinitely.

### Likelihood Explanation
Likelihood is moderate: it requires a beneficiary (order user or filling solver) to become non-compliant with one of several escrowed/output tokens after order placement (e.g., blacklisted by a centralized-issuer stablecoin, or the token pausing), which is a realistic and externally-triggerable event for common tokens like USDC/USDT. No malicious admin, governance, or node behavior is required — an ordinary user placing a multi-token order and later being blacklisted on one token (by that token's own issuer, entirely outside Hyperbridge's control) suffices to permanently lock the order's other tokens.

### Recommendation
Avoid bundling multiple unrelated token transfers into a single all-or-nothing call reachable from cross-chain message delivery. Either:
- Make `_withdraw`/`withdraw` resilient per-token: wrap each token transfer in a try/catch (or use a low-level call and record failures), and route amounts of failed transfers into a per-user pull-based claim mapping (analogous to `SweepDust`) instead of reverting the whole loop; or
- Process each input token as an independent settlement unit (separate escrow entries settled individually) so a stuck token cannot block release of the others.

### Proof of Concept
1. User places a cross-chain order with two input tokens escrowed: a normal ERC20 (`TokenA`) and a compliance-gated stablecoin (`TokenB`, e.g., USDC-like with a blacklist), via `placeOrder`.
2. Before the order is filled or cancelled, the user's address is added to `TokenB`'s blacklist by its issuer (an event entirely outside the protocol's control).
3. A solver fills the order on the destination chain; `fillOrder` dispatches a `RedeemEscrow` request back to the source chain.
4. A relayer delivers the message; the host calls `onAccept()` → `_authenticate` → `_withdraw(body, false, true)`.
5. In `_withdraw`'s loop, the transfer of `TokenA` to the solver succeeds and decrements escrow, but the subsequent `IERC20(TokenB).safeTransfer(beneficiary, amount)` reverts because the solver/beneficiary is blacklisted for `TokenB`.
6. The whole `_withdraw` call reverts, so `TokenA`'s escrow decrement is rolled back along with everything else; the entire message-delivery transaction reverts.
7. Every subsequent relayer retry of the same message hits the identical revert (blacklist status does not change), permanently freezing both `TokenA` and `TokenB` escrow for this order — even though only `TokenB` was ever problematic.
