### Title
Unbounded ancestry walk over unauthenticated relayer-supplied headers enables infinite-loop/OOM DoS in GRANDPA finality proof verification - (File: modules/consensus/grandpa/primitives/src/justification.rs)

### Summary
The GRANDPA `AncestryChain::ancestry` routine walks a `BTreeMap` of attacker-supplied headers by following `parent_hash` pointers until it reaches a `base` hash, with no cycle detection, no depth bound, and no signature/authenticity check performed before the walk. Because both `unknown_headers` (raw headers) and their `parent_hash` fields are fully attacker-controlled at the point this walk runs, a relayer can craft two or more headers whose `parent_hash` fields point at each other, creating a cycle that never reaches `base`. This is directly analogous to the reported CVE class: crafted structured input drives an internal graph/tree walk into unbounded work, causing a Denial of Service.

### Finding Description
`AncestryChain::ancestry` is defined as: [1](#0-0) 

```
fn ancestry(&self, base: H::Hash, block: H::Hash) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
    let mut route = vec![block];
    let mut current_hash = block;
    while current_hash != base {
        match self.ancestry.get(&current_hash) {
            Some(current_header) => {
                current_hash = *current_header.parent_hash();
                route.push(current_hash);
            },
            _ => return Err(finality_grandpa::Error::NotDescendent),
        };
    }
    Ok(route)
}
```

`self.ancestry` is built directly from the relayer-supplied `finality_proof.unknown_headers` with no validation of header authenticity or internal consistency: [2](#0-1) 

The verifier, `verify_grandpa_finality_proof`, calls `headers.ancestry(...)` on this unauthenticated map *before* the GRANDPA justification signatures are checked: [3](#0-2) 

```
let headers = AncestryChain::<H>::new(&finality_proof.unknown_headers);
...
let base = finality_proof.unknown_headers.iter().min_by_key(|h| *h.number())...;
if base.number() < &consensus_state.latest_height {
    headers.ancestry(base.hash(), consensus_state.latest_hash)...
}
let finalized = headers.ancestry(from, target.hash())...;
// 2. verify justification.
justification.verify(...)...
```

Because `parent_hash` is just a field inside an arbitrary, attacker-crafted header (no relation to the actual cryptographic hash of another header is enforced at this stage), a submitter can construct two headers `A` and `B` where `A.parent_hash = hash(B)` and `B.parent_hash = hash(A)`, forming a 2-cycle. If `target.hash()` (the max-by-number header) or the walk from `from`/`consensus_state.latest_hash` enters this cycle without ever reaching `base`, the `while` loop never terminates: on every iteration `self.ancestry.get(&current_hash)` succeeds (both cycle members are present in the map), so the function never returns `Err(NotDescendent)`, and `route` grows without bound, consuming unbounded memory as it spins.

This entry point is reached via the pallet-ismp unsigned extrinsic `handle_unsigned`, which wraps a `Message::Consensus(ConsensusMessage)` and is validated for free by every node's transaction pool (`validate_unsigned`), executing the full consensus verification path (including this ancestry walk) before any economic cost is paid: [4](#0-3) [5](#0-4) 

The documentation explicitly states this class of extrinsic runs for free and relies on "validity check" filtering to prevent congestion: [6](#0-5) 
— but that validity check is exactly the code path containing the unbounded loop, so the "filter" itself is the DoS surface.

### Impact Explanation
Any node (validator, full node, or light client running the same verifier) that processes this unsigned extrinsic — whether during mempool validation or execution — enters an unbounded loop with unbounded memory growth. This can hang or OOM-crash the node's runtime execution thread, which is a Denial of Service against the ISMP/GRANDPA consensus-client update path, affecting delivery of all cross-chain messages routed through that consensus client. Since `validate_unsigned` runs on every node that receives the gossiped extrinsic (not just the block author), a single crafted extrinsic can propagate and DoS the network broadly. This matches the "route unable to deliver messages" / "sustained crash or unbounded resource usage" impact categories.

### Likelihood Explanation
High. No signature, staking, or privileged role is required to submit `handle_unsigned` — it is explicitly an unsigned, permissionless, free extrinsic. The attacker fully controls the SCALE-encoded `H` header type's `parent_hash` field and `number` field independently, making constructing a 2-header cycle with an attacker-chosen "highest number" trivial. The only precondition is that a supported GRANDPA consensus client exists for the target state machine (a normal, expected deployment condition), and that `min_by_key`/`max_by_key` header selection resolves to headers that participate in the crafted cycle — both are straightforward for an attacker to arrange since they fully control the header set contents.

### Recommendation
- Bound `unknown_headers`/the ancestry walk to a fixed maximum depth (e.g., matching `max_block_range` already used by the honest prover) and reject proofs exceeding it before walking.
- Track visited hashes in `ancestry()` (a `BTreeSet`) and return an error immediately if a hash is revisited, preventing infinite loops regardless of size limits.
- Consider deferring the ancestry walk until after `justification.verify(...)` succeeds, or otherwise avoid running unbounded graph traversal over unauthenticated data in the transaction-pool validation path.

### Proof of Concept
Conceptual (no live proof source, but derivable directly from the code path above):
1. Craft header `B` with `number = N`, arbitrary fields, and `parent_hash = hash(A)` (to be fixed once `A` is built).
2. Craft header `A` with `number = N+1` (highest, so it becomes `target`), and `parent_hash = hash(B)`.
3. Set `finality_proof.unknown_headers = [A, B]`, `finality_proof.block = hash(A)`, and any (even bogus) `justification` bytes — the loop triggers before justification decoding/verification matters for the initial `ancestry` calls reachable via `base.number() < consensus_state.latest_height` or via `from`/`target.hash()` not directly connecting to `base`/`from`.
4. Submit as `Message::Consensus(ConsensusMessage { ... })` inside `pallet_ismp::Call::handle_unsigned { messages: vec![msg] }` as an unsigned extrinsic.
5. On any node that validates/executes this extrinsic, `AncestryChain::ancestry` enters the `A -> B -> A -> B -> ...` cycle, `route` grows unbounded, and the call never returns — causing the executing thread to hang/OOM.

Note: I was unable to execute this PoC in a sandbox; the analysis is based on static code review of the cited functions and their call graph. Confirming exact runtime crash behavior (OOM vs. weight-limited abort under the fixed weight metering, if any is applied before this point) would benefit from execution in a Devin session with access to the full test harness.

## Transaction fees

Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free as unsigned transactions. The upside to this is that it cannot be exploited as a spam vector, since the transaction pool will check if the submitted extrinsics are valid before they are included in the pool. This validity check ensures that the transaction can be successfully executed and contains valid proofs. Malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing and potential network congestion.
