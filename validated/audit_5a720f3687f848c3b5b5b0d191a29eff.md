### Title
`msg.value` credited once per duplicate `address(0)` entry in `erc20TokenAddresses`, allowing unbacked shielded ETH minting - (File: `contracts/Hinkal.sol`)

### Finding Description
The invariant that should hold is:

`Σ balanceDif_i (over duplicate address(0) entries) == actual ETH received by the contract in this call (msg.value) + any net internal ETH transfer`

In `Hinkal.transact`, for every entry `i` of `circomData.erc20TokenAddresses` equal to `address(0)`, the balance-diff correction adds `msg.value` unconditionally per iteration: [1](#0-0) 

This correction exists because `msg.value` is already reflected in `address(this).balance` at the moment `oldBalances` is snapshotted (line 78), so a single `+ msg.value` term is needed to recover the pre-call balance for one ETH-denominated slot. [2](#0-1) 

Nothing in `dimensionsCheck`, `checkOnchainCreation`, or `performHinkalChecks` enforces that `circomData.erc20TokenAddresses` contains unique addresses. [3](#0-2)  An attacker can therefore submit `erc20TokenAddresses = [address(0), address(0), ...]`, `amountChanges` and matching output UTXOs for each duplicate index. For each duplicated index, `oldBalances[i]` and `newBalances[i]` are identical (same global ETH balance snapshot taken once via `getBalancesForArray`), so `balanceDif` at every duplicate index equals `realDelta + msg.value` — the full `msg.value` is added again at each occurrence instead of being split/attributed once.

The subsequent per-index balance equation check then independently validates, for each duplicate index, that this inflated `balanceDif` equals `amountChanges[i] + utxoAmount_i`: [4](#0-3) 

Since the check is applied per array index rather than per unique token, an attacker who sends `X` wei of `msg.value` and lists `address(0)` twice can back two independent sets of shielded output UTXOs (or `amountChanges` + UTXO combinations) each up to `~X` in value — minting up to `2X` of shielded ETH backed by only `X` real wei transferred into the contract. Because circuit-side constraints (`inTotal + amountChanges === outTotal`) operate per index in the same way, the ZK circuit does not prevent duplicate token-address indices either — the attacker generates their own valid proof for their own chosen `CircomData`, satisfying the circuit's per-index arithmetic without any global token-uniqueness constraint.

### Impact Explanation
This allows an unprivileged attacker to mint shielded ETH UTXOs (or claim `amountChanges` credit) that exceed the actual ETH deposited into the Hinkal contract, directly causing protocol insolvency — matching the Critical category "minting shielded value without backing." The exploit is repeatable per transaction and scales with the number of duplicate `address(0)` entries the attacker includes (bounded only by array-length/dimension limits), each multiplying the effective ETH credit by the duplication count.

### Likelihood Explanation
- Preconditions: attacker only needs to call `transact` with a self-crafted `CircomData`/proof; no privileged role, whitelisted relay, or victim funds are required (self-serve deposit case, `relay == address(0)`, `originalSender == msg.sender`).
- No uniqueness constraint exists in `dimensionsCheck`/`checkOnchainCreation`/`performHinkalChecks` to reject duplicate `erc20TokenAddresses` entries.
- Attacker cost is just the gas plus generating a locally valid proof for their own crafted circuit inputs (explicitly within attacker capabilities per rules).
- Fully repeatable, limited only by max dimensions allowed by the circuit/verifier.

### Recommendation
Enforce uniqueness of `circomData.erc20TokenAddresses` in `dimensionsCheck` (or a dedicated check in `performHinkalChecks`), rejecting the transaction if any address (including `address(0)`) appears more than once. Alternatively, apply the `+ msg.value` correction exactly once globally (e.g., precompute it before the loop and only add it at the first `address(0)` occurrence, or refactor to compute `balanceDif` per unique token rather than per array slot).

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal` with mocked verifier/helper (or generate a real proof locally with snarkjs for a circuit input where `erc20TokenAddresses = [address(0), address(0)]`, `onChainCreation = [false, false]`, `amountChanges = [X, X]`, and two output UTXOs of amount `X` each with `erc20Address = address(0)`).
2. Call `transact{value: X}(...)` with this `circomData`.
3. Assert: before the call, record `address(hinkal).balance == B0`. After the call, `address(hinkal).balance == B0 + X` (only `X` wei actually received).
4. Assert: sum of newly inserted ETH-denominated commitments/UTXO amounts == `2X` (or `amountChanges` sum == `2X`), i.e., `mintedShieldedETH (2X) > actualBalanceDelta (X)`, proving the equality `Σ balanceDif == msg.value` is broken and unbacked value was minted.
