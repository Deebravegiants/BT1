## Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs (for HMAC validation purposes) only the raw request body, while the `shop` (and `topic`/`webhook_id`/`api_version`) values are read directly from unauthenticated HTTP headers. `Utils::HmacValidator.validate` only proves that the *body* was signed by the app's shared `client_secret` — it proves nothing about which shop the header claims the request came from. Since the same `client_secret` is used for HMAC signing across every shop that has the app installed, an attacker who legitimately receives one signed webhook (e.g. by installing the app on their own shop) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header of a victim shop, and the signature will still validate.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `to_signable_string` (i.e. the body only) and compares it to the `hmac-sha256` header value — it never binds the `shop` header into the signature: [3](#0-2) 

`Webhooks::Registry.process` trusts this unauthenticated `shop` value once the (body-only) HMAC check passes, and forwards it straight to the app's handler as the tenant identity: [4](#0-3) 

This breaks the intended identity binding: `HMAC-verified(body, client_secret) == HMAC-verified(body, client_secret) AND shop == request.shop` is expected, but the gem only enforces the first half. The `shop` field is "acted on but not covered by the HMAC" — exactly the class of binding failure called out as in-scope.

### Impact Explanation
Because `client_secret` is shared by the app across all shops (not shop-specific), any unprivileged user who installs the app on their own shop can capture a validly-signed webhook (body + `hmac-sha256`). They can then send that same body/HMAC pair to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to any victim shop that also has the app installed. `Registry.process` will pass HMAC validation and hand the handler a `WebhookMetadata` claiming to be from the victim shop: [5](#0-4) 

Any host application logic that uses `request.shop`/`WebhookMetadata#shop` to look up or act on a specific merchant's session, access token, or data (the gem's own documented/intended usage pattern for `Registry.process`) will act on the wrong tenant — this is a cross-tenant access primitive, satisfying the "Critical - cross-tenant access" bar.

### Likelihood Explanation
The attacker only needs the ability to install the target app on a shop they control (an unprivileged action any Shopify user can perform) and network access to the app's webhook endpoint — no leaked secrets, tokens, or privileged access are required. Capturing a self-triggered webhook and replaying it with a modified header is trivial once the app is installed.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed payload, or otherwise cryptographically bind the `x-shopify-shop-domain` header to the signed body before trusting it in `Registry.process`/`WebhookMetadata`. At minimum, document that host applications must independently verify `shop` against a shop known to have installed the app (via a stored session) rather than trusting the header value directly.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; capture a delivered webhook's raw body and its `x-shopify-hmac-sha256` value (both are valid because Shopify signed them with the shared `client_secret`).
2. Also install the app on/target a victim shop `victim.myshopify.com` (victim's install is legitimate; attacker doesn't need its secret).
3. Send a POST to the app's webhook endpoint with the identical captured raw body and `x-shopify-hmac-sha256`, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `HmacValidator.validate` passes (it only hashes `@raw_body`), and `Registry.process` invokes the handler with `shop: "victim.myshopify.com"`, causing the app to act as though the event originated from the victim tenant. [4](#0-3) [6](#0-5)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
