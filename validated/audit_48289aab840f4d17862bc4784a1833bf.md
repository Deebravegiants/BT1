## Title
Reward amount is read from mutable governance storage at claim-time rather than snapshotted at delivery-time, permanently destroying already-earned relayer rewards - ([File: modules/pallets/relayer/src/outbound_request.rs], [File: modules/pallets/relayer/src/outbound_consensus.rs])

### Summary
`pallet-relayer`'s outbound-delivery reward claims (`claim_outbound_request_delivery_reward` and `claim_outbound_consensus_delivery_reward`) compute the payout by reading the *current* value of `OutboundRequestDeliveryReward` / `OutboundConsensusDeliveryReward` at the moment the claim is processed, not the value that was in effect when the relayer actually performed the delivery being rewarded. If governance changes (lowers or zeroes) that reward between the time a relayer delivers a message/proof and the time it submits its claim, the relayer permanently loses the reward it already earned for completed work — the same "claimable resets to zero and can never be recovered" pattern described in the external H-02 report for `Voter.killGauge`/`reviveGauge`.

### Finding Description
Both reward-claim paths follow the same shape: an unprivileged relayer submits an unsigned extrinsic carrying a state proof of delivery, and the pallet looks up the reward to pay from a governance-controlled `StorageMap` at the time the claim extrinsic executes: [1](#0-0) [2](#0-1) 

The reward values themselves are pure governance-mutable state, overwritten unconditionally and with no history/snapshot per in-flight delivery: [3](#0-2) [4](#0-3) 

The relayer's actual work — delivering the mandatory consensus rotation to the destination `EvmHost`, or delivering a hyperbridge-originated request — is proven entirely through the *destination* chain's state (`EvmHost._epochs[set_id]` or `RequestReceipts[commitment]`), which is immutable once written. But the *amount* owed for that already-completed, provable work is read from a storage cell that keeps changing independently of when the delivery happened. This is structurally identical to the reported bug class: `claimable[_gauge]` in `Voter` represents work/value already accrued, yet a subsequent privileged state change (`killGauge`, here `set_outbound_request_delivery_reward`/`set_outbound_consensus_delivery_reward`) zeroes or changes the value backing that entitlement with no way to recover the value that existed at delivery-time.

Concretely:
1. Governance sets `OutboundRequestDeliveryReward[module_id] = R` (or `OutboundConsensusDeliveryReward[dest] = R`).
2. A relayer delivers a hyperbridge-originated request (or a consensus rotation) to the destination, at real cost (gas, bandwidth), earning entitlement to `R`.
3. Before the relayer's claim extrinsic lands, governance calls `set_outbound_request_delivery_reward(module_id, 0)` (or lowers/removes the per-chain reward) — a routine, non-malicious parameter update, exactly analogous to `killGauge` being a routine emergency-council action rather than an attack.
4. The relayer's claim then fails permanently at `ensure!(reward > BalanceOf::<T>::default(), Error::<T>::OutboundRequestNoRewardConfigured)` (or is silently underpaid if the reward was lowered rather than zeroed) — the entitlement for the already-completed, provable delivery is lost forever, with no snapshot mechanism and no `reviveGauge`-style recovery path.

### Impact Explanation
Relayers are the entities that keep messages, consensus rotations, and requests flowing to destination chains; they are only economically willing to do this work because of these configured rewards (as documented in `docs/outbound-request-incentivization.md`, "relayers have no economic reason to pick them up" without them). A design where the payout for delivered work depends on a governance value read at claim time rather than delivery time means honest relayers can lose real, already-spent value (gas fees on destination chains) with no recovery, purely because of an ordinary/expected reward-table update racing their claim. This directly disincentivizes relayer participation, undermining the liveness of Hyperbridge's outbound message and consensus-rotation delivery — a High-impact issue for the relayer-incentive model.

### Likelihood Explanation
Reward parameters are expected to be adjusted by governance over time (as the design doc itself notes reward tuning is a normal governance lever), and claim submission is inherently delayed relative to delivery (it waits for Hyperbridge to observe a state commitment for the destination and for the challenge period to elapse — see `observe_challenge_period` calls in the claim tasks). This creates a realistic window during which a routine reward update can race an honest relayer's pending claim, making the loss-of-reward scenario Medium likelihood rather than a contrived edge case.

### Recommendation
Snapshot the reward amount at delivery time (e.g., record it alongside the delivery receipt / claimable commitment when the request or rotation is first observed as delivered) rather than re-reading the live `OutboundRequestDeliveryReward`/`OutboundConsensusDeliveryReward` map at claim time. Alternatively, queue reward-parameter changes to only apply to deliveries that occur after the change (e.g., versioned/height-gated reward tables), so in-flight claims for already-completed work are settled at the rate that was in effect when the work was performed.

### Proof of Concept
1. Governance calls `set_outbound_request_delivery_reward(module_id, 100)`.
2. A relayer observes a hyperbridge-originated `PostRequest` from `module_id` and delivers it to the EVM destination, paying gas to do so, and the destination's `RequestReceipts[commitment]` records the relayer as the deliverer.
3. Before the relayer submits `claim_outbound_request_delivery_reward`, governance calls `set_outbound_request_delivery_reward(module_id, 0)`.
4. The relayer submits its (otherwise fully valid, correctly-signed, correctly-proven) claim; `process_outbound_request_delivery_claim` reads `OutboundRequestDeliveryReward::get(module_id) == 0` and rejects with `OutboundRequestNoRewardConfigured` — see the check at [5](#0-4) . The relayer's earned reward for real, already-verified delivery work is permanently unrecoverable; there is no path to reclaim it even if governance later restores the reward.
