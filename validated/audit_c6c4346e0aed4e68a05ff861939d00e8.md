### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-spoofing / cross-tenant webhook attribution - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` validates only the raw request body against the HMAC signature, but the `shop` field (parsed from the `x-shopify-shop-domain` / `shopify-shop-domain` header) is never included in the signed material. `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` as the tenant identifier and forwards it directly into `WebhookMetadata`, which the host application's `WebhookHandler#handle` uses to route/apply the webhook payload to a specific shop's data.

### Finding Description
The HMAC validation path is:
- `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against `verifiable_query.hmac` [1](#0-0) .
- For webhooks, `Request#to_signable_string` returns only `@raw_body` [2](#0-1) , while `Request#shop` is read straight from an HTTP header with no cryptographic binding to the signature [3](#0-2) .
- `Registry.process` only calls `Utils::HmacValidator.validate(request)` (i.e., verifies the body) and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) .

This breaks the intended identity binding: `shop authenticated (by HMAC) == shop the payload is attributed to`. In this gem, only `body == HMAC(body)` is enforced; `shop_header == HMAC(body)` is not. Contrast this with `Auth::Oauth::AuthQuery#to_signable_string`, which correctly folds `shop` into the signed string alongside `code`, `host`, `state`, and `timestamp` [5](#0-4) , showing that the library's own pattern for other verifiable queries is to include the tenant identifier in the signed payload — a pattern webhook `Request` does not follow.

Because the app's `client_secret` (HMAC key) is shared across all shops that install the app, an attacker who controls one installed shop (Shop A, an "unprivileged" tenant relative to Shop B) receives genuine Shopify webhooks for Shop A with a valid `(raw_body, hmac)` pair. Since `shop` is excluded from the signed content, the attacker can replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header to name a different shop (Shop B). `HmacValidator.validate` will still pass because it only checks the body against the secret, and the handler will receive `WebhookMetadata` claiming the payload is `shop: "shop-b.myshopify.com"` even though it was never sent by Shopify for Shop B.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` to select which tenant's records to create/update/delete (a very common pattern for webhook processing, e.g., "update shop X's order/inventory record from `body`"), an attacker-controlled shop can forge webhook bodies that appear to originate from a victim shop, corrupting or manipulating a different tenant's data. This constitutes cross-tenant access/write via a boundary the app developer reasonably assumes the gem enforces (verified webhook ⇒ verified sender's shop). Impact is Critical per the given classification (cross-tenant access), since it lets one tenant's forged payload be attributed to and applied against a different, arbitrary tenant.

### Likelihood Explanation
Medium-to-high: exploitation requires the attacker to operate at least one legitimate install of the target app (trivial for public apps — anyone can install a Shopify app on their own dev/test store) to obtain a valid `(body, hmac)` pair, and then simply resend that payload to the app's webhook endpoint with a different `shop-domain` header value. No knowledge of `api_secret_key` or access tokens is required — only observation of one's own legitimately delivered webhook.

### Recommendation
Bind the `shop` (and other trust-relevant fields such as `topic`/`webhook_id`, if attribution matters) into the HMAC-signed material for webhook requests, or otherwise cryptographically tie the shop-domain header to the signed body before it is surfaced to `WebhookHandler#handle`. At minimum, `to_signable_string` for `Webhooks::Request` should mirror `Auth::Oauth::AuthQuery`'s approach of including the header-derived shop value in the signed string, or the registry should independently confirm that the shop asserted in the header matches a shop known to be associated with this exact `raw_body`/`hmac` pair (e.g., look up an existing session/install for that shop and validate against it) before forwarding it downstream.

### Proof of Concept
1. Install the target app on attacker-controlled Shop A; trigger any webhook topic the app subscribes to (e.g., `orders/create`).
2. Capture the delivered request's `raw_body` and `x-shopify-hmac-sha256` header — this is a valid signature since `Request#to_signable_string` only signs `@raw_body` [2](#0-1) .
3. Replay the identical `raw_body` and `hmac` header to the app's webhook endpoint, but set `x-shopify-shop-domain: shop-b.myshopify.com` (Shop B, the victim, arbitrary/unrelated shop that also installed the app).
4. `Registry.process` calls `HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the shared `api_secret_key` [6](#0-5) .
5. `handler.handle` is invoked with `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: <attacker-controlled body from Shop A>, ...)` [7](#0-6) , causing the app to process attacker-chosen data under Shop B's tenant context.
