### Title
Webhook `topic` and `shop` headers are not cryptographically bound to the HMAC, allowing dispatch to any registered handler (including mandatory GDPR topics) with attacker-forged headers - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`Registry.process` validates only that the raw request body matches the HMAC signature; it never verifies that the `topic` or `shop-domain` headers were part of what Shopify signed, and it never re-applies the `mandatory_webhook_topic?` gate that protects `register`/`unregister`. Because `Request#to_signable_string` returns only `@raw_body` [1](#0-0) , any attacker who has obtained one validly-signed webhook body (e.g. by installing the app on their own development shop and receiving a legitimate `orders/create` callback) can resend that exact body to the app's webhook endpoint with a forged `X-Shopify-Topic` (and forged `X-Shopify-Shop-Domain`) header and have it dispatched to whatever handler is registered for that topic.

### Finding Description
Binding claimed to hold: `mandatory_webhook_topic?(topic) == true` at registration time ⇒ handler for that topic is unreachable outside Shopify's dashboard-controlled mandatory-webhook pipeline at process() time. This binding is false.

`Registry.process` is:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
end
``` [2](#0-1) 

It never calls `mandatory_webhook_topic?`, which is only invoked inside `register` and `unregister` [3](#0-2) [4](#0-3)  and is documented as existing solely because "Mandatory webhooks are subscribed to via the partner dashboard not the API" [5](#0-4) .

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the raw body) against the HMAC header [6](#0-5) . `Request#topic`, `Request#shop`, `Request#webhook_id`, and `Request#api_version` are all read straight from attacker-controllable HTTP headers and are never part of the signed content [7](#0-6) .

Exploit flow:
1. Attacker creates their own development shop, installs the app, and lets it register handlers for both `orders/create` and `shop/redact` (a common pattern since apps must implement all three GDPR mandatory topics).
2. Attacker triggers a real `orders/create` event on their own shop; Shopify delivers a genuinely signed webhook (body `B`, header `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Topic: orders/create`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`).
3. Attacker resends the identical body `B` and HMAC `H` to the app's single webhook route, but sets `X-Shopify-Topic: shop/redact` and (since `shop` is likewise unsigned) `X-Shopify-Shop-Domain` to any victim shop domain they choose.
4. `HmacValidator.validate` recomputes HMAC over `B` only — it matches, because the body was not altered.
5. `Registry.process` looks up `@registry["shop/redact"]` and invokes its handler with `WebhookMetadata.new(topic: "shop/redact", shop: <victim-shop>, body: <attacker-chosen orders/create JSON>)`, even though this topic was registered as mandatory-only.

Existing guards do not stop this: `mandatory_webhook_topic?` is process()-unreachable, `HmacValidator` never binds header fields, and there is no `ShopValidator.sanitize!` or session lookup in the webhook path to validate the `shop` claim against anything actually authenticated.

### Impact Explanation
This is a forged-webhook authentication bypass: a value that was never authenticated (topic and shop headers) is trusted as if it came from Shopify's mandatory-webhook pipeline, and the merchant-facing GDPR erasure/redaction handler (or any other registered handler) can be invoked with attacker-chosen body content and an attacker-chosen target shop string, one merchant's app instance touching data attributed to another shop. This is repeatable against arbitrary victim shop identifiers (limited only by whatever validation the app's own `shop/redact` handler performs on the `shop` value, which is out of this gem's scope) and costs the attacker nothing beyond installing the app once on a shop they control.

### Likelihood Explanation
Preconditions are realistic and match common integration patterns: the app must register an HTTP handler for a mandatory topic (`shop/redact`, `customers/redact`, `customers/data_request`) as most compliant apps do, and must expose a single webhook endpoint that routes by header topic as the gem's documented usage recommends [8](#0-7) . No secrets are required; the attacker only needs a validly-signed body, which they can obtain legitimately from their own development shop's webhook deliveries.

### Recommendation
Re-apply `mandatory_webhook_topic?` (or an equivalent explicit source check) inside `Registry.process` to reject dispatch for mandatory topics unless additional out-of-band verification exists, and/or bind `topic` and `shop` into the signable string / a secondary integrity check so that the HMAC covers the full set of trust-relevant values rather than the body alone.

### Proof of Concept
```ruby
# test/webhooks/registry_topic_confusion_test.rb
def test_process_dispatches_forged_mandatory_topic_with_unrelated_signed_body
  ShopifyAPI::Webhooks::Registry.clear
  redact_called = false
  redact_handler = TestHelpers::FakeWebhookHandler.new(lambda do |data|
    assert_equal("shop/redact", data.topic)
    assert_equal("victim-shop.myshopify.com", data.shop)
    redact_called = true
  end)

  ShopifyAPI::Webhooks::Registry.add_registration(
    topic: "shop/redact", path: "path", delivery_method: :http, handler: redact_handler,
  )

  body = '{"orders_create":"payload"}'
  hmac = Base64.encode64(
    OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body),
  )

  forged_headers = {
    "x-shopify-topic" => "shop/redact",              # attacker-forged, not part of signature
    "x-shopify-hmac-sha256" => hmac,                  # valid signature for `body`, computed for a different (real) event
    "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-forged, not part of signature
  }

  ShopifyAPI::Webhooks::Registry.process(
    ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers),
  )

  assert(redact_called)
end

def test_process_never_calls_mandatory_webhook_topic_check
  ShopifyAPI::Webhooks::Registry.expects(:mandatory_webhook_topic?).never
  # ... process a valid request and assert no call was made
end
```
Both sides of the binding: `mandatory_webhook_topic?("shop/redact")` is `true` (registration-time guarantee), but `Registry.process` reaches and executes the handler anyway — the assertions above demonstrate the divergence.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
