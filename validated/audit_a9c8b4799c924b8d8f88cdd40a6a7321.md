## Title
Webhook `shop` tenant identifier is not covered by the HMAC signature, allowing cross-tenant webhook impersonation - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) from an HTTP header, but `Utils::HmacValidator.validate` (invoked in `Registry.process`) only authenticates the raw request body via `to_signable_string`. The `shop` field that the host application uses to attribute the webhook to a tenant is never bound to the cryptographic signature, breaking the equality `shop authenticated == shop delivered to the handler`.

### Finding Description
`Registry.process` is the only integrity gate for inbound webhooks: [1](#0-0) 

It calls `Utils::HmacValidator.validate(request)`, which computes the HMAC exclusively over `request.to_signable_string`: [2](#0-1) 

`to_signable_string` returns only `@raw_body`: [3](#0-2) 

Meanwhile `shop` (and `topic`, `webhook_id`, `api_version`) are pulled straight from HTTP headers with no cryptographic tie to the body or the signature: [4](#0-3) 

After HMAC validation passes, `Registry.process` builds `WebhookMetadata` using this unauthenticated `request.shop` value and forwards it to the app's handler as the tenant identity: [1](#0-0) [5](#0-4) 

This is structurally the same class of bug as the referenced report: a value (`multiplier`/`utilizationRate` there, `shop` here) is treated as validated/derived-from-trusted-state, but the code path that actually verifies integrity (`_applySlopes` there, `HmacValidator.validate` here) never covers that value. Here, the gap means: **HMAC-verified bytes (`raw_body`) ≠ bytes used to establish tenant identity (`shop-domain` header)**.

Because the webhook endpoint is a public HTTP endpoint (it must be reachable by Shopify's infrastructure directly, with no additional network-layer allowlisting enforced by this gem), any unprivileged internet user who can install the app on their own store (a normal, unprivileged action) can:
1. Trigger a legitimate webhook for their own shop with attacker-chosen body content (e.g., edit a product title/description before triggering `products/update`).
2. Capture the resulting `raw_body` and its valid `X-Shopify-Hmac-Sha256` value — this pair is valid for *any* shop, since the shop is never part of the signed content.
3. Replay that exact `(raw_body, hmac)` pair directly to the app's public webhook endpoint, substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain.
4. `HmacValidator.validate` still returns `true` (it only checks `raw_body` against the secret), so `Registry.process` accepts the request and dispatches `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)` to the handler.

### Impact Explanation
This breaks the tenant/session-key binding the gem is expected to guarantee for webhook consumers: the handler receives attacker-controlled data attributed to a shop the attacker does not own. Any host application that uses `data.shop` from `WebhookMetadata` to look up records, update local database state, or gate authorization decisions (the intended and only documented use of this API, matching the `shop:` reference in `ShopifyApp`'s `SessionController`) will process forged data under a foreign tenant's identity. This is a cross-tenant access primitive: an unprivileged attacker (who only needs their own app installation, not the victim's credentials, access token, or `client_secret`) can inject fabricated events into a victim shop's data pipeline.

### Likelihood Explanation
High. The only prerequisites are: (a) the app is a public/multi-tenant app that unprivileged users can install on their own store (typical), and (b) the attacker can control some body content of a webhook topic they can trigger. Both are trivially satisfiable without any privileged access, credentials, or social engineering — matching the "unprivileged internet user" threat model. No TLS interception or local access is needed since the webhook endpoint is inherently public-facing.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value that is actually HMAC-verified, or otherwise cryptographically tie the header-derived identity to the signed body — e.g., include the shop domain in the signable string, or require the host application to cross-check the header-derived shop against an independently-verified webhook subscription record (keyed by `webhook_id`) rather than trusting the header directly. At minimum, document prominently that `WebhookMetadata#shop` is *not* authenticated by the HMAC check and must not be used as a sole tenant-authorization key.

### Proof of Concept
```ruby
require "openssl"
require "digest"

secret = ShopifyAPI::Context.api_secret_key

# 1. Attacker's own shop triggers a webhook with attacker-chosen body
raw_body = '{"title":"legit product on attacker shop"}'
hmac_digest = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, raw_body)
valid_hmac_b64 = [hmac_digest].pack("m0") # what Shopify would send as X-Shopify-Hmac-Sha256

# 2. Attacker replays identical body+hmac, but swaps the shop-domain header
forged_headers = {
  "x-shopify-topic" => "products/update",
  "x-shopify-hmac-sha256" => valid_hmac_b64,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # <-- not covered by HMAC
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# 3. Passes validation because HmacValidator only checks raw_body
ShopifyAPI::Webhooks::Registry.process(request)
# => handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker JSON, ...)
```
This confirms `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) accepts the request purely on `raw_body` integrity, while `Request#shop` (`lib/shopify_api/webhooks/request.rb:20-23`) is trusted unauthenticated for tenant attribution in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`).

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
