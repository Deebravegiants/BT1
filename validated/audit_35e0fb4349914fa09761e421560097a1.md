Audit Report

## Title
Unbounded slippage in `SwapFirstAssetTrader::buy_weight` allows AMM price manipulation to overcharge XCM fee payers - (File: cumulus/primitives/utility/src/lib.rs)

## Summary
`SwapFirstAssetTrader::buy_weight` computes a fixed `Target`-denominated fee via `WeightToFee::weight_to_fee(&weight)` and swaps the user's entire supplied payment asset for that exact amount via `SwapCredit::swap_tokens_for_exact_tokens`, without passing or enforcing any `amount_in_max`/slippage bound. Since `pallet_asset_conversion` pools are permissionless and freely manipulable, the amount of the user's asset actually consumed for a fixed `Target` fee is entirely dependent on the pool's price at execution time, bounded only by the total `credit_in` the user supplied.

## Finding Description
In `buy_weight`, the fee is computed statically as `WeightToFee::weight_to_fee(&weight)` [1](#0-0) , and the entire `credit_in` (built from the full fungible amount in `BuyExecution`) is passed to `SwapCredit::swap_tokens_for_exact_tokens(vec![swap_asset, Target::get()], credit_in, fee)` [2](#0-1) . This is confirmed to be an exact-output swap where `pallet_asset_conversion::Pallet::<T>::swap_tokens_for_exact_tokens` (the `SwapCredit` trait impl) determines however much of the input asset is required at the current pool ratio to yield exactly `amount_out`, consuming that amount from `credit_in` and returning the remainder as `credit_change` [3](#0-2) . The `SwapCredit` trait's `swap_tokens_for_exact_tokens` signature takes no `amount_in_max` parameter at all [4](#0-3) , unlike the analogous `Swap` trait (non-credit variant) which does expose an optional `amount_in_max` [5](#0-4) . `SwapFirstAssetTrader` does not call `QuotePrice::quote_price_tokens_for_exact_tokens` before swapping to sanity-check the price, even though its trait bound requires `SwapCredit: ... + QuotePrice<...>` [6](#0-5) , so the `QuotePrice` capability is present but unused for slippage protection. The only effective bound on the amount consumed is that it cannot exceed the entire `given_credit_amount` supplied in the `BuyExecution` payment, in which case the swap fails and returns `XcmError::FeesNotMet` [7](#0-6) .

## Impact Explanation
If the `swap_asset`/`Target` pool is skewed unfavorably to the payer at the moment `buy_weight` executes, the payer's asset consumption for a fixed weight/fee can rise well above fair value, up to the entirety of the amount they supplied in `BuyExecution`. This is a real, in-scope loss of value for a user whose XCM message happens to execute against a manipulated pool, and the excess is captured by whoever controls the pool skew (arbitrageurs/attackers), consistent with sandwich/slippage extraction mechanics.

## Likelihood Explanation
The precondition — an unprivileged, permissionless liquidity pool for the `swap_asset`/`Target` pair that any account can trade against via `pallet_asset_conversion` — is realistic for any deployment that configures `SwapFirstAssetTrader` to accept non-`Target` assets for fees using on-chain AMM pools (e.g., configured in `asset-hub-rococo`/`asset-hub-westend`/`penpal` xcm configs, as found via reference in `cumulus/parachains/runtimes/assets/asset-hub-rococo/src/xcm_config.rs` and similar). An attacker does not need exact same-block front-running; leaving the pool in a skewed state before a victim's message is processed (then reversing afterward) is sufficient and repeatable by any unprivileged account, especially against thin-liquidity pools.

## Recommendation
Enforce a slippage bound in `SwapFirstAssetTrader::buy_weight`: quote the expected input via `QuotePrice::quote_price_tokens_for_exact_tokens` before swapping, and reject or cap the swap (returning `XcmError::TooExpensive`) if the amount that would be consumed from `credit_in` exceeds the quoted price by more than an acceptable tolerance, rather than accepting whatever the current pool state demands. Alternatively, extend `SwapCredit::swap_tokens_for_exact_tokens` to accept an `amount_in_max` parameter (mirroring the non-credit `Swap` trait) and have the trader pass a bounded value.

## Proof of Concept
1. Configure a runtime with `pallet_asset_conversion` and a permissionless pool for `(swap_asset, Target)`.
2. Query `quote_price_tokens_for_exact_tokens(swap_asset, Target::get(), fee, true)` to obtain a `baseline_input` for a given `WeightToFee::weight_to_fee(&weight)`.
3. As an unprivileged account, call `pallet_asset_conversion::swap_exact_tokens_for_tokens` to skew the pool ratio (e.g., dump `Target` into the pool to make `swap_asset` relatively expensive).
4. Execute a `BuyExecution` XCM instruction with `swap_asset` as payment, invoking `SwapFirstAssetTrader::buy_weight` for the same `weight`, and observe the amount actually deducted from the payer's `credit_in` (`given_credit_amount - credit_change.peek()`).
5. Confirm this consumed amount exceeds `baseline_input` by an amount proportional to the pool skew, with no rejection or cap triggered by `buy_weight` until the entire supplied payment is exhausted, demonstrating the lack of an `amount_in_max`/slippage guard as described in `substrate/frame/asset-conversion/src/swap.rs` L109-113 and `cumulus/primitives/utility/src/lib.rs` L469-489.

	fn swap_tokens_for_exact_tokens(
		path: Vec<Self::AssetKind>,
		credit_in: Self::Credit,
		amount_out: Self::Balance,
	) -> Result<(Self::Credit, Self::Credit), (Self::Credit, DispatchError)> {
		let credit_asset = credit_in.asset();
		with_transaction(|| -> TransactionOutcome<Result<_, DispatchError>> {
			let res = Self::do_swap_credit_tokens_for_exact_tokens(path, credit_in, amount_out);
			match &res {
				Ok(_) => TransactionOutcome::Commit(Ok(res)),
				// wrapping `res` with `Ok`, since our `Err` doesn't satisfy the
				// `From<DispatchError>` bound of the `with_transaction` function.
				Err(_) => TransactionOutcome::Rollback(Ok(res)),
			}
		})
		// should never map an error since `with_transaction` above never returns it.
		.map_err(|_| (Self::Credit::zero(credit_asset), DispatchError::Corruption))?
	}
