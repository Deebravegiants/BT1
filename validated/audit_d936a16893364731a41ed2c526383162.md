### Title
Unbounded dust deposits can exhaust the position-NFT account namespace and permanently block new accounts - ([File: contracts/controller/src/account.rs](contracts/controller/src/account.rs))

### Summary

`Controller::supply` accepts `account_id = 0` to create a new account and only requires each supplied amount to be greater than zero. [1](#0-0)  Account creation mints a new sequential `u32` position NFT and writes persistent account metadata, while the supplied asset creates persistent position state. [2](#0-1) [3](#0-2)  Because there is no minimum economic deposit, account-creation fee, active-account cap, or per-owner account cap, one unprivileged address can create arbitrarily many live accounts with one-unit deposits. [4](#0-3) [5](#0-4) 

The position NFT issues sequential `u32` token IDs, with ID `0` consumed during construction and each `mint` returning the next `u32`. [6](#0-5)  Repeating the deposit path can therefore consume the complete account-ID namespace; after exhaustion, every account-creating flow that relies on `nft_mint_call` fails, permanently preventing new lending accounts. [7](#0-6) 

### Finding Description

The vulnerable path is:

```text
supply(
  caller = attacker,
  account_id = 0,
  spoke_id = active_spoke,
  assets = [(HubAssetKey { hub_id, asset }, 1)]
)
```

`process_supply` authenticates only `caller`, aggregates the positive payment, and calls `load_or_create_account`; the `account_id == 0` branch immediately invokes `create_account` without checking a minimum deposit or any global account bound. [8](#0-7)  The new account receives an NFT-backed ID and persistent `AccountMeta`, then `process_deposit` pulls the attacker’s measured token payment and records the supply position. [9](#0-8) 

Position limits restrict only the number of distinct assets inside each account; they do not restrict the number of accounts one owner can create. [10](#0-9)  NFT IDs are not reused after account deletion, so even cycling deposits and withdrawals still permanently advances the namespace. [11](#0-10) [12](#0-11) 

### Impact Explanation

A single unprivileged actor can permanently consume all `u32` position IDs through repeated one-unit deposits. [13](#0-12)  Once no unused `u32` ID remains, `PositionNft::mint` cannot produce another token ID, so `create_account` cannot complete. [14](#0-13)  This permanently disables every account-opening route that reaches `nft_mint_call`, including `supply`, `multiply`, `flash_position`, `migrate_from_blend`, and liquidation `Credit(0)` receiver creation. [15](#0-14) 

Even before namespace exhaustion, each retained dust account forces durable controller metadata, a supply-position map, NFT ownership state, and NFT enumeration state. [16](#0-15) [17](#0-16)  The resulting persistent ledger growth is unbounded relative to the one-unit economic deposit because the protocol charges no account-creation cost apart from storage rent paid by the transaction. [18](#0-17) 

### Likelihood Explanation

The attack needs no privileged role, leaked key, malformed oracle price, third-party contract behavior, or special market condition: the attacker authorizes ordinary token transfers and repeatedly calls the public `supply` entrypoint. [1](#0-0)  The only contract-side amount requirement is `amount > 0`, and the repository already demonstrates 64 distinct accounts created by one actor with 64 one-unit deposits. [18](#0-17) 

The eventual denial of new-account creation requires consuming the full `u32` ID range rather than merely creating a small number of accounts. [6](#0-5)  That makes the attack economically and operationally expensive, so the issue is appropriately Medium rather than Critical or High.

### Recommendation

Introduce an economic or explicit bound on account creation rather than allowing every positive deposit to mint a permanent NFT-backed account. Suitable mitigations include:

- Require a governance-configured minimum USD value for the first deposit when `account_id == 0`.
- Charge and retain a non-refundable account-creation fee denominated in a listed asset.
- Add a governance-configured global active-account cap.
- Optionally bound the number of live position NFTs held by one owner.

The check should occur before `create_account` calls `nft_mint_call`, so a rejected account does not consume an NFT ID or partially initialize metadata. [2](#0-1)  Any minimum-value check should use the same strictly validated oracle/index context used for risk decisions rather than a raw token amount that changes meaning across decimals and prices. [19](#0-18) 

### Proof of Concept

The repository contains a direct reproduction in `tests/test-harness/tests/controller/supply.rs`. It mints only `N = 64` base units to one attacker, then repeatedly submits:

```rust
let dust = vec![&t.env, (hub_asset(asset.clone()), 1i128)];
let id = ctrl.supply(&attacker, &0u64, &1u32, &dust);
```

Each call returns a new positive account ID, and every spammed account remains queryable through `account_exists`. [18](#0-17) 

```rust
#[test]
fn poc_single_actor_spams_unbounded_dust_accounts() {
    let mut t = LendingTest::new().with_market(usdc_preset()).build();
    let attacker = t.get_or_create_user("attacker");
    let usdc = t.resolve_market("USDC");

    const N: u64 = 64;
    usdc.token_admin.mint(&attacker, &(N as i128));

    for _ in 0..N {
        let dust = vec![&t.env, (hub_asset(usdc.asset.clone()), 1i128)];
        let id = t
            .ctrl_client()
            .supply(&attacker, &0u64, &1u32, &dust);
        assert!(id > 0);
        assert!(t.ctrl_client().account_exists(&id));
    }
}
```

The same call repeated indefinitely advances the sequential `u32` NFT counter until no fresh account ID remains. [20](#0-19)

    asset: &Address,

## Lifecycle

- ID `0` creates an account through `supply`, `multiply`, `flash_position`,
  `migrate_from_blend`, or liquidation `Credit(0)`. Store the returned ID.
- `account_exists(id)` checks and renews only the controller's
  `AccountMeta(id)`. It does not renew or prove the existence of position maps,
  delegates, NFT entries, your local pointer, or your contract instance.
- Cleanup depends on the operation. `withdraw` and the strategy verbs remove
  the account when both position maps end empty. Liquidation and
  `clean_bad_debt` remove it through their own paths. `repay` writes only the
  debt side and does not remove an empty account.
- Deletion removes controller entries and burns the NFT atomically. IDs are
  not reused.

fn poc_single_actor_spams_unbounded_dust_accounts() {
    let mut t = LendingTest::new().with_market(usdc_preset()).build();

    let attacker = t.get_or_create_user("attacker");
    let usdc = t.resolve_market("USDC");

    const N: u64 = 64;
    usdc.token_admin.mint(&attacker, &(N as i128));
    let asset = usdc.asset.clone();

    let ctrl = t.ctrl_client();
    let mut created: u64 = 0;
    let mut last_id: u64 = 0;
    for _ in 0..N {
        let dust = vec![&t.env, (hub_asset(asset.clone()), 1i128)];
        let id = ctrl.supply(&attacker, &0u64, &1u32, &dust);
        assert!(id > 0, "1-unit deposit must be accepted (no dust floor)");

        assert!(id > last_id, "each supply(id=0) must mint a new account id");
        assert!(
            ctrl.account_exists(&id),
            "spammed account persists in storage"
        );
        last_id = id;
        created += 1;
    }

    assert_eq!(
        created, N,
        "one actor created {N} distinct accounts with dust deposits"
    );
