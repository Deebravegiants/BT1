### Title
Webhook tenant identity (`shop-domain` header) is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable string from only the raw request body [1](#0-0) , while `shop` — the value used by `Registry.process` to identify which merchant/tenant the webhook belongs to — is pulled straight from an HTTP header that is completely outside the HMAC's signed scope [2](#0-1) .

### Finding Description
`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the `hmac` field using a constant-time comparison [4](#0-3) . For webhooks, `to_signable_string` returns solely `@raw_body`, the JSON body bytes [1](#0-0) . Shopify's own `X-Shopify-Hmac-SHA256` header is computed only over the body too, so this matches Shopify's real contract — but the gem then treats `request.shop` as an authenticated tenant identifier when it is not covered by any signature at all: it is read verbatim from `shopify-shop-domain`/`x-shopify-shop-domain` headers with no cross-check against the signed body [2](#0-1) .

`Registry.process` validates only `Utils::HmacValidator.validate(request)` (i.e., only the body) before constructing `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` and invoking the topic handler [3](#0-2) . Equality that should hold — `shop-that-produced-the-signed-bytes == shop-value-trusted-by-handler` — is broken: the HMAC only proves "the body bytes were produced by someone holding `api_secret_key`" (i.e., Shopify), it proves nothing about which shop's header accompanies those bytes.

Any unprivileged party who can reach the app's webhook HTTP endpoint (this includes a malicious merchant installing the app, who legitimately receives valid signed webhook deliveries for their own shop) can capture one genuine `(raw_body, hmac)` pair for shop A and replay it to the same endpoint with the `shop-domain` header rewritten to shop B. Because `to_signable_string` never includes the shop header, the HMAC still validates, and `Registry.process` will dispatch the handler with `WebhookMetadata#shop == "B"` even though the payload was never actually sent by/for shop B.

### Impact Explanation
Applications built on this gem that use `WebhookMetadata#shop` (as documented/intended usage) to key per-tenant storage, authorization, or side effects (e.g., "look up shop B's session/access token and act using this webhook body") can be tricked into applying data or actions under the wrong tenant identity — a cross-tenant confusion primitive. Depending on how the host app uses the `shop` field (e.g., `customers/redact`, `shop/redact` mandatory webhooks, order/inventory sync), this can result in cross-tenant data leakage or corruption purely by replaying a legitimately-received webhook body under a different `shop-domain` header value, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Any app merchant (an unprivileged, non-credentialed actor relative to other tenants) who installs the app receives genuine signed webhook bodies for their own shop and can trivially replay them with a modified header at the app's public webhook endpoint — no `api_secret_key`, access token, or other privileged material is required, since headers are attacker-controlled and unauthenticated.

### Recommendation
Bind `shop` cryptographically to the signature verification: either require callers to pass the expected shop to `Registry.process`/`HmacValidator.validate` and assert `request.shop == expected_shop` after HMAC success, or extend `to_signable_string` to include the `shop-domain` header value so a mismatched header invalidates the signature, mirroring how `AuthQuery#to_signable_string` binds `shop` into its signed parameters [5](#0-4) .

### Proof of Concept
1. App merchant for `shop-a.myshopify.com` installs the app and receives a legitimate webhook POST with body `raw_body` and header `x-shopify-hmac-sha256: H` (valid HMAC over `raw_body` only, per `to_signable_string` at `lib/shopify_api/webhooks/request.rb:35-38`) and `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker (same merchant, or anyone able to capture that request) replays the exact same body and `hmac` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only — unchanged from step 1 — so validation passes [6](#0-5) .
4. The handler is invoked with `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: <shop-a's data>, ...)`, i.e., shop A's payload is now processed as if it belonged to shop B [7](#0-6) .
