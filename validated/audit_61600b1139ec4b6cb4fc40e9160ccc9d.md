### Title
First-depositor donation attack lets the pool creator steal a subsequent depositor's funds via inflated vault balances - (File: `program/src/processor.rs`)

### Summary
`Pool::process_deposit` computes the LP tokens to mint for a depositor using the *live* SPL token balances of the AMM's coin/PC vaults as the ratio denominator, while the LP "total supply" tracked on-chain (`amm.lp_amount`) is only updated when `process_deposit`/`process_withdraw` run. Because the vault token accounts are ordinary SPL token accounts owned by the AMM authority, anyone (including the pool's first depositor) can transfer additional tokens directly into them with a plain SPL `Transfer` instruction, inflating the vault balance without minting any LP tokens or increasing `amm.lp_amount`. This lets the first depositor (who initially owns virtually all `amm.lp_amount`) manipulate the deposit exchange rate against the next depositor and later redeem an outsized share of the pool via `Withdraw`.

### Finding Description
On `Initialize2`, `amm.lp_amount` is set to the full geometric-mean liquidity value while only `liquidity - 10^decimals` LP tokens are actually minted to the depositor: [1](#0-0) [2](#0-1) [3](#0-2) 

The `10^decimals` portion is never minted to anyone (a Uniswap-V2-style locked minimum), but for any pool with meaningfully-sized initial liquidity this locked amount is a negligible fraction of the total, so the first depositor still owns essentially 100% of `amm.lp_amount`.

In `process_deposit`, the coin/PC totals used to compute the mint ratio come directly from the **current on-chain balances** of the vault token accounts (via `unpack_token_account`), not from any internally-tracked deposit ledger: [4](#0-3) 

The resulting `total_pc_without_take_pnl` / `total_coin_without_take_pnl` are then used as the denominator when computing how many LP tokens a new deposit is worth, while `amm.lp_amount` (the numerator/supply term) is used unchanged: [5](#0-4) [6](#0-5) 

Because the coin/PC vault accounts created in `Initialize2` are just standard SPL token accounts owned by the AMM `$authority` PDA: [7](#0-6) 

any account holding the corresponding mint can execute an SPL `Transfer` directly to `amm_coin_vault` / `amm_pc_vault` without going through any Raydium instruction and without any authorization check from the AMM program — this is a permissionless, single-transaction action.

This decouples "real balance used to price a deposit" from "LP supply used to size that deposit's mint," which is the same root cause as the reported Surge Pool bug: an actor who already owns (almost) all of the LP supply can inflate the balance-based denominator right before a victim deposits, causing the victim to receive disproportionately few LP tokens for their contribution. On `Withdraw`, the redemption math uses the same live vault balances against `amm.lp_amount`: [8](#0-7) 

so the attacker, still holding virtually all the LP supply, can withdraw and reclaim their own donation plus a large fraction of the victim's newly-added funds, since the victim's contribution was minted at a diluted rate.

### Impact Explanation
This is a direct, permissionless theft of a legitimate depositor's funds by the pool's first/dominant LP holder, reachable in a handful of standard transactions (`Initialize2` with attacker-chosen large initial amounts → direct SPL `Transfer` donation to the vault(s) → victim's `Deposit` → attacker's `Withdraw`). It matches the "concrete theft of user funds" bar for High severity. It is not first-depositor-only in the strict zero-supply sense (Raydium's minimum-liquidity lock in `Initialize2` prevents that specific zero/near-zero supply degenerate case), but the same balance-vs-supply-decoupling bug class is fully reachable whenever one party controls a dominant share of `amm.lp_amount`, which trivially includes the pool creator right after `Initialize2` and before any other liquidity provider joins.

### Likelihood Explanation
Likelihood is high for newly created pools: pool creation via `Initialize2` is permissionless (any signer, no privileged role check beyond standard account/PDA validation), and donating tokens to a known, derivable vault PDA is a single unauthenticated SPL transfer. An attacker only needs to watch for (or front-run) the first sizeable deposit into a pool they created.

### Recommendation
Do not derive the deposit/withdraw exchange ratio purely from live SPL balances of the vaults; instead track pool reserves internally (update them explicitly on every deposit/withdraw/swap) so that unsolicited direct transfers into the vault cannot be used to manipulate `total_pc_without_take_pnl`/`total_coin_without_take_pnl` independent of `amm.lp_amount`. Alternatively/additionally, reconcile any excess vault balance beyond the tracked reserve as a permissionless "skim" that does not affect LP-share pricing, similar to how some AMMs handle unexpected balance surpluses.

### Proof of Concept
1. Attacker calls `Initialize2` with meaningfully large `init_coin_amount`/`init_pc_amount` (e.g. equal-valued X and Y), receiving `user_lp_amount = liquidity - 10^decimals` LP tokens while `amm.lp_amount = liquidity` (attacker owns ~100% of supply since the locked minimum is negligible relative to a normal-size pool) — see [9](#0-8) .
2. Attacker sends a plain SPL `Transfer` of additional coin and/or PC tokens directly to `amm_coin_vault`/`amm_pc_vault` (no Raydium instruction call needed) — vault accounts are ordinary SPL accounts per [7](#0-6) , inflating real balances without touching `amm.lp_amount`.
3. Victim calls `Deposit`; `process_deposit` reads the now-inflated real balances via `unpack_token_account` ( [4](#0-3) ) and computes `mint_lp_amount` against the unchanged `amm.lp_amount` ( [5](#0-4) ), minting the victim a diluted LP amount relative to the true value they contributed.
4. Attacker calls `Withdraw` for their (near-total) LP balance; redemption is computed from the current, now victim-enlarged vault balances divided by `amm.lp_amount` ( [8](#0-7) ), letting the attacker recover their donation plus a disproportionate share of the victim's deposit.

Note: exact numeric profitability depends on the specific ratio of donation size to pool size and the `10^decimals` locked-liquidity fraction from step 1; a full economic proof-of-concept (with concrete numbers/units) would need to be built and run in a local test harness, which was not available in this review — the structural root cause (balance-based pricing decoupled from LP-supply accounting, exploitable via unauthenticated vault donation) is confirmed directly from the cited code.
