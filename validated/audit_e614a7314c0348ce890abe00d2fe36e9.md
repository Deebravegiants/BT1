Based on my investigation, I've confirmed the analog exists in the `CallDispatcher` used across the Intent Gateway and HyperFungibleToken calldata-execution flows.

### Title
`CallDispatcher.dispatch` checks only low-level call success and never inspects ERC20 `transfer`/`approve` return data, allowing non-reverting-on-failure tokens to silently fail sweeps and strand escrowed funds - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch` executes each `Call` with a raw `to.call{value: call.value}(call.data)` and reverts only when the low-level call itself reverts (`!success`). It never decodes/verifies the `bool` returned by an ERC20 `transfer`/`approve` call. Every place in the Intent Gateway that sweeps ERC20 tokens off the shared `CallDispatcher` builds its calldata with `abi.encodeWithSelector(IERC20.transfer.selector, ...)` and routes it through this same unchecked `dispatch()`.

### Finding Description
`CallDispatcher.dispatch` in [1](#0-0)  only checks whether the external call reverted, not the ABI-encoded boolean many ERC20 implementations return to signal failure without reverting:

```solidity
(bool success, bytes memory result) = to.call{value: call.value}(call.data);
if (!success) revert CallFailed(to, result);
```

This dispatcher is used by `IntentGatewayV2.placeOrder` to sweep predispatch-processed tokens from the shared dispatcher back into escrow, building the sweep call as a raw `transfer` selector: [2](#0-1) . It's also used unconditionally in `IntentsBase._execute`'s postdispatch dust-sweep, which emits `DustCollected` for the full pre-transfer balance without ever re-checking that the balance actually moved after the sweep: [3](#0-2) .

If the input/output token specified in an order (attacker/user-controlled `order.inputs[i].token` or `order.output.assets[i].token`, both arbitrary addresses) is a non-standard ERC20 that returns `false` on a failed `transfer` instead of reverting (a well-known class of legacy/non-compliant tokens), the `to.call(...)` inside `CallDispatcher.dispatch` still reports `success = true`, so `dispatch()` returns normally as if the sweep succeeded.

- In `placeOrder`'s predispatch path, the subsequent "measure actual received" loop does re-read `balanceOf(address(this))` and would set `order.inputs[i].amount` to 0 (mitigating loss detection there), but the tokens that were pulled from the user into the `CallDispatcher` during predispatch (via `IERC20(token).safeTransferFrom(msg.sender, dispatcher, amount)`, [4](#0-3) ) never leave the dispatcher — they are permanently stuck there since `CallDispatcher` is a shared, unowned contract with no sweep/rescue function, and the order is committed with the affected input's amount recorded as `0`.
- In `IntentsBase._execute`'s dust sweep, there is no post-transfer balance check at all: `DustCollected(token, balance)` is emitted unconditionally even though the underlying `transfer` may have silently failed, again leaving the token balance permanently stuck on the `CallDispatcher`.

### Impact Explanation
This is a real freezing-of-funds condition: any order that routes a non-standard ERC20 (one that returns `false` rather than reverting) through predispatch or postdispatch calldata will have the corresponding tokens irrecoverably stranded on the shared `CallDispatcher` contract, which has no owner/rescue mechanism (`evm/src/utils/CallDispatcher.sol`). Because the dispatcher is a single shared contract used by all `IntentGatewayV2` instances and by `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata execution, this affects any user or solver whose order references such a token.

### Likelihood Explanation
Reachable directly from a single unprivileged `placeOrder`/`fillOrder` call by specifying a predispatch/postdispatch asset backed by a non-compliant ERC20 (a well-documented category of real-world tokens). No privileged role or governance action is required — any user placing or filling an order chooses the token addresses in `order.inputs`/`order.output.assets`.

### Recommendation
In `CallDispatcher.dispatch`, use OpenZeppelin's `SafeERC20`-style verification (or generically decode-and-check `bool` return data whenever the call's return data length is 32 bytes) instead of trusting `success` alone. Alternatively, require the sweep calls constructed in `IntentGatewayV2` and `IntentsBase` to use `safeTransfer`-equivalent semantics and add a post-dispatch balance assertion in `_execute` mirroring the one already present in `placeOrder`'s predispatch sweep.

### Proof of Concept
1. Deploy a token whose `transfer(address,uint256)` returns `false` on failure conditions (e.g., a blacklist/pausable ERC20) instead of reverting, following the same non-standard pattern flagged in the referenced Sherlock report.
2. Place an order via `IntentGatewayV2.placeOrder` with `predispatch.assets` containing this token and a `predispatch.call` that triggers the failure condition (e.g., pausing transfers or blacklisting the gateway) before the sweep executes.
3. Observe `ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls))` at [5](#0-4)  completing without reverting even though the token balance never moved from `dispatcher` to the gateway.
4. The order is created with `order.inputs[i].amount == 0` for that token while the user's original tokens remain permanently held by `CallDispatcher`, which has no withdrawal function — the funds are unrecoverable.
