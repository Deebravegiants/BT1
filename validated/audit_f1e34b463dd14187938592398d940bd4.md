## Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-identity spoofing in `ShopifyAPI::Webhooks::Registry.process` — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop` (and `topic`, `webhook_id`, `api_version`) values are read from HTTP headers that are never included in the HMAC computation. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body alone, then trusts the unauthenticated `shop-domain` header when constructing `WebhookMetadata` for the app's handler. Any party who can obtain one genuinely-signed webhook body/HMAC pair (e.g. by installing the app on their own store) can replay it with an arbitrary `shop-domain` header value, causing the app to process the payload as if it belonged to a different, victim shop.

### Finding Description
The signed bytes and the trusted tenant identifier are two different things:

- Signed bytes (HMAC input): `@raw_body` only. [1](#0-0) 

- Trusted tenant identifier (`shop`) used for routing/attribution: read from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of the signed payload. [2](#0-1) 

- Validation only checks the HMAC against `to_signable_string` (the body), never against the shop header: [3](#0-2) 

- `Registry.process` gates handler invocation solely on this body-only HMAC check, then forwards the attacker-controllable `request.shop` straight into `WebhookMetadata` passed to the app's webhook handler: [4](#0-3) 

The equality that should hold is:
`shop value covered by verified HMAC bytes == shop value the handler treats as the authenticated tenant`

Before the attacker's request: for a genuine Shopify-delivered webhook, both sides are `victim-or-own-shop.myshopify.com` and agree because Shopify controls both the body/HMAC and the header together.

After the attacker's replay: the verified HMAC still passes (it only covers `@raw_body`, which is unchanged), but the `shop-domain` header — and therefore `request.shop`/`data.shop` delivered to the handler — can be set to any value the attacker chooses. The two sides of the equality diverge, and the library provides no mechanism to catch this, since `to_signable_string` never binds the header.

### Impact Explanation
An unprivileged attacker who has installed the app on their own shop (or otherwise obtained one legitimately-signed webhook body/HMAC pair for a given topic) can forge webhook deliveries attributed to any other shop domain by simply changing the `shopify-shop-domain` header while replaying the same body and HMAC. Since `data.shop` is the only tenant-scoping signal the library exposes to app handlers (per `docs/usage/webhooks.md`), and apps are expected to use it to select the shop's session/store for side effects (e.g. `shop_domain: data.shop` shown in the gem's own documented example), this allows cross-tenant data injection or corruption: attacker-controlled payloads processed under a victim shop's identity. This satisfies the "cross-tenant access" criterion for Critical impact, since the tenant/shop boundary that host apps rely on this gem to establish is not actually authenticated.

### Likelihood Explanation
Likelihood is high for any app that receives webhooks for topics the attacker can trigger on their own shop (e.g. `app/uninstalled`, `orders/create`, `customers/create`, etc. — any topic the attacker's own store can generate). No secret material is required; the attacker only needs a body they can obtain a valid Shopify-issued HMAC for (their own store's webhook traffic) and the ability to replay an HTTP request to the app's public webhook endpoint with a modified header.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the HMAC-verified data instead of trusting an unauthenticated header in isolation:
- Include the `shop-domain` header (and topic) in `to_signable_string`, matching Shopify's documented signing scheme if it supports header-inclusive verification, or
- Cross-check `request.shop` against a shop already known/authorized for this app installation (e.g. verify a session/webhook subscription exists for that exact `shop` + `webhook_id` combination) before invoking the handler, or
- At minimum, document prominently that `data.shop` from `WebhookMetadata` is not itself cryptographically authenticated and must not be trusted for tenant scoping without additional verification.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw request body `B` and the valid `x-shopify-hmac-sha256` header `H` that Shopify sent to the app's callback URL.
2. Attacker (or anyone with network access to the app's public webhook route) resends the exact same body `B` and `H` to the app's webhook endpoint, but replaces `x-shopify-shop-domain: attacker-shop.myshopify.com` with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim-shop.myshopify.com", "x-shopify-hmac-sha256" => H})` is constructed.
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`) — identical to the original — and passes.
5. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, so the app processes attacker-controlled data as belonging to `victim-shop.myshopify.com`.
