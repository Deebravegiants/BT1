Confirmed root cause: the `shop-domain` header is validated for presence but never bound into the HMAC computation.### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body, so `HmacValidator.validate` cryptographically authenticates the *body bytes* but never binds the `shop`, `topic`, `webhook_id`, or `api_version` values pulled from HTTP headers. Because the HMAC key (`Context.api_secret_key`) is shared across every shop that has the app installed, any (body, HMAC) pair valid for one tenant remains valid when replayed with a forged `shop-domain` header pointing at a different, victim tenant.

### Finding Description
`Registry.process` performs authentication with a single check: [1](#0-0) 

The only thing `Utils::HmacValidator.validate` verifies is that the raw body was HMAC-signed with the app's `client_secret`: [2](#0-1) 

`validate_signature` compares the signature against `verifiable_query.to_signable_string`, which for `Webhooks::Request` is defined as just `@raw_body`: [3](#0-2) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are read directly from attacker-controllable HTTP headers with no cryptographic linkage to the signed body: [4](#0-3) 

After `HmacValidator.validate` passes, `Registry.process` forwards the header-derived, unauthenticated `request.shop` straight into `WebhookMetadata`, which the host application's handler uses to identify which tenant the webhook is "for": [5](#0-4) [6](#0-5) 

**Binding broken (as an equality):**
`shop authenticated by HMAC` should equal `shop acted on by the handler`, but the implementation only guarantees `body authenticated by HMAC` while `shop` (and `topic`, `webhook_id`, `api_version`) are trusted verbatim from unauthenticated headers.

**Before attacker's request:** For a legitimate webhook from Shopify to shop A, `(raw_body_A, hmac(raw_body_A))` arrives with header `shop-domain: A.myshopify.com`. Validation passes and `data.shop == "A.myshopify.com"` — correct.

**Attacker sequence:** An unprivileged user who has installed the app on their own shop (shop A, which they legitimately control, no `client_secret`/access token needed) triggers any webhook-eligible action to capture a valid `(raw_body_A, hmac(raw_body_A))` pair (all webhook payloads are signed with the same app-wide `client_secret`, not a shop-specific secret). They then POST this exact `raw_body_A` and `hmac` value to the app's webhook endpoint, but replace the `x-shopify-shop-domain` header with a victim shop's domain, e.g. `victim.myshopify.com`.

**After attacker's request:** `HmacValidator.validate` still succeeds (body/HMAC pair is untouched), but `request.shop` now returns `"victim.myshopify.com"`. `WebhookMetadata.shop` is `"victim.myshopify.com"` even though the signed body/content actually originated from shop A. If the host app uses `data.shop` to select which merchant's record/session/data to act on (as the library's own documentation instructs, e.g. `Shop.find_by(shopify_domain: data.shop)`), the attacker has forced processing of attacker-supplied webhook content under a victim tenant's identity — a cross-tenant integrity break.

### Impact Explanation
This is a cross-tenant identity-binding break: the field host applications are expected to trust as the request's tenant identifier (`shop`) is not covered by the same cryptographic proof that authenticates the request body. An attacker who legitimately installs the app on any shop can forge webhook deliveries that appear, to the host application, to originate from an arbitrary victim shop, potentially triggering tenant-scoped side effects (data updates, cache invalidation, redact/data-request flows, etc.) against a shop the attacker does not control. This matches the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high: the attacker only needs to install the app on any shop they control (a normal, unprivileged action) to obtain a valid `(body, hmac)` pair, and no `client_secret`, access token, or privileged credential is required. Any host application that follows this gem's documented pattern of dispatching on `data.shop` is exposed.

### Recommendation
Bind the tenant/topic identity into the signed material, or otherwise cryptographically verify that the claimed `shop` header matches the shop that actually owns the signed content — e.g., have `to_signable_string` include a canonicalized representation of `shop`/`topic`/`webhook_id` alongside the body, or require host applications to cross-check `request.shop` against an independently known, already-authenticated shop record before acting on webhook data. Short term, document explicitly (and ideally enforce in code) that `shop`, `topic`, `webhook_id`, and `api_version` are NOT authenticated by `HmacValidator.validate` and must not be used as the sole tenant-selection key without additional verification.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger any subscribed webhook topic (e.g. `products/update`) to receive a legitimate webhook POST with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid_hmac>`, and body `raw_body`.
3. Replay the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the HMAC: [3](#0-2) 
5. `WebhookMetadata.shop` is populated with `"victim.myshopify.com"`, and the host application's handler processes attacker-supplied content under the victim's tenant identity.
