Audit Report

## Title
Dry-run vs. real-transaction `CREATE1` address mismatch in `pallet-revive` due to missing `ExecContext` check - ([File: substrate/frame/revive/src/exec.rs])

## Summary
The current code in `Storage::new_frame` (`substrate/frame/revive/src/exec.rs`, lines 1141–1158) derives the `CREATE1` contract address by subtracting 1 from the account nonce whenever `origin_is_caller` is true, with no distinction between a dry-run/RPC simulation and a real dispatched transaction. `prdoc/stable2506/pr_8504.prdoc` documents that this exact code was the "before fix" state of a known bug (Fixes paritytech/contract-issues#37) and that the actual fix required gating the subtraction on `matches!(exec_context, ExecContext::Transaction)`, but a repository-wide search shows the identifier `ExecContext` exists only in the prdoc file and nowhere in `exec.rs` or the rest of the `pallet-revive` crate.

## Finding Description
`Storage::new_frame`'s `FrameArgs::Instantiate` branch computes: [1](#0-0) 

```rust
FrameArgs::Instantiate { sender, executable, salt, input_data } => {
    let deployer = T::AddressMapper::to_address(&sender);
    let account_nonce = <System<T>>::account_nonce(&sender);
    let address = if let Some(salt) = salt {
        address::create2(&deployer, executable.code(), input_data, salt)
    } else {
        use sp_runtime::Saturating;
        address::create1(
            &deployer,
            // the Nonce from the origin has been incremented pre-dispatch, so we
            // need to subtract 1 to get the nonce at the time of the call.
            if origin_is_caller {
                account_nonce.saturating_sub(1u32.into()).saturated_into()
            } else {
                account_nonce.saturated_into()
            },
        )
    };
```

`origin_is_caller` gates the "-1" adjustment without any check on whether execution is a dry run (RPC simulation, no pre-dispatch nonce increment) or a real dispatched transaction (nonce already incremented pre-dispatch). `prdoc/stable2506/pr_8504.prdoc` documents this exact snippet as the pre-fix bug and states the fix adds `&& matches!(exec_context, ExecContext::Transaction)` to the condition, plus a regression test `nonce_not_incremented_in_dry_run()`. A grep for `ExecContext` across the repository returns matches only inside `prdoc/stable2506/pr_8504.prdoc`, confirming that the described fix was never applied to `exec.rs` in this snapshot — the live code is byte-for-byte the "Before Fix" version described in the prdoc.

## Impact Explanation
When `Storage::new`/`new_frame` is invoked through the dry-run/RPC path with `origin_is_caller = true` (no salt, i.e. `CREATE1`), the returned predicted address is derived using `account_nonce - 1`, while the real dispatched extrinsic (where `frame_system` has already incremented the nonce pre-dispatch) derives the address using the same subtraction against the post-increment nonce — producing different addresses for the simulated vs. actual deployment. This breaks the address-prediction guarantee that off-chain tooling/wallets rely on for Ethereum-JSON-RPC-style `eth_estimateGas`/contract-creation previews, causing tooling to reference, fund, or whitelist an address the deployed contract will never occupy.

## Likelihood Explanation
This is deterministically reachable by any unprivileged user simply by performing a dry-run instantiate (no salt) followed by a real signed `instantiate`/`instantiate_with_code` extrinsic from the same account — no special preconditions, privileged roles, or victim mistakes are required. The bug is not theoretical; it is directly confirmed by comparing the shipped code against the prdoc's own "before fix" snippet, and the absence of `ExecContext` anywhere in the implementation confirms the described mitigation was never merged into this code path.

## Recommendation
Introduce an execution-context distinction (e.g., restore the `ExecContext` enum and thread it through `new`/`new_frame`) so the nonce subtraction in the `CREATE1` branch of `Storage::new_frame` only applies when `origin_is_caller && matches!(exec_context, ExecContext::Transaction)`, matching the intended semantics described in `prdoc/stable2506/pr_8504.prdoc`. Add the `nonce_not_incremented_in_dry_run` regression test referenced in the prdoc to lock in correct behavior for both dry-run and real-transaction paths.

## Proof of Concept
1. Call the dry-run/bare instantiate path (`Storage::new` via `bare_instantiate`) for account `A` at nonce `N` with `salt = None`; since `origin_is_caller` is true and the nonce has not been pre-incremented in the dry-run context, `new_frame` computes `create1(deployer, N-1)`.
2. Submit the real signed `instantiate`/`instantiate_with_code` extrinsic for the same account `A`; by the time `new_frame` executes, `frame_system` has already incremented the nonce pre-dispatch to `N+1`, and the same subtraction computes `create1(deployer, N)`.
3. Compare the two addresses: `create1(deployer, N-1)` (dry-run result) vs. `create1(deployer, N)` (actual deployed address) — they differ, confirming the mismatch exactly as described in `prdoc/stable2506/pr_8504.prdoc`'s "Before Fix" section.
