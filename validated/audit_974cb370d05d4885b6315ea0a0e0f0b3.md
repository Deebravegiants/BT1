### Title
Webhook HMAC validation covers only the request body, allowing shop/topic/webhook-id spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw JSON body, so `Utils::HmacValidator.validate` authenticates *only the body bytes*. The `shop`, `topic`, `webhook_id`, and `api_version` values — all taken directly from unauthenticated HTTP headers — are never covered by the HMAC, yet `Registry.process` trusts them to build `WebhookMetadata` and route/identify the tenant. This is the same identity-binding break as the Popcorn Vault report: a value (`shop`) that is *acted upon* (used as the tenant key passed to the app's handler) is not the same value that is *cryptographically bound* (only the body is signed).

### Finding Description
In `lib/shopify_api/webhooks/request.rb`:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
...
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`Registry.process` only checks:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
``` [2](#0-1) 

`Utils::HmacValidator.validate_signature` recomputes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac-sha256` header:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [3](#0-2) 

Because `to_signable_string` is `@raw_body` alone, the equality that the app implicitly relies on — "the shop/topic that generated this signed byte string == the shop/topic delivered to the handler" — is never enforced. The `shop-domain`, `topic`, and `webhook-id` headers can be altered in transit/replay without invalidating the HMAC, since they were never part of the signed content.

The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify," implying full request authenticity, which is contradicted by the fact that only the body is signed: [4](#0-3) 

### Impact Explanation
A user who legitimately installs the app on their own shop receives genuinely Shopify-signed webhook deliveries (signed with the app's real `api_secret_key` by Shopify's own servers — no secret knowledge required by the attacker). Because the HMAC only signs the body, that same attacker can replay the identical body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header to point at a different, victim shop. The signature check still passes, and the app's handler will process the attacker-controlled body under the victim shop's tenant identity (`data.shop`), e.g. triggering shop-scoped side effects (data updates, redaction flows, job enqueuing keyed by `shop_domain`) attributed to the wrong tenant. This is a cross-tenant identity-binding bypass reachable without any credential beyond having installed the app once as an ordinary merchant.

### Likelihood Explanation
Medium-High. It requires only that the app has at least one installed shop (any user can install an app) to obtain a validly-signed webhook body, then a trivial header substitution and replay to the app's public webhook callback route. No `api_secret_key`, access token, or privileged account is needed — only observation of one's own legitimately delivered webhook request.

### Recommendation
Bind the identity fields into the signed content, or otherwise independently verify them against a trusted source (e.g., known registered shop domains) before dispatching to handlers:
- Include `shop`, `topic`, and `webhook_id` in `to_signable_string` (this requires coordinating with how Shopify actually signs webhooks — since Shopify signs only the body by design, the gem should instead validate `shop-domain` against the set of shops for which the app holds an active session/registration before trusting `request.shop`), and/or
- Explicitly document and enforce that host applications must independently authorize `request.shop` before acting on webhook data, rather than treating `Registry.process`'s HMAC check as full authentication of the shop/topic.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; Shopify delivers a legitimate webhook (e.g., `customers/data_request`) to the app's callback with a valid `X-Shopify-Hmac-Sha256` computed over the raw body using the app's real secret.
2. Attacker captures this exact `raw_body` + `hmac-sha256` header value.
3. Attacker resends the same body/HMAC to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
4. `Utils::HmacValidator.validate` passes because `to_signable_string` never included the header values. [5](#0-4) 
5. `Registry.process` invokes the handler with `WebhookMetadata` carrying `shop: "victim-shop.myshopify.com"` and the attacker's body, despite the request never having been produced by or for that shop. [6](#0-5)
