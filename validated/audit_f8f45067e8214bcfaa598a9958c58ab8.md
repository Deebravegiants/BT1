### Title
Webhook `shop` Identity Not Covered by HMAC Allows Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` (and `topic`/`webhook-id`) values are taken from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only the body HMAC and then hands the header-derived `shop` straight to the app's handler as trusted metadata, breaking the binding between "the entity whose signature was verified" and "the entity the handler believes the event came from."

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#hmac` is read from the `hmac-sha256` header rather than derived from any shop-bound value [2](#0-1) . The `shop` accessor is pulled straight from the `shop-domain` header with no cryptographic linkage to the signed body [3](#0-2) .

`Registry.process` validates only `Utils::HmacValidator.validate(request)` (i.e., body+secret) and then constructs `WebhookMetadata` using `request.shop` unconditionally, passing it to the app's registered handler as if it were verified [4](#0-3) . `HmacValidator.validate_signature` compares the HMAC computed from `verifiable_query.to_signable_string` (the raw body only) against the received signature [5](#0-4) .

The broken identity binding, stated as an equality that should hold but does not:
`shop_authenticated_by_hmac == shop_delivered_to_handler`

In this gem, the left side is undefined (the HMAC never covers `shop`), while the right side is attacker-controlled via the `x-shopify-shop-domain` / `shopify-shop-domain` header. Because a valid HMAC only proves "this body was produced with the app's secret for *some* delivery," and that proof is completely independent of which shop header accompanies the request, an attacker who is a legitimate merchant on their own installed shop can:
1. Receive one genuine webhook delivery (valid `raw_body` + valid `hmac-sha256`) for their own shop.
2. Replay that same `raw_body`/`hmac-sha256` pair to the app's webhook endpoint, substituting the `x-shopify-shop-domain` header with a victim shop's domain.
3. `Registry.process` validates the (unchanged) HMAC successfully and invokes the handler with `WebhookMetadata#shop` set to the victim's domain and the attacker's own body content, since nothing ties the header to the signed bytes.

### Impact Explanation
This is a cross-tenant identity spoofing vector: the gem passes an unauthenticated `shop` claim to the host application as if it had been cryptographically verified alongside the body. Any host app that uses `WebhookMetadata#shop` to select which merchant's records to create/update/delete (the documented, expected use of this field) can be made to apply attacker-supplied webhook data to another tenant's data, i.e., cross-tenant access/write triggered entirely through this gem's own webhook verification API.

### Likelihood Explanation
Requires the attacker to control at least one installed shop that receives real webhook deliveries from the app (a low bar for any public app), and does not require the app's `client_secret`, an access token, or any credential beyond installing the app on their own store. The replay is a simple HTTP request with two headers changed.

### Recommendation
Bind the shop identity into the verified material: either include the `shop-domain` header (and `topic`/`webhook-id`) in the signable string used by `HmacValidator`, or independently verify that `request.shop` matches an actively registered/authorized shop for the receiving app before constructing `WebhookMetadata`, rather than trusting the raw header value once only the body's HMAC has been checked.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com`:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid HMAC of raw_body>
x-shopify-shop-domain: shop-a.myshopify.com

{"id": 123, "note": "attacker-controlled content"}
```
2. Attacker captures `raw_body` and `x-shopify-hmac-sha256` (both valid, since they own `shop-a`).
3. Attacker resends the identical body/signature but changes the shop header:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <same valid HMAC>
x-shopify-shop-domain: victim-shop.myshopify.com

{"id": 123, "note": "attacker-controlled content"}
```
4. `Registry.process` at [4](#0-3)  validates the HMAC (passes, unchanged body) and calls the handler with `shop: "victim-shop.myshopify.com"`, causing the app to process attacker-controlled data under the victim's tenant identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
