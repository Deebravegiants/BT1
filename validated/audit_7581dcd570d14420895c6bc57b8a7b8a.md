### Title
Phantom bid weight derived from live Uniswap V4 spot price lets a solver manipulate pool price and inventory depth with minimal capital - (File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts)

### Summary
`aggregatePhantomBids` weights each solver's phantom bid quote by that solver's on-chain inventory, including any declared Uniswap V4 position's withdrawable amount of the leg's output token. That amount is computed live from the position's `liquidity`, tick range, and the **current spot `sqrtPriceX96`** read from the pool's `StateView.slot0` at aggregation time [1](#0-0) . This is structurally identical to the C4 finding: an economically important value (fee/premium there, inventory weight/price here) is snapshotted from a manipulable spot AMM state rather than a time-weighted or capped source.

### Finding Description
The weight computation calls `positionAmountOfToken`, which converts a position's `liquidity` into token amounts using the pool's live `sqrtPriceX96` [2](#0-1) . Because the position may be entirely token0 or entirely token1 depending on where the current price sits relative to the position's tick range [3](#0-2) , a solver who nudges the spot price of the declared pool (e.g., via a small swap immediately before/around the bid window) can dramatically inflate the reported weight for the leg's output token without adding new capital of that token.

The weight then determines whether a bid dominates `weightedMedian` — per the documented behavior, "a solver holding over half the leg's weight sets the published price verbatim" [4](#0-3) . Because zero-weight quotes are dropped entirely and legs with no backed quote vanish [5](#0-4) , inflating one's own weight via spot-price manipulation can also crowd out other legitimate bidders' influence on the median, letting the manipulator set the leg's price.

This median price is not merely advisory — it is written into `PoolChainLiquidity`/`PoolRoute` rows and merged into the pool's `sellRate`/`buyRate` via a depth-weighted mean [6](#0-5) , and the same declared-position weight is swept into `lpBalances`/`SolverInventoryReading` used elsewhere to size the solver's depth and bidder eligibility [7](#0-6) .

This mirrors the C4 report's root cause exactly: the protocol trusts a spot on-chain reading (fee growth there, `sqrtPriceX96`-derived token amount here) for an economically consequential calculation, and that spot value is trivially moved by whoever controls liquidity/trading around the relevant pool, at gas + swap-fee cost only.

### Impact Explanation
A manipulator who owns even a modest Uniswap V4 position can push the pool's spot price briefly so their declared position appears to hold outsized inventory of the leg's output token. This lets them (a) win outsized weight in `weightedMedian` and set the published leg price to a value they choose ("sets the published price verbatim"), and (b) inflate their reported liquidity depth (`PoolChainLiquidity`, `SolverInventoryReading`) which is consumed by downstream pricing/route selection (`resolvePoolLeg`, `weightedRate`) and by other components of the SDK/simplex FX pricing pipeline that read pool rates. Mispriced legs can mislead order placers' `quoteOrderFees`/fill decisions and cause economic loss to counterparties trusting the published rate, analogous to the borrower being forced to overpay premium in the original report.

### Likelihood Explanation
As in the original C4 discussion, this requires the attacker to already hold (or open) a Uniswap V4 position on the relevant pool and time a price move around the aggregation window — a cost roughly equal to swap fees plus gas versus the gain from dominating a leg's median or depth. It is impractical against genuinely deep, competitive pools with many honest LPs/bidders (mirroring the "impractical unless dominant LP" debate in the original report), but becomes feasible on newer or thinner pools/tick ranges, or narrow-range positions deliberately opened to make small price nudges disproportionately swing `positionAmountOfToken`. The judge in the original report kept this Medium because "not infeasible" — the same reasoning applies here.

### Recommendation
Avoid pricing/weighting solver inventory purely off a single spot `sqrtPriceX96` read. Options: use a TWAP-derived price for `positionAmountOfToken`, cap the influence any single position/solver can have on a leg's weight (e.g., a maximum weight share per bidder before falling back to true median instead of "verbatim" selection), or require multiple price observations across a short window before trusting a declared-position valuation to dominate a leg.

### Proof of Concept
1. Attacker opens (or already holds) a narrow-range Uniswap V4 position on the pool backing a phantom order's leg output token, per `declaration.uniswapV4Positions` in a phantom bid [8](#0-7) .
2. Immediately before/around the bid window, attacker performs a swap on that pool to move `sqrtPriceX96` so the position is valued (per `getAmountsForLiquidity`) almost entirely in the leg's output token, inflating `positionAmountOfToken` for that token far beyond what the position's collateral value would suggest at a fair/TWAP price [9](#0-8) .
3. Attacker's phantom bid is aggregated; `weights` for that leg use the manipulated `readPosition` result, giving the attacker outsized weight [1](#0-0) .
4. If the attacker's weight exceeds half the leg's total, `weightedMedian` picks their exact quoted price as the leg's `medianPrice`/`lowestPrice`/`highestPrice`, published as the market rate for that pool/leg [4](#0-3) .
5. Attacker reverses the price-moving swap after the snapshot is taken, retaining the manipulated pricing/depth influence at the cost of only swap fees and gas.

/**
 * The token0/token1 amounts `liquidity` is worth at the current price, mirroring
 * LiquidityAmounts.getAmountsForLiquidity.
 *
 * Below its range a position is entirely token0, above it entirely token1, and inside it holds
 * both — which is why a declared position's contribution to a leg depends on which side that leg
 * pays out, and why it can legitimately be zero.
 */
export function getAmountsForLiquidity(params: {
	sqrtPriceX96: bigint
	sqrtRatioAX96: bigint
	sqrtRatioBX96: bigint
	liquidity: bigint
}): { amount0: bigint; amount1: bigint } {
	let { sqrtRatioAX96, sqrtRatioBX96 } = params
	const { sqrtPriceX96, liquidity } = params
	if (sqrtRatioAX96 > sqrtRatioBX96) [sqrtRatioAX96, sqrtRatioBX96] = [sqrtRatioBX96, sqrtRatioAX96]

	const amount0For = (from: bigint, to: bigint) => (liquidity * Q96 * (to - from)) / to / from
	const amount1For = (from: bigint, to: bigint) => (liquidity * (to - from)) / Q96

	if (sqrtPriceX96 <= sqrtRatioAX96) {
		return { amount0: amount0For(sqrtRatioAX96, sqrtRatioBX96), amount1: 0n }
	}
	if (sqrtPriceX96 < sqrtRatioBX96) {
		return {
			amount0: amount0For(sqrtPriceX96, sqrtRatioBX96),
			amount1: amount1For(sqrtRatioAX96, sqrtPriceX96),
		}
	}
	return { amount0: 0n, amount1: amount1For(sqrtRatioAX96, sqrtRatioBX96) }
}

export function positionAmountOfToken(params: {
	info: PoolAndPositionInfo
	liquidity: bigint
	sqrtPriceX96: bigint
	outputToken: string
}): bigint {
	const { info, liquidity, sqrtPriceX96 } = params
	const outputToken = params.outputToken.toLowerCase()
	if (outputToken !== info.currency0 && outputToken !== info.currency1) return 0n
	if (liquidity <= 0n || sqrtPriceX96 <= 0n) return 0n

	const { amount0, amount1 } = getAmountsForLiquidity({
		sqrtPriceX96,
		sqrtRatioAX96: getSqrtRatioAtTick(info.tickLower),
		sqrtRatioBX96: getSqrtRatioAtTick(info.tickUpper),
		liquidity,
	})
	return outputToken === info.currency0 ? amount0 : amount1
