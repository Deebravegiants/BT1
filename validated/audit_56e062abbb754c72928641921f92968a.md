### Title
Unauthenticated `CallDispatcher.dispatch()` allows theft of any tokens/ETH stranded in the shared dispatcher contract - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher` is a single, shared, unauthenticated relay contract used by `IntentGatewayV2` (predispatch swaps, output/postdispatch calldata execution, and solver-fee swaps) to temporarily hold user/solver tokens while executing arbitrary `Call[]` sequences. Its `dispatch()` function has no access control — literally anyone can call it directly with an arbitrary `Call[]` payload. This mirrors the Silo Labs bug class: an unprivileged actor supplying attacker-controlled call parameters (`_swapArgs`-equivalent) to a contract that holds pooled balances/approvals from other users, resulting in unauthorized extraction of value that was never meant to be reachable by that caller.

### Finding Description
`CallDispatcher.dispatch()` is `external` with no caller restriction: [1](#0-0) 

`IntentGatewayV2.placeOrder()` transfers user input tokens into this same dispatcher *before* invoking `dispatch()` on the predispatch calls, then issues a second `dispatch()` call to sweep the resulting balances back to the gateway: [2](#0-1) 

Similarly, `IntentsBase._execute()` forwards output tokens to the dispatcher, executes solver-supplied postdispatch calldata, then sweeps back only the tokens explicitly listed in `order.output.assets`: [3](#0-2) 

Because the dispatcher is a shared singleton with no owner/caller check, and the sweep-back logic only accounts for tokens known to the calling flow (the declared `order.inputs` / `order.output.assets` list), any token that is not part of that declared set — e.g., an intermediate hop token from a multi-step swap (WETH from an unwrap, a router's native refund, unconsumed approval residue, or rounding/slippage dust from a `predispatch`/`postdispatch` swap) — is left sitting in the `CallDispatcher` contract's balance or allowance state after the transaction completes. The documentation itself acknowledges standing approvals can be left behind ("Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution"), confirming this is a known residue risk that the code does not enforce.

Because `dispatch()` is callable by anyone, an attacker can submit their own transaction directly to `CallDispatcher.dispatch()` with a crafted `Call[]` (e.g., `{to: strandedToken, data: transfer(attacker, balance)}` or, if a router approval was left standing, a call that spends that allowance) to sweep out any balance/allowance the contract is holding at that moment — funds that belong to the protocol (accounted as "dust" in the gateway's internal bookkeeping) or to a user/solver mid-composition. This is directly analogous to the Silo Labs incident, where an unprivileged caller manipulated a parameter passed into a shared contract to execute unauthorized value-extracting calls against balances/approvals that other parties had left there.

### Impact Explanation
This is Medium severity: any stranded ERC-20/native balance or approval on the `CallDispatcher` (from incomplete sweeps of non-listed intermediate tokens, failed dust accounting, or approvals granted by predispatch/postdispatch `Call[]` sequences) can be permanently and unilaterally extracted by an unrelated third party with a single transaction, with no authentication and no way for the protocol or affected user to prevent it once the residue exists. This constitutes concrete theft of funds reachable from a single submitted transaction, matching the Silo Labs bug class of an unprivileged caller draining value via a manipulable call to a shared, under-guarded contract.

### Likelihood Explanation
Likelihood is Medium: it requires funds/allowances to actually be left in `CallDispatcher` outside of the atomic sweep performed by the calling gateway logic. This can occur through multi-hop swaps where an intermediate token isn't in the declared `assets`/`inputs` list, rounding dust from swap routers, or a Uniswap-router approval that isn't fully consumed in a single call (explicitly warned about in the docs). Given the dispatcher is a shared, long-lived singleton used across many `placeOrder`/`fillOrder` calls from arbitrary users and solvers, and its `dispatch()` entrypoint is fully public, any accumulation of residue is trivially and immediately exploitable by a bot monitoring the dispatcher's balance.

### Recommendation
Restrict `CallDispatcher.dispatch()` to a caller allow-list (e.g., only the registered `IntentGatewayV2`/HFT contracts that are meant to use it), or better, deploy an ephemeral/ per-call dispatcher (e.g. via `CREATE2`/minimal proxy per invocation) so no shared contract persists between calls. At minimum, enforce that the dispatcher never retains a nonzero balance of any token or a standing approval after `dispatch()` returns (revert if residual balance detected for tokens touched during the call), removing the incentive/target for direct unauthenticated `dispatch()` calls.

### Proof of Concept
1. A user calls `IntentGatewayV2.placeOrder()` with a `predispatch.call` that swaps ETH → DAI via a multi-hop path through an intermediate token (e.g., ETH → WETH → USDC → DAI), where only DAI is declared in `order.inputs`.
2. Due to slippage/rounding, a small amount of the intermediate `USDC` remains in `CallDispatcher` after the sweep call in `IntentGatewayV2.placeOrder()` (lines 260–289) collects only the declared input tokens.
3. An attacker observes the `CallDispatcher`'s non-zero USDC balance on-chain and submits a direct transaction: `CallDispatcher.dispatch(abi.encode([Call({to: USDC, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, strandedBalance)})]))`.
4. Since `dispatch()` has no access control, the call succeeds and the attacker receives the stranded tokens with no interaction from the gateway or governance.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
