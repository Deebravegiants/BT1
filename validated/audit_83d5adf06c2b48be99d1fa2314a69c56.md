## Title
Webhook shop identity (and topic/webhook-id) not covered by HMAC signature — allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` only includes the raw HTTP body in the HMAC-signed payload, while the `shop-domain` (and `topic`, `webhook-id`) HTTP headers — used later to route and identify the tenant the webhook belongs to — are read directly from unauthenticated headers. This breaks the identity binding `shop authenticated == shop acted upon`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `#shop`, `#topic`, and `#webhook_id` are pulled straight from HTTP headers with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then forwards the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` straight to the app's handler as the source of truth for which tenant/topic the payload belongs to: [3](#0-2) 

`Utils::HmacValidator.validate` only compares `verifiable_query.hmac` against a signature computed from `to_signable_string` (i.e., the body), never touching `shop`, `topic`, or `webhook_id`: [4](#0-3) 

Because the shared secret (`api_secret_key`) is per-app, not per-shop, any merchant who installs the app on their own store can capture a legitimate `(raw_body, hmac)` pair delivered by Shopify to the app's webhook endpoint. That pair remains a valid signature no matter which `shop-domain`/`topic`/`webhook-id` headers are attached, because those headers are never part of the signed content. The attacker can then replay the same body+HMAC to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header, and the gem will report the payload as authenticated and originating from the victim shop.

This is exactly the "field acted on but not covered by the HMAC" identity-binding break: the equality that should hold is
`hmac_signed(shop, topic, webhook_id, body) == (shop, topic, webhook_id, body) used by the app`,
but the gem only enforces `hmac_signed(body) == body`, leaving `shop`, `topic`, and `webhook_id` unauthenticated.

### Impact Explanation
This crosses a tenant boundary: a host application relying solely on this gem's `Registry.process`/`HmacValidator.validate` to authenticate webhooks can be made to process attacker-supplied `shop`, `topic`, and `webhook_id` values attributed to a different merchant than the one who actually triggered the webhook. Depending on the handler logic (e.g. `shop/redact`, `customers/redact`, `orders/*`, `app/uninstalled`), this can lead to cross-tenant data corruption, spoofed mandatory-compliance webhooks (redact/uninstall) against a shop that never requested it, or injection of attacker-controlled data attributed to a victim shop — satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation only requires: (1) the attacker installs the app on any shop they control (or otherwise triggers any webhook delivery to the app, which they can do simply by taking an action, e.g. placing/cancelling an order, in their own store) to obtain one valid `(body, hmac)` pair, and (2) sending an HTTP POST directly to the app's public webhook endpoint with the captured body/HMAC header but a forged `shop-domain`/`topic`/`webhook-id` header. No access token, `client_secret`, or privileged account is required — this is achievable by an unprivileged internet user/merchant.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (and any other header fields relied upon for routing/tenant identification) in the HMAC-signed payload — or, at minimum, require the caller/host app to independently verify that `request.shop` corresponds to a shop with an active, known session/installation before trusting it, and document that these headers are unauthenticated. Ideally, change `Request#to_signable_string` to bind the full identifying context, not just the raw body.

### Proof of Concept
1. Attacker installs the app on shop `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`) to capture the raw POST from Shopify, including `X-Shopify-Hmac-Sha256: <hmac>` and body `{"id":1,...}`.
2. Attacker sends the same raw body and the same `hmac` header directly to the app's webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim.myshopify.com` (and optionally a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body against the HMAC and succeeds:
```ruby
ShopifyAPI::Webhooks::Registry.process(
  ShopifyAPI::Webhooks::Request.new(
    raw_body: captured_body,
    headers: {
      "x-shopify-hmac-sha256" => captured_hmac,
      "x-shopify-topic" => "orders/create",
      "x-shopify-shop-domain" => "victim.myshopify.com", # forged
    }
  )
)
```
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and processes attacker-controlled data as if it belonged to the victim shop, despite the HMAC never having covered the shop field.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
