### Title
`begin_auth` builds the Shopify authorization URL from an unsanitized `shop` parameter, enabling forced OAuth completion / session fixation - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` accepts a caller-supplied `shop` value and uses it, completely unvalidated, to build the host that receives the app's `client_id`, requested `scope`, `redirect_uri`, and the anti-CSRF `state` nonce. The gem ships a `ShopifyAPI::Utils::ShopValidator.sanitize!` helper specifically meant to restrict `shop` to trusted Shopify domains, but `begin_auth` never calls it, and the gem's own documented usage example feeds an unsanitized header value straight into `begin_auth`.

### Finding Description
`begin_auth` computes the authorization redirect as: [1](#0-0) 

`auth_base_uri` performs no domain validation at all: [2](#0-1) 

Meanwhile the gem defines `ShopValidator.sanitize!`, whose entire purpose is to reject any `shop` that isn't a subdomain of `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.com`, `myshopify.io`, `spin.dev`, `shop.dev`): [3](#0-2) [4](#0-3) 

`begin_auth` never invokes `ShopValidator` anywhere in `lib/shopify_api/auth/oauth.rb`, and the gem's own documented integration example passes a raw request header directly into `begin_auth` with no sanitization step shown: [5](#0-4) 

The broken binding is:
`host that receives client_id/redirect_uri/state` (attacker-controlled `shop`) ≠ `host validated as a genuine Shopify domain` (never checked).

Because `state` is generated and stored only in a cookie on the victim's own browser (`SessionCookie.new(value: state, ...)`, line 38 of `oauth.rb`) and is also embedded in the URL sent to `auth_base_uri(shop)`, an attacker who controls the `shop` value receives that `state` nonce on their own server when the victim's browser is redirected there.

### Impact Explanation
This enables a forced OAuth completion / session-fixation attack:
1. Attacker lures the victim into the app's "begin auth" route with `shop=attacker-controlled-host`.
2. The victim's browser is redirected to `https://attacker-controlled-host/admin/oauth/authorize?...&state=<NONCE>&redirect_uri=<real_app_callback>`, leaking `client_id`, `redirect_uri`, and the fresh CSRF `state` nonce to the attacker, while the victim's browser retains a cookie binding that same `state`.
3. The attacker separately performs a legitimate install of the app on their own real, HMAC-valid `*.myshopify.com` store, obtaining a genuinely Shopify-signed callback URL (valid `hmac`, real `code`).
4. The attacker substitutes the `state` value in that legitimate callback with the nonce captured in step 2, and sends this crafted callback link to the victim.
5. `validate_auth_callback` accepts it: the HMAC is valid (it was genuinely signed by Shopify for the attacker's shop), and the state matches the victim's cookie: [6](#0-5) 

The victim's browser session then ends up bound to the attacker's own shop and access token — a cross-tenant session-fixation/forced-OAuth-completion condition, matching the explicitly in-scope High-impact class.

### Likelihood Explanation
Exploitation requires only that the host application pass an attacker-influenced `shop` value (e.g. a query parameter or header, as shown in the gem's own documented example) into `begin_auth` without separately calling `ShopValidator.sanitize!` first. Since the gem does not perform this validation internally and its own documentation does not demonstrate it, apps that follow the documented pattern verbatim are exposed. No credentials, tokens, or privileged access are required by the attacker.

### Recommendation
Call `ShopifyAPI::Utils::ShopValidator.sanitize!(shop)` inside `begin_auth` (and ideally also re-validate `auth_query.shop` inside `validate_auth_callback`) before using it to construct `auth_base_uri`, raising `Errors::InvalidShopError` for any host outside `TRUSTED_SHOPIFY_DOMAINS`. Update the documentation example to show sanitizing the shop parameter before calling `begin_auth`.

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]

          raise Errors::InvalidOauthError,

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end

class ShopifyAuthController < ApplicationController
  def login
    shop = request.headers["Shop"]

    # Builds the authorization URL route to redirect the user to
    auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")

    # Store the authorization cookie
    cookies[auth_response[:cookie].name] = {
      expires: auth_response[:cookie].expires,
      secure: true,
      http_only: true,
      value: auth_response[:cookie].value
    }

    # Redirect the user to "auth_response[:auth_route]" to allow user to grant the app permission
    # This will lead the user to the Shopify Authorization page
    head 307
    response.set_header("Location", auth_response[:auth_route])
  end
