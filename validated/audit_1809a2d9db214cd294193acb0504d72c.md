### Title
OAuth callback sends `client_secret` and authorization `code` to an unvalidated `shop` host - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` uses the raw `auth_query.shop` value — taken straight from caller-supplied query parameters — to build the session whose `shop` field determines the HTTPS host that receives the POST containing `client_id`, `client_secret`, and the authorization `code`. Unlike every other credential-exchange path in this gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`), this path never calls `Utils::ShopValidator.sanitize!` on the shop value before it is used to construct the outbound request host.

### Finding Description
`validate_auth_callback` in `lib/shopify_api/auth/oauth.rb` does: [1](#0-0) 

It validates the HMAC over the query (`code`, `host`, `shop`, `state`, `timestamp`) with `Utils::HmacValidator.validate(auth_query)`, and checks the `state` cookie, but never runs `auth_query.shop` through `Utils::ShopValidator.sanitize!`. It then builds `null_session = Auth::Session.new(shop: auth_query.shop)` and passes it to `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")`.

`HttpClient#initialize` derives the request host directly from `session.shop`: [2](#0-1) 

So the host that receives the POST body containing `client_secret` (and the authorization `code`) is `https://#{auth_query.shop}` — a value that is only integrity-checked via HMAC (proving it was signed with the app's secret at some point), but never checked for being a legitimate `*.myshopify.com`/trusted Shopify domain via `ShopValidator`.

This is the exact hardening pattern applied everywhere else credentials are sent:
- `ClientCredentials.client_credentials`: `validated_shop = Utils::ShopValidator.sanitize!(shop)` before building the session and sending `client_secret`. [3](#0-2) 
- `RefreshToken.refresh_access_token`: same pattern. [4](#0-3) 
- `TokenExchange.migrate_to_expiring_token`: same pattern. [5](#0-4) 

`Oauth.validate_auth_callback` is the odd one out: the binding it should enforce is `host_that_receives(client_secret, code) == ShopValidator.sanitize!(shop)`, but instead it enforces only `host_that_receives(client_secret, code) == auth_query.shop` (an HMAC-authenticated but domain-unvalidated string). Because `ShopValidator` exists specifically to reject attacker-controlled or lookalike domains (`evil.com`, `myshopify.com.evil.com`, `test-shop.notmyshopify.com`, userinfo tricks like `shop.myshopify.com@evil.com`) — as proven by its own test suite — its absence here means any code path that reaches `validate_auth_callback` with attacker-influenced `shop`/`hmac` values (e.g., a host application that doesn't itself validate the callback's shop domain before constructing the `AuthQuery`, or any future internal caller that forwards raw request parameters) will exfiltrate the app's `client_secret` and the OAuth `code` to the domain named in `shop`, with only the gem's own HMAC check as the sole guard, and no defense-in-depth against relaxed/duplicate params or non-Shopify hosts that other flows explicitly defend against.

### Impact Explanation
High: successful exploitation results in the app's `client_secret` (and the sensitive OAuth `code`, exchangeable for an access token) being transmitted to a domain string that is never validated against the trusted Shopify domain list, unlike every sibling code path in the same module. This is SSRF-with-credentials carrying the app's `client_secret`.

### Likelihood Explanation
Medium: exploitation requires a caller of `validate_auth_callback` to supply an `AuthQuery` whose `shop`/`hmac` pair the gem accepts without the host application performing its own shop-domain sanity check — a realistic scenario given the gem's own documentation examples build `AuthQuery` directly from raw `request.parameters` and rely on this method for validation, and given every other similar method in the codebase (`ClientCredentials`, `RefreshToken`, `TokenExchange.migrate_to_expiring_token`) treats `ShopValidator.sanitize!` as a mandatory step that `validate_auth_callback` conspicuously omits.

### Recommendation
In `lib/shopify_api/auth/oauth.rb`, sanitize `auth_query.shop` through `Utils::ShopValidator.sanitize!` before constructing `null_session` in `validate_auth_callback`, mirroring the pattern already used in `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token`. Use the sanitized value both for the outbound `HttpClient` session and for the returned `Session`'s `shop` field.

### Proof of Concept
1. Compare `lib/shopify_api/auth/oauth.rb` line 73 (`null_session = Auth::Session.new(shop: auth_query.shop)`) against `lib/shopify_api/auth/client_credentials.rb` line 25 (`validated_shop = Utils::ShopValidator.sanitize!(shop)`), `lib/shopify_api/auth/refresh_token.rb` line 24, and `lib/shopify_api/auth/token_exchange.rb` line 103 — all three call `ShopValidator.sanitize!` before building the session that determines the request host; `oauth.rb`'s callback path does not.
2. Trace `Clients::HttpClient#initialize` (`lib/shopify_api/clients/http_client.rb:16-19`): `@base_uri = "https://#{api_host || session.shop}"` — the unsanitized `shop` value directly becomes the destination host for the subsequent `client.request(...)` call in `validate_auth_callback` (`lib/shopify_api/auth/oauth.rb:81-94`), which sends `client_id`, `client_secret`, and `code` in the POST body.
3. `test/utils/shop_validator_test.rb` demonstrates the classes of malicious `shop` strings `ShopValidator.sanitize!` is designed to reject (`evil.com`, `myshopify.com.evil.com`, `test-shop.notmyshopify.com`, `shop.myshopify.com@evil.com`) — none of these protections apply on the `validate_auth_callback` path.

```ruby
        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end
```
