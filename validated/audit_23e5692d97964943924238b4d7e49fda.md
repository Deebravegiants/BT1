### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, allowing shop-domain spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the webhook's `shop` from the `x-shopify-shop-domain` HTTP header, but the HMAC signature that `Registry.process` verifies covers only the raw request body, never the shop header. Any request whose body/HMAC pair is valid for the app's shared `api_secret_key` will be accepted regardless of which shop the `shop-domain` header claims to be, breaking the binding `shop_verified_by_hmac == shop_trusted_by_handler`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)`, which in turn calls `verifiable_query.to_signable_string` (i.e., body only) and `verifiable_query.hmac`: [3](#0-2) [4](#0-3) 

After the HMAC check passes, the un-signed `request.shop` value is handed to the webhook handler as the tenant identifier without further verification: [5](#0-4) 

Because `api_secret_key` is a single app-wide secret shared across every shop that installs the app (not a per-shop secret), any merchant who installs the app can legitimately trigger a webhook delivery to their own endpoint with a valid HMAC for a given body, then replay that exact body/HMAC pair to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. The HMAC still validates (it only covers the body, which is unchanged) even though the `shop` claim is now attacker-controlled. This is the same class of bug as the reported `RLN.slashCommit`/`slashReveal` flaw: an identity field (`account` there, `shop` here) is used to key/route sensitive state but is never itself covered by the cryptographic check that is supposed to authenticate the request.

### Impact Explanation
If the host application (following this gem's documented pattern of trusting `WebhookMetadata#shop` from `Registry.process`) uses `shop` to route data (e.g., writing/deleting per-tenant records, triggering GDPR redaction flows via the mandatory `shop/redact` or `customers/redact` topics, or updating tenant-scoped settings), an attacker who controls one shop can inject spoofed webhook events into another shop's tenant context. This is a cross-tenant access primitive, matching the Critical impact bucket in scope.

### Likelihood Explanation
Any developer/merchant that can install the target app on a shop they control automatically receives real, validly-signed webhook deliveries (topic subscriptions are mandatory, e.g. `customers/data_request`, `customers/redact`, `shop/redact`), giving them body/HMAC pairs they can replay with an arbitrary `shop-domain` header. No access token, `client_secret`, or privileged account beyond "being an app installer" is required, and the exploit path is entirely within this gem's own `Webhooks::Request`/`Registry` code.

### Recommendation
Bind the shop identity into the signed material, or otherwise verify it out-of-band before trusting it: e.g., include the `shop-domain` header value in `to_signable_string` (matching Shopify's documented webhook verification, which signs the raw body only by design — so instead the gem should require callers to independently confirm the resolved `shop` has an active session/registration for the topic before dispatching), and/or reject processing when the shop asserted in the header does not match a shop known to have registered that specific webhook topic in `Registry`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets Shopify deliver a real `customers/data_request` webhook, capturing `raw_body` and the `x-shopify-hmac-sha256` value (both are visible to the attacker's own endpoint).
2. Attacker POSTs to the app's webhook endpoint with the same `raw_body` and same `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged header successfully (headers are only checked for presence, not authenticity) — see `lib/shopify_api/webhooks/request.rb:45-63`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and matches the attacker-supplied HMAC, since the body is unchanged — see `lib/shopify_api/webhooks/registry.rb:188-190` and `lib/shopify_api/utils/hmac_validator.rb:26-31`.
5. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, letting the attacker trigger tenant-scoped logic (e.g., a redaction/data-request handler) for `victim-shop` — see `lib/shopify_api/webhooks/registry.rb:198-199`.
