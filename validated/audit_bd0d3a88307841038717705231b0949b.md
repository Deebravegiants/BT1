Webhook `shop`, `topic`, and `webhook_id` identity fields are not covered by HMAC, allowing tenant/topic spoofing on replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the `shop`, `topic`, `api_version`, and `webhook_id` fields that identify *which tenant* and *which event* the payload belongs to are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then trusts these header-derived values to build the `WebhookMetadata` passed to the app's handler, breaking the binding between "bytes verified" and "identity acted on."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from the `X-Shopify-*` headers, none of which are part of the signed content: [2](#0-1) 

`HmacValidator.validate` only checks `hmac` against `to_signable_string` (the raw body) using the app's secret: [4](#0-3) 

`Registry.process` validates the request, then immediately builds `WebhookMetadata` (topic, shop, webhook_id) from the unauthenticated headers and dispatches it to the registered handler: [5](#0-4) 

`WebhookMetadata.shop` is a plain `String` field with no additional verification, and `WebhookHandler#handle` receives it as the trusted tenant identifier: [6](#0-5) 

This is exactly the class of bug the reference report describes for `BathBuddy`: state that an operation depends on (here, the tenant/topic identity used by the handler) is not covered by the same accounting/verification mechanism (the HMAC) that authenticates the payload. The binding that should hold is:

`hmac == HMAC(secret, raw_body || shop || topic || webhook_id)`

but the actual implementation only enforces:

`hmac == HMAC(secret, raw_body)`

leaving `shop`, `topic`, and `webhook_id` completely unauthenticated even though they are the fields the handler uses to decide which merchant/tenant and event type the data belongs to.

### Impact Explanation
An unprivileged internet user who can obtain any single genuine, validly-signed webhook body/HMAC pair (e.g., by installing the app on their own trial/development store, which requires no special privilege or secret) can replay that exact `raw_body` + `hmac-sha256` header to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header. Because the gem's HMAC validation only checks the body, the forged request passes validation, and the host application's handler is invoked believing the payload originates from the attacker-chosen shop and/or topic. This is a cross-tenant identity confusion: data attributable to the attacker's own shop is processed as belonging to another tenant of the app's choosing, or a payload is dispatched to a handler with a topic it wasn't actually issued for. Depending on what the host app's handler does with `shop` (e.g., look up records, update per-shop settings, or trigger side effects), this can lead to cross-tenant data corruption or unauthorized actions performed under a spoofed tenant identity, without ever needing the app's `api_secret_key`, an access token, or the merchant's credentials.

### Likelihood Explanation
Likelihood is moderate-to-high: obtaining one legitimately-signed webhook body/HMAC pair requires only installing the app once on any accessible store (a normal, unprivileged action for any developer/merchant), and replaying it with modified headers to the app's public webhook endpoint requires no cryptographic secret. The only constraint is that the raw body must remain byte-identical to what was originally signed (which is trivial to satisfy — replay the exact captured request body).

### Recommendation
Include the tenant/event identity fields in the signable content, or otherwise independently bind them to the verified payload:
- Extend `to_signable_string` (or add a separate verification step) to incorporate `shop`, `topic`, and `webhook_id` alongside `raw_body`, and have the app-side `HmacValidator` verify all of them together.
- Alternatively, since Shopify's own signature only covers the raw body by design, document clearly (and/or enforce in this gem) that consumers must independently confirm the `shop-domain` header corresponds to a shop with a valid, currently-installed session/access token before trusting it, rather than treating any HMAC-valid request as authoritative proof of tenant identity.

### Proof of Concept
1. Install the app on attacker-controlled store `attacker.myshopify.com`; trigger any webhook (e.g. `orders/create`) to capture a real request: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for secret `S`).
2. Send a forged HTTP POST to the app's public webhook endpoint with the same body `B` and header `X-Shopify-Hmac-Sha256: H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com` and/or a different `X-Shopify-Topic`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Utils::HmacValidator.validate(request)` succeeds because it only checks `B` against `H` — see: [7](#0-6) 
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(topic: forged_topic, shop: "victim.myshopify.com", body: parsed_body, ...)`, i.e., the host application processes attacker-supplied `body` under an arbitrary attacker-chosen `shop`/`topic` identity, despite the request never having originated from Shopify for that tenant/topic.
