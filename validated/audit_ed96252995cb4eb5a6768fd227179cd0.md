## Title
Manipulable spot-price venue pricing lets a flash-loan attacker drain Simplex's Uniswap V4 LP funds through mispriced intent fills - (File: `sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts`)

### Summary
Simplex's `UniswapV4FundingPlanner` prices "venue" pairs (pairs with no static bid/ask curve) directly off a Uniswap V4 pool's **instantaneous** `sqrtPriceX96`, with no TWAP, no size/impact term, and an *optional* deviation guard that most operators can (and per the docs may) leave unset. This mirrors the WSM exploit's bug class: an unbacked, single-block AMM spot price is trusted as the price oracle for a value-transferring action (there, `buyWithBNB`; here, sizing and filling an `IntentGatewayV2` order and, atomically, withdrawing LP inventory to fund it).

### Finding Description
`UniswapV4FundingPlanner.getExoticTokenPrice` / `computeDirectPoolPriceUsd` read the pool's current tick/`sqrtPriceX96` and hand back "the raw pool mid" as the USD price for the exotic token: [1](#0-0) 

This is consumed by `FXFiller.resolveLegRates`/`referenceRate` in `fx.ts` to price an intent order's legs whenever the pair is "curveless" and quoted against a USD stable: [2](#0-1) 

The only defense is `checkPriceGuard`, which compares the live pool quote to a *static* `referencePrice` within `maxDeviationBps` — and it is explicitly optional: [3](#0-2) [4](#0-3) 

Even when configured, the guard only checks deviation from a static number, not execution cost/impact, and the pool's own fee tier is stored but never applied to the price used for sizing: [5](#0-4) 

Crucially, the funding side is on-chain and atomic with the fill: LP withdrawal calls are prepended to the same `UserOperation` batch that fills the order, so the solver's actual delivery of exotic tokens is computed from — and executed alongside — this manipulable spot price: [6](#0-5) 

This is the same root cause as the WSM report: a flash-loan-movable AMM spot price (no TWAP) is used directly as the input to a value-releasing operation, with only an optional/soft guard.

### Impact Explanation
An attacker who flash-loan-manipulates the referenced Uniswap V4 pool (the pool paired with USDC/USDT for the exotic token) skews `getExoticTokenPrice`'s "raw pool mid." If (a) no `referencePrice`/`maxDeviationBps` guard is configured for that chain (the docs call this the default, unguarded state), or (b) the guard band is wide enough to still allow a profitable deviation, a subsequently placed `IntentGatewayV2` order priced against that pool gets filled by the solver at the distorted rate. Because LP withdrawal from the Uniswap V4 position is batched atomically with the fill, the solver can be made to release more exotic tokens (or accept less USD) than the true market rate justifies, directly transferring solver-held LP value to the attacker's counter-order. This is concrete theft of solver/protocol funds reachable purely by an unprivileged party placing/filling intents around a self-manipulated pool — matching the "intent solver" reachable path called out in scope.

### Likelihood Explanation
Likelihood is contingent on operator configuration: chains/positions without `referencePrice`/`maxDeviationBps` set are "left unguarded" by design, and the documentation itself warns pool-based pricing "leaves the solver exposed to a manipulated, stale, or thin pool." Thinly-liquid exotic-token pools (the exact profile Simplex targets — e.g., cNGN) are cheapest to move with a flash loan, and no TWAP or size/impact correction exists even when the guard is enabled, only a static-reference deviation check.

### Recommendation
- Require the price guard (`referencePrice`/`maxDeviationBps`) to be mandatory, not optional, for any curveless venue-priced pair, and fail closed if unset — the current opt-in design leaves unconfigured chains fully exposed.
- Replace or augment the instantaneous `sqrtPriceX96` mid with a TWAP/observation-based price (Uniswap V4 truncated oracle observations) so a single-block flash loan cannot move the quoted price.
- Apply the pool's fee tier and a size/impact term when deriving `computeDirectPoolPriceUsd`, rather than linearly extending the raw mid across the whole notional.
- Consider bounding LP-withdrawal-funded fills to a maximum deviation from a slower-moving external reference (e.g., recent fills, oracle feed) independent of the same pool being priced.

### Proof of Concept
Conceptually mirroring the WSM PoC's flash-loan-then-manipulate pattern:
1. Attacker takes a flash loan and swaps heavily against the exotic-token/USDC Uniswap V4 pool that backs a Simplex `[vault.uniswapV4]` position with no `referencePrice` guard configured, pushing `sqrtPriceX96` far from the fair value.
2. Attacker (or a colluding/second account) places an `IntentGatewayV2` order for that pair; the FXFiller's `resolveLegRates` → `getVenueUsdPrice` → `computeDirectPoolPriceUsd` prices the fill off the now-skewed pool mid, since `checkPriceGuard` passes trivially (no guard) or within an overly wide band.
3. The solver's `SolverAccount` UserOperation batches the Uniswap V4 LP withdrawal (`UniswapV4FundingPlanner.planWithdrawalForToken`) with `fillOrder`, delivering an inflated amount of the exotic token to the attacker's beneficiary at the manipulated rate.
4. Attacker reverses the initial swap to restore the pool price and repays the flash loan, netting the difference between the manipulated fill and the true market rate as profit, at the solver's expense.

		pos: HydratedV4Position,
		sdkPool: V4Pool,
		chain: string,
	): { exoticToken: string; priceUsd: Decimal } | null {
		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {
				exoticToken: c1,
				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

		if (c1 === usdc || c1 === usdt) {
			// currency1 is stable → exotic is currency0
			// token0Price = "token1 per token0" = USD per exotic
			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),
			}
		}

		return null
	}

	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}

```text
## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
```
