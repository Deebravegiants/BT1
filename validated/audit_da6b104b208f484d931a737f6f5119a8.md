### Title
Malicious `payer`/`relayer` address can permanently block POST/GET timeout processing and message finalization via forced fee-transfer revert - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchTimeOut(PostRequestTimeout)`, `dispatchTimeOut(GetRequestTimeout)`, and `dispatchIncoming(GetResponse)` all push protocol/relayer fees directly to an externally-controlled address (`meta.sender`/`relayer`) inside the same atomic call that performs the request's terminal state transition (deleting `_requestCommitments`, invoking the app's timeout callback, or crediting a relayer). If that fee token transfer to the designated recipient reverts, the entire call reverts, so the request/response can never be finalized — reproducing the exact "push payment blocks the whole operation" pattern from the PuttyV2 report, but here the un-guarded destination is attacker-influenced (`post.payer`) rather than the contract owner.

### Finding Description
When an app dispatches a POST request via `EvmHost.dispatch(DispatchPost memory post)`, the fee metadata is stored as: [1](#0-0) 

using `post.payer` supplied by the calling contract — this value is not constrained to `msg.sender`, so any unprivileged app/dispatcher can set it to an arbitrary address, including a contract engineered to revert on receiving `feeToken()` (e.g. via an ERC777 `tokensReceived` hook, or simply a token with blacklist/pausable transfer semantics where the address later becomes disallowed).

When the request times out, `HandlerV2.handlePostRequestTimeouts` calls `host.dispatchTimeOut` directly (no try/catch): [2](#0-1) 

Inside `dispatchTimeOut(PostRequestTimeout)`, the commitment is deleted, the app's `onPostRequestTimeout` callback is invoked, and only *after* that succeeds is the fee refunded via an unconditional `safeTransfer` to `meta.sender` (the attacker-controlled `payer`): [3](#0-2) 

The identical pattern exists for GET request timeouts, refunding `meta.sender`: [4](#0-3) 

and for GET responses, rewarding the `relayer` argument supplied by whoever calls `handleGetResponses`: [5](#0-4) 

Since none of these transfers are wrapped in a try/catch or deferred to a pull-based withdrawal, a revert during the `safeTransfer` call unwinds the *entire* external transaction — including the app-level state changes that were supposed to release/refund escrowed assets for that specific request (e.g., an intents/token-gateway app's `onPostRequestTimeout` handler that would otherwise unlock a user's escrowed funds). Because every future relayer submission of the same timeout proof re-executes the identical code path, the transfer will revert every time, making the timeout permanently non-deliverable and freezing whatever funds that specific request's timeout was meant to release.

### Impact Explanation
This is a direct analog of the PuttyV2 finding: an unconditional "push" of tokens to an externally-designated address, embedded in a state-mutating function, that can be made to always revert, thereby permanently blocking legitimate state transitions (timeouts/finalization) and freezing funds tied to that message. Any app built on top of Hyperbridge that escrows value pending a POST timeout (e.g., IntentGatewayV2/TokenGateway-style refund-on-timeout flows) can have that specific order's refund permanently stuck if the `payer` becomes an address that reverts on `feeToken()` transfers. This satisfies "permanent freezing of funds" / "a route unable to deliver messages."

### Likelihood Explanation
Likelihood is Medium: it requires (1) an app or dispatcher to set an attacker-influenced `payer` (fully possible since `dispatch()` is permissionless and `post.payer` is not validated against `msg.sender`), and (2) the configured `feeToken()` to be one that can be made to revert transfers to a chosen address (ERC777-style hook token, or an ERC20 with blacklist/pause capability such as USDC — both realistic given `feeToken()` is a governance-configurable ERC20). No privileged role is required to trigger the block; only a single permissionless `dispatch()` call with a crafted `payer`.

### Recommendation
Adopt a pull-payment pattern for all fee/relayer-reward payouts in `EvmHost`:
- For POST/GET timeout refunds, credit `meta.sender`'s balance in an internal accounting map (e.g., `_claimableFees[token][account] += amount`) instead of calling `safeTransfer` inline, and let the finalize/timeout logic (deletion of `_requestCommitments`, app callback) succeed unconditionally.
- Provide a separate `claimFees(address token)` function that lets the account withdraw its accrued balance, wrapping the transfer so a revert there cannot undo the timeout/finalize state transition.
- Apply the same pattern to the relayer reward in `dispatchIncoming(GetResponse)`.

### Proof of Concept
1. Attacker deploys `MaliciousPayer`, a contract with no fallback/receive logic or one that reverts unconditionally, or arranges for its address to be blacklisted on the configured `feeToken()` (e.g., USDC).
2. Attacker (or any unprivileged app) calls `EvmHost.dispatch(DispatchPost({..., payer: address(MaliciousPayer), fee: X, ...}))`, escrowing `X` fee tokens and storing `FeeMetadata({sender: MaliciousPayer, fee: X})` per [6](#0-5) .
3. The request times out without being delivered.
4. A relayer submits `HandlerV2.handlePostRequestTimeouts`, which calls `host.dispatchTimeOut(PostRequestTimeout(...), meta, commitment)`.
5. `onPostRequestTimeout` succeeds on the destination app (releasing/refunding its escrowed assets in memory/storage within the same call), but the subsequent `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)` reverts because `MaliciousPayer` cannot receive the token.
6. The whole transaction reverts, rolling back the app's asset release along with the fee payment — this happens identically on every retry, permanently freezing the underlying request's timeout-triggered refund.

    function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                post.fee, path, address(this), block.timestamp
            );
        } else if (post.fee > 0) {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
        }

        // adjust the timeout
        uint64 timeoutTimestamp = post.timeout == 0 ? 0 : uint64(block.timestamp) + uint64(post.timeout);
        PostRequest memory request = PostRequest({
            source: host(),
            dest: post.dest,
            nonce: uint64(_nextNonce()),
            from: abi.encodePacked(_msgSender()),
            to: post.to,
            timeoutTimestamp: timeoutTimestamp,
            body: post.body
        });

        // make the commitment
        commitment = request.hash();
        _requestCommitments[commitment] = FeeMetadata({sender: post.payer, fee: post.fee});
