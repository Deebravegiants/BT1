### Title
Session ID Derived from Unsigned, Attacker-Guessable Cookie Bytes Enables Cross-Tenant Session Hijacking - (File: lib/shopify_api/utils/session_utils.rb)

### Summary
`ShopifyAPI::Utils::SessionUtils.current_session_id` — the library's documented mechanism for host applications to determine which stored `Session` (and therefore which merchant's access token) to load for an incoming request — accepts the raw, unsigned `shopify_app_session` cookie value as the authoritative session id with no cryptographic verification, while the parallel JWT-based path is fully HMAC-verified.

### Finding Description
For the non-embedded (and cookie-fallback embedded) flow, `SessionUtils.current_session_id` calls `cookie_session_id`, which simply reads the cookie and returns it verbatim as the session id: [1](#0-0) 

```ruby
def cookie_session_id(cookies)
  cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]
end
```

Contrast this with the JWT branch of the same method, `session_id_from_shopify_id_token`, which requires `Auth::JwtPayload.new(id_token)` to succeed — i.e., the token must carry a valid HMAC-SHA256 signature computed with `Context.api_secret_key`: [2](#0-1) [3](#0-2) 

No such signature check exists for the cookie path. The identity binding that should hold is:

`session id used to key session storage` == `session id that was actually derived from an HMAC-verified OAuth exchange for that shop`

The cookie path breaks this: the bytes accepted are whatever the browser sends, unauthenticated, and the format of the legitimate value is fully predictable/deterministic — `session.id` is built as `"#{shop}_#{associated_user.id}"` for online sessions or `"offline_#{shop}"` for offline sessions: [4](#0-3) 

and this exact string is what gets written into the `SessionCookie` value after OAuth completes: [5](#0-4) 

`SessionCookie` itself is a plain struct with no signature/MAC field — only `name`, `value`, `expires`: [6](#0-5) 

Because the cookie value is (a) deterministic/enumerable (`{shop}.myshopify.com_{user_id}` or `offline_{shop}.myshopify.com`) and (b) carries no integrity check binding it to a genuine, HMAC-verified `validate_auth_callback` completion for that shop, any party who can place this cookie name/value on a victim's request to the app (e.g. cookie fixation via a shared parent domain, response header injection, or any app surface that reflects/sets cookies without care) causes `SessionUtils.current_session_id` — and consequently the host application's session storage lookup, which this method exists to drive — to resolve to an arbitrary victim shop's session id. The host app then loads that shop's stored `Session`, including its access token, for the attacker's request. This is a direct violation of the equality "the identity used to fetch a tenant's credentials must equal the identity that was cryptographically authenticated," mirroring the analog bug class where an internal state changes/derives from data that was never revalidated against the original cryptographic check.

### Impact Explanation
If successful, an attacker's request resolves to another merchant's `Session`, i.e., cross-tenant access to that merchant's access token via the host app's session storage — Critical impact per the given rubric (cross-tenant access / theft of a merchant access token).

### Likelihood Explanation
Exploitability depends on the attacker's ability to set/override the specific cookie name (`shopify_app_session`) on a victim's browser for the app's origin (cookie fixation, subdomain cookie scoping issues, or any endpoint on the app that lets an attacker set cookies). Given the value's format is fully documented and deterministic (`{shop}_{user_id}` / `offline_{shop}`), no secret knowledge is needed to construct a target victim's session id once the shop domain is known (shop domains are public). The library provides zero integrity protection on this value, unlike its own JWT path, making this a structural weakness rather than a theoretical one.

### Recommendation
Do not use the raw, attacker-suppliable cookie value as a trusted session identifier. Either:
- Sign/MAC the `SessionCookie` value (e.g., HMAC it with `api_secret_key`, mirroring `Utils::HmacValidator`) and verify that MAC in `cookie_session_id` before trusting it, or
- Store only an opaque, cryptographically random session identifier (not a predictable `{shop}_{user}` string) as the cookie value, decoupling the externally-visible cookie bytes from the internal shop/session mapping, or
- Require the JWT-based (`session_id_from_shopify_id_token`) path exclusively for embedded apps and clearly document that non-embedded/cookie-based session ids must be independently authenticated (e.g., re-verified against stored, server-side session state, not derived solely from client-supplied bytes).

### Proof of Concept
1. Attacker learns the target's shop domain, e.g. `victim-shop.myshopify.com` (public information).
2. Attacker computes the expected offline session id per the library's own deterministic scheme: `offline_victim-shop.myshopify.com` (see `offline_session_id` in `lib/shopify_api/utils/session_utils.rb:63-66`).
3. Attacker sets this exact value as the `shopify_app_session` cookie on a request to the target app (via cookie fixation/injection vector on the app's origin).
4. The app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `"offline_victim-shop.myshopify.com"` from `cookie_session_id` with no verification whatsoever.
5. The host application looks up and loads the `Session` (and access token) for `victim-shop.myshopify.com` from its session storage using this attacker-supplied id, granting the attacker's request access to the victim merchant's credentials.
