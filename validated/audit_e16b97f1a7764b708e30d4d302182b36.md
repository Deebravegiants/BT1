### Title
Unchecked-length copy of attacker-controlled BEEFY vote signature causes a panic/DoS in consensus proof conversion - ([File: evm/rust/src/conversions.rs])

### Summary
`evm/rust/src/conversions.rs` converts a decoded `Vote.signature` (a Solidity `bytes` field — Solidity has no fixed byte type larger than `bytes32`, so `signature` must be dynamic-length) into a fixed 65-byte array with `copy_from_slice` without first checking the length matches 65 bytes. [1](#0-0) 

### Finding Description
`From<Vote> for SignatureWithAuthorityIndex` does:
```
let sig_bytes = value.signature.to_vec();
let mut signature: TSignature = [0u8; 65];
signature.copy_from_slice(&sig_bytes);
``` [2](#0-1) 

`Rust`'s `copy_from_slice` requires the source and destination slices to have identical lengths, or it panics. Because `Vote.signature` is ABI-decoded from attacker-controlled BEEFY/relayer proof bytes (`RelayChainProof` → `MmrProof` → `signed_commitment.votes` conversion chain) and is a dynamic `bytes` field with no on-chain length assertion prior to this conversion, a relayer can submit a consensus proof whose `Vote.signature` is any length other than 65 (0, 64, 66, etc.). This is the same root-cause class as CVE-2016-3633: a fixed-size buffer is populated from an external, length-unchecked source buffer with an unvalidated assumption about its size, leading to an out-of-bounds/invalid memory operation (here, a Rust panic/abort rather than a silent OOB read, since Rust performs a runtime bounds/length check and aborts instead of reading past the buffer — but the reachable path and root cause, "copy without validating source length," are identical).

The unsafe conversion sits directly in the BEEFY consensus-proof decoding pipeline: `RelayChainProof.signedCommitment.votes` → `Vote` → `SignatureWithAuthorityIndex`, feeding `BvpSignedCommitment` used by the consensus verification path. [3](#0-2) 

### Impact Explanation
Any unprivileged party able to submit or relay a BEEFY consensus proof (or trigger this SP1/native conversion code that runs over an untrusted proof, e.g. within a zkVM guest program or off-chain prover invoked as part of consensus verification) can craft a `Vote.signature` of a length other than 65 to abort the process handling the proof. This can be used to reliably crash/deny the BEEFY consensus verification/proving path, preventing consensus state updates (and therefore state-commitment/message delivery) from being produced — matching the "route unable to deliver messages" impact category.

### Likelihood Explanation
Likelihood is high for any code path that exercises this `From<Vote>` conversion on attacker-supplied proof bytes without a prior length check: constructing a malformed `Vote.signature` is trivial (any length ≠ 65 bytes), and the conversion is unconditionally invoked while parsing every vote in a submitted `signedCommitment`.

### Recommendation
Validate `sig_bytes.len() == 65` before calling `copy_from_slice`, returning a decode error (propagated up through `TryFrom`/`Result`) instead of panicking, consistent with the length-checked decoding pattern already used elsewhere in the codebase (e.g. `ByteVector<N>::decode`, `bsc` extra-data length checks, `EthereumTrie` node-codec bounds checks). [4](#0-3) 

### Proof of Concept
1. Construct a `Vote` with `signature` set to a `bytes` value of length 0 (or any length ≠ 65) and a valid `authorityIndex`.
2. Include this `Vote` in `SignedCommitment.votes` inside a `RelayChainProof`/`BeefyConsensusProof` submitted through the normal consensus-proof relaying flow.
3. When the proof is converted via `From<Vote> for SignatureWithAuthorityIndex` (`evm/rust/src/conversions.rs:356-366`), `signature.copy_from_slice(&sig_bytes)` panics because `sig_bytes.len() != 65`, aborting the process performing the conversion (e.g., the SP1 guest/prover or native verifier binary) before any signature or consensus validity check occurs.
