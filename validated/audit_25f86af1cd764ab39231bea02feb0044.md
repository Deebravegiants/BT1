### Title
Withdrawal status misreported when a NEAR transaction contains multiple withdrawals of the same asset - (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
### Finding Description
`PoaBridge.describeWithdrawal` resolves the on-chain outcome of a withdrawal by calling `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which matches purely by `assetId` (i.e., `near_token_id`), ignoring `index`, `destinationAddress`, and `amount`: [1](#0-0) 

The POA Bridge API's `withdrawals` list is explicitly documented as unsorted, and the code comment even states the match is "by assetId, not by index." When a single NEAR transaction batches multiple withdrawals of the *same* token (e.g., two `ft_withdraw`/POA withdraw intents for the same `assetId` but different `destinationAddress`/`amount` in one tx), calling `describeWithdrawal` for each `WithdrawalIdentifier` (each with a distinct `index`) will invoke `findMatchingWithdrawal` with the same `assetId` and can return the *same* array element (the first one matching that asset) for every call, regardless of which `index` was requested.

This breaks the equality the caller relies on: "the status/tx hash reported for withdrawal N corresponds to the on-chain settlement of withdrawal N." Instead, the SDK can report withdrawal index 1's completion using the tx hash/amount that actually belongs to withdrawal index 0's row (or vice versa), because nothing in `findMatchingWithdrawal` disambiguates rows with an identical `near_token_id`.

### Impact Explanation
Callers of `sdk.waitForWithdrawalCompletion` (and the underlying `describeWithdrawal`) use the returned `{status, txHash}` to determine when a withdrawal is settled and to which destination transaction it corresponds. If two withdrawals of the same asset are batched, an integrator could:
- Mark the wrong withdrawal as "completed" (double credit: two withdrawal records get resolved by matching to only one real on-chain withdrawal record), or
- Associate the wrong `transfer_tx_hash` with a withdrawal, misreporting which destination transaction fulfilled which user's withdrawal request.

This falls under "a status or hash misreport making an integrator credit or refund twice" (High impact per the provided severity rubric).

### Likelihood Explanation
This requires the caller to batch multiple withdrawals of the *same* `assetId` in one NEAR transaction (a supported, unprivileged usage pattern — no admin/relayer/bridge-operator collusion needed) and then track completion per-withdrawal via `describeWithdrawal`/`waitForWithdrawalCompletion`. Any user/integrator constructing a multi-withdrawal intent batch that includes duplicate assets can trigger this; it does not require any malicious third party, only that batch composition exists, which the SDK explicitly supports (`WithdrawalIdentifier.index`).

### Recommendation
Match POA bridge withdrawal status rows using additional discriminating fields beyond `assetId`/`near_token_id` — at minimum also compare `amount` and `address` (destination) from `withdrawal.data`, and prefer positional correlation when the API guarantees order for same-asset entries. Track already-consumed rows across multiple `describeWithdrawal` calls for the same `tx.hash` so that duplicate-asset withdrawals are not both matched to the same underlying entry.

### Proof of Concept
The existing test `matches withdrawal by assetId, not by index` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.test.ts` (lines 1054-1111) demonstrates that `describeWithdrawal` intentionally ignores `index` and matches purely by asset. Extending this scenario to two withdrawal rows sharing the *same* `near_token_id` but different `amount`/`address` shows `findMatchingWithdrawal` (in `poa-bridge.ts`) returns the first array match for both `index: 0` and `index: 1` calls, causing the SDK to report identical `{status, txHash}` for two distinct withdrawals of the same asset — i.e., resolving one withdrawal's completion for what is actually a different withdrawal's on-chain settlement.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
