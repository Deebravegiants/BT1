Audit Report

## Title
Path Traversal in Workflow Artifact HTTP Fetcher Escapes Configured Base Path - ([File: core/services/workflows/syncer/v2/fetcher.go])

## Summary
`newHTTPFetcher`, which implements the HTTP branch of `types.FetcherFunc` returned by `NewFetcherFunc`, joins a caller-supplied request path onto an operator-configured `baseURL` using `filepath.Join` without validating that the resulting path remains under the configured base path. This is unlike its sibling `newFileFetcher`, which explicitly checks the joined path against `basePath` before use. The gap allows a `req.URL` containing `../` segments to move the outbound request outside the intended sub-path on the same configured host.

## Finding Description
`NewFetcherFunc` dispatches to `newFileFetcher` or `newHTTPFetcher` based on scheme [1](#0-0) . The file variant validates containment after joining paths: [2](#0-1) . The HTTP variant only cleans the incoming path and joins it to the base URL's path with `filepath.Join`, with no equivalent prefix check against the original base path: [3](#0-2) . Because `filepath.Join` collapses `..` segments together with the joined-in base segments, a value like `req.URL = "../admin/secret"` combined with `baseURL = "http://host/api/workflows"` resolves to `http://host/api/admin/secret` — outside the `/api/workflows` sub-path the operator intended to restrict fetches to.

This function is genuinely wired into the production node, not just test code: `ChainlinkAppFactory.NewApplication` in `core/cmd/shell.go` calls `syncerv2.NewFetcherFunc(cfg.CRE().WorkflowFetcher().URL(), appLggr)` whenever `cfg.CRE().WorkflowFetcher().URL()` is configured [4](#0-3) . The `req.URL` value passed into the fetcher originates from `binaryURL`/`configURL` fields recorded when a workflow is registered on the on-chain `WorkflowRegistry`, and is passed through unvalidated by `artifacts.Store.FetchWorkflowArtifacts` as `ghcapabilities.Request.URL` [5](#0-4) [6](#0-5) .

Workflow registration itself goes through `UpsertWorkflow` on the `WorkflowRegistry` contract. Registering/updating a workflow (and thus supplying `binaryURL`/`configURL`) requires the calling address to first be added to the contract's allowed-signers list and to link its owner identity via a signed ownership proof [7](#0-6) , i.e., workflow registration is gated by an allowlist/link step rather than being fully open to any address, but this gate is a workflow-owner/tenant-level permission, not a node-operator or admin-of-the-fetcher privilege — the party supplying the malicious URL is still distinct from, and untrusted relative to, the node operator who configures and trusts the base URL's host boundary.

## Impact Explanation
If a node operator enables `CRE.WorkflowFetcher.URL` pointing at an `http(s)://` endpoint scoped to a specific sub-path of an internal service (the intended, documented use of this "bypass the gateway" feature), a workflow owner allowed to register/update workflows can supply a `binaryURL`/`configURL` containing `../` segments to cause the node to issue GET requests to sibling or parent paths on that same host, outside the sub-path boundary the operator relied on. This is a request-path confusion / limited SSRF-adjacent issue reachable from a workflow-owner action, matching the reported CVE-2023-5123-style bug class of joining unvalidated caller input onto an operator base path.

## Likelihood Explanation
Exploitability is gated on the operator actually enabling the HTTP variant of `NewFetcherFunc` (via `CRE.WorkflowFetcher.URL` set to `http`/`https`) and configuring a base URL whose sub-path carries security meaning; the code comment marks this path as bypassing the gateway, suggesting it is intended primarily for local/dev/non-default deployments rather than the default gateway-mediated `FetcherService.Fetch` flow. Where enabled, any account permitted to register a workflow (an allowlisted/linked workflow owner, not a node admin) can trivially trigger the traversal on every artifact fetch.

## Recommendation
In `newHTTPFetcher`, after computing `u.Path = filepath.Join(u.Path, cleanPath)`, verify the resulting path is still prefixed by the original base path (mirroring the check in `newFileFetcher`) and reject the request otherwise. Also consider rejecting any `req.URL` containing `..` segments outright before joining.

## Proof of Concept
1. Start a test HTTP server and configure `fetcher, _ := NewFetcherFunc(server.URL+"/workflows", lggr)`, mirroring the existing test setup in `fetcher_test.go`'s `"http fetcher"` subtest.
2. Call `fetcher(ctx, "msg", ghcapabilities.Request{URL: "../admin/secret"})`.
3. Observe that the resulting outbound request path (loggable via `lggr.Debugw("Fetching HTTP resource", "url", fetchURL, ...)`) resolves outside `/workflows`, e.g. `/admin/secret`, rather than being rejected as `newFileFetcher` would reject an analogous `../../../etc/passwd` traversal attempt (see the existing `"Test path traversal attempt"` case in `fetcher_test.go` for the file-fetcher equivalent that currently has no HTTP-fetcher counterpart).
