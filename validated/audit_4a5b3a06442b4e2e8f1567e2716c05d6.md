### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` validates the webhook payload's HMAC over the raw body only, but the `shop` value used downstream by handlers is read directly from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header. The HMAC therefore proves nothing about which shop the payload belongs to, breaking the intended binding of `hmac_signed_body == body_for_shop_X`.

### Finding Description
`Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, secret, verifiable_query.to_signable_string)` and compares it against the `hmac` field [1](#0-0) . For webhooks, `Request#to_signable_string` returns only `@raw_body` [2](#0-1) , while `Request#shop` is pulled straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the signed body [3](#0-2) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` and then forwards `request.shop` unchecked into the handler's `WebhookMetadata` [4](#0-3) . Because the HMAC only authenticates the body bytes and the app's possession of the secret, not the header identifying the tenant, the equality the library implicitly assumes — "the shop whose data was HMAC-signed" == "the shop passed to the handler" — does not hold. Any request with a raw body/HMAC pair the attacker legitimately obtained (e.g., from a genuine webhook delivered to their own shop after installing the app) can be replayed with the `shop-domain` header swapped to a victim shop's domain, and it will still pass `HmacValidator.validate` because that check never inspects the header at all.

This mirrors the report's bug class: a field that is acted upon (`shop`, used to attribute/route webhook data) is not covered by the authenticity check (the HMAC), so the two "views" of identity — the body's cryptographic origin and the header-derived shop — can diverge.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` (as delivered by this gem) to select which merchant's session/data record to update — which is the documented purpose of the `shop` field — an attacker who installs the target app on their own shop can capture a validly-HMAC'd webhook body and shop-domain-swap it to impersonate another merchant. This is a cross-tenant data-integrity/access issue: the handler acts on attacker-supplied "which shop" information while believing it is protected by HMAC. Per the rules, cross-tenant access is a Critical-impact category.

### Likelihood Explanation
Exploitation requires only: (1) installing the target Shopify app on an attacker-controlled shop to receive one legitimately signed webhook (a normal, low-privilege action any developer/merchant can take), and (2) sending an HTTP POST to the app's exposed webhook endpoint with the captured `raw_body`/`hmac` pair but an attacker-chosen `shopify-shop-domain` header. No knowledge of `client_secret` or access tokens is required, and the vulnerable check (`HmacValidator.validate` + `Registry.process`) is exactly the code path every integrating app relies on for webhook trust.

### Recommendation
Bind the `shop` (and ideally `topic`, `api-version`) values into the signed material, or otherwise cryptographically tie the header-derived shop to the payload before trusting it. If Shopify's webhook HMAC scheme itself only signs the body (which is the real-world behavior), then `Registry.process`/`Request` should not present `shop` as a trusted/verified value to handlers without documenting that it is unauthenticated header input, and should encourage/require handlers to cross-check `request.shop` against the shop actually recorded for the referenced session or resource before mutating tenant-specific state.

### Proof of Concept
1. Install the target app on `attacker.myshopify.com`; capture a genuine webhook POST, noting `raw_body` and the `shopify-hmac-sha256` header value.
2. Build a new HTTP POST to the app's webhook endpoint with the identical `raw_body` and `shopify-hmac-sha256`, but set `shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `raw_body` [2](#0-1) .
4. The handler receives `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: ..., ...)` [5](#0-4) , causing the app to attribute attacker-controlled webhook data to the victim shop.
