### Title
Signup marked "Successful" for User-Centric Signups Without Verifying Personal Custody Package (PCP) Was Actually Built and Uploaded - (File: `src/plans/mod.rs`)

### Summary
In `do_signup` (`src/plans/mod.rs`), when `user_centric_signup` is true, the final enrollment `success` status is derived purely from the local `signup_reason` value, without any dependency on whether the personal custody package (PCP) — which contains the encrypted iris/face biometric data — was ever actually built or uploaded to the backend. If `TryInto<personal_custody_package::Credentials>` fails (e.g., missing backend keys in `UserData`), the entire PCP-build/upload block is silently skipped, yet the signup can still be reported and recorded as successful.

### Finding Description
`ResolvedQrCodes -> Credentials` conversion is fallible and silently discards the error: [1](#0-0) . The conversion (`TryInto<personal_custody_package::Credentials>`) returns `Err(())` whenever any of `backend_iris_public_key`, `backend_iris_encrypted_private_key`, `backend_normalized_iris_public_key`, `backend_normalized_iris_encrypted_private_key`, `backend_face_public_key`, `backend_face_encrypted_private_key`, or `self_custody_user_public_key` is `None` in `UserData` [2](#0-1) . When that happens, `if let Ok(mut credentials) = qr_codes.try_into() { ... }` simply falls through with no error handling and no `debug_report`/enrollment status update [3](#0-2) .

Execution then proceeds directly to the final enrollment-status computation:
```
let success = if user_centric_signup && !orb.config.lock().await.ignore_user_centric_signups {
    debug_report.enrollment_status(match signup_reason {
        SignupReason::Normal => enroll_user::Status::Success,
        _ => enroll_user::Status::Error,
    });
    signup_reason == SignupReason::Normal
} else {
    Box::pin(self.enroll_user(...)).await.is_success()
};
``` [4](#0-3) 

For a `user_centric_signup`, this branch does not call `enroll_user` (which performs the network-verified backend enrollment handshake in `src/plans/enroll_user.rs`) — it only checks the local `signup_reason` variable, which is set earlier purely from `pipeline`/`fraud_detected` (biometric pipeline outcome), independent of whether the PCP (containing the actual iris/face biometric package the backend needs to complete/verify the signup) was ever produced or transmitted [5](#0-4) . Consequently, the state transition "enrollment success" is recorded — mirroring the reported bug class where a state transition (`Active -> Funded`) happens without performing the associated required bookkeeping (`fees[raise.currency] += raise.fees`) — while the analogous required side effect here (building/uploading the biometric PCP so the backend can register the signup) can be skipped entirely.

### Impact Explanation
If credentials conversion fails (any missing backend key in `UserData`) for a user-centric signup, the Orb will report `debug_report.enrollment_status = Success` and set `SignupResult.success = true`, and downstream code (`after_signup`) forwards `success: true` to the relay app via `SignupEnded` [6](#0-5)  — even though no biometric package was ever uploaded to the backend. This is a misattributed/false-positive signup completion: the app/backend is told the signup succeeded while the actual biometric enrollment data never reached the backend, creating a state where the user believes they are verified/enrolled but no verifiable biometric record backs that claim.

### Likelihood Explanation
The trigger condition (missing backend-provided keys in `UserData`) is backend-controlled data returned as part of the user QR-code validation flow and is not something a non-privileged local attacker on the orb can directly force under normal circumstances; reaching this path in practice depends on backend response completeness for `user_centric_signup` flows. I could not fully verify from the indexed code how reliably the backend guarantees these fields are populated for `user_centric_signup=true`, so likelihood is not conclusively assessed as attacker-reachable without further confirmation of the backend contract.

### Recommendation
In the `user_centric_signup` success-determination branch, do not report/record success unless credential conversion and the PCP build/upload path actually completed successfully; propagate the `try_into()`/`build_pcp` failure into the success/enrollment-status computation (e.g., only allow `success = true` when both `signup_reason == SignupReason::Normal` AND the PCP was confirmed built and uploaded), and log an explicit error instead of silently discarding the `TryInto` failure.

### Proof of Concept
1. Complete a signup flow where `user_data.user_centric_signup == true` and `ignore_user_centric_signups == false`.
2. Have the backend-provided `UserData` omit one of the required key fields (e.g., `backend_face_encrypted_private_key: None`), causing `TryInto<Credentials>` at `src/plans/mod.rs:574` to return `Err(())`.
3. Because the `if let Ok(...)` fails, the entire PCP-build/upload block (`src/plans/mod.rs:574-637`) is skipped without recording any failure in `debug_report`.
4. `signup_reason` was set to `SignupReason::Normal` earlier (biometric pipeline succeeded, no fraud detected) at `src/plans/mod.rs:565-571`.
5. The `success` computation at `src/plans/mod.rs:639-645` evaluates `signup_reason == SignupReason::Normal` → `true`, and `debug_report.enrollment_status` is set to `Success`, despite no PCP ever having been uploaded to the backend.

    type Error = ();

        let ResolvedQrCodes { operator_data, user_data, user_qr_code, user_qr_code_string } = self;
        if let (
            Some(backend_iris_public_key),
            Some(backend_iris_encrypted_private_key),
            Some(backend_normalized_iris_public_key),
            Some(backend_normalized_iris_encrypted_private_key),
            Some(backend_face_public_key),
            Some(backend_face_encrypted_private_key),
            Some(self_custody_user_public_key),
        ) = (
            user_data.backend_iris_public_key,
            user_data.backend_iris_encrypted_private_key,
            user_data.backend_normalized_iris_public_key,
            user_data.backend_normalized_iris_encrypted_private_key,
            user_data.backend_face_public_key,
            user_data.backend_face_encrypted_private_key,
            user_data.self_custody_user_public_key,
        ) {
            Ok(personal_custody_package::Credentials {
                operator_qr_code: operator_data.qr_code,
                user_qr_code,
                user_qr_code_string,
                backend_iris_public_key,
                backend_iris_encrypted_private_key,
                backend_normalized_iris_public_key,
                backend_normalized_iris_encrypted_private_key,
                backend_face_public_key,

                self_custody_user_public_key,
                pcp_version: user_data.pcp_version,
