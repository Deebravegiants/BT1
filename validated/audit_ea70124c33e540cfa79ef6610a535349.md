### Title
`IntentGatewayV2.placeOrder` on the Tron deployment never refunds unspent native token overpayment, permanently trapping user ETH/TRX in the contract - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` accepts native token payment (`payable`) for order inputs and fees but, unlike the canonical EVM implementation in `evm/src/apps/IntentGatewayV2.sol`, contains no logic to return any unspent `msg.value` to the caller at the end of execution.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `placeOrder` (lines 338-506) tracks a local `msgValue` variable that is decremented as native-token inputs are escrowed [1](#0-0) . When `order.fees > 0` and `msgValue > 0`, the contract swaps the *entire remaining* `msgValue` for the fee token via `swapETHForExactTokens{value: msgValue}(order.fees, ...)`, but it never captures the `amounts[0]` actually spent nor subtracts it from `msgValue`, and the function ends immediately after storing `_orders[commitment][TRANSACTION_FEES]` and emitting `OrderPlaced` — there is no refund step [2](#0-1) .

This differs from the mainline `IntentGatewayV2.sol`, which explicitly tracks the swap output (`msgValue -= amounts[0]`) and unconditionally refunds any leftover `msgValue` to `msg.sender` via `_sendValue` before emitting the event [3](#0-2) . The corresponding Foundry test suite for the mainline contract explicitly validates this refund behavior (`testPlaceOrder_RefundsExcessNativeToken`, `testPlaceOrder_FeeSwap_RefundsExcessNativeToken`) [4](#0-3) [5](#0-4) , but the Tron variant has no equivalent protection.

Practically, any user who:
1. Sends `msg.value` greater than the sum of native-token order inputs (e.g., pads for gas price uncertainty or miscalculates the exact `order.fees` swap cost), or
2. Pays `order.fees` in native token where the Uniswap swap consumes less than the full amount sent (very likely, since `amountInMaximum` semantics mean the swap only spends what's needed to get `order.fees` exact fee tokens out),

will have the excess native token balance permanently stranded in the `IntentGatewayV2` contract on the Tron deployment, with no `_sendValue`, `sweep`, or withdrawal path exposed to ordinary users for this stuck native balance.

### Impact Explanation
This is a direct, unrecoverable loss of user funds analogous to the referenced `TrancheRouter.issue` bug class: any leftover native token sent by an unprivileged user calling `placeOrder` is trapped in the contract rather than returned. Because Uniswap's `swapETHForExactTokens` only ever consumes up to `order.fees` worth of ETH and refunds nothing back into `msgValue` accounting here, essentially every native-token fee payment through this Tron path leaves a permanent residue, and any input overpayment does too. Funds become effectively frozen/stolen by whoever can eventually claim them (there's no user-facing sweep of accrued native balance in this file), satisfying the "permanent freezing of funds" / "concrete theft" bar.

### Likelihood Explanation
High likelihood: this triggers on the single most common user action in the Intent Gateway — placing an order — any time a user pays `order.fees` in native token (the swap virtually never consumes exactly `msg.value`) or slightly overestimates the native input amount. No special conditions, admin cooperation, or malicious actors are needed; it happens under normal usage.

### Recommendation
Mirror the mainline `IntentGatewayV2.sol` behavior: capture the actual amount spent from `swapETHForExactTokens` (`amounts[0]`), deduct it from the local `msgValue`, and unconditionally refund any remaining `msgValue` to `msg.sender` at the end of `placeOrder` (and audit `fillOrder`/other payable entry points in this Tron contract file for the same pattern).

### Proof of Concept
1. User calls `placeOrder{value: X}(order, graffiti)` on the Tron `IntentGatewayV2` where `order.inputs` contains no native-token entries (all ERC-20) and `order.fees > 0`.
2. `msgValue = X` remains unchanged through the ERC-20 input escrow loop [6](#0-5) .
3. Since `msgValue > 0`, the contract calls `swapETHForExactTokens{value: msgValue}(order.fees, path, address(this), block.timestamp)` — Uniswap only pulls the exact ETH needed to produce `order.fees` fee tokens (bounded by `msgValue` as `amountInMaximum`), refunding the rest of the `msg.value` sent with the call back to the router's *caller*, which is this contract, not the router itself refunding to `msg.sender` [7](#0-6) .
4. The unspent ETH now sits in the `IntentGatewayV2` contract's balance; `msgValue` is never decremented and no refund is issued to `msg.sender`.
5. Function returns after emitting `OrderPlaced` [8](#0-7) , leaving the user's excess native token trapped.
