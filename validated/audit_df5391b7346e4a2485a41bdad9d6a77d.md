### Title
Orb-relay client replies to `RequestState` with the last sent message without verifying the sender's identity - ([File: orb-relay-client/src/client.rs])

### Summary
The reported ERC1155 issue is a case of a "transfer" protocol proceeding without verifying that the counterparty is the legitimate, authorized recipient. The `orb-relay-client` (used by orb-core to bind an Orb session to a specific self-serve App instance during signup, via `orb_relay_announce_orb_id`) contains an analogous authorization gap: the message-source identity check that is normally enforced for incoming payloads is bypassed for `RequestState` messages, causing the client to redisclose the last message (which can include `AnnounceOrbId` / `SignupEnded`, containing signup/session data) to a peer without validating that the peer is the expected destination.

### Finding Description
In `PollerAgent::main_loop`, incoming relay payloads are normally validated against the expected destination id before being handled: [1](#0-0) 

```
if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx.send(self.last_message.clone()).await...
} else if src.id != self.config.dst_id {
    tracing::error!("Skipping received message from unexpected source: ...");
} else {
    self.handle_message(...).await?;
}
```

The `src.id != self.config.dst_id` check — the equivalent of "does the recipient/sender match the expected counterparty" — is only applied in the `else` branch. When the incoming payload matches `self_serve::app::v1::RequestState`, the client immediately resends `self.last_message` (the last payload the orb sent, e.g., `AnnounceOrbId` or `SignupEnded`) to whoever sent the `RequestState`, with **no check that `src.id == self.config.dst_id`**. This mirrors the Hats/ERC1155 issue: an operation (here, releasing session state) proceeds without verifying the counterparty is the legitimate, expected party, because the "acceptance"/identity check that exists elsewhere in the protocol is skipped for this code path.

`orb_relay_announce_orb_id` (in `src/plans/mod.rs`) uses this same client to bind the orb's relay session to `orb_relay_app_id` taken from the scanned user QR code, and treats a successful blocking send/ack as authorization to proceed with the self-serve signup (biometric capture, `SignupEnded`, etc.): [2](#0-1) 

Because `RequestState` handling does not check `src.id`, any relay peer able to reach the same relay channel/session (not just the specific paired App) can obtain the orb's last relayed message (including the `AnnounceOrbId`/session binding payload or the `SignupEnded` result) without being the verified counterparty of that session.

### Impact Explanation
This breaks the intended identity binding between an Orb signup session and the specific App instance the user scanned. If an unauthorized party can trigger the `RequestState` reply path, it can obtain signup-session metadata (e.g., `AnnounceOrbId`, `SignupEnded` including `failure_feedback`) belonging to another session/user without being the authenticated destination, which is a form of cross-signup state disclosure. This is exactly the same class of flaw the ERC1155 report describes — an operation that should require verifying the actual, authorized receiver instead unconditionally trusts the operation and discloses/transfers state to whoever asks.

### Likelihood Explanation
Exploitability depends on: (1) whether the relay server's own authorization model would already prevent a non-paired peer from being routed messages tagged with another session/app id (this is server-side and outside orb-core, so it cannot be fully confirmed from this repo alone), and (2) whether `src.id` can differ from `dst_id` while still being delivered to this client at all. Given the code explicitly guards against `src.id != self.config.dst_id` in the general case, the omission of that same guard for `RequestState` strongly suggests the developers assumed such mismatched-source messages are possible and defended against them everywhere except this one path — making it a real, reachable gap rather than dead code.

### Recommendation
Apply the same `src.id == self.config.dst_id` validation to the `RequestState` branch before resending `self.last_message`, so that state is only replayed to the verified, expected counterparty of the session — analogous to requiring the ERC1155 receiver to explicitly accept the transfer before it is executed.

### Proof of Concept
Conceptual (not fully verifiable without the relay server's routing/auth code, which lives outside this repo):
1. Orb starts a self-serve signup and calls `orb_relay_announce_orb_id`, sending `AnnounceOrbId` (and later `SignupEnded`) over the relay channel keyed by `orb_relay_app_id`.
2. A peer connected to the same relay endpoint, with a `src.id` that does not match `self.config.dst_id`, sends a `self_serve::app::v1::RequestState` payload.
3. Per [3](#0-2) , the Orb client responds by resending `self.last_message` to the sender_tx regardless of `src.id`, disclosing the last signup-related payload without verifying the requester is the authorized App for that session.

async fn orb_relay_announce_orb_id(
    orb: &mut Orb,
    orb_relay_app_id: String,
    is_self_serve_enabled: bool,
    reties: u32,
    timeout: Duration,
    wait_for_pending_messages: Duration,
    wait_for_shutdown: Duration,
) -> Result<()> {
    let mut relay = Client::new_as_orb(
        RELAY_BACKEND_URL.to_string(),
        get_orb_token()?,
        ORB_ID.to_string(),
        orb_relay_app_id,
    );
    if let Err(e) = relay.connect().await {
        dd_incr!("main.count.orb_relay.failure.connect");
        return Err(eyre::eyre!("Relay: Failed to connect: {e}"));
    }
    for _ in 0..reties {
        let now = Instant::now();
        if let Ok(()) = relay
            .send_blocking(
                common::v1::AnnounceOrbId {
                    orb_id: ORB_ID.to_string(),
                    mode_type: if is_self_serve_enabled {
                        common::v1::announce_orb_id::ModeType::SelfServe.into()
                    } else {
                        common::v1::announce_orb_id::ModeType::Legacy.into()
                    },
                    hardware_type: if identification::HARDWARE_VERSION.contains("Diamond") {
                        common::v1::announce_orb_id::HardwareType::Diamond.into()
                    } else {
                        common::v1::announce_orb_id::HardwareType::Pearl.into()
                    },
                },
                timeout,
            )
            .await
        {
            // Happy path. We have successfully announced and acknowledged the OrbId.
            dd_timing!("main.time.orb_relay.announce_orb_id", now);
            orb.orb_relay = if is_self_serve_enabled {
                Some(relay)
            } else {
                relay.graceful_shutdown(wait_for_pending_messages, wait_for_shutdown).await;
                None
            };
            return Ok(());
        }
        dd_incr!("main.count.orb_relay.retry.send.announce_orb_id");
        tracing::error!("Relay: Failed to AnnounceOrbId. Retrying...");
        relay.reconnect().await?;
        if relay.has_pending_messages().await? > 0 {
            sleep(Duration::from_secs(1)).await;
        }
    }
    dd_incr!("main.count.orb_relay.failure.send.announce_orb_id");
    Err(eyre::eyre!("Relay: Failed to send AnnounceOrbId after a reconnect"))
}
