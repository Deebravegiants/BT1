### Title
Webhook `shop-domain` and `topic` headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then dispatches the handler using the `shop`, `topic`, and `webhook_id` values taken from unauthenticated HTTP headers. Because those identity-bearing headers are never included in the signed payload, any two headers/body combination that share a valid `(raw_body, hmac)` pair will be accepted regardless of which shop or topic the headers claim.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers, independent of the signature: [2](#0-1) 

`HmacValidator.validate` computes the HMAC over `to_signable_string` (the body only) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` treats a passing HMAC check as proof of authenticity for the *entire* request, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` that is handed to the app's handler: [4](#0-3) 

Identity-binding equality that is broken: `hmac_valid(raw_body) == true` is treated as equivalent to `hmac_valid(raw_body, shop, topic, webhook_id) == true`. Because `shop`/`topic`/`webhook_id` are not part of the signed bytes, the binding `signed_bytes == (body, shop, topic)` does not hold — only `signed_bytes == body` holds.

This is exactly the "bytes verified versus bytes parsed/acted on" pattern: the code verifies the signature over the body, but acts on header fields that were never part of what was verified.

### Impact Explanation
Because a single app-wide `client_secret` is used to sign all webhooks for all shops that installed the app (not a per-shop secret), any entity capable of obtaining one genuine `(raw_body, hmac)` pair for its own shop (e.g., an unprivileged merchant who installed the app and can observe/log its own inbound webhook traffic) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header (and/or `shopify-topic`, `shopify-webhook-id`) with a different value. `HmacValidator.validate` still returns `true` because it never inspects those headers, and `Registry.process` will invoke the handler believing the payload originated from the attacker-chosen shop/topic. This is a cross-tenant identity confusion: data believed to belong to shop B is actually attacker-controlled content from shop A's own webhook stream, processed under shop B's/another topic's identity by the host application's handler logic (e.g., order creation/fulfillment handlers keyed by `shop`).

### Likelihood Explanation
Moderate: it requires the attacker to be a real, installed merchant of the app (an "unprivileged" tenant relative to other tenants, no elevated credentials needed) and to have access to at least one legitimate webhook delivery for their own shop and topic, which is normal and expected for any installed merchant. No `client_secret`, access token, or TLS interception is required — only a body+hmac pair the attacker legitimately received for their own tenant.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signed material used for HMAC verification, or otherwise cryptographically bind them to the request (e.g., require the host application to independently confirm that `request.shop` corresponds to a shop with an active installation/session before trusting webhook content), rather than relying purely on a body-only HMAC to imply the authenticity of headers that were never part of the signature.

### Proof of Concept
1. App installs on `shop-a.myshopify.com`; the app receives genuine webhook `topic=orders/create`, with `raw_body=B` and header `shopify-hmac-sha256=H` where `H = HMAC(secret, B)` (per `HmacValidator.validate_signature`, [5](#0-4) ).
2. Merchant of `shop-a` (an unprivileged tenant of the app) captures this exact `(B, H)` pair.
3. Attacker sends a new HTTP request to the app's webhook endpoint with the same `raw_body=B` and `shopify-hmac-sha256=H`, but sets `shopify-shop-domain: shop-b.myshopify.com` and/or a different `shopify-topic`.
4. `ShopifyAPI::Webhooks::Request.new` parses `shop`/`topic` straight from the attacker-controlled headers ( [6](#0-5) ), and `Registry.process` validates `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H` ( [7](#0-6) ).
5. The handler for the (possibly forged) topic is invoked with `WebhookMetadata` claiming `shop: "shop-b.myshopify.com"`, even though the content actually originated from `shop-a`'s webhook stream.

          received_signature = verifiable_query.hmac
