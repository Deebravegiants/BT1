### Title
Unbounded RAY market-value accrual permanently freezes an oversized debt market - (common/src/rates/scaling.rs)

### Summary
Interest accrual converts scaled debt and supply balances back to RAY-denominated values with `scaled_to_original`, which performs a checked `Ray` multiplication and reverts on `i128` overflow. Because this calculation runs before every market mutation, an oversized market can reach a state where even repayment, withdrawal, liquidation, and explicit index updates all fail permanently.

### Finding Description
`Controller::update_indexes` is permissionless after ordinary caller authorization and delegates to the pool for each submitted `HubAssetKey` [1](#0-0) [2](#0-1) . The pool accrues every requested market through `interest::global_sync` [3](#0-2) , and the same synchronization is performed when loading any ordinary market-operation leg [4](#0-3) .

Each accrual step calls `scaled_to_original` on both `borrowed * borrow_index` and `supplied * supply_index` before calculating utilization and rates [5](#0-4) . `scaled_to_original` delegates to `Ray::mul` [6](#0-5) , which ultimately panics with `MathOverflow` if the resulting RAY value does not fit in `i128` [7](#0-6) .

The borrow index cap does not prevent this condition because the intermediate position value can exceed `i128::MAX` while the index itself remains below `MAX_BORROW_INDEX_RAY`; the cap is applied only after multiplying the old index by the interest factor [8](#0-7) . Once the stored scaled balance and index product crosses the representable-value boundary, `global_sync` always reaches the same overflowing calculation before any mutation can reduce the balance.

### Impact Explanation
This is a permanent freezing-of-funds condition for the affected market: borrowers cannot repay, suppliers cannot withdraw, liquidators cannot liquidate, and `update_indexes` cannot advance the market. The protocol can retain user collateral and supplier cash in the pool with no in-protocol path to reduce the oversized scaled balances because all relevant mutations synchronize the same market first. The integration test demonstrates that both `withdraw` and `repay` revert with `MATH_OVERFLOW` after the cliff is reached [9](#0-8) .

### Likelihood Explanation
Exploitation requires an exceptionally large market and sustained high utilization rather than a single transaction or privileged call. An unprivileged actor can create the required state by supplying the target asset, posting sufficient collateral, and borrowing most of the pool, but the market's configured caps must permit the position and enough ledger time must elapse for index growth to make `scaled * index` exceed `i128::MAX`. The reproduction uses a one-billion-token 18-decimal market at 98% utilization and shows the failure occurs before the borrow-index ceiling [10](#0-9) .

### Recommendation
Prevent scaled balances from reaching a value that can overflow during valuation, rather than relying only on token caps and index caps. At minimum:

- Bound admitted `supplied` and `borrowed` scaled RAY balances against a conservative maximum future index, or dynamically reject additional exposure when `scaled * index` approaches `i128::MAX`.
- Replace the accrual-time `scaled_to_original` calculation with a wider or saturating market-value representation where safe, so utilization and rate selection can continue when nominal market value exceeds `i128`.
- Add a pre-mutation solvency/recovery path that can reduce debt or supply without first requiring the overflowing market valuation.
- Add regression coverage asserting that `update_indexes`, `repay`, `withdraw`, and liquidation remain callable at the maximum permitted scaled balance after extreme index growth.

### Proof of Concept
The test setup creates an 18-decimal market, permits the required cap, supplies `1_000_000_000 * 10^18` base units, supplies separate collateral, and borrows 98% of the principal [11](#0-10) . It then advances time and repeatedly invokes the permissionless index update until the call returns `MATH_OVERFLOW` [12](#0-11) . At that point the borrow index is still below `MAX_BORROW_INDEX_RAY`, while both withdrawal and repayment fail with the same arithmetic error [13](#0-12) .

```rust
let principal = 1_000_000_000i128 * 10i128.pow(18);

controller.supply(supplier, 0, spoke_id, vec![(BIG18, principal)]);
controller.supply(borrower, 0, spoke_id, vec![(COLLATERAL, enough_collateral)]);
controller.borrow(borrower, borrower_id, vec![(BIG18, principal * 98 / 100)], None);

// After sufficient high-utilization accrual:
controller.update_indexes(keeper, vec![BIG18]);        // MathOverflow
controller.repay(anyone, borrower_id, vec![(BIG18, 1)]); // MathOverflow
controller.withdraw(supplier, supplier_id, vec![(BIG18, 1)], None); // MathOverflow
```

/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);

        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
