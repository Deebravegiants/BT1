Audit Report

## Title
Outbound HTTP response cache in the CRE Gateway omits `WorkflowID` from its cache key, breaking documented workflow isolation - (File: `core/services/gateway/handlers/capabilities/v2/response_cache.go`)

## Summary
The gateway's `responseCache` caches outbound HTTP action responses keyed only by `gateway.OutboundHTTPRequest.Hash()`, which the repository's own test suite proves does not incorporate `WorkflowID` or `CacheSettings`, despite the `v2/README.md` explicitly documenting "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage." As a result, two distinct workflows sharing the same `WorkflowOwner` and issuing an identical HTTP method/URL/headers/body will collide on the same cache entry and one workflow's cached response can be served to the other.

## Finding Description
`responseCache.Fetch`, `Set`, and `isExpiredOrNotCached` all key exclusively off `req.Hash()` [1](#0-0) [2](#0-1) [3](#0-2) . The struct's own comment describes the key as covering "method, URL, headers, body, workflowOwner" — `workflowID` is absent [4](#0-3) , contradicting the module's README claim that "Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" [5](#0-4) .

This is directly proven by the existing test suite in the same package: requests differing only in `WorkflowID` produce identical hashes, and requests differing only in `CacheSettings` also produce identical hashes, while requests differing in `WorkflowOwner` correctly produce different hashes [6](#0-5) .

The call path that reaches this cache originates from `gatewayHandler.makeOutgoingRequest`, which handles `OutboundHTTPRequest`s forwarded from workflow-executing nodes and calls `h.responseCache.Fetch`/`Set` keyed purely on the flawed hash [7](#0-6) . No other isolation mechanism (e.g., a per-workflow sub-map, or workflow ID appended to the cache key) exists in this code to compensate.

## Impact Explanation
This maps to the "cross-user response corruption" in-scope impact category: an HTTP action response cached for one workflow (which may contain sensitive/tenant-specific data returned by an external endpoint) can be silently served to a different workflow executing under the same owner address, purely because they share owner + method + URL + headers + body. It also means a request with `CacheSettings.Store=false` can still receive a cached value poisoned by another workflow's `Store=true` request, since `CacheSettings` is excluded from the hash as well.

## Likelihood Explanation
Triggering this requires no privilege beyond deploying/operating a workflow as a normal (non-admin) workflow owner — the collision occurs automatically whenever an owner runs two or more workflows that call a common HTTP endpoint (a realistic and common scenario, e.g., shared price/reference-data fetches), with no adversarial action needed to reach the cache confusion.

## Recommendation
Incorporate `WorkflowID` into the `OutboundHTTPRequest.Hash()` used as the cache key (and factor in cache-affecting `CacheSettings` fields) so the implementation matches the documented per-workflow isolation guarantee, or explicitly redocument and validate that owner-level (not workflow-level) response sharing is the intended, safe behavior.

## Proof of Concept
Run the existing test in this repo:
```
go test ./core/services/gateway/handlers/capabilities/v2/... -run TestRequestHash -v
```
The subtest "having different workflowID results in same Hash" demonstrates that two requests identical except for `WorkflowID` ("workflow-123" vs "workflow-456") hash to the same cache key [8](#0-7) , confirming that a response cached while serving one workflow will be transparently returned to a different workflow's subsequent matching request via `responseCache.Fetch` in `makeOutgoingRequest` [7](#0-6) .

func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}
