Confirmed: `WebhookMetadata.shop` is populated directly from `request.shop` (the `shop-domain` header) and passed to the host app's handler as the tenant identity, while the HMAC only covers the raw body.

### Title
Webhook shop-domain header is not covered by HMAC, allowing cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor sourced from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, and `ShopifyAPI::Webhooks::Registry.process` forwards this value unauthenticated as the tenant identity (`WebhookMetadata#shop`) to the host application's webhook handler, even though the HMAC signature only covers the raw request body.

### Finding Description
The HMAC check in `Registry.process` is `Utils::HmacValidator.validate(request)` [1](#0-0) , which internally calls `verifiable_query.to_signable_string` to compute the signature. For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [2](#0-1) . None of the other identity-bearing headers — `shop`, `topic`, `webhook_id`, `api_version` — are included in the signed material; they are read straight from attacker-controllable HTTP headers [3](#0-2) .

`Registry.process` then builds `WebhookMetadata` using `request.shop` as the trusted tenant identifier passed to the app's handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) . `WebhookMetadata#shop` is a plain `String` field consumed by host applications to key their per-shop logic (e.g., session/token lookup, tenant-scoped operations) [5](#0-4) .

This breaks the intended binding: `shop-header-used-for-signature == shop-header-trusted-for-tenant-routing`. In fact zero headers are bound to the signature at all, only the body bytes are. Because the app's webhook secret (`Context.api_secret_key`) is shared across every shop that installs the app [6](#0-5) , any entity that can obtain one genuine `(body, hmac)` pair for the app — for instance by installing the app on their own attacker-controlled shop and receiving a real webhook — can replay that exact body and HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop. The HMAC check still passes because it never inspected the header, and `Registry.process` will hand the host app a `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker who legitimately installs the app on their own shop (an unprivileged, self-service action) can cause the app to process webhook events attributed to any other shop of the attacker's choosing. Any host application that uses `WebhookMetadata#shop` to select which shop's session/access token to act on, or to write/trust data scoped to that shop, will act on behalf of, or write into, another merchant's tenant based on attacker-controlled input. This satisfies the Critical "cross-tenant access" bar because the tenant boundary (`shop`) is derived from unauthenticated header bytes rather than the HMAC-verified payload.

### Likelihood Explanation
The prerequisite is that the attacker can install the app on at least one shop they control (or otherwise obtain any valid webhook body+HMAC pair for the app) and can send arbitrary HTTP requests to the app's public webhook endpoint — both are standard, unprivileged capabilities for anyone who can install a public/embedded Shopify app. No access token, `client_secret`, or victim-side credential is required.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the HMAC-verified material, or otherwise cryptographically associate the delivered `shop-domain` header with the specific webhook subscription/secret for that shop, instead of trusting it as a bare unauthenticated header. At minimum, `Webhooks::Request#to_signable_string` should incorporate the shop domain so a replayed body cannot be revalidated under a different shop identity.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering a genuine webhook delivery with body `B` and header `x-shopify-hmac-sha256: H` computed over `B` using the app's shared `api_secret_key`.
2. Attacker replays a request to the app's webhook endpoint with the same body `B` and the same header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` recomputes the HMAC over `B` only [7](#0-6)  and it matches `H`, so `Registry.process` proceeds and invokes the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)` [4](#0-3) , even though the request was never sent by, or on behalf of, `victim-shop.myshopify.com`.
