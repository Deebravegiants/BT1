### Title
Registry-cache inconsistency: `consensusClient` swap via `updateHostParams` leaves stale `_consensusState` cache unvalidated - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.updateHostParamsInternal` allows governance (via `hostManager`, or `admin` on `TestnetHost`) to replace `_hostParams.consensusClient` with a new implementation address, but it never checks that the newly configured consensus client is compatible with the currently cached `_consensusState` bytes, nor does it clear/rebuild that cache. This mirrors the yToken registry-cache bug: a pointer to an external "source of truth" (registry / consensus client) is updated, but the derived cache (`_cachedVaults` / `_consensusState`) is left stale and is fed straight into computations that trust it implicitly.

### Finding Description
`updateHostParamsInternal` validates that the new `consensusClient` address has code and implements `IConsensusV2`, but performs no check relating it to the previously stored `_consensusState`: [1](#0-0) 

The stale `_consensusState` bytes are exactly what get passed, unmodified, into the new consensus client on the very next consensus update: [2](#0-1) 

`host.consensusState()` returns whatever was stored for the *old* consensus client's encoding format, and `IConsensusV2(host.consensusClient()).verify(previousState, proof)` decodes it as if it were the new client's trusted state. Since `previousState` is opaque `bytes` (ABI-encoded per implementation), there is no on-chain guarantee that the new client can meaningfully decode it: this can revert (silently blocking all future consensus updates once relayers start submitting proofs), or — more dangerously — decode into a structurally valid-but-semantically wrong "trusted state" (e.g., misaligned fields shifting byte offsets into plausible-looking values), which the new client would then treat as authoritative when verifying the next proof, producing an unsound state commitment.

`storeConsensusState` is only ever invoked by the trusted `handler` after `verify`, so there is no other path that resets or validates the cache on a `consensusClient` swap: [3](#0-2) 

### Impact Explanation
If governance rotates `consensusClient` to a different consensus-client implementation (a legitimate, non-malicious action — e.g. migrating from one light-client scheme to another, or fixing a bug in the verifier), the stale `_consensusState` is silently reused. Depending on the new client's decode behavior this either (a) permanently DoSes consensus updates for that host (freezing the bridge's ability to accept new state commitments, and by extension freezing all inbound messages/funds gated behind proof verification), or (b) produces a corrupted "verified" consensus state that the new client accepts as trusted context for future proof verification, undermining the soundness of all subsequent state-commitment verification (`storeStateMachineCommitment`) and hence message/proof delivery through `HandlerV2`.

### Likelihood Explanation
This requires a legitimate `updateHostParams` call changing `consensusClient` — a governance-only action reachable through the documented `SetHostParam` flow (`HostManager.onAccept` → `IHostManager.updateHostParams`), not an attacker-controlled path, and not requiring any malicious governance intent. Any planned migration to a new consensus client contract (which the codebase explicitly supports via the `consensusClient` field and `updateHostParams`) will hit this gap unless operators manually coordinate re-initialization out-of-band, which is undocumented in-code.

### Recommendation
When `consensusClient` changes in `updateHostParamsInternal`, either (1) require `_consensusState` to be re-initialized in the same governance action (e.g., accept a new bootstrapping consensus state alongside the new client address), or (2) clear `_consensusState`/`_consensusUpdateTimestamp` and require the `TestnetHost`-style re-init path (`_canReinitConsensus`) to be exercised on mainnet as well before any further consensus proofs are accepted, with an explicit `ConsensusClientRotated` guard state that blocks `handleConsensus` until re-initialized.

### Proof of Concept
1. Deploy `EvmHost` with `consensusClient = ClientA`, and let `_consensusState` accumulate a valid `ClientA`-encoded trusted state via normal `handleConsensus` calls.
2. Governance dispatches `updateHostParams` with `consensusClient = ClientB` (a different, otherwise-valid `IConsensusV2` implementation with a different state encoding), per [4](#0-3) .
3. A relayer calls `HandlerV2.handleConsensus(host, proof)`; internally `previousState = host.consensusState()` (still `ClientA`-encoded) is passed to `ClientB.verify(previousState, proof)`, per [5](#0-4) .
4. `ClientB` either reverts on decode (permanent DoS of consensus updates for this host) or misdecodes the bytes into a plausible-but-wrong trusted state, which is then stored via `storeConsensusState` and used to validate the *next* proof — an unsound state commitment enters the system.

    function handleConsensus(IHost host, bytes calldata proof) external notFrozen(host) {
        uint256 delay = block.timestamp - host.consensusUpdateTime();
        if (delay >= host.unStakingPeriod()) revert ConsensusClientExpired();

        bytes memory previousState = host.consensusState();
        (bytes memory verifiedState, IntermediateState[] memory intermediates, uint256 nextAuthoritySetId) =
            IConsensusV2(host.consensusClient()).verify(previousState, proof);

        if (keccak256(previousState) == keccak256(verifiedState)) return;
        host.storeConsensusState(verifiedState);
