### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing shop impersonation on replayed webhooks - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` value that is subsequently trusted and handed to the host application's handler is read from an HTTP header that is never included in the signed material.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` verifies this signable string via `Utils::HmacValidator.validate(request)` and, once it passes, immediately trusts `request.shop` (parsed straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header) to build the `WebhookMetadata` handed to the app's handler: [2](#0-1) 

`HmacValidator.validate` computes `HMAC-SHA256(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header value: [3](#0-2) 

Because `to_signable_string` is exactly `@raw_body`, the `shop` header is never part of the signed bytes: [4](#0-3) 

The binding the gem is expected to enforce is:
`shop authenticated by HMAC == shop acted upon by the handler`

but in reality the gem only proves:
`bytes verified (raw_body) == bytes signed (raw_body)`

while `shop` is parsed, unauthenticated, from headers, and is the value forwarded to the tenant-scoped handler logic. Any party capable of obtaining one validly-signed `(raw_body, hmac)` pair (which does not require possessing `api_secret_key`) can resubmit that exact body/HMAC pair to the app's webhook endpoint with a different `shop-domain` header, and `Registry.process` will treat the payload as authentic and attribute it to the attacker-chosen shop.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` to select or scope which tenant's records the webhook payload is applied to (the documented purpose of the field, as seen in the test assertions `assert_equal(@shop, data.shop)`), an attacker who can capture or replay one legitimately-signed webhook body can cause the library to authenticate that payload under an arbitrary shop domain, i.e., **cross-tenant access**: data intended for shop A can be attributed to and processed as belonging to shop B purely by tampering with an unauthenticated header, without needing `api_secret_key` or any privileged credential.

### Likelihood Explanation
Exploitation only requires the ability to submit an HTTP POST to the app's public webhook endpoint with attacker-controlled headers and a previously-observed valid `(body, hmac)` pair — no secret key or session is needed. The likelihood of obtaining at least one legitimate signed webhook (e.g., from a shop the attacker legitimately controls, or from any publicly-inspectable delivery) is realistic for typical merchant-facing apps, making this a practically reachable cross-tenant vector rather than a purely theoretical one.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value verified by the HMAC check, or otherwise require the caller to independently authenticate the source of the `shop-domain` header (e.g., cross-checking against a known/registered shop record before trusting it) rather than trusting it purely from an unauthenticated header once body-only HMAC validation succeeds. At minimum, document that `request.shop` is unauthenticated and must not be used by consuming apps for tenant selection without additional verification.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and receives a legitimate webhook delivery: raw body `B` with header `x-shopify-hmac-sha256: H` (valid for secret `api_secret_key`) and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays the exact same body `B` and HMAC header `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim.myshopify.com", "x-shopify-hmac-sha256" => H})` is constructed; `to_signable_string` still returns `B`, so `Utils::HmacValidator.validate` succeeds (per `lib/shopify_api/utils/hmac_validator.rb` and `lib/shopify_api/webhooks/request.rb`).
4. `Registry.process` passes validation and invokes the handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed_body, ...)` (`lib/shopify_api/webhooks/registry.rb:188-199`), causing the host application to process attacker-controlled data under `victim.myshopify.com`'s identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
