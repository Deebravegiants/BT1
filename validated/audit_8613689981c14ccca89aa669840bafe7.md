### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) fields are trusted without HMAC coverage, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the shop identity (`shopify-shop-domain`/`x-shopify-shop-domain` header) and other routing metadata are read straight from unauthenticated headers and passed downstream after HMAC validation succeeds. This breaks the intended binding of "HMAC-verified bytes == the shop the webhook is attributed to."

### Finding Description
`Request#to_signable_string` is defined as `@raw_body` only [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors instead read directly from HTTP headers via `shopify_header`, which are never included in the signed payload [2](#0-1) .

`Registry.process` validates the request with `Utils::HmacValidator.validate(request)` and, if it passes, immediately constructs `WebhookMetadata` using `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` taken from the same unauthenticated headers, then dispatches it to the app's registered handler [3](#0-2) . `HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string` (the raw body) and compares it against the `hmac` header using `OpenSSL.secure_compare` [4](#0-3) .

This means: `HMAC-valid(body) == HMAC-valid(body)` holds for *any* value of the `shop-domain` header, because that header is never part of the signed content. The identity equality the library is supposed to guarantee — "the shop stored/acted upon == the shop that produced the HMAC-signed bytes" — does not hold.

### Impact Explanation
An unprivileged internet user who has legitimately installed the app on their own (attacker-controlled) shop can receive genuine webhook deliveries with valid HMAC signatures for topics/bodies they control (e.g., `customers/data_request`, `orders/create` with attacker-supplied order content, or any topic the app subscribes to). Because the `shop-domain`, `topic`, and `webhook-id` header values are not covered by the HMAC, the attacker can resend that exact body+HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `Registry.process` will accept the HMAC as valid (it only checks the body) and hand the handler a `WebhookMetadata` claiming the payload originated from the victim shop [5](#0-4) . Any host application that uses `data.shop` to look up per-tenant state, write to per-shop records, or trigger shop-scoped side effects (billing, data deletion, order sync, etc.) can be tricked into cross-tenant data corruption/injection attributed to a shop the attacker doesn't own — a cross-tenant identity-binding failure reachable purely from an unprivileged network position, without any credential of the app.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the target app on an attacker-owned trial/free shop to legitimately harvest a valid `(body, hmac)` pair for a chosen topic, and (2) the ability to POST an HTTP request to the app's public webhook endpoint with forged headers — both are unprivileged-internet-user actions with no access token, `client_secret`, or elevated account required. The library provides no `shop` binding at the HMAC layer and no separate cryptographic assurance that the `shop-domain` header matches the entity that produced the signed body, so any host application that trusts `WebhookMetadata#shop` as returned by this gem inherits the flaw.

### Recommendation
Include the shop-identifying header (and ideally `topic`/`webhook-id`) inside the signable content used for HMAC verification, or independently verify that the `shop-domain` header matches an expected/registered shop before dispatching to handlers. At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are not HMAC-covered and must not be trusted for authorization decisions without additional server-side verification (e.g., cross-checking against the shop for which the webhook subscription was registered).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook the app subscribes to (e.g., `orders/create`), capturing the raw request body `B` and the valid `X-Shopify-Hmac-Sha256: H` header Shopify computed over `B` with the app's `client_secret`.
2. Attacker sends a new HTTP request to the app's webhook endpoint with the same body `B` and same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation passes [6](#0-5) .
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [5](#0-4) , causing the host application to process attacker-controlled data as if it came from the victim tenant.
