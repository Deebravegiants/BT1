### Title
Use of `block.timestamp` as the Uniswap V2 swap deadline in `EvmHost.dispatch()`/`fundRequest()` provides no protection against delayed/held transactions - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all let an unprivileged caller pay the relayer fee in native ETH, which is swapped for the fee token via `IUniswapV2Router02.swapETHForExactTokens`. In all three call sites the `deadline` argument passed to the router is `block.timestamp`, evaluated at execution time rather than at signing/submission time.

### Finding Description
The three swap call sites are: [1](#0-0) [2](#0-1) [3](#0-2) 

In each, `swapETHForExactTokens{value: msg.value}(feeAmount, path, address(this), block.timestamp)` is called with `block.timestamp` as the deadline. Because `block.timestamp` is read inside the transaction itself, the deadline check inside the Uniswap V2 router (`require(deadline >= block.timestamp)`) is trivially satisfied no matter how long the transaction has been sitting unmined in the mempool — it is always "now" when it finally executes. This is precisely the bug class from the referenced report: using `block.timestamp` for a swap deadline gives a miner/validator/relayer the ability to hold a transaction indefinitely (subject to gas price decay) until the state of the AMM pool is more favorable to them (or to a colluding party) before finally including it, defeating the purpose of the deadline parameter, which exists to bound the staleness of the price the caller implicitly accepted when signing.

This is directly reachable by any unprivileged actor: `dispatch()` is the ISMP message-dispatch entrypoint used by any HyperApp/user paying with native ETH, and `fundRequest()` is likewise open to any caller topping up a relayer fee with ETH.

### Impact Explanation
`swapETHForExactTokens` requests an *exact output* amount of `feeToken`, with `msg.value` as the (implicit) maximum input. Because there is no `amountInMax` check surfaced at the `EvmHost` level and the deadline offers no protection, a transaction can be held and only executed once pool conditions make the ETH-for-feeToken exchange rate maximally unfavorable to the caller, causing the caller to pay a larger ETH cost than intended for the same fixed fee-token output — a direct loss of value to the message sender. Because the swap is embedded in the core dispatch path used to pay Hyperbridge relayer fees for every outgoing POST/GET request, this affects the primary fee-payment flow of the protocol, not an edge case.

### Likelihood Explanation
Exploitability requires a miner/validator/searcher able to selectively delay inclusion of the specific transaction (e.g., via MEV bundling, private-order-flow relationships, or simple mempool monitoring) until a more favorable moment, which is a realistic capability on public EVM chains and does not require any privileged protocol role.

### Recommendation
Compute the deadline from a caller-supplied, or at least bounded, value rather than `block.timestamp`, e.g. accept a `deadline` parameter (or a fixed short window added at submission time, such as `block.timestamp + MAX_SWAP_WINDOW`) so that the deadline enforces staleness relative to when the caller intended the swap to execute, not relative to whenever it actually lands on-chain. Additionally consider exposing `amountInMax`/slippage protection on the ETH path rather than relying solely on `msg.value` as an implicit cap.

### Proof of Concept
1. User calls `EvmHost.dispatch(DispatchPost)` with `msg.value > 0` to pay the relayer fee in ETH, signing the transaction based on the current ETH/feeToken price.
2. A miner/searcher observes the transaction in the mempool but does not include it immediately.
3. The searcher manipulates the ETH/feeToken UniswapV2 pool price (or waits for market movement) so that at the moment of inclusion the effective ETH cost to receive the fixed `post.fee` amount of fee tokens is much higher.
4. The transaction is finally included; because the deadline argument is `block.timestamp` (evaluated at inclusion time), the router's deadline check always passes, and the swap executes at the unfavorable rate, at the caller's expense (all `msg.value` up to the amount consumed is used, and no protection bounds the maximum ETH the caller loses beyond `msg.value` itself, which the user set expecting the earlier price).
