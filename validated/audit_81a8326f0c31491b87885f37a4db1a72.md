## Finding: Incomplete Secret Redaction in Web Request Logging Exposes Key Material

### Title
Insufficient Secret-Field Blacklist in HTTP Request Logging Leaks Keystore Material - (File: `core/web/router.go`)

### Summary
The gin request-logging middleware `loggerFunc` in `core/web/router.go` logs every request body at Debug level after passing it through a sanitizer that only redacts JSON fields whose key name contains the substring `"password"`. Any other sensitive field name (e.g., encrypted keystore blobs submitted to key-import endpoints) is logged verbatim, mirroring the CVE-2025-65957 bug class of "configuration/ログ summaries failing to redact sensitive data."

### Finding Description
`loggerFunc` buffers the raw request body and, after the handler runs, logs it via `readBody`: [1](#0-0) 

`readBody` delegates to `readSanitizedJSON`, which walks the top-level JSON keys and redacts only keys matched by `isBlacklisted`: [2](#0-1) 

`isBlacklisted` and the underlying `blacklist` map only cover password-related field names — no entry exists for key material, secrets, tokens, or keystore fields: [3](#0-2) 

This sanitizer is applied uniformly to all API request bodies, including key-import endpoints such as `ETHKeysController.Import`, which reads the raw request body (an Ethereum keystore v3 JSON blob containing `crypto`, `ciphertext`, `kdfparams`, `mac`, and `salt` fields — none matching `"password"`) directly from `c.Request.Body`: [4](#0-3) 

Because the `oldpassword`/`newpassword` used to encrypt/decrypt the key material is passed as a query parameter (`redact(c.Request.URL.Query())` does correctly blacklist it), but the encrypted key JSON body itself is not blacklisted, the full keystore JSON — including salt, KDF parameters, and ciphertext — is written unredacted into the node's Debug logs. The same code path (`loggerFunc` wrapping every handler) applies to analogous import/export endpoints for CSA, VRF, OCR, and OCR2 keys, which follow the identical raw-body-read pattern.

### Impact Explanation
Anyone with read access to the Chainlink node's Debug-level logs (log aggregation systems, shared log storage, support tooling, etc.) can recover the complete encrypted keystore for an ETH/CSA/VRF/OCR key, including the KDF salt and ciphertext. This materially lowers the cost of an offline brute-force/dictionary attack against the encryption password to recover the underlying private key, which can control on-chain funds or OCR signing identity. This aligns with the CVE's "credential disclosure via logs" bug class, adapted to the Chainlink node's HTTP API surface rather than a Discord bot's webhook/config summaries.

### Likelihood Explanation
Exploitation requires: (1) the node operator has `LOG_LEVEL=debug` enabled (a supported, not uncommon, operational configuration for troubleshooting) and (2) an actor obtains read access to logs (a lower bar than direct node compromise) or a privileged API session imports/exports a key while logs are collected centrally. This is a plausible but not universally-enabled condition, so likelihood is moderate rather than trivial.

### Recommendation
Extend the redaction blacklist in `isBlacklisted`/`blacklist` (`core/web/router.go`) to cover known sensitive field names beyond `"password"` — e.g. `crypto`, `ciphertext`, `secret`, `privatekey`, `mac`, `keyjson` — or, better, switch key-import/export endpoints to skip body logging entirely (opt out of `loggerFunc` for these routes) rather than relying on a generic keyword blacklist.

### Proof of Concept
1. Start a Chainlink node with `LOG_LEVEL=debug`.
2. As an authenticated API session, `POST /v2/keys/eth/import?oldpassword=<pw>&evmChainID=<id>` with an Ethereum V3 keystore JSON body (containing `crypto.cipherparams`, `crypto.kdfparams.salt`, `crypto.ciphertext`, `mac`).
3. Observe the node's Debug log output produced by `loggerFunc`/`readBody` for this request: the full keystore JSON body is present unredacted (`"body": "{...\"crypto\":{...\"ciphertext\":\"...\",\"kdfparams\":{\"salt\":\"...\"}}...}"`), because none of its keys match the `"password"`-only blacklist in `isBlacklisted`.
4. An actor with access to these logs can extract the ciphertext/salt/KDF params to mount an offline password-cracking attack against the key. [3](#0-2) [4](#0-3)

func readSanitizedJSON(buf *bytes.Buffer) (string, error) {
	var dst map[string]any
	err := json.Unmarshal(buf.Bytes(), &dst)
	if err != nil {
		return "", err
	}

	cleaned := map[string]any{}
	for k, v := range dst {
		if isBlacklisted(k) {
			cleaned[k] = "*REDACTED*"
			continue
		}
		cleaned[k] = v
	}

	b, err := json.Marshal(cleaned)
	if err != nil {
		return "", err
	}
	return string(b), err
}

// NOTE: keys must be in lowercase for case insensitive match
var blacklist = map[string]struct{}{
	"password":             {},
	"newpassword":          {},
	"oldpassword":          {},
	"current_password":     {},
	"new_account_password": {},
}

func isBlacklisted(k string) bool {
	lk := strings.ToLower(k)
	if _, ok := blacklist[lk]; ok || strings.Contains(lk, "password") {
		return true
	}
	return false
}
