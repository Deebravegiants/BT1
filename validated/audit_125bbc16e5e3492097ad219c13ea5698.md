### Title
Unauthorized cross-session state disclosure via `RequestState` bypass of source-identity check - ([File: orb-relay-client/src/client.rs])

### Summary
The Orb-Relay client's message-receive loop verifies that an incoming message's `src.id` matches the expected peer (`dst_id`) before processing it, but this check is completely bypassed for messages that match the `self_serve::app::v1::RequestState` payload type. Any entity able to deliver a `RequestState` message to this connection causes the client to immediately reply with `self.last_message`, without verifying who is asking for it.

### Finding Description
In `PollerAgent::main_loop`, every incoming `RelayPayload` is supposed to be validated against the expected counterpart before being handled: [1](#0-0) 

The `if self_serve::app::v1::RequestState::matches(&payload).is_some()` branch is checked *first* and, when it matches, the code unconditionally sends `self.last_message.clone()` back to the sender — it never checks `src.id != self.config.dst_id` for this branch, unlike every other payload type which falls into the `else if src.id != self.config.dst_id { ... }` rejection path.

The code comment at the top of `main_loop` explicitly acknowledges the multiplexed nature of this channel and the reliance on this src/dst check for isolation: "We need to split auth and subscription... That will avoid multiplexing messages from different sources." [2](#0-1) 

This client (`Client::new_as_orb` / `new_as_app`) is used by `orb_relay_announce_orb_id` in the MasterPlan to communicate self-serve signup session state (`AnnounceOrbId`, `SignupEnded`, `CaptureStarted`, `AgeVerificationRequiredFromOperator`, etc.) between the Orb and the paired user app over a shared relay backend: [3](#0-2) . `self.last_message` is set on every outgoing send and is exactly the value replayed: [4](#0-3) 

Because messages arriving on the connection are multiplexed by the relay server and only filtered client-side by `src.id == dst_id`, and because the `RequestState` handling path skips that filter entirely, any party capable of sending a `RequestState`-typed payload into this stream (not necessarily the legitimate paired app/orb for this specific session) can force the client to disclose the last signup-session state message intended for the actual authorized counterpart.

### Impact Explanation
`last_message` can carry self-serve signup lifecycle data (e.g., `SignupEnded` success/failure feedback, `CaptureStarted`, `AgeVerificationRequiredFromOperator`) tied to a specific orb/session pairing. An unauthorized entity that is not the legitimate `dst_id` for that pairing can obtain this state by simply sending a `RequestState` message, which is a form of cross-session state disclosure — the exact class of "cross-signup state bleed" the audit brief calls out. It also means an attacker on the relay who is not part of the intended orb↔app pairing can passively probe or replay pending signup outcome data without being authenticated as that pairing's counterpart.

### Likelihood Explanation
Every self-serve signup session on the Orb goes through `orb_relay_announce_orb_id`, which uses this exact client and message loop, so the vulnerable code path is on the primary/reachable self-serve signup flow. Triggering it only requires the ability to inject a `self_serve::app::v1::RequestState` payload into the relay stream that reaches this client — no cryptographic break, privilege escalation, or hardware access is required, only interaction with the messaging/relay layer that the client trusts based on server-side multiplexing.

### Recommendation
Move the `src.id != self.config.dst_id` check ahead of the `RequestState` handling so that state-request replies are also gated on the sender being the expected counterpart, e.g.:
```rust
if src.id != self.config.dst_id {
    tracing::error!("Skipping received message from unexpected source: {:?}", src.id);
} else if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx.send(self.last_message.clone()).await?;
} else {
    self.handle_message(...).await?;
}
```
Additionally, consider server-side scoping (per the existing TODO) so the relay only delivers messages from the authenticated, session-bound counterpart rather than relying solely on client-side filtering.

### Proof of Concept
1. An orb connects via `Client::new_as_orb` for a self-serve signup session and sends `AnnounceOrbId`/`SignupEnded` as `last_message`.
2. A third party (not holding the `dst_id`/session identity paired with this orb) sends a payload matching `self_serve::app::v1::RequestState` into the relay stream reaching this orb client.
3. In `main_loop`, the `RequestState::matches` branch is taken unconditionally, and `self.last_message` (the sensitive signup-state message) is sent back to the unauthenticated sender via `sender_tx`, bypassing the `src.id != self.config.dst_id` check applied to all other message types. [5](#0-4)
