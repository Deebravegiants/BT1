### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking `Utils::HmacValidator.validate(request)` [1](#0-0)  before dispatching to the app's handler with `shop: request.shop` taken directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) . However, `Request#to_signable_string` returns only `@raw_body`, never any header [3](#0-2) , so the HMAC authenticates the body bytes only, not the shop that the framework hands to the merchant-facing handler.

### Finding Description
This is the analog of the DAI-permit report's bug class: a value that is *acted upon* (here, the `shop` used to attribute the webhook to a tenant) is not covered by the cryptographic check that is supposed to bind it (the HMAC). The identity binding that should hold is:

`shop authenticated by HMAC == shop delivered to WebhookHandler#handle`

But the actual binding is:

`HMAC verifies raw_body only` while `shop == unauthenticated header value`

`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the `hmac` header [4](#0-3) . For `Webhooks::Request`, `to_signable_string` is just `@raw_body` [5](#0-4) , and `shop` is read from a header that is never mixed into that signable string [6](#0-5) . Consequently, `HMAC(secret, body)` is valid for *any* value of the `shop-domain` header as long as `body` and the secret match — the signature says nothing about which shop the body belongs to.

An unprivileged internet user who operates their own legitimate Shopify development store receives real, validly-HMAC-signed webhooks from Shopify for their own store (this requires no privileged access, leaked secret, or victim credentials — merely operating any store that has the target app installed, which any merchant/developer can do via the app’s public install flow). They can capture one `(raw_body, hmac header)` pair from their own store's webhook, then replay it to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header value with the victim shop's domain. `HmacValidator.validate` still passes because it only checks `raw_body` against the secret, and `Registry.process` forwards `shop: request.shop` (now the victim's domain) to the app's `WebhookHandler#handle` [2](#0-1) .

### Impact Explanation
The gem's own documentation instructs handler authors to trust `data.shop` as "The shop domain of the webhook" and to key downstream work off of it (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [7](#0-6) , and states that `Registry.process` "will verify the request did indeed come from Shopify" [8](#0-7)  — implying the whole payload, including shop attribution, is authenticated. Because the shop is not bound to the signature, an attacker who controls their own store's webhook traffic can forge a webhook that the host app will process and record as belonging to a different, victim tenant, using attacker-chosen body content (subject to matching a topic schema Shopify would send). This is a cross-tenant identity-confusion vector: the app will act on/store attacker-supplied data under the victim shop's identity, satisfying the "cross-tenant access" high/critical impact criterion.

### Likelihood Explanation
The prerequisite is low: obtaining one legitimate `(body, hmac)` pair only requires installing the target app on any store the attacker controls (a normal, unprivileged action any developer/merchant can perform), then replaying it with a modified `shop-domain` header to the app's public webhook endpoint — no access to `api_secret_key`, tokens, or victim credentials is needed. This is a systemic gap in the gem's `Webhooks::Request`/`HmacValidator` design rather than a host-application misuse, since the documented processing flow relies entirely on `Registry.process` for validation.

### Recommendation
Bind the `shop-domain` header (and ideally `topic`/`webhook-id`) into the value that is HMAC-verified, or require the caller to separately verify that `request.shop` matches an expected/known shop for the delivered `webhook_id`/subscription before dispatch. At minimum, `Request#to_signable_string` should not diverge from all data later trusted by the handler, and the documentation in `docs/usage/webhooks.md` should be corrected to state that only the raw body is authenticated, not the shop header, so integrators know they must independently confirm shop identity (e.g., by cross-checking against Shopify's mandatory webhook list of active installations) before trusting `data.shop`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and lets Shopify deliver a real `orders/create` webhook, capturing `raw_body` and the `x-shopify-hmac-sha256` header — both valid per `HmacValidator` because they were genuinely signed by Shopify with the app's `client_secret`.
2. Attacker sends a POST to the app's webhook endpoint with the exact same `raw_body` and `x-shopify-hmac-sha256` header, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `@raw_body` [5](#0-4)  — validation succeeds.
4. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `shop == "victim.myshopify.com"` [2](#0-1) , causing the host app to process attacker-controlled webhook content as if it originated from the victim's store.
