## Finding: Stale operator authorization reused for signup attribution until an arbitrary expiration timer elapses

### Title
Operator QR-code authorization is not re-verified with the backend before being reused for subsequent signups, allowing misattributed signups on stale authorization data - (File: `src/plans/mod.rs`)

### Summary
The Wildcat bug class is: a piece of pending/cached state (the withdrawal batch) is only reconciled with the latest authoritative information (the repaid assets) when an unrelated timer expires, so stale state gets used to compute security/financial outcomes in the interim. The equivalent pattern exists in `orb-core`'s signup-attribution flow: once an operator QR-code has been validated against the backend, the resulting `OperatorData` (containing the operator identity used to attribute/authorize the signup) is cached and reused for every subsequent signup for up to `operator_qr_expiration_time` (23 hours by default) purely based on a local `Instant` check, without ever re-querying the backend to confirm the operator is still authorized.

### Finding Description
`scan_remaining_qr_codes` decides whether to reuse the previously scanned operator data or to re-scan/re-verify it purely based on an elapsed-time guard: [1](#0-0) 

Both the `QrCodes::Both` and `QrCodes::Operator` branches short-circuit straight to reusing `operator_data` — including its already-validated identity/location — as long as `operator_data.timestamp.elapsed() < operator_qr_expiration_time`. The backend re-validation call, `verify_operator_qr_code`, is only invoked in the fallback `_` branch, i.e. only when the cached data has expired: [2](#0-1) 

The same caching pattern gates the very first scan for the whole idle loop: [3](#0-2) 

`operator_qr_expiration_time` defaults to 23 hours: [4](#0-3) 

The cached `operator_data.qr_code.user_id` is what ultimately gets sent to the backend as the `distributorId` for every signup performed during that window: [5](#0-4) 

Exactly like the Wildcat `_getUpdatedState()` bug — where the market's pending-withdrawal state is only reconciled with the newly repaid assets once an expiry condition is hit, rather than on every state-mutating call — the Orb's operator-authorization state is only reconciled with the backend's authoritative state (is the operator still valid/authorized?) once the local expiry timer fires, rather than being re-verified on each use. Any change in operator authorization status (e.g. an operator being deactivated, having their session revoked, or their permissions changed on the backend) will not be observed by the Orb for up to 23 hours, during which every signup performed continues to be silently attributed to — and requires no re-authorization from — the stale operator identity.

### Impact Explanation
Because the operator identity is only checked against the backend once per `operator_qr_expiration_time` window, a revoked/deauthorized operator's identity can keep being used to attribute (and thus authorize) signups for up to 23 hours after backend-side revocation, leading to misattributed signups performed under an operator credential that should no longer be valid. This is a cross-signup state bleed: the trust decision made at the first QR scan silently propagates to every subsequent signup in the window without being re-checked.

### Likelihood Explanation
This is on the default signup hot path (`MasterPlan::run` → `scan_initial_qr_codes` / `idle_wait_for_signup_request` → `scan_remaining_qr_codes`) that every non-self-serve-button, non-oneshot Orb execution goes through, and requires no special hardware/operator/peer privileges to trigger — it happens automatically for any operator scanning their QR code once and then performing repeated signups within the (very long, 23-hour) expiration window.

### Recommendation
Re-verify the operator QR-code's authorization with the backend (`verify_operator_qr_code`) on each signup attempt (or at minimum on a much shorter interval), rather than trusting the locally cached `OperatorData` purely based on an elapsed-time check, mirroring the fix recommended in the analog bug of always reconciling with the latest available authoritative state instead of deferring to an arbitrary expiry.

### Proof of Concept
1. Operator scans their QR code; `scan_initial_qr_codes`/`scan_remaining_qr_codes` calls `verify_operator_qr_code`, which succeeds and populates `OperatorData { timestamp: Instant::now(), .. }` [6](#0-5) .
2. Backend revokes/deactivates that operator's authorization.
3. Within the next 23 hours (default `operator_qr_expiration_time`), the Orb performs additional signups. Because `operator_data.timestamp.elapsed() < operator_qr_expiration_time` holds, `scan_remaining_qr_codes` takes the `QrCodes::Both`/`QrCodes::Operator` fast-path and never calls `verify_operator_qr_code` again [7](#0-6) .
4. Each such signup is submitted to the backend still tagged with the now-revoked operator's `user_id` as `distributorId` [8](#0-7) , i.e. the Orb keeps operating on stale authorization state instead of reconciling with the backend's current (updated) state.

    async fn scan_initial_qr_codes(
        &mut self,
        orb: &mut Orb,
        qr_codes: &mut QrCodes,
        self_serve: bool,
        operator_qr_expiration_time: Duration,
    ) -> Result<()> {
        if self_serve
            && qr_codes
                .operator_timestamp()
                .map_or(true, |ts| ts.elapsed() > operator_qr_expiration_time)
        {
            loop {
                let qr_capture_start = Instant::now();
                let operator_qr_code =
                    self.scan_operator_qr_code(orb, None).await?.expect("to never timeout");
                let Some(operator_qr_code) =
                    self.handle_magic_operator_qr_code(orb, operator_qr_code).await?
                else {
                    continue;
                };
                let Some((_, operator_location_data)) =
                    self.verify_operator_qr_code(orb, &operator_qr_code, qr_capture_start).await?
                else {
                    continue;
                };
                *qr_codes = QrCodes::Operator {
                    operator_data: OperatorData {
                        qr_code: operator_qr_code,
                        location_data: operator_location_data,
                        timestamp: Instant::now(),
                    },
                };
                break;
            }
        }
        Ok(())
    }
