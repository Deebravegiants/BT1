### Title
Webhook `shop` domain is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `request.shop` (read from the `X-Shopify-Shop-Domain` / `shopify-shop-domain` header) is used unauthenticated as the tenant identifier passed to the app's webhook handler. Because the app's `api_secret_key` is shared across every shop that installs the app, an attacker who controls their own installation can capture a validly-signed webhook (`raw_body` + HMAC) and replay it with the `shop-domain` header rewritten to a victim shop, producing a request that passes `HmacValidator.validate` yet carries an attacker-chosen tenant identity.

### Finding Description
`HmacValidator.validate` verifies the signature only over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to return solely the raw request body: [2](#0-1) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain` header, which is **not** part of the signed material: [3](#0-2) 

`Registry.process` only validates the HMAC of the request and then dispatches the handler using the same unauthenticated `request.shop`, treating it as the tenant identity for the webhook payload: [4](#0-3) 

Because `api_secret_key` is a single, app-wide secret (not per-shop), any merchant who installs the app can generate a body+HMAC pair that is valid for the app's secret. That attacker can then substitute the `shop-domain` header value with a victim shop's domain before delivering the request to the app's webhook endpoint. The signature check still passes — it only checked the body — but the handler receives `shop: <victim-shop>` bound to a payload the attacker fully controls (their own order/customer data, or fabricated data crafted to match the victim's records), corrupting or exfiltrating cross-tenant state. This is precisely the same identity-binding gap described in the source report: a value (`payout.ratio`-equivalent “shop”) is *used* to key downstream logic (tenant routing) without actually being covered by the same authenticity check (HMAC) that gates entry to that logic.

### Impact Explanation
Impact is Critical: cross-tenant access. Any host application that uses `request.shop` from `ShopifyAPI::Webhooks::Registry`/`Request` as the tenant key for persisting or acting on webhook data (the documented, intended usage pattern of this gem) can be made to apply attacker-supplied webhook data under a victim merchant's identity, or vice versa exfiltrate/poison the victim's state, without ever needing the app's `client_secret` or a stolen access token — only a legitimate (even free/trial) install of the app under the attacker's own shop.

### Likelihood Explanation
Likelihood is high: getting a valid `raw_body` + HMAC pair requires nothing more than installing the app on a shop the attacker controls and triggering any webhook (e.g., `orders/create`) to capture the exact bytes and their corresponding valid signature, then replaying the captured request with a modified `shop-domain` header value. No secret material, no privileged access, and no interaction with Shopify's servers beyond normal app installation is required.

### Recommendation
Include the shop domain in the HMAC-signable material for webhooks (Shopify's newer `verify_webhook`/`x-shopify-shop-domain` guidance ties the shop to the signature check contextually), or, at minimum, have `Registry.process`/consuming apps cross-check `request.shop` against the shop associated with the currently-registered/expected session/store before trusting it as a tenant key. `to_signable_string` for `Webhooks::Request` should be updated so the shop and topic headers participate in, or are otherwise bound to, the authenticity check the same way `Auth::Oauth::AuthQuery#to_signable_string` binds `shop`, `code`, `state`, etc.

### Proof of Concept
```ruby
# Attacker step 1: install the app on their own shop "attacker.myshopify.com"
# and let Shopify deliver a legitimate webhook, capturing:
raw_body = '{"id":1,"note":"legit"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, raw_body)
# (APP_SECRET is the app's single api_secret_key, unknown to attacker but this
#  value is legitimately produced by Shopify for the attacker's own request)

# Attacker step 2: replay the exact same body+hmac to the app's webhook
# endpoint, but with the shop-domain header rewritten:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # <-- forged, unsigned
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (only raw_body was checked),
#    handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
#    is invoked, attributing attacker-controlled data to the victim tenant.
```
