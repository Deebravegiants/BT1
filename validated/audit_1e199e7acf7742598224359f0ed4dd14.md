## Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) headers are trusted without HMAC coverage, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates an incoming webhook solely by checking that the HMAC signature matches the **raw request body**. The `shop` (and `topic`, `webhook_id`, `api_version`) values that the handler subsequently trusts and acts on are read straight from unauthenticated HTTP headers that are never included in the signed content. This breaks the identity binding: `shop attributed to the webhook handler == shop covered by the verified HMAC`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are parsed from headers with no cryptographic protection: [2](#0-1) 

`Registry.process` validates the HMAC over that signable string (i.e., only the body) and then hands `request.shop`, `request.topic`, and `request.webhook_id` straight to the app's handler as trusted context: [3](#0-2) 

`HmacValidator.validate` computes the signature only from `verifiable_query.to_signable_string`, so for webhooks it is a function of the body alone, never the shop/topic/id headers: [4](#0-3) 

Contrast this with the OAuth callback `AuthQuery`, where `shop` and `host` are explicitly included inside the signed string so they cannot be tampered with independently of the signature: [5](#0-4) 

Because the `api_secret_key` (the app's client secret) is shared across every shop that installs the app, any tenant that has the app installed legitimately receives real webhooks with a body + valid HMAC signed under that same shared secret. That tenant can capture one such (body, hmac) pair and replay it to the app's webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`/`shopify-webhook-id`) header for a different, victim shop. `HmacValidator.validate` still succeeds, because it only checks the body against the shared secret, and `Registry.process` passes the attacker-controlled `shop` value straight into `WebhookMetadata`, so the handler executes attributed to the wrong tenant.

The gem's own documentation asserts that `Registry.process` "will verify the request did indeed come from Shopify," implying full authenticity of the delivered metadata, not just the body bytes: [6](#0-5) 

That claim is broader than what the implementation actually guarantees, since the `shop` field used to key per-tenant data is excluded from the signed payload.

### Impact Explanation
This allows cross-tenant data confusion in any app that trusts `WebhookMetadata#shop` (as the gem's own docs' example handler does — `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) without independently re-verifying it against a known/installed shop list. An attacker who is a legitimate but malicious tenant of the app can cause webhook-driven state changes or data writes to be attributed to another merchant's tenant, since the "come from Shopify" guarantee documented for `Registry.process` does not actually bind the shop identity to the signature.

### Likelihood Explanation
Exploitation requires the attacker to control at least one legitimate installation of the vulnerable app (to obtain a valid body+HMAC pair) and the ability to POST directly to the app's public webhook endpoint with modified headers — both are available to an ordinary, unprivileged internet user/merchant, with no access to `api_secret_key`, access tokens, or any Shopify-side privilege required.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signed content (or otherwise cryptographically bind them, e.g. by validating them against Shopify's `X-Shopify-Hmac-Sha256` computed over a canonical string that includes these header values), analogous to how `AuthQuery#to_signable_string` binds `shop`/`host` into the OAuth callback signature. At minimum, update `docs/usage/webhooks.md` to clarify that `Registry.process` only verifies the body's authenticity, not the shop/topic/webhook-id headers, and that consuming apps must independently validate `data.shop` against their own installed-shop records before trusting it.

### Proof of Concept
1. App "Acme" is installed on both `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, sharing one `api_secret_key`.
2. Shopify sends a legitimate webhook to attacker's installation: body `B`, headers `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-hmac-sha256: H` (valid HMAC of `B`).
3. Attacker replays a POST to the app's webhook endpoint with the same body `B` and HMAC `H`, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` because it only checks `B` against `H`: [7](#0-6) 
5. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the app to act on the victim tenant using attacker-controlled body content: [8](#0-7)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
