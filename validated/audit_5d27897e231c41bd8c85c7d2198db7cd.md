### Title
Webhook `shop` (and other metadata) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by `ShopifyAPI::Webhooks::Registry.process` and handed to the app's `WebhookHandler` are taken from unauthenticated HTTP headers. Because the `client_secret` (`Context.api_secret_key`) used to compute the HMAC is shared across every shop that has installed the app, a valid HMAC only proves "some webhook was signed with this app's secret" — it does not bind the signature to the specific `shop` claimed in the request.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read directly from attacker-controllable HTTP headers, none of which are part of the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then trusts the header-derived `request.shop` (and `topic`, `webhook_id`, `api_version`) when constructing the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The `HmacValidator.validate` call only proves the raw body bytes were signed with `Context.api_secret_key`; it says nothing about which shop the body belongs to: [4](#0-3) 

Since `api_secret_key` is the app's single `client_secret`, shared by design across all shops that install the app (it's the same value used in `Auth::Oauth.validate_auth_callback` for every merchant), any merchant who installs the app can capture a legitimate webhook that Shopify sends to their own shop (valid body + valid HMAC), then replay that exact body/HMAC pair to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` (and `X-Shopify-Webhook-Id`/`X-Shopify-Topic`) header to name a *different* victim shop. The gem's documentation explicitly claims `Registry.process` "will verify the request did indeed come from Shopify," which overstates what is actually checked — only body integrity/authenticity is checked, not the shop binding: [5](#0-4) 

This is the "field acted on but not covered by the HMAC" analog described in the rules: `shop` is trusted and dispatched to the handler as an identity/tenant key, but is not part of the equality the HMAC actually verifies. The equality the code should enforce is `hmac == HMAC(secret, shop || body)` but instead it only enforces `hmac == HMAC(secret, body)`, leaving `shop` unauthenticated.

### Impact Explanation
Any app that uses `data.shop` from `WebhookMetadata` to key per-tenant state (e.g., looking up which merchant's session/access token to act on, as shown in the gem's own webhook doc example `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) can be tricked into attributing a replayed, validly-signed webhook body to an arbitrary victim shop chosen by the attacker. This is a cross-tenant confusion: a merchant with valid app installation (attacker) can inject webhook data that the app processes as if it originated from another merchant's store, because the trust boundary the app relies on (`Registry.process` "verified this came from Shopify for shop X") does not actually hold for the `shop` field.

### Likelihood Explanation
Requires only that the attacker be one of the app's installed merchants (a routine, low-privilege position — no leaked secrets, no TLS interception) and be able to capture one legitimate webhook delivery to their own store (trivial, since Shopify sends every subscribed webhook to the merchant's registered endpoint, easily observed via any reverse proxy/logging on the attacker's own server) and replay it with a modified header to the same public endpoint.

### Recommendation
Bind the shop identity into the signed content, or otherwise authenticate the header-derived `shop`/`topic`/`webhook_id` against a value obtained through an authenticated channel (e.g., cross-check `shop` against the specific webhook subscription that was registered for that `webhook_id` via a signed/looked-up mapping) rather than trusting it purely from an unauthenticated header. At minimum, document clearly that `Registry.process` only authenticates the body, not the `shop`/`topic`/`webhook_id` metadata, so consuming apps do not treat `data.shop` as a verified tenant identifier.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and subscribes to an `orders/create` webhook.
2. Shopify delivers a webhook to the attacker's registered endpoint with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and a JSON body.
3. Attacker captures the raw body and the `X-Shopify-Hmac-Sha256` value (both valid, since the app's `client_secret` is shared across all installs).
4. Attacker re-sends the identical body and HMAC header to the same webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` builds a request object where `hmac` is validated successfully (`Utils::HmacValidator.validate`, `lib/shopify_api/utils/hmac_validator.rb:12-22`) because it only checks the raw body against the shared secret; `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) then calls the app's handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, even though the body never belonged to that shop.
