## Title
Webhook HMAC only authenticates the request body, not the `shop`/`topic`/`webhook-id` headers, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC exclusively over that string. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers — which `ShopifyAPI::Webhooks::Registry.process` trusts to route the payload and to populate `WebhookMetadata` (and thus determine which tenant/handler the payload is attributed to) — are never included in the signed material. Passing `HmacValidator.validate` therefore only proves "this body was HMAC-signed with the app's secret at some point"; it proves nothing about which shop or topic that signature was issued for.

### Finding Description
`Request#to_signable_string` at [1](#0-0)  returns `@raw_body` only, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight out of unauthenticated headers at [2](#0-1) .

`HmacValidator.validate_signature` computes the HMAC purely over `verifiable_query.to_signable_string` and compares it to the `hmac` field: [3](#0-2) . For webhook requests this means the signature covers the body bytes only.

`Registry.process` treats a passing `HmacValidator.validate(request)` check as sufficient authentication for the entire request, then dispatches based on `request.topic` and forwards `request.shop` into the handler payload untouched: [4](#0-3) .

The binding the code implicitly assumes but does not enforce is:
`HMAC_valid(raw_body) == true` ⟹ `(shop-domain, topic, webhook-id)` headers are also authentic for that body.

That equality does not hold: the HMAC covers only `raw_body`. Any entity capable of triggering one genuinely-signed webhook delivery for an arbitrary body (e.g., an app installer receiving a legitimate webhook to their own store) can capture the `(raw_body, hmac)` pair and resubmit it directly to the app's public webhook endpoint with a different `x-shopify-shop-domain` and/or `x-shopify-topic` header. `HmacValidator.validate` will still return `true` because it never inspects those headers, and `Registry.process` will hand the attacker-chosen `shop`/`topic` to the registered handler as if Shopify itself had sent that topic for that shop.

### Impact Explanation
This breaks the tenant/topic identity binding that `Registry.process` relies on to decide "which shop's data store to update" and "which handler to invoke." A handler that uses `WebhookMetadata#shop` to select the tenant record to mutate (a common, documented usage pattern in this library's webhook docs) can be made to apply attacker-supplied body content under a victim shop's identity, or have a payload meant for one topic dispatched to a different topic's handler. This is cross-tenant data poisoning/confusion reachable by any party who can get one legitimately signed webhook delivered to them (i.e., any shop that installs the app), without needing the `api_secret_key` itself.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on an attacker-controlled shop to receive one authentic signed webhook, and (2) replaying that captured `(raw_body, hmac)` to the app's public webhook endpoint with forged `shop-domain`/`topic` headers. No secret material, TLS interception, or privileged access is required — this is achievable by any ordinary app installer/unprivileged internet user who can reach the webhook endpoint.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the material that is cryptographically bound to the signature check, or otherwise cross-validate them against an independently trusted source (e.g., verify `shop` against the registered/expected shop for that endpoint, or require topic to be encoded within the signed payload) rather than trusting the raw headers once `to_signable_string` (body-only) passes HMAC validation.

### Proof of Concept
1. Register the app on attacker-owned shop `attacker.myshopify.com` and receive a legitimate webhook for topic `orders/create`, with headers:
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-topic: orders/create`
   - `x-shopify-hmac-sha256: <valid signature over raw_body>`
2. Capture the exact `raw_body` and `x-shopify-hmac-sha256` value.
3. POST that same `raw_body` and `x-shopify-hmac-sha256` to the app's public webhook endpoint, but replace headers with:
   - `x-shopify-shop-domain: victim.myshopify.com`
   - `x-shopify-topic: orders/create` (or a different registered topic)
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers/body [5](#0-4) , `HmacValidator.validate` returns `true` because only `raw_body` is checked, and `Registry.process` invokes the handler with `shop: "victim.myshopify.com"` and the attacker's body content [6](#0-5) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
