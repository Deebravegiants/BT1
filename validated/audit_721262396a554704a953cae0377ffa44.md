### Title
Webhook `shop` header is not covered by the HMAC signature, allowing shop-identity spoofing in webhook processing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content solely from the raw request body (`to_signable_string` returns `@raw_body`), while the `shop` value that is later handed to the application's webhook handler is read from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never included in the signed bytes. `Registry.process` only checks `Utils::HmacValidator.validate(request)` (which validates the body) before dispatching `WebhookMetadata.new(... shop: request.shop ...)` to the handler, so the `shop` field consumed by the host application is unauthenticated.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

`Request#shop` is read from an HTTP header, not from the signed body: [1](#0-0) [3](#0-2) 

`Registry.process` validates only the HMAC of the request (i.e., of the body) and then trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`, i.e., the body only: [5](#0-4) 

The equality that should hold — "shop authenticated == shop attributed to the processed webhook data" — is broken: the shop identity delivered to `WebhookMetadata#shop` is never part of the cryptographically verified payload. This maps directly to the reported bug class: "a field acted on but not covered by the HMAC."

An unprivileged internet user who can install the app on their own shop (a normal, permitted action) receives real webhooks from Shopify with a valid `hmac-sha256` value computed only over the JSON body and their own `shop-domain` header. Because the body content for many topics is generic/predictable or can be triggered repeatedly by the attacker on their own shop, the attacker can capture a `(body, hmac)` pair and replay it directly against the victim application's webhook endpoint while substituting an arbitrary `shop-domain` header (e.g., a victim shop domain). `Registry.process` will still validate successfully (the HMAC only checks the body, not headers), and the handler will receive `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` to select which merchant's session/tenant data to update, delete, or reprocess (the intended and documented use, per `Registry.process`), this allows cross-tenant data confusion/injection: an attacker-controlled webhook body can be attributed to another shop's tenant context. This matches the Critical impact category "cross-tenant access."

### Likelihood Explanation
The attacker only needs their own legitimate app installation to generate a validly-HMAC'd webhook body/signature pair (no `api_secret_key`, access token, or privileged access to the victim required), then a direct HTTP POST to the app's public webhook endpoint with a forged `shop-domain` header — well within the "unprivileged internet user" threat model.

### Recommendation
Bind the `shop` (and `topic`/`webhook_id`, if used for authorization decisions) into the HMAC-verified payload rather than trusting the raw header value. Concretely, include the shop domain in `to_signable_string` (or otherwise cryptographically bind header values to the signature, mirroring the effect of adding a "balance/amount" style consistency check from the report), or validate that `request.shop` matches an independently-authenticated identity (e.g., a shop already associated with the specific webhook subscription being looked up) before constructing `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and lets Shopify deliver a real webhook (e.g., `orders/create`) to the app's endpoint; attacker captures the raw JSON `body` and the `x-shopify-hmac-sha256` header — both valid because Shopify signed them with the app's real `api_secret_key`.
2. Attacker sends a new HTTP POST to the same webhook endpoint with the identical `body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body`. [6](#0-5) 
4. The handler executes with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own shop — demonstrating the shop-identity binding is not enforced by the cryptographic check.
