### Title
Webhook `shop` identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authenticated purely because `Utils::HmacValidator.validate(request)` succeeds, and then forwards `request.shop` (and `topic`, `webhook_id`, `api_version`) straight to the app's handler as the trusted tenant identifier. However, `Request#to_signable_string` only returns `@raw_body`; none of the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers are part of the signed material.

### Finding Description
The binding that should hold is: `HMAC-verified bytes == bytes the handler treats as authoritative`. In this gem that equality is broken:

- `HmacValidator.validate` computes `HMAC(api_secret_key, request.to_signable_string)` and compares it to the `hmac-sha256`/`x-shopify-hmac-sha256` header [4](#0-3) .
- `Request#to_signable_string` returns only `@raw_body` [3](#0-2) .
- `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read directly from unauthenticated HTTP headers [5](#0-4) .
- `Registry.process` validates the HMAC once, then constructs `WebhookMetadata` using `request.shop` (an unauthenticated header value) alongside the HMAC-verified body, and calls the app's handler with it [6](#0-5) .
- The documentation instructs handler authors to trust `data.shop` as "The shop domain of the webhook" with no caveat to re-verify it [2](#0-1) , and states that `Registry.process` "will verify the request did indeed come from Shopify" [7](#0-6) , implying the entire request — including its identifying headers — is authenticated when only the body is.

Because a single `api_secret_key` is shared by every shop that installs the app, any merchant/unprivileged user who legitimately installs the app on their own store can trigger a real, correctly-HMAC-signed webhook delivery for their own shop (e.g. by editing a product to trigger `products/update`). That attacker fully controls the resulting `raw_body` and can capture the valid `(raw_body, hmac)` pair Shopify sent to the app. Because `shop-domain`, `topic`, and `webhook_id` are outside the signed material, the attacker can replay that same `raw_body`/`hmac` pair directly to the app's webhook endpoint while substituting any other tenant's `shop-domain` header (and/or a different registered `topic`). `HmacValidator.validate` will still return `true` since it only checks `raw_body` against the same shared secret, and `Registry.process` will invoke the handler with `WebhookMetadata` claiming the forged shop as the source.

### Impact Explanation
This is a cross-tenant identity confusion: an app built on this gem cannot distinguish "verified body from shop A" from "verified body falsely attributed to shop B" using only what this gem provides, despite the gem's documentation implying the whole request is authenticated. Any handler that uses `data.shop` to select which tenant's records to create/update/delete (a extremely common and gem-recommended pattern, per the sample handler at lines 19-29 of the docs) can be tricked into writing attacker-controlled webhook body content into a victim shop's data path — a cross-tenant access impact.

### Likelihood Explanation
Requires only that the attacker be able to install the app on their own store (or otherwise trigger any topic/webhook to their own installation) and send an arbitrary HTTP POST to the app's public webhook endpoint — both are unprivileged-internet-user-level actions with no access token, `client_secret`, or victim credentials needed.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-covered signable string (or otherwise cryptographically bind them to the body), so `HmacValidator.validate` fails if any of these are altered independently of the signed body. At minimum, update the documentation to explicitly warn that `data.shop`/`data.topic` are not currently covered by the HMAC and must be independently cross-checked by the app (e.g., against the shop recorded when the specific `webhook_id`/subscription was registered).

### Proof of Concept
1. App merchant M installs the target app on `attacker-shop.myshopify.com` and registers for `products/update` webhooks (normal, unprivileged flow).
2. M edits a product on their own store, causing Shopify to POST a legitimately HMAC-signed webhook to the app's endpoint:
   - Headers: `x-shopify-topic: products/update`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw_body with api_secret_key>`
   - `raw_body`: fully controlled by M (M can name/describe the product however they want).
3. M captures this `(raw_body, hmac)` pair (trivial — M owns the store, can also self-host a receiving endpoint by pointing the topic path elsewhere, or sniff their own traffic).
4. M sends a new POST directly to the app's public webhook route with the same `raw_body`/`x-shopify-hmac-sha256`, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate(request)` returns `true` (it only hashes `raw_body`) [3](#0-2) .
6. `Registry.process` invokes the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)` [6](#0-5) , and any handler that uses `data.shop` to route the update (as the gem's own documented example does [8](#0-7) ) processes attacker-controlled content under the victim tenant's identity.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
