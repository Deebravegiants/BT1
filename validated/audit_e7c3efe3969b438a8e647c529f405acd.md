### Title
Denial of Service via unchecked reserve subtraction in `canGraduate` reachable through `Pair.swap`'s `+1` K-invariant slack - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.canGraduate` and `Bonding.previewLtUntilGraduation` compute `assetReserve - _launchTimeVirtualLtReserve(token_, pair)` without a floor check [1](#0-0) . Both `Bonding.buy` (via the post-trade graduation check inside `_executeBuy`) and `Bonding.sell` (directly) call `canGraduate` unconditionally on every trade [2](#0-1) . If `assetReserve` is ever driven below the recovered launch-time virtual LT reserve, this subtraction underflows and reverts with a Solidity Panic, permanently bricking both buy and sell for that token — an unrecoverable, permissionless DoS, analogous to CVE-2018-18206's unguarded arithmetic leading to a crash.

### Finding Description
`Pair.swap` enforces the K-invariant with a `+1` slack on both reserves: `(newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k` reverts [3](#0-2) . This `+1` tolerance is a per-trade rounding allowance, not a bound on the reserves' absolute floor. `_pool.k` is fixed at mint to `totalSupply * virtualLtReserve` and never changes [4](#0-3) , and `Bonding._launchTimeVirtualLtReserve` recovers that exact value as `Pair.k() / Token.TOTAL_SUPPLY()` [5](#0-4) .

`canGraduate`'s USD leg assumes `assetReserve >= _launchTimeVirtualLtReserve` always holds and computes the difference with plain subtraction: [6](#0-5) 

`previewLtUntilGraduation` performs the same unguarded subtraction on the same two reads [7](#0-6) .

The invariant test suite documents that this floor is expected to hold only via the initial seeding relationship (`tokenReserve` starts at `totalSupply`, only decreases via buys, and sell-backs are bounded by prior buys) [8](#0-7) , but that invariant is about `tokenBalance() < tokenReserve`, not about a hard floor on `assetReserve` under the `+1` K-slack rounding tolerance across many repeated buy/sell round-trips. Each swap is allowed to leave the true `tokenReserve * assetReserve` product up to `~tokenReserve + assetReserve` below `k` (the `+1` slack on each side), so a long sequence of small buy/sell round-trips by a single unprivileged trader can ratchet `assetReserve` down relative to `tokenReserve` beyond what a single-trade rounding tolerance would suggest, without ever tripping `KInvariantViolated`. Because `canGraduate` is invoked unconditionally by `Bonding.sell` on line 598 and by the buy path's post-trade graduation check, once the subtraction underflows the token is permanently unable to process buys or sells — there is no recovery path since `canGraduate` is not gated behind any admin function and lifecycle state can't be reset by a token creator or admin call in the reachable surface.

### Impact Explanation
A successful drift of `assetReserve` below the recovered virtual reserve permanently DoSes the affected bonding curve: every subsequent `Zap.buy`/`Zap.sell` call and every direct `Bonding.buy`/`Bonding.sell` call reverts with an arithmetic panic, freezing the token pre-graduation. Traders who already hold curve tokens lose the ability to exit via the curve (their only path is the frozen curve, since the token cannot graduate either — `finalizeGraduation`'s `_prepareGraduationLiquidity` performs the identical unguarded subtraction at line 1084 and would also revert). This is a permanent freezing of trader funds and matches the "Reject... no-impact analogs" bar since it stops all fund movement for the token, satisfying "permanent freezing of trader funds."

### Likelihood Explanation
This requires an unprivileged trader to execute many small buy/sell round trips (each individually passing the `+1` K-invariant check) to accumulate rounding drift large enough to breach the floor. This is gas-costly and its exact feasibility depends on the magnitude of per-trade rounding loss versus the size of `virtualLtReserve`, which I was not able to fully quantify with the tools available — the reachable severity depends on precise reserve magnitudes and the number of round-trips needed, which requires numerical simulation beyond static code reading.

### Recommendation
Guard the subtraction in `canGraduate`, `previewLtUntilGraduation`, and `_prepareGraduationLiquidity` with a `assetReserve > virtualLtReserve` check (treating the USD leg as `0`/not-yet-graduatable when it's not), and audit whether `Pair.swap`'s `+1` slack should instead be a fixed absolute floor tied to `_pool.k` rather than a per-call relative tolerance, to remove the possibility of cumulative drift across repeated trades.

### Proof of Concept
Not fully verified with concrete numbers — I could not execute or simulate the contracts with the available read-only tools to confirm the exact number of round-trip trades required to breach the floor under the `+1` K-slack. A Devin agent with terminal access should write a Foundry fuzz/invariant test that repeatedly calls `Bonding.buy` then `Bonding.sell` with the maximum amount received each time, checks `assetReserve` and `_launchTimeVirtualLtReserve(token, pair)` after each round trip, and confirms whether `assetReserve` can be driven below `_launchTimeVirtualLtReserve` (triggering the panic in `canGraduate`) within a gas-bounded number of iterations.
