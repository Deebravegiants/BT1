### Title
JWT replay-guard check-then-record race allows concurrent duplicate HTTP-trigger executions - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` decides whether a JWT (identified by its `jti` claim) has already been used by calling `h.jwtCache.isReplay(claims.ID)` and, only if that returns false, later calling `h.jwtCache.recordUsage(claims.ID)`. These are two separate, non-atomic operations on the same cache. This is the same bug class as the reported vault issue: a value is read ("check"), a decision is made based on that stale read, and the state is updated ("record") afterward, with no atomicity between the two steps — so two requests arriving "at the same time" can both pass the check before either records its usage.

### Finding Description
In `Authorize`:
```go
if h.jwtCache.isReplay(claims.ID) {
    ...
    return nil, errors.New("JWT token has already been used...")
}
...
h.jwtCache.recordUsage(claims.ID)
``` [1](#0-0) 

The struct backing this cache (`jwtReplayCache`) is defined with its own `sync.RWMutex`: [2](#0-1) 

I could not view the bodies of `isReplay`/`recordUsage` in this final pass (the file read failed due to a tool-call error on the last iteration), so I cannot confirm with 100% certainty whether the two methods use a single held lock across both operations or acquire/release the lock independently. Given the API is exposed as two separate public methods (`isReplay` then, afterward, `recordUsage`) rather than a single atomic `CheckAndRecord`-style method (which is exactly the pattern used correctly elsewhere in this codebase, e.g. `RequestReplayGuard.CheckAndRecord` in `core/capabilities/vault/request_replay_guard.go`, which holds a single mutex across the check-and-set), the design of `Authorize` itself is check-then-act at the call-site level regardless of internal locking: even if each individual cache method is thread-safe internally, `isReplay(...)` and `recordUsage(...)` are invoked as two independent, non-atomic calls separated by other logic (looking up `authorizedKeys`, building the `AuthorizedKey`). Two goroutines handling two HTTP requests carrying the identical JWT can both call `isReplay` and both observe "not yet used" before either calls `recordUsage`, defeating the replay guard — directly analogous to the vault's balance-diff race where two concurrent depositors both observe the same "before" state.

Compare to the vault capability's own replay guard, which correctly performs check-and-record under one lock in a single method: [3](#0-2) 

The `WorkflowMetadataHandler.Authorize` path is reached directly from an unprivileged client's inbound HTTP trigger request via `httpTriggerHandler.authorizeRequest` → `workflowMetadataHandler.Authorize`, which is the request-impersonation/authentication gate for the internet-facing gateway: [4](#0-3) 

### Impact Explanation
If the check-then-record pattern is exploitable (i.e., if `isReplay` and `recordUsage` are not executed under one atomic critical section spanning both), an attacker (or a client experiencing legitimate retries/duplication at the network layer) could get the same signed JWT accepted twice concurrently, resulting in a duplicated/duplicate workflow execution being dispatched to the DON under one authorization token — a replay-protection bypass on the internet-facing gateway's authentication path. This matches the requested vulnerability classes ("concrete authentication or role bypass ... request impersonation ... cross-user response confusion").

### Likelihood Explanation
Requires an attacker (or client) to send two requests with the same JWT at nearly the same time, which is plausible for anyone with a valid signed token (e.g., a compromised token, or a legitimate signer replaying their own token). No special network position or node compromise is required — it's reachable from a normal client of the HTTP trigger gateway endpoint.

### Recommendation
Refactor `jwtReplayCache` to expose a single atomic method (e.g., `CheckAndRecord(jti string) error`) that performs the existence check and the recording of usage under one held lock, mirroring `RequestReplayGuard.CheckAndRecord` in `core/capabilities/vault/request_replay_guard.go`. Update `WorkflowMetadataHandler.Authorize` to call this single atomic method instead of the separate `isReplay`/`recordUsage` calls.

### Proof of Concept
Not independently verified end-to-end due to inability to view the `isReplay`/`recordUsage` method bodies in this session (tool call failed on the final iteration). Conceptually: two goroutines call `Authorize(workflowID, sameToken, sameReq)` simultaneously; both call `jwtCache.isReplay(claims.ID)` before either calls `jwtCache.recordUsage(claims.ID)`, so both proceed past the replay check and the workflow trigger is dispatched twice for the same JWT.

**Note on uncertainty:** I was not able to confirm the exact internal locking granularity of `isReplay`/`recordUsage` due to a failed file read in the final iteration; this finding is based on the call-site pattern (two separate method invocations rather than one atomic check-and-record call) and the contrast with the codebase's own correctly-atomic `RequestReplayGuard.CheckAndRecord` implementation used for the same purpose elsewhere in the vault capability. A Devin session with full file access should verify `jwtReplayCache`'s method implementations directly before treating this as confirmed.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}

func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}
