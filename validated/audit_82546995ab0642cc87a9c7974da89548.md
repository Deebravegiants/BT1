This confirms the vulnerability: the `Webhooks::Request#to_signable_string` returns only `@raw_body`, while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers via `shopify_header` [1](#0-0) . `Registry.process` validates only the HMAC over the raw body via `Utils::HmacValidator.validate(request)`, then dispatches to the handler using `request.shop`, `request.topic`, and `request.webhook_id` unmodified [2](#0-1) . ### Title
Webhook shop/topic/webhook_id headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values that `Registry.process` forwards to the app's webhook handler are taken directly, unauthenticated, from HTTP headers.

### Finding Description
The identity binding that should hold is: `hmac_signed(bytes) == bytes_the_handler_acts_on`. In this gem it does not. `to_signable_string` returns only `@raw_body` [4](#0-3) , but `shop`, `topic`, and `webhook_id` are read from `shopify_header(...)` — plain HTTP headers with no cryptographic linkage to the HMAC [5](#0-4) . `Registry.process` validates only `Utils::HmacValidator.validate(request)` (i.e., the body's signature) and then builds `WebhookMetadata` from `request.topic`, `request.shop`, and `request.webhook_id` taken straight from those headers [2](#0-1) . `HmacValidator.validate_signature` compares `compute_signature(verifiable_query.to_signable_string, secret)` against the received HMAC — it never incorporates `shop`, `topic`, or `webhook_id` [6](#0-5) .

Before the attack: `request.shop`/`request.topic`/`request.webhook_id` are supposed to equal the values Shopify actually generated the HMAC for. After the attack: an internet-facing actor who can present the app's webhook endpoint with *any* previously-observed valid `(raw_body, hmac)` pair (e.g., captured from their own store's genuine webhook traffic, or from a publicly-visible sample payload of a shared/generic topic) can freely substitute the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` headers while keeping the body and HMAC unchanged, and the check in `Registry.process` will still pass, because the signature verification never reads those headers.

### Impact Explanation
This breaks the shop/tenant identity binding for webhook processing: the merchant/topic value passed to the app's handler is not the one the signature actually vouches for. A host application that trusts `WebhookMetadata#shop` (as the documented API instructs it to, see `docs/usage/webhooks.md` example calling `perform_later(shop_domain: data.shop, ...)`) can be tricked into associating attacker-chosen webhook bodies with an arbitrary victim shop domain, or mislabeling the topic/webhook_id used for idempotency/deduplication logic. This is a cross-tenant confusion at the trust boundary the gem is responsible for (verifying "this webhook data really is for shop X"), matching the Critical "cross-tenant access" impact category, since a party who legitimately receives (or otherwise obtains) one valid signed webhook body can replay it under a different shop's identity indefinitely.

### Likelihood Explanation
Exploitation only requires the ability to send arbitrary HTTP requests to the app's public webhook callback endpoint plus one legitimate `(raw_body, hmac)` sample — no `api_secret_key`, access token, or privileged account is needed. Any merchant with the app installed on their own store already receives such valid pairs from Shopify legitimately, so this is reachable by an ordinary unprivileged actor.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the value that is HMAC-verified (or otherwise cryptographically bind them to the body/signature), or document and enforce that the host application must independently authenticate/authorize the `shop` value in `WebhookMetadata` before using it (e.g., by only trusting shops with an active registered webhook subscription id looked up server-side) rather than trusting the header value directly.

### Proof of Concept
1. Register a webhook handler and have Shopify deliver one legitimate webhook to shop A's endpoint, capturing `raw_body` and the `X-Shopify-Hmac-Sha256` header.
2. Replay the same `raw_body` and `hmac` header to the same app endpoint, but replace `X-Shopify-Shop-Domain` with shop B's domain and/or change `X-Shopify-Topic`/`X-Shopify-Webhook-Id`.
3. `ShopifyAPI::Webhooks::Registry.process` still calls `Utils::HmacValidator.validate(request)` successfully — as shown by `test/webhooks/registry_test.rb`, validation only ever checks the raw body against the HMAC header [7](#0-6)  — and the handler is invoked with `data.shop == "shop B"` even though the payload actually originated for shop A.
