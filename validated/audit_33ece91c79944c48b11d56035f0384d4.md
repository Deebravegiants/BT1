This confirms the vulnerability. In `lib/shopify_api/auth/oauth/auth_query.rb`, `to_signable_string` includes `shop` in the signed content (matching Shopify's OAuth HMAC design), but in `lib/shopify_api/webhooks/request.rb`, `to_signable_string` returns only `@raw_body` — the `shop-domain` header used as `request.shop` is never part of the HMAC-signed material.

### Title
Webhook Shop-Domain Header Not Bound to HMAC Signature Allows Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, excluding the `shopify-shop-domain` / `x-shopify-shop-domain` header value that is later exposed via `request.shop` and passed into the webhook handler as the tenant identifier. Since all shops installed on a given app share the same `api_secret_key`, an attacker with network access to a webhook endpoint can take any validly HMAC-signed body (e.g., captured from a webhook delivered to their own shop, or any endpoint that echoes a signable body) and re-submit it with an arbitrary `shop-domain` header. The HMAC check passes because the shop value was never covered by the signature, breaking the intended binding: `authenticated_bytes (body signed by HMAC) == data acted upon by handler (topic + body + shop)`.

### Finding Description
`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string` to compute the expected signature and compares it to the received `hmac` value: [1](#0-0) 

For OAuth callbacks, `AuthQuery#to_signable_string` deliberately includes `shop` in the signed parameters: [2](#0-1) 

But for webhooks, `Request#to_signable_string` only returns the raw body, and `shop` is read from an unsigned header: [3](#0-2) 

`Registry.process` validates the HMAC over that same body-only string, then immediately trusts `request.shop` (from the unsigned header) as the tenant identity passed to the handler: [4](#0-3) 

Because `api_secret_key` is shared across every shop installed on the same app (it is the app's client secret, not per-shop), any party who can obtain one validly-signed `(body, hmac)` pair — for instance from a webhook delivered to their own shop's endpoint, or a shared/replayed payload — can present that same `(body, hmac)` pair to the victim application's webhook endpoint with a forged `shopify-shop-domain` header pointing at a different, victim shop. `HmacValidator.validate` will accept it because the signature never covered the shop value, so `authenticated content` != `content the handler treats as authoritative (shop identity)`.

### Impact Explanation
This breaks the tenant/shop binding for webhook processing: the handler receives `WebhookMetadata` claiming to be from an arbitrary victim shop while only the body was actually authenticated. Any app logic keyed off `data.shop` (data isolation, per-shop side effects, GDPR redact/data-request handlers) can be triggered against a shop the attacker doesn't control, enabling cross-tenant data confusion — analogous to the LDAP-injection report's core defect of trusting an unvalidated/unbound identity value in a security decision.

### Likelihood Explanation
Exploitation requires only network access to the app's public webhook endpoint and a single previously-observed valid `(body, hmac)` pair for the shared `api_secret_key` — no privileged credentials, access tokens, or TLS interception are needed, matching the "unprivileged internet user" threat model.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) in the HMAC-signable string for webhooks, or otherwise cryptographically bind the header value used for tenant identification to the payload signature, mirroring how `AuthQuery#to_signable_string` binds `shop` for OAuth callbacks.

### Proof of Concept
1. Register a webhook handler that trusts `data.shop` for tenant-scoped logic.
2. As the attacker, install the target app on your own shop `attacker.myshopify.com` and capture a legitimately delivered webhook `(raw_body, x-shopify-hmac-sha256)` pair — this HMAC is valid because it's computed with the shared `api_secret_key`.
3. Replay the exact same `raw_body` and `hmac` header value to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds (per `lib/shopify_api/utils/hmac_validator.rb` and `Request#to_signable_string` in `lib/shopify_api/webhooks/request.rb`, since `shop` is excluded from the signed string), and `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, per `lib/shopify_api/webhooks/registry.rb` lines 188-200.
