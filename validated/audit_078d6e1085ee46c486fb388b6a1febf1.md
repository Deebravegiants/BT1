This confirms the pattern: `createWithdrawalIdentifiers` in `withdrawal-watcher.ts` assigns each `WithdrawalParams` entry an `index`, incrementing per bridge route, so a batch of intents can contain **multiple withdrawals of the same asset** (same `bridge.route`, e.g. two BTC withdrawals to different destination addresses in one NEAR transaction) [1](#0-0) . Each resulting `WithdrawalIdentifier` still carries a distinct `index`, but the POA bridge's status-matching function ignores it entirely.

### Title
POA bridge withdrawal status matched only by `assetId`, causing status/txHash misattribution across withdrawals of the same token in one transaction - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`, `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`)

### Summary
### Finding Description
`findMatchingWithdrawal` in both `poa-bridge.ts` and `waitForWithdrawalCompletion.ts` looks up the withdrawal to report on solely by `nep141:${near_token_id} === assetId`, discarding the `index` that `createWithdrawalIdentifiers` computed to disambiguate multiple withdrawals of the same asset within a single NEAR transaction [2](#0-1) [3](#0-2) . The code comment self-acknowledges this: "matches by assetId... multiple withdrawals of the same token in a single transaction are not supported" [4](#0-3) . A dedicated test even documents "matches withdrawal by assetId, not by index" [5](#0-4) , but that test only exercises the case where the two withdrawals have **different** assetIds; it never exercises the same-assetId, multi-destination case, which is the actually dangerous one.

The equality broken here: the caller queries `describeWithdrawal({ index: i, withdrawalParams: paramsForIndex_i })` expecting the status/tx-hash of the withdrawal that corresponds to index `i`'s specific `destinationAddress`/`amount`. Instead, `Array.prototype.find` returns the **first** array element whose `near_token_id` matches, regardless of which destination/amount it actually belongs to. If a NEAR transaction contains two withdrawals of the same token (e.g. BTC to address A and BTC to address B), both `describeWithdrawal` calls (index 0 and index 1) resolve to the same first-matching POA record and report the same status/`transfer_tx_hash` for both, even though only one of the two withdrawals may actually be completed.

### Impact Explanation
`watchWithdrawal` in `withdrawal-watcher.ts` treats a "completed" status as authoritative and returns the `txHash` to the caller [6](#0-5) . If an integrator uses this SDK to process a batch of same-asset withdrawals to distinct recipients in one intent transaction, index 1's withdrawal could be reported "completed" with index 0's `transfer_tx_hash` while its own destination transfer is still pending or has a different hash — a status/hash misreport that can make an integrator credit or reconcile a withdrawal that did not actually settle to that recipient, or reconcile the wrong on-chain transaction against the wrong withdrawal record. This matches the "status/hash misreport" High-impact category from the rules.

### Likelihood Explanation
Requires the SDK/integrator to submit more than one withdrawal of the identical NEP-141 asset in a single NEAR transaction — a legitimate, user-controlled batching pattern already supported by `createWithdrawalIdentifiers`' per-route index bookkeeping [7](#0-6) . No malicious counterparty is needed — an ordinary user or integrator batching two same-token withdrawals to different addresses triggers it. Likelihood is moderate: it depends on batch usage patterns, and the authors are aware of the gap (per the code comment), but nothing in the code currently prevents or detects this scenario.

### Recommendation
Disambiguate `findMatchingWithdrawal` beyond `assetId` — incorporate `destinationAddress` and/or `amount` (and reject/throw when multiple POA records share the same asset and destination/amount ambiguously), or track per-asset occurrence counts on both sides (SDK-side params order vs. POA API response order) as the code comment itself suggests, before enabling/allowing batched same-asset withdrawals in a single transaction.

### Proof of Concept
1. Build a withdrawal transaction containing two POA-bridge withdrawals of `nep141:btc.omft.near`: index 0 to address `A`, index 1 to address `B`.
2. `createWithdrawalIdentifiers` assigns `index: 0` and `index: 1` to the two `WithdrawalIdentifier`s for the same `bridge.route` [8](#0-7) .
3. POA bridge completes the withdrawal to `A` first; the withdrawal to `B` is still `PENDING`.
4. Calling `describeWithdrawal` for index 1 (address `B`) still matches the array element for address `A` (since `findMatchingWithdrawal` only checks `assetId`) and returns `{ status: "completed", txHash: <A's tx hash> }`, per the matching logic in `poa-bridge.ts` lines 313-343 and 418-427 [9](#0-8) .
5. `watchWithdrawal` reports the withdrawal to `B` as completed with `A`'s transfer tx hash, even though `B` never received funds — a status/hash misreport.

**Note on completeness**: I could not fully trace, within available tool calls, whether upstream SDK entry points (`sdk.ts`) actively prevent constructing batches with duplicate `assetId` withdrawals to different destinations; this would need to be confirmed by inspecting `sdk.ts`'s withdrawal-execution path in full before treating this as conclusively exploitable in production usage.

	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;

	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;

			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
