### Title
Unfallible `exchangeRate()` reads inlined into `canGraduate()` / `previewLtUntilGraduation()` let a single external-LT revert permanently brick both buy and sell on the curve - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.canGraduate()` and `Bonding.previewLtUntilGraduation()` unconditionally call `IBounceLeveragedToken(info.ltAddress).exchangeRate()` whenever the curve's real token balance is non-zero (i.e., for almost the entire life of a token). These two views are wired directly into the hot trading path — `canGraduate()` is called at the end of every `Bonding.buy` and gates every `Bonding.sell`, and `previewLtUntilGraduation()` is called unconditionally by `Zap._executeBuy` on every non-graduated buy. None of these call sites use `try/catch` or a fallback value. If the external LT's `exchangeRate()` ever reverts, every buy and every sell on that curve reverts too, with no path to graduation (which itself requires `canGraduate()` to succeed) and no path to redeem via the post-graduation HyperSwap pool (graduation can't happen). This is the same bug class as the reported finding: an oracle-style external read embedded in a value/eligibility computation that "MUST NOT revert" bubbles a third-party failure into critical application logic, except here the blast radius is worse — it takes down both sides of the market, not just a read-only ERC-4626 view.

### Finding Description
`Bonding.canGraduate()`: [1](#0-0) 

reads `IPair(pair).tokenBalance()`; only if that balance is exactly `0` (curve fully sold out) does it short-circuit `true` without touching the LT. Otherwise it always calls `IBounceLeveragedToken(info.ltAddress).exchangeRate()` to compute `valueUsd`. This function is:

- Called at the end of every `Bonding.sell()`, where a revert propagates and blocks the sell outright: [2](#0-1) 

- Called at the end of every `Bonding.buy()` via `_executeBuy`, *after* the router swap has already executed on-chain logic, so a revert here unwinds the whole buy transaction: [3](#0-2) 

`Bonding.previewLtUntilGraduation()` has the same unconditional `exchangeRate()` read (short-circuits only when `realBalance == 0`): [4](#0-3) 

and is called unconditionally by `Zap._executeBuy` on every curve buy that hasn't yet graduated, purely to pre-size the LT mint against the graduation cap: [5](#0-4) 

None of the three call sites (`Bonding.sell`, `Bonding._executeBuy`→`canGraduate`, `Zap._executeBuy`→`previewLtUntilGraduation`) wraps the external call in `try/catch` or substitutes a fallback/last-known value. This mirrors the reported pattern exactly: `NoyaValueOracle._getValue()` "explicitly may revert" and is embedded in `totalAssets()`, which then poisons `convertToShares`/`convertToAssets`. Here, `IBounceLeveragedToken.exchangeRate()` may revert and is embedded in `canGraduate`/`previewLtUntilGraduation`, which then poison `Bonding.buy`, `Bonding.sell`, and `Zap.buy` — the core trading primitives, not just read-only accessors.

The interface itself documents no non-reverting guarantee: [6](#0-5) 

and the project's own docs acknowledge `exchangeRate()`'s freshness/staleness quirks as an accepted risk class, but only reason about *drift*, never about a *revert*: [7](#0-6) 

### Impact Explanation
If the paired BounceTech LT's `exchangeRate()` reverts for any reason (staleness guard, admin pause of the price feed, a transient computation failure inside the LT, etc. — a common pattern for leveraged/rebasing tokens), then for every token still on the curve (`tokenBalance() != 0`, i.e., essentially always except at the very last unit sold):

- `Bonding.sell()` unconditionally reverts (line 598's `canGraduate(tokenAddress)` call reverts instead of returning), so no seller — trader or creator — can exit.
- `Bonding.buy()` unconditionally reverts (the post-trade `canGraduate` check at line 929 reverts, unwinding the whole transaction even though the AMM swap logic itself succeeded), so no buyer can enter.
- `Zap.buy()` reverts even earlier via `previewLtUntilGraduation` at line 325, before even reaching `Bonding.buy`.
- Because `canGraduate()` also cannot return `true` while `exchangeRate()` reverts (unless the token happens to be at exactly `tokenBalance() == 0`), the token cannot transition into `Graduating`/`Graduated`, so holders cannot escape onto the HyperSwap V2 pool either.

The net effect is a total freeze of all curve-side trading and of the only exit ramp (graduation) for every token paired to the affected LT, for as long as the external `exchangeRate()` call keeps reverting. Traders' and creators' capital in the curve (LT already raised, tokens already bought) becomes inaccessible — this is a permanent-freezing-of-funds condition per the validation criteria, since neither buy, sell, nor graduation is reachable during the outage, and there's no time bound on how long the outage lasts.

### Likelihood Explanation
The trigger requires nothing from an attacker beyond the passive existence of a condition in the external LT's `exchangeRate()` implementation that causes a revert (e.g., a staleness check, a pause flag, or a transient divide-by-zero in the underlying price computation) — no privileged access to alt.fun's own contracts is needed. Given that the LT is an *external, third-party, upgradeable* dependency whose exact reversion conditions alt.fun's contracts do not control or defensively guard against, and given that the code paths that would revert (`Bonding.buy`, `Bonding.sell`, `Zap.buy`) are exactly the ones every ordinary trader must use, the likelihood of this occurring during the operational life of a widely-traded LT is non-trivial. The docs explicitly assume `exchangeRate()` "still works" even for retired LTs, which shows the team has not modeled the revert case at all — only the drift/staleness case.

### Recommendation
Wrap the `exchangeRate()` calls inside `canGraduate()` and `previewLtUntilGraduation()` in a `try/catch` (or a low-level `staticcall` with success check). On failure, either:
- Skip the USD-trigger leg entirely for that call (fall back to the supply-trigger-only behavior, which is monotonic and donation-resistant), allowing buys/sells to keep functioning without evaluating graduation eligibility that round, or
- Cache the last successfully-read exchange rate and use it as a stale fallback with an explicit "stale" flag surfaced to callers/off-chain consumers.
Either approach decouples the availability of core `buy`/`sell` functionality from the liveness of an uncontrolled external dependency, consistent with how `AccountingManager.totalAssets()` was recommended to return `0` instead of reverting when its price oracle is unavailable.

### Proof of Concept
1. Launch a token via `Bonding.launch` and buy tokens through `Zap.buy` so that `tokenBalance() > 0` (curve not sold out).
2. Have the paired LT's `exchangeRate()` revert (e.g., in a Foundry test, mock the call: `vm.mockCallRevert(address(lt), abi.encodeWithSelector(IBounceLeveragedToken.exchangeRate.selector), "")`).
3. Call `bonding.canGraduate(tokenAddr)` — observe it reverts instead of returning `false`/`true` (`Bonding.sol` L689-694).
4. As any trader, call `zap.sell(tokenAddr, tokenAmount, 0)` — observe the transaction reverts inside `Bonding.sell`'s `canGraduate` check (`Bonding.sol` L598), even though the trader legitimately holds tokens and wants to exit.
5. As any trader, call `zap.buy(tokenAddr, usdcAmount, 0, address(0))` — observe the transaction reverts inside `Zap._executeBuy`'s `previewLtUntilGraduation` call (`Zap.sol` L325) before even reaching the router.
6. Confirm there is no other path (direct `Bonding.buy`/`Bonding.sell` via an allow-listed router hits the same `canGraduate` calls) to trade or exit while `exchangeRate()` remains reverting, and that `triggerGraduation` also reverts for the same reason (`Bonding.sol` L977 calls `canGraduate`).

**Exchange-rate freshness on the USD trigger.** The USD trigger reads the LT's `exchangeRate()`, a view that reports `totalAssets / totalSupply` *without* settling the LT's accrued streaming fee — that fee is only realised when a `mint` / `redeem` / agent checkpoint runs on the LT. The view therefore sits marginally above the post-checkpoint rate, by at most the pending fee (`≈ streamingFee × leverage × time-since-last-checkpoint`; sub-cent for the actively-traded LTs supported here). The effect is benign and one-directional: a token can enter `Graduating` a touch before its settled reserve value crosses the threshold.
