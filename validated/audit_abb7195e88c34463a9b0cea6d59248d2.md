The report's Ethereum bug class is **input binding / unbounded griefing via front-running account creation**. Mapping this to NEAR core-contracts, the closest analog is not staking-pool-factory or lockup-factory (both explicitly guard against this), but `multisig-factory`, which has no such protection at all.

### Title
Unrecoverable loss of attached deposit via front-run/failed `MultisigFactory::create` (no existence check, no refund callback) - (File: `multisig-factory/src/lib.rs`)

### Summary
`MultisigFactory::create` derives the new multisig account name directly from an attacker/user-controlled `name` parameter and immediately fires a `create_account → deploy_contract → transfer(attached_deposit) → function_call("new", ...)` promise chain with **no pre-check that the target account doesn't already exist and no callback to handle promise failure**. [1](#0-0) 

### Finding Description
Sibling factory contracts in the same repo (`staking-pool-factory` and `lockup-factory`) both defend against this exact class of bug:
- `staking-pool-factory` asserts the derived account id isn't already reserved (`self.staking_pool_account_ids.insert(...)`) *before* dispatching any promise, so a name collision fails the whole transaction and the attached deposit is never spent. [2](#0-1) 
- `lockup-factory` additionally implements `on_lockup_create`, a callback that checks `is_promise_success()` and explicitly returns the attached deposit to the original caller if account creation failed. [3](#0-2) 

`multisig-factory::create` has **neither** protection: it does not check whether `{name}.{current_account_id}` already exists, and it has no `on_create`-style callback at all — the function is only 21 lines and ends immediately after building the promise chain. [4](#0-3) 

Because `create_account`, `deploy_contract`, `transfer`, and `function_call` are all chained into the *same* outgoing receipt, if the `create_account` action fails (e.g., because the account name is already taken), the entire receipt fails atomically. Per NEAR protocol semantics, the balance that was earmarked for the failed receipt's `transfer` action is refunded back to the **predecessor of that receipt** — which is the `multisig-factory` contract itself (since the promise's predecessor is the contract, not the original transaction signer) — not to the original user who called `create()` and attached the deposit. With no callback to detect the failure and manually re-transfer the funds to `env::predecessor_account_id()`, the deposit becomes permanently stuck in the factory contract's balance with no method exposed to recover or forward it.

An unprivileged attacker can trigger this deterministically by front-running: watching the mempool for a pending `create(name, members, num_confirmations)` call and submitting their own `create(name, attacker_members, ...)` with the identical `name` and a minimal deposit. Whichever transaction lands first successfully creates `name.multisig-factory`; the second one's `create_account` action fails (account already exists on-chain) and its attached NEAR deposit is lost to the factory contract with no refund path — this is strictly the same input-binding root cause as the reported Ethereum `createAccount` front-running bug (unvalidated, attacker-observable identifier reused to grief a user's in-flight transaction), but on NEAR the consequence is worse: total, unrecoverable loss of the attached deposit rather than just wasted gas.

### Impact Explanation
This matches the Critical scoped impact: "Permanent freezing, unrecoverable lock, or irrevocable loss of user or protocol funds in ... factory refund ... flows." The victim's attached NEAR deposit (which per the sibling contracts' `MIN_ATTACHED_BALANCE` conventions is expected to be tens of NEAR) is irrecoverably lost with no owner/administrative recovery function present in `MultisigFactory`. [5](#0-4) 

### Likelihood Explanation
Likelihood is realistic: the entrypoint `create` is fully public and payable, requires no privilege, and NEAR's mempool/transaction propagation delay gives an attacker a practical window to observe and front-run a pending `create` call with the same `name`, exactly mirroring the bridge-delay front-running condition described in the external report. It can also occur accidentally (two users independently choosing the same common `name`), but the attacker-driven griefing path is the qualifying scenario.

### Recommendation
Apply the same pattern already used in `staking-pool-factory`/`lockup-factory`:
1. Track created account IDs (or at minimum check `env::is_valid_account_id` and reject if already in use) before dispatching the promise chain, and/or
2. Add an `on_create` callback (`is_promise_success()`), and on failure explicitly `Promise::new(predecessor_account_id).transfer(attached_deposit)` to refund the original caller, matching `on_lockup_create`/`on_staking_pool_create`.

### Proof of Concept
1. Attacker monitors mempool for pending tx: `multisig-factory.create({name: "mypool", members: [...], num_confirmations: N})` attaching `D` NEAR from victim `V`.
2. Attacker submits `multisig-factory.create({name: "mypool", members: [attacker], num_confirmations: 1})` with minimal deposit and higher gas price/priority so it lands first.
3. Attacker's tx succeeds: `mypool.multisig-factory` is created and controlled by the attacker.
4. Victim's tx executes afterward: `create_account` on `mypool.multisig-factory` fails since the account already exists; the entire receipt (`create_account`, `deploy_contract`, `transfer(D)`, `function_call("new")`) fails atomically.
5. Because `multisig-factory::create` has no callback, `D` NEAR is refunded to the `multisig-factory` contract account itself (the receipt's predecessor), not to `V`. `V` has no way to reclaim the funds — total loss of `D`. [6](#0-5)

#[near_bindgen]
#[derive(BorshSerialize, BorshDeserialize, Default)]
pub struct MultisigFactory {}

#[near_bindgen]
impl MultisigFactory {
    #[payable]
    pub fn create(
        &mut self,
        name: AccountId,
        members: Vec<MultisigMember>,
        num_confirmations: u64,
    ) -> Promise {
        let account_id = format!("{}.{}", name, env::current_account_id());
        Promise::new(account_id)
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                json!({ "members": members, "num_confirmations": num_confirmations })
                    .to_string()
                    .as_bytes()
                    .to_vec(),
                0,
                env::prepaid_gas() - CREATE_CALL_GAS,
            )
    }
}

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(

            );
            true
        } else {

                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
