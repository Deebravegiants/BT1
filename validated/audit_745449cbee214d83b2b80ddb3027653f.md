Based on the analysis, the webhook processing flow in this gem exhibits the exact pattern the task requires: a field acted upon (the `shop` and `topic` headers) that is not covered by the HMAC signature.

### Title
Webhook `shop` and `topic` identity are not covered by HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC only over the raw JSON body [1](#0-0) , while the `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from HTTP headers that are never included in the signed content [2](#0-1) . `Registry.process` validates only that HMAC-over-body relationship, then forwards the unauthenticated `shop`/`topic` header values to the app's handler as trusted identity fields [3](#0-2) .

### Finding Description
The equality the gem is supposed to guarantee is: *the `shop` value delivered to the handler == the shop that Shopify's signature actually attests to*. Because `to_signable_string` returns only `@raw_body` [1](#0-0) , `HmacValidator.validate` verifies nothing about the `shopify-shop-domain`, `shopify-topic`, or `shopify-webhook-id` headers [4](#0-3) . Since a single app uses one shared `api_secret_key` (`Context.api_secret_key`) across all installed shops, any tenant who has their own legitimately installed shop can capture an authentic `(raw_body, hmac)` pair from a real webhook Shopify sent them, and then resend that exact body/hmac pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header (e.g., a victim shop) and/or a different `shopify-topic` header. `HmacValidator.validate` will still return `true` because the signature only covers `@raw_body`, which is unchanged. `Registry.process` will then dispatch to the topic handler and build `WebhookMetadata` using the attacker-controlled, unauthenticated `shop` field [3](#0-2) . The documented usage pattern explicitly instructs host apps to key their processing off `data.shop` as an authenticated identity to route/attribute the payload [5](#0-4) , so the gem's own contract treats `shop` as a value the caller can trust after `Registry.process` succeeds — but the code path never actually binds it to the HMAC.

### Impact Explanation
This breaks the tenant identity binding at the point the gem hands data to the application layer, enabling cross-tenant data confusion: a webhook payload can be attributed to a shop it did not originate from, which is a cross-tenant integrity violation. Since apps typically use `data.shop` to select tenant-scoped database records, sessions, or business logic, this can lead to state corruption or data leakage across tenants purely by replaying/relabeling requests to the app's public webhook endpoint — no access token or `client_secret` is required by the attacker, only their own valid webhook traffic from their own shop.

### Likelihood Explanation
Any merchant/developer who installs the app on a shop they control automatically receives genuine webhook deliveries (body + valid HMAC) for that shop, and the webhook endpoint is a public, unauthenticated HTTP endpoint by design (protected only by HMAC). Forging headers on an HTTP POST is trivial, so exploitation requires no special privilege beyond normal app installation on any store — a fully unprivileged capability from the perspective of the target app's other tenants.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, and ideally `webhook-id`) in the HMAC-signed content, or otherwise cryptographically bind them (e.g., verify `shop` against `Context`'s known session/shop store before trusting it), instead of relying solely on `to_signable_string => @raw_body`. At minimum, document that `shop`/`topic` from `WebhookMetadata` are not authenticated and must be independently verified by the host app against a known/installed shop list before being used for tenant-scoped logic.

### Proof of Concept
1. App merchant A installs the target Shopify app on `attacker.myshopify.com` and configures a webhook subscription (e.g., `orders/create`).
2. Shopify delivers a legitimate webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid_hmac_of_raw_body>`, and some `raw_body`.
3. Merchant A (or anyone with access to a proxy/logging of that request) captures this exact `raw_body` and `X-Shopify-Hmac-Sha256` value.
4. Merchant A re-sends a POST to the same webhook endpoint, keeping `raw_body` and `X-Shopify-Hmac-Sha256` unchanged, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request#hmac` decodes the unchanged header [6](#0-5) , `to_signable_string` returns the unchanged `raw_body` [1](#0-0) , so `HmacValidator.validate` succeeds using the app's single shared `api_secret_key` [4](#0-3) .
6. `Registry.process` dispatches to the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "orders/create", body: <attacker's order data>, ...)` [7](#0-6) , causing the app to process/attribute attacker-controlled data as belonging to a victim tenant it has no relationship to in this request.
