### Title
Unsafe raw `IERC20.transfer` call in Tron IntentGatewayV2 escrow withdrawal/dust-sweep silently accepts failed transfers for non-standard ERC20 tokens - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2` (a token-bridge/intent-escrow contract reachable by any user filling or cancelling a cross-chain intent) does not use `SafeERC20.safeTransfer` for releasing escrowed funds. Instead, `withdraw()` and the `SweepDust` branch of `onAccept()` perform raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and treat the transfer as successful purely based on the low-level `success` flag, without checking the ABI-decoded boolean return value.

### Finding Description
In `withdraw()`: [1](#0-0) 
tokens are released to `beneficiary` via `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))`, checking only `success` (whether the call reverted), not the returned `bool` value. The same pattern is used for fee-token payout at line 720, and for dust sweeping in the `SweepDust` handler: [2](#0-1) 

Many real-world ERC20 tokens (and especially TRC20 tokens on Tron, which are the deployment target of this exact file) do not strictly follow the standard: some return `false` on failure instead of reverting, and some don't return any data at all. A raw `.call` only reports `success = false` when the callee itself reverts; if the token's `transfer` function returns `false` (or nothing) without reverting, `success` is `true` and the contract proceeds as if the transfer succeeded — decrementing the internal `_orders[commitment][token]` escrow accounting and marking the order `_filled`/emitting `EscrowReleased`/`DustSwept` — even though the beneficiary never received the tokens. `SafeERC20.safeTransfer`, which is already used correctly elsewhere in the same codebase (e.g. `IntentsBase.sol` `_withdraw`, `WrappedHyperFungibleToken.sol`), explicitly checks that the call succeeded AND that any returned data decodes to `true` (or that no data was returned by a known non-standard token per its allowlist behavior), which the Tron file's raw pattern fails to replicate.

### Impact Explanation
For a "bad" or non-standard TRC20/ERC20 output/input token configured in the gateway, a failed transfer during escrow withdrawal or dust sweep is misreported as successful. This causes:
- Escrow accounting desync: `_orders[commitment][token]` is decremented and the order is marked filled/cancelled even though tokens remain locked in the contract, permanently freezing the beneficiary's funds (they can never re-claim, since the order is already marked `_filled`).
- Silent loss of funds for solvers/users expecting a redemption or refund that never physically arrives, while the contract's internal state believes the obligation was discharged.

This qualifies as concrete permanent freezing/loss of user funds reachable from a normal `cancelOrder`/relayed `RedeemEscrow`/`RefundEscrow`/`SweepDust` message, which any relayer can deliver once a valid Hyperbridge proof exists.

### Likelihood Explanation
Likelihood is moderate: it requires the gateway to be configured with (or a user/solver to select) a token whose `transfer` does not strictly follow the ERC20 return-value/revert convention. Given Tron's TRC20 ecosystem has several tokens with non-standard transfer implementations, and the gateway is permissionless with respect to which token addresses can be used in `order.inputs`/`order.output.assets`/`SweepDust.outputs`, this is a realistic occurrence rather than a purely theoretical one.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` (in `withdraw()` and the `SweepDust` branch of `onAccept()`) with `IERC20(token).safeTransfer(...)` using OpenZeppelin's `SafeERC20`, consistent with the rest of the codebase (`IntentsBase.sol`, `ExtrinsicIntents.sol`, `WrappedHyperFungibleToken*.sol`).

### Proof of Concept
1. Deploy (or use) a token whose `transfer(address,uint256)` returns `false` on insufficient balance/paused state instead of reverting (or returns no data on failure, decodable as falsy by strict callers but not checked here at all).
2. Configure this token as an escrowed input/output asset in an `IntentGatewayV2` order on the Tron deployment.
3. Trigger a state where the token transfer inside `withdraw()` (called via `RedeemEscrow`/`RefundEscrow` `onAccept` or same-chain `cancelOrder`) would fail (e.g., contract balance insufficient due to a prior dust-collection edge case, or the token enters a paused state).
4. Observe that `success` from the low-level `.call` is `true` (no revert), so the code proceeds to decrement `_orders[...]`, set `_filled[commitment]`, and emit `EscrowReleased`/`EscrowRefunded`, despite the beneficiary's token balance being unchanged — funds are now unrecoverable via the normal flow.
