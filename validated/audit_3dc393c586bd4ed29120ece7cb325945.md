### Title
Face Identifier's `score`/`is_valid` fraud signal is never thresholded before signup enrollment - all fraud checks are stubbed to always pass - (File: src/plans/mod.rs, src/agents/python/face_identifier/types.rs)

### Summary
`face_identifier` model output (`IsValidOutput`/`FIIsValidOutput`) carries an explicit `is_valid: Option<bool>` and `score: Option<f64>` confidence signal, and `rgb_net` predictions carry a per-bbox `score: f64` [1](#0-0) [2](#0-1) . Neither `MegaAgentTwo`'s output plumbing nor the downstream fraud-check step consumes/enforces these confidence values before a signup is treated as valid: `detect_fraud` in the master signup plan is hard-coded to always return `Ok(false)` ("FOSS: WE HAVE DELETED ALL FRAUD CHECKS"), so a low-confidence/near-random prediction can never be rejected on that basis [3](#0-2) .

### Finding Description
`MegaAgentTwo::Output` fans out `RgbNet`, `FaceIdentifier`, and the fused `FusionRgbNetFaceIdentifier { rgb_net, face_identifier }` variants purely by type, with no inspection of the numeric confidence fields carried inside those payloads [4](#0-3) . The broker's dispatcher (`handle_mega_agent_two`) likewise just routes by enum variant, forwarding the payload unchanged to plan handlers regardless of score/is_valid content [5](#0-4) .

Downstream, `biometric_pipeline::Plan::run` collects `face_identifier_fraud_checks` (type `face_identifier::FraudChecks`) into the `Pipeline` result [6](#0-5) , but the `FraudChecks` struct itself only contains an `error: Option<PyError>` field — there is no score or confidence field carried through at all in this fraud-check path [7](#0-6) . The signup plan's `detect_fraud` function, which is the sole place a `Pipeline` result could be used to reject a low-confidence signup, is stubbed out and unconditionally returns `Ok(false)` (no fraud detected) with the comment "FOSS: WE HAVE DELETED ALL FRAUD CHECKS" [3](#0-2) . A repo-wide search for any score/confidence threshold constant (`MIN_SCORE`, `SCORE_THRESHOLD`, etc.) returns no matches, confirming no enforcement exists anywhere in this codebase copy.

Because of this, an ambiguous/adversarial scene that causes RGB-Net or Face Identifier to emit a low `score`/`is_valid=false` prediction still flows through `fusion_rgb_net_face_identifier` and the biometric pipeline into `enroll_user` without any gate rejecting it based on confidence.

### Impact Explanation
This matches the described impact: an identity/fraud decision (whether to enroll/bind a user, or flag fraud) can be made on a near-random/low-confidence model output because the confidence signal is structurally discarded before reaching the enforcement point. This corresponds to a Worldcoin/Orb "liveness/fraud bypass" or "wrong-identity binding" class impact, since the fraud-check gate that should consume this signal is present as dead code (always `false`).

### Likelihood Explanation
This is unconditionally true in this repository state — it does not depend on attacker sophistication or occlusion tricks; `detect_fraud` always returns `false` regardless of any model score, and no other code path thresholds `FraudChecks`, `is_valid`, or `score`. This is highly likely to be intentional FOSS redaction (fraud checks were deliberately removed from this open-source release, as explicitly stated in the comment) rather than a bug reachable purely via unprivileged scene manipulation in the production Orb — the comment strongly suggests the real enforcement logic exists in a private/proprietary variant not present in this repo. This uncertainty should be noted: I could not confirm whether the production (non-FOSS) build re-inserts fraud/confidence checks; only the code available in this repository is assessed.

### Recommendation
Reinstate score/`is_valid`-based thresholding in `detect_fraud` (or in `biometric_pipeline::Plan::run`) that inspects `face_identifier_fraud_checks`/`face_identifier_bundle` scores and RGB-Net prediction scores, rejecting or flagging signups whose confidence falls below a defined minimum before allowing `enroll_user` to proceed.

### Proof of Concept
Unit/integration test plan:
1. Construct a `biometric_pipeline::Pipeline` with `face_identifier_fraud_checks = Ok(FraudChecks { error: None })` (i.e., no error, simulating a "successful" call) and mock a low `score`/`is_valid: Some(false)` in the associated `IsValidOutput` used elsewhere in the flow.
2. Call `Plan::detect_fraud(orb, debug_report, Some(&pipeline))` and assert it returns `true` (fraud detected) when confidence is below threshold — currently it always returns `Ok(false)`, which the test should show fails the expected invariant.
3. Add an integration test around `fusion_rgb_net_face_identifier` verifying that when `rgb_net`'s primary prediction `score` is below a defined minimum, `Output::FusionError` (or an explicit rejection variant) is produced instead of proceeding to face identifier evaluation. [8](#0-7)

impl Environment<'_> {
    fn fusion_rgb_net_face_identifier(
        &mut self,
        py: Python,
        frame: &camera::rgb::ArchivedFrame,
    ) -> Result<Output> {
        let ndframe = frame.into_ndarray();

        let rgb_net_res = self.rgb_net_env.rgb_net_estimate(py, ndframe.clone())?;
        // If RGB-Net fails to estimate the eyes coordinates and bbox, avoid running the slow Face Identifier.
        let Some(prediction) = rgb_net_res.primary() else {
            return Ok(Output::FusionError(FusionErrors::RgbNetFaceIdentifier(
                Some(rgb_net::Output::Error),
                None,
            )));
        };
        let face_identifier_res = self.face_identifier_env.is_valid(
            py,
            ndframe,
            (prediction.landmarks.left_eye, prediction.landmarks.right_eye),
            prediction.bbox.coordinates,
        )?;

        Ok(Output::FusionRgbNetFaceIdentifier {
            rgb_net: rgb_net_res,
            face_identifier: face_identifier_res,
        })
    }

    fn handle_mega_agent_two(
        &mut self,
        plan: &mut dyn Plan,
        output: port::Output<mega_agent_two::MegaAgentTwo>,
    ) -> Result<BrokerFlow> {
        let source_ts = output.source_ts;
        match output.value {
            mega_agent_two::Output::RgbNet(value) => {
                self.handle_rgb_net(plan, port::Output { value, source_ts })
            }
            mega_agent_two::Output::FaceIdentifier(value) => {
                self.handle_face_identifier(plan, port::Output { value, source_ts })
            }
            mega_agent_two::Output::FusionRgbNetFaceIdentifier { rgb_net, face_identifier } => self
                .handle_fusion_rgb_net_face_identifier(plan, source_ts, rgb_net, face_identifier),
            mega_agent_two::Output::FusionError(e) => match e {
                FusionErrors::RgbNetFaceIdentifier(rne, fie) => {
                    // In fusion agents we make the assumption that there is an order in decision making.
                    if let Some(value) = rne {
                        if let BrokerFlow::Break =
                            self.handle_rgb_net(plan, port::Output { value, source_ts })?
                        {
                            return Ok(BrokerFlow::Break);
                        }
                    }
                    if let Some(value) = fie {
                        if let BrokerFlow::Break =
                            self.handle_face_identifier(plan, port::Output { value, source_ts })?
                        {
                            return Ok(BrokerFlow::Break);
                        }
                    }
                    Ok(BrokerFlow::Continue)
                }
            },
            mega_agent_two::Output::Iris(_) | mega_agent_two::Output::Config(_) => {
                plan.handle_mega_agent_two(self, output)
            }
        }
    }
