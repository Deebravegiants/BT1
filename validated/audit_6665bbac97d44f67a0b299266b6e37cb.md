### Title
Emporium relay-fee payment bypasses balance-equation check via unsigned `feeToken`/`relay` fields, allowing a whitelisted relayer to drain arbitrary tokens from a `HinkalWallet` - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
This is the same bug class as the Safe.sol gas-refund finding: a trusted, off-chain-signed authorization omits fields that later control fund destination/amount, and an on-chain actor (here, the whitelisted relay who calls `Hinkal.transact`) can freely set those omitted fields to redirect funds to itself. In Hinkal's Emporium flow, the wallet owner's EIP-712 signature (`verifyWallet`) only commits to `emporiumMessage`, the hashed `ops`, `maxFee`, and `deadline` — it never commits to `circomData.feeStructure.feeToken` or `circomData.relay`. Worse, when the chosen `feeToken` is not one of `circomData.erc20TokenAddresses`, the fee payment happens entirely outside the balance-equation check performed in `Hinkal.transact`.

### Finding Description
`EmporiumUpgradeable.verifyWallet` recovers the signer from: [1](#0-0) 
which binds only `circomData.emporiumMessage`, `_hashEmporiumOps(stack.ops)`, `stack.maxFee`, and `stack.deadline`. The `feeStructure` (containing `feeToken`, `flatFee`, `variableRate`) and `circomData.relay` are **not** part of this signed struct.

`payRelayFees` then pays the relay directly from the `HinkalWallet` using `sendToRelayFromWallet` → `IHinkalWallet.doSendToRelay`, capped only by `flatFee <= stack.maxFee` (numeric cap, no token binding): [2](#0-1) 

Critically, the "token not found in the transacted list" branch fires when `feeStructure.feeToken` is not one of `circomData.erc20TokenAddresses`, and still pays the relay the full `flatFee` in that arbitrary token: [3](#0-2) 

The balance/equality check performed by the entrypoint only iterates over `circomData.erc20TokenAddresses` and checks `balanceDif == amountChanges[i] + utxoAmount` for each listed token: [4](#0-3) 

Since `feeToken` can be chosen to be a token that is **not** in `circomData.erc20TokenAddresses`, the transfer of up to `stack.maxFee` units of that token from the `HinkalWallet` to `circomData.relay` is never reflected in, nor constrained by, this balance equation — it happens completely "off the books" relative to the equality the protocol relies on to bound fund movement.

`circomData.relay` is likewise unconstrained by the user's signature; the only check is `relayerIsValid`, which merely requires the relay to be `tx.origin` and whitelisted — i.e., any whitelisted relayer submitting the transaction can name itself as the recipient: [5](#0-4) 

`circomData.calldataHash` does technically commit to `feeStructure` (via `getHashedCalldata2`) and to `relay` (via `getHashedCalldata1`): [6](#0-5) 
but that hash is generated by the party constructing the proof and calling `transact` — the same untrusted relay/operator — not by the wallet owner who produced the EIP-712 signature. It therefore provides no protection against a malicious relay choosing `feeToken`/`relay` itself.

### Impact Explanation
A whitelisted relay (an "operator" analogous to the SubAccount operator in the referenced report) can call `Hinkal.transact` with an Emporium `externalActionData` whose `feeStructure.feeToken` is set to any valuable ERC-20 token held by the target `HinkalWallet`, and `flatFee` set up to the user-signed `maxFee` (a numeric cap the signer approved without knowing which token it would apply to). Because that token is excluded from `circomData.erc20TokenAddresses`, the balance-equation check in `Hinkal.transact` does not see or constrain this transfer, and `payRelayFees`'s "token not found" branch unconditionally pays it to `circomData.relay`, an address the relay controls. This is theft of protocol/relay fees or user funds via unauthorized token/recipient selection — funds move that the wallet owner's signature never approved for that specific token or recipient. This matches the High-impact category "theft ... of protocol/relay fees ... executing calls or moving assets a wallet owner or prover never authorised."

### Likelihood Explanation
Likelihood is Medium: it requires the caller to be a whitelisted relay (`isRelayInList` + `tx.origin == relay`), which limits the attacker set to entities the protocol has already trusted for other purposes, and the wallet must be a stateful `HinkalWallet` with `signerAddress != address(0)` and hold a valuable token not included in the transaction's `erc20TokenAddresses` list. However, any operator on the whitelist can trigger this without needing the wallet signer's cooperation or knowledge, at any time a valid `emporiumMessage`/`ops`/`maxFee`/`deadline` signature exists.

### Recommendation
Include `feeStructure.feeToken`, `feeStructure.flatFee` (or at least an upper bound tied to a specific token), `feeStructure.variableRate`, and `circomData.relay` in the EIP-712 typed data hashed and verified in `EmporiumUpgradeable.verifyWallet` (i.e., add these fields to `EMPORIUM_SIGNATURE_TYPEHASH`), so the wallet-owner's signature explicitly authorizes the fee token and the fee recipient, not just a numeric cap. Additionally, ensure `payRelayFees`'s "not found" branch cannot pay from tokens excluded from `circomData.erc20TokenAddresses`, or fold that payment into the balance-equation check in `Hinkal.transact` so it cannot bypass the accounting invariant.

### Proof of Concept
1. Wallet owner signs an `EmporiumStack` authorizing some `ops` with `maxFee = X` (e.g., intending to pay X units of USDC as a relay fee), without any on-chain binding to a specific fee token.
2. A whitelisted relay observes this signature and constructs `circomData` for the same `emporiumMessage`/`ops`/`maxFee`/`deadline`, but sets:
   - `circomData.erc20TokenAddresses` = some unrelated small list not containing the wallet's high-value token (e.g., WBTC held in the wallet).
   - `circomData.feeStructure.feeToken` = WBTC (the wallet's high-value token).
   - `circomData.feeStructure.flatFee` = X (same numeric cap, now denominated in WBTC units instead of USDC).
   - `circomData.relay` = itself (a whitelisted relay address, satisfying `relayerIsValid`).
3. Relay calls `Hinkal.transact` with a proof it generates itself (calldataHash committing only to its own chosen values, not the user's).
4. `EmporiumUpgradeable.runAction` → `verifyWallet` passes because `maxFee`, `ops`, `deadline`, `emporiumMessage` all match the user's actual signature.
5. `payRelayFees` executes the `!foundToken` branch since WBTC isn't in `erc20TokenAddresses`, and calls `payRelay` → `sendToRelayFromWallet` → `HinkalWallet.doSendToRelay(relay, X, WBTC)`, transferring X units of WBTC from the wallet to the relay.
6. `Hinkal.transact`'s balance-equation loop only checks tokens in `circomData.erc20TokenAddresses`, so this WBTC outflow is never verified against `amountChanges`/`utxoAmount`, and the transaction succeeds despite the wallet owner never authorizing a WBTC-denominated fee to that relay.

    function payRelayFees(
        CircomData calldata circomData,
        address signerAddress,
        int256[] calldata deltaAmountChanges
    ) internal {
        FeeStructure calldata feeStructure = circomData.feeStructure;

        bool foundToken = false;

        for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            // tokens deposited into Emporium are not charged
            if (deltaAmountChanges[i] >= 0) {
                continue;
            }

            address erc20TokenAddress = circomData.erc20TokenAddresses[i];
            bool isFeeToken = erc20TokenAddress == feeStructure.feeToken;

            if (isFeeToken) {
                foundToken = true;
            }

            uint256 relayFee = 0;
            uint256 flatFee = isFeeToken ? feeStructure.flatFee : 0;

            if (signerAddress == address(0)) {
                uint256 sumAbs = uint256(-deltaAmountChanges[i]);

                EmporiumStorageVars storage $ = _getEmporiumStorage();
                relayFee = $._hinkalHelper.calculateRelayFee(
                    sumAbs,
                    flatFee,
                    feeStructure.variableRate
                );
            } else {
                relayFee = flatFee;
            }

            payRelay(
                circomData.relay,
                signerAddress,
                relayFee,
                erc20TokenAddress
            );
        }

        if (!foundToken && feeStructure.flatFee != 0) {
            require(
                signerAddress != address(0),
                "Gas Token in Emporium is not found"
            );

            payRelay(
                circomData.relay,
                signerAddress,
                feeStructure.flatFee,
                feeStructure.feeToken
            );
        }
    }
