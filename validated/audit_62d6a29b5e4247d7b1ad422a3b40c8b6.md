### Title
Webhook shop identity spoofing — `shop-domain` header not covered by HMAC verification - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then trusts the unauthenticated `shop-domain` HTTP header to attribute the webhook to a specific merchant. Because the HMAC signature never covers the header, an attacker who possesses one valid `(body, hmac)` pair — trivially obtainable by installing the app on their own store and letting Shopify deliver a real webhook — can replay that exact body/hmac pair while swapping the `shop-domain` header to an arbitrary victim shop domain, and the gem will treat the forged request as authentic and originating from the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` extracts identity/routing fields from HTTP headers: [1](#0-0) 

Critically, `to_signable_string` — the data actually covered by the HMAC — is only the raw body, never the headers: [2](#0-1) 

`Registry.process` validates only that body-derived signature and then dispatches using the unauthenticated `shop` header taken straight from the request: [3](#0-2) 

`HmacValidator.validate` computes the HMAC over `to_signable_string` (the body) and compares it against the `hmac` value read from the same request (also header-derived, but mathematically tied only to the body, not to `shop`, `topic`, or `webhook_id`): [4](#0-3) 

The identity binding that should hold is:
`shop asserted by the request == shop cryptographically bound by the HMAC`

In this code, the HMAC binds only the body bytes; the `shop` field used for downstream handler dispatch (`WebhookMetadata.new(..., shop: request.shop, ...)`) is carried by a header outside the signed scope. Any unprivileged internet user who can obtain one legitimate `(raw_body, hmac)` pair signed with the app's real `api_secret_key` — which Shopify will produce for them automatically the moment they install the public app on any store they control — can resend that identical body+hmac to the app's webhook endpoint with a forged `shopify-shop-domain` (or `x-shopify-shop-domain`) header naming a different, victim shop. `HmacValidator.validate` still returns `true` because the signature check only concerns the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the victim shop's identity while the body content is attacker-controlled.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: an attacker-controlled payload can be attributed to an arbitrary shop domain of the attacker's choosing. Depending on how the host application's webhook handlers key off `data.shop` (e.g., looking up sessions/access tokens for that shop, writing shop-scoped records, or acting on `app/uninstalled`-style topics), this enables cross-tenant data injection/corruption or triggering shop-scoped side effects against a shop the attacker does not control — a cross-tenant access impact, without needing any of the app's credentials or a privileged account.

### Likelihood Explanation
Likelihood is high: no secret, access token, or privileged account is required. The attacker only needs to install the target public app on any shop they control (free/dev store) to receive one valid webhook body/hmac pair from Shopify, then replay it to the app's public webhook endpoint with a different `shop-domain` header. The `Registry.process`/`HmacValidator` code path performs no additional binding check between the header-derived shop and the signed body.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-covered signable content, or otherwise cryptographically bind the `shop` header value to the verified payload before it is used for routing/dispatch. At minimum, `Request#to_signable_string` should incorporate `shop`, `topic`, and `webhook_id` alongside the raw body so that `HmacValidator.validate` fails if any of those header values are altered relative to what Shopify actually signed.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a shop they fully control) and triggers any registered webhook topic (e.g., `orders/create`) by creating an order — Shopify delivers a POST to the app's callback URL with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid hmac over body>`, and the JSON body.
2. Attacker captures this exact raw body and its valid `hmac` value.
3. Attacker resends an HTTP POST to the same app webhook endpoint with the identical raw body and `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (the unchanged body) and matches the unchanged `hmac` header — validation succeeds.
5. The registered handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker-controlled data>, ...)`, i.e., attacker data is processed as if it belongs to the victim shop. [3](#0-2) [5](#0-4)
