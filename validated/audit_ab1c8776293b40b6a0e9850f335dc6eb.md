### Title
Escrow decrement occurs after external transfer in `withdraw()`, allowing reentrant double-redemption of escrowed funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.withdraw()` sends escrowed native/ERC20 tokens to the beneficiary via a raw `.call` *before* decrementing the corresponding `_orders[commitment][token]` escrow balance, violating checks-effects-interactions. This mirrors the external-report bug class ("call to sender without reentrancy protection... allows the caller to reenter this and other functions"), and unlike the newer `IntentsBase._withdraw()` used by the mainline EVM `IntentGatewayV2.sol` (which decrements escrow *before* the external transfer), this Tron contract has not been ported to the fixed pattern, nor does it use any `nonReentrant` guard anywhere in the file.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` is invoked from `onAccept` (for `RedeemEscrow`/`RefundEscrow` requests) and from `onGetResponse`: [1](#0-0) 

For each token in the withdrawal body it:
1. Checks `_orders[body.commitment][token] == 0` (revert if so).
2. Performs an external transfer — either a raw native `.call{value: amount}("")` or an ERC20 `.call(transfer(...))`.
3. Only *after* that external call does it execute `_orders[body.commitment][token] -= amount;`.

The same pattern repeats for `TRANSACTION_FEES`: the fee token transfer happens, then `delete _orders[body.commitment][TRANSACTION_FEES]` follows: [2](#0-1) 

Because the escrow balance is not zeroed/decremented until after the external call returns, a beneficiary that is a smart contract (for native-token payouts) or a malicious/callback-capable ERC20 token can re-enter during that external call. The contract has no `nonReentrant` modifier anywhere (`grep` for `nonReentrant`/`ReentrancyGuard` in this file returns no hits), and `withdraw()`/`onAccept()`/`onGetResponse()` carry no reentrancy protection of their own.

This is the same root-cause class flagged in the external Sherlock report against DODO's `_routeWithdraw()`: an external call to a caller-controlled address made before internal accounting is finalized, with no reentrancy guard on the function or its call graph.

By contrast, the currently-shipped EVM implementation (`IntentsBase._withdraw`) already applies the fix — escrow is decremented *before* the token transfer: [3](#0-2) 

and the corresponding fill-side CEI fix and dedicated regression tests exist for `IntrinsicIntents._fillSameChain`: [4](#0-3) 

The Tron contract, however, still contains the vulnerable ordering, and it is a separately deployed/maintained copy of the intent gateway (not inheriting from `IntentsBase`/`ReentrancyGuardTransient`).

### Impact Explanation
If a relayer delivers a `RedeemEscrow`/`RefundEscrow` post request naming a malicious contract as beneficiary (or naming a malicious/ERC777-like token in `body.tokens`), that beneficiary/token can re-enter `withdraw()` (via a second, distinct but already-authenticated incoming request processed in the same nested call, or via a token callback) before `_orders[commitment][token]` is decremented. Since the check `_orders[body.commitment][token] == 0` still reads the pre-decrement (nonzero) value, the same escrow can be paid out multiple times, draining the escrow account for that commitment/token and permanently under-collateralizing legitimate future settlements — a direct theft of escrowed user/solver funds. This is Medium/High severity theft-of-funds impact within the scope of "token bridge mint/burn... intents escrow" flows called out as in-scope.

### Likelihood Explanation
Exploitation requires either: (a) an ERC20 token registered for use in an intent order that has transfer-hook/callback behavior (e.g. ERC777-style tokens or a token deliberately crafted by an attacker who also controls order creation), or (b) a native-token beneficiary contract capable of reentering the gateway/host during the `.call{value:}` and the surrounding relayer/host call path permitting a nested `onAccept`/`onGetResponse` invocation before the first one completes. Given `withdraw()` is only reachable through `onAccept`/`onGetResponse` (gated by `onlyHost`/authentication of the source gateway), the practical trigger is a single relayed message whose beneficiary is attacker-controlled, combined with a callback path back into another already-provable request. Because there's no reentrancy guard at all on this file, likelihood is elevated relative to a codebase where such guards are the norm (as seen in the sibling EVM contract).

### Recommendation
Port the CEI fix already present in `IntentsBase._withdraw()` to `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `withdraw()`: decrement `_orders[body.commitment][token]` (and delete the `TRANSACTION_FEES` entry) *before* performing the external `.call`/`transfer`. Additionally, add a reentrancy guard (e.g. `ReentrancyGuardTransient` or a standard `nonReentrant` modifier) to `onAccept` and `onGetResponse`, consistent with the guards already applied to `placeOrder`/`fillOrder`/`cancelOrder` in the mainline EVM gateway.

### Proof of Concept
1. Attacker crafts (or controls) an order whose output/escrow token is address(0) (native) and whose beneficiary is a malicious contract `M`.
2. Attacker arranges for a valid `RedeemEscrow`/`RefundEscrow` PostRequest naming `M` as beneficiary to be delivered via `onAccept`.
3. Inside `withdraw()`, the native transfer `(bool sent,) = beneficiary.call{value: amount}("")` invokes `M`'s `receive()`.
4. `M`'s `receive()` triggers a second, independently-provable request (already accumulated/authenticated by Hyperbridge) targeting the same commitment/token, causing a nested `onAccept` → `withdraw()` call.
5. Because `_orders[body.commitment][token]` has not yet been decremented from step 3's iteration, the nested call's `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` check passes, and a second payout of `amount` is sent to `M` before either call finishes decrementing state — resulting in double payout from a single escrowed balance.

(Note: step 4's exact re-entry vector — whether via a second batched proof, or via the destination-chain host's message-delivery loop permitting nested calls — could not be fully verified without deeper inspection of the Tron `HyperApp`/host delivery code, which was not fully covered in the retrieved index. The core, verified root cause is the CEI violation in `withdraw()`'s external-call-before-state-update ordering, absent in the fixed `IntentsBase._withdraw()` used elsewhere in the same repo.)
