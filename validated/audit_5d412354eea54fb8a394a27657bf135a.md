### Title
Webhook `shop` identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the shop identity (`shop`), topic, webhook id and API version straight from unauthenticated HTTP headers, while the HMAC signature that `Utils::HmacValidator` checks is computed only over the raw request body. The signature therefore never binds the `shop` value that `Registry.process` hands to the application's webhook handler, breaking the equality "shop authenticated == shop the handler trusts as the tenant identity."

### Finding Description
`Registry.process` verifies the request and then dispatches to the handler using `request.shop` as the tenant identifier: [1](#0-0) 

The HMAC check delegates to `HmacValidator.validate`, which computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — none of the HTTP headers are included in the signed material: [3](#0-2) 

But `shop`, `topic`, `webhook_id`, and `api_version` — the values that get passed to the app's handler as the trusted tenant/context — are all read directly from headers, none of which are part of the HMAC-covered bytes: [4](#0-3) 

The initializer only checks that the headers are *present*, not that they are consistent with anything cryptographically verified: [5](#0-4) 

So `HmacValidator.validate(request)` returning `true` only proves "this raw body was HMAC-signed with the app's secret at some point" — it proves nothing about which shop, topic, or webhook the body was originally associated with. `Registry.process` nonetheless forwards `request.shop` to `WebhookMetadata` as if it were verified: [6](#0-5) 

This is the same class of defect as the reported Solidity bug: the report described accounting logic that only covers part of `assets` (leaving a remainder unaccounted for and thus mishandled); here, the verification logic only covers part of the request (the body) and leaves the `shop-domain` header — the field the handler actually trusts as tenant identity — completely outside of what's verified.

### Impact Explanation
An attacker who has ever received a legitimate, correctly-HMAC'd webhook body (e.g. for their own shop, or by intercepting one) can resend that exact body to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain. `HmacValidator.validate` still returns `true` because it never inspected the header, and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain. If the host application uses this `shop` value to look up or act on a per-tenant session (as the gem's own documentation instructs, i.e. "at any point that you have a session for a shop..."), this results in cross-tenant data confusion/spoofing — the app believes data or an event legitimately belongs to a shop it does not.

### Likelihood Explanation
Exploitation requires only network access to the app's public webhook endpoint plus one previously observed valid (body, hmac) pair — no access token, `client_secret`, or privileged account is needed, since the header is never authenticated. Any app that trusts `WebhookMetadata#shop` (the documented, expected pattern) for tenant-scoped logic is affected without any misuse of the gem's documented API.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the signable string used for HMAC verification, or otherwise cryptographically bind `shop` to the verified body before it is handed to `Registry.process`'s handler dispatch, so that a verified HMAC guarantees both the payload and the shop identity are authentic together.

### Proof of Concept
1. Attacker's own shop (or an intercepted request) produces a webhook POST with body `B` and a valid `X-Shopify-Hmac-Sha256` header computed by Shopify over `B` with the app's secret, plus `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical body `B` and identical HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present) — see `lib/shopify_api/webhooks/request.rb:45-63`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (= `B` only) and it matches, since the header change did not alter `B` — `lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-31`.
5. `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` is invoked with `shop == "victim-shop.myshopify.com"` even though that shop never sent this webhook — `lib/shopify_api/webhooks/registry.rb:188-199`.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
