### Title
`configure()` allows the underlying/host asset to be repointed after funds are already escrowed, breaking custody accounting - ([File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol])

### Summary
`WrappedHyperFungibleToken` (and its upgradeable variant) locks non-native/underlying ERC20 tokens in the contract on `send()` and unlocks them on `onAccept()`. The `_underlying` token address is set via `configure()`, which — unlike `_host` — has **no set-once guard**: the owner can call `configure()` again at any time and repoint `_underlying` (and `_dispatcher`/`_isWeth`) after users have already locked balances of the *old* underlying token in the contract.

### Finding Description
`configure()` in `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol` (lines ~178-185) is:

```solidity
function configure(WrappedConfigOptions calldata options) external onlyOwner {
    if (_host == address(0)) {
        _host = options.host;
    }
    _dispatcher = options.dispatcher;
    _underlying = options.underlying;
    _isWeth = options.isWeth;
}
``` [1](#0-0) 

Only `_host` is guarded by a "set once" check (`if (_host == address(0))`); `_underlying` is unconditionally overwritten on every call, and the interface explicitly documents `configure` as re-callable rather than one-shot for these fields:

```solidity
/// @notice Configures the host, dispatcher, and underlying token, and WETH flag (host is set-once)
function configure(WrappedConfigOptions calldata options) external;
``` [2](#0-1) 

This is the same class of bug as the referenced report: a single mutable reference to a custody-bearing asset that other logic (mint/burn/lock/unlock accounting, and `ERC20` balance semantics via `isWeth`) assumes is fixed. Concretely:
- The contract's ERC20 wrapper balance represents claims on `_underlying` tokens held in the contract at the time of lock (`send()` transfers `_underlying` into escrow, mints/burns the wrapper representation).
- The `onAccept()` unlock path (mint on receive / refund on timeout) operates against whichever `_underlying` is currently configured, using `SafeERC20`/native transfers gated by `_isWeth`.
- If the owner repoints `_underlying` to a different token after users have already locked the old token, all subsequent unlocks/refunds/transfers act on the *new* token address, while the actual custodied balance of the old token remains stranded in the contract with no code path referencing it anymore.
- Toggling `_isWeth` compounds this: WETH-specific refund logic (unwrap-and-send-native vs plain `IERC20.transfer`) would apply to a token it was never validated against.

### Impact Explanation
Once the underlying is repointed, funds locked in the contract under the previous underlying token become permanently unreachable through the contract's normal unlock/refund/timeout logic (no getter/withdraw path references the stale token), which is a permanent freezing of user funds. Simultaneously, `onAccept`/timeout paths will attempt token transfers against the *new* `_underlying`, which the contract may not actually hold, causing reverts (denial of service for legitimate deliveries) or, if the contract happens to hold balance of the new token for unrelated reasons, an unbacked/mismatched transfer relative to what was actually escrowed for that wrapped balance. This satisfies "permanent freezing of funds" and "unsound state commitment between minted/burned representation and escrowed asset."

### Likelihood Explanation
This requires the contract owner (an `onlyOwner`-gated action) to call `configure()` a second time with a different `underlying`/`isWeth`, which is a privileged action — however per the analog-selection rules this is scoped to reachability via privileged reconfiguration rather than an attacker, and the bug class itself (mutable reference to a custody token with no re-init guard, unlike the sibling `_host` field which *is* guarded) is a genuine design gap that mirrors the reported `setRedeemable` issue: nothing prevents accidental or malicious reconfiguration mid-operation, and there is no sweep/drain-check comparable to `EvmHost.updateHostParams`'s `CannotChangeFeeToken` balance check that exists elsewhere in this same codebase for the fee token. The presence of that exact safeguard on `EvmHost` for an analogous mutable-asset-reference elsewhere in the repo underscores that its absence here is an inconsistency/oversight rather than an accepted trust assumption.

### Recommendation
Apply the same "set-once, or drain-before-change" pattern used for `EvmHost.feeToken` (`CannotChangeFeeToken` check) to `_underlying` in `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable`: either make `_underlying` immutable after first configuration (like `_host`), or require the contract's balance of the current `_underlying` to be zero before allowing `configure()` to change it, and likewise guard `_isWeth` since it changes how refunds are executed against `_underlying`.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken`, call `configure({host, dispatcher, underlying: TokenA, isWeth: false})`.
2. User calls `send()`, locking `TokenA` in the contract and minting wrapper balance.
3. Owner calls `configure({host, dispatcher: dispatcher, underlying: TokenB, isWeth: false})` — succeeds because `_underlying` has no set-once guard. [1](#0-0) 
4. A subsequent timeout/refund or destination `onAccept` for the user's earlier transfer now operates against `TokenB`, which the contract never received for that transfer; `TokenA` held in escrow is now unreferenced by any code path, permanently stuck.
