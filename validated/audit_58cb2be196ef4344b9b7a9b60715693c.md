### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, allowing cross-tenant attribution of webhook payloads - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `api_version`, and `webhook_id` are all read from separate, unsigned HTTP headers. `Registry.process` verifies only that the body's HMAC is valid, then unconditionally trusts `request.shop` (derived from the `X-Shopify-Shop-Domain` header) as the tenant to which the payload belongs.

### Finding Description
The binding the library needs to hold is: `shop authenticated by HMAC == shop attributed to the payload`. `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the `hmac` header [4](#0-3) . For `Webhooks::Request`, `to_signable_string` is exactly `@raw_body`, and none of `shop-domain`, `topic`, `api-version`, or `webhook-id` headers are part of that signed string [5](#0-4) . `Registry.process` uses `request.topic` to select a handler and passes `request.shop` into `WebhookMetadata` for the handler to act on, without any secondary verification that this header matches the shop that actually produced the signed body [6](#0-5) . Consequently, a valid `(body, hmac)` pair genuinely produced by Shopify for one shop can be replayed to the app's webhook endpoint with a substituted `shop-domain` header, and it will pass HMAC validation and be attributed to a different (target) shop.

### Impact Explanation
This breaks the tenant-binding guarantee the HMAC check is supposed to provide: the entity that receives/acts on the webhook (the "shop" recorded in `WebhookMetadata`) is not the entity that the HMAC actually authenticates (the body producer). App handlers built on this gem key their persistence/business logic by `data.shop`, so a replayed payload with a forged shop header causes the app to process/store data under the wrong tenant — a cross-tenant integrity issue reachable by any actor able to capture one legitimate webhook delivery for their own store (which requires no privileged credentials, `api_secret_key`, or access token) and resend it to the app's public webhook endpoint with a modified header.

### Likelihood Explanation
Moderate: exploitation requires the attacker to have captured a legitimate webhook body+HMAC pair (e.g., from their own installed shop) and to be able to reach the app's public webhook endpoint, both of which are attainable by an ordinary unprivileged merchant/developer without needing the app's `client_secret` or an access token. No interception of Shopify-to-app traffic or credential theft is required.

### Recommendation
Include `shop` (and ideally `topic`/`api_version`/`webhook_id`) in the signed material verified for webhooks, or otherwise cryptographically bind the shop header to the signed body (e.g., verify the header-derived shop against a value embedded in/derivable from the signed payload) before trusting `request.shop` in `Registry.process`.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; capture a real webhook delivery Shopify sends to the app's endpoint (raw body `B`, valid `X-Shopify-Hmac-Sha256: H` computed over `B` with the app's secret, and header `X-Shopify-Shop-Domain: attacker.myshopify.com`).
2. Replay the exact same request to the app's webhook endpoint, only changing `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
3. `HmacValidator.validate(request)` succeeds because it only checks `B` against `H` (`to_signable_string` returns only `@raw_body`) [5](#0-4) .
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker's parsed body>, ...)`, causing attacker-controlled data to be processed/stored under the victim shop's identity [7](#0-6) .
