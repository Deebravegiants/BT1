### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable content as only the raw HTTP body [1](#0-0) , while the `shop` (tenant identity), `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` handed to the host application's handler, without re-checking that the shop is consistent with anything cryptographically bound to the request [3](#0-2) .

### Finding Description
The identity binding that should hold is:
`hmac == HMAC(api_secret_key, body)` **and** `shop header == the shop that produced this body`.

In this gem only the first half is checked. `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received HMAC [4](#0-3) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are excluded from the signed material — they are parsed straight out of `@headers` with no cryptographic tie to the body or to the HMAC secret [5](#0-4) .

Since `Context.api_secret_key` is a single shared secret across every shop that installs the app (not shop-specific), any merchant who has installed the app can obtain a genuine, validly-signed webhook body for one of their own events (HMAC computed over that body with the app's shared secret). Because the shop identity is carried out-of-band in an unsigned header, that same merchant can resend the identical body to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a different (victim) shop's domain. `HmacValidator.validate` will still pass, because the signable string (body only) is unchanged, and `Registry.process` will hand the handler a `WebhookMetadata` claiming `shop: <victim-shop>` [6](#0-5) . The host application, trusting that "HMAC validated" implies the whole request (including the shop attribution) is authentic, will process attacker-controlled data under the wrong tenant.

### Impact Explanation
This breaks the tenant identity binding for webhook processing: the `shop` value the gem hands to application code as the source-of-truth for "which merchant this event belongs to" is not covered by the only integrity check the gem performs. An attacker (any unprivileged merchant who has installed the app — no special access needed) can inject attacker-chosen webhook bodies under an arbitrary victim shop's identity, since only the body needs to have a valid HMAC and the tenant-binding header is unchecked. This is a cross-tenant access primitive: host applications commonly use the `shop` from `WebhookMetadata` to look up/update per-tenant records (subscriptions, order state, GDPR data, inventory, billing), so forged shop attribution can lead to cross-tenant data corruption/injection.

### Likelihood Explanation
Any developer/merchant who can install the app (a normal, unprivileged action) can obtain arbitrarily many genuinely-signed webhook bodies for their own shop and then freely edit the `shopify-shop-domain` (or `x-shopify-shop-domain`) header before replaying the request to the app's public webhook endpoint. No secret material, TLS interception, or privileged access is required — only knowledge that the gem's webhook processing never binds the shop header into the signed content.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) in the value that is HMAC-verified, or otherwise cryptographically/contextually bind the shop header to the signed body before trusting it — e.g., have `Webhooks::Request#to_signable_string` incorporate the shop domain (or verify the shop domain against a known-registered value for the delivered webhook subscription) rather than relying solely on `@raw_body`.

### Proof of Concept
1. App merchant "attacker.myshopify.com" installs the app and triggers a webhook (e.g., `orders/create`), receiving from Shopify a POST with a valid `x-shopify-hmac-sha256` computed by Shopify with the app's shared `client_secret` over the raw body, and header `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker captures this request, keeps the body and the HMAC header untouched, but changes `x-shopify-shop-domain` to `victim.myshopify.com`, and resends it directly to the app's public webhook endpoint (bypassing Shopify).
3. The gem builds `ShopifyAPI::Webhooks::Request` from these headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, raw_body)` — matches, because body is unmodified [7](#0-6) .
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ...)` [6](#0-5) , causing the host app to process attacker-supplied data as if it originated from `victim.myshopify.com`.
