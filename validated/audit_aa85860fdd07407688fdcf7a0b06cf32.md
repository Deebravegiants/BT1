## Title
`IntentGatewayV2`/`IntentsBase`: `_sweepDust` can drain tokens still escrowed for unfilled orders, causing `_withdraw` to permanently revert - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._sweepDust` (reached via `RequestKind.SweepDust` in `IntentGatewayV2.onAccept`) transfers arbitrary amounts of any token out of the gateway contract to a beneficiary with no on-chain check that the swept amount is actually surplus/dust rather than tokens still reserved for outstanding orders in the `_orders` escrow mapping. This is the same root-cause pattern as the referenced `MuteAmplifier.rescueTokens` finding: a token-recovery/sweep path that protects nothing on-chain against balances the contract owes elsewhere, unlike other functions in the same contract (`_withdraw`) that do track reserved amounts per commitment.

### Finding Description
`IntentsBase` escrows input tokens and Hyperbridge relayer fees per order commitment in `_orders[commitment][token]`, decrementing them only when `_withdraw` releases funds to a solver or refunds a user [1](#0-0) . Accumulated protocol dust (fee deductions, surplus splits, calldata-execution residuals) is tracked only via the `DustCollected` event, not via any on-chain running total [2](#0-1) .

`_sweepDust`, dispatched by Hyperbridge governance through `RequestKind.SweepDust`, transfers whatever `amount` is specified in the request body for any token, with the only bound being the caller-supplied `req.outputs` array — there is no check against `_orders` escrow, no per-token "free balance" computation, and no comparison against a running dust total:

```solidity
function _sweepDust(SweepDust memory req) internal {
    for (uint256 i; i < outputsLen;) {
        ...
        if (token == address(0)) {
            _sendValue(req.beneficiary, amount);
        } else {
            IERC20(token).safeTransfer(req.beneficiary, amount);
        }
        ...
    }
}
``` [3](#0-2) 

The equivalent path on the Tron variant is identical: `SweepDust` iterates `req.outputs` and force-transfers, with no escrow check [4](#0-3) .

Contrast this with `_withdraw`, which *does* enforce the invariant that a token cannot be released beyond what is escrowed for that specific commitment (`escrowed == 0` reverts with `UnknownOrder`, and the mapping is decremented before transfer) [5](#0-4) . `_sweepDust` has no analogous guard: it can transfer out tokens that are simultaneously recorded as escrowed for a live, unfilled order in `_orders`.

Because "dust" computation is entirely off-chain (governance decides the `amount` to sweep based on its own accounting of `DustCollected` events), any discrepancy — a miscalculation, a race between an order being placed/filled and a sweep being dispatched, or simply governance rounding up — can cause the contract's real token balance to fall below what `_orders` still promises to a solver or user.

### Impact Explanation
When a legitimate solver later calls `fillOrder`/cross-chain redemption and `_withdraw` attempts `IERC20(token).safeTransfer(beneficiary, amount)` for that token [6](#0-5) , the transfer reverts due to insufficient balance because governance already swept the tokens out as "dust." Since `_orders[commitment][token]` is only decremented on successful transfer, the order becomes permanently unfillable and unrefundable through the normal code path — a permanent freeze of escrowed user/solver funds. The same applies to the `TRANSACTION_FEES` bucket that pays relayer fees to the beneficiary on finalize [7](#0-6) .

### Likelihood Explanation
This does not require assuming a malicious governance actor — the same operational-error class that was demonstrated (and confirmed) against `MuteAmplifier.rescueTokens`. Any error in computing "dust" off-chain, or any sweep dispatched while orders are in flight for the same token, triggers the freeze. Because dust accounting is entirely event-based/off-chain with no on-chain reserved-balance invariant, this is a systemic design gap rather than a one-off edge case, mirroring exactly why the referenced report was rated Medium and confirmed.

### Recommendation
Track protocol dust with an on-chain running total per token (incremented wherever `DustCollected` is emitted) and constrain `_sweepDust` to `amount <= dustTotal[token]`, decrementing it on sweep — analogous to how `MuteAmplifier`'s fix requires rescue amounts to respect `totalFees0/1` minus already-claimed amounts. Alternatively/additionally, bound the sweepable amount for any given token by `balanceOf(this) - sum(_orders[*][token])` is impractical on-chain without an aggregate; the safer fix is the maintained running dust counter.

### Proof of Concept
1. User places an order on the source chain; `input` tokens (token `T`) and relayer fees are escrowed in `_orders[commitment][T]` / `_orders[commitment][TRANSACTION_FEES]`.
2. Governance computes (off-chain, from `DustCollected` events) that `X` amount of `T` is sweepable dust and dispatches `RequestKind.SweepDust` with `outputs = [{token: T, amount: X}]`, where `X` is miscalculated (or a race occurs) such that `X` exceeds the contract's actual free balance of `T`, cutting into the amount reserved for the still-open order.
3. `onAccept` routes to `_sweepDust`, which unconditionally calls `IERC20(T).safeTransfer(beneficiary, X)` [3](#0-2) , succeeding because there's no check against `_orders`.
4. When the solver or user later triggers `_withdraw` for the original order's commitment, `IERC20(T).safeTransfer(beneficiary, amount)` reverts because the contract's `T` balance is now less than `_orders[commitment][T]` [6](#0-5) , permanently freezing the escrowed funds for that order.
