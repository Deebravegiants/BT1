## Finding

### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity via HMAC, but the signable content used for that verification is only the raw request body. The `shop` value used to identify which tenant the webhook belongs to is taken from an HTTP header that is never included in the HMAC computation, so it can be swapped without invalidating the signature.

### Finding Description
`Request#hmac` reads the signature from the `hmac-sha256` header, and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

Separately, `Request#shop` is derived from the `shop-domain` header, which is not part of the signed bytes at all: [3](#0-2) 

`Utils::HmacValidator.validate` (the same validator used by OAuth) only checks `verifiable_query.to_signable_string` against the HMAC: [4](#0-3) 

This is the same class of bug as the reported analog: an identity-bearing field (`toTokenId`/`shop`) is acted upon by downstream logic, but the value that is cryptographically verified (`checkpoints[toTokenId]` write / HMAC over `raw_body`) does not actually bind to that field. Here, the binding that should hold is:

`shop used for tenant dispatch == shop the HMAC-signed body was actually generated for`

but the gem never enforces this equality — `shop` is read straight from an attacker-visible, unsigned header, while the HMAC only proves "this body byte-string was signed with the app's secret," not "this body belongs to shop X."

### Impact Explanation
Any shop that installs the app receives Shopify-generated, validly-signed webhooks for its own store. Because the `shop-domain` header is excluded from the signable string, an unprivileged user who has installed the app on their own (e.g., free/dev) store can capture a validly-HMAC'd webhook payload from Shopify and replay it to the app's webhook endpoint while altering only the `shop-domain` header to point at a victim shop. `Request` will still validate successfully (`HmacValidator.validate` returns true), and `request.shop` will report the attacker-chosen victim domain to the host application/registry dispatch, since nothing in this gem cross-checks `shop` against the signed body. If a host app uses `request.shop` as the tenant/session key when handling verified webhooks (the intended and documented use, per `Webhooks::Registry` dispatch), this results in cross-tenant confusion: an attacker can inject syntactically-valid, "verified" webhook events under another merchant's identity. This satisfies the Critical/High bar of cross-tenant access, without requiring `api_secret_key`, an access token, or any privileged credential — only that the attacker installs the app on a shop they control.

### Likelihood Explanation
Requires no secrets, tokens, or privileged access — an attacker only needs to install the target app on any shop (including a free development store) to receive genuine, Shopify-signed webhook payloads, then replay one with a rewritten `shop-domain` header. The exploit path is entirely within the gem's own verification logic (`Request#hmac`/`to_signable_string`/`shop` and `HmacValidator.validate`), not dependent on the host app ignoring documented behavior.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC-verified content, or otherwise require the caller to supply the expected shop domain (e.g., from an authenticated session already associated with that webhook subscription) and reject the request if it doesn't match `request.shop`. At minimum, document clearly that `request.shop` is unauthenticated and must not be trusted as a tenant identifier on its own.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled shop `attacker.myshopify.com`.
2. Trigger any subscribed webhook event on that shop; Shopify delivers a POST with a valid `X-Shopify-Hmac-Sha256` header computed over the JSON body using the app's `client_secret`.
3. Replay the exact same body/HMAC header to the app's webhook endpoint, but change the `X-Shopify-Shop-Domain` header to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `HmacValidator.validate(auth_query)` succeeds because `to_signable_string` never included the shop header [2](#0-1) , and `request.shop` now returns `victim.myshopify.com` [3](#0-2) , causing the host app to process an attacker-controlled event as if it belonged to the victim tenant.

Note: I was unable to fully inspect `lib/shopify_api/webhooks/registry.rb` and `webhook_handler.rb` before the tool budget ran out, so I could not confirm the exact call signature by which `request.shop` is passed to registered handlers. This is a limitation on confirming the full downstream sink, though the root-cause gap (unsigned `shop` header) in `lib/shopify_api/webhooks/request.rb` is directly verified from source.
