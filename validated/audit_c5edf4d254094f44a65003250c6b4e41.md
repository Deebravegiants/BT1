### Title
Withdrawal status/tx-hash misattribution when multiple POA withdrawals of the same asset are batched in one NEAR transaction - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` and the lower-level `waitForWithdrawalCompletion` helper in `internal-utils` both resolve a withdrawal's on-chain destination transaction hash by matching PoA Bridge API results **only on `assetId`** (i.e. `nep141:{near_token_id}`), never on `amount`, `destinationAddress`, or the ordinal index of the withdrawal within the NEAR transaction. If a single NEAR transaction contains two or more withdrawal intents for the same token (e.g., two different `ft_withdraw` legs to two different recipients, or two different amounts), the first matching entry returned by the PoA API is used for every caller polling that transaction/asset pair, regardless of which specific withdrawal (recipient/amount) the caller actually created.

### Finding Description
`findMatchingWithdrawal` is duplicated in two places with identical logic and an explicit comment acknowledging the limitation: [1](#0-0) [2](#0-1) 

`describeWithdrawal` calls this matcher using only `args.withdrawalParams.assetId`, discarding `amount`, `destinationAddress`, and `index`: [3](#0-2) 

The `WithdrawalIdentifier` type carries `index` and the full `withdrawalParams` (including `amount` and `destinationAddress`), but `describeWithdrawal`/`findMatchingWithdrawal` never uses them to disambiguate between multiple withdrawals of the same asset: [4](#0-3) 

`watchWithdrawal` in `withdrawal-watcher.ts` polls `describeWithdrawal` and treats whatever `txHash`/`status` comes back as authoritative truth for that specific withdrawal: [5](#0-4) 

The existing test `"matches withdrawal by assetId, not by index"` only proves disambiguation across *different* assets; it does not cover — and the code does not handle — two withdrawals of the *same* asset in the same NEAR tx, which the code comment explicitly flags as unsupported: [6](#0-5) 

Because the match is keyed solely on `nep141:{near_token_id} === assetId`, `Array.prototype.find` returns the **first** entry in an unsorted API response whenever ≥2 withdrawals share the asset — independent of which `destinationAddress`/`amount` the caller is actually tracking.

### Impact Explanation
An integrator/relayer that batches multiple same-asset withdrawals into one NEAR transaction (e.g., processing two user withdrawal requests together) and then polls per-withdrawal status via `watchWithdrawal`/`describeWithdrawal` can receive the **destination `txHash` and completion status belonging to a different withdrawal** (wrong recipient/amount) as if it were the tracked one. This is a status/hash misreport: an integrator that credits or marks a specific user's withdrawal as fulfilled based on this reported `txHash` could incorrectly confirm delivery for the wrong withdrawal, or confirm the wrong withdrawal as "completed" while the actually-requested one is still pending/failed — matching the "status or hash misreport making an integrator credit or refund twice" High-impact class.

### Likelihood Explanation
This requires the integrating application to submit multiple withdrawals of the same token within a single NEAR transaction (a supported and plausible batching pattern given `IntentPrimitive[]` returned by `createWithdrawalIntents` can be combined), and for the PoA API to return multiple matching entries in an order that doesn't correspond to submission order — a scenario the code's own comments admit is unhandled. It does not require any malicious actor; it's a correctness gap in an in-scope, unprivileged code path (`PoaBridge.describeWithdrawal`).

### Recommendation
Disambiguate `findMatchingWithdrawal` using more than `assetId` — incorporate `destinationAddress`, `amount`, and/or a stable ordering (e.g., sort both local withdrawal params and API results by `amount` as the existing comment suggests, or require the PoA API to return an index/nonce) before this pattern is exercised in production with batched same-asset withdrawals. At minimum, throw/flag when more than one candidate withdrawal matches the same `assetId` for a given `tx.hash` rather than silently returning `withdrawals.find(...)`'s first match.

### Proof of Concept
1. Caller creates two withdrawal intents for the same asset (`nep141:btc.omft.near`) with different `destinationAddress`/`amount` in one NEAR transaction, and calls `createWithdrawalIdentifier` for each (`index: 0` and `index: 1`).
2. PoA Bridge API's `getWithdrawalStatus` returns both entries for `tx_hash`, unsorted, both with `near_token_id: "btc.omft.near"`.
3. Both callers invoke `describeWithdrawal` with the same `tx.hash` and `assetId`; `findMatchingWithdrawal` (`poa-bridge.ts:418-427`) returns the same first array entry for both, so both `watchWithdrawal` callers converge on identical `{status:"completed", txHash: <same address/amount>}` even though their `withdrawalParams.destinationAddress`/`amount` differ from that entry. /**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
