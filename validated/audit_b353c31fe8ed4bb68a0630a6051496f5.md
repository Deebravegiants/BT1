### Title
Webhook HMAC does not bind the `shop` (or `topic`/`webhook-id`) header, enabling cross-tenant webhook forgery via replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its verifiable signature only over the raw HTTP body, while the shop domain, topic, and webhook id used for routing and dispatch are taken from unauthenticated headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then trusts those headers as-is, so a valid `(raw_body, hmac)` pair legitimately delivered to one shop can be replayed with a different `shopify-shop-domain` header to make the app process the payload as if it came from a different tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#hmac` is derived purely from the `hmac-sha256` header: [1](#0-0) 

`Utils::HmacValidator.validate` verifies `verifiable_query.hmac` against `HMAC(secret, to_signable_string)`, i.e. against the raw body only: [2](#0-1) 

`Registry.process` performs the HMAC check and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` — all of which come straight from HTTP headers that are not part of the signed content — to route and label the payload: [3](#0-2) 

The identity binding that should hold is: `shop` value cryptographically bound to the payload == `shop` value the handler acts on. Here that equality does not hold — the HMAC only proves "this body/hmac pair was produced by Shopify using the app's secret for *some* delivery," not "this body belongs to shop X." Any header claiming a different shop is accepted unchanged because it is outside the signed scope.

### Impact Explanation
An unprivileged attacker who legitimately runs (or installs the app on) their own shop, Shop A, will receive real webhook deliveries from Shopify for Shop A, each with a valid `(raw_body, hmac)` pair signed with the app's `client_secret`. The attacker can capture such a delivery and replay the identical `raw_body` and `hmac-sha256` header to the app's webhook endpoint while substituting the `shopify-shop-domain` header (and/or `webhook-id`/`api-version`) to point at Shop B. Since `HmacValidator.validate` only re-derives the HMAC from the raw body, the replayed request still passes validation, and `Registry.process` dispatches `WebhookMetadata` labelled with the attacker-chosen `shop` to the app's handler. This constitutes cross-tenant access/confusion: the app processes and stores data (order/customer/app-uninstall payloads, etc.) as belonging to a shop that never actually sent it, without needing the victim's credentials, access token, or the app's `client_secret`.

### Likelihood Explanation
The only prerequisite is that the attacker's own shop has the app installed (an ordinary, unprivileged merchant action) so they can receive at least one real webhook and capture its raw body/HMAC header pair. No secret material, token theft, or privileged access is required to mount the replay against the app's public webhook endpoint.

### Recommendation
Bind the identity fields used for routing/dispatch to the signed material: include `shop`, `topic`, and `webhook_id` in the HMAC-signed payload validation (e.g., verify them against fields present inside the signed JSON body, or require the app to independently confirm the destination shop against its own session store before acting), rather than trusting the corresponding HTTP headers unconditionally in `Registry.process`.

### Proof of Concept
1. Install the app on attacker-controlled Shop A; capture a legitimate webhook POST that Shopify delivers, e.g. headers `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: <validHmac>`, and raw body `B`.
2. Replay the exact same raw body `B` and `x-shopify-hmac-sha256: <validHmac>` to the app's webhook endpoint, but change `x-shopify-shop-domain` to `shop-b.myshopify.com` (a shop the attacker does not control).
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (only presence is checked), `Utils::HmacValidator.validate` succeeds because the HMAC still matches the unmodified raw body, and `Registry.process` invokes the registered handler with `shop: "shop-b.myshopify.com"` and the attacker's body content — the app now processes cross-tenant data under Shop B's identity.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
