Based on this analysis, I've found a concrete identity-binding break matching the analog category ("a field acted on but not covered by the HMAC").

### Title
Webhook shop-domain and topic headers are trusted for tenant attribution without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body [1](#0-0) , while the `shop` and `topic` values used for tenant/topic attribution are read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only the HMAC over the body and then dispatches to the handler using these header-derived, unsigned `shop`/`topic` values [3](#0-2) .

### Finding Description
The binding that should hold is: `shop-domain header == shop that produced/authorized the signed body`. Shopify's HMAC over webhooks only covers the raw JSON body, not the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, or `X-Shopify-Webhook-Id` headers. `HmacValidator.validate` calls `to_signable_string`, which for `Request` returns only `@raw_body` [1](#0-0) , and separately calls `verifiable_query.hmac` which decodes the `hmac-sha256` header [4](#0-3) . Neither the `shop` nor `topic` header value participates in the signed input at all.

`Registry.process` uses `request.shop` and `request.topic` purely from headers to route the payload to the correct handler and pass `shop` onward into `WebhookMetadata`, which apps use to attribute the payload to a specific merchant/tenant [3](#0-2) . This is the documented usage pattern where a host app trusts `data.shop` to identify which tenant's data the webhook body belongs to [5](#0-4) .

Because `shop` (and `topic`) are not covered by the HMAC, if an attacker who controls or has intercepted a genuinely-signed webhook body from Shopify (e.g. from their own store's legitimate webhook, or any body/HMAC pair leaked in logs, error trackers, or proxy layers) can submit an HTTP request directly to the app's webhook endpoint with the same `raw_body` and valid `hmac-sha256` header, but a different `shop-domain` header, `HmacValidator.validate` still returns `true` — the signature check only recomputes and compares against the body. The handler then processes the payload as if it belonged to the attacker-chosen shop, breaking the identity binding `shop-domain == originating tenant`.

### Impact Explanation
This is a cross-tenant data attribution issue: an unprivileged actor able to relay or replay a validly-signed webhook body can cause the app to process/store that data (e.g. order or customer payloads) under an arbitrary `shop` value. Depending on how the host app uses `data.shop` (e.g. for DB lookups, tenant scoping, or triggering per-shop actions), this can lead to cross-tenant data contamination or state corruption, meeting the High impact bar for a scope/binding bypass carrying identity information the app relies on.

### Likelihood Explanation
Exploitation requires the attacker to possess a validly-signed body+HMAC pair — which they can obtain trivially by owning/operating any shop that installs the app (a legitimate low-privilege actor), since Shopify signs webhooks per-topic/body and no shop-specific binding is enforced by the signature itself. No leaked secrets, tokens, or elevated access are required; only network access to the app's public webhook endpoint.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the signed/verified material, or otherwise cross-check the header-derived `shop` against server-side expectations (e.g., verify the shop is currently installed and that the specific webhook subscription id belongs to that shop) before dispatching to handlers, rather than trusting `X-Shopify-Shop-Domain` as an unauthenticated identity claim.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body and its `X-Shopify-Hmac-Sha256` header from Shopify.
2. Attacker sends a POST directly to the app's public webhook endpoint with the same `raw_body` and `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and any registered `X-Shopify-Topic`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and succeeds [6](#0-5) .
4. The handler is invoked with `WebhookMetadata` where `shop: "victim-shop.myshopify.com"` even though the body/topic actually originated from the attacker's own shop [7](#0-6) , causing the host app to process/store attacker-controlled data as if it came from the victim tenant.
