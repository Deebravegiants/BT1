### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC over that raw body alone. The `shop` (from the `x-shopify-shop-domain`/`shopify-shop-domain` header) is read directly from the unauthenticated header and passed straight through to the handler as the tenant identifier, without ever being bound to the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes `shop` as a plain, unverified header read: [1](#0-0) 

Its `to_signable_string`, used for HMAC verification, only ever returns the raw body: [2](#0-1) 

`Utils::HmacValidator.validate` computes/compares the signature purely against `verifiable_query.to_signable_string` (the body), never incorporating shop, topic, or any header: [3](#0-2) 

`Registry.process` validates the HMAC (body-only) and then forwards the unauthenticated `request.shop` straight to the app's handler as the trusted tenant identifier: [4](#0-3) 

The documentation explicitly instructs developers to key their per-tenant processing off `data.shop`, treating it as a trusted value equivalent to the HMAC-verified payload: [5](#0-4) 

Because the app's `api_secret_key` is shared across all shops that install the app (it's not per-shop), any body+HMAC pair that is valid for one shop is valid for every shop. This breaks the identity binding: `shop claimed in WebhookMetadata == shop that actually produced/owns the HMAC-signed body` — the equality does not hold, since `shop` is attacker-controlled header data entirely outside the HMAC's scope.

### Impact Explanation
An unprivileged internet user who can obtain one legitimately-signed webhook delivery for the target app (e.g., by installing the app themselves on their own store, or intercepting/replaying a webhook they legitimately received) can resend that exact body+HMAC to the app's webhook endpoint while substituting the `shop-domain` header for an arbitrary victim shop. `Utils::HmacValidator.validate` will still succeed because it never checks the shop header, so the app's handler executes with `data.shop` set to the victim's domain while `data.body` is attacker-supplied content. Any app that uses `data.shop` (as shown in this gem's own documented example) to look up the victim's session/access token or to attribute/store data against the victim tenant will process attacker-controlled data under the victim's identity — a cross-tenant confusion/injection primitive reachable without any credentials beyond running the app once as an attacker-owned shop.

### Likelihood Explanation
Reaching this requires only sending an HTTP POST to the app's public webhook callback URL with attacker-chosen headers and a previously-observed, validly-signed body — no access token, `api_secret_key`, or elevated privilege is needed. Any developer following the gem's own webhook documentation (using `data.shop` to key work) is exposed.

### Recommendation
Bind the shop domain (and topic) into the HMAC-verified material, or otherwise independently verify that `request.shop` corresponds to a shop with an active, installed session before trusting it in `WebhookMetadata`. At minimum, document that `data.shop` is not HMAC-verified and must be cross-checked against known installed shops before being used for tenant-sensitive operations.

### Proof of Concept
1. Install the target app on an attacker-controlled development store `attacker.myshopify.com`; capture a legitimately delivered webhook: raw body `B` and header `x-shopify-hmac-sha256: H` (valid because it's signed with the app's shared `api_secret_key`).
2. Replay the exact same request to the app's webhook endpoint, keeping body `B` and `hmac` header `H` unchanged, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which only checks `HMAC(secret, B) == H` — this still passes.
4. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, i.e., attacker-controlled body data processed as if it belongs to `victim-shop`.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
