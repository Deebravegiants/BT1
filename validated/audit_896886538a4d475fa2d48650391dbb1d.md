## Analog Found [1](#0-0) 

### Title
Iris-code signature omits signup-session context (signup_id/operator/reason), enabling cross-signup signature replay and misattribution - (File: src/plans/enroll_user.rs)

### Summary
The reported ParaSpace bug class is: a signed data structure (`Credit`) is missing a context-binding field (marketplace address), so a signature that was validly produced for one context can be replayed and misattributed to a completely different, unintended context. The direct analog in `orb-core` is `make_signature` in `src/plans/enroll_user.rs`, which computes the Secure-Element-signed "iris code signature" attached to every signup submission but leaves out the fields that bind that signature to *this specific signup transaction*.

### Finding Description
`make_signature` builds the SHA-256 digest that is signed by the Secure Element and sent to the backend as the `signature` field of the signup request: [1](#0-0) 

The hashed context includes only:
- `ORB_ID`
- `user_qr_code.user_id`
- pipeline/iris-code version strings and the iris code/mask bytes for both eyes

It does **not** include the `signup_id`, the `operator_qr_code` identity, the `signup_reason`, or any timestamp/nonce. All of those values, however, are independently transmitted alongside the signature in the same multipart request: [2](#0-1) 

Because the signed payload is decoupled from `signup_id`/`operator_qr_code`/`signup_reason`, the same signature blob generated by the Secure Element for a given user's iris data is valid irrespective of which `signup_id`, which operator session, or which `signup_reason` it is submitted under — exactly the missing "MarketplaceAddress"-equivalent binding described in the report. A signature computed for one signup context can be resubmitted (e.g., captured and replayed, or reused across a retried/duplicated flow) attached to a different `signup_id`/operator/reason without the signature itself proving that association, since the cryptographic attestation covers only the iris/user data, not the transaction context it is meant to authorize.

### Impact Explanation
This allows misattribution of a cryptographically-signed biometric attestation to a signup transaction other than the one it was actually produced for (different `signup_id`, different operator session, or different `signup_reason` such as `Fraud`/`Failure` vs `Normal`). Since the backend's fraud/duplicate detection and signup bookkeeping key off `signup_id`/`operator_qr_code`/`reason` fields that are not covered by the signature, an attacker able to intercept or replay a previously valid signup submission (over the request path, not requiring any privileged orb/backend access) could cause the backend to accept a signature as proof for an unrelated signup event, undermining the integrity guarantee the signature is meant to provide.

### Likelihood Explanation
The signing code path is exercised on every normal signup by an unprivileged end user/operator interacting with the orb through the standard enrollment flow — no elevated access is required to trigger `make_signature`/`signup_post::request`. The missing context binding is a structural property of the signed payload, not a rare edge case, matching the "credit struct lacks marketplace identifier" root cause directly.

### Recommendation
Include the transaction-binding fields — `signup_id`, `operator_qr_code.user_id`, and `signup_reason` (and ideally a timestamp/nonce) — inside the SHA-256 context hashed in `make_signature` before it is passed to `secure_element::sign`, so the resulting signature cryptographically commits to the specific signup transaction it is meant to authorize, mirroring the fix of adding `MarketplaceAddress` to the `Credit` struct in the original report.

### Proof of Concept
1. Observe that `make_signature` (`src/plans/enroll_user.rs:290-304`) hashes only `ORB_ID`, `user_qr_code.user_id`, and pipeline/iris fields.
2. Observe that `signup_post::request` (`src/backend/signup_post.rs:100-143`) sends `signup_id`, `operator_qr_code.user_id` (as `distributorId`), and `signup_reason` as separate, unsigned form fields alongside the `signature`.
3. Because none of these three fields are part of the signed digest, a party who can resubmit/replay a signup request (e.g., across a retried session or via request interception) can attach the identical valid `signature` to a request carrying a different `signup_id`, `distributorId`, or `reason` value, and the signature will still verify — since the signature never committed to those values in the first place.

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}
