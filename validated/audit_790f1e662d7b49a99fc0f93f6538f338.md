## Analysis

**The equality being tested:** tokens leaving `ExternalActionSwap`/`LifiExternalAction` in a given `Hinkal.transact` call must equal `-deltaAmountChanges[i]` that `Hinkal._externalTransact` sent to the action for that call (i.e., the action must not disburse more value than it was funded with in that same transaction).

**Trace:**
- `Hinkal._externalTransact` sends `-deltaAmountChanges[i]` of `inputToken` to the action and then calls `runAction` → `swap`. [1](#0-0) 
- `ExternalActionSwap.swap` computes `inputAmount = uint256(-deltaAmounts[0])` but this value is **never passed to or enforced by** `callRouter` for the ERC‑20 path — it is purely informational. [2](#0-1) 
- `LifiExternalAction.callRouter` grants `approveUnlimited(inputToken, router)` and then executes `router.call(externalActionMetadata)`, fully attacker-controlled calldata that decides exactly how much `inputToken` the router pulls via the standing unlimited allowance. `swappedAmount` is measured purely as the *output*-token balance delta around that call, with no check that the amount of `inputToken` actually consumed matches `inputAmount`. [3](#0-2) 
- `swap` then forwards the entire `swappedAmount` (minus fees) to `msg.sender` (Hinkal) and mints a UTXO for exactly that amount, to the caller's own `stealthAddressStructure`. [4](#0-3) 
- `Hinkal`'s balance-equation check only verifies that *Hinkal's own* balance change equals `amountChanges[i] + utxoAmount` — it has no knowledge of, or constraint on, how much `inputToken` the action actually consumed to produce that output, and `slippageValues[i]` is only a floor, never a ceiling. [5](#0-4) 
- `HinkalHelper.performHinkalChecks`/`dimensionsCheck`/`checkOnchainCreation` only validate internal consistency of the attacker's own self-generated proof/calldata (via `calldataHash`); nothing binds the router's actual token movement to the declared `inputAmount`. [6](#0-5) 

**Root cause:** because the ERC‑20 swap path never limits or verifies how much `inputToken` the router draws against the unlimited allowance, and never refunds/tracks leftover `inputToken` between transactions, any `inputToken` balance stranded in the shared `ExternalActionSwap`/`LifiExternalAction` contract (e.g., dust left when a router route under-consumes the transferred `inputAmount`, or partial-fill refunds) sits unaccounted for. A subsequent, unprivileged caller can craft `externalActionMetadata` that has the router pull that stranded balance too (on top of their own tx's funded `inputAmount`) and convert it to `outputToken`; since `swappedAmount` is measured only as a plain output-token balance delta, the inflated amount is fully forwarded and minted as the attacker's own UTXO. This breaks the invariant: tokens leaving the action in that tx exceed `-deltaAmountChanges` Hinkal sent it that tx.

The "tree has exactly one prior leaf" condition in the question title is unrelated to this exploit path — merkle root/leaf state does not gate or affect this specific accounting flaw in `ExternalActionSwap.swap`/`LifiExternalAction.callRouter`; it appears to be an unrelated precondition attached to the question.

### Title
Unbounded router pull via standing `approveUnlimited` lets an attacker sweep stranded input-token balance in `ExternalActionSwap`/`LifiExternalAction` into their own output UTXO - (File: contracts/external-actions/swaps/ExternalActionSwap.sol, contracts/external-actions/swaps/LifiExternalAction.sol)

### Summary
`ExternalActionSwap.swap` computes `inputAmount` from `-deltaAmounts[0]` but never enforces it against what the router actually consumes; `LifiExternalAction.callRouter` gives the router unlimited allowance and executes fully attacker-controlled calldata, measuring only the resulting `outputToken` balance delta. Any `inputToken` balance left stranded in the shared action contract from a prior transaction (e.g. a route that doesn't consume the full transferred amount) can be swept by a later, unrelated caller and converted entirely into their own shielded UTXO output.

### Finding Description
The broken equality is: tokens leaving the action contract in a `Hinkal.transact` call == `-deltaAmountChanges` Hinkal sent that action in the same call. `ExternalActionSwap.swap` derives `inputAmount` [7](#0-6)  but that value is not threaded into the router call for ERC-20 swaps — `LifiExternalAction.callRouter` simply does `approveUnlimited(inputToken, router)` then `router.call(externalActionMetadata)`, an opaque, attacker-supplied blob, and measures `swappedAmount` solely from the `outputToken` balance delta around that call [8](#0-7) . Because the allowance is unlimited and persistent, and the amount actually pulled from the action's `inputToken` balance is dictated entirely by the attacker-chosen calldata, an attacker can craft a swap route that consumes both their own tx-funded `inputAmount` *and* any leftover `inputToken` balance already sitting in the shared action contract (left over from a prior transaction whose route under-consumed the transferred amount, or any other stranding cause), and have the entire resulting `outputToken` proceeds forwarded to Hinkal and minted as their own UTXO via `transferERC20TokenOrETH`/`utxoSet[0]` [9](#0-8) . `Hinkal._internalTransact`'s balance check only validates Hinkal's own balance delta against `amountChanges` and the UTXO set the action returns [10](#0-9) , which is self-consistent regardless of whether the action's output was inflated by stolen stranded input. `slippageValues[i]` is only a floor, never a ceiling, so no guard rejects an inflated output.

### Impact Explanation
An unprivileged attacker can steal in-flight/stranded user funds parked in the shared `ExternalActionSwap`/`LifiExternalAction` contract by directing the router (via crafted `externalActionMetadata`) to consume more `inputToken` than this transaction's `deltaAmountChanges` funded, using the pre-existing unlimited allowance, and claiming the resulting excess `outputToken` as their own shielded UTXO. This is a direct theft of another user's (or the protocol's) parked funds and is repeatable each time stranded balance accumulates in the action contract.

### Likelihood Explanation
Preconditions: a nonzero `inputToken` balance stranded in the action contract (plausible from partial/under-consuming router fills, dust, or direct transfers) and a standing unlimited allowance from a prior legitimate swap using that token (`approveUnlimited` is idempotent and persists). The attacker only needs the ability to perform a normal Hinkal swap transaction with self-crafted `externalActionMetadata`/proof — no privileged role required — making this low-cost and realistically triggerable whenever the action contract accumulates a nonzero balance of a token with an already-granted router allowance.

### Recommendation
Constrain the router call to only spend the exact `inputAmount` transferred to the action in that transaction (e.g., verify the action's pre/post `inputToken` balance delta equals `inputAmount`, or use a scoped/one-time approval sized to `inputAmount` instead of `approveUnlimited`), and refund/revert on any leftover `inputToken` rather than allowing it to remain in the shared contract's balance.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `LifiExternalAction` with a mock router and mock ERC-20 tokens.
2. Perform a legitimate swap transaction where the mock router's swap logic intentionally consumes less than `inputAmount` of `inputToken` (simulating partial fill), leaving a residual `inputToken` balance stranded in `LifiExternalAction`. Record `strandedBalance`.
3. As a second, unrelated attacker, perform a Hinkal swap transaction with `deltaAmounts[0] = -X` (small legitimate amount) but craft `externalActionMetadata` so the mock router pulls `X + strandedBalance` of `inputToken` (allowed by the unlimited allowance) and returns proportional `outputToken`.
4. Assert: `outputToken` amount minted into attacker's UTXO (`utxoSet[0].amount`) > amount attributable to `X` alone (i.e., exceeds `-deltaAmountChanges[1]`/expected ratio for `X`), proving `tokens_leaving_action != -deltaAmountChanges_sent_this_tx`.
5. Assert `strandedBalance` in the action contract is now zero/moved to attacker, confirming the stranded funds were captured by the attacker rather than refunded to the original depositor.

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
