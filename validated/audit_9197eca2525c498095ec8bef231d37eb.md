### Title
Webhook `shop` domain is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable string from the raw request body only, excluding the `shopify-shop-domain` header. `ShopifyAPI::Webhooks::Registry.process` validates only that HMAC before dispatching the webhook to the app's handler with `shop: request.shop` taken straight from the unauthenticated header, letting an attacker rebind a validly-signed payload to an arbitrary tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while the tenant identifier used downstream, `shop`, is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header and is never mixed into the signed data: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, i.e. it only proves the body is intact and was signed with the app's `api_secret_key`; it performs no check binding that signature to the shop the event claims to be from, then hands `request.shop` straight to the handler: [3](#0-2) 

`HmacValidator.validate` confirms the equality `HMAC(secret, raw_body) == received_hmac`, which says nothing about which shop the payload belongs to: [4](#0-3) 

Because a single app has one `api_secret_key` shared across every merchant that installs it, an attacker who controls one shop that has the app installed can capture a legitimate webhook (body + `X-Shopify-Hmac-Sha256`) that Shopify sent for their own shop, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting a victim shop's domain in the `X-Shopify-Shop-Domain` header. The HMAC check passes (it only covers the body), and the handler executes with `shop` set to the victim's domain — breaking the identity binding: `shop authenticated by HMAC` ≠ `shop used as the tenant key for handling the event`.

### Impact Explanation
This crosses a tenant boundary: an app's webhook handler (e.g. `app/uninstalled`, GDPR mandatory webhooks, order/customer webhooks) can be triggered with attacker-chosen body content while impersonating any other shop that has the app installed, since the body itself is unconstrained by the shop identity. Depending on what the host application does with `WebhookMetadata#shop` (data writes, deletion, deactivation, syncing), this enables cross-tenant data corruption or unauthorized state changes attributed to a shop the attacker doesn't own, matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for any attacker who is a legitimate merchant/user of the target app: obtaining one valid signed webhook from their own shop's install (trivial — webhooks fire routinely) is enough to build the replay; no access to `api_secret_key`, access tokens, or the host app's infrastructure is required, only network access to the app's public webhook endpoint.

### Recommendation
Bind the shop identity into the verified signature material, or explicitly cross-check it against a trusted source before dispatching:
- Include `shop-domain` (and ideally `webhook-id`/`topic`) in the HMAC-covered signable string used by `Webhooks::Request`, or
- After HMAC validation, require the host app to correlate `request.shop` against the shop associated with the specific `webhook_id`/session store before acting on the payload, and document this requirement prominently since the current API silently trusts the header.

### Proof of Concept
1. App X is installed on both `attacker.myshopify.com` (attacker-owned) and `victim.myshopify.com`.
2. Shopify sends a legitimate webhook to App X's endpoint for `attacker.myshopify.com`:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid-hmac-of-body>
   X-Shopify-Shop-Domain: attacker.myshopify.com
   Body: {"id": 1, ...attacker-controlled order payload...}
   ```
3. Attacker captures this raw body and its `X-Shopify-Hmac-Sha256` value.
4. Attacker resends the identical body and HMAC header, only changing the shop header:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <same-hmac-as-step-2>
   X-Shopify-Shop-Domain: victim.myshopify.com
   Body: <same body as step 2>
   ```
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, raw_body)` — identical to step 2 — and passes.
6. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled>, ...)`, causing App X to act on attacker-controlled data under the victim's tenant identity.
