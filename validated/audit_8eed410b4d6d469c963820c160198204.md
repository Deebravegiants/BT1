### Title
Webhook `shop` / `topic` / `webhook_id` fields are trusted but not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` verifies the authenticity of an incoming webhook using `Utils::HmacValidator.validate`, but the HMAC is computed only over the raw request body. The `shop`, `topic`, and `webhook_id` header values — which are trusted downstream to identify the tenant and route the payload to a handler — are never included in the signed content. Since the HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every shop that installs the app, anyone who legitimately receives one authentic webhook delivery (e.g., by installing the app on their own store) obtains a `(body, hmac)` pair that remains valid for that body regardless of which `shop`/`topic`/`webhook_id` headers accompany it. That pair can be replayed to the app's webhook endpoint with arbitrary `shop-domain`/`topic`/`webhook-id` headers, and `HmacValidator.validate` will still accept it.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . `HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` and compares it to the `hmac` header: [2](#0-1) . Meanwhile `Registry.process` uses `Utils::HmacValidator.validate(request)` to authorize the request, then trusts `request.topic`, `request.shop`, and `request.webhook_id` (all parsed straight from unauthenticated headers) to route to a handler and populate `WebhookMetadata`: [3](#0-2) . The `shop`, `topic`, and `webhook_id` accessors on `Request` simply read headers with no cryptographic binding to the body/HMAC: [4](#0-3) .

This breaks the identity binding that host applications rely on: `verified HMAC == signed(body)`, while the tenant identity used by the application is `request.shop == unauthenticated header value`. Because the same `api_secret_key` is used to sign webhooks for every shop that installs the app, an attacker who runs their own store install of the app can capture a valid `(body, hmac)` pair from their own genuine webhook deliveries, then replay that exact body+HMAC to the app's public webhook endpoint while substituting a different shop's domain in the `shop-domain` header (and/or a different `topic`/`webhook-id`). `HmacValidator.validate` only checks body integrity, not header binding, so the forged request passes verification and is handed to the handler tagged with the attacker-chosen `shop`.

### Impact Explanation
This is a cross-tenant identity confusion: the host application's webhook handler receives `WebhookMetadata.shop` claiming to be any shop the attacker chooses, backed by a cryptographically valid HMAC. Handlers commonly use `data.shop` to look up sessions/access tokens or to trigger shop-scoped side effects (data sync, deletion flows for mandatory `shop/redact` topics, order/customer processing, etc.). An attacker with only a low-privilege install of the app on their own store can forge webhook events appearing to originate from a completely different, unrelated shop, potentially causing the host app to act on incorrect tenant data — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to have at least one genuine webhook delivery from their own store (readily obtainable by installing the app on a free/dev shop and subscribing to any webhook topic) and network access to POST to the app's public webhook endpoint (no authentication is required to reach it besides HMAC). No access token, `client_secret`, or privileged account is needed.

### Recommendation
Bind the trusted routing fields into the signed content, or otherwise cryptographically verify them against the source shop before trusting `request.shop`/`request.topic`/`request.webhook_id`. At minimum, `HmacValidator`/`Request` should incorporate the `shop-domain` (and ideally `topic`, `webhook-id`) headers into the signable string, or the host-app-facing API should require verifying the caller's registered domain against Shopify's known shop for that install (e.g., cross-check `shop-domain` against an active session before dispatching to a handler), rather than trusting the header value verified only through a shop-independent HMAC.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a real webhook delivery from Shopify, e.g. body `{}` with topic `orders/create`, correctly HMAC-signed with the app's shared `api_secret_key`: `hmac = OpenSSL::HMAC.digest(sha256, api_secret_key, "{}")` (mirrors test setup): [5](#0-4) .
2. Attacker replays this exact `(raw_body="{}", hmac)` pair to the app's public webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and any desired `x-shopify-topic`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only re-derives the signature from the body: [6](#0-5) .
4. The registered handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, where `shop` is `"victim-shop.myshopify.com"` even though the payload never actually came from Shopify on behalf of that shop: [7](#0-6) .

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
