This confirms the analysis. `begin_auth` at `lib/shopify_api/auth/oauth.rb:22-24` uses `ShopifyAPI::Context.scope` only as a default OAuth scope request parameter (part of the `client_id`/`scope`/`redirect_uri`/`state` query built for the merchant's own OAuth consent screen), which is set once by the app developer at process startup via `Context.setup` — the attacker never controls this value, and it plays no role in shop identity resolution. Identity in the callback path is derived from `auth_query.shop` (validated via HMAC) and in JWT flows from the `dest`/`sub` claims, not from `scope`.

### Analysis of the claimed bug

**Binding claimed broken:** "the value that was verified" (secret used to compute a valid HMAC/JWT signature) must equal "the value that is used" (secret Context trusts for future validation).

Tracing this: `Utils::HmacValidator.validate` at `lib/shopify_api/utils/hmac_validator.rb:13-22` first tries `Context.api_secret_key`, and only if that fails and `Context.old_api_secret_key` is present/non-empty, retries with the old key. `JwtPayload#initialize` at `lib/shopify_api/auth/jwt_payload.rb:24-31` does the same fallback pattern. [1](#0-0) [2](#0-1) 

`old_api_secret_key` is an explicit, documented key-rotation mechanism: the app developer sets it via `Context.setup(old_api_secret_key: ...)` and is expected to clear it (call `setup` again with `old_api_secret_key: nil`) once rotation is complete. That's application-level configuration lifecycle, not a defect in the gem — the gem never invents, leaks, or auto-refreshes this value; it only reads whatever the developer put there. There is no attacker-controlled input that populates `old_api_secret_key`, and no code path lets an unprivileged HTTP requester influence it. [3](#0-2) 

**Identity binding:** Shop/session identity is never derived from `scope` or `old_api_secret_key`. In OAuth, `auth_query.shop` is what's used to build the `null_session` and final `Session`, gated by `Utils::HmacValidator.validate(auth_query)` and the `state` cookie check, both independent of `scope`. [4](#0-3) 

In JWT flows, identity comes from `dest`/`sub`, gated by the `aud == Context.api_key` check. [5](#0-4) 

**Cross-thread/cross-request session isolation:** `Context.active_session` is backed by `Concurrent::ThreadLocalVar`, and `test_active_session_is_thread_safe` in `test/context_test.rb:64-92` already demonstrates that two concurrently-running threads activating different sessions never observe each other's session — each thread reads only its own thread-local value. [6](#0-5) [7](#0-6) 

`Session.temp` explicitly saves/restores `Context.active_session` around the block using `ensure`, so even within a single thread nested/sequential temp-session usage always restores the prior identity rather than leaking. [8](#0-7) 

No code path lets one tenant's `shop`/`scope`/secret bleed into another tenant's validation or session because: (1) `scope` never participates in the equality checks used to accept a signature or JWT, (2) `old_api_secret_key` is developer-managed static configuration, not attacker input, and (3) session state is thread-isolated with save/restore semantics already covered by an existing passing test.
