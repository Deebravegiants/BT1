### Title
Webhook shop-domain header is excluded from HMAC coverage, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content as only the raw request body [1](#0-0) , while the `shop` used for tenant routing is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in that signed content [2](#0-1) . `Registry.process` validates the HMAC and then forwards `request.shop` unchecked into `WebhookMetadata`, which host apps use to identify which merchant/tenant the webhook body belongs to [3](#0-2) .

### Finding Description
The intended binding is: `hmac == HMAC(secret, raw_body)` should also imply `shop == the tenant the body actually belongs to`. In reality the HMAC only binds the body bytes, not the shop header. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the signature purely over `request.to_signable_string` (i.e., `@raw_body`) and compares it against `request.hmac` (decoded from the `hmac-sha256` header) [4](#0-3) [5](#0-4) . The `shop`, `topic`, `api-version`, and `webhook-id` values are all pulled from headers that sit completely outside this signature [6](#0-5) .

Because a valid HMAC only proves "this body was signed by Shopify at some point for some shop," it does not prove which shop the accompanying `shop-domain` header refers to. An attacker who can influence or replay the header (e.g., a reverse proxy/host app that maps arbitrary headers into the raw HTTP request passed to `Request.new`, or an attacker capturing one legitimately-delivered webhook and replaying its body with a substituted `shop-domain` header value) can make `Registry.process` accept the swapped identity: HMAC validation succeeds (it only checks body bytes) while `request.shop` — now attacker-chosen — is handed to the handler as the trusted tenant identifier [7](#0-6) .

### Impact Explanation
Downstream `WebhookHandler` implementations receive `WebhookMetadata#shop` as an authenticated fact and typically use it to select which merchant's session/access token/data the webhook body should be applied to [8](#0-7) . Because the field a handler trusts for tenant scoping (`shop`) is not covered by the cryptographic check that authenticates the request (`hmac` over `raw_body` only), the gem's `HmacValidator.validate(request) == true` gives no guarantee about which tenant the payload is really for, enabling cross-tenant data misattribution in any app that relies on this metadata's `shop` field for per-tenant routing.

### Likelihood Explanation
Exploitability depends entirely on whether an attacker (or a compromised/misconfigured intermediary) can control the `shop-domain` header independently of the body — this is plausible in typical Rack/Rails deployments where headers and body are read from the same request but are not cryptographically linked, and requires no possession of the app's `api_secret_key` since the check that is bypassed is precisely "does the header match what was signed," which the gem never performs.

### Recommendation
Include `shop` (and ideally `topic`/`api_version`) in `Request#to_signable_string` is not possible since Shopify only signs the raw body server-side; instead, the gem should not treat `request.shop` as authenticated merely because `HmacValidator.validate(request)` passed. At minimum, document/enforce that host apps must independently verify `request.shop` against the shop associated with the body (e.g., an `id`/`shop_id` field inside `parsed_body`, or a shop looked up via `webhook_id` from Shopify's API) before trusting it for tenant routing in `Registry.process`.

### Proof of Concept
1. A legitimate webhook for `shop-a.myshopify.com` arrives with a valid `X-Shopify-Hmac-Sha256` header computed over `raw_body`.
2. Attacker (or a misbehaving proxy in front of the app) replays the exact same `raw_body` and `hmac-sha256` header, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
3. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC only over `raw_body` — it matches, since the body and hmac are unchanged [9](#0-8) .
4. `request.shop` returns `"shop-b.myshopify.com"` from the header, unrelated to the HMAC check [10](#0-9) .
5. `handler.handle` receives `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: <shop-a's data>, ...)`, causing shop-a's webhook payload to be processed under shop-b's tenant context [7](#0-6) .
