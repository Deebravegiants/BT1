The documentation at `docs/usage/webhooks.md` explicitly states that `Registry.process` "will verify the request did indeed come from Shopify" and instructs developers to trust `data.shop` as the shop domain of the webhook, with no caveat that this field is unauthenticated. This confirms the gem's own documented contract treats `shop` as verified, which is the binding broken by the code.

### Title
Webhook `shop` field is not covered by HMAC verification, allowing tenant spoofing on webhook processing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, excluding the `shop` header from the HMAC-signed content, yet `ShopifyAPI::Webhooks::Registry.process` passes `request.shop` straight to the handler as an authenticated tenant identifier.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` verifies a `VerifiableQuery` by computing `HMAC(secret, to_signable_string)` and comparing it to the supplied `hmac` value [1](#0-0) . For webhooks, `to_signable_string` is defined to return only the raw body, and `shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header without being part of the signed data [2](#0-1) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` before invoking the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` [3](#0-2) . Since `shop` is never part of the HMAC-signed content, an attacker who obtains any single valid `(body, hmac)` pair signed with the app's shared `api_secret_key` — for example by installing the app on their own shop and capturing a genuine webhook delivery — can resubmit that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. The signature check still passes because the HMAC only covers the body, and the handler receives `data.shop` set to the attacker-chosen value instead of the shop that actually produced the payload.

This breaks the intended binding: shop authenticated (the tenant that produced the signed body) ≠ shop delivered to the handler (`request.shop`, taken from an unsigned header). The documentation for this gem explicitly tells integrators that `process` "will verify the request did indeed come from Shopify" and that `data.shop` is "The shop domain of the webhook" [4](#0-3) [5](#0-4) , with no caveat that `shop` is unauthenticated — so host applications following the documented API and using `data.shop` to select the tenant context (as shown in the gem's own example, `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) inherit this cross-tenant confusion [6](#0-5) .

### Impact Explanation
This allows cross-tenant data/action confusion: a webhook payload legitimately generated for the attacker's own shop can be replayed and attributed by the app to a victim shop, since the gem itself vouches that `data.shop` came from a request that "did indeed come from Shopify." Depending on how the host app uses `data.shop` (as documented, to select the tenant record/job queue), this can lead to cross-tenant data being written into or actions being triggered under a different merchant's account.

### Likelihood Explanation
Requires only that the attacker install the app on their own shop (or otherwise obtain one legitimate signed webhook body/HMAC pair) and send a forged HTTP request with a different `shop-domain` header directly to the app's public webhook endpoint — no access token, secret, or privileged access is needed beyond normal app installation.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values in the HMAC-signed content, or otherwise cryptographically bind them to the body, so that `Registry.process`/`HmacValidator.validate` reject requests whose `shop` header does not match the shop the body was actually signed for.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC(api_secret_key, B)`.
2. Attacker resends an HTTP POST to the app's webhook endpoint with the same raw body `B` and the same `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request#hmac` decodes `H` and `HmacValidator.validate` recomputes `HMAC(api_secret_key, B)` — matching, since `shop` was never part of `to_signable_string` [7](#0-6) .
4. `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)`, causing the app to process attacker-controlled data under the victim shop's tenant context.
