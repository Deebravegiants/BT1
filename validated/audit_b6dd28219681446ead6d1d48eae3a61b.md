Found it: `Bonding.launch()` never validates `creator_ != address(0)`, and every downstream permission check in `Bonding.sol` treats `info.creator == address(0)` as the sentinel for "token doesn't exist" rather than as a rejected input.

### Title
Authorization Bypass via Blank/Zero Creator ID in `Bonding.launch` - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding.launch(LaunchParams, address creator_)` accepts `creator_` from the caller (a Zap, invoked from `Zap.createToken`) with no `creator_ == address(0)` guard, unlike every other address parameter in `initialize`/`initializeBounceGlobalStorage`/`transferCreator`, which do check for `address(0)` [1](#0-0) . The stored `info.creator` value is simultaneously used across the contract as the existence sentinel for the token: `if (info.creator == address(0)) revert TokenNotTrading();` in `buy`/`sell`, and `if (info.creator == address(0)) return 0;` in `previewLtUntilGraduation` [2](#0-1) [3](#0-2) .

### Finding Description
This is the same bug class as the OpenClaw analog: a caller-supplied identity/authorization field that is left blank is treated by downstream checks not as "an invalid/rejected identity" but as "no identity attached" — which flips restrictive logic into a bypassed state. Here, `creator_` is fully attacker-controlled (any unprivileged caller of `Zap.createToken` picks it), and it is written unvalidated into `TokenInfo.creator` via `_storeTokenInfo` [4](#0-3) . If a caller launches with `creator_ = address(0)`, the resulting token is stored with `info.creator == address(0)`.

Every subsequent authorization/existence check for that token — `buy`, `sell`, `previewLtUntilGraduation` — treats `info.creator == address(0)` as "unknown token" and therefore reverts with `TokenNotTrading`, permanently freezing that token's curve from any trading, sells, or graduation math despite the token being live, having a real `Pair`, and (via `Zap.createToken`'s mandatory `MIN_SEED_USDC` seed) holding real user funds in the curve. `transferCreator` also becomes unusable to fix this, since it is gated on `msg.sender == info.creator`, and no one can ever match `address(0)` [5](#0-4) .

### Impact Explanation
An unprivileged token creator calling `Zap.createToken` with `creator = address(0)` (directly reachable, no privileged access required) permanently bricks their own launched token: the seeded LT/USDC deposited by `MIN_SEED_USDC` is trapped in the `Pair` because `Bonding.buy`/`Bonding.sell` unconditionally revert with `TokenNotTrading` for that token forever, and `transferCreator` can never repoint the zero-address creator to a real one. This is a permanent freeze of trader/creator funds in the curve `Pair`, satisfying the "permanent freezing of funds" impact bar.

### Likelihood Explanation
Reachable trivially and permissionlessly by any address calling `Zap.createToken` (or driving `Bonding.launch` directly if allowlisted as a router in a misconfigured deployment) and simply passing `address(0)` as the `creator` argument — no special privileges, timing, or preconditions are required beyond the standard `MIN_SEED_USDC` seed. It could be triggered accidentally (a wallet-integration bug passing a zero default) or maliciously against a third party's flow if any upstream caller ever forwards an unvalidated address.

### Recommendation
Add `if (creator_ == address(0)) revert ZeroAddress();` at the top of `Bonding.launch`, mirroring the existing `ZeroAddress` guards used elsewhere in the contract (`initialize`, `initializeBounceGlobalStorage`, `transferCreator`), so `info.creator` can never legitimately be zero and the "unknown token" sentinel check remains sound.

### Proof of Concept
1. Attacker (or any user) calls `Zap.createToken(params, seedUsdc)` where `params.ltAddress` is valid, but arranges/forces the `creator` argument passed through to `Bonding.launch` to be `address(0)` (e.g., via a custom router added to `Bonding._routers`, or any future caller path that doesn't itself validate the address before forwarding it to `Bonding.launch`).
2. `Bonding.launch` executes with no zero-address check, calls `_storeTokenInfo(tokenAddr, ..., address(0))`, deploys the `Pair`, and seeds the curve with real LT via `_deployAndSeed`/the seed buy.
3. Any subsequent call to `Bonding.buy(...)` or `Bonding.sell(...)` for `tokenAddr` hits `if (info.creator == address(0)) revert TokenNotTrading();` and reverts unconditionally.
4. `Bonding.transferCreator(tokenAddr, newCreator)` requires `msg.sender == info.creator` (`address(0)`), which no EOA/contract can satisfy, so the creator can never be repaired.
5. Result: the token's `Pair` permanently holds the seeded LT/tokens with no way to trade, sell, or graduate it out — a permanent freeze of curve funds. [6](#0-5) [4](#0-3) [5](#0-4)
