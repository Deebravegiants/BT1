### Title
Emporium `Min`-proof path with empty `erc20TokenAddresses` lets an unprivileged caller drain any tokens/ETH held by the Emporium contract with zero balance accounting - (File: `contracts/CircomDataBuilder.sol`, `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, which only proves `message == Poseidon(messageSeed)` and leaves `rootHashHinkal`, nullifiers, commitments and amounts completely unconstrained by the circuit. `EmporiumUpgradeable.runAction` then executes attacker-supplied `EmporiumStack.ops` from the Emporium's own identity (`stack.signerAddress == address(0)` skips the EIP-712 signature check entirely) while its balance-accounting loops iterate over the (empty) `erc20TokenAddresses` array, so any token movement caused by the ops is never checked against `balancesBefore`/`balancesAfter`.

### Finding Description
The broken equality is: *assets Emporium can move in a transaction == assets accounted for in `balancesBefore`/`balancesAfter`*.

Path:
1. `Hinkal.transact` (`contracts/Hinkal.sol:30-65`) calls `hinkalHelper.performHinkalChecks`, which requires either a whitelisted relay OR `circomData.originalSender == msg.sender && circomData.relay == address(0)` [1](#0-0) . The second branch lets **any unprivileged EOA** call `transact` directly with `relay == address(0)`, bypassing `relayerIsValid`'s whitelist check entirely [2](#0-1) .
2. With `externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` selects `formInputEmporiumMin` [3](#0-2) , which produces a public input vector proving only `message = Poseidon(messageSeed)` per `MainEVMCircuitMin` [4](#0-3) . No root hash, nullifier, amount, or stealth-address binding is enforced by this circuit.
3. `dimensionsCheck` (`contracts/HinkalHelper.sol:64-150`) only requires the arrays (`amountChanges`, `inputNullifiers`, `outCommitments`, etc.) match `dimensions.tokenNumber`, which the attacker can set to 0 to match the empty `erc20TokenAddresses` — no protection against emptiness itself [5](#0-4) .
4. `Hinkal._externalTransact` invokes `EmporiumUpgradeable.runAction` with `deltaAmountChanges` of length 0 (matching the empty token array) [6](#0-5) .
5. Inside `runAction`, `stack = abi.decode(circomData.externalActionData.externalActionMetadata, (EmporiumStack))` is fully attacker-controlled [7](#0-6) . If `stack.signerAddress == address(0)`, `verifyWallet` returns immediately after marking the message used — **no ECDSA signature check is performed** [8](#0-7) .
6. The op loop then executes `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract's own address (`msg.sender == Emporium`) for any non-`invokeWallet` op [9](#0-8) . An attacker sets `endpoint` = any ERC20 that Emporium holds a balance of, and `callData` = `transfer(attacker, balance)`. This succeeds because Emporium is the token holder calling `transfer` on its own behalf.
7. The subsequent balance-accounting loop that would normally catch unaccounted balance decreases (`balanceChange < 0 → revert BalanceChangeShouldBePositive`) iterates `circomData.erc20TokenAddresses` — which is **empty** — so it never runs and never sees the stolen token [10](#0-9) . Likewise `Hinkal.transact`'s outer slippage/balance-diff checks at lines 97-147 also iterate the empty array and add zero protection [11](#0-10) .

The only remaining guard is `onlyAllowedRecipient` on `runAction`, which only checks `msg.sender == externalActionMap[HINKAL_EMPORIUM_ACTION_ID]` (i.e., that it's the real Hinkal contract calling), not that the caller has any right to Emporium's funds [12](#0-11) . This does not prevent the exploit because Hinkal itself is the caller in the normal flow.

The "prior tx in the same block left residual state" framing in the question is not actually required — the vulnerability is exploitable standalone, in a single transaction, against any funds Emporium already holds (e.g. leftover dust from prior ops, relay fees routed to Emporium, or funds an attacker first deposits into Emporium via a legitimate signed op then steals back via this bug, or funds transiently held by Emporium mid-multi-op-call in the same or a later transaction).

### Impact Explanation
Any ERC20 (or ETH, via `op.value`/`callData` targeting a payable contract) balance held by the Emporium contract can be transferred to an attacker-controlled address with zero on-chain accounting, using only the trivial `Min` proof (a single Poseidon hash) and no signature. This matches **Critical: direct theft of shielded or in-flight user funds** — Emporium routinely holds shielded users' funds transiently between deposit and execution of signed operations, relay fees, and inter-op balances. The attack is repeatable every block against whatever balance Emporium currently holds.

### Likelihood Explanation
Preconditions: Emporium must hold a non-zero balance of some token/ETH at call time (a very common condition given its design as a transient custody/execution contract for signed ops and relay fee routing). The attacker needs no special role — `relay == address(0)` and `originalSender == msg.sender` is sufficient to bypass the relay whitelist, and `signerAddress == address(0)` in `EmporiumStack` skips signature verification. Attacker cost is a single transaction and gas; the exploit is fully deterministic and repeatable.

### Recommendation
- Do not allow `HINKAL_EMPORIUM_ACTION_ID` transactions with `erc20TokenAddresses.length == 0` to execute arbitrary `ops`; either require the `Min` path to disallow stateless/unauthenticated `ops`, or require at least one accounted token dimension whenever ops can move funds.
- In `EmporiumUpgradeable.runAction`, do not allow `stack.signerAddress == address(0)` to skip signature verification when `ops` contains calls to arbitrary endpoints; that "no signer" branch should be restricted to a fixed, non-fund-moving action set (e.g., only relay-fee payment), never generic `endpoint.call`.
- Ensure balance-accounting (`balancesBefore`/`balancesAfter` and the `balanceChange < 0` revert) is enforced independent of `erc20TokenAddresses.length`, e.g. by tracking a comprehensive/fixed asset list or an internal accounting invariant that isn't attacker-selectable via the token array's length.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, and a mock ERC20 `TKN`.
2. Register Emporium as `HINKAL_EMPORIUM_ACTION_ID` external action and as `isAllowedRecipient`.
3. Fund Emporium directly with `TKN.transfer(address(emporium), 1000e18)` to simulate residual/in-flight balance.
4. As attacker EOA (no relay role), build `CircomData` with:
   - `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`
   - `erc20TokenAddresses = []`, `amountChanges = []`, `inputNullifiers = []`, `outCommitments = []`, `onChainCreation = []`, `slippageValues = []`
   - `originalSender = attacker`, `relay = address(0)`
   - `externalActionData.externalActionMetadata = abi.encode(EmporiumStack({v:0,r:0,s:0, signerAddress: address(0), ops: [EmporiumOperation({endpoint: address(TKN), invokeWallet: false, value: 0, callData: abi.encodeCall(TKN.transfer, (attacker, 1000e18))})], maxFee:0, deadline: type(uint256).max}))`
   - `emporiumMessage = Poseidon(messageSeed)` computed locally, `calldataHash` computed via `getHashedCalldata`.
5. Generate a `Min`-circuit proof locally (snarkjs) proving `message == Poseidon(messageSeed)`.
6. Call `Hinkal.transact(a,b,c,dimensions,circomData)` from attacker.
7. Assertions on both sides of the broken equality:
   - Before: `TKN.balanceOf(emporium) == 1000e18`, `TKN.balanceOf(attacker) == 0`.
   - After: `TKN.balanceOf(emporium) == 0`, `TKN.balanceOf(attacker) == 1000e18`.
   - Assert `runAction`'s `balancesBefore`/`balancesAfter` arrays are both length 0 (no accounting occurred) while actual token balance moved by `1000e18` — proving the equality "assets moved == assets accounted" is violated.
   - Assert transaction does not revert (no `BalanceChangeShouldBePositive`, no `InvalidSignature`).
