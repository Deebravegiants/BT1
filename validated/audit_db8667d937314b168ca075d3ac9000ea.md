### Title
`PoaBridge.describeWithdrawal` matches withdrawal status by `assetId` only, misattributing status/txHash between same-asset withdrawals in a batch - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`describeWithdrawal` resolves the on-chain status for a `WithdrawalIdentifier` by calling `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which selects the first PoA API record whose `nep141:${near_token_id}` equals `assetId`, ignoring `index` and `destinationAddress` entirely [1](#0-0) . When a batch withdrawal contains two withdrawals with the same `assetId` but different `destinationAddress`, both indices' `describeWithdrawal` calls resolve to the same unsorted array element, so status/txHash for withdrawal 0 and withdrawal 1 can be swapped or duplicated.

### Finding Description
The broken equality: `describeWithdrawal(wid_i).txHash/status` should equal the outcome of the physical withdrawal that was created at `index i` (i.e., the one addressed to `withdrawalParams[i].destinationAddress`). Instead, both `wid0` and `wid1` (same `assetId`, different `destinationAddress`) invoke `findMatchingWithdrawal(response.withdrawals, assetId)`, which does `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)` [2](#0-1) . This lookup has no dependency on `index`, `destinationAddress`, or amount, so it deterministically returns the same array element (or, worst case, the wrong one among the two, since `.find` always returns the first match) for both calls.

The same defect exists independently in `waitForWithdrawalCompletion`'s local `findMatchingWithdrawal(result.withdrawals, withdrawalCriteria)`, which also only matches on `assetId` [3](#0-2) .

Root cause is explicitly acknowledged in the code's own comments: "NOTE: Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported. POA API doesn't currently support this case either." [4](#0-3) 

No existing guard prevents this: `supports()`, `validateWithdrawal`, `compareAddresses`, and `createWithdrawalIdentifier` do not check for duplicate `assetId` within a batch and do not encode `destinationAddress` into the identifier used for matching [5](#0-4) . `createWithdrawalIdentifier` only carries `index`, `withdrawalParams`, `landingChain`, and `tx` — `index` is stored but never actually used to disambiguate in `describeWithdrawal`.

Attacker input: an unprivileged user can simply request a batch withdrawal (`withdrawalParams: [w0, w1]`) where `w0.assetId === w1.assetId` but `w0.destinationAddress !== w1.destinationAddress` — this is a normal, permitted user action, not an escape hatch.

Exploit flow: PoA processes both withdrawals (e.g., one completes fast to address A, one is still pending to address B). An integrator calling `waitForWithdrawalCompletion`/`describeWithdrawal` for index 0 and index 1 can both receive the COMPLETED record (for the same underlying withdrawal), or the completed status can be attributed to the wrong index. If the integrator credits/refunds a user off-chain based on `destinationTx[i]`, it can credit the wrong withdrawal as complete (double credit) or fail to detect the actual failure of the other withdrawal (missed failure).

### Impact Explanation
This is a status/hash misreport that can cause an integrator to credit or refund a user twice, or fail to flag a genuinely failed/stuck withdrawal, matching the "High" impact category (status or hash misreport making an integrator credit or refund twice) as defined in the rules. It does not itself move funds inside the protocol (no signature or intent execution is altered), so it is not a Critical fund-movement bug — the actual on-chain funds go where designated by PoA infra; the error is purely in the SDK's off-chain status-reporting/matching, misleading the caller's bookkeping.

### Likelihood Explanation
Preconditions: a batch withdrawal with ≥2 entries sharing the same `assetId` and different `destinationAddress`/status timing. This is a normal, easily reachable feature (batch withdrawals are documented and supported) requiring no special privilege — any user can construct such a withdrawal set. This is fully repeatable per batch and requires no unusual token/route state beyond same-asset multi-destination withdrawals, which the code comments confirm are a known, unhandled case.

### Recommendation
Disambiguate matching beyond `assetId`: either (a) reject/validate batches with duplicate `assetId` at withdrawal-creation time until the PoA API supports per-withdrawal disambiguation, or (b) match using additional withdrawal-identifying fields (e.g., `destination_address`/amount) returned by the PoA API, or implement the amount-sorting heuristic mentioned in the code comment (sort both local withdrawal params and API results by amount, matching by relative rank) so `index` correctly disambiguates status.

```typescript
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
```
