## Title
`vesting::distribute()` unbounded all-or-nothing shareholder loop can freeze rewards/vested APT for every shareholder if one recipient opts out of unsolicited coin transfers - (File: `aptos-move/framework/aptos-framework/sources/vesting.move`)

### Summary
`aptos_framework::vesting::distribute()` iterates over *all* shareholders in a vesting pool inside a single, un-guarded loop and calls `aptos_account::deposit_coins` for each one, exactly mirroring the FactoryDAO `withdraw()` pattern of "require all transfers in a loop to succeed or the whole exit reverts." `aptos_account::deposit_coins` can abort for a specific recipient (`EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`), and because Move transactions are atomic, that single abort reverts the entire `distribute()` call — blocking payout to every other, unrelated shareholder as well.

### Finding Description
`distribute()` withdraws all unlocked stake as `Coin<AptosCoin>` and then does: [1](#0-0) 

for every shareholder returned by `grant_pool.shareholders()`, unconditionally calling `aptos_account::deposit_coins(recipient_address, share_of_coins)` with no per-recipient isolation, no try/catch (Move has none), and no skip-on-failure logic.

`aptos_account::deposit_coins` can abort for a specific address: [2](#0-1) 

If the recipient's account exists but has never registered a `CoinStore<AptosCoin>` and has called `set_allow_direct_coin_transfers(account, false)` (a completely legitimate, unprivileged, self-service opt-out any account holder can invoke): [3](#0-2) 

then `deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.

Because `distribute()` has no filtering of "eligible" shareholders before entering the loop, and because Move aborts are atomic (the whole transaction, including the earlier `withdraw_stake` from the underlying stake pool, is rolled back), a single shareholder in this state makes `distribute()` — the *only* function that pays out unlocked stake rewards/vested APT to shareholders — permanently unusable for the entire vesting pool, freezing funds for every other shareholder too.

Critically, the module's own comment on `set_beneficiary` shows the developers were aware of exactly this DoS class and patched it for the beneficiary-reassignment path only: [4](#0-3) 

`assert_account_is_registered_for_apt(new_beneficiary)` only checks that a `CoinStore<AptosCoin>` exists at assignment time; it does not, and cannot, prevent an account (whether the original shareholder with no beneficiary set, or a beneficiary that was valid at assignment time but is not required to keep a registered `CoinStore<AptosCoin>` going forward via any other path than deposit) from later toggling `allow_arbitrary_coin_transfers` to `false` if it somehow lacks a registered `CoinStore<AptosCoin>` for AptosCoin. The equivalent guard is missing for:
1. The default case where a shareholder has no beneficiary set (`create_vesting_contract` does not validate that shareholder addresses are registered for direct APT transfers), and
2. Any code path allowing `distribute()` to be triggered without pre-validating every current recipient's eligibility to receive an un-requested coin deposit.

### Impact Explanation
`distribute()` and `terminate_vesting_contract()` (which calls `distribute()` internally) are the sole mechanisms to release unlocked/withdrawn stake rewards and vested principal from a vesting contract's resource account to shareholders: [5](#0-4) 

If any single shareholder enters the "not registered + opted out" state, all shareholders — including entirely uninvolved, honest parties — lose the ability to withdraw their vested APT/rewards indefinitely, since the vesting stake pool keeps accumulating unlocked funds that can never be pulled out via `distribute()`. This is a genuine custody/lock-of-value impact on APT held by a resource-account-controlled staking/vesting pool, matching the "Permanent lock or non-recoverable loss of ... resource-account-held value" custody pivot.

### Likelihood Explanation
Triggering the freeze requires no privileged role: any shareholder can independently call `aptos_account::set_allow_direct_coin_transfers(false)` on their own account provided they are not yet registered for `AptosCoin` — a state that is easy to reach for a shareholder address that was never funded with APT directly (e.g. only ever set up to receive other assets) before being added to a vesting contract's shareholder list. This can be done either by a malicious shareholder deliberately griefing the entire pool, or accidentally by an uninformed user managing their own transfer preferences, without any admin action or governance involvement.

### Recommendation
- Mirror the existing `set_beneficiary` protection at the point recipients enter the distribution loop: prior to looping, filter/validate that each `recipient_address` (shareholder or set beneficiary) is registered to receive AptosCoin (`assert_account_is_registered_for_apt`) or is otherwise eligible for a direct deposit, and enforce the equivalent constraint on `create_vesting_contract`'s shareholder addresses.
- More robustly, make the per-shareholder payout resilient to individual recipient failures: skip (and re-buy-in the shares of) any recipient whose deposit would abort, rather than aborting the whole `distribute()` call, so that the failure of one payout leg can never block payouts to the rest of the pool.

### Proof of Concept
1. Admin creates a vesting contract via `create_vesting_contract` with shareholders `[A, B]`, where `A` is an existing account that has never registered `CoinStore<AptosCoin>`.
2. `A` calls `aptos_account::set_allow_direct_coin_transfers(false)` on their own account (unprivileged, self-service).
3. Time passes; stake accrues rewards; someone calls `vesting::distribute(contract_address)`.
4. Inside `distribute()`'s shareholder loop, when it reaches `A`, `aptos_account::deposit_coins` hits `coin::is_account_registered<AptosCoin>(A) == false` and `can_receive_direct_coin_transfers(A) == false`, aborting with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
5. The abort propagates and reverts the entire `distribute()` transaction, including the earlier `withdraw_stake` call — so `B`'s legitimate share is also blocked, and this remains true for every future call to `distribute()` until `A`'s state changes (which `A` can refuse to do indefinitely).

I was not able to fully trace whether `create_vesting_contract` enforces registration on the initial shareholder list (`aptos-move/framework/aptos-framework/sources/vesting.move:536-630` was only partially inspected), so I could not conclusively confirm whether the "unregistered shareholder from the start" sub-case is blocked at contract-creation time versus only the "later opt-out" sub-case being exploitable; this should be verified directly against the full `create_vesting_contract` function before treating the PoC as complete.

    public entry fun terminate_vesting_contract(admin: &signer, contract_address: address) acquires VestingContract {
        assert_active_vesting_contract(contract_address);

        // Distribute all withdrawable coins, which should have been from previous rewards withdrawal or vest.
        distribute(contract_address);

        let vesting_contract = borrow_global_mut<VestingContract>(contract_address);
        verify_admin(admin, vesting_contract);
        let (active_stake, _, pending_active_stake, _) = stake::get_stake(vesting_contract.staking.pool_address);
        assert!(pending_active_stake == 0, error::invalid_state(EPENDING_STAKE_FOUND));

        // Unlock all remaining active stake.
        vesting_contract.state = VESTING_POOL_TERMINATED;
        vesting_contract.remaining_grant = 0;
        unlock_stake(vesting_contract, active_stake);

        emit(
            Terminate {
                admin: vesting_contract.admin,
                vesting_contract_address: contract_address,
            },
        );
    }
