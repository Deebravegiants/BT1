### Title
Interest accrued while a vault has zero outstanding shares is permanently unaccounted for and later windfalls to the next depositor - ([File: mainnet/contracts/vault/v0-vault-usdc.clar], and the equivalent `accrue`/`convert-to-shares-preview` pair in `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdh.clar`)

### Summary
The external report describes EIP1559 rewards accrued by the Syndicate while `numberOfRegisteredKnots == 0` being unaccounted for by `updateAccruedETHPerShares`, later mis-distributed to whoever registers next. The same "distribution ledger has no slot for value earned while the distribution-key population is zero" bug class exists in the Zest vault's interest-accrual mechanism: interest is continuously accrued against outstanding debt via `total-debt`/`calc-cumulative-debt`, independent of `total-supply` (the `zft` share supply), but the fee/yield distribution logic in `accrue` and `convert-to-shares-preview` divides by `total-supply`, silently producing zero when supply is zero.

### Finding Description
`accrue` computes `debt-delta` from the change in `total-debt` (driven purely by `scaled-principal` and `index`, which are unrelated to `total-supply`) and derives `reserve-inc` (the protocol's fee share of interest) from it: [1](#0-0) 

The treasury mint amount is:
```
treasury-lp = mul-div-down(reserve-inc, total-supply, total-assets-preview - reserve-inc)
```
If `total-supply` (i.e., `ft-get-supply zft`) is `u0` at the time `accrue` runs — which is fully reachable if every liquidity supplier redeems out (`redeem` burns `zft`, unaffected by outstanding `principal-scaled`/`total-borrowed`) while a borrower still has outstanding debt — then `treasury-lp` computes to `u0` regardless of how large `reserve-inc`/`debt-delta` is: [2](#0-1) 

Meanwhile `total-assets`/`total-assets-preview` keep growing by the full `interest = debt - borrowed` component regardless of `total-supply`: [3](#0-2) 

When the next depositor arrives while `total-supply` is still `u0`, `convert-to-shares-preview` short-circuits to a 1:1 mint (`amount` shares) ignoring the vault's existing `total-assets-preview`: [4](#0-3) 

This is the exact identity break the report describes: interest/value *created* (`total-debt` growth) and value *distributed* via shares (`treasury-lp` mint / `convert-to-shares-preview`) go out of sync whenever the share-holder population (`total-supply`) hits zero while the underlying revenue-generating position (`principal-scaled`/`total-borrowed`) is still non-zero. Interest generated in that window is not captured by anyone; whichever depositor re-enters next either (a) gets the accrued interest for free by being minted 1:1 shares against an already-inflated `total-assets-preview` (theft of unclaimed yield from the perspective of who should have earned protocol reserve fees), or (b) if no new deposit occurs, the reserve-fee accrual for that period is permanently lost since `accrue` only mints treasury shares when `total-supply > 0`, and there is no snapshot/carry-forward mechanism (analogous to the missing `else` branch in `updateAccruedETHPerShares`).

### Impact Explanation
This falls under theft/permanent loss of unclaimed yield: the DAO treasury's reserve-factor fee revenue accrued during the zero-supply window is irrecoverably lost (never minted, no accounting variable retains `reserve-inc` for later capture), and/or a future depositor receives value they did not earn because `convert-to-shares-preview` ignores `total-assets-preview` when `total-supply == u0`. Both outcomes match the required impact bar: theft of unclaimed yield / permanent freezing (loss) of unclaimed yield.

### Likelihood Explanation
Reachable without any privileged or DAO action: any borrower can take on debt via `system-borrow` (called by an authorized market contract on behalf of a user) and all suppliers can independently `redeem` their full `zft` balance, driving `total-supply` to zero while `principal-scaled`/`total-borrowed` remain non-zero. Interest continues to accrue purely from elapsed time (`next-index`), so the window need only be non-trivial in duration for a meaningful `debt-delta` to accumulate before the next `deposit` or `accrue` call.

### Recommendation
Track reserve/interest accrued while `total-supply == u0` in a persisted accumulator (e.g., a `pending-reserve` var) and either (a) mint the deferred treasury shares retroactively as soon as `total-supply` becomes non-zero again using a total-assets snapshot taken before the new depositor's shares are computed, or (b) have `convert-to-shares-preview` always base the 1:1 fallback on `total-assets-preview` rather than blindly assuming an empty vault, so pre-existing accrued value is proportionally reflected instead of donated to the next depositor.

### Proof of Concept
1. Supplier A deposits `1000` USDC via `deposit`, minting `1000` `zft` (`total-supply = 1000`).
2. Borrower borrows `900` USDC via `system-borrow` (through the authorized market contract), setting `principal-scaled`/`total-borrowed` accordingly.
3. Supplier A calls `redeem` for their full `1000` `zft` balance; this succeeds because `redeem` only checks `available-assets`/`current-assets`, not outstanding debt exposure, dropping `total-supply` to `u0` while `principal-scaled`/`total-borrowed` remain non-zero.
4. Time passes; each subsequent `accrue` call increases `total-debt` (via `next-index`) so `debt-delta` and `reserve-inc` are non-zero, but `treasury-lp = mul-div-down(reserve-inc, 0, ...) = 0` — no treasury shares are minted, and `total-assets-preview` silently absorbs the full `interest`.
5. Supplier B calls `deposit` with `total-supply` still `u0`: `convert-to-shares-preview` mints `inkind = amount` shares 1:1, ignoring the interest already embedded in `total-assets-preview` from step 4 — Supplier B is now entitled to a proportional claim on that stale interest they never contributed to, and the protocol treasury permanently lost the reserve-factor cut for that period.
