### Title
Duplicate/arbitrary input tokens in `IntentGatewayV2.placeOrder` (Tron variant) let escrow be credited above what the gateway actually receives - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` credits escrow using the attacker-controlled `order.inputs[i].amount` (`_orders[commitment][token] += reducedInputs[i].amount;`) instead of the actually-received/swept token balance, and does not reject duplicate input tokens the way the mainline EVM contract does. This mirrors the `PodUnwrapLocker` root cause: user-supplied, unchecked/duplicated input entries are trusted for accounting while the actual asset movement can diverge, letting escrow be inflated beyond real balances.

### Finding Description
In `evm/src/apps/IntentGatewayV2.sol::placeOrder`, the protocol explicitly guards against duplicate input tokens before crediting escrow: [1](#0-0) 
and separately measures the *actual* balance delta received by the gateway/dispatcher rather than trusting the caller-specified amount: [2](#0-1) 

The Tron fork of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, implements `placeOrder` without either protection. Escrow is credited additively per input index using the caller-supplied `order.inputs[i].amount` (via `reducedInputs[i].amount`), with no check that the token has already appeared in this order: [3](#0-2) [4](#0-3) 

In the predispatch path, the "required amount" and "balance" used to build the sweep `transferCalls` are recomputed per loop index from `IERC20(token).balanceOf(dispatcher)` *before* any of the sweep calls are executed: [5](#0-4) 

If `order.inputs` contains the same token address twice (nothing prevents this here), both iterations read the *same* pre-sweep `balance` for that token and each credits `_orders[commitment][token] += reducedInputs[i].amount` for up to `balance` each — i.e. escrow can be credited for `2×balance` (or more, with more duplicate legs) even though the dispatcher only ever held `balance` of that token. The subsequent `CallDispatcher.dispatch` executes the two identical sweep calls sequentially; `CallDispatcher.dispatch` reverts the whole transaction only if a call reverts: [6](#0-5) 
so the exploit's viability depends on whether the second, duplicate `transfer` call reverts (insufficient dispatcher balance) or the attacker crafts predispatch calldata so the dispatcher actually holds `2×balance` of the token when the sweep executes (e.g., by having the predispatch call itself top up the dispatcher's balance of that specific token, since the predispatch call is fully attacker-controlled calldata dispatched via `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)`). Either way, escrow accounting is decoupled from verified received balances and duplicate-token accumulation is unchecked, which is exactly the `PodUnwrapLocker` bug class: trusting attacker-supplied/duplicated inputs for balance-based bookkeeping.

Once escrow is over-credited, `withdraw()` in the same Tron contract pays out the inflated `_orders[commitment][token]` amount to the beneficiary/filler from the gateway's real token balance, draining funds deposited by other users: [7](#0-6) 

Additionally, `placeOrder` in the Tron variant lacks the `nonReentrant` modifier that the mainline contract has, widening the attack surface for any composed exploit involving the attacker-controlled predispatch call.

### Impact Explanation
An attacker can inflate the escrow ledger for a token beyond what the gateway/dispatcher actually holds, then redeem that inflated escrow via `withdraw()` (triggered through `onAccept`/`RedeemEscrow` or same-chain fill/cancel flows), draining tokens that legitimate users deposited in other orders. This is a direct theft-of-funds / fund-freezing vector on the token bridge/intents escrow, reachable from a single `placeOrder` transaction by any unprivileged user — matching the Sherlock report's impact class exactly.

### Likelihood Explanation
Reachability requires only calling `placeOrder` with a crafted `Order` containing (a) a predispatch call/assets pair and (b) duplicate token entries in `order.inputs`, which is fully within an unprivileged caller's control. The main technical uncertainty is whether the attacker can arrange for the `CallDispatcher` to actually hold enough of the duplicated token at sweep time (via the attacker-supplied `predispatch.call`) without the second identical `transfer` call reverting — this is plausible since the predispatch call is arbitrary attacker calldata executed in the dispatcher's context before the sweep. Given the missing duplicate-token check and lack of balance-verification (both of which the mainline EVM contract added as explicit fixes/tests), this is a credible Medium/High-severity issue in the Tron fork specifically.

### Recommendation
Port the two safeguards already present in `evm/src/apps/IntentGatewayV2.sol` into the Tron variant:
1. Reject duplicate input tokens before crediting escrow (as in `evm/src/apps/IntentGatewayV2.sol:364-373`).
2. Compute escrow credit from the actual balance delta received by the gateway (snapshot-before/after), not from attacker-supplied `order.inputs[i].amount`, as in `evm/src/apps/IntentGatewayV2.sol:260-311`.
3. Add `nonReentrant` to `placeOrder` in the Tron contract to match the mainline implementation.

### Proof of Concept
Conceptual (cannot be fully validated without executing against the Tron contract in a test harness):
1. Attacker deploys/uses a malicious predispatch `call` targeting `_params.dispatcher`, engineered so that after execution the dispatcher holds `balance` of target token `X` (e.g., via a flash-mint/self-funded loop, or simply having the attacker pre-fund the dispatcher with `2×balance` of `X` as a `predispatch.assets` entry, then let the predispatch call be a no-op).
2. Attacker calls `placeOrder` with `order.inputs = [ {token: X, amount: balance}, {token: X, amount: balance} ]`.
3. Both entries pass their individual `if (balance < requiredAmount)` checks (line 429) since `balance` is recomputed identically for each duplicate entry pre-sweep.
4. Escrow accumulates `_orders[commitment][X] += reducedInputs[i].amount` twice (lines 440-441), crediting `2×balance` even though the dispatcher/gateway may only actually retain `balance` (or less) after the sweep completes.
5. Attacker later triggers `withdraw()` (via `RedeemEscrow`/cancel/fill flow) to pull the inflated `_orders[commitment][X]` balance, draining token `X` deposited by other users of the gateway.
