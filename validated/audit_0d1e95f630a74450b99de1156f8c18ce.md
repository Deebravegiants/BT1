### Title
DelegateAction (meta-transaction) signature omits any network/chain identifier, enabling cross-network replay - ([File: core/primitives/src/signable_message.rs], [File: core/primitives/src/action/delegate.rs], [File: runtime/runtime/src/actions.rs])

### Summary
`SignedDelegateAction`/`VersionedSignedDelegateAction` (NEP-366 meta transactions) are signed via `SignableMessage`, whose serialized payload consists only of a `MessageDiscriminant` (a NEP number tag) and the `DelegateAction`/`DelegateActionV2` body itself. [1](#0-0) [2](#0-1) 
Neither the discriminant nor the `DelegateAction` struct contains any network/chain identifier (e.g. mainnet vs. testnet vs. a private/forked network). [3](#0-2) 

### Finding Description
Regular NEAR `SignedTransaction`s are implicitly bound to a specific chain because they include a `block_hash` referencing a recent block, which the runtime validates against the actual chain's recent blocks — this naturally prevents cross-network replay since block hashes are chain-specific and effectively never collide between independent NEAR networks.

`DelegateAction`, however, deliberately replaces this mechanism with a plain `nonce` (checked against the sender's on-chain access-key/gas-key nonce) and a `max_block_height` (a bare integer, not a block hash) as documented in the design rationale. [4](#0-3) 
The signature covers `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key` — none of which distinguishes one NEAR network from another. [3](#0-2) 
The actual signature-verification and validation logic (`apply_delegate_action` → `validate_delegate_action_key`) only checks the signature, `max_block_height` against the local chain's block height, and the nonce/gas-key-nonce against the local access key's stored nonce — all of which are network-local state, not values that are unique across networks. [5](#0-4) [6](#0-5) 

Because a `SignedDelegateAction` is forwarded off-chain to a relayer and then wrapped into a transaction anyone can submit, [7](#0-6) 
if the same `AccountId` and `PublicKey` exist on more than one independent NEAR network (mainnet/testnet/betanet, or any forked/private network sharing genesis state, e.g. after a network split or a testing fork derived from a mainnet snapshot), a `SignedDelegateAction` produced/authorized for use on one network can be resubmitted verbatim on the other network. Verification succeeds there as long as that network's independent access-key nonce for the same public key has not yet reached the signed nonce value and the local block height is still below `max_block_height` — both are plausible, since nonces and heights are small integers reused across independent chains, especially shortly after a fork or when a relayer/testnet mirrors mainnet account state.

### Impact Explanation
A successfully replayed `DelegateAction` causes the runtime to execute the exact same inner actions (`get_actions()`) on the other network with `sender_id` as predecessor, using that network's relayer to pay gas. [8](#0-7) 
This results in unauthorized action execution and unintended state/balance changes on a network the signer never intended (e.g. a transfer, function call, or key/action authorized only for testnet being replayed against the user's mainnet account, or vice versa), which is exactly the class of impact ("unauthorized state or balance change") called for in the analog rules.

### Likelihood Explanation
The exploitation requires the same `(AccountId, PublicKey)` pair to be valid and reachable on more than one NEAR network with the nonce/height windows still open — this is a real but non-trivial precondition (it depends on operational practices such as reusing seed phrases/keys across mainnet and testnet, or forked/derived networks preserving account state). It is not exploitable purely from within a single running chain and depends on external conditions outside of a single node's control, which lowers likelihood relative to a typical single-chain replay bug. This is a design gap rather than an actively demonstrated exploit path within one deployed network.

### Recommendation
Include an explicit network/chain identifier (e.g. `genesis_config.chain_id` or a protocol-defined network tag) inside the `DelegateAction`/`DelegateActionV2` payload that gets signed (or in the `MessageDiscriminant`), and have `apply_delegate_action`/`validate_delegate_action_key` reject any `DelegateAction` whose embedded chain id does not match the runtime's own `chain_id`. This mirrors how the original `SignedTransaction.block_hash` implicitly binds a transaction to one specific chain.

### Proof of Concept
1. Deploy/observe two independent NEAR networks (e.g. mainnet and a forked/private network derived from the same genesis or sharing an account created with the same seed phrase) such that `alice.near` has the same public key and an access key with a nonce not yet advanced past the value used below on Network B.
2. On Network A, Alice signs a `DelegateAction{sender_id: alice.near, receiver_id: ft.near, actions: [ft_transfer(mallory, 1000)], nonce: N, max_block_height: H, public_key: alice_pk}` intending it to only be relayed on Network A.
3. `SignedDelegateAction::sign` produces a signature over `SignableMessage{discriminant: NEP_366, msg: delegate_action}` — no network identifier is included. [9](#0-8) 
4. An attacker who observes this `SignedDelegateAction` (it is transmitted off-chain to a relayer before being included on-chain) wraps the identical bytes into a transaction and submits it to Network B via any relayer.
5. On Network B, `apply_delegate_action` verifies the signature (valid, since it doesn't depend on network), checks `apply_state.block_height <= max_block_height` (satisfied if Network B's height is still below H), and `validate_delegate_action_key` checks the nonce against Network B's independently-tracked access key nonce for `alice.near`/`alice_pk` (satisfied if it has not separately advanced past N). [10](#0-9) [11](#0-10) 
6. The `ft_transfer` action executes on Network B against Alice's balance there, even though Alice only authorized it for Network A.

```rust
impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
}
```

**File:** docs/architecture/how/meta-tx.md (L40-52)
```markdown
With meta transactions, Alice can create a `DelegateAction`, which is very
similar to a transaction. It also contains a list of actions to execute and a
single receiver for those actions. She signs the `DelegateAction` and forwards
it (off-chain) to a relayer. The relayer wraps it in a transaction, of which the
relayer is the signer and therefore pays the gas costs. If the inner actions
have an attached token balance, this is also paid for by the relayer.

On chain, the `SignedDelegateAction` inside the transaction is converted to an
action receipt with the same `SignedDelegateAction` on the relayer's shard. The
receipt is forwarded to the account from `Alice`, which will unpacked the
`SignedDelegateAction` and verify that it is signed by Alice with a valid Nonce
etc. If all checks are successful, a new action receipt with the inner actions
as body is sent to `FT`. There, the `ft_transfer` call finally executes.
```

```markdown
## Limitation: Accounts must be initialized

Any transaction, including meta transactions, must use NONCEs to avoid replay
attacks. The NONCE must be chosen by Alice and compared to a NONCE stored on
chain. This NONCE is stored on the access key information that gets initialized
when creating an account.

Implicit accounts don't need to be initialized in order to receive NEAR tokens,
or even $FT. This means users could own $FT but no NONCE is stored on chain for
them. This is problematic because we want to enable this exact use case with
meta transactions, but we have no NONCE to create a meta transaction.

For the MVP, the proposed solution, or work-around, is that the relayer will
have to initialize the account of Alice once if it does not exist. Note that
this cannot be done as part of the meta transaction. Instead, it will be a
separate transaction that executes first. Only then can Alice even create a
`SignedDelegateAction` with a valid NONCE.
```

```rust
pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // The inner delegate signature is verified below, here on the receiver shard.
    // Meter its verification compute against this shard's `compute_limit`; the gas
    // for it was already burnt at tx conversion on the signer shard. Without the
    // fix the compute is instead mis-charged on the signer shard (which never runs
    // this verify), letting the work escape the receiver shard's budget. See
    // `signature_verification_cost`.
    if apply_state.config.wasm_config.fix_ml_dsa_cost_charging {
        let verify_compute = delegate_signature_verification_compute(
            &apply_state.config.fees,
            signed_delegate_action.delegate_action().public_key(),
        );
        result.compute_usage = safe_add_compute(result.compute_usage, verify_compute)?;
    }
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),
        }
        .into());
        return Ok(());
    }

    validate_delegate_action_key(state_update, apply_state, delegate_action, result)?;
```

```rust
fn validate_delegate_action_key(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    delegate_action: VersionedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let sender_id = delegate_action.sender_id();
    let public_key = delegate_action.public_key();
    // 'sender_id' account existence must be checked by a caller
    let mut access_key = match get_access_key(state_update, sender_id, public_key)? {
        Some(access_key) => access_key,
        None => {
            result.result = Err(ActionErrorKind::DelegateActionAccessKeyError(
                InvalidAccessKeyError::AccessKeyNotFound {
                    account_id: sender_id.clone(),
                    public_key: public_key.clone().into(),
                },
            )
            .into());
            return Ok(());
        }
    };

    // A plain nonce advances the single access_key.nonce and forbids gas keys;
    // a gas key nonce advances one of the gas key's nonces selected by
    // nonce_index.
    let delegate_nonce = delegate_action.nonce();
    let (current_nonce, nonce_update) = match delegate_nonce {
        TransactionNonce::Nonce { .. } => {
            if access_key.gas_key_info().is_some() {
                result.result = Err(ActionErrorKind::DelegateActionAccessKeyError(
                    InvalidAccessKeyError::DelegateActionRequiresNonGasKey,
                )
                .into());
                return Ok(());
            }
            (access_key.nonce, DelegateNonceUpdate::AccessKey)
        }
        TransactionNonce::GasKeyNonce { nonce_index, .. } => {
            let Some(gas_key_info) = access_key.gas_key_info() else {
                result.result = Err(ActionErrorKind::DelegateActionAccessKeyError(
                    InvalidAccessKeyError::DelegateActionRequiresGasKey,
                )
                .into());
                return Ok(());
            };
            if nonce_index >= gas_key_info.num_nonces {
                result.result = Err(ActionErrorKind::DelegateActionInvalidNonceIndex {
                    nonce_index,
                    num_nonces: gas_key_info.num_nonces,
                }
                .into());
                return Ok(());
            }
            // The index is range-checked above and gas keys initialize every
            // nonce row at creation, so a missing row is inconsistent state.
            let current_nonce =
                get_gas_key_nonce(state_update, sender_id, public_key, nonce_index)?.ok_or_else(
                    || {
                        StorageError::StorageInconsistentState(format!(
                            "gas key nonce row missing for {} {} at in-range index {nonce_index} (num_nonces {})",
                            sender_id, public_key, gas_key_info.num_nonces,
                        ))
                    },
                )?;
            (current_nonce, DelegateNonceUpdate::GasKey { nonce_index })
        }
    };

    if delegate_nonce.nonce() <= current_nonce {
        result.result = Err(ActionErrorKind::DelegateActionInvalidNonce {
            delegate_nonce: delegate_nonce.nonce(),
            ak_nonce: current_nonce,
        }
        .into());
        return Ok(());
    }
```
