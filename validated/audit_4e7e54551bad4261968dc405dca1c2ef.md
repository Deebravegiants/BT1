### Title
Unbacked EVM-side mint from wrong decimal-scaling direction in `convert_to_erc20`/`convert_to_balance` when a registered asset has more decimals than the paired chain's ERC20 precision - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token`'s decimal-conversion helpers assume the ERC20 side always has *more or equal* decimals than the local Substrate asset. They compute the scaling exponent with `erc_decimals.saturating_sub(local_decimals)`, which silently clamps to `0` whenever `local_decimals > erc_decimals`. In that case `send()` embeds the *raw, unscaled* local-decimal amount into the cross-chain message as if it were already in ERC20 (lower) precision, and the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract mints/releases that raw integer verbatim. This causes an unbacked over-mint on the EVM side by a factor of `10^(local_decimals - erc_decimals)`, exactly the same class of bug as the reference report: a scaling factor computed with the wrong assumption about which side is more precise (there: `1e28` vs the real `1e18` for `CNOTE`; here: an unconditional `erc_decimals - local_decimals` that ignores the opposite direction).

### Finding Description
The two conversion helpers are: [1](#0-0) 

`convert_to_erc20(value, erc_decimals, local_decimals)` multiplies by `10^(erc_decimals.saturating_sub(local_decimals))`. This is only correct for the case `erc_decimals >= local_decimals` (e.g. the documented BRIDGE token: local 12 decimals on nexus vs EVM 18 decimals, see `evm/src/apps/BridgeToken.sol` comment). When a registered asset instead has `local_decimals > erc_decimals` for a given destination chain (a legitimate, explicitly supported configuration per the pallet's own README: "Decimals between this chain and each remote chain may differ"), `erc_decimals.saturating_sub(local_decimals)` clamps to `0`, so the multiplier becomes `10^0 = 1` instead of the required division by `10^(local_decimals - erc_decimals)`.

This function is invoked directly from the `send` extrinsic, callable by any signed account: [2](#0-1) 

The resulting `erc20_amount` is placed into the dispatched `Message.amount` and delivered cross-chain via ISMP. On the EVM side, `HyperFungibleToken.onAccept` mints this value verbatim with no independent decimal check: [3](#0-2) 

So for an asset with, say, `local_decimals = 18` registered against a destination chain configured with `erc_decimals = 6` in `Precisions`, escrowing/burning `1` whole local token (`1e18` raw units) produces `erc20_amount = 1e18` unchanged (should have been divided down to `1e6`). The EVM contract, whose own token also uses 6-decimals-equivalent accounting for this pairing, mints `1e18` raw units — `1e12` times more tokens than were ever escrowed on the source chain. This is an unbacked mint reachable from a single signed `send` extrinsic with no privileged or malicious actor required; the decimals mismatch is a normal registration outcome, not an admin attack.

The reverse helper, `convert_to_balance`, has the mirrored flaw for `on_accept` (`erc_decimals < local_decimals` clamps to `0`), which instead under-credits the local balance — a fund-freezing effect rather than an unbacked mint, but the same root cause. [4](#0-3) 

### Impact Explanation
The `send` → `convert_to_erc20` → EVM `onAccept`/`_mint` path allows unbacked minting of the wrapped/bridged token on the destination EVM chain whenever a registered asset's local decimals exceed the configured `erc_decimals` for that destination. Since the EVM contract's supply is expected to always be backed 1:1 by the pallet's escrow/burn accounting (per the contract's own documentation: "the supply of this token is always backed by the pallet's escrow account"), this breaks that invariant and lets a user mint tokens on the destination chain far in excess of what they escrowed on the source chain — a critical loss for the protocol/liquidity backing that token, and in the `WrappedHyperFungibleToken` case, a direct drain of the underlying ERC20/WETH reserve held by the contract.

### Likelihood Explanation
This does not require a malicious admin: decimal mismatches between chains are explicitly anticipated and supported by design (`Precisions` storage exists precisely because "decimals ... may differ"), so any token registered with a higher-decimals local representation than its EVM counterpart's configured precision triggers the bug on the very first `send` call. No special privilege beyond a normal signed extrinsic is needed to exploit it once such a token is registered.

### Recommendation
Compute the conversion using explicit sign-aware scaling instead of `saturating_sub`, e.g.:
```rust
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```
and symmetrically for `convert_to_balance`. Add test coverage for the `local_decimals > erc_decimals` case (currently only `18/10`-style, i.e. `erc_decimals > local_decimals`, is exercised in `modules/pallets/testsuite/src/tests/pallet_hyper_fungible_token.rs`).

### Proof of Concept
1. Runtime configures an asset in `register_token` with e.g. 18 local decimals, and sets `Precisions::<T>::insert(asset_id, dest_chain, 6)` (a 6-decimal EVM counterpart contract deployed as `HyperFungibleToken`).
2. A user calls `send` with `amount = 1_000_000_000_000_000_000` (1 whole token, 18 decimals). The pallet burns/escrows exactly that.
3. `convert_to_erc20(1e18, 6, 18)` computes `6u8.saturating_sub(18) = 0`, so `erc20_amount = 1e18 * 10^0 = 1e18` (unscaled), instead of the correct `1e18 / 10^12 = 1e6`.
4. The dispatched `Message.amount = 1e18` is delivered to `HyperFungibleToken.onAccept` on the EVM chain, which calls `_mint(beneficiary, 1e18)` — minting `1,000,000,000,000` (1 trillion) whole tokens' worth of raw units instead of `1`, an unbacked mint of `10^12`x the escrowed amount.

///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount

/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
