Audit Report

## Title
Observable Response Discrepancy on Admin/API Login Enables Email Enumeration - (File: core/web/sessions_controller.go, core/sessions/localauth/orm.go)

## Summary
The `/sessions` login endpoint returns the raw underlying authentication error message to the unauthenticated caller. Depending on whether the submitted email exists, the response body differs (sqlx "no rows"-style error for unknown email vs. `"Invalid password"` for a known email with wrong password), allowing an unprivileged actor to enumerate valid Chainlink node user accounts.

## Finding Description
`SessionsController.Create` forwards the authentication provider's error verbatim to the HTTP client via `jsonAPIError(c, http.StatusUnauthorized, err)` [2](#0-1) . `jsonAPIError` calls `err.Error()` directly into the JSON response body with no generalization or sanitization [1](#0-0) .

For the local auth provider, `CreateSession` first calls `FindUser`, and if that fails (unknown email → `sql.ErrNoRows` propagated from `findUser`'s `GetContext` call), it returns that raw DB error directly [3](#0-2) [4](#0-3) . If the user is found but the password is wrong, it instead returns the distinct string `"Invalid password"` [5](#0-4) . These two error paths are textually distinguishable in the client-visible JSON response, creating an oracle for account existence. The LDAP provider's local-admin fallback path (`localLoginFallback`) has the identical pattern, returning distinct `"invalid email"` vs `"invalid password"` errors [6](#0-5) .

No existing middleware or wrapper normalizes these errors before they reach the client; `jsonAPIError` passes `err.Error()` through unmodified unless the error is a `*models.JSONAPIErrors` type, which these are not.

## Impact Explanation
This is a username/email enumeration vulnerability (CWE-204, Observable Response Discrepancy) reachable by any unauthenticated network client on the node's admin login endpoint (`POST /sessions`). An attacker can iterate candidate emails to determine which correspond to real Chainlink node operator accounts, which become higher-value targets for credential stuffing, phishing, or brute-force attacks against the admin API. This is a confidentiality-only disclosure (account existence), not an authentication/authorization bypass or fund-movement issue, so it maps to a lower-severity information-disclosure category within node API authentication concerns rather than a critical bypass.

## Likelihood Explanation
High likelihood of exploitation in terms of reachability: the endpoint requires no authentication and is exposed via the unauthenticated route group, and differing error strings are returned in the JSON body verbatim, requiring no timing analysis or advanced technique — just comparing two response bodies. The existing test suite already exercises "incorrect pwd" and "incorrect email" cases separately but only asserts status code ≥ 400, not message parity, confirming the discrepancy is untested/unhandled [7](#0-6) .

## Recommendation
Normalize error paths in `orm.CreateSession` (and the LDAP `localLoginFallback` equivalent) so "user not found" and "password mismatch" produce an identical generic error (e.g., `"invalid credentials"`) before returning to `SessionsController.Create`. Apply constant-time behavior across both branches to avoid replacing the message-based side channel with a timing-based one. Additionally, avoid passing raw provider errors into `jsonAPIError`; map to a single generic unauthorized message at the controller boundary.

## Proof of Concept
1. `POST /sessions` with `{"email":"unknown@nowhere.test","password":"x"}` → response body contains the raw `FindUser`/DB "no rows" style error.
2. `POST /sessions` with `{"email":"<real-admin-email>","password":"wrong"}` → response body contains `"Invalid password"`.
3. Compare the two response bodies — the differing error text lets an attacker confirm the second email belongs to a valid, registered node user. This can be verified by extending `TestSessionsController_Create` in `core/web/sessions_controller_test.go` (which already has separate "incorrect pwd" and "incorrect email" test cases) to assert on response body content rather than only status code.

func (l *ldapAuthenticator) localLoginFallback(ctx context.Context, sr sessions.SessionRequest) (sessions.User, error) {
