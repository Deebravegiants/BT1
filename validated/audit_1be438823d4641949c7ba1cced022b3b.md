## Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC that `Utils::HmacValidator.validate` checks in `Registry.process` authenticates the *body bytes* only. The `shop-domain` header, which is read separately via `shop` and passed straight into `WebhookMetadata.shop` for the app's handler, is never part of the signed material. This breaks the intended binding: `HMAC(secret, signed_bytes) == HMAC(secret, signed_bytes)` should imply `shop_header == shop_that_actually_sent(signed_bytes)`, but the gem only proves the body was signed with the app's secret — it proves nothing about which shop the header claims to be.

### Finding Description
`Utils::HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the supplied `hmac`. [1](#0-0) 
For webhook requests, `to_signable_string` is defined as just the raw body: [2](#0-1) 
Meanwhile `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the signed payload: [3](#0-2) 
`Registry.process` validates only the HMAC of the body, then forwards the untrusted, unsigned `shop` header directly into the `WebhookMetadata` struct passed to the app's registered handler: [4](#0-3) 
`WebhookMetadata.shop` is a plain `String` field with no further validation performed by the gem before the handler consumes it: [5](#0-4) 
The gem's own documentation confirms this is the intended app-facing contract — `data.shop` is presented as the authenticated shop identity for the webhook and used to route tenant-scoped work (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`): [6](#0-5) 

Because the client_secret used to compute this HMAC is shared per-app across every installed shop (it is the app's `client_secret`, not a per-shop secret), any tenant with the app installed can obtain genuinely-signed webhook deliveries whose body content is attacker-influenced or predictable (e.g. compliance/GDPR webhooks, or topics with attacker-controllable/duplicable fields), and replay that valid `(body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value. Since the header is outside the signed bytes, `Utils::HmacValidator.validate` still returns `true`, and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from a victim shop while carrying attacker-supplied body content.

### Impact Explanation
This breaks the identity binding `shop_header == shop_that_actually_authorized(signed_bytes)` that `WebhookHandler` implementations are documented to rely on for tenant-scoped actions (job queuing, per-shop record updates, etc., as shown in the gem's own usage docs). An attacker who controls one tenant of a multi-tenant app can cause the app to process/act on webhook data under another shop's identity — a cross-tenant access primitive within the boundaries of the gem's public webhook-processing API (`Registry.process`), satisfying the Critical "cross-tenant access" impact criterion.

### Likelihood Explanation
Requires only that the attacker operate a shop with the app installed (an unprivileged position from the perspective of any other tenant) and be able to submit crafted HTTP requests to the app's public webhook endpoint — no access token, `api_secret_key`, or privileged account for the *target* shop is needed. Exploitability depends on the attacker being able to produce or observe a validly-signed `(body, hmac)` pair whose `shop-domain` they then swap; because signing only covers the body, this is possible whenever body content is attacker-influenced, predictable, or reused across shops (e.g. empty/standard bodies for certain topics), which the gem does nothing to prevent.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed material, or otherwise verify the header out-of-band, e.g.: incorporate the `shop-domain` header into `to_signable_string` before hashing, or have `Registry.process` cross-check `request.shop` against an app-controlled record of which shop the webhook subscription/session actually belongs to (analogous to how `LibSilo.stalkReward` in the referenced report fixes an unguarded field by routing it through the correct, bound calculation) rather than trusting the raw header value.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers/receives a legitimately Shopify-signed webhook for a topic whose body is empty or fully attacker-controlled (many compliance/webhook topics send `{}` or predictable JSON), yielding a valid `(raw_body, hmac)` pair signed with the app's shared `client_secret`.
2. Attacker POSTs to the app's webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request#hmac`/`to_signable_string` only cover `raw_body`, so `Utils::HmacValidator.validate` succeeds.
4. `Registry.process` builds `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)` and invokes the app's handler, which performs tenant-scoped work as if it legitimately originated from `victim-shop.myshopify.com`.
