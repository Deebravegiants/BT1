### Title
Precision-conversion underflow in `pallet-hyper-fungible-token` causes unbacked minting/incorrect crediting when a registered token's EVM decimals are lower than its local decimals - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`convert_to_balance`/`convert_to_erc20` in `pallet-hyper-fungible-token` scale amounts between an EVM contract's decimals (`erc_decimals`) and the local asset's decimals (`local_decimals`) using `erc_decimals.saturating_sub(local_decimals)` as the scaling exponent. This is only correct under the unstated assumption `erc_decimals >= local_decimals`. When a token is registered with `erc_decimals < local_decimals` (a legitimate, plausible configuration — e.g. an EVM token with 6 decimals such as USDC paired with a local asset configured with 12 or 18 decimals), `saturating_sub` clamps to `0`, so no scale-down division occurs on receipt and no scale-up multiplication occurs on send. This silently mis-prices every cross-chain transfer for that asset pair by orders of magnitude, analogous to the GoonFi config/logic bug that caused pool mispricing.

### Finding Description
`convert_to_balance` (called from `on_accept`/`on_timeout` in `modules/pallets/hyper-fungible-token/src/module.rs`) computes:
```
dec_str = (value / 10^(erc_decimals.saturating_sub(local_decimals))).to_string()
``` [1](#0-0) 

and `convert_to_erc20` (used in the `send` extrinsic) computes the inverse:
```
U256::from(value) * 10^(erc_decimals.saturating_sub(local_decimals))
``` [2](#0-1) 

Both directions are keyed on the *same* asymmetric exponent, which is only valid if `erc_decimals >= local_decimals` everywhere. `erc_decimals` for a given `(AssetId, StateMachine)` pair is stored in `Precisions` and is set entirely by whatever value `register_token`/`update_token` (via `CreateOrigin`) supplies for that chain's `ChainConfig.decimals`, with no validation against the local asset's own decimals: [3](#0-2) [4](#0-3) 

In `on_accept` (the handler reached by *any* relayer submitting a legitimate ISMP POST from a registered `HyperFungibleToken`/`BridgeToken` EVM contract), the receive path is:
```
let decimals = ...; // local asset decimals
let erc_decimals = Precisions::<T>::get(...);
let amount = convert_to_balance(U256::from_big_endian(&message.amount...), erc_decimals, decimals)?;
``` [5](#0-4) 

If `erc_decimals < decimals` (e.g. EVM token 6 decimals, local asset 18 decimals), `saturating_sub` yields `0`, so `amount` is minted/transferred **without any upscaling**, i.e. the raw ERC20-precision integer is credited 1:1 as if it were already in the local asset's 18-decimal units — a ~10^12x under-scaling on the *destination* side relative to what the sender actually locked/burned on the EVM side (the opposite failure mode also exists: on the EVM→send direction the amount would be *under-scaled outward*, and vice versa depending on which asset triggers the mismatch). Either direction breaks the 1:1 backing invariant the module's own doc comments assert (e.g. `BridgeToken.sol` explicitly documents "the pallet scales by 10^6 in both directions" as a hard-coded assumption that decimals are ordered a specific way) [6](#0-5) , and no runtime check enforces that assumption for any token registered through the generic `register_token` path.

### Impact Explanation
For any asset pair registered with `erc_decimals < local_decimals`, incoming cross-chain transfers are credited at the wrong scale — either massively over-crediting the beneficiary (unbacked mint / drain of the pallet's escrowed balance for native assets, or unbacked mint for non-native assets) or massively under-crediting them, depending on which side of the transfer hits the clamped exponent. Because native assets use the escrow/custody model (`pallet_account()` holds locked funds) [7](#0-6) , an over-crediting mis-scale directly drains the escrow account for every other user's locked collateral, i.e. concrete theft of escrowed funds — the same shape of loss (mispriced conversion exploited atomically for real value) as the GoonFi incident. This is High impact for any misconfigured pair, since it is exploitable by any ordinary user calling `send` on the paired EVM `HyperFungibleToken`/`BridgeToken` contract and is not gated by any privileged role at execution time.

### Likelihood Explanation
The trigger condition depends only on the *decimals values* chosen for a registered token pair, which is a normal configuration input (not a governance compromise or malicious admin scenario) — many real ERC20 tokens use 6 or 8 decimals while Substrate assets commonly default to 10, 12, or 18 decimals, making `erc_decimals < local_decimals` a realistic, easy-to-hit configuration rather than an edge case. Once such a pair is registered, exploitation requires only a single ordinary `send` transaction and a normal relayer delivery — no special privileges, timing, or governance action. This matches the required entry point ("unprivileged... token bridger" reaching "token bridge mint/burn").

### Recommendation
Replace the asymmetric `saturating_sub`-based scaling in `convert_to_balance`/`convert_to_erc20` with a signed/bidirectional scale factor (or explicitly reject registration/messages where `erc_decimals < local_decimals` is not intended), and add an explicit invariant check in `register_token`/`update_token` and in `on_accept`/`on_timeout` that fails closed instead of silently truncating the exponent to zero, on both the pallet and the mirrored EVM `HyperFungibleToken.sol`/`BridgeToken.sol` contracts.

### Proof of Concept
1. Governance (or whoever holds `CreateOrigin`) registers a new non-native asset `X` with local decimals `18` (e.g. an `pallet-assets` asset created with 18 decimals) and, for `StateMachine::Evm(N)`, sets `ChainConfig.decimals = 6` (matching a real 6-decimal ERC20 like USDC) via `register_token`, populating `Precisions[X][Evm(N)] = 6`. [3](#0-2) 
2. A user calls `HyperFungibleToken.send(...)` on the EVM contract for asset `X`, burning `1_000_000` raw units (i.e. `1.0` token at 6 decimals).
3. The relayer delivers the POST request; `on_accept` runs with `erc_decimals = 6`, `decimals (local) = 18`, so `erc_decimals.saturating_sub(decimals) = 0`. [8](#0-7) 
4. `convert_to_balance` returns `1_000_000` **unscaled** as the local balance to mint/transfer, i.e. `0.000000000001` of what a correctly-scaled `18`-decimal amount of `1.0` token should be (`1_000_000_000_000_000_000`) — an under-credit of 12 orders of magnitude in this direction, or conversely a massive over-credit if the decimal relationship is reversed for the escrow-holding side. Either direction demonstrates the amount minted/transferred to the beneficiary does not match the value actually locked/burned on the source chain, breaking the bridge's backing invariant.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
