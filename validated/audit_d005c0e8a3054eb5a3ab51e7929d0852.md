### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only. The `shop` (from the `shopify-shop-domain` / `x-shopify-shop-domain` header) that identifies *which tenant* the webhook belongs to is never included in the signed material. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then unconditionally trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler, so an attacker who can obtain any one validly-signed body/HMAC pair (e.g. by installing the app on their own store and receiving a real webhook) can replay that exact body+HMAC while substituting the `shop-domain` header for a victim shop, producing a payload that passes signature validation but is falsely attributed to the victim tenant.

### Finding Description
The binding that should hold is:

`hmac == HMAC(secret, body_bytes_bound_to_shop)`

but the actual implementation only enforces:

`hmac == HMAC(secret, body_bytes)`

- `VerifiableQuery#to_signable_string` is required to return the exact bytes the HMAC certifies [1](#0-0) .
- `Webhooks::Request#to_signable_string` implements this by returning only `@raw_body` [2](#0-1) .
- `Webhooks::Request#shop` is read straight from an attacker-controllable HTTP header with no cryptographic tie to the body: [3](#0-2) .
- `Utils::HmacValidator.validate` verifies exactly `verifiable_query.to_signable_string` (i.e., the body) against the secret, and nothing else [4](#0-3) .
- `Registry.process` calls the validator and, on success, immediately forwards `request.shop` to the handler with no additional check that it matches the shop the body/signature actually originated from: [5](#0-4) .

Because the app's `api_secret_key` is shared across every shop that installs the app, any two webhook deliveries with byte-identical bodies (which is common — many Shopify webhook payloads, e.g. `app/uninstalled`, GDPR redact topics, or any topic with a fixed/predictable body shape, do not embed the shop domain inside the JSON body itself) will produce byte-identical HMAC values regardless of which shop triggered them. An unprivileged attacker only needs to:
1. Install the target app on their own store (no special privilege — any internet user can do this) and capture one legitimately delivered webhook (raw body + `x-shopify-hmac-sha256` header).
2. Replay that exact body and HMAC to the app's webhook endpoint, but with the `shop-domain` header rewritten to the victim shop's domain.

`Utils::HmacValidator.validate` will pass because it never looks at the header, and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` is the forged victim domain [6](#0-5) , causing the app's business logic (which trusts `shop` as documented, since it is the field Shopify webhooks provide precisely for tenant attribution) to act on the wrong tenant.

### Impact Explanation
This breaks the equality `shop authenticated == shop the signed content was produced for`, letting an attacker cross a tenant boundary using data they legitimately possess for their own shop, and impersonate a delivery from a shop they do not control. Depending on the topic and the app's handler logic (uninstall cleanup, data redaction/GDPR compliance webhooks, order/customer processing), this can cause cross-tenant state corruption or unauthorized actions attributed to another merchant — matching the "cross-tenant access" High/Critical-class impact category, since the gem itself provides no mechanism to bind the header-derived `shop` to the HMAC-verified body.

### Likelihood Explanation
Likelihood is moderate-to-high: no secrets, tokens, or privileged access are required — only the ability to install the target app once (a normal, unprivileged action) and send a crafted HTTP POST with a spoofed header to the target's public webhook endpoint. The attack is most directly exploitable for webhook topics whose body content is shop-independent or attacker-influenceable (fixed-shape or empty bodies), which are common among mandatory compliance webhooks.

### Recommendation
Bind the shop identity into what is HMAC-verified before trusting it, or independently authenticate the `shop` value against the app's own session/shop store before processing:
- At minimum, `Webhooks::Registry.process` should verify that `request.shop` corresponds to a shop with an active, previously-established session/installation in the app's own storage (which the app already must possess to have `access_token`s), rejecting webhooks for shops the app cannot independently corroborate.
- Consider documenting explicitly in `lib/shopify_api/webhooks/request.rb` / `registry.rb` that `shop` is unauthenticated relative to the HMAC and must not be trusted for tenant attribution without a secondary lookup, since the current API surface (`WebhookMetadata#shop` being handed straight to the handler after `HmacValidator.validate` succeeds) invites the assumption that it is trustworthy once HMAC validation passes.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled store; receive one legitimate webhook delivery, e.g. `app/uninstalled` with body `{}` and header `x-shopify-hmac-sha256: <valid_hmac_for_body>`.
2. Compute/observe that `HmacValidator.validate` only hashes `@raw_body` [2](#0-1)  — the same body+HMAC pair is valid for any `shop-domain` header value.
3. Replay: `POST /webhooks` with the captured body and HMAC unchanged, but headers set to
   `x-shopify-topic: app/uninstalled`, `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` which returns `true` (body/HMAC pair is valid for the shared secret) [7](#0-6) , then dispatches the handler with `shop: "victim-shop.myshopify.com"` [6](#0-5) , causing the app to process an uninstall/redact/etc. action for a shop the attacker never installed on or controls.

If you need to confirm the exact `WebhookMetadata` implementation, a full Devin session with filesystem access would be needed to verify this last detail.
