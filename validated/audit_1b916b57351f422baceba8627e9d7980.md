### Title
Webhook shop/topic/webhook_id headers are not bound to the HMAC signature, enabling cross-tenant webhook impersonation - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a request as authentically originating from Shopify for a given shop solely because `Utils::HmacValidator.validate(request)` succeeds. However, the HMAC is computed only over the raw request body; the `shop-domain`, `topic`, `webhook-id`, and `api-version` header values used to identify the tenant and route the payload are never included in the signed data.

### Finding Description
`HmacValidator.validate` calls `verifiable_query.to_signable_string`, and for webhooks `Request#to_signable_string` returns only `@raw_body` [1](#0-0) . The HMAC itself is parsed from the `hmac-sha256` header [5](#0-4) , and the tenant-identifying fields `shop`, `topic`, `webhook_id`, and `api_version` are read from separate headers with no cryptographic tie to the signed body [6](#0-5) .

`Registry.process` performs exactly one check — `Utils::HmacValidator.validate(request)` — before dispatching `request.shop`, `request.topic`, `request.parsed_body`, and `request.webhook_id` straight to the consumer's handler [3](#0-2) . Because `shop` is not part of the signed payload, the binding "the shop the HMAC authenticates" == "the shop the handler stores/acts on" does not hold. Any two values of `X-Shopify-Shop-Domain` are equally valid for the same `(body, hmac)` pair, since the signature never depends on that header.

The documentation instructs developers to trust exactly this unauthenticated field for tenant-scoped side effects, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [7](#0-6) , and states that `process` "will verify the request did indeed come from Shopify" [8](#0-7) , which overstates what the HMAC check actually proves — it proves the body is untampered for *some* shop using this app's secret, not that the accompanying shop header is authentic.

### Impact Explanation
An unprivileged internet user who installs the target app on a shop they control (a normal, unprivileged app-install flow requiring no leaked credentials) will legitimately receive HMAC-signed webhook deliveries for their own shop. Because the signature covers only the body, the attacker can replay that exact `(raw_body, hmac-sha256)` pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Webhook-Id`/`X-Shopify-Topic`) header to name a victim shop. `HmacValidator.validate` still passes because it never inspects those headers, and the handler receives `WebhookMetadata` claiming the victim's shop with attacker-chosen body content — a cross-tenant write/impersonation, matching the pattern of "the shop authenticated ≠ the shop stored/acted on."

### Likelihood Explanation
Webhook endpoints are public HTTP(S) endpoints with no additional authentication by design (per `docs/usage/webhooks.md`), and any user can obtain a legitimately signed webhook for a shop they themselves install the app on, since app installation itself requires no privileged credential. Crafting a replay with modified headers is straightforward with standard HTTP tooling.

### Recommendation
Bind the tenant-identifying headers into the signed material used for verification, or otherwise cryptographically tie `shop`, `topic`, and `webhook_id` to the HMAC (e.g., include them in the string signed/verified, or require the consuming application to cross-check the delivered shop against a locally known set of shops that this app is actually installed on, verified independently of the header). At minimum, update the documentation to clarify that `HmacValidator`/`Registry.process` only proves body integrity, not the authenticity of the `shop`, `topic`, or `webhook_id` headers, so integrators do not use them as an untrusted tenant key without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (ordinary unprivileged install) and registers a webhook topic, e.g. `orders/create`.
2. Shopify delivers a legitimate webhook to the app's public callback URL with headers including `X-Shopify-Hmac-Sha256: <hmac>` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, and some JSON body `B`.
3. Attacker captures `(B, hmac)` from this delivery (it is delivered to infrastructure the attacker controls, e.g. their own ngrok/webhook receiver if they can point the app's webhook path there, or simply from their own captured HTTP request/response logging).
4. Attacker sends a new POST request directly to the app's public webhook route with the same raw body `B` and the same `X-Shopify-Hmac-Sha256` value, but with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `hmac` still matches `B` under the app's secret [5](#0-4) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which returns `true` because it only checks `B` against the secret [9](#0-8) .
6. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)` [10](#0-9) , causing the app to act on attacker-controlled data under the victim shop's tenant identity.
