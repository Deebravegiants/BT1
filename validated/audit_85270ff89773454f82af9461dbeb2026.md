Based on the evidence gathered, the strongest analog to the JUMPI bug class (a security-relevant field being acted upon without being covered by the check meant to authenticate it) is in the webhook processing path, where the shop attribution used to route webhook data is not covered by the HMAC that is supposed to authenticate the request.

### Title
Webhook shop attribution is not covered by HMAC authentication, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop-domain` header to attribute the payload to a tenant. Because the `api_secret_key` is shared across every shop that has installed the app, any shop that installs the app can compute a valid HMAC for an arbitrary body and then set the `shop-domain` header to a different (victim) shop, breaking the binding between "HMAC-verified sender" and "shop the data is attributed to."

### Finding Description
`Utils::HmacValidator.validate` is invoked in `Registry.process` before any handler runs: [1](#0-0) . The value it validates comes from `VerifiableQuery#to_signable_string`, which for a webhook request is only the raw HTTP body: [2](#0-1) . The `shop` value handed to the webhook handler, however, is read directly from the `shop-domain` header, which is never part of the signed string: [3](#0-2)  and [4](#0-3) .

The equality that should hold is:
`shop_bound_by_hmac == shop_used_for_tenant_attribution`

but in reality:
`shop_bound_by_hmac` = "any shop whose app installation shares this app's single `api_secret_key`" (i.e., unconstrained — the HMAC only proves "some installer of this app produced this body", not "this specific shop produced this body")
`shop_used_for_tenant_attribution` = whatever string is in the `x-shopify-shop-domain` / `shopify-shop-domain` header, which is fully attacker-controlled and outside the HMAC.

Because the same `api_secret_key` is used for every shop of a given app, a low-privilege attacker who legitimately installs the app on their own shop can:
1. Receive/produce genuine webhook bodies for their own shop (or fabricate arbitrary JSON bodies) and compute a valid HMAC using the shared secret (attacker only needs their own valid installation — not the victim's credentials).
2. Send a POST to the app's webhook endpoint with that valid HMAC but with the `shop-domain` header set to a victim shop's domain.
3. `Registry.process` passes HMAC validation (it never checked the header) and calls the handler with `WebhookMetadata.new(shop: request.shop, ...)`, i.e., the victim's domain, together with attacker-chosen body content.

This is a genuine architectural gap in this gem's webhook trust model, not merely a downstream app's failure to follow documented API — the gem's own `Request`/`Registry` classes define what "authenticated shop" means for webhook consumers, and they define it incorrectly (header instead of the signed payload).

### Impact Explanation
Any host application that uses `request.shop` (or the `shop` field of `WebhookMetadata`) to decide which tenant's data to update, look up sessions, or dispatch access-token-scoped side effects — this is the sanctioned way to consume `Registry.process`'s handler callback — can be tricked into acting on behalf of a shop the attacker does not own. This is a cross-tenant confusion vulnerability: data intended for/about one merchant can be attributed to and processed as belonging to another merchant, satisfying the "cross-tenant access" bucket in scope.

### Likelihood Explanation
Exploitation requires only an ordinary, unprivileged install of the app by the attacker on their own shop (a normal, unprivileged action any internet user can take by installing a public app) — no `access_token`, no `client_secret`, no privileged account, and no interception of TLS traffic is needed, since the `api_secret_key` is shared across all installs and the attacker can locally compute a valid HMAC for a body they construct.

### Recommendation
Bind the shop identity into the HMAC-covered material (e.g., include the `shop-domain` header, or the per-shop token, in the signable string / validation), or otherwise cross-check the header-derived shop against a value that is cryptographically tied to that specific shop (such as validating against a stored, previously-registered webhook endpoint/shop pairing) before trusting `request.shop` for tenant attribution in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, obtaining knowledge that the app's `api_secret_key` is shared (attacker does not need to know the value, just that any request they can get accepted from Shopify — or any body they choose to sign with, if they can obtain a valid HMAC from Shopify's own webhook delivery for their shop — will validate).
2. Attacker captures (or triggers, e.g., by placing an order in their own shop) a legitimate webhook delivery: raw body `B`, HMAC `H = HMAC_SHA256(secret, B)`, and original headers including `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the identical body `B` and HMAC `H` to the app's webhook endpoint but replaces the header with `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in [5](#0-4)  succeeds because it only checks `B` against `H`, ignoring headers.
5. `Registry.process` invokes the registered handler with `shop: "victim-shop.myshopify.com"` and the attacker's body content [4](#0-3) , causing the host application to process/store data under the wrong tenant.
