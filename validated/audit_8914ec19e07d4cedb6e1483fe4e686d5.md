## Title
Webhook HMAC signs only the raw body, not the `shop-domain` header, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable string from the raw HTTP body alone, while the `shop` (tenant identity) is read from an unsigned header. `ShopifyAPI::Webhooks::Registry.process` validates only that HMAC before dispatching the request to the app's handler with the (unauthenticated) `shop` value attached. Since a public app's `client_secret` is shared across every shop that installs it, any merchant who legitimately receives one valid `(body, hmac)` pair for their own shop can replay that exact pair to the app's webhook endpoint while swapping the `x-shopify-shop-domain`/`shopify-shop-domain` header to a victim shop, and the request will still pass validation.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop` is read directly from a header that is never included in the signed content: [2](#0-1) [3](#0-2) 

`Registry.process` validates only the HMAC over that signable string, then forwards the untrusted `shop` value straight to the handler: [4](#0-3) 

`Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` (i.e. the body only) using `Context.api_secret_key`, which is the single `client_secret` shared by the app across **all** shops that install it: [5](#0-4) 

The identity binding that should hold is: `hmac == HMAC(secret, body ∥ shop)`. What is actually enforced is `hmac == HMAC(secret, body)`, with `shop` unbound. Because the secret is per-app (not per-shop), a merchant who has installed the app can legitimately obtain a `(body, hmac)` pair addressed to their own shop, then resend it to the app's webhook endpoint with the `shop-domain` header changed to any other tenant of the same app. The signature still validates because `shop` was never part of what was signed, so the host application processes attacker-controlled data under a victim shop's identity — a cross-tenant injection.

### Impact Explanation
This breaks tenant isolation for any app built on this gem's webhook processing path: an unprivileged (but installed) merchant of a multi-tenant app can forge webhook deliveries that the receiving application will attribute to a different shop, since `WebhookMetadata#shop` is populated straight from the unauthenticated header. Depending on how the host app uses `data.shop` (e.g., to look up a session/store record and act on it), this enables cross-tenant data corruption or unauthorized actions attributed to another merchant, matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation only requires being a legitimate (but low-trust) installer of the target app — no access to `client_secret`, tokens, or Shopify infrastructure is needed. The attacker merely needs one previously-delivered webhook `(body, hmac)` pair to their own shop, then can replay it with a different `shop-domain` header value. This is a realistic capability for any customer of a multi-tenant SaaS app built on this gem.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) into the value being authenticated, or otherwise cryptographically verify that the `shop-domain` header matches an expected/known shop for the delivery before trusting it — e.g., verify the shop is on the app's list of active installations tied to that specific HMAC delivery, or require the host app to cross-check `data.shop` against the session used to register the webhook. At minimum, document clearly that `request.shop` is unauthenticated and must not be trusted for tenant routing without independent verification.

### Proof of Concept
1. Merchant M installs public app P (shares one `client_secret` with all other installs of P).
2. Shopify sends M a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: H = HMAC(secret, B)`, `x-shopify-shop-domain: m.myshopify.com`.
3. M replays the identical `B`/`H` to P's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `B` and succeeds (`lib/shopify_api/webhooks/registry.rb:190`, `lib/shopify_api/webhooks/request.rb:36-38`).
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and `body: B`, and the host application processes attacker-controlled data as if it originated from `victim`.
