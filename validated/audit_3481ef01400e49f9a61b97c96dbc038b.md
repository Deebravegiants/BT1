### Title
Standing token allowance to the pool is not bound to a specific flash loan — any initiator can force an arbitrary WASM receiver to pay the flash fee - (File: contracts/pool/src/ops/flash.rs)

### Summary
CVE-2024-45340 is a credential-scope bug: GOAUTH credentials were not segmented by domain, so a credential ambiently available for one context was usable in another. The lending pool carries the same shape in flash-loan repayment: `collect_repayment` settles `principal + fee` through a standing token allowance (`transfer_from`) that is scoped only to the pool contract, not to the loan instance, the initiator, or the amount the receiver intended to borrow. Any unprivileged address can call `controller::flash_loan` naming a victim receiver contract that holds such an allowance, forcing the victim to pay the flash fee for a loan it never requested.

### Finding Description
`apply` pays `amount` to `receiver`, invokes the receiver's `execute_flash_loan` callback, and then collects repayment via allowance:

```rust
// contracts/pool/src/ops/flash.rs:173-179
assert_with_error!(
    env,
    asset.allowance(receiver, pool) >= terms.total_repayment,
    FlashLoanError::InvalidFlashloanRepay
);
asset.transfer_from(pool, receiver, pool, &terms.total_repayment);
```

The check only proves `allowance(receiver, pool) >= amount + fee`. Nothing binds that allowance to this flash loan: `initiator` is attacker-chosen, `amount` is attacker-chosen (bounded only by `cache.require_reserves(amount)` at line 85), and `data` is attacker-chosen. The pool consumes whatever allowance the receiver has granted it — a credential the receiver presumably set up for its own flash loans (the documented integration is "receiver approves amount + fee to the pool"), but which the pool will happily spend on behalf of any caller, exactly like the unsegmented `.netrc` credentials in the advisory.

Net effect per call: the victim receives `amount` and immediately loses `amount + fee`, i.e. it pays `fee` for a loan it did not initiate and may not even use during its own callback. If the victim's `execute_flash_loan` implementation is passive (e.g., it simply re-approves the pool, a common pattern to avoid per-call approval transactions), it has no way to refuse: the callback runs before `collect_repayment`, and the allowance is drained regardless of what the callback does with the funds.

### Impact Explanation
Theft of user funds. Each forced `flash_loan` call steals `fee = flashloan_fee_bps * amount` from the victim receiver. `amount` can be set to the market's full cash reserves to maximize the fee, and the attacker can repeat the call until `allowance(receiver, pool) < total_repayment`. Total theft is bounded by the victim's standing allowance and by the pool's lendable cash per call. The initiator needs no privilege: `controller::flash_loan` is permissionless (`INV-AUTH-03` in `scripts/permissionless_entrypoints.txt:77`), and `require_wasm_receiver` (line 49) is the only constraint on `receiver` — a victim integration contract trivially satisfies it.

### Likelihood Explanation
Any receiver contract that keeps a non-zero standing allowance to the pool — a natural pattern to avoid re-approving per loan, or residual allowance left after a larger approval — is exposed. The attack requires no price moves, no oracle interaction, and no special timing; a single transaction can loop the call. The cost to the attacker is only transaction fees. Likelihood depends on receivers holding standing allowances, but the protocol design (approve-then-pull rather than push-settlement) actively encourages that posture, and the victim cannot defend itself inside the callback since collection happens after it returns.

### Recommendation
Do not settle flash repayment from an ambient allowance. Either:
- Require the receiver to push the repayment inside `execute_flash_loan` and verify `balance == balance_after_repayment` after the callback (keep the existing `require_balance` checks), or
- Have the controller pass a per-loan nonce/expected repayment into the callback and have the pool pull only an allowance the receiver authorizes within that same invocation (`authorize_as_current_contract` inside the callback), so a pre-existing allowance can never be consumed by a foreign initiator.

At minimum, bind the consumed allowance to the loan by zeroing expectations: reject if `receiver` did not itself authorize this specific loan (e.g., require the callback to explicitly acknowledge the terms before allowing `transfer_from`).

### Proof of Concept
1. Victim contract `V` integrates with flash loans and, to save approvals, holds `allowance(V, pool) = X` on the market token (e.g., it approved once and reuses it, or approved a headroom amount).
2. Attacker `A` (any address) calls `controller.flash_loan(caller = A, hub_asset = M, receiver = V, amount = min(cash_M, X / (1 + fee_bps)), data = arbitrary)`.
3. Pool transfers `amount` of token `M` to `V`, calls `V.execute_flash_loan(...)` — `V`'s callback runs; even if `V` does nothing useful, control returns.
4. `collect_repayment` sees `allowance(V, pool) >= amount + fee` and executes `transfer_from(pool, V, pool, amount + fee)`. `V` nets `-fee` while `A` pays nothing.
5. `A` repeats until `X` is consumed, extracting `fee` per iteration.
