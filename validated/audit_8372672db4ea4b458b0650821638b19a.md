## Title
Webhook shop-domain (and topic/api-version/webhook-id) headers are trusted unauthenticated while only the raw body is HMAC-verified, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

## Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` (invoked by `Registry.process`) proves nothing more than "this body was signed with our secret." The `shop` (and `topic`, `api_version`, `webhook_id`) values used to route and attribute the event are read straight from HTTP headers that are never part of the signed material, then handed to the app's handler as if authenticated.

## Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `HmacValidator.validate_signature` computes the HMAC only over that signable string: [2](#0-1) 

`Registry.process` treats a passing HMAC check as proof the whole request "did indeed come from Shopify" and then forwards `request.shop`, taken from the unauthenticated `shop-domain` header, to the handler: [3](#0-2) [4](#0-3) 

The gem's own docs assert this stronger guarantee that is not actually delivered: [5](#0-4) 

This is exactly the "field acted on but not covered by the HMAC" pattern from the report: the equality that should hold is `shop_header == shop_bound_by_hmac`, but the HMAC only binds `raw_body`, not `shop_header`. Any request whose body+HMAC pair is genuine (e.g., captured from a webhook fired by the attacker's own shop, which has the app installed) can be replayed with an arbitrary `x-shopify-shop-domain` header, and `HmacValidator.validate` will still return `true` because it never inspects that header.

## Impact Explanation
An unprivileged app user (a merchant who installs the app on their own store, generating genuine Shopify-signed webhook bodies) can replay one of those signed bodies to the app's webhook endpoint while substituting a victim shop's domain in the `shop-domain` header. Since `Registry.process` only checks the raw body's HMAC and unconditionally trusts the header-derived `shop`, the handler receives `WebhookMetadata` claiming the (attacker-controlled) payload belongs to the victim tenant. Any host app that uses `data.shop` as the tenant key (as the gem's own docs recommend: `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) will ingest attacker-supplied order/customer/inventory data under the victim's tenant record — a cross-tenant data injection inside a supposedly per-tenant isolated pipeline.

## Likelihood Explanation
Reaching this requires only: (1) installing the app on any store the attacker controls (a normal, unprivileged merchant action, not a privileged account or leaked secret), and (2) capturing one legitimate webhook delivery to obtain a valid `(raw_body, hmac)` pair, then replaying it with a modified `shop-domain` header to the app's public webhook endpoint. No `api_secret_key`, access token, or TLS interception is needed — the HMAC and body are genuine and unmodified; only the unauthenticated header is changed.

## Recommendation
Include the identity-relevant headers (`shop`, `topic`, `api_version`, `webhook_id`) in the HMAC-signed material, or otherwise cryptographically bind them to the verified body, so `Registry.process` cannot attribute an arbitrary signed payload to an attacker-chosen shop.

## Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw POST body and the `x-shopify-hmac-sha256` value Shopify sent.
2. Attacker POSTs to the app's webhook route with:
   - Body: the captured raw body (unchanged)
   - `x-shopify-hmac-sha256`: the captured, still-valid HMAC
   - `x-shopify-shop-domain`: `victim-shop.myshopify.com` (changed)
3. `ShopifyAPI::Webhooks::Request.new` parses the forged header successfully (headers aren't validated for consistency), and `Utils::HmacValidator.validate` returns `true` because it only recomputes the HMAC over `raw_body`, per `to_signable_string`.
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's own order data>, ...)`, causing the host app to associate attacker-controlled data with the victim tenant. [3](#0-2)
