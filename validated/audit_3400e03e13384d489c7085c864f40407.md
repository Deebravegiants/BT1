Audit Report

## Title
JWT Replay-Guard TOCTOU Allows Concurrent Reuse of a Single-Use JWT - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
`WorkflowMetadataHandler.Authorize` checks JWT replay status via `jwtCache.isReplay(claims.ID)` and only marks the JWT as used via `jwtCache.recordUsage(claims.ID)` after unrelated authorization logic executes, with no lock held across the whole sequence. Two concurrent requests carrying the same JWT can both pass `isReplay` before either calls `recordUsage`, defeating the single-use guarantee and allowing the same signed HTTP-trigger JWT to authorize multiple workflow executions.

## Finding Description
`Authorize` is reached from `httpTriggerHandler.authorizeRequest` → `h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)`, which is invoked directly from `HandleUserTriggerRequest`, the externally-reachable entry point for HTTP Trigger requests [1](#0-0) [2](#0-1) .

Inside `Authorize`, `isReplay` is checked, followed by unrelated `authorizedKeys`/signer lookups, and only then is `recordUsage` called to mark the `jti` spent: [3](#0-2) . `isReplay` takes an `RLock` and releases it immediately after the read, and `recordUsage` independently takes its own `Lock` later — no lock spans the full check-then-record sequence: [4](#0-3) .

Checking the call chain confirms there is no other serialization point that would prevent two concurrent `Authorize` calls with an identical `jti` from interleaving: `setupCallback`'s uniqueness check operates on the JSON-RPC `req.ID` (an attacker-controlled, arbitrary field distinct from the JWT's `jti` claim), not on the JWT id, so an attacker can freely send two requests with different `req.ID`s but the same JWT/`jti`, bypassing that unrelated dedup mechanism entirely [5](#0-4) . Thus the only defense against JWT replay is the racy `isReplay`/`recordUsage` pair, and it is genuinely bypassable by two concurrent requests.

## Impact Explanation
This breaks the intended single-use invariant of the HTTP-trigger JWT authentication scheme, allowing an external, unprivileged caller who possesses one valid signed JWT to trigger duplicate workflow executions concurrently by racing the check-then-record window. This maps to the in-scope "unauthorized job run" / authentication-bypass impact category for the gateway, since it lets a caller invoke a workflow execution more times than the single-use token should permit.

## Likelihood Explanation
The race window is narrow (a few map operations under lock contention) but is genuinely reachable by any external caller who fires two near-simultaneous requests carrying an identical signed JWT to `HandleUserTriggerRequest`, requiring no credentials beyond the JWT itself and no host/operator access. The interleaving requires precise timing to reliably win the race, but is realistically achievable with parallel request bursts, and is repeatable per captured JWT until it expires or the cleanup period passes.

## Recommendation
Merge `isReplay` and `recordUsage` into a single atomic check-and-set operation performed under one lock, e.g., a `checkAndRecord(jti)` method that atomically checks presence and inserts under a single `mu.Lock()` critical section, and call this from `Authorize` in place of the separate `isReplay`/`recordUsage` calls, rejecting the request immediately if the JWT was already recorded.

## Proof of Concept
1. Obtain one valid signed JWT (`jti = X`) authorized for a workflow.
2. Send two concurrent `workflows.execute` requests to the gateway with distinct JSON-RPC `id` fields (to bypass the unrelated `setupCallback` requestID-uniqueness check) but the identical JWT/`jti` in the `Auth` field.
3. Both goroutines execute `Authorize`; both call `isReplay("X")` and observe `exists == false` before either calls `recordUsage("X")`, per the unguarded critical sections in `isReplay`/`recordUsage`.
4. Both requests pass authorization and are dispatched via `sendWithRetries` to the DON, confirming the single-use JWT was consumed more than once — verifiable with a Go unit test that calls `Authorize` from two goroutines synchronized via a barrier immediately before the `isReplay` check, asserting both return no error.

```go
func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
```

```go
func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
```
