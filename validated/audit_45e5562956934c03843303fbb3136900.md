### Title
Unvalidated relayer-supplied `authorityIndex` used as array index in BEEFY authority-set merkle proof verification - ([File: modules/consensus/beefy/verifier/src/lib.rs])

### Summary
The BEEFY consensus verifier builds a list of authority indices directly from the untrusted `sig.index` field carried in a relayed BEEFY `ConsensusMessage` and feeds it straight into a merkle multi-proof verification call without first checking that the index is within the bounds of the current authority set (`authority_set.len`). This mirrors the pattern behind CVE-2026-43274, where an unchecked, potentially out-of-range index (`hartid`) was used to index into a bounded array (`cluster_cfg`) instead of a value guaranteed to be within range. Here `sig.index`, fully controlled by whoever submits the consensus update (a relayer), is used the same way against the authority-set leaf array.

### Finding Description
In `verify_mmr_update_proof` [1](#0-0) , the function selects the claimed authority set and only checks a *participation threshold* (`check_participation_threshold(signatures_length, authority_set.len)`), never validating that each signature's `index` field is `< authority_set.len`.

It then builds the authority index/leaf vectors directly from attacker-controlled data: [2](#0-1) 
```
for sig in mmr.signed_commitment.signatures.iter() {
    ...
    authority_leaves.push(authority_address_hash.into());
    authority_indices.push(sig.index as usize);
}
...
let valid = merkle_proof.verify(
    authority_set.keyset_commitment.into(),
    &authority_indices,
    &authority_leaves,
    authority_set.len as usize,
);
```
`sig.index` comes from `SignatureWithAuthorityIndex.index: u32` [3](#0-2) , which is decoded straight out of the relayed, unsigned `ConsensusMessage`/`MmrProof` payload — there is no range check anywhere in this path constraining `index` to `[0, authority_set.len)`. The equivalent Solidity path has the identical construction with `vote.authorityIndex` used unchecked as the `Leaf.index` passed to `MerkleMultiProof.VerifyProof` [4](#0-3) .

This is structurally the same bug class as the kernel CVE: an externally supplied index value (`hartid`/`sig.index`) that is not guaranteed to be within `[0, N)` is used to position/index elements against an array sized by `N` (`cluster_cfg`/authority leaves), instead of deriving a bounds-guaranteed index (`cpuid`/a verified array position).

### Impact Explanation
This function is on the core consensus-update path: `verify_consensus`/`verify_mmr_update_proof` is invoked whenever a relayer submits a new BEEFY consensus proof to update the trusted `ConsensusState` used for all subsequent state-proof verification and message delivery in Hyperbridge. If passing out-of-range indices into the underlying merkle-proof verification routine causes a panic (denial of service on the consensus-update dispatch) rather than a clean rejection, an unprivileged relayer can repeatedly submit malformed BEEFY proofs to halt processing of the unsigned consensus-update extrinsic, freezing the light client's ability to advance state and thereby blocking all message delivery routed through this consensus client — a "route unable to deliver messages" condition. If instead the underlying multi-proof library treats out-of-range indices permissively (rather than rejecting them, as intended by `check_participation_threshold`/membership checks), it could enable forged authority-set membership claims, undermining the supermajority signature check that gates acceptance of a new consensus state — leading to forged message delivery / unsound state commitment.

### Likelihood Explanation
Likelihood is high for reachability: submitting a BEEFY consensus update is an unprivileged, externally triggerable action (via the relayer/tesseract client or directly crafting the unsigned extrinsic), and the vulnerable code path executes on every consensus update attempt before any authority-index bounds validation occurs.

### Recommendation
Before constructing `authority_indices`/`authority_leaves` in `verify_mmr_update_proof`, explicitly validate that every `sig.index < authority_set.len` (rejecting the proof with an appropriate error such as `Error::InvalidAuthorityIndex` otherwise), mirroring the fix pattern in the referenced CVE of only using indices guaranteed to be within the valid bound. Apply the same bounds check to the analogous Solidity path in `EcdsaBeefy.sol::verifyMmrUpdateProof` for `vote.authorityIndex`.

### Proof of Concept
1. As a relayer, submit a `ConsensusMessage` whose `mmr.signed_commitment.signatures` contains a valid signature/authority pairing, but with `SignatureWithAuthorityIndex.index` set to a value `>= authority_set.len` (e.g. `u32::MAX`).
2. `verify_mmr_update_proof` passes `check_participation_threshold` (which only checks the count of signatures, not their indices) and proceeds to call `merkle_proof.verify(..., &authority_indices, &authority_leaves, authority_set.len as usize)` with the out-of-range index included.
3. Observe whether the underlying merkle-proof verification panics (DoS on the consensus update path) or incorrectly validates, instead of being rejected cleanly at the index-validation stage — either outcome demonstrates the missing bounds check identified above.

pub fn verify_mmr_update_proof<H: Keccak256 + EcdsaRecover + Send + Sync>(
	mut trusted_state: ConsensusState,
	mmr: MmrProof,
) -> Result<(ConsensusState, H256), Error> {
	let signatures_length = mmr.signed_commitment.signatures.len();
	let latest_height = mmr.signed_commitment.commitment.block_number;

	if trusted_state.latest_beefy_height >= latest_height {
		return Err(Error::StaleHeight {
			trusted_height: trusted_state.latest_beefy_height,
			current_height: latest_height,
		});
	}

	let commitment = mmr.signed_commitment.commitment.clone();

	// Pick the authority set the commitment claims to be signed under, then judge
	// participation against that set alone.
	let authority_set = if commitment.validator_set_id == trusted_state.current_authorities.id {
		&trusted_state.current_authorities
	} else if commitment.validator_set_id == trusted_state.next_authorities.id {
		&trusted_state.next_authorities
	} else {
		return Err(Error::UnknownAuthoritySet { id: commitment.validator_set_id });
	};

	if !check_participation_threshold(signatures_length as u32, authority_set.len) {
		return Err(Error::SuperMajorityRequired);
	}
