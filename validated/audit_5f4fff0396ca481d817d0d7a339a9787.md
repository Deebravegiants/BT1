I found a genuine access-control gap analogous to the report: `HyperFungibleTokenImpl.superApprove` is a `public` function with **no access-control modifier at all**, and it directly calls the internal `_approve` primitive on behalf of an arbitrary `owner` supplied by the caller.

### Title
`HyperFungibleTokenImpl.superApprove` allows any caller to grant unlimited ERC20 allowance on behalf of any token holder — (File: `evm/src/utils/HyperFungibleTokenImpl.sol`)

### Summary
`superApprove(address owner, address spender)` is declared `public` with no `onlyRole`, `onlyOwner`, or `msg.sender == owner` check, unlike every other state-changing function in the same contract (`mint`, `burn`, `grantMinterRole`, `grantBurnerRole`, `revokeMinterRole`, `revokeBurnerRole`), all of which are correctly gated with `onlyRole(...)`. [1](#0-0) 

### Finding Description
This mirrors the audit finding pattern exactly: a sensitive state-mutating function (`setPoolActive` in the report, `superApprove` here) is missing the modifier present on its sibling functions in the same contract. `mint`/`burn`/role-management functions all correctly enforce `onlyRole(MINTER_ROLE|BURNER_ROLE|DEFAULT_ADMIN_ROLE)`: [2](#0-1) 

But `superApprove` calls the internal OpenZeppelin `_approve(owner, spender, type(uint256).max)` — which bypasses `msg.sender`-based `approve()` semantics entirely — using an attacker-supplied `owner` parameter, with zero restriction on who may call it or which `owner` address they target: [1](#0-0) 

`HyperFungibleTokenImpl` is the token implementation deployed and used as the fee token / bridged token in the Hyperbridge EVM stack (e.g. instantiated for the fee token and faucet flow in `DeployIsmp.s.sol`, and granted a minter role to the `TokenFaucet`). [3](#0-2) 

Because `superApprove` sets `type(uint256).max` allowance for `spender` over `owner`'s balance regardless of `owner`'s consent, any unprivileged address can call `superApprove(victim, attacker)` and immediately gain unlimited `transferFrom` rights over the victim's balance of this token.

### Impact Explanation
This is a direct, concrete theft primitive: any address holding this token (used as Hyperbridge's fee token / faucet-derived token per the deployment script) can have its full balance drained by an attacker calling `superApprove(victimAddress, attackerAddress)` followed by `transferFrom(victim, attacker, balance)`. This satisfies "concrete theft of funds" — no privileged role, governance action, or malicious actor assumption is needed; a single unprivileged transaction from any external caller is sufficient.

### Likelihood Explanation
High — the function is `public`, requires no proof, signature, or special caller state, and is reachable in a single transaction. The comment ("Helper function for tests") suggests it was intended to be test-only scaffolding but is not gated by test-mode flags, `onlyRole`, or removed from the production contract, exactly the same class of oversight described in the original report (a helper/utility path that should have been restricted but wasn't).

### Recommendation
Either remove `superApprove` entirely from the production contract (moving it into a test harness / mock contract instead), or restrict it so it can only set an allowance where `msg.sender == owner` (i.e., behave like normal `approve`), or gate it behind `onlyRole(DEFAULT_ADMIN_ROLE)` if a privileged override is genuinely required.

### Proof of Concept
1. Deploy/observe `HyperFungibleTokenImpl` as used for the fee token (see `DeployIsmp.s.sol` lines 100–105) with victim holding a balance. [4](#0-3) 
2. Attacker (unprivileged, no role) calls:
```solidity
token.superApprove(victim, attacker);
```
This succeeds because `superApprove` has no access-control modifier. [5](#0-4) 
3. Attacker then calls `token.transferFrom(victim, attacker, token.balanceOf(victim))`, draining the victim's entire balance using the unlimited allowance just granted without victim consent.

**Note on scope/uncertainty**: I searched extensively for other analogs (EvmHost setters, HostManager, IntentGatewayV2's `cancelOrder`/`select`/`fillOrder`, BandwidthManager, LayerZero endpoint, BridgeToken) and all other sensitive setters I could find were correctly protected by `onlyOwner`, `onlyHost`, `restrict(...)`, or signature-based authentication. `superApprove` is the one clear match to the report's bug class (a state-changing function missing the access-control modifier its sibling functions have) that I could locate with confidence via the indexed codebase.
