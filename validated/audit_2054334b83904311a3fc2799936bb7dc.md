### Title
Webhook `shop`, `topic`, `webhook_id` and `api_version` are trusted from unauthenticated HTTP headers while the HMAC only covers the raw body, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, while the shop identity (`shop-domain`), `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers that are never included in the signed bytes. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC against the body only, then unconditionally forwards the header-derived `shop` value to the handler as if it were verified.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC (which only covers `@raw_body`) and then trusts `request.shop`/`request.topic`/`request.webhook_id` verbatim when building `WebhookMetadata` passed to the app's handler: [3](#0-2) [4](#0-3) 

This is exactly the identity-binding break described in the analog class: "bytes verified versus bytes parsed" — the HMAC verifies only the request body, but the shop identity that the app acts on is parsed from headers outside that verified byte range. `Utils::HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it against the `hmac-sha256` header, entirely independent of any other header: [5](#0-4) 

**Attack path:** An attacker who operates their own Shopify store with the app installed receives genuine webhook deliveries from Shopify — real `raw_body` + valid `hmac-sha256` signature pairs, computed with the app's own `client_secret`, for topics/data belonging to *their* shop. Because the HMAC never covers the `shop-domain`, `topic`, or `webhook_id` headers, the attacker can replay that exact `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header (and/or `topic`/`webhook_id`). `HmacValidator.validate` still succeeds because it only checks the untouched body bytes, and `Registry.process` hands the forged `shop` value straight to the app's handler as authoritative shop identity.

### Impact Explanation
This breaks the identity binding `shop authenticated == shop the handler acts on`, letting a store owner (an otherwise unprivileged, non-cross-tenant actor) impersonate an arbitrary other tenant's shop identity in webhook processing. Any app logic keyed off `WebhookMetadata#shop` (e.g., updating per-shop billing/subscription state, triggering shop-scoped data mutations, or the mandatory GDPR topics `shop/redact`, `customers/redact`, `customers/data_request`) can be invoked under a spoofed shop, constituting cross-tenant access/action — a Critical-impact class per the rubric.

### Likelihood Explanation
Likelihood is meaningful but bounded: the attacker must possess at least one legitimate, previously-received `(raw_body, hmac-sha256)` pair, which any merchant who installs the app can obtain (e.g., from any webhook topic delivered to their own shop, including easily triggerable ones like `app/uninstalled` or product/order events). No secret key, access token, or privileged account is required beyond running an ordinary store that installs the app — this is within the "unprivileged internet user" threat model. The main constraint is that the forged payload's `body` content (JSON) still corresponds to the originally captured shop's data, so the practical impact depends on how much the handler trusts `shop` versus `body` contents; still, the shop attribution itself is fully forgeable.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the HMAC-verified surface, e.g., by including the `shop-domain`, `topic`, and `webhook_id` header values in the canonical string that `to_signable_string` returns (in addition to the body), or by requiring host applications to cross-check `request.shop` against a shop known to be currently installed via a separately-authenticated channel (e.g., session storage keyed by an offline token) before trusting it. At minimum, document prominently that `request.shop`/`request.topic` are unauthenticated and must not be trusted for authorization decisions.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`; app subscribes to webhook topic `T`.
2. Shopify delivers a legitimate webhook to the attacker's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H = HMAC(secret, B)`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures `(B, H)` and replays a POST to the target app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac` returns the header value; `to_signable_string` returns `B` (unchanged); `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` and it matches `H` — validation passes: [6](#0-5) [7](#0-6) 
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the app to act as though the webhook originated from `victim-shop.myshopify.com` even though it never sent it.

          received_signature = verifiable_query.hmac
