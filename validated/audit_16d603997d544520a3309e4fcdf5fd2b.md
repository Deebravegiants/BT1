### Title
Webhook shop attribution (`shop-domain` header) is not covered by the HMAC signature, allowing shop-spoofed webhook delivery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw body, while the `shop` attribute used to attribute the event to a tenant is read from an unauthenticated HTTP header.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes/compares the signature exclusively over that signable string [2](#0-1) . The `shop` value, however, is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header without any cryptographic binding to the body or the signature [3](#0-2) .

`Registry.process` validates only the HMAC of the body and then immediately trusts `request.shop` to build the metadata handed to the app's webhook handler: [4](#0-3) 

Because the HMAC secret (`Context.api_secret_key`) is shared across every shop that installs the app, any signature that is valid for a given raw body remains valid for that same body regardless of which `shop-domain` header accompanies it. This breaks the intended identity binding `hmac == HMAC(secret, body) AND shop == the store the body actually originated from`. In practice: `hmac` is verified against `body` only, but `shop` — the value the host application uses as a tenant key — is taken from an out-of-band, unverified header. `request.shop` (unauthenticated header) is treated as equal to "the store this webhook came from" (a claim that should require the same authenticity guarantee as the body).

### Impact Explanation
This is a cross-tenant binding failure inside the gem's own webhook-processing pipeline: an attacker who can produce a body+HMAC pair that is valid for the app's shared secret (e.g., by triggering/replaying a legitimate webhook delivery to their own shop, or intercepting/replaying a request before it reaches the app) can arbitrarily change the `shop-domain` header to a victim shop and have `Registry.process` construct `WebhookMetadata` attributing that body to the victim shop. Any host application that relies on this gem's shop attribution to route webhook data to per-tenant storage/handlers (this is the documented use of `WebhookMetadata#shop`, per `Registry.process`) will process/store attacker-supplied data under the wrong tenant, i.e., cross-tenant data injection — this is called out as an accepted impact category (cross-tenant access).

### Likelihood Explanation
Exploitability depends on the attacker being able to relay/replay a validly-signed body (from their own installed shop) with a modified shop header to the app's public webhook endpoint. It does not require the `api_secret_key`, an access token, or any privileged credential — only ability to control the header on an HTTP request reaching the app's webhook controller, which is the standard entry point for this gem's webhook processing.

### Recommendation
Include the shop domain (and ideally topic/webhook-id/api-version) in the string that is HMAC-verified, or otherwise cryptographically bind the `shop` value to the verified body (e.g., look up the shop via a separately-authenticated channel, or require the shop domain to be embedded in and validated against the JSON payload itself) rather than trusting an unauthenticated header for the value used to key data.

### Proof of Concept
1. App installs on Attacker's own shop; a legitimate Shopify webhook is delivered with body `B` and header `shopify-hmac-sha256: HMAC(secret, B)`.
2. Attacker intercepts/relays this request to the app's webhook endpoint, replacing `shopify-shop-domain: attacker-shop.myshopify.com` with `shopify-shop-domain: victim-shop.myshopify.com`, leaving body `B` and the HMAC header unchanged.
3. `ShopifyAPI::Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` (the header-independent `to_signable_string`) and it matches, so validation succeeds [1](#0-0) .
4. `Registry.process` calls the handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` is now `victim-shop.myshopify.com` [5](#0-4) , causing the host app to process attacker-controlled body content under the victim's tenant.

Note: I was unable to inspect `lib/shopify_api/webhooks/webhook_metadata.rb` (file not indexed/found), so the exact fields carried into the handler beyond `topic`, `shop`, `body`, `api_version`, and `webhook_id` (as constructed in `registry.rb`) could not be fully confirmed; a Devin session with full filesystem access would be needed to verify that file's contents.
