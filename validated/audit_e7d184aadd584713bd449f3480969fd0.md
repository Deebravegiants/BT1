## Title
Webhook cross-tenant spoofing via `shop-domain`/`topic` headers not covered by HMAC signature - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop`, `topic`, and `webhook_id` values taken from HTTP headers to route and label the payload — even though none of those header values are part of the signed bytes.

### Finding Description
`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` and compares it against the `hmac` field: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read directly from unauthenticated HTTP headers, none of which are included in the signed string: [3](#0-2) 

`Registry.process` validates the HMAC of the body only, then forwards `request.shop` and `request.topic` — values that were never bound by the signature — straight to the app's handler as authenticated identity/routing data: [4](#0-3) 

The equality this breaks is: `shop_authenticated_by_hmac == shop_acted_upon_by_handler`. The HMAC only proves "these bytes (`raw_body`) were signed with our api_secret_key at some point, for some tenant, for some topic." It does **not** prove which shop, which topic, or which webhook id the signed bytes belong to.

### Impact Explanation
Any unprivileged internet user who can obtain **one** legitimately-signed webhook delivery for **any** shop that installed the app (e.g., their own free/dev store) can capture the `raw_body` + valid `x-shopify-hmac-sha256` pair. They can then replay that exact body/HMAC pair to the app's webhook endpoint while substituting arbitrary `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` header values. `Utils::HmacValidator.validate` still returns `true` (the body bytes/HMAC are unchanged and valid), while `Registry.process` dispatches the attacker-chosen `shop` and `topic` to the registered handler. Any host application that trusts `WebhookMetadata#shop` as the authenticated tenant identifier (which is the documented and expected use per this library's contract) will process/act on data under the wrong shop's identity — a cross-tenant confusion condition, since the shop value that reaches business logic is fully attacker-controlled despite `Registry.process` appearing to have "verified" the request.

### Likelihood Explanation
High from a mechanics standpoint: the only prerequisite is possessing one valid signed webhook from any shop (trivially obtainable — anyone can spin up a free Shopify dev store and install a public app to receive webhooks for topics they control), and no secret material or privileged account is required. It is a design flaw in the signature scope, not a probabilistic timing or race condition.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook_id`) in the HMAC-signed material, or otherwise cryptographically bind them (e.g., require the handler to independently verify `request.shop` against a known/expected value from session storage before trusting it). At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are **not** authenticated by `Registry.process` and must not be trusted for tenant-scoping decisions without independent verification.

### Proof of Concept
1. Attacker installs the target app on their own Shopify dev store (`attacker.myshopify.com`) and configures the app to receive a webhook for topic `orders/create`.
2. Shopify delivers a webhook with a body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's real `api_secret_key`), along with `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays the exact same `B`/`H` pair to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and/or `x-shopify-topic: customers/redact` (or any registered topic).
4. `Utils::HmacValidator.validate(request)` at [5](#0-4) 
returns `true` because only `B` and `H` are checked; `Registry.process` then invokes the handler with `shop: "victim-shop.myshopify.com"` and the attacker-chosen topic, even though Shopify never actually sent a webhook about `victim-shop`.
