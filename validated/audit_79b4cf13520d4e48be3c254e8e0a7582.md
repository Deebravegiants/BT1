### Title
Webhook signature verification does not bind the `shop`/`topic` identity headers to the signed payload, enabling cross-tenant webhook forgery via replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, while the tenant-identifying `shop` field is read from an unauthenticated HTTP header and passed straight into the handler. This breaks the binding `shop-that-produced-signed-body == shop-attributed-to-request`, allowing a merchant who has legitimately installed the app on their own store to replay one of their own genuinely-signed webhook deliveries against the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` header for a victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, and `webhook_id` are extracted directly from request headers, independent of the signed content: [2](#0-1) 

`Registry.process` validates the HMAC over that body-only signable string, then immediately forwards the unauthenticated `request.shop` header value into the metadata handed to the host app's handler, without ever tying it back to the signature: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` confirm this: the HMAC compares `compute_signature(verifiable_query.to_signable_string, secret)` against the received signature — for a `Request`, `to_signable_string` is exactly `@raw_body`, so the header-derived `shop` never enters the signature computation at all: [4](#0-3) 

Because the identity check (`HMAC(body, api_secret_key)`) and the identity acted upon (`shop` header forwarded to the handler as the tenant) are decoupled, any bytes that pass the body-HMAC check can be paired with an arbitrary `shop` header and will be processed by `Registry.process` as if they belonged to that shop.

### Impact Explanation
This is a cross-tenant identity binding failure: `shop-header-used-by-handler == shop-that-actually-produced-the-signed-body` is never enforced. An attacker who has installed the app on a store they control (an ordinary, unprivileged action available to any Shopify merchant/tester — no leaked credentials or access token required) can obtain a genuinely HMAC-signed webhook body/signature pair for their own shop, then replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint with `X-Shopify-Shop-Domain` (or `X-Shopify-Topic`) rewritten to a victim shop. `Utils::HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"`, causing the host application — following this gem's documented webhook-processing contract — to attribute the attacker's forged payload to the victim tenant. This satisfies the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Any external actor can trivially install a Shopify app on a shop they operate to receive a legitimately signed webhook, then send an unauthenticated, forged HTTP POST directly to the app's webhook endpoint reusing that valid body+signature with a substituted shop header. No secrets, tokens, or privileged access are required beyond the ability to install the target app, which is the normal unprivileged path any internet user with a development store can take.

### Recommendation
Include the tenant-identifying headers (`shop`, `topic`, `webhook_id`, `api_version`) in the value that is HMAC-verified — e.g., construct a canonical signable string that concatenates these header values with the raw body before computing/comparing the digest — or otherwise cryptographically bind the header-derived `shop` to the specific signed delivery so a captured `(body, hmac)` pair cannot be replayed under a different shop identity.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` (self-service, unprivileged).
2. Trigger any webhook topic the app subscribes to; capture the genuine delivery: `raw_body = B`, `X-Shopify-Hmac-Sha256 = H` (valid for `B`), `X-Shopify-Shop-Domain = attacker-shop.myshopify.com`.
3. Send a new POST directly to the app's webhook endpoint with the same `B` and `H`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shopify-shop-domain" => "victim-shop.myshopify.com", "shopify-hmac-sha256" => H, ...})` is constructed; `Utils::HmacValidator.validate(request)` returns `true` because it only re-derives the HMAC from `B` [5](#0-4) .
5. `Registry.process(request)` invokes the app's handler with `shop: "victim-shop.myshopify.com"` and attacker-controlled body `B`, causing the host app to act on victim-shop's tenant data using attacker-supplied content [6](#0-5) .

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
