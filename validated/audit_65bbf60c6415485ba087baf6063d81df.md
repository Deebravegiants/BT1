## Analysis

The external report describes a whitelist-enable state where the contract validates the *minter/caller* role but never re-checks that the token holder (`from`) itself satisfies the same invariant — breaking the equality "only a validated address can trigger this state transition."

Searching `packages/intents-sdk/src/**` for the closest analog — a place where a withdrawal record is looked up and reported back to a caller/integrator without validating that the record actually corresponds to the specific withdrawal being queried — surfaces `findMatchingWithdrawal` used by `PoaBridge.describeWithdrawal`. ### Title
Status/txHash reported for a withdrawal is not the on-chain outcome of that specific withdrawal — POA bridge matches by `assetId` only, ignoring index/amount/destination - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` resolves the completion status of a specific withdrawal (identified by `landingChain`, `index`, `withdrawalParams`, `tx`) by calling `findMatchingWithdrawal`, which matches entries in the POA indexer's response purely by `assetId` (`near_token_id`), using `Array.prototype.find` — the first entry whose asset matches, regardless of destination address, amount, or the caller-supplied `index`. This is explicitly acknowledged in the code comment as a known limitation.

### Finding Description
`createWithdrawalIntents`/`sdk.ts` can batch multiple withdrawals of the same token (e.g. same `nep141:btc.omft.near`) with different destination addresses/amounts inside a single NEAR intents transaction (see `createWithdrawalIdentifiers` in `packages/intents-sdk/src/core/withdrawal-watcher.ts`, which assigns a separate `index` per bridge route but does not disambiguate by asset within the same route). When `describeWithdrawal` (`poa-bridge.ts:313-337`) is later polled for withdrawal `index=0` of that asset, `findMatchingWithdrawal` (`poa-bridge.ts` / `waitForWithdrawalCompletion.ts:144-153`) returns the *first* withdrawal object in the (explicitly "unsorted") API response with a matching `near_token_id`/`assetId` — this could be the record belonging to withdrawal `index=1`'s destination/amount instead of `index=0`'s. The comment at `poa-bridge.ts:318` and `waitForWithdrawalCompletion.ts:136-142` both state: "Response list is unsorted, so we match by assetId instead of index" and "multiple withdrawals of the same token in a single transaction are not supported."

This breaks the equality that the status/txHash returned for withdrawal N must be the actual on-chain settlement outcome for withdrawal N's specific destination/amount — an integrator polling per-index could receive a `completed` status with a `txHash` that actually belongs to a *different* withdrawal in the same batch.

### Impact Explanation
If an integrator relies on `describeWithdrawal`/`waitForWithdrawalCompletion` to gate crediting a user or releasing downstream funds once a withdrawal is "completed," a mismatch could make the SDK report withdrawal A as completed using withdrawal B's transaction hash (or vice versa) when two same-asset withdrawals exist in the same NEAR transaction. This matches the "status/hash misreport" impact category (High) — the integrator could credit/refund based on incorrect on-chain evidence, or falsely conclude a still-pending withdrawal has completed.

### Likelihood Explanation
Requires the specific but realistic condition of two-or-more same-`assetId` withdrawals batched in one processing/intents transaction — plausible for any caller/integrator using `processWithdrawal`/`createWithdrawalIntents` with array-style batching for the same token to different recipients. The code comments confirm the authors are aware this scenario is unhandled, and there is no guard rejecting such batches upstream (`sdk.ts` `createWithdrawalIntents`, `createWithdrawalIdentifiers`).

### Recommendation
Match POA withdrawal status entries using a further disambiguating field (destination address, amount, and/or a per-withdrawal correlation id returned by the POA API) rather than `assetId` alone, or reject/serialize batches containing multiple same-asset PoA withdrawals until the indexer response can be uniquely correlated with `index`.

### Proof of Concept
1. Call `sdk.processWithdrawal`/`createWithdrawalIntents` with two `withdrawalParams` for `nep141:btc.omft.near` to two different Bitcoin destination addresses in the same NEAR transaction, both routed via `PoaBridge`.
2. Both settle on POA, producing two entries in `getWithdrawalStatus` for the same `near_token_id` with different `transfer_tx_hash`/`address`.
3. Call `describeWithdrawal({ index: 0, withdrawalParams: <withdrawal-for-address-A>, tx })`; `findMatchingWithdrawal` returns the first entry with matching `near_token_id`, which may be the entry for address B due to the indexer's unsorted list, per `poa-bridge.test.ts:1054-1111` ("matches withdrawal by assetId, not by index"). 	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
