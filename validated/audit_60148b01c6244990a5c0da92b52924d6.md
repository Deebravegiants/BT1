### Title
Webhook `X-Shopify-Shop-Domain` header is not covered by HMAC verification, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for an incoming webhook from an HTTP header, while `ShopifyAPI::Utils::HmacValidator` only authenticates the raw request body. The `shop` value that the host application uses to route/attribute the webhook is therefore never bound by the cryptographic check that supposedly "validates" the request.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` (the tenant identifier ultimately handed to the app's webhook handler) is read straight from a header, entirely outside the signed material: [2](#0-1) 

`Registry.process` verifies the HMAC over the body only, then immediately trusts `request.shop` (and `request.topic`) as authoritative tenant/topic identity when dispatching to the handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e. the body) and compares it with `OpenSSL.secure_compare`: [4](#0-3) 

This breaks the intended identity binding `shop-authenticated == shop-acted-upon`: the bytes that are HMAC-verified (raw body) are disjoint from the bytes that are parsed and trusted as the shop identity (`shopify-shop-domain` / `x-shopify-shop-domain` header). Because the HMAC is computed with the app's `api_secret_key` over the body alone, **any** request whose body was previously signed by Shopify for **any** shop (e.g. the attacker's own store, on which they can install the target app) produces a valid HMAC regardless of which `shop-domain` header value is later attached to the request.

### Impact Explanation
An attacker who operates their own (unprivileged) shop and installs the vulnerable app can capture one or more legitimately Shopify-signed webhook deliveries to their own store (body + HMAC pair, which is fully within their control/observation). They can then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with an arbitrary victim shop domain. Because `HmacValidator.validate` only checks the body, the forged request passes verification, and `Registry.process` will invoke the merchant's registered handler with `shop: <victim-shop>` and attacker-controlled `body`/`topic` (topic is also unauthenticated). This enables cross-tenant data injection/spoofing — the app processes attacker-supplied data (e.g. fake `orders/create`, `customers/data_request`, `shop/redact`) as if it originated from the victim's tenant, which can corrupt the victim's records, trigger unauthorized data deletion/redaction flows, or otherwise cause cross-tenant compromise in any multi-tenant app built on this gem.

### Likelihood Explanation
Likelihood is moderate-to-high in any real multi-tenant deployment: the only prerequisite is that the attacker be an unprivileged installer of the app on their own store (the "unpriviledged internet user" persona), which is trivial in the standard Shopify app-install model. No access to `api_secret_key`, tokens, or any privileged account is required — only observation/capture of one legitimately delivered webhook to a store the attacker controls, then a single forged HTTP request to the app's public webhook endpoint with a swapped shop header.

### Recommendation
Do not treat the `shop-domain` (or `topic`/`webhook-id`/`api-version`) headers as trusted tenant identity purely because the body HMAC validates. At minimum:
- Cross-check the resolved `shop` against a shop that the app has an active session/installation for, and/or
- Bind the shop identity to the verified channel by additionally validating it against Shopify's known webhook endpoint registration for that specific shop (e.g. reconcile with the `webhookId`/subscription previously registered for that shop via `Registry.register`), or
- Require the host application to perform out-of-band verification (mTLS/IP allow-listing to Shopify) in addition to HMAC, and document this gap clearly if it is intentionally left to the host app.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers any webhook topic the app registers for (e.g. `orders/create`), capturing the raw body `B` and the `X-Shopify-Hmac-Sha256` header value `H` that Shopify sent.
2. Attacker sends a forged HTTP POST to the app's public webhook endpoint with:
   - Body: `B` (unmodified)
   - Header `X-Shopify-Hmac-Sha256: H` (unmodified, still validates because body unmodified)
   - Header `X-Shopify-Topic: orders/create` (unmodified or attacker-chosen, also unauthenticated)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (swapped to victim)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H` using the shared `api_secret_key`: [3](#0-2) 
4. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled body content, despite the request never having been authenticated for that shop.
