### Title
Webhook `shop-domain` header is trusted without HMAC coverage, allowing cross-tenant identity spoofing on otherwise-valid webhook deliveries - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity solely via `Utils::HmacValidator.validate(request)`, which computes the HMAC over the raw request body only. The `shop` identifier used to attribute the webhook to a tenant is read from an HTTP header that is never included in the signed bytes, breaking the equality "bytes verified == bytes that determine identity."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

The `shop` accessor, however, is pulled straight from the `shopify-shop-domain` (or `x-shopify-shop-domain`) HTTP header, completely outside the HMAC's coverage: [2](#0-1) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (which re-derives the signature from `to_signable_string`, i.e. the body) before dispatching to the handler with `request.shop` passed straight into `WebhookMetadata`: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` confirm only that the *body* bytes match a signature computed with `Context.api_secret_key`; they never fold the `shop` header into that computation: [4](#0-3) 

Identity-binding equality that should hold: `shop header bound by HMAC == shop attributed to the payload`. Here that equality does not exist — the HMAC only proves "these body bytes were signed by the app's secret," not "this body belongs to shop X." This is analogous to the reported bug class: a field that is acted upon (`shop`, used to attribute/dispatch the payload) is not covered by the integrity check (the HMAC), so its binding to the rest of the verified data can be broken independently.

Concretely: any host application that receives webhook requests behind a shared endpoint and forwards raw headers/body to `ShopifyAPI::Webhooks::Request.new` is vulnerable to a "shop-domain swap": if an attacker holds a legitimately-signed `(raw_body, hmac)` pair for their own shop (trivial, since they can freely install the app on a shop they control and capture a real Shopify-signed webhook), they can replay that exact `raw_body`/`hmac` pair while substituting the `shop-domain` header for an arbitrary victim shop domain (which they can freely choose since Shopify shop domains are public/predictable, e.g. `victim.myshopify.com`). `HmacValidator.validate` still returns `true` because it only checks the body against the secret; `Registry.process` then dispatches `WebhookMetadata.new(topic:, shop: request.shop, body:, ...)` to the app's handler with `shop` set to the attacker-chosen victim domain, while `body` is really the attacker's own shop's data.

### Impact Explanation
This is a cross-tenant identity-confusion primitive: an app's webhook handler will believe attacker-controlled/attacker-owned payload data belongs to a different, victim merchant, because the only field distinguishing tenants (`shop`) is unauthenticated relative to the HMAC. Depending on how a host app uses `WebhookMetadata#shop` (e.g., to look up/update the shop's session, orders, or other tenant-scoped records), this can result in cross-tenant data writes or reads attributed to the wrong merchant — matching the "cross-tenant access" Critical impact category, since the gem's own webhook-verification API provides no binding between the authenticated bytes and the tenant identifier it hands to the handler.

### Likelihood Explanation
Requires the attacker to be a legitimate (even free-tier) app installer on their own shop, which is an unprivileged internet-user capability — no leaked credentials, `api_secret_key`, or access token needed. They only need one genuine webhook delivery from Shopify to their own store to obtain a valid `(raw_body, hmac)` pair, then can replay it against the shared webhook endpoint with a spoofed `shop-domain` header. The main constraint is that the replayed body content must plausibly apply to the target shop (it's the attacker's own shop's data, not literally the victim's), which the classic report's team explicitly treated as an acceptable "self-inflicted, low-precondition" attack path (analogous to "one user depositing to another" in the original report). Likelihood is Medium: no secret material required, but the practical value of the confusion depends on host-app logic that keys business actions off `WebhookMetadata#shop`.

### Recommendation
Include the `shop` domain (and ideally `topic`/`webhook_id`) in the HMAC-signable string, or otherwise cryptographically bind the header value to the signed payload, e.g.:
```ruby
sig { override.returns(String) }
def to_signable_string
  "#{shop}|#{topic}|#{@raw_body}"
end
```
and update `Registry.process` / documentation so integrators are told the shop header is only trustworthy after this binding is verified, not merely because `HmacValidator.validate` returned `true`.

### Proof of Concept
```ruby
require "shopify_api"

ShopifyAPI::Context.setup(
  api_key: "key",
  api_secret_key: "shared_secret",
  api_version: "2024-01",
  is_private: false,
  is_embedded: true,
  scope: "read_orders",
  host_name: "app.example.com",
)

# Step 1: attacker installs the app on their own shop "attacker-shop.myshopify.com"
# and receives a real Shopify webhook, e.g. orders/create:
raw_body = '{"id":1,"note":"attacker-owned data"}'
real_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "shared_secret", raw_body)
)

# Step 2: attacker replays the same (raw_body, hmac) pair, but swaps the
# shop-domain header to a victim shop they do not own/control.
spoofed_headers = {
  "x-shopify-topic"          => "orders/create",
  "x-shopify-hmac-sha256"    => real_hmac,
  "x-shopify-shop-domain"    => "victim-shop.myshopify.com", # attacker-chosen
  "x-shopify-webhook-id"     => "spoofed-id",
  "x-shopify-api-version"    => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: spoofed_headers)

# Passes validation because only raw_body is checked against the HMAC:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# The registered handler receives shop == "victim-shop.myshopify.com"
# even though the payload originated from the attacker's own shop.
ShopifyAPI::Webhooks::Registry.process(request)
```
