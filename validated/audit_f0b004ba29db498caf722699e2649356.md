### Title
Webhook shop-domain identity is not covered by the HMAC signature, allowing cross-tenant webhook attribution - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook by HMAC-validating only the raw request body, but the tenant identifier (`shop`) that the gem hands to the app's handler is taken from an unauthenticated HTTP header that is never part of the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate`/`validate_signature` compute and compare the HMAC exclusively over that signable string [2](#0-1) . Meanwhile `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the body or the HMAC [3](#0-2) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching, and then builds `WebhookMetadata` (the object passed to the app's `handle` method) using `request.shop` verbatim, alongside the topic and body [4](#0-3) . `WebhookMetadata.shop` is documented and used by consuming apps as the tenant key for routing/storing the webhook payload [5](#0-4) [6](#0-5) .

The identity binding that should hold is: `shop verified by HMAC == shop delivered to handler`. Because the header carrying `shop` (and `topic`, `webhook-id`, `api-version`) is outside `to_signable_string`, that equality does not hold — the HMAC only proves the body bytes were signed with the app's `api_secret_key`; it proves nothing about which shop header accompanies those bytes.

Since a single Shopify app has one shared `client_secret`/`api_secret_key` across all its merchant installations, any merchant (an unprivileged internet user who installed the app) legitimately receives webhook deliveries whose body+HMAC are valid under that same shared secret. Such a merchant can capture one of their own legitimately-signed webhook deliveries (raw body + `x-shopify-hmac-sha256`) and replay it to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header value for a different (victim) shop. `HmacValidator.validate` still succeeds, because it never inspects the shop header, and `Registry.process` will call the handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop domain.

### Impact Explanation
This breaks the identity binding between "HMAC-authenticated sender" and "shop the data is attributed to," letting one merchant's legitimately-signed webhook traffic be relabeled and attributed to another tenant. Any app logic that trusts `data.shop` as the tenant key (session/data lookups, per-shop storage, billing/order processing keyed by shop) can be tricked into cross-tenant data association — this matches the Critical category of "cross-tenant access" defined in scope, since it lets an attacker inject data under another tenant's identity without holding that tenant's credentials.

### Likelihood Explanation
Exploitation requires only: (1) being an app-installing merchant able to receive at least one webhook delivery (a routine, unprivileged event), and (2) resending an HTTP POST to the app's public webhook endpoint with a modified header, no secrets or elevated access needed. This is a low-effort, no-privilege replay, made possible purely by the gem's signing scope choice.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed material, or independently and cryptographically bind `request.shop` to the verified payload (e.g., verify against Shopify's per-request `X-Shopify-Shop-Domain` only after establishing it cannot be swapped independently of the HMAC, such as by additionally validating the webhook against the shop's registered/expected domain from the session store before dispatch). At minimum, document prominently that `WebhookMetadata.shop` is unauthenticated and must not be trusted as a tenant key without app-side cross-checking against the shop that originally registered the webhook subscription.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and legitimately receives a webhook: raw body `B`, header `x-shopify-hmac-sha256: H` (valid because `H = HMAC-SHA256(api_secret_key, B)`), and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends `POST /callback/orders/create` to the app with the same body `B` and header `H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop: "victim.myshopify.com", hmac: H})` is constructed [7](#0-6) .
4. `Registry.process` calls `HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and matches `H` — validation passes [8](#0-7) .
5. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, i.e., attacker-originated data now attributed to the victim shop [9](#0-8) .

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
