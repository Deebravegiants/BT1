### Title
Single global `maxOracleAge` staleness bound applied to native and token oracles with different heartbeats - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster` prices ERC-4337 gas sponsorship in stablecoins using two independent Chainlink feeds — `nativeOracle` (e.g. ETH/USD or BNB/USD) and a per-token `tokenOracle` (e.g. USDC/USD, USDT/USD) — but validates staleness for both feeds against the same single state variable `maxOracleAge`, even though the contract's own documentation acknowledges these feeds have materially different heartbeats.

### Finding Description
`_getOraclePrice` is the sole staleness check used for every oracle read in the contract, and it takes only the oracle address/decimals — not a per-oracle staleness bound: [1](#0-0) 

Both `_tokenPrice` (used to price every UserOp's gas cost) and `swapAndDeposit` (used to compute the minimum swap output for fee recycling) call `_getOraclePrice` for the `nativeOracle` and the token's `tokenOracle` using the exact same global `maxOracleAge`: [2](#0-1) [3](#0-2) 

The `Params` struct and its doc comment explicitly acknowledge that heartbeats differ across chains/feeds — BSC stablecoin feeds update roughly every 27 seconds while Base/Ethereum stablecoin feeds can go up to 24 hours between updates — yet only a single `maxOracleAge` field exists to bound staleness for both the native-asset feed and every registered token feed: [4](#0-3) 

Because governance must pick one value that accommodates the slowest-heartbeat oracle in use (e.g. up to `MAX_ORACLE_AGE = 7 days`, or realistically the ~24h Base/Ethereum bound noted in the deploy script), any co-used oracle with a much tighter intrinsic heartbeat (e.g. a ~27s BSC feed) can silently stop updating and still pass the staleness check for the entire loose window. This is the same root cause as the referenced `KeeperFee.getKeeperFee` finding: two logically distinct price sources are gated by one staleness period sized for the least frequently updated one. [5](#0-4) 

### Impact Explanation
Any unprivileged UserOp sender (a "bandwidth purchaser" of ERC-4337 gas sponsorship) triggers `_tokenPrice`/`_getOraclePrice` on every paymaster validation. If the fast-heartbeat oracle (native or token) stalls or is manipulated/frozen while still within the loosely-configured global `maxOracleAge`, the paymaster computes gas cost off a stale, unrepresentative price for that leg of the ratio, mispricing every UserOp until the stale feed either recovers or is caught by the loose bound. This can cause users to be over/undercharged in stablecoins relative to actual gas cost, and `swapAndDeposit`'s `amountOutMin` slippage protection is derived from the same stale ratio, so fee-recycling swaps could execute at a bad price, and if reserves are undercharged the paymaster deposit can be drained via repeated cheap UserOps — a fund-loss/mispricing condition, not merely a griefing/DoS issue.

### Likelihood Explanation
The condition requires only that a genuine Chainlink feed with a tight heartbeat degrades or is delayed (a realistic, historically observed failure mode) while still falling inside the shared, necessarily-loose `maxOracleAge` set to accommodate the slower-heartbeat feed on the same deployment (Base/Ethereum stablecoin feeds vs. BSC's ~27s feeds, per the contract's own comments and deploy script). No privileged action or governance misconfiguration beyond ordinary parameter setting is required, and every UserOp naturally re-triggers the vulnerable price path.

### Recommendation
Store and validate staleness independently per oracle: add a `maxOracleAge` (or heartbeat) field to `TokenConfig` for each token oracle, and a separate one for `nativeOracle`, then pass the appropriate bound into `_getOraclePrice` for each call site (`_tokenPrice` and `swapAndDeposit`) instead of relying on one shared `maxOracleAge`.

### Proof of Concept
1. Governance configures `maxOracleAge = 24 hours` to accommodate a Base/Ethereum stablecoin `tokenOracle` with a 24h heartbeat, per the deploy script's guidance. [5](#0-4) 
2. The `nativeOracle` (e.g. a BNB/USD feed with a ~27s heartbeat) stops updating due to an upstream outage; `latestRoundData().updatedAt` freezes.
3. For up to 24 hours, `_getOraclePrice(nativeOracle, ...)` in `_tokenPrice` still passes the `block.timestamp - updatedAt > maxOracleAge` check because the shared bound is sized for the token oracle, not the native oracle. [6](#0-5) 
4. Every UserOp submitted during this window is priced/charged in stablecoins using the stale native price, and any `swapAndDeposit` call during this window computes `amountOutMin` from the same stale ratio, exposing the paymaster's fee-recycling swaps and gas-cost accounting to a materially wrong price with no revert to signal the failure.

    function _tokenPrice(TokenConfig memory cfg) internal view returns (uint256) {
        uint256 nativeUsd = _getOraclePrice(nativeOracle, nativeOracleDecimals);
        uint256 tokenUsd = _getOraclePrice(cfg.tokenOracle, cfg.tokenOracleDecimals);

        return (nativeUsd * (10 ** cfg.tokenDecimals) * (10_000 + markupBps)) / (tokenUsd * 10_000);
    }

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
