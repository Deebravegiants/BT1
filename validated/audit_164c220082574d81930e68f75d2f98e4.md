Based on my investigation of the in-scope library code (`lib/shopify_api/webhooks/**`, `lib/shopify_api/utils/hmac_validator.rb`), I found a concrete identity-binding gap that matches the report's bug class ("a field acted on but not covered by the HMAC").

### Title
Webhook HMAC validation does not cover the `shop`/`topic`/`webhook-id` identity headers, allowing a validly-signed payload to be replayed under a forged shop identity - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body. The `shop`, `topic`, and `webhook-id` values that are subsequently trusted and handed to the application's webhook handler are read straight from HTTP headers that are **not included in the signed material**, so they carry no cryptographic binding to the verified body.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all derived purely from HTTP headers, outside the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC only over `verifiable_query.to_signable_string`, i.e., the raw body: [3](#0-2) 

`Webhooks::Registry.process` uses this validation as its sole authenticity gate, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` (all unsigned headers) to build the `WebhookMetadata` passed to the application's handler: [4](#0-3) 

This is the same root-cause pattern as the H-2 report: a check validates one artifact (the divider's `combine()` yield / here, the raw body's HMAC), while a *different*, related artifact that the caller actually acts upon (the ejected/target balance transferred to the user / here, the `shop` identity attributed to the payload) is not covered by that same check. The equality that should hold — `shop_bound_by_hmac == shop_delivered_to_handler` — does not hold, because the left-hand side doesn't exist at all: the gem never binds `shop` to the signature.

### Impact Explanation
Because the header-derived `shop` (and `topic`/`webhook_id`) is not bound to the HMAC, any party that possesses one valid `(raw_body, hmac)` pair previously issued by Shopify for the app's secret can replay that exact HTTP request while substituting an arbitrary `x-shopify-shop-domain` header. `Registry.process` will accept it (HMAC over the body still matches) and hand the host application a `WebhookMetadata` whose `shop` attribute has been forged to a different tenant than the one that actually generated the data. If the host application uses this `shop` value as the tenant/session key when persisting or acting on the webhook body (the documented and expected usage per `docs/usage/webhooks.md`), this results in cross-tenant data misattribution — one shop's order/customer/GDPR data being written into or triggering actions for a completely different shop's session.

### Likelihood Explanation
Exploitation requires the attacker to already possess a legitimately-signed `(raw_body, hmac)` pair for the target app (e.g., from their own installed shop's webhook traffic, from debug/error logs that echo the raw payload and headers, or from any other non-TLS-interception avenue of observing one legitimate delivery). No knowledge of `api_secret_key` is required — only re-use of an already-valid signature over a re-purposed identity header — which is exactly the class of "bytes verified versus bytes parsed" gap called out as in-scope. This is a design gap in the gem itself (`Registry.process` / `HmacValidator`), independent of any host application misuse, so it is not excluded by the "ignoring documented API" carve-out.

### Recommendation
Bind the webhook's tenant/topic identity into the authenticity check rather than trusting unsigned headers verbatim:
- Have `VerifiableQuery`/`to_signable_string` for webhook requests include `shop`, `topic`, and `webhook_id` (or otherwise incorporate them into the HMAC input) so a replayed body cannot be reattributed to a different shop.
- Alternatively/additionally, cross-check `request.shop` against the shop associated with the session/topic registration before invoking the handler, rejecting mismatches.

### Proof of Concept
1. Obtain any one legitimate webhook delivery to the target app: raw JSON body `B` and its valid header `x-shopify-hmac-sha256: H` (computed by Shopify over `B` with the app's `client_secret`), for `shop.myshopify.com`.
2. Replay the exact same body `B` and HMAC header `H` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` succeeds because it only checks `B` against `H`: [5](#0-4) 
4. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the application to process/store legitimate order/customer data under the wrong tenant.
