### Title
Accrued market totals overflow `i128` before the borrow-index cap, permanently freezing the market - (File: common/src/rates/scaling.rs) [1](#0-0) 

### Summary
A market whose scaled borrow or supply principal is close to the RAY value ceiling can become permanently unusable when interest accrual multiplies the scaled principal by the updated index. `scaled_to_original` performs a checked `Ray` multiplication, so an accrued value exceeding `i128::MAX` panics with `MathOverflow` before the borrow-index ceiling can clamp growth. [1](#0-0) [2](#0-1) 

### Finding Description
Every pool accrual begins by unscaling the market's stored scaled borrow and supply balances with `scaled_to_original`. [3](#0-2)  That helper calls `Ray::mul`, and a result outside the `i128` domain panics as `GenericError::MathOverflow`. [1](#0-0) [4](#0-3) 

The intended borrow-index ceiling is `MAX_BORROW_INDEX_RAY`, but it is applied only after the pre-accrual balance multiplication succeeds. [5](#0-4)  Consequently, a sufficiently large market can cross the absolute RAY value ceiling while `borrow_index` remains below `MAX_BORROW_INDEX_RAY`, leaving the accrual function unable to complete. [6](#0-5) 

### Impact Explanation
This is a permanent freezing-of-funds condition for the affected hub asset. Once the market enters the overflowing state, `update_indexes`, `repay`, `withdraw`, liquidation-related accrual, and other market mutations fail during the same prerequisite accrual step, so suppliers cannot exit and borrowers cannot reduce debt. [7](#0-6) 

The in-repository reproduction demonstrates a one-billion-token, 18-decimal market at 98% utilization failing with `MATH_OVERFLOW` while the stored borrow index is still below `MAX_BORROW_INDEX_RAY`; subsequent one-unit withdrawal and repayment attempts fail identically. [8](#0-7) 

### Likelihood Explanation
An unprivileged borrower can initiate the trajectory through ordinary `supply` and `borrow` calls if a listed market's caps and token supply permit a position near the demonstrated domain boundary. [9](#0-8)  Afterward, anyone can advance the failure through the permissionless `update_indexes(caller, assets)` entrypoint; no malformed storage or privileged call is required. [10](#0-9) 

The exploit requires an exceptionally large whale market and sustained high utilization, so it is less likely in tightly capped markets, but the protocol's documented cap domain alone does not prevent admitted balances from later exceeding the accrued-value domain. [11](#0-10) 

### Recommendation
Bound or saturate the underlying RAY-valued market totals before calling `scaled_to_original`, rather than relying solely on the index ceiling. In particular, accrual should detect `scaled * index > i128::MAX`, stop index growth or clamp the affected value at a protocol-defined ceiling, and still commit a state that permits repayment, withdrawal, liquidation, and bad-debt processing. At listing and entry time, caps should also be checked against the maximum accrued RAY value for the configured index ceiling, not merely the amount representable at the current index. [12](#0-11) [13](#0-12)

/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
