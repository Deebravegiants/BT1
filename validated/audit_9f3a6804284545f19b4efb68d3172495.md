### Title
Unwrapped relayer-fee `safeTransfer` in `EvmHost.dispatchIncoming(GetResponse,...)` lets one starved fee balance revert an entire GET-response batch - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatchIncoming` for `GetResponse` messages unconditionally pays the delivering relayer the request's full recorded `fee` via `IERC20(feeToken()).safeTransfer(relayer, fee)` after the app's `onGetResponse` callback succeeds. This transfer is hard-coded to the exact fee amount with no fallback, no cap to the host's actual balance, and, critically, is not wrapped in a try/catch the way the `onGetResponse` app callback is. `HandlerV2.handleGetResponses` calls `dispatchIncoming` in a plain loop for every response in a verified batch, so if the host's fee-token balance is insufficient to cover even one relayer's fee, `safeTransfer` reverts and unwinds the entire batch transaction — including all app-level GET response deliveries and side effects for every other request in that same call, plus the state changes already made to `_responseReceipts`.

### Finding Description
`dispatchIncoming(GetResponse memory response, address relayer)` is restricted to the handler and is the code path responsible for both invoking `IApp.onGetResponse` on the destination app and paying the relayer's fee: [3](#0-2) 

The app callback failure path is deliberately non-reverting (`if (!success) { delete _responseReceipts[commitment]; return; }`), consistent with the pattern documented for `dispatchIncoming(PostRequest,...)`, which is designed precisely to let a rejected/failing delivery stay retryable rather than block the whole batch: [4](#0-3) 

However, the relayer fee payout that follows the successful callback breaks this isolation model: it is a plain external call, not gated behind a `(bool success,) = ... call(...)` pattern, so any revert inside `safeTransfer` (e.g. `ERC20InsufficientBalance` when the host's fee-token balance is below `fee`) propagates up through `dispatchIncoming` and up through `HandlerV2.handleGetResponses`'s loop, reverting the whole batch: [5](#0-4) 

This is the same bug class as the reported hard-coded slippage/all-or-nothing transfer: the amount paid to the relayer is rigidly fixed to the escrowed `fee` with no mechanism to pay out a lesser (or zero) amount and let the app-side delivery succeed regardless. Unlike the `WithdrawParams`/`WithdrawRelayerFees` flows elsewhere in this codebase (which are similarly all-or-nothing but are isolated to their own dispatch and therefore fail without touching unrelated deliveries — see `HostManager.onAccept` at `evm/src/core/HostManager.sol:134-159` and the `modules/pallets/ismp/src/dispatcher.rs` withdrawal module), this GET-response relayer reward payout is entangled with the message-delivery critical path for an entire batch.

### Impact Explanation
Any relayer submitting a `handleGetResponses` batch is fully at the mercy of the host's current fee-token balance for every request in that batch. If the host's fee-token balance ever dips below the fee owed on any single response in a batch (e.g., because outbound dispatch fees were spent down, drained, or a race with another concurrent withdrawal/consumption of the fee token occurs), the entire batch reverts: no GET responses in that transaction are delivered, no relayer is paid, and every app expecting its query result stalls. Because `_responseReceipts` for the whole batch were about to be set but nothing commits on revert, a relayer must retry — but every retry with the same starved balance reverts identically, effectively creating a stall in GET response delivery to the destination chain state machine (denial of service on all apps relying on GET/response query flows on that host) until the host is manually replenished. Given GET-response delivery underpins ISMP query semantics used by other in-scope surfaces (consensus proof relays, state queries), a sustained shortfall in the host fee-token balance can block message delivery broadly, not just a single relayer's reward.

### Likelihood Explanation
This requires no malicious actor: it triggers purely from an ordinary imbalance between fees owed and the host's actual fee-token balance, which can occur naturally (e.g. concurrent consumption of the fee token by other host operations, governance withdrawals draining the balance, or fee-token migrations noted in `EvmHost.updateHostParams`'s `CannotChangeFeeToken` check). Any relayer batching multiple GET responses together (the intended, gas-efficient usage pattern) is exposed; a single underfunded response commitment poisons the entire batch for that relayer.

### Recommendation
Wrap the relayer-fee `safeTransfer` in `dispatchIncoming(GetResponse,...)` in the same non-reverting `.call()` pattern already used for the `onGetResponse` invocation (or a dedicated low-level `try/catch`), so a starved fee-token balance degrades gracefully — e.g., pay what's available or skip the transfer and leave `fee` claimable later — rather than reverting the delivery and unwinding the entire GET-response batch. At minimum, isolate the transfer per-response so failures don't propagate to sibling deliveries in the same `handleGetResponses` call.

### Proof of Concept
1. Multiple apps dispatch GET requests; Hyperbridge accrues distinct `fee`s recorded in `_requestCommitments[commitment].fee` for each, via the normal outbound dispatch flow.
2. The host's fee-token balance is drawn down below the sum (or even a single one) of these outstanding fees — e.g., through legitimate governance `withdraw()` calls (`evm/src/core/EvmHost.sol:651-660`) or a fee-token migration.
3. A relayer submits a `handleGetResponses` batch containing responses for several requests, including the one whose fee now exceeds the host's remaining balance.
4. `HandlerV2.handleGetResponses` loops and calls `host.dispatchIncoming(leaf.response, _msgSender())` for each; for the underfunded response, the app's `onGetResponse` succeeds, but `IERC20(feeToken()).safeTransfer(relayer, fee)` reverts with `ERC20InsufficientBalance`.
5. Because this call is not caught, the revert propagates out of `handleGetResponses`, reverting the entire transaction — including the successful deliveries to all other apps' `onGetResponse` in the same batch — and consuming the relayer's gas with zero effect.
6. Every subsequent retry with the same fee-token shortfall fails identically until the host balance is restored, stalling GET response delivery for the affected destination chain.

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }

    function handleGetResponses(IHost host, GetResponseMessage calldata message) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(message.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 responsesLength = message.responses.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](responsesLength);

        for (uint256 i = 0; i < responsesLength; ++i) {
            GetResponseLeaf memory leaf = message.responses[i];
            // don't check for timeouts because it's checked on Hyperbridge

            // known request? also serves as source check
            FeeMetadata memory meta = host.requestCommitments(leaf.response.request.hash());
            if (meta.sender == address(0)) revert UnknownMessage();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.response.hash());
        }

        bytes32 root = host.stateMachineCommitment(message.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, message.proof.multiproof, leaves, message.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < responsesLength; ++i) {
            GetResponseLeaf memory leaf = message.responses[i];
            // duplicate response?
            if (host.responseReceipts(leaf.response.request.hash()).relayer != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.response, _msgSender());
        }
    }
