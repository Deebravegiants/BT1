### Title
Bridge selection is re-evaluated independently for withdrawal execution vs. status tracking, allowing the tracked bridge to diverge from the executing bridge - (File: `packages/intents-sdk/src/sdk.ts`, `packages/intents-sdk/src/core/withdrawal-watcher.ts`)

### Summary
`IntentsSDK.createWithdrawalIntents` (`packages/intents-sdk/src/sdk.ts:334-372`) selects a bridge for a withdrawal by iterating `this.bridges` and calling each bridge's `supports()` at intent-creation time [1](#0-0) . Later, `createWithdrawalCompletionPromises` independently calls `createWithdrawalIdentifiers`, which again iterates `this.bridges` calling `supports()` to pick the bridge used for `describeWithdrawal`/status polling [2](#0-1) . These two bridge-selection passes happen at different times (before vs. after intent settlement, per `processWithdrawal`'s multi-step flow) [3](#0-2) , and `supports()` for PoaBridge/OmniBridge is not a pure/static function of `assetId` - it depends on time-varying, cached external state.

### Finding Description
`PoaBridge.supports()` checks `POA_TOKENS_MIGRATED_TO_OMNI_BRIDGE` against the parsed asset's `contractId`, returning `false` once a token is present in that migration map [4](#0-3) . `OmniBridge.supports()` performs an async, cached lookup (`getCachedDestinationTokenAddress`) to decide support, and that cache/backing data can change between calls [5](#0-4) .

Because bridge selection is performed twice - once in `createWithdrawalIntents` to build/execute the withdrawal intent, and again in `createWithdrawalCompletionPromises`/`createWithdrawalIdentifiers` to build the `WithdrawalIdentifier` used for status polling - if the underlying "migrated"/"supported" state used by `supports()` changes between the two calls (e.g., a token transitioning between PoA and Omni bridge support during the window between intent signing and settlement), the second pass can pick a *different* `Bridge` instance than the one that actually executed and holds custody of the withdrawal on-chain. `watchWithdrawal` then polls `describeWithdrawal` on the wrong bridge [6](#0-5) , which has no record of the withdrawal, so it never reports `"completed"`. This breaks the equality that "the bridge queried for status is the bridge that custodies/executed the withdrawal."

### Impact Explanation
If the two `supports()` evaluations diverge, the withdrawal actually completes on-chain via bridge A, but the SDK polls bridge B for status. `watchWithdrawal` will never see the withdrawal as completed and will eventually throw `WithdrawalWatchError` (poll timeout) [7](#0-6) , misreporting a successful withdrawal as stuck/unresolved and requiring manual/off-band investigation to confirm actual on-chain completion. Per the rules, this maps to "a status reported that is not the on-chain outcome" / "a withdrawal stuck until manual intervention."

### Likelihood Explanation
The window for divergence requires `POA_TOKENS_MIGRATED_TO_OMNI_BRIDGE` (a static, hardcoded map compiled into the running process) to change, or the Omni bridge's async destination-token cache to flip results, between `createWithdrawalIntents` (called before signing) and `createWithdrawalIdentifiers` (called after intent settlement, potentially much later). Since `POA_TOKENS_MIGRATED_TO_OMNI_BRIDGE` is a static constant baked in at build time, it cannot change within a single running SDK instance without a redeploy, and the Omni bridge cache is keyed by token/chain pair with no illustrated invalidation-based flip evidence found in the explored code. I could not fully verify the TTL/invalidation behavior of `getCachedDestinationTokenAddress` or confirm a concrete, attacker-controlled path to force divergence within a single process lifetime, so likelihood is low/uncertain based on what was inspected.

### Recommendation
Select the bridge once per withdrawal (at intent-creation time) and thread that same `Bridge` reference/route through to the status-tracking phase (e.g., by persisting the selected bridge's `route` alongside the intent/withdrawal record) rather than re-deriving it independently via a second `supports()` pass in `createWithdrawalIdentifiers`.

### Proof of Concept
Not concretely demonstrable from the explored code: the divergence would require the static `POA_TOKENS_MIGRATED_TO_OMNI_BRIDGE` constant or the Omni bridge's destination-token cache to change value between the two `supports()` calls within one SDK process lifetime, which was not confirmed to be reachable through any code path inspected in `packages/intents-sdk/src/**`.

export async function watchWithdrawal(args: {
	bridge: Bridge;
	wid: WithdrawalIdentifier;
	signal?: AbortSignal;
	logger?: ILogger;
}): Promise<TxInfo | TxNoInfo> {
	const stats = getWithdrawalStatsForChain({
		chain: args.wid.landingChain,
		bridgeRoute: args.bridge.route,
	});
	let consecutiveErrors = 0;

	try {
		return await poll(
			async () => {
				try {
					const status = await args.bridge.describeWithdrawal({
						...args.wid,
						logger: args.logger,
					});

					consecutiveErrors = 0;

					if (status.status === "completed") {
						return status.txHash != null
							? { hash: status.txHash }
							: { hash: null };
					}

					if (status.status === "failed") {
						throw new WithdrawalFailedError(status.reason);
					}

					return POLL_PENDING;
				} catch (err: unknown) {
					if (err instanceof WithdrawalFailedError) {
						throw err;
					}

					consecutiveErrors++;
					if (consecutiveErrors >= MAX_CONSECUTIVE_ERRORS) {
						throw new WithdrawalWatchError(err);
					}

					args.logger?.warn(
						`Transient error (${consecutiveErrors}/${MAX_CONSECUTIVE_ERRORS}): ${err}`,
					);
					return POLL_PENDING;
				}
			},
			{ stats, signal: args.signal },
		);
	} catch (err: unknown) {
		if (err instanceof PollTimeoutError) {
			throw new WithdrawalWatchError(err);
		}
		throw err;
	}
}

async function findBridgeForWithdrawal(
	bridges: Bridge[],
	params: WithdrawalParams,
): Promise<Bridge | undefined> {
	for (const bridge of bridges) {
		if (await bridge.supports(params)) {
			return bridge;
		}
	}
	return undefined;
}
