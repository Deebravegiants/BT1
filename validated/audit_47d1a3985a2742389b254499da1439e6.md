### Title
Duplicate authority votes in `EcdsaBeefy.verifyMmrUpdateProof` are not deduplicated before checking the BEEFY supermajority threshold - (File: `evm/src/consensus/EcdsaBeefy.sol`)

### Summary
The `AggregatorOracle` report flags that supplying the same oracle source more than once silently defeats a quorum-style safety check (max-deviation across N *independent* sources) because the code never verifies that the supplied sources are distinct. The same bug class is reachable in Hyperbridge's ECDSA-BEEFY consensus client: `verifyMmrUpdateProof` in `evm/src/consensus/EcdsaBeefy.sol` counts `relayProof.signedCommitment.votes.length` directly against the 2/3+1 supermajority threshold without ever checking that the `authorityIndex` values (and therefore the underlying signers) in `votes` are unique.

### Finding Description
`verifyMmrUpdateProof` computes `sigLen` as the raw length of the caller-supplied `votes` array and passes it straight into `checkParticipationThreshold`: [1](#0-0) 

```solidity
uint256 sigLen = relayProof.signedCommitment.votes.length;
...
if (!checkParticipationThreshold(sigLen, authoritySet.len)) revert SuperMajorityRequired();
```

`checkParticipationThreshold` is a pure arithmetic comparison with no notion of who signed: [2](#0-1) 

After the threshold check passes, each vote is recovered via `ECDSA.recover` and turned into a `MerkleMultiProof.Leaf{index: vote.authorityIndex, hash: ...}`, then verified as a batch against the authority-set merkle root: [3](#0-2) 

Nowhere in this flow — nor in the equivalent off-chain Rust verifier `verify_mmr_update_proof` in `modules/consensus/beefy/verifier/src/lib.rs` — is there a check that the `authorityIndex`/`sig.index` values submitted in the votes/signatures array are distinct: [4](#0-3) 

This is the identical root cause pattern as the `AggregatorOracle` finding: a count-based quorum/threshold check (`len >= 2/3 * total + 1`, analogous to "N-of-M sources within max deviation") is satisfied by *counting array entries* instead of counting *distinct, verified signers*. A relayer constructing the `RelayChainProof` can repeat the same `(authorityIndex, signature)` pair (or the same signature under different indices signed by a single validator, if replay of a single validator's own signature at multiple claimed indices were otherwise accepted) to inflate `sigLen` past the supermajority requirement while the number of genuinely distinct, honest signers backing the commitment is far below 2/3+1.

Whether this is fully exploitable end-to-end depends on the external `MerkleMultiProof.VerifyProof` (from `@polytope-labs/solidity-merkle-trees`, not vendored in this repo, so its exact duplicate-index handling could not be verified in this session). If that library's multi-proof algorithm does not itself reject duplicate `index` entries in the `Leaf[]` array (many merkle multi-proof algorithms only check that supplied leaves are consistent with the claimed root and total leaf count — sorting/pairing by k-index — and do not enforce leaf-index uniqueness across the whole proof), then a single validator's one real, valid signature can be duplicated N times in `votes` to pass both `checkParticipationThreshold` and `MerkleMultiProof.VerifyProof`, since every duplicated entry has an identical, verifiably-correct index/hash pair.

### Impact Explanation
If duplicate votes are accepted, the on-chain BEEFY consensus client can be advanced (authority set rotation, MMR root update, and downstream parachain-header state commitments) with far fewer than 2/3+1 of the real authority set's cooperation — potentially with the cooperation of just one or a handful of compromised/complicit signers replaying their own valid signature. Since `verifyMmrUpdateProof` feeds directly into `verifyParachainHeaderProof` and ultimately into state-machine commitments trusted by `pallet-ismp`/`HandlerV2` for message/state proof verification, this would let an attacker forge finalized state for connected parachains, enabling forged message delivery or unbacked minting on the receiving side. This satisfies "unsound state commitment" / "forged message delivery" impact.

### Likelihood Explanation
This path is reachable by any relayer submitting a `RelayChainProof` to `EcdsaBeefy.verify` — a permissionless, unauthenticated entry point (no `onlyOwner`/access control), which is strictly more exposed than the `onlyOwner`-gated `AggregatorOracle._setPrimarySources`. The only barrier is whether the external merkle-multi-proof library independently rejects duplicate leaf indices; this could not be confirmed from the code available in this repository's index, so likelihood is assessed as medium pending verification of that library's exact algorithm.

### Recommendation
In `verifyMmrUpdateProof` (and the mirrored Rust `verify_mmr_update_proof`), before computing `sigLen`/`signatures_length` and before running the merkle multi-proof check, deduplicate on `authorityIndex`/`sig.index` (e.g. build a `BTreeSet`/bitmap of seen indices and reject the proof if any index repeats), analogous to the `ensure_unique_addresses` helper already used in the Tendermint verifier (`modules/consensus/tendermint/verifier/src/verifier.rs:219-229`). Only count the size of the deduplicated set against `checkParticipationThreshold`.

### Proof of Concept
1. An attacker (or colluding relayer) obtains one valid ECDSA signature `sig` from authority `i` over a legitimate BEEFY commitment (or waits for one to appear in the gossip network).
2. They construct a `RelayChainProof` whose `signedCommitment.votes` array repeats `Vote{authorityIndex: i, signature: sig}` enough times to make `sigLen = votes.length >= (2*authoritySet.len)/3 + 1`.
3. They supply a `proof` (merkle multi-proof) whose `Leaf[]` array is built to satisfy the same repeated `(index, hash)` pairs — if the underlying `MerkleMultiProof.VerifyProof` algorithm does not itself enforce distinct leaf indices across the batch, this proof verifies successfully against `authoritySet.root`.
4. `verifyMmrUpdateProof` accepts the update, rotates/advances `trustedState`, and `verifyParachainHeaderProof` commits attacker-controlled parachain state, despite only one real authority having signed.

*(Step 3's feasibility against the vendored `@polytope-labs/solidity-merkle-trees` library could not be independently confirmed in this session since that library's source is not present in this repository's indexed content; this is flagged as an open verification item for whoever investigates further.)*
