### Title
Webhook HMAC verification covers only the raw body, not the `shop`/`topic` headers, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so `Utils::HmacValidator.validate` authenticates nothing but the body bytes. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values, which `Webhooks::Registry.process` trusts to route and tenant-scope the webhook, are read straight from unauthenticated HTTP headers. Anyone who can obtain one valid `(body, hmac)` pair can replay it against the host application's webhook endpoint with an arbitrary `shop-domain`/`topic` header and still pass HMAC validation.

### Finding Description
`Request#hmac`/`#to_signable_string` bind the signature only to `@raw_body`: [1](#0-0) [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` compares the received HMAC against `HMAC(secret, verifiable_query.to_signable_string)`, i.e. `HMAC(secret, raw_body)` only: [4](#0-3) 

`Webhooks::Registry.process` validates that HMAC and then unconditionally trusts `request.shop` and `request.topic` (both header-derived, unauthenticated values) to select the handler and to build the tenant-identifying `WebhookMetadata`: [5](#0-4) 

This breaks the intended identity binding `hmac-verified-body == request-processed-as-shop`. The equality that should hold is `shop_bound_by_hmac == shop_used_for_tenant_dispatch`, but the HMAC binds nothing about `shop` (or `topic`), so the equality is vacuously false: any `shop-domain`/`topic` header value satisfies a body-only HMAC check.

### Impact Explanation
Because many webhook topics have small, predictable, or identical body payloads across all shops (e.g., `app/uninstalled` is delivered with an empty JSON body `{}` for every shop), an attacker who legitimately receives even one webhook delivery for their own shop/app installation can capture the `(raw_body, hmac)` pair and replay it to the same endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic` header) with a value pointing at a different, victim shop. `Registry.process` will pass HMAC validation and invoke the registered handler with attacker-chosen `shop:`/`topic:` in `WebhookMetadata`, causing the host application to execute shop-scoped business logic (data deletion/redaction, cache invalidation, uninstall side effects, entitlement changes, etc.) attributed to a shop the attacker does not control. This is a cross-tenant identity-confusion vulnerability directly enabled by the gem's webhook verification API.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one valid `(body, hmac)` pair, which is trivially available to any merchant/tenant that installs the app (they will legitimately receive webhooks for their own shop, e.g. on install/uninstall). No secret, access token, or privileged access is required — only observing one's own app's webhook traffic and replaying it to the public webhook endpoint with a different `shop-domain` header. This is realistically low-effort for any unprivileged user who can install the app once.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, and ideally `webhook-id`) in the signable string that is HMAC-verified, or otherwise cryptographically bind them to the body before comparison — matching Shopify's documented webhook verification guidance to treat body+headers together, and rejecting mismatches between the header values used for HMAC and those used for dispatch.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; capture a legitimate webhook delivery for `app/uninstalled` (or any topic with a static/predictable body), noting the raw body `{}` and the `x-shopify-hmac-sha256` header value — this is valid per `HmacValidator.validate` for that body under the app's `api_secret_key`.
2. Replay the same request to the app's webhook endpoint, keeping the raw body `{}` and the `x-shopify-hmac-sha256` header unchanged, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) calls `Utils::HmacValidator.validate(request)`, which succeeds because only the body is signature-checked (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. The handler is invoked with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", ...)`, causing the host app to run uninstall/data-deletion logic for `victim-shop.myshopify.com` triggered entirely by the attacker.
