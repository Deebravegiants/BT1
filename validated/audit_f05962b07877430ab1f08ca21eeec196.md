### Title
Donation-driven desync between `Pair`'s virtual `tokenReserve` and real token balance causes a permanent arithmetic-underflow revert (DoS) in `Router._computeBuy` - (File: packages/contracts/src/Router.sol)

### Summary
`Router._computeBuy` caps `tokensOut` at the pair's *real* token balance and then derives a `cappedReserveToken = reserveToken - tokensOut` from the *virtual* stored reserve. The code only guards the case `cappedReserveToken == 0`; it does not guard the case where the real balance exceeds the virtual reserve, which causes an unconditional `uint256` underflow (Solidity Panic) instead of a handled revert. An unprivileged attacker can create this exact condition by repeatedly buying tokens on the curve and then donating them straight back into the `Pair` via a plain ERC20 `transfer` (explicitly a permissionless, in-scope action). This permanently and irreversibly bricks `Router.buy` / `Bonding.buy` / `Zap.buy` for that token, since the underflow-triggering imbalance can never self-heal.

### Finding Description
`Pair` tracks two independent notions of the token side of the curve:
- `_pool.tokenReserve` — the *virtual* reserve, mutated only by `Pair.swap` (i.e. only through `Router.buy`/`Router.sell`). [1](#0-0) 
- `tokenBalance()` — the *real* ERC20 balance of `launchedToken` held by the pair, which anyone can inflate at will by simply calling `IERC20(launchedToken).transfer(pair, amount)`. [2](#0-1) 

`Router._computeBuy` caps `tokensOut` at the real balance and back-derives `amountInUsed` from a "capped" virtual reserve:
```
uint256 realBalance = pair.tokenBalance();
if (tokensOut > realBalance) {
    tokensOut = realBalance;
    uint256 cappedReserveToken = reserveToken - tokensOut;
    if (cappedReserveToken == 0) revert OverflowCapDegenerate();
    ...
}
``` [3](#0-2) 

The explicit guard only handles `reserveToken == realBalance` (division by zero on the next line). It does **not** handle `realBalance > reserveToken`: in that case `reserveToken - tokensOut` (where `tokensOut = realBalance`) underflows a `uint256` before the guard is even evaluated, triggering an unconditional Solidity Panic revert.

Normal curve trading can never trigger this: a buy reduces both `reserveToken` and `realBalance` by the identical amount `tokensOut` (via `Pair.swap`), so the gap `reserveToken - realBalance` (fixed at launch to `LP_RESERVE = 250,000,000e18`, the un-sellable virtual buffer noted in `_deployAndSeed`/`_prepareGraduationLiquidity`) never shrinks through legitimate buys/sells. [4](#0-3) 

However, an attacker can shrink that gap using a "buy, then donate" cycle:
1. Buy `X` tokens on the curve via `Zap.buy` → `Bonding.buy` → `Router.buy`. This reduces `realBalance` by `X` and `reserveToken` by `X` (gap unchanged).
2. Directly `transfer` those same `X` tokens back into the `Pair` (a plain ERC20 transfer, not a curve `sell`). This raises `realBalance` back up by `X`, but `reserveToken` is untouched (only `Pair.swap`, called exclusively by `Router`, can move it).

Net effect per cycle: `realBalance` returns to its pre-buy value, while `reserveToken` is permanently reduced by `X`. Repeating this shrinks (and can eventually invert) the gap `reserveToken - realBalance` until a subsequent buy's `tokensOut > realBalance` branch computes `reserveToken - realBalance` on the underflow side, permanently reverting every future `buy()` call on that token with an unrecoverable Panic. `Pair.tokenBalance()` can never be decreased back down by anyone (only curve buys remove tokens, and buys are exactly what's now bricked), so the DoS is permanent for that token's curve.

This is the direct analog of CVE-2019-2805: an unprivileged, remotely reachable input (a malformed/adversarial state transition — here, a raw token donation interleaved with ordinary buys) that the target's internal state-machine/parser (here, `Router._computeBuy`'s reserve-accounting logic) does not fully validate, producing an unhandled crash that permanently denies service.

### Impact Explanation
Once triggered, `Bonding.buy` (and therefore `Zap.buy`/`Zap.createToken`'s mandatory seed buy for any not-yet-launched interactions, and all subsequent buys) reverts unconditionally for the affected token. Because the token is still `Lifecycle.Curve` and stuck, it can never reach `canGraduate` via further buys, and any curve-raised LT and the creator's/traders' capital already in the `Pair` remain in a curve that can no longer trade on the buy side — a permanent freeze of trading functionality and of the funds locked in that curve (sells may remain available depending on `_computeSell`'s independent math, but the token's price-discovery/graduation path is permanently dead). This satisfies the "permanent freezing of trader/creator funds" impact bar.

### Likelihood Explanation
The precondition — an unprivileged wallet can (a) call `Zap.buy` to acquire `launchedToken`, and (b) call `IERC20.transfer` on that token to send it directly to the `Pair` address — is explicitly listed as an in-scope, permissionless reachable path. No special role, timing, or governance action is required; the attacker only needs enough capital to run buy/donate cycles until the gap is exhausted, which is a bounded, deterministic amount (initially `LP_RESERVE = 250,000,000e18` tokens' worth of curve buys, but the required closing amount shrinks as the curve naturally progresses, so the attack is cheapest late in a curve's life, e.g. shortly before organic graduation).

### Recommendation
In `Router._computeBuy`, replace the unconditional subtraction with a saturating/explicit check that reverts with `OverflowCapDegenerate` (or a new descriptive error) whenever `realBalance >= reserveToken`, not just `==`. Additionally, consider deriving the cap check from a reserve invariant that cannot be desynced by raw donations (e.g., ignore `tokenBalance()` in favor of accounting exclusively through `Pair.swap`-tracked state, or `skim`-style donation handling as already used for the graduation LP-seeding path) so a plain ERC20 transfer into the pair cannot influence curve-buy math at all.

### Proof of Concept
1. Launch a token via `Zap.createToken`; note `pair` address and `reserveToken = TOTAL_SUPPLY`, `realBalance = curveSupply` (gap = `LP_RESERVE`).
2. Loop N times:
   a. Call `Zap.buy(token, usdcAmount, 0, address(0))` to buy `X` tokens on the curve (attacker now holds `X` tokens; `reserveToken -= X`, `realBalance -= X`).
   b. Call `IERC20(token).transfer(pair, X)` directly (bypassing `Zap`/`Bonding`/`Router`) to restore `realBalance += X` while `reserveToken` stays reduced.
3. After enough iterations, gap `reserveToken - realBalance` reaches 0 and then goes negative in effect: the next `Zap.buy` call computes, inside `Router._computeBuy`, `tokensOut = realBalance` (since `tokensOut > realBalance` from the raw k-based formula) and then `cappedReserveToken = reserveToken - tokensOut` underflows, reverting with a Panic(0x11).
4. All subsequent `Zap.buy`/`Bonding.buy` calls for this token now revert unconditionally and permanently — the curve is bricked.

Note: I was not able to execute this end-to-end in a live test harness (no terminal/execution access in this mode); the above is derived purely from the on-chain arithmetic in `Router.sol`/`Pair.sol` and the documented curve invariants in `Bonding.sol`. Confirming the exact attacker capital required to fully close the gap (and verifying no other guard elsewhere intercepts this state) would benefit from a Foundry PoC in a live Devin session.
