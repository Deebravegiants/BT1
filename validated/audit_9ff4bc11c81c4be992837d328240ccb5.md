## Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling shop-spoofing / cross-tenant replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated request headers. `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC exclusively over that signable string (the body), never binding the `shop-domain` header to the signature. `ShopifyAPI::Webhooks::Registry.process` then forwards `request.shop` unchecked to the app's handler as the authoritative merchant identity. This breaks the identity binding `shop_header == shop_covered_by_hmac`, which should hold but does not.

### Finding Description
- `Webhooks::Request#shop` reads the shop straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the payload: [1](#0-0) 

- `to_signable_string` (the bytes actually HMAC-verified) is only the raw body — none of the identifying headers (shop, topic, webhook id, api version) participate in the signature: [2](#0-1) 

- The validator computes/compares the HMAC purely against `to_signable_string`, so it can never detect that the `shop` header has been altered: [3](#0-2) 

- After a successful (body-only) HMAC check, `Registry.process` trusts `request.shop` and hands it straight to the app's webhook handler as the merchant identity for that payload: [4](#0-3) 

Contrast this with the OAuth callback path, where `shop` and `host` *are* included in the signed string, correctly binding those identity fields to the HMAC: [5](#0-4) 

This is the exact class of bug described in the analog report: a field that is acted on (`shop`, used to attribute the webhook payload to a tenant) is not covered by the integrity check (the HMAC), so an attacker can substitute it without invalidating the signature.

### Impact Explanation
Any unprivileged internet user who can install the app on a shop they control (e.g., a free/trial development store) receives genuine webhook deliveries — real `(raw_body, hmac)` pairs signed with the app's shared secret for their own shop's events. Because the `shop-domain` header is outside the signed bytes, the attacker can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` value. `HmacValidator.validate` still succeeds (body unchanged), and `Registry.process` passes the attacker-chosen shop through to the handler as if it were the authenticated tenant for that data. Any host application built on this gem's documented webhook flow (using `WebhookMetadata#shop` to key merchant records/data) will misattribute the payload cross-tenant — writing or acting on another merchant's data using content the attacker controls. This constitutes cross-tenant access, a Critical-severity impact per the given classification.

### Likelihood Explanation
No access to the app's `api_secret_key`, an access token, or privileged credentials is required — only a normal store install (available to any internet user) to obtain one legitimately signed webhook, plus the ability to POST an HTTP request with a modified header to the app's public webhook endpoint. This is a low-effort, directly reachable attack path through the gem's own `Webhooks::Request`/`HmacValidator`/`Registry` code, not a host-application misuse issue, since the gem is the component asserting the shop identity is trustworthy once `Registry.process` returns without error.

### Recommendation
Include the identity-bearing headers (`shop`, and ideally `topic`/`webhook_id`) in the HMAC-covered signable string, mirroring what `Oauth::AuthQuery#to_signable_string` already does for `shop`/`host`. At minimum, `Webhooks::Request#to_signable_string` should incorporate the `shop-domain` header value so that tampering with it invalidates the signature, and/or `Registry.process` should independently verify that the `shop` header matches the shop context under which the request was expected to be received.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g. `orders/create`) to receive a genuine delivery with body `raw_body` and header `x-shopify-hmac-sha256: H` valid against `raw_body`.
2. Capture the request (attacker owns the endpoint used for testing, or proxies delivery).
3. Replay the request to the production app webhook endpoint, keeping `raw_body` and `x-shopify-hmac-sha256: H` unchanged, but setting `x-shopify-shop-domain: victim.myshopify.com`.
4. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb#L26-31`) succeeds because it only checks `raw_body` against `H`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb#L188-200`) invokes the app's handler with `shop: "victim.myshopify.com"` and the attacker's crafted body content, causing the host app to process/store attacker-controlled data under the victim shop's identity.
