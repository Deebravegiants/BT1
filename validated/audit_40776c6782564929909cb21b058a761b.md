### Title
Fee-on-transfer collateral token breaks `collateral` map vs. actual token balance identity in `v0-market-vault.clar` `collateral-add`/`collateral-remove` - (File: `mainnet/contracts/market/v0-market-vault.clar`)

### Summary
`collateral-add` credits the user's collateral ledger with the full nominal `amount` *before* actually pulling tokens in via `receive-tokens`, and never verifies that the contract's real token balance increased by that same `amount`. For any SIP-010 asset that charges a transfer fee, the sum of the `collateral` map entries for that asset will exceed the tokens the contract actually holds, breaking the identity `Σ(collateral[asset]) == balanceOf(vault, asset)`.

### Finding Description
`collateral-add` in `mainnet/contracts/market/v0-market-vault.clar` computes `result` via `add-user-collateral`, which records the caller-supplied `amount` into the `collateral` map unconditionally: [1](#0-0) 

The token transfer itself is performed afterward by `receive-tokens`, which simply forwards the call to the token contract with no post-transfer balance check: [2](#0-1) 

Symmetrically, `collateral-remove` decrements the ledger by the requested `amount` and then calls `send-tokens` to push out exactly `amount` tokens: [3](#0-2) [4](#0-3) 

The `<ft-trait>` parameter accepted by `collateral-add`/`collateral-remove` is generic — this is exactly the mechanism the top-level `market.clar`/`v0-4-market.clar` (`get-asset`, `collateral-add`) uses to support new collateral assets beyond the six ztoken vaults hardcoded today: [5](#0-4) 

If a fee-on-transfer SIP-010 token (analogous to USDT-style fee toggles in the referenced report) is ever onboarded through this generic path, every `collateral-add` will register more collateral in the map than the vault actually received, and every `collateral-remove` will push out `amount` tokens the vault may not fully have, since the balance was never topped up by the fee amount that was skimmed on deposit. This is the same root cause as the referenced Malt finding: the code assumes `transfer(x)` always results in a balance increase of exactly `x`.

Note: the six vault-specific contracts (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`) hardcode their underlying token contract principals and none of those specific tokens (wSTX, sBTC, ststx, usdcx, usdh) are fee-on-transfer, so today's live deployment is not directly exploitable. The exposure is in the generic `<ft-trait>` collateral path in `v0-market-vault.clar`, which is designed to onboard additional collateral assets in the future without further code changes.

### Impact Explanation
If a fee-on-transfer asset were listed as collateral through this generic mechanism, the `collateral` map would systematically over-state the tokens actually custodied by the vault by the cumulative fee amount. Over time, the vault's real balance for that asset falls short of the sum of all users' recorded collateral. When users attempt to withdraw (`collateral-remove`), `send-tokens` will eventually fail (insufficient balance) or drain the vault such that later withdrawers cannot retrieve their recorded collateral — a permanent freezing of funds / partial insolvency for that collateral asset, since the ledger and actual custody diverge and can never be reconciled by users.

### Likelihood Explanation
This requires that a fee-on-transfer asset be listed as a market collateral asset via the generic `<ft-trait>` path — a normal governance/asset-onboarding action, not a compromise or misconfiguration of the DAO. Given the protocol's own stated intent to add more collateral pools over time, and that the vulnerable code path (`receive-tokens`/`add-user-collateral` in `v0-market-vault.clar`) is unconditional and not tied to any specific token, the risk is latent but real for any future asset addition without a corresponding fee-on-transfer safeguard.

### Recommendation
In `receive-tokens` (and the `deposit`/`collateral-add` flow), measure the vault's actual balance before and after the transfer and use the observed delta — not the caller-supplied nominal `amount` — when crediting `add-user-collateral`. Alternatively, explicitly disallow onboarding of fee-on-transfer tokens as collateral assets (e.g., via an on-chain balance-delta assertion during asset registration/testing) so any future asset addition is provably safe.

### Proof of Concept
1. DAO/governance lists a new collateral asset `feeToken`, a SIP-010 token that charges e.g. 1% on `transfer`.
2. User calls `collateral-add` with `amount = 1000`. `v0-market-vault.clar` credits `collateral[user, feeToken] += 1000` via `add-user-collateral`, then `receive-tokens` calls `feeToken.transfer(1000, user, vault)`, but the vault's balance only increases by `990` due to the fee.
3. Repeat across many users/deposits: `Σ(collateral[feeToken])` grows to `N * 1000` while the vault's actual `feeToken` balance is only `N * 990`.
4. When users start calling `collateral-remove` for their full recorded amounts, the vault's real balance is exhausted before all recorded collateral can be paid out — `send-tokens` reverts for the last withdrawers, permanently freezing their collateral. [1](#0-0) [6](#0-5)

(define-public (collateral-add (account principal) (amount uint) (ft <ft-trait>) (asset-id uint))
  (let ((states (var-get pause-states))
        (entry (resolve-or-create account))
        (user-id (get id entry))
        (mask (get mask entry))
        (updated-mask (mask-update mask asset-id true true)) ;; collateral, insert

(define-public (collateral-remove (account principal) (amount uint) (ft <ft-trait>) (asset-id uint) (recipient principal))
  (let ((states (var-get pause-states))
        (entry (resolve account))
        (user-id (get id entry))
        (mask (get mask entry))
        (remaining (try! (remove-user-collateral user-id asset-id amount)))
        (updated-mask (if (is-eq remaining u0)
                        (mask-update mask asset-id true false) ;; collateral, remove
                        mask))
        (updated-entry (merge entry (refresh updated-mask))))

    (try! (check-impl-auth))
    (asserts! (not (get collateral-remove states)) ERR-PAUSED)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)

    (insert updated-entry)
    (try! (send-tokens ft amount recipient))
    
    (print {
      action: "collateral-remove",
      caller: contract-caller,
      data: {
        account: account,
        recipient: recipient,
        asset-id: asset-id,
        amount: amount,
        updated-collateral-amount: remaining,
        mask-before: mask,
        mask-after: updated-mask
      }
    })
    
    (ok remaining)))

  (let ((asset-contract (contract-of asset)))
    (if (is-eq asset-contract ZEST-STX-WRAPPER-CONTRACT)

          (try! (contract-call? asset transfer amount tx-sender account none)))
