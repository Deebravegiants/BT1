### Title
Webhook `shop`/`topic` headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/utils/hmac_validator.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, while the `shop` and `topic` values that the handler subsequently trusts as the tenant/event identity are taken from HTTP headers that are never included in the signed payload. This breaks the intended binding `HMAC-verified bytes == (shop, topic, body)` down to `HMAC-verified bytes == body only`.

### Finding Description
`Utils::HmacValidator.validate` computes the signature exclusively over `verifiable_query.to_signable_string`, and for a webhook `Request`, `to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` values are read straight from headers, which are not part of the HMAC-signed material at all: [2](#0-1) 

`HmacValidator.validate_signature` only compares `computed_signature` (over the body) against the received `hmac`; it never binds the header fields into the check: [3](#0-2) 

`Registry.process` then uses the *unauthenticated* `request.topic` to select a handler and passes the *unauthenticated* `request.shop` directly into `WebhookMetadata`, which is the tenant-identifying field the host application is documented to rely on: [4](#0-3) 

`WebhookMetadata.shop` is explicitly the field apps are told to key their per-shop logic on: [5](#0-4) [6](#0-5) 

Because the signature check only covers the body, any actor who is able to obtain one genuine `(raw_body, hmac)` pair signed with the app's secret — for example a merchant who installs the app on their own shop and captures a webhook Shopify sends them for their own store — can replay that exact body+hmac to the app's webhook endpoint while substituting the `shopify-shop-domain` and/or `shopify-topic` headers for an arbitrary shop/topic. `HmacValidator.validate` still returns `true` because the body bytes (the only thing verified) are unchanged, so `Registry.process` accepts the request and invokes the handler believing the webhook belongs to a different shop and/or topic than it actually does.

### Impact Explanation
This is a cross-tenant identity-binding failure: the equality the code should enforce is `authenticated(body) ∧ authenticated(shop) ∧ authenticated(topic)`, but only `authenticated(body)` holds. An attacker who legitimately has access to their own shop's webhook traffic can forge webhook deliveries that appear to originate from another merchant's shop or represent a different (possibly more sensitive) topic than what was actually signed, corrupting whatever per-shop/per-topic business logic the host application executes in its `WebhookHandler#handle` (e.g., app-uninstall handling, order/customer data sync keyed by `data.shop`, GDPR/customer-redact handlers, billing webhooks). This matches the "Critical – cross-tenant access" category, since the attacker crosses a tenant boundary using only their own legitimate access, without needing the victim's or the app's credentials.

### Likelihood Explanation
Exploitability depends entirely on the attacker being able to obtain at least one valid `(body, hmac)` pair, which any legitimate merchant installing the app can trivially do by triggering webhook events on their own store and capturing the raw POST. Replaying the same body with modified `shop-domain`/`topic` headers to the public webhook callback endpoint requires no secrets. The severity of what can be forged is bounded by which body was captured (topic and shop are freely modifiable, but the JSON payload content is fixed to what was captured), so real-world impact varies by how strictly the host app's handler logic depends on `data.body` matching `data.topic`/`data.shop` versus how much it trusts those fields blindly per the documented usage pattern.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values in the HMAC-signed material (or otherwise cryptographically bind them to the signed body), so that tampering with any of these header fields invalidates the signature. At minimum, document to consumers that `data.shop` and `data.topic` in `WebhookMetadata` are not covered by the HMAC guarantee and must be independently corroborated (e.g., cross-checked against a known session/shop and against the payload contents) before being trusted for tenant-scoped operations.

### Proof of Concept
1. Install the app (as any ordinary merchant) on `attacker-shop.myshopify.com` and trigger a real webhook event (e.g., `orders/create`), capturing the raw request: headers `shopify-topic: orders/create`, `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-hmac-sha256: <H>`, and raw body `B`.
2. Resend the exact same body `B` and hmac `H` to the app's webhook endpoint, but change the headers to `shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different registered `shopify-topic`).
3. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` — unchanged from step 1 — and returns `true` because only `B` is checked [1](#0-0) [3](#0-2) .
4. `Registry.process` accepts the forged request and calls `handler.handle` with `WebhookMetadata.shop == "victim-shop.myshopify.com"` even though the payload actually came from and was signed for `attacker-shop.myshopify.com` [4](#0-3) , corrupting any per-shop logic the host app performs based on that field.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
