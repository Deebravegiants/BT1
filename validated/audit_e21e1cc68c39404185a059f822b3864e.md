### Title
Webhook shop identity spoofable because `Registry.process` trusts the unauthenticated `shop-domain` header while HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's HMAC only over the raw request body, then hands the caller's app a `WebhookMetadata` whose `shop` field is taken from the unauthenticated `shopify-shop-domain` HTTP header. The identity binding "the HMAC-authenticated payload == the shop attributed to that payload" is broken, exactly analogous to the reported bug's pattern of authenticating one piece of state while acting on another.

### Finding Description
`Webhooks::Request#hmac` is computed from the `shopify-hmac-sha256` header and `to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is *not* part of the signed material: [2](#0-1) 

`Registry.process` validates the HMAC (covering only the body bytes) and then immediately trusts `request.shop` (from the header) to build the `WebhookMetadata` that is passed to the host application's handler: [3](#0-2) 

Because a merchant/app-developer who owns their own Shopify store receives genuinely-signed webhooks from Shopify for their own shop (with a valid `hmac-sha256` computed over the real body using the app's `client_secret`), that same person can take one such legitimate webhook delivery and resend it to the app's webhook endpoint after only changing the `shopify-shop-domain` header to a victim shop's domain. Since the HMAC never covered the header, the signature check in `HmacValidator.validate(request)` still succeeds, and the host application's `WebhookHandler#handle` is invoked with `data.shop` set to the victim's domain while `data.body` is the attacker's own webhook payload.

This is the same class of bug as the report: the value that is *verified* (raw body bytes/XAstro `total_voting_power` state) is not the same value that is *acted upon* (the shop identity/`total_votes` state), so the two are silently allowed to diverge, breaking the equality `verified_shop == acted_shop` that the security model assumes.

### Impact Explanation
An app that keys any per-tenant behavior (session lookup, GDPR/customer-data actions, cross-shop authorization decisions, log correlation, feature toggles) off `WebhookMetadata#shop` can be tricked into attributing an attacker-controlled payload to an arbitrary victim shop domain, despite the HMAC passing. This is a cross-tenant identity-binding break driven entirely by this gem's own webhook verification API (`Registry.process`/`Utils::HmacValidator.validate`), not by any misuse of documented behavior — the gem explicitly performs signature validation and then exposes `shop` as trusted, attributable data in `WebhookMetadata`.

### Likelihood Explanation
Exploitation requires only that the attacker control a real (even a free/dev) Shopify store that has the target app installed, so they can generate one authentically-signed webhook of any subscribed topic, capture it, and replay it with a modified `shop-domain` header at the app's public webhook endpoint. No `api_secret_key`, access token, or privileged account belonging to the victim is needed.

### Recommendation
Bind the shop identity into the verified signable content, or otherwise cryptographically/contextually tie the `shop-domain` header to the specific signed body/subscription before trusting it in `WebhookMetadata`. Concretely: extend `to_signable_string` in `lib/shopify_api/webhooks/request.rb` to include the normalized `shop` (and `topic`/`webhook_id`) alongside the raw body, or have `Registry.process` cross-check `request.shop` against an independently-authenticated source (e.g., look up the webhook subscription/session state by `webhook_id` and compare) before constructing `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook (e.g., `orders/create`) which Shopify signs and sends to the app's endpoint with headers `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures the raw HTTP request, then resends it to the same endpoint, changing only `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`; the body and its HMAC are untouched.
4. The app calls `ShopifyAPI::Webhooks::Registry.process(request)`; `Utils::HmacValidator.validate(request)` succeeds because it only checks the raw body bytes.
5. `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: attacker_body, ...))` is invoked, causing the host app to process attacker-controlled data as if it originated from the victim shop.
