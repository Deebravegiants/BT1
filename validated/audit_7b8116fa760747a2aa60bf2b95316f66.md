# Session Fixation via Unauthenticated, Predictable Session-ID Cookie

## Summary
`ShopifyAPI::Utils::SessionUtils.cookie_session_id` treats the raw, client-supplied `shopify_app_session` cookie value as the trusted session-storage lookup key, with no cryptographic binding to the OAuth handshake that produced it. Because the corresponding session IDs generated by `ShopifyAPI::Auth::Session.from` are deterministic strings derived from public data (the shop domain and, for online sessions, the numeric Shopify user id), an attacker can set/guess this cookie value for a victim's session id and cause the host application to retrieve and act under the victim's stored session/access token.

## Finding Description
This mirrors the reported EVM bug class: a value that is *supposed to be authoritatively bound* to a specific execution context is instead substituted with an unrelated, attacker-influenceable value. Here the broken identity binding is:

`session id trusted from the client cookie` **should equal** `a value cryptographically bound to this shop's completed OAuth/token-exchange event`

but instead equals:

`an unsigned, deterministic string that the client can set directly`.

Trace of the root cause:

1. When OAuth completes, `ShopifyAPI::Auth::Session.from` builds the session `id` deterministically: [1](#0-0) 
   - Offline: `id = "offline_#{shop}"` — fully derivable from the public shop domain.
   - Online: `id = "#{shop}_#{associated_user.id}"` — derivable from the public shop domain plus a small, enumerable Shopify user id.

2. `ShopifyAPI::Auth::Oauth.validate_auth_callback` puts this predictable `id` directly into the `SessionCookie` value that gets set in the user's browser: [2](#0-1) 

3. On every subsequent request, `SessionUtils.current_session_id` (for non-embedded apps, and as the embedded fallback) resolves the active session purely from this cookie value, with **no HMAC, signature, or freshness check**: [3](#0-2) [4](#0-3) 

Compare this with the JWT-based path in the same file, `session_id_from_shopify_id_token`, which derives the session id only from a value inside a payload that was cryptographically verified by `JwtPayload` (HMAC'd with `Context.api_secret_key`): [5](#0-4) [6](#0-5) 

The cookie-based path has no equivalent protection: `cookie_session_id` just echoes back whatever bytes the client sent. Unlike the HMAC-covered OAuth callback query (`AuthQuery#to_signable_string`, verified by `Utils::HmacValidator.validate`) which does bind `shop`/`code`/`state`/`timestamp` together, the *cookie issued after* that verification carries no signature of its own — it is a bare, guessable string that downstream code treats as an authenticated session key.

## Impact Explanation
This is a session fixation / cross-tenant session hijack vector against apps built on this library. If a host app implements `SessionRepository.store_session`/lookup keyed by the id returned from `current_session_id` (exactly as documented in `docs/usage/oauth.md`), any party who can influence or predict the victim's `shopify_app_session` cookie value can cause the requesting browser context to be treated as the victim shop's authenticated session, gaining access to that shop's stored access token for the remainder of the request lifecycle. This falls under the explicitly listed High-impact category "session fixation or forced OAuth completion."

## Likelihood Explanation
Exploitation requires only knowledge of the target shop's `.myshopify.com` domain (public) for offline sessions, or additionally a small integer user id for online sessions — no secret, access token, or `client_secret` is needed. The attacker needs some means to set the cookie value on the victim's browser for the app's domain (e.g., cookie injection via a related subdomain, a non-HttpOnly deployment, or a network position short of TLS interception such as an open Wi-Fi/proxy that can set cookies over plain HTTP if the app doesn't enforce `Secure`). Likelihood is moderate: it depends on deployment specifics of the host app, but the root weakness — an unsigned, predictable session identifier — is entirely within this gem's code and design, not a misuse of a documented API.

## Recommendation
- Do not use a predictable, unsigned string as the externally-facing session cookie value.
- Either (a) sign/HMAC the cookie value (bind it to `Context.api_secret_key` the same way `AuthQuery`/`JwtPayload` are verified) and validate that signature in `cookie_session_id` before trusting it, or (b) use a cryptographically random, unguessable session id (as already done for online-session fallback via `SecureRandom.uuid` in `Session#initialize`) instead of the deterministic `"offline_#{shop}"` / `"#{shop}_#{user_id}"` forms, or (c) require and verify a companion signed value (e.g., re-validate against `Context.api_secret_key`) whenever `current_session_id` falls back to the cookie path.
- Add unit tests asserting that tampering with the cookie value to a different (even validly-formatted) session id is rejected unless it can be cryptographically tied to a real OAuth completion for that shop.

## Proof of Concept
1. Attacker installs the app on their own shop `attacker-shop.myshopify.com`, completes OAuth, and receives cookie `shopify_app_session=offline_attacker-shop.myshopify.com`.
2. Attacker learns (public) that a target merchant uses domain `victim-shop.myshopify.com`.
3. Attacker overwrites their own browser's `shopify_app_session` cookie to `offline_victim-shop.myshopify.com` (or triggers this in a victim's browser via subdomain cookie injection where non-HttpOnly/non-scoped cookies are possible) and requests any authenticated route of the host app.
4. The host app calls:
```ruby
session_id = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)
# => "offline_victim-shop.myshopify.com"
session = SessionRepository.load_session(session_id)
```
5. `SessionRepository` (built on the documented storage pattern) returns the victim shop's real `Session`, including its Shopify access token, and the attacker's request is now processed with the victim's credentials.

        end
