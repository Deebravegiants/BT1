### Title
Webhook shop-domain header is not covered by HMAC signature, enabling cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity using an HMAC computed only over the raw HTTP body, while the `shop` identifier used by `Webhooks::Registry` to route the payload to a tenant is read from an unsigned HTTP header. This breaks the binding `shop authenticated == shop used as processing key`, allowing an unprivileged actor who has captured one legitimately-signed webhook (e.g., for their own shop) to replay it against the app's webhook endpoint with a different `shopify-shop-domain` header, causing the app to process/attribute the payload to an arbitrary victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#hmac` decodes the `hmac-sha256` header and is checked via `Utils::HmacValidator.validate`, which compares this HMAC to `OpenSSL::HMAC.hexdigest(sha256, api_secret_key, to_signable_string)`: [2](#0-1) 

However, `Webhooks::Request#shop` (and `topic`, `webhook_id`, `api_version`) are pulled directly from HTTP headers that are **not** part of the signed material: [3](#0-2) [4](#0-3) 

`Webhooks::Registry.process` relies on this unsigned `shop` value to build the `WebhookRequestData` passed to the app's handler (confirmed in the registry test, where `data.shop` is asserted to equal the header value `@shop`, sourced from `shopify-shop-domain`): [5](#0-4) 

The invariant the library implicitly claims is: *"shop covered by the verified HMAC == shop the handler receives and acts upon."* In reality the equality is:
`shop_used_by_handler (from unsigned header) != shop_bound_by_hmac (none, since shop isn't in to_signable_string)`.

Because the `shop-domain` header is completely outside the signed payload, any body+HMAC pair that validates for shop A also validates unchanged for a forged request that swaps the `x-shopify-shop-domain`/`shopify-shop-domain` header to shop B. No knowledge of `api_secret_key` is needed to construct this — the attacker only needs to observe one authentic, correctly-signed webhook delivery for a shop they control (which they legitimately receive from Shopify as the operator of that shop) and can then replay the exact same `raw_body`/`hmac-sha256` pair to the app's webhook endpoint with a different shop-domain header value.

### Impact Explanation
This is a cross-tenant confusion: an app that trusts `Webhooks::Registry`'s validated request to key data by `shop` (e.g., updating merchant-specific records, triggering per-shop side effects, or associating billing/inventory events) can be made to attribute attacker-controlled webhook content to a victim shop it has no relationship-verification for beyond this HMAC. This matches the Critical "cross-tenant access" impact category, since it allows one tenant's data/events to be injected into another tenant's processing context purely by manipulating headers outside the gem's signature boundary.

### Likelihood Explanation
Likelihood is realistic for any actor who is a legitimate (even free-tier) merchant using the target app — they can capture one authentic webhook payload+signature delivered to their own installation, then directly POST a replay of that exact body/HMAC to the app's public webhook endpoint with an altered shop-domain header. No secrets, tokens, or privileged access are required beyond having any single shop installation of the app, which satisfies the "unprivileged internet user" threat model.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-covered signable material, or otherwise cryptographically bind the tenant identity to the verified payload before it is exposed to `Registry.process`/handlers. At minimum, `Webhooks::Request#to_signable_string` should not allow the `shop`, `topic`, and `webhook_id` values consumed downstream to originate from data that falls outside the verified HMAC input.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (or otherwise legitimately receives one webhook).
2. Shopify sends the app a real webhook with headers `x-shopify-hmac-sha256: <valid HMAC over raw_body>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures the exact `raw_body` and `hmac-sha256` value.
4. Attacker sends a new HTTP request directly to the app's webhook endpoint, reusing the identical `raw_body` and `hmac-sha256` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` succeeds because `to_signable_string` only checks `raw_body` [1](#0-0) , and `Registry.process` builds `WebhookRequestData` using `shop: victim-shop.myshopify.com` taken straight from the forged header [3](#0-2) , causing the handler to act as though the payload legitimately originated from the victim shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
