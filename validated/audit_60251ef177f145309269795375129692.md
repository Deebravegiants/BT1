### Title
Unauthorized arbitrary external calls from `Emporium` drain any tokens held by the Emporium contract - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`, `circuits/MainEVMCircuitMin.circom`)

### Summary
`Hinkal.transact()` for the Emporium external action can be driven by a trivial ZK proof (`MainEVMCircuitMin`) that carries **no ownership/authorization constraint whatsoever**, only knowledge of an arbitrary `messageSeed`. When `circomData.erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` routes to `formInputEmporiumMin`, which supplies only `emporiumMessage`, `timeStamp`, and `calldataHash` as public inputs. Since `calldataHash` commits to `circomData.externalActionData` (including the `EmporiumStack`/`EmporiumOperation[]` that will be executed), an attacker can produce a valid proof for **any** attacker-chosen `EmporiumOperation[]` without owning any shielded UTXO, without a valid EdDSA spending signature, and (if `signerAddress == address(0)`) without any EIP-712 wallet signature either (`verifyWallet` skips signature checking entirely when `signerAddress == address(0)`).

### Finding Description
The call path is:
1. `Hinkal.transact()` calls `hinkalHelper.performHinkalChecks(...)`, which only checks `getHashedCalldata(circomData) == circomData.calldataHash` and dimension/relay sanity - it never checks that the caller owns any funds tied to the operation when the emporium-min path is used [1](#0-0) .
2. `formInputForCircom` detects `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0` and switches to the minimal input builder, exposing only 3 public signals [2](#0-1) .
3. `MainEVMCircuitMin` only computes `message = Poseidon(messageSeed)`; it does not constrain `calldataHash`, spending keys, nullifiers, or any relationship between the caller and the operation content [3](#0-2) .
4. `Hinkal._externalTransact` then dispatches to `EmporiumUpgradeable.runAction`, which decodes `EmporiumStack` (including attacker-chosen `endpoint`/`callData`/`value` and `signerAddress`) from `externalActionData.externalActionMetadata` [4](#0-3) .
5. `verifyWallet` returns immediately without checking any signature when `stack.signerAddress == address(0)` [5](#0-4) .
6. For "Case 2: Stateless Interaction," the Emporium contract itself executes `op.endpoint.call{value: op.value}(op.callData)` with no restriction on `endpoint`/`callData` besides blocking the `callHinkalWallet`/`doSendToRelay` selectors [6](#0-5) .
7. The post-call solvency check (`balanceChange < 0` revert) only iterates over `circomData.erc20TokenAddresses` supplied by the attacker [7](#0-6) . Because the attacker fully controls that array (and it is empty in the emporium-min path), any token/ETH balance the Emporium contract holds that is **not** listed there is completely unchecked.

Combining these: an unprivileged EOA can submit a valid `transact()` call with `erc20TokenAddresses = []`, a forged/trivial proof for `MainEVMCircuitMin`, and an `EmporiumStack` whose `ops` are e.g. `token.transfer(attacker, balanceOf(emporium))` or `token.approve(attacker, type(uint256).max)` for any token the Emporium contract holds (fee dust, refunds, previously-approved allowances, tokens sent by mistake, etc.), executed with `msg.sender == Emporium`. This exactly mirrors the `submitLogicCall` bug class in the referenced report: an arbitrary logic call is authorized on behalf of the holder contract without a corresponding equality/ownership check tying the call to real value the caller controls.

### Impact Explanation
This breaks the equality between "value the prover is authorized to move" and "value actually moved": the ops execute with the Emporium contract as `msg.sender` (not the attacker's own funds), stealing any residual protocol/relay-fee balances or leftover tokens/ETH held by the Emporium contract. This is at minimum theft of protocol/relay fee balances and can extend to temporary/permanent freezing or theft of any funds accidentally or transiently held on the Emporium contract - matching the High-severity "executing calls or moving assets a wallet owner or prover never authorised" criterion.

### Likelihood Explanation
High. No privileged role, relayer, or wallet key is required. The only requirement is submitting a proof for the minimal circuit (`MainEVMCircuitMin`), which imposes no real cryptographic constraint tying the caller to any UTXO or signature, plus crafting `calldataHash` to match an attacker-chosen `EmporiumOperation[]`. Any funds transiently sitting on the Emporium contract (fees, rounding dust, refunds from failed prior ops, mistaken sends) are immediately at risk.

### Recommendation
- Require `signerAddress != address(0)` (i.e., a verified EIP-712 signature) for every op, or otherwise cryptographically bind the emporium-min path to a real authorization over the specific `ops` content and any funds it can touch.
- In `runAction`, restrict "Case 2: Stateless Interaction" `endpoint` calls to a safe allow-list of routers/contracts (mirroring `ExternalActionSwap`'s pattern) and disallow calls to arbitrary ERC-20/NFT contracts unless the Emporium contract's balance change for that exact token is reconciled - not only for tokens the attacker chooses to list in `erc20TokenAddresses`.
- Ensure the Emporium contract never accumulates standing token/ETH balances between transactions (sweep to zero after each `runAction`), so there is nothing of value to steal via unchecked tokens.
- Consider removing/hardening the "emporium min" trivial-circuit path so it cannot authorize execution of an arbitrary `EmporiumOperation[]` without proof of real ownership.

### Proof of Concept
1. Attacker (no shielded balance) builds `circomData` with `erc20TokenAddresses = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalActionMetadata = abi.encode(EmporiumStack{signerAddress: address(0), ops: [EmporiumOperation{endpoint: victimToken, invokeWallet: false, callData: abi.encodeWithSelector(IERC20.transfer.selector, attacker, victimToken.balanceOf(emporium))}], ...})`.
2. Attacker computes `calldataHash = getHashedCalldata(circomData)` and generates a valid `MainEVMCircuitMin` proof for arbitrary `messageSeed` (no ownership needed, per `circuits/MainEVMCircuitMin.circom`).
3. Attacker calls `Hinkal.transact(a, b, c, dimensions, circomData)`.
4. `performHinkalChecks` passes (calldata-hash matches, dimensions consistent with empty token array); `verifyProof` passes against `MainEVMCircuitMin`.
5. `_externalTransact` → `EmporiumUpgradeable.runAction` decodes the stack, `verifyWallet` returns immediately (signerAddress is zero), and executes `op.endpoint.call(...)` as the Emporium contract, transferring `victimToken` balance to the attacker.
6. The post-call solvency loop iterates over the empty `erc20TokenAddresses` array, so no revert occurs regardless of the stolen balance.

        uint256[] memory balancesBefore = getBalancesForArray(
            circomData.erc20TokenAddresses
        );

        verifyWallet(stack, circomData);

        for (uint256 i = 0; i < stack.ops.length; i++) {
            EmporiumOperation memory op = stack.ops[i];

            bool success;
            bytes memory err;

            // CASE 1: Stateful Interaction
            if (op.invokeWallet && stack.signerAddress != address(0)) {
                (success, err) = IHinkalWallet(stack.signerAddress)
                    .callHinkalWallet(op.endpoint, op.callData, op.value);

                    selector == IHinkalWallet.doSendToRelay.selector
                ) {
                    revert UnauthorizedWalletCall();
                }

                (success, err) = op.endpoint.call{value: op.value}(op.callData);
