## Title
Escrowed order funds become permanently frozen when the beneficiary/solver address is blacklisted by a stablecoin like USDC/USDT - (File: `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol`, `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Intent Gateway's cross-chain escrow-release path (`_withdraw` / `withdraw`) transfers escrowed `stakingToken`-like assets directly to a hard-coded `beneficiary` address using `safeTransfer`/`transfer`, with no ability to redirect the recipient if that address is later blacklisted by a compliant stablecoin issuer (USDC/USDT). This mirrors the `LM_PC_Staking_v1.unstake()` finding: a token-level recipient check can make fund-release permanently unexecutable.

### Finding Description
When a cross-chain order is filled or cancelled, the destination/source chain dispatches a `RedeemEscrow` or `RefundEscrow` message that is delivered via the ISMP host to `onAccept`, which authenticates the message and calls `_withdraw`: [1](#0-0) 

`_withdraw` unconditionally transfers each escrowed token to the `beneficiary` address decoded from the `WithdrawalRequest` body: [2](#0-1) 

The `beneficiary` for `RedeemEscrow` is set at fill time to the filling solver's address, and for `RefundEscrow` it is the original order `user` — both fixed, non-substitutable addresses baked into the dispatched cross-chain message: [3](#0-2) 

If any escrowed input token is a blacklist-capable stablecoin (USDC/USDT) and the `beneficiary` address (solver or user) is or becomes blacklisted by the token issuer before delivery, `IERC20(token).safeTransfer(beneficiary, amount)` reverts. Because this transfer is part of the same top-level call as `onAccept` (the ISMP message handler), the revert unwinds the entire request-processing transaction — the request is never marked delivered/consumed, `_filled` and `_orders` state are not updated, and there is no code path to substitute a different beneficiary or otherwise flush the escrow. The identical pattern exists in the Tron variant of the gateway: [4](#0-3) 

Because the beneficiary is immutably fixed inside the signed/committed order (and re-derived identically on every retry), any relayer resubmission of the same proof will hit the exact same blacklist check and revert again, forever.

### Impact Explanation
The user's (or solver's) escrowed input tokens become permanently locked in the `IntentsBase`/`IntentGatewayV2` contract with no recovery mechanism: `RedeemEscrow` cannot complete because the solver is blacklisted, and `RefundEscrow`/cancellation cannot complete because the original user is blacklisted. There is no admin sweep, no alternate-recipient parameter, and no way to re-route the transfer, so funds are frozen indefinitely — a direct match to the "permanent freezing of funds" impact class.

### Likelihood Explanation
Reachable by any ordinary order flow: a user escrows USDC/USDT via `placeOrder`, and later either the filling solver's address or the original user's address is blacklisted by the token issuer (a routine compliance action on Optimism/Polygon/mainnet USDC deployments) before the cross-chain settlement message is delivered. No privileged action by Hyperbridge, solvers, or governance is required to trigger the freeze — it is purely a consequence of a third-party issuer blacklisting one of the two counterparties whose address is embedded in the order.

### Recommendation
Do not hard-fail the entire settlement transaction when a single token transfer to a beneficiary reverts. Options include:
- Wrap each token transfer in `_withdraw`/`withdraw` in a try/catch (or low-level call) and, on failure, escrow the amount into a per-beneficiary "pull" balance that can be claimed later or redirected to an alternate address supplied by the affected party (analogous to a `claim(address recipient)` pattern), rather than reverting the whole withdrawal.
- Allow the beneficiary to specify/update a redemption address before finalization, or support a fallback recipient mechanism, so a single blacklisted address cannot block release of escrowed funds tied to that commitment.

### Proof of Concept
1. Alice places a cross-chain order escrowing 1,000 USDC via `placeOrder` on the source chain.
2. Solver Bob fills the order on the destination chain; `_body(RequestKind.RedeemEscrow, commitment, order.inputs, bytes32(uint256(uint160(bob))))` is dispatched back to the source chain (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:207-212`).
3. Before the message is relayed and delivered, USDC's issuer blacklists Bob's address.
4. A relayer delivers the `RedeemEscrow` proof; `onAccept` calls `_withdraw`, which calls `IERC20(USDC).safeTransfer(bob, 1000e6)` — this reverts because `bob` is blacklisted (`notBlacklisted(to)` in USDC's `transfer`).
5. The entire `onAccept` transaction reverts; the request is never marked processed. Every subsequent relay attempt with the same proof hits the same revert. Alice's escrowed USDC (and Bob's earned input) remain locked in the gateway with no way to redirect or recover them.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {

                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;

            }
        }
