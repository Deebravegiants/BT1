### Title
Unauthorized `transferFrom` pull of arbitrary user funds via unchecked `originalSender` in `DepositOnChainUtxosExternalAction` - (File: `contracts/external-actions/DepositOnChainUtxosExternalAction.sol`)

### Summary
`DepositOnChainUtxosExternalAction.runAction` pulls ERC20 tokens with `transferERC20TokenFrom(tokenAddress, userAddress, msg.sender, tokenTotal)` where `userAddress = circomData.originalSender` [1](#0-0) [2](#0-1) . Nowhere in this function, or in the caller path through `Hinkal._externalTransact`, is `circomData.originalSender` checked against the actual transaction sender/prover identity. This is the same bug class as the reported `RWAHubNonStableInstantMints` issue: the contract trusts a caller-supplied "owner" field instead of verifying that the entity invoking the action is that owner, allowing any unprivileged caller to move a third party's funds.

### Finding Description
`Hinkal._externalTransact` routes to `IExternalActionV2(externalAddress).runAction(circomData, deltaAmountChanges)` for any caller whose `externalActionId` maps to a registered external action [3](#0-2) . Any address can submit a `transact()`/proof call as long as `deltaAmountChanges[i] == 0` for this action (required by the contract itself) [4](#0-3) , meaning the caller does not even need to move any of their own on-chain balance through the top-level balance equation in `Hinkal.sol` — the actual value transfer happens entirely inside this external action via a direct `transferFrom` call.

Inside `runAction`, the token source for the pull is `circomData.originalSender`, not `msg.sender` of the outer `transact()` call and not any address whose signature or key material is verified in this path: [1](#0-0) [2](#0-1) 

`circomData.originalSender` is only referenced elsewhere as part of the `calldataHash` that binds the ZK proof to the specific calldata blob [5](#0-4)  and in `CircomData.sol`'s struct definition [6](#0-5) . Binding this field into `calldataHash` only proves that *some* valid proof (belonging to the prover's own shielded nullifier set) was generated for this exact value of `originalSender` — it does not prove that `originalSender` authorized, signed, or is the entity constructing the proof. The prover only needs valid nullifiers/UTXOs of their own (which can be zero-value or unrelated to this deposit, since `deltaAmounts[i] == 0` is enforced) to produce a syntactically valid proof containing an attacker-chosen `originalSender`.

Contrast this with the correct pattern enforced in `Hinkal._internalTransact`, where a deposit explicitly requires `circomData.externalActionData.externalAddress == msg.sender`, "Deposit should come from the sender" [7](#0-6) . `DepositOnChainUtxosExternalAction` has no equivalent check tying `originalSender` to `msg.sender`/the real depositor, breaking the intended equality "funds pulled from address X ⇒ X authorized this pull."

Any address that has an outstanding ERC20 `approve()` to this external action contract (e.g., from a prior legitimate deposit flow, or from token approval UIs that pre-approve Hinkal contracts) can have its tokens pulled by an unrelated attacker who simply sets `circomData.originalSender` to the victim's address and directs the resulting on-chain UTXOs to the attacker's own `stealthAddressStructure` [8](#0-7) .

### Impact Explanation
This is theft of user funds via an unauthorized `transferFrom` — asset movement never authorized by the token owner/prover, satisfying the "transferFrom / wallet op not authorised by the prover or signer" analog class. Any victim address holding an outstanding ERC20 allowance to this contract can have those funds stolen and redirected to an attacker-controlled shielded UTXO, which the attacker can later withdraw. This meets the Critical bar (direct theft of user funds / minting shielded value the attacker does not own).

### Likelihood Explanation
Exploitability depends on a victim having a nonzero ERC20 allowance outstanding to `DepositOnChainUtxosExternalAction`. Such allowances are a normal artifact of legitimate deposit flows (approve-then-deposit UX patterns), making this a realistic, not merely theoretical, precondition. No admin/relay/owner privilege is required by the attacker — only submission of a valid ZK proof for the attacker's own (possibly empty/zero-value) shielded UTXO set with a forged `originalSender` field, and a registered `externalActionId` pointing at this contract, which is the intended, unprivileged way to invoke external actions through `Hinkal._externalTransact`.

### Recommendation
Enforce that `circomData.originalSender == msg.sender` (i.e., the actual `Hinkal.sol` transaction sender) before using it as the token source in `transferERC20TokenFrom`, mirroring the check already present in `Hinkal._internalTransact` ("Deposit should come from the sender"). Alternatively, require an explicit signature from `originalSender` authorizing this specific deposit (message including tokens/amounts/UTXO destination), verified inside `runAction`, similar to the EIP-712 signer verification pattern used in `EmporiumUpgradeable.verifyWallet` [9](#0-8) .

### Proof of Concept
1. Victim `V` previously approved `DepositOnChainUtxosExternalAction` to spend `N` tokens of `ERC20` (e.g., as part of a normal deposit flow, or a pre-approval convenience pattern).
2. Attacker `A` (no KYC/privilege needed) constructs a valid ZK proof for their own shielded UTXO set (can be trivial/zero-value) and calls `Hinkal.transact()` with `circomData.externalActionData.externalActionId` set to this action's ID, `circomData.externalActionData.externalActionMetadata` encoding `utxoAmounts = [[N]]`, `deltaAmounts[0] == 0`, and crucially `circomData.originalSender = V`.
3. `Hinkal._externalTransact` calls `runAction`, which decodes `userAddress = V` and calls `transferERC20TokenFrom(ERC20, V, address(Hinkal), N)` [2](#0-1) , pulling `V`'s approved tokens using `V`'s existing allowance — no check verifies `A` is `V` or is authorized by `V`.
4. The resulting on-chain UTXO uses `circomData.stealthAddressStructure`, which `A` fully controls, so `A` can later withdraw the stolen `N` tokens as their own shielded balance.
