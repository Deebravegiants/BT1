Audit Report

## Title
Global, unscoped `requestID` uniqueness check in HTTP trigger handler allows cross-workflow griefing/DoS - (core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

## Summary
The gateway's `httpTriggerHandler` tracks in-flight requests in a `callbacks` map keyed solely by the client-supplied `requestID` string, with no scoping to the targeted `workflowID` or its owner. Because authorization only checks that the caller holds a valid signing key for their own targeted workflow (not that they "own" the `requestID` namespace), any unprivileged, unrelated workflow owner can pre-empt a victim's `requestID` by submitting their own validly-authorized request with the same ID, causing the victim's legitimate request to fail with a conflict error.

## Finding Description
`HandleUserTriggerRequest` validates `requestID` only for emptiness/format via `validateRequestID`, and authorizes the caller only against the workflow they target via `authorizeRequest`; neither step binds the `requestID` to the calling workflow or owner. The `callbacks map[string]savedCallback` is a single global map keyed by `requestID` alone, and `setupCallback` rejects any second request whose `requestID` already exists in the map — irrespective of which workflow or owner it belongs to. Since any external account can register its own workflow on-chain and sign valid requests for it, an attacker can observe/predict a victim's chosen `requestID` and submit a colliding, validly-authorized request against their own unrelated workflow, causing whichever request lands second to be rejected with `jsonrpc.ErrConflict`. The existing test suite ("duplicate request ID", "duplicate JWT token and request ID") only exercises same-workflow/same-signer collisions and does not cover this cross-workflow/cross-owner case. By contrast, the vault gateway's analogous handler namespaces its active-request map by `authorizedOwner + separator + requestID`, avoiding this exact issue.

## Impact Explanation
This is a griefing/availability issue: an unprivileged, unrelated CRE tenant can deny a targeted user's specific workflow-execution request by colliding on `requestID`, without needing operator/admin access or any credential beyond registering their own workflow (a normal permissionless action). It does not enable fund theft, secret exfiltration, or authentication bypass, but it is a concrete DoS against a specific request that maps to a legitimate in-scope impact category (gateway request availability/griefing).

## Likelihood Explanation
Exploitability is bounded by the attacker's ability to observe or predict the victim's `requestID` before the victim's request is processed, since it is entirely caller-chosen and unscoped. Low-entropy or reused IDs (a common client pattern, as reflected in the codebase's own test fixtures using values like `"1"` or fixed constants) make this practical; for high-entropy random IDs the race becomes harder, but the underlying missing-scoping design flaw remains regardless.

## Recommendation
Scope the `callbacks` map key (and the in-flight uniqueness check in `setupCallback`) by `(workflowID, requestID)` or `(workflowOwner, requestID)` instead of `requestID` alone, mirroring the owner-prefixing pattern already used in `core/capabilities/vault/gateway_vault_request_processor.go`'s `activeRequests` map.

## Proof of Concept
1. Register two independent workflows on-chain (attacker's own, and note victim's `workflowID`), each with its own valid signing key.
2. Victim submits `workflows.execute` with `id: "abc123"` targeting their own `workflowID`.
3. Attacker submits a validly-authorized `workflows.execute` request for their own unrelated `workflowID` using the same `id: "abc123"`, timed to reach `setupCallback` first.
4. `setupCallback` finds `"abc123"` already present in the global `callbacks` map and returns `jsonrpc.ErrConflict` for whichever request arrives second — extend the existing `TestHttpTriggerHandler` "duplicate request ID" test (`http_trigger_handler_test.go`) to use two different `workflowID`s/signers with the same `requestID` to demonstrate the cross-tenant collision.

func (h *httpTriggerHandler) HandleUserTriggerRequest(ctx context.Context, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback, requestStartTime time.Time) error {
	triggerReq, err := h.validatedTriggerRequest(ctx, req, callback)
	if err != nil {
		return err
	}

	workflowID, err := h.resolveWorkflowID(ctx, triggerReq, req.ID, callback)
	if err != nil {
		return err
	}

	key, err := h.authorizeRequest(ctx, workflowID, req, callback)
	if err != nil {
		return err
	}

	if err = h.checkRateLimit(ctx, workflowID, req.ID, callback); err != nil {
		return err
	}

	legacyExecutionID, err := workflows.EncodeExecutionID(strippedWorkflowID, req.ID) //nolint:staticcheck // legacy ID kept for observability comparison

		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID: " + err.Error())
	}
	// Workflows shouldn't use more than one HTTP trigger. If we ever need to support multiple triggers, we'd need to pass

	// Execution IDs here are used only for logging.

		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID with trigger index: " + err.Error())

		"legacyExecutionID", legacyExecutionID,
		"executionIDWithTriggerIndex", executionIDWithTriggerIndex,

		"workflowID", workflowID)

	if err != nil {
		return err
	}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
