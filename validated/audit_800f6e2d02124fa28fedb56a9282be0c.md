### Title
Webhook shop/topic identity spoofing via signature that only covers the raw body, not the headers - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats the `shop-domain`, `topic`, `webhook-id`, and `api-version` HTTP headers of an inbound webhook as authenticated, tenant-identifying data and hands them straight to the host app's webhook handler. However, `Webhooks::Request#to_signable_string` — the value that `Utils::HmacValidator` actually verifies — is defined as only the raw request body. None of the identity headers are part of the HMAC-covered bytes, so a request with a *valid* signature can carry *any* shop/topic/webhook-id combination an attacker chooses.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`hmac` is read from the `x-shopify-hmac-sha256` header, and `to_signable_string` returns only `@raw_body`. `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from attacker-controllable HTTP headers with no cryptographic tie to the signature.

`HmacValidator.validate` only checks that the HMAC matches `to_signable_string`: [2](#0-1) 

i.e. it proves "these bytes (the body) were signed by Shopify," not "this body was sent for shop X and topic Y." `Registry.process` then uses the *unauthenticated* header values as the trusted identity for dispatch: [3](#0-2) 

The broken identity binding, expressed as an equality that should hold but doesn't:
`hmac_signed_bytes(raw_body) == identity_used_by_handler(shop, topic, webhook_id)` — the gem only proves the left side, then feeds the caller-supplied (never-verified) `shop`/`topic` into `WebhookMetadata`, which host apps use to route/attribute data to a specific merchant.

Because the signature is computed purely over the body, and merchants (including an attacker's own shop) can legitimately trigger webhooks with arbitrary JSON bodies and receive valid `hmac-sha256` signatures for them, an attacker can:
1. Obtain one legitimate `(raw_body, valid_hmac)` pair for a topic they control on their own store (or any topic body they can predict/construct, since the body is just JSON they can often shape via their own store data).
2. Replay that exact body+signature to the app's webhook endpoint while substituting `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) to point at a victim shop.
3. `HmacValidator.validate` still succeeds (body/signature match), and `Registry.process` invokes the app's handler with `WebhookMetadata.shop == <victim shop>`, causing the host application to process attacker-controlled data as if it originated from the victim's store — a cross-tenant data-integrity/identity break.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to guarantee for webhook consumers: a merchant-scoped signature is presented as authenticating an arbitrary shop identity. Any host application that uses `WebhookMetadata#shop` (or `#topic`) to select which tenant's records to update (as the documented usage pattern encourages) can be tricked into writing/mutating data under the wrong shop, or into treating one topic's payload as another topic — a cross-tenant access impact.

### Likelihood Explanation
Exploitability requires only the ability to send a legitimate webhook to the app once (e.g., by installing/uninstalling the app on the attacker's own development store, which is unprivileged and free) and the ability to POST directly to the app's public webhook endpoint with attacker-chosen headers (webhook endpoints are plain, unauthenticated HTTP endpoints by design). No `api_secret_key`, access token, or other privileged credential is required — only header manipulation on replay.

### Recommendation
Bind the identity headers into the signable material (or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the verified signature) before `Registry.process` trusts them, e.g., by including the normalized headers in `to_signable_string`, or by requiring the caller to independently verify `shop` against the session/store the webhook was registered for rather than trusting the header value that arrived with the request.

### Proof of Concept
```ruby
# 1. Attacker registers/owns a shop and receives one legitimate webhook call
#    for topic "app/uninstalled" with body '{"id":1}' and a valid
#    x-shopify-hmac-sha256 signature computed by Shopify using the app's secret.

raw_body = '{"id":1}'
valid_hmac = "<hmac captured from the legitimate delivery>"

# 2. Attacker replays the exact same body+signature to the same endpoint,
#    but swaps the shop-domain (and/or topic) header to target a victim shop:
headers = {
  "x-shopify-topic"        => "orders/create",              # forged topic
  "x-shopify-hmac-sha256"  => valid_hmac,                    # unchanged, still valid for raw_body
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com",   # forged shop
  "x-shopify-webhook-id"   => "forged-id",
  "x-shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate succeeds (only checks raw_body against valid_hmac),
#    handler.handle is invoked with shop: "victim-shop.myshopify.com",
#    even though Shopify never sent this event for that shop/topic.
```
