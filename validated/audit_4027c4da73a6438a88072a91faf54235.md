### Title

Accrual overflow permanently freezes a saturated lending market - ([File: `common/src/rates/simulate.rs`])

### Summary

`accrue_step()` converts total scaled debt and supply back to RAY asset value before applying the borrow-index cap; once `borrowed * borrow_index / RAY` or `supplied * supply_index / RAY` exceeds `i128::MAX`, the multiplication panics instead of saturating. Because every pool mutation synchronizes interest first and `update_indexes` commits nothing when the accrual panics, the market can enter a state where no future operation can complete. [1](#0-0) [2](#0-1) 

### Finding Description

The pool stores market totals as scaled RAY shares and restores their asset value through `scaled_to_original()`, which calls `Ray::mul()` and panics with `MathOverflow` when the result does not fit `i128`. [3](#0-2) [4](#0-3) 

`accrue_step()` performs this conversion for the entire `borrowed` and `supplied` books before calculating utilization, updating indexes, or applying the borrow-index ceiling. [1](#0-0)  The cap is therefore applied only after the potentially overflowing total-value computation, so it does not prevent a large market from crossing the representable RAY-value boundary. [5](#0-4) 

`ops::synced_market()` loads a market and calls `interest::global_sync()` before every operation leg, while `market::accrue()` calls the same accrual routine for `update_indexes`. [6](#0-5) [7](#0-6)  A caller can reach the vulnerable state through normal `supply`, `borrow`, and permissionless market-index updates; `repay`, `withdraw`, `liquidate`, and `clean_bad_debt` subsequently hit the same first-stage synchronization. [8](#0-7) 

### Impact Explanation

Once accrued index growth pushes either market total above `i128::MAX` in RAY units, the accrual transaction rolls back before `last_timestamp` is advanced. All later calls that load that market repeat the same overflowing conversion and revert, including repayment, withdrawal, liquidation, bad-debt cleanup, and future `update_indexes` calls. [9](#0-8) [10](#0-9) 

This permanently freezes supplier collateral and pool cash and prevents borrowers or liquidators from reducing the debt that caused the overflow. [11](#0-10)  Protocol revenue and recoverable collateral in the affected market are likewise stranded because the market cannot complete its mandatory synchronization step. [2](#0-1) 

### Likelihood Explanation

Triggering the state does not require a privileged call, leaked key, malformed parameter, or malformed token; an unprivileged actor supplies a large position, another sufficiently collateralized account borrows most of it, and anyone advances market accrual with `update_indexes`. [12](#0-11) [13](#0-12) 

The precondition is a very large market whose RAY-denominated book value approaches `i128::MAX`, followed by enough index growth for the multiplication to overflow. Repository documentation explicitly notes that market value can overflow before the index ceiling and block repayment or withdrawal, and the regression test demonstrates this with a 1-billion-token, 18-decimal market at 98% utilization. [14](#0-13) [15](#0-14) 

Likelihood therefore depends on asset issuance, market caps, collateral value, and rate parameters permitting such a book, but the admitted cap and index bounds do not themselves prevent the state. [16](#0-15) 

### Recommendation

Apply the representable-value bound before multiplying the market total, instead of relying only on the index ceiling. [1](#0-0) 

A safe design is to derive a market-specific maximum index of `i128::MAX / scaled_total` for both `borrowed` and `supplied`, clamp index growth to that bound, and treat the resulting state as “interest saturated” rather than reverting. Operations should still be able to repay, withdraw available cash, liquidate, and socialize bad debt at the saturated index. Alternatively, make total-value accrual use widened arithmetic and explicitly define how values exceeding `i128` are reduced or capped before entering existing i128 accounting paths.

The boundary should be tested at `borrowed * borrow_index / RAY == i128::MAX`, one unit above it, and with supplied/revenue shares at their respective limits; repayment, withdrawal, liquidation, `clean_bad_debt`, and `update_indexes` should remain executable at saturation. [17](#0-16) 

### Proof of Concept

1. Create an 18-decimal market with a high-utilization rate curve and sufficient caps.
2. Supplier calls `supply(caller, account_id, spoke_id, assets)` to deposit `1_000_000_000 * 10^18` base units.
3. A collateralized borrower calls `borrow(caller, account_id, borrows, to)` for `980_000_000 * 10^18` base units.
4. Let time advance until index growth makes `borrowed * borrow_index / RAY > i128::MAX`.
5. Call `update_indexes` for that `HubAssetKey`.
6. The call panics in `accrue_step -> scaled_to_original -> Ray::mul`; `last_timestamp` is not advanced.
7. Repeat `repay(caller, account_id, payments)` or `withdraw(caller, account_id, withdrawals, to)`; each call synchronizes the market first and panics at the same multiplication.

The repository’s regression test performs the same sequence and asserts `MATH_OVERFLOW` from `update_indexes`, `withdraw`, and `repay`: [17](#0-16) 

```rust
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);

let debt = principal / 100 * 98;
t.borrow_raw(ALICE, "BIG18", debt);

loop {
    t.advance_time(YEAR_SECS);
    t.try_update_indexes_for(&["BIG18"])?; // eventually MathOverflow
}

// Both remain permanently unusable:
t.try_withdraw_raw(BOB, "BIG18", 1);  // MathOverflow
t.try_repay(ALICE, "BIG18", 1.0);    // MathOverflow
```

/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);

        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);

bounded indexes do not guarantee that future accrual fits. Value overflow can
