### Title
Relay fee funds become permanently stranded in `ExternalActionSwap` when `circomData.relay == address(0)` while `feeStructure.flatFee`/`variableRate` are nonzero - (File: contracts/external-actions/swaps/ExternalActionSwap.sol)

### Summary
`ExternalActionSwap.swap` computes `relayFee`/`hinkalFee` from attacker-controlled `circomData.feeStructure` fields regardless of `circomData.relay`, and unconditionally subtracts `totalFee` from `amountToSendToHinkal` before forwarding only the remainder to `msg.sender` (Hinkal). Because `Transferer.sendToRelay` silently no-ops when `relay == address(0)`, the `totalFee` portion of `outputToken` is never transferred anywhere and remains stuck in the `ExternalActionSwap` contract's own balance, while Hinkal's own accounting only tracks the (correct) amount it actually received, so nothing on the `Hinkal.sol` side detects the discrepancy.

### Finding Description
The broken equality is exactly as stated: tokens leaving `ExternalActionSwap` in the transaction (`amountToSendToHinkal` only) should equal `-deltaAmounts[0]`'s corresponding swap proceeds minus `totalFee` that was supposed to go to the relay. Instead: [1](#0-0) 

- `relayFee = circomData.feeStructure.flatFee` and `hinkalFee = hinkalHelper.calculateRelayFee(...)` are computed purely from attacker-supplied `circomData.feeStructure`, with no check that `circomData.relay != address(0)`.
- `sendToRelay(circomData.relay, ..., outputToken)` is called, but in `Transferer.sol`: [2](#0-1) 

when `relay == address(0)` the function body is skipped entirely — no revert, no fallback.
- `totalFee` is still subtracted from `swappedAmount` to compute `amountToSendToHinkal`, and only that reduced amount is sent back to `msg.sender` (Hinkal) and recorded in the returned `UTXO`.

The attacker's exact call: submit `Hinkal.transact` with `externalActionData.externalActionId` pointing at the swap action, `circomData.relay = address(0)`, and `circomData.feeStructure.flatFee > 0`/`variableRate > 0`. All of these are ordinary user-supplied `CircomData` fields, not privileged.

Existing guards do not catch this:
- `performHinkalChecks` / `dimensionsCheck` operate on structural dimensions of the proof, not on the semantic relationship between `relay` and `feeStructure`.
- The circuit constraint `inTotal + amountChanges === outTotal` and the on-chain balance equality in `Hinkal.sol` only check **Hinkal's own** balance delta against `amountChanges[i] + utxoAmount`: [3](#0-2) 

Since Hinkal only received `amountToSendToHinkal` and the UTXO created also equals `amountToSendToHinkal`, this equation trivially balances — it has no visibility into what stayed behind inside `ExternalActionSwap`.
- Notably, `Hinkal._internalTransact` *does* have an explicit guard for this exact class of bug — `require(circomData.relay == address(0) || hasPaidToRelay, "relay not paid")` [4](#0-3)  — but this guard exists only in the internal-transact path, not in the external-action path (`_externalTransact` / `ExternalActionSwap.swap`), so there is no analogous protection there.

### Impact Explanation
Every call to `ExternalActionSwap.swap` with `relay == address(0)` and nonzero fee parameters permanently locks `totalFee` worth of `outputToken` inside the `ExternalActionSwap` contract, unreachable by the intended relay and untracked by any UTXO/nullifier accounting. This is at minimum a **High** severity finding under "permanent freezing of protocol/relay fees" — the relay fee is computed and deducted from the user's swap proceeds but never delivered, and there is no code path in `ExternalActionSwap.sol` to recover or re-distribute it. The bug is fully repeatable by any unprivileged caller on every swap transaction where they choose `relay = address(0)`.

Whether this residual balance can subsequently be *stolen* by a later unrelated caller (as the question's proof idea suggests) depends on whether `callRouter`'s returned `swappedAmount` in the concrete implementation (`LifiExternalAction.sol`) is computed from an absolute post-swap token balance of the contract (in which case a leftover stranded balance would inflate the next caller's `swappedAmount` and get swept into their `amountToSendToHinkal`/UTXO) or from the router's own return value/pre-swap balance-diff (in which case the stranded amount would simply keep accumulating rather than being swept). I could not fully confirm this detail from `LifiExternalAction.sol` within the available context, so I cannot certify the "theft by a second unprivileged party" leg of the exploit as proven — but the primary bug (permanent fee-freezing due to missing relay-address validation) is confirmed by code and already meets the High-impact bar on its own.

### Likelihood Explanation
No special preconditions are required beyond calling the public swap flow with attacker-chosen `CircomData` — `relay`, `feeStructure.flatFee`, and `feeStructure.variableRate` are all fields the attacker fully controls when generating their own proof for their own UTXOs. There is no cost beyond normal swap gas/proof generation, and the bug is triggerable on every transaction, making it trivially and repeatedly reachable.

### Recommendation
In `ExternalActionSwap.swap`, mirror the guard already present in `Hinkal._internalTransact`: require that `circomData.relay != address(0)` whenever `totalFee > 0` (i.e., whenever `flatFee` or `variableRate` are nonzero), or alternatively make `sendToRelay` revert instead of silently no-op when `relay == address(0)` and `actualAmount > 0`, forcing the fee structure to be internally consistent with the relay address before any funds are deducted from `amountToSendToHinkal`.

### Proof of Concept
Hardhat fork test plan:
1. Deploy/fork with `ExternalActionSwap`/`LifiExternalAction` registered in `Hinkal`.
2. Generate a valid proof for a deposit + swap transaction where `circomData.relay = address(0)`, `feeStructure.flatFee > 0`, `feeStructure.variableRate > 0`, `erc20TokenAddresses = [inputToken, outputToken]`.
3. Call `Hinkal.transact` with this proof; assert `ExternalActionSwap`'s `outputToken` balance after the call equals `totalFee` (i.e., `relayFee + hinkalFee` was neither sent to relay nor accounted in the returned UTXO), confirming the stranding equality break: `amountToSendToHinkal (transferred+UTXO'd) != swappedAmount - totalFee` is *false* algebraically but `totalFee` itself never left the contract to any party — assert relay's balance stayed at 0 and Hinkal's `ExternalActionSwap` residual balance equals `totalFee`.
4. (To test the sweep claim) Run a second, unrelated unprivileged swap transaction through the same `ExternalActionSwap` contract for the same `outputToken`; inspect whether `callRouter`'s computed `swappedAmount` in this second call includes the stranded residual from step 3 (requires reading `LifiExternalAction.callRouter`'s balance-measurement logic to confirm) and, if so, assert the second caller's resulting `UTXO.amount` exceeds `expectedSwappedAmount - totalFee` by the stranded residual.
