### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) header values are trusted by `WebhookMetadata` without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the app's HMAC secret only authenticates the body bytes. All other webhook identity attributes — `shop`, `topic`, `webhook_id`, `api_version` — are read straight from unauthenticated HTTP headers and are handed unchecked to the app's handler via `WebhookMetadata`. This breaks the intended binding `hmac_verifies(bytes) == identity_of(bytes)`: the bytes that are cryptographically verified (body) are not the bytes that determine which shop the event is attributed to (headers).

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it against the `hmac` field: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only `@raw_body`, while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers that are never included in the signed material: [2](#0-1) 

`Registry.process` validates the HMAC and, once it passes, builds `WebhookMetadata` directly from these unauthenticated header-derived accessors (`request.shop`, `request.topic`, `request.webhook_id`, `request.api_version`), then dispatches it to the app's handler: [3](#0-2) 

The equality the gem is supposed to guarantee is: `bytes_verified_by_hmac == bytes_that_determine_shop_identity`. In reality: `bytes_verified_by_hmac (raw_body) != bytes_that_determine_shop_identity (shopify-shop-domain header)`. Any party in possession of one valid `(raw_body, hmac)` pair for the app's client secret — trivially obtainable by triggering any webhook-eligible event on a shop they control that has the same app installed — can replay that exact body+hmac to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` (and `topic`/`webhook_id`) header. `HmacValidator.validate` still succeeds because it never inspects headers, and the forged `shop` value flows straight into the handler as trusted data.

The gem's own documentation reinforces that this is a real trust boundary and not host misuse: it states that `Registry.process` "will verify the request did indeed come from Shopify" before describing `data.shop` as "The shop domain of the webhook," giving no indication that this field is unauthenticated: [4](#0-3) [5](#0-4) 

### Impact Explanation
Applications that use `data.shop` from `WebhookMetadata` to decide which tenant's records to look up, update, or act on (the exact documented usage pattern: `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) can be made to attribute a legitimate, HMAC-valid webhook event to an arbitrary victim shop of the attacker's choosing. This is a cross-tenant data/identity confusion: an unprivileged internet user who merely has the app installed on their own shop can forge events "from" any other shop that also has the app installed, without ever needing the app's `client_secret`, an access token, or any credential belonging to the victim shop.

### Likelihood Explanation
The webhook HTTP endpoint is, by design, a public route (`docs/usage/webhooks.md` example is a plain unauthenticated Rails controller action). Obtaining one valid `(body, hmac)` pair only requires installing the target app on an attacker-controlled shop (a normal, unprivileged action) and triggering an event; the header swap and replay require no cryptographic material. The only gem-level gate — `HmacValidator.validate` — is bypassed by design because it doesn't cover the header fields at all.

### Recommendation
Include the shop domain (and ideally topic/webhook_id/api_version) in the material that is HMAC-verified, or otherwise cryptographically bind the header-derived `shop` to the signed body (e.g., require the shop domain to be embedded in and derived from the signed payload rather than a sibling header). At minimum, update `to_signable_string` to incorporate these headers, and document clearly that any header value on `WebhookMetadata` used before this fix is unauthenticated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a shop they legitimately control) and triggers a subscribed event (e.g., `orders/create`), causing Shopify to POST a webhook to the app's public callback URL with a body `B` and a valid `X-Shopify-Hmac-Sha256: H` computed over `B` with the app's shared `client_secret`.
2. Attacker captures `(B, H)` from their own delivery (or their own server logs).
3. Attacker replays an HTTP POST to the same app webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches `H`, so validation passes: [6](#0-5) 
5. The handler receives `WebhookMetadata` with `shop == "victim-shop.myshopify.com"` even though the event body actually originated from `attacker-shop.myshopify.com`, and performs whatever tenant-scoped action the app implements keyed on `data.shop`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
