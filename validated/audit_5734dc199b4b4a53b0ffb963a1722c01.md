### Title
Unrestricted swap-route pool addresses can steal a caller’s unrelated wallet tokens through the signed authorization tree - ([File: contracts/swap-aggregator/src/execute/mod.rs])

### Summary

The swap aggregator treats every pool address in a user-supplied route as an untyped `Address` and invokes venue functions on it without checking a pool allowlist. During `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, or a direct router call, a malicious route can place attacker-controlled contract code beneath the caller’s authorized operation. That code can add a token transfer from the caller’s wallet to the caller’s authorization tree. If a client signs the authorization tree returned by simulation without rejecting the extra child, unrelated wallet tokens are transferred to the attacker while the visible lending swap still completes.

### Finding Description

`Router::execute_strategy` accepts arbitrary `StrategyPayload` bytes, decodes the route, and executes it for the authorized `sender`. [1](#0-0)  The route’s `assets` registry explicitly contains both token and pool addresses. [2](#0-1)  Program decoding validates only that the pool registry index exists; it does not verify that the address is a known venue contract. [3](#0-2) 

At execution time, a swap hop copies the payload-selected `pool`, `token_in`, and `token_out` addresses into `SwapHop` and dispatches it to the selected venue adapter. [4](#0-3)  The Soroswap adapter then invokes attacker-controlled code at the supplied pool address through `get_reserves` and `swap`. [5](#0-4) 

The controller reaches this router from `swap_collateral`, which requires owner-or-delegate authorization, withdraws collateral, and submits the caller-supplied swap payload. [6](#0-5)  `swap_tokens` authorizes only the expected routed-input transfer from the controller, but it does not constrain what the selected pool does under the original caller’s broader `sender.require_auth()` authorization at the router entrypoint. [7](#0-6) [8](#0-7) 

The repository’s authorization-tree test demonstrates the exploit directly: a payload-selected rogue pool calls `token.transfer(victim, attacker, amount)`, simulation attaches that unrelated wallet transfer as a child of the victim’s `swap_collateral` authorization, and enforcing mode executes it when that child is signed. [9](#0-8) [10](#0-9) [11](#0-10) 

### Impact Explanation

A malicious pool can transfer any token for which the victim can authorize `transfer(victim, attacker, amount)`, including assets unrelated to the loan position and never supplied to the protocol. The theft is not bounded by `total_in`, `min_out`, routed collateral value, or the final account health check. The test demonstrates loss of the victim’s entire `77_770_000_000` wallet balance while the swap still deposits the expected output. [12](#0-11) [13](#0-12) 

This is theft of user funds. The controller’s post-swap accounting only verifies that the configured input was not overspent and that a positive output arrived. [14](#0-13)  It cannot detect an unrelated transfer from the caller’s wallet performed by route-selected code.

### Likelihood Explanation

An attacker needs to persuade a victim to execute a strategy carrying a malicious route and sign the authorization tree produced during simulation. That is plausible when routes are assembled by a third-party UI, API, bot, or quote service rather than independently decoded by the wallet user. No privileged role, leaked key, upgrade, or market manipulation is required. The pool address is route-controlled, and the tested transaction succeeds while returning a fair-looking swap output. [15](#0-14) [16](#0-15) 

The exploit is limited by Soroban authorization: a caller who signs only the honest expected authorization tree causes the rogue transfer to fail and the transaction to roll back. [17](#0-16)  Therefore the practical prerequisite is a client or signer accepting a poisoned simulated authorization tree without enforcing the expected child set.

### Recommendation

Do not allow payload-selected addresses to reach venue calls as arbitrary pools. Maintain an allowlist of pool contract addresses or hashes per venue, or validate pools through venue factories/registries before dispatch. The authorization-sensitive boundary should also be minimized: router `sender.require_auth()` should authorize only the exact expected input-transfer subtree where possible, and clients must reject any authorization tree containing children beyond the expected exact input transfer.

### Proof of Concept

1. The victim owns a funded lending account and also holds an unrelated token never supplied to the protocol.
2. The attacker deploys a malicious pool contract whose `swap` function calls:
   ```rust
   token::Client::new(&env, &wallet_token)
       .transfer(&victim, &attacker, &wallet_balance);
   ```
   The test’s `RogueHopPool::swap` implements this behavior. [18](#0-17) 
3. The attacker constructs `swap_collateral(caller=victim, account_id, current=USDC, amount, new=ETH, swap=malicious_route)`, with `assets` containing the malicious pool address. `Program::decode` accepts it because the pool is merely an indexed `Address`. [3](#0-2) 
4. The router pulls the routed input, dispatches the hop, and invokes the malicious pool. [19](#0-18) [20](#0-19) 
5. Simulation records the unrelated `wallet_token.transfer(victim, attacker, wallet_balance)` as a child of the victim’s `swap_collateral` authorization. [21](#0-20) 
6. If the victim signs that tree, the unrelated token moves to the attacker, while the swap output is still deposited. [11](#0-10)

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
