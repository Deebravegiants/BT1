### Title
Webhook HMAC only signs the raw body, letting the `shop` (and `topic`) attribution be forged for cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from unsigned HTTP headers. `Registry.process` validates the HMAC and then unconditionally trusts `request.shop` for downstream business logic, so the binding between "bytes the HMAC verified" and "the shop the event is attributed to" is broken — mirroring the report's bug class of "a value acted on but not covered by the HMAC."

### Finding Description
`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` using `Context.api_secret_key`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body, excluding all headers: [2](#0-1) 

But `shop`, `topic`, `api_version`, and `webhook_id` — which are used to route to a handler and are handed to application code as trusted identity data — are read straight from the (unsigned) headers: [3](#0-2) 

`Registry.process` validates only the body HMAC, then dispatches to the handler using the unsigned `request.shop`/`request.topic` values, treating them as authenticated: [4](#0-3) 

Because Shopify's `client_secret`/`api_secret_key` is shared across every shop that installs the app (not per-tenant), any merchant who has installed the app can receive a legitimately-signed webhook for their own store (valid body + valid HMAC over that body), then replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (and/or `x-shopify-topic`) header. Since the HMAC never covers those headers, `Utils::HmacValidator.validate` still returns `true`, and the handler receives `WebhookMetadata` attributing attacker-controlled body content to a victim shop of the attacker's choosing.

This breaks the equality that should hold: `shop bound by HMAC == shop delivered to handler`. Instead: `shop verified by HMAC (none, body-only) != shop trusted by handler (header, attacker-controlled)`.

### Impact Explanation
This allows a merchant already using the shared app (an unprivileged/low-trust party relative to other tenants) to inject fabricated, attacker-crafted webhook events that the host application will process as if they originated from a different, victim shop. Depending on how the host app's webhook handlers act on `data.shop` (e.g., writing order/customer records, triggering fulfillment logic, updating per-shop state), this is a cross-tenant data-integrity/cross-tenant access issue — one tenant can inject data attributed to another tenant's identity.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate (if low-privilege) install of the app — no leaked secret, no TLS interception, and no privileged account is needed. Capturing one's own real webhook deliveries and replaying them with a modified header is straightforward and reproducible by any app-installing merchant.

### Recommendation
Bind the shop (and ideally topic) identity into the value verified by the HMAC, or independently confirm the header-derived shop against a value that is itself authenticated (e.g., look up the recipient shop server-side by matching the webhook against a known active session/subscription rather than trusting the header verbatim). At minimum, document and enforce that `request.shop`/`request.topic` must not be treated as authenticated when only the body HMAC has been checked.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and receives a legitimate `orders/create` webhook: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, header `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker crafts `B` to contain arbitrary/malicious content (e.g., control over order note/customer fields) since it is their own store's data.
3. Attacker POSTs the same `B` and same `hmac-sha256` header to the app's webhook endpoint, but replaces `x-shopify-shop-domain` with `victim.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` returns `true` because `to_signable_string` only checks `B`: [5](#0-4) 
5. `Registry.process` calls the registered handler with `data.shop == "victim.myshopify.com"` and `data.body` fully attacker-controlled: [6](#0-5)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
