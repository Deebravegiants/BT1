### Title
Fee-on-transfer tokens create escrow insolvency in Tron `IntentGatewayV2.placeOrder` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` credits escrow with the user-requested input amount (minus protocol fee) instead of the amount actually received by the contract, unlike the hardened EVM mainnet version which measures actual balances before/after transfer. If a fee-on-transfer (FOT) token is used as an order input, the gateway under-collects tokens but over-credits escrow accounting, creating a shortfall that can be exploited to drain other users' legitimately escrowed funds.

### Finding Description
`evm/src/apps/IntentGatewayV2.sol::placeOrder` was hardened against fee-on-transfer tokens: it snapshots the ERC20 balance before and after `safeTransferFrom`/predispatch sweep and uses the *actually received* amount to both compute the commitment and credit `_orders[commitment][token]` [1](#0-0) , with the non-predispatch path explicitly doing:
```
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
``` [2](#0-1) 

However, the Tron deployment at `evm/tron/contracts/apps/IntentGatewayV2.sol` does not contain this fix. `reducedInputs[i].amount` is derived purely from `order.inputs[i].amount` (the user-declared, pre-transfer-fee amount) minus the protocol fee [3](#0-2) . The token transfer itself calls `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` without checking the actual balance delta, and the escrow map is then incremented by the un-adjusted `reducedInputs[i].amount`:
```
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
...
_orders[commitment][token] += reducedInputs[i].amount;
``` [4](#0-3) 

The same defect exists in the predispatch branch: dust/shortfall is only checked via `balance - requiredAmount` (assuming balance ≥ requiredAmount, reverting otherwise) but the amount credited to escrow, `reducedInputs[i].amount`, is still computed from the original requested `order.inputs[i].amount` rather than the amount actually swept back from the dispatcher [5](#0-4) .

For a FOT token, the gateway physically receives less than `order.inputs[i].amount`, yet the internal escrow ledger (`_orders[commitment][token]`) is inflated to the pre-fee value. Because `_orders` is a shared per-token ledger across all commitments/orders held by the same contract, the resulting deficit means the contract's on-chain token balance is insufficient to cover the sum of all outstanding escrow entries. When later orders are filled/redeemed (`RedeemEscrow`/refund paths transferring out the full recorded `_orders[commitment][token]` amount), the contract will pay out more than it holds for that token, effectively draining balances that belong to other, unrelated orders escrowed in the same token — a first-come-first-served insolvency race.

### Impact Explanation
This is a direct accounting/fund-safety bug reachable by any unprivileged user submitting a `placeOrder` transaction with a FOT token as input on Tron. It does not merely mis-price a single user's own order; it corrupts the shared escrow ledger for that token contract-wide, enabling later fillers/redeemers to withdraw more tokens than the contract holds, at the expense of other orders' legitimately escrowed principal. This can cause permanent loss of funds for other users and is not contained to the FOT order placer alone. Given that the audit scope for this program explicitly allows fee-on-transfer tokens to be submitted, this is a concrete accounting/theft vector, meeting Medium severity per the impact criteria (potential loss of escrowed user funds).

### Likelihood Explanation
Likelihood is moderate to high: it requires only a single `placeOrder` call using an FOT-style ERC20 as an input token, something the protocol explicitly does not prevent (no allow-list preventing FOT tokens is evident in this function). No privileged access or governance action is needed — any user (or an attacker deliberately deploying/using an FOT token, or interacting with a token that later becomes fee-charging via governance) can trigger it.

### Recommendation
Apply the same fix already present in `evm/src/apps/IntentGatewayV2.sol` to the Tron variant: measure the actual token balance of the gateway (and the dispatcher, in the predispatch sweep) before and after each `safeTransferFrom`/sweep, and use the delta (actual received amount) — not the user-declared `order.inputs[i].amount` — as the basis for `reducedInputs[i].amount`, the commitment hash, and the value credited to `_orders[commitment][token]`.

### Proof of Concept
1. Deploy an ERC20 with a transfer fee (e.g., 1% burned on `transferFrom`, as modeled by the `FeeOnTransferToken` test contract used against the mainnet EVM contract) [6](#0-5) .
2. Call `IntentGatewayV2(tron).placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}` and no predispatch. The contract transfers `1000e18` via `safeTransferFrom` but the gateway's FOT balance only increases by `990e18` (1% fee burned) [7](#0-6) .
3. `_orders[commitment][FOT]` is nonetheless credited with `reducedInputs[0].amount` computed from the full `1000e18` (minus any protocol fee) — i.e., ~`1000e18` rather than the actual `990e18` held.
4. Place a second, unrelated order using the same FOT token as input, correctly escrowing its own funds.
5. When the first order is filled/redeemed via the cross-chain settlement path, the contract attempts to release the over-stated escrow amount for the first commitment, consuming FOT balance that includes the second order's escrowed principal, leaving the second order's escrow unbacked/undercollateralized when it is later redeemed — resulting in a failed transfer or partial loss for the second order's beneficiary.

contract FeeOnTransferToken {
    string public name = "FeeOnTransferToken";
    string public symbol = "FOT";
    uint8 public decimals = 18;
    uint256 public totalSupply;
    uint256 public feeBps;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    constructor(uint256 _feeBps) {
        feeBps = _feeBps;
    }

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        totalSupply += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        return _transfer(msg.sender, to, amount);
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
        // fee is burned
        totalSupply -= fee;
        return true;
    }
