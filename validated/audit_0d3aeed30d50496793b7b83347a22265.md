## Analysis

I traced the exact equality this question is testing:

**Claimed invariant:** *one value-bearing leaf → one nullifier ever accepted for it.*

**Actual on-chain/circuit behavior:** a nullifier is a pure function of `(commitment, signature)` content — **not** of the leaf's tree index — and `commitment` itself has **no per-note random blinding factor**, so two structurally identical UTXOs collapse to the *same* nullifier.

### Trace

- `OriginalCommitmentCalculator` computes `commitment = Poseidon(amount, erc20TokenAddress, publicKey, timeStamp)` — deterministic, content-only, no nonce/salt. [1](#0-0) 

- `NullifierCalculator` computes `out = Poseidon(commitment, signature) * (1 - isZero(commitment))`, where `signature = Poseidon(nullifyingPrivateKey, commitment)`. Nothing here references the leaf's Merkle position, chain id, or contract address. [2](#0-1) 

- In `MainEVMCircuit`, all outputs in a single `transact` call share **one** `outTimeStamp` signal, and each output's `publicKey` (`outPublicKeys[i][j]`) is a raw, prover-supplied private input with **no distinctness constraint** across outputs. The circuit only re-checks `calcOutCommitment[i][j].out === outCommitments[i][j]` per output — it never forces `outCommitments[i][j1] != outCommitments[i][j2]`. [3](#0-2) 

- On the spend side, the nullifier check is `inNullifiers[i][j] === calcNullifier[i][j].out`, purely content-derived, and it is verified against the Merkle root generically (`MerkleRootCalculator` accepts any valid inclusion path) — no linkage from nullifier to the specific leaf index used. [4](#0-3) 

- On-chain, `insertNullifiers` maintains one global `mapping(uint256 => bool) nullifiers` and reverts unconditionally on any repeat value, with zero awareness of which leaf/tree-index it corresponds to: [5](#0-4) 

- Neither `dimensionsCheck` nor `checkOnchainCreation` in `HinkalHelper` enforce distinctness of `outCommitments`, and `circomData.timeStamp` is never checked against `block.timestamp` in the base flow (only `ExternalActionSwap` has a deadline window, irrelevant here). [6](#0-5) 

### Consequence

A malicious **sender** (unprivileged, self-funded) building an ordinary `Hinkal.transact` call can freely choose two output slots `outCommitments[i][j1]` and `outCommitments[i][j2]` with identical `(amount, erc20TokenAddress, publicKey, timeStamp)` targeting a third-party recipient's stealth address (the sender legitimately knows the recipient's real public key + freely chosen ephemeral randomness to construct valid stealth outputs, since stealth-address computation is entirely off-circuit input here). Both leaves get inserted into the Merkle tree at distinct indices, and the contract's ERC20 balance is correctly increased/backed for both. When the honest recipient later spends *one* of the two identical UTXOs, `insertNullifiers` records nullifier `N`. The second, economically distinct, fully-backed UTXO is permanently unspendable: any valid proof of ownership over it *must* re-derive the same content-only `(commitment, signature)` pair and hence the same `N`, which `insertNullifiers` will always reject as already used.

This matches the Critical impact category "permanent freezing of user funds" — the victim recipient loses access to one of two seemingly-independent value transfers forever, while the funds remain locked and unrecoverable inside the contract.

### Title
Nullifier is a pure function of UTXO content with no per-note salt or leaf-index binding, allowing duplicate output commitments whose second instance is permanently unspendable - (`circuits/NullifierCalculator.circom`, `circuits/OriginalCommitmentCalculator.circom`, `contracts/HinkalBase.sol::insertNullifiers`)

### Summary
`NullifierCalculator` derives a nullifier solely from `Poseidon(commitment, signature)`, and `OriginalCommitmentCalculator` derives `commitment` solely from `(amount, erc20TokenAddress, publicKey, timeStamp)` — with no random blinding factor and no leaf-index binding. Because `MainEVMCircuit` never enforces distinctness across `outCommitments`, and all outputs of one call share a single `outTimeStamp`, a sender can create two economically real, fully-funded UTXOs that are bit-for-bit identical; spending either produces the same nullifier, and `HinkalBase.insertNullifiers`'s global `nullifiers` mapping then permanently blocks the second, value-bearing leaf from ever being redeemed.

### Finding Description
Broken equality: *"one funded leaf ⇒ one nullifier eventually accepted for it"* fails because nullifiers are keyed purely by `(commitment, signature)` content, and `commitment` has no per-instance uniqueness guarantee (no nonce/blinding, no leaf index, no chain/contract domain separation).

Attack path:
1. Attacker (as sender) calls `Hinkal.transact` with `dimensions.outputAmount >= 2` for one token, choosing `outAmounts[i][j1] = outAmounts[i][j2] = X`, `outPublicKeys[i][j1] = outPublicKeys[i][j2] = P` (recipient's real stealth pubkey with attacker-chosen ephemeral randomness), and relies on the shared circuit-wide `outTimeStamp`. `erc20TokenAddresses[i]` is identical for both. This produces `outCommitments[i][j1] == outCommitments[i][j2]` — both circuit-valid, since the only check is `calcOutCommitment[i][j].out === outCommitments[i][j]` per slot, with no cross-output inequality constraint (`circuits/MainEVMCircuit.circom:152-165`).
2. Deposit/transfer amounts are `2X`; the contract's balance requirement (`balanceDif == amountChanges + utxoAmount`) is satisfied honestly — both leaves are genuinely backed.
3. `insertCommitments` inserts both identical leaves at distinct tree positions.
4. Victim recipient later spends leaf `j1` with a valid proof; `insertNullifiers` sets `nullifiers[N] = true` (`contracts/HinkalBase.sol:135-152`).
5. Victim (or anyone with the spending key) attempts to spend leaf `j2`. Any valid proof of ownership must reconstruct the identical `(commitment, signature)` pair, hence identical `N` — `insertNullifiers` reverts with "Nullifier cannot be reused" forever.

Existing guards do not prevent this: `dimensionsCheck`/`checkOnchainCreation` never check for duplicate `outCommitments`; the Merkle inclusion check (`ForceEqualIfEnabled`) is per-leaf-path and accepts either identical leaf; `OverflowPreventer`/`inTotal+amountChanges===outTotal` only bound total sums, not distinctness.

### Impact Explanation
Value corresponding to the second duplicate UTXO becomes permanently frozen inside the Hinkal contract — no key material can ever produce a fresh, acceptable nullifier for it, because the nullifier is fully determined by content that is identical to an already-spent nullifier. This matches "permanent freezing of user funds" (Critical). The attacker is the transaction's sender (who chooses the duplicate outputs); the loss falls on the recipient of those outputs, i.e., a third party, or on the attacker's own funds if self-targeted. It is repeatable per attacker-crafted transaction, and the frozen amount scales with however many duplicate outputs are packed into one call.

### Likelihood Explanation
Preconditions: attacker must be able to build a valid Groth16 proof for `MainEVMCircuit` with `outputCount >= 2` for some token — entirely achievable by any unprivileged user who can run the proving toolchain the protocol already ships. No special role, timing, or third-party cooperation required beyond crafting the calldata; the recipient does not need to consent or even be aware, since `outPublicKeys` are private circuit inputs chosen solely by the sender. Cost is one legitimate deposit of `2X` tokens (fully self-funded, no external capital needed) plus gas. This is straightforward and fully reproducible.

### Recommendation
Add a unique per-UTXO random blinding value (nonce/salt) to the commitment preimage (in addition to amount/token/publicKey/timeStamp) so that two economically-identical UTXOs never share a commitment, and hence never share a nullifier. Additionally/alternatively, bind the nullifier or commitment to the leaf's tree index or insertion order so that content collisions cannot map to the same nullifier value. As a circuit-side defense-in-depth, also enforce `outCommitments[i][j1] != outCommitments[i][j2]` for `j1 != j2` within a single proof.

### Proof of Concept
Foundry/Hardhat plan:
1. Deploy `Hinkal` + circuits with a small `MainEVMCircuit` configuration (`tokenCount=1, outputCount=2`).
2. Attacker deposits `2X` tokens and generates a valid Groth16 proof for a `transact` call producing `outCommitments[0][0] == outCommitments[0][1]` (identical `amount=X`, `erc20TokenAddress`, `publicKey`, shared `outTimeStamp`).
3. Submit `transact`; assert both leaves inserted (`NewCommitment` events with distinct indices, equal commitment value), contract balance increased by `2X`.
4. Generate a valid spend proof for leaf index 0 (using the correct `nullifyingPrivateKey`/`H0` reproducing `publicKey`); submit `transact`; assert `nullifiers[N] == true` and recipient receives `X`.
5. Generate a valid spend proof for leaf index 1 using the same key material (necessarily producing nullifier `N` again); submit `transact`; assert it **reverts** with `"Nullifier cannot be reused"`.
6. Assert: contract still holds `X` tokens backing leaf 1, and no combination of valid witnesses can produce a nullifier `N' != N` for that leaf — proving the value is permanently stranded (equality `funded leaves == successfully-nullified leaves` is broken: `2 != 1`).

  signal input commitment;
  signal input signature;

    function insertNullifiers(
        uint256[][] calldata inputNullifiers,
        bool[] calldata onChainCreation
    ) internal {
        for (uint256 i = 0; i < inputNullifiers.length; i++) {
            for (uint256 j = 0; j < inputNullifiers[i].length; j++) {
                if (onChainCreation[i] == true) break;
                if (inputNullifiers[i][j] != 0) {
                    require(
                        !nullifiers[inputNullifiers[i][j]],
                        "Nullifier cannot be reused"
                    );
                    nullifiers[inputNullifiers[i][j]] = true;
                    emit Nullified(inputNullifiers[i][j]);
                }
            }
        }
    }
