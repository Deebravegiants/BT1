### Title
Webhook `shop-domain`, `topic`, `api-version`, and `webhook-id` headers are not covered by the HMAC signature, allowing cross-tenant metadata forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers to build the `WebhookMetadata` passed to the app's handler. Because the signature never binds the shop identity to the payload, any party that can obtain one valid `(body, hmac)` pair for the app's shared secret can replay that pair with an arbitrary `shop-domain` header and have the library report it as belonging to a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC over exactly that signable string and secure-compares it to the `hmac` header value: [2](#0-1) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all read straight from HTTP headers with no cryptographic binding to the signed body: [3](#0-2) 

`Registry.process` validates only the HMAC, then forwards `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` unchanged into `WebhookMetadata` for the app's handler: [4](#0-3) 

`WebhookMetadata` is a plain struct with a `shop` field the handler is expected to trust for tenant identification: [5](#0-4) 

The broken binding, stated as an equality that the code fails to enforce:
`shop bytes covered by the HMAC` ≠ `shop bytes acted upon by the handler`.
The HMAC secret (`Context.api_secret_key`) is a single shared secret for the app across *all* installed shops, not scoped per-tenant. Since the signature covers only the JSON body and not the shop header, any valid `(body, hmac)` pair obtained from one tenant's genuine webhook delivery remains valid when replayed with a different `shop-domain` header. `Registry.process` will pass HMAC validation and hand the handler a `WebhookMetadata` claiming an attacker-chosen `shop`, `topic`, `api_version`, or `webhook_id` alongside the original signed body.

### Impact Explanation
This is a cross-tenant identity-binding break: an unprivileged actor who can capture (e.g., as the merchant/owner of their own shop where the app is installed, observing their own legitimately-delivered webhook) a valid `(body, hmac)` pair can relabel it as coming from any other shop merely by changing the `shop-domain` header, since nothing in the signed payload constrains which tenant it applies to. Any app relying on `WebhookMetadata#shop` for tenant-scoped writes (this is the documented, intended use of the field per `lib/shopify_api/webhooks/webhook_handler.rb`) can be made to apply attacker-supplied JSON body content under a victim shop's identity — a cross-tenant integrity issue that satisfies the "cross-tenant access" impact bucket, because the library itself provides no means to distinguish a genuine shop-bound webhook from a relabeled one.

### Likelihood Explanation
Likelihood is bounded by the fact that the attacker needs at least one genuine `(body, hmac)` pair signed with the app's secret — trivially available to any shop where the app is installed (a legitimate but unprivileged tenant of a multi-tenant app), since Shopify delivers webhooks to a public HTTPS endpoint the merchant does not otherwise control. Reusing that pair with a modified `shop-domain` header is a pure header-rewrite with no cryptographic obstacle, since `to_signable_string` never includes the header.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the value that is HMAC-verified, or independently authenticate `request.shop` against the session/shop the caller is registered for before constructing `WebhookMetadata`. At minimum, document that `Registry.process` does not authenticate the shop header and that host apps must not treat `WebhookMetadata#shop` as an authenticated tenant identifier unless corroborated by a stored, previously-established shop-session mapping.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; attacker (as installer) triggers a webhook delivery (e.g., `orders/create`) and captures the raw request: body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)`.
2. Attacker replays the request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` recomputes HMAC over `B` only [2](#0-1)  and it matches `H`, so validation passes.
4. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: B, ...)` [6](#0-5) , causing the app to act on attacker-controlled body content under the victim shop's identity.
