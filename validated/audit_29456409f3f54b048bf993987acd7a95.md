Confirmed. The webhook HMAC covers only the raw body (`to_signable_string` returns `@raw_body`), while the `shop`, `topic`, `webhook_id`, and `api_version` values that identify *which tenant* the webhook belongs to are all pulled from HTTP headers that are never included in the signature.

### Title
Webhook `shop` identifier is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body [1](#0-0) , so `Utils::HmacValidator.validate` in `Registry.process` only proves that the *body* was signed with the app's secret [2](#0-1) . The `shop` value, which is taken from the `shopify-shop-domain`/`x-shopify-shop-domain` header [3](#0-2) , is never part of the signed payload, yet it is trusted as the tenant identifier and forwarded straight into the handler's `WebhookMetadata` [4](#0-3) .

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, body || headers-that-determine-tenant)`. Instead the gem only checks `hmac == HMAC(secret, body)` and then unconditionally trusts the unauthenticated `shop-domain` header as the source of tenant identity passed to the app's webhook handler. Since an app's `client_secret` (and thus the HMAC key) is shared across all shops that install the app, any shop that installs the app can trigger a legitimate webhook (e.g. `orders/create`) and receive a body + valid HMAC pair signed with that shared secret. The header (`shop-domain`, `topic`, `webhook-id`, `api-version`) is completely decoupled from the signature, so an attacker can replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate(request)` still passes because it only recomputes the HMAC over `@raw_body` [5](#0-4) [6](#0-5) , and `Registry.process` then dispatches the (attacker-controlled) body to the app's handler tagged as belonging to the victim's `shop` [7](#0-6) .

### Impact Explanation
This breaks the tenant boundary the gem is supposed to guarantee for webhook consumers: the handler is told "this event belongs to shop X" purely on the basis of an unauthenticated header, even though the only cryptographic guarantee provided is "this body was produced by some shop that has this app installed." A malicious merchant can therefore inject arbitrary attacker-chosen webhook bodies attributed to any other merchant using the same app (cross-tenant access/data injection), e.g. spoofing `app/uninstalled`, `shop/redact`, `customers/data_request`, or `orders/create` payloads against a victim shop that never sent them. Depending on what the host app does with `WebhookMetadata#shop` (session/token lookup, data deletion, compliance actions), this can trigger destructive or trust-breaking actions against an unrelated tenant.

### Likelihood Explanation
Any unprivileged internet user who can install the same app on their own free/dev shop (a normal, low-privilege action) can generate valid `(body, hmac)` pairs and replay them with a forged `shop-domain` header — no access token, `client_secret`, or privileged account is required.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed payload used by `to_signable_string`, or otherwise cryptographically bind the `shop` value to the verified body, instead of trusting it purely from unauthenticated headers.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g. updates an order) to receive a legitimate `(raw_body, X-Shopify-Hmac-Sha256)` pair from Shopify, signed with the app's shared `client_secret`.
2. Attacker replays that exact `raw_body` and `hmac` header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` and (optionally) another `X-Shopify-Topic`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only [1](#0-0)  — validation succeeds since the body/HMAC pair is genuinely valid.
4. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body:, ...)` [4](#0-3) , causing the host application to process attacker-controlled data as if it originated from the victim shop.
