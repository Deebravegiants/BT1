### Title
Pharos consensus client accepts a single supermajority-signed block as immediately "finalized" with no reorg/adjacency safeguard, unlike the BSC client's equivalent check - ([File: modules/consensus/pharos/verifier/src/lib.rs])

### Summary
The Fortuna report's root cause is that a randomness provider conflated "sufficiently confirmed" with "actually final," allowing a chain reorg to invalidate a state the provider had already acted on. The Pharos `ConsensusClient` in Hyperbridge exhibits the analogous flaw: `verify_pharos_block` treats any block carrying a single BLS aggregate signature from ≥2/3+1 stake of the *currently trusted* validator set as immediately and irreversibly `finalized_block_number`, with **no requirement that this attestation be confirmed by a subsequent round/child block** before Hyperbridge commits the corresponding `StateCommitment` and starts the message-relay/challenge-period clock.

### Finding Description
`verify_pharos_block` in `modules/consensus/pharos/verifier/src/lib.rs` advances `finalized_block_number`/`finalized_hash` as soon as `verify_block_signature` passes: [1](#0-0) 

`verify_block_signature` only checks (a) all signers belong to the trusted validator set, (b) signers hold >2/3 stake, and (c) the aggregate BLS signature is valid over the single block's `block_proof_hash`: [2](#0-1) 

This is a **single-round attestation check** — it never inspects a child/subsequent block to confirm that the attested block cannot be reorged. Compare this to the BSC consensus client in the same codebase, which implements exactly the safeguard that is missing here: BSC's `verify_bsc_header` explicitly refuses to treat a `source_header` as finalized unless a `target_header` justifying it is its *direct child* (`NonConsecutiveFinalization`), because "a supermajority-signed but non-adjacent vote justifies `target_header` yet leaves `source_header` merely justified and still reorg-able": [3](#0-2) [4](#0-3) 

The Pharos client has no equivalent "two consecutive attestations" (or any other reorg-resistance) rule — `verify_pharos_block` only compares `update_block_number` to the previously stored `finalized_block_number` and epoch continuity, then immediately commits: [5](#0-4) 

Once `PharosClient::verify_consensus` returns this state, `update_client` in ISMP core stores it as a canonical `StateCommitment` and starts the `challenge_period`/relay clock immediately — the same commitment used later for `verify_membership`/`verify_non_membership` when relayers deliver POST requests or process timeouts: [6](#0-5) [7](#0-6) 

If the underlying Pharos protocol allows more than one supermajority-signed block to exist for the same height/round before a subsequent commit stage locks it in (any BFT variant that isn't strictly single-round, or any liveness attack that lets a colluding/compromised subset of validators — or previously-honest validators re-signing after a fork — produce a competing supermajority-signed block), a relayer/attacker can get Hyperbridge's light client to record a state root that later gets reorged out, exactly mirroring the Fortuna finality-gadget bug: "reveal"/deliver against a not-yet-truly-final state, then have the underlying chain reorg away from it.

The PharosClient's `verify_fraud_proof` (double-sign detection) is the only backstop, and it depends entirely on the fisherman/relayer network observing and submitting the conflicting header **within the configured `challenge_period`** (5 minutes in the integration test config) before request/response messages become processable: [8](#0-7) [9](#0-8) 

This after-the-fact fraud-proof model is precisely the kind of finality assumption the Fortuna report warns is unsound for consensus systems with a separate liveness/finality distinction: it works only if a signed-but-not-truly-final block can be proven equivocated and only if that proof arrives before the challenge period elapses and messages are delivered — there is no positive confirmation that the committed block is unreorgable at commitment time.

### Impact Explanation
If a supermajority-signed-but-reorgable Pharos block is committed as `StateCommitment` and used to satisfy `verify_membership`/`verify_non_membership` for POST/GET request delivery (`modules/ismp/state-machines/evm/src/lib.rs`) before the underlying chain's true finality catches up, a subsequent reorg can invalidate the state root that requests/responses/timeouts were proven against. This can lead to forged message delivery (a request that was never actually included on the canonical Pharos chain being accepted as delivered) or double-processing after a reorg reverts the referenced state — a High severity outcome per the ruleset (unsound state commitment / forged message delivery), reachable by any relayer submitting a `ConsensusMessage` carrying a validly-signed-but-non-final Pharos block update.

### Likelihood Explanation
Exploitation requires the ability to produce (or observe) two conflicting supermajority-signed blocks at essentially the same height before Pharos's own finality mechanism resolves them, or to exploit whatever confirmation delay exists between Pharos's block-signing and its actual irreversibility guarantee — analogous to the difficulty described in the Fortuna report for Ethereum PoS finality-gadget stalls. This is High difficulty (requires validator collusion, a liveness fault, or an as-yet-unconfirmed understanding of Pharos's exact commit rules) but the code path itself provides zero defense-in-depth against it, unlike the sibling BSC client in the same repository which explicitly hardened this exact class of bug.

### Recommendation
Add an analogous adjacency/2-round confirmation rule to `verify_pharos_block`/`verify_block_signature`, mirroring BSC's `NonConsecutiveFinalization` check: require proof that a subsequent block (or round) also attests to/builds on the signed block before advancing `finalized_block_number`, so that a single supermajority signature is never alone sufficient to mark a block as unreorgable. Alternatively, require an explicit protocol-level finality proof from Pharos consensus (if one exists) rather than inferring finality from block-level BLS signatures. Document precisely what finality guarantee a single Pharos `BlockProof` provides and validate that assumption against the actual Pharos client implementation before treating it as final in Hyperbridge's state machine.

### Proof of Concept
Not independently reproducible from the indexed code alone: doing so requires confirming Pharos's actual underlying consensus/commit-round semantics (i.e., whether a single 2/3+1 BLS-signed block can be re-signed differently after a fork, or whether Pharos guarantees single-round finality by design). This is not present in the indexed docs (`docs/content/protocol/consensus/parlia.mdx` documents BSC's Parlia consensus in detail but there is no equivalent Pharos consensus-protocol write-up in the indexed docs). Given index size limits, some file contents describing Pharos's native consensus protocol may not be available; a Devin session with full repository/documentation access should verify whether Pharos's protocol provides single-round finality equivalent to what `verify_pharos_block` assumes before confirming exploitability.

pub fn verify_pharos_block<C: Config, H: Keccak256 + Send + Sync>(
	trusted_state: VerifierState,
	update: VerifierStateUpdate,
) -> Result<VerifierState, Error> {
	let update_block_number = update.block_number();
	let current_block_number = trusted_state.finalized_block_number;

	if update_block_number <= current_block_number {
		return Err(Error::StaleUpdate {
			current: current_block_number,
			update: update_block_number,
		});
	}

	let computed_hash = Header::from(&update.header).hash::<H>();

	if computed_hash != update.block_proof.block_proof_hash {
		return Err(Error::BlockProofHashMismatch {
			computed: computed_hash,
			provided: update.block_proof.block_proof_hash,
		});
	}

	fn verify_fraud_proof(
		&self,
		_host: &dyn IsmpHost,
		trusted_consensus_state: Vec<u8>,
		proof_1: Vec<u8>,
		proof_2: Vec<u8>,
	) -> Result<(), Error> {
		let update_1 = VerifierStateUpdate::decode(&mut &proof_1[..]).map_err(|e| {
			Error::AnyHow(
				anyhow::anyhow!("Cannot decode pharos update for proof 1: {:?}", e).into(),
			)
		})?;

		let update_2 = VerifierStateUpdate::decode(&mut &proof_2[..]).map_err(|e| {
			Error::AnyHow(
				anyhow::anyhow!("Cannot decode pharos update for proof 2: {:?}", e).into(),
			)
		})?;

		let header_1 = &update_1.header;
		let header_2 = &update_2.header;

		if header_1.number != header_2.number {
			return Err(Error::Custom("Invalid fraud proof: different block numbers".to_string()));
		}

		let header_1_hash = Header::from(header_1).hash::<H>();
		let header_2_hash = Header::from(header_2).hash::<H>();

		if header_1_hash == header_2_hash {
			return Err(Error::Custom("Invalid fraud proof: identical headers".to_string()));
		}

		let consensus_state =
			ConsensusState::decode(&mut &trusted_consensus_state[..]).map_err(|e| {
				Error::AnyHow(
					anyhow::anyhow!("Cannot decode trusted consensus state: {:?}", e).into(),
				)
			})?;

		let trusted_state: VerifierState = consensus_state.into();

		verify_pharos_block::<C, H>(trusted_state.clone(), update_1)
			.map_err(|e| Error::AnyHow(anyhow::Error::from(e).into()))?;

		verify_pharos_block::<C, H>(trusted_state, update_2)
			.map_err(|e| Error::AnyHow(anyhow::Error::from(e).into()))?;

		Ok(())
	}
