### Title
Webhook `shop` and `topic` headers are unauthenticated (HMAC only covers raw body), enabling cross-tenant handler invocation via `Registry.process` - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`Registry.process` selects the handler from the shared `@registry` class-level Hash using `request.topic`, and constructs `WebhookMetadata` using `request.shop`, but `HmacValidator.validate` only verifies the HMAC over the raw request body (`Request#to_signable_string` returns `@raw_body`), never over the `shop-domain` or `topic` headers. Any attacker who has legitimately received one genuinely-signed webhook (e.g., on their own development shop) can replay that exact validated body+HMAC pair directly to the app's webhook endpoint while freely substituting the `X-Shopify-Shop-Domain` and `X-Shopify-Topic` headers, causing `handler.handle` to run with attacker-chosen `shop` and attacker-selected registered handler.

### Finding Description
The claimed binding is: `WebhookMetadata.shop` (lib/shopify_api/webhooks/webhook_handler.rb:8) == the one Shopify-authenticated identity that produced the HMAC. Tracing the code:

- `Registry.process` (lib/shopify_api/webhooks/registry.rb:188-200) does: `raise ... unless Utils::HmacValidator.validate(request)`, then `handler = @registry[request.topic]&.handler`, then calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))`.
- `Request#shop` and `Request#topic` (lib/shopify_api/webhooks/request.rb:16-23) are read directly from the `shopify-shop-domain`/`shopify-topic` HTTP headers with no cryptographic binding.
- `HmacValidator.validate` (lib/shopify_api/utils/hmac_validator.rb:12-31) calls `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to `verifiable_query.hmac`.
- `Request#to_signable_string` (lib/shopify_api/webhooks/request.rb:35-38) returns only `@raw_body` — the `shop-domain` and `topic` headers are **not** part of the signable string and are **not** covered by the HMAC.

Because of this, the equality `WebhookMetadata.shop == authenticated identity` never holds: the HMAC only proves the raw JSON body was signed with `api_secret_key`; it proves nothing about which shop or topic headers accompanied that body. An attacker who runs their own development shop, installs the target app, and receives one genuine webhook (valid body + valid HMAC signature) can capture that raw body/HMAC pair and POST it directly to the app's public webhook endpoint with arbitrary `X-Shopify-Shop-Domain` and `X-Shopify-Topic` header values. `HmacValidator.validate` still returns `true` (body unchanged), `Registry.process` looks up `@registry[forged_topic]` — a handler shared across all tenants — and invokes it with `WebhookMetadata.shop` set to the forged victim shop domain. No component in this file, `Request`, or `HmacValidator` binds headers to the signature, and there is no `ShopValidator.sanitize!` or session/install lookup performed in this code path to confirm the claimed shop actually corresponds to the signed payload.

### Impact Explanation
Any handler registered in the shared, process-global `@registry` (lib/shopify_api/webhooks/registry.rb:7) executes host-app business logic keyed on an attacker-controlled `shop` value and an attacker-selected `topic`. If the host app's handler uses `WebhookMetadata.shop` to look up/act on merchant-specific records (the documented and expected use), an attacker can trigger that logic against an arbitrary target shop identifier while supplying a payload body they control (their own real webhook body). This is a cross-tenant authentication/authorization bypass at the identity-binding layer: the "authenticated" shop asserted to host app handlers is actually unauthenticated attacker input. Severity: Critical — cross-tenant access, repeatable against arbitrary victim shop domains since the attacker only needs one genuine signed webhook and can replay it indefinitely with different forged headers.

### Likelihood Explanation
Preconditions are all attacker-obtainable per the threat model: create a free development shop, install the app, and let it deliver one real webhook to an endpoint the attacker controls, capturing the raw body and its valid `X-Shopify-Hmac-Sha256` value. No `api_secret_key` or victim credential is needed. The attacker then sends this captured (body, HMAC) pair directly via HTTP to the target app's public webhook route with forged `shop-domain`/`topic` headers — a standard HTTP request, fully within the attacker's control per the rules (headers, body, ordering are attacker-controlled). This requires no race condition and is trivially repeatable against any topic present in `@registry` and any shop string.

### Recommendation
Bind the `shop` and `topic` (and any other trust-relevant metadata) into the HMAC-verified signable content, or otherwise require the resolved shop to be validated against a known/installed session before dispatching to the handler. At minimum, `Registry.process` should cross-check `request.shop` against an authenticated session/install record (e.g., via `Utils::ShopValidator.sanitize!` plus a session store lookup for that shop) rather than trusting the raw header value once HMAC (which never covered it) passes.

### Proof of Concept
```ruby
# test/webhooks/registry_cross_tenant_test.rb
require_relative "../test_helper"

class RegistryCrossTenantTest < Minitest::Test
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
    @handler = Class.new do
      extend T::Sig
      include ShopifyAPI::Webhooks::WebhookHandler
      def self.handle(data:); $captured_shop = data.shop; end
    end
    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "orders/create", delivery_method: :http, path: "/webhooks", handler: @handler
    )
  end

  def test_forged_shop_header_is_accepted_with_valid_body_hmac
    raw_body = '{"id":1}'
    hmac = Base64.strict_encode64(
      OpenSSL::HMAC.digest("sha256", "secret", raw_body)
    )
    # legitimate victim shop the attacker never controls
    forged_headers = {
      "x-shopify-hmac-sha256" => hmac,
      "x-shopify-topic" => "orders/create",
      "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-chosen
      "x-shopify-api-version" => "2023-10",
      "x-shopify-webhook-id" => "abc",
    }
    request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

    ShopifyAPI::Webhooks::Registry.process(request)

    assert_equal "victim-shop.myshopify.com", $captured_shop
    # Demonstrates handler executed with an attacker-supplied, unauthenticated shop value
    # despite HMAC validation succeeding, because to_signable_string only covers raw_body.
  end
end
```
This test shows `HmacValidator.validate` passes for any header combination as long as `raw_body` matches the precomputed HMAC, and `Registry.process` dispatches the shared handler using the forged `shop` header — proving the claimed binding is broken.
