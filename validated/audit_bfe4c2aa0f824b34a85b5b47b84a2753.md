Based on my investigation, I found the default global rate limit for HTTP triggers is quite conservative — a test comment confirms "global default (every 30s, burst 3)" for `PerWorkflow.HTTPTrigger.RateLimit` [1](#0-0) , and this is enforced per-workflow (not merely per-owner as the claim states) via `checkRateLimit` [2](#0-1) . I also confirmed that even successfully processed callbacks are *not* removed immediately — they stay in the map (marked `processed`) until the next reaper tick [3](#0-2) , and the reaper only runs once per `CleanUpPeriodMs` (default 10 minutes) via a ticker [4](#0-3) . `setupCallback` indeed only checks for a duplicate `requestID`, never total map size [5](#0-4) , unlike the sibling `capabilities/handler.go`, which enforces both an age-based prune and a `MaxSavedCallbacks` size-based eviction [6](#0-5) .

Audit Report

## Title
Unbounded memory growth in HTTP Trigger callback map lacks a size cap, unlike sibling caches - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

## Summary
`httpTriggerHandler.callbacks` grows by one entry per accepted user trigger request via `setupCallback`, which checks only for duplicate request IDs and never checks total map size, and entries are only reclaimed by a time-based reaper tied to `CleanUpPeriodMs` (default 10 minutes), not by a hard size cap as in the structurally similar `capabilities/handler.go`.

## Finding Description
`setupCallback` inserts a new `savedCallback` entry (containing per-shard response aggregators and a `doneCh` channel) into `h.callbacks[requestID]` after only checking for a duplicate ID [5](#0-4) . Entries are not removed synchronously when a response is sent — they are only marked `processed` and left in the map until the periodic reaper's next sweep [3](#0-2) , and that reaper runs on a fixed interval driven by `CleanUpPeriodMs` (default 600000ms / 10 minutes) [4](#0-3) [7](#0-6) . The only other guard is `checkRateLimit`, a per-workflow rate limiter [2](#0-1) , which throttles the *rate* of new entries but not the total outstanding count. By contrast, `capabilities/handler.go`'s `pruneCallbacks` explicitly enforces a `MaxSavedCallbacks` size ceiling in addition to age-based expiry [6](#0-5) , confirming this is an inconsistency between the two handlers rather than a false claim about the code's behavior.

However, unlike the CVE analogy of truly unbounded allocation, growth here is mathematically bounded by `rate_limit × CleanUpPeriodMs` per workflow, and the default rate limit is quite restrictive — test code documents the default as "every 30s, burst 3" per workflow [1](#0-0) . At that default, a single workflow can accumulate on the order of tens of entries over a 10-minute window before reaping, not an unbounded amount. Scaling this to a memory-exhaustion DoS would require either many distinct registered workflows under attacker control simultaneously, or a misconfigured/loosened rate-limit override — the latter being an operator configuration decision, not a code defect exploitable by a single unprivileged caller.

## Impact Explanation
The underlying observation (missing explicit `MaxSavedCallbacks`-style cap, inconsistent with the sibling handler) is accurate as a defense-in-depth/hardening gap. However, at documented default settings, the per-workflow rate limit already bounds accumulation to a small number of entries per reap cycle, meaning the realistic memory impact under default configuration is minor and does not constitute a practically demonstrated denial-of-service. The report itself acknowledges the impact is speculative and contingent on rate-limit configuration values it could not confirm — and the configuration that was found (default burst 3 / every 30s) undermines the "unbounded growth" framing.

## Likelihood Explanation
Exploitability depends on non-default, loosened rate-limit settings or an attacker controlling many distinct registered workflows, neither of which is demonstrated as a realistic default-configuration path. This does not meet the bar of a concretely reproducible, default-configuration DoS; it is closer to a code-hygiene/defense-in-depth suggestion.

## Recommendation
As defense-in-depth, consider adding a `MaxSavedCallbacks`-style size cap to `h.callbacks` mirroring `capabilities/handler.go`'s `pruneCallbacks`, and/or removing callback entries immediately upon successful response rather than deferring to the periodic reaper.

## Proof of Concept
Not demonstrated against default configuration; the referenced test (`TestHttpTriggerHandler_CheckRateLimit_PerOrgOverride`) confirms the default per-workflow rate limit is "every 30s, burst 3," which bounds accumulation far below any DoS-relevant threshold within a 10-minute reap window [1](#0-0) .

func (h *handler) pruneCallbacks() {
	h.mu.Lock()
	defer h.mu.Unlock()

	// First, remove expired callbacks.
	maxAge := time.Duration(h.config.CallbackMaxAgeSec) * time.Second
	now := time.Now()
	var expired int
	for id, cb := range h.savedCallbacks {
		if now.Sub(cb.createdAt) > maxAge {
			delete(h.savedCallbacks, id)
			expired++
		}
	}

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}

	if expired > 0 || evicted > 0 {
		h.lggr.Infow("Pruned savedCallbacks", "expired", expired, "evicted", evicted, "remaining", len(h.savedCallbacks))
	}
}
