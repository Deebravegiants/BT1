### Title
Webhook topic dispatch trusts unsigned `X-Shopify-Topic` header, allowing a body signed for one topic to be replayed as any other topic - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so the HMAC computed by `HmacValidator.validate` never covers the `topic` header returned by `#topic` [2](#0-1) . `Registry.process` validates only the body HMAC and then dispatches strictly on `request.topic` [3](#0-2) , so an attacker who owns any validly-signed webhook body can relabel it with a different topic header and cause the app to run a handler (e.g. `app/uninstalled`) that Shopify never actually signed for that payload.

### Finding Description
Binding claimed: `topic acted upon by Registry.process` (`request.topic`, read from the mutable `x-shopify-topic` header) `== topic implicitly certified by to_signable_string` (`@raw_body` only). Tracing the code confirms this binding is false:

- `Request#to_signable_string` is defined as `@raw_body` with no topic, shop, webhook-id, or api-version mixed in [1](#0-0) .
- `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to `verifiable_query.hmac` (from `x-shopify-hmac-sha256`) [4](#0-3) . This only proves the body bytes were produced by someone holding `api_secret_key`; it says nothing about which topic that body was originally delivered under.
- `Registry.process` does `raise ... unless Utils::HmacValidator.validate(request)` and then looks up the handler via `@registry[request.topic]&.handler`, later invoking `handler.handle(data: WebhookMetadata.new(topic: request.topic, ...))` [3](#0-2) . `request.topic` is read straight from the attacker-controlled `x-shopify-topic`/`shopify-topic` header via `shopify_header("topic")` [5](#0-4) .

Exploit flow: The attacker installs the app on their own development shop (unprivileged, per rules). Shopify delivers a real webhook (e.g. `orders/create`) to the attacker's own endpoint with a valid `x-shopify-hmac-sha256` computed over that raw body. The attacker captures this exact `raw_body` + valid HMAC, then sends a new HTTP request directly to the app's webhook receiving endpoint with the same body/HMAC but `x-shopify-topic: app/uninstalled` (and, if they also control `x-shopify-shop-domain`, an arbitrary shop value, since that header is likewise excluded from `to_signable_string`). `HmacValidator.validate` returns `true` (body signature still checks out) and `Registry.process` invokes the `app/uninstalled` handler using `orders/create` payload data mislabeled as topic `app/uninstalled`.

No existing guard closes this gap: `HmacValidator.validate` only checks the raw body signature [6](#0-5) ; there is no separate binding of `topic`, `shop`, `webhook-id`, or `api-version` into the signed content anywhere in `Request` or `HmacValidator`.

### Impact Explanation
This lets an attacker cause the app to execute the wrong topic-specific handler logic against a body it never actually received Shopify's authorization for under that topic — e.g., triggering the `app/uninstalled` handler (often used to revoke tokens / purge tenant data) using a body signed for an unrelated event. However, per the audit rules, the attacker here only ever supplies a body Shopify signed for their **own** installed shop/session; the topic/shop headers being unsigned means the *label* on that body can be forged, but the attacker cannot fabricate arbitrary body content Shopify never sent. Combined with the sibling shop-domain-header issue (also excluded from `to_signable_string`), an attacker could additionally forge the `shop` field in `WebhookMetadata` to point at a victim shop, which is what would elevate this into genuine cross-tenant impact — that combination is what actually crosses the tenant boundary; the topic-only mislabeling by itself keeps the blast radius within the attacker's own tenant/session unless the handler trusts the `shop`/`topic` header for authorization decisions it shouldn't. Within the scope of this question (topic only), the concrete, repeatable capability is: forcing a topic-specific handler to run with data/shape it didn't expect, using any topic the attacker chooses, for their own tenant, on every request they craft.

### Likelihood Explanation
Low cost, fully repeatable: the attacker only needs one legitimately-delivered webhook body+HMAC pair from their own shop (trivial to obtain by installing the app and triggering any event), and can then replay it with an arbitrary `x-shopify-topic` value on demand. No secrets, no privileged access, and no TLS interception are required — this only requires the ability to POST directly to the app's public webhook endpoint, which is inherent to how webhook receivers work.

### Recommendation
Bind the topic (and shop domain, webhook-id, api-version) into the value that is HMAC-verified, or otherwise cryptographically/structurally tie the header claims to the signed body — e.g., include `topic`/`shop` in `to_signable_string`, or cross-check `topic`/`shop` against fields embedded in the parsed JSON payload before dispatch, and reject/flag any request that reaches Shopify webhook delivery only through the app's public endpoint without going through Shopify's known delivery IP ranges/verification, or require that `WebhookMetadata` values used for authorization-sensitive decisions never come solely from unauthenticated headers.

### Proof of Concept
```ruby
# test/webhooks/registry_topic_confusion_test.rb
require "test_helper"

class RegistryTopicConfusionTest < Minitest::Test
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
    ShopifyAPI::Webhooks::Registry.clear
    @handled = nil
    handler = Class.new do
      define_method(:handle) { |data:| @handled = data }
    end
    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "app/uninstalled", delivery_method: :http, path: "/webhooks",
      handler: handler.new,
    )
  end

  def test_body_signed_for_orders_create_is_accepted_as_app_uninstalled
    raw_body = '{"id":1,"order_number":42}' # body Shopify actually signed for orders/create
    hmac = OpenSSL::HMAC.digest("sha256", "secret", raw_body)
    signature = Base64.strict_encode64(hmac)

    # Attacker replays the SAME body+signature but relabels the topic header
    forged_request = ShopifyAPI::Webhooks::Request.new(
      raw_body: raw_body,
      headers: {
        "x-shopify-topic" => "app/uninstalled", # attacker-chosen, never signed
        "x-shopify-hmac-sha256" => signature,
        "x-shopify-shop-domain" => "victim-shop.myshopify.com",
      },
    )

    assert ShopifyAPI::Utils::HmacValidator.validate(forged_request)
    assert_equal "app/uninstalled", forged_request.topic

    # Dispatch runs the app/uninstalled handler with orders/create data
    ShopifyAPI::Webhooks::Registry.process(forged_request)
    assert_equal "app/uninstalled", @handled.topic
  end
end
```
This demonstrates that `HmacValidator.validate` is `true` and `Registry.process` dispatches to a handler for a topic that differs from what Shopify actually signed the body for, confirming the broken binding.
