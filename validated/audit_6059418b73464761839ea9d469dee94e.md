### Title
LP collateral price can be inflated by donating reserves to the underlying Aquarius pool (price is derived from live `get_reserves` balances) - (File: contracts/price-aggregator/src/providers/aquarius.rs)

### Summary
The price-aggregator derives the fair value of Aquarius LP shares from the pool's *spot* reserves read via `get_reserves` at the moment the price is consumed. A direct token transfer to the pool address — which requires no pool interaction and no privileged role — inflates one reserve, and the `2 * sqrt(value_a * value_b)` formula inflates the reported LP price by `sqrt(1 + donation / reserve)`. An attacker holding LP collateral can therefore over-borrow against it within a single transaction window.

### Finding Description
`contracts/price-aggregator/src/providers/aquarius.rs:90-114` reads `aquarius_pool_reserves_call` (`common/src/oracle/providers/aquarius.rs:45-57`, a live `get_reserves` cross-contract call) and feeds the reserves into `fair_lp_price_wad` (`common/src/oracle/lp.rs:57-87`), which computes `total_value = 2 * sqrt(value_a * value_b)` where each leg value is `reserve * price_wad / 10^decimals`. The same path is used for stable pools via `fair_stable_lp_price_wad`, whose invariant-based math also grows when a donation enlarges `D`.

On Soroban/Stellar, `token.transfer(from, pool, amount)` only requires `from.require_auth()`, so any unprivileged address can inflate `reserve_a` or `reserve_b` at will — there is no sync/skew mechanism that would reject the donated balance. This is the exact analog of the USSD `getSupplyProportion` `balanceOf(pool)` flaw: the spot balance of the referenced pool is trusted for a value-sensitive decision.

The resulting LP price feeds `Context`-cached strict prices, so the inflated collateral value is usable by `supply` (LP as collateral), `borrow`, `update_account_threshold`, `multiply`/`flash_position`, etc., all reachable by a single unprivileged EOA within the manipulation window.

Cost analysis: donation `D` of leg-A raises the LP price by `sqrt(1 + D·p_a / V_a)`. The donated tokens are *not* lost — they remain in the pool and are implicitly distributed to all LP shareholders, including the attacker. If the attacker owns a fraction `f` of pool shares, the effective cost is only `D·(1−f)`. A dominant LP holder (or the sole LP of a thin pool, which is plausible for small Aquarius pools) can therefore inflate the LP price nearly for free, bounded only by the configured `min_sanity_price_wad`/`max_sanity_price_wad` band. Notably, bands in `configs/mainnet/markets.json` are wide — e.g. `AQUAUSDC_LP` allows `min=5.36e15`, `max=5.36e16` (a 10x span), so a multi-fold inflation still passes validation, and `tolerance`/`RequireDisjoint` checks do not detect single-source reserve manipulation.

### Impact Explanation
Theft of user funds / protocol insolvency: the attacker supplies (or already holds) LP shares as collateral, inflates their per-share price via a donation, borrows up to `LTV × inflated_value` of other users' supplied assets, then abandons the position. The collateral's real value is far below the borrowed amount, leaving bad debt for the protocol that `clean_bad_debt` writes down against suppliers' supply index.

### Likelihood Explanation
Medium. The attack requires the attacker to hold meaningful LP-share collateral and, for the near-free variant, to be a large share of the target Aquarius pool; sanity bands cap the achievable inflation (but at up to ~10x in current configs). No privileged access, no oracle compromise, and no multi-block timing is needed — reserves, donation, and `borrow` all settle in the same ledger state or adjacent transactions. The donation cannot be clawed back, but since it accrues to all LPs, a dominant LP recovers most of it.

### Recommendation
Do not price LP collateral purely from spot reserves. Options:
- Validate reserves against a manipulation-resistant reference (e.g., TWAP reserves, or recompute implied leg ratio against the strict leg prices and reject if the implied spot price deviates beyond a tolerance, similar to the existing dual-leg `tolerance` mechanism).
- Add a `max_reserve_ratio`/imbalance check: reject the observation when `reserve_a·p_a` vs `reserve_b·p_b` deviate beyond what a normal trade path could produce.
- Tighten `min_sanity_price_wad`/`max_sanity_price_wad` bands for LP assets so that sqrt-scaled donation inflation is rejected.

### Proof of Concept
1. Attacker acquires/mints `S` Aquarius LP shares of pool `P` (e.g., `AQUAUSDC_LP`) — ideally being the dominant LP (share fraction `f` ≈ 1) — and supplies them as collateral via the controller's `supply`.
2. Attacker calls `token_a.transfer(attacker, P, D)` directly on the leg token SAC with a large `D` (e.g., `D ≈ 3·reserve_a`). This requires only `attacker.require_auth()`.
3. Next ledger, `borrow`/`update_indexes` triggers price resolution; `read()` in `providers/aquarius.rs` sees `reserve_a' = reserve_a + D`, and `fair_lp_price_wad` returns `2·sqrt((r_a+D)·p_a·r_b·p_b)/shares` ≈ `2×` the honest price — still within the 10x sanity band.
4. Attacker calls `borrow` for `LTV × 2 × honest_collateral_value` of another asset and withdraws; the position is deeply undercollateralized. The donated `D` largely returns to the attacker pro-rata as the dominant LP. `clean_bad_debt` later socializes the shortfall to suppliers.

Note: I verified the reserve-read and fair-price math, the donation reachability (SAC `transfer` auth model), and the wide configured sanity bands. I was not able to fully verify within the available iterations whether `get_reserves` on the real Aquarius pool returns raw `balanceOf` (the in-repo mock does) or internal accounting that would reject donations; if Aquarius `get_reserves` uses internally-tracked balances and no `sync` exists, the donation path would fail and this analog would not stand.
