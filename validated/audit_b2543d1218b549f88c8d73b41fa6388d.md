## Finding

### Title
Webhook shop identity spoofing due to `shop-domain` header not covered by HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the webhook HMAC signature over the raw request body only, but the `shop` (tenant) identity that is handed to the application's webhook handler is read from the `X-Shopify-Shop-Domain` HTTP header, which is never part of the signed bytes. An attacker who can obtain any validly-signed webhook payload (trivially, by triggering a real webhook on their own shop) can replay it with a forged `shop-domain` header pointing at a victim shop, and the gem's `Registry.process` will accept it as authentic.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is derived from the `shopify-shop-domain` / `x-shopify-shop-domain` header, completely independent of the signed content: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)`, which internally calls `to_signable_string` (i.e., only checks `@raw_body`), and then immediately trusts `request.shop` and forwards it unchecked to the app's handler as the tenant identifier: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` compute the signature purely from `verifiable_query.to_signable_string`, so any field not included in that string (here, the shop domain header) is never verified: [4](#0-3) 

This is the same identity-binding break described in the analogous report: the bytes actually verified (`raw_body`) do not equal the bytes/fields the application acts on (`shop-domain` header, used as the tenant key). The docs explicitly show apps using `data.shop` to key background jobs/storage per tenant: [5](#0-4) 

### Impact Explanation
Since HMAC covers only the body, an attacker who controls their own Shopify store can generate a webhook with a valid HMAC (Shopify signs it against the shared `client_secret`... but note: the signature only binds to body content, not the header). By replaying that same body+hmac pair while spoofing the `X-Shopify-Shop-Domain` header to a different (victim) shop, the gem accepts the request as fully authenticated ("Invalid webhook HMAC." check passes) and dispatches it to the handler with `shop: <victim-shop>`. Any host application that uses `WebhookMetadata#shop` as a tenant/session key (exactly as illustrated in this gem's own documentation) will process attacker-supplied data under the victim's tenant identity — a cross-tenant data injection/confusion condition reachable by any unprivileged internet user who can register or already owns a Shopify store capable of emitting webhooks.

### Likelihood Explanation
Any developer/merchant can install the same app on their own shop (or receive a public app's webhooks) and thus obtain a validly HMAC-signed webhook body from Shopify without needing any of this app's secrets. Replaying that body with a modified `shop-domain` header requires no cryptographic material at all — it only requires network-level ability to POST to the app's public webhook endpoint with fabricated headers. This makes the likelihood high given webhook endpoints are unauthenticated-by-header-value internet-facing routes.

### Recommendation
Include the shop domain (and topic/webhook-id, if used for authorization decisions) in the HMAC-signed material, or otherwise cryptographically bind the header to the payload/signature before trusting `request.shop` for tenant attribution. At minimum, `Registry.process` should cross-check `request.shop` against an independently-verified source (e.g., a per-shop webhook secret or a stored mapping of webhook subscription IDs to shop) rather than trusting an unauthenticated header value verbatim.

### Proof of Concept
1. Attacker installs/owns "attacker-shop.myshopify.com" and receives a legitimate webhook (e.g. `orders/create`) from Shopify with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(client_secret, B)`).
2. Attacker replays the exact same `B` and `H` to the victim app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, B)` and compares to `H` — it matches, since the shop header was never part of the signed string (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
4. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's own order data>, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host app to process attacker-controlled data as belonging to the victim's tenant.
