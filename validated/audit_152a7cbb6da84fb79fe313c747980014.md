### Title
Orb-Relay client replays last session state to any sender claiming `RequestState`, bypassing source-identity validation - ([File: orb-relay-client/src/client.rs])

### Summary
The `PollerAgent::main_loop` function in the orb-relay client used for self-serve signup sessions replays the last sent session message (`self.last_message`) whenever it receives a payload matching `self_serve::app::v1::RequestState`, but it does this **before** performing the source-identity check that is applied to every other incoming message type. This mirrors the reported DCA bug class: a state-changing/state-disclosing action is triggered by an attacker-influenced field (the message type) without validating that the request actually originates from the paired counterparty (`dst_id`), similar to `stopDca` trusting a caller-supplied `_taskId` without binding it to the DCA owner.

### Finding Description
In `orb-relay-client/src/client.rs`, `PollerAgent::main_loop` processes each incoming `RelayPayload` from the relay stream: [1](#0-0) 

```rust
message = response_stream.next() => {
    match message {
        Some(Ok(RelayConnectResponse {
            msg: Some(relay_connect_response::Msg::Payload(RelayPayload {
                src: Some(src), dst, seq, payload: Some(payload),
            })),
        })) => {
            if self_serve::app::v1::RequestState::matches(&payload).is_some() {
                sender_tx.send(self.last_message.clone()).await
                    .wrap_err("Failed to send outgoing message")?;
            } else if src.id != self.config.dst_id {
                tracing::error!("Skipping received message from unexpected source: ...");
            } else {
                self.handle_message(...).await?;
            }
        }
        ...
```

For every message type *except* `RequestState`, the client explicitly checks `src.id != self.config.dst_id` — i.e., it verifies the message actually originates from the paired entity (Orb ↔ App bound to a specific `session_id`/`orb_id` pair set up in `Client::new_as_orb` / `Client::new_as_app`, see [2](#0-1) ). The `RequestState` branch skips this validation entirely and unconditionally replays `self.last_message` — the most recently sent `RelayPayload`, which can contain session-sensitive content such as `AnnounceOrbId`, `SignupEnded`, `CaptureStarted`/`CaptureTriggerTimeout`, or other self-serve signup protocol messages (see message types wired via `IntoPayload` in [3](#0-2) ).

Just as `stopDca` trusted the caller-supplied `_taskId` without checking it belonged to the DCA being stopped, this code trusts the caller-supplied payload *type* (`RequestState`) as sufficient authorization to receive privileged session state, without validating the caller's identity (`src.id`) against the bound counterparty (`dst_id`) for that session.

### Impact Explanation
If the relay transport or server ever delivers (or can be induced to deliver, e.g., through misrouting, multiplexing bugs, or a malicious/compromised third entity sharing the transport) a payload whose `src.id` differs from the expected counterparty but whose body matches `RequestState`, the Orb (or App) client will disclose its last transmitted signup-session payload to that unverified sender — a cross-signup/cross-session state disclosure. This is a "confused deputy" style authorization gap: the identity check that protects every other message type is bypassed specifically for the message that triggers a state replay, which is the exact same "missing binding check on a state-mutating/state-revealing action" pattern flagged in the DCA report.

### Likelihood Explanation
Likelihood depends on whether the relay server can ever deliver a payload for one session with an `src` that does not match the intended counterparty (e.g., due to server-side routing errors, replay, or a rogue participant sharing infra). The client-side check on every other branch indicates the developers anticipated this scenario and defended against it — but forgot to apply the same defense to the `RequestState` fast-path, making this an inconsistency/oversight rather than a defense-in-depth no-op.

### Recommendation
- **Short term:** Move the `src.id != self.config.dst_id` check above the `RequestState` special case (or fold it into the same condition) so that a `RequestState` request is honored only when it comes from the verified counterparty for the session.
- **Long term:** Document the trust boundary for relay messages (which fields are attacker-controlled vs. server-verified) and add unit/integration tests asserting that `RequestState` replay is rejected when `src.id` does not match the expected peer, mirroring the tests recommended for the original DCA finding (state-transition tests, adversarial-source tests).

### Proof of Concept
1. Establish a paired Orb/App relay session (`Client::new_as_orb` / `Client::new_as_app`) as in `orb-relay-client/src/bin/manual-test.rs`.
2. Have the Orb client send a sensitive message (e.g., `AnnounceOrbId` or `SignupEnded`), which is cached in `self.last_message`.
3. Deliver a `RelayConnectResponse` payload matching `self_serve::app::v1::RequestState` with `src.id` set to a value other than `self.config.dst_id` (simulating an unpaired/unauthorized entity reaching the stream).
4. Observe that `main_loop`'s first branch matches on message type alone and calls `sender_tx.send(self.last_message.clone())` without ever checking `src.id`, replaying the cached session payload to the unauthorized sender — unlike any other message type, which would be dropped by the `else if src.id != self.config.dst_id` check.
