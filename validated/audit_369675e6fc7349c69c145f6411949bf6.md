Based on my analysis, this vulnerability is real and confirmed by the code.

### Title
XRPL token-address block bypass via X-address/classic-address encoding mismatch in `compareAddresses` - (File: packages/intents-sdk/src/lib/compareAddresses.ts)

### Summary
`validateAddress` for XRPL accepts both classic (`r...`) addresses and X-addresses as valid destination formats, but `compareAddresses` for XRPL only performs raw string equality (`a === b`) with no canonicalization between these two encodings. An attacker can supply the token's origin address encoded as an X-address (or with different casing tolerated by the XRPL codec) while the stored `tokenInfo.origin_chain_address` is a classic address, causing `compareAddresses` to return `false` even though both strings resolve to the same underlying XRPL account.

### Finding Description
The broken equality: for XRPL, `compareAddresses(tokenAddress, destinationAddress, 'xrpl:0')` is expected to be `true` whenever `tokenAddress` and `destinationAddress` denote the same XRPL account, but the implementation only checks `a === b` [1](#0-0) .

`validateAddress` for XRPL accepts either a classic address or an X-address as valid formats via `xrp_isValidClassicAddress(address) || xrp_isValidXAddress(address)` [2](#0-1) , both of which the `ripple-address-codec` library considers valid, distinct textual encodings that can represent the very same underlying account (classic address + optional tag ↔ X-address).

In `PoaBridge.validateWithdrawal`, the code first validates the destination address format with `validateAddress`, which passes for either encoding [3](#0-2) . It then compares the token's `origin_chain_address` (stored in whatever encoding the bridge backend uses, typically the classic `r...` form) against `args.destinationAddress` using `compareAddresses` [4](#0-3) . If the attacker supplies the X-address form of the exact same account that the token contract's classic address represents, `compareAddresses` performs `a === b` string comparison, which is `false` for two different encodings of the same account, so `DestinationAddressMatchesTokenAddressError` is never thrown.

Exploit flow: attacker calls `processWithdrawal`/`createWithdrawalIntents` with `assetId` for an XRPL-issued POA token and `destinationAddress` set to the X-address encoding of `tokenInfo.origin_chain_address`. `validateAddress` passes (X-address is a valid XRPL address format). `compareAddresses` returns `false` because the strings differ even though they denote the same account. `validateWithdrawal` proceeds, and the withdrawal intent is created sending tokens to the token issuer/contract's own account, where they become unrecoverable (analogous to sending tokens to the token contract itself).

Existing guards fail because: `validateAddress` is format-agnostic per encoding and doesn't reject the alternate encoding; `compareAddresses` for XRPL has no canonical-form normalization step (unlike EVM's `getAddress`, TON's `tryParseTonAddress`, or Tron's `decodeTronAddress`/base58+hex normalization) despite XRPL genuinely having multiple valid encodings for the same account.

### Impact Explanation
If exploited, a withdrawal intent is signed and executed (debited from the user's/solver's balance) with tokens routed to the token's own issuing/contract address on XRPL instead of a legitimate recipient — funds delivered to the wrong destination with no path to recovery, since the token contract address is not a normal wallet that can return funds. This matches the "Critical - funds delivered to a wrong address/chain/contract with no recovery" impact category. It is repeatable for any XRPL-based POA-bridge token whose `origin_chain_address` is non-native, each time the attacker chooses to encode the destination as an X-address (or another codec-legal alternate form) of the token address instead of the canonical classic form recorded by the bridge.

### Likelihood Explanation
Preconditions: the target asset must be an XRPL POA-bridge token with a non-native `origin_chain_address` (i.e., an issued token with a known issuer/token account on XRPL). The attacker only needs to encode that known, public token address as an X-address (a purely client-side, deterministic transformation available via the public `ripple-address-codec` library) and pass it as `destinationAddress` to `createWithdrawalIntents`/`processWithdrawal`. No privileged access, relayer collusion, or race condition is required — this is a straightforward encoding mismatch exploitable by any unprivileged caller who knows (or looks up) the token's issuer address, which is public information exposed via the same `getSupportedTokens` API used by `validateWithdrawal` itself.

### Recommendation
Canonicalize XRPL addresses in `compareAddresses` before comparison, analogous to the Tron/TON logic: decode both `a` and `b` via `ripple-address-codec` (e.g., using `xAddressToClassicAddress`/`classicAddressToXAddress` or decoding to the underlying account ID + tag) into a canonical (accountId, tag) tuple, and compare those tuples instead of raw strings.

### Proof of Concept
```ts
// packages/intents-sdk/src/lib/compareAddresses.spec.ts (illustrative addition)
import { classicAddressToXAddress } from "ripple-address-codec";
import { compareAddresses } from "./compareAddresses";
import { validateAddress } from "./validateAddress";

test("XRPL classic address and its X-address encoding must compare equal", () => {
  const classicTokenAddress = "rExampleTokenIssuerAddress...";
  const xAddressEncoding = classicAddressToXAddress(classicTokenAddress, false, false);

  // Both must be accepted as valid destination addresses
  expect(validateAddress(classicTokenAddress, "xrpl:0")).toBe(true);
  expect(validateAddress(xAddressEncoding, "xrpl:0")).toBe(true);

  // Since they denote the same account, compareAddresses must return true.
  // Currently this FAILS (returns false) because compareAddresses does raw a === b.
  expect(compareAddresses(classicTokenAddress, xAddressEncoding, "xrpl:0")).toBe(true);
});
```
End-to-end reproduction: mock `poaBridge.httpClient.getSupportedTokens` to return `origin_chain_address` as the classic address for an XRPL token, then call `PoaBridge.validateWithdrawal` with `destinationAddress` set to the X-address encoding of that same address; assert that no `DestinationAddressMatchesTokenAddressError` is thrown (bug), whereas it should be thrown.
