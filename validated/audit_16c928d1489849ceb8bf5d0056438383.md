### Title
Webhook `shop-domain` Header Not Covered by HMAC Allows Cross-Tenant Shop Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the shop identity (`shop-domain` header) and topic used by the application's webhook handler are read directly from unauthenticated HTTP headers. This breaks the binding `shop asserted by header == shop that produced the HMAC-signed payload`, letting an attacker who legitimately receives one signed webhook (e.g., from their own store) replay the exact body with a forged `shop-domain` header and have it accepted as originating from a different (victim) shop.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by recomputing an HMAC over `to_signable_string` and comparing it to the `hmac` value with `OpenSSL.secure_compare`: [1](#0-0) 

For webhook requests, `Request#to_signable_string` returns only `@raw_body`, and `Request#hmac` is parsed from the `hmac-sha256` header. Critically, `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers and are **not** part of the signed string: [2](#0-1) 

`Registry.process` validates only the HMAC of the request (i.e., the body) and then dispatches to the handler using the unauthenticated `request.shop` field: [3](#0-2) 

Because the HMAC secret (`Context.api_secret_key`) is shared across all shops connected to the app, the HMAC over a given body is identical no matter which shop the payload nominally belongs to. An attacker who controls a legitimate installation of the app on their own shop will receive genuinely-signed webhook deliveries containing a valid `hmac-sha256` header for the raw body. Because `shop-domain` is excluded from the signable string, the attacker can capture that request and re-send it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain. `HmacValidator.validate` still succeeds (only the body is checked), and `Registry.process` passes `shop: request.shop` (now the victim's domain) into `WebhookMetadata`, which is handed to the app's `handler.handle`. The equality the gem should be enforcing — "the shop identity acted upon equals the shop that produced/authorized the signed bytes" — is never checked.

### Impact Explanation
This is a cross-tenant identity-binding break: an unprivileged attacker (any merchant/developer able to install the app on their own store, i.e. an "unprivileged internet user" relative to other merchants' data) can cause the host application to process attacker-controlled webhook data while believing it originates from a different, victim shop. Depending on the webhook handler's logic (e.g., updating order/customer records, triggering `shop/redact` type deletions, or writing merchant-scoped data), this can result in cross-tenant data corruption or disclosure — satisfying the "cross-tenant access" Critical impact category, since the gem itself provides no mechanism to bind the header-derived shop to the cryptographically verified payload.

### Likelihood Explanation
Likelihood is high for any app that trusts `request.shop` from `ShopifyAPI::Webhooks::Registry`/`Request` without independently verifying that the shop is one the app has an active session for: the attacker only needs their own legitimate app installation to obtain a validly-signed webhook body, and then simply replays it with a modified header — no access to `api_secret_key` or any victim credential is required.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the signed material, or otherwise cryptographically bind the header value to the payload before trusting it, e.g. by having `Request#to_signable_string` incorporate `shop-domain` (mirroring how `AuthQuery#to_signable_string` binds `shop` into its HMAC input at `lib/shopify_api/auth/oauth/auth_query.rb:34-43`), or by requiring callers to cross-check `request.shop` against a known/expected shop for the session prior to invoking the handler in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and configures a webhook subscription, receiving genuine Shopify-signed webhook POSTs.
2. Attacker captures one such POST: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(api_secret_key, B)`), and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker resends the identical body `B` and identical `X-Shopify-Hmac-Sha256: H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. The app calls `ShopifyAPI::Webhooks::Registry.process(request)`, which calls `Utils::HmacValidator.validate(request)`: [4](#0-3) 
   Since only `@raw_body` is hashed (`to_signable_string`), validation succeeds even though `shop-domain` was changed.
5. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with `shop == "victim-shop.myshopify.com"` and passed to `handler.handle`, causing the app to act on victim-shop data/scope despite the payload actually originating from the attacker's shop.
