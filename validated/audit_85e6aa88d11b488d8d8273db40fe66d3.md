### Title
UTXO withdrawal status reports provisional `pending_sign_id` as final txHash, allowing status/txHash divergence from the real BTC transaction - (File: packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts)

### Summary
`describeWithdrawal` returns `status: "completed"` with `txHash` set to `transfer.utxo_meta?.pending_sign_id` when running in a browser context for UTXO-destination withdrawals, even though the code comment explicitly states this identifier is not the finalized transaction hash and "may change if the BTC transfer fails to be submitted." [1](#0-0)  This creates a real divergence between what is reported to the caller as the completed withdrawal's txHash and the eventual real on-chain BTC transaction hash.

### Finding Description
The broken equality: `reported txHash (transfer.utxo_meta.pending_sign_id)` == `eventual finalized on-chain hash (transfer.finalised.transaction_hash)`.

In `describeWithdrawal`, for UTXO destination chains, the branch selects `pending_sign_id` when `typeof window !== "undefined"` (browser/FE context) and `transfer.finalised?.transaction_hash` when not (BE/Node context): [2](#0-1) 

The code's own comment acknowledges that `pending_sign_id` "is not the finalised tx hash" and "the hash may change if the BTC transfer fails to be submitted," yet the method still returns `status: "completed"` as soon as `pending_sign_id` exists — there is no re-check against `finalised.transaction_hash` before marking the withdrawal complete in the browser code path. `watchWithdrawal`/callers rely on `describeWithdrawal` returning `completed` to stop polling and consider the withdrawal done with that reported hash.

Existing guards do not prevent this: `validateAddress`, `compareAddresses`, `FeeExceedsAmountError`, and the intents contract's signature/nonce checks operate on intent construction and fee/address correctness — none of them validate that a reported `txHash` for a completed withdrawal is the immutable, final on-chain identifier. This is purely a reporting-layer defect, and the environment branching (`typeof window !== "undefined"`) means the exact same withdrawal can report two different "completed" hashes depending on whether the SDK runs in a browser vs. Node context.

### Impact Explanation
An integrator (or its FE) that treats `describeWithdrawal`'s `completed` status as final and uses the returned `txHash` as an idempotency key, a receipt reference, or a trigger to credit a user, will store/act on a value (`pending_sign_id`) that is not guaranteed to equal the real BTC transaction hash. If the underlying BTC broadcast fails and is resubmitted with a new txid, the previously reported hash never appears on-chain, and any reconciliation, refund, or double-payout logic keyed on that hash breaks — this matches the "status or hash misreport making an integrator credit or refund twice" High-severity category. This is repeatable for every UTXO-destination Omni Bridge withdrawal run in a browser context, not a one-off edge case, since it is deterministic on the `typeof window` check and any BTC resubmission event.

### Likelihood Explanation
Preconditions are narrow but plausible: the SDK is running in a browser (`typeof window !== "undefined"`) and the withdrawal targets a UTXO chain (BTC), and the BTC broadcast fails and requires resubmission — a known, acknowledged occurrence per the inline comment. No attacker action is required beyond initiating a normal UTXO withdrawal (which any unprivileged user with funds can do); the divergence occurs due to normal bridge/relayer retry behavior, not attacker manipulation. This is an inherent, code-acknowledged design gap rather than a hypothetical exploit, but it depends on external BTC broadcast failure/resubmission actually happening, so it is not guaranteed on every withdrawal.

### Recommendation
For the browser code path, either avoid reporting `status: "completed"` until `transfer.finalised?.transaction_hash` is available (mirror the BE behavior), or return a distinct status (e.g., `"pending-fast-hash"` or include an explicit `isFinal: false` flag alongside `pending_sign_id`) so callers cannot conflate a provisional signing identifier with a final, immutable transaction hash. If a fast UX signal is required, decouple it from the `completed` status used for crediting/reconciliation logic.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const transfer = (
			await this.omniBridgeAPI.getTransfer({
				transactionHash: args.tx.hash,
			})
		)[args.index];

		if (transfer == null || transfer.recipient == null) {
			return { status: "pending" };
		}

		const destinationChain = getChain(transfer.recipient as OmniAddress);
		let txHash = null;
		if (
			isEvmChain(destinationChain) ||
			destinationChain === ChainKind.Sol ||
			destinationChain === ChainKind.Fogo ||
			destinationChain === ChainKind.Strk ||
			destinationChain === ChainKind.Aptos
		) {
			txHash = transfer.finalised?.transaction_hash;
		} else if (isUtxoChain(destinationChain)) {
			// pending_sign_id is not the finalised tx hash. In rare cases, the hash may
			// change if the BTC transfer fails to be submitted. We return fast hash for FE and
			// wait for final one (transfer.finalised?.transaction_hash) for BE.
			txHash =
				typeof window !== "undefined"
					? transfer.utxo_meta?.pending_sign_id
					: transfer.finalised?.transaction_hash;
		} else {
			return { status: "completed", txHash: null };
		}

		if (!txHash) {
			return { status: "pending" };
		}

		return { status: "completed", txHash };
	}
