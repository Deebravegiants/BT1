### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `HmacValidator.validate` computes/verifies the HMAC exclusively over that body. The `shop` (and `topic`, `webhook_id`, `api_version`) values are read straight from HTTP headers and are never included in the signed material, yet `Registry.process` trusts `request.shop` as the tenant identity handed to the application's webhook handler.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which returns only `@raw_body`. The `shop`, `topic`, `api_version`, and `webhook_id` accessors are populated purely from headers with no cryptographic binding: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` verify the HMAC only against `verifiable_query.to_signable_string` (i.e., the body), never against the headers: [3](#0-2) 

`Registry.process` gates on this body-only HMAC check and then unconditionally forwards `request.shop` (a header-derived, unauthenticated value) to the app's handler as the tenant identity: [4](#0-3) 

Because the app's webhook secret (`Context.api_secret_key`) is shared across every shop that has the app installed, a valid `(body, hmac)` pair obtained from any legitimately delivered webhook (e.g., from the attacker's own installed store) remains cryptographically valid when replayed with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to point at a different shop. The equality the gem should enforce — `shop asserted in header == shop the HMAC covers` — is never checked; the HMAC only proves `body == HMAC(secret, body)`. This lets an unprivileged holder of one valid webhook delivery relabel it as belonging to an arbitrary other shop.

### Impact Explanation
This breaks the tenant/identity boundary the webhook pipeline is supposed to enforce: the handler is invoked with `WebhookMetadata#shop` set to an attacker-chosen value while the HMAC validation reports success. Any host application that uses `request.shop`/`WebhookMetadata#shop` from this gem as an authenticated tenant key (e.g., to look up a session, mark a shop as uninstalled/redacted, or write cross-tenant data) can be tricked into acting on behalf of, or against, a shop the attacker does not control — a cross-tenant access condition.

### Likelihood Explanation
The attacker only needs to have obtained one legitimate webhook payload+HMAC pair for any shop using the app (trivial to do by installing the app on their own store) and can freely replay it with an arbitrary `shop-domain` header value; no access token, `client_secret`, or privileged account is required.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the signed material, or otherwise independently verify that the `shop-domain` header corresponds to a shop for which this exact `(body, hmac)` pair was actually issued (e.g., require the host app to look up the shop's per-install secret or reject unless the shop matches an expected value passed in by the caller) before trusting `request.shop`/`WebhookMetadata#shop` downstream.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and receives a real webhook delivery, capturing raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(secret, B)`).
2. Attacker sends `POST /webhooks` to the victim app with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` and compares to `H` — it matches, since neither `shop` header nor topic is part of `to_signable_string` [1](#0-0) .
4. `Registry.process` proceeds and invokes the handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)` [5](#0-4) , causing the host application to process attacker-controlled data attributed to `victim-shop.myshopify.com`.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
