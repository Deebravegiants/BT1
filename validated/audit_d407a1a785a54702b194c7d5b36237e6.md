### Title
Receipt size validated before `output_data_receivers` are attached, allowing over-limit receipts that get permanently stuck in cross-shard forwarding - ([File: runtime/runtime/src/lib.rs], [File: runtime/runtime/src/verifier.rs], [File: runtime/runtime/src/congestion_control.rs])

### Summary
This mirrors the Biconomy `LiquidityPool` bug class: a value (transfer amount) is validated once at time A against a limit, but a second, larger value derived from the same object (amount + reward) is what actually matters downstream, and no equivalent check/enforcement exists at time B — so an object that passed the first check can violate the real limit later, with no path to recover (funds/receipts get stuck). In nearcore, the analogous value is a **receipt's serialized size**: it is validated once via `validate_receipt(..., ValidateReceiptMode::NewReceipt)` right after the receipt is created, but `output_data_receivers` are appended to that receipt's `ReceiptIndex` *after* this validation, growing its real size past `max_receipt_size` without any re-validation.

### Finding Description
`validate_action_receipt` / `validate_receipt` (`runtime/runtime/src/verifier.rs:540-586`) checks a newly created receipt in `ValidateReceiptMode::NewReceipt` mode immediately when it is produced during action execution. Per the runtime execution flow, each new receipt created by an action is validated at creation time [1](#0-0) , but output data receivers are only attached to the receipt afterward, once all actions for the parent receipt have finished executing [2](#0-1) . This means a contract can craft a receipt that is exactly at `max_receipt_size` at validation time (check #1, "amount"), and the runtime's subsequent attachment of `output_data_receivers` pushes the *actual* persisted/forwarded size over the limit (check #2, "amount + reward") — but there is no second `validate_receipt` call to catch this.

The `ValidateReceiptMode` enum itself documents this exact defect and references it as a known, unfixed bug: [3](#0-2) 

The consequence downstream is handled with a workaround rather than a fix, in the receipt-forwarding admission logic (`try_forward`), which explicitly clamps any oversized receipt's `size` down to `max_receipt_size` "to avoid receipts getting stuck": [4](#0-3) 

This is structurally identical to the Biconomy finding: one check (`NewReceipt` size validation) uses a smaller/incomplete value, while the real consequential value (final receipt size including `output_data_receivers`) is what the bandwidth/congestion admission logic (`forward_limit.size >= size`, `runtime/runtime/src/congestion_control.rs:451`) actually needs to respect. Without the clamp workaround, an oversized receipt would never satisfy `forward_limit.size >= size` against any realistic per-shard bandwidth grant, and would be buffered forever (a stuck/lost-in-limbo receipt, analogous to a user's tokens being unsendable in the original report). This is already tracked as issue near/nearcore#12606 and demonstrated by the codebase's own regression test.

### Impact Explanation
An oversized receipt (created via crafting `output_data_receivers` growth after a receipt already sits at `max_receipt_size`) can bypass the size check that is supposed to bound cross-shard receipt/state-witness/storage-proof sizes. The project's own workaround (clamping `size` to `max_receipt_size` in `try_forward`) prevents receipts from getting permanently stuck, but it does so by under-reporting the receipt's true size to the bandwidth/congestion accounting (`own_congestion_info`, `outgoing_metadatas`, per-shard `OutgoingLimit.size`), i.e., real bandwidth/storage consumption exceeds what congestion control believes it is admitting. This can inflate real state-witness/chunk sizes beyond configured limits, undermining the congestion-control invariant that outgoing size stays within `outgoing_receipts_usual_size_limit`/`outgoing_receipts_big_size_limit`, and — absent the clamp — would otherwise cause an unrecoverable stuck receipt (denial of the corresponding action/promise callback for the affected accounts), which is the direct analog of "user loses funds because the transaction can never be sent."

### Likelihood Explanation
Reachable purely from an ordinary, unprivileged transaction: any account can deploy/call a contract that creates a receipt near `max_receipt_size` and attaches enough `output_data_receivers` (via promise chaining/`promise_return`) to push it over the limit — exactly what the existing regression test `test_max_receipt_size_promise_return` exercises and comments as a known, currently-unfixed bug (issue #12606) [5](#0-4) . No validator/network privilege is required.

### Recommendation
Re-validate (or at minimum re-measure and enforce `max_receipt_size`) after `output_data_receivers` are attached to a receipt, rather than only validating at creation time before that mutation occurs. Alternatively, compute the worst-case size (including maximum possible `output_data_receivers`) before creation-time validation so the `NewReceipt` check and the eventual forwarded/persisted size are checked against the same, final value — matching the Biconomy remediation of "both checks should be made over the same amount."

### Proof of Concept
The existing test `test_max_receipt_size_promise_return` in-tree already reproduces the root cause end-to-end: it builds a receipt whose base size equals `max_receipt_size`, then triggers a promise chain (`A -then-> B`, with `A` creating `C` and doing `promise_return`) so that `output_data_receivers` are appended to `C`'s receipt after creation-time validation, pushing it above `max_receipt_size`; the test then asserts (via `assert_oversized_receipt_occurred`) that an oversized receipt does occur on-chain instead of being rejected [6](#0-5) , and the corresponding `try_forward` workaround is what currently prevents this from turning into a permanently stuck receipt [7](#0-6) .

        receipt: Receipt,

        mut size: u64,
        shard: ShardId,

        outgoing_receipts: &mut Vec<Receipt>,
        apply_state: &ApplyState,

    ) -> Result<ReceiptForwarding, RuntimeError> {
        // There is a bug which allows to create receipts that are above the size limit. Receipts

        // that all receipts are at most `max_receipt_size` to avoid receipts getting stuck.
        // See https://github.com/near/nearcore/issues/12606
        let max_receipt_size = apply_state.config.wasm_config.limit_config.max_receipt_size;
        if size > max_receipt_size {
            tracing::debug!(
                target: "runtime",
                receipt_id=?receipt.receipt_id(),
                size,
                max_receipt_size,
                "try_forward observed a receipt with size exceeding the size limit",
            );
            size = max_receipt_size;
        }

fn test_max_receipt_size_promise_return() {

    // When promise A is executed, it creates a third promise - `C` and does a `promise_return`.
    // The DAG changes to: [C ->then-> B]

        predecessor_id: account.clone(),

        receipt_id: CryptoHash::default(),

            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();
