### Title
Registry.process trusts the `x-shopify-shop-domain` header (excluded from HMAC signing) to select the tenant for handler dispatch, enabling cross-tenant impersonation via header substitution - (File: lib/shopify_api/webhooks/registry.rb)

### Summary
`Registry.process` validates only the HMAC over the raw request body via `Utils::HmacValidator.validate(request)`, then builds `WebhookMetadata` using `request.shop`, which is read straight from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header. Because `Request#to_signable_string` returns only `@raw_body`, an attacker holding one validly signed webhook from their own development shop can replay that exact body/HMAC pair with an arbitrary forged shop-domain header, causing any handler keyed on `WebhookMetadata#shop` to execute privileged, shop-scoped logic attributed to a victim shop chosen by the attacker.

### Finding Description
The binding the app implicitly relies on is:
`request.shop` (the tenant identity acted upon by `handler.handle`) `==` `the shop whose secret produced request.hmac`.

Tracing the code:
- `Request#initialize` normalizes headers and requires `topic`, `hmac-sha256`, and `shop-domain` headers to be present, but performs no cryptographic binding between them [1](#0-0) .
- `Request#shop` simply returns the raw `shop-domain` header value with no validation against the signature [2](#0-1) .
- `Request#to_signable_string` returns only `@raw_body` - the shop-domain header is never part of the bytes that get HMAC'd [3](#0-2) .
- `HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` (i.e., body only) and compares it to the received signature using `OpenSSL.secure_compare` [4](#0-3) .
- `Registry.process` gates only on that body-only HMAC check, then immediately dispatches to the registered handler for `request.topic`, constructing `WebhookMetadata` with `shop: request.shop` taken directly from the unauthenticated header [5](#0-4) .

Attacker flow: the attacker installs the app on their own development shop, receives one legitimately signed webhook (e.g., `orders/create`) with valid body+HMAC for their own shop. They resend the identical raw body and HMAC header to the app's webhook endpoint, but substitute `x-shopify-shop-domain` with `victim-shop.myshopify.com`. `HmacValidator.validate` still returns `true` because the check never inspects the shop header. `Registry.process` then invokes the registered handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the bytes were signed only for the attacker's own shop. If any handler performs shop-scoped privileged writes keyed off `data.shop` (billing updates, refund confirmations, order sync, etc.), the attacker can trigger that logic against any guessed/enumerated victim shop domain, repeatable at will and in bulk.

No existing guard prevents this: `HmacValidator.validate` is body-only by design (`to_signable_string`), there is no separate shop-domain signature or lookup against a known/installed shop list, and Sorbet typing only enforces that `shop` is a `String`, not that it matches the signer.

### Impact Explanation
This is a cross-tenant impersonation primitive: it lets an unprivileged attacker cause the app's webhook handler(s) to execute shop-scoped side effects while believing they originated from an arbitrary victim shop, using only their own single validly-signed webhook as raw material. Depending on what handlers exist in the host app (e.g., data sync, billing operations, cache invalidation, order fulfillment triggers), this can result in cross-tenant data corruption or unauthorized actions attributed to victim shops, matching the "cross-tenant access" Critical category. The blast radius scales with the number of shop domains the attacker chooses to target, since domains are guessable/enumerable `myshopify.com` subdomains and no rate limiting or shop-existence check gates the header value in the gem.

### Likelihood Explanation
Preconditions are minimal and attacker-achievable: the attacker only needs to install the app on their own free development shop and capture one webhook delivery to obtain a valid body/HMAC pair for any topic they care about; no `api_secret_key` or victim credentials are needed. The success of the exploit further depends on the host app registering a handler whose `handle` method performs privileged actions keyed on `WebhookMetadata#shop`, which is a common and encouraged pattern per the gem's own documentation. Given no additional protections in `Registry.process` or `Request`, this is fully repeatable and low-cost per forged shop.

### Recommendation
Bind the shop-domain header into the signed material, or independently verify that the shop domain in the header corresponds to a shop that installed the app and matches the signing key used, before trusting `request.shop`. At minimum, `Registry.process` (or `Request`) should cross-check the resolved shop against an authoritative session/install record rather than trusting the raw header value for dispatch. Document clearly in `WebhookHandler`/`WebhookMetadata` that `shop` must not be treated as authenticated unless additionally verified by the host app.

### Proof of Concept
Add a test to `test/webhooks/registry_test.rb` (or a new file) that:
1. Registers a handler for topic `orders/create` that records `data.shop`.
2. Builds one `Request` with `raw_body = "{}"`, a correctly computed HMAC using `ShopifyAPI::Context.api_secret_key`, and `x-shopify-shop-domain = "attacker-shop.myshopify.com"`.
3. Calls `ShopifyAPI::Webhooks::Registry.process(request)` and asserts `Utils::HmacValidator.validate(request) == true` and the handler was invoked with `data.shop == "attacker-shop.myshopify.com"`.
4. Builds a second `Request` reusing the identical `raw_body` and HMAC header from step 2, but with `x-shopify-shop-domain` replaced by `"victim-shop.myshopify.com"` (and other victim domains in a loop).
5. Calls `Registry.process` again and asserts `Utils::HmacValidator.validate(request) == true` still holds, and the handler is invoked once per forged domain with `data.shop` equal to each distinct victim domain - demonstrating that `request.shop` is fully attacker-controlled and independent of the signing shop, contradicting the intended binding `request.shop == signing shop`.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
