`AncestryChain::ancestry` walks `current_hash = header.parent_hash()` in a `while current_hash != base` loop with no visited-set / iteration bound, over a `BTreeMap` built directly from attacker-supplied `unknown_headers` (arbitrary `H: Header + codec::Decode` structs whose `parent_hash` field is fully attacker-chosen). Since a submitter can locally compute two header structs whose `parent_hash` fields point at each other's hash (no collision needed — just plug the computed hash of one into the other's field), the walk cycles between them forever without ever reaching `base`, hanging the runtime that processes the unsigned extrinsic — matching CVE-2021-2031's "attacker with network access causes a hang / complete DoS" bug class, but here fully unprivileged and reachable via a single submitted extrinsic.

### Title
Unbounded ancestry walk in GRANDPA consensus verification allows an attacker-crafted header cycle to hang the runtime - (File: modules/consensus/grandpa/primitives/src/justification.rs)

### Summary
`AncestryChain::ancestry`, used by `verify_grandpa_finality_proof` (and transitively by `GrandpaConsensusClient::verify_consensus`), walks a chain of headers from a target hash back to a base hash via `parent_hash` pointers with no cycle detection and no iteration bound. The header set (`unknown_headers`) it walks over is fully attacker-controlled content submitted inside a `ConsensusMessage` proof. An attacker can construct two (or more) headers whose `parent_hash` fields point at each other, forming a cycle that never reaches `base`, causing the walk to loop forever.

### Finding Description
`AncestryChain::new` builds a `BTreeMap<H::Hash, H>` straight from the submitter-provided `unknown_headers: Vec<H>` [8](#0-7) . `ancestry` then walks:
```
let mut route = vec![block];
let mut current_hash = block;
while current_hash != base {
    match self.ancestry.get(&current_hash) {
        Some(current_header) => {
            current_hash = *current_header.parent_hash();
            route.push(current_hash);
        },
        _ => return Err(finality_grandpa::Error::NotDescendent),
    };
}
``` [9](#0-8) 

Each header's hash is a `BlakeTwo256` digest of its full content (including its own `parent_hash` field), which the submitter fully controls before submission. This means the submitter can:
1. Pick arbitrary content for header B (parent_hash = X, arbitrary), compute `hash(B)`.
2. Build header A with `parent_hash = hash(B)`, compute `hash(A)`.
3. Go back and set B's `parent_hash = hash(A)`.

Both A and B then exist in `unknown_headers` under distinct keys `hash(A)` and `hash(B)`, each pointing at the other via `parent_hash`. If neither hash equals `base`, the `while` loop in `ancestry` alternates between A and B indefinitely — it has no "have we seen this hash before" check, only an equality check against the fixed `base`.

This is reached from the fully permissionless entry point: `pallet_ismp::Call::handle_unsigned` (`ensure_none` origin) [1](#0-0) , whose `ValidateUnsigned::validate_unsigned` implementation itself calls `Self::execute(messages.clone())` — meaning even *mempool validation* of the extrinsic triggers the hang, before the transaction is ever included in a block [2](#0-1) . `execute` → `handle_incoming_message` → `consensus::update_client` → `GrandpaConsensusClient::verify_consensus` → `verify_parachain_headers_with_grandpa_finality_proof` / `verify_grandpa_finality_proof`, both of which call `AncestryChain::ancestry` on the attacker's `unknown_headers` before the GRANDPA signature check that would otherwise gate the ancestry walk to only genuinely-finalized chains [10](#0-9) .

Note that a similar risk in the GRANDPA prover's own local ancestry check was already hardened elsewhere in this same module (`RelayHeaderNotInUnknownHeaders` guard, `Error::InvalidAncestry` for base/target checks), but those guard against a missing entry, not against an infinite cycle among *present* entries — the cycle case is not covered by those fixes.

### Impact Explanation
Any node (light client, collator, full node) that executes or even validates a `handle_unsigned` extrinsic carrying a malicious GRANDPA `ConsensusMessage` will hang in an infinite loop inside transaction-pool validation and/or block execution. Because this reaches `validate_unsigned`, a single gossiped extrinsic can hang every node's mempool validation, not just block execution on validators — a network-wide denial of service against the chain that hosts `pallet-ismp` with the GRANDPA consensus client configured (e.g., a parachain bridging to a relay chain or standalone GRANDPA chain). This blocks all Hyperbridge message delivery, consensus updates, and other extrinsics on the affected chain, i.e., "a route unable to deliver messages" and a broader liveness failure.

### Likelihood Explanation
High. No special privileges are required — any account (or even an unsigned submitter) can construct the two colliding headers offline (trivial hash computation, no cryptographic difficulty) and submit them as `unknown_headers` inside a `FinalityProof`/`ParachainHeadersWithFinalityProof`. The GRANDPA justification signature check and other validations run *after* the vulnerable ancestry walk is reached in some call paths (`verify_parachain_headers_with_grandpa_finality_proof` computes ancestry inside `verify_grandpa_finality_proof` before the justification's cryptographic verification only gates the *result*, but the ancestry walk over `unknown_headers` itself is unconditionally executed against attacker data).

### Recommendation
Add cycle detection (e.g., track visited hashes in a `BTreeSet`/`HashSet` and return `Err(NotDescendent)` immediately if a hash is revisited) or bound the walk to at most `unknown_headers.len()` iterations in `AncestryChain::ancestry`. Alternatively, validate that `unknown_headers` forms an acyclic chain (e.g., strictly increasing block numbers from base to target) before invoking `ancestry`.

### Proof of Concept
1. Construct header `B` with arbitrary fields and a placeholder `parent_hash`; compute `hash(B)`.
2. Construct header `A` with `parent_hash = hash(B)`; compute `hash(A)`.
3. Re-construct `B` with `parent_hash = hash(A)` (fields chosen so `hash(B)` is unaffected by this change, e.g. use a field unrelated to the hash pre-image ordering, or iterate to find a consistent fixed point — trivial since the attacker fully controls both structs and can iterate offline).
4. Submit `unknown_headers = [A, B]` (or more) inside a `ConsensusMessage::Polkadot`/`StandaloneChain` proof via `Message::Consensus` in `pallet_ismp::Call::handle_unsigned`, with `target = A.hash()`/`base` chosen such that neither A nor B's hash equals `base`.
5. `validate_unsigned` (or block execution) calls `Self::execute` → ... → `verify_grandpa_finality_proof` → `AncestryChain::ancestry(from, target.hash())`, which loops forever alternating between A and B, hanging the node.
