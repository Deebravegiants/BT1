### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header is trusted without being covered by the HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` authenticates the *body* of an incoming webhook but never the `x-shopify-shop-domain`, `x-shopify-topic`, or `x-shopify-webhook-id` headers. `Registry.process` nevertheless trusts `request.shop` and `request.topic` directly from these unauthenticated headers to dispatch the webhook and identify the tenant, breaking the binding between "HMAC-verified sender" and "shop the data is attributed to."

### Finding Description
`Request#hmac`/`to_signable_string` compute the signable content solely from the raw body: [1](#0-0) [2](#0-1) 

`Registry.process` validates the HMAC over that request, but then reads `request.shop` (and `topic`) — both taken verbatim from attacker-controllable HTTP headers — and forwards them unauthenticated to the handler: [3](#0-2) 

The identity binding that should hold is:
`HMAC-authenticated bytes == bytes that determine the tenant (shop) the webhook is attributed to`

Here, `HmacValidator.validate_signature` only proves `HMAC(secret, raw_body)` is correct; it says nothing about which shop sent it. Since the webhook endpoint is a single public HTTP endpoint shared across all merchants who install the app, any unprivileged internet user who can obtain **one** valid `(raw_body, hmac)` pair — trivially by installing the app on their own free development store and capturing their own legitimate webhook delivery — can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header (and topic/webhook-id) for a victim shop. The HMAC check still passes because it only checks the body, but `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` now presents attacker-chosen topic/shop paired with the attacker's own body content to the host application's handler as if it legitimately originated from the victim shop.

### Impact Explanation
Host applications built on this gem typically use `WebhookMetadata#shop` as the tenant key to look up/update per-merchant records (e.g., marking a shop uninstalled, updating shop-scoped data, or triggering redact/data-request flows for `shop/redact`, `customers/redact`, `customers/data_request` — the very topics this gem marks `MANDATORY_TOPICS`). By spoofing the `shop-domain` header on a replayed, still-HMAC-valid request, an attacker can make the host app process a forged event as if it belongs to a different shop it does not control, i.e., cross-tenant confusion/spoofing of webhook events without possessing that shop's credentials or the app's `client_secret`.

### Likelihood Explanation
Reachable by any unprivileged internet user: obtaining a valid `(raw_body, hmac)` pair only requires installing the app on the attacker's own (or a free development) store, which is a normal, unprivileged action, and the webhook endpoint accepts arbitrary HTTP headers from any caller since header authenticity is never checked by this gem.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable content used for HMAC verification, or otherwise cryptographically bind them to the verified body (e.g., verify shop domain against a value derived from a signed claim rather than a raw header), so that the HMAC proves both message integrity and the claimed shop/topic identity together.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and captures a legitimate webhook delivery, e.g. topic `customers/redact` with body `raw_body` and header `x-shopify-hmac-sha256: H`, where `H = HMAC_SHA256(api_secret_key, raw_body)`.
2. Attacker sends a POST to the app's public webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` in `lib/shopify_api/webhooks/registry.rb` line 190 succeeds because it only checks `raw_body` against `H`.
4. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and invokes the handler, causing the host app to process attacker-controlled data attributed to `victim-shop.myshopify.com`.
