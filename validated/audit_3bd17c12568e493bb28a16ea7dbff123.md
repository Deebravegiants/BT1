## Title
Directly-transferred LT donations to the curve `Pair` become permanently frozen once the token graduates - (File: `packages/contracts/src/Pair.sol` / `packages/contracts/src/Router.sol` / `packages/contracts/src/Bonding.sol`)

### Summary
Any unprivileged wallet can call `IERC20(lt).transfer(pair, amount)` directly on a still-`Curve`-stage bonding pair. This "donated" LT is by design excluded from the `ltFromPair` amount that `Router.graduate` drains, so it stays in the `Pair` contract. Once the token graduates (`Bonding.finalizeGraduation` flips `lifecycle` to `Graduated`), the only code path capable of pulling assets out of the `Pair` — `Router.graduate`, gated by `BONDING_ROLE` and called only from `Bonding._prepareGraduationLiquidity` — becomes permanently unreachable for that token. The donated LT is stranded in the abandoned `Pair` contract forever, exactly analogous to the `StakingEscrow` bug where FORT sent directly to the contract could never be released because it was never accounted for by `pendingReward`.

### Finding Description
The dual-graduation design deliberately reads the pair's **stored** `assetReserve` (not the live `balanceOf`) to compute `ltFromPair`, specifically so that direct LT donations don't skew the LP-open price or the USD graduation trigger: [1](#0-0) 

`Router.graduate` transfers out only the explicit `amount` (`ltFromPair`), intentionally leaving any donated surplus behind in the `Pair`: [2](#0-1) 

The protocol's own natspec acknowledges the "locked" surplus is unreachable once the lifecycle flips past `Curve`, since `BONDING_ROLE`'s only caller of `graduate` is `_prepareGraduationLiquidity`, which never runs again for a graduated token: [3](#0-2) 

`Pair.sol` exposes no other withdrawal path for its asset token besides `transferAsset`, which is `onlyRouter`-gated and only invoked by `Router.sell` / `Router.graduate` — both of which require `Curve` lifecycle state that is gone after graduation: [4](#0-3) 

This is explicitly documented as accepted/intended behavior in the project's own scope docs and invariant test suite — "Donated LT remains locked in the curve pair", confirmed by `test_graduate_leavesDonationBehind`: [5](#0-4) [6](#0-5) 

Because `Bonding.buy`/`sell` are the only trading paths and neither of them ever reads or moves LT sitting idle in a graduated `Pair`, and `Router` has no admin rescue function, any LT sent directly to the `Pair` before graduation — whether by an unaware creator/trader trying to "top up" liquidity, an integrator mistake, or a leftover overshoot from some future flow — is permanently frozen the moment graduation completes.

### Impact Explanation
This is a permanent freezing-of-funds bug reachable by any unprivileged wallet with zero special permissions: `IERC20(lt).transfer(pair, X)` is a plain ERC20 transfer to a public address. Once the corresponding token graduates (a state change any trader can also trigger via `Bonding.triggerGraduation` / a threshold-crossing `Zap.buy`), the donated LT value is unrecoverable by the depositor, the creator, or the protocol — there is no admin sweep, no rescue function, and no documented off-chain recovery process referenced in the contracts. Given LT is itself a leveraged, appreciating asset, the frozen amount can represent real economic value.

### Likelihood Explanation
High reachability, low likelihood of large-scale abuse: the transfer requires no privilege and no unusual conditions, but it is a self-damaging action (loss is borne by whoever sends the donation, not exploited against a victim), so it is more of an accidental-loss/permanent-freeze bug than an attacker-profit exploit. It matches the "L2 tokens could get stuck" bug class precisely: tokens transferred directly to a contract that only releases previously-accounted-for balances become stuck by design, with no warning enforced on-chain (only in docs/tests, not in the contract itself via a revert or event).

### Recommendation
Add either (a) an owner-gated (or permissionless-but-safe) sweep function on `Pair`/`Router`, callable only after the pair has graduated, that forwards any residual `assetBalance() - assetReserve` (or, post-graduation, the full residual balance) to a designated recipient (mirroring `FeeVault.sweepDonations()`'s pattern), or (b) a `Pair.skim`-style mechanism reachable post-graduation via `BONDING_ROLE` regardless of lifecycle state, so that stranded donations can still be recovered and distributed (e.g., to the protocol owner or burned) instead of being permanently locked.

### Proof of Concept
1. Launch a token via `Bonding.launch`; the token is in `Lifecycle.Curve` with pair `P`.
2. A wallet calls `IERC20(lt).transfer(P, 1000e18)` directly — an ordinary ERC20 transfer, no approvals or roles required.
3. Trading continues normally; eventually a buy crosses the graduation threshold, `Bonding._enterGraduating` computes `ltFromPair` from the **stored** `assetReserve` (excluding the 1000e18 donation) and caches it.
4. `finalizeGraduation` is called (permissionless); `Router.graduate` drains only `ltFromPair`; the 1000e18 donation remains in `P`, as demonstrated by `test_graduate_leavesDonationBehind` [6](#0-5) .
5. `info.lifecycle` is now `Graduated`. No function in `Bonding`, `Router`, or `Pair` can move assets out of `P` anymore (`Router.graduate`'s only caller path is gated by `Lifecycle.Curve`, which no longer holds). The 1000e18 LT is permanently frozen in `P`.

    /// @dev Burns unsold curve tokens, drains real raised LT, computes
    ///      `tokensForLP` for zero-gap LP seeding, burns the LP excess.
    ///
    ///      Price equality: `tokensForLP / ltFromPair = tokenReserve / assetReserve`,
    ///      with `ltFromPair = assetReserve - virtualLtReserve` (the LT
    ///      actually raised by the curve, excluding the launch-time virtual
    ///      seed; the seed is recovered as `Pair.k() / TOTAL_SUPPLY`, see
    ///      `_launchTimeVirtualLtReserve`). Substituting gives LP price =
    ///      `assetReserve / tokenReserve` = curve close marginal price.
    ///      Donations of LT directly to the pair don't move the stored
    ///      `assetReserve`, so they're excluded from `ltFromPair`.
    ///
    ///      Token-side donations are handled by `unsoldBurned`: any tokens
    ///      sitting in the pair beyond the curve's accounting are burned.
    ///
    ///      With virtual `tokenReserve = totalSupply` and `curveSupply = 75%`,
    ///      the parabola `tokensForLP(sold) = sold·(S−sold)/S` peaks at
    ///      `S/4 = LP_RESERVE` when `sold = S/2`, so `tokensForLP ≤ LP_RESERVE`
    ///      is mathematically invariant. The cap is defensive.
    function _prepareGraduationLiquidity(
        address tokenAddress
    ) internal returns (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) {
        address pairAddr = _s().tokenInfo[tokenAddress].pair;
        (uint256 tokenReserve, uint256 assetReserve) = IPair(pairAddr).getReserves();

        unsoldBurned = IPair(pairAddr).tokenBalance();
        if (unsoldBurned > 0) {
            Token(tokenAddress).burn(pairAddr, unsoldBurned);
        }

        ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
        if (ltFromPair > 0) {
            _s().router.graduate(tokenAddress, ltFromPair);
        }

        tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
        if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;

        lpBurned = LP_RESERVE - tokensForLP;
        if (lpBurned > 0) {
            Token(tokenAddress).burn(address(this), lpBurned);
        }
    }

    /// @notice Transfer exactly `amount` of LT out of the pair to the caller.
    ///         Called by `Bonding._prepareGraduationLiquidity` during graduation
    ///         with `amount = stored assetReserve - virtualLtReserve` (i.e. the
    ///         real LT raised by the curve, excluding the virtual seed).
    /// @dev    Donation-resistant: passing an explicit `amount` instead of
    ///         draining `assetBalance()` ensures any LT that was donated
    ///         directly to the pair via `IERC20.transfer` is left behind and
    ///         excluded from LP seeding.
    ///
    ///         "Locked" here is a trust-assumption claim, not an on-chain
    ///         guarantee. `Pair.transferAsset` is gated by `onlyRouter`, and
    ///         `Router` only exposes it via this function and `sell`. Both
    ///         require `BONDING_ROLE`, which only `Bonding` holds. `Bonding`
    ///         in turn only calls `graduate` from
    ///         `_prepareGraduationLiquidity` — which is unreachable once the
    ///         token's lifecycle has flipped past `Curve`. So the leftover
    ///         is unreachable as long as (a) `BONDING_ROLE` is not granted
    ///         to any other address, and (b) future `Bonding` upgrades
    ///         preserve the lifecycle gate.
    function graduate(
        address token,
        uint256 amount
    ) external onlyRole(BONDING_ROLE) {
        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();
        IPair(pairAddr).transferAsset(msg.sender, amount);
    }

    function test_graduate_leavesDonationBehind() public {
        // The whole point of the new signature: passing an explicit amount
        // means anything `IERC20.transfer`-donated to the pair stays put.
        uint256 raised = 4000 ether;

        vm.prank(bondingRole);
        router.graduate(address(token), raised);

        assertEq(asset.balanceOf(bondingRole), raised, "Only the requested amount is drained");
        assertEq(IPair(pairAddr).assetBalance(), donated, "Donation remains locked in pair");
