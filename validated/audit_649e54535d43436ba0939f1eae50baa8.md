### Title
Quadratic-cost `bytes.concat` re-encoding of attacker-sized BEEFY commitment payload in `Codec.Encode` - ([File: evm/src/consensus/Codec.sol])

### Summary
`Codec.Encode(Commitment memory commitment)` SCALE-encodes a BEEFY commitment by repeatedly calling `bytes.concat(payload, ...)` inside a loop over `commitment.payload`, where `payload` is a `bytes memory` accumulator that is fully reallocated and copied on every iteration. [1](#0-0) 
This is structurally the same bug class as the xmldom `normalize()` issue: repeated remove/append of adjacent nodes forcing full reindexing and string rebuilding on every step, giving O(n²) behavior for an O(n) input.

### Finding Description
`Codec.Encode` builds up the encoded commitment payload with:
```solidity
for (uint256 i = 0; i < payloadLen; i++) {
    payload = bytes.concat(
        payload,
        abi.encodePacked(commitment.payload[i].id),
        ScaleCodec.encodeBytes(commitment.payload[i].data)
    );
}
``` [2](#0-1) 
`bytes.concat` allocates a brand-new byte array and copies the entire accumulated `payload` plus the new chunk on every call — this is the Solidity analog of xmldom's adjacent-text-node "remove and re-append" pattern. As `payload` grows across `payloadLen` iterations, the total cost of the loop is O(n²) in the total payload size, not O(n).

This function is invoked from `EcdsaBeefy.verifyMmrUpdateProof`, an unprivileged, permissionless code path reached directly from `EcdsaBeefy.verify()`:
```solidity
bytes32 commitmentHash = keccak256(Codec.Encode(commitment));
``` [3](#0-2) 
`verify()` is the `IConsensusV2` entry point that any relayer can call with an arbitrary ABI-decoded `RelayChainProof`/`ParachainProof`:
```solidity
function verify(bytes calldata previousState, bytes calldata proof)
    external
    pure
    returns (bytes memory, IntermediateState[] memory, uint256)
{
    ...
    (RelayChainProof memory relay, ParachainProof memory parachain) =
        abi.decode(proof, (RelayChainProof, ParachainProof));
    ...
    (BeefyConsensusState memory newState, bytes32 headsRoot) = verifyMmrUpdateProof(consensusState, relay);
``` [4](#0-3) 
`commitment.payload` is an ABI-decoded dynamic array whose length is controlled entirely by the calldata submitted by the caller. I found no bound on `commitment.payload.length` in `Codec.sol` or `EcdsaBeefy.sol` — only `sigLen` (number of votes) is checked against the supermajority threshold via `checkParticipationThreshold`, and `mmrRoot` extraction itself already iterates the full `payload` array once before the encode call:
```solidity
uint256 payloadLength = commitment.payload.length;
bytes32 mmrRoot;
for (uint256 i = 0; i < payloadLength; i++) {
    if (commitment.payload[i].id == MMR_ROOT_PAYLOAD_ID && commitment.payload[i].data.length == 32) {
        mmrRoot = Bytes.toBytes32(commitment.payload[i].data);
    }
}
if (mmrRoot == bytes32(0)) revert MmrRootHashMissing();
``` [5](#0-4) 
This confirms `payload` entries with arbitrary `id`/`data` are accepted as long as one entry carries the mmr-root id — an attacker can pad the array with many additional bogus entries (any `id` other than `mh`, small `data`) purely to blow up the cost of the subsequent `Codec.Encode` call.

### Impact Explanation
`EcdsaBeefy` is the gas-expensive but permissionless ECDSA-based BEEFY consensus client documented as an option requiring "no off-chain proving infrastructure," used to update trusted consensus state / MMR root for a counterparty chain. [6](#0-5) 
Because `Codec.Encode` is on the hot path that computes `commitmentHash` — which every recovered signature must match — the O(n²) rebuild happens before any signature or merkle-proof check can reject a padded commitment. An attacker submitting a proof with a moderately large padded `payload` array can inflate the gas cost of `verify()` disproportionately (quadratically) relative to legitimate proofs. This can:
- Push otherwise-valid-looking submissions over the block gas limit, effectively denying the ability to relay legitimate consensus updates through this verifier (a route unable to deliver messages), and/or
- Force every relayer attempting to process the (malformed) proof to pay excessive gas, griefing honest relayers economically.

Because `verify()` is `pure` and called by relayers/consensus modules that trust untrusted proof bytes before any signature check succeeds, this is reachable from a single submitted consensus proof/message with no privileged role required, matching the "route unable to deliver messages" acceptance criterion.

### Likelihood Explanation
Likelihood is Medium: exploitation requires only crafting a `Commitment` with an artificially large `payload` array (each entry just needs a distinct `id`/short `data`, one of them the real MMR root entry) and submitting it as part of a `BeefyConsensusProof`/`RelayChainProof` to `EcdsaBeefy.verify()`. No signature forgery or privileged access is needed to trigger the quadratic cost — the loop runs, and the full re-encode happens, before authority-set/signature checks can reject the update. The severity is bounded by EVM calldata/gas limits (unlike an unbounded parser), which caps how large `payloadLen` can practically be made, keeping this at Medium rather than Critical.

### Recommendation
Rewrite `Codec.Encode(Commitment memory commitment)` to compute the total encoded length up front (or use a pre-sized buffer / `abi.encodePacked` accumulation pattern that appends via a single pass, e.g. building into a fixed-size `bytes` buffer with `mstore`/`copy`, or collecting sub-encodings into an array and concatenating once with a single `bytes.concat(...)` call over all elements) so the total cost is O(n) rather than O(n²). Additionally, consider bounding `commitment.payload.length` to a small sane maximum (BEEFY commitments in practice carry only 1–2 payload items, e.g. the MMR root) before performing any encoding work, rejecting oversized payload arrays early.

### Proof of Concept
1. Construct a `Commitment` whose `payload` array contains `N` entries: one legitimate `{id: "mh", data: <32 bytes>}` and `N-1` filler entries `{id: bytes2(0), data: <small bytes>}`.
2. Wrap it in a `BeefyConsensusProof`/`RelayChainProof` with any (even invalid) votes/proof — the cost is paid inside `verifyMmrUpdateProof` before signature verification would reject it, since `Codec.Encode(commitment)` (called at line 152 of `EcdsaBeefy.sol`) runs immediately after the mmr-root scan loop.
3. Call `EcdsaBeefy.verify(previousState, proof)` with increasing `N` and measure gas consumption; observe it grows quadratically with `N` (each `bytes.concat` copies the whole accumulated buffer), rather than linearly, matching the `Codec.sol:41-47` loop structure.
4. Compare against `Codec.DecodeHeader`'s digest loop, which does not re-concat cumulative state and stays linear, confirming the quadratic behavior is specific to the `Encode` function's `bytes.concat` accumulator pattern.

    function Encode(Commitment memory commitment) internal pure returns (bytes memory) {
        uint256 payloadLen = commitment.payload.length;
        bytes memory payload = bytes("");
        for (uint256 i = 0; i < payloadLen; i++) {
            payload = bytes.concat(
                payload,
                abi.encodePacked(commitment.payload[i].id),
                ScaleCodec.encodeBytes(commitment.payload[i].data)
            );
        }

        return bytes.concat(
            ScaleCodec.encodeUintCompact(payloadLen),
            payload,
            ScaleCodec.encode32(commitment.blockNumber),
            ScaleCodec.encode64(commitment.validatorSetId)
        );
    }
