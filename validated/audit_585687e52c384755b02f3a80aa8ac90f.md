### Title
Caller-controlled flash-loan receiver can attach unauthorized token transfers to the caller’s authorization tree - (File: `contracts/controller/src/strategies/flash_loan.rs`) [1](#0-0) 

### Summary
`flash_loan` authenticates `caller`, but accepts an arbitrary Wasm `receiver` and opaque `data` without binding them to a trusted callback implementation or restricting authorization demanded by the callback. [1](#0-0)   
The pool transfers loan proceeds to that receiver and invokes its `execute_flash_loan` callback, allowing attacker-deployed code to execute inside the caller-authorized transaction. [2](#0-1) 

### Finding Description
The controller validates only that `amount` is positive, the hub is active, and `receiver` is a Wasm contract; it does not validate the receiver’s implementation, callback behavior, or semantic contents of `data`. [3](#0-2)   
The pool sends `amount` directly to `receiver`, invokes `execute_flash_loan(initiator, asset, amount, fee, pool, data)`, and only afterward requires principal-plus-fee repayment. [4](#0-3)   
Soroban authorization records host calls made by nested contracts beneath the caller’s root authorization, and the repository’s auth-tree test demonstrates that a nested rogue contract can add a `token.transfer(victim, attacker, amount)` child to that tree. [5](#0-4)   
If the victim signs the tree produced by simulation, the host accepts the malicious child transfer rather than limiting authorization to the intended flash-loan operation. [6](#0-5) 

### Impact Explanation
A malicious receiver can transfer unrelated tokens held by the caller to an attacker while still approving repayment of the flash loan, causing permanent theft of user wallet funds rather than merely failing the loan. [7](#0-6)   
The receiver can use the borrowed principal or its own funds to satisfy `amount + fee`, so the protocol’s repayment invariant does not constrain theft of other caller assets authorized as a child invocation. [8](#0-7) 

### Likelihood Explanation
Any unprivileged caller can deploy a Wasm receiver and pass its address and arbitrary `data` to `flash_loan`; no governance approval or allowlist check intervenes. [3](#0-2)   
Exploitation requires the victim to sign an authorization tree containing the malicious child transfer, so wallet or client authorization-tree presentation materially affects practical exploitability. [9](#0-8) 

### Recommendation
Use governance-controlled trusted receiver implementations or code-hash allowlists for flash-loan callbacks instead of accepting arbitrary receiver contracts. [10](#0-9)   
If arbitrary receivers remain supported, require clients to present the complete simulated authorization tree and explicitly reject trees containing any child invocation beyond the expected repayment approval. [11](#0-10)   
Define and validate a versioned callback payload schema where possible, and document that `data`, `receiver`, and every nested authorization request are untrusted inputs. [12](#0-11) 

### Proof of Concept
1. The attacker deploys a Wasm contract implementing `execute_flash_loan(initiator, asset, amount, fee, pool, data)`. [12](#0-11) 
2. The victim invokes `Controller::flash_loan(caller=victim, asset, amount, receiver=attacker_contract, data=attacker_bytes)`. [13](#0-12) 
3. The pool transfers `amount` to `attacker_contract` and calls its callback. [14](#0-13) 
4. Inside the callback, the contract calls `token.transfer(victim, attacker, victim_balance)` for an unrelated token held by the victim; the token’s `transfer` requires `victim` authorization. [15](#0-14) 
5. Simulation records that transfer as a child of the victim’s `flash_loan` authorization, and signing the resulting poisoned tree makes the transaction succeed. [11](#0-10) 
6. The malicious receiver approves `amount + fee` to the pool, satisfying repayment while the unrelated victim tokens remain transferred to the attacker. [16](#0-15)
