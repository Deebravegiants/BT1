### Title
Hyperbridge withdrawal router authenticates only the source *chain*, not the sending *module* — a coprocessor-chain module can forge relayer-fee withdrawals - ([File: modules/pallets/ismp/src/dispatcher.rs])

### Summary
CVE-2022-25182 is a sandbox-bypass where a "specially crafted" identifier (a library name), evaluated once a privileged resource is already configured (a global Pipeline library), lets an attacker reach code that was meant to be restricted to that privileged context. The Hyperbridge analog is `IsmpHostRouter::module_for_id` / `HyperbridgeWithdrawalModule::on_accept` in `pallet-ismp`: once a chain has configured a `Coprocessor` (the Hyperbridge/Nexus chain), *any* inbound `PostRequest` whose `to` field equals the reserved id `b"HYPR-FEE"` is routed to the built-in withdrawal handler, and that handler authenticates only the request's **source chain**, never the **sending module** on that chain.

### Finding Description
`IsmpHostRouter::module_for_id` intercepts the well-known 8-byte id before deferring to the runtime router: [1](#0-0) 

`HyperbridgeWithdrawalModule::on_accept` then only checks `request.source` — the chain the message came from — before decoding the body and transferring funds out of `RELAYER_FEE_ACCOUNT`: [2](#0-1) 

There is no check of `request.from` (the originating *module/pallet* on the coprocessor chain). The router/module design elsewhere in the codebase (e.g. `ProxyModule::on_accept` in `parachain/runtimes/nexus/src/ismp.rs`) dispatches based on the attacker/relayer-influenced `to`/`from` byte strings decoded via `ModuleId::from_bytes`: [3](#0-2) [4](#0-3) 

Any pallet on the coprocessor chain (Nexus) that implements/uses the generic `IsmpDispatcher::dispatch_request` interface and lets a caller (directly or indirectly) influence the outgoing `to` bytes of a `Post` request can set `to = b"HYPR-FEE"`. Because the message's `source` field is always stamped with `self.host_state_machine()` at dispatch time (see `dispatcher.rs` lines 92-151, `source: self.host_state_machine()`), any message genuinely dispatched from Nexus — regardless of which pallet/account triggered it — will satisfy `Some(source) == T::Coprocessor::get()` on the receiving chain, and will be decoded and executed as a legitimate `WithdrawRelayerFees` instruction, moving funds from `RELAYER_FEE_ACCOUNT` to an attacker-chosen account for an attacker-chosen amount (bounded only by the account's balance).

This mirrors the Jenkins bug class precisely: the "sandbox" here is "only the protocol's own fee-accumulation logic may address `HYPR-FEE`"; the actual enforced boundary is much weaker ("any message that genuinely originated on the configured coprocessor chain"), which is bypassable by crafting the module identifier (`to`) rather than by any cryptographic forgery.

### Impact Explanation
If any reachable, less-privileged path exists on the coprocessor (Nexus) chain that lets a caller set an outgoing request's `to` field to `b"HYPR-FEE"`, this results in unauthorized draining of the `RELAYER_FEE_ACCOUNT` escrow on every chain configured with that coprocessor — i.e., theft of protocol/relayer funds without any of the intended fee-accumulation proof checks. This satisfies the "concrete theft ... of funds" and "relayer fee and reward accounting" in-scope criteria.

### Likelihood Explanation
Exploitability is contingent on whether an unprivileged (or lightly privileged) pallet on Nexus exposes a way for a caller to fully control the `to` bytes of a dispatched `Post` request to another chain. I was not able to fully confirm such a path within this investigation — the token/messaging pallets examined (`pallet-hyper-fungible-token`, `pallet-token-gateway`) appear to derive `to` from admin-registered per-chain contract mappings rather than raw user input, which would reduce likelihood. However, the *validation gap itself* — checking only `request.source` and never `request.from` in `HyperbridgeWithdrawalModule::on_accept` — is a genuine missing authorization check that departs from defense-in-depth expectations for a fund-moving code path, and should be treated as a real weakness pending confirmation of a concrete unprivileged caller with `to`-field control (e.g., a future generic-messaging pallet, or governance/extrinsic misconfiguration).

### Recommendation
Add an explicit check of `request.from` in `HyperbridgeWithdrawalModule::on_accept`, restricting it to the specific expected sending module id on the coprocessor chain (e.g. the relayer-fee-accumulation pallet's own module id), in addition to the existing `request.source` check, so that the withdrawal path cannot be reached merely by any pallet capable of dispatching a message with a crafted `to`/destination-module id.

### Proof of Concept
Conceptual (not fully verified against a concrete unprivileged caller in this codebase snapshot):
1. Identify or introduce a pallet/extrinsic on the Nexus (coprocessor) chain that calls `Pallet::<T>::dispatch_request` (via `IsmpDispatcher`) with a caller-influenced `to: Vec<u8>` field for an outgoing `Post` request targeting a victim chain `B` that runs `pallet-ismp` with `Coprocessor = Nexus`.
2. Set `to = b"HYPR-FEE"` and `body = Message::WithdrawRelayerFees(WithdrawalRequest { account: attacker, amount: X }).encode()`.
3. Relay the resulting request to chain `B`. On delivery, `IsmpHostRouter::module_for_id` routes it to `HyperbridgeWithdrawalModule::on_accept`; `request.source == Nexus == T::Coprocessor::get()` passes, the message decodes successfully, and `T::Currency::transfer(&RELAYER_FEE_ACCOUNT, &attacker, X, ...)` executes, moving escrowed relayer fees to the attacker's account — without any check that the *sending pallet* on Nexus was the intended fee-accumulation logic.

impl<T: Config> IsmpModule for HyperbridgeWithdrawalModule<T> {
	fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
		// Only the configured coprocessor may instruct withdrawals.
		let source = request.source;
		if Some(source) != T::Coprocessor::get() {
			Err(IsmpError::Custom(format!("Invalid request source: {source}")))?
		}

		let message = Message::<T::AccountId, T::Balance>::decode(&mut &request.body[..])
			.map_err(|err| IsmpError::Custom(format!("Failed to decode message: {err:?}")))?;

		match message {
			Message::WithdrawRelayerFees(WithdrawalRequest { account, amount }) => {
				T::Currency::transfer(
					&RELAYER_FEE_ACCOUNT.into_account_truncating(),
					&account,
					amount,
					Preservation::Expendable,
				)
				.map_err(|err| {
					IsmpError::Custom(format!("Error withdrawing protocol fees: {err:?}"))
				})?;

				Pallet::<T>::deposit_event(Event::<T>::RelayerFeeWithdrawn { amount, account });
			},
		}

		Ok(<T as frame_system::Config>::DbWeight::get().reads_writes(0, 0))
	}

/// Module identification types supported by ismp
#[derive(PartialEq, Eq, scale_info::TypeInfo)]
pub enum ModuleId {
	/// Unique Pallet identification in runtime
	Pallet(PalletId),
	/// Contract account id
	Contract(AccountId32),
	/// Evm contract
	Evm(H160),
}

impl ModuleId {
	/// Convert module id to raw bytes
	pub fn to_bytes(&self) -> Vec<u8> {
		match self {
			ModuleId::Pallet(pallet_id) => pallet_id.0.to_vec(),
			ModuleId::Contract(account_id) => account_id.as_slice().to_vec(),
			ModuleId::Evm(account_id) => account_id.0.to_vec(),
		}
	}

	/// Derive module id from raw bytes
	pub fn from_bytes(bytes: &[u8]) -> Result<Self, &'static str> {
		if bytes.len() == 8 {
			let mut inner = [0u8; 8];
			inner.copy_from_slice(bytes);
			Ok(Self::Pallet(PalletId(inner)))
		} else if bytes.len() == 32 {
			Ok(Self::Contract(AccountId32::from_slice(bytes).map_err(|_| "slice is 32 bytes")?))
		} else if bytes.len() == 20 {
			Ok(Self::Evm(H160::from_slice(bytes)))
		} else {
			Err("Unknown Module ID format")
		}
	}
}
