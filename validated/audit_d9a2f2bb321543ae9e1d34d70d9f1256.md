Audit Report

## Title
`T::Currency::transfer` in `pallet-nfts::do_claim_swap` uses live-looked-up NFT owners with no restriction on destination accounts, allowing drainage of any account (including pallet-derived sovereign accounts such as `pallet-asset-conversion` pool accounts) that unknowingly "holds" an NFT - ([File: substrate/frame/nfts/src/features/atomic_swap.rs])

## Summary
`do_claim_swap` resolves `send_item.owner` and `receive_item.owner` fresh from `Item` storage at claim time and unconditionally calls `T::Currency::transfer` between these two accounts based on `swap.price.direction`, with no check on the identity or nature of either account. Since `do_transfer` in `substrate/frame/nfts/src/features/transfer.rs` allows any current owner to move an NFT to an arbitrary destination `AccountId` without that destination's consent, an attacker can seed an NFT onto any account address they can compute — including a `pallet-asset-conversion` pool's deterministic, keyless sovereign account — and then claim a self-created swap to pull `T::Currency` funds out of it.

## Finding Description
`do_claim_swap` reads item ownership live from storage and performs the price transfer purely based on `price.direction`, with no verification of what kind of account `send_item.owner`/`receive_item.owner` are: [1](#0-0) 

The only checks present are: the caller must own `send_item`, the swap's `desired_collection`/`price` must match the witness, the optional `desired_item` must match, and the deadline must not have passed. None of these validate the destination of a `T::Currency::transfer` beyond "whoever currently owns the NFT," and nothing in the codebase restricts NFT ownership to accounts with a private key or consent mechanism.

This is corroborated by `do_transfer` in `substrate/frame/nfts/src/features/transfer.rs`, which unconditionally overwrites the `owner` field to any destination `AccountId` passed in, with zero consent check from the destination: [2](#0-1) 

Separately, `pallet-asset-conversion`'s pool sovereign accounts are derived deterministically and publicly via `AccountIdConverter::try_convert`, requiring no private key or on-chain registration to become the destination of an arbitrary transfer: [3](#0-2) 

The exploit flow described in the claim is directly supported by the code: an attacker (1) creates a swap via `do_create_swap` offering an NFT they own with a `price`/`direction`, (2) transfers that NFT to the target sovereign account using the normal, unrestricted `transfer` extrinsic (no consent required per `do_transfer`), and (3) calls `claim_swap` from a second account they control, which triggers `T::Currency::transfer` sourced from `receive_item.owner` (now the sovereign account) to `send_item.owner` (the attacker), per `PriceDirection::Send` handling at lines 195-200. None of the pallet's existing guards check whether `receive_item.owner`/`send_item.owner` are "normal" signed accounts versus pallet-derived accounts backing unrelated funds.

## Impact Explanation
If a runtime's `pallet_nfts::Config::Currency` (or `pallet_uniques::Config::Currency`) shares the same fungible implementation as the native asset used by `pallet-asset-conversion` pools — a realistic configuration (e.g., Asset Hub-style runtimes using `Balances` for both) — an attacker can drain that pool's native reserves down to the existential deposit, bypassing `swap_exact_tokens_for_tokens`/`add_liquidity`/`remove_liquidity` entirely and without any reserve/LP accounting update. This desynchronizes the pool's actual backing from LP-token-implied entitlements, harming liquidity providers and corrupting subsequent live-balance-based pricing/swaps. This is a genuine cross-pallet accounting break with concrete, quantifiable loss, not a purely theoretical scenario.

## Likelihood Explanation
The attack requires only unprivileged, signed accounts and three ordinary extrinsics (`create_swap`, a standard NFT `transfer`, `claim_swap`), all fully within a normal user's capability when `PalletFeature::Swaps` is enabled. The only non-trivial precondition is a runtime-level configuration choice — sharing the `Currency` type between `pallet-nfts` and an asset-conversion pool's native asset — which is plausible but not universal; it does not hold for every deployment. No governance, leaked keys, or privileged access is needed, and the target account address is publicly and deterministically computable. This makes the vulnerability real and repeatable wherever the currency-sharing precondition is met.

## Recommendation
- In `do_claim_swap` (and ideally `do_create_swap`), reject swaps where the resolved `send_item.owner` or `receive_item.owner` is a pallet-derived/reserved account (e.g., via a shared "protected accounts" registry or trait exposed by `frame_support`), rather than trusting arbitrary live NFT ownership as a valid currency-transfer counterparty.
- Independently, `pallet-asset-conversion` should not rely purely on a pool account's live `T::Currency`/`T::Assets` balance as authoritative reserve state without any protection; consider balance freezes/locks on pool accounts (similar to `pallet-nomination-pools`'s freeze-reason pattern) so unrelated pallets cannot silently move funds out from under LP accounting.
- More generally, any pallet performing `T::Currency::transfer` using accounts derived from unrelated, attacker-influenced storage (like NFT ownership) should validate that counterparties are not addresses reserved/derived by other pallets.

## Proof of Concept
1. Configure a test runtime with `pallet-nfts` and `pallet-asset-conversion` sharing `Balances` as the native currency, and enable `PalletFeature::Swaps`.
2. Create an asset-conversion pool and add liquidity as an honest LP; compute the pool's sovereign account via `PoolLocator::address`.
3. Attacker mints NFT #1 in collection C, calls `create_swap` offering NFT #1 with `price = Some({amount: X, direction: Send})`.
4. Attacker transfers NFT #1 to the pool's sovereign account via the standard `Nfts::transfer` extrinsic (succeeds, no consent required per `do_transfer`).
5. A second attacker-controlled account mints an NFT in the desired collection and calls `claim_swap`, matching the swap's price/witness.
6. Assert: the pool account's native balance decreases by `X`, and the attacker's account balance increases by `X` — with no `pallet-asset-conversion` extrinsic ever invoked, confirming the unauthorized drain and desynced pool reserves relative to outstanding LP token supply.
