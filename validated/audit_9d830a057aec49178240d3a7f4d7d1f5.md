## Title
Unrestricted, Unauthenticated Invocation of `CallDispatcher.dispatch()` Enables Theft of Any Funds Held by the Shared Dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` is a fully public, access-control-free function that executes an arbitrary attacker-supplied `Call[]` (target, value, calldata) from the `CallDispatcher` contract's own context and balance. [1](#0-0)  This mirrors the "dangerous type, no restriction on who can trigger it" pattern of the reported CVE: rather than restricting execution to the intended, trusted callers (`IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`), any unprivileged address can invoke `dispatch()` directly on the deployed singleton and move out whatever native ETH or ERC-20 balance the dispatcher is holding at that moment.

### Finding Description
`CallDispatcher` is explicitly documented as dispatching "untrusted call(s)" [2](#0-1) , and the implementation performs no `msg.sender` check whatsoever before looping over the calls and executing `to.call{value: call.value}(call.data)` against each target: [3](#0-2) 

The intended flow is that `IntentGatewayV2` (or the HFT apps) transiently push assets into this shared dispatcher and then immediately call `dispatch()` themselves as part of the same top-level transaction (predispatch swap-then-escrow, or postdispatch fill-then-act), sweeping any resulting balance back afterward:
- `IntentGatewayV2._placeOrder`/fill flow sends predispatch assets (ETH via `_sendValue`, or ERC-20 via `safeTransferFrom`) to `dispatcher`, then calls `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)`, then sweeps back only the tokens listed in `order.inputs`: [4](#0-3) 
- `IntentsBase._execute` dispatches `order.output.call` (also attacker/user-supplied) through the same dispatcher and then sweeps back only balances for the tokens enumerated in `order.output.assets` (`outputsLen`): [5](#0-4) 
- The same unrestricted-dispatch pattern is used by `HyperFungibleToken`/`WrappedHyperFungibleToken` `onAccept`, which forward the message's `data` straight to `ICallDispatcher(_dispatcher).dispatch(message.data)`: [6](#0-5) 
- `CallDispatcher` also accepts arbitrary native ETH via a public `receive()`: [7](#0-6) 

Because the sweep logic in both `IntentGatewayV2` and `IntentsBase` only reclaims balances for the specific input/output tokens known to that particular order (`inputsLen`/`outputsLen`), any other asset that ends up on the dispatcher's balance during a user- or solver-supplied predispatch/postdispatch call (e.g., swap dust, referral/reward tokens sent to `msg.sender == dispatcher`, or native ETH sent to it directly) is left sitting on the shared, singleton `CallDispatcher` contract between transactions. Since `dispatch()` has no caller restriction, any unprivileged address can subsequently call `CallDispatcher.dispatch()` directly with calldata such as `IERC20.transfer(attacker, balance)` or a raw ETH transfer to sweep out that residual balance, regardless of who legitimately deposited it.

### Impact Explanation
This is directly reachable by any unprivileged transaction — no proof, relayer, or privileged role is required, only a call to the already-deployed `CallDispatcher.dispatch()`. Because the contract is a shared singleton used across every `IntentGatewayV2` order and every `HyperFungibleToken`/`WrappedHyperFungibleToken` cross-chain message with calldata, any native ETH or ERC-20 dust that transiently lands on it (from swaps, DEX slippage, or other calldata side-effects in `order.predispatch.call`/`order.output.call`/`message.data`) is stealable by an outside attacker who front-runs or simply calls `dispatch()` before the intended internal sweep occurs, or after any run that leaves an untracked token/asset behind. This is concrete theft of funds that were never meant to be freely spendable by an arbitrary caller.

### Likelihood Explanation
High: `dispatch()` requires zero authentication and the contract's design intentionally routes value (ETH and ERC-20) through it as part of ordinary user-driven flows (`placeOrder`, `fillOrder`, HFT `onAccept` calldata execution). Any user can also construct a malicious `predispatch.call`/`output.call`/HFT `data` payload that intentionally directs some non-tracked asset to the dispatcher, then separately (or via a colluding/front-running address) call `dispatch()` to claim it.

### Recommendation
Add an access-control modifier to `CallDispatcher.dispatch()` restricting callers to an explicit allowlist of authorized invokers (e.g., the specific `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` instances configured at deployment), or make `CallDispatcher` per-caller/per-order (non-shared) so no cross-order/cross-app balance can accumulate. At minimum, ensure any balance left on the dispatcher after a dispatch cannot be swept by an arbitrary third party.

### Proof of Concept
1. Attacker (or any user) places an `IntentGatewayV2` order whose `order.predispatch.call` performs a swap/claim that results in some token `X` (not part of `order.inputs`) being credited to the `CallDispatcher` address (since the dispatcher is `msg.sender` for that call).
2. The gateway's sweep only reclaims tokens in `order.inputs`/`order.output.assets`, so token `X`'s balance remains on `CallDispatcher`.
3. An attacker directly calls the publicly deployed `CallDispatcher.dispatch(abi.encode([Call({to: X, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, X.balanceOf(dispatcher))})]))`.
4. Because `dispatch()` performs no caller check [3](#0-2) , the call succeeds and transfers the stranded token balance to the attacker.

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
