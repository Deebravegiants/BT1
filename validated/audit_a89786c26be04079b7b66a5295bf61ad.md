Confirmed: `SimplexPaymaster` is deployed live on Ethereum, Arbitrum, Base and Polygon (per `docs/content/developers/evm/simplex/configuration.mdx:81` and `sdk/packages/simplex/docs/ai/decisions/2026-09-07-...md`), and `evm/script/DeploySimplexPaymaster.s.sol` deploys it to Arbitrum among other chains. Arbitrum runs a centralized sequencer, and `SimplexPaymaster` prices every gas payment directly off Chainlink `AggregatorV3Interface.latestRoundData()` with only a staleness (`maxOracleAge`) bound, no `L2SequencerUptimeFeed` check.

### Title
Missing L2 Sequencer Uptime Check in SimplexPaymaster Chainlink Oracle Pricing - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster._getOraclePrice()` fetches Chainlink `latestRoundData()` for both the native/USD and token/USD feeds and only checks `answer > 0` and that `updatedAt` is within `maxOracleAge`. It never checks Arbitrum's L2 Sequencer Uptime Feed. The paymaster is deployed live on Arbitrum [1](#0-0)  via `evm/script/DeploySimplexPaymaster.s.sol` [2](#0-1) .

### Finding Description
`_getOraclePrice` is the sole pricing primitive used to compute how much ERC-20 stablecoin a UserOp sender pays for gas, via `_tokenPrice` → `estimateTokenCost`/`getTokenPrice`/the internal prefund path: [3](#0-2) 

The staleness check (`block.timestamp - updatedAt > maxOracleAge`) only bounds *how old* the last update is; it does nothing to detect that the Arbitrum sequencer itself is offline. Chainlink's Arbitrum price feeds are pushed on-chain by transactions that must go through the sequencer. When the sequencer halts and later recovers, a backlog of price-update and consumer transactions can be processed in a burst, and `updatedAt` for a report can appear timestamped close to `block.timestamp` even though the underlying market price is stale relative to the L1/off-chain reality during the outage window — the standard failure mode Chainlink's own docs warn about (`https://docs.chain.link/data-feeds#l2-sequencer-uptime-feeds`). A basic `maxOracleAge` bound, unlike an explicit `sequencer.latestRoundData()` + grace-period check, cannot detect this condition.

### Impact Explanation
Any UserOp sender (an unprivileged party — no admin or governance role required) reaching `validatePaymasterUserOp`/`_prefund` can exploit mispriced token/native rates during or immediately after an Arbitrum sequencer outage to pay far less ERC-20 stablecoin than the true gas cost of their operation, systematically draining `SimplexPaymaster`'s EntryPoint deposit and stablecoin surplus. This is a permissionless, funds-affecting path: SimplexPaymaster sponsors gas by pulling stablecoins from users via Permit/Permit2 and paying gas from its own EntryPoint deposit [4](#0-3) , so a systematically wrong price directly transfers value out of the contract's treasury/stake.

### Likelihood Explanation
Exploitability depends on an Arbitrum sequencer outage/recovery event occurring, which is infrequent but has happened historically (multi-hour Arbitrum sequencer outages are documented). During such a window, this is trivially reachable by any bundler-submitted UserOp using mode 0x00/0x02 paymasterData — no privileged access needed, matching the "unprivileged... relayer" reachability bar.

### Recommendation
Add an Arbitrum `L2SequencerUptimeFeed` check (with grace period) inside `_getOraclePrice`, reverting when the sequencer is down or has been up for less than the grace period, mirroring the pattern recommended by Chainlink and cited in the external report:
```solidity
function isSequencerActive() internal view returns (bool) {
    (, int256 answer, uint256 startedAt,,) = sequencerUptimeFeed.latestRoundData();
    if (answer != 0 || block.timestamp - startedAt <= GRACE_PERIOD_TIME) return false;
    return true;
}
```
This should be wired into governance-configurable `Params` (per-chain, since only Arbitrum among the deployed chains has this requirement) and enforced before any price is trusted.

### Proof of Concept
1. On Arbitrum, the sequencer halts for several hours (as has occurred historically).
2. During/immediately after recovery, a burst of Chainlink update transactions land with `updatedAt` timestamps close to `block.timestamp`, satisfying `maxOracleAge` while not reflecting the true price at execution time.
3. An attacker submits a UserOp with mode 0x00 (permit) paymasterData referencing `SimplexPaymaster`; `_getOraclePrice` accepts the fresh-but-mispriced feed data because it never queries `L2SequencerUptimeFeed`.
4. `_tokenPrice`/`estimateTokenCost` compute an undervalued token cost, so `PaymasterERC20._postOp`'s ERC-20 pull under-charges the user relative to the actual EntryPoint gas cost, draining the paymaster's deposit/surplus over repeated ops [4](#0-3) .

```text
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
