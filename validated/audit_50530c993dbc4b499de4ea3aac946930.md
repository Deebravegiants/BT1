This confirms the design contrast: `AuthQuery#to_signable_string` in `lib/shopify_api/auth/oauth/auth_query.rb` deliberately includes `shop`, `host`, `code`, `state`, and `timestamp` in the HMAC-signed string, binding the shop identity to the signature. By contrast, `Webhooks::Request#to_signable_string` in `lib/shopify_api/webhooks/request.rb` returns only `@raw_body` — the `shop-domain` and `topic` headers are read directly from unauthenticated HTTP headers and never included in the HMAC computation.

### Title
Webhook `shop` and `topic` identity not bound to HMAC signature, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only [1](#0-0) , while the `shop` and `topic` values used to route and process the webhook are read straight from HTTP headers that are not covered by the signature [2](#0-1) . `Registry.process` validates only this body HMAC before dispatching to the handler with the header-derived `shop` [3](#0-2) .

### Finding Description
The identity binding that should hold is: `shop asserted in the HMAC-signed material == shop used by the host application to attribute the webhook`. In `Webhooks::Request`, `hmac` is derived from the `hmac-sha256`/`x-shopify-hmac-sha256` header [4](#0-3) , and `HmacValidator.validate` only checks that this HMAC matches `HMAC-SHA256(api_secret_key, raw_body)` [5](#0-4) . Neither `shop` nor `topic` is part of `to_signable_string`, so the signature proves only "this body was signed by our app secret" — it proves nothing about which shop or topic it was issued for. Since a single app has one `api_secret_key` shared across every shop that installs it, any party who can obtain one genuine (body, HMAC) pair from Shopify for *any* shop that installs the app (including a shop the attacker legitimately owns/controls, e.g., a free development store) can replay that exact body+HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` and/or `x-shopify-topic` headers for a different, victim shop/topic. `Registry.process` will accept it because HMAC validation passes, and will invoke the handler with `WebhookMetadata` built from the attacker-controlled `shop`/`topic` headers [3](#0-2) . This contrasts directly with the OAuth flow, where `AuthQuery#to_signable_string` explicitly folds `shop` into the signed payload [6](#0-5) , showing the gem's own pattern for correctly binding shop identity to a signature — a pattern not applied to webhooks.

### Impact Explanation
An attacker who legitimately installs the target app on their own (attacker-controlled) shop receives genuinely-signed webhooks for that installation. By replaying the captured body+HMAC to the shared webhook endpoint with a forged `shop-domain` header naming a victim tenant, the attacker can inject attacker-chosen webhook payloads that the host application will process and persist as if they originated from the victim shop. Depending on how the host app's webhook handlers use `WebhookMetadata#shop`/`topic` (e.g., updating shop records, revoking access on `app/uninstalled`, mutating tenant data keyed by `shop`), this is a cross-tenant data integrity/confusion primitive attributable to a break in the shop-identity binding.

### Likelihood Explanation
Likelihood is constrained by the fact that the attacker must obtain at least one genuine (body, HMAC) pair emitted by Shopify for the target app — achievable by installing the app on the attacker's own store/dev store (which is available to any unprivileged internet user with a free Shopify Partner account) and triggering an event whose body is generic/predictable enough to be useful for a different topic/shop (e.g., topics with static or attacker-influenced payloads). The webhook endpoint itself is a public, unauthenticated HTTP endpoint by design, so no additional access is required to deliver the forged request.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or at minimum `shop`) in the HMAC-signable string for webhook requests, mirroring the approach already used in `AuthQuery#to_signable_string`, so that the signature cryptographically binds the asserted shop/topic to the payload rather than only the raw body. Alternatively/additionally, document and enforce that host applications must independently verify the `shop` header against a known/registered shop before trusting `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker creates their own free Shopify development store and installs the target app (`api_secret_key` is shared by the app across all shops).
2. Attacker triggers a webhook topic with a static/predictable body (e.g., an event whose payload the attacker controls or that is topic-agnostic), capturing the genuine `raw_body` and `x-shopify-hmac-sha256` value sent by Shopify to the app's webhook endpoint.
3. Attacker sends a new HTTP request to the same webhook endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` identical, but setting `x-shopify-shop-domain: victim-shop.myshopify.com` and/or `x-shopify-topic` to a different registered topic.
4. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) succeeds because it only checks `HMAC(api_secret_key, raw_body)`, which is unchanged.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) dispatches to the handler with `WebhookMetadata.new(topic: "victim-topic", shop: "victim-shop.myshopify.com", body: <attacker body>, ...)`, and the host app processes it as a legitimate webhook for the victim shop.
