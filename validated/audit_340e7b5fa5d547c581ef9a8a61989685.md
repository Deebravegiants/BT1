### Title
Excess native fee sent to `EvmHost.dispatch` is permanently lost, never refunded to caller - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch` accepts native token payment for POST request fees and swaps `msg.value` for `feeToken` via UniswapV2's `swapETHForExactTokens`. Any native ETH left over after the swap (i.e., excess sent above the exact fee needed) is refunded by the Uniswap router to `msg.sender` of the swap call — which is `EvmHost` itself, not the original caller/user. `EvmHost` has no logic to forward that refund back to the app or user that supplied the excess `msg.value`, so the excess is permanently stranded in the host contract.

### Finding Description
`dispatch()` performs the fee payment like this: [1](#0-0) 

`IUniswapV2Router02.swapETHForExactTokens` is called with the entire `msg.value`, requesting only `post.fee` output tokens. Per the standard UniswapV2 router implementation, any unused ETH (`msg.value - amounts[0]`) is refunded via `TransferHelper.safeTransferETH(msg.sender, ...)` — and since `EvmHost` itself is the caller of the router (not the upstream app/user), that refund lands on `EvmHost`, not on the party that originally supplied the native value. There is no code path in `dispatch()` that captures the swap's returned `amounts[0]` or forwards a refund of the unused portion back to `_msgSender()`/`post.payer`.

This is exactly the same bug class as the reported `WrappedBitcornNativeOFTAdapter.send` issue: the contract has intermediary logic that consumes `msg.value` for fee payment but silently keeps any overpayment instead of returning it, because the refund mechanism (here, the router's built-in refund) resolves to the wrong recipient (the contract itself instead of the paying party).

This is broadly reachable: every app built on Hyperbridge that pays native fees through `dispatch()` — `HyperFungibleToken.send`, `WrappedHyperFungibleToken.send`, `HyperbridgeLzEndpoint.send` (LayerZero message relay), and any custom `HyperApp` following the documented "Native Token Payment" pattern — forwards `msg.value` directly into `dispatch{value: msg.value}(...)`. Any user/app that doesn't send the *exact* required fee (which is common, since fee estimation quotes typically include a safety buffer, and `HyperbridgeLzEndpoint.quote()` explicitly applies "a generous 2x buffer" per its own comment) will lose 100% of the buffer/overpayment to `EvmHost` with each dispatch.

Notably, `IntentGatewayV2.placeOrder` and `ExtrinsicIntents` in the same codebase correctly handle this by capturing the swap's return value and refunding the leftover to the caller: [2](#0-1) 

This shows the codebase's authors are aware refunds must be explicitly forwarded — but `EvmHost.dispatch()`, the primitive used by essentially all other apps, was not fixed to do the same.

### Impact Explanation
Every user or contract dispatching a POST request and paying in native token loses any amount sent above the exact `post.fee` requirement, on every single call, with no recovery path (no `withdraw` function for stray native ETH was found in `EvmHost.sol`). Given that:
- `HyperbridgeLzEndpoint.quote()` deliberately quotes 2x the required fee "to absorb legacy per-byte protocol fees," meaning up to 50% of every LayerZero-relayed message's fee is permanently lost by design/oversight.
- Any `HyperFungibleToken`/`WrappedHyperFungibleToken` user who doesn't send the exact quoted fee (e.g., due to price movement between quote and send, or intentionally overpaying for safety) loses the difference.

This is a permanent, protocol-wide freezing/loss of user funds (native ETH) affecting a wide swath of applications built on Hyperbridge's core dispatch primitive, not an isolated app-level bug.

### Likelihood Explanation
High. This triggers on any normal usage pattern where the sender doesn't supply the exact wei-precise fee amount — which is the common case, since quotes are typically computed with buffers/slippage tolerance and native/feeToken exchange rates can move between quote and execution. No malicious actor or privileged role is required; a single unprivileged user calling `send()` on any native-fee-paying app is sufficient to trigger fund loss.

### Recommendation
In `EvmHost.dispatch()`, capture the amount actually spent by the swap and refund the difference to `_msgSender()` (or `post.payer`):
```solidity
if (msg.value > 0) {
    address[] memory path = new address[](2);
    address uniswapV2 = _hostParams.uniswapV2;
    path[0] = IUniswapV2Router02(uniswapV2).WETH();
    path[1] = feeToken();
    uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
        post.fee, path, address(this), block.timestamp
    );
    uint256 unspent = msg.value - amounts[0];
    if (unspent > 0) {
        (bool ok, ) = payable(_msgSender()).call{value: unspent}("");
        require(ok, "refund failed");
    }
}
```
Apply the equivalent fix to any other core dispatch entrypoints (e.g., `dispatchWithFeeToken`/`quote`-adjacent flows) that swap native ETH for fee tokens without capturing/refunding the unspent remainder.

### Proof of Concept
1. Call `HyperFungibleToken.quote(params)` to get `nativeFee`.
2. Call `HyperFungibleToken.send{value: nativeFee + X}(params)` for any `X > 0` (simulating slippage/buffer, or simply overpaying).
3. Trace through: `send()` forwards `msg.value` to `IDispatcher(_host).dispatch{value: nativeFee + X}(request)`.
4. In `EvmHost.dispatch()`, `swapETHForExactTokens{value: nativeFee + X}(post.fee, ...)` only needs `amounts[0] ≈ nativeFee` worth of ETH; the router refunds `X` back to `msg.sender`, which is `EvmHost`, not the calling `HyperFungibleToken` contract or the end user.
5. Assert `address(_host).balance` increased by `X` after the call — the excess sent is now stuck in `EvmHost` permanently, with no owner-only or user-facing function to reclaim it. [1](#0-0) [3](#0-2) [4](#0-3)
