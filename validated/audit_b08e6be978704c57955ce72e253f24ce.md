### Title
Webhook shop-domain and topic headers are not covered by the HMAC signature, allowing cross-tenant webhook forgery/replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` and `topic` directly from unauthenticated HTTP headers, while the HMAC signature verified by `Utils::HmacValidator` only covers the raw request body. This breaks the identity binding: `HMAC-verified bytes == raw_body` but `acted-upon identity == shop-domain/topic headers`, which are never part of the signed content.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile, `Request#shop` and `Request#topic` are read straight from the `X-Shopify-Shop-Domain` / `X-Shopify-Topic` headers with no cryptographic binding to the body or the HMAC: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then trusts `request.topic` and `request.shop` to route and label the payload for the handler: [3](#0-2) 

`HmacValidator.validate` computes `HMAC(api_secret_key, verifiable_query.to_signable_string)` and compares it to the `hmac-sha256` header — for webhooks this is `HMAC(api_secret_key, raw_body)` only: [4](#0-3) 

Because the app's `api_secret_key` is shared across every shop that has installed the app, any unprivileged user who installs the app on their own store receives genuine, correctly-signed webhooks (valid `hmac-sha256` for a given raw body). That attacker can then replay the exact same raw body/HMAC pair to the victim app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header with an arbitrary victim shop domain or a different topic. Since these headers are not part of `to_signable_string`, `HmacValidator.validate` still succeeds, and `Registry.process` will hand the attacker-controlled body to the handler labeled as if it came from the victim shop (`WebhookMetadata#shop`) and/or dispatched to a different topic handler than the one Shopify actually intended.

This is the "field acted on but not covered by the HMAC" identity-binding break: the equality the code implicitly assumes — `hmac-verified content == (shop, topic, body)` — actually only holds for `hmac-verified content == body`.

### Impact Explanation
This enables cross-tenant data injection: an attacker with no relationship to the victim's store can cause a host application to process forged webhook events "from" the victim shop (e.g., spoof `customers/data_request`, `app/uninstalled`, `orders/create`, etc., for a `shop` value they choose), since the shop identity is entirely attacker-controlled while the payload retains a valid signature. Depending on how the host application uses `WebhookMetadata#shop` (e.g., to look up/mutate per-tenant records), this can lead to cross-tenant data corruption or unauthorized actions attributed to a shop the attacker does not control — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Requires only that the attacker be able to install the app on a shop they control (a normal, unprivileged action for any public/installable app) and be able to POST to the app's webhook endpoint with custom headers (trivial, since delivery endpoints are typically public URLs). No leaked secrets, no privileged account, and no TLS interception are needed — the attacker uses their own legitimately-issued webhook body/HMAC and simply changes unauthenticated headers.

### Recommendation
Include `shop-domain` and `topic` (and ideally `webhook-id`, `api-version`) in the signed/verified content, or otherwise cryptographically bind them to the verified payload before trusting them — e.g., verify that the header-derived shop matches a shop that's actually expected to be sending this webhook (via a stored per-shop mapping) rather than trusting the header value outright for identity purposes.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, a shop they legitimately control.
2. Attacker triggers/receives a genuine webhook (e.g. `orders/create`) with header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid_hmac_for_body>`.
3. Attacker resends the identical raw body and `X-Shopify-Hmac-Sha256` value to the victim host app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate(request)` at `lib/shopify_api/utils/hmac_validator.rb:12-31` succeeds because it only checks the raw body.
5. `Registry.process` at `lib/shopify_api/webhooks/registry.rb:188-200` calls the topic handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)`, and the host application processes the forged event as belonging to the victim shop.
