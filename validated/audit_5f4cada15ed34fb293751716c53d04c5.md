### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying an HMAC over the raw request body, while the `shop` identity used to dispatch the webhook payload to application handlers is taken from an HTTP header that is never included in the signed material. An attacker who can obtain one validly-signed webhook (e.g. by installing the app on their own store and receiving a legitimate webhook for it) can replay that same body/HMAC pair while substituting the `shopify-shop-domain` header for a victim shop, and the gem will accept it as authentic.

### Finding Description
`Webhooks::Registry.process` verifies authenticity with: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, and `hmac`, `shop`, `topic`, `webhook_id`, `api_version` are all pulled independently from HTTP headers: [3](#0-2) 

The `shop` value is never part of the signed string, so the HMAC only proves "this body was signed with the app secret" — it proves nothing about which shop the header claims to be from. Because Shopify's webhook HMAC secret (`client_secret`) is shared across every shop that has the app installed, any shop that is a legitimate app tenant can generate a validly-HMAC'd payload for itself, then replay the exact same `raw_body`/`hmac` pair to the app's webhook endpoint with the `shopify-shop-domain` (or `x-shopify-shop-domain`) header changed to any other shop's domain. `Registry.process` will pass HMAC validation and invoke the registered handler with `WebhookMetadata` built from the attacker-controlled `request.shop`: [1](#0-0) 

The equality that should hold is: `shop_verified_by_hmac == shop_used_to_key_application_state`. In practice, `shop` is never part of `to_signable_string`, so the shop the handler receives is completely unauthenticated relative to the signature — only the JSON body content is authenticated, not its attribution to a specific tenant.

### Impact Explanation
This breaks the tenant boundary the HMAC check is meant to enforce for host applications relying on `WebhookMetadata#shop` to select which shop's session/data to act on (a documented, intended usage pattern for this gem's webhook processing API). An attacker with legitimate access to only their own shop's app installation can produce webhook deliveries that the gem accepts as coming from an arbitrary other shop, letting them drive the host application's webhook handlers to read, write, or delete data keyed by a victim shop — a cross-tenant access.

### Likelihood Explanation
Any merchant/developer who installs the target app on a store they control receives real, validly signed webhooks from Shopify for that store. Forging the `shopify-shop-domain` header on a replayed request is a simple HTTP-level change and requires no credentials, private keys, or the app's `client_secret` beyond what the attacker already legitimately possesses as an app tenant.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) in the signed material verified against the HMAC, or otherwise cryptographically bind the shop-domain header to the signature (Shopify does not natively support this, so at minimum the gem/host app should cross-check the `shop` header against a shop known to be associated with the specific webhook subscription/session before trusting it, rather than treating an HMAC-valid body as proof of shop identity).

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; capture a legitimate webhook request, e.g. body `{"id":1}` with headers `x-shopify-hmac-sha256: <valid-hmac-of-body>`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`.
2. Replay the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `@raw_body` against the HMAC — passes.
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, causing the host app to act as though `victim.myshopify.com` sent this webhook.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
