### Title
Legacy Bitcoin Cash addresses accepted without base58Check checksum verification - (File: packages/intents-sdk/src/lib/validateAddress.ts)

### Summary
`validateBchAddress` accepts legacy 1-/3-prefixed BCH addresses via a pure regex check on length/charset, with no base58Check checksum verification, unlike the sibling functions `validateBtcBase58Address`, `validateDashAddress`, and `validateLitecoinBase58Address` which all decode and verify the sha256d checksum. A user withdrawing to a BCH legacy address with a corrupted checksum (e.g. a typo) will pass validation and the funds will be sent to that malformed, unrecoverable destination.

### Finding Description
The broken equality: "an address accepted by `validateAddress(address, Chains.BitcoinCash)`" should equal "an address that is a legitimate base58Check-encoded BCH destination (valid checksum)." For every other base58Check chain in this file — Bitcoin (`validateBtcBase58Address`, lines 140-158), Tron (`validateTronBase58Address`, lines 384-403), Litecoin (`validateLitecoinBase58Address`, lines 537-567), Dash (`validateDashAddress`, lines 801-831) — the code decodes with `base58.decode`, splits payload/checksum, and compares `sha256(sha256(payload))` against the trailing 4 bytes. For BitcoinCash's legacy branch (lines 214-221), the code only runs:

```
/^1[1-9A-HJ-NP-Za-km-z]{25,34}$/.test(address) ||
/^3[1-9A-HJ-NP-Za-km-z]{25,34}$/.test(address)
``` [1](#0-0) 

This never decodes base58 or checks the checksum bytes at all, so any string of correct length using the base58 alphabet and starting with `1` or `3` passes — including one with a bit-flipped checksum, or one with an entirely wrong 20-byte hash160 that happens to line up with garbage checksum bytes.

Call path: `PoaBridge.validateWithdrawal` calls `validateAddress(args.destinationAddress, assetInfo.blockchain)` [2](#0-1) , which for `Chains.BitcoinCash` dispatches to `validateBchAddress` [3](#0-2) . If this returns `true`, the withdrawal proceeds and `createWithdrawIntentPrimitive`/`createWithdrawMemo` encode the raw address into `memo: "WITHDRAW_TO:<address>"` verbatim [4](#0-3) . No downstream code re-verifies the checksum before this memo is embedded in the signed `ft_withdraw` intent.

Attacker input: any user constructs a 25-34 character base58-alphabet string starting with `1` or `3` whose last 4 bytes (after decoding) do not match `sha256d(payload)[0:4]`. This is trivially producible without knowing any real private key or hash160.

### Impact Explanation
The signed NEAR intent embeds a `memo` field containing an unchecksummed, unverifiable destination address. The relayer/bridge operator that services this "WITHDRAW_TO" memo would forward the raw string to the actual BCH network layer, where a checksum-invalid legacy address is either (a) rejected by that layer (in which case this is a stuck/failed withdrawal — High) or (b) — if the off-chain relay logic decodes hash160 loosely instead of validating checksum — funds are sent to a garbage/attacker-uncontrolled hash, which is unrecoverable (Critical, matching "funds delivered to a wrong address ... with no recovery"). This SDK-level check is the only checksum verification present on this path within the repo; whether the POA bridge backend itself re-validates checksum is outside this repo's scope, but the described bug is a genuine correctness violation of documented invariant ("format-only validation" is expected to still gate implausible/corrupted addresses the way the Bitcoin, Litecoin, Dash, Tron variants do).

### Likelihood Explanation
Precondition is simply a PoA withdrawal to a BitcoinCash asset with an attacker/user-supplied legacy-format address — no privileged access needed, reachable by any SDK caller supplying `destinationAddress`. Cost is zero (just typing/generating a string). It is trivially repeatable on every call.

### Recommendation
In `validateBchAddress`'s legacy branch (validateAddress.ts lines 214-221), decode the address with `base58.decode`, verify total length is 25 bytes, verify version byte is `0x00` (P2PKH) or `0x05` (P2SH), and verify the last 4 bytes equal `sha256(sha256(payload)).subarray(0,4)`, mirroring `validateBtcBase58Address`.

### Proof of Concept
```ts
// validateAddress.spec.ts
import { validateBchAddress } from "./validateAddress";
import { base58 } from "@scure/base";
import { sha256 } from "@noble/hashes/sha2";

test("legacy BCH address with corrupted checksum should be rejected", () => {
  // Build a valid P2PKH payload (version 0x00 + 20-byte hash160)
  const version = 0x00;
  const hash160 = new Uint8Array(20).fill(1);
  const payload = new Uint8Array([version, ...hash160]);
  const goodChecksum = sha256(sha256(payload)).subarray(0, 4);
  const corruptChecksum = new Uint8Array(goodChecksum);
  corruptChecksum[0] ^= 0xff; // flip bits -> invalid checksum

  const corruptedAddressBytes = new Uint8Array([...payload, ...corruptChecksum]);
  const corruptedAddress = base58.encode(corruptedAddressBytes);

  // EQUALITY CHECK: a correctly-checksummed BTC-style base58 address is rejected by BTC path
  const btcValidAddressBytes = new Uint8Array([...payload, ...goodChecksum]);
  // (not applicable here directly, but for BCH:)

  // Left side: SDK claims address is a well-formed destination
  const accepted = validateBchAddress(corruptedAddress);

  // Right side: ground truth — checksum does NOT match
  const decoded = base58.decode(corruptedAddress);
  const actualPayload = decoded.subarray(0, 21);
  const actualChecksum = decoded.subarray(21, 25);
  const expectedChecksum = sha256(sha256(actualPayload)).subarray(0, 4);
  const checksumValid = Buffer.from(actualChecksum).equals(Buffer.from(expectedChecksum));

  expect(checksumValid).toBe(false);     // ground truth: checksum is invalid
  expect(accepted).toBe(true);           // BUG: current code still accepts it
});
```
This demonstrates the equality break: `validateBchAddress(address) === true` while `checksumValid === false`, confirming legacy BCH addresses bypass checksum verification unlike every other base58Check chain in the same file.

export function validateBchAddress(address: string): boolean {
	// Legacy address format (same as Bitcoin)
	if (
		/^1[1-9A-HJ-NP-Za-km-z]{25,34}$/.test(address) ||
		/^3[1-9A-HJ-NP-Za-km-z]{25,34}$/.test(address)
	) {
		return true;
	}

function createWithdrawMemo({
	receiverAddress,
	xrpMemo,
}: {
	receiverAddress: string;
	xrpMemo: string | undefined;
}) {
	// Strip "bitcoincash:" prefix from BCH CashAddr addresses
	const normalizedAddress = receiverAddress
		.toLowerCase()
		.startsWith("bitcoincash:")
		? receiverAddress.slice("bitcoincash:".length)
		: receiverAddress;

	const memo = ["WITHDRAW_TO", normalizedAddress];

	if (xrpMemo != null && xrpMemo !== "") {
		memo.push(xrpMemo);
	}

	return memo.join(":");
}
