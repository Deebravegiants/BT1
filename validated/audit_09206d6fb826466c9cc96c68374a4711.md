### Title
Unbounded BEEFY Signature/Vote Array Drives Uncontrolled secp256k1/ECDSA Recovery Before Rejection - (File: modules/consensus/beefy/verifier/src/lib.rs)

### Summary
Both the Rust BEEFY consensus verifier and its Solidity `EcdsaBeefy` counterpart accept a relayer-supplied signature/vote count with no upper bound before performing expensive elliptic-curve public-key recovery for every entry. This mirrors the `jose2go` CWE-400 pattern: an attacker-controlled iteration count (`p2c` there, signature count here) drives costly CPU work before the check that would ultimately reject the malformed input runs.

### Finding Description
`verify_mmr_update_proof` reads `signatures_length = mmr.signed_commitment.signatures.len()` and only checks a *lower* bound via `check_participation_threshold(signatures_length as u32, authority_set.len)` [1](#0-0) . There is no upper bound tying `signatures_length` to `authority_set.len`, and no de-duplication of `sig.index`. The function then iterates over every signature and calls the expensive `secp256k1_recover` for each entry: [2](#0-1) 

Only after this entire loop completes does the code validate authority-set membership via a merkle multi-proof, which is where duplicate/forged indices would actually be rejected: [3](#0-2) 

This function (`verify_mmr_update_proof` → `verify_consensus`) is the entry point invoked by `BeefyConsensusClient::verify_consensus`, which is the `ConsensusClient` implementation wired into `pallet-ismp`'s consensus-update path and reachable by any relayer submitting a BEEFY consensus proof: [4](#0-3) .

The same shape exists in the Solidity `EcdsaBeefy` verifier: `sigLen` is taken directly from `relayProof.signedCommitment.votes.length` and used to size and iterate an `ECDSA.recover` loop before `MerkleMultiProof.VerifyProof` (which would catch bogus/duplicate authority indices) ever runs, gated only by a lower-bound `checkParticipationThreshold` check: [5](#0-4) .

In neither implementation is `signatures_length`/`sigLen` capped to (or checked against duplicates within) the actual authority-set size before the expensive cryptographic recovery loop executes.

### Impact Explanation
An unprivileged relayer can submit a consensus update/proof whose signature or vote array is padded far beyond the honest authority set size (duplicating a single valid signature/vote many times, or including alongside it many bogus-but-structurally-valid signature bytes that still trigger a full `secp256k1_recover`/`ECDSA.recover` computation). This forces the node (in the Rust off-chain/runtime verifier) or the EVM light client (in the Solidity path) to perform a number of expensive elliptic-curve recoveries proportional to the attacker-chosen array length before the merkle-multi-proof membership check — which is the actual gate against forged/duplicate authorities — is ever reached. In the Substrate/pallet-ismp path this can consume disproportionate CPU/validation time per submitted consensus message relative to its legitimate cost, directly analogous to the reported `jose2go` CWE-400 CPU-exhaustion class, and can degrade or stall processing of the BEEFY consensus-update route for the affected chain (a route-availability/DoS impact), rather than any funds-theft or forgery outcome (the merkle-proof check would still ultimately reject the bogus set).

### Likelihood Explanation
Likelihood is limited by extrinsic/calldata size limits (which bound how many signature entries can be packed into one message) and, on the EVM side, by the block gas limit (which would eventually revert an overly large `votes` array on its own, capping — but not eliminating — the wasted work an honest node/relayer must pay for). Still, any unprivileged party who can submit a consensus-update proof can trigger this without needing a valid authority set beyond one real signature to satisfy the *lower*-bound participation check, making the trigger condition trivial to reach; the actual amplification factor depends on max extrinsic/calldata size versus per-recovery cost.

### Recommendation
- Cap `signatures_length` / `sigLen` to a small fixed multiple of (or exactly) `authority_set.len` / `authoritySet.len` before performing any `secp256k1_recover` / `ECDSA.recover`, rejecting proofs that exceed this bound immediately.
- Reject duplicate `sig.index` / `vote.authorityIndex` entries up front (before the recovery loop), since a legitimate BEEFY commitment can have at most one signature per authority index.
- Perform the merkle multi-proof membership sizing/validation check (or at minimum a cheap sanity check on cardinality/duplicates) prior to the costly cryptographic recovery loop, so malformed/oversized proofs are rejected cheaply.

### Proof of Concept
1. Construct a `ConsensusMessage`/`MmrProof` (or Solidity `RelayChainProof`) whose `signed_commitment.signatures` (`votes`) array contains one genuine, currently-valid authority signature repeated `N` times (or `N` distinct 65-byte signature blobs, valid or not, each of which is syntactically able to be passed to `secp256k1_recover`/`ECDSA.recover`), where `N` is chosen as large as the extrinsic size limit (Substrate) or calldata/gas limit (EVM) allows.
2. Submit this as an unsigned/relayed consensus update through `BeefyConsensusClient::verify_consensus` (or the `EcdsaBeefy.verify` entry point).
3. Observe that `verify_mmr_update_proof` / `verifyMmrUpdateProof` performs `N` full public-key-recovery operations — each with clean pass-through of `check_participation_threshold`, since duplicating one valid signature/vote index still exceeds the 2/3+1 lower-bound threshold — before the merkle multi-proof check at the end rejects the forged/duplicated authority set, at which point all `N` recoveries have already been computed.
