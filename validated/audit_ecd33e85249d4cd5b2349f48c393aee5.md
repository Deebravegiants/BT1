## Title
Tron `IntentGatewayV2.placeOrder` credits escrow with pre-transfer amounts, causing insolvency for fee-on-transfer tokens - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder()` computes the escrowed/committed token amount (`reducedInputs`) from the caller-supplied `order.inputs[i].amount` *before* any token transfer occurs, and then performs a plain `safeTransferFrom` without verifying the amount actually received by the contract. For fee-on-transfer (or otherwise deflationary) ERC20 tokens, this causes the gateway to record and later release/redeem more tokens than it actually holds.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `reducedInputs` (the amount that is committed to the order hash and stored in the `_orders` escrow mapping) is derived purely from the nominal `order.inputs[i].amount` supplied by the user: [1](#0-0) 

Later, in the non-predispatch path, the contract pulls tokens with a single `safeTransferFrom` call and immediately credits escrow with the pre-computed `reducedInputs[i].amount`, without measuring the actual balance received: [2](#0-1) 

The same pattern is present in the predispatch branch, where dust is measured relative to `requiredAmount` (still the nominal amount) but the escrow credit again uses `reducedInputs[i].amount`, not the actually-swept balance: [3](#0-2) 

This is precisely the bug class from the referenced Allo `Allo.sol#_fundPool` report: the protocol credits an internal accounting balance based on the pre-fee/nominal transfer amount rather than the actual tokens received, which is incorrect whenever the token deducts a fee on transfer.

By contrast, the primary EVM `IntentGatewayV2.sol` in this same repository was hardened against exactly this issue: it snapshots `balanceOf` before and after each `safeTransferFrom`/sweep and mutates `order.inputs[i].amount` to the actual delta before computing the commitment and any protocol-fee-reduced escrow amount: [4](#0-3) 

The Tron deployment was not updated with this fix, leaving it vulnerable to the exact accounting flaw described in the external report.

### Impact Explanation
Any user can call `placeOrder` with a fee-on-transfer (or deflationary/rebasing-down) ERC20 as an input token. The gateway's `_orders[commitment][token]` mapping will record more tokens than it actually received and holds. When the order is later filled/redeemed and the escrow is released to the filler/beneficiary (via the redeem-escrow request path), the contract will attempt to pay out the recorded (inflated) amount, which can exceed the token balance actually available. This can:
- Cause the redemption to fail (permanently freezing legitimately escrowed funds and any co-mingled dust for that token), or
- Drain the balance backing *other* orders' escrow in the same token, since the mapping merely tracks "owed" units, not conserved supply, causing shared insolvency across users of that token.

This is a concrete accounting/insolvency vulnerability within the reachable intents escrow path.

### Likelihood Explanation
Reachable directly by any unprivileged user submitting a single `placeOrder` transaction with a fee-on-transfer token as an input — no special privileges required. Fee-on-transfer tokens are common in practice (many deflationary/rebase/tax tokens exist on EVM-compatible chains including Tron), making this readily triggerable whenever the gateway allows an arbitrary ERC20 input.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: measure `balanceOf(address(this))` immediately before and after each token pull (and after any predispatch sweep), mutate `order.inputs[i].amount` to reflect the actual amount received, and only then compute `reducedInputs`/protocol fees and the commitment hash from the *actual* received amount rather than the nominal, user-specified amount.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 token (e.g., 1% fee burned on every transfer) as used in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`'s `FeeOnTransferToken` test helper.
2. Call `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs[0] = {token: FOT, amount: 1000e18}`.
3. `reducedInputs[0].amount` is computed as `1000e18` (or `1000e18` minus protocol fee) at line 362-370, before the transfer.
4. `safeTransferFrom(msg.sender, address(this), 1000e18)` at line 459 actually delivers only `990e18` to the gateway (1% burned in transfer).
5. `_orders[commitment][FOT] += reducedInputs[0].amount` at line 463 credits `1000e18` (or fee-reduced nominal amount) even though the gateway's actual FOT balance only increased by `990e18`.
6. When the escrow is later redeemed for the full recorded amount, the payout can exceed the contract's actual token balance, reverting/blocking legitimate withdrawals or depleting balance backing other users' orders in the same token.
