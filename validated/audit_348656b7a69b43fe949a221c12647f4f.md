### Title
Webhook `shop` (and `topic`/`api-version`/`webhook-id`) identity fields are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature over the raw request body only, while the shop identity (`shop-domain` header) that the registry hands to the app's webhook handler is taken from an unsigned HTTP header. This breaks the binding `shop (authenticated by HMAC) == shop (acted on by handler)`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` (invoked from `Registry.process`) verifies the HMAC exclusively against that signable string: [2](#0-1) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers, none of which are part of the signed material: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately forwards `request.shop` (the unauthenticated header) to the application's handler as the tenant identity: [4](#0-3) 

This is structurally the same class of bug as the reNFT report: an invariant check (HMAC integrity) is scoped too narrowly, so a field that is "acted on" (the `shop` used to key the handler's tenant-scoped logic) is not covered by the binding check that is supposed to guarantee its authenticity (the HMAC).

Concretely, the identity equality that should hold is:

`shop bound by HMAC == shop delivered to WebhookMetadata`

Before the request reaches `Registry.process`, both sides are equal only because Shopify's own delivery infrastructure sets consistent headers/body. But once an attacker can produce *any* valid `(raw_body, hmac)` pair — trivially obtainable by owning/operating their own Shopify dev store and observing genuine webhook deliveries the gem's app receives for that shop — they can replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. `HmacValidator.validate` still passes (it only checks the body), and `Registry.process` hands the handler `shop: <attacker-chosen value>` together with the (unrelated) body content.

### Impact Explanation
This crosses a tenant boundary: an unprivileged actor who legitimately owns one Shopify store (or merely captures one authentic webhook delivery for it) can make the host application process/store that event under a different, victim shop's identity, since the gem provides no protection binding the header-derived `shop` to the HMAC-verified payload. Depending on how the host app uses `WebhookMetadata#shop` (e.g., looking up the tenant's session/access token, writing to a shop-scoped record, or driving app logic keyed by shop), this enables cross-tenant data corruption/confusion — matching the Critical "cross-tenant access" impact category, since the gem itself supplies no guarantee that the `shop` field it exposes to the handler is authenticated.

### Likelihood Explanation
Moderate-to-high: exploitation only requires network ability to send a crafted HTTP request to the app's public webhook endpoint plus possession of one genuine `(body, hmac)` pair, which is obtainable by any developer with their own free/dev Shopify store (no access token, no `api_secret_key`, and no privileged account on the victim's shop are needed). This is fully reachable through the gem's own documented webhook-processing API (`Registry.process`), not a misuse of undocumented behavior.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) in the HMAC-signed material, or otherwise cryptographically bind them to the body (e.g., have `to_signable_string` concatenate the canonicalized headers with the raw body before computing/verifying the signature), so that the shop asserted to the handler cannot be swapped independently of the signed payload.

### Proof of Concept
1. Attacker registers a free Shopify development store `attacker.myshopify.com` and installs the target app, so the app's registered webhook endpoint legitimately receives, e.g., an `orders/create` webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(secret, B)`), and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays an HTTP POST to the same app endpoint with the identical body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a request object; `Registry.process` calls `Utils::HmacValidator.validate(request)`: [5](#0-4) 
   The validator only checks `B` against `H`, which still matches, so the check passes.
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: <attacker's order data>, ...)`, i.e., the app processes attacker-controlled data under the victim shop's identity.
