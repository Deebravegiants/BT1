### Title
Silent truncation of accumulated relayer fees from U256 to u128 during substrate withdrawal causes permanent loss of funds - (File: modules/pallets/relayer/src/withdrawal.rs)

### Summary
`pallet-ismp-relayer`'s `withdraw` function reads the relayer's accumulated fee balance as a `U256` from the `Fees` storage map and, for substrate destination chains, truncates it to `u128` via `.low_u128()` before dispatching the payout message, then unconditionally zeroes the full `U256` balance in storage. If the accumulated balance ever exceeds `u128::MAX`, the relayer is paid only the low 128 bits while the entire (larger) balance is erased, permanently freezing/losing the difference. This mirrors the reported bug class (an unchecked/incorrect-width arithmetic operation on an accounting balance that causes accounting corruption in a claim/withdrawal flow).

### Finding Description
`Fees` is a `StorageDoubleMap<StateMachine, Vec<u8> (address), U256>` [1](#0-0) , accumulated via `+=` on the full-width `U256` in `accumulate` and `accumulate_fee_and_deposit_event` [2](#0-1) [3](#0-2) . Any relayer address's fee balance can, in principle, exceed `u128::MAX` given enough accumulated fee-bearing message deliveries (each `total_fee` from `validate_results` is itself `U256`, unconstrained by any per-call cap) [4](#0-3) .

In `withdraw`, the entire stored `U256` is read into `available_amount` [5](#0-4) . For the substrate destination branch, the withdrawal message encodes `amount: available_amount.low_u128()` — a lossy truncation that silently drops the high bits of the balance rather than checking that the value fits or capping the withdrawal at `u128::MAX` [6](#0-5) . Regardless of how much was actually included in the dispatched message, `Fees::<T>::insert(...,  U256::zero())` immediately zeroes the *entire* balance [7](#0-6) , and the `Withdraw` event still reports the full, un-truncated `available_amount` [8](#0-7) , masking the discrepancy from off-chain observers/indexers.

This is directly analogous to the referenced report: an accounting field is advanced/consumed using a narrower integer type than the value it's tracking, and the mismatch between the "recorded" claimed amount and the "actually paid" amount corrupts accounting — in this case resulting in unrecoverable fund loss instead of over-claiming, but rooted in the identical class of bug (unsafe narrowing cast on a balance during a claim/withdraw operation reachable by any relayer, an unprivileged actor).

### Impact Explanation
Any relayer whose accumulated cross-chain delivery fees (denominated in the fee token's smallest unit, typically 18-decimals ERC-20 stablecoins) exceed `u128::MAX` (~3.4 × 10^38) on a given (address, destination state machine) pair will have the excess permanently and silently destroyed on withdrawal to a substrate destination — the `Fees` entry is zeroed but only the truncated low-128-bit amount is ever paid out. This is a fund-freezing/loss bug reachable via a normal, unprivileged relayer withdrawal extrinsic (`withdraw`), which is unsigned but requires only a valid relayer signature — no privileged role is involved.

### Likelihood Explanation
Reaching `u128::MAX` for a single relayer/chain pair requires an extraordinarily large accumulated balance (values that would represent an implausible volume of fees even at 18-decimal precision), so this is a low-probability event under normal operating conditions. However, the code path is reachable by any relayer through routine calls (`accumulate` + `withdraw`) with no additional privilege, and the truncation is completely silent (no revert, no saturating clamp, no event discrepancy flag), meaning it would go undetected until funds are already lost. Given the strict "no low severity" instruction and the concrete, provable loss-of-funds mechanism with exact root cause identified, this is assessed as valid but with practically low likelihood of triggering absent an extreme fee-accumulation scenario or a griefing/overflow vector not fully ruled out by this review (e.g., a compromised/duplicated proof pipeline artificially inflating `total_fee` — this indexer/tesseract-side amplification was not verified within available time and is noted as an open question).

### Recommendation
Replace the unchecked `.low_u128()` truncation in `modules/pallets/relayer/src/withdrawal.rs` with a checked conversion (e.g. `available_amount.try_into().map_err(|_| Error::<T>::...)?`) that rejects (or splits into multiple withdrawals) any balance that does not fit into `u128`, and only zero out the portion of the `Fees` entry that was actually included in the dispatched withdrawal message rather than always zeroing the full `U256` value.

### Proof of Concept
1. Through many `accumulate_fees` calls (unprivileged, unsigned extrinsic), attribute delivery fees to a single relayer address / destination-state-machine pair until `Fees::<T>::get(dest_chain, relayer)` exceeds `u128::MAX`.
2. Relayer calls `withdraw` targeting a substrate `dest_chain`.
3. `withdraw` reads `available_amount` (full `U256`, > `u128::MAX`), computes `available_amount.low_u128()` for the dispatched `WithdrawalRequest.amount`, dispatches the ISMP POST request with only the truncated amount, then executes `Fees::<T>::insert(dest_chain, relayer, U256::zero())`, discarding the untruncated remainder.
4. The relayer's destination-chain payout equals only the low 128 bits of the true balance; the remainder is unrecoverable since the source-chain `Fees` accounting has already been reset to zero. [9](#0-8)
