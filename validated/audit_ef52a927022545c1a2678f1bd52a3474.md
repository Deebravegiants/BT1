### Title
Unrestricted swap-route contracts can add unauthorized wallet transfers to the caller’s signed authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
Controller strategy entrypoints accept caller-supplied route bytes and forward them to the configured router without binding the route to trusted pool contracts. A malicious pool can execute arbitrary code during the route and invoke `token.transfer(victim, attacker, amount)`; Soroban records that transfer as a child of the victim’s original `swap_collateral` authorization, so signing the poisoned simulation result permits theft of unrelated wallet assets. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`swap_collateral(caller, account_id, current, amount, new, swap)` authenticates `caller`, withdraws collateral into the controller, and passes the opaque `swap` bytes into `swap_tokens`. [4](#0-3) [5](#0-4)  `swap_tokens` authorizes only the controller’s exact input transfer to the configured router, then invokes `execute_strategy(controller, amount_in, swap)`. [6](#0-5) 

The route payload’s asset registry supplies the pool address for each hop, while its opcode selects only the venue adapter; the pool itself is not restricted to a deployed-pool registry or allowlist. [7](#0-6) [8](#0-7)  For a Soroswap hop, the router calls the supplied pool’s `get_reserves` and `swap` functions directly. [2](#0-1) [9](#0-8) 

Consequently, a contract selected by route data can run attacker-controlled logic beneath the victim’s controller invocation. The repository’s regression test demonstrates that a rogue pool’s `token.transfer(victim, attacker, amount)` is recorded as a child invocation under the victim’s `swap_collateral` entry and succeeds when that poisoned tree is signed. [10](#0-9) [3](#0-2) [11](#0-10) 

### Impact Explanation
An attacker can steal tokens held directly by a strategy caller, including tokens unrelated to the lending position and not included in the swap input. The measured input, output, solvency, and refund checks only bound the routed position assets; they do not bound an extra child `transfer` authorized by the caller’s signature. [12](#0-11) [13](#0-12) [14](#0-13) 

### Likelihood Explanation
The attack requires inducing a user or automated client to sign the authorization tree produced by simulating a malicious route. Because `swap` is opaque XDR route data and the rogue transfer appears as a nested authorization rather than a controller argument, clients that display only the top-level call or route economics can sign it. An unprivileged attacker can deploy the pool, construct the route, obtain the victim-signed authorization entry through the normal simulation/signing flow, and submit the transaction. [15](#0-14) [16](#0-15) [11](#0-10) 

### Recommendation
Restrict route pool addresses to a governance-maintained registry of audited venue contracts, rather than accepting arbitrary addresses from route bytes. Clients should also simulate every strategy, decode the complete authorization tree, and reject any child invocation other than the expected input-token transfer to the router. The controller-side exact-input authorization should remain, but it does not constrain authorizations requested by route-selected code for the user’s unrelated wallet assets. [17](#0-16) [1](#0-0) 

### Proof of Concept
1. The attacker deploys a contract implementing `get_reserves() -> (i128, i128)` and `swap(amount_0_out, amount_1_out, to)`. Its `swap` sends a sufficient amount of the configured `token_out` to the router and calls `token.transfer(victim, attacker, victim_balance)` on an unrelated wallet token. [2](#0-1) [18](#0-17) 
2. The attacker encodes a one-hop `StrategyPayload` whose `assets` registry contains the route input token, output token, and rogue pool address, and whose instruction selects `Swap(Soroswap)` with the rogue-pool index. [7](#0-6) [8](#0-7) 
3. The victim is induced to call `swap_collateral(victim, account_id, current = HubAssetKey(USDC), amount, new = HubAssetKey(ETH), swap = malicious_payload)`. [15](#0-14) 
4. Simulation records `token.transfer(victim, attacker, victim_balance)` as a child of the victim’s `swap_collateral` authorization. [16](#0-15) 
5. If the victim signs that tree, the attacker submits the transaction; the victim receives a valid swap while the unrelated wallet token balance is transferred to the attacker. [14](#0-13) [11](#0-10)

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
