Audit Report

## Title
`InboundXcmpSuspended::try_insert` failure on `MaxInboundSuspended` exhaustion silently leaves excess channels unsuspended, degrading backpressure - (File: cumulus/pallets/xcmp-queue/src/lib.rs)

## Summary
`Pallet::on_queue_changed` suspends a sibling channel by sending a `ChannelSignal::Suspend` and recording the para in `InboundXcmpSuspended` via `try_insert`, bounded by `T::MaxInboundSuspended` [1](#0-0) . If enough distinct `ParaId`s simultaneously exceed `suspend_threshold` to fill `MaxInboundSuspended`, subsequent `try_insert` calls fail and are only logged, leaving those channels without local suspension bookkeeping even though the `Suspend` signal was already sent to the remote side. However, the per-channel `drop_threshold` enforcement in `enqueue_xcmp_messages` via `get_batches_footprints`/`search_best_by` is independent of `InboundXcmpSuspended` and always caps queue growth for any individual channel regardless of suspension bookkeeping state [2](#0-1) .

## Finding Description
The suspend mechanism has two independent effects when `fp.ready_pages >= suspend_threshold`: sending `ChannelSignal::Suspend`, and, only on success, inserting `para` into `InboundXcmpSuspended` bookkeeping [1](#0-0) . If `try_insert` fails because `InboundXcmpSuspended` (bounded by `T::MaxInboundSuspended`) is already full, the signal is still sent, but the channel is not tracked locally as suspended, so the resume branch (`suspended_channels.contains(&para)`) never fires for it later, and `on_queue_changed` will keep re-attempting `Suspend` signals whenever the same channel exceeds `suspend_threshold` again [3](#0-2) .

Critically, the actual bound on per-channel queue growth is enforced independently by `enqueue_xcmp_messages`, which computes `get_batches_footprints(sender, xcms, drop_threshold)` and enqueues only the best batch keeping total pages within `drop_threshold`; excess messages are dropped and logged, regardless of `InboundXcmpSuspended` membership [4](#0-3) . This confirms the `drop_threshold` cap is a structural limit checked unconditionally on every enqueue call, not gated by suspension bookkeeping success.

## Impact Explanation
The confirmed consequence is limited to backpressure signaling degradation, not unbounded queue growth: a channel whose `try_insert` fails loses the ability to be auto-resumed via the `suspended_channels.contains(&para)` check, and will repeatedly resend redundant `Suspend` signals, consuming outbound bandwidth/weight. The claimed severe outcome — "unbounded" or uncontrolled growth past `drop_threshold` — does not occur, because `enqueue_xcmp_messages` enforces the page cap unconditionally for every sender on every call, independent of `InboundXcmpSuspended` state. This is a minor availability/efficiency degradation for a subset of channels under an extreme, resource-intensive precondition, not a fund-loss, consensus-break, or unbounded-growth vulnerability.

## Likelihood Explanation
Triggering this requires an attacker to control or influence enough distinct `ParaId`s (up to `MaxInboundSuspended`, typically configured generously in production runtimes) to simultaneously push that many channels past `suspend_threshold` within overlapping blocks — a large-scale, multi-chain resource requirement rather than a single-account exploit. This is only plausible in a permissionless parachain/parathread environment with many attacker-controlled chains and sustained message flooding across all of them concurrently.

## Recommendation
Decouple remote suspend-signal state from local bookkeeping capacity, e.g., retry `try_insert` in later blocks, raise `MaxInboundSuspended` to a safe ceiling, or replace the bounded set with an unbounded `StorageMap` keyed by `ParaId` so suspension state can never be lost to capacity exhaustion, while keeping `drop_threshold` as the independent hard backstop it already is.

## Proof of Concept
Add a test to `cumulus/pallets/xcmp-queue/src/tests.rs`: configure mock `T::MaxInboundSuspended = N`; call `on_queue_changed` for `N` distinct `ParaId`s with `fp.ready_pages >= suspend_threshold`, verifying all are inserted into `InboundXcmpSuspended`; then call it for an `N+1`-th `ParaId` with the same footprint and assert (a) `try_insert` fails and the channel is absent from `InboundXcmpSuspended`, (b) the `Suspend` signal was still queued via `send_signal`, and (c) repeated calls to `enqueue_xcmp_messages` for that channel never push its page count past `drop_threshold`, confirming the drop cap holds independent of the suspension-bookkeeping failure.

	fn enqueue_xcmp_messages<'a>(
		sender: ParaId,
		xcms: &[BoundedSlice<'a, u8, MaxXcmpMessageLenOf<T>>],
		is_first_sender_batch: bool,
		meter: &mut WeightMeter,
	) -> Result<(), ()> {
		let QueueConfigData { drop_threshold, .. } = <QueueConfig<T>>::get();
		let batches_footprints =
			T::XcmpQueue::get_batches_footprints(sender, xcms.iter().copied(), drop_threshold);

		let best_batch_footprint = batches_footprints.search_best_by(|batch_info| {
			let required_weight = T::WeightInfo::enqueue_xcmp_messages(
				batches_footprints.first_page_pos.saturated_into(),
				batch_info,
				is_first_sender_batch,
			);

			match meter.can_consume(required_weight) {
				true => core::cmp::Ordering::Less,
				false => core::cmp::Ordering::Greater,
			}
		});

		meter.consume(T::WeightInfo::enqueue_xcmp_messages(
			batches_footprints.first_page_pos.saturated_into(),
			best_batch_footprint,
			is_first_sender_batch,
		));
		T::XcmpQueue::enqueue_messages(
			xcms.iter().take(best_batch_footprint.msgs_count).copied(),
			sender,
		);

		if best_batch_footprint.msgs_count < xcms.len() {
			tracing::error!(
				target: LOG_TARGET,
				used_weight=?meter.consumed_ratio(),
				"Out of weight: cannot enqueue entire XCMP messages batch; \
				dropped some or all messages in batch."
			);
			return Err(());
		}
		Ok(())
	}
