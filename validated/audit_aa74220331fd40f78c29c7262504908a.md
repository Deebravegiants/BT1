The docs explicitly promise: `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" [1](#0-0) , and instructs apps to trust `data.shop` and `data.topic` directly for dispatch/business logic [2](#0-1) . ### Title
Webhook shop/topic identity spoofing via HMAC that only signs the request body, not the `X-Shopify-Shop-Domain`/`X-Shopify-Topic` headers - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, and `Utils::HmacValidator.validate` computes/compares the HMAC solely over that body [3](#0-2) [4](#0-3) . Meanwhile `request.shop` and `request.topic` are read directly, unauthenticated, from the `shopify-shop-domain` and `shopify-topic` headers [5](#0-4) , and `Registry.process` passes them straight into the handler after only checking the body HMAC [6](#0-5) . Because every shop that installs the app shares the same `api_secret_key`, any tenant can legitimately obtain a validly-signed webhook body for a given payload, then replay that same body with forged `shopify-shop-domain`/`shopify-topic` headers claiming to be a different shop/topic, and `HmacValidator.validate` still returns `true`.

### Finding Description
The identity binding that should hold is: `shop header used by handler == shop that the HMAC signature actually authenticates`. In this gem, the HMAC only binds the body bytes to the shared `api_secret_key`; it never binds `shop-domain` or `topic`. `Registry.process` treats a passing HMAC check as proof the whole request "did indeed come from Shopify" for that shop/topic combination (as the docs claim [1](#0-0) ), then constructs `WebhookMetadata` from unauthenticated header values and dispatches to the registered handler [6](#0-5) . An attacker who is a legitimate (even free/self-serve) installer of the app on their own store can capture a real, validly-signed webhook delivery for their own shop, then POST the identical raw body to the app's webhook endpoint with the `shopify-shop-domain` header swapped to a victim shop's domain (and/or the `shopify-topic` header swapped to a registered topic of their choosing). Since `to_signable_string` is only `@raw_body`, the signature still matches, `HmacValidator.validate` returns `true`, and the handler executes believing the event legitimately originated from the victim shop.

### Impact Explanation
This breaks the cross-tenant isolation the whole HMAC check exists to provide. Handlers are documented to key business logic and background jobs off `data.shop` and `data.topic` without additional verification [7](#0-6) , so a malicious merchant can inject fabricated "events" attributed to any other shop known to have installed the app (shop domains are typically public), e.g. triggering fulfillment, mandatory-compliance (`customers/redact`, `shop/redact`), or data-processing jobs for a shop they don't control. This is a cross-tenant access/data-integrity issue rooted entirely in this gem's own signature scope, not requiring any secret, token, or host-app misuse beyond following the documented API.

### Likelihood Explanation
Likelihood is realistic: the attacker only needs to be an installer of the vulnerable app on their own store (a normal, unprivileged action) to obtain one validly HMAC-signed body/secret pair, then can freely vary the headers on replay since headers are entirely outside the signed content. No access token, `client_secret`, or victim credentials are required.

### Recommendation
Include `shop-domain`, `topic`, and `webhook_id`/`api_version` (or bind them via a canonicalized string) in the value that is HMAC-verified, or otherwise cryptographically bind the header-derived identity fields to the signed payload before trusting them in `WebhookMetadata`, mirroring the remediation pattern in the referenced bug class (validate the type/identity field instead of assuming it from unauthenticated data).

### Proof of Concept
1. App installs the vulnerable library and registers a handler for `orders/create` per the documented pattern [8](#0-7) .
2. Attacker installs the same app on their own store `attacker.myshopify.com`, triggers an `orders/create` event, and captures the raw POST: body `B`, headers including a valid `x-shopify-hmac-sha256` computed by Shopify over `B` with the shared `api_secret_key`, `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays the exact same body `B` and `hmac` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes the HMAC over `B` only (see `to_signable_string`) [3](#0-2) , it matches, and `Registry.process` calls the handler with `WebhookMetadata(shop: "victim.myshopify.com", topic: "orders/create", body: B)` [6](#0-5) , spoofing the victim shop identity despite a "valid" signature.
