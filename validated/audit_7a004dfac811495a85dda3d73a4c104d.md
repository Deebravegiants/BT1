The docs confirm `ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify" and then invoking the handler — the caller is not instructed to independently re-verify the shop domain against its own installed-shop registry before trusting `data.shop`. The gem itself owns the full authentication contract here.

### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw JSON body, so `HmacValidator.validate` authenticates the body bytes but never binds the `shop` value read from the `x-shopify-shop-domain`/`shopify-shop-domain` header. `Registry.process` treats a passing HMAC check as full authentication of the request, including the shop identity it hands to the app's handler.

### Finding Description
`Webhooks::Registry.process` performs a single authentication check — `Utils::HmacValidator.validate(request)` — and, on success, calls the app's handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)`. [1](#0-0) 

The HMAC is computed and verified only over `to_signable_string`, which returns `@raw_body`: [2](#0-1) 

`request.shop`, however, is read straight from the `shop-domain` header and is completely outside the signed content: [3](#0-2) 

`HmacValidator.validate` confirms only that `OpenSSL::HMAC.hexdigest(secret, raw_body)` matches the supplied `hmac`, using the app's single shared `api_secret_key` (the same secret is used for every shop the app serves, unlike an access token which is per-shop): [4](#0-3) 

**The broken identity binding, stated as an equality:**
`shop_identity_trusted_by_handler == shop_domain_header` should equal `shop_identity_cryptographically_bound_by_hmac`, but the HMAC only binds `raw_body`, not `shop_domain_header`. Since `api_secret_key` is shared across every shop that has the app installed, any shop that has installed the app (including one an attacker controls) can generate a body/HMAC pair that is valid for *any* shop domain, because the domain never enters the signed material.

**Before/after the attacker's request sequence:**
- Before: attacker installs the app on their own store and triggers a webhook (e.g. `orders/create`) for that store. They capture the raw request body and its correctly-computed `hmac` — a legitimate `(body, hmac)` pair signed with the app's real `api_secret_key`.
- Attacker action: they POST that identical `(body, hmac)` pair to the app's webhook endpoint again, but replace the `x-shopify-shop-domain` header with a victim shop's domain.
- After: `HmacValidator.validate` still succeeds (it never looked at the shop header), and `Registry.process` invokes the handler with `WebhookMetadata#shop` set to the victim's domain and attacker-controlled `body`, `topic`, etc.

### Impact Explanation
This breaks the tenant boundary the gem is documented to enforce: `Registry.process`'s doc states it "will verify the request did indeed come from Shopify" before calling the handler, implying the whole `WebhookMetadata` (including `shop`) is trustworthy once that check passes. Because `shop` is unauthenticated, an attacker who controls one legitimately-app-installed shop can forge webhook events under any other merchant's shop domain, causing the host application to write/act on data (orders, customers, product updates, uninstall/GDPR events, etc.) attributed to a shop the attacker does not own. This is a cross-tenant integrity/access issue rooted entirely in this gem's `Webhooks::Request`/`Registry` design.

### Likelihood Explanation
Any unprivileged internet user can install a free/dev app instance (or otherwise be a legitimate merchant using the same app) and trigger events on their own store to obtain a valid `(body, hmac)` pair signed with the app's shared secret, requiring no access token, no `client_secret`, and no privileged account beyond ordinary merchant self-service. Swapping the shop-domain header and replaying is trivial with any HTTP client.

### Recommendation
Include the shop domain (and topic/webhook id) in the signed material verified against the HMAC, or — since Shopify's real HMAC only covers the body by design — require `Registry.process`/`Webhooks::Request` to independently authenticate `shop` (e.g., cross-check it against a shop known to have a valid, stored session/access token for this app) before constructing `WebhookMetadata`, rather than implicitly treating a body-only HMAC pass as authentication of the shop identity.

### Proof of Concept

# and captures a legitimately-signed webhook for their own store.
body = '{"id":1,"note":"hello"}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)
)

# Attacker replays the exact same (body, hmac) pair, only changing the shop header
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
  "x-shopify-webhook-id" => "forged-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) succeeds (only raw_body is checked),
#    handler.handle receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
