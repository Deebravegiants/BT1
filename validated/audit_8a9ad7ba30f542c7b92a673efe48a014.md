### Title
Webhook shop identity not bound by HMAC, enabling cross-tenant webhook attribution - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC computed by `Utils::HmacValidator.validate` verifies solely that the *body* bytes are authentic. The `shop` (and `topic`, `webhook_id`, `api_version`) values are read directly from unauthenticated HTTP headers and are handed to the application's `WebhookHandler` as the tenant identifier, without ever being covered by the signature.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

`to_signable_string` returns `@raw_body` only — it does not include `shop`, `topic`, or `webhook_id`. Those fields are parsed straight from HTTP headers via `shopify_header`: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC over the body, then immediately forwards `request.shop` (an unauthenticated header value) to the app's handler as the trusted tenant identity: [4](#0-3) [5](#0-4) 

The identity binding that should hold is:
`shop authenticated by HMAC == shop delivered to the handler as tenant context`

but the actual binding enforced by this code is only:
`body bytes authenticated by HMAC == body bytes parsed`,
while `shop` (the value used for tenant-scoped effects, e.g. `customers/redact`, `shop/redact`) is taken from a header that carries no cryptographic binding to the signature at all. This is the same class of bug as the reported vault issue: a value the code *acts on* (shares issued / shop tenant) is decoupled from the value that is *actually verified* (assets transferred / body bytes), and an attacker can drive the two apart to bypass a fairness/identity check.

### Impact Explanation
Any request whose `raw_body` + `hmac` pair is valid for the merchant's `client_secret`-derived signature (e.g., a webhook the attacker can legitimately trigger on their own store, since anyone can install an app and generate real webhook traffic for their own shop) can be replayed to the same endpoint with the `X-Shopify-Shop-Domain` header rewritten to any other shop domain the app has session data for. Because `Registry.process` never checks that the header-derived `shop` matches anything tied to the signature, the handler executes with attacker-chosen tenant context — an instance of the "cross-tenant access" impact category, since data or actions intended for shop A can be attributed to/processed as shop B (e.g., mandatory compliance webhooks like `customers/redact`/`shop/redact` being fired against a domain the attacker doesn't own, or app-level per-shop side effects being triggered for a victim shop from attacker-controlled, self-signed traffic).

### Likelihood Explanation
Medium-to-High: exploitation requires only that the attacker can generate one legitimately HMAC-signed webhook (trivial — installing the app on their own dev store yields fully valid signed webhook traffic for any subscribed topic), then replay it with a modified shop-domain header to the same public webhook endpoint. No possession of `api_secret_key` or any merchant's access token is required, satisfying the "unprivileged internet user" constraint.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in `Request#to_signable_string` — but since Shopify's actual HMAC contract only signs the raw body, the correct fix is to require host applications to authenticate `request.shop` against a known/registered shop record before trusting it (e.g., cross-check `shop` against a session lookup by webhook id or by verifying it belongs to an app installation with a currently valid access token) rather than passing the raw header value straight into `WebhookMetadata` as trusted tenant identity. At minimum, document and enforce that `Registry.process` must independently authorize the parsed `shop` against known installed shops before the handler acts on it.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets it emit a real webhook (e.g. `orders/create`) to the app's registered endpoint. This body/HMAC pair is fully valid for the app's `client_secret`.
2. Attacker captures `raw_body` and the `X-Shopify-Hmac-Sha256` header from that delivery.
3. Attacker sends a forged HTTP request to the same webhook endpoint using the identical `raw_body`/HMAC, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks `raw_body` against the HMAC — [6](#0-5)  — and `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"` [7](#0-6) , even though nothing about the signature ties the payload to that shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
