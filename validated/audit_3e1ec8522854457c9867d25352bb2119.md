### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw HTTP body against the app's shared `api_secret_key`. The `shop-domain` header — which is what `ShopifyAPI::Webhooks::Registry.process` hands to the host application's handler as the authoritative tenant identifier — is never included in the signed material. Any party who can obtain one genuinely-signed webhook (e.g., a merchant who installs the app and receives their own real webhooks) can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header, and the gem will report the HMAC as valid and dispatch the payload to the host app's handler tagged with the attacker-chosen shop.

### Finding Description
The identity binding that should hold is:

`shop that cryptographically produced/authorized the payload == shop value the handler trusts (request.shop)`

`Request#to_signable_string` returns only the raw body, not the shop header: [1](#0-0) 

`Request#shop` is read straight from an attacker-controllable header with no cryptographic tie to the signed bytes: [2](#0-1) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (the body) against the HMAC — it has no knowledge of, and never validates, the shop header: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately forwards `request.shop` — the unauthenticated header — to the handler as the trusted tenant identity, with no secondary check that the shop matches anything cryptographically bound to the body: [4](#0-3) 

Because Shopify signs webhooks with the app's single shared `api_secret_key` (the same key for every shop that has installed the app), any shop that has legitimately installed the app can capture one of its own correctly-signed webhook deliveries (valid body + valid HMAC) and replay that exact pair to the app's webhook endpoint while swapping only the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to name a different, victim shop. `Utils::HmacValidator.validate` will still return `true` because it never inspected the shop header, and `Registry.process` will call the handler with `WebhookMetadata#shop` set to the forged victim shop name, as demonstrated by the registry test asserting `data.shop` equals whatever the `x-shopify-shop-domain` header contained. [5](#0-4) 

### Impact Explanation
This is a cross-tenant confusion vulnerability: it allows an app-installing merchant (an "unprivileged" actor relative to other tenants, requiring no `api_secret_key`, access token, or privileged account) to make the host application process attacker-supplied webhook data under a different shop's identity. Any host application logic that trusts `WebhookMetadata#shop` (e.g., to look up per-shop settings, credentials, or to write data scoped by shop) can be tricked into acting on behalf of, or writing data into, another tenant's context, satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires the attacker to have installed the app on at least one shop (a normal, unprivileged action available to any merchant) and to capture one legitimately delivered webhook for that shop — both of which are trivial for any app user. No secret key or elevated access is required; only header manipulation on replay.

### Recommendation
Include the shop domain (and other identity-relevant headers such as topic/api-version/webhook-id) in the signed material verified by `Utils::HmacValidator`, or independently verify that `request.shop` matches a shop the app has previously registered/authorized before invoking handlers in `Registry.process`. At minimum, document that `WebhookMetadata#shop` is not cryptographically authenticated and host apps must independently verify shop identity before trusting webhook payload data.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. topic `orders/create`, with headers:
   - `x-shopify-hmac-sha256: <valid HMAC of raw body B>`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - body `B`
2. Attacker resends the identical body `B` and identical `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes the header to `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only (per `Request#to_signable_string`, `lib/shopify_api/webhooks/request.rb:35-38`) and succeeds, because `B` and the HMAC are unchanged.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches to the registered handler with `WebhookMetadata.new(shop: request.shop, ...)`, where `request.shop` now returns `"victim-shop.myshopify.com"` — a value the host app never authenticated — even though the payload was never produced by or authorized for that shop.
