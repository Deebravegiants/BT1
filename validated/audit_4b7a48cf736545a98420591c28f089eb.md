Confirmed: `send()` in `WrappedHyperFungibleToken.sol` and `WrappedHyperFungibleTokenUpgradeable.sol` has no `amount == 0` validation, and `EvmHost.dispatchIncoming` (evm/src/core/EvmHost.sol:794-818) permanently retries a failing `onAccept` call via `_requestReceipts[commitment]` deletion, with deterministic re-failure if the underlying token reverts on zero-value transfers.

### Title
Zero-amount `send()` on WrappedHyperFungibleToken permanently locks escrowed underlying tokens for ERC20s that revert on zero-value transfers - ([File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol])

### Summary
`WrappedHyperFungibleToken.send()` and its upgradeable counterpart accept and lock `params.amount` with no non-zero check, then dispatch a cross-chain `Message` carrying that same amount. On the destination, `onAccept` unconditionally calls `IERC20(_underlying).safeTransfer(beneficiary, message.amount)` (or, for WETH-mode, attempts a native push then re-wraps and calls `safeTransfer`). If `message.amount == 0` and the underlying ERC20 reverts on a zero-value `transfer` (a documented behavior of several real-world tokens), delivery of the cross-chain message deterministically fails forever.

### Finding Description
`send()` in `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol` locks `params.amount` of the underlying token via `safeTransferFrom` with no `amount > 0` guard [1](#0-0) , then builds and dispatches a `DispatchPost` carrying `message.amount = params.amount` unchanged [2](#0-1) .

On the destination chain, `onAccept` executes an unconditional token transfer of `message.amount`: [3](#0-2) 

If `_isWeth` is false, this is a direct `IERC20(_underlying).safeTransfer(beneficiary, message.amount)` with `message.amount == 0`. Several deployed ERC20 tokens revert on transferring a zero amount, which will make this `onAccept` call revert.

Delivery of `onAccept` is handled by `EvmHost.dispatchIncoming`, which treats a failed low-level call as retryable by simply deleting the replay-protection receipt and returning, without ever reverting the batch: [4](#0-3) 

Because the failure is caused by the token's own zero-amount rejection (not a transient condition), every future retry of the same commitment fails identically. The message can never be delivered.

The same unguarded pattern exists in `WrappedHyperFungibleTokenUpgradeable.sol`'s `send`/`onAccept` [5](#0-4) , and in the `onPostRequestTimeout` refund paths of both contracts, which also call `safeTransfer`/`safeTransferFrom` with `message.amount` unconditionally [6](#0-5) .

### Impact Explanation
On the source chain, `params.amount` of the underlying ERC20 is escrowed in the `WrappedHyperFungibleToken` contract via `safeTransferFrom` before the message is dispatched. If the destination `onAccept` (or, symmetrically, the `onPostRequestTimeout` refund path back on the source chain for a message that times out) permanently reverts because the underlying token disallows zero-value transfers, the escrowed tokens can never be released to any beneficiary — they are frozen in the contract indefinitely, with no alternate withdrawal path. This is a permanent freezing-of-funds condition for any deployment where the wrapped underlying is a zero-transfer-averse ERC20.

### Likelihood Explanation
Reachable by any unprivileged caller of `send()` — no special privileges are required to submit `params.amount = 0`. The likelihood of hitting a token that reverts on zero-value transfers depends on which underlying ERC20 is configured for the `WrappedHyperFungibleToken` deployment; this is a real, documented behavior class of ERC20 tokens, and the protocol's own token-bridge design explicitly supports "any ERC20" as the underlying with no enforced allowlist.

### Recommendation
Add an explicit `if (params.amount == 0) revert InvalidAmount();` check in `send()` (and equivalently reject/skip zero-amount messages in `onAccept` / `onPostRequestTimeout`) in both `WrappedHyperFungibleToken.sol` and `WrappedHyperFungibleTokenUpgradeable.sol`, mirroring the zero-amount guard already present elsewhere in the codebase (e.g., `IntentsBase._withdraw`'s `if (amount == 0) continue;` at [7](#0-6) ).

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` with an underlying ERC20 that reverts on `transfer(to, 0)` (e.g., a token following the strict `require(amount > 0)` pattern).
2. Call `send()` with `params.amount = 0` (no zero-check prevents this); the source-side `safeTransferFrom` of 0 succeeds trivially, and a POST request with `message.amount = 0` is dispatched.
3. On the destination, the relayer submits the request; `EvmHost.dispatchIncoming` calls `onAccept`, which calls `IERC20(_underlying).safeTransfer(beneficiary, 0)`, which reverts inside the underlying token.
4. `dispatchIncoming` catches the failure, deletes `_requestReceipts[commitment]`, and returns — marking the request as retryable.
5. Every subsequent relayer retry replays the same call and reverts identically; the message can never be delivered, and any tokens escrowed for this or associated flows remain permanently locked with no code path to release them.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
