### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, while the `shop` (tenant identity) is read from an unauthenticated HTTP header that is never included in the signed content.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `hmac` is derived purely from the `shopify-hmac-sha256`/`x-shopify-hmac-sha256` header [2](#0-1) . The `shop` accessor, however, is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding to the signed body [3](#0-2) .

`Registry.process` validates `Utils::HmacValidator.validate(request)` — which only checks the HMAC over `to_signable_string` (i.e., the raw body) — and, if valid, immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) . `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it only against `hmac` [5](#0-4) ; the `shop` field never enters the signed string.

This breaks the identity binding: `shop_header == authenticated_tenant`. In reality, `HMAC(secret, raw_body) == valid` binds only the *body bytes*, not the `shop-domain` header. The gem's documentation explicitly tells integrators that `Registry.process` "will verify the request did indeed come from Shopify" [6](#0-5)  and that the resulting `data.shop` is "The shop domain of the webhook" [7](#0-6) , instructing app authors to use `data.shop` for tenant-scoped work (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [8](#0-7) . Since only the raw body is authenticated, an unprivileged party who possesses one legitimately-signed webhook payload (e.g. captured from their own shop, which they can obtain simply by installing the app on their own store) can replay that exact body+HMAC pair while substituting an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` still returns true because the signature check never inspects the shop header, and `Registry.process` will hand the attacker-chosen `shop` value straight to the app's `WebhookHandler`.

### Impact Explanation
Any app relying on `WebhookMetadata#shop` for tenant scoping (exactly as this gem's own documentation recommends) can be tricked into processing/crediting/persisting webhook data under a victim shop's identity while the payload content actually belongs to the attacker's own shop, or vice versa — a cross-tenant data confusion in a multi-tenant SaaS app built on this gem. This matches the "Critical – cross-tenant access" impact category since the authentication boundary meant to bind an inbound event to a specific merchant tenant is bypassed.

### Likelihood Explanation
Likelihood is realistic: an attacker only needs to be a legitimate (even free) merchant capable of installing the app on their own store to receive at least one validly-signed webhook body, then can replay it against the same public webhook endpoint with a forged `shop-domain` header. No access to `api_secret_key`, tokens, or victim credentials is required — only observation of a legitimately-received webhook of their own.

### Recommendation
Include the shop domain (and ideally webhook id / topic) inside the HMAC-signed material, or independently verify that `shop` corresponds to a shop with an active, registered webhook subscription/session before trusting it in `WebhookMetadata`. At minimum, document that `data.shop` is not cryptographically authenticated and must be cross-checked against the app's known/installed shops before being used for tenant-scoped operations.

### Proof of Concept
1. App A registers webhook handler that uses `data.shop` to select the tenant's session/database, per the documented pattern in `docs/usage/webhooks.md`.
2. Attacker installs the app on `attacker-shop.myshopify.com`, triggers an event (e.g. `orders/create`), and captures the resulting POST — raw body `B` and header `x-shopify-hmac-sha256: H` (valid since `H = HMAC(secret, B)`).
3. Attacker resends the identical body `B` and header `H` to the same webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` returns `true` because it only checks `HMAC(secret, B) == H`, unaffected by the shop header.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and calls the app handler, which now processes attacker-controlled data under the victim's tenant identity.
