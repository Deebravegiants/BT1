### Title
Attacker-selected flash-loan receiver can be charged through its existing pool allowance - (File: contracts/pool/src/ops/flash.rs)

### Summary

`Controller::flash_loan` lets any authorized caller choose an arbitrary deployed WASM `receiver`. The pool transfers principal to that receiver, invokes its public `execute_flash_loan` callback, and then pulls `amount + fee` with `transfer_from` using the receiver’s allowance to the pool. No check ties that pre-existing allowance to the caller or proves that the receiver intentionally initiated the loan. A compatible receiver contract that leaves a permissive callback and a stale token allowance can therefore be forced to pay the flash-loan fee, repeatedly draining its balance up to the available allowance.

### Finding Description

The public controller entrypoint accepts `caller`, `asset`, `amount`, `receiver`, and arbitrary `data`, requiring authorization only from `caller` and that `receiver` be a WASM contract. It never requires the receiver to authorize or register for the operation. [1](#0-0) [2](#0-1) 

The pool sends `amount` to the selected receiver and invokes `execute_flash_loan` with the caller supplied as `initiator`. [3](#0-2) [4](#0-3) 

Settlement checks `asset.allowance(receiver, pool) >= amount + fee` and then executes `asset.transfer_from(pool, receiver, pool, amount + fee)`. The allowance is therefore treated as repayment consent even though it may have existed before the transaction and was not issued to, or for, the initiating caller. [5](#0-4) 

A receiver callback is not required to create the allowance: a callback that simply returns is a valid implementation path, with repayment failing only when the required allowance is absent or insufficient. [6](#0-5) 

### Impact Explanation

This allows theft of funds from a vulnerable receiver contract. For each forced loan, the victim first receives `amount`, but the pool then withdraws `amount + fee`; its net loss is `fee`. Repeating the operation consumes the victim’s pool allowance while extracting fees from its token balance. With a sufficiently large or persistent allowance, repeated small loans can drain substantially all reachable balance.

The impact is theft of user/contract funds and unplanned protocol revenue generated at the victim’s expense. The exact drain rate depends on the configured fee and the victim’s allowance and balance.

### Likelihood Explanation

Likelihood is conditional rather than universal. The target must:

- be a deployed WASM contract;
- expose a compatible `execute_flash_loan` callback that returns without enforcing an expected initiator or operation;
- have at least `amount + fee` balance after receiving principal; and
- have a live `receiver -> pool` allowance of at least `amount + fee`.

The allowance condition is realistic for integrations that intentionally approve the pool, over-approve repayment, or retain residual allowance. The project’s own integration guidance recognizes that callback gates must bind a trusted caller and initiator, but the protocol does not enforce that requirement on arbitrary receiver contracts. [7](#0-6) 

### Recommendation

Do not treat `receiver -> pool` token allowance alone as consent for an arbitrary caller-initiated loan. Bind the loan to explicit receiver consent. Practical options include:

- require the receiver contract itself to initiate the flash loan through a dedicated receiver-authenticated flow;
- add a controller/pool registry where the receiver explicitly opts in to a caller, asset, maximum amount, nonce, and expiry before a loan can use it;
- or replace passive allowance settlement with an authenticated receiver settlement step that validates the caller and loan terms.

At minimum, reject `receiver != initiator` unless the receiver has explicitly authorized that initiator for the operation. Receiver documentation and examples should also require validating `pool`, `initiator`, asset, amount, fee, and a single-use operation nonce before returning successfully.

### Proof of Concept

1. A victim WASM contract exposes:

```rust
pub fn execute_flash_loan(
    env: Env,
    initiator: Address,
    asset: Address,
    amount: i128,
    fee: i128,
    pool: Address,
    data: Bytes,
) {
    // Compatible but permissive implementation: returns successfully.
}
```

2. During a previous legitimate integration, the victim approves the pool for `amount + fee`, or retains a larger reusable allowance.

3. An attacker calls:

```rust
controller.flash_loan(
    attacker,
    HubAssetKey { hub_id, asset },
    amount,
    victim_contract,
    attacker_controlled_data,
);
```

4. `process_flash_loan` authenticates only `attacker` and forwards the attacker-selected `victim_contract` to the pool. [8](#0-7) 

5. The pool transfers `amount` to the victim and calls its permissive callback. [9](#0-8) 

6. After the callback returns, the pool consumes the victim’s existing allowance and pulls `amount + fee`. [10](#0-9) 

7. The victim loses `fee` net despite never initiating or consenting to that specific loan. The attacker repeats the call while allowance and balance remain sufficient.

    caller: &Address,
    hub_asset: &HubAssetKey,
    amount: i128,
    receiver: &Address,
    data: &Bytes,

    require_positive_amount(env, amount);

    let mut cache = Context::new(env);

    let fee = storage::with_flash_guard(env, || {
        pool_flash_loan_call(env, &pool_addr, hub_asset, caller, receiver, amount, data)
    });

pub(crate) fn apply(
    env: &Env,
    hub_asset: HubAssetKey,
    initiator: Address,
    receiver: Address,
    amount: i128,
    data: Bytes,
) -> i128 {
    let mut cache = prepare(env, hub_asset, amount);
    require_wasm_receiver(env, &receiver);

    let pool = env.current_contract_address();
    let asset = token::Client::new(env, &cache.params().asset_id);
    let terms = terms(
        env,
        amount,
        cache.params().flashloan_fee,
        asset.balance(&pool),
    );

    asset.transfer(&pool, &receiver, &amount);
    require_balance(env, &asset, &pool, terms.balance_after_payout);
    invoke_receiver(
        env, &cache, &receiver, initiator, amount, terms.fee, &pool, data,
    );

    require_balance(env, &asset, &pool, terms.balance_after_payout);
    collect_repayment(env, &asset, &pool, &receiver, &terms);
```

/// Pulls principal + fee via `transfer_from` after verifying allowance.
fn collect_repayment(
    env: &Env,
    asset: &token::Client,
    pool: &Address,
    receiver: &Address,
    terms: &FlashTerms,
) {
    assert_with_error!(
        env,
        asset.allowance(receiver, pool) >= terms.total_repayment,
        FlashLoanError::InvalidFlashloanRepay
    );
    asset.transfer_from(pool, receiver, pool, &terms.total_repayment);
    require_balance(env, asset, pool, terms.balance_after_repayment);
```
