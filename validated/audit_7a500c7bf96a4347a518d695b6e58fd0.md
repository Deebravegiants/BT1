### Title
GET request `payer` field is silently discarded by `EvmHost.dispatch(DispatchGet)`, causing relayer-fee refunds to be blackholed in calling contracts with no sweep mechanism - (File: evm/src/core/EvmHost.sol)

### Summary
`ExtrinsicIntents._cancelFromSource` (and similarly `IntentGatewayV2`/tron `IntentGatewayV2`) dispatches a `DispatchGet` request on behalf of an end user, explicitly setting `payer: msg.sender` so that the fee refund on GET timeout goes to the original caller. However, `EvmHost.dispatch(DispatchGet memory get)` never reads `get.payer` — it hardcodes the fee-refund recipient to `_msgSender()`, i.e., the direct caller of `dispatch()`, which is the intents gateway contract itself, not the intended user. Since these gateway contracts have no function to sweep or forward arbitrary fee-token balances to a specific beneficiary, any refunded relayer fee becomes permanently stuck in the contract. This is a direct analog of the reported L1GraphTokenGateway bug, where a contract's address used as a hardcoded refund target (instead of an explicit refund parameter) blackholes value, except here Hyperbridge exposes a `payer` field specifically to prevent this and then fails to honor it.

### Finding Description
`DispatchGet` includes a dedicated `payer` field documented as "Account responsible for paying the fees... If different from msg.sender" [1](#0-0) . Callers such as `ExtrinsicIntents._cancelFromSource` correctly populate this field with the actual end-user address (`msg.sender` of the intents contract call) so that the user, not the intents contract, receives any fee refund [2](#0-1) .

However, `EvmHost.dispatch(DispatchGet memory get)` never uses `get.payer` when recording the `FeeMetadata` for the request; it always records `_msgSender()` (the immediate caller of `dispatch`, i.e., the `ExtrinsicIntents`/`IntentGatewayV2` contract) as the refund `sender`: [3](#0-2) 

Compare this to the POST-request path, where `dispatch(DispatchPost memory post)` correctly honors `post.payer`: [4](#0-3) 

On a GET timeout, the fee is refunded to whatever `sender` was recorded — i.e. the gateway contract, not the actual user: [5](#0-4) 

Neither `ExtrinsicIntents.sol` nor the EVM/Tron `IntentGatewayV2.sol` expose any rescue/sweep function to move an arbitrary ERC20 (fee token) balance out to a specific beneficiary — no `rescue`, `sweep`, `withdrawToken`, or similar function was found in `evm/src/apps/**/*.sol`. Thus any fee token that lands in the gateway contract via this mis-refund has no path back to the user.

### Impact Explanation
Any time a user calls `cancelOrder` on `ExtrinsicIntents` (or the analogous cross-chain GET-based cancellation path in `IntentGatewayV2`) and the resulting GET request times out, the relayer fee that should be refunded to that user is instead credited to the intents/gateway contract's own balance in the fee token, and is permanently unrecoverable by that user. This is a leak/loss-of-value bug affecting every unprivileged user who dispatches a GET request through these intents apps and experiences a timeout — the class of impact matches the referenced Medium-severity finding (loss of relayer/submission fee due to an unusable hardcoded refund target), not outright asset theft.

### Likelihood Explanation
Likelihood is moderate-to-high: any legitimate cross-chain order cancellation flow using `_cancelFromSource` sets a non-zero relayer fee and can time out under normal network conditions (slow relayers, congestion, or a deliberately non-responsive relayer network), triggering the timeout-refund path with no attacker action required. The bug is purely a protocol-level omission (ignoring `get.payer`) reachable from a single unprivileged `cancelOrder` transaction with a subsequent timeout-proof submission — no admin/privileged actions are involved.

### Recommendation
Update `EvmHost.dispatch(DispatchGet memory get)` to record `get.payer` (falling back to `_msgSender()` only if unset/zero) as the `FeeMetadata.sender`, mirroring the `DispatchPost` dispatch path, so that the refund recipient matches what callers explicitly specify:
```solidity
_requestCommitments[commitment] = FeeMetadata({sender: get.payer, fee: get.fee});
```
Additionally, consider adding a safe token-rescue mechanism to `ExtrinsicIntents`/`IntentGatewayV2` to recover any fee tokens that may already be stuck due to this or similar misrouting.

### Proof of Concept
1. User calls `ExtrinsicIntents.cancelOrder(...)` for an expired order sourced remotely, triggering `_cancelFromSource`, which builds `DispatchGet{ ..., fee: relayerFee, payer: msg.sender }` and calls `IDispatcher(hostAddr).dispatch(request)` [6](#0-5) .
2. Inside `EvmHost.dispatch(DispatchGet memory get)`, the fee is collected from `ExtrinsicIntents` (the `_msgSender()` of this call), and `_requestCommitments[commitment]` is stored with `sender: _msgSender()` (i.e., the `ExtrinsicIntents` contract address), completely ignoring `get.payer` [7](#0-6) .
3. If the GET request subsequently times out and a timeout proof is submitted, `dispatchTimeOut(GetRequestTimeout...)` refunds `meta.fee` to `meta.sender`, which resolves to the `ExtrinsicIntents` contract address rather than the user who called `cancelOrder` [8](#0-7) .
4. Because `ExtrinsicIntents` has no function to withdraw arbitrary fee-token balances to a chosen address, the refunded fee is permanently stuck in the contract, reproducing the same value-blackholing pattern described in the original L1GraphTokenGateway finding.
