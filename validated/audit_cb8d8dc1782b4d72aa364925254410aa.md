### Title
Fee Payout Re-Entrancy in `EvmHost.dispatchIncoming` (GetResponse) — ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatchIncoming(GetResponse, address relayer)` performs an untrusted external call into the destination application (`IApp.onGetResponse`) and only *afterwards* pays out the relayer fee held in `_requestCommitments[commitment].fee`. Unlike the POST-timeout paths in the same contract, this function never zeroes/deletes the fee entry after payment, and it sets `_responseReceipts[commitment]` unconditionally rather than checking it was previously unset. A malicious application contract that is the original requester (`request.from`) can re-enter through the same delivery path from within its `onGetResponse` callback and collect the same fee repeatedly before the first call frame ever clears the corresponding state, draining the host's fee-token balance.

### Finding Description
`dispatchIncoming` for `GetResponse` is: [1](#0-0) 

Key issues:
1. `_responseReceipts[commitment]` is written unconditionally with no prior check that a receipt already exists, so the same response can be "delivered" more than once.
2. After the external call to the destination app succeeds, the fee is read from `_requestCommitments[commitment].fee` and transferred to `relayer` — but that mapping entry is never deleted or zeroed afterward.

Compare this to the sibling functions in the very same contract, `dispatchTimeOut` for GET and POST requests, which correctly apply checks-effects-interactions by deleting `_requestCommitments[commitment]` **before** making the external call to the app: [2](#0-1) [3](#0-2) 

`dispatchIncoming(GetResponse,...)` breaks this pattern: the state that gates the fee payout (`_requestCommitments[commitment].fee`) is read and paid *after* the external call, and is never cleared, so the same commitment can be paid multiple times if the external call re-enters the delivery path.

Because the destination of the external call, `_bytesToAddress(response.request.from)`, is an arbitrary application contract that any unprivileged user can deploy and use to originate a GET request (paying the request fee at dispatch time), an attacker fully controls the callback logic invoked from within `dispatchIncoming`. From that callback the attacker can drive another delivery of the same (or another) response for the same commitment (e.g., by having their controlled relayer/app trigger the handler's response-delivery entrypoint again), reaching `dispatchIncoming` a second time while `_requestCommitments[commitment].fee` is still non-zero, thereby claiming the fee again.

This is the direct analog of the NFTX `distribute` bug: an unprivileged, attacker-reachable dispatch function invokes an external, attacker-controlled contract before finalizing/zeroing the accounting state that gates a payout, allowing repeated collection of funds meant to be paid once.

### Impact Explanation
Repeated fee collection allows an attacker to drain the `feeToken` balance held by `EvmHost` that is meant to pay legitimate relayers for GET-response delivery. This is a direct, permanent loss of protocol/relayer funds — concrete theft of funds reachable from a single relayed GET response delivered through the permissionless message-delivery path (`HandlerV2` → `EvmHost.dispatchIncoming`).

### Likelihood Explanation
The attack requires only:
- Deploying an ordinary `IApp` contract (unprivileged) that dispatches a GET request with a non-zero fee.
- Implementing `onGetResponse` to re-enter the delivery path before the outer call returns.

No governance, admin, or validator collusion is needed — any relayer/user can construct and submit the crafted proof/response, making this a fully unprivileged, single-transaction exploit path.

### Recommendation
Apply checks-effects-interactions consistently in `dispatchIncoming(GetResponse,...)`:
- Reject if `_responseReceipts[commitment]` is already set (add an explicit guard rather than unconditionally overwriting it).
- Zero/delete `_requestCommitments[commitment]` (or at least its `fee` field) **before** making the external call to the destination app, mirroring the pattern already used in `dispatchTimeOut`.
- Consider adding a re-entrancy guard around the dispatch/delivery entrypoints in `EvmHost`/`HandlerV2` as defense in depth.

### Proof of Concept
1. Attacker deploys `EvilApp` implementing `IApp`, dispatches a GET request (`request.from = EvilApp`), paying `fee` in `feeToken`.
2. When the GET response is ready, the relayer (attacker-controlled or anyone) submits it through `HandlerV2`, which calls `EvmHost.dispatchIncoming(response, relayer)`: [4](#0-3) 
3. Inside `EvilApp.onGetResponse`, the attacker re-enters the delivery path (re-submits the same/duplicate response through the handler) before the outer `dispatchIncoming` call returns.
4. Because `_responseReceipts[commitment]` was set unconditionally (no "already delivered" guard) and `_requestCommitments[commitment].fee` was not cleared, the re-entrant call reaches the fee-payment line again: [5](#0-4) 
5. The fee is transferred to `relayer` a second (or Nth) time, draining `feeToken` from `EvmHost` beyond the single legitimate payout.

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
