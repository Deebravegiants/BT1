Predictable, unsigned session ID used as browser session cookie enables session fixation/hijacking - ([File: lib/shopify_api/auth/session.rb])

### Summary
For non-embedded apps, `ShopifyAPI::Auth::Oauth.validate_auth_callback` sets the browser's session cookie value to the raw `Session#id`, which is deterministically derived as `"#{shop}_#{associated_user.id}"` (online) or `"offline_#{shop}"` (offline). This value is not a secret, is not signed, and is not bound to anything an attacker cannot know or guess, so it functions as a bearer session identifier that can be constructed by any unprivileged party.

### Finding Description
`Session.from` computes the session `id` purely from public/guessable inputs: [1](#0-0) 

This `id` is then placed directly into the `SessionCookie` value that the host application is instructed to set in the user's browser: [2](#0-1) 

`shop` (the myshopify domain) is public information, and Shopify user IDs (`associated_user.id`) are small sequential integers that are frequently observable/guessable (e.g., surfaced in other API responses, admin URLs, or simply brute-forceable given their low entropy). Unlike `state` (a `SecureRandom.alphanumeric(15)` nonce checked against a cookie) or the HMAC-protected OAuth callback fields, this cookie value carries no cryptographic binding to the specific authenticated browser session — it is just `"{shop}_{user_id}"` or `"offline_{shop}"`.

The library's own documentation instructs `current_session_id`/`cookie_session_id` to trust this cookie value directly as the session lookup key for non-embedded apps: [3](#0-2) [4](#0-3) 

The equality this breaks: "session id presented by the browser" should equal "an unforgeable, unguessable token bound to one specific authenticated OAuth completion," but instead "session id presented by the browser" == "any string an attacker can construct from `shop` + a small integer user ID," with no secret or signature involved.

### Impact Explanation
Any unprivileged internet user who can guess or observe a valid `shop` + Shopify user ID (or knows the target only uses offline tokens, in which case the ID is simply `"offline_#{shop}"` — trivially derivable with zero secret knowledge) can set `shopify_app_session=<guessed id>` in their own browser and, per the documented flow, `SessionUtils.current_session_id` returns that attacker-supplied value directly. The host application then uses this ID as the primary key to look up the corresponding `Session` (containing the shop's real access token) from its session store, per the documented pattern in `docs/usage/oauth.md` and `BREAKING_CHANGES_FOR_V16.md`. This lets an attacker who has never completed OAuth for a shop, and who possesses no access token, secret, or credential, obtain an authenticated session context for that shop/user — a cross-tenant session-hijacking / authentication-bypass primitive squarely tied to this gem's own session-ID design (`Session.from`, `SessionCookie`, `SessionUtils`), not to any host-app misuse.

### Likelihood Explanation
For offline sessions the ID (`"offline_#{shop}"`) requires zero secret knowledge — only the target's myshopify domain, which is always public. For online sessions, the numeric Shopify user ID has low entropy and is frequently disclosed elsewhere (webhooks, `associated_user` payloads, admin UI, GraphQL `customer`/`staffMember` IDs), making it feasible to enumerate. The only mitigating factor is that this class of forgery is only reachable for apps using the non-embedded cookie flow (embedded apps use JWT-bound session-token derivation instead, which is properly signed) — but the authorization code grant / cookie flow is a fully supported, documented path in this library.

### Recommendation
Do not use the deterministic `Session#id` (`"{shop}_{user_id}"` / `"offline_{shop}"`) as the bearer value stored in the browser cookie. Instead, generate a separate cryptographically random, unguessable session token (e.g. `SecureRandom` value, as already done for the OAuth `state` nonce) to serve as the cookie value, and map that opaque token to the internal `Session#id`/record server-side, never exposing the shop+user-derived ID as something a client can present to authenticate.

### Proof of Concept
1. Attacker learns (or knows) the target's myshopify domain `victim-shop.myshopify.com` (public) and, for offline-token apps, needs nothing else.
2. Attacker sets the browser cookie: `shopify_app_session=offline_victim-shop.myshopify.com`.
3. Attacker calls the app endpoint that internally does:
   `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` → returns `cookie_session_id(cookies)` → `"offline_victim-shop.myshopify.com"` verbatim (see `lib/shopify_api/utils/session_utils.rb:68-71`), with no verification that this value was ever issued by the app.
4. The host app (per the documented `SessionRepository` pattern) looks up the stored `Session` by this ID and finds the real session/access token for `victim-shop.myshopify.com`, granting the attacker an authenticated context for that shop.
