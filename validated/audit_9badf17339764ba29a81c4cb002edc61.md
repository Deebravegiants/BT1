### Title
Webhook HMAC only authenticates the request body, not the `shop`/`topic`/`webhook_id` headers, enabling cross-tenant shop impersonation - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies webhook authenticity by validating an HMAC that is computed over the raw request body only. The `shop`, `topic`, and `webhook_id` values consumed by the handler come from HTTP headers that are never included in the signed payload, so an attacker who possesses one genuine `(body, hmac)` pair can replay it with arbitrary `shop-domain`/`topic`/`webhook-id` headers and have it accepted as authentic.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 
`to_signable_string` returns only `@raw_body`. Meanwhile `shop`, `topic`, and `webhook_id` are read straight from headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates only this body-derived HMAC and then trusts `request.shop`/`request.topic`/`request.webhook_id` to build the data handed to the app's handler: [3](#0-2) 

`HmacValidator.validate` (shared with OAuth) simply checks `OpenSSL.secure_compare(computed_signature, received_signature)` against `to_signable_string`, so it is agnostic to what is actually being signed: [4](#0-3) 

The documented contract for `Registry.process` explicitly claims it "will verify the request did indeed come from Shopify," implying the whole payload — including the shop identity — is authenticated: [5](#0-4) 

This is exactly the identity-binding gap described in the report's bug class: a field that is acted upon (`shop`, used by the host app to attribute the webhook to a tenant) is not covered by the HMAC that is checked (`raw_body` only). The equality that should hold is `HMAC_verified(secret, raw_body) == HMAC_verified(secret, raw_body ‖ shop ‖ topic ‖ webhook_id)`, but the gem only proves the former while callers rely on the latter.

### Impact Explanation
Since the `shop` header is not bound to the signature, an attacker who obtains one legitimate `(raw_body, hmac)` pair — trivially available by installing the app on their own development store and capturing/triggering a webhook — can resend that exact body+HMAC to the app's webhook endpoint while substituting a victim shop's domain in the `shopify-shop-domain` header (and/or a different `topic`/`webhook-id`). `Registry.process` will accept it as authentic and invoke the handler with `WebhookMetadata` attributing the attacker-controlled body to the victim's shop, breaking the tenant boundary the app relies on for the `shop` field. This matches the Critical "cross-tenant access" category since the identity of the shop the webhook data is attributed to can be forged.

### Likelihood Explanation
Medium-to-High: no privileged credentials or Shopify secret are required — only a genuine webhook capture from any shop the attacker controls (an unprivileged internet user can install a public app on a free dev store to obtain one). Header spoofing to the app's own webhook endpoint requires no special access.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the signed content (or otherwise cryptographically verify them, e.g. by cross-checking against Shopify's known webhook payload structure/IP allowlist) rather than trusting header values that sit outside the HMAC. At minimum, document loudly that `Registry.process` only authenticates the body and that callers must independently validate the `shop` header against a known/registered shop before trusting it, and consider deriving `shop`/`topic` from the signed body where the API includes them.

### Proof of Concept
1. Attacker installs the target app on a store they control (`attacker-shop.myshopify.com`) and lets Shopify deliver a legitimate webhook, e.g. `orders/create`. Attacker captures the raw body `B` and the valid `X-Shopify-Hmac-Sha256` header `H`.
2. Attacker sends a POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid since it only signs `B`), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and any desired `X-Shopify-Topic`/`X-Shopify-Webhook-Id`.
3. `ShopifyAPI::Webhooks::Request.new` parses these headers un-authenticated [6](#0-5) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and matches `H`, so validation succeeds [7](#0-6) .
4. The app's handler is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: ..., body: B, ...)`, causing the host application to process attacker-supplied data as if it originated from the victim shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)

```markdown
To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
