### Title
Lost-update race condition in `ConnectedOrigins` read-modify-write operations can revert an unauthorized dApp origin's trust/connection state - (File: `features/connected-origins/module/connections.js`)

### Summary
The `@exodus/connected-origins` module, which gatekeeps whether a third-party website (dApp origin) may access wallet accounts, persists its entire authorization list using a non-atomic read-then-write pattern. Every mutating method (`add`, `#setAttributes`, `connect`, `disconnect`, `untrust`, `clearConnections`) reads the full `connectedOrigins` array, computes a new array in memory, and then writes it back, with no locking or optimistic-concurrency check. This is structurally the same class of bug as the reported Sherlock finding: a shared, mutated collection (`valueStaked` / `earningsPerValueX128` in Burve vs. the `connectedOrigins` array here) is updated based on a value read *before* another concurrent state-changing operation completed, so the later write silently clobbers/dilutes the concurrently-applied change.

### Finding Description
All connected-origins mutations follow this pattern: [1](#0-0) 

`#setAttributes`, used by `setAutoApprove`, `setFavorite`, `connect`, `disconnect`, and `updateConnection`, re-reads the origin and the full array, then writes the whole array back: [2](#0-1) 

`add()` similarly reads the existing origin entry first and then either calls `#setAttributes` or `#addNewItem`, both of which read the array again before writing: [3](#0-2) 

`untrust()` performs the same unguarded read-then-write on the full list: [4](#0-3) 

Because none of these operations serialize on a shared lock, coordinate via CAS/versioning, or diff against the very latest state at write time, two concurrent calls interleave as follows:
1. Call A (e.g. `untrust({origin: 'evil.com'})`, triggered by the user revoking access) reads the array (contains `evil.com`).
2. Call B (e.g. `connect`/`add`/`setFavorite` for an unrelated origin `foo.com`, triggered automatically by a background dApp interaction) reads the same stale array (still containing `evil.com`).
3. Call A finishes and writes the array without `evil.com`.
4. Call B finishes and writes its own array, which was derived from the array captured in step 2 — i.e. it still contains `evil.com`, silently re-instating the origin that the user just revoked.

This is directly analogous to the Burve root cause: `self.valueStaked` (the shared accumulator) is updated to include the new staker before `addEarnings` recomputes shares from it, so the freshly-added value pollutes the denominator used for existing holders. Here, the shared accumulator is the `connectedOrigins` array/`connectedAccountsAtom`, and a concurrent, unrelated mutation "pollutes" (overwrites) another mutation's already-committed effect because both operations captured a stale snapshot before either write landed.

### Impact Explanation
Since `connectedOrigins.isTrusted` / `isAutoApprove` gate whether a dApp can silently obtain account addresses via `getConnectedAccounts` and auto-approve future `connect()` calls without prompting the user, a lost update that resurrects a revoked/untrusted origin effectively restores unauthorized cross-origin access to wallet accounts without any further user confirmation — a real authorization-bypass / origin-isolation violation, not merely a UI inconsistency. Any flow that triggers multiple near-simultaneous connected-origins mutations (multiple dApp tabs connecting concurrently, an `updateConnection`/`connect` call racing with a user-initiated `untrust`, etc.) can trigger this.

### Likelihood Explanation
Likelihood is moderate: it requires two connected-origins mutations to be in flight concurrently (e.g. the user revoking one site while another open dApp tab performs a routine `connect`/`updateConnection`/`add` call, which is a realistic, unprivileged, naturally-occurring scenario given multiple dApp tabs are commonly connected at once). No special privileges are required — only ordinary browsing behavior with two dApps open.

### Recommendation
Serialize mutations to the `connectedOrigins`/`connectedAccountsAtom` state (e.g., a per-module async mutex/queue, or use the atom's `set` with a functional updater that receives the latest value, as is already done elsewhere in the codebase, e.g. `#externalWalletAddressesAtom.set((current) => ...)` in `features/wallet-accounts/src/module/wallet-accounts.ts`) so that `#getData`/read and the subsequent `#setData`/write happen atomically with respect to other connected-origins mutations, eliminating the lost-update/dilution window.

### Proof of Concept
1. Add origin `evil.com` and mark it trusted via `connectedOrigins.add({...})`.
2. Concurrently invoke: `connectedOrigins.untrust({ origin: 'evil.com' })` and, before it resolves, `connectedOrigins.add({ origin: 'foo.com', ... })` (or `connect`/`setFavorite` for any other already-existing origin) — both operations will call `#getData()` before either has called `#setData()`.
3. Await both promises, then call `connectedOrigins.isTrusted({ origin: 'evil.com' })`.
4. Depending on interleaving, `evil.com` reappears as trusted in the persisted array (the `foo.com`/other-origin write silently re-includes the stale `evil.com` entry it read before `untrust` committed), demonstrating the lost update restoring access the user explicitly revoked.
