### Title
Missing recipient validation in vault `deposit`/`redeem`/`transfer` allows funds to be permanently lost to an unvalidated `recipient`/`to` principal - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and sibling vaults `v0-vault-sbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`)

### Summary
All Zest tokenized vaults expose `deposit`, `redeem`, and `transfer` functions that take an arbitrary, caller-supplied `recipient`/`to` principal and move value (mint shares, burn shares + send underlying, or move share balance) to that principal without validating it against the vault's own `NULL-ADDRESS` constant. This mirrors the FETH `withdrawFrom` finding: the `to` parameter is trusted blindly, so a value-moving call can send funds to an address nobody controls, permanently freezing them while the vault's internal aggregate accounting (`assets`, `total-supply`) proceeds as if the transfer succeeded normally.

### Finding Description
Each vault defines a `NULL-ADDRESS` constant explicitly for this purpose: [1](#0-0) 

Yet the value-moving entry points do not assert the recipient/`to` differs from it. `deposit` mints shares directly to `recipient` after receiving underlying, with no check that `recipient` isn't `NULL-ADDRESS`: [2](#0-1) 

`redeem` burns the caller's shares and sends underlying assets to `recipient`, again without validating `recipient`: [3](#0-2) 

`transfer` only checks that `to` isn't the vault contract itself (`ERR-TOKENIZED-VAULT-PRECONDITIONS`), but never checks `to` against `NULL-ADDRESS`: [4](#0-3) 

The same pattern is repeated identically across `v0-vault-sbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, and `v0-vault-ststxbtc.clar`.

The value identity broken is: `assets_before - inkind == assets_after` and `shares_burned == amount`, both of which hold at the vault-aggregate level regardless of whether `recipient` is a reachable principal — the vault's books balance perfectly even though the actual underlying asset transferred via `send-underlying` (or the ft-shares transferred via `ft-transfer?`/`ft-mint?`) is delivered to an address that cannot spend it, creating a permanent loss for the depositor/redeemer without any corresponding protocol benefit.

### Impact Explanation
If `recipient`/`to` is passed as `NULL-ADDRESS` (or any other address effectively unrecoverable, e.g. due to integration error, malicious front-end, or user mistake), the caller's principal (underlying assets on `redeem`, or vault shares on `deposit`/`transfer`) is permanently and irrecoverably frozen. This qualifies as "permanent freezing of funds," matching the Critical/High impact bar for this scan.

### Likelihood Explanation
Likelihood is moderate: it requires a caller (user, integrator, or a contract composing with the vault) to supply a bad `recipient`/`to` value, which is exactly the class of unprivileged-principal error the original FETH finding addressed. Given the vault already defines `NULL-ADDRESS` as a recognized sentinel elsewhere in the codebase, the missing check in these hot paths is a clear oversight rather than an intentional design choice.

### Recommendation
Add an explicit precondition in `deposit`, `redeem`, and `transfer` (and any other function accepting a `recipient`/`to` principal that mints, burns, or transfers value) asserting `(not (is-eq recipient NULL-ADDRESS))` / `(not (is-eq to NULL-ADDRESS))`, returning a dedicated error (e.g. `ERR-INVALID-ADDRESS`, which already exists as a constant in these contracts) before performing the mint/burn/transfer.

### Proof of Concept
1. Attacker/user calls `deposit(amount, min-out, NULL-ADDRESS)` on `v0-vault-stx.clar`.
2. `receive-underlying` pulls `amount` from the caller into the vault, `assets` is incremented, and `ft-mint?` mints `inkind` shares to `NULL-ADDRESS`.
3. The shares are now permanently unspendable since no private key corresponds to `NULL-ADDRESS`; the depositor has lost `amount` of underlying with no ability to redeem the minted shares.
4. Equivalently, calling `redeem(amount, min-out, NULL-ADDRESS)` burns the caller's shares correctly but sends the underlying via `send-underlying` to `NULL-ADDRESS`, permanently freezing the withdrawn assets while `assets` is decremented as if the withdrawal succeeded for a legitimate recipient.
