This is a legitimate finding: the webhook `shop` field is used for tenant attribution but is not covered by the HMAC signature.

**Analysis of the identity binding break:**

The `Request` class exposes `shop` purely from the untrusted `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature only covers the raw request body: [1](#0-0) 

```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
...
def to_signable_string
  @raw_body
end
```

`Registry.process` validates the HMAC over the body only, then immediately trusts `request.shop` (and `request.topic`) — fields never included in the signed content — to build the `WebhookMetadata` that is handed to the app's handler: [2](#0-1) 

The binding that should hold is: `shop_attributed_to_event == shop_that_actually_produced_the_signed_body`. Because `shop` sits outside `to_signable_string`, that equality is never checked — only `hmac(body) == hmac(body)` is checked, which says nothing about which shop the body belongs to.

**Exploitability:** Any merchant who installs the app (a routine, unprivileged action) receives genuine webhook deliveries signed with the app's single shared `api_secret_key` (the same secret used for every installed shop, since webhook HMAC has no per-shop key). That merchant can capture a `(raw_body, hmac)` pair from their own legitimate webhook and replay it to the app's public webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `Utils::HmacValidator.validate` will still pass (body/HMAC pair is authentic), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event came from the victim shop. Any app logic that uses `WebhookMetadata#shop` to select which merchant's data/session to act on (a extremely common and directly encouraged pattern — see the handler example using `data.shop` in `test/webhooks/registry_test.rb` lines 246–252) will act on the wrong tenant.

This matches the report's underlying bug class — trusting/asserting something (here, tenant identity) that wasn't actually verified by the check performed — and satisfies the rule allowing "a field acted on but not covered by the HMAC," crossing a tenant boundary without needing any secret or privileged access. ### Title
Webhook `shop` (tenant) is not covered by HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#shop` is read directly from the `x-shopify-shop-domain` header, which is not part of `to_signable_string` (only the raw body is signed). `Registry.process` validates the HMAC of the body but then passes the unverified `shop` header straight into `WebhookMetadata`, which app handlers use to identify the tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [4](#0-3) 

`Request#shop` is derived from a header, entirely outside the HMAC-signed data: [5](#0-4) 

`Registry.process` checks HMAC over the body, then forwards `request.shop` unchanged to the handler: [2](#0-1) 

Since `api_secret_key` is shared across all shops that install the app, any merchant can obtain valid `(body, hmac)` pairs for their own shop and replay them against the app's webhook endpoint with a forged `shop-domain` header pointing at a different (victim) shop.

### Impact Explanation
This is a cross-tenant identity binding failure: the value used to select/attribute a tenant (`shop`) is not authenticated by the same mechanism (HMAC) that authenticates the payload. An app that keys off `WebhookMetadata#shop` to load merchant records, session/access tokens, or write data can be tricked into operating on/exposing another merchant's data using only a webhook payload the attacker legitimately owns. This is a Critical-class impact (cross-tenant access) per the rubric.

### Likelihood Explanation
Requires only that the attacker be able to install the app on their own store (ordinary onboarding, no privilege) and send an arbitrary HTTP request to the app's public webhook endpoint with a custom header — no secrets, tokens, or elevated access needed.

### Recommendation
Include the shop domain (and topic) in the value that is HMAC-verified, or otherwise cryptographically bind `shop` to the signed body (e.g., require the app to independently verify that the shop in the header matches a shop for which the app expects this specific webhook subscription/topic, or validate against Shopify's webhook `X-Shopify-Webhook-Id` via an authenticated Admin API lookup instead of trusting the header at face value). At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant selection without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`, triggering a genuine webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H` (computed by Shopify using the app's shared `api_secret_key` over `B`).
2. Attacker captures `(B, H)`.
3. Attacker POSTs to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged, still valid), but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds (body/HMAC match); `Registry.process` invokes the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`.
5. If the handler uses `shop` to look up/act on victim's stored session or data, the attacker has achieved cross-tenant action using a payload they authored.
