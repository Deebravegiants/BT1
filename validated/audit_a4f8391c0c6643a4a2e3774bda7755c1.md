### Title
Attacker-controlled swap route can add unauthorized wallet-token transfers to the caller’s signed authorization tree - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
`swap_collateral`, `multiply`, `swap_debt`, and `repay_debt_with_collateral` accept opaque `swap: Bytes` and pass it to the configured router. The controller constrains only its own input-token transfer and measured balances, while route-selected code may execute beneath the caller’s original authorization and request additional transfers from that caller. An attacker can therefore craft a route whose nested contract transfers unrelated wallet tokens from the signer to the attacker; if the signer approves the poisoned authorization tree produced by simulation, those transfers execute. [1](#0-0) [2](#0-1) 

### Finding Description
`process_swap_collateral` authenticates `caller` and checks account ownership or delegation, but treats the supplied `swap` payload as opaque routing data. [3](#0-2) 

`swap_tokens` authorizes only `token_in.transfer(controller, configured_router, amount_in)` for the controller, then invokes `router.execute_strategy(&controller, &amount_in, swap)`. [1](#0-0)  The helper’s controller authorization has no nested invocations, so it does not authorize arbitrary controller spending. [4](#0-3) 

The missing confinement is on the user-facing authorization path: third-party code reached through the payload can request a token transfer from `caller`, and simulation records that transfer as a child of the caller’s original `swap_collateral` authorization. [2](#0-1)  The controller’s subsequent checks cover only router input overspend and positive measured output, not whether unrelated authorization children were introduced. [5](#0-4) 

### Impact Explanation
An attacker can steal tokens held directly in the victim’s wallet, including assets unrelated to the lending position and amounts beyond the routed collateral. [6](#0-5)  The route can still return fair output, so the position-level accounting and post-swap risk checks can succeed while the unrelated wallet transfer also succeeds. [7](#0-6)  This is theft of user funds rather than route-quality loss because the malicious hop adds a separate caller-signed transfer outside the intended swap input. [8](#0-7) 

### Likelihood Explanation
Any unprivileged user can supply the `swap` argument to `swap_collateral`, and an attacker can present the resulting poisoned authorization tree to a victim through a malicious frontend, quote, or signing flow. [9](#0-8) [2](#0-1)  Exploitation requires the victim to sign the authorization tree containing the extra transfer, but transaction simulation can surface that child without making its malicious origin obvious to a client that does not decode the route and compare every authorization descendant. [10](#0-9) [11](#0-10) 

### Recommendation
Constrain route execution to audited venue contracts or otherwise reject payload-selected contracts that can issue caller-authorized token transfers. [2](#0-1)  The controller or router interface should expose the exact expected authorization tree, and strategy execution should reject any route that introduces caller-authorized sub-invocations beyond the intended input payment. [1](#0-0)  Until contract-level confinement exists, clients must decode every route, enumerate the simulated authorization tree, and reject any caller authorization child other than the expected input transfer. [12](#0-11) 

### Proof of Concept
1. The victim owns a supplied `USDC` position and also holds `WALLET_BALANCE` of an unrelated token. [13](#0-12) 
2. The attacker supplies `swap` bytes naming an attacker-deployed hop contract. [14](#0-13) 
3. The router invokes that hop while processing the victim’s `swap_collateral(caller, account_id, current, amount, new, swap)` call. [15](#0-14) 
4. The hop calls `wallet_token.transfer(victim, attacker, WALLET_BALANCE)`. [16](#0-15) 
5. Simulation records the malicious transfer as a child under the victim’s `swap_collateral` authorization. [8](#0-7) 
6. If the victim signs that returned tree, execution moves the full unrelated wallet balance to the attacker while still crediting the expected swap output. [11](#0-10)

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
}
