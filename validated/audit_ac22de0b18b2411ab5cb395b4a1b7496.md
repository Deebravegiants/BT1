### Title
Webhook HMAC Does Not Cover the `shop-domain` Header, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (and `topic`/`api_version`/`webhook_id`) values are read directly from unauthenticated HTTP headers. `Webhooks::Registry.process` validates the HMAC and then forwards the header-derived `shop` value, unauthenticated, to the app's webhook handler as the tenant identifier.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of the signed content: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` passed to the app's handler, with no additional binding to the signed bytes: [4](#0-3) 

Equality that should hold but does not: `bytes_verified_by_hmac == bytes_used_to_identify_the_tenant`. Here, `bytes_verified_by_hmac = raw_body` while `bytes_used_to_identify_the_tenant = header["shop-domain"]`, which is disjoint from the signed payload. Any party capable of sending an HTTP request to the app's public webhook endpoint (which is an unauthenticated internet-facing endpoint by design) can take a body+HMAC pair that Shopify legitimately generated for one shop (e.g., the attacker's own store, to which they are a legitimate merchant/tenant) and resubmit it with a different `shopify-shop-domain` header value. `HmacValidator.validate` will still report success, because it never inspects the header, and `Registry.process` will hand the handler `WebhookMetadata` claiming the payload came from an arbitrary victim shop.

### Impact Explanation
This breaks the shop-authentication boundary the webhook signature is supposed to provide. Any consuming app that uses `WebhookMetadata#shop` (as documented/intended) to select per-tenant state, storage, or access tokens will process attacker-controlled webhook bodies under the identity of a different, arbitrary shop — a cross-tenant access vulnerability satisfying the "Critical - cross-tenant access" bar.

### Likelihood Explanation
Likelihood is high: the webhook endpoint is a public HTTP endpoint by design (any unprivileged internet user can POST to it), no access token or secret is required to exploit it, and the attacker only needs one legitimate (body, hmac) pair for any tenant (including their own) to replay against the endpoint with a forged `shop-domain` header.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` (i.e., all fields consumed downstream as trust-relevant metadata) in the HMAC-signed content, or otherwise cryptographically bind the header values to the signature, so that `HmacValidator.validate` cannot succeed if any of those fields have been tampered with independently of the body.

### Proof of Concept
1. App registers a webhook handler that uses `WebhookMetadata#shop` to select the tenant's session/access token (the documented/intended usage, see `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))`) [5](#0-4) .
2. Attacker owns/controls shop `attacker.myshopify.com` and triggers a real event (e.g., product update) so Shopify delivers a genuine webhook to the app's endpoint with body `B` and a valid `x-shopify-hmac-sha256: H` computed by Shopify over `B` with the app secret.
3. Attacker replays the exact same request to the same endpoint, but changes only the `x-shopify-shop-domain` header to `victim.myshopify.com`, keeping body `B` and header `H` unchanged.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged header into `request.shop == "victim.myshopify.com"`.
5. `HmacValidator.validate(request)` recomputes HMAC over `B` only, matches `H`, and returns `true` — [6](#0-5) .
6. `Registry.process` calls the handler with `WebhookMetadata(shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to act on attacker-supplied data under the victim tenant's identity.
