### Title
Stale `FeeMetadata` left after GET-response delivery enables a second relayer-fee payout via the GET-timeout path - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming(GetResponse, address relayer)` pays the relayer fee out of `_requestCommitments[commitment].fee` but never clears that storage slot on success, unlike the timeout-dispatch functions in the same contract, which explicitly `delete _requestCommitments[commitment]` before invoking the module callback.

### Finding Description
`CVE-2019-8912` is a bug class where a "release" routine forgets to null out a structure member, leaving a stale reference that is later reachable and misused. The direct Solidity analog here is `EvmHost.dispatchIncoming` for `GetResponse`: [1](#0-0) 

```
function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
    // replay protection
    bytes32 commitment = response.request.hash();
    _responseReceipts[commitment] = ResponseReceipt({ relayer: relayer, responseCommitment: response.hash() });
    (bool success,) = _bytesToAddress(response.request.from).call(...onGetResponse...);
    if (!success) { delete _responseReceipts[commitment]; return; }
    // reward the relayer fee
    uint256 fee = _requestCommitments[commitment].fee;
    if (fee != 0) { IERC20(feeToken()).safeTransfer(relayer, fee); }
    emit GetRequestHandled(...);
}
```

Compare this to the two `dispatchTimeOut` overloads immediately below it, both of which delete the `FeeMetadata` entry (with a compensating restore on failed callback) as part of the "release" of the request: [2](#0-1) 

The GET-response path is the only one of the three "final disposition" paths for a request (`dispatchIncoming(GetResponse,...)`, `dispatchTimeOut(GetRequestTimeout,...)`, `dispatchTimeOut(PostRequestTimeout,...)`) that leaves `_requestCommitments[commitment]` populated after the request has been fully settled. The `FeeMetadata` struct (including `.fee` and `.sender`) for that commitment remains live in storage indefinitely — a stale reference to funds that have already been disbursed.

Replay of `dispatchIncoming(GetResponse,...)` itself is blocked because `HandlerV2.handleGetResponses` checks `responseReceipts(...).relayer != address(0)` before calling it: [3](#0-2) . However, I was not able to confirm within the available tool budget whether the GET-timeout message-handling function in `HandlerV2.sol` (the counterpart to `handlePostRequestTimeouts` for GET requests) checks `_responseReceipts` for the same commitment before accepting a timeout proof and calling `host.dispatchTimeOut(GetRequestTimeout,...)`. If it does not perform that check, a relayer/dispatcher could, after a response has already been delivered and its fee paid, also submit a valid timeout proof (the request's `timeoutTimestamp` may still be reachable independent of delivery status) and trigger a second, redundant payout of the same `fee` amount — this time refunded to `meta.sender` — because `_requestCommitments[commitment].fee` was never cleared by the response path.

### Impact Explanation
If the timeout path lacks a response-delivered guard, this is a direct theft/double-payment of protocol fee-token funds: the same escrowed relayer fee is paid out twice for a single GET request — once to the relayer on response delivery, once to the original sender on a later timeout proof — draining the host's fee-token balance by the duplicated amount. This matches the "concrete theft ... unbacked mint" bar in the validation rules for a Medium/High analog. Even absent full confirmation of the second payout path, leaving `FeeMetadata` un-cleared after settlement is a genuine defect relative to the pattern the rest of the contract follows, and is the exact bug class named in the CVE (failure to null a released reference).

### Likelihood Explanation
Reachable by any relayer/dispatcher submitting two permissionless messages through `HandlerV2`: a `GetResponseMessage` (to trigger the fee payout) followed by a `GetRequestTimeoutMessage` for the same commitment (to trigger the second payout), provided the timeout-handling code path does not itself gate on `_responseReceipts`. This requires no privileged role — only the ability to relay a valid response proof and, separately, a valid non-membership/timeout proof for the same request, both of which unprivileged relayers routinely produce. The likelihood is contingent on the unverified guard in the GET-timeout handler in `HandlerV2.sol`.

### Recommendation
Delete `_requestCommitments[commitment]` inside `dispatchIncoming(GetResponse memory response, address relayer)` immediately after the fee is read (mirroring the pattern in both `dispatchTimeOut` overloads), so the `FeeMetadata` cannot be read again by any later timeout or retry path. Additionally, audit the GET-request timeout handler in `HandlerV2.sol` to confirm it rejects a timeout submission when `host.responseReceipts(commitment).relayer != address(0)`, independent of this storage fix, so settlement is provably single-shot from both directions.

### Proof of Concept
Conceptual sequence (pending confirmation of the timeout handler's guard):
1. App dispatches an outgoing GET request; `_requestCommitments[commitment]` is stored with a non-zero `fee` and `sender`.
2. Relayer submits a valid `GetResponseMessage` via `HandlerV2.handleGetResponses` → `EvmHost.dispatchIncoming(GetResponse,...)` succeeds → relayer is paid `fee` from the fee token, but `_requestCommitments[commitment]` is left intact with the same `fee` value.
3. The same or a colluding party later submits a `GetRequestTimeoutMessage` for the identical commitment (if the timeout condition and any handler-side check permit it despite the response already existing) → `EvmHost.dispatchTimeOut(GetRequestTimeout,...)` reads the still-populated `meta.fee` and refunds it a second time to `meta.sender`.
4. Net effect: the fee-token balance held by the host is depleted by one extra `fee` payout per exploited commitment.

    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
