### Title
Webhook `shop` (tenant) identity is not bound to the HMAC signature, enabling cross-tenant webhook injection - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` (and `topic`/`webhook_id`) values used to route and process the webhook are taken from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then trusts `request.shop` for tenant attribution without any check that this value was part of what was actually verified.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors are pulled straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC solely over `to_signable_string` (the body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` validates only that HMAC, then forwards `request.shop` (an unsigned header value) straight into the handler as the tenant identity: [4](#0-3) 

The broken identity binding, expressed as an equality that should hold but does not:
`HMAC-verified bytes (raw_body) == bytes acted upon for tenant attribution (shop header)`

Because the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header is not part of the signed content, any entity that can obtain one genuine `(raw_body, hmac)` pair signed with the app's real `client_secret` — for example a shop that has installed the app itself and receives a legitimate webhook delivery to its own endpoint — can resend that exact `(raw_body, hmac)` pair to the app's webhook receiver while substituting the `shop-domain` header with a different (victim) shop's domain. `HmacValidator.validate` will still succeed because it never looks at the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: an unprivileged party (any merchant who can install the app on their own store, or an attacker with visibility into a wire-level webhook delivery) can get the library to attribute forged/replayed body content to an arbitrary shop of their choosing. Depending on the handler's use of `WebhookMetadata.shop` (e.g., looking up the target shop's offline session/access token, writing to that shop's records, or triggering shop-scoped side effects), this is a cross-tenant data injection / cross-tenant access vector — the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is moderate to high in embedded/multi-tenant app deployments: obtaining one valid `(body, hmac)` pair is trivial (install the app on a free/dev store and subscribe to a webhook topic), and the header-swap-and-replay requires no possession of `client_secret`, access tokens, or any privileged credential — only the ability to make an HTTP request to the app's public webhook endpoint with attacker-chosen headers, which is exactly the "unprivileged internet user" threat model this scan targets.

### Recommendation
Bind the tenant/topic identity to the verified content, not just the body:
- Include `shop`, `topic`, and `webhook_id` in the HMAC-signable string (matching what Shopify itself covers), or
- After HMAC validation, independently verify that the `shop` header corresponds to a shop with a known/expected relationship to this specific delivery (e.g., cross-check against the webhook subscription's registered shop via the API, not solely the header), and treat the header purely as routing metadata rather than an authoritative tenant identifier for security-sensitive operations.
- At minimum, document prominently that `WebhookMetadata#shop` is not cryptographically bound to the HMAC and must not be trusted by host applications as an authenticated tenant identifier without additional verification.

### Proof of Concept
1. Install the target app on an attacker-owned/dev shop `attacker-shop.myshopify.com` and trigger a webhook subscription (e.g., `orders/create`) so Shopify delivers a legitimate webhook to the app's endpoint. Capture the exact `raw_body` and the `X-Shopify-Hmac-Sha256` header value — both are valid because Shopify signed them with the real `client_secret`.
2. Replay this exact request to the same webhook endpoint, keeping `raw_body` and the `hmac-sha256` header unchanged, but replacing the `X-Shopify-Shop-Domain` header with `victim-shop.myshopify.com`.
3. Observe that `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which passes (validation only checks `raw_body`), then invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` — i.e., the gem attributes attacker-controlled/replayed webhook data to a shop the attacker does not control or own.
