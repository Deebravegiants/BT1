### Title
Webhook `shop` (and topic/api-version/webhook-id) headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw HTTP body when validating a webhook's authenticity, while the `shop` (and `topic`, `api_version`, `webhook_id`) values that are handed to the app's webhook handler are taken from unauthenticated HTTP headers. Because these header values are never part of the HMAC computation, an attacker who can obtain one validly-signed webhook body (e.g., by triggering a real webhook delivery to their own installed app/dev store) can replay that exact body with a forged `shopify-shop-domain` header, and the gem will accept it as authentic and hand the forged shop identity to the app's handler.

### Finding Description
`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `shop`, `topic`, `api_version`, and `webhook_id` — the values actually used downstream to identify the tenant and dispatch to a handler — are pulled straight from the (unsigned) HTTP headers: [3](#0-2) 

`Registry.process` only calls `Utils::HmacValidator.validate(request)` (which checks the body-derived HMAC) and then trusts `request.shop`, `request.topic`, etc. to build `WebhookMetadata` passed to the handler: [4](#0-3) 

The identity binding that should hold is: `shop authenticated by HMAC == shop delivered to handler`. Because the header carrying `shop` is outside the signed bytes, this equality is not enforced — the body's HMAC only proves "this body byte-sequence was signed with the app's secret at some point for some shop," not "this body came from `shop-domain: X`."

### Impact Explanation
An attacker who controls (or has installed the app on) their own development/test shop can capture a legitimately-signed webhook payload delivered to their app (same `client_secret`, so HMAC is valid), then replay that request to the app's webhook endpoint while substituting the `x-shopify-shop-domain`/`shopify-shop-domain` header with a victim merchant's domain. `HmacValidator.validate` will still pass because it only checks the raw body against the shared secret, and `Registry.process` will invoke the handler with `WebhookMetadata` claiming the data belongs to the victim shop. If the host application uses `request.shop` (as returned by this gem) to select per-tenant data, credentials, or session records, this results in cross-tenant data confusion/injection — data or events attributed to the wrong merchant tenant.

### Likelihood Explanation
The attacker needs a legitimately-signed webhook body, which is trivially obtainable by installing the app on any shop the attacker controls (a normal, low-privilege action) and capturing a real webhook delivery. No access to `api_secret_key`, tokens, or victim credentials is required. The only prerequisite is that the app's webhook receiving endpoint is reachable and uses this gem's `Webhooks::Request`/`Registry.process` as documented, which is the standard integration pattern recommended by this gem.

### Recommendation
Include the shop domain (and ideally topic/webhook id/api version) inside the signed payload verification, or otherwise cryptographically bind the header-derived `shop` value to the signed body — e.g., verify the HMAC over a canonical string that incorporates `shop-domain` together with the body, or independently validate that the shop present in the signed body/GraphQL context matches the header before trusting `request.shop` for tenant dispatch. At minimum, document that `request.shop` is unauthenticated and must not be used as a tenant-selection key without additional verification (e.g., cross-checking against a known/registered shop).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook, e.g.:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid HMAC of body B for attacker's shop>
x-shopify-shop-domain: attacker.myshopify.com
Body: B
```
2. Attacker replays the exact same body `B` and HMAC header, but changes only the shop header:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <same valid HMAC of body B>
x-shopify-shop-domain: victim.myshopify.com
Body: B
```
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `victim.myshopify.com` from the header [5](#0-4) .
4. `Utils::HmacValidator.validate(request)` succeeds because it only recomputes the HMAC over `@raw_body` (`B`), which is unchanged and still matches the secret [1](#0-0) .
5. `Registry.process` dispatches to the handler with `WebhookMetadata.new(... shop: request.shop ...)` set to `victim.myshopify.com`, even though the payload actually originated from the attacker's own shop [4](#0-3) .
