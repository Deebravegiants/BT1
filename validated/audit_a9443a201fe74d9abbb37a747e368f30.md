### Title
Webhook `shop` tenant identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body via HMAC, while the `shop` (tenant) identity used by `ShopifyAPI::Webhooks::Registry.process` to route and label the resulting event is taken from an HTTP header that is completely outside the HMAC's coverage. An attacker who owns any Shopify store can legitimately trigger a webhook to obtain a body/HMAC pair signed by the app's real `client_secret`, then replay that exact body+HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header to name a different shop, forging a webhook that the app will process as if it originated from that victim shop.

### Finding Description
`Request#to_signable_string` returns only the raw body:

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`Utils::HmacValidator.validate` computes/verifies the HMAC exclusively against `to_signable_string`:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [2](#0-1) 

Meanwhile, `Request#shop` — the tenant-identity field the registry acts on — is read straight from the (attacker-controllable, in a directly-exposed webhook endpoint) `x-shopify-shop-domain` header, with no cryptographic binding to the signed payload:
```ruby
sig { returns(String) }
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [3](#0-2) 

`Registry.process` validates the HMAC (over body only) and then immediately trusts `request.shop` to build the metadata handed to the app's handler:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

The broken identity binding, stated as an equality that should hold but doesn't:
`shop_bound_by_HMAC == shop_used_by_handler` is **false** — the value verified by the signature (`raw_body` only) does not include or bind the `shop` value that `Registry.process` passes on to `WebhookHandler#handle`. Any party capable of producing one valid (body, hmac) pair for the app — trivially available to any merchant who installs the app and can trigger their own webhooks — can pair that valid HMAC with a forged `x-shopify-shop-domain` header naming an arbitrary victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: a merchant/attacker can make the app believe a webhook body (e.g., `orders/create`, `customers/data_request`, `app/uninstalled`) originated from a different, victim shop. Any host application logic that keys per-tenant data, session lookups, or entitlement decisions off `WebhookMetadata#shop` (the documented/intended use of the field returned by this gem) will process or store attacker-supplied data under the wrong tenant, i.e. cross-tenant data injection/corruption. This satisfies the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Medium-High: exploitation requires only that the webhook endpoint is reachable over the internet (standard deployment) and that the attacker controls at least one Shopify store to obtain one legitimate (body, HMAC) pair from Shopify — no access to the app's `client_secret`, access tokens, or any privileged account is needed.

### Recommendation
Bind the tenant identity into the signed payload the gem verifies, e.g., include the `shop-domain` header (and other routing-relevant headers) in `to_signable_string`, or independently authenticate the `shop` value (for instance by requiring it to match the session/shop the webhook was registered for) before it is handed to `WebhookHandler#handle`. At minimum, document and enforce that `Registry.process` must not trust `request.shop` unless it is cryptographically bound to the verified body.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body `B` and the legitimate `X-Shopify-Hmac-Sha256: H` header sent by Shopify (H is a valid HMAC over `B` using the app's real `client_secret`).
2. Attacker sends a new POST to the app's public webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`. [5](#0-4) 
4. `Registry.process` builds `WebhookMetadata.new(..., shop: request.shop, ...)` with `shop == "victim.myshopify.com"`, and dispatches to the app's registered handler as if the event legitimately came from the victim shop. [6](#0-5)
