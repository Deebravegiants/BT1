### Title
Front-runnable `initialize` in `HyperFungibleTokenUpgradeable`/`WrappedHyperFungibleTokenUpgradeable` lets an attacker seize ownership and forge the bridge's host/peer configuration - ([File: sdk/packages/core/contracts/apps/HyperFungibleTokenUpgradeable.sol])

### Summary
`HyperFungibleTokenUpgradeable.initialize` and `WrappedHyperFungibleTokenUpgradeable.initialize` are `public` functions guarded only by OpenZeppelin's `initializer` modifier, which prevents double-initialization but places **no restriction on who may call it**. Unlike `IntentGatewayV2` and `SimplexPaymaster` in the same codebase — which are deployed atomically via `ERC1967Proxy(implementation, initData)` so `initialize` executes inside the proxy's own constructor and can never be front-run — these two token contracts have no such atomic-deployment guarantee anywhere in the repo, and are documented/intended for standalone deployment by third-party integrators.

### Finding Description
The constructor only disables initializers on the raw implementation contract: [1](#0-0) 

`initialize` itself carries no `msg.sender` check, and directly sets the `initialOwner` from a caller-supplied parameter: [2](#0-1) 

The wrapped variant has the identical pattern: [3](#0-2) 

Whereas `IntentGatewayV2.initialize` and `SimplexPaymaster.initialize` are safe specifically because every deployment script in the repo (`DeployIntentGateway.s.sol`, `DeploySimplexPaymaster.s.sol`) wires the `initialize` call into the `ERC1967Proxy` constructor's `initData`, so no transaction window exists where the proxy is deployed but uninitialized: [4](#0-3) 

No equivalent atomic-proxy deployment path exists anywhere in the repo for `HyperFungibleTokenUpgradeable` or `WrappedHyperFungibleTokenUpgradeable` — they are meant to be deployed as a proxy pointing at the implementation and then `initialize`d in a separate transaction (mirroring the plain, non-upgradeable `HyperFungibleToken`/`WrappedHyperFungibleToken` pattern shown in the docs, which uses `new HyperFungibleToken(...)` followed by a separate `configure()` call). Any address observing the proxy-deployment transaction in the mempool can submit `initialize(name, symbol, attacker)` (or `initialize(attacker)` for the wrapped variant) with higher gas and land first, becoming `owner` before the legitimate deployer's `initialize` call executes (which will then revert with `InvalidInitialization`).

Once the attacker holds `owner`, they control every privileged setter:
- `configure()` sets `_host` and `_dispatcher` to attacker-chosen addresses (host is only settable once, so the attacker permanently binds it to a malicious/mock contract they control).
- `addChain()` registers arbitrary `(chainId, moduleId)` pairs as trusted peers.

### Impact Explanation
Because `onAccept`/`onPostRequestTimeout` are gated only by `onlyHost` and a `_supportedChains` source check — both of which the attacker-as-owner fully controls — the attacker can deploy a trivial mock "host" contract, call it directly, and have it invoke `onAccept` with a forged `source` matching an attacker-registered peer, causing the token to mint arbitrary amounts to any address (`HyperFungibleTokenUpgradeable`) or release the underlying escrowed ERC20/ETH (`WrappedHyperFungibleTokenUpgradeable`) with no real cross-chain message ever delivered. This is an unbacked mint / outright theft of the wrapped underlying, and it permanently locks out the legitimate deployer, who can never regain ownership of the contract they believed they deployed.

### Likelihood Explanation
Any deployment of these upgradeable token templates that does not embed `initialize` in the proxy's constructor calldata is exposed; front-running a public mempool transaction that calls a permissionless `initialize` function is a well-known, cheap, and reliable attack (identical in mechanism to the referenced Notional `CrossCurrencyVault` report). Given the repo's own deploy scripts for other upgradeable apps (`IntentGatewayV2`, `SimplexPaymaster`) explicitly work around this exact issue by using atomic proxy construction, but no such script/pattern exists for these two token templates, the vulnerability is directly reachable by whatever deployment process integrators actually use for them.

### Recommendation
Either:
1. Always deploy these contracts via `new ERC1967Proxy(implementation, abi.encodeCall(initialize, (...)))` so `initialize` runs atomically in the proxy's constructor (as done for `IntentGatewayV2`/`SimplexPaymaster`), and document this as the only supported deployment path; or
2. Add an immutable "expected deployer/factory" check (or a `Create2`-salt-committed factory that calls `initialize` in the same transaction it deploys the proxy) so `initialize` cannot be reached by an arbitrary third party.

### Proof of Concept
1. Deployer sends a transaction deploying an `ERC1967Proxy` pointing at the `HyperFungibleTokenUpgradeable` implementation (no init data), intending to call `initialize("MyToken","MTK", deployer)` in a follow-up transaction.
2. Attacker observes the pending/most-recent proxy-creation transaction, computes the resulting proxy address, and submits `initialize("MyToken","MTK", attacker)` with higher gas so it mines first.
3. Deployer's subsequent `initialize` call reverts with `InvalidInitialization` (already initialized).
4. Attacker, now `owner`, calls `configure({host: attackerMockHost, dispatcher: attackerDispatcher})` and `addChain(anyChainId, attackerModuleId)`.
5. Attacker calls `attackerMockHost` to invoke `onAccept` on the token with a forged `source == anyChainId`, minting arbitrary token amounts to any address they choose.
