## Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` header, but the HMAC signature computed by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. Any actor who can obtain one legitimately-signed webhook body/HMAC pair (e.g. by installing the app on their own shop) can replay that exact body with a forged `shop-domain` header pointing at a different, victim shop, and the signature check still passes. This breaks the binding "shop the webhook is attributed to" == "shop the signature actually authenticates," letting an attacker inject data attributed to a shop they do not control.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shop-domain` header without any cryptographic binding to the body: [2](#0-1) 

`HmacValidator.validate` computes the signature purely over `to_signable_string`: [3](#0-2) 

`Registry.process` trusts `request.shop` as the tenant identity once the HMAC check passes, and forwards it unchecked to the app's handler as `WebhookMetadata.shop`: [4](#0-3) 

The library's own documentation confirms that apps are expected to key their business logic (job enqueueing, storage, etc.) off `data.shop` from the webhook handler, treating it as an authenticated tenant identifier: [5](#0-4) 

Because the signature never covers the shop-domain header, the equality that should hold — `shop authenticated by HMAC == shop acted upon by the handler` — does not hold. Any body+signature pair that Shopify legitimately issued for shop A (which the app's own merchant/attacker can trivially capture, since Shopify sends it directly to them for their own shop) remains valid when replayed with the header rewritten to shop B.

### Impact Explanation
This is a cross-tenant integrity bypass: a single-secret app (one `api_secret_key`/`client_secret` shared across all installed shops) cannot distinguish "genuine webhook for shop A" from "genuine webhook for shop A relabeled as shop B" using this gem's verification alone. A malicious merchant who installs the app on their own shop can synthesize webhook deliveries that the host application will process as if they originated from an arbitrary victim shop, since only `Registry.process` + `HmacValidator.validate` gate processing, and neither checks that the signed body was actually destined for the claimed shop. This matches the Critical "cross-tenant access" category — data written or actions taken by the app for shop A can be attributed to and processed against shop B's session/tenant context.

### Likelihood Explanation
Any developer that installs the app themselves (a normal, unprivileged onboarding step) can capture arbitrary numbers of validly-signed `(raw_body, hmac)` webhook pairs for topics they control (e.g. `products/update` by editing their own product repeatedly), since Shopify delivers both the body and the HMAC directly to them. They can then POST these to the app's public webhook endpoint with the `shop-domain` header rewritten to any other shop already using the app, no secret or token required. The check that would catch this — binding shop identity into the signed payload or validating `shop` against expected/registered shops per delivery — does not exist in this gem's webhook path.

### Recommendation
Include the shop domain (and ideally webhook id / topic) inside the HMAC-covered signable string, or have `Registry.process` independently verify that `request.shop` corresponds to a shop for which the app is actually expecting/has registered this webhook before invoking the handler, rather than trusting the header value implicitly once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker-shop.myshopify.com` and registers for `products/update`.
2. Attacker updates a product on their shop; Shopify delivers a webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker captures `(B, H)` (they receive it directly as the shop admin, no secret needed).
4. Attacker crafts a new HTTP POST to the same webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but header `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `HmacValidator.validate` recomputes the HMAC over `@raw_body` only (`request.rb` L35-38, `hmac_validator.rb` L26-31), which still equals `H`, so validation passes.
6. `Registry.process` invokes the topic handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` (`registry.rb` L198-199), and the host application processes attacker-controlled data as if it were an authentic event from the victim shop.
