### Title
Webhook HMAC Signature Covers Only the Raw Body, Not the `shop-domain` Header, Enabling Cross-Tenant Webhook Forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated HTTP headers and passed downstream as trusted values. Because the HMAC secret (`Context.api_secret_key`) is a single, app-wide secret shared across every installed shop, any user who can obtain one genuine, HMAC-signed webhook body from Shopify (e.g., by installing the app on their own store) can replay that exact body+HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. The signature check still passes because the shop identity was never part of the signed content.

### Finding Description
`Webhooks::Registry.process` validates the webhook using `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` and compares against `request.hmac`: [1](#0-0) 

`to_signable_string` is defined to return only `@raw_body`: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all derived directly from HTTP headers supplied by the caller, with no cryptographic binding to the signed body: [3](#0-2) 

After validation succeeds, `Registry.process` builds `WebhookMetadata` using these unauthenticated header values, including `shop: request.shop`, and dispatches it to the app's registered handler: [4](#0-3) 

This is the same class of defect described in the analog report: a value the code *acts on* (`shop`, used to attribute the webhook to a tenant) is not covered by the integrity check (`HMAC` over `raw_body` only). The equality that should hold — `shop authenticated by HMAC == shop the handler stores/acts on` — is broken, because the HMAC only authenticates `raw_body`, not `shop-domain`.

### Impact Explanation
Because `Context.api_secret_key` is one shared secret for the whole app (not per-shop), a valid `(raw_body, hmac)` pair obtained from any single tenant (including an attacker's own free/dev store) remains valid under `HmacValidator.validate` regardless of which `shop-domain` header accompanies it. An attacker can therefore forge a webhook event that the app attributes to a victim shop (`WebhookMetadata#shop`), while the HMAC check reports success. Any app logic that trusts `WebhookMetadata#shop` to look up/act on a specific tenant's data (e.g., storing data keyed by shop, triggering per-shop side effects) would perform cross-tenant actions using attacker-supplied `shop` and attacker-controlled body content — matching the Critical impact category of cross-tenant access.

### Likelihood Explanation
Exploitation requires only: (1) install the target app on any shop the attacker controls to obtain one legitimately signed webhook `(raw_body, hmac)` pair, and (2) replay it to the app's webhook endpoint with a spoofed `shopify-shop-domain` (or `x-shopify-shop-domain`) header. No access token, `client_secret`, or privileged account is needed — this is achievable by any unprivileged internet user who can install a public/dev app instance and reach the app's public webhook endpoint.

### Recommendation
Include `shop-domain` (and ideally `topic`/`webhook_id`) in the signed content that is verified, or otherwise cryptographically bind the shop identity to the payload before trusting `request.shop` in `WebhookMetadata`. At minimum, document and enforce that consuming applications must independently verify the `shop-domain` header corresponds to a shop they have a stored, valid relationship with (e.g., cross-check against a known/installed shop list) before acting on webhook data, since the current signature does not protect that field.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header — both valid under the app's shared `api_secret_key`.
2. Attacker POSTs the identical `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `@raw_body` [5](#0-4)  — validation succeeds despite the header spoof.
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` is built with `shop == "victim.myshopify.com"` [6](#0-5)  and passed to the app's handler, which processes attacker-controlled data as if it originated from the victim shop.
