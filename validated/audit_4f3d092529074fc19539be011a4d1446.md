### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by HMAC-signing only the raw request body, while the `shop-domain` header — the field the gem's `Registry.process` uses to attribute the webhook to a tenant — is never included in the signed material. This breaks the identity binding: `HMAC(raw_body)` should equal `HMAC(shop || raw_body)` (or otherwise bind shop to the signature), but here it does not.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#hmac` reads the `hmac-sha256` header: [1](#0-0) 

`HmacValidator.validate` verifies the received HMAC against `verifiable_query.to_signable_string`, i.e. the body only: [2](#0-1) 

`Registry.process` accepts the request once the body HMAC checks out, then dispatches to the handler using `request.shop`, which is read straight from the (unauthenticated-by-HMAC) `shop-domain` header: [3](#0-2) 

Because Shopify signs webhooks with the app's `client_secret`, which is shared across every shop that has installed the app (not a per-shop secret), any shop that has the app installed can obtain a genuinely-signed webhook (valid `hmac-sha256` over a body it controls, e.g. by creating an order with attacker-chosen field values in its own store). That attacker can then replay the exact same HTTP body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still passes (it only checks the body), and `Registry.process` forwards `WebhookMetadata.new(shop: <victim-domain>, body: <attacker-controlled-body>, ...)` to the app's handler.

This exactly matches the rule-bank's "field acted on but not covered by the HMAC" bug class: the `shop` value the handler trusts for tenant attribution is not the value verified by the signature.

### Impact Explanation
Any downstream app logic that uses `WebhookMetadata#shop` to select which merchant's data/session/access-token to act on (a very common pattern for multi-tenant Shopify apps) can be tricked into applying attacker-supplied webhook data under a victim shop's identity — a cross-tenant data-integrity/confusion issue. This meets the "High" bar of scope-or-binding-check bypass across a tenant boundary, since it lets one authenticated app-installer (unprivileged relative to other merchants) inject data attributed to a different merchant.

### Likelihood Explanation
Exploitation requires the attacker to be a legitimate installer of the target app (so they can generate a genuinely HMAC-signed webhook for their own store) and to be able to replay/forge the HTTP request to the app's public webhook endpoint with a modified header — both are within reach of an ordinary, unprivileged user of the app with no special credentials, satisfying the "unprivileged internet user" threat model.

### Recommendation
Bind the shop identity into the verified material instead of trusting an unauthenticated header:
- Include the `shop-domain` (and ideally `topic`/`webhook-id`) in the string that is HMAC-verified, or
- Independently confirm the `shop` header value matches a shop resolvable from an authenticated context before dispatching to handlers, or
- Document/require that host applications not use webhook `shop` for tenant attribution unless it is otherwise verified (e.g., cross-checked against known installed shops with an active session), and add a check in `Registry.process` to enforce this.

### Proof of Concept
1. App is installed on `attacker.myshopify.com` and on `victim.myshopify.com`.
2. Attacker creates an order in their own store `attacker.myshopify.com` with attacker-chosen payload contents; Shopify emits a genuine webhook: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, header `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures this request and re-sends it to the app's webhook endpoint, keeping body `B` and the HMAC header unchanged, but replacing `x-shopify-shop-domain` with `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `HmacValidator.validate` recomputes `HMAC(secret, B)` and it matches, so `Registry.process` proceeds and calls the handler with `shop: "victim.myshopify.com"` and the attacker-controlled body `B`. [3](#0-2)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
