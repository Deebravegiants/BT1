### Title
Stake reward commission split truncates fractional lamports instead of crediting them, causing silent value loss - (File: runtime/src/inflation_rewards/mod.rs)

### Summary
`commission_split` in `runtime/src/inflation_rewards/mod.rs` computes the voter and staker portions of a stake reward independently via integer division (`on * split / MAX_BPS` and `on * (MAX_BPS - split) / MAX_BPS`), each of which floors to the nearest lamport. When the commission bps does not evenly divide the reward amount, the sum of the two computed portions is strictly less than the original reward, and the residual (up to 1 lamport per split, but recurring on every stake/vote account every epoch) is neither paid to the voter nor the staker — it is simply discarded, analogous to the Gumball `swap()` bug where a user's whole input amount is consumed but only a rounded-down portion is credited back as NFTs.

### Finding Description
`commission_split` at [1](#0-0)  calculates `mine` and `theirs` symmetrically and independently using truncating integer division, and the code comment explicitly acknowledges: "we intentionally discard any residual fractional lamports." This means `mine + theirs <= on`, with the shortfall lost from the total reward amount rather than distributed to either party or accounted for elsewhere, unlike `commission_split_preserve_lamports` at [2](#0-1)  which explicitly assigns the remainder to the voter so "no lamports are lost." The property test for the lossy variant at [3](#0-2)  confirms the invariant that up to 1 lamport of the total `rewards` amount can be truncated away and unaccounted for on every call, matching the report's root cause pattern: a whole input amount is "taken" for reward accounting purposes, but a portion computed via floor-division is silently lost instead of being fully distributed to the parties entitled to it.

### Impact Explanation
This causes concrete, reproducible loss of value: the total lamports distributed via `commission_split` (`mine + theirs`) is less than the reward pool being split, for any non-0%/100% commission and any reward amount not evenly divisible by the commission bps (an extremely common case given `u64` reward amounts and `u16` bps precision). This is a real accounting divergence in the bank's inflation reward distribution/commit path, not a validator/operator-only concern — it affects the lamports actually credited to unprivileged stake and vote accounts, i.e., true, measurable value loss in a fee/rent-accounting-adjacent (reward) settlement path.

### Likelihood Explanation
High likelihood of triggering on essentially every epoch boundary for any stake account whose `(reward_amount * commission_bps)` is not an exact multiple of `MAX_BPS` (10,000), which is the overwhelming majority of reward/commission combinations, as shown directly by the test cases in `test_commission_split_bps` (e.g., `commission_split(9_900, 1) == (0, 0, true)` — the entire lamport is discarded) at [4](#0-3) .

### Recommendation
Replace all remaining production call sites of the lossy `commission_split` with `commission_split_preserve_lamports`, which computes only the staker's floored share and assigns the exact remainder (`on - staker_rewards`) to the voter, guaranteeing `voter + staker == rewards` with zero lamports lost, as already implemented and tested at [2](#0-1) .

### Proof of Concept
Using the existing test values: `commission_split(9_900, 1)` (99% commission on a 1-lamport reward) returns `(0, 0, true)` — [5](#0-4)  — meaning the 1-lamport reward is fully consumed from the pool but zero lamports are credited to either the voter or the staker, an exact analog of the reported GBT truncation loss.

I was not able to fully confirm from the index which specific call sites in `runtime/src/block_component_processor/vote_reward.rs` invoke the lossy `commission_split` versus the lamport-preserving variant for the current (non-legacy) reward path — file content for that call site was not retrievable within the tool budget, so likelihood/impact should be validated against that call site directly in a full checkout.

fn commission_split(commission_bps: u16, on: u64) -> (u64, u64, bool) {
    const MAX_BPS: u16 = 10_000;
    const MAX_BPS_U128: u128 = MAX_BPS as u128;
    match commission_bps.min(MAX_BPS) {
        0 => (0, on, false),
        MAX_BPS => (on, 0, false),
        split => {
            let on = u128::from(on);
            // Calculate mine and theirs independently and symmetrically instead of
            // using the remainder of the other to treat them strictly equally.
            // In Tower, this is also to cancel the rewarding if either of the parties
            // should receive only fractional lamports, resulting in not being rewarded at all.
            // Thus, note that we intentionally discard any residual fractional lamports.
            let mine = on
                .checked_mul(u128::from(split))
                .expect("multiplication of a u64 and u16 should not overflow")
                / MAX_BPS_U128;
            let theirs = on
                .checked_mul(u128::from(
                    MAX_BPS
                        .checked_sub(split)
                        .expect("commission cannot be greater than MAX_BPS"),
                ))
                .expect("multiplication of a u64 and u16 should not overflow")
                / MAX_BPS_U128;

            (mine as u64, theirs as u64, true)
        }
    }
}

fn commission_split_preserve_lamports(commission_bps: u16, on: u64) -> (u64, u64, bool) {
    const MAX_BPS: u16 = 10_000;
    const MAX_BPS_U128: u128 = MAX_BPS as u128;
    match commission_bps.min(MAX_BPS) {
        0 => (0, on, false),
        MAX_BPS => (on, 0, false),
        split => {
            let staker_bps = MAX_BPS
                .checked_sub(split)
                .expect("commission cannot be greater than MAX_BPS");
            let staker_rewards = u128::from(on)
                .checked_mul(u128::from(staker_bps))
                .expect("multiplication of a u64 and u16 should not overflow")
                / MAX_BPS_U128;
            let staker_rewards = staker_rewards as u64;
            let voter_rewards = on
                .checked_sub(staker_rewards)
                .expect("staker rewards cannot exceed total rewards");

            (voter_rewards, staker_rewards, true)
        }
    }
}
