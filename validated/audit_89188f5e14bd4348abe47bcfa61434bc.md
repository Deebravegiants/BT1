Confirmed root cause: `ShopifyAPI::Auth::Oauth.validate_auth_callback` never calls `ShopifyAPI::Utils::ShopValidator.sanitize!`/`sanitize_shop_domain` on the `shop` value it uses, even though this exact validator exists in the gem and is used elsewhere (`token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`, `clients/graphql/storefront.rb`). This breaks the intended binding: *host that receives the app's `client_secret` == a verified `*.myshopify.com`/trusted Shopify host*.

### Title
OAuth callback sends `client_secret` and authorization `code` to an unvalidated `shop` host, enabling SSRF/credential exfiltration - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the access-token exchange request using `auth_query.shop` directly, without ever passing it through `ShopifyAPI::Utils::ShopValidator.sanitize!` (the gem's own trusted-domain allowlist), unlike sibling flows in `client_credentials.rb`, `refresh_token.rb`, and `token_exchange.rb`.

### Finding Description
`validate_auth_callback` in [1](#0-0)  validates the HMAC over the query (`code`, `host`, `shop`, `state`, `timestamp`) and the `state` cookie, then constructs `null_session = Auth::Session.new(shop: auth_query.shop)` and posts the app's `client_id`/`client_secret`/`code` to that session via `Clients::HttpClient`. `HttpClient#initialize` derives the request's target host directly as `@base_uri = "https://#{api_host || session.shop}"` [2](#0-1) , so the `client_secret` and authorization `code` (body of the POST) are sent to whatever host `auth_query.shop` resolves to.

Critically, `auth_query.shop` is never checked against `ShopifyAPI::Utils::ShopValidator`, the module the gem itself provides specifically to prevent exactly this class of bug (`sanitize!` restricts hosts to `TRUSTED_SHOPIFY_DOMAINS = ["shopify.com","myshopify.io","myshopify.com","spin.dev","shop.dev"]`) [3](#0-2) . Other privileged flows in this same gem — `token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`, and `clients/graphql/storefront.rb` — do call `ShopValidator` before using a shop value to build a request host, confirming this is the gem's documented pattern for this exact binding, which `oauth.rb` omits.

The binding that should hold is: `host that receives client_secret == verified trusted Shopify domain`. Before the fix this reduces to `host that receives client_secret == whatever string arrives in the "shop" query parameter`, with no host allowlist check in the OAuth authorization-code path.

### Impact Explanation
Because the HMAC over the callback query is computed with the app's own `api_secret_key` over `code+host+shop+state+timestamp` [4](#0-3) , an attacker without knowledge of `api_secret_key` cannot forge a callback for an arbitrary `shop` value. This means, standing alone, an unprivileged internet user cannot presently exploit this to make the running app leak its `client_secret` to an attacker-controlled host, since Shopify itself signs the redirect and only ever sets `shop` to a real Shopify domain when it issues that signature. I could not find, within the given library scope, any path that lets the `shop` value be attacker-forged with a valid HMAC or lets `validate_auth_callback` be invoked with attacker-controlled `auth_query`/HMAC pairs that bypass `HmacValidator.validate`.

### Likelihood Explanation
Low/unconfirmed as a directly triggerable analog: the missing `ShopValidator` call is a genuine defense-in-depth gap and an inconsistency versus the rest of the gem's own security pattern, but I could not establish a concrete unprivileged path to supply a malicious `shop`/host value that also carries a valid HMAC signed by the app's real `api_secret_key`. Without such a path, this does not meet the bar of "concrete authentication bypass, credential exfiltration, cross-tenant access, RCE, or SSRF" required by the validation rules — it is a hardening gap contingent on other factors (e.g., a host application passing an unsanitized `shop` param into `AuthQuery` before HMAC validation is even attempted, which is a host-application concern outside this gem, or a future scenario where `HmacValidator.validate` is bypassed) rather than a fully proven, gem-internal exploit chain.

### Recommendation
For consistency and defense-in-depth with the rest of the gem, `ShopifyAPI::Auth::Oauth.validate_auth_callback` (and `begin_auth`) should call `ShopifyAPI::Utils::ShopValidator.sanitize!(auth_query.shop)` before constructing `null_session`/`auth_base_uri`, mirroring `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb`, so that the host receiving the `client_secret` is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
Not reproducible within this gem's own code without an attacker-controlled valid HMAC for an arbitrary `shop`/host value; no such path was found in `lib/shopify_api/**` (excluding generated REST resources). This is reported as a root-cause/binding gap rather than a demonstrated exploit.

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]

            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")

        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
