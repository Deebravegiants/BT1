### Title
Front-runnable EIP-2612 permit in `SimplexPaymaster._executePermit` allows griefing of the once-per-chain delegation bootstrap - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster` mode `0x00` (`PERMIT`) executes an EIP-2612 `permit()` call on an externally-controlled ERC-20 token as part of `_validatePaymasterUserOp`, using signature fields `(v, r, s)` carried in plaintext inside `paymasterData` of a `PackedUserOperation`. Because this signature and its parameters are visible in the public mempool/bundler before inclusion, exactly like the reported `repayWithPermit`/`supplyWithPermit` case, any third party can submit the same `token.permit(...)` call directly, consuming the owner's nonce first. When the paymaster's own `_executePermit` subsequently attempts the same permit call, the token reverts (nonce mismatch), and `_executePermit`'s `catch` block reverts the whole UserOp with `PermitFailed`.

### Finding Description
`_validatePaymasterUserOp` decodes mode `0x00` paymasterData and calls `_executePermit(userOp)` before any state is durably committed for that op: [1](#0-0) 

`_executePermit` extracts `(tokenAddr, permitAmount, deadline, v, r, s)` straight from `userOp.paymasterData()` and calls the token's `permit()`: [2](#0-1) 

This is functionally identical to the reported ZeroLend bug: a signed permit tuple `(owner, spender, value, deadline, v, r, s)` is broadcast as part of a larger transaction/UserOp before it lands on-chain. Anyone observing it in the mempool (or via ERC-4337 bundler `eth_sendUserOperation` RPC broadcast, or simulation endpoints) can call `IERC20Permit(tokenAddr).permit(owner, address(paymaster), permitAmount, deadline, v, r, s)` directly, consuming the token's sequential nonce for `owner`. This is documented in the codebase itself: the design notes explicitly acknowledge that a permit signed for this flow is front-runnable — [3](#0-2) 

The permit mode is now scoped exclusively to `DelegationService`'s first-time delegation UserOp per chain, which pairs the permit with `approve(Permit2, max)` in its own callData batch: [4](#0-3) 

Since the EIP-2612 nonce is a single sequential counter per owner (unlike Permit2's unordered bitmap), any front-run consumption of it invalidates the exact permit signed for the paymaster: [5](#0-4) 

### Impact Explanation
An unprivileged observer of the mempool/bundler traffic (no special access or profit motive required — pure griefing, matching the report's "Griefing" category) can permanently deny a specific solver account from ever completing its EIP-2612-based delegation bootstrap on a given chain: each time the solver signs and submits a new permit-mode UserOp, the attacker races it with a direct `permit()` call using the leaked `(v, r, s)`, burning the nonce and forcing `PermitFailed` revert in `_executePermit`, before `PaymasterERC20`'s prefund/transferFrom ever runs. Because this bootstrap op is a prerequisite for installing the account's Permit2 allowance (`approve(Permit2, max)` carried in the same batched callData), the account is blocked from paying gas via `SimplexPaymaster` entirely on that chain until it falls back to a native-funded approve, defeating the "zero native, stablecoins only" bootstrap the permit path exists for.

### Likelihood Explanation
High feasibility: ERC-4337 UserOps are broadcast to public bundler endpoints/mempools before inclusion, and `paymasterData` (containing `v, r, s, deadline, permitAmount`, and implicitly `owner = userOp.sender`) is fully visible pre-confirmation. No specialized tooling beyond a standard front-running bot watching bundler RPCs or the alt-mempool is required, and the token's `permit()` function is always public. The maintainers' own design docs already treat "a front-run permit loses the bid" as an accepted, known risk, but the finalized scoping (delegation-only, once per chain) actually increases the effectiveness of a targeted griefing attack: a griefer who identifies which chains a given solver is bootstrapping on can repeatedly deny that one specific, infrequent, and high-value setup op.

### Recommendation
Do not rely on a bare EIP-2612 `permit()` call whose parameters are broadcast pre-confirmation for any operation whose failure reverts the whole transaction/UserOp. Wrap `_executePermit`'s external call so a revert (e.g., nonce already used) is tolerated when the resulting allowance is already sufficient — check `IERC20(tokenAddr).allowance(owner, address(this)) >= permitAmount` (or `IERC20Permit(tokenAddr).nonces(owner)` having already advanced with the allowance in place) before treating the permit failure as fatal, mirroring the standard "permit front-run" mitigation pattern (try permit, then proceed if the allowance already covers the requested amount regardless of whether the permit call itself succeeded). Alternatively, migrate the delegation-bootstrap flow fully to Permit2's unordered-nonce `SignatureTransfer`, eliminating the sequential-nonce class of front-running entirely, consistent with the direction already taken for all non-bootstrap ops.

### Proof of Concept
1. Solver's `DelegationService` builds a first-time delegation `PackedUserOperation` with `permitBootstrap = true`, calling `buildPermitMode` to sign an EIP-2612 permit `(owner=solverAccount, spender=paymaster, value=recommended, deadline=maxUint256, v, r, s)` and packs it into `paymasterData` as mode `0x00`: [6](#0-5) 
2. This UserOp is submitted to a public bundler RPC (`eth_sendUserOperation`), making `paymasterData` (hence `v, r, s, deadline, permitAmount`) publicly visible before inclusion.
3. An attacker extracts `(v, r, s)` from the pending UserOp and calls `IERC20Permit(tokenAddr).permit(solverAccount, paymasterAddress, permitAmount, deadline, v, r, s)` directly in a higher-priority-fee transaction, consuming `solverAccount`'s permit nonce.
4. When the bundler later includes the original UserOp, the EntryPoint invokes `_validatePaymasterUserOp` → `_executePermit`, whose `IERC20Permit(tokenAddr).permit(...)` call now reverts (stale/reused nonce), and the `catch` block reverts with `PermitFailed(tokenAddr)`: [7](#0-6) 
5. The entire UserOp fails validation and is dropped/never included, denying the solver's delegation bootstrap on that chain; repeating steps 2–4 for every retry (a fresh permit with a new deadline each time) sustains the denial indefinitely.
