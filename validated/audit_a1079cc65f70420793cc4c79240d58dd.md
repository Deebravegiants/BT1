Confirmed: `Webhooks::Request#hmac` computes signature over `@raw_body` alone via `to_signable_string`, while `shop`, `topic`, `webhook_id`, and `api_version` are pulled directly from HTTP headers and never enter the signable string, yet are the values `Registry.process` trusts and forwards to the app's handler.### Title
Webhook `shop-domain`, `topic`, `webhook-id` and `api-version` are not covered by the HMAC signature, allowing cross-tenant identity spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content as the raw HTTP body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by `Registry.process` to route and attribute the webhook are read directly from unauthenticated headers.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all derived from HTTP headers that are never mixed into the signable string: [2](#0-1) .

`Registry.process` validates only this body-derived HMAC via `Utils::HmacValidator.validate(request)`, and then trusts `request.topic`, `request.shop`, `request.webhook_id`, and `request.api_version` (all header-sourced) when building the data handed to the app's registered handler: [3](#0-2) .

`HmacValidator.validate` simply recomputes the HMAC of `to_signable_string` (the raw body) with the app's `api_secret_key` and compares: [4](#0-3) . Since the `api_secret_key` is the same shared secret used for *all* shops that install a given app (it's a per-app secret, not per-shop), any two independent merchants/installations of the same app receive webhooks that are indistinguishable at the HMAC level except for their body content and headers.

**Binding broken (as an equality):** the identity attributed to the processed webhook, `request.shop` (unauthenticated header), is trusted as if it equalled the shop whose data actually produced/authorized the signed body, `hmac_valid_for(raw_body)`. These are not the same value — the HMAC proves "this body was produced by an app holder of `api_secret_key`", not "this body belongs to shop X". The code implicitly assumes `request.shop == shop_that_the_hmac_authenticates`, which is false.

### Impact Explanation
An attacker who is a legitimate (but unprivileged, from the app's perspective) merchant/installer of the target app can install the app on their own shop, capture a legitimately Shopify-signed webhook (raw body + valid `hmac-sha256` header, both signed using the app's shared `api_secret_key`), and replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with an arbitrary/victim value. Because none of these header fields are covered by the HMAC, `HmacValidator.validate` still returns `true`, and `Registry.process` will invoke the app's webhook handler with attacker-chosen `shop`/`topic`/`webhook_id` metadata paired with attacker-controlled body content. Any host application that relies on `WebhookMetadata#shop` to decide which merchant's data record to update (a common and expected usage pattern, since the docs present `shop` as the authenticated tenant identifier) can be made to attribute forged data to another tenant — a cross-tenant data-integrity/confusion issue for the merchant identity binding.

### Likelihood Explanation
The prerequisite (owning any single valid installation of the app, i.e., being an unprivileged merchant of that app) is trivial to obtain for any public/publicly-installable Shopify app, and no `api_secret_key`, access token, or other privileged credential is required — the attacker only replays an already Shopify-issued webhook they legitimately received for their own shop. The library provides no shop/topic binding to compensate, so any host application that trusts `WebhookMetadata#shop` as an authenticated tenant identifier (matching this gem's own documented `shop:` field on `WebhookMetadata`) is exposed.

### Recommendation
- Include `shop`, `topic`, `webhook_id`, and `api_version` (at minimum `shop`) in the signable string used for HMAC computation, or otherwise cryptographically bind them to the verified body.
- If Shopify's HMAC scheme is defined to cover only the body (as it is today, per Shopify's actual webhook HMAC spec), document explicitly and loudly that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are **not** authenticated by `HmacValidator.validate` and must not be trusted as tenant identifiers without additional verification (e.g., cross-checking against a known/registered shop list or session store).
- Consider exposing a stricter verification mode that rejects a webhook if the header-derived `shop` does not correspond to an actively registered/installed shop tracked by the host app before invoking handlers.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Shopify sends a legitimate webhook to the app's endpoint: body `B`, headers including `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `api_secret_key`) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker intercepts/captures `(B, H)` and replays a POST to the same webhook endpoint with the same body `B` and same HMAC header `H`, but with `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shopify-shop-domain" => "victim-shop.myshopify.com", "shopify-hmac-sha256" => H})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation succeeds (see [3](#0-2)  and [5](#0-4) ).
5. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...)`, causing the host application to process attacker-controlled data as though it belonged to `victim-shop.myshopify.com`.
