### Title
Residual/stranded token balances left in `ExternalActionSwap` can be swept into an attacker's own on-chain UTXO via attacker-controlled router calldata and unlimited router approval - (File: `contracts/external-actions/swaps/ExternalActionSwap.sol`)

### Summary
`ExternalActionSwap.swap` only ever consumes/returns index `0` (input) and `1` (output) of `erc20TokenAddresses`, so any additional token whose `deltaAmountChanges[i] < 0` is transferred by `Hinkal._externalTransact` to the swap action but is never used or refunded, becoming a stranded balance inside the action contract [1](#0-0) . Because the action grants the router unlimited allowance on the input token every call and computes the swap's credited output strictly from a balance delta rather than from the amount actually escrowed for that transaction, a later unprivileged caller can supply LI.FI calldata (`externalActionMetadata`, fully attacker-controlled) that pulls in and swaps any stranded token balance together with their own funds, crediting the entire resulting output to their own on-chain-created UTXO.

### Finding Description
The claimed invariant is: *tokens leaving the action in a transaction == `-deltaAmountChanges` that Hinkal sent to it that transaction*. This is violated whenever a residual balance already sits in the action contract before `swap()` is called.

Root cause chain:
1. `Hinkal._externalTransact` transfers to the action every token with negative `deltaAmountChanges[i]`, for **all** indices in `erc20TokenAddresses` [2](#0-1) , but `ExternalActionSwap.swap` only ever reads index `0` (`inputToken`) and index `1` (`outputToken`) [3](#0-2) . Any token placed at index ≥ 2 with a negative delta is sent to the action and never referenced again — it is neither swapped, refunded, nor represented in the returned `utxoSet`. This satisfies Hinkal's own per-token balance equation for that same transaction (`balanceDif == amountChanges[i] + utxoAmount`, with `utxoAmount == 0`) [4](#0-3) , so the check passes while the funds become stranded inside the action contract.
2. `LifiExternalAction.callRouter` calls `approveUnlimited(inputToken, router)` every invocation and then executes `router.call(externalActionMetadata)` where `externalActionMetadata` is fully attacker-supplied calldata [5](#0-4) . The router therefore has standing unlimited allowance over whatever `inputToken` balance the action contract holds — not just the amount Hinkal transferred for the current call.
3. `swappedAmount` is computed purely as `getERC20OrETHBalance(outputToken) - balanceBefore`, i.e., an absolute balance delta with no check that only `inputAmount` of `inputToken` was consumed [6](#0-5) . There is no post-call assertion in `swap()` that the action's `inputToken` balance decreased by exactly `inputAmount`.
4. The entire `swappedAmount` (minus fees) is forwarded to Hinkal and wrapped into a single on-chain-created `UTXO` addressed to the caller's own `stealthAddressStructure` [7](#0-6) . Because this output is an on-chain-created commitment, the circuit does not independently constrain its amount — Hinkal's balance equation (`balanceDif == amountChanges[i] + utxoAmount`) is satisfied by construction since `utxoAmount` and the actual Hinkal balance increase are the same self-referential value, forcing `amountChanges[1]` toward `0` and leaving the UTXO amount fully determined by the (attacker-influenced) real swap execution, not by any proof-verified quantity.

Exploit flow: an attacker submits their own valid proof/UTXOs through `Hinkal.transact` targeting the swap action, with `erc20TokenAddresses[0] = inputToken` (the token stranded from a prior transaction), a small legitimate `inputAmount`, and `externalActionMetadata` crafted so the LI.FI router pulls more than `inputAmount` from the action (using the standing unlimited approval) — sweeping in the stranded residual — and swaps it for `outputToken`. The full resulting `swappedAmount`, including the value derived from the stranded tokens that never belonged to the attacker, is credited to the attacker's own on-chain UTXO.

None of the existing guards catch this: `performHinkalChecks`/`dimensionsCheck` only validate array-length consistency, `checkOnchainCreation` and the slippage `require(circomData.slippageValues[1] != 0, ...)` only bound the caller's own declared min/max, and the per-token balance equation in `Hinkal.sol` is satisfied because it is computed relative to Hinkal's own balance change, not the action's internal balance provenance.

### Impact Explanation
An unprivileged attacker can directly steal value that another user's transaction stranded inside the swap action contract (or any leftover dust from partial-fill swaps), converting it into their own shielded UTXO. This is direct theft of in-flight/shielded protocol funds and is repeatable for every occurrence of a stranded/residual balance, matching the Critical severity category (direct theft of shielded or in-flight user funds).

### Likelihood Explanation
Requires a residual balance to exist in the action contract — either from a prior transaction that included an extra token index (≥2) with a negative delta not consumed by `swap()`, or from any inputToken dust left after a partial-fill/multi-hop LI.FI swap. Given `swap()` never validates that exactly `inputAmount` of `inputToken` was consumed, and grants unlimited allowance every call, an attacker only needs to observe an on-chain residual balance (visible via `balanceOf`) and then craft matching LI.FI calldata. This is a low-cost, fully unprivileged attack (attacker only needs to run their own valid proof through the normal `Hinkal.transact` flow), and is repeatable each time residual funds accumulate.

### Recommendation
- In `ExternalActionSwap.swap`, explicitly track and enforce that only `inputAmount` of `inputToken` leaves the action contract during `callRouter` (e.g., assert `balanceBefore(inputToken) - balanceAfter(inputToken) == inputAmount`), rather than trusting the router calldata blindly.
- Avoid reusable unlimited approvals; approve exactly `inputAmount` immediately before the router call and reset to zero afterward.
- Reject/refund any `erc20TokenAddresses` index ≥ 2 with a negative delta that `swap()` does not use, or extend `swap()` to explicitly handle and return all tokens sent to it so nothing can be stranded.
- Add balance invariant checks so any leftover balance in the action contract after `swap()` completes reverts the transaction instead of silently persisting.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `LifiExternalAction` (with a mock LI.FI router), and register the action.
2. Seed the residual: submit a first `Hinkal.transact` call with `erc20TokenAddresses = [inputToken, outputToken, thirdToken]`, `amountChanges[2] < 0`, causing `thirdToken` to be transferred to the action and stranded (assert `thirdToken.balanceOf(action) > 0` after tx 1, with no UTXO created for `thirdToken`).
3. As a different, unprivileged attacker EOA, generate a fresh valid proof for their own UTXOs and call `Hinkal.transact` again with `erc20TokenAddresses[0] = thirdToken` (reused as `inputToken`), a small `inputAmount`, and craft `externalActionMetadata` for the mock router to pull the entire `thirdToken` balance of the action (small `inputAmount` + stranded residual) via the standing unlimited approval, swapping all of it for `outputToken`.
4. Assert that the attacker's resulting on-chain UTXO amount for `outputToken` exceeds what corresponds strictly to `-deltaAmountChanges[0]` sent to the action in transaction 2 (i.e., `swappedAmount > f(inputAmount_tx2)` and instead reflects `inputAmount_tx2 + strandedResidual`), proving the equality "tokens leaving the action == `-deltaAmountChanges` sent that tx" is broken and the attacker captured value they never contributed.

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
