### Title
Missing relayer permission check in Tron `IntentGatewayV2.onAccept` allows an unauthorised delivery of `RedeemEscrow`/`RefundEscrow` requests - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of the Intent Gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) implements `onAccept` without the relayer-allowlist gate (`_checkRelayer`) that the canonical EVM implementation (`evm/src/apps/intentsv2/ExtrinsicIntents.sol`) enforces before decoding and acting on any incoming request body. This is the same bug class as the Jenkins advisory: a missing authorization check lets an unprivileged party (any relayer who can push a message through the host, including one who forged/exploited a consensus proof) drive privileged escrow-release logic that should only be reachable through a trusted, allow-listed relayer.

### Finding Description
On the canonical EVM contracts, `onAccept` deliveries into the Intent Gateway are gated by `_checkRelayer(incoming.relayer)` *before* the request body is even decoded: [1](#0-0) 

This gate exists specifically to close the "forged consensus → arbitrary relayer" attack path, as documented in the project's own decision log: [2](#0-1) 

and the delivery-flow doc that traces exactly how a delivery reaches `onAccept` and where the check sits: [3](#0-2) 

The Tron implementation of the same contract, however, omits this check entirely. `onAccept` is `onlyHost`-gated (so only the local host can call it) but performs no `_checkRelayer` on `incoming.relayer` before dispatching on `RequestKind`: [4](#0-3) 

A `grep` for `_relayer`/`relayer`/`_checkRelayer` across this file confirms there is no relayer-gate field, setter, or check anywhere in the Tron contract — it only defines `RequestKind`, escrow withdrawal, governance-source checks (`Unauthorized` when `request.source` isn't Hyperbridge), and the `onlyHost` modifier on `onAccept`. The `authenticate()` call for `RedeemEscrow`/`RefundEscrow` only checks that the *module* on the source chain matches the registered gateway instance; it says nothing about which relayer delivered the message. This is precisely the pattern the 2026-09-03 fix was written to close on the mainline EVM contracts, and that fix was evidently never ported to the Tron fork.

### Impact Explanation
`EvmHost.dispatchIncoming` calls `onAccept` with whatever `relayer` address the configured handler reports as `msg.sender`, after proof verification: [5](#0-4) 

Because the mainline gateways enforce a single allow-listed relayer for these deliveries, only that trusted key can trigger `RedeemEscrow`/`RefundEscrow`/governance actions. On the Tron gateway, any relayer whose delivery passes the host's proof-verification (i.e., anyone able to get any request "through" the host layer — including through a forged/compromised consensus client or handler swap, the exact scenario the mainline fix defends against) can trigger escrow redemption/refund logic for orders on this gateway. This is a direct route to unauthorized release of escrowed funds (theft/forged message delivery) on the Tron deployment, since the app-level defence-in-depth that the rest of the protocol relies on is absent here.

### Likelihood Explanation
Reachability requires only a delivered `PostRequest` whose body decodes to `RedeemEscrow`/`RefundEscrow` and whose source module matches the registered instance — no relayer allow-listing stands in the way. Given the project's own documentation shows this exact class of attack (a compromised/forged proof reporting an arbitrary relayer) was the motivating threat for adding `_checkRelayer` on the EVM side, the same threat model applies unmitigated to the Tron contract. Likelihood is Medium: it depends on an attacker being able to get a forged/relayed request past the host's own proof verification (consensus compromise or handler swap), same precondition as the original Jenkins-analog bug class (missing permission check reachable by anyone who can already reach the dispatch path).

### Recommendation
Port the relayer-allowlist gate from `evm/src/apps/intentsv2/ExtrinsicIntents.sol` / `IntentsBase.sol` to `evm/tron/contracts/apps/IntentGatewayV2.sol`: add an `_relayer` storage slot, a host-gated `setRelayer`, and call `_checkRelayer(incoming.relayer)` at the very top of `onAccept` before `RequestKind` is even read, mirroring the mainline fix and its associated tests (`testOnAcceptRejectsUnlistedRelayer`, `testOnAcceptGovernanceRejectsUnlistedRelayer` in `evm/tests/foundry/IntentGatewayV2Test.sol`).

### Proof of Concept
1. Deploy/observe the Tron `IntentGatewayV2` with an order escrowed for cross-chain redemption.
2. Obtain (or forge, via a compromised consensus client / swapped handler on that chain) a `PostRequest` whose body is `RequestKind.RedeemEscrow` (or `RefundEscrow`) with a valid `WithdrawalRequest` encoding and a `from` matching the registered gateway instance on the source chain.
3. Have the host deliver it via `dispatchIncoming`, reporting an arbitrary/unauthorized address as `relayer`.
4. `onAccept` (`evm/tron/contracts/apps/IntentGatewayV2.sol:629`) proceeds straight to `authenticate(incoming.request)` and `withdraw(...)` — no `_checkRelayer` call rejects the unauthorized submitter, unlike the mainline gateway, releasing escrowed funds. [6](#0-5)

    /**
     * @dev Once a relayer is set, rejects deliveries from anyone else before the body is read. The
     * host records the revert as undelivered, so the authorised relayer can resubmit. While unset,
     * every delivery passes: a proxy from before the gate stays open until `migrate` arms it.
     * @param relayer The account that submitted the message to the handler.
     */
    function _checkRelayer(address relayer) internal view {
        address authorised = _relayer;
        if (authorised != address(0) && relayer != authorised) revert Unauthorized();
    }

   verification the handler calls `host.dispatchIncoming(request, _msgSender())`. `_msgSender()` is
   plain `msg.sender`; the handler has no trusted forwarder.
2. `EvmHost.dispatchIncoming` (restricted to the handler) writes a receipt for the request
   commitment, then low-level calls the module with `IApp.onAccept(IncomingPostRequest(request,
   relayer))`. If that call fails the host deletes the receipt and returns without reverting, so the
   rest of the batch proceeds and the message stays deliverable.
3. `ExtrinsicIntents.onAccept` runs `onlyHost`, then `_checkRelayer(incoming.relayer)`, which reverts

   first body byte read as a `RequestKind`. `onGetResponse` has the same two steps before touching
   the response.

So a delivery from anyone but the authorised relayer never decodes the body, never runs
`_authenticate`, and leaves no receipt. The authorised relayer submitting the same message later
takes the normal path. A gateway whose `_relayer` is zero accepts every relayer: that is the state
a fresh proxy is in until governance arms it, below.

    /**
     * @notice Executes an incoming post request.
     * @dev This function is called when an incoming post request is accepted.
     * It is only accessible by the host.
     * @param incoming The incoming post request data.
     */
    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            authenticate(incoming.request);
            WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
            return withdraw(body, kind == RequestKind.RefundEscrow);
        }

        // only hyperbridge is permitted to perfom these actions
        if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
