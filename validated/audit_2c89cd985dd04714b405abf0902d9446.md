### Title
Non-embedded OAuth session cookie value is predictable, enabling cross-tenant session fixation - (File: lib/shopify_api/auth/oauth.rb, lib/shopify_api/auth/session.rb, lib/shopify_api/utils/session_utils.rb)

### Summary
For non-embedded apps, `ShopifyAPI::Auth::Oauth.validate_auth_callback` sets the browser session cookie's value directly to `session.id` [1](#0-0) . For offline sessions this id is deterministically derived as `"offline_#{shop}"` [2](#0-1) , and the same deterministic derivation is exposed directly to any caller via `ShopifyAPI::Utils::SessionUtils.offline_session_id(shop)` and `jwt_session_id(shop, user_id)` [3](#0-2) . This value is not an unguessable secret bound to the browser/OAuth flow — it is a pure function of the public, well-known Shopify shop domain (`{shop}.myshopify.com`). The documented flow for non-embedded apps is to take the raw cookie value from the browser and treat it as the session id for storage lookup: `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` simply returns `cookies[SESSION_COOKIE_NAME]` unmodified via `cookie_session_id` [4](#0-3) , with no signature or binding check on the cookie contents.

### Finding Description
The intended identity binding is: `session cookie value == session id that was actually established through a completed, HMAC/state-validated OAuth callback for a specific browser`. Because the offline session id is `"offline_#{shop}"` — a value computable by anyone who knows the target's `myshopify.com` domain, with no random or secret component — the binding degrades to: `session cookie value == f(public shop name)`, which any unauthenticated party can compute without ever completing OAuth.

`validate_auth_callback` does perform HMAC and `state` verification, but only to establish the *session at OAuth-callback time* [5](#0-4) . Once that session is created, the cookie that represents it to the browser carries no further authentication of its own — it's simply the raw, predictable id [6](#0-5) . Any user of the host application (which is following the gem's documented, recommended non-embedded flow) who submits a forged `shopify_app_session` cookie with value `offline_<target-shop>.myshopify.com` will have `SessionUtils.current_session_id` hand that id straight back to the host app for use as a session-storage lookup key, with no verification that the requester ever completed OAuth or was ever issued that cookie by the server [7](#0-6) .

### Impact Explanation
If exploited against a host application that persists sessions keyed by this id (the documented pattern — e.g. ShopifyApp gem `SessionRepository`), an attacker can fixate/forge a session identifier for any shop whose domain they know (shop domains are not secret) and gain access to that shop's already-established offline session/access token in the host app's storage — a cross-tenant access issue matching the "session fixation" bullet in scope. This crosses a tenant boundary using only public information (a shop's `myshopify.com` domain), without any credential, matching the High-severity "session fixation or forced OAuth completion" category.

### Likelihood Explanation
Likelihood is constrained by two factors: (1) it depends on the host application storing/looking up sessions purely by this id string without an additional server-side binding to the browser (e.g., no additional signed cookie, no CSRF-style secret) — a very common pattern since this is exactly the flow the gem's own docs describe (`docs/getting_started.md` lines 47-52) [8](#0-7) ; and (2) the attacker needs the offline session for the target shop to already exist in the host app's storage (i.e., the merchant has installed the app). Given the id derivation is entirely within this gem's control and the cookie-setting code path is exactly as documented, this is a root-cause issue in the library, not merely host misuse.

### Recommendation
Do not use a deterministic, publicly-derivable value (`offline_#{shop}` / `#{shop}_#{user_id}`) as the literal bytes stored in the browser-facing session cookie. Either (a) sign/HMAC the cookie value (bind it to `api_secret_key` so it cannot be forged), or (b) use a random, unguessable session identifier (e.g. `SecureRandom.uuid`, as already used as the default for `Session#id` when no explicit id is supplied) for the cookie value, keeping the internal storage key separate from the externally-facing cookie value, or (c) explicitly document that host apps handling non-embedded sessions must additionally bind the cookie to the browser via a signed/encrypted cookie mechanism rather than relying on `SessionCookie.value` alone.

### Proof of Concept
1. Attacker learns/guesses target shop's domain `target-shop.myshopify.com` (public, discoverable, or via storefront).
2. Attacker computes candidate session id `offline_target-shop.myshopify.com` (matches `Session.from`/`SessionUtils.offline_session_id` derivation) [2](#0-1) .
3. Attacker sets their own browser cookie `shopify_app_session=offline_target-shop.myshopify.com` and visits the host application (which never completed OAuth from this attacker's browser).
4. Host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns the forged id verbatim [9](#0-8) .
5. Host app looks up this id in its session store and finds the real offline session (with access token) for `target-shop`, previously created when the legitimate merchant installed the app — attacker is now treated as that shop's authenticated session.

        def current_session_id(shopify_id_token, cookies, online)
          if Context.embedded?
            if shopify_id_token
              id_token = shopify_id_token.gsub("Bearer ", "")
              session_id_from_shopify_id_token(id_token: id_token, online: online)

              # falling back to session cookie

            end
          else
            raise Errors::CookieNotFoundError, "Session cookie not found for app" unless
              cookies && cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]

            cookie_session_id(cookies)
          end
        end

```markdown
#### Cookie
Cookie based authentication is not supported for embedded apps due to browsers dropping support for third party cookies due to security concerns. Non-embedded apps are able to use cookies for session storage/retrieval.

For *non-embedded* apps, you can pass the cookies into:
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, true)` for online (user) sessions or
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` for offline (store) sessions.
```
