### Title
Webhook `shop` identifier is not covered by HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature (`to_signable_string`) using only the raw request body, while the `shop` (tenant identifier) is read directly from the unauthenticated `x-shopify-shop-domain` HTTP header and is never included in the signed payload. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC but then dispatches the handler using this unauthenticated `shop` value, breaking the binding between "the shop whose data actually produced the signed body" and "the shop the host application believes the webhook belongs to."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived purely from a client-controlled header, not from the signed body: [2](#0-1) 

`Registry.process` validates the HMAC against `request` (i.e. against the body only), then immediately trusts `request.shop` — a value untouched by the signature check — to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

Because `api_secret_key` is shared across every merchant that has installed a given app, a valid `hmac-sha256` value for a given raw body is valid **regardless of which shop the body actually came from**. `Utils::HmacValidator.validate` only recomputes the signature over `to_signable_string` (the body) and compares it to the header-supplied HMAC — it never ties the signature to the `shop-domain` header: [4](#0-3) 

The broken identity binding, stated as an equality that the code fails to enforce:
`shop_that_produced(signed_body) == request.shop_header` — this is never checked; only `hmac(raw_body) == received_hmac` is checked, and `shop` plays no role in that computation.

### Impact Explanation
Any merchant who has installed the app (an "unprivileged" actor with respect to any other tenant of the same app) receives legitimate webhooks for their own shop, each with a valid HMAC over the body (signed with the app's shared `client_secret`). By replaying that exact raw body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim merchant's domain, the attacker causes `Registry.process` to pass HMAC validation (body is untouched) and dispatch the handler with `shop: <victim shop>`. Any host application logic that uses `WebhookMetadata#shop` to select the tenant's session/credentials/database record (the documented and expected usage pattern, per `docs/usage/webhooks.md`) will act on the wrong tenant, resulting in cross-tenant data confusion — e.g., attacker-controlled order/product data getting written into another merchant's records, or triggering `shop/redact`/`customers/redact` compliance workflows against the wrong shop. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Medium-to-High. The attacker needs no privileged credentials or `client_secret` — only their own legitimate installation of the target app (a normal, unprivileged position for any app user) and the ability to POST to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header, which is straightforward since this gem performs no binding between the signed body and the shop header.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values in the data covered by the HMAC check, or otherwise cryptographically bind the header-supplied shop to the signed body before it is handed to `WebhookMetadata`/the handler. At minimum, document/require host applications to independently verify that `request.shop` corresponds to a shop with an active installation before trusting it, and consider deriving `shop` from a value that is itself part of the signed payload.

### Proof of Concept
1. App `X` is installed on merchant shops `attacker.myshopify.com` and `victim.myshopify.com`, both sharing the same `api_secret_key`.
2. Shopify sends a legitimate webhook to the app for `attacker.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)`.
3. The attacker (who controls their own shop/webhook receiving endpoint or intercepts their own webhook deliveries) captures `B` and `H`.
4. The attacker POSTs to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged, still valid because it only signs `B`), but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, B) == H`.
6. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the host application to process attacker-supplied data as if it originated from the victim shop.
