### Title
Governance parameter updates to `surplusShareBps`/`protocolFeeBps` apply with immediate effect and unintentionally reprice in-flight fills, causing solvers to receive an unexpected surplus split - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._updateParams` writes new `surplusShareBps`/`protocolFeeBps`/destination-fee values into live storage the instant a governance-originated `UpdateParams` message is accepted, with no timelock or staging delay. `_splitSurplus`, which is invoked from `_fillCrossChain`/`_fillSameChain`, reads `_params.surplusShareBps` at the moment `fillOrder` executes, not at the time the order was placed or the time the solver committed to a fill. This is the same bug class as the referenced report: a privileged, "trustworthy" role changes a protocol parameter with immediate effect while an unprivileged, permissionless actor (here, an intent solver) has already committed to a specific economic outcome, and there is no way for that actor to recover the difference if the parameter changes between commitment and settlement.

### Finding Description
`_splitSurplus` computes the solver's/beneficiary's take of any overpayment strictly from the *current* value of `_params.surplusShareBps`: [1](#0-0) 

This is called on every fill path, both same-chain and cross-chain, at the exact block the solver's `fillOrder` transaction lands: [2](#0-1) [3](#0-2) 

Governance updates these parameters via `_updateParams`, which validates bounds and then applies the new `Params` struct (including `surplusShareBps` and `protocolFeeBps`) synchronously, with no delay or challenge/timelock window before the new value is live: [4](#0-3) 

On the Hyperbridge side, `pallet-intents-coprocessor::update_params` is a single governance-origin extrinsic that merges the update and dispatches it cross-chain immediately — no staging period, no queued/delayed execution: [5](#0-4) 

A solver evaluates an order's profitability (including the expected surplus split it can recapture when overfilling, or in solver-selection auctions, the split priced into its bid) at quote/bid-signing time, then submits (or has already signed) a `fillOrder` transaction/UserOperation. Because `surplusShareBps` is read live rather than snapshotted at order placement or bid time, any governance update to that parameter that lands on-chain between when the solver commits to its output amounts and when the fill transaction executes changes the payout split the solver actually receives — exactly analogous to `Auction.sol`/`Factory.sol` in the referenced report, where `auctionDecrement`/`auctionMultiplier` could change between bonding and `settleAuction()`.

There is no recovery path: once `fillOrder` executes, the solver has already transferred output tokens to the beneficiary based on its own pre-computed amounts; the surplus split is applied atomically inside the same transaction using whatever `surplusShareBps` is live at that instant, and there is no mechanism to revert, adjust, or compensate the solver if the split differs from what it assumed when sizing its fill.

### Impact Explanation
An intent solver that sizes a fill (or signs a bid off-chain, per `docs/content/developers/evm/intent-gateway/overview.mdx`'s SolverAccount/bid flow) based on the currently observed `surplusShareBps` can have that value changed by governance before its transaction lands. If the protocol's share increases immediately before settlement, the solver receives less of the surplus it was economically counting on recouping, silently changing its expected P&L for that fill with no way to cancel or adjust after commitment. Symmetrically, `protocolFeeBps`/destination fee changes taking effect between when a user calculates the expected input deduction and when `placeOrder` actually executes can cause the user to pay a different protocol fee than quoted. This is a Medium-severity griefing/economic-integrity issue: no funds are stolen from the protocol, but an unprivileged solver or user is exposed to unbounded, uncompensated repricing of an in-flight economic commitment purely because of the lack of a staging delay on a parameter with immediate financial effect on already-in-motion transactions.

### Likelihood Explanation
The report itself is explicit that this class of issue does not require malicious intent — normal governance tuning of fee parameters is a routine, expected operation, and the referenced report's own resolution ("assumed the owner is trustworthy... will add mitigations") shows the underlying flaw is structural rather than requiring a bad actor. Any period in which a solver has sized/signed a fill and the update lands on-chain before that fill is included is sufficient to trigger the mismatch; given `update_params` is a normal governance operation expected to be used periodically (e.g., fee schedule tuning) and solver fills/bids can be in flight for the duration of the ERC-4337 bundling/relay window (or the bid-validity window described for phantom/simplex bids), the window of exposure is real and recurring, not a one-off edge case.

### Recommendation
- Snapshot the fee-relevant params (`surplusShareBps`, `protocolFeeBps`, and any applicable `destinationFeeBps`) into the order/commitment at `placeOrder` time rather than reading `_params` live at fill time in `_splitSurplus`/withdrawal, so the terms a solver evaluated when bidding are the terms actually applied at settlement.
- Alternatively, add a delay (timelock) between `_updateParams` being accepted and the new values taking effect, mirroring the one-day timelocks the referenced report recommends elsewhere, so in-flight fills/bids cannot be repriced mid-flight.
- If snapshotting is infeasible, expose the params version/values used at fill time so solvers can pass an expected `surplusShareBps`/fee value into `fillOrder` and have the call revert (slippage-style check) if the live value has diverged from what was assumed when the fill was sized/signed.

### Proof of Concept
1. A solver observes `IntentGatewayV2.params().surplusShareBps == 5000` (50/50 split) and sizes/signs a `fillOrder` call (or a bid `UserOperation`) expecting to keep 50% of any surplus it provides, per `_splitSurplus`: [6](#0-5) .
2. Before that transaction is included, Hyperbridge governance calls `pallet-intents-coprocessor::update_params` to raise `surplus_share_bps` to `10000` (100% to protocol) for legitimate fee-policy reasons: [7](#0-6) . This dispatches cross-chain and, once relayed, is applied immediately via `_updateParams`: [8](#0-7) , matching the exact effect demonstrated in `testSurplusSplitWith0PercentToBeneficiary`/`testSurplusSplitWith100PercentToBeneficiary` in `evm/tests/foundry/IntentGatewayV2Test.sol` (lines ~1008-1090), which show the split is taken from whatever `Params.surplusShareBps` is set to at the moment `fillOrder` executes.
3. The solver's previously-sized `fillOrder` transaction then lands and executes `_splitSurplus` against the new `10000` value, giving 100% of the surplus to the protocol instead of the 50% the solver counted on when it committed its output tokens — with no revert, no compensation, and no way to recover the difference.

    /// @dev Splits overpayment between protocol and beneficiary. An order with output calldata
    /// gives the beneficiary nothing, since the surplus is not the caller's to give.
    function _splitSurplus(uint256 dust, bool hasOutputCall)
        internal
        view
        returns (uint256 protocolShare, uint256 beneficiaryShare)
    {
        if (hasOutputCall) return (dust, 0);
        protocolShare = (dust * _params.surplusShareBps) / 10_000;
        beneficiaryShare = dust - protocolShare;
    }

    /**
     * @dev Updates the gateway's configuration parameters and per-destination protocol fees.
     * Called by Hyperbridge governance to modify fee settings, host address, dispatcher,
     * price oracle, and other operational parameters.
     *
     * Validates all params before applying. Emits ParamsUpdated with the old and new params,
     * then iterates over any destination-specific fee overrides and applies them to
     * `_destinationProtocolFees`.
     *
     * @param update The parameter update containing new params and destination fee overrides.
     */
    function _updateParams(ParamsUpdate memory update) internal {
        _validateParams(update.params);

        emit ParamsUpdated({previous: _params, current: update.params});
        _params = update.params;

        for (uint256 i; i < update.destinationFees.length;) {
            bytes memory chain = update.destinationFees[i].chain;
            uint256 feeBps = update.destinationFees[i].destinationFeeBps;
            if (feeBps >= 10_000) revert InvalidInput();
            _destinationProtocolFees[keccak256(chain)] = feeBps;

            unchecked {
                ++i;
            }
            emit DestinationProtocolFeeUpdated(string(chain), feeBps);
        }
    }

		#[pallet::call_index(3)]
		#[pallet::weight(T::WeightInfo::update_params())]
		pub fn update_params(
			origin: OriginFor<T>,
			state_machine: StateMachine,
			params_update: types::ParamsUpdate,
		) -> DispatchResult {
			T::GovernanceOrigin::ensure_origin(origin)?;

			// Get gateway info
			let mut gateway_info =
				Gateways::<T>::get(state_machine).ok_or(Error::<T>::GatewayNotFound)?;

			// Store old params for event
			let old_params = gateway_info.params.clone();

			// Merge update with current params
			let updated_params = gateway_info.params.update(params_update.clone());

			// Create complete params update for cross-chain dispatch
			let complete_update = types::CompleteParamsUpdate {
				params: updated_params.clone(),
				destination_fees: params_update.destination_fees.unwrap_or_default(),
			};

			// Prepare cross-chain request
			let request = RequestKind::UpdateParams(complete_update);
			let body = request.encode_body();

			// Dispatch cross-chain message
			Self::dispatch(state_machine, gateway_info.gateway, body)?;

			// Update local storage
			gateway_info.params = updated_params.clone();
			Gateways::<T>::insert(state_machine, gateway_info);

			Self::deposit_event(Event::GatewayParamsUpdated {
				state_machine,
				old_params,
				new_params: updated_params,
			});

			Ok(())
		}
