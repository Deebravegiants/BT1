## Finding

### Title
Accumulating `need_take_pnl_pc`/`need_take_pnl_coin` accounting variables can exceed real vault balances, causing `checked_sub` underflow that permanently blocks Deposit/Withdraw/Swap - (File: `program/src/math.rs`)

### Summary
The Omnipool tracks a monotonically-growing "amount owed to the pnl owner" via `amm.state_data.need_take_pnl_pc` / `need_take_pnl_coin`. Every `Deposit`, `Withdraw`, `SwapBaseIn`/`SwapBaseOut`, and `WithdrawPnl` instruction begins by computing the pool's usable reserves as `vault.amount - need_take_pnl_*` using `checked_sub`, which hard-reverts on underflow instead of saturating. This is functionally identical to the reported `totalDeposited` bug class: an accounting variable that can grow larger than the real backing balance and, once it does, makes the subtraction underflow and revert every subsequent operation — freezing all remaining LP funds in the pool.

### Finding Description
`Calculator::calc_total_without_take_pnl_no_orderbook` computes the pool's tradable/withdrawable reserves by subtracting the accrued-but-unclaimed pnl (`need_take_pnl_pc`/`need_take_pnl_coin`) from the actual SPL token vault balances, using `checked_sub` that maps any underflow straight to `AmmError::CheckedSubOverflow`: [1](#0-0) 

This function is invoked unconditionally at the top of every user-reachable pool instruction that touches reserves — `process_deposit`, `process_withdraw`, `process_swap_base_in`, `process_swap_base_out`, and `process_withdrawpnl`: [2](#0-1) [3](#0-2) [4](#0-3) 

`need_take_pnl_pc`/`need_take_pnl_coin` are only ever incremented (via `checked_add` in `calc_take_pnl`) and are reset to zero only through the privileged `WithdrawPnl` instruction: [5](#0-4) [6](#0-5) 

`calc_take_pnl` derives the amounts to add to these counters through repeated fixed-point conversions between the pool's internal `sys_decimal_value` scale and each token's native decimals (`normalize_decimal_v2` / `restore_decimal`), which are computed independently for the `pc` and `coin` sides and truncate on integer division: [7](#0-6) 

Because `calc_take_pnl` is invoked on essentially every swap and every withdraw (any time `amm.status != WithdrawOnly`), rounding/truncation asymmetries between the pc-side and coin-side decimal conversions accumulate into `need_take_pnl_pc`/`need_take_pnl_coin` over the pool's lifetime. There is no code path that reconciles these counters against the real vault balances except the subtraction itself, and no invariant enforced that `need_take_pnl_pc <= pc_vault.amount` (or the coin equivalent) at the time `calc_take_pnl` updates them — the check only happens later inside `calc_total_without_take_pnl_no_orderbook`, on the *next* instruction. If, over enough swap/withdraw activity (or an adversarial sequence of many small swaps crafted to maximize rounding drift), the accrued counter for either token exceeds the vault's real balance, `checked_sub` fails and returns `AmmError::CheckedSubOverflow` for **every** subsequent Deposit, Withdraw, and Swap instruction on that pool — because they all call this same helper before doing anything else.

### Impact Explanation
Once the underflow condition is reached, the pool becomes permanently unusable: LPs can no longer call `Withdraw` to redeem their LP tokens for underlying coin/pc, and no more swaps or deposits can occur, since all of them dead-end at `calc_total_without_take_pnl_no_orderbook`'s `checked_sub`. This mirrors exactly the reported dynamic: users who withdraw early are fine, but once the imbalance is discovered, remaining LPs racing to exit before the counter fully outpaces the vault balance will find the pool frozen, and any user with LP tokens still in the pool has their principal permanently stuck (the only unlock path, `WithdrawPnl`, is gated behind the privileged `amm_config.pnl_owner` signer and doesn't repair a state where `need_take_pnl > vault.amount`, since that transfer itself would also fail/`TakePnlError` if the vault can't cover it).

### Likelihood Explanation
`calc_take_pnl` runs on nearly every state-changing pool instruction (`Deposit`, `Withdraw`, `SwapBaseIn`, `SwapBaseOut`, unless status is `WithdrawOnly`), so the drift-accumulating code path is exercised continuously by ordinary, unprivileged market activity — no special permissions are required to trigger repeated calls. The magnitude of any single rounding step is small, but it compounds over the life of a high-volume pool, especially for token pairs with very different decimal precisions (e.g., 6 vs 9 decimals), making eventual underflow a realistic long-tail outcome rather than a purely theoretical one.

### Recommendation
Replace the `checked_sub`/hard-revert semantics in `calc_total_without_take_pnl_no_orderbook` with a saturating subtraction (clamping `need_take_pnl_*` to the actual vault balance when it would otherwise exceed it), and/or periodically reconcile `need_take_pnl_pc`/`need_take_pnl_coin` against real vault balances in `calc_take_pnl` so they can never be incremented past what the vault can back. Alternatively, allow an emergency/anyone-callable path to clamp `need_take_pnl_pc`/`need_take_pnl_coin` down to `min(need_take_pnl, vault.amount)` so LP withdrawals are never blocked by this internal accounting drift.

### Proof of Concept
1. Over the life of an active pool, repeatedly execute `SwapBaseIn`/`SwapBaseOut` swaps in both directions; each call that increases pool value invokes `calc_take_pnl`, which independently rounds pc-side and coin-side amounts via `restore_decimal`/`normalize_decimal_v2` before `checked_add`-ing them into `need_take_pnl_pc`/`need_take_pnl_coin` (`program/src/processor.rs:244-254`).
2. Because the pnl owner has not called `WithdrawPnl` to flush these counters, and because rounding truncation is not symmetric between the two token decimal scales, `need_take_pnl_pc` (or `_coin`) can drift upward relative to what the vault balance can actually support.
3. Once `need_take_pnl_pc > amm_pc_vault.amount` (or the coin equivalent), any call to `Deposit`, `Withdraw`, `SwapBaseIn`, or `SwapBaseOut` fails at `Calculator::calc_total_without_take_pnl_no_orderbook`'s `pc_amount.checked_sub(amm.state_data.need_take_pnl_pc).ok_or(AmmError::CheckedSubOverflow)?` (`program/src/math.rs:243-245`), permanently reverting the pool's core instructions and locking in any remaining LPs' funds.

```rust
    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
```
