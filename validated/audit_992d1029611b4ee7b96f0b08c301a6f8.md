### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity solely by checking the HMAC over the raw request body, then passes the unauthenticated `shop-domain` header straight through to the app's handler as the tenant identifier. The HMAC never covers the `shop` value, so the binding `HMAC(secret, signed_bytes) == HMAC(secret, shop ‖ body)` that a developer would reasonably assume does not hold — in reality it is only `HMAC(secret, body)`. Anyone who can obtain one valid `(raw_body, hmac)` pair (e.g. by receiving a legitimate webhook to their own store, which any merchant installing the app can do) can replay that exact body/HMAC pair while substituting an arbitrary `shopify-shop-domain` header, and the request still passes `HmacValidator.validate`.

### Finding Description
The webhook `Request` object implements `VerifiableQuery`, and its signable string used for HMAC verification is defined as only the raw body: [1](#0-0) 

Meanwhile `shop` is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header without any cryptographic binding to the signed content: [2](#0-1) 

`Registry.process` performs the authenticity check using only this body-derived HMAC, and then constructs the `WebhookMetadata` passed to the app's handler using the *unauthenticated* `request.shop`: [3](#0-2) 

The documentation states that `Registry.process` "will verify the request did indeed come from Shopify," implying the whole request — including the shop attribution — is trusted once this call succeeds: [4](#0-3) 

and it explicitly instructs handler authors to use `data.shop` as the tenant/shop identifier for downstream processing (e.g. enqueuing per-shop jobs): [5](#0-4) 

Because `shop` is excluded from `to_signable_string`, the equality the library implicitly promises — "the shop the HMAC-verified body belongs to" == "the shop reported in the header" — is not enforced. This is analogous to the report's underlying bug class: a field that is *acted upon* (used to attribute/route the trusted payload) but is *not covered by the authentication mechanism* that establishes trust in the request. Just as the liquidator could supply attacker-controlled swap `data` that wasn't bound to the protocol's expected invariants, here an attacker can supply an attacker-controlled `shop` header that isn't bound to the HMAC that "proves" the request is authentic.

### Impact Explanation
Any unprivileged internet user who has legitimately installed the app on their own store (a normal, unprivileged flow) receives real webhooks with valid `(body, hmac)` pairs signed with the app's shared secret. They can replay that exact body and HMAC to the app's webhook endpoint while forging the `shopify-shop-domain` header to name a different, victim shop that also uses the app. `HmacValidator.validate` still succeeds because the header is not part of the signed content, and the handler receives `WebhookMetadata` attributing the (attacker-controlled) body to the victim shop's `shop` field. If the host application follows the gem's documented pattern of using `data.shop` to key session lookups, queue jobs, or write shop-scoped records (as shown in the gem's own docs), this allows cross-tenant data injection/corruption — an attacker can make the app process attacker-chosen webhook content under another merchant's identity. This matches the Critical-impact category of cross-tenant access defined by the rules.

### Likelihood Explanation
Likelihood is high for any app that installs the gem's documented webhook flow verbatim: no additional protections (e.g., binding the registered webhook's expected shop, or validating `shop` against the session/store that a subsequent registration expects) are enforced by the library itself. The only requirement is that the attacker possess one valid, previously delivered `(body, hmac)` pair, which is achievable by any merchant capable of installing the app on their own store and capturing their own webhook deliveries — no access token, `api_secret_key`, or privileged access is required.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) in the HMAC-signed content, or otherwise cryptographically bind the shop domain to the verified payload before it is handed to `WebhookMetadata`/handlers. At minimum, `Utils::HmacValidator.validate` should be extended (or a new check added in `Registry.process`) so that the `shop` header used for tenant attribution is verified against Shopify-known session data, rather than being trusted as an unauthenticated header once the body-only HMAC succeeds.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers for a webhook topic (e.g. `orders/create`).
2. Shopify delivers a legitimate webhook to the app's endpoint with headers including `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw body>`, and the raw JSON body.
3. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value.
4. Attacker replays a request to the same webhook endpoint using the identical `raw_body`/`x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses the forged header set; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `@raw_body` (per `to_signable_string`) — validation succeeds because the body/HMAC pair is genuinely valid.
6. The handler executes with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)`, i.e., attacker-controlled data is processed under the victim shop's identity, exactly as documented in `docs/usage/webhooks.md`'s example handler (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`).

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
