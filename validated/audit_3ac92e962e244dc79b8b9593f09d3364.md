### Title
Divergent rounding between per-account scaled debt (market-vault) and vault aggregate `principal-scaled` in `repay` allows dust-repayment drift, breaking the debt-ledger identity - (File: `mainnet/contracts/market/v0-4-market.clar`, `mainnet/contracts/vault/v0-vault-usdc.clar` and sibling vaults)

### Summary
The Cooler `roll`/`repay` bug is a case of a paired conversion (collateral ↔ debt) being updated by two different, independently-rounded formulas, letting dust repayments silently desynchronize the two quantities. Zest has the same structural pattern between the **per-account scaled debt** stored in `v0-market-vault` and the **vault-wide aggregate `principal-scaled`** stored in each asset vault (`v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, etc.). `market.clar`'s `repay` computes the scaled-debt reduction for the specific account using the market's own borrow-index conversion, while the vault's `system-repay` independently re-derives a scaled-principal reduction from the raw token amount using a *different* formula (`calc-principal-ratio-reduction`, a ratio of `capped-amount` to the vault's own `scaled-principal`/`debt` aggregate). These two values are not guaranteed to be equal, and there is no single source of truth passed between them (unlike the liquidation path, which explicitly avoids this by passing the scaled amount directly).

### Finding Description
In `repay` (`mainnet/contracts/market/v0-4-market.clar:1316-1378`), the market computes a per-account scaled reduction: [1](#0-0) 
It asserts `repaid-scaled-debt > 0` (`ERR-INSUFFICIENT-SCALED-DEBT`) so the *per-account* ledger cannot silently round to zero: [2](#0-1) 

It then calls `vault-system-repay` with the **token amount** `amount-to-repay` (not the scaled amount), and separately tells `v0-market-vault` to remove `repaid-scaled-debt` from the specific account's ledger.

The vault's `system-repay`, however, does not receive `repaid-scaled-debt` at all — it independently re-derives a scaled reduction from the raw token amount using its own aggregate state: [3](#0-2) 

This is a second, independently rounded computation (`calc-principal-ratio-reduction(capped-amount, scaled-principal, debt)`) of "how much scaled principal should this token repayment retire," computed from the vault's *aggregate* `scaled-principal`/`debt`, rather than from the market's per-account borrow-index conversion. Nothing enforces that this vault-side scaled reduction equals the `repaid-scaled-debt` already subtracted from the account in `v0-market-vault`.

Notably, the developers were aware of exactly this risk in the liquidation/bad-debt path and explicitly avoided it there by passing the scaled amount directly instead of letting the vault re-derive it from a token amount: [4](#0-3) 
The regular `repay` path does not apply the same fix — it lets the vault recompute the scaled reduction on its own via a token-amount-based ratio, using the vault's own `mul-div-down` rounding (visible pattern in `system-repay`/`socialize-debt`): [5](#0-4) 

This is the same "paired-conversion rounding" structure as the Cooler `repay`/`roll` bug: two representations of the same debt (per-user ledger vs. aggregate ledger) are updated via different formulas, each with its own rounding, and repeated small (dust) repayments can accumulate a persistent divergence between "sum of per-account scaled debt in `v0-market-vault`" and "`principal-scaled` in the vault" — an identity that should always hold:
`Σ account-scaled-debt_i (market-vault) == principal-scaled (vault)`

### Impact Explanation
`principal-scaled` in the vault (together with `index`) determines `total-debt()`, which feeds `total-assets-preview()`/`accrue()` and therefore the zToken share price used for `deposit`/`redeem` (`convert-to-shares-preview`/`convert-to-assets-preview`). If the vault's aggregate is inflated relative to the true sum of outstanding per-account debt (because dust repayments reduced individual accounts' debt in `v0-market-vault` fully while the vault-side ratio-based reduction rounded down/differently), the vault will perpetually believe it is owed more than it actually is. This overstates backing for zToken holders, and since the "phantom" debt is uncollectible (the borrower's obligation was already cleared per-account), the discrepancy is never corrected — it manifests as inflated share price / overstated `total-assets`, risking insolvency for later redeemers (a permanent shortfall of backing versus outstanding shares). Conversely, if the divergence runs the other way, LPs are shortchanged. Either direction is a value-accounting break between the per-user debt ledger and the vault aggregate, consistent with the explicitly allowed analog category.

### Likelihood Explanation
Triggering requires only repeatedly calling the public `repay` function with small `amount` values against an asset with nonzero borrow index (any market with accrued interest), a normal, unprivileged, permissionless action. The per-account guard (`ERR-INSUFFICIENT-SCALED-DEBT`) prevents the account's own ledger from zeroing out, but does not constrain or synchronize the vault's independent, ratio-based recomputation, so the drift is reachable through ordinary repeated small repayments — no privileged role, oracle manipulation, or DAO action needed.

### Recommendation
Do not let the vault independently re-derive a scaled-principal reduction from a token amount in `system-repay`. Instead, pass the already-computed `repaid-scaled-debt` (or an amount derived from the same index/precision the market used) from `market.clar`'s `repay` into the vault, mirroring the fix already applied in the liquidation/socialization path (`vault-socialize-debt` receiving the scaled amount directly "to avoid rounding"). This guarantees `Σ account-scaled-debt_i == principal-scaled` is maintained exactly across every repayment, regardless of dust amounts.

### Proof of Concept
Note: I could not retrieve the full body of `calc-principal-ratio-reduction` within the available tool budget, so the exact rounding direction/magnitude of the vault-side divergence per call is not fully confirmed; the finding is based on the confirmed fact that `repay` and `system-repay` use two structurally different, independently-rounded formulas to update what should be the same debt quantity in two places, and that the project's own code elsewhere (`socialize-debt-asset`) treats this exact pattern as a rounding hazard to be avoided. A conclusive PoC would require:
1. Borrow on an asset (e.g., USDC) to create nonzero `principal-scaled` in `v0-vault-usdc.clar` and a matching per-account scaled debt in `v0-market-vault`.
2. Advance time/blocks so `index` in the vault increases (interest accrues, `index > INDEX-PRECISION`).
3. Repeatedly call `market.clar`'s `repay` with the smallest amount that satisfies `repaid-scaled-debt > 0` per the per-account formula.
4. After each call, compare `v0-market-vault`'s stored scaled debt for the account against `v0-vault-usdc.clar`'s `principal-scaled`, and observe that the two decrease by different amounts over repeated dust repayments, producing a persistent, growing gap between the per-user ledger and the vault aggregate.
