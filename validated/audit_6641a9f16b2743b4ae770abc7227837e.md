### Title
Fee-in-asset payment relies on manipulable on-chain AMM spot price with no user-supplied slippage bound - ([File: substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs])

### Summary
`pallet-asset-conversion-tx-payment`'s `SwapAssetAdapter::withdraw_fee` (and its `can_withdraw_fee`/`correct_and_deposit_fee` counterparts) determine how much of a non-native asset a signer must pay for transaction fees by quoting the current spot price of `pallet-asset-conversion`'s constant-product pool at the moment the extrinsic is validated/prepared, with no user-configurable maximum. This is the same vulnerability class as the reported Curve `sharePrice` issue: a critical monetary amount is computed on-chain from a manipulable AMM reserve ratio, and the party bearing the cost (the fee payer) has no protection against the price being moved against them between quoting and execution.

### Finding Description
`withdraw_fee` quotes the exact amount of `asset_id` needed to cover the fee by calling the pool's spot-price function directly against current reserves, and immediately withdraws and swaps that amount: [1](#0-0) 

This mirrors `quote_price_tokens_for_exact_tokens`, which derives the price purely from the pool's current on-chain balances (`get_reserves`) via `get_amount_in`/`quote`, i.e. the constant-product spot price — directly analogous to Curve's `calc_withdraw_one_coin` computing `sharePrice` from the pool's current invariant state: [2](#0-1) 

Critically, `ChargeAssetTxPayment` never exposes a "max amount of `asset_id` I'm willing to pay" parameter — the extension only carries `tip` and `asset_id`: [3](#0-2) 

`validate()` and `prepare()` each independently re-derive the fee amount from the live pool state and unconditionally withdraw+swap it — there is no `amount_in_max`-style slippage guard analogous to what `swap_tokens_for_exact_tokens` exposes to ordinary swappers: [4](#0-3) 

Since `pallet-asset-conversion` reserves can be moved arbitrarily by anyone via `swap_exact_tokens_for_tokens`/`swap_tokens_for_exact_tokens` (unprivileged, permissionless calls), and block authors/searchers control intra-block transaction ordering, an attacker can:
1. Front-run the victim's fee-paying extrinsic with a swap that skews the `asset_id`/native pool ratio, inflating the spot price of `asset_id` in terms of native currency.
2. Let the victim's `prepare()` execute `S::quote_price_tokens_for_exact_tokens` against the skewed reserves, withdrawing an inflated `asset_fee` of `asset_id` from the victim and swapping it for the exact native `fee`.
3. Back-run with a reverse swap to restore the pool and capture the spread extracted from the victim.

The same manipulable-quote pattern also occurs in `correct_and_deposit_fee`'s refund path, which quotes `S::quote_price_exact_tokens_for_tokens` at post-dispatch time to convert unused native fee back into `asset_id`: [5](#0-4) 

### Impact Explanation
A user paying fees in a non-native asset can be forced to pay more of that asset than the fair market rate, and/or receive a smaller-than-fair refund, purely because of atomic pool-reserve manipulation by a third party within the same block. Unlike ordinary swaps in `pallet-asset-conversion`, which give callers `amount_out_min`/`amount_in_max` slippage protection, `ChargeAssetTxPayment` offers no such protection to the fee payer — the extension design implicitly assumes the spot price is trustworthy at the instant of `prepare()`/`post_dispatch_details()`. The magnitude of extractable value is bounded by pool depth and the size of the fee, so it's most exploitable against thinly-liquidated asset/native pools, but it directly reproduces the root cause pattern of the reported issue: a security-relevant balance calculation computed on-chain from a spot price with no off-chain computation, no oracle, and no slippage bound for the affected party.

### Likelihood Explanation
Any unprivileged account can call `swap_exact_tokens_for_tokens`/`swap_tokens_for_exact_tokens` against the pool, and transaction ordering within a block is influenced by whoever authors/relays the block (a realistic MEV/searcher scenario on parachains with public transaction pools). No privileged role is required to manipulate the pool; the victim only needs to submit a `ChargeAssetTxPayment` extrinsic with `asset_id != None` against a pool with limited depth.

### Recommendation
Add a caller-supplied slippage bound to `ChargeAssetTxPayment` (e.g., `max_asset_fee: Option<Balance>`) and thread it through `OnChargeAssetTransaction::withdraw_fee`/`can_withdraw_fee`, failing validation if the quoted `asset_fee` (or refund) exceeds/falls below the caller's tolerance, mirroring the `amount_in_max`/`amount_out_min` protections already available to ordinary `pallet-asset-conversion` swappers.

### Proof of Concept
1. Create a shallow `NativeOrWithId::WithId(asset)` / `Native` pool via `pallet_asset_conversion::create_pool` + `add_liquidity`.
2. Victim submits a signed extrinsic with `ChargeAssetTxPayment::from(tip, Some(asset_id))`.
3. Attacker submits (and gets ordered before the victim's extrinsic in the same block) a large `swap_exact_tokens_for_tokens` skewing the pool ratio in favor of `asset_id` being expensive relative to native.
4. Victim's `prepare()` calls `withdraw_fee`, which calls `S::quote_price_tokens_for_exact_tokens(asset_id, Native, fee, true)` — as shown at [6](#0-5)  — returning an inflated `asset_fee`, which is withdrawn from the victim.
5. Attacker submits a reverse swap after the victim's extrinsic to restore the pool and realize the profit extracted from the victim's overpayment.

		pub fn quote_price_tokens_for_exact_tokens(
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			amount: T::Balance,
			include_fee: bool,
		) -> Option<T::Balance> {
			// Swaps reject zero amounts, match that behavior.
			if amount.is_zero() {
				return None;
			}
			let pool_account = T::PoolLocator::pool_address(&asset1, &asset2).ok()?;

			let (balance1, balance2) = Self::get_reserves(asset1.clone(), asset2.clone()).ok()?;

			if balance1.is_zero() {
				return None;
			}

			// Swap withdrawals from pools use `keep_alive=true` (Preserve). Use the same
			// preservation level to determine the actual withdrawable amount.
			let max_output =
				T::Assets::reducible_balance(asset2.clone(), &pool_account, Preserve, Polite);
			if amount > max_output {
				return None;
			}

			if include_fee {
				let fee = Self::pool_fee_for(&asset1, &asset2).ok()?;
				Self::get_amount_in(fee, &amount, &balance1, &balance2).ok()
			} else {
				Self::quote(&amount, &balance2, &balance1).ok()
			}
		}

	fn validate(
		&self,
		origin: <T::RuntimeCall as Dispatchable>::RuntimeOrigin,
		call: &T::RuntimeCall,
		info: &DispatchInfoOf<T::RuntimeCall>,
		len: usize,
		_self_implicit: Self::Implicit,
		_inherited_implication: &impl Encode,
		_source: TransactionSource,
	) -> ValidateResult<Self::Val, T::RuntimeCall> {
		let Some(who) = origin.as_system_origin_signer() else {
			return Ok((ValidTransaction::default(), Val::NoCharge, origin));
		};
		// Non-mutating call of `compute_fee` to calculate the fee used in the transaction priority.
		let fee = pallet_transaction_payment::Pallet::<T>::compute_fee(len as u32, info, self.tip);
		self.can_withdraw_fee(&who, call, info, fee)?;
		let priority = ChargeTransactionPayment::<T>::get_priority(info, len, self.tip, fee);
		let validity = ValidTransaction { priority, ..Default::default() };
		let val = Val::Charge { tip: self.tip, who: who.clone(), fee };
		Ok((validity, val, origin))
	}

	fn prepare(
		self,
		val: Self::Val,
		_origin: &<T::RuntimeCall as Dispatchable>::RuntimeOrigin,
		call: &T::RuntimeCall,
		info: &DispatchInfoOf<T::RuntimeCall>,
		_len: usize,
	) -> Result<Self::Pre, TransactionValidityError> {
		match val {
			Val::Charge { tip, who, fee } => {
				// Mutating call of `withdraw_fee` to actually charge for the transaction.
				let (_fee, initial_payment) = self.withdraw_fee(&who, call, info, fee)?;
				Ok(Pre::Charge { tip, who, initial_payment, weight: self.weight(call) })
			},
			Val::NoCharge => Ok(Pre::NoCharge { refund: self.weight(call) }),
		}
	}
