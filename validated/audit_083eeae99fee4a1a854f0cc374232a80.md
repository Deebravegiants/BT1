### Title
Webhook shop-domain header is trusted for tenant routing but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` attribute read directly from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, but the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` is computed only over the raw request body. The registry passes this unauthenticated `shop` value straight into the handler's `WebhookMetadata`, so the tenant identity that the host application acts on is never bound to the cryptographic proof of authenticity.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and for webhook requests that method returns only `@raw_body`: [1](#0-0) [2](#0-1) 

The `shop` value used by the rest of the pipeline, however, comes straight from an HTTP header that is completely outside the signed content: [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then forwards `request.shop` — unverified — to the app's handler as the tenant identifier: [4](#0-3) 

Because Shopify apps typically share a single `client_secret` across every merchant that installs the app, any shop that installs the app can capture one legitimate `(raw_body, hmac)` pair generated by Shopify for their own store (e.g. from an `orders/create` webhook they control by placing an order in their own store) and replay it to the app's public webhook endpoint with the `x-shopify-shop-domain` header rewritten to point at a victim shop. `HmacValidator.validate` will still succeed, since it never inspects the shop header — it only recomputes the HMAC over the untouched body bytes. The equality that should hold is:

`shop authenticated by HMAC == shop the handler acts on`

but in this implementation:

`shop authenticated by HMAC (⊆ body only)` ≠ `shop the handler acts on (header value)`

This breaks the identity binding the report's bug class describes: a field (`shop`) that is acted on by the application but not covered by the integrity check (`hmac-sha256`).

### Impact Explanation
An attacker who can install the target app on any shop (including a free/trial store they control) can forge webhook deliveries that are accepted as authentic for an arbitrary victim `myshopify.com` domain, because the shop attribution is never bound to the HMAC. Depending on how the host application uses `WebhookMetadata#shop` (e.g. to look up/update the corresponding merchant record, mark an event, or trigger data sync), this enables cross-tenant data confusion/injection — an attacker-controlled payload processed under a victim shop's identity. This matches the "Critical: cross-tenant access" impact category, since the tenant boundary (`shop`) that the rest of the library and downstream app rely on as authenticated is not actually authenticated.

### Likelihood Explanation
Exploitation only requires the ability to install the target app on any Shopify store (attacker's own store) to obtain one valid `(body, hmac)` pair for a chosen topic, then replaying it with a modified `shop` header to the app's public webhook endpoint. No access to the app's `client_secret`, access tokens, or the victim's credentials is required — this is fully reachable by an unprivileged internet user with a free Shopify dev/trial store, so likelihood is high for apps that key any tenant logic off `WebhookMetadata#shop`.

### Recommendation
Bind the shop identity into the material that is HMAC-verified, or otherwise cross-check it independently of the header value:
- Include the shop domain (and topic/webhook id) in the signable string used for HMAC verification, mirroring how `AuthQuery#to_signable_string` binds `shop` into its signed payload, or
- Require the host application to have a registered webhook per-shop endpoint/secret pairing, or independently verify that the shop in the header corresponds to a shop for which the app holds an active session/installation before trusting `WebhookMetadata#shop`, and document this requirement prominently since the gem currently presents `request.shop`/`data.shop` as if it were verified.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled store `attacker-shop.myshopify.com`.
2. Trigger a webhook event (e.g. `orders/create`) and capture the raw POST body and the `x-shopify-hmac-sha256` header Shopify sends — this HMAC is valid because it was computed with the app's real `client_secret` over the raw body.
3. Replay the exact same body and HMAC header to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes the HMAC over the (unchanged) raw body: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-supplied body content, despite the request never having been produced by or authorized for that shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
