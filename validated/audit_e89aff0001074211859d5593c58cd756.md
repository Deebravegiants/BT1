This confirms a concrete, transaction-reachable price-manipulation analog: the `weightedMedian` price-selection mechanism used to publish `PhantomOrderPriceSnapshotV2` prices is weighted purely by a solver's *instantaneous, unauthenticated on-chain balance* of the leg's output token, read via a plain `getBalance`/`eth_call` at the current block — exactly the kind of value a flash loan can inflate for the duration of one transaction (analogous to NORMIE's attacker inflating the tax-collection wallet's balance with borrowed funds to skew a balance-dependent calculation).

### Title
Flash-loan-inflatable balance weight lets a single bid dictate the published Phantom order price - ([File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts])

### Summary
`aggregatePhantomBids` weights every solver bid in the `weightedMedian` price selection by `getBalance(destUrl, chain, outputToken, solver)` — a live `balanceOf` read (plus vault/position balances) taken at aggregation time [1](#0-0) . Because `weightedMedian` picks the exact price of whichever quote's cumulative weight first reaches half the total weight, a bidder holding over half the total weight sets the published price verbatim [2](#0-1) .

### Finding Description
The weight has no cost basis or holding-period requirement attached to it — it is a raw `eth_call` balance snapshot of the solver's wallet/vault at whatever block the aggregation runs against [3](#0-2) . A solver (or anyone controlling a solver-delegated EIP-7702 account, which only needs a valid bid signature, not any special privilege) can flash-loan the leg's output token into that wallet immediately before the phantom bid window closes and the snapshot is read, submit (or already have submitted) a bid, and repay the flash loan after the balance read. This inflates `weight` far beyond the solver's real deliverable inventory, letting a near-zero-capital actor's quoted `price` dominate the weighted median and become the published `medianPrice` in `PhantomOrderPriceSnapshotV2`. This directly mirrors the NORMIE root cause: a balance figure that feeds a protocol calculation (there, tax-dilution math; here, the published trade rate) is trusted at face value even though it can be transiently manipulated with borrowed capital within a single transaction/block.

### Impact Explanation
`PhantomOrderPriceSnapshotV2.medianPrice` is not a cosmetic figure — it directly feeds `updateLiquidityPools`, publishing `sellRate`/`buyRate` for the cross-chain `LiquidityPool` entity [4](#0-3) , and is consumed live by `PhantomSnapshotIntentQuoteStrategy.quote()` to price real user swaps, converting `medianPrice`/`standardAmount` directly into `amountOut`/`amountIn` for real orders [5](#0-4) . An attacker who flash-loan-inflates their weight can push the published rate to whatever is most profitable for their own subsequent real fills (or to whatever misprices other users' quotes), causing real value transfer at a manipulated exchange rate — concrete theft/mispricing of user funds routed through the intents/solver system.

### Likelihood Explanation
No special privilege is required beyond running a solver-delegated EIP-7702 account and having a valid signed bid — this is exactly the "intent solver / bandwidth purchaser" unprivileged path called out as in-scope. Flash loans of ERC-20 tokens are freely available on any EVM chain hosting the destination gateway, and the balance read is a single `eth_call` at whatever block the indexer processes the `PhantomBidWindowExhausted` event, giving the attacker a full block (or more, depending on indexer timing) to hold the borrowed balance.

### Recommendation
Do not weight quotes by a spot `balanceOf` read. Options: (1) require weight to be backed by an escrowed/locked deposit (e.g., the solver's actual committed collateral in `IntentGatewayV2` or a staked bond) rather than a freely-flash-loanable wallet balance; (2) average the balance over multiple blocks/checkpoints so a single-block flash loan cannot dominate; (3) cap any single solver's weight contribution to the median (e.g., a maximum weight share) so no bidder can unilaterally set the price regardless of momentary balance size.

### Proof of Concept
1. Attacker deploys/controls a solver account delegated (EIP-7702) to the chain's `SolverAccount`, satisfying `isVerifiedSolverBid`.
2. Just before a `PhantomOrder`'s bid window closes, attacker takes a flash loan of the leg's output token (e.g., large USDC amount) into the solver's wallet.
3. Attacker submits (or has pre-submitted) a bid quoting a favorable-to-attacker `price` for that leg.
4. `handlePhantomOrderPrices` fires on `PhantomBidWindowExhausted`, calling `aggregatePhantomBids`, which reads the solver's `balanceOf` — inflated by the flash loan — as `weight` [1](#0-0) .
5. Attacker's weight exceeds half the total weight, so `weightedMedian` returns the attacker's exact quoted price [6](#0-5) , published as `medianPrice`.
6. Attacker repays the flash loan (same transaction/block as step 2, before the snapshot read window closes).
7. Subsequent real orders quoted via `PhantomSnapshotIntentQuoteStrategy` or priced off `LiquidityPool.sellRate/buyRate` use the manipulated rate, letting the attacker (or a colluding filler) extract value from real fills at the skewed price.

export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
}
