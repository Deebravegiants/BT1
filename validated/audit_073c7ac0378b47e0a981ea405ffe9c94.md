### Title
Unsigned, unaccounted arbitrary calls from `EmporiumUpgradeable` via the Min-proof path — funds Emporium can move are never balance-checked - (File: `contracts/CircomDataBuilder.sol` / `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`formInputForCircom` routes any transaction with `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0` to `formInputEmporiumMin`, which only proves `message == Poseidon(messageSeed)` — a value the attacker fully controls with no linkage to any real UTXO, spending key, or the `EmporiumStack` payload. `EmporiumUpgradeable.runAction` then executes `stack.ops[i].endpoint.call(op.callData)` as itself with **no signature check at all** when `stack.signerAddress == address(0)` (`verifyWallet` returns early), and the before/after balance accounting loop is over `circomData.erc20TokenAddresses`, which is empty, so the arbitrary call's effects are never accounted for or capped.

### Finding Description
The claimed equality — "assets Emporium can move in a tx == assets accounted in `balancesBefore`/`balancesAfter`" — is broken:

- `formInputForCircom` selects the minimal circuit whenever `erc20TokenAddresses.length == 0`: `contracts/CircomDataBuilder.sol:134-148`. `formInputEmporiumMin` produces only `[emporiumMessage, timeStamp, calldataHash]` as public signals (`contracts/CircomDataBuilder.sol:150-161`), matching `MainEVMCircuitMin.circom:1-18` which only enforces `message === Poseidon(messageSeed)`. No spending key, signature, nullifier, or root-tied constraint is present in this circuit — the attacker can trivially produce a valid proof for any `messageSeed` they pick.
- `dimensionsCheck` (`contracts/HinkalHelper.sol:64-171`) permits `tokenNumber == 0`, so `erc20TokenAddresses`, `amountChanges`, `inputNullifiers`, `outCommitments`, `slippageValues`, `onChainCreation` can all legitimately be empty arrays, satisfying every other Hinkal-level require.
- `_externalTransact` (`contracts/Hinkal.sol:234-261`) then calls `EmporiumUpgradeable.runAction` with `deltaAmountChanges = []` because the token array is empty.
- Inside `runAction` (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:76-160`), `balancesBefore`/`balancesAfter` are computed over the empty `circomData.erc20TokenAddresses`, so the closing accounting loop (lines 132-157) iterates zero times — it accounts for nothing regardless of what happened inside.
- `verifyWallet` (lines 302-349) marks `usedMessages[emporiumMessage] = true` and then, if `stack.signerAddress == address(0)`, **returns immediately** (line 314-316) — no EIP-712 signature is checked in this branch.
- The op loop (lines 91-118): when `stack.signerAddress == address(0)`, `op.invokeWallet && stack.signerAddress != address(0)` is false, so every op falls into the "Stateless Interaction" branch and is executed as `op.endpoint.call{value: op.value}(op.callData)` — a raw call originating from the `EmporiumUpgradeable` contract's own address. The only restriction is blocking the `callHinkalWallet`/`doSendToRelay` selectors (lines 104-110); any other endpoint/selector is unrestricted.

**Attacker's exact call:** call `Hinkal.transact` with `dimensions.tokenNumber = 0`, `circomData.erc20TokenAddresses = []`, `circomData.externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `circomData.externalActionData.externalActionMetadata = abi.encode(EmporiumStack{signerAddress: address(0), ops: [EmporiumOperation{endpoint: victimToken, invokeWallet: false, value: 0, callData: transferFrom(victim, attacker, amount)}], maxFee: 0, deadline: ..., v/r/s: unused})`, `emporiumMessage = Poseidon(attacker-chosen messageSeed)`, and a proof generated locally for `MainEVMCircuitMin` with that `messageSeed`. Because `verifyWallet` short-circuits with `signerAddress == address(0)`, no signature over `stack.ops` is required, and because the accounting arrays are empty, the resulting arbitrary call (e.g., draining any standing `approve()` a victim previously granted to the Emporium contract address, or invoking any other privileged/approved action Emporium is entitled to) is executed and never checked against `balancesBefore`/`balancesAfter`.

Existing guards do not prevent this: `performHinkalChecks` only validates hash integrity, relay whitelisting, dimension consistency, and on-chain creation constraints — none of which constrain the contents of `externalActionMetadata` or tie the Min-circuit message to the `EmporiumStack`/ops. `rootHashExists` only checks that some root exists in the tree, not that it's tied to the attacker. The circuit itself (`MainEVMCircuitMin`) constrains nothing about tokens, amounts, or ops.

### Impact Explanation
Any unprivileged attacker can force `EmporiumUpgradeable` to execute an arbitrary `call` to any address with any calldata, without needing to prove ownership of any real shielded funds and without any signature, and with zero balance/slippage accounting since the token array is empty. If any party (a user, another external action, or Emporium itself during normal operation) has ever left a standing ERC20 approval to the Emporium proxy address, or if any privileged capability is reachable through a call originating from Emporium's address, the attacker can trigger `transferFrom`-style theft or misuse that capability. This matches **Critical: direct theft of shielded or in-flight user funds** / **executing calls or moving assets a wallet owner or prover never authorised**, since the call is executed as Emporium and no accounting or signature ties it to any authorized party.

### Likelihood Explanation
- Preconditions: attacker needs (a) the ability to generate a trivial Min-circuit proof (self-contained, requires only picking `messageSeed`), and (b) a target where Emporium holds a standing approval or where an arbitrary call from Emporium's address has value (e.g., calling a contract that trusts `msg.sender == Emporium`, or exploiting any allowance previously granted to the Emporium address by any actor).
- Attacker cost: one transaction, gas only; no capital required beyond gas since no funds need to be deposited by the attacker.
- Repeatable: each valid `emporiumMessage`/proof can be used once (`usedMessages` mapping), but the attacker can mint an unlimited number of fresh, self-chosen `messageSeed`s, so the attack is repeatable at will, once/if a valuable pre-condition (standing allowance to Emporium, or a call-from-Emporium-trusting integration) exists.
- I could not find in the indexed contracts a concrete, currently-existing case where a user grants direct ERC20 approval to the `EmporiumUpgradeable` contract address itself (deposits into Emporium are funded by Hinkal's own balance transfer in `_externalTransact`, not by user-granted allowances to Emporium). This means the "standing approval" precondition, while structurally reachable via this same primitive (arbitrary unauthenticated call-as-Emporium), may not have an immediately obvious victim in the current codebase without an additional integration granting Emporium such privilege. The core bug — unauthenticated, unaccounted arbitrary calls from Emporium's identity when `signerAddress == address(0)` and `erc20TokenAddresses.length == 0` — is nonetheless real and independently exploitable against any future or existing integration that trusts Emporium's address.

### Recommendation
- Require `stack.signerAddress != address(0)` (i.e., always require a valid signature) whenever the "Min" proof path is used, or disallow the Min path from executing arbitrary `ops` at all — the Min circuit should only be usable for actions that do not perform arbitrary external calls.
- Alternatively, bind the Min circuit's public `message` to a hash of `stack.ops` (endpoint/selector/calldata/value) so that at minimum the attacker cannot supply ops unconstrained by any proof, and require the signature check unconditionally in `verifyWallet` regardless of `signerAddress`.
- Do not allow `erc20TokenAddresses.length == 0` combined with `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and a non-empty `stack.ops` — require at least one token to force real balance accounting, or add an explicit accounting/allow-list mechanism for stateless calls with zero tokens.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (as allowed recipient), and a mock ERC20 token; have a "victim" account call `token.approve(emporiumProxyAddress, largeAmount)` to simulate a standing approval to Emporium (or substitute any other capability reachable only by `msg.sender == Emporium`).
2. As an unprivileged attacker EOA (no deposits, no relay role), build `CircomData` with `dimensions.tokenNumber = 0`, `erc20TokenAddresses = []`, `amountChanges = []`, `inputNullifiers = []`, `outCommitments = []`, `onChainCreation = []`, `slippageValues = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalAddress = emporiumProxyAddress`, `externalActionData.externalActionMetadata = abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation({endpoint: address(token), invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transferFrom, (victim, attacker, largeAmount))})], maxFee: 0, deadline: block.timestamp + 1, v: 0, r: 0, s: 0}))`.
3. Generate a valid `MainEVMCircuitMin` proof locally for a self-chosen `messageSeed`, set `emporiumMessage = Poseidon(messageSeed)`.
4. Call `Hinkal.transact(a, b, c, dimensions, circomData)` from the attacker.
5. Assert: transaction succeeds (`verifyProof` passes, `verifyWallet` returns early with no signature, `token.transferFrom` executes), `token.balanceOf(attacker)` increases by `largeAmount`, `token.balanceOf(victim)` decreases by `largeAmount`, while `balancesBefore == balancesAfter == []` inside `runAction` and no `slippage`/accounting `require` in `Hinkal.transact` or `EmporiumUpgradeable.runAction` reverted or captured the movement — demonstrating assets moved by Emporium ≠ assets accounted for by the balance-diff loop.
