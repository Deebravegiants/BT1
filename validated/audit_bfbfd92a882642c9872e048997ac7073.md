### Title
Unchecked ERC20 return value in `withdraw`/`SweepDust`/fee-redemption permanently locks escrowed funds for non-standard tokens - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron `IntentGatewayV2` contract escrows ERC20/TRC20 tokens using `SafeERC20.safeTransferFrom` when tokens enter escrow (`placeOrder`), but releases them using a raw low-level `.call` to the `transfer` selector and only checks that the call did not revert — it never inspects the ABI-encoded boolean return value. This is the same class of defect flagged in the external report: the protocol implicitly assumes every token strictly follows the "standard" success semantics (revert-on-failure), and silently mishandles tokens that deviate from that assumption (return `false` instead of reverting).

### Finding Description
`placeOrder` escrows tokens with `SafeERC20`, which correctly validates the return data: [1](#0-0) 

But when escrow is released — in `withdraw` (both for order tokens and for `TRANSACTION_FEES`) and in the `SweepDust` branch of `onAccept` — the contract instead does: [2](#0-1) [3](#0-2) 

`(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount)); if (!success) revert TransferFailed();` only reflects whether the call reverted at the EVM/TVM level. Many tokens do not follow the "revert on failure" convention and instead return `false` from `transfer()` on failure (e.g., blocklist rejection, paused token, insufficient allowance edge-cases, or any non-`SafeERC20`-checked token deployed with non-reverting semantics). Because the return data is never decoded, such a `false` return is indistinguishable from a genuine success.

As a direct consequence, `withdraw` still executes `_orders[body.commitment][token] -= amount;` and marks `_filled[body.commitment] = beneficiary;`, permanently finalizing the order as filled/refunded even though the beneficiary received zero tokens. The escrow accounting is decremented and the order is closed, so the tokens can never be reclaimed through `withdraw` again — they remain unrecoverable inside the contract.

### Impact Explanation
This causes permanent freezing/loss of user or solver funds for any order or fee redemption denominated in a token whose `transfer()` can return `false` without reverting. Since `_filled` and `_orders` are updated unconditionally, there is no retry path once the silent failure occurs — the escrowed value is stuck, and the beneficiary (a user awaiting refund or a solver awaiting settlement) never receives what they are owed. This matches the "permanent freezing of funds" impact class for the IntentGatewayV2 escrow path.

### Likelihood Explanation
This path is reachable from a single relayed ISMP message: an authenticated `RedeemEscrow`/`RefundEscrow` request (or a `SweepDust` instruction from Hyperbridge) delivered via `onAccept`, which any relayer can submit once the corresponding proof exists, and the token used in the order is chosen by the order-placing user/solver at `placeOrder` time — no privileged action is required to select a non-standard token as an order's input/output asset.

### Recommendation
Use `SafeERC20.safeTransfer` (already imported and used elsewhere in the same file) consistently in `withdraw`, the fee-redemption branch, and the `SweepDust` handler, instead of raw `.call` with only a revert-boolean check. This ensures both revert-on-failure tokens and false-return tokens are correctly detected and handled before the escrow/`_filled` state is mutated.

### Proof of Concept
1. An order is placed with an ERC20/TRC20 token `T` whose `transfer()` implementation returns `false` on failure instead of reverting (e.g., a blocklist-style token, or the beneficiary becomes blocklisted between escrow and redemption).
2. `placeOrder` successfully escrows `T` via `safeTransferFrom` (works because sender/allowance are valid at that time). [1](#0-0) 
3. Later, a relayer delivers a `RedeemEscrow`/`RefundEscrow` request; `onAccept` calls `withdraw(body, ...)`.
4. Inside `withdraw`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` (the call itself didn't revert) even though the token's internal logic returned `false` and moved no funds. [4](#0-3) 
5. `_orders[body.commitment][token] -= amount;` and `_filled[body.commitment] = beneficiary;` execute, permanently closing the order. The beneficiary never receives `amount` of `T`, and there is no remaining mechanism to retry or reclaim it.
