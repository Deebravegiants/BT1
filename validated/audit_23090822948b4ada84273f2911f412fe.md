### Title
Unbounded `Order.inputs` / `Order.output.assets` array length can permanently freeze escrowed funds via out-of-gas message delivery - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentGatewayV2.placeOrder()` never bounds the length of `order.inputs` or `order.output.assets`, only checking `order.inputs.length == 0`. These arrays are later embedded verbatim into a `WithdrawalRequest.tokens` and iterated over in `IntentsBase._withdraw()` when a cross-chain `RedeemEscrow`/`RefundEscrow` message is delivered by `HandlerV2.handlePostRequests()` on the source chain. An order can be crafted with an arbitrarily large number of token legs, making the resulting escrow-release message too gas-expensive to ever execute within a block, permanently freezing the escrowed tokens.

### Finding Description
`placeOrder()` only checks that inputs are non-empty [1](#0-0) , then loops over `inputsLen` several times (fee reduction, escrow crediting) with no cap on how large `inputsLen` can be [2](#0-1) . `fillOrder()` similarly only checks that `order.output.assets.length == options.outputs.length == order.inputs.length`, again with no upper bound [3](#0-2) .

When a cross-chain order is filled or refunded, the destination/source chain dispatches a `WithdrawalRequest` whose `tokens` field is `order.inputs` (used verbatim, e.g. see the `RedeemEscrow` body construction in tests) [4](#0-3) . On the source chain, this request is delivered through `HandlerV2.handlePostRequests()`, which dispatches to the application's `onAccept`/withdrawal handler in a loop over all requests in the batch [5](#0-4) . The application-level handler, `IntentsBase._withdraw()`, then loops over every entry in `body.tokens` (i.e., every input/output leg of the original order) to decrement escrow and transfer tokens out [6](#0-5) .

Since there is no upper bound on the number of token legs an order creator can specify, a user (or attacker acting as an order creator) can construct an order with an extremely large `inputs`/`output.assets` array. Once escrowed and (potentially) filled by an unsuspecting solver, the resulting `RedeemEscrow`/`RefundEscrow` message becomes too large/expensive to process within any single block's gas limit. Per the ISMP module contract (`IsmpModule::on_accept` must succeed atomically or the receipt is not persisted, allowing replay [7](#0-6) , and the docs explicitly warn this design forces "all invariants" to be maintained before/atomically with state changes [8](#0-7) ), a message that reverts every time (because it always runs out of gas) can never be delivered — it can only be resubmitted indefinitely, never succeeding, and it is not automatically refunded either (only successful/failed callbacks trigger receipt/timeout accounting).

### Impact Explanation
The escrowed input tokens held by `IntentGatewayV2` on the source chain become permanently unrecoverable: `withdraw()`/`_withdraw()` can never complete because the loop over `body.tokens` (sized to the attacker's chosen order) cannot fit in any achievable block gas limit. This is a genuine "route unable to deliver messages" / permanent freezing-of-funds outcome as described by the validation criteria — the escrow can be neither released to a solver who filled the order (loss for the solver, who already delivered real value on the destination chain) nor refunded to the original order creator via the same code path. Any relayer attempting delivery would simply have the transaction revert (out-of-gas), and since the transaction can never succeed, no receipt is ever written and the funds sit frozen in `_orders[commitment][token]` forever.

### Likelihood Explanation
Likelihood is moderate: it requires (a) a malicious or careless order creator to submit an order with an excessively large `inputs`/`output.assets` array, and (b) a solver (or the creator themselves, for a same-chain refund/cancel-with-many-inputs case) to interact with that order such that a `WithdrawalRequest` with the oversized token array is dispatched cross-chain. No privileged role is needed — `placeOrder()` and `fillOrder()` are both permissionless, callable by any address with funds, and there is no validation anywhere in `IntentGatewayV2`/`IntentsBase` limiting array size, so the attack is fully reachable from a single unprivileged transaction plus a single relayed cross-chain message.

### Recommendation
Enforce an explicit maximum on `order.inputs.length` and `order.output.assets.length` in `placeOrder()` (and correspondingly validate it again in `fillOrder()`/`cancelOrder()`), sized conservatively so that the worst-case gas cost of the resulting `_withdraw()` loop (including external `transfer` calls) is guaranteed to fit well within the smallest expected block gas limit across all supported destination/source chains. Reject orders (and messages) whose token-array length exceeds this bound before escrowing any funds.

### Proof of Concept
1. Attacker calls `placeOrder()` with `order.inputs` containing e.g. 5,000+ distinct dust-amount token legs and a matching-length `order.output.assets` — this succeeds since only `inputs.length == 0` is checked [1](#0-0) .
2. A solver, unaware of the gas implications, calls `fillOrder()` for a cross-chain fill, paying out on the destination chain and triggering dispatch of a `RedeemEscrow` `WithdrawalRequest` carrying all 5,000+ token legs back to the source chain.
3. A relayer submits this request via `HandlerV2.handlePostRequests()` [9](#0-8) ; the inner dispatch calls `IntentsBase._withdraw()`, which loops over all 5,000+ legs performing an `SLOAD`/`SSTORE`/external transfer per leg [10](#0-9) , exceeding the block gas limit and reverting the whole transaction.
4. Because the transaction always reverts, no request receipt is ever stored, so the message is permanently undeliverable; the solver's paid-out value on the destination chain is not compensated, and/or the escrowed input tokens on the source chain remain locked in `_orders[commitment][token]` indefinitely.

    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
        }

        bytes32 root = host.stateMachineCommitment(request.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, request.proof.multiproof, leaves, request.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // duplicate request?
            if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.request, _msgSender());
        }
    }

The request `handle` is used to notify onchain `IsmpModule`s of new requests to be processed. A relayer will construct the `RequestMessage` which holds a batch of new `PostRequest`s, as well as a _multi-proof_<sup>[1]</sup> of their existence on the source chain. The handler will perform the following operations

- Assert that the state machine's consensus client is not frozen
- Assert that the configured `challenge_period` for the `StateCommitment` has elapsed
- Assert that the requests have not been previously processed
- Assert that the requests have not timed out
- Assert that the membership proof for the requests verify
- Finally dispatch the requests to the relevant `IsmpModule::on_accept` and store a receipt for each request to prevent requests from being replayed.

<Callout title={'Danger'} type={"warn"}>
It's important to note that if the `IsmpModule::on_accept` does not return `Ok`, the receipt of this request will not be persisted, allowing the request to be **replayed**. Consequently, the `IsmpModule` is responsible for maintaining all invariants before modifying it's internal state to prevent partial state changes that could result in critical vulnerabilities in their request handler. This model ensures that if a request cannot be executed successfully on a destination state machine, it can time out gracefully on the source.
</Callout>
