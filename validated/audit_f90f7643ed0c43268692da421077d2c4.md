## Title
Atomic dual-token transfer in `Withdraw`/`Deposit`/swap instructions permanently freezes LP funds if either the coin or pc mint blocks/freezes transfers — (File: `program/src/processor.rs`)

### Summary
The Raydium AMM bundles the coin and pc sides of a pool into a single atomic instruction for `Deposit`, `Withdraw`, and all four swap variants. Every one of these instructions performs two sequential SPL token transfers (one per side) via `Invokers::token_transfer`/`token_transfer_with_authority` [1](#0-0) , and only completes (burning/minting LP, updating pnl) if both transfers succeed. This mirrors the root cause in the referenced report: bundling multiple distinct tokens into one all-or-nothing operation means a single problematic token (paused, frozen, or otherwise transfer-restricted) blocks the entire operation for users, even though only one of the two assets is affected.

### Finding Description
`process_withdraw` transfers the coin vault balance to the user, then the pc vault balance to the user, and only afterward burns the user's LP tokens: [2](#0-1) 

Because SPL token accounts can be frozen by the mint's `freeze_authority` (a standard, in-scope SPL Token mechanic, not a privileged-signer or non-default-build scenario from the AMM program's perspective), if either `amm_coin_vault` or `amm_pc_vault` — or the user's destination coin/pc account — is frozen by its issuer, the corresponding `spl_token::instruction::transfer` CPI fails. Since both transfers and the LP burn occur within the same instruction/transaction, the entire `Withdraw` call reverts atomically; there is no code path that allows a partial withdrawal of only the unaffected side.

The same atomic dual-transfer pattern exists in `process_deposit` [3](#0-2)  and in every swap instruction (`SwapBaseIn`, `SwapBaseOut`, and their pre-IDO/other variants), each of which requires both an inbound and an outbound transfer to succeed: [4](#0-3) [5](#0-4) .

There is no alternative "single-token" or "emergency" exit instruction that lets an LP withdraw only the unaffected token while leaving the frozen token's share pending, analogous to the recommended `getReward(address[] tokens)` mitigation in the referenced report.

### Impact Explanation
If either the coin mint or the pc mint of a pool becomes non-transferable for the AMM's vault account (e.g., the mint's freeze authority freezes the vault, or the token otherwise blocks transfers to/from program-owned accounts), then:
- LP holders can never call `Withdraw` successfully, because the burn of LP tokens is gated behind both transfers succeeding — this permanently locks both the frozen token's share *and* the otherwise-healthy token's share of every LP position in that pool.
- `Deposit` and both swap directions for that pool become permanently unusable as well, since every one of them requires a transfer involving both vaults.

This results in a permanent freeze of user/LP funds for the entire pool, not just the token that is actually impacted, which qualifies as concrete, permanent freezing of user funds.

### Likelihood Explanation
This requires an external condition — a coin or pc mint whose issuer/freeze authority freezes the AMM's vault (or the counterparty's destination) token account. Raydium pools can be created for arbitrary SPL mints via `Initialize2`, and nothing in the program restricts pool creation to mints without a freeze authority, so this is reachable by any unprivileged pool creator or by any user depositing into an existing pool whose paired token later becomes frozen. The odds are lower than a routine user error, but the scenario is externally triggerable and not reliant on any privileged action within the AMM program itself, consistent with how the original report was judged (Medium severity, low likelihood, externally-triggered).

### Recommendation
Provide a recovery path that does not require both transfers of a pool's two tokens to succeed atomically — for example, an instruction that lets an LP holder redeem/burn LP for only the unfrozen side while leaving a claim for the frozen side, or an admin-gated emergency-withdraw path scoped per vault. At minimum, document the risk that pools paired with mints having a freeze authority (or any pausable-transfer semantics) can have all LP funds (both sides) permanently locked if that authority is exercised against the AMM's vault.

### Proof of Concept
1. A pool is created (`Initialize2`) pairing `TOKEN_A` (no restrictions) with `TOKEN_B`, whose mint has an active `freeze_authority`.
2. The issuer of `TOKEN_B` freezes the AMM's `amm_pc_vault` token account (a standard SPL Token `FreezeAccount` instruction executed by the freeze authority — no cooperation from the AMM program is required).
3. Any LP holder calls `Withdraw`; `process_withdraw` first attempts `token_transfer_with_authority` for the coin side, then for the pc side [6](#0-5) . The pc-side transfer CPI fails because the vault is frozen, reverting the whole transaction — the coin-side transfer and the LP burn never take effect.
4. The LP holder's position (both `TOKEN_A` and `TOKEN_B` shares) remains permanently locked, since no instruction exists to withdraw only the `TOKEN_A` side or otherwise bypass the frozen `TOKEN_B` vault.

    pub fn token_transfer<'a>(
        token_program: AccountInfo<'a>,
        source: AccountInfo<'a>,
        destination: AccountInfo<'a>,
        owner: AccountInfo<'a>,
        deposit_amount: u64,
    ) -> Result<(), ProgramError> {
        let ix = spl_token::instruction::transfer(
            token_program.key,
            source.key,
            destination.key,
            owner.key,
            &[],
            deposit_amount,
        )?;
        solana_program::program::invoke_signed(
            &ix,
            &[source, destination, owner, token_program],
            &[],
        )
    }

    /// Issue a spl_token `Transfer` instruction.
    pub fn token_transfer_with_authority<'a>(
        token_program: AccountInfo<'a>,
        source: AccountInfo<'a>,
        destination: AccountInfo<'a>,
        authority: AccountInfo<'a>,
        amm_seed: &[u8],
        nonce: u8,
        amount: u64,
    ) -> Result<(), ProgramError> {
        let authority_signature_seeds = [amm_seed, &[nonce]];
        let signers = &[&authority_signature_seeds[..]];
        let ix = spl_token::instruction::transfer(
            token_program.key,
            source.key,
            destination.key,
            authority.key,
            &[],
            amount,
        )?;
        solana_program::program::invoke_signed(
            &ix,
            &[source, destination, authority, token_program],
            signers,
        )
    }
