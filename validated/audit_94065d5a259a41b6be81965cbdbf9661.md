### Title
Lack of ERC20 Return Value Checks in Tron IntentGatewayV2 Escrow Withdrawals — Silent Transfer Failures Cause Permanent Loss of Funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed tokens, refunds, protocol fees, and dust sweeps using raw low-level `.call()` invocations of the ERC20 `transfer` function, checking only whether the call itself reverted (`success`) but never decoding/validating the boolean return value that the ERC20 standard requires for indicating transfer success. This mirrors the reported "Invoke Library: Lack of Return Value Checks in ERC20 operations" bug class, applied to a real fund-release path reachable by any relayed `RedeemEscrow`/`RefundEscrow` message.

### Finding Description
In `withdraw()`, escrowed tokens are released to the beneficiary via: [1](#0-0) 

and the transaction fee payout uses the identical pattern: [2](#0-1) 

The same unchecked-return pattern also appears in the `SweepDust` handler within `onAccept`: [3](#0-2) 

In each case, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` returns `(bool success, bytes memory data)`. `success` only indicates that the external call did not revert; it says nothing about the ERC20 `data` payload, which per the standard should be `abi.decode(data, (bool))` to confirm the transfer actually succeeded. Many real-world and legacy ERC20 tokens (and some non-compliant ones deployed on Tron/TVM-compatible chains, where this contract set specifically targets) return `false` on failure (e.g., due to blacklisting, pausing, or insufficient balance/allowance edge cases) instead of reverting. Because `data` is never decoded here, such a `false` return is silently treated as success.

Critically, `withdraw()` unconditionally updates internal accounting before/after the unchecked transfer regardless of whether tokens actually moved: [4](#0-3) 

`_filled[body.commitment]` is marked, `_orders[body.commitment][token]` is decremented, and `EscrowReleased`/`EscrowRefunded` is emitted — all as if the beneficiary received the funds. This is precisely the same "silent failure and incorrect internal accounting" risk cited in the original report, but here it directly leads to a fund-loss condition rather than a hypothetical.

This differs from the non-Tron `evm/src/apps/IntentGatewayV2.sol`, which imports and appears to rely on OpenZeppelin's `SafeERC20` (`safeTransfer`/`safeTransferFrom`) for token movements, correctly validating return data. The Tron fork does not follow this pattern for the escrow-release and dust-sweep code paths, using raw low-level calls instead.

### Impact Explanation
This is reachable directly from Hyperbridge's cross-chain message delivery path: `onAccept` is invoked by the host when a relayed `RedeemEscrow`, `RefundEscrow`, or `SweepDust` request is delivered, and `onGetResponse` also triggers `withdraw()` for refunds. If the escrowed token silently returns `false` on transfer (rather than reverting), the beneficiary never receives the funds, yet:
- The order is marked `_filled`, preventing any retry or alternate settlement.
- The escrow accounting (`_orders[commitment][token]`) is decremented as if paid out.
- `EscrowReleased`/`EscrowRefunded` events fire, masking the failure from off-chain monitoring/relayers.

The result is permanent freezing/loss of the user's or solver's escrowed funds with no recovery path, since the contract's internal state no longer reflects any outstanding balance for that commitment. This satisfies the "permanent freezing of funds" criterion for a valid Medium/High finding.

### Likelihood Explanation
Likelihood depends on whether any token used with this Tron gateway deployment is non-compliant (returns `false` instead of reverting on failure). This is a known and common trait among tokens deployed on Tron/TVM ecosystems and many legacy ERC20-style tokens generally (e.g., some don't revert on transfers to blacklisted or paused states, or on insufficient balance in older implementations). Since the intent-gateway design explicitly supports arbitrary configured input/output tokens, the operator/protocol cannot fully guarantee only fully-standard tokens are ever used, making this a realistically reachable scenario rather than purely theoretical.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw()` and the `SweepDust` branch of `onAccept`) with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the non-Tron `evm/src/apps/IntentGatewayV2.sol` implementation. This ensures both call-reversion and boolean-return-value checks are enforced, so a failed transfer reverts the whole `withdraw`/`onAccept` execution instead of silently updating escrow state.

### Proof of Concept
1. Configure (or have configured) an order whose escrowed `token` is a non-standard ERC20 that returns `false` on `transfer()` failure instead of reverting (a realistic scenario for Tron-native/TRC20-style tokens or legacy tokens).
2. A solver fills the order; the source-chain gateway locks the input tokens in escrow via `_orders[commitment][token]`.
3. Hyperbridge relays a `RedeemEscrow` message to the Tron `IntentGatewayV2`; `onAccept` → `withdraw()` is invoked.
4. Suppose the token transfer to `beneficiary` fails internally (e.g., beneficiary is blacklisted on that token) and the token returns `false` without reverting:
   `(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));` — `success` is `true` because the call itself didn't revert.
5. The `if (!success) revert TransferFailed();` check passes (since `success == true`), so execution continues: `_orders[body.commitment][token] -= amount;`, `_filled[body.commitment] = beneficiary;`, and `EscrowReleased` is emitted.
6. The beneficiary never actually receives the tokens, but the contract's records show the order as filled/settled with zero remaining escrow — the tokens are permanently stuck in the contract with no code path to reclaim them for that commitment.
