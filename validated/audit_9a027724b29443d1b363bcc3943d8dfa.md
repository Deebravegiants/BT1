### Title
`PoaBridge.describeWithdrawal` misreports withdrawal status/txHash when multiple withdrawals of the same asset exist in one transaction - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`describeWithdrawal()` is supposed to report the on-chain outcome of a *specific* withdrawal, identified by `(tx.hash, index, destinationAddress, amount)`. The POA bridge implementation matches the API response only by `assetId`, so when a single NEAR transaction contains more than one withdrawal of the same token (e.g. two `ft_withdraw` intents for the same asset going to different destination addresses), every call to `describeWithdrawal` for that asset returns the same (first-matching) entry, regardless of which `index`/`destinationAddress` was actually requested.

### Finding Description
`findMatchingWithdrawal` only filters by `nep141:${w.data.near_token_id} === assetId` and returns the first match, ignoring `index`, `destinationAddress`, and `amount`: [1](#0-0) 

This is invoked from `describeWithdrawal`, which then reports that match's `status`/`transfer_tx_hash` as the outcome for the caller's specific withdrawal identifier: [2](#0-1) 

The same equality-breaking pattern exists in the shared helper used by `waitForWithdrawalCompletion`, which also matches solely on `near_token_id` and ignores destination/amount, then returns whichever withdrawal happens to match first: [3](#0-2) 

The code even documents this as a known gap ("multiple withdrawals of the same token in a single transaction are not supported"), but callers of `describeWithdrawal`/`waitForWithdrawalCompletion` have no way to know that the returned status does not correspond to the specific withdrawal they queried — this breaks the equality: `reported_status(index, destinationAddress) == on_chain_status(index, destinationAddress)`.

### Impact Explanation
When a user (or an integrator batching intents) submits two `ft_withdraw` intents for the *same* NEAR-side asset in one transaction, but to different destination addresses/amounts, `describeWithdrawal(index=0)` and `describeWithdrawal(index=1)` can both resolve to the same underlying POA withdrawal record. If withdrawal #1 completes first, `describeWithdrawal` for withdrawal #0 will report `status: "completed"` with withdrawal #1's `txHash`, even though withdrawal #0 might still be pending or later fail. An integrator (exchange, custodial wallet, or automated system) relying on this SDK to confirm delivery could credit/mark-complete the wrong withdrawal, or credit the same destination twice while the actual second payout is still outstanding — matching the "status or hash misreport making an integrator credit or refund twice" impact class.

### Likelihood Explanation
This does not require any malicious actor — it is triggered by ordinary usage: any user or integrator that withdraws the same token to two different destinations (or amounts) within a single transaction via the SDK's multi-intent withdrawal support (`sdk.createWithdrawalIntents` accepts arrays of `withdrawalParams`, and `RouteEnum.PoaBridge` per-bridge indexing is tracked separately — see `createWithdrawalIdentifiers`/`withdrawal-watcher.test.ts` which explicitly tests per-bridge index counters). Since same-asset multi-leg withdrawals are a supported, unprivileged flow, the collision is realistically reachable.

### Recommendation
Match withdrawals using the full identifying tuple available from `WithdrawalIdentifier` (at minimum `destinationAddress` and `amount`, not just `assetId`), and only fall back to assetId-only matching when it is provably unambiguous (e.g., only one matching entry exists). If POA's API cannot disambiguate multiple same-asset withdrawals in one tx, `describeWithdrawal` should throw/return an explicit "ambiguous/indeterminate" status rather than silently returning a possibly-wrong txHash, so integrators do not act on it.

### Proof of Concept
1. Build one NEAR transaction with two `ft_withdraw` intents for the same `assetId` (e.g. `nep141:eth.omft.near`), one to `destinationAddress: A`, another to `destinationAddress: B`.
2. Use `PoaBridge.createWithdrawalIdentifier` to get `wid0` (index 0, destination A) and `wid1` (index 1, destination B).
3. Mock/observe the POA API returning two `withdrawals` entries for `near_token_id` matching this asset — one `COMPLETED` (destination B) and one `PENDING` (destination A), in arbitrary order (API is documented as unsorted).
4. Call `bridge.describeWithdrawal(wid0)` — per `findMatchingWithdrawal`'s implementation (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:418-427`), it returns the first array element matching the assetId, irrespective of index/destination, so it can return `{status:"completed", txHash: "<B's tx hash>"}` even though the withdrawal actually bound to `wid0` (destination A) is still pending.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
