### Title
Webhook Shop Domain Is Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable string from the raw request body only, while `shop` (and `topic`) are read from HTTP headers that are never part of the signed payload. `Registry.process` accepts any request whose body/HMAC pair is valid and then forwards the header-derived `shop` value to the app's webhook handler as the authenticated tenant identity, without binding it to the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is derived from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is not included in the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC purely against `to_signable_string` (the body), independent of `shop`: [3](#0-2) 

`Registry.process` trusts this validation result and then uses the unauthenticated `request.shop` header value to build `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The identity binding broken here is: `shop reported in WebhookMetadata == shop that the HMAC-signed body actually originated from`. Because the app's `api_secret_key` is a single shared per-app secret used to sign webhooks from every shop that installs the app, any merchant who has installed the app can capture a genuine `(body, hmac)` pair from their own shop's webhook deliveries (e.g., by placing an order or updating a resource in their own store to control the JSON body content) and know a valid HMAC for that exact body. That attacker can then replay the same body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still returns `true` (body untouched), so `Registry.process` proceeds and calls the handler with `shop: <victim shop>`, `topic`, and `body` fully attacker-influenced (within what the attacker's own store data allowed).

### Impact Explanation
If a host application uses `WebhookMetadata#shop` to look up/update tenant-scoped records (the documented, intended use of this field, per `docs/usage/webhooks.md` and `WebhookHandler`), a malicious merchant can inject data attributed to a different, victim shop — a cross-tenant write/read primitive. This satisfies the "cross-tenant access" impact category, since no privileged credential of the victim is required — only a legitimate installation of the app by the attacker's own shop.

### Likelihood Explanation
Requires the attacker to have the app installed on their own shop (an ordinary, unprivileged merchant relationship, not a privileged secret), and requires influence over some part of the JSON body used in a chosen webhook topic (achievable for most resource webhooks since the attacker controls their own store's data). No access to `api_secret_key`, tokens, or the victim's credentials is needed.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed payload used for verification, or bind the header-derived `shop`/`topic` to a separate authenticated channel (e.g., confirm the webhook subscription belongs to the claimed shop via a stored, per-shop registration lookup) before trusting them in `WebhookMetadata`. At minimum, document that `WebhookMetadata#shop`/`#topic` are not cryptographically bound to the signature and must not be used as sole tenant-identification without additional verification.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a genuine webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`.
2. Attacker crafts `B` content as desired by placing a corresponding order/update in their own store (values embedded in `B` are attacker-controlled).
3. Attacker replays the captured request to the app's webhook receiver endpoint, keeping `B` and the valid `hmac` header unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which returns `true` because it only hashes `B`. [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, and any host logic keyed on `shop` now processes attacker data under the victim's tenant.
