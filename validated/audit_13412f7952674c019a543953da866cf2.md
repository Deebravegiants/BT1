The code matches the claim exactly as cited, and I've confirmed there are no additional safeguards in the pallet against this rounding-to-zero scenario. The pallet's own test suite acknowledges rounding behavior ("Note: There are occasionally off by 1 errors due to rounding. In practice this is insignificant") but that's for the small-magnitude test values used, not the large-magnitude realistic scenario described in the claim. This is a legitimate, reachable-by-unprivileged-user precision loss bug in reward accounting: any staker can call `stake` to grow `total_tokens_staked`, and once it's large relative to `reward_rate_per_block * blocks_elapsed * 4096`, the per-block increment truncates to zero and that period's reward is permanently and silently lost, with no guard rejecting this case.

Audit Report

## Title
Reward-per-token calculation loses rewards to precision truncation when `total_tokens_staked` is large relative to `reward_rate_per_block` - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`pallet-asset-rewards`'s `reward_per_token` function computes `reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked`, where `PRECISION_SCALING_FACTOR` is a fixed constant of only `4096` [1](#0-0) . When `total_tokens_staked` grows large relative to the numerator (realistic for `u128` balances with 18-decimal assets), integer division truncates the increment to `0`, and because `last_update_block` advances regardless, that period's rewards are silently and permanently lost.

## Finding Description
The core computation is in `reward_per_token`, which multiplies `reward_rate_per_block` by `rewardable_blocks_elapsed` and `PRECISION_SCALING_FACTOR` before dividing by `pool_info.total_tokens_staked` [2](#0-1) . `total_tokens_staked` is a `PoolInfo` field that grows whenever any unprivileged account calls `stake`, with no cap tied to the reward rate or `PRECISION_SCALING_FACTOR` [3](#0-2) . `ensure_mul`/`ensure_div` only guard against overflow, not against division rounding to zero — `ensure_div` returns `Ok(0)` whenever the numerator is smaller than the denominator. Immediately after computing `reward_per_token`, `update_pool_rewards` unconditionally advances `last_update_block` to the current block and stores the (possibly zero-incremented) `reward_per_token_stored` value [4](#0-3) , so the elapsed-block window used in the truncated computation can never be recovered later. `derive_rewards` divides by the same fixed `PRECISION_SCALING_FACTOR` when computing a staker's share, compounding the issue for individual stakers [5](#0-4) .

## Impact Explanation
When `reward_rate_per_block * rewardable_blocks_elapsed * 4096 < total_tokens_staked`, that period's reward-per-token increment truncates to `0`, and since `last_update_block` is advanced unconditionally, the reward for that window is permanently and silently lost to all stakers in the pool, even though the pool may be fully funded. This is a concrete, in-scope accounting bug reachable through the pallet's normal extrinsic paths (`stake`, `unstake`, `harvest_rewards`), not requiring any privileged action.

## Likelihood Explanation
Any unprivileged account can call `stake` to increase `total_tokens_staked` arbitrarily (subject to their own asset balance), and `reward_rate_per_block` is set at pool creation by the pool creator/admin, who is not privileged over other users' stakes [6](#0-5) . Given `PRECISION_SCALING_FACTOR` is a small fixed constant (`4096`) independent of the `Balance` type's magnitude (`u128`, commonly reaching `1e18`+ for standard 18-decimal assets), the truncation-to-zero condition is easily reachable under realistic reward-rate/stake-size combinations used on real chains, not a contrived edge case.

## Recommendation
Increase `PRECISION_SCALING_FACTOR` substantially (e.g., a much larger fixed-point scale, or one derived relative to the `Balance` type's expected range) or switch the reward-per-token computation to a wider intermediate type (e.g. `U256`), mirroring the approach used in `pallet-nomination-pools`'s `balance_to_point`, which converts to `U256` before dividing to avoid analogous precision loss [7](#0-6) . Alternatively, retain the un-scaled remainder across updates instead of discarding it.

## Proof of Concept
1. Create a pool with `reward_rate_per_block = 10 * 10^18` (18-decimal reward asset).
2. Have stakers cumulatively `stake` a total of `1_000_000 * 10^18` tokens (`total_tokens_staked = 1e24`), realistic for an 18-decimal staking asset.
3. Advance one block and call any extrinsic that triggers `update_pool_and_staker_rewards` (e.g. `harvest_rewards`): `reward_per_token` computes `numerator = 10e18 * 1 * 4096 = 4.096e22`, `denominator = 1e24`, and `4.096e22 / 1e24 = 0` under integer division.
4. `reward_per_token_stored` does not advance for that block, but `last_update_block` does, permanently consuming that reward window.
5. Any staker's `derive_rewards` computation for that period returns `0` reward despite holding stake in a funded pool [8](#0-7) .
