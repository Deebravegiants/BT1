### Title
POA Bridge withdrawal status is matched by asset ID only, causing wrong destination tx hash to be reported for batched withdrawals of the same token - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain completion status of a specific withdrawal (identified by `index` within a NEAR transaction) by calling `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which selects a withdrawal record from the POA Bridge API response using only the `assetId`, ignoring the `index` and the `destinationAddress`/`amount` that make each withdrawal in a batch unique.

### Finding Description
`describeWithdrawal` is documented as being asset-id scoped rather than index scoped: [1](#0-0) 

`createWithdrawalIdentifier` builds a `WithdrawalIdentifier` per withdrawal item (indexed within a single NEAR tx that may contain multiple `ft_withdraw` intents): [2](#0-1) 

The SDK explicitly supports orchestrating multiple withdrawals from a single call (`createWithdrawalCompletionPromises`, `waitForWithdrawalCompletion`), each producing its own `WithdrawalIdentifier` with a distinct `index`, and each polled independently via `watchWithdrawal` → `bridge.describeWithdrawal`: [3](#0-2) 

If a caller batches two (or more) withdrawals of the *same* `assetId` to *different* `destinationAddress` values in one NEAR transaction (e.g. splitting a withdrawal between two recipients), each of the resulting `describeWithdrawal` calls queries the same POA Bridge status endpoint for that transaction and then picks a match using only `assetId`: [4](#0-3) 

Because the match key does not include `index`, `amount`, or `destinationAddress`, both `WithdrawalIdentifier`s (index 0 and index 1) can resolve to the *same* withdrawal record returned by the bridge API. This breaks the equality the caller relies on: the `txHash`/`status` reported for withdrawal-at-index-N must correspond to the on-chain outcome of that specific withdrawal, not to a different withdrawal that happens to share the same token.

### Impact Explanation
An integrator using `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` for a batch containing two same-asset withdrawals to different addresses could receive a "completed" status with a `txHash` for the wrong withdrawal (or the same `txHash` reported twice). This is a status/hash misreport that can cause an integrator to mark a withdrawal as delivered to the wrong destination as completed, or double-credit/finalize accounting for a withdrawal that has not actually settled — matching the "status or hash misreport making an integrator credit or refund twice" impact class.

### Likelihood Explanation
This requires a caller (integrator) to legitimately batch multiple withdrawals of the identical `assetId` in one NEAR transaction with different destinations/amounts — a supported usage pattern of the SDK's batch APIs, not an attacker-controlled or malicious input. No privileged or malicious actor is needed; it is a straightforward correctness gap in matching logic that surfaces under ordinary usage of the documented batching feature. I was not able to fully confirm from the available code whether the SDK enforces uniqueness of `assetId` within a single withdrawal batch (i.e., whether this exact scenario is reachable end-to-end via `sdk.ts`'s intent-building path) — this would need to be verified by inspecting `sdk.ts`'s `createWithdrawalIntents`/`waitForWithdrawalCompletion` batch-construction logic in more depth than the indexed snippets allowed.

### Recommendation
Match withdrawals returned by the POA Bridge API using a key that uniquely identifies the specific withdrawal within the batch (e.g. combine `assetId` with `destinationAddress`/`amount`, or use an explicit per-intent identifier/index returned by the bridge if available), rather than `assetId` alone, in `findMatchingWithdrawal` inside `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`.

### Proof of Concept
1. Construct a single NEAR transaction with two `ft_withdraw` intents for the same `assetId` (e.g. `nep141:usdc.token.near`) but different `destinationAddress` values (withdrawal A to address X, withdrawal B to address Y).
2. Call `sdk.createWithdrawalCompletionPromises` (or equivalent) which creates two `WithdrawalIdentifier`s with `index: 0` and `index: 1`, both referencing the same `tx.hash`.
3. Both resulting calls to `PoaBridge.describeWithdrawal` query the POA Bridge status endpoint for the same `tx.hash` and then call `findMatchingWithdrawal(response.withdrawals, assetId)`, which is identical for both calls.
4. If the API response contains withdrawal records that are indistinguishable by `assetId` alone (e.g., due to ordering or duplicate token entries), both `describeWithdrawal` calls can return the same `txHash`/status, misreporting the outcome for withdrawal B as though it were withdrawal A's outcome.
