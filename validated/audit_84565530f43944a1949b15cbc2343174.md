Important finding: `hookData` (including `preHookContract`/`postHookContract`) is fully attacker-controlled and only constrained by inclusion in `calldataHash` (via `getHashedCalldata2`) [1](#0-0) , not by any allowlist — any address can be supplied as the hook contract in `CircomData.hookData`, unlike Bunni's Hooklet which is a pool-level immutable configuration.

### Title
Post-transaction hook is invoked before nullifiers/commitments are finalized, allowing an attacker-controlled hook to reenter with stale tree/nullifier state - (File: contracts/Hinkal.sol)

### Summary
`Hinkal::transact` calls the user-supplied `postHookContract.afterTransact()` **before** `insertNullifiers()` and `insertCommitments()` are executed [2](#0-1) . This mirrors the Bunni report's root cause exactly: an "after" callback is invoked while critical state (there, Hooklet bookkeeping; here, the nullifier registry and Merkle tree) has not yet been updated, letting an external contract that is invoked mid-transaction observe/act on stale on-chain state.

### Finding Description
In `transact()`, the sequence is:
1. Proof/root verified [3](#0-2) 
2. Token transfers happen via `_internalTransact`/`_externalTransact` (arbitrary external calls to `externalActionMap[...]` or router/wallet contracts) [4](#0-3) 
3. Balance/slippage equation checked [5](#0-4) 
4. `postHookContract.afterTransact(circomData)` is called [6](#0-5) 
5. Only afterward: `insertNullifiers(...)` and `insertCommitments(...)` [7](#0-6) 

`hookData.postHookContract` is not restricted to an allowlist; it is entirely attacker-chosen data that is merely folded into `calldataHash` for integrity, not for authorization [1](#0-0) . Because `nonReentrant` on `transact`/`prooflessDeposit` only prevents reentering those two specific entry points [8](#0-7) [9](#0-8) , it does not prevent the attacker's hook contract from reading any other view/state on `Hinkal`/`HinkalBase` (e.g. `rootHashExists`, `nullifiers[...]`) while the current transaction's nullifiers have not yet been marked spent and its new commitments have not yet been inserted into the tree.

I was unable to fully verify, within the remaining budget, whether any *other* non-`nonReentrant` state-mutating entry point in `HinkalBase`/`Merkle`/`MerkleBase` reads or depends on the not-yet-inserted root/nullifier state in a way that could be combined with this callback to break the core equality (double-spend a nullifier, or accept a (leaf,root) pair the tree never produced). The report only explicitly shows the ordering hazard (external call before nullifier/commitment finalization), but a concrete unauthorized-value-transfer or double-spend path executed purely by an unprivileged EOA through this ordering issue was not confirmed by reading `MerkleBase.sol`'s `rootHashExists`/`roots` mapping logic or other externally-reachable functions that might be reentered during the `afterTransact`/`preTransact` window.

### Impact Explanation
If a reachable double-spend or root-forgery path exists through this ordering (e.g., using the not-yet-updated `nullifiers` mapping or root history to pass a check inside a reentered call before the current transaction's nullifiers are marked spent), it would constitute a nullifier double-spend / unbacked minting — Critical severity per the program's rubric. Without confirming a concrete secondary state read that is exploitable, the impact cannot be confirmed as more than a design smell.

### Likelihood Explanation
The attacker fully controls `hookData.postHookContract`/`preHookContract` for their own transaction (no admin/relayer key needed), so the code *path* is trivially reachable by any EOA; what's unproven is whether it can be chained into an equality-breaking outcome given the `nonReentrant` guard on `transact` itself.

### Recommendation
Move `insertNullifiers()` and `insertCommitments()` to occur before invoking `postHookContract.afterTransact()`, and reorder `preHookContract.preTransact()` similarly so that no external call is made with intermediate/incomplete state — matching the pattern Bacon Labs applied in Bunni v2 PR #120 (move the effect-completing logic to after the hook call, or, symmetrically, ensure all state that must be "final" for other contracts to reason about with this transaction is written before any external call within `transact`).

### Proof of Concept
Not confirmed as end-to-end exploitable within the available investigation. A background agent with full repo/test access should:
1. Deploy a malicious contract implementing `ITransactHook.afterTransact` and set it as `hookData.postHookContract` in a `transact()` call.
2. Inside `afterTransact`, attempt to read `nullifiers[...]` / `rootHashExists(...)` for the nullifiers/commitments of the in-flight transaction (not yet inserted) and attempt to trigger any other Hinkal-adjacent function (e.g. a second, independently-proven `transact()` call using a different nullifier set that relies on the stale root, or an external action contract that reads Hinkal balances) to see if a double-spend, extra minting, or unauthorized fund movement can be produced before `insertNullifiers`/`insertCommitments` execute.
3. If no exploitable state dependency is found, downgrade/close this finding as a defense-in-depth ordering issue rather than a concrete vulnerability.
