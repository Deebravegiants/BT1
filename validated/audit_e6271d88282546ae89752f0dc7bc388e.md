### Title
Webhook `shop-domain` (tenant identity) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw HTTP body, then trusts the `shop-domain` header (and `topic`/`webhook-id`/`api-version` headers) as the tenant identity handed to the app's handler. Because the HMAC is computed only from the body and signed with the app-wide `api_secret_key` (shared across every shop that installs the app), any party that can generate one legitimately-signed webhook body (e.g., by installing/using the app on their own store) can replay that body with a forged `shop-domain` header pointing at a victim shop, and the signature will still validate.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are read straight from HTTP headers that are never part of the signed material: [2](#0-1) 

`Registry.process` performs exactly one authentication check — the HMAC over the body — and then dispatches the handler using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` values as the tenant/topic identity: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` compute the HMAC using `Context.api_secret_key`, which is the single shared secret for the whole app across all merchant shops (not a per-shop secret): [4](#0-3) 

**Equality being broken:** the intended binding is `authenticated(shop header) == shop the HMAC actually proves`. In reality the HMAC only proves "some request body was signed with the app's global secret" — it says nothing about which shop the header claims to be from. Since the same secret authenticates webhook traffic from *every* shop that has installed the app, an unprivileged user who has installed the app on their own store (a normal, no-privilege action) can capture one of their own store's legitimately-signed webhook deliveries (topic + raw body + valid `x-shopify-hmac-sha256`), then replay that exact body/HMAC pair to the app's webhook endpoint while substituting `x-shopify-shop-domain` (and, if desired, `x-shopify-topic`) for a victim shop. `Utils::HmacValidator.validate` will still return `true` because it never inspects the header values, and `Registry.process` will invoke the handler with `WebhookMetadata.new(shop: <victim shop>, topic: ..., body: ...)`.

Many webhook bodies are shop-independent or attacker-influenced in content (e.g., `app/uninstalled`, `shop/update`, `customers/redact`, or any topic where the JSON body the attacker controls/observes on their own shop is byte-identical to what a legitimate handler expects), so this is not merely a theoretical body/shop mismatch — the attacker chooses which topic to replay and can tailor which of their own store's events to capture and replay against a different shop identity.

### Impact Explanation
Any downstream logic that keys off `WebhookMetadata#shop` to select which merchant's session/access token to use, to write per-tenant state, or to trigger mandatory compliance/lifecycle actions (uninstall cleanup, redaction, etc.) can be made to act on behalf of a shop the requester does not control. This is a cross-tenant boundary break: the "shop" field is acted upon by the application but is not bound by the cryptographic check that is supposed to authenticate the request, meeting the "cross-tenant access" criteria for a Critical-impact finding.

### Likelihood Explanation
Exploitation requires no privileged credentials — only the ability to install/trigger the target app on an attacker-controlled store (any developer/merchant can do this) and the ability to send an arbitrary HTTP request with attacker-chosen headers to the app's public webhook endpoint (which every embedded app must expose). Capturing one's own webhook payload/HMAC pair and replaying it with a different `shop-domain` header requires only standard HTTP tooling.

### Recommendation
Bind the tenant identity into the authenticated material rather than trusting an unsigned header:
- Include `shop-domain` (and ideally `topic`/`webhook-id`) in the value that is HMAC-verified, or independently verify that the `shop-domain` header corresponds to a shop for which the app holds an active, previously-established session/installation before acting on the payload.
- At minimum, document and enforce in `Registry.process` that the `shop` conveyed in `WebhookMetadata` must be cross-checked against the app's own session store for that shop before any tenant-scoped action is taken, since the HMAC alone cannot vouch for header authenticity.

### Proof of Concept
1. Attacker installs the target Shopify app on their own development/trial store (`attacker.myshopify.com`) — no special privileges required.
2. Attacker triggers a webhook whose body content they can predict or observe verbatim (e.g. `app/uninstalled`, which typically has an empty/minimal JSON body `{}`), capturing:
   - `raw_body`
   - `x-shopify-hmac-sha256` header (valid, computed by Shopify using the app's real `api_secret_key`)
3. Attacker POSTs to the app's public webhook endpoint with:
   - the identical `raw_body`
   - the identical `x-shopify-hmac-sha256`
   - `x-shopify-topic: app/uninstalled` (or another topic expecting the same body shape)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
4. `Utils::HmacValidator.validate` (see `lib/shopify_api/utils/hmac_validator.rb:12-31`) validates successfully because it only checks `raw_body` against the shared secret.
5. `Registry.process` (see `lib/shopify_api/webhooks/registry.rb:188-200`) invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "app/uninstalled", ...)`, causing the app to perform victim-shop-scoped actions (e.g., deleting/deactivating the victim's stored session/data) triggered entirely by the attacker.
