### Title
Unbounded string-length arithmetic in Pharos BLS key decoding can overflow/underflow and corrupt or crash consensus verification - (File: modules/consensus/pharos/verifier/src/state_proof.rs)

### Summary
The reported bug class (ImageMagick JLSEC-2026-905 / CVE-2023-34151) is "undefined behavior from casting an oversized numeric value into `size_t` during untrusted data parsing." The closest reachable analog in this codebase is the Solidity-long-string length decoding used by the Pharos consensus client when it decodes the validator-set storage proof: a 256-bit header value taken from proof data is truncated to `u64`/`usize` and then used in unchecked arithmetic (`length + 31`, `length - i*32`) to size buffers and slice storage arrays, with no upper bound check before the arithmetic is performed.

### Finding Description
`bls_data_slots_from_header` and `decode_bls_key_from_string_slot` in `modules/consensus/pharos/verifier/src/state_proof.rs` implement the Solidity "long string" storage-layout decoding: [1](#0-0) 

```
let header_val = decode_u256_from_storage(header_value)?;
...
let length = (header_val - 1) / 2;
let str_len = length.low_u64() as usize;
Ok((str_len + 31) / 32)
```

and [2](#0-1) 

`str_len` is derived from `header_val.low_u64()`, i.e. only the low 64 bits of a full `U256` value are kept, and the resulting length is then used unchecked in `str_len + 31`, `str_len - (i * 32)`, and to size a `Vec::with_capacity(str_len)`. There is no explicit bound on `str_len` before these operations.

This code is reached from an untrusted, relayer-submitted proof: `PharosClient::verify_consensus` decodes the wire proof and calls `verify_pharos_block`, which (at an epoch boundary) calls `state_proof::verify_validator_set_proof`, which calls `compute_all_storage_keys` and `decode_validator_set_from_storage` — both of which call `bls_data_slots_from_header`/`decode_bls_key_from_string_slot` on `proof.storage_values`, a plain `Vec<Vec<u8>>` field of the wire-decoded `ValidatorSetProof`: [3](#0-2) [4](#0-3) [5](#0-4) 

Critically, `compute_all_storage_keys` runs this length arithmetic on `storage_values` **before** `verify_all_storage_proofs` checks those bytes against the real state root: [6](#0-5) 

So the order-of-operations lets the header-length arithmetic execute on attacker-controlled bytes prior to any cryptographic check that those bytes actually exist in the proven trie. If the arithmetic panics (Rust debug/overflow-checked builds panic on `usize` addition/subtraction overflow) or silently wraps (release builds without overflow-checks), the failure occurs during the very first parsing pass, independent of whether the merkle proof would ultimately fail.

### Impact Explanation
A malformed/crafted `ValidatorSetProof.storage_values` entry that produces a `str_len` near `usize::MAX` (via the low-64-bit truncation of an arbitrarily large `U256` "header" value) can cause:
- an arithmetic-overflow panic on `str_len + 31` (Substrate runtimes commonly build with `overflow-checks = true`), aborting extrinsic/consensus-update execution, or
- an arithmetic-underflow panic on `str_len - (i * 32)` in `decode_bls_key_from_string_slot` if `data_slots`/`str_len` become inconsistent, or
- a huge/failed allocation via `Vec::with_capacity(str_len)`.

Any of these halts consensus-proof processing for the Pharos light client, which is the mechanism that finalizes state commitments consumed by ISMP message delivery for that state machine — i.e. it can be used to deny bridge message delivery/finality for the affected route (availability impact), matching the CVSS vector in the report (`C:N/I:N/A:H`).

### Likelihood Explanation
Reachability requires only a normal (unprivileged) relayer submitting a consensus update/proof to `PharosClient::verify_consensus` — no special privilege is needed to submit the proof itself. The remaining uncertainty (and reason this is Medium rather than higher) is whether the attacker can get an out-of-range `header_val` accepted as a "real" value that will still pass `verify_all_storage_proofs` against a genuine Pharos state root, since normal Solidity string-length headers are bounded by realistic on-chain string sizes. I could not fully confirm from the available Solidity source whether the Pharos staking contract's `blsPublicKey`/description string fields are writable with attacker-chosen raw header words (e.g., via low-level `sstore` in a registration path) that would not correspond to an actually-stored string of that length. This should be verified against the live Pharos staking contract before treating this as fully weaponizable; absent that, it stands as an unsound length-parsing routine with no defensive bound, which is the same root-cause pattern as the reported analog.

### Recommendation
- Add an explicit maximum length check on `str_len` (and pre-checks on `header_val` before subtracting 1 / dividing) immediately after computing it in both `bls_data_slots_from_header` and `decode_bls_key_from_string_slot`, rejecting any value above a small sane bound (e.g. a few hundred bytes, consistent with a 48-byte BLS key encoded as hex).
- Use `checked_add`/`checked_sub`/`saturating_*` for all arithmetic derived from these lengths instead of `+`/`-`.
- Reorder `verify_validator_set_proof` so that raw `storage_values` are cryptographically verified against `state_root` (via `verify_all_storage_proofs`) before any length-derived arithmetic/key-derivation is performed on them, removing the current key-computation pass over unverified bytes.

### Proof of Concept
1. Craft a `ValidatorSetProof` whose `storage_values[idx]` (the BLS header slot for some pool) encodes a `U256` header value `H` such that `H` is odd (long-string flag set) and `(H - 1) / 2` truncated to `u64` is close to `u64::MAX` (e.g. `H = 2 * (u64::MAX - 5) + 1`, encoded as a 32-byte big-endian value with the low 64 bits set accordingly).
2. Submit this as part of a `VerifierStateUpdate` proof to `PharosClient::verify_consensus` (reachable by any relayer through the normal consensus-update dispatch path).
3. Execution reaches `compute_all_storage_keys` → `bls_data_slots_from_header`, computing `str_len ≈ u64::MAX - 5`, then `(str_len + 31) / 32` overflows `usize` addition, panicking the runtime (or, in a build without overflow checks, wrapping to a small/incorrect slot count and corrupting subsequent key/value bookkeping) before the storage proof itself is ever checked against `state_root`.

pub fn bls_data_slots_from_header(header_value: &[u8]) -> Result<usize, Error> {
	let header_val = decode_u256_from_storage(header_value)?;
	let header_bytes = header_val.to_big_endian();
	let lowest_byte = header_bytes[31];

	if lowest_byte & 1 == 0 {
		// Short string - data is in the header itself
		Ok(0)
	} else {
		// Long string - header = length * 2 + 1
		let length = (header_val - 1) / 2;
		let str_len = length.low_u64() as usize;
		Ok((str_len + 31) / 32)
	}
}
