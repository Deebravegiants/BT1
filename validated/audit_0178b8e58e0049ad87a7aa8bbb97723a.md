## Title
Webhook Shop-Domain Header Is Not Bound to the HMAC Signature, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the `shop-domain`, `topic`, `api-version`, and `webhook-id` headers are read directly from unauthenticated HTTP headers and passed to the handler as if they were verified. `Registry.process` validates the HMAC and then immediately hands `request.shop` to the app's webhook handler as the trusted tenant identifier, even though `shop` is not part of what was actually verified.

### Finding Description
The signable string used for HMAC verification is defined as: [1](#0-0) 

Only `@raw_body` is signed. The `shop` accessor, however, is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, entirely outside the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC and, on success, forwards `request.shop` to the developer's handler as the authenticated shop for that webhook: [3](#0-2) 

The broken identity binding is: `shop header verified-by-HMAC == shop header delivered-to-handler`. In truth, only the request body is authenticated; the shop header is asserted, not verified. Since a single app's `client_secret` (the HMAC key used by `HmacValidator`/`Context.api_secret_key`, see `lib/shopify_api/utils/hmac_validator.rb:16`) is shared across every shop that has installed the app, any merchant who can install the app can capture one legitimately HMAC-signed webhook body sent to their own store, then replay that exact `raw_body` + valid `hmac` value to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` header naming a victim shop. `HmacValidator.validate` will still pass (it only checks the body against the shared secret), and `Registry.process` will invoke the handler believing the webhook legitimately originated from the victim shop.

### Impact Explanation
This breaks the tenant boundary the webhook processing pipeline is implicitly relying on: a handler written against this API naturally trusts `WebhookMetadata#shop` because it is only reachable after `HmacValidator.validate` succeeds. An attacker with no privileges beyond being able to install the target app on their own shop can trigger handler logic (e.g., `orders/create`, `app/uninstalled`, GDPR mandatory webhooks) tagged as coming from an arbitrary victim shop domain, resulting in cross-tenant data confusion/access inside the host application. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on an attacker-controlled/free store to receive one genuine, HMAC-valid webhook, and (2) replaying that exact body+HMAC pair with a forged shop header to the app's public webhook endpoint. No access token, `api_secret_key`, or privileged account is needed — this is entirely within reach of an ordinary internet user who can install a public app.

### Recommendation
Bind the shop identity into the verified material. Options: include the `shop-domain` (and ideally `topic`, `webhook-id`) header values as part of the signable string alongside the body, or require host applications to cross-check `request.shop` against a known, previously-installed shop record (and reject amounts/replays) before trusting it. At minimum, document loudly that `Webhooks::Request#shop` is not covered by the HMAC and must be independently validated by the consuming application against its own shop/session store before use.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, and configures/subscribes to a webhook topic (e.g. `customers/data_request` or any topic the app registers).
2. Shopify sends a legitimately signed webhook to the app's endpoint:
   ```
   POST /webhooks
   x-shopify-topic: customers/data_request
   x-shopify-hmac-sha256: <valid HMAC over body>
   x-shopify-shop-domain: attacker.myshopify.com
   Body: {"shop_id":111,"shop_domain":"attacker.myshopify.com", ...}
   ```
   Attacker captures the raw body and the `x-shopify-hmac-sha256` value.
3. Attacker replays the identical body and HMAC to the same endpoint, but sets:
   ```
   x-shopify-shop-domain: victim.myshopify.com
   ```
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13-22`) recomputes the signature over `to_signable_string` (the raw body only) using the app's shared `api_secret_key`, and it matches — validation succeeds.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) invokes the app's handler with `WebhookMetadata` whose `shop` is `"victim.myshopify.com"`, even though the webhook never originated from Shopify for that shop.
