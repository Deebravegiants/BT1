### Title
`SolverAccount._containsFillOrder` scans for a single `fillOrder` selector, so its bid-replay-griefing guard is silently disabled against v1 IntentGatewayV2 deployments - (File: `evm/src/apps/intentsv2/SolverAccount.sol`)

### Summary
This is the same bug class as the Curve report: a contract hard-codes one function interface/selector for an external call target that in production actually speaks two incompatible ABI shapes, and the mismatch silently disables the intended logic rather than erroring loudly.

### Finding Description
`SolverAccount.validateUserOp` treats a 65-byte-signature userOp as plain ECDSA-signed only if the calldata does **not** contain a call to `IntentGatewayV2.fillOrder`, because a public bid already carries a valid solver ECDSA signature over `userOpHash` and could otherwise be replayed by anyone, consuming the solver's nonce and gas: [1](#0-0) 

The detection relies on a single hard-coded selector taken from the interface currently imported into this file: [2](#0-1) 

and the scan itself only ever compares against that one selector: [3](#0-2) 

Independently, the SDK's own docs establish that `IntentGatewayV2.fillOrder` exists in **two incompatible on-chain shapes with different selectors** (`0x5cfb1ea5` for the pre-`validUntil` "v1" gateway, `0xa5470064` for the "v2" gateway with `FillOptions.validUntil`), that gateways are upgraded per-chain (so both shapes are live at once across chains), and that as of the writing "every mainnet gateway still runs the pre-`validUntil` implementation" (v1): [4](#0-3) [5](#0-4) 

The off-chain/indexer side of the codebase already had to patch exactly this class of bug twice — once in the SDK's `decodeFillOrder` (tries v2 then v1) and once in the indexer's `phantom-decode.ts`, which originally built an ethers `Interface` from only the v2 ABI and therefore silently rejected every real (v1) bid on mainnet: [6](#0-5) 

`SolverAccount.sol`, however, was never updated to account for the two shapes: `IIntentGatewayV2.fillOrder.selector` resolves to whatever single signature is declared in the imported interface (the v2 one, since it's the "current" interface), while `INTENT_GATEWAY_V2` is set at deployment to point at the actual (possibly v1) gateway on that chain. On any chain where the deployed gateway is still v1 — which per the SDK's own docs is every mainnet chain — a genuine `fillOrder` call in the batch is encoded with the v1 selector (`0x5cfb1ea5`), not the v2 selector the account checks for. `bytes4(calls[i].callData) == FILL_ORDER_SELECTOR` never matches, so `_containsFillOrder` always returns `false` for real fills on that chain, and the anti-replay/anti-griefing branch is completely bypassed.

### Impact Explanation
With the check bypassed, anyone who observes a solver's public bid (a valid userOp containing a 65-byte ECDSA solver signature over `userOpHash` plus a `fillOrder` call in its ERC-7821 batch) can resubmit that exact userOp through the plain ECDSA-validation path. `super.validateUserOp` will accept it (the signature is valid), consuming the solver's account nonce and burning the solver's prefunded gas, without a corresponding `select()` having staged the session key — the fill itself then reverts at execution, but the EntryPoint still charges gas against the solver account. This is a direct loss-of-funds griefing vector against every solver operating against an unpatched (v1) `IntentGatewayV2`, reachable by any unprivileged party who can see pending/broadcast bids (mempool, bundler, or on-chain history) and resubmit them through an ERC-4337 EntryPoint — no special privilege required.

### Likelihood Explanation
High. The SDK's own documentation states the v1 gateway shape was, at the time of the fix, deployed on **every mainnet chain**; `SolverAccount` is constructed with `INTENT_GATEWAY_V2` fixed at deploy time to that same gateway address, so the mismatch is not a hypothetical edge case but the default production condition until every gateway is individually upgraded past `validUntil`. Exploitation requires no signature forgery — only replaying calldata that is already public as part of the bidding protocol.

### Recommendation
Mirror the fix already applied to the off-chain codec/indexer: have `_containsFillOrder` recognize **both** `fillOrder` selectors (the pre- and post-`validUntil` shapes), e.g. by comparing against both `bytes4` constants derived from the two known signatures (as `FILL_ORDER_V1_ABI` / `IntentGatewayV2ABI` already do off-chain), or by deriving the selector to check from the gateway's actual deployed version (mirroring `getFillOptionsVersion`) rather than from whichever interface happens to be imported at compile time. Add a regression test that deploys `SolverAccount` against a mock v1-shaped gateway and confirms a 65-byte-signature userOp containing a v1 `fillOrder` call is still rejected.

### Proof of Concept
1. Deploy `SolverAccount` with `INTENT_GATEWAY_V2` pointing at a v1 (pre-`validUntil`) `IntentGatewayV2` deployment, matching current mainnet state per the SDK docs cited above.
2. A solver signs and submits (or has bundled) a userOp whose `callData` is an ERC-7821 `execute(mode, executionData)` batch containing a call to the gateway with `fillOrder` encoded in the **v1** shape (selector `0x5cfb1ea5`), and whose `op.signature` is the plain 65-byte ECDSA signature over `userOpHash` (the shape used for a public bid).
3. Anyone observing this userOp resubmits it unchanged to the EntryPoint.
4. `validateUserOp` computes `bytes4(calls[i].callData) == FILL_ORDER_SELECTOR`, comparing the v1 selector against the hard-coded v2 selector — no match, `_containsFillOrder` returns `false`.
5. Execution proceeds to `super.validateUserOp`, which accepts the valid ECDSA signature; the solver's nonce is consumed and gas is charged, even though `fillOrder` will subsequently revert (no `select()` was staged), confirming the griefing outcome the check was meant to prevent.

```text
    function _containsFillOrder(bytes calldata callData) private view returns (bool) {
        if (callData.length < 4 || bytes4(callData[0:4]) != EXECUTE_SELECTOR) return false;

        (, bytes memory executionData) = abi.decode(callData[4:], (bytes32, bytes));
        Execution[] memory calls = abi.decode(executionData, (Execution[]));

        for (uint256 i = 0; i < calls.length; i++) {
            bool hasFillOrder = calls[i].target == INTENT_GATEWAY_V2 && bytes4(calls[i].callData) == FILL_ORDER_SELECTOR;
            if (hasFillOrder) return true;
        }
        return false;
    }
```

```markdown
# 2026-08-27 — The implementation address identifies the FillOptions shape

Chosen: `getFillOptionsVersion` reads the ERC-1967 implementation slot and checks the address
against `LEGACY_FILL_OPTIONS_IMPLEMENTATIONS`, a set of implementations deployed before
`validUntil` existed. Anything else is v2.

EIP-1967 standardises three slots — implementation, admin, beacon — all holding addresses. There
is no version field in the spec to read, and OZ `Initializable`'s `uint64` only moves under
`reinitializer(N)`, which this contract does not use. The implementation address is the only value
the proxy actually updates on upgrade, so it is what identifies the deployed code.

The list is of **legacy** implementations, not current ones, so the default is v2. That direction
is the whole point: a newly shipped implementation needs no edit here, and once every deployment
is upgraded the set is vestigial and still correct.

A single entry covers every chain that runs it. The protocol contracts are CREATE2-deployed, so
`0x976B268b06f545c4A2BF44866Aa2465bd8B3C67d` is the pre-`validUntil` implementation on those
chains — confirmed with the maintainers rather than inferred, since the CREATE2 claim in the tree
is about the proxies and does not by itself say anything about implementations.
```

```markdown
# 2026-08-28 — Decode phantom bids of either `fillOrder` shape

`extractFillDataVm2` built one ethers `Interface` from `FILL_ORDER_ABI`. When `FillOptions` gained `validUntil`
that ABI moved to the v2 shape, and since ethers validates the selector before decoding, every v1-shaped bid
started throwing. The throw was swallowed by a `continue`, the function returned null, and `aggregatePhantomBids`
drops a null bid with no log line — so the loss was silent.

That is not a future risk: `@hyperbridge/sdk` is a `workspace:*` dependency, so the indexer picked up the v2 ABI
immediately, while every mainnet gateway still runs the pre-`validUntil` implementation. `getFillOptionsVersion`
therefore returns 1 and simplex encodes v1 bids, all of which were being discarded — no bidder rows, no median,
no pool-rate snapshot from any of them.

Now tries both shapes, mirroring the SDK's `decodeFillOrder`. The selectors differ (`0x5cfb1ea5` vs
`0xa5470064`), so neither can mis-decode the other's payload. The v1 ABI is imported from the SDK rather than
re-declared here, so the two cannot drift apart again.
```
