### Title
Native ETH returned by an Emporium op is never tracked and gets permanently stuck in the Emporium contract - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` lets a user route through arbitrary external calls (`stack.ops`) and then reconciles balances *only* for the tokens listed in `circomData.erc20TokenAddresses` [1](#0-0) . If one of the called endpoints (e.g. a Curve-style pool, exactly the protocol class described in the external report) pays back native ETH to the Emporium contract, but `address(0)` was not included in `erc20TokenAddresses`, that ETH is invisible to the `balanceChange` computation and is never wrapped into a `UTXO`, nor forwarded to `msg.sender` by `handleOut` [2](#0-1) . Unlike the Curve report's `Curve.sol`, which at least has `withdrawOneCoinI`/`withdrawOneCoinU` wrapping ETH into WETH for sweeping, Emporium and its base contracts have no sweep/rescue path at all for stray ETH.

### Finding Description
`runAction` snapshots `balancesBefore` for exactly the tokens supplied by the caller in `circomData.erc20TokenAddresses`, executes the arbitrary `stack.ops` (each of which can be a stateless low-level call `op.endpoint.call{value: op.value}(op.callData)` to any third-party contract), and then snapshots `balancesAfter` for that *same, caller-chosen* token list [3](#0-2) . The only asset accounting performed is:

```
balanceChange = balancesAfter[i] - balancesBefore[i]  (+ adjustment for deposited delta)
```

for `i` ranging over `circomData.erc20TokenAddresses`, and only positive `balanceChange` values get forwarded to `msg.sender` via `handleOut` -> `transferERC20TokenOrETH` [4](#0-3) . If native ETH (`address(0)`) is not part of that list — e.g. the user's operation targets a Curve-like pool's `remove_liquidity`/`withdraw` for an ETH/stETH pool, expecting only the LP or stable token to move — any ETH the pool sends back to the Emporium contract as `msg.value` in the low-level `.call` reply is completely outside the tracked equality and is dropped.

I confirmed there is no sweep, rescue, or owner-withdraw path for stray native ETH anywhere in the relevant contracts: `ExternalActionBaseUpgradeable` only exposes `setAllowedRecipients`/`runAction` [5](#0-4) , `ExternalActionBaseV2` is likewise limited [6](#0-5) , and `EmporiumUpgradeable` only adds fee/relay and signature-verification helpers with no ETH rescue function [7](#0-6) . This is the same root-cause class as the external Curve report: an integration that forwards calls to a third-party contract capable of returning ETH, without the wrapper accounting for/handling that ETH outside the specific "expected" token set, and with no path for the user to reclaim it.

The equality broken is Hinkal's core solvency/accounting invariant for external actions: *"total change of external-action balance = value moved to it via deltaAmountChanges + value returned to the caller as UTXOs."* Here, ETH silently returned by a called endpoint is neither charged against the caller's deposit nor emitted as a UTXO — it simply vanishes from the equation while remaining physically on the Emporium contract's balance.

### Impact Explanation
This causes permanent freezing of the depositor's own funds: the ETH the user's own shielded balance/deposit was converted into by interacting with the third-party protocol (via `stack.ops`) becomes permanently stuck on the `EmporiumUpgradeable` contract with no recovery mechanism, exactly mirroring the "user can not claim his ETH liquidity" scenario from the report, but with no way to ever recover it (not even by the contract owner). Per the impact classification, permanent freezing of user funds is Critical.

### Likelihood Explanation
High. Reaching this path requires nothing beyond an ordinary, unprivileged EOA calling `Hinkal.transact` with `externalActionId` pointing at `EmporiumUpgradeable`, and encoding an `EmporiumStack` whose `ops` target any protocol (Curve-style ETH pools, or any contract that can push back native ETH as a refund/reward/withdrawal) while `circomData.erc20TokenAddresses` doesn't happen to include `address(0)`. No signer/relay/owner privilege is required when `stack.signerAddress == address(0)` (the stateless path) [8](#0-7) [9](#0-8) .

### Recommendation
In `runAction`, always include `address(0)` in the balance reconciliation regardless of whether it was supplied in `circomData.erc20TokenAddresses`, or require/validate that any ETH balance increase on the Emporium contract after executing `stack.ops` is captured and forwarded to `msg.sender`/wrapped as a UTXO (mirroring the WETH-wrap approach recommended for `Curve::withdrawOneCoinI`/`withdrawOneCoinU` in the original report). Alternatively, add an explicit, permissioned sweep for stray native ETH that only benefits the affected depositor via UTXO issuance, not an arbitrary owner claim.

### Proof of Concept
1. User A holds a shielded UTXO and wants to call, via `Hinkal.transact` → `EmporiumUpgradeable.runAction`, a Curve-style ETH/stETH pool's `remove_liquidity`/`withdraw` function through a stateless op (`invokeWallet = false`, `signerAddress = address(0)`).
2. `circomData.erc20TokenAddresses` is built to list only the LP/pool token being withdrawn (matching what the proof/circuit expects) — `address(0)` (ETH) is not included, since the user's intent per the proof is only about the pool token.
3. `runAction` executes `op.endpoint.call{value: op.value}(op.callData)` targeting the pool's withdraw function; the pool sends native ETH back to `EmporiumUpgradeable` as part of the call's `msg.value` refund/return.
4. `balancesBefore`/`balancesAfter` are computed only over the listed pool token; the returned ETH balance increase on the Emporium contract is never observed. `handleOut` iterates only over `circomData.erc20TokenAddresses` and never sends the ETH to `msg.sender` (Hinkal) or creates a UTXO for it.
5. The ETH remains on `EmporiumUpgradeable` permanently; no function in `ExternalActionBaseUpgradeable`, `ExternalActionBaseV2`, or `EmporiumUpgradeable` exists to recover it for the affected user or anyone else.

    function handleOut(
        int256 balanceChange,
        CircomData calldata circomData,
        uint256 i
    ) internal returns (UTXO memory outUtxo) {
        // total change can be less than zero if there was some balance before the call -> that's why we have <=

            return outUtxo;

        transferERC20TokenOrETH(
            circomData.erc20TokenAddresses[i],
            msg.sender,
            uint256(balanceChange)

            uint256(balanceChange),
            circomData.erc20TokenAddresses[i],
            circomData.stealthAddressStructure,
            circomData.timeStamp

    function payRelayFees(
        CircomData calldata circomData,
        address signerAddress,
        int256[] calldata deltaAmountChanges
    ) internal {
        FeeStructure calldata feeStructure = circomData.feeStructure;

        bool foundToken = false;

        for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            // tokens deposited into Emporium are not charged
            if (deltaAmountChanges[i] >= 0) {
                continue;
            }

            address erc20TokenAddress = circomData.erc20TokenAddresses[i];
            bool isFeeToken = erc20TokenAddress == feeStructure.feeToken;

            if (isFeeToken) {
                foundToken = true;
            }

            uint256 relayFee = 0;
            uint256 flatFee = isFeeToken ? feeStructure.flatFee : 0;

            if (signerAddress == address(0)) {
                uint256 sumAbs = uint256(-deltaAmountChanges[i]);

                EmporiumStorageVars storage $ = _getEmporiumStorage();
                relayFee = $._hinkalHelper.calculateRelayFee(
                    sumAbs,
                    flatFee,
                    feeStructure.variableRate
                );
            } else {
                relayFee = flatFee;
            }

            payRelay(
                circomData.relay,
                signerAddress,
                relayFee,
                erc20TokenAddress
            );
        }

        if (!foundToken && feeStructure.flatFee != 0) {
            require(
                signerAddress != address(0),
                "Gas Token in Emporium is not found"
            );

            payRelay(
                circomData.relay,
                signerAddress,
                feeStructure.flatFee,
                feeStructure.feeToken
            );
        }
    }

    function payRelay(
        address relay,
        address signerAddress,
        uint256 relayFee,
        address erc20TokenAddress
    ) internal {
        if (relay == address(0) || relayFee == 0) {
            return;
        }

        if (signerAddress == address(0)) {
            sendToRelay(relay, relayFee, erc20TokenAddress);
        } else {
            sendToRelayFromWallet(
                relay,
                signerAddress,
                relayFee,
                erc20TokenAddress
            );
        }
    }
