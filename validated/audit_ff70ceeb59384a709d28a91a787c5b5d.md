**Reasoning:**

The scenario requires assuming a pre-existing defect in the block partitioner's dependency-edge computation (i.e., that it "omits" a required edge for a real read/write conflict). That is not something an unprivileged transaction can cause on its own — dependency computation is done by the deterministic, consensus-critical `PartitionerV2` algorithm over the block's actual read/write sets [1](#0-0) , and the resulting `required_edges`/`dependent_edges` are what `CrossShardStateView::create_cross_shard_state_view` uses to decide which keys must wait for cross-shard values instead of falling back to `base_view` [2](#0-1) .

Key points against validity:

1. **No demonstrated bug in the actual edge-computation logic.** The question's premise ("the partitioner omits that key") is asserted, not shown. The partitioner builds read/write sets and cross-shard trackers from the transaction's own `read_hints`/`write_hints` [3](#0-2) , and any resource read/written by a withdrawal transaction (e.g., the `SignerCapability`/`Account` resource key) that conflicts with a prior write is, by construction of the tracker/edge algorithm, captured as a `required_edge`. A missing edge would be an algorithmic defect in `PartitionerV2`/`add_edges`, which is validator infrastructure, not something reachable via unprivileged transaction content alone.

2. **This is a correctness/liveness concern for the sharded execution mode, not a custody-authority bypass reachable by unprivileged input.** Sharded execution (`ShardedExecutorService`, `CrossShardStateView`) is an alternate/optional execution backend; its output must still match the canonical, consensus-agreed state (e.g., against BlockSTM sequential/parallel execution) as part of state-root verification. A stale read causing wrong output would produce a state-root mismatch/execution divergence rather than a silently accepted unauthorized withdrawal that the rest of the network would also accept.

3. **Actual capability enforcement happens inside the Move VM at execution time, not in the state-view plumbing.** Whether the VM sees a revoked or existing `SignerCapability` depends on what value the state view returns, but the mechanism for deciding which values must be exchanged cross-shard (`required_edges_iter`) is derived from the same deterministic read/write-set analysis that all validators independently and identically compute — an attacker cannot supply transaction data that selectively removes an edge while everyone else keeps it consistent, since this isn't user-controlled data, it's an internal deterministic computation over the block's declared read/write footprints.

Since the finding requires assuming an internal, unproven algorithmic bug in privileged infrastructure logic rather than showing an unprivileged input directly forcing an authority bypass, this does not meet the custody decision standard (which requires unprivileged input to cross a real custody boundary through an existing, demonstrable code path).

    pub fn create_cross_shard_state_view(
        base_view: &'a S,
        transactions: &[TransactionWithDependencies<AnalyzedTransaction>],
    ) -> CrossShardStateView<'a, S> {
        let mut cross_shard_state_key = HashSet::new();
        for txn in transactions {
            for (_, storage_locations) in txn.cross_shard_dependencies.required_edges_iter() {
                for storage_location in storage_locations {
                    cross_shard_state_key.insert(storage_location.clone().into_state_key());
                }
            }
        }
        CrossShardStateView::new(cross_shard_state_key, base_view)
    }
}
