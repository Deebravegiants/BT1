### Title
Native ETH sent to `EvmHost.dispatch()`/`fundRequest()` beyond the exact fee-swap requirement becomes permanently stuck - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` all accept `msg.value` and forward the entire amount to `swapETHForExactTokens`, but never capture the `amounts` return value nor refund the unused ETH change that the Uniswap router sends back. This is the same root-cause pattern as the referenced report: a payable entrypoint conditionally routes value into a sub-operation, and any excess/unused value is silently absorbed by the contract instead of being returned to the payer.

### Finding Description
In `EvmHost.sol`, all three fee-paying entrypoints follow the same pattern: [1](#0-0) [2](#0-1) [3](#0-2) 

In each case, `swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` is called. `UniswapV2Router02.swapETHForExactTokens` only consumes the ETH required to buy `fee` units of `feeToken`, and refunds any leftover ETH to `msg.sender` of that call — which is `EvmHost` itself, not the original external caller (`_msgSender()`/`tx.origin`). Because `EvmHost` discards the returned `amounts` array and performs no post-swap refund logic, any leftover ETH becomes an unattributed increase in the host's own balance with no accounting entry, and no function exists to return it to the payer.

Contrast this with `IntentGatewayV2.placeOrder`, which performs the equivalent swap correctly by capturing the returned `amounts[0]` and refunding the difference to `msg.sender`: [4](#0-3) 

Since callers such as `ExtrinsicIntents._cancelFromSource` forward the entire `msg.value` straight into `IDispatcher(hostAddr).dispatch{value: msg.value}(request)` with no local overpayment estimate/refund of its own: [5](#0-4) 

any imprecision between the amount of native token the caller estimated (via an off-chain quote/slippage buffer) and the exact amount the router actually needs is stranded inside `EvmHost` for that transaction. Unlike `placeOrder`'s local swap where the calling contract itself receives the router's refund and can forward it on, here `EvmHost` is the direct caller of the router, so the refund lands in `EvmHost`'s own balance rather than in the downstream caller/user's hands, and there is no path defined for a user to reclaim it.

### Impact Explanation
Any user (or any HyperApp built with `HyperApp`/`dispatchWithFeeToken`) dispatching a POST/GET request or funding a request with native token, and slightly overestimating the swap input (a normal and expected practice to account for AMM price movement/slippage between quoting and execution), permanently loses the difference — it is not returned to them, nor is it credited toward the request's fee metadata. This is a protocol-wide freezing-of-funds bug reachable from a single unprivileged, permissionless transaction (`dispatch`, `fundRequest`, or any app such as `IntentGatewayV2._cancelFromSource` that forwards its own `msg.value`).

### Likelihood Explanation
High. `swapETHForExactTokens` is documented Uniswap V2 behavior to always refund unspent ETH, and callers must generally send `msg.value` above the exact quoted amount to guard against slippage between quoting and inclusion — the exact excess this bug fails to account for. This occurs on virtually every native-fee dispatch unless the caller sends exactly the precise wei amount the AMM will consume at execution time, which is impractical to predict off-chain.

### Recommendation
Capture the `amounts` array returned by `swapETHForExactTokens` in all three functions (`dispatch(DispatchPost)`, `dispatch(DispatchGet)`, `fundRequest`) and refund `msg.value - amounts[0]` back to `_msgSender()` (or `payable(msg.sender)`), mirroring the pattern already implemented correctly in `IntentGatewayV2.placeOrder`.

### Proof of Concept
1. Caller quotes the fee-token cost for a `PostRequest` off-chain and adds a slippage buffer, then calls `EvmHost.dispatch{value: quotedAmount + buffer}(post)` with `post.fee` set to the exact feeToken amount needed.
2. Inside `dispatch`, `swapETHForExactTokens{value: quotedAmount + buffer}(post.fee, path, address(this), block.timestamp)` executes; the router spends only `amounts[0] <= quotedAmount + buffer` ETH and refunds `(quotedAmount + buffer) - amounts[0]` ETH back to `EvmHost` via a native transfer.
3. `dispatch` returns normally; the request is dispatched successfully.
4. The refunded excess ETH now sits in `EvmHost`'s balance with no `FeeMetadata` entry crediting it to the caller and no function permitting the caller to withdraw it — the funds are permanently stuck, exactly analogous to the ETH-stuck condition described in the referenced report.
