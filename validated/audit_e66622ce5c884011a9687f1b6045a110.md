### Title
Webhook `shop-domain`/`topic`/`webhook_id` headers are not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, while the shop, topic, and webhook id used by the application are taken from unauthenticated HTTP headers. This breaks the intended binding "HMAC-authenticated bytes == the shop/topic the app trusts," analogous to the Linea bug where a value used as an authoritative identity anchor (`stateRootHash`) was not actually covered by the equality check meant to protect it.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are read directly from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies that `hmac == HMAC(secret, to_signable_string)`, i.e., it authenticates the body bytes, not the headers: [3](#0-2) 

`Registry.process` accepts the request once `HmacValidator.validate(request)` passes, then dispatches the handler using `request.shop`, `request.topic`, and `request.webhook_id` taken straight from headers, with no re-validation that those headers correspond to the HMAC-checked body: [4](#0-3) 

Because the HMAC is computed with the app's single global `client_secret` (not a per-shop secret), any legitimate webhook delivery to any tenant of the app yields a `(raw_body, hmac)` pair that is valid for that body regardless of which shop it was meant for. A merchant/tenant of the app who receives genuine webhook deliveries can capture a valid `(body, hmac)` pair from their own store and replay it to the app's webhook endpoint with the `shop-domain` (and/or `topic`/`webhook-id`) header rewritten to point at a different, victim shop. `HmacValidator.validate` will still pass (it only checks the body/hmac pair), and `Registry.process` will hand the handler a `WebhookMetadata` object asserting the victim's `shop` even though Shopify never sent that data for the victim.

### Impact Explanation
This breaks the identity binding "bytes authenticated by HMAC == shop identity the app acts on," letting one tenant's traffic be reattributed to another tenant. Any host application logic that uses `WebhookMetadata#shop` to select the tenant record to update (a documented, expected usage pattern per the webhooks doc) can be tricked into writing/deleting/processing data under a shop identity the attacker does not control access to. This constitutes cross-tenant access, which is rated Critical in the given impact list.

### Likelihood Explanation
Requires only a legitimate but unprivileged relationship with the app (installed as a merchant on their own shop, receiving normal webhook traffic) — no leaked secrets, no TLS interception, and no access to `client_secret` are needed; the attacker just needs one genuine `(body, hmac)` pair they were entitled to receive and the ability to POST to the app's public webhook endpoint with a modified header. This is a realistic, low-effort replay achievable by any existing merchant/tenant of the app.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the HMAC-verified payload rather than trusting the raw header value for tenant attribution — e.g., verify the `shop-domain` header against the shop context established during webhook registration/subscription for that specific `webhook_id`, or include the shop domain in the signable string used for HMAC validation, so that switching the header without knowledge of the secret invalidates the HMAC.

### Proof of Concept
1. App tenant "attacker-shop.myshopify.com" installs the app and receives a legitimate webhook: `raw_body = B`, header `x-shopify-hmac-sha256 = HMAC(client_secret, B)`, header `x-shopify-shop-domain = attacker-shop.myshopify.com`.
2. Attacker replays the exact same `raw_body` and `hmac` header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds a request whose `hmac` and `to_signable_string` (`= B`) still match, so `Utils::HmacValidator.validate(request)` returns `true` (`lib/shopify_api/utils/hmac_validator.rb:12-31`).
4. `Registry.process(request)` proceeds and invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though Shopify never sent this payload for `victim-shop.myshopify.com`.

          received_signature = verifiable_query.hmac
