### Title
Emporium `runAction` fails to detect theft of tokens outside `circomData.erc20TokenAddresses` via stateless op - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` only snapshots `balancesBefore`/`balancesAfter` for tokens listed in `circomData.erc20TokenAddresses`. When `stack.signerAddress == address(0)`, `verifyWallet` returns immediately with no signature check [1](#0-0) , so any unprivileged caller running their own proof can freely craft `stack.ops[i]` with an arbitrary `endpoint`/`callData` (Case 2) that is not checked against `erc20TokenAddresses` at all.

### Finding Description
Equality claimed broken: `tokens leaving Emporium via op.callData == Σ(-deltaAmountChanges[i]) for i in erc20TokenAddresses`. This holds only for tokens present in `erc20TokenAddresses`; for any other token, the left side can be nonzero while the right side has no corresponding term.

Trace: `Hinkal.transact` → `_externalTransact` → `EmporiumUpgradeable.runAction(circomData, deltaAmountChanges)` [2](#0-1) . Inside `runAction`, `balancesBefore`/`balancesAfter` are computed strictly over `circomData.erc20TokenAddresses` [3](#0-2)  and [4](#0-3) . The loop over ops executes `op.endpoint.call{value: op.value}(op.callData)` in Case 2 when `stack.signerAddress == address(0)` [5](#0-4) , with the only restriction being a selector blacklist against `callHinkalWallet`/`doSendToRelay` — nothing restricts `op.endpoint` to a token address in `erc20TokenAddresses`.

`verifyWallet` skips all signature/EIP-712 verification when `stack.signerAddress == address(0)`, only marking `emporiumMessage` used [6](#0-5) . `HinkalHelper.performHinkalChecks` → `dimensionsCheck` and `checkOnchainCreation` only validate array lengths and onChainCreation invariants; they never inspect `externalActionData.externalActionMetadata` (which encodes `stack.ops`), so the circuit/on-chain checks impose no constraint linking `op.endpoint`/`op.callData` to `erc20TokenAddresses` [7](#0-6) . `calldataHash` only binds the metadata bytes to the proof for integrity — it doesn't validate the *content* is scoped to the declared tokens.

Attacker's exact call: attacker (any unprivileged user, using their own deposited UTXOs/proof) calls `Hinkal.transact` with `circomData.externalActionData.externalActionId` pointing to Emporium, `circomData.erc20TokenAddresses` = [tokenA] (their own token, excluding `tokenX`), and `externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)` and one op: `{endpoint: tokenX, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, tokenXAmount))}`. Since `runAction` is invoked as `msg.sender == Emporium` when calling `tokenX.transfer`, and Emporium holds a `tokenX` balance (e.g. stray dust), the transfer succeeds. `balancesBefore`/`balancesAfter` for `tokenA` are unaffected; `deltaAmountChanges` for `tokenX` doesn't exist since `tokenX` isn't in `erc20TokenAddresses`; no `balanceChange < 0` revert is triggered for `tokenX` because that token is never examined by the post-loop.

### Impact Explanation
Direct theft of protocol/other-users' `tokenX` funds sitting in the Emporium contract, with no debit recorded in any UTXO/nullifier accounting. This matches Critical severity ("direct theft of shielded or in-flight user funds"/protocol funds), and is repeatable for every stray token balance the Emporium accumulates (e.g., leftover dust from swaps, partial withdrawals, or accidental transfers).

### Likelihood Explanation
Requires: (1) Emporium holding a non-zero balance of some `tokenX` not declared by the attacker in `erc20TokenAddresses` — plausible from dust/rounding in swaps, `handleOut`'s `<=0` skip logic, or funds left behind by other flows; (2) the attacker only needs to generate a valid proof for their own UTXOs and craft the `externalActionMetadata`, both fully within an unprivileged attacker's capability per the rules. No signer signature is required since `signerAddress == address(0)` bypasses `verifyWallet`'s EIP-712 check entirely. Attacker cost is a single transaction; the only limiting factor is whether the target token balance exists on the Emporium at exploit time.

### Recommendation
In `EmporiumUpgradeable.runAction`, restrict stateless (`signerAddress == address(0)`) op targets so `op.endpoint` must be a member of `circomData.erc20TokenAddresses` (or otherwise snapshot balances for every address touched by `stack.ops`, not just the declared token list), and revert if any token balance change is detected on an address absent from `erc20TokenAddresses`.

### Proof of Concept
Foundry test:
1. Deploy `EmporiumUpgradeable`, `HinkalHelper`, `Hinkal`, and a mock `tokenX` ERC20; mint `tokenX` directly to the Emporium contract address to simulate stray balance.
2. Attacker deposits their own `tokenA` UTXO and generates a valid proof for a `transact` call where `circomData.erc20TokenAddresses = [tokenA]`.
3. Craft `externalActionData.externalActionMetadata` = `abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation({endpoint: tokenX, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, tokenXAmount))})], ...}))`.
4. Call `Hinkal.transact(...)`.
5. Assert: `tokenX.balanceOf(attacker)` increased by `tokenXAmount` (LHS of equality nonzero) while no entry in `circomData.amountChanges`/`deltaAmountChanges` or nullifier set corresponds to `tokenX` (RHS term absent) — proving the equality `tokens leaving Emporium == -Σ deltaAmountChanges` is violated for `tokenX`.
