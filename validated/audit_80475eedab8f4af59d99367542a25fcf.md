### Title
Missing Chainlink price feed round-completeness and price-bound checks in SimplexPaymaster - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster._getOraclePrice` consumes `AggregatorV3Interface.latestRoundData()` to price ERC-20 gas payments against a native asset, but only validates that the returned `answer` is positive and that `updatedAt` is not older than `maxOracleAge`. It never validates round completeness (`answeredInRound >= roundId`) or enforces sane price bounds, so any unprivileged UserOp sender relying on this paymaster's pricing can be under/overcharged whenever the underlying feed reports a stale round or is pinned at the aggregator's hard-coded min/max answer during extreme volatility.

### Finding Description
`_getOraclePrice` is the sole price-validation gate for both the native/USD and token/USD Chainlink feeds used to compute `tokenPrice` for every ERC-4337 gas payment routed through the paymaster: [1](#0-0) 

The function destructures `latestRoundData()` and discards `roundId` and `answeredInRound` entirely: [2](#0-1) 

This means:
- No check that `answeredInRound >= roundId`, so a round that was started but never completed (a known Chainlink edge case that leaves `updatedAt` looking "fresh" while the reported `answer` is actually carried over from a prior, potentially stale, round) is silently accepted.
- No upper/lower sanity bound (min/maxPrice circuit breaker) on `answer`. Chainlink aggregators clamp reported answers to a hard-coded `minAnswer`/`maxAnswer`; during a market dislocation the feed can report a flat, incorrect price at that bound without violating the staleness check (the round is still "fresh"), and the paymaster has no independent bound to catch it.

Both `_tokenPrice` (used in `_fetchDetails`, called on every UserOp validated by the paymaster) and `swapAndDeposit` (fee-recycling) depend directly on `_getOraclePrice`'s output without any secondary sanity check: [3](#0-2) [4](#0-3) 

### Impact Explanation
`_fetchDetails` is invoked for every paymaster-sponsored UserOp submitted by any unprivileged sender (the paymaster is a permissionless ERC-4337 gas-payment mechanism, gated only by token registration, not by sender identity): [5](#0-4) 

If either the token/USD or native/USD feed reports an incorrect-but-"fresh" price (stuck at an aggregator bound during a crash, or carried over from an incomplete round), `tokenPrice` is miscomputed and every UserOp priced against it either:
- Drains the paymaster's treasury by letting senders pay far less ERC-20 than the actual gas cost (a form of fund theft from the protocol-funded paymaster), or
- Overcharges legitimate senders.

This is a direct, concrete economic-drain vector reachable from a single unprivileged ERC-4337 UserOp, satisfying the Medium severity bar (protocol fund loss without requiring any privileged action).

### Likelihood Explanation
Exploitation requires an actual Chainlink feed anomaly (extreme price bound clamp or an incomplete round), which is an external dependency rather than something an attacker can trigger at will. However, once such a feed condition occurs (documented historical precedent, e.g. de-peg/crash events causing feeds to sit at `minAnswer`), the paymaster has zero additional defense — any sender can immediately exploit the mispriced gas cost with an ordinary UserOp, with no special privileges needed. Likelihood is therefore tied to real-world oracle market conditions rather than attacker-controlled preconditions.

### Recommendation
Extend `_getOraclePrice` to:
```solidity
(uint80 roundId, int256 answer, , uint256 updatedAt, uint80 answeredInRound) = oracle.latestRoundData();
if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
if (answeredInRound < roundId) revert StaleOraclePrice(address(oracle), updatedAt);
if (block.timestamp - updatedAt > maxOracleAge) revert StaleOraclePrice(address(oracle), updatedAt);
if (answer <= minPrice || answer >= maxPrice) revert InvalidOraclePrice(address(oracle), answer);
```
Add governance-configurable per-oracle `minPrice`/`maxPrice` bounds (mirroring the existing `Params`/`TokenConfig` governance pattern) so extreme aggregator-bound answers are rejected rather than silently used for pricing.

### Proof of Concept
1. Assume `usdcOracle` (token/USD Chainlink feed registered via `_registerToken`) experiences a market dislocation and its aggregator clamps `answer` to its hard-coded `minAnswer` (e.g., reports token price as $0.10 instead of the true ~$1.00), while `updatedAt` continues to tick within `maxOracleAge`.
2. `_getOraclePrice` passes both the `answer <= 0` check and the staleness check — the clamped, incorrect price is accepted: [2](#0-1) 
3. Any unprivileged UserOp sender calling into the paymaster with that token via `_fetchDetails`/`_tokenPrice` now gets `tokenPrice` computed off the wrong (10x too low) token/USD value, so `prefundAmount = _erc20Cost(...)` charges ~10x too little ERC-20 for the sponsored gas.
4. Repeating this across many UserOps drains the paymaster's EntryPoint deposit/treasury relative to actual gas expenditure, with no governance or privileged action required to trigger or benefit from the mispricing.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
