### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) headers are trusted as the tenant identity but are not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::HmacValidator` only verifies the raw request body against the HMAC signature. The `shop-domain`, `topic`, and `webhook-id` headers — which are the values the gem hands to application code as the *tenant identity* for the event — are not part of the signed material and can be freely altered by anyone able to produce one valid `(body, hmac)` pair for the shared `api_secret_key`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it with the `hmac` header: [2](#0-1) 
So the equality actually being checked is:
`HMAC(secret, raw_body) == received_hmac`

But `Webhooks::Registry.process` treats `request.shop`, `request.topic`, and `request.webhook_id` — read straight from unauthenticated headers — as trusted identity fields once that check passes, and hands them to the app's handler: [3](#0-2) 
`shop`, `topic`, and `webhook_id` are defined as simple header reads with no cryptographic binding to the body: [4](#0-3) 

This is precisely the bug class from the report: an "identity" field (`shop`) is *acted upon* (passed into `WebhookMetadata` and handed to the handler as the tenant for the event) but is *not covered* by the same authenticator (`HMAC`) that is used to establish trust in the request. The equality the code actually verifies (`hmac` over `raw_body`) differs from the equality the handler implicitly relies on (`shop header == shop that generated this body`).

### Impact Explanation
Any unprivileged internet user who can install the target app on a shop they control (a completely normal, unprivileged action for any public/testable app) will receive one or more legitimate webhook deliveries with a valid `(raw_body, x-shopify-hmac-sha256)` pair computed with the app's real `api_secret_key`. Because the signature covers only the body, the attacker can replay that exact `raw_body`/`hmac` pair while substituting an arbitrary `x-shopify-shop-domain` (and/or `x-shopify-topic`) header pointing at a victim shop. `HmacValidator.validate` still returns `true`, and `Registry.process` will dispatch to the registered handler with `shop` set to the victim's domain. Any host application that uses the `shop` value from `WebhookMetadata` to key session/data lookups or to perform shop-scoped actions (e.g. `app/uninstalled` cleanup, GDPR `customers/redact`/`shop/redact` handling, subscription/billing state changes) will now perform those actions against a *different tenant* than the one that actually sent/authorized the event — a cross-tenant integrity violation achievable without ever compromising the victim shop or obtaining its credentials.

### Likelihood Explanation
Likelihood is meaningful but bounded: the attacker needs at least one authentic `(body, hmac)` pair signed by the app's actual `api_secret_key`, which they can trivially obtain by installing the app themselves and capturing any webhook delivery (e.g. `app/uninstalled`). No access to the `api_secret_key`, an access token, or any victim-shop secret is required — only normal use of the app as an unprivileged merchant/installer. The gem provides no header-body binding to prevent this, so the vulnerability is inherent to `HmacValidator`/`Webhooks::Request` rather than a misuse of a documented safeguard.

### Recommendation
Bind the identity headers into the signed material, or otherwise cryptographically tie `shop`, `topic`, and `webhook_id` to the verified payload before exposing them to handlers — e.g., include the relevant headers in `to_signable_string`, or require/perform a follow-up authenticated lookup (shop ↔ webhook delivery ID) before trusting `shop` for any tenant-scoped side effect. At minimum, the library should document prominently (and ideally enforce) that `shop`/`topic`/`webhook_id` are unauthenticated header values and must not be used for authorization decisions without independent verification.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; capture a delivered webhook, e.g. `app/uninstalled`, with body `B` and header `x-shopify-hmac-sha256: H` (valid for `api_secret_key`).
2. Replay to the app's webhook endpoint:
```
POST /webhooks
x-shopify-topic: app/uninstalled
x-shopify-hmac-sha256: H
x-shopify-shop-domain: victim-shop.myshopify.com
x-shopify-webhook-id: <any>

B
```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(secret, B) == H`: [5](#0-4) 
4. The handler registered for `app/uninstalled` is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, even though the victim shop never sent this request, letting the host application perform shop-scoped teardown/side effects for a tenant it does not control.
