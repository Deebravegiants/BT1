## Title
Webhook cross-tenant shop spoofing via HMAC that only covers the request body, not the `shop` header - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then hands the caller-supplied `shop` header value — which is **not** part of the signed bytes — to the application's webhook handler as the trusted tenant identity. Any actor who can install the target app on their own store (a normal, unprivileged, self-service action) can capture one of their own legitimately-signed webhook deliveries and replay the identical `body` + `hmac` pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header, causing the handler to process the payload as if it belonged to a different (victim) shop.

### Finding Description
`Registry.process` performs exactly one authentication check before invoking the registered handler:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [1](#0-0) 

`request.shop` is read straight from the `X-Shopify-Shop-Domain` header, with no cryptographic tie to the signature:

```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
...
def to_signable_string
  @raw_body
end
``` [2](#0-1) 

`HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` (i.e., the raw body):

```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [3](#0-2) 

**Identity binding broken:** the equality the check is supposed to guarantee is
`shop_that_owns_the_signed_body == shop_passed_to_the_handler`. In reality the code only proves `HMAC(body, api_secret_key) == received_hmac`; the `shop` header is never part of the input to that HMAC. Since `api_secret_key` is a single shared secret for *all* shops that have the app installed, `HMAC(body, api_secret_key)` is identical no matter which shop the event is "for." Consequently, capturing any one genuinely-signed `(body, hmac)` pair (trivially obtainable by installing the app on an attacker-controlled store) is sufficient to produce a request that will pass `Registry.process` validation for **any** `shop` value the attacker chooses to put in the header.

### Impact Explanation
An app author using `Registry.process`/`WebhookMetadata#shop` to decide which tenant's data to read, mutate, or delete would act on attacker-chosen tenant identity while believing it was cryptographically authenticated (the library raises `InvalidWebhookError` only when the HMAC check fails, implying "authenticated" once it passes). This enables cross-tenant access/manipulation — an app installer for Shop A can trigger the handler as if the event came from victim Shop B, without ever compromising Shop B's credentials or the app's `client_secret`. This matches the Critical/High "cross-tenant access" impact category.

### Likelihood Explanation
Requires only self-service installation of the target app on an attacker-owned store (no special privileges, no leaked secrets, no TLS interception) and a single captured webhook delivery to that store — a low bar for a legitimate but "unprivileged" installer, and consistent with the report's bug class of "a field acted on but not covered by the [integrity check]."

### Recommendation
Do not treat the header-derived `shop` as authenticated purely because the body HMAC validated. `Registry.process`/`WebhookMetadata` should require callers to cross-check `request.shop` against a shop that is independently known to have a valid, still-installed session/access token before dispatching to handlers, and the docs/handler contract should explicitly warn that `shop` is unauthenticated header data. Longer term, incorporate the `shop` (and other identity-relevant headers) into the value that is verified, or otherwise document and enforce that consumers must correlate `shop` with their own session store prior to trusting it.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, which is a normal, unprivileged action.
2. Shopify delivers a legitimate webhook to the app's endpoint, e.g.:
   ```
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid-hmac-of-body>
   X-Shopify-Shop-Domain: attacker.myshopify.com
   Body: {"id": 1, ...}
   ```
3. Attacker replays this exact `Body` and `X-Shopify-Hmac-Sha256` to the same endpoint, but sets:
   ```
   X-Shopify-Shop-Domain: victim.myshopify.com
   ```
4. `HmacValidator.validate` recomputes `HMAC(body, api_secret_key)`, which matches the replayed HMAC (it never included the shop domain), so `Registry.process` proceeds and calls the app's handler with `shop: "victim.myshopify.com"`, `body` from the attacker's own store — causing the app to act on victim data/context under attacker-supplied inputs.
