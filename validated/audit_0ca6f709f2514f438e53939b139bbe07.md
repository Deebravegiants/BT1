### Title
Donating launched tokens directly to a `Pair` breaks the `tokenBalance() < tokenReserve` invariant and permanently reverts the curve's overflow-capped closing buy in `Router._computeBuy` - (File: `packages/contracts/src/Router.sol`)

### Summary
The external report's bug class is an unhandled edge case (`get_block_by_hash` returning `Ok(None)`) that hit an `unreachable!()` panic instead of a graceful error path. Alt.fun's `Router._computeBuy` has the same shape: it contains a defensive `revert OverflowCapDegenerate()` guard for a branch its own test suite documents as "unreachable" under the assumed invariant `pair.tokenBalance() < tokenReserve` [1](#0-0) . That invariant is not actually enforced on-chain — it is only true as long as no one transfers launched tokens directly into the `Pair`. Any unprivileged holder of the launched `Token` (e.g., an earlier curve buyer) can break it with a plain ERC20 `transfer`, turning the "unreachable" branch into a reachable revert (or a raw arithmetic-underflow panic) that bricks the curve's closing buy.

### Finding Description
`Router._computeBuy` caps `tokensOut` at the pair's live token balance to implement the overflow-buy protection, then back-calculates `amountInUsed` from a "capped reserve": [2](#0-1) 

`reserveToken` is the *stored* virtual reserve (`_pool.tokenReserve`), which starts at `totalSupply` (1B) and is only ever mutated by `Pair.swap` [3](#0-2) . `realBalance` is `pair.tokenBalance()`, a live `balanceOf` read [4](#0-3) , which starts at `curveSupply` (75% of total, i.e. 750M) and only decreases via `Router.buy`'s `transferToken` [5](#0-4) .

Nothing stops an unprivileged holder of the launched `Token` from calling `Token.transfer(pairAddress, amount)` directly — a plain ERC20 transfer explicitly listed as in-scope. This inflates `pair.tokenBalance()` above the stored `tokenReserve` as the curve sells down toward exhaustion, breaking the property the project's own regression test asserts as a "hard invariant" and documents as making the degenerate branch "unreachable": [6](#0-5) 

Once `realBalance >= reserveToken` near curve exhaustion, the overflow-cap branch in `_computeBuy` computes `cappedReserveToken = reserveToken - tokensOut` where `tokensOut` has just been set to the inflated `realBalance`. This either underflows (Solidity `Panic(0x11)`) or, in the exact-equal case, deliberately reverts via `revert OverflowCapDegenerate()` [7](#0-6) . Every subsequent attempt to execute the curve's final, supply-exhausting buy through `Bonding.buy` → `Router.buy` hits the same reverting arithmetic, because the donation is permanent and can only grow. This is the same "invariant assumed to always hold, guarded only by a panic/revert instead of a graceful path" bug class the kona-node fix addressed.

### Impact Explanation
The supply-side graduation trigger (`IPair.tokenBalance() == 0`) can never fire for the affected token, because the buy that would drain the last real tokens on the curve is the exact buy that hits the reverting overflow-cap branch. Unless the USD trigger independently fires (which depends on LT exchange-rate conditions outside the attacker's control), the token is permanently stuck in `Lifecycle.Curve`, unable to sell out and graduate via the supply path, and the last chunk of curve liquidity becomes unbuyable — a permanent denial-of-service on trading/graduation for that token, reachable by any address that has bought tokens on the curve (i.e., any trader) with a single follow-up ERC20 transfer.

### Likelihood Explanation
High reachability: no privileged role is needed. Any address that has ever bought launched tokens on the curve (a normal, unprivileged action via `Zap.buy`) already holds the ERC20 `Token` needed to execute the griefing transfer, and `Token.transfer` to the `Pair` address is unrestricted. The only requirement is timing the donation so the inflated balance is still present when the curve nears exhaustion — well within a single attacker's control since the donation is irrevocable and standing.

### Recommendation
Do not derive the overflow cap from the raw live `tokenBalance()`. Either (a) track sold/available supply purely from the router's own accounting (`reserveToken` deltas) instead of trusting `balanceOf`, or (b) explicitly subtract/quarantine any balance above what the curve's own bookkeeping expects (mirroring the donation-immunity treatment already applied to `_prepareGraduationLiquidity`'s `ltFromPair`/`unsoldBurned` logic) before computing `cappedReserveToken`, so a donation can only ever be burned/ignored, never able to push the cap computation into underflow or the `OverflowCapDegenerate` revert.

### Proof of Concept
1. Attacker (any address) buys tokens on the curve via `Zap.buy`, receiving real `Token` balance.
2. As the curve approaches exhaustion (real `tokenBalance()` close to 0, `reserveToken` close to its floor), attacker calls `Token.transfer(pairAddress, X)` directly, inflating `pair.tokenBalance()` above the current stored `reserveToken`.
3. Any subsequent buyer submits a buy sized to trigger the overflow cap (`tokensOut > realBalance` branch in `Router._computeBuy`).
4. `tokensOut` is capped to the inflated `realBalance` (now ≥ `reserveToken`), so `cappedReserveToken = reserveToken - tokensOut` underflows or equals zero, and the call reverts with `Panic(0x11)` or `OverflowCapDegenerate()` [7](#0-6) .
5. Every future closing buy on that curve reverts the same way; the token can never exhaust its real supply to satisfy the supply-side graduation trigger, freezing the remaining curve liquidity for that token.

```text
    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
```

```text
        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.tokenReserve = newTokenReserve;
        _pool.assetReserve = newAssetReserve;
        emit Swap(tokenIn, tokenOut, assetIn, assetOut);
        return true;
    }
```
