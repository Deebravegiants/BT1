### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing tenant-spoofing when a valid signed webhook body is replayed with a different shop header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` for HMAC verification, but its `to_signable_string` returns only the raw request body, never the `shop-domain` header. `Registry.process` validates the HMAC against the body and then trusts `request.shop` (parsed from the unauthenticated header) to build the `WebhookMetadata` tenant identity passed to the host app's handler. The `shop` field is *acted on* (used as the tenant key) but not *covered by* the HMAC, exactly matching the report's bug class of a field used for a security decision that isn't bound by the same signature that authenticates the message.

### Finding Description
- `Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 
- `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no verification: [2](#0-1) 
- `HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the body) against the HMAC secret — the header-derived `shop` is never part of the signed payload: [3](#0-2) 
- `Registry.process` validates the HMAC over the body, then immediately trusts `request.shop` as the tenant identity handed to the app's `WebhookHandler`: [4](#0-3) [5](#0-4) 

The equality that should hold is: `shop authenticated by HMAC == shop used as tenant key in WebhookMetadata`. In this code, the HMAC only authenticates the body bytes; it says nothing about which shop the request claims to be from. Any request carrying a body/HMAC pair that Shopify legitimately signed for tenant A can be replayed with the `shop-domain` header rewritten to tenant B's domain, and `Registry.process` will still accept it (the HMAC check passes because the body is unchanged) and dispatch it to the handler labeled as belonging to tenant B.

### Impact Explanation
This breaks the tenant binding at the point where the gem hands data to the host application: the library asserts (via `WebhookMetadata.shop`) that a signed message originated from a specific shop, but that shop value carries no cryptographic guarantee. A host app that uses `data.shop` to look up the session/access token for the shop or to scope data writes (the intended, documented usage of this field) can be made to attribute genuinely-signed webhook content to the wrong tenant, or process attacker-influenced tenant context under a valid signature. This matches "cross-tenant access" (Critical) per the accepted impact categories, since the credential/tenant boundary (which shop a signed webhook is attributed to) is not actually enforced by the signature that is supposed to authenticate it.

### Likelihood Explanation
The prerequisite is only that the attacker can obtain one genuinely Shopify-signed webhook body for any shop under their control (trivial — anyone can install the app on their own development/test store and trigger a webhook, e.g. `orders/create`), then replay that body with the same HMAC but a modified `shop-domain` header value pointed at the victim shop. No access token, `api_secret_key`, or privileged access to Shopify is required — this only exploits the fact that `to_signable_string` excludes the header. Likelihood is high wherever a host app derives tenant identity from `WebhookMetadata#shop` without independently re-verifying shop membership.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed material, or otherwise cryptographically bind the `shop-domain` header to the signed payload before trusting it in `Registry.process`/`WebhookMetadata`. At minimum, document that `WebhookMetadata#shop` is not authenticated by the HMAC and must be cross-checked by the host application against known installed shops before being used for tenant-scoped lookups.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) so Shopify sends a legitimately HMAC-signed request with body `B` and header `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the exact same body `B` and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`= @raw_body = B`) only — validation succeeds because the body was untouched: [6](#0-5) 
4. `WebhookMetadata.new(... shop: request.shop ...)` is built with `shop = "victim.myshopify.com"` and passed to the app handler as if the (validly signed) event genuinely originated from the victim shop.
