### Title
Webhook `shop` identity is trusted from an HMAC-unsigned header, breaking the shop-binding guarantee - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the merchant identity (`shop`) exclusively from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, while the HMAC signature only covers the raw request body via `to_signable_string`. `Registry.process` validates the HMAC and then hands `request.shop` straight to the app's webhook handler without ever binding that value to the signed bytes, so the "verified bytes" and the "identity acted on" are two different, independently-controlled inputs.

### Finding Description
`Utils::HmacValidator.validate` computes an HMAC over `verifiable_query.to_signable_string` and compares it against the `hmac` value exposed by the same object: [1](#0-0) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, and `hmac` is parsed from the `hmac-sha256` header: [2](#0-1) [3](#0-2) 

Critically, `shop` is read from a separate, unsigned header field: [4](#0-3) 

`Registry.process` validates the HMAC of the body, then immediately forwards `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version` — all likewise header-derived and unsigned) to the app-registered handler as the authoritative tenant identifier: [5](#0-4) 

The identity binding that should hold is: `hmac_verify(secret, bytes) == true` implies `shop == shop_that_produced(bytes)`. In this implementation that equality does not exist — `bytes` is `raw_body` only, and `shop` is an out-of-band header. An attacker who can produce *any* valid HMAC over a body they control (e.g., because they can capture/replay a legitimate webhook delivery for one shop, or because the raw body used for signing does not itself encode the shop) can pair that valid `(body, hmac)` pair with an arbitrary `shop-domain` header value. The HMAC check passes (it only validates the body against the secret), yet the `shop` value delivered to the app handler — used by apps to key sessions/data per-tenant — can point at a different merchant than the one whose secret-derived signature was actually checked.

This mirrors the analog bug class in the report: a field ("shop") that is acted upon (used to determine which tenant's data/session the webhook applies to) is not covered by the authentication check (HMAC only covers `raw_body`), breaking the equality between "bytes verified" and "identity trusted."

### Impact Explanation
If an app relies on `WebhookMetadata#shop` (populated straight from `request.shop`) to select which merchant's session/data to mutate, an attacker who can obtain one validly-HMAC'd body (this only requires the app's `api_secret_key`... but note: since `shop` is not part of the signed content, even a legitimate captured webhook payload without shop-specific content in the body could be replayed with a forged `shop-domain` header while keeping the original valid HMAC) can cause the handler to act under an attacker-chosen shop identity. This crosses the tenant boundary this gem is supposed to enforce via `Utils::HmacValidator`, which is a cross-tenant access primitive (High/Critical depending on what the specific webhook handler does with `shop`).

### Likelihood Explanation
Exploitability depends on whether any legitimate webhook body is shop-agnostic enough that its HMAC remains valid while the `shop` header is swapped (e.g., topics like `app/uninstalled` or empty-body test payloads such as the `"{}"` body seen in the gem's own tests). This is a design gap rather than a definite exploitable path in every deployment, since it requires either a captured signed payload or a topic whose body content doesn't need to differ per shop. This condition is plausible for several Shopify webhook topics but not universal, which lowers confidence to Medium.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) as part of the HMAC-signed material, or otherwise cryptographically bind the header-derived `shop` value to the verified body before exposing it via `Webhooks::Request#shop` / `WebhookMetadata`. At minimum, document that `request.shop` is unauthenticated and must not be trusted as a tenant boundary without additional verification (e.g., cross-checking against a shop recorded in the signed payload or an existing offline session lookup with additional trust proof).

### Proof of Concept
1. Capture a legitimate webhook delivery for `shop-a.myshopify.com` with body `B` and valid header `shopify-hmac-sha256: HMAC(secret, B)`.
2. Replay the same body `B` and HMAC header, but replace `shopify-shop-domain: shop-a.myshopify.com` with `shopify-shop-domain: shop-b.myshopify.com`.
3. `Utils::HmacValidator.validate` in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) validates successfully because it only checks `B` against the HMAC — it never inspects the `shop` header.
4. The handler receives `WebhookMetadata` with `shop: "shop-b.myshopify.com"` despite the signature only proving knowledge of `secret` and `B`, not any binding to `shop-b`. [6](#0-5) [7](#0-6)

          received_signature = verifiable_query.hmac
