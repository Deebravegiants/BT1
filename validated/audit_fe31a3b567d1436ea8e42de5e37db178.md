### Title
Webhook shop attribution is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` attributes an incoming webhook to a shop using the `shopify-shop-domain` / `x-shopify-shop-domain` header, but the HMAC signature that authenticates the webhook is computed over the raw body only. The shop identity is therefore never cryptographically bound to the signature that "proves" the webhook is genuine, exactly the class of bug described in the report: a field that is acted on (shop attribution) is not covered by the value that is verified (the HMAC).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from an unauthenticated header and is never mixed into the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` only checks that `HMAC(secret, request.to_signable_string) == request.hmac`, i.e. it verifies the body, not the shop header: [3](#0-2) 

`Webhooks::Registry.process` calls this validator and then forwards `request.shop` — the unverified header value — directly to the handler as the tenant identifier for the payload: [4](#0-3) 

Because `shop` is never part of `to_signable_string`, any request whose body+HMAC pair is valid for the app's secret (i.e., any body that was ever legitimately signed by Shopify for *some* shop using this app) will still pass `HmacValidator.validate` regardless of which `shop-domain` header value accompanies it. This breaks the intended identity binding:

- Expected invariant: `shop-that-produced-valid-signature(raw_body, hmac) == shop-attributed-to-event`
- Actual behavior: `hmac` only proves the body was signed by *some* legitimate call to this app's webhook secret; `shop` is supplied out-of-band and unauthenticated, so `shop-attributed-to-event` can be set independently by whoever sends the HTTP request to the app's webhook endpoint.

### Impact Explanation
An attacker who has legitimate access to a low-privilege Shopify store (e.g., a free trial store where the target app is installed — no `client_secret`, access token, or social engineering required) will receive real webhooks from Shopify for their own store, correctly HMAC-signed with the app's shared secret. Because the shop header is not part of the signed content, the attacker can capture one such `(raw_body, hmac)` pair and replay it directly to the app's public webhook endpoint with an arbitrary `shopify-shop-domain` header value pointing at a victim shop. `Registry.process` will pass HMAC validation and hand the handler a `WebhookMetadata` object claiming the (attacker-controlled) body belongs to the victim shop. Depending on how the host app's handler uses `shop` (e.g., to update per-tenant data, deactivate/reinstall records, or trigger uninstall/GDPR cleanup logic keyed by shop), this enables cross-tenant data confusion or corruption using only the attacker's own signed traffic — no privileged credentials needed. This matches the "cross-tenant access" criterion for High/Critical impact.

### Likelihood Explanation
Likelihood is high: the webhook endpoint is by design a public HTTP endpoint that accepts arbitrary internet requests, obtaining a validly-signed `(body, hmac)` pair only requires installing the app on any store (including a free development store), and forging the shop header is a trivial HTTP header change with no cryptography to break.

### Recommendation
Include the shop identity (and ideally topic/webhook id) inside the HMAC-covered payload, or otherwise cryptographically bind the shop attribution to the signed body — e.g., verify the header-provided shop against a shop the app actually has an active session/webhook registration for, or require the signature to cover a canonical string that includes the shop domain, similar to how `Oauth::AuthQuery#to_signable_string` includes `shop` in the signed data: [5](#0-4) 

### Proof of Concept
1. Install the target app on an attacker-controlled Shopify development store (no privileges beyond a normal merchant needed).
2. Trigger any webhook event on the attacker's store (e.g. `orders/create`) and capture the raw POST body and the `x-shopify-hmac-sha256` header value sent by Shopify — both are valid because Shopify signs with the app's real `api_secret_key`.
3. Replay this exact `(raw_body, hmac)` pair to the app's public webhook endpoint, but change the `x-shopify-shop-domain` header to the victim shop's domain.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb` lines 12-31) succeeds because it only checks `raw_body` against the HMAC.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb` lines 188-200) invokes the handler with `shop: request.shop` set to the victim's domain, even though the body content originated from the attacker's own store.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
