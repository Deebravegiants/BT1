### Title
Push-based token delivery in `WrappedHyperFungibleToken` permanently locks underlying tokens when the recipient transfer reverts - ([File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol])

### Summary
`WrappedHyperFungibleToken` delivers cross-chain transfers and timeout refunds by directly pushing the underlying ERC20 (e.g. a USDC-like blacklistable token, or WETH) to the beneficiary/refundee inside `onAccept` and `onPostRequestTimeout`. There is no pull-based withdrawal/escrow fallback. If the recipient can never accept the token (blacklisted address, or a contract that always reverts on `receive`/token transfer), the underlying tokens become permanently stuck in the contract with no recovery path, analogous to the Moloch "emergency processing" bug where a blocked push-transfer can permanently freeze funds.

### Finding Description
`onAccept` mints/unlocks and pushes tokens directly to the destination beneficiary: [1](#0-0) 

`onPostRequestTimeout` similarly pushes the refund directly to the original sender: [2](#0-1) 

Both paths call `IERC20(_underlying).safeTransfer(...)` (or attempt a native ETH push with a WETH fallback) directly to a caller-controlled address, with no pull/claim mechanism if that transfer reverts.

At the host level, `EvmHost.dispatchIncoming` wraps the call to `onAccept` in a low-level `.call`, and on failure deletes the receipt "so that it can be retried": [3](#0-2) 

The same retry-on-failure pattern applies to `dispatchTimeOut` for POST requests: [4](#0-3) 

This isolation prevents one blocked message from blocking *other* messages in the same batch (unlike the referenced Moloch bug, where the whole proposal queue got stuck). However, for the *specific* message whose transfer target is permanently blocked (e.g. blacklisted on the underlying token, or a contract that always reverts), retries will never succeed: `onAccept`/`onPostRequestTimeout` will keep reverting on the internal `safeTransfer`, so the receipt/commitment is deleted and re-tried indefinitely but can never be marked delivered. The escrowed/locked underlying tokens for that specific transfer (and the burned wrapped-side balance, since burn already occurred on the source chain) remain permanently stranded in the `WrappedHyperFungibleToken` contract, with no pull-style claim function to let the beneficiary/refundee recover funds through an alternate address.

### Impact Explanation
This is a permanent freezing-of-funds condition for the affected transfer: the underlying ERC20 held by `WrappedHyperFungibleToken` for that specific commitment can never be delivered or refunded once the recipient address is untransferable (blacklist, revert-on-receive contract, etc.), and there is no alternate withdrawal path. Because the tokens were already burned/escrowed on the source side, the user's funds are lost/inaccessible.

### Likelihood Explanation
Likelihood is moderate: it requires either (a) an underlying token with blacklist functionality (e.g. USDC/USDT-style tokens), which is explicitly the assumed wrapped-token use case for `WrappedHyperFungibleToken`, or (b) a smart-contract beneficiary/refundee that unconditionally reverts on token receipt (self-inflicted or griefing via a malicious `to`/`from` address chosen by an unprivileged sender in `send()`). Both scenarios are reachable by a normal unprivileged user submitting a bridge transfer.

### Recommendation
Implement a pull-based recovery pattern for both `onAccept` and `onPostRequestTimeout`: if the direct `safeTransfer` (or native push) to the beneficiary/refundee fails, credit an internal claimable balance for that address instead of reverting the whole call, and expose a separate `claim()`/`withdraw()` function so the recipient (or a designated alternate address) can retrieve the funds once able to. This mirrors the standard mitigation recommended for the referenced Moloch bug class — converting push transfers into pull withdrawals to avoid permanent fund freezing from a single blocked recipient.

### Proof of Concept
1. Owner configures `WrappedHyperFungibleToken` on chain B to wrap a blacklistable ERC20 (e.g. USDC) as `_underlying`.
2. User on chain A calls `send()` with `to` set to an address that is later blacklisted on the chain B underlying token (or is already blacklisted at time of delivery), locking/escrowing tokens on chain A side and dispatching the POST request.
3. Relayer delivers the request; `EvmHost.dispatchIncoming` calls `onAccept`, which attempts `IERC20(_underlying).safeTransfer(beneficiary, amount)` — this reverts because `beneficiary` is blacklisted.
4. `dispatchIncoming` catches the failure, deletes the request receipt, allowing indefinite retries — but every retry hits the same revert since the blacklist is permanent.
5. If the request times out and `dispatchTimeOut`/`onPostRequestTimeout` is invoked to refund the original sender, and that sender address is also unable to receive the token (or is a reverting contract), the same permanent revert loop occurs on the refund path.
6. Underlying tokens transferred to `WrappedHyperFungibleToken` for this transfer are now permanently unrecoverable — no claim/pull function exists to redirect funds to a different, valid address.

    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }

    function dispatchTimeOut(
        PostRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onPostRequestTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit PostRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
