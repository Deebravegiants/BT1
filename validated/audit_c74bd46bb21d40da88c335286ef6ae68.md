### Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) header is trusted for tenant identity without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then passes the `shop` field taken from an unauthenticated HTTP header directly to the app's webhook handler as the tenant identifier. The HMAC signature never covers the `shop-domain` header, so the binding `authenticated_body == identified_shop` does not hold.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes and compares the HMAC exclusively against that signable string (i.e. the raw body): [2](#0-1) 

Meanwhile, `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header with no cryptographic binding to the signed body: [3](#0-2) 

`Registry.process` validates only the HMAC of the body, then immediately trusts `request.shop` (along with `topic`, `webhook_id`, `api_version` - also unauthenticated headers) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

`WebhookMetadata.shop` is the sole tenant identifier surfaced to the consuming application's `WebhookHandler#handle`: [5](#0-4) 

This is precisely the "field acted on but not covered by the HMAC" identity-binding gap: the equality the library implicitly claims to guarantee is `hmac_valid(body) => shop_header_is_authentic`, but the actual guarantee is only `hmac_valid(body) => body_came_from_holder_of_secret`. The `shop` header is orthogonal to the signed content and can be swapped freely.

### Impact Explanation
Any party who can produce a body/HMAC pair that validates for a given app (e.g., an app-installing merchant capturing their own genuine webhook deliveries, since HMAC only requires knowledge of `api_secret_key` which Shopify itself uses when signing legitimate traffic to the app, not something the caller must additionally possess to exploit this particular gap) can replay that same signed body while substituting the `shop-domain` header for a different, victim shop. Because `Registry.process` and `WebhookHandler#handle` derive the tenant exclusively from this unauthenticated header, the host application ends up attributing webhook data/actions to the wrong shop - a cross-tenant confusion at the library layer. Any host app that uses `WebhookMetadata#shop` to look up per-tenant sessions, API credentials, or records (a documented, expected usage pattern of this field) inherits a tenant-boundary break directly caused by this gem's own `Registry#process`/`Request#shop` implementation, not by host misuse.

### Likelihood Explanation
Exploitation requires the attacker to have at least one legitimately signed webhook payload for the target app (obtainable, for topics with static/predictable bodies such as `app/uninstalled` with an empty JSON body `{}`, from the attacker's own installation of the same app) and the ability to POST to the app's public webhook endpoint with a forged `shop-domain` header. No possession of `api_secret_key` or any privileged credential is required by the attacker themselves - only a routine merchant relationship with the target app, which is an "unprivileged internet user" position relative to other tenants of that app.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) values in the HMAC-signed content, or otherwise cryptographically bind them to the body before trusting them as the tenant identifier. At minimum, `Utils::VerifiableQuery#to_signable_string` for webhooks should incorporate the shop-domain header (and other trust-sensitive headers) into the signed string used by `HmacValidator.validate`, so that `Registry.process` cannot be fed a validly-signed body paired with an attacker-controlled shop.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Attacker triggers/observes a genuine webhook delivery for a topic with a static body, e.g. `app/uninstalled` with raw body `{}`, capturing the valid `x-shopify-hmac-sha256` value Shopify computed with the app's `api_secret_key`.
3. Attacker replays a POST to the app's webhook endpoint with the same raw body `{}` and the same valid HMAC header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13-22`) succeeds because it only checks the body's HMAC.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) builds `WebhookMetadata.new(... shop: request.shop ...)` using the forged `victim-shop.myshopify.com` value and invokes the host app's handler, which now processes an event under the wrong shop's identity.
