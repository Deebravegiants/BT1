### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` are not covered by the HMAC signature, allowing cross-tenant impersonation - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authenticated once `Utils::HmacValidator.validate(request)` passes, and then forwards `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` to the host application's handler as trusted, verified metadata. In reality, the HMAC only covers the raw request body — the identity fields that the handler uses to decide *which tenant* the payload belongs to are read straight from unauthenticated HTTP headers.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are pulled directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`, or their `x-shopify-` variants) with no cryptographic binding to those header values: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` computes the signature exclusively from `verifiable_query.to_signable_string`, so it authenticates the body bytes only, never the header-derived fields: [4](#0-3) 

`Registry.process` uses this single HMAC check as the sole authentication gate, then builds `WebhookMetadata` — including the unauthenticated `shop`, `topic`, `webhook_id`, `api_version` — and passes it to the app's `WebhookHandler#handle`: [5](#0-4) [6](#0-5) 

The broken identity binding, stated as an equality that should hold but doesn't:
`shop header value used to attribute the payload to a merchant` ≠ `shop value actually covered by the HMAC signature (none — only the body is signed)`.

Concretely: an attacker who legitimately controls any Shopify shop (e.g., a free development store) will receive real webhooks from Shopify for their own shop, each with a valid `hmac-sha256` computed over the body using the app's `client_secret`. Because the signature never covers the `shopify-shop-domain`, `shopify-topic`, or `shopify-webhook-id` headers, the attacker can replay that exact body+HMAC pair to the app's webhook endpoint while substituting a victim shop's domain (or a different topic/webhook id) in the headers. `Utils::HmacValidator.validate` still returns `true` because it only recomputes the signature over `@raw_body`, and `Registry.process` hands the handler a `WebhookMetadata` claiming the (forged) victim `shop`, causing the host application to attribute attacker-chosen body content to another merchant's tenant.

### Impact Explanation
This breaks the tenant boundary the gem is documented to enforce via `Registry.process`/`HmacValidator.validate`: an app author reasonably assumes that a webhook passing `HmacValidator.validate` is fully authenticated, including which shop it originated from. Since `shop` (and `topic`/`webhook_id`) are unauthenticated, an attacker can inject falsified webhook payloads attributed to any shop domain of their choosing, enabling cross-tenant data corruption/injection (e.g., triggering `orders/update`-style handlers with attacker-controlled body content stamped with a victim's shop domain). This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires only an attacker who can obtain at least one genuine signed webhook (trivial: create a free/dev store and subscribe to any webhook topic for their own shop) and the ability to POST arbitrary headers to the app's public webhook endpoint — no privileged credentials, access tokens, or `client_secret` knowledge needed. This is a design-level gap in the gem's own `Request`/`Registry` classes, not a misuse of a documented API by the host app.

### Recommendation
Extend `to_signable_string` (or add a separate verification step in `Registry.process`) to bind the `shop`, `topic`, and `webhook_id` header values into the data verified by the HMAC — e.g., reject the webhook if these headers are altered independently of the signed body, or require the host app to additionally verify `shop` against its own known-tenant list before trusting `WebhookMetadata#shop`. At minimum, document prominently that `shop`/`topic`/`webhook_id` in `WebhookMetadata` are NOT covered by the HMAC and must not be used as the sole tenant-attribution key without additional server-side verification (e.g., cross-checking against the shop associated with a stored, previously-authenticated session).

### Proof of Concept
```ruby
require "shopify_api"
require "openssl"
require "base64"

ShopifyAPI::Context.setup(
  api_key: "key", api_secret_key: "secret", host_name: "app.example.com",
  api_version: "2024-01", is_embedded: true, is_private: false, scope: []
)

# Attacker's own dev shop receives a genuine webhook for topic "orders/create"
raw_body = '{"id": 1, "note": "attacker-controlled content"}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# Attacker replays the SAME body+hmac but swaps the shop-domain header to the victim's shop
forged_headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => valid_hmac,          # still valid: only body is signed
  "shopify-shop-domain" => "victim-shop.myshopify.com", # forged, unauthenticated
  "shopify-webhook-id" => "forged-id",
  "shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Passes validation despite the shop header being forged:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process will hand this to the handler as if it truly came from victim-shop.myshopify.com
ShopifyAPI::Webhooks::Registry.process(request)
```

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
