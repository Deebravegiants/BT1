### Title
Opaque caller-supplied swap route lets attacker-named pool code attach arbitrary wallet-draining transfers to the caller's signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, and `flash_position` accept a fully opaque `swap_xdr`/`StrategySwap` blob that is forwarded verbatim to the configured router. The controller never inspects which pool or token contracts the route names. Because the router calls those addresses underneath the caller's `require_auth` root, a malicious pool contract embedded in the route can call `token.transfer(victim, attacker, amount)` for any token in the victim's wallet; the Soroban host records that transfer as a child of the caller's authorization entry during simulation, and a wallet that signs the simulated tree authorizes the theft. This is the on-chain analog of CVE-2022-1307: the signed/approved content (the authorization tree) is spoofed relative to what the user believes they approved (a swap). The codebase's own test harness demonstrates the theft end to end.

### Finding Description
`swap_tokens` forwards the user-supplied `swap` payload to `router.execute_strategy` without validating the pool/token addresses inside it [1](#0-0) . The controller only guards its own grant (`authorize_transfer_as_current` for one exact input transfer) and the measured output — nothing constrains what other contract code the route puts on the call stack [2](#0-1) . The entrypoint `process_swap_collateral` opens the caller's authorization root via `require_authorized_caller`, then executes the route [3](#0-2) .

The threat model itself states the router "calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization... The loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it" [4](#0-3) . The dedicated test `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` shows a rogue hop pool stealing Alice's entire unrelated wallet-token balance (77,770 units) as a recorded child of her `swap_collateral` auth entry while still delivering the fair swap output [5](#0-4) , and `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` confirms the theft executes once the simulated ("poisoned") tree is signed [6](#0-5) . Source-account credentials exhibit the same behavior [7](#0-6) .

### Impact Explanation
Theft of user funds: any token balance in the victim's wallet — including assets never deposited into or listed by the protocol — can be transferred to the attacker inside a transaction the victim intentionally signed as a routine `swap_collateral`/`swap_debt`/etc. The loss is unbounded by the route's `min_out`, the controller's measured-output check, or the final health-factor gate, since the draining transfer is collateral to the swap, not part of its accounting.

### Likelihood Explanation
Medium. Exploitation requires the victim to sign a route supplied by a malicious party (phishing frontend, compromised or malicious quote source) — analogous to the CVE's user-interaction requirement — rather than being freely executable on-chain. However, the route is opaque packed XDR that users cannot reasonably audit, the auth tree contents are not surfaced by the contract, and the swap itself can succeed at a fair price, so nothing in the user-visible outcome reveals the appended transfer. The protocol explicitly relies on the off-chain client to decode the route and refuse extra auth children, which is a UI-layer mitigation the contract does not enforce.

### Recommendation
Enforce route/venue integrity on-chain instead of relying on client-side decoding. Concretely: have the controller (or router, if in scope for a coordinated fix) whitelist or registry-pin the pool addresses permitted in routes per listed market, or reject any route that produces a caller-authorization child beyond the single expected input transfer — e.g., by executing the router call under the controller's own authorization (`authorize_as_current_contract` for the input spend, as already done) while structuring entrypoints so the caller's `require_auth` covers only the entrypoint frame and cannot be joined by deeper `require_auth(caller)` calls from route-named contracts. Short of that, emit the decoded set of route-named contracts in an event so wallets and indexers can surface them before signing.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: a `RogueHopPool` contract whose `swap()` executes `token.transfer(alice, attacker, WALLET_BALANCE)` on an unlisted token is embedded as the route's hop pool; calling `ctrl.swap_collateral(alice, account_id, USDC, 50_000_000_000, ETH, route)` records the stealing transfer inside Alice's signed authorization tree, leaves Alice's wallet balance at 0 and the attacker's at 77,770,000,000, while the swap itself completes normally (Alice's ETH supply is credited `FAIR_OUT_ETH`) [5](#0-4) .

Note: the same exposure exists on the router's direct `execute_strategy` path per the threat model, but router internals are out of scope; the in-scope root cause is the controller forwarding the opaque route under the caller's auth context with no venue validation.

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
