### Title
`RpcHandlerActor::process_tx` performs unbounded, unrate-limited signature verification and DB lookups per submitted transaction, enabling RPC-layer resource-exhaustion DoS - (File: `chain/client/src/rpc_handler.rs`)

### Summary
Any unprivileged client can call the public JSON-RPC transaction-submission methods (`broadcast_tx_async` / `broadcast_tx_commit`) with a flood of arbitrary `SignedTransaction`s. Each request reaches `RpcHandlerActor::process_tx` / `process_tx_internal`, which performs multiple non-trivial operations — chain-store/DB reads, epoch/shard lookups, and (via `runtime.validate_tx`) Ed25519 signature verification — before any admission or throttling decision is made. There is no per-origin/per-IP/per-account rate limiting at the JSON-RPC HTTP layer or inside `RpcHandlerActor` gating how many such requests can be processed, so the CPU/DB cost of "attempting to authenticate a transaction" is fully attacker-controllable, mirroring the reported `DisperseBlobAuthenticated` pattern where challenge/verification work is done before any rate limiting is applied.

### Finding Description
`chain/client/src/rpc_handler.rs` implements `Handler<ProcessTxRequest, ProcessTxResponse>` for `RpcHandlerActor`, which is the actor behind the public `send_tx_async`/`send_tx`/`send_tx_commit` JSON-RPC methods [1](#0-0) .

`process_tx_internal` runs, per incoming transaction and prior to any throttling:
1. `chain_store.head()` and `chain_store.get_block(...)` reads,
2. `check_transaction_validity_period(...)`,
3. `epoch_manager.get_epoch_id_from_prev_block(...)`, `get_epoch_protocol_version(...)`, `get_shard_layout(...)`,
4. `self.runtime.validate_tx(...)`, which performs the actual **signature verification** via `ValidatedTransaction::new` (`signed_tx.signature.verify(...)`), plus size/action-limit checks. [2](#0-1) [3](#0-2) 

Only after all of the above (chain reads + crypto verification) does the code reach any pool-size limiting (`ShardedTransactionPool::insert_transaction` → `InsertTransactionResult::NoSpaceLeft`) [4](#0-3) . That pool-size limit only bounds memory for *accepted* transactions belonging to accounts the node cares about — it does nothing to stop the pre-admission cost (DB reads + signature verification) incurred by every submitted transaction, including transactions with invalid signers, invalid signatures, or receivers on shards not tracked by this node.

Searches of the JSON-RPC HTTP entry point (`chain/jsonrpc/`) found no rate-limiting middleware (no `tower` rate-limit/governor layer, no per-IP throttling) guarding the `/` POST endpoint that dispatches to `ProcessTxRequest`; only a request body size limit exists. This is structurally identical to the reported issue: an authentication/verification step with non-negligible CPU and I/O cost is reachable by an unauthenticated caller with no rate limiting applied before or during that expensive work, only after a much later stage (successful pool insertion).

### Impact Explanation
An external, unprivileged attacker can submit a high-volume stream of syntactically-valid but garbage-signed (or expired/invalid-signer) transactions to a node's public RPC endpoint. Each one forces the node to perform DB reads (block/epoch lookups) and an Ed25519 signature verification on `RpcHandlerActor`'s dedicated multithreaded pool [5](#0-4) , none of which are gated by any origin-based rate limit. Sustained flooding can exhaust the `RpcHandlerActor` thread pool and associated DB/epoch-manager query capacity, degrading or denying transaction-processing service for legitimate users (RPC nodes and, if a validator co-locates or forwards from the same actor, potentially chunk producers), consistent with the "node panic or unbounded resource use / chain stall" impact class.

### Likelihood Explanation
High reachability: the JSON-RPC transaction endpoints are intentionally public and require no authentication or fee payment to attempt submission (the fee/nonce/balance checks all occur *after* the expensive verification work, or are skipped entirely for invalid-signature/invalid-signer transactions). Constructing an arbitrary volume of malformed `SignedTransaction`s that pass borsh deserialization and reach `validate_tx` is trivial and cheap for the attacker, while verification cost on the server side is real and unavoidable per request. No special network position or credentials are needed.

### Recommendation
Add origin-based (IP/account) rate limiting at the JSON-RPC HTTP layer (or in `RpcHandlerActor::process_tx`) that throttles the number of transaction-submission attempts processed per time window, incremented even on signature/validation failure, before the costly DB reads and signature verification are performed. Consider a lightweight pre-check (e.g., cheap structural checks or a token-bucket keyed by remote IP) ahead of `runtime.validate_tx`, and add scoring/backoff for clients repeatedly submitting invalid signatures.

### Proof of Concept
1. Start a node exposing the JSON-RPC server (default port 3030).
2. From an unprivileged client, repeatedly POST `broadcast_tx_async` requests containing `SignedTransaction`s with random/invalid signatures (or signers) at high frequency, e.g. thousands of requests per second.
3. Observe via metrics (`TRANSACTION_PROCESSED_TOTAL`, `TRANSACTION_PROCESSED_FAILED_TOTAL`) and CPU profiling that every request reaches `process_tx_internal` → `validate_tx`/signature verification and chain-store/epoch-manager reads regardless of validity, with no rejection or throttling prior to that work, and that RPC responsiveness for legitimate transactions degrades under load.         // here it is fine to use `cur_block_header` as it is a best effort estimate. If the transaction
```rust
        // were to be included, the block that the chunk points to will have height >= height of
        // `cur_block_header`.

        ) {
            tracing::debug!(target: "client", ?signed_tx, "invalid tx: expired or from a different fork");
            return Ok(ProcessTxResponse::InvalidTx(e));
        }
        let gas_price = cur_block_header.next_gas_price();
        let epoch_id = self.epoch_manager.get_epoch_id_from_prev_block(&head.last_block_hash)?;
        let protocol_version = self.epoch_manager.get_epoch_protocol_version(&epoch_id)?;
        let shard_layout = self.epoch_manager.get_shard_layout(&epoch_id)?;
        let receiver_shard =
            shard_layout.account_id_to_shard_id(signed_tx.transaction.receiver_id());
        // TODO(spice): get_last_certified_block_header does multiple DB reads

        // chain state so this is O(1).
        let spice_certified_header = if ProtocolFeature::Spice.enabled(protocol_version) {

            None

                &shard_layout,
                certified_header.as_ref(),

            cur_block.block_congestion_info().get(&receiver_shard).copied()

        let validated_tx = match self.runtime.validate_tx(

            signed_tx.clone(),

            Ok(validated_tx) => validated_tx,
            Err((err, signed_tx)) => {
                tracing::debug!(target: "client", tx_hash = ?signed_tx.get_hash(), ?err, "invalid tx during basic validation");
                return Ok(ProcessTxResponse::InvalidTx(err));
```

```rust
    pub fn insert_transaction(
        &mut self,
        validated_tx: ValidatedTransaction,
    ) -> InsertTransactionResult {
        let tx_hash = validated_tx.get_hash();
        if self.unique_transactions.contains(&tx_hash) {
            return InsertTransactionResult::Duplicate;
        }
        // We never expect the total size to go over `u64` during real operation as that would
        // be more than 10^9 GiB of RAM consumed for transaction pool, so panicking here is intended
        // to catch a logic error in estimation of transaction size.
        let new_total_transaction_size = self
            .total_transaction_size
            .checked_add(validated_tx.wire_size())
            .expect("Total transaction size is too large");
        if let Some(limit) = self.total_transaction_size_limit {
            if new_total_transaction_size > limit {
                return InsertTransactionResult::NoSpaceLeft;
            }
        }

        // At this point transaction is accepted to the pool.

        // This is guaranteed to succeed because of the check above that the
        // hashset does not contain this hash.  This can be improved once the
        // entries API is stabilized
        // (https://github.com/rust-lang/rust/issues/60896).
        assert_eq!(self.unique_transactions.insert(tx_hash), true);
        self.total_transaction_size = new_total_transaction_size;
        let signer_id = validated_tx.signer_id();
        let signer_public_key = validated_tx.public_key();
        self.transactions
            .entry(self.key(signer_id, signer_public_key, validated_tx.nonce().nonce_index()))
            .or_insert_with(Vec::new)
            .push(validated_tx);

        self.transaction_pool_count_metric.inc();
        self.transaction_pool_size_metric.set(self.total_transaction_size as i64);
        InsertTransactionResult::Success
    }
```

```markdown
### RpcHandlerActor

Defined in `chain/client/src/rpc_handler.rs`. A **separate multithreaded actor** dedicated to transaction pre-processing. It exists to keep transaction validation work (signature checks, nonce lookups, balance verification) off the consensus-critical `ClientActor`. Thread count is configurable via `handler_threads`.

When `process_tx()` is called with a `SignedTransaction`:

1. Validates transaction validity period and basic validity (signature, etc.).
2. Determines the signer's shard via shard layout.
3. **If this node tracks the shard:** deeper validation (balance, nonce), then inserts into transaction pool or forwards to validators.
```
