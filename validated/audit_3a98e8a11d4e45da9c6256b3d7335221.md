### Title
Webhook shop identity not bound to HMAC signature allows cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` value used by webhook handlers is read from an unsigned header. Any app-installing merchant who receives a genuine webhook for their own store can replay that (still validly-signed) body while swapping the shop header to a victim shop's domain, and `Registry.process` will accept it as valid and hand the handler a fabricated `shop` identity.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is derived independently, straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, with no cryptographic tie to the body or the HMAC: [2](#0-1) 

`Registry.process` validates only the HMAC of the body via `HmacValidator.validate(request)` and then immediately trusts `request.shop` (and `request.topic`) to construct the metadata passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received `hmac`; because `to_signable_string` for a webhook request is just the raw body, the shop header is never part of what is verified: [4](#0-3) 

**Binding that should hold, but doesn't:**
`hmac_verified(body) == true` should imply `shop_header == shop_that_produced(body)`. Instead, `hmac_verified(body) == true` only proves the body was signed by the app's shared `api_secret_key` at some point — it says nothing about which shop the header claims to be. Since a webhook signing secret (`client_secret`) is shared across every shop that installs the app (it's not per-tenant), any tenant that legitimately receives one genuine `(body, hmac)` pair can present that same pair again to the app's webhook endpoint with an arbitrary `shop-domain` header (e.g., a victim's `myshopify.com` domain), and the HMAC check still passes.

### Impact Explanation
This breaks the shop/tenant boundary: a malicious but unprivileged app-installing merchant (no special credentials, no access to `api_secret_key` needed — they only need a webhook that Shopify legitimately delivered to their own store) can cause the host application to process fabricated webhook events "as if" they came from a different, arbitrary shop. Any app logic keyed off `data.shop` (e.g., loading/updating that shop's stored access token, session, or business data) can be tricked into acting on the wrong tenant's context, which is a cross-tenant access impact.

### Likelihood Explanation
Likelihood is Medium-to-High for any app that installs on multiple untrusted merchants: the attacker only needs to be a legitimate (if malicious) installer of the app, capture one of their own real webhook deliveries (trivial — browser dev tools/logging, or by triggering an event on their own store), and resend it with a different `shop-domain` header to the app's public webhook endpoint. No secret key or privileged account is required.

### Recommendation
Bind the shop identity into the HMAC-verifiable content, or otherwise cryptographically tie the `shop-domain` header to the body before trusting it in `Registry.process`. For example, include `shop`, `topic`, and `webhook_id` in `Webhooks::Request#to_signable_string` (if Shopify's real signature scheme allows it) or, at minimum, cross-check the header's shop domain against a `shop`/`admin_graphql_api_id`-derived value inside the parsed body/gid before dispatching to the handler, and document that host apps must not treat the header as authenticated on its own.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` (ordinary merchant signup — no privileged access needed).
2. Trigger any subscribed webhook topic (e.g. `orders/create`) on `attacker-shop.myshopify.com`; capture the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent — this pair is a valid `(body, hmac)` under the app's shared `client_secret`.
3. Replay the exact same body + hmac to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only — matches, so validation passes.
5. `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` is invoked with `shop == "victim-shop.myshopify.com"`, even though the signed body content belongs to the attacker's own store — demonstrating the identity confusion.

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
