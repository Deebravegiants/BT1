### Title
Webhook shop/topic/webhook-id metadata is not covered by HMAC verification, allowing cross-tenant webhook forgery in `Webhooks::Registry.process` - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from raw HTTP headers, but `to_signable_string` — the value validated by `Utils::HmacValidator` — only covers the raw request body. `Webhooks::Registry.process` validates only this body-HMAC and then forwards the unauthenticated header values straight into `WebhookMetadata`, which is handed to the app's handler as if fully verified. [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
The HMAC binding this gem verifies is: `HMAC(client_secret, raw_body) == received_hmac`. It says nothing about which shop, topic, or webhook id produced that body. `HmacValidator.validate` calls `verifiable_query.to_signable_string`, and `Request#to_signable_string` returns only `@raw_body`: [5](#0-4) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers with no cryptographic link to the body or to each other: [6](#0-5) 

`Registry.process` checks only the HMAC-over-body and, once that passes, unconditionally trusts every header-derived field, packaging them into `WebhookMetadata` for the handler: [3](#0-2) 

Because `shop` is a `const :shop, String` field on `WebhookMetadata` that app code is expected to use to select the tenant/session the event applies to, and because it is outside the authenticated boundary, an attacker who can obtain any one genuine `(raw_body, hmac)` pair from Shopify (trivially available to them as the owner/operator of their own installed shop) can replay that exact body+HMAC to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header (and topic/webhook-id) of their choosing. The library provides no mechanism, and performs no check, that the `shop` header actually corresponds to the shop that produced the signed body.

This breaks the intended identity binding:
`shop_that_produced(raw_body, hmac) == shop_delivered_to_handler`
which the library implicitly claims to guarantee by exposing `request.shop`/`WebhookMetadata.shop` only after `Registry.process` reports the request as HMAC-validated, but which is in fact never enforced because `shop` is not part of `to_signable_string`.

### Impact Explanation
This is a cross-tenant confusion vector: an app that (as commonly done, and as shown in the gem's own docs) keys tenant data or session lookups off `WebhookMetadata#shop` can be tricked into applying a legitimate, signature-valid payload under the identity of a victim shop chosen by the attacker. Depending on the handler, this can lead to writing/deleting data, disabling features, or triggering side effects attributed to a shop the attacker does not control — a cross-tenant integrity/confidentiality impact.

### Likelihood Explanation
The attacker only needs to be an ordinary merchant who has installed the app on their own store (no privileged credentials, no access token, no `client_secret`) to obtain at least one legitimate `(body, hmac)` pair by triggering any registered webhook topic on their own shop, then replay it directly via HTTP with a forged `shopify-shop-domain` header. `Registry.process`'s only defense, `HmacValidator.validate`, does not fail because the body and HMAC are unmodified and genuinely valid.

### Recommendation
Include `shop_domain` (and ideally `topic`/`webhook_id`) in the signed/verified material, or independently verify that the shop asserted in the header corresponds to a shop with an active session/installation before trusting `WebhookMetadata#shop`. At minimum, document prominently that `request.shop`/`WebhookMetadata#shop` is not authenticated by the HMAC check and must be cross-validated by the host application against its own store of installed shops.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers any registered webhook topic (e.g. `orders/create`), capturing the real delivery: `raw_body = "{...}"`, `x-shopify-hmac-sha256 = "<valid-hmac-for-body>"`.
2. Attacker sends a direct HTTP POST to the app's webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and any desired `x-shopify-topic`/`x-shopify-webhook-id`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (no header is validated) and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC of `raw_body` — it passes because the body and HMAC are unchanged and genuinely signed by Shopify's secret.
4. `Registry.process` dispatches the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` where `shop == "victim-shop.myshopify.com"`, even though that shop never sent this event.
5. Any handler logic keyed on `data.shop` now operates on the victim shop's tenant context using attacker-supplied body content.
