This confirms the vulnerability. The `Request` class's `to_signable_string` returns only `@raw_body` (`lib/shopify_api/webhooks/request.rb:36-38`), meaning the HMAC signature covers exclusively the JSON body. The `shop`, `topic`, `api_version`, and `webhook_id` fields are all extracted from HTTP headers (`lib/shopify_api/webhooks/request.rb:20-33`) and are never included in the signable string, so `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-22`) cannot detect tampering with them. `Registry.process` then passes `request.shop` directly into `WebhookMetadata` (`lib/shopify_api/webhooks/registry.rb:189-199`, `lib/shopify_api/webhooks/webhook_handler.rb:6-12`), which is the value host applications use to identify which tenant/shop the webhook event belongs to.

### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) header fields are not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are read from unauthenticated HTTP headers. `HmacValidator.validate` only proves the body bytes weren't altered — it says nothing about the header values that `Registry.process` uses to route the webhook and identify the originating shop.

### Finding Description
The identity binding broken is: **shop verified by HMAC == shop acted upon by the handler**. In reality:
- HMAC-verified bytes = `@raw_body` only [1](#0-0) 
- Shop identity used for tenant routing = `shopify_header("shop-domain")`, an ordinary HTTP header with no cryptographic binding to the body or to the HMAC secret [2](#0-1) 

`HmacValidator.validate` computes the HMAC purely from `verifiable_query.to_signable_string` (the body) and compares it with the `hmac` header [3](#0-2) . `Registry.process` treats this HMAC check as sufficient proof of authenticity for the *entire request*, then forwards the unauthenticated `shop` header straight into the handler's `WebhookMetadata` [4](#0-3) . Any request whose body byte-sequence matches a validly-signed body (e.g., one the attacker legitimately received for their own shop) can be replayed with an arbitrary `shopify-shop-domain` header value and will pass verification while claiming to belong to a different shop.

### Impact Explanation
This is a cross-tenant identity binding failure: a webhook payload cryptographically proven to have originated from the app's Shopify integration can be attributed to an arbitrary shop of the attacker's choosing. Since `WebhookMetadata.shop` [5](#0-4)  is the only tenant-identifying value host apps typically use to select which merchant's database row/session to update, an attacker who controls one legitimate shop installation of the target app can capture a genuinely-signed webhook body (e.g., a body they fully control the content of, or a generic/empty body) and resend it with a forged `shop-domain` header pointing at a victim shop, causing the app to process attacker-controlled webhook data (e.g., `app/uninstalled`, `customers/redact`, GDPR events, product/order updates) under the victim's tenant context.

### Likelihood Explanation
Exploitability requires the attacker to be able to trigger webhook deliveries to their own endpoint under their own real/dev shop (which is trivial to obtain), then replay/forge headers to the app's public webhook receiving route while keeping a body that produces a valid HMAC. Since bodies are frequently generic JSON shapes shared across shops for a given topic (or the attacker can find a topic where they fully control body content, e.g. their own order/product data resembling another shop's schema), this is a realistic and low-cost attack against any app relying on `WebhookMetadata#shop` for tenant identification, with no dependency on leaked secrets.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `api_version`, `webhook_id`) header values in the HMAC signable string, or otherwise cryptographically bind the shop header to the signed payload, so `to_signable_string` cannot be satisfied by any request whose headers were altered independently of the body.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and registers webhook topic `X`.
2. Attacker triggers/receives a legitimate webhook for topic `X`; the raw body `B` was HMAC-signed by Shopify using the app's shared `client_secret`, satisfying `HmacValidator.validate` for body `B`.
3. Attacker resends the exact same request to the app's public webhook receiver endpoint, keeping the identical `hmac-sha256` header and body `B`, but rewrites `shopify-shop-domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers [6](#0-5) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only re-hashes body `B` and succeeds [7](#0-6) .
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though the payload never touched Shopify's systems for that shop, achieving cross-tenant webhook injection.
