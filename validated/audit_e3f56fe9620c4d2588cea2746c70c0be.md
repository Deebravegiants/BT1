### Title
Webhook `shop-domain` identity is not bound by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC over the raw request body, but the `shop` identity that the handler acts on is read from an HTTP header that is never included in that signature. An attacker who can obtain one valid `(raw_body, hmac)` pair for a shop they control can replay it against the app's public webhook endpoint with an arbitrary `shop-domain` header and have it accepted and processed as if it originated from a different, victim shop.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC exclusively over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw body — the `shop` accessor (populated from the `shopify-shop-domain`/`x-shopify-shop-domain` header) is intentionally excluded from the signable string: [2](#0-1) 

`Registry.process` validates the HMAC and, if valid, immediately trusts `request.shop` to build the `WebhookMetadata` that is handed to the app's business-logic handler: [3](#0-2) 

This breaks the intended identity binding: `HMAC(body) == HMAC(body)` is checked, but the equality that actually matters for tenant isolation — `shop_header == shop_that_produced(body)` — is never verified. Because the header is not part of the signed material, the same `(body, hmac)` pair remains valid under any `shop-domain` value the request sender supplies. This is the same class of bug as the report's "field acted on but not covered by the HMAC" — analogous to `SwapHelper.getAmounts` computing fees on the wrong parameter and being unbound from the actual balance being transferred.

### Impact Explanation
An attacker only needs the ability to generate one legitimate webhook from a shop they control (e.g., by installing the vulnerable app on their own free/dev store and triggering any subscribed webhook topic such as `orders/create`, whose JSON body content — line items, notes, customer fields — is largely attacker-controlled). Capturing that request's raw body and `X-Shopify-Hmac-Sha256` header, the attacker can replay it to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header naming a victim shop. `Registry.process` will accept it as authentic (HMAC still matches the unchanged body) and dispatch it to the app's handler tagged with the victim's shop, causing the host application to process attacker-controlled data under another tenant's identity — a cross-tenant confusion/injection primitive. For mandatory compliance topics such as `shop/redact` or `customers/redact`, this could be used to trigger destructive per-tenant actions (e.g., data deletion routines keyed off the webhook's `shop`) against a shop the attacker does not own.

### Likelihood Explanation
No credentials, access tokens, or `api_secret_key` are required — only a valid webhook the attacker can trigger for their own shop, plus network access to POST to the app's public webhook endpoint (an unprivileged internet capability). The gem provides no complementary check (e.g., verifying the header shop against a known/expected shop, or including it in the signed payload) before invoking the handler.

### Recommendation
Bind the shop identity to the signature: either require the app to reconcile `request.shop` against the shop tied to the session/webhook subscription before invoking the handler, or (preferably) validate the `shop-domain` header value against Shopify's expected format/allowlist and cross-check it against the topic's registered destination, rather than trusting a header value entirely excluded from `to_signable_string`.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger `orders/create` to receive a legitimate webhook POST with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because it was truly signed with the app's `api_secret_key` by Shopify for `attacker.myshopify.com`).
2. Replay the exact same `B` and `H` to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` which only checks `HMAC(B) == H` — passes.
4. `handler.handle(data: WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: B, ...))` executes with attacker-controlled `body` attributed to `victim.myshopify.com`, as shown in [3](#0-2) .
