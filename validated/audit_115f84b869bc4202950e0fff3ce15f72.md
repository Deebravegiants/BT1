The core finding: `ShopifyAPI::Webhooks::Request` computes and validates the HMAC only over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` fields—used to identify the tenant and route the payload—come from HTTP headers that are never included in the signed content.### Title
Webhook `shop` (tenant) identifier is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` fields used to identify the tenant and route the event are read directly from unauthenticated HTTP headers. `Registry.process` validates only that the body's HMAC is correct, then passes the header-derived `shop` value straight to the app's `WebhookHandler` as the trusted tenant identifier.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read from HTTP headers, none of which are part of the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC of the body via `Utils::HmacValidator.validate(request)`, then trusts `request.shop` (a header value) as the tenant identity forwarded to the handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (the raw body) and compares it against the `hmac` header — it never incorporates `shop`, `topic`, or `webhook_id`: [4](#0-3) 

The broken identity binding is:
`shop_authenticated_by_hmac (∅, since HMAC covers body only) ≠ shop_used_as_tenant_key (request.shop, an unauthenticated header value passed to WebhookMetadata)`

Because the HMAC is computed purely over the body bytes and does not bind the `shop-domain` header, any party who can obtain one genuine `(raw_body, hmac)` pair — trivially available to any merchant who installs the app on their own store and observes a real webhook delivery, or replays a `curl` capture of one — can resend that exact `(raw_body, hmac)` payload to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header (and arbitrary `x-shopify-topic`/`x-shopify-webhook-id` headers). The HMAC still validates because the body it protects is unchanged, but `WebhookMetadata.shop` (and `.topic`/`.webhook_id`) will reflect attacker-controlled values, causing the app to process data attributed to a victim shop it does not actually belong to.

### Impact Explanation
This crosses a tenant boundary: an attacker who owns any legitimate Shopify store (a free/low-cost prerequisite, not a privileged account of the target) can forge webhook events that the host app attributes to a different, victim shop of the attacker's choosing. Depending on how the host application uses `data.shop` (e.g., looking up/mutating shop-scoped records, triggering `app/uninstalled` cleanup, updating cached shop state, revoking tokens, or writing customer/order data keyed by the spoofed shop), this can result in cross-tenant data corruption or disclosure. This matches the "cross-tenant access" impact category in scope for this analog.

### Likelihood Explanation
Likelihood is moderate-to-high for a determined attacker: no access to the app's `client_secret`/API key or the victim's session is required — an attacker only needs to capture one legitimate webhook body+HMAC pair from a store they control (e.g., by installing any dev/free plan app instance and inspecting its own webhook traffic) and replay it with modified identity headers to the same, shared webhook endpoint. The library does nothing to prevent this: the shop/topic/webhook_id are simply not part of the verified content.

### Recommendation
Bind the `shop`, `topic`, and `webhook_id` values into the HMAC-verified content (or otherwise cryptographically bind them to the request, e.g., by requiring the host app to cross-check `shop` against a `session`/known installation before trusting `WebhookMetadata.shop`), rather than trusting header values whose only relationship to the signed body is coincidental co-delivery in the same HTTP request. At minimum, document prominently that `data.shop` in `WebhookMetadata` is unauthenticated and must be independently verified by the host application (e.g., against its own installed-shops table) before being used for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the target app (or any app using this gem) on their own Shopify store `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`).
2. Attacker captures the exact HTTP request Shopify sends to the app's webhook endpoint, including `raw_body` and the `x-shopify-hmac-sha256` header — both valid and verifiable, since the attacker's own store legitimately produced them: [5](#0-4) 
3. Attacker resends the identical `raw_body` and `hmac-sha256` header to the same webhook endpoint, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only and succeeds, since the body was untouched: [6](#0-5) 
5. The registered handler receives `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` with `shop == "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own shop: [7](#0-6) 
6. Any downstream logic in the host app that trusts `data.shop` as the source-of-truth tenant identifier (per the documented usage pattern) now acts on behalf of/against `victim-shop.myshopify.com` using attacker-supplied data.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
