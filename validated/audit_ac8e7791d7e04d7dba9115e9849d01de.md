### Title
Bad-debt write-down clamps `supply_index` to `SUPPLY_INDEX_FLOOR_RAW`, resurrecting wiped suppliers' claims that drain the next deposit - ([File: contracts/pool/src/interest.rs])

### Summary
The CVE-2016-5384 class — trusting attacker-shaped data to drive an invalid free/write-down that corrupts shared accounting — maps onto the pool's bad-debt socialization. `apply_bad_debt_to_supply_index` reduces the supply index by `1 - bad_debt/total_supplied_value`, but clamps the result at `SUPPLY_INDEX_FLOOR_RAW` (`RAY/1000`). When bad debt reaches or exceeds total supplied value, the index should go to ~0 (wiping every supplier's claim); the floor clamp instead leaves every live scaled share with a phantom claim of `scaled * RAY/1000`. Those claims are then payable out of any future cash.

### Finding Description
In `contracts/pool/src/interest.rs`, `apply_bad_debt_to_supply_index` computes `new_supply_index` and floors it at `SUPPLY_INDEX_FLOOR_RAW` instead of zeroing or burning the stranded shares: [1](#0-0) 

It is invoked on the borrow side of every seize, from `seize::apply`, which is reachable by an unprivileged caller through `clean_bad_debt`/liquidation in the controller: [2](#0-1) 

The repo's own tests prove the exploit shape: after a wipeout clamps the index to the floor, `unscale_supply_floor(old_scaled)` still returns a positive "stranded" claim; once fresh cash is deposited, the wiped position's `resolve_withdrawal`/`require_reserves`/`debit_cash` sequence pays out real tokens and leaves the fresh depositor undercollateralized — `cash < bob_claim`, "fresh depositor lost funds": [3](#0-2)  and [4](#0-3) 

An attacker reaches this by creating bad debt ≥ total supplied value on a (hub, token) book — e.g., borrow against collateral, crash the collateral price via their own oracle-affecting trades or wait for a genuine move, then call `clean_bad_debt`/`liquidate` so `seize` socializes the unpaid debt. Any suppliers still holding scaled shares in that market (including the attacker's own dust position, or a position the attacker supplies *after* the clamp but the clamp leaves index at floor so their `calculate_scaled_supply` mints at floor) retain claims far exceeding the remaining backing. The next depositor's cash is drained on withdrawal.

### Impact Explanation
Theft of user funds / protocol insolvency: wiped-out shares are resurrected as claims worth `scaled * RAY/1000` each, and the withdrawal path (`resolve_withdrawal` → `require_reserves` → `burn_supply` → `debit_cash`) honors them once any cash exists. The test demonstrates exact draining of a fresh deposit and the pool ending `cash < claim` for the honest depositor.

### Likelihood Explanation
Requires bad debt ≥ the book's total supplied value, i.e., a full wipeout — most feasible on thin/dust markets or after a sharp oracle price drop on a borrowed asset. `clean_bad_debt` and liquidation seizes are unprivileged, and the clamp path is unconditional in `apply_bad_debt_to_supply_index`; there is no guard preventing `supplied > 0` shares surviving a wipeout.

### Recommendation
On write-down, when `capped == total_supplied_value` (or the reduced index would hit the floor), explicitly zero the index (or burn stranded supply shares / mark the book wiped) rather than clamping to `SUPPLY_INDEX_FLOOR_RAW`; alternatively gate withdrawals when `supply_index == floor && supplied > 0` so phantom claims cannot be paid. Concretely, replace the `.max(Ray::from(SUPPLY_INDEX_FLOOR_RAW))` clamp in `contracts/pool/src/interest.rs:88` with a wipeout branch that prevents residual claims from outliving the backing.

### Proof of Concept
The scenario is already encoded in `contracts/pool/tests/interest.rs::test_raw_cache_floor_clamp_strands_claim_without_supply_guard` and `test_raw_cache_seizure_residual_would_drain_fresh_cash_without_supply_guard`: state `supplied=1000*RAY`, apply bad debt of `5000*RAY` → index clamps to floor; `unscale_supply_floor(old_scaled)` is still positive; mint a fresh deposit of that amount; the wiped position's withdrawal pays out exactly the fresh deposit, leaving `cash < fresh_claim`. The missing piece is only whether production guards (e.g., `require_reserves` in `withdraw::accounting`/`gate_and_debit`) block the withdraw while cash is zero — they do not, since the attacker's withdraw happens *after* a fresh deposit credits cash, which is exactly what the second test demonstrates end-to-end.

pub(crate) fn apply_bad_debt_to_supply_index(cache: &mut Cache, bad_debt: Ray) {
    let total_supplied_value = cache.supplied().mul(cache.env(), cache.supply_index());

    if total_supplied_value == Ray::ZERO {
        return;
    }

    let capped = bad_debt.min(total_supplied_value);
    let remaining = total_supplied_value.checked_sub(cache.env(), capped);

    let reduction_factor = remaining.div_floor(cache.env(), total_supplied_value);
    let new_supply_index = cache
        .supply_index()
        .mul_floor(cache.env(), reduction_factor);

    cache.set_supply_index(new_supply_index.max(Ray::from(SUPPLY_INDEX_FLOOR_RAW)));
}
