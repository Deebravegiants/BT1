### Title
Webhook `shop` and `topic` identity are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the handler a `WebhookMetadata` struct built from the `shop`, `topic`, `webhook_id`, and `api_version` HTTP headers — none of which are covered by that signature. This breaks the identity binding `shop_verified_by_hmac == shop_delivered_to_handler`, letting anyone who can obtain one legitimately-signed webhook body relabel it as coming from an arbitrary victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` fields are read straight from unauthenticated HTTP headers: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then immediately trusts `request.shop` and `request.topic` to build the `WebhookMetadata` passed to the app's handler — with no check that the `shop` header corresponds to a shop that actually has this app/webhook installed, nor that it matches the shop that produced this particular signed payload: [3](#0-2) 

`WebhookMetadata.shop` is a plain, unauthenticated `String` field that downstream handler code is expected to trust as the tenant identity for the payload: [4](#0-3) 

Because the signature only proves "this body was HMAC'd with our `api_secret_key`" and not "this body was sent for shop X", the equality the report's bug class describes — `shop authenticated == shop stored/acted on` — does not hold. Any actor who can obtain one validly-signed webhook body/HMAC pair (e.g., by installing the app on their own store and receiving a real webhook from Shopify) can replay that exact body+HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and `x-shopify-topic`) header for a different, victim shop. `Utils::HmacValidator.validate` will still pass because it only recomputes the HMAC over `raw_body`: [5](#0-4) [6](#0-5) 

The `Registry` never cross-checks the delivered `shop` against a known/installed-shop session store before dispatching to the handler, so the gem hands the host application data that is only partially authenticated — the tenant-identifying field is fully attacker-controlled.

### Impact Explanation
This crosses a tenant boundary: a handler that uses `WebhookMetadata#shop` to look up or mutate per-shop state (sessions, orders, inventory records, etc. — the documented, intended use of this field) can be made to apply attacker-supplied webhook data to a victim shop's identity. This matches the Critical "cross-tenant access" impact category, since the gem's own API surface (`Registry.process` / `WebhookMetadata`) is the thing asserting the (false) guarantee that `shop` has been authenticated together with the payload.

### Likelihood Explanation
Moderate-to-high: exploitation requires only (1) the attacker's own real, validly-signed webhook body from Shopify (trivially obtainable by installing any app under the attacker's control that shares webhook infrastructure, or by an app that broadcasts identical bodies across shops, e.g. `app/uninstalled` with an empty `{}` body as seen in the test fixtures) and (2) the ability to POST arbitrary headers to the app's public webhook endpoint — no `api_secret_key`, access token, or privileged account needed. No cryptographic secret needs to be known; only the header identifying the tenant needs to be forged, since it sits entirely outside the signed content.

### Recommendation
Bind the delivered `shop` (and ideally `topic`/`webhook_id`) to the authenticated payload:
- Include the `shop`, `topic`, and `webhook_id` in the HMAC-signable string used by `Request#to_signable_string` (mirroring how `Oauth::AuthQuery#to_signable_string` includes `shop` in its signed params), so any tampering with these headers invalidates the signature.
- Additionally/alternatively, require callers of `Registry.process` to supply the set of shops for which the app currently holds a valid session, and reject webhooks whose `shop` header isn't in that set before invoking the handler.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and configures a webhook subscription for a topic whose body content is invariant or attacker-influenced (e.g., `app/uninstalled`, which Shopify sends with body `{}`).
2. Shopify delivers a real webhook to the app's endpoint with headers:
   ```
   x-shopify-topic: app/uninstalled
   x-shopify-hmac-sha256: <valid HMAC of "{}">
   x-shopify-shop-domain: attacker.myshopify.com
   ```
3. Attacker captures this exact `(raw_body, hmac)` pair and re-POSTs it to the same endpoint, changing only the shop header:
   ```
   x-shopify-topic: app/uninstalled
   x-shopify-hmac-sha256: <same valid HMAC, unchanged>
   x-shopify-shop-domain: victim.myshopify.com
   ```
4. `HmacValidator.validate` at `lib/shopify_api/utils/hmac_validator.rb#L12-L22` recomputes the HMAC over `raw_body` only (`Request#to_signable_string`, `lib/shopify_api/webhooks/request.rb#L35-L38`) — it still matches, since `shop` is not part of the signed string.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb#L188-L200`) accepts the request and invokes the app's handler with `WebhookMetadata(shop: "victim.myshopify.com", topic: "app/uninstalled", body: {})`, causing the app to act (e.g., delete/deactivate) on `victim.myshopify.com`'s data despite the attacker having no relationship to that shop.
