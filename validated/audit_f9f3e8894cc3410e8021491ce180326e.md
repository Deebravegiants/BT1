### Title
Webhook `shop` field is trusted from an unauthenticated header while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's HMAC before invoking the app's handler, but the HMAC only ever covers the request body. The `shop` value that is handed to the app's `WebhookHandler` (and used to attribute the webhook payload to a tenant) is read directly from the `X-Shopify-Shop-Domain` header, which is never included in the signed material. This breaks the binding: `hmac(secret, body) == received_hmac` is verified, but `shop-domain header == shop that produced body` is never checked.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`to_signable_string` returns only `@raw_body`, and `shop` is read straight out of the (attacker-controllable, in the sense that it's just an HTTP header on the request the app receives) `shopify-shop-domain` / `x-shopify-shop-domain` header - none of the headers are part of the signed string.

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body) and compares it with `verifiable_query.hmac`: [2](#0-1) 

`Registry.process` uses this same validated `request` object to build the `WebhookMetadata` passed to the app's handler, taking `shop: request.shop` directly from the header, with no cross-check against the signed body or any shop allow-list: [3](#0-2) 

`WebhookMetadata` is a plain struct carrying that unauthenticated `shop` value on to the app: [4](#0-3) 

Because a single `api_secret_key` is shared by an app across every shop that installs it (`Context.api_secret_key`, used uniformly in `HmacValidator.validate_signature`), any shop that has installed the app can generate a request with a **valid** HMAC for a body of their choosing (e.g., by triggering a real webhook from their own store, or, since only the body is signed, by controlling body content on their own tenant), and then submit it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header set to an arbitrary victim shop domain. The HMAC check in `HmacValidator.validate` passes because it only checks `secret` and `body`; it has no way to know or enforce which shop the request "should" belong to.

This equality is what should hold but doesn't:
`shop_header_used_by_handler == shop_that_actually_generated_and_signed_the_body`

### Impact Explanation
This is a cross-tenant data injection / cross-tenant access primitive at the library's trust boundary: the gem hands the host application a `shop` value that it presents as authenticated (having just passed `HmacValidator.validate`) but which is not bound to the signed payload at all. Any application that uses `WebhookMetadata#shop` to select which tenant's data to update (a normal and expected usage pattern, since that's the field's entire purpose) can be made to apply an attacker's webhook body under a victim shop's identity, as long as the attacker is themselves an installed user of the app (an "unprivileged internet user" with respect to any other tenant). This matches the Critical category of cross-tenant access via a broken identity-binding check performed by the gem itself.

### Likelihood Explanation
Exploitation requires only that the attacker has installed the app on a shop they control - a normal, unprivileged install available to any internet user for public apps - and that they can trigger or observe a legitimately-signed webhook for their own store (trivial, e.g. triggering `orders/create` on their own shop). No access to `api_secret_key`, tokens, or the victim's credentials is required. The only precondition outside this gem's control is that the host app relies on `WebhookMetadata#shop` to identify the tenant, which is the field's documented purpose (`shop` header is what `Registry.process` explicitly forwards for that reason).

### Recommendation
Bind the `shop` header cryptographically into the material that is verified, or verify it out-of-band: e.g., include the shop domain in the signable string used by `Request#to_signable_string`, or have `Registry.process` cross-check `request.shop` against the current session/shop the app expects for that webhook subscription before invoking the handler, instead of trusting the header unconditionally once only the body's HMAC has been validated.

### Proof of Concept
```ruby
# Attacker owns shop "attacker-shop.myshopify.com", app installed there,
# so requests for that shop are correctly HMAC-signed by Shopify with the
# app's shared api_secret_key.

raw_body = '{"id": 1, "note": "malicious payload"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Attacker replays this legitimately-signed body but swaps the shop-domain header
# to the victim's shop instead of their own.
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # spoofed
  "x-shopify-webhook-id" => "attacker-controlled-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

# HmacValidator.validate(request) => true, because only raw_body is signed,
# not the shop-domain header.
ShopifyAPI::Webhooks::Registry.process(request)
# => app's handler.handle(data) is invoked with data.shop == "victim-shop.myshopify.com"
#    even though the payload actually originated from attacker-shop.
```
