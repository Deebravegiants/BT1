### Title
Webhook `shop-domain` header is trusted for tenant attribution without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields come from unauthenticated HTTP headers. `Registry.process` validates the HMAC against the body, then unconditionally forwards the header-derived `shop` value to the app's webhook handler as the identity of the tenant that the payload belongs to. The binding "shop attributed to this webhook" == "shop whose secret produced this HMAC" is never enforced, because the HMAC never covers the shop field.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic tie to the body or to the secret: [2](#0-1) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (i.e., the body) against the HMAC — it never incorporates `shop`, `topic`, or any header: [3](#0-2) 

`Registry.process` validates only that the body's HMAC is correct, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the metadata passed to the app's handler: [4](#0-3) 

Because the shop-domain header is not part of the signed material, `(computed_hmac, body)` is valid for *any* shop-domain header value. An attacker who is themselves a legitimate merchant (or who otherwise obtains one valid `(body, hmac)` pair signed with the app's real `api_secret_key`, e.g. from their own dev-store webhook deliveries) can replay that exact body+HMAC pair to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header for a victim shop. `HmacValidator.validate` still returns `true` because it only ever re-derives the HMAC from the (unchanged) body. `Registry.process` then dispatches to the handler with `shop: request.shop` set to the victim's domain, so the host application processes attacker-controlled data as if it originated from the victim shop's Shopify instance — a cross-tenant identity-binding break: `shop authenticated by HMAC` ≠ `shop delivered to the handler`.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: the shop identity handed to the app is unauthenticated, enabling a cross-tenant data confusion/injection scenario where an attacker-controlled payload is processed under a victim shop's identity. This matches the Critical "cross-tenant access" impact category, since any app logic that keys off `WebhookMetadata#shop` (e.g., looking up the victim's stored access token/session, writing to the victim's records) is misattributed.

### Likelihood Explanation
Requires the attacker to obtain at least one legitimately-signed `(body, hmac)` pair for the target app (trivially available by installing the app themselves on any store and capturing their own webhook deliveries), then POST to the app's public webhook receiver endpoint with a forged shop-domain header. No knowledge of `api_secret_key` is needed since the HMAC never has to be recomputed for the forged header. The webhook endpoint is by design unauthenticated/internet-reachable.

### Recommendation
Include the shop domain (and topic) in the signable content used by `Request#to_signable_string`/`HmacValidator`, or otherwise cryptographically bind `shop-domain` to the HMAC before it is trusted, so that the HMAC verification covers the identity fields actually consumed downstream, not merely the body bytes.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and captures a legitimate webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's real `api_secret_key`), plus `x-shopify-topic: orders/create`.
2. Attacker POSTs to the app's public webhook endpoint with the same body `B` and same `H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, `HmacValidator.validate` recomputes HMAC over `B` only and it matches `H`, so `Registry.process` proceeds: [4](#0-3) 
4. The app's handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-controlled `body`, processing it as authentic data from the victim tenant.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
