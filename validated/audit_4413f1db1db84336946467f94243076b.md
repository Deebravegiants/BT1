### Title
Webhook shop-domain header trusted for tenant identification but not covered by HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` HTTP header, but the HMAC signature that `Utils::HmacValidator.validate` checks only covers the raw request body, not this header. `Registry.process` accepts any request whose body-HMAC is valid and then trusts the (unsigned) shop header to route/attribute the webhook to a tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (i.e. the body only) and compares it against the `hmac` field extracted from the same request: [3](#0-2) 

`Registry.process` gates on that body-only HMAC check and then forwards `request.shop` — read straight from the unsigned header — as the tenant identity to the webhook handler: [4](#0-3) 

The binding the gem is supposed to enforce is:
`hmac == HMAC(secret, body ‖ shop)` (the tenant claim is bound to the signature)

What is actually enforced is:
`hmac == HMAC(secret, body)` (the tenant claim `shop` is accepted unauthenticated)

Because `shop-domain` is excluded from the signed data, any request that carries a *(body, hmac)* pair that is valid for the secret — regardless of which shop it was originally generated for — will pass verification with an attacker-chosen `shop-domain` header value. `Registry.process` does not perform any additional cross-check that the shop in the header actually generated that body/HMAC pair.

### Impact Explanation
This breaks the tenant/shop binding that webhook consumers rely on: `WebhookMetadata.shop` is the only identity information the host application receives to know which merchant’s data the webhook event belongs to. If a `(body, hmac)` pair valid for the app's shared `client_secret` can be paired with an arbitrary `shop-domain` value, an app that trusts `data.shop` for record lookups, authorization, or data updates can be led to attribute or apply data intended for one shop to a different shop — a cross-tenant confusion inside the app built on this gem. This matches the Critical impact category of cross-tenant access via a broken identity binding.

### Likelihood Explanation
Exploitability is constrained by the fact that the attacker must still possess a `(body, hmac)` pair that is valid for the app's `client_secret` — which in practice can only be obtained from a genuine Shopify-delivered webhook. Shopify sends webhooks directly server-to-server to the registered app endpoint, so an external, unprivileged attacker normally cannot capture or replay that pair themselves unless they control (or can observe traffic to) the app's own receiving endpoint, or unless multiple shops can trigger topics whose body content is identical/predictable (e.g., near-empty compliance payloads), which would let a `(body, hmac)` pair legitimately produced for one shop be reused for another. This narrows likelihood to Medium/Low in typical unprivileged-external-attacker scenarios, but the root-cause defect — the shop identity not being covered by the signature — is unambiguous and directly matches the requested bug class ("a field acted on but not covered by the HMAC").

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signable data used for HMAC verification, or have `Registry.process` independently verify that `request.shop` is consistent with a trusted, previously-established session/shop record before invoking the handler, instead of trusting the raw header value once the body-only HMAC succeeds.

### Proof of Concept
1. Register a webhook handler with `ShopifyAPI::Webhooks::Registry.add_registration`.
2. Obtain any `(raw_body, hmac-sha256)` pair that is valid for the app's `client_secret` for a topic with static/predictable body content (e.g., a compliance webhook with minimal JSON body).
3. Send a request to the app's webhook endpoint using that exact `raw_body` and `hmac-sha256` header, but set the `shopify-shop-domain` header to a different (victim) shop's domain.
4. `Utils::HmacValidator.validate` in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) succeeds because it only checks the body's HMAC.
5. The handler receives `WebhookMetadata` with `shop` equal to the attacker-supplied victim domain (`lib/shopify_api/webhooks/registry.rb:198-199`), even though that shop never produced the signed payload.
