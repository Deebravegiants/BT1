### Title
Excess native-token payment in `EvmHost.dispatch()`/`fundRequest()` is refunded to the Host contract instead of the user, permanently stranding user ETH - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept native token payment (`msg.value`) and forward it to `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. This is directly analogous to the reported bug class: an unprivileged, ordinary user action (dispatching a cross-chain message) deposits ETH into a contract, and any leftover ETH that isn't consumed has no path back to the depositor, similarly to the reported "contracts receive ETH deposits with no way to withdraw them" issue. [1](#0-0) 

### Finding Description
`swapETHForExactTokens(amountOut, path, to, deadline)` on Uniswap V2 only consumes the ETH required to produce `amountOut` tokens; it refunds any unused ETH to `msg.sender` of the router call. In `EvmHost`, the router is invoked by the `EvmHost` contract itself (`IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(...)`), so `msg.sender` from the router's perspective is `address(this)` (the `EvmHost`), not the original transaction sender who supplied `msg.value` to `dispatch()`/`fundRequest()`. Any excess ETH sent by a user beyond what is required for the swap is refunded by the router back into the `EvmHost` contract's own balance rather than to the user. [2](#0-1) [3](#0-2) [4](#0-3) 

Once ETH lands in `EvmHost`'s balance this way, there is no user-callable withdrawal path for it — it can only ever be moved out via the governance-gated `withdraw(WithdrawParams)` function, which is restricted to the cross-chain `hostManager` (governance), not to the depositor. [5](#0-4) 

Even if governance later sweeps native ETH via `withdraw`, that mechanism disburses to an arbitrary `beneficiary` chosen by governance — it has no way to identify or refund the specific user who overpaid, since `EvmHost` never records who deposited how much excess native ETH. From the perspective of the individual depositor, the excess ETH is a permanent, unrecoverable loss functionally identical to the "stuck ETH with no user withdraw path" bug class described in the report, even though a *generic* revenue-sweep exists for the protocol as a whole.

### Impact Explanation
Any user (or any `HyperApp`/integrating contract on their behalf) who calls `dispatch()` or `fundRequest()` with `msg.value` that is even slightly greater than the exact amount consumed by the Uniswap swap (e.g. due to price movement between fee estimation and execution, or simply overestimating slippage) will have the difference permanently trapped inside `EvmHost`, unattributed to them and unrecoverable by them. Because native-token payment is a documented, supported first-class dispatch flow (see `docs/content/developers/evm/messaging/post-requests.mdx`), this affects ordinary end users of any Hyperbridge-integrated dApp, not just a hypothetical edge case. This is a permanent freezing-of-funds condition for affected users, satisfying the "Medium/High" bar via loss of individual user funds at scale.

### Likelihood Explanation
High. Since `swapETHForExactTokens` requires an exact output amount, callers must generally overestimate `msg.value` to guard against price slippage between fee-quoting and transaction execution (the docs explicitly instruct users to "send enough native tokens to cover fees"). Any conservative overestimation — which is the recommended safe practice — directly causes leftover ETH to be misrouted into the Host's balance rather than refunded. This requires no attacker and triggers on completely normal usage.

### Recommendation
In `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, after performing the Uniswap swap, compute the actual ETH consumed (or capture the router's return value / check `address(this).balance` delta) and refund any unspent `msg.value` directly to `_msgSender()` via a low-level `call`, rather than allowing the router's refund to accrue inside `EvmHost`. Alternatively, use `swapExactETHForTokens`-style patterns with pre-computed amounts so no residual ETH can occur, or explicitly forward the refund destination — pass `_msgSender()` (or a captured pre-swap balance snapshot) so any leftover funds are returned to the depositor in the same transaction rather than being silently absorbed by the contract.

### Proof of Concept
1. User A wants to dispatch a `POST` request with `post.fee = 100 DAI`-equivalent in `feeToken`.
2. Uniswap quotes 0.05 ETH for 100 feeToken units, but due to normal price movement/slippage, A sends `msg.value = 0.06 ETH` to be safe.
3. `EvmHost.dispatch()` calls `swapETHForExactTokens{value: 0.06 ether}(100e18, path, address(this), deadline)`.
4. The router consumes only ~0.05 ETH (the actual required input) and refunds the remaining ~0.01 ETH — but the refund target is `msg.sender` of the router call, i.e., `EvmHost` itself, since `EvmHost` is the caller of the router.
5. The 0.01 ETH excess becomes part of `EvmHost`'s ETH balance, with no mapping back to user A and no way for A to reclaim it. Repeated over many dispatches by many users, this ETH balance accumulates and is permanently frozen from each depositor's perspective, only sweepable in bulk (and to an arbitrary beneficiary) by governance via `withdraw`.

    /**
     * @dev Dispatch a POST request to Hyperbridge
     *
     * @notice Payment for the request can be made with either the native token or the feeToken.
     * If native tokens are supplied, it will perform a swap under the hood using the local uniswap router.
     * Will revert if enough native tokens are not provided.
     *
     * If no native tokens are provided then it will try to collect payment from the calling contract in
     * the feeToken.
     *
     * @param post - post request
     * @return commitment - the request commitment
     */
    function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                post.fee, path, address(this), block.timestamp
            );
        } else if (post.fee > 0) {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
        }
