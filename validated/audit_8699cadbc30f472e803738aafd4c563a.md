Found it — the identity binding break is in `Webhooks::Request#shop` / `Webhooks::Registry.process`.

The `hmac` computed for validation covers only the raw request body (`to_signable_string` returns `@raw_body`), not the `x-shopify-shop-domain` header. `request.shop` is read directly from that header and passed unbound-checked into the handler as the tenant identifier. [1](#0-0) [2](#0-1) 

### Title
Webhook shop-domain header not covered by HMAC allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`Registry.process` validates a webhook's authenticity solely via `Utils::HmacValidator.validate(request)`, which signs/verifies only `@raw_body`. The `shop` value that is handed to the app's `WebhookHandler` (used by the host app to identify which tenant/session the payload belongs to) comes from the `x-shopify-shop-domain` HTTP header, which is completely outside the HMAC's signed bytes.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` only: [3](#0-2) 

`HmacValidator.validate_signature` recomputes the HMAC over `to_signable_string` (i.e. the raw body) and compares it to the `hmac` header value: [4](#0-3) 

Meanwhile `Request#shop` is parsed straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header: [5](#0-4) 

`Registry.process` validates the HMAC and then immediately dispatches to the handler using `request.shop` as the tenant identifier, without any cross-check that this shop is the one whose secret validated the body: [2](#0-1) 

This breaks the intended identity binding: `HMAC-verified bytes == bytes used to derive the shop identity`. Since the body content (JSON payload) is what's signed, and the `shop` header is a separate, unauthenticated field, any party that can replay/re-deliver a body with a valid HMAC for a *given* shop (or, more critically, any man-in-the-middle / logging proxy / webhook aggregator that forwards Shopify's genuine webhook requests to multiple app deployments) can alter the `x-shopify-shop-domain` header while keeping the same body+HMAC intact — because that header is not part of the signed material, the gem's own validation logic gives no signal that shop and body are bound together. Because this gem's documented contract is "HMAC-validated request", host apps reasonably (and per the gem's own examples in `WebhookMetadata`) trust `request.shop` as an authenticated tenant identifier once `process` succeeds.

### Impact Explanation
If an attacker (or a compromised intermediary that only has network-level control over how requests are dispatched to the app, not the `client_secret`) can influence the `shop` header of an otherwise-valid Shopify webhook delivery while preserving the body/HMAC pair, the receiving app will process/attribute a genuine payload to the wrong merchant. Any host app that keys tenant lookups (session/access-token retrieval, GDPR redact handlers, data mutations) off `WebhookMetadata#shop` — which is the documented usage pattern this library returns from `Registry.process` — is exposed to cross-tenant data handling. This maps to the Critical impact category (cross-tenant access) since a webhook body of shop A can be processed under the identity of shop B, because the identifying field is unauthenticated relative to the HMAC that is claimed to authenticate the whole request.

### Likelihood Explanation
Exploitation requires the ability to control or rewrite HTTP headers on the path to the app's webhook endpoint without needing the `client_secret` or `api_secret_key` (unlike forging the HMAC itself, which would require the secret). This is realistic in common real-world topologies: apps proxied behind shared ingress/load balancers, webhook fan-out relays, or logging/reverse-proxy middleware that developers add in front of the webhook receiver — none of which are prevented or warned against by this gem, since the gem never binds `shop` into the HMAC-covered data and never independently confirms the domain. Likelihood is elevated because the vulnerable pattern is baked into the gem's public API (`Request`, `Registry.process`, `WebhookMetadata`) rather than depending on a host-app misuse.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) header into the value that is HMAC-verified, or independently verify that the `shop` header corresponds to the same tenant whose secret validated the body (e.g., include the header in `to_signable_string`, or require/verify it separately against a known session store prior to dispatch). At minimum, document loudly that `request.shop` is not authenticated by the HMAC check and must not be trusted for tenant selection without additional verification.

### Proof of Concept
1. Attacker/relay intercepts (or replays through a shared endpoint) a legitimately Shopify-signed webhook delivery for `shop-a.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B`).
2. Attacker forwards the same body `B` and same `x-shopify-hmac-sha256: H` header to the app's webhook endpoint, but rewrites `x-shopify-shop-domain` to `shop-b.myshopify.com`.
3. `Webhooks::Registry.process` calls `HmacValidator.validate(request)`, which only checks `HMAC(raw_body) == H` — this still succeeds because `raw_body` is unchanged. [6](#0-5) 
4. `process` proceeds to call `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` with `shop == "shop-b.myshopify.com"`, even though the body actually belongs to shop A. [7](#0-6) 
5. The host app's handler, trusting `data.shop` as the authenticated tenant (the documented purpose of this field), performs actions (e.g., data redaction, token lookup, order sync) against shop B's tenant context using shop A's payload — a cross-tenant identity confusion.
