### Title
Escrow accounting in the Tron `IntentGatewayV2.placeOrder` can be inflated relative to real token balance, causing insolvency/frozen funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron deployment of `IntentGatewayV2` credits its internal escrow ledger `_orders[commitment][token]` with the *nominal* fee-adjusted input amount immediately after an external `safeTransferFrom` call, without ever verifying that the contract's real token balance increased by that amount, and without a reentrancy guard on `placeOrder`. This mirrors the reported ERC4626 bug class: an accounting total (`_totalSupply` there, `_orders[...]` escrow here) is derived from an assumed transfer outcome rather than from actual balance deltas measured around an external call, which can be manipulated or simply wrong for non-standard tokens.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder` (lines 338-506), the commitment is computed **before** any token transfers occur, using the nominal, non-fee-on-transfer-adjusted `order.inputs[i].amount`: [1](#0-0) 

Then in the input-escrow loop, for each token the contract does an external call and immediately updates escrow accounting with the *reduced nominal* amount, not the amount actually received: [2](#0-1) 

Contrast this with the "main" EVM contract (`evm/src/apps/IntentGatewayV2.sol`), which explicitly guards against this class of bug by (a) measuring the actual balance received around every `safeTransferFrom` call and mutating `order.inputs[i].amount` to the real received amount before computing the commitment or crediting escrow, and (b) protecting `placeOrder` with `nonReentrant`: [3](#0-2) [4](#0-3) 

The Tron variant has neither protection: `placeOrder` has no `nonReentrant` modifier, and it trusts `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` to have delivered the full nominal amount before crediting `_orders[commitment][token] += reducedInputs[i].amount`.

### Impact Explanation
If any input token used with the Tron gateway is fee-on-transfer, rebasing, or otherwise delivers less (or more, via reentrant top-up) than the nominal amount, the escrow ledger `_orders[commitment][token]` no longer reflects the contract's actual token balance. Because escrow ledger entries across many concurrently-open orders share the same underlying token balance pool, an under-collateralized credit for one order means the contract's real balance is insufficient to honor the sum of all outstanding escrow claims. When solvers fill orders and the protocol later transfers out escrowed tokens via `_withdraw`/`safeTransfer` for *other* orders (see `IntentsBase._withdraw`), a shortfall causes: (1) legitimate order withdrawals/refunds to permanently revert due to insufficient balance (funds frozen), or (2) whichever order is settled first drains real tokens that were nominally credited to other unrelated orders (funds effectively stolen from other users' escrow), since the ledger, not the real balance, gates individual order operations.

### Likelihood Explanation
This path is reachable by any unprivileged user calling `placeOrder` on the Tron `IntentGatewayV2` with an ERC20 token that has non-standard transfer semantics (fee-on-transfer/deflationary), which is common on Tron (TRC20 tokens with burn/fee mechanisms exist) and is explicitly a scenario the sibling EVM contract already defends against — proving this is a known, exploitable class in this codebase, just unfixed in the Tron fork. No admin/governance/relayer action is required; a single `placeOrder` transaction with such a token is sufficient to desynchronize escrow accounting from real balance.

### Recommendation
Port the balance-diff pattern from `evm/src/apps/IntentGatewayV2.sol` into the Tron contract: measure `IERC20(token).balanceOf(address(this))` before and after each `safeTransferFrom`, use the actual delta (not the nominal amount) both for computing the commitment and for crediting `_orders[commitment][token]`, and add `nonReentrant` to `placeOrder` (and any other externally callable state-mutating entry points) to prevent reentrant manipulation during the external transfer calls.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with a TRC20 token `FeeToken` that deducts e.g. 1% on every `transferFrom`.
2. User calls `placeOrder` with `order.inputs[0] = {token: FeeToken, amount: 1000}`. The loop calls `IERC20(FeeToken).safeTransferFrom(user, gateway, 1000)`, but the gateway's real balance only increases by 990.
3. Despite this, `_orders[commitment][FeeToken] += reducedInputs[0].amount` credits (approximately) the full nominal 1000 (minus only protocol fee, not the transfer fee) — a 10-unit discrepancy between ledger and real balance for this order alone; repeated across many orders this compounds.
4. When solvers later fill orders and the contract attempts to pay out escrowed amounts via `_withdraw`'s `IERC20(token).safeTransfer(beneficiary, amount)`, the sum of all credited escrow amounts can exceed the gateway's actual `FeeToken` balance, causing later withdrawals to revert (frozen funds) or allowing an early withdrawal to consume balance that rightfully belonged to a different order's escrow (fund theft from other users).
