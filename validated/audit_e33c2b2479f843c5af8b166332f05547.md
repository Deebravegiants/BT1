### Title
Webhook `shop-domain` Header Not Covered by HMAC Signature Allows Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The `Webhooks::Request#to_signable_string` method used for HMAC validation only signs the raw request body, while the `shop` attribute exposed by the same object is read directly from an unauthenticated HTTP header (`shopify-shop-domain` / `x-shopify-shop-domain`). Because the HMAC never covers this header, an attacker who possesses any single validly-signed webhook payload can change the `shop-domain` header value and have the request still pass HMAC validation, causing the host application to process the webhook as if it originated from an arbitrary, attacker-chosen shop.

### Finding Description
`Webhooks::Registry.process` validates a webhook exclusively via `Utils::HmacValidator.validate(request)`, which in turn calls `request.to_signable_string` to compute the expected signature: [1](#0-0) 

`to_signable_string` is implemented to return only `@raw_body`: [2](#0-1) 

However, `shop` — the field that identifies which merchant/tenant the webhook belongs to — is parsed straight from the `shop-domain` header without any cryptographic binding to the signature: [3](#0-2) 

`Registry.process` then trusts this unauthenticated field and forwards it directly to the application's webhook handler as the tenant identity for the event: [4](#0-3) 

This is the exact identity-binding break called out in the bug class: the equality that should hold is
`shop_bound_by_hmac == shop_used_by_handler`
but instead the gem only enforces `hmac(raw_body) == received_hmac`, leaving `shop` completely outside the signed material. Any request with a valid `(raw_body, hmac)` pair — regardless of which merchant it was actually issued for — will validate successfully no matter what `shop-domain` value is attached to it, since `OpenSSL.secure_compare` in `HmacValidator#validate_signature` only checks the signature against the body.

### Impact Explanation
This is a cross-tenant identity confusion vulnerability. An attacker who is a legitimate merchant of the app (and therefore receives correctly-signed webhooks for their own shop, since Shopify signs webhooks with the app's shared secret regardless of which merchant it's for) can capture one such valid `(body, hmac)` pair and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. Because `shop` is not covered by the HMAC, the request still passes `HmacValidator.validate`, and the host application's handler will process the event believing it originates from the victim tenant — e.g. writing/deleting victim data, triggering tenant-scoped side effects, or associating attacker-controlled payload content with another merchant's account. This crosses the tenant boundary the HMAC is meant to enforce, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any app merchant (an unprivileged, non-credentialed party relative to other tenants) can trivially obtain one legitimately signed webhook for their own shop and replay it with a modified `shop-domain` header — no access to `api_secret_key`, access tokens, or victim credentials is required. The only precondition is that the host application relies on `WebhookMetadata#shop` (sourced from `request.shop`) to determine which tenant's data to act on, which is the documented and expected usage pattern of this field.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) header values in the signable string used for HMAC verification, or otherwise cryptographically bind the tenant identity to the signature, so that changing the `shop-domain` header invalidates the HMAC. At minimum, `to_signable_string` should incorporate the shop domain so `HmacValidator.validate` cannot succeed for a payload whose `shop` value has been tampered with.

### Proof of Concept
1. Attacker registers/operates their own shop `attacker.myshopify.com` on the app and subscribes to a webhook topic.
2. Shopify sends the attacker a legitimately signed webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app secret), `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker resends this exact `(B, H)` pair to the app's webhook endpoint, but changes the header to `x-shopify-shop-domain: victim.myshopify.com`.
4. `Webhooks::Request.new` parses the tampered headers; `Utils::HmacValidator.validate` computes HMAC over `to_signable_string` (`= B` only) and it matches `H`, so validation succeeds: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and processes the attacker's payload as if it were a genuine event for the victim tenant.
