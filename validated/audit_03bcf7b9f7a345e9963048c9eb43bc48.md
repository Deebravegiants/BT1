### Title
Panic via unchecked fixed-size buffer write on Secp256k1 signature length in Tendermint light-client verification - (File: modules/consensus/tendermint/verifier/src/hashing.rs)

### Summary
`SpIoSignatureVerifier::verify` for the `PublicKey::Secp256k1` branch copies `signature.as_bytes()` directly into a fixed `[0u8; 65]` buffer via `sig_65_bytes[..64].copy_from_slice(raw_sig)` without first checking `raw_sig.len() == 64`. [1](#0-0) 

### Finding Description
`cometbft::Signature` is a generic, non-length-fixed byte container reconstructed from proof bytes submitted by an untrusted relayer via `cometbft::Signature::try_from(sig_bytes.as_slice())` in `CodecCommitSig::to_commit_sig` — this only validates the type is decodable, not that Secp256k1-path signatures are exactly 64 bytes long. [2](#0-1)  When such a `Signature` later reaches `SpIoSignatureVerifier::verify` during commit verification, `raw_sig = signature.as_bytes()` is copied unchecked into a fixed 64-byte slice of `sig_65_bytes`: any length other than exactly 64 causes `copy_from_slice` to panic (length-mismatch `assert_eq!` inside the standard library, i.e., an unchecked write against a stack-allocated fixed buffer) — the same underlying bug class as CVE-2017-11628 (fixed/stack buffer write driven by unvalidated parser input length). [3](#0-2)  The codebase has multiple prior fixes for exactly this pattern elsewhere (e.g. `modules/utils/serde/src/lib.rs`, `modules/ismp/core/src/host.rs`, `parachain/node/fisherman/src/lib.rs`), each explicitly noting that `copy_from_slice` panics on untrusted-length input and must be length-checked first — this call site was missed. [4](#0-3) [5](#0-4) 

### Impact Explanation
A panic inside runtime/off-chain worker code that verifies a Tendermint consensus proof is a denial-of-service on the code path that any unprivileged relayer can trigger by submitting a crafted consensus/commit proof containing a malformed Secp256k1 signature of a length other than 64 bytes. Depending on whether this executes inside a wasm runtime extrinsic handler (trap → node/relayer crash) or an off-chain prover/relayer process, this blocks delivery of legitimate consensus updates for that Tendermint-tracked chain, i.e. a route becomes unable to deliver messages.

### Likelihood Explanation
Reachable directly from a single submitted consensus proof/extrinsic containing an attacker-crafted signed header/commit for a Secp256k1-keyed validator; no privileged role is required. `Signature::try_from` performs generic decoding but does not enforce that bytes carried through the Secp256k1 verification path are exactly 64 bytes, so the trigger only requires supplying a signature byte string of any other length (shorter or longer) alongside an otherwise well-formed commit structure.

### Recommendation
Before the `copy_from_slice` call, validate `raw_sig.len() == 64` and return `signature::Error::MalformedSignature` otherwise, mirroring the length checks already applied at the other `copy_from_slice` call sites in this codebase (`modules/utils/serde/src/lib.rs`, `modules/ismp/core/src/host.rs`, `parachain/node/fisherman/src/lib.rs`).

### Proof of Concept
1. Construct a `CodecConsensusProof`/`CodecCommitSig::BlockIdFlagCommit` whose validator uses a `CodecPublicKey::Secp256k1` key and whose `signature` field contains a byte string of length ≠ 64 (e.g., 63 or 65 raw bytes, distinct from the `65`-byte length that would be produced by a correctly r||s||v-formatted signature elsewhere in the codebase).
2. `cometbft::Signature::try_from(sig_bytes.as_slice())` in `to_commit_sig` succeeds because it does not enforce a fixed length for this signature representation. [2](#0-1) 
3. Submit this as part of a consensus/commit verification call that reaches `SpIoSignatureVerifier::verify` for the Secp256k1 arm.
4. `raw_sig.len() != 64` causes `sig_65_bytes[..64].copy_from_slice(raw_sig)` to panic, aborting the verifying thread/process. [3](#0-2)
