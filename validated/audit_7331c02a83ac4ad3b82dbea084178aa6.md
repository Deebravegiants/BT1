### Title
POA Bridge withdrawal status matched only by `assetId`, causing tx-hash/status misreport in same-token batch withdrawals - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal()` looks up the on-chain settlement status of a specific withdrawal by matching entries returned for a NEAR transaction using only the withdrawal's `assetId`, not its destination address, amount, or index. When a single batch withdrawal (a feature explicitly supported by the SDK) contains two or more withdrawals of the *same* token to *different* recipients, this matching cannot disambiguate between them, so the SDK can report the wrong entry's `status`/`txHash` for a given `WithdrawalIdentifier`.

### Finding Description
`describeWithdrawal` fetches the full unsorted list of withdrawals for a NEAR tx hash and matches by asset only: [1](#0-0) 

The comment explicitly documents that index-based correlation was abandoned in favor of asset-based matching: "Response list is unsorted, so we match by assetId instead of index". A regression test confirms the matcher keys off `near_token_id` (derived from `assetId`) alone: [2](#0-1) 

The SDK's batch withdrawal feature builds one `WithdrawalIdentifier` per withdrawal request and calls `describeWithdrawal` independently for each, relying on the result being specific to that identifier's `index`: [3](#0-2) 

If two withdrawals in the same batch/NEAR tx share the same `assetId` (e.g., sending the same token to two different destination addresses, or the same token to the same address twice with different amounts — a normal, unprivileged usage pattern documented in the README's "Batch Withdrawals" section), `findMatchingWithdrawal` has no way to tell them apart. Both `WithdrawalIdentifier`s for that tx will resolve to the same (or an arbitrary) entry in the unsorted `response.withdrawals` array, so at least one identifier receives a `status`/`txHash` that actually belongs to the *other* withdrawal's on-chain settlement.

### Impact Explanation
This breaks the equality "status/txHash reported for withdrawal W == the actual on-chain outcome of withdrawal W." An integrator polling `waitForWithdrawalCompletion`/`describeWithdrawal` per withdrawal in a batch can be told withdrawal B is `"completed"` with a `txHash` that in fact corresponds to withdrawal A's transfer (or the reverse — A's completion is masked while B is still pending). Since integrators typically use "completed" + `txHash` as the signal to credit a user or close out an off-chain ledger entry, this can cause the integrator to credit/confirm the wrong withdrawal, matching the High-impact category of "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
This does not require any privileged or malicious actor — it is triggered by a normal caller using the SDK's documented batch-withdrawal capability to withdraw the same token to multiple destinations (or twice to the same destination) within one call. No admin, relayer, or bridge operator misbehavior is needed; the bug is purely in the SDK's own client-side matching logic.

### Recommendation
Disambiguate withdrawals using more than `assetId`: incorporate the batch `index` correlated against a stable per-withdrawal API field (e.g., match by `destinationAddress` + `amount`, or use whatever unique reference the POA bridge API returns per withdrawal within a tx), and fail closed (return `pending`/unknown rather than a possibly-wrong match) when multiple candidates share the same `assetId` and cannot be uniquely resolved.

### Proof of Concept
1. Call `sdk.processWithdrawal` (or the batch withdrawal API) with two withdrawal params in the same batch: same `assetId` (e.g., `nep141:usdt.tether-token.near`), different `destinationAddress` values (A and B).
2. Both withdrawals settle in the same NEAR transaction, producing two entries in the POA bridge's `getWithdrawalStatus` response for that tx hash, both sharing the same `near_token_id`.
3. Call `describeWithdrawal` for withdrawal-identifier index 0 (destination A) and index 1 (destination B).
4. Because `findMatchingWithdrawal` selects by `assetId` only (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:319-322`), both calls can resolve to the same array entry — e.g., destination B's identifier receives destination A's `transfer_tx_hash`/status, or the withdrawal that actually completed for B is reported as still `pending` while A's hash is duplicated.

*Note: I could not directly view the full body of `findMatchingWithdrawal` (only its call site and a test asserting `near_token_id`-based matching) due to reaching the tool-call limit, so I cannot rule out that it internally also uses `amount`/`destinationAddress` for further disambiguation. This should be verified against the actual implementation of `findMatchingWithdrawal` (referenced in both `poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) before treating this as fully confirmed.*

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}
