### Title
Webhook `shop` and `topic` are trusted for tenant routing without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from raw, unauthenticated HTTP headers, while `Utils::HmacValidator` (via `to_signable_string`) only computes/verifies the HMAC over the raw request body. `Registry.process` then forwards the header-derived `shop`/`topic` straight into `WebhookMetadata` for the app's handler to act on, even though those values were never bound by the HMAC check that "validated" the request.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate`/`validate_signature` compute the HMAC solely over that signable string [2](#0-1) . Meanwhile `Request#shop` and `Request#topic` are read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` and `shopify-topic`/`x-shopify-topic` headers [3](#0-2) , which are never included in the bytes that get HMAC-verified.

`Registry.process` calls `Utils::HmacValidator.validate(request)` and, if it passes, immediately trusts `request.topic` and `request.shop` to dispatch to the registered handler and populate `WebhookMetadata` [4](#0-3) . The equality that should hold is: `shop value bound by HMAC == shop value used to route/process the webhook`. In this implementation that equality does not hold — the HMAC only binds the body, not the shop/topic headers used for tenant identification and dispatch.

By contrast, the OAuth callback path in this same gem does this correctly: `AuthQuery#to_signable_string` includes `shop`, `host`, `code`, `state`, and `timestamp` in the signed payload [5](#0-4) , so the shop used to create the session in `Oauth.validate_auth_callback` is provably the one the merchant/Shopify authenticated [6](#0-5) . The webhook path has no equivalent binding for `shop`.

### Impact Explanation
An actor who controls (or has observed) any single legitimately-signed webhook body/HMAC pair — for example the operator of their own installed shop, who receives real webhooks from Shopify with a valid HMAC over the body — can replay that same body+HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for a different tenant. `HmacValidator.validate` will still return `true` because it never inspected those headers, and `Registry.process` will hand the forged `shop`/`topic` to the app's handler as `WebhookMetadata`. Any host application that uses `data.shop` from this metadata to look up sessions, write per-tenant data, or route processing (the documented and intended use of `WebhookMetadata`) will process attacker-controlled data under the wrong tenant identity — a cross-tenant confusion/injection primitive reachable by an unprivileged (or lightly privileged, e.g. self-installed-app) actor without needing the app's `client_secret` or any merchant's access token.

### Likelihood Explanation
Exploitation only requires the ability to send arbitrary HTTP requests to the app's public webhook endpoint and possession of one valid (body, HMAC) pair, which is trivially obtainable by installing the app on an attacker-controlled development store and capturing the resulting webhook call. No secret material or elevated privilege is required to forge the header values.

### Recommendation
Include `shop` (and ideally `topic`) as part of the signed/verified material for webhooks, or otherwise cryptographically bind the header-derived tenant identity to the verified body (e.g., verify `shop`/`topic` against Shopify's known webhook metadata via a secondary authenticated channel, or require the host app to cross-check `request.shop` against an existing, already-authenticated session before trusting it). At minimum, the library should not present `request.shop`/`request.topic` as "validated" data in `WebhookMetadata` immediately after a body-only HMAC check succeeds — the documentation and API should make explicit that these fields are unauthenticated and must be independently verified by the caller.

### Proof of Concept
1. Attacker installs the target app on their own store (`attacker-shop.myshopify.com`) and triggers a webhook (e.g. `orders/create`), receiving from Shopify a POST with body `B`, headers including `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's `client_secret`), and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays the exact same body `B` and HMAC `H` to the app's webhook endpoint, but changes the header to `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into `shop = "victim-shop.myshopify.com"`, `hmac = H` [7](#0-6) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `H` against `B` [8](#0-7) .
5. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes it as legitimate victim-shop data [9](#0-8) , despite the payload never having been authenticated for that tenant.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
