### Title
Cross-Asset Trust State Bleed in `ConnectedOrigins.add()` — Silent Escalation of dApp Address Exposure Without Re-Approval ([File: features/connected-origins/module/connections.js])

### Summary
The `connected-origins` module gates dApp access to wallet addresses behind a single `trusted` flag per origin, but `add()` allows the set of exposed `assetNames` to grow independently of that flag, and preserves `trusted` from the prior call whenever a new call omits it. This mirrors the reported ERC20 "shared allowance across functions" bug class: a single authorization state (`trusted`) is reused across unrelated actions (asset-scope changes) that were never individually re-approved by the user.

### Finding Description
`ConnectedOrigins.add()` is the single entry point used both to record the user's initial connection approval and to update the origin's connected asset list later on [1](#0-0) . When an origin record already exists, `trusted: trusted ?? value.trusted` preserves whatever trust value was previously granted if the caller does not explicitly pass `trusted` on this call [2](#0-1) . At the same time, `assetNames` for that origin are merged and grown via a `Set` union of the new call's `assetNames`/`connectedAssetName` and the previously stored ones [3](#0-2) .

This is confirmed by the test `updates accounts when new assets added`: an origin is first trusted only for `solana`, then a second `add()` call — passing no `trusted` flag — extends `assetNames` to `['solana', 'ethereum']`, and the origin's already-`trusted: true` status is carried over to expose Ethereum addresses as well [4](#0-3) . `isTrusted()` only checks the boolean flag, not which assets were consented to [5](#0-4) , and `getConnectedAccounts()` uses that same flag as the sole gate before returning addresses for every asset name currently associated with the origin (`connectedAssetName` + `assetNames`) [6](#0-5) .

In other words, the "approval" primitive (`trusted`) is not scoped to the specific asset/action that was approved — exactly the structural flaw described in the external report, where an ERC20 allowance intended for one function is silently reusable by a different function. Here, trust granted for one chain silently authorizes exposure of addresses for chains added afterward through the same `add()` call, with no code path shown that re-prompts the user specifically for the newly added asset.

### Impact Explanation
If any code path (e.g. connecting to an additional chain, or a dApp declaring more `assetNames` on a later interaction) invokes `connectedOrigins.add()` for an already-trusted origin without an explicit fresh `trusted: true`/re-approval semantics tied to the new asset, that origin gains silent access to wallet addresses for assets the user never explicitly approved exposing to it. This is a cross-asset/account privilege bleed: address disclosure the user did not consent to for that specific origin, undermining the per-origin/per-asset consent model that `connected-origins` is meant to enforce (its own README states it "maintains a list of the third-party websites that the user has authorized to interact with Exodus" [7](#0-6) ). Severity is bounded because the disclosed data is public wallet addresses, not secrets/keys, and no signing authorization is bypassed — this parallels the "Low" severity of the original Pool report.

### Likelihood Explanation
Exploitability depends entirely on which caller(s) invoke `add()` after the initial trust grant and whether they pass a fresh explicit `trusted` value tied to renewed user consent for the added asset. Within the module itself, no additional consent gate exists in `add()`/`#setAttributes()`; the merge logic unconditionally unions `assetNames` and defaults `trusted` to the previous value. I could not find, within the indexed code, the specific background/RPC call sites that invoke `connectedOrigins.add()` in production (they were not present in the indexed context — only test call sites were found), so I cannot confirm whether a production caller passes `assetNames` for a new chain without simultaneously re-confirming user approval. This is a genuine gap in my verification and should be checked directly in the browser-extension/web3-provider background handlers.

### Recommendation
Scope trust to the (origin, asset) pair rather than treating `trusted` as a single global per-origin flag that silently blesses any assets later merged into `assetNames`. Concretely:
- Require an explicit `trusted` decision (from a fresh user-approval flow) whenever `assetNames`/`connectedAssetName` gains any name not already covered by the existing approved scope, rather than defaulting to `trusted ?? value.trusted`.
- Track per-asset approval (e.g., a set of approved asset names) instead of a single boolean, so `getConnectedAccounts()` can gate exposure per asset rather than gating the whole record with one flag.
- Audit all production call sites of `connectedOrigins.add()` to confirm none of them expand `assetNames` for an existing trusted origin without a corresponding fresh user-approval popup for the new asset.

### Proof of Concept
Using the module's public API directly (as exercised by the existing test suite):
1. `connectedOrigins.add({ origin: 'evil.com', connectedAssetName: 'solana', assetNames: ['solana'], trusted: true })` — user approves connecting `evil.com` for Solana only.
2. Later, `connectedOrigins.add({ origin: 'evil.com', assetNames: ['solana', 'ethereum'] })` is invoked (e.g., triggered by the site or by an internal flow) without passing `trusted` [8](#0-7) .
3. Because `trusted` defaults to the previous `value.trusted` (`true`) and `assetNames` is unioned to include `ethereum`, `isTrusted({ origin: 'evil.com' })` still returns `true`, and `getConnectedAccounts({ origin: 'evil.com' })` now returns Ethereum addresses for every enabled wallet account [6](#0-5)  — data the user never explicitly approved sharing with `evil.com` when they only consented to a Solana connection.

  add = async ({
    connectedAssetName,
    origin,
    name,
    icon,
    assetNames = [],
    trusted,
    favorite,
    walletAccount,
  }) => {
    const value = await this.#getOrigin({ origin })

    const allConnectedAssetNames = new Set([
      connectedAssetName,
      ...assetNames,
      ...(value?.assetNames ?? []),
    ])

    if (value) {
      await this.#setAttributes({
        origin,
        attributes: {
          icon: icon ?? value.icon,
          name: name ?? value.name,
          connectedAssetName: connectedAssetName ?? value.connectedAssetName,
          trusted: trusted ?? value.trusted,
          favorite: favorite ?? value.favorite,
          assetNames: [...allConnectedAssetNames],
          walletAccount: walletAccount ?? value.walletAccount,
        },
      })

      return
    }

    await this.#addNewItem({
      origin,
      icon,
      name,
      connectedAssetName,
      trusted,
      favorite,
      assetNames: [...allConnectedAssetNames],
      walletAccount,
    })
  }

  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }
