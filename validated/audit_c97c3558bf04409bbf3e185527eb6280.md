### Title
Webhook `shop` identity is not covered by HMAC signature, allowing cross-tenant impersonation - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authenticated once `Utils::HmacValidator.validate(request)` succeeds, then hands `request.shop` to the app's handler as the trusted tenant identity. However, the HMAC is computed only over the raw body, never over the `shop` header, so the “verified” signature and the “acted-upon” shop identity are two different values with no cryptographic binding between them.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively from `to_signable_string`: [2](#0-1) 

`Registry.process` uses this validation as the sole authentication gate before dispatching the request, and then passes `request.shop` — read straight from the unsigned `shopify-shop-domain`/`x-shopify-shop-domain` header — into `WebhookMetadata` given to the app's handler: [3](#0-2) [4](#0-3) 

The identity binding the gem should enforce is: `hmac_valid(body, shop) == true` implies `shop` is authentic for that body. What is actually implemented is `hmac_valid(body) == true`, with `shop` read from an independent, unauthenticated header. Since the `api_secret_key` is per-app (shared across every shop that installs the app), any holder of one valid `(body, hmac)` pair — obtainable legitimately from a webhook delivered for their own shop — can resubmit the same body and hmac to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop domain. `Utils::HmacValidator.validate` still returns `true` because it never inspects the shop header, and `Registry.process` forwards the attacker-chosen shop straight to the handler as `WebhookMetadata#shop`, per the documented handler contract: [5](#0-4) 

The library's own documentation instructs handlers to key their business logic (enqueuing jobs, looking up store/session state, applying merchant-scoped side effects) on `data.shop`: [6](#0-5) 

Because `data.shop` is presented to the handler as having been "verified" (the whole point of calling `HmacValidator.validate` first), but is in fact unauthenticated attacker-controlled input, any handler that trusts it for tenant scoping is vulnerable to cross-tenant impersonation.

### Impact Explanation
An attacker who is a legitimate (even free/trial) merchant of the app can capture one authentic `(raw_body, hmac)` pair sent to their own webhook endpoint, then replay that exact payload to the app's webhook URL with the `shop` header rewritten to a victim's shop domain. The gem's `Registry.process` will accept it as valid and hand the forged shop identity to the handler, which per the gem's documented pattern uses `data.shop` to scope side effects (queuing jobs, updating merchant records, resolving the shop's session/access token). This crosses a tenant boundary using only the attacker's own credentials against another merchant's install — satisfying the High-impact bar for cross-tenant access.

### Likelihood Explanation
Likelihood is high for any app author who follows the gem's own documented usage pattern (`data.shop` used for tenant-scoped processing) without independently re-verifying the shop against the signed payload. No secret material, TLS interception, or privileged access is required — only an existing account/install of the same app, which is the minimum bar of an "unprivileged internet user" for a multi-tenant SaaS app.

### Recommendation
Bind the shop identity into the authenticated payload before dispatch: either include the `shop` header in the HMAC-signed material verified by `Utils::HmacValidator` (mirroring how `Auth::Oauth::AuthQuery#to_signable_string` includes `shop` in its signed params), or require handlers/`Registry.process` to independently cross-check `request.shop` against a shop value obtained from a source that is itself covered by the signature (e.g. embedding shop identity in the body and validating consistency), rejecting the webhook if they disagree.

### Proof of Concept
1. Register a webhook handler that, mirroring `docs/usage/webhooks.md`, enqueues work keyed on `data.shop` (e.g. `perform_later(shop_domain: data.shop, webhook: data.body)`).
2. As the attacker, install the target app on `attacker-shop.myshopify.com` and capture one legitimate webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Send a POST to the app's webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) validates successfully because it only checks `B` against `H`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) dispatches to the handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, causing the app to perform victim-shop-scoped actions triggered entirely by attacker-supplied body content.
