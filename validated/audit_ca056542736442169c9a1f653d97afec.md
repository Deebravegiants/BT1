### Title
`validateStellarAddress` accepts regex-shaped Stellar addresses with an invalid CRC16 checksum, letting corrupted addresses reach `HotBridge.createWithdrawalIntents` as `receiver` - (File: `packages/intents-sdk/src/lib/validateAddress.ts`)

### Summary
`validateStellarAddress` only checks the shape `G[A-Z0-9]{55}` and never verifies the base32 CRC16 checksum embedded in a real Stellar `StrKey` account ID [1](#0-0) . `HotBridge.validateWithdrawal` relies solely on this function to gate `destinationAddress` before building the withdrawal intent [2](#0-1) , and `createWithdrawalIntents` forwards the same unvalidated string as `receiver` to `this.hotSdk.buildGaslessWithdrawIntent` [3](#0-2) .

### Finding Description
The broken equality: "`validateAddress(destinationAddress, Chains.Stellar) === true`" should imply "`destinationAddress` decodes to a valid Stellar Ed25519 public key with a correct checksum". This repo already contains the correct checksum-verifying decoder, `stellarAddressToBytes`, which explicitly throws `"invalid checksum"` for a 56-char `G...` string that fails CRC16 verification [4](#0-3) , and this is proven by an existing unit test with a regex-matching-length address that still fails checksum verification [5](#0-4) . However, `validateAddress.ts`'s `validateStellarAddress` does not call this (or any) checksum routine — it is a pure regex test [1](#0-0) .

Exploit flow: an attacker (any NEAR Intents user, or a counterparty whose destination address string an integrator forwards) supplies a `destinationAddress` that is 56 characters, starts with `G`, and consists only of `[A-Z0-9]` — this passes the regex — but has a corrupted last few base32 symbols so the embedded CRC16 checksum does not match the payload. `HotBridge.validateWithdrawal` calls `validateAddress(...) === false` and, since the regex matches, does not throw `InvalidDestinationAddressForWithdrawalError` [2](#0-1) . Execution proceeds to the trustline check (`hotSdk.stellar.isTrustlineExists`) and then to `createWithdrawalIntents`, which builds and pushes an `mt_withdraw` intent with `receiver: args.withdrawalParams.destinationAddress` set to the corrupted address, without ever calling a checksum-validating decoder [6](#0-5) .

### Impact Explanation
If the downstream signing/broadcast path (inside `@hot-labs/omni-sdk`'s `buildGaslessWithdrawIntent`, or the Stellar-side bridge relayer) does not itself re-verify the checksum before submitting a real Stellar operation, funds would be routed to an address with no valid decodable public key, i.e., unrecoverable — this matches the Critical category ("funds delivered to a wrong address/chain/contract with no recovery"). The affected party is the withdrawing user whose intent is signed and submitted with a `receiver` value that this repo's own gate (`validateAddress`) should have rejected. This is repeatable per withdrawal call and requires no privilege beyond being a normal user submitting a withdrawal.

### Likelihood Explanation
The repo's own `validateAddress.ts` provides zero checksum verification for Stellar, and this is asserted only at the `validateWithdrawal`/`createWithdrawalIntents` boundary in `hot-bridge.ts` — no other guard in this file (`compareAddresses`, `assert` sanity checks on `intent.amounts`, `FeeExceedsAmountError`, `getUnderlyingFee`) checks address validity. Constructing such a bit-flipped-but-regex-matching address is trivial (flip any character in the last two base32 symbols encoding the checksum). Whether this actually reaches an irreversible on-chain transfer is contingent on the third-party `@hot-labs/omni-sdk`'s internal behavior (which is out of this repo's control and not verifiable from this codebase), but the validation gap itself — inconsistent with the checksum-aware `stellarAddressToBytes` already used elsewhere in the monorepo (e.g., `authIdentity.ts`) — is a concrete defect in this repo's responsibility boundary.

### Recommendation
Replace the regex-only `validateStellarAddress` in `packages/intents-sdk/src/lib/validateAddress.ts` with a check that also verifies the CRC16 checksum, e.g., by calling the existing `stellarAddressToBytes` (or Stellar SDK's `StrKey.isValidEd25519PublicKey`) and returning `false` if it throws, rather than relying on shape alone.

const validAddr = "GAXQC6TWRKQ4TK7OVADU2DQMXHFYUDHGO6JIIIHLDD7RTBHYHXPSNUTV";

const corruptedAddr = validAddr.slice(0, -1) + (validAddr.at(-1) === "V" ? "W" : "V");

it("BROKEN EQUALITY: regex accepts checksum-invalid Stellar address", () => {

  expect(() => stellarAddressToBytes(corruptedAddr)).toThrow("invalid checksum"); // proves it's not a real key
});

	async validateWithdrawal(args: {
		assetId: string;
		amount: bigint;
		destinationAddress: string;
		logger?: ILogger;
	}): Promise<void> {
		const assetInfo = this.parseAssetId(args.assetId);
		assert(assetInfo != null, "Asset is not supported");
		hotBlockchainInvariant(assetInfo.blockchain);

		if (
			validateAddress(args.destinationAddress, assetInfo.blockchain) === false
		) {
			throw new InvalidDestinationAddressForWithdrawalError(
				args.destinationAddress,
				assetInfo.blockchain,
			);
		}
		const nativeAsset = "native" in assetInfo;
		const token = nativeAsset ? "native" : assetInfo.address;
		if (
			!nativeAsset &&
			compareAddresses(token, args.destinationAddress, assetInfo.blockchain)
		) {
			throw new DestinationAddressMatchesTokenAddressError(token, args.assetId);
		}

		if (assetInfo.blockchain === Chains.Stellar) {
			const hasTrustline = await this.hotSdk.stellar.isTrustlineExists(
				args.destinationAddress,
				token,
			);

			if (!hasTrustline) {
				throw new TrustlineNotFoundError(
					args.destinationAddress,
					args.assetId,
					assetInfo.blockchain,
					token,
				);
			}
		}
	}

import { base32 } from "@scure/base";

export function stellarAddressToBytes(encoded: string): Uint8Array {
	if (typeof encoded !== "string") {
		throw new TypeError("encoded argument must be of type String");
	}

	const decoded = base32.decode(encoded);
	const payload = decoded.slice(0, -2);
	const data = payload.slice(1);
	const checksum = decoded.slice(-2);

	if (encoded !== base32.encode(decoded)) {
		throw new Error("invalid encoded string");
	}

	const expectedChecksum = calculateChecksum(payload);

	if (!verifyChecksum(expectedChecksum, checksum)) {
		throw new Error("invalid checksum");
	}

	return new Uint8Array(data);
}
