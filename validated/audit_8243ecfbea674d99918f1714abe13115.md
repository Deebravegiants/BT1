## Title
Webhook Shop/Topic Identity Spoofing Due to HMAC Covering Only the Raw Body, Not Headers - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The webhook `Request#to_signable_string` method used for HMAC verification returns only the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values — all derived from unauthenticated HTTP headers — are trusted and passed downstream to webhook handlers without being part of the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` is defined as: [1](#0-0) 

It returns only `@raw_body`. The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all read directly from HTTP headers with no cryptographic binding: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which computes the HMAC exclusively over `to_signable_string` (i.e., the raw body) and compares it to the `hmac` header via `OpenSSL.secure_compare`: [3](#0-2) 

After this check passes, `Registry.process` dispatches to the handler using the *unverified* `shop` and `topic` headers: [4](#0-3) 

This is the same bug class as the referenced report: a value that the application logic acts on (`bonding_curve.real_sol_reserves` there; `shop`/`topic` here) is not the value actually covered by the integrity check (`sol_escrow_lamports` there; the raw body HMAC here). The identity binding that should hold is:

`HMAC-verified content == content the handler trusts (shop, topic, webhook_id)`

but in reality only

`HMAC-verified content == raw_body`

while `shop`, `topic`, `webhook_id`, `api_version` are excluded and can be freely modified by anyone who can produce (or replay) a validly-signed body for *some* shop.

### Impact Explanation
Any actor who can obtain one genuine HMAC-signed webhook body for a given topic (e.g., by installing the app on their own store and receiving real webhook deliveries, which any unprivileged internet user offering the app installation can do) can replay that exact `raw_body` + `hmac` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for an arbitrary victim shop domain and/or the `x-shopify-topic` header for a different topic. Because `HmacValidator` never inspects headers, the signature check still succeeds, and `WebhookMetadata` is built with the attacker-chosen `shop` and `topic`: [5](#0-4) 

If the host application uses `data.shop` to select which tenant's records to update (a documented and expected usage pattern for this gem, e.g., writing to that shop's session/data store), this results in cross-tenant data corruption/injection: the attacker's own webhook payload gets attributed to and processed against a victim shop's tenant context. This satisfies the Critical "cross-tenant access" impact category, since it breaks the shop-to-payload identity binding across tenant boundaries using only unprivileged access (self-installing the app).

### Likelihood Explanation
Likelihood is high for any attacker capable of installing the app on their own shop (a normal, unprivileged action for any public Shopify app) — no access token, client secret, or privileged account is required. The only requirement is capturing one legitimately-signed webhook delivery for their own shop and replaying it with modified headers to the app's public webhook endpoint.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, and ideally `webhook_id`) in the HMAC-signed content, or otherwise cryptographically bind them (e.g., verify `shop` against the session/shop the webhook subscription was registered for). At minimum, `to_signable_string` should not allow verification to succeed for a body if the accompanying `shop`/`topic` headers were not the ones the signature was actually computed over by Shopify.

### Proof of Concept
1. Install the app on attacker-owned shop `attacker.myshopify.com`; trigger a real webhook (e.g., `orders/create`) and capture the raw request: `raw_body`, and header `x-shopify-hmac-sha256`.
2. Replay this exact `raw_body` and `hmac` header to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com` (and optionally a different `x-shopify-topic`).
3. `Utils::HmacValidator.validate(request)` in `lib/shopify_api/webhooks/registry.rb` line 190 returns `true` because it only checks `raw_body` against the HMAC header — the forged `shop-domain` header is never checked.
4. `Registry.process` dispatches `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: request.parsed_body, ...)` to the registered handler, which will act as if the attacker's payload came from `victim.myshopify.com`.
