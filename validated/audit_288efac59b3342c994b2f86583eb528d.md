### Title
Fake escrow credit from unchecked non-standard ERC20 `transfer` return value in `placeOrder` predispatch sweep drains other users' escrowed tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
In the Tron variant of `IntentGatewayV2.placeOrder`, the predispatch sweep-back step (moving swapped tokens from the `CallDispatcher` back to the gateway) credits the order's escrow ledger (`_orders[commitment][token] += reducedInputs[i].amount`) *before* verifying that the tokens actually arrived at the gateway's balance, and the underlying `transfer()` call is executed through `CallDispatcher.dispatch()`, which only checks that the low-level call didn't revert — it never checks the ABI-encoded boolean return value of `IERC20.transfer`. A token that returns `false` on failure instead of reverting (the same non-standard-ERC20 behavior class described in the referenced report) lets an attacker fabricate escrow credit for a token they never actually deposited into the gateway, which is later paid out of the shared token balance funded by *other* users' legitimately escrowed orders.

### Finding Description
`placeOrder`'s predispatch branch works as follows <cite repo="AYontt/hyperbridge--006" path="evm/tron/contracts/apps/IntentGatewayV2.sol" start="416="450" /> [1](#0-0) :

1. It computes `balance = IERC20(token).balanceOf(dispatcher)` and requires `balance >= requiredAmount`.
2. It builds a `Call` that will invoke `IERC20.transfer(address(this), balance)` **on the dispatcher's behalf**, to be executed later.
3. It immediately credits `_orders[commitment][token] += reducedInputs[i].amount` for every input token in the same loop, *before* the transfer call is ever executed.
4. Only after the loop finishes for all tokens does it call `ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls))` to actually perform the transfers.

`CallDispatcher.dispatch()` only reverts if the low-level `.call()` itself reverts [2](#0-1) :
```
(bool success, bytes memory result) = to.call{value: call.value}(call.data);
if (!success) revert CallFailed(to, result);
```
It never decodes/checks the returned `bool` from `IERC20.transfer`. Per ERC20 semantics, `transfer` is allowed to return `false` on failure instead of reverting — exactly the edge case the referenced report exploited against `ERC20Votes.transferFrom`. If `order.inputs[i].token` is such a non-standard token (attacker-supplied, since `order.inputs` is fully user-controlled input to `placeOrder`), the transfer silently fails: the gateway's real balance of that token never increases, yet `_orders[commitment][token]` is already credited with `reducedInputs[i].amount`.

This differs from the non-Tron `evm/src/apps/IntentGatewayV2.sol`, which snapshots `balancesBefore[i]` and sets `order.inputs[i].amount` to the *actual* balance delta after the dispatch call, so a silent-fail transfer results in `received == 0` and the escrow credited is `0` — no accounting break. The Tron variant omits this before/after balance reconciliation for the predispatch escrow path and trusts the pre-transfer `balanceOf(dispatcher)` reading to determine the amount to credit, then never re-verifies it against the gateway's own balance.

Because escrow is tracked per-commitment (`_orders[commitment][token]`) against a single pooled ERC20 balance held by the gateway contract, a fabricated credit for commitment A is fungible with real tokens deposited by other orders/users for the same `token`. When commitment A is later filled or cancelled, `_withdraw()` executes `IERC20(token).safeTransfer(beneficiary, amount)` out of the gateway's aggregate balance [3](#0-2) , paying the attacker with tokens that were actually escrowed by unrelated, legitimate orders.

### Impact Explanation
This allows direct theft of other users' escrowed ERC20 tokens held by the gateway: the attacker places a same-chain order with `predispatch.call` and `predispatch.assets` populated, using a non-standard (silently-failing) ERC20 as one of `order.inputs`. The false credit lets the attacker's commitment claim tokens it never deposited, and that claim is honored from the shared pool, draining balance backing other users' escrows for the same token. This is concrete theft of funds — Medium/High severity depending on token prevalence, matching the judged severity of the original ENS finding (Medium, "should fix" — contract security should not depend on external ERC20 behavior).

### Likelihood Explanation
Requires (a) a non-standard ERC20 token that returns `false` on `transfer` failure instead of reverting, and (b) the gateway holding co-mingled escrow for that same token from other legitimate orders at the time of exploitation. Both the ERC20MultiDelegate report and ENS judges accepted this as a valid "should fix"/Medium finding despite most real tokens reverting on failure — the same reasoning applies here since the Intent Gateway is explicitly designed to be token-agnostic (any ERC20 can be used as an order input) and does not restrict `order.inputs[i].token` to a known-safe allowlist.

### Recommendation
In the predispatch sweep-back loop of `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`, mirror the pattern already used in `evm/src/apps/IntentGatewayV2.sol`: snapshot `IERC20(token).balanceOf(address(this))` before dispatching `transferCalls`, execute the dispatch, then compute the actual received delta and only credit `_orders[commitment][token]` with the amount that was actually received (or revert if the delta is insufficient), instead of crediting based on the pre-transfer `balanceOf(dispatcher)` reading. Additionally, `CallDispatcher.dispatch()` or its callers should decode and check the boolean return value of `transfer`/`transferFrom` calls (or callers should use `SafeERC20`-style verification) rather than treating a non-reverting call as unconditional success.

### Proof of Concept
1. Deployer/attacker crafts `EvilToken`, an ERC20 whose `transfer()` always returns `false` (no revert) when called by the `CallDispatcher` (e.g. gated on `msg.sender == CallDispatcher` or a state flag), but functions normally elsewhere so `balanceOf`/`safeTransferFrom` from the attacker still succeed for the earlier escrow steps.
2. Attacker calls `placeOrder` with:
   - `order.predispatch.assets` containing some benign asset (or the same `EvilToken`) and `order.predispatch.call` a no-op/benign call satisfying the `>0` length checks.
   - `order.inputs[0] = {token: EvilToken, amount: X}`.
3. Inside `placeOrder`: `balance = EvilToken.balanceOf(dispatcher)` returns `>= X` (attacker funded the dispatcher via the predispatch legs). `_orders[commitment][EvilToken] += reducedInputs[0].amount` (≈X) is credited.
4. `ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls))` calls `EvilToken.transfer(address(this), balance)`, which returns `false` without reverting; `CallDispatcher` sees `success == true` from the low-level call and does not revert.
5. Gateway's real `EvilToken` balance is unchanged (transfer silently failed), but `_orders[commitment][EvilToken]` now shows a credit of `≈X` that is backed by nothing.
6. Attacker (or a colluding solver) fills/cancels this order; `_withdraw()` calls `EvilToken.safeTransfer(beneficiary, X)`, which succeeds by pulling `X` `EvilToken` tokens out of the gateway's pooled balance — i.e., out of other users' legitimately escrowed `EvilToken` orders — paying the attacker with funds they never deposited.
