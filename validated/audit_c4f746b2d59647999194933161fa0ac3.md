### Title
Webhook shop/topic/webhook-id spoofing via HMAC that only signs the raw body — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the webhook HMAC over the raw request body only, while the tenant-identifying fields (`shop`, `topic`, `webhook_id`, `api_version`) are read straight from HTTP headers that are excluded from the signed payload. `Registry.process` trusts these header-derived fields to select the handler and to construct the `WebhookMetadata` passed to app code, so the identity binding "HMAC-verified bytes == bytes acted upon" does not hold for the fields the app actually uses to attribute the event to a shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all pulled from headers (`shopify_header`), which are never included in `to_signable_string`: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `hmac` against `to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` uses the header-derived, unauthenticated `topic` to select the handler, and forwards the header-derived, unauthenticated `shop`, `api_version`, and `webhook_id` straight into `WebhookMetadata` given to the host app's handler: [4](#0-3) 

The equality that should hold is: `shop/topic bound by HMAC == shop/topic the handler acts on`. In reality, only the body is bound by the HMAC; `shop`, `topic`, and `webhook_id` are unauthenticated header values that a request forwarder/replayer can set independently of the signed body.

### Impact Explanation
Any merchant who installs the app can obtain one legitimately-signed webhook delivery for their own shop (e.g. via the Admin "send test notification" feature or by performing any action that fires a real webhook). Because the HMAC covers only the body, that same `(raw_body, hmac)` pair remains valid regardless of the `shop-domain`, `topic`, or `webhook-id` headers sent alongside it. An attacker who can deliver a request to the app's public webhook endpoint with the original body/HMAC pair but forged `shop-domain`/`topic` headers will pass `HmacValidator.validate` and have the handler process the payload as if it originated from an arbitrary shop and/or arbitrary topic (e.g. `app/uninstalled`), leading to cross-tenant data/state corruption or unintended privileged handler execution attributed to a victim shop. This lands in the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation requires the ability to deliver an HTTP request with attacker-controlled headers but a previously-captured legitimate `(body, hmac)` pair to the app's public webhook endpoint — something any installed merchant can obtain once and then replay/forward with modified headers, since nothing in this gem ties the header values to the signature. No access to `api_secret_key` or any credential is required, only observation of one legitimate webhook delivery.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed material, or otherwise cryptographically bind them to the body before trusting them in `Registry.process`/`WebhookMetadata`. At minimum, `to_signable_string` should incorporate `shop`, `topic`, and `webhook_id` so `HmacValidator.validate` actually authenticates the fields the handler dispatches and acts on.

### Proof of Concept
1. Merchant A (attacker) triggers any real webhook for their own shop, capturing `raw_body` and the resulting `x-shopify-hmac-sha256` value — both are validly signed by Shopify with the app's real secret.
2. Attacker sends a request directly to the app's public webhook endpoint reusing that exact `raw_body` and `hmac` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and `x-shopify-topic: app/uninstalled` (or any registered topic of the attacker's choosing).
3. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13-22`) succeeds because it only checks the (unchanged) body against the (unchanged) hmac.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) looks up the handler for the forged `topic` and invokes it with `shop: "victim-shop.myshopify.com"`, letting attacker-controlled body content be processed under the victim shop's identity.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
