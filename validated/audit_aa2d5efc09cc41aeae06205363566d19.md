## Title
Webhook `shop` and `topic` fields are trusted from unauthenticated HTTP headers while the HMAC signature only covers the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` directly from HTTP headers, but its `to_signable_string` implementation — the value that gets HMAC-verified — only returns the raw request body. This breaks the identity binding between "the bytes that were verified" and "the bytes that get acted upon," analogous to the range-check flaw in the reported finding: a field that governs processing (here, tenant identity via `shop`) is not covered by the cryptographic check that is supposed to guarantee its authenticity.

### Finding Description
`ShopifyAPI::Utils::VerifiableQuery` requires implementers to provide `hmac` and `to_signable_string`, and `HmacValidator.validate` computes the HMAC purely over `to_signable_string` and compares it to the `hmac` value: [1](#0-0) 

For the OAuth callback (`AuthQuery`), the signed string explicitly binds `shop`, `host`, `state`, `code`, and `timestamp` together: [2](#0-1) 

But for webhooks, `Webhooks::Request#to_signable_string` returns only `@raw_body`: [3](#0-2) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers, which are not part of the signed payload: [4](#0-3) 

`Webhooks::Registry.process` validates only the HMAC over the body, then dispatches the handler using the unauthenticated `request.shop` and `request.topic`: [5](#0-4) 

The equality that should hold is: `bytes verified by HMAC == bytes that determine tenant/topic routing`. In this implementation that equality fails — `to_signable_string` (verified) is `{ raw_body }`, while the value used for tenant identification and routing (acted upon) is `{ shop-domain header, topic header }`, which are disjoint from the verified set.

### Impact Explanation
Since the app's `client_secret`/`api_secret_key` is shared across every shop that has the app installed (it is not shop-specific), Shopify computes the webhook HMAC identically regardless of which shop triggered the event. Because `shop` is excluded from the signed content, a request with a valid HMAC for one shop's payload can be replayed with an arbitrary, attacker-chosen `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header value, and `HmacValidator.validate` will still report success — the app will then process the webhook `WebhookMetadata` believing it originated from a different, attacker-chosen tenant. This is a cross-tenant identity-confusion primitive: any handler that uses `WebhookMetadata#shop` to select which merchant's records to update/fetch can be misdirected to operate on the wrong tenant's data using a signature that was never bound to that tenant.

### Likelihood Explanation
Exploitation requires the attacker to be able to submit an HTTP POST directly to the app's public webhook endpoint with a valid `(raw_body, hmac)` pair and a forged shop-domain header. The attacker does not need the `api_secret_key`: any single genuine webhook delivery (e.g., one legitimately triggered on a shop the attacker administers, or a "send test webhook" payload) supplies a valid `(body, hmac)` pair that remains valid under any spoofed shop-domain/topic header, since neither is part of the signed content. This requires network reachability to the app's own publicly reachable webhook route — no leaked secret, TLS interception, or privileged account is needed, only a merchant/app-user capable of triggering (or observing) one webhook delivery for use in the replay.

### Recommendation
Bind `shop`, `topic`, `api_version`, and `webhook_id` into the value that is HMAC-verified, mirroring the `AuthQuery` approach, e.g. by including these header values (along with the raw body) in `to_signable_string`, or otherwise cryptographically binding the header-derived identity fields to the payload before they are trusted for routing/dispatch in `Webhooks::Registry.process`.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com`; attacker (as the merchant) triggers an event (e.g., creates an order) causing Shopify to deliver a webhook with body `B` and header `X-Shopify-Hmac-Sha256: H` to the app's public webhook endpoint, where `H = HMAC-SHA256(B, app_client_secret)`.
2. Attacker captures `(B, H)` (e.g., via Shopify's "send test notification" feature, or by controlling infrastructure that observes their own shop's outbound webhook).
3. Attacker issues a new POST to the same public webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com` (a shop they do not administer) and/or a different `X-Shopify-Topic`.
4. `ShopifyAPI::Utils::HmacValidator.validate` recomputes the HMAC over `to_signable_string`, which is only `B`; since `B` and `H` are unchanged, validation succeeds.
5. `Webhooks::Registry.process` dispatches the handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", topic: <attacker-chosen>, body: parsed_body, ...)`, causing the app to process data intended for `shop-a` under `shop-b`'s tenant identity, exactly analogous to the reported issue where a check that should bind the acted-upon field to a validated range was silently bypassed.
