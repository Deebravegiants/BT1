### Title
Webhook `shop` identity is not covered by the HMAC and can be forged - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's HMAC and then hands the caller-supplied `shop-domain` header, unauthenticated, to the app's handler as the trusted tenant identifier. The HMAC only signs the raw body, never the shop header, so the "which shop does this event belong to" binding is not cryptographically enforced.

### Finding Description
`Utils::HmacValidator.validate` computes the signature from `verifiable_query.to_signable_string`, and for webhooks `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no relation to the signed bytes: [2](#0-1) 

`Registry.process` verifies only the HMAC of the body, then trusts `request.shop` when building the object passed to the app's handler: [3](#0-2) 

The identity binding that should hold is `hmac(body, secret) == received_hmac AND shop == authenticated_shop_of(body, secret)`. In reality the code only checks `hmac(body, secret) == received_hmac`, and `shop` is taken from an out-of-band header that is never part of the signed material. This is exactly the "field acted on but not covered by the HMAC" pattern from the rules: the byte range that is cryptographically verified (`@raw_body`) is narrower than the identity data that downstream code (`WebhookMetadata.shop`) treats as authenticated.

The gem's own documentation confirms `data.shop` is meant to be trusted by host apps as "The shop domain of the webhook" and used directly for per-tenant actions (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [4](#0-3) 

### Impact Explanation
Any party capable of obtaining one genuine `(raw_body, hmac)` pair signed with the app's `api_secret_key` — for example a merchant who has legitimately installed the app on their own store and thus receives real webhook deliveries — can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header for a victim shop. Because the header is outside the signed scope, `HmacValidator.validate` still succeeds, and `Registry.process` forwards the forged shop identity to the handler as if Shopify had authenticated it for that shop. Any host app that keys per-tenant side effects off `data.shop` (exactly as the gem's own documented usage pattern instructs) can be induced to record, act on, or attribute another merchant's data/events to the wrong tenant — a cross-tenant confusion, matching the High-impact "scope or expiry/identity check bypass" category.

### Likelihood Explanation
No access token, `client_secret`, or privileged credentials are required beyond something an unprivileged internet actor can obtain: a normal app install on their own store gives them a valid signed webhook payload, and the app's webhook receiving endpoint is public by design so it can accept calls from Shopify. Constructing the replay request only requires copying the observed body and HMAC header while changing the shop-domain header, which is a low-effort, reliably reproducible action.

### Recommendation
Bind the shop identity into the material that is verified — e.g., include the `shop-domain` (and ideally `webhook-id`/`topic`) header value in `to_signable_string`, or otherwise cryptographically tie the claimed shop to the HMAC before it is trusted in `Registry.process`/`WebhookMetadata`. At minimum, document/require host apps to cross-check `data.shop` against a shop they already have an active session/installation record for before acting on the payload.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com`, triggers any webhook topic, and captures the raw POST body plus the `x-shopify-hmac-sha256` header Shopify sent — this HMAC is valid because it was produced by Shopify with the real `api_secret_key`.
2. Attacker replays the identical body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `HmacValidator.validate` recomputes the HMAC over `@raw_body` only and it matches, so `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker's own webhook body>, ...)`.
4. Any host-app logic that persists or acts on webhook data keyed by `data.shop` (per the gem's documented usage) now processes attacker-controlled data under the victim's tenant identity.

```ruby
        sig { params(request: Request).void }
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
```
