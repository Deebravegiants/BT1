### Title
Personal Custody Package (biometric identity data) is built and uploaded to self-custody storage regardless of fraud detection or enrollment outcome - (File: `src/plans/mod.rs`, `src/plans/personal_custody_package.rs`)

### Summary
The reported Concur bug is a class of "state not synchronized/wiped across two independent tracking systems," letting a user retain benefits from one system (`ConvexStakingWrapper.sol`) after being invalidated ("sheltered") in the authoritative system, because the two systems' state is not reconciled. The orb-core analog is that the Personal Custody Package (PCP) upload path — which persists a signup's full biometric identity material (iris codes, iris code shares, face embeddings, encrypted private keys) to self-custody backend storage — is entirely decoupled from the fraud/enrollment determination path. `signup_reason` is threaded through only as a descriptive tag embedded in the package metadata, never as a gate that prevents the upload.

### Finding Description
In `do_signup` (`src/plans/mod.rs`), fraud detection and signup outcome are computed first: [1](#0-0) 

Immediately after, regardless of `signup_reason` being `Fraud`, `Failure`, or `Normal`, the code unconditionally proceeds to build and upload the PCP (tiers 0/1/2) as long as `qr_codes.try_into()` succeeds: [2](#0-1) [3](#0-2) 

`build_pcp` passes `signup_reason` down into `personal_custody_package::Plan`, but its only use there is as a serialized string field (`signup_reason: &'a str`) embedded inside the encrypted package's `info.json`-equivalent metadata — it is not used to abort or block the upload: [4](#0-3) [5](#0-4) 

The actual outcome/gating (fraud vs success) is decided later and separately, either via the backend `enroll_user` call or, for `user_centric_signup`, locally without any backend call at all: [6](#0-5) 

Meanwhile fraud detection itself is a no-op in this build (`detect_fraud` always returns `false`, all checks removed): [7](#0-6) 

So the two "accounting systems" — (1) the self-custody biometric package storage, and (2) the enrollment/fraud verdict — are not reconciled: the PCP upload (biometric secret material) happens unconditionally and independently of whatever the fraud/enrollment path later decides, exactly analogous to the reported bug where `ConvexStakingWrapper.sol` balances kept earning `MasterChef.sol` rewards independent of the `Shelter.sol` invalidation because the two systems were never synchronized.

### Impact Explanation
A signup that is determined to be fraudulent, invalid, or otherwise rejected by the authoritative enrollment/fraud path still has its complete biometric identity package (iris codes/shares, face embeddings, encrypted private keys tied to `self_custody_user_public_key`) persisted to backend self-custody storage. This constitutes disclosure/persistence of biometric data for a signup that the system itself considers invalid, and creates cross-signup state bleed: self-custody-held biometric material exists for signups that should have been discarded, with no mechanism to retract/wipe it once fraud or failure is confirmed.

### Likelihood Explanation
This is reached on every signup attempt that produces valid QR credentials, regardless of `signup_reason`; no special conditions are required. Since local fraud checks are currently disabled entirely (`detect_fraud` hardcoded to `false`), practically every otherwise-fraudulent local signup proceeds straight to unconditional PCP build/upload, making the decoupling directly reachable in the current build.

### Recommendation
Gate the PCP build/upload behind the same determination used for the enrollment/fraud verdict (i.e., skip or defer the self-custody upload when `signup_reason != Normal`), or provide a reconciliation/wipe mechanism so that self-custody-held biometric packages for fraud/failed signups are retracted once the authoritative verdict is known — mirroring the report's recommendation to either prevent dual-state accrual or wipe state upon invalidation.

### Proof of Concept
1. Trigger a signup where `signup_reason` resolves to `Fraud` (e.g., a fraud check flags the pipeline output) or where `user_centric_signup` path is taken and later fails enrollment.
2. Observe that `do_signup` already called `build_pcp` and `upload_pcp_tier_0`/`data_uploader::Input::Pcp` for tiers 0–2 before the enrollment/fraud verdict was finalized, at `src/plans/mod.rs:574-636`.
3. Confirm `signup_reason` is only serialized into the package metadata (`src/plans/personal_custody_package.rs:124-146,197-209`) and never used to block the upload — the biometric package for the fraud/failed signup remains stored in self-custody backend infrastructure with no cleanup path tied to the later-determined verdict.
