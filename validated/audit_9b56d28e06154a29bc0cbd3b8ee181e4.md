### Title
Accrual arithmetic overflows before the borrow-index cap and permanently freezes a whale market - (File: `common/src/rates/simulate.rs`)

### Summary
A sufficiently large market can grow its scaled debt or supply value beyond `i128::MAX` before either index reaches `MAX_*_INDEX_RAY`. Every subsequent accrual panics in `scaled_to_original` before `update_borrow_index` or `update_supply_index` can apply their index ceilings. [1](#0-0) [2](#0-1) 

### Finding Description
`accrue_step` first unscales `borrowed * borrow_index` and `supplied * supply_index` to calculate utilization. [3](#0-2)  Both products use non-saturating RAY multiplication through `scaled_to_original`. [4](#0-3)  The borrow-index ceiling is applied only after those products have already succeeded. [2](#0-1)  Consequently, a market whose scaled RAY value reaches the `i128` ceiling before its index reaches the configured ceiling can never complete another accrual.

The mutating path is `Pool::update_indexes` → `ops::market::accrue` → `interest::global_sync` → `accrue_chunk` → `accrue_step`. [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7)  The controller exposes `update_indexes` permissionlessly, while withdrawals, repayments, and other market mutations also synchronize the market before applying their operation. [9](#0-8) [10](#0-9) 

The repository contains a production regression test demonstrating the condition: a very large 18-decimal market at sustained 98% utilization eventually fails `update_indexes` with `MATH_OVERFLOW`, while `borrow_index` remains below `MAX_BORROW_INDEX_RAY`. [11](#0-10)  The same test then shows supplier withdrawal and borrower repayment reverting with the same overflow. [12](#0-11) 

### Impact Explanation
Once the scaled RAY value crosses the `i128` product limit, every path that must accrue the market aborts before state is committed. Supplier withdrawals and debt repayments are therefore permanently unavailable for that market, and accrued yield or revenue cannot be processed through normal synchronized paths. [13](#0-12) [12](#0-11) 

This is permanent freezing of user funds, not merely a bounded execution-cost issue: the panic arises from value-domain arithmetic before the configured index cap can engage. [1](#0-0) [14](#0-13) 

### Likelihood Explanation
The condition requires a very large listed asset, permissive market caps, sustained high utilization, and enough elapsed time for index growth. The attacker does not need privileged access after the market is listed: one account can supply the debt asset and collateral, borrow the debt asset at high utilization, and leave the position to accrue. [15](#0-14) [16](#0-15) 

Market creation and caps are governed inputs, but the failing quantities are otherwise reachable through ordinary user positions; `max_cap_for_decimals` only ensures that an asset amount can be represented as RAY, not that `amount * index` remains representable after accrual. [17](#0-16)  The required scale and horizon make this a Medium-severity liveness failure rather than an immediate permissionless freeze.

### Recommendation
Do not unscale `borrowed` or `supplied` before checking whether the resulting index and value domain would exceed the safe product bound. At minimum:

- calculate the next borrow index with a saturating or division-based cap test, so the cap engages without multiplying two oversized `i128` values;
- add an explicit market value ceiling derived from `i128::MAX / max(index)` and reject further growth before `scaled_to_original`;
- if the cap is reached, transition the market to a defined saturated-index state rather than reverting every subsequent synchronization;
- preferably perform accrual intermediates in a wider integer type or decompose multiplication so a capped index never requires an overflowing product;
- add the existing whale-market regression as a permanent test for `update_indexes`, `withdraw`, `repay`, liquidation, revenue claims, and rate-model replacement.

### Proof of Concept
```text
1. Governance lists BIG18 with valid parameters, a high borrow-rate curve,
   and a cap large enough to admit an extremely large position.
2. A user calls Controller.supply with BIG18 and collateral in one account.
3. The user calls Controller.borrow for approximately 98% of the BIG18 pool.
4. Time advances while the market remains at high utilization.
5. Any caller invokes:
      Controller.update_indexes(caller, [HubAssetKey { hub_id, asset: BIG18 }])
   The pool reaches Cache::elapsed_ms() > 0, enters global_sync, and calls
   accrue_step.
6. accrue_step calls scaled_to_original(borrowed, borrow_index) or
   scaled_to_original(supplied, supply_index).
7. The scaled value exceeds i128::MAX, so the multiplication panics with
   MathOverflow before update_borrow_index can clamp to MAX_BORROW_INDEX_RAY.
8. Later Controller.withdraw and Controller.repay calls enter the same
   synchronization path and revert identically, leaving both supplied funds
   and debt processing frozen.
```

The checked-in reproduction is `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`, which seeds the large market, advances time until `try_update_indexes_for(["BIG18"])` fails, asserts the index cap did not engage, and then confirms that both withdrawal and repayment fail. [18](#0-17)

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);

/// Returns the largest cap, in asset base units, whose ray-scaled form still
/// fits in `i128`.
///
/// Returns 0 when `asset_decimals > RAY_DECIMALS`, since the ray form is not
/// representable in that case. Enforced by
/// [`require_cap_within_asset_domain`], so stored caps can never overflow the
/// asset→ray rescale.
pub fn max_cap_for_decimals(asset_decimals: u32) -> i128 {
    let Some(exp) = RAY_DECIMALS.checked_sub(asset_decimals) else {
        return 0;
    };
    let upscale = 10i128
        .checked_pow(exp)
        .expect("10^(RAY_DECIMALS - asset_decimals) fits i128 for asset_decimals <= RAY_DECIMALS");
    i128::MAX / upscale
}

/// Panics with `CollateralError::AssetDecimalsTooHigh` if `asset_decimals`
/// exceeds `RAY_DECIMALS`, or with `CollateralError::InvalidBorrowParams` if
/// `cap` exceeds the value returned by `max_cap_for_decimals`.
pub fn require_cap_within_asset_domain(env: &Env, cap: i128, asset_decimals: u32) {
    if RAY_DECIMALS.checked_sub(asset_decimals).is_none() {
        panic_with_error!(env, CollateralError::AssetDecimalsTooHigh);
    }
    assert_with_error!(
        env,
        cap <= max_cap_for_decimals(asset_decimals),
        CollateralError::InvalidBorrowParams
    );
