### Title
Direct LT donations to a graduated `Pair` are permanently unrecoverable — ([File: packages/contracts/src/Pair.sol])

### Summary
`Pair.sol` accepts `IERC20.transfer` deposits of the LT (`assetToken`) from anyone at any time, since it is a plain ERC20 balance with no deposit gate. The only extraction path for that asset balance is `Pair.transferAsset`, callable exclusively by `router` (`onlyRouter`), and `Router.graduate`/`Router.sell` are the only functions that invoke it, both gated to `BONDING_ROLE` held solely by `Bonding`. `Bonding` calls `Router.graduate` exactly once per token, from `_prepareGraduationLiquidity` during phase-1 graduation, draining only the curve-raised amount (`ltFromPair = storedAssetReserve - virtualLtReserve`) and deliberately leaving any donated LT behind. After a token reaches `Lifecycle.Graduated`, `Bonding.sell`/`Bonding.buy` are unreachable (trading is frozen on the curve permanently) and `Router.graduate` is never called again for that token — so any LT sent to the pair after (or even before, if undetected) graduation has no code path back out.

### Finding Description
`Pair.transferAsset` is the sole exit for LT held by a `Pair`: [1](#0-0) 

It is `onlyRouter`, and the only two `Router` functions that call it are `sell` (curve-only, requires `BONDING_ROLE`) and `graduate` (single-use, also `BONDING_ROLE`): [2](#0-1) 

`Bonding` only ever calls `Router.graduate` once, from `_prepareGraduationLiquidity`, and it drains exactly the curve-raised amount, not the pair's full LT balance — any LT sitting in the pair beyond `ltFromPair` (i.e., donated LT) is intentionally left behind: [3](#0-2) 

This is explicitly acknowledged in the project's own documentation as a trust assumption with no on-chain enforcement or recovery: donated LT "remains in the curve pair... reachable only via `Pair.transferAsset`... Both require `BONDING_ROLE`, which only `Bonding` holds. `Bonding` in turn only calls `graduate` from `_prepareGraduationLiquidity` — which is unreachable once the token's lifecycle has flipped past `Curve`." The docs candidly note this leftover is "unreachable as long as... future `Bonding` upgrades preserve the lifecycle gate" — i.e., under current code there is no function anywhere that can move this LT back out. [4](#0-3) 

Once a token graduates, all further trading of that token moves to the HyperSwap V2 pool through `Zap`; the original curve `Pair` is retired from any code path — `Bonding.buy`/`sell` gate on `Lifecycle.Curve` and revert once the token is `Graduating`/`Graduated`, and `Router.graduate` is a one-shot call already consumed. Consequently, any LT transferred directly into the `Pair` contract — whether before graduation (excluded from the graduation drain by design) or after graduation (when no function ever touches that pair again) — sits in the contract forever with zero code path to move it, exactly the "no function to return money" pattern from the external report, but for an ERC20 asset instead of native ETH.

This differs from the analogous risk in `FeeVault`, which the team explicitly hardened with a permissionless `sweepDonations()` to recover exactly this class of stray-donation exposure: [5](#0-4) 

No equivalent `sweep`/`rescue` function exists on `Pair`, `Router`, or `Bonding` for LT stuck in a post-graduation (or even pre-graduation-donation) `Pair`.

### Impact Explanation
Any LT sent directly to a `Pair` contract address is permanently and irrecoverably locked — this is a genuine, non-transient freezing of funds, not merely a design tradeoff with a pending mitigation. Since the LT is the reserve/backing asset (itself backed by real yield-bearing collateral via BounceTech), any amount donated or mistakenly sent is a total, permanent loss for the sender, with no owner-level, permissionless, or upgrade-gated recovery path exposed by the current contracts. The impact scales with the size of the donation and is unbounded in principle (any unrelated wallet can send LT to any `Pair` address at any time, including well after graduation).

### Likelihood Explanation
High reachability, low complexity: any unprivileged wallet holding the LT token can call `IERC20.transfer(pairAddress, amount)` directly — `Pair` addresses are public (`Factory.getPair`) and long-lived, so accidental transfers (wrong-address paste, wallet auto-complete, bot misuse) or intentional "donation" attempts are plausible over the pair's operational lifetime. The team's own comments show this scenario was considered and consciously left as a trust-assumption gap rather than mitigated with a sweep, unlike the parallel `FeeVault.sweepDonations()` precedent.

### Recommendation
Add a permissionless sweep function analogous to `FeeVault.sweepDonations()`, e.g. on `Router` (gated to a role, or fully permissionless like `FeeVault`), that computes `assetBalance() - trackedReserve` (and similarly for `launchedToken`) for a given pair and forwards the surplus to a fixed, admin-configured recipient (e.g., the protocol `feeTo`/treasury or, for pre-graduation curves, back to depositors is infeasible so treasury is the pragmatic target). This mirrors the existing `FeeVault` pattern and closes the "no function to return money" gap without touching the core AMM math or graduation invariants. For post-graduation pairs specifically, since `Bonding` never re-enters that pair, the sweep should not depend on the `Lifecycle.Curve` gate.

### Proof of Concept
1. Deploy/launch a token via `Bonding.launch`, obtaining `pairAddr` from `Factory.getPair(token, lt)`.
2. Any unrelated wallet calls `LT.transfer(pairAddr, X)` (a plain ERC20 transfer, no permission required).
3. Drive the token to graduation via ordinary buys until `Bonding.canGraduate()` fires and `finalizeGraduation` completes (`Lifecycle.Graduated`). `_prepareGraduationLiquidity` computes `ltFromPair = storedAssetReserve - virtualLtReserve` and calls `Router.graduate(token, ltFromPair)`, draining only the curve-raised amount — the donated `X` is untouched and remains in `pairAddr`. [6](#0-5) 
4. Post-graduation, attempt to locate any function across `Pair`, `Router`, `Bonding`, `Zap`, `Factory` that can move LT out of `pairAddr` for that token: `Pair.transferAsset`/`transferToken` are `onlyRouter`; `Router.sell`/`Router.graduate` are the only two callers of them and both require `BONDING_ROLE`; `Bonding.buy`/`sell` revert on a non-`Curve` lifecycle; `Router.graduate` for this token has already been consumed (single call in `_prepareGraduationLiquidity`) and nothing re-invokes it. `X` LT is now permanently stranded at `pairAddr` with no reachable withdrawal path in the current codebase.

    function sell(
        uint256 amountIn,
        address token,
        address to
    ) external onlyRole(BONDING_ROLE) returns (uint256 tokensIn, uint256 assetOut) {
        if (amountIn == 0) revert ZeroAmount();

        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();
        tokensIn = amountIn;

        IERC20(token).safeTransferFrom(to, pairAddr, amountIn);

        assetOut = _computeSell(pairAddr, amountIn);

        IPair(pairAddr).transferAsset(to, assetOut);

        IPair(pairAddr).swap(amountIn, 0, 0, assetOut);
    }

    function _computeSell(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 assetOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        uint256 newReserveToken = reserveToken + amountIn;
        assetOut = reserveAsset - (k / newReserveToken);
    }

    /// @notice Transfer exactly `amount` of LT out of the pair to the caller.
    ///         Called by `Bonding._prepareGraduationLiquidity` during graduation
    ///         with `amount = stored assetReserve - virtualLtReserve` (i.e. the
    ///         real LT raised by the curve, excluding the virtual seed).
    /// @dev    Donation-resistant: passing an explicit `amount` instead of
    ///         draining `assetBalance()` ensures any LT that was donated
    ///         directly to the pair via `IERC20.transfer` is left behind and
    ///         excluded from LP seeding.
    ///
    ///         "Locked" here is a trust-assumption claim, not an on-chain
    ///         guarantee. `Pair.transferAsset` is gated by `onlyRouter`, and
    ///         `Router` only exposes it via this function and `sell`. Both
    ///         require `BONDING_ROLE`, which only `Bonding` holds. `Bonding`
    ///         in turn only calls `graduate` from
    ///         `_prepareGraduationLiquidity` — which is unreachable once the
    ///         token's lifecycle has flipped past `Curve`. So the leftover
    ///         is unreachable as long as (a) `BONDING_ROLE` is not granted
    ///         to any other address, and (b) future `Bonding` upgrades
    ///         preserve the lifecycle gate.
    function graduate(
        address token,
        uint256 amount
    ) external onlyRole(BONDING_ROLE) {
        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();
        IPair(pairAddr).transferAsset(msg.sender, amount);
    }

    ///         direct USDC transfers would otherwise inflate `balanceOf` above
    ///         the accrual tally and silently mask the `accrue` underfund
    ///         check. Permissionless — funds always go to the admin-set `feeTo`.
    function sweepDonations() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        uint256 backed = $.totalAccruedCreator + $.protocolBalance;
        uint256 balance = $.usdc.balanceOf(address(this));
        if (balance <= backed) revert NothingToClaim();
        amount = balance - backed;
        address feeTo_ = $.feeTo;
        $.usdc.safeTransfer(feeTo_, amount);
