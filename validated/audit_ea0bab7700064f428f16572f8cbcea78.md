### Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) header is not covered by the HMAC, enabling cross-tenant webhook replay/spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable payload as the raw HTTP body only, while `shop`, `topic`, `webhook_id` and `api_version` are read directly from unauthenticated HTTP headers and then handed to the application's webhook handler as trusted metadata. Because these fields are outside the HMAC-protected payload, an attacker who can obtain (or produce) one validly-signed webhook body can replay it with a forged `X-Shopify-Shop-Domain` header, and `Utils::HmacValidator.validate` will still report success — causing the consuming application to process the payload under an attacker-chosen shop identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` (and `topic`, `webhook_id`, `api_version`) are pulled straight from headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC over the request (which only checks `raw_body`) and then dispatches `request.shop` straight into the handler metadata without any further binding check: [3](#0-2) 

`HmacValidator.validate` computes the HMAC only from `verifiable_query.to_signable_string`, i.e. `raw_body` in the webhook case, so `shop` never participates in the signature check: [4](#0-3) 

This breaks the identity binding `HMAC(secret, raw_body) == received_hmac` from also implying `shop-domain header == originating shop`. An attacker who has legitimate access to one shop (e.g., installs the app in their own store, which is unprivileged and self-service) can capture one genuine webhook (valid HMAC for its `raw_body`), then resend the exact same body to the app's webhook endpoint while substituting a victim shop's domain in the `X-Shopify-Shop-Domain` header. The HMAC check still passes (it only depends on `raw_body` and the shared secret), and `Registry.process` forwards `shop: request.shop` (the forged value) to `WebhookMetadata` and the handler, so the application believes the event originated from the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding break: the shop identity attached to webhook-driven business logic (e.g., updating merchant records, revoking access, syncing data keyed by shop) is not authenticated, only the request body is. Any consuming application that keys per-shop side effects off `WebhookMetadata#shop` (the documented/intended usage of this API) can be tricked into performing shop-A-authorized mutations against shop-B's data, which matches the "cross-tenant access" critical impact category.

### Likelihood Explanation
Exploitability requires only that the attacker be able to install the app on any shop they control (a normal, unprivileged action for any Shopify merchant) to obtain one genuinely-signed webhook body, then replay it with a forged `shop-domain` header to the app's public webhook endpoint. No access token, `api_secret_key`, or privileged account is required — the shared secret's role in the signature is unaffected because the body is replayed verbatim.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`/`api_version`) in the HMAC-protected/signable representation of the webhook request, or otherwise cryptographically bind the shop domain to the payload before trusting it in `Registry.process`/`WebhookMetadata`. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must be cross-checked by the host application against a known/allow-listed shop list before being used for any authorization decision.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger a webhook event, capturing `raw_body` and the valid `x-shopify-hmac-sha256` header Shopify sent.
2. Replay the same `raw_body` and `hmac` header to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request whose `shop` returns `"victim.myshopify.com"`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates successfully since it only hashes `raw_body`: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and processes the (attacker-supplied) body as though it came from the victim shop.

            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
