### Title
Attacker-controlled swap route can execute arbitrary contract code that steals caller wallet assets - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
Controller strategy entrypoints such as `swap_collateral` accept caller-supplied `swap` bytes and forward them to the configured router, while authorizing only the controller’s input-token transfer to the router. [1](#0-0)  The router decodes payload-selected pool addresses and invokes those contracts through venue adapters without an allowlist. [2](#0-1)  A malicious payload can therefore place attacker-deployed code inside the transaction’s authorization tree and cause the caller to sign an unrelated wallet-token transfer. [3](#0-2) 

### Finding Description
`swap_collateral` authenticates the caller and verifies account ownership or delegation, but it does not decode or restrict the supplied route. [4](#0-3)  The shared `swap_tokens` helper only takes balance snapshots, authorizes one exact input transfer from the controller to the configured router, and calls `execute_strategy` with the raw `swap` payload. [5](#0-4)  That payload supplies the router’s asset registry, including the `pool` address used for every hop. [6](#0-5)  Dispatch then selects a venue and invokes the attacker-selected pool contract; for example, the Soroswap adapter calls `get_reserves` and `swap` on `hop.pool`. [7](#0-6) 

The post-call checks measure only the controller’s input spend and positive output receipt. [8](#0-7)  They do not prevent route code from requesting an additional authorization from the original caller while the transaction is being simulated. [9](#0-8)  The repository’s regression test demonstrates a rogue hop pool calling `token.transfer(victim, attacker, WALLET_BALANCE)` and that transfer being recorded as a child authorization under the victim’s `swap_collateral` entry. [10](#0-9) [11](#0-10) 

### Impact Explanation
An unprivileged attacker can construct a route whose venue contract performs arbitrary token-transfer authorization requests against the victim, rather than merely executing an economically poor swap. [12](#0-11)  If the victim signs the simulated authorization tree, the malicious contract can drain assets completely unrelated to the lending position, while still returning the expected output so the strategy completes successfully. [13](#0-12)  This is theft of user funds and is not bounded by the supplied collateral amount, route minimum output, controller balance-delta checks, or final health-factor validation. [8](#0-7) 

### Likelihood Explanation
The attacker needs no privileged role because `swap_collateral`, `multiply`, `swap_debt`, and `repay_debt_with_collateral` all accept route bytes through user-facing strategy entrypoints. [14](#0-13)  Exploitation requires the victim to submit or sign a malicious route and to approve the expanded authorization tree, so wallet and client-side signing behavior determines practical reachability. [15](#0-14)  The demonstrated transaction remains valid because the rogue transfer is attached beneath the victim’s existing authorization entry and executes after that tree is signed. [16](#0-15) 

### Recommendation
Do not allow arbitrary pool or venue contract addresses in routes that execute under a caller-facing authorization context. [2](#0-1)  Maintain an on-chain allowlist of deployed venue contracts and verify `hop.pool` before dispatch, or constrain routes to immutable venue adapter deployments that cannot request unrelated caller authorizations. [17](#0-16)  In addition, controller clients should simulate the complete transaction, decode the route, and reject any authorization tree containing children other than the expected router input transfer. [9](#0-8) 

### Proof of Concept
1. Deploy a contract exposing the venue functions expected by the selected adapter, such as `get_reserves` and `swap`. [18](#0-17) 
2. Inside that contract’s `swap` method, call `token.transfer(victim, attacker, victim_balance)` for an unrelated wallet token. [10](#0-9) 
3. Have the malicious contract pay enough `token_out` to satisfy the route’s declared minimum and return normally. [19](#0-18) 
4. Encode that contract address as the hop pool in a `StrategyPayload` whose `token_in` and `token_out` are accepted collateral assets. [2](#0-1) 
5. Ask the victim to call `swap_collateral(caller, account_id, current, amount, new, swap)` with that payload. [20](#0-19) 
6. During simulation, Soroban records the unrelated wallet transfer as a child invocation under the victim’s controller authorization entry. [9](#0-8) 
7. Once the victim signs that authorization tree, the transaction succeeds: the victim loses the unrelated wallet-token balance, the attacker receives it, and the account still receives the expected swapped collateral. [13](#0-12)

        no_args,

        (reserve_0, reserve_1)

    env: &Env,
    router: &Address,

    amount_in: i128,
    tokens_cache: &mut Map<Address, Vec<Address>>,

    let ctx = HopContext::new(env, router, hop, amount_in);
    let before_in = ctx.input_balance();

    match hop.venue {
        SwapVenue::Soroswap => soroswap::swap(&ctx),
        SwapVenue::Aquarius => aquarius::swap(&ctx, tokens_cache),
        SwapVenue::Phoenix => phoenix::swap(&ctx),
        SwapVenue::Sushi => sushi::swap(&ctx),
        SwapVenue::CometDex => comet::swap(&ctx),
