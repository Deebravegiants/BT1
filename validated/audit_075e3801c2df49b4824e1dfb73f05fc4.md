### Title
Unfunded `repay`/`recapitalize` overpayment refund is paid out of supplier custody without measuring inbound tokens - (File: contracts/pool/src/ops/repay.rs)

### Summary
The pool computes the repay "overpayment" refund from the *declared* `action.amount`, not from tokens actually received, and pays it to `payer` via `transfer_out` without debiting `cash` or passing `require_reserves`. On a market with zero debt, the entire declared amount is classified as overpayment and refunded out of the pool's real token custody — suppliers' cash — to an arbitrary caller. The identical pattern exists in `ops::recapitalize::apply` (`refund = amount - applied`, refunded out of custody). This is the direct analog of CVE-2021-4157's small out-of-bounds write: the contract "writes" (transfers) tokens beyond the bounds of what was actually deposited, letting an attacker reach past the received buffer into unrelated supplier funds.

### Finding Description
`resolve_repay` takes the full-close branch whenever `amount >= current_debt_ceil` and returns `overpayment = amount - current_debt_ceil` [1](#0-0) . In `ops::repay::accounting`, `net_repay = amount - overpayment` is credited to cash, `burned` shares are removed, and — critically — the zero-share guard passes on its `net_repay == 0` disjunct, so a repay against a market with no debt is accepted with `net_repay = 0` and `overpayment = amount` [2](#0-1) . `ops::repay::apply` then calls `outcome.cache.transfer_out(payer, outcome.overpayment)` [3](#0-2) , sending real tokens from the pool's custody to `payer`. No balance-delta measurement verifies that `amount` was ever transferred in; the doc comment assumes "the controller transfers the repay amount into the pool before this call" [4](#0-3) , but the pool itself enforces nothing.

The repo's own test proves the hole: `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` calls `client().repay(&payer, &t.ract(0, custody_before))` with "nothing transferred in, no debt to retire" and asserts the refund drains custody while the book is untouched [5](#0-4) . `ops::recapitalize::accounting` computes `refund = amount - applied` and `apply` transfers it to `payer` the same way [6](#0-5) .

### Impact Explanation
Theft of user funds / protocol insolvency. An attacker calls `repay` (or `recapitalize` with `amount` above the backing shortfall) with `amount` equal to the pool's token balance on a market with zero outstanding debt. The full `amount` becomes `overpayment` and is transferred to the attacker out of supplier deposits, while `cash` and share accounting are unchanged — books show full liabilities but custody is drained, so honest withdrawals fail (permanent freezing/insolvency for remaining suppliers). The attacker's `payer` argument is self-controlled, so `require_auth` on `payer` (if any) is satisfied by the attacker's own signature; the refund is bounded only by the token balance the pool holds.

### Likelihood Explanation
High if the pool entrypoints are reachable by arbitrary callers. The pool test-suite calls `client().repay` directly with a generated address [7](#0-6) , and neither `repay::accounting` nor `recapitalize::accounting` checks an inbound balance delta or a controller-caller allowlist in the code shown — they trust the declared `amount`. Uncertainty: I could not confirm within the iteration budget whether `contracts/pool/src/lib.rs` adds a controller-only guard on the `repay`/`recapitalize` entrypoints; if such a guard exists, exploitability narrows to paths where the controller invokes these without enforcing prefunding (e.g., strategy/liquidation refund flows), which still leaves the refund unfunded whenever measured inbound < declared `amount`. Even then, the accounting assumption is fragile — any caller path that reaches `repay` without a prior transfer of exactly `amount` drains custody.

### Recommendation
Measure, don't declare: in `ops::repay::apply` and `ops::recapitalize::apply`, record the pool's token balance before and after the expected inbound transfer (or require the controller to pass the measured received amount), and cap `overpayment`/`refund` at `measured_in - net_applied` rather than `declared - net_applied`. Alternatively, restrict `repay`/`recapitalize` to the controller address and make the controller transfer exactly `debt_ceil`/`shortfall` (not the user-declared `amount`) before the call. At minimum, `transfer_out` of any refund should debit `cash` or be gated by `require_reserves` so refunds can never exceed received funds.

### Proof of Concept
```rust
// Pool client, called directly (or via any path that reaches repay without prefunding).
// Precondition: market (hub, asset) has cash > 0 in custody and borrowed == 0.
let attacker = Address::generate(&env);
let custody = token.balance(&pool);          // e.g. 50_000 USDC base units
// Declare amount = custody. current_debt_ceil == 0 → overpayment = amount,
// net_repay = 0 → RepayRoundsToZeroShares assert passes via net_repay == 0.
pool.repay(&attacker, &vec![&env, PoolAction {
    hub_asset, position: Ray::ZERO, amount: custody, ..Default::default()
}]);
// ops::repay::apply → transfer_out(attacker, custody): entire supplier
// balance moves to attacker; state.cash unchanged → books insolvent.
assert_eq!(token.balance(&pool), 0);
assert_eq!(token.balance(&attacker), custody);
```

```rust
/// A repay against a market with no debt makes the entire declared amount an
/// overpayment: `current_debt_ceil` is zero, so `resolve_repay` takes the
/// full-close branch and `net_repay` is zero. The `RepayRoundsToZeroShares`
/// assert in `ops::repay::accounting` passes on its `net_repay == 0` disjunct,
/// and the whole amount is refunded out of real custody with the book untouched.
#[test]
fn test_unfunded_repay_overpayment_refund_also_pays_out_of_custody() {
    let t = TestSetup::new();
    let token = token::Client::new(&t.env, &t.asset);
    let payer = Address::generate(&t.env);

    let custody_before = token.balance(&t.pool);
    let before = t.state_snapshot();
    assert_eq!(
        before.cash, custody_before,
        "fixture guard: book and custody must start in sync"
    );
    assert_eq!(before.borrowed, 0, "fixture must carry no debt");

    // Nothing transferred in, no debt to retire: the whole amount is "excess".
    let credited = t
        .client()
        .repay(&payer, &t.ract(0, custody_before))
        .get_unchecked(0)
        .actual_amount;
    assert_eq!(credited, 0, "no debt was retired, so nothing is credited");
    assert_unfunded_refund_drained_custody(&t, &payer, custody_before, &before);
```
