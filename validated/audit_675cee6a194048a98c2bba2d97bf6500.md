### Title
Webhook shop attribution is not covered by HMAC verification, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
### Finding Description
`ShopifyAPI::Webhooks::Request` computes its signable string using only the raw request body: [1](#0-0) 

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
```

The `shop` attribute that identifies which tenant a webhook belongs to is instead read directly, and unauthenticated, from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header: [2](#0-1) 

```ruby
sig { returns(String) }
def shop
  T.cast(shopify_header("shop-domain"), String)
end
```

`ShopifyAPI::Webhooks::Registry.process` verifies the request purely through `Utils::HmacValidator.validate(request)`, which — per `HmacValidator#validate_signature` — hashes `request.to_signable_string` (i.e., just `@raw_body`) with the app's `api_secret_key` and compares it to the `hmac-sha256` header: [3](#0-2) 

```ruby
sig { params(request: Request).void }
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

The broken identity binding is: `hmac-verified bytes (raw_body only)` ≠ `shop identity acted upon (shop-domain header, passed unauthenticated into WebhookMetadata.shop and handed to the app's handler)`. The `topic`, `api-version`, and `webhook-id` headers are similarly excluded from the signed data.

Because the app's `api_secret_key` is a single, per-app (not per-shop) secret, any store that installs the app can receive at least one legitimately HMAC-signed webhook body for its own shop. That exact `(raw_body, hmac-sha256)` pair remains valid for signature verification regardless of which `shop-domain` header accompanies it, since the header is never part of the signed payload. This is exactly the report's bug class: a value used downstream for per-tenant identification/actions is not covered by the integrity check that gates those actions.

### Impact Explanation
An attacker who has installed the app on their own store (an ordinary, unprivileged action requiring no special access) can capture one genuinely signed webhook `(raw_body, hmac)` pair for their own shop, then replay it directly to the app's public webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop's domain. `Utils::HmacValidator.validate` still passes because it only checks the body hash, and `Registry.process` will dispatch `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` to the host app's handler, exactly as documented in `docs/usage/webhooks.md`. This causes attacker-controlled event data to be attributed to (and processed under) a different tenant's shop identity — a cross-tenant data-integrity/authentication violation, satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
The attack requires only: (1) a normal app installation on an attacker-controlled store to obtain one valid `(body, hmac)` pair, and (2) the ability to send an arbitrary HTTP POST with custom headers to the app's own webhook endpoint (not through Shopify's proxy) — both are trivially available to any unprivileged internet user. No access token, `api_secret_key`, or privileged account is required, and no host-application misuse of the documented API is needed; the exact documented `Registry.process(Request.new(...))` flow is affected.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) in the HMAC-signed payload construction — or independently re-verify the `shop-domain` header against a known/authorized shop list before dispatching to the handler — rather than trusting header values that are entirely outside the HMAC's coverage. At minimum, document prominently that `request.shop`/`request.topic` are unauthenticated and require independent verification by the host application before being trusted for tenant routing.

### Proof of Concept
1. Install the target app on an attacker-owned development store `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw POST body `B` and its valid `x-shopify-hmac-sha256` header `H` (computed by Shopify over `B` using the app's shared `api_secret_key`).
2. Send a new HTTP POST directly to the app's webhook endpoint with:
   - Body: the exact same `B`
   - Headers: `x-shopify-hmac-sha256: H`, `x-shopify-topic: orders/create`, `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (== `B`) and matches `H` — validation succeeds.
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", body: JSON.parse(B), ...)`, causing the host app to process/store attacker-supplied data as belonging to `victim-shop.myshopify.com`.
