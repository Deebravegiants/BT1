### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only [1](#0-0) , while the `shop` (tenant identity), `topic`, and `webhook_id` fields are read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only the body's HMAC and then dispatches the handler using the unverified `shop` header value [3](#0-2) . This is the same class of bug as the reference report: a field that is acted upon (here, `shop`, used to attribute the webhook payload to a tenant) is not bound by the cryptographic authenticity check (the HMAC), so it can be swapped independently of the verified data.

### Finding Description
The equality the library should enforce is:

`shop-that-produced-the-HMAC-signed-body == shop-attributed-to-the-processed-webhook`

`Utils::HmacValidator.validate` verifies only `verifiable_query.to_signable_string`, and for webhooks that string is `@raw_body` alone [4](#0-3) [1](#0-0) . The `shop`, `topic`, and `webhook_id` values are pulled straight from HTTP headers with no cryptographic binding to the signed body [5](#0-4) .

`Registry.process` then trusts these header-derived values to build the `WebhookMetadata` object passed to the host application's handler: [3](#0-2) 

Because `shop` is never included in the signed bytes, two different (body, hmac) pairs and two different `shop` header values can be freely recombined by anyone who is able to obtain one legitimately-signed webhook delivery (e.g., an attacker's own store that has the target app installed, since a single app typically shares one `client_secret` across all merchant installs). The attacker takes a genuinely-signed webhook body+HMAC from their own tenant and re-POSTs it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. `HmacValidator.validate` still passes (it only checks the body against the shared secret), and `Registry.process` calls the handler with `shop: <victim-shop>` while `body` is really the attacker's own data.

### Impact Explanation
This lets an unprivileged internet user (any merchant with the app installed) inject data that the host application will process as if it originated from a shop they do not control, since `shop` is the identity fields host apps rely on to scope credentials, data stores, or side effects for a given tenant. This crosses the tenant boundary this gem is responsible for asserting when it validates and returns webhook authenticity, which maps to the required "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to have at least one legitimately-signed webhook delivery for the shared app secret (trivially available to anyone who installs the app on their own development/test store and receives any webhook), plus the ability to POST arbitrary headers to the app's own public webhook endpoint. No access token, `client_secret`, or privileged credential is required — only normal, unprivileged app installation.

### Recommendation
Bind the tenant/topic identity into the signed material the gem verifies, or otherwise cryptographically tie the `shop`/`topic`/`webhook_id` headers to the payload before trusting them in `Registry.process`. At minimum, `Webhooks::Request#to_signable_string` should incorporate `shop`, `topic`, and `webhook_id` (or the registry should independently confirm the delivered `shop` matches a shop for which the corresponding webhook subscription/topic combination was actually registered) before dispatching to the handler.

### Proof of Concept
```ruby
# Attacker owns shop "attacker.myshopify.com" with the app installed.
# Shopify sends a legitimately signed webhook for it:
raw_body = '{"id":123,"note":"attacker-controlled payload"}'
hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), Context.api_secret_key, raw_body)
).strip

# Attacker replays the same (body, hmac) to the app's public webhook endpoint,
# but swaps the shop-domain header to a victim shop they do not control.
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # <-- not covered by HMAC
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) passes (body signature is valid),
# handler.handle receives WebhookMetadata with shop: "victim-shop.myshopify.com"
# even though the payload actually came from the attacker's own store.
``` [3](#0-2)
