### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing tenant identity spoofing on an otherwise-authentic webhook - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the raw HTTP body against the `X-Shopify-Hmac-Sha256` header via `HmacValidator.validate`. The `shop` value that is subsequently trusted and handed to the app's handler (used for tenant identification/routing) is read from the `shopify-shop-domain` HTTP header, which is never included in the HMAC-signed payload. This breaks the intended identity binding: `shop authenticated by HMAC` ≠ `shop trusted by the handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

`shop` is read independently from an HTTP header that carries no cryptographic binding to the signed body: [2](#0-1) 

`HmacValidator.validate` verifies only `verifiable_query.to_signable_string` (the body) against the secret; it never incorporates `shop`, `topic`, or any other header into the signature computation: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`/`request.webhook_id`) as authenticated tenant metadata, passing it straight into the handler: [4](#0-3) 

Consequently, `HmacValidator.validate` proves only that "this body was signed by our secret at some point in the past" — it says nothing about which shop it was signed for. There is also no timestamp/nonce/replay protection in `validate`, so a `(body, hmac)` pair remains valid indefinitely.

Documented consumer code demonstrates the trust placed in `data.shop` (e.g., using it to key background jobs, `shop_domain: data.shop`), i.e., host apps are expected to use this value as the tenant key: [5](#0-4) 

### Impact Explanation
An unprivileged internet user who is able to obtain any single legitimate `(raw_body, hmac)` pair for the target application — e.g., by installing/uninstalling the app on their own store, or observing/replaying a webhook they legitimately received — can resubmit that exact body/HMAC combination to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. Because `HmacValidator.validate` never binds `shop` to the signed content, the forged request passes validation and is delivered to the handler labeled as coming from an arbitrary (attacker-chosen) shop. Depending on how the host app keys tenant state off `WebhookMetadata#shop` (session lookup, per-tenant background jobs, `shop/redact`/`customers/redact` compliance actions, cache invalidation, etc.), this enables cross-tenant data confusion or triggering of shop-scoped app logic under a victim's identity — matching the "cross-tenant access" class of impact.

### Likelihood Explanation
Medium-High: no attacker-controlled forgery of the HMAC itself is required (the secret is never learned), only reuse of one authentic (body, hmac) pair with a swapped header — attainable by any developer who can install the target app on a store they control and capture their own webhook traffic. There is no nonce/replay window enforced by this gem, so the captured pair is reusable indefinitely.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived shop to the signed body (e.g., include them in `to_signable_string`, or independently validate `shop` against `ShopValidator` plus corroborate it against a value obtained through an already-authenticated channel, such as the session/access-token store keyed by shop). At minimum, document/enforce that `request.shop` must not be treated as authenticated by the HMAC check alone, and add replay protection (timestamp/nonce or webhook-id de-duplication window) to `HmacValidator`.

### Proof of Concept
1. Register the app on an attacker-owned dev store; trigger any webhook topic (e.g. `orders/create`) to capture a legitimate `(raw_body, X-Shopify-Hmac-Sha256)` pair addressed to `attacker-shop.myshopify.com`.
2. POST directly to the app's public webhook endpoint with the same `raw_body` and `X-Shopify-Hmac-Sha256`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` (via `Registry.process`) succeeds because it only checks `raw_body` against the HMAC: [6](#0-5) 
4. The handler receives `WebhookMetadata` with `shop == "victim-shop.myshopify.com"` even though the payload was never actually generated or signed for that shop, demonstrating the broken binding between the authenticated (signed) content and the trusted tenant identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
