## Title
Session hijacking via unsigned, predictable session-id cookie trusted by `SessionUtils.cookie_session_id` - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
For non-embedded apps, this gem sets the persistent session cookie's *value* to the deterministic session id (`shop_userid` or `offline_shop`) with no signature or encryption, and later blindly trusts whatever value is present in that cookie as the authoritative session identifier. Because the session id is derived from public/guessable inputs (the shop's myshopify domain and the numeric Shopify user id) rather than an unguessable secret, and because the cookie carrying it is never verified, an attacker can forge the cookie for a target shop and have the host application load and use that shop's authenticated session (including its access token) on the attacker's request.

### Finding Description
When completing OAuth for a non-embedded app, `Oauth.validate_auth_callback` sets the app's persistent cookie value to the raw session id: [1](#0-0) 

That session id is fully deterministic and derived from public information, not a random secret: [2](#0-1) 

The cookie type itself (`SessionCookie`) is a plain struct with no HMAC/signature over its `value`: [3](#0-2) 

On every subsequent request, `SessionUtils.current_session_id` retrieves that same cookie and returns its raw contents as the authoritative session id, with zero verification that the value actually originated from this library's own OAuth flow: [4](#0-3) 

This is the exact, documented usage pattern for non-embedded apps (`current_session_id(nil, cookies, true/false)`), so the host application is not misusing the API — it is following it as specified: [1](#0-0) 

**Identity binding broken:** the value used to select which merchant's access token is loaded (`session_id`) is supposed to equal `HMAC/cryptographically-bound(shop, user)` established during the verified OAuth callback, but instead equals `raw, unauthenticated cookie bytes supplied on the current request`. Because `session_id = "#{shop}_#{associated_user.id}"` (online) or `"offline_#{shop}"` (offline) contains no secret component, and the cookie transporting it is unsigned, an attacker who merely knows a target shop's `myshopify.com` domain (public) and the target user's numeric id (frequently observable/enumerable, e.g., from admin URLs or GraphQL global ids) can construct the exact same string themselves.

This directly mirrors the reported bug class: a value is computed/assigned for one identity but there is no mechanism binding it — or verifying its provenance — before it is used to unlock access on behalf of that identity (in the report, `_resolvedPay[newAddress]` is set but nothing checks who is allowed to claim it; here, `session.id` string is set in a cookie but nothing checks that the request presenting that string is the party the OAuth flow actually authenticated).

### Impact Explanation
If the host application follows the gem's documented pattern (store/retrieve sessions keyed by the string returned from `current_session_id`), an attacker who forges the `shopify_app_session` cookie to a guessed `shop_userid`/`offline_shop` value causes the app to load and act with another merchant's session, including its Admin API access token. This is cross-tenant access to another merchant's data/actions using their access token — Critical impact per the scope's severity table.

### Likelihood Explanation
Exploitability depends on the attacker knowing/guessing a valid `shop` domain and, for online sessions, a valid associated user id — both are frequently discoverable (myshopify domains are often public; Shopify user/staff ids are small sequential integers visible in the Admin UI/URLs and GraphQL responses) and no secret token, encryption key, or credential is required to construct the cookie value. The likelihood is Medium-High for apps that use the documented cookie-based session lookup for non-embedded installations.

### Recommendation
Do not use the raw, predictable session id as the cookie's trust anchor. Either (a) sign/HMAC the cookie value with `Context.api_secret_key` (similar to `Utils::HmacValidator`) and verify the signature in `cookie_session_id` before returning it, or (b) replace the deterministic `shop_userid` cookie value with an unguessable random token that is itself mapped server-side to the real session id, so that presenting the cookie proves possession of a secret rather than knowledge of public identifiers.

### Proof of Concept
1. Attacker discovers target's shop domain `victim-shop.myshopify.com` (public) and target's numeric Shopify user id `123456789` (observable via Admin URLs/GraphQL ids).
2. Attacker computes the deterministic online session id: `"victim-shop.myshopify.com_123456789"` (per `Session.from`, `lib/shopify_api/auth/session.rb:107-118`) — or simply `"offline_victim-shop.myshopify.com"` for the offline case.
3. Attacker sets a cookie `shopify_app_session=victim-shop.myshopify.com_123456789` on a request to the target app (any host allowing cross-site cookie setting, or when testing directly against the app domain).
4. The app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, true)`, which returns the attacker-supplied string unchanged (`lib/shopify_api/utils/session_utils.rb:68-71`).
5. The host app looks up this id in its session store, finds the victim's real session record (created earlier via legitimate OAuth), and uses the victim's access token to serve the attacker's request — cross-tenant access achieved without ever touching `api_secret_key` or any credential belonging to the attacker.

module ShopifyAPI
  module Auth
    module Oauth
      class SessionCookie < T::Struct
        extend T::Sig

        SESSION_COOKIE_NAME = "shopify_app_session"

        const :name, String, default: SESSION_COOKIE_NAME
        const :value, String
        const :expires, T.nilable(Time)

        alias_method :eql?, :==
        sig { params(other: T.nilable(SessionCookie)).returns(T::Boolean) }
        def ==(other)
          return false unless other

          name == other.name &&
            value == other.value &&
            expires == other.expires
        end
      end
    end

        def current_session_id(shopify_id_token, cookies, online)
          if Context.embedded?
            if shopify_id_token
              id_token = shopify_id_token.gsub("Bearer ", "")
              session_id_from_shopify_id_token(id_token: id_token, online: online)
            else

              cookie_session_id(cookies)
            end
          else
            raise Errors::CookieNotFoundError, "Session cookie not found for app" unless
              cookies && cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]

            cookie_session_id(cookies)
          end
        end

        def session_id_from_shopify_id_token(id_token:, online:)
          raise Errors::MissingJwtTokenError, "Missing Shopify ID Token" if id_token.nil? || id_token.empty?

          payload = Auth::JwtPayload.new(id_token)
          shop = payload.shop

          if online
            jwt_session_id(shop, T.must(payload.sub))
          else
            offline_session_id(shop)
          end
        end

        sig { params(shop: String, user_id: String).returns(String) }
        def jwt_session_id(shop, user_id)
          "#{shop}_#{user_id}"
        end

        sig { params(shop: String).returns(String) }
        def offline_session_id(shop)
          "offline_#{shop}"
        end

        sig { params(cookies: T::Hash[String, String]).returns(T.nilable(String)) }
