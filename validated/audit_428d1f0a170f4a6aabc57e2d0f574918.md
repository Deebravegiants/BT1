## Title
Fee-on-transfer / deflationary fee token breaks the `order.fees` escrow accounting in `IntentGatewayV2.placeOrder`, permanently freezing order escrow on `withdraw()` - (File: evm/src/apps/IntentGatewayV2.sol, evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`placeOrder` in both `IntentGatewayV2.sol` (main EVM) and the Tron variant swaps native token for the fee token via UniswapV2's `swapETHForExactTokens` and unconditionally records `_orders[commitment][TRANSACTION_FEES] = order.fees`, assuming the contract now holds exactly `order.fees` units of the fee token. If the configured fee token has any transfer tax/deflationary mechanic (a "commission"-style external-integration behavior, analogous to the OKX commission in the referenced report), the router's exact-output math does not account for a tax applied on the final leg of the transfer, so the gateway can end up holding fewer fee-token units than `order.fees` records. Because `withdraw()` later performs an unconditional, unguarded token transfer of the recorded `fees` amount and reverts the entire function (including the release of the user's/solver's actual escrowed principal) if that transfer fails, this mismatch can permanently DoS `withdraw()` for the order, freezing the legitimately escrowed input tokens.

### Finding Description
In `placeOrder`, when the user pays the solver fee in native token: [1](#0-0) 

`swapETHForExactTokens` is an *exact-output* swap: the router computes `amounts[0]` (ETH in) from reserves so that `amounts[1]` (fee token out) equals `order.fees`. Uniswap V2's `_swap` internals move the output token from the pair contract directly to `to` via the token's own `transfer`, with no post-transfer balance check against `amountOut`. If the fee token itself charges a transfer fee (deflationary/tax token), the actual balance credited to the gateway is `order.fees` minus the token's tax, yet the contract unconditionally sets:

```solidity
_orders[commitment][TRANSACTION_FEES] = order.fees;
```

recording an IOU larger than the tokens actually held for this bucket. The same unguarded pattern exists in the Tron variant: [2](#0-1) 

This is the direct analog of the external-report's root cause: an external DEX/router integration silently short-changes the amount actually received relative to what the protocol's internal accounting assumes, because the router does not (and cannot) guarantee delivery of the nominal amount when a fee-charging token/route is involved.

Unlike the *input* token handling in the same function — which explicitly measures actual balance received and mutates `order.inputs[i].amount` to match reality (visible a few lines earlier in the same contract) — the `TRANSACTION_FEES` bucket has no such reconciliation: [3](#0-2) 

This asymmetry means the escrow bucket for `order.fees` can be over-credited relative to the contract's real fee-token balance.

The over-credit surfaces destructively in `withdraw()`, which is reached both from a normal fill settlement (`RedeemEscrow`) and from cancellation refunds (`RefundEscrow`). It unconditionally attempts to pay out the full recorded fee amount to the beneficiary/relayer:

```solidity
uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
if (fees > 0) {
    address feeToken = IDispatcher(host()).feeToken();
    (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
    if (!success) revert TransferFailed();
    ...
}
```
(Tron variant, matching pattern in the main contract's `withdraw`.) [4](#0-3) 

If the contract's actual fee-token balance for that bucket is short (because the fee token taxed the inbound swap), `feeToken.transfer(beneficiary, fees)` reverts (standard ERC-20 behavior on insufficient balance) or returns `false`, triggering `revert TransferFailed()`. Since this fee payout is not isolated behind a try/catch and runs in the same function body that releases the user's/solver's real escrowed principal tokens, the *entire* `withdraw()` call reverts — permanently, since the shortfall never resolves on its own. This is unauthenticated/permissionless-reachable: any user calling `placeOrder` with `order.fees > 0` and native-token payment, when the configured `feeToken` is (or later becomes) a fee-charging ERC-20, triggers this state.

### Impact Explanation
A successful trigger permanently freezes the escrowed principal tokens of the affected order: `withdraw()` can never complete for that commitment because it always reverts on the fee-transfer step, blocking both the "happy path" `RedeemEscrow` settlement to the solver and the cancellation/refund paths (`RefundEscrow`, `onGetResponse`) that also call `withdraw()`. This is a permanent freezing of user/solver funds triggered by a single unprivileged `placeOrder` transaction — no admin or governance action can recover the specific order's escrow without a contract upgrade, satisfying the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Likelihood depends on whether the deployed `feeToken` (returned by `IDispatcher(hostAddr).feeToken()`) can be a fee-on-transfer/deflationary token, or is guaranteed to always be a plain, tax-free ERC-20 for the lifetime of the deployment. Given that `feeToken()` is a host-configurable/governance-settable parameter shared across the protocol, and the report's rule explicitly treats externally-integrated token/router fee behavior as in-scope, this is a realistic configuration risk rather than a purely theoretical one — but it is conditioned on the fee-token choice, so it is not guaranteed under every current deployment.

### Recommendation
Mirror the reconciliation pattern already used for `order.inputs` in `placeOrder`: after the `swapETHForExactTokens` (or any fee-token acquisition path), measure the actual fee-token balance delta received by the contract and store that measured amount in `_orders[commitment][TRANSACTION_FEES]` instead of the nominal `order.fees`. Additionally, in `withdraw()`, cap the fee payout to `min(recorded fees, actual feeToken balance)` or isolate the fee-transfer failure so it cannot block release of the order's principal tokens.

### Proof of Concept
1. Governance/host configures `feeToken()` to an ERC-20 with a transfer tax (e.g., 1% burned on every `transfer`/`transferFrom`), or a token that later adds such behavior via an upgradeable proxy.
2. A user calls `placeOrder` with `order.fees > 0`, paying the fee in native token, causing the swap path `WETH -> feeToken` via `swapETHForExactTokens(order.fees, ...)`.
3. Because of the feeToken's tax, the gateway receives `order.fees * (1 - taxBps)` actual fee tokens, but `_orders[commitment][TRANSACTION_FEES]` is set to the full nominal `order.fees`.
4. When the order is later filled (or cancelled), `withdraw()` attempts `feeToken.transfer(beneficiary, order.fees)`. Since the gateway's real balance for that bucket is short by the tax amount, the transfer reverts (or `transfer` returns `false`, triggering `revert TransferFailed()`).
5. The revert propagates through the entire `withdraw()` call, so the escrowed input tokens (`order.inputs`) — real user/solver funds — are never released, for the lifetime of the order commitment.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
