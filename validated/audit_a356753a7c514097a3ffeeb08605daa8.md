### Title
Phantom-order weighted-median price feed lets a dominant solver dictate the "fair" anchor price that `IntentGateway.quoteIntent` uses for real orders - ([File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts])

### Summary
The reported `AntiSandwichHook` bug is that the contract trusts the price observed at the start of a block as "fair," while its own design removes the arbitrage incentive that would normally keep that anchor accurate. Hyperbridge's intents pricing pipeline has the analogous structural flaw: the protocol's own `LiquidityPool.sellRate`/`buyRate` — the "anchor price" that `IntentGateway.quoteIntent` uses by default to size real user orders — is derived from a `weightedMedian` over solver-submitted phantom bids, where weight is the solver's own reported inventory. Whoever controls more than half of a leg's weight sets the published price *verbatim*, with no external, disinterested party (there is no protocol-level analog of Uniswap's cross-pool arbitrage) forcing that price back toward the true market rate.

### Finding Description
`aggregatePhantomBids` builds a per-leg price by calling `weightedMedian` over verified solver bids, where each bid's weight is that solver's own on-chain balance of the leg's output token: [1](#0-0) 

The `weightedMedian` implementation itself documents the consequence directly in its own comments and tests: a bidder with a majority of the weight sets the returned value to its own exact quote, not a blend: [2](#0-1) [3](#0-2) 

This selected value becomes `PhantomOrderPriceSnapshotV2.medianPrice`, and `lowestPrice`/`highestPrice` are deliberately overwritten with that same value "so consumers cannot read an outlier bid as a tradeable bound": [4](#0-3) 

These per-chain samples are then merged by `weightedRate` (a depth-weighted mean, not a median) into the pool's single `sellRate`/`buyRate`: [5](#0-4) 

Critically, this indexed rate is not a passive analytics artifact — it is the *default* pricing source the SDK uses to size real, user-submitted `IntentGateway` orders: [6](#0-5) [7](#0-6) 

The design assumes that because solvers "rebalance and arbitrage away per-chain drift," the published rate tracks the true market price: [8](#0-7) 

But nothing in the protocol enforces that assumption. Unlike `AntiSandwichHook`'s block-start price (which at least starts from a real, externally-arbitrageable AMM state before the hook's own mechanism disincentivizes correction), the phantom-price anchor here is a self-referential construction: a solver's *own reported balance* determines both whether its quote counts and how much it counts, and the median-selection formula guarantees that a solver crossing the 50%-weight threshold on a given leg's output token publishes its own chosen number as the "fair" market rate — not an average, not a market-cleared price, but its verbatim quote. The only bound protecting the *solver's own client* from stale/manipulated venue prices is the optional, client-side `checkPriceGuard`/`referencePrice`/`maxDeviationBps` mechanism in `simplex` — this is opt-in filler configuration, not an on-protocol/indexer safeguard applied when the price is *published* to `LiquidityPool` or consumed by `quoteIntent`.

### Impact Explanation
Any actor that can accumulate more than half of a phantom leg's counted weight (the solver's on-chain balance of that leg's output token on the destination chain, which is attacker-controlled and cheap to size for a thinly-traded pair/chain) can dictate the published `sellRate`/`buyRate` for that pool. Because `IntentGateway.quoteIntent` defaults to these indexed rates to compute the `amountIn`/`amountOut` for real user orders, a manipulated anchor directly translates into mispriced real-money swaps — the classic "start-of-block price is stale/manipulated and there's no incentive to correct it" failure mode, but here manifesting as ongoing mispricing of live user intents rather than a single-block window. This is a concrete asset-pricing integrity break reachable from an unprivileged actor (any solver submitting phantom bids), matching the "unauthorized app action" / mispriced value-transfer class the validation rules require.

### Likelihood Explanation
Requires only: (1) being a delegated solver able to submit phantom bids (a normal, permissionless participant role), and (2) holding a majority of one leg's output-token balance on one chain for a period spanning a bid window — most plausible on newly-added, thin, or low-liquidity pairs/chains where a single well-capitalized actor can dominate the weight. No governance or admin privilege is needed, and the mechanism's majority-weight-wins behavior is by design, not an edge-case bug, making exploitation deterministic once the weight threshold is met.

### Recommendation
Do not let the phantom weighted-median act as an unconstrained protocol-level price anchor for real order pricing. Options: cap any single solver's weight contribution per leg (e.g., a max-share clamp before the median), require a minimum number of *independent* backing solvers before a snapshot is trusted for `quoteIntent`, or bound the published `LiquidityPool` rate against an external reference (extending the currently client-only `checkPriceGuard`/`referencePrice` concept to the indexer/`quoteIntent` path). At minimum, document prominently in `LiquidityPool`/`quoteIntent` that the indexed rate assumes competitive, non-dominant phantom bidding and is not safe as a sole pricing source for pairs without deep, diversified solver participation — mirroring the recommendation given for `AntiSandwichHook`.

### Proof of Concept
1. Attacker deploys/operates a delegated `SolverAccount` on a target chain and funds it with a majority of the leg's output token relative to all other bidding solvers for a low-liquidity pair (verifiable via `PhantomOrderPriceSnapshotV2`/`PoolBidder` history).
2. During the next phantom bid window for that pair/chain, the attacker's solver submits a bid quoting an output amount favorable to itself (e.g., understating the true output to later profit, or overstating it to win user routing away from honest solvers) — see `weightedMedian` selecting the majority-weight bidder's exact price verbatim: [9](#0-8) .
3. `handlePhantomOrderPrices` -> `aggregatePhantomBids` -> `updateLiquidityPools` persists this attacker-chosen value as `LiquidityPool.sellRate`/`buyRate`.
4. A real user calls `gateway.quoteIntent(...)` with the default `indexed_rates` strategy; the SDK reads the manipulated `LiquidityPool.buyRate`/`sellRate` and computes the order's `amountIn`/`amountOut` from it: [10](#0-9) .
5. The user's real `IntentGatewayV2` order is now sized off a rate the attacker unilaterally set, rather than a market-cleared price — repeatable every bid window as long as the attacker retains majority weight.

```typescript
export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
```

```typescript
function mergeChainRowsIntoPool(pool: LiquidityPool, rows: PoolChainLiquidity[], referenceBlock: bigint): void {
	for (const direction of [SELL, BUY]) {
		const directionRows = rows.filter((row) => row.direction === direction)
		if (directionRows.length === 0) continue

		// Blocks are processed in order, so the difference is non-negative in practice; a row
		// from a "future" block would simply count as fresh, which is the right reading anyway.
		const fresh = directionRows.filter((row) => referenceBlock - row.lastUpdatedBlock <= MAX_SAMPLE_AGE_BLOCKS)
		const merged = fresh.length > 0 ? fresh : directionRows

		warnOnDivergentSample(pool.id, direction, merged)

		const depth = merged.reduce((acc, row) => acc + row.depth, 0n)
		const rate = weightedRate(merged)
		const bidCount = merged.reduce((acc, row) => acc + row.bidCount, 0)

		if (direction === SELL) {
			pool.sellRate = rate
			pool.sellDepth = depth
			pool.sellBidCount = bidCount
		} else {
			pool.buyRate = rate
			pool.buyDepth = depth
			pool.buyBidCount = bidCount
		}
	}
}
```
