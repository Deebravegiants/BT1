## Analysis

The reported bug class — an unprivileged actor artificially inflating a threshold value that gates a withdrawal, thereby permanently locking a legitimate account holder out — has a concrete analog in agave's vote program via the `DepositDelegatorRewards` instruction and its interaction with `pending_delegator_rewards`.

### Title
Unprivileged `DepositDelegatorRewards` griefing permanently blocks vote account withdrawal/closure via `pending_delegator_rewards` inflation - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
`VoteInstruction::DepositDelegatorRewards` lets *any* signer transfer lamports into an arbitrary V4 vote account and unconditionally increment that account's `pending_delegator_rewards` counter. The `withdraw` instruction subsequently refuses to fully close a vote account while `pending_delegator_rewards > 0`, and requires any partial withdrawal to leave `rent_exempt_minimum + pending_delegator_rewards` behind. Because the deposit instruction requires no relationship to the vote account (only that the caller sign for their own transfer), any address can grief a vote account's authorized withdrawer, blocking full withdrawal/closure indefinitely for a trivial cost — the exact "artificially raise a shared minimum to block withdrawal" pattern described in the external report.

### Finding Description
`deposit_delegator_rewards` only verifies that the *source* account signs the transfer — it performs no check that the caller has any authority over the target vote account: [1](#0-0) 

It then unconditionally adds the deposited amount to `pending_delegator_rewards` on the target vote account: [2](#0-1) 

`add_pending_delegator_rewards` is a simple saturating counter increment with no cap tied to actual stake/participation, and no way for the withdrawer (or anyone) to directly zero it out: [3](#0-2) 

The `withdraw` instruction then enforces this attacker-controlled value as a hard floor: full closure is rejected while `pending_delegator_rewards > 0`, and partial withdrawals must leave at least `rent_exempt_minimum + pending_delegator_rewards` lamports: [4](#0-3) 

This is dispatched from the vote processor with no additional authorization check on the vote account itself — only feature-gate checks: [5](#0-4) 

`pending_delegator_rewards` is only reduced during epoch reward distribution, proportionally to the vote account's share of block rewards for that epoch (`calculate_block_reward`), which is entirely outside the withdrawer's control and can be arbitrarily slow (or effectively never fully drained if the attacker periodically re-deposits a minimal amount): [6](#0-5) 

This mirrors the `StakedUSDf` bug precisely: a shared, globally-enforced minimum (`MIN_SHARES` vs. `pending_delegator_rewards`) that any unprivileged actor can inflate with a small, low-cost deposit into someone else's account, causing the legitimate withdrawal/closure to permanently revert with `InstructionError::InsufficientFunds`.

### Impact Explanation
An attacker can call `DepositDelegatorRewards` with a source account they control and a target vote account they do not, depositing as little as 1 lamport. This permanently prevents the authorized withdrawer from fully closing the vote account and forces every partial withdrawal to reserve the attacker-inflated amount. The attacker can repeat this cheaply and indefinitely to keep `pending_delegator_rewards` above the rate at which block-reward distribution can drain it, resulting in a durable griefing/DoS of vote-account fund withdrawal — undeclared, attacker-driven mutation of another account's withdrawable balance.

### Likelihood Explanation
Likelihood is Low: the instruction is gated behind three not-yet-fully-shipped features (`commission_rate_in_basis_points`, `custom_commission_collector`, `block_revenue_sharing` / SIMD-0123, SIMD-0185, SIMD-0232, SIMD-0291), so it is only reachable once these are activated on a cluster. Once active, exploitation requires only a funded system account and a single instruction — no special privilege.

### Recommendation
Restrict `DepositDelegatorRewards` to only be invocable in contexts tied to legitimate delegator/stake reward flow (e.g., verify the source is a recognized stake/reward-distribution account or cap deposits to actual owed rewards), or decouple the withdraw/close gating from an externally-inflatable counter — e.g., track `pending_delegator_rewards` as an internally computed/distributed value rather than one incrementable via an arbitrary, permissionless deposit instruction.

### Proof of Concept
1. Feature set activates `commission_rate_in_basis_points`, `custom_commission_collector`, and `block_revenue_sharing` (SIMD-0123 stack) on a V4 vote account.
2. Attacker funds an arbitrary keypair `attacker` with a small amount of lamports.
3. Attacker submits `VoteInstruction::DepositDelegatorRewards { deposit: 1 }` with accounts `[victim_vote_account, attacker]`, signing as `attacker` per [7](#0-6) .
4. This succeeds unconditionally (no relation to `victim_vote_account` required) and sets `pending_delegator_rewards = 1` (or increments it further on repeat calls).
5. The vote account's authorized withdrawer subsequently calls `Withdraw(full_balance)`; it now fails with `InstructionError::InsufficientFunds` because `pending_delegator_rewards > 0`, per [8](#0-7) , exactly as confirmed by the existing test `test_withdraw_pending_delegator_rewards` at [9](#0-8) .
6. The attacker repeats step 3 with fresh minimal deposits as needed to outpace any epoch block-reward drainage, keeping the withdrawer permanently blocked from closing/fully withdrawing the vote account.

    if remaining_balance == 0 {
        // SIMD-0123: vote account cannot be closed if
        // pending_delegator_rewards > 0.
        if pending_delegator_rewards > 0 {
            return Err(InstructionError::InsufficientFunds);
        }

        let reject_active_vote_account_close = vote_state
            .epoch_credits()
            .last()
            .map(|(last_epoch_with_credits, _, _)| {
                let current_epoch = clock.epoch;
                // if current_epoch - last_epoch_with_credits < 2 then the validator has received credits
                // either in the current epoch or the previous epoch. If it's >= 2 then it has been at least
                // one full epoch since the validator has received credits.
                current_epoch.saturating_sub(*last_epoch_with_credits) < 2
            })
            .unwrap_or(false);

        if reject_active_vote_account_close {
            return Err(VoteError::ActiveVoteAccountClose.into());
        } else {
            // Deinitialize upon zero-balance
            VoteStateHandler::deinitialize_vote_account_state(&mut vote_account, target_version)?;
        }

        // is lamports - pending_delegator_rewards - rent_exempt_minimum.
        let min_rent_exempt_balance = rent_sysvar.minimum_balance(vote_account.get_data().len());

        if remaining_balance < min_balance {
            return Err(InstructionError::InsufficientFunds);
