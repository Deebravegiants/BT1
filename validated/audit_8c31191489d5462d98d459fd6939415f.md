### Title
Unvalidated arbitrary output-token address lets a filler poison VWAPOracle's cumulative spread accounting - (File: evm/src/utils/VWAPOracle.sol)

### Summary
`VWAPOracle.recordSpread` is called by `IntentGatewayV2`/`IntentGatewayV3` whenever an order fills, and it reads `IERC20Metadata(outputToken).decimals()` directly on an address taken from the order's `output.assets[i].token` — a field fully controlled by whoever places or fills the order — with no check that this address is a real, registered ERC20 or that it matches the token the gateway actually transferred. This mirrors the Aloe `VolatilityOracle.prepare` finding: an externally-supplied contract address is trusted and fed straight into a financial calculation without validating that the contract is what it claims to be.

### Finding Description
`recordSpread` is restricted to `msg.sender == _intentGateway` [1](#0-0) , but the `inputs`/`outputs` `TokenInfo[]` arrays it receives are pass-throughs of the `Order.output.assets` and `Order.inputs` fields that originate from the order itself — user- and filler-supplied data, not values the gateway independently verifies to be legitimate tokens. Inside the loop, the output token's decimals are read live from whatever contract address is encoded in the order:

```solidity
address outputToken = address(uint160(uint256(outputs[i].token)));
...
uint8 outputDecimals = outputToken == address(0) ? 18 : IERC20Metadata(outputToken).decimals();
``` [2](#0-1) 

There is no check that `outputToken` is a token actually escrowed/transferred as part of the fill, no allowlist, and no bytecode/interface verification — any contract (or an EOA that reverts, or a malicious contract returning an attacker-chosen `decimals()` value) can be named here. A malicious contract can return an arbitrary `uint8` (e.g. 0 or 30+) to distort `_normalizeAmount`, which scales the recorded amount by `10**(18-decimals)` or divides by `10**(decimals-18)` [3](#0-2) . This directly corrupts the weighted `spreadBps` computation and is accumulated into `_tokenSpreads[sourceChainHash][inputToken]` [4](#0-3) , which is exposed via the public `spread()` view for any external consumer of `IIntentPriceOracle` [5](#0-4) .

The same class of problem — trusting an externally supplied contract's self-reported metadata without validating it's the real thing — also appears independently in `getTokenMetadata` (indexer) which calls `.symbol()`/`.decimals()` on unvalidated addresses [6](#0-5) , but that is an off-chain reporting path with no funds/consensus impact and does not qualify per the scope rules.

### Impact Explanation
`_tokenSpreads` is the sole persistent, cross-consumer signal of filler behavior (spread quality) per (sourceChain, token) pair, and `spread()`/`decimals()` are exposed publicly through the `IIntentPriceOracle` interface for any downstream integrator (e.g., solver reputation scoring, dynamic fee/incentive systems, or monitoring dashboards built on this data) to consume. By supplying a malicious "output token" contract whose `decimals()` returns an extreme value, an attacker (a filler placing an order with themselves, or paying a nominal amount to fill a real order with a crafted output leg) can:
- Massively inflate or deflate `outputAmountNormalized`, producing an arbitrarily large positive or negative `spreadBps` for a real `inputToken`, permanently skewing the weighted-average spread record for that token/chain pair.
- Repeat this cheaply (no real value moved beyond whatever `inputs`/native minimum is required to trigger a fill) to poison the oracle's historical average, which cannot be corrected without redeploying/resetting state (there is no decay or admin reset mechanism visible in this contract).

This is a permanent corruption of an on-chain accounting/oracle state that other protocol components or integrators rely on for pricing/reputation signals — not merely a display bug, since the data is exposed through a public interface method (`spread`) explicitly documented for external consumption.

### Likelihood Explanation
High likelihood: any account can place an order through `IntentGatewayV2`/`V3` and act as its own filler (same-chain fills are supported per the `IntentGatewayV2SameChainTest.sol` tests), specifying an attacker-deployed contract as an output token. The `recordSpread` call is unconditionally reached on every successful fill with no allowlist or sanity check on the output token identity, and the fill only requires satisfying whatever token transfer the gateway itself validates for `inputs`/native value — the `outputToken` used for the decimals lookup need not be a real liquid asset the filler holds any significant value in beyond what the fill mechanics require.

### Recommendation
1. Do not trust `decimals()` from an address supplied inside `Order`/fill data as ground truth for financial normalization. Instead:
   - Maintain (and require) explicit governance-configured decimals for output tokens too (mirroring the existing `_tokenDecimals` mapping used for source-chain tokens), rather than trusting a live external call.
   - If a live read is unavoidable, wrap it in bounds checks (e.g., reject decimals outside a sane range like 0–30) and revert/skip the record instead of silently using an attacker-chosen value.
2. Cross-check that `outputToken` corresponds to a token actually transferred by the recorded fill (e.g., pass verified transfer amounts/addresses from the gateway's own accounting rather than raw order-supplied values), so an attacker cannot name an arbitrary contract unconnected to the real fill.
3. Consider adding rate limiting / outlier rejection (e.g., discard or cap `spreadBps` values beyond a plausible bound) before folding them into the cumulative weighted average, so a single malicious fill cannot dominate the aggregate.

### Proof of Concept
1. Deploy `MaliciousERC20Metadata` implementing `IERC20Metadata` where `decimals()` returns `0` (or `36`) regardless of any real token semantics.
2. Craft/place an `Order` (same-chain fill supported, per `IntentGatewayV2SameChainTest.sol`) whose `output.assets[0].token` is set to this malicious contract's address, with an arbitrary `amount`.
3. Fill the order as the attacker's own solver so `IntentGatewayV2.fillOrder` executes and internally calls `IIntentPriceOracle(priceOracle).recordSpread(commitment, order.source, order.inputs, order.output.assets)` — reachable per the price-oracle wiring on `IntentGatewayV2Test.sol`'s `priceOracle` param and `VWAPOracle`'s `restrict(_intentGateway)` modifier [7](#0-6) .
4. `VWAPOracle.recordSpread` calls `IERC20Metadata(maliciousToken).decimals()` and gets the attacker's chosen value (e.g., `0`), which via `_normalizeAmount` multiplies the raw `amount` by `10**18`, producing an extreme `outputAmountNormalized`.
5. Observe via `VWAPOracle.spread(sourceChain, inputToken)` that the weighted-average spread for `inputToken` is now wildly skewed by this single fill, with no way to revert or correct the corrupted cumulative state.

**Uncertainty note:** I was unable to trace every downstream consumer of `IIntentPriceOracle.spread()`/`.decimals()` within the indexed portion of the codebase (e.g., whether any on-chain contract besides analytics/reporting reads this value to gate solver behavior or fees) — the index only surfaced the interface definition, the `VWAPOracle` implementation, and test files. If a background Devin session is needed to grep the full `evm/` tree for all callers of `IIntentPriceOracle`, that would confirm the exact blast radius beyond what's cited here.

    function _normalizeAmount(uint256 amount, uint8 _decimals) private pure returns (uint256 normalized) {
        if (_decimals == 18) {
            return amount;
        } else if (_decimals < 18) {
            return amount * (10 ** (18 - _decimals));
        } else {
            return amount / (10 ** (_decimals - 18));
        }
    }
