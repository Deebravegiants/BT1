### Title
Signup extension mode bypasses biometric pipeline and fraud detection, forcing success - (File: src/plans/mod.rs)

### Summary
In the Astaria report, LPs could call `mint` on `PublicVault` to bypass the `whenNotPaused` guard that was only enforced on the sibling `deposit` function, letting them skip a safety gate that should apply uniformly. The analogous pattern in orb-core is in `MasterPlan::do_signup`: when a signup carries a `signup_extension_config` (derived from the scanned user QR code's `SignupMode`), the code takes an early-return path that sets `result.success = true` and completely skips the biometric pipeline and fraud-detection calls that are otherwise mandatory for every signup.

### Finding Description
`do_signup` first runs biometric capture, then decides whether to run the full biometric pipeline and fraud checks: [1](#0-0) 

If `self.skip_pipeline()` is true (a dev-only, feature-gated flag) **or** `debug_report.signup_extension_config.is_some()`, the code sets `result.success = true` and returns immediately — the calls to `self.biometric_pipeline(...)` (which produces iris/face embeddings) and `self.detect_fraud(...)` (which runs fraud/liveness checks against the pipeline output) never execute for that signup: [2](#0-1) 

`signup_extension_config` is populated from `SignupMode` values (`PupilContractionExtension`, `FocusSweepExtension`, `MirrorSweepExtension`, `MultiWavelength`, `Overcapture`, `Basic`) that are parsed as part of the user-scanned QR code data and are dispatched purely based on that mode in `biometric_capture`: [3](#0-2) 

I was not able to fully confirm — due to not finishing review of `src/plans/qr_scan/user.rs` before running out of iterations — whether `SignupMode` selection is restricted to privileged/operator-only QR codes, restricted to staging/internal builds, or genuinely reachable by an ordinary end-user QR code in production. This is the key unresolved fact that determines whether this is a real unprivileged-user-reachable bug or an intended internal-testing/extension-data-collection path (in which case it would be excluded by the "test-only paths" rule).

### Impact Explanation
If `signup_extension_config` can be set by an unprivileged user's own QR-code content (rather than being locked to operator/staff/internal-testing QR codes), then a malicious user could force `signup_reason` handling to be skipped entirely: no `detect_fraud` liveness/fraud check runs, and enrollment success is asserted directly from the extension branch rather than from real pipeline output. This mirrors the pause-bypass root cause — a security-relevant checkpoint (fraud/liveness enforcement) that exists on the "normal" code path is absent on an alternate, reachable entry path — and could lead to fraudulent/misattributed signups without the intended fraud checks being applied.

### Likelihood Explanation
Likelihood is **uncertain pending verification** of how `SignupMode`/`signup_extension_config` is gated in `src/plans/qr_scan/user.rs`. If extension modes are strictly limited to internal-testing/staff QR codes or feature-gated (e.g., behind `internal-data-acquisition`/`allow-plan-mods`), this reduces to a non-issue per the exclusion rules for test-only paths. If extension modes are selectable by any signed but otherwise ordinary user QR code in production builds, likelihood is high since it is directly reachable during normal signup flow.

### Recommendation
- Confirm in `src/plans/qr_scan/user.rs` whether `SignupMode` parsing/`try_parse` restricts non-`Basic` modes to privileged/internal contexts (e.g., staff QR codes, `#[cfg(feature = "internal-data-acquisition")]`).
- If extension modes are reachable by ordinary users in production, do not let `signup_extension_config.is_some()` alone force `result.success = true` and skip fraud detection — extension-mode signups should still go through `biometric_pipeline` and `detect_fraud` before being marked successful, or explicitly restrict `SignupMode` selection to trusted/authenticated operator contexts only.

### Proof of Concept
Not confirmed as concretely exploitable — this requires establishing (in `src/plans/qr_scan/user.rs`) that a normal end-user-controlled QR code can set a `SignupMode` other than `Basic`, which then results in the `do_signup` early-return at src/plans/mod.rs:558-561 skipping `biometric_pipeline`/`detect_fraud` and forcing `result.success = true`.
