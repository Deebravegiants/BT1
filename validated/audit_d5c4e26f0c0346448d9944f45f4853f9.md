### Title
Webhook shop identity trusted from unauthenticated header, not covered by HMAC verification - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate` only authenticates the JSON body bytes [2](#0-1) . The tenant-identifying `shop` value, however, is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed material [3](#0-2) . `Registry.process` passes this unauthenticated header value straight into the webhook handler as the shop of record [4](#0-3) .

### Finding Description
The binding that should hold is: `hmac_signed_bytes == bytes_that_determine_the_shop`. In this gem it does not — `verify(raw_body) == true` while `shop` is taken from a header that was never fed into the HMAC computation. `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac-sha256` header [5](#0-4) ; for `Webhooks::Request`, `to_signable_string` is defined as `@raw_body` only [1](#0-0) . The `topic`, `shop`, `api_version`, and `webhook_id` accessors all read straight from HTTP headers with no cryptographic tie to the signature [6](#0-5) .

Because HMAC validation succeeds as long as the body bytes are unchanged, any party who has legitimately received one valid webhook delivery (i.e., a merchant/app-installer on their own shop, an unprivileged party with respect to *other* tenants) possesses a `(raw_body, hmac)` pair that remains valid under `HmacValidator.validate` regardless of which `shop-domain` header value accompanies it. That party can replay the same body with a different `shopify-shop-domain` header pointed at another tenant of the same app, and `Registry.process` will accept it and dispatch `WebhookMetadata.new(topic:, shop: request.shop, body:, ...)` to the handler under the attacker-chosen shop [4](#0-3) .

### Impact Explanation
This breaks the tenant boundary the gem's webhook subsystem is meant to enforce: the `shop` value returned by `Registry.process`/`WebhookMetadata` is the field host applications rely on (per this gem's own documented API — `data.shop`, see `docs/usage/webhooks.md`) to determine which tenant a webhook event belongs to, e.g. to look up that shop's stored session/access token or apply the event to that shop's records. Since this value is not bound to the HMAC, an attacker can cause a legitimately-signed payload to be attributed to an arbitrary other shop, resulting in cross-tenant data confusion/access — a Critical-impact class per the given rubric (cross-tenant access), reachable purely through this gem's own `Webhooks::Request`/`Registry.process` code path with no access token, `api_secret_key`, or other privileged credential required beyond having received one legitimate webhook for one's own shop.

### Likelihood Explanation
Moderate-to-high likelihood in any deployment with multiple tenants sharing one app: any existing merchant/installer already receives valid `(body, hmac)` webhook deliveries for their own store as part of normal operation, and headers are trivially attacker-controlled when replaying a captured request to the same webhook endpoint (the endpoint is a plain HTTP endpoint the host app exposes; nothing in this gem ties the delivery to a specific origin beyond the `shop-domain` header). No cryptographic secret or privileged account is needed to perform the replay — only possession of one prior valid delivery.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable material used for HMAC verification, or otherwise cryptographically bind them to the signed body (e.g., require they be verified against a value embedded in the signed payload) so that `HmacValidator.validate` fails if any of these fields are altered independently of the body it authenticates.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com` and `shop-b.myshopify.com` (both use the same `api_secret_key`).
2. A legitimate webhook fires for `shop-a`: headers include `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: <hmac of raw_body>`, and `raw_body` (e.g. `{"id":123}`).
3. Attacker (a user/operator with access to `shop-a`'s webhook traffic — no `api_secret_key` needed) captures this delivery and resends it to the same endpoint, only replacing the header:
   `x-shopify-shop-domain: shop-b.myshopify.com`
   while keeping `raw_body` and `x-shopify-hmac-sha256` identical.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (== `raw_body`, unchanged) and it matches [7](#0-6) .
5. The handler is invoked with `WebhookMetadata.new(topic:, shop: "shop-b.myshopify.com", body: {"id":123}, ...)` [8](#0-7) , i.e. the app now processes shop-a's event data as if it belonged to shop-b, despite the HMAC never having authenticated the `shop` field.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
