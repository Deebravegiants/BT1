### Title
Checks-Effects-Interactions Violation in Tron `IntentGatewayV2.withdraw()` Enables Reentrant Double-Release of Escrowed Funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Perennial report's bug class is a mismatch between "local" and "global" account-state updates that are not synchronized with the actual settlement flow, letting an attacker exploit the *ordering* of state mutations to extract more value than is actually owed. The Hyperbridge Intent Gateway has a directly analogous ordering flaw in its Tron deployment: the escrow-accounting storage decrement in `withdraw()` happens **after** the external value transfer, rather than before, breaking the checks-effects-interactions pattern that the mainline EVM contract correctly follows.

### Finding Description
In the actively-maintained EVM `IntentsBase._withdraw` (`evm/src/apps/intentsv2/IntentsBase.sol:451-470`), the escrow ledger is decremented **before** any external call:
```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
_orders[body.commitment][token] = escrowed - amount;
if (token == address(0)) {
    _sendValue(beneficiary, amount);
} else {
    IERC20(token).safeTransfer(beneficiary, amount);
}
``` [1](#0-0) 

The Tron variant of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, implements the equivalent `withdraw()` function with the operations **reversed** — the native-token `.call{value: amount}` (and ERC20 `transfer`) executes first, and the `_orders[body.commitment][token] -= amount` ledger update happens only afterward:
```solidity
if (_orders[body.commitment][token] == 0) revert UnknownOrder();
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}
_orders[body.commitment][token] -= amount;
``` [2](#0-1) 

This is the same class of vulnerability the external report describes for `AccountLib.processGlobal`/`processLocal`: the code path that should atomically synchronize a value transfer with the corresponding accounting decrement instead performs the transfer while the accounting state is still stale, opening a window where the timing of execution (here, a reentrant call triggered by the native-token `.call` or a malicious ERC20's `transfer` hook) can be manipulated to read/act on outdated escrow state. The check `if (_orders[body.commitment][token] == 0) revert UnknownOrder()` only guards against the balance being *fully zero* — it does not re-validate `amount` against the current escrow after any reentrant mutation, and the decrement that would prevent a second release doesn't happen until after the funds have already left the contract.

`withdraw()` is reached from `onAccept()` [3](#0-2)  when a relayer delivers a `RedeemEscrow`/`RefundEscrow` settlement message from the paired gateway on another chain — i.e., from a single relayed proof submitted by an unprivileged relayer, exactly the class of "single relayed proof / message delivery" reachability required.

### Impact Explanation
If the beneficiary of a withdrawal is (or delegates to) a malicious contract, or if the token used is a non-standard/malicious ERC20 with transfer hooks, the external call executed before `_orders[...] -= amount` can re-enter and trigger another release for the same commitment/token before the escrow ledger reflects the first payout. Because the pre-check only asserts non-zero escrow rather than sufficient remaining escrow, a reentrant call can drain more of the escrowed balance than was actually owed, causing direct loss of user/solver funds held by the gateway — matching the "concrete theft" bar in the validation criteria.

### Likelihood Explanation
Exploitability depends on whether the calling path (`onAccept`, gated `onlyHost`) can be reentered with the *same* commitment before the underlying ISMP host itself finalizes/marks the incoming request as delivered — I was not able to fully verify, within the scope of this investigation, whether the Tron chain's host/dispatcher marks request delivery status before or after invoking the module's `onAccept`, which determines whether a literal double-delivery of the identical message is blocked at the host layer. Independent of that, the CEI violation itself is a real deviation from the pattern used everywhere else in this codebase (the mainline `IntentsBase._withdraw` explicitly does effects-before-interactions), and any reentrant path back into `withdraw()` for the same commitment (e.g., via a malicious beneficiary token's `transfer` callback if `token.call` targets a non-standard token, or via nested processing of a queued second message for the same commitment) would be immediately exploitable given the current ordering.

### Recommendation
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, mirror the effects-before-interactions ordering used in `evm/src/apps/intentsv2/IntentsBase.sol`: read the escrowed amount, validate `amount <= escrowed`, write the decremented value to `_orders[body.commitment][token]`, and only then perform the native-token `.call` or ERC20 `transfer`. Additionally add a reentrancy guard on `withdraw()`/`onAccept()` as defense in depth, and switch the ERC20 transfer to `safeTransfer` (SafeERC20) instead of a raw low-level `.call` with manual success decoding, consistent with the mainline contract.

### Proof of Concept
1. A user places a cross-chain order on the source chain via `placeOrder`, escrowing tokens under `_orders[commitment][token]` in the Tron `IntentGatewayV2` deployment.
2. A solver fills the order on the destination chain; a `RedeemEscrow` (or `RefundEscrow`) message is dispatched back to the source (Tron) chain.
3. A relayer delivers the message; the host invokes `onAccept` → `withdraw(body, isRefund)` [4](#0-3) .
4. `withdraw()` checks `_orders[commitment][token] != 0`, then immediately calls `beneficiary.call{value: amount}("")` (or `token.transfer`) — a beneficiary contract (or malicious token) can re-enter before `_orders[commitment][token] -= amount` executes.
5. If a reentrant path into `withdraw()` for the same commitment is reachable (e.g. via a second in-flight message for the same commitment being processed concurrently, or a malicious token's transfer hook invoking back into the gateway), the stale (not-yet-decremented) `_orders` value lets the reentrant call pass the `!= 0` check and release funds a second time, exceeding the actual escrowed balance and causing the gateway to pay out more than it holds for that order — a direct loss-of-funds condition attributable to the same "state mutated out of sync with the externally observable transfer" root cause identified in the source report.
