### Title
Permissionless pool-address squatting via front-run `Initialize2` permanently blocks legitimate pool creation for a market/mint pair - (File: `program/src/processor.rs`)

### Summary
`process_initialize2` derives the AMM account, LP mint, coin vault, PC vault and target-orders account as PDAs computed solely from the (publicly known) `market` pubkey and fixed seed strings. Any signer can call `Initialize2` for any market/mint pair with an arbitrary (dust-sized) `init_coin_amount`/`init_pc_amount`, permanently claiming these deterministic addresses. Once occupied, the legitimate project cannot ever initialize the "real" pool for that market, because the same addresses can never be re-derived differently and re-initialization is rejected. This mirrors the reported Curve `setPool()` front-running class: an unprivileged attacker races and permanently corrupts/blocks the pool-initialization step that the protocol depends on, causing a Denial-of-Service against the intended pool.

### Finding Description
The vault/LP-mint/target-orders/AMM addresses used by `Initialize2` are computed with: [1](#0-0) 

using only `program_id`, `market_account.key`, and a fixed seed suffix — **not** the caller's wallet. `market_info` is just "a seed for AMM account. Can be any account" per the code comments: [2](#0-1) 

`process_initialize2` accepts caller-supplied `init.init_coin_amount` / `init.init_pc_amount` and caller-supplied token source accounts, mints, and wallet, with no requirement that the caller be the market creator or hold any privileged role: [3](#0-2) 

The helper `generate_amm_associated_spl_token`/`generate_amm_associated_account` only succeeds when the target PDA is still owned by the system program (i.e., un-created); otherwise it fails with `RepeatCreateAmm`: [4](#0-3) 

and the AMM status check rejects re-initialization once set: [5](#0-4) 

Because the market pubkey (and typically the coin/pc mints, e.g. a project's new token and a well-known quote asset) is known before the "real" pool-seeding transaction lands, an attacker can precompute the exact `amm_info`, `amm_coin_vault`, `amm_pc_vault`, `amm_lp_mint`, and `amm_target_orders` addresses off-chain, race the legitimate deployer's transaction, and submit their own `Initialize2` with a minimal `init_coin_amount`/`init_pc_amount` (just enough to satisfy the `InitLpAmountTooLess` floor). Since `amm.status` becomes `WaitingTrade`/`SwapOnly` immediately, all subsequent `Initialize2` calls for that exact market — including the legitimate deployer's — permanently fail with `AlreadyInUse`, and the coin/PC vault PDAs permanently fail with `RepeatCreateAmm`. There is no admin/privileged path to reset or reassign these deterministic PDAs to a different pool.

This is directly analogous to the reported issue: an unprivileged actor front-runs the protocol's one-shot, address-pinned initialization step, exploiting the fact that the initialization check ("perfectly balanced pool" in the original report; "PDA must be un-created" here) can trivially be satisfied by the attacker first, permanently denying the legitimate initializer the ability to ever complete setup at that pinned address.

### Impact Explanation
The impact is a permanent, irreversible Denial-of-Service against pool creation for the targeted market/mint pair — the legitimate project can never launch its real, properly-funded pool for that market, since the deterministic PDAs are irrecoverably squatted with dust liquidity by the attacker. This is analogous to the accepted-High original finding, whose core harm was also "protocol becomes permanently unable to complete its one-time initialization step," not direct fund theft. The griefer only spends a small amount of both tokens (whatever satisfies `InitLpAmountTooLess`), while the victim's entire pool-launch plan for that market is permanently disabled with no on-chain recovery mechanism.

### Likelihood Explanation
This requires the attacker to: (1) know the target `market` pubkey (public, since OpenBook/market accounts are created before AMM pool setup) and mints, (2) hold a small quantity of both the coin and PC token, and (3) win a single-transaction race against the legitimate initializer. Because `market`, `coin_mint`, and `pc_mint` are public well before pool creation transactions are broadcast (mempool visibility / predictable deployment sequences), and Solana's transaction-ordering allows straightforward front-running via fee/priority bidding, this is readily executable by any unprivileged actor holding minimal amounts of the relevant tokens.

### Recommendation
Bind the derived PDAs (or at least gate `Initialize2`) to the intended pool creator, e.g., include the creator's pubkey (or a nonce chosen/committed by the intended creator) in the seed derivation, or require the caller to be a pre-registered/whitelisted creator for that market (as already partially supported via `amm_config`/`create_fee_destination`). Alternatively, add a minimum-liquidity/anti-dust threshold tied to real economic cost, and/or provide an admin-gated recovery/override path allowing migration to a newly derived address if a market's canonical pool PDA is squatted with negligible liquidity before the intended launch.

### Proof of Concept
1. Attacker observes a new OpenBook `market` account and its `coin_mint`/`pc_mint` being published/created ahead of the project's planned pool launch.
2. Attacker computes the deterministic PDAs via `get_associated_address_and_bump_seed(program_id, &market, seed, program_id)` for `amm_info`, `amm_coin_vault`, `amm_pc_vault`, `amm_lp_mint`, `amm_target_orders` (all derivable off-chain since inputs are public).
3. Attacker acquires the minimal amount of each token needed to pass the `InitLpAmountTooLess` check (`liquidity = sqrt(pc_amount * coin_amount) > 10^lp_decimals`).
4. Attacker submits `Initialize2` with these accounts and dust amounts, using a higher priority fee to land before the legitimate deployer's own `Initialize2` transaction.
5. `process_initialize2` succeeds, creating the vaults/mint/target-orders PDAs and setting `amm.status` to `WaitingTrade`/`SwapOnly` at [5](#0-4)  and [6](#0-5) .
6. The legitimate deployer's subsequent `Initialize2` call for the same `market` now always fails: the PDA account checks in `generate_amm_associated_spl_token`/`generate_amm_associated_account` return `AmmError::RepeatCreateAmm` (line 380/543), and even if those accounts happened to already exist for another reason, `amm.status != Uninitialized` triggers `AmmError::AlreadyInUse` (line 846), permanently preventing the intended pool from ever being initialized at that market's canonical address.
