Based on my analysis of the webhook signature-verification code, I found a valid identity-binding break analogous to the reported bug class.### Title
Webhook shop-domain identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](), [File: lib/shopify_api/webhooks/registry.rb]())

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes/compares the HMAC over exactly that signable string [2](#0-1) . The `shop-domain`, `topic`, `webhook-id`, and `api-version` HTTP headers are read directly from attacker-controllable request headers via `shopify_header` [3](#0-2)  and are never included in the HMAC-signed content. `Registry.process` trusts `request.shop` and `request.topic` straight from these unverified headers to build the `WebhookMetadata` passed to the app's handler [4](#0-3) .

### Finding Description
The identity binding that should hold is:
`hmac_valid(body) == true` **should imply** `(body, shop, topic)` were jointly produced/authorized by Shopify for that specific shop.

In this gem, the binding actually enforced is only:
`hmac_valid(body) == true` implies `body` bytes are unmodified — it says nothing about `shop` or `topic`.

Because the `shop-domain` header is outside the signed material, any party who can obtain **one** valid `(raw_body, hmac)` pair — trivially available to any developer/tester by installing the app on their own store and receiving a real webhook, or by observing webhook traffic to their own endpoint — can replay that exact body and HMAC to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `Utils::HmacValidator.validate(request)` in `Registry.process` will still pass, because it only re-derives the HMAC from `@raw_body`, which is untouched [5](#0-4) . The handler then receives `WebhookMetadata` claiming the payload originated from the attacker-chosen (victim) `shop` [6](#0-5) , even though it was never sent by Shopify for that shop.

Evaluating both sides of the equality:
- Before request: legitimate webhook exists with `shop = attacker-shop.myshopify.com`, `body = B`, `hmac = H = HMAC(secret, B)`.
- Attacker's replayed request: `shop header = victim-shop.myshopify.com`, `body = B` (unchanged), `hmac header = H` (unchanged).
- `HmacValidator.validate` recomputes `HMAC(secret, B) == H` → true, since `to_signable_string` never includes `shop`.
- `Registry.process` therefore invokes the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, topic: T, ...)`, incorrectly asserting cross-tenant provenance.

Any application built on this gem that trusts `WebhookMetadata#shop` (e.g., to select which merchant's DB row to update, to trigger app-uninstall cleanup, GDPR data-request/erasure flows, or to write body-derived data into a specific tenant's records) can be made to act on attacker-supplied data under a victim shop's identity, purely because the gem's webhook verification never binds `shop` (or `topic`) to the signature it validates.

### Impact Explanation
This breaks the tenant boundary between shops: an unprivileged (or minimally privileged — anyone who can install a free/dev copy of the app on any store) actor can make the app process fabricated webhook data attributed to a different shop, i.e., cross-tenant access/confusion. Depending on how the consuming app's webhook handlers use `shop`, this can range from data corruption in another tenant's records to forcing lifecycle actions (e.g. `app/uninstalled`) against a victim shop. This matches the "cross-tenant access" Critical impact category, since the shop identity used to route/act on the webhook payload is not authenticated at all by the gem's `HmacValidator`.

### Likelihood Explanation
Likelihood is high for any deployment that exposes a public webhook endpoint (the standard configuration) and where the underlying app trusts `WebhookMetadata#shop` for authorization or tenant-selection decisions (a documented, expected usage pattern per `docs/usage/webhooks.md` and `WebhookMetadata`'s existence). Obtaining one valid `(body, hmac)` pair requires no privileges beyond installing the app on any store (including the attacker's own free/dev store) — something explicitly permitted by the OAuth flow. No access token, `client_secret`, or `api_secret_key` is needed by the attacker; they only replay bytes they already legitimately received.

### Recommendation
Bind the trusted identity fields into the signed material that `HmacValidator` verifies, or otherwise cross-check them after HMAC validation:
- Extend `Webhooks::Request#to_signable_string` (or add a separate binding check in `Registry.process`) to incorporate `shop`, `topic`, and ideally `webhook_id` into what is cryptographically verified, OR
- After `HmacValidator.validate`, require the caller (or the gem) to verify `request.shop` against the shop the app expects to receive a webhook for (e.g., known via session/installation lookup) before invoking the handler, and reject if it doesn't match a shop that legitimately installed the app.
- Document explicitly in `docs/usage/webhooks.md` that `WebhookMetadata#shop`/`#topic` are **not** authenticated by the HMAC and must be independently verified by the consuming application before being trusted for tenant-scoped actions.

### Proof of Concept
1. Attacker installs the target app on their own development store `attacker-shop.myshopify.com` and triggers any webhook topic the app subscribes to (e.g. `orders/create`).
2. Attacker captures the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` that Shopify sent to the app's public webhook endpoint.
3. Attacker crafts a new HTTP POST to the same public webhook endpoint with:
   - Body: `B` (byte-for-byte identical)
   - Header `X-Shopify-Hmac-Sha256`: `H` (unchanged)
   - Header `X-Shopify-Shop-Domain`: `victim-shop.myshopify.com` (arbitrary target)
   - Header `X-Shopify-Topic`: unchanged or of attacker's choosing
4. The app's controller constructs `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` and calls `ShopifyAPI::Webhooks::Registry.process(request)`.
5. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `HMAC(secret, B) == H`, which still holds [7](#0-6) .
6. `Registry.process` invokes the registered handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)` [6](#0-5) , causing the application to act on the payload as if Shopify sent it for `victim-shop`, despite it never having done so.
