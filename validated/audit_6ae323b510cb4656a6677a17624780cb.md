### Title
Webhook `shop-domain` header is trusted for tenant identity without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `shop-domain` header — which is *not* part of the signed payload — as the tenant identity passed to the app's webhook handler. Since Shopify's webhook HMAC secret (`api_secret_key`/`client_secret`) is shared across all shops that install a given app, an attacker who controls one legitimate shop installation can capture a validly-signed webhook body from their own store and resubmit it with the `shop-domain` header rewritten to any victim shop, producing a webhook that passes HMAC validation but is attributed to the wrong tenant.

### Finding Description
The webhook `Request` object binds its HMAC exclusively to the raw body: [1](#0-0) 

while `shop` is read straight from an unauthenticated header and never cross-checked against anything derived from the signature: [2](#0-1) 

`Registry.process` validates only the HMAC, then immediately forwards `request.shop` to the app's handler as the authoritative tenant identity: [3](#0-2) 

The identity binding that should hold is:
`shop_claimed_in_header == shop_whose_key_produced_a_valid_HMAC_for_this_body`

But the HMAC only proves "this body was signed with *an* app-wide secret" — it says nothing about which shop the body belongs to, because the shared secret (`Context.api_secret_key`) is identical for every shop that has installed the app (confirmed by `HmacValidator.validate`, which signs with the single, non-shop-scoped secret): [4](#0-3) 

Consequently, any party who legitimately receives one correctly-signed webhook (e.g., because they installed the app on their own store) can detach the valid `(body, hmac)` pair from its true `shop-domain` header and pair it with an arbitrary victim `shop-domain` value, and the gem will accept it as authentic and hand it to the handler as if it originated from the victim.

### Impact Explanation
This breaks the tenant/identity boundary the HMAC is supposed to enforce and enables cross-tenant confusion: the app's webhook handler will process attacker-supplied (but validly-signed-for-a-different-shop) data under a victim shop's identity (`data.shop`), potentially triggering shop-scoped side effects (data writes, session lookups keyed by `shop`, order/customer state changes, GDPR/compliance webhook logic, etc.) against the wrong tenant. This matches the "Critical - cross-tenant access" impact category, since a merchant/attacker with only their own legitimate app installation can impersonate any other shop that also installed the same app.

### Likelihood Explanation
Requires only an unprivileged actor who has installed the target app on any store (a normal, unprivileged merchant action) — no access to `api_secret_key`, no access token, and no TLS interception is needed. All that's required is capturing one of their own valid, correctly-signed webhook deliveries (e.g., via their own logging/proxy/inspecting outbound network traffic to their own server) and replaying it with a modified `shop-domain` header.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) in the value that is authenticated, or otherwise bind the verified body to the specific shop before dispatch — e.g., require the caller to supply the expected shop for the session/handler being invoked and reject webhooks whose header shop doesn't match an expected/registered shop, rather than trusting the header value implicitly once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, obtaining legitimate webhook deliveries signed with the app's shared `client_secret`.
2. Attacker captures one such delivery: raw body `B` with header `x-shopify-hmac-sha256: H` (valid for `B`) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker sends a new POST to the app's webhook endpoint with the same body `B` and the same header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `B` only, which still matches `H`, so validation succeeds: [5](#0-4) 
5. `handler.handle` is invoked with `shop: "victim-shop.myshopify.com"` (from `request.shop`) even though the body/signature pair actually belongs to `attacker-shop.myshopify.com`, as shown by the metadata construction in `Registry.process`: [6](#0-5)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
