### Title
Relayer fee balance is zeroed before the cross-chain payout is confirmed, and the payout can be permanently blocked by a single admin-gated delivery key with no timeout to restore it - ([File: modules/pallets/relayer/src/withdrawal.rs])

### Summary
`pallet_ismp_relayer::withdraw` dispatches an ISMP POST request instructing the destination chain to pay out a relayer's accumulated fees, then unconditionally zeroes the relayer's `Fees` entry on the source chain — exactly the pattern in the reported `Cooler.rescind` bug: irreversible state mutation performed before/without any guarantee that the corresponding value transfer actually completes.

### Finding Description
`Pallet::withdraw` reads `available_amount`, dispatches a `DispatchPost` to the destination's host manager, and — as soon as `dispatch_request` merely succeeds in queueing the message (not in delivering/executing it) — zeroes the balance: [1](#0-0) 

Two properties combine to make this state clearing unsafe:

1. **No timeout.** The `DispatchPost` is built with `timeout: 0`, i.e. the request never expires and there is no `onPostRequestTimeout`-style path in this flow that could restore `Fees` if delivery never happens.
2. **Delivery is gated to a single admin key on EVM destinations.** For EVM destinations the message is addressed to `params.host_manager`, whose `onAccept` requires the delivering relayer to equal `_params.admin`: [2](#0-1) 

Since the fee-withdrawal body encodes `OnAcceptActions.Withdraw` (byte `0`) via `WithdrawalParams::abi_encode`, it is routed through this same admin-only `onAccept`: [3](#0-2) 

So the only address ever allowed to complete the payout is the configured host-manager `admin`, not an arbitrary relayer. If that admin key is offline, rotated away, or simply never submits the delivery for that specific relayer's withdrawal (no on-chain incentive/enforcement forces it to), the request sits undelivered forever — it cannot time out (`timeout: 0`) — while the relayer's `Fees` entry on the Substrate side has already been permanently zeroed.

### Impact Explanation
This is a High-severity permanent-freezing-of-funds bug: an unprivileged relayer's own earned protocol fees can become irrecoverable. The source-chain accounting record of what is owed is destroyed unconditionally at dispatch time, but the actual payout depends entirely on a privileged, single-key delivery path with no expiry/refund mechanism to recreate the claim if that delivery never occurs.

### Likelihood Explanation
Any relayer that has accumulated fees and calls `withdraw` for an EVM destination chain is exposed. The scenario does not require any malicious actor — an admin key that is lost, rotated, or simply lagging is enough to make the funds unrecoverable, and there is no code path (timeout, retry-with-refund, or role broadening) that restores the zeroed `Fees` entry.

### Recommendation
- Do not zero `Fees` until the withdrawal is confirmed delivered and executed on the destination (e.g. via a response/receipt callback), or
- Give the withdrawal request a finite `timeout` and implement a timeout handler that re-credits `Fees::<T>` on the source chain, mirroring how `EvmHost.dispatchTimeOut` restores `_requestCommitments` on failed delivery (`evm/src/core/EvmHost.sol` lines 856-877), and
- Reconsider gating `HostManager.onAccept` delivery of relayer fee withdrawals to the single `admin` relayer; either broaden delivery authorization for this specific action or ensure a permissionless fallback exists.

### Proof of Concept
1. Relayer accumulates `Fees[dest_chain][relayer] = X` on the Hyperbridge parachain.
2. Relayer calls `withdraw` (`modules/pallets/relayer/src/withdrawal.rs:81-187`) for an EVM `dest_chain`. `dispatch_request` succeeds (message merely queued/committed), so `Fees` is immediately set to zero at line 177.
3. The dispatched `DispatchPost` has `timeout: 0` (line 166), so it never expires.
4. On the EVM destination, only the configured `HostManager` `admin` address may call `onAccept` to execute the payout (`evm/src/core/HostManager.sol:134-148`). If that admin never delivers this message (key unavailable, deprioritized, rotated), the payout never executes.
5. `Fees` remains zero forever on the source chain with no timeout/refund path to restore it — the relayer's fee amount `X` is permanently lost despite having been legitimately earned and never actually paid out.
