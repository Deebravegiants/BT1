### Title
Stale delegate grants regain full account-spending authority after an NFT ownership round trip - (File: `contracts/controller/src/storage/account.rs`)

### Summary

A delegate grant is keyed only by `account_id` and the granting owner’s address, with no ownership epoch or transfer-version component. When the position NFT moves to a new owner, the stale grant remains stored; when the NFT returns to the original owner, the same grant becomes live again without any new authorization from that owner. A previously delegated, globally active position manager can then call `borrow` or `withdraw` and direct proceeds to itself. This is a stale-authority/lifecycle analog and permits theft of collateral or borrowed assets.

### Finding Description

`DelegateGrant` stores only `granted_by` and `delegates`; the type documentation explicitly notes that a grant can become live again if the NFT returns to `granted_by` before an intervening owner overwrites or deletes it. [1](#0-0) 

The controller resolves the account owner from the position NFT at operation time, rather than caching ownership in account metadata. [2](#0-1)  `get_delegates` then returns the stored delegate list whenever `grant.granted_by` equals that current owner. [3](#0-2)  Because no transfer epoch is compared, `Alice -> Bob -> Alice` restores the exact authorization state that existed before the first transfer.

The authorization gate accepts a caller when the caller is the current owner or both an active position manager and a member of the returned delegate list. [4](#0-3)  `add_delegate` authenticates the then-current owner and requires the delegate to be an active manager, but it does not bind the grant to that particular continuous ownership period. [5](#0-4) 

Once reactivated, the stale delegate can invoke account-spending paths. `process_borrow` loads the account, applies `require_owner_or_delegate`, accepts a caller-selected recipient, and settles borrow proceeds to that recipient subject only to post-operation solvency. [6](#0-5)  `withdraw` similarly accepts owner/delegate authority and supports caller-selected output through `to`. [7](#0-6) 

### Impact Explanation

High severity. If the returned account is debt-free, the stale delegate can withdraw its collateral directly. If it already has debt, the delegate can withdraw all collateral permitted by the solvency checks and borrow up to the account’s risk limit to an attacker-controlled recipient. The owner can therefore lose collateral outright or be left holding a maximally leveraged position while the delegate receives the borrowed assets. The result is theft of user funds and potentially forced liquidation losses.

### Likelihood Explanation

The exploit requires three conditions: the victim previously delegated to an active position manager, the position NFT leaves that owner, and the NFT later returns while the stored grant remains untouched and the manager remains active. Those are ordinary account-lifecycle operations rather than privileged actions, upgrades, oracle manipulation, or leaked keys. NFT sale cancellations, temporary transfers between user wallets, custodial migrations, or contract-mediated position transfers can create the ownership round trip. The prior delegate needs no new signature or transaction from the victim after the NFT returns.

### Recommendation

Bind delegate grants to an ownership epoch rather than an owner address. For example, have the position NFT maintain a monotonically increasing transfer counter for each token and expose it to the controller, store `owner_epoch` in `DelegateGrant`, and return delegates only when both `granted_by` and the stored epoch match the NFT’s current owner epoch. Alternatively, add an NFT transfer hook that notifies the controller to delete `ControllerKey::Delegates(account_id)` on every transfer. Merely comparing `granted_by` is insufficient because address equality cannot distinguish the original ownership period from a later ownership period.

### Proof of Concept

Assume `MANAGER` is an already governance-approved active position manager and `alice_account` holds USDC collateral.

```rust
// 1. Alice grants the manager once.
controller.add_delegate(
    &alice,
    &alice_account,
    &manager,
);

// 2. Alice transfers the position NFT to Bob.
position_nft.transfer(&alice, &bob, &u32::try_from(alice_account).unwrap());

// 3. While Bob owns it, no delegate write occurs.
//    The old grant remains stored because removal is lazy.

// 4. Bob later transfers the same NFT back to Alice.
position_nft.transfer(&bob, &alice, &u32::try_from(alice_account).unwrap());

// 5. The stale grant is live again: current owner == grant.granted_by.
//    For a debt-free account this withdraws all USDC to the manager.
controller.withdraw(
    &manager,
    &alice_account,
    &vec![&env, (usdc_hub_asset, 0)], // zero means full withdrawal
    &Some(manager),
);
```

At step 5, `account_owner` resolves to Alice; `get_delegates(..., owner = Alice)` returns Alice’s old grant because it was never purged; and `is_owner_or_delegate` accepts `manager`. No authorization from Alice occurs after the NFT returns, yet the manager receives the account’s collateral subject only to the normal withdrawal gates.

```rust
/// Accepts the owner or a registered, active manager delegated by that owner.
pub(crate) fn is_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,
) -> bool {
    if caller == owner {
        return true;
    }

        storage::get_position_manager(env, caller).is_some_and(|config| config.is_active);
    active_manager && storage::get_delegates(env, account_id, owner).contains(caller)
}
```

```rust
/// Borrows to `to` or the authorized owner/delegate, then checks solvency.
/// Persists supply alongside debt when the check restamps supply LTVs.
pub(crate) fn process_borrow(
    env: &Env,
    caller: &Address,
    account_id: u64,
    borrows: &Vec<HubPayment>,
    to: Option<Address>,
) {
    validation::require_authorized_caller(env, caller);

    let mut account = storage::get_account(env, account_id);
    require_owner_or_delegate(env, account_id, caller, &account.owner);

    let recipient = to.unwrap_or_else(|| caller.clone());
    let mut cache = Context::new(env);
    require_external_recipient(env, &mut cache, &recipient);
    let aggregated = payments::aggregate_positive_payments(env, borrows);

    validate_position_entry_gates(
        env,
        &account,
        &aggregated,
        &mut cache,
        AccountPositionType::Borrow,
    );
    settle_borrow(env, &mut account, &recipient, &aggregated, &mut cache);
```
