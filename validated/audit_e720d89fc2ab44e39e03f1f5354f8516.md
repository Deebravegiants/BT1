## Title
Attacker-inflated token vault balances can permanently panic `calc_take_pnl`, freezing swap, deposit, withdraw and PnL withdrawal on a pool - (File: `program/src/processor.rs`)

### Summary
The CVE-2022-20771 report describes a parser that panics/DoSes on attacker-supplied malformed input due to unchecked arithmetic on untrusted values. The reachable analog in this codebase is `Processor::calc_take_pnl` [1](#0-0) , which performs a chain of `checked_sub(...).unwrap()` and `checked_mul(...).unwrap()` operations on values derived directly from the live SPL token vault balances (`amm_pc_vault.amount`, `amm_coin_vault.amount`). Because any unprivileged party can inflate those vault balances via an ordinary SPL token transfer directly into the AMM's coin/pc vault accounts (no signer/authority checks required by the token program to receive funds), an attacker can force this internal computation into a state where a `checked_sub` underflows and `.unwrap()` panics.

### Finding Description
`calc_take_pnl` computes `x2` (the "post take-pnl" x value) via `Calculator::calc_x_power` and `integer_sqrt`, then computes `y2 = x2 * y1 / x1`, and finally `diff_x = x1 - x2` and `diff_y = y1 - y2` using `.checked_sub(...).unwrap()`: [2](#0-1) 

`x1`/`y1` are normalized decimals of `total_pc_without_take_pnl` / `total_coin_without_take_pnl`, which are themselves derived from the *actual* vault token balances via `calc_total_without_take_pnl_no_orderbook`: [3](#0-2) 

Since `y2 = x2 * y1 / x1` is a simple cross-multiplication and not a true invariant-preserving square root split, an asymmetric skew of the pool's `x1:y1` ratio (achievable by donating a large amount of only one token directly to `amm_coin_vault` or `amm_pc_vault`, without going through `Deposit`/`Swap`) can make `x2 > x1` or `y2 > y1` in edge cases, causing `x1.checked_sub(x2).unwrap()` or `y1.checked_sub(y2).unwrap()` to panic (`unwrap()` on `None`). All in-scope unprivileged flows funnel through `calc_take_pnl`: `Deposit` [4](#0-3) , `Withdraw` [5](#0-4) , and `WithdrawPnl` [6](#0-5) . `SwapBaseIn`/`SwapBaseOut` (v1/v2) instead call `calc_total_without_take_pnl_no_orderbook` directly on the same skewed vault balances for pricing [7](#0-6) , so the same donation can also corrupt swap pricing/underflow the pnl accounting path indirectly used by future deposits/withdrawals.

Critically, none of these functions validate that vault balances match some previously-recorded/expected state, or bound the ratio drift between `x1/y1` and `target.calc_pnl_x/calc_pnl_y` before performing the subtraction — there is only a `checked_mul` product comparison (`pool_pc*pool_coin >= calc_pc*calc_coin`) which does not prevent skewed ratios that satisfy the product inequality yet produce `x2 > x1` or `y2 > y1` from the cross-multiplied `y2` formula.

### Impact Explanation
Because the panicking `.unwrap()` sits inside `calc_take_pnl`, which is invoked from `Deposit`, `Withdraw`, and `WithdrawPnl`, a single low-cost donation transaction (a plain SPL `Transfer` to the public vault addresses, requiring no signer authority over the AMM) can push the pool into a state where every subsequent call to these instructions panics and aborts, since the corrupted vault balances persist until fixed. This constitutes a permanent freezing of LP funds (LPs cannot withdraw), pool PnL (owner cannot call `WithdrawPnl`), and further deposits, i.e., a Denial-of-Service on core pool operations reachable by any account, matching the severity bar (permanent freezing of user/LP funds) requested for this analog.

### Likelihood Explanation
The attack requires only knowledge of the AMM's public `coin_vault`/`pc_vault` addresses (visible on-chain) and enough tokens of one side to sufficiently skew the `x1:y1` ratio; no privileged signer, program upgrade, or off-chain component is needed. This is directly reachable from a single submitted transaction with attacker-chosen accounts/amounts (a standard SPL token transfer), fitting the "unprivileged swapper/LP" threat model in scope.

### Recommendation
- Replace `.unwrap()` in `calc_take_pnl`'s `diff_x`/`diff_y` computation with `checked_sub().ok_or(AmmError::CalcPnlError)?` (or equivalent saturating logic) so malformed/skewed states return a program error instead of panicking.
- Bound or reconcile vault balances against tracked pool state (e.g., require vault balances to only change through program-mediated instructions, or clamp the skew ratio) rather than trusting live SPL balances unconditionally for PnL math.
- Add fuzz/property tests for `calc_take_pnl` with adversarial `x1`,`y1` ratios (donation scenarios) to ensure no panics occur for any combination of `u64` vault balances.

### Proof of Concept
1. Deploy/observe an existing Raydium AMM pool; note its `coin_vault` and `pc_vault` public addresses.
2. Submit a standard `spl_token::instruction::transfer` sending a very large amount of the coin (or pc) token directly into `amm_coin_vault_info` (a permissionless action; no AMM authority signature required, only ownership of the sender's own token account).
3. Call `Withdraw`, `Deposit`, or `WithdrawPnl` on the pool. `calc_total_without_take_pnl_no_orderbook` picks up the inflated vault balance [3](#0-2) , producing a skewed `x1`/`y1` pair passed into `calc_take_pnl`.
4. Inside `calc_take_pnl`, `x2`/`y2` are computed via the cross-multiplication `y2 = x2*y1/x1` [8](#0-7) ; for sufficiently skewed inputs this yields `x2 > x1` or `y2 > y1`, causing `x1.checked_sub(x2).unwrap()` / `y1.checked_sub(y2).unwrap()` to panic [9](#0-8) , aborting the transaction and (since the donated balance persists on-chain) reproducing the panic on every subsequent call until the vault balance is restored — a persistent DoS on the pool's core instructions.

*Note: The exact numeric threshold at which `x2 > x1` or `y2 > y1` occurs depends on precise fixed-point arithmetic in `calc_x_power`/`integer_sqrt`/`restore_decimal`, and I was not able to execute the on-chain math to confirm concrete threshold values within this session; a background agent with test/fuzzing tooling should be used to derive and confirm exact PoC parameters before treating this as fully validated.*

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
