Confirmed. This is a real, in-scope analog: the webhook `shop-domain` header is trusted to attribute payload data to a tenant, but it is **not covered by the HMAC signature**, which only signs the raw body.

### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0)  while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers [2](#0-1) . `Utils::HmacValidator.validate` verifies that signature against the same body-only string with the app's `api_secret_key` [3](#0-2) , so the HMAC check proves only "this body was signed with our app secret" and says nothing about which shop the header claims to be from. `Registry.process` then trusts `request.shop` at face value to build the `WebhookMetadata` handed to the app's handler [4](#0-3) .

### Finding Description
The intended binding is: `hmac == HMAC(secret, body)` should imply `shop == the tenant that actually generated body`. In this gem that equality does not hold because the `shop` field is never part of the signed material — the equality that is actually checked is `hmac == HMAC(secret, body)` **independent of** `shop`.

Since `api_secret_key` is a single app-wide secret shared across every shop that has installed the app (not a per-shop secret), any actor who can install the app on their own store (an unprivileged action available to any internet user) will legitimately receive HMAC-valid `(body, hmac)` pairs for their own webhooks. That attacker can then replay the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header. `HmacValidator.validate` will still return `true`, because it only re-derives the signature from `raw_body` [5](#0-4) , and `Registry.process` will invoke the host application's handler with `WebhookMetadata` claiming the victim shop as the source [6](#0-5) .

### Impact Explanation
This lets an attacker inject attacker-controlled webhook data (order, product, GDPR, or other topic payloads) that is falsely attributed to a victim shop of their choosing. Any host application logic that uses `data.shop` to scope database writes, trigger per-tenant side effects, or route data (a documented and expected usage pattern per `docs/usage/webhooks.md`) can be corrupted with attacker-supplied content associated with a shop the attacker does not own — a cross-tenant integrity breach.

### Likelihood Explanation
The prerequisite (installing the app on one's own store to obtain one genuine `(body, hmac)` pair) is available to any unprivileged internet user, since app installation itself requires no special privilege. No knowledge of `api_secret_key` is needed; only replay of an intercepted/self-generated valid pair with a modified header is required, and this gem's `Request`/`HmacValidator`/`Registry.process` pipeline performs no check binding `shop` to the signed payload.

### Recommendation
Include `shop` (and ideally `topic`, `webhook_id`, `api_version`) in the signable string verified by the HMAC, or independently verify that the `shop-domain` header corresponds to a shop with an active webhook registration/session before trusting it in `WebhookMetadata`.

### Proof of Concept
1. Install the target app on attacker-owned store `attacker.myshopify.com`; capture a genuine webhook delivery — raw body `B` and header `x-shopify-hmac-sha256: H` (valid because `H == HMAC(api_secret_key, B)`).
2. POST to the app's webhook endpoint with the same body `B` and header `H`, but replace `x-shopify-shop-domain: attacker.myshopify.com` with `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` returns `true` (only `B` and `H` matter) [5](#0-4) ; `Registry.process` calls the handler with `shop: "victim.myshopify.com"` [6](#0-5) , causing the host app to process attacker-controlled data under the victim tenant's identity.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
