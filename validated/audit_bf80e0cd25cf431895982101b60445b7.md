### Title
Rebasing input tokens escrowed by IntentGatewayV2/ExtrinsicIntents are not accounted for and their yield is permanently stuck - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentGatewayV2` (and its `ExtrinsicIntents`/`IntrinsicIntents` implementations) escrow a user's input tokens by recording a fixed amount in `_orders[commitment][token]`, measured once at `placeOrder` time via a balance-delta snapshot. If the escrowed token is a rebasing token (balance increases automatically while held by the contract), the extra balance accrued between `placeOrder` and the eventual `RedeemEscrow`/`RefundEscrow` withdrawal is never tracked or released to anyone — it becomes permanently stuck in the gateway contract, exactly analogous to the referenced Allo `_fundPool`/pool-accounting issue.

### Finding Description
At order placement, the escrow amount stored per commitment/token is fixed to the balance actually received at that moment: `order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;` and later `_orders[commitment][token] += reducedInputs[i].amount;` [4](#0-3) . On fill/settlement, `_withdraw` only ever transfers exactly the recorded `_orders[commitment][token]` amount and decrements the mapping — it never re-checks the gateway's live token balance: `uint256 escrowed = _orders[body.commitment][token]; ... _orders[body.commitment][token] = escrowed - amount; IERC20(token).safeTransfer(beneficiary, amount);` [5](#0-4) .

The only sweep mechanism, `SweepDust`, only moves amounts that were explicitly recorded via `DustCollected` (protocol fees and surplus over the required input amount) [1](#0-0) ; it has no way to identify or claim balance growth from a rebasing token that was not part of a `DustCollected` event, since that growth accrues silently on the ERC-20 balance itself rather than through any transfer the contract observes.

Consequently, if governance (or a user placing an order using an unlisted/arbitrary ERC-20, since `IntentGatewayV2` accepts any token address supplied in `order.inputs`) escrows a rebasing token, any positive rebase applied to the gateway's balance while the order is pending is orphaned: it is neither delivered to the solver/filler on `RedeemEscrow`, nor returned to the user on `RefundEscrow`/cancellation, nor recoverable via `SweepDust`.

### Impact Explanation
This is a permanent freezing-of-funds bug: any positive rebase yield on an escrowed rebasing token accumulates in the `IntentGatewayV2`/`ExtrinsicIntents` contract with no code path to recover it, for as long as such tokens continue to be used as order inputs. Because `placeOrder` does not restrict `order.inputs[i].token` to a governance-curated allowlist, any user submitting an order can cause this class of value to become trapped, and the amount trapped grows with usage.

### Likelihood Explanation
Likelihood depends on whether rebasing tokens are ever used as intent inputs on a deployed chain. Since `IntentGatewayV2.placeOrder` takes an arbitrary token address per order with no allowlist check visible in the escrow path (unlike protocol/fee token governance parameters), any unprivileged user can place an order using a rebasing ERC-20 as input, making this directly reachable by an ordinary intent submitter rather than requiring privileged action.

### Recommendation
Either explicitly disallow known-rebasing/elastic-supply tokens at the protocol level, or change escrow accounting to track shares/ratios instead of fixed absolute amounts, or extend the dust/sweep mechanism to also capture the delta between a token's live balance and the sum of all currently-escrowed amounts for that token, allowing governance to reclaim genuine rebase yield without touching funds still owed to pending orders.

### Proof of Concept
1. User calls `placeOrder` with `order.inputs[0]` set to a rebasing ERC-20 token and amount `A`; the gateway measures and stores `_orders[commitment][token] = A` (post balance-delta) [2](#0-1) .
2. Time passes; the rebasing token increases every holder's balance, including the gateway's, so `IERC20(token).balanceOf(gateway)` is now `A + yield` while `_orders[commitment][token]` still reads `A`.
3. A solver fills the order; Hyperbridge delivers `RedeemEscrow`, and `onAccept`/`_withdraw` transfers exactly `A` to the filler and zeroes `_orders[commitment][token]` [3](#0-2) .
4. `yield` remains in the gateway contract's balance with no order referencing it and no `SweepDust` entry for it, permanently unclaimable by the user, the filler, or governance.
