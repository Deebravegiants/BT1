### Title
Full remaining fee credit is forfeited (not just `corrected_fee`) and misreported as `corrected_fee_with_tip` when a transaction's own dispatch kills the payer's account - ([File: substrate/frame/transaction-payment/src/payment.rs])

### Summary
In `FungibleAdapter::correct_and_deposit_fee`, if the dispatched call itself removes all providers/reference count from `who` (e.g. a "transfer all" pattern), `frame_system::Pallet::<T>::account_exists(who)` returns `false` at post-dispatch time, and the code intentionally forwards the *entire* `remaining_credit` (the amount withdrawn up-front, `fee_with_tip`) to `OU::on_unbalanceds` instead of splitting off only `corrected_fee` and refunding the rest. This means the user is charged the full pre-dispatch `fee_with_tip` even though weight refund logic determined a smaller `corrected_fee_with_tip` was owed, and no error or distinguishing event is surfaced for this over-collection.

### Finding Description
The relevant logic is: [1](#0-0) 

When `account_exists(who)` is `true`, the code splits `remaining_credit` into `fee_credit` (= `corrected_fee`) and `refund_credit` (the excess), attempting `F::resolve(who, refund_credit)` to give the excess back. When `account_exists(who)` is `false` (account was killed during the call's own execution — e.g., the call transferred away the account's entire balance / removed all providers), the code takes the *whole* `remaining_credit` as `fee_credit` — skipping the split entirely — and passes it straight to `OU::on_unbalanceds`. The inline comment `// skip refund if account was killed by the tx` shows this is a deliberate design choice, not an accidental omission.

The attacker path: a normal signed user submits an extrinsic whose call logic (reachable via ordinary balances/proxy/multisig dispatch) transfers away all funds/providers of `who` before the pallet's `post_dispatch` hook runs `correct_and_deposit_fee`. Because `fee_with_tip` was withdrawn upfront in `withdraw_fee` (via `F::withdraw` with `Preservation::Preserve`) before the call executes, the withdrawal itself does not require the account to remain alive afterward — the account can still die later purely due to the call's own effects. Consequently `corrected_fee < fee_with_tip` (declared weight >> actual weight) combined with account death causes 100% of `fee_with_tip` to be forwarded to `OU`, not the discounted `corrected_fee`.

Separately, the event emitted by the pallet (`TransactionFeePaid`) is constructed from the `corrected_fee_with_tip` value computed by the runtime *before* calling `correct_and_deposit_fee`, not from what was actually resolved/forwarded inside the adapter. Since `correct_and_deposit_fee` returns `Ok(())` regardless of which branch was taken, there is no way for callers or event consumers to detect that the full `fee_with_tip` (rather than `corrected_fee_with_tip`) was actually confiscated in the account-killed branch.

### Impact Explanation
This causes a real, self-inflicted accounting asymmetry: a user whose own transaction kills their account is overcharged up to `fee_with_tip - corrected_fee` beyond what fee-correction determined was owed, with the excess unconditionally donated to `OU::on_unbalanceds` and misreported by `TransactionFeePaid` as if only `corrected_fee_with_tip` was charged. This matches the scoped impact ("fee overcharge / stuck accounting asymmetry ... testable as an accounting invariant break") — it is not theft from other users, but it is a genuine violation of the stated invariant that "fee correction should never confiscate more than corrected_fee."

### Likelihood Explanation
Fully reachable and reproducible by any unprivileged signed account: the attacker only needs to submit a call (e.g. a "transfer all remaining balance" call, or any call that removes all providers as a side effect) combined with a weight declaration overestimating actual execution weight so `corrected_fee < fee_with_tip`. No special privileges, races, or governance actions are required — this is deterministic given the described call sequence.

### Recommendation
When `account_exists(who)` is `false` post-dispatch, still attempt to compute `corrected_fee` and only forward the excess `remaining_credit - corrected_fee` to `OU`, treating the un-refundable remainder as unavoidable dust (or explicitly document/emit a distinguishing event, e.g. a `FeeOverCollected`/`AccountKilledPreventedRefund` event) so the discrepancy between the intended `corrected_fee_with_tip` and the actually collected amount is observable rather than silently absorbed into `TransactionFeePaid`.

### Proof of Concept
Rust unit test in `substrate/frame/transaction-payment/src/tests.rs`, mirroring `asset_account_killed_post_withdraw_emits_full_fee_event` from `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/tests.rs`:
1. Configure a mock runtime using `FungibleAdapter` with a call whose dispatch transfers the account's entire balance to another account (killing all providers), and declare a `DispatchInfo` weight noticeably larger than actual post-dispatch weight so `corrected_fee < fee_with_tip`.
2. Execute the extrinsic via `SignedExtension`/`ChargeTransactionPayment` post-dispatch hook (or directly invoke `withdraw_fee` then the call then `correct_and_deposit_fee`).
3. Assert: (a) `frame_system::Pallet::<Test>::account_exists(who)` is `false` after the call; (b) the total amount forwarded to `OU::on_unbalanceds` (captured via mock `OnUnbalanced`) equals `fee_with_tip`, not `corrected_fee`; (c) the emitted `TransactionFeePaid` event's `actual_fee` field equals `corrected_fee_with_tip`, which is strictly less than what was actually deducted from the user — demonstrating the mismatch between reported and actual fee collection.
