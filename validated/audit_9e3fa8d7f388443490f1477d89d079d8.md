### Title
Signature computed by `make_signature` does not bind `signup_id` or `signup_reason`, allowing biometric-proof replay/misattribution across signup contexts - (File: src/plans/enroll_user.rs)

### Summary
`KeystoreAccount.isValidSignature` in the external report is vulnerable because the signed hash omits a domain/context binding (the contract address), letting a valid signature be replayed in an unintended context. The analogous pattern exists in orb-core's `make_signature` function, used to produce the secure-element-backed proof that accompanies a signup submission: the hash it signs commits only to `ORB_ID`, `user_id`, and pipeline/iris-code version strings, but never to `signup_id` or `signup_reason`. The resulting signature is then sent alongside those unsigned fields to the backend, so the cryptographic proof does not bind to the specific signup transaction it is meant to authenticate.

### Finding Description
`make_signature` builds the signed digest as: [1](#0-0) 

It hashes `ORB_ID`, the `user_id` from the QR code, and per-eye iris/mask codes and their version strings, then signs via the secure element: [2](#0-1) 

This signature is computed once per enrollment attempt and then submitted together with `signup_id` and `signup_reason` as **separate, unsigned** multipart fields in the backend request: [3](#0-2) 

Because `signup_id` and `signup_reason` are not part of the signed payload, the secure-element signature that is supposed to attest "this iris/user data was genuinely processed by this Orb" carries no cryptographic link to *which* signup transaction, nor to whether the attempt was flagged `Normal`, `Failure`, or `Fraud`: [4](#0-3) [5](#0-4) 

This mirrors the reported bug class exactly: a hash that omits a context/domain field (there, the verifying contract address; here, `signup_id`/`signup_reason`) enables the same valid signature to be presented in a different context than the one intended, because nothing in the signed data prevents it.

By contrast, the personal custody package signing in `Package::build` explicitly salts and hashes `signup_id` and `signup_reason` into the signed `hashes.json` blob before calling `secure_element::sign`, demonstrating that the codebase is aware such binding is necessary elsewhere but omitted it in `make_signature`: [6](#0-5) [7](#0-6) 

### Impact Explanation
Because the secure-element signature in `make_signature` binds only `(ORB_ID, user_id, iris/mask codes+versions)` and not `signup_id`/`signup_reason`, a signature produced for one signup submission carries no cryptographic guarantee tying it to the specific `signup_id` or to the fraud/failure classification under which the backend evaluates it. If the same biometric pipeline output (deterministic for a given capture) is resubmitted with a different `signup_id` or with `signup_reason` altered from `Fraud`/`Failure` to `Normal` (or vice versa), the backend has no signed evidence to detect the mismatch — the "signature" field alone cannot prove the reason/id pairing is authentic. This is a cross-signup state-bleed / misattribution risk: it weakens the backend's ability to trust that a validated secure-element signature corresponds to the exact signup attempt and fraud classification it accompanies, potentially enabling a fraud-flagged attempt to be re-presented as a normal one, or a signup record to be misattributed to a different signup session for the same user.

### Likelihood Explanation
Exploitation requires the ability to influence what `signup_id`/`signup_reason` value accompanies an already-computed signature before/while it's posted to the backend, or to capture and replay a previously produced `(signature, iris data)` pair against a different `signup_id`. Since `signup_id` and `signup_reason` are determined by orb-core's own control flow (`MasterPlan`/`enroll_user::Plan`) rather than external attacker input directly, the primary realistic trigger is a logic bug, retried/duplicated request path, or a compromised/misbehaving component within the on-device pipeline (e.g., an agent that sets or overrides `signup_reason` after the signature is computed) exploiting the lack of binding. This is a lower-likelihood, defense-in-depth-style gap rather than a trivially externally triggerable bug — I could not fully trace the exact call path that sets/overrides `SignupReason` at runtime within the time available, so the concrete external attacker precondition for altering `signup_reason` independent of the signed data remains unconfirmed.

### Recommendation
Include `signup_id` and `signup_reason` (and ideally a monotonic nonce/timestamp) in the digest signed by the secure element in `make_signature`, mirroring the approach already used in `personal_custody_package.rs`'s `make_info_json`/`Package::build`, so the signature cryptographically commits to the exact signup transaction and its classification, preventing any replay or reason-substitution across signup contexts.

### Proof of Concept
1. Observe that `make_signature` (src/plans/enroll_user.rs:290-304) signs only `ORB_ID`, `user_id`, and iris/mask code+version fields.
2. Observe that `signup_post::request` (src/backend/signup_post.rs:100-133) sends `signup_id` and `signature.map_or(...)` as independent form fields, with `signup_reason` also sent unsigned.
3. Because `signup_id`/`signup_reason` are outside the signed digest, any component or logic path capable of reusing a previously computed `(signature)` value with a different `signup_id` or `signup_reason` string would produce a backend request that still carries a "valid" secure-element signature, since the signature verification (at whatever end validates it) cannot detect the substitution — analogous to replaying a `KeystoreAccount.isValidSignature`-style signature across differing execution contexts due to missing domain binding.

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}

/// Every signup needs to be tagged with a reason for the backend to process it.
#[derive(Serialize, Debug, Default, Copy, Clone, PartialEq, Eq)]
pub enum SignupReason {
    /// Signup was successfully processed on the Orb.
    #[default]
    Normal,
    /// Signup failed due to some agent dying in the biometric pipeline or some internal error.
    Failure,
    /// Signup was detected as a fraud attempt at the orb (not to be confused with the backend fraud checks).
    Fraud,
}

/// Converts the signup reason to screaming snake case.
impl SignupReason {
    /// Converts the signup reason to screaming snake case. Using Serde's renaming won't work because Serde
    /// automatically adds "" (quotes) to the produced string. I.e. the output from Serde is "\"NORMAL\"".
    #[must_use]
    pub fn to_screaming_snake_case(&self) -> &str {
        match self {
            SignupReason::Normal => "NORMAL",
            SignupReason::Failure => "FAILURE",
            SignupReason::Fraud => "FRAUD",
        }
    }
}
