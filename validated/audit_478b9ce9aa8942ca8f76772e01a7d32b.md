## Title
Unbacked cross-chain mint via fee-on-transfer/deflationary underlying tokens in `WrappedHyperFungibleToken.send()` - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.send()` locks the underlying ERC20 token with `safeTransferFrom` and then dispatches a cross-chain message encoding the *requested* `params.amount`, without ever verifying how many tokens the contract actually received. On the destination chain, `onAccept()` mints exactly `message.amount` unconditionally [1](#0-0) . If the configured `_underlying` token charges a transfer fee, is deflationary/rebasing, or otherwise delivers less than the requested amount to the contract, the destination chain mints more tokens than were actually locked on the source chain — an unbacked mint that permanently desyncs the bridge's 1:1 backing invariant. This is the same root-cause class as the reported ERC777 double-credit bug: crediting/minting based on a caller-supplied "amount" instead of the balance actually received.

### Finding Description
`send()` performs the lock step like this: [2](#0-1) 

Note that in the non-WETH branch it calls `IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount)` and then immediately builds the dispatch message using the same `params.amount` — there is no balance-before/balance-after check.

Compare this to `IntentGatewayV2.placeOrder()`, which explicitly guards against exactly this class of bug by measuring the actual balance delta before crediting escrow: [3](#0-2) 

`WrappedHyperFungibleToken` has no equivalent safeguard. The cross-chain message body embeds the unverified `params.amount`: [4](#0-3) 

On the destination chain, `onAccept()` mints `message.amount` unconditionally to the beneficiary with no cross-check against what was actually locked: [5](#0-4) 

Any deviation between "amount debited from `msg.sender`" and "amount actually received by the contract" (fee-on-transfer tax, deflationary burn-on-transfer, rebasing token, or any ERC20 that does not move exactly the requested amount) is silently absorbed as extra unbacked supply minted on the destination side.

The same unverified-amount assumption also affects the timeout-refund path, which pays out `message.amount` from the contract's own balance: [6](#0-5) 

If the underlying token is fee-on-transfer, this refund path can also revert or double-pay relative to what is actually held, causing under-collateralization or refund failures.

### Impact Explanation
Every `send()` call with a non-standard underlying token mints more wrapped tokens on the destination chain than are actually locked on the source chain. This is a direct unbacked-mint condition: the wrapper's total minted supply on destination chains permanently exceeds the value actually escrowed on the source chain. Over repeated calls this drains the peg, eventually leaving later redeemers unable to unlock their tokens on the source chain (funds effectively frozen/lost for the last holders) — a protocol insolvency exploitable by any ordinary user, not requiring any privileged action.

### Likelihood Explanation
Reachable by any unprivileged user calling `send()` a single time — no special preconditions beyond the pool being configured with a token that isn't a "clean" ERC20 (fee-on-transfer, deflationary, or rebasing), which are commonplace tokens in the wild. The bug requires no admin misconduct or governance compromise: an honestly-configured but non-standard token is enough to trigger the mismatch on every transfer.

### Recommendation
Mirror the pattern already used in `IntentGatewayV2.placeOrder()`: measure `balanceOf(address(this))` before and after the `safeTransferFrom` call, and use the actual delta as the dispatched `amount` (and as the amount credited/minted on the destination side), rather than trusting the caller-supplied `params.amount`. Alternatively, explicitly restrict `_underlying` to tokens verified to transfer exact amounts (as documented for `StreamingYieldVault`), and reject configuration of fee-on-transfer/rebasing/ERC777-hooked tokens.

### Proof of Concept
1. Owner configures `WrappedHyperFungibleToken` with `_underlying` = a fee-on-transfer ERC20 that takes a 1% fee on `transferFrom` (a common token pattern, e.g. certain deflationary/tax tokens).
2. User calls `send({ amount: 1000e18, dest: ..., to: ... })`.
3. `safeTransferFrom(user, address(this), 1000e18)` results in the contract only receiving `990e18` (1% fee burned/redirected), but `params.amount = 1000e18` is still embedded into the dispatched `Message`.
4. On the destination chain, `onAccept()` decodes `message.amount = 1000e18` and calls `_mint(beneficiary, 1000e18)` — 10e18 more than was ever actually locked on the source chain.
5. Repeating this call systematically inflates destination-chain supply beyond source-chain collateral, until source-chain withdrawals cannot be honored for everyone, permanently freezing/losing funds for later redeemers.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
