### Title
Zero-fee-on-transfer input tokens can escrow zero value while the maker's order still demands a full-value output - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.placeOrder` measures the actual amount of an input token received via `balanceAfter - balanceBefore` to support fee-on-transfer tokens, but never checks that the resulting received amount is greater than zero when the protocol fee is disabled. This mirrors the OpenQ `_receiveERC20` finding, where `balanceAfter >= balanceBefore` allows a zero-value transfer to be silently accepted as "funded."

### Finding Description
In the non-predispatch branch of `placeOrder`, the gateway only checks that the *requested* input amount is non-zero, not the amount actually received after the transfer: [1](#0-0) 

```solidity
for (uint256 i; i < inputsLen;) {
    if (order.inputs[i].amount == 0) revert InvalidInput();
    ...
    uint256 balBefore = IERC20(token).balanceOf(address(this));
    IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
    order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
    ...
}
```

If `order.inputs[i].amount` becomes `0` after this subtraction (e.g. because `token` is a fee-on-transfer/rebasing token that levies a 100% fee, or a malicious token whose `transferFrom` no-ops without reverting), the code proceeds to Phase 2: [2](#0-1) 

The zero-amount check `if (originalAmount == 0) revert InvalidInput();` only exists inside the `if (protocolFeeBps > 0)` branch. When `protocolFeeBps == 0` (a valid, commonly-used configuration — either globally via `_params.protocolFeeBps` or per-destination via `_destinationProtocolFees`), `reducedInputs = order.inputs;` is used as-is with no zero check at all.

Phase 3 then escrows this zero amount without complaint: [3](#0-2) 

```solidity
for (uint256 i; i < inputsLen;) {
    address token = address(uint160(uint256(order.inputs[i].token)));
    if (_orders[commitment][token] != 0) revert InvalidInput();
    _orders[commitment][token] = reducedInputs[i].amount; // can be 0
    ...
}
```

The identical gap exists in the predispatch/sweep branch, where `received` for a given input can also settle to `0` with no downstream check: [4](#0-3) 

Meanwhile, `order.output.assets` (what the filler/solver must pay out) is completely independent of the input measurement and is committed to unchanged. `fillOrder` requires `order.inputs.length == options.outputs.length` but does not validate that each input amount is non-zero before routing to `_fillSameChain`/`_fillCrossChain`, so a solver filling the order pays the full output while receiving an escrow entry of `0` for that input token.

### Impact Explanation
An order maker can place an order using an ERC20 input token that yields zero net balance change (a fee-on-transfer token with 100% fee, a broken/malicious token, or one they control) while specifying real, valuable `order.output.assets`. The order commitment is still generated and emitted via `OrderPlaced`, appearing to solvers as a normal, fundable intent. A solver that fills it (`fillOrder` → `_fillSameChain`/`_fillCrossChain`) delivers the requested output tokens to the beneficiary but the escrow backing the input side is `0`, i.e., the solver is not compensated with any real value from escrow. This is a direct funds-loss vector for solvers/relayers and a way to mint a "free" cross-chain intent fill, which maps to concrete theft of funds under the validation criteria.

### Likelihood Explanation
Likelihood is Medium-High: it requires only a single `placeOrder` transaction from an unprivileged user with a custom/zero-fee-on-transfer ERC20 as input and no special protocol privilege. Any deployment with `protocolFeeBps == 0` (globally or for a specific destination, both are supported first-class configurations) is exposed. A solver would need to fill without independently re-verifying escrowed input balances, but nothing in the on-chain interface signals the zero-escrow condition to naive/automated fillers, and the event/commitment data looks like a legitimate order.

### Recommendation
Add an explicit check that the actually-received/reduced input amount is greater than zero for every input, unconditionally (not only inside the `protocolFeeBps > 0` branch), in both the predispatch and non-predispatch code paths of `placeOrder`:

```solidity
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
if (order.inputs[i].amount == 0) revert InvalidInput();
```

and similarly after computing `received` in the predispatch sweep loop, and before entering the `protocolFeeBps == 0` else-branch in Phase 2 (or by moving the zero-check outside the `if (protocolFeeBps > 0)` conditional entirely so it always executes on `reducedInputs[i].amount`).

### Proof of Concept
1. Deploy a custom ERC20 whose `transferFrom` succeeds but transfers `0` tokens to the recipient (or a legitimate 100%-fee-on-transfer token), fully analogous to `FeeOnTransferToken` used in the repo's own tests: [5](#0-4) .
2. Configure the gateway with `protocolFeeBps == 0` (default/no destination-specific fee set) — a supported, normal configuration path: [6](#0-5) .
3. Call `placeOrder` with `inputs = [{token: zeroFeeToken, amount: X}]` and `output.assets` set to a real, valuable token/amount. Since `token` returns `balanceAfter - balanceBefore == 0`, `order.inputs[0].amount` becomes `0`; Phase 2's `else { reducedInputs = order.inputs; }` skips the zero check because `protocolFeeBps == 0`, and Phase 3 stores `_orders[commitment][token] = 0`.
4. A solver observing the `OrderPlaced` event calls `fillOrder`, delivering the full `order.output.assets` to the beneficiary, while the maker's escrow entry for the input token is `0` — the solver receives nothing for the input side. [7](#0-6)

    function fillOrder(Order calldata order, FillOptions calldata options) public payable nonReentrant {
        uint256 blockNumber = _blockNumber();
        if (order.deadline < blockNumber) revert Expired();
        // The solver's own bound on how long its quoted price stands. Zero means unbounded,
        // which is the right default for a solver filling directly — it is only at risk from
        // its own staleness. It matters for a bid signed through the coprocessor, where the
        // order placer chooses the moment of execution and nothing else caps the wait.
        if (options.validUntil != 0 && blockNumber > options.validUntil) revert FillExpired();
        bytes32 commitment = keccak256(abi.encode(order));

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain && orderSource != currentChain) revert WrongChain();
        if (!isSameChain && orderDest != currentChain) revert WrongChain();

        if (_filled[commitment] != address(0)) revert Filled();

        if (_params.solverSelection) {
            bytes32 storedSelectionHash;
            assembly {
                storedSelectionHash := tload(commitment)
            }

            bytes32 expectedSelectionHash = keccak256(abi.encode(msg.sender, order.session));
            if (storedSelectionHash != expectedSelectionHash) revert Unauthorized();
        }

        uint256 outputsLen = order.output.assets.length;
        if (options.outputs.length != outputsLen) revert InvalidInput();
        if (order.inputs.length != outputsLen) revert InvalidInput();

        if (isSameChain) {
            _fillSameChain(order, options, commitment);
        } else {
            _fillCrossChain(order, options, commitment);
        }
    }

/// @dev ERC20 with a configurable transfer fee (in basis points).
contract FeeOnTransferToken {
    string public name = "FeeOnTransferToken";
    string public symbol = "FOT";
    uint8 public decimals = 18;
    uint256 public totalSupply;
    uint256 public feeBps;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    constructor(uint256 _feeBps) {
        feeBps = _feeBps;
    }

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        totalSupply += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        return _transfer(msg.sender, to, amount);
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
