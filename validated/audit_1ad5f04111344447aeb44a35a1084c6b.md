### Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted for tenant dispatch without HMAC coverage - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then dispatches the handler using the `shop`, `topic`, and `webhook_id` values taken directly from HTTP headers that are **not** included in the signed payload. An attacker who can obtain one valid `(body, hmac)` pair from the app's own webhook secret (e.g., by installing the app on a store they control) can replay that exact body/HMAC to the same public webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop, causing the app to process attacker-controlled data under the victim tenant's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` computes and compares the HMAC only against `to_signable_string` (i.e., the body): [4](#0-3) 

`Registry.process` treats a passing HMAC check as full authentication of the request, then hands the handler the unverified `shop` (and `topic`/`webhook_id`) values: [5](#0-4) 

The identity binding that should hold is: `hmac_verified(raw_body) == authenticated(shop, topic, webhook_id, body)`. In the current implementation, only `hmac_verified(raw_body)` is true; `shop`, `topic`, and `webhook_id` are unauthenticated header values that the handler nonetheless trusts as the tenant/topic identity, per the gem's own documented usage pattern (`shop_domain: data.shop`): [6](#0-5) [7](#0-6) 

The docs explicitly claim `Registry.process` "will verify the request did indeed come from Shopify," which is only true for the body content, not the shop/topic/webhook_id headers used to route and attribute that body.

### Impact Explanation
Because `shop` is not covered by the HMAC, an attacker who legitimately installs the app on a shop they control (an ordinary, unprivileged action — installing a public app or using a free Shopify partner/dev store) will receive real webhook deliveries with a valid `x-shopify-hmac-sha256` computed over the body using the app's actual `client_secret`. The attacker can capture one such `(raw_body, hmac)` pair and replay it to the app's public webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop that also uses the app. `HmacValidator.validate` will accept it (the body and secret are unchanged), and `Registry.process` will invoke the handler with `shop: <victim shop>` and attacker-controlled `body`. Any handler following the gem's documented pattern will act on this data as if it originated from the victim tenant — this is a cross-tenant data-injection/spoofing primitive achieved without any of the victim's credentials, satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
The prerequisite is only that the attacker can install/operate the target app on a shop of their own — a normal, unprivileged action for any Shopify merchant or dev-store owner, requiring no leaked secrets, no access token theft, and no social engineering. Capturing one legitimate `(body, hmac)` pair from their own installation and replaying it with a different `shop` header is a straightforward HTTP replay.

### Recommendation
Bind the tenant/topic identity into the authenticated payload before trusting it: either (a) include `shop`, `topic`, and `webhook_id` header values in the string that is HMAC-verified (mirroring how `AuthQuery#to_signable_string` binds `shop` into its signed string), or (b) cross-check the `shop` header against an independently known, already-authenticated session/shop record before dispatching to the handler, rejecting the request if they don't match. At minimum, the docs and API should stop asserting that `process` fully "verifies the request did indeed come from Shopify" when only the body is covered.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` (their own shop) and registers a webhook, e.g. `orders/create`.
2. Shopify delivers a webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)` — computed exactly as in [8](#0-7) .
3. Attacker captures `(B, H)` (they control the receiving server/logs for their own shop's webhook).
4. Attacker sends a new request to the same public webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses headers, `HmacValidator.validate` succeeds because it only checks `B` against `H` ( [9](#0-8) ), and the handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)` — attributing attacker-controlled data to the victim shop.
