### Title
Reachable division-by-zero panic in `Calculator::calc_x_power` via `calc_take_pnl` permanently DoSes Deposit/Withdraw/WithdrawPnl - (File: program/src/math.rs, program/src/processor.rs)

### Summary
`Calculator::calc_x_power` performs an unchecked `checked_div(current_y).unwrap()` [1](#0-0)  and `Processor::calc_take_pnl` also does `x2.checked_mul(y1).unwrap().checked_div(x1).unwrap()` [2](#0-1) . Both `x1`/`y1` are derived from `total_pc_without_take_pnl`/`total_coin_without_take_pnl`, which are computed as `vault_amount.checked_sub(amm.state_data.need_take_pnl_*)` [3](#0-2) . If either value reaches exactly zero, the subsequent normalized value (`x1` or `y1`) is `0`, and the unconditional `unwrap()` on a division by that zero value panics, aborting the transaction with no error handling.

### Finding Description
`calc_take_pnl` is invoked from `process_deposit`, `process_withdraw`, and `process_withdrawpnl` [4](#0-3) [5](#0-4) [6](#0-5) , all instructions reachable by unprivileged liquidity providers (or, for WithdrawPnl, whoever holds the `pnl_owner` role, but the crash condition itself is driven purely by pool state that any swapper can influence). Inside `calc_take_pnl`, when the pool-value check passes (`pool_pc_amount * pool_coin_amount >= calc_pc_amount * calc_coin_amount`), the code calls `Calculator::calc_x_power(target.calc_pnl_x, target.calc_pnl_y, x1, y1)` where the last step is `.checked_div(current_y).unwrap()` with `current_y = y1` [1](#0-0) . Immediately after, `y2 = x2.checked_mul(y1).unwrap().checked_div(x1).unwrap()` divides by `x1` [2](#0-1) .

`x1` and `y1` come from `Calculator::normalize_decimal_v2(total_pc_without_take_pnl, ...)` and `normalize_decimal_v2(total_coin_without_take_pnl, ...)` [7](#0-6) , and these totals are `vault.amount.checked_sub(amm.state_data.need_take_pnl_pc/coin).ok_or(...)` [3](#0-2) . Because the subtraction only errors on underflow, an exact-equality result of `0` is a perfectly valid `Ok(0)` — there is no floor/guard preventing the pool's coin or pc reserve (net of accrued but unwithdrawn pnl) from reaching exactly zero. Repeated swaps via `SwapBaseIn`/`SwapBaseOut` (which do not call `calc_take_pnl` and freely move `amm_coin_vault.amount`/`amm_pc_vault.amount` — see `process_swap_base_in` computing the same `total_*_without_take_pnl` without any minimum-reserve floor [8](#0-7) ) can be used by an attacker to drive one side's vault balance down until it equals `need_take_pnl_pc` or `need_take_pnl_coin` exactly, producing `total_*_without_take_pnl == 0`.

Once in that state, any subsequent `Deposit`, `Withdraw`, or `WithdrawPnl` transaction hits the `unwrap()` on division by zero inside `calc_take_pnl`/`calc_x_power` and panics, aborting the instruction unconditionally (this is not a returned `ProgramError`, it is a Rust panic/abort). Because `WithdrawPnl` — the only path that could reduce `need_take_pnl_pc`/`need_take_pnl_coin` back toward a non-zero-triggering state — itself calls `calc_take_pnl` before performing the transfer [9](#0-8) , it also panics and can never succeed to fix the accounting. Only `Swap` instructions (which skip `calc_take_pnl`) can move the vault balance, but an attacker can trivially re-create the exact zero-difference condition on every subsequent block by targeting the vault balance again, and LP providers attempting `Deposit`/`Withdraw` in the interim will have their transactions panic.

### Impact Explanation
This is the closest reachable analog to CVE-2018-14553's "NULL pointer dereference via specific function call sequence": an unprivileged party can, purely with a swap-instruction sequence and no special accounts, drive on-chain pool state into a configuration that causes an unconditional Rust panic in `calc_take_pnl`/`calc_x_power` whenever `Deposit`, `Withdraw`, or `WithdrawPnl` is subsequently invoked. This constitutes denial-of-service against LP deposit/withdraw functionality and against pnl withdrawal for the pool, effectively freezing liquidity providers' ability to add/remove liquidity for as long as the triggering vault balance persists, and it is self-perpetuating because the only privileged remediation path (`WithdrawPnl`) is itself panicking.

### Likelihood Explanation
Reaching `total_pc_without_take_pnl == 0` or `total_coin_without_take_pnl == 0` exactly requires the attacker to land the vault balance on a specific integer value equal to the accrued `need_take_pnl_pc`/`need_take_pnl_coin`. This is a narrow but not implausible condition: an attacker fully controls the amounts and count of swaps in a single transaction/sequence and can iteratively approach the exact target value (swap fees and lot-size floors make the arithmetic deterministic and computable off-chain). Reaching this state does not require any privileged signer, leaked key, or malicious validator — only ordinary `SwapBaseIn`/`SwapBaseOut` calls from a normal swapper account.

### Recommendation
- Add explicit zero-guards before the divisions in `Calculator::calc_x_power` (`current_x`/`current_y` and `x1` in the `y2` computation) and return an `AmmError` (e.g., `CalcPnlError`) instead of `unwrap()`-panicking.
- Alternatively, short-circuit `calc_take_pnl` to skip the power/sqrt computation and just leave `delta_x = delta_y = 0` when either `x1 == 0` or `y1 == 0`, mirroring the existing "not enough to take pnl" fallback branch already present in the function [10](#0-9) .
- Audit all `checked_div(...).unwrap()` call sites in `math.rs`/`processor.rs` reachable from user-facing instructions and replace with `ok_or(AmmError::...)?` propagation.

### Proof of Concept
1. Attacker (or any swapper) observes `AmmInfo.state_data.need_take_pnl_coin` (or `need_take_pnl_pc`) for a target pool via `AmmInfo::load_checked`.
2. Attacker issues a sequence of `SwapBaseIn`/`SwapBaseOut` instructions (standard swapper-signed transactions, no special accounts) sized to drive `amm_coin_vault.amount` (or `amm_pc_vault.amount`) down to exactly equal `need_take_pnl_coin` (or `need_take_pnl_pc`). Since swap math is fully deterministic (`Calculator::swap_token_amount_base_in`/`_out`), the exact target amount is reachable with iterative/binary-search swap sizing.
3. Once the vault balance matches, `Calculator::calc_total_without_take_pnl_no_orderbook` returns `(x, 0)` or `(0, y)` [3](#0-2) .
4. Any subsequent `Deposit`, `Withdraw`, or `WithdrawPnl` transaction calls `calc_take_pnl` → `Calculator::calc_x_power`, hitting `checked_div(current_y).unwrap()` (or the `y2` division by `x1`) on a zero divisor, causing the program to panic and the transaction to fail unconditionally, blocking all LP deposit/withdraw and pnl-withdraw activity on the pool until vault balances move away from that exact value (which, per step 2, the attacker can re-trigger).

    pub fn calc_x_power(last_x: U256, last_y: U256, current_x: U256, current_y: U256) -> U256 {
        // must be use u256, because u128 may be overflow
        let x_power = last_x
            .checked_mul(last_y)
            .unwrap()
            .checked_mul(current_x)
            .unwrap()
            .checked_div(current_y)
            .unwrap();
        x_power
    }

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
