### Title
Stale account-existence cache in DirectBridge lets `validateWithdrawal` clear a NEAR withdrawal to an account that no longer exists - (File: `packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts`)

### Summary
`DirectBridge.validateWithdrawal` gates NEAR withdrawals to named (explicit) accounts on an existence check that is cached for one hour with a positive-only TTL cache. If the destination account is deleted after being cached as existing, the SDK will keep reporting it as valid and let the withdrawal intent go through, mirroring the class of bug in the Cilium advisory where a revoked grant kept being honored because the controller's authorization state wasn't re-checked before use.

### Finding Description
`getCachedAccountExistenceCheck` stores a `true` result in `accountExistenceCache` (LRUCache, `ttl: 3600000` = 1 hour) the first time an account is confirmed to exist, and every subsequent call within that hour returns the cached `true` without re-querying NEAR: [1](#0-0) 

This cache is consulted directly in `validateWithdrawal`, which is the function responsible for authorizing a NEAR withdrawal to an explicit (named) account before the withdrawal intent is built and signed: [2](#0-1) 

The underlying check queries `view_account` and treats `AccountDoesNotExist` as `false`: [3](#0-2) 

NEAR named accounts can be deleted via `delete_account`, at which point `view_account` starts returning `AccountDoesNotExist`. Because only positive results are cached (`if (exist) { cache.set(...) }`) and the TTL is 1 hour, once an account was seen to exist, `validateWithdrawal` will keep returning "valid" for up to an hour even after the account is deleted on-chain — the equality the code is supposed to enforce ("destination account currently exists" == "destination account existed at time of last check") is broken.

Once `validateWithdrawal` passes, `createWithdrawalIntents` builds an `ft_withdraw`/`native_withdraw` intent addressed to that now-deleted account: [4](#0-3) 

This intent is signed and submitted through the normal `signAndSendWithdrawalIntent`/`IntentExecuter` flow, which does not perform a second on-chain existence check before submission.

### Impact Explanation
On NEAR, submitting a `Transfer`/`ft_transfer` action to a named account that no longer exists causes the receipt to fail. Because withdrawal intents in this SDK settle by debiting the user's internal (intents.near) balance as part of the same atomic intent execution, a failed on-chain transfer to a deleted receiver can leave the withdrawal in a state where funds were already committed/debited internally but never delivered to any valid destination, requiring manual intervention to trace and recover — this falls under "a withdrawal stuck until manual intervention" / "funds delivered to a wrong address/chain/contract with no recovery" per the impact bands provided. The root cause is architecturally identical to the Cilium ReferenceGrant bug: a previously-valid authorization/state fact is cached and used for authorization decisions well past the point where the real-world state changed (revoked ReferenceGrant vs. deleted NEAR account).

### Likelihood Explanation
This requires no privileged or malicious actor: a legitimate user could withdraw to a named account, then later delete that same account (a normal, permitted NEAR account operation) and immediately retry/queue another withdrawal to the same address within the 1-hour cache window — or a third party could withdraw to an account that the account owner deletes shortly after being observed by the SDK in an unrelated call sharing the same long-lived `DirectBridge`/SDK instance (e.g., a server-side integrator process that keeps one `IntentsSDK` instance alive across many users' withdrawals, which is the SDK's documented usage pattern). Given the 1-hour TTL and that only successes are cached (never invalidated on account deletion), the window is realistic in a long-running server process.

### Recommendation
- Do not treat a positive account-existence result as valid for a full hour; either shorten the TTL substantially or re-validate immediately before submitting the withdrawal intent (i.e., perform the existence check right before signing rather than relying on a stale cache entry).
- Alternatively, remove the cache for this specific check (existence changes are rare but security-relevant, and the RPC cost of `view_account` is low), or invalidate cache entries when the SDK detects an on-chain failure for that account.

### Proof of Concept
1. Instantiate `IntentsSDK` once (long-lived server process) and call `sdk.processWithdrawal`/`sdk.signAndSendWithdrawalIntent` for `assetId: 'nep141:...'`, `destinationAddress: 'victim.near'` (a named account that currently exists). `DirectBridge.validateWithdrawal` calls `getCachedAccountExistenceCheck('victim.near')`, which caches `true` for 1 hour. [5](#0-4) 
2. Shortly after, `victim.near` calls `delete_account` on NEAR, removing the account from state.
3. Within the 1-hour TTL window, another withdrawal to `victim.near` is requested through the same SDK instance. `getCachedAccountExistenceCheck` returns the stale cached `true` without calling `accountExistsInNEAR` again. [6](#0-5) 
4. `validateWithdrawal` passes, the withdrawal intent is built and signed/submitted, and the on-chain transfer to the now-nonexistent account fails, leaving the withdrawal in an inconsistent/stuck state relative to the already-executed internal balance debit.

	/**
	 * Checks account existence to avoid frequent RPC calls.
	 */
	private async getCachedAccountExistenceCheck(
		accountId: string,
	): Promise<boolean> {
		const cached = this.accountExistenceCache.get(accountId);
		if (cached !== undefined) {
			return cached;
		}

		const exist = await accountExistsInNEAR(this.nearProvider, accountId);
		if (exist) {
			this.accountExistenceCache.set(accountId, exist);
		}

		return exist;
	}

export async function accountExistsInNEAR(
	provider: providers.Provider,
	accountId: string,
): Promise<boolean> {
	try {
		const client = unwrapNearFailoverRpcProvider(provider);
		await client.query({
			request_type: "view_account",
			account_id: accountId,
			finality: "final",
		});
		return true;
	} catch (error) {
		if (
			error instanceof providers.TypedError &&
			error.type === "AccountDoesNotExist"
		) {
			return false;
		}
		throw error;
	}
}
