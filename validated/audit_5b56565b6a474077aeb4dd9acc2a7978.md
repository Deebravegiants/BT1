### Title
Unchecked ERC-20 return value in `IntentGatewayV2.withdraw`/`SweepDust` allows silent escrow-release failure and fund loss on Tron - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed intent funds and sweeps dust using raw low-level `.call()` invocations of the `transfer(address,uint256)` selector, checking only that the call did not revert (`success`) but never decoding/checking the ABI-encoded boolean the ERC-20 standard requires callers to inspect. This is the exact bug class from the referenced report (Vyper `raw_call`/ERC-20 return-value ignored), reproduced here in Solidity via `token.call(abi.encodeWithSelector(...))`.

### Finding Description
In `withdraw()`, escrow accounting is decremented unconditionally while the actual transfer to the beneficiary is only "checked" for call success, not for the ERC-20 boolean result: [1](#0-0) 
The same pattern is used for the accumulated relayer/protocol fee payout: [2](#0-1) 
And again in the `SweepDust` admin-triggered branch of `onAccept`: [3](#0-2) 

For any ERC-20 that does not revert on failure but instead returns `false` (a well-known non-conforming/edge-case token behavior explicitly guarded against by OpenZeppelin's `SafeERC20`), `token.call(...)` returns `success = true` even though no tokens moved. `withdraw()` still decrements `_orders[body.commitment][token] -= amount`, marks `_filled[body.commitment] = beneficiary`, and emits `EscrowReleased`/`EscrowRefunded` — permanently finalizing the order and burning the escrow accounting entry without the beneficiary ever receiving the tokens.

This directly contradicts the safe pattern already used elsewhere in the codebase (the canonical EVM `IntentsBase._withdraw` uses `IERC20(token).safeTransfer(beneficiary, amount)`, which decodes and enforces the boolean return value): [4](#0-3) 
The Tron contract instead reimplements the transfer manually and drops this safety check, making it a real regression/analog of the exact bug class described in the report.

`withdraw()` is reachable from a relayed, ISMP-delivered `RedeemEscrow`/`RefundEscrow` POST request processed via `onAccept`, which any relayer can deliver once a valid membership proof exists for the corresponding fill/cancel commitment on the counterparty chain: [5](#0-4) 

### Impact Explanation
Escrowed user/solver funds can become permanently unrecoverable: the `_orders` accounting is decremented and the order is marked filled/refunded (`_filled[body.commitment] = beneficiary`) even though the token transfer silently failed, so `UnknownOrder` will guard against re-attempting withdrawal and the tokens remain stuck in the `IntentGatewayV2` contract with no code path left to release them to the rightful beneficiary. This is a permanent freezing/loss-of-funds condition for users interacting with any ERC-20 (including many TRC-20 tokens on Tron, which historically have non-standard/no-revert-on-failure implementations) that fails without reverting.

### Likelihood Explanation
Likelihood is Medium: it requires a token contract that returns `false` instead of reverting on transfer failure (e.g., insufficient balance/blacklist/paused conditions in non-standard TRC-20 tokens), which is common on Tron where many token implementations deviate from strict ERC-20/OpenZeppelin conventions. No privileged actor is needed — any relayer delivering a normal `RedeemEscrow`/`RefundEscrow`/`SweepDust` message triggers the vulnerable code path as part of the intended intents-escrow flow.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` (both the per-token loop and the fee payout) and in the `SweepDust` handler with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the reference implementation in `IntentsBase._withdraw`, so that both call success and the ERC-20 boolean return value are enforced before finalizing escrow state.

### Proof of Concept
1. Deploy a "silent-fail" TRC-20/ERC-20 token whose `transfer()` returns `false` (instead of reverting) when, e.g., the caller's balance is insufficient or the recipient is blacklisted.
2. Place an order on `IntentGatewayV2` (Tron) escrowing this token via `placeOrder`.
3. Arrange for the token's internal state (e.g., contract balance manipulated by an unrelated prior partial sweep, or a blacklist flag) such that a subsequent `transfer(beneficiary, amount)` call from the gateway returns `false` without reverting.
4. Have a relayer deliver a `RedeemEscrow` POST request for the commitment; `onAccept` → `withdraw()` executes `token.call(...)`, gets `success = true` (the call itself didn't revert), decrements `_orders[...]`, sets `_filled[commitment] = beneficiary`, and emits `EscrowReleased`.
5. Observe that the beneficiary's token balance is unchanged while the order is now marked filled and the escrow entry is gone — the funds are stuck in the contract with no further withdrawal path.
