### Title
Unsigned cross-chain calldata dispatch derives its execution origin from an attacker-supplied `message.from` field via a pluggable, non-injective `EvmToSubstrate` mapping - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`pallet_hyper_fungible_token`'s `on_accept` executes arbitrary runtime calls carried in the token-transfer message body. When the message carries no cryptographic signature over the call, the pallet derives the dispatch origin purely by feeding the untrusted `message.from` bytes through a pluggable `EvmToSubstrate` conversion, then dispatches the call as `RawOrigin::Signed(origin)` with no further authentication [1](#0-0) . This mirrors the CVE-2018-11767 bug class: a privilege/identity decision is delegated to a pluggable, "non-default" mapping mechanism, and an incorrect or non-injective mapping causes access to be granted to (or under) the wrong identity.

### Finding Description
The pallet's `Config` trait documents `EvmToSubstrate` as an externally-supplied, swappable component: *"Authenticates incoming EVM-originated runtime calls by mapping an EVM address to a substrate account. The unit type `()` is acceptable if you do not need this dispatch path."* [2](#0-1) 

In `on_accept`, once the token mint/transfer is complete, if the decoded message carries optional calldata:
- If `substrate_data.signature` is `Some`, the signature is cryptographically verified against `beneficiary` (the recipient), and origin = `beneficiary`.
- If `substrate_data.signature` is `None`, the origin is derived with **no verification at all**: `message.from` (an attacker-controlled field inside the ABI-encoded body of the bridged token message) is passed straight into `T::EvmToSubstrate::convert(...)`, and the resulting `AccountId` becomes the signer for `runtime_call.dispatch(RawOrigin::Signed(origin))` [3](#0-2) .

The only prior authentication in `on_accept` is `ContractToAsset::<T>::get(source, &from)`, which checks the ISMP-level `PostRequest.from` (the registered bridge contract address on the source chain), not the inner ABI-body `message.from` field [4](#0-3) . Nothing ties `message.from` to the actual caller of the source-chain send function, and nothing constrains `T::EvmToSubstrate::convert` to be injective/collision-resistant. Because a runtime is explicitly permitted to wire `EvmToSubstrate = ()` while still exposing this unsigned-calldata dispatch path, or to use any deployment-specific mapping that is not provably 1:1 (e.g., truncation, hashing collisions, or a deliberately/accidentally degenerate mapping), any unprivileged token bridger can craft `message.from` bytes that resolve — through the runtime's chosen mapping — to a substrate `AccountId` they do not control, and have a runtime call dispatched under that identity's authority.

### Impact Explanation
`runtime_call.dispatch(RawOrigin::Signed(origin))` executes as a fully signed, privileged origin subject only to `BaseCallFilter` [5](#0-4) . If the configured `EvmToSubstrate` mapping is non-injective or degenerate (explicitly sanctioned by the pallet's own documentation for `()`), an attacker can impersonate another account for any call not blocked by the filter — e.g. moving/approving assets owned by the collided account, voting, or invoking other pallets' privileged extrinsics as that account. This is unauthorized app action / improper privilege management with concrete impact up to theft or manipulation of funds and state controlled by the impersonated identity.

### Likelihood Explanation
Reachable from a single permissionless token bridge send with attached calldata (`data` field of the `Message`) from any EVM chain registered in `ContractToAsset` — no admin or governance action required beyond the routine chain-onboarding that every hyper-fungible-token deployment already performs. Exploitability is entirely gated on how the deployment implements `EvmToSubstrate`; deployments that follow the pallet's own guidance of using `()` "if you do not need this dispatch path" while still routing unsigned calldata through it, or any implementation that isn't strictly injective, are directly exploitable by any unprivileged sender.

### Recommendation
Never derive a dispatch origin from unauthenticated body fields. Either (a) require a valid signature (as already implemented for the `Some(signature)` branch) for every calldata dispatch and remove the unsigned fallback, or (b) if the unsigned fallback is kept for UX reasons, require `EvmToSubstrate` to be a provably injective, canonical derivation (e.g., a fixed derivation function baked into the pallet, not a pluggable `Config` type), and reject deployments that set it to `()` while calldata dispatch is enabled.

### Proof of Concept
1. Deployment configures `EvmToSubstrate = ()` (or any non-injective mapping) while calldata dispatch is live, per the pallet's documented supported configuration.
2. Attacker calls the source-chain bridge contract's send function with any input tokens, setting the ABI-encoded `Message.data` to `SubstrateCalldata { signature: None, runtime_call: <privileged call> }` and `Message.from` to bytes chosen to collide (per the deployed mapping) with a target account.
3. Relayer delivers the `PostRequest`; `on_accept` passes `ContractToAsset` authentication (based on the registered bridge contract address, unrelated to `message.from`).
4. `T::EvmToSubstrate::convert(message.from)` resolves to the target's `AccountId`; `runtime_call.dispatch(RawOrigin::Signed(target))` executes without ever verifying a signature from `target` [6](#0-5) .
