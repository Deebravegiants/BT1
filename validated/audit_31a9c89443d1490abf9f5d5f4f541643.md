Found it: `ShopifyAPI::Webhooks::Request` (`lib/shopify_api/webhooks/request.rb`) is the exact analog of the "oracle account" bug. The HMAC (`to_signable_string`) only covers the raw request body — it never includes the `shop-domain` header — yet `#shop` reads that header directly and is trusted downstream (passed into `WebhookMetadata` and to the app's handler) as the tenant identity for the payload whose *body* was verified.

### Title
Webhook `shop-domain` identity is not covered by the HMAC signature that authenticates the payload - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by verifying the HMAC over the raw request body via `Utils::HmacValidator.validate(request)`, where `Request#to_signable_string` returns only `@raw_body`. The `shop` (tenant identifier) returned by `Request#shop` is read straight from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` header and is never included in the signed bytes nor cross-checked against anything derived from the signature. This is the same class of bug as the audited Solana program: a value (`oracle`/here, `shop`) that is passed alongside a cryptographically-verified item is trusted for identity purposes without being bound into what was actually verified.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC(api_secret_key, verifiable_query.to_signable_string)` and compares it to the caller-supplied `hmac` value with `OpenSSL.secure_compare`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to return only the raw JSON body: [2](#0-1) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from HTTP headers that are completely outside the HMAC computation: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately hands the caller's `request.shop` (and other header values) to the app's webhook handler as trusted metadata, alongside the HMAC-verified body: [4](#0-3) 

The binding that should hold is: `shop` used to attribute the webhook to a tenant == a value that is cryptographically bound to the same bytes that were verified by the HMAC. Instead, the gem verifies `bytes(body)` but attributes the identity via `bytes(header) ∉ signed_bytes`. Any party capable of reaching the app's webhook endpoint (the endpoint is public-facing, unauthenticated HTTP by design) can supply a body whose HMAC matches a *previously observed* legitimate webhook payload for `shop_A` (a merchant/attacker can trivially capture their own real webhook's `body` + `hmac`, since HMAC is computed over the body alone and the same `api_secret_key` is shared by every shop that installed the app), and then replay that exact `(body, hmac)` pair with an arbitrary `x-shopify-shop-domain` header of `shop_B`. The signature still validates (it never touched the header), and `Registry.process` will invoke the handler believing the webhook is from `shop_B`.

### Impact Explanation
This lets an attacker who is a legitimate but unprivileged installer of the app (any merchant can install most public Shopify apps) capture one of their own genuine webhooks and relay it to the app's webhook endpoint while spoofing the `shop-domain` header to point at a victim shop. Because host applications built on this gem are documented to trust `WebhookMetadata#shop` (returned by `Registry.process`) as the tenant key for storage/lookup, this enables cross-tenant data confusion/injection — e.g., writing attacker-controlled data (the body of the replayed webhook, which the attacker fully controls since it's their own webhook) under a victim shop's identity, or triggering shop-scoped side effects (billing, order processing, uninstall handling, etc.) attributed to a shop the attacker does not control. This matches the "cross-tenant access" Critical impact bucket, since the identity binding broken here is exactly analogous to the oracle-account binding in the report.

### Likelihood Explanation
High. No secrets, tokens, or privileged access are required beyond installing the app once (or simply intercepting any webhook delivery, since deliveries are plain unauthenticated HTTP POSTs to a public callback URL and the payload/hmac pair can be captured and replayed). Constructing the malicious request is a simple HTTP replay with one header changed; the gem's `Request` and `HmacValidator` classes provide no defense against it since header/body separation is baked into `to_signable_string`.

### Recommendation
Bind the shop identity into the authenticated bytes, or independently verify it: either (a) require the host application to confirm `request.shop` corresponds to a shop for which a webhook was actually registered/expected (e.g., compare against a known/allow-listed set of installed shop domains) before trusting `WebhookMetadata#shop`, or (b) have the gem itself refuse to expose the header-derived `shop` as trusted unless it can be corroborated — e.g., by embedding the shop domain in a value covered by the signed payload. At minimum, document conspicuously that `WebhookMetadata#shop` is unauthenticated and must not be used as a lookup key without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and receives a real webhook delivery, e.g., `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H` (where `H = HMAC-SHA256(api_secret_key, B)`), per: [5](#0-4) 
2. Attacker replays the exact same `raw_body: B` and `x-shopify-hmac-sha256: H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (only presence, not correlation, is checked): [6](#0-5) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only recomputes HMAC over `B`: [7](#0-6) 
5. The handler receives `WebhookMetadata` with `shop == "victim-shop.myshopify.com"` even though the payload actually originated from the attacker's own shop, demonstrating the identity spoof.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
