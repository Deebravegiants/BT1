This confirms the finding: the gem's own documentation states `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" (`docs/usage/webhooks.md:125`), and hands the handler a `WebhookMetadata.shop` field documented as "The shop domain of the webhook" (`docs/usage/webhooks.md:14`) — implying the entire `WebhookMetadata`, including `shop`, is authenticated. That is not true for the `shop` field.

### Title
`Webhooks::Registry.process` treats the unauthenticated `shop-domain` header as verified, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's HMAC before invoking the app's handler and documents this as proof "the request did indeed come from Shopify," yet the HMAC signs only the raw body — never the `shop-domain` header that is passed to the handler as the trusted tenant identifier.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns solely `@raw_body` [1](#0-0) , and `#shop` is read directly, unauthenticated, from the `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) . `Registry.process` validates only this body-based HMAC via `Utils::HmacValidator.validate(request)` and, once it passes, forwards `request.shop` straight into `WebhookMetadata` given to the app's handler [3](#0-2) . `HmacValidator` computes the signature purely from `to_signable_string` (i.e., the body) and the shared `api_secret_key` [4](#0-3) . The `VerifiableQuery` interface only requires `hmac` and `to_signable_string`, with no hook to bind auxiliary fields like `shop` into the signed payload [5](#0-4) .

Because the same `api_secret_key` is shared across all shops installing the app, and Shopify computes the HMAC only over the body, an unprivileged internet user who controls their own installed shop (a legitimate, unprivileged tenant) will legitimately receive genuine `(raw_body, hmac)` pairs from Shopify for their own shop's webhooks. That attacker can then replay the exact same body and HMAC to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop. `HmacValidator.validate` still succeeds (the body/HMAC pair is genuinely valid), so `Registry.process` calls the handler with `WebhookMetadata.shop` set to the victim's domain instead of the attacker's own shop.

This breaks the identity binding: shop authenticated (the actual shop whose HMAC secret produced the signature — effectively "any shop, since it's a shared secret") versus the shop stored/acted upon (`request.shop`, taken from an attacker-controlled header and never covered by the signature).

### Impact Explanation
Apps built on this gem are documented to trust `data.shop` as the authenticated tenant identifier for the webhook (`docs/usage/webhooks.md:14`), typically using it as a database/session lookup key (e.g., to mark a shop's app as uninstalled, redact customer data for `customers/redact`/`shop/redact`, or update per-shop cached state). An attacker who has installed the app on a shop they control can forge a request that appears to be an authentic webhook for an arbitrary victim shop domain, causing the app to perform shop-scoped webhook side effects (state changes, redaction, uninstall handling, etc.) attributed to a shop they do not own — a cross-tenant confusion condition rooted entirely in this gem's `Webhooks::Request`/`Registry` design, not in host-app misuse of an undocumented API.

### Likelihood Explanation
Likelihood is high for any app that has a publicly reachable webhook endpoint (a requirement of the gem's documented usage) and at least one attacker who can self-install the app to harvest a genuine `(body, hmac)` pair; no access token, `client_secret`, or privileged access is required — only the ability to receive one real webhook to their own shop and replay it with a modified header.

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`webhook-id`) header into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived `shop` to the signed body (e.g., by including it in `to_signable_string`, or by separately validating shop identity against a known/expected value such as the previously stored offline session for that shop) before it is handed to the handler as trusted metadata.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and subscribes to a webhook topic (e.g., `orders/create`).
2. Shopify sends a legitimate webhook to the app's callback URL with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and some `raw_body`.
3. Attacker captures this `(raw_body, hmac)` pair and resends it to the same endpoint, replacing only the `X-Shopify-Shop-Domain` header with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses the forged headers; `Utils::HmacValidator.validate(request)` succeeds because it only checks `raw_body` against the shared secret [6](#0-5) .
5. `Registry.process` invokes the app's handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"` [7](#0-6) , causing the app to perform shop-scoped actions against the victim tenant based on attacker-controlled input.
