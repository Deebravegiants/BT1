### Title
Non-constant-time comparison of the OAuth `state` anti-CSRF token enables timing-based state forgery, allowing forced OAuth completion / session fixation - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` binds an OAuth callback to the browser session that started the flow by comparing the value stored in the `SESSION_COOKIE_NAME` cookie against the `state` query parameter returned by Shopify. This comparison is done with plain Ruby `==` instead of a constant-time comparison, unlike the HMAC check performed one line earlier in the same method, which correctly uses `OpenSSL.secure_compare`.

### Finding Description
The identity binding this code is supposed to enforce is:

`cookies[SESSION_COOKIE_NAME] (state set for this browser at begin_auth) == auth_query.state (state returned in the callback)` [1](#0-0) 

This is the CSRF-protection nonce created in `begin_auth` via `SecureRandom.alphanumeric(NONCE_LENGTH)` and stored both in a cookie and forwarded to Shopify as `state`: [2](#0-1) 

In `validate_auth_callback`, the HMAC signature — which also binds `shop`, `code`, `timestamp`, `host`, `state` — is verified with a constant-time comparison: [3](#0-2) 

But immediately after, the CSRF-binding `state` check uses a plain, short-circuiting `==`: [4](#0-3) 

Ruby's `String#==` returns as soon as the first non-matching byte is found, so the comparison time leaks how many leading bytes of the guess are correct. Because the cookie is sent automatically by the browser on any same-site request to the callback endpoint (including cross-site `fetch`/`XHR` requests issued by a page the victim is lured to visit, since the cookie itself is not readable by script but is still attached), an attacker who can trigger repeated requests to the app's callback endpoint from the victim's browser can perform a classic byte-at-a-time timing attack to recover the value the app's cookie holds, without ever needing the `api_secret_key`. This breaks the same trust boundary the constant-time HMAC check right above it is designed to protect, but through an inconsistent, timing-unsafe comparison of the "bytes verified" (`state`) that binds the callback to the initiating browser session.

### Impact Explanation
Recovering the victim's `state` value lets an attacker construct/replay a callback request that will pass the `state == auth_query.state` check as if it originated from the victim's own OAuth-initiation flow, enabling forced OAuth completion or session fixation for the app's install/session flow — one of the explicitly listed High-impact categories (session fixation / forced OAuth completion). This is exploitable purely from the internet, without possession of `api_secret_key`, an access token, or any privileged credential — only network timing observations against the app's own callback endpoint.

### Likelihood Explanation
Exploitation requires the attacker to make many timed requests (potentially through the victim's browser) against the callback route to iteratively recover a 15-character alphanumeric nonce. This is a known, practical technique against non-constant-time string comparisons in web request handlers, though it requires many samples and a stable network/timing signal, which is a realistic but non-trivial precondition.

### Recommendation
Replace the plain `==` comparison of `state` with a constant-time comparison, consistent with how `hmac` is already verified:

```ruby
require "openssl"
raise Errors::InvalidOauthError,
  "Invalid state in OAuth callback." unless state && OpenSSL.secure_compare(state, auth_query.state)
```

### Proof of Concept
Conceptual timing attack outline (illustrates the exploitable primitive; full weaponization requires statistical timing analysis over many requests):
```ruby
# Attacker-controlled script issuing many callback requests through
# the victim's browser (cookie attached automatically by the browser),
# varying a single guessed state prefix at a time and measuring
# server response latency to detect where the `==` comparison
# short-circuits (i.e. how many leading bytes of the guess matched
# the victim's cookie-stored state).
guess = ""
NONCE_LENGTH.times do
  best_char, best_time = nil, 0
  ALPHANUMERIC_CHARS.each do |c|
    t = measure_response_time_for(state: guess + c)  # cookie sent by victim's browser
    best_char, best_time = c, t if t > best_time
  end
  guess += best_char
end
# `guess` converges toward the victim's actual cookie-held state value,
# which can then be reused in a forged callback to satisfy
# `state == auth_query.state` in lib/shopify_api/auth/oauth.rb.
```

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state
