### Title
Webhook shop identity is trusted from an unauthenticated header while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC binding only over `@raw_body` [1](#0-0) , while the `shop` tenant identifier that the gem hands to the host application's handler is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never included in the signed material [2](#0-1) .

### Finding Description
`Registry.process` validates the webhook by checking `Utils::HmacValidator.validate(request)` against `request.to_signable_string`, and on success immediately constructs a `WebhookMetadata` using `request.shop`, which is passed unchecked to the app-supplied `handler.handle` [3](#0-2) . The HMAC computed by `HmacValidator` is `OpenSSL::HMAC.hexdigest(sha256, secret, verifiable_query.to_signable_string)` [4](#0-3) , and for `Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop` accessor pulls straight from the `shopify-shop-domain` header [2](#0-1) , and `WebhookMetadata.shop` is a plain `String` field with no cross-check against the signed body or against `Context.private_shop`/session store [5](#0-4) .

Because `api_secret_key` is shared across every shop that has installed the app, any merchant who has genuinely installed the app receives real webhooks with a valid HMAC over a raw body they fully control (they can trigger webhook-eligible events in their own store, e.g. product/order updates, and observe the signed body/HMAC pair delivered to the app's endpoint). Since the header carrying the shop identity is outside the signed bytes, that merchant can resend the same `(raw_body, hmac)` pair to the app's webhook endpoint while substituting a different `shop-domain` header value for a victim tenant. `HmacValidator.validate` and `Registry.process` still accept it — the equality actually enforced is `hmac == HMAC(secret, raw_body)`, not `hmac == HMAC(secret, raw_body ∥ shop)`, so the "authenticated shop" and the "shop used as the WebhookMetadata/session key" are never the same bound value.

### Impact Explanation
Downstream apps built on this gem are expected to use `WebhookMetadata#shop` to select the correct merchant/tenant record or session, exactly as shown in the gem's own registry tests, which key sessions and outgoing GraphQL calls by shop (`ShopifyAPI::Auth::Session.new(shop: ...)`) [6](#0-5) . Any process that trusts `WebhookMetadata.shop` to attribute a validly-HMAC'd payload to a tenant is exposed to cross-tenant data injection/impersonation: a malicious but legitimately-installed shop can make the app process attacker-supplied webhook content under a victim shop's identity, without ever possessing the victim's or the app's `client_secret`/access token. This crosses the tenant boundary that the HMAC is meant to enforce, matching the "Critical - cross-tenant access" impact class.

### Likelihood Explanation
Requires only an ordinary, legitimately-installed shop account (no elevated privilege, no leaked secret, no TLS interception) — the same "unprivileged internet user relative to other tenants" posture the rules target. The attacker only needs to capture one real webhook delivery for their own shop (trivial, since they control that shop's data) and replay it with a modified `shop-domain` header to the app's public webhook endpoint.

### Recommendation
Bind the shop identity into the value that is actually HMAC-verified: either include the `shop-domain` header (and other identity-bearing headers such as topic/webhook-id) in `to_signable_string` for `Webhooks::Request`, or independently re-derive/verify the shop by looking it up from data inside the signed JSON body rather than trusting the header, and reject/flag any mismatch between the header-asserted shop and the body-derived shop before invoking the handler.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; attacker triggers a real webhook (e.g. `orders/create`) and captures the POST: headers `x-shopify-hmac-sha256: <H>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, and raw body `B`.
2. `H = HMAC-SHA256(api_secret_key, B)` is valid because `to_signable_string` only signs `B` [1](#0-0) .
3. Attacker replays the identical `(B, H)` to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds (it never inspects the shop header) [7](#0-6) , and `Registry.process` builds `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` and invokes the handler with attacker-controlled `body` attributed to the victim shop [3](#0-2) .

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
