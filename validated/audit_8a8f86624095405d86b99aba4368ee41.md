### Title
Webhook shop/topic/webhook_id identity fields are unauthenticated (not covered by HMAC), enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates only the raw request body via HMAC, but dispatches to handlers using `shop`, `topic`, `webhook_id`, and `api_version` values taken from unauthenticated HTTP headers that are never included in the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic binding to that body [2](#0-1) .

`ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC using `verifiable_query.to_signable_string`, i.e. only the body bytes, via `OpenSSL.secure_compare` [3](#0-2) . `Registry.process` then trusts `request.shop` for tenant attribution when building `WebhookMetadata` passed to the app's handler, without any additional check that the shop header matches the entity whose secret signed the body: [4](#0-3) .

The identity binding that should hold is:
`shop used for tenant dispatch (request.shop from header)` == `shop cryptographically bound to the signed bytes (HMAC covers only @raw_body)`

This equality does not hold: the same `api_secret_key` is shared across every shop that installs the app, so any body signed for one shop's webhook produces a valid HMAC regardless of which `shop-domain` header accompanies it. An attacker who legitimately installs the app on their own store (or otherwise obtains one genuine, validly-signed webhook payload/HMAC pair for that shared secret) can replay that exact body to the app's webhook endpoint while substituting `x-shopify-shop-domain` (or `shopify-shop-domain`) with a victim shop's domain. `HmacValidator.validate` still passes (it only checks the body bytes), and `Registry.process` forwards the attacker-chosen `shop` value straight into `WebhookMetadata` for the handler, which per the gem's own documented contract is expected to use `data.shop` to attribute the event to a tenant [5](#0-4) .

### Impact Explanation
This breaks a tenant/session boundary: the app's business logic (queued jobs, order/customer processing, mandatory `shop/redact`/`customers/redact`/`customers/data_request` compliance webhooks, etc.) can be triggered under a spoofed `shop` value that was never actually verified, causing cross-tenant data confusion/processing attributable to the wrong merchant. This matches the "cross-tenant access" criterion since the app is misled into acting on behalf of a shop that did not actually send the (necessarily identical, replayed) payload.

### Likelihood Explanation
Requires the attacker to possess at least one genuine, validly-HMAC-signed webhook body/signature pair from Shopify for the target app (trivially available to any merchant who installs the app themselves, since the same `api_secret_key` signs all shops' webhooks), plus the ability to POST directly to the app's public webhook endpoint with custom headers (webhook endpoints are ordinary HTTP endpoints, not restricted to Shopify's IPs by this gem). No access token, `client_secret`, or privileged account is needed.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signable representation (or otherwise cryptographically bind them to the verified body), so that `HmacValidator.validate` fails if any of these header-derived identity fields are altered relative to what Shopify actually signed.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; capture a genuine webhook POST from Shopify, e.g. body `{"id":1}` with header `x-shopify-hmac-sha256: <valid hmac over body computed with the app's shared api_secret_key>` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Replay the exact same body and HMAC header to the app's webhook endpoint, but change `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates only `@raw_body` and succeeds [1](#0-0) .
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` [6](#0-5) , causing the app to process/attribute attacker-controlled webhook data as if it came from the victim shop.
