### Title
Webhook `shop-domain` header is trusted for tenant attribution but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC that is computed only over the raw JSON body, then hands the handler a `shop` value that is read from the unauthenticated `shop-domain` header. This breaks the intended identity binding `authenticated_bytes == acted_on_identity`: the bytes verified by the HMAC and the shop identity acted upon are not the same thing.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 

`shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, while `to_signable_string` returns only `@raw_body`. `HmacValidator.validate` computes the signature exclusively from `to_signable_string`: [2](#0-1) 

`Webhooks::Registry.process` then trusts `request.shop` as the tenant identity for the callback, after only checking the HMAC over the body: [3](#0-2) 

`WebhookMetadata` propagates this unauthenticated `shop` value directly to the host application's handler: [4](#0-3) 

Because `shop` is never included in the signed bytes, any party capable of producing one valid `(raw_body, hmac)` pair signed with the app's `client_secret` — e.g. a merchant who has installed the app and triggers a legitimate webhook delivery for their own store — can replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. `HmacValidator.validate` will still return `true` because it only checks the body, so the handler executes with `data.shop` set to the attacker-chosen shop domain, while `data.body` actually contains the attacker's own store's data.

### Impact Explanation
This directly breaks the binding `bytes verified != identity acted on` named in the target rule. Host applications built on this gem's documented interface receive `WebhookMetadata#shop` as the authenticated indicator of which tenant a webhook payload belongs to (this is the field the gem's own docs advertise as validated: "This will verify the request did indeed come from Shopify"). If the host stores/keys data (e.g., order/customer records, GDPR-relevant data, per-shop feature state) by `data.shop`, a merchant with an ordinary account in the app can cause tenant-attributed data belonging to their own store to be written or acted on under another merchant's shop domain, or trigger shop-scoped side effects (webhook-triggered sync, cache invalidation, notifications) for a shop they don't operate — a cross-tenant confusion condition.

### Likelihood Explanation
Exploitation only requires an unprivileged actor with a legitimate (even trial) install of the app to receive one webhook delivery for their own store, then replay it with a different `shop-domain` header value to the app's public webhook endpoint. No access token, `client_secret`, or victim credentials are needed. Any host application using `ShopifyAPI::Webhooks::Registry.process`/`WebhookMetadata#shop` exactly as documented is affected, since the gem itself never validates the header against the signed payload.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) header values in the HMAC-signed string, or independently verify that the shop present in the header matches a shop value derivable from an authenticated source (e.g., cross-check against the session/registration under which the webhook topic was registered) before constructing `WebhookMetadata`. At minimum, document prominently that `WebhookMetadata#shop` is not itself cryptographically bound to the request body and must not be trusted for authorization decisions without additional verification.

### Proof of Concept
1. App merchant A installs the app and triggers `orders/create`; Shopify delivers a webhook with `raw_body = B` and header `x-shopify-hmac-sha256 = HMAC(secret, B)` and `x-shopify-shop-domain: a.myshopify.com`.
2. Merchant A captures this request (it targets their own public app instance, so they can simply inspect their own network traffic/logs).
3. Merchant A resends the identical `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `HmacValidator.validate` recomputes the HMAC only over `raw_body`, matches, and returns `true`: [5](#0-4) 
5. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: <A's body>, ...)` and invokes the host's handler, which now believes this data pertains to `victim.myshopify.com`.
