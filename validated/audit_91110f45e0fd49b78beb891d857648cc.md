Audit Report

## Title
`ExchangeAsset` capacity check validates only `want.len()`, not the actual assets returned by `AssetExchange::exchange_asset`, allowing `AssetsInHolding` to silently exceed `MaxAssetsIntoHolding` - (File: polkadot/xcm/xcm-executor/src/lib.rs)

## Summary
In the `ExchangeAsset` instruction handler, `ensure_can_subsume_assets(want.len())` is checked before calling `Config::AssetExchanger::exchange_asset`, but the `AssetExchange` trait only guarantees "at least `want`" assets are returned, not an upper bound. `subsume_assets` then merges the returned assets into holding with no size check, so a multi-asset `AssetExchanger` can push `AssetsInHolding` past `MaxAssetsIntoHolding` undetected. [1](#0-0) [2](#0-1) 

## Finding Description
The `ExchangeAsset` handler removes `give` from holding leniently via `saturating_take`, checks capacity only for `want.len()` distinct assets via `ensure_can_subsume_assets`, invokes the configured `AssetExchanger`, and then calls `self_ref.holding.subsume_assets(received)` unconditionally on success. [1](#0-0)  The `AssetExchange` trait's documentation for `exchange_asset` states "At least want must be in the set," placing no upper bound on the returned `AssetsInHolding`. [2](#0-1)  The tuple impl of `AssetExchange` forwards to whichever adapter in the tuple succeeds, without adding any additional bound on the result size. [3](#0-2)  `subsume_assets` performs no bound/limit check — it merges fungibles by summing amounts and appends non-fungibles into a `BTreeSet`, with no reference to `MaxAssetsIntoHolding`. [4](#0-3)  The only shipped implementation of `AssetExchange`, `SingleAssetExchangeAdapter`, self-restricts to exactly one asset in both `give` and `want` (`ensure!(want.len() == 1, give)`, `ensure!(give_assets.len() == 1, give)`), but this restriction lives in that specific adapter, not in the trait contract or the executor. [5](#0-4)  Thus a differently-implemented or tuple-composed `AssetExchange` could legally return more distinct assets than `want.len()`, and the executor would merge them into holding without any bound enforcement.

## Impact Explanation
If a runtime's `AssetExchanger` is configured with a custom or tuple-composed `AssetExchange` implementation that does not itself cap its output count relative to `want`, `AssetsInHolding` can grow past the runtime's configured `MaxAssetsIntoHolding` with no error raised at the `ExchangeAsset` instruction. Any subsequent instruction in the same XCM program that performs its own `ensure_can_subsume_assets` check would then unexpectedly fail due to the already-inflated holding size, causing cascading failure of otherwise-legitimate instructions. This is a real accounting-invariant gap in the shared `xcm-executor` code, not merely a theoretical concern, though its severity is contingent on runtime configuration.

## Likelihood Explanation
Exploitability requires the runtime to configure `AssetExchanger` with a custom or tuple-composed `AssetExchange` that doesn't itself bound its returned asset count. The bundled `SingleAssetExchangeAdapter` is safe because it self-enforces a single-asset restriction. Given a vulnerable configuration, the attack path is straightforward and reachable by an unprivileged party via a normal `WithdrawAsset` + `ExchangeAsset` XCM sequence, with no barrier or origin check preventing it.

## Recommendation
Enforce the `MaxAssetsIntoHolding` bound at the point `received` is subsumed into holding in the `ExchangeAsset` handler in `polkadot/xcm/xcm-executor/src/lib.rs`, e.g., verify `self_ref.holding.len() + received.len() <= Config::MaxAssetsIntoHolding::get()` after `exchange_asset` returns and before calling `subsume_assets`, returning a defined `XcmError` on violation. Alternatively, make the check-and-insert atomic within `subsume_assets`/`ensure_can_subsume_assets` so no caller (including `ExchangeAsset`) can exceed the bound.

## Proof of Concept
1. Configure a mock runtime with `MaxAssetsIntoHolding = 4` and an `AssetExchanger` (not `SingleAssetExchangeAdapter`) whose `exchange_asset` always returns more than 4 distinct fungible assets regardless of `want`.
2. Build holding via `WithdrawAsset` with `MaxAssetsIntoHolding - 1` distinct assets.
3. Execute `ExchangeAsset { give: <one existing asset>, want: vec![<1 asset>], maximal: true }` and observe it succeeds while `holding.len() > MaxAssetsIntoHolding`.
4. Follow with a legitimate `WithdrawAsset` of one more asset and observe it fails purely due to the prior silent overflow, demonstrating cascading failure of an otherwise-valid instruction.

	/// Mutate `self` to contain all given `assets`, saturating if necessary.
	///
	/// NOTE: [`AssetsInHolding`] are always sorted
	pub fn subsume_assets(&mut self, assets: AssetsInHolding) {
		// for fungibles, find matching fungibles and sum their amounts so we end-up having just
		// single such fungible but with increased amount inside
		for (asset_id, accounting) in assets.fungible.into_iter() {
			match self.fungible.entry(asset_id) {
				btree_map::Entry::Occupied(mut e) => {
					e.get_mut().saturating_subsume(accounting);
				},
				btree_map::Entry::Vacant(e) => {
					e.insert(accounting);
				},
			}
		}
		// for non-fungibles, every entry is unique so there is no notion of amount to sum-up
		// together if there is the same non-fungible in both holdings (same instance_id) these
		// will be collapsed into just single one
		let mut non_fungible = assets.non_fungible;
		self.non_fungible.append(&mut non_fungible);
	}
