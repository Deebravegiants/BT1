### Title
Permanent freezing of escrowed native ETH when order beneficiary/refund-recipient is a contract without a payable fallback - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2`'s escrow release/refund path uses a raw `.call{value: amount}("")` that **reverts** the whole withdrawal if the recipient cannot accept native ETH. Unlike the codebase's own `WrappedHyperFungibleToken`, which explicitly falls back to a WETH transfer when a native push fails, `IntentGatewayV2` has no such fallback for its native-token escrow. If the order's escrowed native ETH must be paid to a contract address that has no `receive()`/payable `fallback()`, that escrow can never be released or refunded — the funds are permanently stuck.

### Finding Description
`IntentsBase._sendValue` is the single native-ETH transfer primitive used throughout `IntentGatewayV2`: [1](#0-0) 

It is used both to release escrow to the beneficiary on a successful fill/refund and to refund excess native token on `placeOrder`: [2](#0-1) 

`placeOrder` escrows `order.inputs` (which can include native ETH, `token == address(0)`) under the commitment keyed to `order.user = msg.sender`: [3](#0-2) [4](#0-3) 

`cancelOrder` is permissionless (any account can trigger the destination-side cancellation route after expiry) and its terminal effect — on the source chain — is `_withdraw`, refunding the original escrowed native ETH back to `order.user` via `_sendValue`: [5](#0-4) 

Because `_sendValue` reverts instead of degrading to a WETH transfer (as `WrappedHyperFungibleToken.onAccept`/`onPostRequestTimeout` explicitly do to avoid this exact failure mode): [6](#0-5) 

...any order whose `user` (refund recipient) or fill `beneficiary` (release recipient) is a contract without a payable fallback causes every attempt to refund or release that escrow to permanently revert. There is no alternate recovery path: `_sweepDust` only sweeps protocol-owned dust, not order-owned escrow, so the ETH is locked in the contract indefinitely once this state is reached.

### Impact Explanation
This is a permanent freezing-of-funds bug reachable from a single ordinary user transaction: any account (e.g. a smart-contract wallet, vault, or any contract lacking `receive()`) that calls `placeOrder` with a native-ETH input, or is selected as `order.output.beneficiary`/`order.session` context resolving to a non-payable contract on fill, will have its escrowed ETH become permanently unretrievable on cancellation/refund/release, since `_sendValue` always reverts rather than falling back. Given the protocol already recognizes and mitigates this exact failure mode elsewhere (`WrappedHyperFungibleToken`), its absence in `IntentGatewayV2`'s escrow path is a design inconsistency that leads to genuine, permanent loss of user funds — qualifying as at least Medium severity.

### Likelihood Explanation
Likelihood is moderate: it requires the order's `user`/refund-target or fill beneficiary to be a contract account without a payable fallback. This is realistic for many common integrations (smart contract wallets, multisig accounts, vault contracts, other protocols calling `placeOrder` on behalf of users) that do not anticipate needing to receive raw native ETH pushes. No special privileges or malicious actor cooperation is required — a normal user of a non-payable contract wallet placing a native-ETH order is sufficient to trigger the freeze upon expiry/cancellation.

### Recommendation
Mirror the mitigation already present in `WrappedHyperFungibleToken.onAccept`/`onPostRequestTimeout`: when the native ETH push via `_sendValue` fails, wrap the ETH into the fee/WETH token and deliver it as an ERC-20 transfer to the same recipient instead of reverting, so the refund/release path can never permanently strand funds. Alternatively, expose an explicit pull-based claim function keyed to the order commitment so beneficiaries whose native push fails can still retrieve their funds via an ERC20-wrapped balance.

### Proof of Concept
1. Deploy (or use) a contract `C` with no `receive()`/payable `fallback()`.
2. `C` calls `IntentGatewayV2.placeOrder(order, graffiti)` with `order.inputs` containing a native-ETH `TokenInfo{token: address(0), amount: X}` and sufficient `msg.value`. `order.user` is set to `address(C)` by the gateway.
3. Let the order expire without a fill (or have it fail cross-chain), then call `cancelOrder(order, options)` from any account.
4. On the source chain, the cancellation path eventually calls `_withdraw(...)` → `_sendValue(address(C), X)`, which executes `address(C).call{value: X}("")`; since `C` has no payable fallback, the call fails and `_sendValue` reverts with `InsufficientNativeToken`.
5. Every subsequent retry of the refund reverts identically — the escrowed ETH `X` is permanently locked in `IntentGatewayV2` with no recovery mechanism.

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable nonReentrant {
        bytes32 commitment = keccak256(abi.encode(order));

        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        // Emitted here, once, rather than from each of the three routes below. Every check those
        // routes make — Unauthorized, NotExpired, UnknownOrder — reverts, and a revert discards
        // logs, so an early emit can never announce a cancellation that did not happen. Emitting
        // before the branch also keeps `EscrowRefunded` the last log on the same-chain route, where
        // the refund is processed in this same transaction. Three emit sites cost bytecode this
        // contract does not have: it sits within ~100 bytes of the EIP-170 limit.
        emit OrderCancelled({commitment: commitment, canceller: msg.sender});

        if (isSameChain) {
            // Checked here rather than inside `_cancelSameChain`, which used to re-read `host()`,
            // re-query the host's state machine id and re-hash `order.source` to reach the same
            // answer this function already has. Same check, one external call fewer.
            if (currentChain != orderSource) revert WrongChain();
            _cancelSameChain(order, commitment);
        } else if (currentChain == orderSource) {
            _cancelFromSource(order, options, commitment);
        } else if (currentChain == orderDest) {
            _cancelFromDest(order, options, commitment);
        } else {
            revert WrongChain();
        }
    }
