### Title
Unsanitized JWT `dest` claim used as request host for `client_secret`/session-token exchange - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` takes the shop hostname it POSTs the app's `client_secret` and the caller-supplied session token to directly from the unauthenticated-format `dest` claim of the JWT, with no domain-format validation. Every other credential-bearing OAuth flow in the same module (`refresh_access_token`, `client_credentials`, and even `TokenExchange.migrate_to_expiring_token`) explicitly runs the shop value through `Utils::ShopValidator.sanitize!` before using it to build the outbound request host. `exchange_token` skips this step.

### Finding Description
`exchange_token` decodes the session token via `ShopifyAPI::Auth::JwtPayload.new(session_token)` and takes `dest_shop = jwt_payload.shop`: [1](#0-0) 

`JwtPayload#shop` only strips the `"https://"` prefix from the raw `dest` claim — it performs no check that the resulting string is a real Shopify-owned domain (`myshopify.com`, `myshopify.io`, `spin.dev`, `shop.dev`, or the unified admin domain): [2](#0-1) 

`JwtPayload`'s constructor only verifies the JWT signature (against `Context.api_secret_key`) and that `aud == Context.api_key`; it never validates `iss`/`dest` against a trusted-domain allow-list: [3](#0-2) 

`dest_shop` is then used unsanitized to build the session whose `shop` attribute becomes the request host: [4](#0-3) 

`Clients::HttpClient#initialize` builds the outbound base URI directly from `session.shop`: [5](#0-4) 

The request body sent to that host contains the app's `client_secret` and the raw `subject_token` (the session token being exchanged): [6](#0-5) 

Contrast this with the sibling flows in the very same file and module, which all call `Utils::ShopValidator.sanitize!(shop)` — a function that raises `Errors::InvalidShopError` unless the host resolves to one of the `TRUSTED_SHOPIFY_DOMAINS` — before building a session used to send `client_secret`: [7](#0-6) [8](#0-7) [9](#0-8) [10](#0-9) 

The broken binding, stated as an equality that the gem fails to enforce for this one path:
`request_host (used for client_secret POST) == ShopValidator.sanitize!(shop)`
holds in `refresh_access_token`, `client_credentials`, and `migrate_to_expiring_token`, but in `exchange_token` the gem instead uses:
`request_host == jwt_payload.dest.gsub("https://", "")` (unchecked against the trusted-domain allow-list).

The only integrity guarantee on `dest` is the JWT signature (bound to `Context.api_secret_key`) and the `aud == api_key` check — neither of which constrains the *value* of `dest` to a Shopify-owned hostname. Any signed token accepted by `JwtPayload` (e.g., one obtained from a legitimately-issued session token whose `dest` was manipulated by a compromised/rogue Storefront/custom-domain proxy, or reused across app installations that share the same `client_id`/`client_secret` pair) will cause the gem to POST the app's `client_secret` and the `subject_token` to whatever host is embedded in `dest`, with the format of that host never checked against the same allow-list the other flows enforce.

### Impact Explanation
Sending the app's `client_secret` and the session token itself to a host that is never validated against the Shopify trusted-domain list is exactly the credential-leakage / SSRF-with-app-credentials class called out in scope ("SSRF with the app's credentials" / "credential leakage into logs or error output"). If the destination host is not the genuine, dedicated `myshopify.com` shop, the app's long-lived `client_secret` and the caller's session token are exfiltrated to that host — enabling full impersonation of the app (minting arbitrary access tokens) or theft of the caller's session token for token exchange elsewhere.

### Likelihood Explanation
The `dest` claim is signature-protected by the app's own secret, so on a single, correctly-isolated app deployment, exploitation requires the same trust assumptions as any other JWT consumer. The concrete, provable defect is a code-level inconsistency: this is the only credential-bearing OAuth path in the module that omits the `ShopValidator.sanitize!` call that all its siblings perform, meaning the gem itself supplies no defense-in-depth against a malformed/`dest` value even though it clearly considers this necessary elsewhere in the same file.

### Recommendation
In `ShopifyAPI::Auth::TokenExchange.exchange_token`, sanitize `dest_shop` the same way `migrate_to_expiring_token`, `refresh_access_token`, and `client_credentials` do:
```ruby
dest_shop = Utils::ShopValidator.sanitize!(jwt_payload.shop)
```
before constructing `shop_session` and issuing the `HttpClient` request that carries `client_secret`.

### Proof of Concept
1. Compare `exchange_token` (`lib/shopify_api/auth/token_exchange.rb:40-65`) against `migrate_to_expiring_token` (same file, lines 97-115), `refresh_access_token` (`lib/shopify_api/auth/refresh_token.rb:24-33`), and `client_credentials` (`lib/shopify_api/auth/client_credentials.rb:25-33`).
2. In all three sibling methods, the `shop` value is passed through `Utils::ShopValidator.sanitize!` (which raises `Errors::InvalidShopError` for any host outside `TRUSTED_SHOPIFY_DOMAINS`) before being used to build the `Auth::Session` that determines the HTTP request host in `Clients::HttpClient#initialize` (`lib/shopify_api/clients/http_client.rb:16-19`).
3. In `exchange_token`, `dest_shop = jwt_payload.shop` is used directly with no equivalent call, and `jwt_payload.shop` (`lib/shopify_api/auth/jwt_payload.rb:47-51`) performs no domain-format validation on the JWT's `dest` claim — the `JwtPayload` constructor only checks the HMAC signature and `aud == Context.api_key` (`lib/shopify_api/auth/jwt_payload.rb:23-45`).
4. Any JWT accepted by `JwtPayload` therefore causes `client_secret` and `subject_token` to be POSTed to `https://#{dest}/admin/oauth/access_token` with `dest`'s format unchecked, unlike every other flow in the same module.
