## Finding

### Title
Webhook `shop` and `topic` identifiers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only. The `shop` and `topic` values — which the webhook registry treats as the trusted identity of the event and hands directly to the app's handler — come from HTTP headers that are excluded from the signed content. Anyone who can obtain one validly-signed `(raw_body, hmac)` pair (e.g., by installing the app on their own store and receiving a legitimate webhook) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `shop-domain` and/or `topic` header, since neither is bound by the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` and `topic` are read straight from attacker-controlled headers with no cross-check against the signed payload: [2](#0-1) 

`ShopifyAPI::Utils::HmacValidator.validate` verifies only `to_signable_string` (the raw body) against the shared secret: [3](#0-2) 

`Webhooks::Registry.process` treats the HMAC check as authorizing the request, then forwards the *unauthenticated* `request.shop` and `request.topic` to the app's handler as trusted identity fields: [4](#0-3) 

This breaks the intended identity binding `hmac == HMAC(secret, body ‖ shop ‖ topic)`; in reality `hmac == HMAC(secret, body)`, so `shop` and `topic` can be freely substituted after the fact without invalidating the signature — exactly the "field acted on but not covered by the HMAC" analog to the report's underlying bug class (a value the code relies on for identity/state that isn't bound by the verification it passed).

### Impact Explanation
Any handler that uses `WebhookMetadata#shop` to select which tenant's stored session/data to act on (a standard pattern — e.g., "delete customer data for `shop`", "mark `shop` uninstalled", "disable feature for `shop`") can be tricked into acting on a victim shop it has no relationship with, using a signature that legitimately validates. This is a cross-tenant confusion/spoofing vector reachable by an unprivileged internet user who only needs to operate their own (even free/dev) Shopify store to harvest one valid `(body, hmac)` pair, then replay it against the target app's public webhook endpoint with a forged `shop`/`topic` header.

### Likelihood Explanation
Obtaining a legitimate `(raw_body, hmac)` pair only requires installing the target app on an attacker-controlled store and capturing one webhook delivery — no leaked secrets or privileged access needed. The webhook endpoint is a public, unauthenticated internet-facing route by design, and neither `Request` nor `HmacValidator` nor `Registry.process` re-validates `shop`/`topic` against anything bound by the signature.

### Recommendation
Include `shop` and `topic` (and any other header-derived fields consumed by handlers) in the HMAC-signed content, or otherwise cryptographically bind them to the signed body (e.g., verify against a per-shop webhook secret or a signed envelope that covers headers). At minimum, document that `WebhookMetadata#shop`/`#topic` are not authenticated by `Registry.process` and instruct consuming apps to independently confirm the shop identity (e.g., cross-reference against `webhook_id` via a GraphQL lookup) before performing tenant-scoped mutations.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers a webhook handler is invoked with a legitimate delivery, capturing `raw_body` and the `X-Shopify-Hmac-Sha256` header (both valid, since Shopify computed them with the real `api_secret_key`).
2. Attacker sends a POST directly to the app's public webhook endpoint with the same `raw_body` and `hmac` header, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` and/or a different `X-Shopify-Topic` for a topic the app has a registered handler for.
3. `ShopifyAPI::Webhooks::Request.new` parses these headers unchanged; `HmacValidator.validate` recomputes the HMAC over `raw_body` only and it matches, per [1](#0-0)  and [5](#0-4) .
4. `Registry.process` dispatches to the handler with `shop: "victim.myshopify.com"` as shown in [4](#0-3) , causing the app to perform whatever tenant-scoped action the handler implements against the victim shop, despite the request never having come from Shopify on behalf of that shop.
