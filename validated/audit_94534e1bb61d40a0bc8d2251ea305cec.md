Audit Report

## Title
Unauthenticated `MessageID` collision allows cross-user response hijacking in the WebAPI capabilities gateway handler - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
The gateway's `capabilities` handler correlates in-flight user HTTP requests with future DON-node responses using an attacker-supplied `MessageID` as the sole key into a shared map, `h.savedCallbacks`, with no uniqueness enforcement before insertion. This allows a second request with a colliding `MessageID` to silently overwrite the stored callback of a still-pending first request, causing the DON's eventual response to be delivered to the wrong caller.

## Finding Description
`ProcessRequest` in `core/services/gateway/gateway.go` (L221-295) is the entry point invoked per incoming HTTP request. For legacy requests it calls `msg.Validate()` [1](#0-0) , which in `core/services/gateway/api/message.go` only checks the `MessageID`'s length and that it doesn't end in a null byte [2](#0-1)  — there is no uniqueness or per-caller namespacing check. It then calls `h.HandleLegacyUserMessage(ctx, msg, callback)` synchronously and blocks on `callback.Wait(ctx)` for the eventual response [3](#0-2) .

Inside `HandleLegacyUserMessage`, after basic payload/staleness checks, the handler stores the caller's callback keyed purely by `msg.Body.MessageID` without checking whether that key is already occupied by another pending request:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageID] = &savedCallback{id: msg.Body.MessageID, createdAt: time.Now(), Callback: callback}
``` [4](#0-3) 

Because Go map assignment silently overwrites, if two callers submit requests with the same `MessageID` while the first is still outstanding (bounded by `CallbackMaxAgeSec`, default 120s), the second caller's callback replaces the first's in the map. When the DON eventually responds, `HandleNodeMessage` dispatches to `handleWebAPITriggerMessage`, which looks up and deletes the callback strictly by `MessageID` and delivers the DON's payload to whatever `Callback` is currently stored there:
```go
savedCb, found := h.savedCallbacks[msg.Body.MessageID]
delete(h.savedCallbacks, msg.Body.MessageID)
...
return savedCb.SendResponse(...)
``` [5](#0-4) 

`pruneCallbacks` only removes entries by age/count and does not protect against a live overwrite [6](#0-5) . No other layer (HTTP server, `ProcessRequest`, `Message.Validate`) namespaces the key by session/caller identity, so the map is a purely global, attacker-controlled correlation table.

## Impact Explanation
Two unprivileged callers of the gateway's user-facing HTTP endpoint (or an attacker racing a victim) submitting `web_api_trigger` requests with an identical `MessageID` while both are outstanding can cause the gateway to deliver one user's DON response to the other's HTTP connection. This is a genuine cross-user response confusion issue — it can leak response data intended for another caller to an attacker, or cause a victim's request to receive attacker-influenced/unexpected output. This maps to the in-scope "cross-user response corruption" impact category for the gateway.

## Likelihood Explanation
No special privileges are required: any caller of the gateway's public HTTP endpoint can freely choose `MessageID`, and there is no check anywhere in the validated code path (`Message.Validate`, `HandleLegacyUserMessage`) that enforces per-caller uniqueness or namespacing of this value. An attacker only needs to send a request with a `MessageID` matching (or guessed to match) a concurrently outstanding victim request within the callback lifetime window (default 120s) to trigger the collision, which is realistically exploitable via flooding/racing against short or predictable IDs.

## Recommendation
Do not trust the caller-supplied `MessageID` alone as the correlation key. Either (a) reject/collide-detect on insertion into `savedCallbacks` if the ID is already in use rather than silently overwriting, or (b) namespace the map key with a gateway-generated, non-guessable, per-request correlation identifier independent of the caller-supplied `MessageID`, and use that internal ID for lookups in `handleWebAPITriggerMessage`/`HandleNodeMessage`.

## Proof of Concept
1. Caller A sends a `web_api_trigger` legacy JSON-RPC request to the gateway's user HTTP port with `MessageID = "X"`; `HandleLegacyUserMessage` stores A's callback at `h.savedCallbacks["X"]` (handler.go L411-414) and A's HTTP request blocks in `callback.Wait(ctx)` (gateway.go L281).
2. Before any DON node replies, Caller B sends its own legacy request also with `MessageID = "X"`; this overwrites `h.savedCallbacks["X"]` with B's callback.
3. A DON node processes A's originally forwarded request and replies referencing `MessageID = "X"`.
4. `handleWebAPITriggerMessage` looks up `h.savedCallbacks["X"]` (now B's callback) and calls `savedCb.SendResponse(...)`, delivering A's intended response to B's HTTP connection instead of A's.

A Go integration test can simulate this by directly invoking `handler.HandleLegacyUserMessage` twice with the same `MessageID` and distinct callbacks, then invoking `handler.HandleNodeMessage` with a response for that `MessageID`, and asserting which callback received the response.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.

```go
func (h *handler) pruneCallbacks() {
	h.mu.Lock()
	defer h.mu.Unlock()

	// First, remove expired callbacks.
	maxAge := time.Duration(h.config.CallbackMaxAgeSec) * time.Second
	now := time.Now()
	var expired int
	for id, cb := range h.savedCallbacks {
		if now.Sub(cb.createdAt) > maxAge {
			delete(h.savedCallbacks, id)
			expired++
		}
	}

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}

	if expired > 0 || evicted > 0 {
		h.lggr.Infow("Pruned savedCallbacks", "expired", expired, "evicted", evicted, "remaining", len(h.savedCallbacks))
	}
}
```
