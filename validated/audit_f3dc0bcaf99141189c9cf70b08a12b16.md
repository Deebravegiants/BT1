### Title
Reputation-Based Collator Selection Can Be Farmed via Self-Dispatched, Self-Relayed Messages - (File: `modules/pallets/messaging-incentives/src/lib.rs`)

### Summary
`pallet-messaging-incentives::on_executed` mints non-transferable Reputation Asset to whatever account's signature is recovered from a delivered message, scaled purely by the byte-size of the message body, with no check that the message represents genuine third-party relaying activity or that the dispatcher and the relayer are distinct parties. Because dispatching a message on Polkadot-SDK chains costs no protocol fee, and Reputation Asset is the sole input to Collator (block-producer) selection, a single actor can self-dispatch garbage-payload messages to itself and self-relay them to mint reputation cheaply — bypassing the entire economic rationale of the reputation system, exactly analogous to the reported Teller `lenderAcceptBid` issue where a wallet self-deals to fabricate a good reputation score that other parties then rely on.

### Finding Description
`pallet-messaging-incentives::on_executed` recovers a "relayer" account purely from the sr25519 signature embedded in the `Message` (via `relayer_for`), then mints `rate * bytes` Reputation Asset to that account with no validation that the message dispatcher and message relayer are unrelated parties, or that the message serves any real cross-chain application need: [1](#0-0) [2](#0-1) 

The mint amount is derived solely from `message_bytes`, a per-request byte count with a 32-byte floor, entirely controlled by whoever crafts the request body: [3](#0-2) 

Dispatching a message on Polkadot-SDK-based Hyperbridge chains is free at the protocol layer — only an optional relayer fee is attached, which an application (or the attacker's own dispatching contract/pallet) may set to zero for self-relay: [4](#0-3) 

Reputation Asset minted this way is the exclusive ranking criterion `pallet-collator-manager::new_session` uses to select the next Collator set — controllers are ranked strictly by `T::ReputationAsset::balance`, with no distinction between reputation earned via genuine, externally-useful relaying and reputation earned by self-dealing: [5](#0-4) 

Documentation confirms this is precisely the intended mechanism: "the more messages you relay... the more `$BRIDGE` you earn, the higher your reputation score becomes, and the better your chances of being selected as a Collator," with no self-dealing exclusion described: [6](#0-5) 

This mirrors the reported Teller bug class exactly: the reputation primitive (there, "good repayer"; here, "Reputation Asset / active relayer") is meant to signal trustworthy, externally-validated behavior that other parties or protocol logic rely on for a privileged decision (there, loan underwriting by other lenders; here, Collator — block producer — selection). In both cases, nothing prevents the same actor from playing both roles in the interaction (borrower+lender there; dispatcher+relayer here) to fabricate the reputation signal essentially for free.

### Impact Explanation
Collators are not a low-stakes role — they are block producers with real privileges over the Hyperbridge parachain, and they also run the fisherman fraud-detection task that vetoes L2 state commitments: [7](#0-6) 

An attacker who cheaply mints Reputation Asset via self-dispatched/self-relayed garbage messages can outrank genuine, high-value relayer/prover operators in the per-session reputation ranking, allowing them to seize the Collator set and gain block production authority, transaction ordering power, and fisherman veto authority — without ever performing genuine, economically valuable relaying service to the network. This is an unauthorized escalation of a privileged network role (collator, block producer) achieved by gaming a reputation primitive that other protocol logic (`pallet-collator-manager`) unconditionally trusts, which fits "unauthorized app action" impact.

### Likelihood Explanation
Dispatch of a message on a Polkadot-SDK Hyperbridge chain costs nothing at the protocol layer (transaction fee only, no relayer fee required for self-relay), and message delivery via `on_executed` only requires a valid signature over the request body recoverable to the caller's own account — there is no check that the message dispatcher and message relayer differ, nor that the message content serves any genuine cross-chain purpose. Any account able to submit signed messages (a normal, unprivileged relayer operation) can perform this loop repeatedly and cheaply, making this readily reachable by any single unprivileged actor motivated to obtain Collator status.

### Recommendation
- Exclude self-dealt reputation: when recovering the relayer for reputation-minting purposes, verify the message's originating dispatcher (source module/account) is not the same account as the recovered relayer signer, or otherwise ensure reputation is only minted for messages whose fee-payer is a distinct external party.
- Tie reputation minting to real economic cost/usefulness signals already present in the protocol (e.g., only mint reputation for messages that had a non-zero relayer fee actually paid by a third party and collected via `pallet-ismp-relayer`'s fee accumulation, rather than purely byte-count of an arbitrary self-authored payload).
- Consider rate-limiting or diminishing-returns curves per source/destination pair, or per module id, similar to the uncle-reward decay used for BEEFY provers, to reduce the value of repeatedly self-dispatched traffic.

### Proof of Concept
1. Attacker controls account `A` and runs a relayer node with the corresponding sr25519 key.
2. `A` dispatches a `PostRequest` (via any permissionless ISMP dispatch entry point) from itself to a destination chain it also controls, with `fee = 0` (self-relay, no protocol fee is charged for dispatch on Polkadot-SDK chains, per `docs/content/developers/polkadot/fees.mdx`), and with a large, dummy `body` to maximize `message_bytes`.
3. `A` then submits the corresponding `RequestMessage` for execution on Hyperbridge, signing it with its own key, matching the `signed_request` test-harness pattern in `modules/pallets/testsuite/src/tests/pallet_messaging_incentives.rs` lines 47-80.
4. `pallet_ismp` invokes `MessagingRelayerIncentives::on_executed`, which recovers `A` as the relayer (`relayer_for`) and mints `MintPerByte * message_bytes` Reputation Asset directly to `A`, as shown in `on_executed_mints_reputation_proportional_to_bytes` (`modules/pallets/testsuite/src/tests/pallet_messaging_incentives.rs` lines 99-115).
5. `A` repeats steps 1–4 cheaply and at volume (bounded only by chain-level tx fees, not by any protocol fee or genuine third-party relay demand), accumulating a large Reputation Asset balance.
6. At the next session boundary, `pallet-collator-manager::new_session` ranks all candidate controllers purely by `T::ReputationAsset::balance` (`modules/pallets/collator-manager/src/lib.rs` lines 511-529) and selects the top-ranked accounts — `A` is selected as a Collator despite having performed no genuine, externally valuable relaying service, having only self-dealt to inflate its reputation score.

```rust
	/// Same minimum-byte rule as the bandwidth gate (`max(body, 32)`),
	/// applied **per request** so packing requests into one envelope
	/// vs. splitting them across many produces identical mints.
	/// Applying the floor once per envelope would let a relayer inflate
	/// the mint by splitting (each split picks up its own 32-byte floor).
	fn message_bytes(message: &Message) -> u32 {
		match message {
			Message::Request(req) => req
				.requests
				.iter()
				.map(|p| core::cmp::max(p.body.len() as u32, 32))
				.sum::<u32>(),
			_ => 0,
		}
	}
```

```rust
	fn relayer_for(message: &Message) -> Option<T::AccountId> {
		let (signer, signed) = match message {
			Message::Request(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			Message::Response(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			_ => return None,
		};
		Signature::decode(&mut &signer[..])
			.ok()?
			.verify_and_get_sr25519_pubkey(&signed, None)
			.ok()
			.map(T::AccountId::from)
	}
```

```rust
	fn on_executed(
		messages: Vec<MessageWithWeight>,
		_events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let rate = MintPerByte::<T>::get();
		if !rate.is_zero() {
			for mw in &messages {
				let bytes = Self::message_bytes(&mw.message);
				let bytes_balance: BalanceOf<T> = (bytes as u128).saturated_into();
				let amount = rate.saturating_mul(bytes_balance);
				if amount.is_zero() {
					continue;
				}
				if let Some(relayer) = Self::relayer_for(&mw.message) {
					match T::ReputationAsset::mint_into(&relayer, amount) {
						Ok(_) =>
							Self::deposit_event(Event::ReputationMinted { relayer, bytes, amount }),
						Err(err) => log::warn!(
							target: "messaging-incentives",
							"reputation mint failed for {bytes}b: {err:?}",
						),
					}
				}
			}
		}
		Ok(PostDispatchInfo { actual_weight: None, pays_fee: Pays::No })
	}
```

```text
# Hyperbridge Fees

Hyperbridge no longer charges a protocol fee on Polkadot-SDK chains. Dispatching is free at the runtime layer — applications only need to attach an optional **relayer fee** if they want third-party relayers to deliver their messages.

## Relayer Fees

The relayer fee is an optional incentive provided by applications initiating cross-chain transactions. It compensates Hyperbridge's decentralized relayers for delivering messages to the destination chain. Apps that prefer to self-relay can leave the fee at zero.

The fee is collected by `pallet-ismp`'s `IsmpDispatcher` from the configured `Currency` (typically a stablecoin). It's escrowed into the `RELAYER_FEE_ACCOUNT` and paid out to the relayer that delivers the message (or refunded to the payer on timeout).
```
