### Title
Division-by-zero panic in `Processor::calc_take_pnl` permanently DoSes Deposit/Withdraw/WithdrawPnl after decimal-truncated reserves reach zero - (File: `program/src/processor.rs`)

### Summary
`CVE-2022-21607` describes a MySQL optimizer path that lets an authorized-but-abusive client crash/hang the server through an unhandled internal error during query planning, resulting in repeatable Availability-only DoS. The closest reachable analog in this program is `Processor::calc_take_pnl`, which is invoked by `process_deposit`, `process_withdraw`, and `process_withdrawpnl` and performs unchecked integer division that can legitimately divide by zero, panicking the instruction and repeatably bricking pool operations for every LP.

### Finding Description
`calc_take_pnl` normalizes on-chain vault reserves into a common `sys_decimal_value` scale via `Calculator::normalize_decimal_v2`, then uses the normalized values (`x1`, `y1`) as divisors: [1](#0-0) 

```
let x2_power = Calculator::calc_x_power(target.calc_pnl_x, target.calc_pnl_y, x1, y1); // divides by y1 internally
let x2 = x2_power.integer_sqrt();
let y2 = x2.checked_mul(y1).unwrap().checked_div(x1).unwrap();      // divides by x1
```

`calc_x_power` itself does `... .checked_div(current_y).unwrap()` [2](#0-1) , i.e. divides by `y1` (the caller's `current_y`). Both `x1` and `y1` are computed from the *current* vault balances via `normalize_decimal_v2`: [3](#0-2) 

`normalize_decimal_v2` truncates: `val * sys_decimal_value / 10^native_decimal` using integer division. For a token with more decimals than `sys_decimal_value` (e.g. 9-decimal mint vs. default `sys_decimal_value = 10^6`), any `val` (native reserve amount) small enough that `val * 10^6 / 10^9 < 1` truncates to **exactly 0**. That means whenever `total_pc_without_take_pnl` (or `total_coin_without_take_pnl`) is driven down to a small native amount by ordinary swap activity, `x1` (or `y1`) legitimately evaluates to `0`.

Reserves can be pushed toward this low native value by a normal, unprivileged swapper: `process_swap_base_in`/`process_swap_base_out` (and their V2 variants) only guard against the total reaching *exactly* zero (`if swap.amount_out >= total_pc_without_take_pnl { return Err(...) }` [4](#0-3) ), not against it reaching a small residual amount that truncates to zero once normalized. Once `x1 == 0` or `y1 == 0`, the very next call into `calc_take_pnl` (via Deposit, Withdraw, or WithdrawPnl) hits an unchecked `.checked_div(0).unwrap()` and panics, aborting the instruction with a runtime panic instead of a handled `ProgramError`.

`calc_take_pnl` is called unconditionally on every `process_deposit` [5](#0-4) , on `process_withdrawpnl` [6](#0-5) , and on `process_withdraw` unless `amm.status == WithdrawOnly` [7](#0-6) . Because the low-decimal-normalized reserve state persists on-chain (it is a function of the current vault balances, not a one-off input), every subsequent attempt to deposit, withdraw, or take PNL will panic identically until the imbalance is repaired — which for `Deposit`/`WithdrawPnl` there is no code path to bypass.

### Impact Explanation
This is a repeatable, attacker-triggerable availability failure reachable from unprivileged swap transactions, mirroring the CVE's "hang or frequently repeatable crash" DoS class. Concretely:
- LPs are unable to deposit new liquidity (`process_deposit` always calls `calc_take_pnl`).
- LPs are unable to withdraw existing liquidity through the normal path (`process_withdraw` calls `calc_take_pnl` unless the pool is already in `WithdrawOnly` status — a state only the pool admin can set), effectively freezing LP funds already deposited in the pool.
- The PNL owner cannot withdraw accrued PNL (`process_withdrawpnl`).

This constitutes permanent freezing of LP funds for as long as the reserve imbalance persists, satisfying the funds-freezing bar for a Medium-severity finding.

### Likelihood Explanation
Reaching the zero-divisor condition requires only ordinary swap transactions from any unprivileged user against a pool whose token decimals exceed `sys_decimal_value`'s implied precision (a common real-world configuration, e.g. a 9-decimal SPL token paired against USDC-like assets under the default `sys_decimal_value = 10^6`). No privileged signer, leaked key, or validator collusion is required — a single attacker-controlled swap sequence using standard `SwapBaseIn`/`SwapBaseOut` instructions with attacker-chosen amounts can drive one side's post-PNL reserve down to a native amount that normalizes to zero.

### Recommendation
Replace the unchecked `.unwrap()` divisions in `calc_take_pnl` (and in `Calculator::calc_x_power`) with `checked_div`/`checked_mul` chains that propagate a proper `AmmError` (e.g. `AmmError::CalcPnlError`) instead of panicking when `x1` or `y1` is zero. Additionally, `normalize_decimal_v2` (and `normalize_decimal`) should reject or explicitly branch on truncation-to-zero cases so degenerate small reserves cannot silently become divisors.

### Proof of Concept
1. Initialize a pool where the coin (or pc) mint has decimals large enough relative to `amm.sys_decimal_value` (default `10^6`) that a small native reserve amount normalizes to `0` via `Calculator::normalize_decimal_v2` (e.g. a 9-decimal mint: `val * 10^6 / 10^9 == 0` whenever `val < 1000`).
2. As an unprivileged swapper, repeatedly call `SwapBaseIn`/`SwapBaseOut` to drain that side's `total_*_without_take_pnl` down to a residual native amount below the truncation threshold (the swap-side checks only forbid the total reaching exactly `0`, not a small nonzero residual) — see the guard in `process_swap_base_out` at [4](#0-3) .
3. Call `Deposit`, `Withdraw`, or `WithdrawPnl`. `Calculator::normalize_decimal_v2` on the drained side now returns `0`, and `Processor::calc_take_pnl`'s `checked_div(...).unwrap()` calls ( [1](#0-0) ) panic, aborting the transaction.
4. Every subsequent `Deposit`/`Withdraw`/`WithdrawPnl` transaction against this pool panics identically, freezing LP funds until an admin intervenes (e.g. forcing `WithdrawOnly` status, which only unblocks `Withdraw`, not `Deposit`/`WithdrawPnl`).

    pub fn calc_x_power(last_x: U256, last_y: U256, current_x: U256, current_y: U256) -> U256 {
        // must be use u256, because u128 may be overflow
        let x_power = last_x
            .checked_mul(last_y)
            .unwrap()
            .checked_mul(current_x)
            .unwrap()
            .checked_div(current_y)
            .unwrap();
        x_power
    }
