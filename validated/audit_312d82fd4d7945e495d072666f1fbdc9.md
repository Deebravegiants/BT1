### Title
Litecoin legacy vs. new P2SH address encodings bypass `compareAddresses`, allowing PoaBridge withdrawal to the token's own address - (File: packages/intents-sdk/src/lib/compareAddresses.ts)

### Summary
`compareAddresses` compares Litecoin addresses with raw string equality (`a === b`), but `validateAddress`/`validateLitecoinAddress` accepts two distinct base58 textual encodings of the same underlying hash160 script — legacy P2SH (`3...`, version `0x05`) and modern P2SH (`M...`, version `0x32`). If the bridged token's `origin_chain_address` is recorded in one form and the attacker supplies the other, `validateWithdrawal` in `PoaBridge` fails to detect that the destination is actually the token contract's own address, so `DestinationAddressMatchesTokenAddressError` is never thrown.

### Finding Description
The invariant that should hold is: for any accepted Litecoin address `d` and the token's own address `t`, if `d` and `t` denote the same script/account, `compareAddresses(t, d, 'bip122:...')` must return `true`.

In `packages/intents-sdk/src/lib/validateAddress.ts`, `validateLitecoinAddress` (lines 506-535) explicitly accepts three base58 P2SH-capable prefixes for the same 20-byte hash160 payload class: P2PKH `L` (version `0x30`), new P2SH `M` (version `0x32`), and legacy P2SH `3` (version `0x05`) — the comment even notes "[Inference] This also matches Bitcoin P2SH; cannot distinguish by prefix+version alone," confirming both `3...` and `M...` are treated as valid Litecoin addresses by this validator. On the Litecoin network, the version byte is purely an address-encoding convention for P2SH; both the legacy `3...` and modern `M...` encodings of the same hash160 payload construct the identical `OP_HASH160 <hash> OP_EQUAL` scriptPubKey and are spendable/received identically on-chain — they are the same account with two textual encodings.

However, `compareAddresses` in `packages/intents-sdk/src/lib/compareAddresses.ts` (lines 48-60) handles `Chains.Litecoin` (along with Near/Bitcoin/BitcoinCash/Zcash/Dogecoin/Solana/Fogo/XRPL/Cardano/Aleo/Dash) via plain `a === b` string comparison, with no chain-specific base58/version-byte canonicalization like the ones implemented for Ethereum (`getAddress`), Tron (`decodeTronAddress`), or TON (`tryParseTonAddress`).

Exploit flow in `PoaBridge.validateWithdrawal` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`, lines 170-219):
1. Suppose the PoA bridge's `getSupportedTokens` response returns `tokenInfo.origin_chain_address` for the bridged LTC-side token contract as the modern P2SH form, e.g. `M...`.
2. The attacker supplies `destinationAddress` as the legacy P2SH encoding `3...` of the **same** hash160 payload.
3. `validateAddress(args.destinationAddress, Chains.Litecoin)` returns `true` (line 182) since `validateLitecoinBase58Address` accepts version `0x05`.
4. `compareAddresses(tokenInfo.origin_chain_address, args.destinationAddress, Chains.Litecoin)` at line 209 does `a === b` on the two differently-prefixed strings and returns `false`, even though they resolve to the same on-chain script.
5. `DestinationAddressMatchesTokenAddressError` is never thrown, and `createWithdrawalIntents`/`processWithdrawal` proceeds to sign and submit a withdrawal that sends the bridged token's underlying LTC (or LTC-native asset) to the token contract's own address, where it becomes unrecoverable.

No other guard intercepts this: `supports()` only checks route/asset-id shape, `getUnderlyingFee`/`FeeExceedsAmountError` are unrelated to address matching, and the intents contract's own signature/nonce checks do not validate destination-address semantics at all — they only verify the signer authorized the (already-wrong) intent.

### Impact Explanation
This causes funds to be irreversibly delivered to the bridged token's own contract address instead of a real recipient — a direct, permanent loss of user funds with no recovery path once the withdrawal is broadcast to the Litecoin network, matching the "Critical: funds delivered to a wrong address/chain/contract with no recovery" category. Any unprivileged NEAR Intents user (or an integrator forwarding an untrusted destinationAddress) triggers this per withdrawal call, and it is repeatable for every LTC-denominated PoA bridge asset whose `origin_chain_address` happens to be recorded in one P2SH textual form while the attacker supplies the equivalent alternate encoding.

### Likelihood Explanation
The precondition is that the token's registered `origin_chain_address` (from the PoA bridge's `getSupportedTokens` API) is a P2SH-type Litecoin address (legacy `3...` or modern `M...`), and the underlying script has a valid alternate-prefix encoding accepted by `validateLitecoinAddress`. The attacker needs no privileges beyond initiating a normal withdrawal with a chosen `destinationAddress` — computing the alternate base58 encoding of a known hash160 (same payload, different version byte, recomputed checksum) is trivial and requires no special access.

### Recommendation
In `compareAddresses.ts`, add Litecoin/Bitcoin-family-specific canonicalization for base58 P2SH-style addresses analogous to `compareTronAddress`: decode both addresses, extract the raw hash160 payload independent of the version byte (or normalize known equivalent version-byte pairs, e.g. Litecoin's `0x05` and `0x32` P2SH), and compare the underlying payload bytes rather than raw strings. Alternatively, restrict `validateLitecoinAddress` to accept only the canonical/modern P2SH prefix so ambiguous legacy encodings cannot be used to defeat the equality check.

  expect(validateAddress(legacyP2SH, Chains.Litecoin)).toBe(true);

it("compareAddresses fails to recognize same-account equivalence (BUG)", () => {
  // These denote the same script/account on Litecoin, so this SHOULD be true
  expect(compareAddresses(modernP2SH, legacyP2SH, Chains.Litecoin)).toBe(false); // currently false — bug
});

export function validateLitecoinAddress(address: string): boolean {
	const first = address[0];

	// ---- Base58 (mainnet) ----

	// P2PKH: L... (0x30)
	if (first === "L") {
		return validateLitecoinBase58Address(address, 0x30);
	}

	// P2SH (new): M... (0x32)
	if (first === "M") {
		return validateLitecoinBase58Address(address, 0x32);
	}

	// P2SH (legacy): 3... (0x05)
	// [Inference] This also matches Bitcoin P2SH; cannot distinguish by prefix+version alone.
	if (first === "3") {
		return validateLitecoinBase58Address(address, 0x05);
	}

	// ---- Bech32 / Bech32m (SegWit) ----

	const lower = address.toLowerCase();
	if (!lower.startsWith("ltc1")) {
		return false;
	}

	return validateLitecoinBech32Address(address);
}
