### Title
Malicious order input token can permanently block escrow refund/release in `_withdraw` - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentGatewayV2.placeOrder` lets the order creator pick arbitrary `order.inputs[].token` addresses to escrow, including any ERC20-shaped contract. `_cancelSameChain`/`_fillSameChain` (and their cross-chain counterparts via `_cancelFromDest`/RedeemEscrow) route through the shared `_withdraw` function, which loops over every escrowed token and calls `IERC20(token).safeTransfer(beneficiary, amount)` unconditionally, in the same way `calculateRemainingPrincipal()` unconditionally calls `ownerOf()` in the Sherlock report. If any single one of the order's input tokens reverts on transfer (blocklist-style token, a token that reverts on transfer to a "burned"/paused/zero-code beneficiary, or a token whose owner can pause/blacklist a specific recipient after escrow is created), the entire `_withdraw` loop reverts, and with it the entire `cancelOrder`/`fillOrder` transaction.

### Finding Description
`_withdraw` (`evm/src/apps/intentsv2/IntentsBase.sol:451-485`) iterates `body.tokens` and does:
```solidity
if (token == address(0)) {
    _sendValue(beneficiary, amount);
} else {
    IERC20(token).safeTransfer(beneficiary, amount);
}
``` [1](#0-0) 

There is no `try/catch` around the transfer, unlike the recommendation in the Sherlock report (which suggests wrapping `ownerOf()` in try/catch). Because `placeOrder` (`evm/src/apps/IntentGatewayV2.sol:194-415`) allows the order creator to escrow **any** token address as an input (only rejecting duplicates, not validating the token's transfer behavior), a user can place an order with a normal token (e.g. USDC) plus one attacker-controlled/blocklist-capable ERC20 as a second input. If that token's owner (or the order creator itself, if the token is self-deployed) later blocks the `beneficiary` address (the solver on fill, or `order.user` on cancel) from receiving transfers, every subsequent call into `_withdraw` for that commitment — both `_cancelSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol:159-180`) and `_fillSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol:53-143`) — reverts on that one bad token, permanently freezing every other escrowed token for that same commitment as well, since `_withdraw` is atomic across the whole `tokens[]` array.

This mirrors the root cause of H-11 exactly: a single external call embedded in a loop over per-order/per-protection state, whose revert is fully attacker-triggerable (burn vs. blocklist), poisons the entire batched state transition (`lockCapital()` vs. `cancelOrder()`/`fillOrder()`), denying the counterparty (buyer vs. order creator/solver) their expected outcome while leaving funds stuck in escrow.

### Impact Explanation
A blocked transfer inside `_withdraw` permanently freezes **all** escrowed tokens tied to that commitment, not just the malicious token's amount — the user's other legitimate input tokens (e.g. USDC) become unrecoverable through `cancelOrder`, and a solver who already delivered outputs on `fillOrder` can be denied their input-side escrow release. This is a permanent freezing-of-funds condition reachable by any unprivileged order placer choosing their own input token list.

### Likelihood Explanation
Likelihood is High: placing an order is a fully permissionless, single-transaction action (`placeOrder`), and the input token list is entirely attacker-controlled with only a duplicate check (`evm/src/apps/IntentGatewayV2.sol:195-221`) — no allowlist or transfer-safety check is applied to `order.inputs[].token`.

### Recommendation
In `_withdraw` (`evm/src/apps/intentsv2/IntentsBase.sol:451-485`), isolate each token transfer with a low-level call and `try/catch` (or a `.call` + success flag) instead of `safeTransfer` directly in the loop, and skip/queue failed transfers for later retry rather than reverting the whole batch — mirroring the Sherlock recommendation of treating a failing external call as "not deliverable now" rather than aborting the entire state transition. At minimum, decouple failure of one token in the array from the others so a single malicious/blocklisting token cannot hold the rest of the escrow hostage.

### Proof of Concept
1. Attacker (as order user) calls `placeOrder` with `order.inputs = [ {token: USDC, amount: X}, {token: MALICIOUS_TOKEN, amount: Y} ]`, escrowing both.
2. After escrow is locked (`evm/src/apps/IntentGatewayV2.sol:364-373`), the attacker (owner of `MALICIOUS_TOKEN`, or exploiting a token with pausable/blacklist admin functions) blacklists the `beneficiary` address that will later receive `MALICIOUS_TOKEN` on refund/release (either their own address for a cancel-refund griefing scenario against a solver, or the solver's address to grief the solver on `fillOrder`).
3. Order expires or a solver fills it; `cancelOrder` → `_cancelSameChain` → `_withdraw`, or `fillOrder` → `_fillSameChain` → `_withdraw`, iterates both tokens; the `safeTransfer` call for `MALICIOUS_TOKEN` reverts.
4. The entire `_withdraw` call reverts, so the USDC leg is never released either — the escrowed USDC is now permanently stuck, since every future `cancelOrder`/`fillOrder` call hits the same revert. [2](#0-1) [3](#0-2) [4](#0-3)

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }
