### Title
Emporium-min proof path accepts an authorization message with no binding to the spender's key - (File: `circuits/MainEVMCircuitMin.circom`, `contracts/CircomDataBuilder.sol`)

### Summary
When a transaction targets the Emporium external action with zero ERC20 addresses, `CircomDataBuilder.formInputForCircom` routes to `formInputEmporiumMin`, which is verified against a minimal circuit (`MainEVMCircuitMin`) that has no EdDSA signature check and no `nullifyingPrivateKey`/`spendingPublicKey` at all.

### Finding Description
The dispatch logic in `contracts/CircomDataBuilder.sol` selects the minimal input-forming path whenever the external action is the Emporium action and no ERC20 token addresses are supplied: [1](#0-0) 

That minimal path only emits `emporiumMessage`, `timeStamp`, and `calldataHash` as the public-input vector: [2](#0-1) 

Compare this to `MainEVMCircuitMin`, which is the circuit template matching this reduced signal set: [3](#0-2) 

This circuit's only constraint is `message <== Poseidon(1)([messageSeed])`, where `messageSeed` is a private witness fully chosen by the prover. There is no `spendingPublicKey`, `eddsaSignature`, or `signedMessageHash` signal anywhere in this template — unlike the full circuit (`MainEVMCircuit.circom`), which requires a `SignatureVerifier` component binding the prover to a specific `spendingPublicKey`: [4](#0-3) [5](#0-4) 

Because `emporiumMessage` (the circuit's `message` output) is just `Poseidon(messageSeed)` for an attacker-chosen `messageSeed`, **anyone** can produce a valid Groth16 proof for any arbitrary `emporiumMessage` value — there is no proof that the caller controls the stealth address / spending key that the message is supposedly issued on behalf of. This is the same class of bug as the reported one: a value (`message`/`emporiumMessage`) that is treated as an authenticated authorization by downstream logic is not actually bound to `signedMessageHash` or any owner-controlled key inside the circuit that gets exercised on this path.

I confirmed via `HinkalHelper.dimensionsCheck` that this minimal path forces `tokenNumber`, `nullifierAmount`, and `outputAmount` to zero (so no nullifiers are spent and no commitments are inserted through this specific call): [6](#0-5) 

That rules out a direct double-spend of the shielded UTXO tree through *this exact call*. However, `emporiumMessage` is referenced 13 times in `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`, strongly suggesting it is used there as an authorization token for a follow-on action (e.g., an already-deposited balance in `HinkalWallet.sol`/`EmporiumStack.sol` being spent/withdrawn on the strength of a validated `message`). **I was not able to read that file's contents before running out of iterations**, so I cannot confirm whether a forged `emporiumMessage` (with no real signature backing) can actually be replayed there to move funds that were not authorized by the wallet owner.

### Impact Explanation
If `EmporiumUpgradeable`/`HinkalWallet` trusts a verified `emporiumMessage` as proof that the wallet owner authorized a specific action (this is the typical purpose of such a "message" output in Hinkal's design, mirroring the `signedMessageHash` pattern used in the full circuit), then this would allow an attacker to forge that authorization without knowing the owner's `spendingPublicKey`/private key, since `MainEVMCircuitMin` never checks a signature. That would constitute unauthorized movement of funds/execution of calls a wallet owner never authorized — a Critical/High severity issue per the given impact classes. This is unverified because the consuming contract's logic could not be inspected in this session.

### Likelihood Explanation
The attack requires no privileged role — any unprivileged EOA can call `Hinkal.transact` with `erc20TokenAddresses.length == 0` and `externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID`, then supply a self-chosen `messageSeed` and compute a matching Groth16 proof for `MainEVMCircuitMin`, which has no signature or key-ownership constraint. If the downstream Emporium/Wallet logic indeed keys authorization off `emporiumMessage`, exploitation is straightforward and requires no relayer, admin, or oracle assumptions.

### Recommendation
Verify what `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol` and `contracts/external-actions/emporium/HinkalWallet.sol` do with `circomData.emporiumMessage`. If it is used to authorize spending of previously deposited/committed value or execution of wallet calls, `MainEVMCircuitMin` must be extended to bind `message`/`emporiumMessage` to a real signature check (`SignatureVerifier` over `spendingPublicKey`) the same way the full `MainEVMCircuit` does, rather than a bare `Poseidon(messageSeed)` with no key binding.

### Proof of Concept
Not producible without confirming the downstream consumer of `emporiumMessage`. The provable part of the chain is:
1. Caller submits `circomData` with `erc20TokenAddresses = []` and `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`.
2. `CircomDataBuilder.formInputForCircom` selects `formInputEmporiumMin`, producing public input `[emporiumMessage, timeStamp, calldataHash]` [7](#0-6) .
3. Caller picks any `messageSeed`, computes `emporiumMessage = Poseidon(messageSeed)`, and generates a valid Groth16 proof against `MainEVMCircuitMin` — no signature or private key required [3](#0-2) .
4. `Hinkal.transact` accepts the proof since `verifyProof` only checks the Groth16 proof against these public inputs, not any signature semantics [8](#0-7) .

Whether step 4's accepted `emporiumMessage` can then be replayed to move real funds in the Emporium/Wallet contracts is the missing link that needs to be confirmed by reading `EmporiumUpgradeable.sol` (not fully available to me in this session — a full Devin session with file-system access would be needed to confirm or refute this final step).

  spendingPublicKeySubgroupCheck.Ax <== spendingPublicKey[0];

  component r8SubgroupCheck = BabyJubjubSubgroupCheck();
  r8SubgroupCheck.Ax <== eddsaSignature[0];
