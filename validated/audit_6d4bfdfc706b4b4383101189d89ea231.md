### Title
`PollerAgent::main_loop` bypasses the `src.id` sender-identity check for `RequestState` messages, allowing any relay peer to trigger a replay of the last sent message — ([File: orb-relay-client/src/client.rs])

### Summary
`orb-relay-client`'s `PollerAgent::main_loop` enforces a sender-identity check (`src.id != self.config.dst_id`) before processing incoming relay payloads, discarding messages from unexpected sources. However, this check is skipped entirely for one specific payload type, `self_serve::app::v1::RequestState`: any message that matches this type causes the client to immediately resend its last outgoing message, with no verification of who sent the triggering `RequestState`. This mirrors the `UnionToken` finding's root cause — an authorization/identity check that is bound to the wrong (or no) party, letting an untrusted actor act as if it were the trusted counterpart.

### Finding Description
In `main_loop`, the relay response is matched as: [1](#0-0) 

The check order is:
1. If the payload matches `RequestState`, resend `self.last_message` — **no identity check at all**.
2. Else if `src.id != self.config.dst_id`, drop the message as "unexpected source".
3. Else handle normally.

The `src.id` check in branch 2 exists specifically because the underlying transport multiplexes messages from multiple sources onto the same stream, as documented by the developers themselves: [2](#0-1) 

That TODO explicitly states that the current design "will avoid multiplexing messages from different sources" once implemented — confirming that today, messages from sources other than the intended `dst_id` peer can and do reach this handler. The `RequestState` branch bypasses the very check meant to filter those foreign-sourced messages, so a message tagged `RequestState` arriving from a source that is not the paired `dst_id` still causes the client (Orb or App) to resend its `last_message`.

This is structurally identical to the `UnionToken` bug: a privileged action (`_beforeTokenTransfer`'s whitelist enforcement / here, "reply only to my paired peer") is gated by the wrong entity check — in `UnionToken` it checked `msg.sender` instead of `from`; here it checks nothing for `RequestState` instead of checking `src.id` like every other payload type.

### Impact Explanation
`last_message` can contain the most recent session/signup state payload sent over the relay channel (see `no_state()`/`self.last_message` usage in `PollerAgent`, `RelayPayload`). An entity that is not the legitimate paired counterpart (i.e., not equal to `config.dst_id`) can force replay of that state to itself by sending a `RequestState` payload that reaches the stream (per the acknowledged multiplexing behavior). This is a cross-session/cross-peer state disclosure and replay primitive: an unauthorized relay client can pull the last state message intended for a specific Orb/App pairing, potentially leaking session or signup-related state to a party it was never destined for, and can also spuriously trigger state replays observable by the legitimate peer.

### Likelihood Explanation
Exploitability requires only the capability of an ordinary relay client (App or Orb identity, authenticated via `Auth::Token` or ZKP as already supported by this same client — no elevated privilege), and the ability to send a `RequestState` message on a channel that the target is also multiplexed onto. The code's own comment acknowledges multiplexing occurs today, making this reachable by design rather than a hypothetical edge case.

### Recommendation
Perform the `src.id == self.config.dst_id` identity check uniformly for **all** incoming payload types, including `RequestState`, before taking any action (including the "resend last message" convenience path). If `RequestState` must be answerable from any relay-level participant, explicitly scope and audit that decision instead of implicitly exempting it from the existing trust-boundary check.

### Proof of Concept
1. Two legitimate peers (Orb `O` and App `A`) establish a relay session; `O`'s `main_loop` runs with `config.dst_id == A`'s session id.
2. A third relay client `M` (any authenticated app/orb entity, not part of this pairing) manages to have a message delivered into the same multiplexed stream that `O` is reading (per the documented multiplexing behavior noted in the TODO at `client.rs:389-391`).
3. `M` sends a `self_serve::app::v1::RequestState` payload.
4. `O`'s handler at `client.rs:436-440` matches `RequestState` unconditionally and sends `self.last_message` back on the stream — without ever checking that the payload's `src` equals the expected `dst_id`.
5. The last state message, intended only for `A`, is transmitted again in response to `M`'s unauthenticated-for-this-pairing request. [1](#0-0) [2](#0-1)
