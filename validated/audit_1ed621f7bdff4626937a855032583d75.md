## Finding

### Title
Webhook shop/topic/webhook_id identity is trusted from unauthenticated headers while the HMAC only covers the body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` from raw HTTP headers, none of which are covered by the HMAC signature. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then unconditionally trusts these header-derived values to build the `WebhookMetadata` object handed to the host application's handler, allowing the tenant identity (`shop`) carried by a webhook delivery to be forged independently of a valid signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes and compares the signature strictly against `to_signable_string`, i.e. only the body: [2](#0-1) 

Meanwhile, `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from request headers with no cryptographic binding to the signed payload: [3](#0-2) 

`Registry.process` validates only the HMAC (i.e. only the body) and then immediately trusts the header-derived `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` to construct the metadata object passed to the app's handler: [4](#0-3) 

The identity binding that should hold is: `shop covered by HMAC == shop used to attribute webhook data`. Instead, the equality actually enforced is only `body covered by HMAC == body used`, while `shop (header, unauthenticated) == shop delivered to handler`. Because the app's `api_secret_key` is shared across every shop that has the app installed, any actor who can get the app installed on a shop they control (a normal, unprivileged install — no special privilege beyond installing an app) will receive genuine webhook deliveries whose bodies are validly HMAC-signed with that same shared secret. That attacker can capture one such valid `(raw_body, hmac)` pair and replay it to the app's public webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header value naming a different, victim shop. `HmacValidator.validate` will still pass (it only checks the body/secret pair), and `Registry.process` will hand the host application a `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
This breaks the tenant boundary the library is expected to enforce for webhook processing: a request's cryptographic authenticity (HMAC over body) does not extend to the reported shop identity. Any host application that uses `WebhookMetadata#shop` to attribute incoming webhook data to a specific merchant/tenant (the documented and expected usage pattern) can be made to associate forged or replayed data with an arbitrary victim shop, i.e. cross-tenant data injection/impersonation using only a shared secret common to every installer of the app.

### Likelihood Explanation
Any actor able to install the app on their own store (a normal, low-privilege action, not requiring any leaked credential or admin access) automatically receives real, validly-signed webhook bodies. Replaying such a body with a substituted `shop-domain` header to the same publicly reachable webhook endpoint is trivial and requires no knowledge of `api_secret_key` value, only observation of one legitimate delivery.

### Recommendation
Do not rely solely on unauthenticated headers for tenant attribution. At minimum, document/require that host apps only trust `shop` values from `WebhookMetadata` when they correspond to a shop that has an active, previously-established session/installation record, and consider incorporating shop/topic into a broader validation step (e.g. cross-checking the header shop against the topic's expected recipient using Shopify's webhook ID lookup) rather than passing header-derived identity straight through once only the body has been authenticated.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; the app's webhook endpoint will receive a real webhook, e.g. body `{"id":1}` with header `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Replay the same raw body and HMAC value to the app's public webhook URL, but set `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally a different `X-Shopify-Topic`).
3. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks the body against the shared secret.
4. `ShopifyAPI::Webhooks::Registry.process` in `lib/shopify_api/webhooks/registry.rb` invokes the host handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the application to process attacker-supplied data as if it originated from the victim shop.
