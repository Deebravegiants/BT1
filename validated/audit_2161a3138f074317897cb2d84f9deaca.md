### Title
Unauthenticated dispatch of arbitrary runtime calls via unsigned cross-chain calldata - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
The MONAI advisory is a class of "decode untrusted bytes → immediately execute/act on them without validating who supplied them." The closest reachable analog in Hyperbridge is `hyper-fungible-token`'s `on_accept` handler, which SCALE-decodes attacker-supplied `data` from an inbound cross-chain token message into a `SubstrateCalldata { signature: Option<Vec<u8>>, runtime_call: Vec<u8> }` and then `Decode`s and `dispatch`es the embedded `runtime_call` as a live extrinsic. When `signature` is `None`, the code skips all cryptographic authentication and derives the dispatch `origin` directly from the message's own `from` field, which is part of the attacker-controlled cross-chain payload.

### Finding Description
In `modules/pallets/hyper-fungible-token/src/module.rs`, `on_accept` decodes the optional calldata: [1](#0-0) 

When `substrate_data.signature` is `Some(...)`, the code verifies an Ed25519/Sr25519/Ecdsa signature over `(nonce, runtime_call)` before letting the call proceed under the beneficiary's account: [2](#0-1) 

But when `signature` is `None`, no proof-of-key-ownership is required at all — the origin is simply derived from `message.from`, a byte field carried inside the same attacker/source-contract-controlled ABI message: [3](#0-2) 

The decoded `runtime_call` is then dispatched under that unauthenticated origin, gated only by the runtime's generic `BaseCallFilter` (not by any identity check tying the call to the actual message sender): [4](#0-3) 

This mirrors the MONAI root cause structurally: bytes originating from an external, untrusted source (`pickle.loads(data_bytes)` in MONAI vs. `SubstrateCalldata::decode` / `T::RuntimeCall::decode` here) are turned directly into executable behavior (arbitrary Python object construction/`__reduce__` call vs. arbitrary `RuntimeCall::dispatch`) without validating that the origin of the bytes is entitled to trigger that behavior when the "no signature" branch is taken.

### Impact Explanation
Any relayer delivering a POST request into `hyper-fungible-token::on_accept` can attach a `data` payload whose `SubstrateCalldata.signature` is `None`. The pallet then dispatches an arbitrary (filter-permitted) extrinsic as the account derived from the attacker-controlled `message.from` bytes — for EVM sources, this is `EvmToSubstrate::convert(H160::from(from_bytes))`, and for non-EVM sources, it's the raw 32-byte account id taken verbatim from `message.from`. Because `message.from` is part of the same message the caller constructs, an attacker can choose it to collide with any account whose funds/permissions they want to act on, then have the pallet execute arbitrary runtime calls (transfers, approvals, governance-adjacent calls not excluded by `BaseCallFilter`, etc.) as that account with zero cryptographic proof of control. This is unauthorized app action / potential theft of funds reachable from a single relayed cross-chain message.

### Likelihood Explanation
Reachable by any unprivileged relayer or token bridger simply by crafting an inbound ERC20-bridge POST message with a `data` field containing a SCALE-encoded `SubstrateCalldata` with `signature = None`. No special privileges, governance, or malicious-admin/relayer collusion is required beyond normal message delivery through the existing dispatch path, which matches the required threat model (message dispatcher/relayer/token bridger).

### Recommendation
Require signature verification (or another cryptographically binding proof linking `message.from` to the dispatch origin) unconditionally before dispatching `runtime_call`, rather than allowing an unauthenticated fallback keyed only on attacker-supplied `message.from` bytes. If the "no signature" path is intended to represent "the calldata is dispatched as the token recipient/sender who initiated the transfer on the source chain," that invariant must be enforced by the source-chain contract (i.e., `message.from` must be provably `msg.sender` there) and/or cryptographically checked on the destination, not merely trusted from the decoded payload.

### Proof of Concept
1. Attacker (or any relayer) prepares a cross-chain `Message` whose ABI-encoded `data` field decodes to `SubstrateCalldata { signature: None, runtime_call: <SCALE-encoded RuntimeCall> }`, where `runtime_call` is any call allowed by `BaseCallFilter` (e.g., an asset transfer or another permitted extrinsic).
2. Attacker sets `message.from` to the 20/32-byte representation of a victim account (or any account they want to act as) — this field is fully controlled by whoever calls the source-chain bridging contract and is not independently authenticated on the destination.
3. The message is relayed and delivered to `on_accept` in `modules/pallets/hyper-fungible-token/src/module.rs`.
4. Since `substrate_data.signature` is `None`, no signature check runs; `origin` is derived directly from `message.from` ( [3](#0-2) ), and `runtime_call.dispatch(RawOrigin::Signed(origin))` executes as that account ( [5](#0-4) ).
5. The result is an arbitrary filter-permitted extrinsic executed under an account the attacker never proved control of.

Note: full confirmation that the source-chain Solidity contract does not itself constrain `message.from == msg.sender` could not be completed due to index size limits on `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`; a Devin session with full repo access would be needed to verify that side of the trust boundary conclusively.
