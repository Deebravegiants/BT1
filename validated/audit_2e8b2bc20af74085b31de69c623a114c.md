### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](https://github.com/Alyssadaypin/shopify-api-ruby--013/blob/main/lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while `shop`, `topic`, `webhook_id` and `api_version` are read from headers that are never included in that signable string. `Registry.process` validates the HMAC and then forwards the unverified `request.shop` value straight to the host application's handler as the tenant identifier, breaking the binding between "shop whose data was HMAC-authenticated" and "shop the handler acts on".

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is part of the `@headers` hash and is completely independent from `@raw_body`: [2](#0-1) 

`Utils::HmacValidator.validate` only ever recomputes the HMAC from `verifiable_query.to_signable_string`, i.e. the body — the shop header plays no role in the signature check: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) to build the `WebhookMetadata` object passed to the app's handler: [4](#0-3) 

Because Shopify signs webhooks with the app's single `client_secret` (`Context.api_secret_key`) shared across every shop that has the app installed, the same secret produces a valid signature for the same body regardless of which shop it was originally sent for. This breaks the intended identity equality: `shop authenticated by HMAC == shop the handler acts on`. In reality the equality that holds is only `body authenticated by HMAC == body received`; the `shop` binding is asserted by the gem to callers via `WebhookMetadata#shop` without any cryptographic backing.

### Impact Explanation
Since `WebhookMetadata#shop` is what host applications (e.g. `shopify_app`) use to look up the tenant/session the webhook data belongs to, an attacker who legitimately installs the app on their own store (an unprivileged action requiring no special credentials beyond installing a public app) can obtain genuinely HMAC-signed webhook payloads for their own shop, then replay the identical raw body to the app's webhook endpoint while substituting a victim shop's domain in the `X-Shopify-Shop-Domain` header. `HmacValidator.validate` still succeeds (it never inspects the header), so `Registry.process` dispatches the attacker-controlled body to the handler as if it originated from the victim shop — a cross-tenant data-confusion/injection primitive.

### Likelihood Explanation
Any app using this gem's webhook `Registry` is affected by construction, since the vulnerability is in the shared `HmacValidator`/`Request` design rather than in any specific app's configuration. Exploitation only requires an attacker who can install the target app on a store they control (a normal, low-privilege step for any public app) and the ability to send an arbitrary HTTP POST to the app's public webhook endpoint — no access token, session, or leaked secret is needed.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the HMAC-signable string, or otherwise cryptographically bind them to the payload, so that a signature computed for shop A's payload cannot be replayed under shop B's identity. At minimum, `Registry.process` should cross-check that the shop claimed in the header matches a shop that is expected to be able to produce this specific payload (e.g., via a per-shop verification step) before invoking the handler.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Attacker triggers a webhook (e.g. `orders/create`) and captures the raw POST: body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker resends the exact same request to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com`, keeping body `B` and header `H` unchanged.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC from `request.to_signable_string` (`B` only) and matches `H` — validation succeeds despite the falsified shop.
5. `Registry.process` builds `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` and calls the app's handler, which processes attacker-controlled data under the victim tenant's identity.
