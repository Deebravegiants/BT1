### Title
Tokens pushed to the controller during `flash_position` — or sent directly — are permanently stranded with no recovery path - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
The analog to the Axelar Executor finding is the XOXNO controller's handling of token balances it holds but did not measure. When `flash_position` invokes the receiver callback, the receiver pays collateral back to the controller via plain token `transfer`. The controller only accounts for assets declared in `collaterals` (deposited to the account) or `refund_assets` (refunded to the caller). Any other token balance increase is neither credited nor returned. There is no sweep, rescue, or recovery entrypoint on the controller: `claim_revenue` deliberately forwards only the measured pool receipt and leaves pre-existing controller balances untouched, so stranded tokens are locked forever. A direct `token.transfer` to the controller strands funds the same way.

### Finding Description
In `process_flash_position`, the controller snapshots `collateral_before` / `refund_before` balances, invokes `execute_flash_position` on the caller-chosen receiver, and then measures balance deltas only for the declared asset lists. Post-callback settlement deposits positive deltas for declared collateral markets and refunds positive deltas for declared refund assets. Tokens of any other asset transferred to the controller during the callback receive neither treatment.

This is confirmed by the protocol's own documentation: "Undeclared callback assets receive neither credit nor refunds. There is no controller sweep endpoint" (docs/reference/endpoints.md line 86), and INV-STRAT-04 / ADR-0020 document that returned assets "remain uncredited if in neither list."

Worse, the refund path cannot rescue such tokens even when the user wants them back: `validate_refund_assets` requires each refund asset to be listed in the debt hub and the account's spoke, disjoint from collateral declarations, and capped at `max_supply_positions` (docs/reference/endpoints.md line 84). Any token that is not a listed market asset — a reward token, an airdrop, a third-leg output of a multi-hop swap inside the receiver, or any SAC not yet/never listed — has no declare-or-refund option at all.

`claim_revenue` does not help either: `claim_revenue_for_asset` snapshots the controller balance, calls pool `claim_revenue`, and forwards only the measured delta to the accumulator. The test `claim_revenue_forwards_the_measured_amount_and_leaves_controller_dust_intact` proves pre-existing controller dust is intentionally untouched. There is no other entrypoint capable of moving a pre-existing controller token balance.

### Impact Explanation
Permanent freezing / loss of user funds. Any unlisted token, undeclared asset, or direct transfer that lands on the controller address is unrecoverable by anyone, including governance. Unlike the Axelar case there is no recovery-address fallback; the balance sits at the controller indefinitely and is explicitly excluded from revenue claims.

### Likelihood Explanation
Medium. Reachable by a single unprivileged address through `flash_position` (in-scope entrypoint) with its own receiver contract, or by a plain token `transfer` to the controller. The stranding requires the caller to receive/push an asset not in its declared lists — realistic when a routed swap emits an unexpected output token or a protocol pays out an unlisted reward — but the caller controls the declaration lists, which lowers likelihood for listed assets. For unlisted tokens there is no mitigation whatsoever.

### Recommendation
Add a recovery path for non-accounted controller balances, e.g. a governance-executable `rescue_token(asset, to, amount)` op, or extend the flash-position refund rules so any positive post-callback delta for assets not declared as collateral is refunded to the caller regardless of listing status. Short of that, restrict receiver payouts to declared assets where feasible.

### Proof of Concept
1. Alice calls `flash_position` with a listed debt market and declares `collaterals = [(hub, XLM, min)]` and `refund_assets = []`.
2. Her receiver, inside `execute_flash_position`, buys XLM and transfers it to the controller, and also receives/transfers a third token (e.g. an unlisted reward token, or USDC she forgot to list in `refund_assets`) to the controller.
3. The transaction succeeds: declared XLM delta is measured and deposited; the third token's positive delta matches neither list, so it is neither credited nor refunded — matching `flash_position_refund_undeclared` behavior in `tests/integration/flows/flash_position.sh` (controller balance delta asserted unchanged means the extra is only refunded when declared; when not declared it stays).
4. No subsequent call — `claim_revenue`, `recapitalize`, any strategy verb, or governance operation — can move the stranded balance. `claim_revenue_for_asset` forwards only the measured pool receipt (contracts/controller/src/markets.rs `claim_revenue_for_asset`), and the harness test `claim_revenue_forwards_the_measured_amount_and_leaves_controller_dust_intact` proves controller dust is untouched. The tokens are permanently frozen.
