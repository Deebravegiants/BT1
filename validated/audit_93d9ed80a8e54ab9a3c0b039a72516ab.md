### Title
Fee-on-transfer / deflationary input tokens let `placeOrder` over-credit escrow, allowing withdrawal of tokens the gateway never held - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron deployment of `IntentGatewayV2.placeOrder` credits `_orders[commitment][token]` with the *nominal* order amount (minus protocol fee) instead of the amount actually received by the contract. Unlike the mainline EVM `IntentGatewayV2.sol`, which measures `balanceOf` before/after `safeTransferFrom` to account for fee-on-transfer/deflationary tokens, the Tron variant blindly trusts the requested amount, exactly the class of bug that let the BCE attacker distort AMM reserve accounting and drain funds it never legitimately backed.

### Finding Description
In `placeOrder`, the non-predispatch branch performs: [1](#0-0) 

`IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` is called, then `_orders[commitment][token] += reducedInputs[i].amount` is credited using the *pre-transfer* requested amount rather than the token's actual balance delta. The predispatch branch has the identical flaw: [2](#0-1) 

Here `balance` (the dispatcher's post-call token balance) is used only to compute `dust = balance - requiredAmount` for the `DustCollected` event; `_orders[commitment][token]` is still incremented by `reducedInputs[i].amount`, the caller-declared value, not what the gateway actually received.

Contrast this with the mainline EVM contract, which explicitly guards against this by snapshotting balances and mutating `order.inputs[i].amount` to the true received amount before computing the commitment and escrow: [3](#0-2) 

The withdrawal path (`withdraw`) later trusts this escrow ledger and performs a raw `token.call(...transfer...)` for the full recorded `amount` without any balance check: [4](#0-3) 

Because the ERC20 balance held by the gateway is a single shared pool across all commitments for that token address, any deflationary/fee-on-transfer/rebasing token accepted as an order input (there is no allow-list visible restricting `order.inputs[i].token` to "safe" tokens) creates a permanent shortfall between the sum of `_orders[*][token]` ledger entries and the contract's real token balance. This is the same root-cause pattern as the BCE exploit: an internal accounting variable (`scheduledDestruction` in BCE, `_orders[commitment][token]` here) is trusted for later balance-affecting operations instead of being reconciled against the real, up-to-date token balance.

### Impact Explanation
Any unprivileged user can call `placeOrder` with a fee-on-transfer, deflationary, or rebasing ERC20 as an input token. Each such order inflates the escrow ledger beyond what the contract actually holds for that token. Since the underlying token balance is a single shared pool, this shortfall is drawn down against every other legitimate order using the same token — whichever withdrawal (fill redemption, cancel, or refund) is settled last for that token will revert due to insufficient balance, permanently freezing that user's escrowed funds, or, if the attacker structures deposits/withdrawals to redeem their own inflated escrow first, they extract more tokens from the shared pool than they contributed, at the expense of other users' legitimate escrows of the same token. This satisfies "concrete theft or permanent freezing of funds" and reaches funds via the unprivileged intents escrow path explicitly in scope.

### Likelihood Explanation
Likelihood is High: exploitation requires only a single `placeOrder` call using a deflationary/fee-on-transfer ERC20 as `order.inputs[*].token` — no privileged role, no cross-chain proof forgery, and no dependency on price oracles or governance. Such tokens are common enough that the gateway's token allow-list (if any exists off-chain/at UI level) would be the only mitigating factor, but nothing in the on-chain code enforces this.

### Recommendation
Mirror the mainline EVM `IntentGatewayV2.sol` fix in the Tron contract: snapshot `IERC20(token).balanceOf(address(this))` (or the dispatcher's balance in the predispatch case) before the transfer, and after the transfer, credit `_orders[commitment][token]` with the *actual received delta*, not the caller-declared `order.inputs[i].amount`/`reducedInputs[i].amount`. Recompute the commitment hash using the actual received amount as is already done for the equivalent EVM path.

### Proof of Concept
1. Deploy/identify a deflationary or fee-on-transfer ERC20 `T` (burns or fee-deducts X% per transfer) and register it as a valid input token for the Tron `IntentGatewayV2`.
2. Attacker calls `placeOrder` with `order.inputs = [{token: T, amount: 1000}]` and `order.output` specifying some output token/amount.
   - `safeTransferFrom(attacker, gateway, 1000)` actually delivers `1000 - fee` tokens to the gateway (e.g., 990 if 1% fee).
   - `_orders[commitment][T] += reducedInputs[0].amount` credits `1000` (minus protocol fee if any) — i.e., more than the `990` actually held.
3. Repeat step 2 with a second, unrelated legitimate order also using token `T` (or wait for another user's legitimate order in `T`), so the shared token balance now backs the sum of ledger entries but is short by the fee amounts accumulated.
4. Attacker (or the destination-chain flow) triggers `onAccept`/`withdraw` for `RedeemEscrow`/`RefundEscrow`/`cancelOrder`, redeeming their inflated ledger entry first.
5. When the second (legitimate) order attempts to withdraw its escrow, `token.call(...transfer...)` fails because the gateway's real `T` balance is insufficient to cover the sum of outstanding `_orders[*][T]` entries — funds are frozen or, if attacker races withdrawal ordering, the attacker extracts value drawn from the other order's contribution.
