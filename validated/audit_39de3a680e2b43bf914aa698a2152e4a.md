### Title
Unvalidated swap routes can inject attacker-controlled contract calls into a user's authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
High severity. The controller forwards attacker-controlled opaque `swap` bytes to the configured router without decoding or constraining the venue addresses encoded inside them. A malicious route can therefore place attacker-controlled contract code beneath the caller's `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral` authorization. During simulation, a token transfer from the caller to the attacker can be recorded as an authorization child; if that simulated tree is signed, the malicious venue can transfer unrelated wallet tokens that were never supplied to the lending protocol.

### Finding Description
`swap_collateral` authenticates only the caller and verifies that the caller owns or delegates the target account, then forwards the user-controlled `swap` bytes into the shared router path. [1](#0-0) [2](#0-1)  The same opaque argument is accepted by `swap_debt`, `repay_debt_with_collateral`, and `multiply`. [3](#0-2) [4](#0-3) 

`swap_tokens` requires only nonempty bytes for a cross-token swap, obtains the configured router, authorizes one exact controller-to-router input transfer, and calls `execute_strategy(&controller, &amount_in, swap)` without decoding the route or validating venue addresses contained in it. [5](#0-4)  The authorization deliberately covers only the token input transfer and contains no sub-invocations, so it does not constrain what code the router subsequently invokes. [6](#0-5) 

The router interprets the payload as registries of attacker-selectable `Address` values and packed operations, resolves each swap's `pool`, `token_in`, and `token_out` from those registries, and dispatches the selected venue. [7](#0-6) [8](#0-7)  Venue adapters then call the payload-selected `pool` address directly, for example through `get_reserves`/`swap`, rather than checking an allowlist of known pool contracts. [9](#0-8) [10](#0-9) 

This is the contract-code analogue of argument injection: untrusted input supplies an address that is used as executable code. A rogue venue can request a token transfer from the transaction signer while executing below the caller's root authorization; an honest simulation exposes that transfer as an additional authorization child, and the host executes it when the caller signs the poisoned tree. [11](#0-10) [12](#0-11) 

### Impact Explanation
The attacker can steal arbitrary token balances from the caller's wallet, including assets unrelated to the lending position. The protocol's measured input/output checks and final account-health checks do not bound that loss because the malicious transfer targets the caller rather than controller-held swap input. The documented threat model confirms that the loss is the caller's wallet and is not bounded by the route minimum or the final risk gate. [13](#0-12) 

The exploit preserves a fair-looking protocol result: the rogue hop can return enough output for the strategy to satisfy minimum-output, measured-receipt, and solvency checks while performing an additional wallet-token transfer inside the signed authorization tree. [14](#0-13) [15](#0-14) 

### Likelihood Explanation
Likelihood is Medium. An attacker can unilaterally deploy the malicious venue and craft the route, but cannot directly target another account because the controller requires the caller to be the account owner or an authorized delegate. [16](#0-15)  Exploitation therefore depends on convincing a user or integrating client to submit and sign a poisoned route.

That prerequisite is realistic because route bytes are opaque and intended to be produced off-chain. The malicious transfer appears only in the simulated authorization tree, not as a self-evident field in the lending call; a client that signs simulation output without comparing the tree to the expected single input-transfer authorization enables the theft. [17](#0-16)  The checked-in exploit demonstrates that both recording mode and enforcing mode attach the rogue transfer to the caller's `swap_collateral` authorization and execute it when signed. [11](#0-10) [18](#0-17) 

### Recommendation
Do not allow opaque route bytes to select arbitrary executable pool addresses. Enforce a governance-managed venue/pool allowlist or a registry of audited pool implementations before dispatching any swap hop. The allowlist should cover every opcode that can call a pool, including Aquarius, Soroswap, Phoenix, Sushi, Comet, burn, and mint routes.

Independently, controller and client integrations should require the signed authorization tree to match the expected shape. For a controller strategy, reject any caller authorization child other than the exact intended input transfer; for a direct router swap, the expected child is only `token_in.transfer(caller, router, total_in)`. Requiring this invariant at the protocol boundary is preferable because wallet inspection alone should not be the only defense against executable route payloads.

### Proof of Concept
1. The attacker deploys a contract exposing the pool ABI expected by a selected venue. Its `swap` function calls `wallet_token.transfer(victim, attacker, victim_balance)` before returning a plausible swap result.
2. The attacker constructs `swap` bytes whose `assets` registry contains the rogue contract as the hop `pool`, with ordinary listed `token_in` and `token_out` addresses and a fair `min_out`.
3. The victim invokes `swap_collateral(caller=victim, account_id=victim_account, current=USDC_market, amount=5_000_USDC, new=ETH_market, swap=poisoned_route)`.
4. The controller authorizes only the expected input transfer and invokes `router.execute_strategy(controller, amount, poisoned_route)`. [19](#0-18) 
5. The router resolves `pool` from route-controlled `assets` and invokes the attacker's contract. [8](#0-7) 
6. During simulation, the rogue contract's `transfer(victim, attacker, victim_balance)` is attached beneath the victim's `swap_collateral` authorization entry. [20](#0-19) 
7. If the victim signs that simulated tree, enforcing mode executes the extra transfer; the repository's test drains `77_770_000_000` units of an unrelated wallet token while still crediting the expected swapped collateral. [12](#0-11)

#[test]
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
