### Title
Native-token overpayment in `EvmHost` dispatch functions reverts because the contract cannot receive the Uniswap refund - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept native-token payment and swap the full `msg.value` through `swapETHForExactTokens`, relying on the Uniswap V2 router to refund any unspent ETH. `EvmHost` has no `receive()` or `fallback()` function, so the router's low-level ETH refund back to `EvmHost` fails, reverting the entire transaction whenever a caller sends more native token than the exact fee requires.

### Finding Description
All three payable entry points forward the entire `msg.value` to `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`: [1](#0-0) [2](#0-1) [3](#0-2) 

Uniswap V2's `swapETHForExactTokens` computes the exact input needed and, if `msg.value` exceeds that amount, refunds the difference to `msg.sender` of the router call using a low-level ETH transfer that requires success. Because the router is called with `{value: msg.value}` from within `EvmHost`, the router's `msg.sender` is `EvmHost` itself — the refund is sent back to the `EvmHost` contract, not to the original caller. `EvmHost.sol` defines no `receive()` or `fallback()` function anywhere in the contract, confirmed by an exhaustive search of the file, so this refund transfer fails and the router call reverts, unwinding the whole `dispatch`/`fundRequest` transaction.

This is the inverse of the reported bug class but with a stronger consequence: rather than merely failing to refund excess ETH to the user (fund-return bug), the protocol cannot accept overpayment at all — any caller who does not supply the *exact* wei amount required by the swap will have their transaction revert. The project's own documentation and SDK code explicitly encourage sending a buffer above the estimated fee (e.g. a documented 2x buffer in the LayerZero endpoint adapter, "Excess native is refunded by the uniswap router"), which assumes the refund path works: [4](#0-3) 

### Impact Explanation
Any unprivileged app or relayer dispatching a POST/GET request or funding a relayer fee via native token — the exact reachable path highlighted in the scope (EvmHost dispatch and delivery) — will have its message dispatch transaction revert whenever it supplies more native token than the exact fee, which is the normal/recommended usage pattern given price volatility and documented buffering guidance. This breaks the "native token payment" delivery route for POST/GET dispatch and relayer-fee funding across every EVM deployment of `EvmHost`, constituting a route that is unable to deliver messages under realistic and even encouraged usage conditions.

### Likelihood Explanation
High. Any slippage between the client-side fee estimate and the actual Uniswap price, or any deliberate buffer (as recommended in the SDK/docs), triggers the revert. Because `EvmHost` never implements `receive()`/`fallback()`, there is no configuration or caller behavior that avoids the failure except sending the wei-exact required amount, which is impractical to compute on-chain ahead of the swap execution.

### Recommendation
Add a `receive() external payable {}` (or equivalent) to `EvmHost` so the Uniswap router's overpayment refund can land on the contract, and then explicitly forward that leftover ETH back to `_msgSender()` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, mirroring the excess-refund pattern already implemented in `IntentGatewayV2.placeOrder`/`fillOrder` and `ExtrinsicIntents._fillCrossChain`: [5](#0-4) [6](#0-5) 

### Proof of Concept
1. Caller estimates the fee client-side and calls `EvmHost.dispatch(DispatchPost)` (or `dispatch(DispatchGet)`/`fundRequest`) with `msg.value` set slightly above the exact fee (a normal buffer, as documented).
2. Inside `dispatch`, `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` executes; the router computes `amounts[0] < msg.value` and attempts to refund `msg.value - amounts[0]` ETH to `msg.sender`, which is `EvmHost`.
3. `EvmHost` has no `receive()`/`fallback()`, so the refund transfer fails inside the router, causing `swapETHForExactTokens` to revert.
4. The entire `dispatch` call reverts, and the message is never dispatched — despite the caller supplying sufficient (indeed more than sufficient) funds.
