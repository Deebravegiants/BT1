### Title
Webhook `shop-domain` header is trusted but not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's HMAC against only the raw request body, then unconditionally forwards the attacker-controlled `shop-domain` header to the merchant's registered handler as the identity of the shop that triggered the event. The `shop` value that host applications rely on to scope tenant data is never bound by the signature that is supposed to authenticate the request.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The HMAC validator computes/verifies the signature strictly against that `to_signable_string` value: [2](#0-1) 

But `Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which plays no part in the signed payload: [3](#0-2) 

`Registry.process` validates the HMAC and then, without any further check tying `request.shop` to the signed body, builds a `WebhookMetadata` object carrying that unverified shop value and dispatches it to the app's handler: [4](#0-3) 

`WebhookMetadata.shop` is documented as the field the handler is meant to use as the tenant identifier for the event: [5](#0-4) 

This breaks the identity binding the report describes: the equality that should hold is `shop_authenticated_by_hmac == shop_delivered_to_handler`, but in this gem `shop_authenticated_by_hmac` is undefined (the signature covers only the body) while `shop_delivered_to_handler` is taken verbatim from an attacker-controllable header. Any party who can produce one *valid* HMAC/body pair for the app's `api_secret_key`—for example the legitimate holder of their own shop's genuine webhook payloads, or anyone who can replay/observe a real webhook delivery from Shopify for shop A—can resend the exact same signed body to the app's webhook endpoint while substituting `shop-domain: shop-b.myshopify.com` in the headers. `HmacValidator.validate` still returns `true` because it never inspected the header, and the handler executes with `data.shop == "shop-b.myshopify.com"` even though the payload was never associated with shop B by Shopify.

### Impact Explanation
Because the `shop` identifier delivered to the app's webhook handler is not cryptographically bound to the signature, an attacker can make the handler process (or attribute) webhook events under an arbitrary tenant identity. Any host application that uses `WebhookMetadata#shop` (as documented/intended by this gem) to select the session/access token or scope database writes for a merchant is exposed to cross-tenant data confusion/injection driven entirely by unauthenticated header content. This matches the "Critical – cross-tenant access" category: the gem itself hands the app a spoofable tenant identifier under the guise of an HMAC-verified request.

### Likelihood Explanation
Likelihood is moderate-to-high for any endpoint that terminates the raw webhook request through this gem: the header is fully attacker-controlled and requires no secret to modify (only a previously-observed valid signed body, which many real-world integrations log, replay in tests, or otherwise leak/observe legitimately). No access token, `api_secret_key`, or privileged account is required — only network access to the app's public webhook endpoint and knowledge of one valid signed body/HMAC pair, which is standard telemetry an attacker with even a single merchant relationship or webhook log access would have.

### Recommendation
Include the shop domain (and ideally other identity-bearing headers such as topic/api-version) inside the HMAC-signed material, or otherwise cryptographically bind them, e.g. by having `Request#to_signable_string` incorporate a canonical representation of `shop-domain` alongside the raw body, and rejecting requests where a signed shop claim doesn't match the header. At minimum, document that `WebhookMetadata#shop` is unauthenticated and must not be used to select a per-tenant session/credential without independent verification (e.g., confirming an existing, previously-established session for that shop).

### Proof of Concept
1. App owner captures one legitimate webhook delivery for `shop-a.myshopify.com`: raw body `B`, and its valid `x-shopify-hmac-sha256` header `H` (computed by Shopify over `B` using the app's `api_secret_key`).
2. Attacker (or the same party) sends a new HTTP POST to the app's webhook endpoint with body `B` unchanged, header `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `to_signable_string` is still `B`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` and compares to `H` — validation succeeds because `shop-domain` was never part of the signed data: [4](#0-3) 
5. The handler is invoked with `WebhookMetadata(shop: "shop-b.myshopify.com", ...)`, even though Shopify never signed a webhook for shop B with this body — demonstrating the identity-binding break.
