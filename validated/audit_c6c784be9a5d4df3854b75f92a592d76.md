### Title
Webhook `shop` domain is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity using only an HMAC computed over the raw request body, then trusts the separate, unauthenticated `shop-domain` header as the tenant identity passed to the app's handler.

### Finding Description
`Registry.process` calls `Utils::HmacValidator.validate(request)` before dispatching to the handler: [1](#0-0) . `HmacValidator.validate_signature` computes the signature over `verifiable_query.to_signable_string` [2](#0-1) , and for a `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — the shop identity is never part of what's signed: [3](#0-2) . Meanwhile `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header with no cryptographic binding to the HMAC-verified body: [4](#0-3) . That unauthenticated `shop` value is then forwarded as-is into `WebhookMetadata` and delivered to the app's handler as the authoritative tenant identifier: [5](#0-4) , [6](#0-5) . The gem's own documentation explicitly instructs host apps to treat `data.shop` as the verified store identity after `Registry.process` "will verify the request did indeed come from Shopify": [7](#0-6) , [8](#0-7) .

The identity binding broken here is: `shop-domain header value == shop that produced the HMAC-signed body`. Because these two values are never cross-checked, an attacker who legitimately owns Shop A (and thus receives a genuinely-HMAC-valid webhook body/signature pair for their own store, without needing `api_secret_key`) can replay that exact `raw_body` + `hmac` while substituting an arbitrary `shop-domain` header (e.g., a victim tenant, Shop B). `HmacValidator.validate` still passes because it only checks the body, and `Registry.process` then invokes the handler claiming the payload came from Shop B.

### Impact Explanation
This is a cross-tenant identity-spoofing primitive reachable by any unprivileged internet user who can install the app on their own store (a normal, unprivileged action) and capture one legitimate webhook. If the host application (following the gem's documented pattern of trusting `data.shop`) uses this field to select which tenant's session/database record to update, log, or act upon, the attacker can inject data attributed to a victim shop, corrupting cross-tenant records or triggering shop-scoped side effects (e.g., app-uninstalled/redact handling, data synchronization, billing state) under a victim's identity — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is realistic: the attacker only needs to be a legitimate merchant of their own store where the target app is installed (no leaked secrets, no access token, no privileged account, no TLS interception required) — replay of a captured legitimate webhook body/HMAC pair with a modified header is trivial once the raw body and signature are observed (e.g., via the app's own logs, a debugging proxy the attacker controls on their own traffic, or by simply reading their own webhook deliveries in the Shopify partner/webhook logs).

### Recommendation
Include the shop domain (and ideally the topic, webhook id, and timestamp) as part of the data covered by the HMAC verification, or otherwise cryptographically bind the `shop-domain` header to the signed body before trusting it (e.g., verify the header-derived shop against the tenant that owns the specific `webhook_id` via a Shopify API lookup, rather than trusting the header verbatim). At minimum, update `Utils::HmacValidator`/`Webhooks::Request` so `to_signable_string` incorporates the shop domain header, and document that host apps must never trust `data.shop` as an authenticated value on its own.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`) to their own registered endpoint, capturing the raw request body `B` and header `x-shopify-hmac-sha256: H` (valid because Shopify signs `B` with the app's shared secret).
2. Attacker sends a forged HTTP request to the app's public webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which only checks `HMAC(secret, B) == H` — this passes since `B` and `H` are unchanged [9](#0-8) .
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the body content actually originated from the attacker's own shop [5](#0-4) , allowing the attacker to inject attacker-controlled webhook data attributed to the victim tenant.
