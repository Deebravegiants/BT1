### Title
Webhook `shop-domain` identity is trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from an HTTP header, but the HMAC signature it validates covers only the raw request body, not the `shop-domain` header. `Registry.process` trusts this unauthenticated header value to build `WebhookMetadata` handed to the app's handler, breaking the binding "bytes verified == bytes the shop identity is derived from," analogous to the EIP-4494 report's core theme of an identity/nonce field not being covered by the cryptographic check that is supposed to authenticate it.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop` is read straight from the (attacker-controllable, at the HTTP layer) `shopify-shop-domain` / `x-shopify-shop-domain` header, with no relation to the signed payload: [2](#0-1) 

`HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (the body) and secure-compares it to the `hmac` header: [3](#0-2) 

`Registry.process` gates on this HMAC check, then immediately trusts `request.shop` (the unauthenticated header) to construct the metadata passed to the app-provided handler: [4](#0-3) 

The equality this breaks: `shop used for tenant routing == shop covered by the verified HMAC` is false — the HMAC only proves `body == HMAC⁻¹(secret, hmac)`, it does not prove anything about which shop the header claims to be from. Since the app's `client_secret`/webhook secret is shared across **all** shops of the app (it is per-app, not per-shop), any two genuine webhook deliveries for the same app share the same key. A merchant who has installed the app on their own (unprivileged) store legitimately receives real webhook deliveries (body + valid HMAC) addressed to their own shop domain. Because the header is not part of the signed content, that same valid `(body, hmac)` pair remains "HMAC-valid" if replayed to the app's webhook endpoint with the `shop-domain` header swapped to a different, arbitrary shop (including one the attacker does not control), since the check in `HmacValidator.validate_signature` recomputes and compares only against the body.

### Impact Explanation
This satisfies the "cross-tenant access" Critical-impact category from the rules: the app's webhook handler is invoked believing it is processing data `for shop B`, while the HMAC only certifies "sent using this app's secret," not "for shop B." A handler implementation that looks up per-shop state (installation record, offline access token, feature flags, redaction jobs, etc.) keyed by `WebhookMetadata#shop` can be made to process an attacker-supplied `(topic, body)` combination under a victim shop's identity, or vice versa — attacker's own legitimate webhook content gets attributed to a different, arbitrary `shop` value entirely of the attacker's choosing, none of which is bound by cryptography.

### Likelihood Explanation
Any merchant who has installed the app (unprivileged relative to other tenants, and requiring no access token, `api_secret_key`, or credential leakage) receives real webhooks for their own shop and can capture a legitimate `(raw_body, hmac)` pair via a simple network capture of their own inbound webhook traffic — no interception of Shopify's traffic or the app's secret is needed. They can then re-POST that exact body/HMAC to the same public webhook endpoint URL with a forged `shop-domain` header. This requires no privileged account, no TLS interception, and no knowledge of `api_secret_key`, satisfying the in-scope, unprivileged-internet-user threat model.

### Recommendation
Bind the trusted identity fields into the signed content, or otherwise verify them independently of the raw body:
- Include `shop-domain`, `topic`, and `webhook-id` in the value that is HMAC-verified (this would require a change in what the gem hashes, consistent in spirit with Shopify's server-side signing, or the gem should document/enforce that these headers must never be trusted for authorization decisions without additional verification such as a live shop lookup).
- At minimum, cross-check that the shop in `shop-domain` matches an installation/session already known to be authenticated (e.g., an existing offline session for that shop) before acting on the payload, rather than trusting the header value outright inside `WebhookMetadata`.
- Document clearly in `docs/usage/webhooks.md` that `WebhookMetadata#shop` is not covered by the HMAC and must not be used as the sole tenant-selection key without additional binding.

### Proof of Concept
1. Merchant "Attacker Shop" installs the app; a legitimate webhook is delivered:
   - Headers: `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-topic: orders/create`, `shopify-hmac-sha256: <valid HMAC of body>`
   - Body: `{"id": 1, ...}`
2. Attacker records `raw_body` and the valid `hmac` value (trivial — it is delivered to their own server).
3. Attacker re-sends an HTTP POST to the same app's public webhook endpoint, keeping `raw_body` and `hmac` unchanged, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this successfully (all three required headers present) [5](#0-4) .
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only and succeeds (the body wasn't changed) [6](#0-5) .
6. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` even though the payload never touched Shopify's systems for that shop [7](#0-6) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
