### Title
Webhook `shop-domain` (and `topic`/`webhook_id`/`api_version`) header is trusted but not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC over the raw request body, then unconditionally trusts the `shop-domain`, `topic`, `webhook-id`, and `api-version` HTTP headers when building the `WebhookMetadata` passed to the app's handler. Because these headers are not part of the signed material, a party who can obtain any one valid `(raw_body, hmac)` pair signed with the app's `api_secret_key` can replay it against the endpoint with an arbitrary, attacker-chosen `shop-domain` header, and the library will report it as an authenticated webhook "from" that (attacker-chosen) shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are read straight from HTTP headers and are never included in the signable string: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate`, which calls `to_signable_string` (i.e. body-only) and compares against `request.hmac`: [3](#0-2) 

After that single check passes, `Registry.process` builds `WebhookMetadata` directly from the unauthenticated headers and dispatches it to the app's handler: [4](#0-3) [5](#0-4) 

The identity binding that should hold is:
`hmac == HMAC(api_secret_key, raw_body ++ shop ++ topic ++ webhook_id)`

but the actual implementation only enforces:
`hmac == HMAC(api_secret_key, raw_body)`

Because `api_secret_key` is a single shared secret for the whole app (not per-shop), any merchant who has installed the app can legitimately trigger genuine Shopify webhooks for their own shop and thus obtain valid `(raw_body, hmac)` pairs. That merchant (an "unprivileged" caller with respect to any other tenant of the same app) can then POST the identical `raw_body`/`hmac` to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header with a victim shop's domain. The HMAC check still passes — it never inspected the header — so the library hands the app a `WebhookMetadata` claiming the payload originated from the victim shop.

This is the exact bug class described in the report ("a field acted on but not covered by the HMAC"): the endpoint verifies the bytes of the body, but the shop-identity field consumed downstream is disjoint from what was actually verified.

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata#shop` to select which merchant's session/access token/data to act on (the documented and expected usage pattern per `docs/usage/webhooks.md`) can be tricked into processing another merchant's webhook body under a spoofed shop identity, or into replaying a legitimate merchant's own webhook body against a different tenant's records. This crosses a tenant boundary using only capabilities available to an ordinary (if malicious) merchant who installed the app — no access token, `api_secret_key`, or elevated privilege is required beyond normal app installation. This satisfies the "cross-tenant access" criterion for a Critical/High-impact finding, since downstream handlers (order sync, inventory writes, GDPR data deletion webhooks, etc.) commonly key off `data.shop` to decide which tenant's records to mutate.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on an attacker-controlled shop (or otherwise obtaining one valid webhook delivery with its raw body/HMAC, e.g. from network capture or a shop the attacker controls), and (2) replaying that exact raw body to the app's public webhook HTTP endpoint with a forged `x-shopify-shop-domain` header. No cryptographic secret needs to be broken. This is straightforward for any developer/tester with basic HTTP tooling and is the standard "signature doesn't cover context" replay pattern.

### Recommendation
Bind the identity fields into the verified material instead of trusting bare headers:
- Extend `VerifiableQuery`/`Request#to_signable_string` (or add a secondary check in `Registry.process`) so that `shop`, `topic`, and `webhook_id` are included in what is HMAC-verified, or
- Cross-check `request.shop` against an expected/registered shop for the delivery (e.g., match against the shop that owns the active session used to register that specific webhook subscription) before dispatching to the handler, and
- Document prominently that `WebhookMetadata#shop`/`#topic` are currently unauthenticated and must not be trusted for tenant selection without additional verification.

### Proof of Concept
1. Install the target Shopify app on attacker-owned shop `attacker.myshopify.com`. Trigger a genuine webhook delivery (e.g. `orders/create`); capture the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header `H` — this pair is valid because `H = Base64(HMAC_SHA256(api_secret_key, B))`.
2. Replay the request to the same app's webhook endpoint, keeping body `B` and header `H` unchanged, but set:
   ```
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: H
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which recomputes the HMAC over `B` only — it succeeds because `B`/`H` are unchanged: [6](#0-5) 
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and, per the documented usage pattern, will look up/act on `victim-shop`'s session and data using attacker-controlled body content `B` — a cross-tenant data-integrity/confusion attack achieved without any secret material beyond normal app installation.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
