### Title
Webhook shop identity is not bound by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authentic for a given shop once `Utils::HmacValidator.validate(request)` succeeds, but the HMAC only ever covers the raw request body — never the `shop-domain` header that the handler is told to trust as the tenant identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop` is read straight from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header: [2](#0-1) 

`Registry.process` validates only the body-derived HMAC, then forwards `request.shop` (the unauthenticated header value) into the handler as the tenant identity: [3](#0-2) 

`Utils::HmacValidator.validate` computes and compares the HMAC purely against `verifiable_query.to_signable_string`, which for webhooks is the raw body only: [4](#0-3) 

The identity binding the gem implicitly promises to the host app is: `shop that HMAC authenticates == shop the handler acts on`. In reality: `shop that HMAC authenticates` = "whoever holds `api_secret_key`, for this exact body bytes", while `shop the handler acts on` = "whatever string appears in an unsigned header". These are not equal. Since `api_secret_key` is the app's single client secret shared across every merchant that installs the app (not a per-shop secret), any unprivileged internet user who can trigger even one legitimate webhook delivery for their own shop (e.g., install the app on their own free/dev store) obtains a raw body + valid HMAC pair. They can then replay that exact body with a valid HMAC and an arbitrary `shop-domain`/`x-shopify-shop-domain` header pointing at a victim shop. `HmacValidator.validate` still passes (it never looks at the header), and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce: an attacker-controlled webhook body is accepted as authentic for a shop the attacker does not control. Any host application that keys its handler logic off `WebhookMetadata#shop` (e.g. to look up the stored session/access token for that shop, or to perform per-shop data operations like `shop/redact`, `app/uninstalled` cleanup, inventory/order sync) can be made to act as if the event originated from a victim shop. This is a cross-tenant access vulnerability rooted entirely in this gem's own verification logic (`HmacValidator` + `Webhooks::Request`), not a misuse of a documented contract by the host app — the gem's own `process` method presents `request.shop` as verified data once `HmacValidator.validate` passes.

### Likelihood Explanation
Exploitability only requires the ability to obtain one legitimate webhook delivery, which any developer can do for free by installing the target app on their own development/trial store and capturing the HTTP request Shopify sends. No access to `api_secret_key`, tokens, or the victim's credentials is required — the attacker directly crafts the replay request to the app's public webhook endpoint.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the signed payload actually verified, e.g. include the `shop-domain`, `topic`, and `webhook-id` headers in the HMAC signable string (or verify them against a per-shop record established during OAuth, such as confirming a session/access token already exists for that shop) before trusting `request.shop` in `WebhookMetadata`. At minimum, document and enforce that host apps must cross-check `request.shop` against their own known merchant list rather than trusting it as authenticated purely because `HmacValidator.validate` returned true.

### Proof of Concept
1. Install the app (or otherwise receive a legitimate webhook) on attacker-controlled shop `attacker.myshopify.com`; capture the raw POST body `B` and the resulting `x-shopify-hmac-sha256` header value `H` (valid because `H = HMAC-SHA256(api_secret_key, B)`, and `api_secret_key` is shared across all installs of the app).
2. Send a new HTTP POST to the app's webhook endpoint with the same body `B`, the same `hmac-sha256` header `H`, the same `topic` header, but `shop-domain` header set to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts it; `Utils::HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, B)` and finds it equals `H`, so validation passes (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` invokes the app's handler with `WebhookMetadata#shop == "victim.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the request never touched `victim.myshopify.com`'s data or credentials — demonstrating the shop identity is unauthenticated relative to the HMAC that supposedly proves the request's legitimacy.
