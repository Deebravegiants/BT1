### Title
Stale `approveUnlimited` allowance in `LifiExternalAction.callRouter` lets router calldata pull more than a transaction's own `inputAmount`, stealing stranded balances - (contracts/external-actions/swaps/LifiExternalAction.sol)

### Summary
`LifiExternalAction.callRouter` grants `router` an unlimited, persistent `IERC20` allowance over the contract's own balance via `approveUnlimited`, then executes attacker-supplied `externalActionMetadata` calldata against `router`. `ExternalActionSwap.swap` measures `swappedAmount` purely from the *output*-token balance delta, never verifying that the router only consumed `inputAmount` (i.e. `-deltaAmounts[0]`) of the input token, so any tokens already sitting in the contract (stranded from prior transactions) can be swept into the same swap and credited to the current caller.

### Finding Description
The claimed equality is:
`-deltaAmountChanges[0]` (input tokens sent to `LifiExternalAction` for this tx by `Hinkal._externalTransact`) `==` tokens actually pulled from `LifiExternalAction` by `router` in this tx.

Trace:
- `Hinkal._externalTransact` computes `deltaAmountChanges[i]` from the proof-constrained `circomData.amountChanges`, and for negative deltas transfers exactly `uint256(-deltaAmountChanges[i])` of `inputToken` to `LifiExternalAction` before calling `runAction` [1](#0-0) .
- `ExternalActionSwap.swap` derives `inputAmount = uint256(-deltaAmounts[0])` and calls `callRouter(inputToken, inputAmount, outputToken, circomData.externalActionData.externalActionMetadata)` [2](#0-1) .
- `LifiExternalAction.callRouter` calls `approveUnlimited(inputToken, router)`, which only refreshes the allowance to `type(uint256).max` when the current allowance drops below `type(uint256).max/2` — it does **not** reset to `0` after the swap, so a large residual allowance survives across transactions [3](#0-2) . It then executes `router.call(externalActionMetadata)` with fully attacker-controlled calldata [4](#0-3) .
- `swappedAmount` is computed solely as `getERC20OrETHBalance(outputToken)` before/after — there is no corresponding check on how much `inputToken` balance the router actually consumed [5](#0-4) .
- Back in `swap`, this unchecked `swappedAmount` is used to compute fees and `amountToSendToHinkal`, which is transferred directly to `msg.sender` [6](#0-5) .

Root cause: The contract's `inputAmount` parameter is never used to bound what the router calldata actually withdraws. It is only used to compute fees/expected proceeds after the fact; the router call itself is unconstrained arbitrary calldata against a pre-approved `type(uint256).max` allowance. If `LifiExternalAction` already holds a stranded `inputToken` balance (e.g., left over from a previous transaction whose `router` call didn't consume the full transferred amount, or dust left from prior actions), an attacker can craft `externalActionMetadata` for the *same* `inputToken`/`router` pair that instructs `router` to pull `inputAmount + strandedBalance` via `transferFrom`, swap it all, and route the output back to `LifiExternalAction`. `swappedAmount` then reflects the inflated output, and the attacker's `transact` walks away with proceeds from tokens that were never `this transaction's -deltaAmountChanges[0]`.

None of the existing guards stop this: `performHinkalChecks`/`verifyProof` only constrain the proof's public commitments to the attacker's own UTXOs and the declared `amountChanges`/`deltaAmountChanges` — they say nothing about what the external router actually pulls once given unlimited approval. `Hinkal.sol`'s slippage check (`balanceDif >= circomData.slippageValues[i]`) is a floor, not a ceiling, so an inflated output balance change trivially satisfies it. `onlyAllowedRecipient`/`nonReentrant` restrict caller identity/reentrancy, not the amount pulled by `router`.

### Impact Explanation
An attacker who observes (or engineers) a state where `LifiExternalAction` holds a stranded `inputToken` balance can, in a single `transact` call, direct the pre-approved `router` to pull that stranded balance in addition to their own legitimately-deposited `inputAmount`, swap it, and receive the combined output. This is direct theft of other depositors'/protocol's parked token balance sitting in `LifiExternalAction`, matching the Critical category ("direct theft of shielded or in-flight user funds"). It is repeatable every time a residual balance accumulates in the action contract and the attacker holds an unlimited stale allowance for that `inputToken`/`router` pair.

### Likelihood Explanation
Preconditions: (1) `LifiExternalAction` must hold a non-zero stranded balance of `inputToken` (a state reachable via the stranded-balance conditions referenced by findings #1-5, not fabricated by the attacker in isolation); (2) the `inputToken`/`router` allowance must already be at/near `type(uint256).max` from a prior legitimate swap of that pair, which is the normal steady state once any user has swapped that token through this router. Attacker cost is a single ordinary `transact` call with self-crafted `externalActionMetadata` — fully within an unprivileged attacker's capability, since `externalActionMetadata` is attacker-supplied calldata targeting the fixed, known `router` address. No special role or victim key is required.

### Recommendation
Do not rely solely on output-token balance delta to determine `swappedAmount`. Additionally track and enforce the input-token balance delta consumed by `router` against the tx's own `inputAmount` (e.g., `require(balanceBefore(inputToken) - balanceAfter(inputToken) <= inputAmount)`), and/or avoid persistent unlimited approvals — approve exactly `inputAmount` before the router call and reset the allowance to `0` immediately after, regardless of whether it was fully consumed.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `LifiExternalAction` (with a mock `router`), a mock ERC20 `inputToken`/`outputToken`.
2. Simulate the "stranded balance" precondition by directly transferring an extra `strandedAmount` of `inputToken` to `LifiExternalAction` (representing residual funds from a prior transaction/finding #1-5), and have `LifiExternalAction` already hold an allowance of `type(uint256).max` for `router` on `inputToken` (simulate a prior legitimate swap having called `approveUnlimited`).
3. Craft a legitimate `transact` call with `deltaAmountChanges[0] = -inputAmount` (attacker's own funds), and set `externalActionMetadata` to call the mock `router`'s `transferFrom(LifiExternalAction, router, inputAmount + strandedAmount)` followed by minting/sending back `outputToken` proportional to the *pulled* amount to `LifiExternalAction`.
4. Assert: `IERC20(inputToken).balanceOf(router)` increased by `inputAmount + strandedAmount`, i.e., strictly greater than `inputAmount = uint256(-deltaAmountChanges[0])` — breaking the claimed equality.
5. Assert `swappedAmount` (and the resulting `amountToSendToHinkal` sent to `msg.sender`) reflects the inflated pulled amount, exceeding what a swap of only `inputAmount` would have produced, confirming the attacker received proceeds derived from the stranded balance rather than solely their own deposited funds.

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
