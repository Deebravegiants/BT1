Found a valid analog: `on_timeout` in the hyper-fungible-token pallet re-reads the *current* `Precisions` value to compute the refund, instead of using the decimals that were in effect when the transfer was originally dispatched by `send`.

### Title
Timeout refunds and inbound mints use live `Precisions` instead of the value cached at dispatch time, letting a governance precision update corrupt in-flight refund/mint amounts - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`pallet_hyper_fungible_token::send` reads `Precisions::<T>::get(asset_id, destination)` at dispatch time to convert the local amount into the ERC20-denominated amount embedded in the outgoing `Message` [1](#0-0) . That ERC20 amount is committed into the cross-chain message and cannot change afterward. However, `on_timeout` and `on_accept` do not use the precision that was active when the message was created — they call `Precisions::<T>::get(local_asset_id, dest)`/`source` again at *handling* time [2](#0-1) [3](#0-2) . If `update_token` changes `Precisions` for that `(asset_id, chain)` pair while the message is still in flight (pending delivery or pending timeout), the refund/mint amount is computed with the wrong decimals relative to the amount that was actually escrowed/burned.

### Finding Description
This is the exact bug class from the report: a value (decimals/precision) used to convert an amount is cached nowhere and can be updated by governance between the time a critical calculation is committed and the time it is later relied upon to reconstruct that same amount. In the original report, `CurrencyController.decimalCaches` could be updated after `marketTerminationPrices` were fixed, corrupting settlement math. Here, `send()` fixes the ERC20 amount using `erc_decimals` at dispatch time [4](#0-3) , but `on_timeout` (refund of the locally-escrowed/burned amount) and `on_accept` (minting for inbound messages) recompute the local amount by reading `Precisions` fresh, with no way to know what precision was in effect when the counterpart amount was created [5](#0-4) . `update_token` is unauthenticated with respect to in-flight messages — it has no check for pending sends/timeouts and applies immediately via `T::CreateOrigin` [6](#0-5) .

### Impact Explanation
If governance (or the `CreateOrigin`, which could be root or a council depending on runtime config) updates a token's `Precisions` entry for a chain while a `send()` transfer to that chain is in flight, a subsequent timeout will refund the sender using the *new* decimals against the *old* encoded amount, over- or under crediting the refund relative to what was actually escrowed/burned. Symmetrically, inbound `on_accept` messages already committed by the EVM contract with the old decimals will be misconverted if `Precisions` changes before the message is delivered on the substrate side. Depending on direction, this can mint/refund more tokens than were locked (protocol insolvency / unbacked mint) or fewer (permanent partial loss of user funds) — both are concrete freezing/unbacked-mint conditions.

### Likelihood Explanation
Requires a `Precisions` update (via `update_token`, gated by `T::CreateOrigin`) to race with an in-flight `send()` message to the same `(asset_id, chain)` pair, and normally decimals are stable/rarely changed, so likelihood is not high, but the same governance action that legitimately reconfigures a chain (e.g., re-pointing a token contract, migrating decimals) will silently corrupt any transfer that was mid-flight at that moment — this is a foreseeable operational hazard rather than a contrived attack, matching the client's addressed root cause of the original report (cache precision at commit time, not at use time).

### Recommendation
Cache the `erc_decimals` (and local `decimals`) used at `send()` time inside the request/timeout tracking so `on_timeout` reconstructs the refund using the same conversion factor used to build the outgoing message, rather than re-reading `Precisions` at handling time. Since `on_timeout` only receives the decoded `Message` body and `dest`/`to`, the simplest fix is to encode the erc20 amount alongside a fixed local-amount record keyed by the request commitment (mirroring how `RequestMetadata`/`FeeMetadata` is tracked elsewhere in `pallet-ismp`), or to store a per-message decimals/amount pair keyed by commitment at dispatch and consult that record — never the live `Precisions` map — during timeout handling. For inbound `on_accept`, since the amount is fully determined by the sender's encoding, this direction is less risky but should still be documented as best-effort so operators know not to change `Precisions` for a chain while inbound messages might be in flight, or a versioned/timestamped precision history should be used to look up the value valid at the commitment's dispatch time.

### Proof of Concept
1. Register asset `X` with `Precisions[X][EVM-chain] = 18`.
2. User calls `send()` transferring `amount` of `X` to `EVM-chain`; the pallet burns/escrows `amount` at local decimals and encodes `erc20_amount = convert_to_erc20(amount, 18, local_decimals)` into the dispatched `PostRequest` [7](#0-6) .
3. Before the request is delivered or times out, governance calls `update_token` changing `Precisions[X][EVM-chain]` to `6` [6](#0-5) .
4. The request times out. `on_timeout` decodes the same `Message` (with the amount encoded under the old 18-decimal assumption) but converts it back using the now-6 `Precisions` value [3](#0-2) , producing a refund amount that is off by a factor of `10^12` relative to what was actually escrowed/burned in step 2 — either draining the pallet's escrow account or permanently under-refunding the user.
