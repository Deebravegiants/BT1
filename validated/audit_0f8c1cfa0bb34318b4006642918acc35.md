### Title
Emporium wallet-signature omits `relay` and `feeStructure.feeToken` from the signed payload, allowing fee redirection and token substitution - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.verifyWallet()` authenticates a wallet-owner's off-chain EIP-712 signature (`EMPORIUM_SIGNATURE_TYPEHASH`) before letting `runAction()` invoke `IHinkalWallet(signerAddress).doSendToRelay(...)` to pull ERC20 fees out of the user's `HinkalWallet`. Just like the reported Farcaster bug — where a removal signature omits the `fid` it should be scoped to, letting it be replayed against a different `fid` — the Emporium signature omits the `relay` address and the `feeStructure.feeToken`, letting whoever submits the transaction pick both of those fields freely while numerically satisfying the one field that *is* signed (`maxFee`).

### Finding Description
The signed struct is: [1](#0-0) 

and it is hashed/verified as: [2](#0-1) 

`hashedMessage` only commits to `circomData.emporiumMessage`, `_hashEmporiumOps(stack.ops)`, `stack.maxFee`, and `stack.deadline`. It never commits to `circomData.relay` or `circomData.feeStructure.feeToken`. Both fields are attacker-controllable calldata that flow, unconstrained by the signature, into the fee-payment path: [3](#0-2) 

`payRelay()` then calls `sendToRelayFromWallet()`, which invokes the signer's own wallet contract to push tokens to `relay`: [4](#0-3) 

The only numeric guard tying the fee back to the signature is: [5](#0-4) 

`stack.maxFee` is a bare `uint256` with no denomination attached in the signed message — it is only ever compared against `feeStructure.flatFee`, and `feeStructure.feeToken` (which determines what token that number is *denominated in*) is never bound by the signature. Because `verifyWallet()` never revalidates `circomData.relay` or `circomData.feeStructure.feeToken` against anything the signer actually approved, `runAction()`'s caller (an `onlyAllowedRecipient` relay in `Hinkal.sol`'s external-action flow) can reuse a signature/ops pair that a wallet owner produced expecting, e.g., "pay up to 10 units in USDC to relay R1" and instead redirect it to "pay up to 10 units of WBTC to relay R2" — the numeric cap `maxFee` is satisfied, but the actual value extracted from the wallet is entirely different and moved to an attacker-chosen recipient.

This mirrors the report's root cause exactly: a signature is scoped to an action but omits binding a critical contextual identifier (there: `fid`; here: `relay` and `feeToken`), so anyone who obtains that signature can replay it in an unintended context that still passes the narrower checks that are performed.

### Impact Explanation
This breaks the authorization/balance equality that the signature is meant to enforce: "wallet moves at most `maxFee` of the specific token the owner intended, to the relay the owner intended." Because `relay` and `feeToken` are unauthenticated, an executor of `runAction()` can redirect the wallet's `doSendToRelay` call to itself and select any token present in `circomData.erc20TokenAddresses` for the fee, extracting value the signer never approved for that recipient/token — an unauthorized wallet operation and theft of value that should have gone to the intended relay/token, matching the "theft of protocol/relay fees" / "executing calls or moving assets ... never authorised" High-severity category.

### Likelihood Explanation
Exploitation only requires observing/obtaining a validly-signed `(emporiumMessage, ops, maxFee, deadline, v, r, s)` tuple and being (or colluding with) the `onlyAllowedRecipient` caller that drives `runAction()`. Since `emporiumMessage` is single-use (`usedMessages`) but `relay`/`feeToken` are not part of what's consumed, a single legitimate signature grants a one-shot but fully attacker-steerable fee redirection.

### Recommendation
Include `relay` and `feeStructure.feeToken` (and ideally the full `feeStructure`) inside `EMPORIUM_SIGNATURE_TYPEHASH` so the signer explicitly authorizes both the recipient and the denomination of any fee taken from their wallet, closing the same class of gap identified in the external report.

### Proof of Concept
1. Alice (a `HinkalWallet` owner) signs an `EmporiumSignature` off-chain intending `relay = R1`, `feeToken = USDC`, `maxFee = 10`.
2. A relay operator observes this signature/ops pair before it's submitted (or is itself the party submitting it) and calls `Hinkal`'s external-action entrypoint with `circomData.relay = R2` (attacker) and `circomData.feeStructure = {feeToken: WBTC, flatFee: 10, ...}`, keeping `ops`, `emporiumMessage`, `maxFee`, `deadline` identical.
3. `verifyWallet()` recomputes `hashedMessage` from `emporiumMessage`, `ops`, `maxFee`, `deadline` only — it matches Alice's original signature, so verification passes; `flatFee (10) <= maxFee (10)` also passes.
4. `payRelayFees()` → `payRelay()` → `sendToRelayFromWallet()` calls `IHinkalWallet(Alice's wallet).doSendToRelay(R2, 10, WBTC)`, sending 10 units of WBTC from Alice's wallet to the attacker's relay address `R2` — a token and recipient Alice never authorized.

```text
    function payRelayFees(
        CircomData calldata circomData,
        address signerAddress,
        int256[] calldata deltaAmountChanges
    ) internal {
        FeeStructure calldata feeStructure = circomData.feeStructure;

        bool foundToken = false;

        for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            // tokens deposited into Emporium are not charged
            if (deltaAmountChanges[i] >= 0) {
                continue;
            }

            address erc20TokenAddress = circomData.erc20TokenAddresses[i];
            bool isFeeToken = erc20TokenAddress == feeStructure.feeToken;

            if (isFeeToken) {
                foundToken = true;
            }

            uint256 relayFee = 0;
            uint256 flatFee = isFeeToken ? feeStructure.flatFee : 0;

            if (signerAddress == address(0)) {
                uint256 sumAbs = uint256(-deltaAmountChanges[i]);

                EmporiumStorageVars storage $ = _getEmporiumStorage();
                relayFee = $._hinkalHelper.calculateRelayFee(
                    sumAbs,
                    flatFee,
                    feeStructure.variableRate
                );
            } else {
                relayFee = flatFee;
            }

            payRelay(
                circomData.relay,
                signerAddress,
                relayFee,
                erc20TokenAddress
            );
        }
```

```text
    function verifyWallet(
        EmporiumStack memory stack,
        CircomData calldata circomData
    ) internal {
        EmporiumStorageVars storage $ = _getEmporiumStorage();

        if ($.usedMessages[circomData.emporiumMessage]) {
            revert UsedMessage();
        }

        $.usedMessages[circomData.emporiumMessage] = true;

        if (stack.signerAddress == address(0)) {
            return;
        }

        bytes32 hashedMessage = _hashTypedDataV4(
            keccak256(
                abi.encode(
                    EMPORIUM_SIGNATURE_TYPEHASH,
                    circomData.emporiumMessage,
                    _hashEmporiumOps(stack.ops),
                    stack.maxFee,
                    stack.deadline
                )
            )
        );

        (address recoveredAddress, ECDSA.RecoverError err) = ECDSA.tryRecover(
            hashedMessage,
            stack.v,
            stack.r,
            stack.s
        );
        bool verified = err == ECDSA.RecoverError.NoError &&
            recoveredAddress == stack.signerAddress;
        if (!verified) {
            revert InvalidSignature();
        }

        if (block.timestamp > stack.deadline) {
            revert SignatureExpired();
        }

        if (circomData.feeStructure.flatFee > stack.maxFee) {
            revert FeeExceedsSignedMax();
        }
```
