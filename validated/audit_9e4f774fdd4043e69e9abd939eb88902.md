## Analysis

The reported bug class — a field that is acted upon by the code but not actually covered by the HMAC signature — has a direct analog in this gem's webhook processing.

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop`, `topic`, and `webhook_id` fields are read straight from HTTP headers and are never included in the signed payload: [1](#0-0) 

`ShopifyAPI::Webhooks::Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` — which calls `request.to_signable_string`, i.e. only the raw body — and then, once that check passes, unconditionally trusts `request.shop` and `request.topic` (taken from unauthenticated headers) to dispatch the webhook to the handler: [2](#0-1) 

`Utils::HmacValidator.validate_signature` computes the digest purely from `verifiable_query.to_signable_string` against the app's single, shop-independent `Context.api_secret_key`: [3](#0-2) 

Because the same `client_secret`/`api_secret_key` is used to sign webhooks for every shop that installs the app, and the signature covers only the JSON body bytes, any body+HMAC pair legitimately obtained from a real webhook delivery (e.g., one triggered by installing the app on an attacker-controlled store) remains a valid signature no matter what `shop-domain`/`topic`/`webhook-id` headers are attached to it. An attacker can therefore replay that body with the `X-Shopify-Shop-Domain` header changed to a victim shop, and `HmacValidator.validate` still returns `true`, causing `Registry.process` to invoke the handler with `WebhookMetadata` claiming the (forged) victim shop as the origin.

### Title
Webhook `shop`/`topic` identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw body. The `shop`, `topic`, and `webhook_id` values that `Registry.process` passes to the app's webhook handler come from unauthenticated HTTP headers and are never covered by the HMAC check.

### Finding Description
`Utils::HmacValidator.validate` treats a request as authentic Shopify traffic solely because `HMAC(api_secret_key, raw_body)` matches the `hmac-sha256` header. It never verifies that the `shop-domain`, `topic`, or `webhook-id` headers are consistent with that signature. Since a single app's `api_secret_key` is shared across every shop that installs it, anyone who can install the app on their own (attacker-controlled) shop can obtain a legitimately signed `(raw_body, hmac)` pair from a real webhook delivery, then replay that exact body/HMAC to the app's public webhook endpoint while substituting the `shop-domain` (and/or `topic`/`webhook-id`) headers with a victim shop's identity. `Registry.process` will accept the HMAC as valid and hand the handler a `WebhookMetadata` object whose `shop` field is attacker-controlled: [4](#0-3) . The equality that should hold — "the shop attributed to the event equals the shop cryptographically bound by the signature" — is broken because the signature binds only the body, not the tenant identity.

### Impact Explanation
This crosses a tenant boundary: an unprivileged internet user who has (or can obtain) any single valid webhook body+signature pair can cause the app's business logic to run under an arbitrary victim shop's identity, since the app trusts `WebhookMetadata#shop` for tenant-scoped actions (data writes, lookups, cache/session keys, etc.) without further verification. This matches the Critical "cross-tenant access" bucket in scope.

### Likelihood Explanation
Exploitation requires only: (1) obtaining one legitimately-signed webhook body from any shop (trivially available to anyone who installs the target public app on their own store or otherwise observes any delivered webhook), and (2) POSTing that same body with forged Shopify headers to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is needed — this is fully within the "unprivileged internet user" threat model.

### Recommendation
Bind the tenant/topic identity into the signed material actually verified, e.g. include `shop`, `topic`, and `webhook_id` (not just the raw body) in `to_signable_string`, or otherwise cryptographically bind those header values before trusting them in `Registry.process`/`WebhookMetadata`. At minimum, document and encourage host applications to cross-check the `shop` in `WebhookMetadata` against a shop known to have a valid, currently-active session/install before acting on the payload.

### Proof of Concept
1. Install the target Shopify app on attacker-owned store `attacker.myshopify.com`; capture a real delivered webhook: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(api_secret_key, B)`).
2. POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim.myshopify.com` and any desired `X-Shopify-Topic`.
3. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` (per `lib/shopify_api/utils/hmac_validator.rb` line 26-31, only `B` is hashed).
4. `ShopifyAPI::Webhooks::Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: forged_topic, body: parsed(B), ...)`, causing the host application to process an event as if it legitimately originated from the victim shop.
