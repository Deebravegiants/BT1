### Title
Stale atom observers after onStop→onLoad cycle silently drop lock/restore state broadcasts - ([File: features/application/src/plugins/lifecycle.ts])

### Summary
`applicationLifecyclePlugin`'s `onStop` calls `observer.unregister()` on each atom observer, which fully unsubscribes from the atom (`unobserve?.()` and `unobserve = undefined`), while the subsequent `onLoad` only calls `observer.start()`, never `observer.register()` again. Since `register()` is only invoked once via `immediateRegister` at construction time, an `onStop` → `onLoad` cycle leaves the atom permanently unsubscribed, so future `lockedAtom`/`restoreAtom`/etc. changes are never re-broadcast to the port.

### Finding Description
`createAtomObserver` (`libraries/atoms/src/factories/observer.ts:10-53`) keeps an internal `unobserve` closure set only during `register()`, and `unregister()` clears it: [1](#0-0) . `start()` merely calls `emitWhenReady()`, which reads `atom.get()` and emits a one-time snapshot — it does not call `register()`: [2](#0-1) .

In `features/application/src/plugins/lifecycle.ts`, observers are created with default `immediateRegister = true`, so `register()` runs exactly once, at plugin construction: [3](#0-2) . `onStop` unregisters all observers (fully removing the `atom.observe` subscription), and `onLoad` only calls `observer.start()` for each, with no re-`register()` call anywhere in this file: [4](#0-3) .

The README explicitly documents `onLoad` as a "hack to support the browser extension, where the UI might die and be recreated while the background process is long-lived," triggered whenever a new UI reconnects to the background: [5](#0-4) . The application module exposes `stop()` which fires `Hook.Stop`, and `load()` which fires `Hook.Load`, both independently callable by the SDK consumer/host wiring the port lifecycle: [6](#0-5) [7](#0-6) .

Because this plugin's `register()` is never called again after the first `onStop`, once `onStop` then `onLoad` execute (e.g., triggered by the documented UI reconnect flow), the observer's `atom.observe` callback is gone permanently. `onLoad`'s `start()` call emits one correct snapshot at reconnect time, but any subsequent change to `lockedAtom`/`restoreAtom`/`lockHistoryAtom`/etc. will not trigger `port.emit`, since there is no live subscription left.

### Impact Explanation
A UI/consumer relying on `port` events for `locked`/`restore`/`lockHistory` state (security-sensitive lock/unlock display) will silently stop receiving live updates after any stop/load cycle, showing stale lock state until another `onLoad` reconnect happens to refresh the snapshot. This can mask an actual lock/unlock transition from the UI, a state-consistency/availability defect in a security-relevant path rather than a direct signing/auth bypass.

### Likelihood Explanation
This is reachable purely through the documented "reconnection hack" — no privileged access or config changes needed, only causing repeated `onStop`/`onLoad` transitions (e.g., forcing extension UI disconnect/reconnect), which the codebase and README confirm is an intended, attacker-triggerable UI lifecycle event. The bug is deterministic given the code shown: `register()` is only invoked once (construction) and unconditionally cleared by `unregister()`, with no compensating call in `onLoad`.

### Recommendation
In `features/application/src/plugins/lifecycle.ts`, call `observer.register()` for each observer inside `onLoad` (or `onStart`) before calling `observer.start()`, matching the pattern used elsewhere in the codebase (e.g., `features/geolocation/plugin/index.js`, `features/wallet-accounts/src/plugins/lifecycle.ts`, which explicitly re-`register()` on start-type hooks after `unregister()` in `onStop`).

### Proof of Concept
Unit test in `features/application/src/plugins/__tests__/lifecycle.test.ts` (or equivalent):
1. Instantiate `applicationLifecyclePlugin` with a mock `port` (`{ emit: jest.fn() }`) and a real/in-memory `lockedAtom`.
2. Call `plugin.onLoad()` — assert `port.emit` is called with the initial `locked` value.
3. Call `plugin.onStop()`.
4. Call `plugin.onLoad()` again (simulating UI reconnect) — assert `port.emit` is called once more with the current snapshot value.
5. Mutate `lockedAtom` (e.g., `await lockedAtom.set(true)`).
6. Assert `port.emit` is called with `('locked', true)` — this assertion **fails** with the current code because `register()` was never re-invoked after `unregister()`, proving the atom change is no longer broadcast.
