### Title
Webhook `shop` domain is trusted from an unauthenticated HTTP header while only the raw body is HMAC-verified, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives its `shop` (and `topic`, `webhook_id`, `api_version`) from HTTP headers, but the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` verifies is computed only over the raw request body, never over these headers.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` (and `topic`, `webhook_id`, `api_version`) are read straight from caller-supplied headers with no cryptographic binding to the body: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC (which only covers `@raw_body`) and then constructs `WebhookMetadata` using `request.shop`, which was never part of the signed material: [4](#0-3) 

`HmacValidator.validate` confirms this: it signs/compares against `verifiable_query.to_signable_string`, i.e. just the body: [5](#0-4) 

This is the equality that is broken:
`shop asserted in signed bytes` (nonexistent — the signed material is only the raw body) `≠` `shop the handler acts on` (`request.shop`, taken from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header).

This mirrors the report's bug class: a field that is *used* by application logic (here, tenant/shop attribution of the webhook) is not covered by the same authenticity check (the HMAC) that is presented as proving authenticity of the whole message.

### Impact Explanation
Any unprivileged actor who operates their own Shopify store receives genuine, correctly-HMAC'd webhooks from Shopify for their own shop's events (the app's `client_secret`/`api_secret_key` is used by Shopify to sign, and the gem/host only verifies that signature over the body). Because the `shop-domain` header is not part of the signed payload, an attacker can replay that same valid `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `Registry.process` will pass HMAC validation (body/HMAC pair is genuinely valid) and will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop. Any host application that keys per-tenant storage, side effects (e.g. order/customer updates, GDPR redact processing, inventory changes) off `WebhookMetadata#shop` will attribute attacker-controlled/replayed data to another merchant's tenant — a cross-tenant data integrity/confidentiality issue that crosses the multi-tenant trust boundary this gem is responsible for establishing via HMAC verification.

### Likelihood Explanation
Likelihood is elevated by the fact that no privileged credentials are needed: the attacker only needs their own (or any) legitimate Shopify shop to obtain a validly-signed webhook body/HMAC pair, then send a forged HTTP request with a different `shop-domain` header directly to the app's public webhook endpoint. This requires no access to the app's `client_secret` and no interception — only knowledge that the header isn't bound to the signature, which is discoverable by reading this gem's source (as done here).

### Recommendation
Include the shop domain (and topic/webhook id, if they are relied upon for routing/attribution) inside the HMAC-signed material, or otherwise cryptographically bind the header claims to the verified body (e.g., by having the host validate that the `shop` claim matches an existing, previously-established session/tenant record rather than trusting the header value emitted from `Request#shop` at face value). At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as the sole tenant identifier without additional server-side verification (e.g., cross-checking against the shop that installed the app for that specific topic/webhook_id).

### Proof of Concept
1. Attacker owns/controls Shop A (their own Shopify development or paid store) with the target app installed.
2. Shopify sends a legitimate webhook for Shop A: raw body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: shop-a.myshopify.com`.
3. Attacker captures this `(B, HMAC)` pair (e.g., by intercepting their own webhook traffic on their own server — no elevated access needed since it's their own shop).
4. Attacker sends a new HTTP POST to the app's public webhook endpoint with the same body `B` and same valid `hmac-sha256` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` accepts headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, B)` — unaffected by the changed shop header: [6](#0-5) 
6. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and `body` from Shop A's event, causing the host app to process/store attacker-influenced data under the victim tenant's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
