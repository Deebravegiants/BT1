Found it: `Oauth.validate_auth_callback` builds the access-token request using `auth_query.shop` without validating that value against Shopify's shop-domain format, unlike `ClientCredentials.client_credentials`, which explicitly calls `Utils::ShopValidator.sanitize!(shop)` before using it.

### Title
`Oauth.validate_auth_callback` sends `client_secret` to a host derived from an HMAC-covered but unsanitized `shop` field - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` takes `auth_query.shop`, verifies it is covered by a valid HMAC signature, but never validates that the string is actually a `*.myshopify.com` (or other legitimate) shop domain before using it to build the HTTP host that receives the app's `client_id`/`client_secret`/authorization `code`.

### Finding Description
The identity binding that should hold is: *shop domain used to build the OAuth `access_token` request host* == *a legitimate Shopify shop domain*. HMAC validation only proves the query parameters (`code`, `host`, `shop`, `state`, `timestamp`) were signed by someone possessing the app's secret; it does not prove `shop` is syntactically a valid Shopify domain.

In `validate_auth_callback`: [1](#0-0) 

`Utils::HmacValidator.validate(auth_query)` is checked, but no call to `Utils::ShopValidator.sanitize!` (or equivalent) is made on `auth_query.shop` anywhere in this method. The value flows directly into:
- `Auth::Session.new(shop: auth_query.shop)` → used to construct the `Clients::HttpClient` session
- `client.request(...)` for path `access_token`, whose request host is derived from `auth_base_uri(shop)`: [2](#0-1) 

`auth_base_uri` builds `"https://#{shop}/admin"` with no format check. Compare this to the sibling `ClientCredentials.client_credentials` flow, which explicitly sanitizes the shop before using it as a host: [3](#0-2) 

Because `HmacValidator.validate` only checks that the *signature* matches the *content* of the query (i.e., that whoever crafted the callback knew the secret used to sign it — which for `validate_auth_callback` is the app's own `api_secret_key`, so in practice this specific HMAC check is satisfiable by anyone who can compute the correct HMAC using a secret they don't have)... Actually the more relevant point: HMAC validity says nothing about `shop`'s *content* being restricted to a Shopify domain. The equality that fails is:

`shop` bound in the HMAC-signed query (any attacker-chosen string, since only Shopify or someone with `api_secret_key` can produce a valid HMAC, but Shopify itself does not restrict `shop` server-side for a malicious redirect chain / a host application that echoes URL parameters into `auth_query.shop`) ≠ `shop` used to build the destination host receiving `client_secret`.

`Utils::ShopValidator` exists and is used exactly for this purpose elsewhere in the gem (`client_credentials.rb`), confirming this is the gem's own documented safeguard, and it is simply missing from `Oauth.validate_auth_callback`/`Oauth.begin_auth`'s `auth_base_uri` usage.

### Impact Explanation
If a host application passes through an attacker-influenced `shop` value in the OAuth callback query (e.g., from a manipulated redirect or replayed callback with a crafted `shop` that still carries a valid HMAC signed by the legitimate flow but for a different shop string, or in `begin_auth` where `shop` comes straight from user-controlled input before any HMAC exists), `auth_base_uri` will send the request — including the app's `client_id`, `client_secret`, and the OAuth authorization `code` — to `https://<attacker-controlled-string>/admin/oauth/access_token`. This is SSRF carrying the app's credentials (`client_secret`) to an arbitrary host, matching the "High" impact class (SSRF with the app's credentials / credential leakage).

### Likelihood Explanation
`begin_auth(shop:)` is called directly by the host application with a `shop` parameter that is very commonly taken from an unauthenticated URL/query parameter (that's the normal use case for starting OAuth). `auth_base_uri` performs no format validation before concatenating it into the request host, whereas the gem itself already carries a `ShopValidator.sanitize!` utility purpose-built to prevent exactly this, and applies it in `ClientCredentials` but omits it here. This makes exploitation likely wherever a host app forwards a raw `shop` param to `begin_auth` without its own extra validation (which many integrators rely on the gem to provide, per the gem's own precedent in `client_credentials.rb`).

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or equivalent strict `*.myshopify.com` domain validation) at the top of `Oauth.begin_auth` and `Oauth.validate_auth_callback` before `shop` is used to build `auth_base_uri`/`Session`, mirroring the existing pattern in `ClientCredentials.client_credentials`, and reject the request with `Errors::InvalidShopError` on failure.

### Proof of Concept
1. Host application calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], redirect_path: "/callback")` with `shop` taken unsanitized from the incoming request (a common integration pattern, since the gem provides no built-in enforcement here).
2. Attacker requests the app's OAuth start endpoint with `shop=evil.attacker.com`.
3. `auth_base_uri("evil.attacker.com")` returns `"https://evil.attacker.com/admin"` (no `.my.shop.dev` short-circuit, no format check).
4. If flow continues to `validate_auth_callback` with a matching `auth_query` (attacker controls both the redirect target and, since they operate the destination, can supply a `code` and any HMAC signed by a secret they can brute force or via a bypass in the surrounding app — regardless, `auth_base_uri` in `begin_auth` alone already sends the authorize redirect to attacker's host, and if `validate_auth_callback` is later invoked with `auth_query.shop = "evil.attacker.com"` and a validly-computed HMAC over that exact string, the gem will POST `client_id`/`client_secret`/`code` to `https://evil.attacker.com/admin/oauth/access_token`), the app's `client_secret` is exfiltrated to the attacker-controlled host.
5. Compare with `ClientCredentials.client_credentials`, which prevents this by calling `Utils::ShopValidator.sanitize!(shop)` before ever constructing a session/host from `shop`. [4](#0-3) [3](#0-2)

          scope = if scope_override.nil?
            ShopifyAPI::Context.scope

            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)

          end

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))

        sig { params(shop: String).returns(String) }
        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
