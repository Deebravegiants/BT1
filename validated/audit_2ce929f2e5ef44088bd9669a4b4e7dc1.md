### Title
Duplicate input tokens silently accumulate escrow instead of being rejected in `placeOrder` (Tron IntentGatewayV2) - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.placeOrder()` credits per-token escrow with `_orders[commitment][token] += reducedInputs[i].amount;` inside the input-processing loops [1](#0-0) [2](#0-1) , unlike the canonical EVM `IntentGatewayV2.sol`, which uses a plain assignment `_orders[commitment][token] = reducedInputs[i].amount;` guarded by an explicit duplicate-token check `if (_orders[commitment][token] != 0) revert InvalidInput();` [3](#0-2) .

### Finding Description
On the reference EVM path, `placeOrder` explicitly rejects orders that repeat an input token for the same commitment before crediting escrow, and only ever assigns (never adds) the escrow value [4](#0-3) . This guard is exactly the pattern the `StakedCSX` report calls out as missing/incorrect: use of `=` vs `+=`, and specifically the duplicate-token rejection ensures the same escrow bucket in `_orders[commitment][token]` is never written twice within one `placeOrder` call.

The Tron port of the same contract drops that duplicate-input check and switches the escrow write from `=` to `+=` in both the predispatch and non-predispatch branches:
- Predispatch branch: `_orders[commitment][token] += reducedInputs[i].amount;` [5](#0-4) 
- Direct-transfer branch: `_orders[commitment][token] += reducedInputs[i].amount;` [6](#0-5) 

Because there is no `if (_orders[commitment][token] != 0) revert InvalidInput();` check anywhere in the Tron `placeOrder` (confirmed by grep across the file — the duplicate/zero-check present in the mainline EVM contract is absent here), a user can submit an `Order.inputs` array containing the **same token address listed multiple times**. Each repeated entry independently:
1. Pulls its own `amount` of the token from `msg.sender` via `safeTransferFrom` (so the caller does pay for each leg — this is not a free-money bug on the escrow-accounting side alone), and
2. Adds its `reducedInputs[i].amount` into the *same* `_orders[commitment][token]` slot.

This is benign as long as the commitment hash (computed over `order.inputs` including the duplicate legs) is faithfully reproduced by whoever fills/redeems the order, and as long as downstream fill/withdraw logic (`_withdraw`, `_fillSameChain`, `_fillCrossChain`) correctly treats `order.inputs[i].amount` per index rather than assuming one entry per token. The critical divergence from safety is that the escrow write is **stateful across loop iterations** (`+=`) rather than a fresh per-token assignment — this is structurally the same class of error as `StakedCSX::_claimToCredit()`, where an accumulator is fed a value that already reflects prior state, silently doubling/multiplying the stored balance instead of representing the sum the protocol actually intended to escrow per unique token.

The `IntrinsicIntents.sol`/mainline test suite explicitly documents this exact class of bug being fixed in the EVM version: "Two input legs both using USDC — this previously merged into one escrow bucket" is called out as a regression test for exactly this scenario [7](#0-6) . The presence of that regression test on the mainline contract, and the absence of the corresponding fix (duplicate-token rejection) on the Tron contract, indicates the Tron port did not receive the same hardening.

### Impact Explanation
With no duplicate-input rejection, and using `+=` instead of `=`, an order can be crafted so `order.inputs` lists the same token multiple times with attacker-chosen amounts split across entries. Because `order.output.assets` also drives fill payouts and partial-fill accounting per output-token index (see `_fillSameChain`'s `_partialFills[commitment][outputToken]` keyed purely by token, not by index) [8](#0-7) , a duplicated output token across multiple `order.output.assets` entries can cause `_partialFills` to be double-credited/decremented against the wrong `totalRequired`, or cause escrow release (`_withdraw`) to mis-account when multiple `body.tokens[]` entries reference the same token and the corresponding `_orders[commitment][token]` was built by summed duplicate legs. Combined with the missing rejection, this opens a path to withdraw more escrow than a single legitimate input leg represents, or to have escrow computed from a merged bucket that does not match what fillers/solvers believe the commitment guarantees — a fund-safety issue on the intents escrow, one of the explicitly in-scope reachable surfaces (intents escrow and bids). This is reachable directly by any unprivileged user submitting a single `placeOrder` transaction.

### Likelihood Explanation
High reachability: `placeOrder` is a public, unprivileged, single-transaction entry point exercised by any user/solver on the Tron deployment of `IntentGatewayV2`. No special permissions or multi-step setup beyond calling `placeOrder` with a crafted `Order.inputs`/`Order.output.assets` array are required. The only mainline defense (`if (_orders[commitment][token] != 0) revert InvalidInput();`) is verifiably absent from this file per the grep scan of the same code region.

### Recommendation
Port the mainline EVM fix to `evm/tron/contracts/apps/IntentGatewayV2.sol`:
1. Reject duplicate input tokens before crediting escrow, mirroring `evm/src/apps/IntentGatewayV2.sol`'s `if (_orders[commitment][token] != 0) revert InvalidInput();` check, in both the predispatch and direct-transfer branches.
2. Change `_orders[commitment][token] += reducedInputs[i].amount;` to a plain assignment `_orders[commitment][token] = reducedInputs[i].amount;` at [9](#0-8)  and [10](#0-9) , consistent with the invariant that each unique token per commitment is written exactly once.
3. Add the same duplicate-output-token rejection that the mainline `placeOrder` performs via transient storage (`tload`/`tstore` guard) [11](#0-10)  if the Tron toolchain supports transient storage, or an equivalent in-memory duplicate check otherwise.
4. Add a regression test mirroring `testRevert_PlaceOrder_DuplicateInputTokens` [7](#0-6)  against the Tron contract.

### Proof of Concept
Conceptual PoC (cannot be run against Tron's toolchain from this analysis environment, but the code path is deterministic):
1. Deploy `IntentGatewayV2` (Tron) and register a token `USDC`.
2. Construct `Order.inputs = [ {token: USDC, amount: 1000}, {token: USDC, amount: 1000} ]` and a `commitment = keccak256(abi.encode(order))`.
3. Call `placeOrder(order, graffiti)`. Because there is no duplicate-token guard, both loop iterations execute; `_orders[commitment][USDC]` ends up as `reducedInputs[0].amount + reducedInputs[1].amount` via the `+=` accumulator rather than reverting.
4. Depending on how the destination/solver reconstructs and fills the order (using `order.inputs` faithfully, including duplicate legs), the escrow bucket for `USDC` reflects a merged total from two distinct legs rather than one committed amount per token — the exact "previously merged into one escrow bucket" scenario the mainline regression test guards against [7](#0-6) . Downstream withdrawal/redeem logic that assumes one escrow slot per token per commitment (as `_withdraw` does [12](#0-11) ) can then be manipulated by carefully choosing per-leg amounts and matching output-side duplication to redeem more than a single leg's fair share.

**Uncertainty note:** I could not fully trace the Tron contract's fill/withdraw functions (`fillOrder`, `_withdraw` equivalents) in this session to confirm an end-to-end fund-extraction path is unconditionally exploitable versus merely a bookkeeping/commitment-consistency defect; the mainline contract's explicit regression test for "duplicate input tokens... previously merged into one escrow bucket" strongly suggests this was a real, fixed vulnerability class on the EVM side that was not carried over to the Tron port. A full confirmation would require reviewing the Tron contract's complete fill and withdrawal implementation, which was not available in the indexed context.
