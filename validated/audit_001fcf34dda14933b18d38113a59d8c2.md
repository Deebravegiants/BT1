## Title
Webhook shop identity spoofing via HMAC that only covers the request body, not the `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The gem's webhook signature verification only authenticates the raw request body. The `shop` (tenant identity) used by the handler to decide *which merchant's* data the webhook event applies to is read directly from an HTTP header that is never included in the HMAC computation, and the HMAC secret (`Context.api_secret_key`) is the same app-wide "client secret" shared by every installed shop. This breaks the identity binding `shop_claimed_by_attacker == shop_that_produced_valid_hmac`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, completely outside the signed data: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the signature only over `verifiable_query.to_signable_string` (i.e. the body), using `Context.api_secret_key`, which is a single secret shared by the app across **every** installed shop, not a per-shop secret: [3](#0-2) 

`Registry.process` trusts the unsigned `request.shop` value as the tenant identity once the (body-only) HMAC passes, and forwards it straight to the app's handler as the authoritative shop for the event: [4](#0-3) 

Because the shared secret produces a valid signature for a given body regardless of which shop the body actually came from, any party who can obtain one genuine `(body, hmac)` pair — e.g., by installing the app on their own shop and receiving a real webhook — can replay that exact body/HMAC to the app's public webhook endpoint while substituting an arbitrary victim `shop-domain` header. `HmacValidator.validate` will still return `true` (the body and secret match), yet `request.shop` — and therefore `WebhookMetadata#shop` passed to the handler — is now attacker-controlled and unrelated to the shop that actually produced the signed payload.

### Impact Explanation
This is a cross-tenant identity binding break: the party that satisfies "produced a validly-signed webhook body" is not required to be the party recorded as the affected shop. Depending on how the host application's webhook handler uses `data.shop` (e.g., `app/uninstalled` to revoke a token, `shop/redact`/`customers/redact`/`customers/data_request` to delete data, or business-logic webhooks that update per-shop state), an attacker who is merely a legitimate installer of the app on their own store can cause the handler to act on a victim shop's identity — i.e., cross-tenant access/manipulation using only their own, unprivileged installation. This satisfies the Critical "cross-tenant access" impact class.

### Likelihood Explanation
Exploitability requires only: (1) the attacker installs the target app on a shop they control (a normal, unprivileged action available to any Shopify merchant/developer), (2) they capture one legitimate webhook delivery (body + `x-shopify-hmac-sha256`) sent to their own endpoint, and (3) they POST that same body/HMAC pair directly to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header. No access token, `client_secret`, or privileged credential is required — the attacker uses their own legitimate installation's traffic. The webhook endpoint is inherently internet-reachable, and the gem performs no validation binding the header-supplied shop to the signed content.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed material, or otherwise cryptographically bind the claimed shop to the verified payload before trusting it (e.g., verify the `shop-domain` header against a per-shop registered value, or use Shopify's newer webhook secret-per-topic scheme where available). At minimum, document that `WebhookMetadata#shop` must not be treated as authenticated on its own and require host applications to cross-check it against records established during OAuth for the specific installation.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers a webhook (e.g. `products/update`).
2. Shopify sends a legitimate webhook to the app: body `B`, header `x-shopify-hmac-sha256: H` (where `H = HMAC-SHA256(app_client_secret, B)`), header `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures `B` and `H` from their own delivered request (they own this endpoint traffic; no secret is needed to observe it).
4. Attacker crafts a new HTTP POST directly to the app's public webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses headers; `Utils::HmacValidator.validate(request)` recomputes `HMAC(app_client_secret, B)`, which equals `H`, so validation passes: [5](#0-4) 
6. `Registry.process` invokes the app's handler with `shop: request.shop` = `"victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own shop: [6](#0-5)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
