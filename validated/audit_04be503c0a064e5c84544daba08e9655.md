## Title
Attacker can drain arbitrary ERC20 balances sitting in the shared `CallDispatcher` via `IntentGatewayV2.placeOrder`'s predispatch sweep - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`placeOrder`'s predispatch path sweeps the *entire* current balance of `_params.dispatcher` for each token listed in the attacker-supplied `order.inputs`, rather than only the amount the attacker actually deposited/produced via `predispatch`. Because `CallDispatcher` is a single, persistent, unprivileged-callable contract shared across all orders (and across other products such as `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata execution, which intentionally park tokens there mid-flight), any balance the dispatcher happens to hold for a token can be swept into an attacker's own escrow and then withdrawn via `cancelOrder`. This mirrors the Tempus finding: a caller-supplied, loosely-validated "amm"/dispatcher balance is trusted and transferred out based on `balanceOf`, not on what the caller actually contributed.

### Finding Description
In `placeOrder`, when `order.predispatch.call.length > 0 && order.predispatch.assets.length > 0`: [1](#0-0) 

the attacker transfers arbitrary (attacker-chosen, possibly trivial) `predispatch.assets` to `dispatcher`, then has the gateway execute fully attacker-controlled calldata via `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)`: [2](#0-1) 

Crucially, `order.inputs` — the tokens/amounts that get swept out of `dispatcher` back to the gateway — is a **completely separate, attacker-controlled list** from `predispatch.assets`. The sweep logic reads the dispatcher's *live* `balanceOf(token)` for whatever token the attacker names in `order.inputs[i].token`, and transfers that *entire* balance (not the attacker's own contribution) back to the gateway as escrow for the attacker's order: [3](#0-2) 

```solidity
uint256 balance = IERC20(token).balanceOf(dispatcher);
if (balance < requiredAmount) revert InvalidInput();
transferCalls[i] = Call({
    to: token,
    value: 0,
    data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
});
```

The only guard is `balance >= requiredAmount`, and `requiredAmount` is itself the attacker's own `order.inputs[i].amount`. An attacker can therefore set `requiredAmount` equal to the dispatcher's *current* balance of any token, causing the entire balance to be swept and (since `received == order.inputs[i].amount`, no "dust" branch) fully credited to `_orders[commitment][token]` for the attacker's own order: [4](#0-3) 

The attacker (as `order.user`) can then immediately call `cancelOrder` (same-chain path) to redeem the full escrowed amount to themselves via `_withdraw`: [5](#0-4) 

`CallDispatcher` is a bare, permissionless, persistent contract with no owner and no scoping to a single order or caller — it accepts native tokens via `receive()` and executes whatever calls it's told to: [6](#0-5) 

The documentation itself confirms the dispatcher is expected to transiently hold tokens across multiple unrelated flows (e.g. `HyperFungibleToken`/`WrappedHyperFungibleToken` mint/unlock destinations, or leftover approvals), explicitly warning that "the dispatcher contract holds tokens temporarily during execution": [7](#0-6) 

Any residual, dust, or transiently-parked balance in this shared `dispatcher` — from any user or any product using it — is thus exposed to an unrelated `placeOrder` caller who simply names that token in `order.inputs` with `amount` set to the observed balance.

### Impact Explanation
This lets an unprivileged caller redirect arbitrary ERC20 (and native) balances that happen to sit in the shared `CallDispatcher` into their own intent-order escrow and withdraw them via `cancelOrder`, with only a trivial, unrelated `predispatch` deposit as a formality. This is direct theft of funds belonging to other users/flows that transiently route tokens through the same dispatcher (e.g., `HyperFungibleToken` cross-chain calldata execution recipients, or dust left by other orders' predispatch/postdispatch sweeps), satisfying the "concrete theft of funds" bar.

### Likelihood Explanation
Reachable from a single, unprivileged `placeOrder` transaction followed by a `cancelOrder` — no special permissions, governance, or trusted role needed. The precondition (dispatcher holding some balance of a token at the moment of the attacker's call) is realistic given the dispatcher's documented use as a transient token holder for multiple products (HFT calldata execution, predispatch/postdispatch swaps), and an attacker can also try to race/front-run legitimate flows that briefly park funds there.

### Recommendation
Do not trust `IERC20(token).balanceOf(dispatcher)` as the sweep amount. Instead, scope the sweep strictly to the delta the *current* predispatch call actually produced, e.g., snapshot the dispatcher's balance for each `order.inputs[i].token` immediately before executing `predispatch.call`, and only sweep `min(requiredAmount, postBalance - preBalance)`. Alternatively, deploy a fresh, single-use dispatcher (or otherwise isolate execution) per `placeOrder` call so no cross-order/cross-flow balance can ever be observed or swept by an unrelated caller.

### Proof of Concept
1. Wait for (or induce) `CallDispatcher` to hold a nonzero balance of some token `T` (e.g. dust left from another order's postdispatch sweep, or tokens routed there mid-flight by `HyperFungibleToken`'s `onAccept` calldata execution).
2. Attacker calls `placeOrder` with:
   - `predispatch.assets` = a trivial amount of any token the attacker owns (just to pass the `assets.length > 0` and `amount == 0` checks).
   - `predispatch.call` = a harmless no-op call to any contract (must not revert).
   - `order.inputs[0]` = `{token: T, amount: currentDispatcherBalanceOfT}`.
3. `placeOrder` executes the sweep: `balanceOf(dispatcher) >= requiredAmount` passes, and the entire balance of `T` is transferred from `dispatcher` to the gateway and fully credited to the attacker's escrow (`_orders[commitment][T] = requiredAmount`, no dust).
4. Attacker calls `cancelOrder` (same-chain) as the order owner; `_withdraw` transfers the full escrowed `T` balance to the attacker. [3](#0-2) [5](#0-4)

```text
contract CallDispatcher is ICallDispatcher {
    /**
     * @dev error thrown when the target is not a contract.
     */
    error NotContract(address target);

    /**
     * @dev error thrown when a call fails.
     */
    error CallFailed(address target, bytes result);

    /**
     * @dev Receive function to accept ETH transfers
     */
    receive() external payable {}

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```

```text
The `data` field is an ABI-encoded `Call[]` array, where each `Call` specifies a target contract, a native value to forward, and the calldata to execute. On the destination chain, the HFT contract mints or unlocks tokens to the `to` address, then forwards the entire `data` payload to the `CallDispatcher`, which executes each call sequentially. If the calls need to spend the bridged tokens (e.g., approve then swap), set `to` to the `CallDispatcher` address so tokens are delivered directly to it.

For code examples, see the [HyperFungibleToken](/developers/evm/hyper-fungible-token/hyper-fungible-token#calldata-execution) and [WrappedHyperFungibleToken](/developers/evm/hyper-fungible-token/wrapped-hyper-fungible-token#calldata-execution) pages.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
```
