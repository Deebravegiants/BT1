### Title
Duplicate `address(0)` entries in `erc20TokenAddresses` let a single `msg.value` satisfy multiple independent balance equations, minting unbacked shielded ETH - (File: contracts/Hinkal.sol)

### Summary
`Hinkal.transact` verifies a per-token balance equation in a loop over `circomData.erc20TokenAddresses`, and for the ETH leg it adds `msg.value` back into `balanceDif` to compensate for ETH already being part of `address(this).balance` when the payable call begins. Neither `dimensionsCheck`/`checkOnchainCreation` in `HinkalHelper.sol` nor the balance loop in `Hinkal.sol` enforce that `address(0)` appears at most once in `erc20TokenAddresses`, so an attacker can list `address(0)` at two separate indices and have the *same* `msg.value` satisfy two independent `amountChanges` claims, minting twice the shielded ETH value actually deposited.

### Finding Description
Broken equality: the protocol's intended invariant is
`sum over i of (real ETH backing consumed for index i) == sum over i of (amountChanges[i] + utxoAmount[i])` for all `i` where `erc20TokenAddresses[i] == address(0)`, with `msg.value` backing exactly one such term.

In `Hinkal.sol`, the balance-check loop computes, for every `i`: [1](#0-0) 

For any index where `erc20TokenAddresses[i] == address(0)`, `balanceDif` is computed as `newBalances[i] + msg.value - oldBalances[i]`, using the *global* `msg.value` and the *global* current ETH balance (`getERC20OrETHBalance(address(0))` returns `address(this).balance` regardless of index): [2](#0-1) 

Because `address(this).balance` and `msg.value` are identical for every index tagged `address(0)`, if the attacker crafts `circomData.erc20TokenAddresses` with `address(0)` appearing twice (e.g. `[tokenA, address(0), address(0)]`, with the swap performed entirely between `tokenA`/some ERC20 `tokenB` so ETH balance is otherwise untouched), then for both duplicate indices `j` and `k`:
`balanceDif[j] == balanceDif[k] == msg.value` (since `newBalances == oldBalances` for the untouched ETH pool).

The check at line 137-146 requires `balanceDif[i] == amountChanges[i] + utxoAmount[i]` independently per index. The attacker sets `amountChanges[j] = amountChanges[k] = msg.value` (both `onChainCreation=false`, so neither produces an on-chain UTXO matched from `utxoSet`, avoiding the `onChainCommitments` array bound). Both independent checks pass with a single real ETH payment (`msg.value`), because nothing in `dimensionsCheck` or `checkOnchainCreation` rejects duplicate token addresses: [3](#0-2) [4](#0-3) 

The ZK circuit constrains each token slot's `in + amountChanges == out` independently per index and has no cross-index constraint forbidding the same token address from occupying two slots in the same public-input vector, so the prover can freely generate a valid proof for two off-chain output UTXOs of the declared `amountChanges` values, each nominally "backed" by the same `msg.value`.

The attacker's call: `Hinkal.transact{value: V}(a, b, c, dimensions, circomData)` where `circomData.externalActionData.externalActionId` points to `LifiExternalAction`/`ExternalActionSwap`, `circomData.erc20TokenAddresses = [tokenIn, tokenOut, address(0), address(0)]`, `amountChanges[2] = amountChanges[3] = V`, `onChainCreation[2] = onChainCreation[3] = false`, and the swap itself is performed entirely between `tokenIn`/`tokenOut` (no ETH involved in the swap), leaving the ETH pool's `newBalances == oldBalances`. Both duplicate-index checks pass with the single `V` wei sent, and the proof creates two off-chain shielded UTXOs each worth `V`, i.e. `2V` of shielded ETH backed by only `V` real ETH.

Existing guards (`performHinkalChecks`, `dimensionsCheck`, `checkOnchainCreation`, `verifyProof`, `rootHashExists`, slippage `require`, `insertNullifiers`) do not check for duplicate entries in `erc20TokenAddresses`, and the balance/slippage `require`s are satisfied independently per index precisely because both indices reuse the identical `msg.value`/global-balance snapshot.

### Impact Explanation
The attacker mints shielded ETH value without backing: for a deposit of `V` wei of real ETH, `2V` (or more, with additional duplicate `address(0)` entries) of shielded ETH commitments/UTXOs are created inside Hinkal's tree. This is direct protocol insolvency — the shielded ledger no longer matches the contract's actual ETH holdings, and the excess shielded balance can subsequently be withdrawn by the attacker, draining real ETH deposited by other users. This matches the Critical category: "minting shielded value without backing." The attack is repeatable per transaction and scales linearly with the number of duplicate `address(0)` entries the attacker includes (bounded only by gas/array-size limits), each requiring only one prepaid `msg.value`.

### Likelihood Explanation
- Preconditions: attacker needs only to be able to call `transact` with a self-generated valid proof (no privileged role required), and pick an `externalActionId` (e.g., LiFi swap) whose logic does not itself touch ETH, or a swap where ETH balance nets to zero change.
- Attacker cost: only the gas and the single `msg.value` deposit `V`; proof generation is fully local since the prover is untrusted input to `Hinkal.transact` and no witness-generation service enforces uniqueness of token addresses.
- Feasibility: straightforward — no cryptographic bypass is needed, only careful construction of `circomData` arrays (all attacker-controlled per the rules) and a matching valid proof, since the circuit's per-slot equation is satisfiable independently for duplicate slots.
- Repeatable indefinitely until patched.

### Recommendation
Enforce uniqueness of `erc20TokenAddresses` (in particular `address(0)`) within a single `transact` call, e.g., add a check in `dimensionsCheck` (or a new check in `performHinkalChecks`/the `transact` balance loop) that rejects any duplicate address in `circomData.erc20TokenAddresses`. Alternatively, restructure the balance-equation loop to consume `msg.value` once (subtract it from a running total that starts at `msg.value` and is decremented as it's attributed to the first `address(0)` index encountered, reverting if a second `address(0)` index tries to draw from an already-exhausted pool) rather than adding the same `msg.value` to every matching index independently.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, and a `LifiExternalAction` (or any registered external action) with a mock router that performs a simple ERC20-to-ERC20 swap (no ETH involved).
2. Fund the attacker EOA with `V` ETH and enough `tokenIn`/allowance for the swap.
3. Off-chain (test harness), generate a proof for `circomData` with:
   - `erc20TokenAddresses = [tokenIn, tokenOut, address(0), address(0)]`
   - `amountChanges = [-inputAmount, 0, V, V]`
   - `onChainCreation = [false, true, false, false]` (index 1 is the swap's on-chain output UTXO; indices 2 and 3 are off-chain deposits)
   - matching `slippageValues`, `inputNullifiers`, `outCommitments`, `encryptedOutputs` so the equation and circuit constraints hold per index.
4. Call `hinkal.transact{value: V}(a, b, c, dimensions, circomData)`.
5. Assert:
   - LHS: `address(this).balance` (Hinkal contract) increased by exactly `V` (real ETH backing).
   - RHS: sum of newly inserted off-chain commitments' declared ETH value == `2V` (i.e., `amountChanges[2] + amountChanges[3]`).
   - Assert `RHS (2V) > LHS (V)`, proving unbacked shielded ETH was minted.
6. Confirm the transaction does not revert (both `balanceDif[2]` and `balanceDif[3]` independently equal `msg.value = V`, matching `amountChanges[2]` and `amountChanges[3]` respectively).
