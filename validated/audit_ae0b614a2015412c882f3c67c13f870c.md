### Title
Webhook `shop` identity field is not covered by the HMAC signature, allowing tenant spoofing in `WebhookMetadata` - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, but exposes `shop`, `topic`, `api_version`, and `webhook_id` as trusted attributes derived from unauthenticated HTTP headers. `Registry.process` verifies the HMAC and then immediately hands `request.shop` (and the other header-derived fields) to the host application's webhook handler as an authenticated tenant identifier, even though `shop` was never part of the signed bytes.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by recomputing an HMAC over `to_signable_string` and comparing it to the `hmac` value with `OpenSSL.secure_compare`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `Request#shop` (the tenant identity used downstream) is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never included in the HMAC computation: [3](#0-2) [4](#0-3) 

`Registry.process` validates the HMAC and then, having *only* verified the body bytes, builds `WebhookMetadata` using the unverified `request.shop` (and `request.topic`, `request.api_version`, `request.webhook_id`) and dispatches it to the app's handler as if it were an authenticated field: [5](#0-4) 

This is the same class of bug as the reported issue: a value the code treats as verified/authoritative (the inflator update / here, the `shop` identity) is not actually covered by the check that is supposed to guarantee its integrity (the interest accrual condition / here, the HMAC signature). The binding that should hold is:
`hmac_valid(raw_body) == true` implies `shop == the shop that actually sent this webhook`
but in reality `hmac_valid` only proves `raw_body` is untampered — it says nothing about `shop`, because `shop` is sourced from a header outside the signed payload.

### Impact Explanation
An attacker who can reach the app's webhook endpoint (which per Shopify's model must accept unauthenticated POSTs bearing only an HMAC over the body) can submit a request with a body/HMAC pair that legitimately validates (e.g., replaying a previously captured, legitimately-signed body from their own shop, since HMAC is computed with the single shared `api_secret_key` for the whole app, not per-shop), while forging the `shopify-shop-domain` header to name a *different* merchant's shop. `Registry.process` will accept the HMAC as valid and pass the forged `shop` value to the handler untouched. Any host application that uses `data.shop` from `WebhookMetadata` (a documented, intended use of this struct) to look up which merchant/session/tenant the payload applies to — rather than independently re-verifying shop against something authenticated — will process or attribute webhook data under the wrong tenant. This crosses a tenant boundary using only a forged header, i.e., cross-tenant confusion driven entirely by this gem's own metadata contract.

### Likelihood Explanation
Exploitation requires only the ability to send arbitrary HTTP requests to the app's public webhook endpoint plus possession of one validly-HMAC'd raw body (which is not shop-specific — the same `api_secret_key` signs webhooks for every shop installed on the app, and Shopify test/mandatory webhook bodies such as `customers/redact` are simple, predictable JSON). No access token, session, or `api_secret_key` knowledge is required beyond what any webhook subscriber already needs to receive callbacks. The gem's own documented contract (`WebhookMetadata#shop`) invites host applications to trust this field as the identified shop, making this reachable through normal, intended API use rather than misuse.

### Recommendation
Do not expose `shop`/`topic`/`webhook_id`/`api_version` as though they were authenticated by the HMAC when they are sourced purely from headers. Either:
1. Include the shop domain (and other identity-bearing headers) in the signed payload computation used for these purposes, or
2. Clearly document that `Request#shop` and `WebhookMetadata#shop` are **unauthenticated** header values and that host applications must independently verify the shop identity (e.g., by cross-checking it exists in their own installed-shops list) before using it as a tenant key, or
3. Have `Registry.process` require the caller to supply/confirm the expected shop separately from trusting the header value.

### Proof of Concept
1. Attacker's own shop (`attacker-shop.myshopify.com`) receives a legitimately Shopify-signed webhook with body `{}` and header `x-shopify-hmac-sha256` computed with the app's shared `api_secret_key` (this signature depends only on the body, not the shop).
2. Attacker replays this exact body/HMAC pair to the app's webhook endpoint but replaces the header `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, and `Utils::HmacValidator.validate` succeeds because it only checks `@raw_body` against the HMAC: [6](#0-5) 
4. `Registry.process` raises no error and calls `handler.handle(data: WebhookMetadata.new(... shop: request.shop ...))` with `shop == "victim-shop.myshopify.com"`, even though the request never actually originated from Shopify on behalf of that shop: [5](#0-4) 
5. Any host application logic keyed on `data.shop` (e.g., session/tenant lookup, GDPR redact processing, order/customer data writes) now operates under the wrong tenant's identity.

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
