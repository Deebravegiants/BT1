### Title
Unchecked `borrowed * borrow_index` value overflows `i128` and permanently bricks the market before the index cap can engage - (File: common/src/rates/index.rs)

### Summary
Every controller verb accrues interest before acting. Accrual computes the market's total debt as `borrowed_shares * borrow_index` via `scaled_to_original` / `calculate_supplier_rewards`, a RAY-scaled product that panics with `MathOverflow` once `supplied * index` leaves `i128`. `MAX_BORROW_INDEX_RAY` is meant to bound the index, but the value-side overflow is reached first when a market holds a whale-scale book: the index still has headroom below the cap while `borrowed * index` already exceeds `i128::MAX`. Once crossed, `update_indexes`, `withdraw`, `repay`, `liquidate`, and every other entrypoint reverts at the same multiplication, permanently freezing all supplier funds in that market.

### Finding Description
The interest pipeline unprivately reachable through `controller::update_indexes` (and implicitly through `supply`/`borrow`/`withdraw`/`repay`/`liquidate`) computes:

- `update_borrow_index` multiplies `old_index.mul(interest_factor)` **before** clamping to `MAX_BORROW_INDEX_RAY`, so the pre-clamp product is itself an overflow site [1](#0-0) 
- `calculate_supplier_rewards` computes `borrowed.mul(new_borrow_index)` and `borrowed.mul(old_borrow_index)` — the scaled-debt value that overflows first at large `borrowed` [2](#0-1) 
- `update_supply_index` computes `supplied.mul(old_index)` with the same exposure [3](#0-2) 
- `Ray::mul` resolves through `mul_div_half_up`, which widens to `I256` but still panics with `GenericError::MathOverflow` when the final quotient doesn't fit `i128` [4](#0-3) 
- `Cache::calculate_utilization` calls `scaled_to_original(borrowed, borrow_index)` on the same path [5](#0-4) 

The index ceiling bounds `index` but not `scaled_shares * index`. For an 18-decimals market at ~98% utilization on a steep rate curve, `borrowed * borrow_index` crosses `i128::MAX` while `borrow_index < MAX_BORROW_INDEX_RAY`, so the cap never engages. The repo's own test demonstrates the cliff: after accrual panics, `withdraw` and `repay` both revert with `MATH_OVERFLOW` because every verb accrues first [6](#0-5) .

### Impact Explanation
Permanent freezing of funds. Once `borrowed * borrow_index > i128::MAX`, every state-changing entrypoint on that (hub, token) book — `withdraw`, `repay`, `liquidate`, `update_indexes`, `claim_revenue`, `recapitalize` — panics at the same multiplication during accrual. Suppliers cannot exit, borrowers cannot repay, liquidators cannot act. There is no admin escape listed among the reachable entrypoints that skips accrual, so the freeze is permanent for that market.

### Likelihood Explanation
A single unprivileged address can set up the precondition: supply a whale-scale amount of a high-decimals asset (the in-repo PoC uses ~10^27 base units of an 18-decimals token, feasible for a large holder or via repeated supply), borrow near the utilization kink, and let time pass. No privileged role, leaked key, or bad parameter is needed — the interest curve is a configured market input and caps can be lifted to allow large books. The barrier is capital scale plus sustained high utilization, making this Medium likelihood: expensive to stage but fully permissionless and irreversible once achieved.

### Recommendation
Perform the clamp before the multiply, or make the value-side products saturating:
- In `update_borrow_index`, detect `old_index > MAX_BORROW_INDEX_RAY / interest_factor`-equivalent bounds and clamp without forming the overflowing product.
- In `calculate_supplier_rewards` / `update_supply_index` / `scaled_to_original`, use a saturating `mul_div` for `scaled * index` (as `calculate_scaled_cap` already does with `mul_div_floor_saturating`) so accrual caps the accrued value instead of trapping, keeping exits and repayments live.
- Alternatively enforce a supply cap / debt ceiling per market such that `max_shares * MAX_BORROW_INDEX_RAY` provably stays below `i128::MAX` (extend `require_cap_within_asset_domain` to account for index ceilings, not only `RAY` rescaling).

### Proof of Concept

```rust
let principal = BILLION * 10i128.pow(18);          // whale-scale supply
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;                    // ~98% utilization
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);

loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; }
}
// -> errors::MATH_OVERFLOW, with borrow_index still < MAX_BORROW_INDEX_RAY
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

Path: `controller::update_indexes` → accrual → `update_borrow_index` → `calculate_supplier_rewards` → `borrowed.mul(env, new_borrow_index)` → `fp_core::mul_div_half_up` → `I256` quotient fails `.to_i128()` → `panic_with_error!(GenericError::MathOverflow)`. All subsequent `withdraw`/`repay`/`liquidate` calls on the book hit the identical panic, so user funds are frozen permanently.

```rust
pub fn try_mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> Option<i128> {
    if x < 0 || y < 0 || d <= 0 {
        return None;
    }
    let half = d / 2;

    // Fast path: the biased product fits `i128`, so the whole computation is
    // native. `x * y + half` is non-negative here, so `/` is the floor the
    // widened path would produce.
    if let Some(biased) = x
        .checked_mul(y)
        .and_then(|product| product.checked_add(half))
    {
        return Some(biased / d);
    }

    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    x256.mul(&y256)
        .add(&I256::from_i128(env, half))
        .div(&d256)
        .to_i128()
}
```

```rust
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {

        .with_market(big("BIG18", 18, xlm_curve()))

    t.borrow_raw(ALICE, "BIG18", debt);

    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
```
