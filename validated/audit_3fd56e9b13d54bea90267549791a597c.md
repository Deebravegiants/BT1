### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, never the `shopify-shop-domain` header, yet `Registry.process` trusts `request.shop` (built straight from that header) when constructing `WebhookMetadata` passed to the host app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` verifies authenticity solely via `Utils::HmacValidator.validate(request)` at [1](#0-0) , which calls `verifiable_query.to_signable_string` for signature computation. For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, excluding any headers: [2](#0-1) .

The `shop` accessor is derived purely from the unauthenticated `shopify-shop-domain` header: [3](#0-2) .

That value is forwarded unchanged into `WebhookMetadata.shop`, which is delivered to the app's handler as the identity of the sending tenant: [4](#0-3)  and [5](#0-4) .

The identity binding broken is: `hmac_valid(body, api_secret_key) == true` should imply `request.shop == the-tenant-that-actually-sent-this-body`, but the gem only proves `hmac_valid(body)`, never `hmac_valid(body, shop)`. Since a single app's `api_secret_key` is shared across every merchant shop that installs it, any merchant who has legitimately received one authentic webhook (valid body + valid HMAC, both attributable to their own shop) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with an arbitrary victim shop domain. `HmacValidator.validate` at [6](#0-5)  will still pass because it never inspects the shop header, so the forged request is delivered to the handler as if it originated from the victim shop.

### Impact Explanation
This breaks the shop-authentication guarantee that host applications rely on to route webhook data to the correct tenant record. An attacker who is a normal (unprivileged relative to other tenants) installer of a public app can cause the app to process attacker-controlled webhook bodies under an arbitrary victim shop's identity, leading to cross-tenant data confusion/injection in any host application that uses `WebhookMetadata#shop` to select the tenant session/record (the exact documented usage pattern for this gem's webhook API). This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any installed public app: the attacker needs no secrets, no privileged account, and no interception — only a genuine webhook delivery to their own shop (trivially obtained by performing an action that triggers a subscribed webhook topic) and the ability to send an HTTP request with a modified `shopify-shop-domain`/`x-shopify-shop-domain` header to the app's public webhook endpoint.

### Recommendation
Bind the shop domain (and other trust-critical headers like topic/webhook-id) into the signed content, or otherwise cryptographically tie the `shop` claim to the verified payload before constructing `WebhookMetadata`. At minimum, the library should document/enforce that host apps cannot rely on `request.shop`/`WebhookMetadata#shop` as an authenticated value unless verified independently (e.g., cross-checked against a shop the app already has an active session for), and ideally `Registry.process` should reject webhooks whose declared shop cannot be corroborated against session state before invoking the handler.

### Proof of Concept
1. Install the target app on `attacker.myshopify.com` (this is app's shared `api_secret_key`, same for every tenant).
2. Trigger a subscribed webhook topic (e.g. `orders/create`) on `attacker.myshopify.com`; capture the resulting raw body `B` and the genuine `x-shopify-hmac-sha256` header `H` computed by Shopify over `B` with the app's secret.
3. Replay a POST to the app's webhook endpoint with the same body `B`, the same `x-shopify-hmac-sha256: H`, and `x-shopify-topic`/`x-shopify-webhook-id` unchanged, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls `HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H`, so validation succeeds at [7](#0-6) .
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` and processes attacker-supplied data under the victim's identity.
