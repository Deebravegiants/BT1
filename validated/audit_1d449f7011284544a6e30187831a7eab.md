### Title
Webhook Shop-Domain Tenant Identifier Not Covered by HMAC Signature Allows Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that is handed to webhook handlers from the unauthenticated `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature verified by `HmacValidator` only covers the raw request body. Any caller who can obtain one valid `(raw_body, hmac)` pair (e.g., a legitimate webhook delivered to their own store) can replay that body/HMAC pair while substituting an arbitrary `shop-domain`, `topic`, `webhook-id`, or `api-version` header, and the gem will treat the request as authentic and dispatch it under the attacker-chosen shop identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC purely over `to_signable_string`, i.e., the raw body: [2](#0-1) 

But `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled directly from HTTP headers with no cryptographic binding to the HMAC: [3](#0-2) 

`Registry.process` verifies the HMAC and then immediately trusts `request.shop` as the tenant identity forwarded to the app's handler: [4](#0-3) 

The identity binding that should hold is:
`shop_used_by_handler == shop_covered_by_hmac`

but the actual binding is:
`shop_used_by_handler == shop_header_value` (unauthenticated) while `hmac_covers == raw_body_only`

Because `shop`, `topic`, and `webhook_id` are never part of the signed payload, an attacker who has legitimate access to any one valid Shopify webhook delivery (for example, from their own development/test store, since mandatory webhooks like `customers/data_request` or `shop/redact` are delivered to every installed app) can capture that `(raw_body, X-Shopify-Hmac-Sha256)` pair and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain. `HmacValidator.validate` will still pass because it never looks at the shop header, and `Registry.process` will invoke the registered handler with `shop: <victim-shop>`.

### Impact Explanation
This breaks the tenant/authentication boundary the HMAC is supposed to enforce: the gem allows an unprivileged, unauthenticated actor to make the host application process attacker-controlled data under a different merchant's identity. Depending on how the hosting app uses `WebhookMetadata#shop` (commonly used to look up the merchant's session/access token or trigger merchant-scoped side effects such as GDPR data export/erasure per `customers/data_request` / `shop/redact`), this can result in cross-tenant data confusion or actions being taken against the wrong merchant — matching the "cross-tenant access" class of impact.

### Likelihood Explanation
Exploitation only requires the attacker to have received any single legitimate webhook delivery (trivially obtainable by installing the target app on their own development store, since Shopify sends mandatory compliance webhooks to every installed app) and the ability to POST to the app's public webhook endpoint with modified headers — no access token, `client_secret`, or privileged credentials are required.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the HMAC-signed payload verification, or otherwise cryptographically bind `X-Shopify-Shop-Domain` to the verified signature before it is used as a tenant identifier in `Registry.process`. At minimum, cross-check the header-derived shop against a shop the app already has an active/authorized session for, rather than trusting it unconditionally post body-HMAC validation.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and receives a mandatory webhook (e.g., `customers/data_request`) with a valid `X-Shopify-Hmac-Sha256` header for a given `raw_body`.
2. Attacker replays the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `raw_body` against the HMAC.
4. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` line 198 constructs `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-supplied `shop-domain` header, and invokes the app's handler as if the event genuinely originated from `victim-shop.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
