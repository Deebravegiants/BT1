### Title
Unvalidated route payload lets arbitrary contracts execute under the sender's signed auth tree and drain wallet funds - (File: contracts/swap-aggregator/src/venues/)

### Summary
`execute_strategy` executes a fully caller-supplied route: every `pool`, `token_in`, and `token_out` address comes from the `StrategyPayload` `assets` registry, and the router keeps no allowlist of venues, pools, or tokens. A route naming an attacker-deployed "pool" puts that contract on the call stack inside the sender's authorization tree, where it can invoke `token.transfer(sender, attacker, amount)` as a child of the sender's signature — exactly the policy-enforcement gap class of CVE-2020-6501 (a crafted payload bypasses the intended containment boundary).

### Finding Description
`SwapHop.pool` is resolved from the payload's `assets` registry by `u8` index with only bounds validation in `Program::decode` — there is no venue/pool/token admission check anywhere in the router [1](#0-0) . `execute_strategy` calls `sender.require_auth()`, then the sender's auth covers the nested `token_in.transfer(sender, router, total_in)`; simulation produces that auth tree, and any additional authorized invocation a hop contract makes from `sender` is recorded as another child of the same signature [2](#0-1) . The threat model states this explicitly: "a route can put third-party code on the call stack below the caller's authorization… The loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it." The harness demonstrates the primitive: `RogueHopPool::swap` calls `token.transfer(victim, attacker, amount)` during the route's venue call [3](#0-2) . The `total_min_out` check only bounds the measured `token_out` delta; it does not constrain what the named pool does with the sender's auth.

### Impact Explanation
Theft of user funds. Any ERC20-style token the victim holds can be transferred out by the rogue pool contract during route execution, bounded only by what the victim's signed auth tree accepts — not by `total_in`, `min_out`, or slippage. Since routes are built off-chain and signed as opaque XDR, a compromised or malicious route builder (or a phishing frontend) can ship a payload that looks like a fair swap and still drains the signer's wallet.

### Likelihood Explanation
The attack requires the victim to sign a malicious `swap_xdr` and its simulated auth tree. That is the normal flow: routes arrive as opaque XDR and wallets display the auth tree rather than the decoded route, so a user who does not independently decode the payload is exposed. No privilege, oracle manipulation, or timing is needed — only a crafted route and an inattentive signature. The loss is unbounded relative to the swap size, matching a Medium characterization.

### Recommendation
Maintain an owner-managed allowlist of pool/venue addresses (parallel to the existing `WhitelistedTokens`/`add_to_whitelist` machinery in `storage.rs`) and reject any `SwapHop.pool` or `token_in`/`token_out` not on it in `execute/mod.rs` before dispatch. Alternatively, restrict venue adapters to dispatch only to addresses attested at config time, or sandbox hop calls so they cannot perform `transfer` from `sender` — e.g., enforce that the only `sender`-authorized invocation is the single input transfer, as the controller path already does via `authorize_transfer_as_current` with no sub-invocations (INV-STRAT-01) [4](#0-3) .

### Proof of Concept
1. Attacker deploys `Rogue` contract whose `swap()` entrypoint calls `token::Client::transfer(victim, attacker, victim_balance)` (as in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`).
2. Attacker serves the victim a route XDR: `assets[0] = Rogue`, `assets[1] = USDC`, `assets[2] = XLM`; one Swap instruction with `idx_a = 0`, `min_out` set to a plausible quote, `total_in` normal.
3. Victim submits `execute_strategy(victim, total_in, swap_xdr)`; simulation builds an auth tree containing the USDC input transfer plus the rogue child transfer. Victim signs.
4. During the instruction loop the router invokes `Rogue.swap`; the nested `transfer(victim → attacker)` executes under the victim's signature, draining the wallet balance while the swap itself still returns `min_out` and passes all checks.

/// Attacker-deployed "pool". `amount == 0` is the benign control.
#[contract]
pub struct RogueHopPool;

#[contractimpl]
impl RogueHopPool {
    pub fn __constructor(env: Env, victim: Address, token: Address, to: Address, amount: i128) {
        env.storage()
            .instance()
            .set(&symbol_short!("PLAN"), &(victim, token, to, amount));
    }

    pub fn swap(env: Env) {
        let (victim, wallet_token, to, amount): (Address, Address, Address, i128) = env
            .storage()
            .instance()
            .get(&symbol_short!("PLAN"))
            .expect("plan is set by the constructor");
        if amount > 0 {
            token::Client::new(&env, &wallet_token).transfer(&victim, &to, &amount);
        }
    }
}

### INV-STRAT-01 — Controller router authority binds one input transfer

The controller authorizes one exact
`token_in.transfer(controller, configured_router, amount_in)` invocation,
without sub-invocations. This grants invocation authority, without a token
allowance.

The controller ignores the router's return value, rejects input-balance growth
and rejects measured spending above `amount_in`.
