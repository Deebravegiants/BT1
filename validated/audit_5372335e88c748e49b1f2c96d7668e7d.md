### Title
Webhook shop domain, topic, and webhook-id headers are trusted without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw request **body only**, while the shop, topic, and webhook-id are read straight from unauthenticated HTTP headers. `Registry.process` validates the HMAC and then unconditionally trusts those header-derived fields when constructing the `WebhookMetadata` passed to the app's handler, so the identity binding "HMAC-verified bytes == data acted upon" is broken: the signature covers the body, but the shop attribution comes from a field the signature never touched.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, and `webhook_id` are pulled directly from HTTP headers that are never included in the signed string: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `verifiable_query.to_signable_string` against the HMAC: [3](#0-2) 

`Registry.process` validates the HMAC and then hands the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` straight to the app's registered handler as trusted metadata: [4](#0-3) 

This is the same bug class as the report: a field that is *acted on* (here, the shop/topic identity used to attribute webhook data to a tenant) is not covered by the cryptographic check (here, the HMAC) that is supposed to authenticate the whole message. Notably, the gem does the correct thing elsewhere — `Auth::Oauth::AuthQuery#to_signable_string` explicitly folds `shop` into the signed string: [5](#0-4) 

but the webhook `Request` class does not follow the same pattern for its identity fields, leaving shop/topic/webhook-id outside the authenticated envelope.

### Impact Explanation
Since `x-shopify-shop-domain` (or `shopify-shop-domain`) is not part of the signed content, any HTTP client that can present a body+HMAC pair that validates against the app's `api_secret_key` for *some* shop event can resubmit that exact body with a different `shop-domain` header, and the app will process it as if it came from an arbitrary other shop. Because `api_secret_key` is shared across every shop that has installed a given app, any merchant who installs the app can capture a genuinely-signed webhook for their own store and then replay it against the app's public webhook endpoint with the `shop-domain` header swapped to point at a different tenant. Handlers that key persistence, authorization, or business logic off `WebhookMetadata#shop` (as the library encourages via `handler.handle(data: WebhookMetadata.new(topic: ..., shop: request.shop, ...))`) will attribute the (attacker-influenced) event data to the wrong tenant — a cross-tenant data-integrity/confusion issue reachable by any unprivileged internet user who can install the target app on their own store.

### Likelihood Explanation
Exploitation requires no access to the app's `api_secret_key`, access tokens, or TLS interception — only the ability to install the app on any Shopify store (or otherwise obtain one legitimately-signed webhook body) and resend an HTTP POST to the app's public webhook endpoint with a modified header. The header-swap step is trivial once a valid (body, HMAC) pair is in hand, since `HmacValidator` never inspects headers.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signable content used for webhook HMAC verification, or otherwise cryptographically bind the header-derived identity fields to the signature before they are surfaced to handlers — mirroring the approach already used in `Auth::Oauth::AuthQuery#to_signable_string`, which folds `shop` into the signed payload.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers a webhook event (e.g. `orders/create`), capturing the raw JSON `body` and the valid `x-shopify-hmac-sha256` value Shopify sent for it.
2. Attacker POSTs to the app's webhook endpoint with the identical `body`/`x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` passes because it only checks the body against the HMAC (`lib/shopify_api/webhooks/request.rb` `to_signable_string`, `lib/shopify_api/utils/hmac_validator.rb`).
4. `Registry.process` calls the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's captured body>, ...)`, causing the app to process/attribute the attacker's webhook payload as if it belongs to `victim-shop`.
