### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity is taken from unauthenticated HTTP headers while the HMAC only covers the raw body, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as verified once `Utils::HmacValidator.validate(request)` returns true, but the HMAC signature computed by this gem only ever covers the raw request body — never the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers that are handed to the app's handler as trusted identity fields.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate_signature` computes and compares the HMAC exclusively against `verifiable_query.to_signable_string`, i.e. the body: [2](#0-1) 

`Registry.process` uses this single body-only check as its sole authenticity gate, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`), all of which are read straight from HTTP headers with no cryptographic binding: [3](#0-2) [4](#0-3) 

The identity equality that should hold is: `HMAC-verified data == data acted upon by the handler`. In reality, only `body` is HMAC-verified, while `shop` (the tenant identity) is taken from an unverified header. Because a single app's `client_secret`/`api_secret_key` is shared across every shop that installs the app, any merchant who has installed the app can legitimately receive a webhook for their own store — a valid `(body, HMAC)` pair signed with the app's shared secret. That merchant can then replay the same body and HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`/`x-shopify-webhook-id`) header with an arbitrary value, e.g. a victim shop's domain. `HmacValidator.validate` still succeeds (it never looked at the header), and `Registry.process` calls the app's handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)`, `shop` being fully attacker-controlled.

This breaks the tenant-authentication boundary the gem's own documentation promises: "This will verify the request did indeed come from Shopify" (docs/usage/webhooks.md), and applications built per that documented contract (using `data.shop` to key sessions, look up merchants, or perform per-shop side effects) will act on forged tenant identity.

### Impact Explanation
This enables cross-tenant confusion: an authenticated app-installing attacker can make the host application process arbitrary attacker-chosen webhook bodies under the identity of any other shop known to the attacker (shop domains are guessable/public, `*.myshopify.com`). Depending on how the host app's handler uses `data.shop` (e.g., to route data into that shop's records, trigger emails, update local caches keyed by shop, or invalidate/refresh sessions), this can lead to cross-tenant data corruption or injection of forged events attributed to a victim merchant — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any attacker who can install the target app on their own development/trial store (a normal, unprivileged action for public apps) since they only need to capture one legitimately signed webhook from their own shop and replay it with a modified `shop-domain` header — no access token, `api_secret_key`, or privileged access is required.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) headers as part of the signable string / HMAC computation, or otherwise cryptographically bind the shop identity to the signed payload before trusting `request.shop` in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets Shopify deliver a legitimate webhook (e.g. `orders/create`) to the app's callback URL, capturing the raw body `B` and the resulting `x-shopify-hmac-sha256` header value `H` (valid because `H = HMAC(client_secret, B)`).
2. Attacker resends the exact same HTTP request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but replacing `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` invokes the registered handler with `shop: request.shop == "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:189-199`), even though the payload actually originated from the attacker's own shop — demonstrating the forged, unauthenticated tenant binding.
