### Title
Webhook `shop-domain` and `topic` headers are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `Registry.process` validates only the HMAC of the body and then forwards the unauthenticated `shop`/`topic` values to the application's handler, breaking the binding between "the request that passed HMAC validation" and "the shop the data is attributed to."

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which returns only `@raw_body`. Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from HTTP headers with no cryptographic binding: [2](#0-1) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e., only the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` relies solely on this body-only HMAC check before dispatching the (unauthenticated) `shop` and `topic` values to the application's handler: [4](#0-3) 

The identity-binding equality that should hold is: `shop authenticated by HMAC == shop the handler/business logic attributes the payload to`. Here, the HMAC only proves "this body byte-string was signed by the app's secret at some point" — it says nothing about which shop or topic that body belongs to, because `shop`/`topic` are never part of the signed material. An attacker who owns/controls their own installed shop can trigger a real webhook delivery from Shopify containing attacker-chosen content (e.g., an `orders/create` payload with arbitrary customer data, since the merchant controls the order's fields), thereby obtaining a **genuinely valid** `(body, hmac)` pair signed with the app's real secret. They can then replay that exact body+HMAC to the same endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header with a victim shop's domain. `HmacValidator.validate` still passes (body unchanged), and `Registry.process` calls the handler with `shop: <victim shop>` and attacker-controlled body content, causing the host application to process/store attacker-chosen data as if it originated from the victim tenant.

### Impact Explanation
This is a cross-tenant data-integrity/identity-binding break: content the attacker fully controls (from their own shop's legitimate webhook delivery) can be relabeled and injected into another tenant's processing pipeline while still passing this gem's own signature verification. Any host application relying on this gem's `Registry.process`/`HmacValidator.validate` as the authenticity guarantee for `WebhookMetadata#shop` will incorrectly trust the shop attribution, enabling cross-tenant data injection — falling under the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation requires only: (1) the attacker operates or controls a shop with the target app installed (a normal, unprivileged merchant/developer capability), so they can trigger webhook deliveries with content of their choosing and capture a valid `(body, hmac)` pair from Shopify; and (2) the ability to send an arbitrary HTTP request to the victim app's public webhook endpoint with modified headers, which is trivial. No access to the app's `api_secret_key`, access tokens, or the victim's credentials is required.

### Recommendation
Include the security-relevant headers (`shop`, `topic`, at minimum) in the material that is cryptographically bound to the request, or independently verify `shop`/`topic` against a source of truth (e.g., the shop/topic combination registered via `Registry.add_registration`, or a lookup keyed by a value that is itself covered by the HMAC) before dispatching to handlers. At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are **not** authenticated by `HmacValidator.validate`, so consuming applications do not mistakenly treat them as verified.

### Proof of Concept
```ruby
# 1. Attacker installs the app on their own shop "attacker.myshopify.com" and
#    triggers a real webhook (e.g. orders/create) with attacker-chosen order data.
#    Shopify delivers a genuine (raw_body, hmac) pair signed with the app's real secret:
raw_body = '{"id": 1, "note": "arbitrary attacker-controlled content"}'
valid_hmac_base64 = "<captured from the real Shopify delivery>"

# 2. Attacker replays the exact body+hmac to the victim app's webhook endpoint,
#    but swaps the shop-domain header to the victim tenant:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac_base64,   # still valid: body unchanged
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, unauthenticated
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) passes because it only checks raw_body,
# and the handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker content)
``` [4](#0-3)

          received_signature = verifiable_query.hmac
