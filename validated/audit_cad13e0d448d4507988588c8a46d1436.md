Confirmed root cause: `Webhooks::Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) returns only `@raw_body`. The `shop`, `topic`, `api_version`, and `webhook_id` fields are read straight from HTTP headers (`shopify_header`, lines 20-33) and are **never included in the HMAC-signed data**. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) only recomputes the HMAC over `to_signable_string` (the raw body) and compares it — it never checks that the `shop` header matches anything. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-200`) then trusts `request.shop` and forwards it unauthenticated into `WebhookMetadata`, which is handed to the host app's handler as the tenant identifier.

Since Shopify webhook HMACs are computed with the app's single `api_secret_key`/`client_secret` shared across every shop that installs the app, any merchant who is a legitimate destination of real webhooks (e.g. shop A) possesses raw bodies with valid HMACs signed by that same app secret. Eve, who controls shop A, can capture any webhook Shopify sent to her (valid `hmac-sha256` + `raw_body`), then replay that exact body/HMAC pair to the app's webhook endpoint while substituting `shop-domain` (and optionally `topic`/`webhook-id`) with victim shop B's domain. `HmacValidator.validate` still succeeds because it only checks the body bytes, and `Registry.process` will dispatch the handler with `shop: "shopB.myshopify.com"` even though the payload never originated from B. This breaks the identity binding `shop authenticated == shop the bytes actually came from`, letting one tenant forge webhook events attributed to another tenant — a cross-tenant integrity violation matching the report's "field acted on but not covered by the HMAC" bug class.

### Title
Webhook `shop` (and `topic`/`webhook_id`) are not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are taken verbatim from unauthenticated HTTP headers. `HmacValidator` accepts the request as long as the body+HMAC pair is valid, regardless of which shop the headers claim it is from.

### Finding Description
`to_signable_string` returns `@raw_body` only: [1](#0-0) . The `shop` accessor reads directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding: [2](#0-1) . `HmacValidator.validate`/`validate_signature` verify only `verifiable_query.to_signable_string` against the supplied HMAC: [3](#0-2) . `Registry.process` trusts this unauthenticated `request.shop` value once the body HMAC checks out and forwards it as the tenant identifier to the app's handler: [4](#0-3) . Because the app's HMAC secret (`Context.api_secret_key`) is shared across every shop that installs the app, a valid `(raw_body, hmac)` pair captured from any one shop's real webhook can be replayed with a forged `shop-domain` header naming a different shop, and validation will still pass — the binding "authenticated shop == shop that produced the signed bytes" is broken.

### Impact Explanation
This crosses a tenant boundary: a merchant (or anyone who can capture one legitimate webhook delivery for their own shop) can make the host application process data under another merchant's shop identity, since `WebhookMetadata.shop` is derived from the unauthenticated header rather than anything cryptographically bound to the payload. Depending on how the host app's `WebhookHandler` uses `data.shop` (e.g., to select a session/store to update), this enables cross-tenant data corruption or an application to act on behalf of the wrong shop — a High/Critical-class cross-tenant integrity violation.

### Likelihood Explanation
Any actor who has (or previously had) a legitimate app install and thus receives real webhook deliveries for their own shop can capture a valid `(raw_body, x-shopify-hmac-sha256)` pair from Shopify's own delivery and simply resend it to the app's webhook endpoint with a different `x-shopify-shop-domain` header value. No secret material needs to be recovered — only header substitution on a replayed valid payload is required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the signed material, or otherwise verify the `shop-domain` header against an authenticated source (e.g., cross-check against a known/registered shop for that webhook subscription) before trusting `request.shop` in `Registry.process`. At minimum, document/enforce that `HmacValidator` must validate the full set of security-relevant headers, not just the raw body.

### Proof of Concept
1. App receives a genuine webhook for `shopA.myshopify.com`: raw body `B` with header `x-shopify-hmac-sha256: HMAC(secret, B)` and `x-shopify-shop-domain: shopA.myshopify.com`. This validates and is processed normally.
2. Attacker (who controls or observed a delivery to `shopA`) resends the identical body `B` and identical `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: shopB.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers (`lib/shopify_api/webhooks/request.rb:45-63`), `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and succeeds (`lib/shopify_api/utils/hmac_validator.rb:13-31`).
4. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: request.topic, shop: "shopB.myshopify.com", body: ..., ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to act on shop A's data under shop B's identity.
