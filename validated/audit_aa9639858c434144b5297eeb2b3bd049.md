This confirms the design: `VerifiableQuery#to_signable_string` is the only material verified by `HmacValidator.validate` [1](#0-0) , and `Webhooks::Request#to_signable_string` returns only `@raw_body`, while `Webhooks::Request#shop` is read from an unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header [2](#0-1) . `Registry.process` passes this unauthenticated `request.shop` straight into the `WebhookMetadata` handed to the host application's handler after only validating the HMAC of the body [3](#0-2) .

### Title
Webhook tenant identity (`shop` domain) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from the `x-shopify-shop-domain` HTTP header, but the HMAC signature validated by `Utils::HmacValidator` only covers the raw JSON body (`to_signable_string` returns `@raw_body`). The shop-domain header is never included in the signed material, so `Registry.process` binds handler-visible tenant identity to a value the HMAC does not attest to.

### Finding Description
`HmacValidator.validate` computes and compares an HMAC solely over `verifiable_query.to_signable_string` [4](#0-3) . For webhooks, `to_signable_string` is defined to return just the raw request body: `@raw_body` [5](#0-4) . The `shop` accessor, however, is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of that signed string [6](#0-5) .

`Registry.process` validates only the HMAC of the body, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build `WebhookMetadata` passed to the app's `handler.handle` [7](#0-6) . The intended binding is: `shop header value == shop cryptographically bound in the signed payload`. Because Shopify signs webhooks with the app's single `client_secret` shared across every shop that installs the app (not a per-shop secret), a byte-identical `(raw_body, hmac)` pair remains a *valid* signature no matter which shop-domain header accompanies it. An attacker who controls or observes any one legitimate webhook delivery for the app (e.g., from their own installed store) can replay that exact body+HMAC while substituting an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` will still return `true`, and the forged `shop` value will flow, unauthenticated, into the host application's webhook handler.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: `Utils::HmacValidator.validate` proves the *body* came from Shopify using the app's secret, but the code lets a caller-controlled header decide *which merchant* that body is attributed to. Any host application that uses `WebhookMetadata#shop` (as documented/intended) to scope database writes, redaction actions, or session lookups can be made to apply attacker-supplied JSON under a victim shop's identity — a cross-tenant access/injection primitive that maps to the report's "shop authenticated versus the shop bound in the verified payload" identity-binding failure.

### Likelihood Explanation
Exploitability only requires network access to the app's public webhook endpoint plus one legitimately obtained `(raw_body, hmac)` pair, which any merchant that installs the app (including the attacker, on their own store) can generate for themselves via ordinary events (e.g. `orders/create`). No `api_secret_key`, access token, or privileged account is needed — the attacker never learns the secret, they merely replay a signature that remains valid across shops because the secret is shared per-app, not per-shop, and the header carrying tenant identity is outside the HMAC.

### Recommendation
Bind the shop domain into the signed material checked by `HmacValidator`, or independently authenticate the header value against the caller's session/shop before use — e.g. include the `shop`, `topic`, and `webhook_id` headers in `Webhooks::Request#to_signable_string` (matching what Shopify actually signs, if Shopify includes them) or otherwise verify header authenticity, rather than trusting `x-shopify-shop-domain` unconditionally.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a real event (e.g. creates an order), receiving from Shopify a webhook POST with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker replays the identical POST to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body normally [8](#0-7) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(client_secret, B)` and finds it equal to `H`, so validation succeeds [9](#0-8) .
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker-controlled body `B`, even though `victim.myshopify.com` never sent this webhook [10](#0-9) .
