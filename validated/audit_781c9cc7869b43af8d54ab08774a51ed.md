### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the HMAC-verified payload solely from the raw request body, while the `shop` field used to attribute the webhook to a tenant is read from an unauthenticated header. Since Shopify signs a webhook body with the app's `client_secret`, which is shared across every shop that installs the app, an attacker who controls one shop (their own free/dev store with the app installed) can capture a validly-signed `(raw_body, hmac)` pair and replay it to the app's webhook endpoint with the `shopify-shop-domain` / `x-shopify-shop-domain` header changed to point at a victim shop. The signature still validates because the header is never part of the signed material, so the app processes attacker-controlled data under the identity of a different, arbitrary shop.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`: [1](#0-0) 

For incoming webhooks, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

But the `shop` accessor used to attribute the request to a specific tenant is read straight from the `shopify-shop-domain` HTTP header, entirely outside the signed material: [3](#0-2) 

`Webhooks::Registry#process` validates the HMAC over the body only, then hands the (unverified) `request.shop` straight to the handler as the tenant identity, without any cross-check that this shop actually matches the shop whose secret was used to sign the payload: [4](#0-3) 

The equality the gem implicitly relies on is:
`shop that produced/owns the HMAC signature == shop attributed in WebhookMetadata (request.shop)`

Because Shopify apps use a single `client_secret` per app (shared across every merchant install), any merchant who installs the app can obtain a body correctly signed with that same secret from their own store's genuine webhook deliveries. Nothing in this gem binds that signature to the specific shop domain that produced it — the "bytes verified" (raw body) and the "bytes trusted for tenant identity" (the `shop-domain` header) are disjoint. An attacker can therefore:

1. Install the target app on their own shop and let Shopify deliver a real webhook (e.g. `orders/create` with attacker-controlled order content), obtaining a genuine `(raw_body, hmac-sha256)` pair signed with the app's shared `client_secret`.
2. POST that same body/hmac to the app's webhook receiving endpoint, but with the `shopify-shop-domain` header rewritten to `victim-shop.myshopify.com`.
3. `HmacValidator.validate` passes (only the body is checked), `Registry#process` proceeds, and the handler receives `WebhookMetadata` claiming the payload originated from the victim shop, along with attacker-chosen body content.

This is a direct instance of "bytes verified versus bytes parsed": the signature guarantees the body's origin/integrity, but the host application (following this gem's documented API and `WebhookMetadata#shop`) is led to trust a completely separate, attacker-controlled channel (the header) for tenant attribution.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook processing: an unprivileged, unauthenticated internet user (any merchant capable of installing the target app in a free store) can make the host application process attacker-chosen data under another merchant's identity/session. Depending on the handler logic built by the host app on top of `WebhookMetadata#shop` (e.g., looking up and mutating the victim shop's stored session/data), this constitutes cross-tenant access, satisfying the Critical impact bar defined in scope ("cross-tenant access").

### Likelihood Explanation
Likelihood is high for any app that relies on this gem's webhook verification API as documented: it requires no leaked credentials, no TLS interception, and no privileged account — only the ability to install the target app on an attacker-owned store (a normal, unprivileged action) and to send an HTTP POST with a modified header to the app's public webhook endpoint.

### Recommendation
Bind the trusted `shop` identity to the signature verification itself instead of trusting an unauthenticated header:
- Extend `VerifiableQuery`/`to_signable_string` (or add a webhook-specific check) so the `shop-domain` is either included in the signed material, or cross-validated by looking up which shop's stored secret (if per-shop secrets are ever used) or registered shop actually produced the signature before it is exposed via `WebhookMetadata#shop`.
- At minimum, document/enforce that host applications must not use `request.shop` as an authoritative tenant identifier without independently verifying that the shop is one where the webhook topic/id was actually registered (e.g., cross-check against `Registration`/subscription records for that specific shop) before acting on the payload.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" with the app installed and
# receives a genuine webhook delivery from Shopify for that shop:
raw_body       = '{"id":1,"note":"forged"}'
genuine_hmac   = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"),
                                      ShopifyAPI::Context.api_secret_key, raw_body)

# Attacker replays the same (raw_body, hmac) to the victim's webhook receiver,
# only changing the shop-domain header:
headers = {
  "shopify-topic"        => "orders/create",
  "shopify-hmac-sha256"  => Base64.encode64(genuine_hmac),
  "shopify-shop-domain"  => "victim-shop.myshopify.com", # attacker-controlled, unsigned
  "shopify-webhook-id"   => "forged-id",
  "shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) => true, because only raw_body is signed.
# Handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker data)
```

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
