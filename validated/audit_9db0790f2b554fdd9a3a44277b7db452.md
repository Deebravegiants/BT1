### Title
Webhook `shop` domain is trusted from an unauthenticated header while only the raw body is HMAC-verified - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, but the tenant-identifying field (`shop`) that is handed to the application's handler is read directly from an HTTP header that is never covered by that HMAC. This breaks the binding "authenticated bytes == bytes the shop identity is derived from," analogous to the report's core pattern of an identity check being performed against the wrong/unbound value.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` and defines the signable string as only the raw body: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers, independent of that signature: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which internally calls `request.to_signable_string` (the raw body only) — it never incorporates `request.shop`: [3](#0-2) [4](#0-3) 

After that check passes, `request.shop` (from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header) is passed straight into `WebhookMetadata` and delivered to the app's handler, which the documentation explicitly tells developers to use for tenant-scoped work (e.g., `shop_domain: data.shop`): [5](#0-4) 

The equality that should hold is: `shop value authenticated by HMAC == shop value delivered to the handler`. In this design the left side does not exist — the HMAC never covers `shop` at all — so the value delivered to the handler is unauthenticated.

### Impact Explanation
Any entity capable of observing or replaying a single valid `(raw_body, hmac)` pair for a given topic — for example, a webhook the attacker's own installed shop legitimately received, or any body/HMAC pair leaked/logged/proxied somewhere — can resend that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary value in the `shop-domain` header. `Registry.process` will still validate the HMAC (since it only checks the body) and will hand the handler a `WebhookMetadata` claiming the payload belongs to the attacker-chosen shop. If the host application uses `data.shop` (as this gem's own documentation instructs) to select which tenant's database record/session to update, this results in cross-tenant data injection/confusion — one merchant's webhook data can be attributed to a different merchant's shop. This matches the "cross-tenant access" criterion for High/Critical impact.

### Likelihood Explanation
Likelihood is bounded by the need for the attacker to first obtain one legitimate `(body, hmac)` pair, which is trivially available to any developer/merchant with their own shop installed (a legitimate, low-privilege actor), or to anyone who can capture webhook traffic in transit/logs. No access to `api_secret_key` or any token is required — only a previously observed legitimate webhook delivery for any topic, which is realistic for an "unprivileged internet user" who is also a merchant on the platform.

### Recommendation
Include the tenant-identifying header (`shop-domain`) in the signed/verified payload used for HMAC validation — e.g., have `to_signable_string` incorporate the resolved `shop` (and ideally `topic`) alongside the raw body, or otherwise cryptographically bind the shop value to the verified payload before it is exposed via `WebhookMetadata`. At minimum, document prominently that `data.shop` is not authenticated by the HMAC check, so implementers do not use it as a trust boundary for tenant selection.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and receives a legitimate webhook for topic `orders/create` with raw body `B` and a valid header `x-shopify-hmac-sha256: H` (computed by Shopify over `B` using the app's real secret).
2. Attacker replays the exact same request to the app's webhook endpoint, but changes the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`, keeping body `B` and hmac header `H` unchanged.
3. `ShopifyAPI::Webhooks::Request.new` parses the modified headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(B, secret)` and compares it to `H` — this still matches, because `shop` is not part of `to_signable_string`.
4. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed(B), ...)`.
5. Any application logic keyed off `data.shop` (per the gem's own documented usage pattern) processes/stores `B`'s contents under the victim's tenant record, achieving cross-tenant data corruption without ever needing the app's `api_secret_key`, access token, or the victim's credentials.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
