I found a concrete vulnerability: the webhook `shop` identity is not covered by the HMAC signature, yet it is trusted as the tenant identifier for handler dispatch.

### Title
Webhook `shop-domain` Header Not Covered By HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, excluding the `shop-domain` (and `topic`) headers. `Webhooks::Registry.process` validates that signature and then trusts `request.shop`, taken straight from the unauthenticated header, as the tenant identity passed to the app's webhook handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of that signable string: [2](#0-1) 

`Registry.process` validates the HMAC over the body, and then unconditionally forwards `request.shop` to the registered handler as the tenant identity, with no cross-check that the shop is bound to the signed payload: [3](#0-2) 

`HmacValidator.validate` only verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string` (body-only), never touching `shop`: [4](#0-3) 

Because the HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is shared across every shop that has installed the app, any body+HMAC pair that is valid for one tenant is valid for **all** tenants. An attacker who legitimately installs the app on their own store (an unprivileged, self-service action) will receive genuine Shopify webhook deliveries containing a valid `(raw_body, hmac)` pair signed with the app's shared secret. Because this app's webhook endpoint is a public HTTP endpoint that must accept unauthenticated internet traffic (that's the entire point of webhook delivery), the attacker can freely replay that captured `(raw_body, hmac)` pair while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it never inspects the header), and `Registry.process` will dispatch the payload to the app's handler with `shop: <victim-shop>`.

This breaks the intended identity binding: `shop authenticated == shop used to attribute/store the webhook data`. The header is acted upon (used as the tenant key by the handler) but is not covered by the HMAC that is supposed to authenticate the message's origin.

### Impact Explanation
This enables cross-tenant confusion: a host application that trusts `WebhookMetadata#shop` (populated from `request.shop`) to select which tenant's records to update/create will process attacker-supplied data under a victim shop's identity, or an attacker-controlled webhook body will be persisted/acted upon as if it originated from a shop the attacker does not control. This matches the Critical "cross-tenant access" impact category, since the shop-scoping guarantee that the HMAC is meant to provide is bypassed entirely for the `shop` field.

### Likelihood Explanation
Any user can self-install the app on their own store to obtain a valid `(body, hmac)` pair signed with the shared app secret, since HMAC validity is independent of which shop it was issued for. The app's webhook endpoint is, by design, open to the public internet to receive Shopify's POSTs, so nothing prevents an attacker from re-sending a captured payload with an altered `shop-domain` header. No credentials, tokens, or privileged access are required beyond a free/unprivileged shop install.

### Recommendation
Bind the shop identity into the signed content, or independently authenticate it. Concretely: include the `shop-domain` header (and `topic`) in `Request#to_signable_string` so the HMAC covers them, and/or require the caller to check that `request.shop` matches a shop for which the app has a known/expected installation record before dispatching to the handler. At minimum, document clearly that `request.shop` is not cryptographically authenticated by `HmacValidator.validate` and must be independently verified by the host application against its own session/install store before being trusted as a tenant key.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, triggering a real webhook delivery, e.g. `orders/create`, to the app's webhook endpoint. The attacker captures the raw POST: `raw_body` and header `x-shopify-hmac-sha256: <valid-hmac>` (computed by Shopify using the app's shared `client_secret`), along with `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the exact same `raw_body` and `x-shopify-hmac-sha256` value to the same public webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged request; `to_signable_string` returns the unchanged `raw_body`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` with `Context.api_secret_key` and matches the (unchanged, still-valid) supplied HMAC — validation succeeds despite the shop header being forged: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, so the host application processes attacker-controlled webhook content attributed to the victim tenant.
