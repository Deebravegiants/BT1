### Title
HandlerV2 batch delivery falsely assumes tx-level success implies every inner message was delivered - ([File: tesseract/messaging/evm/src/tx.rs])

### Summary
The Linux `i2c: virtio` bug stemmed from the driver treating a single "notify" completion as proof that *every* queued buffer had finished, when the device could complete buffers individually or not at all. The same completion-granularity mismatch exists in Hyperbridge's EVM relayer: `submit_batch_messages` treats a non-reverting `IHandlerV2.batchCall` transaction as proof that *every* bundled ISMP message was delivered, while `EvmHost.dispatchIncoming` is explicitly designed to let individual message deliveries fail silently (module `onAccept`/`onGetResponse` reverts, or destination has no code) without reverting the enclosing transaction.

### Finding Description
`EvmHost.dispatchIncoming` (POST) and `dispatchIncoming` (GET response) deliberately swallow a failing downstream call so "the rest of the batch proceeds": [1](#0-0) [2](#0-1) 

`HandlerV2.handlePostRequests`/`handleGetResponses` call `dispatchIncoming` per message inside the batch, and multiple handler calls are bundled behind a single outer `batchCall(bytes[])` transaction (delegatecalls), as documented in the SDK tracking docs and in `tesseract/messaging/evm/src/tx.rs`'s own comment on `submit_batch_messages`: [3](#0-2) 

Crucially, when the batched path is used, the relayer hard-codes an empty "unsuccessful" bucket instead of checking whether each message's completion event (`PostRequestHandled`/`GetRequestHandled`) was actually emitted: [4](#0-3) 

Contrast this with the legacy serial path (`submit_messages`), which the developers correctly wrote to detect per-message failure by checking whether the message's expected event set is empty and only then marking it `unsuccessful`: [5](#0-4) 

`handle_message_submission` routes any batch of ≥2 messages through `submit_batch_messages`, i.e. the path that never populates `unsuccessful`: [6](#0-5) 

`result.unsuccessful` is the only signal the outbound pipeline uses to re-queue a message for retry via `park_undelivered`: [7](#0-6) 

So exactly like the virtio driver that assumed one notify meant all buffers were done (when the device could complete only some), the batched EVM submission path assumes one non-reverting `batchCall` transaction means all of its inner ISMP messages were delivered (when `EvmHost.dispatchIncoming` can silently fail a subset of them). Any message whose destination module's `onAccept`/`onGetResponse` reverts, or whose destination address has no code, is "completed" from the tx's point of view but was never actually delivered, and it is dropped from the retry/park bookkeeping entirely.

### Impact Explanation
A `PostRequest` (or `GetResponse` delivery) that is silently rejected inside a batched `batchCall` is never added to `unsuccessful`, so it is never parked for retry and produces no delivery-claim row. Its on-chain request receipt was correctly rolled back by `EvmHost.dispatchIncoming`, so in principle any relayer could resubmit it — but the off-chain tracking that normally drives resubmission (the `unsuccessful`/`park_undelivered`/retry-table flow) never surfaces it as pending. If the `PostRequest.timeout_timestamp` is `0` (no timeout, a value the protocol allows), the message can never time out either, so it is effectively frozen indefinitely: the source-side fee/escrow tied to that request is never refunded and the cross-chain action never completes. Even with a nonzero timeout, the message sits undelivered until timeout instead of the intended immediate-or-retried delivery, which for token-bridge/intents flows can mean assets are locked longer than the protocol's normal delivery guarantees promise. This matches "permanent freezing of funds" / "a route unable to deliver messages."

### Likelihood Explanation
No privileged action is required. Any application (module) that legitimately reverts inside `onAccept`/`onGetResponse` under some condition — a common, permitted pattern, since the ISMP model explicitly relies on failed `on_accept` calls being retryable — will trigger this whenever its message happens to be batched with other, successful messages in the same `batchCall` transaction (which is the default relayer batching behavior for ≥2 messages). This requires no adversarial control over the relayer, and can even be triggered unintentionally by ordinary destination-side application logic (e.g., temporary balance checks, reentrancy guards) failing once.

### Recommendation
In `submit_batch_messages` (`tesseract/messaging/evm/src/tx.rs`), stop assuming atomicity for the message-delivery outcome: after a successful `batchCall`, check per-message completion the same way `submit_messages` does — verify that each request/response's expected `PostRequestHandled`/`GetRequestHandled` event is present in `events`, and populate `unsuccessful` with any message whose event is missing, exactly mirroring the existing check in `submit_messages` (tx.rs:624-626). This restores the retry/park pipeline's ability to catch messages that `EvmHost.dispatchIncoming` silently failed to deliver inside a batch.

### Proof of Concept
1. Deploy an `IApp` module `M` on the destination chain whose `onAccept` reverts whenever `body[0] == 0x01` (a normal, permitted application behavior).
2. Dispatch two `PostRequest`s from the source chain in the same relayer batching window: request A targeting `M` with `body[0] == 0x01` (designed to revert) and request B targeting a normal, always-succeeding module, with `timeout_timestamp = 0` for request A.
3. The relayer's outbound task collects both into one batch and calls `submit_batch_messages`, which builds a single `IHandlerV2.batchCall` transaction.
4. `HandlerV2.handlePostRequests` calls `EvmHost.dispatchIncoming` for both; for A, the low-level call to `M.onAccept` fails, so `EvmHost.dispatchIncoming` deletes A's receipt and returns without reverting (`evm/src/core/EvmHost.sol:809-816`); for B, `PostRequestHandled` is emitted normally.
5. The outer `batchCall` transaction succeeds. `wait_for_success` returns the event set containing `PostRequestHandled` only for B.
6. `submit_batch_messages` returns `Ok((events, Vec::new(), new_epochs))` — `Vec::new()` regardless of A's silent failure (`tesseract/messaging/evm/src/tx.rs:536-538`).
7. `forward_request_delivery_claims`/`park_undelivered` never see request A as `unsuccessful`; because its timeout is `0`, A is never retried and never refunded — permanently stuck, even though the destination-side receipt shows it was never actually delivered.

            // so that it can be retried
            delete _requestReceipts[commitment];
            return;

/// Top-level submission entry.
///
/// - **Batch of 1** (e.g. the mandatory-consensus-only chunks from the outbound rotation catch-up)
///   routes through the legacy per-message [`submit_messages`] path. Wrapping a single call in
///   `IHandlerV2.batchCall` adds a self-delegatecall frame with no upside, costs extra gas, and
///   makes the receipt harder to interpret downstream.
/// - **Batch of ≥2** dispatches through [`submit_batch_messages`], the atomic
///   `IHandlerV2.batchCall` path. Chains whose handler doesn't implement `IHandlerV2` will revert
///   at the handler address — the legacy serial-submit fallback is no longer supported for real
///   batches.
pub async fn handle_message_submission(
	client: &EvmClient,
	messages: Vec<Message>,
) -> anyhow::Result<TxResult> {
	if messages.is_empty() {
		return Ok(TxResult::default());
	}

	let (receipts, unsuccessful, new_epochs) = if messages.len() == 1 {
		submit_messages(client, messages.clone()).await?
	} else {
		submit_batch_messages(client, messages.clone()).await?
	};
	let height = client.client.get_block_number().await?;
	Ok(build_tx_receipts(receipts, unsuccessful, messages, height, new_epochs))
}
