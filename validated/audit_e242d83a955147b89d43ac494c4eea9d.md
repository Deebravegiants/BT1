### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC that `Registry.process` verifies binds nothing but the body bytes. The `shop`, `topic`, `webhook_id`, and `api_version` values, which are all read straight from unauthenticated HTTP headers and handed to the host app's handler as trusted tenant/routing metadata, are never part of the signed data.

### Finding Description
`Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it against the `hmac` header value: [2](#0-1) 

For webhooks, `to_signable_string` is defined to be exactly `@raw_body`, i.e. the HMAC only ever certifies the message body, not any header: [3](#0-2) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from `shopify-*`/`x-shopify-*` headers that the caller (any internet client hitting the app's webhook endpoint) fully controls and that are never mixed into the signed string: [4](#0-3) [5](#0-4) 

These unauthenticated values are then forwarded verbatim into `WebhookMetadata`, which the host application's `WebhookHandler#handle` implementation relies on as the tenant/routing identity for the webhook payload: [6](#0-5) [7](#0-6) 

The identity binding that is broken: `shop authenticated by HMAC == shop trusted by the handler`. In reality, the HMAC only authenticates "this body was produced with our `api_secret_key`" — it says nothing about which shop, topic, or webhook id that body belongs to.

Because a single app has one `api_secret_key` shared across every installed shop, any merchant who has installed the app on their own store (an "unprivileged" tenant relative to other merchants) can legitimately trigger a webhook for their own shop, capture the resulting `(raw_body, hmac)` pair — which is valid forever for that exact body — and replay it to the same endpoint with the `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) header rewritten to point at a victim shop. `HmacValidator.validate` will still pass because it only checks the (unchanged) body against the (unchanged) hmac, and `Registry.process` will happily construct `WebhookMetadata` with the attacker-chosen `shop`, causing the host app to ingest and persist attacker-controlled body content under another tenant's identity.

### Impact Explanation
This breaks tenant isolation: an attacker who legitimately controls one shop's webhook traffic can forge webhooks that the host application will process as belonging to a different shop, injecting attacker-controlled JSON body content (e.g., fake order/product/customer data) into another tenant's data store, or triggering business logic (e.g., inventory updates, fulfillment actions, GDPR mandatory-webhook handling) against the wrong tenant. This is cross-tenant access/data injection achieved purely through gem-internal verification logic, without needing the app's `client_secret`, an access token, or any credential belonging to the victim, satisfying the Critical "cross-tenant access" bar.

### Likelihood Explanation
Likelihood is realistic: any developer/merchant who can install the target app on a store they control (a common, low-privilege capability for public/embedded Shopify apps) can capture one valid `(body, hmac)` pair from their own legitimate webhook traffic and immediately replay it with a modified `shop-domain` header — no cryptographic secret or brute force is required, only header rewriting in the replayed HTTP request.

### Recommendation
Bind the header fields into the signed material, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the verified body before trusting them:
- Include `shop`, `topic`, and `webhook_id` in the string that is HMAC-verified (Shopify's webhook HMAC is computed over the raw body only by design, so this requires the gem to independently bind these headers, e.g. by additionally verifying them against Shopify via an authenticated API call, or by requiring/validating them against a per-install allowlist of expected shop domains before dispatching to `handler.handle`).
- At minimum, `Registry.process` should validate that `request.shop` corresponds to a shop that actually has this app installed (known session/shop record) before invoking the handler, rather than trusting the header value implicitly once the body-only HMAC check passes.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger any subscribed webhook topic (e.g. `products/create`) so Shopify sends a real webhook request to the app's endpoint:
   ```
   POST /webhooks
   x-shopify-topic: products/create
   x-shopify-hmac-sha256: <valid HMAC of raw_body with app's api_secret_key>
   x-shopify-shop-domain: attacker.myshopify.com
   x-shopify-webhook-id: <id>
   x-shopify-api-version: 2024-01
   Body: {"id": 1, "title": "..."}
   ```
3. Capture this exact request (`raw_body` + `x-shopify-hmac-sha256` are unchanged).
4. Replay the same request to the app's webhook endpoint, changing only:
   ```
   x-shopify-shop-domain: victim.myshopify.com
   ```
5. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate(request)`, which validates `HMAC(secret, raw_body)` — unchanged — and passes: [8](#0-7) 
6. `handler.handle` is invoked with `WebhookMetadata#shop == "victim.myshopify.com"`, even though the payload originated from and was signed for `attacker.myshopify.com`: [9](#0-8)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
