## Confirmed Vulnerability

### Title
Webhook `shop-domain` header is trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies the webhook payload's HMAC over the raw body only, but the `shop-domain` header — which is used to attribute the webhook to a specific merchant/tenant — is never included in the signed material. An attacker who controls any Shopify shop that has the target app installed can generate a legitimately-signed webhook for their own shop, then replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header rewritten to a victim shop's domain. The HMAC check will still pass because it only validates the body bytes, letting the attacker's payload be processed as if it came from the victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the signed bytes: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)`, which calls `verifiable_query.to_signable_string` (i.e., only the body) and compares it against `verifiable_query.hmac`: [3](#0-2) 

After that single check succeeds, `Registry.process` immediately forwards `request.shop` — the unauthenticated header value — to the app's handler as the tenant identity for the webhook: [4](#0-3) 

The broken identity binding is: `hmac_valid(raw_body, secret) == true` is treated as proof that `shop-domain header == originating shop`, but the header is never part of the signed bytes, so these two are not actually bound together.

### Impact Explanation
Any user who can install the app on their own Shopify development/test store (a normal, unprivileged action available to any Shopify merchant) can obtain a validly-signed webhook body/HMAC pair for their own shop from Shopify's real webhook delivery. By replaying that request to the app's public webhook endpoint with the `shop-domain` header swapped to a victim shop, the app will process attacker-controlled JSON body content and hand it to the registered handler under the identity of the victim's shop (`WebhookMetadata#shop`) — an unrelated, unprivileged tenant impersonating another tenant's webhook stream. Depending on how the host application uses `WebhookMetadata.shop`/`body` (e.g., to update local records keyed by shop, trigger side effects, or write app data scoped to "shop"), this is a cross-tenant data-integrity/confusion issue: the attacker can inject fabricated webhook events attributed to a victim shop they do not control.

### Likelihood Explanation
Likelihood is High for any app that has at least one legitimate merchant install (including the attacker's own store) and exposes its webhook endpoint publicly, since:
- No secrets are needed — the attacker gets a real, correctly-signed body+HMAC pair from Shopify for events on their own shop.
- The only step required is rewriting one HTTP header before forwarding the request, which is trivial for any external caller (webhook endpoints are internet-facing).

### Recommendation
Bind the tenant-identifying header into the material that is HMAC-verified, or otherwise authenticate the `shop-domain` value independently of the raw header, e.g.:
- Include `shop-domain` (and ideally `topic`, `webhook-id`) as part of `to_signable_string`, matching however Shopify documents webhook signature coverage, or
- Cross-validate the header-derived shop against another already-authenticated source (e.g., known list of shops with active app installs plus additional Shopify-supplied signed claims), rejecting requests where the header shop cannot be corroborated.
- At minimum, treat `request.shop` as untrusted downstream and require host applications to reconcile it against their own installed-shop registry before using it for any state-changing action — and document this clearly, since the current API surface presents `shop` as if it were verified.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, obtaining legitimate webhook deliveries for real events (e.g., `orders/create`).
2. Attacker captures a genuine delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for secret `S` and body `B`), along with `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker crafts and sends a new HTTP request to the app's webhook endpoint with the same body `B` and same `X-Shopify-Hmac-Sha256: H`, but `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Request.new` parses headers/body successfully [5](#0-4) ; `Registry.process` calls `HmacValidator.validate`, which recomputes HMAC over `B` only and matches `H` [6](#0-5) , so validation succeeds.
5. `handler.handle` is invoked with `shop: "victim.myshopify.com"` and the attacker-controlled `body`, even though `victim.myshopify.com` never sent this webhook [4](#0-3) .

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
