### Title
Unswept native-token dust in `IntentGatewayV2.placeOrder` (Tron) leaves user ETH permanently stuck when paying fees via `swapETHForExactTokens` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` performs an `EXACT_OUT`-style native-token swap (`swapETHForExactTokens`) to acquire the protocol fee token, but — unlike the canonical EVM implementation — never accounts for or forwards the leftover native token that the Uniswap V2 router returns to the gateway contract after the swap. This is the same bug class as the referenced `PositionAction.sol#onCreditFlashLoan` finding: an `EXACT_OUT`/`EXACT_IN` swap consumes less than the amount supplied, and the residual is not routed back to the rightful owner, leaving it permanently trapped in the contract.

### Finding Description
`placeOrder` in `evm/tron/contracts/apps/IntentGatewayV2.sol` escrows the user's `order.inputs`, then if `order.fees > 0` and there is leftover native value (`msgValue > 0`), it swaps ETH for the exact fee-token amount needed: [1](#0-0) 

The call `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(order.fees, path, address(this), block.timestamp)` sends the **entire remaining `msgValue`** to the router, but `swapETHForExactTokens` only consumes as much ETH as needed to produce `order.fees` output tokens — the router refunds any unspent ETH back to `msg.sender` of the swap call, which is the `IntentGatewayV2` contract itself, not the original order-placer.

Critically, this function never captures the swap's returned `amounts[0]` (actual ETH spent) nor decrements `msgValue` by it, and there is no subsequent step forwarding any leftover native balance back to `msg.sender` (the user). This is in direct contrast to the sibling EVM implementation, which explicitly tracks and refunds this exact scenario: [2](#0-1) 

Note the `msgValue -= amounts[0];` and the final `if (msgValue > 0) { _sendValue(msg.sender, msgValue); }` block in the EVM contract — both of these are absent from the Tron contract's fee-swap branch, and no equivalent unspent-native refund exists anywhere else in `placeOrder` for the Tron contract.

Any user who overestimates the native ETH needed to cover `order.fees` (or supplies `msg.value` beyond the sum of native `order.inputs` plus the exact fee cost) will have that excess silently absorbed into the gateway contract's balance with no on-chain accounting path to reclaim it — precisely analogous to the `residualAmount` that goes unaccounted after an `EXACT_OUT`/`EXACT_IN` swap pair in the referenced report.

### Impact Explanation
This is a permanent freezing-of-funds bug reachable by any unprivileged user calling `placeOrder` with a native-token fee payment. Excess ETH sent to cover slippage/price uncertainty in `order.fees` swap becomes permanently stuck in the `IntentGatewayV2` contract with no mechanism (user-facing or governance) demonstrated in this code path to return it to the depositor. Given `placeOrder` is a primary, frequently used entry point (every order with `order.fees > 0` funded natively), this can affect a large volume of user funds over time.

### Likelihood Explanation
High. Users naturally supply `msg.value` with some safety margin over the exact ETH cost of `order.fees` (since the required input amount depends on the live Uniswap V2 price at execution time, which the caller cannot know exactly in advance). Any such margin is silently lost. No special conditions, timing, or privileged role is required — this triggers on ordinary use of the fee-paid, native-ETH `placeOrder` path.

### Recommendation
Mirror the EVM implementation's handling: capture the `amounts` array returned by `swapETHForExactTokens`, decrement `msgValue` by `amounts[0]`, and after all escrow/fee logic, refund any remaining `msgValue` to `msg.sender`:
```solidity
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
    order.fees, path, address(this), block.timestamp
);
msgValue -= amounts[0];
...
if (msgValue > 0) {
    (bool sent, ) = msg.sender.call{value: msgValue}("");
    if (!sent) revert InsufficientNativeToken();
}
```

### Proof of Concept
1. User calls `placeOrder` on the Tron `IntentGatewayV2` with `order.fees = F` (paid in native token) and no native-token entries in `order.inputs`, sending `msg.value = M` where `M > cost(F)` (the true ETH cost of `F` fee tokens at execution time).
2. Inside `placeOrder`, `msgValue = M` reaches the `order.fees > 0` branch (assuming no native `order.inputs` consumed it).
3. `swapETHForExactTokens{value: M}(F, path, address(this), ...)` executes; the router uses only `cost(F) < M` ETH and refunds `M - cost(F)` ETH to `address(this)` (the gateway).
4. `placeOrder` returns without ever reading the swap's `amounts[0]` or refunding the surplus; `M - cost(F)` remains permanently in the `IntentGatewayV2` contract's balance, unrecoverable by the user through any function visible in this contract.
