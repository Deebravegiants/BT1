## Analog Found

### Title
Late, un-snapshotted re-read of `ignore_user_centric_signups` allows a mid-signup config push to skip the real backend enrollment/dedup call - ([File: src/plans/mod.rs])

### Summary
This mirrors the C4 bstop_rate bug class: a value that determines how an already-accrued/computed state should be dispositioned is captured live at the *end* of a long-running process instead of being fixed/snapshotted at the *start* of that process, alongside the other decision inputs that were captured together. In orb-core, the analogous "config value read late instead of snapshotted" is `ignore_user_centric_signups`, which gates whether the Orb performs the actual backend enrollment/duplicate-detection call (`enroll_user::Plan`) for a signup.

### Finding Description
In `do_signup`, a batch of `Config` fields is destructured/snapshotted once at the very start of the signup transaction: [1](#0-0) 

This snapshot deliberately excludes `ignore_user_centric_signups`. The signup then proceeds through multi-second/multi-minute stages — QR scans, biometric capture, the biometric pipeline (iris/face inference), and fraud detection: [2](#0-1) 

Only at the very end, after all that work has produced a `signup_reason` (Normal/Fraud/Failure), does the code re-read the config live and branch on it: [3](#0-2) 

If `user_centric_signup && !ignore_user_centric_signups`, the code **never calls `enroll_user`** — it just trusts the locally computed `signup_reason` and marks `success = signup_reason == SignupReason::Normal`. Only the `else` branch invokes `enroll_user::Plan`, which is the code path that actually POSTs to the signup backend and polls for the real uniqueness/duplicate decision: [4](#0-3) [5](#0-4) 

Meanwhile, `Config` is mutated in place behind a shared `Arc<Mutex<Config>>` by a background task that polls the backend every `CONFIG_UPDATE_INTERVAL` and overwrites the whole config object, including `ignore_user_centric_signups`, with no relation to any signup in progress: [6](#0-5) [7](#0-6) 

Because the flag is captured at signup *start* for logging/telemetry via `debug_report`'s config clone, but re-read live at signup *end* to decide the enrollment path, a config change delivered by the backend mid-signup (between capture start and the final decision point) is applied inconsistently with the rest of the signup's snapshot — exactly analogous to `bstop_rate` being applied to interest that accrued under the old rate.

### Impact Explanation
If `ignore_user_centric_signups` flips from `true`→`false` while a signup is in flight, a signup that was expected to go through the real backend dedup/enrollment path (`enroll_user`, which performs iris-uniqueness checking via `signup_post`/`signup_poll`) instead takes the "trust local `signup_reason`" branch and is marked successful purely based on the orb-local (now largely stubbed-out — see `detect_fraud`, which always returns `false` in this build) fraud determination, without the server ever validating uniqueness for that signup. This is a genuine unauthorized/misattributed-signup risk: a person could be marked as a successfully enrolled/verified signup without the backend's iris-uniqueness/dedup check ever running, enabling duplicate or otherwise unauthorized enrollments to be locally accepted (`result.success = true`, `debug_report.signup_successful()`) despite bypassing the actual identity-binding step performed by the backend.

Conversely, flipping `false`→`true` mid-signup forces an enrollment call for a signup that the client had marked as app-centric (already handled client-side), which is a lesser but still real behavioral inconsistency (duplicated/unexpected enrollment attempts, resource use, and mismatched signup accounting) relative to what `debug_report`'s own persisted config snapshot recorded for that signup.

### Likelihood Explanation
Reachability is high in terms of code path: this is normal control flow, not a privileged/hardware/test-only code path, and does not require operator misbehavior — only a backend-driven config change occurring while a signup is in progress. Given the observed config polling loop (`CONFIG_UPDATE_INTERVAL`) and that biometric capture + biometric pipeline stages can span from several seconds to minutes (especially with signup extensions such as pupil contraction/focus sweep/mirror sweep), the timing window where a config re-fetch could land between snapshot and final decision is realistic. However, exploiting this to reliably force an unauthorized "successful" signup requires the operator/backend admin to actually toggle `ignore_user_centric_signups` during the narrow window of an in-flight signup, which is a backend-side condition outside orb-core's control; it is a config-race hazard rather than something a purely unprivileged local user can trigger deterministically on demand.

### Recommendation
Include `ignore_user_centric_signups` (and `user_centric_signup`'s counterpart decision inputs) in the single `Config` snapshot taken at the start of `do_signup`, and use that snapshotted value at the decision point at line 639, instead of re-locking and re-reading `orb.config` live after the biometric capture/pipeline/fraud-detection stages have already run. This ensures the entire signup transaction is evaluated consistently against the configuration that was in effect when the transaction began, mirroring the fix recommended for the analogous `bstop_rate` issue (snapshot state/config before using it to gate a decision that depends on prior computation).

### Proof of Concept
1. Backend serves `ignore_user_centric_signups = false` and the user's QR sets `user_data.user_centric_signup = true`.
2. Orb starts `do_signup`; the initial `Config` snapshot (line 497) does not carry `ignore_user_centric_signups`, only fields such as `self_serve`, `pcp_v3`, etc.
3. Orb runs `biometric_capture` and `biometric_pipeline` (multi-second to multi-minute duration), producing `signup_reason = SignupReason::Normal` from local (largely stubbed) fraud detection at line 564 (`detect_fraud` unconditionally returns `false` in `src/plans/mod.rs:1390-1406`).
4. During this window, the backend config poll (`observer.rs` `config_update`) refreshes the shared `Config`, and backend now also happens to reflect `ignore_user_centric_signups=false` still, or the flag flips — the crux is that line 639 re-reads `orb.config.lock().await.ignore_user_centric_signups` fresh, not the value captured with the rest of the transaction's decision inputs.
5. Because `user_centric_signup && !ignore_user_centric_signups` is true, the `else` branch calling `enroll_user::Plan` (the only path that talks to `signup_post`/`signup_poll` for real backend dedup) is skipped; `success` is set purely from `signup_reason == SignupReason::Normal`, and `debug_report.signup_successful()` is recorded — with no backend-side uniqueness check having executed for this signup.

This proof of concept demonstrates the reachable inconsistency window; full confirmation that the backend can push a differing `ignore_user_centric_signups` value specifically within a single signup's duration would require live/integration testing against the real config backend, which is outside static analysis.
