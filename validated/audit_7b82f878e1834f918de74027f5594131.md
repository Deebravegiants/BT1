### Title
Webhook `shop` identity is taken from an unauthenticated header while the HMAC only signs the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `X-Shopify-Shop-Domain` HTTP header, but `HmacValidator` only verifies the raw request body against the HMAC. The header is never covered by the signature, so the field that `Registry.process` treats as an authenticated tenant identifier is not actually bound to the cryptographic proof of authenticity.

### Finding Description
`Utils::HmacValidator.validate` computes and compares an HMAC over `verifiable_query.to_signable_string` only: [1](#0-0) 

For webhooks, `to_signable_string` returns only `@raw_body` — the shop domain, topic, webhook id, and API version headers are excluded from the signable content entirely: [2](#0-1) 

Yet `Request#shop` reads directly from the (attacker-controllable, unauthenticated) `x-shopify-shop-domain` / `shopify-shop-domain` header: [3](#0-2) 

`Registry.process` gates on `Utils::HmacValidator.validate(request)` succeeding, and — once it does — treats the request as fully authenticated, forwarding `request.shop` (the unauthenticated header value) to the app's handler as trusted tenant metadata: [4](#0-3) 

The identity binding that should hold is:
`shop used for tenant attribution (request.shop, from header)` == `shop whose secret/content actually produced the HMAC (implied only by raw_body, not bound to any shop claim)`

This equality does not hold: `Request#to_signable_string` never includes `shop`, `topic`, `webhook_id`, or `api_version`, so any of these header values can be swapped without invalidating the HMAC, as long as the body bytes stay identical.

### Impact Explanation
All apps built on this gem share one `api_secret_key`/HMAC key across every installed shop (this is how Shopify webhook HMACs work — the same app secret signs webhooks for every tenant of that app). A merchant who has installed the app on their own shop can trigger events to legitimately receive a validly-signed `(raw_body, hmac)` pair from Shopify. Because the header carrying `shop` is not part of the signed content, that same attacker can resend the identical body+HMAC to the app's webhook endpoint while substituting a different `X-Shopify-Shop-Domain` header value naming a *different* (victim) tenant that also uses the same app. `HmacValidator.validate` will still return `true` (it only checks the body), and `Registry.process` will hand the forged `shop` value to the app's `WebhookHandler#handle` as if it were verified — resulting in cross-tenant data/action confusion (e.g., an app that keys off `WebhookMetadata#shop` to look up a per-shop access token, update per-shop state, or attribute events could act on the wrong tenant's session/data). This falls under the Critical impact category of cross-tenant access, since the identity binding between "verified sender" and "claimed shop" is broken by the gem's own webhook verification primitive.

### Likelihood Explanation
The prerequisite is limited to being any merchant who has installed the target app (which is the standard actor model for cross-tenant confusion issues in a multi-tenant SaaS app) and knowing/guessing another shop's myshopify domain that also uses the app (often discoverable or guessable). No access token, `client_secret`, or privileged credential is required — only the ability to receive one's own legitimately signed webhook and replay it with a modified header to the app's public webhook endpoint. This is a realistic, low-effort attack path entirely enabled by the gem's own `Request`/`HmacValidator` design.

### Recommendation
Bind the shop (and ideally topic/webhook id) to the HMAC-verified content, not to an unauthenticated header:
- Either verify that `request.shop` matches an independently authenticated value (e.g., cross-check against the shop domain embedded in the JSON body or against the session lookup the app performs before trusting metadata), or
- Document/enforce that `WebhookMetadata#shop` must not be trusted as authenticated without an app-side secondary check, or
- Extend `to_signable_string`/verification to incorporate the shop-domain header into an app-level second factor before dispatching to `WebhookHandler#handle`.

### Proof of Concept
1. App "MyApp" is installed on `shop-a.myshopify.com` and `shop-b.myshopify.com`, sharing one `api_secret_key`.
2. Attacker controls `shop-a.myshopify.com` and triggers a webhook event (e.g. `orders/create`), receiving Shopify's POST to MyApp's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B`).
3. Attacker (or a MITM-less replay against the app's public endpoint, since it's a normal internet-reachable POST target) resends the exact same request to MyApp's webhook endpoint but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac`/`#shop` read from headers; `HmacValidator.validate` recomputes HMAC over `@raw_body` (unchanged) and it matches `H`, so validation passes: [5](#0-4) 
5. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: parsed_body(B), ...)`, causing MyApp to process shop-a's webhook payload as if it belonged to shop-b — a cross-tenant identity confusion enabled purely by the gem's verification logic never binding `shop` to the HMAC.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
