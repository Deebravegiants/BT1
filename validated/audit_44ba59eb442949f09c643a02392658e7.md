### Title
Predictable, unsigned session cookie value allows cross-tenant session hijacking - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
`ShopifyAPI::Utils::SessionUtils.current_session_id` and `cookie_session_id` treat the raw `shopify_app_session` cookie value as an authenticated session identifier, but this gem never signs, HMACs, or otherwise binds that cookie value to the shop that actually completed OAuth. The identifier itself is a fully deterministic, guessable string (`"#{shop}_#{user_id}"` or `"offline_#{shop}"`), so any unprivileged internet user can set this cookie value in their own browser to reference another merchant's session record.

### Finding Description
For the non-embedded (and embedded-without-JWT) flow, `ShopifyAPI::Auth::Oauth.begin_auth`/`validate_auth_callback` mint a `SessionCookie` whose `value` is simply `session.id` [1](#0-0) , and `Session.id`/`Session.from` construct that id deterministically as `"#{shop}_#{associated_user.id}"` or `"offline_#{shop}"` [2](#0-1) .

When the host application later needs to resolve "who is this browser," it calls `ShopifyAPI::Utils::SessionUtils.current_session_id`, which for the cookie-based path returns the raw cookie value untouched, with no cryptographic verification: [3](#0-2) [4](#0-3) .

Documentation confirms the intended usage: the returned `id` is meant to be used directly as a lookup key into the app's own session storage (`SessionRepository.store_session(session)` / retrieval by `session.id`), since this gem has no built-in storage of its own [5](#0-4) .

The equality this design implicitly relies on is:
```
shop bound to cookie value  ==  shop that completed OAuth and owns the stored access token at that id
```
But nothing enforces this equality. The cookie is not an opaque, unguessable, server-signed token — it's the literal composite key format. Any attacker who knows (or enumerates) a victim's `{shop}.myshopify.com` name and, for online sessions, a small integer `associated_user.id` (Shopify user ids are sequential/enumerable), can simply set their own `shopify_app_session` cookie to `"victim-shop.myshopify.com_123"` or `"offline_victim-shop.myshopify.com"`. `current_session_id` returns that exact attacker-chosen string with no verification, and a host app built per this gem's documented pattern will use it to fetch the corresponding `Session` (containing the victim's real access token) from its session store, then serve authenticated Admin API responses using the victim's credentials to the attacker's own request.

This differs from the JWT-based flow, where `session_id_from_shopify_id_token` at least derives the id from a cryptographically verified `Auth::JwtPayload` whose `dest`/`sub` claims are Shopify-signed [6](#0-5) . The cookie-based branch has no equivalent binding at all — the "session id" is derived from unauthenticated bytes supplied by whoever holds the socket, exactly the class of bug this task's rules call out.

### Impact Explanation
This breaks the tenant isolation the whole library is built around: an unprivileged internet user, with no credentials, access token, or `api_secret_key`, can cause the host application to load another merchant's stored `Session` (including its live `access_token`) purely by supplying a predictable string as a cookie value. That yields cross-tenant access — reading/writing another shop's data through the app using its access token — which maps to the Critical bucket ("cross-tenant access ... theft of a merchant access token" is not directly exfiltrated to the attacker, but the attacker's authenticated requests are serviced with the victim's token, which is functionally cross-tenant access).

### Likelihood Explanation
Exploitation only requires: (1) knowing the victim shop's `.myshopify.com` domain, which is public/enumerable, and (2) for online sessions, guessing a small numeric Shopify user id, or for offline sessions, no secondary value at all — `"offline_{shop}"` is trivially derivable from the shop name alone. No interception, no leaked secrets, and no privileged access are required, only that the host app follows this gem's documented cookie/session-id pattern (which the gem explicitly recommends since it does not provide its own session storage).

### Recommendation
- Never expose the raw storage key as the browser-facing session cookie value. Generate a random, unguessable, server-side session token (e.g., `SecureRandom` bytes) that is mapped internally to the deterministic session id, or
- Sign/HMAC the cookie value (session id + expiry) with `Context.api_secret_key` and verify the signature in `SessionUtils.cookie_session_id`/`current_session_id` before trusting it, rejecting any cookie whose signature doesn't match.
- Document prominently that `Session#id` must never be handed directly to the browser as a bare, unsigned cookie value.

### Proof of Concept
1. App uses this gem's documented flow: `begin_auth` → sets cookie `shopify_app_session=offline_victim-shop.myshopify.com` (or `victim-shop.myshopify.com_42` for an online session) for the *victim* merchant after real OAuth completes, and stores the corresponding `Session` (with real access token) in its own `SessionRepository` keyed by that same id, per `docs/usage/oauth.md`.
2. Attacker, in their own browser, manually sets the cookie `shopify_app_session=offline_victim-shop.myshopify.com`.
3. Attacker requests any authenticated route of the app.
4. Host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` → returns `"offline_victim-shop.myshopify.com"` unchanged (`lib/shopify_api/utils/session_utils.rb:19-37,68-71`).
5. Host app looks up `SessionRepository.load_session("offline_victim-shop.myshopify.com")`, retrieves the victim's real `access_token`, and uses it to serve the attacker's request — full cross-tenant access with zero credentials from the attacker.

          if is_online

        def current_session_id(shopify_id_token, cookies, online)
          if Context.embedded?
            if shopify_id_token
              id_token = shopify_id_token.gsub("Bearer ", "")
              session_id_from_shopify_id_token(id_token: id_token, online: online)
            else
              # falling back to session cookie
              raise Errors::CookieNotFoundError, "JWT token or Session cookie not found for app" unless
                cookies && cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]

              cookie_session_id(cookies)
            end
          else
            raise Errors::CookieNotFoundError, "Session cookie not found for app" unless
              cookies && cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]

            cookie_session_id(cookies)
          end
        end

## Session Persistence
Session persistence is deprecated from the `ShopifyAPI` library gem since [version 12.3.0](https://github.com/Shopify/shopify-api-ruby/blob/main/CHANGELOG.md#version-1230). The responsibility of session storage typically is fulfilled by the web framework middleware.
This API library's focus is on making requests and facilitate session creation.

⚠️ If you're not using the [ShopifyApp](https://github.com/Shopify/shopify_app) gem, you may use ShopifyAPI to perform OAuth to create sessions, but you must implement your own session storage method to persist the session information to be used in authenticated API calls.
