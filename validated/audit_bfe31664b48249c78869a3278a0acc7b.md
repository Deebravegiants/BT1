### Title
Webhook `shop` Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
The bug report's "missing status check on a value returned outside the covered/verified data" bug class maps to a concrete identity-binding break in this gem's webhook processing: the HMAC signature that authenticates an inbound webhook covers only the raw request body, while the `shop` identity that downstream handler code trusts is read from an unauthenticated HTTP header. This breaks the equality `bytes verified == identity acted upon`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 

`to_signable_string` returns only `@raw_body`, and `shop` is read from the `shopify-shop-domain` (or `x-shopify-shop-domain`) header, which is a plain, attacker-controllable HTTP header: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature strictly over `verifiable_query.to_signable_string`: [3](#0-2) 

`Webhooks::Registry.process` validates only this body-based HMAC, then forwards the unauthenticated `shop` header value straight into the tenant-identifying `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because the HMAC key (`api_secret_key`) is a single secret shared by the app across *all* shops that install it (not a per-shop secret), any unprivileged attacker who installs the target app on their own free/dev Shopify store can receive a legitimately-signed webhook. The attacker can then replay the exact same body/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header value with a victim shop's domain. `Utils::HmacValidator.validate` will still pass (it only checks the body), and the app's webhook handler will process the event as if it originated from the victim shop — breaking the identity equality `authenticated signer's shop == shop trusted by handler`.

### Impact Explanation
This is a cross-tenant identity spoofing vector: an attacker with no privileges on the victim's shop can make the app process webhook data (e.g. `app/uninstalled`, `customers/data_request`, `shop/redact`, or app-defined handlers keyed on `shop`) as if it came from the victim's store, potentially triggering cross-tenant side effects (data deletion, session invalidation, other shop-scoped writes) inside the host application. This matches the "Critical — cross-tenant access" impact bucket.

### Likelihood Explanation
Exploitation requires only: (1) installing the vulnerable app on an attacker-controlled Shopify development/trial store (free, requires no privileged credentials), (2) capturing one legitimately signed webhook delivery, and (3) replaying it with a modified `shop-domain` header. No access to the app's `client_secret` or any merchant's access token is needed, since the HMAC is verified purely against body bytes that the attacker already possesses unmodified.

### Recommendation
Bind the shop identity into the value that is actually authenticated. Include the `shop` (and/or `topic`, `webhook_id`) header value as part of the signed payload validated against the HMAC, or independently verify that the `shop-domain` header corresponds to a shop context that the host application has already established for the associated access token/session, before trusting `WebhookMetadata#shop` for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the target app on their own Shopify dev store `attacker-shop.myshopify.com`.
2. Attacker triggers a real webhook (e.g. `orders/create`) and captures the raw POST body `B` and the legitimate `X-Shopify-Hmac-SHA256` header `H` computed by Shopify over `B` using the app's `api_secret_key`.
3. Attacker sends a POST to the app's webhook endpoint with the same body `B`, the same `X-Shopify-Hmac-SHA256: H`, `X-Shopify-Topic: orders/create`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `@raw_body` (`B`) and matches `H` — validation succeeds.
5. The handler receives `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, and any app logic keyed on `shop` executes as though the event genuinely originated from the victim shop.
