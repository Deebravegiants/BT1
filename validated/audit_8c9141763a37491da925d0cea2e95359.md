## Title
Relayer fee ledger (`Fees<T>`) is zeroed unconditionally on dispatch, before the destination chain confirms payout — unbacked bad-debt / permanent-loss analog of the "last withdrawer" problem - ([File: modules/pallets/relayer/src/withdrawal.rs])

### Summary
`pallet-ismp-relayer`'s `withdraw()` treats the ISMP POST dispatch to a destination chain's `HostManager`/`EvmHost` as if it were the actual settlement, zeroing the relayer's internal `Fees<T>` ledger entry the instant the message commitment is written — not once the destination confirms the token transfer succeeded. This mirrors the reported bug class exactly: an internal accounting balance (`Fees<T>`) that is not reconciled against the real backing asset (the destination `EvmHost`'s `feeToken` balance), so whichever relayer's payout lands when that balance is insufficient effectively becomes the "last withdrawer" who absorbs a loss with no insurance fund or loss-socialization mechanism to recover it.

### Finding Description
Relayers accumulate a fee credit into `Fees<T>` (keyed by `(dest_chain, address)`) via `accumulate_fees`, which is fully backed 1:1 by state-proof-verified fee metadata read from the origin chain [1](#0-0) .

To realize that credit, `withdraw()` dispatches an ISMP POST to the destination's `HostManager` (or `HYPERBRIDGE_MODULE_ID` for substrate) instructing it to disburse `available_amount`, and **immediately zeroes the `Fees` entry right after the dispatch call succeeds — before any confirmation that the destination side actually transferred funds**: [2](#0-1) 

The pallet's own doc comment confirms this is fire-and-forget: "The on-chain effect is just dispatching the message; the destination chain settles the payout when the ISMP request is delivered there" [3](#0-2) .

On the destination, the payout is executed by `EvmHost.withdraw()`, which uses a plain `safeTransfer` from the host's `feeToken` balance with no reservation/escrow accounting against outstanding relayer claims: [4](#0-3) 

If that balance is insufficient, the transfer reverts — a failure mode the test suite explicitly exercises: `test_host_manager_insufficient_balance` shows the `onAccept`/`withdraw` path reverting when the host holds no fee tokens [5](#0-4) .

Because `Fees<T>` was already zeroed on Hyperbridge at dispatch time, and the destination-side `onAccept` failure causes the host to simply delete the receipt and let the message "stay deliverable" for later retry [6](#0-5) , the relayer's claim is left in limbo: it is no longer trackable in `Fees<T>` (so it cannot be re-derived or re-withdrawn through the normal flow), yet it was never paid out. There is no invariant anywhere in the pallet enforcing that the sum of all outstanding `Fees<T>` entries for a given `dest_chain` never exceeds that chain's actual `feeToken` balance, and no insurance/loss-socialization mechanism exists to make whichever relayer's withdrawal lands after the pool is drained whole again.

### Impact Explanation
Any relayer whose withdrawal request lands after the destination `EvmHost`'s `feeToken` balance has been drawn down below the sum of outstanding relayer claims permanently loses the accounting record of their earned fee (it's zeroed at dispatch, not at confirmed settlement) while receiving nothing on-chain — a direct loss of relayer-earned funds with no recovery path, identical in shape to the reported "last withdrawer" bad-debt scenario: early claimants succeed, later claimants absorb the shortfall, and the protocol has no insurance fund or socialization mechanism to fix it.

### Likelihood Explanation
This requires no privileged actor — any relayer that has legitimately earned fees can trigger `withdraw_fees` via an unsigned extrinsic once `accumulate_fees` credits them, and multiple relayers withdrawing concurrently from the same destination chain's finite `feeToken` balance is an ordinary, expected operating condition of the protocol (not an edge case requiring governance error or malicious insiders).

### Recommendation
- **Short term**: Do not zero `Fees<T>` until the destination confirms successful settlement (e.g., re-credit on a receipted timeout/failure callback, or keep the entry pending until a delivery-receipt proof is submitted back to Hyperbridge).
- **Long term**: Track a per-`dest_chain` reserved/outstanding-claims total and reconcile it against the destination host's actual `feeToken` balance before crediting further claims, or add an insurance/treasury backstop that can top up a destination host's balance when outstanding relayer claims exceed it, so no single relayer's withdrawal ordering determines whether they get paid.

### Proof of Concept
1. Two relayers, A and B, each accumulate legitimate fee credits into `Fees<T>` for `dest_chain = X` via `accumulate_fees`, each backed by real fee tokens paid on chain X when the respective requests were originally dispatched.
2. Relayer A calls `withdraw_fees`. The pallet dispatches the POST to chain X's `HostManager`/`EvmHost` and immediately zeroes A's `Fees` entry (`modules/pallets/relayer/src/withdrawal.rs:177`). Suppose chain X's `feeToken` balance is drained in the interim (e.g., by a legitimate governance revenue withdrawal via `EvmHost.withdraw`, or simply because A's and B's claims plus other legitimate relayer claims cumulatively exceed the balance actually resident on X at any given moment — nothing serializes/reserves against it).
3. Relayer B calls `withdraw_fees` for the same `dest_chain`. B's `Fees` entry is likewise zeroed on Hyperbridge before the destination-side transfer executes.
4. When B's dispatched POST is delivered to chain X, `EvmHost.withdraw()` calls `safeTransfer`, which reverts because the balance is now insufficient (as reproduced by `test_host_manager_insufficient_balance`). The host deletes the receipt per the documented failure-handling behavior, leaving the message "retryable" — but B has no `Fees<T>` record left on Hyperbridge to prove or re-trigger the claim, and no insurance mechanism exists to make B whole if chain X's balance is never replenished.

    /**
     * @dev withdraws host revenue to the given address, can only be called by cross-chain governance
     * @param params, the parameters for withdrawal
     */
    function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
    }

#[test]
fn test_host_manager_insufficient_balance() {
	let mut env = TestEnv::new();
	let manager = host_manager_of(&mut env);

	// Host has no fee tokens; withdraw attempt should fail on SafeERC20 transfer
	let params = WithdrawalParams {
		beneficiary_address: H160::random().as_bytes().to_vec(),
		amount: SubstrateU256::from(500_000_000_000_000_000_000u128),
		token: H160::from_slice(env.fee_token.as_slice()),
	};

	let post = router::PostRequest {
		source: StateMachine::Kusama(2000),
		dest: StateMachine::Evm(1),
		nonce: 0,
		from: env.sender.as_slice().to_vec(),
		to: vec![],
		timeout_timestamp: 100,
		body: params.abi_encode().expect("20-byte beneficiary"),
	};
	let evm_request: EvmPostRequest = post.into();

	let host_addr = env.host;
	let calldata = onaccept_calldata(evm_request, env.sender);
	let err = env
		.call_as_may_revert(host_addr, manager, calldata)
		.expect_err("expected revert");
	assert!(!err.is_empty(), "expected non-empty revert data");
}
