### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw HTTP body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by `Registry.process` to dispatch to a handler come from unauthenticated HTTP headers that are never included in the signed data.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read directly from HTTP headers with no cryptographic binding to the body or the HMAC: [2](#0-1) 

`Registry.process` validates only the HMAC of the body via `HmacValidator.validate`, then immediately trusts `request.shop`/`request.topic`/`request.webhook_id` to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`HmacValidator.validate` in turn only ever hashes `verifiable_query.to_signable_string`, i.e. the raw body, against `Context.api_secret_key`: [4](#0-3) 

This is the exact bug class in the report: a security-critical field (`shop`, the tenant identity used by the handler to key data/actions) is *acted on* by `Registry.process` but is *not covered by the HMAC* that is supposed to authenticate the request. The equality the code implicitly assumes but never enforces is:

```
shop_header (used for dispatch) == shop_that_produced_the_HMAC-signed_body
```

Because the `api_secret_key` is shared across every shop that installs the app, any merchant who installs the app can obtain a validly-signed webhook body for their own shop (e.g. by performing an action that triggers `orders/create` or a similar topic) and then replay that exact `body + hmac` pair to the app's webhook endpoint with a forged `x-shopify-shop-domain` (or `shopify-shop-domain`) header claiming to be a *different* shop. `Utils::HmacValidator.validate` will still pass (it only checks the body against the shared secret), and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` is the attacker-chosen value while `body` is genuine, causing the host application to process/attribute the payload to a shop that never sent it.

### Impact Explanation
This breaks the tenant-identity binding that host applications rely on `ShopifyAPI::Webhooks::WebhookMetadata#shop` to enforce data isolation between merchants (e.g., updating settings, provisioning resources, or crediting usage for "shop"). An attacker who is merely an installer of the app (no access token, no `api_secret_key`, no privileged account) can cause the app to process attacker-controlled webhook bodies under a victim shop's identity — a cross-tenant confusion/spoofing primitive, matching the "cross-tenant access" High-impact category in scope.

### Likelihood Explanation
Likelihood is constrained by the need to (a) install the app on at least one shop to obtain a legitimately-signed body/HMAC pair for a chosen topic, and (b) be able to POST that captured `body`+`hmac` pair to the app's public webhook endpoint with a different `shop-domain` header — both are actions available to any unprivileged internet user who can sign up for the app (no secrets or TLS interception required, since it's the attacker's own genuine webhook being replayed).

### Recommendation
Bind the identity fields to the signed payload, e.g. include `shop`, `topic`, and `webhook_id` in `to_signable_string` (as Shopify's HMAC actually only ever attests to the body — so instead the gem should cross-check `shop` against an independently-verified source, such as an active session for that shop, or reject processing unless the shop header matches a shop known to have an active/expected subscription) before invoking `handler.handle`.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; trigger a subscribed webhook topic (e.g., `orders/create`) to obtain Shopify's POST request containing `raw_body` and the valid `x-shopify-hmac-sha256` value (computed by Shopify with the app's `api_secret_key`).
2. Replay the identical `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but substitute `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `raw_body`: [5](#0-4) 
4. The handler receives `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: <attacker's genuine payload>, ...)` and the host application processes/attributes the event as coming from `victim-shop.myshopify.com`.
