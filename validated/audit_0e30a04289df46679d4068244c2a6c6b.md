### Title
Webhook shop identity not bound to HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop-domain` header to identify which tenant the webhook belongs to. Because the HMAC signature never covers the shop identity, a party that can obtain one valid `(body, hmac)` pair signed with the app's `client_secret` can replay it while substituting any victim shop's domain in the header, and the gem will hand that forged shop identity to the app's handler as authenticated data.

### Finding Description
`Webhooks::Registry.process` performs authentication like this: [1](#0-0) 

The only check is `Utils::HmacValidator.validate(request)`, which computes an HMAC over `request.to_signable_string`: [2](#0-1) 

`Webhooks::Request#to_signable_string` returns only the raw body (`@raw_body`), and `#shop` is read directly from an unauthenticated header, entirely independent of the HMAC: [3](#0-2) 

After the HMAC check passes, `Registry.process` builds `WebhookMetadata` using this unauthenticated `request.shop` value and passes it straight to the app's registered handler as trusted, tenant-identifying data: [4](#0-3) 

The identity-binding equality that should hold is: `shop_that_HMAC_authenticates == shop_the_handler_acts_on`. In this code, the left side is undefined (the HMAC never touches `shop`), while the right side is attacker-controlled via the `x-shopify-shop-domain` / `shopify-shop-domain` header. Because Shopify's `client_secret` (and thus the HMAC key) is the **same for every shop that has installed a given app**, any shop that has installed the app can capture a legitimate webhook delivery (valid body + valid HMAC for that secret) and replay the identical `(body, hmac)` pair to the app's webhook endpoint while forging the `shop-domain` header to name a different, victim shop that also has the app installed. `HmacValidator.validate` will report success, since it only recomputes the HMAC of the body, and `Registry.process` will invoke the handler believing the event genuinely originated from and pertains to the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged attacker who has installed the app on their own store can cause the app to process fabricated webhook data (body content of their choosing/timing) attributed to a different merchant's shop. Any handler logic that uses `data.shop` to select which tenant's records to update, deprovision, or notify (a common, encouraged pattern per this gem's own webhook docs) can be tricked into acting on the wrong tenant, corrupting or leaking that tenant's state, without ever needing that tenant's access token, session, or `client_secret`. This satisfies "cross-tenant access" under the Critical impact bucket, since a boundary between two authenticated-but-different shops is broken using only capabilities available to any regular (non-privileged) installer of the app.

### Likelihood Explanation
The prerequisite is simply that the attacker has installed the target app in their own shop (a normal, unprivileged action any Shopify merchant/developer can take) and can capture one legitimate outbound webhook delivery from Shopify (trivial, since Shopify sends these routinely, e.g. on `app/uninstalled`, `orders/create`, etc., to the same generic endpoint every installed shop shares). Forging the `shop-domain` header on an HTTP POST is trivial. No secret material, tokens, or elevated privileges are required, making this readily exploitable by any unprivileged internet user who is also an app installer.

### Recommendation
Bind the shop identity into the authenticated payload rather than trusting an unsigned header:
1. Do not rely on `request.shop` (header) alone as the tenant identity for handler dispatch; cross-check it against the `shop` domain embedded in the webhook body content Shopify provides where available, or maintain a per-shop mapping validated independently of the header.
2. Where feasible, incorporate the `shop-domain` header value into the HMAC verification step (or otherwise cryptographically bind it), so a `(body, hmac)` pair captured from shop A cannot be replayed with shop B's identity.
3. Update `docs/usage/webhooks.md` to explicitly warn implementers that `WebhookMetadata#shop` is not itself HMAC-authenticated and must not be used as the sole tenant-selection key without additional verification (e.g., confirming a corresponding active session/install record for that shop before applying webhook effects).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a normal, unprivileged install).
2. Shopify delivers a legitimate webhook (e.g., `orders/create`) to the app's shared webhook endpoint with headers:
   - `x-shopify-hmac-sha256: <valid HMAC of body B, signed with the app's client_secret>`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - body: `B`
3. Attacker captures this `(B, hmac)` pair.
4. Attacker (or any actor able to reach the endpoint) resends an HTTP POST to the same endpoint with:
   - body: `B` (unchanged)
   - `x-shopify-hmac-sha256: <same hmac>`
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
5. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` using the app's `client_secret` — it matches, since `B` and the key are unchanged; see [5](#0-4) .
6. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, per [4](#0-3) , causing the app to process attacker-controlled webhook content under the victim shop's identity.
