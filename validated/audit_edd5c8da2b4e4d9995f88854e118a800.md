### Title
Unrestricted `CallDispatcher.dispatch()` lets anyone execute arbitrary calls from the shared dispatcher, draining tokens/allowances left stranded outside the order's swept asset list - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch()` is a fully public function with no caller restriction that executes attacker-controlled `Call[]` (`to`, `value`, `data`) from the dispatcher's own context. This mirrors the `D3MMLiquidationRouter::D3Callee` pattern: a shared, persistent contract exposes an unauthenticated `target.call(data)` primitive. Because `CallDispatcher` is a long-lived singleton reused across every `IntentGatewayV2`/`HyperFungibleToken`/`WrappedHyperFungibleToken` order (not redeployed per call), and because the post-execution "sweep" only recovers balances of the tokens explicitly declared in the order's `inputs`/`output.assets`, any intermediate token, dust, or dangling ERC-20 allowance created by a predispatch/postdispatch swap is left exposed. Since `dispatch()` has zero access control, any third party can call it directly to pull that residual value out before the intended flow captures it.

### Finding Description
`CallDispatcher.dispatch()` has no modifier restricting the caller: [1](#0-0) 

It decodes an attacker-supplied `Call[]` and issues `to.call{value: call.value}(call.data)` for each entry with the dispatcher itself as `msg.sender` — the same "arbitrary external call" primitive as the reported `D3Callee` bug, except here there is no restriction at all (D3Callee at least required going through the liquidation flow's approve step; `dispatch()` doesn't even require that).

`CallDispatcher` is a shared, persistent contract address used by multiple apps (`IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`) and is documented as a stable, long-lived deployment: [2](#0-1) 

Its `receive()` accepts ETH from anyone unconditionally: [3](#0-2) 

During normal order processing, predispatch/postdispatch calldata routes tokens through the dispatcher and the protocol only sweeps back the balances of the tokens the order declares as `inputs`/`output.assets`: [4](#0-3) [5](#0-4) 

The docs explicitly acknowledge that this design leaves standing allowances at risk, because order-crafted `Call[]` entries commonly `approve()` DEX routers for large or unlimited amounts and only "should" use exact amounts — a convention, not an enforced invariant: [6](#0-5) 

Any multi-hop swap path (e.g., ETH → WETH → intermediate token → final token) that leaves a residual balance of a token not present in `order.inputs`/`order.output.assets`, or leaves a nonzero ERC-20 allowance from the dispatcher to a router that didn't fully consume it, permanently strands value on the dispatcher. Because `dispatch()` is callable by anyone with no restriction to the gateway contracts, any external actor can subsequently call `CallDispatcher.dispatch()` directly with a `Call[]` moving that stranded balance/allowance to themselves — functionally identical to the reported bug's `router.call(routeData)` drain, just triggered on the dispatcher rather than the liquidation router.

### Impact Explanation
Any token dust, native ETH sent to the dispatcher (via its unconditional `receive()`), or unconsumed ERC-20 allowance created during a predispatch/postdispatch swap can be swept by an unrelated third party rather than being captured as protocol dust or returned to the user/beneficiary. Since `CallDispatcher` is a shared, persistent contract reused across all orders and all supported apps, this is not a one-off/self-inflicted loss — it is a standing, protocol-wide drain vector reachable by any unprivileged address, satisfying the "concrete theft of funds" bar.

### Likelihood Explanation
Likelihood is high for any real usage that involves multi-hop DEX routing or non-exact-amount approvals in predispatch/postdispatch `Call[]` — a pattern the documentation itself anticipates and only discourages by convention rather than by code enforcement. An attacker only needs to monitor the `CallDispatcher` contract's token/ETH balances and outstanding allowances and race a single unrestricted `dispatch()` call.

### Recommendation
Restrict `CallDispatcher.dispatch()` to a whitelist of authorized callers (e.g., the `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` contracts) via an `onlyAuthorized` modifier, and/or make the dispatcher ephemeral (deployed per-call via `CREATE2`/minimal proxy and self-destructed or rendered inert after use) so no value or allowance can persist between transactions for an unauthenticated caller to claim.

### Proof of Concept
1. A user places an order whose `predispatch.call` swaps ETH → USDC → DAI through a multi-hop router, declaring only DAI in `order.inputs`.
2. The multi-hop swap leaves a small USDC remainder (rounding, partial fill, or an approve for `type(uint256).max` to the router that is not fully consumed) on the `CallDispatcher`.
3. `IntentGatewayV2`'s sweep logic only iterates `order.inputs`/`order.output.assets` (DAI), never touching the intermediate USDC balance/allowance: [7](#0-6) 
4. Attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: USDC, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, danglingBalance)})]))` directly — no authorization check prevents this — and receives the stranded USDC.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

            if (token == address(0)) {
                uint256 balance = dispatcher.balance;
                if (balance > 0) {

                    });

                }
