### Title
Direct-transfer donation to `StreamingYieldVault` bypasses the yield-vesting lock and lets an attacker instantly manipulate the exchange rate to steal from co-depositors - ([File: sdk/packages/core/contracts/vaults/StreamingYieldVault.sol])

### Summary
`StreamingYieldVault` computes its ERC-4626 exchange rate from the vault's raw asset balance minus a tracked "locked yield" amount. The locked-yield tracking only recognizes value added through the owner-only `addYield`/`onTransferReceived` path; a plain `asset.transfer()` (or `transferAndCall` from any non-owner) directly to the vault address inflates `balanceOf(this)` without being registered as a vesting tranche, so it is counted as immediately-realized `totalAssets()`. This is the same root-cause pattern as the Yearn Finance yUSDT incident: the contract's share-price/reserve calculation trusts a balance that can be independently inflated outside the code path the accounting model assumes, letting an attacker manipulate the exchange rate for profit.

### Finding Description
`totalAssets()` is defined as: [1](#0-0) 

and the "not yet vested" deduction is computed purely from the internal `_vestingAmount`/`_vestingStart` state set by `_startVesting`, which is only ever invoked from the owner-gated `addYield` or the owner-source-checked `onTransferReceived`: [2](#0-1) 

Critically, `_lockedYield()` has no way to know about, or discount, assets that entered the vault's balance through any other means than these two gated calls. Since the underlying asset is a standard ERC-20 (and, per the contract's own doc-comment, may additionally be ERC-1363), *anyone* — not just the owner — can call `IERC20(asset()).transfer(vault, amount)` directly. That transfer increases `IERC20(asset()).balanceOf(address(this))`, which `totalAssets()` reads unconditionally, but it is never added to `_vestingAmount`, so `_lockedYield()` doesn't discount it. The result: an arbitrary, un-vested balance increase is instantly and fully reflected in the ERC-4626 exchange rate (`totalAssets()/totalSupply()`), in the very same block.

This directly defeats the module's stated security invariant, documented in its own header: [3](#0-2) 

The comment claims "no single block can be sandwiched around a yield event," but that claim only holds for yield added via `addYield`. A raw donation is a same-block, unvested exchange-rate jump — the exact "yield sniping" the contract was designed to prevent, now achievable by anyone with a wallet, for free (no owner privilege required), since deposits/mints are only blocked (`maxDeposit`/`maxMint` = 0) *while a tranche added via `addYield` is vesting*: [4](#0-3) 

A donation performs none of the state changes that would trip this guard, so deposits/withdrawals remain fully open around it.

### Impact Explanation
This is directly analogous to the Yearn yUSDT incident's root cause: a reserve-balance value used to compute a share/exchange rate can be pushed by an unprivileged actor through a path the accounting logic does not track, letting the attacker mint or extract value disproportionate to their actual claim. Concretely: an attacker can front-run a pending honest deposit, donate assets directly to the vault to spike `totalAssets()`/share instantly, causing the honest depositor's subsequent `deposit()`/`mint()` to receive far fewer shares than the fair value of their input (their assets are absorbed into the inflated share price), then the attacker redeems their own shares for a proportional cut of the honest depositor's assets. This is a same-transaction/same-block, no-privilege attack path — the class of exploit the design's virtual-share offset (`DECIMALS_OFFSET`) mitigates only for the classic *first-depositor* inflation case, not for this ongoing "donate mid-cycle to reprice existing shares" vector, since the offset does not prevent balance manipulation after the vault already has supply.

### Likelihood Explanation
High reachability: any address holding the underlying asset can call a plain ERC-20 `transfer` to the vault with no permission checks, no owner gating, and no interaction with `addYield`'s cooldown/window guards. The only requirement is timing a transaction to land between another user's deposit submission and its inclusion (standard MEV/front-running), which is routine on public EVM chains. No consensus proof, relayer, or governance action is needed — a single unprivileged transaction plus ordinary block-ordering control is sufficient.

### Recommendation
Track the vault's "accounted" balance explicitly (e.g., a running total updated only by `_startVesting`/withdrawals) instead of deriving `totalAssets()` from the raw `balanceOf(this)`. Any balance above the accounted total should either be swept/ignored by `totalAssets()` or explicitly folded into the next vesting tranche rather than being recognized immediately. This closes the gap between the "yield can only enter through `addYield`" design assumption and the actual ERC-20 transfer semantics that make that assumption false.

### Proof of Concept
1. Vault `V` holds `100` underlying tokens, `totalSupply() = 100e6` shares (post virtual-offset scaling), so price-per-share ≈ 1.
2. Honest user `H` submits `deposit(1000)` intending to receive ≈`1000e6` shares.
3. Attacker `A`, seeing `H`'s pending tx in the mempool, front-runs with: `asset.transfer(V, 100000)` — a plain ERC-20 transfer, not `addYield` (which is `onlyOwner` and would revert for `A`).
   - `IERC20(asset()).balanceOf(V)` jumps by `100000`.
   - `_lockedYield()` is unaffected (no `_vestingAmount` was set), so `totalAssets()` — [1](#0-0)  — immediately reports the inflated balance.
   - Price-per-share jumps roughly 1000x in the same block.
4. `H`'s `deposit(1000)` now executes against the inflated price, minting `H` a negligible number of shares for their `1000` tokens.
5. `A` redeems their existing shares immediately after, capturing a share of `H`'s deposited `1000` tokens proportional to `A`'s holdings — profit extracted from `H` with no economic loss (net) to `A` beyond gas and the donated principal returned to them via their own share of the pool.

This mirrors the Yearn incident's mechanism: an unprivileged actor manipulates a balance the contract's exchange-rate math implicitly trusts as fully-accounted, producing value extraction disproportionate to legitimate deposits.

    /// @dev Linear unlock of the current tranche, keyed on `block.timestamp` so that a deposit
    ///      and withdrawal within the same block observe an identical, unchanged share price.
    function _lockedYield() internal view returns (uint256) {
        uint256 start = _vestingStart;
        uint256 elapsed = block.timestamp - start;
        if (elapsed >= VEST) return 0;
        return (_vestingAmount * (VEST - elapsed)) / VEST;
    }
    
    /// @notice Add a new yield tranche, pulled from the caller. Reverts unless the previous
    ///         tranche has fully vested, which guarantees tranches never overlap and no yield
    ///         is ever left permanently locked.
    /// @param amount The amount of `asset` to stream in over `VEST`.
    function addYield(uint256 amount) external onlyOwner {
        // Pull the funds first so `balanceOf` already reflects `amount` before it is marked
        // locked; otherwise `totalAssets` would transiently underflow when a tranche exceeds
        // the current backing (e.g. the very first `addYield` on a near-empty vault).
        IERC20(asset()).safeTransferFrom(msg.sender, address(this), amount);

        _startVesting(amount);
    }

    /// @dev Arms a new tranche after validating the no-overlap / deposit-window guards. The caller
    ///      must have already moved `amount` of `asset` into the vault (so `balanceOf` reflects it
    ///      before `_vestingAmount` is set, avoiding a transient `totalAssets` underflow).
    function _startVesting(uint256 amount) private {
        if (amount == 0) revert ZeroAmount();

        uint256 start = _vestingStart;
        if (start != 0) {
            if (block.timestamp < start + VEST) revert YieldStillVesting(start + VEST);
            // Hold off until the guaranteed deposit window has elapsed, so new capital always has
            // a chance to enter between tranches regardless of how promptly the keeper runs.
            if (block.timestamp < start + VEST + MIN_WINDOW) revert DepositWindowOpen(start + VEST + MIN_WINDOW);
        }

        _vestingAmount = amount;
        _vestingStart = block.timestamp;

        emit YieldAdded(amount, block.timestamp);
    }
