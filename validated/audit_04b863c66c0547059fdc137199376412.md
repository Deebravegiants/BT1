### Title
Webhook `shop` identity is read from an unauthenticated header while the HMAC only signs the raw body, allowing shop-domain spoofing in webhook processing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The bug class in the referenced report is about a value used to determine payout/identity (the provision-count-derived rate) not being bound by the same cryptographic check that legitimizes the transaction, letting an attacker manipulate an unchecked dimension to break the "each party gets what its share should mean" invariant. The analogous binding here is: `hmac == sign(body)` should also guarantee `shop == the tenant the signed body belongs to`, but in this gem that binding does not exist.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes `shop` straight from the `X-Shopify-Shop-Domain` / `Shopify-Shop-Domain` HTTP header: [1](#0-0) 

but the HMAC that this same class computes/validates only covers the raw request body, never the shop-domain (or topic, or api-version) header: [2](#0-1) 

`Utils::HmacValidator.validate` simply verifies `HMAC(secret, to_signable_string)` against the supplied signature: [3](#0-2) 

The equality the gem should guarantee is:
`hmac_valid?(body) == true` implies `shop_reported_in_header == shop_that_body_was_generated_for`

but the gem only checks `hmac_valid?(body)`; `shop` is taken from a header that is not part of the signed material, exactly analogous to the audited bug where a value (`nbOfPositions`) that determines who gets credited/how much is not constrained relative to the value that is cryptographically checked (`interests == minInterestsToRepay`).

Because Shopify signs webhooks with the app's single shared `api_secret_key` (identical for every shop that has installed the app), any unprivileged user who installs the app on their own store legitimately receives valid `(raw_body, hmac)` pairs signed with that same secret. That user can then replay the exact same body+hmac to the app's webhook endpoint while substituting the `Shopify-Shop-Domain` header with a victim shop's domain. `ShopifyAPI::Webhooks::Request#shop` will happily report the victim's domain even though the HMAC-verified bytes are the attacker's own webhook payload — the gem provides no method or check that ties the two together.

### Impact Explanation
If the host application (as the gem's own documentation instructs) uses `Webhooks::Request#shop` to select which tenant/session record to look up, mutate, or credit as a result of a "validated" webhook, an attacker can forge the tenant identity of an otherwise legitimately-signed request. This is a cross-tenant identity confusion: the signature guarantees "this body was produced with our secret" but not "this body belongs to shop X", letting one tenant's traffic be attributed to another tenant purely because the shop attribute lives outside the signed envelope.

### Likelihood Explanation
Any user can self-serve install the app on their own development/test store (no special privilege, no leaked credentials, no `api_secret_key` needed by the attacker), capture a legitimate webhook `(body, hmac)` pair, and replay it against the app's public webhook endpoint with a modified shop header. This requires only standard, unprivileged interaction with the app's public HTTP endpoint.

### Recommendation
Bind the shop identity to the HMAC-verified material rather than trusting an out-of-band header: include the shop domain (and ideally webhook id / topic) inside `to_signable_string`, or require the host app to independently corroborate `shop` against a value obtained from `parsed_body` before it is used to select which tenant's data to act on. At minimum, document prominently that `Request#shop` is unauthenticated and must never be used as the sole basis for selecting which shop's resources to modify.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com`; the app is configured with a single shared `api_secret_key`.
2. Shopify sends the attacker's store a legitimate webhook: body `B`, header `Shopify-Shop-Domain: attacker.myshopify.com`, header `Shopify-Hmac-Sha256: HMAC(secret, B)`.
3. Attacker replays `POST /webhooks` to the app with the same body `B` and same valid HMAC header, but sets `Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `hmac` validates successfully via `HmacValidator.validate` (checks only `B`), and `.shop` returns `"victim.myshopify.com"` because it is read straight from the (attacker-controlled) header, per [4](#0-3)  — the host application acting on `request.shop` now processes attacker-supplied data as if it belonged to the victim shop.
