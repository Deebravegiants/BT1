### Title
`DirectBridge.describeWithdrawal` reports `completed` unconditionally even when `ft_transfer_call` with attacker-supplied `msg` causes a token refund/redirect - (File: `packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts`)

### Summary
`createWithdrawIntentPrimitive` builds an `ft_withdraw` intent that, when `routeConfig.msg` is set, becomes a NEP-141 `ft_transfer_call` with `min_gas` intentionally omitted, and `DirectBridge.describeWithdrawal` unconditionally returns `{ status: "completed", txHash: args.tx.hash }` without inspecting the actual outcome of that call. This lets an unprivileged caller construct a withdrawal whose tokens are refunded or redirected by the receiving contract's `ft_on_transfer`, while the SDK still reports `completed`.

### Finding Description
The broken equality: "tokens credited to `destinationAddress`" should equal "`amount`" whenever `describeWithdrawal` reports `status: "completed"`. This equality is not enforced.

Code path:
- `createWithdrawIntentPrimitive` (`packages/intents-sdk/src/bridges/direct-bridge/direct-bridge-utils.ts:43-60`) — when `params.msg !== undefined`, it builds `ft_withdraw` with `msg: params.msg` and `min_gas: undefined` (the comment at line 57-59 explicitly documents that gas consumption becomes "unpredictable" once `msg` is set, turning the intent into a NEP-141 `ft_transfer_call`). [1](#0-0) 
- `DirectBridge.createWithdrawalIntents` passes `args.withdrawalParams.routeConfig?.msg` straight through with no size/shape validation. [2](#0-1) 
- `DirectBridge.validateWithdrawal` only checks that `destinationAddress` is a valid NEAR address, is not the token contract itself, and (for explicit accounts) exists — it never inspects `msg` nor checks whether the receiver actually accepts/keeps the tokens. [3](#0-2) 
- `DirectBridge.describeWithdrawal` hard-codes `completed` regardless of what happened inside the NEAR transaction/receipts. [4](#0-3) 

By contrast, every other bridge adapter (`PoaBridge`, `OmniBridge`, `HotBridge`) queries an external status source (indexer/API/contract view) before reporting `completed`, and can return `pending`/`failed` if delivery is not confirmed. [5](#0-4) 

Root cause: for a NEP-141 `ft_transfer_call`, the receiving contract's `ft_on_transfer` can return an "unused amount" (or the whole amount), which triggers `ft_resolve_transfer` on the token contract to refund that amount back to the *predecessor* of the transfer call — i.e., `intents.near` itself — as a follow-up receipt after the `ft_withdraw` intent's outer transaction has already succeeded. The outer NEAR transaction (whose hash is `args.tx.hash`) still finalizes successfully because a benign "no-op" return from `ft_on_transfer` (or even a failing receiver call that the token contract catches) doesn't revert the outer transaction. `DirectBridge.describeWithdrawal` has no logic to inspect these follow-up receipts, so it reports `completed` with that same `tx.hash` irrespective of whether the tokens actually landed at `destinationAddress` or were bounced back.

Exploit input: attacker calls `IntentsSDK.processWithdrawal` with `createNearWithdrawalRoute({ msg: <2KB JSON blob> })`, `assetId = "nep141:eth.bridge.near"`, and `destinationAddress` = some existing NEAR account whose `ft_on_transfer` refunds unused tokens (this is normal, standards-compliant NEP-141 receiver behavior, not malicious code). None of `validateAddress`, `compareAddresses`, `validateWithdrawal`, or `supports()` block this, because they check only address format/existence, not economic outcome of the transfer.

### Impact Explanation
The SDK reports `status: "completed"` with a genuine `txHash` while the actual token delivery to `destinationAddress` did not occur (tokens were refunded to `intents.near` or redirected per the receiver's `msg`-driven logic). An integrator that treats `completed` as proof of delivery (as `watchWithdrawal` does — it resolves the poll on `status === "completed"`) could credit the withdrawal as successful and, when the user disputes non-receipt, credit/refund it again — a double-credit/misreport scenario. This matches the "status or hash misreport making an integrator credit or refund twice" High-severity category. It is repeatable per withdrawal call and costs the attacker only the withdrawal amount plus normal transaction fees. [6](#0-5) 

### Likelihood Explanation
Preconditions: the caller needs an `assetId` that is a NEP-141 token routed via `NearWithdrawal`, a `destinationAddress` that is an existing NEAR account implementing `ft_on_transfer` (standard for any NEP-141-integrated contract), and any `msg` payload (size/shape unchecked, up to whatever the transaction size limits allow). No special privileges, contract admin access, or malicious RPC/relayer is required — this is a purely a client-side SDK call with attacker-controlled `msg`/`destinationAddress`, matching the "unprivileged caller" threat model. The only remaining question is whether `intents.near`'s own `ft_withdraw` handling is guaranteed to succeed the outer transaction even when the inner `ft_transfer_call` triggers a refund; this is standard NEP-141 semantics (refunds happen asynchronously via `ft_resolve_transfer` and do not revert the initiating transaction), which is consistent with why the SDK code explicitly warns about "unpredictable gas consumption" for this exact `msg` case.

### Recommendation
`DirectBridge.describeWithdrawal` should not unconditionally return `completed`. When the withdrawal intent used `msg` (i.e., `ft_transfer_call`), the SDK should inspect the transaction's receipts/logs for the actual NEP-141 transfer events (e.g., `ft_transfer` logs indicating amount delivered to `destinationAddress` vs. refunded to `intents.near`) before reporting `completed`, or otherwise surface a distinct status/warning that delivery could not be confirmed. Additionally, `createWithdrawIntentPrimitive`/`DirectBridge.createWithdrawalIntents` should validate or bound `msg` size and clearly document/flag (or reject) `msg`-carrying NEAR direct withdrawals whose completion status cannot be reliably determined.

### Proof of Concept
Vitest plan (mocks only HTTP/RPC, no code changes):
1. `createWithdrawIntentPrimitive` unit test (already partially covered by existing test) — assert that with `msg: "<2KB JSON>"`, the produced intent has `intent === "ft_withdraw"`, `msg` set to that blob, and `min_gas === undefined` (extending the existing test at `direct-bridge.test.ts:220-232` with a 2 KB payload).
2. `DirectBridge.describeWithdrawal` integration test:
   - Construct a `WithdrawalIdentifier` with `tx: { hash: "near-tx-hash", accountId: "test.near" }`.
   - Call `bridge.describeWithdrawal(wid)`.
   - Assert `result` equals `{ status: "completed", txHash: "near-tx-hash" }` — this passes today unconditionally, demonstrating the equality break: there is no code path in which this result depends on whether the FT actually reached `destinationAddress` or was refunded via `ft_resolve_transfer`. Add a second scenario mocking (via `nearProvider.query`/tx status) a receipt trail showing the FT amount refunded to `intents.near` instead of transferred to `destinationAddress`, and assert (currently failing) that `describeWithdrawal` should NOT return `completed`, or should return a different `txHash`/status reflecting the refund — confirming the SDK cannot currently distinguish "delivered" from "refunded".

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
