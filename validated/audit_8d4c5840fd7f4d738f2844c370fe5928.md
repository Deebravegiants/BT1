Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `shop-domain`, `topic`, and `webhook-id` HTTP headers — none of which are covered by that signature — to build the `WebhookMetadata` object handed to the host application's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, whose `to_signable_string` only returns `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers, independent of the HMAC: [2](#0-1) 

`HmacValidator.validate` computes and compares the signature only against `to_signable_string` (the body), never against headers: [3](#0-2) 

`Registry.process` treats a valid body-HMAC as sufficient authentication, then passes the unauthenticated `request.shop` header straight into `WebhookMetadata`, which is delivered to the app's registered handler as the trusted tenant identifier: [4](#0-3) [5](#0-4) 

This is the exact bug class from the report: a field ("shop") is acted upon (used as the tenant key passed to the handler) while it is not covered by the integrity check (HMAC only signs the body). The binding that is broken is:

`shop authenticated by HMAC == shop delivered to handler`

but in reality the code only guarantees:

`body authenticated by HMAC != shop delivered to handler`

### Impact Explanation
Because the signature never binds the `shop-domain` header to the body, any party who possesses one valid `(body, hmac)` pair from Shopify (e.g., from a webhook fired for their own, legitimately-installed shop/tenant) can replay that exact body+HMAC to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` header value. `Registry.process` will accept it as authentic (HMAC still validates, since it only checks the body) and invoke the registered handler with `WebhookMetadata#shop` set to the attacker-chosen shop domain. Any host application that uses `data.shop` from the handler to select the tenant record, credentials, or database scope to write into — the documented and expected usage pattern for this field — will act on attacker-supplied tenant identity while believing it is Shopify-authenticated. This is a cross-tenant confusion vector at the trust boundary this gem is responsible for (Critical: cross-tenant access), since the library itself is what asserts "this webhook's `shop` is authentic" via `Utils::HmacValidator.validate` succeeding.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one genuine `(body, hmac)` pair — achievable by legitimately installing the app on their own shop (a normal, unprivileged onboarding step for any public/multi-tenant Shopify app) and capturing one of the webhooks Shopify sends them. No `api_secret_key`, access token, or privileged access is needed; only a normal merchant-level relationship with the app. This is a realistic, unprivileged-internet-user path given the requirement is "install as a shop, receive one webhook."

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed material that `HmacValidator` verifies, or otherwise cryptographically bind them to the HMAC (e.g., verify against a canonicalized string containing both headers and body, matching what Shopify actually signs if it does so on its side), instead of only checking the raw body in `to_signable_string`. At minimum, document loudly that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are unauthenticated and must not be trusted for tenant selection without additional verification (e.g., cross-checking against the shop stored for the session tied to the topic).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook, e.g. for `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `api_secret_key`).
2. Attacker replays the exact same request to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com` (a shop that also has the app installed), keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — this still passes. [6](#0-5) 
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: JSON.parse(B), ...)` and invokes the app's handler with this forged shop value, even though the body `B` genuinely originated from `attacker.myshopify.com`. [7](#0-6) 
5. If the host app's handler uses `data.shop` to select which tenant's records to update (the documented pattern for `WebhookMetadata#shop`), the attacker has caused a cross-tenant write/read confusion using only their own legitimate webhook credentials.
