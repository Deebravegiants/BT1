### Title
Unchecked ERC-20 return value in IntentGatewayV2 (Tron) escrow withdrawal and dust sweep - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2` on the Tron target uses a raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` to move escrowed tokens to solvers/beneficiaries, checking only that the call did not revert (`success`) but never decoding/validating the returned `bool`. This is exactly the unsafe-ERC20-transfer pattern flagged in the report: non-reverting ERC-20s that return `false` on failure will silently "succeed" while moving zero tokens, yet the escrow accounting proceeds as if the transfer worked.

### Finding Description
In `withdraw()`, the escrow release path does: [1](#0-0) 

Each iteration calls `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` and only reverts if `success` is false (i.e., if the low-level call itself reverted). It never inspects the returned data to confirm `transfer()` actually returned `true`. Regardless of whether the transfer moved funds, `_orders[body.commitment][token] -= amount` is unconditionally executed, permanently marking that portion of the escrow as redeemed.

The same unchecked pattern appears in the `SweepDust` incoming-request handler: [2](#0-1) 

and again for transaction-fee redemption inside `withdraw`: [3](#0-2) 

This directly contrasts with the rest of the codebase, including the non-Tron `IntentGatewayV2`/`ExtrinsicIntents` fill path in `evm/src/apps/intentsv2/ExtrinsicIntents.sol`, which consistently uses OpenZeppelin's `SafeERC20.safeTransferFrom`: [4](#0-3) 

and the Tron file itself imports `SafeERC20` and does `using SafeERC20 for IERC20;` yet does not apply it to these outbound transfer sites: [5](#0-4) 

### Impact Explanation
`withdraw()` is reached both from the ISMP-delivered `RedeemEscrow`/`RefundEscrow` paths in `onAccept` (any relayer can deliver a valid cross-chain message that triggers this) and potentially from local same-chain fills. If the escrowed input token is a non-standard ERC-20 that returns `false` instead of reverting on failure (e.g., due to a blacklist, paused state, or insufficient allowance edge case introduced by upgradeable/proxy tokens), `success` from the low-level call will still be `true` (the call executed without reverting), so the function proceeds to decrement `_orders[...]` and emit `EscrowReleased`/`EscrowRefunded` even though the beneficiary received nothing. The result is permanent loss of the escrowed funds — the tokens remain stuck in the contract with no path to reclaim them, since the accounting has already zeroed out the entitlement. The `SweepDust` path has the identical flaw for protocol-collected dust.

### Likelihood Explanation
This is reachable by any unprivileged relayer delivering a `RedeemEscrow`/`RefundEscrow` post request (standard intents flow) or by governance triggering `SweepDust`, using any ERC-20 token configured as an order input/output asset that deviates from strict-revert-on-failure `transfer()` semantics. No special privileges are required beyond normal participation in the intents/escrow protocol, and such non-compliant ERC-20 tokens are common enough in practice that this is a realistic path to fund loss rather than a purely theoretical one.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` handler with `SafeERC20.safeTransfer()` (the contract already imports `SafeERC20` and declares `using SafeERC20 for IERC20;`), consistent with the rest of the codebase (e.g. `ExtrinsicIntents.sol`'s use of `safeTransferFrom`). This reverts on both call failure and on tokens that return `false`, preventing the escrow accounting from advancing when the underlying transfer did not succeed.

### Proof of Concept
1. Configure/select a non-standard ERC-20 as an order's input/output token (e.g., a token that returns `false` on `transfer()` failure instead of reverting — such tokens exist among widely used assets).
2. A solver fills the cross-chain order; escrow accounting records `_orders[commitment][token] += amount` as usual (unaffected by this bug).
3. Once the request finalizes, `onAccept` is invoked with `RequestKind.RedeemEscrow`, calling `withdraw(body, false)`.
4. Cause the `transfer()` call to return `false` without reverting (e.g., beneficiary is blacklisted by the token, or contract token balance briefly manipulated to induce a soft-fail path some tokens implement).
5. `token.call(...)` returns `success == true` (the call executed), so the code does not revert; `_orders[commitment][token] -= amount` proceeds and `EscrowReleased` is emitted, even though the beneficiary's balance never increased.
6. The escrowed tokens remain locked in the `IntentGatewayV2` contract with no accounting path left to redeem them — permanent loss of funds for the beneficiary/solver.
