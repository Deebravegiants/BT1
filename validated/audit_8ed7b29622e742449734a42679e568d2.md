### Title
Webhook `shop` domain (and topic/api-version) are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop`, `topic`, `webhook_id`, and `api_version` header values when dispatching to the merchant-supplied handler. Because these identity fields are never part of the signed payload, any party who can obtain one validly-signed webhook body (e.g., a legitimate merchant receiving webhooks for their own store) can replay that same body to the app's webhook endpoint while swapping the `x-shopify-shop-domain` header to a victim shop, producing a request that passes HMAC validation yet is attributed to the wrong tenant.

### Finding Description
The signable content for a webhook request is defined as only the raw body: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers, independent of the signature: [2](#0-1) 

`HmacValidator` only ever authenticates `to_signable_string`, i.e. the body — never the headers: [3](#0-2) 

`Registry.process` checks the HMAC and then immediately builds `WebhookMetadata` using the *unauthenticated* `request.shop`/`request.topic`/`request.webhook_id` values, handing them to the app's handler as trusted tenant-identifying data: [4](#0-3) 

This breaks the intended binding: `HMAC(secret, body) == valid` should imply `shop header == the shop that produced this body`. In reality the equality only proves `body` is untampered; the `shop` header can be any value chosen by whoever replays the request.

### Impact Explanation
Any actor who can capture a legitimately-signed webhook payload — most simply, a merchant who has installed the app and thus legitimately receives real, correctly-HMAC'd webhooks from Shopify for their own store — can resend that exact body to the app's public webhook endpoint with a forged `x-shopify-shop-domain` (or `shopify-shop-domain`) header pointing at a different, victim shop. Because the gem only re-validates the body's HMAC and never binds it to the shop header, the forged request is accepted and routed to the handler as if it originated from the victim shop. Depending on how the host app keys its business logic off `WebhookMetadata#shop` (session lookup, entitlement checks, order/customer state updates, `app/uninstalled` handling, etc.), this enables cross-tenant data confusion/injection — an attacker-controlled event is processed under another merchant's identity.

### Likelihood Explanation
Exploitation requires no privileged credentials, access tokens, or the app's `client_secret` — only possession of the app on the attacker's own (unprivileged) shop, which is the normal state for any merchant who installs the app, or interception of any single legitimate webhook. The webhook endpoint is public by design (it's how Shopify delivers webhooks), so the replay is trivially reachable over the internet.

### Recommendation
Include the identity-binding header(s) — at minimum `shop-domain` (and ideally `topic`/`webhook_id`) — in the signed payload used for HMAC verification, or independently verify that the `shop` header corresponds to a shop session/installation known to the app before trusting it in `WebhookMetadata`. Alternatively, cross-check the shop domain against Shopify's webhook delivery metadata (e.g., via a per-shop webhook secret or a registered mapping of webhook id → shop) rather than trusting the raw header value.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets Shopify deliver a real webhook (e.g. `orders/create`) to the app, with a valid `x-shopify-hmac-sha256` computed by Shopify over the JSON body using the app's shared `client_secret`.
2. Attacker captures the raw body and the valid HMAC header from this delivery.
3. Attacker resends an HTTP POST to the same webhook endpoint with the identical body and HMAC header, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb:13-22` validates because it only hashes `raw_body`, which is unchanged.
5. `ShopifyAPI::Webhooks::Registry.process` in `lib/shopify_api/webhooks/registry.rb:189-200` proceeds and calls the handler with `shop: "victim.myshopify.com"`, even though the payload actually originated from the attacker's own store.
