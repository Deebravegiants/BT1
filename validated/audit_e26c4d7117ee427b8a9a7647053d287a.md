### Title
BLS aggregate/subset public keys are never checked for the identity (infinite) point before signature verification, letting a forged all-zero signature satisfy the pairing check - (File: modules/utils/bls-utils/src/bls.rs, modules/consensus/sync-committee/verifier/src/crypto.rs)

### Summary
Hyperbridge's BLS aggregation helpers (`aggregate_public_keys` in [1](#0-0)  and `subtract_points_from_aggregate` in [2](#0-1) ) sum/subtract decompressed G1 points and pass the result straight to `bls::verify` without ever checking whether the resulting aggregate is the identity element (point at infinity). This is the exact bug class described in Teku's CL-2021-30: `aggregate()` silently returns the infinite point whenever the summed/subtracted keys cancel out, and a verifier that doesn't special-case this will accept the "identity" signature for *any* message as valid.

### Finding Description
The consensus verifiers that rely on BLS aggregate signatures — `sync-committee` (Ethereum light client, [3](#0-2) ), `bsc` ( [4](#0-3) ), and `pharos` ( [5](#0-4) ) — all compute an aggregate/subset public key by folding individual `BlsPublicKey`s with elliptic-curve point addition/subtraction, then hand the resulting point to `bls::verify`/`bls::fast_aggregate_verify`. None of these code paths check that the resulting aggregate is not the group identity (the point at infinity) before using it in the pairing check.

For the sync-committee verifier specifically, the non-participant subset is chosen by the attacker via `sync_committee_bits` in the untrusted `VerifierStateUpdate` ( [6](#0-5) ), and the resulting `aggregate = subtract_points_from_aggregate(&sync_committee.aggregate_public_key, &non_participant_pubkeys)` is used directly. If this arithmetic ever nets to the identity point (a mathematically possible outcome any time cancelling subsets of real committee keys are chosen, or if a malicious/compromised sync-committee member's registered public key is itself the identity point — which is a validly-encoded compressed G1 point, not something `bls::pubkey_to_point`'s length/format check would reject), then per the pairing identity `e(g1, σ) = e(apk, H(m))`, an attacker only needs to supply the trivially-computable identity signature (σ = point at infinity in G2) to make the equation hold for **any** message, with **no** knowledge of any validator's private key.

The `bls-utils::aggregate_public_keys` function's own doc comment only guards against keys that "fail to decompress" — it explicitly does not address the orthogonal case where all keys decompress successfully but their sum is the identity ( [7](#0-6) ). This mirrors CL-2021-30's precise root cause ("If one of the public keys to aggregate is invalid...", "If the sum of (valid) public keys happens to be zero").

### Impact Explanation
If exploitable, this allows forging a valid consensus update/finality proof without any real validator signatures — i.e., unsound state commitment / forged message delivery into `pallet-ismp`'s consensus client. Since `sync-committee`'s `verify_sync_committee_attestation` result is consumed by `beacon_client.rs`'s `verify_consensus` to update the intermediate state commitment used by ISMP for cross-chain state proofs ( [8](#0-7) ), a successful forgery could let an attacker inject an arbitrary finalized header/state root, enabling unauthorized state-membership proofs and downstream fund theft (mint/withdraw forgery) via HandlerV2/EvmHost message delivery.

### Likelihood Explanation
Exploitability is uncertain and likely low in practice for the reasons below, which I could not fully resolve given index limits:
- Producing a genuinely cancelling subset from real, honestly-generated committee/validator BLS keys has negligible probability by chance.
- The realistic attack vector requires an attacker-influenced validator/committee-member public key equal to (or the negation of) another key, or the literal identity point, being accepted into the trusted validator/committee set upstream (via BSC's epoch `extra_data.validators`, Pharos's staking-contract storage proof `ValidatorInfo`, or the sync-committee's SSZ-proven `SyncCommittee.public_keys`) without an explicit "not-identity / in correct subgroup" check at registration time.
- I could not inspect the external `bls` crate's `pubkey_to_point`/`verify` implementation (not vendored in this repo) to confirm whether it independently rejects infinity-encoded or non-subgroup points during decompression — this is the decisive factor for whether the bug is actually reachable, and it is outside what the codebase index can show me.

### Recommendation
Explicitly reject the identity/point-at-infinity result after every aggregation and subtraction in `bls-utils::aggregate_public_keys`, `sync-committee`'s `subtract_points_from_aggregate`, and the BSC/Pharos aggregate-key helpers, returning an error before calling `bls::verify`. Additionally, validate at validator/committee-registration time (BSC epoch header parsing, Pharos storage-proof decoding, sync-committee SSZ decoding) that no individual `BlsPublicKey` is the identity point or an otherwise degenerate encoding.

### Proof of Concept
Not constructible from the available code alone: exploitation depends on (a) whether the external `bls` crate's point decompression accepts the infinity encoding as "valid" (unverified — crate not present in the indexed repo), and (b) whether any of the three validator-set ingestion paths (BSC extra-data, Pharos storage proof, sync-committee SSZ) allow an attacker-influenced key to be the identity point or a canceling pair. Given these unresolved dependencies, I cannot provide a concrete end-to-end PoC; a Devin session with full repository/dependency access would be needed to confirm reachability.

/// Aggregate multiple BLS public keys into a single public key.
///
/// Any input key that fails to decompress is propagated as an error
/// rather than silently dropped — otherwise a caller's participant
/// count would diverge from the aggregate, letting an attacker pad the
/// quorum with junk keys that contribute nothing to the signature.
pub fn aggregate_public_keys(keys: &[BlsPublicKey]) -> Result<Vec<u8>, BLSError> {
	let mut aggregate = G1ProjectivePoint::default();
	for key in keys {
		aggregate = aggregate + pubkey_to_projective(key)?;
	}
	Ok(bls::point_to_pubkey(aggregate.into()))
}

pub fn subtract_points_from_aggregate(
	aggregate: &BlsPublicKey,
	points: &[BlsPublicKey],
) -> Result<G1ProjectivePoint, BLSError> {
	let aggregate = pubkey_to_projective(aggregate)?;
	let points = points
		.iter()
		.map(|point| pubkey_to_projective(point))
		.collect::<Result<Vec<_>, _>>()?;
	let subset_aggregate = points.into_iter().fold(aggregate, |acc, point| acc - point);
	Ok(subset_aggregate)
}

/// Verify the BLS aggregate signature.
fn verify_bls_signature(
	participants: &[BlsPublicKey],
	block_proof: &BlockProof,
	block_proof_hash: H256,
) -> Result<(), Error> {
	if participants.is_empty() {
		return Err(Error::NoParticipants);
	}

	let aggregate_pubkey =
		bls_utils::aggregate_public_keys(participants).map_err(Error::BlsError)?;

	// The message signed is the block_proof_hash
	let message = block_proof_hash.as_bytes().to_vec();

	let is_valid = bls::verify(
		&aggregate_pubkey,
		&message,
		&block_proof.aggregate_signature,
		&PHAROS_BLS_DST.as_bytes().to_vec(),
	);

	if !is_valid {
		return Err(Error::InvalidSignature);
	}

	Ok(())
}
