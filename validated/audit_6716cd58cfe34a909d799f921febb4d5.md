### Title
Webhook shop-domain, topic, and webhook-id headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authentic once `Utils::HmacValidator.validate(request)` succeeds, then passes `request.shop`, `request.topic`, and `request.webhook_id` — none of which are covered by that signature — straight to the app's handler as trusted identity/routing data.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all read from HTTP headers that are never mixed into the signed material: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. it authenticates the body bytes, not the headers: [3](#0-2) 

`Registry.process` uses this validation result as the sole gate before trusting `request.shop` and `request.topic` and forwarding them to the app's handler: [4](#0-3) 

The identity binding that should hold is: `shop header used by handler == shop cryptographically bound to this exact HMAC`. Because `api_secret_key` is a single, app-wide secret shared across every shop that installs the app (not a per-shop secret), any merchant who has installed the app can legitimately trigger a webhook for their own store, capture the `(raw_body, X-Shopify-Hmac-Sha256)` pair Shopify sent them, and replay that exact body/HMAC pair to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) with a victim shop's domain. `HmacValidator.validate` still succeeds because the signature only ever covered the body, so `Registry.process` calls the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` reporting the victim shop's domain and/or an arbitrary topic — even though the payload actually originated from the attacker's own store.

### Impact Explanation
Any handler logic that trusts `WebhookMetadata#shop` (or `#topic`) post-validation — e.g. looking up that shop's stored session/access token, writing data keyed by shop, or dispatching to different app logic per topic — can be made to act on behalf of a victim tenant using attacker-supplied payload content. This crosses the tenant boundary this gem is meant to enforce (each webhook is supposed to originate from, and be attributable to, the shop identified in the request), qualifying as cross-tenant access.

### Likelihood Explanation
The attacker only needs to be an ordinary merchant with the target app installed on their own store (an "unprivileged" party from the gem's perspective — no access token, `client_secret`, or credential theft required), plus the ability to send arbitrary HTTP requests to the app's public webhook endpoint. Capturing a `(body, hmac)` pair from a webhook fired on their own shop and replaying it with a different `shop-domain`/`topic` header is trivial and requires no cryptographic work.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the signed material verified by `HmacValidator`, or otherwise require the host application to independently authenticate/authorize the shop identified in `WebhookMetadata` (e.g., cross-check against a shop the app actually has an active session for, and treat the header only as a hint) rather than treating `request.shop`/`request.topic` as verified merely because `Utils::HmacValidator.validate(request)` returned true.

### Proof of Concept
1. App is installed on attacker-owned shop `attacker.myshopify.com` and on victim shop `victim.myshopify.com`.
2. Attacker triggers any event (e.g., `orders/create`) on their own store and captures Shopify's legitimate webhook request: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for secret `S`, which is the same `api_secret_key` for every install of this app).
3. Attacker POSTs to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally a different `X-Shopify-Topic`).
4. `Utils::HmacValidator.validate` recomputes the HMAC over `B` with secret `S` and it matches `H`, so validation succeeds [5](#0-4) .
5. `Registry.process` invokes the handler with `shop: "victim.myshopify.com"` and attacker-controlled body content, even though nothing from `victim.myshopify.com` was ever sent [6](#0-5) .

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
