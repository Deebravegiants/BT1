### Title
Unbounded scrypt cost parameters in stored SECO container allow DoS/resource-exhaustion of `decrypt()` during wallet unlock - (File: libraries/secure-container/src/index.js)

### Summary
`decrypt()` passes the `metadata.scrypt.{n,r,p}` values read straight out of the untrusted stored container into `scrypt()` via `stretchPassphrase`/`boxDecrypt` with no upper-bound validation. Because the file's `checksum` is a plain `sha256` hash (not a MAC/signature tied to the passphrase), anyone who can overwrite the stored container bytes can set `n` (a `UInt32BE`, up to ~4.29e9) to an enormous value and recompute a matching checksum without knowing the passphrase, forcing every future `decrypt()`/unlock attempt with the correct passphrase to hang or consume excessive CPU/memory.

### Finding Description
The unlock path is: `seco-storage/seco.js` `decryptString()` [1](#0-0)  calls `secure-container`'s `decrypt(encryptedData, passphrase)` [2](#0-1) . Inside `decrypt()`:
1. `conFile.decode` deserializes `header`, `checksum`, `metadata`, `blob`. The integrity check is `fileObj.checksum.equals(await computeChecksum(fileObj.metadata, fileObj.blob))` [3](#0-2) , and `computeChecksum` is a plain, keyless `sha256(metadata || blobLen || blob)` [4](#0-3) . This is only a corruption check, not a MAC bound to the passphrase or any secret — anyone with write access to the stored bytes can tamper `metadata.scrypt.n` and simply recompute a fresh valid checksum, without knowing the passphrase.
2. `conMetadata.decode` parses `scrypt.n/r/p` as raw `UInt32BE` fields with no range validation [5](#0-4) .
3. `decryptBlobKey` → `boxDecrypt` merges these attacker-controlled values into `scryptParams` and calls `stretchPassphrase`, which calls `scrypt(passphrase, salt, { N: n, r, p, dkLen: 32 })` with **no bound checks anywhere** [6](#0-5) [7](#0-6) .

Since `n` is validated only by the `UInt32BE` type (allowing up to 2^32-1) and `r`/`p` are similarly unconstrained, setting `n = 2**31` (or higher, combined with `r`) drives scrypt's required memory to gigabytes and its CPU time to durations far outside interactive/UI bounds, since scrypt memory usage scales as `O(N * r)`. There is no upper-bound assertion on `n`, `r`, or `p` anywhere in `decrypt()`, `boxDecrypt`, `stretchPassphrase`, or `createScryptParams` before scrypt is invoked.

### Impact Explanation
This is a denial-of-service / resource-exhaustion primitive against the wallet unlock flow: an attacker who can overwrite the stored encrypted seed container (e.g., via a storage-migration or sync path that writes to `seedStorage`/`unsafeStorage` without needing the passphrase) can make every subsequent legitimate unlock attempt with the *correct* passphrase hang or exhaust memory/CPU, since `decrypt()` unconditionally honors the tampered cost parameters. This blocks legitimate signing/approval flows that require an unlocked wallet, effectively bricking wallet access until the container is restored from a clean backup — a lock-state availability violation, though it does not itself leak secrets or bypass the passphrase check.

### Likelihood Explanation
Requires the stated precondition that an attacker can write/replace the stored SECO container bytes without needing the passphrase (e.g., a storage sync/migration mechanism accepting attacker-influenced data). Given that precondition, exploitation is trivial and fully repeatable: the checksum is unkeyed sha256, so the attacker recomputes it after modifying only 4 bytes (`scrypt.n`) in the fixed-size metadata blob; no cryptographic material or passphrase knowledge is needed.

### Recommendation
Enforce sane upper (and lower) bounds on `metadata.scrypt.n`, `r`, and `p` in `libraries/secure-container/src/crypto.js` (`stretchPassphrase`/`boxDecrypt`) and/or in `conMetadata.decode`, e.g. reject `n > 2**20`, `r > 16`, `p > 4` (or whatever the app's chosen max cost is) before calling `scrypt()`, throwing rather than proceeding. Additionally, consider binding the file `checksum`/authenticity to something the attacker cannot recompute (e.g., verifying metadata integrity is inherently tied to a MAC keyed by a value the attacker doesn't control), though bounding the scrypt cost parameters is the direct fix for this DoS vector.

### Proof of Concept
Unit/integration test in `libraries/secure-container`:
1. Use `encrypt()` to create a container with a real passphrase, obtaining `metadata` and `encryptedData`.
2. Decode the metadata region of `encryptedData`, overwrite `scrypt.n` to `2**31` (staying within `UInt32BE` range), re-encode metadata, recompute `checksum = sha256(metadata || blobLen || blob)` using `conFile.computeChecksum`, and rebuild `encryptedData` via `conFile.encode` — all without touching the passphrase or blob.
3. Call `decrypt(tamperedData, correctPassphrase)` with a timeout guard (e.g., 2s) and assert it either throws a "scrypt cost parameters exceed allowed maximum" error immediately, or completes within the timeout.
4. Expected current behavior (bug confirmed): the call proceeds to `scrypt()` and either hangs/times out or throws only after excessive CPU/memory use — i.e., no upfront bound check exists. After the fix, `decrypt()` should throw synchronously before invoking `scrypt`.

export async function decrypt(encryptedData, passphrase) {
  const fileObj = conFile.decode(encryptedData)

  const checksum = await conFile.computeChecksum(fileObj.metadata, fileObj.blob)
  if (!fileObj.checksum.equals(checksum))
    throw new Error('seco checksum does not match; data may be corrupted')

  const metadata = conMetadata.decode(fileObj.metadata)
  const blobKey = await conMetadata.decryptBlobKey(metadata, passphrase)
  const header = conHeader.decode(fileObj.header)
  const data = await conBlob.decrypt(fileObj.blob, metadata, blobKey)

  return { data, blobKey, metadata, header }
}
