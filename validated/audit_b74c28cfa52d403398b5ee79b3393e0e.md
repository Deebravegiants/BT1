Audit Report

## Title
JWT replay-check-then-record race in `WorkflowMetadataHandler.Authorize` allows request duplication - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
`WorkflowMetadataHandler.Authorize` checks JWT single-use status via `h.jwtCache.isReplay(claims.ID)` and only records usage via `h.jwtCache.recordUsage(claims.ID)` after performing unrelated workflow-lookup and signer-authorization logic in between [1](#0-0) . The two operations acquire and release the `jwtReplayCache`'s `RWMutex` independently rather than sharing one critical section [2](#0-1) , creating a TOCTOU window where two concurrent requests bearing the same signed JWT can both pass the replay check before either records usage.

## Finding Description
`Authorize` is reached from `authorizeRequest` in `http_trigger_handler.go`, which is called directly by `HandleUserTriggerRequest` — the externally-reachable entry point for HTTP-triggered workflow executions [3](#0-2) [4](#0-3) .

Inside `Authorize`, the sequence is: (1) verify JWT signature, (2) `isReplay(claims.ID)` check under `RLock`, (3) workflow-ID lookup, (4) signer-authorization lookup, (5) `recordUsage(claims.ID)` under a separate `Lock` [5](#0-4) . Because steps 2 and 5 are not part of one atomic critical section, two goroutines handling duplicate requests with the same `jti` can each execute `isReplay` (returning `false`) before either reaches `recordUsage`. Both will then pass authorization.

This is materially different from the request-deduplication check in `setupCallback`, which keys on `requestID` (`req.ID`), not on the JWT `jti` [6](#0-5) . Since `req.ID` is caller-supplied and independent from the JWT's `jti`, an attacker can send two requests with the same JWT (`Auth` header) but two distinct `id` fields; the `setupCallback` dedup by `requestID` will not block the second request, and the JWT-replay race is the only mechanism intended to prevent the same JWT from authorizing more than one execution.

The vault package's `RequestReplayGuard.CheckAndRecord` demonstrates the correct atomic pattern: check-existence and insert happen under one `mu.Lock()` in the same critical section [7](#0-6) , which `jwtReplayCache` does not replicate.

## Impact Explanation
A single signed HTTP-trigger JWT, intended to authorize exactly one workflow execution, can under race conditions authorize more than one execution by sending duplicate requests with distinct `requestID`s and the same `Auth` token concurrently. Each successful authorization proceeds through rate-limiting and fans out to DON nodes via `sendWithRetries`, consuming per-workflow rate-limit budget and triggering duplicate downstream workflow executions/side effects. This falls under unauthorized/duplicated job run — an in-scope impact class — though it is a narrow race window rather than a deterministic bypass, and the fix (single atomic check-and-record) is straightforward and localized.

## Likelihood Explanation
Exploitation requires only an unprivileged external caller capable of sending two HTTP requests with the same previously obtained signed JWT and different `requestID`s at nearly the same time — trivial to script with two parallel HTTP clients. No privileged role, host access, or cooperation from any node is needed; only the natural race window of the in-memory, non-atomic check-then-record sequence needs to be hit, which is realistic under real network jitter/concurrency.

## Recommendation
Collapse `isReplay` and `recordUsage` into a single atomic method, e.g., `checkAndRecordJTI(jti string) error`, that performs the existence check and the insert while holding `cache.mu.Lock()` for the entire operation — mirroring `RequestReplayGuard.CheckAndRecord`. Call this atomic method immediately after JWT signature verification in `Authorize`, before any workflow-lookup or signer-authorization logic, so no other code path can interleave between the check and the record.

## Proof of Concept
1. Obtain a valid signed HTTP Trigger JWT with `jti = "X"` for a registered workflow (via normal client flow).
2. Fire two HTTP trigger requests concurrently (e.g., two goroutines/HTTP clients) to the gateway's `HandleUserTriggerRequest` endpoint, both with `Auth = jwt(jti=X)` but distinct `id` fields (e.g., `"req-1"` and `"req-2"`).
3. In `WorkflowMetadataHandler.Authorize`, both requests can independently call `isReplay("X")` and observe `false` before either calls `recordUsage("X")`, since these are separated by workflow-ID and signer lookups.
4. Both requests pass authorization, pass `setupCallback`'s per-`requestID` dedup check (since `id` differs), and are dispatched via `sendWithRetries`, resulting in two distinct workflow executions authorized by the single JWT.
5. A Go unit test can reproduce this deterministically by calling `Authorize` from two goroutines with a synchronization barrier placed between the `isReplay` check and the `recordUsage` call (e.g., via a test hook or by making the intervening map lookups slow), asserting both calls return `nil` error.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}

func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}

	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
