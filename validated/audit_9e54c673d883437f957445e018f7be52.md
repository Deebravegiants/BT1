### Title
`ShopifyAPI::Webhooks::Request#shop` is trusted for tenant identification but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body, but the `shop` (and `topic`/`webhook_id`/`api_version`) values that are handed to the app's handler as trusted tenant-identifying metadata come from unauthenticated HTTP headers that are never part of the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` performs authentication like this: [1](#0-0) 

The only check performed is `Utils::HmacValidator.validate(request)`, which compares a computed HMAC against the request's `hmac` attribute using `to_signable_string` as the signed payload: [2](#0-1) 

For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [3](#0-2) 

However, `shop` (and `topic`, `webhook_id`, `api_version`) are read straight from HTTP headers, which are completely outside the HMAC-signed payload: [4](#0-3) 

After the HMAC check passes, `process` builds `WebhookMetadata` using this unauthenticated `request.shop` value and hands it to the app's handler as if it were an authenticated tenant identifier: [5](#0-4) 

Critically, the HMAC secret (`Context.api_secret_key`) used to validate webhooks is the app's single `client_secret`, shared across every shop that has installed the app — it is **not** shop-specific. This means the identity binding that should hold is:

`shop authenticated by the signed material == shop asserted to (and trusted by) the handler`

but the actual binding enforced by the code is:

`HMAC(raw_body, app_secret) is valid` (says nothing about which shop) `!=` `shop header value trusted for routing/tenant attribution`

Any entity that can get the app to deliver **any** legitimately HMAC-signed webhook body (e.g., by installing the app on their own shop and triggering a webhook, since they legitimately receive a valid `(body, hmac)` pair signed with the app's single shared secret) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header value. Because `shop-domain` is not covered by the signature, `Utils::HmacValidator.validate` will still pass, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload originated from any shop the attacker chooses — including shops that never installed the app or belong to other tenants.

### Impact Explanation
This breaks the tenant boundary the gem is expected to guarantee for webhook processing: an unprivileged internet user, without ever needing another shop's access token or `client_secret`, can cause an app to process attacker-supplied data as if it belonged to a shop of the attacker's choosing (cross-tenant data injection/confusion). Depending on what the host application does with `data.shop` (attributing writes, looking up per-shop settings/tokens, triggering per-shop side effects), this can lead to cross-tenant access or data corruption attributed to a victim shop, which matches the "cross-tenant access" Critical impact category in scope.

### Likelihood Explanation
Likelihood is meaningful because the only prerequisite is that the attacker have access to *any* real webhook delivery from the app (trivially obtainable by installing the app, even on a free/development store, and observing one webhook delivery's raw body + `hmac-sha256` header), plus the ability to POST to the app's public webhook endpoint with a forged `shop-domain` header — both of which are within reach of an unprivileged internet user and require no possession of any other shop's credentials, access token, or the app's `client_secret`.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC-signed material, or otherwise cryptographically tie the header-derived `shop` value to the verified body before it is trusted by `Registry.process`/`WebhookMetadata`. At minimum, `to_signable_string` in `lib/shopify_api/webhooks/request.rb` should incorporate the `shop-domain` header (and other trusted-metadata headers) so that tampering with them invalidates the HMAC check, matching the fixed pattern in the referenced Burve report where the previously unaccounted-for value was folded into the authenticated computation.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged action) and triggers any registered webhook topic (e.g., `products/update`), capturing the raw POST body `B` and the `X-Shopify-Hmac-Sha256: H` header Shopify sends — `H = HMAC-SHA256(app_client_secret, B)`.
2. Attacker sends a new POST to the app's webhook endpoint with the same body `B` and the same `H` header, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and finds it matches `H` — validation succeeds (`lib/shopify_api/webhooks/registry.rb:188-190`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, causing the host application to process attacker-controlled data as belonging to `victim-shop.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
