The code explicitly documents this exact limitation, and there are two independent implementations affected: the `PoaBridge.describeWithdrawal()` used by `sdk.withdraw()` / `createWithdrawalCompletionPromises()`, and the standalone `waitForWithdrawalCompletion()` in `internal-utils`.

### Title
Duplicate-asset batch withdrawals cause POA bridge status/txHash misreport, enabling double-credit - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
When a single NEAR transaction contains two or more PoaBridge withdrawal intents for the same `assetId` (e.g., two `nep141:usdc.omft.near` withdrawals to different destination addresses), `PoaBridge.describeWithdrawal()` cannot distinguish between them. Both `WithdrawalIdentifier` entries (index 0 and index 1) resolve to the same reported `(status, txHash)` pair, since matching is done only by `assetId`, not by amount, destination address, or index.

### Finding Description
The broken equality: `describeWithdrawal({index:0, assetId:"nep141:usdc.omft.near", ...})` reports the same `{status:"completed", txHash: X}` as `describeWithdrawal({index:1, assetId:"nep141:usdc.omft.near", ...})`, even though these correspond to two distinct on-chain payouts to two different `destinationAddress` values.

Root cause is in `findMatchingWithdrawal()`: [1](#0-0) 
This function is called from `describeWithdrawal()`: [2](#0-1) 
The comment explicitly acknowledges the gap: "NOTE: Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported." Since the POA bridge status API returns an unsorted list and the SDK's own `WithdrawalIdentifier.index` (assigned per-bridge-route in `createWithdrawalIdentifiers()`) is never used to disambiguate, `Array.prototype.find()` always returns the first list entry whose `near_token_id` matches — the same entry — for every withdrawal identifier sharing that `assetId`.

The call path from attacker input: `sdk.withdraw()` builds withdrawal intents from `withdrawalParams`, `createWithdrawalIdentifiers()` assigns sequential per-route indices: [3](#0-2) 
Both resulting `WithdrawalIdentifier`s (index 0 with destination A, index 1 with destination B) are passed independently to `watchWithdrawal()` → `bridge.describeWithdrawal()`, and both calls hit the identical `findMatchingWithdrawal` result once the POA API reports one of the two payouts as `COMPLETED`.

None of the existing guards prevent this: `validateWithdrawal`, `compareAddresses`, `supports()` ordering, and `FeeExceedsAmountError` all operate on withdrawal *construction/validation*, not on *status disambiguation*; they do not check for or reject duplicate-`assetId` withdrawals within a batch. The identical vulnerable pattern also exists independently in `waitForWithdrawalCompletion()`: [4](#0-3) 

### Impact Explanation
An integrator polling withdrawal status for a batch of two same-asset PoA withdrawals with different destination addresses will receive the same `txHash` and `completed` status for both `WithdrawalIdentifier`s once the first (in API list order) payout completes. If the integrator uses this to trigger downstream actions (e.g., marking both withdrawals as fulfilled, releasing custody, crediting balances, or dispatching refunds) it can incorrectly treat withdrawal #2 as delivered when only withdrawal #1's payout has actually landed — a misreport matching the "status or hash misreport making an integrator credit or refund twice" High-severity category. This is repeatable for every batch of same-asset PoA withdrawals until the underlying withdrawal completes/fails, and the misreport persists for the full observation window.

### Likelihood Explanation
Preconditions are trivial for an ordinary unprivileged user: initiate any withdrawal batch (`sdk.withdraw()`) containing two or more `withdrawalParams` with the same PoA-bridged `assetId` (e.g., `nep141:usdc.omft.near`) but different `destinationAddress`. No special routeConfig, contract state, or solver cooperation is required beyond normal PoA bridge routing (`feeInclusive` value is irrelevant to the matching bug). This is fully attacker-controllable and repeatable on every such batch.

### Recommendation
Disambiguate withdrawals of the same `assetId` within a batch by additional criteria (destination address + amount, or an ordinal sequence number returned/assigned by the POA API), or reject/serialize batches containing duplicate `assetId` withdrawals to the same bridge route until the POA API supports per-withdrawal correlation. At minimum, sort both the API response list and the local withdrawal params by amount (as the code comment suggests) to preserve relative ordering, or require the POA bridge API to return a client-supplied correlation ID per withdrawal.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
