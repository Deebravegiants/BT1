The docs explicitly state `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" [1](#0-0) , and the handler is told to trust `data.shop` as "The shop domain of the webhook" [2](#0-1) , but the HMAC only ever signs the raw body, not the shop-domain header.

### Title
Webhook shop-domain header not covered by HMAC allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, and `ShopifyAPI::Webhooks::Registry.process` validates the HMAC solely against that body. The `shop` (and `topic`, `webhook_id`, `api_version`) values, however, are read directly from HTTP headers that are never part of the signed payload. Because a single app-level `api_secret_key` is shared across every shop that installs the app, any merchant who receives a genuine, validly-signed webhook can replay that exact body while substituting an arbitrary `shop-domain` header, and the signature will still validate.

### Finding Description
`Request#hmac` is computed from the `hmac-sha256`/`x-shopify-hmac-sha256` header, and `Request#to_signable_string` returns `@raw_body` only [3](#0-2) . `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are pulled straight out of headers with no cryptographic binding to the body or to the HMAC [4](#0-3) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (which re-derives the signature from `to_signable_string`, i.e. the body) before dispatching to the handler with `shop: request.shop` taken verbatim from the unauthenticated header [5](#0-4) . `HmacValidator.validate` itself only ever hashes `verifiable_query.to_signable_string` [6](#0-5) .

The equality that should hold but doesn't: `shop header used by the handler == shop bound inside the HMAC-signed payload`. Instead, the shop header is fully attacker-controllable while the HMAC only proves "this body was signed with the app's secret," not "this body came from this specific shop."

Because `api_secret_key` is the same for all installations of a given app, a merchant/attacker who installs the app on their own store `attacker.myshopify.com` will receive genuine, correctly-signed webhooks for that store. They can capture the raw body + valid HMAC header pair from their own legitimate webhook delivery, then POST it to the app's webhook endpoint again with `x-shopify-shop-domain` (or `shopify-shop-domain`) rewritten to a victim's domain, e.g. `victim.myshopify.com`. `HmacValidator.validate` still passes because it only checks the body against the secret; `Registry.process` then invokes the app's handler with `WebhookMetadata` claiming `shop: "victim.myshopify.com"` [7](#0-6) .

### Impact Explanation
Host applications are documented to trust `data.shop` as the authenticated identity of the webhook sender (the docs' own example does `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [8](#0-7) . Since this value is not bound to the signature, an attacker can make the app process attacker-controlled webhook bodies under a victim tenant's identity. Depending on the topic, this enables cross-tenant data injection/corruption (e.g. forging `orders/create`, `products/update` payloads attributed to a victim shop) or state-mutating side effects scoped to the victim's tenant (e.g. triggering `app/uninstalled`-class logic against the victim's stored session/tokens), which is a cross-tenant access impact.

### Likelihood Explanation
Any developer/attacker can freely install almost any public embedded Shopify app on their own development store, which is enough to receive genuine, validly HMAC-signed webhooks signed with the app's shared `api_secret_key`. Replaying that request with a modified `shop-domain` header requires no special privilege beyond normal HTTP request crafting, and the gem performs no server-side check that the header matches the entity that the secret-holder (Shopify) intended.

### Recommendation
Bind the shop identity into the value that is cryptographically verified, or independently verify the shop header against Shopify's servers/known installed-shop list before trusting it. Concretely: include the `shop-domain` (and ideally `topic`/`webhook_id`) header bytes in the signed string checked by `Utils::HmacValidator`, or have `Registry.process` cross-check `request.shop` against a store of shops for which the app currently holds an active session, rejecting webhooks for shops that were never granted the topic/webhook subscription server-side.

### Proof of Concept
1. Install the target app on `attacker.myshopify.com`; trigger a webhook of interest (e.g. `orders/create`). Capture the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent — this HMAC is valid because it's computed with the app's shared `api_secret_key` over the raw body only, per `Request#to_signable_string` [9](#0-8) .
2. Replay the exact same raw body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes the body [10](#0-9) .
4. The registered handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's data>, ...)` [7](#0-6) , causing the host app to process attacker-controlled data as if it originated from the victim tenant.

          received_signature = verifiable_query.hmac
