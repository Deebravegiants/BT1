## Title
Direct token donation to `amm_coin_vault`/`amm_pc_vault` inflates deposit share pricing, causing depositors to be under-minted LP tokens and lose principal — ([File: program/src/processor.rs], [File: program/src/math.rs])

### Summary
Raydium's `process_deposit` and `process_withdraw` compute pool reserves directly from the live SPL token balances of the AMM's coin/pc vaults (`amm_coin_vault.amount`, `amm_pc_vault.amount`), exactly the "use `balance_of`" pattern flagged as insufficient in the referenced Opus report. Because `amm.lp_amount` (the internally tracked LP-share denominator) is only updated inside `Deposit`/`Withdraw`, an attacker can inflate the vault balances with a plain SPL token transfer (no AMM instruction required) without minting any LP shares. This desynchronizes "assets per share," causing a subsequent depositor's `mint_lp_amount` to round down catastrophically, and the value lost by that depositor accrues to existing LP holders (including the attacker), reproducing the exact rounding-loss mechanics described in the Opus finding.

### Finding Description
`Calculator::calc_total_without_take_pnl_no_orderbook` computes the pool's usable reserves straight from the vault token accounts passed into the instruction: [1](#0-0) 

This is called with the *live* vault balances (`amm_pc_vault.amount`, `amm_coin_vault.amount`) in `process_deposit`: [2](#0-1) 

The resulting `total_coin_without_take_pnl` is then used as the denominator for minting LP tokens, using floor-rounding division: [3](#0-2) [4](#0-3) 

The same balance-derived reserves are used symmetrically in `process_withdraw` to compute `coin_amount`/`pc_amount` owed for a given amount of burned LP tokens (also floor-rounded): [5](#0-4) 

Crucially, `amm.lp_amount` — the value used as `token_total` in these share calculations — is only mutated inside `process_deposit`/`process_withdraw` themselves: [6](#0-5) [7](#0-6) 

Because `amm_coin_vault_info`/`amm_pc_vault_info` are ordinary SPL token accounts owned by the pool's `$authority` PDA, *any* unprivileged party can call the SPL Token `Transfer` instruction to send extra coin or pc tokens into these vaults at any time, increasing `amm_coin_vault.amount`/`amm_pc_vault.amount` (and thus the reserves the AMM program reads) without touching `amm.lp_amount`. This is functionally identical to the Opus root cause: the program trusts a directly-observable balance (`balance_of`/token-account `.amount`) as the basis for share-price math instead of a value that only changes through accounted deposit/withdraw flows.

### Impact Explanation
An attacker who holds (or controls) most of a pool's existing LP supply — trivial for a newly created pool, since the pool creator receives essentially all LP tokens from `Initialize2` — can:
1. Transfer a large amount of coin and/or pc tokens directly into `amm_coin_vault`/`amm_pc_vault` (no AMM instruction, no signer over the AMM program required — just an SPL token transfer from any account the attacker controls) immediately before a victim's `Deposit` transaction lands.
2. The victim's `Deposit` computes `mint_lp_amount = deduct_coin_amount * amm.lp_amount / total_coin_without_take_pnl` (Floor), which now rounds down severely because `total_coin_without_take_pnl` has been artificially inflated while `amm.lp_amount` has not changed.
3. The victim receives a disproportionately small number of LP tokens for the value they deposited. If they later withdraw those LP tokens via `process_withdraw`, `coin_amount`/`pc_amount` are computed against the (now slightly higher) `amm.lp_amount`, and the victim recovers substantially less value than they deposited.
4. The value the victim lost is not burned — it remains in the vaults and inflates the claimable value of the *other* outstanding LP shares, i.e., it is transferred to the attacker's (and other LPs') holdings when they subsequently withdraw.

This is a concrete mechanism for theft of LP/user funds reachable from a single attacker-controlled transaction sequence (an SPL transfer plus timing relative to a victim's `Deposit`), matching "concrete theft ... of user or LP funds."

### Likelihood Explanation
The precondition — a pool with comparatively low LP supply relative to the size of a feasible attacker donation, and the ability of the attacker to land their donation transaction before a victim's deposit — is realistic, especially for newly created or low-liquidity pools (which are common on Raydium, e.g., freshly launched tokens). No privileged role, leaked key, or validator collusion is required; the only capability needed is holding tokens to transfer and ordinary transaction submission, both available to any unprivileged user. The attack does not require modifying the AMM program's account set beyond what any depositor could already reach (the vault token accounts are public, well-known PDAs derivable from the pool address).

### Recommendation
Do not derive pool reserves solely from live vault token-account balances (`amm_coin_vault.amount` / `amm_pc_vault.amount`) for LP mint/redeem math. Track deposited/withdrawn coin and pc amounts in `AmmInfo` state (updated only through `Deposit`/`Withdraw`/`Swap` instructions) and use that internally accounted reserve — reconciled with, but not blindly trusting, the vault balance — as the basis for `InvariantPool::exchange_token_to_pool`/`exchange_pool_to_token` calculations. Alternatively, enforce a minimum-deposit-value check (reject deposits whose resulting `mint_lp_amount` falls below a safe threshold relative to `deduct_coin_amount`/`deduct_pc_amount`) so that a donation-inflated reserve cannot silently truncate a legitimate depositor's minted shares.

### Proof of Concept
1. Pool created via `Initialize2` with modest initial liquidity; `amm.lp_amount` ≈ 1000, attacker (as creator) holds ~all corresponding LP tokens.
2. Attacker submits an SPL `Transfer` instruction sending e.g. 99,900 extra coin tokens directly to `amm_coin_vault` (bypassing `Deposit`). `amm.lp_amount` is unaffected; `amm_coin_vault.amount` jumps from ~100 to ~100,000.
3. Victim calls `Deposit` (base_side = coin) with `deduct_coin_amount = 199`. In `process_deposit`, `total_coin_without_take_pnl` = 100,000 (inflated). `mint_lp_amount = 199 * 1000 / 100000` (Floor) = 1, per [3](#0-2) . Victim's coin (and matching pc, per the pool ratio) is transferred in; only 1 LP token is minted; `amm.lp_amount` becomes 1001.
4. Victim calls `Withdraw` with their 1 LP token. In `process_withdraw`, `coin_amount = 1 * total_coin_without_take_pnl(≈100,199) / 1001` (Floor) ≈ 100, per [8](#0-7) .
5. Net result: victim deposited value equivalent to 199 coin but recovered only ~100 — a loss of ~99, which remains claimable by the attacker's residual LP holdings.

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
