### Title
Predispatch surplus from rebasing/appreciating tokens is fully captured as protocol dust instead of credited to the depositing user - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
In `IntentGatewayV2.placeOrder`, when an order includes `predispatch` calldata (used to unwrap LP/interest-bearing tokens before escrow), the gateway measures the actual balance received for each input token via a before/after diff and compares it to the amount the user declared in `order.inputs[i].amount`. If the actual received amount is *less* than declared (e.g., fee-on-transfer token), the user's escrowed amount is reduced to match reality — the user bears the loss. If the actual received amount is *greater* than declared (e.g., a rebasing/interest-accruing token that appreciated, or an LP unwrap that yielded more principal than expected), the entire surplus is treated as "dust" and permanently retained by the protocol via `emit DustCollected(token, dust)`, never credited to the user who supplied the underlying principal.

### Finding Description
The relevant logic is in the predispatch branch of `placeOrder`: [1](#0-0) 

```solidity
// Measure actual received, emit dust for excess, update order.inputs.
for (uint256 i; i < inputsLen;) {
    ...
    if (received > order.inputs[i].amount) {
        uint256 dust = received - order.inputs[i].amount;
        emit DustCollected(token, dust);
    } else {
        order.inputs[i].amount = received;
    }
    ...
}
```

The comment above the function explains the predispatch path exists specifically to run calldata such as "unwrapping LP tokens" before escrowing the resulting balances: [2](#0-1) . If the unwrapped/received asset is a rebasing token, an interest-bearing wrapper, or simply appreciates between the pre-funding transfer and the sweep-back measurement, `received` can legitimately exceed the amount the user declared for their own principal. Instead of crediting that surplus back to the user's escrow (which is what happens symmetrically when `received` is short, at line 305), 100% of the surplus is swept into gateway-held "dust," which is only ever released to a governance-controlled beneficiary via the `SweepDust` ISMP action: [3](#0-2) , or its EVM equivalent, not the order's depositor.

This is inconsistent with how the codebase treats surplus in other flows — e.g., `_splitSurplus` proportionally shares fill-side surplus between the protocol and the order beneficiary: [4](#0-3) . On the deposit/predispatch side, no such split exists; the depositing user gets none of the upside while bearing all of the downside.

### Impact Explanation
Any user who places an order with `predispatch` assets that are rebasing, interest-accruing, or otherwise capable of yielding more tokens than declared during the pre-funding → unwrap → sweep sequence permanently loses that surplus to the protocol's dust pool. This is an unauthorized transfer of user-owned value to the protocol, satisfying the "concrete theft ... of funds" bar. Reachable directly by any unprivileged caller of `placeOrder` — no privileged role is required to trigger the loss; it happens automatically whenever `received > order.inputs[i].amount` for a predispatch asset.

### Likelihood Explanation
Any predispatch integration that touches a rebasing/interest-bearing token (explicitly called out in the code's own comment as the intended use case for "unwrapping LP tokens") can trigger this on every `placeOrder` call, so likelihood is high wherever such input assets are used, and the loss compounds with each rebase/accrual cycle between the pre-fund transfer and the balance measurement.

### Recommendation
Symmetrically credit any excess received amount back to `order.inputs[i].amount` (crediting the user's escrow) instead of unconditionally emitting it as protocol dust, or explicitly document/disallow rebasing and interest-bearing tokens as predispatch inputs. If retaining a fee is intended, apply the same proportional split used for fill-side surplus (`_splitSurplus`) rather than taking 100% of the excess.

### Proof of Concept
1. User calls `placeOrder` with a `predispatch.call` that unwraps an interest-bearing LP token X into token Y, declaring `order.inputs[0] = {token: Y, amount: 100}`.
2. Due to accrued yield in X (or a rebase during the transfer→dispatch→sweep sequence), the dispatcher ends up holding 105 Y after unwrapping.
3. The sweep-back measurement in `placeOrder` computes `received = 105`, which is `> order.inputs[0].amount (100)`, so `dust = 5` is emitted via `DustCollected` and the 5 Y surplus is retained by the gateway contract.
4. The user's escrowed principal remains 100 Y (matching only their declared amount); the 5 Y surplus is never returned to them and can only be extracted later by governance via `SweepDust`, to a beneficiary chosen by governance — not the user.
