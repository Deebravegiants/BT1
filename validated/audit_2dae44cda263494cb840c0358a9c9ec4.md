### Title
Webhook shop/topic/webhook-id headers are trusted for tenant identification despite not being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook request by HMAC-validating only the raw request body, then dispatches to the registered handler using the `shop`, `topic`, and `webhook_id` values taken from HTTP headers that are never covered by that signature. This breaks the identity binding `shop authenticated == shop acted upon`: the HMAC proves the *body bytes* were produced with the app's `client_secret`, but the *tenant identity* attached to that body is taken from unauthenticated header bytes.

### Finding Description
`Webhooks::Registry.process` performs the authenticity check like this: [1](#0-0) [2](#0-1) 

The only thing HMAC-verified is `request.to_signable_string`, which is defined as the raw body only: [3](#0-2) 

Yet `shop`, `topic`, and `webhook_id` — all read straight from attacker-controllable HTTP headers — are used to route to a handler and are handed to application code as the trusted tenant identity via `WebhookMetadata`: [4](#0-3) [5](#0-4) 

`HmacValidator.validate` simply verifies `verifiable_query.to_signable_string` against `verifiable_query.hmac`, with no reference to `shop`/`topic`/`webhook_id` at all: [6](#0-5) 

This is the same bug class as the GMX report: a value (`initialCollateralDeltaAmount`/here, the `shop` header) is consumed as if it had gone through the same validation as another value (`estimatedRemainingCollateralUsd`/here, the HMAC-covered body) when it in fact was not converted/verified at all. The binding the code implicitly assumes is:

`hmac_valid(raw_body) == shop_header_is_authentic`

but the actual binding provided by the gem is only:

`hmac_valid(raw_body) == raw_body_was_produced_with_client_secret`

Because all shops installed on a given app share the same `client_secret`/HMAC key, any merchant who installs the app (an unprivileged party with respect to *other* tenants of the same app) can capture one of their own legitimately-signed webhook deliveries and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header swapped to a victim shop's domain. The HMAC check still passes (body untouched), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload is `shop: <victim-shop>`.

### Impact Explanation
This crosses the tenant boundary the gem is supposed to enforce for host applications relying on it to authenticate webhook origin: the `shop` attribute delivered to the handler cannot be trusted to actually correspond to the shop that produced the body. Any host app that uses `WebhookMetadata#shop` to select which merchant's session/data to update (the intended and documented usage) can be made to apply a payload under a different shop's identity — a cross-tenant confusion enabled entirely by this gem's own webhook-verification API, not by the host app ignoring documented behavior (the header-derived `shop` is the only shop value the gem exposes from `Webhooks::Request`).

### Likelihood Explanation
Any user who can install the target Shopify app on their own store (the normal, unprivileged installation flow for public apps) can generate an authentic HMAC over a body of their choosing and then re-send it with a modified shop header — no access to `api_secret_key`, tokens, or any other credential of the app or the victim shop is required, and no TLS interception or social engineering is needed.

### Recommendation
Do not treat `shop` (or `topic`/`webhook_id`) as trusted merely because the request's body HMAC validates. Either:
- Include the shop domain (and topic) inside the signable content that's HMAC-verified, or
- Independently confirm the `shop` header corresponds to a shop with an active, stored session/installation for this app before dispatching to handlers, or
- Clearly document in `Webhooks::Request`/`Registry` that `shop`/`topic`/`webhook_id` are unauthenticated metadata and must not be used as a tenant key without separate verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged action for any public app) and triggers a webhook subscription (e.g., `orders/create`).
2. Attacker captures the raw POST from Shopify: body `B`, and header `X-Shopify-Hmac-Sha256: H` (valid, since it was computed with the app's real `client_secret` over `B`).
3. Attacker replays this exact request to the app's webhook endpoint, but rewrites `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and, if desired, `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` (`B`) and compares to `H` — validation succeeds because body bytes weren't altered. [2](#0-1) 
5. The handler receives `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: B, ...)` and processes attacker-controlled payload `B` as if it originated from the victim shop.
