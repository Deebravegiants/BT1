### Title
Governance `SweepDust` action can drain funds needed to cover pending order escrow refunds/redemptions - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._sweepDust` transfers an arbitrary, governance-specified amount of any token out of the IntentGateway contract with no on-chain check that the amount actually corresponds to "spare" protocol dust rather than tokens still reserved for open orders. Because escrowed order inputs, escrowed transaction fees, and protocol dust all sit in the same contract token balance with no separate on-chain ledger for dust, an honest (non-malicious) `SweepDust` dispatch sized from an off-chain dust estimate can leave the contract without enough balance to satisfy outstanding `RedeemEscrow`/`RefundEscrow` withdrawals — the same "contract may not have enough funds to cover refund" bug class as the ForgottenRunes report, where `withdrawAll()` could drain funds needed for pending refunds.

### Finding Description
Protocol dust accrues from several sources without any persistent on-chain accumulator:
- Fee-deduction "dust" during order placement: [1](#0-0) 
- Surplus-share dust during fills, only ever emitted as an event: [2](#0-1) 
- Post-dispatch calldata sweep residuals: [3](#0-2) 

None of these paths increment an on-chain "dust" balance variable — `DustCollected` is purely an event for off-chain observers to reconstruct an estimate. Meanwhile, real user funds sit in the very same contract balance, tracked per-order in `_orders[commitment][token]` and `_orders[commitment][TRANSACTION_FEES]`: [4](#0-3) 

Hyperbridge governance periodically sweeps the accumulated dust via a `SweepDust` request, which `onAccept` decodes and forwards straight into `_sweepDust` with no validation against reserved escrow: [5](#0-4)

Since `amount` is supplied off-chain (from Hyperbridge governance's estimate of dust, reconstructed from `DustCollected` events across potentially many orders and destinations, with no on-chain reconciliation against currently-escrowed balances), the sweep can transfer out tokens that are actually still owed to users/solvers for open orders — particularly if new orders are placed, filled, or partially filled between when the off-chain dust figure was computed and when the `SweepDust` message is delivered, or if the off-chain accounting simply drifts. This is functionally identical to the audited bug: a routine, non-malicious privileged withdrawal drains the shared balance without checking against pending obligations, and the contract has no way to be "topped up" automatically for stuck orders.

### Impact Explanation
If the swept amount exceeds the true dust reserve, subsequent `_withdraw()` calls (`RedeemEscrow` on fill settlement, `RefundEscrow` on cancellation, or same-chain fill/cancel paths) will revert with an ERC20 transfer failure once the token balance is insufficient, since `_withdraw` performs an unconditional `IERC20.safeTransfer`/`_sendValue` for the full escrowed amount without any balance check beforehand: [7](#0-6) . This permanently freezes the affected users' and solvers' escrowed funds until governance manually re-funds the contract (if it even can, and if it can even determine which orders are now under-collateralized) — a concrete freezing-of-funds outcome reachable from ordinary order placement and settlement flows plus a routine governance maintenance action, not an adversarial governance action.

### Likelihood Explanation
`SweepDust` is documented as routine, periodic governance maintenance ("Protocol fees are retained as 'dust' in the gateway and can be swept to a treasury via Hyperbridge governance"): [8](#0-7) . Because the dust figure is computed off-chain from events rather than an on-chain invariant, any timing drift, rounding difference, or missed order state (partial fills, in-flight cross-chain orders) between computation and delivery of the sweep message can cause an over-sweep. No malicious intent by governance is required — this mirrors the original finding's characterization that the bug is something an honest operator would do "accidentally."

### Recommendation
Maintain an explicit on-chain dust accumulator (incremented at every point dust is currently only emitted as an event) and cap `_sweepDust` transfers to that tracked balance, decrementing it on sweep. Alternatively, before transferring, assert `IERC20(token).balanceOf(address(this)) - totalEscrowedForToken(token) >= amount`, where `totalEscrowedForToken` is derived from an on-chain running total of live per-token escrow across all open orders, so a sweep can never dip into funds reserved for pending `RedeemEscrow`/`RefundEscrow` obligations.

### Proof of Concept
1. Users place several cross-chain orders on `IntentGatewayV2`/`ExtrinsicIntents`, escrowing input tokens and `order.fees` via `placeOrder`, recorded in `_orders[commitment][token]`.
2. Over time, `DustCollected` events accumulate from protocol-fee deductions and surplus splits, but no on-chain dust total exists.
3. Hyperbridge governance computes an off-chain dust estimate from these events and dispatches a `SweepDust` request sized to (or exceeding) that estimate.
4. Between the estimate and message delivery, additional orders are placed/filled such that the actual "spare" balance is now lower than the swept amount; `onAccept` still executes `_sweepDust` unconditionally: [9](#0-8) , draining tokens genuinely owed to open orders.
5. A solver or user later triggers `_withdraw` for one of those orders (`RedeemEscrow`/`RefundEscrow`); `IERC20.safeTransfer` reverts because the contract's balance for that token is now insufficient, permanently blocking settlement/refund for that order.
