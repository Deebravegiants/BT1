### Title
Webhook `shop` field is not covered by the HMAC signature, allowing tenant-attribution spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the HMAC over the raw request body only, but exposes a separate `shop` accessor that reads directly from the unauthenticated `X-Shopify-Shop-Domain` HTTP header. `Registry.process` passes this unauthenticated `shop` value straight into the `WebhookMetadata` object delivered to the host application's handler, without it ever being covered by, or cross-checked against, the HMAC signature.

### Finding Description
The equality that should hold is: `shop_used_by_handler == shop_bound_by_hmac_signature`. In this gem it does not.

- `Request#to_signable_string` returns only `@raw_body` [1](#0-0) .
- `Request#shop` reads the `shopify-shop-domain` (or `x-shopify-shop-domain`) header directly, with no cryptographic binding to the body or to the HMAC computation [2](#0-1) .
- `HmacValidator.validate` calls `verifiable_query.to_signable_string`, which for a webhook `Request` is exactly `@raw_body` — the `shop` header plays no role in the signature check [3](#0-2) .
- `Registry.process` validates the HMAC over the body and then immediately constructs `WebhookMetadata` using `request.shop`, `request.parsed_body`, etc., handing this tenant-identifying field to the app's handler as if it were authenticated [4](#0-3) .

Because Shopify computes the HMAC over the raw body with the app's shared secret, an attacker who can replay or forward a legitimately-signed webhook body (e.g., a previously observed webhook for their own store, or one obtained via a public/leaked payload) can attach an arbitrary `X-Shopify-Shop-Domain` header. The HMAC check still passes (it never inspects the header), and the handler receives `WebhookMetadata#shop` set to the attacker-chosen shop domain instead of the shop that actually generated the payload — a cross-tenant identity confusion at the boundary this gem is responsible for authenticating.

This directly matches the "field acted on but not covered by the HMAC" class from the reference report: just as `DelegatorFactory::create` acted on `type_` without checking the blacklist that should have gated it, `Registry.process`/`WebhookMetadata` acts on `shop` without it being covered by the same HMAC check that gates the rest of the payload.

### Impact Explanation
Any host application that trusts `WebhookMetadata#shop` (or `Request#shop`) as an authenticated tenant identifier — a documented and expected usage pattern for multi-tenant Shopify apps — can be made to process, store, or act on webhook data under the wrong shop's identity. This is a cross-tenant boundary violation: data intended for/about shop A can be attributed to shop B purely by header manipulation, without any credential for shop B. This satisfies the "cross-tenant access" criterion for High/Critical impact, since it breaks the tenant isolation this gem is expected to enforce as part of webhook verification.

### Likelihood Explanation
Exploitability requires an attacker to possess or intercept one validly-HMAC-signed raw webhook body (e.g., from their own store's webhook subscription, which is easy for any merchant/developer to obtain) and then replay it against the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header pointing at a different, victim shop. Since the header is never part of the signable string, this requires no knowledge of the `api_secret_key`. The likelihood is moderate: it depends on the host app's endpoint being reachable and on the app trusting `data.shop` from this gem without additional verification — which is exactly what the gem's own webhook flow encourages via `WebhookMetadata`.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the HMAC-verified signable string, or otherwise cryptographically bind them to the payload before exposing them to `WebhookMetadata`. Concretely:
```diff
 sig { override.returns(String) }
 def to_signable_string
-  @raw_body
+  @raw_body + "\n" + shop + "\n" + topic
 end
```
Alternatively, since Shopify's own webhook HMAC scheme signs only the body by design, add a documented, explicit warning in `Registry.process`/`WebhookMetadata` that `shop`/`topic`/`webhook_id` values are unauthenticated headers, and provide (or require) a secondary authenticated channel — e.g. validating `shop` against a known, previously-authorized shop record — before the handler is invoked, rather than presenting `WebhookMetadata#shop` as if it were verified.

### Proof of Concept
```ruby
# Attacker captures a legitimately signed webhook for their own shop "attacker.myshopify.com"
raw_body = '{"id":123,"note":"legit payload from attacker shop"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
# (attacker doesn't need the secret; they just replay bytes+signature Shopify already sent them)

# Attacker forges the shop-domain header to point at the victim shop
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # attacker-controlled, unauthenticated
  "x-shopify-webhook-id" => "attacker-picked-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

# HMAC validation succeeds because it only checks raw_body against the (valid) signature
ShopifyAPI::Webhooks::Registry.process(request)
# => handler receives WebhookMetadata with shop == "victim-shop.myshopify.com",
#    even though the payload/signature never originated from victim-shop.
