### Title
Mnemonic and private key material persist in memory after `lock()` / `removeAllSeeds()` due to lack of secure memory wiping - ([File: features/keychain/module/keychain.js])

### Summary
The `@exodus/keychain` module underlying the hydra wallet SDK keeps the plaintext mnemonic-derived seed and all HD master keys resident in JavaScript memory for the entire duration a wallet session is "unlocked," and even when the wallet is explicitly locked, the sensitive buffers are only dereferenced rather than zeroed/wiped. This mirrors the reported bug class (mnemonic staying in memory too long / relying only on the OS or GC to clean it up), giving an attacker with heap/crash-dump access (e.g. via a crash reporter or a memory-dumping exploit chain) a large time window and, even post-"lock," a chance to recover the plaintext mnemonic/private keys from stale memory.

### Finding Description
`Wallet#unlock()` fetches the plaintext seed object (which includes the mnemonic string) from storage and immediately hands the raw seed buffer to the keychain via `this.#keychain.addSeed(seed)` [1](#0-0) . Internally, `Keychain#addSeed` derives and stores all HD master keys (`this.#masters[seedId] = masters`) in a plain object field that lives for as long as the `Keychain` instance is unlocked [2](#0-1) .

When the wallet is later locked, `Wallet#lock()` calls `keychain.removeAllSeeds()` [3](#0-2) , and `removeAllSeeds()`/`removeSeeds()` merely replace/delete the object references (`this.#masters = Object.create(null)`, `delete this.#masters[id]`) rather than overwriting the underlying key material buffers [4](#0-3) . This does not guarantee the plaintext bytes are scrubbed from the process heap — they remain until garbage collection reclaims and the memory page is reused, and even then standard GC does not zero freed memory.

This exact limitation is explicitly acknowledged in the module's own documentation: *"`keychain.removeAllSeeds()` does not guarantee that private keys get completely cleared from memory"* [5](#0-4) .

Additionally, `Wallet#getMnemonic()` reads and returns the raw mnemonic string from storage on every call (e.g., "show mnemonic in settings") [6](#0-5) , and `Wallet#addSeed()` for extra seeds keeps the plaintext `mnemonic` string embedded directly inside the in-memory `extraSeeds` array entries that get pushed to storage (`const data = { mnemonic, seed, dateCreated, compatibilityMode }`) [7](#0-6) , further multiplying the number of plaintext copies of the secret that transiently exist in the heap during normal wallet operation.

This is functionally the same bug class as the reported iOS/Android issue: sensitive mnemonic/seed material is loaded into process memory far longer, and in more copies, than strictly necessary to perform the requested operation, and is never actively wiped — only "removed" by breaking references and relying on the language runtime's garbage collector.

### Impact Explanation
If the hosting application process were to crash or be inspected (heap snapshot, crash reporter upload, memory-disclosure vulnerability in a native module, debugger attach, etc.) while the wallet is unlocked — or shortly after locking, before GC has run and the memory has been overwritten — an attacker could recover the plaintext mnemonic and/or derived master keys for all seeds (primary and extra), leading directly to full compromise of all assets controlled by the wallet.

### Likelihood Explanation
Exploitation requires an auxiliary capability (crash-dump/heap access, a memory-disclosure bug, or physical/debugger access), so likelihood is not "trivial remote," but the window of exposure is large: the keychain masters remain live in memory for the entire unlocked session (which can be long-lived on desktop/headless integrations), and `removeAllSeeds()`/`removeSeeds()` provide no hard security guarantee once locked, as documented by the maintainers themselves.

### Recommendation
- In `Keychain#removeAllSeeds()`/`#removeSeeds()`, actively overwrite (zero-fill) the master key/seed buffers before dropping references, rather than only deleting object keys.
- Avoid keeping the raw `mnemonic` string embedded in the `extraSeeds` in-memory array structures in `features/wallet/module/wallet.js`; derive/re-fetch it on demand from encrypted storage only when needed (e.g., for `getMnemonic()`), and scrub local variables/buffers after use.
- Consider deriving keys just-in-time for a specific signing/export operation rather than caching all HD masters for the whole unlocked session, reducing the residency window of decrypted key material.
- Update `features/keychain/README.md` guidance into an actual mitigation instead of a caveat, and add tests asserting buffers are zeroed after `removeAllSeeds()`/`removeSeeds()`.

### Proof of Concept
1. `wallet.unlock()` → `keychain.addSeed(seed)` stores derived HD masters in `Keychain#masters` [2](#0-1) .
2. Take a heap snapshot (or trigger a crash dump) while unlocked: master private key material and, if `getMnemonic()`/`addSeed()` for extra seeds was ever called, plaintext mnemonic strings are present in the JS heap.
3. Call `wallet.lock()` → `keychain.removeAllSeeds()` only does `this.#masters = Object.create(null)` [8](#0-7)  — the old buffers are not zeroed, so a heap snapshot taken immediately afterward (before GC compaction) can still contain the plaintext key material.

  getMnemonic = async ({ passphrase, seedId } = {}) => {
    try {
      // always need to get primary seed first to make sure the user entered the right passphrase
      // even if passed seedId is not primary
      const { mnemonic } = await this.#getSeed({ passphrase })
      if (!mnemonic) throw new Error('Wrong password. Try again.')

      if (!seedId || (await this.getPrimarySeedId()) === seedId) return mnemonic

      // Sequential, as sync fallback is slower
      for (const seed of await this.#getExtraSeeds()) {
        if (seedId !== (await getSeedId(seed.seed))) continue
        if (!seed.mnemonic) throw new Error('No mnemonic found for seedId.')
        return seed.mnemonic
      }

      throw new Error('No seed matches seedId.')
    } catch (err) {
      if (err.message === 'No seed matches seedId.') {
        this.#logger.debug('getMnemonic() failed: no seed matches seedId.')
        throw err
      }

      this.#logger.debug('getMnemonic() failed: wrong password')
      throw new Error('Wrong password. Try again.')
    }
  }

  removeAllSeeds() {
    this.#masters = Object.create(null)
    this.#seedLockStatus = Object.create(null)
  }

  async removeSeeds(seeds = []) {
    const seedIds = await getUniqueSeedIds(seeds)
    const existingSeedIds = new Set([
      ...Object.keys(this.#masters),
      ...Object.keys(this.#seedLockStatus),
    ])
    const seedIdsToRemove = seedIds.filter((seedId) => existingSeedIds.has(seedId))

    for (const id of seedIdsToRemove) {
      delete this.#masters[id]
      delete this.#seedLockStatus[id]
    }

    return seedIdsToRemove
  }
