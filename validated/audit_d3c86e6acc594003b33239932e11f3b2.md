### Title
Predictable, unsigned offline-session ID used as the browser's session cookie enables cross-tenant session hijacking - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
For non-embedded apps, `ShopifyAPI::Auth::Oauth.validate_auth_callback` sets the browser's session cookie value directly to `session.id`, and `ShopifyAPI::Utils::SessionUtils.cookie_session_id`/`current_session_id` later trusts that raw cookie value as the authoritative session identifier with no further cryptographic verification. For offline sessions this ID is `"offline_#{shop}"` - fully deterministic from the public, guessable shop domain and carrying no secret/random component tied to the specific browser or OAuth completion.

### Finding Description
`Session.from` computes the session `id` as `"offline_#{shop}"` for offline tokens (`shop` alone, no randomness) or `"#{shop}_#{associated_user.id}"` for online tokens. [1](#0-0) 

`Oauth.validate_auth_callback` then stores that exact `session.id` value as the `SessionCookie` value sent to the browser for non-embedded apps (`secure`/`http_only` are the host app's responsibility, but the value itself is unsigned): [2](#0-1) 

Later, `SessionUtils.current_session_id` for non-embedded apps (and as a fallback for embedded apps without a JWT) simply returns whatever value is present in the `shopify_app_session` cookie, with **no signature, no binding check to `Context.api_secret_key`, and no verification that the ID actually corresponds to a session this browser completed OAuth for**: [3](#0-2) [4](#0-3) 

This breaks the identity binding: `session id claimed by an unauthenticated cookie == session id issued to the browser that actually completed OAuth for that shop`. Because the offline ID is `"offline_#{shop}"` with `shop` being the public `*.myshopify.com` domain (visible in storefront URLs, app listings, partner dashboards, etc.), any unprivileged internet user who has installed the app on their own shop (or simply knows another store's domain) can set their own browser's `shopify_app_session` cookie to `"offline_<victim-shop>.myshopify.com"`. When the host application calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` as documented in `docs/getting_started.md`, this gem returns that attacker-chosen string verbatim as "the" session id, which the host app then uses to look up its stored `Session` (containing the victim's offline access token) and to make authenticated Admin API calls on the victim's behalf.

### Impact Explanation
Successful exploitation lets an attacker retrieve/use another merchant's stored offline access token by supplying a guessed/known shop domain in a cookie, i.e., cross-tenant access to another shop's Admin API session — this is a Critical impact per the given categories (cross-tenant access / theft of a merchant access token), achieved purely by an unprivileged internet user manipulating client-side, unauthenticated bytes that this gem treats as trusted.

### Likelihood Explanation
The `offline_#{shop}` format is generated and documented by this gem itself (`Session.from`, `SessionUtils.offline_session_id`), so any integrator following the documented cookie-based flow in `docs/getting_started.md` inherits this weakness. The only "secret" needed by an attacker is the target's `*.myshopify.com` domain, which is routinely public. No access token, `client_secret`, or privileged account is required — only the ability to edit one's own browser cookie before calling into the host app, which in turn calls this gem's `current_session_id`/`cookie_session_id` methods exactly as designed.

### Recommendation
- Do not use a value derived purely from public/predictable data (`shop`) as the trusted session cookie value. Either sign/HMAC the cookie value with `Context.api_secret_key` (and verify it in `cookie_session_id`), or use the random `SecureRandom.uuid` fallback that `Session#initialize` already generates by default instead of overriding it with the deterministic `shop`-derived id for the cookie use case.
- In `SessionUtils.cookie_session_id`/`current_session_id`, verify the cookie's authenticity (e.g., a signed/encrypted cookie or a server-side lookup keyed by an opaque random token) rather than trusting the raw string as an index into privileged session storage.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com`, completing OAuth normally (non-embedded flow), and observes that the app's `Set-Cookie: shopify_app_session=offline_attacker.myshopify.com` follows the pattern `offline_<shop>` (per `Session.from`, `lib/shopify_api/auth/session.rb:107-117`).
2. Attacker learns the target's shop domain `victim.myshopify.com` (public information).
3. Attacker edits their browser's `shopify_app_session` cookie to `offline_victim.myshopify.com` and issues a request to the host app.
4. Host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` per the documented flow (`docs/getting_started.md:50-52`), which returns `"offline_victim.myshopify.com"` unchanged (`lib/shopify_api/utils/session_utils.rb:19-37, 63-71`) with no verification.
5. Host app looks up its session store by this ID, retrieves the victim's stored `Session`/access token, and the attacker's subsequent request is served using the victim's credentials — a cross-tenant compromise.
