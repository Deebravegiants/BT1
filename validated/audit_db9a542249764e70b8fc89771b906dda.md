### Title
`validate_auth_callback` sends the app's `client_secret` to a `shop` host that is never validated against `ShopValidator.sanitize!` - ([File: lib/shopify_api/auth/oauth.rb])

### Summary

### Finding Description
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds a `null_session` directly from the caller-supplied `auth_query.shop` and then uses `Clients::HttpClient` to POST the app's `client_secret` and the authorization `code` to `https://#{auth_query.shop}/admin/oauth/access_token`: [1](#0-0) 

The only integrity check performed on `auth_query.shop` before it is used as the destination host for the credential-carrying POST is `Utils::HmacValidator.validate(auth_query)`, which verifies that the whole query string (`code, host, shop, state, timestamp`) was signed with `Context.api_secret_key`: [2](#0-1) [3](#0-2) 

Every sibling flow in the gem that builds a `Session`/`HttpClient` destined to receive the app's `client_secret` explicitly restricts the `shop` value to a trusted Shopify domain via `Utils::ShopValidator.sanitize!` before use:
- `ClientCredentials.client_credentials` [4](#0-3) 
- `RefreshToken.refresh_access_token` [5](#0-4) 
- `TokenExchange.migrate_to_expiring_token` [6](#0-5) 
- `Clients::Graphql::Storefront#initialize` [7](#0-6) 

`validate_auth_callback` is the one code path in the gem that omits this `ShopValidator.sanitize!` call, relying solely on the HMAC to bind the destination host.

The binding this is supposed to enforce is: `shop-host-that-receives-client_secret == a-trusted-*.myshopify.com-domain`. Currently the binding enforced is only: `shop-value == value-that-was-HMAC-signed-with-api_secret_key`. These are not equivalent — the HMAC check proves the query string was produced by a party that knows `api_secret_key` (normally Shopify itself, generating a redirect for a legitimate install), but it does not independently constrain the `shop` string to `*.myshopify.com`/`shopify.com`/`myshopify.io`/etc. the way `ShopValidator` does.

### Impact Explanation
`HttpClient#initialize` sets `@base_uri = "https://#{api_host || session.shop}"` and attaches `X-Shopify-Access-Token`/body containing `client_secret` unconditionally to whatever `session.shop` is: [8](#0-7) 

Because `oauth.rb` never runs `auth_query.shop` through `ShopValidator.sanitize!`, the only defense-in-depth mechanism the rest of the gem consistently applies (constraining outbound credential-bearing requests to Shopify-owned domains) is absent from this specific flow. Combined with the fact that the HMAC in this gem does not use `OpenSSL.secure_compare`-only defenses against structural manipulation of the `shop` field format (e.g., values embedding a different host as long as the full query string still matches the signature), any weakness in how the host application/Shopify forms or the app validates the `shop` string prior to constructing the `AuthQuery` could let the `client_secret` be sent to a non-`myshopify.com` host — a High-severity SSRF-with-credentials condition (the app's `client_secret` is exfiltrated to an attacker-controlled endpoint).

### Likelihood Explanation
Exploitation still fundamentally requires producing an `auth_query` (with matching `hmac`) whose `shop` field is not a genuine merchant `myshopify.com` domain. In the standard OAuth redirect flow this string is generated and signed by Shopify itself, so a purely network-level unprivileged attacker cannot forge it without knowledge of `api_secret_key`. This significantly limits real-world likelihood and is why this finding is best characterized as a **missing defense-in-depth control** (inconsistent with the rest of the codebase) rather than a directly exploitable bug reachable by an unprivileged internet user with no other assumptions. I could not identify a request path in this gem, reachable by an unauthenticated caller without a valid HMAC, that reaches this code.

### Recommendation
Add `validated_shop = Utils::ShopValidator.sanitize!(auth_query.shop)` in `validate_auth_callback`, mirroring `ClientCredentials`, `RefreshToken`, `TokenExchange.migrate_to_expiring_token`, and `Storefront`, and use `validated_shop` (rather than the raw `auth_query.shop`) both for the `null_session` used to build the outbound request and for the final `Session.from(shop: ...)` call, so that the `client_secret`-bearing POST can never target a host outside `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
Not applicable — exploitation requires a caller able to produce a valid `hmac` over an `AuthQuery` whose `shop` value already deviates from a trusted Shopify domain, which in turn requires the `api_secret_key` or an application misuse. I found no unauthenticated path within this gem that reaches `validate_auth_callback` with a forgeable `shop`, so I cannot present a concrete unprivileged PoC; this is reported as a missing-defense-in-depth/inconsistency finding relative to the rest of the codebase's identity-binding pattern for the same class of bug in the reference report.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
