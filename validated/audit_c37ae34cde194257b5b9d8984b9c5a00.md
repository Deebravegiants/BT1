### Title
`findMatchingWithdrawal` matches multiple same-token withdrawals in a batch to the wrong `WithdrawalIdentifier`, causing status/txHash misreport - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the status of a specific `WithdrawalIdentifier` by finding the first entry in the POA API's `withdrawals` list whose `near_token_id` matches the identifier's `assetId`. When a single intent batch contains two or more withdrawals of the same NEP-141 token (e.g. two `nep141:ltc.omft.near` withdrawals to different destinations/amounts), both `WithdrawalIdentifier`s produced for that batch resolve to the same lookup key, so `Array.prototype.find` returns the same (first) matching withdrawal for both, regardless of which one actually belongs to which destination.

### Finding Description
The broken equality: `describeWithdrawal(wid_A).txHash` should correspond to the on-chain payout for `wid_A.withdrawalParams.destinationAddress`/`amount`, and likewise for `wid_B`. After tracing the code, this equality does not hold when a batch contains repeated `assetId`.

- `createWithdrawalIdentifiers` (`packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107`) builds a `WithdrawalIdentifier` per `WithdrawalParams` entry in a batch. The `index` it assigns is only a per-bridge-route counter (`indexes.get(bridge.route) ?? 0`), not tied to token identity, destination, or amount, and there is no check anywhere in the SDK that rejects or deduplicates repeated `assetId` values within a batch.
- `PoaBridge.describeWithdrawal` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:313-343`) calls `getWithdrawalStatusWithRetry` to fetch `{ withdrawals: [...] }` from the POA bridge API keyed by the shared NEAR intent tx hash (`args.tx.hash`), then calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`.
- `findMatchingWithdrawal` (`poa-bridge.ts:418-427`) does `withdrawals.find((w) => \`nep141:${w.data.near_token_id}\` === assetId)`. The function's own doc comment (lines 409-417) admits: *"multiple withdrawals of the same token in a single transaction are not supported... matching could be done by sorting both API results and withdrawal params by amount"* — i.e., the author is aware this only works for a single withdrawal per token per batch, yet nothing in `supports()`, `validateWithdrawal()`, or the batch-construction path (`createWithdrawalIdentifiers`) prevents such a batch from being built and processed.
- Because `find` always returns the first array element that matches the token id — irrespective of which underlying intent primitive/output actually produced it — when two withdrawals share `assetId`, `describeWithdrawal` for the *second* `WithdrawalIdentifier` (different destination/amount) will be given the *first* matching withdrawal's `status`/`transfer_tx_hash`, and vice versa. This propagates through `watchWithdrawal` (`packages/intents-sdk/src/core/withdrawal-watcher.ts:20-78`) into `IntentsSDK.waitForWithdrawalCompletion`, which reports `{status:"completed", txHash: ...}` for a withdrawal identifier whose actual on-chain payout may be pending, failed, or gone to a different destination.
- None of the existing guards catch this: `supports()` and `parseAssetId()` only validate that the token belongs to the POA bridge, `validateAddress`/`compareAddresses` only validate a single destination at creation time, and there is no per-identifier correlation key (e.g., output index, memo, or NEAR receipt/output ordinal) returned by the POA bridge API that the SDK uses to disambiguate multiple same-token withdrawals within one NEAR transaction.

### Impact Explanation
An integrator that batches multiple withdrawals of the same PoA token (e.g., two `ltc.omft.near` payouts to different LTC addresses/amounts in one call) can receive a `completed` status with a `txHash` for the wrong `WithdrawalIdentifier`. This is a status/hash misreport that can cause an integrator to credit or reconcile a payout as done when it is not (or attribute the wrong tx hash to a destination), matching the "status or hash misreport making an integrator credit or refund twice" High-severity category. The misreport affects the reporting/reconciliation layer (`IntentsSDK.waitForWithdrawalCompletion` / `watchWithdrawal`), not the on-chain funds movement itself (the actual on-chain transfers still go to their correctly signed destinations per the original intents) — the risk is entirely in what the SDK tells the caller about which payout completed and with what hash.

### Likelihood Explanation
Preconditions: an ordinary user (or an integrator building a batch on a user's behalf) issues a single intent batch containing two or more `nep141:<token>` withdrawals for the *same* underlying PoA token with different destinations/amounts. This is fully within attacker/ordinary-user control — no privileged access, no malicious relayer, no RPC compromise needed; it only requires calling the public SDK batch-withdrawal APIs with a repeated `assetId`. Nothing in `supports()`, `validateWithdrawal()`, or `createWithdrawalIdentifiers` rejects such a batch, so the precondition is trivially reachable and repeatable on every call that constructs such a batch.

### Recommendation
Reject (or explicitly disallow) batches containing multiple withdrawals with the same `assetId` for the PoA route at validation time (e.g., in `validateWithdrawal` or `createWithdrawalIdentifiers`), until the POA bridge API provides a stable per-withdrawal correlation key (destination address/amount/output index) that `findMatchingWithdrawal` can use to disambiguate. Alternatively, implement the amount-based sorting/matching strategy the code comment already proposes, and add a runtime assertion that fails loudly (rather than silently misreporting) whenever multiple withdrawals for the same token are detected in a single `getWithdrawalStatus` response.

		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function watchWithdrawal(args: {
	bridge: Bridge;
	wid: WithdrawalIdentifier;
	signal?: AbortSignal;
	logger?: ILogger;
}): Promise<TxInfo | TxNoInfo> {
	const stats = getWithdrawalStatsForChain({
		chain: args.wid.landingChain,
		bridgeRoute: args.bridge.route,
	});
	let consecutiveErrors = 0;

	try {
		return await poll(
			async () => {
				try {
					const status = await args.bridge.describeWithdrawal({
						...args.wid,
						logger: args.logger,
					});

					consecutiveErrors = 0;

					if (status.status === "completed") {
						return status.txHash != null
							? { hash: status.txHash }
							: { hash: null };
					}

					if (status.status === "failed") {
						throw new WithdrawalFailedError(status.reason);
					}

					return POLL_PENDING;
				} catch (err: unknown) {
					if (err instanceof WithdrawalFailedError) {
						throw err;
					}

					consecutiveErrors++;
					if (consecutiveErrors >= MAX_CONSECUTIVE_ERRORS) {
						throw new WithdrawalWatchError(err);
					}

					args.logger?.warn(
						`Transient error (${consecutiveErrors}/${MAX_CONSECUTIVE_ERRORS}): ${err}`,
					);
					return POLL_PENDING;
				}
			},
			{ stats, signal: args.signal },
		);
	} catch (err: unknown) {
		if (err instanceof PollTimeoutError) {
			throw new WithdrawalWatchError(err);
		}
		throw err;
	}
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
