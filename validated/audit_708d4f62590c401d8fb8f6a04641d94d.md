Audit Report

## Title
Unauthenticated Gateway callers can freely spam `savedCallbacks`/DON fan-out via legacy `web_api_trigger` requests with no allowlist or rate limiting - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
`gateway.ProcessRequest` is the public HTTP entry point (`GetUserPort`) reached by any unauthenticated client, and for legacy JSON-RPC requests carrying a `DonID` it dispatches directly into `handler.HandleLegacyUserMessage` with no authentication, allowlist, or rate-limit check applied at either the HTTP server layer or the gateway dispatch layer.<cite repo="Alyssadaypin/chainlink--010" path="core/services/gateway/gateway.go" start="253,270,272" end="272"/> Inside the handler, the code explicitly documents the missing protection with `// TODO: apply allowlist and rate-limiting here`, after which every accepted request unconditionally inserts an entry into the shared `savedCallbacks` map and fans the message out to every DON member.<cite repo="Alyssadaypin/chainlink--010" path="core/services/gateway/handlers/capabilities/handler.go" start="384,411,412,417,418" end="418"/>

## Finding Description
The gateway's user-facing HTTP server (`network.httpServer.handleRequest`) reads the raw request, optionally extracts a JWT from the `Authorization` header (but does not validate or require it), and calls `ProcessRequest` unconditionally.<cite repo="Alyssadaypin/chainlink--010" path="core/services/gateway/network/httpserver.go" start="226,233,234" end="234"/> `ProcessRequest` decodes the JSON-RPC envelope, and for legacy messages (those carrying `msg.Body.DonID`) only validates message shape via `msg.Validate()` before routing directly to `h.HandleLegacyUserMessage`.<cite repo="Alyssadaypin/chainlink--010" path="core/services/gateway/gateway.go" start="253,256,257,270,272" end="272"/>

`HandleLegacyUserMessage` performs payload decoding and a timestamp freshness check (`payload.Timestamp` vs `MaxAllowedMessageAgeSec`), but the comment immediately following these checks — `// TODO: apply allowlist and rate-limiting here` — confirms that no caller-identity or rate-limit check is applied before the method proceeds.<cite repo="Alyssadaypin/chainlink--010" path="core/services/gateway/handlers/capabilities/handler.go" start="372,384" end="384"/> The function then unconditionally inserts an entry keyed by attacker-controlled `MessageID` into `h.savedCallbacks` and loops over every DON member sending the message via `don.SendToNode`.<cite repo="Alyssadaypin/chainlink--010" path="core/services/gateway/handlers/capabilities/handler.go" start="411,412,416,417,418" end="418"/>

The only bound on the `savedCallbacks` map size is the periodic `pruneCallbacks` background routine, which evicts by age and, once `MaxSavedCallbacks` (default 20000) is exceeded, evicts the oldest half of entries regardless of whether they belong to legitimate in-flight requests.<cite repo="Alyssadaypin/chainlink--010" path="core/services/gateway/handlers/capabilities/handler.go" start="299,314,317,329,330" end="331"/> This confirms the reported behavior: an unprivileged actor can freely append/spam state and trigger DON-wide fan-out with only a well-formed timestamp, no allowlist entry, and no rate limit gating this specific legacy code path.

I note that the handler does have a `nodeRateLimiter`, but it only governs *outbound* messages *from* nodes (`handleWebAPIOutgoingMessage`), not inbound user-originated legacy trigger requests.<cite repo="Alyssadaypin/chainlink--010" path="core/services/gateway/handlers/capabilities/handler.go" start="164,166,167" end="167"/> Separately, the newer v2 HTTP handler path (`core/services/gateway/handlers/capabilities/v2/http_handler.go`) does implement a `userRateLimiter` and JWT-based authentication for HTTP triggers, showing the project is aware of and has since built these protections for the newer path — but the legacy `web_api_trigger` path validated here still lacks them, per the outstanding TODO.<cite repo="Alyssadaypin/chainlink--010" path="core/services/gateway/handlers/capabilities/v2/http_handler.go" start="149,150,151,152" end="152"/>

## Impact Explanation
This is a legitimate availability/denial-of-service impact: an unauthenticated caller can flood the legacy `web_api_trigger` endpoint, each request forcing an insertion into `savedCallbacks` and one internal message per DON member via `don.SendToNode`, amplifying a single external HTTP request into N internal fan-out messages.<cite repo="Alyssadaypin/chainlink--010" path="core/services/gateway/handlers/capabilities/handler.go" start="411,417,418" end="418"/> Once `MaxSavedCallbacks` is exceeded, `pruneCallbacks` evicts the oldest half of the map indiscriminately, which can churn out legitimate, still-pending callbacks belonging to real users, causing their triggered workflow responses to be dropped/timed out.<cite repo="Alyssadaypin/chainlink--010" path="core/services/gateway/handlers/capabilities/handler.go" start="314,317,329,330" end="331"/> This maps to a DON-wide resource exhaustion / availability degradation impact category.

## Likelihood Explanation
High from a reachability standpoint. The gateway's user HTTP port is explicitly exposed for external callers (`GetUserPort`), and the HTTP server itself applies no per-caller authentication or rate limiting before forwarding to `ProcessRequest` — only a request-size limiter and CORS validation are present.<cite repo="Alyssadaypin/chainlink--010" path="core/services/gateway/network/httpserver.go" start="211,218,234" end="234"/> The legacy handler path itself gates only on message shape and timestamp freshness, both trivially satisfiable by any client crafting a well-formed request with a fresh timestamp and unique `MessageID`. The `// TODO: apply allowlist and rate-limiting here` comment in production code is direct, first-party confirmation that this is a known, unaddressed gap rather than a speculative concern. [1](#0-0) 

## Recommendation
Add per-caller authentication and/or rate limiting to `HandleLegacyUserMessage` before inserting into `savedCallbacks` and fanning out to DON members — resolving the outstanding TODO. This could reuse patterns already implemented for the newer v2 HTTP trigger handler, which applies a `userRateLimiter` and JWT-based authorization before dispatch.<cite repo="Alyssadaypin/chainlink--010" path="core/services/gateway/handlers/capabilities/v2/http_handler.go" start="149,150,151,152,170" end="170"/>

## Proof of Concept
1. Deploy a Gateway configured with the legacy `capabilities` handler (`core/services/gateway/handlers/capabilities/handler.go`) for a DON with `N` member nodes.
2. From an unauthenticated client, repeatedly POST well-formed legacy JSON-RPC requests to the Gateway's user HTTP port with method `web_api_trigger`, a fresh `Timestamp`, a unique `MessageID` each time, and a valid `DonID`.
3. Observe `gateway.ProcessRequest` accepts every request without any caller-identity check <cite repo="Alyssadaypin/chainlink--010" path="core/services/gateway/gateway.go" start="253,270,272" end="272"/>, and each request causes `HandleLegacyUserMessage` to insert into `savedCallbacks` and issue `N` `don.SendToNode` calls.<cite repo="Alyssadaypin/chainlink--010" path="core/services/gateway/handlers/capabilities/handler.go" start="411,417,418" end="418"/>
4. With sufficient request volume, `savedCallbacks` repeatedly exceeds `MaxSavedCallbacks`, causing `pruneCallbacks` to evict legitimate pending callbacks from real DON workflow triggers, and the DON receives amplified fan-out traffic sourced from a single unauthenticated attacker.<cite repo="Alyssadaypin/chainlink--010" path="core/services/gateway/handlers/capabilities/handler.go" start="317,329,330" end="331"/>
