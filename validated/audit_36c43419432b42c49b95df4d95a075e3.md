### Title
Signup success is trusted from a locally self-computed value instead of backend verification in the user-centric signup path - ([File: src/plans/mod.rs])

### Summary
The reported bug class is a discrepancy where a security-critical boolean decision is computed two different ways in two different code paths: one path derives it from an authoritative, externally-verified value, while the other path recomputes it from a locally-derived value that should not be trusted for enforcement, causing inconsistent, unsafe outcomes. The analogous pattern exists in `MasterPlan::do_signup()` in orb-core, where the signup "success" outcome (which gates whether a person's Personal Custody Package / identity data was validly enrolled) is decided by two structurally different mechanisms depending on the `user_centric_signup` flag, one of which bypasses backend verification entirely.

### Finding Description
In `do_signup()`, after fraud detection and pipeline execution, `signup_reason` is computed locally (`Normal`, `Fraud`, or `Failure`) purely from on-Orb pipeline/fraud outcomes: [1](#0-0) 

The PCP credentials are then built and uploaded to the backend unconditionally, before the success/enrollment decision is finalized: [2](#0-1) 

The final enrollment `success` value is then computed via two divergent branches: [3](#0-2) 

- In the `else` branch (backend-mediated / app-centric-off path), `success` is derived from `self.enroll_user(...)`, which sends the signup to the backend via `signup_post::request` and polls `signup_poll::request` until the backend explicitly confirms `Status::Completed` with `success: true`. The backend enforces its own checks (duplicates, legacy requests, inflight matches, backend-side fraud) as noted in the comment in `enroll_user::Plan::run`: [4](#0-3) 

- In the `if user_centric_signup && !ignore_user_centric_signups` branch, `success` is set to `signup_reason == SignupReason::Normal` — a value computed entirely on-device from the local pipeline and local fraud engine, with **no backend confirmation call at all**. `enroll_user()`/`signup_post`/`signup_poll` (and their backend-side duplicate/fraud verification) are never invoked in this branch.

This mirrors the reported bug class precisely: one code path bases a critical accept/reject decision on an authoritative, externally verified computation (`enroll_user()` → backend `signup_post`/`signup_poll`), while the other path recomputes the same decision from a value (`signup_reason`, derived solely from local, Orb-side pipeline/fraud output) that is not equivalent to the backend's own verification and is not meant to be authoritative on its own.

### Impact Explanation
Because `success` (and the resulting `debug_report.enrollment_status`) in the user-centric branch depends only on the on-device `signup_reason`, a signup can be reported/treated as successful without ever having been confirmed by the backend's own duplicate-detection and fraud-verification logic that the `enroll_user()` path performs. This creates a path where a signup may be locally accepted while being unverified/uncorroborated by the backend and could lead to state that is inconsistent with the backend's actual determination of validity, an unauthorized or misattributed enrollment outcome, depending on what other systems trust the Orb-reported success flag downstream.

### Likelihood Explanation
This code executes on every signup where `user_centric_signup` is `true` and `ignore_user_centric_signups` is `false` — this is a normal, reachable configuration set via backend-provided `UserData.user_centric_signup` and the `Config::ignore_user_centric_signups` flag, not a rare or hardware-dependent edge case: [5](#0-4) [6](#0-5) 

### Recommendation
Ensure the enrollment "success" decision is consistently derived from an authoritative source in both branches. Either always perform backend confirmation (via `enroll_user()`/`signup_post`/`signup_poll`) regardless of `user_centric_signup`, or clearly document/verify that the local `signup_reason`-based success determination in the user-centric branch is semantically equivalent to backend verification and cannot be used to short-circuit dedup/fraud checks that the non-user-centric branch relies on.

### Proof of Concept
Not applicable — this is a logic/design discrepancy demonstrated by comparing the two branches at `src/plans/mod.rs:639-656`, not an exploit requiring external reproduction.
