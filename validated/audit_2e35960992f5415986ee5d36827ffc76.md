### Title
Webhook tenant identity (`shop-domain`) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields that are handed to the app's business logic are read from unauthenticated HTTP headers. `Registry.process` validates only the HMAC-over-body and then trusts those header-derived fields as the tenant identity for dispatch, exactly the "field acted on but not covered by the HMAC" class of bug described in the source report (there, `growthInside1LastX128` was populated from the wrong accumulator; here, the trusted `shop` field is populated from a channel the cryptographic check never touches).

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all sourced from HTTP headers (`shopify-shop-domain`/`x-shopify-shop-domain`, etc.), which are never part of the signable string: [2](#0-1) 

`Registry.process` validates the request with `Utils::HmacValidator.validate(request)` — which calls `request.to_signable_string` (body only) — and then, once that single check passes, forwards the header-derived `request.shop`, `request.topic`, and `request.webhook_id` straight into `WebhookMetadata` for the app's handler: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` compute and compare the HMAC strictly against `verifiable_query.to_signable_string`: [4](#0-3) 

`WebhookMetadata` (the object the handler receives and typically uses to resolve which tenant/shop record to act on) carries `shop` as a plain, unauthenticated `String` field: [5](#0-4) 

The identity binding that should hold is: **shop authenticated by the cryptographic check == shop acted on by the handler**. Because the HMAC covers only `@raw_body`, this equality is never enforced — an attacker can keep a genuine, previously-observed `(raw_body, hmac)` pair valid while substituting an arbitrary `shopify-shop-domain` header value, and the check in `HmacValidator.validate` still returns `true`.

### Impact Explanation
An attacker who has legitimately installed the app on their own shop (a normal, unprivileged Shopify merchant, no special credentials required) will receive real webhook deliveries from Shopify — bodies signed with the app's shared `client_secret` (same secret for every installation of the app). Because that secret authenticates the body but never the `shop-domain` header, the attacker can replay the identical signed body directly to the app's webhook endpoint while swapping the `shopify-shop-domain` header to a victim shop's domain. `Registry.process` will accept the request (HMAC still valid) and dispatch it to the app's handler labeled as belonging to the victim shop. Any handler that uses `WebhookMetadata#shop` to select/update per-tenant records (a standard multi-tenant pattern) will write or act on data under the wrong tenant, i.e. cross-tenant access/data injection without ever needing the attacker to know the app's `client_secret` or any victim credential.

### Likelihood Explanation
Any merchant that installs the target app can trivially capture one of their own genuine webhook deliveries (raw body + `X-Shopify-Hmac-Sha256`) and replay it with a modified `shop-domain` header using a normal HTTP client — no secrets, no privileged access, and no interaction with Shopify's own infrastructure are required. The only precondition is that the app's webhook handler trusts `WebhookMetadata#shop` for tenant resolution, which is the intended, documented use of that field.

### Recommendation
- Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the signable string, or otherwise verify them out-of-band (e.g., cross-check against an allow-list of shops the app has installed and reject webhooks whose header `shop-domain` does not match a shop the payload itself claims to originate from), before constructing `WebhookMetadata`.
- Alternatively, document explicitly that `WebhookMetadata#shop` is not cryptographically authenticated and must not be used alone to resolve tenant identity without an additional binding check (e.g., verifying the shop is a known/expected installation before trusting the payload).
- Add regression tests asserting that a valid-HMAC request with a header `shop-domain` inconsistent with the signed body/tenant is rejected.

### Proof of Concept
1. Install the target app normally on `attacker.myshopify.com` (no special privilege beyond being a regular merchant).
2. Trigger any webhook topic the app subscribes to; capture the raw HTTP request Shopify sends, including `raw_body` and the `X-Shopify-Hmac-Sha256` header.
3. Re-send an HTTP POST to the app's webhook endpoint with the identical `raw_body` and `X-Shopify-Hmac-Sha256` header, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the HMAC.
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` and performs its normal tenant-scoped action against `victim.myshopify.com`, even though the payload actually originated from and pertains to `attacker.myshopify.com`.

          received_signature = verifiable_query.hmac
