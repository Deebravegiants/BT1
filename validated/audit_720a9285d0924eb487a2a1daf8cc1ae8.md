## Title
Webhook shop identity is not covered by the HMAC binding, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before invoking the app's handler, but the HMAC signature only authenticates the request body. The `shop` (and `topic`/`webhook_id`) values that the handler actually acts on are read directly from unauthenticated HTTP headers, so they are never bound to the signature. This is the same class of bug as the Oracle report: a field the code *acts on* (which member/shop the event is attributed to) is disjoint from the field the cryptographic check actually covers (which vote/HMAC was validated).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

and `shop` is read straight from a header with no cryptographic tie to the HMAC: [2](#0-1) 

`Registry.process` validates only this body-based HMAC and then forwards the untrusted `shop` value straight to the application handler: [3](#0-2) 

The identity binding that should hold is:
`shop authenticated by HMAC == shop the handler acts on`

but the actual binding implemented is:
`hmac(raw_body, api_secret_key) verified == true`, while `shop` (and `topic`, `webhook_id`, `api_version`) are parsed from headers that are completely outside the signable string.

Because `api_secret_key` is the same shared secret for every shop that installs a given app, any party who can obtain one valid `(raw_body, hmac)` pair — trivially done by installing the app on their own store and capturing a real webhook delivery, since webhook bodies for many topics are attacker-influenced or predictable (e.g., `orders/create` with attacker-controlled order data, or a fixed-shape body such as `{}`/mandatory GDPR topics) — can replay that exact body and HMAC to the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` header to any victim shop's domain. `HmacValidator.validate` will still return `true` because it never inspects the `shop` header, so `Registry.process` will call the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` even though the payload never originated from that shop.

### Impact Explanation
Handlers are documented and expected to use `data.shop` to key per-tenant work (see `docs/usage/webhooks.md`'s example handler dispatching `perform_later(shop_domain: data.shop, ...)`), including the three GDPR-mandated topics (`shop/redact`, `customers/redact`, `customers/data_request`). An attacker can forge webhook deliveries attributed to a shop they do not own/operate, causing the app to perform shop-scoped side effects (queuing jobs, data redaction/export flows, state changes keyed by shop) against another tenant's identity — a cross-tenant confusion that requires no access token, no `api_secret_key`, and no privileged account, satisfying the Critical "cross-tenant access" bar.

### Likelihood Explanation
The only prerequisite is possession of one valid `(body, hmac)` pair for the target app, which an attacker can generate for free by installing the app themselves (a normal, unprivileged action any merchant/dev-store owner can perform) and capturing the resulting webhook delivery. The `shop` header is then trivially swappable client-side since it is never re-derived from or checked against the signature.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-covered signable string, or independently verify `request.shop` against the shop associated with an already-authenticated session/install record before dispatching to handlers, rather than trusting the `X-Shopify-Shop-Domain` header as-is.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets a webhook (e.g. `customers/data_request`, whose body attacker controls via their own store data) fire to the app's endpoint. Attacker captures `raw_body` and the resulting `X-Shopify-Hmac-Sha256` value — both valid because `HmacValidator.validate` only checks `raw_body` against `Context.api_secret_key`, a value shared by all shops of this app. [4](#0-3) 
2. Attacker replays the exact same `raw_body` + `hmac` to the app's webhook route, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` — passes, since it only checks the body. [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the app to perform shop-scoped processing (e.g., data-redaction/export workflow) attributed to `victim-shop.myshopify.com` despite the payload never coming from that shop. [6](#0-5)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end
