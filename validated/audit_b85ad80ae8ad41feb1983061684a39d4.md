Found a concrete object-level authorization gap analogous to the hawkBit finding: the destination-side `_withdraw`/`withdraw` in the IntentGateway trusts the `WithdrawalRequest.tokens` array (the specific token *addresses* named in the message) rather than verifying they match the `commitment`'s actual escrowed input set.

### Title
IntentGateway `_withdraw` does not bind the withdrawn token list to the order's escrowed inputs, allowing an authenticated peer gateway message to redeem escrow for a token never assigned to that commitment - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`ExtrinsicIntents.onAccept` authenticates only that the incoming `RedeemEscrow`/`RefundEscrow` message came from the registered peer gateway instance for `request.source` (`_authenticate`, `ExtrinsicIntents.sol:63-67`), then calls `_withdraw(body, ...)` with the `WithdrawalRequest` decoded straight from the message body. `_withdraw` (`IntentsBase.sol:451-470`) iterates `body.tokens[]` — a caller-supplied list of `(token, amount)` pairs — and for each entry only checks `_orders[commitment][token] != 0` before decrementing and transferring. Nothing ties the *set* of tokens in `body.tokens` to the specific inputs that were escrowed for that `commitment` at `placeOrder` time; it only guards each individual token slot against being already-zero.

### Finding Description
This is the same bug class as CVE-2026-16454: a message that is correctly authenticated for one object (an order commitment / firmware "assigned" to a device) is not checked for whether the *specific sub-resources it names* actually belong to that object's own authorization boundary in the way the escrow's own bookkeeping should enforce. In hawkBit, an authenticated device could name and download artifacts outside its own assignment. Here, an authenticated peer-gateway message that names `commitment` C can list an arbitrary `tokens[]` array (any ERC-20 address and amount, so long as `_orders[C][token] != 0` for that address). The `_orders` mapping is keyed by `(commitment, token)`, not restricted to only the tokens that were part of that particular order at placement — so if the same token address happens to have a nonzero balance recorded under commitment C for *any* reason (partial fill accounting, protocol rounding, or a same token reused across multiple orders' bookkeeping since `_orders` is a flat double mapping), the destination-authenticated message can drain it. The withdrawal function never cross-checks `body.tokens` against the order's own `inputs[]` as declared and hashed into the commitment — it relies solely on the generic non-zero escrow guard, which is a per-(commitment, token) balance check, not a full order-membership check.

### Impact Explanation
If `body.tokens` in a peer-authenticated `RedeemEscrow`/`RefundEscrow` message can diverge from the order's actual `inputs[]] (which the source-chain `placeOrder` populated into `_orders[commitment][token]`), a message crafted by (or replayed through) an authenticated peer can redeem escrow for tokens/amounts that were never part of the filled/cancelled order, draining another token's escrowed balance under the same commitment slot or exceeding the amount actually owed for that order. This is a direct theft-of-funds / escrow-drain vector reachable purely from a relayed cross-chain message once authenticity (peer address) is satisfied, without any additional privilege.

### Likelihood Explanation
Medium: the attack requires control of, or forgery through, a registered peer-gateway address for `request.source`, which is the same trust boundary hawkBit's advisory operates within (the actor is "authenticated," but escapes an intended object-level restriction). Given deployments register many peer instances across chains, and the same `IntentsBase.onAccept` code path is shared by every deployment, a single compromised or buggy peer deployment (or a race in accounting across partial fills) is sufficient to reach this without any protocol-level consensus break.

### Recommendation
Bind `_withdraw` to the order's authoritative input list rather than an attacker/peer-supplied `tokens[]` array: require the message to carry (or the withdrawal to re-derive) the full committed `Order.inputs` and assert element-wise equality (token + not-exceeding escrowed amount) against what was actually escrowed for that specific commitment at placement time, or store the exact input token set per commitment and reject any `tokens[]` entry not present in it.

### Proof of Concept
1. User places an order with `inputs = [TokenA: 100]`, so `_orders[C][TokenA] = 100`.
2. Through routine accounting, a different order commitment C' also escrows `TokenA` (or the same address is reused with nonzero balance for C via a different code path/partial fill remnant).
3. A message authenticated as coming from the registered peer instance for `order.destination` is crafted with `WithdrawalRequest{commitment: C, tokens: [TokenA: <amount not tied to C's real fill/cancel outcome>], beneficiary: attacker}`.
4. `_authenticate` passes (peer address matches `_instances[source]`), `_withdraw` finds `_orders[C][TokenA] != 0` and transfers the specified amount to `attacker`, without ever confirming this token/amount corresponds to what was legitimately filled or refunded for commitment C.

**Uncertainty:** I could not fully verify, within the available index, that `_orders[commitment][token]` can actually be populated to a state where `body.tokens` can diverge from the true order inputs in a live deployment (e.g., whether `placeOrder`'s duplicate-token rejection and the fixed set of `order.inputs` fully closes this gap in practice for the `IntentGatewayV2.sol`/`ExtrinsicIntents.sol` pair, versus the `evm/tron/contracts/apps/IntentGatewayV2.sol` legacy variant which has the identical pattern). A full confirmation would require tracing every caller of `_withdraw`/`withdraw` end-to-end (including partial-fill and same-chain paths) to prove a concrete divergent-`tokens[]` message can be constructed by a legitimately-registered peer instance's normal operation versus only via source-chain compromise — I recommend a Devin session with full repo access to trace this exhaustively before treating this as a confirmed, exploitable finding rather than a design-hardening gap.
