### Title
Webhook shop domain is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` only validates the HMAC over the raw request body, then trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken directly from unauthenticated HTTP headers when constructing the `WebhookMetadata` that is handed to the app's `WebhookHandler`. Because the shared `client_secret`/`api_secret_key` HMAC never binds the `shop-domain` header to the signed payload, any party that can obtain one genuinely-signed webhook body (e.g., by installing the app on their own shop) can replay that exact body with a forged `shop-domain` header and have it accepted as an authentic webhook for a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely outside the HMAC-signed data: [2](#0-1) 

`Registry.process` validates only this body-based HMAC via `Utils::HmacValidator.validate(request)`, and then forwards `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`, all header-derived) unchanged into `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely over `verifiable_query.to_signable_string`, i.e. the raw body, with no shop binding: [4](#0-3) 

The identity binding that should hold is: `shop authenticated by HMAC == shop the handler acts on`. Here, the `shop` value the handler receives is never part of the signed bytes, so this equality is not enforced — the verified bytes (raw body) and the bytes acted upon (headers, including `shop-domain`) are disjoint. The gem's own documentation instructs apps to key downstream logic (job enqueue, session/shop lookup) directly on `data.shop`: [5](#0-4) 

### Impact Explanation
Since the `client_secret`/`api_secret_key` used to compute webhook HMACs is shared across every shop that installs the same app (it is not per-tenant), any actor who can install the app on a shop they control can obtain a validly-signed webhook body for a topic of their choosing. By capturing that raw body/HMAC pair and re-sending it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop, `Registry.process` will pass HMAC validation (body unchanged) and dispatch a `WebhookMetadata` claiming to originate from the victim shop. Any handler that trusts `data.shop` for tenant-scoped actions (loading the victim's session/access token, writing to the victim's records, enqueuing jobs keyed by `shop_domain` as shown in the gem's own example) is exposed to cross-tenant data confusion/injection using attacker-controlled body content attributed to another tenant.

### Likelihood Explanation
Exploitability requires only an ability to install the target app on an attacker-controlled shop (a normal, unprivileged action many "public" Shopify apps allow) and the ability to send an HTTP POST with modified headers to the app's public webhook endpoint — no `api_secret_key`, access token, or other stolen credential is needed. This is fully triggerable by an unprivileged internet user relative to the app's threat model.

### Recommendation
Bind the shop identity to the signed material before trusting it: either include the `shop-domain` header in the HMAC-signable string alongside the body, or — for apps using this gem — require the handler layer to cross-check `data.shop` against the tenant that is actually expected (e.g., match against a shop known to have `webhook_id` registered, or against the shop embedded in the JSON body payload itself where Shopify includes it). At minimum, the library should not present `shop` as an implicitly trustworthy field in `WebhookMetadata` without documenting that it is unauthenticated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering a genuine webhook (e.g., `orders/create`) signed by Shopify with the app's shared `client_secret`.
2. Attacker captures the raw POST: body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B`).
3. Attacker resends the same `B`/`H` to the app's webhook route, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and matches `H`, passing validation.
5. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and invokes the app's handler with attacker-controlled body content attributed to the victim shop.

          received_signature = verifiable_query.hmac
