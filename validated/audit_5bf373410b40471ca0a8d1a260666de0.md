### Title
Webhook shop-domain header not covered by HMAC, allowing cross-tenant shop spoofing on otherwise-valid webhook signatures - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC solely against that body. The `shop` (and `topic`, `webhook_id`, `api_version`) values, however, are taken directly from HTTP headers that are never included in the signed material. This breaks the intended binding: `hmac(body) == valid` should imply `shop header == the shop that produced that body`, but the gem only enforces `hmac(body) == valid`, independent of which shop header accompanies it.

### Finding Description
In `lib/shopify_api/webhooks/request.rb`: [1](#0-0) 
`shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, while `to_signable_string` returns only `@raw_body`.

`ShopifyAPI::Webhooks::Registry.process` validates the request using only this signable string: [2](#0-1) 
It calls `Utils::HmacValidator.validate(request)`, which computes `HMAC(secret, request.to_signable_string)` and compares it to `request.hmac`: [3](#0-2) 

Since the HMAC only covers `@raw_body`, the `shop`, `topic`, `webhook_id`, and `api_version` header values can be freely modified by anyone who can produce (or replay) a body/HMAC pair, without invalidating the signature. The gem then constructs `WebhookMetadata` using the unauthenticated `shop` value and passes it straight to the app's handler: [4](#0-3) 

Because Shopify apps typically share a single `client_secret` across all installing shops, any shop that installs the app can legitimately trigger a webhook for itself and obtain a validly-signed `(body, hmac)` pair (the secret used to compute the HMAC is the app-level secret, not a per-shop secret). That attacker-controlled shop can then replay the exact same body/HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still returns `true` (it never inspects the shop header), so `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the victim's domain and attacker-chosen `body`.

The gem's own documentation confirms `shop` is presented to the handler as a trusted identifier with no additional binding described: [5](#0-4) 
There is no guidance instructing host apps to independently authenticate the `shop` header against anything cryptographically bound to the payload — the library's `process` method is documented as the complete verification step ("This will verify the request did indeed come from Shopify..."): [6](#0-5) 

### Impact Explanation
This is a cross-tenant identity-binding break: a value acted upon (`shop`) is not covered by the cryptographic check that is supposed to authenticate the whole webhook. An attacker who is a legitimate (even free/trial) merchant of the app can forge webhook deliveries that the host app's handler will process as if they originated from a different shop, since `Registry.process` reports the request as fully verified. Depending on how the host app uses `data.shop` (e.g., to look up/update per-tenant records, attribute orders, or select which access token/session to act with), this can result in cross-tenant data corruption or the attacker's webhook payload being written into another merchant's tenant data — satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Exploitation requires only that the attacker control at least one shop that has installed the target app (a normal, unprivileged position for any Shopify merchant/developer who installs a public app), and the ability to send arbitrary HTTP requests to the app's public webhook endpoint. No access to the app's `client_secret`, access tokens, or any other shop's credentials is required — only observation/replay of one's own legitimately signed webhook traffic with a substituted header.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`/`api_version`) values in the HMAC-signed material, or otherwise cryptographically bind them to the verified payload, instead of relying on unauthenticated headers, e.g. incorporate the shop header into `to_signable_string` so `HmacValidator.validate` fails if the shop is altered post-signing.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) with a body they control.
2. Shopify signs the delivery using the app's single `client_secret`: `hmac = HMAC-SHA256(client_secret, raw_body)`.
3. Attacker intercepts/replays this request to the app's webhook endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` unchanged but replacing `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses `shop` from the (attacker-modified) header.
5. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(client_secret, raw_body) == hmac` — unaffected by the header change — and returns `true`.
6. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker_controlled_body, ...)`, and the host app processes attacker data under the victim shop's identity.
