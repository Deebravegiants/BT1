### Title
Simplex venue pricing derives fill rates from raw Uniswap V4 spot price (`sqrtPriceX96`) with no TWAP, enabling flash-loan/sandwich manipulation of solver fills - (File: `sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts`, `sdk/packages/simplex/src/strategies/fx.ts`)

### Summary
For curve-less "venue-priced" pairs, the Simplex FX filler prices intent-order legs directly from the current Uniswap V4 pool spot price (read from `slot0`/`sqrtPriceX96` on-chain), the same manipulable price primitive the external report warns about. There is no TWAP and no execution-cost/size adjustment; the only defense is an optional, coarse static-reference deviation guard. An attacker can move the pool price with a flash loan immediately before triggering a solver fill, causing the solver to size/price its output against a manipulated rate and hand over more value than the true price warrants.

### Finding Description
`UniswapV4LiquidityState.refresh()` fetches the pool's live `slot0` (`sqrtPriceX96`, `tick`) and rebuilds a `V4Pool` SDK object from it immediately before every planning/pricing call: [1](#0-0) 

`UniswapV4FundingPlanner.computeDirectPoolPriceUsd` then converts that instantaneous pool state directly into a USD price via `sdkPool.token0Price`/`token1Price` — the raw pool mid, with no averaging window: [2](#0-1) 

`getExoticTokenPrice` selects the highest-liquidity qualifying position and returns this spot-derived price to the caller: [3](#0-2) 

In `FXFiller` (`fx.ts`), `getVenueUsdPrice`/`venuePriceMemo` fetch this spot price per order evaluation and feed it straight into `resolveLegRates` → `computeLegPolicyOutput`, which prices the *entire* leg notional linearly at that single rate: [4](#0-3) [5](#0-4) 

The only mitigation is `checkPriceGuard`, which is optional per chain and only rejects a fill if the *live* quote deviates from a *static, operator-set reference price* by more than `maxDeviationBps`: [6](#0-5) 

This is precisely the bug class in the external report: pricing/slippage logic keyed off an on-chain AMM's spot state (`slot0`/`sqrtPriceX96`) rather than a manipulation-resistant TWAP. The project's own internal documentation acknowledges this gap explicitly: [7](#0-6) 

Additionally, the overfill clamp that historically bounded losses from a "manipulated venue price" has been disabled, and the code comment states this explicitly: [8](#0-7) 

### Impact Explanation
An attacker who moves the pool's `sqrtPriceX96` (e.g., via a flash-loan swap) inside a narrow window can:
1. Push the venue price outside the guard band **but the guard is optional/best-effort** (`priceGuard` is only configured per chain if the operator set `referencePrice`/`maxDeviationBps`; unconfigured chains are "unguarded" per the docs), or
2. Push the price within the guard's tolerated deviation band (`maxDeviationBps`, e.g. up to 200 bps = 2% by example config) while still extracting value, since the guard only checks static-vs-live deviation, not execution/impact cost, and `computeDirectPoolPriceUsd`/`computeLegPolicyOutput` apply the manipulated mid rate flat across the whole notional with no depth/impact term.

Because the solver (Simplex) is the entity delivering real tokens on `fillOrder`, a manipulated rate directly translates into the solver overpaying output tokens relative to the true market price — a fund loss for the solver, and because the overfill ceiling/clamp is explicitly disabled, there is no safety net capping this loss. This is reachable by any unprivileged actor able to submit a swap against the referenced Uniswap V4 pool immediately around the time an intent order the solver is filling is processed — i.e., through the intent-order/solver-fill path described in the Intent Gateway flow (`fillOrder`), a path explicitly in scope.

### Likelihood Explanation
Likelihood is Medium-to-High for pairs actually configured to use venue (pool) pricing (`[vault.uniswapV4]` with no bid/ask curves): the pool price is refreshed and consumed synchronously right before quoting/planning a fill, `checkPriceGuard` is optional and coarse, and the linear/no-impact pricing model means any transient price shift directly scales into the payout. Exploitation requires only capital to move the specific configured pool (which may be thin, as the docs' own price-guard rationale concedes: "a manipulated, stale, or thin pool"), well within a flash-loan attacker's reach.

### Recommendation
1. Replace or supplement spot `slot0`/`sqrtPriceX96` reads with a Uniswap V3/V4 TWAP oracle (or an off-chain trusted price feed) for venue pricing, especially before sizing/pricing a fill.
2. Make the price guard (`checkPriceGuard`) mandatory for all venue-priced chains/pairs, not opt-in, and consider bounding it dynamically (e.g., against a recent TWAP rather than only a static operator-set reference).
3. Re-enable and enforce the overfill/output ceiling (`maxOverfillBps`) as a hard cap rather than a warn-only log, so a manipulated or stale venue quote cannot cause unbounded overpayment.
4. Incorporate execution/size impact into `computeDirectPoolPriceUsd`/`computeLegPolicyOutput` instead of treating the raw pool mid as valid across the whole notional.

### Proof of Concept
Conceptual/root-cause based (no live exploit run, per report scope constraints):
1. Operator configures a curve-less pair (`[[pairs]] token0=USDC, token1=CNGN`) priced from `[vault.uniswapV4]`, per the documented pattern. [9](#0-8) 
2. Attacker submits a large swap against the referenced Uniswap V4 pool, shifting `sqrtPriceX96` significantly (or just within `maxDeviationBps` if a guard is configured, or entirely unguarded if it is not).
3. Attacker (or a colluding party) submits/triggers an intent order matched to this pair while the price is skewed.
4. `UniswapV4LiquidityState.refresh()` reads the skewed `slot0` on-chain; `computeDirectPoolPriceUsd` converts it to a skewed USD mid; `FXFiller.calculateProfitability` uses this rate via `computeLegPolicyOutput` to size the solver's output, producing an output amount inflated relative to the token's true value.
5. Solver's `fillOrder` transaction executes at this inflated output, transferring more value to the counterparty/attacker than intended; because the overfill clamp is disabled, nothing halts or reduces this payout. [10](#0-9)

	async getExoticTokenPrice(chain: string, exoticToken: string): Promise<Decimal | null> {
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}

	private computeDirectPoolPriceUsd(
		pos: HydratedV4Position,
		sdkPool: V4Pool,
		chain: string,
	): { exoticToken: string; priceUsd: Decimal } | null {
		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {
				exoticToken: c1,
				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

		if (c1 === usdc || c1 === usdt) {
			// currency1 is stable → exotic is currency0
			// token0Price = "token1 per token0" = USD per exotic
			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),
			}
		}

		return null
	}

	private async getVenueUsdPrice(chain: string, token1Address: string): Promise<Decimal | null> {
		if (this.fundingVenues.length === 0) return null

		// Prefer V4, fall back to others
		const v4 = this.fundingVenues.filter((v) => v.name === "UniswapV4")
		const venues = v4.length > 0 ? v4 : this.fundingVenues

		for (const venue of venues) {
			const usdPrice = await venue.getExoticTokenPrice(chain, token1Address)
			if (usdPrice?.isPositive()) return usdPrice
		}
		return null
	}

	/** Per-evaluation memo over `getVenueUsdPrice`, keyed by (chain, token1). */
	private venuePriceMemo(): (chain: string, token1Address: string) => Promise<Decimal | null> {
		const cache = new Map<string, Decimal | null>()
		return async (chain: string, token1Address: string) => {
			const key = `${chain}:${token1Address}`
			const cached = cache.get(key)
			if (cached !== undefined) return cached
			const price = await this.getVenueUsdPrice(chain, token1Address)
			cache.set(key, price)
			return price
		}
	}

	/**
	 * Validates a live venue quote against the static reference price for the chain.
	 * Returns true (pass) when no guard is configured, or no reference exists for the
	 * chain. Returns false when the quote (token1 per USD) deviates from the reference
	 * by more than `maxDeviationBps`, in which case the order must not be filled.
	 */
	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}

## Pool-Based Pricing

When **`[vault.uniswapV4]`** lists at least one position, cross-asset pairs without curves derive bid/ask prices from **Uniswap V4 pool state** (current tick). The pool acts as the price oracle instead of a static curve. Note this yields a **single** price used in both directions — a venue-priced pair has no bid/ask spread of its own, so its margin comes from `order.fees` alone.

With Uniswap V4 positions configured, you can **omit** `bidPriceCurve` and `askPriceCurve` on the pair. Pool pricing requires the pair's `token0` to be a USD stablecoin, and same-token pairs always need their curve. The optional **`spreadBps`** field (basis points) sets the slippage tolerance for on-chain LP redemptions; defaults to `50` (0.50%).

Uniswap V4 venue pricing uses pools that pair the exotic token with **USDC or USDT** (addresses from your chain config). When multiple positions exist for the same exotic token on a chain, the most-liquid qualifying pool's price is used.
