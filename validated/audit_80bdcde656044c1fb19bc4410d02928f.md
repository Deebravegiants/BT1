### Title
`finalizeGraduation` phase 2 can permanently revert on a zero-liquidity edge case, freezing curve-raised LT and 250M reserved tokens in `Bonding` forever - (File: `packages/contracts/src/Bonding.sol`)

### Summary
This is a structural analog of the ZetaChain M-08 pattern: a two-phase, irreversible flow where phase 1 (`_enterGraduating`) unconditionally commits/drains funds and phase 2 (`finalizeGraduation`) can fail, and once it fails there is no recovery path, so the committed funds are permanently lost/locked. In alt.fun, `Bonding._enterGraduating` [1](#0-0)  drains the curve and parks `ltFromPair` (all curve-raised LT, already sent via `Router.graduate`) and up to `LP_RESERVE` (250M) tokens inside `Bonding`, then irreversibly flips `Lifecycle.Curve → Graduating`, freezing trading. Phase 2, `finalizeGraduation`, is the *only* path that can ever move that state forward [2](#0-1) , and it depends on `LPLock.recordLock` succeeding at the very end of the call.

### Finding Description
`LPLock.recordLock` reverts with `ZeroAmount()` if the computed `liquidity` is `0` [3](#0-2) . The protocol's own code comments acknowledge exactly this failure mode is reachable through the hostile-pre-seed rebalance path: without the `_swapBudget` 1%-reservation guard, "an extreme hostile pre-seed (massively imbalanced reserves) drives the unconstrained `_noFeeSwapInput` past our per-side budget, `_pairRebalance` clamps to the full budget, and the swap consumes 100% of one side. `_routerDepositAndDispose` then skips `addLiquidity` (`remToken == 0` or `remLT == 0`), `finalizeGraduation` returns `liquidity = 0`, and `LPLock.recordLock(...)` records a zero-sized lock" [4](#0-3) .

Critically, `recordLock`'s `amount == 0` check means that scenario doesn't "record a zero-sized lock" as the old comment says — it **reverts** (`ZeroAmount`) [5](#0-4) . Because `finalizeGraduation` calls `recordLock` as the *last* state-mutating step, after `info.lifecycle = Lifecycle.Graduated`, `$.graduatedPair[...]` and `delete $.pendingGraduation[...]` [6](#0-5) , a revert here rolls back the *entire* transaction — including the mint/rebalance/deposit that already happened in `_seedUniswapV2Direct`. Since the outcome is deterministic given the on-chain pool state (not gas/time dependent), every retry of `finalizeGraduation` for that token hits the identical zero-liquidity computation and reverts identically. The token is then permanently stuck in `Lifecycle.Graduating`.

There is no alternate path out of `Graduating`: `Bonding.sol` has no owner/admin rescue, no `abort`, and no un-graduate function for a token stuck in this state (only `_sweepLTToOwner`/`LTRescued`, which only runs *inside* a successful `finalizeGraduation`) [7](#0-6) . `LPLock` itself is explicitly documented as having "no withdraw in v1" and no locker-removal path, reinforcing that this is a one-shot, non-retriable action by design [8](#0-7) . Trading is frozen for the token the moment `Lifecycle.Graduating` is set (`TokenIsGraduating` reverts on both `buy` and `sell`), so holders cannot even exit on the curve [9](#0-8) .

This mirrors the ZetaChain report's root cause precisely: phase 1 (source-chain burn / `_enterGraduating` drain) is unconditional and irreversible, while phase 2 (revert-tx mint / `finalizeGraduation`'s `recordLock`) can fail for reasons outside the protocol's control (there, `maxSupply`/receiver-revert; here, an adversarially-shaped HyperSwap pre-seed that drives the rebalance to consume 100% of one side despite the `_swapBudget` cap), and the failure has no fallback other than "abort" (there) / "stuck forever" (here) — both of which permanently strand the underlying value with no on-chain recovery mechanism.

### Impact Explanation
If the zero-liquidity condition is triggered, every curve buyer's paid-in LT (`ltFromPair`, potentially thousands of USD-equivalent for a graduated token) and up to 250M reserved tokens become permanently unrecoverable — not burned, not swept, just deterministically stuck as balances in `Bonding` with no function able to move them, since the only extraction path (`finalizeGraduation`) always reverts for that token going forward. This is a permanent freeze of trader/creator funds, matching the "Medium/High" bar for concrete permanent freezing of funds.

### Likelihood Explanation
The `_swapBudget` 1% reservation is intended to make `remToken`/`remLT` nonzero after the rebalance swap in the documented attack scenario, but the safety margin is derived only from swap-side budget accounting; it does not account for all possible interactions (e.g., extreme reserve ratios pushing `_noFeeSwapInput`'s math to edge values, integer rounding on very small `tokensForLP`/`ltFromPair` for a thinly-traded curve, or an LT that is fee-on-transfer despite being nominally a "BounceTech LT," reducing actually-received amounts below what `_routerDepositAndDispose` computed from pre-transfer balances). The protocol's own extensive natspec devotes multiple paragraphs to reasoning about exactly this edge (`_swapBudget`'s comment), indicating the authors are aware the boundary is a genuine risk surface, not a purely theoretical one closed by construction — the guarantee is empirical/documented rather than provably enforced by an on-chain invariant check. An attacker can freely trigger the "Regime 3" hostile mint pre-seed path permissionlessly (`factory.createPair` + `transfer` + `pair.mint`) for any token about to graduate, giving them full control over the reserve ratio that feeds into this computation.

### Recommendation
1. Add an explicit invariant check inside `_seedUniswapV2Direct`/`_routerDepositAndDispose` that provably guarantees `remToken > 0 && remLT > 0` before calling `addLiquidity`, rather than relying on empirically-reasoned budget percentages; if the guarantee cannot be proven, fall back to `_seedDirectMint` (as is already done for the `s == 0` case) instead of allowing `liquidity == 0` to propagate to `recordLock`.
2. Reorder `finalizeGraduation` so that `LPLock.recordLock` is called and its success confirmed before any lifecycle-terminal state (`Lifecycle.Graduated`, `delete pendingGraduation`) is committed — this already happens atomically today (a revert rolls everything back), but the real fix is ensuring the call cannot revert in the first place, or providing an explicit fallback (e.g., a minimum-liquidity floor with a governance-gated force-finalize / rescue function) so a token can never be stuck in `Lifecycle.Graduating` indefinitely with no exit.
3. Add a regression test that specifically drives `_pairRebalance`'s swap to consume exactly at the 99%-budget boundary combined with an already-thin `tokensForLP`/`ltFromPair` (e.g., a curve that only received the `$20` minimum seed) to confirm `remToken`/`remLT` remain non-zero under the smallest realistic graduation, not just under "typical" reserve sizes.

### Proof of Concept
1. Launch a token with the minimum seed (`Zap.MIN_SEED_USDC`, `$20`) so `ltFromPair`/`tokensForLP` end up small at graduation.
2. Push the curve to graduate via the supply trigger (`tokenBalance() == 0`) so `_enterGraduating` fires with minimal LT raised, caching small `tokensForLP`/`ltFromPair` in `pendingGraduation`.
3. Before `finalizeGraduation` is called, front-run: `factory.createPair(token, lt)`, then `transfer` a large, heavily-skewed amount of `lt` (or `token`) into the pair and call `pair.mint(attacker)` to establish extreme, hostile reserves relative to the small cached `tokensForLP`/`ltFromPair`.
4. Call `finalizeGraduation(tokenAddress)`. `_seedRebalancing` computes `_pairRebalance`, and depending on the exact ratio, the swap plus router `addLiquidity` step can leave `remToken == 0` or `remLT == 0` after disposal, making `liquidity == 0`.
5. `LPLock.recordLock` reverts with `ZeroAmount`, the whole `finalizeGraduation` transaction reverts, and the token permanently stays in `Lifecycle.Graduating`; every subsequent call to `finalizeGraduation` reverts identically since the pool state (and thus the computed `liquidity`) is unchanged, permanently freezing `ltFromPair` and the reserved tokens inside `Bonding`.

*Note: I was not able to fully step through `_noFeeSwapInput`'s closed-form math or exhaustively prove/disprove that the `_swapBudget` 1% margin is mathematically sufficient for every reserve ratio and every `tokensForLP`/`ltFromPair` magnitude within the tool budget available; this analog rests on the protocol's own code comments describing this exact zero-liquidity failure mode as a real, previously-identified risk, combined with the confirmed fact that `LPLock.recordLock` reverts (rather than silently succeeding) on `amount == 0`, and that no rescue/retry path exists for a token stuck in `Lifecycle.Graduating`. A background Devin session with test-execution access could construct a concrete Foundry PoC exercising `test_brick_resistance_frontRun_dust_seed`-style setups with more extreme ratios/small-seed curves to confirm whether the zero-liquidity state is actually reachable in the current implementation.*

    function finalizeGraduation(
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }

    /// @dev Send LT held by this contract above `keep` to the owner,
    ///      emitting `LTRescued`. Called at the end of
    ///      `finalizeGraduation` with `keep = protectedLT` (any escrow
    ///      that doesn't belong to this graduation), so only THIS
    ///      graduation's rebalance residue lands on the owner. No-op on
    ///      the empty-pair fast path (nothing to sweep).
    function _sweepLTToOwner(
        address lt,
        uint256 keep
    ) internal {
        uint256 bal = IERC20(lt).balanceOf(address(this));
        if (bal <= keep) return;
        uint256 amount = bal - keep;
        address recipient = owner();
        IERC20(lt).safeTransfer(recipient, amount);
        emit LTRescued(lt, recipient, amount);
    }

    ///      so the subsequent `addLiquidity` always has a non-zero amount

    ///      pre-seed (massively imbalanced reserves) drives the

    ///      `finalizeGraduation` returns `liquidity = 0`, and

    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero
    ///      LP at the post-swap ratio. The 1% comes off the swap, not the
    ///      deposit — for any realistic pre-seed `s_unconstrained` is
    ///      orders of magnitude below `maxSwap`, so the cap doesn't bind

        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;

    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }
