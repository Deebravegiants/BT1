### Title
Ambiguous `"::"`-concatenated seed in `create_token_seed` allows collection/token name collisions to the same object address - (File: `aptos-move/framework/aptos-token-objects/sources/token.move`)

### Summary
`token::create_token_seed` builds a token's deterministic seed by naively concatenating `collection_name || "::" || token_name` with no length-prefixing or separator-escaping [4](#0-3) . Because `"::"` is permitted as ordinary content inside both a collection name and a token name (only a max-length check is enforced), two semantically distinct `(collection, name)` pairs can produce byte-identical seeds, and therefore the identical deterministic object address via `object::create_object_address(creator, seed)` [5](#0-4) . This is the same root-cause class as the Linea bug: an identifier scheme that fails to disambiguate two distinct logical entities collapses them onto the same custody slot.

### Finding Description
The token address derivation is:
```
seed = collection_bytes || "::" || name_bytes
obj_addr = sha3_256(creator || seed || 0xFE)
``` [6](#0-5) 

Neither `collection::create_collection` nor `token::create` reject `"::"` inside `description`/`name`/`collection` strings — only `ECOLLECTION_NAME_TOO_LONG` / `ETOKEN_NAME_TOO_LONG` bounds are enforced [7](#0-6) [8](#0-7) . Consequently, for the same creator address, `(collection = "A", name = "B::C")` and `(collection = "A::B", name = "C")` yield the identical concatenated byte string `"A::B::C"`, hence the identical `obj_addr`.

`create_object_internal` will only allow the *first* creation to succeed — the second attempt aborts with `EOBJECT_EXISTS` [9](#0-8) . This means whichever `(collection, name)` pair is submitted first "wins" the address, and the token/collection state stored under that address (`Token.collection`, `Token` name/description fields) legitimately belongs to that first submitter's chosen collection/name — but any code path (marketplace, indexer, third-party contract) that reconstructs the expected address purely from the *other* colliding `(collection, name)` pair via `create_token_address`/`create_token_address_with_seed` will resolve to an object whose actual `Token.collection` differs from what the caller assumed [10](#0-9) .

### Impact Explanation
Any protocol or marketplace that trusts `create_token_address(creator, collection, name)` to uniquely and safely identify "the token from collection X named Y" can be tricked: an attacker who front-runs by creating `(collection="A::B", name="C")` under the *same creator address* (e.g., a resource account or well-known creator whose collections are permissionlessly extendable, or simply the attacker being the creator of both) squats the address that a legitimate `(collection="A", name="B::C")` token would later resolve to. Since `Object<Token>` addresses are used directly as capability/authorization anchors in downstream systems (transfer refs, royalty payout targets, marketplace listings keyed by `create_token_address`), a caller that computes the expected token address off-chain/on-chain and interacts with "that token" (e.g., transferring funds, verifying ownership, checking royalty object) can be misled into operating on an attacker-controlled token object instead of the intended one, or the legitimate creation can be permanently blocked (`EOBJECT_EXISTS`), causing denial of the intended token's minting.

This requires the collision to occur within a single creator's namespace (since `creator` is part of the seed), which narrows real-world exploitability compared to the Linea bridge case (there, unrelated parties collided). It is most impactful for creators who allow **permissionless collection creation under one account** (e.g., resource-account-backed launchpads/marketplaces where any user can trigger `create_collection`/`create_token` calls with attacker-chosen names under a shared resource-account signer) — a common pattern in Move-based NFT platforms.

### Likelihood Explanation
Moderate-to-low likelihood on core `aptos_token_objects`, because most marketplaces creating tokens are the sole namespace owner and choose collection/name themselves rather than accepting fully attacker-controlled strings. However, any framework built on top (e.g., a permissionless collection factory under a single resource-account creator, common in launchpad/marketplace dApps) that lets end users freely choose collection and token name strings is directly exposed, since the framework itself performs no `"::"`-rejection or length-prefixed encoding.

### Recommendation
Change `create_token_seed`/`create_token_name_with_seed` to use an unambiguous, length-prefixed encoding (e.g., BCS-serialize `(collection, name)` as a tuple, or prefix each field with its byte length) instead of a bare `"::"` separator, so that no two distinct `(collection, name)` pairs can ever produce the same seed bytes. Alternatively, explicitly reject `"::"` substrings inside collection and token names at creation time.

### Proof of Concept
```move
// Same creator address for both flows
let seed1 = token::create_token_seed(&string::utf8(b"A"), &string::utf8(b"B::C"));
let seed2 = token::create_token_seed(&string::utf8(b"A::B"), &string::utf8(b"C"));
assert!(seed1 == seed2, 0); // both equal b"A::B::C"

let addr1 = object::create_object_address(&creator, seed1);
let addr2 = object::create_object_address(&creator, seed2);
assert!(addr1 == addr2, 0); // identical deterministic object address

// First creator to submit wins the address; the second create_named_object call
// (via token::create) will abort with EOBJECT_EXISTS in object::create_object_internal,
// or — if the first creation happens after some third party already computed addr2
// expecting collection "A::B"/name "C" — that party's assumption about which
// collection "owns" addr2 is now false.
``` [11](#0-10) [12](#0-11) 

**Note on confidence**: I was unable to fully trace every downstream consumer of `create_token_address`/`create_token_address_with_seed` across the broader ecosystem (e.g., specific marketplace or launchpad contracts within this repo) due to index scope limits, so the concrete "high/critical" custody impact (actual fund transfer to the wrong party) is demonstrated at the object-address-collision level but not confirmed end-to-end against a specific value-transfer consumer in this codebase. If a full trace into a specific marketplace/launchpad module confirming direct fund misdirection is required, a Devin session with full repo access would be needed to verify.

    /// Named objects are derived from a seed, the token's seed is its name appended to the collection's name.
    public fun create_token_seed(collection: &String, name: &String): vector<u8> {
        assert!(name.length() <= MAX_TOKEN_NAME_LENGTH, error::out_of_range(ETOKEN_NAME_TOO_LONG));
        let seed = *collection.bytes();
        seed.append(b"::");
        seed.append(*name.bytes());
        seed
    }
