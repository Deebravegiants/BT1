### Title
Pool-wide DoS via `need_take_pnl_pc`/`need_take_pnl_coin` underflow in `calc_total_without_take_pnl_no_orderbook` freezes Deposit/Withdraw/Swap - ([File: program/src/math.rs], [File: program/src/processor.rs])

### Summary
Raydium's AMM tracks accumulated (but not-yet-swept) protocol PnL in `AmmInfo.state_data.need_take_pnl_pc` / `need_take_pnl_coin`. Every user-facing instruction that touches the pool (`Deposit`, `Withdraw`, `SwapBaseIn`, `SwapBaseOut`, `WithdrawPnl`) first computes the "real" tradable balances by subtracting these accrued values from the live vault balances via `Calculator::calc_total_without_take_pnl_no_orderbook`, using `checked_sub`. Because `need_take_pnl_pc`/`need_take_pnl_coin` only ever grows during normal operation (via `calc_take_pnl`, invoked from `Deposit`/`Withdraw`/`Swap`) and is only reset by the privileged `pnl_owner` calling `WithdrawPnl`, it is disconnected from the actual vault balance once LPs start withdrawing liquidity. If enough LP withdrawals draw the actual vault balance down while `need_take_pnl_*` keeps growing from swap fee accrual, the vault balance can fall below the recorded `need_take_pnl_*`, causing the `checked_sub` to fail and return `AmmError::CheckedSubOverflow`, which reverts the transaction.

### Finding Description
`Calculator::calc_total_without_take_pnl_no_orderbook` computes: [1](#0-0) 

This is called from every liquidity-affecting user path: `process_deposit` [2](#0-1) , `process_withdraw` [3](#0-2) , `process_withdrawpnl` [4](#0-3) , and both swap entry points (`process_swap_base_in`/`process_swap_base_out`, called before the swap-amount math shown at `program/src/processor.rs:1976-1982`).

`need_take_pnl_pc`/`need_take_pnl_coin` are increased inside `calc_take_pnl` whenever the pool's k has grown relative to `target_orders.calc_pnl_x/calc_pnl_y` (i.e., after swap fees accumulate): [5](#0-4) 

These fields are reduced to zero only in `process_withdrawpnl`, gated by a signer check requiring `amm_config.pnl_owner` (a privileged/permissioned account): [6](#0-5) [7](#0-6) 

Critically, `process_withdraw` — which any unprivileged LP can call — never decrements `need_take_pnl_pc`/`need_take_pnl_coin`; it only removes coin/pc/lp from the pool's actual vault balances via `Invokers::token_transfer_with_authority` and `Invokers::token_burn`: [8](#0-7) 

So the accrued "IOU" (`need_take_pnl_*`) keeps growing from trading fees while the real vault balance can be depleted arbitrarily via `Withdraw`, which is a fully unprivileged instruction reachable from a single transaction with attacker (or any user)-chosen accounts. Once `amm_pc_vault.amount < need_take_pnl_pc` (or the coin equivalent), the very next call to `calc_total_without_take_pnl_no_orderbook` in any `Deposit`, `Withdraw`, `SwapBaseIn`, or `SwapBaseOut` returns `AmmError::CheckedSubOverflow` and the transaction is reverted for every user of that pool — not just the account that triggered the imbalance.

This exactly mirrors the reported bug class: a cumulative, unilaterally-incrementing "ledger" state variable (`netAssetDeposits` in the original / `need_take_pnl_pc`/`coin` here) subtracted via `checked_sub` from a value it isn't strictly bounded by, causing legitimate user operations to revert with an underflow-style error.

### Impact Explanation
Once triggered, the pool becomes fully unusable for ordinary users: `Deposit`, `Withdraw`, `SwapBaseIn`, and `SwapBaseOut` all revert with `CheckedSubOverflow`, freezing LP redemption and trading for the entire pool until the privileged `pnl_owner` intervenes by calling `WithdrawPnl`. This is a pool-wide denial of service impacting all depositors/traders, not just a single actor's funds, matching the "medium" classification precedent in the referenced report (temporary but externally-triggerable freezing, correctable only by a privileged party, not by user action).

### Likelihood Explanation
The condition requires the actual vault balance to fall below the accumulated `need_take_pnl_*` value. This is plausible on any active pool where LPs are net-withdrawing liquidity faster than the `pnl_owner` sweeps accrued PnL, since `need_take_pnl_*` is monotonically non-decreasing except for the permissioned sweep. No attacker privilege is required to reach this state — ordinary `Withdraw` calls by any LP progressively shrink the vault while swap fee accrual (also from ordinary `Swap` calls) keeps increasing `need_take_pnl_*`. Whether this can be forced deterministically within a single attacker-controlled transaction (vs. requiring many transactions/LPs over time) is not fully confirmed from the indexed code; reaching the exact threshold likely requires accumulated activity rather than a single crafted call, which is a mitigating factor.

### Recommendation
Bound `need_take_pnl_pc`/`need_take_pnl_coin` growth or decay proportionally to LP withdrawals (e.g., scale down the accrued-but-unswept PnL when LP supply decreases), or clamp the subtraction with `saturating_sub` combined with correspondingly reducing `need_take_pnl_*` so it can never legitimately exceed the real vault balance, ensuring `Deposit`/`Withdraw`/`Swap` cannot be permanently gated on a privileged `WithdrawPnl` call.

### Proof of Concept
1. Pool is created and receives sustained swap volume; `calc_take_pnl` (via `Deposit`/`Withdraw`/`Swap` calls) repeatedly increases `amm.state_data.need_take_pnl_pc` and `need_take_pnl_coin` as trading fees accumulate [5](#0-4) .
2. `pnl_owner` does not call `WithdrawPnl` for an extended period (this instruction is permissioned, so ordinary users cannot trigger the sweep themselves) [6](#0-5) .
3. LPs progressively call the unprivileged `Withdraw` instruction, draining real coin/pc from `amm_coin_vault`/`amm_pc_vault` without any corresponding reduction of `need_take_pnl_pc`/`need_take_pnl_coin` [8](#0-7) .
4. Once `amm_pc_vault.amount < amm.state_data.need_take_pnl_pc` (or the coin equivalent), any subsequent `Deposit`, `Withdraw`, `SwapBaseIn`, or `SwapBaseOut` calls `Calculator::calc_total_without_take_pnl_no_orderbook`, whose `checked_sub` fails and returns `AmmError::CheckedSubOverflow`, reverting the transaction [9](#0-8) .
5. All remaining LPs and traders are now blocked from interacting with the pool until the permissioned `pnl_owner` calls `WithdrawPnl` to zero out `need_take_pnl_pc`/`need_take_pnl_coin` [7](#0-6) .

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
