### Title
Webhook shop-domain and topic headers are trusted for tenant identification but are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to identify the tenant and dispatch the payload are read straight from unauthenticated HTTP headers. An attacker who can generate at least one legitimately-signed webhook (e.g. by installing the app on their own store) can replay that valid `(body, hmac)` pair while swapping the `x-shopify-shop-domain` header to a victim shop, and the gem will accept it as authentic and hand it to the app's handler labeled as coming from the victim shop.

### Finding Description
The equality that should hold is: `shop identified by the HMAC == shop delivered to the handler`. In this gem it does not.

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are pulled from headers that are never part of the signed material: [2](#0-1) 

`Registry.process` validates only the HMAC over that signable string (i.e., the body) and then unconditionally trusts `request.shop`/`request.topic` to build the metadata passed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` confirms this — it only ever signs/compares `verifiable_query.to_signable_string`, which for webhooks is just `@raw_body`: [4](#0-3) 

Because the shop-identifying header is outside the HMAC's coverage, any two requests with the same body and secret produce the same valid HMAC regardless of which shop's domain header accompanies them. An attacker who legitimately installs the app on their own development/test store can capture a real `(raw_body, x-shopify-hmac-sha256)` pair from a webhook Shopify sends them, then resend that exact body/HMAC pair to the app's webhook endpoint with `x-shopify-shop-domain` rewritten to a target/victim shop. `Registry.process` will validate the HMAC successfully (it only checks the body) and invoke the handler with `WebhookMetadata#shop` set to the victim's domain, even though the payload actually originated from the attacker's own shop.

### Impact Explanation
This breaks the tenant boundary the webhook mechanism is meant to enforce: the app's business logic (typically keyed by `shop` to load/mutate per-merchant records, e.g. `app/uninstalled`, `orders/create`, `shop/update`, GDPR webhooks) will process attacker-controlled data under an incorrect shop identity. Depending on how the host application consumes `WebhookMetadata#shop`, this can lead to cross-tenant data corruption or unauthorized actions attributed to a shop the attacker does not control — matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation requires only that the attacker can obtain one valid signed webhook body/HMAC pair for a topic that has attacker-controllable content (many Shopify webhook topics allow the store owner to shape the body, e.g. by naming products/orders in their own store), and that they know or can guess the target shop's `myshopify.com` domain (which is not secret). No access token, `client_secret`, or privileged account is required — only an ordinary Shopify store, which is the "unprivileged internet user" bar for this class of finding.

### Recommendation
Bind the shop identity to the signature verification: include the shop domain (and ideally topic/webhook id) header values into the HMAC-signable string, or otherwise cryptographically bind the delivered shop to the signed payload before trusting it. At minimum, document/require that consuming apps cross-check `request.shop` against an independently-known installed-shop list before acting on webhook data, since the gem itself does not bind that header to the signature.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`) with an attacker-crafted order payload.
2. Attacker captures the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent for that webhook — both are valid for the app's `api_secret_key`.
3. Attacker POSTs the identical body and HMAC header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `request.to_signable_string` (`@raw_body`) — this still matches, so validation passes.
5. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: <attacker-controlled>, ...)`, causing the host app to process attacker data as if it belonged to `victim.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
