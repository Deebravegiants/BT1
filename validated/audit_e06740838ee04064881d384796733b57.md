### Title
RAY-value overflow in accrual permanently bricks a market — every verb panics inside `global_sync` before the borrow-index cap can engage - (File: contracts/pool/src/interest.rs)

### Summary
The analog of CVE-2019-6468 (an assertion failure that crashes the daemon once a specific feature combination is enabled) is the panic path inside interest accrual. Every state-changing entrypoint on a pool market first runs `interest::global_sync`, which evaluates `scaled_to_original(borrowed, borrow_index)` per compound chunk. When `borrowed_scaled * borrow_index` exceeds the `i128` domain, `common::math::fp_core` panics with `GenericError::MathOverflow`. Because the panic happens *before* any mutation, and because accrual is unconditionally first in every verb (`supply`, `borrow`, `withdraw`, `repay`, `seize_positions`, `net_settle`, `recapitalize`, `claim_revenue`, `update_indexes`), the market enters a state where no operation can ever succeed again — the exact shape of the BIND crash: the code path that is supposed to run on every request is the one that aborts.

### Finding Description
`global_sync` chunks elapsed time and calls `accrue_chunk`, which calls `common::rates::accrue_step` to grow the borrow index and compute debt value [1](#0-0) . Debt value is computed as `scaled_to_original(borrowed, borrow_index)` = `borrowed * borrow_index / RAY`; the `mul_div` widens to `I256` only for intermediates and panics with `MathOverflow` if the final `i128` does not fit [2](#0-1) . `MAX_BORROW_INDEX_RAY` caps the *index* at `1e36`, but the *value* `borrowed_scaled * index` overflows `i128` well before that cap when the scaled borrow base is large: scaled shares are RAY-denominated, so a market holding on the order of `1e29` raw scaled debt crosses the value ceiling while the index is still far below `MAX_BORROW_INDEX_RAY`.

The kill condition is reached via unprivileged calls only:
1. `controller.supply` deposits a whale-sized amount (caps are governance-set and can saturate to `i128::MAX` per `calculate_scaled_cap`); the token-to-RAY input bound is ~`i128::MAX / 10^(27-d)` ≈ 170 billion whole tokens for 18-decimal assets, so the position fits.
2. `controller.borrow` draws ~98% utilization.
3. Time accrues at high utilization (steep curve segment). Anyone — including the attacker — then calls the permissionless `update_indexes` (or any withdraw/repay/liquidate). The first accrual that pushes `borrowed * borrow_index` past `i128::MAX` panics inside `scaled_to_original`, and `last_timestamp` is never advanced, so the same panic repeats on every subsequent call forever.

The protocol's own harness confirms the freeze: after the cliff is hit, `try_update_indexes_for`, `try_withdraw_raw` and `try_repay` all fail with `MATH_OVERFLOW`, and the borrow index is still below `MAX_BORROW_INDEX_RAY` (the cap never engages) [3](#0-2) . Since `recapitalize` and `seize_positions` also accrue first (`ops::synced_market` → `global_sync`), there is no recovery path — not even forced socialization or governance intervention can execute, because no pool mutator can be entered without tripping the panic.

### Impact Explanation
Permanent freezing of funds, market-wide. Once the value-overflow state is reached, all supplier principal, all outstanding interest, and all protocol revenue in that market are unrecoverable: withdraw, repay, liquidate, clean-bad-debt seizure and recapitalize all abort in `global_sync` before touching state. This is strictly worse than a fail-closed guard (which is input-dependent): the market's *state itself* becomes poisonous, analogous to the CVE's assertion killing the process on the nxdomain-redirect+ECS path. No privileged rescue exists — the panic is in the shared accrual step, so an upgrade is the only remedy, and collateral seized as `SeizeMode::Credit` share positions in other markets referencing these indexes also becomes illiquid through the same pool calls.

### Likelihood Explanation
Low–Medium. Two compounding requirements must both hold: (a) a single market must accumulate scaled borrow on the order of `1e29` raw (≈170 billion whole tokens at 18 decimals, or proportionally more shares at lower supply indexes after bad-debt write-downs), and (b) high utilization must persist for the years needed for index growth to push the product over `i128::MAX` — the harness reproduces the cliff in "a few years" at 98% utilization on the steep segment of the XLM curve [4](#0-3) . The capital requirement is real but bounded by the admitted `i128` input maximum, not by token supply economics; on a low-decimals, low-price token with lifted caps it is materially cheaper. The attacker needs no privilege — `update_indexes` is callable by anyone — and accrual can be accelerated only by time, so this is a latent landmine rather than a quick trigger. Documentation acknowledges the arithmetic bound exists ("value overflow can occur before the index ceiling and block repayment/withdrawal"), but no mitigation path is implemented, so it is reported as a finding rather than dismissed.

### Recommendation
Break the panicking dependency on the full debt value inside `accrue_step`:
- Compute the accrual step from the *index delta* alone and clamp the product: if `borrowed * new_index` exceeds `i128::MAX`, saturate the booked borrow value (or cap `borrow_index` at `i128::MAX / borrowed`) instead of panicking, so exits and repayments remain possible at the saturated valuation.
- Alternatively, advance `last_timestamp` and commit the capped index *before* evaluating debt value, so a single over-large market degrades to a zero-interest state rather than a permanently poisoned one.
- Add a controller-side guard or emit an event when `borrowed` approaches `i128::MAX / MAX_BORROW_INDEX_RAY`, and gate `supply`/`borrow` entry with `require_backed_market`-style headroom against the representable value ceiling, not just the index ceiling.

### Proof of Concept
Reproduced by the existing harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` [5](#0-4) :

```rust
// BIG18 market, 18 decimals, XLM curve, caps lifted to i128::MAX
let principal = BILLION * 10i128.pow(18);          // ~1e29 base units supplied
t.supply_raw(BOB, "BIG18", principal);
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98); // 98% utilization

// advance years at high utilization until the value product overflows
loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; }
}
// => Error(Contract, MATH_OVERFLOW) from scaled_to_original inside global_sync

// market is permanently bricked:
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0),  errors::MATH_OVERFLOW);
// last borrow_index < MAX_BORROW_INDEX_RAY — the index cap never engaged
```

Reachability is fully unprivileged: `supply`, `borrow`, and `update_indexes` are all callable by any address; the panic is deterministic once the arithmetic bound is crossed, and no entrypoint bypasses `global_sync`.

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Applies one compound step of `delta_ms` to indexes and protocol revenue.
///
/// The arithmetic lives in [`accrue_step`], shared with the read-only
/// `simulate_update_indexes` so the view and the mutator cannot drift.
fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);
}

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
    std::println!(
        "ray-value cliff reached after {years} years at 98 percent utilization on the XLM curve; last index x{:.1}",
        last.borrow_index as f64 / RAY as f64
    );
}
