**Why the ParaSpace bug class doesn't map here:**

The ParaSpace vulnerability is rooted in an on-chain smart contract's `Credit` struct lacking a marketplace identifier, so a signed credit authorization for one `orderId`/marketplace could be replayed against a different, cheaper order in a different marketplace adapter. This requires the *signer* (the marketplace protocol) to construct and verify a domain-insufficient signed payload that is later matched against attacker-supplied order data.

The hydra repo is the Exodus Wallet SDK — it does not implement or verify any such "credit"/order-matching structure. Its signing surfaces are:
- `@exodus/message-signer` (`features/message-signer/src/module/seed-signer.ts`, `hardware-signer.ts`) — signs whatever raw message or EIP-712 typed data a caller supplies via `signMessage`, with EIP-712 domain separation handled entirely by the caller's own typed-data domain object, not by wallet-side credit/order matching logic. [1](#0-0) 
- `@exodus/tx-signer` (`features/tx-signer/src/module/transaction-signer.ts`) — delegates transaction signing to seed-based or hardware signers, again just signing opaque `unsignedTx` data passed in by the caller. [2](#0-1) 
- The Solana provider's `signIn` and `connected-origins` feature manage dApp connection/trust state keyed by `origin`, with `isTrusted`/`isAutoApprove` checks scoped per origin string. [3](#0-2) 

None of these implement a "credit"/bid-matching struct with an `orderId` that gets checked against marketplace-specific state — that logic, if it existed, would live in a dApp's own smart contract, entirely outside this SDK's trust boundary. The wallet's job here is only to produce a signature over data it's asked to sign; it has no visibility into, or responsibility for, whether a downstream marketplace contract properly binds that signature to a specific order/marketplace. There's also no "maker/taker credit reuse across marketplaces" concept anywhere in the signing, RPC, or connected-origins code I found.
