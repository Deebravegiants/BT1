## Custody Invariant Reduction

The Sherlock bug boils down to one invariant: **a shares-to-value accounting system must never treat an existing non-zero pooled balance as "fresh" just because the current share count is zero** — otherwise whoever buys in next inherits value they never contributed (or accrued value that should have gone to the correct owner is stranded/misdirected).

## Candidate Paths Considered

1. `dispatchable_fungible_asset`/`fungible_asset` freeze & dispatch hooks — reviewed but standard `TransferRef`/`DispatchFunctionStore` gating did not reveal an unprivileged authority break.
2. `stake::distribute_rewards` (zero `stake_amount` guard) — this correctly no-ops and mints nothing, so no value is lost or misdirected; not a custody break.
3. **`aptos_std::pool_u64_unbound` + `aptos_framework::delegation_pool`** — the delegation pool's active-stake accounting uses this shares module, and its "empty pool" fallback interacts with `synchronize_delegation_pool`'s update ordering. This is the strongest candidate.

## Strongest Candidate

### Title
Zero-share `active_shares` pool lets the next buy-in claim previously accrued/stranded active stake in `delegation_pool.move` - (File: aptos-move/framework/aptos-framework/sources/delegation_pool.move)

### Summary
`delegation_pool::synchronize_delegation_pool` first overwrites the internal `active_shares` pool's tracked coin total to match the real stake-pool balance, and only afterward buys shares for the operator's commission out of that already-updated total. `pool_u64_unbound::amount_to_shares_with_total_coins`, used by `active_shares`, treats any pool whose `total_shares == 0` as an empty pool and mints new shares in direct 1:1 proportion to the incoming deposit, completely ignoring any existing (non-zero) `total_coins` already recorded in the pool. If the active-shares pool's `total_shares` reaches zero while its `total_coins` is non-zero (e.g., after all active shareholders — delegators and any prior operator commission shares — have exited, but the underlying `stake::StakePool.active` still holds value that gets folded in by `update_total_coins`), the very next buyer of active shares receives shares entitling them to 100% of the pool, including the pre-existing balance that isn't theirs.

### Finding Description
`synchronize_delegation_pool` (delegation_pool.move) performs, in order:
1. `pool.active_shares.update_total_coins(active - commission_active)` — sets the pool's `total_coins` directly to the delta-corrected on-chain active stake, independent of `total_shares`. [1](#0-0) 
2. `buy_in_active_shares(pool, beneficiary_for_operator(...), commission_active)` — mints the operator's commission shares using the state set in step 1. [2](#0-1) 

`update_total_coins` unconditionally overwrites `total_coins` with no relation to `total_shares`: [3](#0-2) 

The pool module used by `delegation_pool` is `pool_u64_unbound` (aliased `pool_u64`): [4](#0-3) 

Its share-minting math explicitly special-cases `total_shares == 0` (or `total_coins == 0`) as an "empty pool," minting shares 1:1 for the *new* deposit alone, discarding any information about a pre-existing `total_coins` balance: [5](#0-4) 

So: if at the moment `buy_in_active_shares` runs, `active_shares.total_shares == 0` but `active_shares.total_coins > 0` (set moments earlier in step 1, or left over from a prior epoch where all delegators + operator commission shares were fully redeemed while stray active balance remained), the buyer (operator, via commission, or the next delegator calling `add_stake`) is minted shares computed only from their own contribution, yet after `buy_in`'s `self.total_coins += coins_amount`, they become the pool's sole shareholder holding claim to the *entire* `total_coins`, i.e., their contribution *plus* the stranded balance that belonged to prior stakeholders/rewards. This is the same bug class as the report: a "no deposits / zero-supply" edge case causes accounted value to be silently mis-custodied — except here it isn't merely stuck, it is captured by an unrelated new party, corrupting the shares↔stake mapping (a custody accounting corruption moving value to the wrong holder).

### Impact Explanation
If reachable, an operator or a delegator who is first to re-enter an active-shares pool that has hit `total_shares == 0` with residual `total_coins` would receive shares redeemable for real APT stake they never contributed — value diverted from whichever delegators/operator should have owned it. This is a supply/custody accounting corruption directly tied to real staked APT held by the delegation pool's resource-account-controlled `StakePool`, satisfying the custody-grade bar (movement of value to the wrong holder).

### Likelihood Explanation
Medium-low confidence/likelihood. I was able to confirm structurally that (a) `update_total_coins` is unconditionally applied before shares are re-bought, and (b) `pool_u64_unbound`'s empty-pool branch discards residual `total_coins` when `total_shares == 0`. What I could **not** fully verify from static reading alone — and would require live Move unit testing/tracing to confirm — is whether the codebase's other invariants (e.g., always maintaining at least the operator's or `NULL_SHAREHOLDER`'s minimal share presence, or `redeem_active_shares`/`buy_in_active_shares` being invoked together atomically each sync in a way that never leaves `total_shares == 0` with `total_coins > 0` even transiently) prevent this state from ever being observable by an external buy-in call. The module's own documentation asserts the invariant "the pending withdrawal exists at an OLC iff delegator owns some shares," which suggests the maintainers are aware of edge cases here, but I did not find an explicit guard preventing the specific ordering issue in `synchronize_delegation_pool` described above.

### Recommendation
In `synchronize_delegation_pool`, avoid calling `update_total_coins` on a shares pool whose `total_shares == 0` without also atomically minting/preserving proportional shares for the correct owner (or route any coins added to a zero-share pool to a safe/burn/treasury destination, mirroring the `NULL_SHAREHOLDER` pattern already used elsewhere in the file for `add_stake` fees). Alternatively, patch `pool_u64_unbound::amount_to_shares_with_total_coins` so that when `total_shares == 0` but `total_coins > 0`, the deposit's proportional new shares also account for absorbing the stranded balance correctly (e.g., mint the new shareholder shares matching only their own contribution's fraction of the resulting total, not shares that also claim the untouched legacy balance).

### Proof of Concept
Conceptual trace (would need to be validated with an actual Move unit test against `delegation_pool.move` + `pool_u64_unbound.move`):
1. Delegation pool `P` has an `active_shares` pool with `total_shares = 100`, `total_coins = 100` held entirely by delegator `D` (operator commission = 0%, no operator shares yet).
2. `D` fully unlocks/withdraws all active stake: `redeem_shares` reduces `active_shares` to `total_shares = 0`, `total_coins = 0` — consistent so far.
3. Before the next sync, the underlying `stake::StakePool.active` accrues rewards from stake that is *not* delegator-owned in the accounting sense (e.g., leftover `pending_active`/fee-buffer amounts merged via `stake::update_stake_pool`), so real on-chain `active` balance becomes `> 0` while `active_shares.total_shares == 0`.
4. Next `synchronize_delegation_pool` call: `calculate_stake_pool_drift` computes `commission_active` from the delta; `update_total_coins(active - commission_active)` sets `active_shares.total_coins` to a non-zero value while `total_shares` is still `0`.
5. `buy_in_active_shares(pool, operator, commission_active)` invokes `amount_to_shares_with_total_coins`, which — because `total_shares == 0` — mints `new_shares = commission_active * scaling_factor` and ignores the already-set `total_coins`. After `buy_in`, operator ends up sole shareholder with `total_shares = new_shares`, `total_coins = active` (full amount) — able to redeem the entire `active` stake, not just their commission.

Because I lack the ability to execute Move tests in this environment, step 3's exact real-world trigger (a concrete transaction sequence producing `active_shares.total_shares == 0` with non-zero pending stake before `synchronize_delegation_pool` runs) is asserted from code reading rather than empirically confirmed — this should be validated with a Devin session capable of running the Move test suite against `delegation_pool.move` before treating this as fully confirmed.

    public fun amount_to_shares_with_total_coins(self: &Pool, coins_amount: u64, total_coins: u64): u128 {
        // No shares yet so amount is worth the same number of shares.
        if (self.total_coins == 0 || self.total_shares == 0) {
            // Multiply by scaling factor to minimize rounding errors during internal calculations for buy ins/redeems.
            // This can overflow but scaling factor is expected to be chosen carefully so this would not overflow.
            (coins_amount as u128) * (self.scaling_factor as u128)
        } else {
            // Shares price = total_coins / total existing shares.
            // New number of shares = new_amount / shares_price = new_amount * existing_shares / total_amount.
            // We rearrange the calc and do multiplication first to avoid rounding errors.
            self.multiply_then_divide(coins_amount as u128, self.total_shares, total_coins as u128)
        }
    }
