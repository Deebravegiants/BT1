### Title
Webhook shop-domain header not covered by HMAC allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but the tenant identity (`shop`) used downstream by the app is read from the `x-shopify-shop-domain` header, which is never part of the signed content. Anyone who can obtain one valid `(body, hmac)` pair — e.g., a legitimate webhook delivered to their own installed shop — can replay that exact body and HMAC to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header, and the app will process the payload as belonging to a different tenant.

### Finding Description
`HmacValidator.validate` verifies `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` [1](#0-0) . For webhooks, `to_signable_string` returns only `@raw_body` [2](#0-1) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read from separate, unsigned HTTP headers [3](#0-2) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., that the body's HMAC is valid for *some* payload signed with the app secret) before dispatching to the topic handler with `request.shop` taken straight from the unauthenticated header [4](#0-3) . The `shop` value flows directly into `WebhookMetadata.shop`, which is the field host applications use to route webhook data to the correct tenant/store record [5](#0-4) .

The broken identity binding is: `hmac-authenticated-content (raw body)` ≠ `shop identity acted upon (x-shopify-shop-domain header)`. Since the HMAC never covers the shop header, its value is not authenticated at all — only the body's origin (someone possessing the shared secret, i.e., Shopify) is verified, not which shop it was generated for.

### Impact Explanation
This is a cross-tenant identity binding break in the sense required by the rules: a field acted on (`shop`, used to key merchant data) is not covered by the HMAC. An attacker who legitimately receives real webhooks for their own installed store (any merchant is an "unprivileged internet user" from the app's perspective, since HTTP webhook endpoints are public URLs, not protected by any further authentication) can capture one valid `(raw_body, x-shopify-hmac-sha256)` pair and replay it to the app's own public webhook endpoint with the `x-shopify-shop-domain` header rewritten to an arbitrary victim shop domain. Because the signature check only depends on the body and the shared secret — both unchanged in the replay — validation succeeds, and the handler processes the attacker's own data as if it originated from the victim shop. Depending on how the host application implements `WebhookHandler#handle` (per the documented contract, trusting `WebhookMetadata.shop` as the authenticated tenant), this can lead to cross-tenant data corruption or injection of attacker-controlled data into another merchant's records.

### Likelihood Explanation
Exploitation requires no privileged credentials: any user who can install the app on their own store (or otherwise obtain one valid signed webhook body/HMAC pair) and can send arbitrary POST requests to the app's public webhook receiver endpoint can perform this attack. The gem provides no cross-check that the header-derived `shop` matches anything covered by the signature, so the vulnerability is directly reachable through the library's own documented `Registry.process` API.

### Recommendation
Include the `shop-domain` (and `topic`, `webhook_id`) header values in the signable content used for HMAC verification, or otherwise cryptographically bind the shop identity to the signed payload before trusting `request.shop` for tenant routing. At minimum, document that `WebhookMetadata.shop` is unauthenticated and must not be used as a sole tenant-routing key without additional verification.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and legitimately receives a real webhook, capturing the raw body `B` and its valid header `x-shopify-hmac-sha256: H` (where `H = HMAC(secret, B)`).
2. Attacker sends a POST directly to the app's public webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), `x-shopify-topic` unchanged, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and compares it to `H` — this passes because `to_signable_string` only returns `B` [2](#0-1) .
4. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's parsed body>, ...)` [6](#0-5) , causing the host application to process attacker-controlled data under the victim's tenant identity.
