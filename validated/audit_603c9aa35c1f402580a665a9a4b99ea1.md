## Title
Webhook `shop` identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authenticated once the HMAC check passes, but the HMAC signature computed by `HmacValidator` only covers the raw request body — not the `shop-domain` header that the rest of the pipeline (and the gem's own documentation) treats as the authenticated tenant identifier. This breaks the identity binding `shop authenticated by HMAC == shop delivered to the handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes/compares the signature exclusively over `verifiable_query.to_signable_string`: [2](#0-1) 

`Registry.process` uses this HMAC check as its sole authenticity gate, then immediately forwards `request.shop` — read straight from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header — into `WebhookMetadata` given to the app's handler: [3](#0-2) [4](#0-3) 

Because the HMAC secret (`api_secret_key`) is a single per-app secret shared across all shops (not shop-specific), the valid HMAC digest for a given raw body is identical no matter which shop the body was originally delivered for. An attacker who legitimately receives one authentic webhook delivery (e.g., by installing the app on a store they control, or intercepting a webhook payload/HMAC pair some other way) can replay that exact `raw_body` + HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `HmacValidator.validate` will still return `true`, because it never inspects the shop header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the (attacker-chosen) victim shop.

The gem's own documentation confirms the intended (but unmet) guarantee — that `process` "will verify the request did indeed come from Shopify" — and that `data.shop` is meant to be trusted as "The shop domain of the webhook", explicitly shown being used to scope downstream work (`perform_later(shop_domain: data.shop, ...)`): [5](#0-4) 

This is the "field acted on but not covered by the HMAC" pattern: `shop` is acted on (dispatched to per-tenant handler logic) but not part of the signed bytes.

### Impact Explanation
Any consuming application that follows the documented pattern of using `data.shop` to select which tenant's records/session/job queue to act on (exactly as shown in the gem's own docs) is exposed to cross-tenant data injection: an attacker can cause webhook-triggered processing to run against a victim shop's identity using data the attacker fully controls (their own store's webhook body), since the body/shop pairing is never cryptographically bound. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only an unprivileged actor who can obtain one authentic `(raw_body, hmac)` pair for any shop (trivially achievable by installing the app on their own free/dev store and capturing an outgoing webhook), plus the ability to POST to the app's public webhook callback endpoint. No access token, `client_secret`, or privileged credentials are required — only knowledge that this gem computes the signature over the body alone.

### Recommendation
Bind the shop identity into the authenticated material used by `Registry.process`/`HmacValidator`, e.g. by requiring the caller to supply the expected shop (from the session store keyed by webhook subscription/registration) and comparing it against `request.shop`, or by verifying webhook authenticity together with a lookup that ties the delivered `webhook_id`/shop pair back to Shopify's registration records rather than trusting the unsigned header at face value.

### Proof of Concept
1. Install the app (or otherwise obtain webhook delivery) on attacker-owned shop `attacker.myshopify.com`; capture a legitimate webhook POST, including its raw body and the `x-shopify-hmac-sha256` value Shopify computed with the app's shared `api_secret_key`.
2. Replay the identical raw body and HMAC header to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) validates successfully because it only re-hashes the raw body.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the app handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: attacker_controlled_body, ...)`, causing the host application to process attacker-controlled data under the victim shop's identity.
