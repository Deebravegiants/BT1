### Title
Shared `CallDispatcher` balance-based crediting misattributes donated/leftover token balance into an unrelated order's escrow - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder`'s predispatch path credits an order's escrowed input amount from the **absolute** token balance of the shared `CallDispatcher` contract rather than a delta strictly attributable to that order's own funds, exactly the balance-based misclassification root cause behind the DTXT exploit (a transfer classified by comparing raw balances rather than tracking what was actually contributed by the current operation).

### Finding Description
`_params.dispatcher` is a single `CallDispatcher` instance shared by every order and by both the predispatch and output-execution paths of `IntentGatewayV2`/`IntentsBase` [1](#0-0) . It has no access control and an unconditional `receive()` [2](#0-1) , so anyone can send ETH or `IERC20.transfer` arbitrary tokens to it at any time, and it can also retain unswept token dust: `_execute` only sweeps tokens present in `order.output.assets` (`outputsLen`), so a token left on the dispatcher by a call that is not part of that list is never collected [3](#0-2) .

In `placeOrder`'s predispatch branch, the gateway determines how much of an input token it "received" by reading the dispatcher's **current total balance**, not the amount specifically produced by this order's own predispatch call: [4](#0-3) 

That whole balance is swept into the gateway, and the delta at the gateway is treated as `received` and directly written into `order.inputs[i].amount` whenever it is less than or equal to the requested amount: [5](#0-4) 

Because `balance` is read as `IERC20(token).balanceOf(dispatcher)` (an absolute snapshot) rather than a value scoped to what this order's own predispatch transfer produced, any pre-existing balance sitting on the shared dispatcher — from a direct external donation, or from residual dust left by a prior, unrelated order's output-call execution that wasn't included in that order's `outputsLen` sweep — gets folded into the current order's `received` figure. If the order placer's actual predispatch call underdelivers (e.g., a fee-on-transfer token, a lossy swap, or an order placer who deliberately shortchanges their own predispatch output), that shortfall can be silently topped up by unrelated funds already sitting on the dispatcher, up to `order.inputs[i].amount`. The gateway then escrows `order.inputs[i].amount` under `_orders[commitment][token]` even though the order placer did not actually contribute that full value — the difference is effectively protocol dust or a third party's funds being misattributed into this order's private escrow, later withdrawable by the order's solver or (on cancellation) the order placer.

This is the same class of bug as DTXT: an accounting decision (how much of a transfer belongs to the current operation) is made by comparing raw balances of a shared contract instead of tracking a delta scoped to the specific transfer that was authorized for this operation, allowing outside balance perturbations to be misclassified as this operation's own funds.

### Impact Explanation
A successful exploitation lets an order placer under-fund their own escrowed input (partially or, if enough dust/donation exists, fully) while still having the gateway record and later release the full nominal `order.inputs[i].amount` to a solver or back to themselves on cancellation. This is a theft-of-funds vector against the protocol/dust pool and, transitively, against solvers who fill against an under-collateralized escrow, since `_withdraw` will pay out from `_orders[commitment][token]` without re-validating that the tokens genuinely originated from this order's own deposit [6](#0-5) .

### Likelihood Explanation
Requires (a) the predispatch route to be used (order carries `predispatch.call` and `predispatch.assets`), and (b) the shared `CallDispatcher` to hold token balance not owned by the current order at the moment of the sweep — achievable directly via a plain `IERC20.transfer` to the dispatcher's public address (no access control), or opportunistically via dust left behind by a prior order whose output call touched a token outside its declared `outputsLen`. Both preconditions are attacker-controllable from a single, unprivileged transaction sequence, making this a realistically reachable path rather than a purely theoretical one; however, exact monetary impact per attack depends on how much unattributed balance can be parked on the dispatcher at exploitation time.

### Recommendation
Track the amount contributed by the current order's own predispatch transfer/call explicitly (e.g., snapshot the dispatcher's balance immediately before the predispatch assets are transferred in, not only immediately before the sweep-out), and cap `received` to the delta produced specifically by this order's own predispatch flow rather than the dispatcher's total balance. Any balance on the dispatcher not attributable to the current order's inbound transfer should be excluded from escrow crediting and swept only as protocol dust, never folded into a specific order's `_orders[commitment][token]`.

### Proof of Concept
1. Attacker sends `X` units of `TOKEN` directly to the `CallDispatcher` address via a plain `IERC20.transfer` (no permission required, since `CallDispatcher` imposes no access control on inbound transfers).
2. A user (potentially the attacker themselves, or an accomplice) places an order via `placeOrder` with `predispatch.assets` containing `TOKEN` and a `predispatch.call` that intentionally causes the dispatcher to only actually retain less than `order.inputs[i].amount` of `TOKEN` from the legitimately-supplied funds (e.g., using a lossy or fee-charging predispatch step, or simply supplying less than the declared `order.inputs[i].amount`).
3. At the sweep step, `balance = IERC20(token).balanceOf(dispatcher)` reads the dispatcher's balance including the attacker's earlier donation `X`, and the full amount is swept to the gateway and credited as `order.inputs[i].amount = received` (up to the requested amount) [5](#0-4) .
4. `_orders[commitment][token]` now reflects an escrow value inflated by the donated `X`, which a solver can later claim via `fillOrder`/`_withdraw`, or the order placer can reclaim via cancellation — funds that were never actually contributed by the order placer for this specific order.

Note: I was not able to fully verify a live, end-to-end numeric PoC (e.g., an exact fee-on-transfer token scenario combined with a concrete pre-existing dispatcher balance) within the available exploration; the mechanism is demonstrated purely through the cited code paths in `IntentGatewayV2.sol` and `CallDispatcher.sol`.

contract CallDispatcher is ICallDispatcher {
    /**
     * @dev error thrown when the target is not a contract.
     */
    error NotContract(address target);

    /**
     * @dev error thrown when a call fails.
     */
    error CallFailed(address target, bytes result);

    /**
     * @dev Receive function to accept ETH transfers
     */
    receive() external payable {}

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
}

        Call[] memory sweepCalls = new Call[](outputsLen);
