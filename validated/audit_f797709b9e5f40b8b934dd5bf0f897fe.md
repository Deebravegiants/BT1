### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` fields are dispatched to handlers without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers and passed to the registered handler as if they were verified. This breaks the identity binding `shop_verified_by_hmac == shop_used_for_dispatch`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are pulled directly from HTTP headers with no cross-check against the signed body: [2](#0-1) 

`Registry.process` validates only this body-only HMAC via `Utils::HmacValidator.validate(request)` and then immediately forwards the header-derived, unauthenticated `shop`/`topic`/`webhook_id`/`api_version` values to the app's handler as `WebhookMetadata`: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `to_signable_string`, i.e., the raw body, using the app's `api_secret_key` — a secret shared across *every* shop that has installed the app, not scoped to a single tenant: [4](#0-3) 

The library's own documentation reinforces the false assumption that `process` fully authenticates the request ("This will verify the request did indeed come from Shopify") and shows the example handler trusting `data.shop` directly as the tenant identifier (`shop_domain: data.shop`) — this is exactly the value that isn't bound by the signature. The equality that should hold — `shop header value == shop covered by HMAC` — does not hold: only bytes of the body are verified, not the header claiming which shop the body belongs to.

### Impact Explanation
Because the HMAC secret (`api_secret_key`/`old_api_secret_key`) is the same for all shops that installed a given app, any tenant that legitimately receives a real Shopify webhook (a valid `raw_body` + `hmac` pair for their own shop) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` (or `x-shopify-shop-domain`), `shopify-topic`, and `shopify-webhook-id` headers to impersonate a different shop. `Registry.process` will accept it (HMAC over body still matches) and hand the handler data claiming to originate from an arbitrary victim shop. If the host application trusts `data.shop` to select the tenant record to update (as the documented example does), this results in cross-tenant data injection/corruption without ever needing the victim's access token or credentials — Critical impact per the given classification (cross-tenant access).

### Likelihood Explanation
Any developer or malicious merchant who has installed the target app on their own store can trivially capture a genuine signed webhook (body + `hmac-sha256`) sent to them and replay it with modified headers, since none of `shop`, `topic`, `webhook_id`, or `api_version` participate in the signature. No secrets, tokens, or privileged access are required beyond having installed the app as a normal (even free) merchant — a low bar, making this readily exploitable.

### Recommendation
Include the `shop`, `topic`, `webhook_id`, and `api_version` header values in the signable payload used for HMAC verification (or otherwise cryptographically bind them to the request), and/or require host applications to cross-check `data.shop` against a shop that is actually known/installed (e.g., has a stored session) before trusting it. At minimum, update `Request#to_signable_string` so it authenticates all fields the library exposes to handlers, and correct the documentation's claim that `process` "verif[ies] the request did indeed come from Shopify" for those header-derived fields.

### Proof of Concept
1. Attacker installs the target app on their own store, `attacker.myshopify.com`, and legitimately receives a real webhook from Shopify:
   - Headers: `shopify-topic: orders/create`, `shopify-hmac-sha256: <valid-hmac-of-body>`, `shopify-shop-domain: attacker.myshopify.com`, `shopify-webhook-id: <id-A>`
   - Body: `{"id": 1, "note": "hello"}`
2. Attacker replays the identical `raw_body` and `shopify-hmac-sha256` value to the app's webhook endpoint, but changes:
   - `shopify-shop-domain: victim.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `OpenSSL.secure_compare(computed_signature, received_signature)` over the raw body (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: {...}, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though Shopify never sent this data for `victim.myshopify.com`.
