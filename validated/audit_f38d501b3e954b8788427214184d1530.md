### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop-domain` header to identify which tenant the webhook belongs to. Because the `shop` identity used downstream is never bound to the HMAC that authenticated the request, an attacker who legitimately receives one signed webhook (e.g., for their own shop) can replay the same body/HMAC pair to the app's shared webhook endpoint while substituting a different shop's domain in the header, causing the host application to process/attribute the payload to a victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines the signable content as only the raw body: [1](#0-0) 

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [2](#0-1) 

The `shop` accessor simply reads the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is never included in `to_signable_string`: [3](#0-2) 

`Utils::HmacValidator.validate` only recomputes and compares the HMAC over `to_signable_string` (i.e., the body) using the app's shared `Context.api_secret_key`: [4](#0-3) 

`Registry.process` gates entirely on this body-only HMAC check, then immediately trusts `request.shop` (the unauthenticated header) as the tenant identity handed to the app's handler: [5](#0-4) 

The identity binding that should hold is:
`shop authenticated by HMAC == shop delivered to the handler`

In this implementation, the left side is actually never computed — the HMAC only proves "some request body was signed with the app's client secret at some point," not "this body belongs to this shop." Since the app's `client_secret` (used to compute/verify the HMAC) is shared across every shop that has installed the app, any installed merchant can obtain a validly signed `(body, hmac)` pair for their own store's webhooks, then re-POST that exact body/HMAC to the same public webhook endpoint with the `shop-domain` header rewritten to a different, victim shop. `HmacValidator.validate` still returns `true` (the body/HMAC pair is genuinely valid), and `Registry.process` forwards `WebhookMetadata.new(..., shop: request.shop, ...)` — now carrying the attacker-chosen shop — to the host application's handler.

### Impact Explanation
This breaks the tenant boundary the HMAC check is meant to enforce: the gem asserts to the consuming application that a webhook body has been verified as authentic for the `shop` field it hands over, when in fact `shop` was never authenticated at all. A multi-tenant app whose webhook handler uses `WebhookMetadata#shop` to look up/act on a shop's data (a common, encouraged pattern per this gem's own `docs/usage/webhooks.md`) can be made to process attacker-supplied (but validly-signed-for-a-different-shop) webhook data under a victim shop's identity — i.e., cross-tenant data injection/spoofing.

### Likelihood Explanation
Requires only that the attacker be an ordinary installed merchant of the target app (no `api_secret_key`, no access token, no privileged account, no TLS interception) — they merely capture one webhook legitimately delivered to their own store and replay it to the app's public webhook endpoint with a modified `shop-domain` header. This satisfies the "unprivileged internet user" threat model and does not depend on the host ignoring documented behavior — the gem's `process` method itself performs no binding between the verified signature and the shop field it exposes.

### Recommendation
Bind the shop identity to the authenticated content: include the `shop-domain` (and ideally `topic`/`webhook-id`) in the HMAC-signable string, or otherwise cryptographically bind the shop to the verified payload before trusting `request.shop` in `Registry.process`. At minimum, document that `WebhookMetadata#shop` is unauthenticated header data and must be independently corroborated (e.g., against a known/installed shop record) before being used for tenant-scoped data access.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook delivery: body `B`, header `x-shopify-hmac-sha256: H` (valid for the app's shared `client_secret`), `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker sends a raw HTTP POST directly to the app's public webhook endpoint with body `B`, `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= B`) — validation succeeds because the header is never part of the signed content: [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: JSON.parse(B), ...)`, causing the host app to process attacker-controlled data under the victim shop's identity.
