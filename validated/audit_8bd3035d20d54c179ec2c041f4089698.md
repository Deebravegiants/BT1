### Title
Webhook `shop` identity is taken from an unauthenticated header not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (`File: lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#shop` returns the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header value, but the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` validates only covers the raw request body. Because the app's `client_secret` (the key used to compute the HMAC) is shared across every shop that has installed the app, any merchant who has installed the app on their own store can capture a legitimate `raw_body`+`hmac` pair delivered to their shop and replay it with a forged `shop-domain` header pointing at a different (victim) shop. The HMAC check still passes, and the forged `shop` value is handed unauthenticated to the app's webhook handler.

### Finding Description
The identity binding that should hold is:
`shop_value_verified_by_hmac == shop_value_delivered_to_handler`

In this gem that equality does not hold:

- `Request#shop` is parsed straight from a header, independent of the signed payload: [1](#0-0) 

- `Request#to_signable_string`, the material actually fed into HMAC verification, is only the raw body — it never includes the shop-domain header: [2](#0-1) 

- `HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the supplied `hmac`, using only the (single, per-app) `Context.api_secret_key`/`old_api_secret_key` — there is no shop-specific secret or shop-bound claim: [3](#0-2) 

- `Registry.process` trusts `request.shop` once the (shop-independent) HMAC check passes, and forwards it straight to the app-supplied handler as authoritative tenant identity: [4](#0-3) 

- The documented handler contract explicitly tells integrators to trust `data.shop` as "The shop domain of the webhook" and to key persisted work off it (e.g. `shop_domain: data.shop`): [5](#0-4) 

Because the secret is shared across all shops for a given app (it is the app's `client_secret`, not a per-shop secret), an attacker who is a merchant with the app installed on their own store can:
1. Trigger any webhook event on their own store to receive a genuine `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's secret.
2. Resend that exact body and hmac to the app's webhook endpoint, but replace the `x-shopify-shop-domain` header with a victim shop's domain.
3. `HmacValidator.validate` passes (it never looked at the shop header), and `Registry.process` calls the handler with `shop: <victim-shop>`, `body: <attacker-controlled-but-genuinely-signed-JSON>`.

This breaks the intended equality between "the entity whose secret produced this signature" and "the entity the host app will act on behalf of," which is the same class of defect as the audited Solidity bug (an amount used by the contract that isn't actually bound by the value it was derived from) — here, a tenant identifier used by the app that isn't actually bound by the cryptographic check that gates the request.

### Impact Explanation
This is a cross-tenant confusion vector: an unprivileged merchant of a multi-tenant app can cause the host application (which follows this gem's documented API exactly as shown in `docs/usage/webhooks.md`) to process/store webhook data under a different shop's identity, since the HMAC never certifies which shop the payload belongs to. Depending on how the host app uses `data.shop` (e.g., to select which merchant's DB row/tokens to update), this can lead to data being attributed to, or overwriting state for, a shop the attacker does not control — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is high for any app built per this gem's documented pattern: no privileged credentials, TLS interception, or leaked secrets are required — only that the attacker is a legitimate installer of the app (a normal, unprivileged tenant), and that they can capture one genuine webhook delivery to their own shop and replay it with a different header value to the app's public webhook endpoint.

### Recommendation
Bind the shop identity into the verified material instead of trusting an unauthenticated header:
- Include the shop domain (and ideally webhook id / topic) inside the HMAC-signable string, or
- Cross-check `request.shop` against the shop associated with the webhook subscription/session that the app expects for that endpoint before invoking the handler, and reject mismatches in `Registry.process`.

### Proof of Concept
1. App A is installed on `attacker-shop.myshopify.com` and on victim `victim-shop.myshopify.com`, both webhooks routed to the same app endpoint using the app's single `client_secret`.
2. Attacker triggers an `orders/create` webhook on their own shop, capturing `raw_body` and the genuine `x-shopify-hmac-sha256` value Shopify sent.
3. Attacker POSTs to the app's webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (lib/shopify_api/utils/hmac_validator.rb:12-31) recomputes HMAC over `raw_body` only and it matches — verification succeeds.
5. `Registry.process` (lib/shopify_api/webhooks/registry.rb:188-200) invokes the handler with `shop: "victim-shop.myshopify.com"` and the attacker's order body, and the host app (following the documented pattern in docs/usage/webhooks.md:19-29) stores/acts on this data as if it legitimately belonged to `victim-shop.myshopify.com`.

```ruby
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
```

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```
