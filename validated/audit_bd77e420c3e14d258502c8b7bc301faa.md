## Title
Webhook `shop` domain is not bound by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, then hands the handler a `shop` value taken from an HTTP header that is **not** part of the signed material. Any party who can obtain one validly-signed webhook body (e.g. by installing the app on their own shop and triggering a real webhook) can replay that exact body with an arbitrary `X-Shopify-Shop-Domain` header, and the gem will report the webhook as coming from whatever shop the attacker names, having passed HMAC validation.

### Finding Description
The `Request` class computes the signable string as the raw body only, and exposes `shop` from a header that is excluded from that signable string: [1](#0-0) [2](#0-1) 

`HmacValidator.validate` verifies only `verifiable_query.to_signable_string` against the HMAC: [3](#0-2) 

`Registry.process` validates the HMAC and then constructs the `WebhookMetadata` handed to the app's handler directly from `request.shop`, `request.topic`, etc. — none of which (other than the body) are covered by the signature: [4](#0-3) 

The identity-binding equality that should hold is:
`shop_bound_by_hmac == shop_delivered_to_handler`

but the actual state is:
`shop_bound_by_hmac (undefined, not in to_signable_string) != shop_delivered_to_handler (request.shop, from unauthenticated header)`

Because the HMAC is computed with the app's shared `client_secret` and is identical for every shop that installs the app, any shop that legitimately receives one signed webhook (trivial to obtain by installing the app on a test/free shop and generating any event) possesses a `(body, hmac)` pair that will pass validation regardless of which `shop-domain` header accompanies it. Replaying that exact body/HMAC pair to the app's public webhook endpoint with a different `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header value causes `Utils::HmacValidator.validate` to succeed and `Registry.process` to invoke the app's handler with the attacker-chosen `shop`.

### Impact Explanation
This breaks the tenant boundary the webhook metadata is supposed to guarantee: the gem's contract is that a validated webhook's `shop` identifies the tenant that generated it. An attacker who is merely an unprivileged shop owner (no access token, no `api_secret_key`, no privileged account) can make the app believe a webhook event/payload originated from a different, victim shop. Depending on how the host app keys its own state/session lookups off `WebhookMetadata#shop` (a documented, intended usage pattern of this gem's API — see `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))`), this can lead to cross-tenant data confusion/access — for example a forged `shop/redact` or `customers/data_request` compliance webhook, or a forged domain/app-subscription event, being processed as if issued by another merchant's shop.

### Likelihood Explanation
Likelihood is high for any app that exposes a webhook endpoint reachable over the internet (the standard deployment) and relies on this gem's `Registry.process`/`Request#shop` to identify the tenant, since:
- No secret, token, or privileged access is required — only the ability to install the app on any shop (even a free trial/dev store) to obtain one valid `(body, hmac)` pair.
- The forged request is a normal unauthenticated HTTP POST to the app's public webhook URL with a modified header.

### Recommendation
Include the shop domain (and other identity-relevant fields such as topic/api-version) in the HMAC-verifiable material, or otherwise cryptographically bind the `shop-domain` header to the signed payload before trusting it in `WebhookMetadata`. At minimum, document/enforce that host apps must independently verify `request.shop` corresponds to a shop with an active, known installation/session before acting on webhook data, since the header itself carries no integrity guarantee from this gem.

### Proof of Concept
1. Install the app on shop `attacker.myshopify.com` and trigger any webhook subscription (e.g. `orders/create`) so Shopify delivers a real POST with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Capture `B` and `H` (attacker fully controls their own shop's traffic/logs).
3. Send a new HTTP POST to the app's webhook endpoint with the identical body `B`, identical `X-Shopify-Hmac-Sha256: H`, but with `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and `X-Shopify-Topic` unchanged.
4. `ShopifyAPI::Utils::HmacValidator.validate` computes the signature over `@raw_body` only (`to_signable_string` at `lib/shopify_api/webhooks/request.rb:36-38`) — it matches `H`, so `process` (`lib/shopify_api/webhooks/registry.rb:190`) does not raise `InvalidWebhookError`.
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), i.e., attacker-controlled body processed under the victim's shop identity.
