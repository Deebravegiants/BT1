### Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted from unauthenticated headers while the HMAC signature only covers the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then hands the handler a `shop`, `topic`, and `webhook_id` that are read directly from HTTP headers which are never included in that HMAC computation. This breaks the intended binding: `HMAC-verified(body) == HMAC-verified(shop/topic/webhook_id)`, when in fact only the body is authenticated.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from attacker-visible HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., the raw body): [3](#0-2) 

`Registry.process` treats a passing HMAC check as full authentication of the request, then forwards the unauthenticated `shop`/`topic`/`webhook_id` header values straight to the host application's handler: [4](#0-3) 

The binding this breaks, stated as an equality that should hold but doesn't:
`HMAC-authenticated(shop, topic, webhook_id, body) == HMAC-authenticated(body only)`

Since `shop`/`topic`/`webhook_id` are not part of the signed material, any party who can obtain one genuinely-signed webhook body (e.g., by installing the app on their own store and receiving a real webhook for a topic with a body that carries no shop-specific data, such as `app/uninstalled` or other minimal-payload topics) can replay that exact `raw_body` + `x-shopify-hmac-sha256` pair to the same endpoint while substituting arbitrary values for `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id`. `HmacValidator.validate` will still succeed because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event came from a different shop and/or topic than the one that actually produced it.

### Impact Explanation
This is a cross-tenant identity-binding bypass: the app's webhook handler acts on a `shop` value that was never verified as belonging to the request that produced the signed body. Any application built on this gem that keys per-tenant side effects off `WebhookMetadata#shop` (e.g., updating shop-specific state, triggering shop-scoped billing/plan changes, or logging events attributed to a shop) can be made to attribute an attacker-controlled body to an arbitrary victim shop domain, and/or have the body dispatched to a handler registered for a different topic than the one Shopify actually signed it for. This matches the "cross-tenant access" class of impact, since tenant attribution is entirely attacker-controlled despite HMAC verification appearing to pass.

### Likelihood Explanation
Exploitation requires only an internet-reachable webhook endpoint and the ability to obtain at least one legitimately HMAC-signed webhook body — trivially achievable by any developer/attacker who installs the target app on their own (attacker-controlled) Shopify development store and receives one real webhook delivery. No access token, `api_secret_key`, or privileged credentials are needed; the attack is purely a header-substitution replay against the app's public webhook route.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the material that is HMAC-verified (or otherwise cryptographically bind them to the body), rather than trusting them as separate unauthenticated header values in `ShopifyAPI::Webhooks::Request`. At minimum, `Registry.process` should not pass header-derived `shop`/`topic` values to handlers as "verified" once only the body has been authenticated; documentation and API should make clear these fields are unauthenticated unless the host app performs its own additional shop/topic validation against known-registered values.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and triggers a webhook topic with a minimal, shop-agnostic body (e.g. `{}`), capturing the raw body and the resulting `x-shopify-hmac-sha256` header that Shopify sent.
2. Attacker POSTs to the app's public webhook endpoint using the exact same `raw_body` and `x-shopify-hmac-sha256`, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: <topic the app's handler treats specially>`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body against the HMAC — this passes because the body and signature are the ones genuinely issued by Shopify.
4. The handler is invoked with `WebhookMetadata.new(topic: "<attacker-chosen topic>", shop: "victim-shop.myshopify.com", body: {}, ...)`, causing the host application to process an event as if it were a verified webhook from `victim-shop.myshopify.com`, even though Shopify never sent any webhook referencing that shop or that body/topic pairing.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
