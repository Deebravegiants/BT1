### Title
Unvalidated swap route contracts can steal unrelated caller funds through injected authorization - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
A crafted `swap` payload can place attacker-controlled code inside a caller-authorized controller strategy invocation. During that invocation, the malicious venue can request an unrelated token transfer from the caller; if the caller signs the authorization tree produced by simulation, that transfer executes even though it is unrelated to the lending swap. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_collateral` authenticates the account owner or delegate and accepts caller-controlled `swap` bytes without interpreting the contracts that the configured router will invoke. [3](#0-2)  The controller snapshots balances, authorizes only the controller-to-router input transfer, and invokes `execute_strategy` with those bytes. [4](#0-3) 

The router decodes pool and token contract addresses from the payload’s attacker-controlled `assets` registry and dispatches the selected venue without an independent pool allowlist. [5](#0-4) [6](#0-5)  For example, the Soroswap adapter calls `get_reserves` and `swap` on the payload-selected `pool`, so a compatible malicious contract can execute arbitrary contract code inside the caller’s authorization scope. [7](#0-6) [8](#0-7) 

A regression test demonstrates that a rogue hop contract can invoke `wallet_token.transfer(victim, attacker, amount)` and have that invocation recorded as a child of the victim’s `swap_collateral` authorization. [9](#0-8)  Enforcing authorization rejects the transfer when the victim signs only the honest tree, but executes it when the victim signs the simulation-produced tree containing the malicious child. [10](#0-9) 

### Impact Explanation
This is theft of user funds: the malicious venue can drain arbitrary token balances held by the caller, independent of the collateral amount being swapped. [11](#0-10)  The strategy can still return a fair swap output and pass the controller’s balance-delta and final-risk checks, so neither the measured settlement nor account solvency bounds the stolen wallet funds. [12](#0-11) 

### Likelihood Explanation
The attacker can deploy a venue-compatible contract and encode it as the pool address in a valid compact route, while setting reserves and output so the strategy otherwise succeeds. [13](#0-12) [14](#0-13)  Exploitation requires the victim to submit a poisoned authorization tree after simulation, analogous to the CVE’s reliance on crafted user-supplied configuration and executable files. [15](#0-14)  Because transaction simulations commonly present additional contract calls as nested authorization entries, a malicious quote or interface can make the injected transfer difficult for a user to distinguish from a legitimate route dependency. [16](#0-15) 

### Recommendation
Do not allow route payloads to select arbitrary executable venue contracts for calls made beneath caller authorization; bind each supported venue to a governance-approved pool registry or otherwise cryptographically verify the deployed pool identity before dispatch. [6](#0-5)  Until pool identity is constrained, wallets and integrating clients must decode `swap` bytes and reject any authorization tree containing calls other than the exact expected input transfer. [17](#0-16) 

### Proof of Concept
1. The victim owns a Normal account with USDC collateral and holds an unrelated `wallet_token` balance. [18](#0-17) 
2. The attacker deploys a contract exposing the venue calls used by the selected adapter, such as `get_reserves` and `swap`, and programs it to invoke `wallet_token.transfer(victim, attacker, victim_balance)` while also paying a valid `token_out` amount to the router. [19](#0-18) [20](#0-19) 
3. The attacker supplies a `StrategyPayload` whose `assets` registry contains the malicious contract as the hop pool and whose instruction selects a supported venue opcode. [21](#0-20) 
4. The victim calls `Controller.swap_collateral(caller=victim, account_id, current=HubAssetKey(USDC), amount, new=HubAssetKey(ETH), swap=payload)`. [22](#0-21) 
5. During simulation, the unrelated wallet-token transfer appears as a child authorization under the victim’s `swap_collateral` root rather than as a separate obvious transaction. [23](#0-22) 
6. If the victim signs that tree, the malicious pool moves the victim’s unrelated wallet balance to the attacker while the collateral swap completes successfully. [11](#0-10)

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
