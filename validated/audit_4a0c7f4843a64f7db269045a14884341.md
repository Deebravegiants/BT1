Audit Report

## Title
Global (non-sender-scoped) `req.ID` map allows an unprivileged client to force another user's Vault / Confidential-Relay gateway request to fail - ([File: core/services/gateway/handlers/vault/handler.go], [File: core/services/gateway/handlers/confidentialrelay/handler.go])

## Summary
Both the Vault and Confidential-Relay gateway handlers key their in-flight `activeRequests` map solely by the caller-supplied JSON-RPC `id`, with no sender/owner namespacing, unlike the codebase's own `common.RequestCache`, which correctly uses a `globalID{sender, id}` composite key. This allows any client that can reach the handler (for Confidential-Relay, before any authorization/attestation check runs; for Vault, after the attacker's own request passes signature-based `ProcessRequest`) to preempt an `id` value and cause a victim's request using the same `id` to fail with "request ID already exists."

## Finding Description
`HandleJSONRPCUserMessage` in both handlers only validates that `req.ID` is non-empty and ≤200 characters before allocating a slot in the shared `activeRequests` map keyed purely by `req.ID`: [1](#0-0) [2](#0-1) 

For the Vault handler, `newActiveRequest` is only reached after `h.requestProcessor.ProcessRequest` succeeds, meaning the attacker must submit a request that passes signature-based authorization (`req.Auth`) for their own identity — this is a real barrier (the attacker cannot occupy the slot with a garbage/unauthenticated request), but the attacker does not need to be the *victim's* owner, and the map key does not include the owner: [3](#0-2) [4](#0-3) 

For the Confidential-Relay handler, `newActiveRequest` is called directly in `HandleJSONRPCUserMessage` with no authorization or attestation gate beforehand in that function — the only checks preceding it are the empty/length checks on `req.ID`: [5](#0-4) 

By contrast, `common.RequestCache`, used elsewhere in the gateway, keys pending requests by `globalID{sender, id}` precisely to avoid this class of collision: [6](#0-5) 

The existing unit tests in both packages confirm the current (vulnerable) contract — resubmitting the same `id` unconditionally fails regardless of sender identity: [7](#0-6) [8](#0-7) 

The gateway's `multiHandler.HandleJSONRPCUserMessage` dispatches directly to the per-method handler with no upstream deduplication or sender-aware ID rewriting, so this reaches the vulnerable code path unmodified: [9](#0-8) 

## Impact Explanation
This is an in-scope, gateway-level request denial-of-service. For the Confidential-Relay handler, any caller — without needing to pass attestation or produce a valid workflow/capability payload — can occupy an arbitrary `id` slot before authorization occurs, since `newActiveRequest` runs unconditionally in `HandleJSONRPCUserMessage`, ahead of any authorization/attestation logic visible in that function. For the Vault handler, the bar is higher: the attacker must submit a request that passes `ProcessRequest`'s signature-based authorization for their *own* account, but since the map key is only `req.ID` (not owner+ID), a successfully authorized attacker request with a colliding `id` will still cause a legitimate, unrelated owner's request using the same `id` to be rejected with "request ID already exists" / "request was already authorized previously." This matches an in-scope "unauthorized denial of legitimate gateway request" impact class, though it is bounded to causing request failure/retry rather than fund loss, secret exfiltration, or impersonation.

## Likelihood Explanation
Moderate for Confidential-Relay (no authentication barrier to occupy a slot), lower for Vault (requires the attacker to have valid signed credentials of their own, i.e., not a fully anonymous exploit, but still requires no privilege over the victim or the victim's resource). Exploitability in both cases is bounded by the entropy/predictability of the `id` values chosen by legitimate clients, which is determined by SDK/workflow code outside this repo and could not be verified here. If IDs are low-entropy, sequential, or derived from predictable identifiers (as the confidential-relay code path's retry-related comments suggest is a plausible client pattern), collision is straightforward to engineer.

## Recommendation
Scope `activeRequests` by a composite key of `(sender/authenticated identity, req.ID)` rather than `req.ID` alone, mirroring the `globalID{sender, id}` pattern already used in `core/services/gateway/handlers/common/requestcache.go`. For the Confidential-Relay handler specifically, ensure `newActiveRequest`/ID-collision checks do not execute (or do not leak collision information) before minimal caller identity/attestation is established. Add regression tests proving two different senders can reuse the same `id` concurrently without one rejecting the other.

## Proof of Concept
1. Confidential-Relay: send `HandleJSONRPCUserMessage` with `id = "X"` and no valid attestation from an arbitrary/unauthenticated caller; it will occupy the map slot as shown by `TestConfidentialRelayHandler_DuplicateRequestID` [7](#0-6) . A second, legitimate request with the same `id` from an unrelated sender will fail with "request ID already exists."
2. Vault: an attacker with their own valid signed credentials submits a `secrets.*` request with `id = "X"` for their own owner; a victim's unrelated, legitimately authorized request with the same `id` subsequently fails with "request was already authorized previously," as shown by the existing `unhappy path - duplicate requestId` test [8](#0-7) , modified so the two calls originate from different owners/callbacks instead of the same one.

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	labels := h.extractRequestLabels(req)
	l := h.requestLogger(req, labels)
	l.Debugw("handling confidential relay request", "nodes", len(h.donConfig.Members), "f", h.donConfig.F)

	ar, err := h.newActiveRequest(req, labels, callback)
	if err != nil {
		return err
	}

	return h.fanOutToNodes(ctx, l, ar)
}

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], labels requestLabels, callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID, "executionID", labels.ExecutionID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		labels:    labels,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}

type globalID struct {
	sender string
	id     string
}

type pendingRequest[T any] struct {
	handlers.Callback
	responseData *T
	timeoutTimer *time.Timer
	mu           sync.Mutex
}

func NewRequestCache[T any](timeout time.Duration, maxCacheSize uint32) RequestCache[T] {
	return &requestCache[T]{cache: make(map[globalID]*pendingRequest[T]), timeout: timeout, maxCacheSize: maxCacheSize}
}

func (c *requestCache[T]) NewRequest(lggr logger.Logger, request *api.Message, callback handlers.Callback, responseData *T) error {
	if request == nil {
		return errors.New("request is nil")
	}
	if responseData == nil {
		return errors.New("responseData is nil")
	}
	key := globalID{request.Body.Sender, request.Body.MessageID}
	c.mu.Lock()
	defer c.mu.Unlock()
	_, ok := c.cache[key]
	if ok {
		return errors.New("request already exists")
	}
	if len(c.cache) >= int(c.maxCacheSize) {
		return errors.New("request cache is full")
	}
