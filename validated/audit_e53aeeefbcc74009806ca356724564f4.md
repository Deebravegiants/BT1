## Title
Webhook `shop` domain identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop` (tenant) identifier used to route and label webhook data to the host application's handler is read from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is **not** included in the signed bytes. This breaks the identity binding `hmac == sign(topic, shop, body, webhook_id, api_version)` down to `hmac == sign(body)` only, so a request whose body+hmac pair was legitimately produced for one shop can be replayed with an arbitrary `shop-domain` header and will still pass HMAC validation while being attributed to a different (victim) shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop` is derived purely from an attacker-controllable header, with no cryptographic tie to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the signature strictly against `to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` trusts this unvalidated `request.shop` value and forwards it directly to the app's handler as the tenant identity for the event: [4](#0-3) 

The identity equality the gem is supposed to enforce is:
`hmac_valid(request) == (shop_header_is_the_shop_that_produced(body, hmac))`

But the actual behavior is:
`hmac_valid(request) == (body_bytes_produced_this_hmac)`, independent of `shop`.

**Attack sequence:**
1. An unprivileged attacker installs the app on their own (Shop A) — no special privilege required, this is the normal installation flow.
2. Shopify sends the attacker's app instance a legitimate webhook for Shop A: `body = B`, `x-shopify-hmac-sha256 = HMAC(secret, B)`, `x-shopify-shop-domain = shop-a.myshopify.com`.
3. The attacker captures this exact `(B, HMAC(secret, B))` pair (they are the legitimate recipient, so no secret leakage is required).
4. The attacker replays the exact same body and HMAC header to the app's public webhook endpoint, but substitutes `x-shopify-shop-domain: shop-b.myshopify.com` (any victim shop that also uses the app).
5. `Utils::HmacValidator.validate` still returns `true` because it only checks `HMAC(secret, B)` against `B`, ignoring the `shop-domain` header.
6. `Registry.process` builds `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: B, ...)` and dispatches it to the app's handler, which now believes this data belongs to Shop B.

### Impact Explanation
This crosses a tenant boundary: an attacker with no relationship to the victim shop can cause the host application to process attacker-supplied webhook content (topic + body) under the victim shop's identity. Depending on how the host app's webhook handler uses `data.shop` (e.g., updating records keyed by shop, syncing state, billing acknowledgment, triggering per-shop side effects), this enables cross-tenant data confusion/corruption — a Critical-class impact ("cross-tenant access") per the scope's own rubric, and matches the explicitly called-out analog "a shop authenticated versus the shop stored as a session key."

### Likelihood Explanation
Moderate-to-high: no secrets, tokens, or privileged access are needed. Any developer/attacker can install the app for free on a throwaway shop, capture one legitimate webhook body+HMAC pair for any topic they can trigger (many topics are triggerable by ordinary shop actions, e.g. `app/uninstalled`, `shop/update`, or order/customer topics if a dev store is used), and replay it against the shared public webhook endpoint with a different `shop-domain` header. The only friction is guessing/knowing a target shop's `myshopify.com` domain, which is generally discoverable/public.

### Recommendation
Include the tenant-identifying headers (`shop-domain` at minimum, ideally `topic`, `webhook-id`, `api-version`) in the HMAC-signable bytes, or otherwise cryptographically bind the shop to the signed payload before trusting `request.shop`/emitting `WebhookMetadata`. Since Shopify's actual webhook HMAC only signs the body (this is Shopify's documented behavior, not something this gem controls), the gem should instead document/require that host apps must independently verify that `request.shop` corresponds to an active, previously-established session/installation for that shop before acting on the payload, and the gem's own `Registry.process` should not implicitly present `request.shop` as trustworthy purely because `HmacValidator.validate` returned `true`.

### Proof of Concept
```ruby
require "shopify_api"

secret = ShopifyAPI::Context.api_secret_key
body = '{"id":123}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, body)

# Step 1: legitimate webhook received by attacker's own shop
legit_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
}
legit_request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: legit_headers)
ShopifyAPI::Utils::HmacValidator.validate(legit_request) # => true (expected)

# Step 2: replay identical body+hmac but swap shop-domain to a victim shop
spoofed_headers = legit_headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")
spoofed_request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: spoofed_headers)
ShopifyAPI::Utils::HmacValidator.validate(spoofed_request) # => true (STILL PASSES — vulnerability)

ShopifyAPI::Webhooks::Registry.process(spoofed_request)
# Handler#handle is invoked with data.shop == "victim-shop.myshopify.com",
# even though the attacker fully controls the body and never proved
# any relationship with victim-shop.
```

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
