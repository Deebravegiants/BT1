In `ShopifyAPI::Webhooks::Request` (`lib/shopify_api/webhooks/request.rb`), `to_signable_string` returns only `@raw_body`, so the HMAC computed by `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) authenticates the body bytes only. The `shop`, `topic`, `api_version`, and `webhook_id` fields are all read straight from HTTP headers (`shopify_header`) and are never part of the signed content, yet `Registry.process` (`lib/shopify_api/webhooks/registry.rb`) passes `request.shop` directly into `WebhookMetadata` used by the host app's handler as the tenant identifier.

### Title
Webhook `shop` (and topic/webhook_id) identity is unauthenticated — cross-tenant confusion via header/body mismatch - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns `@raw_body`, so `Utils::HmacValidator.validate` verifies the integrity of the JSON body but not of the `x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`, or `x-shopify-api-version` headers. `Registry.process` trusts `request.shop` (and `request.topic`/`request.webhook_id`) as the tenant/event identity passed to the app's handler once only the body's HMAC has been checked.

### Finding Description
The equality the code implicitly assumes is: `shop reported to handler == shop that produced the signed body`. In reality:
- `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` header [1](#0-0) .
- `Request#to_signable_string` returns solely `@raw_body`, excluding every header [2](#0-1) .
- `Request#shop`, `#topic`, `#webhook_id`, `#api_version` are all read from headers with zero cryptographic binding to the body/HMAC [3](#0-2) .
- `Registry.process` uses the unauthenticated `request.shop` to build `WebhookMetadata` handed to the merchant's own handler code, which apps commonly use to select which tenant record to mutate [4](#0-3) .

Since a Shopify app's `api_secret_key` is shared across *all* installed shops (it is a per-app secret, not per-shop), any legitimate webhook delivery an attacker's own shop receives is HMAC-valid under the very same secret used for every other tenant of that app. Because the header set (shop domain, topic, webhook id) sits entirely outside the signed bytes, an attacker who operates their own shop installation of the target app can capture one authentic `raw_body`+`hmac` pair from a webhook Shopify sent them, then resubmit that exact `raw_body`/`hmac` to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop. `HmacValidator.validate` still returns `true` (the body bytes and secret are unchanged), and the handler receives `WebhookMetadata` claiming the event belongs to the victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: `shop authenticated (by HMAC) ≠ shop reported to the handler`. Any app whose webhook handlers key off `WebhookMetadata#shop` to look up/update per-merchant state (a normal and encouraged pattern, per `docs/usage/webhooks.md`) can be made to attribute an attacker-controlled event to another merchant's shop record — a cross-tenant data-integrity/isolation violation stemming purely from this gem's request-parsing/verification logic, not from host misuse.

### Likelihood Explanation
Requires only: (1) the attacker's own working installation of the target app (any unprivileged merchant can install most public apps), and (2) the ability to POST arbitrary headers to the app's public webhook endpoint (trivial, unprivileged, internet-reachable by design). No access token, `client_secret`, or privileged account is needed — the only "credential" involved (the raw body + valid HMAC) is handed to the attacker for free by Shopify the moment they receive one webhook for their own store.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable content used for verification, or otherwise cryptographically bind them to the payload (e.g., verify `shop` against a value embedded/expected in the parsed body, or require callers to separately validate `request.shop` against a known/authorized shop list before trusting it). At minimum, document prominently that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are **not** covered by the HMAC and must not be trusted for tenant routing without an independent authorization check.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook, capturing `raw_body` = `B` and header `x-shopify-hmac-sha256` = `H` (valid because `H = HMAC(app_secret, B)`).
2. Attacker POSTs to the app's public webhook route with the identical `raw_body: B` and `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`/`x-shopify-webhook-id` if the target topic's body shape permits).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(app_secret, B)` and matches `H` — verification succeeds [5](#0-4) .
4. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-supplied data under the victim shop's identity [6](#0-5) .
