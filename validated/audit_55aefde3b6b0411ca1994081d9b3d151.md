## Title
Unchecked ERC20 `transfer()` return value in Tron `IntentGatewayV2.withdraw()`/`SweepDust` allows escrow to be marked settled while tokens are never delivered - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` imports and correctly uses `SafeERC20.safeTransferFrom` when *pulling* tokens into escrow (`placeOrder`), but the two code paths that *pay out* escrowed and dust tokens — `withdraw()` and the `SweepDust` branch of `onAccept()` — bypass `SafeERC20` entirely and instead make raw low-level calls, checking only that the call did not revert, not that the token actually returned `true`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`withdraw()` is the function that releases user-escrowed input tokens to a solver (on `RedeemEscrow`) or refunds a user (`RefundEscrow`). For every non-native token it does:

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
```

`success` is only `false` when the low-level call itself reverts (e.g., no code at `token`, or the callee explicitly reverts). Any ERC20/TRC20 implementation that **returns `false` instead of reverting on failure** (a well-documented category of non-standard tokens, and one the very external report this analog is based on explicitly warns about) will make this call return `success = true` with `returndata` decoding to `false`. Because the code never inspects `returndata`, it treats this as a successful transfer:
- `_orders[body.commitment][token] -= amount` is decremented as if the beneficiary was paid.
- `_filled[body.commitment] = beneficiary` is set unconditionally before the loop, permanently marking the order as filled.
- `EscrowReleased`/`EscrowRefunded` is emitted.

The same defect exists for the transaction-fee payout in the same function, and again in the hyperbridge-governed `SweepDust` handler in `onAccept()`:

```solidity
(bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
if (!success) revert TransferFailed();
```

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, req.beneficiary, amount));
if (!success) revert TransferFailed();
```

`withdraw()` is reached from `onAccept` when a `RedeemEscrow`/`RefundEscrow` ISMP POST request is delivered by any relayer, and directly from same-chain `cancelOrder`, and from `onGetResponse` for cross-chain cancellation — i.e. it is on the primary, permissionless settlement path of every intent order, not a privileged-only path.

By contrast, the canonical EVM `IntentsBase.sol` implementation uses `SafeERC20.safeTransfer` for the equivalent outbound payouts, confirming the Tron file's raw-`call` pattern is a regression/inconsistency rather than intentional design: [4](#0-3) 

### Impact Explanation
If the escrowed input token or the protocol fee token used on the Tron deployment is one of the non-reverting ERC20/TRC20 variants (returns `false` on failure rather than reverting — e.g., insufficient balance held by the gateway due to a prior fee-on-transfer mismatch, a paused/blacklisted token, or any TRC20 with non-standard failure semantics), then:
- The beneficiary (solver or user) receives **zero tokens**.
- The escrow accounting is nonetheless decremented to zero and the order is marked `_filled`, so the loss is **permanent and unrecoverable** — the tokens remain stuck in the `IntentGatewayV2` contract with no order referencing them, and the legitimate beneficiary has no further recourse (order is already "filled").
- This is a direct, concrete loss/freezing of user or solver funds, matching the Medium/High "permanent freezing of funds" criterion.

### Likelihood Explanation
This is triggered by ordinary protocol operation — no malicious actor is required. Any relayer delivering a normal `RedeemEscrow`/`RefundEscrow` message, or a user calling `cancelOrder` same-chain, exercises `withdraw()`. The only precondition is that the escrowed/fee token returns `false` on a failed transfer instead of reverting, which is a known, non-exotic ERC20/TRC20 behavior class (this is precisely the risk class the underlying Sherlock report calls out). Given the contract is explicitly built for the Tron/TRC20 ecosystem, where non-standard token return-value behavior is common, likelihood is reasonably high whenever the gateway is configured with such a token.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` payout sites in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw()` for both token payouts and fee payout, and the `SweepDust` branch in `onAccept()`) with `SafeERC20.safeTransfer`, consistent with the `safeTransferFrom` already used in `placeOrder` and with the pattern used in `evm/src/apps/intentsv2/IntentsBase.sol`. This ensures a `false` return value causes a revert rather than being silently treated as success, keeping escrow state consistent with actual token movement.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron) with a token `T` whose `transfer()` returns `false` on failure instead of reverting (e.g., due to the gateway's balance for `T` being insufficient because of an unrelated fee-on-transfer/dust accounting edge case, or a blacklist/pause condition on `T`).
2. A user places an order with input `T`, escrowing `amount` via `placeOrder` (uses `safeTransferFrom`, succeeds).
3. A solver fills the order on the destination chain and the settlement `RedeemEscrow` POST request is relayed back and delivered via `onAccept` → `withdraw()`.
4. Inside `withdraw()`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` executes: the call does not revert but the encoded return data is `false`. `success` evaluates to `true`, so the `if (!success) revert TransferFailed();` check passes.
5. `_orders[commitment][token] -= amount` executes, `_filled[commitment] = beneficiary` is set, and `EscrowReleased` is emitted — even though `beneficiary`'s token balance never changed.
6. The `amount` of `T` is now permanently stuck in the `IntentGatewayV2` contract with no order record pointing to it, and the beneficiary has no way to reclaim it since the order is already marked filled.
