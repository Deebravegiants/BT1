### Title
Loaded-accounts cost model charges only account *data bytes* (rounded to 32 KiB pages), letting an attacker trigger many real disk-index probes almost for free - (File: `accounts-db/src/accounts_index/in_mem_accounts_index.rs`, `cost-model/src/cost_model.rs`)

### Summary
`InMemAccountsIndex::get_internal_inner` performs a real disk bucket read (`load_account_entry_from_disk` → `BucketApi::read_value`) for every distinct pubkey that has been evicted from the in-memory index, one lookup per pubkey with no batching or amortized cost. `CostModel::calculate_loaded_accounts_data_size_cost` and the SVM's `load_transaction_accounts` only account for total loaded bytes (with a 64-byte-per-account base charge, `TRANSACTION_ACCOUNT_BASE_SIZE`), rounded up to 32 KiB pages, and charge nothing proportional to the number of distinct index/disk lookups performed.

### Finding Description
When a transaction message references K accounts, `load_transaction_accounts` iterates every non-fee-payer key and calls `load_transaction_account` → `AccountLoader::load_account` → ultimately `AccountsIndex::get_and_then` → `InMemAccountsIndex::get_internal_inner` for each key [1](#0-0) [2](#0-1) . If a pubkey is not resident in the in-memory hash map (i.e., it was previously flushed to disk and evicted), `get_internal_inner` falls back to `load_account_entry_from_disk`, which does a genuine disk bucket read via `BucketApi::read_value` [3](#0-2) [4](#0-3) . This I/O cost is per-pubkey and independent of account size — a zero-byte cold account triggers the exact same bucket lookup as a large one.

On the cost-accounting side, every collected account contributes only `TRANSACTION_ACCOUNT_BASE_SIZE` (64 bytes, fixed per SIMD-0186) plus its actual data length to `loaded_tx_data_size` [5](#0-4) [6](#0-5) . `CostModel::calculate_loaded_accounts_data_size_cost` converts this accumulated byte total into CU cost only by rounding total bytes up to a 32 KiB page and multiplying by `DEFAULT_HEAP_COST` (8 CU/page) [7](#0-6) [8](#0-7) . Since 32 KiB / 64 bytes = 512, an attacker can reference up to ~512 distinct zero/near-zero-byte cold accounts in a single transaction and still fall entirely within one 32 KiB page, i.e., pay the exact same 8 CU loaded_accounts_data_size_cost as a transaction touching a single already-resident account of equivalent total data size. Yet each of those ~512 cold accounts independently triggers a distinct disk bucket read in `get_internal_inner`, which is real disk I/O work that scales linearly with the number of distinct accounts, not with the (page-quantized) byte total.

No existing guard mitigates this: account key sanitization only limits transaction size/format, not the "coldness" of referenced accounts; write-lock cost (`WRITE_LOCK_UNITS * num_write_locks`) is unrelated to read-account disk lookups and doesn't scale with distinct read-only accounts either. The cost model's `COST_UPPER_BOUND` invariant (loaded_accounts_data_size_cost should upper-bound the real cost of loading accounts) is therefore violated for the disk-I/O dimension of account loading — it only bounds byte-copying/serialization cost, not per-account index-lookup cost.

### Impact Explanation
An unprivileged attacker can craft ordinary transactions (using normal account lists, or address lookup tables to cheaply reference many resolved accounts within the packet size limit) that reference hundreds of distinct cold, evicted, small accounts. Each such transaction forces the validator to perform hundreds of real bucket-map disk reads in `InMemAccountsIndex::get_internal_inner`/`load_account_entry_from_disk`, while the cost tracker (`bank.write_cost_tracker().try_add`) only charges a near-zero, page-quantized `loaded_accounts_data_size_cost`. Submitted at scale across many transactions in a block, this allows extraction of real disk I/O work far in excess of what is charged, materially underpricing execution and potentially degrading validator/replay throughput — matching the "materially underpriced execution" bounty category tied to the `COST_UPPER_BOUND` invariant.

### Likelihood Explanation
This requires no privileged access: any user can submit a transaction (or a batch of transactions) referencing many distinct small/cold accounts (e.g., freshly-created zero-lamport or minimal accounts that have since aged out of the in-memory index into disk buckets, achievable by simply waiting for the routine flush/eviction cycle). It is fully repeatable and does not depend on validator, leader, or peer control; only ordinary account creation and transaction crafting are needed. Feasibility is bounded by the number of distinct accounts a single transaction/message can reference (limited by packet size but multipliable via lookup tables), and by needing target accounts to actually reside on disk (a normal, common state for old/cold accounts on a live cluster).

### Recommendation
Add a cost component to `CostModel`/`TransactionCost` that scales with the number of *distinct* accounts referenced by the transaction (not just quantized total bytes), reflecting the fixed cost of an index/disk lookup per account (analogous to `write_lock_cost` for writable locks, but for the guaranteed one-lookup-per-key cost regardless of size). Alternatively, remove/lower the 32 KiB-page quantization granularity for the base-64-byte-per-account charge so cost scales near-linearly with account count rather than saturating at zero marginal cost until a full page is filled.

### Proof of Concept
Integration test outline (accounts-db + cost-model crates):
1. Build an `AccountsDb`/`AccountsIndex` configured with disk index enabled (`new_disk_buckets_for_test`).
2. Insert K (e.g. 500) unique small (0-byte data) accounts, flush them to disk, and force eviction from the in-memory map (age forward + `flush`), verifying via `get_only_in_mem` that they are absent from memory.
3. Construct a `RuntimeTransaction` (or use `SVMMessage`) referencing all K pubkeys as read-only accounts (or via one/several ALTs to fit packet-size limits).
4. Call `load_transaction_accounts`/`AccountLoader::load_account` for each pubkey, instrumenting/counting calls into `InMemAccountsIndex::load_account_entry_from_disk` (e.g., via the existing `stats().load_disk_found_count`/`load_disk_missing_count` counters) — assert count == K, confirming K real disk reads occurred.
5. Compute `CostModel::calculate_loaded_accounts_data_size_cost(loaded_accounts_data_size, &feature_set)` for this transaction's actual `loaded_accounts_data_size` and compare it against the cost for a control transaction that touches a single already-in-memory account with data of the same *total* size (K * 64 bytes concentrated in one account).
6. Assert both transactions produce an equal (or near-equal, single-page) `loaded_accounts_data_size_cost`, while `load_disk_found_count`/`load_disk_missing_count` (or measured wall-clock/I/O op count) differs by ~K, proving the cost model fails to upper-bound the real per-account disk-lookup cost.

    fn load_from_disk(&self, pubkey: &Pubkey) -> Option<(SlotList<U>, RefCount)> {
        self.bucket.as_ref().and_then(|disk| {
            let m = Measure::start("load_disk_found_count");
            let entry_disk = disk.read_value(pubkey);
            match &entry_disk {
                Some(_) => {
                    Self::update_time_stat(&self.stats().load_disk_found_us, m);
                    Self::update_stat(&self.stats().load_disk_found_count, 1);
                }
                None => {
                    Self::update_time_stat(&self.stats().load_disk_missing_us, m);
                    Self::update_stat(&self.stats().load_disk_missing_count, 1);
                }
            }
            entry_disk.map(|(slot_list, ref_count)| {
                // SAFETY: ref_count must've come from in-mem first, so converting back is safe.
                (slot_list, ref_count as RefCount)
            })
        })
    }

    /// lookup 'pubkey' in index (in_mem or disk).
    /// call 'callback' whether found or not
    pub(super) fn get_internal_inner<RT>(
        &self,
        pubkey: &Pubkey,
        // return true if item should be added to in_mem cache
        callback: impl for<'a> FnOnce(Option<&AccountMapEntry<T>>) -> (bool, RT),
    ) -> RT {
        self.get_only_in_mem(pubkey, true, |entry| {
            if let Some(entry) = entry {
                callback(Some(entry)).1
            } else {
                // not in cache, look on disk
                let stats = self.stats();
                let disk_entry = self.load_account_entry_from_disk(pubkey);
                if disk_entry.is_none() {
                    return callback(None).1;
                }
                let disk_entry = disk_entry.unwrap();
                let mut map = self.map_internal.write().unwrap();
                let capacity_pre = map.capacity();
                let entry = map.entry(*pubkey);
                let retval = match entry {
                    Entry::Occupied(occupied) => callback(Some(occupied.get())).1,
                    Entry::Vacant(vacant) => {
                        debug_assert!(!disk_entry.dirty());
                        let (add_to_cache, rt) = callback(Some(&disk_entry));
                        // We are holding a write lock to the in-memory map.
                        // This pubkey is not in the in-memory map.
                        // If the entry is now dirty, then it must be put in the cache or the modifications will be lost.
                        if add_to_cache || disk_entry.dirty() {
                            stats.inc_mem_count();
                            vacant.insert(Box::new(disk_entry));
                        }
                        rt
                    }
                };
                let capacity_post = map.capacity();
                drop(map);
                stats.update_in_mem_capacity(capacity_pre, capacity_post);
                retval
            }
        })
    }

    /// Compute the number of pages needed to contain provided number of bytes.
    fn calculate_pages_for_bytes(bytes: u32) -> u64 {
        u64::from(bytes)
            .saturating_add(ACCOUNT_DATA_COST_PAGE_SIZE.saturating_sub(1))
            .saturating_div(ACCOUNT_DATA_COST_PAGE_SIZE)
    }

    pub fn calculate_pages_cost(num_pages: u64) -> u64 {
        num_pages.saturating_mul(DEFAULT_HEAP_COST)
    }

        loaded_accounts_data_size: u32,
        _feature_set: &FeatureSet,
