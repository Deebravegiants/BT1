### Title
Webhook `shop` identity not bound to HMAC, enabling cross-tenant webhook data injection - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from an HTTP header (`shopify-shop-domain` / `x-shopify-shop-domain`) that is never included in the HMAC signature computation. `HmacValidator` only authenticates the raw request body, so an attacker who can obtain any validly-signed webhook body (e.g., by triggering a webhook to their own installed shop) can resend that exact body with a different `shop-domain` header and have it pass HMAC verification while being attributed to an arbitrary victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop` is read directly and exclusively from an attacker-controllable HTTP header, with no cross-check against anything covered by the signature: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)`, which internally calls `verifiable_query.to_signable_string` (i.e., only the body) and compares against `verifiable_query.hmac`: [4](#0-3) [5](#0-4) 

After this check succeeds, `request.shop` — a value that was never part of what was signed — is passed straight into `WebhookMetadata` and handed to the host application's handler as the trusted tenant identifier: [4](#0-3) 

This breaks the identity binding: **HMAC-covered bytes (body only) ≠ bytes the gem treats as authenticated (body + shop header)**. Any party capable of producing one validly-signed body/HMAC pair (trivially available to any developer who installs the target app on their own shop, since webhooks are signed with the single app-wide `client_secret` shared across all shop installs) can replay that same body with a forged `shop-domain` header pointed at a different, victim shop, and `Registry.process` will accept it as authentic data for the victim shop.

### Impact Explanation
This is a cross-tenant data injection: a multi-tenant app that keys per-shop state (sessions, inventory sync, order processing, GDPR/customer data) off `WebhookMetadata#shop` can be made to process attacker-supplied webhook payloads under a victim shop's identity, since the shop field is unauthenticated relative to the HMAC that gates acceptance. This matches the "cross-tenant access" Critical-impact category, because the gem itself — not merely host-application misuse — supplies the unauthenticated `shop` value as if it had been verified.

### Likelihood Explanation
Exploitation only requires an attacker to install the target app on a shop they control (or any shop already sending it webhooks) to legitimately obtain one valid `(body, hmac)` pair, since the `client_secret` used to sign webhooks is shared across every shop that installs the app, not shop-specific. The attacker then simply retransmits that body with a modified `shop-domain` header to the app's webhook endpoint. No secret material, TLS interception, or privileged access is needed beyond normal app installation.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook-id`) values into the signed material, or independently verify that the `shop-domain` header matches a shop that is expected/authorized for the delivered webhook (e.g., cross-check against a known session/shop record) before constructing `WebhookMetadata`. At minimum, document that `request.shop` is unauthenticated and must not be trusted as a tenant boundary by host applications, and consider extending `to_signable_string`/`HmacValidator` to incorporate header-derived identity fields.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers (or receives) a legitimate webhook, e.g. `orders/create`, with body `B`, correctly signed as `HMAC(app_secret, B)` and headers including `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the exact same raw body `B` and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `HmacValidator.validate`, which only checks `HMAC(app_secret, B)` — this still matches since `B` is unchanged: [4](#0-3) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, which the host app processes as authentic data belonging to the victim tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
