### Title
Unbounded length-prefixed allocation in livestream `Upstream` TCP reader causes memory-exhaustion DoS - (File: `src/agents/livestream/upstream.rs`)

### Summary
The orb's livestream ingestion service opens a raw TCP listener on `0.0.0.0:9201` and, for every accepted connection, reads a 4-byte big-endian length prefix and immediately allocates a buffer of that exact size before reading any payload bytes. There is no upper bound on the declared length, so a single connection can force the process to allocate up to ~4 GiB, and repeated/parallel connections can exhaust host memory, mirroring the "unbounded request size" bug class from the reference report.

### Finding Description
`Upstream::new` binds a `TcpListener` to all interfaces on a fixed port: [1](#0-0) 

Each accepted connection is driven by `EventReader::poll_stream`, which first reads 4 bytes to determine the payload length and then allocates a `Vec<u8>` of exactly that many bytes with no sanity check or maximum-size cap: [2](#0-1) 

```rust
if self.len_read == 4 {
    self.buf = vec![0; u32::from_be_bytes(self.len) as usize];
}
```

`u32::from_be_bytes` allows any value up to `0xFFFFFFFF` (~4.29 GiB), fully attacker-controlled from the 4 raw bytes sent over the socket, before a single byte of actual payload has been validated. This is structurally identical to the Covenant Signer flaw: an externally reachable network listener with no cap on the size of an incoming message, allowing memory exhaustion and process termination (OOM kill) on the orb.

### Impact Explanation
A remote peer able to reach TCP port 9201 on the orb (e.g., anyone on the same local network segment, since the listener binds `0.0.0.0`) can send a small 4-byte length header claiming a multi-gigabyte payload, forcing the orb process to attempt a large allocation per connection. Repeating this with multiple connections drives memory pressure until the OS OOM-killer terminates the orb-core process, taking down signup/biometric processing entirely — a device-wide denial of service, not merely of the livestream feature.

### Likelihood Explanation
Likelihood is high for any attacker with local network reachability to the orb: no authentication, handshake, or size validation occurs before the allocation, and the attack requires only a handful of bytes per connection attempt.

### Recommendation
Cap the declared payload length before allocating (e.g., reject/close the connection if `len > MAX_LIVESTREAM_MSG_SIZE`), and consider reading/allocating incrementally (e.g., with `Vec::with_capacity` plus a hard ceiling, or a bounded `BytesMut`) rather than trusting the attacker-supplied 4-byte length outright. Additionally, evaluate whether this listener needs to be reachable on all interfaces (`0.0.0.0`) or can be restricted/authenticated.

### Proof of Concept
1. Start orb-core so that the livestream `Upstream` listener binds to `0.0.0.0:9201`.
2. From another host/process reachable on that network, open a TCP connection to port 9201.
3. Send 4 bytes `FF FF FF FF` (declaring a ~4.29 GiB payload) without sending any further bytes.
4. Observe `EventReader::poll_stream` immediately allocate `vec![0; 0xFFFFFFFF]`, consuming ~4 GiB of memory for this single pending connection.
5. Repeat the connection from multiple sockets/processes in parallel to multiply memory consumption until the OS kills the orb-core process (analogous to the `psrecord`-observed OOM behavior in the original report).

Note: I was unable to fully trace call sites in `src/agents/livestream/mod.rs` (tool access ended) to confirm whether any additional authentication layer wraps this TCP listener before `Upstream` is polled; this should be verified in a follow-up review to confirm there is no upstream connection-level gate.
