## Title
Webhook Shop/Topic Identity Spoofing via Unsigned Headers - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook by validating only the HMAC over the raw request body, then trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from HTTP headers that are never covered by that signature. Any party who can supply a body/HMAC pair that was legitimately generated once (e.g. by installing the app on their own store and capturing one of their own webhook deliveries) can resubmit that exact body with a forged `shop-domain` header, and the gem will pass the attacker-chosen shop identity to the host application's handler as if it were verified.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and the HMAC comparison in `Utils::HmacValidator.validate` is computed exclusively against that body: [1](#0-0) [2](#0-1) 

However, `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` are all read straight from attacker-controllable HTTP headers, entirely outside the signed content: [3](#0-2) 

`Registry.process` validates only the HMAC (i.e., only the body), then immediately hands the unauthenticated `request.shop` value to the application's webhook handler as the identity of the tenant the payload belongs to: [4](#0-3) 

The broken binding is:
`HMAC(raw_body, client_secret) == received_hmac` is treated as proof of `shop-domain header == authentic origin shop`, but the equality that is actually needed — `shop-domain header ⊆ signed content` — never holds. `shop`, `topic`, and `webhook_id` are parsed but never verified.

Because a single app's `client_secret` is shared across every merchant that installs the app, any merchant (an "unprivileged internet user" relative to other tenants of the same app) can:
1. Install the app on their own shop and capture one legitimate webhook delivery (raw body + `x-shopify-hmac-sha256` header) — this is a valid signature under the shared app secret.
2. Replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint, substituting the `x-shopify-shop-domain` header with a victim shop's domain (and optionally a different `topic`/`webhook_id`).
3. `HmacValidator.validate` still succeeds because the body is unchanged, so `Registry.process` dispatches the payload to the handler tagged with the victim's shop, via `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`.

Any host application that uses `request.shop` (or the resulting `WebhookMetadata#shop`) as the tenant key to look up a session, update per-shop records, or authorize a subsequent write/API call will act on attacker-chosen data under the wrong tenant's identity — a cross-tenant confusion entirely enabled by this gem's failure to bind the shop/topic identity to the HMAC-verified bytes.

### Impact Explanation
This breaks the tenant isolation guarantee the HMAC check is supposed to provide: a signature that only proves "this body came from Shopify for *some* shop using this app" is being relied upon by consuming applications as "this body came from Shopify for *this specific* shop." That satisfies the Critical criterion of cross-tenant access, since data intended for/about shop A can be injected and attributed to shop B purely by manipulating unauthenticated headers on a public HTTP endpoint.

### Likelihood Explanation
Any user who can install (or has previously installed) the target app on a shop they control can capture a self-authored, validly-signed webhook body, since the app's `client_secret` is identical for all installs. Replaying it with a modified `shop-domain` header against the app's public webhook endpoint requires no special access, no leaked credentials, and no interception of another tenant's traffic — only the ability to send an HTTP POST, which satisfies the "unprivileged internet user" threat model.

### Recommendation
Bind the identity fields to the signed payload before trusting them:
- Require the host application (or the gem itself) to cross-check `request.shop` against the shop associated with the currently-loaded session/webhook registration for that topic before dispatch, rather than trusting the header verbatim.
- Where possible, include `shop`, `topic`, and `webhook_id` in the value that is HMAC-verified (or independently verify `shop` against Shopify's known shop list/API for the app) instead of relying solely on `raw_body`.
- At minimum, document prominently that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are NOT authenticated by `HmacValidator` and must not be used as an authorization/tenant boundary without additional verification.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com"
# and captures one legitimate webhook delivery:
raw_body = '{"id":123,"note":"hello"}'
valid_hmac_b64 = "<hmac captured from Shopify's real delivery, computed with the app's shared client_secret over raw_body>"

# Attacker replays the same body+hmac to the app's public webhook endpoint,
# but swaps the shop header to a victim shop they do not control:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac_b64,   # still valid: HMAC only covers raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # unauthenticated
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) succeeds (body unchanged),
#    handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
#    is invoked with attacker-controlled body attributed to the victim shop.
``` [5](#0-4)
