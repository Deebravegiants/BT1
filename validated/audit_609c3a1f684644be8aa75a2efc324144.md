### Title
Unvalidated caller-supplied swap route lets a rogue venue contract join the caller's auth tree and drain their wallet - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The external report describes attacker-controlled data reaching a dangerous sink (`shell.openExternal` executing a `file://`/`smb://` binary) after the victim is tricked into approving a single action. The XOXNO Lending analog is the router strategy path: controller entrypoints `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, and `flash_position` accept a fully attacker-constructed `StrategySwap`/route XDR and pass it unmodified to the swap router, which invokes whatever pool/token addresses the payload names. Neither the controller nor the router validates or allowlists the venue/pool addresses, so a malicious "pool" contract runs with the caller's authorization on the stack and can attach a `token.transfer(caller, attacker, amount)` child invocation that an honest simulation records under the caller's own auth entry. If the victim signs that tree — exactly analogous to the victim clicking the malicious link — arbitrary tokens in the victim's wallet are stolen, not just the routed `amount_in`.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs` authorizes only one exact input transfer `token_in.transfer(controller, router, amount_in)` and then calls `router.execute_strategy(&controller, &amount_in, swap)` inside the flash guard, with no inspection of `swap`'s contents and no minimum-output bound enforced by the controller (only `received > 0`). The threat model explicitly states the router "calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization," and that "a token transfer that such code makes from the caller is recorded by an honest simulation as a child of the caller's authorization entry, and it executes if the caller signs that tree." The harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` proves this end-to-end: a rogue `hop_pool` contract invoked during `swap_collateral` performs `token::Client::transfer(&victim, &to, &amount)` on an unrelated token held only in the victim's wallet, and it executes once Alice signs the auth tree. The controller's post-swap checks (`RouterOverspend`, `NoSwapOutput`, final HF gates) all pass because the router can pay a fair `min_out` — the theft is orthogonal to swap accounting, just as the URI payload was orthogonal to the auth dialog.

### Impact Explanation
Theft of user funds. The attacker drains any token balance in the victim's wallet (including tokens the protocol never listed, e.g., `WALLET_BALANCE` in the test), bounded by what the victim holds and signs for, not by `amount_in`. This is strictly worse than a bad-price swap: the measured-output and risk gates cannot bound a loss that bypasses protocol accounting entirely.

### Likelihood Explanation
High exploitability with one social-engineering step identical to the report's `galleon://` lure: the attacker crafts a malicious `routeXdr` (an "own swap route" is an allowed reach) and delivers it through a compromised or malicious frontend/quote, email, or website. The victim's transaction simulates successfully because the rogue transfer is a legitimate child of their auth entry; only a client that decodes the route and inspects the auth tree — a behavior the docs say clients "must" implement but the contract does not enforce — would refuse it. Any of the five router-backed strategy entrypoints exposes the path.

### Recommendation
Mirror the report's "whitelist before the dangerous call" fix on-chain rather than relying on clients: maintain a governance-managed allowlist of venue pool/token addresses (extending `INV-STRAT-03`'s approved-pool pattern to router venues), and have the controller or router reject a `StrategyPayload` whose `assets` registry references non-allowlisted pools before any venue call. Additionally, enforce a caller-supplied `min_out` bound in the controller's measured-output check so a compromised route cannot consume authorized input for dust while passing risk gates.

### Proof of Concept
1. Attacker deploys a contract `RogueHopPool` whose `swap()` calls `token::Client::new(&wallet_token).transfer(&victim, &attacker, amount)` (pattern: `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` lines 51-72).
2. Attacker builds a route XDR naming `RogueHopPool` as the Aquarius/Soroswap hop pool, with `min_out` set to a fair output so the router and controller checks pass, and delivers it to the victim as a "swap_collateral USDC→ETH" quote.
3. Victim submits `controller.swap_collateral(victim, account_id, usdc_key, amount_in, eth_key, route)`. `swap_tokens` authorizes the exact input transfer and calls `execute_strategy` (`contracts/controller/src/strategies/swap.rs:34-38`); the router invokes `RogueHopPool.swap()` under the victim's auth tree.
4. The rogue pool's `transfer(victim → attacker)` of the victim's unrelated wallet token executes because the signed auth tree includes it; the router pays fair ETH out, `verify_router_output` passes, final HF gates pass, and the transaction succeeds. Victim loses `WALLET_BALANCE` tokens beyond the routed amount.
