Based on my investigation, I've identified the strongest analog to the airdrop re-claim vulnerability in the orb-core codebase.

### Title
Signup success is determined locally without the backend's authoritative duplicate/fraud validation when `user_centric_signup` is set - ([File: src/plans/mod.rs])

### Summary
The reported bug is a **skipped re-validation check**: `AirdropDistribution.claimExact()` allows `amount` to reach `0` (a state indicating "airdrop fully claimed"), but `validate()` only checks `amount == 0` and not the separate `validated[msg.sender]` flag, so it overwrites the claim state with fresh values and lets the user claim again. The root cause is that a locally-observed state variable is trusted as proof of "not yet completed", instead of consulting the authoritative record of completion.

### Finding Description
In `MasterPlan::do_signup`, when a signup finishes the biometric pipeline, the Orb decides whether the signup is a *success* in one of two ways: [1](#0-0) 

- If `user_centric_signup` is `true` (a flag returned from the backend's `authenticated_app_data`, see [2](#0-1) ), success is derived **purely from the locally computed `signup_reason`** (`SignupReason::Normal` when the local biometric pipeline succeeded and local fraud detection did not flag anything).
- Only in the `else` branch does the Orb call `self.enroll_user(...)`, which performs the actual backend request via `signup_post::request` / `signup_poll::request`. That backend round-trip is the **authoritative** check — its own code comments explicitly document that "Backend duplicates" is one of the failure conditions it can return: [3](#0-2) 

This mirrors the airdrop bug's structure precisely: a security-relevant "already done"/"duplicate" determination that should be checked against an authoritative, server-side record (`validated[msg.sender]` in the airdrop case; the backend's duplicate-signup database in this case) is instead inferred from locally-observed, replayable state (`amount == 0` in the airdrop case; `signup_reason` derived from the orb's own local pipeline in this case). In both cases, the code path that is supposed to gate re-entry into a "completed" state skips the canonical check and trusts a value that can be reproduced identically on a subsequent attempt.

### Impact Explanation
For any signup where `user_centric_signup == true`, the orb never calls the backend's duplicate-signup / uniqueness enforcement (`signup_post`/`signup_poll`) at all — it only decides success/failure from data computed entirely on-device. Because the on-device signup_reason can be `Normal` on more than one occasion for the same identity (e.g., repeated presentations of the same iris/face, or repeated attempts with the same or replayed QR-code/session data), this bypasses the backend's central duplicate/fraud-of-record check that other paths rely on. This can result in a person being credited with (or misattributed to) multiple successful signups that the backend was never asked to authoritatively validate or de-duplicate, undermining the core "one signup per person" guarantee the backend enrollment call exists to enforce.

### Likelihood Explanation
The `user_centric_signup` branch is reachable by any unprivileged user whose QR-code/session data comes back from the backend with `user_centric_signup = true` (the default operational mode for such apps), and does not require any special privilege, hardware access, or operator collusion — it's purely a function of the signed QR-code/session payload and the on-device pipeline's own (locally computed) result. Whether this is exploitable end-to-end depends on whether `signup_reason::Normal` can be reproduced for the same person more than once (e.g., re-presenting the same biometric or replaying capture data), which is plausible given the pipeline's determination is entirely local and not tied to any single-use, backend-issued token.

### Recommendation
For `user_centric_signup` signups, still call the backend enrollment/duplicate-check endpoint (or an equivalent authoritative validation step) before reporting `success`, rather than deriving success solely from the locally computed `signup_reason`. At minimum, ensure the backend receives and records every completed signup attempt so that its duplicate/fraud-of-record checks cannot be bypassed by this code path.

### Proof of Concept
1. A user obtains a QR-code/session whose backend-verified `authenticated_app_data.user_centric_signup` is `true` (see [2](#0-1) ).
2. The user completes biometric capture; the local pipeline succeeds and local fraud detection does not flag anything, so `signup_reason == SignupReason::Normal`.
3. In `do_signup`, because `user_centric_signup` is true and `ignore_user_centric_signups` is false, the branch at [4](#0-3)  sets `success = true` directly — `enroll_user` (and thus `signup_post`/`signup_poll`, the only code path that can detect "Backend duplicates", per [5](#0-4) ) is never invoked.
4. The user repeats the process (e.g., in another session or with a re-presented capture) and again obtains `SignupReason::Normal` locally; success is again reported as `true` without any backend duplicate check ever executing, exactly as the airdrop's `validate()` re-entry skipped the authoritative "already validated" check.
