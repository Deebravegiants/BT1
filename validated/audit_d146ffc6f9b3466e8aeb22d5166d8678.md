### Title
RAY-denominated debt valuation can overflow `i128` and permanently freeze an entire market - (File: common/src/rates/scaling.rs)

### Summary
An oversized but admitted market can grow until `borrowed * borrow_index` no longer fits in `i128`, at which point `accrue_step` panics while converting scaled debt to its RAY-denominated value. [1](#0-0)  Because every mutating pool operation syncs the market before applying the requested mutation, the same arithmetic overflow blocks repayment, withdrawal, liquidation and subsequent index updates. [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
Positions and market totals store RAY-scaled share counts, while `scaled_to_original` reconstructs their underlying RAY value with `scaled.mul(index)`. [5](#0-4)  `Ray::mul` ultimately performs a checked multiply-divide and raises `MathOverflow` when the representable result exceeds `i128`. [6](#0-5) [7](#0-6) 

During accrual, `accrue_step` calculates both `borrowed_original` and `supplied_original` before deriving utilization and the next borrow index. [8](#0-7)  Although `update_borrow_index` caps the index itself at `MAX_BORROW_INDEX_RAY`, that cap does not ensure that `borrowed * borrow_index` remains representable. [9](#0-8) [10](#0-9)  The repository documents that valid caps and bounded indexes do not guarantee that future accrued market values fit the RAY domain. [11](#0-10) 

The in-repository stress test reaches this state through the public position flow by supplying one billion 18-decimal tokens, borrowing 98% of the supplied principal, advancing accrual, and then observing `update_indexes` fail with `MathOverflow`. [12](#0-11)  The same test proves that withdrawal and repayment subsequently fail with the same error, while the stored borrow index remains below its configured ceiling. [13](#0-12) 

### Impact Explanation
Once the market crosses the representable-value boundary, the failing multiplication occurs during the mandatory pre-operation accrual and the transaction reverts before a new index or state can be committed. [14](#0-13) [2](#0-1)  Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot force the pool to process the affected market, and recapitalization or index maintenance cannot move the market past the failing point. [15](#0-14)  This produces permanent freezing of all user funds and outstanding debt in that `(hub_id, token)` market unless the deployed code is changed externally. [16](#0-15) 

### Likelihood Explanation
The attack requires a market whose configured caps and actual token supply permit a sufficiently large position, plus enough collateral and ledger-time accrual for `borrowed * borrow_index` to exceed `i128::MAX`. [17](#0-16) [12](#0-11)  A single account can provide both the debt-market liquidity and the separate collateral needed to borrow most of that liquidity, so no privileged pool operation or victim action is required. [18](#0-17) [19](#0-18)  The required capital and accrued-value scale make this less likely than an ordinary liquidation exploit, but the resulting failure is market-wide and unrecoverable through the normal entrypoints. [11](#0-10) 

### Recommendation
Bound accrued share-value products, rather than only the indexes. Before writing a new borrow index, cap it at `min(MAX_BORROW_INDEX_RAY, i128::MAX / borrowed)` or perform the utilization and accrued-debt comparisons in widened arithmetic and clamp the index before `calculate_supplier_rewards` multiplies by it. [20](#0-19) [21](#0-20)  Apply the equivalent bound to `supplied * supply_index`, and add admission-time checks that keep configured caps below the largest principal that can safely reach the chosen index ceilings. [22](#0-21) [23](#0-22)

pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))
```

pub fn calculate_supplier_rewards(
    env: &Env,
    params: &MarketParams,
    borrowed: Ray,
    new_borrow_index: Ray,
    old_borrow_index: Ray,
) -> (Ray, Ray) {
    let old_total_debt = borrowed.mul(env, old_borrow_index);
    let new_total_debt = borrowed.mul(env, new_borrow_index);

    let accrued_interest = new_total_debt.checked_sub(env, old_total_debt);

    let protocol_fee = params.reserve_factor.apply_to_ray(env, accrued_interest);
    let supplier_rewards = accrued_interest.checked_sub(env, protocol_fee);

    (supplier_rewards, protocol_fee)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;

    while let Some(nonzero) = NonZeroU64::new(remaining) {

        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);

/// Returns the largest cap, in asset base units, whose ray-scaled form still
/// fits in `i128`.
///
/// Returns 0 when `asset_decimals > RAY_DECIMALS`, since the ray form is not
/// representable in that case. Enforced by
/// [`require_cap_within_asset_domain`], so stored caps can never overflow the
/// asset→ray rescale.
pub fn max_cap_for_decimals(asset_decimals: u32) -> i128 {
    let Some(exp) = RAY_DECIMALS.checked_sub(asset_decimals) else {
        return 0;
    };
    let upscale = 10i128
        .checked_pow(exp)
        .expect("10^(RAY_DECIMALS - asset_decimals) fits i128 for asset_decimals <= RAY_DECIMALS");
    i128::MAX / upscale
}

/// Panics with `CollateralError::AssetDecimalsTooHigh` if `asset_decimals`
/// exceeds `RAY_DECIMALS`, or with `CollateralError::InvalidBorrowParams` if
/// `cap` exceeds the value returned by `max_cap_for_decimals`.
pub fn require_cap_within_asset_domain(env: &Env, cap: i128, asset_decimals: u32) {
    if RAY_DECIMALS.checked_sub(asset_decimals).is_none() {
        panic_with_error!(env, CollateralError::AssetDecimalsTooHigh);
    }
    assert_with_error!(
        env,
        cap <= max_cap_for_decimals(asset_decimals),
        CollateralError::InvalidBorrowParams
    );
```
