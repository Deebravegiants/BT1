This confirms the vulnerability. The `WebhookMetadata.shop` field (line 8 of `webhook_handler.rb`) is a `String` const that host applications rely on to identify which tenant/shop the webhook payload belongs to, but it is sourced directly from the `x-shopify-shop-domain` HTTP header via `Request#shop` [1](#0-0)  — a header that is never included in the HMAC-signed material.

### Title
Webhook shop-domain identity spoofing via HMAC scope gap — `WebhookMetadata.shop` is trusted but unauthenticated (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `HmacValidator.validate` verifies the HMAC solely over that body. The `shop`, `topic`, `webhook_id`, and `api_version` values — all taken straight from HTTP headers — are never covered by the signature, yet `Registry.process` forwards `request.shop` unchanged into `WebhookMetadata` and hands it to the host application's handler as the authenticated tenant identifier.

### Finding Description
`Request#to_signable_string` is defined as:
```ruby
def to_signable_string
  @raw_body
end
``` [2](#0-1) 

`HmacValidator.validate` computes the signature purely over that string:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [3](#0-2) 

`Registry.process` only checks that this body HMAC is valid, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) as authenticated identity fields when building `WebhookMetadata`:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

`request.shop` itself is a pure pass-through of the `x-shopify-shop-domain` (or `shopify-shop-domain`) header:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [1](#0-0) 

Because the header is not part of the signed material, the equality the library implicitly promises — "the `shop` field returned by `Request#shop`/`WebhookMetadata.shop` equals the tenant that produced the HMAC-signed body" — does not actually hold. Any request whose body carries a valid HMAC for the configured `api_secret_key` will be accepted regardless of what shop-domain header accompanies it. An attacker who legitimately installs the app on their own store (an unprivileged action requiring no special access) receives correctly-HMAC-signed webhook deliveries for their own shop. They can then replay that exact body (unmodified, so the signature remains valid) directly at the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. `Registry.process` will validate successfully and hand the host application data via `WebhookMetadata` claiming it originated from the victim shop, while the payload content is actually attacker-controlled.

### Impact Explanation
Host applications built on this gem (per the documented `WebhookHandler#handle(data:)` contract) key their per-tenant business logic and data storage off `WebhookMetadata#shop` — this is the field's entire purpose as identity binding for multi-tenant Shopify apps. Since the shop header is outside HMAC coverage, an attacker can make the app believe attacker-controlled data belongs to a shop the attacker doesn't operate, causing cross-tenant data injection into the victim's stored orders/customers/products/etc., depending on how the host app persists webhook payloads. This satisfies the "Critical - cross-tenant access" impact category, since it lets one merchant/tenant inject or corrupt another tenant's data via a boundary this gem is supposed to enforce.

### Likelihood Explanation
Likelihood is high for any app author who follows the documented processing flow (`Registry.process`) verbatim, since the gem provides no additional protection and nothing in the public API surface enforces that the header-derived `shop` is bound to the signed body. The only prerequisite is that the attacker can install the target app on a shop they control (standard, unprivileged Shopify app installation) to obtain a validly-signed webhook body, and can issue an arbitrary HTTP POST to the app's public webhook endpoint with custom headers — both trivially available to an internet-connected attacker.

### Recommendation
Include the shop domain (and ideally topic/webhook id/api version) in the signable material that is HMAC-verified, or otherwise cryptographically bind the header-derived identity fields to the signed body before constructing `WebhookMetadata`. At minimum, `to_signable_string` should incorporate the `shop-domain` header value so that `HmacValidator.validate` fails if the header is altered relative to what Shopify actually signed.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) with a controlled order payload.
2. Shopify delivers a POST to the app's webhook endpoint with headers including `x-shopify-hmac-sha256: <valid-hmac-of-body>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`, and body `raw_body`.
3. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value (both untouched, so the signature remains valid), and replays them directly to the app's public webhook endpoint but with `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `@raw_body` against the secret — this passes because the body/HMAC pair is unmodified.
5. `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)` is passed to the host app's handler, which processes/stores attacker-controlled data as if it belongs to `victim-shop.myshopify.com`.
