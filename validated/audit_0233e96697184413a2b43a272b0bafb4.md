## Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by verifying an HMAC over the raw request body, but the tenant-identifying `shop` field (and topic/webhook-id/api-version) that downstream app code relies on to attribute the webhook to a merchant is taken from an HTTP header that is never included in the signed content.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signable string: [2](#0-1) 

`HmacValidator.validate` only compares the HMAC over `verifiable_query.to_signable_string` (i.e. the body) against the secret-derived signature: [3](#0-2) 

`Registry.process` treats the request as authentic once this body-only HMAC check passes, and then forwards the *unauthenticated* `request.shop` header value straight into the handler's data payload, which is the value host applications use to identify which merchant/tenant the event belongs to: [4](#0-3) 

The equality the gem should guarantee is: `shop attributed to the webhook == shop that the HMAC-authenticated payload actually originated from`. Because `shop` is read from an unsigned header while only the body is signed, an attacker who legitimately receives one valid `(body, hmac)` pair for their own store (e.g. by installing the app on an attacker-controlled shop and triggering a webhook) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `HmacValidator.validate` still returns `true` (the body and HMAC are unchanged and correctly signed), but `WebhookMetadata.shop` now reports whatever shop domain the attacker chose.

### Impact Explanation
Any downstream logic in the host application that uses `WebhookMetadata#shop` to scope data (e.g., "look up shop X's session/access token and apply this order/webhook payload to shop X's records") can be tricked into applying attacker-controlled webhook content under a victim shop's identity — a cross-tenant data-integrity/confusion issue that the gem's own `process` method presents as fully "verified" (`Errors::InvalidWebhookError` is only raised when the body HMAC fails). This crosses the tenant boundary the HMAC check is supposed to enforce.

### Likelihood Explanation
Requires only that the attacker be able to install the target app (or otherwise trigger any legitimate webhook delivery) on a shop they control, in order to harvest one valid `(raw_body, hmac)` pair, and then send a crafted HTTP POST to the app's public webhook endpoint with a modified `shop` header — no access token, `api_secret_key`, or privileged account needed.

### Recommendation
Bind the `shop` (and other identity-relevant headers such as `topic`/`webhook-id`/`api-version`) into the signed content that `HmacValidator` verifies, e.g., by including these header values in `to_signable_string`, or by having Shopify's servers sign the headers as well and verifying that signature, so `request.shop` cannot be altered independently of the HMAC-authenticated body.

### Proof of Concept
1. Attacker installs the app on their own store `attacker-shop.myshopify.com` and triggers any webhook (e.g. `orders/create`) with a body they fully control.
2. Attacker captures the resulting `raw_body` and the valid `x-shopify-hmac-sha256` header Shopify computed for it.
3. Attacker sends a POST to the app's webhook endpoint with the identical `raw_body`/`hmac` but with `x-shopify-shop-domain` header set to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body HMAC and succeeds: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload originated from and was signed for the attacker's own shop, letting the attacker inject/attribute arbitrary webhook content to a victim tenant.
