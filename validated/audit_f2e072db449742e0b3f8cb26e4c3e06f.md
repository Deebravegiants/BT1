### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC over the raw request body, then blindly trusts the `shop` value taken from the unauthenticated `X-Shopify-Shop-Domain` HTTP header when dispatching the webhook to the app's handler. The HMAC never covers the `shop` header, so an attacker can present a body/HMAC pair that is valid (because it was legitimately signed by Shopify for the attacker's own shop) together with a forged `shop-domain` header naming a different (victim) shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed material at all: [2](#0-1) 

`Registry.process` validates the request purely against `Utils::HmacValidator.validate(request)` (i.e., the raw body signature), and then immediately constructs `WebhookMetadata` using `request.shop` — the unauthenticated header — as the tenant identity passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature only from `verifiable_query.to_signable_string`, so any header outside of that string, including `shop`, is not authenticated: [4](#0-3) 

This breaks the identity binding: `shop-domain header == cryptographically authenticated shop`. The equality that should hold is `shop used by handler == shop bound by HMAC`, but in this gem `shop used by handler (header) != any value covered by HMAC (body only)`.

**Attack path:** Any internet user who has (or creates) their own shop and installs the merchant's app receives legitimately Shopify-signed webhooks for their own shop (valid `hmac-sha256` over the real body). They can replay that exact body/HMAC pair to the app's webhook endpoint while overriding the `X-Shopify-Shop-Domain` (or `X-Shopify-Shop-Domain`/`Shopify-Shop-Domain`) header to name an arbitrary victim shop domain. `Utils::HmacValidator.validate(request)` still succeeds because it only checks the body signature, and `Registry.process` forwards `WebhookMetadata.new(shop: request.shop, ...)` with the attacker-chosen shop to the app's `WebhookHandler#handle`.

### Impact Explanation
This is a cross-tenant identity-confusion vector: the app-level handler (which relies on this gem's webhook dispatch to establish which merchant/tenant a webhook belongs to) will process attacker-controlled payload data attributed to a shop the attacker does not own. Depending on the webhook topic the app subscribes to, this can be used to: attribute GDPR/compliance topics (`customers/data_request`, `customers/redact`, `shop/redact`) to the wrong shop, trigger app-side session/data mutations keyed by `shop` for a victim tenant, or otherwise pollute per-tenant state — all without possessing any credential belonging to the victim shop. This matches the "cross-tenant access" class of impact, since the tenant/shop boundary that the gem is trusted to enforce during webhook processing is not actually authenticated.

### Likelihood Explanation
Any unprivileged internet user can trigger this if they can install the merchant's app on a shop they control (many apps allow public installation) or otherwise obtain one legitimately-signed webhook body/HMAC pair for a topic the target app subscribes to, then replay it with a forged shop header. No secrets, tokens, or elevated access are required — only the ability to receive one authentic webhook for an attacker-owned shop and resend it with a modified header to the app's public webhook endpoint.

### Recommendation
Include the shop domain (and ideally topic/api-version) inside the HMAC-signed material, or otherwise cryptographically bind the header-derived `shop` to the verified body — e.g., only trust the `shop` header after confirming it is included in the signable payload, or require the caller to independently authenticate the header via a per-shop webhook signing secret. At minimum, `Request#to_signable_string` should not omit fields that the caller (`Registry.process` / `WebhookHandler`) subsequently treats as authenticated tenant identity.

### Proof of Concept
1. Attacker creates/owns `attacker.myshopify.com` and installs the victim's app; app registers a webhook (e.g., `customers/data_request`) pointing at its public endpoint.
2. Shopify sends a legitimately HMAC-signed webhook to the app for `attacker.myshopify.com`; attacker intercepts the raw body and the `X-Shopify-Hmac-Sha256` header (both under their own control since it's their own shop's webhook).
3. Attacker replays the exact same `raw_body` and `hmac-sha256` header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds successfully (all required headers present).
5. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`raw_body`) only — it matches, since the body/HMAC pair is a legitimate Shopify signature.
6. `Registry.process` calls the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: attacker_controlled_body, ...)`, i.e., the app now believes attacker-controlled data came from the victim shop. [3](#0-2) [5](#0-4)
