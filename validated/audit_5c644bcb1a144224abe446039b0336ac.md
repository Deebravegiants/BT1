### Title
Webhook `shop-domain` header is not covered by HMAC validation, allowing cross-tenant shop impersonation - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `HmacValidator.validate_signature` computes/verifies the HMAC solely over that body with the app's single `api_secret_key`. The `shop-domain` header (`request.shop`) is never part of the signed material, yet `Registry.process` trusts it unconditionally and forwards it as `WebhookMetadata#shop` to the app's handler.

### Finding Description
The identity binding that should hold is: `shop authenticated by HMAC == shop delivered to the handler`. In this gem's webhook pipeline that equality is never enforced, because:
- `Request#hmac` is computed from the `x-shopify-hmac-sha256`/`shopify-hmac-sha256` header, and `HmacValidator.validate` checks that this equals `HMAC(api_secret_key, raw_body)` [6](#0-5) .
- `to_signable_string` is defined as just `@raw_body` [2](#0-1) , so the `shop-domain` header is never fed into the signature computation.
- `api_secret_key` is a single, app-wide secret (`Context.api_secret_key`), not a per-shop secret — the same key is used to validate every shop's webhooks for the app [7](#0-6) .
- `Registry.process` only checks `Utils::HmacValidator.validate(request)` and then unconditionally builds `WebhookMetadata` using `request.shop` taken straight from the unauthenticated header [4](#0-3) .

Because the HMAC secret is shared across every shop that has installed the app, any body+HMAC pair that is valid for shop A's webhook is *also* a cryptographically valid pair when replayed with `shop-domain` set to shop B — the signature says nothing about which shop the event pertains to. A user who runs their own store with the app installed (an "unprivileged" actor relative to other tenants) can:
1. Trigger a webhook delivery to their own endpoint for a topic where they control body content that they want the app to associate with another shop (e.g., a webhook whose JSON body is attacker-influenced, or simply capture any legitimately-delivered body/HMAC pair from their own shop).
2. Resend that exact `raw_body` and `hmac-sha256` value to the app's webhook endpoint, but with the `shop-domain` header swapped to the victim shop's domain.
3. `HmacValidator.validate` still succeeds because the signature only ever depended on `raw_body` and the shared `api_secret_key`, never on `shop-domain`.
4. `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker_controlled_body, ...)`, so the app is misled into treating attacker-supplied data as an authenticated event for the victim's tenant.

### Impact Explanation
Documented usage patterns show handlers keying persistence/business logic directly off `data.shop` (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [8](#0-7) , and `WebhookMetadata#shop` is a plain, unauthenticated string field consumed as ground truth [5](#0-4) . Since the gem provides no per-shop binding of the HMAC, any app relying on `data.shop` for tenant attribution (which is the documented, intended use) is exposed to cross-tenant data confusion/injection — satisfying the "cross-tenant access" Critical impact bucket.

### Likelihood Explanation
Exploitation only requires an attacker to install the target app on their own (attacker-controlled) shop — a normal, unprivileged onboarding step requiring no leaked secrets, no `api_secret_key`, and no access token theft. From there they can generate arbitrarily many valid `(body, hmac)` pairs for their own shop and replay them with a forged `shop-domain` header, which is trivial request tampering (no TLS interception needed since it's their own outbound webhook receiver forwarding to the app, or a direct POST to the app's public webhook endpoint).

### Recommendation
Bind the shop identity into the verified material: include `shop-domain` (and ideally `topic`) as part of the HMAC-signed input, or independently verify that `request.shop` corresponds to a shop with a currently active, installed session/access token for this app before dispatching to the handler. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant attribution without additional verification.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com" and
# captures a legitimately-signed webhook delivery:
raw_body = '{"id":1,"note":"hello"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Replay it, claiming to be a different (victim) shop:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),   # still valid! secret is app-wide
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # unauthenticated
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) returns true (only checks raw_body+secret)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: ..., ...))
```
