### Title
Emporium `runAction` never accounts for ETH moved via `EmporiumOperation.value` when the wallet path is used or when ETH is excluded from `circomData.erc20TokenAddresses` - (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` enforces balance conservation only by diffing `getBalancesForArray(circomData.erc20TokenAddresses)` before/after executing `stack.ops`, i.e. only for the tokens the attacker chose to list. `EmporiumOperation.value` (forwarded as real ETH both through `IHinkalWallet.callHinkalWallet` and directly via `op.endpoint.call{value: op.value}`) can move ETH out of the Emporium contract or out of the `HinkalWallet` without ever being reflected in that balance snapshot, breaking the invariant that "tokens leaving an action == `-deltaAmountChanges`".

### Finding Description
Equality that should hold: for every token `i` acted on, `balancesAfter[i] - balancesBefore[i] == deltaAmountChanges[i] adjustment` as enforced at [1](#0-0) .

This check is computed purely from `getBalancesForArray(circomData.erc20TokenAddresses)`, which for the native-token entry reads `address(this).balance` of **the Emporium contract itself**: [2](#0-1) 

Two independent bypasses exist:

1. **Stateless path with ETH omitted from the token array.** `circomData.erc20TokenAddresses` and the rest of `CircomData` are fully attacker-controlled (they build their own proof). If the attacker's `ops` array performs `op.endpoint.call{value: op.value}(...)` (Case 2) but the attacker simply does not include `address(0)` in `circomData.erc20TokenAddresses`, then `getBalancesForArray` never samples ETH before/after, so the outflow of Emporium's own ETH balance is invisible to the `BalanceChangeShouldBePositive` guard entirely: [3](#0-2) 

2. **Stateful (wallet) path.** When `op.invokeWallet` is true, `IHinkalWallet(stack.signerAddress).callHinkalWallet(op.endpoint, op.callData, op.value)` is called with **no `{value: ...}`** from Emporium, so Emporium forwards 0 ETH to the wallet: [4](#0-3) 
Inside `HinkalWallet.callHinkalWallet`, the wallet then spends `op.value` **from its own existing ETH balance** to `op.endpoint`: [5](#0-4) 
`getBalancesForArray` in `runAction` only ever samples `address(this)` where `this == EmporiumUpgradeable`, never the wallet's balance — so this ETH transfer is structurally outside the balance-conservation check regardless of whether `address(0)` is listed in `erc20TokenAddresses`.

Root cause: the balance-conservation guard is scoped to a caller-supplied token list and to a single contract's own balance, while `op.value` lets calldata reach into a *different* balance pool (the wallet's, or Emporium's un-tracked-token balance) that the circuit's `amountChanges`/`deltaAmountChanges` accounting never constrains.

### Impact Explanation
Any ETH sitting in the `HinkalWallet` (its `receive()` is open to anyone: `EthReceivedOnWallet` event confirms unsolicited deposits are accepted) or stray/residual ETH held by `EmporiumUpgradeable` (e.g. from prior rounding, partially-completed actions, or another user's un-swept balance) can be redirected to an attacker-controlled `op.endpoint` while the proof-verified `deltaAmountChanges` for ETH reports zero movement. This is a direct value leak outside the equality the whole balance-check mechanism exists to enforce, matching the Critical category (theft of pooled funds not reflected in balance accounting). Repeatable every time residual/stray ETH balance exists in either contract.

### Likelihood Explanation
The attacker only needs: (a) a valid proof for their own UTXOs (any innocuous action works, since the ops array bypasses accounting independent of the actual swap logic), (b) to control `circomData.erc20TokenAddresses` (trivial — it's their own calldata), and (c) either be the `signerAddress`/own wallet with a pre-existing ETH balance in it from third-party deposits, or a scenario where Emporium itself holds stray ETH. The primary uncertainty is how much attacker-inaccessible ETH realistically accumulates in `HinkalWallet`/`EmporiumUpgradeable` in production (this depends on the wallet-deployment/factory pattern and typical dust amounts), which I could not fully verify — the wallet factory / per-user wallet deployment code was not found in the indexed portion of the repo, so I cannot confirm whether `HinkalWallet` instances are strictly per-user or how isolated other users' stray ETH truly is.

### Recommendation
- Include the native token unconditionally in the balance snapshot taken in `runAction` (don't rely on attacker-supplied `erc20TokenAddresses` to opt in ETH accounting).
- When `op.invokeWallet` is used, forward and track ETH through Emporium (e.g., require `msg.value`/tracked ETH balance changes on the `signerAddress` wallet too, snapshotting `stack.signerAddress.balance` before/after `runAction`), not just `address(this)`.
- Alternatively, disallow `op.value > 0` entirely for the wallet-invoking path unless the wallet's own balance change is included in the conservation check.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, `HinkalWallet(emporium)`, an attacker-controlled `endpoint` contract with a `receive()`.
2. Fund `HinkalWallet` with residual ETH via a plain `.call{value: X}("")` from an unrelated address (simulating stray/other-user ETH), and/or send stray ETH directly to `EmporiumUpgradeable` (or arrange it via a normal deposit flow that leaves residue).
3. Build `CircomData` where `erc20TokenAddresses` excludes `address(0)` (or includes an unrelated ERC20) and `EmporiumStack.ops` contains one `EmporiumOperation{ endpoint: attackerEndpoint, invokeWallet: true, value: X, callData: "" }` with `signerAddress = attacker's wallet` validly signed by the attacker.
4. Call `Hinkal.transact(circomData)` (through the normal external-action flow reaching `EmporiumUpgradeable.runAction`).
5. Assert: `attackerEndpoint.balance` increased by `X`; `deltaAmountChanges` for the ETH index (if present) stayed `0`; no revert of `BalanceChangeShouldBePositive` occurred — demonstrating `balancesAfter[ETH] - balancesBefore[ETH] (Emporium) != actual ETH that left the system (wallet balance -X)`, i.e. the equality "tokens leaving == `-deltaAmountChanges`" is violated for ETH moved through `op.value`.

        address _erc20TokenAddress
    ) internal view returns (uint256) {
        if (_erc20TokenAddress == address(0)) {
            return address(this).balance;
        } else {
            IERC20 outToken = IERC20(_erc20TokenAddress);
            return outToken.balanceOf(address(this));
        }

    function getBalancesForArrayMemory(
