### Title
`ValidateResourceQuotaStatusUpdate` does not restrict `Status.Hard` changes, letting status-only RBAC grantees raise the enforced quota ceiling - ([File: pkg/apis/core/validation/validation.go])

### Summary
The status-subresource strategy for `ResourceQuota` only protects `Spec` from being modified via `/status`, but `ValidateResourceQuotaStatusUpdate` validates `Status.Hard` and `Status.Used` identically, with no restriction preventing a status-only actor from inflating `Status.Hard`. Because the `ResourceQuota` admission plugin enforces limits against `resourceQuota.Status.Hard` (not `Spec.Hard`), and the resource-quota controller only reconciles `Status.Hard` back to `Spec.Hard` on a slow resync cycle, an actor holding only `resourcequotas/status update` can persist an inflated `Status.Hard` and get admission control to honor it until the next controller resync.

### Finding Description
`resourcequotaStatusStrategy.PrepareForUpdate` only resets `Spec` from `old`, leaving `Status` (including `Hard`) fully attacker-controlled: [1](#0-0) . Its `ValidateUpdate` simply calls `validation.ValidateResourceQuotaStatusUpdate(obj, old)` [2](#0-1) , which the question states validates `Hard` and `Used` maps identically without limiting which fields a status-only caller may change.

The `GetResetFields` for the status strategy only marks `spec` as reset, confirming `status.hard` is writable through the `/status` subresource by design: [3](#0-2) . `StatusREST.Update` forwards directly to the generic store without additional masking: [4](#0-3) .

Critically, the actual enforcement path — the `ResourceQuota` admission plugin's `CheckRequest` — computes `hardResources` and does its `LessThanOrEqual` comparison against `resourceQuota.Status.Hard`, not `Spec.Hard`: [5](#0-4) . So `Status.Hard` is the value that actually gates admission of new pods/objects, not merely a cosmetic mirror of `Spec.Hard`.

The resource-quota controller only overwrites `Status.Hard` from `Spec.Hard` when it detects a mismatch (`statusLimitsDirty`) during its periodic sync, which defaults to a 5-minute full resync interval, as confirmed by the e2e conformance test and its comment referencing https://issues.k8s.io/121911: [6](#0-5) , [7](#0-6) . The e2e test itself demonstrates that patching `status.hard` via the `/status` subresource is accepted and persisted, and that the reported/reconciled value stays inflated until the controller resync fires: [8](#0-7) , [9](#0-8) .

Exploit flow: an actor holding only `update` on `resourcequotas/status` in a namespace calls `PATCH .../resourcequotas/<name>/status` with `{"status":{"hard":{"cpu":"1000"}}}`. `ValidateResourceQuotaStatusUpdate` accepts it because it treats `Hard` the same as `Used`. The generic store persists it. On the next pod/object creation, the `ResourceQuota` admission plugin reads the informer-cached quota object and compares requested usage against the inflated `Status.Hard`, permitting resource consumption beyond the namespace's actual configured `Spec.Hard` ceiling — until the controller's next full resync (up to ~5 minutes, longer if the controller is degraded/rate-limited) restores `Status.Hard` to `Spec.Hard`.

### Impact Explanation
This is a scoped privilege escalation / control bypass: an actor without permission to modify `ResourceQuota.Spec` can nonetheless raise the effectively enforced resource ceiling for their namespace via the status subresource, bypassing the quota constraints an administrator configured. This maps to Kubernetes bounty's "privilege escalation via built-in resource" / "policy bypass" class — it does not grant cluster-wide compromise, but it does let a namespace-scoped, minimally-privileged actor circumvent a security/cost control (`ResourceQuota`) that other users and admission logic rely on to be trustworthy.

### Likelihood Explanation
Preconditions: the attacker needs an RBAC grant of `update`/`patch` on `resourcequotas/status` (no `resourcequotas` write, no `spec` write needed). This is not part of default bootstrap ClusterRoles (`edit`/`admin` grant `resourcequotas` broadly but status-subresource-only grants are a plausible custom Role an operator might create for a "reporting" or "reconciler" service account, believing status updates are harmless telemetry). Given such a Role exists, exploitation is trivial and repeatable: a single PATCH request, with impact persisting until the next controller resync cycle.

### Recommendation
Restrict `ValidateResourceQuotaStatusUpdate` (or `resourcequotaStatusStrategy.PrepareForUpdate`) to preserve `Status.Hard` from the previous object, only allowing `Status.Used` (and any read-only observed fields) to change via the `/status` subresource — mirroring the `Spec` field protection already applied. Additionally, consider having the admission plugin enforce against `Spec.Hard` directly (or a value it trusts is derived only from `Spec.Hard`) rather than the mutable `Status.Hard`.

### Proof of Concept
Integration test plan:
1. Start an API server with RBAC enabled; create a Role granting only `update`/`patch`/`get` on `resourcequotas/status` in namespace `ns`, bound to a test ServiceAccount `sa`.
2. As cluster-admin, create a `ResourceQuota` in `ns` with `Spec.Hard{cpu: "1"}`; wait for controller to set `Status.Hard{cpu:"1"}`.
3. Impersonating `sa`, `PATCH` `/api/v1/namespaces/ns/resourcequotas/<name>/status` with `{"status":{"hard":{"cpu":"1000"}}}`. Assert the request succeeds (200) and `GET` shows `Status.Hard.cpu == "1000"`.
4. Immediately (before controller resync), as `sa` (or any namespace user), create pods totaling `cpu` requests > 1 but < 1000. Assert admission allows it (violating the admin-configured `Spec.Hard` of 1 CPU), proving the elevated `Status.Hard` was honored by the `ResourceQuota` admission plugin.
5. Expected fix assertion: after the fix, step 3's PATCH should either be rejected or should have `Status.Hard` silently reset/ignored to match `Spec.Hard`, and step 4 should fail admission once cumulative cpu requests exceed `Spec.Hard` (1 CPU).

// syncResourceQuota runs a complete sync of resource quota status across all known kinds
func (rq *Controller) syncResourceQuota(ctx context.Context, resourceQuota *v1.ResourceQuota) (err error) {
	// quota is dirty if any part of spec hard limits differs from the status hard limits
	statusLimitsDirty := !apiequality.Semantic.DeepEqual(resourceQuota.Spec.Hard, resourceQuota.Status.Hard)

	// dirty tracks if the usage status differs from the previous sync,
	// if so, we send a new usage with latest status
	// if this is our first sync, it will be dirty by default, since we need track usage
	dirty := statusLimitsDirty || resourceQuota.Status.Hard == nil || resourceQuota.Status.Used == nil

	used := v1.ResourceList{}
	if resourceQuota.Status.Used != nil {
		used = quota.Add(v1.ResourceList{}, resourceQuota.Status.Used)
	}
	hardLimits := quota.Add(v1.ResourceList{}, resourceQuota.Spec.Hard)

	var errs []error

	newUsage, err := quota.CalculateUsage(resourceQuota.Namespace, resourceQuota.Spec.Scopes, hardLimits, rq.registry, resourceQuota.Spec.ScopeSelector)
	if err != nil {
		// if err is non-nil, remember it to return, but continue updating status with any resources in newUsage
		errs = append(errs, err)
	}
	for key, value := range newUsage {
		used[key] = value
	}

	// ensure set of used values match those that have hard constraints
	hardResources := quota.ResourceNames(hardLimits)
	used = quota.Mask(used, hardResources)

	// Create a usage object that is based on the quota resource version that will handle updates
	// by default, we preserve the past usage observation, and set hard to the current spec
	usage := resourceQuota.DeepCopy()
	usage.Status = v1.ResourceQuotaStatus{
		Hard: hardLimits,
		Used: used,
	}

	dirty = dirty || !quota.Equals(usage.Status.Used, resourceQuota.Status.Used)

	// there was a change observed by this controller that requires we update quota
	if dirty {
		_, err = rq.rqClient.ResourceQuotas(usage.Namespace).UpdateStatus(ctx, usage, metav1.UpdateOptions{})
		if err != nil {
			errs = append(errs, err)
		}
	}
	return utilerrors.NewAggregate(errs)
