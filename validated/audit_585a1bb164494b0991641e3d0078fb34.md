### Title
Missing Arbitrum Sequencer Uptime check in SimplexPaymaster's Chainlink price feeds allows mispriced gas prefunds during sequencer downtime/recovery - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster._getOraclePrice` reads `AggregatorV3Interface.latestRoundData()` for both the native/USD and token/USD feeds and only checks `answer <= 0` and `block.timestamp - updatedAt <= maxOracleAge` [1](#0-0) . It never checks Arbitrum's L2 Sequencer Uptime Feed, unlike the recommended Chainlink pattern for optimistic-rollup deployments cited in the report.

### Finding Description
`SimplexPaymaster` is deployed on Arbitrum mainnet as one of its supported chains, per the release-order decision doc and deployment configs listing Arbitrum alongside Ethereum, Base, Polygon and BSC [2](#0-1) , and `sdk/packages/simplex/filler-config-example.toml` configures `42161` (Arbitrum) rebalancing balances for the paymaster's supported tokens [3](#0-2) .

`_tokenPrice` and all downstream pricing (`getTokenPrice`, `estimateTokenCost`, `_fetchDetails`, `swapAndDeposit`) rely on `_getOraclePrice`, which only guards against a non-positive answer or staleness beyond `maxOracleAge`, never consulting the Arbitrum L2 Sequencer Uptime Feed [4](#0-3) . When the Arbitrum sequencer goes down and later resumes, Chainlink feeds on L2 can report a `updatedAt` timestamp that looks fresh (post-recovery) while the underlying price is stale/unreliable relative to the true off-chain market, because the feed itself was frozen during the outage and only catches up after the sequencer resumes — exactly the scenario Chainlink's L2 sequencer-feed guidance is meant to prevent. This code path is reachable by any unprivileged party: any account can submit an ERC-4337 `UserOperation` naming this paymaster with mode `0x00`/`0x02` paymasterData, driving `_fetchDetails`/`_prefund`/`_validatePaymasterUserOp` which all price the gas-for-token conversion off this unguarded oracle read [5](#0-4) [6](#0-5) .

### Impact Explanation
A mispriced `tokenPrice` directly changes how much stablecoin is pulled from a solver's account (via `permit`/Permit2) to cover native gas costs in `_prefund`, and how much native the treasury-only `swapAndDeposit` router swap expects back [7](#0-6) . If the sequencer-stale price understates the native/USD rate or overstates the token/USD rate at the moment of resumption, gas prefunds collected from solvers can fall short of actual EntryPoint gas costs, draining the paymaster's EntryPoint deposit (funded by governance/treasury) over repeated operations — a concrete freezing/loss-of-funds condition for the paymaster's stake and deposit, which per the codebase's own note is otherwise "permanently locked" and unrecoverable except through prefunded gas usage [8](#0-7) . This qualifies as Medium severity: concrete economic loss to the paymaster's funds is possible without any privileged action, purely by an attacker/solver timing operations around an Arbitrum sequencer outage-and-recovery window.

### Likelihood Explanation
Arbitrum sequencer outages, while infrequent, are a documented and recurring event; any solver or attacker monitoring L2 sequencer status can time-submit UserOperations exactly in the recovery window when Chainlink feeds resume reporting but before they've caught back up to true market price, making this readily exploitable by an unprivileged actor with no special access.

### Recommendation
Add an Arbitrum Sequencer Uptime Feed check to `_getOraclePrice` (or a shared guard called before it), reverting with a dedicated error (e.g. `SequencerDown`) when the uptime feed reports the sequencer down, or has not been up for a governance-configured grace period after recovery, mirroring Chainlink's documented `https://docs.chain.link/data-feeds/l2-sequencer-feeds` pattern, applied to every chain in `SimplexPaymaster`'s deployment set that runs an optimistic/Arbitrum-style L2 sequencer.

### Proof of Concept
1. Deploy/observe `SimplexPaymaster` on Arbitrum mainnet with `nativeOracle` and a registered token oracle, per `DeploySimplexPaymaster.s.sol` [9](#0-8) .
2. Simulate/await an Arbitrum sequencer outage window; Chainlink price feeds on Arbitrum freeze during the outage.
3. As soon as the sequencer resumes and the feed posts its first fresh round (satisfying `updatedAt` staleness bound but reflecting off-market/stale pricing), submit a `UserOperation` with paymasterData mode `0x00`/`0x02` naming a favorable-priced token.
4. `_fetchDetails`→`_tokenPrice`→`_getOraclePrice` returns the stale-but-"fresh" price without any sequencer-liveness check [4](#0-3) , causing an under-collection of the stablecoin prefund relative to actual native gas cost, draining paymaster EntryPoint funds over repeated operations.

    function _tokenPrice(TokenConfig memory cfg) internal view returns (uint256) {
        uint256 nativeUsd = _getOraclePrice(nativeOracle, nativeOracleDecimals);
        uint256 tokenUsd = _getOraclePrice(cfg.tokenOracle, cfg.tokenOracleDecimals);

        return (nativeUsd * (10 ** cfg.tokenDecimals) * (10_000 + markupBps)) / (tokenUsd * 10_000);
    }

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
