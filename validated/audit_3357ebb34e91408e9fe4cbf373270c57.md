### Title
Webhook HMAC signs only `@raw_body`, leaving `x-shopify-topic` and `x-shopify-shop-domain` headers unauthenticated and used for tenant dispatch - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `HmacValidator.validate` only proves that the *body* bytes were signed with `api_secret_key`, never the `x-shopify-topic` or `x-shopify-shop-domain` headers [2](#0-1) . `Registry.process` nevertheless uses the unauthenticated `request.topic` to pick the handler and forwards the unauthenticated `request.shop` straight into `WebhookMetadata#shop`, which is the value host apps use to identify the tenant to act on [3](#0-2) .

### Finding Description
The invariant that should hold is: `bytes signed by compute_signature == bytes that determine which shop/handler is acted on`. Concretely: `HMAC(secret, to_signable_string) == HMAC(secret, @raw_body)` while `WebhookMetadata#shop == request.shop == headers["x-shopify-shop-domain"]` and `WebhookMetadata#topic == headers["x-shopify-topic"]`. Since `to_signable_string` never includes the headers [1](#0-0) , the header values that drive tenant identification and handler selection are outside the signed byte range and are fully attacker-controllable once an attacker can hit the app's webhook endpoint directly with arbitrary headers.

Exploit flow:
1. Attacker creates their own development shop, installs the app, and registers a webhook (any topic, e.g. a low-impact one). Shopify legitimately delivers a real request to the app with `raw_body = B` and a correctly computed `x-shopify-hmac-sha256` for `B`.
2. Attacker captures this legitimate `(B, hmac)` pair — this requires no secret, since Shopify computed the digest for them.
3. Attacker crafts a new raw HTTP POST directly to the app's public webhook receiver URL (nothing in this gem restricts webhook receivers to only accept traffic that actually originated from Shopify's infrastructure), reusing the exact same body `B` and `hmac` header, but replacing `x-shopify-shop-domain` with the victim's shop domain and/or `x-shopify-topic` with a more consequential topic that has a registered handler (e.g. `app/uninstalled`, `customers/data_request`, `shop/redact`, or any topic whose handler writes/deletes data keyed by `data.shop`).
4. `HmacValidator.validate` recomputes `HMAC(secret, B)` — identical to the original — and accepts it [4](#0-3) .
5. `Registry.process` selects the handler for the attacker-chosen `request.topic` and builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the raw, unauthenticated header values [3](#0-2) .
6. The host app's handler trusts `data.shop` as the tenant identifier (this is the gem's documented contract — `WebhookMetadata#shop` is the only "shop" signal handlers receive), and mutates/reads records for the victim shop using attacker-supplied body content, even though the byte range that was actually verified (`B`) says nothing about which shop it's for.

Existing guards do not stop this: `HmacValidator.validate` only ever checks `verifiable_query.to_signable_string`, which is scoped to `@raw_body` for `Webhooks::Request` [5](#0-4) ; there is no header canonicalization, no shop-domain/topic binding into the signature, and no IP/source validation anywhere in `Request#initialize` [6](#0-5) .

### Impact Explanation
Any topic/shop pairing that has a registered handler on the target app can be triggered for an arbitrary victim shop domain, using only a body the attacker legitimately obtained for their own shop. Depending on the app's handler logic (e.g., uninstall cleanup, GDPR redaction, order/customer sync), this is repeatable per-body/per-topic pair the attacker collects and can be aimed at any victim `myshopify.com` domain string, since `shop` is taken verbatim from the header with no verification against the merchant that actually installed the app. This is a cross-tenant data integrity/confidentiality break: one shop's (attacker's) signed payload is used to read or mutate another shop's (victim's) records purely because the tenant-selecting fields were never part of the signed byte range.

### Likelihood Explanation
The attacker needs: (a) their own development shop and app install (freely obtainable), (b) knowledge or discovery of the app's public webhook endpoint URL (typically fixed/predictable per app), and (c) the ability to send a direct HTTP POST to that endpoint reusing a captured legitimate `(body, hmac)` pair with modified headers. No secret, token, or TLS interception is required — the gem performs no origin/IP validation, and header values outside `to_signable_string` are not authenticated at all. This is low-cost and fully repeatable against any registered topic/handler and any target shop domain string.

### Recommendation
Include the header values that drive dispatch and tenant identity (`x-shopify-topic`, `x-shopify-shop-domain`, and ideally `x-shopify-webhook-id`/`x-shopify-api-version`) in the signed byte range checked by `to_signable_string`, or otherwise cryptographically bind them to the verified body (e.g., verify against Shopify's known webhook signature construction, and additionally cross-check `shop-domain` against an app-known/allow-listed shop before dispatching, rather than trusting the raw header unconditionally).

### Proof of Concept
```ruby
# test/webhooks/registry_test.rb (new test)
def test_shop_and_topic_headers_are_unauthenticated_relabel
  body = "{}"
  hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)
  encoded_hmac = Base64.encode64(hmac)

  # "Legitimate" webhook the attacker received for their own shop/topic
  attacker_headers = {
    "x-shopify-topic" => "orders/create",
    "x-shopify-hmac-sha256" => encoded_hmac,
    "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
  }
  attacker_request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: attacker_headers)

  # Replayed request: same body/hmac, relabeled topic + shop
  relabeled_headers = {
    "x-shopify-topic" => "app/uninstalled",
    "x-shopify-hmac-sha256" => encoded_hmac,
    "x-shopify-shop-domain" => "victim-shop.myshopify.com",
  }
  relabeled_request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: relabeled_headers)

  # Byte identity claim: signable string is identical for both
  assert_equal(attacker_request.to_signable_string, relabeled_request.to_signable_string)

  # Both pass HMAC validation despite different topic/shop
  assert(ShopifyAPI::Utils::HmacValidator.validate(attacker_request))
  assert(ShopifyAPI::Utils::HmacValidator.validate(relabeled_request))

  # Registry.process dispatches on unauthenticated topic/shop
  handler_data = nil
  handler = TestHelpers::FakeWebhookHandler.new(->(data) { handler_data = data })
  ShopifyAPI::Webhooks::Registry.add_registration(
    topic: "app/uninstalled", path: "path", delivery_method: :http, handler: handler,
  )

  ShopifyAPI::Webhooks::Registry.process(relabeled_request)

  assert_equal("victim-shop.myshopify.com", handler_data.shop)
  assert_equal("app/uninstalled", handler_data.topic)
end
```
This proves the same signed body validates under two divergent header sets, and that `Registry.process`/`WebhookMetadata#shop` hand the host app a `shop` value ("victim-shop.myshopify.com") that was never part of the verified byte range.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
