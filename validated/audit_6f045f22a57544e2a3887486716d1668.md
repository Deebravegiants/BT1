### Title
Webhook `shop` Header Is Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body via HMAC, while the `shop` (tenant identifier), `topic`, `api_version`, and `webhook_id` values are read from unauthenticated HTTP headers that are never included in the signed payload. `ShopifyAPI::Webhooks::Registry.process` trusts this unauthenticated `shop` value directly when dispatching webhook data to the app's handler, breaking the equality that should hold between "the tenant whose secret produced this signature" and "the tenant the payload is attributed to."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived purely from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of that signable string: [2](#0-1) 

`HmacValidator.validate` computes the HMAC over `to_signable_string` (i.e., the body only) and compares it to the `hmac` header, never touching `shop`: [3](#0-2) 

`Registry.process` validates only that HMAC, then immediately forwards `request.shop` (the unauthenticated header value) to the app's handler as the authoritative tenant identity: [4](#0-3) 

Because `shop` is acted upon (used as the tenant key passed into `WebhookMetadata` and thus into the app's per-shop business logic/data lookups) but is not covered by the HMAC, the binding `shop_that_signed_body == shop_the_app_attributes_the_data_to` is broken. An attacker who possesses one genuine `(raw_body, hmac)` pair — trivially obtainable by installing the app on their own store and receiving a real webhook for an event they trigger themselves — can replay that exact body+HMAC to the app's shared webhook endpoint while substituting the `shopify-shop-domain` header with a victim merchant's domain. `HmacValidator.validate` still passes (it only checks the body), and `Registry.process` hands the handler data tagged with the victim's shop, even though the payload actually originated from, and was signed for, the attacker's own store.

### Impact Explanation
This enables cross-tenant confusion in any multi-tenant app built on this gem: an unprivileged app user (merely installing the app on their own shop, no leaked credentials or `client_secret` needed) can cause the app to process/store attacker-supplied webhook payloads under another merchant's identity. Depending on the handler, this can lead to cross-tenant data corruption, injection of forged events (e.g., fake `orders/create`, `app/uninstalled`, or GDPR `customers_redact`/`shop_redact` triggers) attributed to a victim shop, or logic that keys off `shop` for authorization decisions being fooled. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high: no secrets are required. Any user can register as a merchant, install the vulnerable app on their own store (a normal, low-privilege action), trigger a real event to receive one legitimate `(raw_body, hmac)` pair, and then replay it with a modified `shop-domain` header directly against the app's public webhook endpoint. The gem performs no binding between the header-derived `shop` and the cryptographically verified body.

### Recommendation
Include the tenant-identifying fields (`shop`, `topic`, `webhook_id`) in the HMAC-signed payload verification, or otherwise cryptographically bind the `shop` header value to the signature before trusting it in `Registry.process`. At minimum, document that consuming applications must independently verify that `request.shop` corresponds to a shop with an active, known session/installation before acting on the webhook payload, and consider rejecting webhooks whose `shop` header does not match an app-tracked installed shop within the gem itself.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and registers a webhook (e.g., `orders/create`).
2. Attacker triggers an order creation, causing Shopify to POST a webhook to the app's endpoint with:
   - body: `raw_body`
   - headers: `shopify-hmac-sha256: <valid HMAC of raw_body>`, `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-topic: orders/create`
3. Attacker captures this exact `raw_body` and `hmac` header value.
4. Attacker crafts a new POST to the same webhook endpoint, reusing the identical `raw_body` and `hmac` header, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
5. Server-side, `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds the request object; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against `hmac` — both untouched.
6. `Registry.process` dispatches `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` with `shop == "victim-shop.myshopify.com"` to the handler, even though the payload was never produced by or for that shop. [4](#0-3)
