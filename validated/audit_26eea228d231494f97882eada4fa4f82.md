## Analysis

The reported bug class (`OuterSet.getValidators` in the external report) is about a critical field (the address determining *whose* validator set is returned) not being covered by the same authenticity check as the payload it's tied to. The direct analog in this gem is in the webhook processing path: `ShopifyAPI::Webhooks::Registry.process` verifies the HMAC only over the raw request body, but the `shop` field returned by `ShopifyAPI::Webhooks::Request#shop` — which is used downstream to attribute the webhook data to a specific tenant — is read straight from the `X-Shopify-Shop-Domain` header, which is **not** included in the HMAC-signed bytes.

### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#hmac` is verified against `to_signable_string`, which returns only `@raw_body` — the shop-domain header is excluded from the signed material. `Registry.process` calls `Utils::HmacValidator.validate(request)` (checking only the body) and then hands `request.shop` (from the unauthenticated header) directly to the app's handler as the tenant identifier, exactly as documented in `docs/usage/webhooks.md`.

### Finding Description
`Request#to_signable_string` only returns the raw body: [1](#0-0) 

`Request#shop` is derived purely from an HTTP header that is not part of that signable string: [2](#0-1) 

`HmacValidator.validate` computes/compares the signature only over `to_signable_string` (i.e., the body), never the shop header: [3](#0-2) 

`Registry.process` validates the HMAC (body-only) and then trusts `request.shop` as the tenant for the handler: [4](#0-3) 

This is the documented, intended usage pattern — the docs explicitly instruct apps to key their tenant-scoped work off `data.shop`: [5](#0-4) 

The broken identity binding is: `shop attested by the HMAC` should equal `shop attributed to the payload by the handler`, but in fact `shop (unauthenticated header)` ≠ `shop (implicitly bound by HMAC, which is none)`. Any raw body + valid HMAC pair — which an attacker can legitimately obtain for their **own** shop (e.g., by installing the app on a shop they control and capturing/replaying the genuine Shopify webhook POST, since HMAC is computed only from the api_secret_key and body, not the destination or shop) — remains valid if the attacker swaps the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header value to a victim shop's domain before resending it to the app's public webhook endpoint. The gem will accept it as valid and hand it to the handler labeled as belonging to the victim shop.

### Impact Explanation
This crosses a tenant boundary: an unprivileged attacker who merely installs the app on a shop they control can forge webhook events (including mandatory GDPR topics like `customers/redact`, `shop/redact`, `customers/data_request`) that the host application will process as belonging to an arbitrary victim shop domain, since `WebhookMetadata#shop` is populated directly from the unauthenticated header. Depending on how the host app uses `data.shop` (as documented — for job attribution, record scoping, redaction targeting, etc.), this enables cross-tenant data injection/corruption or spoofed data-subject requests against a merchant who is not the attacker, satisfying the "cross-tenant access" Critical criterion.

### Likelihood Explanation
High feasibility for anyone who can install the app on a shop they control (the standard, unprivileged path for any Shopify merchant/developer): they receive a genuine, correctly-HMAC-signed webhook body for their own shop, then simply replay it to the app's public webhook endpoint with a modified shop-domain header, no `api_secret_key` or other privileged secret needed.

### Recommendation
Bind the shop domain into the authenticity check, e.g. include the shop-domain header (and ideally webhook ID/topic) in the HMAC-signed material used by `to_signable_string`, or independently verify that the `shop` header corresponds to a shop for which this HMAC/webhook was actually registered (e.g., cross-check against the session/shop store) before trusting it as the tenant identity passed to the handler.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST: `raw_body` and header `X-Shopify-Hmac-Sha256: <valid-hmac>`.
2. Attacker sends a new POST to the app's webhook endpoint using the exact same `raw_body` and `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged header into `#shop`. [2](#0-1) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the HMAC — it passes because both are unchanged. [6](#0-5) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload actually originated from the attacker's own shop. [7](#0-6)
