## Analog Found

### Title
Missing zero-amount validation on predispatch order inputs permanently strands escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron fork of `IntentGatewayV2.placeOrder` fails to validate that `order.inputs[i].amount != 0` for orders that use the predispatch/call-dispatcher path, unlike the canonical `evm/src/apps/IntentGatewayV2.sol` implementation which enforces this check on every input amount. This mirrors the reported `TokenStaking`/`TokenGrant` class of bug: a caller-supplied "amount" field that gates how much value is escrowed/accounted for is never required to be non-zero, letting an unprivileged order-placer create escrow bookkeeping entries that do not match the actual value moved into the contract.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `placeOrder` (lines 338-469) has two escrow code paths. The non-predispatch (`else`) branch correctly guards each input: [1](#0-0) 

But the predispatch branch — used whenever `order.predispatch.call.length > 0 && order.predispatch.assets.length > 0` — never checks `order.inputs[i].amount != 0` before computing `requiredAmount`, sweeping the dispatcher's balance, and crediting escrow: [2](#0-1) 

When `order.inputs[i].amount == 0`, `requiredAmount` is `0`, so `balance < requiredAmount` never reverts. The full token balance held by the `dispatcher` (the entire output of the predispatch call — e.g., proceeds from unwrapping LP tokens or a swap) is then computed as `dust = balance - requiredAmount = balance`, emitted only via `DustCollected`, and swept into the `IntentGatewayV2` contract itself while `_orders[commitment][token] += reducedInputs[i].amount` credits only `0` to escrow: [3](#0-2) 

The corresponding upstream contract explicitly closes this gap with a hard `revert InvalidInput()` on both the predispatch-asset amounts and the input amounts: [4](#0-3) [5](#0-4) 

Additionally, the Tron `placeOrder` lacks the `nonReentrant` guard that the upstream version applies: [6](#0-5) 
compared to [7](#0-6) 

### Impact Explanation
Just as the keep-core bug let an attacker create operator entries decoupled from real stake, here an order-placer can create an order whose on-chain escrow accounting (`_orders[commitment][token]`) is `0` even though real ERC20/native value produced by the predispatch call was swept out of the dispatcher and into the gateway contract, permanently misclassified as protocol "dust." That value is not attributable to any commitment, is not refundable via `cancelOrder`, and is not fillable via `fillOrder` (since the escrowed requirement is `0`) — constituting a permanent freezing of funds for the order placer. Because `placeOrder` is reachable by any unprivileged intent placer with a single transaction, this satisfies the "unauthorized app action / permanent freezing of funds" bar.

### Likelihood Explanation
High: any user submitting an order with a predispatch call (a documented, first-class feature — e.g., unwrapping LP tokens before escrow) can trivially set one `order.inputs[i].amount` to `0` while leaving `order.predispatch` populated. No special privileges, front-running, or race conditions are required — a single crafted `placeOrder` call reliably triggers the mis-accounting.

### Recommendation
Add the same guard the canonical `evm/src/apps/IntentGatewayV2.sol` uses: `if (order.inputs[i].amount == 0) revert InvalidInput();` inside the predispatch-branch loop that computes `requiredAmount`/`dust` (mirroring line 264 of the upstream contract), and add the `nonReentrant` modifier to `placeOrder` in the Tron contract to match upstream hardening.

### Proof of Concept
1. Attacker (any user) builds an `Order` with:
   - `order.predispatch.call` = calldata that unwraps/produces at least one ERC20 the dispatcher will hold (e.g., swap or LP-unwrap).
   - `order.predispatch.assets` = the input tokens required for that call.
   - `order.inputs[k].amount = 0` for the token produced by the predispatch call, with `order.inputs[k].token` set to that token's address.
2. Call `placeOrder(order, graffiti)` on the Tron `IntentGatewayV2`.
3. Execution reaches the predispatch branch; `requiredAmount = 0` for input `k`; `balance` (full dispatcher balance of that token after the predispatch call) satisfies `balance >= 0`; the full `balance` is swept to `address(this)` and emitted as `DustCollected`, while `_orders[commitment][token] += 0` is stored.
4. The commitment now has no recorded escrow for that token, so it can never be filled or reclaimed via `cancelOrder`, permanently stranding the swept value inside the `IntentGatewayV2` contract.
