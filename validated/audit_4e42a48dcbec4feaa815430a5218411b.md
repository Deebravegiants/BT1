### Title
Webhook HMAC validation does not bind the `shop` (or `topic`) identity to the signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `Utils::HmacValidator.validate` computes/verifies the HMAC exclusively over that body [1](#0-0) [2](#0-1) . The `shop` domain that identifies the tenant for the webhook is read straight from an unauthenticated header and is never part of the signed material [3](#0-2) . `Registry.process` validates the HMAC and then dispatches the handler using this unauthenticated `shop` field as the tenant identity [4](#0-3) .

### Finding Description
The identity binding that should hold is:
`hmac_valid(body, secret) == true` should imply `(topic, shop, body)` together were produced/authorized by Shopify for that specific shop.

In this gem, the actual binding is only:
`hmac_valid(body, secret) == true` implies only that `body` bytes were HMAC'd with the app's shared `api_secret_key` — it says nothing about which shop, topic, or webhook-id header accompanies that body [5](#0-4) .

Because a single app's `api_secret_key` is shared across every shop that installs the app, any store owner who has legitimately installed the app can:
1. Trigger a real webhook delivery to their own endpoint for an event they control (e.g. `orders/create` in their own store), capturing a valid `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's real secret.
2. Replay that exact body/HMAC pair to the app's webhook endpoint, but with the `x-shopify-shop-domain` header (and/or `x-shopify-topic`) changed to point at a victim shop.
3. `Utils::HmacValidator.validate` still returns `true`, because it only checked the body against the secret — it never checked that the `shop`/`topic` claimed in headers match what was actually signed [6](#0-5) .
4. `Registry.process` then invokes the app's handler with `WebhookMetadata` carrying the forged `shop` value [7](#0-6) , causing the host application to process attacker-controlled data as if it originated from the victim's tenant.

This is the exact pattern called out in scope: "a field acted on but not covered by the HMAC" — here the `shop` domain used to route/attribute the webhook is acted upon by the application but is completely outside the HMAC's protection.

### Impact Explanation
This breaks tenant isolation: an app built on this gem cannot actually trust that a webhook whose HMAC validates truly originates from, or concerns, the shop named in the `shop-domain` header. Any authenticated installer of the app (an "unprivileged internet user" relative to other tenants — they only need to install the app on their own free/dev store, not obtain any other merchant's credentials) can inject data attributed to an arbitrary victim shop into the host application's webhook processing pipeline, e.g. fabricating `orders/create`, `customers/data_request`, or `app/uninstalled` events for a shop they do not own. This is a cross-tenant access vulnerability per the Critical impact bucket in scope.

### Likelihood Explanation
Exploitation only requires: (a) installing the target app on an attacker-controlled shop (which is the normal, unprivileged path any developer/merchant can take), and (b) capturing one legitimately delivered webhook body/HMAC pair and replaying it with a modified `shop-domain`/`topic` header to the same public webhook endpoint. No access to another merchant's access token, session, or the app's `client_secret` is required — the attacker uses their own legitimate delivery as the signed payload. This makes the likelihood high once the general pattern (HMAC over body only) is understood, since it's inherent to how `HmacValidator`/`Request` are implemented in this gem rather than a host-app misconfiguration.

### Recommendation
Bind the identity fields into the verified signature/context rather than trusting the unauthenticated `shop-domain`/`topic`/`webhook-id` headers verbatim:
- At minimum, document/require that consuming applications independently verify that the `shop` in the webhook belongs to a shop with an active installation/session before trusting `WebhookMetadata#shop`.
- Better, extend the HMAC computation or add a secondary integrity check that incorporates the shop/topic headers (matching what Shopify's own webhook signing guarantees), or reject processing when the `shop` header does not match a shop for which the app holds a valid stored session/token.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, obtaining the app's real `api_secret_key`-signed webhook deliveries.
2. Attacker triggers `orders/create` on their own store, capturing:
   - `raw_body` = `{"id":1,...}`
   - `x-shopify-hmac-sha256` = valid HMAC-SHA256(raw_body, api_secret_key) (base64)
3. Attacker sends a POST to the app's public webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256`, but sets:
   - `x-shopify-shop-domain: victim.myshopify.com`
   - `x-shopify-topic: orders/create`
4. `ShopifyAPI::Webhooks::Request.new` parses these headers [8](#0-7) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `raw_body` [9](#0-8) .
5. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: ..., ...)` [7](#0-6)  and processes attacker-controlled order data attributed to the victim's shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          received_signature = verifiable_query.hmac
