### Title
Webhook `shop` (and other metadata) is trusted from unauthenticated headers but excluded from the HMAC digest, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` computes the HMAC signature over the raw request body only. The `shop`, `topic`, `webhook_id`, and `api_version` values are parsed straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) and are never included in the bytes that `Utils::HmacValidator` verifies. `Registry.process` then trusts `request.shop` as the tenant identifier passed to the app's `WebhookHandler`. Anyone who can obtain one valid `(body, hmac)` pair — trivially available since the attacker can install the app on their own store and trigger a webhook themselves — can replay that unmodified body/hmac to the app's public webhook endpoint while swapping the `shopify-shop-domain` header to a victim shop, and the signature will still validate.

### Finding Description
The identity binding that should hold is:

`shop value verified by HMAC == shop value acted on by the handler`

but the actual binding in this gem is:

`bytes verified by HMAC (raw_body only) != bytes the handler trusts as tenant identity (shop header)`.

Concretely:
- `Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` header value. [1](#0-0) 
- For webhooks, `to_signable_string` returns *only* `@raw_body`: [2](#0-1) 
- Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from HTTP headers, none of which feed into the signable string: [3](#0-2) 
- `Registry.process` validates the HMAC and then unconditionally forwards `request.shop` (a header value with zero cryptographic binding to the signature) to the handler as the trusted tenant identity: [4](#0-3) 
- `WebhookMetadata.shop` is the field documented and expected to be used by host apps to resolve the merchant/session the webhook body should be applied to: [5](#0-4) 

Because the signature covers only the body, any two webhook deliveries that happen to carry the identical body (which an attacker fully controls by triggering the webhook from their own shop) produce the identical valid HMAC regardless of which `shop-domain` header accompanies them. The gem therefore lets an attacker "detach" a genuine signature from the tenant it was actually generated for.

### Impact Explanation
This is a cross-tenant access primitive: an attacker who legitimately installs the app on a shop they control (or even a free/dev store) can capture a real `(raw_body, hmac)` pair for any topic they can trigger (e.g. `orders/create`, `customers/create`, `app/uninstalled`), then submit a forged HTTP request to the same webhook endpoint with the same body/hmac but an arbitrary `shopify-shop-domain` header pointing at a different, victim shop that also has the app installed. `Registry.process` will accept the payload as authentic and hand the handler a `WebhookMetadata` claiming it came from the victim shop. Any host application that uses `data.shop` to select which merchant record/session/database row to update (the pattern explicitly shown in this gem's own docs) will apply attacker-controlled webhook data to a different tenant's data — a cross-tenant data-integrity/access violation, satisfying the Critical "cross-tenant access" bar.

### Likelihood Explanation
Medium-to-high:
- No privileged credentials, TLS interception, or social engineering are required — only a normal app install (attacker's own store) to obtain one valid signed body.
- Webhook endpoints are internet-reachable by design, and this gem provides no header-binding to prevent the replay described above.
- Nothing in the gem's HMAC verification path (`Utils::HmacValidator`, `Webhooks::Request#to_signable_string`) or the documented webhook usage guide warns integrators that `shop`/`topic`/`webhook_id` are unauthenticated metadata; the docs present `data.shop` as trustworthy. [6](#0-5) 

### Recommendation
Bind the header-derived identity fields into the value that is HMAC-verified, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the signature before trusting them:
- Change `Webhooks::Request#to_signable_string` so it includes `shop`, `topic`, and `webhook_id` (not just `@raw_body`) in the signed string, matching what Shopify's outbound webhook signature actually protects, or
- Verify `shop` independently (e.g. against a per-shop secret or an allow-list of installed shop domains) before constructing `WebhookMetadata`, so that no header value influences tenant selection unless it has been authenticated.

### Proof of Concept
1. Install the target app (legitimately) on attacker-owned shop `attacker.myshopify.com`.
2. Trigger a webhook topic the app subscribes to (e.g. `orders/create`) with an attacker-chosen body (order payload). Capture the raw POST: headers (`x-shopify-topic`, `x-shopify-hmac-sha256`, `x-shopify-shop-domain: attacker.myshopify.com`, ...) and raw body.
3. Resend this exact HTTP request to the app's webhook endpoint, but replace only the `x-shopify-shop-domain` header value with `victim.myshopify.com` (a shop with the same app installed). Leave the body and `x-shopify-hmac-sha256` untouched.
4. `Utils::HmacValidator.validate` succeeds because it only re-hashes `@raw_body`, which is unchanged: [2](#0-1) 
5. `Registry.process` calls the handler with `WebhookMetadata.shop == "victim.myshopify.com"` and `body` equal to the attacker's crafted order payload: [7](#0-6) 
6. Any host application logic keyed on `data.shop` (per the gem's documented handler pattern) now processes attacker-controlled data under the victim shop's tenant context.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
