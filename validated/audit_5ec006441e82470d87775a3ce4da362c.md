### Title
Webhook `shop` identity is trusted from an unauthenticated header while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (tenant) attribute directly from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, but `Utils::HmacValidator` only ever signs/verifies the raw request body. The header is never part of the HMAC-covered material, so its value has no cryptographic binding to the payload that was actually signed by Shopify.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `HmacValidator.validate` computes/compares the HMAC exclusively against that signable string: [2](#0-1) 

Meanwhile, `Request#shop` is read straight from the headers without any cross-check against the HMAC: [3](#0-2) 

`Registry.process` validates the HMAC (body-only) and then immediately builds `WebhookMetadata` using that unauthenticated `request.shop` value, handing it to the host application's handler as the trusted tenant identifier: [4](#0-3) [5](#0-4) 

The binding that should hold is: `shop-domain header == shop that produced/authorized this exact body`. Because the HMAC only certifies `raw_body`, that equality is never actually checked — an attacker who possesses one valid `(raw_body, hmac)` pair signed by the app's secret (e.g. from a webhook Shopify legitimately sent them for their own shop) can resubmit that same body+HMAC to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` will still pass (it never looks at the header), and the gem will hand the host application a `WebhookMetadata` claiming the payload belongs to any shop the attacker chooses.

### Impact Explanation
Every merchant that installs the app is issued the same `api_secret_key`-based signing relationship for all their webhooks (the secret is shared per-app, not per-shop). A malicious but otherwise legitimate merchant of the app can capture body+HMAC pairs Shopify sent for their own store's webhooks and replay them against the same endpoint while spoofing the `shop-domain` header to point at a victim shop. Because the gem asserts no equality between the signed bytes and the shop header, the host application (which relies on `WebhookMetadata#shop` to select the tenant's database record/session) can be made to process attacker-controlled webhook data under a different merchant's identity — a cross-tenant data-integrity violation stemming directly from this gem's trust boundary.

### Likelihood Explanation
Requires only: (1) the attacker to be a legitimate installer of the app (no special privilege beyond a normal shop install, so effectively "unprivileged internet user" relative to other tenants), and (2) the app's webhook endpoint to be internet-reachable, which by design it must be for Shopify to call it. No access token, `client_secret`, or victim credentials are needed. The gem provides no defense — the check is fundamentally structural to `to_signable_string` returning only the body.

### Recommendation
Include the shop domain (and ideally topic/api-version) in the HMAC-signable string, or otherwise cryptographically bind the header value to the body before trusting `Request#shop`/`WebhookMetadata#shop`. At minimum, document prominently that `request.shop` is unauthenticated and must be independently cross-checked by host applications against a known/installed shop list before being used as a tenant key.

### Proof of Concept
1. Attacker legitimately installs the app on `attacker-shop.myshopify.com` and receives a real Shopify webhook: raw body `B` with header `x-shopify-hmac-sha256: H` (valid for the app's `api_secret_key` over `B`) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker POSTs the exact same body `B` and `hmac-sha256: H` to the app's webhook endpoint again, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers (only checks presence, not the shop value) — see [6](#0-5) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation succeeds despite the forged shop header ( [7](#0-6) ).
5. The handler receives `WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed B, ...)`, and any host-app logic keyed on `data.shop` (e.g., "look up victim's DB row and apply `body`") is executed against the wrong tenant.

```ruby
      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
```
