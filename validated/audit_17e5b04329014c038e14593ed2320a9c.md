### Title
Webhook `shop-domain` header is not covered by HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` binds `hmac` validation only to the raw request body, while the `shop`, `topic`, `api-version`, and `webhook-id` values — all of which are read from unauthenticated HTTP headers — are used verbatim by `Registry.process` to identify which tenant/topic a webhook belongs to. This breaks the intended identity binding: "bytes verified" (the JSON body) ≠ "bytes/fields acted on" (the header-derived `shop`).

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all pulled directly from HTTP headers, none of which participate in the signable string: [2](#0-1) 

`HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (i.e., the body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` validates the HMAC and then passes `request.shop` straight into the handler as the tenant identifier, without any additional cross-check that this shop is the one the signature/body actually originated from: [4](#0-3) 

Because only the body is signed, two webhook deliveries with an identical body (e.g., an identical `orders/create` payload structure, or any payload where the shop identity is not embedded inside the JSON itself) will produce an identical valid HMAC regardless of which `x-shopify-shop-domain` header value is sent alongside it. This means the equality the code relies on — "the shop the HMAC vouches for" == "the shop passed to the handler" — does not actually hold; the HMAC vouches only for the body bytes, not for the shop attribution.

### Impact Explanation
This is a tenant-identity-binding gap: the field the application logic keys tenant-scoped side effects on (`shop`) is not covered by the same authenticity mechanism (HMAC) that gates whether the request is trusted at all. If an app's webhook handler uses `data.shop` to route or scope any per-tenant action (session lookup, data writes, cache keys, GDPR/redact handling, etc.), a request with a validly-signed body but an attacker-controlled `shop-domain` header would be processed under the wrong tenant identity, per the exact bug class this scan is looking for (field acted upon but not covered by the HMAC).

### Likelihood Explanation
Exploitation requires the attacker to possess a body/HMAC pair that is valid for the configured `api_secret_key` — normally this means having previously received a real, Shopify-signed webhook for *some* shop and body content that overlaps with what they want to spoof. This gem's own request-verification code offers no header-shop binding, so nothing in this library prevents replay of a captured body+hmac pair with a substituted `shop-domain` header even for a completely different tenant. Per this scan's exclusions, exploitation paths requiring possession of `api_secret_key` are out of scope; however, this analog does not require the secret — it requires only a signed body/HMAC pair the attacker was legitimately delivered for their own shop, which is a normal unprivileged capability (any merchant can install the app and trigger events to receive real webhooks for their own store), then replay it toward another shop's identity. Likelihood is assessed as low-to-moderate given the payload similarity constraint and reliance on downstream host-application behavior, consistent with the acknowledged/low-risk framing of the analog bug class described in the report.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`) header values in the HMAC-signable content, or at minimum require host applications to independently verify that `request.shop` corresponds to a shop with a currently valid installed session before trusting `WebhookMetadata.shop`. Document this binding gap explicitly so implementers do not assume `shop` is HMAC-protected.

### Proof of Concept
1. App receives (or an attacker captures) a legitimately Shopify-signed webhook for `shop-a.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`.
2. Attacker replays the exact same body `B` and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `B` against the HMAC.
4. `Registry.process` in `lib/shopify_api/webhooks/registry.rb:188-200` calls the handler with `WebhookMetadata.new(... shop: "shop-b.myshopify.com" ...)`, causing the app to process body `B` under `shop-b`'s tenant context despite the signature never having certified that association.
