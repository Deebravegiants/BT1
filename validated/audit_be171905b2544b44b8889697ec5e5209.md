### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC over the raw body only, while the `shop` identity that is handed to the app's `WebhookHandler` is read from an unauthenticated header. This breaks the equality that should hold: `hmac_verified_bytes == bytes_that_determine_tenant_identity`. An attacker who can obtain one genuine `(body, hmac)` pair signed with the app's `client_secret` (e.g. by triggering a webhook for a shop they legitimately control) can replay that exact body/HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with an arbitrary victim shop domain, and the signature check still passes.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the (attacker-controlled, unauthenticated) HTTP header, independently of the HMAC: [2](#0-1) 

`HmacValidator.validate` only checks that `to_signable_string` (the body) matches the signature — it never binds `shop`, `topic`, `webhook_id`, or `api_version` into the signed material: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately forwards the header-derived, unauthenticated `shop` (and `topic`/`webhook_id`/`api_version`) to the app's handler as trusted metadata: [4](#0-3) 

`WebhookMetadata` carries `shop` as a plain `String` with no further validation performed by the gem: [5](#0-4) 

Because the identity binding `hmac(body) == hmac_received` says nothing about which shop the body belongs to, any consumer whose `WebhookHandler#handle` implementation trusts `data.shop` (which is the pattern explicitly promoted in the gem's own webhook documentation) to key per-tenant storage, access-token lookup, or GDPR/data-deletion actions can be made to operate on the wrong tenant, using only a body/HMAC pair the attacker legitimately obtained for their own shop.

### Impact Explanation
This falls under Critical — cross-tenant access. `shop` is the sole tenant-identity field surfaced to application code by this gem's webhook framework, and it can be forged without ever touching `client_secret`, an access token, or TLS interception: the attacker only needs one authentic `(body, hmac)` pair generated by Shopify for a shop under their own control (trivially obtainable by installing the app on their own dev/test store and triggering any webhook topic), then replays it with a different `shop` header value.

### Likelihood Explanation
Likelihood is high for any app that relies on the gem's promoted pattern of trusting `WebhookMetadata#shop` (as shown in the gem's own `docs/usage/webhooks.md` example) to select the tenant/session for subsequent processing, since the webhook endpoint is a public, unauthenticated HTTP route by design and the attacker-required precondition (owning/installing the app on one shop to harvest a valid body+HMAC) is trivially satisfiable by any developer able to install a free/public app.

### Recommendation
Include `shop` (and ideally `topic`, `api_version`, `webhook_id`) in the HMAC-signed material used for verification, or otherwise cryptographically bind the header-derived shop to the request before exposing it via `WebhookMetadata`. At minimum, document (and enforce in the gem) that `data.shop` must be re-validated against the shop for which the raw body's HMAC was computed, rather than trusted as an independent field. Adopting the same defense used elsewhere in the codebase for shop-domain trust (`ShopifyAPI::Utils::ShopValidator`) is not sufficient here since it only confirms syntactic validity of a myshopify domain, not that the caller actually owns it.

### Proof of Concept
1. Install the target app on an attacker-controlled Shopify dev store; trigger any subscribed webhook topic (e.g. `orders/create`) so Shopify POSTs `{raw_body, X-Shopify-Hmac-Sha256, X-Shopify-Shop-Domain: attacker-shop.myshopify.com}` to the app's public webhook endpoint.
2. Capture this exact `raw_body` and its valid `X-Shopify-Hmac-Sha256` value (attacker fully controls their own network path/browser devtools/proxy to their own store — no interception of Shopify-to-victim traffic is required).
3. Replay the identical `raw_body` and `hmac` header to the same public webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because `to_signable_string` is only `raw_body`, which is unchanged: [6](#0-5) 
`Registry.process` calls the app's handler with `shop: request.shop` == `"victim-shop.myshopify.com"`, `body:` the attacker's own (fully attacker-authored) order payload: [7](#0-6) 
5. If the app's handler uses `data.shop` to look up/act on tenant state (session storage, local DB records, data deletion, etc.), the attacker has caused cross-tenant action against `victim-shop` using data they fully controlled, without ever knowing `client_secret` or any victim credential.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
