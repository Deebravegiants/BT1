### Title
Webhook HMAC signature does not cover the `shop-domain` (or `topic`/`webhook-id`) header, allowing shop impersonation - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from an unauthenticated HTTP header, while the HMAC signature validated by `HmacValidator` only covers the raw request body. This breaks the binding `shop used for tenant identity == shop covered by HMAC`, allowing an attacker who possesses any single valid `(body, hmac)` pair to relabel it as belonging to an arbitrary victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `Request#shop`, `#topic`, and `#webhook_id` are read straight from HTTP headers, entirely outside the signed content: [2](#0-1) 

`HmacValidator.validate` verifies the HMAC exclusively against `verifiable_query.to_signable_string` (i.e., the body), and never incorporates the headers: [3](#0-2) 

`Registry.process` gates all further processing on this body-only HMAC check, then immediately trusts `request.shop` (from the unauthenticated header) as the tenant identity passed to the app's handler: [4](#0-3) 

Contrast this with `Auth::Oauth::AuthQuery`, used for the OAuth callback, where `shop` (and `host`) *is* included inside `to_signable_string` and therefore is cryptographically bound to the HMAC: [5](#0-4) 

This is the same bug class as the referenced report: the identity/routing field (`min_fill_amount`/shop) that a downstream `require`/authorization decision relies on is not computed over the same data that was actually verified (`fill_amt`/HMAC-signed body). Here, the equality that should hold is:
`shop asserted to caller (WebhookMetadata.shop) == shop cryptographically bound by HMAC`
but in fact the HMAC binds nothing about `shop`, `topic`, or `webhook-id` — only the JSON body bytes.

### Impact Explanation
Any actor who can obtain one legitimately Shopify-signed `(raw_body, hmac)` pair — for example, by installing the app on their own store and receiving a real webhook delivery to an endpoint they control, or from any other correctly-signed webhook they can capture — can replay that exact body and HMAC to the app's webhook endpoint while substituting the `shop-domain` (and/or `topic`, `webhook-id`) header for a victim's shop domain. `HmacValidator.validate` will still pass because it only checks the body, and `Registry.process` will hand the forged `shop` value to the app's `WebhookHandler` as if the payload legitimately originated from the victim's store. Depending on how the host application uses `WebhookMetadata#shop` (e.g., looking up a session/tenant record, writing data scoped to that shop, or acting on mandatory compliance topics like `customers/redact`), this constitutes cross-tenant data injection / a broken tenant-identity binding, rising to Critical severity (cross-tenant access) under the given criteria.

### Likelihood Explanation
The attacker needs only one valid signed webhook payload — trivially obtainable by installing (or trialing) the target app on a shop they control and capturing any inbound webhook — and then can craft arbitrary forged headers server-side with no knowledge of `api_secret_key`. No TLS interception, credential theft, or privileged account is required; this is reachable by an ordinary unprivileged internet user who is a legitimate (even free) merchant of the same app.

### Recommendation
Include the identity/routing headers actually relied upon by the caller (`shop-domain`, `topic`, `webhook-id`) inside the signable string used for HMAC verification, or otherwise cryptographically bind them (e.g., verify `shop` against a value independently obtained from a call to Shopify's API, not solely from headers). At minimum, `Request#to_signable_string` should incorporate the shop/topic/webhook-id headers so `HmacValidator.validate` fails if any of them are altered post-signing.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw POST: headers (`x-shopify-hmac-sha256: <H>`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`) and `raw_body`.
2. Replay this exact `raw_body` and `x-shopify-hmac-sha256: <H>` to the same webhook endpoint, but replace `x-shopify-shop-domain` with `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request whose `hmac` is unchanged and whose `shop` is now `victim.myshopify.com`.
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only (`request.rb:35-38`, `hmac_validator.rb:26-31`) — it matches `<H>`, so validation succeeds.
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, causing the host application to process attacker-supplied webhook content attributed to the victim's shop. [6](#0-5)
