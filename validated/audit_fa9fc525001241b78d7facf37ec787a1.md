## Finding

### Title
Batched message delivery reverts entirely on a single duplicate/timed-out entry, enabling cheap griefing that blocks legitimate message delivery - (File: evm/src/core/HandlerV2.sol)

### Summary
`HandlerV2.handlePostRequests` (and the structurally identical `handleGetResponses`, `handlePostRequestTimeouts`, `handleGetRequestTimeouts`) verifies a batch of independent messages against a single Merkle multiproof and then dispatches them in a loop. If any single leaf in the batch is a duplicate (already delivered) or otherwise fails a per-item check, the whole call reverts with `DuplicateMessage()` — even though every other leaf in the batch is valid, unprocessed, and covered by a valid proof. This is the same push-style, all-or-nothing batch-processing hazard described in the `PaymentSplitter._release_all` report: one already-settled item poisons the entire batch for everyone else in it.

### Finding Description
`handlePostRequests` does the dispatch loop like this: [1](#0-0) 

Every leaf that was already delivered (its `host.requestReceipts(...)` slot is non-zero) causes the entire transaction to `revert DuplicateMessage()`, discarding the dispatch of every other, still-undelivered leaf in the same `request.requests` array, despite the fact that the Merkle proof already verified all of them together: [2](#0-1) 

The same shape exists for responses: [3](#0-2) 

The substrate-side counterpart, `pallet_ismp::Pallet::execute`, has the identical all-or-nothing semantics: it maps every message in the batch through `handle_incoming_message` and `.collect::<Result<Vec<_>, _>>()?` short-circuits on the first error, aborting the whole `handle_unsigned` extrinsic: [4](#0-3) 
This is documented as intentional ("short-circuit and revert if any of the provided messages are invalid") in both the code comment and the pallet call doc: [5](#0-4) 

Both `handlePostRequests`/`handleGetResponses` (permissionless, called by any relayer) and `handle_unsigned` (unsigned extrinsic, permissionless) are directly reachable by anyone with a valid proof — exactly the "unprivileged relayer" actor class in scope.

### Impact Explanation
Hyperbridge relayers batch multiple pending requests/responses together to amortize gas/verification cost, exactly as the `IHandlerV2.batchCall` and `handlePostRequests`/`handleGetResponses` design intends. Because dispatch is a strict per-call, all-or-nothing loop:
- A single already-delivered leaf (a normal outcome of the permissionless "relay race," where multiple relayers race to deliver the same message) causes the *entire* batch to revert, wasting the submitting relayer's gas and, more importantly, failing to deliver every other still-pending, validly-proven message bundled in that transaction.
- An adversarial actor can cheaply front-run a single low-value leaf in a relayer's known pending batch (deliver it first, e.g. by watching the mempool or by simply always beating the batch on that one message) to force repeated reverts of larger batches, delaying delivery of unrelated cross-chain messages — a "route unable to deliver messages" condition for the messages bundled behind the poisoned one.
- The failure mode is amplified as batch sizes grow (more independent leaves = higher probability that any one has already landed), which pressures relayers toward smaller batches, defeating the batching optimization and increasing costs/latency network-wide.

This does not itself cause fund loss, but it is a concrete availability/DoS vector against message delivery reachable by a single relayed proof from an unprivileged actor, matching the "route unable to deliver messages" acceptance criterion.

### Likelihood Explanation
High likelihood of naturally occurring (relay races are a designed, expected part of the protocol's incentive model — see the relayer race-to-deliver framing in `docs/content/developers/explore/nexus/relayer.mdx`), and trivially and cheaply weaponizable by any third party who can observe pending relayer batches and deliver a single leaf ahead of time. No privileged access or governance action is required.

### Recommendation
Change per-leaf dispatch in `handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, and `handleGetRequestTimeouts` (and the analogous substrate `execute`/`handle_incoming_message` batch path) to a pull/best-effort model: skip (and optionally emit an event for) already-delivered or per-item-invalid entries instead of reverting the whole call, so the remaining valid, unprocessed leaves in the batch are still dispatched. If atomicity guarantees are required for specific reasons, consider bounding batch composition so a relayer can exclude/re-submit only the poisoned leaf rather than losing the whole batch, or expose a `try`/`catch`-style per-leaf dispatch that records failures without aborting the batch.

### Proof of Concept
1. Relayer A observes N pending, provable `PostRequest` leaves and builds a Merkle multiproof covering all N, then submits `handlePostRequests(host, request)` with `request.requests.length == N`.
2. Before A's transaction is included, an unrelated actor (or a competing relayer, or a deliberate griefer) delivers just leaf `k` (`0 <= k < N`) via any other transaction, setting `host.requestReceipts(leaf_k.hash()) != address(0)`.
3. A's transaction executes: the proof-verification loop at lines 190-202 succeeds (all N leaves are still validly proven against the stored root), but the dispatch loop at lines 204-209 hits `if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();` for leaf `k` and reverts the entire call.
4. Result: none of the N-1 still-undelivered, validly-proven requests are dispatched; A's gas is wasted; delivery of those N-1 messages is delayed until A (or another relayer) resubmits a smaller batch excluding leaf `k`, repeatable at low cost by the griefer.
