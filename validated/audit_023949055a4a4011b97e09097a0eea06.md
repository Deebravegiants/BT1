# Title
Webhook Shop-Domain Header Not Covered by HMAC Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signable string from the raw request body only, while the `shop` (tenant identity) is read from a separate, unsigned HTTP header. `Registry.process` validates the HMAC and then hands the *unverified* `shop` value straight to the host application's webhook handler as trusted tenant context. Because every shop installed on an app shares the same `Context.api_secret_key`, any merchant who has the app installed on their own store can generate a validly-signed webhook body and then replay that body with a different `shop-domain` header, causing the host app to process the payload as if it belonged to a victim tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived purely from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is never included in the signed content: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, and then forwards `request.shop` — the unauthenticated header value — as the tenant identity delivered to the app's handler: [3](#0-2) 

The HMAC itself is computed with a single shared `Context.api_secret_key`/`old_api_secret_key`, not a per-shop secret: [4](#0-3) 

The identity binding the gem is supposed to guarantee to the host application is: `shop header == shop that produced this signed body`. Because `shop` is excluded from `to_signable_string`, that equality is never checked — only `body == body` is verified. A merchant with the app installed on their own shop can capture a legitimate webhook (valid body + valid HMAC, since it's generated by their own real event and signed with the app-wide secret), then resend the identical body/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop. `Registry.process` will accept it, because `Utils::HmacValidator.validate` only reasons about the body bytes, and hands `WebhookMetadata` with the attacker-chosen `shop` to the handler as if it were verified.

### Impact Explanation
This breaks the tenant boundary the gem is meant to enforce for webhook consumers: the `shop` field delivered to `WebhookMetadata` (and therefore to any host-app logic that looks up/updates per-shop records, revokes access, or triggers billing/state changes based on the webhook shop) is attacker-controlled despite HMAC validation succeeding. Any app that trusts `WebhookMetadata#shop` post-validation (which is the documented contract of `Registry.process` and `Utils::HmacValidator`) is exposed to cross-tenant data confusion/injection — e.g., an attacker-owned shop's order/customer/app-uninstall payload can be attributed to and processed against a victim shop's session/records.

### Likelihood Explanation
Exploitation only requires the attacker to be an ordinary, unprivileged user who installs the target app on their own (possibly free/trial) Shopify store — no access token, `client_secret`, or victim credentials are needed. They can trigger any webhook topic the app subscribes to, capture the resulting `raw_body` + `hmac-sha256` header from their own store's webhook delivery, and replay it to the app's public webhook endpoint with a forged `shop-domain` header. Since `api_secret_key` is shared across all installations of the app, the replayed HMAC still validates.

### Recommendation
Bind the shop identity into the verified material: include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in `to_signable_string`, or independently verify that the `shop` a handler receives matches a shop known to have a currently-installed/active session before trusting it for tenant-scoped operations. At minimum, document/enforce that `Registry.process` callers must cross-check `request.shop` against their own installed-shop registry rather than treating it as authenticated purely because the body HMAC matched.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Attacker triggers a subscribed webhook topic (e.g. `orders/create`) on their own store, capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header sent by Shopify (signed with the app's shared `client_secret`).
3. Attacker resends this exact body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds (it only checks `@raw_body`), `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, and the host app processes/acts on data as though it originated from the victim tenant.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
