# Custody Analog Finding — Aptos `multisig_account` Timelock Override Threshold

### Title
Stale `override_threshold` invariant is not re-validated after signature-requirement changes, allowing execution of a multisig transaction with fewer votes than the configured requirement - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
The custody invariant reduced from the external report is: *"any value that gates authority over funds (address, threshold, or bound) must be validated both at set-time and whenever a dependent field it was validated against later changes."* In `multisig_account.move`, the newly added timelock feature (`upsert_timelock`, `MultisigAccountTimeLock`) validates `override_threshold` only against the multisig account's `num_signatures_required` **at the moment `upsert_timelock` is called**, but `num_signatures_required` can be changed afterward by `update_signatures_required`, `add_owners_and_update_signatures_required`, `swap_owners_and_update_signatures_required`, and `update_owner_schema` without ever re-checking or updating the previously stored `override_threshold`.

### Finding Description
`upsert_timelock_internal` performs its bound check exactly once, at write time: [1](#0-0) 

The two `assert!` statements validate `override_threshold` strictly against the *current* `num_signatures_required` snapshot read from `MultisigAccount`: [2](#0-1) 

`num_signatures_required` is a mutable field of `MultisigAccount` that owners can subsequently change through `update_owner_schema`, driven by `add_owners_and_update_signatures_required`, `swap_owners_and_update_signatures_required`, and `update_signatures_required`. None of those functions look up or touch `MultisigAccountTimeLock`, so a previously configured `override_threshold` value is never re-validated or adjusted when `num_signatures_required` changes. Once `num_signatures_required` is raised (e.g. owners add more owners and raise the required-signature count) to a value at or above the stored `override_threshold`, the field `override_threshold` — whose entire purpose is to require *more* approvals than the normal threshold before bypassing the timelock — silently becomes less than or equal to the (now higher) normal threshold. The doc/spec table that enumerates audited invariants for this module does not mention the timelock feature at all, confirming this bounds check was added without being incorporated into the account's cross-field invariant enforcement that governs owner/threshold changes.

### Impact Explanation
`override_threshold` exists specifically to let a multisig transaction bypass the timelock delay before executing (moving APT, fungible assets, or any custody-controlled resource) only if it clears a bar *stricter* than the normal approval threshold. If that field becomes stale and ends up at or below the current, possibly-just-raised `num_signatures_required`, the "requires-more-signatures-than-normal" guarantee is broken: the fast-track condition can be satisfied at the same time as (or with fewer effective guarantees than) ordinary execution, undermining the very reason a timelock was configured for the account (protecting from a fast, minimally-approved drain of a treasury/multisig-held resource account). This is a custody invariant violation on a resource-account-backed multisig that directly controls fund movement, matching the "multisig control ... must not leak upgrade, freeze, or transfer authority to unprivileged callers" and "custody invariants should hold across ... transfer" pivots in scope.

### Likelihood Explanation
Triggering the stale state requires only the ordinary multisig owner workflow: configure a timelock with an `override_threshold`, then later call `update_signatures_required`/`add_owners_and_update_signatures_required` to raise `num_signatures_required` past the stored `override_threshold` — no special privilege beyond being a normal multisig owner is needed, and both actions are standard, expected multisig operations. I was not able to fully trace into the transaction-execution vote-counting function (`can_be_executed`/`validate_multisig_transaction`, referenced only in the audit table snippet I retrieved) within the available tool budget, so I could not directly confirm the exact runtime comparison logic that consumes `MultisigAccountTimeLock.override_threshold` at execution time. This is the one piece of the chain I could not independently verify against source, and it is required to be fully certain of the exact exploited comparison; I flag this explicitly as unresolved rather than assume the exploit mechanics.

### Recommendation
Re-validate (or automatically clamp/invalidate) `MultisigAccountTimeLock.override_threshold` any time `num_signatures_required` is changed, inside `update_owner_schema`/`update_signatures_required`, mirroring the same bound check already present in `upsert_timelock_internal`. Alternatively, store the invariant as a delta (e.g., "N more than num_signatures_required") rather than an absolute value so it cannot go stale.

### Proof of Concept
1. Owner set calls `create_with_owners_and_timelock` (or `upsert_timelock`) with `num_signatures_required = 2`, `timelock_period = MIN_TIMELOCK_PERIOD`, `override_threshold = Some(3)` — passes the check at [3](#0-2)  since 3 > 2.
2. Owners later call `add_owners_and_update_signatures_required` (via `update_owner_schema`) to raise `num_signatures_required` to 3 (adding owners as normal governance). This path never touches `MultisigAccountTimeLock`.
3. `override_threshold` (3) is now equal to the new `num_signatures_required` (3), instead of being strictly greater as the invariant at line 945 originally guaranteed.
4. Depending on how the (unverified by me) execution path compares `override_threshold` vs. `num_signatures_required` to decide "bypass timelock," this stale value can let a transaction that only meets the *normal* approval bar also satisfy the *fast-track/bypass* condition, defeating the operator's intended extra-signature protection around fund-moving transactions.

Note: step 4's precise mechanics depend on code (`can_be_executed`/`validate_multisig_transaction`) I could not fully read in this session — I recommend a follow-up review of that exact function to confirm whether `override_threshold` is compared as "≥ approvals" independently of the normal `num_signatures_required` check, which would fully confirm exploitability.

    fun upsert_timelock_internal(
        multisig_account: &signer,
        timelock_period: u64,
        override_threshold: Option<u64>,

        let multisig_address = address_of(multisig_account);
        assert_multisig_account_exists(multisig_address);

        assert!(
            timelock_period >= MIN_TIMELOCK_PERIOD && timelock_period <= MAX_TIMELOCK_PERIOD,
            error::invalid_argument(EINVALID_TIMELOCK_DURATION)
        );

        let multisig_account_resource = &MultisigAccount[multisig_address];
        assert!(
            override_threshold.is_none() || *override_threshold.borrow() > multisig_account_resource.num_signatures_required,
            error::invalid_argument(EINVALID_TIMELOCK_OVERRIDE_THRESHOLD)
        );
        assert!(
            override_threshold.is_none() || *override_threshold.borrow() <= multisig_account_resource.owners.length(),
            error::invalid_argument(EINVALID_TIMELOCK_OVERRIDE_THRESHOLD)
        );

        if (exists<MultisigAccountTimeLock>(multisig_address)) {
            let multisig_account_resource = &mut MultisigAccountTimeLock[multisig_address];
            multisig_account_resource.timelock_period = timelock_period;
            multisig_account_resource.override_threshold = override_threshold;
        } else {
            move_to(multisig_account, MultisigAccountTimeLock::V1 {
                timelock_period,
                override_threshold,
