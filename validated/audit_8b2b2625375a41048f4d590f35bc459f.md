## Title
Single malicious/blocked token or beneficiary in a multi-asset intent order permanently freezes the entire order's escrow - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw` (and the equivalent `IntentGatewayV2.withdraw` in the Tron fork) releases every escrowed asset for an order commitment in a single loop over `body.tokens`. If any single token transfer or native-ETH send in that loop reverts — because a token is a blacklisting stablecoin (e.g. USDT/USDC) and the beneficiary got blacklisted, or the beneficiary is a contract that rejects ETH — the entire `_withdraw` call reverts, which unwinds delivery of the *whole* cross-chain message, blocking release of every other (perfectly fine) asset bundled in that same order forever, exactly like the referenced report where one blocked recipient prevents an unrelated party from ever getting paid.

### Finding Description
`_withdraw` iterates every entry in `body.tokens` and unconditionally reverts the whole function if any single transfer fails: [1](#0-0) 

- Native transfers use `_sendValue`, which reverts with `InsufficientNativeToken` if the low-level call fails: [2](#0-1) 
- ERC-20 transfers use `IERC20(token).safeTransfer`, which reverts if the token's `transfer` returns false or reverts (e.g. USDC/USDT blacklist).

The identical pattern exists in the Tron `IntentGatewayV2.withdraw`, which loops over `body.tokens` and reverts with `TransferFailed`/`InsufficientNativeToken` on any single failure: [3](#0-2) 

This `_withdraw`/`withdraw` function is reached from an unprivileged, relayer-submitted ISMP `RedeemEscrow`/`RefundEscrow` POST request via `onAccept`, which is dispatched by `EvmHost.dispatchIncoming` using a low-level `.call()`: [4](#0-3) 

When the app call fails, the host deletes the request receipt "so it can be retried" and returns without reverting the batch — this makes the message perpetually re-deliverable, but it never actually delivers if the failing transfer is deterministic (e.g. beneficiary permanently blacklisted on one output token, or beneficiary is a non-payable contract for the native leg). Because a single order can bundle multiple output assets (`body.tokens` array) for one beneficiary, one poisoned asset in that array blocks the release of every other legitimate asset in the same order — the escrow can never be redeemed or refunded through this path, and `_filled`/order state is never finalized since the whole transaction reverts.

### Impact Explanation
This is a permanent freezing-of-funds bug reachable by any ordinary user placing a cross-chain intent order with multiple output assets. If one of the output tokens is a blacklisting stablecoin and the beneficiary is later blacklisted (or is simply a malicious/broken contract for the ETH leg), the entire order's escrowed value — not just the poisoned asset's share — becomes permanently unrecoverable through the intended settlement path, since every retry of the same request hits the same deterministic revert. This matches "High" impact per the referenced report's rationale: an uncooperative or compromised third party blocks funds due to another party.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires an order with multiple output tokens where at least one has blacklist/censorship semantics (common for USDC/USDT) or a beneficiary contract that reverts on ETH receipt, combined with that beneficiary later becoming blocked/malicious. This mirrors the original report's "Low" likelihood characterization for a similarly conditional trigger.

### Recommendation
Do not let a single failing leg abort the whole settlement. Options:
- Isolate each token transfer with `try/catch` (for external calls) or low-level `call` and, on failure, escrow the failed amount for later separate claim (e.g., push-pull pattern) instead of reverting the entire `_withdraw`.
- Finalize the order state (`_filled`, fee release, events) independent of any single transfer outcome, and expose a per-asset recovery/claim function so a stuck asset does not block the rest.

### Proof of Concept
1. User places a cross-chain order whose output (`body.tokens`) contains two assets: (a) USDC/USDT with amount X, (b) native ETH with amount Y, both destined for `beneficiary`.
2. Before the fill/redeem message is delivered, `beneficiary` is added to the stablecoin issuer's blacklist (or is a contract with no payable `receive`/`fallback` for the ETH leg).
3. A relayer delivers the `RedeemEscrow`/`RefundEscrow` POST request; `EvmHost.dispatchIncoming` invokes `onAccept` → `_withdraw`.
4. The loop reaches the blacklisted/blocked leg, `safeTransfer`/`_sendValue` reverts, unwinding the entire `_withdraw` call including the already-processed successful ETH/token leg.
5. `EvmHost.dispatchIncoming` catches the failed call, deletes the receipt, and returns — the message is "retryable" but every retry fails identically.
6. Both the good and bad assets stay locked in escrow indefinitely; no path exists to redeem the unaffected asset alone.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }
