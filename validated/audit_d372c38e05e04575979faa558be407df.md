## Analysis Result

I found a real analog of the reported bug class in this codebase, but the strength of the finding depends on facts I could not fully verify in the time available (see "Uncertain" note below).

### Title
Team-agnostic-style fallback in `IntentGatewayV2.instance()` lets an unregistered EVM chain masquerade as a legitimate gateway peer - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` resolves a source chain's gateway address for authentication with a silent fallback: if no per-chain instance is registered, it returns `address(this)` instead of reverting. [1](#0-0) 

### Finding Description
`instance()` is the scoped lookup that maps a `stateMachineId` to the registered peer `IntentGatewayV2` deployment address:
```solidity
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    return gateway == address(0) ? address(this) : gateway;
}

function authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    if (instance(request.source) != module) revert Unauthorized();
}
``` [1](#0-0) 

This is exactly the CVE-2026-68872 bug shape: a scoped lookup (`_instances[keccak256(stateMachineId)]`, analogous to the team-scoped Connection/Variable) that, on a miss, silently falls through to a broader/default value (`address(this)`, analogous to the team-agnostic id) rather than rejecting. The equivalent function on the canonical EVM contracts explicitly rejects the unregistered case instead of falling back:
```solidity
function _instance(bytes calldata stateMachineId) internal view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    if (gateway == address(0)) revert UnknownInstance();
    return gateway;
}
``` [2](#0-1) 

Because `IntentGatewayV2` is deployed with the same address across EVM-compatible chains via deterministic (CREATE2-style) deployment, `address(this)` is identical on every chain that runs an instance of this contract. If a state machine (source chain) is *not yet registered* in `_instances` on the destination chain (e.g., a newly supported chain before governance calls whatever sets `_instances`, or any EVM-compatible chain Hyperbridge's consensus clients track but that was never explicitly whitelisted as a "known instance"), then `instance(request.source)` returns `address(this)` on the destination — and any inbound message whose `request.from` equals that same address (which is exactly what a genuine `IntentGatewayV2` deployment on that unregistered chain would set as its own sender address when dispatching) satisfies `instance(request.source) == module`, passing `authenticate()` despite that chain never being registered as a trusted peer.

### Impact Explanation
`authenticate()` is the gate used by `onAccept` before processing `RedeemEscrow`/`RefundEscrow`/other requests that release escrowed input tokens to a solver or refund a user. A forged or unauthorized-chain-originated message that passes this check reaches `withdraw()`, releasing real escrowed funds from the destination-side gateway's balance. This is a concrete path to theft/loss of escrowed order funds without ever having a legitimate, governance-approved instance registered for the originating chain — i.e., forged message delivery/unauthorized app action reachable directly from a relayed ISMP message, which the analog's validation criteria call for.

### Likelihood Explanation
Exploitation requires: (1) an EVM-compatible chain Hyperbridge's consensus clients already track but for which the destination `IntentGatewayV2`'s `_instances` mapping has no entry for that chain's `stateMachineId`, and (2) a genuine (or bytecode-identical) `IntentGatewayV2`/CREATE2 deployment at the same address on that chain. Both conditions plausibly occur in normal chain-onboarding sequencing (a chain can be live under Hyperbridge consensus before its gateway instance is registered), making this reachable by an ordinary relayer/dispatcher path rather than requiring a malicious admin, governance, or node.

### Recommendation
Change `instance()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to revert (e.g., `UnknownInstance`) when no gateway is registered for the given `stateMachineId`, matching the canonical `_instance()` behavior in `evm/src/apps/intentsv2/IntentsBase.sol`, and audit any other callers of `instance()` in the Tron contract for the same self-fallback pattern.

### Proof of Concept
1. Identify (or wait for) an EVM chain that Hyperbridge already tracks under consensus, but for which the target destination `IntentGatewayV2`'s `_instances[keccak256(sourceStateMachineId)]` is unset.
2. Deploy `IntentGatewayV2` at the address matching `address(this)` on the destination (same deployer/salt/bytecode — deterministic deployment is the documented deployment method for this contract family).
3. From that chain, dispatch (or otherwise construct, since the sender address is simply the deploying contract's own address) a `PostRequest` with `source = <that chain>`, `from = <that same address>`, `to = <destination gateway>`, `body` encoding a `RedeemEscrow`/`RefundEscrow` request referencing a real order commitment with outstanding escrow.
4. Relay it through Hyperbridge; on the destination, `authenticate()` computes `instance(request.source) == address(this)` (fallback) `== module`, passes, and `withdraw()` releases escrowed tokens.

**Uncertainty**: I could not verify within the available tool calls (a) whether `evm/tron/contracts/apps/IntentGatewayV2.sol` is actually deployed to a live/production Tron or EVM-compatible network reachable by Hyperbridge's tracked consensus clients (Tron's consensus model differs from EVM, and I did not find a Tron-specific `ConsensusClient` implementation in my searches), (b) how `_instances` entries are actually populated (I found `setInstance`-adjacent references but did not read that setter's full logic or governance gating), and (c) whether some other layer (e.g., a required deployment record / `NewDeployment` request kind) prevents an unregistered chain's messages from ever reaching `onAccept` in practice. These would need to be confirmed before treating this as a confirmed exploitable production issue rather than a code-pattern match to the reported CVE class.
