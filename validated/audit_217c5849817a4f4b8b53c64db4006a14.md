### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop-domain` header when dispatching to the app's handler. Because the `shop` identity is never part of the signed material, an attacker who controls a genuine, validly-signed webhook body (e.g. from their own shop installation of the app) can present it to the app's webhook endpoint with a forged `shop-domain` header, causing the app to process data under the wrong tenant identity.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, and `to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is not included anywhere in the signable string: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which computes `HMAC-SHA256(secret, raw_body)` and compares it to the `hmac` field — again, no header, including `shop`, is part of this computation: [3](#0-2) 

After this check passes, `Registry.process` builds `WebhookMetadata` directly from the unauthenticated `request.shop` header and hands it to the app-registered handler: [4](#0-3) 

This breaks the intended identity binding: `hmac == HMAC(secret, body)` is verified, but the equality that actually matters for tenant isolation — `shop_header == shop_that_produced_this_body` — is never checked. Since the `api_secret_key` is a single per-app secret shared across every shop that installs the app (not shop-specific), any merchant who installs the app receives genuine webhook deliveries with valid HMACs computed from that same shared secret. Such a merchant (an "unprivileged internet user" relative to other tenants of the same app) can capture one of their own legitimately-signed webhook deliveries and replay the identical `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value naming a different merchant's shop. The HMAC check still passes (it only checks the body), and the handler receives `WebhookMetadata` claiming to be from the victim shop.

### Impact Explanation
This is a cross-tenant data confusion vector: any host application that uses `WebhookMetadata#shop` to key persistence, cache invalidation, per-tenant business logic, or to look up/update a tenant's records (a documented and expected usage pattern per the gem's own webhooks documentation) can be made to associate attacker-controlled webhook payloads (order data, product data, GDPR payloads, app-uninstall events, etc., depending on which topics the attacker's shop can generate) with a victim shop's identity. Depending on the handler's use of `shop`, this can range from data corruption to triggering privileged per-tenant actions (e.g., an `app/uninstalled` webhook forged against another shop, or fake `orders/create` data injected into a victim's records) — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on their own (attacker-controlled) shop — a normal, unprivileged action any merchant can take — and be able to send an arbitrary HTTP POST to the app's publicly reachable webhook endpoint with custom headers, which is standard. No access token, `client_secret`, or `api_secret_key` is required; the attacker simply reuses a body/HMAC pair Shopify itself generated for their own shop. The only gating factor is whether the specific webhook topic and payload content are useful for a cross-tenant effect in the host app's handler, but the underlying binding failure in this gem is unconditional.

### Recommendation
Bind the `shop` (and ideally `topic`, `api_version`, `webhook_id`) header values into the HMAC-verified signable material, or otherwise independently verify that the `shop-domain` header corresponds to a shop session/registration the app expects for the given webhook delivery, before constructing `WebhookMetadata` and invoking the handler. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted by host applications without additional verification (e.g., cross-checking against known installed shops).

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com`, obtaining legitimate webhook deliveries signed with the app's shared `api_secret_key`.
2. Attacker captures one such delivery: `raw_body = "{...attacker payload...}"`, `x-shopify-hmac-sha256 = HMAC-SHA256(api_secret_key, raw_body)` (valid, since it was really generated by Shopify for the attacker's shop).
3. Attacker sends a POST to the app's webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged header successfully (headers are only checked for presence, not content) — [5](#0-4)  — and `Registry.process` passes HMAC validation because it only checks `raw_body` — [4](#0-3) .
5. The app handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-controlled `body`, processing it as if Shopify itself sent this data for the victim's shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
