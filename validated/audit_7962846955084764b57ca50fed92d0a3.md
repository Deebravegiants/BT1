The strongest analog to the TrueFi "deposit can revert" pattern is `EvmHost.dispatch()`'s dependency on an external Uniswap V2 pool that Hyperbridge does not control.

### Title
EvmHost native-fee dispatch path can be permanently DoS'd by external Uniswap V2 pool state - (File: evm/src/core/EvmHost.sol)

### Summary
When a user or application dispatches a POST/GET request (or funds an existing one) paying in native token, `EvmHost` unconditionally calls `IUniswapV2Router02.swapETHForExactTokens` to convert the native token into `feeToken`. This call has no fallback and no error handling: if the underlying Uniswap V2 pool for `WETH -> feeToken` becomes illiquid, is drained, or the router/pair otherwise reverts (e.g. `INSUFFICIENT_LIQUIDITY`, `EXCESSIVE_INPUT_AMOUNT`, pool removed), every native-token dispatch on that host reverts, exactly analogous to how TrueFi's `pauseStatus` blocked `tfUSDC.join` and thus `Sherlock.yieldStrategyDeposit`.

### Finding Description
`dispatch(DispatchPost)`, `dispatch(DispatchGet)` and `fundRequest()` in `EvmHost.sol` all follow the same pattern: if `msg.value > 0`, they build a `WETH -> feeToken` path and call `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(...)` with no try/catch and no alternative path. [1](#0-0) [2](#0-1) [3](#0-2) 

`uniswapV2` and the AMM pool it points to are external, third-party-controlled infrastructure — Hyperbridge does not own the Uniswap V2 pair's liquidity, and cannot prevent it from being drained, having its liquidity removed, or otherwise becoming unable to fill the exact-output swap. Just like TrueFi's owner-controlled `pauseStatus` could unilaterally block `TrueFiPool2.join()` and thus `Sherlock.yieldStrategyDeposit()`, any third party (or just organic LP withdrawal) that drains/disables the configured Uniswap V2 pool blocks every native-token-funded dispatch call on the affected `EvmHost` — a core, permissionless, single-transaction entry point reachable by any user.

The only remediation is a governance-driven `SetHostParam` action from the Hyperbridge parachain through `HostManager.onAccept`, which updates `_hostParams.uniswapV2` — a privileged, cross-chain, multi-step action, not something available in the same transaction or to the affected caller. [4](#0-3) 

### Impact Explanation
Native-token dispatch is a primary, documented payment path for `IDispatcher.dispatch` (both POST and GET) and `fundRequest`. [5](#0-4) 
If the configured Uniswap V2 pool cannot service the exact-output swap, this entire payment path is unable to deliver messages — a full DoS on native-fee dispatch for that host until Hyperbridge governance dispatches a `SetHostParam` update to repoint `uniswapV2`. This matches the "route unable to deliver messages" acceptance criterion: the underlying request never gets committed/dispatched, so no cross-chain message can be sent with native-token payment on that chain during the outage.

### Likelihood Explanation
Any user calling `dispatch{value: ...}` or `fundRequest{value: ...}` triggers the vulnerable code path — no special privilege needed to trigger the revert, only an adverse (or malicious, e.g. sandwich/liquidity-drain) external market condition on the Uniswap V2 pool Hyperbridge relies on. Given `swapETHForExactTokens` requires exact-output liquidity and reverts hard on `INSUFFICIENT_LIQUIDITY`/slippage, this is a plausible operational condition, not a contrived edge case, especially for lower-liquidity `feeToken` pairs on smaller EVM chains.

### Recommendation
Wrap the Uniswap V2 swap call in a low-level call with graceful failure handling, or provide fallback logic (e.g., revert with an actionable error distinct from the router's internal revert, or allow callers to pre-approve/pay in `feeToken` if the swap path fails) so that a single external pool's liquidity state cannot indefinitely block the native-payment dispatch path. At minimum, consider gating dispatch to fail fast with a clear custom error, and give governance a lower-friction way (e.g., an admin-settable fallback swap path/slippage tolerance) to react without waiting on a full cross-chain `SetHostParam` round trip.

### Proof of Concept
1. Deploy/operate an `EvmHost` with `uniswapV2` pointing to a Uniswap V2 router whose `WETH/feeToken` pair has thin liquidity.
2. A third party removes liquidity from (or sandwiches) that pair such that `getAmountsIn`/`swapETHForExactTokens` for the requested `fee` output amount reverts (`UniswapV2Library: INSUFFICIENT_LIQUIDITY` or `EXCESSIVE_INPUT_AMOUNT`).
3. Any user calling `EvmHost.dispatch{value: msg.value}(post)` (see [1](#0-0) ) or `fundRequest{value: msg.value}(...)` now has their transaction revert, with no fallback, blocking all native-fee dispatches on the host until governance repoints `uniswapV2` via `HostManager`'s `SetHostParam` action.
