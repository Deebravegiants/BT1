## Title
Webhook `shop`, `topic`, `api_version`, and `webhook_id` fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw HTTP body only, while the identifying fields that `ShopifyAPI::Webhooks::Registry.process` hands to the app's webhook handler — `shop`, `topic`, `api_version`, and `webhook_id` — come straight from HTTP headers that are never included in that signable string. An attacker who can obtain one legitimately-signed `(body, hmac)` pair (e.g., by installing the target app in their own Shopify store and triggering a webhook to themselves) can replay that same body/HMAC to the app's webhook endpoint while forging the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header to name a different, victim shop. `HmacValidator.validate` still passes, and the forged `shop` is delivered to the app's handler as authentic.

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature over `verifiable_query.to_signable_string` and compares it (via `OpenSSL.secure_compare`) to the `hmac` field: [1](#0-0) 

For webhook requests, `to_signable_string` is defined to be only the raw request body: [2](#0-1) 

However, `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from attacker-controllable HTTP headers, none of which participate in the signable string: [3](#0-2) 

`Registry.process` validates only the HMAC over the body, then dispatches the handler using these unauthenticated header-derived fields as if they were verified: [4](#0-3) 

This breaks the intended identity binding: **the shop whose secret produced the HMAC** should equal **the shop the app acts on (`WebhookMetadata#shop`)**. Because the header is outside the signed material, those two values can diverge without invalidating the signature — exactly the "field acted on but not covered by the HMAC" class of defect.

### Impact Explanation
Any merchant who installs the target app in their own store is, from Shopify's perspective, a legitimate but unprivileged source of webhooks for their own tenant only. Such a user can capture a validly-signed `(raw_body, x-shopify-hmac-sha256)` pair generated by Shopify for their own shop, then POST it to the app's webhook receiver with the `x-shopify-shop-domain` header rewritten to a victim shop's domain (and/or `x-shopify-topic` rewritten to a topic they don't legitimately trigger). `Registry.process` accepts it as valid and calls the app's handler with `WebhookMetadata.new(topic: ..., shop: <victim-shop>, body: ..., ...)`, exactly matching the doc-described contract: [5](#0-4) 
Since host applications are expected (and only able, given this gem's API) to trust `shop`/`topic` from `WebhookMetadata` as verified, this enables cross-tenant data injection/confusion — attacker-authored webhook content is processed and attributed to a victim shop's tenant. This meets the "cross-tenant access" bar for a valid High/Critical-class finding.

### Likelihood Explanation
Exploitation requires only: (1) the attacker be a merchant with the app installed on their own store (an unprivileged, self-serve action available to any internet user via the Shopify app install flow), and (2) knowledge of the victim's `myshopify.com` domain, which is public. No access token, `client_secret`, or privileged account is required — only the gem's own signature-verification logic, which fails to bind the header fields it exposes to handlers.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` (or at minimum `shop` and `topic`) in the value that is HMAC-verified for webhook requests, or otherwise cryptographically bind them to the signed body (e.g., signing a canonical string of `header-values + body` similar to how `AuthQuery#to_signable_string` binds `shop` into its signed parameters: [6](#0-5) ). At minimum, document prominently that these header-derived `Request`/`WebhookMetadata` fields are unauthenticated and must not be trusted for tenant identification without additional out-of-band verification.

### Proof of Concept
1. Attacker signs up for a Shopify dev/trial store `attacker.myshopify.com` and installs the target app.
2. Attacker triggers any webhook topic registered by the app (e.g., `orders/create`) on their own store, capturing the raw POST body and the genuine `x-shopify-hmac-sha256` header Shopify computed with the app's real `client_secret`.
3. Attacker replays this exact `(raw_body, x-shopify-hmac-sha256)` pair to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and adjusts `x-shopify-topic`/`x-shopify-webhook-id` if desired).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the HMAC — this still passes because the body is unmodified: [7](#0-6) 
5. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-supplied body content, believing it originated from the victim.
