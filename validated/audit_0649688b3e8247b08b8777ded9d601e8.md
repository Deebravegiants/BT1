### Title
`_getOraclePrice()` lacks Chainlink min/max circuit-breaker price bound checks, allowing stale-crash-price manipulation of gas fee charges - ([File: evm/src/utils/SimplexPaymaster.sol])

### Summary
`SimplexPaymaster._getOraclePrice()` only validates that the Chainlink `answer` is positive and not stale, but never checks it against the aggregator's `minAnswer`/`maxAnswer` bounds. If an underlying asset (native gas token or a registered ERC-20 fee token) crashes or depegs past the feed's configured price bounds, Chainlink's aggregator continues to report the clamped `minAnswer` (a stale, inflated-relative-to-market price) instead of reverting, exactly the class of issue described in the referenced report.

### Finding Description
`_getOraclePrice()` is the sole price-validation gate used for every gas-fee/token-price computation in the paymaster: [1](#0-0) 

It checks `answer <= 0` and staleness via `updatedAt`, but performs no comparison against the aggregator's circuit-breaker bounds (`minAnswer`/`maxAnswer`). When a Chainlink feed's underlying market price crashes below `minAnswer` (or spikes above `maxAnswer`), the aggregator's `latestRoundData()` keeps returning the clamped bound value with a fresh `updatedAt` timestamp, so this check passes even though the reported price no longer reflects the real market price.

This price feeds directly into `_tokenPrice()`, which is used by `_fetchDetails()` (called during `_validatePaymasterUserOp` for every UserOp) to compute how many token units are charged per unit of gas, and by `swapAndDeposit()` to compute the minimum acceptable swap output: [2](#0-1) [3](#0-2) 

Any unprivileged bundler/user submitting an ERC-4337 UserOp through this paymaster reaches `_fetchDetails` → `_tokenPrice` → `_getOraclePrice`, so this is reachable from a completely permissionless entry point (any UserOp using the paymaster), matching the "single submitted transaction" reachability bar.

### Impact Explanation
If `nativeOracle` or a registered token's oracle clamps at `minAnswer`/`maxAnswer` during a crash/depeg, `_tokenPrice()` returns a stale, mispriced ratio. Depending on which side is clamped:
- Users could be overcharged in the ERC-20 fee token relative to actual gas value (fund loss for users), or
- Users could be undercharged, letting the paymaster's native EntryPoint deposit drain faster than fee-token revenue replenishes it (fund loss/insolvency for the paymaster treasury).

The treasury-gated `swapAndDeposit()` also derives its `amountOutMin` slippage floor directly from the same unclamped oracle values, so a clamped price additionally skews the swap execution price used when recycling collected fees into native gas.

### Likelihood Explanation
Likelihood is tied to a real-world asset depeg/crash event of a registered fee token or the native asset feed (e.g., a stablecoin depeg or a LUNA-style native-asset collapse) — not attacker-controlled directly, but requires no special privilege to trigger the exploitable state, and any UserOp sender automatically inherits the mispriced rate once the feed is clamped.

### Recommendation
In `_getOraclePrice()`, fetch `minAnswer`/`maxAnswer` from the aggregator (via `AggregatorV2V3Interface`/direct aggregator lookup, since `answer` bounds aren't exposed on the standard `AggregatorV3Interface` — this typically requires querying the underlying `aggregator()` contract) and revert if `answer <= minAnswer || answer >= maxAnswer`, in addition to the existing positivity and staleness checks.

### Proof of Concept
1. Governance registers a token whose Chainlink feed has `minAnswer = X`.
2. The token's real market price crashes below the equivalent of `X`; Chainlink's aggregator clamps and continues returning `answer = X` with `updatedAt = block.timestamp` (satisfies both current checks).
3. `_getOraclePrice()` returns `X` as if it were the live price.
4. `_tokenPrice()` computes a distorted `tokenPrice`, and any subsequent UserOp's `_fetchDetails()`/`_prefund()` charges the user based on this stale clamped price instead of reverting, as demonstrated by the existing staleness/positivity test pattern in [4](#0-3)  which shows only staleness and non-positive-answer paths are tested — no min/max bound test exists.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
