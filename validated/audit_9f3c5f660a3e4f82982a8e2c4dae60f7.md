Audit Report

## Title
Missing slippage protection in `SwapFirstAssetTrader::refund_weight` allows sandwiching of XCM fee-swap refunds - (File: `cumulus/primitives/utility/src/lib.rs`)

## Summary
`SwapFirstAssetTrader::refund_weight` calls `SwapCredit::swap_exact_tokens_for_tokens(vec![Target::get(), refund_swap_asset], refund, None)` with `amount_out_min` hard-coded to `None`, disabling `pallet_asset_conversion`'s `ProvidedMinimumNotSufficientForSwap` slippage check on the refund path. This is asymmetric with `buy_weight`, which is inherently bounded because it uses `swap_tokens_for_exact_tokens` with an exact output amount.

## Finding Description
`buy_weight` swaps the user's supplied asset into `Target` via `swap_tokens_for_exact_tokens(vec![swap_asset, Target::get()], credit_in, fee)`, where `fee` is the exact output requested — this path is self-bounding since the caller specifies the exact amount of `Target` to receive [3](#0-2) . In contrast, `refund_weight` swaps the leftover `Target` back to the original asset via `swap_exact_tokens_for_tokens` with `amount_out_min` set to `None` [4](#0-3) . In `pallet_asset_conversion::do_swap_exact_tokens_for_tokens`, the `ProvidedMinimumNotSufficientForSwap` check is entirely skipped when `amount_out_min` is `None` [2](#0-1) , meaning the refund swap accepts any resulting output amount, however unfavorable, executing against whatever the constant-product AMM price is at that moment.

## Impact Explanation
Since Substrate/Cumulus block authors (collators) control intra-block extrinsic ordering, a malicious or MEV-motivated collator could place price-moving swap/liquidity extrinsics against the same `Target`/`refund_swap_asset` pool immediately before the XCM-executing extrinsic that triggers `refund_weight`, causing the refund to execute at a manipulated, unfavorable price, then reverse the price move afterward to capture the difference. This is a genuine, code-verified logic flaw producing value extraction from the XCM sender's fee refund, matching an in-scope "unbounded slippage in an on-chain swap" impact category.

## Likelihood Explanation
`SwapFirstAssetTrader` is confirmed wired into live runtime configs (Asset Hub Westend, Asset Hub Rococo, Penpal, staking-async parachain), not just test mocks, so the code path is reachable in production whenever XCM messages pay fees via this trader in a non-`Target` asset and over-provision `BuyExecution` weight relative to actual consumption — a routine occurrence. Exploitation requires the ability to control extrinsic ordering within a block (collator) or race with the refund transaction/same-block swaps against a pool with limited liquidity, which is a realistic, moderate-capability threat model (not requiring privileged/admin access), though it does require the target pool to have exploitable liquidity depth and the attacker to be a block author or win an ordering race.

## Recommendation
Do not pass `None` for `amount_out_min` in `SwapFirstAssetTrader::refund_weight`. Compute a reasonable minimum acceptable output—e.g., via `QuotePrice::quote_price_exact_tokens_for_tokens` at refund time with a configurable slippage tolerance—and pass `Some(min_amount)`, mirroring the implicit protection on the `buy_weight` path. If a safe minimum cannot be computed, prefer skipping the refund swap (keep the excess in `Target`) rather than executing at an unbounded price.

## Proof of Concept
1. Configure a runtime (e.g., mirroring `asset-hub-westend`'s XCM config) with `SwapFirstAssetTrader` backed by a `pallet_asset_conversion` pool for `Target`/`OtherAsset` with limited liquidity.
2. Submit an XCM message with `BuyExecution` paying in `OtherAsset`, over-provisioning weight relative to actual program execution weight.
3. `buy_weight` swaps `OtherAsset` → `Target` for the exact `fee` amount (bounded by design).
4. In the same block, before the `refund_weight` step executes (via collator ordering control or a race), submit a large `swap_tokens_for_exact_tokens`/`add_liquidity` operation to move the pool price against `Target` → `OtherAsset` conversion.
5. `refund_weight` executes `swap_exact_tokens_for_tokens(vec![Target, OtherAsset], refund, None)`; since `amount_out_min` is `None`, the swap succeeds at the manipulated price instead of reverting via `ProvidedMinimumNotSufficientForSwap`.
6. Observe the user receiving a refund below the pre-manipulation fair quote, while the attacker profits by reversing the price-moving swap afterward.
