Audit Report

## Title
Signed unix timestamp field is converted to `uint` without bounds checking, allowing bypass of the gateway's stale-message check - ([File: core/services/gateway/handlers/capabilities/handler.go])

## Summary
`HandleLegacyUserMessage` validates message freshness by checking `payload.Timestamp == 0` and then computing `uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp)`. Because `payload.Timestamp` is a signed `int64` fully controlled by the message sender, and both sides of the comparison are converted to `uint`, a negative timestamp wraps to a huge unsigned value, unconditionally passing the freshness check and completely bypassing the staleness gate.

## Finding Description
The code at `core/services/gateway/handlers/capabilities/handler.go` (around lines 341-421) unmarshals the attacker-controlled JSON body into `webapicap.TriggerRequestPayload`, whose `Timestamp` field is an `int64`. The only validation performed is `if payload.Timestamp == 0 { ... }`, which rejects only the exact value zero. The staleness check that follows, [1](#0-0) 
converts `payload.Timestamp` directly to `uint`. For a negative value like `-1`, `uint(payload.Timestamp)` becomes `math.MaxUint64` (or `MaxUint32` on 32-bit builds), which is always greater than `uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec`, so the "stale message" branch is never taken and the message flows through unimpeded.

Downstream, `common.ValidatedRequestFromMessage` (`core/services/gateway/handlers/common/message_util.go`, lines 82-105) only validates that `MessageID`, `Method` are non-empty and re-marshals the message — it performs no independent timestamp/staleness re-validation: [2](#0-1) 
After that, the message is forwarded to all DON members via `don.SendToNode`, confirming the staleness check is the sole gate against old/malformed timestamps before dispatch: [3](#0-2) 

This matches the code exactly as cited in the claim, and I was unable to find any other timestamp validation in `msg.Validate()`/`msg.Sign()` (in `core/services/gateway/api/message.go`) that would independently reject negative or out-of-bounds timestamps before reaching this handler — the signature only proves the message body wasn't tampered with, not that the timestamp value is sane.

## Impact Explanation
This is a genuine logic bug: the staleness/freshness check can be trivially and unconditionally bypassed by supplying any negative `Timestamp`. However, the actual security impact is limited. The staleness check's purpose is only to reject old (potentially replayed) `web_api_trigger` messages before forwarding them to DON members; bypassing it does not grant authentication bypass, key/secret exfiltration, unauthorized fund movement, or allowlist bypass by itself — it only means a message with a nonsensical/negative timestamp is forwarded instead of rejected. The downstream capability/DON processing (e.g., `webapicap` trigger handling on the node side) is what would ultimately act on the message, and there is no evidence in the reachable code that a negative timestamp causes any further miscalculation, cache poisoning, cross-user response corruption, or unauthorized action — the observed effect is limited to skipping one input-validation branch on an already externally-reachable, signed message path (note: signature/allowlist enforcement for this specific method appears to still be a `TODO` at line 384, `// TODO: apply allowlist and rate-limiting here`, indicating unrestricted forwarding is already an accepted/expected state at this point of the codebase regardless of this bug).

## Likelihood Explanation
Any client capable of sending a `web_api_trigger` message to the gateway can trigger this with a single crafted request (negative `Timestamp` value); no special precondition beyond normal message construction is required. This part of the claim is accurate and trivially reproducible.

## Recommendation
- Validate `payload.Timestamp` is non-negative and within a sane bounded range before use.
- Perform the staleness comparison in signed 64-bit arithmetic instead of converting to `uint`, e.g., `age := time.Now().Unix() - payload.Timestamp; if age < 0 || age > int64(h.config.MaxAllowedMessageAgeSec) { reject }`.
- Remove the `//nolint:gosec // G115` suppression once fixed.

## Proof of Concept
1. Craft a `web_api_trigger` message with `webapicap.TriggerRequestPayload{Timestamp: -1, ...}`, sign it per the normal message-signing flow, and send it to the gateway's `HandleLegacyUserMessage` entry point.
2. Observe `payload.Timestamp == 0` is false, so execution proceeds.
3. `uint(payload.Timestamp)` evaluates to `math.MaxUint64`, so `uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp)` is false, and the "stale message" branch is skipped.
4. The message is forwarded to all DON members via `don.SendToNode`, confirming the staleness check was bypassed.

A Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go` constructing such a payload and asserting `HandleLegacyUserMessage` does not return the "stale message" error would concretely demonstrate this.

// ValidatedRequestFromMessage converts a legacy Gateway Message to a JSON-RPC request
func ValidatedRequestFromMessage(msg *api.Message) (*jsonrpc.Request[json.RawMessage], error) {
	if msg == nil {
		return nil, errors.New("nil message")
	}
	if msg.Body.MessageID == "" {
		return nil, errors.New("message ID is empty")
	}
	if msg.Body.Method == "" {
		return nil, errors.New("method is empty")
	}
	params, err := json.Marshal(msg)
	if err != nil {
		return nil, fmt.Errorf("failed to marshal message: %w", err)
	}
	rawParams := json.RawMessage(params)
	req := &jsonrpc.Request[json.RawMessage]{
		Version: "2.0",
		ID:      msg.Body.MessageID,
		Method:  msg.Body.Method,
		Params:  &rawParams,
	}
	return req, nil
}
