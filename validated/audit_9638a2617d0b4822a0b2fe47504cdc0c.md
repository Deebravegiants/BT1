### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only. The `shop` (and `topic`/`webhook-id`/`api-version`) values are taken from unauthenticated HTTP headers and are never bound into the signature that `Utils::HmacValidator` checks.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC(api_secret_key, verifiable_query.to_signable_string)` and compares it to the `hmac` supplied by the caller (`lib/shopify_api/utils/hmac_validator.rb:26-31`). For webhook requests, `to_signable_string` returns `@raw_body` alone (`lib/shopify_api/webhooks/request.rb:35-38`). Meanwhile `Request#shop` is read straight from the `x-shopify-shop-domain` header without any cryptographic binding (`lib/shopify_api/webhooks/request.rb:20-23`).

`Registry.process` treats a passing HMAC check as proof the *entire request*, including `request.shop`, is authentic from Shopify, and forwards it unchanged to the app's handler:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
```
(`lib/shopify_api/webhooks/registry.rb:188-199`)

Since a Shopify app's `api_secret_key` is shared across every shop that installs the app, any legitimately installed (unprivileged) merchant can trigger a real webhook delivery for their *own* store and obtain a genuinely valid `(raw_body, hmac)` pair. Because `shop` is excluded from the signed content, that same `(raw_body, hmac)` pair remains valid when replayed with an attacker-chosen `x-shopify-shop-domain` header value (e.g., a victim shop's domain). The equality the code implicitly assumes — `shop_that_produced_the_body_and_hmac == shop_header_delivered_to_the_handler` — is never enforced.

### Impact Explanation
This breaks the tenant boundary the webhook handler relies on: an app's webhook handler will process attacker-controlled `body` content while believing it originates from an arbitrary victim shop (`WebhookMetadata#shop`). Depending on how the host application uses `data.shop` (e.g., to look up/update per-shop records, to key data ingestion, or to grant behavior tied to the shop), this enables cross-tenant data injection/corruption using only a webhook subscription on the attacker's own shop — no access token or leaked credential required. This matches the "cross-tenant access" Critical impact category, since the gem's own signature-verification logic (`HmacValidator`/`Registry.process`) is what fails to bind the tenant identifier.

### Likelihood Explanation
Any entity that can install the public app on their own store (unprivileged relative to other merchants) can trigger a webhook for a topic the app subscribes to, capture the resulting `(raw_body, x-shopify-hmac-sha256)` pair, and replay it to the app's webhook endpoint with a forged `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) header. No secret material beyond what Shopify already sent them is required.

### Recommendation
Bind the tenant/shop (and ideally topic and webhook id) into the HMAC-covered material, or otherwise verify `request.shop` against a value that is itself authenticated (e.g., cross-check against the shop associated with a known/stored session for that webhook subscription) before trusting it in `WebhookMetadata`. At minimum, document that consumers of `WebhookMetadata#shop` must not rely on it as an authenticated tenant identifier unless additional out-of-band verification (e.g., comparing against the shop for which the specific webhook topic/id was registered) is performed.

### Proof of Concept
1. Install the target app (or a similarly configured app using this gem) as a low-privilege attacker on `attacker-shop.myshopify.com`, and subscribe to a webhook topic the app handles (e.g., `orders/create`).
2. Trigger the topic to receive a genuine Shopify-delivered POST containing `raw_body` and header `x-shopify-hmac-sha256: <valid hmac for raw_body>`.
3. Replay that exact `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` still returns `true` because `to_signable_string` only checks `raw_body`. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)`, causing the app to act on forged data attributed to the victim shop.
