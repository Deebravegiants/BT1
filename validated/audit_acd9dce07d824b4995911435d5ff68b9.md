### Title
Emporium "erc20TokenAddresses.length == 0" path lets an EOA drain ETH from the Emporium contract with zero balance/UTXO accounting - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`, `contracts/CircomDataBuilder.sol`)

### Summary
`CircomDataBuilder.formInputForCircom` contains a special "min" branch that is taken whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `circomData.erc20TokenAddresses.length == 0`: [1](#0-0) 

In that case the SNARK public input reduces to `emporiumMessage`, `timeStamp`, `calldataHash` only — none of the balance-changing fields (`amountChanges`, `inputNullifiers`, `outCommitments`, `erc20TokenAddresses`) are part of the proof at all, and `dimensions.tokenNumber` is checked only for internal array-length consistency, not against any real token accounting: [2](#0-1) 

Because `circomData.erc20TokenAddresses` has length 0, every balance-equation loop that is supposed to enforce "value moved == value proven by the circuit" degenerates to a no-op:
- The top-level solvency check in `Hinkal.transact` (`for (uint64 i; i < circomData.erc20TokenAddresses.length; i++)`) never executes. [3](#0-2) 
- The Emporium-internal solvency check in `EmporiumUpgradeable.runAction` (`for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++)`) also never executes. [4](#0-3) 

Yet the operation loop that actually moves value is *not* gated by that array at all — it iterates over attacker-supplied `stack.ops` decoded from `externalActionMetadata` and, for stateless ops, performs a raw call with attacker-chosen `op.value` in ETH: [5](#0-4) 

### Finding Description
The Hinkal balance invariant is: *"CHANGE IN BALANCE SHOULD EQUAL TO (1) change in off-chain utxos + (2) change in on-chain utxos"*, enforced token-by-token over `circomData.erc20TokenAddresses`. This is exactly analogous to the report's bug class: "value moved by Hinkal or an external action but not counted in the balance equation."

When a user submits an Emporium transaction with `dimensions.tokenNumber == 0` (hence `circomData.erc20TokenAddresses = []`), the ZK proof no longer asserts anything about token movement — the min-input branch drops `amountChanges`, `inputNullifiers`, and `outCommitments` from the public input vector entirely. `dimensionsCheck` only verifies that the various array lengths are mutually consistent (all length 0), not that they correspond to any real UTXO spend. `performHinkalChecks` calls `getHashedCalldata`/`calldataHash` only for self-consistency of the caller's own submitted data — it does not force `erc20TokenAddresses` to include ETH.

`EmporiumUpgradeable.runAction` is reached from `Hinkal.sol` via `_externalTransact` for any `externalActionId != 0`, and is restricted only by `onlyAllowedRecipient` (i.e., that Emporium is a registered external action, not that the ops inside `stack` are constrained). Inside `runAction`, for `CASE 2: Stateless Interaction`, the attacker fully controls `op.endpoint` and `op.value`, and the contract performs:
```solidity
(success, err) = op.endpoint.call{value: op.value}(op.callData);
```
with no requirement that the caller be `stack.signerAddress`-authorized (that check only applies to `CASE 1`, `invokeWallet` path via `IHinkalWallet`). With `erc20TokenAddresses.length == 0`, the post-loop balance check (`balancesBefore`/`balancesAfter` over `circomData.erc20TokenAddresses`) is an empty loop and therefore cannot detect or reject any ETH outflow caused by these ops.

Since Emporium acts as shared custody for many users' shielded balances (users deposit ETH/tokens into Emporium backing their private UTXOs, later spent via proofs), any ETH sitting in the Emporium contract's balance from other users' deposits can be swept out by an attacker who crafts `EmporiumOperation[]` with `invokeWallet=false`, an arbitrary `endpoint` (e.g., the attacker's own address or a trivial receiver), and `value` equal to the contract's ETH balance — without ever proving ownership of that ETH via nullifiers/UTXOs, and without the top-level or Emporium-level balance equations ever running to catch the discrepancy.

### Impact Explanation
This breaks the core solvency invariant of the protocol: it allows unbacked withdrawal of ETH held in the Emporium contract that backs other users' private shielded balances — i.e., theft of shielded user funds with no corresponding nullifier consumption. This matches the "Critical" impact bucket: direct theft of shielded funds / proof verification bypass of the balance equation, since the SNARK never actually constrains the moved value in this code path.

### Likelihood Explanation
The attack requires only:
1. A user-generated proof for the trivial `tokenNumber = 0` Emporium dimension (which exists as a first-class, explicitly supported path — `formInputEmporiumMin` — not an edge case that needs special circuit tampering).
2. Crafting `externalActionMetadata` to decode into an `EmporiumStack` with a stateless op (`invokeWallet=false`) pointing at an attacker-controlled or trivial endpoint with `value` equal to the drainable ETH balance.

No admin, relayer, or third-party key is required; this is fully reachable by any unprivileged EOA that can call `Hinkal.transact` with a self-generated, otherwise-valid proof. The main uncertainty (not verifiable from the indexed context) is whether the verifier contract selected via `buildVerifierId` for `tokenNumber=0`/Emporium actually accepts a trivially-satisfiable circuit instance (e.g., requiring only a valid EdDSA signature over `emporiumMessage`) — if such a minimal verifier is deployed and registered, the exploit is directly executable; this should be confirmed against the deployed verifier/circuit-selection mapping, which wasn't fully enumerable from the available index.

### Recommendation
- Do not allow the balance-equation loops (`Hinkal.sol` lines ~96-146, `EmporiumUpgradeable.runAction` lines ~122-151) to be silently skipped when `erc20TokenAddresses.length == 0`.
- Either forbid the `formInputEmporiumMin` / zero-token-number path from being combined with any op that carries non-zero `op.value` or performs token transfers, or force ETH (`address(0)`) and every token touched by `stack.ops` to be included in `circomData.erc20TokenAddresses` so it is captured by both balance checks and constrained by the SNARK.
- Add an explicit invariant check in `EmporiumUpgradeable.runAction` that the Emporium's ETH/token balance never decreases beyond what is accounted for by `deltaAmountChanges`/UTXO output, independent of `erc20TokenAddresses.length`.

### Proof of Concept
1. Attacker deposits a negligible amount (or nothing) and obtains a valid proof for an Emporium transaction with `dimensions.tokenNumber = 0`, so `circomData.erc20TokenAddresses = []` and `formInputEmporiumMin` is used [6](#0-5) .
2. Attacker encodes `externalActionData.externalActionMetadata` as an `EmporiumStack` with one `EmporiumOperation{invokeWallet: false, endpoint: attackerAddr, value: address(Emporium).balance, callData: ""}`.
3. Attacker calls `Hinkal.transact(...)` with `circomData.externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`.
4. `Hinkal.sol` verifies the (weak) proof, calls `_externalTransact` → `EmporiumUpgradeable.runAction`, which executes `op.endpoint.call{value: op.value}(op.callData)`, sending all of Emporium's ETH to the attacker [7](#0-6) .
5. Both the Emporium-internal and `Hinkal.sol` top-level balance checks iterate 0 times (empty `erc20TokenAddresses`) and never revert [8](#0-7) [3](#0-2) .

    function formInputForCircom(
        uint256 chainId,
        address verifyingContract,
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory) {
        if (
            circomData.externalActionData.externalActionId ==
            HINKAL_EMPORIUM_ACTION_ID &&
            circomData.erc20TokenAddresses.length == 0
        ) {
            return formInputEmporiumMin(circomData);
        } else {
            return formInputNormal(chainId, verifyingContract, circomData);
        }
    }

    function formInputEmporiumMin(
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory input) {
        input = new uint256[](circomData.publicSignalCount);

        uint16 index = 0;

        input[index++] = circomData.emporiumMessage;

        input[index++] = circomData.timeStamp;
        input[index++] = circomData.calldataHash;
    }
