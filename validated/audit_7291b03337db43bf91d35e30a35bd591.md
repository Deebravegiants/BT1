## Title
Webhook shop-domain header is trusted without being covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

## Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as verified once the HMAC check passes, but the HMAC is computed only over the raw body, never over the `shop-domain` (or `topic`/`webhook-id`) header. `Registry.process` then forwards the unauthenticated `shop` header straight to the app's handler as the tenant identity. This breaks the binding `shop_covered_by_hmac == shop_used_for_tenant_dispatch`: the left side doesn't exist at all, and the right side is attacker-controlled.

## Finding Description
`Utils::HmacValidator.validate` is invoked in `Registry.process`: [1](#0-0) 

The HMAC validation calls into `Request#to_signable_string`, which returns only the raw body: [2](#0-1) 

Meanwhile `Request#shop` is read directly from the `shop-domain`/`x-shopify-shop-domain` HTTP header with no cryptographic binding to the signed payload: [3](#0-2) 

After the HMAC check succeeds, `Registry.process` builds `WebhookMetadata` using this unauthenticated `request.shop` value and dispatches it to the app-provided handler, which the docs explicitly tell developers to key their tenant logic on: [4](#0-3) 

The gem's own documentation overstates the guarantee, claiming the HMAC check "will verify the request did indeed come from Shopify" and instructing handler authors to use `data.shop` as the tenant/shop identifier for their app logic (e.g. `shop_domain: data.shop`), without any caveat that `shop` is unauthenticated: [5](#0-4) [6](#0-5) 

Because the `api_secret_key` is shared across every shop that installs a given app, any unprivileged user can install the app on their own (even free/dev) store and legitimately receive a webhook with a valid `hmac-sha256` value for a known raw body. That attacker can then replay the exact same body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim merchant's domain. `Registry.process` will accept it as valid (the body's HMAC still matches) and hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

## Impact Explanation
This is a cross-tenant identity-binding failure: the shop identity the app acts on (`data.shop`) is never covered by the cryptographic check that is supposed to authenticate the message. Any app that keys per-shop side effects (data writes, cache/session lookups, enqueuing jobs "for shop X") off `WebhookMetadata#shop` — exactly as the gem's own documentation instructs — can be made to process attacker-supplied webhook bodies under a victim shop's identity. This matches the Critical "cross-tenant access" category.

## Likelihood Explanation
Requires only: (1) ability to install the app on any store (any unprivileged Shopify Partner/dev store, which is free and does not require any privileged credential belonging to the app or the victim), (2) capturing one legitimate raw_body + HMAC pair delivered to the attacker's own webhook endpoint, and (3) replaying it with a modified shop-domain header to the app's public webhook URL. No `api_secret_key`, access token, or victim credentials are needed.

## Recommendation
Bind the shop (and topic/webhook-id) into the value that is actually authenticated — e.g., require the app to cross-check `request.shop` against a shop known from an existing, independently-authenticated session/webhook subscription record before dispatch, or have `Registry.process` reject processing unless the `shop` header corresponds to a shop for which a registration/session is known, rather than passing an arbitrary caller-supplied header straight into the trusted `WebhookMetadata`. At minimum, update `HmacValidator`/`Request#to_signable_string` and the documentation to make clear the `shop` header is unauthenticated so apps do not rely on it alone as a tenant boundary.

## Proof of Concept
```ruby
# 1. Attacker installs the target app on their own dev shop, gets a legitimate webhook:
headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => "<valid hmac for raw_body computed with the app's shared api_secret_key>",
  "x-shopify-shop-domain"  => "attacker-shop.myshopify.com",
  "x-shopify-webhook-id"   => "b1234-...",
  "x-shopify-api-version"  => "2024-01",
}
raw_body = '{"id":1,"note":"attacker controlled"}'

# 2. Attacker replays the SAME raw_body + hmac to the app's public webhook endpoint,
#    but swaps only the shop-domain header:
forged_headers = headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC check passes (it only checks raw_body), handler is invoked with
#    WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker-controlled JSON)
```
`Registry.process` never validates that `victim-shop.myshopify.com` corresponds to the shop that actually sent the request; only `raw_body` is checked against the HMAC. [1](#0-0) [7](#0-6)

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
