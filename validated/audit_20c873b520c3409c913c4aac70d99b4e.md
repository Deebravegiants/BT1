### Title
`WrappedHyperFungibleToken.send()` locks nominal `params.amount` without verifying actual tokens received, letting fee-on-transfer/deflationary underlying tokens make the escrow insolvent - ([File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol])

### Summary
`WrappedHyperFungibleToken.send()` pulls `params.amount` of the underlying ERC20 via `safeTransferFrom` and then dispatches a cross-chain `Message` whose `amount` field is the caller-supplied `params.amount`, not the amount actually received by the contract. For a fee-on-transfer/rebasing/deflationary underlying token, the contract's real balance increases by less than `params.amount`, yet the destination chain mints (via `HyperFungibleToken.onAccept`) or a return-trip `onAccept` unlocks the full nominal amount. This is the same accounting-vs-actual-balance divergence flagged in the original Masset/mAsset report: internal bookkeeping (the amount promised/dispatched) is not reconciled against the real custodied balance.

### Finding Description
In `send()`:
```solidity
} else {
    IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
}

DispatchPost memory request = _buildDispatchPost(params);
``` [1](#0-0) 

`_buildDispatchPost`/message construction uses `params.amount` verbatim (analogous pattern shown in the upgradeable variant): [2](#0-1) 

No before/after `balanceOf` check is performed, unlike `IntentGatewayV2.placeOrder`, which explicitly measures actual received tokens for fee-on-transfer assets and mutates `order.inputs[i].amount` to the real received amount before computing the commitment/escrow: [3](#0-2) 

On the unlock/receive side, `onAccept` transfers the fixed `message.amount` (the nominal, unadjusted amount) out of the contract's real balance:
```solidity
IERC20(_underlying).safeTransfer(beneficiary, message.amount);
``` [4](#0-3) 

Because the lock side never reconciles the escrow's internal notion of "amount owed to be minted/unlocked elsewhere" with the actual token balance received, a deflationary underlying token causes the contract's real balance to fall permanently behind the cumulative amount it has promised across all outstanding cross-chain sends. This mirrors the audited mAsset bug: `Masset._mintTo` credited the vault based on the nominal deposit amount rather than the integration's actual balance increase, causing vault accounting to exceed the real custodied balance in the lending pool.

### Impact Explanation
Every `send()` on a fee-charging/deflationary underlying token silently under-collateralizes the wrapper by the fee amount, while the destination side unconditionally mints/unlocks the full nominal amount. As sends accumulate, the wrapper's actual token balance is insufficient to satisfy all outstanding "unlock" or return-trip transfers. This leads to:
- Later, legitimate return-trip unlocks reverting (transfer to a beneficiary fails because `balanceOf(this) < message.amount`), freezing those users' bridged funds permanently at the ISMP relay layer (a route that cannot deliver messages), and/or
- An effective unbacked over-mint on the remote `HyperFungibleToken`, since more tokens are minted on the destination than were actually escrowed on the home chain, breaking the "supply always backed by locked balance" invariant advertised for this token model.

This is a Medium/High severity accounting-integrity bug reachable by any unprivileged user simply calling `send()` on a wrapper configured (by the token deployer, not by a malicious admin of Hyperbridge) around any real-world deflationary/fee-on-transfer/rebasing ERC20 — a legitimate and foreseeable deployment configuration, not a malicious-admin scenario.

### Likelihood Explanation
Likelihood is moderate: it requires the underlying token to be fee-on-transfer or otherwise non-1:1 on transfer (a known real-world token category, e.g. deflationary/reflection tokens, and some tokens with switchable transfer fees). No malicious actor or governance compromise is required — a single ordinary `send()` call by any user triggers the divergence, and repeated use compounds the shortfall until an unlock fails.

### Recommendation
Mirror the fix already applied in `IntentGatewayV2.placeOrder`: measure the wrapper's actual token balance before and after `safeTransferFrom`, and use the measured `received` amount (not `params.amount`) both for the dispatched cross-chain `Message.amount` and any commitment/accounting derived from it. If `received < params.amount`, either reduce the message amount accordingly or revert if partial receipt is disallowed, so the amount promised on the destination chain never exceeds the amount actually collateralized on the source chain.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` with `underlying` set to an ERC20 that charges, e.g., a 1% fee on transfer (identical semantics to the `FeeOnTransferToken` test helper already used elsewhere in the test suite: [5](#0-4) ).
2. User calls `send({amount: 1000e18, to: recipient, dest: remoteChain, ...})`. `safeTransferFrom` only delivers 990e18 to the wrapper, but the dispatched `Message.amount` is 1000e18.
3. Remote `HyperFungibleToken.onAccept` mints 1000e18 to the recipient — 10e18 more than what is actually escrowed on the home chain.
4. Repeat sends accumulate a growing shortfall; the wrapper's real `_underlying` balance is less than the sum of all amounts it has promised via dispatched messages.
5. When a later return-trip `onAccept` (unlock) attempts `IERC20(_underlying).safeTransfer(beneficiary, message.amount)` for the full nominal amount, it reverts once the shortfall exceeds the remaining balance, freezing that user's funds; alternatively, on the remote chain, the excess minted supply is never backed, breaking the 1:1 backing invariant documented for the HFT design (`// BRIDGE is native to nexus... the supply of this token is always backed by the pallet's escrow account.` analog): [6](#0-5) .

    function _buildDispatchPost(HyperFungibleTokenUpgradeable.SendParams calldata params)
        internal
        view
        returns (DispatchPost memory)
    {
        bytes memory dest = _supportedChains[params.dest];
        if (dest.length == 0) revert UnsupportedChain();

        bytes memory body = abi.encode(
            HyperFungibleTokenUpgradeable.Message({
                from: abi.encodePacked(msg.sender),
                to: params.to,
                amount: params.amount,
                data: params.data
            })
        );

        return DispatchPost({
            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,
            payer: msg.sender
        });
    }
