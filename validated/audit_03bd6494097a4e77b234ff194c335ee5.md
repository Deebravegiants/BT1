## Title
Webhook shop-domain identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` value that is subsequently handed to the app's webhook handler is taken from an HTTP header that is never included in that signature. This breaks the intended binding "shop used by the handler == shop authenticated by the HMAC," letting a party who controls a legitimately-signed webhook body (from any shop where the app is installed) relabel it as belonging to a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` compute/verify the HMAC exclusively over `@raw_body`: [1](#0-0) [2](#0-1) 

The `shop` (and `topic`, `webhook_id`, `api_version`) values are pulled straight from HTTP headers, completely outside the signed material: [3](#0-2) 

`Registry.process` validates only the HMAC of the request, then immediately forwards `request.shop` (the unsigned header) to the application's webhook handler as the tenant identity to act on: [4](#0-3) 

This is the same bug class as the report: a value that is acted upon (`shop`, used by the handler to select/scope tenant data) is not covered by the cryptographic authenticator (HMAC covers only the body). The binding the code implicitly claims to enforce is:
`shop authenticated by HMAC == shop the handler acts on`
but in reality:
`shop authenticated by HMAC = ∅ (not part of signable_string)` while `shop the handler acts on = header value, attacker/network controlled`.

Because the HMAC secret (`Context.api_secret_key`) is the same for every shop that installs a given app, any shop owner that has legitimately installed the app can obtain genuinely-signed webhook deliveries for data they themselves control (e.g. by creating orders/products/customers in their own store to trigger a webhook body of their choosing). Since the header carrying `shop` is not part of the signed payload, that same valid `(body, hmac)` pair can be replayed with the `x-shopify-shop-domain` header rewritten to name a different, victim shop, and `Utils::HmacValidator.validate` will still accept it because it only re-derives the HMAC from `@raw_body`.

### Impact Explanation
This allows cross-tenant webhook injection: an attacker who can reach the app's webhook endpoint (directly, or by intercepting/relaying a delivery they legitimately received for their own shop) can make the host application believe attacker-crafted data (order, customer, GDPR, app/uninstall, etc.) originated from an arbitrary victim shop domain, since `WebhookMetadata#shop` is derived from the unauthenticated header. Depending on how the host app uses `data.shop` (e.g. to look up the victim's stored session/access token to react to the event), this can lead to cross-tenant state corruption or actions being taken against the wrong merchant's data — matching the "cross-tenant access" critical-impact category.

### Likelihood Explanation
Requires the attacker to be able to submit HTTP requests to the app's public webhook endpoint and to possess at least one validly-signed `(body, hmac)` pair, which any merchant who installs the app can trivially obtain by triggering webhooks in their own store. No access token, `client_secret`, or privileged credentials are needed beyond ordinary use of the app as an installed merchant, satisfying the "unprivileged internet user" bar.

### Recommendation
Include the shop domain (and other trust-relevant metadata like the webhook topic/id) inside the HMAC-signed material, or independently verify `request.shop` against the set of shops known to have installed the app (with a valid, stored session) before dispatching to the handler, rather than trusting the raw header value once only the body's HMAC has been checked.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; attacker triggers an event (e.g., updates a product) causing Shopify to send a legitimately HMAC-signed webhook to the app's endpoint, with body `B` and header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker intercepts/replays this request to the same endpoint but changes only the header to `x-shopify-shop-domain: victim-shop.myshopify.com`, leaving body `B` and the `x-shopify-hmac-sha256` value untouched.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC solely from `@raw_body` (`to_signable_string`) — this still matches since the body was not altered.
4. The handler receives `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim-shop.myshopify.com"` even though the payload actually originated from the attacker's own shop, as shown in: [5](#0-4)
