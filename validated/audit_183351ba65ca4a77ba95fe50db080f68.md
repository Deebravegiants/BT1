### Title
Unbounded gas forwarded to attacker-controlled `to` module in `EvmHost.dispatchIncoming` can exhaust relayer gas and DoS batched message delivery - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming(PostRequest, ...)` performs a low-level `.call()` to the destination module address decoded from the incoming request's `to` field, without any gas stipend or gas cap, exactly the "forward all remaining gas to an untrusted/attacker-influenced address" pattern that made the Notional `_isWrappedFCash` check a gas bomb.

### Finding Description
`dispatchIncoming` resolves `destination = _bytesToAddress(request.to)` and dispatches to it via: [1](#0-0) 

The call `address(destination).call(abi.encodeWithSelector(IApp.onAccept.selector, ...))` carries no explicit gas limit, so Solidity forwards essentially all gas remaining in the current call frame (minus the 63/64 EIP-150 reserve) to `destination`. The `to` address is attacker-influenced: `PostRequest.to` is set by the module dispatching the cross-chain message on the source chain, and messages are relayed permissionlessly by whoever submits the proof transaction to `HandlerV2`, which then loops over a batch of requests and invokes `EvmHost.dispatchIncoming` for each one. The same unbounded-forwarding pattern recurs in the sibling functions `dispatchIncoming(GetResponse,...)`, `dispatchTimeOut(GetRequestTimeout,...)`, and `dispatchTimeOut(PostRequestTimeout,...)`, all of which call `_bytesToAddress(...).call(...)` with no gas cap: [2](#0-1) [3](#0-2) [4](#0-3) 

`HandlerV2.sol` contains the batch-processing loop that invokes these host dispatch functions once per message in a single relayer transaction (confirmed by presence of the batch-loop and `dispatchIncoming` call sites), mirroring the Notional bug's "not the last position in the batch" scenario: an attacker deploys (or is granted, via a legitimate app registration) a `to` module whose `onAccept`/`onGetResponse`/`onPostRequestTimeout` fallback/logic does not revert but performs expensive, unbounded computation (loops, storage writes, recursive external calls) consuming nearly all gas forwarded to it. Because there is no gas ceiling on the call, one malicious/broken module in the middle of a batch can consume the entire remaining gas budget, aborting delivery to every subsequent legitimate message in that batch (the call fails with out-of-gas, which is caught by `success == false`, but no gas remains for the rest of the loop).

### Impact Explanation
This falls into the "route unable to deliver messages" impact category: a single malicious or buggy application module registered as a message recipient can grief the relayer batch, causing legitimate POST requests/responses/timeouts bundled in the same transaction to fail delivery (their `success` check returns false due to out-of-gas propagating up through the loop, or the entire relayer transaction reverts if the relayer under-provisioned gas). This degrades the relay's reliability and can be used to selectively censor or delay other users' cross-chain messages that happen to be batched alongside the malicious module's message, and forces relayers to either over-provision gas (raising relay costs) or risk failed batches.

### Likelihood Explanation
Likelihood is constrained: `eth_estimateGas`/simulation would generally catch pathological gas usage before broadcast (as the original judge noted for the analogous Notional finding), and batching/target selection is partly under relayer control. However, unlike the Notional case, the `to` address here is fully attacker-controlled application-layer input (any deployed contract can register as an `IApp` and receive dispatched messages), so an attacker can deliberately craft a module with an expensive but non-reverting `onAccept` and wait to be batched with real transactions, or force relayers into per-message dispatch (single-message batches) where they must always over-allocate gas, degrading throughput and fee economics.

### Recommendation
Cap the gas forwarded to destination modules in all four dispatch paths (`dispatchIncoming(PostRequest,...)`, `dispatchIncoming(GetResponse,...)`, `dispatchTimeOut(GetRequestTimeout,...)`, `dispatchTimeOut(PostRequestTimeout,...)`) using an explicit `{gas: moduleGasLimit}` value (configurable via `_hostParams`), so that a single misbehaving or malicious `IApp` module cannot consume more than its allotted share of gas and cannot starve the rest of a relayed batch. Emit/track the gas limit as a host parameter updatable by governance, and document it for app developers implementing `IApp`.

### Proof of Concept
1. Deploy a contract `EvilApp` implementing `IApp.onAccept` that runs an unbounded loop (e.g., repeated `SSTORE`s) but never reverts, consuming close to `gasleft()`.
2. Register `EvilApp` as a normal cross-chain message recipient by having some source-chain module dispatch a `PostRequest` with `to = address(EvilApp)`.
3. Have a relayer submit a `HandlerV2` batch that includes the proof for the `EvilApp` message alongside proofs for other legitimate `PostRequest`s destined for well-behaved modules.
4. Observe that `EvmHost.dispatchIncoming` for `EvilApp` consumes nearly all remaining gas in the transaction (no gas cap on the low-level `.call`), causing the loop in `HandlerV2` to run out of gas for subsequent legitimate messages in the same batch, or forcing the relayer to supply a much larger gas limit than the "honest" cost of the batch would otherwise require.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
