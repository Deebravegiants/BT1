### Title
Zero latest-height sentinel silently drops the first-ever state machine commitment for newly onboarded chains - (File: `evm/src/core/HandlerV2.sol`)

### Summary
`HandlerV2.handleConsensus` uses `host.latestStateMachineHeight(...) != 0` as the gate for whether to persist a new `IntermediateState` commitment. This is the same "zero used as a false negative" pattern flagged in the CoreOracle report: `latestStateMachineHeight` legitimately returns `0` both when a state machine is unsupported/unknown *and* when it is a freshly onboarded, supported state machine that has simply never received a commitment yet. The check cannot distinguish these two cases, so the very first `IntermediateState` ever produced for a newly added counterparty state machine is silently discarded instead of stored.

### Finding Description
In `handleConsensus`:
```solidity
uint256 latestHeight = host.latestStateMachineHeight(intermediate.stateMachineId);
if (latestHeight != 0 && intermediate.height > latestHeight) {
    StateMachineHeight memory stateMachineHeight =
        StateMachineHeight({stateMachineId: intermediate.stateMachineId, height: intermediate.height});
    host.storeStateMachineCommitment(stateMachineHeight, intermediate.commitment);
}
``` [1](#0-0) 

`latestHeight` is read from a storage mapping on `IHost` (`EvmHost.sol`) keyed by `stateMachineId`; an unset entry and an entry that is genuinely at height 0 are indistinguishable — both read back as `0`. The `latestHeight != 0` conjunct treats "no commitment recorded yet" identically to "unknown/unsupported state machine," so for a state machine that a relayer has just successfully verified consensus for (via `IConsensusV2.verify`) but for which no on-chain commitment has ever been stored, this gate evaluates to `false` and `host.storeStateMachineCommitment` is never invoked, no matter what `intermediate.height` is. This mirrors the reported CoreOracle flaw where `price == 0` was used to infer "not supported" even though 0 is also the legitimate value returned during initialization.

### Impact Explanation
Because the state machine commitment is never written, `host.stateMachineCommitment(height)` and `host.stateMachineCommitmentUpdateTime(height)` remain empty/zero for that height on this state machine. Downstream consumers such as `HandlerV2.handlePostRequests` depend on a non-zero `overlayRoot` from `stateMachineCommitment` to verify MMR proofs (`if (root == bytes32(0)) revert StateCommitmentNotFound();`) [2](#0-1) . With the commitment silently dropped, every post-request/response/timeout proof anchored at that height is unverifiable, so messages from/to the newly onboarded state machine cannot be delivered — a denial of the route rather than a state root corruption, but a concrete "route unable to deliver messages" until a later, subsequent consensus update happens to arrive with a state machine height already non-zero (which itself depends on the same code path having stored a commitment previously — a chicken-and-egg gap for onboarding).

### Likelihood Explanation
This triggers deterministically, not via any malicious actor, whenever a new counterparty state machine is onboarded to `IsmpHost`/`EvmHost` and its first `IntermediateState` is relayed through `handleConsensus` — an ordinary, expected relayer action. Any relayer submitting the first legitimate consensus proof for a newly added chain reproduces this.

### Recommendation
Do not use `latestHeight != 0` as a proxy for "state machine supported." Either:
- Track support for a `stateMachineId` explicitly (e.g., a separate boolean/registered-set rather than overloading the height value), or
- Change the condition to unconditionally store when `intermediate.height > latestHeight` (since `0` is already a valid "no prior height" baseline, any positive intermediate height should be accepted), removing the `latestHeight != 0` guard entirely for state machines the host is configured to support.

### Proof of Concept
1. Host registers/enables a new counterparty `stateMachineId` for which no commitment has ever been stored (`latestStateMachineHeight` returns `0` by default from the storage mapping).
2. A relayer calls `handleConsensus(host, proof)` with a valid consensus proof producing `IntermediateState { stateMachineId, height: H, commitment }` for `H > 0`.
3. In the loop, `latestHeight = host.latestStateMachineHeight(stateMachineId) == 0`, so `latestHeight != 0` is `false`, and `host.storeStateMachineCommitment` is skipped regardless of `H`.
4. `host.stateMachineCommitment(H)` remains unset (`overlayRoot == bytes32(0)`).
5. Any subsequent `handlePostRequests` call proving requests at height `H` for that state machine reverts with `StateCommitmentNotFound` [3](#0-2) , permanently blocking message delivery for that height until a later commitment happens to be accepted.

Note: I was unable to fully retrieve the exact storage-mapping implementation of `latestStateMachineHeight`/`storeStateMachineCommitment` in `evm/src/core/EvmHost.sol` within the available context (grep matched but content wasn't returned in full); the analysis above is based on the documented semantics ("Latest height, or 0 if the state machine is unsupported") [4](#0-3)  and the call-site logic in `HandlerV2.sol`, which is sufficient to establish the root cause but a full review of `EvmHost.sol`'s storage defaults would further confirm whether any additional guard exists elsewhere.
