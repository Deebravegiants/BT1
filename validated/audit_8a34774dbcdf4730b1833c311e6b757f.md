### Title
Zero-amount order inputs on the Tron IntentGatewayV2 can permanently freeze cross-chain escrow funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.placeOrder`'s predispatch branch on the Tron variant of the Intent Gateway does not reject zero-amount entries in `order.inputs`, unlike the identical non-predispatch branch and unlike the audited `evm/src` implementation. Combined with the Tron `withdraw()` function reverting on *any* input token whose escrow balance reads zero, an order containing one zero-amount input alongside legitimate escrowed inputs becomes permanently un-cancelable and un-fillable — freezing all escrowed funds in that order.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`, the non-predispatch escrow loop explicitly rejects zero-amount inputs: [1](#0-0) 

But the predispatch branch, which transfers assets to the `CallDispatcher`, executes calldata, and sweeps tokens back for escrow, performs **no equivalent check** on `order.predispatch.assets[i].amount` or `order.inputs[i].amount`: [2](#0-1) 

This is the same bug class as the referenced Sherlock `YoloV2.depositETHIntoMultipleRounds` finding: an array element with value `0` slips past validation that is enforced everywhere else, letting a user construct a state (here, an `Order.inputs` array containing a zero-amount token) that downstream logic doesn't expect.

The consequence surfaces in `withdraw()`, the single function used to release escrow on cancellation or fill settlement (both same-chain cancel and cross-chain `RedeemEscrow`/`RefundEscrow` `onAccept`/`onGetResponse` paths route through it): [3](#0-2) 

`withdraw()` iterates every token in `body.tokens` (derived from `order.inputs`) and reverts with `UnknownOrder()` if `_orders[body.commitment][token] == 0` for **any** entry — it does not skip zero-amount entries the way the fixed `evm/src` implementation's `_withdraw` does: [4](#0-3) 

Since a predispatch order can carry an input whose `amount` was never validated as non-zero, its corresponding escrow entry `_orders[commitment][token]` legitimately stays `0`. Any later call to `withdraw()` for that commitment (cancel, redeem, or refund) will always revert on that zero-escrow token entry, and because the loop is atomic, the revert blocks release of every other (legitimately non-zero) escrowed token in the same order too.

### Impact Explanation
This permanently freezes user funds: once an order is placed through the predispatch path with a zero-amount input mixed with real inputs, none of the escrowed tokens for that order can ever be withdrawn — not via same-chain cancel, not via source-chain `onGetResponse` refund, and not via destination-chain `RedeemEscrow`/`RefundEscrow` `onAccept`. `_filled[commitment]` is set only after `withdraw()` succeeds, so the freeze is permanent and unrecoverable (no path re-derives escrow amounts). This matches the "permanent freezing of funds" impact criterion for intents escrow.

### Likelihood Explanation
Any unprivileged user submitting an order via `placeOrder` with `predispatch.call.length > 0 && predispatch.assets.length > 0` controls `order.inputs` directly and can include a zero-amount entry (deliberately, e.g., to build in a calldata-only leg, or by relying on incomplete client-side input construction). Since the predispatch branch performs no zero-amount validation, the transaction succeeds and creates a permanently frozen order. No special privileges or race conditions are required — this is a single, ordinary `placeOrder` transaction.

### Recommendation
Add the same `if (amount == 0) revert InvalidInput();` guard to the predispatch branch of `placeOrder` (for both `predispatch.assets[i].amount` and `order.inputs[i].amount`) that already exists in the non-predispatch branch and in `evm/src/apps/IntentGatewayV2.sol`. Additionally, harden `withdraw()` to skip token entries whose requested `amount` is `0` (mirroring `IntentsBase._withdraw`'s `if (amount == 0) continue;`) so a stray zero-amount entry can never block release of the rest of an order's escrow.

### Proof of Concept
1. User calls `placeOrder` on the Tron `IntentGatewayV2` with `order.predispatch.call` and `order.predispatch.assets` non-empty, and `order.inputs` containing two entries: `inputs[0] = {token: USDC, amount: 1000e6}` and `inputs[1] = {token: DAI, amount: 0}`.
2. The predispatch branch (lines 389–446) transfers/executes calldata and escrows both entries without reverting, since no `amount == 0` check exists on this path; `_orders[commitment][DAI] += 0` leaves the DAI escrow slot at `0`.
3. User (or anyone eligible) later calls `cancelOrder` → `withdraw(body, true)` where `body.tokens = order.inputs` (both USDC and DAI entries).
4. Inside `withdraw()` (lines 691–714), the loop hits the DAI entry, reads `_orders[commitment][DAI] == 0`, and reverts with `UnknownOrder()` — reverting the entire transaction, including the USDC transfer that would otherwise have succeeded.
5. Every subsequent cancel/redeem/refund attempt hits the same revert, permanently locking the escrowed 1000 USDC in the contract.
