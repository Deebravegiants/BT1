### Title
Malicious strategy route can execute attacker-controlled calls under the caller’s authorization - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller accepts an opaque `StrategySwap` payload and forwards it to the configured router without restricting which pool, token, or venue contracts that payload can invoke. [1](#0-0)  The controller’s explicit contract authorization only permits one exact `transfer` of the routed input token from the controller to the router, but it does not isolate other calls made beneath the caller’s `require_auth` tree. [2](#0-1) 

### Finding Description
The strategy entrypoints treat `swap` as untrusted serialized routing instructions rather than as a constrained list of safe operations: `multiply` accepts `swap: Bytes` and passes it into `swap_tokens_or_passthrough`, while `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral` follow the same pattern. [3](#0-2) [4](#0-3)  After obtaining caller authorization, `swap_tokens` invokes `SwapAggregatorClient::execute_strategy` with the caller-controlled `swap` payload. [5](#0-4) 

The analogous injection is therefore the route payload: attacker-authored routing data can name third-party contracts and cause calls below the caller’s authorized invocation. [6](#0-5)  The balance checks afterward only verify that the controller did not overspend its input and received positive output; they do not bound unrelated token transfers requested from the caller by a malicious route contract. [7](#0-6) [8](#0-7) 

### Impact Explanation
A malicious route can place an unauthorized-looking token call in the transaction’s authorization tree, such as transferring an unrelated asset from the victim’s address to an attacker-controlled address. [9](#0-8)  If the victim signs the complete simulated tree, the injected call executes with the victim’s authorization even though it is unrelated to the lending operation and is not bounded by the controller’s one-transfer authorization. [10](#0-9)  This can result in theft of user funds beyond the routed input amount, while the strategy can still satisfy the controller’s positive-output and account-solvency checks. [11](#0-10) 

### Likelihood Explanation
The attacker must induce a victim to submit or sign a strategy transaction containing the malicious route, so exploitation is not fully unilateral. [12](#0-11)  Nevertheless, the vulnerable surface is exposed through ordinary permissionless strategy calls, the payload is opaque `Bytes`, and the router interface places no venue allowlist requirement in the controller-side call boundary. [13](#0-12) [6](#0-5) 

### Recommendation
Constrain strategy routes at the trust boundary instead of forwarding arbitrary routing instructions under the caller’s authorization tree. [1](#0-0)  Decode and validate route venues against a governance-approved allowlist, or redesign execution so router venue calls cannot request additional authority from the end user. [6](#0-5)  At minimum, reject any authorization tree containing calls other than the expected controller-owned input transfer and require clients to display every nested invocation before signing. [10](#0-9) 

### Proof of Concept
1. Deploy or identify a malicious route contract that, when reached by the router, requests a token transfer from the strategy caller to the attacker. [9](#0-8) 
2. Construct a `swap` payload that routes through that contract and submit it as the `swap` argument to `multiply`, `swap_debt`, `swap_collateral`, or `repay_debt_with_collateral`. [14](#0-13) [15](#0-14) 
3. Have the victim authorize the strategy; the strategy requires caller authorization before the route is executed. [16](#0-15) 
4. The controller authorizes only its own input transfer to the router, then forwards the attacker-controlled route to `execute_strategy`. [5](#0-4) [10](#0-9) 
5. The malicious venue adds the victim-funded transfer beneath the caller authorization; if included in the signed authorization tree, it executes even though the controller only validates its own input balance and output receipt afterward. [7](#0-6)

```rust
/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
```
