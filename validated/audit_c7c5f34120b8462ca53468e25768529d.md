This confirms the vulnerability. The webhook HMAC only signs `@raw_body` [1](#0-0) , while `topic`, `shop`, `webhook_id`, and `api_version` are all read straight from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only that body-HMAC and then dispatches `request.shop`/`request.topic` directly to the app's handler as trusted identity metadata [3](#0-2) .

### Title
Webhook shop/topic identity headers are not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` cryptographically authenticates the payload bytes but never binds the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers to that signature. `Registry.process` treats a passing HMAC check as proof that the whole request — including which shop it came from — is authentic, then forwards `request.shop` unchanged to the host application's handler.

### Finding Description
The intended identity binding is: `shop that authorized/sent the webhook == shop value the handler acts on`. The code instead verifies:

- Binding checked: HMAC-SHA256(`api_secret_key`, raw_body) == `shopify-hmac-sha256` header [4](#0-3) [5](#0-4) 
- Binding relied upon by the handler: `data.shop` == the shop the merchant/host app believes sent the webhook [3](#0-2) 

Because `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers that are excluded from `to_signable_string`, any request whose body+HMAC pair is valid for the app's shared `api_secret_key` will pass `Utils::HmacValidator.validate` regardless of what shop-domain/topic headers are attached to it. Since Shopify computes the webhook HMAC using only the app's `client_secret` and the raw body (not per-shop), a merchant who has installed the app receives genuine webhooks for their own shop with a valid body+HMAC pair. That merchant (an unprivileged actor with respect to any other tenant of the same app) can replay that exact body+HMAC to the app's public webhook endpoint while substituting a different `shop-domain` header value belonging to another merchant. `Registry.process` will accept it, since only the body's HMAC is checked [6](#0-5) , and will hand the forged `shop` value straight to the host app's webhook handler as `WebhookMetadata#shop` [7](#0-6) .

### Impact Explanation
This breaks the tenant boundary the gem is supposed to guarantee to consuming apps: "HMAC validated" is documented as "this will verify the request did indeed come from Shopify" [8](#0-7) , but that verification silently excludes the shop identity. Any host application that trusts `WebhookMetadata#shop` (as the library's own docs/examples imply is safe) after `Registry.process` succeeds can be tricked into writing, deleting, or otherwise processing data under the wrong tenant's record — i.e., cross-tenant access/data corruption using only a webhook payload the attacker already legitimately received for their own store.

### Likelihood Explanation
Any merchant who installs the app (no special privilege, no leaked secrets, no access token needed) automatically receives real webhooks with valid body+HMAC for their own shop and can immediately replay them with a modified `shop-domain` header against the app's public webhook endpoint. No race condition or timing is required, unlike the referenced report's front-running scenario; the exploit is deterministic and repeatable.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string, or otherwise cryptographically bind them to the same HMAC (e.g., compose the signable string as canonicalized header values concatenated with the body) so `Utils::HmacValidator.validate` fails whenever any of these fields is altered relative to what Shopify actually signed for that shop.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any webhook (e.g., `orders/create`), capturing the real `raw_body` and `shopify-hmac-sha256` header Shopify sent.
2. Attacker sends a POST to the app's webhook endpoint with the same `raw_body`/`shopify-hmac-sha256`, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers [9](#0-8) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `raw_body` [6](#0-5) .
4. The host app's handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, acting on data as if it came from the victim tenant [7](#0-6) .
