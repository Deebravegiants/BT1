### Title
Webhook shop-tenant identity (`shop-domain` header) is not covered by HMAC verification, enabling cross-tenant webhook spoofing — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines the HMAC-signable content as the raw request body only: [1](#0-0) 

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
```

`Utils::HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it (via `OpenSSL.secure_compare`) against the `hmac-sha256`/`x-shopify-hmac-sha256` header: [2](#0-1) 

However, the tenant-identifying `shop` field, as well as `topic` and `webhook_id`, are pulled straight from unauthenticated HTTP headers and are never included in the signed bytes: [3](#0-2) 

`Registry.process` verifies only the body HMAC, then hands the *unverified* `request.shop`, `request.topic`, and `request.webhook_id` straight to the app's handler as if they were verified: [4](#0-3) 

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
```

**Binding that should hold, but doesn't:**
`HMAC_valid(raw_body) == true` is treated by the library as proof that `(shop, topic, webhook_id, body)` all originate from Shopify for that specific shop. In reality the equality that actually holds is only:

`HMAC(secret, raw_body) == received_hmac`

There is no cryptographic binding of the form `HMAC(secret, raw_body ‖ shop ‖ topic) == received_hmac`. Because Shopify's own webhook HMAC scheme signs only the body (this mirrors Shopify's real behavior, so it's not a library bug against Shopify's own webhooks reaching the app through a trusted, TLS'd connection) — but the library exposes `Registry.process(request)` as a generic verification entry point that any host application is documented/expected to call directly on a `Webhooks::Request` built from raw HTTP input. If any component (proxy, gateway, queue, or even a malicious sender that discovers/guesses a body whose HMAC they already possess for one shop) can deliver a request to the app's webhook endpoint with attacker-controlled headers but the same, already-known-valid body/HMAC pair (e.g., an empty-body `{}` webhook — demonstrated as valid in the library's own test fixtures — or any other topic whose body content is fixed/predictable across shops, such as `shop/redact`, `app/uninstalled` when body carries only the shop's numeric ID), the library will accept it as legitimate and report an attacker-chosen `shop-domain`, `topic`, and `webhook_id` to the app's handler.

This is the same root-cause pattern as the reported bug class ("a field acted on but not covered by the HMAC"): the verifier authenticates only the body bytes, while the library treats the shop identity and topic — the values actually acted upon (dispatch to per-tenant handler, `WebhookMetadata#shop` used by the app to attribute the event to a merchant) — as if they were part of the authenticated payload.

### Impact Explanation
If an app's webhook consumers place any trust in the `shop` field carried in `WebhookMetadata` produced by this library (which is the documented purpose of `Registry.process` — to safely convert an inbound HTTP payload into a trusted, per-shop event), an attacker who can reach the webhook endpoint with a body whose valid HMAC they can obtain (replay of a previously-observed webhook, or a predictable/fixed-content topic) can spoof the shop attribution and topic. This can result in cross-tenant data confusion (Critical: cross-tenant access) — e.g., mandatory compliance webhooks like `shop/redact` or `customers/data_request` being attributed to the wrong shop, or an attacker forcing processing of a stale/replayed webhook body under an arbitrary shop identity of their choosing.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one valid `(raw_body, hmac)` pair, which is trivial for any topic with a fixed or attacker-known body (mandatory topics, or any webhook the attacker's own shop legitimately receives), and to be able to send a raw HTTP request that reaches the app's `Registry.process` call (i.e., the app's webhook route) with forged `shop-domain`/`topic` headers. No possession of `api_secret_key` or any credential is needed — only knowledge of a body/HMAC pair, which is not secret in Shopify's model (only the HMAC signing key is secret, but the pair itself is observable to any recipient of any webhook, including the attacker's own store's).

### Recommendation
Bind the shop, topic, and webhook id into the signed material used for HMAC verification (or otherwise cryptographically bind them to the HMAC), e.g. by having `to_signable_string` include the normalized `shop-domain`, `topic`, and `webhook-id` headers alongside the raw body, and reject requests where these headers don't match what's embedded/covered by the signature. At minimum, document clearly (and enforce in code) that `shop`/`topic` returned from `Webhooks::Request` are NOT authenticated by the HMAC and must not be trusted for tenant attribution without additional verification (e.g., cross-checking against a known/expected shop for the delivery channel).

### Proof of Concept
1. Register a webhook handler for topic `T` with delivery to your app's webhook endpoint, using shop `victim-shop.myshopify.com`. Note a legitimately delivered webhook `raw_body` (e.g., an empty-body event: `{}`) and its accompanying valid `hmac-sha256` header value.
2. Construct a new HTTP POST to the app's webhook endpoint with the same `raw_body` and the same `hmac-sha256` value, but replace `shopify-shop-domain` with `attacker-shop.myshopify.com` and/or `shopify-topic`/`shopify-webhook-id` with values of choice.
3. Call `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` and `ShopifyAPI::Webhooks::Registry.process(request)`; observe that `Utils::HmacValidator.validate(request)` returns `true` (per [5](#0-4)  only `to_signable_string`/body is checked), and the handler receives `WebhookMetadata` with `shop: "attacker-shop.myshopify.com"` and the forged `topic`/`webhook_id`, even though these values were never covered by the HMAC.
