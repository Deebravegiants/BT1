### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, while the tenant identifier (`shop`) is read from a separate, unsigned HTTP header. `ShopifyAPI::Webhooks::Registry.process` trusts this header value directly when dispatching to the host app's handler. This breaks the identity binding: `shop` acted on ≠ `shop` covered by the HMAC.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is parsed from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of that signable string: [2](#0-1) 

`Registry.process` validates only the body's HMAC via `Utils::HmacValidator.validate(request)`, then forwards `request.shop` (the unsigned header) straight into `WebhookMetadata`, which is handed to the host app's handler as the tenant identity for the event: [3](#0-2) 

`WebhookMetadata.shop` is a plain `String` field with no further verification step in this gem: [4](#0-3) 

`Utils::HmacValidator.validate` recomputes the HMAC only over `verifiable_query.to_signable_string` (the raw body) and compares it to the `hmac` header — it never touches `shop`: [5](#0-4) 

This is structurally identical to the report's bug class: an identity field (`to_chain`/`to_handler` in the Starknet case, `shop` here) is *acted on* by the settlement/dispatch logic but is *not covered* by the cryptographic check that is supposed to bind the message to its origin. The equality that should hold is:

`shop used by handler.handle(data:)` == `shop that Shopify actually signed the payload for`

but the code only proves:

`hmac(raw_body, api_secret_key)` == `received hmac`

with `shop` free to be set to any value by whoever sends the HTTP request, as long as the accompanying `raw_body`+`hmac` pair was ever validly issued for *some* shop.

### Impact Explanation
Any unprivileged internet user who can install the app on a shop they control (a standard, credential-free action for public apps) can:
1. Trigger a real webhook event on their own shop and capture the resulting `raw_body` and `shopify-hmac-sha256` value that Shopify sent to the app's webhook endpoint.
2. Replay that exact `raw_body` + `hmac` pair to the app's webhook endpoint, but substitute the `shopify-shop-domain` header with a victim shop's domain.
3. `HmacValidator.validate` succeeds (the body/hmac pair is legitimate — just not for the claimed shop), and `Registry.process` invokes the handler with `WebhookMetadata.shop` set to the victim's domain.

Because host applications (as documented for this gem) treat `WebhookMetadata.shop` as the authoritative tenant key for looking up sessions and mutating shop-scoped data, this allows cross-tenant data confusion/corruption without any credentials belonging to the victim — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is realistic but bounded: the attacker must obtain at least one genuinely-signed `(body, hmac)` pair, which they can trivially do by installing the app on their own store and triggering any webhook topic. No secret material, TLS interception, or privileged account is required — only normal use of the app as an unprivileged merchant/customer plus direct HTTP requests to the app's public webhook endpoint. The only mitigating factor is that the replayed body content is fixed (from the attacker's own store), limiting attacks to topics/shapes the attacker can generate themselves, but the tenant attribution can be freely spoofed.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-covered signable content, or independently verify that the `shop` header corresponds to a shop with an active, known session/installation before dispatching to the handler, rather than trusting `x-shopify-shop-domain` as an unauthenticated header value.

### Proof of Concept
```ruby
# Step 1: capture a legitimately signed webhook from the attacker's own shop
raw_body = '{"id":1}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Step 2: replay it against the endpoint, but with the victim's shop domain
headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => Base64.encode64(hmac),
  "shopify-shop-domain" => "victim-shop.myshopify.com", # spoofed, not covered by hmac
  "shopify-webhook-id" => "attacker-controlled-id",
  "shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) returns true (hmac matches raw_body)
# => handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", ...))
```
