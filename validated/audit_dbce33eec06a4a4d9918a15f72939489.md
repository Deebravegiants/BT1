### Title
Webhook Shop-Domain Spoofing via HMAC That Only Signs the Request Body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, and `webhook_id` are all read straight from unauthenticated HTTP headers. `Registry.process` validates the HMAC and then, without any further check, hands `request.shop` (the unauthenticated header value) to the app's webhook handler as the tenant identifier. Because the app's `client_secret` is shared across every shop that has the app installed, any shop that installs the app can capture one of its own genuine webhook deliveries (valid body + valid HMAC) and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop, producing a request that passes HMAC validation but is attributed to the wrong tenant.

### Finding Description
The webhook HMAC binding only covers the body: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are pulled from headers that are never part of `to_signable_string`, so they are not authenticated by the HMAC at all. `Registry.process` verifies the HMAC and then dispatches directly using the unauthenticated `shop` value: [2](#0-1) 

`HmacValidator.validate` simply recomputes the signature over whatever `to_signable_string` returns and compares it to the supplied HMAC — it has no notion of the shop the request claims to be from: [3](#0-2) 

This is the same class of bug as the referenced report: the value that is *checked* (the raw body, signed with the app's single shared `api_secret_key`) is not the same as the value that is *acted upon* (the `shop` header, used as the tenant/session key passed to the handler). Because the `api_secret_key` is one value shared by the app across all its installed shops, a genuine, validly-signed webhook obtained from any one installation can be replayed against the same endpoint with the shop header altered, and the signature will still verify — breaking the equality `shop authenticated == shop used as tenant key`.

### Impact Explanation
Any merchant who installs the app (an unprivileged actor with respect to other merchants) can produce arbitrary valid `(body, hmac)` pairs by triggering events on their own store, then replay them with a forged `X-Shopify-Shop-Domain` header pointing at a different, victim shop that also has the app installed. `Registry.process` will accept the request and invoke the handler with `shop: <victim shop>` and attacker-chosen body content, since nothing in this gem binds the shop to the signature. Depending on how the host app's handler uses `WebhookMetadata#shop` (e.g., to look up/update per-tenant records, inventory, or orders), this enables cross-tenant data corruption/injection — a merchant can inject fabricated data attributed to another merchant's store.

### Likelihood Explanation
Exploitation requires only that the attacker be an app-installing merchant (unprivileged relative to other tenants) capable of sending raw HTTP requests to the app's public webhook endpoint with custom headers — no access to `api_secret_key`, access tokens, or the target shop is needed. Because Shopify's webhook signing scheme uses one secret per app across all installations, capturing a valid `(body, hmac)` pair from the attacker's own store is trivial.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) into the signed material, or independently verify that `request.shop` corresponds to a shop with an active, legitimately stored session/installation record before dispatching to handlers, rather than trusting the header value once the (body-only) HMAC passes.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers an event (e.g. creates an order) to receive a genuine webhook POST with a valid `X-Shopify-Hmac-Sha256` header computed over the JSON body using the app's shared `client_secret`.
2. Attacker replays this exact request to the app's webhook endpoint, changing only the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (the unchanged raw body) — validation succeeds.
4. The handler is invoked via `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` with `shop` set to `victim-shop.myshopify.com`, even though the payload actually originated from the attacker's own store. [2](#0-1)

          received_signature = verifiable_query.hmac
