### Title
`onPostRequestTimeout` refund path is blocked by `whenNotPaused`, freezing already-burned/locked user funds during a pause - ([File: sdk/packages/core/contracts/apps/HyperFungibleToken.sol])

### Summary
`HyperFungibleToken`, `HyperFungibleTokenUpgradeable`, `WrappedHyperFungibleToken`, and `WrappedHyperFungibleTokenUpgradeable` all gate `onPostRequestTimeout()` — the function that refunds a user whose cross-chain transfer timed out — behind the `whenNotPaused` modifier. This mirrors the reported OmniPool bug class: a critical fund-recovery action for a user who already committed value (burned tokens or locked underlying tokens via `send()`) is blocked whenever the contract owner pauses it, even though pausing is meant to stop *new* risk-taking actions, not recovery of already-committed funds.

### Finding Description
`send()` burns (or locks, in the wrapped variant) the user's tokens immediately and dispatches an ISMP POST request [1](#0-0) . If that message is not delivered before its timeout, the only way for the user to get their funds back is via `onPostRequestTimeout()`, which re-mints (or unlocks) the amount to the original sender [2](#0-1) .

That refund function is marked `onlyHost whenNotPaused`: [3](#0-2) 

The same pattern exists in the upgradeable and wrapped variants: [4](#0-3) [5](#0-4) 

Because `onAccept()` (successful delivery) is *also* gated by `whenNotPaused` [6](#0-5) , while the contract is paused a relayer can neither deliver nor time out any in-flight message. Tokens that were already burned/locked by `send()` prior to (or even during, if `send()` itself weren't paused) the pause remain in limbo: the user cannot receive their tokens on the destination chain, and cannot get them refunded via timeout, until the owner unpauses the contract — this is functionally identical to the OmniPool `repay()` finding, where a legitimate emergency pause blocks the one function users need to protect/recover their own already-committed value.

### Impact Explanation
Users' bridged funds (burned supply on the source side, or ERC20/WETH locked in the wrapper) are frozen for the entire duration of any pause, with no way for the user or relayer to force settlement. This is a freezing-of-funds condition on a core token-bridge mint/burn path, directly reachable by any user who called `send()` before or during a pause — no privileged action beyond the ordinary/expected use of `pause()` is required to trigger the freeze; the harm materializes as soon as a timeout occurs while paused.

### Likelihood Explanation
`pause()`/`unpause()` are documented, expected owner controls (e.g., for emergencies or migrations) [7](#0-6) , not an attack. Any timeout that occurs during a legitimately-triggered pause (e.g. a relayer outage, an unrelated exploit response, or a migration window) will hit this bug. Given ISMP timeouts are a normal, expected occurrence (not an edge case), and pauses are a normal operational tool, the likelihood of overlap is realistic over the life of a deployment.

### Recommendation
Remove `whenNotPaused` from `onPostRequestTimeout()` in `HyperFungibleToken.sol`, `HyperFungibleTokenUpgradeable.sol`, `WrappedHyperFungibleToken.sol`, and `WrappedHyperFungibleTokenUpgradeable.sol` so that refunds of already-committed funds can always be processed regardless of pause state, consistent with only using `pause()` to block *new* value-at-risk actions (`send()`/`onAccept()` minting new value) rather than recovery of funds already committed by users.

### Proof of Concept
1. User calls `send()` on `HyperFungibleToken`, burning `amount` tokens and dispatching a POST request with a timeout [1](#0-0) .
2. Before the relayer delivers the message, the owner calls `pause()` [8](#0-7)  (e.g. in response to an unrelated incident).
3. The message times out. A relayer attempts to submit the timeout proof by calling `onPostRequestTimeout()`, but the call reverts because the contract is paused, per the existing test asserting `onAccept` reverts when paused for the same modifier pattern [9](#0-8) .
4. The user's burned tokens cannot be re-minted, and the message also cannot be delivered via `onAccept` (same modifier), leaving the funds frozen until the owner chooses to `unpause()` — with no on-chain guarantee of when or whether that happens.

    /**
     * @notice Handles timeout of a previously dispatched cross-chain transfer
     * @dev Called by the ISMP host when a sent message times out without being delivered.
     * Re-mints the burned tokens back to the original sender as a refund.
     * @param incoming The timed-out POST request and the relayer that submitted the timeout proof
     */
    function onPostRequestTimeout(PostRequestTimeout memory incoming) public virtual override onlyHost whenNotPaused {
        Message memory message = abi.decode(incoming.request.body, (Message));
        address refundee = _toAddr(message.from);
        _mint(refundee, message.amount);
        emit Refunded({to: refundee, amount: message.amount});
    }

    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }

## Pausability

Both contracts inherit from OpenZeppelin's `Pausable`. The owner can pause and unpause all operations:

```solidity lineNumbers
IHyperFungibleToken(tokenAddress).pause();
IHyperFungibleToken(tokenAddress).unpause();
```

When paused, `HyperFungibleToken` blocks all ERC20 transfers (`transfer` and `transferFrom`) in addition to cross-chain `send()` and `onAccept()`. This is a full stop on all token movement — use it for emergency situations or during migrations.
