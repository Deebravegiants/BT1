## Finding: Status/TxHash Misreport for Same‑Asset Batch Withdrawals in PoA Bridge

### Title
Same-asset batch withdrawals cause PoA Bridge to misreport completion status/txHash of the wrong withdrawal - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal()` and the standalone `waitForWithdrawalCompletion()` helper in `internal-utils` both resolve which withdrawal record in a settlement response belongs to a particular withdrawal request using `findMatchingWithdrawal`, which matches **only by `assetId`** (derived from `near_token_id`), ignoring `destinationAddress`, `amount`, and the withdrawal `index`. When a single settled NEAR intent contains two or more withdrawals of the *same* asset (a legitimate, unrestricted use case via the SDK's batch withdrawal API), `Array.prototype.find()` returns the same record for every lookup, so the SDK can report withdrawal B's `txHash`/status as if it belonged to withdrawal A.

### Finding Description
`findMatchingWithdrawal` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`: [1](#0-0) 

is called from `describeWithdrawal`: [2](#0-1) 

The comment explicitly documents that it only distinguishes withdrawals by `assetId`, not by index or amount, and that multiple withdrawals of the same token in one transaction are "not supported" — but the code does not fail loudly for that case, it silently returns whichever matching record `.find()` locates first, for *every* index lookup.

The same pattern exists in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`: [3](#0-2) 

Nothing in the batch-withdrawal path prevents a caller from constructing a batch with two same-`assetId` withdrawals to different `destinationAddress`. `IntentsSDK.createWithdrawalIntents` / `processWithdrawal` loop over `withdrawalParams` per-bridge with no de-duplication check: [4](#0-3) [5](#0-4) 

`createWithdrawalIdentifiers` assigns a per-route running `index` to each withdrawal request, which is passed down to `describeWithdrawal`, but `PoaBridge.describeWithdrawal` never actually uses that `index` to disambiguate — it only uses `assetId`.

### Impact Explanation
Before the attacker/caller's action: each withdrawal in a batch should independently report its own completion status and destination transaction hash, matching the on-chain outcome for that specific `(index, destinationAddress, amount)` tuple.

After: with two same-asset withdrawals in one settled transaction, both `describeWithdrawal` calls (for index 0 and index 1) can return the *same* record — e.g., withdrawal #0 (destined for address X) gets reported as "completed" with the `transfer_tx_hash` that actually belongs to withdrawal #1 (destined for address Y), while the real destination for X may still be pending or use a completely different transaction. This breaks the "status reported == on-chain outcome" equality relied upon by any integrator that credits/marks-as-settled a specific withdrawal based on the SDK's `waitForWithdrawalCompletion` / `createWithdrawalCompletionPromises` / `processWithdrawal` output, matching the explicitly listed High-impact class: "a status or hash misreport making an integrator credit or refund twice."

This requires no malicious/adversarial actor — a normal user or integrating operator that batches two same-token withdrawals to two recipients in one signed intent (a legitimate use of the documented batch withdrawal feature) triggers it.

### Likelihood Explanation
Likelihood is moderate: it requires only that a batch contain two-or-more withdrawals of the same underlying NEP-141 asset routed through the PoA bridge, which is not blocked or validated anywhere in the withdrawal-building or fee-estimation code paths. This is a realistic pattern for services that batch multiple user withdrawal requests of the same popular token (e.g., `btc.omft.near`) to different destinations in a single settlement.

### Recommendation
Disambiguate matching in `findMatchingWithdrawal` (both `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) using additional fields the API returns (`amount`, `address`) together with `assetId`, and/or explicitly reject/validate batches containing duplicate `assetId` entries before submission so silent misattribution cannot occur; at minimum, throw rather than silently returning a possibly-wrong match when more than one candidate shares the same `assetId`.

### Proof of Concept
1. Build a batch withdrawal with two entries: `{ assetId: "nep141:btc.omft.near", destinationAddress: "addrX", amount: 100000n }` and `{ assetId: "nep141:btc.omft.near", destinationAddress: "addrY", amount: 200000n }`, submitted together via `sdk.processWithdrawal({ withdrawalParams: [...] })`.
2. After settlement, POA Bridge's `getWithdrawalStatus` returns an unsorted list containing both withdrawal records for the same `near_token_id`.
3. `describeWithdrawal({ index: 0, withdrawalParams: addrX-entry })` and `describeWithdrawal({ index: 1, withdrawalParams: addrY-entry })` both call `findMatchingWithdrawal(withdrawals, "nep141:btc.omft.near")`, which returns the *same* first matching record via `.find()` in both calls (existing test at `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.test.ts:1054-1111` demonstrates matching purely by `assetId` irrespective of `index`, and the module comment at lines 410-417 confirms the same-asset multi-withdrawal collision is unhandled).
4. The caller/integrator receives `addrY`'s `transfer_tx_hash` reported for the `addrX` withdrawal (or vice versa), leading to incorrect completion accounting. [1](#0-0)

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
