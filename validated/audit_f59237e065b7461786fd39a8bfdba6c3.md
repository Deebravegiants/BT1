Audit Report

## Title
Cross-dispatch-class corruption of `BlockWeight` via un-keyed `ExtrinsicWeightReclaimed` value - (File: cumulus/pallets/weight-reclaim/src/lib.rs)

## Summary
`frame_system::ExtrinsicWeightReclaimed` is a single class-agnostic `StorageValue<Weight>` written at the end of `post_dispatch` for one extrinsic and consumed at the start of the next extrinsic's `post_dispatch` via `current_weight.accrue(already_reclaimed, info.class)`, where `info.class` is the *current* extrinsic's class rather than the class of the extrinsic that produced the value. [1](#0-0) [2](#0-1)  When a Normal-class extrinsic is immediately followed by an Operational-class extrinsic (or vice versa) in the same block, the leftover reclaim value earned against one class bucket is credited into the other class bucket, corrupting per-class `BlockWeight` accounting. The same pattern exists in `frame_system::Pallet::reclaim_weight`, used by `CheckWeight` and `WeightReclaim` extensions. [3](#0-2) [4](#0-3) 

## Finding Description
The code path is confirmed exactly as described: `ExtrinsicWeightReclaimed` is read and accrued to `current_weight` under `info.class` — the class of the extrinsic *currently* being processed — before being reduced and re-accrued with the accurate weight, and then overwritten at the end of the same function for later consumption. [5](#0-4) 

Existing unit tests (`extrinsic_already_refunded_more_precisely`, `extrinsic_already_refunded_less_precisely`, `different_dispatch_class`) in `substrate/frame/system/src/extensions/weight_reclaim.rs` all pre-set `ExtrinsicWeightReclaimed` using the *same* class as the current extrinsic's `info.class`, confirming that no test exercises the cross-class scenario. [6](#0-5) [7](#0-6) 

There is no mechanism visible in the reviewed code that resets or keys `ExtrinsicWeightReclaimed` by `DispatchClass`, nor any check comparing the class of the stored value against the current extrinsic's class before accruing it back. The storage item is a plain, unkeyed `Weight` value that persists from the end of one extrinsic's `post_dispatch` to the start of the next's, with no class tag attached, which matches the root cause described in the claim.

## Impact Explanation
If confirmed to manifest in practice, this would corrupt `frame_system::BlockWeight`'s per-`DispatchClass` accounting, potentially allowing the Normal class to exceed its intended weight/PoV budget or spuriously exhausting the Operational reserved pool — both of which are legitimate, in-scope accounting-integrity concerns for block-limit enforcement.

## Likelihood Explanation
I could not fully verify within the available iterations whether this is actually exploitable end-to-end, because I was unable to complete review of `frame_system::Pallet::reclaim_weight` in `substrate/frame/system/src/lib.rs` (the function body itself, only its existence was confirmed via grep) to check whether it clears/gates `ExtrinsicWeightReclaimed` based on class, and I was unable to trace the full executive/`apply_extrinsic` pipeline to confirm the precise interleaving assumption (i.e., whether `ExtrinsicWeightReclaimed` is guaranteed reset between extrinsics of different classes by some mechanism not yet inspected, such as in `frame_executive`). The code shown is consistent with the claim's described mechanics, but full confirmation of the exploit's reachability under real block execution (extension pipeline ordering, whether `reclaim_weight`'s internal logic differs meaningfully from what's quoted, and whether any surrounding guard exists elsewhere) was not completed due to the iteration limit.

## Recommendation
Key `ExtrinsicWeightReclaimed` by `DispatchClass`, or store `(Weight, DispatchClass)` pairs, so the undo step in both `frame_system::Pallet::reclaim_weight` and `StorageWeightReclaim::post_dispatch_details` accrues the leftover value back into the class it was originally taken from. Alternatively, clear/ignore the stored value whenever `info.class` differs from the class recorded with it.

## Proof of Concept
As proposed in the claim: construct a mock block executing two extrinsics through the full `TxExtension` pipeline — a Normal-class extrinsic with non-zero unspent weight followed immediately by an Operational-class extrinsic — and assert that each class's `BlockWeight` bucket reflects only its own extrinsic's consumption, not a leaked/credited amount from the other class.

**Note on confidence**: Due to the iteration limit, I was unable to fully read `frame_system::Pallet::reclaim_weight`'s implementation in `substrate/frame/system/src/lib.rs` or the executive's extrinsic-application loop to conclusively confirm there is no existing guard preventing this cross-class credit. The evidence gathered strongly supports the claim's described code behavior in `cumulus/pallets/weight-reclaim/src/lib.rs`, but a full confirmation would require inspecting `reclaim_weight`'s body directly. I recommend a Devin session with terminal/build access to run the proposed integration test and confirm the exploit deterministically, since the static review here is consistent with — but not a complete substitute for — a running proof of concept.
