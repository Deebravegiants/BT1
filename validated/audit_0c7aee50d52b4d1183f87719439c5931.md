### Title
Webhook `shop-domain` header is trusted but not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` identity for a webhook entirely from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, while `Utils::HmacValidator` only validates the HMAC over the raw request body. Because the header is never part of the signed material, the binding `hmac_verified_bytes == bytes_used_for_shop_identity` does not hold: an attacker who owns a legitimate merchant install of the app can capture one of their own valid (body, hmac) webhook pairs and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop, producing a request that passes `HmacValidator.validate` yet is attributed to a different tenant.

### Finding Description
`Utils::HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns just the raw HTTP body: [2](#0-1) 

But the `shop` value used for downstream tenant-scoped handling is read straight from the `shop-domain` header, which is disjoint from the signed bytes: [3](#0-2) 

`Registry.process` only checks the HMAC before dispatching, then hands the header-derived (unauthenticated) `shop` value straight into the handler's metadata: [4](#0-3) 

The equality that should hold is: `shop bound by HMAC == shop trusted by handler`. In this gem it is instead: `hmac validates body bytes only`, while `shop = header value, not covered by hmac`. Any attacker who can obtain a genuine `(body, hmac)` pair for a webhook delivered to their own shop (trivial — they own that shop and receive its webhooks at their app endpoint) can resend that exact body/hmac pair to the app's webhook receiver with a different `shopify-shop-domain` header. `HmacValidator.validate` still returns `true` because it never inspects the header, and `Registry.process` forwards the forged shop into `WebhookMetadata`, letting the host application apply another tenant's webhook payload under an attacker-chosen shop identity.

### Impact Explanation
This breaks the tenant-isolation boundary that host applications rely on `WebhookMetadata#shop` to enforce. An attacker-controlled shop can cause a webhook payload to be processed as if it originated from another (victim) shop, e.g. injecting fabricated order/product/customer data attributed to a shop the attacker does not own, or triggering shop-scoped side effects (data writes, uninstall/reinstall handling, billing events) against a foreign tenant. This satisfies the Critical "cross-tenant access" impact category, since the tenant boundary (`shop`) that gates per-merchant data processing is not authenticated by the same mechanism (`hmac`) that gates payload integrity.

### Likelihood Explanation
Moderate-to-high likelihood. The attacker only needs their own legitimate app install (no leaked secrets, tokens, or `client_secret` are required) to obtain a valid `(body, hmac)` pair, and then simply forges the shop header when POSTing to the app's public webhook endpoint. The gem's own `HmacValidator`/`Request` design does nothing to prevent it, since header integrity was never part of the threat model.

### Recommendation
Include the shop domain (and any other host-application-trusted metadata such as topic/webhook-id) in the HMAC-covered signable string, or independently cross-check the header-derived `shop` against a value obtained through an authenticated channel (e.g., match against the `shop` recorded for the specific `webhook_id` at registration time) before dispatching to handlers. At minimum, document clearly that `WebhookMetadata#shop` is not itself HMAC-authenticated so host applications don't implicitly trust it for tenant-scoping decisions.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook at the app's endpoint with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC(secret, B)` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the same request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a request object whose `hmac` and `to_signable_string` are unaffected by the header change: [5](#0-4) 
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `to_signable_string` (the unchanged body): [6](#0-5) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes attacker-supplied body content as if it came from the victim's store.
