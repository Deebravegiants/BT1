### Title
Unsafe raw `IERC20.transfer` calls dispatched through `CallDispatcher` ignore boolean return value, causing broken dust/sweep accounting - (File: `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/src/apps/IntentGatewayV2.sol`, `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentsBase._execute`, `IntentGatewayV2.placeOrder` (predispatch sweep path) and the Tron variant of `IntentGatewayV2` build raw calldata with `abi.encodeWithSelector(IERC20.transfer.selector, ...)` and dispatch it through `CallDispatcher.dispatch`, which only checks the low-level `call` succeeded — it never decodes/validates the returned boolean. [1](#0-0) 

### Finding Description
`CallDispatcher.dispatch` executes each `Call` with a raw `to.call{value: call.value}(call.data)` and only reverts if `success` is false; it never inspects `result` to confirm the ERC20 token actually returned `true`. [1](#0-0) 

`IntentsBase._execute` uses this dispatcher to sweep dust left on the untrusted `dispatcher` contract after arbitrary output calldata execution: it reads `IERC20(token).balanceOf(dispatcher)`, immediately emits `DustCollected(token, balance)` as if the funds were captured, and only afterward issues the raw `transfer` call via `CallDispatcher.dispatch`. [2](#0-1) 

The same pattern (sweep-then-assume-success) is used in the predispatch flow of `IntentGatewayV2.placeOrder`, where a `Call` is built with `abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)` and dispatched via `ICallDispatcher(dispatcher).dispatch(...)`. [3](#0-2) 

For any ERC20 token that does not revert on a failed transfer but instead returns `false` (legacy non-compliant tokens such as old ZRX, or any custom token with this semantic), the low-level `call` in `CallDispatcher.dispatch` reports `success = true` even though no tokens moved, because the dispatcher never decodes the `bool` return value. This is the same root cause identified in the analogous report: code that accepts non-standard ERC20 return semantics without validating them, leading to silent no-ops that corrupt accounting.

In `IntentGatewayV2.placeOrder`, the subsequent balance-delta check (`received = IERC20(token).balanceOf(address(this)) - balancesBefore[i]`) does correctly detect a silent no-op and sets `order.inputs[i].amount = 0` [4](#0-3) 
so that specific path is self-correcting. However, `IntentsBase._execute` has **no such balance-delta verification** — `DustCollected(token, balance)` is emitted unconditionally before the transfer's success is confirmed against an actual balance change, and the code does not re-check `dispatcher`'s or `address(this)`'s balance afterward. [5](#0-4) 

### Impact Explanation
If the residual output token left in the untrusted `dispatcher` after `_execute`'s arbitrary calldata execution is a non-compliant ERC20 that returns `false` instead of reverting on failed transfer (e.g., due to a paused token, blacklist, or non-standard implementation), the sweep silently no-ops: tokens remain stranded in the `CallDispatcher` contract while the gateway has already emitted `DustCollected` and treats the funds as protocol-owned. Any downstream accounting or governance sweep that relies on the `DustCollected` event/aggregate rather than a fresh on-chain balance check will believe the protocol holds funds it does not — this is a permanent-freezing-of-funds condition for the affected tokens (they remain unreachable in the `CallDispatcher`, which has no dedicated withdrawal path besides being driven by more `Call` dispatches from a gateway).

### Likelihood Explanation
Likelihood is lower than a High because it requires: (1) an order whose output token is a non-standard ERC20 with false-return-on-failure semantics, and (2) a scenario where the token transfer legitimately fails during the sweep (e.g., recipient blacklisted, paused, or the balance changes mid-call due to reentrancy-adjacent effects from the `order.output.call`). This mirrors the judge's assessment in the referenced report that such "no-op" scenarios are lower likelihood but still break accounting when triggered — hence Medium severity rather than High.

### Recommendation
Replace the raw `abi.encodeWithSelector(IERC20.transfer.selector, ...)` calldata construction with `SafeERC20.safeTransfer`-compatible encoding, or have `CallDispatcher.dispatch` (or the caller) decode and validate the boolean return value for known ERC20 `transfer`/`transferFrom` selectors. At minimum, `IntentsBase._execute` should verify the destination balance actually increased by the swept amount before emitting `DustCollected`, mirroring the balance-delta check already present in `IntentGatewayV2.placeOrder`.

### Proof of Concept
1. Deploy a non-compliant ERC20 mock whose `transfer` returns `false` (no revert) when called by a specific caller/blacklisted state, mimicking legacy token behavior.
2. Place an order via `IntentGatewayV2`/`ExtrinsicIntents` with `order.output.call` set such that the mock token ends up with a non-zero balance on the `CallDispatcher` (`_params.dispatcher`).
3. Trigger fill/settlement so `IntentsBase._execute` runs: it reads `balanceOf(dispatcher) > 0`, emits `DustCollected(token, balance)`, and dispatches the sweep `Call` with `IERC20.transfer.selector`.
4. Have the mock token's `transfer` return `false` for this call (simulating the failure condition) without reverting; `CallDispatcher.dispatch` sees `success = true` and does not revert.
5. Observe that the token balance remains on the `CallDispatcher` (never moved to `address(this)`), while the gateway has already emitted `DustCollected` — the recorded/assumed dust and the actual location of funds diverge, and the tokens are unreachable outside of gateway-driven `Call` dispatches, i.e., stuck in the dispatcher.
