This confirms the identity-binding gap: `Webhooks::Request#shop` at [1](#0-0)  reads the tenant identity from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, but `to_signable_string` — the value that is actually HMAC-verified — is only the raw request body: [2](#0-1) . `HmacValidator.validate` verifies the signature over that signable string only [3](#0-2) , and `Registry#process` accepts the request once that check passes, then dispatches `request.shop` straight into `WebhookMetadata` for the handler without any additional check that the header shop matches anything cryptographically bound to the body [4](#0-3) .

### Title
Webhook tenant identity (`shop-domain` header) is not covered by the HMAC signature, allowing shop spoofing on genuine Shopify webhooks - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`Webhooks::Request` derives the `shop` used for tenant dispatch from an HTTP header that is excluded from the HMAC-signed payload, so the "shop verified by HMAC" and "shop acted upon by the handler" are not the same binding.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [2](#0-1) , and `Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header [1](#0-0) . `Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the `hmac-sha256` header value [5](#0-4) . Because the signature never covers the `shop-domain` header, that header can be swapped without invalidating the HMAC. `Registry#process` only checks `Utils::HmacValidator.validate(request)` [6](#0-5)  before handing `request.shop` (the unauthenticated header) to the handler as the tenant identifier [7](#0-6) . The binding the gem should enforce is `shop_verified_by_hmac == shop_used_for_tenant_dispatch`; instead it enforces `body_verified_by_hmac == body_parsed`, while `shop_header (unverified) == shop_used_for_tenant_dispatch`.

### Impact Explanation
This is an identity-binding break matching the "field acted on but not covered by the HMAC" analog class. A host application (or any component in front of it, e.g., a shared load balancer/proxy or a misconfigured webhook relay) that forwards a genuinely-signed Shopify webhook body but with a modified/attacker-controlled `X-Shopify-Shop-Domain` header would pass HMAC validation while the handler processes the payload under a different tenant's identity — a cross-tenant data-attribution issue. Note this requires something upstream of the gem (proxy, custom router, or an application that lets the header be set from unauthenticated request data) to actually let an attacker control the header value on an otherwise-genuine request; the gem itself provides no defense once that header is attacker-influenced.

### Likelihood Explanation
Low-to-moderate: exploitation requires a delivery path where the `shop-domain` header can diverge from the body's true origin while the HMAC (computed only over the body with the real `client_secret`) still validates — e.g., a genuine Shopify webhook replayed/relayed with a rewritten header, or a host framework that merges header values from less-trusted sources than the raw POST. In a pure end-to-end Shopify→app HTTPS delivery this header is not attacker-writable, so the gem-level fix (bind shop into the verified material or at minimum document/cross-check it) reduces risk from any intermediary that does not protect header integrity as strictly as body integrity.

### Recommendation
Include the `shop-domain` header value in the HMAC signable string (or otherwise cryptographically bind it), or, at minimum, cross-validate `request.shop` against a shop value embedded in the verified body/session context before dispatching to handlers, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` includes `shop` in its signed fields [8](#0-7) .

### Proof of Concept
1. Capture a legitimate Shopify webhook POST (valid body, valid `X-Shopify-Hmac-Sha256`, valid `X-Shopify-Shop-Domain: victim.myshopify.com`).
2. Replay it through any intermediary/relay that rewrites `X-Shopify-Shop-Domain` to `attacker.myshopify.com` while leaving the raw body untouched.
3. `Utils::HmacValidator.validate(request)` still succeeds because it only hashes `@raw_body` [2](#0-1) .
4. `Registry#process` dispatches the handler with `request.shop == "attacker.myshopify.com"` [7](#0-6) , causing the payload to be attributed to the wrong tenant.
