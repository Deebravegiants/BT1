### Title
Webhook shop/topic identity not covered by HMAC signature enables cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are trusted and passed unverified to the webhook handler. Because the app's `client_secret` (used to sign webhooks) is shared across every shop that has installed the app, any merchant who has installed the app can capture a validly-signed webhook body from their own store and replay it to the app's webhook endpoint with a forged `shop-domain` header, causing the handler to process attacker-controlled data as if it came from a different (victim) tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The other identity-bearing fields, most importantly `shop`, are parsed straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the signature purely against `verifiable_query.to_signable_string`, i.e. the raw body: [3](#0-2) 

`Registry.process` trusts `request.shop` (and `request.topic`) as authoritative once the HMAC check passes, and forwards them straight into the handler's `WebhookMetadata`: [4](#0-3) 

The `api_secret_key` used to compute/verify this HMAC is the app's single `client_secret`, shared by Shopify across every shop that installs the app — it is not shop-specific. This is confirmed by `HmacValidator.validate` always signing/verifying against the single `Context.api_secret_key` (or `old_api_secret_key`), with no per-shop key material: [5](#0-4) 

Consequently, the equality the app implicitly relies on — "the shop whose data the handler will act on" == "the shop that actually produced this signed payload" — is not enforced. Only "body integrity" is proven; "which shop/topic this body belongs to" is not.

### Impact Explanation
Any user who is an ordinary merchant/admin of their own shop (an unprivileged action: simply installing the app, which any Shopify merchant can do) can:
1. Trigger some webhook-worthy event on their own store (or observe one that Shopify sends) to obtain a `(raw_body, hmac)` pair that is valid under the shared `client_secret`.
2. POST that identical body and HMAC to the app's public webhook endpoint, but with the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header changed to point at a different (victim) shop that also uses the app.
3. `Registry.process` accepts the request because `HmacValidator.validate` only checks the body/signature, and dispatches the handler with `shop: request.shop` set to the attacker-chosen victim domain.

Depending on the app's webhook handlers, this enables cross-tenant data injection/corruption (e.g. spoofing `orders/create`, `app/uninstalled`, or other lifecycle events for a shop the attacker does not own), which is a cross-tenant access vulnerability — Critical per the given impact criteria.

### Likelihood Explanation
Exploitation requires no secrets, tokens, or privileged access — only the ability to install the app on one's own store (a normal, unprivileged Shopify merchant action) and the ability to send arbitrary HTTP POST requests to the app's public webhook endpoint URL. The only "difficulty" is discovering/guessing the endpoint URL and a victim shop's `.myshopify.com` domain, both of which are typically discoverable or guessable (shop domains are often public/predictable).

### Recommendation
Bind the trusted identity fields (`shop`, `topic`, and ideally `webhook_id`/`api_version`) into the signed material, or otherwise cryptographically tie them to the signature — e.g., include them in `to_signable_string`, or require the app to independently confirm the `shop-domain` header corresponds to a shop with an active, known installation/session before trusting it. At minimum, document that `HmacValidator`/`Webhooks::Request` only proves body integrity and does not authenticate the `shop-domain` or `topic` headers, and require consuming apps to cross-check `request.shop` against a known/installed shop list before acting on webhook data.

### Proof of Concept
```ruby
# Attacker owns shop "attacker-shop.myshopify.com" and has installed the target app.
# Step 1: Attacker triggers/observes a legitimate webhook Shopify sends to the app,
# capturing the raw body and the "x-shopify-hmac-sha256" value Shopify computed
# using the app's single shared client_secret.
raw_body = captured_body   # e.g. '{"id":123,"malicious_field":"..."}'
hmac     = captured_hmac   # valid HMAC-SHA256(raw_body, app_client_secret)

# Step 2: Attacker replays it to the same public webhook endpoint,
# forging the shop-domain header to a victim shop that also uses the app.
POST https://app.example.com/webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <hmac>              # unchanged, still valid (only body is signed)
x-shopify-shop-domain: victim-shop.myshopify.com   # forged, not covered by HMAC
Body: <raw_body>                            # unchanged

# ShopifyAPI::Webhooks::Registry.process(request) will:
#   - pass HmacValidator.validate(request) because it only checks raw_body
#   - call the handler with shop: "victim-shop.myshopify.com"
# demonstrating the app cannot distinguish this from a genuine webhook for victim-shop.
