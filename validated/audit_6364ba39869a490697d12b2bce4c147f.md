**Analysis:**

The premise of the question — that `materialize_type`/`instantiate` has an "ability-inference gap" that could cause a generic wrapper to incorrectly derive `copy` for a non-copy capability payload — does not match how the verifier actually computes abilities.

`materialize_type` and `instantiate` in `type_safety.rs` are purely structural helpers that build or substitute `SignatureToken`s (e.g. `StructInstantiation(idx, type_args)`); they do not compute or cache ability sets at all. [1](#0-0) 

The actual ability check invoked by `ReadRef` is `verifier.abilities(&inner)`, which resolves to `BinaryIndexedView::abilities`. For a `StructInstantiation`, this correctly computes the ability set from the struct's *declared* abilities intersected with the abilities of each non-phantom type argument, via `AbilitySet::polymorphic_abilities`: [2](#0-1) 

This means a generic wrapper `struct Wrapper<T> has copy { cap: T }` only actually has `copy` ability for a specific instantiation `Wrapper<Capability>` if `Capability` itself has `copy`. If the capability struct is declared without `copy` (as capability/permission tokens conventionally are), `Wrapper<Capability>` will not have `copy`, and `verifier.abilities(&inner).has_copy()` at `type_safety.rs:989` will correctly return `false`, rejecting the `ReadRef`.

The same intersection-based derivation is implemented consistently across the codebase — in the Move model (`infer_struct_abilities`), the VM runtime types (`runtime_types.rs:857-880`), and the signature verifier (`signature_v2.rs`), all matching the documented Move ability rules (conditional copy/drop/store/key based on type arguments): [3](#0-2) [4](#0-3) 

There is no code path where a struct's actual instantiated ability set can diverge from this correct derivation — an attacker cannot cause a non-copy capability type to be treated as copy-able merely by wrapping it in a generic struct, because the ability of the *instantiated* type is always the intersection of the declared abilities and the type arguments' abilities, not just the declared abilities of the wrapper. This mechanism is exactly what's designed to prevent the described exploit, and it is extensively covered by the Move ability-check test suite. [5](#0-4) 

No unprivileged-input path exists that bypasses this intersection check to duplicate a non-`copy` capability via `ReadRef`.

    fn infer_struct_abilities(&self, qid: QualifiedId<StructId>, ty_args: &[Type]) -> AbilitySet {
        let (_, ty_params, struct_abilities) = self.struct_signature(qid);
        let ty_args_abilities_meet = ty_args
            .iter()
            .zip(ty_params)
            .map(|(ty_arg, param)| {
                let ty_arg_abilities = self.infer_abilities(ty_arg).1;
                if param.1.is_phantom {
                    // phantom type parameters don't participate in ability derivations
                    AbilitySet::ALL
                } else {
                    ty_arg_abilities
                }
            })
            .fold(AbilitySet::ALL, AbilitySet::intersect);
        // a struct has copy/drop/store if it's declared with the ability
        // and all it's fields have the ability
        // a struct has key if it's declared with key
        // and all fields have store
        let result = struct_abilities.intersect(ty_args_abilities_meet);
        if struct_abilities.has_ability(Ability::Key)
            && ty_args_abilities_meet.has_ability(Ability::Store)
        {
            result.add(Ability::Key)
        } else {
            result.remove(Ability::Key)
        }
    }
