### Title
Webhook shop identity spoofing — `shop-domain` header not covered by HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`, then forwards `request.shop` to the app's handler as trusted tenant identity. The HMAC signature, however, is computed only over the raw request body, never over the `shop-domain` (or `topic`/`api-version`/`webhook-id`) header. This breaks the binding: `shop domain authenticated by HMAC == shop domain delivered to handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers and are never part of the signable string: [2](#0-1) 

`Registry.process` validates the request purely via `HmacValidator.validate`, which recomputes the HMAC over `to_signable_string` (i.e., the body only) and compares it to the `hmac` accessor: [3](#0-2) [4](#0-3) 

Once the body-HMAC check passes, `request.shop` (attacker-controlled header, unauthenticated) is packaged into `WebhookMetadata` and handed to the app's handler as if it were a verified tenant identifier: [5](#0-4) 

Because the app's secret (`api_secret_key`) is shared across every shop that installs the app, any unprivileged user can install the target app on their own store (a normal, unprivileged action) and receive a legitimately-HMAC-signed webhook whose body they fully control (e.g. a product/order they create). They can then replay that exact body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop. The signature still validates (it only covers the body), so `Registry.process` accepts the request and invokes the handler with `shop: "victim-shop.myshopify.com"` even though the body actually originated from the attacker's own shop.

### Impact Explanation
Host applications commonly use `WebhookMetadata#shop` to select per-tenant state, credentials, or records to mutate (e.g., look up the victim shop's session/access token and act on its behalf, or write attacker-controlled body content into the victim's tenant record). Since the shop value here is not authenticated, this is a cross-tenant identity confusion vector reachable by any unprivileged internet user who can install the app once, satisfying the "Critical — cross-tenant access" impact bucket in a design where the app relies on this gem's shop attribution as trustworthy.

### Likelihood Explanation
Requires only that the attacker be able to install the target app on any shop they control (no special privilege) and know/guess the webhook endpoint URL (typically public/documented). No access token, `client_secret`, or privileged account is needed — the attacker only reuses a webhook payload their own shop legitimately received.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the signed material, or require the host application to separately verify `shop-domain` against a known-installed-shop table keyed by the same request instance; document clearly that `WebhookMetadata#shop` is not itself HMAC-protected and must be cross-checked before being used to select tenant-scoped state.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (unprivileged, self-service).
2. Attacker triggers a benign webhook (e.g., `products/create`) whose body the attacker controls, and captures the raw body + the valid `X-Shopify-Hmac-Sha256` header Shopify sent (valid because it's computed with the app's shared `api_secret_key` over that body).
3. Attacker replays this exact HTTP request to the app's webhook endpoint, but replaces the `X-Shopify-Shop-Domain` header with `victim-shop.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds (body/HMAC unchanged), and `Registry.process` in `lib/shopify_api/webhooks/registry.rb` invokes the handler with `shop: "victim-shop.myshopify.com"` and the attacker's chosen body, confusing tenant attribution in the host app.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
