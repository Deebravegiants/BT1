### Title
Webhook shop-domain (and topic/webhook-id) not covered by HMAC signature, enabling cross-tenant event spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, so the HMAC verified by `Utils::HmacValidator` binds nothing but the JSON payload. The `shop`, `topic`, `webhook_id`, and `api_version` values — all pulled straight from unauthenticated HTTP headers — are handed to the app's `WebhookHandler` as trusted tenant-identifying metadata without ever being covered by the signature.

### Finding Description
`Registry.process` only calls `Utils::HmacValidator.validate(request)` before dispatching to the handler: [1](#0-0) 

`HmacValidator.validate_signature` recomputes the HMAC over `verifiable_query.to_signable_string` and compares it to the received `hmac`: [2](#0-1) 

For webhooks, `to_signable_string` is defined as just the raw body: [3](#0-2) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read directly from attacker-controllable HTTP headers with no relation to the signed bytes: [4](#0-3) 

These unverified fields are then packaged into `WebhookMetadata` and passed to the app's handler as if they were authenticated: [5](#0-4) [6](#0-5) 

This breaks the identity binding `shop authenticated == shop acted upon`: the HMAC authenticates only the body bytes, not the shop the event is attributed to. By contrast, the OAuth callback verifier in this same gem does bind `shop` into the signed string (`shop` is part of the HMAC input in `AuthQuery#to_signable_string`): [7](#0-6) 

showing the gem is capable of, but does not apply, this binding for webhook requests.

### Impact Explanation
Because a single app-wide `api_secret_key` is shared by all merchants who install the app, any merchant that installs the app (an unprivileged internet user relative to other tenants) can capture a legitimately-signed `(raw_body, hmac)` pair delivered to their own shop's webhook endpoint, then replay that exact body/hmac pair to the same webhook endpoint while substituting a different `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`webhook-id`) header pointing at another tenant. `HmacValidator.validate` still succeeds because only the body is checked, and `Registry.process` forwards the attacker-chosen `shop` value straight into `WebhookMetadata` for the handler to act on. Any host application that uses `data.shop` from the webhook handler to look up tenant records, apply billing/inventory changes, or trigger tenant-scoped side effects can be tricked into attributing another merchant's data/action to itself — a cross-tenant integrity issue.

### Likelihood Explanation
Exploitation requires only that the attacker control one shop that has installed the app (a normal, unprivileged position — no access token, secret, or special privilege needed) and the ability to send an HTTP POST to the app's public webhook route with forged headers, which this gem does not restrict to Shopify's IP ranges. The gem's documented processing contract (`docs/usage/webhooks.md`) recommends exactly the `Registry.process(Request.new(...))` pattern shown above, so any app following the documented usage inherits this gap.

### Recommendation
Include the tenant-identifying and routing fields (`shop`, `topic`, `webhook_id`) in the signed string used by `HmacValidator`, or otherwise cryptographically bind them to the verified payload (e.g., by requiring the app to separately confirm `shop` against a known/registered shop before trusting `WebhookMetadata#shop`). At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated header data and must not be trusted for tenant identification without independent verification.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook: headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid hmac of raw body>`, plus a raw JSON body.
2. Attacker captures this `(raw_body, hmac)` pair from their own server logs.
3. Attacker POSTs the identical `raw_body` and `hmac` to the same webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` → `HmacValidator.validate` recomputes HMAC over `raw_body` only (`lib/shopify_api/webhooks/request.rb:35-38`) — it matches, since the body is unchanged.
5. `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...))` is invoked, the app now processes the attacker's captured event as if it originated from `victim-shop.myshopify.com`.
