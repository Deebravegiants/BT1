### Title
Cross-chain transfer timeout refunds are blocked by `whenNotPaused`, freezing already-burned user funds - ([File: sdk/packages/core/contracts/apps/HyperFungibleToken.sol])

### Summary
`HyperFungibleToken.send()` burns tokens on the source chain before dispatching a cross-chain POST request. If that request times out, `onPostRequestTimeout()` is the only path that re-mints the burned tokens back to the original sender. This refund function is gated by `whenNotPaused`, so while the owner has the contract paused, users whose transfers time out cannot recover the tokens they already burned — mirroring the reported bug class where a repayment/refund action is unfairly blocked by a pause that is meant to stop *new* risk-taking actions, not settlement of funds already owed to users.

### Finding Description
In `send()`, tokens are unconditionally burned from the caller before the ISMP message is dispatched: [1](#0-0) 

If the destination never accepts the message (timeout), the *only* mechanism to make the sender whole is `onPostRequestTimeout`, which re-mints the previously burned amount: [2](#0-1) 

This function carries the `whenNotPaused` modifier, identical to `send()` and `onAccept()`: [3](#0-2) 

`pause()`/`unpause()` are owner-controlled and are documented to pause "all cross-chain operations (send and receive)": [4](#0-3) 

The relayer submits the timeout proof, the ISMP host verifies it and invokes `onlyHost`-gated `onPostRequestTimeout` — this is a message-relay-triggered code path reachable by any relayer submitting a valid timeout proof, not merely an admin action. Pausing the contract for a legitimate reason (e.g., to stop new transfers during an incident) simultaneously blocks *settlement of debts already incurred by burning tokens* for any in-flight message that times out during the pause window. Unlike `send()` (which prevents new burns) or `onAccept()` (which prevents new mints from untrusted sources), `onPostRequestTimeout` only returns funds that a user already gave up — there is no new risk introduced by allowing it to proceed while paused. Blocking it does not eliminate risk; it just delays it and can compound losses (e.g., if the paused period is extended or the pause becomes effectively permanent due to a compromised/unavailable owner), a direct analog of the referenced report where `repayBorrow`/`repayInterest` should remain callable under pause because paying down a debt cannot itself create new risk.

The identical pattern is duplicated across:
- `HyperFungibleTokenUpgradeable.onPostRequestTimeout` [5](#0-4) 
- `WrappedHyperFungibleToken.onPostRequestTimeout` [6](#0-5) 
- `WrappedHyperFungibleTokenUpgradeable.onPostRequestTimeout` [7](#0-6) 

For the wrapped variants, the impact is more severe: they hold real underlying ERC20/WETH collateral, so a blocked timeout refund freezes actual escrowed value, not just re-mintable synthetic supply.

### Impact Explanation
Any user whose `send()` transfer times out while the contract is paused has their burned tokens (and, for the wrapped variants, their underlying escrowed collateral) locked until an owner action (`unpause()`) occurs. If the owner is unresponsive, compromised in a way that prevents unpausing, or deliberately keeps the pause active, affected users' funds remain frozen indefinitely with no alternative recovery path in the contract. This constitutes freezing of user funds that rightfully belong to them, triggered by a normal operational action (pause) rather than by any fault of the user.

### Likelihood Explanation
Likelihood is moderate-to-high: pausing is an expected operational lever (e.g., during an incident response) that owners are likely to exercise, and cross-chain message timeouts are a routine part of ISMP operation (network congestion, relayer unavailability, destination-chain issues). Any timeout that occurs to fall within a pause window — even a short, well-intentioned one — immediately locks the affected user's funds until unpause.

### Recommendation
Remove the `whenNotPaused` modifier from `onPostRequestTimeout` in `HyperFungibleToken.sol`, `HyperFungibleTokenUpgradeable.sol`, `WrappedHyperFungibleToken.sol`, and `WrappedHyperFungibleTokenUpgradeable.sol` (and any equivalent refund-only path), so that returning previously escrowed/burned funds to users is always possible regardless of pause state. Restrict `whenNotPaused` to functions that create new outbound risk (`send()`, `onAccept()`, ERC20 `transfer`/`transferFrom` if intended), consistent with the principle that pausing should stop new exposure, not the settlement of existing obligations.

### Proof of Concept
1. Owner calls `pause()` on `HyperFungibleToken` (or a wrapped variant) for operational reasons.
2. A user had previously called `send()`, burning `amount` tokens and dispatching a POST request that is now in flight.
3. The destination-chain request times out; a relayer submits the timeout proof to the ISMP host on the source chain.
4. The host attempts to call `onPostRequestTimeout` — this reverts due to `whenNotPaused`, since the contract is still paused.
5. The user's burned tokens (or underlying collateral in the wrapped variant) remain unrecoverable until the owner calls `unpause()`; if the owner never does (key loss, governance delay, intentional freeze), the funds are permanently locked with no alternative recovery mechanism in the contract.

    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }

    /**
     * @notice Handles timeout of a previously dispatched cross-chain transfer
     * @dev Called by the ISMP host when a sent message times out without being delivered.
     * Attempts to unwrap WETH and refund native tokens.
     * @param incoming The timed-out POST request and the relayer that submitted the timeout proof
     */
    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }
