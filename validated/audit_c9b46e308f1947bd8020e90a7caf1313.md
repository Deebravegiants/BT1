Confirmed: `Router.sol`'s `_computeBuy` still contains an unguarded version of exactly this underflow class, unpatched, and it is reachable by any unprivileged trader via `Zap.buy`.

### Title
`Router._computeBuy`'s overflow-cap branch underflows and reverts once a token donation makes `tokenBalance() > reserveToken`, DoS'ing the terminal curve buy - ([File: packages/contracts/src/Router.sol])

### Summary
`Router._computeBuy` caps `tokensOut` at `pair.tokenBalance()` on the final, curve-draining buy and back-calculates `amountInUsed` from `cappedReserveToken = reserveToken - tokensOut`. This subtraction assumes `tokenBalance() <= reserveToken`, an invariant that is normally true but that the codebase's own regression tests demonstrate can be violated by a plain ERC20 donation of the launched `Token` directly to the pair. When violated, `reserveToken - tokensOut` underflows and reverts, permanently DoS'ing the capped/terminal buy path for that token.

### Finding Description
`_computeBuy` computes the capped branch as:
```solidity
uint256 realBalance = pair.tokenBalance();
if (tokensOut > realBalance) {
    tokensOut = realBalance;
    uint256 cappedReserveToken = reserveToken - tokensOut;   // assumes reserveToken >= tokensOut(=realBalance)
    if (cappedReserveToken == 0) revert OverflowCapDegenerate();
    uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
    amountInUsed = cappedReserveAsset - reserveAsset;
}
``` [1](#0-0) 

The codebase itself documents and tests that `pair.tokenBalance()` (a live `IERC20.balanceOf`, donation-inflatable) can exceed the stored `reserveToken` after a `Token` donation to the pair — this is exactly the "donation attack" regression the team already patched in `Bonding.previewLtUntilGraduation`: [2](#0-1) 

The invariant `tokenBalance() < reserveToken` is asserted to hold "at every state of the curve" under **honest** operation only (no donation): [3](#0-2) 

But `_computeBuy` (unlike `previewLtUntilGraduation`, which was fixed with an explicit `if (realBalance >= reserveToken) return ...` guard) has no such guard: [4](#0-3) 

Once an attacker (any unrelated wallet, using standard `ERC20.transfer`) donates enough `Token` to the pair to push `tokenBalance() > reserveToken`, any subsequent buy whose uncapped `tokensOut` (computed from the constant-product formula) exceeds `realBalance` enters the capped branch, and `reserveToken - tokensOut` underflows and reverts with a Solidity Panic. This branch is guaranteed to trigger for the terminal/large buy that would otherwise drain or graduate the curve — this is the buy class exercised by `test_inv_overflowCap_refundsLt`, `previewLtUntilGraduation`'s companion "supply-leg" logic in `_prepareGraduationLiquidity`/`triggerGraduation`, and the general large-buy/graduation-completing flow used throughout `Zap.buy`.

### Impact Explanation
This bricks the curve's terminal/capped buy path for any token whose pair has received a `Token` donation large enough to invert `tokenBalance()` vs `reserveToken` (the same donation mechanics the team's own `_stageDonationAttack` test helper demonstrates are trivially reachable and cheap). Concretely:
- Large buys that would otherwise complete the curve and trigger graduation start reverting with an unhandled Panic instead of executing.
- `Zap.buy`'s pre-sizing (`Router.previewBuy` → `_computeBuy`) and the actual `Router.buy` call both revert, so no unprivileged buyer can execute the terminal-size buy, freezing the token below its true final price and blocking a legitimate, cheap-to-reach graduation path.
- This is a fund-freezing/DoS impact matching the Medium-severity bar of the referenced report: a specific, reachable, unprivileged-transaction combination (`Token.transfer(pair, donation)` + `Zap.buy` of a large amount) makes a core public entry point permanently revert for that token.

### Likelihood Explanation
High reachability: any wallet can call `ERC20.transfer` (the launched `Token` supports normal transfers) to donate tokens directly to the pair address, and any unrelated buyer can then submit a large `Zap.buy`. The team's own test suite proves the preconditions (`realBalance > reserveToken`) are reachable with a single drain-and-donate sequence costing only the price of buying and donating tokens on the curve — the exact scenario is already reproduced in `test_donation_realBalanceExceedsReserveToken`, just applied there to a different function (`previewLtUntilGraduation`) rather than `_computeBuy`.

### Recommendation
Mirror the fix already applied to `Bonding.previewLtUntilGraduation`: guard `_computeBuy`'s capped branch against `realBalance >= reserveToken` (return/clamp instead of subtracting), e.g.:
```solidity
uint256 realBalance = pair.tokenBalance();
if (tokensOut > realBalance) {
    tokensOut = realBalance;
    if (realBalance >= reserveToken) revert OverflowCapDegenerate();
    uint256 cappedReserveToken = reserveToken - tokensOut;
    ...
}
```
This aligns `_computeBuy` with the donation-resistance guarantee already established for `previewLtUntilGraduation` and prevents the underflow panic on donation-inflated pairs.

### Proof of Concept
1. Launch a token normally via `Zap.createToken` (creates curve with `Token`/LT `Pair`).
2. Attacker (any wallet) buys a sizable amount of `Token` through the curve (`Bonding.buy`/`Zap.buy`), receiving real `Token` balance — as done in `_stageDonationAttack`: [5](#0-4) 
3. Attacker calls `Token.transfer(pairAddr, donatedTokens)`, inflating `pair.tokenBalance()` above the stored `reserveToken` — this exact state is asserted in `test_donation_realBalanceExceedsReserveToken`: [6](#0-5) 
4. Any user then submits a large `Zap.buy` sized to trigger the overflow-cap branch in `Router._computeBuy` (the same buy-size class exercised by `test_inv_overflowCap_refundsLt`): [7](#0-6) 
5. Inside `_computeBuy`, `tokensOut` is capped to `realBalance` (now > `reserveToken`), and `cappedReserveToken = reserveToken - tokensOut` underflows, reverting the entire buy transaction with a Panic — bricking that token's terminal buy/graduation path.

    // A TOKEN donation that drives `realBalance > reserveToken` previously

    // cascading into a `Zap.buy` DoS. Guard added; tests pin the fix.

    function _stageDonationAttack(
        address tokenAddr
    ) internal returns (uint256 drainLtSpent, uint256 donatedTokens) {
        address pairAddr = bonding.getTokenInfo(tokenAddr).pair;
        address drainer = makeAddr("donationDrainer");
        // Size the drain so `tokensOut > 250M` (the LP-reserve floor) under
        // any `VIRTUAL_LIQUIDITY_USD`. Constant-product math gives
        // `tokensOut = TOTAL_SUPPLY × ltIn / (virtual + ltIn)`, which crosses
        // 250M (= ¼ of TOTAL_SUPPLY) when `ltIn = virtual / 3`. Spending the
        // full opening virtual reserve lands `tokensOut = 500M` — plenty of
        // headroom to push `realBalance > reserveToken` after the donation.
        drainLtSpent = _initialVirtualLt();
        lt.mintDirect(drainer, drainLtSpent);
        if (!bonding.isRouter(drainer)) bonding.addRouter(drainer);
        vm.startPrank(drainer);
        lt.approve(address(curveRouter), drainLtSpent);
        bonding.buy(drainLtSpent, tokenAddr, 0, drainer);
        vm.stopPrank();
        donatedTokens = Token(tokenAddr).balanceOf(drainer);
        vm.prank(drainer);
        Token(tokenAddr).transfer(pairAddr, donatedTokens);
    }
