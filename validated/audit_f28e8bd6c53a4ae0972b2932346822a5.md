### Title
Webhook `shop` header not covered by HMAC allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` binds the HMAC signature only to the raw request body via `to_signable_string`, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unsigned HTTP headers. `Utils::HmacValidator.validate` therefore only proves "this body was signed with the app's client secret at some point," not "this body came for this shop/topic." Since the app's `client_secret` (used to compute every merchant's webhook HMAC) is shared across all shops installing the app, any merchant who receives their own legitimate webhook (valid `body` + `hmac`) can replay that exact `body`/`hmac` pair to the app's webhook endpoint while substituting a different `shop-domain`, `topic`, or `webhook-id` header — the signature will still validate because none of those fields are part of the signed string.

### Finding Description
`VerifiableQuery#to_signable_string` is the value that `HmacValidator.validate_signature` HMACs and compares against the received `hmac` ( [4](#0-3) ). For webhooks, `Request#to_signable_string` returns `@raw_body` only ( [5](#0-4) ), while `shop`, `topic`, `webhook_id`, and `api_version` are pulled unauthenticated from headers via `shopify_header` ( [6](#0-5) ).

`Registry.process` validates only the HMAC of the body, then trusts `request.shop` and `request.topic` to dispatch and populate `WebhookMetadata` passed to the app's handler: [2](#0-1) 

This breaks the intended binding: `shop attributed to the webhook == shop that produced the signed bytes`. In reality the HMAC only proves the *body bytes* were signed with the shared `client_secret`; it says nothing about which shop, topic, or webhook the body belongs to. Because the same `client_secret` is used to compute HMACs for every merchant's webhooks for a given app, an attacker who is a legitimate (but malicious) merchant of the app can:
1. Receive their own genuine webhook (`raw_body`, `X-Shopify-Hmac-Sha256`) from Shopify.
2. Replay that identical `raw_body` + `hmac` to the app's webhook endpoint, but with `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) rewritten to a victim shop or a different topic.
3. `HmacValidator.validate` still returns `true` since it only checks the body bytes, so `Registry.process` proceeds and invokes the handler believing the payload originated from the victim shop/topic.

### Impact Explanation
This is a cross-tenant integrity/authentication issue: the app's webhook handler makes trust decisions (e.g., which shop's local records to update, which topic-specific side effects to run) based on `WebhookMetadata#shop`/`#topic`, values that are not cryptographically bound to the payload. An attacker-controlled merchant tenant can forge webhook deliveries impersonating another shop or a different topic while reusing a validly-HMAC'd body, letting them inject data attributed to another tenant or trigger unintended topic handlers (e.g., firing a `customers/redact` or `shop/redact` handler for an arbitrary shop id) purely from their own webhook traffic — a cross-tenant access issue as covered by the Critical impact bucket.

### Likelihood Explanation
Exploitation requires only that the attacker operate a shop that has this app installed (an unprivileged action available to any internet user who installs the app) and be able to send an HTTP request to the app's public webhook endpoint with attacker-chosen headers — no access token, `client_secret`, or privileged account is needed. Capturing one's own legitimate webhook body/HMAC pair is straightforward since Shopify delivers webhooks to any installed app.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (and `api_version`) in the signed string used to validate webhook authenticity, or otherwise cryptographically bind them to the body before trusting them for dispatch — e.g., verify that the shop domain returned in headers matches an expected/registered shop for that webhook subscription, and consider using a per-shop derived secret or check `X-Shopify-Shop-Domain` against session/tenant data already known to the app rather than trusting the header verbatim.

### Proof of Concept
```ruby
require "shopify_api"
require "openssl"
require "base64"

secret = ShopifyAPI::Context.api_secret_key
body = '{"id":1,"note":"legit payload for attacker-shop.myshopify.com"}'
hmac = Base64.encode64(OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, body)).strip

# Attacker captured this (body, hmac) pair from their OWN shop's legitimate webhook delivery.
# Now they replay it, but claim it's from the victim shop / different topic:
forged_headers = {
  "x-shopify-topic" => "shop/redact",              # attacker-chosen topic
  "x-shopify-hmac-sha256" => hmac,                  # unchanged, still validates against body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-chosen shop
  "x-shopify-webhook-id" => "arbitrary-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true because to_signable_string == body only;
#    handler is invoked with WebhookMetadata(shop: "victim-shop.myshopify.com", topic: "shop/redact", ...)
```
