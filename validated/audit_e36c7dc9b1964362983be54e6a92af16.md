### Title
Webhook shop identity not covered by HMAC allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` binds the HMAC signature only to the raw request body, while the `shop` (and `topic`, `webhook_id`, `api_version`) values used by `ShopifyAPI::Webhooks::Registry.process` are taken from unauthenticated HTTP headers. Any party that has ever received one valid signed webhook (e.g. by installing the app on their own store) can replay that exact `(body, hmac)` pair while substituting an arbitrary `shop-domain` header, and the gem will report the request as HMAC-valid and hand the attacker-chosen shop identity to the app's webhook handler.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in that signable string: [2](#0-1) 

`Registry.process` treats a passing `Utils::HmacValidator.validate(request)` check as authorization for the entire request, then forwards the header-derived, unauthenticated `request.shop` straight into `WebhookMetadata` given to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes `HMAC(api_secret_key, verifiable_query.to_signable_string)` and compares it to the `hmac` header — for `Request` this is `HMAC(api_secret_key, raw_body)` only: [4](#0-3) 

The identity binding that should hold is:
`shop credited to the handler == shop that Shopify actually generated this HMAC for`

What is actually verified is only:
`HMAC(api_secret_key, raw_body) == received_hmac`

Since a single app has one `api_secret_key` shared across every shop that installs it, and `shop-domain` is outside the signed material, these two statements are independent. An unprivileged attacker who is a legitimate merchant of the app (installs the app on their own store — no special privilege, no access token, no `client_secret` needed) can:
1. Capture one legitimate webhook Shopify sends to the app for their own shop: `(raw_body, hmac)`.
2. Replay this exact `(raw_body, hmac)` to the app's public webhook endpoint, but with the `X-Shopify-Shop-Domain` header changed to any victim shop domain that also uses the app.
3. `HmacValidator.validate` still succeeds because the signed bytes (`raw_body`) are unchanged and were genuinely signed by Shopify with the app's `api_secret_key`.
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with the forged victim shop string, which the app is documented to trust and act on (e.g. attributing/persisting the payload "for" `data.shop`), per the gem's own documented usage: [5](#0-4) 

This is precisely the "field acted on but not covered by the HMAC" identity-binding failure class: the gem verifies bytes it signs (`raw_body`) but then acts on a different, unauthenticated field (`shop`) as if it had been verified too.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: a request cryptographically proven only to be "some webhook body Shopify signed for this app" is delivered to the handler labeled as belonging to an arbitrary shop of the attacker's choosing. Any app that uses `data.shop` (as the gem's own documentation instructs) to route, store, or act on webhook data per-tenant can have attacker-controlled data attributed to, or overwrite state for, a victim shop it does not control — a cross-tenant access/data-integrity violation reachable by any user who can install the app on one shop.

### Likelihood Explanation
High. No secrets beyond a normal merchant relationship with the app are required — the attacker only needs to install the app on a store they control (a completely unprivileged, self-serve action) to obtain one valid `(body, hmac)` pair, then replay it against the same public webhook endpoint with a rewritten header. No access token, `api_secret_key`, or admin privileges are needed.

### Recommendation
Include the shop domain (and ideally topic/webhook_id) as part of the HMAC-signed material, or otherwise cryptographically bind them to the verified body before trusting `request.shop` in `Registry.process`/`WebhookMetadata`. At minimum, document that `shop` on `Request` is unauthenticated and must be cross-checked by the app against a known/registered shop before being trusted for tenant-scoped operations.

### Proof of Concept
```ruby
# Attacker owns shop "attacker.myshopify.com" and has the app installed there.
# Shopify sends this legitimate, correctly signed webhook to the app:
raw_body = '{"id":1,"note":"hi"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_api_secret_key, raw_body)

# Attacker replays the *same* body+hmac but swaps the shop-domain header:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac), # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (only raw_body is checked),
#    handler.handle receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
```
