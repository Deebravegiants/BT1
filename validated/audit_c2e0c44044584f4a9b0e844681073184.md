### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing tenant impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while the `shop` value used downstream by the handler is read straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) . `HmacValidator.validate` only checks the HMAC against `to_signable_string`, i.e. the body [3](#0-2) . `Registry.process` then passes `request.shop` (the unverified header) directly into `WebhookMetadata` given to the host application's handler [4](#0-3) .

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, body || shop || topic)` such that the shop attributed to a webhook is cryptographically tied to the same message that was signed. Instead the binding actually enforced is only `hmac == HMAC(secret, body)`, leaving `shop`, `topic`, `webhook-id`, and `api-version` as free-form, attacker-controlled header values that travel with — but are not bound to — the signed body.

Because these header fields are not part of the signable string, any party who possesses one valid `(raw_body, hmac)` pair — for example a merchant who has installed the app on their own store and thus legitimately receives real webhooks with valid signatures — can replay that exact body and HMAC to the app's webhook endpoint while substituting a different `shopify-shop-domain` header value. `HmacValidator.validate` will still return `true` because it never inspected the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the spoofed shop [4](#0-3) .

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` to look up which merchant's session/store the webhook body should be applied to (the documented and expected usage pattern for this field) can be made to attribute another tenant's session to attacker-supplied/replayed data, or conversely attribute the attacker's own data to a victim shop. This is a cross-tenant identity confusion rooted entirely in this gem's webhook verification logic, matching the Critical "cross-tenant access" category, since the shop identity used to select a tenant's session is not bound to the cryptographic proof of authenticity.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on at least one shop they control (a normal, unprivileged action for any Shopify merchant/developer) in order to harvest one valid `(body, hmac)` pair, then POST it to the app's public webhook endpoint with a forged `shop-domain` header. No access token, `api_secret_key`, or privileged credential is required — only observation of a legitimately delivered webhook for the attacker's own store.

### Recommendation
Bind the `shop` (and ideally `topic`) values into the signed material, or otherwise verify that `request.shop` matches an independently established relationship (e.g., that a webhook subscription/session for that shop exists and was registered by this app) before trusting it in `to_signable_string` / before `Registry.process` passes it to handlers. At minimum, document loudly that `WebhookMetadata#shop` is unauthenticated and must not be used to select tenant context without additional verification.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; trigger any webhook so Shopify sends a genuine request with body `B` and header `x-shopify-hmac-sha256: H` (valid for secret `S`).
2. Capture `(B, H)`.
3. POST to the app's webhook endpoint with body `B`, headers `x-shopify-hmac-sha256: H`, `x-shopify-topic: <same topic>`, and `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` returns `true` (it only checks `B` against `H`) [3](#0-2) .
5. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [5](#0-4) , causing the host app to act on the victim shop's identity using attacker-controlled body content.
