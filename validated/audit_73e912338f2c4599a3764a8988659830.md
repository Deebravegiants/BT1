## Analysis

The `NativeDepositOf` map is keyed `(contract, payer)` and a row is created every time a distinct payer's `charge_and_hold` falls back to the native currency (i.e., the payer had insufficient PGAS) via `record_native_deposit` [1](#0-0) , called from `charge_and_hold` on the native fallback branch [2](#0-1) . Any unprivileged caller that pays storage deposits into a target contract (e.g. via distinct signed accounts calling into the contract, each triggering a storage deposit charge) increases the distinct-payer row count for that contract, fully attacker-controlled and reachable from ordinary extrinsics.

`process_deletion_queue_batch` processes the deletion queue strictly FIFO via `queue.next()`, which always reads the entry at `delete_counter` [3](#0-2) . For the head entry, Phase 1 (`NativeDepositOf::clear_prefix`) must reach `result.maybe_cursor.is_none()` before Phase 2 (`child::kill_storage`) is even attempted [4](#0-3) . Crucially, when `maybe_cursor.is_some()`, the code does `break` out of the **entire outer loop**, not just skip to the next queue entry [5](#0-4) . Since the queue is a strict FIFO (no reordering, no skip-ahead), this means:

1. A terminated contract with an inflated `NativeDepositOf` row count sits at the head of the queue.
2. Every `on_idle` invocation spends its entire available "native key" budget draining rows for that one entry and then breaks, never reaching Phase 2 (trie kill) for that entry.
3. Because it's FIFO, **all other queue entries behind it are also blocked** — not just its own trie reclamation is delayed, but the entire deletion queue is stalled behind this one entry until its `NativeDepositOf` prefix is fully drained.

This matches the invariant described: state reclamation for the trie is deferred, indefinitely if the attacker inflates payer count enough, purely by inflating an unrelated resource (`NativeDepositOf` row count) tied to the same queue entry. The number of rows is bounded only by how many distinct payers contributed native-fallback deposits to the contract before termination, which is attacker-controllable (an attacker deploying the target contract can arrange for many distinct funded accounts to each pay into it before terminating it, or fund victims to unknowingly do so).

I could not fully verify from available context (1) the exact benchmarked weight ratio between `deletion_queue_per_native_deposit_key` and `deletion_queue_per_trie_key` to bound the number of blocks required practically, nor (2) whether there is an upstream cap on distinct payer count per contract elsewhere in the codebase (e.g. a max-contributors check in `charge_and_hold`) that would limit the row count. No such cap was found in `deposit_payment.rs`.

### Title
FIFO deletion-queue processing lets an inflated NativeDepositOf row count for one contract stall trie reclamation for that contract and block the entire queue - (File: substrate/frame/revive/src/storage.rs)

### Summary
`ContractInfo::process_deletion_queue_batch` processes queue entries strictly FIFO and requires Phase 1 (`NativeDepositOf::clear_prefix`) to fully finish for the head entry before Phase 2 (child-trie kill) even starts; when Phase 1 doesn't finish in a block, the code breaks the entire outer loop rather than skipping to the next entry. An attacker who inflates a contract's distinct native-deposit-payer count before terminating it can make Phase 1 alone consume the whole per-block deletion budget for many consecutive blocks, indefinitely deferring the contract's trie reclamation and blocking reclamation of every other queued contract behind it.

### Finding Description
`NativeDepositOf` rows are created per distinct payer whenever a storage deposit charge falls back to the native currency, via `record_native_deposit` called from `PGasDeposit::charge_and_hold` [6](#0-5) . This is fully attacker-controllable through ordinary extrinsics: an attacker's contract can be funded by many distinct accounts (e.g., by depositing storage under many different callers or by the attacker controlling many accounts) prior to termination, producing an arbitrarily large number of `(contract, payer)` rows for a single contract.

At deletion time, `queue_for_deletion` pushes a `DeletionQueueItem` containing both the `trie_id` and `account_id` [7](#0-6) . `process_deletion_queue_batch` fetches only the FIFO head via `queue.next()` [8](#0-7) , and for that head entry runs Phase 1 (`NativeDepositOf::clear_prefix`) bounded by `key_budget`; if `result.maybe_cursor.is_some()` (i.e., Phase 1 not finished), it `break`s out of the entire batch loop, never reaching Phase 2 for this entry, and never advancing to any subsequent queue entry either [9](#0-8) . Only once Phase 1 fully completes (`maybe_cursor.is_none()`) does Phase 2 (`child::kill_storage`) run [10](#0-9) .

Because the queue has no mechanism to skip a stuck head entry and move to entries behind it, an entry with a very large `NativeDepositOf` row count occupies the head of the queue for as many blocks as it takes to drain all its rows at the per-block `key_budget`, and during that entire span neither its own child-trie nor any subsequently queued contract's trie or deposits are touched.

### Impact Explanation
This produces chain-wide state-size / PoV growth degradation: a contract's (potentially attacker-inflated) child-trie storage remains fully on-chain and unreclaimed for as long as its `NativeDepositOf` backlog takes to drain, and — more severely — this stalls reclamation of every other contract queued for deletion behind it, since the queue is strictly FIFO and a stuck head blocks all progress. This is a genuine violation of the stated invariant: reclamation of one resource (the trie) is made indefinitely deferrable by inflating an unrelated resource (payer row count) on the same queue entry, and the effect compounds to block unrelated contracts' reclamation too.

### Likelihood Explanation
Reachable entirely through unprivileged extrinsic paths: any signed account can pay storage deposits into a target contract (native fallback happens automatically when the payer lacks sufficient PGAS), and the contract owner/attacker terminates the contract afterward, pushing it (with its now-large `NativeDepositOf` backlog) into the deletion queue via `queue_for_deletion`. No governance, no privileged origin, and no special weight/fee bypass is required — the attacker only needs to arrange for many distinct payer accounts to have contributed native-fallback deposits before termination, which is feasible with sufficiently many funded accounts (e.g., cheap accounts making minimal calls that trigger a storage deposit charge).

### Recommendation
Decouple Phase 1 completion from queue-entry ordering: either (a) do not block the outer loop on an incomplete `NativeDepositOf` drain — continue to Phase 2 for that entry with whatever remaining budget exists, and/or allow subsequent queue entries to be processed independently of the stuck entry (e.g., process `NativeDepositOf` draining and trie draining as separate, independently-progressing sub-queues rather than a single two-phase gate per entry); or (b) cap/limit the number of distinct `NativeDepositOf` payer rows a single contract can accumulate, bounding the worst-case Phase 1 drain time; or (c) allow the trie-kill phase to proceed for the head entry even while `NativeDepositOf` rows remain, only removing the entry from the queue once both are drained, so PoV/state growth from the trie is reclaimed independently of the deposit-row backlog.

### Proof of Concept
Rust integration test in `substrate/frame/revive/src/tests.rs` (or a dedicated test module):
1. Create contract A with a child trie of size `N` items and exactly 1 `NativeDepositOf` row (single payer).
2. Create contract B with an identical child trie of size `N` items but `M` (large, e.g. thousands) distinct `NativeDepositOf` rows, achieved by having `M` distinct signed accounts each trigger a native-fallback storage deposit charge into B before termination.
3. Terminate both contracts in the same block (A queued before B, or vice versa — test both orderings).
4. Run `on_idle` for successive blocks, recording after each block whether A's and B's child tries have been fully removed (`child::kill_storage` returning `AllRemoved` / entry no longer in `DeletionQueue`).
5. Assert: blocks-to-full-trie-reclaim for A and B should be equal (since trie sizes are identical) — expected to **fail**, showing B's trie reclamation is delayed by many additional blocks proportional to `M`, and additionally assert that if B precedes A in the queue, A's trie reclamation is also delayed (blocked) by B's backlog, which should also fail the "independent progress" assertion.
