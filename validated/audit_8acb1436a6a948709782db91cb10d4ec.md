## Analysis

The relevant contract is `ShopifyAPI::Webhooks::Request` and how it's consumed by `ShopifyAPI::Webhooks::Registry.process`.

`Request#hmac` is computed from `Digest.hexencode(Base64.decode64(shopify_header("hmac-sha256")))`, and `to_signable_string` returns **only** `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from the `X-Shopify-Shop-Domain` header, which is never part of the signed payload: [2](#0-1) 

`HmacValidator.validate` only checks `hmac` against `to_signable_string` (the raw body), never binding any header value: [3](#0-2) 

`Registry.process` validates HMAC and then trusts `request.shop` (the unauthenticated header) to build `WebhookMetadata` dispatched to the app's handler: [4](#0-3) 

### Title
Webhook shop-domain identity is not bound by HMAC, allowing cross-tenant shop spoofing on replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw HTTP body via HMAC-SHA256, while `Request#shop` (from the `X-Shopify-Shop-Domain` header) is used unauthenticated by `Registry.process` to build `WebhookMetadata` passed to the app's webhook handler. The HMAC secret (`Context.api_secret_key`) is shared across all shops that install a given app — it is not shop-specific — so the binding `hmac-authenticated-bytes == bytes-used-for-tenant-identification` does not hold: the `shop` value is never covered by the signature.

### Finding Description
Shopify webhook authenticity for a given app is verified with a single, app-wide HMAC secret shared by every merchant/shop that has installed the app; only the raw body is signed. The `shop-domain` header, which the gem exposes as `Request#shop` and which `Registry.process` uses to determine `WebhookMetadata.shop` for the handler, is not included in `to_signable_string` and therefore is not covered by the signature. Any party who can obtain one legitimately-signed webhook (body + hmac) for a shop they control can resubmit the same body/hmac pair to the app's webhook endpoint while altering the `X-Shopify-Shop-Domain` header. `HmacValidator.validate` will still report a valid signature (it only checks the body), and `Registry.process` will hand the handler a `WebhookMetadata` object attributing the (attacker-controlled) body to an arbitrary victim shop domain.

### Impact Explanation
This breaks the identity binding between the cryptographically-verified bytes (body) and the bytes used to route/attribute the event to a tenant (shop header). A host application that trusts `WebhookMetadata.shop` — as the gem's own API contract implies it should, since it is delivered post-HMAC-validation — can be made to apply attacker-supplied webhook data (e.g., an `orders/create`, `app/uninstalled`, or GDPR payload) under a victim shop's identity, corrupting cross-tenant state or triggering side effects for a shop the attacker does not control. This matches the "Critical - cross-tenant access" impact category, since the attack crosses a tenant boundary using only a webhook the attacker legitimately received for their own store.

### Likelihood Explanation
Any merchant who installs the app receives real webhooks with valid HMACs for their own shop and can freely replay that request with a modified shop header, since no additional secret or privileged access is required — only standard, unprivileged use of the app as an installed merchant.

### Recommendation
Include the shop domain (and ideally webhook id / topic) in the HMAC-signed payload verification, or derive `WebhookMetadata.shop` only from a value that is cryptographically bound to the verified body (e.g., verify that the `X-Shopify-Shop-Domain` header matches a shop already associated with the specific webhook subscription/session, rather than trusting the header value outright after only a body-HMAC check).

### Proof of Concept
1. App receives a legitimate webhook for `attacker-shop.myshopify.com` with body `B` and header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: H` (valid signature over `B`).
2. Attacker resends the same `B`/`H` to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request#hmac` decodes `H`; `HmacValidator.validate` recomputes HMAC over `to_signable_string` (`B` only) and it matches — validation passes. [5](#0-4) 
4. `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(... shop: request.shop ...)`, where `request.shop` now returns `"victim-shop.myshopify.com"`. [6](#0-5) 
5. The host app processes attacker-controlled data under the victim's tenant identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
