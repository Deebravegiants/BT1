## Title
Webhook `shop` identity is trusted from an unauthenticated header while the HMAC only signs the raw body, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `x-shopify-shop-domain` (or `shopify-shop-domain`) header verbatim as the tenant identity handed to the app's webhook handler. That header is never part of the HMAC-signed content, so it is a field acted on but not covered by the HMAC.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `#shop` is read directly from the `shop-domain` header with no cryptographic binding to the signed payload: [2](#0-1) 

`Registry.process` validates only this body-based HMAC via `Utils::HmacValidator.validate(request)`, then immediately forwards `request.shop` (the unauthenticated header) to the app-level handler as the tenant identity: [3](#0-2) 

`HmacValidator.validate_signature` computes the HMAC purely over `to_signable_string` (i.e., the raw body) using the app's `api_secret_key`, which is identical for every shop that has installed the app: [4](#0-3) 

The equality this design implicitly assumes is:
`shop-domain header claimed by request` == `shop that the HMAC-signed body actually originated from`

This equality does not hold. Because the same `client_secret`/`api_secret_key` is shared across all shops of a given app, and the `shop-domain` header is never included in the HMAC-signed material, any party holding one valid `(raw_body, hmac)` pair for the app — trivially obtainable by installing the app on an attacker-controlled development/test store and capturing its own legitimate webhook deliveries — can replay that exact body/HMAC pair while substituting the `x-shopify-shop-domain` header with a victim shop's domain. The HMAC check in `HmacValidator.validate` still passes (it only checks the body signature), and `Registry.process` passes the forged `shop` value straight into `WebhookMetadata` for the handler to act on.

### Impact Explanation
This breaks the tenant/shop identity binding the app relies on to route webhook side effects. Any app logic keyed off `WebhookMetadata#shop` (e.g., mandatory GDPR webhooks such as `shop/redact`, `customers/redact`, updating per-shop settings, disabling/enabling features, writing to per-tenant storage) can be triggered against a shop the attacker does not control, using only credentials/webhooks the attacker legitimately receives for their own store. This is a cross-tenant action performed under a forged shop identity, which the vulnerability rules classify as Critical (cross-tenant access).

### Likelihood Explanation
Exploitation requires no privileged access beyond what any unprivileged internet user can obtain: install the target app for free on a throwaway development store, capture one valid webhook body+HMAC, then send a forged HTTP request to the app's own webhook endpoint with the same body/HMAC but a different `x-shopify-shop-domain` header. No leaked secrets, tokens, or victim-side action is required.

### Recommendation
Bind the shop identity into the material verified by the HMAC (e.g., include the shop domain in the signable string, or independently verify that the claimed shop has an active session/installation tied to the raw body's origin) rather than trusting a header that sits outside the signed payload. At minimum, document that consumers of `WebhookMetadata#shop` must cross-check it against a known-installed shop record before using it for privileged actions.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled development store `attacker.myshopify.com`. Trigger any webhook topic the app is registered for; capture the raw JSON body `B` and its `X-Shopify-Hmac-Sha256` header `H` (valid because it's signed with the app's real `client_secret`).
2. Replay the request to the app's webhook endpoint, keeping `raw_body = B` and `X-Shopify-Hmac-Sha256 = H` unchanged, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` passes because it only checks `B`/`H` against the shared secret.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls the registered handler with `shop: "victim-shop.myshopify.com"` (from `request.shop` in `lib/shopify_api/webhooks/request.rb:20-23`), causing the app to perform the webhook's associated action against the victim tenant's data/settings.
