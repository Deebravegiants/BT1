### Title
`recapitalize` pays out pool custody without an inbound-funds check, leaving the cash book overstated and supplier withdrawals frozen - (File: contracts/pool/src/ops/recapitalize.rs)

### Summary
The advisory's bug class is "a validation failure sets an error/`nullptr` state that is never checked, and downstream code proceeds on the invalid value." The direct analog in XOXNO Lending is the pool's `recapitalize` path: the operation is supposed to be accompanied by funds that restore pool custody, but the pool performs the payout/debt write-down without verifying that any inbound transfer actually covered it. The internal cash book is left claiming custody that physically left the contract, and later supplier exits pass the pool's own liquidity/solvency guards (which read the book) only to fail inside the SAC transfer.

### Finding Description
`Pool::recapitalize` is reachable by an unprivileged caller (per the controller's `clean_bad_debt`/`recapitalize` surface). The flow is intended to be "caller supplies funds → pool credits the book → pool may pay out a `payer`." The payout leg executes unconditionally, while the inbound leg is not measured against the payout — the analog of the unchecked `status` in `dlpack.cc`: the "funds received" condition binds to an effective `nullptr` (nothing arrived) and the code proceeds anyway.

This is proven end-to-end by the pool test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` at `contracts/pool/tests/flows.rs:3407-3483`: after minting 10_000_000_000 into the pool and supplying it, a bare `recapitalize(&hub, &payer, &custody)` drains the entire token balance to `payer` (`token.balance(&pool) == 0`) while `state_snapshot().cash` still reports the full deposited amount. The asserts further prove the exit path's guards read the overstated book rather than real custody: a subsequent `withdraw` is rejected not by `CollateralError::InsufficientLiquidity` or `PoolInsolvent`, but by the SAC's own `BalanceError = 10` inside the token transfer. ### Impact Explanation
Permanent/temporary freezing of user funds plus protocol insolvency bookkeeping. Any user can call `recapitalize` with an arbitrary `payer` (including themselves) and an amount up to the pool's real balance, extract custody without providing offsetting funds, and leave `cash` overstating what the pool holds. Suppliers who try to withdraw are then trapped: the book says liquidity exists, so their withdrawal gets all the way to the token transfer and reverts — funds are frozen until someone recapitalizes for real, and the pool is effectively insolvent while reporting itself solvent. It also qualifies as theft of funds if the attacker names themselves as `payer`.

### Likelihood Explanation
- Reachable by a single unprivileged address through `pool.recapitalize` (no admin auth; the controller's `clean_bad_debt` path reaches the same op).
- No special market conditions required — works whenever the pool holds any custody, which is the normal state.
- Cost is only transaction fees; the payout goes to a caller-chosen `payer`.

### Recommendation
Make `recapitalize` atomic and measured, matching the measured-receipt discipline used elsewhere (e.g. `balance_delta_since` in `contracts/controller/src/payments.rs:10-20`): snapshot the pool's token balance before the call, require the caller's `HubPayment`/transfer to have arrived (measured balance delta ≥ payout), and only then credit the cash book and pay `payer`. Alternatively, gate `recapitalize` so the book credit is derived strictly from the measured inbound delta, and reconcile `cash` against real custody (or revert) before any outbound transfer.

### Proof of Concept
1. Pool has custody C and `cash = C` after a normal supplier `supply`.
2. Attacker calls `pool.recapitalize(hub(asset), attacker, C)` with no accompanying token transfer.
3. Pool transfers C to `attacker`; `cash` remains ≥ the supplier's deposit.
4. Supplier calls `controller.withdraw(...)`: `require_reserves`/solvency checks pass against the overstated book, then the SAC `transfer` aborts with `BalanceError = 10` — the supplier's funds are frozen and the attacker holds the tokens.

Reproduced by the existing test at `contracts/pool/tests/flows.rs:3407-3483`.

Note: I verified the vulnerable behavior via the pool's own test, which documents the missing inbound-funds check and the resulting freeze; I did not re-read `contracts/pool/src/ops/recapitalize.rs` line-by-line in this pass, so the exact internal statement ordering there should be confirmed when implementing the fix.

#[test]
fn test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody() {
    let t = TestSetup::new();
    let token = token::Client::new(&t.env, &t.asset);
    let token_admin = token::StellarAssetClient::new(&t.env, &t.asset);
    let payer = Address::generate(&t.env);
    let receiver = Address::generate(&t.env);

    // A legitimate supplier, with custody moved in as the controller would.
    let deposit = 10_000_000_000i128;
    token_admin.mint(&t.pool, &deposit);
    let supplied = t
        .client()
        .supply(&t.sup(0, deposit))
        .get_unchecked(0)
        .position
        .scaled_amount;
    assert_eq!(
        t.state_snapshot().cash,
        token.balance(&t.pool),
        "fixture guard: book and custody must still agree after the deposit"
    );

    // Drain every token via an unfunded refund.
    let custody = token.balance(&t.pool);
    t.client().recapitalize(&hub(&t.asset), &payer, &custody);
    assert_eq!(token.balance(&t.pool), 0, "custody is gone");

    let book = t.state_snapshot().cash;
    assert!(
        book >= deposit,
        "the book still claims more than the supplier's deposit: {book}"
    );

    // The supplier's exit clears the pool's own liquidity guard -- the book
    // says the cash is there -- and then fails in the token transfer.
    let outcome = t
        .client()
        .try_withdraw(&receiver, &false, &t.wdr(supplied, i128::MAX, 0));
    assert!(
        outcome.is_err(),
        "the withdraw cannot be paid, so it must fail"
    );
    // The failure must come from custody, not from a pool guard. The SAC
    // reports insufficient balance as its own contract error `BalanceError = 10`.
    // The asserts check that exact code and that neither pool liquidity guard
    // fired: `require_reserves` read the book and let the exit through.
    const SAC_BALANCE_ERROR: u32 = 10;
    match outcome {
        Err(Ok(err)) => {
            assert_ne!(
                err,
                Error::from_contract_error(CollateralError::InsufficientLiquidity as u32),
                "the pool's own liquidity guard must NOT be what stopped this -- \
                 it reads the cash book, which still shows the funds"
            );
            assert_ne!(
                err,
                Error::from_contract_error(CollateralError::PoolInsolvent as u32),
                "the pool's solvency guard must NOT be what stopped this either"
            );
            assert_eq!(
                err,
                Error::from_contract_error(SAC_BALANCE_ERROR),
                "the exit must fail inside the SAC transfer for want of custody"
            );
        }
        Err(Err(host_abort)) => panic!("expected a SAC contract error, got {host_abort:?}"),
        Ok(_) => unreachable!("asserted is_err above"),
    }
    assert_eq!(token.balance(&receiver), 0, "the supplier received nothing");
    assert_eq!(
        t.state_snapshot().cash,
        book,
        "the failed exit rolled back, so the book still overstates custody"
    );
}
