### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, but the HMAC signature that `Utils::HmacValidator` verifies is computed only over the raw request body. The `shop` field that the registry hands to application webhook handlers is therefore never cryptographically bound to the signature that "authenticates" the request.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#hmac` is read from the `hmac-sha256` header: [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature strictly over `verifiable_query.to_signable_string` (i.e. the body) and compares it with the received HMAC: [2](#0-1) 

`Webhooks::Registry.process` validates only this body HMAC and then immediately trusts `request.shop` (parsed from the unauthenticated header) to build the metadata handed to the app's handler: [3](#0-2) 

So the identity binding that should hold is:
`hmac_valid(body) == true` should imply `shop == the tenant that actually produced (body, hmac)`.

In reality the equality only holds for `body`; `shop` is a free-form header value that can be swapped for any string without invalidating the HMAC check, because `shop` never enters `to_signable_string`.

### Impact Explanation
An unprivileged internet user who controls (or has access to) a legitimate Shopify store using the same app — and can therefore capture one genuine, validly-signed webhook `(raw_body, hmac)` pair delivered to the app for their own shop — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` passes the attacker-chosen `shop` value straight to the application's `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))`. Any host application that uses `shop` to route data, look up per-tenant records, or otherwise trust the webhook as originating from that tenant will act on forged data attributed to a shop the attacker does not control — a cross-tenant data integrity/access issue.

### Likelihood Explanation
Medium: it requires the attacker to possess at least one legitimate app-signed webhook body (achievable by owning/operating a store that has the same app installed, which is a normal, low-privilege position for a merchant/developer), plus the ability to POST directly to the app's webhook endpoint with custom headers (webhook endpoints are public HTTP endpoints by design). No access token, `client_secret`, or session is required.

### Recommendation
Include the shop-identifying header (`shopify-shop-domain`) as part of the string that is HMAC-verified, or otherwise cryptographically bind `shop` to the signed payload before it is exposed via `Request#shop`/`WebhookMetadata`, mirroring how `Auth::Oauth::AuthQuery` binds `shop` into its own signable string used for HMAC validation.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com` with body `B` and header `shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker (who owns `shop-a.myshopify.com` and can observe this webhook, e.g., via their own server logs) replays a POST to the app's webhook endpoint with the same body `B` and the same `shopify-hmac-sha256: H`, but sets `shopify-shop-domain: shop-victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shopify-shop-domain" => "shop-victim.myshopify.com", "shopify-hmac-sha256" => H})` is constructed; `hmac` returns the decoded `H`, `shop` returns `"shop-victim.myshopify.com"`.
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and succeeds (`lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. The handler receives `WebhookMetadata.new(..., shop: "shop-victim.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`) and processes it as if it were a genuine event for `shop-victim.myshopify.com`, even though the payload actually originated from `shop-a.myshopify.com`.
