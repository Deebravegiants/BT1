## Title
Iris-code signature computed in `make_signature` is not bound to `signup_id`, enabling cross-signup replay of a Secure-Element-signed biometric attestation - (File: `src/plans/enroll_user.rs`)

### Summary
The C4 report describes a replay class of bug: a cryptographic attestation (validator signature) is bound only to a subset of the fields that determine its intended execution context (`from_chain`, `from_handler`, `to_handler`, payload) but *not* to the `to_chain` identifier that the receiving contract must match, allowing the same signed message to be replayed in an unintended context. The orb-core analog is `make_signature` in `src/plans/enroll_user.rs`, which produces the Secure-Element signature attached to every `signup_post::request` call. That signature is computed over `ORB_ID`, `user_qr_code.user_id`, and the biometric pipeline codes/versions, but it never includes the `signup_id` that uniquely identifies *this* signup attempt/session.

The resulting `signature` is then submitted alongside `signup_id` as two independent, unlinked fields in the multipart request: [2](#0-1) 

and the plan that drives this call retries with the *same* signature across `RETRIES_COUNT` attempts and can also be invoked again for the same user with a different `signup_id` (e.g. a `Fraud`- or `Failure`-tagged retry) as long as the same biometric codes are still in scope: [3](#0-2) [4](#0-3) 

This is structurally identical to the reported bug class: the signature only asserts "these iris codes belong to this user on this orb," but not "for this specific signup attempt/session." Any backend logic that trusts the signature as attestation that this exact `signup_id`'s submission is a genuine, freshly-signed Secure-Element capture is vulnerable to the signature being replayed across a different `signup_id` for the same user/orb pair (e.g. resubmitting a previously fraud-flagged capture bundle under a new `signup_id`, or reusing a stale signed capture on a retried signup entry) — precisely the "signature valid on unintended target" pattern from the report, translated to a per-signup binding instead of a per-chain binding.

### Impact Explanation
Because `signup_id` is excluded from the signed digest, an unprivileged actor able to influence submission plumbing (e.g. replaying an intercepted/stored HTTP request, or the orb software itself resubmitting the same signature under a different `signup_id`/`reason`) can cause the backend to accept the same Secure-Element attestation as proof of a fresh capture for a *different* signup record than the one it was originally computed for. This enables cross-signup state bleed: a signature originally tied to one signup attempt (e.g. a `Fraud` or `Failure` outcome) can be misattributed to a different signup_id, undermining the integrity guarantee that the backend expects — that each `signup_id`'s submitted biometric payload was freshly authenticated by the orb's secure hardware for that specific signup event.

### Likelihood Explanation
The vulnerable code path is exercised on every signup and retried automatically up to `RETRIES_COUNT` times without a fresh `signup_id`-bound signature, and the missing field is a straightforward omission (the digest already includes 8 other fields but not `signup_id`), so no privileged access or hardware compromise is required to observe or reuse this cross-session gap — it is a design-level omission reachable through the normal, unprivileged signup flow.

### Recommendation
Include `signup_id` (and ideally `signup_reason`) as part of the data hashed and signed in `make_signature`, so the Secure-Element signature cryptographically binds the biometric attestation to the specific signup session it is submitted for, mirroring the report's recommendation to bind `to_chain` into the signed message hash.

### Proof of Concept
1. Orb performs a signup capture; `make_signature` computes `sig = Sign(ORB_ID || user_id || iris/mask codes/versions)` — note `signup_id` is absent from the input. [1](#0-0) 
2. `signup_post::request` is called with `sig` and `signup_id_A`, both attached as independent multipart fields. [2](#0-1) 
3. Because `sig` never encodes `signup_id_A`, the exact same `sig` value remains valid for a resubmission using `signup_id_B` (a different signup attempt, e.g. after retry/fraud reclassification) carrying the identical biometric codes, since nothing in the signed digest changes with the signup identifier — the backend cannot cryptographically distinguish which signup session the attestation was intended for.

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}
