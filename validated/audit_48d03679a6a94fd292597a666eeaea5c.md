This confirms the vulnerability. The `Utils::HmacValidator` only ever verifies `hmac` against `to_signable_string`, and for webhooks `to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only the HMAC and then trusts `request.shop` and passes it straight to the handler as verified metadata [3](#0-2) .

### Title
Webhook `shop-domain` header is not covered by HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, excluding the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers. `Registry.process` validates the HMAC and then unconditionally trusts `request.shop` as the identity of the originating store, breaking the binding `shop authenticated == shop bound by the signature`.

### Finding Description
`Utils::HmacValidator.validate` recomputes an HMAC over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac` [4](#0-3) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop` accessor, however, is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is never part of the signed material [5](#0-4) .

`Registry.process` raises only if the HMAC (computed on body bytes) fails; it never verifies that the `shop` header is consistent with anything else, then constructs `WebhookMetadata` from the unauthenticated `request.shop` and hands it to the app's registered handler as trusted, verified data [3](#0-2) .

Because the HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is shared across all shops that install the app, any shop that has installed the app can receive/trigger a legitimately-signed webhook for its own store, then replay that exact `raw_body` + valid `hmac` header pair while substituting an arbitrary `x-shopify-shop-domain` header value. The HMAC will still validate (it only covers the body bytes), yet the handler will process the event as if it originated from the spoofed shop. This breaks the identity binding `shop verified via header == shop bound by the HMAC signature`, since the signature binds only the body, not the shop claim.

### Impact Explanation
This allows a merchant/attacker who controls one legitimate shop install of the app to make the app process fabricated events under another tenant's identity (cross-tenant confusion): e.g., triggering `shop/redact`, `customers/redact`, `customers/data_request`, or any app-specific handler logic (billing, order sync, GDPR erasure, etc.) attributed to a victim shop's `shop` value, without ever needing that victim shop's data or credentials. Any app logic keyed off `WebhookMetadata#shop` (e.g., session/tenant lookups, data deletion, entitlement changes) inherits this spoofed identity, meeting the cross-tenant access bar.

### Likelihood Explanation
Medium-to-High: the attacker only needs a legitimate app installation on any single shop (a normal, unprivileged merchant) to obtain one validly-HMAC'd body/signature pair, then can freely swap the `shop-domain` header on replay since the header is never checked against the signature. No access to `api_secret_key`, tokens, or victim credentials is required.

### Recommendation
Bind the shop identity into the signed payload verification path — e.g., have `Registry.process` (or an app-level check) confirm that the delivered `shop` matches the shop associated with a currently known/active session or app installation record before dispatching to handlers, or require that webhook consumers independently confirm shop provenance (e.g., cross-referencing with the shop that originally registered for the topic) rather than trusting the raw header value implied by an HMAC that never covers it.

### Proof of Concept
1. App is installed on `attacker.myshopify.com`; attacker triggers any registered webhook topic (e.g. `orders/create`) for their own shop and captures the raw POST body and `x-shopify-hmac-sha256` header Shopify sent.
2. Attacker replays that exact body and HMAC header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the HMAC [1](#0-0) .
4. `Registry.process` dispatches the handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", ...)` [6](#0-5) , causing app logic to act as though the victim shop sent this webhook.
