### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , and `Utils::HmacValidator.validate` computes/checks the HMAC solely over that signable string [2](#0-1) . The `shop`, `topic`, `webhook_id`, and `api_version` values are all pulled straight from unauthenticated HTTP headers [3](#0-2)  and are never included in the signed content. `Registry.process` passes `request.shop` straight into the `WebhookMetadata` handed to the app's handler after only validating the body HMAC [4](#0-3) .

### Finding Description
The identity binding that should hold is: `shop authenticated by HMAC == shop the handler is told the data belongs to`. Because the HMAC secret (`Context.api_secret_key`) is shared across every shop that installs the same app, and the signature covers only the request body — not the `shop-domain` header — any shop that can generate one legitimately-signed webhook body (which every installing merchant can do simply by using their own store to trigger a webhook, e.g. placing an order with attacker-chosen content) can replay that exact body + HMAC pair to the app's webhook endpoint while setting an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` will pass (the body/HMAC pair is genuinely valid for the shared secret), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload came from any shop of the attacker's choosing [4](#0-3) . The app has no way to detect the mismatch because the shop identity is never part of the cryptographic proof.

Before request: `shop-domain header == real originating shop` (true, for legitimate Shopify-delivered webhooks).
After attacker's replay: `shop-domain header != real originating shop`, yet `HmacValidator.validate` still returns `true` because it only checks `@raw_body` against the HMAC [5](#0-4) [1](#0-0) .

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged internet user who is merely a merchant/installer of the app (no special privileges, no access token, no leaked secrets) can make the host application process webhook data under the identity of a different shop. Since host applications typically key data storage/side-effects (order sync, inventory updates, GDPR redaction handling, etc.) off `WebhookMetadata#shop`, this allows one tenant to inject/forge data attributed to another tenant — a cross-tenant access vulnerability.

### Likelihood Explanation
Moderate-to-high: exploitation only requires installing the app as a normal merchant (something any internet user can do for any public app) and then sending a forged HTTP request directly to the app's webhook endpoint with a captured/replayed body and its HMAC, but a spoofed `shop-domain` header. No knowledge of `api_secret_key`, access tokens, or any other credential is required — only observation of one's own legitimate webhook deliveries.

### Recommendation
Bind the shop identity into the verified data: either include `shop`, `topic`, and `webhook_id` inside the HMAC-signed material (e.g., signing a canonical string containing the headers plus body), or independently verify that the `shop-domain` header corresponds to a session/shop the receiving app actually has installed/expects for that specific delivery (e.g., cross-check against a known shop-to-webhook-id mapping) before trusting `WebhookMetadata#shop`. At minimum, document prominently that `HmacValidator` only authenticates body integrity, not tenant identity, so integrators do not rely on `request.shop` as a trusted value.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and legitimately receives a webhook for topic e.g. `orders/create` with a body they control (e.g., by placing an order with an attacker-chosen `note` field). Shopify signs this with the shared `api_secret_key`, producing a valid `x-shopify-hmac-sha256` value for that exact body.
2. Attacker captures the raw body and the `x-shopify-hmac-sha256` header from that delivery.
3. Attacker sends a POST directly to the app's webhook endpoint with:
   - same raw body,
   - same `x-shopify-hmac-sha256`,
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (arbitrary victim of attacker's choosing),
   - `x-shopify-topic: orders/create`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the body against the HMAC [6](#0-5) .
5. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)` [7](#0-6)  and processes attacker-controlled data as if it belongs to `victim-shop.myshopify.com`.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
