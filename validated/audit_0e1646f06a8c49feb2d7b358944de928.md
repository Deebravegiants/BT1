### Title
RAY-scaled market totals can overflow `i128` during accrual and permanently brick a market - (File: contracts/pool/src/interest.rs)

### Summary
Medium. A sufficiently large market can reach a state where converting scaled supply or debt back to its RAY-denominated value overflows `i128`; because every market mutation performs accrual first, the overflow permanently blocks index updates, repayments, withdrawals, liquidations, and cleanup for that market. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`Cache::load` reads the stored scaled `supplied`, `borrowed`, `supply_index`, and `borrow_index`, after which `interest::global_sync` executes one or more `accrue_step` calls before mutating the market. [4](#0-3) [5](#0-4)  Each step computes `borrowed * borrow_index / RAY` and `supplied * supply_index / RAY` through `scaled_to_original`. [6](#0-5) [7](#0-6)  `scaled_to_original` calls `Ray::mul`, which ultimately uses checked `mul_div_half_up` and panics with `MathOverflow` when the resulting RAY value does not fit in `i128`. [8](#0-7) [9](#0-8) 

The borrow-index ceiling is applied only when calculating the next index and does not bound the market-value multiplication to `i128`. [10](#0-9)  Market caps only ensure that an input token amount can be represented after token-to-RAY conversion; they do not ensure that `scaled_amount * index` remains representable after interest accrues. [11](#0-10) [12](#0-11) 

An unprivileged caller can create or enter this state through `supply`, `borrow`, and the permissionless `update_indexes` maintenance call. [13](#0-12) [14](#0-13)  Once the aggregate RAY value exceeds `i128::MAX`, `accrue_step` panics before `last_timestamp` advances, so later calls repeat the same failing calculation. [5](#0-4) [15](#0-14) 

### Impact Explanation
All users with funds or debt in the affected `(hub_id, asset)` market lose access to repayment, withdrawal, liquidation, bad-debt cleanup, revenue claims, and recapitalization paths that require market synchronization. [16](#0-15) [17](#0-16) [18](#0-17)  The production test demonstrates that after the overflow, both withdrawal and repayment revert with `MathOverflow`, and the borrow index remains below its configured ceiling. [19](#0-18)  This is permanent freezing of user funds unless a privileged contract upgrade changes the arithmetic or state. [2](#0-1) 

### Likelihood Explanation
The attack requires a very large, validly configured market and sustained high utilization, so it is capital- and time-dependent rather than immediately executable in a small market. [20](#0-19)  No privileged call is required after deployment: the attacker can supply the large balance, provide separate collateral, borrow to create high utilization, and permissionlessly trigger accrual. [21](#0-20) [14](#0-13)  The configured cap may be as high as approximately 170 billion whole tokens, while the demonstrated one-billion-token market remains far below that admitted bound. [22](#0-21) [23](#0-22) 

### Recommendation
Ensure every accrual step can make progress before stored scaled totals are multiplied by their indexes, either by performing the affected aggregate-value calculations with widened/saturating arithmetic or by enforcing dynamic market and index bounds that guarantee `scaled_amount * index / RAY <= i128::MAX`. [24](#0-23) [7](#0-6)  If index saturation is used, derive the maximum safe index from the market’s stored scaled totals before `scaled_to_original`, and add regression coverage proving that `update_indexes`, `repay`, `withdraw`, liquidation, `clean_bad_debt`, and `recapitalize` remain callable at that boundary. [2](#0-1) [19](#0-18) 

### Proof of Concept
```text
Precondition:
- DEBT is a listed 18-decimal, borrowable market whose cap admits at least
  1_000_000_000 whole tokens.
- COL is a listed collateral market with sufficient valuation and caps.

1. attacker calls:
   supply(attacker, 0, spoke_id, [(DEBT, 1_000_000_000 * 10^18)])

2. attacker supplies enough COL to the returned account and calls:
   borrow(attacker, account_id,
          [(DEBT, 980_000_000 * 10^18)],
          None)

3. After ledger time advances, any caller calls:
   update_indexes(caller, [DEBT])

   Once borrowed.raw() * borrow_index.raw() / RAY exceeds i128::MAX,
   accrue_step -> scaled_to_original -> Ray::mul reverts with
   GenericError::MathOverflow (#33).

4. Every subsequent market operation repeats the same accrual first:
   repay(caller, account_id, [(DEBT, 1)])              -> MathOverflow
   withdraw(owner, account_id, [(DEBT, 1)], None)      -> MathOverflow
   update_indexes(caller, [DEBT])                      -> MathOverflow
```

The repository’s regression test constructs the same shape: one billion 18-decimal tokens supplied, a 98% borrow, repeated index updates until `MathOverflow`, then confirms `borrow_index < MAX_BORROW_INDEX_RAY` and that both withdrawal and repayment remain bricked. [20](#0-19) [25](#0-24)

        return;

    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);

        remaining = remaining.saturating_sub(chunk);
    }

pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))

/// Returns the largest cap, in asset base units, whose ray-scaled form still
/// fits in `i128`.
///
/// Returns 0 when `asset_decimals > RAY_DECIMALS`, since the ray form is not
/// representable in that case. Enforced by
/// [`require_cap_within_asset_domain`], so stored caps can never overflow the
/// asset→ray rescale.
pub fn max_cap_for_decimals(asset_decimals: u32) -> i128 {
    let Some(exp) = RAY_DECIMALS.checked_sub(asset_decimals) else {
        return 0;
    };
    let upscale = 10i128
        .checked_pow(exp)
        .expect("10^(RAY_DECIMALS - asset_decimals) fits i128 for asset_decimals <= RAY_DECIMALS");
    i128::MAX / upscale
}
