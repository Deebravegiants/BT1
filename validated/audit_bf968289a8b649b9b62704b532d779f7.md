## Equality being validated

Claimed broken equality: **"value extracted by `EmporiumUpgradeable.runAction`'s `stack.ops` execution must be authorized by either a valid UTXO-ownership proof (nullifier/signature over spent funds) or a valid ECDSA signature from `stack.signerAddress`."**

Tracing the code shows this equality is never enforced when `circomData.erc20TokenAddresses.length == 0` and `stack.signerAddress == address(0)`.

## Trace

`Hinkal.transact` → `hinkalHelper.performHinkalChecks` → `dimensionsCheck`/`checkOnchainCreation` → `verifyProof` → `_externalTransact` → `EmporiumUpgradeable.runAction`.

- `CircomDataBuilder.formInputForCircom` routes to `formInputEmporiumMin` (public input = `[emporiumMessage, timeStamp, calldataHash]`, only 3 signals) whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`. [1](#0-0) 
- `MainEVMCircuitMin` only constrains `message <== Poseidon(1)([messageSeed])`; the attacker freely picks `messageSeed`, hence `emporiumMessage` (`message`), `outTimeStamp`, and `calldataHash` are entirely attacker-chosen with no binding to any spending key, nullifier, or Merkle root. [2](#0-1) 
- `dimensionsCheck` with `tokenNumber = 0` makes every per-token loop a no-op; it only forces `H0x != 0` and `onChainEncryptedOutput.length > 0`, both trivially satisfiable. [3](#0-2) 
- In `EmporiumUpgradeable.runAction`, `verifyWallet` returns immediately without any signature check when `stack.signerAddress == address(0)`: [4](#0-3) 
- With `signerAddress == 0`, every op falls into "CASE 2" and executes `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract's own balance: [5](#0-4) 
- The post-execution balance-conservation loop (`balanceChange < 0 → revert BalanceChangeShouldBePositive`) is bounded by `circomData.erc20TokenAddresses.length`, which is `0` on this path — so it never executes and never checks what the ops actually did to the contract's balance: [6](#0-5) 
- Back in `Hinkal.sol`, the balance-diff / slippage / UTXO-accounting loop is likewise bounded by `circomData.erc20TokenAddresses.length`, so with an empty array it is entirely skipped: [7](#0-6) 
- `HinkalWallet.receive()` and `EmporiumUpgradeable.receive()` both accept plain ETH from anyone, so the Emporium contract can and does hold a real balance between transactions: [8](#0-7) [9](#0-8) 

## Root cause

There is no requirement anywhere in the reachable call path (`performHinkalChecks`, `dimensionsCheck`, `checkOnchainCreation`, `verifyProof`, `verifyWallet`, or the post-`ops` balance check) that forces `stack.signerAddress != address(0)` whenever `circomData.erc20TokenAddresses.length == 0` (i.e., whenever `MainEVMCircuitMin` — a proof carrying no key material — is the verifier used). This lets an unprivileged attacker submit a `transact()` call with a trivially self-generated `MainEVMCircuitMin` proof, `dimensions.tokenNumber = 0`, and an `EmporiumStack` with `signerAddress = address(0)`, whose `ops` call arbitrary `endpoint.call{value: op.value}(callData)` (e.g., `token.transfer(attacker, balance)` or a raw ETH send) using whatever ETH/ERC20 balance the shared `EmporiumUpgradeable` proxy currently holds — funds that may belong to other users (e.g., leftover dust from prior swaps, ETH sent directly via `receive()`, or funds parked mid multi-step flow) — with zero cryptographic or economic authorization check on that balance.

## Impact

Critical/High — an unprivileged attacker can drain any ETH/ERC20 balance resident in the shared `EmporiumUpgradeable` contract at the time of the call, using a proof that proves nothing about fund ownership and a signature check that is skipped entirely. This is fully repeatable (each call just needs a fresh `emporiumMessage`/`calldataHash`/`outTimeStamp` and costs only gas + trivial proof generation), and it constitutes execution of fund-moving calls that neither a wallet owner nor a legitimate prover ever authorized.

## Recommendation

Enforce, in `dimensionsCheck` or `EmporiumUpgradeable.runAction`/`verifyWallet`, that when `dimensions.tokenNumber == 0` (the `MainEVMCircuitMin` path), `stack.signerAddress` must be non-zero and pass full ECDSA verification (i.e., disallow the `signerAddress == address(0)` bypass on this path), and additionally re-enable a balance-conservation check for the zero-token-count path so that `ops` cannot cause the contract's balance to decrease without an equal, accounted-for `deltaAmountChanges`/deposit in the same transaction.
