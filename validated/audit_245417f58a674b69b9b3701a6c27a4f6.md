This confirms the asymmetry: `verify_signed_message` (used by `offer_signer_capability` and by `multisig_account::create_with_existing_account*`) verifies purely against the `message: T` bytes and the account's current auth key — it performs no chain-id check itself [1](#0-0) . Whether replay-across-chains is prevented depends entirely on whether the caller-supplied challenge struct `T` embeds a `chain_id`.

### Title
Missing chain_id in `SignerCapabilityOfferProofChallengeV2` allows cross-network replay of `offer_signer_capability` signatures - (File: `aptos-move/framework/aptos-framework/sources/account/account.move`)

### Summary
`account::offer_signer_capability` authorizes granting full signer capability over an account to a `recipient_address` based on a signature over `SignerCapabilityOfferProofChallengeV2 { sequence_number, source_address, recipient_address }` [2](#0-1) . Unlike its sibling `RotationCapabilityOfferProofChallengeV2`, which the framework explicitly patched to add a `chain_id` field specifically "to prevent replaying the challenge message" [3](#0-2) , `SignerCapabilityOfferProofChallengeV2` never received the equivalent fix and still lacks `chain_id`.

### Finding Description
The custody invariant broken here is the same class as the external report: a signature authorizing a privileged state change must be bound to a unique execution context so it cannot be replayed in another valid context to re-grant/misuse authority. The Gateway bug reduces to "signature validity isn't scoped tightly enough to the intended one-time action." In Aptos, `RotationCapabilityOfferProofChallengeV2` was deliberately hardened with `chain_id` for exactly this reason [4](#0-3) , but `SignerCapabilityOfferProofChallengeV2`, which grants an even more powerful capability (a full signer, not just rotation), was left with only `sequence_number` and `source_address` [5](#0-4) .

Because Aptos accounts freshly created without any key rotation have their address derived from (and equal to) their authentication key, the same address/public-key/sequence-number tuple can legitimately exist on multiple independent networks (mainnet, testnet, devnet, or any custom deployment sharing the framework) that a user or custody system interacts with using the same keypair. `verify_signed_message` checks only the auth key and the message signature — no `chain_id` is compared against the executing chain [1](#0-0) . A signer-capability-offer message signed by a user on one network (e.g., a testnet a custodian or wallet integration test-signs against) is therefore byte-for-byte valid input to `offer_signer_capability` on any other Aptos-based network where the account exists at the same sequence number, silently handing full signer capability of that account to whatever `recipient_address` was embedded in the original message.

This is a genuinely local, framework-level root cause independent of governance or admin trust — a permissionless `offer_signer_capability` call reusing a foreign-chain signature is enough.

### Impact Explanation
`offer_signer_capability` swaps in a new `recipient_address` in `Account.signer_capability_offer.for` [6](#0-5) , and `create_authorized_signer` (invoked with that offer) lets the recipient obtain a raw `signer` for the victim account, enabling arbitrary asset transfers, resource mutation, and complete custody takeover of any assets held by that account (APT, fungible assets, objects owned by the account, etc.). This satisfies the custody-grade bar: unauthorized takeover of account/signer control tied to live assets.

### Likelihood Explanation
Exploitation requires: (1) a victim who signs a `SignerCapabilityOfferProofChallengeV2` message intended for one Aptos network (this happens for legitimate reasons — SDKs, dApps, or custody backends commonly pre-sign such offers for automation), and (2) the same account (same address, same current auth key, same sequence number) existing on another Aptos-compatible network. This is a realistic scenario for accounts that have not yet rotated keys (address == auth key) and interact with multiple Aptos networks/chains using the same keypair, which is common practice for testing and multi-environment deployments. It is not as trivially exploitable as the original Gateway bug (which needed no cross-chain assumption), so likelihood is moderate rather than certain, but the missing field is a clear, unforced regression relative to the parallel `RotationCapabilityOfferProofChallengeV2` fix.

### Recommendation
Add a `chain_id` field to `SignerCapabilityOfferProofChallengeV2` (mirroring `RotationCapabilityOfferProofChallengeV2`), include `chain_id::get()` when constructing the challenge in `offer_signer_capability`, and treat this as a breaking struct change requiring careful migration (old signed offers would need to be re-issued). Given `has copy, drop` semantics and BCS-based signing, this cannot be done as a pure additive change without invalidating previously-generated valid signatures, so it should be versioned (e.g., a `SignerCapabilityOfferProofChallengeV3`) with the old entry point deprecated or gated behind a feature flag once verified.

### Proof of Concept
Conceptual (cannot be executed without two live networks sharing account state):
1. On Network A, Alice's account exists at address `A`, un-rotated auth key `pk_A`, sequence_number `n`.
2. Alice signs `SignerCapabilityOfferProofChallengeV2 { sequence_number: n, source_address: A, recipient_address: Mallory }` for a legitimate purpose scoped to Network A (e.g., a dApp integration test on testnet).
3. The same address `A` with the same un-rotated key and sequence number `n` also exists on Network B (mainnet or another Aptos-based chain), e.g., because the account was freshly created there with the same keypair and has made the same number of prior transactions.
4. Mallory submits `account::offer_signer_capability(A, sig_bytes, ED25519_SCHEME, pk_A_bytes, Mallory)` on Network B. `verify_signed_message` passes because it only checks the auth key match and BCS-signature validity of the message fields present, none of which differ between networks [1](#0-0) .
5. Mallory now calls `create_authorized_signer(&mallory_signer, A)` on Network B and obtains a `signer` for Alice's Network-B account, draining its assets.

Note: I could not verify from the indexed code whether a concrete "same address across networks with un-rotated key" scenario is officially supported/expected in this codebase's deployment model (e.g., whether devnet/testnet/mainnet genesis accounts can practically collide), so likelihood assessment above is conditioned on that assumption; a Devin session with full checkout/build access could confirm real-world exploitability by examining account creation and cross-network address derivation more thoroughly.
