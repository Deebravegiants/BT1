### Title
Permissionless `CallDispatcher.dispatch()` lets anyone drain assets/allowances the shared dispatcher is holding mid-flight — (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a single shared, non-custodial-by-design "trusted" execution relay that `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` all route escrowed/bridged assets through while executing attacker- or solver-supplied `Call[]` arrays. Its `dispatch(bytes)` function has no access-control modifier at all — any address, not just the gateway/token contracts that are supposed to own that moment's balance, can call it directly. This is the same bug class as ALPINE-CVE-2020-14339: a privileged capability (here, whatever ERC-20 balance or standing allowance the dispatcher happens to hold) that is meant to be used only by/for the trusted caller that just funded it leaks into a context (an arbitrary permissionless caller) that has no business touching it.

### Finding Description
`CallDispatcher.dispatch` decodes an arbitrary `Call[]` and executes each `to.call{value}(data)` with the dispatcher itself as `msg.sender`, with zero restriction on who may invoke `dispatch`: [1](#0-0) 

The dispatcher is not scoped per-order or per-caller — it is one fixed, shared address wired into every `IntentGatewayV2`/`HyperFungibleToken`/`WrappedHyperFungibleToken` deployment on a chain, and it temporarily holds real user/protocol funds while the surrounding `onAccept`/`_execute`/predispatch flow runs: [4](#0-3) [5](#0-4) 

The intended flow is: (1) the gateway/token transfers the order's/message's assets to the dispatcher, (2) it calls `dispatch()` with attacker/solver-controlled calldata to run swaps or other DeFi composability, (3) it sweeps back whatever balance remains for the tokens it explicitly knows about (`order.inputs`/`order.output.assets`). That sweep is scoped only to the declared token list: [6](#0-5) 

Because `dispatch()` itself is public, an attacker does not need to wait for a sweep gap — they can simply call `CallDispatcher.dispatch()` directly, in their own transaction, at any point the dispatcher holds a balance or a standing token allowance that was left over from someone else's in-flight or completed order. This can happen through:
- Any token not enumerated in `order.inputs`/`order.output.assets` that a prior `Call[]` sent to or approved on the dispatcher (e.g. a bonus/reward token from a swap, or an approval granted to a spender for more than the swap actually consumed) — the docs themselves flag this residue risk but rely on caller discipline rather than a contract-enforced guarantee: "Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution." [3](#0-2) 
- Native ETH or ERC-20 sent to the dispatcher outright between a funding transfer and the `dispatch()` call in a multi-step external interaction (e.g. `_sendValue(dispatcher, amount)` then `IERC20(token).safeTransferFrom(msg.sender, dispatcher, amount)` prior to the actual `dispatch()` invocation in `IntentGatewayV2.sol`): [7](#0-6) 

Since there is no `onlyGateway`/`onlyHost`/reentrancy or caller check anywhere in `CallDispatcher`, whoever notices the dispatcher briefly holding value or a live approval can race a transaction that calls `dispatch()` with a `Call` such as `token.transferFrom(dispatcher, attacker, allowance)` or `token.transfer(attacker, balance)`, executed with the dispatcher as `msg.sender`.

### Impact Explanation
Concrete theft of funds: any value (native or ERC-20) sitting on the shared `CallDispatcher`, or any lingering token allowance granted from it during a legitimate order/transfer, is stealable by an arbitrary unprivileged third party. Because the dispatcher is shared across every `IntentGatewayV2` order and every `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata-bearing transfer on the chain, this is not confined to the attacker's own funds — it exposes other users' and the protocol's assets that transiently pass through the same dispatcher instance.

### Likelihood Explanation
High reachability: `dispatch()` requires no proof, no consensus verification, and no relationship to the gateway/token — it is directly callable by anyone with a plain EOA transaction, satisfying the "single submitted transaction" bar. The attack surface is populated continuously by ordinary intent fills and HFT calldata transfers, which the docs already acknowledge can leave residue on the dispatcher.

### Recommendation
Restrict `CallDispatcher.dispatch()` to a caller allowlist (the specific gateway/token contracts that are meant to drive it), or make the dispatcher per-call/ephemeral (e.g., deploy a fresh minimal proxy per invocation) so no state or approval can persist across callers. At minimum, revoke any approvals granted during a `Call[]` sequence before returning, and sweep every token/asset the dispatcher could plausibly hold — not just the ones enumerated in `order.inputs`/`order.output.assets` — before the dispatcher is left idle between transactions.

### Proof of Concept
1. A legitimate order/transfer runs through `IntentGatewayV2._execute` (or `HyperFungibleToken.onAccept`) with an `output.call`/`data` payload that includes `token.approve(uniswapRouter, type(uint256).max)` followed by a swap that only consumes part of that allowance (e.g., due to slippage-bounded `swapTokensForExactTokens`), as shown in the existing test flow: [8](#0-7) 
2. The dispatcher is left with a live allowance to `uniswapRouter` (or whichever spender was named) exceeding what the swap consumed, and/or a balance of a token not listed in `order.output.assets` (e.g., a reward/bonus token) — because the sweep in `_execute` only iterates `outputsLen` and the declared asset list. [6](#0-5) 
3. An attacker, watching mempool/state, submits a direct transaction: `CallDispatcher.dispatch(abi.encode([Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transferFrom.selector, dispatcher, attacker, residualAllowanceOrBalance)})]))`. No modifier blocks this call. [1](#0-0) 
4. The attacker receives the residual tokens that belonged to the order's beneficiary/protocol, with no relationship to the order they came from.

    /**
     * @dev Executes arbitrary calldata attached to an order's output via the CallDispatcher.
     * After dispatching the calls, any residual token balances left on the dispatcher
     * are swept back to this contract and accounted for as protocol dust.
     *
     * This enables composable order fulfillment — solvers can route through DEXes,
     * lending protocols, or other DeFi primitives as part of filling an order.
     *
     * @param order The order containing the output calldata to execute.
     * @param outputsLen The number of output assets to sweep after execution.
     */
    function _execute(Order calldata order, uint256 outputsLen) internal {
        if (order.output.call.length == 0) return;

        address dispatcher = _params.dispatcher;
        ICallDispatcher(dispatcher).dispatch(order.output.call);

        Call[] memory sweepCalls = new Call[](outputsLen);
        uint256 sweepCount = 0;

        for (uint256 i; i < outputsLen;) {
            address token = address(uint160(uint256(order.output.assets[i].token)));

            if (token == address(0)) {
                uint256 balance = dispatcher.balance;
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({to: address(this), value: balance, data: ""});
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            } else {
                uint256 balance = IERC20(token).balanceOf(dispatcher);
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({
                        to: token,
                        value: 0,
                        data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
                    });
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            }

            unchecked {
                ++i;
            }
        }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
