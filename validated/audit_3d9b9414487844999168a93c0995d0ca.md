### Title
Stale in-memory account snapshot clobbers flash-callback state changes, resurrecting withdrawn collateral - ([File: contracts/controller/src/strategies/flash_position.rs](file: contracts/controller/src/strategies/flash_position.rs))

### Summary
`process_flash_position` loads the borrower's `Account` into memory once, then invokes an attacker-controlled receiver contract inside `with_flash_guard`, and finally persists the *pre-callback* position maps via `strategy_finalize`/`finalize_position_flow`. The flash guard only blocks liquidation and bad-debt cleanup (`require_not_flash_loaning` is called only from `positions/liquidation/mod.rs`); `withdraw`, `repay`, and `supply` are not covered. A receiver contract that is also the account owner can therefore mutate the account's stored positions during the callback (e.g., fully `withdraw` collateral, receiving real tokens), after which the controller writes back its stale `account` snapshot, restoring supply positions whose tokens were already paid out.

### Finding Description
The classic UAF shape — a freed object being used — maps here to a stale loaded-then-freed position map:

1. `load_or_create_account` loads `account` (supply/borrow positions) into memory at lines 93–101, before any external call.
2. `with_flash_guard` wraps `mint_and_forward` plus `invoke_receiver` (lines 120–143), so the attacker's contract runs while the controller holds only the stale snapshot.
3. `execute_flash_position` receives `account_id` (line 133/`invoke_receiver` lines 297–323), and `receiver` need only differ from the controller and pool (lines 71–84) — nothing prevents `receiver` from being the account owner's own contract.
4. During the callback the owner contract calls `withdraw(account_id, ...)` (or `repay`/`swap_collateral`), which loads fresh state from storage, pays tokens out, and persists the emptied position maps. `require_not_flash_loaning` does not guard these exits — it is enforced only in `process_liquidation`, `process_clean_bad_debt`, and `process_force_socialize_bad_debt`.
5. After the callback, `process_deposit` credits measured receipts onto the **stale** `account` (line 146), and `strategy_finalize` → `finalize_position_flow` → `persist_account_positions` writes `account.supply_positions`/`borrow_positions` back to storage wholesale (`positions/mod.rs:153-170`), silently overwriting the callback's persisted zeroed positions.
6. `require_flash_position_still_open` (lines 152–154) inspects only the stale `account`, so it passes as long as the pre-callback snapshot had debt and supply — which `mint_and_forward` guarantees.

The result is a supply position that exists in storage twice effectively: once paid out as tokens during the callback, once resurrected by the stale write-back — minted-from-nothing collateral backed by pool cash.

### Impact Explanation
The attacker ends with both (a) the withdrawn collateral tokens and (b) a fully restored supply position (plus the deposited collateral receipts merged on top). They can then `withdraw` again or `borrow` against the resurrected collateral, extracting unbacked tokens from the pool — direct theft of other suppliers' funds, potentially up to the full liquidity of the debt/collateral markets used.

### Likelihood Explanation
Fully unprivileged: the attacker needs only an account NFT (free to mint via `supply`/`flash_position` with `account_id == 0`), a WASM receiver contract they control (passes `require_wasm_receiver`), and a flashloanable debt market (`is_flashloanable` flag). One atomic transaction: `flash_position(debt, amount, receiver=attacker_contract, collaterals=[(hub_asset, dust_min)])` → in `execute_flash_position` call `withdraw` on the pre-seeded collateral → return ≥ min collateral to the controller → stale persistence restores the withdrawn position. No oracle manipulation, no privileged role, no timing dependency. The only requirement is that the account holds some collateral before the call (a normal `supply` suffices), and the callback leaves at least `min_amount` of a collateral asset at the controller.

### Recommendation
Reload account state after the guarded callback before merging and persisting — i.e., treat the pre-callback `account` as invalidated: either re-`get_account` after `with_flash_guard` returns, or extend the flash guard (`require_not_flash_loaning`) to every entrypoint that mutates persisted positions for an account that has an in-flight flow (`withdraw`, `repay`, `supply`, `borrow`, `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, `update_account_threshold`). Alternatively, persist nothing in `strategy_finalize` that wasn't recomputed from post-callback storage.

### Proof of Concept
```text
// Attacker contract A: owns account_id, also acts as flash receiver.
1. A.supply(0, spoke, mode=Multiply, USDC_hub, 100_000e6)  -> account_id = N (auth: A's own address)
2. A.flash_position(
     account_id: N, spoke_id, mode: Multiply,
     debt: ETH_hub, amount: X, receiver: A,
     collaterals: [(ETH_hub, 1)],            // dust min, or another asset A deposits in callback
     refund_assets: [], data: ..)
   // inside controller:
   //   account snapshot S0 loaded (USDC supply present)
   //   mint_and_forward: debt minted, ETH forwarded to A
   //   invoke_receiver -> A.execute_flash_position(initiator=A, account_id=N, ...)
3. In A.execute_flash_position (flash guard active — but withdraw is not guarded):
   A.withdraw(N, USDC_hub, u64::MAX)          // pool pays 100_000 USDC to A;
                                              // storage supply_positions[N] now empty
   A transfers 1 wei ETH (or dust collateral) to controller // satisfy CollateralMinimumNotMet
4. Back in controller:
   process_deposit(S0, deposits=[dust ETH])
   strategy_finalize -> set_supply_positions(S0.supply_positions + dust ETH)
   // stale map overwrites the emptied storage — 100_000 USDC position restored
   require_flash_position_still_open(S0)      // passes: S0 still shows debt+supply
5. A.withdraw(N, USDC_hub, u64::MAX)          // second payout of the same collateral,
                                              // backed by other suppliers' cash
   (or A.borrow against restored collateral, then abandon the ETH debt)
```
Net effect: collateral withdrawn twice; residual unbacked ETH debt is absorbed by suppliers via the bad-debt path — theft of user funds from the pool.
