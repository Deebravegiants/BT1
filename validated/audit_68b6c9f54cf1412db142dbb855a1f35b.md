### Title
Same-chain order escrow can be permanently frozen when `order.user` is a smart contract that cannot invoke `cancelOrder` and the order expires unfilled - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`IntentGatewayV2`/`IntrinsicIntents._cancelSameChain` restricts cancellation to `msg.sender == order.user` with no time-based public fallback, unlike the cross-chain destination cancel path which opens to any caller after the deadline. If `order.user` is a smart contract that cannot itself call `cancelOrder` (e.g., a vault, proxy, or purpose-built router contract with no generic call-forwarding function — the exact analog class raised in the external report about club/owner contracts lacking the needed function selector), and the order is never filled before `order.deadline`, the escrowed input tokens become permanently unrecoverable.

### Finding Description
`cancelOrder` in `IntentGatewayV2.sol` routes same-chain orders to `_cancelSameChain`, which enforces:
```solidity
function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
    if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
    ...
    _withdraw(body, true, true);
}
``` [4](#0-3) 

There is no deadline-gated public fallback for this path — the documentation explicitly confirms cancellation is restricted to "Original order user only" at "Any time before it is fully filled," with no public trigger after expiry, unlike the cross-chain destination route which becomes public once `order.deadline >= block.number` is false:
```solidity
function _cancelFromDest(...) internal {
    if (order.deadline >= _blockNumber()) {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
    }
    ...
}
``` [3](#0-2) 

Once `order.deadline` has passed, `fillOrder` also reverts (`Expired()`), so the escrow can no longer be released to a solver either. `placeOrder` never validates that `order.user`, encoded as an arbitrary `bytes32` address, corresponds to an EOA or a contract capable of calling `cancelOrder` itself — any `msg.sender`, including a proxy/router/vault contract without a generic "execute arbitrary calldata" function, can place an order on the user's behalf. If that contract cannot subsequently call `cancelOrder` with `msg.sender == order.user`, the escrowed tokens are locked: not fillable (expired) and not cancellable (unauthorized caller), with no third-party or governance recovery path for same-chain orders.

### Impact Explanation
This results in permanent freezing of escrowed user funds for same-chain orders with no recovery mechanism, satisfying the "permanent freezing of funds" acceptance bar. The affected value is the full escrowed input amount of any same-chain order placed on behalf of a smart-contract `order.user` lacking cancel capability.

### Likelihood Explanation
Likelihood is moderate: it requires `order.user` to be a smart contract (common for smart-contract wallets, vaults, routers, or meta-transaction relayers integrating the Intent Gateway) that does not expose a way to call `cancelOrder` itself, combined with the order going unfilled past its deadline — a realistic operational scenario for any integrator that places orders programmatically without building in cancel capability, mirroring exactly the bug class described in the external report (owner/club contracts lacking the required function).

### Recommendation
Add a deadline-gated public fallback to `_cancelSameChain`, mirroring `_cancelFromDest`: once `order.deadline < block.number`, allow any caller to trigger the refund, with the withdrawal always sent to `order.user` (never redirectable to the caller), just as the cross-chain destination path already does.

### Proof of Concept
1. Deploy a minimal contract `C` with only a function to call `placeOrder` on `IntentGatewayV2` (no generic `execute`/`call` forwarding function), setting `order.user = bytes32(uint256(uint160(address(C))))`.
2. `C` places a same-chain order escrowing input tokens, with `order.deadline = block.number + N`.
3. No solver fills the order before the deadline (or the user intentionally chooses not to have it filled).
4. After `block.number > order.deadline`, `fillOrder` reverts with `Expired()` for any solver attempt.
5. Any attempt to call `cancelOrder` from `address(C)` fails because `C` has no function to invoke it; any other caller reverts with `Unauthorized()`.
6. The escrowed input tokens recorded in `_orders[commitment]` remain locked in the `IntentGatewayV2` contract permanently.

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }
```

```text
    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable nonReentrant {
        bytes32 commitment = keccak256(abi.encode(order));

        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        // Emitted here, once, rather than from each of the three routes below. Every check those
        // routes make — Unauthorized, NotExpired, UnknownOrder — reverts, and a revert discards
        // logs, so an early emit can never announce a cancellation that did not happen. Emitting
        // before the branch also keeps `EscrowRefunded` the last log on the same-chain route, where
        // the refund is processed in this same transaction. Three emit sites cost bytecode this
        // contract does not have: it sits within ~100 bytes of the EIP-170 limit.
        emit OrderCancelled({commitment: commitment, canceller: msg.sender});

        if (isSameChain) {
            // Checked here rather than inside `_cancelSameChain`, which used to re-read `host()`,
            // re-query the host's state machine id and re-hash `order.source` to reach the same
            // answer this function already has. Same check, one external call fewer.
            if (currentChain != orderSource) revert WrongChain();
            _cancelSameChain(order, commitment);
        } else if (currentChain == orderSource) {
            _cancelFromSource(order, options, commitment);
        } else if (currentChain == orderDest) {
            _cancelFromDest(order, options, commitment);
        } else {
            revert WrongChain();
        }
    }
```

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        _post(
            order, _body(RequestKind.RefundEscrow, commitment, order.inputs, order.user), options.relayerFee, msg.value
        );
    }
