### Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from unauthenticated headers. `Registry.process` validates the HMAC over the body only, then trusts the header-derived `shop` value when constructing `WebhookMetadata` and dispatching to the host application's handler. This breaks the identity binding `HMAC-verified-bytes == acted-upon-identity`: the signature proves the body is untampered, but not which shop it belongs to.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
returning only `@raw_body`. Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers with no cryptographic binding: [2](#0-1) 

`Registry.process` validates only the HMAC over the signable string (the body) via `Utils::HmacValidator.validate`, and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` from the (unverified) headers to build `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` compute the HMAC purely from `verifiable_query.to_signable_string` (the body) and compare against the `hmac-sha256` header — it never incorporates `shop-domain`, `topic`, or `webhook-id`: [4](#0-3) 

The equality that should hold is: `shop_bound_by_hmac == shop_acted_upon`. In this implementation, `shop_bound_by_hmac` is undefined (the HMAC signs no shop identifier at all), while `shop_acted_upon = request.shop` is taken unauthenticated from the `x-shopify-shop-domain`/`shopify-shop-domain` header. Anyone who can supply an HTTP request to the app's webhook endpoint with the header set to an arbitrary shop domain — while replaying a body+HMAC pair they captured from any genuine webhook delivery (their own shop's webhook, or one leaked/logged/relayed) — passes `HmacValidator.validate` unchanged, because the signature never depended on the shop header. The gem then reports that body as belonging to the attacker-chosen `shop`.

### Impact Explanation
This is a cross-tenant identity confusion at the gem level: `ShopifyAPI::Webhooks::Registry.process` hands the host application a `WebhookMetadata` whose `shop` field is not authenticated by the HMAC it just validated. Any application that uses `data.shop` from the handler to select which merchant's data/session to act on (the documented and expected usage pattern for multi-tenant Shopify apps) can be made to process a webhook payload under the identity of a different shop than the one that produced/signed it, once an attacker has a valid body+HMAC pair from *any* delivery (e.g., their own store's webhook, or one observed in logs/network). This matches the Critical class: cross-tenant access enabled by a gem-level primitive.

### Likelihood Explanation
Exploitation requires the attacker to already possess one valid `(raw_body, hmac)` pair — which is easy to obtain (create a webhook subscription on any shop they control, or observe one via any leak/log) — and then merely resend that exact byte-for-byte body with a forged `shop-domain` header to the victim app's webhook endpoint. No knowledge of `client_secret` or the target's access token is needed, only network access to the app's public webhook receiver, which is by design internet-reachable. This is a realistic, low-effort attack path.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) in the HMAC-signed material verified by `HmacValidator`, or otherwise cryptographically bind the shop-domain header to the payload before trusting it (e.g., verify the shop against a value independently confirmed via signed session data such as `id_token`, rather than the raw `shopify-shop-domain` header). At minimum, document that `request.shop` is unauthenticated and must not be used by host apps to select tenant context without additional verification, and update `Registry.process`/`WebhookMetadata` to reflect this or reject shop-domain values that host apps haven't independently validated.

### Proof of Concept
1. Attacker registers a webhook on their own controlled shop `attacker.myshopify.com` and receives a genuine delivery: body `B` with header `shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `client_secret`) and `shopify-shop-domain: attacker.myshopify.com`.
2. Attacker sends a new HTTP request to the victim app's webhook endpoint with the *same* body `B` and *same* `H`, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged shop header unauthenticated:
`lib/shopify_api/webhooks/request.rb:21-23`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (= `B`) and it matches `H` — validation succeeds despite the shop being forged:
`lib/shopify_api/webhooks/registry.rb:190`, `lib/shopify_api/utils/hmac_validator.rb:26-31`.
5. `WebhookMetadata.new(shop: request.shop, ...)` is built with `shop: "victim-shop.myshopify.com"` and passed to the app's `handler.handle`, causing the host app to process attacker-controlled webhook content under the victim shop's identity: `lib/shopify_api/webhooks/registry.rb:198-199`.
