### Title
Webhook `shop` domain used for tenant identification is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and verifies the request's authenticity via `HmacValidator.validate`, but the `to_signable_string` method used to compute/verify that HMAC only returns the raw body, while the `shop` attribute (read straight from the unauthenticated `shop-domain` header) is passed downstream as the tenant identifier without ever being covered by the signature.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is derived purely from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, which is attacker-controllable and not part of the signed payload: [2](#0-1) 

`Webhooks::Registry.process` validates the request solely via `Utils::HmacValidator.validate(request)`, which internally calls `verifiable_query.to_signable_string` (body only) and compares it against the HMAC header: [3](#0-2) [4](#0-3) 

After a passing HMAC check, `request.shop` (the unverified header value) is forwarded directly into `WebhookMetadata` and handed to the app's `WebhookHandler#handle`, which merchant apps use to scope data access/writes to a specific tenant: [5](#0-4) [6](#0-5) 

This breaks the identity binding: `bytes_verified_by_hmac (raw_body only) != shop_domain_used_for_tenant_routing (unauthenticated header)`. Because the HMAC secret (`Context.api_secret_key`) is shared across all shops/tenants of a given app, anyone who can produce or replay a request with a valid signature for *some* body (e.g. a merchant who owns their own shop and can trigger genuine webhooks for it, or anyone who has ever observed one valid `(body, hmac)` pair) can resubmit that exact body/hmac pair to the app's webhook endpoint while substituting a different value in the `shop-domain` header. `Utils::HmacValidator.validate` will still pass, since it never re-derives or checks the header, and the handler will process the payload as belonging to the attacker-chosen shop.

### Impact Explanation
This directly maps to the "cross-tenant access" Critical-impact category: the shop identifier that host applications use to scope database records/API calls per-tenant can be forged despite HMAC verification succeeding, letting an attacker cause the host app to associate/write data (e.g. process an `orders/create` or `customers/data_request` payload) under a victim shop's identity, or trigger shop-scoped side effects (data deletion via `shop/redact`, etc.) against a tenant that never actually sent the webhook.

### Likelihood Explanation
Exploitability requires only the ability to send arbitrary HTTP requests to the app's public webhook endpoint with a previously-valid `(raw_body, hmac)` pair (trivial to obtain by installing the app on an attacker-controlled shop, since the secret is shared and only the body is signed) and to change the `X-Shopify-Shop-Domain` header value. No access token, `client_secret`, or privileged account is required beyond running the vulnerable gem's own webhook verification path exactly as documented, so this sits squarely within the gem's own code and satisfies the scope requirement of not depending on host-application misuse.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values in the signed content verified against the HMAC, or otherwise cryptographically bind the shop domain to the signature (e.g., require the host app to reconcile `request.shop` against a known/authorized shop list before trusting it), so that `to_signable_string` cannot diverge from the identity fields exposed via `WebhookMetadata`.

### Proof of Concept
1. An attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook, capturing `raw_body` and its valid `x-shopify-hmac-sha256` value (both computed from/verified against the app's shared `client_secret`).
2. The attacker replays this exact `raw_body` + `hmac` pair to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only checks `raw_body`: [1](#0-0) 
4. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the host app to process/act on data as if it came from the victim tenant. [5](#0-4)
