### Title
Webhook shop-domain identity is trusted from an unauthenticated header while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` directly from unauthenticated HTTP headers, while its `to_signable_string` (the value actually verified against the HMAC) returns only `@raw_body`. `Registry.process` accepts the request as authentic once `Utils::HmacValidator.validate(request)` succeeds, then hands `request.shop` straight to the app's webhook handler as the tenant identity for the payload. This breaks the identity binding: `hmac == HMAC(raw_body)` is verified, but `shop` (the value acted upon to select/attribute tenant data) is never part of the signed bytes.

### Finding Description
`to_signable_string` only returns `@raw_body`: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are read straight from headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates only the HMAC over the request (i.e., over `raw_body`) and then forwards `request.shop` (the unverified header) as the tenant identity to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field, which is also just a header value (`shopify_header("hmac-sha256")`) — none of this touches `shop-domain`: [4](#0-3) [5](#0-4) 

Because the app's `client_secret` is shared across every shop that installs the app, a merchant is an "unprivileged" party relative to other tenants but still receives Shopify's genuine webhook deliveries for their own shop, complete with a valid `X-Shopify-Hmac-Sha256` signature computed over the body. Since the `shop-domain` header sits outside the signed bytes, that same (body, hmac) pair remains valid regardless of which `shop-domain` header value is presented at verification time. The binding the gem should enforce is:

`hmac == HMAC(raw_body || shop || topic)` (or equivalent), but the code only checks `hmac == HMAC(raw_body)`, leaving `shop` (and `topic`) unauthenticated even though `Registry.process` treats `request.shop` as the authenticated tenant identity for the delivered payload.

### Impact Explanation
An attacker who is a legitimate merchant on a multi-tenant app (no special privileges, no access to `api_secret_key`) can capture one of their own genuine webhook deliveries (raw body + valid HMAC) and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body against the HMAC, and `Registry.process` will dispatch the payload to the handler tagged with the attacker-chosen `shop`. Any app logic keyed on `WebhookMetadata#shop` (e.g., updating per-shop state, creating records under a tenant, or driving destructive actions like `shop/redact` handling) can be triggered under a victim tenant's identity — a cross-tenant data/action injection.

### Likelihood Explanation
Medium-High: no credentials beyond installing the app as an ordinary merchant are required. The webhook endpoint is expected to be publicly reachable (it's an inbound Shopify → app endpoint), and any HTTP client can replay a captured body with a modified header, since the header is not covered by the signature. The main constraint is that the attacker needs to have captured at least one legitimate webhook body+HMAC for a topic/body shape useful to them, which is straightforward for an app they've installed themselves.

### Recommendation
Bind the tenant-identifying fields to the signed material. Either:
- Include `shop`, `topic`, and `webhook_id` in `to_signable_string` (mirroring Shopify's actual webhook verification, which signs the raw body but the app should independently cross-check that the shop presented in the header actually matches a shop the app has an active session/install for), or
- After HMAC validation, require the caller to confirm `request.shop` corresponds to a shop with a known, previously stored session/installation before dispatching to handlers, rejecting deliveries for shops with no recognized install state.
At minimum, document and enforce that `request.shop` must never be trusted as an authenticated value on its own — it must be cross-checked against app-side tenant records before being used to key any state-changing operation.

### Proof of Concept
1. Install the target app (built on this gem) on `attacker-shop.myshopify.com`.
2. Trigger any webhook topic the app subscribes to; capture the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sends.
3. Replay the exact same body and HMAC header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and adjust `X-Shopify-Webhook-Id`/`X-Shopify-Topic` headers if desired — none are covered by the signature).
4. `Utils::HmacValidator.validate(request)` returns `true` because it only hashes `@raw_body`, which is unchanged. [6](#0-5) 
5. `Registry.process` dispatches `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` to the app's handler, which now acts as if the event originated from the victim tenant.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
