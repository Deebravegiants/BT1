### Title
Unrestricted swap routes can execute malicious contracts under the caller's authorization tree and transfer unrelated wallet funds - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral`, `multiply`, `swap_debt`, and `repay_debt_with_collateral` accept caller-controlled `StrategySwap` bytes and invoke the configured router without restricting the contracts named by that route. A malicious route can direct execution into attacker-deployed code, which can invoke `token.transfer(caller, attacker, amount)` beneath the caller's top-level authorization. Soroban simulation records that transfer as a child of the caller's authorization tree, so a wallet that signs the simulated tree authorizes theft of an unrelated token in addition to the intended position operation. [1](#0-0) [2](#0-1) 

### Finding Description
The controller authenticates the position owner or delegate with `caller.require_auth()` before executing a strategy. [3](#0-2)  For a swap, it snapshots the controller's input and output balances, authorizes only one exact transfer from the controller to the configured router, and calls `router.execute_strategy(&controller, &amount_in, swap)`. [4](#0-3) 

The controller bounds only the controller's router grant and measured receipts; it does not constrain what contracts the supplied route causes the router to call below the user's authorization. [5](#0-4)  The repository's regression test demonstrates this exact shape: a route names an attacker-deployed hop pool, and that pool calls `token.transfer(victim, attacker, amount)` for an asset unrelated to the lending operation. [6](#0-5) 

In authorization-recording mode, the malicious transfer is attached under the caller's `swap_collateral` authorization entry rather than rejected at construction time. [7](#0-6)  When the caller signs the poisoned tree, the unrelated wallet balance moves to the attacker while the requested collateral swap still succeeds. [8](#0-7) [9](#0-8) 

### Impact Explanation
An attacker can steal any token balance the victim can transfer, including assets never listed by the lending protocol, provided the victim signs an authorization tree generated for a malicious route. The economic loss is not bounded by the swapped collateral: the demonstrated route steals the victim's full unrelated wallet-token balance while returning a fair swap output and preserving the account operation. [10](#0-9) [8](#0-7) 

### Likelihood Explanation
Exploitation requires the victim to submit or sign a transaction containing a malicious route and the resulting poisoned authorization tree. An attacker can facilitate this through a malicious quote, wallet integration, or signed payload; route bytes are opaque enough that a user who trusts simulation output may not notice the extra child transfer. The signed-tree requirement limits the attack to authorization-aware deception, supporting Medium rather than Critical or High severity. [11](#0-10) [12](#0-11) 

### Recommendation
Constrain the authorization surface exposed to route-selected code. At minimum, wallets and quote producers should reject any `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral` authorization tree containing children other than the expected token pull. Preferably, the router boundary should enforce an allowlist of venue contract types or provide a venue-call mechanism that cannot join user-controlled arbitrary contract calls to the caller's auth tree. The existing measured-input and measured-output checks should remain, but they are not a substitute for constraining nested authorization. [13](#0-12) [14](#0-13) 

### Proof of Concept
1. Alice supplies USDC and owns a debt-free account; she also holds an unrelated token that the protocol has never listed. [15](#0-14) 
2. The attacker deploys a contract whose `swap` function calls `token.transfer(alice, attacker, WALLET_BALANCE)` on that unrelated token. [16](#0-15) 
3. Alice invokes `swap_collateral(caller=alice, account_id, current=USDC market, amount=SWAP_IN_USDC, new=ETH market, swap=route)`, where `route` names the malicious contract. [11](#0-10) [17](#0-16) 
4. During simulation, the rogue transfer is recorded as a child beneath Alice's `swap_collateral` authorization entry. [18](#0-17) 
5. If Alice signs that returned tree, enforcement accepts the route, transfers `WALLET_BALANCE` from Alice to the attacker, and still credits Alice with the fair ETH output. [9](#0-8)

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    s.t.env.mock_all_auths();

    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
}
