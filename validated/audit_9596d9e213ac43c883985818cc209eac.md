### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identifiers are not covered by HMAC verification, enabling tenant spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable representation from the raw request body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values used by `Registry.process` to route/attribute the webhook are read directly from unauthenticated HTTP headers.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by comparing a signature computed over `to_signable_string` against the received `hmac`. For webhooks, `to_signable_string` returns only `@raw_body`: [1](#0-0) 
Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from headers, none of which participate in the signature: [2](#0-1) 
`Registry.process` validates only the body-derived HMAC and then forwards the header-derived `shop` (and other header fields) to the app's handler as trusted metadata: [3](#0-2) 

The identity binding that should hold is: `shop authenticated by HMAC == shop delivered to the handler`. Because the signature only covers the body bytes, that equality does not hold — `request.shop` can be swapped to any value without invalidating the HMAC, as long as the (unmodified) body and its valid HMAC pair are kept intact.

### Impact Explanation
An attacker who is a legitimate, unprivileged installer of the app on their own shop receives genuine webhook deliveries to their own endpoint (or can otherwise obtain one authentic `(body, hmac)` pair for a webhook topic that Shopify sends). By replaying that exact body/HMAC pair to the app's webhook endpoint while substituting a victim's `X-Shopify-Shop-Domain` header, `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop. Any host application that trusts `data.shop` for tenant routing, per-shop session lookup, or authorization decisions — which is the documented purpose of this field — can be tricked into acting as though data pertains to a different merchant, resulting in cross-tenant confusion/access without needing the app's `client_secret`, an access token, or any privileged credential.

### Likelihood Explanation
Exploitation requires no secrets: any merchant who installs the app can legitimately trigger a webhook to their own instance, capture the valid `(raw_body, hmac)` pair, and replay it against the shared webhook endpoint with a forged `shop-domain` header. This is a standard HTTP replay with header tampering, well within reach of an unprivileged internet-facing attacker who already interacts with the app as a customer/merchant.

### Recommendation
Bind the identity fields into the HMAC-verified surface, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the verified payload before trusting them:
- Include `shop`, `topic`, and `webhook_id` (in addition to the raw body) in `to_signable_string`, matching how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop`/`host`/`state` into its signable string.
- Alternatively, document explicitly and enforce in `Registry.process` that `WebhookMetadata#shop` must never be used as the sole tenant identifier without cross-checking it against a value obtained from an authenticated channel (e.g., the shop stored for that webhook's session).

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g., `orders/create`) so Shopify delivers a request to the app's webhook endpoint with a valid `X-Shopify-Hmac-Sha256` computed over the raw body.
2. Capture the raw body `B` and its valid `hmac` value `H`.
3. Send a new POST to the same webhook endpoint with the same body `B` and header `X-Shopify-Hmac-Sha256: H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) succeeds because it only checks `B` against `H`; `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, even though the payload was never actually signed for `victim.myshopify.com`.
