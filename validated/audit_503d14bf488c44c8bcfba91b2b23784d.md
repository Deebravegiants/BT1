### Title
Residual Operator-QR Authorization Window Allows Cross-Signup Authorization Bleed - (File: `src/plans/mod.rs`)

### Summary
The reported Notional bug describes an approval that is granted for a maximum amount but not reset/scoped after each use, leaving a "residual allowance" that a compromised counterparty can later exploit. The reachable analog in orb-core is the operator-QR authorization cache: once an operator QR code is scanned and validated, the resulting authorization (`OperatorData`) is cached and treated as valid for every subsequent, unrelated signup request until `operator_qr_expiration_time` elapses, rather than being consumed/reset after each individual signup.

### Finding Description
In `MasterPlan::run`, the operator QR code is scanned once via `scan_initial_qr_codes` into `initial_qr_codes`, and is only re-scanned when `qr_codes.operator_timestamp()` is stale relative to `operator_qr_expiration_time`: [1](#0-0) 

The same cached `OperatorData` (with its `timestamp`) is then reused across the idle loop for potentially many distinct user signups, gated only by an elapsed-time check rather than being re-validated or invalidated per signup: [2](#0-1) [3](#0-2) 

This mirrors the structure of the residual allowance bug: the operator's authorization is granted as a broad, time-bounded permission (`_maxSendAmount`-equivalent = `operator_qr_expiration_time`) instead of a single-use, per-signup credential that is invalidated once consumed. Just as `_approve` in the Notional contract leaves residual allowance until the window/condition changes, `scan_initial_qr_codes`/`scan_remaining_qr_codes` leave the operator authorization "approved" for any signup that falls inside the expiration window, regardless of which user or how many signups occur in that window.

### Impact Explanation
If the trusted party normally required to re-establish authorization per signup (the operator, analogous to Notional's fCash wrapper) is compromised, spoofed, or its QR code replayed/captured within the expiration window, the residual authorization allows multiple, unrelated user signups to be attributed to that single operator authorization without a fresh check — enabling misattributed signups within the validity window (cross-signup state bleed), the same class of impact the analog validation criteria requires (misattributed signup / cross-signup state bleed).

### Likelihood Explanation
This is gated behind `self_serve` configuration and requires the residual window (`operator_qr_expiration_time`) to be nonzero and an attacker to act within that window using a captured/replayed operator QR code; it is a design tradeoff (UX convenience) rather than an accidental omission, so exploitability depends on operational configuration of the expiration duration. Note: I was not able to retrieve the exact default value of `operator_qr_expiration_time` from `src/config.rs` due to tool/index limitations in the final iteration, so the concrete window size (and therefore the practical likelihood) is unconfirmed.

### Recommendation
Scope the operator authorization to a single signup transaction: invalidate/consume the cached `OperatorData` immediately after it authorizes one signup (set its timestamp to already-expired, or require an explicit re-scan) rather than allowing it to remain valid for an arbitrary number of subsequent signups until a time-based expiration. This mirrors the Notional fix of resetting allowance to zero after each use instead of relying on a max-amount/expiration threshold.

### Proof of Concept
Not independently verified with a runnable exploit — this is a structural/code-reachability analog based on `src/plans/mod.rs` control flow (`scan_initial_qr_codes`, `idle_wait_for_signup_request`, `scan_remaining_qr_codes`), not a confirmed exploit chain. Confirming exploitability would require verifying the configured value of `operator_qr_expiration_time` in `src/config.rs`, which could not be retrieved in this session due to tool limitations.

    async fn idle_wait_for_signup_request(
        &mut self,
        orb: &mut Orb,
        qr_codes: &QrCodes,
        self_serve: bool,
        self_serve_button: bool,
        operator_qr_expiration_time: Duration,
    ) -> Result<Option<QrCodes>> {
        // We currently support 4 scenarios:
        // 1. Internal testing with a biometric input file.
        // 2. Self-serve mode that always scans for a user QR code.
        // 3. Self-serve mode that expects a button press to ask for a user QR code.
        // 4. Normal mode that expects a button press to ask for an operator QR code and then a user QR code.
        //
        // Scenarios 3 and 4 are handled by the same code path in the following last else-statement.
        let ui_idle_delay = self.ui_idle_delay.take();
        let qr_codes = if self.oneshot || self.has_biometric_input() {
            qr_codes.clone()
        } else if self_serve && !self_serve_button {
            orb.set_phase("User QR-code idle scanning").await;
            let QrCodes::Operator { operator_data } = &qr_codes else {
                panic!("operator QR code needs to be scanned beforehand in self-serve mode");
            };
            let Some((user_qr_code, user_data, user_qr_code_string)) = self
                .idle_scan_user_qr_code(
                    orb,
                    operator_data,
                    operator_qr_expiration_time,
                    ui_idle_delay,
                )
                .await?
            else {
                return Ok(None);
            };
            qr_codes.with_user_qr_code(user_qr_code, user_data, user_qr_code_string)
        } else {
            orb.set_phase("Idle waiting for button press").await;
            self.idle_wait_for_button_press(orb, ui_idle_delay).await?;
            orb.ui.signup_start_operator();
            qr_codes.clone()
        };
        Ok(Some(qr_codes))
    }
