Audit Report

## Title
Deducted metering balance is never refunded when a capability execution fails - ([File: core/services/workflows/v2/capability_executor.go])

## Summary
In `callCapability`, credits are earmarked from a workflow's local metering balance via `meterReport.Deduct(..., metering.ByDerivedAvailability(...))` before the capability is executed, which immediately subtracts the earmarked amount from `r.balance` via `Minus`. `meterReport.Settle`, the only function that refunds the unused portion of the earmark back to the balance, is only called in the success path after `capability.Execute` returns without error; every error branch (user error, system error, generic error) returns early without ever calling `Settle`, permanently burning the earmarked credits.

## Finding Description
The deduction happens unconditionally before execution: [1](#0-0) . This routes to `ByDerivedAvailability`, which subtracts the earmarked amount from the in-memory balance via `r.balance.Minus(limit.Decimal)`: [2](#0-1) .

After `capability.Execute` is called, all three error branches (`caperrors.Error` with `OriginUser`, `caperrors.Error` with other origin/system error, and generic error) return immediately without touching `meterReport`: [3](#0-2) .

`Settle` — which computes actual spend and refunds `step.Deduction.Sub(spentCredits)` back into `r.balance` — is only invoked on the success path: [4](#0-3) , and the refund logic itself confirms this is the only place unused earmark is returned: [5](#0-4) .

There is no `defer`-based guard or fallback call to `Settle`/refund anywhere else in `callCapability`, so any capability failure permanently loses the earmarked amount from the workflow's local balance tracker.

## Impact Explanation
This is a billing/accounting-integrity bug: every ordinary capability failure (timeout via `CapabilityCallTime.WithTimeout`, a capability returning a user or system error, or any other execution error) causes the workflow's local credit balance to be decremented with no corresponding capability work performed and no refund. Because `ByDerivedAvailability` can earmark up to the entire available balance for a single call (as documented by the deduction logic and metering tests), a single failing call can exhaust a workflow's local balance, causing subsequent legitimate capability calls in the same execution to be denied due to insufficient balance, and results in an inflated/incorrect credits-consumed accounting for the workflow. This is a genuine, code-confirmed correctness bug affecting billing/fund tracking for the workflow, reachable purely through normal (non-malicious) execution — a workflow owner or the DON operating a normal workflow will trigger this whenever any capability call fails.

## Likelihood Explanation
High. Capability calls failing (timeouts, rate limits, transient system errors, user-config errors) is routine, non-malicious behavior, and the code path is deterministic: any `err != nil` from `capability.Execute` unconditionally skips `Settle`. No special privilege or attacker action is required beyond triggering an ordinary capability failure during normal workflow execution.

## Recommendation
Ensure the earmarked amount is settled/refunded on every exit path of `callCapability`, not just on success — e.g., use a `defer` that calls `meterReport.Settle` (or a dedicated refund/cancel method) with zero spend whenever `Deduct` succeeded but `capability.Execute` returns an error, so the full earmark is returned to the local balance when no capability work was actually billed.

## Proof of Concept
1. Configure a workflow with metering enabled (`meterReport != nil`) and a capability that reliably fails (e.g., returns a `caperrors.Error` with `OriginUser`, or simply times out via `CapabilityCallTime`).
2. Call the capability; `callCapability` calls `meterReport.Deduct(meteringRef, metering.ByDerivedAvailability(...))`, which subtracts the derived limit from `r.balance` (can be the full available balance when `openConcurrentCallSlots == 1`).
3. `capability.Execute` returns an error; execution enters `core/services/workflows/v2/capability_executor.go` lines 260-281 and returns without calling `meterReport.Settle`.
4. Inspect `meterReport`'s internal balance (e.g., via a unit test in `core/services/workflows/metering/metering_test.go` style, asserting balance before/after a `Deduct` followed by a simulated failed execution with no `Settle` call) — the earmarked amount remains permanently subtracted, with no corresponding `ReportStep.Spends` recorded, confirming the unrefunded deduction.
