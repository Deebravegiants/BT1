### Title
Emporium-only transaction path skips EdDSA authorization entirely, letting any address submit an arbitrary `emporiumMessage` without proving control of a spending key - (File: `contracts/CircomDataBuilder.sol`, `circuits/MainEVMCircuit.circom`, `circuits/MainEVMCircuitMin.circom`)

### Summary
When `Hinkal.transact` is called with `externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` routes to `formInputEmporiumMin`, which is verified against the minimal circuit `MainEVMCircuitMin`. That circuit only proves knowledge of a `messageSeed` whose Poseidon hash equals the public `message`/`emporiumMessage` value — it contains no `spendingPublicKey`, no `eddsaSignature`, and no `SignatureVerifier` component at all, unlike `MainEVMCircuit` used by every other action type.

### Finding Description
For the "normal" path, `emporiumMessage` is folded into `getSignedMessageHash` [1](#0-0)  and that hash is a public input consumed by `MainEVMCircuit`'s `SignatureVerifier`, which enforces that the EdDSA signature was produced by `spendingPublicKey` over exactly that hash [2](#0-1) . This is the equality that authenticates every field of `CircomData` (root hash, nullifiers, commitments, amounts, stealth address, `emporiumMessage`) as originating from the holder of the spending key.

The Emporium-only branch bypasses this entirely. `formInputForCircom` selects `formInputEmporiumMin` whenever the action id matches and no tokens are involved [3](#0-2) , producing a public-input vector of only `emporiumMessage`, `timeStamp`, `calldataHash`. The corresponding circuit, `MainEVMCircuitMin`, has no `spendingPublicKey`, no `eddsaSignature` input, and no equivalent of `SignatureVerifier`; it simply computes `message <== Poseidon(1)([messageSeed])` [4](#0-3) . Since `messageSeed` is a private witness fully controlled by the prover, anyone can pick an arbitrary `messageSeed`, compute its Poseidon hash off-chain, set `emporiumMessage` to that value, and generate a trivially valid proof — with no relationship whatsoever to any `spendingPublicKey`/EdDSA signature. `HinkalHelper.performHinkalChecks` only re-verifies `calldataHash` integrity and dimensions [5](#0-4) ; it never requires a signature check for this branch, and `Hinkal.transact` proceeds to call `_externalTransact` → `IExternalActionV2(...).runAction(circomData, deltaAmountChanges)` with a fully attacker-chosen `emporiumMessage` and `hookData` once the (unauthenticated) proof verifies [6](#0-5) .

This is the same bug class as the Nethermind envelope report: a type-selector (`externalActionId`/token-count combination, analogous to `TxType`) is allowed to route into a "lightweight" processing path whose validation is materially weaker than the primary path, and downstream code (here, the external-action/Emporium call) trusts the artifact as if it went through the full authorization check.

### Impact Explanation
If any Emporium/hook contract registered via `registerExternalAction` treats a successful `Hinkal.transact` call plus the `emporiumMessage`/`message` value as proof that a specific key holder authorized an action (e.g., initiating a `HinkalWallet` operation or emitting an order tied to a stealth address), this authorization is forgeable by anyone, since the ZK proof for this branch requires no possession of any private/spending key. This falls under "executing calls or moving assets a wallet owner or prover never authorised," a High-severity outcome per the impact criteria. I could not fully verify from the indexed code exactly how `EmporiumUpgradeable`/`HinkalWallet` consume `emporiumMessage` downstream to confirm the concrete asset-moving consequence (the index may not have surfaced the full body of `EmporiumUpgradeable.runAction`), so the ultimate blast radius depends on that contract's trust assumptions about the caller's proof.

### Likelihood Explanation
Likelihood is high for triggering the code path itself: it only requires `erc20TokenAddresses.length == 0` and `externalActionId == HINKAL_EMPORIUM_ACTION_ID`, both fully attacker-controlled inputs to `Hinkal.transact`, and generating the "proof" requires no special knowledge (just picking a random seed and hashing it).

### Recommendation
Require the same `spendingPublicKey`/EdDSA signature verification in `MainEVMCircuitMin` as in `MainEVMCircuit`, binding `emporiumMessage` (and any other fields the Emporium action relies on) to a signature check, so the "message-only" path cannot be used to fabricate an authorization that downstream external-action contracts might rely on.

### Proof of Concept
1. Attacker calls `Hinkal.transact` with `circomData.erc20TokenAddresses = []`, `circomData.externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, and any `circomData.hookData`/`externalActionMetadata` they want processed by the registered Emporium contract.
2. Attacker picks a random `messageSeed`, computes `message = Poseidon(1)([messageSeed])` off-chain, and sets `circomData.emporiumMessage = message`.
3. Attacker generates a Groth16 proof for `MainEVMCircuitMin` — trivial, since it only requires knowing a preimage of a Poseidon hash they themselves chose [7](#0-6) .
4. `Hinkal.transact` verifies the proof successfully (no signature check exists for this branch) and forwards to `_externalTransact`, calling the registered Emporium contract with the attacker's chosen `emporiumMessage`/`hookData`, without the attacker ever proving control of any `spendingPublicKey` [6](#0-5) .

    function formInputForCircom(
        uint256 chainId,
        address verifyingContract,
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory) {
        if (
            circomData.externalActionData.externalActionId ==
            HINKAL_EMPORIUM_ACTION_ID &&
            circomData.erc20TokenAddresses.length == 0
        ) {
            return formInputEmporiumMin(circomData);
        } else {
            return formInputNormal(chainId, verifyingContract, circomData);
        }
    }

    function formInputEmporiumMin(
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory input) {
        input = new uint256[](circomData.publicSignalCount);

        uint16 index = 0;

        input[index++] = circomData.emporiumMessage;

        input[index++] = circomData.timeStamp;
        input[index++] = circomData.calldataHash;
    }
