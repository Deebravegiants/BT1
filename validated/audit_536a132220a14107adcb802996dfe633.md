### Title
Webhook shop identity is not bound by the HMAC signature, enabling cross-tenant impersonation - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats an incoming webhook as authenticated for a given shop once `Utils::HmacValidator.validate` succeeds, then forwards `request.shop` (read from the unauthenticated `X-Shopify-Shop-Domain` header) to the app's handler as trusted tenant identity. The HMAC, however, is computed only over the raw request body, never over the shop-domain header, so the "verified" webhook and the "acted-on" shop identity are two different things.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain` header, with no cryptographic tie to the body or to the HMAC: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` compute and compare the signature exclusively against `verifiable_query.to_signable_string` (the body), and never inspect `shop`, `topic`, or `webhook-id`: [3](#0-2) 

`Registry.process` uses this single HMAC check as the sole authentication gate, then immediately builds `WebhookMetadata` using `request.shop` (the unauthenticated header) as if it had been verified together with the body: [4](#0-3) 

The identity binding that should hold is:
`hmac == HMAC(secret, body || shop || topic)`, but the gem only enforces `hmac == HMAC(secret, body)`, i.e. `shop` (and `topic`, `webhook_id`) are fields that are acted on (passed to the handler as the tenant context) but not covered by the HMAC.

Because `api_secret_key` is shared between Shopify and the app, an unprivileged internet user cannot forge an HMAC from scratch. But any developer/merchant can install the app on their own (attacker-controlled) shop — this requires no special privilege — and thereby legitimately receive Shopify-signed webhooks (raw body + valid HMAC) for events they can trigger (e.g. `orders/create`, `app/uninstalled`). They can then replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, i.e. the app believes Shopify is reporting an event for the victim tenant.

### Impact Explanation
This breaks the tenant boundary that host applications rely on `WebhookMetadata#shop` to enforce (Critical - cross-tenant access). Any handler that uses `data.shop` to select which merchant's stored session/access token to act on, update billing/subscription state, mark data as deleted (e.g. mandatory `shop/redact`, `app/uninstalled` handling), or otherwise mutate per-tenant state will do so against a shop the attacker does not control, using content the attacker fully controls (their own order/webhook payload). Because the gem does the "validation" and hands back a metadata object that looks fully authenticated, downstream apps have no visibility into the fact that `shop` was never part of the signed material.

### Likelihood Explanation
The prerequisite — installing the app on one's own shop to obtain legitimately Shopify-signed webhook bodies — is an unprivileged, self-service action available to any internet user, and no `api_secret_key`, access token, or leaked credential is required. Producing the forged request afterward is a trivial HTTP replay with one header changed and no cryptographic difficulty.

### Recommendation
Bind the tenant identity into the verified material: incorporate `shop`-domain (and topic) into the value that is HMAC-verified, or otherwise cryptographically tie the shop-domain header to the specific webhook delivery (e.g., cross-check against a maintained mapping of installed shops/subscriptions rather than trusting the header outright), so that `Utils::HmacValidator.validate` cannot succeed for a body/shop pair that Shopify itself never combined and signed.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (self-service, no privilege required).
2. Attacker triggers a webhook event on their own shop (e.g. `orders/create`) and captures the exact raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent to the app's webhook endpoint.
3. Attacker resends the identical raw body and HMAC header to the same endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and any topic of choice, since topic is also unchecked).
4. `Utils::HmacValidator.validate` returns `true` (it only checks the body against the HMAC) — see [5](#0-4) .
5. `Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"` — see [6](#0-5)  — even though the payload is entirely attacker-authored content from the attacker's own shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
