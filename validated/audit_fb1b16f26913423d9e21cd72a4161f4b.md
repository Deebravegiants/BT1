### Title
Emporium wallet signature omits `feeToken`/`relay` binding, letting anyone redirect wallet fee payments to an arbitrary token and recipient - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
The Emporium wallet-invoke flow lets a wallet owner sign an EIP-712 message authorizing a set of operations plus a numeric fee cap (`maxFee`). The signature never binds which ERC-20 token pays that fee, nor which address receives it. Any party who possesses (or relays) a validly signed `EmporiumStack` can independently craft the surrounding `CircomData` to pick an arbitrary `feeStructure.feeToken` and set `circomData.relay` to their own address, and the contract will pull up to the signed `maxFee` amount of that attacker-chosen token directly out of the signer's wallet and send it to the attacker.

### Finding Description
`verifyWallet` recovers the signer over:
```solidity
keccak256(abi.encode(EMPORIUM_SIGNATURE_TYPEHASH, circomData.emporiumMessage, _hashEmporiumOps(stack.ops), stack.maxFee, stack.deadline))
``` [1](#0-0) 
This binds only `emporiumMessage`, the `ops` array, `maxFee`, and `deadline`. It never includes `circomData.feeStructure.feeToken`, `circomData.feeStructure.variableRate`, or `circomData.relay`.

After the signature check, `payRelayFees` computes the amount to move using `feeStructure.flatFee`/`feeStructure.feeToken`, which are attacker-controlled at submission time (only bounded by the numeric `flatFee <= stack.maxFee` check):
```solidity
if (isFeeToken) { foundToken = true; }
...
if (!foundToken && feeStructure.flatFee != 0) {
    require(signerAddress != address(0), "Gas Token in Emporium is not found");
    payRelay(circomData.relay, signerAddress, feeStructure.flatFee, feeStructure.feeToken);
}
``` [2](#0-1) 
`payRelay` then calls `sendToRelayFromWallet`, which invokes `IHinkalWallet(signerAddress).doSendToRelay(relay, relayFee, feeToken)` — a real transfer directly out of the signer's wallet to `relay`, in whatever `feeToken` was supplied:
```solidity
function sendToRelayFromWallet(address relay, address signerAddress, uint256 relayFee, address feeToken) internal {
    if (relayFee > 0) {
        IHinkalWallet(signerAddress).doSendToRelay(relay, relayFee, feeToken);
    }
}
``` [3](#0-2) 

Since `feeToken` and `relay` are outside the equality the signer actually authorized (the EIP-712 hash), and `circomData.calldataHash`/ZK-proof binding is only enforced against the *submitter's own* re-hash of `CircomData` (i.e., self-consistency, not the wallet-signer's consent) via `CircomDataBuilder.getHashedCalldata`, any party in possession of a validly signed `EmporiumStack` (e.g., a relay observing it, or anyone it was shared with for submission) can resubmit it with a different `feeStructure.feeToken` (any token the wallet holds) and `circomData.relay` set to themselves, extracting up to the signed numeric `maxFee` of that token from the wallet — a token/recipient the wallet owner never actually agreed to. [4](#0-3) 

This is aggravated by the fact that when `circomData.erc20TokenAddresses.length == 0` (pure wallet-invoke, no shielded-pool token movement), the ZK proof is generated against `MainEVMCircuitMin`, which performs no ownership/authorization check whatsoever — it only outputs `Poseidon(messageSeed)` and constrains nothing about the caller's identity, nullifiers, or root hash:
```
template MainEVMCircuitMin() {
  signal input outTimeStamp;
  signal input calldataHash;
  signal input messageSeed;
  signal output message;
  message <== Poseidon(1)([messageSeed]);
}
``` [5](#0-4) 
so anyone can trivially self-generate this proof, meaning the *only* real authorization gate for the whole wallet-invoke path in this branch is the EIP-712 signature discussed above — and that signature is exactly the one missing the `feeToken`/`relay` binding.

### Impact Explanation
This allows theft/misdirection of protocol relay fees and unauthorized asset movement out of a user's Hinkal wallet: the wallet owner signs off on a numeric fee cap for a specific intended context, but the actual submitter chooses which ERC-20 token is drained and who receives it, up to that cap. An attacker can pick the wallet's most valuable held token instead of the intended low-value gas/fee token, and route the payout to themselves as `relay`. This matches the High-severity class "theft ... of protocol/relay fees" / "moving assets a wallet owner or prover never authorised."

### Likelihood Explanation
Exploitation requires only possession of one validly signed `EmporiumStack` (a routine artifact of normal Emporium usage, since `transact()` is a public entrypoint anyone can call, and relays by design see and submit these signed payloads). No admin, owner, or extra privilege is required, and the trivial `MainEVMCircuitMin` proof removes even the need to hold any shielded-pool key. The only constraint is `usedMessages[emporiumMessage]` (one-time use per message) and the numeric `maxFee` cap, both of which are compatible with a single successful drain of the highest-value token available.

### Recommendation
Include `circomData.feeStructure.feeToken`, `circomData.feeStructure.variableRate` (or an explicit commitment to the intended fee context), and `circomData.relay` inside the `EMPORIUM_SIGNATURE_TYPEHASH` payload that the wallet owner signs, so the signer explicitly authorizes exactly which token and which relay address may be paid, not just a numeric cap.

### Proof of Concept
1. Wallet owner signs an `EmporiumStack` (`emporiumMessage`, `ops`, `maxFee = X`, `deadline`) intending to pay a small fee in `USDC`.
2. Before/at submission, an unprivileged party (e.g., a relay) builds `CircomData` with `erc20TokenAddresses = []` (so the trivial `MainEVMCircuitMin` proof path applies), `circomData.relay = attacker`, `feeStructure = {feeToken: <wallet's high-value token>, flatFee: X, variableRate: 0}`, and the same `emporiumMessage`/`ops`/`maxFee`/`deadline` fields required by the signature.
3. Attacker self-generates a valid Groth16 proof for `MainEVMCircuitMin` (no ownership needed) and calls `Hinkal.transact()`.
4. `verifyWallet` succeeds (signature only checked over `emporiumMessage`, `ops`, `maxFee`, `deadline`, all matched); `flatFee (X) <= maxFee (X)` passes.
5. `payRelayFees` → `sendToRelayFromWallet` transfers `X` units of the attacker-chosen high-value token from the wallet to `attacker` (as `relay`), which the wallet owner never approved for that token/recipient.

    function payRelayFees(
        CircomData calldata circomData,
        address signerAddress,
        int256[] calldata deltaAmountChanges
    ) internal {
        FeeStructure calldata feeStructure = circomData.feeStructure;

        bool foundToken = false;

        for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            // tokens deposited into Emporium are not charged
            if (deltaAmountChanges[i] >= 0) {
                continue;
            }

            address erc20TokenAddress = circomData.erc20TokenAddresses[i];
            bool isFeeToken = erc20TokenAddress == feeStructure.feeToken;

            if (isFeeToken) {
                foundToken = true;
            }

            uint256 relayFee = 0;
            uint256 flatFee = isFeeToken ? feeStructure.flatFee : 0;

            if (signerAddress == address(0)) {
                uint256 sumAbs = uint256(-deltaAmountChanges[i]);

                EmporiumStorageVars storage $ = _getEmporiumStorage();
                relayFee = $._hinkalHelper.calculateRelayFee(
                    sumAbs,
                    flatFee,
                    feeStructure.variableRate
                );
            } else {
                relayFee = flatFee;
            }

            payRelay(
                circomData.relay,
                signerAddress,
                relayFee,
                erc20TokenAddress
            );
        }

        if (!foundToken && feeStructure.flatFee != 0) {
            require(
                signerAddress != address(0),
                "Gas Token in Emporium is not found"
            );

            payRelay(
                circomData.relay,
                signerAddress,
                feeStructure.flatFee,
                feeStructure.feeToken
            );
        }
    }
