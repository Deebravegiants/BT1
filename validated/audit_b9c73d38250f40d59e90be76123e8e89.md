## Analysis Result

I found a strong analog to the reported bug class in `pallet-state-coprocessor`'s `handle_get_requests`/`handle_unsigned` path.

### Title
Unbounded, attacker-supplied `GetRequest.keys` forces the state-coprocessor's fixed-weight `handle_unsigned` to do unbounded state-proof verification work - (File: modules/pallets/state-coprocessor/src/impls.rs)

### Summary
`EvmHost.dispatch(DispatchGet)` and `pallet-ismp`'s `IsmpDispatcher::dispatch_request(DispatchRequest::Get(...))` accept an arbitrary-length `keys: Vec<Vec<u8>>`/`bytes[] keys` from any unprivileged caller, with no bound on the number of keys per `GetRequest`. `handle_get_requests` then calls `verify_state_proof(host, req.keys.clone(), ...)` per request inside a per-request loop, doing one trie lookup per key. `handle_unsigned` is declared with a **fixed** weight (`DbWeight::get().reads_writes(1, 2)`), independent of `keys.len()` or the number of requests in the batch.

### Finding Description
- `EvmHost.dispatch(DispatchGet)` takes `get.keys` directly with no length check: [1](#0-0) 
- `DispatchGet`/`GetRequest.keys` on the Substrate/ISMP core side is likewise unbounded `Vec<Vec<u8>>`: [2](#0-1) 
- `pallet-ismp`'s dispatcher forwards `dispatch_get.keys` straight into the `GetRequest` with no cap: [3](#0-2) 
- On the coprocessor side, `handle_get_requests` iterates `requests` and, for each one, calls `verify_state_proof` with `req.keys.clone()` — one trie/key lookup per key, for every key in every request in the batch: [4](#0-3) 
- The extrinsic that runs this loop, `handle_unsigned`, is declared with a static, request-count-independent weight: [5](#0-4) 

This is structurally the same defect as the BetaFinance report: an unprivileged actor (any contract/app dispatching a `GetRequest`) controls the size of a loop (`keys.len()` × request count) that a *different* party — here, the relayer who must submit `handle_unsigned`/`GetRequestsWithProof`, and the chain that must execute it under a fixed declared weight — is forced to pay for. There is no on-chain validation capping `keys.length` at dispatch time, and no per-key/per-request scaling of the extrinsic's declared weight.

### Impact Explanation
Two consequences follow directly from the missing bound:
1. **Underweighted extrinsic / block-weight exhaustion risk**: because `handle_unsigned`'s weight is fixed regardless of `keys.len()` or `requests.len()`, a large enough batch of keys can make the actual execution time vastly exceed the weight FRAME reserved for the block, degrading block production or effectively DoS-ing the coprocessor pallet — a variant of "route unable to deliver messages," since GetResponses for large-key requests may become impossible to process within block limits.
2. **Relayer gas/compute griefing**: any application can dispatch a `GetRequest` with an extremely large `keys` array for a fixed, attacker-chosen relayer fee (or zero fee for self-relay), forcing whichever relayer picks it up to pay disproportionate compute/proof-generation and verification costs relative to the fee earned, discouraging delivery — exactly the "liquidator declines to act because gas cost exceeds reward" dynamic from the original report, but for GetResponse delivery instead of liquidation.

### Likelihood Explanation
Any application/module can call `dispatch()` with a `DispatchGet` carrying a `keys` array of essentially unbounded length; nothing in `EvmHost.sol`, `pallet-ismp`'s dispatcher, or `pallet-state-coprocessor` rejects an oversized array before it reaches on-chain processing. This requires only a single permissionless dispatch transaction and no special privileges, replicating the "single submitted transaction" reachability required by the report scope.

### Recommendation
- Enforce a maximum number of keys per `GetRequest` (and/or maximum total keys per `GetRequestsWithProof` batch) at dispatch time in both `EvmHost.dispatch(DispatchGet)` and `pallet-ismp`'s `dispatch_request`, rejecting requests that exceed the cap.
- Make `handle_unsigned`'s declared weight scale with `requests.len()` and the sum of `keys.len()` across requests (e.g., via a benchmarked per-key weight component), so the runtime charges/accounts for the real cost instead of a flat `reads_writes(1, 2)`.
- Consider bounding `keys` similarly to how `pallet_bandwidth` already meters payload bytes, but applied pre-emptively at dispatch rather than only charged post-verification.

### Proof of Concept
Conceptually: (1) any app calls `EvmHost.dispatch(DispatchGet{ keys: <N very large keys>, ... })` with `N` chosen large (e.g., thousands of 52-byte EVM storage keys) and a low/zero relayer fee; (2) this reaches `pallet-ismp::dispatch_request` and is stored in `RequestCommitments` without any keys-length check (as shown in the dispatcher code above); (3) when a relayer or the coprocessor eventually processes the corresponding `GetRequestsWithProof` via `handle_unsigned`, `handle_get_requests` performs `N` trie-lookups in `verify_state_proof` per request, while the extrinsic is weighted as a flat `reads_writes(1, 2)` — under-accounting the real execution cost and making the relayer's economic incentive to deliver (fee vs. compute cost) disproportionate, mirroring the original report's gas-griefing mechanism.

**Caveat**: I was unable to fully verify from the indexed context whether an upstream size/weight limit exists elsewhere (e.g., extrinsic length limits, transaction pool validation, or a runtime-level `ensure!` on `keys.len()` that wasn't captured by the search). If such a bound exists in code not surfaced by the index, this finding's severity should be reassessed against it; a Devin session with full repository access could confirm this definitively.
