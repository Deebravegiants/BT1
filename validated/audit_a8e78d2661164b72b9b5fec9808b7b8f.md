### Title
Webhook `shop` (and topic/webhook-id) identity fields are not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates the HMAC over the body only and then trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler [3](#0-2) . This breaks the identity binding `verified(bytes) == body` versus `attributed_tenant == shop header`, which is never checked against the signature.

### Finding Description
Shopify signs webhooks with `OpenSSL::HMAC` over the raw JSON body only, using a single app-wide `client_secret` shared across every shop that installs the app. `HmacValidator.validate` reconstructs the signature strictly from `verifiable_query.to_signable_string` [4](#0-3) , and for `Webhooks::Request` that signable string is `@raw_body` alone [1](#0-0) . The `shop-domain`, `topic`, and `webhook-id` headers are parsed independently and are never mixed into the signed data [2](#0-1) .

By contrast, the OAuth callback path explicitly includes `shop` inside its signed string (`AuthQuery#to_signable_string` folds `code, host, shop, state, timestamp` into the HMAC input) [5](#0-4) , showing the library is capable of, and normally does, bind the tenant identity field into the signature — except in the webhook path.

Because a merchant (an ordinary unprivileged Shopify user) can install any target app on their own store and thereby legitimately receive webhook deliveries signed with the app's real, shared `client_secret`, they obtain a valid `(raw_body, hmac)` pair. They can then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with an arbitrary victim shop domain. `Registry.process` still calls `Utils::HmacValidator.validate(request)` successfully (body/HMAC match), then builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-chosen header value [6](#0-5) , and this metadata is handed to the app's handler as authoritative per-tenant data, exactly as documented (`shop_domain: data.shop`) [7](#0-6) .

### Impact Explanation
This is a cross-tenant identity confusion: an attacker who is a legitimate (but unprivileged relative to other merchants) installer of the app can cause the app to process arbitrary webhook payloads under an arbitrary victim shop's identity. If the host app trusts `data.shop` (as the gem documents and expects) for tenant-scoped writes, job enqueueing, or data updates, the attacker can inject data attributed to a shop they do not own — a cross-tenant access/data-integrity violation.

### Likelihood Explanation
Requires only (1) installing the target app on any shop (a normal, unprivileged action any attacker can perform to become a legitimate merchant of that app), and (2) the ability to POST arbitrary bytes/headers to the app's public webhook endpoint with a replayed body+HMAC and forged `shop-domain` header — no access to `api_secret_key`, tokens, or any other shop's credentials is required.

### Recommendation
Bind the `shop`, `topic`, and `webhook_id` header values into the HMAC-verified signable string (or otherwise independently verify `request.shop` against the set of shops the app has an active session/installation for) before trusting them in `WebhookMetadata`, mirroring the approach already used in `AuthQuery#to_signable_string`.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; capture a legitimate webhook delivery (raw body `B`, header `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Shop-Domain: attacker.myshopify.com`) signed with the app's shared `client_secret`.
2. Replay the request to the app's webhook endpoint, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but set `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally change `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against `H` [4](#0-3) .
4. The registered handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and body `B`, even though `B` was never actually sent by/for `victim.myshopify.com`.
