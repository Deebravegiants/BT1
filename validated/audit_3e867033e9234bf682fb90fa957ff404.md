### Title
Missing zero-amount validation in `IntentGatewayV2.placeOrder` predispatch path permanently freezes escrowed order funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
In the Tron variant of `IntentGatewayV2.sol`, the predispatch branch of `placeOrder` never validates that an input's `amount` is non-zero before crediting escrow, unlike the sibling non-predispatch branch and the main EVM `IntentGatewayV2.sol`. A zero-amount entry stored in `_orders[commitment][token]` later causes the shared `withdraw` function to unconditionally revert with `UnknownOrder`, permanently freezing the entire order's escrow (all tokens, not just the zero one), because `withdraw` iterates every `body.tokens[i]` in a single transaction and reverts atomically on the first zero balance it finds.

### Finding Description
`placeOrder`'s non-predispatch branch explicitly guards against zero amounts: [1](#0-0) 

But the predispatch branch, reached whenever `order.predispatch.call.length > 0 && order.predispatch.assets.length > 0`, has no equivalent check on `order.predispatch.assets[i].amount` or `order.inputs[i].amount`: [2](#0-1) 

The reduced-input/commitment computation (used to populate escrow) also runs *before* the predispatch dispatch, directly off the user-supplied `order.inputs[i].amount`, rather than off actually-received balances as in the main EVM contract: [3](#0-2) 

If a user submits `order.inputs[i].amount = 0` for one of the tokens while using the predispatch path, `requiredAmount` is `0`, so the balance check (`balance < requiredAmount`) never fails, and `_orders[commitment][token] += reducedInputs[i].amount` stores `0` for that token — while any surplus dispatcher balance for that token is emitted only as `DustCollected`, never credited to the user's escrow.

Later, when the order is filled/refunded/cancelled, the shared `withdraw` function is invoked (via `onAccept`'s `RedeemEscrow`/`RefundEscrow` handling, or `cancelOrder`'s same-chain path) and iterates all `body.tokens`: [4](#0-3) 

The check `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` triggers on the zero-amount token, reverting the *entire* `withdraw` call — meaning no token in the order can ever be redeemed, not just the zero-amount one. Compare the upstream `ValidationLogic`/`RevenueManagement` bug class cited in the report: a value that can legitimately be zero is passed into a function whose invariant assumes non-zero, causing a hard revert; here the same class of defect converts into permanent fund lock rather than a mere failed call, because the failing check sits inside the redemption/refund code path itself.

### Impact Explanation
This is a permanent freezing-of-funds bug reachable from a single unprivileged `placeOrder` transaction. Two victims are affected:
- The order's own creator can never cancel/refund the escrow for the entire order (all non-zero tokens locked forever alongside the zero one).
- More severely, a solver/filler who observes the order, delivers the output assets on the destination chain in good faith (per intents flow), and expects `withdraw`/`RedeemEscrow` to release the source-chain escrow to them, will find that redemption permanently reverts — the solver loses the value they already paid out with no recourse. This is a genuine, unbacked loss of solver funds and a stuck escrow, which the hyperbridge intents model explicitly guards against ("solver reward accounting" is in-scope).

### Likelihood Explanation
High likelihood: this requires only a single `placeOrder` call from any unprivileged intents user, using the predispatch feature (a standard, documented feature — e.g., unwrapping LP tokens before escrow) with a zero-amount input entry. No special privileges, timing, or race conditions are needed, and the missing check is a straightforward code omission relative to the sibling non-predispatch branch and the main EVM contract, which both validate `amount != 0`.

### Recommendation
Add the same `if (order.predispatch.assets[i].amount == 0) revert InvalidInput();` and `if (order.inputs[i].amount == 0) revert InvalidInput();` checks to the predispatch branch of `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `placeOrder`, matching the main EVM `IntentGatewayV2.sol` implementation (lines 242 and 264 there), and/or make the zero-balance check in `withdraw` operate per-token (skip/continue rather than revert) so that a single zero-value leg cannot block redemption of the rest of the escrow.

### Proof of Concept
1. Attacker (or any user) calls `placeOrder` with `predispatch.call` and `predispatch.assets` non-empty, and `order.inputs` containing at least one `TokenInfo` with `amount = 0` for a token that will actually be received via the predispatch dispatcher call.
2. `placeOrder` succeeds: the predispatch branch performs no zero check, `requiredAmount = 0` passes the balance check trivially, any real balance received is emitted solely as `DustCollected`, and `_orders[commitment][token] = 0` is stored (via `reducedInputs[i].amount` computed from the original zero amount).
3. A solver fills the order on the destination chain, delivering output tokens to the beneficiary.
4. The redeem/refund/cancel flow calls `withdraw(body, ...)` with `body.tokens = order.inputs` (including the zero-amount token).
5. `withdraw` reverts at `if (_orders[body.commitment][token] == 0) revert UnknownOrder();`, blocking release of escrow for every token in the order, including the legitimately-funded ones — permanently freezing the escrowed funds and denying the solver its expected redemption.
