## Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant impersonation - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop` domain that identifies the tenant is read from an entirely separate, unsigned header. `Webhooks::Registry.process` validates the HMAC over the body alone and then forwards the unauthenticated `shop` value straight into the handler's `WebhookMetadata`, so the "shop that was cryptographically verified" and the "shop that is trusted as the tenant key" are two different, unbound values — the same class of identity-binding failure described in the external report (a check that references one identity while an unrelated identity is what actually gets acted upon).

### Finding Description
`Webhooks::Request` exposes `shop` from the `x-shopify-shop-domain`/`shopify-shop-domain` header: [1](#0-0) 

but the value that is actually HMAC-verified is only the raw body: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the signature strictly over `verifiable_query.to_signable_string`: [3](#0-2) 

`Webhooks::Registry.process` performs this HMAC check and then, without any further binding between `shop` and the verified body, passes `request.shop` on to the handler as the tenant identifier: [4](#0-3) 

Because the app's `client_secret`/`api_secret_key` is shared across every shop that installs the app, any merchant (an ordinary, unprivileged installer of the app) can obtain a validly-signed `(body, hmac)` pair for their *own* store, then resend that exact body/HMAC pair to the app's webhook endpoint with the `shop` header rewritten to a victim shop's domain. The signature still validates (it never covered `shop`), so `WebhookMetadata.shop` ends up being the victim's domain while the payload is attacker-controlled — an equality the code implicitly assumes (`verified body ⇒ shop header is trustworthy`) but never actually enforces.

### Impact Explanation
This breaks the tenant/identity binding `shop authenticated == shop used as the tenant/session key`, letting an attacker who is a legitimate (but unprivileged) installer of the app inject or impersonate webhook data attributed to a different merchant's shop. Any host application that uses `WebhookMetadata#shop` to look up per-shop state, credentials, or to trigger tenant-scoped side effects (which is the documented purpose of that field) can be made to act on forged data as if it came from an arbitrary victim shop — a cross-tenant access impact.

### Likelihood Explanation
Requires only that the attacker be able to install the target app on some shop they control (a normal, unprivileged action available to any merchant) and be able to send arbitrary HTTP requests to the app's public webhook endpoint — no access to the `client_secret`, tokens, or any privileged account of the victim is needed.

### Recommendation
Bind the `shop` value into the signed material, or otherwise cryptographically tie the verified webhook to its claimed shop (e.g., include the shop domain in the HMAC input, or require the caller to independently verify that the `shop` header corresponds to a shop with a registered webhook subscription/id known to the app), instead of trusting an unsigned header for tenant identification.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers any webhook topic on their own store (or crafts a request directly), obtaining a raw body `B` and a valid `x-shopify-hmac-sha256` computed by Shopify using the app's shared `client_secret` over `B` only.
3. Attacker POSTs to the app's webhook endpoint with the same body `B` and the same valid HMAC header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against the HMAC [5](#0-4) .
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: B ...)` [6](#0-5) , letting the attacker inject data under the victim's tenant identity.
