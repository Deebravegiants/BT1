### Title
Webhook shop-domain identity not covered by HMAC allows cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook by validating an HMAC, then hands the handler a `shop` value that was never covered by that HMAC. This mirrors the reported bug class: a field that is acted upon (here, the shop identity used by the handler) is not covered by the integrity check that is supposed to bind the whole request together (there, the fee logic that didn't match what was actually cryptographically/logically guarded).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

`shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, entirely outside the signed material: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then forwards `request.shop` — the unauthenticated header value — to the handler as the tenant identifier: [3](#0-2) 

Because `api_secret_key` is a single per-app secret shared across every merchant that installs the app (not a per-shop secret), any merchant who installs the app can receive a legitimate webhook for their own shop, capture its `body` + valid `hmac-sha256` header (both valid because they share the same app secret with every other tenant), and replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` (which only checks `to_signable_string`, i.e. the body) will still succeed: [4](#0-3) 

The handler then receives `WebhookMetadata` carrying the attacker-chosen `shop` alongside a validly-"authenticated" body, so the identity binding `authenticated_hmac_scope == shop_acted_on` is broken — the gem hands the host application a shop value that was never bound to the signature.

### Impact Explanation
A host application that (as this gem's own docs instruct, e.g. `data.shop` in `WebhookMetadata`) uses `data.shop` to select which tenant's records to update, delete, or redact (e.g. `customers/redact`, `shop/redact`, `orders/create`) can be made to apply an attacker-controlled shop's webhook payload against a different, victim merchant's tenant. This is a cross-tenant data-integrity/confusion issue reachable by any unprivileged merchant who has installed the app — no access token or leaked credential is required, since they only need a webhook that Shopify itself will legitimately deliver to their own shop's endpoint.

### Likelihood Explanation
Requires only: (1) the attacker installs the target app on their own shop (unprivileged, self-service), (2) they observe one webhook delivery to capture a valid `(raw_body, hmac)` pair, and (3) they replay it to the app's public webhook endpoint with a forged `shop-domain` header. No secrets, tokens, or elevated access are needed, making this practically achievable for any app that trusts `request.shop`/`data.shop` from this gem.

### Recommendation
Include the shop domain (and ideally the topic) in the HMAC-signable material used for webhook verification, or otherwise cryptographically bind the `shop` header to the payload before exposing it as `WebhookMetadata#shop`, so that `HmacValidator.validate` fails whenever the shop header has been altered from what Shopify actually signed.

### Proof of Concept
1. Install the target Shopify app on attacker-owned shop `attacker.myshopify.com`.
2. Let Shopify deliver any webhook (e.g. `orders/create`) to the app's HTTP endpoint; capture the raw POST body and the `X-Shopify-Hmac-Sha256` header value.
3. Replay a new POST to the same endpoint with the identical body and `X-Shopify-Hmac-Sha256` header, but set `X-Shopify-Shop-Domain: victim.myshopify.com` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id` as desired).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `request.to_signable_string` (the body) against the shared `api_secret_key`; validation succeeds because the body/hmac pair is legitimate.
5. The registered handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's payload>, ...)`, causing the host app to act on attacker-controlled data as if it originated from `victim.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
