### Title
Stale `SetRelayer`/`UpgradeContract` governance message can be delivered after a newer one, letting the relayer that controls delivery order silently reassign paymaster/gateway/HostManager governance authority - ([File: evm/src/utils/SimplexPaymaster.sol])

### Summary
`SimplexPaymaster.onAccept`, `HostManager.onAccept`, and `ExtrinsicIntents.onAccept` each gate governance requests on a single `_relayer`/`_admin` address, but the underlying ISMP request-delivery layer imposes no ordering or expiry on dispatched requests. When Hyperbridge dispatches two governance requests to the same module in the same interval (e.g. two successive `SetRelayer` rotations, or an `UpgradeContract` followed by a rotation), whichever one the delivering relayer submits *last* wins, regardless of dispatch order. This mirrors the report's "sidebar" bug class: multiple pending, order-dependent state-changing requests share one mutable slot, and whoever controls the *delivery/rendering order* determines the final authoritative state rather than the party that issued the most recent intent.

### Finding Description
`SimplexPaymaster.onAccept` (`evm/src/utils/SimplexPaymaster.sol:313-344`) processes `RequestKind.SetRelayer` by simply overwriting `_relayer` with whatever address is decoded from the delivered body — there is no nonce, sequence number, or timestamp check tying the write to dispatch order: [1](#0-0) 

The `_checkRelayer` gate only verifies that the *current* on-chain `_relayer` matches `incoming.relayer`; it does not verify that the *request being processed* is the most recently dispatched one: [2](#0-1) 

The project's own design notes acknowledge this is not just a theoretical edge case but an explicit, accepted hazard: "requests never expire and the relayer picks delivery order, so a superseded `SetRelayer(A)` delivered last hands A the sole key": [3](#0-2) 

The same pattern of "the currently authorised relayer is checked, but delivery order/staleness of the message content is not" also appears in `HostManager.onAccept` and `ExtrinsicIntents.onAccept`, both of which are documented as relying entirely on the *current relayer's honesty about ordering*: [4](#0-3) [5](#0-4) 

This is directly analogous to the report's core defect: several state-changing "requests" (there: dapp confirmation layers; here: cross-chain governance requests) are queued for the same shared slot with no guarantee that the *last delivered* one is the *last issued* one. In the browser-extension case, the attacker exploits timing on a shared UI layer stack; here, the exploitable party is the **relayer itself** — an unprivileged, permissionless role explicitly reachable in Hyperbridge's threat model — who decides in what order to submit two already-dispatched, still-undelivered messages to the destination chain.

### Impact Explanation
If governance ever dispatches two ordering-sensitive requests to the same contract before the first is confirmed delivered (e.g., a routine relayer-key rotation followed shortly by an emergency rotation reacting to a suspected key compromise, or an `UpgradeContract` followed by a `SetRelayer`), the delivering relayer — who is by design the only party permitted to submit these requests, and by design untrusted for confidentiality/ordering purposes — can choose to submit the *stale* request last. Because `onAccept` unconditionally applies whatever `SetRelayer`/`UpdateParams`/`Withdraw` payload it decodes, the stale message becomes the permanent state: a compromised or malicious relayer key that governance intended to revoke is instead the one left installed, or a parameter rollback silently reinstates the wrong values. Since `_relayer` gates *all* future governance for the paymaster (including asset withdrawal, `WithdrawAssets`/`WithdrawStake`, upgrades, and further `SetRelayer` calls), and the design notes confirm "there is no second key," this can result in **permanent loss of governance control** over EntryPoint deposit, stake, and fee surplus held by `SimplexPaymaster`, or unauthorized persistence of an already-compromised relayer/admin key on `HostManager`/`ExtrinsicIntents`, which gate host parameter updates and gateway upgrades.

### Likelihood Explanation
Exploitation does not require breaking any cryptographic proof — the relayer is already the trusted-but-unprivileged party permitted to submit these ISMP requests, and the vulnerability is purely about *choosing which of two already-valid, already-dispatched messages to submit first*. The precondition (two governance requests targeting the same module outstanding at once) is realistic precisely in the scenario governance most needs it to work correctly: an emergency key rotation issued to displace a relayer that is behaving suspiciously — i.e., the exact moment a malicious/compromised relayer has the strongest incentive to reorder deliveries in its own favor.

### Recommendation
Bind each governance action to the dispatch order rather than relying on delivery order:
- Include an on-chain-readable monotonically increasing sequence number (or the request's own ISMP `nonce`) in the `SetRelayer`/`UpdateParams`/`Withdraw`/`Execute` payload, and have `onAccept` reject any incoming request whose sequence number is not strictly greater than the last applied one for that action class.
- Alternatively, require the pallet dispatcher (`set_paymaster_relayer`, `set_host_manager_admin`, `execute_on_gateway`) to enforce "one outstanding governance request per module at a time," refusing to dispatch a new one until the previous one's `RequestReceipts[commitment]` proves delivery — closing exactly the race the design doc currently just documents and accepts.
- For safety-critical actions (`SetRelayer`/`SetAdmin`), consider also requiring the previous request be explicitly retracted/timed-out on Hyperbridge before a new one for the same slot can be dispatched, so a relayer can never "choose" between two live candidates.

### Proof of Concept
1. Governance dispatches `set_paymaster_relayer(chain, relayerA)` at block N (routine rotation).
2. Before the delivering relayer submits it on the destination chain, governance detects that the *current* relayer key is compromised and dispatches `set_paymaster_relayer(chain, relayerB)` at block N+1 (emergency rotation), intending B to be final.
3. Both `PostRequest`s are now valid, proven-deliverable ISMP messages sitting in the relayer's queue; neither has a `RequestReceipts[commitment]` entry yet.
4. The delivering relayer (which may itself be the "compromised" key being rotated away, or colluding with it) submits the request encoding `relayerA` *after* the request encoding `relayerB`.
5. `SimplexPaymaster.onAccept` (`evm/src/utils/SimplexPaymaster.sol:339-343`) applies `SetRelayer(relayerA)` last with no check against the earlier `SetRelayer(relayerB)` delivery, leaving `_relayer == relayerA` — the key governance intended to revoke — as the sole future governance authority over the paymaster's stake, deposit, and fee surplus.

    function onAccept(IncomingPostRequest calldata incoming)
        external
        override
        restrict(msg.sender, _params.host)
        restrict(incoming.relayer, _params.admin)
    {
        PostRequest calldata request = incoming.request;
        // Only the Hyperbridge parachain can send requests to this module.
        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.Withdraw) {
            // This is where governance & relayers can withdraw their revenue.
            WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
            IHostManager(_params.host).withdraw(withdrawParams);
        } else if (action == OnAcceptActions.SetHostParam) {
            HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
            IHostManager(_params.host).updateHostParams(hostParams);
        } else if (action == OnAcceptActions.SetAdmin) {
            // Rotates the governance relayer.
            address newAdmin = abi.decode(request.body[1:], (address));
            if (newAdmin == address(0)) revert InvalidAdmin();
            emit AdminUpdated({previous: _params.admin, current: newAdmin});
            _params.admin = newAdmin;
        }
    }
