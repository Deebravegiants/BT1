### Title
Blacklisted USDC-style tokens cause permanent freezing of escrowed order refunds in IntentGatewayV2 (`_withdraw`) - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw` always sends escrowed tokens to a hardcoded beneficiary address (`order.user` for cancellations/refunds, `msg.sender` for fills) via `IERC20.safeTransfer`, with no alternate withdrawal path. If the escrowed input token implements an address blacklist (e.g. USDC) and the refund/redeem beneficiary becomes blacklisted, the transfer permanently reverts and the escrowed funds can never be released.

### Finding Description
When an order is cancelled (same-chain or cross-chain) or an escrow is redeemed, `_withdraw` is the single code path that releases the escrowed `TokenInfo[]` to a beneficiary: [1](#0-0) 

The beneficiary is fixed at the time of order placement/cancellation and cannot be redirected:
- Same-chain cancel: `beneficiary = order.user` [2](#0-1) 
- Cross-chain cancel-from-destination: `beneficiary = order.user`, dispatched as a `RefundEscrow` message back to the source chain [3](#0-2) 
- Cross-chain cancel-from-source: `beneficiary = order.user` from the GET-response handler [4](#0-3) 

In all three cases, `_withdraw` executes `IERC20(token).safeTransfer(beneficiary, amount)` unconditionally [5](#0-4) . There is no `IntentsBase` function that lets `order.user` specify or update a different receiving address, and the `_orders[commitment][token]` escrow accounting is only decremented after a successful transfer — so a reverting transfer leaves the accounting (and the tokens) exactly where they were, permanently.

This is the same bug class as the referenced report: a token with blacklist functionality (USDC being the canonical example, and explicitly supported as an escrowable input asset in the test suite, e.g. [6](#0-5) ) can render the escrow-refund/redeem functions unusable for a specific beneficiary, with no recovery mechanism in the contract.

### Impact Explanation
If `order.user`'s address is placed on the token issuer's blacklist at any point before the order is cancelled/refunded (e.g., compliance action, court order, or the attacker deliberately triggering blacklisting on an address they control before placing an order, then getting it blacklisted to grief a solver who partially filled and expects a redeem, or simply an unlucky legitimate user), the corresponding escrowed input tokens become permanently locked inside `IntentGatewayV2`. No governance or emergency function exists in the reviewed contracts to redirect that specific escrow to a different address; `cancelOrder` and `onAccept`/`onGetResponse` will always retry the same hardcoded beneficiary and always revert. This is a permanent freezing of user (or solver) funds, matching the "Accept only concrete theft or permanent freezing of funds" validation bar.

### Likelihood Explanation
Likelihood is moderate: it requires the token used as order input to implement address-level blacklisting (true for USDC/USDT, which the intent gateway explicitly supports as escrowable tokens per the test fixtures) and for the specific beneficiary address to become blacklisted while an order/escrow is outstanding. This is a realistic condition for USDC given Circle's active blacklist enforcement, and the protocol has no way to detect or work around it once triggered — every subsequent cancel/redeem attempt reverts deterministically.

### Recommendation
Add a fallback/pull-based withdrawal mechanism for `_withdraw`: if a direct `safeTransfer` to the beneficiary reverts (e.g. wrap in try/catch), credit the amount to an internal balance mapping keyed by `(beneficiary, token)` that the beneficiary (or a delegate address they designate) can later `claim(token, to)` to pull funds to an alternate, non-blacklisted address. Alternatively, allow the order beneficiary to pre-register/update a recovery address for refunds before the blacklisting event.

### Proof of Concept
1. Alice places a cross-chain order using USDC as `order.inputs`, with `order.user` = Alice's address; USDC is escrowed in `IntentGatewayV2` [7](#0-6) .
2. Before the order is filled, Circle blacklists Alice's address (independent external event).
3. Alice (or anyone, after deadline) calls `cancelOrder`, which on the destination chain marks `_filled[commitment] = order.user` and dispatches a `RefundEscrow` message back to source [3](#0-2) .
4. On the source chain, `onAccept` receives the `RefundEscrow` message and calls `_withdraw(body, true, true)`, which attempts `IERC20(USDC).safeTransfer(alice, amount)` [5](#0-4) ; this reverts because Alice is blacklisted.
5. Because the transfer revert occurs before `_orders[commitment][token]` is decremented, the escrow entry remains intact but unreachable — every future retry of the same message/withdrawal reverts identically, and Alice's USDC is permanently stuck in `IntentGatewayV2` with no alternate recovery path.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

            order, _body(RequestKind.RefundEscrow, commitment, order.inputs, order.user), options.relayerFee, msg.value
