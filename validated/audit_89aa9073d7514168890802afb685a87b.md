## Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as fully authenticated once `Utils::HmacValidator.validate` succeeds, and then forwards `request.shop` (from the `x-shopify-shop-domain` header) to the app's handler as the tenant identifier. However, the HMAC is computed only over the raw body, not over the `shop` header, so the binding `authenticated_body == request.shop` never actually holds — an attacker who owns any store using the same app can replay a legitimately-signed body while substituting a different shop's domain in the header, and the signature still validates.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `hmac` is read from the `hmac-sha256` header while `shop` is read independently from the `shop-domain` header, neither of which participates in the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies `verifiable_query.to_signable_string` (i.e. the raw body) against `verifiable_query.hmac`, using the app's single, per-app `api_secret_key`: [3](#0-2) 

`Registry.process` gates on that same HMAC check, then immediately builds `WebhookMetadata` from `request.shop` — an unauthenticated field — and dispatches it to the handler as trusted tenant context: [4](#0-3) 

Because a single `api_secret_key` is shared by an app across *all* installed shops, any store owner who installs the app can trigger a real webhook, capture its raw body + valid `x-shopify-hmac-sha256` value, and replay that exact body/HMAC pair to the app's webhook endpoint while swapping the `x-shopify-shop-domain` header to point at a different (victim) tenant of the same app. `HmacValidator.validate` still passes because it never looks at the shop header, so `Registry.process` calls the handler with `shop: <victim>` and attacker-supplied body content. This breaks the intended identity binding: "HMAC-authenticated bytes" should equal "the shop the bytes are attributed to," but the shop is parsed from bytes that were never verified.

### Impact Explanation
This is a cross-tenant access/injection primitive: an attacker with only unprivileged access to their own store (a free/dev shop that installs the target app) can make the app process attacker-chosen webhook payloads under a victim shop's identity. Depending on how the host app's handler uses `WebhookMetadata#shop` (e.g., to select the DB tenant/session, credit/debit tenant-scoped resources, redact data, mark GDPR compliance events, etc.), this can lead to cross-tenant data corruption, spoofed events for a shop the attacker doesn't operate, or bypass of tenant isolation — matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation requires no privileged credentials or secrets: the attacker only needs to install the app on a shop they control (a normal, permitted action for any Shopify developer/merchant) to obtain one validly-HMAC-signed body/header pair, and standard HTTP tooling to replay it with a different `shop-domain` header to the public webhook endpoint. No `api_secret_key`, access token, or victim credential is required.

### Recommendation
Bind the shop (and topic/webhook id) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived `shop` to the verified body — e.g. include the shop/topic in `to_signable_string`, or cross-check `request.shop` against a shop already known/authorized for the session/store the webhook claims to originate from before trusting it. At minimum, document and enforce that `request.shop` must not be treated as authenticated purely because `HmacValidator.validate` passed.

### Proof of Concept
1. App is installed on attacker's own shop `attacker.myshopify.com` and on victim shop `victim.myshopify.com`, both under the same Shopify app (same `api_secret_key`).
2. Attacker triggers a real webhook (e.g. `orders/create`) on their own shop, capturing:
   - raw body `B`
   - header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the shared `api_secret_key`)
3. Attacker sends a POST to the app's webhook endpoint with:
   - body `B` (unchanged, so `H` still validates)
   - `x-shopify-topic: orders/create`
   - `x-shopify-hmac-sha256: H`
   - `x-shopify-shop-domain: victim.myshopify.com` (swapped)
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H` (see `lib/shopify_api/webhooks/request.rb:35-43` and `lib/shopify_api/utils/hmac_validator.rb:12-31`).
5. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: <attacker's parsed body>, ...)`, i.e., attacker-controlled data processed under the victim tenant's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
