### Title
Single-DEX (Uniswap V2), unbounded-slippage native-to-fee-token swap in `placeOrder` enables sandwich extraction from order placers - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.placeOrder()` converts native token supplied by the order-placer into the protocol fee token by calling `swapETHForExactTokens` on a single, statically-configured Uniswap V2 router, with no aggregator, no multi-DEX comparison, and no minimum-price/TWAP protection beyond the caller's own `msg.value` buffer. This mirrors the reported bug class ("using only DEX swappers is suboptimal") but manifests here as a reachable value-extraction vector: any user who pays the order's `fees` in native token during `placeOrder` can be sandwiched, paying more ETH than the fair market rate for the fee token.

### Finding Description
In `placeOrder`, when `order.fees > 0` and the user funds the fee with native token (`msgValue > 0`), the contract swaps native token for an exact amount of fee tokens using only Uniswap V2: [1](#0-0) 

The router address (`IDispatcher(hostAddr).uniswapV2Router()`) is a single fixed liquidity source. `swapETHForExactTokens` treats the caller's `msg.value` as an implicit `amountInMax`: if the required input exceeds `msgValue` the whole `placeOrder` transaction reverts, and any leftover `msgValue` (i.e. `msgValue - amounts[0]`) is refunded to the user: [2](#0-1) 

Because the contract relies exclusively on live Uniswap V2 spot pricing (no aggregator to route around a manipulated pool, no oracle/TWAP check, and no floor on how much of the buffer can legitimately be consumed), a searcher can front-run the `placeOrder` transaction by buying the fee token on the same V2 pool to inflate its price, letting the victim's `swapETHForExactTokens` consume a much larger portion of their supplied ETH buffer for the same fixed `order.fees` output, then back-run to sell and capture the difference. Users must supply a generous ETH buffer above the current quoted price to avoid reverts on normal price fluctuation, and that buffer is exactly what is placed at risk to a sandwich attacker since there is no minimum-output/maximum-input check tied to a fair reference price — only the user's own buffer serves as (attacker-exploitable) slack. This directly parallels the audit's "only DEX swappers, no aggregator" finding, but escalates it from "suboptimal rates" to concrete value extraction because there is only one liquidity venue and no external price-comparison or slippage-bound derived from real market data.

`placeOrder` is `public payable` and callable by any unprivileged account, so this is reachable from a single submitted transaction with no special privileges, satisfying the "unprivileged... token bridger" reachability requirement.

### Impact Explanation
An attacker (searcher/MEV bot) can extract value from any order placer who funds the intent fee with native token, by sandwiching the single Uniswap V2 swap. The size of extractable value scales with the ETH buffer the user must supply and the depth/manipulability of the fee-token/WETH V2 pool — for illiquid fee-token pools this can be a significant fraction of the fee payment, representing a direct loss of user funds during a core, everyday user action (placing an order).

### Likelihood Explanation
Every `placeOrder` call that pays `order.fees` in native token exercises this code path, so the attack surface is present on essentially all such orders. Exploitability depends on mempool visibility of the `placeOrder` transaction and the depth of the specific Uniswap V2 fee-token pool, which is realistic on public networks with standard MEV infrastructure. This aligns with the source report's "Medium likelihood — depends on swap size and pool liquidity."

### Recommendation
Do not rely on a single DEX/spot-price swap for a value-bearing conversion inside `placeOrder`. Either (a) require the user to pre-supply the fee token directly (skip on-chain swapping), (b) route the native-to-fee-token conversion through an aggregator or multiple DEXs and pick the best price, or (c) enforce a maximum acceptable input bound derived from an oracle/TWAP price rather than trusting the user-supplied `msg.value` as the only slippage control, and/or use commit-reveal / private relays to prevent sandwiching of the swap.

### Proof of Concept
1. Attacker observes a pending `placeOrder(order, graffiti)` transaction in the mempool where `order.fees > 0` and the caller sends `msg.value` covering both inputs and a fee-token buffer.
2. Attacker front-runs with a large `swapExactETHForTokens`/`swapTokensForExactTokens` on the same Uniswap V2 pool used by `uniswapV2Router`/`feeToken`/WETH pair, pushing the fee-token price up.
3. Victim's `placeOrder` executes `swapETHForExactTokens{value: msgValue}(order.fees, [WETH, feeToken], address(this), block.timestamp)` at the inflated price, consuming a larger share of `msgValue` than it would have absent manipulation (still ≤ `msgValue`, so no revert, but `amounts[0]` is inflated and less is refunded).
4. Attacker back-runs, selling the fee token back into the pool, capturing the price spread as profit at the direct expense of the value transferred out of the victim's `msg.value`.
