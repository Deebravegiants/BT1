### Title
Escrowed intent fees are settled using the host's *current* `feeToken`, not the token actually collected at order placement, causing frozen/misappropriated fees after a `feeToken` update - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
Intent orders escrow protocol/relayer fees under the amount-only key `TRANSACTION_FEES`, without recording which ERC-20 was actually collected. When those fees are released, the contract looks up `IDispatcher(host()).feeToken()` at withdrawal time and transfers that *current* token. If Hyperbridge governance updates the host's `feeToken` (an intended, documented capability) between order placement and settlement, the fee amount recorded for older orders no longer corresponds to any token actually held by the gateway, exactly mirroring the `AgentFactory::assetToken` analog: a single mutable global address is consulted by multiple downstream functions instead of being pinned per-record at creation time.

### Finding Description
`IntentGatewayV2.placeOrder` escrows the order's fee using the fee token that is active *at placement time*: [1](#0-0) 

This only stores the numeric `amount` under a fixed pseudo-token key, `TRANSACTION_FEES`, with no binding to the specific ERC-20 address used to collect it.

At settlement (`RedeemEscrow`/`RefundEscrow`), `_withdraw` releases those fees by re-querying the host for its feeToken *at withdrawal time*, not the token that was actually escrowed: [2](#0-1) 

The same pattern exists in the Tron variant: [3](#0-2) 

The host's `feeToken` is an admin/governance-mutable global (`EvmHost.updateHostParamsInternal`), explicitly documented as changeable "to prevent future regrets": [4](#0-3) [5](#0-4) 

Critically, the only safety check (`CannotChangeFeeToken`) inspects the **EvmHost's own** balance of the old fee token — it has no visibility into balances escrowed inside downstream `IApp` contracts like `IntentGatewayV2`/`IntentsBase`. So governance can legitimately rotate `feeToken` (via `HostManager.onAccept` → `IHostManager.updateHostParams`) at a moment when the EvmHost itself holds zero of the old token, while the IntentGateway still holds old-token balances escrowed as `TRANSACTION_FEES` for outstanding orders: [6](#0-5) 

Once the update lands, any pending order's `_orders[commitment][TRANSACTION_FEES]` amount is interpreted against the new `feeToken`. This is the same root cause pattern as `AgentFactory::assetToken`: a public/global address variable is set once, consulted by multiple functions that operate on independently created records (`Application` there, `Order`/commitment here), and an authorized-but-ordinary update to that variable breaks the binding between the record and the asset it actually holds.

### Impact Explanation
- **Freezing of funds**: If the gateway's balance of the *new* feeToken is insufficient to cover the recorded `fees` amount for old orders, `safeTransfer` reverts, blocking `_withdraw`'s `finalize` step. Since `finalize` also marks the order filled and, in the cross-chain flow, is the only path to release escrowed input tokens for that commitment, this can trap the entire order's escrow (fees plus principal), not just the fee amount — the previously collected old-feeToken balance is permanently stuck in the contract with no recovery function for this accounting bucket.
- **Cross-user fund misappropriation**: If the gateway happens to hold *some* new-feeToken balance (e.g., fees collected from other orders placed after the rotation), an old order's `_withdraw` will pay out that unrelated balance to its beneficiary, effectively taking funds belonging to unrelated newer orders' fee pool, since `TRANSACTION_FEES` accounting is amount-only and not partitioned by actual token.

This satisfies "permanent freezing of funds" and "concrete theft," triggered by an ordinary, documented governance action combined with a normal user's order lifecycle (place → later settle).

### Likelihood Explanation
`feeToken` rotation is an explicitly supported, non-malicious governance operation (the code comment says it's "configurable to prevent future regrets"), and `HostManager`/`EvmHost` provide a straightforward, sanctioned path to perform it. The only guard rail checks the host's own balance, which is trivially satisfied even while IntentGateway apps still hold outstanding escrowed fees for in-flight orders — a realistic and likely operational scenario given intent orders can remain open across a challenge/settlement period.

### Recommendation
Store the actual fee-token address per order/commitment (e.g., add a `feeToken` field to the escrowed fee record or key `_orders[commitment][...]` by the concrete token address that was collected) instead of relying on a live call to `IDispatcher(host()).feeToken()` inside `_withdraw`. Use that stored address for all subsequent fee transfers, mirroring the C4 recommendation to bind assets to the `Application`/`Order` record rather than to a mutable global variable.

### Proof of Concept
1. User places an intent order with `order.fees > 0`; `IntentGatewayV2.placeOrder` collects `order.fees` in `feeToken_A` (current `IDispatcher(host()).feeToken()`), recording `_orders[commitment][TRANSACTION_FEES] = order.fees` (evm/tron/contracts/apps/IntentGatewayV2.sol:471-488).
2. Before the order is filled/settled, Hyperbridge governance rotates the host's fee token to `feeToken_B` via `HostManager.onAccept` → `EvmHost.updateHostParamsInternal` (evm/src/core/EvmHost.sol:617-621). This succeeds because the EvmHost itself holds none of `feeToken_A`, even though the IntentGateway contract still holds the escrowed `feeToken_A` balance for this order.
3. The order is later filled/refunded; `_withdraw` calls `IDispatcher(host()).feeToken()`, which now returns `feeToken_B`, and attempts `IERC20(feeToken_B).safeTransfer(beneficiary, fees)` (evm/src/apps/intentsv2/IntentsBase.sol:472-477).
4. Either the transfer reverts (IntentGateway holds no `feeToken_B`), permanently blocking `finalize` and freezing the order's entire escrow, or if `feeToken_B` balance exists from other orders' newly-collected fees, the beneficiary receives tokens that rightfully belong to those other orders — producing a shortfall when those other orders later attempt to withdraw their own fees.
