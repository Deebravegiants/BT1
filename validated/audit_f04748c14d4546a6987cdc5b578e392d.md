Audit Report

## Title
CORS wildcard-origin allowlist bypass via unanchored `strings.HasSuffix` domain matching - (File: `core/services/gateway/network/httpserver.go`)

## Summary
The gateway's `isAllowedOrigin` function validates wildcard CORS allowlist entries (e.g. `*.ethereum.org`) by stripping the `*.` prefix and checking `strings.HasSuffix(originHost, allowedHost)` without verifying that the match occurs at a domain-label boundary. This allows an attacker who registers a domain like `evilethereum.org` to satisfy the suffix check against `ethereum.org`, bypassing the intended subdomain restriction.

## Finding Description
In `isAllowedOrigin`, once a wildcard entry `*.ethereum.org` is stripped to `ethereum.org`, the code performs `strings.HasSuffix(originHost, allowedHost)` at [1](#0-0) . This does not require a `.` immediately before the matched suffix, so `evilethereum.org` (with no dot separator) passes the check just as legitimately as `remix.ethereum.org` would. This function is called directly from the public-facing request handler `handleRequest`, which reflects the `Origin` header into `Access-Control-Allow-Origin` when `isAllowedOrigin` returns true: [2](#0-1) . There is no other validation, sanitization, or anchoring logic anywhere in this file that would catch this boundary-less match — the exact and wildcard branches are the only two checks performed, both shown at [3](#0-2) .

The existing test suite in `httpserver_test.go` confirms wildcard matching is a supported, documented configuration pattern (e.g. `https://*.ethereum.org`) at [4](#0-3) , but does not include a negative test case for a suffix-only match like `evilethereum.org`, confirming the gap is untested and unmitigated. The negative test cases at [5](#0-4)  only test unrelated domains, port mismatches, and scheme mismatches — none test the boundary-bypass case described in this report.

## Impact Explanation
If an operator configures a wildcard CORS entry (a documented and tested pattern), an attacker can register a domain that shares the trusted domain as a literal suffix without a dot separator (e.g. `evilethereum.org` vs. `*.ethereum.org`). A victim visiting an attacker-hosted page at that domain would have their browser issue cross-origin requests to the gateway with `Origin: https://evilethereum.org`; the gateway would reflect this origin in `Access-Control-Allow-Origin`, permitting the attacker's JavaScript to read the gateway's response cross-origin. This is a concrete allowlist bypass leading to unauthorized cross-origin data access, matching the "allowlist bypass" / "cross-user response corruption" impact categories relevant to gateway request handling.

## Likelihood Explanation
Exploitation requires only that an operator has configured a wildcard `CORSAllowedOrigins` entry (an intended, documented, and tested configuration) and that an attacker registers an inexpensive domain sharing the trusted suffix without a preceding dot. No credentials, authentication, or privileged access is required from the attacker — the malicious request originates from a browser visiting the attacker's page, which is standard CORS-bypass exploitation methodology. This is realistic and repeatable.

## Recommendation
Anchor the wildcard suffix match to a domain-label boundary, e.g.:
```go
if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
    return true
}
```
This ensures `originHost` must either equal `allowedHost` exactly or be a genuine subdomain (separated by a `.`), rejecting values like `evilethereum.org` while still accepting `remix.ethereum.org`.

## Proof of Concept
1. Start the gateway HTTP server with `CORSEnabled: true` and `CORSAllowedOrigins: []string{"https://*.ethereum.org"}` (using the same `startNewServer` helper as in `httpserver_test.go`).
2. Send a request with header `Origin: https://evilethereum.org`.
3. Observe that `isAllowedOrigin` returns `true` because `strings.HasSuffix("evilethereum.org", "ethereum.org")` is `true`, and the response includes `Access-Control-Allow-Origin: https://evilethereum.org`.
4. Add this as a new test case in `httpserver_test.go` alongside `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards`, asserting that `resp.Header.Get("Access-Control-Allow-Origin")` is currently non-empty (bug) versus the expected empty string (fixed behavior) at [6](#0-5) .

func (s *httpServer) handleRequest(w http.ResponseWriter, r *http.Request) {
	if s.config.CORSEnabled {
		origin := r.Header.Get("Origin")
		if s.isAllowedOrigin(origin) {
			w.Header().Set("Access-Control-Allow-Origin", origin)
			w.Header().Set("Access-Control-Allow-Methods", "GET, POST, OPTIONS")
			w.Header().Set("Access-Control-Allow-Headers", "Content-Type")
		}
