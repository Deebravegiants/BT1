### Title
Rounding-to-zero escrow release in partial fills lets the completing solver steal earlier partial fillers' due input tokens - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`_fillSameChain` computes the proportional escrow released to a partial filler as `escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired` [1](#0-0) . When `order.inputs[i].amount` is small relative to `totalRequired` (a ratio fully controlled by the order-placing user, e.g. a low-decimal/low-amount input token paired against a large-amount output requirement), this integer division truncates to zero for any solver whose `fillAmount` is below `totalRequired / order.inputs[i].amount`. That solver delivers real output tokens to the beneficiary but is credited zero input tokens.

### Finding Description
This mirrors the reported Kairos bug (`shareMatched = arg.amount.div(arg.offer.loanToValue)` rounding to zero shares for large-LTV offers). Here, the analogous "share" is the escrowed input amount computed per partial fill.

Because `_withdraw` treats a zero-amount token entry as a no-op rather than a hard failure — `if (amount == 0) continue;` [2](#0-1)  — a rounding-to-zero partial fill neither reverts nor errors. The escrow balance for that token stays untouched in `_orders[commitment][token]` even though the solver already paid the beneficiary. Later, whichever solver's fill happens to make `amountFilled == totalRequired` takes the **entire remaining stored balance** rather than a proportional share:

```solidity
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
}
``` [3](#0-2) 

This full-balance sweep on completion was intentionally added (per the in-repo regression tests) to avoid leaving rounding dust locked in the contract when the *same* solver completes across multiple truncated fills [4](#0-3) . However, it does not distinguish between "dust owed to me" and "dust owed to a different solver whose fill rounded to zero." When distinct solvers partially fill the same order, a solver whose fill rounds to zero is permanently denied their earned escrow, and whichever unrelated solver happens to complete the order collects that solver's due tokens on top of its own.

### Impact Explanation
This is concrete theft of solver funds: a solver transfers real output tokens to the order's beneficiary but receives zero (or less than proportional) escrowed input in return, while a different, later solver is credited the shortfall. An attacker acting as the "completer" solver can watch the mempool/order state, structure fills so an earlier legitimate solver's contribution rounds to zero, then complete the order and collect the full remaining escrow — extracting value that rightfully belonged to another solver.

### Likelihood Explanation
The ratio between `order.inputs[i].amount` and `totalRequired` is fully determined by the order creator and can be arbitrarily skewed (e.g., pairing a tiny-amount/low-decimal input token against a large nominal output amount), so triggering the zero-rounding condition requires no special privilege — any user placing an order controls the exploitability, and any solver (or a colluding pair of accounts) can then exploit the partial-fill race. No governance or admin compromise is needed; a single crafted order plus two ordinary `fillOrder` transactions is sufficient.

### Recommendation
Track escrow entitlement per-filler (or accumulate rounding remainders explicitly) instead of relying solely on "current stored balance" at completion time. At minimum, revert or accrue a claimable credit when `escrowedAmount` rounds to zero for a non-zero `fillAmount`, so a filler's proportional entitlement is never silently dropped and cannot be swept by an unrelated solver.

### Proof of Concept
1. User places an order with `inputs[0].amount = 1` (e.g. a token with very coarse units) and `output.assets[0].amount = 1_000_000` of some output token.
2. Solver A fills with `solverAmount = 999_999` (just short of completion): `fillAmount = 999_999`, `escrowedAmount = (1 * 999_999) / 1_000_000 = 0`. Solver A pays 999,999 output tokens to the beneficiary and is credited 0 input tokens; `_orders[commitment][inputToken]` still holds `1`.
3. Solver B fills the remaining `1` unit: `amountFilled == totalRequired`, so `escrowedAmount = _orders[commitment][inputToken] = 1`. Solver B receives the entire `1` unit of escrowed input despite having contributed only 1/1,000,000th of the output, while Solver A receives nothing for its 999,999-unit contribution.

    /*//////////////////////////////////////////////////////////////
                    ROUNDING DUST IN PARTIAL FILLS (Finding #4)

    /// @notice Verifies that rounding dust from integer division in partial fills
    /// is not permanently locked. The final solver completing the order should
    /// receive the full remaining escrow balance rather than a truncated amount.
    function testPartialFill_RoundingDustReleasedToFinalSolver() public {
        // Choose amounts that produce rounding truncation:
        // input = 100 USDC (100e6), output = 3 DAI (3e18)
        // Each of 3 solvers fills 1 DAI. Proportional release per fill:
        //   100e6 * 1e18 / 3e18 = 33333333 (truncated from 33333333.33...)
        // Without fix: 3 * 33333333 = 99999999, leaving 1 unit locked.
        // With fix: final solver gets remaining balance = 100e6 - 2*33333333 = 33333334
        uint256 inputAmount = 100 * 1e6; // 100 USDC
        uint256 outputAmount = 3 * 1e18; // 3 DAI

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: outputAmount});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        // User places order
        vm.startPrank(user);
        usdc.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;

        uint256 fillPerSolver = 1e18; // Each solver fills 1 DAI
        uint256 truncatedRelease = (inputAmount * fillPerSolver) / outputAmount; // 33333333

        // --- Solver 1 fills 1 DAI ---
        address solver1 = makeCleanAddr("solver1");
        vm.deal(solver1, 1 ether);
        deal(address(dai), solver1, 10 * 1e18);
        uint256 solver1UsdcBefore = usdc.balanceOf(solver1);

        vm.startPrank(solver1);
        dai.approve(address(intentGateway), fillPerSolver);
        TokenInfo[] memory out1 = new TokenInfo[](1);
        out1[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: fillPerSolver});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, validUntil: 0, outputs: out1}));
        vm.stopPrank();

        assertEq(
            usdc.balanceOf(solver1),
            solver1UsdcBefore + truncatedRelease,
            "Solver1 should receive truncated proportional USDC"
        );

        // --- Solver 2 fills 1 DAI ---
        address solver2 = makeCleanAddr("solver2");
        vm.deal(solver2, 1 ether);
        deal(address(dai), solver2, 10 * 1e18);
        uint256 solver2UsdcBefore = usdc.balanceOf(solver2);

        vm.startPrank(solver2);
        dai.approve(address(intentGateway), fillPerSolver);
        TokenInfo[] memory out2 = new TokenInfo[](1);
        out2[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: fillPerSolver});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, validUntil: 0, outputs: out2}));
        vm.stopPrank();

        assertEq(
            usdc.balanceOf(solver2),
            solver2UsdcBefore + truncatedRelease,
            "Solver2 should receive truncated proportional USDC"
        );

        // --- Solver 3 fills final 1 DAI (completes the order) ---
        address solver3 = makeCleanAddr("solver3");
        vm.deal(solver3, 1 ether);
        deal(address(dai), solver3, 10 * 1e18);
        uint256 solver3UsdcBefore = usdc.balanceOf(solver3);

        vm.startPrank(solver3);
        dai.approve(address(intentGateway), fillPerSolver);
        TokenInfo[] memory out3 = new TokenInfo[](1);
        out3[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: fillPerSolver});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, validUntil: 0, outputs: out3}));
        vm.stopPrank();

        // Final solver should receive the remaining balance (truncatedRelease + 1 rounding unit)
        uint256 expectedFinalRelease = inputAmount - (2 * truncatedRelease); // 33333334
        assertEq(
            usdc.balanceOf(solver3),
            solver3UsdcBefore + expectedFinalRelease,
            "Final solver should receive remaining escrow including rounding dust"
        );
        assertGt(expectedFinalRelease, truncatedRelease, "Final release should be larger due to rounding dust");

        // Gateway should have zero USDC — no dust locked
        assertEq(usdc.balanceOf(address(intentGateway)), 0, "Gateway should have zero USDC - no rounding dust locked");
    }
