The docs explicitly claim `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" (line 125), and `data.shop` is documented as "The shop domain of the webhook" (line 14) — implying it is trustworthy. This is the finding.

### Title
Webhook shop-domain (and topic/webhook_id) headers are dispatched to handlers unauthenticated by the HMAC, breaking the shop-identity binding - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only that HMAC-over-body [3](#0-2) , then forwards the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` directly into `WebhookMetadata` passed to the app's handler.

### Finding Description
The equality broken is: **shop bound by the verified HMAC (∅ — only body bytes are covered)** vs. **shop trusted by the handler dispatch (`request.shop`, read from the `shopify-shop-domain`/`x-shopify-shop-domain` header)**. `Utils::HmacValidator.validate` recomputes the signature purely from `verifiable_query.to_signable_string`, and for `Webhooks::Request` that string is `@raw_body` only [4](#0-3) [1](#0-0) . None of `shop`, `topic`, or `webhook_id` participate in the signature computation, yet `Registry.process` uses exactly these unauthenticated fields to build `WebhookMetadata` and invoke the developer's handler [3](#0-2) . The gem's own documentation states that `process` "will verify the request did indeed come from Shopify" and describes `data.shop` as "The shop domain of the webhook" without qualification, giving developers no signal that this field is unauthenticated.

### Impact Explanation
An unprivileged internet user who has ever observed one legitimate webhook delivery for topic X with body B and its valid HMAC H (e.g., from a public test endpoint, logs, or a webhook sent to their own shop for the same app) can replay that exact `(B, H)` pair to the app's webhook endpoint while forging the `shopify-shop-domain` header to name a different (victim) shop. `Utils::HmacValidator.validate` still passes because H matches B. The app's handler then processes data it believes originates from and pertains to the victim shop — a cross-tenant data/action confusion inside the app built on the gem's documented, "verified" webhook API.

### Likelihood Explanation
Likelihood depends on the attacker having captured at least one legitimate `(body, hmac)` pair for the given app and topic; this is plausible for topics with reusable/generic bodies (e.g., app-uninstalled with predictable minimal payload, or attacker's own shop's webhook body being replayed under a different shop header) but not universally trivial to obtain for every payload shape. The core defect — no binding of `shop`/`topic`/`webhook_id` to the signature — is unconditionally present and unconditionally trusted by every consumer of this documented API. Whether it leads to Critical cross-tenant access in a given host app depends on how strictly the handler uses `data.shop`.

### Recommendation
Do not present `request.shop`, `request.topic`, or `request.webhook_id` as verified once `Utils::HmacValidator.validate` passes. Either document explicitly that only the raw body is authenticated by the HMAC and that `shop`/`topic`/`webhook_id` headers must be independently reconciled by the caller (e.g., cross-checked against an authenticated session or against fields inside the signed body), or extend `Registry.process`/`Request` to require and verify that `shop` matches a value obtained from a route/session already bound to that tenant before dispatching to the handler.

### Proof of Concept
```ruby
# Attacker captured a legitimate webhook delivery for shop A (body + valid hmac)
captured_body = '{"id":123,"note":"hello"}'
captured_hmac_b64 = "..." # valid Base64 HMAC-SHA256(secret, captured_body)

# Attacker replays it against the app's webhook endpoint, spoofing the shop header
headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => captured_hmac_b64,
  "shopify-shop-domain" => "victim-shop.myshopify.com", # forged
  "shopify-webhook-id" => "forged-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) is true (only raw_body is checked),
#    handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)) is invoked
```

**Caveat on confidence:** This finding relies on `to_signable_string` covering only the raw body, which I confirmed directly in `lib/shopify_api/webhooks/request.rb` and `lib/shopify_api/utils/hmac_validator.rb`. It reflects the general Shopify webhook HMAC design (body-only signing) rather than a coding mistake unique to this gem, so its severity is contingent on how strictly a given host application relies on `data.shop`/`data.topic` without independent verification — this dependency on host-app usage is a limitation of the analysis I was able to perform from the library code alone.
