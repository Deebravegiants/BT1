### Title
`IntentGatewayV2::placeOrder` (Tron variant) escrows the requested amount instead of the actual amount received, causing withdrawal reverts for fee-on-transfer/rebasing tokens - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron fork of `IntentGatewayV2.placeOrder` pulls input tokens via `IERC20.safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and credits escrow with `reducedInputs[i].amount`, which is derived purely from the user-specified `order.inputs[i].amount` minus the protocol fee bps — never from the actual token balance received by the contract. This is the same root cause as the referenced H-4 finding (`EtherFiLib::_initiateWithdrawImpl`): the protocol assumes "amount transferred == amount received," which is false for fee-on-transfer tokens and rebasing tokens that internally transfer shares (rounding down by 1-2 wei, or by a fee percentage).

### Finding Description
In `placeOrder`, for the non-predispatch path: [1](#0-0) 
the gateway does `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally does `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` is computed from `order.inputs[i].amount` (the user-requested amount) reduced only by the protocol fee bps: [2](#0-1) 

There is no `balanceOf(address(this))` measurement before/after the transfer (unlike the sibling EVM contract `evm/src/apps/IntentGatewayV2.sol`, which does exactly this delta-based accounting): [3](#0-2) 

Because of this divergence, if the input token is fee-on-transfer or a rebasing token (transferring internal shares with rounding, e.g. stETH/eETH-style tokens), the Tron gateway will end up holding strictly less balance than what it records in `_orders[commitment][token]`.

Later, `withdraw()` reads the escrow entry and issues a raw `token.call(transfer.selector, beneficiary, amount)` for the full escrowed `amount`: [4](#0-3) 

Since the contract's actual token balance is lower than the escrowed bookkeeping amount, this transfer will fail once the shortfall exceeds the contract's balance (e.g., across multiple orders using the same fee/rebasing token, or on a token with meaningful transfer fees), causing `withdraw` to revert with `TransferFailed`, or reverting on the `EscrowRefunded`/`EscrowReleased` path for `cancelOrder`/`onAccept` (`RedeemEscrow`/`RefundEscrow`).

### Impact Explanation
This is a permanent-freezing-of-funds / denial-of-service class bug reachable from a single unprivileged `placeOrder` transaction by any user using a fee-on-transfer or rebasing ERC20 as an order input on the Tron deployment of the Intent Gateway. Once triggered, escrow accounting becomes insolvent relative to actual balance, and legitimate withdrawals (`RedeemEscrow` on fill, `RefundEscrow`/`cancelOrder` on expiry) for that token can permanently revert, locking user and solver funds in the contract — matching the accepted High severity precedent in the referenced report (contract functionality DoS / stuck funds due to rounding/rebase mismatch between requested and received amounts).

### Likelihood Explanation
The EVM version of this same contract (`evm/src/apps/IntentGatewayV2.sol`) already recognizes and defends against exactly this class of bug — it snapshots `balanceOf` before/after every ERC20 pull and stores the delta as the escrowed amount, with explicit comments about fee-on-transfer tokens, and has dedicated fee-on-transfer-token tests validating this behavior. The Tron variant, however, was not updated with the same fix and still uses the naively requested `amount` for escrow bookkeeping. Any order placed with such a token on the Tron gateway deterministically triggers the mismatch — no attacker action or special conditions are required beyond selecting a fee-on-transfer/rebasing token as an input asset, which the contract does not restrict.

### Recommendation
Apply the same balance-delta pattern used in `evm/src/apps/IntentGatewayV2.sol::placeOrder` (lines 312-329) to the Tron contract: measure `IERC20(token).balanceOf(address(this))` before and after `safeTransferFrom`, and use the actual delta (not `order.inputs[i].amount`) as the basis for `reducedInputs`/escrow crediting in both the predispatch and non-predispatch code paths of `evm/tron/contracts/apps/IntentGatewayV2.sol`.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) and a fee-on-transfer ERC20 token `FOT` with e.g. a 1% transfer fee (as modeled by `FeeOnTransferToken` in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol:2690-2735`, applicable analogously to the Tron contract).
2. User calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}` and `protocolFeeBps = 0`. `safeTransferFrom` moves 1000e18 nominally but the gateway only receives 990e18 (1% burned/fee) — verifiable via `FOT.balanceOf(gateway)`.
3. `_orders[commitment][FOT] += reducedInputs[0].amount` stores `1000e18` (since `reducedAmount == originalAmount` when `protocolFeeBps == 0`), while the gateway's actual `FOT` balance is only `990e18`.
4. When a solver fills the order and dispatches `RedeemEscrow`, `onAccept` → `withdraw` attempts `token.call(transfer.selector, beneficiary, 1000e18)`, which fails because the gateway holds only `990e18`, causing `TransferFailed()` revert and permanently freezing the escrowed funds for that commitment.
