### Title
Timeout refund miscalculates amount if token precision is updated while a cross-chain transfer is pending - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
The `hyper-fungible-token` pallet's `send()` extrinsic locks/burns a user's tokens and encodes the amount into an ISMP `Message` using the current `erc_decimals` precision. If the message never gets delivered and times out, `on_timeout()` re-derives the conversion factor by reading the `Precisions` storage map *at the time the timeout is processed* rather than reusing the value that was in effect when the funds were escrowed. If governance updates the precision for that (asset, destination-chain) pair via `update_token` while the request is still in flight, the refunded amount will differ from the amount originally escrowed — exactly analogous to the ECO bridge issue where a changing `inflationMultiplier` corrupts the amount recomputed on a reverting/returning cross-chain transfer.

### Finding Description
In `send()`, the outgoing amount is fixed into the ISMP request body using the precision read at dispatch time: [1](#0-0) [2](#0-1) 

`erc20_amount` is computed via `convert_to_erc20(amount, erc_decimals, decimals)` and is what gets ABI-encoded into `message.amount`, baked immutably into the dispatched ISMP POST request.

Later, if the request times out (e.g., destination contract paused, gas issues, or simply exceeding the timeout window), `on_timeout` decodes the same `message.amount` but re-fetches the precision from storage at that later point in time: [3](#0-2) 

`Precisions` is mutable at any time via the `update_token` extrinsic, independent of any in-flight requests: [4](#0-3) 

There is no snapshotting of the precision used at `send()` time inside the request body — only the already ERC20-scaled `amount` is carried, with no accompanying `erc_decimals`/`decimals` metadata. Consequently, `convert_to_balance` in `on_timeout` (and, symmetrically, `on_accept`) uses whatever precision is currently configured, not the one used to construct the message: [5](#0-4) 

If `erc_decimals` increases between send and timeout, `on_timeout` divides by a larger power of 10, under-refunding the user (permanent loss of the difference, tokens stuck in the pallet's custodial account or burned supply never restored). If `erc_decimals` decreases, the user is over-refunded relative to what was escrowed/burned (unbacked mint from the pallet's perspective, since the escrowed/burned amount was fixed at send time). This mirrors the reported ECO bridge bug: a fixed cross-chain payload combined with time-varying local conversion parameters produces an amount mismatch when the destination path fails/reverts and funds are returned via a different, later, recomputation.

### Impact Explanation
This directly causes loss of user funds (under-refund) or effectively an unbacked over-mint of the local asset/currency (over-refund) whenever `update_token` changes an asset's precision for a chain while any `send()` requests to that chain are still pending timeout resolution. Because `update_token` explicitly supports changing `Precisions` for existing chains (not just first registration), and outgoing message timeouts can be arbitrarily long (`params.timeout`), the window for this to occur in normal operational maintenance (e.g., fixing a misconfigured decimals value, or a token redeploy on the destination chain with different decimals) is realistic, not purely theoretical/malicious-governance.

### Likelihood Explanation
Likelihood is moderate: it requires (1) an in-flight `send()` message to a given (asset, destination) pair, (2) the message eventually timing out (destination paused, unreachable, or simply not relayed before the timeout), and (3) a `Precisions` update for that same pair occurring in between via `update_token`. Precision changes are an expected part of asset lifecycle management (e.g., re-registering/redeploying an EVM token contract with different decimals, or correcting a misconfiguration) and are not gated by any check for outstanding in-flight requests, so this can occur without any malicious actor — a legitimate configuration update alone triggers the miscalculation for any request that happens to be pending at that moment.

### Recommendation
Bind the conversion precision to the specific request rather than re-reading current pallet storage in `on_timeout` (and ideally `on_accept`). Options:
- Include the `erc_decimals` (and/or local `decimals`) used at `send()` time inside the ISMP message body/calldata, and use those embedded values exclusively when decoding on `on_timeout`/`on_accept`.
- Alternatively, snapshot the precision per commitment (e.g., a `StorageMap<Commitment, (u8, u8)>`) at dispatch time and consult that snapshot on timeout instead of the live `Precisions` map, clearing the entry after the timeout/accept is processed.

### Proof of Concept
1. Register asset `X` with `Precisions::insert(X, DestChain, 6)` (erc_decimals = 6), local `decimals = 6`.
2. User calls `send()` with `amount = 100` (local balance), locking/burning 100 units; `erc20_amount = 100 * 10^(6-6) = 100`, encoded into `message.amount`, timeout set to `T`.
3. Before the request times out, governance calls `update_token` on asset `X` for `DestChain`, changing precision from 6 to 18 (e.g., destination token was redeployed with 18 decimals).
4. Request times out (destination unreachable/paused). `on_timeout` fires: it reads current `Precisions::get(X, DestChain) = 18`, and computes `convert_to_balance(100, 18, 6) = 100 / 10^(18-6) = 0` (rounds down to zero via integer division since `100 < 10^12`).
5. The user's originally escrowed/burned 100 tokens are refunded as `0`, resulting in a complete, permanent loss of the user's funds despite the cross-chain transfer never succeeding.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
