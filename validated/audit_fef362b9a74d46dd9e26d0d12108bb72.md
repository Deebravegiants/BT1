### Title
Webhook `shop-domain` header is trusted for tenant attribution without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then hands the value of the unauthenticated `shopify-shop-domain` (or `x-shopify-shop-domain`) header straight to the webhook handler as the tenant identifier. Because the signature never covers that header, any request whose HMAC is valid for its body can carry an arbitrary `shop` value, breaking the binding between "the shop the signature actually vouches for" and "the shop the handler believes it received data for."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#shop` is read directly from the (unauthenticated) header: [1](#0-0) 

`Registry.process` verifies the HMAC using `Utils::HmacValidator.validate(request)`, which internally calls `verifiable_query.to_signable_string` (i.e., the body only) and compares it against `verifiable_query.hmac`: [2](#0-1) 

After that check passes, `Registry.process` forwards `request.shop` — the raw header value that was never part of the signed bytes — into `WebhookMetadata`, which the host application uses to know which merchant the payload belongs to: [3](#0-2) 

The binding that should hold is: `shop_bound_by_hmac == shop_used_for_tenant_routing`. In practice the gem only proves `hmac(body) == received_hmac`; it proves nothing about `shop-domain`, so the equality can be false while `HmacValidator.validate` still returns `true`.

### Impact Explanation
Any actor who has legitimately received (or can obtain) a validly-signed webhook body/HMAC pair for a shop that has the app installed — e.g. by installing the app on their own store — can resend that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. The signature still validates because only the body is checked, but the host app's handler will process/store the payload under the attacker-chosen shop identifier. This is a cross-tenant integrity issue: a webhook carrying attacker-controlled content can be misattributed to a victim shop, potentially corrupting that shop's locally-stored state (e.g. install/redact flags, cached settings) keyed by `data.shop`.

### Likelihood Explanation
Exploitability requires only that the attacker (a) can install the app on a shop they control (an unprivileged, ordinary merchant action) to obtain one valid `(body, hmac)` pair, and (b) can send a raw HTTP request directly to the app's public webhook endpoint with a modified header — no `api_secret_key`, access token, or TLS interception is needed, since the header is never covered by the HMAC in the first place.

### Recommendation
Bind the tenant identity into the verified material: either include the `shop-domain` (and `topic`/`webhook_id`) header values in the HMAC-signable string, or require the host application to cross-check `request.shop` against a shop already known/authorized in its own session store before acting on the payload, and document this requirement prominently in `docs/usage/webhooks.md`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering a legitimate webhook whose body is fully attacker-controlled (e.g. product update) and receives a valid `X-Shopify-Hmac-Sha256` for that exact body.
2. Attacker sends a raw HTTP POST to the app's webhook endpoint reusing that same body and HMAC header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged header without complaint (headers are only checked for presence, not authenticity) — [4](#0-3) .
4. `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes the HMAC over `@raw_body`.
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: attacker_body, ...))`, causing the host app to process attacker-controlled data under the victim's tenant identity.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
