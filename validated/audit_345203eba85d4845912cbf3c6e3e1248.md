## Title
Withdraw Instruction Allows Optional/Bypassable Slippage Protection, Enabling Sandwich Attacks on Liquidity Removal - (File: `program/src/processor.rs`)

### Summary
The `process_withdraw` function's slippage check for LP removal is **only enforced when both `min_coin_amount` and `min_pc_amount` are `Some`**. Because these fields are optional (`Option<u64>`) in the instruction encoding, a withdraw transaction can be submitted with no minimum-out protection at all, exactly analogous to the CurveSpell `minOuts = 0` issue — the withdrawing LP receives whatever the manipulated pool state yields, with no on-chain floor enforced.

### Finding Description
The `WithdrawInstruction` struct defines `min_coin_amount` and `min_pc_amount` as optional fields: [1](#0-0) 

During unpacking, if the caller supplies only the 8-byte `amount` field (omitting the extra 16 bytes), both fields default to `None`: [2](#0-1) 

In `process_withdraw`, the computed `coin_amount`/`pc_amount` (derived from the current, potentially manipulated, pool reserves via `Calculator::calc_total_without_take_pnl_no_orderbook` and `InvariantPool::exchange_pool_to_token`) are only checked against `min_coin_amount`/`min_pc_amount` **inside a conditional that requires both to be `Some`**: [3](#0-2) 

If either value is `None` (which happens whenever the instruction data omits them, or a client/SDK builds the withdraw instruction without slippage parameters), the program proceeds directly to transferring `coin_amount`/`pc_amount` and burning LP tokens with **no floor check whatsoever**: [4](#0-3) 

This is the direct analog of the CurveSpell bug: liquidity removal proceeds using pool-derived exchange amounts with an effective `minOut = 0` (no enforced minimum), leaving the withdrawer fully exposed to price manipulation performed immediately before their transaction executes.

### Impact Explanation
An MEV bot observing a pending `Withdraw` instruction with no min-amount fields set can sandwich it: front-run with a large swap that skews the coin/pc vault balance ratio, let the victim's withdrawal execute at the manipulated ratio (extracting a maximal share of one asset and a minimal share of the other from the victim), then back-run to restore the pool and capture the difference. Because there's no on-chain enforcement forcing minimums to be set, the withdrawing LP can lose a significant portion of the expected value of their position — a direct loss of user/LP funds, matching the severity of the reported CurveSpell issue.

### Likelihood Explanation
Likelihood is high whenever a withdraw transaction is built without the optional slippage parameters — this occurs by construction for the 11-account "recommended" withdraw path/any caller/SDK version that constructs `WithdrawInstruction { amount, min_coin_amount: None, min_pc_amount: None }`, or any raw instruction data with only 9 bytes. All such transactions are visible in the mempool before confirmation and are exploitable by any observing searcher/MEV bot with a single front-run/back-run pair of swap transactions.

### Recommendation
Make `min_coin_amount` and `min_pc_amount` mandatory (non-optional) in `WithdrawInstruction`, and reject the instruction (or require the check unconditionally) at [3](#0-2)  rather than only checking when both are present, so that a withdrawal can never execute without an explicit, caller-specified minimum output guarantee.

### Proof of Concept
1. Build a `Withdraw` instruction with tag `4`, an `amount` (LP tokens to burn), and no additional bytes — `AmmInstruction::unpack` sets `min_coin_amount = None`, `min_pc_amount = None` per [2](#0-1) .
2. An attacker observes this transaction in the mempool and front-runs it with a large `SwapBaseIn`/`SwapBaseOut` that skews `amm_coin_vault`/`amm_pc_vault` balances.
3. The victim's withdraw executes: `coin_amount`/`pc_amount` are computed from the skewed reserves via `InvariantPool::exchange_pool_to_token` [5](#0-4) , and since `min_coin_amount`/`min_pc_amount` are `None`, the slippage-check branch is skipped and the transfer/burn proceeds unconditionally [6](#0-5) .
4. The attacker back-runs to restore the pool, having captured the value difference at the victim's expense.
