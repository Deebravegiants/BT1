### Title
Webhook `shop-domain` Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`), `topic`, `webhook_id`, and `api_version` used to route and process a webhook entirely from unauthenticated HTTP headers, while `Utils::HmacValidator` only verifies the raw request body against the app's shared `api_secret_key`. The identity binding the report's bug class targets — "a field acted on but not covered by the HMAC" — is broken here: `shop` is acted upon (used to attribute the webhook to a tenant) but is not part of the signed bytes.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes the HMAC exclusively over that signable string using the app-wide `Context.api_secret_key` (the same secret for every shop that installs the app) [2](#0-1) . Meanwhile, `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from HTTP headers with no cryptographic tie to the body or to each other [3](#0-2) .

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identity when building `WebhookMetadata` and dispatching to the handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) .

Because the HMAC secret is the app's single `api_secret_key`, not a per-shop secret, any legitimate webhook delivery captured from **any** shop that has the app installed carries a body+HMAC pair that is valid for **all** shops using that app. An unprivileged party who has access to their own shop's genuine webhook deliveries (e.g. an app developer's own test shop, or anyone who can observe a delivery to their own installed instance) can take that valid `(raw_body, hmac)` pair and resend it to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop. `HmacValidator.validate` still succeeds because it never inspected the header, so `Registry.process` attributes the payload to the victim's `shop` identity and invokes the handler as if Shopify had sent this event for the victim shop.

The equality being violated: `shop_bound_by_signature == shop_used_by_handler` is assumed by the design but not enforced — the signature binds only `raw_body`, while `handler.handle` acts on `request.shop`, a header untouched by the signature.

### Impact Explanation
This is a cross-tenant confusion vector: an attacker can cause the app to process a forged/replayed webhook under a shop identity of their choosing. Depending on the handler's logic (order sync, uninstall handling, GDPR data requests, subscription updates, etc.), this can trigger unauthorized actions attributed to another merchant, corrupt per-shop state, or be leveraged as a stepping stone toward further tenant-boundary violations — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one genuine `(raw_body, hmac)` pair — trivially available to anyone who installs the same app on their own shop and captures its own legitimate webhook traffic (no `api_secret_key`, access token, or privileged access needed). Replaying that pair to the public webhook endpoint with a swapped `shop-domain` header is a routine HTTP crafting exercise. Some webhook topics with attacker-influenced but shop-agnostic bodies (e.g. `app/uninstalled`, generic topic payloads) make this immediately practical; likelihood is Medium-High for apps that key any sensitive per-shop logic off `WebhookMetadata#shop` without independent verification against installed-session state.

### Recommendation
Bind the shop identity into the verified signature material, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the request that is validated:
- Include the `shop-domain` (and ideally `topic`, `webhook_id`) header values in `to_signable_string` so the HMAC covers them, if the gem controls both signing and verification; or
- Since Shopify signs only the body server-side (this can't be changed unilaterally), have `Registry.process` cross-check `request.shop` against the shop that the app has on record as currently installed/authorized for the given `webhook_id`/topic before invoking the handler, and reject mismatches.
- At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated header data and must not be trusted for authorization decisions without an independent installed-shop check.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and lets Shopify deliver a legitimate webhook (e.g. `orders/create`) to the app's webhook endpoint. Attacker captures the full raw body and the `X-Shopify-Hmac-Sha256` header value.
2. Attacker crafts a new HTTP POST to the same webhook endpoint, reusing the identical raw body and `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` is constructed from these headers; `HmacValidator.validate(request)` recomputes the HMAC over `raw_body` only [5](#0-4)  — it matches, because the secret is shared and the body is unmodified.
4. `Registry.process` proceeds and calls `handler.handle(data: WebhookMetadata.new(..., shop: "victim.myshopify.com", ...))` [6](#0-5)  — the app now processes attacker-controlled webhook content under the victim shop's identity.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
