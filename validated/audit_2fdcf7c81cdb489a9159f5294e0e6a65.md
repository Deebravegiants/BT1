### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw request body only, while the shop identity (`x-shopify-shop-domain` / `shopify-shop-domain` header) is read separately and handed to application webhook handlers as the trusted tenant identifier. Because the header is never part of the signed bytes, an attacker who possesses one valid `(raw_body, hmac)` pair can replay it with an arbitrary `shop-domain` header and the signature will still validate, letting them impersonate any merchant to the app's webhook handler.

### Finding Description
`Utils::HmacValidator.validate` recomputes an HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` value supplied by the caller: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw HTTP body — none of the Shopify-supplied headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) are included in the signed material: [2](#0-1) 

`Registry.process` validates the HMAC and, if it passes, immediately trusts `request.shop` (parsed straight from the unauthenticated header) as the tenant identity passed into the handler: [3](#0-2) 

This breaks the intended identity binding: `hmac == HMAC(secret, body)` should imply `shop == the shop that produced this event`, but the equality actually verified is only `hmac == HMAC(secret, body)`, with `shop` free-floating and attacker-controlled. Any unprivileged party who can produce or capture one valid `(body, hmac)` pair signed with the app's secret (e.g., from their own trial/dev store that legitimately receives real Shopify webhooks) can resend that exact body to the app's webhook endpoint with a forged `shop-domain` header naming a victim merchant. `Utils::HmacValidator.validate` will report success because it never looks at the header, and `Registry.process` will dispatch the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain: [4](#0-3) 

This is the direct analog of the report's root cause: a resource/identity is acted upon (`_transferOutAssets` moves assets for whichever caller wins the race, without checking the auction the caller intended) despite not being covered by the check that was supposed to bind it. Here, the tenant (`shop`) the handler acts on is not covered by the very HMAC check that is supposed to authenticate the whole message.

### Impact Explanation
Because host applications built on this gem key their business logic (data storage, background job dispatch, access-token lookups for follow-up Admin API calls, etc.) off `WebhookMetadata#shop`, an attacker can trigger the app to process/act on data under an arbitrary victim shop identity while only having to supply a body that satisfies whatever the handler expects for that topic. Depending on how the host app implements handlers, this enables cross-tenant data confusion or processing (e.g., forging "app/uninstalled" or "shop/redact" events for a victim shop, or injecting attacker-controlled body content that the app associates with the victim tenant). This falls under the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is moderate: the attacker needs one legitimate `(raw_body, hmac)` pair produced with the app's real `api_secret_key`. This is obtainable by any user who can install the app on their own store (even a free/dev store) and capture a real webhook delivery — a normal, unprivileged action, no leaked credentials or privileged account required. The forged replay itself requires only sending an HTTP POST to the public webhook endpoint with a modified header, which is under full attacker control since the header is not authenticated by this library.

### Recommendation
Include the identity-binding header(s) — at minimum `shop-domain` (and ideally `topic`, `webhook-id`) — in the signed material `to_signable_string` returns, or otherwise cryptographically bind the header values before trusting them, mirroring how OAuth's `AuthQuery#to_signable_string` includes `shop` in its signed params: [5](#0-4) 
Short term, `Registry.process` should reject requests where the `shop-domain` header cannot be independently corroborated (e.g., cross-checked against an expected/registered shop for that webhook subscription). Long term, adopt Shopify's documented webhook verification guidance which treats the shop header as untrusted metadata and requires apps to independently confirm the shop's legitimacy (e.g., via a known session/install record) before acting on it, and update this gem's built-in `Registry` dispatch and tests to make that distinction explicit to consumers.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets Shopify deliver a genuine webhook, e.g. an empty-body event: raw body `"{}"`, header `x-shopify-hmac-sha256: <realHMAC>` computed by Shopify with the app's real `api_secret_key`, and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the exact same raw body `"{}"` and the exact same `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. Inside the gem: `Utils::HmacValidator.validate(request)` recomputes `HMAC(secret, "{}")`, which still equals the captured `hmac`, since `to_signable_string` never looked at the shop header: [6](#0-5) 
4. `Registry.process` passes validation and invokes the registered handler with `WebhookMetadata#shop == "victim.myshopify.com"`, even though this request was never authorized by, or on behalf of, `victim.myshopify.com`: [7](#0-6)
