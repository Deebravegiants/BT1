### Title
Webhook shop/topic identity spoofing via HMAC that only covers the raw body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `webhook_id`, and `api_version` values used to route and process a webhook from unauthenticated HTTP headers, while its HMAC (`to_signable_string`) only covers the raw request body. This breaks the identity binding the report's bug-class targets: "a field acted on but not covered by the HMAC."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But the class also exposes `shop`, `topic`, `webhook_id`, and `api_version`, all sourced directly from HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `to_signable_string` (the raw body) and the app's `client_secret`: [3](#0-2) 

`Webhooks::Registry.process` accepts the request once this body-only HMAC checks out, then forwards the header-derived, unauthenticated `shop` value straight to the app's handler: [4](#0-3) 

For comparison, the OAuth callback's `AuthQuery` includes `shop` in the HMAC-signed content itself, so the shop value cannot be swapped post-signature: [5](#0-4) 

The webhook path has no equivalent binding. Since `shop`/`topic`/`webhook_id` never enter `to_signable_string`, they can be freely modified on any request whose body+HMAC pair is otherwise valid.

### Impact Explanation
Any user who can install the app on their own shop is able to trigger legitimate webhook deliveries and observe genuine `(raw_body, hmac)` pairs computed with the app's `client_secret`. Because the HMAC is computed solely from the body, that same `(body, hmac)` pair remains valid for any `shop-domain`/`topic`/`webhook-id` header combination. The attacker can POST directly to the app's public webhook endpoint (bypassing Shopify) with the observed valid body+HMAC but an arbitrary `x-shopify-shop-domain` header pointing at a victim shop. `HmacValidator.validate` succeeds and `Registry.process` forwards `shop: <victim>` to the app's `WebhookHandler`, causing the app to process attacker-supplied webhook data as if it originated from the victim tenant — a cross-tenant data/identity confusion inside the host application's webhook handling, driven entirely by this gem's incomplete HMAC scope.

### Likelihood Explanation
Requires only unprivileged access: the ability to install the app on one's own store (to obtain a valid body/HMAC sample) and the ability to send arbitrary HTTP requests to the app's public webhook endpoint. No merchant/staff/API credentials, TLS interception, or social engineering are needed.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or otherwise pin them to the signed content, e.g. by validating the shop domain against a known, previously-verified shop associated with the delivery) in the value used for HMAC verification, or independently verify the `shop-domain`/`topic` headers against Shopify-issued, signed data before trusting them in `Webhooks::Registry.process`.

### Proof of Concept
1. Install the app on attacker-owned shop `attacker.myshopify.com`; capture a real webhook delivery, e.g. `orders/create` with raw body `B` and valid header `x-shopify-hmac-sha256: H` (computed as `HMAC-SHA256(client_secret, B)`).
2. Send a forged POST directly to the app's webhook endpoint with:
   - body: `B` (unchanged)
   - `x-shopify-hmac-sha256: H` (unchanged, still valid since only body is signed)
   - `x-shopify-shop-domain: victim.myshopify.com` (swapped)
   - `x-shopify-topic: orders/create` (or any registered topic)
3. `Utils::HmacValidator.validate` returns `true` because `to_signable_string` only checks `B` against `H`. [1](#0-0) 
4. `Registry.process` invokes the app's handler with `shop: "victim.myshopify.com"`, causing the host application to treat attacker-supplied data as belonging to the victim tenant. [4](#0-3)
