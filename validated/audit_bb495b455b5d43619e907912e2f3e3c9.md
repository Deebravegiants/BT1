Based on my investigation, I found a concrete, unpatched authorization gap in the legacy gateway user-message path that fits the "allowlist/subscriptions bypass" analog category from the Kronos-incident bug class (unauthorized access via missing access control on an externally-reachable path).

### Title
Missing allowlist/rate-limit enforcement on legacy WebAPI trigger user messages allows unauthenticated workflow triggering - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage`, the entry point for external client requests routed to the WebAPI capabilities gateway handler, explicitly skips allowlist and rate-limiting checks before fanning the request out to every DON node, as marked by an unresolved `TODO` comment in the code itself.

### Finding Description
The gateway's `handler.HandleLegacyUserMessage` processes messages arriving from unprivileged external clients (`MethodWebAPITrigger`). It validates payload shape, staleness, and method name, but between those checks and forwarding the request to all DON members it contains only a comment acknowledging that authorization is missing: [1](#0-0) 
Immediately after, the handler unconditionally sends the raw user request to every node in the DON with no allowlist, subscription, or per-sender rate-limit check applied: [2](#0-1) 
Compare this to the same handler's `HandleNodeMessage` path (node-to-gateway direction) and to the newer v2 gateway handler (`core/services/gateway/handlers/capabilities/v2/http_handler.go`), both of which enforce `nodeRateLimiter`/`perNodeRateLimiters` checks before processing: [3](#0-2) . No equivalent protection exists for user-originated (client-to-gateway) legacy trigger messages.

### Impact Explanation
Any unprivileged client capable of reaching the gateway's legacy JSON-RPC/message endpoint can submit `web_api_trigger` messages that get broadcast to every node in the DON without being checked against a workflow/sender allowlist or throttled per sender. This directly matches the "allowlist or quota bypass" and "unauthorized job run" categories: an attacker can trigger workflow executions on nodes they are not authorized to invoke, and can flood the DON (since only a global age/staleness check exists, not a per-sender limiter) by re-sending trigger messages, unlike the node-facing and v2 paths which do enforce such limits.

### Likelihood Explanation
The gap is explicit and acknowledged in the code (the `TODO` comment), meaning it is not a subtle edge case but a known-incomplete authorization path still reachable in production via `HandleLegacyUserMessage`, which is part of the public `handlers.Handler` interface invoked directly from gateway user message dispatch. Any client that can send a well-formed `web_api_trigger` message (only requiring a valid timestamp and method name) can exploit this without special privileges.

### Recommendation
Implement the intended allowlist check (validating the sender/workflow against the DON's configured allowlist before dispatch) and add a per-sender rate limiter to `HandleLegacyUserMessage`, mirroring the protections already present in `HandleNodeMessage` and in the v2 gateway handler's `perNodeRateLimiters`/`globalNodeRateLimiter`. Reject unauthorized or over-limit requests with an appropriate JSON-RPC error before calling `don.SendToNode`.

### Proof of Concept
1. Craft a `api.Message` with `Body.Method = "web_api_trigger"`, a valid non-zero `Timestamp`, and a `TriggerRequestPayload` payload, without any prior workflow registration/allowlisting.
2. Send it to the gateway's legacy user-message endpoint so it is routed to `handler.HandleLegacyUserMessage`.
3. Observe that the message passes the staleness/method checks (lines 359–396) and is forwarded via `don.SendToNode` to every DON member (lines 417–419) with no allowlist or per-sender rate check ever performed, unlike the node-to-gateway or v2 handler paths.

**Note on scope/uncertainty:** I was not able to fully trace whether an external gateway-facing HTTP/WS listener actually routes untrusted client traffic into `HandleLegacyUserMessage` in the currently deployed configuration (vs. this being fully superseded/dead code in favor of the v2 handler), because the connector/listener wiring for this specific legacy path was not fully covered by the indexed search results. If this legacy path has been fully decommissioned in favor of `v2/http_handler.go`, this finding would be moot; a Devin session with full repo access should confirm current routing/registration of this handler in `gateway.go`/`multihandler.go` before treating this as exploitable in production.

func (h *gatewayHandler) HandleNodeMessage(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	if resp.ID == "" {
		return fmt.Errorf("received response with empty request ID from node %s", nodeAddr)
	}
	h.lggr.Debugw("handling incoming node message", "requestID", resp.ID, "nodeAddr", nodeAddr)
	nodeRateLimiter, ok := h.perNodeRateLimiters[nodeAddr]
	if !ok {
		return fmt.Errorf("received message from unexpected node %s", nodeAddr)
	}
	if !nodeRateLimiter.Allow(ctx) {
		h.metrics.IncrementCapabilityNodeThrottled(ctx, nodeAddr, h.lggr)
		return fmt.Errorf("rate limit exceeded for node %s", nodeAddr)
	}
	if !h.globalNodeRateLimiter.Allow(ctx) {
		h.metrics.IncrementGlobalThrottled(ctx, h.lggr)
		return errors.New("global rate limit exceeded")
	}
