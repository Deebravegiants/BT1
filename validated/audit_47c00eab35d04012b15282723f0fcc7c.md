### Title
Webhook `shop-domain` header is trusted for tenant identification without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that is read directly from the unauthenticated `X-Shopify-Shop-Domain` HTTP header, while `Utils::HmacValidator.validate` only verifies the raw request body against the app's `client_secret`. The header used to identify *which tenant* the webhook belongs to is never part of the signed material, so a value that is "acted on" (tenant identity) is disjoint from the value that is "verified" (body bytes only) — the same class of binding failure described in the external report, where a pool's specific record was conflated with an unscoped aggregate value.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, and `webhook_id` are all read straight from headers that are never mixed into that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively from `verifiable_query.to_signable_string` (i.e., the raw body for webhooks) and compares it against the `hmac-sha256` header: [3](#0-2) 

`Registry.process` only checks this body-only HMAC before dispatching the handler with the header-derived `shop`: [4](#0-3) 

The equality the code implicitly assumes is:
`shop (bytes verified by HMAC) == shop (header value acted upon by the handler)`

In reality, HMAC-verified-bytes = `raw_body` only, while acted-upon-shop = `headers["shopify-shop-domain"]`. These are two independent channels: the signature proves the *body* originated from Shopify using the correct secret, but proves nothing about which shop the accompanying headers describe. Because every webhook destined for an app is signed with the same single `client_secret` regardless of which installed shop triggered it, a valid `(raw_body, hmac)` pair obtained from a webhook delivered for shop A remains a valid pair no matter what `shop-domain` header value is later attached.

### Impact Explanation
An unprivileged internet user who is themselves the owner/administrator of any shop that has installed the target app can:
1. Install the app on their own shop and trigger any subscribed webhook topic to legitimately receive `(raw_body, hmac)` from Shopify.
2. Replay that exact `raw_body`/`hmac-sha256` pair to the app's webhook endpoint, but substitute the `X-Shopify-Shop-Domain` header with a different (victim) shop's domain.
3. `Utils::HmacValidator.validate` still succeeds because it only checks `raw_body` against the secret, and `Registry.process` dispatches to the handler with `WebhookMetadata` whose `shop` field is the attacker-controlled victim domain, alongside attacker-controlled `parsed_body` content.

Any host application that trusts `data.shop` from the passed `WebhookMetadata` to scope per-tenant state changes (a documented and expected usage pattern for webhook processing) can be made to write, delete, or process attacker-supplied data under another merchant's tenant identity — a cross-tenant data-integrity breach that satisfies the "cross-tenant access" Critical-impact criterion.

### Likelihood Explanation
Exploitation requires only that the attacker run their own installation of the target app (a normal, unprivileged action any merchant/developer can take) — no access to `api_secret_key`, access tokens, or the app's infrastructure is needed. The endpoint is public by design (Shopify posts webhooks to it), and no additional binding between `raw_body` and `shop-domain` exists anywhere in the verification path.

### Recommendation
Include the shop identity in the HMAC-signed material, or independently verify that the `shop-domain` header corresponds to a shop with an active, previously-established session/installation before dispatching to the handler, e.g., cross-check `request.shop` against a store's known session record rather than trusting the header at face value once the body-only HMAC succeeds.

### Proof of Concept
```ruby
# Attacker installs the target app on their own shop "attacker.myshopify.com"
# and receives a legitimate webhook for topic "orders/create":
raw_body = '{"id":1,"note":"hello"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_client_secret, raw_body)
# (attacker does not know app_client_secret, but Shopify computed and delivered this pair to them)

# Attacker replays the same body+hmac but swaps the shop-domain header:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not the attacker's real shop
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) => true, because it only hashes raw_body
# handler.handle receives WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed attacker body, ...)
``` [5](#0-4)
