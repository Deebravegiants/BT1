### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authorizes and dispatches an incoming webhook by validating an HMAC over the raw body only, then separately trusts the `shop` (and `topic`, `webhook_id`, `api_version`) values taken straight from HTTP headers that are never included in the signed bytes. Because the tenant-identifying field (`shop`) is "acted on but not covered by the HMAC," a caller who has captured any single valid `(raw_body, hmac)` pair for one shop can replay the same body/HMAC while substituting an arbitrary `x-shopify-shop-domain` header, and the handler will process the webhook as belonging to a different tenant than the one that actually produced/authorized it.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read directly out of unauthenticated HTTP headers with no cryptographic binding to the signature: [2](#0-1) .

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the raw body) against the HMAC secret; it has no knowledge of, and does not verify, the `shop` header at all: [3](#0-2) .

`Registry.process` then validates the HMAC and, on success, unconditionally forwards `request.shop` (the header value) to the app's handler as the tenant identity, with no cross-check that the signed body actually originated for that shop: [4](#0-3) .

This breaks the equality that should hold: `shop authenticated by HMAC == shop acted upon by handler`. In reality: `shop covered by signature == {}` (empty set) while `shop acted upon by handler == header value, attacker-controlled`.

### Impact Explanation
This falls under "cross-tenant access": an attacker who obtains one legitimate `(raw_body, hmac)` pair for any shop (e.g. their own store, or a shared/public webhook payload with no shop-specific secret material in the body) can submit it to the app's webhook endpoint with a forged `x-shopify-shop-domain`/`shopify-shop-domain` header pointing at a victim shop. `HmacValidator.validate` still returns `true` because it never inspects the header, and `Registry.process` calls the handler with `WebhookMetadata.new(..., shop: request.shop, ...)` set to the attacker-chosen shop. Any app logic keyed off `data.shop` (e.g. looking up the victim's stored access token/session, updating per-tenant state, or triggering mandatory-compliance flows like `shop/redact`/`customers/redact`) is then executed under the wrong tenant identity, which can enable cross-tenant data manipulation depending on how the host app uses `WebhookMetadata#shop`.

### Likelihood Explanation
Likelihood is high once any single valid webhook body+HMAC pair is observable by the attacker (e.g. from their own installed shop's webhook traffic, which they legitimately receive, or leaked via app logs). No access to `api_secret_key`, access tokens, or the merchant's credentials is required — only the ability to replay an HTTP POST with a different header value, which is unprivileged and network-reachable if the app's webhook endpoint is exposed.

### Recommendation
Include the shop domain (and topic) in the HMAC-signed material, or independently verify that `request.shop` matches the shop the webhook subscription was registered for/expected, before dispatching to the handler. At minimum, `Registry.process` should treat `request.shop` as untrusted unless it is bound into `to_signable_string` or cross-validated against a known-good mapping (e.g. registered webhook endpoint's expected shop).

### Proof of Concept
1. App has a webhook handler registered for topic `orders/create` via `Registry.add_registration`.
2. Attacker's own installed shop (`attacker-shop.myshopify.com`) receives a legitimate webhook: raw body `B` and header `shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `api_secret_key`), along with header `shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker POSTs the same `B`/`H` to the app's webhook endpoint but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` recomputes HMAC over `B` only — [1](#0-0)  — and it matches `H`, so validation passes.
5. `Registry.process` dispatches `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...))` — [5](#0-4)  — causing the app to process attacker-supplied data under the victim shop's identity.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
