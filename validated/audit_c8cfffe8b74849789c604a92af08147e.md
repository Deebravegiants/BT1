## Title
Standing ERC-20 approvals granted through `CallDispatcher` calldata cannot be revoked and permanently expose future order/bridge funds to a compromised router - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a single, shared, stateless contract used by every `IntentGatewayV2` order (predispatch and postdispatch calldata) and every `HyperFungibleToken`/`WrappedHyperFungibleToken` cross-chain message (calldata execution on `onAccept`). Any unprivileged user who places an order or sends a bridged transfer can embed an `IERC20.approve(router, type(uint256).max)` call in their `Call[]` payload. That approval is granted from `CallDispatcher`'s own address and is never revoked or reset by the protocol. Because `CallDispatcher` is reused by every subsequent, unrelated order or bridge message that happens to route the same token through it, any balance it holds in the future - even briefly, mid-transaction, before the dust-sweep - remains permanently exposed to that router. If the router is later compromised (the exact "Sushi router" scenario cited in the source report), the attacker can drain whatever tokens `CallDispatcher` is holding at that moment via `transferFrom`, with no way for the protocol to revoke the stale allowance.

### Finding Description
`CallDispatcher.dispatch` executes arbitrary attacker/user-supplied calls with no access control and no cleanup of side effects such as approvals: [1](#0-0) 

It is invoked from three permissionless, unprivileged entry points:
- `IntentsBase._execute`, run after every order's postdispatch fill, on the beneficiary/output tokens sent to `dispatcher`: [2](#0-1) 
- Predispatch calldata execution at order placement, where input/escrow assets are transferred to `dispatcher` first, the `Call[]` runs, and only afterward are balances swept back: [3](#0-2) 
- `HyperFungibleToken.onAccept`/`onAcceptWithCalldata`, where tokens are minted to the dispatcher and then `message.data` (an attacker-supplied `Call[]`) is executed: [4](#0-3) 

The project's own documentation confirms this exact class of `approve(router, max)` pattern is expected usage (see the sample code approving `UNISWAP_V2_ROUTER` for `type(uint256).max` and the test `testPostdispatchTokenSweep` doing the same), and separately warns that unlimited allowances are risky precisely because "the dispatcher contract holds tokens temporarily during execution": [5](#0-4) [6](#0-5) 

However, this warning is documentation-only guidance to integrators - nothing in `CallDispatcher`, `IntentsBase`, `IntentGatewayV2`, or `HyperFungibleToken` prevents, resets, or revokes an approval once it has been granted. `dispatch()` is a global singleton reused by all subsequent orders and all subsequent bridge messages that route the same token, so an approval created inside one user's `Call[]` batch outlives that batch and applies to every future balance the dispatcher will ever hold of that token — exactly the "cannot be revoked/lowered" defect from the source report, but here amplified because the approving actor (dispatcher) is shared infrastructure rather than a single user's own contract.

### Impact Explanation
If any router or DeFi contract that was ever approved via a `Call[]` (predispatch, postdispatch, or HFT calldata) is later compromised or upgraded maliciously, it can call `token.transferFrom(dispatcher, attacker, balance)` at any point the dispatcher is holding that token — including funds belonging to entirely unrelated users' orders or bridge transfers placed after the approval was granted (predispatch escrow assets in flight, postdispatch solver payouts awaiting the dust sweep, or HFT-minted tokens awaiting calldata execution). This is a direct path to theft of user/protocol funds with no on-chain mitigation, satisfying "concrete theft ... of funds" from a permissionless action (placing an order or sending a bridged message).

### Likelihood Explanation
Reaching this requires only a single unprivileged `placeOrder` call (predispatch/postdispatch calldata) or a single `HyperFungibleToken.send` with non-empty `data` — both fully permissionless, user-controlled operations, matching the documented and tested usage pattern (max-approve-then-swap) shown in the repo's own tests and docs. The only external dependency is that some previously-approved router is later compromised — the same precondition the original report treats as realistic (citing the Sushi RouteProcessor2 incident) — after which exploitation is a single `transferFrom` call requiring no special privilege.

### Recommendation
- Never grant standing/unlimited approvals from `CallDispatcher`; require exact-amount approvals scoped to the immediate call sequence.
- Add a mechanism (e.g., a trailing `approve(spender, 0)` call enforced by the protocol, or a dedicated `revokeApproval`/sweep-and-reset step) so any approval created inside a `dispatch()` batch cannot outlive that batch.
- Consider making `CallDispatcher` instances ephemeral (e.g., deployed per-call via `CREATE2`/minimal proxy and self-destructing or never reused) so no approval can persist to expose unrelated future balances.

### Proof of Concept
1. User A places an order (or sends an HFT transfer) whose postdispatch `Call[]` includes `token.approve(routerR, type(uint256).max)` followed by a legitimate swap through `routerR`, exactly as shown in `testPostdispatchTokenSweep` (`evm/tests/foundry/IntentGatewayV2Test.sol:1358-1363`). The approval `token.allowance(dispatcher, routerR) == type(uint256).max` persists after the order completes.
2. `routerR` is later compromised (upgraded/hacked, per the report's cited real-world incident).
3. User B places an unrelated order using the same `token` as an output/input asset, or sends an HFT transfer of `token`, causing `CallDispatcher` to briefly hold a balance of `token` again (per `IntentsBase._execute` / predispatch flow / `HyperFungibleToken.onAccept`).
4. Compromised `routerR`, invoked as part of User B's normal call sequence, instead calls `token.transferFrom(dispatcher, attacker, token.balanceOf(dispatcher))`, using the still-valid max allowance from step 1 to steal User B's funds before the protocol's dust sweep can recover them.

            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
