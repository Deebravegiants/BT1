### Title
Signup-extension mode lets an unprivileged user (via their own QR-code data) force the entire biometric pipeline and fraud-detection stage to be skipped while the signup is still reported as successful - (File: `src/plans/mod.rs`)

### Summary
The Aragon `DAO.execute` bug is a "controlled-resource-exhaustion" pattern: the caller supplies a resource budget (gas) that lets them force a sub-operation to fail while the parent operation still completes and is reported as successful, bypassing the intended all-or-nothing semantics. The closest reachable analog in `orb-core` is the `signup_extension_config` branch in the master signup flow: if a signup-extension mode is active, the code short-circuits and marks the whole signup as `success = true` *without ever running the biometric pipeline or the fraud-detection stage*, exactly mirroring the "sub-check is force-failed/skipped but the outer call still reports success" pattern.

If `debug_report.signup_extension_config` is populated, the entire biometric pipeline (`biometric_pipeline`, which runs iris matching, occlusion detection, and face-identifier fraud checks — see [2](#0-1)  and [3](#0-2) ) and the `detect_fraud` stage are never executed, and the signup is unconditionally marked `success = true`.

`signup_extension_config` is derived from `qr_scan::user::SignupExtensionConfig`, which is attached when the scanned user QR code specifies a signup mode (e.g. `PupilContractionExtension`, `FocusSweepExtension`, `MirrorSweepExtension`, `MultiWavelength`, `Overcapture`) — referenced throughout `src/plans/biometric_capture/mod.rs` (lines 1184-1210) and `src/plans/qr_scan/user.rs`. These extension modes exist to support special data-collection captures used for research/calibration, but the flag is read directly off data associated with the *user*'s own QR code/session, i.e., attacker-controlled input in the same trust position as the malicious voter in the DAO report who supplies the gas parameter that determines whether the "inner" step (the call / here, the fraud-checking pipeline) executes or is skipped, while the "outer" step (the transaction / here, the signup result) still finishes and reports success.

I was not able to fully verify from the indexed content how strictly gated `signup_extension_config` is (e.g., whether it requires operator authorization, a specific backend feature flag, or is bound to non-production builds only) because `src/plans/qr_scan/user.rs` could not be retrieved in this session due to a tool error in the final iteration. This is the key uncertainty for confirming unprivileged reachability.

### Impact Explanation
If `signup_extension_config` can be set through data that a regular (non-operator) user or a modified client controls, this allows a caller to force the fraud-detection/iris-matching pipeline to be skipped entirely while the signup still completes and is marked successful — a direct analog to forcing an inner check to "fail" (never execute) while the outer call finishes successfully. In identity-verification context this could mean unauthorized/misattributed signup completion without the iris/face fraud checks ever running, i.e., a fraud/liveness bypass. This is a high-impact class if reachable without operator privilege.

### Likelihood Explanation
Feasibility hinges entirely on the un-verified gating of `SignupExtensionConfig`. If it is populated solely from operator-approved QR flows or gated behind non-production feature flags, this is not exploitable by an unprivileged user and the analog does not hold. If it can be triggered from ordinary user-side QR/session data without operator authorization, the likelihood is high since it requires no special access — only crafting/selecting a specific QR code payload. Given the missing file content, this finding should be treated as tentative pending confirmation of `src/plans/qr_scan/user.rs`'s authorization logic for `SignupExtensionConfig`.

### Recommendation
- Confirm and, if necessary, enforce that `SignupExtensionConfig` (and by extension, skipping the biometric pipeline/fraud checks) can only be set through operator-authenticated flows or non-production builds, never from unauthenticated user-supplied QR/session data.
- Regardless of who sets it, never allow any code path to mark a signup as `success = true` without having executed the fraud-detection and biometric-pipeline checks (mirroring the DAO fix's principle: don't let attacker-controlled parameters silently bypass a mandatory validation step). At minimum, gate the "extension" short-circuit behind an explicit judgement that fraud/iris verification is not applicable (e.g., a dedicated non-enrolling "capture-only" result type), rather than the generic `success` field used for real enrollments.
