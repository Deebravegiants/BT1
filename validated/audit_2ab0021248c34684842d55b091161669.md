### Title
Division-by-zero panic in `Calculator::calc_x_power` via decimal-normalization underflow permanently freezes LP funds - (File: `program/src/math.rs`, `program/src/processor.rs`)

### Summary
CVE-2021-2020 is a MySQL optimizer bug where an unprivileged, network-reachable attacker can force the server into an unrecoverable hang/crash (complete DoS) using ordinary query input. The analogous bug class here is a reachable division-by-zero/`unwrap()` panic triggered by attacker-controlled, in-scope instructions (`SwapBaseIn`/`SwapBaseIn V2`) that drives pool reserves down to a level where a later, unrelated user's `Deposit`/`Withdraw`/`WithdrawPnl` call panics every time it is invoked, permanently freezing the pool.

### Finding Description
`Calculator::calc_x_power` computes the PNL invariant power term and divides by `current_y` with no zero-check: [1](#0-0) 

`current_y`/`current_x` are always `y1`/`x1`, which are the pool reserves *after* being decimal-normalized via `normalize_decimal_v2`, using integer division that floors toward zero: [2](#0-1) 

If a token's `native_decimal` exceeds `log10(sys_decimal_value)` (e.g. a 9-decimal SPL token normalized against the commonly used `sys_decimal_value = 10^6`), any raw reserve amount smaller than `10^(native_decimal - log10(sys_decimal_value))` normalizes to exactly `0`.

`calc_take_pnl` feeds these normalized `x1`/`y1` values straight into `calc_x_power`: [3](#0-2) 

and `calc_take_pnl` is invoked unconditionally (unless status is `WithdrawOnly`) from `process_deposit`, `process_withdraw`, and `process_withdrawpnl` — all instructions reachable by any unprivileged swapper/LP: [4](#0-3) [5](#0-4) [6](#0-5) 

`process_swap_base_in`/`process_swap_base_in_v2` only require the output amount to be *strictly less than* the total reserve, allowing the reserve to be driven down to `1` native unit (or any arbitrarily small positive amount) in a single attacker-controlled transaction with repeated/chained swap calls: [7](#0-6) 

Once the coin (or pc) reserve is small enough that `normalize_decimal_v2` floors it to `0`, the *next* call into `calc_take_pnl` (from any user's `Deposit`, `Withdraw`, or `WithdrawPnl`) computes `current_y = 0` (or `current_x = 0`) and panics on `checked_div(current_y).unwrap()`. Because `process_deposit` and `process_withdraw` compute `x1`/`y1` from the *current* vault balance *before* applying the incoming/outgoing amounts, the same panic reoccurs on every subsequent attempt — there is no way to top up the pool to escape the zero-normalization state, since the very deposit that would fix the imbalance panics before it can be applied.

### Impact Explanation
Once triggered, every `Deposit`, `Withdraw`, and `WithdrawPnl` transaction against the pool panics and reverts, permanently locking all LP funds in the pool (LPs can never redeem their `lp_amount` tokens) and blocking new liquidity additions. This matches the accepted impact class of "permanent freezing of user or LP funds" and is a direct on-chain analog of the CVE's "hang or crash" characteristic — the pool becomes permanently unusable for its core LP operations from a single attacker-crafted transaction sequence.

### Likelihood Explanation
Any unprivileged user can call `SwapBaseIn`/`SwapBaseInV2` with attacker-chosen `amount_in`/`minimum_amount_out` against attacker-selected AMM/vault accounts, and the only guard is a strict-inequality check (`>=`), which permits draining a reserve down to `1` native unit. Pools whose coin or pc mint has decimals higher than `log10(sys_decimal_value)` (very common, since many SPL tokens use 9 decimals) are directly exposed. No privileged signer, leaked key, or off-chain component is required — the whole exploit fits in a single submitted transaction with attacker-chosen accounts and data.

### Recommendation
- In `Calculator::calc_x_power` (and any other division in `math.rs`), replace `.unwrap()` on `checked_div` with a proper error return (e.g., `AmmError::CalcPnlError`) when the divisor is zero.
- In `calc_take_pnl`, explicitly reject (return an error, not panic) when `x1 == 0` or `y1 == 0` before calling `calc_x_power`.
- Consider normalizing decimals with rounding/ceiling instead of floor truncation for reserve values used in invariant math, or enforce a minimum reserve floor in swap instructions (not just strict `<`) so reserves can never be driven low enough to underflow-to-zero after normalization.

### Proof of Concept
1. Attacker identifies (or creates) a pool where `coin_decimals` (or `pc_decimals`) is large relative to `sys_decimal_value` (e.g., `coin_decimals = 9`, `sys_decimal_value = 10^6`).
2. Attacker submits repeated `SwapBaseIn` (PC2Coin direction) calls in one transaction, each satisfying `swap_amount_out < total_coin_without_take_pnl` per [8](#0-7) , driving `total_coin_without_take_pnl` down to `1` (or any value `< 10^(coin_decimals - log10(sys_decimal_value))`).
3. Any subsequent `Deposit`/`Withdraw`/`WithdrawPnl` call recomputes `y1 = normalize_decimal_v2(1, 9, 10^6) = 0` per [2](#0-1) .
4. `calc_take_pnl` passes `y1 = 0` into `Calculator::calc_x_power`, which panics at `.checked_div(current_y).unwrap()` per [1](#0-0) , causing every future `Deposit`/`Withdraw`/`WithdrawPnl` transaction on this pool to abort, permanently freezing LP funds.

    pub fn calc_x_power(last_x: U256, last_y: U256, current_x: U256, current_y: U256) -> U256 {
        // must be use u256, because u128 may be overflow
        let x_power = last_x
            .checked_mul(last_y)
            .unwrap()
            .checked_mul(current_x)
            .unwrap()
            .checked_div(current_y)
            .unwrap();
        x_power
    }
