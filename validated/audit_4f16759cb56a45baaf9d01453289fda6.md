### Title
Arbitrary unprivileged theft of any non-ERC20/untracked asset left owned by `EmporiumUpgradeable` via CASE-2 stateless ops - (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` executes CASE-2 (`op.invokeWallet=false`) operations as `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract itself, so `msg.sender` observed by any external contract is always `address(EmporiumUpgradeable)`, regardless of which end user's `transact` triggered it. Because `runAction`'s post-processing only reconciles and sweeps ERC20 balances listed in `circomData.erc20TokenAddresses` [1](#0-0) , any non-ERC20 asset (e.g. a Uniswap V3 LP NFT) minted to Emporium during a victim's CASE-2 op is left permanently custodied by the shared Emporium contract, unprotected and untracked as a Hinkal UTXO.

### Finding Description
Broken equality: `positionOwner_after_any_subsequent_transact` should remain equal to `address(Emporium)` until claimed by the rightful stealth-address owner via a Hinkal-verified proof; instead it becomes `attacker` with zero relation to the victim's nullifiers/stealth key.

Path: attacker calls `Hinkal.transact` → `_externalTransact` → `IExternalActionV2(externalActionData.externalAddress).runAction(...)` with `externalActionData.externalActionId` pointing to `EmporiumUpgradeable` [2](#0-1) . Inside `EmporiumUpgradeable.runAction`, the only gate is `onlyAllowedRecipient`, which merely checks that `msg.sender == Hinkal.sol` — it does not restrict `op.endpoint` or `op.callData` in any way [3](#0-2) . The `EmporiumStack` (including all `ops`) is decoded from attacker-controlled `circomData.externalActionData.externalActionMetadata` [4](#0-3) . In CASE 2, the only blocked selectors are `callHinkalWallet`/`doSendToRelay`; any other endpoint/calldata is freely executed via low-level call from Emporium [5](#0-4) .

Exploit flow:
1. Victim's `transact` runs a CASE-2 op calling Uniswap V3 `NonfungiblePositionManager.mint(...)`; because Emporium itself makes the low-level call, the minted NFT's owner is `address(EmporiumUpgradeable)`, not the victim's stealth address.
2. `runAction`'s balance reconciliation loop only iterates `circomData.erc20TokenAddresses` to build `utxoSet` [6](#0-5) ; an ERC721 token is never included there, so the NFT is never swept to the victim and never represented as a Hinkal UTXO — it is simply stranded on Emporium.
3. Attacker, in a completely unrelated `transact`, submits a CASE-2 op with `op.endpoint = positionManager`, `op.callData = abi.encodeWithSelector(safeTransferFrom.selector, address(emporium), attacker, tokenId)`. Because Emporium is again the direct caller (`msg.sender == owner == address(emporium)`), OpenZeppelin/Uniswap's `_isApprovedOrOwner` check trivially passes (owner calling directly needs no approval) — no `setApprovalForAll` trick is even required, contrary to the question's assumption.
4. The NFT moves to the attacker with no nullifier, proof, or stealth-address check tying the transfer to the victim.

No existing guard (`performHinkalChecks`, `verifyWallet`, `payRelayFees`, the ERC20 balance-diff `require`) constrains non-ERC20 assets or restricts which addresses CASE-2 ops may target, because Emporium is architected as a single shared multi-tenant proxy whose identity (`msg.sender`) is indistinguishable between different users' transactions.

### Impact Explanation
Direct theft of a victim's in-flight/stranded, non-ERC20 asset (LP position NFT or any other token type not enumerated in `erc20TokenAddresses`) that Hinkal never tracked as a UTXO, executed by any unprivileged attacker with no interaction with the victim's proof, nullifiers, or stealth keys. This matches the Critical category: "direct theft of shielded or in-flight user funds." It is repeatable for any asset left on Emporium by any prior op (mints, airdrops, refunds, dust, approvals-then-transfers, etc.), and costs the attacker only gas plus crafting one `transact` call.

### Likelihood Explanation
Preconditions: any user (victim or the protocol itself) must have executed a CASE-2 op through `EmporiumUpgradeable` that results in an asset not covered by the ERC20 balance-sweep loop being owned/held by Emporium (e.g., minting an NFT position, or ERC20 dust plus non-standard tokens not declared in `erc20TokenAddresses`). This is a normal usage pattern the CASE-2 "stateless interaction" design explicitly permits since arbitrary `endpoint`/`callData` are attacker-supplied per-call. No privileged role, no signature from the victim, no timing race is required — the attacker only needs to observe (on-chain, publicly) that Emporium now owns an NFT and then submit their own `transact`. Feasibility is high and the attack is fully repeatable against every future occurrence.

### Recommendation
Do not allow CASE-2 ops to leave assets custodied at `address(EmporiumUpgradeable)` across transactions: either (a) require every minted/received non-fungible or arbitrary asset to be atomically forwarded to `msg.sender`/the calling user's designated recipient within the same `runAction` call (mirroring the ERC20 sweep logic but generalized to ERC721/1155 and arbitrary tokens), (b) restrict CASE-2 `op.endpoint` calls to a strict allow-list of pre-audited, stateless functions that cannot leave assets owned by Emporium, or (c) make Emporium spin up a per-transaction/per-user ephemeral proxy (as CASE-1's `HinkalWallet` pattern already does via `signerAddress`) so no shared custodial state persists between unrelated users' calls.

### Proof of Concept
Foundry fork test:
1. Deploy real Uniswap V3 `NonfungiblePositionManager` and pool on a mainnet fork; deploy `EmporiumUpgradeable` with `Hinkal` as allowed recipient.
2. Victim calls `Hinkal.transact` with a valid proof for a CASE-2 op batch containing `positionManager.mint(...)` targeting the pool, funded via the victim's own UTXOs; assert `positionManager.ownerOf(tokenId) == address(emporium)` after the call.
3. Attacker (separate EOA, own funds/UTXOs, no relation to victim) calls `Hinkal.transact` with a CASE-2 op: `op.endpoint = address(positionManager)`, `op.callData = abi.encodeWithSelector(IERC721.safeTransferFrom.selector, address(emporium), attacker, tokenId)`, `op.invokeWallet = false`.
4. Assert the call succeeds (`success == true`, no `CallFailed` revert) and `positionManager.ownerOf(tokenId) == attacker`.
5. Assert no nullifier, root, or public signal in the attacker's `circomData` references the victim's stealth address, UTXO commitment, or `emporiumMessage`, proving the transfer was authorized purely by Emporium's own on-chain ownership rather than any Hinkal-verified proof of the victim's authorization.
