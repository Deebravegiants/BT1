This confirms the vulnerability: the `Webhooks::Request` class's `to_signable_string` returns only `@raw_body`, so the HMAC signature validated by `Utils::HmacValidator.validate` in `Registry.process` only covers the JSON body bytes and never covers the `shop` (from `shopify-shop-domain` header), `topic`, `api_version`, or `webhook_id` fields.### Title
Webhook shop-domain (and topic/api_version/webhook_id) are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`, which checks the HMAC against `request.to_signable_string`. That signable string is defined in `Webhooks::Request#to_signable_string` as just `@raw_body` — nothing else. But `Registry.process` (and the resulting `WebhookMetadata` passed to the host app's handler) trusts `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id`, all of which are read directly from unauthenticated HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) that are never mixed into the HMAC computation.

### Finding Description
The identity binding that should hold is:
`hmac_signed_bytes == bytes_the_handler_trusts_as_the_request's_identity`

In this gem it does not:
- `Webhooks::Request#to_signable_string` returns only the raw JSON body: [1](#0-0) 
- `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from headers with no cryptographic binding to the signature: [2](#0-1) 
- `Registry.process` validates only the HMAC of the body and then immediately trusts `request.shop`/`request.topic` to build `WebhookMetadata`, which is handed to the app's `WebhookHandler.handle`: [3](#0-2) 
- `WebhookMetadata.shop` is a plain `String` const with no further verification, and is the field host applications are expected to use to scope data to a tenant/merchant: [4](#0-3) 

Because the shop-domain header sits outside the HMAC's coverage, two bodies that are byte-identical produce the same valid signature regardless of which `shopify-shop-domain` header accompanies them. An attacker who obtains one legitimate webhook delivery with a valid HMAC (e.g., a webhook Shopify sent to the attacker's own store, or one leaked/logged/forwarded through an intermediary) can resend that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` will still pass, because the header is never part of `to_signable_string`.

### Impact Explanation
This breaks the shop-authenticated vs. shop-acted-upon binding, letting an unprivileged party who has captured a single valid webhook body cause the host application to process attacker-controlled data under a victim merchant's shop identity — a cross-tenant confusion. Depending on how the host app uses `WebhookMetadata.shop` (e.g., to look up which merchant's session/data to mutate for `orders/create`, `app/uninstalled`, GDPR topics, etc.), this can lead to cross-tenant data corruption or disclosure. This matches the Critical "cross-tenant access" impact category in scope, since the gem's own webhook-processing API is the one making the trust promise (that `data.shop` in `WebhookHandler#handle` corresponds to the shop that actually sent the signed payload) and that promise does not hold.

### Likelihood Explanation
Exploitation requires the attacker to first obtain one legitimate signed webhook body — for example by installing the target app on their own store (a normal unprivileged action) and capturing a webhook Shopify sends to their configured endpoint, then replaying that exact body with a forged `shopify-shop-domain` header to the app's public webhook endpoint. No `api_secret_key`, access token, or privileged access is needed; the attacker only needs an internet-reachable copy of one prior signed webhook, which is straightforward for topics they can trigger on their own store (order creation, app-installed events, etc.).

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the payload before trusting them in `WebhookMetadata`. At minimum, document and/or enforce that consumers of `Webhooks::Registry.process` must independently verify `data.shop` against a known/registered shop for that webhook subscription before acting on it, since the gem currently provides no such guarantee.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com` and lets Shopify send a real webhook, e.g. `orders/create`, to the app's public webhook endpoint. The attacker intercepts (or otherwise obtains, e.g. via a shared logging/network path) the raw request:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of body B under app's secret>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   x-shopify-webhook-id: ...

   B = {"id":123,...}
   ```
2. Attacker resends the exact same request to the app's endpoint, changing only the shop header:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <same valid HMAC of body B>
   x-shopify-shop-domain: victim-shop.myshopify.com
   x-shopify-webhook-id: ...

   B = {"id":123,...}
   ```
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (i.e., only `B`) and finds it matches, per [5](#0-4) .
4. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: B, ...)`, per [6](#0-5) , causing the app to process attacker-supplied order data as if it belonged to `victim-shop.myshopify.com`.
