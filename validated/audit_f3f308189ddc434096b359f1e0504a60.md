### Title
Webhook `shop` (and other metadata) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from only the raw request body, while the `shop`, `topic`, `api_version`, and `webhook_id` fields are read from unauthenticated HTTP headers and passed straight through to the application's webhook handler as the trusted tenant identity. Because these header-derived fields are never part of the HMAC computation, an attacker who possesses one genuine `(raw_body, hmac)` pair signed by the shared `client_secret` can freely rebind that signed body to a different `shop-domain`, and the signature will still validate.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all sourced from request headers that are entirely outside the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then immediately trusts `request.shop` (and topic/webhook_id) as the source-of-truth tenant identity forwarded to the handler: [3](#0-2) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (i.e., the raw body) against the HMAC — it has no knowledge of `shop`: [4](#0-3) 

This breaks the intended binding: `hmac == HMAC(secret, body)` should imply `shop == the shop that produced this exact webhook payload`, but the code only proves `hmac == HMAC(secret, body)`; `shop` is asserted, not authenticated. Any unprivileged internet user who can install the merchant's public Shopify app on their own store (a normal, unprivileged action) receives genuine webhooks with valid HMACs computed over bodies they fully control the shape of (e.g. `orders/create` payloads for their own store, or empty bodies for mandatory GDPR topics such as `shop/redact`). They can then replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain. `Registry.process` will accept the request as valid and hand the attacker-chosen `shop` value to the app's `WebhookHandler`, which typically uses it to look up per-tenant session/credentials and apply the (attacker-controlled) body's mutations against the victim tenant's data.

### Impact Explanation
This allows cross-tenant access: an attacker-controlled webhook body — with a valid HMAC obtainable from the attacker's own installation of the app — can be attributed to an arbitrary victim shop domain. Any app whose `WebhookHandler` implementation uses `WebhookMetadata#shop` to select the tenant record/session (a standard and expected pattern, since the gem provides no other way to identify the source shop from a `Request`) will process attacker data as if it originated from the victim shop, enabling cross-tenant data corruption or GDPR-webhook abuse (e.g., forging `shop/redact`/`customers/redact` for a victim shop).

### Likelihood Explanation
Any internet user can install a public Shopify app on their own development store for free, causing Shopify to deliver genuine HMAC-signed webhooks to the app's endpoint. Capturing one such `(raw_body, hmac)` pair and replaying it with a rewritten `shop-domain` header requires no secrets, tokens, or privileged access — only knowledge of the target app's public webhook endpoint URL, which is typically fixed and discoverable.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the HMAC-signable content, or otherwise cryptographically bind them to the body before verification, so that `HmacValidator.validate` fails if the shop-domain header is altered relative to what Shopify actually signed for that specific shop/body pair.

### Proof of Concept
1. Attacker installs the target public app on their own store `attacker.myshopify.com`, receiving Shopify's genuine webhook `orders/create` call with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid hmac over body>`, and some `raw_body`.
2. Attacker resends this exact `raw_body` and `X-Shopify-Hmac-Sha256` to the same app endpoint but changes the header to `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the HMAC against `request.to_signable_string` (the raw body) — unaffected by the header change — and passes: [5](#0-4) 
4. The app's handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker's chosen body, and processes it as a legitimate webhook for the victim's shop.

          received_signature = verifiable_query.hmac
