### Title
Webhook shop identity spoofing via HMAC that only covers the request body, not the `shop-domain` header - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `HmacValidator.validate` verifies the HMAC exclusively against that body [1](#0-0) . The `shop` value used to identify the tenant a webhook belongs to is instead read straight from the `shopify-shop-domain` (or `x-shopify-shop-domain`) HTTP header, which is not covered by the HMAC signature at all [2](#0-1) . `Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching `request.shop` to the app's handler as the trusted tenant identifier [3](#0-2) .

### Finding Description
The intended identity binding is: `shop that the HMAC-signed payload was generated for == shop the gem hands to the application as the webhook's tenant`. This binding is not enforced. `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received `hmac` header [4](#0-3) . For `Webhooks::Request`, `to_signable_string` is just `@raw_body` [1](#0-0) , so the shop-domain header is never part of the signed material. Anyone in possession of a validly-signed webhook body/HMAC pair for *some* shop (e.g., their own store where the app is installed) can resend that exact body+HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. `Registry.process` re-validates only the HMAC over the body, which still matches, then builds `WebhookMetadata.new(topic:, shop: request.shop, body:, ...)` and hands it to the registered handler as though it were the victim shop's authenticated webhook [5](#0-4) .

### Impact Explanation
This breaks the shop/tenant boundary the gem is supposed to enforce for webhook processing: an attacker who controls (or has previously observed) a legitimately-signed webhook payload can make an app process arbitrary webhook data under the identity of a different, victim shop. Depending on how the host app trusts `WebhookMetadata#shop`/`#body` (e.g., to write records, invalidate data, process mandatory compliance topics like `customers/redact` or `shop/redact`, or key persistence lookups), this can lead to cross-tenant data corruption/access — attacker-controlled data attributed to a shop the attacker does not own.

### Likelihood Explanation
Exploitation requires only unauthenticated network access to the app's public webhook endpoint plus one HMAC-valid body (trivially obtainable by installing the app on any shop, including the attacker's own, or from an app whose webhook bodies are largely fixed/predictable per topic). No access to `api_secret_key`, tokens, or the victim shop is required, satisfying the unprivileged-internet-user threat model.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) headers in the signable string used for HMAC verification, or independently authenticate the shop domain against a value derived from a source that is itself HMAC/token-protected (e.g., a stored per-shop secret or session lookup) before trusting `request.shop` in `WebhookMetadata`. At minimum, document that consumers of `WebhookMetadata#shop` must not treat it as cryptographically authenticated, and consider making `Request#to_signable_string` bind the shop header into the signature check performed by `HmacValidator`.

### Proof of Concept
1. Install the app (or otherwise obtain) on `attacker-shop.myshopify.com`; trigger any subscribed webhook topic so Shopify sends a validly HMAC-signed request, e.g.:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid-for-body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   x-shopify-webhook-id: ...
   Body: {"id": 1, ...}
   ```
2. Capture this request (attacker fully controls their own inbound traffic/logs).
3. Replay the identical body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but change the header to:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` still returns `true` because it only checks `@raw_body` against the secret [6](#0-5) .
5. `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body [5](#0-4) , causing the host application to act on behalf of the victim tenant using attacker-supplied data.
