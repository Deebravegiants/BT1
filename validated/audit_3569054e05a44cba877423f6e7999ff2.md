### Title
Webhook shop identity is not authenticated by the HMAC signature, enabling cross-tenant webhook shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop`, `topic`, and `webhook_id` values used downstream by `WebhookHandler`s are read directly from unauthenticated HTTP headers. `Registry.process` accepts any request whose body/HMAC pair validates, then hands the handler a `shop` value that was never covered by that signature, breaking the equality "HMAC-authenticated payload == shop identity acted upon."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors instead read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` (and equivalent) headers, which are not part of the signed material: [2](#0-1) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)` (i.e. body vs. HMAC) and then dispatches to the handler using `request.shop`, `request.topic`, and `request.webhook_id` verbatim: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the raw body) and the app secret, with no binding to headers: [4](#0-3) 

Because the HMAC never covers `shop-domain`, any two requests with the same body are indistinguishable to the validator even if their `shop-domain` header differs. An unprivileged internet user who can install the app on any store they control (a free/dev shop, obtainable by anyone) will legitimately receive genuine webhook deliveries — real body + valid HMAC computed with the target app's secret — for their own shop. They can replay that exact body/HMAC pair to the app's webhook endpoint while substituting a victim shop's domain in the `shop-domain` header. The request still passes `HmacValidator.validate`, and the handler receives `WebhookMetadata` claiming the victim's shop identity while carrying attacker-chosen topic/body semantics (subject to whatever body the attacker was able to legitimately receive, e.g. `app/uninstalled`, which is a fixed, predictable, empty-ish payload for every shop).

### Impact Explanation
This breaks the tenant/shop binding assumption `WebhookHandler` implementations rely on — they trust `data.shop` from a validated webhook to key their storage of sessions/access tokens or drive shop-specific side effects. Spoofing the shop field on an otherwise-valid webhook lets an attacker impersonate another tenant to the host application's webhook handler, which the rules classify as cross-tenant access (Critical impact) — e.g., forging a `shop/redact` or `app/uninstalled` event against a victim shop id to trigger deletion of that shop's stored session/access token, or otherwise poisoning shop-keyed application state.

### Likelihood Explanation
Likelihood is realistic but not trivial: the attacker must (a) be an actual (even free/dev) merchant who installs the target public app to legitimately receive a signed webhook with a predictable/replayable body, and (b) control the raw HTTP headers sent to the app's webhook endpoint (feasible since delivery endpoints are plain HTTP(S) and the library performs no additional header-binding or nonce/replay check). No access token, `client_secret`, or privileged account is required — only participation as an ordinary shop owner.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signable string, or independently verify that the `shop-domain` header corresponds to a shop actually authorized/installed for this app before dispatching to handlers. At minimum, document that `WebhookHandler` implementers must not treat `WebhookMetadata#shop` as authenticated unless the gem also binds it into the signature.

### Proof of Concept
1. Install the target Shopify app on shop `attacker.myshopify.com` (any developer can do this on a free/dev store).
2. Capture a legitimate webhook delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for the app's secret), plus `X-Shopify-Topic: app/uninstalled`.
3. Replay a POST to the app's webhook endpoint with the same body `B` and `X-Shopify-Hmac-Sha256: H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` — which only checks `B` against `H` — and it passes. The handler then executes with `WebhookMetadata.shop == "victim.myshopify.com"`, even though the request was never authorized by/for that shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
