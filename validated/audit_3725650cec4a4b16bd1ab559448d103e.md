Based on my investigation, the key mechanism analogous to the M-5 report is found in `IntrinsicIntents.sol` and `IntentsBase.sol`, where per-leg accounting is keyed by `bytes32` **output token identity**, not by array index, and a *separate* duplicate-input check is keyed by the address-cast of `order.inputs[i].token`. This is the closest structural analog to "collateral cannot be swapped" — a same-token restriction enforced purely by comparing raw token identifiers rather than verifying the underlying asset is actually distinct.

### Title
Duplicate input/output "same token" guards in IntentGatewayV2/IntrinsicIntents rely on raw address equality, bypassable by ERC20s with multiple valid addresses - (File: evm/src/apps/IntentGatewayV2.sol, evm/src/apps/intentsv2/IntrinsicIntents.sol, evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`placeOrder` rejects duplicate output tokens via transient-storage keyed on the raw `bytes32` token identifier [1](#0-0) , and separately rejects duplicate input tokens via `_orders[commitment][token] != 0` keyed on the `address` cast of the token field [2](#0-1) . Partial-fill progress is likewise tracked in `_partialFills[commitment][outputToken]`, keyed on the raw output token identifier [3](#0-2) . All three guards assume that two different `bytes32`/`address` values necessarily represent two economically distinct assets — exactly the assumption the Taurus M-5 report shows is false for ERC20s that expose more than one valid address for the same underlying balance (e.g. legacy/proxy pairs, migrated tokens).

### Finding Description
The regression test explicitly documents *why* the duplicate-output check exists: "same-chain partial fills prematurely finalize repeated output legs" [4](#0-3) . The fix relies solely on `token` (the raw identifier) being unique, never verifying that two identifiers cannot resolve to the same fungible balance. If a token exists in the wild with two callable addresses mapping to one underlying balance (as described in the M-5 report), a user or solver could supply `outputToken = addrA` and `outputToken' = addrB` for the same underlying asset in one order, defeating the "reject duplicate output tokens" check in `placeOrder` while still hitting the exact `_partialFills` collision the check was written to prevent in `_fillSameChain` [5](#0-4) . Similarly, the duplicate-input-token check in `placeOrder` (`_orders[commitment][token] != 0`) can be bypassed the same way, letting an order escrow the same underlying balance twice under two different address keys within a single commitment [2](#0-1) .

### Impact Explanation
This does not directly enable outright theft of protocol funds by itself, since each address still requires a real, separately-approved ERC20 transfer — but it defeats an invariant the codebase itself has already identified as security-critical (the regression test states the pre-fix bug was escrow *prematurely finalizing repeated output legs*, i.e. releasing input escrow before all output legs were genuinely filled). Reintroducing a token-aliasing vector reopens exactly that failure mode: a solver could construct/exploit an order whose two "distinct" output legs are the same underlying multi-address token, causing `_partialFills` accounting or the `isFullyFilled` determination in `_fillSameChain` to diverge from the true state of delivered value, potentially finalizing escrow release (`_withdraw(..., finalize=true)`) before the order is genuinely, fully paid out. This matches a Medium severity per the accepted Sherlock precedent — real but rare token class, escrow/accounting integrity violated rather than an unconditional drain.

### Likelihood Explanation
Low-to-medium likelihood: it requires (a) a token in production that genuinely exposes two independently-callable addresses backed by one balance, and (b) that token being accepted as a valid input/output asset by the gateway (the contracts place no restriction on which ERC20s may be used, unlike the Simplex SDK's off-chain `assertPairSymbolsResolve`/`AssetRegistry`, which the solver operator explicitly built to guard against symbol aliasing to the same address [6](#0-5) ). The on-chain `IntentGatewayV2`/`IntrinsicIntents` contracts have no equivalent protection, so any deployment that accepts arbitrary user-specified `TokenInfo.token` values (which is the design — tokens are referenced by raw address, not through a registry) is exposed if such a token is ever escrowed.

### Recommendation
Do not rely on raw `bytes32`/`address` token-field equality alone to establish "same asset" or "distinct asset" invariants in `placeOrder`'s duplicate-input/output checks and in `_partialFills` accounting. Either (a) maintain an explicit per-deployment allow/deny-list of tokens known to have multiple valid addresses and reject them at `placeOrder`, or (b) as the original report recommends, snapshot balances before/after any transfer involving a given token address to detect unexpected balance movement caused by an aliased address, and document the requirement (mirroring the note Sherlock added to their README) that only single-address, non-rebasing ERC20s are safe collateral/settlement assets for this gateway.

### Proof of Concept
1. Identify (or deploy, for testing) an ERC20-like contract `T` that exposes two distinct addresses `A` and `B`, both of which read/write the same underlying balance mapping (a "multi-address" token, per the Taurus report).
2. Construct an `Order` whose `output.assets` contains two entries: `{token: A, amount: X}` and `{token: B, amount: Y}` — this passes the `placeOrder` duplicate-output check in `IntentGatewayV2.sol:197-211` because `A != B` as raw `bytes32` values, even though they represent the same underlying balance.
3. On fill via `_fillSameChain`, `_partialFills[commitment][A]` and `_partialFills[commitment][B]` are tracked as independent buckets against the same real token balance, letting a solver manipulate `isFullyFilled`/escrow release ordering exactly as described in the pre-fix bug covered by `testRevert_PlaceOrder_DuplicateOutputTokens` [7](#0-6) , but using two addresses instead of one repeated address.
4. A parallel PoC applies to `placeOrder`'s input-side duplicate check at `IntentGatewayV2.sol:363-373`, escrowing the same underlying balance under two `_orders[commitment][...]` keys.

export interface PairAddressResolver {
	getAddress(symbol: string, chain: string): string | null
}

/**
 * Boot-parity resolution checks over `[[pairs]]` symbols, shared by the boot
 * path and the wizard gates so a config is rejected where it is written, not
 * first on `simplex run`:
 *  1. every symbol must resolve to a real deployment on at least one of the
 *     given chains — the SDK stores zero-address sentinels for undeployed
 *     assets, and the zero address doubles as the native-token sentinel in the
 *     fill path;
 *  2. no two distinct symbols may resolve to the SAME contract on a chain
 *     (an [assets] alias of USDC's address): aliasing collapses a cross-asset
 *     pair into a same-asset market — bypassing the same-token safeguards —
 *     and makes leg matching order-dependent.
 */
export function assertPairSymbolsResolve(
	pairs: PairConfig[],
	registry: PairAddressResolver,
	chainNames: string[],
): void {
	const pairSymbols = new Set(pairs.flatMap((pair) => [pair.token0, pair.token1]))
	for (const pair of pairs) {
		for (const symbol of [pair.token0, pair.token1]) {
			const resolvesSomewhere = chainNames.some((chainName) => registry.getAddress(symbol, chainName) !== null)
			if (!resolvesSomewhere) {
				throw new Error(
					`pairs.${pair.token0}/${pair.token1}: '${symbol}' does not resolve to a deployed contract on any configured chain`,
				)
			}
		}
	}

	for (const chainName of chainNames) {
		const addressOwner = new Map<string, string>()
		for (const symbol of pairSymbols) {
			const address = registry.getAddress(symbol, chainName)?.toLowerCase()
			if (!address) continue
			const owner = addressOwner.get(address)
			if (owner && normalizeSymbol(owner) !== normalizeSymbol(symbol)) {
				throw new Error(
					`assets: '${symbol}' and '${owner}' both resolve to ${address} on ${chainName} — symbols must map to distinct contracts`,
				)
			}
			addressOwner.set(address, symbol)
		}
	}
}
