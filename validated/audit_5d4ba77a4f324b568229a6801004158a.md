## Analysis

The reported bug class — failing to check actual balance received via `transferFrom` before crediting an internal accounting ledger — has a direct, unpatched analog in the Tron variant of `IntentGatewayV2`.

The primary EVM implementation at `evm/src/apps/IntentGatewayV2.sol` was hardened against fee-on-transfer tokens: in `placeOrder`, it snapshots `balBefore = IERC20(token).balanceOf(address(this))` before `safeTransferFrom`, then sets `order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore` so the escrow ledger always reflects the token actually received. [1](#0-0) 

The Tron port at `evm/tron/contracts/apps/IntentGatewayV2.sol` never received this fix. In its `placeOrder`, the protocol fee is computed on `order.inputs[i].amount` (the user-declared amount) *before* any transfer occurs, and the escrow mapping is credited with that pre-transfer `reducedInputs[i].amount` immediately after `safeTransferFrom`, with no balance-diff check: [2](#0-1) 

For a fee-on-transfer (or otherwise deflationary) ERC20 token, the gateway physically receives less than `order.inputs[i].amount`, yet `_orders[commitment][token]` is incremented by the full fee-reduced (but not transfer-fee-reduced) amount: [3](#0-2) 

This creates phantom escrow balances that exceed the gateway's actual token holdings, which can be exploited to drain tokens belonging to other orders/users when solvers redeem escrow or users cancel orders, since the ledger no longer matches physical custody.

### Title
Tron `IntentGatewayV2.placeOrder` fails to verify actual token amount received before crediting escrow, enabling insolvent/inflated escrow accounting - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder` in the Tron contracts directory escrows tokens by calling `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then credits `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` is derived from the user-declared `order.inputs[i].amount` rather than the token balance actually received by the contract. The equivalent main EVM `IntentGatewayV2` contract already fixes this by measuring the balance delta before/after the transfer, confirming this omission in the Tron variant is a real regression/gap rather than intended design.

### Finding Description
In `placeOrder` (Tron), the fee-reduced input amounts and the resulting order `commitment` are computed purely from the caller-supplied `order.inputs[i].amount`, never validated against tokens actually delivered: [4](#0-3) 

Then, in the non-predispatch escrow branch, tokens are pulled with `safeTransferFrom` and the escrow ledger `_orders[commitment][token]` is incremented by `reducedInputs[i].amount` unconditionally — with no check of `balanceOf(address(this))` before vs. after the transfer: [2](#0-1) 

If `token` charges a fee on transfer (or is rebasing/deflationary), the gateway's real token balance increases by less than `reducedInputs[i].amount`, but the internal accounting (`_orders` mapping) is credited as if the full amount arrived. Since `_orders` backs later solver payouts/escrow releases and cancellation refunds, the ledger becomes systematically overstated relative to the contract's actual token custody.

Contrast with the corrected logic in the canonical EVM contract, which explicitly measures the delta: [5](#0-4) 

and even test-covers this exact scenario: [6](#0-5) 

### Impact Explanation
Because `_orders[commitment][token]` can be over-credited relative to real token holdings, the gateway's aggregate escrow liabilities can exceed its aggregate token balance. Any downstream flow that pays out based on the `_orders` ledger (escrow redemption to a solver, order cancellation refund, or dust sweep accounting) can then be satisfied using tokens that belong to other, unrelated escrowed orders — i.e., later legitimate order placers/solvers can have their funds partially or fully drained/frozen once the shortfall is realized. This is a direct loss/freezing-of-funds condition reachable by any unprivileged user simply calling `placeOrder` with a standard fee-on-transfer ERC20, matching the Medium-severity classification of the original report.

### Likelihood Explanation
Likelihood is high for any deployment of this Tron gateway that accepts arbitrary/permissionless ERC20 tokens as order inputs (which is the general design intent of an intent-based DEX gateway supporting many tokens). No special privileges are required — a single `placeOrder` call using a fee-on-transfer token is sufficient to desynchronize escrow accounting from actual custody.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: snapshot `balanceOf(address(this))` immediately before each `safeTransferFrom` call in the Tron `placeOrder` escrow paths (including the predispatch sweep path), and compute the amount credited to `_orders[commitment][token]` (and used for `commitment` hashing/protocol fee calculation) from the actual balance delta rather than the caller-declared `order.inputs[i].amount`.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g., 1% fee) and mint balance to `user`.
2. `user` calls `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs[0] = {token: FOT, amount: 1000e18}` and no predispatch.
3. `safeTransferFrom(user, gateway, 1000e18)` only delivers `990e18` to the gateway (contract's real balance increases by 990e18).
4. `reducedInputs[0].amount` is computed from `1000e18` (minus protocol fee, if any), and `_orders[commitment][FOT]` is credited with this larger, transfer-fee-unaware value.
5. The gateway now shows an escrow liability for `FOT` that exceeds its actual `FOT` balance; when this or another order's escrow is later redeemed/cancelled and paid out per the `_orders` ledger, the shortfall causes some order's rightful escrow payout to be partially unpayable/stolen from other users' escrowed tokens.
