I found the analog. The Tron `IntentGatewayV2.sol` `placeOrder` function escrows the pre-fee `reducedInputs[i].amount` while only transferring via `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` without verifying the actual balance received — unlike the audited EVM `IntentGatewayV2.sol` which explicitly measures `balBefore`/`balanceOf` deltas to account for fee-on-transfer tokens. This reproduces the exact root cause from the Kairos report: escrow accounting can promise more tokens than the contract actually holds, and later withdrawals (`_withdraw` in `IntentsBase.sol`) will attempt to pay out the recorded (un-discounted) escrow amount, draining the contract's actual balance and causing later claimants' `safeTransfer` calls to revert or leaving the pool insolvent.

### Title
Escrow credited with pre-fee amount instead of actual received balance for fee-on-transfer tokens, causing insolvent payouts - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` credits escrow with the nominal `order.inputs[i].amount` (reduced only by protocol fee), while pulling tokens via a plain `safeTransferFrom` that does not verify the actual amount received by the contract. For any ERC20 input token that charges a transfer fee (fee-on-transfer / deflationary token), the contract will hold less than what it records as escrowed, exactly mirroring the root cause described in the referenced Kairos audit finding.

### Finding Description
In the non-predispatch branch of `placeOrder`: [1](#0-0) 
the contract does `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally credits `_orders[commitment][token] += reducedInputs[i].amount` — a value derived from `order.inputs[i].amount` reduced only by the protocol fee bps, with no adjustment for what the contract actually received. If `token` deducts a transfer fee, the contract's real balance increase is strictly less than `reducedInputs[i].amount`.

This is precisely the same class of bug flagged in the Kairos report: recording an accounting entry (`provision.amount` / here, `_orders[commitment][token]`) based on the nominal transfer amount instead of the delta actually credited to the contract's balance.

By contrast, the canonical EVM `IntentGatewayV2.sol` in `evm/src/apps/` explicitly guards against this by measuring balances before and after the transfer and mutating `order.inputs[i].amount` to the actual received delta before computing the commitment and crediting escrow: [2](#0-1) 
The Tron variant lacks this balance-delta measurement entirely in both the predispatch and non-predispatch code paths — the "dust" comparison there only compares dispatcher balance against `requiredAmount`, not the amount the gateway itself pulled from `msg.sender`.

When escrow is over-credited relative to actual holdings, later calls to `_withdraw` (shared logic in `IntentsBase.sol`) will attempt `IERC20(token).safeTransfer(beneficiary, amount)` for the recorded (inflated) `amount`: [3](#0-2) 
This transfer will either revert (locking that specific withdrawal, since the escrow accounting has already been decremented while token balance is insufficient) or, in the multi-order scenario described in the report, drain the contract's remaining token balance such that later legitimate withdrawers for unrelated orders/commitments cannot be paid, because the shared token balance was exhausted by earlier over-credited escrow withdrawals.

### Impact Explanation
Users placing orders with fee-on-transfer ERC20 input tokens on the Tron deployment will have escrow entries that exceed the contract's actual token holdings. Filling solvers or refunding users can be left unable to withdraw their rightful (even reduced) share, and — in the worst case with many orders sharing the same input token — earlier withdrawals can drain the shared balance, permanently freezing funds owed to later claimants. This matches "Medium/High" severity: unbacked accounting leading to fund freezing/loss for particular token classes, reachable directly from a single `placeOrder` transaction by any unprivileged user.

### Likelihood Explanation
Likelihood is limited to deployments/orders that use fee-on-transfer (deflationary) ERC20 tokens as inputs on the Tron `IntentGatewayV2`. Given fee-on-transfer tokens are common enough that the EVM sibling contract added explicit handling for them (and has a full test suite covering it, e.g. `IntentGatewayV2SameChainTest.sol`), and that the Tron file is a near-duplicate lacking the same protection, this is a realistic and directly reachable path — any user calling `placeOrder` with such a token triggers the miscalculation without any privileged action.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: measure `IERC20(token).balanceOf(address(this))` before and after each `safeTransferFrom` call in `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `placeOrder` (both the predispatch and direct-transfer branches), mutate `order.inputs[i].amount` to the actual received delta, and derive `reducedInputs`/escrow credits and the commitment hash from that actual-received value rather than the caller-supplied nominal amount.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 token (e.g., 1% fee) on Tron and mint balance to `user`.
2. `user` calls `placeOrder` on the Tron `IntentGatewayV2` with `inputs[0] = {token: FOT, amount: 1000e18}` and `protocolFeeBps = 0`.
3. `safeTransferFrom(user, address(this), 1000e18)` executes, but due to the 1% fee the gateway's actual balance only increases by `990e18`.
4. `_orders[commitment][token]` is nonetheless credited with `reducedInputs[0].amount = 1000e18` (since `protocolFeeBps == 0`, `reducedInputs == order.inputs`).
5. When a solver fills the order and the withdrawal path calls `_withdraw` to transfer `1000e18` of the FOT token to the solver, the transfer reverts (contract holds only `990e18`), or — if multiple orders share the same token pool — earlier withdrawals drain the shared balance and later withdrawers cannot be paid, exactly as in scenario 2 of the referenced report.
