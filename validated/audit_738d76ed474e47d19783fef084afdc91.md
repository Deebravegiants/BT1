## Title
CORS wildcard-origin allowlist bypass via unanchored suffix match in Gateway HTTP server - (File: core/services/gateway/network/httpserver.go)

## Summary
The Gateway's `isAllowedOrigin` function in `core/services/gateway/network/httpserver.go` strips the `*.` prefix from a configured wildcard CORS rule and then checks `strings.HasSuffix(originHost, allowedHost)` without any dot-boundary anchoring. This allows any origin host that merely ends with the same character sequence (e.g., `fakeethereum.org` against a rule for `*.ethereum.org`) to be treated as an allowed subdomain, even though it is an unrelated domain.

## Finding Description
`isAllowedOrigin` at `core/services/gateway/network/httpserver.go` L157-193 parses the incoming `Origin` header and each configured `CORSAllowedOrigins` entry, matching scheme and port exactly, then for wildcard entries (`*.` prefix) strips the prefix and does a bare `strings.HasSuffix` comparison at L185-190. There is no check that the character immediately preceding the matched suffix in `originHost` is a `.`, so the match is not anchored to a label boundary. `handleRequest` at L195-209 uses this function's result to directly reflect the attacker-supplied `Origin` value into the `Access-Control-Allow-Origin` response header along with permissive `Access-Control-Allow-Methods`/`Access-Control-Allow-Headers`. No other validation intervenes — there is no allowlist normalization, no separate anchoring logic, and no additional origin-checking layer downstream. This precisely reproduces the CVE-2019-25211 (GHSA-869c-j7wc-8jqv) bug class in `gin-contrib/cors`.

## Impact Explanation
This is a concrete CORS allowlist bypass on the Gateway, an internet-facing component intended to accept external client requests. If an operator configures any wildcard `CORSAllowedOrigins` entry (a documented, normal usage pattern, exercised by the existing test `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards`), an attacker who controls a domain with a matching suffix (not a genuine subdomain) can have their page's cross-origin JavaScript requests treated as allowed, letting browsers read Gateway JSON responses that should be scoped only to the intended subdomains. This maps to the in-scope "allowlist... bypass" impact category for the internet-facing gateway.

## Likelihood Explanation
Exploitation requires only a standard, supported operator configuration (a wildcard CORS entry) and an attacker who registers/controls a domain with a matching suffix — no operator or admin access, no network position, and no credential is needed beyond normal browser interaction with the attacker's own page. The check is purely string-based and unconditionally reachable by any client sending a crafted `Origin` header.

## Recommendation
Anchor the wildcard suffix match to a label boundary: require `originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost)` instead of the bare `strings.HasSuffix` check, mirroring the fix applied upstream in `gin-contrib/cors` v1.6.0.

## Proof of Concept
1. Start the Gateway HTTP server with `CORSEnabled: true` and `CORSAllowedOrigins: []string{"https://*.ethereum.org"}` (as in `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards`).
2. Send an HTTP request to the Gateway's configured path with header `Origin: https://fakeethereum.org`.
3. Observe the response includes `Access-Control-Allow-Origin: https://fakeethereum.org`, `Access-Control-Allow-Methods: GET, POST, OPTIONS`, and `Access-Control-Allow-Headers: Content-Type`, confirming that `fakeethereum.org` (not a subdomain of `ethereum.org`) was incorrectly treated as an allowed origin because `strings.HasSuffix("fakeethereum.org", "ethereum.org")` returns true.
