### Title
Emporium `runAction` allows unsigned arbitrary calls to drain any token not listed in `erc20TokenAddresses` when using the Min-circuit path - (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol` / `contracts/CircomDataBuilder.sol`)

### Summary
`CircomDataBuilder.formInputForCircom` routes any transaction with `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0` to `formInputEmporiumMin`, whose only public constraint is `emporiumMessage == Poseidon(messageSeed)` — a value the attacker fully controls. Combined with `EmporiumUpgradeable.verifyWallet`, which returns immediately (skipping all ECDSA signature checks) when `EmporiumStack.signerAddress == address(0)`, this lets an unprivileged caller execute **arbitrary, unauthenticated calls from the Emporium contract's own identity**, while the balance-accounting loops in both `runAction` and `Hinkal.transact` only iterate `circomData.erc20TokenAddresses`, which is empty by construction on this path.

### Finding Description
The broken equality: *assets Emporium's ops can move in a transaction == assets accounted for in `balancesBefore`/`balancesAfter` (and in `Hinkal.transact`'s `oldBalances`/`newBalances`)*.

Path:
1. Attacker calls `Hinkal.transact` with `circomData.externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `circomData.erc20TokenAddresses.length == 0`. [1](#0-0) 
2. `formInputEmporiumMin` builds a public-input vector containing only `emporiumMessage`, `timeStamp`, `calldataHash` — no binding at all to the ops the attacker will run. [2](#0-1) 
3. The attacker, knowing their own `messageSeed`, can trivially produce a valid Groth16 proof for this minimal statement.
4. `Hinkal.transact` verifies the proof and calls `_externalTransact`, which forwards `circomData` unmodified to `EmporiumUpgradeable.runAction`, with `msg.sender == Hinkal` (a pre-whitelisted allowed recipient, satisfying `onlyAllowedRecipient`). [3](#0-2) [4](#0-3) 
5. `runAction` decodes the attacker-supplied `EmporiumStack` from `externalActionMetadata`. Since `stack.signerAddress == address(0)`, `verifyWallet` marks the message used and returns **without any signature verification**. [5](#0-4) 
6. In the ops loop, since `stack.signerAddress == address(0)`, every op falls into "CASE 2: Stateless Interaction", executing `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract's own address, with the only restriction being a block on the `callHinkalWallet`/`doSendToRelay` selectors. [6](#0-5) 
7. The attacker sets `op.endpoint` = any ERC20 token held by Emporium and `op.callData` = `transfer(attacker, balance)` or `approve(attacker, type(uint256).max)`. This executes with `msg.sender == EmporiumUpgradeable`, moving/approving Emporium's own token balance to the attacker.
8. Because `circomData.erc20TokenAddresses.length == 0` (required to reach the Min path), the post-loop balance-diff loop in `runAction` and the balance/slippage checks in `Hinkal.transact` both iterate an empty array and account for nothing regarding the drained token. [7](#0-6) [8](#0-7) 

Root cause: the Min-circuit path removes the cryptographic binding between the proven `emporiumMessage` and the actual `EmporiumStack` ops, and the unsigned (`signerAddress == 0`) branch — intended for protocol-initiated/relay-only ops — has no on-chain restriction preventing an attacker from supplying it directly through a normal `transact()` call. `onlyAllowedRecipient` only checks that `msg.sender` is `Hinkal` itself; it does not validate who ultimately controls the payload that reaches `runAction`.

### Impact Explanation
Any ERC20 (or ETH via `op.value`, if funded) balance sitting in the `EmporiumUpgradeable` contract can be transferred or approved to an attacker-chosen address with zero cost, zero signature, and zero balance-accounting check, because the exploited token is deliberately excluded from `circomData.erc20TokenAddresses`. This is direct theft of protocol/shielded funds held by Emporium and matches Critical: "direct theft of shielded or in-flight user funds" / "executing calls or moving assets... never authorised." The exploit is repeatable for every token Emporium holds and for every subsequent balance that accrues in the contract.

### Likelihood Explanation
- No privileged role needed: only `onlyAllowedRecipient` (satisfied because the call arrives via the legitimate `Hinkal` router) and a proof for the trivial Min circuit (attacker knows their own `messageSeed`).
- Requires Emporium to hold a non-zero balance of the target token at call time (e.g., dust left after partial fills, in-flight relayed swaps, or funds routed through `invokeWallet` flows).
- Attacker cost is a single transaction; fully repeatable each time Emporium accumulates balance.

### Recommendation
- Cryptographically bind `emporiumMessage` (or the Min circuit's public inputs) to the hash of the actual ops/`EmporiumStack` being executed, even on the unsigned (`signerAddress == 0`) path, so a valid Min proof cannot be reused for arbitrary op content.
- Do not allow `signerAddress == address(0)` (skipping ECDSA verification) to be reachable from a caller-supplied, attacker-controlled `externalActionMetadata`; restrict the "stateless/unsigned" branch to internally-derived contexts, or require the ops set to be independently authorized/whitelisted.
- Make the balance-diff/slippage accounting in `runAction`/`Hinkal.transact` cover every token actually touched by executed ops, not only `circomData.erc20TokenAddresses`, or forbid `erc20TokenAddresses.length == 0` when the ops list is non-empty and unsigned.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, register it in `Hinkal.externalActionMap` under `HINKAL_EMPORIUM_ACTION_ID`, and set `Hinkal` as an allowed recipient via `setAllowedRecipients`.
2. Fund `EmporiumUpgradeable` with `TOKEN` (e.g., 1000 units) to simulate in-flight/leftover balance.
3. As attacker EOA, build `CircomData` with `erc20TokenAddresses = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `emporiumMessage = Poseidon(attackerSeed)`, and `externalActionMetadata` ABI-encoding an `EmporiumStack{signerAddress: address(0), ops: [{endpoint: TOKEN, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, 1000))}]}`.
4. Generate a valid Groth16 proof locally for the Min-circuit statement (trivial since attacker knows `attackerSeed`).
5. Call `Hinkal.transact(a, b, c, dimensions, circomData)`.
6. Assert: `TOKEN.balanceOf(attacker)` increases by 1000 and `TOKEN.balanceOf(Emporium)` decreases by 1000, while the transaction does not revert on any balance/slippage check (proving the equality `assets moved == assets accounted` is violated).
