### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop-identity spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop` as the raw, unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header, while `Utils::HmacValidator` only verifies the HMAC over the raw request body (`to_signable_string` returns `@raw_body`). The `shop` field that consuming applications rely on to select tenant context is never part of the signed material, so any actor who can obtain one valid `(body, hmac)` pair for the shared app `client_secret` can present that pair together with an arbitrary `shop-domain` header value.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding to that body: [1](#0-0) 

`Registry.process` verifies only the HMAC-vs-body relationship before invoking the handler with `request.shop` as the tenant identifier: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` compute the signature strictly from `verifiable_query.to_signable_string` (the body, in the webhook case) and compare it against the received `hmac`; the `shop` value is never included in what is hashed or compared: [3](#0-2) 

This is a genuine identity-binding gap analogous to the report's bug class ("a field acted on but not covered by the HMAC"). Concretely:

- The equality that *should* hold is: `shop asserted to handler == shop that the HMAC-secret holder actually generated the body for`.
- Because `client_secret` (the HMAC key) is shared across *all* shops that install a given app — it is not a per-shop secret — the HMAC only proves "this body was produced by/for this app," not "this body belongs to shop X."
- Since the `shop-domain` header sits entirely outside the signed bytes, an attacker who controls any shop that has the app installed (e.g., a free/dev/trial store they legitimately created) can capture a genuine `(raw_body, x-shopify-hmac-sha256)` pair that Shopify sent for *their own* shop, then replay that exact body/hmac to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain.
- `Registry.process` will pass HMAC validation (body/HMAC still match each other) and will call the handler with `WebhookMetadata.new(... shop: request.shop ...)` reporting the victim's domain, even though the payload content is attacker-controlled data from the attacker's own shop.
- Contrast this with `Auth::Oauth::AuthQuery`, where `shop` *is* included in `to_signable_string`, so the OAuth callback path does correctly bind shop identity to the HMAC: [4](#0-3) 
This shows the webhook path is inconsistent with the library's own established pattern of binding the shop into the signed payload.

### Impact Explanation
An application that uses `ShopifyAPI::Webhooks::Request#shop` (as returned by `Registry.process` -> `WebhookMetadata#shop`) to select the tenant/session/database record to act on will process attacker-crafted webhook content under another merchant's identity — i.e., cross-tenant data injection/spoofing without needing that victim's access token or credentials. This satisfies the Critical "cross-tenant access" impact category, since the trust boundary between tenants (shops) is broken purely through this gem's webhook verification primitive.

### Likelihood Explanation
Exploitation requires only: (1) the attacker to have their own shop with the target app installed (freely obtainable, since Shopify app installs are self-service), (2) the ability to capture one legitimate webhook body+HMAC for their own shop (trivial — install the app, trigger any event), and (3) the ability to send an HTTP request to the app's public webhook endpoint with a forged `shop-domain` header, which requires no secret at all. This is a low-effort, unprivileged-internet-user attack chain.

### Recommendation
Bind the shop identity into the verified material for webhook requests, e.g., include the `shop-domain` header (and ideally `topic`/`webhook-id`) as part of what `HmacValidator` verifies, or independently confirm that the shop claimed in the header corresponds to a session/store known to have received that specific `webhook-id`/nonce before trusting `request.shop`. At minimum, update `docs/usage/webhooks.md` to explicitly warn integrators that `shop` is not authenticated by the HMAC and must not be trusted as a tenant-selection key without additional verification (e.g., cross-checking against a locally stored active session for that shop).

### Proof of Concept
1. Attacker signs up their own store `attacker.myshopify.com` and installs the target app (client_id/client_secret are shared across all installs).
2. Shopify sends a legitimate webhook to the app's endpoint for `attacker.myshopify.com`:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body over client_secret>`
   - Body: attacker-controlled JSON (attacker can influence content via ordinary shop actions, e.g. renaming a product to arbitrary values before triggering `products/update`).
3. Attacker replays the exact same `raw_body` and `x-shopify-hmac-sha256` value to the same endpoint, but changes the header to `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this successfully (headers just need the three required keys present) — see constructor: [5](#0-4) 
5. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (== `raw_body`, unchanged) and compares to the unchanged `hmac` header — validation **passes**.
6. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: <attacker's JSON>, ...)`, so the app processes attacker-controlled content as if it originated from the victim's store.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
