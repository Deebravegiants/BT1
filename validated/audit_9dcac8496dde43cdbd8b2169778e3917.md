### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC computed only over the raw request body, then trusts the `shop`-domain HTTP header — which is not part of the signed material — as the tenant identity passed to the app's handler. This breaks the identity binding "shop authenticated == shop bound by the signature," letting any user who legitimately installs the app on their own store forge webhook deliveries that Shopify would otherwise send to any other shop that installed the same app.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` value with a constant-time comparison: [1](#0-0) 

For webhooks, `to_signable_string` returns only `@raw_body`, while `shop` is read straight from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header: [2](#0-1) 

`Registry.process` validates the HMAC and, if valid, unconditionally forwards `request.shop` (the header value) into `WebhookMetadata` that is handed to the app's `WebhookHandler#handle`: [3](#0-2) 

```ruby
class WebhookMetadata < T::Struct
  const :topic, String
  const :shop, String   # trusted by downstream app code, but never covered by the HMAC
  ...
end
``` [4](#0-3) 

Shopify signs webhook bodies with the app's `client_secret`, which is the **same secret for every shop that installs the app** — it is not shop-specific. Because the signature only proves "this body was signed by an entity that knows the app's client secret," and the shop identity travels in a separate, unsigned header, the equality the code implicitly assumes:

```
hmac_valid(body) == shop_header_is_authentic
```

does not hold. Any tenant that has installed the app receives real, validly-signed `(body, hmac)` pairs from Shopify for their own webhooks. That tenant can replay the exact same `(body, hmac)` pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it never looks at the shop header), and `Registry.process` dispatches the payload to the app's handler tagged as coming from the victim shop.

This is analogous to the reported bug class: a field that is *acted on* (the `shop` used to key/dispatch webhook data to per-tenant handler logic) is not covered by the same equality/verification (`hmac`) that gates trust, so combining "HMAC valid" with "shop header is authoritative" produces an incorrect assumption exploitable by any unprivileged app-installing user.

### Impact Explanation
An attacker who has legitimately installed the target app on their own store (a normal, unprivileged action) can forge webhook events attributed to any other shop using the same app, without needing the app's `client_secret` (they only need a genuine signed body/hmac pair they can legitimately obtain via their own installation, or via any topic whose body content they control, e.g. a custom app-created resource). Downstream app code that uses `WebhookMetadata#shop` to look up/act on a specific merchant's data (a very common pattern) would process attacker-supplied data under another merchant's identity — a cross-tenant data-integrity/impersonation issue.

### Likelihood Explanation
Requires only that the attacker be able to install the app themselves (any developer/merchant can do this) and be able to POST directly to the app's webhook endpoint with modified headers but a body+HMAC pair they already legitimately possess. No access to the app's `client_secret`, access tokens, or the victim's credentials is required, satisfying the "unprivileged internet user" bar. Likelihood is bounded by whether the receiving application relies on `shop` from `WebhookMetadata` for security-sensitive dispatch (a widely-used pattern documented by this gem itself), but the gem provides no mitigation.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the material that is authenticated, or otherwise cryptographically tie the shop identity to the signed payload before trusting it — e.g., cross-check the shop header against a shop that is known to have registered the specific `webhook_id`, or require verification that the shop is one with an active, stored offline session before dispatching. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted without additional server-side verification (e.g., matching a known/installed shop record) before being used to key merchant-specific operations.

### Proof of Concept
1. Attacker installs "Victim App" on their own store `attacker.myshopify.com` and configures a webhook subscription for a topic whose body they control the content of (or captures any legitimate webhook body Shopify sends them).
2. Shopify sends the webhook to the app's endpoint with:
   - `x-shopify-hmac-sha256: <valid HMAC of body, using app's shared client_secret>`
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - body: `{...}`
3. Attacker (or a malicious relay they control) resends the identical raw body and HMAC header to the same endpoint, but rewrites the header:
   - `x-shopify-shop-domain: victim.myshopify.com`
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the raw body against the HMAC — this still passes. [5](#0-4) 
5. `WebhookMetadata.new(... shop: request.shop ...)` is built with `shop: "victim.myshopify.com"` and handed to the app's handler, which now processes attacker-controlled data attributed to `victim.myshopify.com`. [6](#0-5)
