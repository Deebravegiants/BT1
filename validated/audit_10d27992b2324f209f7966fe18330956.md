### Title
Unvalidated swap routes can attach arbitrary token transfers to the caller’s authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
The controller treats caller-supplied `swap` bytes as an opaque route and invokes the configured router without constraining which venue contracts the route may call. While the controller correctly authorizes only one exact input transfer from the controller to the router, route-controlled third-party code can still issue additional calls that require the account owner’s authorization. Those calls join the authorization tree signed for the strategy invocation, allowing a malicious route to steal unrelated wallet tokens while still returning enough output for the controller’s own settlement checks to pass. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_collateral`, `multiply`, `swap_debt`, and `repay_debt_with_collateral` all accept a `StrategySwap` argument and pass it to `swap_tokens` or `swap_tokens_or_passthrough`. For example, `process_swap_collateral` authenticates the caller, verifies ownership or delegation, withdraws supply, and forwards the caller-provided `swap` bytes to `withdraw_and_swap_from_supply`. [2](#0-1) 

`swap_tokens` only rejects an empty route, snapshots the controller’s input and output balances, invokes `router.execute_strategy(&controller, &amount_in, swap)`, and afterwards requires that the router spent no more than `amount_in` and returned a positive output balance delta. It does not decode the route, identify or bound the venue addresses it contains, restrict venue subcalls to a known interface, or require that the simulated authorization tree contains only the expected transfer. [3](#0-2) 

The authorization granted by the controller is narrow: `authorize_transfer_as_current` creates one leaf authorization for `token_in.transfer(controller, router, amount_in)` with no further sub-invocations. That protects controller-held input and prevents a token allowance from being created. [4](#0-3) 

The remaining problem is the caller’s authorization for the controller entrypoint itself. A malicious route can name an attacker-controlled venue. During execution, that venue can invoke an unrelated token’s `transfer(victim, attacker, amount)`, which requires the victim account owner’s authorization. If the victim signs the authorization tree produced by simulation—including the malicious nested transfer—the transfer executes under the same tree as the otherwise valid strategy call. The router can then return at least the route’s minimum output, so the controller’s positive-output and final-risk checks do not detect the unrelated wallet transfer. [5](#0-4) [6](#0-5) 

This is an analog of the Orion arbitrary-route/contract-call class: the strategy contract executes caller-supplied routing instructions through untrusted destination code while the surrounding transaction carries authority that can be applied to additional token transfers.

### Impact Explanation
An unprivileged attacker can steal arbitrary token balances from a strategy caller, up to the amounts included in the authorization tree the caller signs. The stolen assets need not be the swap input, output, collateral, or debt asset, and the loss is not bounded by `amount_in`, route minimum output, protocol collateral checks, or health-factor validation.

A practical path is `swap_collateral`: the attacker provides a malicious quoted route to a victim, who calls `swap_collateral(caller, account_id, current, amount, new, swap)`. The route reaches attacker-controlled code that transfers unrelated wallet tokens to the attacker. The same exposure exists for other route-bearing entrypoints, including `multiply`’s debt swap and third-asset `convert_swap`, `swap_debt`, and `repay_debt_with_collateral`. [7](#0-6) [8](#0-7) 

### Likelihood Explanation
Likelihood depends on getting a victim to sign a malicious authorization tree, which is feasible when route bytes are opaque and obtained from a quote service, interface, bot, or attacker-supplied integration. The protocol code places no structural venue allowlist or authorization-tree invariant on the `swap` argument. Once signed, execution requires no privileged role, leaked key, oracle manipulation, or broken token behavior; the attacker controls only a route destination contract. [1](#0-0) 

The controller’s exact-transfer authorization is not a mitigation for this loss. It constrains the controller’s invoker-contract authorization to `controller -> router`, but does not prevent an unrelated token call from being added beneath the victim’s authorization for the controller entrypoint. Likewise, balance-delta output checks and final account-risk checks only verify the strategy’s posted collateral/debt result, not that no unrelated victim-funded transfer occurred. [9](#0-8) [10](#0-9) 

### Recommendation
Constrain route execution to a venue/pool registry governed by the protocol or require decoded route destinations to implement a fixed, authenticated swap interface with no arbitrary caller-authorized side effects. Where arbitrary destinations remain necessary, the controller or router should enforce an authorization-tree policy that admits only the expected token pulls and rejects any extra invocation requiring the caller’s authorization.

At minimum, expose a canonical simulation/auth-tree inspection requirement in the contract-facing API and reject routes whose execution records any caller-authorized invocation other than the expected strategy token transfer. Ideally, replace broad invoker auth with a signed permit or explicit transfer intent that cannot be reused by arbitrary route-controlled contracts. [11](#0-10) 

### Proof of Concept
1. Alice owns a normal lending account and holds unrelated `TARGET_TOKEN` in her wallet.
2. Attacker deploys `MaliciousVenue`, whose route callback invokes `TARGET_TOKEN.transfer(alice, attacker, amount)` and then returns normally.
3. Attacker supplies Alice with route bytes that:
   - pull the legitimate `token_in` from the controller;
   - call `MaliciousVenue`;
   - return at least the encoded minimum amount of `token_out` to the controller.
4. Alice calls `swap_collateral(alice, account_id, current, amount, new, malicious_swap)`. [2](#0-1) 
5. The controller authorizes only `token_in.transfer(controller, router, amount)` on its own behalf, then executes the route inside the flash guard. [9](#0-8) [11](#0-10) 
6. `MaliciousVenue` adds a `TARGET_TOKEN.transfer(alice, attacker, amount)` call under Alice’s authorization tree. If Alice signs the simulated tree containing that child, the token contract accepts it and transfers her unrelated wallet balance.
7. The route still returns positive `token_out`; the controller’s `in_after <= in_before`, `actual_spent <= amount_in`, and `received > 0` checks all pass, after which the new collateral is supplied and final risk checks run. [10](#0-9) [12](#0-11)

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
}
