This confirms the vulnerability: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only the HMAC over the body and then trusts `request.shop`/`request.topic` for routing and handler dispatch without any binding to the signature [3](#0-2) .

### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable string solely from the raw body [4](#0-3) , but `Registry.process` uses the unauthenticated `shop`, `topic`, `webhook_id`, and `api_version` header values to route the request to a handler and to populate `WebhookMetadata` passed to app code [5](#0-4) . This is exactly the "field acted on but not covered by the HMAC" bug pattern: the `shop-domain` header identifies the tenant the webhook data belongs to, but the cryptographic signature never binds to that value.

### Finding Description
`HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, verifiable_query.to_signable_string)` and compares it against the `hmac` field of the `VerifiableQuery` [6](#0-5) . For `Webhooks::Request`, `to_signable_string` is just `@raw_body` — it does not include `shop`, `topic`, or any other header [1](#0-0) . Since the HMAC is computed purely as a function of the JSON body and the shared `api_secret_key`, the same HMAC value is valid for that exact body regardless of what `shop-domain` header accompanies it.

An unprivileged internet user who legitimately controls a Shopify store subscribed to the app (i.e., who can receive genuine webhooks addressed to their own shop, generated with the real `api_secret_key`) can capture one such (body, HMAC) pair and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header rewritten to a victim shop. The equality the code is supposed to enforce is:
`HMAC(body) valid ⇒ shop header == shop that produced this payload`
but the actual guarantee provided is only:
`HMAC(body) valid ⇒ body was produced under api_secret_key` (shop unconstrained).

`Registry.process` never independently confirms that `request.shop` corresponds to a shop that is actually installed/authorized to send this topic; it simply forwards `request.shop` into `WebhookMetadata` for the app's handler to act on [7](#0-6) , and the gem's own test suite demonstrates that `data.shop` is expected to come straight from the header value with no additional cross-check [8](#0-7) .

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` to key data updates, uninstall/GDPR flows, or shop-scoped resource lookups (the intended purpose of the field, per the docs) is exposed to cross-tenant data confusion: a merchant with a legitimate, cheap-to-obtain webhook subscription can forge webhook deliveries that the receiving app attributes to a different merchant's shop. Depending on the handler's logic, this can lead to writing/mutating data under another tenant's identity, triggering shop-scoped side effects (e.g., uninstall webhooks like `app/uninstalled`, `customers/redact`) for a shop that never sent them, or bypassing shop-based authorization checks that trust `WebhookMetadata#shop`. This matches the required "cross-tenant access" impact category.

### Likelihood Explanation
Medium: it requires the attacker to control at least one shop that has installed the target app and can receive real webhooks (a normal, unprivileged capability — anyone can install a public app or, for a private/dev app, obtain a dev store), then intercept/replay HTTP requests with a modified header, which is trivial for a webhook the attacker's own store originated.

### Recommendation
Include `shop` (and ideally `topic`) in the signable string used for webhook HMAC verification, or otherwise cryptographically bind the shop identity to the payload before trusting `request.shop` in `Registry.process`. At minimum, document and encourage app authors to cross-check `request.shop` against a shop known to be installed/session-stored before acting on webhook data, since the gem currently provides no such binding itself.

### Proof of Concept
1. Attacker owns `attacker-shop.myshopify.com`, which has installed the victim app and is subscribed to a webhook topic (e.g., `customers/redact` or `orders/create`).
2. Shopify sends a legitimate webhook to the app with body `B`, headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: valid_hmac(B)`.
3. Attacker intercepts this request (they receive it directly, since it's addressed to their own endpoint/shop) and resends it to the app's webhook endpoint, but with `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and the same body `B` and same `valid_hmac(B)`.
4. `Utils::HmacValidator.validate(request)` recomputes HMAC over `B` only (`to_signable_string` = `@raw_body`) [1](#0-0)  and it matches, since `shop` isn't part of the signed data.
5. `Registry.process` proceeds and calls the topic handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)` [7](#0-6) , causing the app to process attacker-controlled webhook data as if it belongs to `victim-shop.myshopify.com`.
