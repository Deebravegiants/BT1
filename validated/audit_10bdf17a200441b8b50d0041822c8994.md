## Finding

The webhook signature verification in this gem binds only the request body to the HMAC, but the `shop` (and `topic`) values are read from unauthenticated headers and handed to the merchant's webhook handler unchecked. This mirrors the report's bug class: a field used to identify the actor/tenant ("shop") is not covered by the same integrity check that authenticates the request.

### Root cause

`ShopifyAPI::Webhooks::Request#to_signable_string` returns **only** `@raw_body`: [1](#0-0) [2](#0-1) 

`shop` and `topic` are pulled straight from HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`), which are attacker-controlled input to any HTTP request the app receives, and are never included in the signed string: [3](#0-2) 

`Utils::HmacValidator.validate` only checks `hmac` against `to_signable_string`, i.e., against the raw body alone: [4](#0-3) 

`Webhooks::Registry.process` trusts `request.shop` (and `request.topic`) once that body-only HMAC passes, and forwards it directly to the app's handler as the tenant identifier for the event: [5](#0-4) 

### The broken binding

The intended invariant is:
`shop_authenticated_by_hmac == shop_delivered_to_handler`

But because `to_signable_string` only covers `@raw_body`, the equality that actually holds is:
`hmac_valid_for(raw_body) ⇏ shop_header_is_authentic`

An attacker who has ever legitimately received one webhook for their own shop (any merchant who installs the app gets real webhooks with valid `hmac-sha256` signatures computed over their own body) possesses a valid `(raw_body, hmac)` pair signed with the app's real secret. They can replay that exact body and hmac to the app's public webhook endpoint while swapping only the `x-shopify-shop-domain` header to a victim shop's domain (and/or the `x-shopify-topic` header). `HmacValidator.validate` still succeeds because it never looks at those headers, and `Registry.process` dispatches to the handler with `shop: request.shop` set to the attacker-chosen victim domain, alongside attacker-controlled body content that the app believes came from Shopify for the victim shop.

This breaks the tenant-identity binding: the field acted upon by the host app (`shop`) is not covered by the cryptographic check (`hmac`) that is supposed to authenticate the whole message as genuinely originating from Shopify for that shop.

### Impact

Cross-tenant confusion/injection: a malicious but otherwise unprivileged app user (any shop that has installed the app) can cause the host application to process forged event data as if it belongs to a different, victim tenant, without ever needing the app's `api_secret_key`, an access token, or network interception — only a normal webhook delivery they legitimately received for their own shop.

### Recommendation

Include `shop`, `topic`, and `webhook_id`/`api_version` in the signed string (or otherwise cryptographically bind them to the HMAC), so the entire identity of the webhook — not just its body bytes — is authenticated before being handed to the handler. [6](#0-5)

### Title
Webhook `shop`/`topic` identity headers not covered by HMAC verification allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw body, while `shop` and `topic` come from unauthenticated headers and are trusted by `Webhooks::Registry.process` for dispatching to the app's handler.

### Finding Description
The HMAC validation in `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) computes/verifies the signature only over `verifiable_query.to_signable_string`, which for webhooks is `@raw_body` alone (`lib/shopify_api/webhooks/request.rb:35-38`). The `shop` and `topic` accessors read directly from HTTP headers (`lib/shopify_api/webhooks/request.rb:15-23`) which are not part of the signed content. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) uses `request.shop` and `request.topic` — post-HMAC-validation — to build the `WebhookMetadata` passed to the app's handler, treating them as trustworthy identifiers of which shop/tenant the event belongs to.

### Impact Explanation
Any actor who has legitimately received one authentic webhook (a valid `(raw_body, hmac)` pair signed with the app's shared secret for their own shop) can replay it to the app's public webhook endpoint while altering only the `shop-domain`/`topic` headers. The HMAC still validates, and the host app processes attacker-supplied event data attributed to a shop the attacker doesn't own — a cross-tenant identity/data confusion that the app has no way to detect since the gem's HMAC check gives it a false assurance that the entire request (including `shop`) is authentic.

### Likelihood Explanation
Any app user who has installed the target app on some shop qualifies as an "unprivileged internet user" relative to other tenants of the same app; they need no `api_secret_key`, no access token, and no network interception — just the ability to POST to the app's public webhook URL, which is by design internet-reachable.

### Recommendation
Bind `shop`, `topic`, `webhook_id`, and `api_version` into the HMAC-signed string (e.g., by including these header values in `to_signable_string`), so the full identity of the webhook is authenticated, not just its body bytes.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. body `{"id":1}` with header `x-shopify-hmac-sha256: <valid_hmac_for_body>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays the identical body and `hmac-sha256` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` succeeds because it only checks the (unchanged) body against the hmac.
4. `Webhooks::Registry.process` calls the app's handler with `shop: "victim-shop.myshopify.com"` and the attacker's body, causing the host app to act as though this data came authentically from the victim shop.

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }
      def shopify_header(name)
        @headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]
      end
    end
  end
end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
