### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
The external report describes a `forceWithdraw` accounting bug where a value that is *acted upon* (the withdrawn amount) is never *bound into* the ledger update (`tokenTotalOnLine`/`totalOnLine`), breaking an invariant between what's tracked and what's real. The structural analog in this gem is `ShopifyAPI::Webhooks::Request`: the field that identifies the tenant (`shop`) is acted upon by the webhook dispatch pipeline, but it is not part of the bytes covered by the HMAC signature.

### Finding Description
`Webhooks::Request#hmac` returns the value from the `x-shopify-hmac-sha256`/`shopify-hmac-sha256` header, and `to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

`Utils::HmacValidator.validate` only checks that `HMAC(secret, raw_body) == received_signature`: [3](#0-2) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated headers via `shopify_header`, entirely outside the HMAC-covered byte range: [4](#0-3) [5](#0-4) 

`Registry.process` validates the HMAC (over the body only) and then dispatches `request.shop` to the host app's handler as the authoritative tenant identifier, without any check that `shop` is bound to the signed body: [6](#0-5) 

This is the exact bug class from the report: the field acted on (`shop`, used to route/attribute the webhook to a tenant) is not the field covered by the integrity check (`raw_body` only), so the identity binding `shop_verified == shop_dispatched` does not hold. An attacker who can reach the app's webhook endpoint and replay/craft a request with a body that matches a topic they know the correct HMAC for (e.g., because they control that request/replay a captured one) can substitute the `shop` header to attribute the payload to a different tenant, since `shop` never enters the signature computation.

### Impact Explanation
This is a cross-tenant issue: the host application's webhook handler receives `WebhookMetadata` with a `shop` value that has no cryptographic binding to the verified payload, so a handler that trusts `request.shop`/`data.shop` for tenant attribution (a documented, intended usage per `WebhookMetadata`) can process data under the wrong tenant's identity. Per the rules, this maps to the "Critical - cross-tenant access" impact category, since it breaks the equality `shop_in_signed_bytes == shop_used_for_tenant_routing`.

### Likelihood Explanation
Exploitability depends on the attacker being able to submit a request to the app's webhook endpoint with an independently valid HMAC for a chosen body while controlling/substituting the `shop` header — this requires either a captured/replayable Shopify-signed webhook body (no secret needed since HMAC only covers body, not shop) or the ability to trigger a webhook for a shop the attacker controls and then present it with a different shop header value pointed at another tenant's endpoint (only relevant to multi-tenant apps hosted on shared infra where the same endpoint serves all shops). This is a real, credential-free manipulation of an unauthenticated header field, making it moderately likely for any app that trusts `request.shop` from `Webhooks::Request` without additional verification.

### Recommendation
Include `shop` (and ideally `topic`, `webhook_id`, `api_version`) in the HMAC-covered signable string, or independently verify that the `shop` header matches a value derived from data inside the signed body/known registration, before dispatching `WebhookMetadata` to handlers. At minimum, document/enforce that `to_signable_string` binds the full set of trust-sensitive headers, not just the raw body, mirroring the fix pattern in the report (explicitly re-binding the value being acted upon into the accounted/verified state).

### Proof of Concept
1. Capture (or otherwise obtain) a valid Shopify webhook POST for shop A, including its raw body and `x-shopify-hmac-sha256` value — the HMAC is valid because `HMAC(secret, raw_body)` only depends on `raw_body`.
2. Replay the same request to the app's webhook endpoint, but modify the `x-shopify-shop-domain` header to shop B's domain, leaving `raw_body` and the `hmac` header untouched.
3. `Utils::HmacValidator.validate(request)` in `Registry.process` succeeds because it only hashes `@raw_body`: [2](#0-1) 
4. `Registry.process` dispatches `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `request.shop` == shop B, even though the verified payload actually originated for shop A: [7](#0-6) 
5. Any handler that trusts `shop` for tenant-scoped side effects (e.g., writing to shop B's data store using shop A's payload) now operates cross-tenant.
