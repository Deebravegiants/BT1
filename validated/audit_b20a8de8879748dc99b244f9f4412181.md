### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then dispatches the handler using the `shop` value taken from the `X-Shopify-Shop-Domain` HTTP header — a field that is never included in the HMAC-signed material. The identity binding the code implicitly relies on (`hmac-verified bytes == the shop the payload is attributed to`) does not actually hold, because the HMAC covers only `@raw_body`, not the `shop-domain` header.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`to_signable_string` — the only material fed into the HMAC comparison — returns just the raw JSON body: [2](#0-1) 

`HmacValidator.validate` computes/compares the signature strictly over that signable string: [3](#0-2) 

`Registry.process` treats a passing HMAC check as sufficient authorization to dispatch the webhook to the handler, and hands the handler the unauthenticated `request.shop` value directly: [4](#0-3) 

The equality the code needs to hold is:
`shop bound by the verified HMAC == shop attributed to the WebhookMetadata dispatched to the handler`

In reality:
`shop bound by the verified HMAC == "" (nothing — the header is outside the signed bytes)`
`shop attributed to the WebhookMetadata == whatever value is present in the shop-domain header`

Because every shop installation of a given app shares the same `api_secret_key`, any webhook payload validly HMAC-signed for one tenant (e.g., one the attacker controls, since they can trigger events like `orders/create` on their own store and observe/replay the signed body) remains HMAC-valid when replayed to the app's webhook endpoint with the `shop-domain` (and `topic`/`webhook-id`) headers rewritten to point at a different, victim tenant. `Registry.process` has no independent check that the claimed `shop` is one that actually produced the signed body, so the handler is invoked believing the data belongs to the victim shop.

### Impact Explanation
This breaks the tenant boundary the webhook handler relies on: an app can be made to process attacker-supplied webhook data (topic, JSON body, webhook id) while believing it originates from a different merchant's shop. Depending on what the host application's webhook handler does with `WebhookMetadata#shop` (e.g., looking up/mutating that shop's stored session, triggering shop-scoped side effects, updating billing/state keyed by shop), this can lead to cross-tenant data confusion or corruption — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to be an app user on at least one store (to obtain any validly-signed webhook body under the app's shared secret) and to know/target the victim's `myshopify.com` domain (which is generally discoverable/public). No access token, no `client_secret`, and no privileged account is required beyond ordinary use of the app on the attacker's own store. This is a realistic, low-friction scenario for any multi-tenant Shopify app built on this gem.

### Recommendation
Do not trust `X-Shopify-Shop-Domain` (or `webhook-id`/`topic`) as authenticated identity data. At minimum, the gem should document/enforce that consumers must independently verify the `shop` from the webhook against a known/authorized shop list (e.g., an existing offline session for that shop) before acting on `WebhookMetadata`, or extend `VerifiableQuery`/`to_signable_string` for webhooks to bind the relevant headers into the integrity check where Shopify's webhook signing scheme allows it.

### Proof of Concept
1. Install the target app on an attacker-owned store `attacker.myshopify.com`; trigger a webhook event (e.g. `orders/create`) and capture the raw POST: body `B` and header `X-Shopify-Hmac-Sha256: H = HMAC-SHA256(secret, B)`.
2. Replay the captured request to the app's webhook endpoint, keeping `body = B` and `X-Shopify-Hmac-Sha256: H` unchanged, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds (it only checks `HMAC(secret, B) == H`), and `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the host app to treat attacker-controlled data as belonging to the victim shop.
