### Title
`SignedDelegateAction` signatures lack chain/network binding, allowing cross-deployment signature replay - (File: `core/primitives/src/signable_message.rs`, `core/primitives/src/action/delegate.rs`)

### Summary
NEAR's meta-transaction (NEP-366/NEP-611) signature scheme signs a `DelegateAction` under a `SignableMessage` whose only domain-separation input is a fixed NEP-number discriminant. Neither the discriminant nor the `DelegateAction` payload itself contains any network/chain identifier (no `chain_id`, `genesis_hash`, or similar). This mirrors the Hermez `_checkSig` finding: the signed digest is portable across any deployment that shares the same message schema, enabling signature reuse across forks/instances of the protocol.

### Finding Description
`SignableMessage::sign` computes `hash(borsh(SignableMessage{discriminant, msg}))` and signs that hash with the account's private key. [1](#0-0) 
The `discriminant` only encodes a NEP number (366 or 611) plus on/off-chain classification — it is a protocol/message-type separator, not a chain/network separator. [2](#0-1) [3](#0-2) 

The `DelegateAction` struct itself carries `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key` — again, nothing that ties the signed bytes to a specific chain instance (no genesis hash, no chain id). [4](#0-3) 

Verification (`SignedDelegateAction::verify` / `VersionedSignedDelegateAction::verify`) only checks the ed25519 signature against this chain-agnostic hash; it performs no comparison against any chain-specific value. [5](#0-4) [6](#0-5) 

On-chain acceptance in `validate_delegate_action_key` relies purely on local state: the access key's current `nonce` for `(sender_id, public_key)` on that chain, and `max_block_height` versus the local `apply_state.block_height`. [7](#0-6) 
None of these checks reference a genesis hash or chain identifier — replay protection is entirely local-nonce-based, not chain-binding-based.

Because NEAR account ids for implicit accounts are deterministically derived from the public key alone, and separately deployed/forked networks running the same nearcore protocol independently maintain their own account/access-key state, the exact same `(DelegateAction, Signature)` bytes that validate on one chain can also validate on a different chain (or a re-genesised/forked instance) as long as the sender's access key on that other chain happens to be at a compatible nonce state (e.g., a freshly created account, or one deliberately kept in sync by an attacker). This is structurally identical to the Hermez issue: the signed payload has no field binding it to "this exact contract instance/fork," so it is portable to any environment implementing the same verification schema.

### Impact Explanation
An attacker who controls or influences a second deployment (a testnet, a private fork, or any nearcore-compatible chain) sharing the same public key/account namespace can capture a `SignedDelegateAction` a victim believed was scoped to one network and replay it on another where they control preconditions (e.g., pre-arranging the access key nonce). Because a `DelegateAction` can wrap arbitrary actions executed with the sender's authority (transfers, function calls, key management, etc., subject to the access key's permissions), a replayed signature can result in unauthorized actions being executed against the victim's account on the other chain — an unauthorized state/balance change under the victim's identity, without the victim intending it for that chain.

### Likelihood Explanation
Exploitation requires a concrete scenario where the attacker can arrange matching access-key state (particularly nonce) between two nearcore-based deployments — e.g., a relayer or wallet reusing signed meta-transactions across mainnet/testnet/private forks, or a malicious "test" deployment set up specifically to harvest reusable signatures (directly parallel to the Hermez exploit scenario "Eve forks Hermez ... asks Bob to test on newly deployed contract ... replays on original contract"). This is a real but conditional vector: it depends on ecosystem/tooling behavior (whether wallets/relayers reuse the same access key nonce across networks or allow such cross-network signing flows) rather than a flaw exploitable purely from a single chain's transaction pool. Still, it is reachable through standard submitted transactions/RPC (`SignedDelegateAction` embedded in `Action::Delegate`/`Action::DelegateV2`) with no privileged/validator access required.

### Recommendation
Bind the signed digest to the specific chain instance by including a chain-identifying value (e.g., genesis hash or a protocol-defined `chain_id`) inside `SignableMessage` or `DelegateAction` itself, so that `SignableMessage::sign`/`verify` incorporate this value into the hashed payload. This ensures a `SignedDelegateAction` produced for one nearcore deployment cannot be verified as valid on any other deployment or fork, closing the cross-instance replay path analogous to EIP-712-style domain separators (`chainId`, `verifyingContract`).

### Proof of Concept
1. User Alice signs a `DelegateAction` (via `SignableMessage::sign`/`VersionedSignedDelegateAction::sign`) intended for Chain A, using her implicit-account public key and an access key with `nonce = N`. [8](#0-7) 
2. The resulting `(DelegateAction, Signature)` bytes contain no chain-identifying data — only `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key`, and a NEP-based discriminant. [4](#0-3) 
3. An attacker who obtains this signed payload (e.g., by operating a second, forked nearcore chain — "Chain B" — where the same implicit account exists with an access key at the same nonce `N`) submits the identical `SignedDelegateAction` inside an `Action::Delegate`/`Action::DelegateV2` transaction on Chain B.
4. `validate_delegate_action_key` on Chain B only checks local nonce/`max_block_height`/access-key state — both of which the attacker arranged to match — and the borsh-identical signature verifies successfully via `verify()`, since nothing in the hashed message distinguishes Chain A from Chain B. [7](#0-6) 
5. Alice's delegated actions execute on Chain B under her authority without her having intended or authorized that specific chain — a direct analog of the Hermez signature-reuse exploit.

**Uncertainty note:** I could not fully verify within the available context whether any additional out-of-band binding (e.g., wallet/RPC-layer enforcement of a specific network endpoint, or a genesis-hash check elsewhere in the client/relayer stack outside `runtime/runtime/src/actions.rs`) mitigates this in practice; the core protocol-level signing/verification code shown above does not include such a check.

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
}
