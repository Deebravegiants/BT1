### Title
Missing length validation on `message.from` causes a slice-index/`copy_from_slice` panic in `HyperFungibleToken::on_accept` — ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
`pallet-hyper-fungible-token`'s `on_accept` validates the length of the ABI-decoded `message.to` field (must be 20 or 32 bytes) before using it, but performs **no equivalent length check on `message.from`** before slicing/copying it into a fixed-size buffer when calldata execution is requested without a signature.

### Finding Description
In `on_accept`, `message.to` is explicitly validated: [1](#0-0) 

But when `message.data` is non-empty and no signature is supplied, `message.from` is consumed with no length check: [2](#0-1) 

- If `source.is_evm()` and `from_bytes.len() < 20`, `from_bytes.len() - 20` underflows `usize`, which panics (or, if overflow checks are compiled out, wraps to a huge index and then panics on out-of-bounds slicing).
- If `source` is not EVM, `account.copy_from_slice(from_bytes)` panics unconditionally unless `from_bytes.len() == 32` exactly (`copy_from_slice` requires equal lengths, unlike the checked branches used for `to_bytes`).

`message` itself is fully attacker-controlled ABI-decoded data (`Message::abi_decode(&body)` at line 59) coming from the ISMP request body — the only authentication performed is that the *ISMP envelope's* `from`/`source` pair maps to a registered asset via `ContractToAsset`; the `message.from` field inside the ABI payload is not required to equal, or have any relationship to, that on-chain sender. A malicious sender contract on the source chain (or a message crafted by the source-chain app) can set `message.from` to an arbitrary-length byte string and pair it with any non-empty `message.data` and a `substrate_data.signature = None`, reaching the unchecked slice/copy.

This is directly analogous to the CVE's bug class: a length/tag-derived field is used to index/copy into a fixed-size buffer without validating that the field's length matches what the buffer expects, which is exactly the missing-bounds-check pattern in MFER tag parsing that caused the stack overflow.

### Impact Explanation
`on_accept` is invoked from the ISMP request-handling path (`modules/ismp/core/src/handlers/request.rs`, `execute`/`lambda` closure), which any relayer can trigger via `handle`/`handle_unsigned` once the corresponding source-chain state/membership proof is available: [3](#0-2) 

A Rust panic inside this closure is not a recoverable `Err` — it unwinds/traps the runtime call rather than being caught and converted into a request-receipt rollback. Because requests are processed in a batch (`msg.requests.into_iter().map(...)`), a single crafted malicious request can abort processing of the entire batch, preventing legitimate requests bundled with it from being delivered. This satisfies the "route unable to deliver messages" impact category: a relayer including this payload (accidentally or maliciously) can repeatedly disrupt message delivery for the `HyperFungibleToken` module and any other requests batched alongside it.

### Likelihood Explanation
Reaching the vulnerable branch requires: (1) a message dispatched to a chain's `HyperFungibleToken` pallet from a source contract already registered in `ContractToAsset` (an existing, legitimate bridge deployment — not attacker-created), (2) `message.data` non-empty, and (3) the decoded `SubstrateCalldata.signature` field set to `None`. All three conditions are controllable by whoever can call the legitimate bridge contract's send function with arbitrary calldata/payload bytes on the source chain, which for a permissionless bridge is any user. This makes the trigger straightforward once the pallet is deployed with an active EVM<->Substrate mint/transfer route, though it does depend on the specific field layout of `SubstrateCalldata`/`Message` construction in the sending app, which was not fully confirmed against the Solidity `HyperFungibleToken.sol` source in this pass.

### Recommendation
Validate `message.from`'s length exactly the way `message.to` is validated before use — reject with `HftError::InvalidRecipientLength`/an equivalent error for any length other than 20 (EVM) or 32 (non-EVM), and use `try_into()`/checked slicing instead of `from_bytes.len() - 20` and `copy_from_slice` so malformed input returns a descriptive `Err` instead of panicking.

### Proof of Concept
1. From a registered source-chain `HyperFungibleToken` sender contract, dispatch a POST request whose ABI-encoded body decodes to a `Message` where:
   - `to` is a valid 20-byte address (passes the `to` check),
   - `data` is non-empty and decodes to `SubstrateCalldata { signature: None, runtime_call: <any> }`,
   - `from` is set to a byte string of length ≠ 20 (e.g., empty or 5 bytes) when `source` is EVM, or ≠ 32 bytes when `source` is not EVM.
2. Relay this request (with its valid state/membership proof) via `handle`/`handle_unsigned`.
3. `on_accept` reaches `from_bytes[from_bytes.len() - 20..]` (underflow panic) or `account.copy_from_slice(from_bytes)` (length-mismatch panic), aborting execution instead of returning a graceful `Err`, which prevents this and any batched requests from being processed by the relayer's transaction.

Note: I was unable to fully confirm within the available search passes whether the Solidity-side `HyperFungibleToken.sol`/`HyperFungibleTokenUpgradeable.sol` contracts constrain the `from` field to `msg.sender` (20 bytes) at construction time, which would affect whether this is reachable purely by calling the official contract normally versus requiring a custom/malicious sender contract already registered in `ContractToAsset`. This should be verified against `sdk/packages/core/contracts/apps/HyperFungibleToken.sol` before treating likelihood as fully confirmed.
