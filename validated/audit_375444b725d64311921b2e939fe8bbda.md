### Title
Fee-on-Transfer Input Tokens Break Escrow Accounting in Tron IntentGatewayV2's `placeOrder` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The DIP exploit desynced an AMM pair's on-chain reserve from its true token balance by exploiting fee-on-transfer transfer semantics combined with `skim`/`sync`, then drained the manipulated pool. The Tron variant of Hyperbridge's Intent Gateway has an analogous accounting flaw: in `placeOrder`'s non-predispatch escrow path, the contract credits `_orders[commitment][token]` using the user-declared nominal input amount (minus only the protocol fee), without ever measuring the token balance actually received via `safeTransferFrom`. For any fee-on-transfer ERC20/TRC20 used as an order input, this inflates the gateway's internal escrow ledger above its real token balance, letting the shared token pool be drained beyond what was actually deposited.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`, the non-predispatch escrow branch is: [1](#0-0) 

```solidity
} else {

```

`reducedInputs[i].amount` is derived purely from the user-declared `order.inputs[i].amount` minus the protocol fee basis points — it is never reconciled against the token balance actually transferred in: [2](#0-1) 

There is no `balanceOf` check before/after the `safeTransferFrom` call in this branch, unlike the sibling `predispatch` branch a few lines above which does compute `dust = balance - requiredAmount` from actual dispatcher balances. For a fee-on-transfer token, `safeTransferFrom` delivers `order.inputs[i].amount − tokenFee` to the contract, but the escrow ledger `_orders[commitment][token]` is credited with `order.inputs[i].amount − protocolFee`, which is strictly larger whenever the token's own transfer fee exceeds zero. `_orders` is a **shared per-token pool** — every order using the same input token draws from and credits into the same real contract balance — so this per-order overcredit compounds across all orders in that token.

This is a regression relative to the hardened logic already present in the primary EVM contract, which explicitly measures actual received balance for exactly this reason: [3](#0-2) 
```solidity
        // Phase 1: Transfer tokens and record actual received amounts.
        // For fee-on-transfer tokens, the gateway receives less than the requested amount.
        // We mutate order.inputs to reflect actual received so the commitment and escrow
        // are consistent with what the gateway holds.
```

and confirmed by the round-trip test suite for the main contract: [4](#0-3) 

The Tron variant's non-predispatch path lacks this reconciliation entirely — the `withdraw()` function later blindly transfers `_orders[commitment][token]` worth of tokens out regardless of whether that much token balance genuinely exists: [5](#0-4) 

### Impact Explanation
Because `_orders[commitment][token]` is a shared accounting bucket for a given token across all orders, one order placed with a fee-on-transfer token inflates the ledger beyond the actual on-chain balance. When the escrow is later released via `withdraw()` — triggered by `fillOrder`'s cross-chain `RedeemEscrow` message, `cancelOrder`'s `RefundEscrow`, or the GET-response cancellation path — the transfer of `body.tokens[i].amount` can:
1. Succeed for early redeemers by consuming real balance that was actually deposited by *other* users' orders on the same token, leaving later, legitimate orders' `withdraw()` calls to revert on insufficient balance — a permanent freeze of those users' escrowed funds; or
2. Allow an attacker to place and then immediately cancel/refund an order with a fee-on-transfer token, extracting more tokens than they net-deposited, effectively siphoning value from the shared pool contributed by unrelated orders.

Both outcomes match the required impact bar: concrete theft of escrowed funds or permanent freezing of other users' funds, reachable from a single unprivileged `placeOrder`/`cancelOrder` transaction — no admin, governance, or relayer collusion required.

### Likelihood Explanation
Likelihood is high wherever this Tron deployment permits fee-on-transfer TRC20/ERC20-style tokens as order inputs (nothing in `placeOrder` rejects such tokens). Any user can trigger the divergence by simply placing an order with such a token; no special timing, governance action, or privileged role is required. The bug is deterministic given the token's fee rate.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: measure `IERC20(token).balanceOf(address(this))` before and after each `safeTransferFrom` in the non-predispatch branch of `placeOrder`, use the *actual received* delta (not the nominal `order.inputs[i].amount`) as the basis for `reducedInputs[i].amount` and the commitment hash, and only credit `_orders[commitment][token]` with that reconciled amount.

### Proof of Concept
1. Deploy a fee-on-transfer TRC20 token `FOT` with a nonzero transfer fee (e.g., 1%), analogous to the DIP token in the referenced report.
2. Attacker calls `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs[0] = {token: FOT, amount: 1000e18}` and no predispatch calldata.
   - `safeTransferFrom` delivers only `990e18` to the contract (1% fee burned/redirected by the token).
   - `reducedInputs[0].amount` is computed as `1000e18 - protocolFee` (e.g., `990e18` at 1% protocol fee, coincidentally, or higher if `protocolFeeBps` is 0) and is stored in `_orders[commitment][FOT]`.
   - If `protocolFeeBps == 0`, `_orders[commitment][FOT] == 1000e18` even though the contract only holds `990e18` of real balance from this order.
3. Attacker calls `cancelOrder` before any fill. `withdraw()` transfers `_orders[commitment][FOT] == 1000e18` to the attacker via `token.call(transfer, ...)`.
4. If the contract's total `FOT` balance (from this and other concurrent orders) covers `1000e18`, the transfer succeeds, and the attacker has extracted `10e18` more `FOT` than they net-deposited — funded out of other users' escrowed `FOT` balances, which will later fail to redeem for insufficient balance.
