### Title
Bad-debt supply-index write-down clamps upward to `SUPPLY_INDEX_FLOOR_RAW`, resurrecting unbacked supply claims that drain later cash - ([File: contracts/pool/src/interest.rs](contracts/pool/src/interest.rs))

### Summary
The tiffcrop CVE is an out-of-bounds write: a computed size escapes its valid domain and corrupts adjacent state. The XOXNO Lending analog is a write that escapes its mathematical bound in `apply_bad_debt_to_supply_index`. When a bad-debt write-off meets or exceeds the whole supplied value, the correct reduction factor is zero — but the function clamps the new supply index *up* to `RAY / 1000`. That writes a residual RAY-index value onto shares that were fully wiped, leaving "phantom" supply claims backed by nothing. The repo's own tests demonstrate that once cash exists in the market again, those residual claims withdraw real tokens that belong to fresh suppliers or recapitalizers.

### Finding Description
`contracts/pool/src/interest.rs::apply_bad_debt_to_supply_index` computes `reduction_factor = (total_supplied_value - min(bad_debt, total_supplied_value)) / total_supplied_value` and then:

```rust
cache.set_supply_index(new_supply_index.max(Ray::from(SUPPLY_INDEX_FLOOR_RAW)));
```

On a full wipeout (`bad_debt >= total_supplied_value`), `reduction_factor` floors to 0, so `new_supply_index` is 0 — the write that *should* be recorded. The `.max(SUPPLY_INDEX_FLOOR_RAW)` clamp overrides it, storing `RAY/1000` instead. Every supply share in that market retains 1/1000th of a RAY-unit claim it no longer has. This is a store past the end of the valid range: the arithmetic bound is `[0, old_index]`, and the clamp writes a value strictly above what the math permits.

`clean_bad_debt` is permissionless (dust-threshold cleanup path on the controller) and `seize_positions` on the pool drives `apply_bad_debt_to_supply_index` plus `burn_debt`. The wipeout is reachable whenever an account's ceiled debt value approaches the market's total supplied value — naturally at the dust/eligibility boundary (`clean_bad_debt` requires remaining collateral ≤ ~$5, i.e., nearly the entire debt is written down).

After the clamp, `unscale_supply_floor(held_scaled)` still returns a positive claim for wiped suppliers (`interest.rs:73-88`). Withdrawal goes through `Cache::resolve_withdrawal` + `require_reserves`, which only checks `cash`, not whether the index ever legitimately supported the claim. The harness tests `test_raw_cache_floor_residual_can_consume_fresh_cash_without_supply_guard`, `test_raw_cache_floor_clamp_strands_claim_without_supply_guard`, and `test_raw_cache_seizure_residual_would_drain_fresh_cash_without_supply_guard` in `contracts/pool/tests/interest.rs` each show the stranded holder extracting exactly a subsequent deposit's cash, leaving the honest supplier's claim unpayable.

The residual is fillable because `recapitalize` injects cash without minting shares (documented in `contracts/pool/README.md` and `docs/reference/formulas.md`), and direct token transfers to the pool are in scope — the backing gate on `supply` blocks *new minting*, but any path that raises `cash` (recapitalization, repayments of surviving debt legs, direct transfers absorbed into reserves) makes the phantom claim withdrawable.

### Impact Explanation
Theft of user funds. A wiped-out supplier — or any attacker who held supply shares in the affected market before `clean_bad_debt` — keeps a positive withdrawable balance that should be zero. Each unit of cash later added to the market (recapitalization, fresh repayment flows) can be withdrawn by phantom claims until drained, directly transferring value from recapitalizers/honest suppliers to the holder of unbacked shares. `docs/reference/formulas.md` itself acknowledges the hazard: "The non-zero floor can leave residual claims without backing."

### Likelihood Explanation
Medium. The trigger requires a bad-debt event where the written-down debt meets/exceeds total supplied value in that (hub, token) book — reachable on small or thin markets, and easiest via the permissionless `clean_bad_debt` path whose eligibility gate (tiny residual collateral) guarantees near-total write-down. Exploitation then needs cash to re-enter the market before the stranded shares are withdrawn, which is precisely what `recapitalize` does by design. No privileged role is required at any step for the share-holder who withdraws.

### Recommendation
Distinguish "no time elapsed / tiny write-down" from "full wipeout" instead of unconditionally clamping. Options:

- When `capped == total_supplied_value` (full wipeout), burn or zero all supply shares / set `supplied` and `revenue` consistently rather than resurrecting them at the floor index; the floor exists to avoid a zero index for *partial* write-downs, not to recreate claims after a total loss.
- Alternatively, gate `resolve_withdrawal`/withdraw on `supply_index > SUPPLY_INDEX_FLOOR_RAW` for markets whose index was clamped from a wipeout, or track a `wiped` flag in `PoolStateRaw` that forces `unscale_supply_floor` to zero until `recapitalize` restores backing.
- At minimum, ensure `recapitalize` and any cash-crediting path cannot be front-run by stranded-share withdrawals — e.g., burn residual `supplied` shares at clamp time so `supplied * floor_index` yields no claim.

### Proof of Concept
Established by the repository's own regression tests:

1. `contracts/pool/tests/interest.rs:298-314` (`test_apply_bad_debt_exactly_at_total_supplied_hits_cap_and_floor`): `apply_bad_debt_to_supply_index` with `bad_debt == total supplied` sets `supply_index = SUPPLY_INDEX_FLOOR_RAW` instead of 0.
2. `contracts/pool/tests/interest.rs:317-369`: after the wipeout clamp, a holder of the old scaled shares withdraws `gross == c` — exactly a fresh supplier's deposit — leaving `cash < fresh_claim`.
3. `contracts/pool/tests/interest.rs:431-495`: same drain via the `seize_positions`-shaped path (`apply_bad_debt_to_supply_index` + `burn_debt`), confirming the residual survives the production bad-debt entry.

Concrete unprivileged sequence:

1. Attacker supplies `S` of token X in a thin market; victim borrows/creates bad debt (or attacker engineers an insolvent dust position via price move within oracle bands).
2. Attacker calls `clean_bad_debt` on the dust account; pool executes `apply_bad_debt_to_supply_index(bad_debt >= total_supplied)` → `supply_index` clamped to `RAY/1000`.
3. Anyone (or attacker via `recapitalize`, or organic repayments) adds cash to the market.
4. Attacker calls `withdraw` on their `S` scaled shares; `resolve_withdrawal` pays `S * RAY/1000` worth of real tokens that have no backing — stolen from the recapitalizer/fresh suppliers.

Caveat: the tests note a hypothetical "supply guard"; production does block *new supply* under a backing shortfall, but no code found blocks *withdrawal of the residual claim* once cash exists, and `recapitalize` is explicitly designed to inject that cash. If a dedicated wipeout flag exists outside the indexed sources, the residual-withdrawal leg would need re-verification against full file contents.
