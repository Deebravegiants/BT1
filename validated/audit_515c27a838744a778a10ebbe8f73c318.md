### Title
Webhook `shop` (tenant identity) is not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (tenant identifier) that is handed to the app's webhook handler is read directly from an HTTP header that is never part of the signed material. This breaks the binding between "the bytes that were HMAC-verified" and "the shop the app believes the webhook came from," letting an attacker with a genuine webhook delivery for their own store relabel it as coming from any victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, independent of the signed body: [2](#0-1) 

`Registry.process` verifies the HMAC and, on success, immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler, without any further check that the shop matches the signed payload: [3](#0-2) 

`HmacValidator.validate` only ever authenticates `verifiable_query.to_signable_string` (here, the raw body) against `verifiable_query.hmac`: [4](#0-3) 

The equality that should hold is:
`shop_bound_by_hmac == shop_delivered_to_handler`

but the actual check performed is only:
`hmac(raw_body) == received_hmac`

with `shop_delivered_to_handler` taken unverified from a header. Since `shop-domain` is not part of `to_signable_string`, any two values of the header produce the same valid HMAC for a given body, so the two sides of the equality are never actually compared.

### Impact Explanation
An attacker who owns/controls a Shopify store can subscribe their own store to a webhook topic and receive a genuine webhook delivery with a valid `X-Shopify-Hmac-Sha256` signature over the body. Because the header is not signed, the attacker can replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `Utils::HmacValidator.validate` will still pass (it only checks the body), and `Registry.process` will invoke the registered handler with `WebhookMetadata#shop` set to the victim's domain. Any app logic that uses this `shop` value to look up per-tenant state, attribute data, or make authorization decisions (e.g., GDPR `customers/redact`, `shop/redact`, order/customer processing) will act on attacker-supplied data under the identity of a different tenant — a cross-tenant confusion/access issue.

### Likelihood Explanation
The attacker only needs their own (even free/trial) Shopify store to obtain a validly-signed webhook body — no access to the app's `api_secret_key`, access tokens, or the victim's credentials is required. The replay itself is a straightforward HTTP request with a modified header, satisfying the "unprivileged internet user" bar. This is reachable through the gem's own documented `Registry.process` entry point.

### Recommendation
Bind the shop domain into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived `shop` to the signed body/topic (e.g., verify the shop against a known/expected session or registration rather than trusting the header verbatim). At minimum, `to_signable_string` (or an additional check in `Registry.process`) should incorporate the shop domain so that altering the header invalidates the signature.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`). Shopify sends a POST with `X-Shopify-Hmac-Sha256: H` computed over body `B`, and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker resends the identical body `B` and identical `H` to the app's webhook endpoint, replacing the header with `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Request#hmac` reproduces `H` from the header, and `Request#to_signable_string` returns `B` unchanged, so `HmacValidator.validate` in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) succeeds.
4. `Registry.process` calls the handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to process attacker-controlled data as if it belonged to `victim.myshopify.com`.
