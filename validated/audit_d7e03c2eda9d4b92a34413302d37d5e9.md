### Title
Local success/enrollment-status declared without backend verification in user-centric signups leads to misattributed signup enrollment - (File: src/plans/mod.rs)

### Summary
In `MasterPlan::do_signup`, when a signup's backend-provided `user_centric_signup` flag is set (and `ignore_user_centric_signups` is false), the orb never calls the backend enrollment/verification endpoint (`enroll_user`, which itself calls `signup_post`/`signup_poll`). Instead it derives `enrollment_status`/`success` purely from a *locally computed* `signup_reason`, which itself is derived from a `detect_fraud()` call whose fraud-check body is empty in this codebase variant. This breaks the invariant that "signup success/enrollment_status must reflect the backend's authoritative verification (duplicate/fraud/liveness check)" — analogous to `userTotalStaked` diverging from the actual per-user stake ledger in the referenced report: one piece of derived state (`debug_report.enrollment_status` / `result.success`) is set without being kept in sync with the actual source of truth (backend enrollment record).

### Finding Description
`do_signup` computes `signup_reason` locally: [1](#0-0) 

`detect_fraud` — the sole gate that could turn `signup_reason` into `Fraud` — is a no-op in this build (all real fraud checks removed): [2](#0-1) 

When the QR-scanned user data indicates `user_centric_signup == true` (a value returned by the backend's own `/user_status` lookup) and the orb config does not override it via `ignore_user_centric_signups`, the code takes a branch that sets `enrollment_status`/`success` directly from the locally computed `signup_reason`, completely bypassing the backend signup/enrollment request (`enroll_user::Plan::run`, which normally posts to `signup_post` and polls `signup_poll` for backend-side duplicate/fraud confirmation): [3](#0-2) 

Contrast this with the non-user-centric path, which actually invokes `enroll_user`, sending the signup to the backend and polling for a `Completed`/`success` verdict that accounts for backend duplicate detection, inflight matches, and backend fraud detection: [4](#0-3) 

Because `SignupReason::Normal` is the `#[default]` and is reached whenever `pipeline.is_some()` and `fraud_detected == false` (which is unconditionally `false` given the empty `detect_fraud`), every completed capture in the `user_centric_signup` branch is locally marked `enroll_user::Status::Success`, `debug_report.signup_status = Success`, and `result.success = true` — all without the backend ever confirming that this iris/face wasn't already enrolled or that the signup fraud/liveness checks passed. The Personal Custody Package (biometric image bundle, iris codes, face embeddings) is still built and uploaded to the backend in this same flow, unconditionally, before this decision point: [5](#0-4) 

This is the direct analog of the report's bug class: a locally maintained field (`enrollment_status`/`success`, analogous to `selfStakes[staker].amount`) is updated in one code path without being kept consistent with the authoritative ledger (the backend's enrollment/duplicate database, analogous to `userTotalStaked`), because the code path that would normally reconcile the two (`enroll_user`) is skipped entirely for this state combination.

### Impact Explanation
An orb operating with `user_centric_signup == true` will locally attest "signup successful" and upload the user's biometric PCP (iris codes, face embeddings, images) under the scanned `user_id`, all while any real duplicate-enrollment or fraud detection that would normally occur through `enroll_user`→`signup_post`/`signup_poll` is skipped. This can result in:
- Misattributed/duplicate signups being reported as successful to the local UI and to the app via `self_serve::orb::v1::SignupEnded { success: true, .. }`, even though the backend was never asked to confirm identity uniqueness for this specific enrollment path.
- Biometric data upload proceeding for a signup whose validity was never confirmed by the backend's own checks, since the upload of tier0/tier1/tier2 PCPs happens before/independent of this success determination.

This matches the "unauthorized or misattributed signup" impact category described in the rules, is reachable by any user going through a normal (unprivileged) self-serve/app-driven signup flow where the backend `/user_status` response sets `user_centric_signup = true`, and does not require any malicious peer/operator/hardware access.

### Likelihood Explanation
Likelihood depends on how commonly `user_centric_signup` is returned `true` by the backend for a given deployment and whether `ignore_user_centric_signups` is enabled server/orb-side; this is a config- and backend-response-dependent code path, so exploitability cannot be fully confirmed from the orb-core repository alone (the backend's decision logic for `user_centric_signup` is out of scope/not visible here). Within the reachable orb-core code, the branch is trivially reachable by any user whose QR scan resolves `UserData::user_centric_signup = true` — no special privileges are required. I flag this uncertainty explicitly since I could not inspect the backend service that sets this flag.

### Recommendation
Do not treat `signup_reason == SignupReason::Normal` as authoritative success for enrollment purposes in the `user_centric_signup` path. Even under `user_centric_signup`, the orb should still submit the signup to the backend (`signup_post`) and require backend confirmation (`signup_poll` reaching `Completed`/`success == true`) before setting `debug_report.enrollment_status` to `Success` and before reporting `result.success = true` / sending `SignupEnded { success: true }`. If the intent of `user_centric_signup` is only to change *who* drives the UX (app vs. orb) and not to skip the backend acknowledgment, then `do_signup` should be refactored so the backend enrollment call is unconditional, and only the *notification path* (app vs. orb UI) differs based on `user_centric_signup`.

### Proof of Concept
Not independently executable from this analysis — no test harness in this repo simulates a backend response with `user_status::UserData::user_centric_signup = true` combined with `ignore_user_centric_signups = false` and a completed biometric pipeline. Reasoning path (traceable directly from source):
1. A user completes QR scan; backend `/user_status` response sets `user_data.user_centric_signup = true` (see `UserData::user_centric_signup`) — [6](#0-5) .
2. Orb config has `ignore_user_centric_signups = false` (the default unless explicitly overridden) — [7](#0-6) .
3. Biometric capture and pipeline succeed (`pipeline.is_some()`); `detect_fraud` always returns `false` — [2](#0-1) .
4. `signup_reason` resolves to `SignupReason::Normal` — [8](#0-7) .
5. `do_signup` takes the `user_centric_signup` branch, sets `enroll_user::Status::Success` locally, and reports `success = true` without ever calling `enroll_user`/`signup_post`/`signup_poll` — [3](#0-2) .
