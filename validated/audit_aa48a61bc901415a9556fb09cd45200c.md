Audit Report

## Title
Username Enumeration via Distinct Login Error Messages in `SessionsController.Create` - (File: `core/web/sessions_controller.go`)

## Summary
The `/sessions` login endpoint returns different, attacker-visible error strings depending on whether the submitted email corresponds to an existing account, allowing unauthenticated enumeration of valid Chainlink node usernames. This occurs because `CreateSession` implementations across all three authentication providers (local, LDAP, OIDC) return raw/distinguishable error text based on whether the account exists versus whether the password was wrong, and this text is passed through to the HTTP response unmodified.

## Finding Description
`SessionsController.Create` forwards any error from `AuthenticationProvider().CreateSession` straight to the client via `jsonAPIError(c, http.StatusUnauthorized, err)`, and `jsonAPIError` embeds `err.Error()` verbatim into the JSON response body when the error is not already a `*models.JSONAPIErrors`. In the local-auth provider, `CreateSession` calls `FindUser`/`findUser`, which executes `SELECT * FROM users WHERE lower(email) = lower($1)` and returns the raw `sql.ErrNoRows` wrapping error immediately if no user is found, while an existing user with a wrong password yields the distinct string `"Invalid password"`. The identical divergent pattern exists in the LDAP provider's `localLoginFallback` (raw SQL error vs. `"invalid password"`) and the OIDC provider's `localLoginFallback` (same pattern). No normalization or generic-error substitution occurs anywhere on this path before the error reaches the HTTP response — the only rate limiting applied is an unauthenticated-tier limiter, which throttles but does not prevent this from being observed.

## Impact Explanation
An unauthenticated attacker can distinguish "account does not exist" from "account exists, wrong password" by inspecting the JSON error body returned from `/sessions`, enabling systematic enumeration of valid node operator emails/usernames (CWE-204, Observable Response Discrepancy). This supports targeted credential stuffing or brute-force password attempts against confirmed accounts, which is a legitimate authentication-hardening concern for a node's admin API, though it does not on its own grant authentication bypass, key exfiltration, or fund movement — it is an information-disclosure precursor to those higher-impact attacks.

## Likelihood Explanation
The `/sessions` endpoint is registered with only an unauthenticated rate limiter, not authentication, so any unauthenticated actor can send repeated login attempts and observe the returned error text. The bug is deterministic and requires no special conditions to reproduce — a plain HTTP POST with any email/password pair is sufficient.

## Recommendation
Return a single generic error message (e.g., "invalid email or password") for all `CreateSession` failure paths in `core/sessions/localauth/orm.go`, `core/sessions/ldapauth/ldap.go`, and `core/sessions/oidcauth/oidc.go`, and ensure `SessionsController.Create` does not leak provider-specific error text to the client. Continue logging the detailed reason (email-not-found vs. wrong-password) only via the existing internal audit log calls (`audit.AuthLoginFailedEmail`, `audit.AuthLoginFailedPassword`).

## Proof of Concept
1. `POST /sessions` with `{"email":"nonexistent@example.com","password":"anything"}` on a local node → response body contains the raw SQL "no rows"/lookup-failure error text from `findUser`.
2. `POST /sessions` with `{"email":"<known-existing-email>","password":"wrongpassword"}` → response body contains `"Invalid password"`.
3. Comparing the two distinct response bodies confirms whether `<known-existing-email>` is a valid account, without any authentication required. This can be verified with a Go handler test invoking `SessionsController.Create` directly, or via `curl` against a running dev node.

	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
