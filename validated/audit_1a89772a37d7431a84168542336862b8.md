## Title
Webhook `shop` (tenant) identifier is not covered by the HMAC signature, allowing cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity by checking only the HMAC over the raw request body, then trusts the `shop` (tenant identifier) taken from an unauthenticated HTTP header to route the webhook data to the host application's handler. This breaks the identity binding: `HMAC-verified bytes == raw_body` but `tenant-context used by handler == request.shop (header, unauthenticated)`.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC only over `verifiable_query.to_signable_string`. For a webhook `Request`, `to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

The `shop` accessor, by contrast, is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, which is never included in the signed bytes: [2](#0-1) 

`Registry.process` validates the HMAC and, if valid, immediately constructs `WebhookMetadata` using `request.shop` (the unauthenticated header) as the tenant identifier passed to the app's handler: [3](#0-2) 

`WebhookMetadata.shop` is documented and typed as the authoritative "shop domain of the webhook" that host applications are expected to use to attribute the event to a merchant/tenant: [4](#0-3) [5](#0-4) 

Because the HMAC only binds `raw_body`, and Shopify signs the body with the app's `api_secret_key`, any `(raw_body, hmac)` pair that was ever legitimately delivered to the app for **any** shop remains a cryptographically valid pair for **any other** `shop` header value. An attacker who controls one legitimate installation (e.g., their own free/test store using the same app) can capture a genuine webhook delivery — a valid `raw_body` + `x-shopify-hmac-sha256` pair signed with the app's real secret — and then directly POST that same body/HMAC to the app's public webhook endpoint while substituting `x-shopify-shop-domain` with a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body bytes), and `Registry.process` will dispatch the event to the handler with `shop` set to the attacker-chosen victim domain.

### Impact Explanation
This is a tenant-identity-binding break: the value verified by the HMAC (`raw_body`) is not the same value trusted for tenant attribution (`shop` header). Depending on how the host application's `WebhookHandler#handle` implementation uses `data.shop` (as universally recommended by the gem's own documentation and by `shopify_app`), this enables cross-tenant event injection — e.g., forging `customers/data_request`, `shop/redact`, `app/uninstalled`, or `orders/create` events attributed to a victim shop, potentially triggering unauthorized data deletion, redaction, deprovisioning logic, or corrupting per-shop state/queues for a shop the attacker does not control. This matches the "cross-tenant access" Critical impact category, since it lets an unprivileged internet user (who merely holds a legitimate credential-free webhook sample of their own) make the host app treat an event as belonging to a different tenant.

### Likelihood Explanation
Exploitation does not require the app's `api_secret_key`, an access token, or any privileged account — only the ability to install the app on an attacker-controlled shop (or otherwise obtain one genuine `(body, hmac)` pair, which Shopify sends over the wire to the app's public webhook URL) and the ability to POST to that same public endpoint with a modified `shop` header, which is normal unauthenticated internet access. The main uncertainty is how much host-application logic keys directly off `data.shop` without additional cross-checks (e.g., confirming the shop against a locally stored, previously verified session); this is application-dependent, but the gem's own webhook API/documentation explicitly instructs handlers to trust `data.shop` as the identifying key.

### Recommendation
Bind the shop identifier into the value that is HMAC-verified, or otherwise cryptographically tie `request.shop` to the signed payload before it is trusted by handlers — e.g., include the `shop` header (and other identifying headers such as `topic`/`api_version`) in the signable string used by `to_signable_string`, or require verification that the shop is one for which the app currently has a stored session/registration before dispatching. At minimum, the documentation should explicitly warn implementers that `data.shop` is not covered by the HMAC and must not be trusted as an authoritative tenant boundary without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. for `orders/create`, with body `raw_body` and header `x-shopify-hmac-sha256: <valid HMAC of raw_body under the app's real secret>`.
2. Attacker POSTs to the app's public webhook endpoint (the same route the app exposes per `docs/usage/webhooks.md`) reusing the exact `raw_body` and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses successfully (all required headers present).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC — unaffected by the swapped `shop` header (`lib/shopify_api/webhooks/registry.rb:190`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(... shop: request.shop ...)`, where `request.shop == "victim-shop.myshopify.com"`, even though this data never actually originated from Shopify on behalf of that shop.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
