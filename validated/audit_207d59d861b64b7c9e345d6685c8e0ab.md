### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body alone, while the `shop` attribute used downstream to attribute the webhook to a tenant is read from an HTTP header that is never included in the signed material. `Webhooks::Registry.process` trusts this unverified `shop` value and hands it straight to the app's handler, breaking the binding between "HMAC validated" and "shop the data belongs to."

### Finding Description
`HmacValidator.validate` verifies a `VerifiableQuery` by recomputing the HMAC over `verifiable_query.to_signable_string` using the app's `api_secret_key` and comparing it to the supplied `hmac`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw request body, while `shop` is read from a separate, unauthenticated header (`shopify-shop-domain` / `x-shopify-shop-domain`): [2](#0-1) 

`Registry.process` validates the HMAC over the body, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build `WebhookMetadata` passed to the host app's handler — with no check that this `shop` value is actually the tenant that produced the signed body: [3](#0-2) 

Since `Context.api_secret_key` is a single, app-wide secret shared across every merchant installation (it is not per-shop), a valid `(body, hmac)` pair only proves "this body was signed by an entity that knows this app's secret" — i.e., "this webhook genuinely came from *some* shop that has this app installed" — not "this body belongs to the shop named in this header." The binding the code implicitly assumes is:

```
shop_that_signed_the_body == shop_named_in_the_header
```

but nothing enforces this equality. An attacker who controls one shop (`attacker-shop.myshopify.com`) that has the app installed can trigger a real, validly-signed webhook event on their own store, capture the `(raw_body, hmac)` pair (both fully attacker-controlled/observable since they own that store and can read the webhook delivery to their own endpoint or proxy), and then replay that exact body/HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a different, victim merchant (`victim-shop.myshopify.com`) that also uses the app. `HmacValidator.validate` still passes, because it never inspects the header, and `Registry.process` will dispatch the handler with `shop: "victim-shop.myshopify.com"` and the attacker-chosen body — causing the host application to record/act on forged data as if it originated from the victim tenant.

### Impact Explanation
This breaks tenant isolation: an attacker with a legitimate (even free/trial) installation of the target app on their own shop can produce arbitrary, validly-"authenticated" webhook payloads attributed to any other shop running the same app, without ever obtaining that shop's credentials. Depending on how the host app uses webhook data (e.g., updating order/customer/fulfillment records, triggering financial actions, or storage keyed by `shop`), this can lead to cross-tenant data corruption or unauthorized actions performed against another merchant's account — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any user of this gem's webhook feature is affected as shipped: `Registry.process` is the standard/only path documented for processing inbound webhooks, and it relies solely on `HmacValidator.validate` plus the untrusted `shop` header. Exploitation only requires the attacker to control one shop with the target app installed (a normal, unprivileged capability) and the ability to send an HTTP POST to the app's public webhook endpoint with a modified header — no secrets, tokens, or privileged access are needed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the material that is HMAC-verified, or otherwise cryptographically/contextually verify that the `shop` header matches the tenant the webhook subscription was registered for (e.g., cross-check against the shop associated with the webhook registration/session rather than trusting the header verbatim). At minimum, document that `request.shop` from `Webhooks::Request` is unauthenticated and must not be used as a sole tenant identifier without independent verification.

### Proof of Concept
1. App has two independent installs: `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, both sharing the same `Context.api_secret_key`.
2. Attacker triggers a webhook-worthy event on `attacker-shop` (e.g., updates an order), and Shopify sends the app a real webhook with body `B` and header `shopify-hmac-sha256: H` where `H = HMAC(secret, B)`.
3. Attacker intercepts/replays this exact `(B, H)` pair to the app's webhook endpoint but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `HmacValidator.validate` recomputes `HMAC(secret, B)` which still equals `H`, so validation succeeds: [4](#0-3) 
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...))`, causing the host app to process attacker-controlled data as belonging to `victim-shop`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
