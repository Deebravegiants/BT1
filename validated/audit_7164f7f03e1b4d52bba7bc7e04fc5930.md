### Title
Webhook `shop` identity is trusted from an unsigned header while the HMAC only covers the raw body, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
The external report's bug class is: a value that gates a security-relevant decision does not account for all the inputs that determine the real state, so the check passes on data it shouldn't (the `currentDebt` check ignores accruing interest and so under-restricts). The equivalent binding failure in this gem is in the webhook pipeline: `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` to attribute an inbound webhook to a tenant, but the HMAC signature that `Utils::HmacValidator.validate` checks is computed **only over the raw request body**, not over the `shop-domain` header. The identity binding `shop_header == shop_that_produced_signed(body, hmac)` is never enforced.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from the (attacker-controllable) HTTP header, entirely independent of the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC solely against `to_signable_string` (the raw body) and the app's `api_secret_key`: [3](#0-2) 

`Registry.process` accepts the request once the body's HMAC checks out, and then forwards `request.shop` (from the header) — not anything derived from the signed body — to the app's handler as the tenant identity: [4](#0-3) [5](#0-4) 

Because the signature never binds `shop-domain` to `body`, an unprivileged party who legitimately owns any Shopify store and has webhooks enabled receives real `(raw_body, hmac)` pairs signed by Shopify with the app's own `api_secret_key`. That party can resend the exact same `raw_body`/`hmac` to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` / `x-shopify-shop-domain` header. `Utils::HmacValidator.validate` will still return `true`, because it only re-derives the HMAC from `raw_body` — it has no way to detect that the `shop` header was swapped. The app's handler then processes attacker-supplied body content under the identity of a shop the attacker does not own.

### Impact Explanation
This breaks the binding `shop == owner_of(signed_body)`, letting an unprivileged internet user (any merchant/store owner who is a legitimate customer of the target app) inject data attributed to a different tenant. Depending on how the app's `WebhookHandler#handle` implementation uses `WebhookMetadata#shop` (e.g., to key per-shop stores, trigger token-authenticated follow-up API calls, or clear/overwrite tenant records), this is a cross-tenant access primitive: Critical per the given impact taxonomy.

### Likelihood Explanation
Requires only that the attacker (a) run their own Shopify store subscribed to at least one webhook topic handled by the target app, and (b) be able to reach the app's public webhook endpoint with custom headers — both are trivial and available to any unprivileged internet user; no access token, `api_secret_key`, or privileged account is needed.

### Recommendation
Bind the tenant identity into the signed material, or otherwise verify it out-of-band: e.g., require the app to independently confirm that the `shop` value in `WebhookMetadata` corresponds to a shop that has a valid registered session/access token before trusting it, and/or document/enforce that `to_signable_string` (or a wrapping check in `Registry.process`) must incorporate the `shop-domain` header into the verified signature computation so header tampering invalidates the HMAC.

### Proof of Concept
1. Attacker registers/owns `attacker-shop.myshopify.com` on the target app, so their webhooks are genuinely signed by Shopify using the app's `api_secret_key`.
2. Shopify delivers a legitimate webhook: `raw_body = B`, header `x-shopify-hmac-sha256 = HMAC(secret, B)`, `x-shopify-shop-domain = attacker-shop.myshopify.com`.
3. Attacker resends the same `B` and same HMAC header to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this successfully (all required headers present).
5. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` from `to_signable_string` (body only) and it matches — validation passes.
6. `Registry.process` invokes the app handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, ...)`, causing the app to act on attacker-controlled data under the victim shop's identity.
