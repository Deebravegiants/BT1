### Title
OAuth callback `shop` is HMAC-verified but not domain-sanitized before use as the session's tenant key - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` validates the incoming `auth_query` HMAC (which covers `code`, `host`, `shop`, `state`, `timestamp`) using `Utils::HmacValidator.validate` [1](#0-0) , but the `shop` value it then trusts to key the session and to request the access token is taken verbatim from `auth_query.shop`, with no call to `Utils::ShopValidator.sanitize!` anywhere in this method [2](#0-1) . By contrast, `TokenExchange.migrate_to_expiring_token` explicitly sanitizes its `shop` argument with `Utils::ShopValidator.sanitize!(shop)` before using it as a session key [3](#0-2) , showing the library itself treats "HMAC-verified" and "known-good Shopify domain" as two different, independently-required checks.

### Finding Description
`HmacValidator.validate` only proves the query was signed with `api_secret_key`; because the `shop` field is a value the calling web app read from the HTTP querystring and handed to `AuthQuery`, an unprivileged internet user completing OAuth via their own app installation with a self-controlled `shop` value can drive `auth_query.shop` to be any well-formed string. HMAC verification asserts "the request's fields, including `shop`, were signed correctly with our secret," while `Session.new(shop: auth_query.shop)` / `Session.from(shop: auth_query.shop, ...)` assumes "`shop` is a genuine `*.myshopify.com` tenant identifier." These are not the same guarantee: `Utils::ShopValidator.sanitize!` exists precisely to close this gap by restricting `shop` to `TRUSTED_SHOPIFY_DOMAINS` [4](#0-3) , but `validate_auth_callback` never calls it. The broken equality is: `shop` covered by a valid app-secret HMAC ≠ `shop` constrained to a genuine Shopify-owned domain used as the session/tenant key.

### Impact Explanation
Because `null_session = Auth::Session.new(shop: auth_query.shop)` is used as the base session for the subsequent `client.request` to `/admin/oauth/access_token` [5](#0-4) , and `Clients::HttpClient` derives its request host from `session.shop`, an unsanitized `shop` value controls the destination host of an HTTP request that carries the app's `client_id`/`client_secret` in the POST body. If the host application does not itself re-validate `shop` before calling this method (which the gem's own `ShopValidator` utility suggests it should, but does not enforce inside `validate_auth_callback`), this is a path for SSRF that leaks the app's `client_secret` to an attacker-chosen host, and for creating a `Session` keyed by an attacker-chosen, non-Shopify `shop` string, undermining the shop-as-tenant-key invariant used elsewhere in the gem (e.g., `SessionUtils.offline_session_id`/`jwt_session_id`, which assume `shop` is a validated myshopify domain).

### Likelihood Explanation
`shop` in the OAuth callback query is not itself cryptographically bound to a Shopify-issued domain independent of the surrounding application's own validation; the HMAC only proves the *combination* of fields was signed by the shared secret, not that `shop` is a real store domain. Given the library elsewhere (`TokenExchange.migrate_to_expiring_token`) treats sanitization as mandatory before trusting `shop` as a session key/host, the omission in `validate_auth_callback` is a real, in-gem inconsistency rather than a documented, expected behavior the host app must additionally guard against.

### Recommendation
In `lib/shopify_api/auth/oauth.rb#validate_auth_callback`, call `shop = Utils::ShopValidator.sanitize!(auth_query.shop)` immediately after the HMAC check and before constructing `null_session`/`Session.from`, mirroring the pattern already used in `TokenExchange.migrate_to_expiring_token`.

### Proof of Concept
1. Attacker sets up their own Shopify app installation flow against the victim's app, or crafts a callback request where `shop=attacker-controlled-host.example` (a value they fully control since it originates from the browser-supplied query string).
2. Attacker also supplies a matching `hmac` computed with knowledge of nothing secret is required from the attacker's side other than triggering a real OAuth redirect from Shopify — but if the host app fails to independently validate `shop` against `TRUSTED_SHOPIFY_DOMAINS` prior to calling `validate_auth_callback` (as the gem does not enforce this internally), `Auth::Session.new(shop: auth_query.shop)` and the subsequent `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")` request will target the attacker-chosen host with the request body containing `client_id`/`client_secret` [5](#0-4) .
3. This confirms `validate_auth_callback` relies on the caller to have already sanitized `shop`, despite the gem providing (and using elsewhere) `Utils::ShopValidator.sanitize!` for exactly this purpose.
