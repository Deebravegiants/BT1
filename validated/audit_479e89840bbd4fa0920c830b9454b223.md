## Analysis

The reported bug class (CWE-401/CWE-770): an unbounded in-memory map is populated *before* the item's legitimacy is verified, letting an unprivileged party grow server memory without limit until a periodic-but-decoupled cleanup catches up. The strongest analog in this codebase is the intents-bid mempool cache used for intent solving.

### Title
Unbounded Memory Growth in Intents `BidCache` via Mempool-Sourced Bids (Denial of Service) - (File: `modules/pallets/intents-coprocessor/rpc/src/lib.rs`)

### Summary
The `BidCache` used by the intents RPC/bid-watcher stores every bid observed in the transaction pool in an in-memory `HashMap<H256, OrderBids>`, where `OrderBids.entries: Vec<BidEntry>` has no per-commitment cap and the map has no cap on the number of distinct commitments tracked, before any check that the referenced order/commitment actually exists or that the bid is otherwise meaningful. Growth is only bounded retroactively by a timer-driven TTL sweep, mirroring the LTI-authenticator nonce-storage bug: data is cached first, validated (if at all) later.

### Finding Description
`BidCache::insert` [1](#0-0)  is invoked from `run_bid_watcher` for every transaction the node's tx-pool marks "ready" that decodes as a `pallet_intents_coprocessor::Call::place_bid` extrinsic [2](#0-1) . `extract_bid` only checks that the extrinsic decodes and is signed — it never checks that `commitment` corresponds to a real, still-open order, nor bounds the size or count of bids per commitment [3](#0-2) .

Unlike the equivalent on-chain path, which caps enumeration at `MAX_ON_CHAIN_BIDS = 30` [4](#0-3) , the off-chain `BidCache` has:
- No cap on the number of distinct `commitment` keys in the `HashMap`.
- No cap on the number of `BidEntry` items (one per distinct `filler`) per commitment — `order.entries.push(entry)` grows without bound [5](#0-4) .
- No size limit on the `user_op` bytes carried per entry.

The only mitigation is `remove_expired`, run on a fixed timer tick, which evicts entries older than `ttl` [6](#0-5) [7](#0-6) . This is decoupled from insertion: memory usage during any `ttl` window scales directly with attacker-controlled insertion rate and payload size, not with anything validated against real intents/orders.

### Impact Explanation
An intent solver (or anyone able to submit signed, fee-paying extrinsics against `place_bid`) can flood the cache with bids for arbitrary/nonexistent order commitments, or many distinct `filler` values for a single commitment, each carrying attacker-chosen `user_op` bytes. This drives unbounded (within the TTL window, proportional to sustained attack rate × payload size) heap growth on every node running the intents RPC/bid-watcher, degrading or crashing the service that intent solvers rely on for sub-second bid discovery (`intents_getBidsForOrder` / `intents_subscribeBids`). This falls squarely within the explicitly in-scope "intents escrow and bids" surface reachable by an unprivileged intent solver.

### Likelihood Explanation
Attack complexity is low to moderate: the attacker only needs enough balance to pay transaction fees for a stream of `place_bid` extrinsics that merely need to be considered "ready" by the pool — they never need to be included in a block, reference a real order, or pass any pallet-level bid-validity check, since the RPC watcher consumes pool "ready" transactions directly. This is analogous to the original advisory's AC:H "attacker with a valid consumer key" requirement, here satisfied by "an account with funds for extrinsic fees."

### Recommendation
- Cap the total number of tracked commitments and the number of entries per commitment in `BidCache` (e.g., LRU eviction or a hard `MaxTrackedBids`/`MaxBidsPerOrder` bound enforced at insert time), rejecting/evicting on overflow rather than growing unboundedly.
- Before inserting, cheaply verify the `commitment` corresponds to an existing, unexpired on-chain order (a light state read) so cache entries can only be created for real intents.
- Bound `user_op` size accepted into the cache.
- Consider decoupling the cleanup cadence from a fixed timer to also fire on insertion-count thresholds, not just wall-clock TTL.

### Proof of Concept
1. Fund an account with enough balance to submit repeated `place_bid` extrinsics.
2. Submit a stream of `place_bid(commitment = random_H256, user_op = large_bytes)` extrinsics with a fresh, non-existent `commitment` (or fresh `filler` signer) each time, faster than the `cleanup_interval`/`ttl` window can evict them.
3. Each extrinsic that reaches "ready" state in the tx-pool triggers `bid_cache.insert(...)` [8](#0-7) , adding a new `HashMap` entry/`Vec` element with no validation that the order exists and no size cap.
4. Sustained submission grows the RPC node's memory proportional to `rate × ttl × payload_size`, degrading or exhausting node memory serving intent bid discovery.

	pub fn insert(
		&self,
		commitment: H256,
		filler: Vec<u8>,
		user_op: Vec<u8>,
	) -> Result<(), String> {
		let entry = BidEntry { filler: filler.clone(), user_op };

		let mut bids = self.bids.write().map_err(|e| format!("BidCache lock poisoned: {e}"))?;
		let order = bids
			.entry(commitment)
			.or_insert_with(|| OrderBids { first_seen: Instant::now(), entries: Vec::new() });
		if let Some(existing) = order.entries.iter_mut().find(|e| e.filler == filler) {
			*existing = entry;
		} else {
			order.entries.push(entry);
		}
		Ok(())
	}

	pub fn remove_expired(&self) -> Result<(), String> {
		let now = Instant::now();
		let mut bids = self.bids.write().map_err(|e| format!("BidCache lock poisoned: {e}"))?;
		bids.retain(|_commitment, order| now.duration_since(order.first_seen) < self.ttl);
		Ok(())
	}

		+ DecodeWithMemTracking,
	T::AccountId: Encode + From<[u8; 32]> + DecodeWithMemTracking,
	Extra: DecodeWithMemTracking,
{
	let xt = sp_runtime::generic::UncheckedExtrinsic::<
		sp_runtime::MultiAddress<T::AccountId, ()>,
		T::RuntimeCall,
		sp_runtime::MultiSignature,
		Extra,
	>::decode(&mut &encoded[..])
	.ok()?;

		},
		_ => return None,
	};

		pallet_intents_coprocessor::Call::place_bid { commitment, user_op } =>
			Some((commitment.clone(), filler, user_op.to_vec())),
		_ => None,
	}
