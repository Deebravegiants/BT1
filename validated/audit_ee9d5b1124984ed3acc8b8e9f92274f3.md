Audit Report

## Title
CORS wildcard-origin allowlist bypass via missing domain-boundary check in `isAllowedOrigin` - (File: core/services/gateway/network/httpserver.go)

## Summary
The Gateway HTTP server's `isAllowedOrigin` function performs a wildcard-origin match using `strings.HasSuffix(originHost, allowedHost)` after stripping the `*.` prefix from a configured allowed origin, without verifying that a domain-boundary character (`.`) precedes the match. This allows any hostname that merely ends with the configured domain string (e.g., `evilremix.com` matching a `*.remix.com` rule) to be treated as an allowed CORS origin.

## Finding Description
In `isAllowedOrigin` [1](#0-0) , when an allowed origin has a `*.` prefix, the code strips the prefix and checks `strings.HasSuffix(originHost, allowedHost)` with no requirement that the character preceding the matched suffix in `originHost` be a `.`. For a configured entry `*.remix.com`, `allowedHost` becomes `"remix.com"`, and any origin host ending in that literal string — such as `evilremix.com` — satisfies the suffix check and is incorrectly treated as a trusted subdomain of `remix.com`.

This flaw is reachable directly in `handleRequest` [2](#0-1) , which reflects the attacker-supplied `Origin` header back as `Access-Control-Allow-Origin` whenever `isAllowedOrigin` returns true, with no additional boundary or allowlist re-validation performed downstream. No other authentication or role check mitigates this specific CORS decision — the only gate is `isAllowedOrigin` itself, which is broken for wildcard entries.

## Impact Explanation
This lets a browser page hosted on an unrelated domain that merely shares a suffix with an operator's configured wildcard origin (e.g., `evilremix.com` vs. `*.remix.com`) receive `Access-Control-Allow-Origin` reflecting its own origin, letting the victim's browser read cross-origin responses from the Gateway HTTP endpoint as if from a trusted subdomain. This is a genuine allowlist-bypass bug affecting the CORS boundary the operator intended to enforce, and maps to the "allowlist bypass" / "gateway request impersonation" impact class. Note that actual request processing (`ProcessRequest`) still requires a valid JWT via the `Authorization` header, so the practical severity depends on what unauthenticated/lightly-authenticated Gateway endpoints exist behind this check, but the CORS boundary itself is concretely broken as written.

## Likelihood Explanation
Exploitation requires only that: (1) the operator has legitimately enabled `CORSEnabled` and configured at least one wildcard entry in `CORSAllowedOrigins` (a normal, documented use of this feature, not a misconfiguration), and (2) an attacker registers or controls any domain sharing the configured suffix and lures a victim's browser to it. No privileged access to the Gateway or node is required, and the flawed match logic is deterministic and repeatable.

## Recommendation
Enforce a domain boundary in the wildcard match, e.g., compare against `"."+allowedHost` as the suffix (or require `originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost)`), so `evilremix.com` no longer matches `*.remix.com` while `foo.remix.com` still does.

## Proof of Concept
1. Configure the Gateway with `CORSEnabled: true` and `CORSAllowedOrigins: ["https://*.remix.com"]`.
2. From a browser at `https://evilremix.com`, send a fetch/XHR request to the Gateway's configured HTTP path with header `Origin: https://evilremix.com`.
3. In `isAllowedOrigin`, `allowedHost` becomes `"remix.com"` and `strings.HasSuffix("evilremix.com", "remix.com")` evaluates to `true`, so the function returns `true`.
4. `handleRequest` sets `Access-Control-Allow-Origin: https://evilremix.com` in the response, verifiable via a Go unit test calling `isAllowedOrigin("https://evilremix.com")` against a config with `CORSAllowedOrigins: []string{"https://*.remix.com"}` and asserting it returns `true`.
