## Analysis: Replay-able Approval Nonce in `usdk::transfer_from` (Analogous Custody Bug)

The external report's core invariant is: *an approval/allowance value must be correctly consumed exactly once per authorized transfer, and the code must not assume that a single grant of authority corresponds to a single controlled use.* Searching Aptos-native custody flows for the same invariant, the strongest analog is not in `object.move` or `dispatchable_fungible_asset.move` (those correctly gate transfers with linear, single-use `LinearTransferRef`/`ExtendRef` capabilities), but in the permit-style allowance implementation for the example stablecoin module.

### Title
Unbounded Replay of Signed `transfer_from` Approval via Non-Consuming Sequence-Number Nonce - (File: `aptos-move/move-examples/fungible_asset/stablecoin/sources/usdk.move`)

### Summary
`usdk::transfer_from` implements an ERC20-`permit`-like off-chain approval: the `from` account signs an `Approval` message binding `owner`, `spender`, `amount`, `to`, `chain_id`, and a `nonce` set to `account::get_sequence_number(from)`. The function verifies the signature but never invalidates or increments this "nonce" as a side effect of consuming the approval, because it borrows the account's global transaction sequence number rather than maintaining a dedicated, incrementing allowance-nonce. Since `transfer_from` is a `public fun` invoked by `spender` (not `from`), executing it does not advance `from`'s on-chain sequence number. The exact same `proof` therefore remains valid and can be resubmitted indefinitely until `from` independently sends a transaction of its own.

### Finding Description [1](#0-0) 

`transfer_from` builds the challenge message using `account::get_sequence_number(from)` as the `nonce` field, then calls `account::verify_signed_message` and immediately performs `primary_fungible_store::transfer_with_ref(transfer_ref, from, to, amount)`. There is no bookkeeping (e.g., a `Table<address,u64>` of consumed nonces, or an explicit increment/invalidate call) tying a successful verification to a state change that would prevent the same `proof` from validating again. The only state that could invalidate the message — `from`'s sequence number — is controlled exclusively by `from` sending its own transactions; it is untouched by `spender` calling `transfer_from`.

Consequently, a single signature obtained from `from` (e.g., to authorize one specific `amount` transfer to one specific `to`) grants `spender` an unlimited number of executions of that exact transfer as long as `from`'s sequence number does not change — which is the common case for custodial/backend-signed or infrequently-active accounts.

### Impact Explanation
This breaks the core custody invariant identified in the external report: a single signed authorization must correspond to a single consumed use. Here, `spender` can drain `from`'s entire USDK balance in `amount`-sized increments by repeatedly resubmitting the identical `proof`, well beyond what `from` intended to authorize. This is a direct custody-impact issue — unauthorized, repeated transfer of fungible-asset-held value away from the rightful owner's primary store, i.e., theft via authority replay, matching the "custody accounting corruption that moves value to the wrong holder" impact class.

### Likelihood Explanation
Likelihood is high in practice: any integrator that reuses this reference stablecoin pattern for a permit-like flow (a common pattern for gasless/back-end relayed transfers) inherits this flaw. The attacker only needs to be the `spender` who received a legitimately signed approval once; no additional privilege or race condition is required, and the exploit is trivially repeatable via ordinary transaction submission.

### Recommendation
Do not reuse the account's global transaction sequence number as an approval nonce. Maintain a dedicated, monotonically-incrementing (or consumed-set) nonce/allowance value under `Management`/`State`, increment or remove it atomically within `transfer_from` upon successful verification, and include that dedicated field in the signed `Approval` message instead of `account::get_sequence_number(from)`. This ties message validity to actual consumption within `transfer_from` itself rather than to unrelated account activity by `from`.

### Proof of Concept
1. `from` signs one `Approval { owner: from, to: spender_receiver, nonce: account::get_sequence_number(from) /* e.g. 5 */, chain_id, spender, amount: 100 }` intending to authorize a single 100-token transfer.
2. `spender` calls `usdk::transfer_from(spender, proof, from, scheme, pubkey, to, 100)`. It succeeds; 100 USDK moves from `from` to `to`. `from`'s sequence number is still `5` because `from` did not sign/submit this transaction.
3. `spender` calls `usdk::transfer_from` again with the identical `proof` and parameters. `account::get_sequence_number(from)` is still `5`, so `verify_signed_message` succeeds again, and another 100 USDK is transferred.
4. Repeat step 3 until `from`'s balance is exhausted, or until `from` happens to submit an unrelated transaction (which increments the sequence number and finally invalidates the replayed proof). [2](#0-1)

    /// Allow a spender to transfer tokens from the owner's account given their signed approval.
    /// Caller needs to provide the from account's scheme and public key which can be gotten via the Aptos SDK.
    public fun transfer_from(
        spender: &signer,
        proof: vector<u8>,
        from: address,
        from_account_scheme: u8,
        from_public_key: vector<u8>,
        to: address,
        amount: u64,
    ) acquires Management, State {
        assert_not_paused();
        assert_not_denylisted(from);
        assert_not_denylisted(to);

        let expected_message = Approval {
            owner: from,
            to: to,
            nonce: account::get_sequence_number(from),
            chain_id: chain_id::get(),
            spender: signer::address_of(spender),
            amount,
        };
        account::verify_signed_message(from, from_account_scheme, from_public_key, proof, expected_message);

        let transfer_ref = &borrow_global<Management>(usdk_address()).transfer_ref;
        // Only use with_ref API for primary_fungible_store (PFS) transfers in this module.
        primary_fungible_store::transfer_with_ref(transfer_ref, from, to, amount);
    }
