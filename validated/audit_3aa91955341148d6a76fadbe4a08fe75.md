Confirmed: `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` swap native tokens via `swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` — no code found anywhere in these functions that refunds unused ETH from the router back to the actual caller (`_msgSender()`); the router's leftover ETH is returned `to`/`msg.sender` of the swap call, which is `EvmHost` itself, not the end user.

### Title
Native-Fee Callers Permanently Lose Excess ETH on `EvmHost.dispatch()`/`fundRequest()` Due to Meaningless `block.timestamp` Deadline and No Refund of Uniswap Change - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` let a caller pay the relayer fee in native token by sending `msg.value` and swapping it for an exact amount of fee tokens via `IUniswapV2Router02.swapETHForExactTokens`. This mirrors the report's root cause: no caller-supplied maximum spend/slippage bound and a deadline parameter that provides no real time-bound protection, exposing the caller to loss of funds.

### Finding Description
In all three native-payment paths [1](#0-0) , [2](#0-1) , and [3](#0-2) , the call is:

```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
```

Two problems combine here, both direct analogs of the Arrakis `mint()` issue (no max-amount cap, no real deadline):

1. **`deadline: block.timestamp`** is evaluated at execution time, so it is always satisfied — it provides zero protection against the transaction sitting in the mempool while ETH/feeToken price on the local Uniswap V2 pool moves. This is the same "deadline offers no protection" pattern flagged in the source report (no `ending_Timestamp` used).
2. **No caller-specified `amountInMax`**: `swapETHForExactTokens` is given the caller's entire `msg.value` as the implicit input ceiling (`msg.value` is the `value` sent with the call, which Uniswap treats as `amountInMax`), and there is no independent, user-chosen "maximum I'm willing to pay" bound separate from what they attach to the transaction. Combined with `address(this)` as the `to` parameter, **any unused ETH from the swap is refunded to `EvmHost` itself, not to `_msgSender()`**. No code in `dispatch()`/`fundRequest()` forwards that ETH back to the caller or reduces `msg.value` before the call — the caller's leftover ETH becomes silently stuck/absorbed by the contract instead of being returned.

This is functionally identical to the Arrakis pattern: the caller has no way to bound what they actually pay, no functioning expiry, and any overpayment is not returned to them, so slippage/price movement between submission and mining directly costs the caller ETH with no recourse.

### Impact Explanation
Any unprivileged user calling `dispatch()` or `fundRequest()` with native token to pay relayer fees can lose the difference between `msg.value` sent and the actual ETH consumed by the swap, because:
- The `block.timestamp` deadline never reverts a stale transaction, so a transaction stuck in the mempool executes at whatever price exists at inclusion time with no bound the user controlled.
- Uniswap's leftover ETH refund goes to `EvmHost` (`address(this)`), not to the user, meaning any amount of `msg.value` above what was needed for the exact-out swap is permanently lost to the caller (retained in `EvmHost`, with no visible withdrawal path back to that user).

This is a direct, reachable loss of funds via a single, unprivileged transaction — exactly the class of impact the rules require ("concrete theft or permanent freezing of funds").

### Likelihood Explanation
Every user paying Hyperbridge relayer fees in native token through `dispatch()`, `fundRequest()`, or any `HyperApp` sending native value hits this path. Overestimating `msg.value` (a common, even recommended, practice to avoid `InsufficientOutputAmount`-style reverts from price movement) is routine, so the loss condition is easily triggered without any adversarial actor — worsened, though not strictly required, by sandwich/MEV activity against the local low-liquidity Uniswap V2 pool given the non-functional deadline.

### Recommendation
- Replace `block.timestamp` with a caller-supplied deadline parameter that is validated against the actual submission time (or pass through from `DispatchPost`/`DispatchGet`/`fundRequest` parameters).
- After `swapETHForExactTokens`, refund any leftover `msg.value` (`address(this).balance` delta, or read the router's return value) back to `_msgSender()` rather than silently keeping it in `EvmHost`.
- Alternatively, use `swapExactETHForTokens` with a caller-specified `amountOutMin` plus an explicit refund step, so the caller controls both worst-case spend and gets unused funds back.

### Proof of Concept
1. Alice calls `EvmHost.dispatch{value: 1 ether}(post)` where `post.fee` requires only 0.4 ETH worth of feeToken at current pool price, intentionally overshooting to tolerate expected slippage.
2. `swapETHForExactTokens{value: 1 ether}(post.fee, path, address(this), block.timestamp)` executes; suppose only 0.45 ETH is actually needed given the price at execution.
3. The router refunds `1 - 0.45 = 0.55 ETH` to the `to`-of-call, which is `EvmHost` itself (per the call's `msg.sender` being `EvmHost`), not Alice.
4. `EvmHost` has no logic to detect or forward this returned ETH to `_msgSender()`; Alice's 0.55 ETH is unrecoverable through the `dispatch()` interface — a permanent loss for the caller. [1](#0-0) [3](#0-2)
