### Title
Attacker-controlled ABI proof fields cause runtime panics (unwrap/expect) in `evm/rust/src/conversions.rs`, reachable from the permissionless `submit_proof` extrinsic - ([File: evm/rust/src/conversions.rs])

### Summary
`pallet-beefy-consensus-proofs::submit_proof` is a signed but permissionless extrinsic: anyone can call it with an arbitrary ABI-encoded `BeefyConsensusProof`/`ecdsa_beefy::BeefyConsensusProof` payload. The pallet ABI-decodes the payload and converts it into internal SCALE types via `From` impls in `evm/rust/src/conversions.rs`. Several of these conversions use `.try_into().expect(...)` or `.next().expect(...)` on fields taken directly from the untrusted proof bytes, so a proof with an out-of-range numeric field or an empty payload vector panics the runtime while processing the extrinsic.

### Finding Description
`do_submit_proof` in [1](#0-0)  decodes the caller-supplied bytes with `abi_decode_params` for both the SP1 and NAIVE (ECDSA) proof types, then calls `.into()` to convert them into the pallet's internal `ConsensusMessage`/`Sp1BeefyProof` representation. That conversion chain runs through [2](#0-1)  (`From<RelayChainProof> for MmrProof`), which does:

```
let leaf_index: u64 = value.latestMmrLeaf.leafIndex.try_into().expect("mmr leaf index out of bounds");
```

`leafIndex` is a `U256` field controlled entirely by the caller/relayer submitting the proof. If it exceeds `u64::MAX`, `try_into()` fails and `.expect()` panics.

The same file contains multiple additional `.expect()` calls on attacker-supplied fields reached by the identical code path:
- `value.leafCount.try_into().expect("leaf count out of bounds")` [3](#0-2) 
- `value.version.try_into().expect("mmr leaf version out of bounds")`, `parentNumber`, `nextAuthoritySet.id`, `nextAuthoritySet.len` [4](#0-3) 
- `value.payload.into_iter().next().expect("commitment has at least one payload entry")` — panics if the caller submits an **empty** payload array [5](#0-4) 
- `value.blockNumber`, `value.validatorSetId` [6](#0-5) 
- `value.authorityIndex.try_into().expect("authority index out of bounds")` [7](#0-6) 
- SP1 proof `commitment.blockNumber` / `commitment.validatorSetId` [8](#0-7) 

These conversions are invoked from `verify_and_apply`/`do_submit_proof`, which run **before** any cryptographic BEEFY/SP1 signature check succeeds — the conversion happens while assembling the `Message::Consensus` payload passed to `handlers::handle_incoming_message`, so a malformed field triggers the panic ahead of (or independent of) proof validity [9](#0-8) .

This is the exact same bug class as CVE-2020-10810 (an unchecked precondition/assumption on caller-supplied state leading to a NULL/panic condition reachable without special privilege) — here materialized as unchecked numeric-range and non-empty-vector assumptions on ABI proof fields decoded from a permissionless extrinsic.

### Impact Explanation
A panic thrown while executing a Substrate/FRAME extrinsic inside `apply_extrinsic` unwinds through the WASM runtime, which traps and aborts block execution rather than merely failing the single transaction gracefully in some execution contexts (and at minimum reliably fails the transaction execution and disrupts the block-authoring/import pipeline for that block). Because `submit_proof` is fee-paying but otherwise open to **any** account with no allowlist, any user can craft an ABI payload with `leafIndex > u64::MAX`, an authority index/set id/parent number out of `u64`/`u32` range, or an empty BEEFY `payload` array and submit it as a normal signed extrinsic to trigger the panic. Repeated submission is a low-cost denial-of-service vector against block production/import for the consensus pallet responsible for advancing Hyperbridge's trusted state commitments — which gates all downstream message delivery, state-proof verification, and token bridging. This satisfies the "route unable to deliver messages" / DoS criterion in scope.

### Likelihood Explanation
High. No privilege or race condition is required — the caller only needs a funded account able to submit a signed extrinsic, and constructing an out-of-range `U256` or an empty array in the ABI-encoded proof is trivial. The vulnerable code executes unconditionally during ABI-to-SCALE conversion, before signature/finality checks can reject the proof.

### Recommendation
Replace every `.try_into().expect(...)` / `.next().expect(...)` in the `From` impls in `evm/rust/src/conversions.rs` (for `BeefyMmrLeaf`, `Commitment`, `Vote`, `RelayChainProof`, `SP1BeefyProof`, and the parachain-proof `leafCount`) with fallible conversions that propagate a typed error (or convert these `From` impls into `TryFrom`), and have `do_submit_proof`/`verify_and_apply` map conversion failures to a typed pallet error (e.g. `Error::<T>::AbiDecodeFailed`) instead of letting them panic. Add regression tests submitting proofs with `leafIndex`/`blockNumber`/`validatorSetId`/`authorityIndex` set beyond `u64`/`u32` range and with an empty BEEFY `payload` vector, asserting the extrinsic returns an `Err` rather than panicking — mirroring the pattern already used elsewhere in this codebase (e.g. the sync-committee, GRANDPA, and pharos SPV verifiers, which were hardened against exactly this class of attacker-controlled panic).

### Proof of Concept
1. Construct an ABI-encoded `ecdsa_beefy::BeefyConsensusProof` (or `sp1_beefy::SP1Beefy::SP1BeefyProof`) where `relay.latestMmrLeaf.leafIndex` is set to a `U256` value greater than `u64::MAX` (e.g. `2^64`), or where `relay.signedCommitment.commitment.payload` is an empty array.
2. Submit `pallet_beefy_consensus_proofs::submit_proof(proof_bytes)` as any signed account (no special role required).
3. `do_submit_proof` → `verify_and_apply` decodes the payload and calls `.into()` on the decoded struct, hitting `From<RelayChainProof> for MmrProof` (or `From<Commitment> for SpCommitment`), which executes `value.latestMmrLeaf.leafIndex.try_into().expect("mmr leaf index out of bounds")` (or `iter.next().expect("commitment has at least one payload entry")`), panicking mid-extrinsic-execution.
4. Observe the panic aborts execution of the extrinsic/block rather than returning a graceful `DispatchError`, confirming the reachable DoS.

(Note: I was unable to fully trace WASM-runtime-panic-vs-catch_unwind behavior for this specific Substrate/FRAME executor configuration within the indexed code — this may cause either a hard node crash/halt or at minimum an uncontrolled extrinsic failure outside normal error handling; either outcome is a denial-of-service on the consensus-update path and warrants the fix regardless of the precise failure mode.)

		/// BEEFY commitment reconstruction. Reassembles the `Payload` from its
		/// `(id, data)` entries, starting with the first entry and pushing the rest via
		/// `push_raw` (which re-sorts by id to keep the invariant `Payload` expects).
		fn from(value: Commitment) -> Self {

			let first = iter.next().expect("commitment has at least one payload entry");
