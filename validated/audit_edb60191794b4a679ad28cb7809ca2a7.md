### Title
Webhook `shop` header is trusted for tenant routing but is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content from the raw request body only, while the `shop` field it exposes (and that `Registry.process` hands to the app's handler as the tenant identifier) comes from an HTTP header that is never included in the signed bytes. An attacker who can obtain any one validly-signed webhook body/HMAC pair for their own store can replay that exact body with a forged `shop-domain` header claiming to be a different (victim) shop, and the HMAC check still passes.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery`, whose contract is `hmac` + `to_signable_string`. For this class: [1](#0-0) 
`to_signable_string` returns only `@raw_body`: [2](#0-1) 
`shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the signed payload: [3](#0-2) 

`Registry.process` validates the request purely via `HmacValidator.validate(request)` — i.e., it only proves the body matches the signature computed with the app's secret — and then immediately trusts `request.shop` as the tenant for dispatch: [4](#0-3) 

`HmacValidator.validate`/`validate_signature` only ever look at `verifiable_query.to_signable_string` (the body) and `verifiable_query.hmac`; the `shop` accessor is completely outside what is authenticated: [5](#0-4) 

**The equality that should hold but doesn't:** `shop` used for tenant routing (`request.shop` → `WebhookMetadata.shop`) should equal the `shop` that produced the HMAC-signed body. Instead, the binding actually enforced is only `hmac == HMAC(secret, raw_body)`; `shop` is disjoint from that equation. This is structurally identical to the referenced bug class: a value the code "acts on" (here, tenant identity) is not covered by the integrity check (here, the HMAC) that is supposed to authenticate the whole message.

### Impact Explanation
This breaks the tenant boundary the gem is documented to provide (`WebhookMetadata` explicitly carries `shop` for the handler to use as the tenant key — confirmed by `test/webhooks/registry_test.rb` asserting `data.shop`). A malicious or unprivileged merchant who installs the app on their own store can capture a legitimately-signed webhook (topic/body/HMAC) for their own shop, then resend the identical body/HMAC to the app's webhook endpoint while spoofing the `shop-domain` header to name a different, victim shop. Because the HMAC only certifies the body, verification succeeds, and the handler processes attacker-supplied webhook data under the victim's tenant identity — a cross-tenant access/data-confusion condition (Critical per the given severity classes: "cross-tenant access").

### Likelihood Explanation
Reachable by any unprivileged internet user who can install the target app on a shop they control (a normal, low-privilege action) and can trigger any webhook delivery for that shop (also normal app behavior, e.g. triggering an order/product event). No access to `api_secret_key`, access tokens, or the app's other credentials is required — only the ability to observe one legitimate webhook delivery to their own store and replay it with a modified header to the same public webhook endpoint.

### Recommendation
Bind `shop` (and ideally `topic`/`api_version`) into the signed content actually verified, or otherwise cryptographically tie the header-derived `shop` to the signed body before it is trusted for routing:
- Have `Webhooks::Request#to_signable_string` incorporate the `shop` (and other routing-relevant headers) it exposes, or
- After body-HMAC verification, cross-validate `shop` against an independently trusted source (e.g., the shop associated with the specific `webhook_id`/subscription that was registered for the current tenant) rather than trusting the raw header value for dispatch.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a legitimate, low-privilege action).
2. Attacker triggers any subscribed webhook topic (e.g., `orders/create`) on their own shop and captures the raw request: body `B`, and header `X-Shopify-Hmac-Sha256: H` (valid because Shopify itself signed it with the app's secret for shop `attacker-shop.myshopify.com`).
3. Attacker replays an HTTP POST to the app's webhook endpoint with:
   - Same raw body `B`
   - Same `X-Shopify-Hmac-Sha256: H`
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - `X-Shopify-Topic`, `X-Shopify-Webhook-Id` as desired
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and compares to `H` — this succeeds because `B` and `H` are unchanged and `shop` never enters the computation: [4](#0-3) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body `B`, believing it originated from and pertains to the victim tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
