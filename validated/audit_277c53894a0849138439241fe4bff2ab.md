The webhook `Request` class's HMAC covers only `@raw_body` (`to_signable_string` returns `@raw_body`), while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers with no cryptographic binding to the signed payload, and are passed downstream into the handler as trusted tenant-identifying metadata.### Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted despite not being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity via `Utils::HmacValidator.validate(request)`, which computes and compares an HMAC solely over `to_signable_string`, defined as the raw request body [1](#0-0) . However, the `shop`, `topic`, and `webhook_id` values that are trusted and forwarded to the merchant's webhook handler are read directly from HTTP headers, which are entirely outside the HMAC's coverage [2](#0-1) .

### Finding Description
`HmacValidator.validate` computes `computed_signature = compute_signature(verifiable_query.to_signable_string, secret)` and compares it via `OpenSSL.secure_compare` against the `hmac` field [3](#0-2) . For `Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop`, `topic`, and `webhook_id` accessors instead read from `@headers` via `shopify_header`, with no cryptographic tie to the signed body [2](#0-1) [4](#0-3) .

`Registry.process` validates only the HMAC and then dispatches the handler using `request.topic`, `request.shop`, and `request.webhook_id` as trusted tenant-identifying metadata, without any additional check that these header values are consistent with the signed body: [5](#0-4) .

The identity binding broken is:
`HMAC(raw_body, api_secret_key) == received_hmac` is verified, but `shop_header == shop_bound_in_signature` is never checked — since `shop` is not part of `to_signable_string` at all.

Because the `api_secret_key` is shared across all merchant installations of a given app (it is not per-shop), a valid `(raw_body, hmac)` pair obtained from a genuine webhook delivery for one tenant (attacker's own shop, to which the attacker has legitimate access as an installed-app merchant) remains cryptographically valid when replayed with an arbitrary `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header pointing at a different tenant. `Registry.process` will accept it as authentic and hand the forged `shop`/`topic` values to the host application's handler as if they came from Shopify for that shop.

### Impact Explanation
This is a cross-tenant identity-binding break: an attacker who has genuine webhook traffic for their own shop (an unprivileged/low-privilege actor relative to other merchants using the same app) can relabel that traffic as belonging to a victim shop and have it pass HMAC verification, because `shop` is verified as "any value the attacker chooses" rather than "the value the signature attests to." Depending on how the host application's webhook handler uses `WebhookMetadata#shop` (e.g., for provisioning, data updates, deletion, redaction — including the mandatory `shop/redact`, `customers/redact`, `customers/data_request` topics), this can lead to cross-tenant data manipulation or spoofed compliance events attributed to a shop the attacker does not control.

### Likelihood Explanation
Requires the attacker to have received at least one legitimate webhook (raw body + valid HMAC) for a shop they control — a low bar for any merchant/developer who has installed the app — and the ability to POST a replayed body with modified headers to the app's public webhook endpoint. No access to `api_secret_key`, tokens, or other merchants' credentials is needed.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed/verifiable string constructed by `Request#to_signable_string`, or otherwise cryptographically bind these header-derived values to the HMAC before they are trusted and passed to `WebhookMetadata`, mirroring how `Oauth::AuthQuery#to_signable_string` binds `shop` into its signature [6](#0-5) .

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a genuine webhook: raw body `B`, header `shopify-hmac-sha256: H`, `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays the exact same body `B` and `H` to the app's webhook endpoint but sets `shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `shopify-topic`/`shopify-webhook-id`).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation succeeds [7](#0-6) .
4. The handler is invoked with `WebhookMetadata` populated from `request.shop` (`victim-shop.myshopify.com`), `request.topic`, and `request.webhook_id`, none of which were actually authenticated by Shopify for that shop [8](#0-7) .
