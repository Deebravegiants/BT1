### Title
Unchecked numeric conversions on relayer-submitted BEEFY/SP1 proof fields can panic block execution - (File: evm/rust/src/conversions.rs)

### Summary
Multiple `From` impls that convert Solidity-ABI-decoded BEEFY/SP1 proof fields into internal SCALE types use `.try_into().expect(...)` on attacker-controlled numeric fields (`blockNumber`, `validatorSetId`, `authorityIndex`, `leafIndex`) instead of returning a typed error. This mirrors the CVE-2016-5037 bug class: a parser dereferences/converts untrusted, crafted input without validating that the conversion can succeed, and panics instead of gracefully rejecting malformed data.

### Finding Description
`pallet-beefy-consensus-proofs::verify_and_apply` and `do_submit_proof` (`modules/pallets/beefy-consensus-proofs/src/lib.rs:805-838`) accept a raw `proof: Vec<u8>` from an unsigned/permissionless caller, ABI-decode it via `<ismp_abi::sp1_beefy::SP1Beefy::SP1BeefyProof as SolType>::abi_decode_params`, and then call `.into()` to convert into the internal `beefy_verifier_primitives::Sp1BeefyProof`/`ConsensusMessage` types: [1](#0-0) 

That `.into()` resolves to `evm/rust/src/conversions.rs`, where the conversion functions use `.expect(...)` on values pulled directly from the attacker-supplied ABI payload: [2](#0-1) 

Specifically:
- `From<Commitment> for SpCommitment`: `iter.next().expect("commitment has at least one payload entry")` panics if `payload` is an empty array; `blockNumber.try_into().expect(...)` and `validatorSetId.try_into().expect(...)` panic if those values don't fit the target integer width.
- `From<Vote> for SignatureWithAuthorityIndex`: `authorityIndex.try_into().expect("authority index out of bounds")`.
- `From<RelayChainProof> for MmrProof`: `latestMmrLeaf.leafIndex.try_into().expect("mmr leaf index out of bounds")`.
- `From<SP1Beefy::SP1BeefyProof> for Sp1BeefyProof`: `commitment.blockNumber.try_into().expect(...)` and `commitment.validatorSetId.try_into().expect(...)`.

None of these conversions are preceded by a bounds check; the ABI decode step only guarantees the bytes parse as the declared Solidity types (e.g. `uint256`/`uint64`), not that they fit the narrower Rust integer the internal type expects. This is the same root cause pattern already fixed defensively elsewhere in this codebase (e.g. `modules/consensus/pharos/primitives/src/spv.rs`, `modules/trees/ethereum/src/node_codec.rs`, `modules/consensus/sync-committee/verifier/src/lib.rs`, `modules/consensus/grandpa/verifier/src/error.rs::RelayHeaderNotInUnknownHeaders`) — all of those were hardened specifically because an adversarial/crafted proof previously drove an `unwrap`/`expect`/array index to panic the runtime; these BEEFY ABI-conversion `.expect()` calls were not.

### Impact Explanation
An unprivileged caller can submit `submit_proof` (or route through `ismp-clients-beefy::verify_consensus` naive path) with a proof whose `payload` array is empty, or whose `blockNumber`/`validatorSetId`/`authorityIndex`/`leafIndex` is out of the target integer's range. If this happens during `handlers::handle_incoming_message` dispatch (called from within a transactional extrinsic, `#[frame_support::transactional]`), the resulting panic aborts the block-executing node process rather than returning a `DispatchError`, since Substrate's runtime panic handling on collator/validator nodes halts block production for that node. This is a "route unable to deliver messages" / consensus-DoS impact: a validator/collator executing the malicious extrinsic can be crashed or forced to diverge, and since `handle_unsigned` messages are permissionless and free, an attacker can repeat this cheaply against every node that processes the block.

### Likelihood Explanation
High: `submit_proof` is a permissionless, unsigned-friendly entry point that takes raw attacker-controlled bytes, ABI-decodes them, and immediately runs the vulnerable conversion before any BEEFY/SP1 cryptographic verification takes place. Crafting a payload with an empty `payload` array or an out-of-range `blockNumber` requires no special knowledge or race condition — it's a single malformed transaction.

### Recommendation
Replace all `.expect(...)` calls on attacker-controlled numeric/vector fields in `evm/rust/src/conversions.rs` with fallible conversions that return a typed decode error (mirroring the pattern already used for `RelayHeaderNotInUnknownHeaders`, `ProofTooDeep`, `nibble_at_depth` returning `Option`), and propagate that error through `AbiDecodeFailed`/`UnknownProofType` in `pallet-beefy-consensus-proofs` and `ismp-clients-beefy::verify_consensus` so malformed proofs are rejected with a `DispatchResult` error rather than panicking mid-extrinsic.

### Proof of Concept
Not independently executed (no sandbox access), but derivable directly from the code: submit `submit_proof` with `proof_type = PROOF_TYPE_SP1`, and an ABI-encoded `SP1BeefyProof` whose `commitment.payload` is empty (`Payload[] payload = []`) — this drives `iter.next().expect("commitment has at least one payload entry")` in `From<Commitment> for SpCommitment` (`evm/rust/src/conversions.rs:334-353`) to panic before any cryptographic proof check runs.

	impl From<Commitment> for SpCommitment {
		/// BEEFY commitment reconstruction. Reassembles the `Payload` from its
		/// `(id, data)` entries, starting with the first entry and pushing the rest via
		/// `push_raw` (which re-sorts by id to keep the invariant `Payload` expects).
		fn from(value: Commitment) -> Self {
			let mut iter = value.payload.into_iter();
			let first = iter.next().expect("commitment has at least one payload entry");
			let mut payload = BeefyPayload::from_single_entry(first.id.0, first.data.to_vec());
			for p in iter {
				payload = payload.push_raw(p.id.0, p.data.to_vec());
			}
			sp_consensus_beefy::Commitment {
				payload,
				block_number: value.blockNumber.try_into().expect("block number out of bounds"),
				validator_set_id: value
					.validatorSetId
					.try_into()
					.expect("validator set id out of bounds"),
			}
		}
	}
