### Title
Webhook Shop/Topic Identity Not Bound to HMAC — Cross-Tenant Webhook Spoofing via Header Substitution - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `shop-domain`, `topic`, `webhook-id`, and `api-version` HTTP headers — none of which are covered by that HMAC — to determine which tenant (shop) and which business event the payload is dispatched to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The HMAC check performed by `Utils::HmacValidator.validate` computes and compares the HMAC exclusively over this signable string: [2](#0-1) 

`Registry.process` then only asserts this body HMAC before pulling `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` straight from unauthenticated headers and handing them to the app's handler as the tenant/event identity: [3](#0-2) [4](#0-3) 

The broken identity binding, stated as an equality that should hold but doesn't:

`request.shop` (and `request.topic`) — the values the gem hands to the app's handler as ground truth for "which merchant/tenant this event is about" and "what happened" — should equal the shop/topic that Shopify's signature actually authenticated. Instead, the signature authenticates only `@raw_body`; `shop`, `topic`, `webhook_id`, and `api_version` are read from headers that sit entirely outside the HMAC's coverage. Any two values (`raw_body`, `hmac`) that are a valid pair for *any* previously-observed genuine webhook (e.g. one sent to the attacker's own shop/app installation) remain a valid pair when replayed with arbitrary `shop-domain`/`topic`/`webhook-id` headers substituted in, because the validator never looks at those headers.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for multi-tenant apps: a webhook handler built on `WebhookMetadata` (populated from `request.shop`/`request.topic`, see `registry.rb:198-199`) that keys any shop-scoped state, authorization decision, or business action off `data.shop`/`data.topic` can be made to act on behalf of a shop it never actually received an event for, or to treat one topic's payload as another topic's event — a cross-tenant/cross-context confusion driven entirely by unauthenticated header values riding along with a validly-signed body.

### Likelihood Explanation
An attacker only needs one legitimately HMAC-signed `(raw_body, hmac)` pair, which is trivial to obtain: install the (public) app on their own throwaway/development shop, trigger any webhook topic, and capture the resulting `raw_body`/`x-shopify-hmac-sha256` value (e.g., via an app feature that displays/logs webhook activity, or any network tooling under the attacker's own control since it is their own traffic to their own installed app). They then replay that exact body+HMAC to the app's public webhook endpoint while substituting the `shop-domain`, `topic`, and/or `webhook-id` headers. `HmacValidator.validate` passes because it never inspects those headers, and `Registry.process` dispatches the (attacker-chosen) topic/shop combination to the handler as if authentic.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the value that is HMAC-verified (or otherwise cryptographically bind them to the body), consistent with the general principle that the client fields an app's handler treats as authoritative must be inside the authenticated boundary — mirroring the report's core recommendation that a message/payload's authoritative fields must always be verified as a whole rather than allowing an unauthenticated side-channel (headers) to select what a signed blob "means."

### Proof of Concept
1. Attacker creates a Shopify development store and installs the target public app, triggering a real webhook (e.g. `orders/create`) so Shopify sends a genuine request to the app's webhook endpoint with a valid `x-shopify-hmac-sha256` over the raw body.
2. Attacker captures that exact `raw_body` and `hmac` value (via any means available on their own installation/traffic — app-provided webhook logs, their own server logging the inbound request, etc.).
3. Attacker sends a new HTTP request to the same webhook endpoint with the identical `raw_body`/`x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain` to a victim shop's domain and/or `x-shopify-topic` to a different registered topic.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which only checks `raw_body` against the HMAC — it succeeds — then dispatches to the handler with the attacker-controlled `shop`/`topic` values [5](#0-4) , causing the app to process the payload under a false tenant/topic identity.
