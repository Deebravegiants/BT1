This confirms the vulnerability: `ShopifyAPI::Webhooks::Registry.process` documents `Registry.process` as verifying "the request did indeed come from Shopify" (docs/usage/webhooks.md line 125), and hands `data.shop` (the shop domain) to the app's handler as trusted tenant identity — but the HMAC only covers the raw body, never the `shop-domain` header.

### Title
Webhook tenant identity (`shop` field) is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `Request#shop` is read directly and unauthenticated from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header [2](#0-1) . `Registry.process` validates the HMAC over only that signable string and, once it passes, forwards the header-derived `shop` value straight to the app's webhook handler as the authoritative tenant identity [3](#0-2) .

### Finding Description
The identity binding that should hold is: `shop` field trusted by the handler == `shop` field cryptographically bound to the HMAC-verified bytes. In this code, that equality does not hold — the HMAC is computed and verified solely over `@raw_body` [4](#0-3) [5](#0-4) , but the `shop-domain` header (and `topic`, `webhook-id`, `api-version` headers) sit entirely outside that signed scope. `Registry.process` only checks `Utils::HmacValidator.validate(request)` (body integrity + shared-secret authenticity) before constructing `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` and invoking the handler [3](#0-2) .

Because the app's own secret (`Context.api_secret_key`) is shared across all shops that install the app, any shop that has the app installed can legitimately trigger a webhook delivery with a validly-signed body (HMAC computed by Shopify with the same shared `client_secret`). An unprivileged attacker who installs the app on their own store can capture one such genuinely-signed `(raw_body, hmac)` pair from a webhook Shopify sends them, then replay that exact body and HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` will still succeed because the header is not part of the signed content, and the handler will process the (attacker-controlled) body as if it originated from the victim shop.

### Impact Explanation
This breaks the tenant boundary that webhook processing is supposed to enforce: an attacker-controlled payload can be attributed to any target shop domain of the attacker's choosing, since `shop` is taken verbatim from an unauthenticated header. Depending on how the host app's `WebhookHandler.handle` implementation uses `data.shop` (as documented, to route persisted data to `shop_domain: data.shop` [6](#0-5) ), this enables cross-tenant data injection/corruption — writing or triggering actions keyed to a shop the attacker does not control, satisfying the Critical "cross-tenant access" criterion.

### Likelihood Explanation
Requires only that the attacker be able to install the target app on their own (attacker-owned) Shopify store — a standard unprivileged, low-cost precondition — and that the app's webhook receiving endpoint be internet-reachable (which it must be, since Shopify delivers webhooks over the open internet). No access token, `api_secret_key`, or privileged account is required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) header values into the HMAC-signed content the library verifies — e.g., by including them in the canonicalized string passed to `HmacValidator.validate`, or by requiring the host application to separately confirm the delivered `shop` domain against the shop tied to the webhook subscription (e.g., verifying it belongs to a shop that actually has this webhook registered) before trusting `WebhookMetadata#shop`.

### Proof of Concept
1. Install the target Shopify app on attacker-owned store `attacker.myshopify.com`.
2. Trigger a webhook (e.g. `orders/create`) with attacker-controlled order data; Shopify signs the raw body with the shared `client_secret` and delivers headers including `x-shopify-shop-domain: attacker.myshopify.com` and `x-shopify-hmac-sha256: <valid-hmac>`.
3. Capture `(raw_body, hmac)` from that request.
4. Replay a POST to the app's webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256` header, but set `x-shopify-shop-domain: victim.myshopify.com`.
5. `Utils::HmacValidator.validate` succeeds (it only checks `raw_body` against the HMAC) [4](#0-3) , and `Registry.process` invokes the handler with `WebhookMetadata(shop: "victim.myshopify.com", body: <attacker-controlled>, ...)` [3](#0-2) .
