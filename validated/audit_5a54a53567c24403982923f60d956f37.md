### Title
Cross-chain messages become permanently undeliverable if their timeout expires while the destination `EvmHost` is frozen - ([File: evm/src/core/HandlerV2.sol])

### Summary
`HandlerV2.handlePostRequests` (and the equivalent Get/response/timeout handlers) are gated by the `notFrozen(host)` modifier, and the request-timeout check inside `handlePostRequests` uses a fixed `leaf.request.timeout()` deadline that is never adjusted for time spent in a frozen state. Analogous to the reported lending-pool bug ("users miss the withdrawal window while paused, with no extension of the window"), a Hyperbridge message dispatched before a freeze can miss its entire delivery window while the host is frozen, and once the host is unfrozen the message can no longer be delivered — only timed out.

### Finding Description
`EvmHost.setFrozenState` lets the admin or handler set `FrozenStatus.Incoming/Outgoing/All` [1](#0-0) . While frozen for `Incoming` or `All`, `HandlerV2`'s `notFrozen(host)` modifier blocks `handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts` and `handleGetRequestTimeouts` [2](#0-1) .

`handlePostRequests` enforces a hard timeout check per leaf:
```
if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
``` [3](#0-2) 

This deadline (`PostRequest.timeoutTimestamp`, set by the sending application at dispatch time [4](#0-3) ) is completely independent of the host's frozen state. If the destination host is frozen for a duration that spans a message's timeout window, relayers are prevented from calling `handlePostRequests` (via `notFrozen`) for the entire freeze, and once the host is unfrozen the timeout has already elapsed, so `handlePostRequests` will now always revert with `MessageTimedOut` for that leaf. The message can never be delivered — the only remaining path is `handlePostRequestTimeouts`, which requires proof of the request's non-existence in the destination state trie and dispatches `dispatchTimeOut` back to the source module [5](#0-4) .

This exactly mirrors the reported bug class: a fixed, time-bound window (there: withdrawal window / loan-repayment deadline; here: `PostRequest.timeoutTimestamp`) is not extended to compensate for the pause/freeze duration, so legitimate, already-submitted user actions silently fall outside their window and are forced into the "default"/"timeout" path instead of successful completion — with no on-chain mechanism to recover the intended cross-chain action.

### Impact Explanation
Any application built on Hyperbridge (e.g. `HyperFungibleToken.send()`, `WrappedHyperFungibleToken.send()`, `HyperbridgeLzEndpoint.send()`) that dispatches a `PostRequest` with a timeout close to the length of a subsequent freeze period will have that request forced into "timed out" rather than delivered, once the freeze is lifted. This is a "route unable to deliver messages" outcome for a class of in-flight, already-paid messages: the request can never reach its destination, and applications only get the fallback (`onPostRequestTimeout`) path rather than the intended cross-chain effect, even though the user acted entirely correctly and in good faith before the freeze. Because freezing is a routine operational lever (used e.g. for the mandatory-consensus submission batch which briefly unfreezes/freezes the host around `handleConsensus` [6](#0-5) , or during incident response), any sufficiently long freeze window silently forecloses delivery for messages whose timeout falls inside it, with no compensating extension.

### Likelihood Explanation
Likelihood is driven entirely by operational timing rather than by an attacker: any relayer-visible freeze (`FrozenStatus.Incoming`/`All`) that lasts long enough to overlap a request's `timeoutTimestamp` triggers this outcome automatically, with no additional actions required from any party. Short application-chosen timeouts (common to bound relayer fee exposure) make this more likely to occur during routine or incident-driven freezes.

### Recommendation
Either (a) make the timeout check in `handlePostRequests`/`handleGetResponses`/`*Timeouts` account for cumulative time spent in a frozen state (e.g. track frozen-duration and subtract it from `block.timestamp` before comparing to `timeout()`), or (b) document explicitly that freezing the host can cause in-flight, already-dispatched messages to be forcibly timed out, and require operators to size freeze windows / communicate them in advance so applications can choose commensurately long timeouts.

### Proof of Concept
1. App A dispatches a `PostRequest` from source chain S to destination chain D with `timeout = now + T`.
2. Before a relayer submits `handlePostRequests` on D, the admin (or handler, e.g. via the consensus-submission batch) calls `EvmHost.setFrozenState(FrozenStatus.Incoming)` on D for a legitimate operational reason, and the freeze lasts longer than `T`.
3. While frozen, `HandlerV2.handlePostRequests` reverts with `HostFrozen` for any relayer attempt [7](#0-6) , so the message cannot be delivered during the freeze.
4. When `setFrozenState(FrozenStatus.None)` is eventually called, `block.timestamp >= leaf.request.timeout()` is now true, so `handlePostRequests` unconditionally reverts with `MessageTimedOut` for that request [8](#0-7) .
5. The request can only be resolved via `handlePostRequestTimeouts`/`dispatchTimeOut`, which never executes the app's intended cross-chain effect (e.g., mint on destination) — the same "missed window, forced into the fallback/default path" outcome described in the source report.

    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());

    function handlePostRequestTimeouts(IHost host, PostRequestTimeoutMessage calldata message)
        external
        notFrozen(host)
    {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            PostRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            // known request? also serves as source check
            bytes32 requestCommitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(requestCommitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(REQUEST_RECEIPTS_STORAGE_PREFIX, requestCommitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(PostRequestTimeout(request, _msgSender()), meta, requestCommitment);
        }
    }
