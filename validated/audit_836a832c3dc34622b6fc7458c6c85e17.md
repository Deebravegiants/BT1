### Title
Webhook shop identity spoofing via unauthenticated `shopify-shop-domain` header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body. The `shop` (and `topic`/`webhook_id`) values that the handler receives and acts on are read directly from HTTP headers that are **not** included in the signed bytes. Any party that can obtain one valid `(body, hmac)` pair signed with the app's shared secret — for example a merchant who installed the app on their own store and simply forwards the webhook their own store received — can replay that pair while swapping the `shop` header to any other shop domain, and the library will accept it as an authentic webhook "from Shopify" for that other shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors are pulled straight from headers, independent of the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header — it only ever covers the body: [3](#0-2) 

`Registry.process` uses this single check to decide the request is authentic, then dispatches to the handler using the **unverified** `request.shop`: [4](#0-3) 

The documented guarantee is that `Registry.process` "will verify the request did indeed come from Shopify": [5](#0-4) 

This is exactly the "field acted on but not covered by the HMAC" identity-binding break: the equality the library implicitly claims is `authenticated(body) == authenticated(shop)`, but in reality only `authenticated(body)` holds — `shop` (the tenant identity the handler trusts) is attacker-controllable while the HMAC still validates.

### Impact Explanation
Because the same `api_secret_key` is shared across every installation of an app, any unprivileged user who installs the app on their own shop receives real, validly-signed webhooks for that shop. By capturing one `(raw_body, X-Shopify-Hmac-Sha256)` pair and re-POSTing it to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header (e.g. a victim's `myshopify.com` domain), the request passes `HmacValidator.validate` and is delivered to the host application's handler tagged as belonging to the victim tenant. Depending on how the host app uses `data.shop` (e.g., to look up records, associate incoming order/customer data, or scope background jobs), this enables cross-tenant data injection/confusion — data intended for or attributed to shop A gets written or processed under shop B's identity. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Any user able to install the app on a shop (a normal, unprivileged action for any merchant) can trigger genuine webhooks and capture a valid `(body, hmac)` pair — no access to `api_secret_key`, tokens, or privileged accounts is required. Forging headers on a replayed HTTP POST is trivial. Exploitability solely depends on the host app trusting `data.shop`/`data.topic` from `WebhookMetadata`, which is exactly what the library's own documentation instructs developers to do.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed bytes checked against the HMAC, or otherwise cryptographically bind the shop identity to the request (e.g., validate that `request.shop` matches an expected/active session's shop before invoking the handler), rather than relying on an out-of-band, unauthenticated header value.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; wait for a real webhook (e.g., `orders/create`) to be delivered to the app's webhook endpoint. Capture the raw body and the `X-Shopify-Hmac-Sha256` header — both are valid because Shopify signed them with the app's shared secret.
2. Replay the exact same raw body and HMAC header to the same webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally alter `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, raw_body)` — this still matches, so no exception is raised.
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: <attacker's original payload>, ...)`, and the host application processes/stores this data as if it legitimately originated from `victim-shop.myshopify.com`.
