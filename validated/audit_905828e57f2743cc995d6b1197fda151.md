### Title
Fee escrowed before request-dispatch can still fail on `Duplicate request`, permanently trapping the relayer fee - ([File: modules/pallets/ismp/src/dispatcher.rs])

### Summary
The CVE fixes an XSK code path that took a buffer out of circulation (removed it from the free pool / prepared it for delivery) but on a subsequent failure (`Rx queue was full`) failed to recycle it back, leaking the buffer. The structurally identical pattern in Hyperbridge is `pallet_ismp::Pallet::<T>::dispatch_request` (`modules/pallets/ismp/src/dispatcher.rs`, lines 92-151): it withdraws the user's relayer fee from their account into `RELAYER_FEE_ACCOUNT` *before* calling the inner `Pallet::<T>::dispatch_request(request, fee)` (`modules/pallets/ismp/src/impls.rs`, lines 90-121), which can fail with `Error::Custom("Duplicate request")` if the computed commitment already exists in `RequestCommitments`. When that inner call errors, the `?` propagates the error out of the outer `dispatch_request`, but the fee that was already transferred out of the payer's account is never reversed.

### Finding Description
`IsmpDispatcher::dispatch_request` for `pallet_ismp::Pallet<T>` in `modules/pallets/ismp/src/dispatcher.rs`:
```
fn dispatch_request(&self, request: DispatchRequest, fee: FeeMetadata<T>) -> Result<H256, anyhow::Error> {
    // collect payment for the request
    if fee.fee != Zero::zero() {
        T::Currency::transfer(&fee.payer, &RELAYER_FEE_ACCOUNT.into_account_truncating(), fee.fee, Preservation::Expendable)
            .map_err(...)?;
    }
    let request = match request { ... };
    let commitment = Pallet::<T>::dispatch_request(request, fee)?;
    Ok(commitment)
}
```
The fee transfer happens unconditionally and irreversibly first. The call into `Pallet::<T>::dispatch_request` (in `modules/pallets/ismp/src/impls.rs`):
```
pub fn dispatch_request(request: Request, meta: FeeMetadata<T>) -> Result<H256, ismp::Error> {
    let commitment = hash_request::<Pallet<T>>(&request);
    if RequestCommitments::<T>::contains_key(commitment) {
        Err(ismp::Error::Custom("Duplicate request".to_string()))?
    }
    ...
    T::OffchainDB::push(Leaf::Request(request));
    RequestCommitments::<T>::insert(commitment, RequestMetadata { ..., fee: meta, claimed: false });
    Ok(commitment)
}
```
computes the commitment hash, and if that commitment is already present in storage returns an error *without any state changes and without any refund path*. Because the caller (`dispatcher.rs`) already moved the fee out of the payer's account before this check, any legitimate caller that triggers a "duplicate request" outcome loses the fee permanently — there is no code path that reverses `T::Currency::transfer` on this error, unlike the timeout/refund flow (`on_request_timeout`) which is the only mechanism that returns fees to `payer`.

This mirrors the CVE precisely: a resource (buffer / escrowed fee) is taken out of the free/available pool in anticipation of a successful enqueue, the enqueue operation (`push` to the request queue / MMR-backed commitment map) can fail, and the code fails to give the resource back on that failure branch.

### Impact Explanation
Any module or pallet built on top of `IsmpDispatcher` (e.g. `pallet_example`'s `dispatch_to_evm`, `pallet-intents-coprocessor`'s `dispatch`, or any downstream integrator) that ends up computing an identical `hash_request` (same `source`, `dest`, `from`, `to`, `nonce`, `timeout_timestamp`, `body`) to an existing unconsumed request commitment will have the caller's fee permanently and irrecoverably transferred into `RELAYER_FEE_ACCOUNT` while the call itself fails and no request is ever queued for delivery. This is a permanent, unrecoverable loss of user funds (fee) with no compensating mint or refund, satisfying the "permanent freezing/loss of funds" impact class. It also represents a systemic risk: because nonce allocation and commitment hashing are entirely deterministic and controlled by pallet logic rather than by the caller, this is not attacker-controlled in the common single-dispatch case, but any implementation detail causing nonce reuse or timestamp collision (e.g., re-dispatching an identical zero-timeout, zero-body message in the same block, or a nonce counter that is not properly bumped across concurrent extrinsics in a block) turns this into a directly triggerable fee-drain/DoS against the fee payer.

### Likelihood Explanation
The likelihood depends on how `next_nonce()` is derived and whether it can plausibly collide for two dispatches with identical `(source, dest, from, to, timeout_timestamp, body)` in practice. I could not fully verify `next_nonce()`'s implementation within this session (tool calls were exhausted before reading `modules/pallets/ismp/src/host.rs`), so I cannot conclusively state how easily an unprivileged caller can force a nonce collision. However, even absent an attacker-controlled collision, this is a live correctness bug: the code contains an error branch (`Duplicate request`) that is explicitly checked for and handled, yet the fee-collection side effect that precedes it is not rolled back on that branch — this is present in the shipped code regardless of exploit difficulty, matching the CVE's own root cause (a genuine, reachable error path with an unrecycled resource), not a hypothetical.

### Recommendation
Reorder the operations in `dispatch_request` (`modules/pallets/ismp/src/dispatcher.rs`) so the fee is only collected *after* `Pallet::<T>::dispatch_request` succeeds (commitment already inserted / duplicate check passed), or wrap the fee transfer with an explicit refund on any subsequent error from the inner dispatch call, e.g.:
```rust
let commitment_precheck = /* compute hash_request and check RequestCommitments before charging fee */;
if fee.fee != Zero::zero() {
    T::Currency::transfer(...)?;
}
match Pallet::<T>::dispatch_request(request, fee.clone()) {
    Ok(commitment) => Ok(commitment),
    Err(e) => {
        if fee.fee != Zero::zero() {
            let _ = T::Currency::transfer(&RELAYER_FEE_ACCOUNT.into_account_truncating(), &fee.payer, fee.fee, Preservation::Expendable);
        }
        Err(e.into())
    }
}
```
The cleanest fix is to perform the duplicate-commitment check (which is deterministic and doesn't require currency operations) strictly before withdrawing any fee, eliminating the possibility of an unrecoverable balance transfer on a rejected dispatch.

### Proof of Concept
Exact reproduction requires knowing the nonce-generation semantics in `modules/pallets/ismp/src/host.rs::next_nonce`, which I was unable to inspect before running out of tool calls. Conceptually:
1. Caller A dispatches a `DispatchPost`/`DispatchGet` with fee `F` via `IsmpDispatcher::dispatch_request`. Fee `F` is transferred to `RELAYER_FEE_ACCOUNT`; a commitment `C` is stored in `RequestCommitments`.
2. Caller A (or any caller producing the same `(source, dest, from, to, nonce, timeout_timestamp, body)` tuple, e.g. because of a nonce-reuse edge case or a deterministic zero-timeout/zero-body message) dispatches again with fee `F2 > 0`. `hash_request` recomputes the same commitment `C`, `RequestCommitments::<T>::contains_key(C)` is `true`, and `Pallet::<T>::dispatch_request` returns `Err(Custom("Duplicate request"))`.
3. The outer `dispatch_request` in `dispatcher.rs` has already executed `T::Currency::transfer(&fee.payer, &RELAYER_FEE_ACCOUNT, F2, ...)` before step 2's failure; that transfer is never undone. `F2` is permanently lost to the caller with no corresponding request queued and no refund mechanism (the only refund path, `on_request_timeout`, is never reached because no request was ever recorded for this attempt).

This gap — fee/resource consumed ahead of a fallible commit into the request queue, with no rollback on that specific failure branch — is present in the current code at `modules/pallets/ismp/src/dispatcher.rs:92-151` and `modules/pallets/ismp/src/impls.rs:90-121`, and is left partially unverified only with respect to how frequently the "Duplicate request" branch can be triggered by an unprivileged caller in production, given I could not complete inspection of `next_nonce()`.
