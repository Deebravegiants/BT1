## Title
Same-chain and cross-chain order fills release escrow proportional to nominal `fillAmount`/`totalRequired` instead of the beneficiary's actual received balance, allowing under-delivery on fee-on-transfer output tokens - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`IntrinsicIntents._fillSameChain` and `ExtrinsicIntents._fillCrossChain` track fill progress and compute the input-escrow amount to release using the *nominal* `fillAmount`/`totalRequired` the solver claims to transfer, not the amount the beneficiary actually receives. `IntentGatewayV2.placeOrder` already defends the input side against this exact class of bug (fee-on-transfer tokens) by snapshotting balances before/after transfer and mutating `order.inputs[i].amount` to the measured delta, but no equivalent balance check exists on the output side of either fill path.

### Finding Description
In `_fillSameChain` [1](#0-0) , `fillAmount` is computed purely from `solverAmount` (the value the solver *claims* to send) and is used directly to:
- update `_partialFills[commitment][outputToken]` (the cumulative-fill tracker used to decide `isFullyFilled`), and
- compute `escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired` — the amount of escrowed input tokens released to the solver.

The actual token movement is `IERC20(token).safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal)` [2](#0-1) . If `token` charges a transfer fee (fee-on-transfer ERC20), the beneficiary receives less than `fillAmount`, yet `amountFilled`/`escrowedAmount` are computed as if the full nominal amount arrived.

The cross-chain path has the same pattern: `_fillCrossChain` transfers `totalRequired + beneficiaryShare` via `safeTransferFrom` [3](#0-2)  and then unconditionally dispatches a `RedeemEscrow` request for the *full* `order.inputs` [4](#0-3) , releasing 100% of the source-chain escrow regardless of how much the beneficiary actually received on the destination chain.

This is the same root-cause class as the reported bug: an accounting step subtracts/tracks the *intended* transfer amount instead of the *actually realized* amount, so remaining/filled state diverges from real token balances.

Notably, the protocol's own `placeOrder` code explicitly guards against this exact scenario on the input side — it snapshots `balancesBefore`, computes `received = balanceAfter - balanceBefore`, and mutates `order.inputs[i].amount` to the measured value [5](#0-4) , with dedicated fee-on-transfer tests [6](#0-5) . No such balance verification exists for the *output* leg in either `_fillSameChain` or `_fillCrossChain`.

### Impact Explanation
A solver (an unprivileged intent solver, one of the allowed reachable actors) can target orders whose output asset is a fee-on-transfer token and systematically under-deliver to the beneficiary while still claiming full (same-chain) or complete (cross-chain, all-or-nothing) release of the escrowed input tokens. This is a direct loss of funds for order placers: they receive fewer output tokens than the input value released to the solver, and for cross-chain orders the entire escrow is redeemed even though delivery was short.

### Likelihood Explanation
Any order whose output token has a transfer fee (a broad and common class of ERC20 behavior, including many deflationary/tax tokens) is affected. The solver role is unprivileged and directly reachable via `fillOrder`; no special permissions or races are required — a solver only needs to select such an order and fill it normally.

### Recommendation
Mirror the `placeOrder` fix on the fill/output side: measure the beneficiary's actual balance delta (or the dispatcher's, when calldata is involved) before and after the output transfer, and use that measured amount — not the nominal `fillAmount`/`totalRequired` — to update `_partialFills`, `isFullyFilled`, and the proportional `escrowedAmount` released in `_fillSameChain`, and to size the `order.inputs` amount redeemed via `RedeemEscrow` in `_fillCrossChain`.

### Proof of Concept
1. User places a same-chain order requesting `1000` units of `FeeToken` (1% transfer fee) as output for `1000 USDC` input.
2. Solver calls `fillOrder` with `outputs[0].amount = 1000`. `safeTransferFrom` sends `1000` nominal, but due to the 1% fee the beneficiary's balance only increases by `990`.
3. `_fillSameChain` computes `fillAmount = 1000` (equal to `totalRequired`), sets `amountFilled = totalRequired`, marks `isFullyFilled = true`, and releases the *entire* `1000 USDC` escrow to the solver via `_withdraw`.
4. The user ends up with only `990 FeeToken` instead of the `1000` they were promised, while the solver walks away with the full `1000 USDC` — the shortfall is pocketed by the solver via the fee-on-transfer mechanic that the accounting never measured.

        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 receivedByGateway = inputAmount - (inputAmount * 100) / 10000; // 990
        uint256 outputAmount = 900 * 1e18;

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: outputAmount});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        // Place order
        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Reconstruct order as placeOrder mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = receivedByGateway; // actual received

        // Solver fills
        uint256 solverFotBefore = fot.balanceOf(solver);

        vm.startPrank(solver);
        dai.approve(address(intentGateway), outputAmount);

        TokenInfo[] memory solverOutputs = new TokenInfo[](1);
        solverOutputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: outputAmount});

        intentGateway.fillOrder(
            order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, validUntil: 0, outputs: solverOutputs})
        );
        vm.stopPrank();

        // Solver should receive the escrowed FOT (with transfer fee applied on the way out)
        uint256 solverFotReceived = fot.balanceOf(solver) - solverFotBefore;
        uint256 expectedSolverReceived = receivedByGateway - (receivedByGateway * 100) / 10000; // 990 - 1% fee
        assertEq(solverFotReceived, expectedSolverReceived, "Solver should receive escrowed FOT minus transfer fee");

        assertEq(fot.balanceOf(address(intentGateway)), 0, "Gateway should have no FOT remaining");
