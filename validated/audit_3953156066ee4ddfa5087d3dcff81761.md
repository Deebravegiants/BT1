### Title
Webhook `shop` identity field is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (and `topic`, `webhook_id`, `api_version`) values solely from HTTP headers, while the HMAC signature it verifies covers only the raw request body. `Utils::HmacValidator.validate` binds the signature exclusively to `to_signable_string`, which returns `@raw_body`. This breaks the identity binding: `shop-header == shop-delivered-to-handler` is trusted, but `shop-header ⊆ HMAC-signed-bytes` is false.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (the body) and compares it with the `hmac` header value — it never incorporates the `shop` header into the signed material: [3](#0-2) 

`Webhooks::Registry.process` uses this unauthenticated `shop` value directly to build the `WebhookMetadata` that is handed to the app's handler, which apps are documented to use as the tenant identifier for the event: [4](#0-3) 

Documentation confirms `shop` is meant to identify "The shop domain of the webhook" and is commonly used by apps to route/attribute the event to a tenant (e.g., `shop_domain: data.shop`): [5](#0-4) 

This is exactly the identity-binding break described in the report's bug class: a field that is *acted on* (`shop`, used for tenant attribution) is *not covered by the HMAC* that is supposed to authenticate the request. Since the HMAC only proves "this body was signed by Shopify with the app's `client_secret`," and not "this body was signed *for shop X*," anyone who can obtain one genuinely-signed `(body, hmac)` pair from Shopify (e.g., by triggering a webhook event in their own, legitimately-installed shop) can replay that exact body+hmac to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value naming a victim shop. `HmacValidator.validate` will still pass (it never looks at the header), and `Registry.process` will invoke the app's handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop.

### Impact Explanation
This is a cross-tenant identity confusion vulnerability reachable entirely with unprivileged access (an attacker's own legitimately installed shop instance is enough to obtain one valid signed payload). Applications that rely on `WebhookMetadata#shop` (as documented) to key session lookups, database writes, background job scoping, or access-token retrieval for multi-tenant processing will attribute the replayed event to the wrong tenant, enabling an attacker to inject attacker-controlled webhook data (e.g., fake order/product/customer events, `app/uninstalled`, etc.) into another merchant's data pipeline — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is meaningful but requires the attacker to have their own store using the same app (to generate a validly signed body+hmac pair) and knowledge/control of the victim shop domain string, both of which are attacker-obtainable without any secret material, access token, or privileged account — satisfying the "unprivileged internet user" threat model.

### Recommendation
Include the shop domain (and ideally webhook id / topic) in the material that is HMAC-verified, or otherwise cryptographically/contextually bind the `shop` header value before trusting it — e.g., cross-check the header's shop against the shop associated with the specific webhook subscription (via `webhook_id`) queried from Shopify, or require callers to pass the expected shop and reject mismatches, rather than handing the raw unauthenticated header value straight to the handler as an implicitly-trusted tenant identifier.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker-shop.myshopify.com` and triggers a webhook event (e.g., updates a product), causing Shopify to POST a genuinely signed webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's `client_secret`), and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays the exact same request to the app's webhook endpoint, but rewrites the header to `x-shopify-shop-domain: victim-shop.myshopify.com`, keeping body `B` and hmac `H` unchanged.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim-shop.myshopify.com", "x-shopify-hmac-sha256" => H})` is constructed.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation succeeds (`lib/shopify_api/utils/hmac_validator.rb:13-22`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed B, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to process attacker-supplied data under the victim tenant's identity.

          received_signature = verifiable_query.hmac
