### Title
Webhook Shop/Topic Identity Not Bound to HMAC Signature Allows Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by checking that the HMAC-SHA256 over the raw request body matches a signature computed with the app's `client_secret` [4](#0-3) . The `shop`, `topic`, and `webhook_id` fields that the handler later uses to attribute the event to a tenant are read straight from HTTP headers and are never included in the signed payload [5](#0-4) . Since `client_secret` is shared by the app across all merchants who install it (not per-shop), any merchant who has genuinely installed the app can capture one of their own validly-signed webhook deliveries (body + HMAC) and replay it to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header naming a different, victim shop. The HMAC check still passes because it only verifies the body, not the shop header.

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, body || shop || topic)` such that the authenticated shop is cryptographically tied to the signature. Instead, the gem only enforces `hmac == HMAC(secret, body)` [1](#0-0)  and `lib/shopify_api/utils/hmac_validator.rb` validates purely against `to_signable_string`, which is the raw body only [6](#0-5) . The `shop` attribute used downstream in `WebhookMetadata` comes from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header [7](#0-6) , with no mechanism forcing correspondence between that header and the signed body content.

Because `client_secret` is a single app-wide secret rather than per-shop, any of the app's own merchants can obtain a legitimately-signed webhook (e.g., by triggering an event on their own store) and then POST that exact body+HMAC to the app's webhook receiver while substituting a different shop domain in the header. `Registry.process` will accept it, since `Utils::HmacValidator.validate(request)` only checks body authenticity, and will invoke the handler with `shop: request.shop` set to the attacker-controlled value [8](#0-7) , causing data belonging to one tenant to be attributed to another.

### Impact Explanation
This breaks the tenant/shop identity binding without requiring `api_secret_key`, an access token, or any privileged credential — only that the attacker be an ordinary merchant who has installed the app (an "unprivileged internet user" relative to other tenants). If the app uses `WebhookMetadata#shop` to look up/update per-tenant records (as is the documented usage pattern), an attacker can inject data or trigger side effects (e.g. uninstall/redact flows, order or product updates) attributed to a victim shop it does not control — a cross-tenant access impact per the Critical impact category.

### Likelihood Explanation
Medium-High: exploitation requires only that the attacker run their own instance of the app (a normal merchant install), capture one legitimate webhook payload+HMAC from their own shop, and replay it to the shared webhook endpoint with a forged shop-domain header. No secret material or victim credentials are needed.

### Recommendation
Bind the shop (and ideally topic) into the value that is authenticated, e.g. require the host application to additionally verify that `request.shop` matches an expected/registered shop for the receiving endpoint, or extend the HMAC/verification contract so header-derived identity fields are cryptographically tied to the payload before being trusted. At minimum, document prominently that `shop`/`topic`/`webhook_id` headers are NOT covered by the HMAC and must not be trusted as tenant identity without additional application-level binding (e.g., correlating against a known/expected shop list).

### Proof of Concept
1. App merchant "attacker-shop" installs the target app; Shopify sends attacker-shop a legitimate webhook, e.g. `POST /webhooks` with body `B` and header `X-Shopify-Hmac-Sha256: H` where `H = HMAC_SHA256(client_secret, B)`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker captures `B` and `H`.
3. Attacker resends `POST /webhooks` with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers [9](#0-8) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H` [4](#0-3) .
5. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body(B), ...)`, causing the app to process attacker-controlled data as if it originated from `victim-shop`.
