### Title
Unvalidated swap routes can steal unrelated caller tokens through the signed authorization tree - (File: `contracts/controller/src/strategies/swap.rs`)

### Summary
Controller strategy entrypoints accept caller-supplied opaque `swap` bytes and forward them to the configured router without restricting which venue or pool contract the route invokes. [1](#0-0)  A malicious venue called from that route can add an unrelated `token.transfer(caller, attacker, amount)` beneath the caller’s strategy authorization; if the victim signs the simulated authorization tree, the transfer executes. [2](#0-1) [3](#0-2) 

### Finding Description
`swap_collateral` authenticates only that `caller` owns or delegates the target account, then passes its `swap` argument into `withdraw_and_swap_from_supply`. [4](#0-3)  The shared router boundary authorizes one exact controller-to-router input transfer and invokes `router.execute_strategy`, but it performs no venue allowlist or authorization-tree restriction on code reachable through the supplied route. [5](#0-4)  The contract-side authorization itself has no sub-invocations, while the caller’s top-level authorization can cover deeper calls made during route execution. [6](#0-5) 

The same pattern is reachable through `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral`, all of which accept caller-controlled route bytes. [7](#0-6) [8](#0-7)  The regression fixture demonstrates that a route-selected pool can transfer an unrelated wallet asset and that simulation records that transfer as a child of the caller’s `swap_collateral` authorization. [9](#0-8) 

### Impact Explanation
A victim who signs the authorization tree produced for a malicious route can lose any spendable token balance named by the malicious venue, not merely the collateral amount being swapped. [3](#0-2)  This is theft of user funds and can exceed the strategy’s `amount_in` because the controller’s measured-input and output checks constrain only the router’s token balances. [10](#0-9) 

### Likelihood Explanation
An unprivileged attacker can deploy a malicious venue and distribute or return a crafted route for a victim to execute; no protocol role, leaked key, upgrade, or privileged configuration is required. [11](#0-10)  Exploitation requires the victim to submit that route and sign the enlarged authorization tree, so it depends on route-provider compromise or deception and on the client not rejecting unexpected child authorizations. [12](#0-11) 

### Recommendation
Restrict strategy execution to governance-recognized venue/pool addresses, or otherwise isolate route execution so calls made by a route cannot be authorized under the caller’s strategy authorization tree. [13](#0-12)  At minimum, all signing and simulation clients should decode the route and reject any authorization child other than the expected input transfer, but contract-side venue admission is the robust fix. [14](#0-13) 

### Proof of Concept
1. Deploy a malicious contract whose venue entrypoint calls `token.transfer(victim, attacker, victim_balance)` for an unrelated token held by the victim. [15](#0-14) 
2. Craft `swap` bytes whose route selects that malicious contract as a hop and otherwise returns enough output to satisfy the strategy checks. [16](#0-15) 
3. Have the victim invoke `swap_collateral(caller, account_id, current, amount, new, swap)` or another route-bearing strategy. [17](#0-16) 
4. Simulation records the malicious token transfer beneath the victim’s strategy authorization; once signed, enforcement accepts it and moves the unrelated wallet balance to the attacker. [18](#0-17) [3](#0-2)

fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.

    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
