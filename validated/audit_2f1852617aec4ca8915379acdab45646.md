Confirmed: the docs explicitly instruct developers to trust `data.shop` from the webhook payload (`docs/usage/webhooks.md:125-133`), and `ShopifyAPI::Webhooks::Registry.process` only validates the HMAC over the raw body before handing the unauthenticated `shop` header straight to the handler.

### Title
Webhook shop-domain header is not covered by HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `#shop` is read from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header [1](#0-0) . `Utils::HmacValidator.validate` verifies the HMAC only against `to_signable_string` (the body) [2](#0-1) , so the shop header is never authenticated. `Registry.process` validates the HMAC and then immediately forwards `request.shop` to the app's handler as the trusted tenant identifier [3](#0-2) .

### Finding Description
The identity binding that should hold is: `shop authenticated by HMAC == shop used to route/attribute the webhook data`. In this gem that equality is broken:
- Left side (authenticated): only the raw body bytes are covered by the HMAC — `hmac` is computed from the `hmac-sha256` header and compared against `HMAC(secret, raw_body)` [4](#0-3) [5](#0-4) .
- Right side (acted on): `request.shop`, taken verbatim from an attacker-controllable header with no cryptographic binding to the body or the HMAC [1](#0-0) .

Because the secret key (`Context.api_secret_key`) is shared across all shops that install a given app, any merchant who has installed the app receives valid `(raw_body, hmac)` pairs signed with that same shared secret for their own shop's events. Since the `shop` header is excluded from the signed content, that same valid `(raw_body, hmac)` pair remains valid when replayed with an arbitrary `x-shopify-shop-domain` header value. `Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching `WebhookMetadata.new(..., shop: request.shop, ...)` to the handler [3](#0-2) [6](#0-5) , so the handler never learns that `shop` was not part of the authenticated payload.

The gem's own documentation reinforces this trust: it tells implementers that `Registry.process` "will verify the request did indeed come from Shopify" and instructs them to key downstream work off `data.shop` directly [7](#0-6) [8](#0-7) , without ever mentioning that the shop value itself is unauthenticated.

### Impact Explanation
This is a cross-tenant integrity issue: a party who has installed the app on shop A (an "unprivileged" merchant relative to other tenants of the same app) can capture one legitimate webhook `(raw_body, hmac)` pair and replay it against the app's public webhook endpoint with the `shop` header set to shop B's domain. Any app that follows the gem's documented pattern of trusting `data.shop` (e.g., to look up the corresponding merchant record, update order/inventory state, or enqueue tenant-scoped background jobs) will apply attacker-supplied body content under another tenant's identity — cross-tenant access/data corruption, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
No secret material needs to be stolen: the attacker only needs (a) their own legitimate app installation to obtain at least one valid signed webhook, and (b) network access to POST to the app's public webhook endpoint with a modified `shop` header — both are trivially available to any merchant/attacker who installs the target app, and no rate limiting or additional signing of headers exists in this gem to prevent it.

### Recommendation
Bind the shop domain into the authenticated material before trusting it: either (a) include the shop domain header in the value that is HMAC-verified (deviates from Shopify's current signing scheme, so this must instead be handled at the app layer), or, more practically, document/enforce that `Registry.process`/`WebhookMetadata` callers must independently verify `data.shop` against a known, previously-recorded shop for the corresponding `webhook_id`/topic before acting on it, and update `docs/usage/webhooks.md` to state explicitly that `shop` is not covered by the HMAC and must not be trusted as a standalone tenant identifier.

### Proof of Concept
1. Install the target app on `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw POST body plus the `x-shopify-hmac-sha256` header value sent by Shopify.
2. Replay the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` because it only checks `HMAC(secret, raw_body)` [9](#0-8) .
4. `Registry.process` dispatches to the app handler with `data.shop == "victim.myshopify.com"` and `data.body` containing the attacker's order payload [3](#0-2) , causing the app to process/attribute attacker-controlled data under the victim tenant's identity.

```markdown
To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
