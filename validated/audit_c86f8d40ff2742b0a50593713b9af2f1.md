### Title
Webhook shop/topic identity spoofing via HMAC that only covers the request body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , so `Utils::HmacValidator.validate` only proves that the body bytes were signed by Shopify's `api_secret_key` [4](#0-3) . The `shop`, `topic`, and `webhook_id` values that `Registry.process` uses to route and tag the delivered data are read straight from HTTP headers and are never bound to that signature [2](#0-1) .

### Finding Description
The binding this code is supposed to enforce is: `hmac-verified(body) == identity(shop, topic)` — i.e., the tenant/topic asserted for a webhook must be the same tenant/topic whose secret produced the signature. In reality, `Request#hmac` decodes `X-Shopify-Hmac-Sha256` (a header) and `Request#to_signable_string` returns `@raw_body` alone [5](#0-4) . `shop`, `topic`, and `webhook_id` are pulled from separate, unsigned headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) [6](#0-5) . `Registry.process` only calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (the body) and compares it to the header-supplied HMAC [7](#0-6) . It then builds `WebhookMetadata` directly from `request.shop` and `request.topic` and hands it to the app's handler with no further check that those header values match anything cryptographically bound to the signature [8](#0-7) .

Since all shops that install the same app share the same `api_secret_key` (the key is per-app, not per-shop), any tenant that has legitimately installed the app can obtain a validly-signed webhook body/HMAC pair from Shopify for their own shop, then replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header to name a victim shop. The HMAC check still passes because it never covered those headers, and the app's handler receives `WebhookMetadata` claiming the victim's shop for attacker-supplied body content.

### Impact Explanation
This breaks tenant isolation: an app relying solely on this gem's webhook verification to authenticate which shop a webhook is "from" can be made to process attacker-controlled payloads under a victim shop's identity. Depending on the handler, this enables cross-tenant data injection/corruption (e.g., writing to the victim's records, triggering `shop/redact` or `customers/redact` handling against the wrong shop, or poisoning app state keyed by `shop`). This matches the Critical "cross-tenant access" impact category, since the shop-identity binding that the app is meant to trust from this gem is forgeable by any other app installer.

### Likelihood Explanation
Requires only that the attacker's own store have the app installed (an ordinary, unprivileged relationship to the app) and the ability to capture one of their own genuine webhook deliveries and replay it with a modified header to the public webhook endpoint — no access to `api_secret_key`, TLS interception, or victim credentials is needed.

### Recommendation
Bind the shop/topic/webhook identity to the signature: either include `shop`, `topic`, and `webhook_id` in the HMAC-signed payload used by `to_signable_string`, or require the consuming app to cross-check the delivered `shop` against a known/expected value (e.g., an offline session already on file) before trusting `WebhookMetadata`. At minimum, document prominently that `request.shop`/`request.topic` are not covered by the HMAC and must not be trusted as an authentication signal on their own.

### Proof of Concept
1. App merchant "attacker.myshopify.com" installs the app and triggers a webhook (e.g., `orders/create`) with body `B`; Shopify sends headers `X-Shopify-Hmac-Sha256: H(B)`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`.
2. Attacker captures this request and resends it to the app's webhook endpoint, only changing `X-Shopify-Shop-Domain` to `victim.myshopify.com` (body and HMAC header unchanged).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`; since `to_signable_string` returns only the unchanged body `B`, the HMAC still matches [1](#0-0) .
4. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: ...)`, i.e., attacker-controlled data attributed to the victim shop [8](#0-7) .
