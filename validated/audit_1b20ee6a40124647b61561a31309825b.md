### Title
Webhook HMAC only signs the raw body, not the `shop-domain` header, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` never binds the `x-shopify-shop-domain` (or `x-shopify-topic`) header to the HMAC signature. Any party that can obtain one genuinely-signed webhook (e.g., a merchant who has installed the app themselves and receives its own legitimate webhook deliveries) can replay that same body+HMAC pair to the app's webhook endpoint while substituting a different shop's domain in the header, and the signature check will still pass.

### Finding Description
`Registry.process` only validates the HMAC over the request: [1](#0-0) 
The HMAC validation itself calls `verifiable_query.to_signable_string`: [2](#0-1) 
But `Webhooks::Request#to_signable_string` is defined as just the raw body: [3](#0-2) 
while `shop` (and `topic`) are read directly, unsigned, from HTTP headers: [4](#0-3) 
The `shop` value that comes out of this unverified header is then handed straight to the developer's handler as the identity of the tenant the webhook is "for": [5](#0-4) 

The equality this breaks is: **shop the HMAC actually authenticates (over the raw body only) ≠ shop attributed to the webhook and passed to the handler (`request.shop`, from an unsigned header)**. This is the same identity-binding class named in the rules ("a shop authenticated versus the shop stored as a session key") — here it's "a shop delivered to the handler versus the shop actually covered by the signature."

Because the HMAC is computed with the app's single `client_secret` shared across every shop that installs the app (not a per-shop secret), any shop that has installed the app receives real webhook deliveries with valid `body + hmac` pairs signed by that shared secret. A malicious merchant can capture one such legitimately-signed delivery from their own store and resend it to the app's public webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain (and/or `x-shopify-topic` changed). `HmacValidator.validate` will still return `true` because it only checks the untouched raw body, so `Registry.process` will accept it and invoke the handler with `shop: <victim-shop>` and attacker-chosen body content.

### Impact Explanation
This crosses the tenant boundary the webhook system is meant to enforce: an app that trusts `request.shop` (as the library's own `WebhookMetadata` explicitly exposes it) to route mutations, look up per-shop records, or attribute compliance webhooks (e.g. `customers/redact`, `shop/redact`) can be made to act on the wrong tenant's data using attacker-supplied body content, purely from a merchant who legitimately installed the app once. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
The attacker only needs to install the app on their own store (a normal, unprivileged action any merchant can take) and receive one real webhook, then replay it with a modified `shop-domain` header to the same public endpoint — no access to `api_secret_key`, access tokens, or the victim's credentials is required.

### Recommendation
Bind the header-derived identity fields (`shop`, `topic`, `webhook_id`, `api_version`) into the signable content used for HMAC verification (or otherwise cryptographically bind the shop domain to the signed payload before trusting it), instead of only signing the raw JSON body in `Webhooks::Request#to_signable_string`.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; trigger any subscribed webhook topic and capture the real request Shopify sends: raw body `B` and header `x-shopify-hmac-sha256: H` (valid because it's signed with the app's shared secret).
2. Replay the request to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` in [6](#0-5)  passes because it only checks `B` against `H`.
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...)`, causing the app to act as though the (attacker-controlled) body belongs to the victim shop.
