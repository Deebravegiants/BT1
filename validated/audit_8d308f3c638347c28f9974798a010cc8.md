Based on my investigation, I found a concrete unprivileged-actor analog: the Vault gateway handler authorizes the request *after* it accepts an arbitrary, attacker-controlled `req.ID`, but the in-flight request de-duplication map (`activeRequests`) is keyed globally by that raw client-supplied `req.ID`, with no per-owner/per-sender namespacing.

### Title
Unauthenticated request-ID collision allows cross-user Denial of Service in Vault gateway handler - ([File: core/services/gateway/handlers/vault/handler.go])

### Summary
`HandleJSONRPCUserMessage` accepts any client-supplied `req.ID` (only checked for emptiness and length) and only enforces per-ID uniqueness after authorization via `newActiveRequest`, which stores requests in a single global map keyed solely by `req.ID`. Because the ID is fully attacker-controlled and not derived from, or scoped to, the authorized owner/session, any unprivileged client on the internet-facing gateway can pre-empt or collide with another user's in-flight request ID, denying that legitimate request.

### Finding Description
`HandleJSONRPCUserMessage` validates only that `req.ID` is non-empty and ≤200 characters [1](#0-0) . Authorization (via `requestProcessor.ProcessRequest`) happens after this check, and only then is `newActiveRequest` called, which rejects the request if the same `req.ID` string is already present in the shared `activeRequests` map [2](#0-1) . This map is a single, gateway-handler-wide `map[string]*activeRequest` [3](#0-2)  not partitioned by workflow owner, tenant, or session — so any two unrelated, unprivileged callers race on the same global keyspace defined entirely by client input.

The same pattern is repeated in the confidentialrelay gateway handler, whose `newActiveRequest` performs an identical un-scoped `req.ID` uniqueness check before any per-request identity isolation [4](#0-3) , and is explicitly covered by a test demonstrating the collision behavior [5](#0-4) .

This mirrors the reported bug class (a privileged-looking control — here, the request-slot reservation — that can be manipulated by an unprivileged party to deny service to others), except the actor here is any ordinary internet-facing gateway client rather than an admin: no special role is required to submit a `jsonrpc.Request` with an arbitrary `ID`.

### Impact Explanation
An unprivileged attacker who can predict or observe another user's in-flight `req.ID` (e.g., a workflow's own generated correlation ID, or a brute-forced/guessed short ID) can submit a duplicate request first, occupying the `activeRequests[req.ID]` slot. The legitimate user's subsequent request then fails with "request ID already exists," resulting in an inability to reach the vault/capability backend for that ID — a targeted, per-request Denial of Service reachable directly from the internet-facing gateway without authentication for the colliding submission (the colliding attempt itself may fail authorization, but the collision check occurs after the ID is claimed only for the authorized path currently — for `MethodPublicKeyGet` the ID check happens with no authorization at all) [6](#0-5) .

### Likelihood Explanation
Moderate: exploitation requires only network access to the gateway and knowledge (or a race/prediction) of the target's `req.ID`, which is far weaker than requiring a malicious/compromised admin as in the source report. If workflows use predictable or short IDs, or an attacker can observe pending IDs (e.g., via shared client tooling, logs, or timing), the collision is trivial to trigger.

### Recommendation
Scope the `activeRequests` (and analogous) de-duplication key by authenticated identity (e.g., `(authorizedOwner, req.ID)` composite key) rather than by the raw client-supplied `req.ID` alone, and perform the ID-uniqueness reservation only after authorization succeeds for every method (including `MethodPublicKeyGet`, which currently reserves an ID pre-authorization). Apply the same fix to `core/services/gateway/handlers/confidentialrelay/handler.go`.

### Proof of Concept
1. Attacker observes or guesses a target's outgoing `req.ID` for a `vault.secrets.*` call to the gateway (unauthenticated at the transport level; the JSON-RPC envelope's `ID` field is plaintext).
2. Attacker sends their own `jsonrpc.Request` with the same `ID` to `HandleJSONRPCUserMessage` before the victim's request is fully processed.
3. Whichever request wins the race populates `activeRequests[ID]` first via `newActiveRequest`; the other is rejected with `"request ID already exists: " + req.ID"` [7](#0-6) , denying the legitimate user's request — demonstrated directly by the existing test `TestConfidentialRelayHandler_DuplicateRequestID`, which shows the second submission with the same ID is rejected outright [5](#0-4) .

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], labels requestLabels, callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID, "executionID", labels.ExecutionID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		labels:    labels,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}

func TestConfidentialRelayHandler_DuplicateRequestID(t *testing.T) {

		Method: MethodCapabilityExec,
		Params: &params,

	require.NoError(t, err)

	cb2 := common.NewCallback()
	err = h.HandleJSONRPCUserMessage(t.Context(), req, cb2)
	require.ErrorContains(t, err, "request ID already exists")
}
