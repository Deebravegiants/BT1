Audit Report

## Title
Node crash via nil pointer dereference in vault `GetPublicKey` gateway handler when `params` is null - ([File: core/capabilities/vault/gw_handler.go])

## Summary
`GatewayHandler.handlePublicKeyGet` unmarshals `*req.Params` without checking whether `req.Params` is nil, unlike every sibling handler path (Create/Update/Delete/List) which is guarded by an explicit `req.Params == nil` check inside `GatewayVaultRequestProcessor`'s per-method handlers before the handler methods run. A gateway forwarding a `vault_getPublicKey` JSON-RPC request with `params` omitted or `null` will cause `handlePublicKeyGet` to dereference a nil pointer and panic, and since the calling `readLoop` goroutine in the connector has no `recover()`, this crashes the node's gateway message loop.

## Finding Description
`HandleGatewayMessage` routes `vaulttypes.MethodPublicKeyGet` directly to `h.handlePublicKeyGet` without any authorization/validation pipeline step, unlike Create/Update/Delete/List which go through `h.requestProcessor.ProcessRequest`. Inside `handlePublicKeyGet`, `json.Unmarshal(*req.Params, r)` directly dereferences `req.Params`, a `*json.RawMessage`. If `req.Params` is `nil` (client omits `params` or sends `"params": null`), this dereference panics. All other request kinds are protected because their respective `process*SecretsRequest`/`processListSecretIdentifiersRequest` functions in `gateway_vault_request_processor.go` explicitly check `if req.Params == nil` and return a typed error before ever calling `json.Unmarshal`. `MethodPublicKeyGet` bypasses this shared validation entirely and has no equivalent guard of its own.

The panic occurs inside `GatewayHandler.HandleGatewayMessage`, which is invoked from `gatewayConnector.readLoop` — a per-gateway goroutine started in `Start`. That call site does not wrap `handler.HandleGatewayMessage` in a `recover()`, so an unrecovered panic will propagate up and, per default Go runtime behavior, crash the entire process (not just the goroutine).

## Impact Explanation
This is a legitimate availability bug: an unauthenticated request forwarded by the Gateway for `vault_getPublicKey` with null/absent `params` reaches the vulnerable code before any authorization step runs, and panics the node process, since the connector's read loop performs no panic recovery around handler invocation. This matches the "node crash / denial of service" impact class, consistent with the CVSS `A:L` framing cited in the report.

## Likelihood Explanation
High. No credentials, prior state, or complex setup are required — a single JSON-RPC request with method `vault_getPublicKey` and `params` omitted or `null`, forwarded through the Gateway to a node's `GatewayHandler.HandleGatewayMessage`, is sufficient to trigger the crash, and it is fully repeatable.

## Recommendation
Add an explicit `if req.Params == nil` guard at the start of `handlePublicKeyGet`, returning `h.errorResponse(ctx, gatewayID, req, api.UserMessageParseError, errors.New("request params must not be nil"))` before calling `json.Unmarshal`, mirroring the pattern in `processCreateSecretsRequest`/`processUpdateSecretsRequest`/`processDeleteSecretsRequest`/`processListSecretIdentifiersRequest`. Additionally, consider wrapping `handler.HandleGatewayMessage` invocation in `gatewayConnector.readLoop` with a `recover()` as defense-in-depth against similar bugs in any current or future handler.

## Proof of Concept
1. Start a node with the Vault gateway handler registered and a Gateway forwarding messages to it (or directly unit-test the handler).
2. Construct `req := &jsonrpc.Request[json.RawMessage]{ID: "poc-1", Method: vaulttypes.MethodPublicKeyGet, Params: nil}` (i.e. `params` omitted, matching a client that omits `params` or sends `"params": null`).
3. Call `gatewayHandler.HandleGatewayMessage(ctx, gatewayID, req)`.
4. Observe a panic at `core/capabilities/vault/gw_handler.go:366` (`json.Unmarshal(*req.Params, r)`), which is unrecovered in `core/services/gateway/connector/connector.go`'s `readLoop`, crashing the process. A minimal Go test invoking `handlePublicKeyGet` directly with a `nil` `req.Params` reproduces the panic deterministically.
