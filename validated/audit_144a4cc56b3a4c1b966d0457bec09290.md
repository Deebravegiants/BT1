### Title
Panic via unchecked-length `copy_from_slice` on relayer-supplied BEEFY vote signatures - (File: `evm/rust/src/conversions.rs`)

### Summary
The Rust mirror of the `EcdsaBeefy`/`SP1Beefy` proof types converts an ABI-decoded `Vote.signature` (`Bytes`, attacker/relayer-controlled length) into a fixed 65-byte array with `copy_from_slice` and no length check first, unlike the analogous, correctly-guarded conversion elsewhere in the codebase.

### Finding Description
`impl From<Vote> for SignatureWithAuthorityIndex` copies the raw signature bytes straight into a `[u8; 65]` buffer without verifying the source length: [1](#0-0) 

`sig_bytes` originates from `value.signature`, an alloy `Bytes` field of the Solidity-mirrored `Vote` struct that is populated directly from a relayer-submitted, ABI-encoded BEEFY consensus proof (`RelayChainProof.signedCommitment.votes`). This conversion is invoked when turning an incoming `RelayChainProof` into the internal `MmrProof` used by the verifier: [2](#0-1) 

`Vec<u8>::copy_from_slice` in Rust panics (rather than silently misreading memory, as the C `memcpy` in the libtiff CVE does) whenever the source and destination slice lengths differ. Because nothing upstream constrains `signature`'s length to exactly 65 bytes before this conversion runs, any relayer able to submit or relay a BEEFY/SP1-BEEFY consensus proof can supply a `Vote.signature` of any other length and trigger a panic during proof decoding/verification.

This is the same bug class as the reported libtiff issue — a length-unchecked buffer copy in a decode/parse path fed by untrusted input — but the trusted-side prover code in this repository (`modules/consensus/beefy/prover/src/lib.rs`) already guards this exact operation: [3](#0-2) 

showing the length check (`if sig.len() != 65 { return None; }`) was recognized as necessary on the honest-prover path but is missing on the untrusted-input conversion path in `evm/rust/src/conversions.rs`.

### Impact Explanation
A panic inside proof conversion/verification for a BEEFY consensus update is a denial-of-service against the consensus-verification route: it can abort processing of the malformed message and, depending on the calling context (native host/relayer/light-client process), crash or halt the worker handling BEEFY consensus updates for that route, preventing legitimate consensus/state updates and therefore blocking message delivery on that route until the process is restarted or the malformed input is filtered out externally. This matches the "route unable to deliver messages" impact criterion.

### Likelihood Explanation
Likelihood is high for reachability: BEEFY/SP1-BEEFY consensus proofs are explicitly designed to be submitted/relayed permissionlessly (any relayer can submit a consensus update), and the vulnerable conversion sits directly in the decode path for such proofs, requiring only that one `Vote.signature` field have a length other than 65 bytes — trivial for a malicious or buggy relayer to construct.

### Recommendation
Add an explicit length check before `copy_from_slice` in `impl From<Vote> for SignatureWithAuthorityIndex`, returning a `TryFrom`/`Result` error instead of an infallible `From`, mirroring the existing guard used in `modules/consensus/beefy/prover/src/lib.rs` (`if sig.len() != 65 { ... }`). Propagate the error through `RelayChainProof -> MmrProof` (and any other call site of this conversion) so malformed proofs are rejected with a typed error rather than panicking.

### Proof of Concept
1. Construct a `RelayChainProof` (as ABI-decoded by the `evm/rust` crate) where `signedCommitment.votes[i].signature` has a length other than 65 bytes (e.g., 64 or 66 bytes) — trivial since `Vote.signature` is an unconstrained `bytes` field in the ABI encoding.
2. Submit/relay this proof to whatever component performs `Into::<MmrProof>::into(relay_chain_proof)` (the `From<RelayChainProof> for MmrProof` conversion at `evm/rust/src/conversions.rs:368-389`).
3. During conversion, `SignatureWithAuthorityIndex::from(vote)` executes `signature.copy_from_slice(&sig_bytes)` with `sig_bytes.len() != 65`, which panics (`source slice length (N) does not match destination slice length (65)`), aborting proof processing for that consensus update.

Note: I was unable to fully trace, within the available tool-call budget, the exact external entry point (native host module vs. off-chain relayer binary) that first calls `RelayChainProof -> MmrProof` in `evm/rust`; this should be confirmed by a follow-up investigation to precisely characterize the blast radius of the panic (single request failure vs. process crash affecting all pending updates).
