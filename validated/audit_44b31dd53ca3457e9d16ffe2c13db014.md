### Title
`IntentGatewayV2.placeOrder()` Locks Excess Native Token Overpayment Forever (Tron Deployment) - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron-targeted fork of `IntentGatewayV2.sol` accepts more native token (`msg.value`) than required in `placeOrder()` but, unlike the canonical EVM version of the same contract, never refunds the unspent remainder to the caller. This exactly matches the reported bug class: a payment-acceptance function that takes `msg.value` greater than what is actually needed, does not return/revert the surplus, and has no admin/withdraw path to recover it — permanently locking user funds in the contract.

### Finding Description
`placeOrder()` tracks a running `msgValue` counter, deducting the native-token input escrow amount(s) [1](#0-0)  and, if `order.fees > 0`, deducting a fee-swap amount via `swapETHForExactTokens` [2](#0-1) . Both of these operations only consume the portion of `msgValue` they actually need (`swapETHForExactTokens` refunds unspent value only to `msg.sender` when called directly by an EOA, but here it is called from within the contract, so any residual ETH from the swap and any residual `msgValue` after both deductions simply remain unaccounted for). The function ends by emitting `OrderPlaced` with **no logic that returns leftover `msgValue` to `msg.sender`** [3](#0-2) .

This is a direct regression relative to the canonical EVM contract `evm/src/apps/IntentGatewayV2.sol`, which explicitly refunds any unspent native tokens after the same escrow/fee-swap sequence: `if (msgValue > 0) { _sendValue(msg.sender, msgValue); }` [4](#0-3) , and this behavior is explicitly unit-tested as `testPlaceOrder_RefundsExcessNativeToken` and `testPlaceOrder_FeeSwap_RefundsExcessNativeToken` for the canonical contract [5](#0-4) [6](#0-5) . The Tron variant is missing this refund entirely.

I was unable to find any admin/owner function in the Tron file capable of sweeping stray native ETH out of the contract to recover such stuck funds (only order-lifecycle `withdraw`/refund paths tied to specific commitments exist), consistent with the external report's note that there is no mechanism for the admin to reclaim overpaid funds.

### Impact Explanation
Any user who calls `placeOrder{value: X}()` on the Tron deployment with `X` greater than the sum of native-token input amounts plus the native fee actually consumed by the Uniswap swap will have the difference permanently locked in the `IntentGatewayV2` contract with no path to recovery — for the user, for the protocol, or for governance. Because overpayment is easy to trigger unintentionally (e.g., estimating the Uniswap fee swap cost slightly high, as is explicitly anticipated and handled by the sibling EVM contract's `testPlaceOrder_FeeSwap_RefundsExcessNativeToken` test), this results in a real and recurring loss of user funds — a permanent freezing/loss-of-funds condition reachable directly by any unprivileged user submitting a single `placeOrder` transaction.

### Likelihood Explanation
High. `placeOrder` is the primary, permissionless entry point of the Intent Gateway and is called by every ordinary user placing an order; overpayment of `msg.value` is a routine and expected occurrence (the SDK/documentation itself recommends sending a buffer above the estimated fee, as seen for the sibling EVM contract's fee-swap flow) — the same usage pattern on the Tron deployment silently forfeits the buffer instead of refunding it.

### Recommendation
Port the missing refund logic from the canonical EVM contract into the Tron `IntentGatewayV2.placeOrder()`: after escrowing inputs and swapping/collecting fees, if `msgValue > 0`, send the residual back to `msg.sender` (mirroring `evm/src/apps/IntentGatewayV2.sol` lines 394-397). Add the equivalent overpayment-refund regression tests that already exist for the canonical EVM contract to the Tron test suite to prevent future regressions.

### Proof of Concept
1. On the Tron-deployed `IntentGatewayV2`, construct an `Order` with a single native-token (`address(0)`) input of amount `inputAmount` and `order.fees = 0`.
2. Call `placeOrder{value: inputAmount + overpayment}(order, graffiti)` from a user account.
3. Inspect the escrow deduction logic — only `inputAmount` is deducted from `msgValue` [1](#0-0) ; the function then proceeds directly to emitting `OrderPlaced` with no further use or return of the remaining `msgValue` [3](#0-2) .
4. Observe that the user's balance decreases by `inputAmount + overpayment` while only `inputAmount` is credited to escrow — the `overpayment` amount remains stuck in the contract's native balance indefinitely, unlike the identical scenario on the canonical EVM contract (`testPlaceOrder_RefundsExcessNativeToken`) where the overpayment is refunded and the user's balance decreases by exactly `inputAmount`.

    /// @notice Excess msg.value beyond native input legs is refunded to the user.
    function testPlaceOrder_RefundsExcessNativeToken() public {
        uint256 inputAmount = 1 ether;
        uint256 overpayment = 0.5 ether;

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(0), amount: inputAmount}); // native ETH

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: 1000 * 1e6});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        uint256 userBalBefore = user.balance;

        vm.prank(user);
        intentGateway.placeOrder{value: inputAmount + overpayment}(order, bytes32(0));

        // User should only have spent inputAmount, overpayment refunded
        assertEq(user.balance, userBalBefore - inputAmount, "Overpayment should be refunded");
        assertEq(address(intentGateway).balance, inputAmount, "Gateway should only hold escrowed amount");
    }

    /// @notice placeOrder with fee swap refunds unused ETH after swapETHForExactTokens.
    function testPlaceOrder_FeeSwap_RefundsExcessNativeToken() public {
        uint256 inputAmount = 1000 * 1e6;
        uint256 feeAmount = 1 * 1e18; // 1 DAI worth of fees

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 1000 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 1000,
            nonce: 0,
            fees: feeAmount,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        uint256 userEthBefore = user.balance;

        vm.startPrank(user);
        usdc.approve(address(intentGateway), inputAmount);
        // Send 5 ETH for a fee swap that should cost much less
        intentGateway.placeOrder{value: 5 ether}(order, bytes32(0));
        vm.stopPrank();

        // User should get back most of the 5 ETH — the swap only needed a tiny fraction
        uint256 ethSpent = userEthBefore - user.balance;
        assertTrue(ethSpent < 1 ether, "User should have been refunded most of the 5 ETH");
