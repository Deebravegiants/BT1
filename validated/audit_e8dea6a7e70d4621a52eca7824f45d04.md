Based on my review of the webhook verification path, I found a genuine identity-binding gap that matches the requested bug class ("a field acted on but not covered by the HMAC").

### Title
Webhook `shop` tenant identifier is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC of the raw request body, but the `shop` value used to attribute the webhook to a specific merchant tenant is read from an HTTP header that is never included in the HMAC-signed material. Any party capable of obtaining one genuine, validly-signed webhook delivery (e.g. an attacker who installs the host app on their own store) can replay that exact body/HMAC pair while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header to any other shop the app serves, and the gem will accept it as authentic for the victim tenant.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC purely over `to_signable_string`, and for webhooks that string is defined as the raw body only: [1](#0-0) 

The `shop` accessor, however, is pulled straight from an unauthenticated header with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` validates only the HMAC and then immediately forwards `request.shop` to the app's handler as the trusted tenant identifier: [3](#0-2) 

The equality the gem implicitly (but incorrectly) asserts is:
`shop used for tenant attribution (WebhookMetadata#shop, from unauthenticated header)` == `shop bound by the cryptographic proof (HMAC over raw_body only)`

These two are disjoint: the HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every shop that installs the app — it is not shop-specific. Any shop owner that installs the app can capture one legitimate webhook delivery (valid body + HMAC, signed for their own shop) and resend that exact byte-identical body/HMAC pair to the app's webhook endpoint while altering only the `shop-domain` header to name a different, victim shop that also uses the same app. Because `to_signable_string` never incorporates the shop header, `HmacValidator.validate` still succeeds, and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop domain — exactly as documented for host apps to use for tenant routing: [4](#0-3) [5](#0-4) 

The docs explicitly promise `process` "will verify the request did indeed come from Shopify" — but the verification only proves body integrity/authenticity, not shop identity, so a host app trusting `data.shop` for cross-tenant routing (as the gem's own documented example does) can be tricked into applying another tenant's data or webhook effects to the wrong shop.

### Impact Explanation
This breaks the tenant boundary the gem is meant to enforce for webhook processing: a shop that has legitimately installed the app can cause the gem to report an HMAC-"verified" webhook as belonging to an arbitrary other shop. Downstream, host applications that use `data.shop` (as directed by this gem's own documentation) to route webhook effects (e.g., updating shop-scoped local records, triggering `shop/redact`/`customers/redact` mandatory compliance webhooks, or enqueueing per-shop background jobs) can have those effects misattributed to a victim tenant, constituting cross-tenant data confusion/injection.

### Likelihood Explanation
Exploitation requires only an internet-reachable webhook endpoint and the ability to install the target app on any Shopify store (including a free development store), which grants the attacker at least one genuinely signed webhook body/HMAC pair to replay with a forged `shop-domain` header. No access to `api_secret_key`, tokens, or privileged accounts is needed.

### Recommendation
Bind the shop (and ideally the webhook id/topic) into the value that is cryptographically verified — e.g., include the `shop-domain`, `topic`, and `webhook-id` headers in the signable string used by `Utils::HmacValidator`, or require host apps to cross-check `request.shop` against an existing, previously-established session/tenant record before trusting it, and clearly document this requirement in `docs/usage/webhooks.md`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Shopify delivers a legitimate webhook to the app's callback URL with a valid `X-Shopify-Hmac-Sha256` header computed over the raw body using the app's shared `client_secret`.
3. Attacker captures this raw body and HMAC value.
4. Attacker resends an HTTP POST to the same webhook endpoint with the identical raw body and HMAC header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses the forged shop header; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the (unchanged) body/HMAC and succeeds.
6. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload actually originated from, and was signed for, the attacker's own shop.
