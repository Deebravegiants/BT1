### Title
`findMatchingWithdrawal` matches by `assetId` only, misreporting status/txHash across withdrawals of the same token to different destinations in a batch NEAR transaction - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`describeWithdrawal` calls `findMatchingWithdrawal`, which selects the first entry in `response.withdrawals` whose `nep141:${w.data.near_token_id}` equals `args.withdrawalParams.assetId`, ignoring `destinationAddress`, `amount`, and index entirely. When a single NEAR transaction batches two `ft_withdraw` intents for the same `assetId` to different `destinationAddress`es, `describeWithdrawal` for both `WithdrawalIdentifier`s resolves to the exact same array element, so the status/txHash reported for index 0 can actually belong to the withdrawal at index 1 (or vice versa).

### Finding Description
The broken equality is: `describeWithdrawal(wid_i).status/txHash == outcome_of_withdrawal_i`. This should hold for every `i` in a batch, but the implementation breaks it whenever two or more withdrawal identifiers in the same batch share `assetId`.

The code path: `PoaBridge.describeWithdrawal` [1](#0-0)  calls `getWithdrawalStatusWithRetry` which queries the POA bridge API keyed only by `args.tx.hash` (the shared NEAR transaction hash for the whole batch) [2](#0-1) , returning an unsorted array of all withdrawals extracted from that transaction. `findMatchingWithdrawal` then returns `withdrawals.find(w => nep141:${w.data.near_token_id} === assetId)` — the first match by asset only [3](#0-2) . The function's own comment explicitly states: "multiple withdrawals of the same token in a single transaction are not supported."

Attacker's exact input: an ordinary user calls `sdk.signAndSendWithdrawalIntent`/`processWithdrawal` with `withdrawalParams: WithdrawalParams[]` containing two entries with the same `assetId` (e.g., `nep141:usdt....omft.near`) but different `destinationAddress` — e.g., index 0 → attacker's own address, index 1 → victim's address. This is a documented, supported usage pattern (batch withdrawals of the same/different tokens per the README) [4](#0-3) ; nothing in `supports()`, `validateWithdrawal()`, or `createWithdrawalIdentifiers` deduplicates or rejects same-`assetId` entries in a batch — each entry is validated independently and assigned an `index` purely from a per-route counter [5](#0-4) .

Exploit flow: after the batch intent settles, `watchWithdrawal`/`createWithdrawalCompletionPromises` calls `bridge.describeWithdrawal({...wid})` per index [6](#0-5) . Both calls hit the same `tx.hash`, get the same `withdrawals` array, and `findMatchingWithdrawal` returns the identical first-matching element for both indices regardless of `destinationAddress`. If withdrawal 1 (to victim) completes first/only, `describeWithdrawal` for index 0 (attacker's own withdrawal) will report `{status: "completed", txHash: <victim's tx>}` even though the attacker's own withdrawal may still be pending or different.

Existing guards do not catch this: `validateAddress`/`compareAddresses` only validate a single address against a single token at intent-creation time and don't participate in status matching; `supports()` only routes by asset/route; the POA API itself doesn't disambiguate same-token entries either (per the code comment), so no downstream check corrects the mismatch.

### Impact Explanation
Nothing is directly re-signed or re-debited, but the SDK **misreports** which real-world outcome (destination tx hash / completion status) corresponds to which caller-supplied withdrawal index. An integrator that credits/refunds a user based on `describeWithdrawal`/`watchWithdrawal` results keyed by index can attribute the wrong destination-chain transaction to the wrong withdrawal, causing double-crediting or crediting a withdrawal as "completed" when it is not, or vice versa. This matches the High/Critical category "a status or hash misreport making an integrator credit or refund twice." The condition is deterministic and repeatable for every batch that contains ≥2 same-`assetId` entries with distinct destinations.

### Likelihood Explanation
Preconditions: attacker only needs to submit a self-authored batch withdrawal (their own funds/keys) with two `ft_withdraw` entries sharing `assetId` but differing `destinationAddress`. This is fully within normal, documented SDK usage (batch withdrawals) and requires no privileged access, no relayer/RPC compromise, and no bypass of validation. Cost is a single normal transaction; the bug is deterministic whenever this asset-collision condition occurs, not merely theoretical — it is explicitly acknowledged as an unsupported case in the code's own comment, confirming the maintainers are aware the matching is not index/address-safe.

### Recommendation
Match withdrawals by more than `assetId` — additionally filter/sort candidates by `destinationAddress` (`data.address`) and `amount`, or track a stable per-transaction ordinal (e.g., ordered by `data.amount` combined with intent order, as suggested in the existing comment) so each `WithdrawalIdentifier.index` deterministically maps to the correct POA withdrawal record. At minimum, throw/flag an error in `createWithdrawalIdentifiers` or `supports()` when a batch contains ≥2 same-route, same-`assetId` withdrawals, to prevent silently returning wrong results until proper per-entry matching (e.g., by destination address + amount) is implemented.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
