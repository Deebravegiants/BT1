### Title
`detect_fraud` unconditionally returns `Ok(false)`, causing fail-open fraud detection and unauthorized upload of fraudulent biometric captures - ([File: src/plans/mod.rs])

### Summary
`MasterPlan::detect_fraud` in `src/plans/mod.rs` always returns `Ok(false)` regardless of the biometric pipeline content, because the underlying fraud-check implementation in `src/plans/fraud_check.rs` has `N_FRAUD_CHECKS` set to `0` and its `Report::fraud_checks()`/`fraud_detected()` always evaluate to no-fraud. This means any physically-presented fraud signal (contact lenses, printed face, multiple faces) that would normally be flagged by the Fraud Check Engine is silently ignored, and `run_signup` proceeds to classify the signup as `SignupReason::Normal`, packaging and uploading the (possibly fraudulent) biometric data via `build_pcp`/`upload_pcp_tier_0`.

### Finding Description
In `run_signup` (`src/plans/mod.rs:558-571`), the fraud gate is computed as:
```
let fraud_detected = !self.skip_fraud_checks()
    && self.detect_fraud(orb, debug_report, pipeline.as_ref()).await?;
let signup_reason = if pipeline.is_none() {
    SignupReason::Failure
} else if fraud_detected {
    SignupReason::Fraud
} else {
    SignupReason::Normal
};

`detect_fraud` (`src/plans/mod.rs:1392-1406`) is implemented as:

    orb.set_phase("Fraud detection").await;

    Ok(false)

``` [2](#0-1) 

Even when the pipeline `Some(pipeline)` is present (i.e., biometric capture succeeded), the function never inspects the pipeline output for fraud indicators — it just returns `false` unconditionally for any non-`None` pipeline. The backing implementation of the fraud engine confirms this is not incidental: `src/plans/fraud_check.rs` defines `const N_FRAUD_CHECKS: usize = 0;` with the comment `"FOSS: This is set to 0 because we manually deleted all fraud checks"`, so `Report::fraud_checks()` returns `[]`, `fraud_checks_strict()` returns `[]`, and `fraud_detected()`/`fraud_detected_with_config()` can never be `true`. [3](#0-2) [4](#0-3) 

Given a successful `biometric_pipeline` call yielding `Some(pipeline)` (`src/plans/mod.rs:1290-1388`), `fraud_detected` is always `false`, forcing `signup_reason = SignupReason::Normal` (`src/plans/mod.rs:565-571`), which then flows into `build_pcp` and `upload_pcp_tier_0` (`src/plans/mod.rs:580-612`), packaging and uploading the biometric data under real backend/self-custody keys as if the signup were genuine. There is no other fail-closed gate in this path — `skip_fraud_checks()` is feature-gated to `allow-plan-mods` builds and defaults to `false` in production (`src/plans/mod.rs:1850-1857`), so it does not mitigate this; the actual fraud evaluation logic itself is the broken component. [5](#0-4) 

### Impact Explanation
This allows an unprivileged attacker physically present at the Orb (e.g., wearing contact lenses, presenting a printed/replayed face, or having multiple faces in frame) to have their fraudulent capture classified as `SignupReason::Normal` instead of `SignupReason::Fraud`. The fraudulent biometric data is then encrypted and uploaded via `upload_pcp_tier_0`/tier1/tier2 as though it were a legitimate signup, defeating the liveness/fraud enforcement that is supposed to be fail-closed before biometric enrollment/upload. This corresponds to a liveness/fraud-bypass class impact under the Orb bounty scope — fraudulent capture is treated and stored as genuine.

### Likelihood Explanation
The precondition is simply that the attacker completes `biometric_pipeline` with any pipeline output (`Some(pipeline)`), which is the normal/expected outcome of a completed capture regardless of fraud indicators (occlusion/contact-lens/multi-face detection is not part of `biometric_pipeline`'s success/failure decision — see `biometric_pipeline::Plan::run` returning `Some`/`None` only based on agent/model errors, not fraud content). Since `detect_fraud` is unconditional and deterministic, this is 100% reproducible on every signup attempt, requiring no special access, tools, or timing — only presenting fraud-indicative content to the cameras during a normal signup flow.

### Recommendation
Restore the Fraud Check Engine so that `detect_fraud` actually evaluates the pipeline's fraud-relevant outputs (contact lenses, occlusion, multiple faces, liveness) and returns `true` for any triggered check, and ensure `Report::fraud_checks_strict()` treats missing/incomplete fraud data as fraud detected (fail-closed), matching the documented invariant that fraud verdicts must never default to "pass."

### Proof of Concept
Unit test in `src/plans/fraud_check.rs` (or an integration test around `MasterPlan::detect_fraud`):
```rust
#[test]
fn fraud_detected_reflects_known_fraud_indicators() {
    // Construct a Report/BackendConfig representing a signup where
    // e.g. contact-lens or multiple-face fraud signals are present.
    let report = Report { /* set fields indicating fraud, once checks exist */ };
    assert!(report.fraud_detected(), "fraud must be flagged when indicators are present");
}
```
Currently this fails because `Report` has no fields (`Report {}`), `N_FRAUD_CHECKS == 0`, and `fraud_detected()` always returns `false` regardless of input, demonstrating the fail-open condition. An invariant/property test can additionally assert: for any `Pipeline` constructed with simulated fraud-indicative fields, `MasterPlan::detect_fraud(...)` must return `Ok(true)`, and `signup_reason` must never resolve to `SignupReason::Normal` when such indicators are present — this currently always fails, confirming the vulnerability.
