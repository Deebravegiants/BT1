### Title
Cross-chain `RedeemEscrow` payout is hardcoded to `msg.sender`, permanently stranding solver proceeds when the filler operates from a contract address not deployed identically on the source chain - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`_fillCrossChain` in `ExtrinsicIntents.sol` dispatches the `RedeemEscrow` message to the source chain using `msg.sender` (the filler's address on the *destination* chain) as the sole beneficiary, with no way for the solver to specify a different receiving address for the source chain. This mirrors the Maia H-03 pattern: an address that is only meaningful/controlled on one chain is used verbatim as the fund recipient on a different chain, and once the cross-chain message is dispatched the beneficiary can never be changed.

### Finding Description
In `_fillCrossChain`, the solver fills an order on the destination chain and the contract immediately encodes the redemption beneficiary as its own `msg.sender`: [1](#0-0) 

This body is posted to the source chain's gateway instance via `_post`, and on arrival `onAccept` calls `_withdraw`, which transfers the escrowed input tokens directly to that raw `beneficiary` address with a plain `safeTransfer`/native `.call`: [2](#0-1) 

Unlike `order.user` (chosen once by the user at order placement and used consistently as their own refund identity), the `RedeemEscrow` beneficiary is derived automatically from whatever address happens to call `fillOrder` on the destination chain — there is no field in `FillOptions` allowing the solver to designate a distinct, chain-appropriate receiving address: [3](#0-2) 

If a solver fills using a smart-contract wallet/proxy (common for flash-loan-funded or session-key solver accounts) rather than a plain EOA, that contract address exists at a specific address on the destination chain but is not guaranteed to be deployed with the same code (or at all) at that same address on the source chain. Once `_fillCrossChain` dispatches the `RedeemEscrow` request, the beneficiary is fixed — there is no redeem/retry path that lets the solver redirect proceeds to a different address, unlike `IHost`'s relayer-fee refund-on-timeout mechanism which at least returns fees to the `payer`.

### Impact Explanation
If the solver's `msg.sender` address has no usable account/contract on the source chain (or is later found to have unrelated code deployed there by a third party via CREATE2 collision), the escrowed input tokens released by `_withdraw` are sent to that raw address permanently. Since `EscrowReleased` marks `_filled[commitment] = beneficiary` and the tokens have already left `_orders` accounting, there is no recovery mechanism — the solver's proceeds are irrecoverably lost, a concrete freezing-of-funds impact matching the Maia H-03 bug class (recipient address valid on one chain but not guaranteed to be a controllable account on the other).

### Likelihood Explanation
Any unprivileged solver/filler can trigger this by simply calling `fillOrder` on the destination chain from a smart-contract address (e.g., an AA/session-key smart account or a flash-loan wrapper contract) that is not identically deployed on the source chain. This requires no malicious admin, governance, or relayer collusion — it is reachable from a single, ordinary `fillOrder` transaction, and the resulting cross-chain `RedeemEscrow` beneficiary is immutable once dispatched.

### Recommendation
Add an explicit, solver-specified beneficiary field to `FillOptions` (or the `fillOrder` call) for the `RedeemEscrow` payout, decoupled from `msg.sender`, so solvers using contract-based accounts can designate a receiving address they control on the source chain, mirroring how `order.user`/`order.output.beneficiary` are explicitly and independently supplied rather than inferred from a caller's context on a different chain.

### Proof of Concept
1. Solver deploys/operates a smart-contract wallet `S` on the destination chain only (e.g., via a destination-chain-specific factory or session-key AA account), with no identical contract at that address on the source chain.
2. Solver calls `fillOrder(order, options)` on the destination chain from `S`; `_fillCrossChain` sets `_filled[commitment] = S` and posts `RedeemEscrow` with `beneficiary = bytes32(uint256(uint160(S)))`. [4](#0-3) 
3. The message is relayed to the source chain; `onAccept` → `_withdraw` sends the escrowed input tokens to raw address `S` on the source chain. [2](#0-1) 
4. Because `S` has no deployed code (or unrelated code) on the source chain, and the beneficiary field cannot be altered post-dispatch, the transferred tokens are permanently inaccessible to the solver.

    function _fillCrossChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            (uint256 protocolShare, uint256 beneficiaryShare) =
                _splitSurplus(solverAmount - totalRequired, order.output.call.length > 0);

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                _sendValue(beneficiary, beneficiaryTotal);
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        // Native dispatch fee only if the solver sent enough to cover it; else the fee token.
        uint256 nativeFee = options.nativeDispatchFee;
        if (nativeFee > msgValue) nativeFee = 0;
        msgValue -= nativeFee;
        _post(
            order,
            _body(RequestKind.RedeemEscrow, commitment, order.inputs, bytes32(uint256(uint160(msg.sender)))),
            options.relayerFee,
            nativeFee
        );

        // Refund any unspent native tokens to the solver.
        if (msgValue > 0) {
            _sendValue(msg.sender, msgValue);
        }

        emit OrderFilled({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: order.inputs});

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;

            uint256 amount = body.tokens[i].amount;

struct FillOptions {
    /// @dev The fee paid in feeTokens to the relayer for processing transactions.
    uint256 relayerFee;
    /// @dev The fee paid in native tokens for cross-chain dispatch.
    uint256 nativeDispatchFee;
    /// @dev Last block number at which this fill may be executed. Zero means no bound.
    ///
    /// @dev A solver bidding through the coprocessor signs this calldata and then has no
    /// further say in when it is used: the order's `deadline` is chosen by the placer with
    /// no upper limit, and retracting the bid on Hyperbridge does not reach this chain. The
    /// placer holds the session key, so without a bound here they may sit on a signed bid
    /// and execute it whenever the price has moved in their favour. Setting this caps how
    /// long the quoted price stands.
    ///
    /// @dev Denominated in blocks, matching `order.deadline`, so both are read against the
    /// same clock (`_blockNumber()`, which is the L2 block number where that differs).
    uint256 validUntil;
    /// @dev The output tokens with amounts the solver is willing to give
    /// @dev Must be strictly >= the amounts requested in order.output.assets
    TokenInfo[] outputs;
}
