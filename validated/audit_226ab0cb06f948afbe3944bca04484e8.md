Confirmed: `Webhooks::Request#to_signable_string` returns only `@raw_body` (`lib/shopify_api/webhooks/request.rb:36-38`), while `#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header (`lib/shopify_api/webhooks/request.rb:20-23`) which is **not** part of the HMAC-signed content. `Registry.process` validates only the body-derived HMAC and then dispatches the handler using the unauthenticated header-derived `shop` value (`lib/shopify_api/webhooks/registry.rb:188-199`).

### Title
Webhook `shop` identity is taken from an unauthenticated header not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC computed over the raw request body [1](#0-0) . The `shop` identity used to route/act on that webhook, however, is read from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, a value that is never included in the signed bytes [2](#0-1) .

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` and its `to_signable_string` method returns only `@raw_body` [3](#0-2) . `HmacValidator.validate` computes the HMAC exclusively over that signable string and compares it with `secure_compare` [4](#0-3) . Meanwhile `Request#shop` is derived purely from a header value with no cryptographic binding to the signed body [5](#0-4) , and `Registry.process` passes that unauthenticated `shop` value directly into the `WebhookMetadata` given to the app's handler after only checking the body HMAC [6](#0-5) .

The broken identity binding, stated as an equality that should hold but doesn't:
`shop_bound_by_HMAC == shop_acted_on_by_handler`
Here, `shop_bound_by_HMAC` is undefined (the signed content is body-only), while `shop_acted_on_by_handler` is the header value trusted by `Registry.process`.

Because the same app secret and (often) generic/empty JSON bodies (e.g. `customers/redact`, `shop/redact`, or any webhook body that is byte-for-byte identical across tenants of the same app) recur across every shop that installs the app, an attacker who legitimately installs the app on their own shop can capture a real, validly-signed webhook delivery (body + HMAC) and replay it to the app's webhook endpoint with the `shop-domain` header swapped to a victim shop the attacker does not control. The HMAC still validates because it never covered the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event is `shop: victim-shop.myshopify.com` even though the body was really generated for the attacker's own shop.

### Impact Explanation
This breaks the tenant-authentication boundary the HMAC is supposed to provide: an app relying on `ShopifyAPI::Webhooks::Registry` to authenticate "this event really happened on this shop" can be tricked into applying attacker-supplied/replayed webhook data to a different, victim tenant's record — a cross-tenant confusion/injection primitive purely through this gem's own verification logic, without requiring any of the app's credentials.

### Likelihood Explanation
Exploitability depends on the app's webhook handler treating `data.shop` (from `WebhookMetadata`) as authoritative for tenant selection while the body content is generic enough to be replayed across shops (compliance webhooks like `shop/redact`/`customers/redact`/`customers/data_request`, or app/uninstalled-style webhooks with sparse bodies, are good candidates). An attacker must be able to install the app on a shop they control to obtain one legitimately-signed delivery, then can freely alter the `shop-domain` header on replay, since only the raw body is HMAC-covered.

### Recommendation
Include the shop domain (and ideally the webhook id / timestamp) inside the HMAC-covered signable string for webhook requests, or otherwise cryptographically bind the header-derived `shop` to the verified body before it reaches `WebhookMetadata`, so `Registry.process` cannot dispatch handler calls with an unauthenticated shop identity.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com` and register/receive a webhook for a topic with a static/predictable body, e.g. `shop/redact` with body `{}`.
2. Capture the delivered HTTP request: headers include `x-shopify-hmac-sha256: <valid-hmac-for-"{}"->` and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Replay the exact same raw body `{}` and HMAC header to the app's webhook endpoint, but change `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body` (`"{}"`) [1](#0-0) .
5. The handler receives `WebhookMetadata.new(topic: "shop/redact", shop: "victim-shop.myshopify.com", body: {}, ...)` [7](#0-6)  and performs the redact/compliance action against the victim tenant, even though Shopify never actually sent that event for that shop.
