### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC verification performed by `HmacValidator.validate` in `Registry.process` never covers the `shop` (from the `x-shopify-shop-domain` / `shopify-shop-domain` header), `topic`, or `webhook_id` values. The identity binding that should hold — `HMAC-verified shop == shop used to process the webhook` — is broken, because `shop` is taken straight from an unauthenticated header while only the body bytes are authenticated.

### Finding Description
`Webhooks::Request` exposes `shop`, `topic`, `webhook_id`, and `api_version` purely from HTTP headers: [1](#0-0) 

`to_signable_string` — the data that actually gets HMAC-verified — is defined as just `@raw_body`: [2](#0-1) 

`Registry.process` validates only this HMAC-over-body, then immediately trusts `request.shop` (an unverified header) to build the metadata passed to the app's handler: [3](#0-2) 

Because Shopify signs webhooks with the app's single `client_secret` (the same secret used for every shop that has the app installed), any merchant who installs the app on their own store can legitimately receive a validly-HMAC'd webhook body for their own store. Since the header (`x-shopify-shop-domain`) is not part of the signed data, that attacker-controlled merchant can replay the exact same body+HMAC pair to the app's webhook endpoint while substituting a different value in the `shop-domain` header (e.g. a victim shop). `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` will hand the handler a `WebhookMetadata` claiming `shop: <victim-shop>` together with the attacker's own body content.

The equality that should hold is:
`hmac_verified_identity(shop) == shop_used_for_tenant_context`
but in this code it is actually:
`hmac_verified_identity(body_only) != shop_header (unverified)`, and the unverified header is what downstream handlers use to select tenant.

### Impact Explanation
This breaks the tenant-isolation guarantee host applications rely on when they trust `WebhookMetadata#shop` to determine which merchant's records a webhook payload should be applied to. An attacker who is a legitimate (even low-privilege) merchant of the app can forge webhooks that are processed as if they originated from a shop they do not control, enabling cross-tenant data confusion/injection in any handler that keys off `data.shop` without independent verification. This matches the "cross-tenant access" Critical-impact category defined in the rules, since the gem's own webhook-processing primitive (`Registry.process`) is what performs the (incomplete) verification and forwards the unverified shop identity to handlers.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the app on a shop they control (a normal, low-privilege action — no leaked secrets, no privileged account, no TLS interception) and send a raw HTTP POST to the app's webhook endpoint with a modified `shop-domain` header, reusing the legitimately-received body/HMAC pair. No knowledge of `api_secret_key` is needed since the attacker obtains a real, valid HMAC from Shopify for their own install.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values as part of the signed/verified material used to authenticate a webhook — Shopify's HMAC is computed over the raw body, so instead the gem should require the caller to independently verify that the shop domain on the request corresponds to the shop targeted, or minimally document/enforce that host applications must record and validate the requesting shop out-of-band (e.g., against the app's own uninstall/install session store) rather than trusting `Webhooks::Request#shop` as an authenticated value. Consider renaming/documenting `WebhookMetadata#shop` to make clear it is unauthenticated header data, and provide an API to cross-check it against a known active session's shop before dispatching to handlers.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker.myshopify.com`, receiving genuine webhook deliveries signed with the app's shared `client_secret`.
2. Attacker captures one such webhook's raw body and its valid `x-shopify-hmac-sha256` header value.
3. Attacker POSTs this same body + HMAC to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate(request)`, which only hashes `@raw_body` [2](#0-1)  — validation succeeds because the body/HMAC pair is genuinely valid.
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)` [4](#0-3) , so any host logic keyed on `data.shop` processes attacker-controlled content as if it came from the victim shop.
