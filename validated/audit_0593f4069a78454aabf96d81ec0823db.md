### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity fields are not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body, then blindly trusts the `shop`, `topic`, `api_version`, and `webhook_id` values taken from unauthenticated HTTP headers when constructing the `WebhookMetadata` handed to the app's handler. Any entity that can obtain one validly-signed webhook body (e.g. by installing the app on their own store, since the API secret used to sign webhooks is the app's single shared `client_secret`, identical for every merchant) can replay that same body+HMAC to the app's webhook endpoint while substituting a different `shop-domain` header, causing the app to process attacker-controlled data under a victim shop's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` define the HMAC-verifiable content as only the raw body: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all parsed straight from HTTP headers and are never included in `to_signable_string`: [2](#0-1) 

`Utils::HmacValidator.validate` computes `HMAC(api_secret_key, verifiable_query.to_signable_string)` and compares it to the received `hmac`: [3](#0-2) 

`Registry.process` only checks this body HMAC, then immediately trusts `request.shop`, `request.topic`, etc. to build the metadata dispatched to the host app's handler: [4](#0-3) 

The broken identity binding, stated as an equality that the code fails to enforce:
`HMAC_valid(body) == true` is treated as if it implies `shop_header == shop_that_produced(body)`, but no such binding exists — the HMAC only proves `body` was generated using the app's `api_secret_key` at some point, by *some* shop with the app installed; it says nothing about which `shop-domain` header accompanies that body in the current request.

Because the API secret (`client_secret`) is a single shared value across every merchant install of a public app, an unprivileged attacker can:
1. Install the target app on their own (attacker-controlled) shop — a normal, unprivileged action any Shopify merchant can take.
2. Trigger any webhook topic on their own shop to obtain a body and its correctly-computed `x-shopify-hmac-sha256` value (both signed with the same shared secret the app uses for all shops).
3. Replay that exact `{raw_body, hmac}` pair to the app's webhook endpoint, but with `x-shopify-shop-domain` (and optionally `x-shopify-topic`) headers rewritten to a victim shop's domain.
4. `Utils::HmacValidator.validate` succeeds (body+hmac pair is valid), and `Registry.process` dispatches `WebhookMetadata.new(shop: <victim shop>, topic: ..., body: <attacker-chosen content>)` to the host app's handler, which will treat the event as authentic data belonging to the victim tenant.

### Impact Explanation
This breaks the tenant-isolation guarantee that the gem's webhook signature verification is supposed to provide. A host application that (reasonably, given the API surface) trusts `WebhookMetadata#shop` once `Registry.process` has not raised `InvalidWebhookError` can be made to apply attacker-chosen webhook payloads (e.g. `orders/create`, `app/uninstalled`, `customers/data_request`, etc.) against a different merchant's tenant record, since nothing in the gem binds the body's authenticity to the specific shop header sent alongside it. This is a cross-tenant data/authenticity confusion rooted directly in this gem's HMAC verification design (`VerifiableQuery`/`HmacValidator`/`Webhooks::Request`), not merely a misuse of a documented safe API.

### Likelihood Explanation
Likelihood is high for any public/multi-tenant app: no privileged credentials, tokens, or `api_secret_key` are needed — only the ability to install the app on a self-controlled shop, which is available to any unprivileged internet user for a listed public app, plus the ability to send an arbitrary HTTP request with custom headers to the app's public webhook endpoint.

### Recommendation
Include the identity fields (`shop-domain`, `topic`, `api-version`, `webhook-id`) in the HMAC-signable content, or otherwise cryptographically bind them to the body (e.g. authenticate the full header set, not just the body) before trusting `WebhookMetadata#shop` in `Registry.process`. At minimum, document clearly that `shop`/`topic` are unauthenticated and require the host application to independently verify shop identity (e.g. via a stored per-shop webhook secret) rather than relying on `HmacValidator.validate` for tenant binding.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, obtaining a valid OAuth session (no special privilege — any merchant can do this for a public app).
2. Attacker triggers a webhook (e.g. update a product) causing Shopify to POST a body `B` with header `x-shopify-hmac-sha256: H`, where `H = HMAC_SHA256(api_secret_key, B)`. Attacker captures `(B, H)`.
3. Attacker crafts an HTTP POST to the app's webhook endpoint:
   ```
   POST /webhooks
   x-shopify-topic: products/update
   x-shopify-hmac-sha256: H
   x-shopify-shop-domain: victim-shop.myshopify.com
   x-shopify-api-version: 2024-01

   B
   ```
4. On the server, `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed and passed to `Registry.process`: [4](#0-3) 
5. `Utils::HmacValidator.validate` succeeds because `H` is indeed `HMAC_SHA256(api_secret_key, B)` — the same secret is used regardless of which shop is named in the header.
6. The handler executes with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: "products/update", body: <attacker's data>)`, letting the attacker inject/attribute arbitrary webhook payloads to a shop they do not control.
