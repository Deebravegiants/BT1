### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the tenant identity (`shop`) that is handed to the app's handler is read from an HTTP header that is never part of the signed payload. This breaks the equality "the shop verified by the HMAC" == "the shop used to build `WebhookMetadata`", allowing a value from an unauthenticated header to determine which tenant a webhook is attributed to.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field using the app's shared `api_secret_key`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw body — the shop domain is excluded from what is signed: [2](#0-1) 

`Request#shop` is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cross-check against the signed body: [3](#0-2) 

`Registry.process` validates only the HMAC/body pair, then forwards `request.shop` — the unauthenticated header — straight into `WebhookMetadata`, which is the tenant-identifying value the app's handler will act on: [4](#0-3) [5](#0-4) 

Because the `api_secret_key` used to compute the HMAC is shared across all shops/tenants of the app (it is not shop-specific), any merchant/tenant with the app installed can obtain a legitimately-signed `(raw_body, hmac)` pair for their own shop (e.g. by triggering any webhook event on their own store) and then replay that exact body+HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a different, victim shop domain. `HmacValidator.validate` still succeeds because it only checks the body/HMAC, which was genuinely signed by Shopify — just for a different shop than the one now claimed in the header. `Registry.process` will then call the handler with `WebhookMetadata(shop: <victim shop>, body: <attacker's own body>)`, i.e., the equality "shop bound by the HMAC" == "shop the handler trusts and acts on" is broken.

This directly matches the report's bug class: a field ("shop") acted on by the handler is not covered by the cryptographic binding (the HMAC), enabling context/identity confusion between a value that is verified and a value that is merely parsed/trusted.

### Impact Explanation
Handlers built on top of `WebhookHandler#handle` typically use `data.shop` to key data deletion, redaction, session lookup, or other tenant-scoped side effects (this is exactly the intended use per the mandatory `shop/redact`, `customers/redact`, `customers/data_request` topics registered in `Registry`). An attacker controlling one tenant can forge webhook deliveries that are attributed to an arbitrary victim shop, resulting in cross-tenant data operations (e.g., triggering redaction/deletion logic, or any app-specific webhook side effect) executed against a shop the attacker does not control. This satisfies the "Critical - cross-tenant access" impact bar defined in scope.

### Likelihood Explanation
Exploitation only requires the attacker to be a legitimate installer of the app on their own shop (an unprivileged-relative-to-other-tenants position) — no access to `api_secret_key`, access tokens, or other privileged credentials is needed. The attacker simply captures one real webhook delivery (body + HMAC header) sent to their own endpoint and replays it with a modified `shop-domain` header. This requires no cryptographic break, only a straightforward HTTP replay with header substitution, making likelihood high wherever the host app trusts `WebhookMetadata#shop` for tenant-scoped decisions.

### Recommendation
Bind the shop domain into the authenticated payload used for validation rather than trusting a bare header:
- Require callers/hosts to cross-check `request.shop` against a shop already associated with the webhook subscription/session before acting, or
- Extend `to_signable_string`/`VerifiableQuery` for webhooks so the shop domain (and topic) are included in the HMAC-covered material, matching what Shopify actually signs, and reject mismatches; at minimum, document prominently that `WebhookMetadata#shop` is not itself authenticated by the gem and must be independently validated against a known/expected shop before being used for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers any webhook (e.g. update a product) so Shopify sends a legitimately-signed request:
   - Headers: `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-hmac-sha256: <valid HMAC over raw_body>`
   - Body: `raw_body`
2. Attacker replays this exact `raw_body` and `shopify-hmac-sha256` value to the app's webhook endpoint, but changes the header to `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only [6](#0-5)  — this still matches since the body/HMAC pair is genuine.
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker-controlled body>, ...)` [7](#0-6) , causing any shop-scoped logic in the handler to run against the victim shop's identity using attacker-supplied data.
