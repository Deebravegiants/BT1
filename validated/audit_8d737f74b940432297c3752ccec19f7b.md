### Title
`describeWithdrawal`/`findMatchingWithdrawal` misreports status by matching same-asset withdrawals only on `assetId`, ignoring `index` - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` matches the PoA bridge's withdrawal-status API response solely by `assetId` via `findMatchingWithdrawal`, never by `index`, `amount`, or `destinationAddress`. When a single signed intent contains multiple withdrawals of the same `assetId`, `watchWithdrawal` polling each `index` independently will collide on the first matching record, so a still-pending or failed withdrawal can be reported as `completed` with a `txHash` that actually belongs to a different withdrawal in the batch.

### Finding Description
The broken equality: `reported_status(index=2)` should equal `actual_on_chain_outcome(index=2)`, but instead `findMatchingWithdrawal` returns whichever array element first satisfies `` `nep141:${w.data.near_token_id}` === assetId ``, with no correlation to `index`, `amount`, `address`, or whether that record was already consumed by a previous `describeWithdrawal` call for a different index [1](#0-0) [2](#0-1) .

`watchWithdrawal` calls `bridge.describeWithdrawal` independently per `WithdrawalIdentifier` (one per index in the batch), and as soon as a call returns `status: "completed"`, it resolves that withdrawal's promise with the returned `txHash`, with no de-duplication against `txHash`es already claimed by sibling withdrawals in the same batch [3](#0-2) , and `createWithdrawalCompletionPromises` fans this out per index across the whole `withdrawalParams` batch [4](#0-3) .

The root cause is explicitly documented as a known limitation in the code itself: `findMatchingWithdrawal`'s comment states "Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported" [2](#0-1) . The identical limitation and matching function also exist in the sibling `waitForWithdrawalCompletion` utility [5](#0-4) .

Attacker input: an ordinary NEAR Intents user (or an integrator forwarding user-controlled `withdrawalParams`) signs one intent with 3 PoA withdrawals of the same `assetId` to 3 different `destinationAddress`es with amounts 100/200/300. No malicious relayer behavior is required — the PoA relayer's normal asynchronous processing (two withdrawals settle, one legitimately fails/delays) is sufficient to produce an API response containing fewer records than requested withdrawals, all sharing the same `assetId`.

Exploit flow: `watchWithdrawal` for index 0 and index 1 each poll and correctly (by luck of ordering) match one COMPLETED record each and resolve. When index 2 polls, `getWithdrawalStatus` still returns the same 2 COMPLETED records (the third withdrawal never appears since it failed/never executed), and `findMatchingWithdrawal(withdrawals, assetId)` returns `withdrawals[0]` again (whichever record `Array.prototype.find` hits first) - the same COMPLETED record already attributed to index 0. `describeWithdrawal` then returns `{ status: "completed", txHash: withdrawal.data.transfer_tx_hash }`, i.e., the txHash belonging to the 100-unit withdrawal to address A, reported for the 300-unit withdrawal to address C. `watchWithdrawal` resolves index 2 as completed with that borrowed hash.

Existing guards do not prevent this: `supports()`, `validateAddress`, `compareAddresses`, and `FeeExceedsAmountError` all operate at withdrawal-construction time and have no visibility into cross-withdrawal collisions during status polling; there is no `index`-aware or `txHash`-uniqueness check anywhere in `describeWithdrawal` or `watchWithdrawal`.

### Impact Explanation
An integrator relying on `watchWithdrawal`/`createWithdrawalCompletionPromises` results to decide whether to credit, refund, or mark a withdrawal delivered will misreport withdrawal index 2 (300 units, address C) as completed using a `txHash` that actually paid address A. This is a status/hash misreport that can cause the integrator to treat a failed/undelivered withdrawal as delivered, matching the "status or hash misreport making an integrator credit or refund twice" category. It is repeatable on every batch containing 2+ withdrawals of the same `assetId` combined with any withdrawal-level ordering skew (completion order differing from `index` order, or one withdrawal failing while earlier COMPLETED records remain in the response).

### Likelihood Explanation
Preconditions require only a single signed intent with 2+ withdrawals of the identical `assetId` — a normal usage pattern (e.g., paying multiple recipients in the same token), not an adversarial construction. The relayer's inherently asynchronous, per-withdrawal completion timing (explicitly acknowledged in code comments) is sufficient to trigger divergence between `index` order and API response order/content; no special relayer misbehavior, malicious RPC, or privileged access is needed. Attacker cost is zero beyond normal transaction fees.

### Recommendation
Extend `findMatchingWithdrawal` (both in `poa-bridge.ts` and `waitForWithdrawalCompletion.ts`) to disambiguate among multiple same-`assetId` records using additional discriminating fields (e.g., `amount` and `address`, matched against the specific `WithdrawalIdentifier`'s `withdrawalParams`), and to track/exclude records already attributed to another `index` within the same batch (e.g., via a per-poll consumed-set keyed by `tx_hash`/`transfer_tx_hash`). Until POA's API supports withdrawal-level correlation IDs, `describeWithdrawal` should refuse to report `completed` for an index when multiple same-asset withdrawals are outstanding and the match is ambiguous, surfacing `pending`/error instead of a possibly-wrong `completed`.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
