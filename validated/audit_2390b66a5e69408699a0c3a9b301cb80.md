### Title
Webhook Shop Identity Spoofing via HMAC Not Covering `shop-domain` Header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` (and `topic`/`webhook_id`/`api_version`) from raw HTTP headers, but the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` validates covers only the raw request body. An attacker who has ever received one genuine, validly-signed webhook for their own shop (e.g., by installing the app on a shop they control) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header for a victim shop's domain. The signature check still passes because the shop header was never part of the signed material, causing the host application to process attacker-controlled data under the identity of a different tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated headers with no cross-check against the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC-over-body via `Utils::HmacValidator.validate(request)`, and then hands `request.shop` (and `request.topic`, `request.webhook_id`) straight to the app's handler as trusted metadata: [3](#0-2) 

`Utils::HmacValidator.validate_signature` only recomputes the HMAC over `to_signable_string` (the body) and compares it to the header-derived HMAC value — it never incorporates `shop`, `topic`, or `webhook_id`: [4](#0-3) 

This breaks the intended identity binding: `hmac_valid == true` should imply `shop_header == shop_that_actually_generated_this_signed_body`, but because `shop` is not covered by the HMAC, an attacker can hold that equality false while `hmac_valid` remains `true`. Concretely: an attacker installs the app on their own shop `attacker.myshopify.com`, receives a real webhook delivery (valid body + valid `hmac-sha256` computed with the app's `client_secret`), and then POSTs that exact `raw_body`/`hmac` pair directly to the app's webhook controller endpoint with the header changed to `x-shopify-shop-domain: victim.myshopify.com`. `Webhooks::Registry.process` will validate the HMAC successfully (body unchanged) and invoke the app handler with `WebhookMetadata#shop == "victim.myshopify.com"`, causing the host application to attribute attacker-supplied data to the victim tenant.

### Impact Explanation
This is a cross-tenant identity confusion: the gem's own webhook-processing API asserts an authenticated shop identity (`request.shop`) to downstream application code based solely on validating the body signature, while the shop identity itself is unauthenticated attacker-controlled input. Any host application that relies on `WebhookMetadata#shop` (as instructed by this library's own documented usage pattern) to select which tenant's records to create/update/delete will act on forged data under another merchant's identity — satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Exploitation only requires the attacker to be a legitimate/trial merchant able to install the app on a shop they control (to obtain one genuine signed webhook body/HMAC pair) and the ability to send an arbitrary HTTP POST directly to the app's public webhook endpoint with custom headers — no access to `client_secret`, access tokens, or privileged accounts is needed. This is fully reachable through the gem's documented `Webhooks::Registry.process` / `Webhooks::Request` API as shown in `docs/usage/webhooks.md`.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the value that is HMAC-verified (or otherwise cryptographically bind them to the body), or at minimum require host applications to only trust `request.shop` after independently confirming it corresponds to a shop domain for which the app currently holds a valid session, before processing the payload as belonging to that shop.

### Proof of Concept
```ruby
# 1. Attacker installs the app on their own shop and captures a genuine
#    webhook delivery: raw_body = '{"id":1}', valid hmac header for that body
#    signed with the real Context.api_secret_key by Shopify.

raw_body = '{"id":1}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# 2. Attacker replays it to the app's webhook endpoint with a forged shop header.
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not the attacker's real shop
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# 3. HMAC validation succeeds because it only checks raw_body, not the shop header.
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# 4. Registry.process dispatches to the handler claiming this is victim-shop's data.
ShopifyAPI::Webhooks::Registry.process(request)
# handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", body: {"id"=>1}, ...)
```
