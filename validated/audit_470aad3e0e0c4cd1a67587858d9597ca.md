### Title
Webhook `shop` (tenant) attribution is not covered by the HMAC signature, allowing cross-tenant spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the HMAC only over the raw request body, while the `shop` (tenant identity) is read from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header and is never included in the signed payload. This breaks the binding: `shop-as-authenticated (HMAC) == shop-as-acted-upon (routing/tenant attribution)`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is parsed independently from an HTTP header that is not part of that signable string: [2](#0-1) 

`Registry.process` validates the HMAC via the shared `HmacValidator`, which only checks `to_signable_string` (the raw body) against the HMAC secret, then immediately forwards `request.shop` — the unauthenticated header value — into `WebhookMetadata`, which is delivered to the app's handler for tenant-specific processing: [3](#0-2) 

`HmacValidator.validate` confirms this: it computes the signature strictly from `verifiable_query.to_signable_string`, i.e. the body only, never the shop header: [4](#0-3) 

This is exactly the identity-binding gap the report describes: a field acted upon (`shop`, used to route/attribute the webhook to a specific tenant) is not covered by the same authentication mechanism (HMAC) that protects the rest of the message. Because the HMAC covers only bytes, any request bearing a body+HMAC pair valid for shop A can be replayed with the `shopify-shop-domain` header rewritten to shop B, and `Registry.process` will still accept it and hand `shop: "B"` to the handler.

### Impact Explanation
A multi-tenant app built on this gem's webhook processing dispatches business logic (data updates/deletes, session/access-token lookups, per-merchant side effects) keyed off `WebhookMetadata#shop`. Since that value is attacker-controllable independent of the cryptographic check, an attacker who obtains any valid (body, HMAC) pair — e.g., from their own shop's legitimate webhook traffic to a shared endpoint — can relabel it as belonging to a different shop, causing the app to process shop-A-signed content under shop B's tenant context. This is a cross-tenant integrity/attribution break reachable by an unprivileged party who controls only HTTP headers on their own webhook deliveries.

### Likelihood Explanation
Moderate-to-high: the attacker needs their own valid webhook body/HMAC pair (which any app-installing merchant naturally has, since Shopify sends them webhooks for their own store), and then only needs to modify the `shop-domain` header when POSTing to the app's shared webhook endpoint. No secrets, tokens, or privileged access are required beyond controlling their own webhook payloads.

### Recommendation
Bind the tenant identity into the authenticated material: either include the `shop-domain` header value inside `to_signable_string` before hashing (not possible without changing Shopify's own signing scheme) or, more practically, require the host app/gem to verify that `request.shop` corresponds to a shop with a known, previously-established session/installation before trusting it, and document this requirement explicitly rather than implying HMAC validation alone authenticates the shop attribution.

### Proof of Concept
1. Legitimate merchant `shop-a.myshopify.com` triggers a webhook; the app's shared endpoint receives body `B` and header `X-Shopify-Hmac-Sha256: H` where `H = HMAC(secret, B)`, plus `X-Shopify-Shop-Domain: shop-a.myshopify.com`.
2. Attacker (who owns `shop-a.myshopify.com`, an unprivileged merchant relative to `shop-b`) captures this request and resends it to the app's endpoint with the same body `B` and HMAC `H`, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` [5](#0-4) , which recomputes the HMAC purely from `@raw_body` and succeeds because the body/HMAC pair is still valid.
4. `handler.handle` is invoked with `shop: request.shop` equal to `"shop-b.myshopify.com"` [6](#0-5) , causing the app to process shop-A's webhook content as if it belonged to shop B.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
