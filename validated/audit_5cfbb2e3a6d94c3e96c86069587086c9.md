## Finding: User Enumeration via Distinct Error Messages on `/sessions` Login Endpoint

### Title
Unauthenticated `/sessions` login endpoint leaks account existence via distinct error messages - (File: core/web/sessions_controller.go)

### Summary
The chainlink node's `/sessions` API endpoint (unauthenticated, rate-limited only) returns raw, distinguishable error messages depending on whether the submitted email corresponds to an existing user or not. This is directly analogous to the Shopware Store API login enumeration bug (CVE-2026-31888): a "not found" case and a "bad password" case surface as different observable strings in the JSON response body.

### Finding Description
`SessionsController.Create` forwards any error from `AuthenticationProvider().CreateSession()` straight into the client response without normalization: [1](#0-0) 

`jsonAPIError` serializes `err.Error()` verbatim into the JSON body: [2](#0-1) 

In the local-auth provider (default `AuthenticationProviderName = "local"`), `CreateSession` first looks up the user by email. If the email is unknown, the raw `sql.ErrNoRows` (`"sql: no rows in result set"`) bubbles up unmodified. If the email is known but the password is wrong, a distinct message `"Invalid password"` is returned instead: [3](#0-2) [4](#0-3) 

The same pattern repeats in the LDAP and OIDC local-admin fallback paths, both of which distinguish `"invalid email"` from `"invalid password"`: [5](#0-4) [6](#0-5) 

The route is reachable by any unauthenticated client, protected only by an IP+email-keyed rate limiter (bypassable by IP rotation, and irrelevant to enumeration since only one probe per email is needed): [7](#0-6) 

### Impact Explanation
An unauthenticated attacker can submit `POST /sessions` with a candidate email and an arbitrary password, then distinguish "account exists" (`"Invalid password"` response) from "account does not exist" (raw SQL error text) purely from the response body — enabling enumeration of registered node-admin/API user accounts. This also leaks internal implementation detail (a raw `database/sql` error string) rather than a generic application error, which is worse than the Shopware case since it directly echoes low-level backend error text instead of a controlled error code.

### Likelihood Explanation
High likelihood of exploitability: the endpoint is unauthenticated by design (`unauth.POST("/sessions", sc.Create)`), requires no special network position, and the existing test suite only asserts status codes (`>= 400`), not message content, so this discrepancy was never caught: [8](#0-7) 

### Recommendation
Normalize all authentication failure paths in `CreateSession` (local, LDAP fallback, OIDC fallback) to return a single generic error (e.g., `"invalid email or password"`) regardless of whether the email lookup failed or the password check failed, mirroring the fix pattern recommended in the Shopware advisory (unify at the login boundary). Additionally, `jsonAPIError` should not propagate raw internal errors (like `sql.ErrNoRows`) to the client at all — wrap/replace them before returning from `CreateSession`.

### Proof of Concept
```
POST /sessions HTTP/1.1
Content-Type: application/json

{"email":"nonexistent@test.com","password":"anything"}
```
Response body contains SQL-driver-level text (e.g. `"sql: no rows in result set"`).

```
POST /sessions HTTP/1.1
Content-Type: application/json

{"email":"knownuser@test.com","password":"wrongpassword"}
```
Response body contains `"Invalid password"`.

The two distinct strings let an attacker script enumerate valid emails at one request per candidate.

// jsonAPIError adds an error to the gin context and sets
// the JSON value of errors.
func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}

func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}

func (l *ldapAuthenticator) localLoginFallback(ctx context.Context, sr sessions.SessionRequest) (sessions.User, error) {
	var user sessions.User
	sql := "SELECT * FROM users WHERE lower(email) = lower($1)"
	err := l.ds.GetContext(ctx, &user, sql, sr.Email)
	if err != nil {
		return user, err
	}
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		l.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return user, errors.New("invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		l.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return user, errors.New("invalid password")
	}

	return user, nil
}
