## Title
`_routerDepositAndDispose` silently skips LP seeding when one side's remainder is zero, permanently bricking `finalizeGraduation` — ([File: packages/contracts/src/Bonding.sol])

### Summary
The reported bug is a payout function whose `if (amount > 0)` guard silently no-ops instead of reverting or notifying the caller when the condition fails. The exact same pattern exists in `Bonding._routerDepositAndDispose`, where `if (remToken > 0 && remLT > 0)` gates the sole `addLiquidity` call in the LP-seeding path. If either side's remainder is zero, the function falls through with `liquidity` left at its default value of `0`, no revert, and no event — just like `payUser`.

### Finding Description
`_routerDepositAndDispose` computes leftover Token/LT inventory and only calls `addLiquidity` when both sides are non-zero: [1](#0-0) 

If `remToken == 0` or `remLT == 0`, the `if` body is skipped entirely and `liquidity` stays `0` — no error, no event, nothing to signal that the deposit did not occur, mirroring the `payUser` `if (amount > 0)` silent-skip pattern from the report.

The contract's own inline documentation acknowledges this exact failure mode and names its consequence directly: [2](#0-1) 

This `liquidity = 0` return value flows straight into `finalizeGraduation`, which unconditionally calls `LPLock.recordLock(tokenAddress, lpPair, liquidity)`: [3](#0-2) 

`LPLock.recordLock` explicitly reverts on a zero amount: [4](#0-3) 

Because `Bonding.finalizeGraduation` has no state rollback / retry-with-different-inputs mechanism — `p.tokensForLP` and `p.ltFromPair` are pinned in `PendingGraduation` at the last curve price during `_enterGraduating` and never recomputed — every subsequent call to `finalizeGraduation` for that token deterministically reproduces `remToken == 0` (or `remLT == 0`) and reverts again with `LPLock.ZeroAmount`. The token becomes permanently stuck in `Lifecycle.Graduating`: it can never reach `Lifecycle.Graduated`, trading through `Zap` remains blocked (`isGraduating` reverts buys/sells), and the curve-raised LT plus the reserved 250M tokens held by `Bonding` for LP seeding have no rescue path — `Bonding` has no admin withdrawal for graduation-earmarked funds and `LPLock` explicitly has "No withdraw in v1."

The 99%-budget cap (`_swapBudget`) documented at line 1374-1378 was added specifically to keep the rebalance-swap branches from consuming 100% of a side's inventory and hitting this exact zero-remainder condition, confirming the developers were aware the condition is reachable and dangerous. However, the cap only protects the two `_pairRebalance` branches; the fall-through "pool already at curve-close ratio" branch (comment at lines 1350-1351) reaches `_routerDepositAndDispose` directly with no such protection, and `tokensForLP` itself can be driven arbitrarily small by the curve's `sold·(S−sold)/S` parabola near either end of the curve's sale range, making a zero (or near-zero, rounding-to-zero) `remToken`/`remLT` a live possibility outside the swap-cap's coverage.

### Impact Explanation
If this zero-remainder condition is hit, the affected token's curve-raised LT reserve and its allotted 250M LP tokens are permanently frozen in `Bonding` with no recovery function — a direct permanent freezing of creator/trader-contributed funds, matching the report's "High" bug class (silent failure of a critical payout/settlement path) but escalated here to a hard, un-recoverable graduation brick rather than a mere missing event.

### Likelihood Explanation
`finalizeGraduation` is fully permissionless and callable by any unrelated wallet once `TokenGraduating` fires, so any attacker can attempt to steer the pre-seed shape (via `pair.mint`/`transfer` before graduation, an in-scope reachable action) toward a reserve ratio and inventory split that drives `remToken` or `remLT` to zero after the capped rebalance, or exploit tokens whose `tokensForLP` naturally lands at a very small value near the parabola's edges. The deterministic nature of `PendingGraduation`'s frozen inputs means one bad configuration is permanent — there is no off-chain retry that changes the outcome.

### Recommendation
Do not let `_routerDepositAndDispose` (and therefore `finalizeGraduation`) fall through silently or revert unrecoverably when `remToken == 0 || remLT == 0`. Add an explicit, named failure mode (event and/or a recorded "stuck" state with an admin/owner rescue path for the escrowed Token/LT) instead of relying on `LPLock.recordLock`'s generic `ZeroAmount` revert to catch it downstream, and extend the `_swapBudget` protection to cover the curve-close-ratio fall-through branch so a legitimate small `tokensForLP` cannot reach a zero deposit amount undetected.

### Proof of Concept
1. Attacker calls `Zap.createToken(...)` is not needed — target any live curve token approaching graduation.
2. Before the threshold-crossing buy/`Bonding.triggerGraduation`, attacker pre-seeds the not-yet-existent HyperSwap V2 TOKEN/LT pair via direct `transfer` + `pair.mint(attacker)` with a ratio/amount engineered so that, after `_prepareGraduationLiquidity` pins `(tokensForLP, ltFromPair)` and the graduation enters the "pool already at curve-close ratio" branch (`packages/contracts/src/Bonding.sol:1350-1353`) or a rebalance branch whose swap consumes the full side despite the 99% cap (e.g. `tokensForLP` or `ltFromPair` at a parabola-edge dust value), `remToken` or `remLT` resolves to `0` in `_routerDepositAndDispose`.
3. Anyone calls `Bonding.finalizeGraduation(tokenAddress)`. `_routerDepositAndDispose` skips `addLiquidity`, returns `liquidity = 0`.
4. `finalizeGraduation` calls `LPLock.recordLock(tokenAddress, lpPair, 0)`, which reverts with `ZeroAmount`.
5. Because `PendingGraduation` state is frozen and never recomputed, every future call to `finalizeGraduation(tokenAddress)` reverts identically — the token is permanently stuck in `Lifecycle.Graduating`, and the LT/Token inventory earmarked for LP is permanently frozen in `Bonding` with no rescue function.

    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }
