## Title
Webhook shop-domain and topic headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, while the shop-identifying header (`shopify-shop-domain`/`x-shopify-shop-domain`) and other headers (`topic`, `webhook-id`, `api-version`) are read directly from unauthenticated HTTP headers and never included in the signed payload. `ShopifyAPI::Utils::HmacValidator.validate` only checks the raw body against the HMAC, so an attacker who possesses one valid `(raw_body, hmac)` pair signed with the app's `api_secret_key` can freely rewrite the `shop-domain` header to any victim shop and the signature will still validate.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all derived from HTTP headers that are not part of that signable string: [2](#0-1) 

`HmacValidator.validate` computes the HMAC purely over `to_signable_string` (i.e., the raw body) and compares it to the `hmac` header value: [3](#0-2) 

`Registry.process` gates entirely on this body-only HMAC check, then trusts `request.shop` (an unauthenticated header) to build the tenant context passed to the app's handler: [4](#0-3) 

This breaks the intended binding: `HMAC(secret, signed_bytes) == received_hmac` should imply `signed_bytes == (shop, topic, body)`, but here `signed_bytes == body` only. The `shop` field is *acted on* (used to route webhook data to the handler as the shop of origin) without being *covered by* the HMAC — structurally identical to the report's bug class ("a field acted on but not covered by the HMAC").

### Impact Explanation
In a multi-tenant Shopify app, the same `api_secret_key` signs webhooks for every installed shop. An unprivileged internet user can install the app on their own (attacker-controlled) shop, legitimately receive a webhook (e.g., `orders/create`) with a valid HMAC over some body they control, then replay that exact body+HMAC to the app's public webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate` still passes (it never looked at the header), and `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: request.shop, ...)` pointing at the victim shop. Any handler logic that trusts `shop` to select tenant data, look up sessions, or authorize actions is now operating under attacker-forged tenant identity — a cross-tenant access/impersonation, matching the Critical impact bucket ("cross-tenant access").

### Likelihood Explanation
Requires only: (1) ability to install the app as any store (self-signup, common for most public Shopify apps) to obtain one valid signed webhook body, and (2) sending a crafted HTTP request to the app's public webhook endpoint with a modified shop header. No access token, `api_secret_key`, or privileged account is needed — purely unauthenticated header manipulation exploiting the gem's own verification logic.

### Recommendation
Include the shop domain (and topic/webhook-id, as applicable) in the value that is HMAC-verified, or otherwise cryptographically bind the header-derived `shop`/`topic` to the signed body before they are used to construct `WebhookMetadata`. At minimum, `Request#to_signable_string` should incorporate the `shop-domain` and `topic` headers, and `HmacValidator`/`VerifiableQuery` should be updated so callers cannot use unmodeled header fields for authorization decisions.

### Proof of Concept
1. Install the target app on attacker's own shop `attacker.myshopify.com`; receive a legitimate webhook POST with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac>`, body `RAW_BODY`.
2. Resend the same request to the app's webhook endpoint, keeping `RAW_BODY` and `x-shopify-hmac-sha256` unchanged, but replacing the header to `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: RAW_BODY, headers: forged_headers)` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only depends on `RAW_BODY`: [5](#0-4) 
4. `handler.handle(data: WebhookMetadata.new(topic:, shop: request.shop, ...))` is invoked with `shop == "victim.myshopify.com"`, even though the payload actually originated from and was signed for `attacker.myshopify.com`, letting the attacker inject/spoof data under a victim tenant's identity.
