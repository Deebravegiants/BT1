### Title
CatFee API secret logged in plaintext via `{:#?}` debug formatting - (File: `tesseract/messaging/tron/src/lib.rs`)

### Summary
`TronClient::new` logs the full `CatFeeConfig` struct — including the plaintext `api_secret` used for HMAC-SHA256 request signing — to the relayer's logs at `info` level whenever CatFee integration is configured.

### Finding Description
`CatFeeConfig` derives `Debug` with no redaction on any field: [1](#0-0) 

When a TRON messaging relayer is configured with CatFee credentials (`catfee_api_key`/`catfee_api_secret` in `TronConfig`), `TronClient::new` builds a `CatFeeConfig` and immediately logs it with the alternate/pretty `Debug` formatter, which serializes every field including `api_secret`: [2](#0-1) 

This is directly analogous to CVE-2024-45784: a secret value that should never leave the process (used only to compute `HMAC-SHA256(secret, timestamp+method+path)` per the module's own doc comment) is instead deliberately written into the log stream by default, with no masking mechanism anywhere in the crate. [3](#0-2)  The `CatFeeConfig` fields (`api_key`, `api_secret`) are populated straight from the operator-supplied `TronConfig.catfee_api_key`/`catfee_api_secret`: [4](#0-3) 

### Impact Explanation
Any relayer operator running a TRON messaging client with CatFee enabled will have their CatFee API secret written to `info`-level logs at every process start. Logs are commonly shipped to centralized aggregators, CI artifacts, or left world-readable on disk; an attacker obtaining this secret can forge signed CatFee API requests, spend the operator's CatFee balance to purchase TRON energy/bandwidth on arbitrary receiver addresses, or exhaust/drain the operator's CatFee account — a direct fee/fund-loss impact to the relayer operator's energy-purchasing budget, which the relayer depends on to keep submitting TRON transactions economically viable. This is a Medium-severity secrets-exposure issue reachable purely from the relayer's own startup configuration path (no attacker input required to trigger the log write, but the resulting secret leak enables theft of CatFee funds/energy by anyone with log access).

### Likelihood Explanation
This fires unconditionally and automatically on every relayer restart whenever an operator has configured CatFee credentials — there is no opt-out short of not enabling the feature. It requires no attacker interaction to trigger; the only precondition is that an attacker (or careless log pipeline) gains read access to the relayer's `info`-level logs, which is a common operational exposure vector (log aggregation services, misconfigured log retention, support-ticket log pastes, etc.).

### Recommendation
Do not derive/print `Debug` on `CatFeeConfig` (or any struct holding `api_secret`) directly into logs. Implement a custom `Debug`/`Display` that redacts `api_secret` (and `api_key`, defensively), e.g. printing `api_secret: "***"`, and change the log line in `TronClient::new` to use the redacted representation instead of `{:#?}` on the raw config. Apply the same audit to any other credential-bearing structs logged elsewhere in the `tesseract` relayer crates.

### Proof of Concept
1. Configure a TRON messaging relayer with `catfee_api_key` and `catfee_api_secret` set in `TronConfig`.
2. Start the relayer (`TronClient::new` is invoked during boot).
3. Observe the process logs: the line `"CatFee integration enabled: {:#?}"` emits the full `CatFeeConfig`, including `api_secret` in cleartext, at `info` level.
4. Anyone with read access to these logs can extract `api_secret` and use it to compute valid `CF-ACCESS-SIGN` HMAC signatures against the CatFee API, impersonating the operator's account.
