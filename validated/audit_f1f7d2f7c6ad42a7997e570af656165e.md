## Title
Webhook `shop-domain` Header Not Covered by HMAC Signature Allows Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the shop identity (`shop-domain` header) that the app relies on to attribute the webhook event is never part of the signed material. Any party capable of producing one genuine, HMAC-valid webhook body for their own shop (i.e., any merchant that installs the app) can therefore replay that exact body+HMAC pair while swapping the `x-shopify-shop-domain` header to a victim shop, and `ShopifyAPI::Webhooks::Registry.process` will accept it as authentic and dispatch it under the victim's shop identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC solely from that signable string: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then unconditionally trusts `request.shop` (parsed straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is *not* part of the signed payload) to build `WebhookMetadata`, which is handed to the app's webhook handler as the tenant identity for the event: [3](#0-2) 

The `shop` accessor is read straight off an unauthenticated header: [4](#0-3) 

The identity binding that should hold is: `shop authenticated by HMAC == shop used for business logic`. Because only the raw body is signed, this equality is broken — the `shop` value acted upon by the handler is not bound to the value covered by the signature. Since a single app-wide `api_secret_key` is shared across every installed shop (this is standard OAuth-app architecture), any merchant who has installed the app can trigger a legitimate webhook to their own shop (valid HMAC over their own body), capture the raw body + HMAC pair, and resend it to the app's webhook endpoint with only the `x-shopify-shop-domain` header altered to a victim shop's domain. `HmacValidator.validate` will still succeed because it only checks the (unmodified) body against the (unmodified) HMAC, and `Registry.process` will hand the payload to the handler labeled as belonging to the victim shop.

### Impact Explanation
This breaks the shop/tenant identity boundary that webhook consumers rely on. An app that keys business logic off `WebhookMetadata#shop` (e.g., updating per-shop billing state, inventory counts, order records, or triggering shop-scoped side effects) can be made to apply another tenant's legitimate-looking event data to a victim shop it does not control — a cross-tenant data-integrity/cross-tenant access issue, consistent with the "Critical: cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any multi-tenant app built on this gem: the attacker only needs to be an ordinary (unprivileged, non-victim) merchant who has installed the app — no access to `api_secret_key`, no TLS interception, and no social engineering are required. They obtain a real, validly-signed webhook body/HMAC pair for their own shop simply by taking normal in-app actions that trigger the topic they want to forge, then replay it against the shared webhook endpoint with a modified shop header.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the HMAC-signed material, or otherwise cryptographically bind the `shop` value used for dispatch to the verified payload before calling the handler, e.g. reject/re-derive `shop` only from data that was included in `to_signable_string`, or require the host application to independently confirm that the reported shop has an active, matching subscription/session before trusting `WebhookMetadata#shop`. At minimum, document prominently that `x-shopify-shop-domain` is unauthenticated and must be cross-checked against known installed shops before use.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and on `victim-shop.myshopify.com` (single shared `api_secret_key`).
2. Attacker triggers a webhook topic in their own shop, receiving a genuine request with:
   - body: `raw_body`
   - `x-shopify-hmac-sha256`: valid HMAC of `raw_body` under the shared `api_secret_key`
   - `x-shopify-shop-domain`: `attacker-shop.myshopify.com`
3. Attacker resends the identical `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (via `Request#to_signable_string` returning only `raw_body`) succeeds because it never inspected the shop header.
5. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` and invokes the app's handler, which now processes attacker-controlled data as if it originated from `victim-shop`. [3](#0-2)
