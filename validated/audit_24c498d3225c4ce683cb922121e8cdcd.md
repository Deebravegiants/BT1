### Title
Stale Iris/IR-Net Model Configuration Persists After Backend Config Update Due to Mega Agent Not Being Re-Deployed - (File: `src/plans/biometric_pipeline/mod.rs`)

### Summary
The biometric pipeline updates `face_identifier`'s model configuration on every signup via an explicit `UpdateConfig` message, but never re-applies updated `iris_model_configs` / `ir_net_model_configs` to the already-running `mega_agent_one` process. Those configs are baked in only once, when the process is first spawned, and are never refreshed unless the process is explicitly killed and respawned (which normally happens only once at boot). This is directly analogous to the reported `HyperdriveFactory` issue: the "deployer" (backend config push) can be updated, but the component responsible for holding the actual model/data configuration (the already-running Mega Agent process) is not re-deployed along with it.

### Finding Description
`run_update_all_configs` in the biometric pipeline explicitly forwards only the face-identifier model config to the running agent on every signup: [1](#0-0) 

There is no equivalent `UpdateConfig` path for the Iris, IR-Net, or Occlusion models that live inside `mega_agent_one`. Those models' configuration is set exactly once, at process-init time, from a snapshot of the shared `Config`: [2](#0-1) [3](#0-2) 

`MegaAgentOne::Input::Config` simply returns a clone of the `MegaAgentOne` struct captured at `init()` time, it does not re-read the live `Config`: [4](#0-3) 

The Mega Agent process is constructed from the shared config only in `init_mega_agent_one`/`init_mega_agent_two`: [5](#0-4) 

But the per-signup path only calls `enable_ir_net`/`enable_rgb_net`, which call `enable_mega_agent_one`/`enable_mega_agent_two`: [6](#0-5) 

Per the broker macro that generates `enable_*`, if the agent `Cell` is already `Enabled` or `Disabled` (i.e., previously spawned), the existing agent instance is simply re-enabled — `init_mega_agent_one` (and therefore the fresh `Config` snapshot) is **not** invoked again: [7](#0-6) 

The only place that actually kills and re-initializes `mega_agent_one`/`mega_agent_two` (thereby picking up a fresh config) is the one-time warmup plan run at process boot, before the main signup loop starts: [8](#0-7) 

Meanwhile, the shared `Config` (including `iris_model_configs` and `ir_net_model_configs`) is refreshed independently and periodically by the `Observer` broker in the background, completely decoupled from any Mega Agent respawn: [9](#0-8) [10](#0-9) 

So once the orb has booted and performed the initial warmup, any subsequent backend push that changes `iris_model_configs` or `ir_net_model_configs` (analogous to updating the "yield-source factory implementation") will be picked up into the shared `Config` object, but the long-running `mega_agent_one` Python process (analogous to the "data provider") keeps using its original, stale model configuration for every subsequent signup during the orb's uptime — exactly mirroring the reported bug where "one can set a new deployer ... but one can't actually change the data provider."

### Impact Explanation
`iris_model_configs` and `ir_net_model_configs` govern which iris/IR-Net model files and parameters are used to produce the iris code and mask code used for identity de-duplication and biometric enrollment. If the backend intends to roll out a corrected/updated iris or IR-Net model (e.g., to fix a fraud-detection weakness, calibration issue, or vulnerability in the currently deployed model) by pushing new `iris_model_configs`/`ir_net_model_configs`, orbs that have already completed their one-time boot warmup will silently continue running biometric captures against the old, stale model configuration for the remainder of their uptime — potentially producing iris codes with degraded fraud/liveness properties or processed by a model version the backend believed had been retired. This directly weakens fraud/liveness enforcement guarantees for biometric signups performed after the intended config rollout.

### Likelihood Explanation
This occurs automatically in normal operation whenever a backend operator updates `iris_model_configs` or `ir_net_model_configs` while an orb is already running (i.e., any time after the initial boot warmup), since the `Observer`'s periodic config-download path never triggers a `mega_agent_one`/`mega_agent_two` restart. No attacker action is required — it is a systemic propagation gap that manifests on every long-lived orb process across an arbitrary number of signups until the orb-core process is restarted.

### Recommendation
When the shared `Config`'s `iris_model_configs`/`ir_net_model_configs` (and any other Mega-Agent-embedded model configuration) changes, either:
1. Kill and respawn `mega_agent_one`/`mega_agent_two` (as done in `warmup::Plan::run`) so the new config is picked up, or
2. Add an explicit `UpdateConfig` input/handler for the Iris, IR-Net, and Occlusion models inside `MegaAgentOne`/`MegaAgentTwo`, mirroring the existing `face_identifier::Input::UpdateConfig` mechanism, and invoke it from `run_update_all_configs` on every signup (or on detected config change) so all models — not just face identifier — stay in sync with the latest backend-pushed configuration.

### Proof of Concept
1. Boot the orb; `warmup::Plan::run` spawns `mega_agent_one` with `iris_model_configs = A` from the initial `Config`.
2. Backend operator later updates the orb's `iris_model_configs` to `B` (e.g., via the management backend config endpoint).
3. `Observer::config_update` downloads the new config and stores `iris_model_configs = B` in the shared `Arc<Mutex<Config>>` — see `src/brokers/observer.rs` lines 187-205.
4. A new signup starts; `MasterPlan` reaches the biometric pipeline, which calls `orb.enable_mega_agent_one()` → `enable_ir_net()`. Because the `mega_agent_one` `Cell` is not `Vacant` (it was already spawned during warmup and merely disabled/enabled between signups), the macro-generated `enable_mega_agent_one` reuses the existing process instance instead of calling `init_mega_agent_one()` again — see `agentwire/macros/src/broker.rs` lines 275-290 and `src/brokers/orb.rs` lines 881-894/999-1005.
5. `run_update_all_configs` in `src/plans/biometric_pipeline/mod.rs` only pushes `face_identifier_model_configs` to `mega_agent_two`; it never sends any config update to `mega_agent_one`.
6. The Iris/IR-Net models used for this and all subsequent signups continue running with the stale config `A`, despite the backend's intended update to `B`, until the orb-core process itself is restarted.

    fn config_update(&mut self, observer: &mut Observer) -> Result<()> {
        if self.before_config_update()? {
            match observer.config_update.as_mut().map(future::FutureExt::now_or_never) {
                Some(None) => return Ok(()),
                Some(Some(result)) => result??,
                None => {}
            }
            let config = Arc::clone(&observer.config);
            let ui = observer.ui.clone();
            observer.config_update = Some(tokio::spawn(async move {
                if let Ok(new_config) = Config::download().await {
                    *config.lock().await = new_config;
                    config.lock().await.propagate_to_ui(ui.as_ref());
                }
                Ok(())
            }));
        }
        Ok(())
    }
