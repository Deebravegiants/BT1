### Title
Webhook tenant identity (`shop`) is not covered by the HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC computed over the raw body, then dispatches the webhook to the app's handler using a `shop` value taken from an HTTP header that is never included in the signed bytes. Any actor who can obtain one genuinely-signed `(body, hmac)` pair for the app (e.g., by installing the app on their own store and receiving a legitimate webhook) can replay that same body/HMAC while substituting the `X-Shopify-Shop-Domain` header for an arbitrary victim shop, and the gem will accept it as an authentic webhook for that victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from the `shopify-shop-domain` / `x-shopify-shop-domain` header, entirely outside the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` only checks that `hmac == HMAC(secret, to_signable_string)`, i.e. it authenticates the body bytes, not the tenant identity: [3](#0-2) 

`Registry.process` trusts the HMAC check as proof the entire request (including `shop`) is authentic, then forwards `request.shop` unchanged into `WebhookMetadata` for the app's handler to act on: [4](#0-3) 

Because the app's `client_secret`/`api_secret_key` is shared across **all** shops that install the app (it is not per-tenant), any merchant who installs the app on their own store receives from Shopify a legitimately-signed `(raw_body, hmac)` pair using that same shared secret. Since `shop` is not part of `to_signable_string`, that merchant can resend the identical body and HMAC to the app's webhook endpoint while changing only the `shop-domain` header to a victim shop's domain. `HmacValidator.validate` will still return `true` (the body/HMAC pair is unchanged and valid), and `Registry.process` will hand the handler a `WebhookMetadata` claiming to originate from the victim shop — this is the "field acted on but not covered by the HMAC" identity-binding break: `hmac_valid(body) == true` is treated as equivalent to `shop_header == authentic_origin_shop`, which the code never establishes.

This is the direct structural analog of the reported bug class: a value (`shop`, playing the role of `startSqrtPriceX96`) that is acted upon by downstream logic but excluded from the cryptographic identifier/binding that is supposed to guarantee its integrity.

### Impact Explanation
This crosses a tenant boundary without needing the `api_secret_key`, an access token, or any privileged credential — only the ability to install the app on one's own store (something any unprivileged user can normally do) and to make a normal HTTP POST to the app's public webhook endpoint with attacker-chosen headers. Depending on what the host app's `WebhookHandler#handle` does with `data.shop` (e.g., deleting data for that shop, triggering `shop/redact` or `customers/redact` side effects, updating per-shop state, invalidating sessions, etc.), this enables cross-tenant data manipulation/corruption attributed to a shop the attacker does not own — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Moderately likely to be exploitable in practice: it requires (1) the ability to install the target app on an attacker-controlled store to harvest one genuine `(body, hmac)` pair, and (2) that the host application's webhook handler acts meaningfully on `WebhookMetadata#shop` without any additional shop verification (which is the intended and documented use of this field per `webhook_handler.rb`). Since the gem provides no mechanism or guidance to bind `shop` into the signature or to cross-check it against a known/registered store, any app built directly on this gem's documented `Registry.process` API inherits the flaw.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the signed body (e.g., by having `Request#to_signable_string` incorporate the shop-domain header, or by requiring the caller to separately verify that the `shop` header corresponds to a shop for which this specific webhook subscription/callback path was registered) so that swapping the `shop-domain` header invalidates the signature.

### Proof of Concept
1. App developer installs their own app on `attacker-shop.myshopify.com`. Shopify sends a legitimate webhook to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC_SHA256(client_secret, B)`, plus `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker constructs a new HTTP POST to the same webhook endpoint using the exact same body `B` and `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shop-domain" => "victim-shop.myshopify.com", "hmac-sha256" => H, ...})` is constructed; `to_signable_string` returns `B` unchanged.
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC_SHA256(client_secret, B) == H` → `true`. [5](#0-4) 
5. The handler's `data.shop` is `"victim-shop.myshopify.com"`, even though Shopify never sent any webhook for that shop — the app processes an attacker-forged event as if it belonged to `victim-shop`.
