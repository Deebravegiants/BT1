### Title
Webhook `shop-domain` (and `topic`/`webhook_id`/`api_version`) header is not covered by the HMAC signature, allowing tenant/topic spoofing via header substitution on an otherwise-valid signed body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values that `ShopifyAPI::Webhooks::Registry.process` hands to the app's `WebhookHandler` are all read from unauthenticated HTTP headers. `HmacValidator.validate` only proves that *some* body byte-string was signed with `api_secret_key`; it proves nothing about which shop or topic that body belongs to. This breaks the intended identity binding `hmac_verified(body) == (shop, topic) trusted`, mirroring the reported bug class where a value used downstream (reserve0) is not covered by the invariant the code relies on (constantProduct check).

### Finding Description
`to_signable_string` for the webhook request returns `@raw_body` exclusively: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers, none of which are part of the signed string: [2](#0-1) 

`Registry.process` validates only the HMAC of the request object and then immediately trusts `request.topic` and `request.shop` to route and identify the tenant for the handler call: [3](#0-2) 

The resulting `WebhookMetadata` struct — which is the only tenant/context information the app-provided `WebhookHandler#handle` receives — carries `shop` and `topic` as trusted fields even though neither was cryptographically bound to the signature: [4](#0-3) 

Because Shopify uses the **same** `api_secret_key` to sign webhooks for every shop that has installed a given app, any body+HMAC pair that was legitimately generated for one shop remains a byte-for-byte valid signature regardless of which `shop-domain`/`topic`/`webhook_id` headers accompany it. An unprivileged user who installs the app on their own (attacker-controlled) shop will receive genuine webhook deliveries with valid `(body, hmac)` pairs for known topics (including the mandatory `customers/redact`, `customers/data_request`, `shop/redact` topics). They can replay that exact body and HMAC directly to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header for a victim shop. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` will dispatch the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop string.

The binding that should hold is:
`hmac_signed_bytes == (body, shop, topic)` for the value the handler treats as authenticated.
What actually holds is:
`hmac_signed_bytes == body` while `shop`/`topic` are attacker-controlled header bytes never covered by the signature — exactly the "field acted on but not covered by the HMAC" identity-binding break called out as in-scope.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` (or `#topic`) to select per-tenant state, trigger tenant-scoped side effects, or fulfill GDPR-style compliance actions (`customers/redact`, `shop/redact`, `customers/data_request` are explicitly special-cased in `Registry`) is exposed to cross-tenant confusion: an attacker who merely installs the app on a shop they control can cause the library to hand the app's handler a forged `shop` value pointing at any victim shop domain, together with an attacker-chosen `body`/`topic` combination that was legitimately signed for the attacker's own tenant. This is a cross-tenant identity binding bypass reachable by an unprivileged internet user with no access to `api_secret_key`, access tokens, or any victim credentials — only to their own legitimately-issued webhook deliveries.

### Likelihood Explanation
Likelihood is high for any deployment that exposes the webhook endpoint publicly (the normal deployment model) and does not itself re-validate `shop` against an out-of-band source. The only prerequisite is that the attacker install the app on a shop of their own — a normal, unprivileged action — and then capture and replay one legitimately delivered webhook body/HMAC pair with modified headers. The gem enables this because it never binds `shop`/`topic` into the signed payload, unlike the OAuth callback flow (`AuthQuery#to_signable_string`) which does include `shop`, `host`, `state`, etc. in its signable string.

### Recommendation
Extend `ShopifyAPI::Webhooks::Request#to_signable_string` (or the validation step in `Registry.process`) to bind the values that the handler subsequently trusts — at minimum `shop` and `topic` — into the HMAC computation, or otherwise cryptographically tie the header-derived `shop`/`topic` to the signed body before constructing `WebhookMetadata`. Document clearly that consuming apps must not treat `WebhookMetadata#shop`/`#topic` as authenticated unless this binding is added, since today only the raw body is protected by the signature.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic the app is subscribed to and capture the raw request: `body`, and the `X-Shopify-Hmac-Sha256`, `X-Shopify-Topic`, `X-Shopify-Shop-Domain` headers Shopify sent.
2. Replay the exact same `body` and `X-Shopify-Hmac-Sha256` value to the app's public webhook endpoint, but change `X-Shopify-Shop-Domain` to `victim.myshopify.com` (and/or `X-Shopify-Topic` to another subscribed topic if the body happens to be reusable, e.g. an empty-payload topic like `shop/redact`).
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers, `HmacValidator.validate(request)` in `Registry.process` succeeds because it only rehashes `@raw_body` — the substituted `shop-domain`/`topic` never enter the HMAC computation (confirmed by `to_signable_string` at `lib/shopify_api/webhooks/request.rb:36-38`).
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` with the attacker-forged `shop` value, causing the app's handler to act as though the event originated from `victim.myshopify.com`.
