### Title
Unauthenticated `EmporiumUpgradeable.runAction` "stateless" arbitrary call drains any ETH/ERC20 held by the Emporium contract - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`transact()` allows a caller to select the "Min" ZK circuit path (`dimensions.tokenNumber == 0`, `circomData.erc20TokenAddresses.length == 0`) when the external action is Emporium (`HINKAL_EMPORIUM_ACTION_ID`). In that path the ZK proof only needs to satisfy `MainEVMCircuitMin`, which contains **no** nullifier/UTXO ownership check and **no** EdDSA signature verification — it merely checks `message == Poseidon(messageSeed)` and that `calldataHash`/`outTimeStamp` match. Combined with `EmporiumStack.signerAddress == address(0)`, `verifyWallet()` performs **no** EIP-712 signature check either. This lets *any* unprivileged address submit a trivially-constructed proof that authorizes `EmporiumUpgradeable.runAction` to execute `op.endpoint.call{value: op.value}(op.callData)` — a fully attacker-controlled external call from the Emporium contract's identity — while the post-call balance reconciliation loop (`for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++)`) never runs because the token array is empty. Any ETH or ERC20 balance held by the Emporium contract at call time (dust, temporarily-held swap/bridge proceeds, protocol/relay fees in transit) can be swept to an attacker-chosen address with zero authorization.

### Finding Description
The generic-call bug class from the LI.FI report (arbitrary `.call()` on user/attacker-controlled `callTo`/`callData` with no whitelist) is reproduced here, but the root cause is worse: the call is not merely unwhitelisted, it is **unauthenticated**.

1. `Hinkal.transact()` verifies the ZK proof against `inputForCircom` produced by `CircomDataBuilder.formInputForCircom`: [1](#0-0) 
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, only `formInputEmporiumMin` is used, producing public inputs `[emporiumMessage, timeStamp, calldataHash]` with **no `signedMessageHash`, no nullifiers, no `rootHashHinkal` binding**.

2. The corresponding circuit, `MainEVMCircuitMin`, does not verify EdDSA ownership of any note or nullifier at all: [2](#0-1) 
Any address can generate a valid witness/proof for this circuit by simply picking any `messageSeed` and computing `Poseidon(messageSeed)`.

3. `HinkalHelper.performHinkalChecks` only checks `calldataHash` integrity, relay validity, dimensions, and onchain-creation constraints — none of which require proof of fund ownership when `dimensions.tokenNumber == 0`: [3](#0-2) 

4. `Hinkal._externalTransact` dispatches to `IExternalActionV2.runAction`. With `erc20TokenAddresses.length == 0`, `deltaAmountChanges` is an empty array and no tokens are moved into Emporium beforehand: [4](#0-3) 

5. Inside `EmporiumUpgradeable.runAction`, when `stack.signerAddress == address(0)`, `verifyWallet` skips signature verification entirely (only marks the message used): [5](#0-4) 
Then, for each `EmporiumOperation` with `invokeWallet == false` (or `signerAddress == 0`), it performs a raw arbitrary call from the Emporium contract itself, only blocking the `callHinkalWallet`/`doSendToRelay` selectors: [6](#0-5) 

6. Finally, the balance-conservation "equality" that would normally catch any unauthorized fund movement only iterates over `circomData.erc20TokenAddresses`: [7](#0-6) 
Since this array is empty in the exploited path, the equation `balanceChange == moved-to-emporium + tx-balance-delta ≥ 0` is never evaluated for **any** token, so an attacker can direct `op.endpoint.call` to steal any ETH/ERC20 the Emporium contract happens to hold (e.g., dust left from a previous legitimate swap/bridge/fee operation, ETH sent to its `receive()`), or to invoke `approve()`/`transfer()` on any token where Emporium retains a balance/allowance, with the theft outside the checked equality entirely.

This directly matches the analog rule: "value moved by Hinkal or an external action but not counted in the balance equation" and "a transferFrom / wallet op not authorised by the prover or signer" — here neither the ZK prover nor an EIP-712 signer authorizes the call at all.

### Impact Explanation
This is theft of protocol/relay-held funds (ETH/ERC20 balances sitting on the `EmporiumUpgradeable` contract) via a completely unauthenticated external call, satisfying the "High — theft ... of protocol/relay fees ... executing calls or moving assets a wallet owner or prover never authorised" criterion. If the Emporium ever accumulates any balance (dust from rounding in swaps, relay fees in transit, native ETH sent via its `receive()`), it is fully drainable by anyone, with no signature and a trivially forgeable ZK proof.

### Likelihood Explanation
Likelihood is moderate-to-high: exploitation requires (a) the Emporium contract to hold some balance at attack time, which can happen naturally through normal operation (dust from previous swaps/fee rounding, or ETH accidentally/intentionally sent to its payable `receive()`), and (b) constructing a trivial `MainEVMCircuitMin` proof and an `EmporiumStack` with `signerAddress = address(0)` — both of which are within reach of any EOA with no special privileges, no relayer collusion, and no admin key.

### Recommendation
- Do not allow the "stateless"/no-signer path (`Case 2`, `op.endpoint.call`) to execute when the accompanying proof provides no ownership/authorization binding — require `MainEVMCircuit` (not `MainEVMCircuitMin`) whenever any external call with `invokeWallet == false && signerAddress == address(0)` is present, i.e., don't allow the empty-token-dimension optimization to be combined with unauthenticated arbitrary calls.
- Alternatively/additionally, whitelist allowed `op.endpoint` addresses and function selectors for stateless interactions (mirroring the LI.FI fix), and ensure the Emporium contract never carries a standing balance across transactions (sweep dust to a UTXO/commitment unconditionally, independent of `circomData.erc20TokenAddresses`).
- Ensure the balance reconciliation loop in `runAction` accounts for **all** tokens/ETH actually touched by `stack.ops`, not just `circomData.erc20TokenAddresses`, so any balance drained from the contract is always checked against the equality.

### Proof of Concept
1. Attacker (no prior deposit, no notes, no signature key) crafts `Dimensions{tokenNumber:0, nullifierAmount:0, outputAmount:0}` and `CircomData` with `erc20TokenAddresses = []`, `amountChanges = []`, `externalActionData = {externalAddress: EmporiumProxy, externalActionId: HINKAL_EMPORIUM_ACTION_ID, externalActionMetadata: abi.encode(EmporiumStack{signerAddress:0, ops:[{endpoint: TARGET_TOKEN, invokeWallet:false, value:0, callData: abi.encodeCall(IERC20.transfer,(attacker, EmporiumBalance))}], maxFee:0, deadline:MAX}) }`.
2. Attacker sets `emporiumMessage` to any unused value, computes `calldataHash = getHashedCalldata(circomData)` per `CircomDataBuilder`, and picks any `messageSeed` such that `Poseidon(messageSeed)` is provided as the circuit's `message` output — this is a self-consistent, trivially satisfiable witness for `MainEVMCircuitMin` (no ownership proof required).
3. Attacker calls `Hinkal.transact(a,b,c,dimensions,circomData)`. `performHinkalChecks` passes (only checks hash/relay/dimensions, no ownership). `verifyProof` succeeds against `VerifierEVMMin0v4`. `_externalTransact` calls `Emporium.runAction` with empty `deltaAmountChanges`.
4. `verifyWallet` sees `signerAddress == address(0)` and returns without any signature check. The loop executes `Case 2`, calling `TARGET_TOKEN.call(callData)` from the Emporium contract, transferring any balance the Emporium holds in `TARGET_TOKEN` to the attacker.
5. The post-call reconciliation loop (`for i < circomData.erc20TokenAddresses.length`) does not run since the array is empty, so no revert occurs regardless of the balance drained.
