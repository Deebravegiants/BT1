## Analysis

The Hats report describes a front‑running griefing pattern: a permissionless multi‑item claim function reverts entirely if even one of its items was already claimed by an attacker who front-ran with a copy of the victim's own claim data. The strongest reachable analog in Hyperbridge is `HandlerV2.handlePostRequests()` (and its sibling `handleGetResponses()`), which is explicitly permissionless and batches many independent messages into one transaction, but fails the whole transaction if any single message in the batch was already delivered. [1](#0-0) 

### Title
Front-running a single leaf inside a `handlePostRequests`/`handleGetResponses` batch reverts the entire relayer transaction, enabling gas-griefing and message-delivery DoS - ([File: evm/src/core/HandlerV2.sol])

### Summary
`HandlerV2.handlePostRequests()` and `HandlerV2.handleGetResponses()` are permissionless functions that accept an arbitrary batch of leaves (`PostRequestLeaf[]` / `GetResponseLeaf[]`) with one combined membership proof, then loop over the batch a second time to dispatch each leaf, reverting the whole call with `DuplicateMessage()` if *any single* leaf in the batch was already delivered. Because relayer transactions (and their full calldata, including the MMR multiproof and every leaf) are visible in the mempool before inclusion, an attacker can front-run by delivering just one of the leaves ahead of the relayer's batch (or by fully replaying the relayer's calldata as their own transaction with higher gas), causing the relayer's original transaction to revert on the duplicate check. This mirrors the reported `multiClaim()` griefing exactly: an unprivileged actor can force expensive, otherwise-valid batched transactions to revert by pre-claiming/pre-delivering one entry, at victim expense.

### Finding Description
`handlePostRequests` builds `leaves[]` for every request in the batch, verifies them all together against the MMR overlay root, and then in the second loop checks per-leaf duplication before dispatch: [2](#0-1) 

```solidity

    PostRequestLeaf memory leaf = request.requests[i];
    // duplicate request?
    if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
    host.dispatchIncoming(leaf.request, _msgSender());
}
```

The same pattern exists in `handleGetResponses`: [3](#0-2) 

Unlike `EvmHost.dispatchIncoming`, which deliberately does *not* revert the whole batch when an individual module call fails (`"instead of reverting the entire batch, early return here"`) [4](#0-3) , the `handlePostRequests`/`handleGetResponses` pre-dispatch duplicate check has no such tolerance — a single already-delivered leaf reverts the *entire* handler call, discarding every other still-undelivered leaf in the batch along with the gas already spent building/verifying the MMR multiproof.

`batchCall` compounds this: relayers routinely wrap `handleConsensus` + `handlePostRequests`/`handleGetResponses` together via `IHandlerV2.batchCall`, and "If any call fails, the entire batch reverts" [5](#0-4) , so a single griefed leaf can also sink an unrelated consensus update bundled in the same transaction.

The relayer's calldata (including the leaves and their MMR proof) is fully public once broadcast (or once observable via the relayer's Rust encoding path in `tesseract/messaging/evm/src/tx.rs`'s `build_batch_inner_calls`/`submit_batch_messages`) [6](#0-5) , so an attacker monitoring the mempool can extract one (or all) of the pending leaves and beat the relayer to inclusion with a smaller/cheaper transaction delivering just that leaf, or even replay the relayer's exact calldata to steal the delivery (and its associated relayer-fee credit recorded via `_requestReceipts[commitment] = relayer`) while dooming the original transaction to `DuplicateMessage()`.

### Impact Explanation
- Any relayer submitting a batched `handlePostRequests`/`handleGetResponses`/`batchCall` transaction can be forced to revert by an attacker who front-runs a single leaf, wasting the relayer's gas on proof verification work that is discarded.
- Because relayers are the mechanism by which Hyperbridge delivers messages to destination chains, repeated griefing of batched deliveries degrades or blocks the delivery route for all pending messages bundled together, not just the griefed one — directly matching the rule's "route unable to deliver messages" criterion.
- The attacker can additionally steal the delivering-relayer role (and associated fee attribution written into `_requestReceipts`) by replaying the whole calldata, redirecting relayer-fee income away from the honest relayer.
- This is systemic: it applies to every batched delivery on every EVM destination chain using `HandlerV2`, and can be repeated indefinitely at low cost to the attacker (front-running/replay is far cheaper than the full batch's verification cost).

### Likelihood Explanation
Delivery transactions are necessarily public before inclusion (mempool visibility), and constructing the front-run transaction requires no special privilege — `handlePostRequests`/`handleGetResponses` are explicitly permissionless [7](#0-6) . Any MEV bot or targeted attacker capable of monitoring pending transactions and outbidding gas can trigger this repeatedly against any relayer, making the likelihood high wherever relayer batches are large or economically valuable enough to be worth disrupting.

### Recommendation
- Change the per-leaf duplicate check in `handlePostRequests`/`handleGetResponses` from a batch-reverting `revert DuplicateMessage()` to a per-leaf skip (mirroring `EvmHost.dispatchIncoming`'s "early return, don't revert the batch" pattern), so that one already-delivered leaf does not sink the rest of the batch.
- Alternatively/additionally, have the handler filter out already-delivered leaves from the batch before verification (or make verification tolerant of a partial leaf set), so the relayer's proof-verification gas is not wasted on leaves already claimed by a front-runner.
- Consider decoupling relayer-fee attribution from `_msgSender()` alone, or requiring some commitment/pre-image scheme, to reduce the value of wholesale calldata replay by a front-runner.

### Proof of Concept
1. Relayer builds and broadcasts a `handlePostRequests` (or a `batchCall` wrapping it) transaction delivering `N` pending `PostRequestLeaf`s to a destination `EvmHost`.
2. Attacker observes the pending transaction in the mempool, extracts one `PostRequestLeaf` (or the entire proof/leaf set) from the calldata.
3. Attacker submits their own `handlePostRequests` transaction (with higher gas price) delivering just that one leaf (or the same full batch), which lands first and sets `host.requestReceipts(leaf.request.hash())` to the attacker's address via `EvmHost.dispatchIncoming` [4](#0-3) .
4. The relayer's original transaction executes; in the dispatch loop it hits `if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();` for the griefed leaf and the entire transaction reverts [2](#0-1) , wasting the relayer's gas for verifying and attempting delivery of all `N` leaves, and (if replay was used) diverting delivery-fee credit to the attacker.
5. Attacker repeats for every subsequent relayer batch, indefinitely degrading message delivery throughput on the affected route.

    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
        }

        bytes32 root = host.stateMachineCommitment(request.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, request.proof.multiproof, leaves, request.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // duplicate request?
            if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.request, _msgSender());
        }
    }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
