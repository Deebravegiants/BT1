### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by checking only that `Utils::HmacValidator.validate(request)` succeeds, but the HMAC signature is computed exclusively over the raw request body. The `shop`, `topic`, and `webhook_id` values, which are taken directly from HTTP headers, are never part of the signed bytes, yet they are trusted and handed to the app's `WebhookHandler#handle` as authenticated tenant-identifying metadata.

### Finding Description
`Utils::VerifiableQuery#to_signable_string` for `Webhooks::Request` returns only `@raw_body`: [1](#0-0) 

The HMAC validator computes and compares the signature against exactly that signable string: [2](#0-1) 

Meanwhile, `shop`, `topic`, and `webhook_id` are read straight from headers with no cryptographic binding to the body or to the signature: [3](#0-2) 

`Registry.process` only gates on `HmacValidator.validate(request)` and then forwards the unauthenticated `request.shop`/`request.topic`/`request.webhook_id` fields straight into `WebhookMetadata`, which is delivered to the host application's handler as if it were trusted, tenant-scoping data: [4](#0-3) [5](#0-4) 

Because the api_secret_key used to sign webhooks is shared per-app across all shops that install the app, an attacker only needs to install the target app on their own (unprivileged) shop to obtain validly-signed webhook payloads for topics whose body content is shop-agnostic or attacker-controlled (e.g. many webhook bodies contain only resource IDs, or for topics like `app/uninstalled` the body is `{}`). The attacker can then replay that same body/HMAC pair while substituting the `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) header with an arbitrary victim shop domain. `HmacValidator.validate` will still pass because it never inspects the headers, and the handler receives a `WebhookMetadata` claiming to be from the victim tenant.

This breaks the identity binding: **shop authenticated (bytes actually covered by the HMAC) ≠ shop acted upon (header value trusted by the handler as the tenant identity)**. This matches the reported bug class of "a field acted on but not covered by the HMAC."

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata#shop` to key data lookups, session retrieval, or business logic (a documented and expected usage pattern, since the gem hands this field to the handler as the delivery's shop) can be tricked into operating on/for the wrong tenant. This is a cross-tenant access vulnerability: an attacker who is a legitimate, unprivileged merchant of the app can forge webhook deliveries that host applications will process as if they originated from a different shop, entirely from within this gem's own webhook-processing code path (no TLS interception, no stolen secrets, no social engineering required beyond normal app installation).

### Likelihood Explanation
Likelihood is moderate to high: exploitation only requires the attacker to be an ordinary app user (install the app on their own store to receive genuinely signed webhooks), then replay the body with a modified `shop-domain` header to the app's public webhook endpoint. No secret material needs to be obtained since the signature check never binds to the shop header at all.

### Recommendation
Include the shop domain (and ideally topic/webhook_id) in the HMAC-signed material, or otherwise cryptographically bind the header-derived identity to the signature before it is exposed via `WebhookMetadata`. At minimum, `Registry.process` should be able to cross-check `request.shop` against out-of-band knowledge (e.g., an active/known session for that shop) before trusting it, and the gem's documentation/API should make explicit that `WebhookMetadata#shop` is not authenticated by the HMAC check performed by `HmacValidator.validate`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, receiving a legitimately HMAC-signed webhook for a topic with static/attacker-controlled body content (e.g., `app/uninstalled` with body `{}`).
2. Attacker captures the raw body and the `x-shopify-hmac-sha256` header from this delivery.
3. Attacker POSTs the same raw body + same HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally changes `x-shopify-topic`/`x-shopify-webhook-id`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes/compares the HMAC over `@raw_body` [1](#0-0)  — validation succeeds because the body/signature pair is untouched.
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", ...)` [6](#0-5)  and performs whatever tenant-scoped action the app implements for that topic, believing it originated from the victim shop.
