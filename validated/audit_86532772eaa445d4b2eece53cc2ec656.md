## Title
Integer underflow/overflow in gateway staleness check allows bypass of message freshness validation - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
`HandleLegacyUserMessage` casts the attacker-controlled, signed `int64` field `TriggerRequestPayload.Timestamp` to an unsigned `uint` when performing its staleness check, and only rejects a timestamp value of exactly `0`. A negative timestamp wraps around to a very large unsigned value, causing the freshness comparison to always evaluate as "not stale," silently bypassing the anti-replay/freshness control.

## Finding Description
The staleness check is: [1](#0-0) 

`payload.Timestamp` is a caller-supplied `int64` field, and the only prior validation is an exact-zero check: [2](#0-1)  Negative values are never rejected. Casting a negative `int64` to `uint` wraps to a value near `math.MaxUint64`, making `now - maxAge > uint(timestamp)` false, so the "stale message" branch is skipped.

This handler is reached via `gateway.ProcessRequest`, where legacy requests only go through structural `msg.Validate()` before being dispatched to `HandleLegacyUserMessage`: [3](#0-2)  `msg.Validate()` only checks field lengths and that the signature is well-formed/extractable — it does not check the signer against any allowlist: [4](#0-3)  Any actor holding an arbitrary ECDSA keypair (i.e., anyone) can self-sign a message and satisfy this check; there's no allowlist gate before the vulnerable timestamp check, confirmed by the explicit TODO left in the code: [5](#0-4) 

After the bypassable check, the message is forwarded unmodified to every DON member: [6](#0-5) 

## Impact Explanation
The staleness check is a documented anti-replay/freshness control (per the schema: "needs to be within certain freshness to be processed"). An attacker can trivially defeat it by supplying `Timestamp: -1`, causing an out-of-freshness message to be forwarded to the entire DON, bypassing a designed security gate. This matches the "gateway request impersonation / freshness bypass" impact class described in scope, though the practical consequence is limited to bypassing the freshness/anti-replay gate itself — no authentication bypass, fund movement, or key exfiltration is demonstrated beyond that specific control being defeated.

## Likelihood Explanation
Reachable by any actor able to reach the gateway's user-facing HTTP endpoint and produce a syntactically valid signed `Message` (self-signing with an arbitrary keypair suffices, since no allowlist is enforced pre-dispatch). No special credentials, DON membership, or operator access are required, making this a low-effort, high-repeatability bypass.

## Recommendation
Explicitly reject negative `payload.Timestamp` values (e.g., `payload.Timestamp <= 0`), and perform the staleness comparison entirely in signed 64-bit arithmetic (`int64`) instead of casting to `uint`, to eliminate wraparound for out-of-range or negative attacker-supplied values.

## Proof of Concept
1. Construct a legacy `api.Message` with `Body.Method = "web_api_trigger"`, a valid `Body.DonID`, and a `TriggerRequestPayload` payload whose `Timestamp` field is set to `-1`.
2. Self-sign the message with any ECDSA keypair so it passes `msg.Validate()` (`core/services/gateway/api/message.go` L54-88), since no allowlist check occurs before `HandleLegacyUserMessage`.
3. Submit via `gateway.ProcessRequest` to the gateway's public user HTTP port.
4. Observe that `payload.Timestamp == 0` check passes (since it's `-1`, not `0`) at `core/services/gateway/handlers/capabilities/handler.go` L359-370.
5. Observe that `uint(-1)` wraps to `math.MaxUint64`, making the comparison at L372 false, so the "stale message" rejection at L373-382 is skipped.
6. Confirm the message is forwarded to all DON members via the loop at L417-418, despite having an invalid/negative timestamp — demonstrating the freshness check bypass. A Go unit test asserting `HandleLegacyUserMessage` does NOT return a "stale message" error for `Timestamp = -1` (while it does for very old positive timestamps) would concretely prove this.
