### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing shop-identity spoofing on otherwise-validly-signed webhook deliveries - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that is handed to the app's webhook handler from the `x-shopify-shop-domain` (or `shopify-shop-domain`) header, but the HMAC signature that `Registry.process` validates only ever covers the raw request body. The `shop` field is never bound to the HMAC, so its authenticity is not actually verified even when `Utils::HmacValidator.validate` succeeds.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` gates all further processing on this HMAC check and then immediately trusts `request.shop` (parsed straight from the header) as the tenant identity passed to the app's handler: [2](#0-1) 

`request.shop` is read directly from `shopify-shop-domain`/`x-shopify-shop-domain` with no cross-check against the HMAC-covered content and no use of `Utils::ShopValidator` (the domain-allowlist utility that exists elsewhere in the gem): [3](#0-2) 

`Utils::HmacValidator.validate` confirms only that `verifiable_query.to_signable_string` (the body) was HMAC-signed with the app's secret; it never inspects or binds `shop`: [4](#0-3) 

This breaks the intended identity binding: `HMAC-verified(body) == body used for {shop, topic, webhook_id} attribution`. In reality the equality only holds for `body`; `shop` (and `topic`/`webhook_id`) are asserted, not authenticated.

Exploit path: an attacker who is a legitimate merchant of the app (i.e., has the app installed on their own store and can therefore trigger real webhook deliveries with genuinely valid HMACs, computed with the app's single shared `api_secret_key`) can capture one such legitimately-signed delivery (body + `x-shopify-hmac-sha256`), then re-POST the identical body and HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with an arbitrary victim shop's `myshopify.com` domain (shop names are frequently guessable/public). `HmacValidator.validate` still succeeds because it only checks the (unchanged) body, and `Registry.process` forwards `shop: <victim-shop>` to the app's webhook handler as if the payload genuinely originated from the victim tenant.

### Impact Explanation
Applications built on this gem are documented and expected to key their session/data lookups off the `shop` value returned in `WebhookMetadata` (mirroring the pattern used everywhere else in the gem, e.g. `Utils::SessionUtils.offline_session_id(shop)`), since that is the only tenant identifier this gem's webhook layer exposes to host apps. Because `shop` is not bound to the HMAC, an attacker can forge the tenant attribution on an otherwise-valid webhook and cause the host app to process/store attacker-supplied webhook data (order/product/customer/GDPR payloads, etc.) under a victim shop's identity — a cross-tenant data-integrity/confusion issue. This matches the report's bug class (a field acted upon, but not covered by the authenticity check).

### Likelihood Explanation
Requires the attacker to already have a store where the target app is installed (to obtain one validly-signed body+HMAC pair) plus knowledge of a victim's `myshopify.com` domain — no leaked credentials, `api_secret_key`, or access tokens are needed, and no TLS interception is required. This is a realistic scenario for any app with public/open installation (Shopify App Store apps), since malicious actors can install the app on a throwaway/free dev store to harvest signed payloads and then target arbitrary shops by domain.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signed material, or otherwise cryptographically bind them (e.g., require verification that the `shop` header matches a shop known to have a currently-installed, HMAC-matching session before invoking the handler). At minimum, document/enforce that `Request#shop` must never be trusted as an authenticated value and require host apps to re-validate it against their own installation records before acting on webhook data. Passing `shop` through `Utils::ShopValidator.sanitize!` does not fix the forgery (it only limits domain format), so the real fix must extend the HMAC computation (or an equivalent binding) to cover the shop field.

### Proof of Concept
```ruby
# Attacker installs the app on their own store "attacker.myshopify.com"
# and receives (or triggers) a real webhook delivery with a valid HMAC:
body = '{"id":1,"note":"legit order from attacker store"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, body) # attacker cannot compute this themselves,
                                                                             # but Shopify sends it to them because they own this store

# Attacker replays the captured (body, hmac) but swaps the shop-domain header:
headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => Base64.encode64(hmac),      # unchanged, still valid for `body`
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com" # forged, not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate succeeds (only checks `body`),
#    handler.handle(data: WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", ...))
#    is invoked, attributing attacker-controlled data to the victim shop.
``` [2](#0-1) [5](#0-4)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
