This confirms the vulnerability. The code itself even documents this limitation in a comment at `findMatchingWithdrawal` [1](#0-0) , acknowledging that "multiple withdrawals of the same token in a single transaction are not supported" and matching is done purely by `assetId`, ignoring `index`.

Tracing the exact equality: `describeWithdrawal` is called per `WithdrawalIdentifier` (containing `index` and `withdrawalParams`), but `findMatchingWithdrawal` only uses `args.withdrawalParams.assetId` to search the withdrawals array returned by the POA bridge API, entirely discarding `args.index` [2](#0-1) . When two withdrawal legs of the same NEAR tx share an `assetId`, `createWithdrawalIdentifiers` assigns them `index: 0` and `index: 1` via a `RouteEnum.PoaBridge` counter [3](#0-2) , but both resulting `watchWithdrawal` polling loops call `describeWithdrawal` with the same `withdrawalParams.assetId` and thus the same, first-matching array element from the API response — so the second watcher reports the first withdrawal's `transfer_tx_hash` as its own [4](#0-3) .

Nothing in the traced path (`supports`, `validateWithdrawal`, `compareAddresses`, contract-level nonce/signature checks) disambiguates two same-asset legs by destination — none of those checks depend on `index` or `destinationAddress` at the `describeWithdrawal` stage. This is a real, reachable bug with attacker-controlled input (any user submitting two same-asset POA withdrawals with different destinations in one tx) and matches the required Critical impact criterion ("a status or hash misreport making an integrator credit or refund twice").

### Title
Same-asset POA withdrawal legs report identical txHash regardless of `index`/destination - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain status of a withdrawal leg solely via `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, ignoring the leg's `WithdrawalIdentifier.index`. When a single signed intent contains two POA withdrawal legs of the same `assetId` but different `destinationAddress`, both legs' watchers converge on the same (first) matching entry from the bridge API's `withdrawals` array, so both report the same `transfer_tx_hash`.

### Finding Description
The broken equality: `(status, txHash)` reported for withdrawal leg `index:1` should equal the actual completion outcome of leg `index:1`'s own transfer to its own `destinationAddress`; instead it equals leg `index:0`'s reported outcome, because `findMatchingWithdrawal` at [5](#0-4)  selects `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)` — a lookup by `assetId` alone, with no dependency on `index`, `destinationAddress`, or amount ordering.

Attacker input: a single NEAR intents tx containing two POA-bridge withdrawal intents for the same token (e.g. `nep141:btc.omft.near`), each to a different `destinationAddress`. `createWithdrawalIdentifiers` assigns them `index:0` and `index:1` using a per-route counter [6](#0-5) . `sdk.createWithdrawalCompletionPromises` spawns one `watchWithdrawal` per identifier, and both call `bridge.describeWithdrawal({...args.wid, ...})` [7](#0-6) . Both calls query the same `withdrawal_hash: args.tx.hash` (the shared NEAR tx) [8](#0-7) , receive the same `response.withdrawals` array with two entries of the same `near_token_id`, and both resolve to the identical first-matching entry, hence the same `transfer_tx_hash`.

None of the existing guards prevent this: `validateAddress`/`compareAddresses` only validate a single withdrawal's destination at creation time, not at status-matching time; `supports()` and `validateWithdrawal` don't distinguish sibling legs; the intents contract's signature/nonce checks authorize the intent but do not affect off-chain status correlation. The code's own comment acknowledges this is a known, unhandled limitation.

### Impact Explanation
An integrator polling withdrawal completion via the SDK for both legs will see both report the same `status: "completed"` and the same `txHash` — the txHash of only one of the two actual on-chain transfers. If the integrator credits/confirms user payouts based on this reported txHash (a common pattern to avoid duplicate crediting on chain reorgs or retries), one destination transfer gets confirmed twice (double-credit) while the second destination's real, distinct transfer remains unconfirmed/unlinked by the integrator's ledger. This is a status/hash misreport causing duplicate crediting, matching the "High" (or "Critical" per the prompt's own framing) impact category of "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
Preconditions are trivial and fully attacker-controlled: any ordinary user can submit a single NEAR intents transaction with two POA-bridge withdrawal legs of the same `assetId` routed to different `destinationAddress`. No special solver, relayer, or privileged role is needed — the attacker only needs to construct and sign an intent with two withdrawal primitives for a supported POA token. The bug is deterministic given the API returns unsorted withdrawals with duplicate `near_token_id`, and is repeatable on every such multi-leg same-asset withdrawal.

### Recommendation
Disambiguate `findMatchingWithdrawal` beyond `assetId`: match by `destinationAddress` (and/or amount, and `destinationMemo`) in addition to `assetId`, or track already-consumed entries in the response so each `index` maps to a distinct API withdrawal record, consistent with the ordering strategy the code comment proposes (sort both API results and withdrawal params by amount).

### Proof of Concept
Vitest test: mock `poaBridge.httpClient.getWithdrawalStatus` to return two `COMPLETED` withdrawals with the same `near_token_id` (e.g., `btc.omft.near`) but distinct `transfer_tx_hash` values (`hashA`, `hashB`) and distinct destination addresses embedded in each entry's data. Construct two `WithdrawalIdentifier`s with `index: 0` (destination A) and `index: 1` (destination B), same `assetId: "nep141:btc.omft.near"`. Call `poaBridge.describeWithdrawal(wid0)` and `poaBridge.describeWithdrawal(wid1)`. Assert: both resolve `status: "completed"` with `txHash === hashA` (i.e., `describeWithdrawal(wid1).txHash` incorrectly equals `describeWithdrawal(wid0).txHash` instead of `hashB`), proving the equality "txHash reported for index 1 == outcome of index 1's own transfer" is broken.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
