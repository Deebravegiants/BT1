### Title
Missing zero-address validation on `order.output.beneficiary` causes permanent loss of native-token fills - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
Neither `placeOrder` nor the fill paths (`_fillSameChain`, `_fillCrossChain`) validate that `order.output.beneficiary` is non-zero. When the output asset is the native token, the solver's payment is pushed to `beneficiary` via a raw low-level `.call{value: ...}("")`, which succeeds against `address(0)` (a call to an address with no code always returns success in the EVM). If the order creator supplies `bytes32(0)` as the beneficiary (by mistake, or via a buggy client/integration), the solver's ETH payment is sent to `address(0)` and is permanently unrecoverable — mirroring the `TimeLockPool.withdraw()` zero-address analog.

### Finding Description
`Order.output.beneficiary` is a user-supplied `bytes32` field that is **not** overwritten by `placeOrder` (unlike `order.user`, `order.source`, `order.nonce`, which are stamped with `msg.sender`/chain data at `evm/src/apps/IntentGatewayV2.sol:224-226`). The beneficiary is decoded from raw bytes with no validation: [1](#0-0) 

and again in the cross-chain fill path: [2](#0-1) 

For native-token outputs, the payout goes through a raw call rather than an ERC-20 transfer: [3](#0-2) [4](#0-3) 

A `call{value: amount}("")` to `address(0)` succeeds trivially (there is no code to execute, and EVM `CALL` to an address with zero code returns success), so `sent` is `true` and no revert occurs — the ETH is simply burned. `placeOrder` itself performs no non-zero check on `order.output.beneficiary` before escrowing the order and committing it to the `_orders` mapping and `OrderPlaced` event (see `evm/src/apps/IntentGatewayV2.sol:194-415`), so a zero beneficiary order can be placed and later filled without any revert.

### Impact Explanation
If a user (or any client library/integration constructing orders) supplies `bytes32(0)` for `output.beneficiary` on an order whose output asset is the native token, the solver who fills that order sends real ETH value that is irrecoverably lost to `address(0)` — the "gain" the solver expected to deliver to the beneficiary vanishes with no revert and no on-chain recovery mechanism. This is a genuine, permanent loss-of-funds bug reachable by any unprivileged order placer through `placeOrder`, matching Sherlock's Medium classification for the analogous `TimeLockPool.withdraw()` finding (no zero-address check on a beneficiary/receiver in a token-transfer flow). For ERC-20 outputs the loss is generally avoided because OpenZeppelin's `ERC20.transfer`/`transferFrom` reverts on transfers to the zero address, but the native-token branch has no equivalent protection.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires an order placer (or a bug in an off-chain SDK/integration building the `Order` struct) to leave/set `output.beneficiary` as zero for a native-asset output leg, and requires the order to actually be filled by a solver before the mistake is caught (no on-chain check ever blocks this). Since this is the exact bug-class of the analog report (a caller mistakenly supplying `address(0)` as a receiver with no defensive check), it is a realistic operational risk, especially for automated integrations that assemble orders programmatically and could pass an unset/zeroed field.

### Recommendation
Add an explicit `beneficiary != address(0)` check either in `placeOrder` (reject an order with a zero `output.beneficiary` for any output leg, or globally) or immediately before value transfer in `_fillSameChain` / `_fillCrossChain`, reverting with a clear error (e.g. `InvalidBeneficiary()`) before the native-value `.call` or ERC-20 transfer is attempted. This closes the loss vector for both same-chain and cross-chain fills.

### Proof of Concept
1. A user calls `placeOrder` with `order.output = PaymentInfo({ beneficiary: bytes32(0), assets: [{token: address(0) /* native */, amount: X}], call: "" })`. `placeOrder` does not validate `beneficiary`, so the order is accepted and escrowed (see `evm/src/apps/IntentGatewayV2.sol:194-415`).
2. A solver calls `fillOrder`, providing `X` native ETH as required output.
3. Execution reaches `_fillSameChain` (same-chain) or `_fillCrossChain` (cross-chain), computing `address beneficiary = address(uint160(uint256(order.output.beneficiary)));` → `address(0)`.
4. The native branch executes `beneficiary.call{value: beneficiaryTotal}("")` → succeeds trivially against `address(0)`, `sent == true`, no revert.
5. The solver's ETH is burned; the escrowed input tokens are still released to the solver per the normal fill logic, so the solver is fully paid on the input side while the intended beneficiary of the output never receives their ETH — it is permanently lost.
