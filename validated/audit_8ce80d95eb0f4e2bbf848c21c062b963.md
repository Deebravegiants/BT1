### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated HTTP headers [2](#0-1) . `HmacValidator.validate` only checks that the raw body matches the HMAC computed with the app's `client_secret` [3](#0-2) ; it never verifies the `shop-domain` header. `Registry.process` then trusts `request.shop` as the tenant identity and forwards it straight to the app's handler after HMAC validation passes [4](#0-3) .

### Finding Description
The binding that should hold is: `shop-domain header used for tenant routing == shop bound by the HMAC signature`. In this gem, the HMAC only covers `@raw_body`, so `hmac(raw_body, client_secret)` is valid for *any* `shop-domain` header value, since that header plays no role in the signature computation.

Because a single `client_secret` is shared across all shops that install the app, any merchant who legitimately installs the app can obtain valid `(raw_body, hmac)` pairs for their own store's webhooks (e.g., by triggering a `products/update` event on their own dev store). Nothing in this gem prevents that same merchant from replaying the exact `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header (e.g., a victim's shop domain). `Utils::HmacValidator.validate` will still return `true` [3](#0-2) , and `Registry.process` will hand the forged `shop` value to the handler as authenticated tenant identity [5](#0-4) .

### Impact Explanation
Host applications built on this gem's documented `Registry.process` / `WebhookMetadata` API are expected to trust `data.shop` as the authenticated tenant for whom the webhook event is being processed (e.g., to look up the merchant's session/access token, or to apply the event to that merchant's records). Since the gem itself does not bind `shop` to the HMAC, an attacker (an ordinary merchant who installs the app — no privileged credentials, no leaked secrets, no TLS interception) can cause the app to process an event body under a victim shop's identity — a cross-tenant data-confusion/spoofing primitive reachable purely through this gem's `process` API, without the host app doing anything wrong beyond following the documented interface.

### Likelihood Explanation
High. Any merchant who installs the app can generate a valid webhook (raw body + HMAC) for their own shop through normal Shopify webhook delivery, then replay it to the app's public webhook endpoint with a modified `shopify-shop-domain` (or `x-shopify-shop-domain`) header. No secret material beyond what a normal merchant already has access to (their own store's delivered webhook payload) is required.

### Recommendation
Include `shop` (and ideally `topic`, `webhook_id`, `api_version`) in the signed/verified material, or otherwise cryptographically bind the shop-domain header to the payload before exposing it via `WebhookMetadata`. At minimum, `Utils::HmacValidator.validate` should be extended (or a companion check added) so that the `shop-domain` header cannot be swapped without invalidating the signature, matching Shopify's actual webhook verification model where the raw body integrity is the only thing HMAC-protected but the shop is expected to be corroborated via a separate trusted channel (e.g., only accept `shop-domain` values for shops with an active session/installation known to the app, rather than trusting the header value verbatim).

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and triggers any subscribed webhook topic (e.g. update a product), causing Shopify to deliver a legitimate webhook: `raw_body = B`, `shopify-hmac-sha256 = HMAC(B, client_secret)`, `shopify-shop-domain: attacker.myshopify.com`.
2. Attacker crafts a new POST request to the app's webhook endpoint reusing `raw_body = B` and the same `shopify-hmac-sha256` value, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. The app calls `ShopifyAPI::Webhooks::Registry.process(request)`. `HmacValidator.validate(request)` computes HMAC over `request.to_signable_string` (`= B`) only, matches the supplied HMAC, and passes [6](#0-5) .
4. `request.shop` returns `victim-shop.myshopify.com` from the attacker-controlled header [7](#0-6) , and this value is passed into `WebhookMetadata` as the authenticated shop for the handler to act on [5](#0-4) , despite the HMAC never having covered the shop identity.
