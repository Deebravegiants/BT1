### Title
Unauthenticated Resume Endpoint Allows Cross-User Task Result Injection via Guessable Task UUID - ([File: core/web/pipeline_runs_controller.go])

### Summary
The `/v2/resume/:runID` endpoint is mounted on the unauthenticated route group and resolves pending pipeline task runs solely by UUID, with no verification that the caller is the bridge/adapter that was actually issued that `responseURL`. Anyone possessing or guessing a pending task's UUID can inject an arbitrary `pipeline.Result` and force-resume that job run.

### Finding Description
The router explicitly wires this route into the unauthenticated group: [5](#0-4) 

`PipelineRunsController.Resume` parses `runID` as a UUID, decodes an arbitrary JSON body into a `pipeline.ResumeRequest`, and calls `ResumeJobV2` with no check tying the caller to the original bridge request or verifying any secret/token bound to that specific pending run: [2](#0-1) 

This flows straight into `ResumeJobV2` → `pipelineRunner.ResumeRun`, which looks up the task purely by `taskID` and immediately updates its result and restarts the pipeline: [3](#0-2) [4](#0-3) 

The only "credential" protecting this action is knowledge of the task UUID, which is embedded in the `responseURL` sent to the external bridge adapter as part of the async bridge task flow (`t.uuid.String()` in `finalizeAndMarshalBridgeRequestData`). This mirrors the NanoClaw pattern precisely: a `questionId`-equivalent value (the task UUID) is the sole gate for submitting a privileged "response" (here, resuming a job run with attacker-controlled data), and there is no responder-identity/role check comparable to `handleApprovalsResponse`'s missing authorization check.

### Impact Explanation
An attacker who obtains or guesses a pending task run UUID (e.g., via logs, error messages, timing side channels, or a leaked bridge callback URL) can submit a forged result to resume any pending async bridge task. This can inject falsified data into a job's pipeline (e.g., forged price/oracle data downstream of a `BridgeTask`), or trigger premature/incorrect completion of a job run, without any authentication.

### Likelihood Explanation
Exploitation requires knowledge of a specific task UUID (128-bit, generally not brute-forceable), which lowers likelihood somewhat versus NanoClaw's simpler flow. However, UUIDs are not secrets by design — they can leak through node logs, monitoring/telemetry, external adapter logs, or network observation of the `responseURL` sent to third-party bridge servers, all of which are outside the node operator's trust boundary. Given the endpoint is unconditionally unauthenticated at the router level, any leak of the UUID is a full compromise of that pending run's integrity.

### Recommendation
Bind the resume capability to a per-run secret (e.g., a signed/HMAC token embedded in the `responseURL` distinct from the plain UUID, or require the external adapter to echo back a shared secret issued at dispatch time) rather than relying on the UUID alone as an implicit bearer credential. Alternatively, scope resume requests to the specific bridge that owns the pending task and verify that binding server-side before calling `ResumeJobV2`.

### Proof of Concept
1. Create a webhook/bridge job with an `Async="true"` bridge task; note that Chainlink dispatches a `responseURL` of the form `.../v2/resume/<taskUUID>` to the external adapter.
2. Obtain the `taskUUID` (e.g., via a monitoring dashboard, external adapter's own logs, or a MITM'd/compromised adapter integration).
3. As an unauthenticated party, send `PATCH /v2/resume/<taskUUID>` with an arbitrary body such as `{"data":"attacker-controlled-value"}`.
4. Observe that `PipelineRunsController.Resume` accepts the request, calls `ResumeJobV2`, and the pipeline resumes using the attacker-supplied value with no authentication or ownership check performed.

// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
}

func (r *runner) ResumeRun(ctx context.Context, taskID uuid.UUID, value any, err error) error {
	run, start, err := r.orm.UpdateTaskRunResult(ctx, taskID, Result{
		Value: value,
		Error: err,
	})
	if err != nil {
		return fmt.Errorf("failed to update task run result: %w", err)
	}

	// TODO: Should probably replace this with a listener to update events
	// which allows to pass in a transactionalised database to this function
	if start {
		// start the runner again
		go func() {
			ctx, cancel := r.chStop.NewCtx()
			defer cancel()
			if _, err := r.Run(ctx, &run, false, nil); err != nil {
				r.lggr.Errorw("Resume run failure", "err", err)
			}
			r.lggr.Debug("Resume run success")
		}()
	}
	return nil
}
