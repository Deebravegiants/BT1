### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers and are never included in the signed payload. `Registry.process` validates the HMAC against the body alone, then trusts the *unauthenticated* `shop` header as the tenant identity that is handed to the app's webhook handler.

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature over `verifiable_query.to_signable_string` and compares it against the `hmac` field using `OpenSSL.secure_compare`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body — it does not include `shop`, `topic`, or `webhook_id`: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) as the tenant/routing identity passed into the handler: [3](#0-2) 

Because the signature only binds the body bytes, and `shop` is sourced from an ordinary HTTP header (`shopify-shop-domain`/`x-shopify-shop-domain`) that is never part of the signed string, the equality the gem implicitly relies on —

`hmac_valid(body) == true` implies `shop_header == shop_that_produced_body`

— does not hold. An attacker who can obtain one valid `(body, hmac)` pair (e.g., by registering the webhook on their *own* shop and receiving a legitimate delivery from Shopify) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` will still pass because it never inspects the header, and `Registry.process` will dispatch the handler with `WebhookMetadata` claiming an attacker-chosen `shop`.

### Impact Explanation
This breaks the tenant-authentication boundary that host applications rely on the gem to enforce: the documented contract of `Registry.process`/`HmacValidator.validate` is that a passing HMAC check certifies the whole webhook (including which shop it is for), but only the body bytes are actually authenticated. Any application that uses `request.shop` (as returned via `WebhookMetadata`) to look up or mutate per-tenant data will process data under, or attribute events to, the wrong merchant — a cross-tenant data confusion condition directly caused by the gem's signing scope, not by host misuse of a documented API.

### Likelihood Explanation
Exploitation requires the attacker to be able to trigger at least one legitimate webhook delivery for a shop they control (trivial — merchant creates a dev/test store and installs the target app, or simply owns their own store), then replay the raw body+HMAC to the target endpoint with a forged shop header. This requires no access token, no `client_secret`, and no privileged account — only public network access to the app's webhook receiver, satisfying the "unprivileged internet user" constraint.

### Recommendation
Include the tenant-identifying headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signed string, or otherwise cryptographically bind them to the HMAC-verified body before they are surfaced to handlers via `WebhookMetadata`, so that a passing HMAC check certifies the complete webhook context rather than only the body bytes.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers/receives one legitimate webhook delivery, capturing the raw body `B` and the valid `x-shopify-hmac-sha256` header `H` (computed by Shopify over `B` with the app's shared secret).
2. Attacker POSTs the same `B` with the same `H`, but sets `x-shopify-shop-domain: victim.myshopify.com`, to the app's public webhook endpoint.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — this passes: [4](#0-3) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though the body/HMAC actually originated from `attacker.myshopify.com`, causing the app to process/act on data under the wrong tenant identity.
