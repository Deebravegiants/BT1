This confirms the vulnerability: the webhook `hmac` verification in `lib/shopify_api/webhooks/request.rb` only signs `@raw_body` (`to_signable_string` returns `@raw_body` alone), while `topic`, `shop`, `webhook_id`, and `api_version` are all read from unauthenticated headers via `shopify_header` and are never included in the signed content. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` computes the HMAC solely over `to_signable_string`, so it validates that the *body* came from Shopify but says nothing about which shop or topic it belongs to.

### Title
Webhook tenant identity (`shop`, `topic`) not covered by HMAC signature allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and the `shop`, `topic`, and `webhook_id` fields used by `ShopifyAPI::Webhooks::Registry.process` to identify the tenant and dispatch to a handler come from HTTP headers that are never part of the signed data.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` verifies incoming webhooks with `Utils::HmacValidator.validate(request)` and, if valid, immediately trusts `request.topic`, `request.shop`, and `request.webhook_id` to route the payload: [1](#0-0) 

`HmacValidator.validate` verifies the signature against `verifiable_query.to_signable_string`: [2](#0-1) 

For `ShopifyAPI::Webhooks::Request`, `to_signable_string` is defined as just the raw body — none of the identity headers are included: [3](#0-2) 

The binding the code implicitly relies on is:
`bytes verified by HMAC == bytes used to determine tenant (shop) and routing (topic)`

but in reality:
`bytes verified by HMAC (raw_body only) != identity fields consumed by handler (shop-domain, topic, webhook-id headers)`

Because `api_secret_key` is a single per-app secret shared across every shop that installs the app (not a per-shop secret), any party who can obtain one valid `(raw_body, hmac)` pair — e.g., an unprivileged merchant who installs the app on their own store and triggers a webhook for their own shop — can replay that exact body/HMAC pair to the app's webhook endpoint while swapping the `shopify-shop-domain` (and/or `shopify-topic`) header to a different, victim shop. `Request` never binds these headers into the signature check, so `Utils::HmacValidator.validate` still returns `true`, and `Registry.process` passes the attacker-chosen `shop` value straight into `WebhookMetadata.new(topic:, shop: request.shop, ...)` for the handler to act on: [4](#0-3) 

### Impact Explanation
This breaks the tenant boundary between shops served by the same app: an unprivileged holder of one valid signed webhook body (obtainable from their own legitimate app installation) can make the host application process arbitrary webhook data (e.g. `orders/create`, `customers/redact`, `shop/redact`, `app/uninstalled`) as if it originated from a different, victim shop with a passing HMAC check. Depending on how the host app's webhook handlers use `shop` (e.g. to look up/mutate per-shop records, deauthorize a session, or trigger data deletion), this enables cross-tenant data corruption/exfiltration or forced state changes against a shop the attacker does not control — matching the "cross-tenant access" impact category, since the tenant-identifying header is never covered by the cryptographic check meant to authenticate it.

### Likelihood Explanation
Likelihood is significant for any app author who trusts `request.shop`/`request.topic` after `Registry.process` returns without additional shop validation, which is the documented/intended usage pattern shown in `docs/usage/webhooks.md`. The attacker only needs an app installation on a shop they control (no leaked secrets, no TLS interception, no privileged access) to obtain a valid `(body, hmac)` pair, then a single crafted HTTP POST with modified headers to the same webhook endpoint.

### Recommendation
Include the tenant/routing identity fields (`shop`, `topic`, and ideally `webhook_id`) in the signed content used by `to_signable_string`, or otherwise cryptographically bind them (e.g., verify `shop` against a known/registered shop-secret mapping, or require the caller to separately validate `request.shop` against the session/shop the webhook was registered for before trusting it) rather than relying solely on a body-only HMAC computed with a secret shared across all shops of the app.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (a normal, unprivileged action) and triggers any webhook topic (e.g. `orders/create`) to their own registered endpoint, capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent.
2. Attacker crafts a new HTTP POST to the same app's webhook endpoint using the identical `raw_body` and `hmac` header values, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com` (and/or changes `X-Shopify-Topic`).
3. The app calls `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body:, headers:))`.
4. `Utils::HmacValidator.validate(request)` recomputes HMAC over `to_signable_string` (`raw_body` only) using the app's single shared `api_secret_key`; since the body/HMAC pair matches, validation passes.
5. `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` is invoked with `shop == "victim-shop.myshopify.com"`, causing the host app to process attacker-supplied data attributed to a shop the attacker does not own. [4](#0-3) [5](#0-4)
