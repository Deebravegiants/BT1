### Title
Confidential Relay Gateway Handler Matches Node Responses to Active Requests by ID Only, Without Verifying Method — Cross-Request/Method Confusion - ([File: core/services/gateway/handlers/confidentialrelay/handler.go])

### Summary
`HandleNodeMessage` in the confidential relay gateway handler resolves a node's response to its pending client request purely by the JSON-RPC `ID` string, and never checks that the response's `Method` matches the method the client actually requested (`ar.req.Method`). This mirrors the VMCI bug class: a lookup keyed on one identifying field (the handle/ID) while silently ignoring a second field that actually distinguishes the object's *type* (the resource type in VMCI, the JSON-RPC method here), allowing objects/requests of different types that happen to share the same key to be confused with each other.

### Finding Description
`activeRequest`s are stored in `h.activeRequests`, a map keyed solely by the request `ID`: [1](#0-0) 

`ID` is fully attacker/client-controlled — it comes directly from the JSON-RPC request the (unprivileged) caller submits via `HandleJSONRPCUserMessage`, with only a length bound (≤200 chars) and non-empty check: [2](#0-1) 

Once a request completes, its entry is deleted from `activeRequests` under lock: [3](#0-2) 

This frees the ID for immediate reuse. A client can then submit a brand-new request reusing the same `ID` but a *different* `Method` (`MethodSecretsGet` vs `MethodCapabilityExec`) as soon as the slot is free — `newActiveRequest` only rejects the ID while it is still active, not permanently: [4](#0-3) 

`HandleNodeMessage` then looks the response up purely by `resp.ID`: [5](#0-4) 

and immediately merges it into whatever `activeRequest` currently occupies that ID slot — with no comparison between `resp.Method` and `ar.req.Method`, and no comparison of `ar.labels` (workflow/execution identity) against the response: [6](#0-5) 

Contrast this with the sibling `vault` handler, which explicitly guards against exactly this class of bug by dropping any node response whose `Method` doesn't match the active request's method: [7](#0-6) 

The confidential relay handler has no equivalent check. Because `bundler.Bundle` decodes the collected per-node `Result` bytes according to `ar.req.Method` (deciding whether to unmarshal as `SignedSecretsResponseResult` or `SignedCapabilityResponseResult`): [8](#0-7) 

a late-arriving/duplicated node response that was produced for an old, already-completed request (e.g., a slow or retried node send from before the ID slot was freed) gets attributed to whatever new, differently-typed and differently-owned request now occupies that same ID, and is decoded/bundled under the wrong method and wrong workflow/execution identity — the type/identity discriminator (`Method`, and the `labels` derived from it) is never rechecked, exactly the missing check that caused the VMCI use-after-free/type-confusion (the resource *type* field was never compared alongside the handle).

### Impact Explanation
This causes cross-request/cross-method response confusion in the gateway used by the confidential-relay capability: a stale node response for one client's request (of one method/workflow) can be merged into and returned as part of a different client's request (of a different method/workflow) simply because both requests reused the same client-chosen `ID`. This can corrupt the bundle delivered to the enclave for a request that never should have contained that node's data, and can leak or misattribute per-node signed payloads across execution/workflow boundaries — a concrete cross-user response confusion consistent with the required impact classes.

### Likelihood Explanation
Reachable entirely from unprivileged client input: `ID` is caller-supplied and freely reusable the instant a prior request with that ID completes (which is normal, frequent behavior — completion happens on every successful/expired/errored request). No malicious node action is required; any legitimately slow or retried node response for the freed ID triggers the confusion. The main precondition — winning the race between the old ID being freed and a late node response arriving — depends on timing, but is a normal condition in a distributed system with node-level retries/latency, not an exotic attack.

### Recommendation
In `HandleNodeMessage` (confidentialrelay/handler.go), reject/drop responses whose `resp.Method` does not equal `ar.req.Method`, mirroring the check already present in `core/services/gateway/handlers/vault/handler.go`. Additionally, consider not reusing the bare client-supplied `ID` as the sole map key — key `activeRequests` by `(ID, Method)` or embed a gateway-generated nonce/generation counter in the map key so responses from a prior generation of the same ID can never be attributed to a newer, unrelated request.

### Proof of Concept
1. Client submits request A: `{"id": "X", "method": "wf_secretsGet", ...}` for workflow W1. Gateway fans out to nodes and registers `activeRequests["X"]` with `req.Method = MethodSecretsGet`, `labels = {WorkflowID: W1}`.
2. Node N is slow; before N's response for A arrives, A reaches quorum from other nodes and completes; `sendResponseAndClearRequest` deletes `activeRequests["X"]`.
3. Client (or another client) immediately submits request B: `{"id": "X", "method": "wf_capabilityExec", ...}` for workflow W2. `newActiveRequest` succeeds because the "X" slot is free; `activeRequests["X"]` now has `req.Method = MethodCapabilityExec`, `labels = {WorkflowID: W2}`.
4. Node N's delayed response for the original request A (containing a `SignedSecretsResponseResult` payload, method `wf_secretsGet`, ID "X") finally arrives at `HandleNodeMessage`.
5. `getActiveRequest("X")` returns B's `activeRequest`; no method check rejects it. The stale secrets-get payload is added to B's `responses` map and passed to `bundler.Bundle(ar.req, ...)` with `ar.req.Method == MethodCapabilityExec`, causing the gateway to attempt to unmarshal a `SignedSecretsResponseResult` payload as a `SignedCapabilityResponseResult` (undecodable in the simplest case, but demonstrating that a differently-typed/differently-owned response is silently merged into an unrelated request purely due to ID reuse and the missing type/method check).

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	labels := h.extractRequestLabels(req)
	l := h.requestLogger(req, labels)
	l.Debugw("handling confidential relay request", "nodes", len(h.donConfig.Members), "f", h.donConfig.F)

	ar, err := h.newActiveRequest(req, labels, callback)
	if err != nil {
		return err
	}

	return h.fanOutToNodes(ctx, l, ar)
}

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], labels requestLabels, callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID, "executionID", labels.ExecutionID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		labels:    labels,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}

func (h *handler) sendResponseAndClearRequest(ctx context.Context, ar *activeRequest, payload gwhandlers.UserCallbackPayload) error {
	if !ar.completed.CompareAndSwap(false, true) {
		// Another path already answered this request.
		return nil
	}

	sendErr := ar.SendResponse(payload)

	h.mu.Lock()
	delete(h.activeRequests, ar.req.ID)
	h.mu.Unlock()

	if sendErr != nil {
		h.lggr.Errorw("error sending response to user", "requestID", ar.req.ID, "executionID", ar.labels.ExecutionID, "error", sendErr)
		return sendErr
	}

	h.recordMetrics(ctx, payload.ErrorCode)
	h.lggr.Debugw("response sent to user", "requestID", ar.req.ID, "executionID", ar.labels.ExecutionID, "errorCode", payload.ErrorCode)
	return nil
}

func (b *bundler) Bundle(req jsonrpc.Request[json.RawMessage], resps map[string]jsonrpc.Response[json.RawMessage], l logger.Logger) (*BundleSummary, error) {
	summary := newBundleSummary(len(resps))

	switch req.Method {
	case relaytypes.MethodSecretsGet:
		out := make([]relaytypes.SignedSecretsResponseResult, 0, len(resps))
		for nodeAddr, r := range resps {
			if r.Error != nil || r.Result == nil {
				summary.addError(nodeAddr, r.Error)
				continue
			}
			var signed relaytypes.SignedSecretsResponseResult
			if err := json.Unmarshal(*r.Result, &signed); err != nil {
				summary.addUndecodable()
				l.Warnw("skipping undecodable secrets response from node", "nodeAddr", nodeAddr, "error", err)
				continue
			}
			out = append(out, signed)
		}
		encoded, err := json.Marshal(relaytypes.SignedSecretsResponseBundle{Responses: out})
		if err != nil {
			return nil, fmt.Errorf("failed to encode secrets response bundle: %w", err)
		}
		summary.setSignedResponse(wrapBundle(req, encoded), len(out))
		return summary, nil
	case relaytypes.MethodCapabilityExec:
		out := make([]relaytypes.SignedCapabilityResponseResult, 0, len(resps))
		for nodeAddr, r := range resps {
			if r.Error != nil || r.Result == nil {
				summary.addError(nodeAddr, r.Error)
				continue
			}
			var signed relaytypes.SignedCapabilityResponseResult
			if err := json.Unmarshal(*r.Result, &signed); err != nil {
				summary.addUndecodable()
				l.Warnw("skipping undecodable capability response from node", "nodeAddr", nodeAddr, "error", err)
				continue
			}
			out = append(out, signed)
		}
		encoded, err := json.Marshal(relaytypes.SignedCapabilityResponseBundle{Responses: out})
		if err != nil {
			return nil, fmt.Errorf("failed to encode capability response bundle: %w", err)
		}
		summary.setSignedResponse(wrapBundle(req, encoded), len(out))
		return summary, nil
	default:
		return nil, fmt.Errorf("%w: %q", errUnknownMethod, req.Method)
	}
