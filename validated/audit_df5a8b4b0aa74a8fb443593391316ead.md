### Title
Unrestricted `CallDispatcher.dispatch()` lets anyone drain residual token/ETH dust left in the shared dispatcher after HFT/WrappedHFT/BridgeToken calldata execution - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher` is deployed once per chain and shared across every app that supports calldata execution — `HyperFungibleToken`, `WrappedHyperFungibleToken`, `BridgeToken`, and `IntentGatewayV2` — as configured via `dispatcher` in each app's setup. [1](#0-0) [2](#0-1) [3](#0-2)  Its `dispatch()` entry point is `external` with **no access control whatsoever** — the target-contract check only guards against sending calls to EOAs, it does not restrict who may call `dispatch()` or which assets the encoded calls may move:

```solidity
function dispatch(bytes memory encoded) external {
    Call[] memory calls = abi.decode(encoded, (Call[]));
    ...
    (bool success, bytes memory result) = to.call{value: call.value}(call.data);
    if (!success) revert CallFailed(to, result);
}
``` [4](#0-3) 

This is functionally identical to the Unistreets bug class: a shared custody contract that holds valuable assets executes attacker-supplied calldata with no restriction on caller or target, letting anyone inject calls (e.g. `IERC20.transfer`/`approve`) to move out any assets it happens to be holding.

### Finding Description
For `HyperFungibleToken`/`WrappedHyperFungibleToken`/`BridgeToken`, when a cross-chain send carries a non-empty `data` field, tokens are minted/unlocked directly to `params.to` (which the sender can set to the `CallDispatcher` address so the encoded `Call[]` can spend them), and then the app forwards the payload to the dispatcher:

```solidity
_mint(beneficiary, message.amount);
if (message.data.length > 0) {
    ICallDispatcher(_dispatcher).dispatch(message.data);
}
``` [5](#0-4) 

Unlike `IntentsBase._execute`, which explicitly sweeps any residual dispatcher balance back to the gateway after executing the order's calldata, [6](#0-5)  the HFT/WrappedHFT/BridgeToken `onAccept` paths perform **no sweep** after `dispatch()` returns. [7](#0-6)  Any tokens or native ETH the encoded `Call[]` doesn't fully consume (slippage, partial fills, DEX refunds of unused ETH on `swapETHForExactTokens`-style calls, an approve that isn't fully drawn down, etc.) is left sitting in the `CallDispatcher`'s own balance — the docs themselves acknowledge the dispatcher "holds tokens temporarily during execution." [8](#0-7) 

Because `dispatch()` has no owner/caller restriction, once any balance accrues in the singleton `CallDispatcher`, **any unprivileged address** can call `dispatch()` directly with an encoded `Call[]` such as `{to: token, value: 0, data: approve(attacker, balance)}` or `{to: token, value: 0, data: transfer(attacker, balance)}` (or simply have the dispatcher forward its native balance), stealing residual funds that were minted/unlocked for a legitimate user's cross-chain transfer.

### Impact Explanation
The `CallDispatcher` is a shared, chain-wide singleton reused across all calldata-executing apps (HFT, WrappedHFT, BridgeToken, IntentGatewayV2). [9](#0-8)  Any residual balance left after a legitimate calldata-execution flow becomes permanently and immediately stealable by any unprivileged party — a concrete, unauthorized theft of funds custodied on behalf of users, matching the Unistreets root cause (unrestricted arbitrary-calldata injection draining a shared custody contract).

### Likelihood Explanation
Any HFT/WrappedHFT/BridgeToken sender who routes calldata through the `CallDispatcher` (per the documented and tested swap-then-forward pattern) can trigger dust accumulation from ordinary slippage or partial execution, and the theft itself requires only a single unprivileged call to a public function with no preconditions — making this trivially and repeatedly exploitable by any observer monitoring the dispatcher's balance.

### Recommendation
Restrict `CallDispatcher.dispatch()` so only the intended caller for a given batch of calls can invoke it (e.g., per-call-session authorization, or making `CallDispatcher` non-shared/ephemeral per invocation), and/or require every consuming app (`HyperFungibleToken`, `WrappedHyperFungibleToken`, `BridgeToken`) to sweep any residual dispatcher balance for the relevant token/ETH back to the app or beneficiary immediately after `dispatch()` returns, exactly as `IntentsBase._execute` already does.

### Proof of Concept
1. A user bridges tokens via `HyperFungibleToken.send()` with `to = CALL_DISPATCHER_ADDRESS` and `data` encoding a swap (e.g., approve + `swapExactTokensForTokens`) as shown in the documented calldata-execution example. [10](#0-9) 
2. On the destination chain, `onAccept` mints tokens to the `CallDispatcher` and calls `dispatch(message.data)`. [5](#0-4)  Due to slippage/partial fill/unused ETH refund, some token or ETH balance remains on the `CallDispatcher` after the swap completes; no sweep occurs.
3. An attacker observes the nonzero balance on the shared `CallDispatcher` and calls `dispatch()` directly (it is `external` with no modifiers) with `Call[] = [{to: leftoverToken, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, leftoverBalance)}]`. [4](#0-3) 
4. The call succeeds unconditionally (only `extcodesize(to) != 0` is checked) and the attacker receives the leftover funds that belonged to the bridging user.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }

        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
