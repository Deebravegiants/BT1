### Title
Webhook shop/topic/webhook-id identity fields are unauthenticated (not covered by HMAC) enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` only verifies that HMAC over the body [1](#0-0) . But `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated HTTP headers, not from the signed body [2](#0-1) . `Registry.process` validates only the HMAC of the body and then forwards these unauthenticated header values straight to the app's handler as trusted tenant-identifying metadata [3](#0-2) .

### Finding Description
The identity binding that should hold is: `HMAC-verified-bytes == bytes-that-determine-tenant(shop)`. In this gem that equality is broken — the HMAC is computed and checked only over `@raw_body` [4](#0-3) , while the `shop` (and `topic`/`webhook_id`) values used to route/attribute the event come from the `shopify-shop-domain` (or `x-shopify-shop-domain`) header, which is not part of the signed content [5](#0-4) .

Since the app's `api_secret_key` used to sign webhooks is the same across all shops that install the app (it's the app's client secret, not per-tenant), any unprivileged merchant who has installed the app can trigger a legitimate webhook for their own store (e.g. `orders/create`), capture the valid `(raw_body, hmac)` pair sent by Shopify to their app's endpoint, and then resend that exact body+HMAC to the same endpoint while substituting the `shop-domain` header with an arbitrary victim shop domain. `Utils::HmacValidator.validate` will still succeed because it only checks the body bytes, not the shop header [6](#0-5) . `Registry.process` then dispatches to the handler with the forged `shop` value [3](#0-2) .

The gem's own documentation instructs host applications to trust `data.shop` directly as the tenant identifier once `Registry.process` succeeds (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), reinforcing that this field is meant to be authoritative [7](#0-6) .

### Impact Explanation
This is a cross-tenant access vector: an unprivileged merchant (who legitimately controls only their own shop and never sees the app's `client_secret`) can forge webhook events that the host application will attribute to a completely different, victim shop, since the shop identifier is never covered by the HMAC. Any downstream host-application logic that trusts `data.shop` to select which tenant's records to create/update/delete (as the gem's own docs recommend) can be corrupted with attacker-supplied body content but a victim's shop tag, leading to writing forged data into another merchant's account context or bypassing per-tenant authorization checks that key off `shop`.

### Likelihood Explanation
Likelihood is limited by the need to control a real installation of the target app (to legitimately receive one valid signed webhook body) and knowledge of the app's public webhook endpoint, both readily available to any unprivileged merchant who installs a public app. No possession of `client_secret`, access tokens, or any other privileged credential is required — only replaying a previously captured, validly-signed request with a modified header.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`/`api_version`) values in the signed/verified material, or otherwise cryptographically bind them to the body before trusting them — e.g., by having `Utils::HmacValidator`/`Webhooks::Request#to_signable_string` incorporate the shop-domain header into the HMAC input (as Shopify does for OAuth `AuthQuery#to_signable_string`, which signs all relevant fields together [8](#0-7) ), or require host applications to cross-check `request.shop` against a known/authorized shop list before trusting the payload.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers for `orders/create`.
2. Attacker triggers an order creation in their own store; Shopify sends a webhook to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same `raw_body: B` and `X-Shopify-Hmac-Sha256` value to the same endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` parses `shop` as `victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, B)` [9](#0-8) .
6. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [10](#0-9) , causing the host app to process attacker-controlled data under the victim shop's tenant identity.
