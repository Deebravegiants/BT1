## Title
Atomic multi-token escrow withdrawal in `IntentsBase._withdraw` permanently locks all escrowed tokens of an order if any single token transfer reverts - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw` releases every token in an order's escrow (`WithdrawalRequest.tokens`, which mirrors `order.inputs`, an array of arbitrary distinct ERC-20 addresses) in a single loop using `safeTransfer`/`_sendValue`. If any one token in that array reverts on transfer (e.g. a blacklist-capable stablecoin like USDC/USDT blacklisting the gateway or the beneficiary, or a paused/malicious token), the entire `_withdraw` call reverts, so none of the other — otherwise perfectly transferable — tokens in that same order can ever be redeemed, refunded, or cancelled.

### Finding Description
Orders can escrow multiple distinct ERC-20 tokens as `inputs` (`TokenInfo[]`), as shown by tests placing orders with both USDC and DAI inputs. All withdrawal paths — cross-chain `RedeemEscrow`/`RefundEscrow` delivered via `onAccept`, `cancelOrder`'s GET-response handler, and the same-chain fill/cancel paths — funnel into the shared `_withdraw` helper: [1](#0-0) 

The loop transfers every token in `body.tokens` unconditionally:
```solidity
for (uint256 i; i < len; i++) {
    ...
    if (token == address(0)) {
        _sendValue(beneficiary, amount);
    } else {
        IERC20(token).safeTransfer(beneficiary, amount);
    }
}
```
`safeTransfer` reverts the whole transaction if the underlying `transfer` reverts (blacklist) or returns `false`. There is no per-token try/catch, no ability to skip a stuck token, and no separate entry point to withdraw the remaining, healthy tokens individually.

For the cross-chain redeem/refund path, `ExtrinsicIntents.onAccept` calls `_withdraw(..., true)` directly on message delivery: [2](#0-1) 

`EvmHost.dispatchIncoming` treats a reverting `onAccept` as "undelivered" (deletes the receipt and lets the relayer retry later) rather than reverting the whole batch. This makes the message retryable, but if the failing token transfer is a *permanent* condition (e.g. the gateway or beneficiary address has been placed on a token's blacklist), every retry of that exact `RedeemEscrow`/`RefundEscrow` message will fail identically forever — the message can never be delivered, and the escrow (including all co-escrowed, perfectly healthy tokens of the same order) is permanently stuck in `_orders[commitment][token]`.

The same-chain cancellation path is worse: it reverts synchronously and has no retry semantics at all beyond calling the same reverting function again: [3](#0-2) 

This exactly mirrors the reported bug class: a destination vault/withdrawal routine that atomically transfers a bundle of tokens, where the failure of one token's transfer (blacklist) locks all the others.

### Impact Explanation
This causes permanent freezing of funds: once a token in a multi-token order becomes permanently untransferable to the escrow's beneficiary (blacklist, pause, malicious/rugged token contract), the entire order's escrow — including any other tokens/ETH input into that same order — becomes irrecoverable. Neither the solver (redeem), the user (refund/cancel), nor governance (there is no admin override in `_withdraw`) can extract the unaffected assets, since the withdrawal is strictly all-or-nothing per commitment.

### Likelihood Explanation
Reachable by any unprivileged user simply by constructing/placing (or having a solver fill) an order whose `inputs` include a token capable of reverting transfers to a specific address (e.g. USDC-style blacklist, a pausable token, or fee-on-transfer/malicious token that reverts under certain conditions) alongside other tokens. No special privilege is required — a normal `placeOrder`/`fillOrder`/`cancelOrder` flow through `IntentGatewayV2`/`ExtrinsicIntents`/`IntrinsicIntents` triggers the vulnerable atomic `_withdraw`.

### Recommendation
Make `_withdraw` resilient to a single token's transfer failure:
- Wrap each token transfer in a low-level call/try-catch instead of `safeTransfer`, and on failure credit the amount to a separate per-beneficiary "pending withdrawal" balance that can be claimed later (pull-payment pattern) instead of reverting the whole loop.
- Alternatively, allow `finalize`/redemption to proceed per-token, decrementing escrow and emitting an event for the token that failed, so the other tokens are still delivered atomically while the stuck token remains claimable separately once the underlying condition clears.

### Proof of Concept
1. User places an order via `IntrinsicIntents.placeOrder`/`ExtrinsicIntents.placeOrder` with `order.inputs = [TokenInfo(USDC, 1000e6), TokenInfo(DAI, 1000e18)]`.
2. The gateway address (or the order's beneficiary) becomes blacklisted on USDC (a realistic, permanent condition per the original report's scenario).
3. A solver fills the order on the destination chain and the resulting `RedeemEscrow` (or the user's `RefundEscrow`/`cancelOrder`) message is delivered to `ExtrinsicIntents.onAccept` / `IntrinsicIntents._cancelSameChain`, which calls `_withdraw` with `body.tokens = [USDC, DAI]`.
4. `IERC20(USDC).safeTransfer(beneficiary, amount)` reverts due to the blacklist; the whole `_withdraw` call reverts, so the DAI leg (perfectly transferable) is never released either.
5. Every retry of the identical message reverts identically, so both the USDC and the DAI portion of the escrow remain permanently locked in `_orders[commitment][...]` with no path to recovery.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

    }
