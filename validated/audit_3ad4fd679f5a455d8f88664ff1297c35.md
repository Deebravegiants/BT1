### Title
Zero/negative-amount withdrawal intent signed when `createWithdrawalIntents` is called with a hand-built `feeEstimation` bypassing `estimateWithdrawalFee`'s `FeeExceedsAmountError` guard - (File: packages/intents-sdk/src/sdk.ts)

### Summary
`IntentsSDK.createWithdrawalIntents` computes `actualAmount = withdrawalParams.amount - feeEstimation.amount` for fee-inclusive withdrawals but never validates that `actualAmount > 0` itself; it only calls `bridge.validateWithdrawal(...)`, and at least `AuroraEngineBridge.validateWithdrawal` performs no amount check at all. This allows a signed withdrawal intent with `amount = 0` (or negative, which would underflow as a `bigint` and throw, but `0` is directly reachable) to be produced and signed.

### Finding Description
The claimed equality: `withdrawalParams.amount (user-requested gross amount)` should always yield `actualAmount > 0` (net amount actually withdrawn) whenever a fee-inclusive withdrawal intent is signed.

Code path in [1](#0-0) :
```
const actualAmount = args.withdrawalParams.feeInclusive
    ? args.withdrawalParams.amount - args.feeEstimation.amount
    : args.withdrawalParams.amount;

await bridge.validateWithdrawal({ ..., amount: actualAmount, ... });
return bridge.createWithdrawalIntents({ withdrawalParams: { ...args.withdrawalParams, amount: actualAmount }, ... });
```
There is no `FeeExceedsAmountError` throw or any `actualAmount > 0n` assertion in `createWithdrawalIntents` itself. That check exists only inside `_estimateWithdrawalFee` (referenced by `FeeExceedsAmountError` in `packages/intents-sdk/src/classes/errors.ts` and used in `sdk.ts`'s fee-estimation path, not in `createWithdrawalIntents`). If a caller supplies its own `feeEstimation` (e.g., a stale quote, a caller-constructed object, or reuses a fee estimation object with `amount` equal to the withdrawal amount) without calling `estimateWithdrawalFee`, this guard is never invoked.

`AuroraEngineBridge.validateWithdrawal` ( [2](#0-1) ) only validates `destinationAddress` via `validateAddress`; it explicitly comments "doesn't have withdrawal restrictions" and performs no amount check. `createWithdrawIntentPrimitive` is then called with `amount: args.withdrawalParams.amount` (the already-zeroed `actualAmount`) with no further guard ( [3](#0-2) ), producing and returning an intent primitive that the caller then signs and publishes.

### Impact Explanation
A signed withdrawal intent with `amount: 0n` (or a downstream underflow for negative cases) can be constructed and published to the relayer through the normal SDK flow, without any error being surfaced to the caller. This consumes a nonce/signature for zero actual value transfer while conceptually still "spending" the fee amount reserved from `withdrawalParams.amount`. This matches the "fee error draining a material share of the amount" pattern described as Critical/High in the audit scope, since the entire withdrawal amount can be consumed as an implicit fee with zero value delivered to the destination.

### Likelihood Explanation
This requires the calling integrator (not a malicious external attacker in the traditional sense, but any unprivileged caller of the public SDK) to bypass `estimateWithdrawalFee` and hand-construct or reuse a `feeEstimation` object whose `amount` equals or exceeds `withdrawalParams.amount`, then call `createWithdrawalIntents` directly with `feeInclusive: true` and route to a bridge (Aurora Engine) whose `validateWithdrawal` doesn't check amount. This is a fully public, unprivileged, repeatable code path — `createWithdrawalIntents` and `feeEstimation` are both plain public API surfaces documented for use together, and nothing in the type system or runtime prevents calling `createWithdrawalIntents` with a `feeEstimation` obtained from a different context or replayed from an earlier quote.

### Recommendation
Add an explicit `actualAmount > 0n` check inside `createWithdrawalIntents` in `sdk.ts` immediately after computing `actualAmount`, throwing `FeeExceedsAmountError` (reusing the existing error class) before calling `bridge.validateWithdrawal` or `bridge.createWithdrawalIntents`. Additionally, add a defense-in-depth `amount > 0n` check inside each bridge's `validateWithdrawal`, including `AuroraEngineBridge.validateWithdrawal`.

### Proof of Concept
```ts
// packages/intents-sdk/src/sdk.zero-amount.test.ts (vitest, mocks HTTP only)
it("throws instead of signing a zero-amount withdrawal intent", async () => {
  const withdrawalParams = {
    amount: 1000n,
    feeInclusive: true,
    assetId: "<virtual-chain nep141 asset>",
    destinationAddress: "0xValidEthAddress",
    routeConfig: { route: RouteEnum.VirtualChain, auroraEngineContractId: "aurora", proxyTokenContractId: "token.near" },
  };
  const feeEstimation = { amount: 1000n, quote: undefined /* mocked */, underlyingFees: [] };

  // Before: withdrawalParams.amount (1000n) === feeEstimation.amount (1000n)
  // actualAmount = 1000n - 1000n = 0n

  await expect(
    sdk.createWithdrawalIntents({ withdrawalParams, feeEstimation }),
  ).rejects.toThrow(FeeExceedsAmountError);

  // After fix: no intent is produced/signed with amount 0n.
});
```
