### Title
Unbacked Reputation minting via free `handle_unsigned` relaying decoupled from actual weight/fee paid — enables cheap farming of collator-selection reputation - (File: modules/pallets/messaging-incentives/src/lib.rs)

### Summary
`pallet-messaging-incentives::message_bytes()` mints a reputation asset to relayers strictly proportional to the byte-length of the `PostRequest.body` fields in a delivered `Message::Request`, with a 32-byte floor per request [1](#0-0) . This reward is granted on `pallet-ismp`'s `on_executed` FeeHandler hook after `handle_unsigned` executes a message batch [2](#0-1) . Crucially, `handle_unsigned` is an **unsigned, free-to-submit** extrinsic — pallet-ismp's own documentation states "This allows users execute ISMP datagrams for free. Use with caution" and that cross-chain messages are "executed for free as unsigned transactions" [3](#0-2) [4](#0-3) . This exactly mirrors the reported EVM bug: gas (real cost) charged is decoupled from the price used to compute a reward/activity metric, letting a party receive far more "activity points" (here: Reputation Asset, which is a direct input into collator selection and eventually `$BRIDGE` block rewards) than the real resource cost incurred on the rewarding chain.

### Finding Description
1. `handle_unsigned` accepts any batch of ISMP `Message`s with a valid state/consensus proof and executes them as a **fee-free unsigned transaction** [5](#0-4) .
2. After successful execution, `Pallet::execute` invokes `T::FeeHandler::on_executed(messages_with_weights, events)` [6](#0-5) .
3. `pallet-messaging-incentives::on_executed` mints `bytes * MintPerByte` reputation to the relayer recovered from the message's `signer` field, where `bytes` is purely `Σ max(request.body.len(), 32)` over all requests packed into the message [7](#0-6) .
4. There is no linkage between the minted amount and the **actual weight/computational cost** consumed to process the message (`mw.weight`, returned by `handle_incoming_message`/`MessageResult::weight()` [8](#0-7) ) — that weight field is available on `MessageWithWeight` but is never consulted by `message_bytes()`.
5. Because `handle_unsigned` costs the submitter nothing on Hyperbridge (no transaction fee, since it's unsigned and free), and the message body originates from a `PostRequest` dispatched on any connected source chain, an attacker who controls both ends (dispatches a request on a cheap/low-fee source chain with an artificially large `body`, then self-relays it to Hyperbridge with a valid proof) can mint Reputation proportional to body size at negligible marginal cost on Hyperbridge itself.
6. The docstring on `message_bytes` shows the authors were aware of one specific gaming vector (splitting into many small requests to repeatedly hit the 32-byte floor) and mitigated it by applying the floor per-request instead of per-envelope [9](#0-8) . However, this mitigation does not address the inverse and larger-impact vector: padding a small number of requests with large bodies, since neither the mint formula nor the free `handle_unsigned` path constrains body size relative to actual execution cost.
7. Reputation Asset is not a cosmetic score — it directly determines collator selection each session (`pallet-collator-manager` ranks candidates by Reputation Asset balance) and collators are paid `0.7 $BRIDGE` per block plus a share of ~4,000,000 $BRIDGE/year [10](#0-9) [11](#0-10) . So the "unbacked mint" here converts into real value (block-production rewards) exactly as the original report describes "receiving more activity points than he spent gas."

### Impact Explanation
This is analogous to the original Critical-severity finding: a pricing/metering mismatch between the actual cost incurred and the reward computed lets an attacker earn disproportionate "activity points." Here, Reputation Asset directly gates who becomes a Hyperbridge collator (block producer) and therefore who earns real `$BRIDGE` treasury rewards. An attacker who can cheaply mint large amounts of unbacked reputation can displace honest, resource-contributing relayers/provers from the collator set, capturing block-production rewards without performing commensurate real work, and can do so repeatedly every session since reputation resets and re-accrues. This is a governance/economic-integrity issue affecting collator selection (a reachable, permissionless message-relaying path), which the scope explicitly includes ("relayer fee and reward accounting").

### Likelihood Explanation
The relaying and dispatch paths involved (`IsmpDispatcher` on any connected chain, `pallet_ismp::handle_unsigned`) are fully permissionless — any account can dispatch a `PostRequest` with an arbitrary body and any account can submit the corresponding relay message. `handle_unsigned` is unsigned and executed "for free," removing the natural economic disincentive (transaction fees) that would otherwise scale with message/body size. The only requirement is a valid consensus/state proof for a real dispatched request, which is achievable by the attacker acting as their own source-chain dispatcher and destination-chain relayer. No governance or privileged role is needed.

### Recommendation
- Base the Reputation Asset mint on the actual `weight` consumed to process the message (already available via `MessageWithWeight.weight`), not on raw `body.len()`, or apply a governance-set cap on the eligible bytes-per-message / bytes-per-session that can be rewarded.
- Introduce a maximum reward-eligible body size, and/or scale the per-byte rate down as body size grows, so the reward tracks realistic marginal processing cost rather than attacker-controlled payload padding.
- Consider requiring `handle_unsigned` batches used for incentive accounting to also account for real resource consumption (proof verification cost, storage writes) rather than purely `Message::Request` body length.
- Add monitoring/alerting on abnormal reputation-mint concentration ahead of session boundaries to detect this pattern before it affects collator selection, as an interim mitigation.

### Proof of Concept
1. On any connected low-fee source chain, an attacker-controlled contract/account calls the ISMP dispatcher to send a `PostRequest` to Hyperbridge with a body padded to, e.g., 100 KB of arbitrary bytes (cost is only whatever the source chain charges for calldata/storage, independent of Hyperbridge's fee model).
2. The attacker (as relayer) submits this request, with a valid state proof from the source chain, via Hyperbridge's `pallet_ismp::handle_unsigned` extrinsic — this is unsigned and executed for free, so no proportional fee is charged on Hyperbridge for the message size [5](#0-4) .
3. On successful execution, `pallet-messaging-incentives::on_executed` computes `bytes = max(100_000, 32) = 100_000` and mints `100_000 * MintPerByte` Reputation Asset to the attacker's signer account [12](#0-11) .
4. Repeating this process across many self-dispatched/self-relayed large-body requests lets the attacker accumulate Reputation Asset far exceeding what honest relayers/provers earn per unit of real cost incurred, at session boundary this inflated balance can win the attacker a collator slot in `pallet-collator-manager::new_session` [13](#0-12) , granting real `$BRIDGE` block-production rewards.

Note: I could not verify the exact `weight()` computation used in the `#[pallet::weight(weight())]` annotation on `handle_unsigned` (i.e., whether any weight/fee is charged that scales with message size) due to index/search limitations; a Devin session with full repository access would be needed to confirm the precise weight formula and any existing indirect cost that might partially offset this issue.

	/// Same minimum-byte rule as the bandwidth gate (`max(body, 32)`),
	/// applied **per request** so packing requests into one envelope
	/// vs. splitting them across many produces identical mints.
	/// Applying the floor once per envelope would let a relayer inflate
	/// the mint by splitting (each split picks up its own 32-byte floor).
	fn message_bytes(message: &Message) -> u32 {
		match message {
			Message::Request(req) => req
				.requests
				.iter()
				.map(|p| core::cmp::max(p.body.len() as u32, 32))
				.sum::<u32>(),
			_ => 0,
		}
	}

	/// Recover the relayer's account from the sr25519 signature on a
	/// `Message`'s `signer` field. Returns `None` if the message has
	/// no signer (e.g. consensus messages) or the signature is bad.
	fn relayer_for(message: &Message) -> Option<T::AccountId> {
		let (signer, signed) = match message {
			Message::Request(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			Message::Response(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			_ => return None,
		};
		Signature::decode(&mut &signer[..])
			.ok()?
			.verify_and_get_sr25519_pubkey(&signed, None)
			.ok()
			.map(T::AccountId::from)
	}
}

impl<T: Config> FeeHandler for Pallet<T>
where
	T::AccountId: From<[u8; 32]>,
{
	fn on_executed(
		messages: Vec<MessageWithWeight>,
		_events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let rate = MintPerByte::<T>::get();
		if !rate.is_zero() {
			for mw in &messages {
				let bytes = Self::message_bytes(&mw.message);
				let bytes_balance: BalanceOf<T> = (bytes as u128).saturated_into();
				let amount = rate.saturating_mul(bytes_balance);
				if amount.is_zero() {
					continue;
				}
				if let Some(relayer) = Self::relayer_for(&mw.message) {
					match T::ReputationAsset::mint_into(&relayer, amount) {
						Ok(_) =>
							Self::deposit_event(Event::ReputationMinted { relayer, bytes, amount }),
						Err(err) => log::warn!(
							target: "messaging-incentives",
							"reputation mint failed for {bytes}b: {err:?}",
						),
					}
				}
			}
		}
		Ok(PostDispatchInfo { actual_weight: None, pays_fee: Pays::No })
	}
}

impl<T: Config> Pallet<T> {
	/// Execute the provided ISMP datagrams, this will short circuit if any messages are invalid.
	/// This also charges fee on valid message delivery
	pub fn execute(messages: Vec<Message>) -> Result<Vec<events::Event>, Error<T>> {
		let host = Pallet::<T>::default();

		let message_results = messages
			.iter()
			.map(|msg| handle_incoming_message(&host, msg.clone()))
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		let messages_with_weights = message_results
			.iter()
			.zip(messages)
			.map(|(result, message)| MessageWithWeight { message, weight: result.weight() })
			.collect::<Vec<_>>();

		let events = message_results
			.into_iter()
			// check that requests will be successfully dispatched
			// so we can not be spammed with failing txs
			.map(|result| match result {
				MessageResult::Request { events, .. } |
				MessageResult::Response { events, .. } |
				MessageResult::Timeout { events, .. } => events,
				MessageResult::ConsensusMessage(events) => events.into_iter().map(Ok).collect(),
				MessageResult::FrozenClient(_) => vec![],
			})
			.flatten()
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		T::FeeHandler::on_executed(messages_with_weights, events.clone())
			.map_err(|_| Error::<T>::ErrorChargingFee)?;

		for event in events.clone() {
			// deposit any relevant events
			Pallet::<T>::deposit_event(event.into());
		}

		Ok(events)
	}

## Transaction fees

Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free as unsigned transactions. The upside to this is that it cannot be exploited as a spam vector, since the transaction pool will check if the submitted extrinsics are valid before they are included in the pool. This validity check ensures that the transaction can be successfully executed and contains valid proofs. Malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing and potential network congestion.
