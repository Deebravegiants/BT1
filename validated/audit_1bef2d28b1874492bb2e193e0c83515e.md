### Title
Webhook Shop Domain Not Bound to HMAC Signature Enables Cross-Tenant Data Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw request body only, while the `shop` (and other identifying headers) used by the library and forwarded to the app's webhook handler are read from unauthenticated HTTP headers that are never covered by the HMAC signature. A party that can obtain one genuine, validly-signed webhook delivery (e.g., an app-installing merchant receiving webhooks for their own shop) can replay the identical signed body to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header, and `Registry.process` will accept it as valid and dispatch it to the handler tagged with the attacker-chosen shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely outside of what gets HMAC'd: [2](#0-1) 

`HmacValidator.validate` only checks that the `hmac` field matches a signature computed over `to_signable_string` (i.e., the raw body), using `Context.api_secret_key`: [3](#0-2) 

`Registry.process` validates the HMAC and then trusts `request.shop` (from the unauthenticated header) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

This is exactly the "field acted on but not covered by the HMAC" identity-binding break: the equality the library implicitly assumes is `shop(header) == shop(HMAC-verified-source)`, but only the raw body is bound to the signature — the shop header is not. Any actor who can capture one authentic, validly-signed webhook body (trivially available to any merchant that installs the app, since all webhooks for an app share the same `client_secret`/HMAC key) can resend that exact body to the app's webhook endpoint with a different `shopify-shop-domain` header value. `HmacValidator.validate` will still return `true` because it only checks the body against the shared secret, and `Registry.process` will hand the handler a `WebhookMetadata` claiming an arbitrary `shop` while the body content is real.

### Impact Explanation
Any host application that uses `data.shop` from the processed webhook to select which merchant's tenant record to update (a standard pattern) can be tricked into attributing another shop's webhook payload to an attacker-chosen shop identifier, since nothing in the verified signature binds `shop` to the payload. This is a cross-tenant data-integrity issue reachable purely from the gem's documented API (`Webhooks::Registry.process`) — an unprivileged party needs only its own legitimate webhook (already something any installing merchant receives) and no access to `api_secret_key`, no privileged account beyond being one of the app's own installed merchants, and no TLS interception.

### Likelihood Explanation
Any merchant who installs the app already receives real, validly HMAC-signed webhook deliveries for their own shop. Capturing and replaying that request body with a modified shop header is trivial and requires no cryptographic material beyond what the attacker already legitimately possesses. Rate-limiting/timestamp replay protections are explicitly out of scope per the rules, so the core binding gap stands regardless of those mitigations.

### Recommendation
Include `shop` (and ideally `topic`, `webhook_id`, `api_version`) inside the value that is HMAC-verified, or otherwise cryptographically bind the shop domain to the signed payload (e.g., verify the header value against the shop encoded in the payload/dest of a related session/JWT, or require the host app to independently confirm `shop` against a known shop record before trusting it) rather than trusting the header for tenant attribution.

### Proof of Concept
1. As an installed merchant "shop-a.myshopify.com", capture a real, Shopify-delivered webhook HTTP request (raw body `B`, header `x-shopify-hmac-sha256: H`, where `H` is a valid HMAC of `B` under the app's shared `client_secret`).
2. Resend the same request to the app's webhook endpoint, keeping `raw_body = B` and `x-shopify-hmac-sha256 = H` unchanged, but set `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: headers)` parses successfully; `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes the HMAC over `B`, per [5](#0-4) .
4. `Registry.process(request)` invokes the registered handler with `WebhookMetadata.new(... shop: "shop-b.myshopify.com" ...)`, even though the payload actually originated from Shopify for `shop-a.myshopify.com`, per [6](#0-5) .
