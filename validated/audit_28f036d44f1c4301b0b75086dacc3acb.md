### Title
Backward-compatibility default in `ConnectedOrigins.isTrusted()` silently treats unspecified trust state as trusted, mirroring the Blocklist/Whitelist interface inconsistency - ([File: features/connected-origins/module/connections.js])

### Summary
The external report flags an inconsistency where `VaultWhitelist`/`VaultBlocklist` handle membership checks and mutation differently, causing implicit-trust confusion. Hydra's `@exodus/connected-origins` module — which gates dApp/site access to wallet accounts and addresses — has the same class of issue: `isTrusted()` treats a stored connection with an *unset* `trusted` field as trusted "for backward compatibility," while every other write path (`add`, `untrust`) treats trust as an explicit boolean. This creates an implicit-allow default analogous to the whitelist/blocklist ambiguity called out in the report.

### Finding Description
`ConnectedOrigins#isTrusted` in [1](#0-0)  returns `true` whenever a stored origin record exists and `value.trusted === undefined`:

```js
isTrusted = async ({ origin }) => {
  const value = await this.#getOrigin({ origin })
  if (!value) return false
  // backward compatibility
  return value.trusted === undefined || value.trusted
}
```

This is the single authorization gate consumed both directly via the public API (`connectedOrigins.isTrusted`, exposed in [2](#0-1) ) and internally by `getConnectedAccounts`, which exposes the user's wallet-account addresses for the origin: [3](#0-2) .

Compare this with `add()`, which explicitly threads through a `trusted` value with no defaulting logic of its own ( [4](#0-3) ), and `untrust()`, which relies on `isTrusted()` to decide whether removal should proceed ( [5](#0-4) ). Any code path that calls `add({ origin, ... })` without passing `trusted` (e.g., a caller that only wants to record metadata, not grant access) results in a record that `isTrusted()` treats as trusted by default, unlike the Redux `trusted` selector which uses the same `?? true` default ( [6](#0-5) ) — so at least the two "trusted" computations agree with each other, but both diverge from the intuitive semantics of an explicit allow-list, exactly the kind of interface inconsistency the report calls out (implicit vs. explicit membership, and undocumented default-allow behavior).

### Impact Explanation
If any caller of `ConnectedOrigins#add` (current or future feature code, e.g. new dApp/provider integrations) omits the `trusted` flag — perhaps assuming untrusted-by-default given the field is optional — the origin becomes immediately trusted and `getConnectedAccounts` will hand back wallet addresses to that origin without any explicit user approval step. This is a cross-origin/account privilege bleed: an origin that should require explicit user consent gains account address disclosure through an implicit default. The risk is entirely dependent on call sites that construct records without `trusted` set, which I could not fully enumerate — no production (non-test) call site of `connectedOrigins.add` was found in the indexed portion of the codebase, only test fixtures.

### Likelihood Explanation
Likelihood is moderate-to-low as verified in the available index: all located calls to `.add()` are in test files (`features/connected-origins/module/__tests__/connections.test.js`, `sdks/headless/__tests__/connected-origins.test.js`), and I was unable to locate the actual production caller(s) (e.g., inside a web3-provider plugin) that construct connection records when a site is first encountered. Given index size limits, some file contents (likely including the web3Browser/provider plugin code that calls `connectedOrigins.add`) may not be available to this search — a full-repo review via a Devin session would be needed to confirm whether any production call path omits `trusted`.

### Recommendation
- Remove the "backward compatibility" implicit-trust default from `isTrusted()`; require `trusted` to be explicitly `true` to grant access, matching a deny-by-default posture consistent with account-address disclosure being a sensitive operation.
- Perform a one-time migration to normalize any persisted records lacking a `trusted` field to `trusted: false` (or `true`, if verified safe) instead of relying on runtime `undefined` coercion.
- Audit every call site of `ConnectedOrigins#add` to ensure `trusted` is always passed explicitly, and consider making the parameter required (not defaulted) in the constructor/type signature.
- Align `isTrusted()`, the Redux `trusted` selector, and any UI/provider code that gates address exposure to use one shared, unambiguous helper rather than duplicating the `?? true` / `=== undefined` logic in multiple places — directly addressing the report's core recommendation of using a single consistent interface instead of scattered, differently-defaulted checks.

### Proof of Concept
Not independently exploitable purely from the module in isolation without a concrete production call site that omits `trusted`; however, the following unit-test-style sequence demonstrates the vulnerable default within the module itself (as already exercised by the existing test suite):

```js
// Directly setting a connection record without `trusted`
await connectedOriginsAtom.set([{ origin: 'malicious.example' }])

// isTrusted() returns true despite no explicit trust grant
const trusted = await connectedOrigins.isTrusted({ origin: 'malicious.example' }) // => true

// getConnectedAccounts then discloses wallet addresses for this "trusted" origin
const accounts = await connectedOrigins.getConnectedAccounts({ origin: 'malicious.example' })
// => returns account addresses, even though no explicit approval ever set trusted: true
```
This matches the existing test at [7](#0-6) , which explicitly asserts this implicit-trust behavior as intended — confirming the code path exists and behaves as described, though the real-world reachability depends on an unverified production caller that must be located via full source access.
