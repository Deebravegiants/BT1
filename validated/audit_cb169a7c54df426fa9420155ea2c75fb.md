### Title
Division-by-zero DoS in `Zap._executeBuy`'s pro-rata fee calculation when `ltMinted` rounds to zero - ([File: packages/contracts/src/Zap.sol])

### Summary
`Zap._executeBuy` divides by `ltMinted` — the amount of LT returned by `IBounceLeveragedToken.mint()` — to compute the pro-rata fee owed on the actually-consumed curve trade. If `ltMinted` is ever `0`, this line panics with a division-by-zero, exactly the CWE-369 class described in the vproxy advisory (untrusted/externally-influenced value flows into a denominator with no zero-check).

### Finding Description
In `_executeBuy`: [1](#0-0) 
```
$.usdc.forceApprove(lt, baseToConvert);
ltMinted = IBounceLeveragedToken(lt).mint(address(this), baseToConvert, 0);
(tokensOut, amountInUsed) = _buyOnCurve(tokenAddress, lt, ltMinted);
...
uint256 effectiveBaseSpent = (amountInUsed * baseToConvert) / ltMinted;
```
`ltMinted` is `baseToLtAmount(baseToConvert)` on the external BounceTech LT — `(baseAmount * 1e18) / exchangeRate` per `IBounceLeveragedToken.baseToLtAmount` and the reference mock implementation.

The only guard on `baseToConvert` is `minUsdcAmount()`, which reads BounceTech's `minTransactionSize()` — a fixed USDC floor that is **not** re-derived from `exchangeRate()`. As `exchangeRate()` for an actively-traded long leveraged token rises over time (this is explicitly the intended, unbounded behavior per the code's own comments about drift and appreciation), the LT amount minted for a fixed USDC floor shrinks. Once `exchangeRate()` grows large enough relative to `minTransactionSize()`, `baseToLtAmount(minTransactionSize())` truncates to `0`. BounceTech's own `mint()` floor check is denominated in USDC, not LT, so it does not prevent `ltMinted == 0` from being returned — it will happily mint `0` LT for a small-but-floor-passing USDC input at a sufficiently appreciated rate.

Once `ltMinted == 0`, the pro-rata fee division at line 386 panics (`Panic(0x12)` divide/modulo by zero), reverting every subsequent buy attempt against that token/LT pair through `Zap.buy`/`buyWithPermit` — for both the curve path and the post-graduation HyperSwap path, since the same division occurs before the `isGraduated` branch check in the code layout.

This mirrors the vproxy bug class precisely: an externally-derived numeric input (there, a TTL parsed from an untrusted header; here, an LT mint amount derived from an externally-controlled, monotonically drifting `exchangeRate()`) is used unguarded as a divisor.

### Impact Explanation
Once the condition is hit, `Zap.buy` / `buyWithPermit` permanently reverts for that token — no unprivileged trader can buy through Zap on that curve or graduated pair again (sells still work via `redeem`, similar to the BounceTech mint-pause tradeoff already accepted elsewhere in the code, but buys are fully bricked). This is a permanent freezing of trading functionality for the affected token, satisfying the "permanent freezing of trader/creator funds" bar via loss of the buy-side market, though it does not directly steal funds.

### Likelihood Explanation
This requires `exchangeRate()` to drift far enough relative to the fixed `minTransactionSize()` floor that `baseToLtAmount(minTransactionSize())` rounds to zero — a condition dependent on the external LT's long-run price appreciation rather than a single attacker-controlled parameter in one transaction. I could not verify the real BounceTech `minTransactionSize()`/`exchangeRate()` magnitudes or scaling relationship in-repo (the LT itself is out of scope and only mocked in tests), so I cannot confirm how close to this threshold a realistic, actively-traded leveraged token would get in practice. This uncertainty means the likelihood should be treated as **speculative/low-to-medium** rather than confidently high, and I flag it explicitly as unverified.

### Recommendation
Guard the divisor before use, e.g.:
```solidity
if (ltMinted == 0) revert ZeroAmount();
```
immediately after the `mint()` call, before it is used both as a divisor and downstream in `_buyOnCurve`/`_buyOnUniswapV2`. Alternatively, use `Math.mulDiv` variants that revert cleanly (they already do, but with the same underlying zero-denominator panic, so the fix must be an explicit pre-check) or use `ltMinted == 0 ? 0 : (...)` with an explicit revert instead of silently returning `0` for `effectiveBaseSpent`, since `0` would misreport `amountInUsed` accounting elsewhere.

### Proof of Concept
Not executable — this requires driving `exchangeRate()` on a live/mocked LT to a value where `baseToLtAmount(minUsdcAmount())` truncates to `0` and then calling `Zap.buy` with `usdcAmount` at/near the floor. This can be demonstrated in the existing Foundry test harness using `MockLeveragedToken.setExchangeRate()` set to an extreme value (e.g., far larger than `minUsdcAmount() * 1e18`), then calling `zap.buy(tokenAddr, minUsdcAmount()+buyFeeMargin, 0, address(0))` and observing a `Panic(0x12)` revert instead of a normal `BelowMinAmount`/success outcome. I was not able to run this in the current session to confirm the exact numeric threshold against production `minTransactionSize()`/`exchangeRate()` values from the real BounceTech contracts, since those live outside `packages/contracts/src`.

        if (ltExcess > 0) {
            IERC20(lt).safeTransfer(msg.sender, ltExcess);

        // Pro-rate fees against the LT actually consumed by the curve.
        // For non-cap and dust-cap buys `amountInUsed ≈ ltMinted` so
        // `effectiveBaseSpent ≈ baseToConvert` and behaviour matches the
        // pre-floor-bump formula. The floor-bump branch overshoots the
        // mint past what the curve consumes; charging fee on the minted
        // size (rather than the consumed slice) would over-charge users
        // who hit this dust band.
