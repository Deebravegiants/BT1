### Title
Webhook shop identity spoofing via header not covered by HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates only the raw request body via HMAC, but the `shop` identity that the gem exposes to the host application's webhook handler is read from an HTTP header that is never included in the signed payload.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` computes/compares the HMAC exclusively against that signable string [2](#0-1) . The `shop`, `topic`, `api_version`, and `webhook_id` values, however, are all parsed straight out of unauthenticated HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) with no cryptographic binding to the signed body [3](#0-2) .

This breaks the identity binding: `HMAC(body) == HMAC(body, secret)` is verified, but the equality that actually matters for tenant isolation — `shop_header == shop_that_produced_this_body` — is never checked. An entity that legitimately receives one authentic (shop, body, HMAC) tuple from Shopify for their own store can swap the `shopify-shop-domain` header (and/or topic/webhook-id headers) to any other value while keeping the original body and valid HMAC untouched. `HmacValidator.validate` will still return `true` because it only ever looks at `@raw_body`, never at the headers [4](#0-3) . The forged request then reaches `Registry.process`, which dispatches to the registered handler using `webhook_request.shop`/`topic` as trusted values, so the app processes attacker-supplied identity metadata as if it came from the header's claimed shop, while the (validated) body content actually originates from the attacker's own store.

### Impact Explanation
Any host application that keys per-tenant business logic off `Webhooks::Request#shop` (e.g. selecting which merchant's session/API credentials to use, or writing/updating records scoped to `shop`) can be tricked into associating attacker-controlled body content with an arbitrary victim shop domain, because the shop-domain claim carries no cryptographic assurance despite the request otherwise passing HMAC validation. This is a cross-tenant boundary violation reachable by any actor who can trigger one legitimate webhook delivery to their own installed app (i.e., any merchant who installs the app) and can then replay it with modified headers directly against the app's webhook endpoint.

### Likelihood Explanation
Exploitation requires the attacker to operate their own shop with the app installed (to obtain one real signed webhook body+HMAC), and requires the host application to trust `Request#shop` for tenant-sensitive decisions rather than independently verifying it against the actual session/store the request is processed under. No secret material is needed to perform the header swap since headers sit entirely outside the signed data.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the HMAC-signed material, or otherwise cryptographically bind them to the body (e.g., signing `"#{shop}\n#{raw_body}"`), and update `Utils::HmacValidator`/`Request#to_signable_string` accordingly. At minimum, document that `Request#shop` must never be trusted independently and that host apps should re-validate the shop against the resolved session for the webhook subscription.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets Shopify deliver a legitimate webhook, capturing the raw body `B` and header `shopify-hmac-sha256: H` (valid for `B` with the app's secret) along with `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends an HTTP request to the app's webhook endpoint with the identical body `B` and identical `shopify-hmac-sha256: H` header, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully (all required headers present) [5](#0-4) .
4. `Registry.process` calls `Utils::HmacValidator.validate(webhook_request)`, which recomputes HMAC over `@raw_body` only and matches `H`, returning `true` [4](#0-3) .
5. The registered handler is invoked with `webhook_request.shop == "victim-shop.myshopify.com"`, even though the body content and signature actually originated from `attacker-shop.myshopify.com`.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
