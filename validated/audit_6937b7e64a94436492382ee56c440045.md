### Title
Webhook `shop-domain` (tenant identity) header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing via replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature it validates against covers only the raw request body. This breaks the intended binding of `hmac == HMAC(shop, topic, body, ...)`; in reality `hmac == HMAC(body)` only, so `shop` can be swapped without invalidating the signature.

### Finding Description
`Request#hmac` reads the signature from the `hmac-sha256` header, and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from the `shop-domain` header without any cryptographic binding to the signed payload: [2](#0-1) 

Verification is performed through `Utils::HmacValidator.validate`, which calls `validate_signature`, comparing `computed_signature = HMAC(to_signable_string, secret)` against the received `hmac`: [3](#0-2) 

Because `to_signable_string` only serializes `@raw_body` and not `shop`, `topic`, or `webhook_id`, the equality the code actually checks is:

`hmac == HMAC(secret, raw_body)`

but a caller consuming this class implicitly assumes the stronger binding:

`hmac == HMAC(secret, raw_body) AND shop == originating_tenant`

These are not equivalent. Any request with a raw body/HMAC pair that was legitimately generated by Shopify for one shop remains valid if the `shop-domain` header is changed to a different value, since the header is never part of the signed content. This is directly analogous to the reported bug class: a value ("last order price" / here, "shop-domain") is used to drive a security-relevant decision (auto-roll price / here, tenant attribution) while only a weaker, unverified signal underlies it, and the value that actually carries security guarantees (block/observation window price / here, the HMAC-signed body) does not cover the field being trusted.

### Impact Explanation
If a host application uses `Request#shop` (or `#topic`, `#webhook_id`) as the authoritative tenant/routing identifier after calling `HmacValidator.validate` — which is the exact intended usage pattern per this gem's own docs (`shop-domain`/`topic` headers plus HMAC-validated body) — an attacker who can obtain one valid `(body, hmac)` pair (e.g., from a webhook fired to their own shop, which they legitimately control) can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value. The signature still validates because the header isn't covered. This is a cross-tenant identity confusion: data or actions intended to be scoped to the attacker's own shop get attributed to a victim shop's tenant context in the consuming application, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Reaching this requires only sending HTTP requests to the app's webhook endpoint (no credentials, no access token, no `client_secret`, no privileged account). The attacker's own Shopify store is sufficient to obtain a legitimately-signed `(body, hmac)` pair, since HMAC uses the merchant-independent `client_secret`/`api_secret_key` of the app, shared across all shops installing that app. This matches the "unprivileged internet user" threat model.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string used for HMAC verification (or otherwise cryptographically bind them, e.g., via a MAC over a canonical concatenation of header values + body), so that `to_signable_string` reflects everything the caller relies on for tenant/topic attribution — not just `@raw_body`. Alternatively, explicitly document that `shop`/`topic`/`webhook_id` are unauthenticated fields and that host applications must independently verify `shop` against their own known/installed-shop list before treating the webhook as trusted for that tenant, rather than only relying on `HmacValidator.validate`.

### Proof of Concept
1. Attacker installs the target app on their own store, `attacker-shop.myshopify.com`, and legitimately receives a webhook (e.g., `orders/create`) with a valid `X-Shopify-Hmac-Sha256` header computed over the raw body using the app's shared `client_secret`.
2. Attacker captures the raw body and the `hmac-sha256` header value from this legitimate webhook delivery.
3. Attacker replays the exact same raw body and `hmac-sha256` header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and any desired `X-Shopify-Topic`/`X-Shopify-Webhook-Id`.
4. The app calls `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` then `HmacValidator.validate(request)`; since `to_signable_string` returns only `raw_body` [4](#0-3) , validation succeeds despite the forged `shop` value, and any host logic keyed on `request.shop` processes the payload as belonging to `victim-shop.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
