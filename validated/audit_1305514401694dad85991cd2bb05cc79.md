### Title
Webhook Shop/Topic/Metadata Headers Are Not Covered by the HMAC Signature, Enabling Cross-Tenant Webhook Forgery - ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/webhooks/registry.rb], [File: lib/shopify_api/utils/hmac_validator.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then dispatches the handler using the `shop`, `topic`, `webhook_id`, and `api_version` values taken from unauthenticated HTTP headers. Because the shared `client_secret` for an app is the same across every shop that has the app installed, any merchant (an unprivileged actor from the app's perspective) who installs the app on their own store can capture a genuinely-signed webhook body Shopify sends them, then replay that same body/HMAC pair to the app's webhook endpoint while forging the `shop-domain` header to name a different, victim shop. The library will accept it as valid and hand the attacker-chosen shop identity to the host application's handler.

### Finding Description
`HmacValidator.validate` computes and compares the signature only over `verifiable_query.to_signable_string`, and for webhooks that is defined to be just the raw body: [1](#0-0) [1](#0-0) 

```
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
```

The `shop`, `topic`, `webhook_id`, and `api_version` accessors read straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` verifies the HMAC over the body, then immediately trusts the unauthenticated `shop` header to build the `WebhookMetadata` passed to the app's handler — the tenant identity acted upon is not the tenant identity verified: [3](#0-2) 

The equality the system implicitly relies on is:
`bytes_verified_by_HMAC (raw_body only)` == `bytes_that_determine_the_tenant (shop header, unauthenticated)`

This equality does not hold. Since the `client_secret` (and thus the HMAC key) is shared by the app across all shops that install it, any merchant who installs the app on a shop they control can obtain a validly-signed webhook body for their own store (e.g., via `orders/create` or any subscribed topic), then POST that identical body + HMAC to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to the victim shop's domain. `Registry.process` will accept it (HMAC over the body still matches) and call the registered handler with `shop: "victim-shop.myshopify.com"`, `topic` and `webhook_id` also attacker-controlled and unauthenticated.

### Impact Explanation
This crosses a tenant boundary: an attacker who is a legitimate, low-privilege user of the app (merely installing the app on any shop) can forge webhook events that the host application will process as if they originated from a different shop's Shopify instance. Depending on how the host app uses the `shop`/`topic` fields (e.g., triggering data sync, uninstall cleanup, order fulfillment logic, GDPR erasure, billing state changes) this enables cross-tenant data confusion/corruption attributable to a shop the attacker does not control — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation only requires the attacker to install the app on any shop they control (a normal, unprivileged action) and to be able to send arbitrary HTTP requests to the app's public webhook endpoint — no access token, `client_secret`, or other privileged credential of the victim is required. The attacker never needs to know the app's actual secret; they only need one Shopify-signed body/HMAC pair for their own shop, which Shopify sends them automatically once they subscribe to any webhook topic.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the HMAC-signable string, or otherwise cryptographically bind them (e.g., verify that `request.shop` corresponds to a shop for which the app holds an active session/installation before dispatching), so that `Utils::HmacValidator.validate` can no longer be satisfied for a body whose associated shop/topic have been altered. At minimum, `Registry.process` should document/require that host applications independently verify `request.shop` against known-installed shops rather than trusting it implicitly once HMAC passes.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (normal onboarding, no privileged access needed).
2. Shopify sends a legitimately HMAC-signed webhook (e.g., `orders/create`) to the attacker's registered endpoint, with `X-Shopify-Hmac-Sha256` computed over the raw JSON body using the app's shared `client_secret`.
3. Attacker captures this raw body and HMAC value.
4. Attacker POSTs the identical body and HMAC to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Webhook-Id`/topic already registered by the app).
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the (unmodified) body against the (unmodified) HMAC — see `HmacValidator.validate_signature` in `lib/shopify_api/utils/hmac_validator.rb:26-31`.
6. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, even though the request has nothing to do with that shop, demonstrating the break in the shop-identity binding.
