### Title
Nested route code can attach an unrelated wallet-token transfer to a caller-signed strategy authorization - (File: `contracts/controller/src/strategies/swap.rs`)

### Summary
A malicious swap route can execute a venue-selected contract that requests additional authorization from the strategy caller, causing simulation to attach an unrelated token transfer beneath the caller's signed controller invocation. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_collateral` authenticates the caller and account owner, withdraws the selected collateral, then forwards the caller-controlled opaque `swap` bytes into the router. [3](#0-2) [4](#0-3) 

The shared swap boundary authorizes only the controller's exact input-token transfer to the router, but it does not constrain contracts invoked below the router from requesting the original caller's authorization. [1](#0-0) 

A route instruction selects its pool address from the route's address registry and dispatches it as a venue hop, so route data can place attacker-deployed contract code inside the authorized transaction. [5](#0-4) [6](#0-5) 

The harness demonstrates that such a contract can call `token.transfer(victim, attacker, amount)`, that honest simulation records this as a child of the victim's `swap_collateral` authorization, and that signing the resulting tree moves the victim's unrelated wallet token while the strategy still succeeds. [7](#0-6) [2](#0-1) 

### Impact Explanation
This is theft of user funds because the nested call can move arbitrary caller-held tokens unrelated to the strategy's declared input, output, `amount`, collateral positions, or protocol risk checks. [8](#0-7) 

The controller's post-swap checks only bound controller input spending and require positive output; they do not inspect or bound unrelated caller-token transfers performed by route-selected code. [9](#0-8) 

### Likelihood Explanation
The attack needs no protocol privilege, leaked key, or governance action: the attacker deploys a route-invoked contract and supplies a malicious route to a victim who signs the simulated authorization tree. [10](#0-9) [11](#0-10) 

The likelihood is moderated because enforcing-mode execution rejects the theft when the victim signs only the honest root invocation without the unexpected child. [12](#0-11) 

### Recommendation
Governance should bind swap routes to approved venue and pool identities rather than allowing route bytes to introduce arbitrary executable pool contracts. [5](#0-4) 

Until that boundary exists, wallets and integrators must decode the route and reject any simulated authorization tree containing children beyond the expected input transfer. [13](#0-12) 

### Proof of Concept
A caller invokes `swap_collateral(caller=victim, account_id, current=USDC, amount, new=ETH, swap=malicious_route)` with a valid account and collateral. [14](#0-13) 

The malicious route names an attacker-controlled pool that executes `token.transfer(victim, attacker, WALLET_BALANCE)` while the router also returns enough output for the controller's strategy checks. [15](#0-14) 

Simulation records the unexpected wallet-token transfer beneath the victim's `swap_collateral` authorization, and after the victim signs that tree the attacker receives `WALLET_BALANCE`, the victim's wallet balance becomes zero, and the strategy deposits the fair ETH output. [2](#0-1) [8](#0-7)

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
