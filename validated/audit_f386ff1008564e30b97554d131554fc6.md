## Title
Token Exchange sends the app's `client_secret` to an unsanitized host taken from the JWT `dest` claim - ([File: lib/shopify_api/auth/token_exchange.rb](https://github.com/AYontt/shopify-api-ruby--024))

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the request host for the Shopify `/admin/oauth/access_token` call directly from the session token's (`Shopify Id Token`) `dest` claim, without ever passing it through `ShopifyAPI::Utils::ShopValidator.sanitize!`. Every sibling method in the same authentication surface (`client_credentials`, `refresh_access_token`, and even `TokenExchange.migrate_to_expiring_token`) explicitly validates the `shop` against the `TRUSTED_SHOPIFY_DOMAINS` allowlist before using it to build the outbound request host that receives the app's `client_secret`. `exchange_token` is the one exception.

### Finding Description
The identity binding that is broken: **the host validated as "the shop that owns this session token" is not equal to the host that actually receives the app's `client_secret`.**

- `JwtPayload#shop` simply strips the scheme from the `dest` claim with no allowlist check: [1](#0-0) 

- `TokenExchange.exchange_token` takes this unsanitized value and uses it to build the `Session` that will host the outbound request, embedding the app's `client_secret` in the POST body: [2](#0-1) 

- `HttpClient#initialize` derives the request's base URI straight from `session.shop`, with no validation performed inside the client either: [3](#0-2) 

Compare this to the three sibling credential-exchange flows in the very same module/class, all of which call `Utils::ShopValidator.sanitize!(shop)` before constructing the `Session` used for the outbound, secret-carrying request: [4](#0-3) [5](#0-4) [6](#0-5) 

`ShopValidator.sanitize!` exists precisely to guard against this class of bug — it only accepts hosts under `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) and raises `InvalidShopError` otherwise: [7](#0-6) 

`exchange_token` is the only credential-exchange entry point in the file that skips this check, despite being the **recommended, primary** auth flow for embedded apps per the gem's own docs.

### Impact Explanation
If the `dest` claim of a session token resolves to (or can be made to resolve to) a host outside the Shopify-controlled domain set — e.g., a shop's misconfigured/attacker-influenced custom primary domain — the app's `client_id` and `client_secret` are sent verbatim, over HTTPS, to that host in the token-exchange POST body. This is SSRF carrying the app's `client_secret`, matching the "High - SSRF with the app's credentials" impact category, and can lead to full compromise of the app's OAuth credentials if the request lands on an attacker-controlled endpoint instead of `*.myshopify.com`.

### Likelihood Explanation
The vulnerable path (`exchange_token`) is the gem's own documented, preferred flow for embedded apps (Token Exchange), so it is exercised on essentially every authenticated request in embedded apps that adopt it. The missing check is a straightforward omission relative to the pattern used everywhere else in the same file, which strongly indicates it should be present here as well; its absence is directly demonstrable by code inspection and by the asymmetry between `exchange_token` and `migrate_to_expiring_token`/`refresh_access_token`/`client_credentials`.

### Recommendation
In `lib/shopify_api/auth/token_exchange.rb#exchange_token`, sanitize `dest_shop` the same way the other three methods do before constructing `shop_session`:
```ruby
dest_shop = Utils::ShopValidator.sanitize!(jwt_payload.shop)
```
This ensures the outbound host receiving `client_id`/`client_secret` is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`, closing the gap between the validated identity (a signed but unchecked `dest` claim) and the host that actually receives the credentials.

### Proof of Concept
1. Obtain/produce a session token whose `dest` claim resolves (via `JwtPayload#shop`, i.e., stripping `https://`) to a host not in `TRUSTED_SHOPIFY_DOMAINS`.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe that `Clients::HttpClient` builds `@base_uri = "https://#{dest}"` unchecked and issues `POST https://#{dest}/admin/oauth/access_token` with body containing `client_id` and `client_secret`, in contrast to calling `client_credentials(shop: dest)` or `refresh_access_token(shop: dest, ...)` with the same `dest`, which both raise `ShopifyAPI::Errors::InvalidShopError` via `ShopValidator.sanitize!` before ever making the request.
