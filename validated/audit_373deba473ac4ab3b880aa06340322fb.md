### Title
Missing Vesting Schedule Validation in Lockup Contract Creation — ([File: lockup/src/lib.rs], [File: lockup-factory/src/lib.rs])

### Summary
The `lockup-factory` contract's public `create` method allows any unprivileged caller to specify a `vesting_schedule` (`VestingScheduleOrHash::VestingSchedule`) when creating a new lockup contract. This schedule is forwarded to the `lockup` contract's `new()` initializer, which stores it directly as `VestingInformation::VestingSchedule(vs)` without ever calling `VestingSchedule::assert_valid()`. Since the vesting schedule is immutable field state once the lockup contract is deployed, a malformed schedule (e.g. `end_timestamp < start_timestamp`, `cliff_timestamp` out of range, or `start_timestamp == end_timestamp`) can be baked in permanently.

### Finding Description
`lockup/src/types.rs` defines `VestingSchedule::assert_valid()`, which checks `start_timestamp <= cliff_timestamp <= end_timestamp` and `start_timestamp < end_timestamp` [3](#0-2) . However, `LockupContract::new()` in `lockup/src/lib.rs` only matches on `VestingScheduleOrHash::VestingSchedule(vs)` to build `VestingInformation::VestingSchedule(vs)` — it never invokes `assert_valid()` on `vs` [2](#0-1) . The `lockup-factory`'s public, unprivileged `create()` method passes through an attacker/user-controlled `vesting_schedule: Option<VestingScheduleOrHash>` argument unchanged into the deployed lockup contract's init call [4](#0-3) . Because the vesting schedule becomes part of the immutable `VestingInformation` (no setter exists to fix it after init), any downstream computation that relies on the invariants asserted by `assert_valid()` (e.g., division by `end_timestamp - start_timestamp` when computing vested percentage) operates on unchecked, potentially degenerate timestamps.

### Impact Explanation
This matches the report's root-cause class (missing validation on an input that becomes immutable and is subsequently used by internal accounting logic), analogous to the `asset_type` issue in the external report. If the vesting math (e.g., `get_unvested_amount`) divides by `end_timestamp - start_timestamp`, a schedule with `start_timestamp == end_timestamp` could cause a division-by-zero panic in every call path that computes vested/unvested balances — including `terminate_vesting`, transfer checks, and staking eligibility checks — effectively freezing the account's funds permanently (owner can't transfer, foundation termination logic could also break). This falls under the "Permanent freezing/irrevocable loss of funds in lockup release/vesting termination" impact category.

### Likelihood Explanation
The `create()` entrypoint on `lockup-factory` is public and payable, callable by any unprivileged user who pays the minimum attached deposit; the `owner_account_id` for the new lockup is also caller-supplied, so an attacker can create a lockup contract for their own account (or for a victim's account, since `owner_account_id` is a free parameter) with a broken vesting schedule. The exact severity depends on whether the vesting math functions in `lockup/src/internal.rs` / `lockup/src/getters.rs` guard against a zero-length interval before dividing; this could not be fully confirmed from the retrieved snippets due to index limitations, so the reachability of a hard panic/division-by-zero (versus just "meaningless" percentages) is not 100% verified here.

### Recommendation
Call `vesting_schedule.assert_valid()` (for the `VestingScheduleOrHash::VestingSchedule` variant) inside `LockupContract::new()` before constructing `VestingInformation::VestingSchedule(vs)`, mirroring the pattern already used for `RewardFeeFraction::assert_valid()` in `staking-pool` and `staking-pool-factory` [5](#0-4) . Since `lockup-factory::create()` forwards user-supplied schedules without validation, either validate there too before creating the promise, or ensure `lockup::new()`'s own validation makes the downstream deployment fail (refunding deposit via the existing `on_lockup_create` rollback path) rather than deploying a contract with an unusable, permanently broken vesting schedule.

### Proof of Concept
1. Call `lockup-factory::create()` as any unprivileged account, supplying `owner_account_id: <target>`, and `vesting_schedule: Some(VestingScheduleOrHash::VestingSchedule(VestingSchedule { start_timestamp: T, cliff_timestamp: T, end_timestamp: T }))` (a zero-length or inverted schedule).
2. The factory forwards this to `lockup::new()` without calling `assert_valid()`; the lockup contract initializes successfully and stores the invalid schedule immutably in `VestingInformation::VestingSchedule`.
3. Any subsequent call that computes vested/unvested balances using `(cliff_timestamp - start_timestamp) / (end_timestamp - start_timestamp)`-style arithmetic will operate on a zero divisor or produce nonsensical results, potentially panicking and blocking transfers/termination for the life of the contract.

*Note: I was unable to directly inspect the exact vesting math implementation (`lockup/src/internal.rs` or equivalent) in this pass due to index/context limits, so the exact panic/degenerate-behavior mechanism could not be fully confirmed — this should be verified with a full read of the vesting-percentage calculation code before treating the division-by-zero claim as certain.*
