### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `api_version`, and `webhook_id` values used by webhook handlers directly from unauthenticated HTTP headers, while the HMAC signature verified by `ShopifyAPI::Utils::HmacValidator.validate` only covers the raw request body. This breaks the intended binding `hmac_signed_bytes == bytes_the_app_trusts_as_shop_identity`, letting anyone in possession of one valid `(body, hmac)` pair replay it with a different `shop-domain` header and have the app process the webhook as if it originated from an arbitrary victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `shop`, `topic`, `api_version`, `webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to that body: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates the request solely via `Utils::HmacValidator.validate(request)`, which internally calls `verifiable_query.to_signable_string` (i.e. only `@raw_body`) and `verifiable_query.hmac` (from the `hmac-sha256` header): [3](#0-2)  and [4](#0-3) 

After the HMAC check passes, `Registry.process` builds `WebhookMetadata` using `request.shop`, which is the raw `shopify-shop-domain`/`x-shopify-shop-domain` header value — never checked against the signed bytes: [5](#0-4) 

The intended identity binding is: `hmac == HMAC(secret, body)` should imply "this body, topic, and shop legitimately originated together from Shopify for this specific shop." In this implementation, `hmac` only binds the body; `shop` (and `topic`/`webhook_id`/`api_version`) float free of that signature. Any attacker who can produce (or capture/replay) one valid `(raw_body, hmac)` pair — trivially obtainable by installing the app on their own free/dev store and receiving one legitimate webhook — can resend that exact body and HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a different, victim shop domain. `HmacValidator.validate` still returns `true` because it never inspects the header, and the handler is invoked with `shop: <attacker-chosen victim shop>`.

### Impact Explanation
This is a cross-tenant identity-binding break: the app's webhook handler code is invoked believing the event came from shop X's tenant when the cryptographic proof only certifies the payload bytes, not the shop association. In any host application that scopes side effects (data writes, session/token invalidation, GDPR redaction processing for `customers/redact`/`shop/redact`/`customers/data_request`, resynchronization jobs, per-tenant caches, etc.) by `WebhookMetadata#shop`, this allows an unprivileged internet user with no credentials for the victim shop to inject fabricated events attributed to that victim shop — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires only: (1) knowledge of the app's public webhook endpoint, and (2) one legitimately captured `(body, hmac)` pair, which is trivially self-obtainable by installing the target app on an attacker-owned store and capturing the webhook Shopify sends to the app (the attacker fully controls where their own store's webhooks are delivered, or can intercept them client-side before the app's server discards the identifying context). No access to `api_secret_key`, access tokens, or victim credentials is needed.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the HMAC-verified material, or otherwise cryptographically tie the header-derived `shop` to the signed payload before trusting it — e.g., verify that the JSON body's own `shop_domain`/similar fields (if present) match the header, or require the host application to reconcile the webhook's shop against an existing, previously-established session/access-token record for that shop rather than trusting the header value directly. At minimum, document prominently that `Request#shop` is unauthenticated and must not be used as a sole tenant-scoping key by consuming applications.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers any registered webhook topic (e.g. `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent to the app's webhook endpoint.
2. Attacker replays the exact same body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, raw_body)` and compares it to the (unchanged, still-valid) HMAC header — validation succeeds.
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with `shop = "victim-shop.myshopify.com"`, and the registered handler executes believing the event is authentically from the victim shop, even though the victim shop never sent it.
