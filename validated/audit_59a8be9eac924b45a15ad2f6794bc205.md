### Title
Failed transactions under-report `loaded_accounts_data_size` to the cost model, allowing systemic underpayment for account-load I/O - ([File: svm/src/account_loader.rs])

### Summary
When a transaction fails during `load_transaction_accounts` (e.g. `ProgramAccountNotFound`, `InvalidProgramForExecution`, insufficient-rent, etc.) after having already read one or more large, non-rollback accounts from accounts-db, `load_transaction` in `svm/src/account_loader.rs` charges the cost model only for `RollbackAccounts::data_size()` — the fee payer (and nonce) account bytes — rather than the bytes actually loaded. This happens whenever the feature `define_ltds_fee_only_semantics` (SIMD-0186 amendment) is inactive, which is the default/legacy path still exercised on clusters where that feature has not yet been activated.

### Finding Description
In `load_transaction` [1](#0-0) , on a load error the `FeesOnlyTransaction.loaded_accounts_data_size` is set as:

```rust
loaded_accounts_data_size: if account_loader.feature_set.define_ltds_fee_only_semantics {
    loaded_transaction_data_size.into()
} else {
    tx_details.rollback_accounts.data_size() as u32
},
```

`RollbackAccounts::data_size()` only sums the bytes of the fee payer and (if present) nonce account [2](#0-1) . It intentionally ignores every other account that `load_transaction_accounts` [3](#0-2)  actually read from accounts-db (writable accounts, program accounts, ALT-resolved accounts, program-data accounts, etc.) before the load failed.

An attacker can construct a transaction that:
1. References several large accounts (writable or read-only) as instruction accounts so they get loaded and their size accumulated into `loaded_tx_data_size` inside `load_transaction_accounts`.
2. Ultimately fails to fully load — e.g. by referencing a final program id that does not exist (`ProgramAccountNotFound`) or is owned by a non-executable program (`InvalidProgramForExecution`) — causing `load_transaction_accounts` to return `Err` only *after* the large accounts were already read and counted.
3. The nonce/fee payer stay tiny (few dozen bytes).

Because the failure is a load error (not a runtime/rent/nonce validation error prior to reaching `load_transaction_accounts`), the transaction becomes a `FeesOnlyTransaction`, and (absent `define_ltds_fee_only_semantics`) its `loaded_accounts_data_size` collapses to just the fee payer's few bytes, even though accounts-db work (page reads/decompression for the large accounts) was already performed. This under-reported value flows into `CommittedTransaction.loaded_account_stats` [4](#0-3)  and is subsequently used by the cost tracker/CostModel to compute the *actual* `loaded_accounts_data_size_cost` charged against the block cost budget, e.g. via `CostModel::calculate_loaded_accounts_data_size_cost` [5](#0-4)  as seen being wired from `CommitTransactionDetails` in banking-stage cost accounting [6](#0-5) .

The gap is explicitly acknowledged in code comments: `data_size()` is "used internally when calculating the actual loaded transaction data size for the cost model. This function will be removed by the fee-payer data size amendment to SIMD-186" [7](#0-6) , and tests confirm the discrepancy directly by parameterizing over `define_ltds_fee_only_semantics` and showing the legacy path yields `0`/small sizes for the same failed transaction that the SIMD-186 path correctly attributes full loaded bytes to [8](#0-7)  and [9](#0-8) .

### Impact Explanation
This directly matches the "materially underpriced execution" category: an attacker can repeatedly send transactions engineered to touch large accounts (near the max loaded-accounts-data-size limit) and fail on the last instruction/program lookup, paying only the tiny fee-payer-sized cost-model charge instead of the true bytes loaded. Aggregated over many transactions/blocks, this systemically underprices real I/O work admitted per block, letting an attacker consume disproportionate accounts-db read bandwidth relative to the block-cost budget they are charged, degrading validator throughput (DoS-adjacent resource exhaustion via cheap large-account loads).

### Likelihood Explanation
Fully attacker-controlled and requires no special privileges: any user can submit a transaction referencing large accounts followed by an instruction that fails to load (missing/invalid program, `InvalidProgramForExecution`, etc.). It is reliably repeatable on any cluster/build where `define_ltds_fee_only_semantics` has not been activated (the feature is listed among features "not activated on all clusters" in the `FeatureSnapshot`) [10](#0-9) , which is the current production default absent that activation.

### Recommendation
Ensure `loaded_accounts_data_size` for `FeesOnlyTransaction` always reflects the actual bytes read by `load_transaction_accounts` (i.e., always use `loaded_transaction_data_size.into()`), independent of the `define_ltds_fee_only_semantics` gate, or accelerate/backport activation of SIMD-0186 semantics so the legacy undercounting path is retired everywhere. At minimum, this indicates the SIMD-186 fix should be prioritized for activation to close the underpricing window while the legacy code path remains reachable.

### Proof of Concept
Extend the existing parametrized test `fee_only_loaded_transaction_data_size` in `svm/tests/integration_test.rs` (already structured for this exact case) [11](#0-10)  or `test_load_and_execute_commit_transactions_fees_only` in `runtime/src/bank/tests.rs` [9](#0-8) , but with `define_ltds_fee_only_semantics` deactivated and a transaction that:
1. Includes several large (e.g. 8 KB) pre-funded accounts as instruction accounts.
2. Ends with an instruction to a non-existent program id, forcing `ProgramAccountNotFound` inside `load_transaction_accounts` after the large accounts were already loaded.
3. Assert that `commit_results[0].loaded_account_stats.loaded_accounts_data_size` (old path) equals only the fee-payer size (near-zero), while capturing/computing the true sum of all account sizes read (via `touched_flags`/accounts vector length before failure) shows the large accounts were loaded. Then assert `CostModel::calculate_loaded_accounts_data_size_cost(loaded_accounts_data_size, ...)` under-charges relative to the real bytes read, demonstrating the underpayment.

    account_loader: &mut AccountLoader<CB>,
    message: &impl SVMMessage,
    loaded_fee_payer_account: LoadedTransactionAccount,
    loaded_tx_data_size: &mut LoadedTransactionDataSize,
    error_metrics: &mut TransactionErrorMetrics,
    rent: &Rent,
) -> Result<Vec<KeyedAccountSharedData>> {
    let account_keys = message.account_keys();
    let mut loaded_transaction_accounts = Vec::with_capacity(account_keys.len());
    let mut additional_loaded_accounts: AHashSet<Pubkey> = AHashSet::new();

    // Transactions pay a base fee per address lookup table.
    loaded_tx_data_size.increase_calculated_data_size(
        message
            .num_lookup_tables()
            .saturating_mul(ADDRESS_LOOKUP_TABLE_BASE_SIZE),
        error_metrics,
    )?;

    let mut collect_loaded_account =
        |account_loader: &mut AccountLoader<CB>, key: &Pubkey, loaded_account| -> Result<()> {
            let LoadedTransactionAccount {
                account,
                loaded_size,
            } = loaded_account;

            loaded_tx_data_size.increase_calculated_data_size(loaded_size, error_metrics)?;

            // This has been annotated branch-by-branch because collapsing the logic is infeasible.
            // Its purpose is to ensure programdata accounts are counted once and *only* once per
            // transaction. By checking account_keys, we never double-count a programdata account
            // that was explicitly included in the transaction. We also use a hashset to gracefully
            // handle cases that LoaderV3 presumably makes impossible, such as self-referential
            // program accounts or multiply-referenced programdata accounts, for added safety.
            //
            // If in the future LoaderV3 programs are migrated to LoaderV4, this entire code block
            // can be deleted.
            //
            // If this is a valid LoaderV3 program...
            if bpf_loader_upgradeable::check_id(account.owner())
                && let Ok(UpgradeableLoaderState::Program {
                    programdata_address,
                }) = bincode::deserialize(account.data())
            {
                // ...its programdata was not already counted and will not later be counted...
                if !account_keys.iter().any(|key| programdata_address == *key)
                    && !additional_loaded_accounts.contains(&programdata_address)
                {
                    // ...and the programdata account exists (if it doesn't, it is *not* a load failure)...
                    if let Some(programdata_account) =
                        account_loader.load_account(&programdata_address)
                    {
                        // ...count programdata toward this transaction's total size.
                        loaded_tx_data_size.increase_calculated_data_size(
                            TRANSACTION_ACCOUNT_BASE_SIZE
                                .saturating_add(programdata_account.data().len()),
                            error_metrics,
                        )?;
                        additional_loaded_accounts.insert(programdata_address);
                    }
                }
            }

            loaded_transaction_accounts.push((*key, account));

            Ok(())
        };

    // Since the fee payer is always the first account, collect it first.
    // We can use it directly because it was already loaded during validation.
    collect_loaded_account(
        account_loader,
        message.fee_payer(),
        loaded_fee_payer_account,
    )?;

    // Attempt to load and collect remaining non-fee payer accounts.
    for (account_index, account_key) in account_keys.iter().enumerate().skip(1) {
        let loaded_account =
            load_transaction_account(account_loader, message, account_key, account_index, rent)?;
        collect_loaded_account(account_loader, account_key, loaded_account)?;
    }

            return Err(TransactionError::ProgramAccountNotFound);

            return Err(TransactionError::InvalidProgramForExecution);
        }
    }
