### Title
Webhook Shop/Topic Identity Spoofing via Fields Not Covered by HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then unconditionally trusts the `shop-domain`, `topic`, and `webhook-id` HTTP headers — none of which are covered by that HMAC — and hands them to the app's handler as if they were verified. This breaks the intended identity binding: `HMAC(raw_body) valid` should imply `shop header == originating shop`, but the header is never part of the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors read straight from HTTP headers, with no cryptographic linkage to the body or to any particular tenant: [2](#0-1) 

`Registry.process` validates only this body HMAC and then immediately constructs `WebhookMetadata` from the unauthenticated header values, dispatching it to the registered handler: [3](#0-2) 

The HMAC secret (`Context.api_secret_key`) used in `Utils::HmacValidator.validate_signature` is the app's single `client_secret`, shared across *every* shop that installs the app — it is not shop-specific: [4](#0-3) 

**Identity binding broken:** the gem's `process` method establishes `hmac_valid(raw_body) == true` and then treats that as proof of `request.shop == <legitimate origin shop>`, but the equality that actually holds is only `hmac_valid(raw_body) == true`, independent of `request.shop`. Any unprivileged internet user who can install the same public app on their own store (a normal, unprivileged action) receives real webhooks whose body+HMAC are valid under the shared app secret. That same attacker can then replay the identical `raw_body`/`hmac-sha256` pair to the merchant's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) headers for a victim shop. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` forwards the forged `shop` value into `WebhookMetadata` untouched.

### Impact Explanation
This allows cross-tenant impersonation of webhook events: an attacker-controlled payload can be attributed to an arbitrary victim shop domain in the app's webhook handler, satisfying the "cross-tenant access" criterion (Critical). Handlers that key persistence, uninstall logic, GDPR redaction, or session/token invalidation off `WebhookMetadata#shop` (as returned by this exact library API) can be tricked into acting on behalf of, or against, a shop the attacker does not control — all without ever needing `api_secret_key`, since the attacker legitimately obtains a valid body/HMAC pair for their own webhook deliveries.

### Likelihood Explanation
High likelihood: obtaining a legitimately signed webhook only requires installing the target public app on an attacker-owned development store, which is an ordinary unprivileged action. No secrets, tokens, or elevated access are required — only the ability to replay an HTTP POST with modified headers to the app's public webhook endpoint.

### Recommendation
Bind the shop identity into the verified material instead of trusting a bare header:
1. Require host applications (and ideally enforce within `Registry.process`) to cross-check `request.shop` against the set of shops known to have installed the app (e.g., via an existing offline session lookup) before dispatching to the handler.
2. Where possible, additionally verify shop-specific webhook subscription IDs (`webhook_id`) against records created during registration, rather than trusting the header value verbatim.
3. Document explicitly that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are **not** authenticated by the HMAC check and must not be used as a sole tenant-identity signal by consuming applications.

### Proof of Concept
1. Attacker installs the target public app on their own store `attacker.myshopify.com`, receiving a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(secret, B)`), and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker replays the exact same body `B` and `X-Shopify-Hmac-Sha256: H` to the merchant app's public webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate(request)` recomputes `HMAC(secret, B)` and finds it equal to `H`, returning `true` (per `lib/shopify_api/utils/hmac_validator.rb` lines 12-31), because only `@raw_body` is signed (`lib/shopify_api/webhooks/request.rb` lines 35-38).
4. `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: ..., ...)` (`lib/shopify_api/webhooks/registry.rb` lines 188-199), causing the host app to process a forged event as if it originated from `victim.myshopify.com`.
