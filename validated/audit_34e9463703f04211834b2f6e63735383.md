The `weightedMedian` mechanism in `aggregatePhantomBids` weights a solver's quote by their reported ERC-20 balance on the destination chain, read via `getBalance` at snapshot time. Since a bid's weight is based on a balance that is not locked, escrowed, or committed in any way, a single solver can transiently inflate its own on-chain balance (e.g., via a flash loan, temporary borrow, or self-transfer) to exceed 50% of the total weight for a leg, at which point `weightedMedian` returns that solver's price "verbatim" — this is functionally identical to the YYDS pattern of manipulating a reserve/balance figure that a price calculation trusts, within an attacker-controlled window, to dictate an outcome that benefits them.

### Title
Solver-controlled balance snapshot lets a single bidder dictate the phantom-order weighted-median price - ([File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts])

### Summary
`aggregatePhantomBids` prices each leg of a phantom order using `weightedMedian`, where a quote's weight is the bidding solver's live ERC-20/vault balance of that leg's output token, read on-demand via `getBalance` [1](#0-0) . Because this balance is read at snapshot time with no escrow, lock, or minimum holding-period requirement, a solver can transiently inflate its own balance of the output token to dominate the weight sum and force `weightedMedian` to return its own quoted price.

### Finding Description
`weightedMedian` performs a selection, not a blend: it returns the exact price of whichever bidder's cumulative weight first reaches half of the total weight [2](#0-1) . The code and docs explicitly acknowledge this dynamic — "a solver holding over half the leg's weight sets the published price verbatim" [3](#0-2)  and "the amount such a bid names is more than the solver would actually be left holding once the swap...clears" — while the corresponding weight/balance is read directly on-chain with no way to distinguish transient inventory from durable inventory [4](#0-3) .

Since `getBalance` simply reads the current ERC-20/vault balance for the solver's address on the destination chain, an unprivileged solver can borrow tokens (flash loan, short-term loan, or coordinated self-funding) immediately before its bid is included in the aggregation window, inflate its `weight` far past 50% of the leg's total, and thereby force the published `medianPrice` to equal whatever price it quoted — regardless of what other, legitimately capitalized solvers quoted.

### Impact Explanation
The `medianPrice` this attack sets propagates directly into `updateLiquidityPools`, feeding `PoolChainLiquidity` rows and ultimately the pool's `sellRate`/`buyRate` [5](#0-4) . These published rates are consumed downstream by other actors (fillers, price-sensitive intent routing) as if they were an honestly liquidity-weighted market price. A solver that no other participant can out-weight (because its "weight" is transient borrowed capital rather than committed inventory) can push published rates in its favor, disadvantaging users and other solvers relying on the snapshot — a stated concrete impact category (unsound/forged state used by dependent systems) once the price is treated as trustworthy market data.

### Likelihood Explanation
This requires no privileged access — any address that can act as a delegated/verified solver and submit a phantom bid is eligible [6](#0-5) . Obtaining a large flash-loanable or borrowable balance of a common output token (e.g. USDC/USDT) on an EVM chain to briefly exceed the other bidders' combined weight is a common, low-cost DeFi technique, making this readily reachable by any unprivileged intent solver.

### Recommendation
Do not weight quotes by an instantaneously-read balance. Options: require the weight to reflect committed/escrowed/staked capital (e.g., solver stake, an on-chain commitment held for a minimum duration) rather than a spot ERC-20 balance; snapshot balances at multiple points across the bidding window and use the minimum; or cap any single solver's contribution to a leg's total weight (e.g., at some fraction below 50%) so no single bidder can unilaterally set the median regardless of momentary balance size.

### Proof of Concept
1. Attacker deploys/controls a solver account registered as a valid `SolverAccount` delegate.
2. Immediately before the phantom bid window closes, attacker flash-loans (or otherwise transiently acquires) a large balance of the leg's output token on the destination chain.
3. Attacker submits a phantom bid quoting an attacker-favorable price for that leg.
4. `aggregatePhantomBids` reads the attacker's balance via `getBalance` at that moment [1](#0-0) , computing a weight that dwarfs all other bidders combined.
5. `weightedMedian` returns the attacker's exact quoted price as `medianPrice` since its cumulative weight passes 50% of the total [2](#0-1) .
6. Attacker repays the flash loan; the published rate remains manipulated in `PoolChainLiquidity`/pool `sellRate`/`buyRate` until the next snapshot, extractable value comes from downstream consumers trading against the skewed rate.

export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
}
