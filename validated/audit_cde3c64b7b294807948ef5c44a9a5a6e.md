### Title
Pool creation for a given market/PDA-seed account can be frontrun, permanently blocking the legitimate creator and letting an attacker set the pool's initial price and PNL/target-order state - (File: program/src/processor.rs)

### Summary
`process_initialize2` derives every pool-related PDA (AMM account, LP mint, coin/pc vault, target-orders) solely from the `market_info.key` account passed by the caller, combined with fixed seed suffixes, via `get_associated_address_and_bump_seed`. Because `market_info` can be "any account" (per the code's own comments) and none of the mint/ratio parameters are bound to it, an attacker who observes a pending `Initialize2` transaction in the mempool can submit their own `Initialize2` call using the same `market_info` key first, at minimal cost, permanently claiming those PDAs for that seed.

### Finding Description
The account derivation for pool creation uses only the market account key as a seed component: [1](#0-0) . This function is invoked identically for the AMM info account, LP mint, coin vault, pc vault, and target-orders account, all keyed off `market_info.key` [2](#0-1) .

In `process_initialize2`, the `market_info` account is explicitly documented as "Just a seed for AMM account. Can be any account," and is not validated against any real market or against the chosen `amm_coin_mint_info` / `amm_pc_mint_info` [3](#0-2) . The only checks performed before account creation are: the AMM config PDA, coin/pc mint distinctness, signer check, SPL/ATA/system program ids, and the authority PDA/nonce [4](#0-3) . None of these checks bind the derived pool PDAs to the intended mint pair, creator, or a commit-reveal secret.

Each of the four `generate_amm_associated_*` helper functions creates the account via `system_instruction::allocate`/`assign` and fails with `AmmError::RepeatCreateAmm` only if the target account is *already* owned by something other than the system program [5](#0-4) [6](#0-5) [7](#0-6) . Whoever's `Initialize2` transaction lands on-chain first wins these PDAs — there is no reservation, commit/reveal, or per-creator binding, which is exactly the bug class described in the report (frontrunning a public identifier-based registration).

An attacker monitoring the mempool for a victim's `Initialize2` transaction can extract the `market_info` pubkey (and any other account) from the pending transaction, then submit their own `Initialize2` instruction using the same `market_info` key but attacker-chosen `amm_coin_mint_info`/`amm_pc_mint_info`, `init_coin_amount`/`init_pc_amount`, and `user_wallet_info` (themselves), landing first with higher priority fee. Because the PDAs are derived only from `market_info.key` and fixed seeds, the attacker's transaction creates and locks the AMM account, LP mint, vaults and target-orders PDAs tied to that `market_info` key. The victim's original transaction then fails when it tries to create the same PDAs, hitting `AmmError::RepeatCreateAmm` in `generate_amm_associated_account`/`generate_amm_associated_spl_token`/`generate_amm_associated_spl_mint`.

Beyond simple griefing/DoS of the victim's pool creation, the attacker becomes the pool's initial LP: they set `init.init_coin_amount`/`init.init_pc_amount` (i.e., the initial price ratio) and mint themselves `user_lp_amount` [8](#0-7) , and `target_order.check_init` seeds the PNL/target-orders invariant baseline from that same attacker-chosen ratio [9](#0-8) . Any downstream party who later swaps/deposits against this attacker-controlled pool (created under the market identifier that others may look up/trust) inherits an attacker-set price and pnl baseline.

### Impact Explanation
The direct, concrete impact is a permanent freeze of the victim's ability to create a pool under the intended `market_info` seed: their transaction reverts with `AmmError::RepeatCreateAmm` and the AMM/LP/vault/target-orders PDAs derived from that seed are permanently occupied by the attacker's pool, with no code path to "give back" or reuse them. Additionally, since the attacker fully controls `init_coin_amount`/`init_pc_amount` for the same seed, they can create a pool with an arbitrary/manipulated initial price and PNL baseline for that identifier, which can be leveraged to disadvantage any user or LP who subsequently interacts with what they believe is "the" pool for that market/seed. This satisfies the "permanent freezing" and "insolvent/attacker-controlled pool accounting" impact bar.

### Likelihood Explanation
The `Initialize2` instruction is reachable by any unprivileged caller with attacker-chosen accounts and data (mint pubkeys, `market_info`, amounts), matching the allowed reachable surface. The attack only requires observing a pending `Initialize2` transaction in the mempool/leader schedule and resubmitting with a higher priority fee/earlier slot — a standard, well-understood frontrunning technique on Solana, requiring no privileged signer or off-chain trust assumption. The cost to the attacker is only the token amounts they choose to seed (they control `init_coin_amount`/`init_pc_amount`, so this can be minimized) plus rent for the new accounts, making the attack cheap and repeatable against any observed pool-creation transaction.

### Recommendation
Bind the AMM PDA derivation to more than just the caller-supplied `market_info` key — e.g., incorporate the creator's wallet pubkey and/or the coin/pc mint pubkeys into the seed, or require that `market_info` be validated as a genuine, unique market object (e.g., an OpenBook/Serum market whose base/quote mints are checked against `amm_coin_mint_info`/`amm_pc_mint_info`) so that an attacker cannot substitute an arbitrary throwaway account as the seed. Alternatively, adopt a commit/reveal scheme for pool creation as suggested in the original report, or require the "market" seed account to be a fresh account created by/for the caller within the same transaction (e.g., via `create_account` with the caller as a required signer over that account), preventing an attacker from reusing a merely-observed public key.

### Proof of Concept
1. Victim builds and submits an `Initialize2` transaction using `initialize2(...)` with a chosen `market` account, `coin_mint`, `pc_mint`, and initial amounts (per `program/src/instruction.rs:663-729`).
2. Attacker observes this pending transaction in the mempool and extracts the `market` pubkey and mint pubkeys.
3. Attacker computes the same PDAs via `get_associated_address_and_bump_seed(program_id, market, <seed>, program_id)` for `AMM_ASSOCIATED_SEED`, `LP_MINT_ASSOCIATED_SEED`, `COIN_VAULT_ASSOCIATED_SEED`, `PC_VAULT_ASSOCIATED_SEED`, `TARGET_ASSOCIATED_SEED` (`program/src/processor.rs:112-126`), and submits their own `Initialize2` transaction with the same `market` account but `user_wallet_info` = attacker, and attacker-chosen `init_coin_amount`/`init_pc_amount`, at a higher priority fee to land first.
4. Attacker's transaction succeeds: `generate_amm_associated_account`/`generate_amm_associated_spl_token`/`generate_amm_associated_spl_mint` allocate/assign the PDAs to the attacker's pool (`program/src/processor.rs:294-546`), and `amm.initialize(...)`/`target_order.check_init(...)` set the pool state and PNL baseline from the attacker's chosen ratio (`program/src/processor.rs:908-983`).
5. Victim's original transaction now executes against already-owned PDAs and fails with `AmmError::RepeatCreateAmm` at the same helper functions, permanently preventing the victim from creating a pool for that `market` seed.

    market_address: &Pubkey,
    associated_seed: &[u8],
    program_id: &Pubkey,
