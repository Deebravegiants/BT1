### Title
Webhook `shop-domain` header is trusted for tenant identification but is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC that `Utils::HmacValidator.validate` checks covers exclusively the body bytes. The `shop` (from the `x-shopify-shop-domain` / `shopify-shop-domain` header) is read separately and is never included in the signed material, yet it is forwarded as the authoritative tenant identifier to the application's webhook handler.

### Finding Description
`Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, then immediately constructs `WebhookMetadata` using `request.shop` as the tenant identifier for the handler: [1](#0-0) 

The HMAC that is validated is computed only from `@raw_body`: [2](#0-1) 

while `shop` is parsed independently from a header that is not part of the signed content: [3](#0-2) [4](#0-3) 

Additionally, `Context.api_secret_key` is a single shared app secret used to validate the HMAC for *every* shop that has the app installed — it is not shop-specific: [5](#0-4) 

The identity binding broken is:
`shop asserted to the handler (request.shop, from an unsigned header) ≠ shop that actually authenticated the request (the shop whose body+shared-secret produced the accepted HMAC)`.

Because the same `api_secret_key` validates webhooks for all shops using the app, and the header carrying the tenant identity is excluded from the signable string, any party that can obtain one validly-signed webhook body (e.g., by installing the app on their own store, which any unprivileged internet user can do for a public app) can replay that body to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header for a victim shop. `Utils::HmacValidator.validate` still returns true (it only checks the body/HMAC pair), and `Registry.process` will hand the forged `shop` value straight to the app's handler in `WebhookMetadata`, which apps commonly use to select per-tenant sessions/data.

### Impact Explanation
This is a cross-tenant identity confusion: a request cryptographically bound to shop A's install is delivered to the application logic labeled as belonging to shop B. Any app handler that keys its shop-lookup off `WebhookMetadata#shop` (the value this gem exposes and documents as the request's shop) can be tricked into operating on/for the wrong tenant, satisfying the "cross-tenant access" high/critical-impact criterion.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the target public app on an attacker-controlled shop to obtain at least one validly HMAC-signed webhook body, and (2) the ability to send a crafted HTTP POST to the app's public webhook endpoint with a modified `shop-domain` header and the captured body/HMAC pair. No access token, `api_secret_key`, or privileged credential of the victim shop is needed — only unprivileged use of the app as any merchant could. This fits squarely within the documented threat pattern of "a field acted on but not covered by the HMAC."

### Recommendation
Include the `shop` (and ideally `topic`/`webhook-id`) header values in the HMAC-signed material, or otherwise cryptographically bind them to the raw body before verification, so that `Utils::HmacValidator.validate` fails if any of these headers are altered after signing. At minimum, document prominently that `WebhookMetadata#shop` must not be trusted as authoritative tenant identity unless independently cross-checked (e.g., against the shop's registered/installed session), and consider exposing a validation helper that ties the shop header to the specific webhook subscription/shop that was expected to receive it.

### Proof of Concept
1. Install the target public Shopify app on attacker-controlled store `attacker.myshopify.com`.
2. Capture a legitimate webhook delivery: body `B`, and header `x-shopify-hmac-sha256: H` (valid because `HMAC(api_secret_key, B) == H`), header `x-shopify-shop-domain: attacker.myshopify.com`.
3. Replay a POST to the same app webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` — [6](#0-5)  — which passes because it only checks `HMAC(api_secret_key, B)`.
5. `WebhookMetadata` is built with `shop: request.shop` = `"victim.myshopify.com"` and delivered to the handler — [7](#0-6)  — even though the payload actually originated from and pertains to the attacker's own shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
