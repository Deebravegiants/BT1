### Title
Unsigned cross-chain calldata lets an attacker impersonate any Substrate account via `HyperFungibleToken` `on_accept` — (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`Pallet::on_accept` in the hyper-fungible-token ISMP module dispatches an embedded runtime call using an origin account derived from `message.from` — a field that lives entirely inside the caller-controlled, ABI-encoded `body`/`data` payload of the cross-chain message — whenever `substrate_data.signature` is `None`. No cryptographic proof ties `message.from` to the actual party that triggered the transfer on the source chain. This is structurally the same bug class as the ZeptoClaw advisory: an untrusted, application-layer "identity" field (`sender`/`chat_id` there, `message.from` here) is trusted to authorize a privileged action, and the authenticating mechanism (the `auth_token`/signature check) is optional and silently skipped when absent.

### Finding Description
`on_accept` decodes the ISMP `PostRequest.body` into an app-level `Message` and, when the message carries non-empty `data`, decodes `SubstrateCalldata { signature: Option<Vec<u8>>, runtime_call }`: [1](#0-0) 

If a signature is present it is verified against `(nonce, runtime_call)` and the recovered/derived account is used as origin — this path is sound: [2](#0-1) 

But if `substrate_data.signature` is `None`, the code falls straight to using `message.from` — parsed out of the same attacker-supplied `body` — as the dispatch origin, with zero authentication: [3](#0-2) 

That origin is then used to dispatch an arbitrary `runtime_call` (only gated by `BaseCallFilter`, not by any ownership check of `origin`): [4](#0-3) 

Crucially, `message.from` is not the ISMP-verified `PostRequest.from` (which is checked via `ContractToAsset::<T>::get(source, &from)` and only authenticates *which source contract* sent the message, not which end user): [5](#0-4) 

`message.from` is a separate field nested inside the ABI-encoded `Message` struct carried in the request body — i.e., payload content the source-chain caller controls when constructing the cross-chain transfer, analogous to the `sender`/`chat_id` fields in the ZeptoClaw `WebhookPayload` that were trusted without being cryptographically bound to the real caller. Just as ZeptoClaw's `validate_auth` defaults to accepting requests when no token is configured, this pallet defaults to accepting the unsigned identity (`message.from`) when no `substrate_data.signature` is supplied, treating optional authentication as authoritative identity in its absence.

### Impact Explanation
Any account able to trigger a cross-chain transfer with attached calldata (any holder able to call the source-chain token contract's transfer/dispatch entrypoint feeding the `Message.data` field) can set `message.from` to an arbitrary Substrate `AccountId` and have the pallet dispatch an arbitrary runtime call `RawOrigin::Signed(that_account)`. This is an unauthorized-app-action / authentication-bypass primitive: the attacker can impersonate any account (including governance-adjacent or high-value accounts) for any call permitted by `BaseCallFilter`, potentially moving funds, altering approvals, or invoking other privileged dispatchables as the victim account — with no signature or proof binding the action to the impersonated account.

### Likelihood Explanation
High. The vulnerable code path is reachable by any unprivileged actor able to initiate an ordinary cross-chain HFT transfer with non-empty calldata (a normal user action, not requiring compromise of governance, collators, or relayers). The only gate — `substrate_data.signature` — is optional by construction (`Option<Vec<u8>>`), so an attacker simply omits it to hit the unauthenticated branch.

### Recommendation
Remove the unauthenticated fallback path. Require `substrate_data.signature` to be present and valid whenever `runtime_call` is dispatched, or otherwise strictly bind the dispatch origin to a cryptographically verified value (e.g., derive `origin` only from a value that has been signature-verified, never from a bare payload field like `message.from`). At minimum, never allow `message.from` to be trusted as a dispatch origin unless proven via `ed25519_verify`/`sr25519_verify`/ECDSA recovery in the same way the signed branch already does.

### Proof of Concept
1. On the source EVM chain, call the HyperFungibleToken transfer entrypoint with a payload whose ABI-encoded `Message.data` decodes to `SubstrateCalldata { signature: None, runtime_call: <arbitrary_call_bytes> }` and `Message.from` set to the bytes of a victim Substrate `AccountId` (e.g., a treasury or governance-controlled account).
2. Relay the resulting POST request to the destination chain running `pallet-hyper-fungible-token`.
3. `on_accept` executes: `substrate_data.signature` is `None`, so `origin = victim_account` (derived from `message.from`) at `modules/pallets/hyper-fungible-token/src/module.rs:176-187`.
4. `runtime_call.dispatch(RawOrigin::Signed(origin))` executes the attacker-chosen call as the victim account (subject only to `BaseCallFilter`), at `modules/pallets/hyper-fungible-token/src/module.rs:197-200` — no signature, proof, or source-chain ownership check ever validated that the caller actually controls `victim_account`.
