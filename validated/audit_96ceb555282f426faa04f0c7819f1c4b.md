### Title
Unbounded `amount_in` in `getFeeQuote`'s primary exact-out path lets a lone malicious solver overcharge the user's fee-asset swap - (File: packages/intents-sdk/src/lib/estimate-fee.ts, packages/internal-utils/src/solverRelay/getQuote.ts)

### Summary
`getFeeQuote` first requests a quote with `exact_amount_out = feeAmount`. In `handleQuoteResult`/`matchesRequest`, only `quote.amount_out` is checked for exact equality to the requested `feeAmount`; `quote.amount_in` is left completely unconstrained and unchecked against any price reference. If a solver is the sole (or best-ranked) responder, its inflated `amount_in` is selected by `sortQuotes` and returned as-is, then propagated verbatim into the signed `token_diff` intent that debits the user.

### Finding Description
The broken equality: the code implicitly assumes `quote.amount_in` reflects a fair market price for `feeAmount` of `feeAssetId`, but nothing enforces `amount_in ≈ marketPrice(feeAmount)`.

Trace:
1. `getFeeQuote` (`packages/intents-sdk/src/lib/estimate-fee.ts:64-80`) calls `solverRelay.getQuote` with `exact_amount_out: feeAmount.toString()`.
2. `handleQuoteResult` (`packages/internal-utils/src/solverRelay/getQuote.ts:32-94`) filters quotes with `matchesRequest`, which for the exact-out case only verifies `BigInt(quote.amount_out) === BigInt(quoteParams.exact_amount_out)` (`getQuote.ts:135-138`). `amount_in` is never validated here.
3. `sortQuotes` for `exact_out` kind sorts ascending by `amount_in` and picks the smallest (`getQuote.ts:96-113`), which is correct *if there are multiple honest bidders*, but provides no protection when the attacker is the only (or the cheapest-looking) bidder.
4. Contrast this with the fallback exact-in branch in `getFeeQuote` (`estimate-fee.ts:139-159`), which explicitly sanity-checks the returned amount against a computed price ratio (`actualRatio > 1500n` and `quote.amount_out < feeAmount`) before accepting the quote. The primary exact-out branch has **no equivalent check** on `amount_in`.
5. The returned `quote` is stored unchanged in `FeeEstimation.quote` and later embedded directly into the signed `token_diff` intent in `createWithdrawalIntents` (e.g. `packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts:120-131` and `packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts:304-315`), using `quote.amount_in` and `quote.amount_out` verbatim as the swap the user signs.
6. `FeeExceedsAmountError` (`packages/intents-sdk/src/sdk.ts:421-424`) only guards the `feeInclusive: true` case by comparing `fee.amount` (== `quote.amount_in`) to `withdrawalParams.amount`; when `feeInclusive` is `false` there is no upper bound at all on `quote.amount_in`.

Attacker input: a permissionless solver replies to the relay's aggregated quote request with `amount_out == feeAmount` exactly (satisfying `matchesRequest`) but an arbitrarily large `amount_in`. If it is the only or cheapest-appearing responder for that asset pair (a solver can simply not compete on other pairs, or the pair only has one liquidity provider), its quote wins.

### Impact Explanation
The selected quote's `amount_in`/`amount_out` becomes a `token_diff` intent that the user signs as part of `signAndSendWithdrawalIntent`/`createWithdrawalIntents`. This directly debits `amount_in` of the withdrawal token from the user's intents balance to receive only the true `feeAmount` of the fee asset, with the surplus captured by the malicious solver settling the counter side of the diff. When `feeInclusive` is `false` there is no cap at all; when `true`, the only cap is that the fee cannot exceed the entire withdrawal amount (`FeeExceedsAmountError`), so an attacker can still drain up to the full withdrawal amount. This matches "a fee overcharge or solver overpaid beyond the displayed fee" / potentially "a fee error draining a material share of the amount."

### Likelihood Explanation
Requires the attacker to control (or be) the sole/most competitive solver responding to the relay's quote for the specific `(tokenAssetId, feeAssetId)` pair at the moment of the request — feasible for thinly-traded or exotic asset pairs where solver competition is sparse, and trivially feasible if the attacker can transiently be the only responder. No privileged access is needed; this is exercised on every `estimateWithdrawalFee`/`processWithdrawal` call for a non-fee-native withdrawal asset, so it is repeatable per call/per victim.

### Recommendation
Add a price-sanity check on `amount_in` in the primary exact-out path of `getFeeQuote`, symmetric to the existing `actualRatio` check in the fallback branch (e.g., compare `quote.amount_in` against the USD-price-derived expected value with a bounded multiplier, and reject/retry with `QuoteError` if it exceeds a threshold). Additionally, consider requiring a minimum number of independent solver responses before trusting a lone quote for the primary path.

### Proof of Concept
Vitest plan (mock only the solver-relay HTTP `quote` JSON-RPC call and `tokens()` price endpoint):
1. Mock `quote` to return a single valid entry: `{ amount_in: "999999999999999999", amount_out: "<feeAmount>", defuse_asset_identifier_in: tokenAssetId, defuse_asset_identifier_out: feeAssetId, expiration_time: <future>, quote_hash: "h1" }`.
2. Call `getFeeQuote({ feeAmount, feeAssetId, tokenAssetId, envConfig, ... })`.
3. Assert `matchesRequest` accepts it (amount_out equality holds) and `handleQuoteResult` returns this quote unchanged — i.e., no rejection despite the absurd `amount_in`.
4. Assert `feeEstimation.amount === BigInt("999999999999999999")` from `estimateWithdrawalFee`, proving the equality `amount_in ≈ marketPrice(feeAmount)` is violated with no guard rejecting it, in contrast to the fallback branch where an equivalent mock (`amount_out` far above `feeAmount * 1.5`) is correctly rejected via the `actualRatio > 1500n` check. function sortQuotes(
	quotes: Quote[],
	quoteKind: "exact_in" | "exact_out",
): Quote[] {
	return quotes.slice().sort((a, b) => {
		if (quoteKind === "exact_in") {
			// For exact_in, sort by `amount_out` in descending order
			if (BigInt(a.amount_out) > BigInt(b.amount_out)) return -1;
			if (BigInt(a.amount_out) < BigInt(b.amount_out)) return 1;
			return 0;
		}

		// For exact_out, sort by `amount_in` in ascending order
		if (BigInt(a.amount_in) < BigInt(b.amount_in)) return -1;
		if (BigInt(a.amount_in) > BigInt(b.amount_in)) return 1;
		return 0;
	});
}

function matchesRequest(
	quote: Quote,
	quoteParams: GetQuoteParams["quoteParams"],
): boolean {
	if (
		quote.defuse_asset_identifier_in !==
			quoteParams.defuse_asset_identifier_in ||
		quote.defuse_asset_identifier_out !==
			quoteParams.defuse_asset_identifier_out
	) {
		return false;
	}

	// Only the side fixed by the request is verified; the other side is what the
	// solver competes on (max amount_out for exact_in, min amount_in for
	// exact_out). Compare as BigInt so formatting differences don't matter.
	if (quoteParams.exact_amount_in != null) {
		return BigInt(quote.amount_in) === BigInt(quoteParams.exact_amount_in);
	}
	return BigInt(quote.amount_out) === BigInt(quoteParams.exact_amount_out);
