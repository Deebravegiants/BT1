### Title
Webhook `shop` domain is not covered by the HMAC signature, enabling cross-tenant webhook forgery via replay - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values used afterwards to build the trusted `WebhookMetadata` handed to the app's handler are taken from unauthenticated headers that are never part of the signed content [2](#0-1) . This breaks the identity binding `hmac(body) == hmac(body, secret)` versus the actually-trusted tuple `(shop, topic, body)`, since only `body` is bound by the signature while `shop` is not.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field [3](#0-2) . For webhook requests, `Webhooks::Request#to_signable_string` returns only `@raw_body`; none of the identifying headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`) are included [4](#0-3) . Yet `Registry.process` reads `request.shop` and `request.topic` directly from these unauthenticated headers and passes them straight into `WebhookMetadata`, which is delivered to the app's handler as trusted tenant-identifying data [5](#0-4) [6](#0-5) .

This is inconsistent with how the same gem handles the OAuth callback: `Auth::Oauth::AuthQuery#to_signable_string` explicitly includes `shop` (along with `code`, `host`, `state`, `timestamp`) in the signed content, so the OAuth `shop` claim is cryptographically bound to the signature [7](#0-6) . The webhook path has no equivalent binding for `shop`, breaking the equality `signed_shop == trusted_shop` that the OAuth flow correctly enforces.

Practical exploitation: any unprivileged internet user who has ever received (or captured, e.g. via debug logging, a proxy, or their own installed instance of the target app) one genuine, validly-signed webhook body+HMAC pair for topic X can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header (and/or `shopify-topic`/`shopify-webhook-id`/`shopify-api-version` headers). `HmacValidator.validate` will still succeed because only the body is checked, and `Registry.process` will dispatch to the handler with `WebhookMetadata.shop` set to the attacker-chosen shop domain and/or `WebhookMetadata.topic` set to an attacker-chosen topic, even though that content was never actually produced or signed for that shop/topic by Shopify.

### Impact Explanation
Any downstream app logic that trusts `WebhookMetadata.shop` to select the tenant/session to act on (the pattern explicitly documented and demonstrated in the gem's own docs: `perform_later(topic: data.topic, shop_domain: data.shop, ...)` [8](#0-7) ) can be made to process attacker-supplied body content under the identity of a different shop than the one that actually produced it, and/or under a different topic than the one the body was actually signed for. This is a cross-tenant integrity confusion at the boundary this gem is responsible for guarding (`Registry.process`/`HmacValidator.validate`), matching the Critical "cross-tenant access" impact class: an app relying on this gem's webhook authentication has no cryptographic guarantee that the `shop` (or `topic`) it is told to act on matches the body it received.

### Likelihood Explanation
The attacker needs one previously-observed valid `(body, hmac)` pair for any topic the target app subscribes to — trivial to obtain by installing the target app on the attacker's own store, or from logs/proxies, since webhook payloads are not secret. No access to `api_secret_key` or any credential is required to perform the replay itself; only the ability to send an HTTP POST to the app's public webhook endpoint with attacker-chosen headers is needed, which is squarely "unprivileged internet user" access.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed/verified content for webhook requests, or otherwise cryptographically bind them (e.g., verify them against Shopify's known webhook delivery metadata, or require mTLS/IP allow-listing at the transport layer as Shopify recommends) instead of trusting header values that fall entirely outside the HMAC's coverage. At minimum, document/require that the `shop` and `topic` used by `WebhookMetadata` are not authenticated by the HMAC, so app authors do not assume tenant safety solely from `Registry.process` succeeding.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com` and trigger a subscribed webhook (e.g., `orders/create`) to capture a genuine `raw_body` and its valid `x-shopify-hmac-sha256` value (computed by Shopify with the app's real secret over that body).
2. Replay that exact `raw_body` and `hmac` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com` (and optionally change `x-shopify-topic`).
3. `HmacValidator.validate` succeeds because it only checks the body/hmac pair via `to_signable_string` (body-only) [4](#0-3) .
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-controlled headers [5](#0-4)  and invokes the app handler, which — following the gem's documented pattern — will act as if this data legitimately originated from `victim.myshopify.com`.

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
