### Title
Webhook `shop` header not covered by HMAC signature allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, excluding the `shop-domain`/`x-shopify-shop-domain` header from the HMAC-signed material. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then passes the unauthenticated `request.shop` value straight to the app's webhook handler as the tenant identifier. This breaks the identity binding: `shop covered by HMAC == shop used to attribute the webhook to a tenant`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which returns only `@raw_body`, never the `shop` header.

`Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC over the signable string (i.e., the body) and then forwards `request.shop` unchanged to the handler as the trusted tenant identifier: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` only ever compares `verifiable_query.hmac` against a digest of `verifiable_query.to_signable_string`, so any field not included in `to_signable_string` is unauthenticated: [4](#0-3) 

Because the app's `api_secret_key` is a single, app-wide client secret (not per-shop), an attacker who controls or has installed the app on their **own** shop can obtain a genuinely-signed webhook HTTP request (valid body + valid HMAC, since the HMAC only proves knowledge of the shared app secret over that specific body). The attacker can then replay that exact request to the app's webhook endpoint while only changing the `shop-domain` header to an arbitrary victim shop domain. Since the header is outside the HMAC-covered `to_signable_string`, the signature still validates, and `Registry.process` will dispatch to the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` claiming to be from the victim shop.

This is the same bug class as the reported issue: a field that is acted upon (the `shop` used for identity/tenant attribution) is not covered by the integrity check (the HMAC), letting an attacker manipulate the unverified field while keeping the signature valid.

### Impact Explanation
If the host application's webhook handler uses `WebhookMetadata#shop` to select/mutate tenant-specific state (look up a merchant's session, apply order/customer/app data changes, trigger uninstall/redact flows, etc.) — which is the documented purpose of that field — an attacker can forge webhook events attributed to any other merchant using the app, without ever possessing that merchant's credentials. This is a cross-tenant integrity/confused-deputy issue: attacker-controlled webhook payloads (constrained to what they can produce for their own shop, but arbitrary within their control) can be attributed to a victim tenant.

### Likelihood Explanation
Requires the attacker to be an app user (install the app on a shop they control) to obtain a validly-signed webhook of their choosing, and requires the target app's webhook endpoint to be reachable directly (not solely invoked via an infrastructure layer that separately authenticates shop, e.g. some hosting setups may add their own binding — this cannot be verified from the gem alone). Within the gem's own logic, no such secondary binding exists, and nothing prevents the header from being altered before the signature is checked.

### Recommendation
Include the `shop` (and ideally `topic`) header value in the HMAC-signed material used for webhook verification, or otherwise cryptographically bind the `shop-domain` header to the payload before trusting it in `WebhookMetadata`. At minimum, document that `WebhookMetadata#shop` is not covered by the HMAC and must not be trusted for tenant attribution without additional verification (e.g., cross-referencing the shop against data embedded in the verified body).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`) that the app sends to their controlled endpoint. They capture the raw HTTP request, including:
   - `x-shopify-hmac-sha256: <valid HMAC of raw body under the app's api_secret_key>`
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-topic: orders/create`
   - body: `{"id": ..., ...}` (attacker-controlled order data, since it's their own shop)
2. Attacker replays this exact request to the target app's real webhook endpoint but replaces only the header:
   `x-shopify-shop-domain: victim.myshopify.com`
3. `Utils::HmacValidator.validate` recomputes HMAC over `request.to_signable_string` (the raw body only, per `lib/shopify_api/webhooks/request.rb:35-38`), which is unchanged — validation passes.
4. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: <attacker's data>, ...)`, per `lib/shopify_api/webhooks/registry.rb:198-199`.
5. Any handler logic keyed on `data.shop` now operates as if the (attacker-controlled) payload legitimately originated from `victim.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
