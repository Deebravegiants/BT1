## Title
Webhook `shop` identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw request body only, while the `shop` (and `topic`/`webhook_id`) values used by `ShopifyAPI::Webhooks::Registry.process` and handed to the app's handler are taken from unauthenticated HTTP headers. The gem verifies "this body was signed with our `api_secret_key`" but never verifies "and this body belongs to *this* shop," so the `shop` identity acted upon by the handler is not bound to the value the HMAC actually authenticates.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from an `X-Shopify-Shop-Domain`/`shopify-shop-domain` header with no cryptographic tie to the body or to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` only checks that `HMAC(secret, raw_body)` matches the supplied `hmac` header - it never incorporates `shop`, `topic`, or `webhook_id` into the signed material: [3](#0-2) 

`Registry.process` validates only that HMAC, then forwards the header-derived `shop` (and `topic`) to the app-supplied handler as trusted identity: [4](#0-3) 

Because Shopify apps use a single, global `api_secret_key`/`client_secret` shared across every installation of the app (not a per-shop secret), any merchant who installs the app receives genuine webhooks whose HMAC is valid under that same shared secret. That merchant (an "unprivileged" actor with respect to *other* tenants of the app) can capture one legitimate `(raw_body, hmac)` pair delivered to their own shop, then replay it to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. `HmacValidator.validate` still succeeds because it only checks the body's authenticity, not which shop it claims to be from. `Registry.process` then invokes the handler with `WebhookMetadata` whose `shop` is the attacker-chosen value: [5](#0-4) 

This is exactly the identity-binding failure described in the rules: a field ("shop") that is acted upon (used to attribute/route webhook data to a tenant) is not covered by the HMAC that is supposed to authenticate the message.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` from `Registry.process` to look up a shop's session/record or to attribute incoming data to a tenant is exposed to cross-tenant data confusion: a malicious but otherwise legitimate app user (any shop that installed the app) can forge webhook deliveries that appear to originate from a victim shop, because the cryptographic guarantee provided by this gem covers only the body bytes, not the shop identity. This crosses a tenant boundary using only the shared, gem-verified secret — no access token or victim credentials are required.

### Likelihood Explanation
Exploitation only requires: (1) installing the app on a shop the attacker controls (a normal, unprivileged action any merchant can take), (2) capturing one webhook delivery to that shop, and (3) POSTing the same body/HMAC to the app's public webhook endpoint with a spoofed shop-domain header. No secret keys, tokens, or elevated access are needed, making this straightforward for any app that trusts `request.shop`/`WebhookMetadata#shop` as returned by this gem.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the material verified by the HMAC — e.g., have `VerifiableQuery`/`Request#to_signable_string` include the shop domain header (as Shopify's own signature scheme allows verifying headers alongside the body), or otherwise cryptographically tie the claimed shop to the signed payload before it is exposed via `WebhookMetadata`. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must be independently correlated by the caller with the shop for which the specific webhook topic/subscription was registered.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; attacker receives a genuine webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(app_secret, B)`), header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker replays the exact same body `B` and HMAC `H` to the app's public webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers; `Utils::HmacValidator.validate` succeeds because it only recomputes `HMAC(app_secret, B)` and compares it to `H` — the shop header is irrelevant to this check (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `ShopifyAPI::Webhooks::Registry.process` calls the app's handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop == "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the payload actually originated from and pertains to `attacker-shop.myshopify.com`.
