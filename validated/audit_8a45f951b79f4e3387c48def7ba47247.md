### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are unauthenticated and excluded from HMAC verification, enabling cross-tenant event spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` cryptographically verifies just the payload bytes. The `shop`, `topic`, `webhook_id`, and `api_version` values that `ShopifyAPI::Webhooks::Registry.process` passes on to the app's handler as the trusted tenant identity are read straight from HTTP headers that carry no cryptographic binding to that HMAC at all.

### Finding Description
`AuthQuery#to_signable_string` (OAuth callback) deliberately includes `shop` in the signed string, so the OAuth callback binds `shop` to the signature: [4](#0-3)  The webhook `Request` class does not follow this pattern — `to_signable_string` returns only `@raw_body`: [5](#0-4) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are parsed purely from headers with zero cryptographic tie to the HMAC or the body: [6](#0-5) .

`Registry.process` validates the HMAC over the body only, then immediately trusts `request.shop` as the tenant identity forwarded to the app's handler: [2](#0-1) . The library's own documentation tells developers that calling `process` "will verify the request did indeed come from Shopify," implying the whole `WebhookMetadata` (including `shop`) is authenticated: [3](#0-2) . This is precisely the "field acted on but not covered by the HMAC" identity-binding break: the equality the gem should enforce — `shop-header == shop-bound-to-signature` — never holds, because the signature covers no header at all.

### Impact Explanation
Any party capable of triggering one legitimate webhook delivery for their own shop (e.g., any merchant installing the vulnerable app and performing a normal store action like creating an order) obtains a `(raw_body, hmac)` pair valid under the app's single, shop-independent `api_secret_key`. Because `shop` isn't part of the signed content, that same `(raw_body, hmac)` pair remains valid if replayed with an arbitrary `shop-domain` header. The receiving app, following this gem's documented contract, will process the payload under `data.shop` equal to the attacker-chosen shop, feeding forged/misattributed data into whatever tenant-scoped logic keys off `WebhookMetadata#shop` (e.g., record updates, redact/GDPR handlers, per-shop billing or state transitions) — a cross-tenant access vector, which is Critical severity per the given rubric.

### Likelihood Explanation
Exploitation only requires being an existing, unprivileged app installer/merchant able to trigger any webhook for their own shop and then POST the captured `(raw_body, headers)` to the app's public webhook endpoint with a modified `shop-domain` header — no `api_secret_key`, access token, or TLS interception is needed. This satisfies the "unprivileged internet user" and "breaks an identity binding" constraints in the rules.

### Recommendation
Include the identity-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed content — e.g., have `Request#to_signable_string` concatenate the normalized headers together with the raw body — mirroring the OAuth `AuthQuery` pattern where `shop` is explicitly part of `to_signable_string`.

### Proof of Concept
1. Merchant A installs the vulnerable app on `shop-a.myshopify.com` and legitimately triggers a webhook (e.g. `orders/create`), capturing the delivered `raw_body` and the `x-shopify-hmac-sha256` header from Shopify (both are visible to Merchant A's own receiving endpoint/logs).
2. Merchant A crafts a new POST to the app's registered webhook path, reusing the exact same `raw_body` and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: shop-b.myshopify.com` (a different, victim tenant) and any desired `x-shopify-topic`/`x-shopify-webhook-id`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers; `Utils::HmacValidator.validate` succeeds because `to_signable_string` only checks `raw_body`, which is unchanged and correctly signed.
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", ...)`, causing the app to act on Merchant A's data/body as though it belongs to `shop-b`, a cross-tenant confusion the app has no way to detect using this gem's verification.
