### Title
Incorrect decimal scaling in `convert_to_balance`/`convert_to_erc20` causes unbacked over-minting or fund loss on cross-chain HFT transfers - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token`'s decimal-conversion helpers only handle the case where the ERC20 side has equal-or-more decimal precision than the local Substrate asset. When a registered asset has a local decimal precision *higher* than its configured `erc_decimals` (a supported, non-malicious configuration per the pallet's generic `AssetRegistration`/`Precisions` design), the scaling factor collapses to `10^0 = 1` via `saturating_sub`, so no rescaling happens at all. Depending on transfer direction this either mints far fewer tokens than owed (fund loss) or, more critically, causes the destination ERC20 contract to mint an amount inflated by `10^(local_decimals - erc_decimals)` — an unbacked mint, analogous to the reported decimal-handling defect that inflated reward/asset calculations by a missing scaling factor.

### Finding Description
The conversion helpers are: [1](#0-0) [2](#0-1) 

`convert_to_balance` divides the incoming ERC20 `U256` amount by `10^(erc_decimals.saturating_sub(local_decimals))`, and `convert_to_erc20` multiplies the outbound local balance by the same `saturating_sub`-derived factor. Both assume `erc_decimals >= local_decimals`. If instead `local_decimals > erc_decimals` (e.g. a locally registered asset with 18 decimals bridged to a remote ERC20 representation configured with 6 decimals — a legitimate configuration, since the pallet's `Precisions` map and `AssetRegistration.precision` are meant to support arbitrary per-chain decimal precision, as documented for the sibling token-gateway pallet's DOT 10-vs-18-decimal example), `saturating_sub` yields `0`, the scale factor is `1`, and **no rescaling occurs at all** in either direction.

This helper is used directly in the inbound accept path: [3](#0-2) 

and in the outbound send path (via `convert_to_erc20`, referenced in `modules/pallets/hyper-fungible-token/src/lib.rs`, not fully inspected but confirmed via grep matches), which burns the local asset and encodes the abi `Message.amount` field dispatched to the remote HFT/`HyperFungibleToken.sol` contract that will call `_mint(beneficiary, message.amount)` verbatim.

Consequences:
- **Inbound** (`on_accept`/`on_timeout`, ERC20→Substrate): when `erc_decimals < local_decimals`, the raw ERC20 amount is minted/transferred unscaled into the higher-precision local asset, so the beneficiary receives an amount smaller by `10^(local_decimals - erc_decimals)` than intended (silent fund loss for the user, and stranded escrow on the sending side).
- **Outbound** (send/burn, Substrate→ERC20): when `local_decimals > erc_decimals`, the raw local balance (already scaled for 18 decimals) is encoded unscaled into `Message.amount` and delivered to a remote HFT contract whose `decimals()`/precision is lower (e.g. 6). The remote contract's `_mint` call mints `amount` raw units under its own 6-decimal accounting, producing `10^(local_decimals - erc_decimals)` times more tokens than were burned — an unbacked mint that permanently breaks the 1:1 backing invariant the HFT pallet's escrow model depends on.

This is the same class of bug as the reported `DSRStrategy.getRewards` issue: a decimal-scaling term is silently dropped (there, a missing `/1e18`; here, a `saturating_sub` that silently degenerates to a no-op scale factor of 1 instead of switching to multiplication for the reverse decimal relationship), producing values off by a power-of-ten factor that directly corrupts on-chain token accounting.

### Impact Explanation
On the outbound path this permits unbacked minting of a bridged ERC20 token on the destination chain whenever a registered asset's local decimals exceed its configured ERC20 precision — a direct, permanent, protocol-level over-issuance of tokens with no compensating burn, reachable by any user simply calling the pallet's normal bridge/`send` extrinsic once such an asset exists. This meets the "unbacked mint" / "concrete theft" bar. Even the inbound-only fund-loss direction (users receiving far fewer tokens than sent) is a High-severity accounting defect for any affected asset pairing.

### Likelihood Explanation
This does not require a malicious admin — `precision`/`Precisions` are ordinary asset-registration parameters supported by the pallet's design for cross-chain decimal normalization (explicitly documented as necessary because different chains use different decimal precisions for the "same" asset, e.g. DOT's 10 vs 18 decimals). Any asset registered with local decimals greater than its remote ERC20 decimals — a realistic and encouraged configuration — triggers the bug on every ordinary transfer, requiring no privileged or adversarial action beyond normal usage.

### Recommendation
Fix `convert_to_balance` and `convert_to_erc20` in `modules/pallets/hyper-fungible-token/src/impls.rs` to handle both directions explicitly instead of relying on `saturating_sub` collapsing to zero:

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256,
    erc_decimals: u8,
    local_decimals: u8,
) -> Result<B, B::Err> {
    let dec_str = if erc_decimals >= local_decimals {
        (value / U256::from(10u128.pow((erc_decimals - local_decimals) as u32))).to_string()
    } else {
        (value * U256::from(10u128.pow((local_decimals - erc_decimals) as u32))).to_string()
    };
    dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```
Add regression tests in `modules/pallets/testsuite/src/tests/pallet_hyper_fungible_token.rs` covering `local_decimals > erc_decimals` for both `on_accept`/`on_timeout` and the outbound send path, asserting minted/burned amounts are correctly scaled in both directions.

### Proof of Concept
1. Register an asset `X` with `local_decimals = 18` (native Substrate asset) and configure `Precisions::<T>::insert(X, remote_contract, 6)` (remote ERC20 representation with 6 decimals) — a supported configuration.
2. A user calls the pallet's send/bridge extrinsic to transfer `1 X` (raw local amount `1_000_000_000_000_000_000`, 18 decimals).
3. `convert_to_erc20(1_000_000_000_000_000_000, erc_decimals=6, local_decimals=18)` computes `saturating_sub(6,18) = 0`, so the result is `1_000_000_000_000_000_000` unscaled, encoded into `Message.amount`.
4. The relayer delivers this to `HyperFungibleToken.sol`'s `onAccept`, which calls `_mint(beneficiary, 1_000_000_000_000_000_000)` on a token with 6 decimals — minting `1,000,000,000,000` (1 trillion) tokens instead of the intended `1_000_000` (1 token in 6-decimal units), a 10^12 unbacked over-mint for every unit burned on the source chain.
