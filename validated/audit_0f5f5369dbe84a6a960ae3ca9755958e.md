### Title
Tokens pushed to the controller during `flash_position` that are neither declared collateral nor refund-listed are permanently stuck — ([File: contracts/controller/src/strategies/flash_position.rs](contracts/controller/src/strategies/flash_position.rs))

### Summary
The bug class from the external report — value sent alongside a call that the contract neither credits nor returns — maps directly onto `controller.flash_position`. During the receiver callback, any token transferred to the controller is only processed if its asset appears in the declared `collaterals` list or in `refund_assets`. A pushed asset that is in neither list is left in the controller's balance with no credit, no refund, and no sweep endpoint, permanently freezing the funds.

### Finding Description
`process_flash_position` mints debt to the account, forwards the measured receipt to a caller-chosen `receiver`, and invokes `execute_flash_position` on it. After the callback returns, the controller settles collateral only through `collect_collateral_deposits`, which snapshots and measures balance deltas exclusively for the assets in the declared `collaterals` vector:

```rust
let baseline = before.get(hub_asset.asset.clone())...;
let delta = balance_delta_since(env, &hub_asset.asset, controller, baseline);
```

Only positive deltas on declared collateral assets are deposited (`flash_position.rs:325-353`), and only positive deltas on `refund_assets` are returned to the caller. Any other token the receiver transfers to the controller inside the callback — including the debt token itself when it is not refund-listed — simply remains in the controller's balance. The protocol explicitly documents this gap: "Undeclared callback assets receive neither credit nor refunds. There is no controller sweep endpoint" (`docs/reference/endpoints.md:86`), and ADR-0020 acknowledges returned debt "can remain uncredited" (`docs/explanation/decisions.md:259`).

Unlike the repayment, liquidation, recapitalization, and router-swap paths — which all measure and refund excess (`refund_controller_balance_delta` in `payments.rs:41-52`, `swap_tokens` leftover refund in `strategies/swap.rs:49-52`, pool-side overpayment refunds in `ops/repay`) — the flash-position path has no generic catch-all refund for assets outside the two declared lists.

### Impact Explanation
Permanent freezing of funds: any token amount transferred to the controller during the callback for an asset absent from both `collaterals` and `refund_assets` is locked in the controller forever. No entrypoint (including `claim_revenue`, which forwards only measured revenue receipts to the accumulator) can recover arbitrary stranded controller balances. This mirrors the original report's impact — the contract holds user value it has no mechanism to return.

### Likelihood Explanation
Medium-low. It requires the caller's own receiver contract (or a buggy integration) to push an undeclared token. However, realistic integrator mistakes trigger it: pushing leftover debt tokens back to the controller expecting auto-repayment (explicitly unsupported — "Refunding unused debt tokens does not repay the minted debt", `skills/xoxno-lending-contracts/flash-loans.md:135`), pushing collateral in a token that resolves to a different market than declared, or omitting a refund asset for a multi-leg swap output. A third party can also grief-lock dust, though that is their own funds.

### Recommendation
Either (a) after collecting declared collateral deposits and refunds, sweep any remaining positive balance delta on all assets the receiver was observed to push (trackable via a post-callback snapshot of touched assets), refunding them to `caller`; or (b) at minimum, extend `refund_assets` handling so the debt token is refunded by default when undeclared, and add a governance-gated recovery entrypoint for stranded balances. If the current behavior is retained intentionally, surface it loudly in the `flash_position` doc so integrators never push undeclared tokens.

### Proof of Concept
1. Alice deploys a flash-position receiver whose `execute_flash_position` transfers `collateral_amount` of the declared collateral **plus** `X` units of an extra token `T` (e.g., leftover output of her own swap) to the controller. The harness receiver already demonstrates this shape via `FlashPositionMode::Undeclared` (`tests/test-harness/src/receivers/flash_position.rs:161-177`).
2. Alice calls `controller.flash_position(caller=alice, account_id=0, spoke_id, debt=HubAssetKey{hub,USDC}, amount, receiver, collaterals=[(XLM, min)], data, refund_assets=[])` — `T` is in neither list.
3. The call succeeds: `collect_collateral_deposits` only checks XLM deltas (`flash_position.rs:331-345`); `T` is never measured or moved.
4. `token::Client::new(env, &T).balance(&controller)` retains `X` permanently; Alice's account is not credited and no refund leg returns `T`. The existing test `test_flash_position_refunds_undeclared_push` (`tests/test-harness/tests/strategy/flash_position.rs:237-268`) confirms the inverse — only a refund-listed asset comes back; without the listing the push strands. The live-flow test seeds the controller with donated balances specifically to prove they are never swept (`tests/integration/flows/flash_position.sh:354-372`).
