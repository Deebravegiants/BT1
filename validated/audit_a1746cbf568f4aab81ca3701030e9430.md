## Finding: Solver-side pricing relies on unmitigated single-block Uniswap V4 spot price, exploitable via flash-loan manipulation

### Title
Flash-loan-manipulable spot price oracle drains intent solver funds via `UniswapV4FundingPlanner` pool pricing - (File: `sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts`)

### Summary
Simplex (the reference intent-solver/filler implementation) prices "venue" pairs that lack static bid/ask curves directly from the current `sqrtPriceX96`/tick of a configured Uniswap V4 pool, with no TWAP and no execution-size/impact adjustment. An attacker who is an unprivileged order placer can flash-loan-swap against that same pool to move its spot price within one block, then place (or have a colluding party place) an intent order sized against the manipulated quote, causing the solver to release output tokens (or accept escrowed inputs) at the manipulated rate and extract value from the solver's own funds — mirroring the flash-loan attack pattern described in the DD Coin incident.

### Finding Description
`UniswapV4FundingPlanner.getExoticTokenPrice()` reads the pool's current price directly from on-chain state and returns it as the USD price used for the trade: [1](#0-0) 

The underlying price comes from a single, instantaneous `getSlot0` read (spot `sqrtPriceX96`/tick), refreshed on demand right before pricing, with no averaging window: [2](#0-1) 

This spot price feeds `FXFiller.resolveLegRates()`, which computes the fill rate directly as `1 / venueUsd` for any "curveless" pair whose `token0` is a USD stablecoin — i.e., the venue price is used verbatim as the execution rate, extended linearly across the whole order size with no depth/impact term: [3](#0-2) 

The only defense is `checkPriceGuard()`, which compares the live quote against a **static** `referencePrice`/`maxDeviationBps` — it bounds deviation from a fixed number, not execution cost, and is optional (both fields can be left unset to leave the chain "unguarded"): [4](#0-3) 

The project's own internal documentation acknowledges this gap directly: the pool acts as the sole price oracle, the fee tier is read but never applied to the price, there is no size/impact term, and `checkPriceGuard` only checks static deviation, not execution cost: [5](#0-4) 

The public docs likewise state plainly that "Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote," and that the guard fields are optional ("omit both to leave the chain unguarded"): [6](#0-5) 

Because Uniswap V4 pools have no built-in manipulation resistance for a single spot read (unlike a TWAP oracle), an attacker can:
1. Flash-loan a large amount of the stablecoin or exotic token.
2. Swap against the exact pool configured in `[vault.uniswapV4].positions` to move `sqrtPriceX96` sharply within the same block.
3. Place (or immediately trigger fill evaluation of) an intent order on the Intent Gateway sized to `maxOrderSize`, priced by the now-manipulated `getExoticTokenPrice()`/`resolveLegRates()` computation.
4. If no guard is configured, or the manipulated price still falls within `maxDeviationBps` of a stale/misconfigured static reference, the solver fills at the bad rate, releasing more output value than the escrowed input is worth.
5. Repay the flash loan and pocket the difference, extracting solver-owned liquidity (either wallet balance or withdrawn Uniswap V4 LP position funds).

This is triggerable entirely by an unprivileged intent placer/solver counterpart interacting with the public `IntentGateway`/Simplex fill flow — no privileged role is required.

### Impact Explanation
A successful attack drains real value from the solver's treasury/LP position funds, which back user fills across the Intent Gateway. Since price guards are optional and configured per-deployment (and even when configured, only bound deviation from a static number rather than sanity-checking manipulation risk or execution cost), a misconfigured or unguarded solver deployment can suffer concrete, repeatable theft proportional to `maxOrderSize` per manipulated fill. This matches the "concrete theft ... of funds" impact bar, scoped specifically to the "intent solver" actor called out as in-scope.

### Likelihood Explanation
Likelihood is Medium-to-High for solver operators who configure venue pricing without setting `referencePrice`/`maxDeviationBps` (explicitly supported, per the docs and `filler-config-example.toml`), or who set an insufficiently tight `maxDeviationBps`. Flash-loan pool manipulation on a single Uniswap V4 pool is a well-established, low-cost, single-transaction attack primitive, and the SECURITY.md explicitly does **not** exclude "oracle manipulation/flash-loan attacks": [7](#0-6) 

### Recommendation
- Require `referencePrice`/`maxDeviationBps` (or an equivalent guard) to be mandatory, not optional, whenever `[vault.uniswapV4]` curveless pricing is enabled, and fail validation otherwise.
- Replace or supplement the single-block spot read (`getSlot0`) with a TWAP/observation-based price, or cross-check against an independent oracle before deriving `venueUsd`.
- Incorporate a size/impact term into `resolveLegRates`/`computeLegPolicyOutput` rather than extending the raw mid price linearly across the whole notional.
- Consider bounding per-order or per-block fill size against pool liquidity depth to limit the profitability of single-block manipulation.

### Proof of Concept
Conceptual PoC (solver-side, off-chain business logic — no protocol contract bug, but a design flaw enabling fund loss):
1. Deploy/observe a Simplex solver configured with `[vault.uniswapV4]` for a `USDC/EXOTIC` pair, no `referencePrice`/`maxDeviationBps` set (supported per `filler-config-example.toml` comments).
2. Attacker takes a flash loan of `USDC` (or `EXOTIC`), swaps a large amount through the exact pool at `positions[].tokenId`'s pool address, shifting `sqrtPriceX96` significantly in one block.
3. Attacker (or accomplice) immediately places an Intent Gateway order sized near `maxOrderSize` for that pair.
4. Solver's `FXFiller.resolveLegRates` → `getVenueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice` reads the now-manipulated spot price (`UniswapV4LiquidityState.refresh`, `computeDirectPoolPriceUsd`), and `canFill`/fill execution proceeds at the bad rate.
5. Attacker repays the flash loan and retains the mispriced arbitrage against the solver's own inventory.

```typescript
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}
```

```typescript
	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}
```

```text
## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
```
