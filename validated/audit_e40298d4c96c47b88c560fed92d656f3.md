## Title
Webhook `shop` (and `topic`/`webhook-id`) identity is not covered by the HMAC signature, allowing cross-tenant shop spoofing of otherwise-valid webhook payloads - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw HTTP body, while the `shop` identity that the library hands to the app's webhook handler is read from the `X-Shopify-Shop-Domain` HTTP header, which is completely outside the HMAC signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and the HMAC digest for verification is extracted from the `hmac-sha256` header: [1](#0-0) 

`Registry.process` verifies the request using `Utils::HmacValidator.validate(request)`, which only checks `HMAC(raw_body, api_secret_key) == hmac header`: [2](#0-1) 

Once the HMAC check passes, `Registry.process` builds the `WebhookMetadata` handed to the app's handler directly from unauthenticated headers, including `request.shop` (`X-Shopify-Shop-Domain`) and `request.topic`: [3](#0-2) 

The binding the app relies on is: *"the `shop` used to attribute/store this webhook payload" == "the shop that Shopify cryptographically vouched for when it computed the HMAC."* Because `to_signable_string` only covers `@raw_body`, this equality does not hold — `shop` is parsed from a header that is verified by nothing. Any attacker who can produce one validly-signed request body for a given topic (e.g., a merchant who installs the app on their own store and thus legitimately receives real, correctly-signed webhooks addressed to their own shop, since all shops using the app share the same `api_secret_key`) can resend that same `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting an arbitrary value in the `X-Shopify-Shop-Domain` header. `HmacValidator.validate` still succeeds (it never inspects `shop`), and `WebhookMetadata.shop` is populated with the attacker-chosen value.

### Impact Explanation
This breaks the tenant-isolation guarantee the HMAC check is supposed to provide. An app that uses `request.shop`/`WebhookMetadata#shop` (exactly as illustrated in this library's own `Registry.process` flow) to decide which merchant's records to update, which access token/session to load, or which tenant's data to write, can be made to process an attacker-controlled shop identifier for a genuinely-signed payload — i.e., cross-tenant data confusion/injection. This satisfies the "cross-tenant access" high-impact criterion.

### Likelihood Explanation
Reachable by any unprivileged internet user who can install the app on a shop they control (a normal, unprivileged path for any Shopify app) and can send arbitrary HTTP requests to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required — only reuse of a webhook delivery that Shopify itself already sent them.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`, `api_version`) into the value that is authenticated, e.g. incorporate the `shop-domain`/`topic` headers into `to_signable_string`, or explicitly cross-check `request.shop` against the shop associated with the session/install record the app expects before trusting it, rather than trusting the header verbatim once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and configures a webhook subscription (e.g., `orders/create`).
2. Shopify sends a legitimate webhook to the app: raw body `B` with headers `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create` — `H = HMAC-SHA256(B, api_secret_key)`.
3. Attacker captures `B` and `H`, then sends a forged request to the same app webhook endpoint with the same body `B` and header `X-Shopify-Hmac-Sha256: H`, but `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which only checks `HMAC(B, api_secret_key) == H` — passes.
5. `WebhookMetadata.new(shop: "victim.myshopify.com", body: JSON.parse(B), ...)` is delivered to the app's handler, which now treats attacker-supplied order data as belonging to `victim.myshopify.com`.
