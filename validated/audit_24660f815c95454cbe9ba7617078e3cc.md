### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant shop spoofing in `ShopifyAPI::Webhooks::Registry.process` - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but the `shop` value that is handed to the app's `WebhookHandler` (and used by apps to select tenant-scoped data/session) is read directly from the `X-Shopify-Shop-Domain` header, which is never included in the signed material.

### Finding Description
The documented processing flow is: build a `ShopifyAPI::Webhooks::Request` from `raw_body` and `headers`, then call `ShopifyAPI::Webhooks::Registry.process` [1](#0-0) .

`Registry.process` validates authenticity using only `Utils::HmacValidator.validate(request)` before dispatching to the app handler: [2](#0-1) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac`: [3](#0-2) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, while `shop` is read verbatim from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic linkage to the HMAC at all: [4](#0-3) 

The un-authenticated `shop` value is then passed straight into `WebhookMetadata`, which is the primary tenant identifier the gem hands to the app's handler: [5](#0-4) [6](#0-5) 

The identity binding that should hold is: `hmac == HMAC(shared_secret, raw_body ‖ shop)` (or equivalent, binding the tenant claim into the signed material). Instead, the binding actually enforced is only `hmac == HMAC(shared_secret, raw_body)`, so `shop` is a free variable that the caller can set to anything while keeping a valid, previously-observed `(raw_body, hmac)` pair.

Because Shopify signs webhooks with a single `client_secret` shared across all shops/tenants of an app, any actor who has legitimately received one webhook for their own store (or has otherwise obtained one valid `(body, hmac)` pair — no `api_secret_key` needed) can replay that exact body+HMAC to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. `HmacValidator.validate` will still return `true` because it never inspects `shop`, and `Registry.process` will hand the forged shop identity straight to the app's handler as `WebhookMetadata#shop`, which the gem's own documentation instructs apps to use directly for tenant-scoped actions (e.g. `perform_later(shop_domain: data.shop, ...)`) [7](#0-6) .

### Impact Explanation
This breaks the tenant-authentication boundary that `Registry.process` is supposed to provide: an unprivileged actor with no access token, no `api_secret_key`, and no privileged account can cause the gem to assert that a webhook payload originated from an arbitrary target shop. Any host application that relies on the gem's HMAC verification to trust `WebhookMetadata#shop` (exactly as the gem's own docs instruct) is exposed to cross-tenant data confusion/injection — e.g., a forged `orders/create`, `customers/redact`, or `shop/redact` event attributed to a victim shop, potentially causing the app to perform destructive or data-disclosing actions scoped to a shop the attacker doesn't operate. This matches the "cross-tenant access" criterion.

### Likelihood Explanation
Exploitation requires only: (1) the ability to POST directly to the app's public webhook endpoint (which is by definition internet-reachable), and (2) one legitimately-signed `(raw_body, hmac)` pair, which an attacker can obtain by installing the target app on their own store (a normal, unprivileged action) and capturing a webhook Shopify sends them. No secrets, tokens, or privileged access are required beyond that. The verification code path is exactly the one documented for all webhook consumers, so this is broadly reachable rather than a corner case.

### Recommendation
Bind the shop identity into the authenticated material before trusting it: e.g., require host apps to independently verify that `request.shop` corresponds to a shop with an active installation/session known to the app (defense already possible today), and/or have `HmacValidator`/`Webhooks::Request` fail closed unless the caller supplies an expected shop to compare against, or include the shop domain in `to_signable_string`/verification so a mismatch is cryptographically detectable rather than left entirely to the host application's own additional checks.

### Proof of Concept
1. Attacker installs the target Shopify app on their own development/test store `attacker.myshopify.com`, and configures a webhook subscription (or triggers a mandatory one) to receive one webhook, e.g. `orders/create`, capturing the exact `raw_body` and the `X-Shopify-Hmac-Sha256` header Shopify sent.
2. Attacker POSTs the same `raw_body` and `X-Shopify-Hmac-Sha256` to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. The app calls `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body:, headers:))` as documented.
4. `Utils::HmacValidator.validate` recomputes HMAC over `raw_body` only [8](#0-7)  and it matches, since `raw_body` and `hmac` are unmodified from the legitimate delivery.
5. `Registry.process` invokes the app handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)` [5](#0-4) , even though the payload was never sent by or for `victim-shop.myshopify.com`.

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```

        sig { params(request: Request).void }
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
