### Title
Webhook shop identity is trusted from an unsigned header while the HMAC only covers the raw body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates a webhook by validating the HMAC over the raw body only, but the `shop` (and `topic`/`webhook_id`) values that are handed to the host application's handler are read from unsigned HTTP headers. This breaks the identity binding: `hmac_valid(raw_body) == true` does not imply `shop_header == shop_that_actually_generated(raw_body)`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate_signature` computes and compares the signature strictly against that signable string: [2](#0-1) 

Meanwhile, `Request#shop` (and `#topic`, `#webhook_id`, `#api_version`) is read directly from the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header, which is never part of the signed payload: [3](#0-2) 

`Registry.process` only checks the body HMAC before dispatching to the handler using the unauthenticated `shop` value: [4](#0-3) 

That value flows straight into `WebhookMetadata`, which is the only tenant identifier the host application's `WebhookHandler#handle` receives: [5](#0-4) 

Because the HMAC covers `raw_body` alone, any request with a `(raw_body, hmac)` pair that is valid for shop A remains HMAC-valid if replayed with the `shop-domain` header changed to shop B. The gem provides no binding between the authenticated bytes and the shop identity it reports to the handler, so `shop_header_trusted_by_registry == shop_that_the_hmac_actually_authenticates` does not hold.

### Impact Explanation
An entity that can obtain one genuine, validly-signed webhook body for a shop it controls (e.g., a merchant who installed the app, capturing traffic sent to their own registered endpoint) can replay that same `(body, hmac)` pair to the app's webhook endpoint with the `shop-domain` header swapped to a different shop. `Utils::HmacValidator.validate` still returns `true` because it never inspects the header, so `Registry.process` dispatches the forged request to the handler tagged with an attacker-chosen shop identity. If the host application uses `WebhookMetadata#shop` to select which tenant's data/session to act on (the gem's own `SessionUtils.offline_session_id(shop)` pattern shows `shop` is treated as the tenant key throughout the library), this enables cross-tenant data corruption or triggering of tenant-scoped side effects (e.g. `shop/redact`, `app/uninstalled`-style handling) attributed to the wrong merchant.

### Likelihood Explanation
Exploitation requires the attacker to already possess one legitimately-signed webhook for some shop (achievable by installing the app on their own store and capturing/replaying traffic to the same webhook endpoint) — no `api_secret_key` or victim credentials are required, only the ability to send an HTTP POST with a modified header. This is a plausible, low-effort attack surface for any external party able to install the app.

### Recommendation
Either include the shop domain (and topic) inside the signed payload the gem verifies, or require the host application to fetch/authorize the shop independently of the header before trusting `WebhookMetadata#shop`. At minimum, document prominently that `Request#shop`/`#topic` are unauthenticated by the HMAC check and must not be used as the sole tenant-identity source without additional verification (e.g., cross-checking against a topic/shop pair recorded when the webhook was registered).

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and registers a webhook endpoint they control.
2. Shopify sends a legitimate webhook: body `B`, header `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: HMAC(secret, B)`.
3. Attacker replays the exact same body `B` and HMAC header to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)`, which still matches (the header was never part of the signed string), so `Registry.process` proceeds and calls `handler.handle(data: WebhookMetadata.new(shop: "victim.myshopify.com", ...))`, `AYontt/shopify-api-ruby--021` `lib/shopify_api/webhooks/registry.rb:188-200`.
5. Any host-app logic keyed on `WebhookMetadata#shop` executes as if the event genuinely originated from `victim.myshopify.com`.
