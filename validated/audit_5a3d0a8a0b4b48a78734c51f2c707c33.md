### Title
`EvmHost` uses a single global `challengePeriod` for all counterparty state machines instead of per-state-machine values - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost` stores a single `challengePeriod` value in `HostParams` that is applied uniformly to every counterparty state machine whose state commitments are relayed to it, whereas the Substrate/`pallet-ismp` side of the protocol (and the core `ConsensusClient` design) explicitly supports a *per-state-machine* challenge period. This is directly analogous to the `ORACLE_FRESHNESS_THRESHOLD` bug: a single safety-margin constant is reused for heterogeneous counterparties that actually require different values.

### Finding Description
On the Substrate side, challenge periods are correctly modeled per `StateMachineId`: [1](#0-0) 
and are stored/retrieved keyed by state machine: [2](#0-1) 
Consensus client creation and updates also propagate a `BTreeMap<StateMachine, u64>` of challenge periods, one per counterparty state machine, confirming the intended design that different state machines require distinct finality/challenge windows: [3](#0-2) [4](#0-3) 

In contrast, `EvmHost.sol` stores `challengePeriod` as a single scalar in `HostParams`, applied to all state machines whose commitments the host tracks, with no per-`StateMachine` differentiation: [5](#0-4) 
The corresponding relayer/SDK query path confirms `challengePeriod()` is a single, argument-less getter on the EVM host (unlike `queryChallengePeriod(id)` used against Substrate providers, which is genuinely per-`StateMachineId`): [6](#0-5) [7](#0-6) 
The generic SDK helper `waitForChallengePeriod` even takes `stateMachineHeight.id` and calls `chain.challengePeriod(stateMachineHeight.id)`, implying the abstraction expects per-state-machine values, but on EVM hosts this parameter is effectively ignored because the underlying contract getter is global: [8](#0-7) 

### Impact Explanation
Different counterparty state machines whitelisted on a single `EvmHost` (e.g., different L2 rollups, different consensus-client-backed chains such as BEEFY/sync-committee/Tendermint sources) have different finality guarantees and reorg/long-range-attack risk profiles. Using one static `challengePeriod` for all of them means chains that need a longer safety window (slower finality, weaker fraud-proof windows, more centralized sequencers) are under-protected: their state commitments become actionable (membership/non-membership proofs accepted, requests/responses dispatched) as soon as the same short global window elapses, even though that window is insufficient for that specific state machine's actual finality/challenge requirements. This can permit processing of requests, responses, or token/asset actions based on state commitments that could still be reverted or that originated from a byzantine/forked view of the counterparty chain, before the same security margin required for other more risk-sensitive chains has actually elapsed — a direct route to accepting an unsound/forged state commitment and acting on it (e.g., unauthorized app dispatch or minting based on invalid proofs).

### Likelihood Explanation
Any relayer submitting a state commitment update and then a subsequent message with a state proof, once the shared `challengePeriod` elapses, can trigger processing for every whitelisted state machine equally, regardless of that specific chain's actual required challenge window. This requires no privileged access — it is triggered by ordinary relaying of consensus and message proofs — and becomes exploitable purely because of a governance/deployment misconfiguration risk inherent in the single-value design (the value must be conservatively set to the maximum required across all onboarded state machines, and if not, weaker chains are silently under-protected).

### Recommendation
Store and enforce `challengePeriod` per `StateMachine` (or per `StateMachineId`) in `EvmHost`/`HostParams`, mirroring the `pallet-ismp` design (`ChallengePeriod::<T>` keyed by `StateMachineId`, `challenge_period(&self, state_machine: StateMachineId)`). Update `HandlerV2.sol` and the relayer/SDK challenge-period query paths (`queryChallengePeriod`, `waitForChallengePeriod`) to always look up the specific counterparty's challenge period rather than relying on the host-wide EVM getter that discards the state-machine identifier.

### Proof of Concept
1. Deploy `EvmHost` with `stateMachines = [ChainA, ChainB]` and a single `challengePeriod = 30 minutes` in `HostParams`, as set in `setHostParams`. [9](#0-8) 
2. Assume ChainA requires only a 5-minute challenge window (fast finality) while ChainB, due to its consensus client / reorg characteristics, actually requires 24 hours to be safely considered final.
3. Because `EvmHost.challengePeriod()` returns the same 30-minute value for both, a relayer can submit a state commitment update for ChainB and, only 30 minutes later, submit a message (request/response) with a state proof against that commitment through `HandlerV2`; the host will treat the challenge period as elapsed and process it — well before ChainB's actual finality window has passed, exposing the bridge to processing requests derived from a state commitment that could still be reverted or was produced under a byzantine/forked view.
4. This mirrors the reported bug pattern of using one fixed freshness/safety constant (`ORACLE_FRESHNESS_THRESHOLD`) for heterogeneous sources instead of the source-specific value that is required for it to be meaningful.
