### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop-identity spoofing in `ShopifyAPI::Webhooks::Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` verifies nothing about the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. `Registry.process` treats a passing HMAC check as proof that the *entire request*, including `request.shop`, is an authentic Shopify webhook, and forwards `request.shop` straight to the app's handler as the identity of the merchant the payload belongs to.

### Finding Description
The verification chain is: [1](#0-0) [2](#0-1) 

`to_signable_string` only returns `@raw_body`, while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated HTTP headers via `shopify_header`: [3](#0-2) [4](#0-3) 

`HmacValidator.validate` only compares the HMAC against `verifiable_query.to_signable_string`, i.e. only the body bytes are authenticated: [5](#0-4) 

The identity binding that should hold is: `shop that produced the signed body == shop attributed to the webhook by the handler`. In this implementation that equality is never checked — the equality actually enforced is only `HMAC(secret, raw_body) == received_hmac`, which is independent of the `shop-domain` header. `Registry.process` then hands `request.shop` (unauthenticated) to the handler as the shop the data belongs to:

```ruby
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
```

Critically, Shopify signs webhooks with the **app's `client_secret`**, which is the same secret for every shop that installs the app — it is not a per-shop secret. This means any merchant who installs the app on their own store can trigger genuine, correctly-signed webhook deliveries (e.g. `orders/create`) whose body they substantially control (order fields, product titles, notes, metafields, etc., depending on the topic and registered `fields`). Since the HMAC only covers the raw body, and the `x-shopify-shop-domain` header is not part of the signed payload, that attacker-obtained `(body, hmac)` pair remains valid for *any* shop-domain header value. They can then replay the captured body+HMAC to the app's own webhook endpoint (which is a public, internet-reachable route by design) while swapping in a victim shop's domain in `X-Shopify-Shop-Domain`.

Because `Utils::HmacValidator.validate` returns true (the body/HMAC pair is genuinely valid), `Registry.process` proceeds and calls the handler with `data.shop == victim-shop.myshopify.com` and attacker-chosen `data.body`. Any host application that uses `data.shop` to look up per-tenant records (a very common, and doc-recommended, pattern — see `docs/usage/webhooks.md` sample handler which does `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) will process attacker-controlled data under the identity of a shop the attacker does not control.

### Impact Explanation
This breaks the tenant-isolation boundary the gem is expected to enforce: `Registry.process`'s only job besides routing is to assert "this webhook truly originates from the claimed shop." Instead it only asserts "this body was HMAC-signed with the app's secret" and silently trusts the shop header. This enables cross-tenant data injection/corruption — an attacker-controlled webhook payload can be attributed to a victim merchant's shop, letting a malicious (but legitimately installed) tenant inject forged webhook events for other tenants (e.g. forged `orders/create`, `products/update`, or GDPR `customers/redact` events) into any application built on this gem's documented API. This matches the Critical "cross-tenant access" impact class, since the underlying flaw is a broken identity-binding equality in the library itself (`to_signable_string` excluding the shop header from the signed set), not merely a host-app oversight.

### Likelihood Explanation
Likelihood is high for any developer following the gem's own documented usage: the doc's canonical webhook handler example uses `data.shop` directly as the tenant key without any additional cross-check, and the gem provides no API to verify shop attribution beyond the plain HMAC check. Any actor able to install the app on a shop they control (i.e., any ordinary merchant/unprivileged internet user who installs a public app) can obtain valid (body, HMAC) pairs for arbitrary registered topics without needing the `client_secret`, `api_secret_key`, or any other credential.

### Recommendation
Bind the shop identity into the verified signable data, or require and check that the `x-shopify-shop-domain` header corresponds to a shop actually known to have the registered webhook/session before invoking the handler. At minimum, document and/or enforce that host applications must cross-reference `data.shop` against known/installed shops before trusting it, and consider surfacing a `Registry.process` variant that accepts an expected shop and rejects mismatches.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, completing OAuth and registering, e.g., the `orders/create` webhook topic (this is a normal, unprivileged installation flow).
2. Attacker creates an order on their own store with attacker-controlled fields (note, line item titles, etc., depending on registered `fields`), triggering Shopify to POST a legitimately signed `orders/create` webhook to the app's webhook endpoint:
   - `X-Shopify-Hmac-Sha256: <valid HMAC over raw_body, computed with app's client_secret>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - `raw_body: <attacker-controlled JSON>`
3. Attacker captures `raw_body` and the `X-Shopify-Hmac-Sha256` value from this legitimate delivery (e.g., via a proxy they control, or by re-deriving the same body server-side and replaying an intercepted delivery).
4. Attacker sends a forged HTTP POST directly to the app's public webhook route with the same `raw_body` and `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses headers, `Utils::HmacValidator.validate` succeeds (HMAC only covers `raw_body`, unaffected by the header change) at `lib/shopify_api/webhooks/registry.rb:190`.
6. `handler.handle` is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"` and attacker-controlled `body`, even though the request never originated from Shopify on behalf of `victim-shop`.
