### Title
Ambiguous status matching in `describeWithdrawal` misreports destination tx hash for batch withdrawals of the same asset - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` and the analogous POA-completion logic in `internal-utils` resolve withdrawal status by matching on `assetId`/`near_token_id` alone, not by index or amount. When a batch (`signAndSendWithdrawalIntent` with an array of `withdrawalParams`) contains more than one withdrawal of the same token in a single NEAR transaction, the wrong withdrawal's status/tx hash can be reported for a given index.

### Finding Description
`describeWithdrawal` calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` which does `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)` [1](#0-0) , and the matching helper itself is documented as only distinguishing by asset id [2](#0-1) . The equality this breaks is: "the withdrawal identifier (index within the batch transaction) the caller is asking about" vs "the withdrawal record actually returned by the bridge for that identifier." If two `WithdrawalParams` entries in the same batch share `assetId` (e.g., two USDT withdrawals to different destination addresses in one `signAndSendWithdrawalIntent` batch call, as documented in the SDK's batch-withdrawal feature [3](#0-2) ), `find()` returns the first array element matching the asset id regardless of which logical withdrawal (`index`) is being queried, so both `describeWithdrawal` calls for index 0 and index 1 can resolve to the same underlying record and its `transfer_tx_hash`.

This is the same root-cause code path exercised (and asserted as intentional) by the "matches withdrawal by assetId, not by index" test [4](#0-3) , and it is explicitly acknowledged as an unhandled multi-withdrawal-of-same-token case in the code comment. The `internal-utils` POA completion helper has the identical limitation for single-withdrawal waits, matching only by `assetId` from a list of withdrawals [5](#0-4) .

### Impact Explanation
An integrator polling withdrawal status per-index in a batch (`watchWithdrawal`/`waitForSettlement` flows built on `describeWithdrawal`, see `withdrawal-watcher.ts` [6](#0-5) ) can be told that withdrawal #1 (to address A) is "completed" with a `txHash` that actually belongs to withdrawal #0 (to address B), or vice versa, whenever the POA bridge processes two same-asset withdrawals from one NEAR transaction out of submission order. This is a status/hash misreport that could cause an integrator to mark the wrong leg of a batch as settled (credit/refund logic keyed off the returned `txHash`), matching the "status or hash misreport making an integrator credit or refund twice" High-impact category.

### Likelihood Explanation
Likelihood is limited: it requires (1) using the batch-withdrawal API with two or more withdrawals of the *same* `assetId` in one call, and (2) the POA bridge's indexer returning them in a different order than requested, or genuinely being ambiguous about which physical transfer corresponds to which logical request. This is not attacker-controlled cross-user manipulation — it's an internal correctness/ordering gap the SDK authors already flagged in comments as a known, unresolved limitation, and no malicious actor input is required or blocked here. The bug is a reachable code defect but its triggering condition (concurrent same-token batch withdrawals in one intent) is narrow and not clearly attacker-triggerable to redirect funds to an unauthorized destination — it is a status-attribution defect within the SDK, not a fund-misdelivery bug, since the actual `ft_withdraw`/bridge intents themselves still carry correct per-item destination addresses and amounts.

### Recommendation
Disambiguate same-asset withdrawals within a batch by additionally matching on `amount` (and preferably `destinationAddress`) rather than `assetId` alone, or track withdrawals via the bridge's returned per-request identifiers if the POA API exposes them. At minimum, document (and ideally throw) when a caller submits a batch containing duplicate `assetId` entries so status cannot be silently cross-attributed, and apply the same fix to `findMatchingWithdrawal` in `waitForWithdrawalCompletion.ts`.

### Proof of Concept
1. Call `sdk.signAndSendWithdrawalIntent` with a batch of two `withdrawalParams`, both `assetId: "nep141:usdt.tether-token.near"`, one destined to address `A` and one to address `B`, in a single NEAR transaction/intent.
2. The POA bridge indexer records two withdrawal entries with the same `near_token_id` but different `address`/`transfer_tx_hash`, potentially returned in non-deterministic order.
3. Call `bridge.describeWithdrawal` for index 0 (expected: address A's transfer) and index 1 (expected: address B's transfer).
4. Because `findMatchingWithdrawal` only filters on `assetId` [7](#0-6) , both calls can resolve to the first array element sharing that `assetId`, causing `describeWithdrawal` to report the same (or swapped) `transfer_tx_hash`/status for the wrong logical withdrawal index — as demonstrated by the existing test explicitly named "matches withdrawal by assetId, not by index" [4](#0-3) .

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],

	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
