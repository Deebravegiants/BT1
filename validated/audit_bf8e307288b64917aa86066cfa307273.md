## Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC-SHA256 signature computed over the raw request body [1](#0-0) . However, the `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to the app's webhook handler are read directly from unauthenticated HTTP headers, and are never part of the signed data.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

`HmacValidator.validate` computes the HMAC over exactly that signable string and compares it to the `hmac-sha256` header: [3](#0-2) 

Meanwhile, `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` are pulled straight from the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers, none of which are covered by the HMAC: [4](#0-3) 

`Registry.process` validates the HMAC and then immediately dispatches the handler using these unauthenticated header values, most notably `shop: request.shop`: [1](#0-0) 

The identity binding that should hold is:
`shop authenticated by HMAC == shop delivered to the handler`

In reality the equality is broken: the HMAC only binds `secret == api_secret_key` to the *body bytes*; it says nothing about which shop, topic, or webhook the body belongs to. Critically, `api_secret_key` (the webhook signing secret) is shared by the app across **every** shop that installs it — it is not shop-specific. This means any unprivileged party who can install the app on their own store (a normal, unprivileged action, not requiring any victim credential) possesses a valid signing capability for arbitrary bodies. They can then submit a POST to the app's webhook endpoint with:
- a body of their choosing, signed with their own valid installation's secret (same secret for the whole app),
- an `x-shopify-shop-domain` header claiming to be any *other* installed shop,
- any `x-shopify-topic` header (e.g. `app/uninstalled`, `orders/create`, `shop/redact`),

and `Registry.process` will accept it as an authentic webhook "from" the victim shop, because HMAC validation passes (same shared secret) and nothing checks that the claimed shop/topic is consistent with what was actually signed.

### Impact Explanation
This breaks the tenant boundary this gem is supposed to protect: an attacker who is merely one (unprivileged) installer of the app can forge webhook events and have them processed as if they originated from a different merchant/shop. Depending on how the host application's webhook handlers act on `shop` and `topic` (e.g., updating billing state, triggering data deletion/redaction flows, marking an app as uninstalled, or writing order data attributed to another tenant), this is a cross-tenant access/injection primitive — the impact class explicitly listed as Critical ("cross-tenant access").

### Likelihood Explanation
Likelihood is high for any app that: (a) is installable by the general public (most apps), and (b) relies on the header-derived `shop`/`topic` fields from `WebhookMetadata` without independently re-validating them against Shopify's Admin API or another authenticated channel. No secrets, tokens, or privileged access belonging to the victim are required — only the attacker's own legitimate installation of the target app.

### Recommendation
Include the critical identity fields (`shop`, `topic`, `webhook_id`) in the HMAC-signed payload verification, or cross-check the `shop-domain` header against a known/authorized shop-to-secret mapping before trusting it. At minimum, document prominently that `shop`/`topic`/`webhook_id` headers are unauthenticated and must not be trusted for tenant-identification purposes without additional verification (e.g., correlating against `Registry`'s expected topic for the delivery, or maintaining a per-shop mapping validated during OAuth).

### Proof of Concept
1. Attacker installs the vulnerable app on their own shop `attacker.myshopify.com`, obtaining the ability to compute valid webhook HMACs (the app-wide `api_secret_key` is shared across shops).
2. Attacker crafts an arbitrary JSON body, e.g. `{}`, and computes `hmac = OpenSSL::HMAC.digest("sha256", api_secret_key, body)` exactly as done in the test setup [5](#0-4) .
3. Attacker sends a POST to the app's webhook endpoint with headers:
   - `x-shopify-hmac-sha256`: the computed signature (valid, since same secret)
   - `x-shopify-shop-domain`: `victim-shop.myshopify.com` (arbitrary, unsigned)
   - `x-shopify-topic`: `app/uninstalled` (or any registered topic, arbitrary, unsigned)
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `Registry.process` validates the HMAC successfully (`Utils::HmacValidator.validate`) and invokes the registered handler with `shop: "victim-shop.myshopify.com"` [6](#0-5) , despite the request never having been produced or signed on behalf of `victim-shop.myshopify.com`.
