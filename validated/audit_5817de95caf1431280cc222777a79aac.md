### Title
Unbacked/Unspendable On-Chain Commitments via Unvalidated `stealthAddressStructure` in `prooflessDeposit` - ([File: contracts/Hinkal.sol])

### Summary
`Hinkal.prooflessDeposit` lets any caller create on-chain UTXO leaves by supplying an arbitrary `StealthAddressStructure` for each deposit, with no zero-knowledge proof and no validation that the point is a valid BabyJubjub subgroup element or that it was legitimately derived from a `spendingPublicKey`/`nullifyingPrivateKey` pair.

### Finding Description
In the normal `transact` flow, a UTXO's ownership tuple (`H0x`, `H0y`, `H1x`, `H1y`, `stealthAddress`) is produced and constrained inside the circuit: `StealthAddressCalculator` in `circuits/StealthAddressCalculator.circom:7-43` requires `H0Ax`/`H0Ay` to pass `BabyJubjubSubgroupCheck` (`circuits/BabyJubjubSubgroupCheck.circom:9-35`) and computes `H1`/`stealthAddress` deterministically from a real `spendingPublicKey` and `nullifyingPrivateKey`. These outputs are then forced to equal the public inputs supplied on-chain via `formBasicInput` in `contracts/CircomDataBuilder.sol:189-191`, so the Groth16 verifier guarantees the recipient's `stealthAddressStructure` is a well-formed point that some key-holder can later reconstruct with a valid `nullifyingPrivateKey`.

`prooflessDeposit` bypasses this entirely: [1](#0-0) 
It only calls `hinkalHelper.performProoflessDepositChecks`, which checks array-length consistency, `amounts[i] > 0`, and that `onChainEncryptedOutputs[i].length > 0` — nothing about the mathematical validity of `stealthAddressStructures[i]`: [2](#0-1) 

The commitment leaf is then built directly from this unvalidated structure and inserted into the Merkle tree: [3](#0-2) 

Because `commitment = hash4(amount, erc20Address, stealthAddressStructure.stealthAddress, timeStamp)` only depends on the (unchecked) `stealthAddress` scalar, a caller can insert a leaf whose `stealthAddress` was not honestly derived via `StealthAddressCalculator` (e.g., it is not `Poseidon(6)(signs, H0Ay, H1Ay, spendingPublicKey.x, spendingPublicKey.y, nullifyingPrivateKey)` for any key pair the depositor — or anyone — actually controls, or where `H0x/H0y` are not a valid subgroup point at all). Later, spending requires the prover to reconstruct exactly this `stealthAddress`/commitment via the circuit's `StealthAddressCalculator`/`OriginalCommitmentCalculator` (`circuits/MainEVMCircuit.circom:107-134`) using real `nullifyingPrivateKey`/`spendingPublicKey` inputs that satisfy the subgroup checks. If the deposited leaf's stealth data was not produced this way, no valid witness exists that can reconstruct the same commitment/nullifier, and the deposited value becomes permanently unspendable.

### Impact Explanation
This breaks the equality the protocol relies on between "a leaf that was inserted into the tree" and "a leaf the circuit can later prove ownership/spend of." Funds locked in Hinkal via `prooflessDeposit` with a malformed or maliciously/mistakenly encoded `stealthAddressStructure` are permanently frozen — the depositor (or anyone) can never produce a satisfying proof to nullify and withdraw them, since the circuit enforces subgroup membership and correct key-derivation that the on-chain path never checked. Per the impact rubric this is a **Critical** finding (permanent freezing of user funds) if triggered by user/integrator error, or usable to grief specific deposits if an attacker can influence/craft the structure for another user's `orderId`-tracked deposit (the front-end fills `stealthAddressStructures` off-chain per the design comment in `prooflessDeposit`, so a compromised or buggy integration/relayer front end could submit invalid values on a user's behalf without the user noticing at deposit time).

### Likelihood Explanation
Likelihood is moderate: `prooflessDeposit`/`HinkalWrapper` are meant to be driven by trusted off-chain tooling that correctly derives `H0x/H0y/H1x/H1y/stealthAddress`, so a well-behaved client will not trigger this. However, since there is **no on-chain enforcement** (no subgroup check, no proof, no consistency check between `H0`, `H1`, and `stealthAddress`), any integration bug, malicious front end, malicious relayer-style wrapper contract, or a user calling the function directly with hand-crafted parameters can cause an unrecoverable loss, and the contract offers no defense-in-depth against it — unlike the internal `transact` path, which is fully protected by the circuit's `BabyJubjubSubgroupCheck`.

### Recommendation
Add on-chain validation in `performProoflessDepositChecks` (or a new helper) mirroring the circuit's guarantees before creating on-chain commitments in `prooflessDeposit`:
- Verify `H0x`/`H0y` are valid points on the BabyJubjub curve and in the correct prime-order subgroup (replicating `BabyJubjubSubgroupCheck` logic in Solidity), and similarly for `H1x`/`H1y`.
- Optionally require the caller to additionally submit a signature/proof-of-knowledge binding `stealthAddress` to a `spendingPublicKey` they control, or restrict `prooflessDeposit` to trusted/whitelisted callers (e.g., only the audited `HinkalWrapper`) until such validation exists.
- At minimum, emit clear warnings/gate the function behind a role until subgroup/derivation validation is added, since currently any syntactically-valid `uint256` values are accepted as `stealthAddressStructure` fields.

### Proof of Concept
1. Caller calls `Hinkal.prooflessDeposit` with `erc20Addresses = [USDC]`, `amounts = [1000e6]`, and `stealthAddressStructures[0]` containing arbitrary `uint256` values for `H0x`, `H0y`, `H1x`, `H1y`, and `stealthAddress` that do NOT correspond to any valid BabyJubjub subgroup point / do not satisfy `stealthAddress == Poseidon(6)(signs, H0Ay, H1Ay, spendingPublicKey.x, spendingPublicKey.y, nullifyingPrivateKey)` for any real key pair.
2. `performProoflessDepositChecks` (`contracts/HinkalHelper.sol:37-62`) passes because it never checks these fields beyond `H0x != 0` isn't even checked here (that check only exists in `dimensionsCheck` for the `transact` path, not for `prooflessDeposit`).
3. `_handleTransfersFromProoflessDeposit` pulls the 1000 USDC from the caller into `Hinkal`.
4. `_createProoflessDepositCommitments` computes `commitment = hash4(amount, USDC, stealthAddress, block.timestamp)` and inserts it via `insertCommitments`/`HinkalBase.createOnchainCommitment` (`contracts/HinkalBase.sol:53-70`).
5. Later, any attempt to spend this UTXO via `Hinkal.transact` requires a Groth16 proof for `MainEVMCircuit` that reconstructs this exact commitment from a real `nullifyingPrivateKey`/`spendingPublicKey`/`H0x`/`H0y` satisfying `BabyJubjubSubgroupCheck` (`circuits/StealthAddressCalculator.circom`, `circuits/MainEVMCircuit.circom:107-134`). Since the deposited `stealthAddress` was not honestly derived, no witness exists that reproduces it, so the 1000 USDC can never be nullified/withdrawn — permanent loss of funds.

    function performProoflessDepositChecks(
        address[] calldata erc20Addresses,
        uint256[] calldata amounts,
        StealthAddressStructure[] calldata stealthAddressStructures,
        bytes[] calldata onChainEncryptedOutputs
    ) external view onlyHinkal {
        require(
            amounts.length == erc20Addresses.length &&
                amounts.length == stealthAddressStructures.length &&
                amounts.length == onChainEncryptedOutputs.length,
            "amounts length must match erc20Addresses, stealthAddressStructures, onChainEncryptedOutputs length"
        );

        require(
            erc20Addresses.length <= MAX_LEAVES_PD,
            "no more than MAX_LEAVES_PD entries allowed"
        );

        for (uint256 i = 0; i < erc20Addresses.length; i++) {
            require(
                onChainEncryptedOutputs[i].length > 0,
                "Missing encrypted output for on-chain commitment"
            );
            require(amounts[i] > 0, "Amount must be greater than zero");
        }
    }

    function createOnchainCommitment(
        UTXO memory utxo,
        bytes calldata onChainEncryptedOutput
    ) internal view returns (OnChainCommitment memory) {
        uint256 commitment = hash4(
            utxo.amount,
            uint256(uint160(utxo.erc20Address)),
            utxo.stealthAddressStructure.stealthAddress,
            utxo.timeStamp
        );

        OnChainCommitment memory onChainCommitment = OnChainCommitment({
            utxo: utxo,
            commitment: commitment,
            onChainEncryptedOutput: onChainEncryptedOutput
        });
        return onChainCommitment;
    }
