## Title
Webhook `X-Shopify-Shop-Domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authentic once `Utils::HmacValidator.validate` succeeds, and then hands `request.shop` straight to the app's handler as the tenant identifier. The HMAC, however, is only computed over the raw request body — never over the `shop` (or `topic`/`api-version`/`webhook-id`) header. Because the signing secret (`Context.api_secret_key`, the app's single `client_secret`) is identical for every shop that installs the app, any merchant who legitimately installs the app can capture a valid `(raw_body, hmac)` pair generated for their own store and replay it with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain. The signature still validates, and the forged shop identity flows unauthenticated into the app.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from unauthenticated headers: [2](#0-1) 

`Utils::HmacValidator.validate_signature` computes the digest with `Context.api_secret_key`/`Context.old_api_secret_key` — a single secret shared across every shop that has this app installed — over `verifiable_query.to_signable_string`, i.e. the body only: [3](#0-2) 

`Registry.process` gates on this HMAC check alone and then forwards `request.shop` (and `request.topic`, `request.webhook_id`) directly into `WebhookMetadata`, which is the identity binding the app's handler trusts: [4](#0-3) 

The broken identity binding is: `shop header verified == shop header trusted`, when in fact only `raw_body verified == raw_body trusted` holds. There is no nonce/timestamp field in `Request` to prevent replay either, so a captured `(raw_body, hmac)` pair from the attacker's own shop remains valid indefinitely and can be resent with an arbitrary `shop` header.

### Impact Explanation
Any account holder who can install the app on their own store (an "unprivileged internet user" relative to other tenants, requiring no access to `api_secret_key`, no leaked credentials, and no privileged account) can:
1. Trigger any webhook topic on their own shop and capture the resulting `raw_body` + `X-Shopify-Hmac-Sha256` value from the delivery.
2. Resend that exact body/HMAC pair to the app's webhook endpoint with `X-Shopify-Shop-Domain` rewritten to a victim shop's domain (and optionally a different `webhook-id`/`api-version`).
3. `HmacValidator.validate` still succeeds because the header isn't part of the signed data, and the handler receives `WebhookMetadata` claiming the event belongs to the victim shop.

Any app that uses `request.shop`/`WebhookMetadata#shop` to select per-tenant records, credentials, or state (the intended and documented use of this field) can have its data corrupted or its per-tenant logic invoked for a shop the attacker doesn't own — this is cross-tenant access achieved purely through this gem's verification primitive, not through host-application misuse.

### Likelihood Explanation
High. Any merchant can install the app to get a first legitimate webhook sample, no secret material or privileged access is required, and the header swap is trivial once a valid body/HMAC pair is captured.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed material used by `HmacValidator`, or otherwise cryptographically bind the `shop` header to the verified payload (e.g., require the raw body to contain/echo the shop domain and cross-check it against the header before trusting `request.shop`). At minimum, document loudly that `request.shop` is unauthenticated header data and must never be trusted for tenant selection without an independent binding (e.g., matching against the shop associated with the resource ID inside the verified body).

### Proof of Concept
```ruby
# Attacker owns "attacker.myshopify.com" and has installed the app.
# Step 1: capture a real delivery for their own shop.
raw_body = '{"id": 1}' # e.g. an app/uninstalled or orders/create payload with no shop domain inside
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_client_secret, raw_body)
hmac_b64 = Base64.encode64(hmac)

# Step 2: replay with a forged shop header pointing at the victim.
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac_b64,       # still valid: HMAC only covers raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) returns true
# => handler.handle(WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
```
