### Title
Denial of curve/post-graduation Sells via draining a shared LT's atomic-redeem buffer - (`packages/contracts/src/Zap.sol`)

### Summary
`Zap._sellInternal` hard-codes a single, non-fallback exit path for every sell (bonding-curve and post-graduation alike): it always calls `IBounceLeveragedToken(lt).redeem(address(this), ltReceived, 0)`, and per the interface's own documentation `redeem` "Reverts if the computed USDC output exceeds `baseAssetBalance()`" [1](#0-0) . Because any address can mint LT with USDC and then redeem it, an attacker can transiently exhaust a target LT's idle-USDC buffer, making every subsequent `Zap.sell`/`sellWithPermit` call on any token paired with that LT revert, exactly mirroring the AAVE-reserve-exhaustion DoS pattern in the referenced report (borrow-out-all-liquidity → downstream `withdraw` reverts → dependent operations brick).

### Finding Description
`Zap._sellInternal` converts the trader's tokens (curve or HyperSwap V2) into LT, then unconditionally redeems that LT for USDC in the same transaction: [2](#0-1) 

The comment directly above this call acknowledges the design has no fallback: *"Intentional v1 tradeoff: sells only use BounceTech's atomic `redeem()` path (no `prepareRedeem` fallback/queue in Zap). If the LT idle-USDC buffer is temporarily depleted, `redeem` reverts."*

`IBounceLeveragedToken.mint`/`redeem` are both permissionlessly callable by any address holding USDC or LT — there is no allowlist, cap, or per-block throttle enforced by `alt.fun`'s contracts on how much LT can be minted-then-redeemed in one transaction. An attacker can:
1. Mint a large amount of LT directly against the target LT contract (or via `Zap.buy` for any token paired with it), and
2. Immediately `redeem()` that LT for the maximum USDC the LT's `baseAssetBalance()` can atomically pay out,

driving `baseAssetBalance()` toward zero. Because `Bonding.launch` allows any creator to pair a new token with any existing BounceTech LT that passes `ltExists` (see `Bonding._deployAndSeed`, which never restricts `ltAddress` to one token) [3](#0-2) , a single LT can back many launched tokens simultaneously, so draining one LT's buffer denies `Zap.sell` for every token that shares it — not just the attacker's own.

Once the buffer is drained, every unrelated trader's `Zap.sell` / `Zap.sellWithPermit` call for any affected token reverts inside `IBounceLeveragedToken.redeem`, since `_sellInternal` has already irreversibly transferred the trader's tokens into LT (via `_sellOnCurve`/`_sellOnUniswapV2`) before attempting the redeem — the whole transaction reverts atomically, so the trader is left unable to exit until the LT's buffer is replenished by unrelated mint activity or LT-side liquidity management.

### Impact Explanation
This is a direct temporary freeze of trader exit liquidity: sellers cannot cash out of their token position through the only exit path `Zap` exposes (`redeem`), across potentially many tokens sharing the drained LT, at the attacker's discretion and re-triggerable at will (the attacker can re-mint and re-drain as soon as the buffer partially refills). This matches the judged severity class of the referenced report — "impairment of core functionalities of the protocol under some preconditions," landing on Medium because the freeze, while forceable, is not indefinite (buffer eventually refills from other mint activity).

### Likelihood Explanation
The attack requires only unprivileged calls (`mint`/`redeem` on a public LT contract, or `Zap.buy`/`sell`), no special access, and no front-run is required — the attacker can execute it standalone whenever they hold or can acquire sufficient USDC/LT, same as the original report's characterization ("can be done maliciously without the need for a front-run").

### Recommendation
- Add a fallback exit path in `Zap._sellInternal` (e.g., BounceTech's queued `prepareRedeem`, if available) so a depleted `baseAssetBalance()` degrades to a delayed redemption instead of reverting the whole sell.
- Consider capping single-LT exposure per launched token or tracking/limiting redeemable amount per block to reduce the drain's blast radius across tokens sharing one LT.
- Surface `baseAssetBalance()` pre-flight in `Zap.sell` and revert with a clear, distinct error before pulling the trader's tokens, so a doomed sell fails before token custody changes hands.

### Proof of Concept
1. Attacker (or any address) acquires USDC and calls `IBounceLeveragedToken(lt).mint(attacker, largeBaseAmount, 0)` to mint a large LT balance against a target LT contract used by one or more `alt.fun` tokens.
2. Attacker calls `IBounceLeveragedToken(lt).redeem(attacker, ltBalance, 0)` repeatedly/at size to drive `baseAssetBalance()` toward `0`.
3. Any trader calls `Zap.sell(tokenAddress, tokenAmount, minUsdcOut)` for a token paired with that LT. `_sellInternal` transfers the trader's tokens into LT via `_sellOnCurve`/`_sellOnUniswapV2`, then calls `IBounceLeveragedToken(lt).redeem(address(this), ltReceived, 0)` [4](#0-3) , which reverts because the computed USDC payout exceeds the now-depleted `baseAssetBalance()`.
4. The trader's entire sell transaction reverts; they cannot exit through `Zap` for any token sharing this LT until the buffer is externally replenished, and the attacker can repeat the drain as replenishment occurs.
