## Analysis

`CallDispatcher.dispatch()` is a permissionless, shared utility contract used by `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` to execute untrusted `Call[]` batches during predispatch/postdispatch order flows and cross-chain calldata execution. [1](#0-0)  The `dispatch` function carries **no access-control modifier whatsoever** — any external account can invoke it directly, at any time, with an arbitrary `Call[]` array specifying any target, any value, and any calldata, executed from the `CallDispatcher`'s own context. [2](#0-1)  The contract also has a public `receive()` that accepts ETH from anyone. [3](#0-2) 

This is the same bug class as CVE-2020-24263: a component that should only be operable by a trusted/limited caller instead grants unrestricted, privileged-equivalent execution capability to any unprivileged caller. In Portainer, a non-admin could spawn containers with host-level capabilities; here, any unprivileged address can drive the shared `CallDispatcher`'s arbitrary-call capability to move out whatever ETH/token balance or approvals the dispatcher currently holds — including tokens/ETH transiently routed through it by `IntentGatewayV2.placeOrder`/`fillOrder` predispatch and postdispatch flows, or by `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata execution on `onAccept`. [4](#0-3) [5](#0-4)  The docs themselves warn that "the dispatcher contract holds tokens temporarily during execution," acknowledging the shared, stateful nature of the contract. [6](#0-5) 

Because `dispatch` is unrestricted, an attacker can front-run or race to call `CallDispatcher.dispatch(...)` themselves with `Call({to: attacker, value: dispatcher.balance, data: ""})` to sweep any ETH sitting in the contract, or call `IERC20(token).transferFrom`/direct `transfer` if the dispatcher holds a residual token balance or a lingering approval (an order's `output.call`/`predispatch.call` is fully attacker/solver-controlled and can leave an `approve()` to an arbitrary spender, per `Call.to`/`Call.data` being unrestricted). [7](#0-6)  Since the same `CallDispatcher` instance is shared across all orders and all HFT/WHFT deployments referencing it, any dust, timing gap, or stuck balance from one flow is directly stealable by anyone, with no need to go through the gateway or token contract at all. [8](#0-7)

### Title
Unrestricted `CallDispatcher.dispatch()` lets any unprivileged caller drain funds held by the shared dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch(bytes memory encoded)` has no caller restriction (no `onlyGateway`/`onlyOwner`/`onlyHost` modifier), so any account can execute arbitrary `Call[]` batches from the dispatcher's own address at will, exactly as `IntentGatewayV2` and the Hyper Fungible Token contracts do for legitimate predispatch/postdispatch/calldata-execution flows.

### Finding Description
`CallDispatcher` is a single shared utility contract deployed once and reused by `IntentGatewayV2.placeOrder`/`fillOrder` (for `predispatch`/`output.call`) and by `HyperFungibleToken`/`WrappedHyperFungibleToken.onAccept` for cross-chain calldata execution. [4](#0-3)  Its only entrypoint, `dispatch`, decodes an ABI-encoded `Call[]` and executes each call with `to.call{value: call.value}(call.data)`, with the sole check being that `to` has code — there is no restriction on which address may invoke `dispatch`, nor on who supplied the `Call[]`. [9](#0-8)  The contract additionally exposes a public `receive()` payable fallback. [3](#0-2) 

Order calldata (`order.predispatch.call`, `order.output.call`) is fully user/solver-controlled and can contain arbitrary `Call[]` entries, including token `approve()` calls to attacker-chosen spenders, as shown by the test harness constructing a `Call({to: dai, data: approve(intentGateway, 1)})`. [7](#0-6)  Because `dispatch()` itself is callable by anyone independent of the gateway, any balance or approval that ends up on the `CallDispatcher` — from a partially-completed flow, a fee-on-transfer remainder, unswept dust, or a stray direct transfer via `receive()` — is directly and immediately stealable by any address, without going through `IntentGatewayV2`, `HyperFungibleToken`, or any escrow accounting at all.

### Impact Explanation
Since `CallDispatcher` is deployed once and shared across the intent gateway and HFT/WHFT token bridging apps, any unswept token/ETH balance is a pooled, unprotected target reachable by an unprivileged single transaction from any address. This can result in theft of funds transiting the dispatcher (fee-on-transfer remainders, dust, native token sent via `dispatcher.call{value: amount}("")` during predispatch) and abuse of any lingering approvals set by attacker-controlled `output.call`/`predispatch.call` payloads from earlier orders.

### Likelihood Explanation
Exploitation requires only a single unprivileged transaction calling `CallDispatcher.dispatch()` directly — no proof, no consensus verification, no relayer role, and no interaction with `IntentGatewayV2`/`HyperFungibleToken` access controls is needed, since the dispatcher is a standalone contract with a fully public entrypoint.

### Recommendation
Add an access-control check to `CallDispatcher.dispatch()` restricting callers to a configured, trusted caller set (e.g., the `IntentGatewayV2` instance(s) and `HyperFungibleToken`/`WrappedHyperFungibleToken` instance(s) that are meant to route calls through it), or make the dispatcher single-use/ephemeral per invocation (e.g., deploy a fresh minimal-proxy dispatcher per call) so it never accumulates a standing balance that an unrelated caller can later drain.

### Proof of Concept
1. Any solver/user places an order (or triggers HFT calldata execution) whose `output.call`/`predispatch.call` includes `Call({to: <token>, value: 0, data: approve(attacker, type(uint256).max)})`, executed through the shared `CallDispatcher`.
2. Later (or during the same block via a stray transfer, fee-on-transfer remainder, or partially executed flow), the `CallDispatcher` ends up holding a nonzero balance of that token or of native ETH (e.g., via its public `receive()`).
3. The attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: attacker, value: address(dispatcher).balance, data: ""})]))` directly — no gateway/host interaction required — draining the dispatcher's ETH, or calls `token.transferFrom(dispatcher, attacker, amount)` using the previously planted approval, draining its token balance.

```text
    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```

```text
### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
```
