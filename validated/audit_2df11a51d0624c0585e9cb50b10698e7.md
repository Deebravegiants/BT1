### Title
Reachable Panic (Unchecked `unwrap()` on `checked_sub`) in Deposit/Withdraw PnL Accounting Causes DoS of Withdrawals - (File: `program/src/processor.rs`)

### Summary
The external CVE describes a reachable-assertion class bug: attacker-controlled input reaches an unchecked arithmetic/assertion path that aborts execution (DoS) instead of failing gracefully. The Raydium AMM program contains an analogous pattern in the LP PnL accounting of `process_deposit` and `process_withdraw`: `target_orders.calc_pnl_x`/`calc_pnl_y` are updated using `checked_sub(...).unwrap()` instead of a graceful `ok_or(AmmError::...)` pattern that is used elsewhere in the same codebase for the identical class of subtraction (`Calculator::calc_total_without_take_pnl_no_orderbook`).

### Finding Description
In `Calculator::calc_total_without_take_pnl_no_orderbook` the developers correctly guard against underflow and return `AmmError::CheckedSubOverflow` instead of panicking: [1](#0-0) 

However, in the very next step of the same instruction flow — updating `target_orders.calc_pnl_x`/`calc_pnl_y` after a `Deposit` — the code performs `checked_add(...).unwrap().checked_sub(U128::from(delta_x)).unwrap()`, with no graceful error path: [2](#0-1) 

The identical unguarded pattern exists in `process_withdraw`'s "step4" pnl update: [3](#0-2) 

and in `process_withdrawpnl`: [4](#0-3) 

`delta_x`/`delta_y` are produced by `calc_take_pnl`, which itself performs a chain of `checked_mul().unwrap()` / `checked_div().unwrap()` / `checked_sub().unwrap()` operations over decimal-normalized (`Calculator::normalize_decimal_v2`) values derived from live vault balances and the persisted `TargetOrders.calc_pnl_x`/`calc_pnl_y` state: [5](#0-4) 

Because `x1`/`y1` are captured **before** `calc_take_pnl` mutates `total_pc_without_take_pnl`/`total_coin_without_take_pnl`, while `pc_amount`/`coin_amount` (in withdraw) are computed **after** that mutation, the subsequent `x1.checked_sub(normalize(pc_amount)).unwrap().checked_sub(delta_x).unwrap()` relies on an implicit invariant that is not independently verified anywhere. Any decimal-normalization rounding drift (`normalize_decimal_v2`/`restore_decimal` truncate/ceil in different directions depending on branch) or precision mismatch between `pc_decimals`/`coin_decimals`/`sys_decimal_value` can make `normalize(pc_amount) + delta_x > x1`, causing the `unwrap()` to panic instead of returning an `AmmError`.

### Impact Explanation
A panic inside `process_withdraw`/`process_deposit`/`process_withdrawpnl` aborts the entire transaction (Solana transactions are atomic, so the preceding SPL token transfer/mint/burn CPIs are also rolled back). The direct consequence is a denial-of-service: a `Withdraw`/`Deposit`/`WithdrawPnl` instruction that hits this arithmetic edge case will always fail for the same on-chain state and withdrawal parameters, rather than being rejected cleanly with a recoverable `AmmError`. Because `TargetOrders.calc_pnl_x`/`calc_pnl_y` is a small piece of long-lived, program-owned pool state that every subsequent `Deposit`/`Withdraw`/`SwapBase*`/`WithdrawPnl` call must recompute against, a pool that drifts into this edge condition risks having its LP-withdrawal path deterministically panic, effectively freezing LP funds until an off-chain remediation (e.g., a compensating swap to move the vault ratio, if even possible) restores the invariant — this matches the "permanent freezing of LP funds" impact category.

### Likelihood Explanation
This requires the accumulated decimal-normalization/PnL state (`TargetOrders.calc_pnl_x/y`, `state_data.need_take_pnl_pc/coin`) to drift relative to live vault balances such that the unchecked subtraction underflows. This is a state-dependent, rounding-driven condition rather than a one-shot trivially-triggerable bug, and the exact numeric window that provokes it was not concretely reproduced here — the finding is based on the direct code-pattern parity with the guarded version in `math.rs`, which shows the developers are aware this exact class of subtraction can underflow but did not apply the same guard consistently across `processor.rs`.

### Recommendation
Replace every `checked_sub(...).unwrap()` (and matching `checked_add/mul/div().unwrap()`) in the `target_orders.calc_pnl_x`/`calc_pnl_y` update paths of `process_deposit`, `process_withdraw`, and `process_withdrawpnl` with `.ok_or(AmmError::CheckedSubOverflow)?` (or an equivalent dedicated error), mirroring the pattern already used in `Calculator::calc_total_without_take_pnl_no_orderbook`, so that any residual rounding/precision mismatch results in a clean instruction failure rather than a raw panic, and add regression tests exercising extreme decimal-precision combinations for `pc_decimals`/`coin_decimals`/`sys_decimal_value`.

### Proof of Concept
Not independently reproduced with concrete numeric inputs; the report is based on static code-pattern analysis showing the inconsistency between the guarded subtraction in [6](#0-5)  and the unguarded, panic-prone subtractions in [7](#0-6)  reachable from the unprivileged `Withdraw` instruction. A concrete PoC would require constructing (via repeated Deposit/Withdraw/Swap sequences) vault balances and `TargetOrders` state such that `normalize_decimal_v2(pc_amount) + delta_x > x1` at withdrawal time.
