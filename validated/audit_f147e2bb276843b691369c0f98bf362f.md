### Title
Weighted-median phantom price is a raw balance-weighted selection, letting a solver with dominant output-token inventory unilaterally set the published intent price - (File: `sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts`)

### Summary
`aggregatePhantomBids` prices every phantom-order leg by taking the `weightedMedian` of solvers' quotes, where each quote's weight is simply the solver's raw wallet + vault + declared Uniswap V4 position balance of the leg's output token on the destination chain, with no cap on how much of the total weight one solver may hold. Just as the Curve vault's spot price becomes unreliable once the vault's LP share of the pool grows too large without any post-deposit enforcement, a solver whose declared/measured inventory exceeds half of a leg's total weight determines the published price outright, and nothing bounds or challenges that concentration.

### Finding Description
`weightedMedian` in `sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts:709-724` sorts bid entries by price and returns the entry at which cumulative weight crosses half of total weight — a selection, not a blend. The code comment at lines 702-708 explicitly documents the danger: with weights all zero "the median becomes whoever quoted higher," but the "safe" path is only marginally better — a bidder controlling >50% of a leg's weight always wins the median regardless of how extreme its price is.

Weight is computed purely from measured token inventory (`sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts:1479-1497`): wallet ERC-20 balance plus redeemable vault balance plus any Uniswap V4 position amount the solver declares and is proven to own. There is no upper bound analogous to Notional's `maxPoolShare` check — nothing prevents one solver (or one entity operating multiple registered `SolverAccount`s) from accumulating or temporarily inflating its output-token balance on a chain immediately before a phantom bid window closes, becoming the dominant weight holder, and quoting an arbitrary price.

That `medianPrice` propagates, unvalidated against any independent oracle, into `PhantomOrderPriceSnapshotV2` and then `updateLiquidityPools` → `mergeChainRowsIntoPool` → `weightedRate` (`sdk/packages/indexer/src/services/liquidityPool.service.ts:161-170, 470-496`), which sets `LiquidityPool.sellRate`/`buyRate`. Those rates are then consumed directly by `IndexedRateIntentQuoteStrategy.quote` (`sdk/packages/sdk/src/protocols/intents/quote/indexedRates.ts:44-77`) to price real user intents via `IntentGateway.quoteIntent`.

This mirrors the Curve vault report's root cause exactly: a price-discovery mechanism that is safe only so long as no single party's holdings dominate the measured quantity (LP share of pool supply vs. weight share of quoted inventory), with no protocol-level limit on that dominance once it occurs.

### Impact Explanation
A dominant-inventory solver can push `medianPrice` far off the true market rate for a leg. Once folded into the pool's `sellRate`/`buyRate`, this corrupts the rate `quoteIntent` returns to any user requesting a quote for that pair — users could be quoted (and place orders at) a manipulated exchange rate, over- or under-paying relative to fair value, or the manipulator's own subsequent real fills could be priced advantageously against the published rate. This is a Medium-severity pricing-integrity issue affecting the intent quoting path used by real fund-moving orders, without requiring any privileged role — only inventory in the relevant output token.

### Likelihood Explanation
Reaching this path only requires being (or controlling) a delegated solver account able to submit phantom bids and hold or briefly acquire enough of a leg's output token to exceed 50% of the bidding weight for that (chain, leg) pair — thinner markets or newly-added pairs with few active solvers make this materially easier, mirroring the "attacker needs considerable amount of LP" caveat in the original report.

### Recommendation
Cap a single solver's contribution to a leg's total weight before running `weightedMedian` (e.g., clamp weight to some percentage of total measured weight, analogous to `maxPoolShare`), and/or corroborate the phantom-derived rate against an independent reference (oracle or cross-chain consensus) before it is allowed to move `LiquidityPool.sellRate`/`buyRate`, rejecting or flagging updates that diverge too far, similar to the existing `warnOnDivergentSample` cross-chain check but enforced rather than only logged.

//
// Callers must not hand this an entry set whose weights are all zero: with nothing to weight by it
// can only pick a quote by position, and for an even-sized set that position is the upper of the
// two middles — so "the median" becomes "whoever quoted higher", settable by a solver holding no
// inventory at all. aggregatePhantomBids drops such legs instead of pricing them. The fallback
// below stays only so an unguarded caller gets a number rather than a crash; treat reaching it as
// a caller bug.
export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
}

// The one rate-merge policy: depth-weighted average, falling back to the unweighted mean when
// the whole sample set carries zero depth (so a price is still reported). Every merge in this
// file — collapsed legs, the cross-chain pool merge, and the divergence alarm's consensus —
// must agree on this, hence the single home.
function weightedRate(samples: { rate: bigint; depth: bigint }[]): bigint {
	const depth = samples.reduce((acc, sample) => acc + sample.depth, 0n)
	return depth > 0n
		? samples.reduce((acc, sample) => acc + sample.rate * sample.depth, 0n) / depth
		: samples.reduce((acc, sample) => acc + sample.rate, 0n) / BigInt(samples.length)
}

function mergeChainRowsIntoPool(pool: LiquidityPool, rows: PoolChainLiquidity[], referenceBlock: bigint): void {
	for (const direction of [SELL, BUY]) {
		const directionRows = rows.filter((row) => row.direction === direction)
		if (directionRows.length === 0) continue

		// Blocks are processed in order, so the difference is non-negative in practice; a row
		// from a "future" block would simply count as fresh, which is the right reading anyway.
		const fresh = directionRows.filter((row) => referenceBlock - row.lastUpdatedBlock <= MAX_SAMPLE_AGE_BLOCKS)
		const merged = fresh.length > 0 ? fresh : directionRows

		warnOnDivergentSample(pool.id, direction, merged)

		const depth = merged.reduce((acc, row) => acc + row.depth, 0n)
		const rate = weightedRate(merged)
		const bidCount = merged.reduce((acc, row) => acc + row.bidCount, 0)

		if (direction === SELL) {
			pool.sellRate = rate
			pool.sellDepth = depth
			pool.sellBidCount = bidCount
		} else {
			pool.buyRate = rate
			pool.buyDepth = depth
			pool.buyBidCount = bidCount
		}
	}
}
