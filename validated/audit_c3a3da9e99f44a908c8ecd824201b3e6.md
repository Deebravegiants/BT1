Based on my investigation, I found a genuine analog of this bug class in `src/plans/mod.rs`'s `do_signup` function.

### Title
User-centric signup success is credited to the enrollment record without pulling backend confirmation of that success - ([File: src/plans/mod.rs])

### Summary
The Swivel bug credits an accounting variable (`fees[u]`) with a value that was never actually pulled/verified from the real source of truth (the user's balance), causing state to diverge from reality. The analogous pattern in `orb-core` is in `do_signup`: when `user_centric_signup` is true, the Orb locally derives `enrollment_status`/`success` purely from its own local `signup_reason` and never actually calls the backend to confirm the enrollment, unlike the non-user-centric path which calls `enroll_user()` and polls the backend (`signup_poll::request`) for real confirmation.

### Finding Description
In `do_signup`, after biometric capture and fraud detection, the code branches on `user_centric_signup`: [1](#0-0) 

When `user_centric_signup && !ignore_user_centric_signups`, `debug_report.enrollment_status(...)` and `success` are set purely from the locally computed `signup_reason` (itself derived from local pipeline/fraud results), never confirmed by the backend via `signup_post::request`/`signup_poll::request` as the other branch does: [2](#0-1) 

This mirrors the Swivel root cause: an internal "credit" (`enrollment_status`/`success` = Success, later used to drive `debug_report.signup_successful()`, UI success feedback, and `SignupEnded{success: true}` sent to the app) is recorded without the corresponding real confirmation ever being "pulled" from the authoritative source (the backend, which is responsible for detecting duplicate/fraudulent/duplicate signups server-side). The `user_centric_signup` flag itself comes from `qr_codes.user_data.user_centric_signup`, which originates from the backend-authenticated user status response and is not attacker-controlled by an unprivileged party in the way the fee flag is; however, the underlying gap — declaring success without pulling confirmation from the backend — is architecturally identical to the pull-omission bug.

### Impact Explanation
If the backend would have rejected this signup (e.g., due to duplicate detection or backend fraud checks — the same categories `enroll_user`'s comment explicitly enumerates: "Backend duplicates," "Backend inflight matches," "Backend detected fraud"), the Orb still reports `signup_successful()` locally, drives `SignupStatus::Success` UI feedback, and relays `SignupEnded{success:true}` to the user's app — a misattributed/unverified signup success recorded without the accounting ever being confirmed against the source of truth. This is analogous to `fees[u]` being incremented without ever confirming the tokens were actually collected.

### Likelihood Explanation
This path executes whenever the backend user data indicates `user_centric_signup: true` (an app-driven, not operator-driven, flow) and `ignore_user_centric_signups` is not set, which is a normal, reachable configuration for self-serve/app-centric signups — not a privileged or malicious-node precondition.

### Recommendation
For the `user_centric_signup` branch, still perform (or require) a backend confirmation step — analogous to pulling `lent + totalFee` instead of only `lent` — before marking `enrollment_status`/`success` as `Success`, so that local success bookkeeping is never divorced from the backend's authoritative confirmation.

### Proof of Concept
1. Configure Orb with `self_serve`/app-centric flow such that `qr_codes.user_data.user_centric_signup == true` and `ignore_user_centric_signups == false`.
2. Complete a biometric capture/pipeline such that `signup_reason == SignupReason::Normal` locally (no orb-side fraud detected).
3. Observe that `do_signup` sets `success = true` and `debug_report.enrollment_status(enroll_user::Status::Success)` purely from local state at [3](#0-2)  — with no call to `signup_post::request`/`signup_poll::request` to confirm with the backend, unlike the `enroll_user::Plan::run` path at [4](#0-3)  which explicitly handles backend-side duplicate/fraud rejection.
4. Even if the backend would independently flag this signup (duplicate, backend-fraud), the Orb has already recorded and surfaced success without ever pulling that confirmation.
