### Title
Malformed SVG token entry causes `storeIcons()` batch rejection via `validate()`/`cleanup()` throw, blocking legitimate icon updates in the same batch - ([File: libraries/svg-safe/src/validate.mjs])

### Summary
`cleanup()` (called from `#storeIcon` in both `adapters/storage-icons-browser/src/utils.js` and `adapters/storage-icons-mobile/src/icons-storage.js`) internally calls `validate()`, which throws via the `assert()` helper on any malformed/unrecognized SVG token/attribute. Since `storeIcons()` in both adapters batches all token updates with `Promise.all(tokens.map(...))`, a single crafted malicious icon entry causes the whole batch's promise to reject, preventing legitimate icon updates bundled in the same `Promise.all` call from being persisted.

### Finding Description
`storeIcons()` (`adapters/storage-icons-browser/src/icons-storage.js:12-28`, mirrored in `adapters/storage-icons-mobile/src/icons-storage.js:26-40`) maps every token to an async `#storeIcon`/`#deleteIcon` call and awaits them all via `Promise.all`. `#storeIcon` calls `unzipIcon(token.icon)`, which invokes `cleanup(unzip.toString('utf8'))` (`adapters/storage-icons-browser/src/utils.js:1-17`). `cleanup()` calls `validate(clean)` (`libraries/svg-safe/src/cleanup.mjs:1-9`), and `validate()`/`tokenizeFile()`/`tokenizeLine()`/`validateOption()` all use the `assert()` helper (`libraries/svg-safe/src/validate.mjs:6-14`) that throws a plain `Error` on any unexpected tag, attribute, or malformed structure. Because `Promise.all` rejects as soon as any one of its promises rejects, a single crafted SVG (e.g., containing a `<script>` tag or unrecognized attribute) in a batch causes the entire `storeIcons()` call to reject — none of the other, legitimate entries in that same batch get persisted, even though their individual `#storeIcon`/`#deleteIcon` writes would have otherwise succeeded independently.

This is reachable from `features/assets-feature/module/assets-module.js`, where remote-registry responses (`#fetchUpdates`, `addRemoteTokens`, `#fetchTokens`) are batched into `#storeIcons(tokens)` (lines 423, 526, 283). However, `#storeIcons` in `assets-module.js` (lines 676-687) wraps the call to `this.#iconsStorage.storeIcons(tokens)` in a `try/catch` that only logs a warning on failure — it does not propagate the rejection further up, and critically, custom-token metadata persistence (`#storeCustomTokens`, which stores names/trust-state/version data) happens as a separate call, generally before or independently of `#storeIcons`. So the crafted entry blocks icon persistence for the whole batch, not the trust/metadata state itself.

### Impact Explanation
The scoped impact is a denial-of-service on icon-sync persistence: legitimate icons for unrelated assets fetched in the same registry-sync batch will fail to be written to the icon store, potentially leaving stale icons in place. However, this does not affect signing, authentication, account/origin scoping, or trust-state persistence, since those are stored via a separate `#storeCustomTokens` path (`features/assets-feature/module/assets-module.js:720-732`) that is unaffected by `storeIcons()` rejecting, and `#storeIcons` failures are already caught and merely logged rather than allowed to propagate and corrupt other state. There is no unauthorized signing, secret disclosure, auth bypass, or wrong-account/origin access — the impact is limited to a display-icon staleness/DoS on the icon cache, not a "trust marker" persistence failure as hypothesized in the question (trust/version fields are persisted via a different, unaffected mechanism).

### Likelihood Explanation
This requires a remote/malicious entry in the custom token registry response (`#fetch('tokens', ...)`) to be included in the same batch as legitimate entries, which is plausible for an attacker who controls or can inject an entry into a remote token-list sync response. The mechanics (crafted SVG causing `validate()`/`cleanup()` to throw, then `Promise.all` rejecting the whole `storeIcons()` batch) are real and reproducible.

### Recommendation
Isolate per-token failures in `storeIcons()` (both `adapters/storage-icons-browser/src/icons-storage.js` and `adapters/storage-icons-mobile/src/icons-storage.js`) by wrapping each `#storeIcon`/`#deleteIcon` call in its own try/catch inside the `.map()` callback (e.g., using `Promise.allSettled` or catching per-item), logging failures for the specific malformed entry while still persisting/writing all other valid icons in the batch.

### Proof of Concept
Integration test for `IconsStorage.storeIcons()` (browser adapter):
1. Construct `tokens = [{ name: 'validAsset', icon: <base64-gzip of a valid SVG fixture, e.g. bitcoin.svg> }, { name: 'maliciousAsset', icon: <base64-gzip of an SVG fixture from src/__tests__/fixtures/invalid/xss-script.svg> }]`.
2. Call `await iconsStorage.storeIcons(tokens)`.
3. Current behavior: the call rejects with the `validate`/`assert` error from the malicious entry, and `storage.set('validAsset', ...)` for the valid entry is never awaited/verified to complete deterministically (racy — under `Promise.all`, the valid write may or may not have committed before rejection, and callers cannot rely on it).
4. Expected assertion after fix: `storeIcons()` should not throw for the whole batch; `storage.get('validAsset')` should return the valid SVG, and the malicious entry should be skipped/logged without blocking the valid entry's persistence.
