### Title
LDAP-authenticated users can silently assume the role of a same-email local admin account, bypassing local password verification - ([File: core/sessions/ldapauth/ldap.go])

### Summary
`SessionsController.Create` is a public, unauthenticated endpoint that forwards `SessionRequest` credentials to `ldapAuthenticator.CreateSession`. When the LDAP bind succeeds, the code calls `FindUser` purely to resolve a *role* for the already-authenticated email, but `FindUser` first checks the local `users` table by email before ever consulting LDAP group membership, and that local lookup performs no password verification. [1](#0-0) [2](#0-1) 

### Finding Description
`CreateSession` binds to LDAP with the caller-supplied email/password. If the bind succeeds (proving only that the caller controls that email's *LDAP* credentials), it calls `l.FindUser(ctx, escapedEmail)` solely to obtain a role to store in the new session: [3](#0-2) 

`FindUser` resolves role by email in this order: (1) local `users` table match (case-insensitive), returned immediately with no password check at all, (2) LDAP group membership, (3) fallback local table match again: [2](#0-1) [4](#0-3) 

Because step (1) is checked and returned before anything derived from the LDAP directory is consulted, the *role* assigned to the new session is taken from whatever row exists in the local `users` table for that email — completely independent of the fact that authentication succeeded via the LDAP bind and not via the local user's `hashed_password`. The session is then persisted with that role and `localauth_user = false`: [5](#0-4) 

This is directly analogous to CVE-2020-25717: Samba's flaw allowed a domain (upstream-authenticated) user to be mapped onto a pre-existing local account and inherit its privileges without validating that the two identities are actually the same principal. Here, an "upstream-authenticated" (LDAP-bound) email is mapped onto a local `users` table row purely by string match, granting that row's role (which may be `admin`) without any check that the LDAP-authenticated party actually knows the local admin's password or is the same person who owns that local account.

### Impact Explanation
If a local CLI/admin account in the `users` table (e.g., a bootstrap admin created via chainlink CLI) shares its email with an account/identity resolvable in the configured LDAP directory (a common scenario, since node operators frequently reuse their corporate/domain email as the CLI admin login), any party who can authenticate to that LDAP server with that email — using credentials entirely unrelated to the local admin password — will be granted a Chainlink node session with the local user's role, up to `UserRoleAdmin`. This is a full authentication/role bypass leading to privilege escalation on an internet/network-facing, unprivileged, unauthenticated endpoint (`POST /sessions`).

### Likelihood Explanation
Requires: (a) LDAP authentication enabled, (b) a local admin/user row present in the `users` table (common for bootstrap/CLI admin accounts and any LDAP fallback flows), and (c) an email collision between an LDAP-resolvable identity and that local row. Given operators frequently provision the local CLI admin using the same corporate email later federated into the LDAP directory, or reuse addresses across environments, this is a realistic misconfiguration rather than a contrived edge case. The endpoint itself requires no prior privilege — only knowledge of an email and its own (unrelated) LDAP credentials.

### Recommendation
In `FindUser`/`CreateSession`, do not resolve role from the local `users` table for a request that authenticated via LDAP bind unless the local row is explicitly confirmed to be the *same* identity (e.g., require the LDAP bind and local table lookup to use a consistent authentication path with no override of the local record's own password check). At minimum, `CreateSession` should not honor a local-table role match unless the login flow performed local password verification for that specific row, and `FindUser`'s local-table shortcut should be reserved strictly for the local-fallback path (`localLoginFallback`), not silently applied to LDAP-bound users.

### Proof of Concept
1. Configure the node with `WebServer.AuthenticationMethod = ldap`, pointed at an LDAP server that the attacker can register/control an account against (or where domain email self-service exists).
2. A local admin row exists in `users` with `email = 'ops@example.com'`, `role = admin` (e.g. bootstrap CLI admin).
3. Attacker obtains/registers an LDAP account for `ops@example.com` with an attacker-chosen password (or is simply a distinct legitimate domain user reusing the address, e.g. after employee offboarding/re-provisioning).
4. Attacker calls `POST /sessions` with `{"email": "ops@example.com", "password": "<attacker's own LDAP password>"}`.
5. LDAP bind succeeds (attacker's own valid domain credential). `CreateSession` calls `FindUser`, which matches the local `users` row for `ops@example.com` and returns `Role: admin` without ever checking the local row's `hashed_password`.
6. A session is created and returned to the attacker with `UserRoleAdmin`, granting full node admin access. [6](#0-5)

// FindUser will attempt to return an LDAP user with mapped role by email.
func (l *ldapAuthenticator) FindUser(ctx context.Context, email string) (sessions.User, error) {
	email = strings.ToLower(email)

	// First check for the supported local admin users table
	var foundLocalAdminUser sessions.User
	checkErr := l.ds.GetContext(ctx, &foundLocalAdminUser, "SELECT * FROM users WHERE lower(email) = lower($1)", email)
	if checkErr == nil {
		return foundLocalAdminUser, nil
	}
	// If error is not nil, there was either an issue or no local users found
	if !errors.Is(checkErr, sql.ErrNoRows) {
		// If the error is not that no local user was found, log and exit
		l.lggr.Errorf("error searching users table: %v", checkErr)
		return sessions.User{}, errors.New("error Finding user")
	}

func (l *ldapAuthenticator) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	conn, err := l.ldapClient.CreateEphemeralConnection()
	if err != nil {
		return "", errors.New("unable to establish connection to LDAP server with provided URL and credentials")
	}
	defer conn.Close()

	var returnErr error

	// Attempt to LDAP Bind with user provided credentials
	escapedEmail := ldap.EscapeFilter(strings.ToLower(sr.Email))
	searchBaseDN := fmt.Sprintf("%s=%s,%s,%s", l.config.BaseUserAttr(), escapedEmail, l.config.UsersDN(), l.config.BaseDN())
	if err = conn.Bind(searchBaseDN, sr.Password); err != nil {
		l.lggr.Infof("Error binding user authentication request in LDAP Bind: %v", err)
		returnErr = errors.New("unable to log in with LDAP server. Check credentials")
	}

	// Bind was successful meaning user and credentials are present in LDAP directory
	// Reuse FindUser functionality to fetch user roles used to create ldap_session entry
	// with cached user email and role
	foundUser, err := l.FindUser(ctx, escapedEmail)
	if err != nil {
		l.lggr.Infof("Successful user login, but error querying for user groups: user: %s, error %v", escapedEmail, err)
		returnErr = errors.New("log in successful, but no assigned groups to assume role")
	}

	isLocalUser := false
	if returnErr != nil {
		// Unable to log in against LDAP server, attempt fallback local auth with credentials, case of local CLI Admin account
		// Successful local user sessions can not be managed by the upstream server and have expiration handled by the reaper sync module
		foundUser, returnErr = l.localLoginFallback(ctx, sr)
		isLocalUser = true
	}

	// If err is still populated, return
	if returnErr != nil {
		return "", returnErr
	}

	l.lggr.Infof("Successful LDAP login request for user %s - %s", sr.Email, foundUser.Role)

	// Save session, user, and role to database. Given a session ID for future queries, the LDAP server will not be queried
	// Sessions are set to expire after the duration + creation date elapsed, and are synced on an interval against the upstream
	// LDAP server
	session := sessions.NewSession()
	_, err = l.ds.ExecContext(
		ctx,
		"INSERT INTO ldap_sessions (id, user_email, user_role, localauth_user, created_at) VALUES ($1, $2, $3, $4, now())",
		session.ID,
		strings.ToLower(sr.Email),
		foundUser.Role,
		isLocalUser,
	)
	if err != nil {
		l.lggr.Errorf("unable to create new session in ldap_sessions table %v", err)
		return "", fmt.Errorf("error creating local LDAP session: %w", err)
	}

	l.auditLogger.Audit(audit.AuthLoginSuccessNo2FA, map[string]any{"email": sr.Email})

	return session.ID, nil
