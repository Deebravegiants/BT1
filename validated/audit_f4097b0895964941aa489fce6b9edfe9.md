Based on my investigation, I found a genuine finding matching the report's bug-class pattern (a field acted on but not covered by the HMAC).

### Title
Webhook `shop` header is not covered by HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The library's webhook verification computes the HMAC signature over the raw body only, while `ShopifyAPI::Webhooks::Registry.process` trusts the unauthenticated `shop-domain` header to determine which tenant a webhook event belongs to. An unprivileged attacker who obtains any single valid `(raw_body, hmac)` pair signed by the app's shared secret (e.g., by installing the app on their own store and receiving a genuine webhook) can replay that exact body/HMAC pair while substituting an arbitrary victim shop domain in the header, and the gem will accept it as authentic for the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, never including the `shop` header in the signable content: [1](#0-0) . The `shop` accessor simply reads the unauthenticated `shopify-shop-domain` (or `x-shopify-shop-domain`) HTTP header with no cross-check against the signed payload: [2](#0-1) .

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which calls `verifiable_query.to_signable_string` (i.e., only the body) and compares it against the same app secret: [3](#0-2) , [4](#0-3) . Once the HMAC (body-only) check passes, `request.shop` — pulled straight from the unauthenticated header — is forwarded unchanged into `WebhookMetadata`, which is the sole tenant identifier the host application's handler receives: [5](#0-4) .

The identity binding broken is: `hmac == HMAC(secret, body)` is verified, but the equality the caller actually relies on — `header.shop == webhook_origin_shop` — is never checked. Since the HMAC secret (`client_secret`) is identical across every shop that has installed the same app, any shop that has legitimately installed the app can generate a valid `(body, hmac)` pair for itself, then resend that same pair with a forged `shop-domain` header pointing at a different, victim shop. The gem has no defense against this because the shop field is completely outside the cryptographically verified surface, per the documented flow in `docs/usage/webhooks.md` lines 12-30, which explicitly hands `data.shop` to the handler as a trusted value.

### Impact Explanation
This breaks the cross-tenant isolation boundary: a store owner who has installed the app can forge webhook events (e.g., `orders/create`, `customers/data_request`, `shop/redact`) that appear to originate from any other merchant's shop, since `data.shop` is the only tenant discriminator passed to `WebhookHandler#handle`. Any host application that (as documented) uses `data.shop` to select which merchant's stored session/data to act on will process attacker-controlled webhook bodies under the wrong tenant's identity — a cross-tenant access issue as scoped by the assessment criteria.

### Likelihood Explanation
Exploitation only requires an attacker to install the app on a shop they control (an ordinary, unprivileged path available to anyone) and capture one webhook's raw body plus its `x-shopify-hmac-sha256` header — both of which are delivered directly to the attacker's own webhook endpoint. No access to `client_secret`, access tokens, or any privileged account is needed to perform the forgery itself.

### Recommendation
Include the shop domain (and topic) in the signed/verified content used by `Utils::HmacValidator`, or explicitly cross-check `request.shop` against an independently trusted source (e.g., a known list of shops the current registry/session store expects) before dispatching to the handler. At minimum, document prominently that `data.shop` is unauthenticated and must be independently validated by the host application before being used as a tenant key.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`). Shopify delivers:
   - `raw_body = '{"id":1,...}'`
   - `x-shopify-hmac-sha256 = HMAC-SHA256(client_secret, raw_body)` (base64)
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
2. Attacker replays the exact same `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds the request; `Utils::HmacValidator.validate` calls `to_signable_string` (body only) as shown at [1](#0-0)  and succeeds because the body/HMAC pair is unchanged.
4. `Registry.process` calls the handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop == "victim-shop.myshopify.com"`, per [5](#0-4) , even though the payload actually originated from the attacker's own shop.
