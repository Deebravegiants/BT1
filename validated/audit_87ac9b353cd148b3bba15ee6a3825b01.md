### Title
`IntentGatewayV2.placeOrder` on Tron escrows the pre-fee order amount instead of the actual fee-on-transfer token received, over-crediting escrow relative to real balance - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
In the Tron variant of `IntentGatewayV2.placeOrder`, when an order has no predispatch call, the contract calls `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally credits `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` is derived from the pre-transfer `order.inputs[i].amount` (minus the protocol fee), not from the tokens actually received by the contract. For a fee-on-transfer ERC20 input token, the contract receives less than `order.inputs[i].amount`, so the escrow ledger records more tokens than the contract actually holds — exactly the `fundPool`/fee-on-transfer bug class from the external report, reachable here through a single unprivileged `placeOrder` call.

### Finding Description
The vulnerable code path is the `else` branch of `placeOrder` (no predispatch assets/call): [1](#0-0) 

```solidity
} else {
    for (uint256 i; i < inputsLen;) {
        if (order.inputs[i].amount == 0) revert InvalidInput();
        address token = address(uint160(uint256(order.inputs[i].token)));
        if (token == address(0)) {
            // native token
            if (msgValue < order.inputs[i].amount) revert InsufficientNativeToken();
            msgValue -= order.inputs[i].amount;
        } else {
            IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
        }

        // Store reduced amount (after protocol fees) in escrow
        _orders[commitment][token] += reducedInputs[i].amount;
        ...
```

`reducedInputs[i].amount` is computed earlier purely from the caller-supplied `order.inputs[i].amount` minus the protocol-fee percentage: [2](#0-1) 

There is no balance-before/balance-after measurement anywhere in this branch, unlike the predispatch branch (which at least compares `balance` on the dispatcher against `requiredAmount` before sweeping, lines 421-438) and unlike the already-fixed EVM mainline `IntentGatewayV2.sol`, which explicitly captures `balBefore`/`balAfter` deltas to compute the actual received amount before crediting escrow and computing the commitment: [3](#0-2) 

For any ERC20 with a transfer fee/tax (a well-known token category on EVM-compatible chains including Tron/TRC20-style tokens), calling `placeOrder` with such a token as input causes:
1. The contract to actually receive `order.inputs[i].amount * (1 - fee)`.
2. The escrow ledger `_orders[commitment][token]` to be credited with `reducedInputs[i].amount`, which is based on the full pre-fee `order.inputs[i].amount`.

This directly mirrors the reported `Allo._fundPool` issue where `increasePoolAmount` used the pre-transfer amount instead of the actual delta received.

### Impact Explanation
Because `_orders[commitment][token]` is the authoritative escrow accounting used for solver fills/redemption/cancellation payouts, an inflated escrow balance means the gateway's bookkeeping claims to hold more of `token` than it physically possesses. When solvers or the order owner later redeem/cancel and pull the escrowed amount, the contract can attempt to pay out more tokens than its actual balance for that token, which will either:
- revert and permanently freeze the affected order's funds together with any other order sharing that token pool once the contract's real balance is exhausted, or
- allow the first claimants to drain the token balance, leaving later legitimate claimants unable to redeem their entitled amounts (fund freezing/loss for other users of the shared token accounting).

This is a Medium-severity accounting/insolvency bug reachable by any ordinary user simply placing an order with a fee-on-transfer token — no privileged role required.

### Likelihood Explanation
Likelihood is high for any deployment where the input token whitelist (or lack thereof) permits fee-on-transfer/tax tokens. `placeOrder` is a fully public, unprivileged entry point, and the bug triggers deterministically on every such token deposit, with no special preconditions beyond the token having a transfer fee.

### Proof of Concept
1. Deploy a 1% fee-on-transfer ERC20 (e.g., the `FeeOnTransferToken` test helper already present in the same repo at `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` lines 2690-2735) and use it as an input token for the Tron `IntentGatewayV2`.
2. User calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}`, no `predispatch`.
3. `safeTransferFrom(msg.sender, address(this), 1000e18)` executes; the FOT token burns/redirects 1% fee, so the gateway's actual balance increases by only `990e18`.
4. `_orders[commitment][FOT] += reducedInputs[0].amount`, where `reducedInputs[0].amount` is `1000e18` minus only the protocol fee (e.g., `997e18` at 30 bps) — still far above the `990e18` actually held.
5. The escrow ledger now claims `997e18` while the contract only holds `990e18` of that token; any later redemption/fill flow that pays out based on the ledger value will fail once actual funds run out, freezing legitimate claims for other orders sharing the same token's escrow pool.

### Recommendation
In the non-predispatch branch of `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`, measure the actual amount received via balance-before/balance-after around `safeTransferFrom` (as already done in the fixed mainline `evm/src/apps/IntentGatewayV2.sol`), mutate `order.inputs[i].amount` to the real received value, and derive `reducedInputs`/the commitment/escrow credit from that actual amount rather than the caller-supplied pre-transfer amount.
