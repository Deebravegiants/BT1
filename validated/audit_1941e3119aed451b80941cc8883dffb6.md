### Title
Escrow credited before token transfer confirmation in `IntentGatewayV2.placeOrder` (predispatch path) — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron fork of `IntentGatewayV2.placeOrder` credits the escrow ledger `_orders[commitment][token]` for predispatch-routed inputs *before* the actual token transfer that is supposed to back that credit has executed, and the transfer itself is performed via a raw low-level `call` whose ERC-20 return value is never checked. This reproduces exactly the "incorrect order of operations" bug class from the referenced report (state updated before the transfer is confirmed).

### Finding Description
In the predispatch branch of `placeOrder`, the gateway builds a batch of ERC-20 `transfer` calls to sweep tokens from the `CallDispatcher` back to itself, and increments the escrow balance in the *same loop*, before that sweep is executed: [1](#0-0) 

```
Call[] memory transferCalls = new Call[](inputsLen);
for (uint256 i; i < inputsLen;) {
    ...
    transferCalls[i] = Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)});
    ...
    // Store reduced amount (after protocol fees) in escrow
    _orders[commitment][token] += reducedInputs[i].amount;   // <-- effect applied here
    ...
}
// Execute transfer calls from call dispatcher
ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls));  // <-- interaction happens after
```

The `dispatch` function only checks that the low-level call did not revert; it never inspects the ERC-20 boolean return value encoded in `result`: [2](#0-1) 

For any ERC-20 that returns `false` on a failed `transfer` instead of reverting (a well-known non-standard/weak-ERC-20 pattern), `to.call(...)` succeeds (`success == true`), no tokens actually move from the dispatcher to the gateway, yet `_orders[commitment][token]` has already been incremented by `reducedInputs[i].amount` in the prior loop iteration. The escrow record is therefore inflated by an amount never actually received by the gateway.

This differs from the up-to-date `evm/src/apps/IntentGatewayV2.sol`, which snapshots balances before the sweep, dispatches the sweep, and only credits escrow (`_orders[commitment][token] = ...`) afterward, using the *measured* balance delta rather than the requested amount — the correct check-effects-interaction ordering that this Tron variant lacks: [3](#0-2) [4](#0-3) 

The Tron `placeOrder` also lacks the `nonReentrant` guard present in the main contract and never re-measures actual received balances, so the bug is not merely cosmetic — the credited escrow amount is trusted without ever verifying it against the dispatcher's real balance change.

### Impact Explanation
A user can place an order with a predispatch call using a non-reverting-on-failure ERC-20 as an input token. If the transfer of that token from the `CallDispatcher` back to the gateway silently fails (returns `false`), the gateway will still credit the full `reducedInputs[i].amount` to `_orders[commitment][token]`, an escrow entry unbacked by any real token balance. The order's commitment can then be filled/withdrawn by a solver expecting to receive that escrow, draining real assets from the gateway's other, correctly-backed balances (fees, other escrowed tokens, or ETH held by the contract) to cover the phantom credit — a direct theft/insolvency vector against the IntentGateway's escrow accounting.

### Likelihood Explanation
Reachable by any unprivileged caller submitting a single `placeOrder` transaction with `predispatch.call` and `predispatch.assets` populated (a normal, documented feature of the Intent Gateway) using an ERC-20 with non-reverting-transfer semantics. No special privileges, governance, or admin access are required — only a suitable token and the standard order-placement flow.

### Recommendation
Follow the pattern already used in the fixed `evm/src/apps/IntentGatewayV2.sol`: snapshot balances before executing the sweep `dispatch` call, execute the transfer/sweep, then measure the actual balance delta and credit `_orders[commitment][token]` with that measured amount — never with the pre-agreed `reducedInputs[i].amount`. Additionally, have `CallDispatcher.dispatch` (or the transfer call construction) use `SafeERC20`/checked-return-value transfers so a `false` return is treated as a failure and reverts, rather than relying solely on the low-level call's `success` flag.

### Proof of Concept
1. Deploy a "weak" ERC-20 whose `transfer` returns `false` on failure instead of reverting (e.g., insufficient balance or a blacklist check that returns `false`).
2. Call `placeOrder` with `predispatch.call`/`predispatch.assets` set so this token is used as one of `order.inputs`, arranging that the `CallDispatcher`'s post-predispatch balance of the token is insufficient to cover `requiredAmount` in a way that still passes the `balance < requiredAmount` check (e.g., balance check passes on `balance`, but the actual `transfer` in the swept `Call` returns `false` due to some transfer-time condition, such as a paused/blacklist state toggled by the attacker's own hook contract during `dispatch(order.predispatch.call)`).
3. Observe that `ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls))` completes without reverting (the low-level `call` succeeds even though the token's internal `transfer` logic returns `false` and moves no tokens).
4. Observe `_orders[commitment][token]` was already incremented by `reducedInputs[i].amount` earlier in the loop, before the sweep executed — the gateway now believes it holds tokens it never received.
5. A solver can subsequently reference this commitment in a fill/withdraw path, extracting real value equal to the phantom escrow from the gateway's genuine holdings.

        Call[] memory calls = abi.decode(encoded, (Call[]));

        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
