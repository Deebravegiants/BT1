### Title
`PoaBridge.describeWithdrawal` reports wrong status/txHash for duplicate-asset withdrawals in one tx - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`findMatchingWithdrawal` matches a withdrawal only by `assetId`, ignoring `WithdrawalIdentifier.index`, so when a single NEAR transaction contains two or more withdrawal legs of the same POA-routed token to different destinations, both `describeWithdrawal` calls resolve to the same (arbitrary, unsorted) API record. This causes an integrator polling per-index status to attribute one leg's `transfer_tx_hash`/completion to both indices, double-crediting one destination while leaving the other's leg unresolved/misreported.

### Finding Description
The broken equality is STATUS_TRUTH: `describeWithdrawal({index: i}).txHash` should equal the destination tx hash of withdrawal leg `i`, and this must be distinct/independent across `i` for `i=0` and `i=1` when two legs share `assetId`.

Code path:
- `createWithdrawalIdentifiers` (`packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107`) assigns per-route counters via `indexes.get(bridge.route)`, so two `nep141:btc.omft.near` withdrawals in the same tx both route to `PoaBridge` and get `index: 0` and `index: 1` respectively, both carrying the same NEAR tx hash (`args.intentTx`).
- `watchWithdrawal` (`packages/intents-sdk/src/core/withdrawal-watcher.ts:20-78`) calls `bridge.describeWithdrawal({...wid, logger})` per identifier independently, in parallel.
- `PoaBridge.describeWithdrawal` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:313-343`) fetches all withdrawals for the shared NEAR tx hash via `getWithdrawalStatusWithRetry`, then calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`.
- `findMatchingWithdrawal` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:418-427`) does `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)` — it returns the **first** array element matching `assetId`, completely ignoring `args.index`. The code comment at lines 409-416 explicitly documents: "This means multiple withdrawals of the same token in a single transaction are not supported."

Attacker's exact input: sign a single NEAR intent containing two `transfer`/withdrawal legs both with `assetId = "nep141:btc.omft.near"` but two different `destinationAddress` values, submitted in one NEAR tx.

Exploit flow: both `describeWithdrawal({index:0,...})` and `describeWithdrawal({index:1,...})` hit the same POA `getWithdrawalStatus` response (`response.withdrawals` is unsorted/unordered per the code comment), and `findMatchingWithdrawal` returns the same array element (whichever happens to appear first) for both calls. If that element is `COMPLETED`, both index-0 and index-1 resolve to the exact same `transfer_tx_hash`, even though the two legs go to different destination addresses and will produce two distinct real on-chain destination transactions.

Existing guards do not prevent this: `supports()` only checks route/asset applicability, not uniqueness; `validateWithdrawal` validates amount/address per-leg, not cross-leg duplication; there is no dedup check in `sdk.ts`, `createWithdrawalCompletionPromises`, or `createWithdrawalIdentifiers` that rejects duplicate `assetId` withdrawals within one tx.

### Impact Explanation
An integrator that credits a user/destination based on the `txHash` returned per withdrawal index will attribute the same destination transaction hash to both legs. This can cause either double-crediting (if the integrator's off-chain accounting treats the same `txHash` as proof for two separate legs) or a leg being left "unconfirmed" indefinitely if it never independently reports the second destination's actual hash — the integrator has no reliable way to distinguish which physical on-chain transfer went to which requested `destinationAddress`. This matches the High/Critical category "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
Preconditions: attacker (an ordinary NEAR Intents user, using only their own funds/keys) must construct one signed NEAR tx with ≥2 withdrawal legs of the same POA-supported `assetId` to different `destinationAddress`es. This is fully within normal SDK usage (`sdk.ts` accepts an array of `withdrawalParams`) and requires no privileged access, no malicious relayer/bridge/RPC, and no escape-hatch misuse — it is a natural consequence of the documented-but-unguarded limitation in `findMatchingWithdrawal`. It is repeatable on every such batch.

### Recommendation
Either (a) explicitly detect and reject batches containing duplicate `assetId` withdrawals routed to `PoaBridge` within `createWithdrawalIdentifiers`/`supports()` until the POA API supports disambiguation, or (b) implement the deterministic sort-and-match-by-amount/index strategy already described in the code's own comment (sort `response.withdrawals` and the withdrawal params by amount, since relayer fees are identical for same-token legs, then match by relative order/index) instead of naive `assetId`-only matching.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
