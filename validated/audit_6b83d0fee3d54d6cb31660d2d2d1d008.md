### Title
`Webhooks::Request#shop` returns an HMAC-unsigned header value trusted as the authenticated shop identity - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Registry.process` validates only the raw request body against the HMAC, then hands `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all of which come from HTTP headers — straight to the app's handler as `WebhookMetadata`. Because `to_signable_string` returns only `@raw_body`, none of these header-derived values are covered by the signature, so any attacker who can obtain one validly-signed webhook body (e.g. via their own dev shop) can replay it with an arbitrary `shopify-shop-domain`/`x-shopify-shop-domain` header and have the app process it as if it came from a different shop.

### Finding Description
The broken binding claimed by the invariant is: `shop == value inside HmacValidator.to_signable_string`. In fact: [1](#0-0) 
`shop` is read via `shopify_header("shop-domain")`, which resolves from `@headers`: [2](#0-1) 

But the value handed to `HmacValidator` is only the raw body: [3](#0-2) 

`HmacValidator.validate` computes the HMAC purely over `to_signable_string` (`@raw_body`) using the app's shared `api_secret_key`: [4](#0-3) 

`Registry.process` checks only this body HMAC, then trusts `request.shop`/`request.topic`/etc. unconditionally when constructing `WebhookMetadata` for the handler: [5](#0-4) 

`api_secret_key` is the app's single client secret, shared across every shop that installs the app — it is not shop-specific. So the equality `shop (header) == shop implied by the signed bytes` never actually holds; it is not enforced anywhere in the code. Any attacker who runs their own development shop, installs the app, and receives one legitimately-signed webhook (any topic, any body) can:
1. Capture the raw body + valid `x-shopify-hmac-sha256` for that body (computed with the shared secret they don't need to know — it's already been computed for them by Shopify when their own webhook fired).
2. Replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint, substituting `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) with a victim shop's domain / a different topic.
3. `HmacValidator.validate` still succeeds, because the signature check never looks at the headers — only `@raw_body` changed nothing.
4. `Registry.process` calls the app's handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own shop.

The `initialize`/`shopify_header` "OR" precedence between `shopify-*` and `x-shopify-*` spellings doesn't itself introduce a second divergence bug (both paths read from the same normalized `@headers` map, so the presence check and the value lookup are consistent with each other) — but it doesn't matter, because the deeper issue is that neither header spelling is ever part of the signed material. There is no code path in `Request`, `HmacValidator`, or `Registry` that cross-checks the header-derived shop/topic against anything present in the signed body.

### Impact Explanation
Any handler that keys off `WebhookMetadata#shop` (e.g., to look up a stored session/access token for that shop, decide which tenant's data to mutate, or trigger shop-specific side effects such as uninstall cleanup) can be made to act on forged shop identity supplied by an unrelated, attacker-controlled webhook delivery. This is a cross-tenant authentication bypass: one tenant's (the attacker's) genuinely-signed traffic can be relabeled to impersonate another tenant (the victim) at the point the gem hands data to the app, with the gem offering no signal that `shop` is unauthenticated. The blast radius is any shop that has installed the same app instance and is chosen as the attacker's spoof target — repeatable per request, at no marginal cost once the attacker has one valid signed body.

### Likelihood Explanation
Preconditions are minimal and squarely inside the stated attacker model: create a dev shop, install the target app, register a webhook, and capture one valid `(raw_body, hmac)` pair delivered to your own endpoint. No secrets, no privileged access, no shop-specific behavior are required — `api_secret_key` is shared across all installs of the app. The forgery step (changing the shop-domain header on replay) is trivial and fully within attacker control of headers, as stated in the rules.

### Recommendation
Do not let `Webhooks::Request#shop`/`#topic`/`#webhook_id`/`#api_version` be treated as authenticated data by downstream code without further application-level verification (e.g., matching against a shop known to be installed with a corresponding registered webhook path/session), and/or document explicitly in `WebhookMetadata` that `shop` is unsigned header data. Where feasible, incorporate a canonicalized set of the relevant headers into `to_signable_string` so header tampering invalidates the HMAC, matching how Shopify's own webhook verification is documented to work end-to-end.

### Proof of Concept
```ruby
# test/webhooks/request_shop_spoof_test.rb
require "test_helper"

class WebhookShopSpoofTest < Test::Unit::TestCase
  def test_same_signed_body_can_be_attributed_to_two_different_shops
    body = "{}"
    hmac = Base64.encode64(
      OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)
    )

    attacker_headers = {
      "x-shopify-topic" => "orders/create",
      "x-shopify-hmac-sha256" => hmac,
      "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
    }
    victim_headers = attacker_headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

    req_attacker = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: attacker_headers)
    req_victim   = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: victim_headers)

    # Both pass the same HMAC check ...
    assert(ShopifyAPI::Utils::HmacValidator.validate(req_attacker))
    assert(ShopifyAPI::Utils::HmacValidator.validate(req_victim))

    # ... yet resolve to two different "authenticated" shops for one signature.
    refute_equal(req_attacker.shop, req_victim.shop)
    assert_equal("attacker-shop.myshopify.com", req_attacker.shop)
    assert_equal("victim-shop.myshopify.com", req_victim.shop)
  end
end
```
This demonstrates that `Webhooks::Registry.process` (which only calls `HmacValidator.validate(request)` before trusting `request.shop`) will accept the victim-attributed request as authentic, even though the shop identity was never part of the signed bytes.
