### Title
Webhook `shop`/`topic`/`webhook_id` identity fields are trusted from unauthenticated headers while the HMAC only signs the raw body, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but only binds the HMAC to the raw request body, not to the `shop`, `topic`, or `webhook_id` header values that `Registry.process` later trusts and dispatches to app handlers. This breaks the intended binding: `HMAC(secret, signed_bytes) == received_hmac` should imply `signed_bytes ⊇ {shop, topic, body}`, but here `signed_bytes = body` only.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Yet `shop`, `topic`, and `webhook_id` are all read straight from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates only the body-HMAC via `HmacValidator.validate`, then immediately trusts `request.topic` and `request.shop` to route the payload to the registered handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `to_signable_string`, i.e., the body: [4](#0-3) 

This is structurally the same class of bug as the report: a value used downstream (fee recipients in the report; `shop`/`topic` tenant-identity fields here) is excluded from the computation/check that is supposed to bind it (the PNL deduction; the HMAC signature here). Compare with `Auth::Oauth::AuthQuery`, where `shop` and other OAuth query params *are* explicitly included in `to_signable_string` and thus covered by the HMAC: [5](#0-4) 

Because the webhook `shop` header is never part of the signed bytes, anyone who obtains one valid `(raw_body, hmac)` pair — e.g., from a legitimate webhook delivered to their own store, since installing the app on a store they control is unprivileged — can resubmit that exact body to the app's webhook endpoint with a different `x-shopify-shop-domain` and/or `x-shopify-topic` header. The signature check still passes because it only verifies the body bytes, and the handler is invoked with attacker-chosen `shop`/`topic` values via `WebhookMetadata`, causing the app to process/store data under the wrong tenant.

### Impact Explanation
This crosses the tenant boundary the report's rubric calls out ("a shop authenticated versus the shop stored" / "a field acted on but not covered by the HMAC"). An app that keys any per-shop state, database writes, or business logic off `WebhookMetadata#shop` (as the library's own webhook contract documents) can be made to attribute another shop's webhook data/actions to an attacker-chosen shop, or reprocess data under a spoofed topic — a cross-tenant integrity violation reachable by any unprivileged user who can install the app on a store they control and capture one legitimate webhook delivery.

### Likelihood Explanation
Getting a valid `(body, hmac)` pair requires no privileged credentials — installing the app on a free/dev store and triggering any webhook (e.g., `orders/create`) is enough, this is exactly the "unprivileged internet user" scenario. Forging the headers is trivial (plain HTTP), and `Registry.process`/`HmacValidator.validate` perform no additional binding check on `shop` or `topic`.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or at minimum `shop` and `topic`) in `Request#to_signable_string`, or otherwise cryptographically bind them to the verified payload before they are handed to `Registry.process` and the registered `WebhookHandler`. If matching Shopify's actual wire format prevents including headers in the HMAC input, at minimum require the host application to cross-check `request.shop` against an independently-authenticated shop identity (e.g., session/account lookup) before acting on webhook data, rather than trusting the header value implicitly.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com` (no privilege required) and trigger a webhook, e.g. `orders/create`, capturing the legitimate request: `raw_body = B`, header `x-shopify-hmac-sha256 = H` (valid for `B`), `x-shopify-shop-domain = attacker-shop.myshopify.com`.
2. Replay the same `B` and `H` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com` (and/or change `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H`: [6](#0-5) 
4. The registered handler is invoked with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body `B`, even though that shop never sent this webhook — demonstrating the cross-tenant identity binding is not covered by the signature.

        end
