### Title
Webhook shop-domain header is trusted for tenant routing without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the HMAC over the raw request body only, while the `shop-domain` (and `topic`) headers used to identify which merchant/tenant the webhook belongs to are read directly from unauthenticated HTTP headers and are never included in the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` verifies the `hmac-sha256` header strictly against `to_signable_string`, i.e. only the body: [2](#0-1) 

But `Request#shop` (from the `shopify-shop-domain` / `x-shopify-shop-domain` header) is read straight from attacker-controllable headers with no cryptographic binding to the HMAC: [3](#0-2) 

`Registry.process` validates only the HMAC and then forwards `request.shop` (and `request.topic`) directly into `WebhookMetadata`, which is handed to the host application's handler as the tenant identifier for the event: [4](#0-3) 

This is the same bug class as the report: a value that downstream logic relies on for identity (here, tenant/shop) is used without being covered by the same integrity check that is supposed to authenticate the request (there, `totalSupply`/`last_update` mutated without the guarding check; here, `shop`/`topic` headers consumed without HMAC coverage). The equality that should hold is: `shop used for tenant lookup == shop cryptographically bound to the signed payload`. In this implementation that equality is not enforced — only `raw_body == HMAC(raw_body, secret)` is checked, and `shop` is disjoint from that check.

### Impact Explanation
Any actor capable of obtaining one genuine, validly-signed webhook delivery for a body they control (e.g. by installing the app on their own store and triggering an event that produces an attacker-influenced body, or capturing/replaying an intercepted delivery) can resend that exact body+HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop. Because the HMAC never covers the header, verification succeeds, and the host application's handler executes with `data.shop` set to the victim shop. If the handler uses `data.shop` to look up a per-shop session/access token or perform per-tenant side effects (the intended and documented usage pattern), this results in cross-tenant processing under a shop identity the attacker does not own/control — an authentication/tenant-binding bypass. This aligns with the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires the attacker to already be able to trigger at least one legitimately-HMAC-signed webhook body (trivially achievable by any developer/merchant who installs the app themselves, since they fully control data that ends up in many webhook payloads, e.g. product/order fields), and does not require the app's `client_secret` or any credential belonging to the victim. Given webhook endpoints are public HTTP endpoints by design, likelihood is moderate-to-high wherever a host application trusts `WebhookMetadata#shop` for tenant context without an independent check (e.g. cross-referencing against the registered webhook_id/shop mapping).

### Recommendation
Bind the identity fields to the authenticated payload rather than trusting bare headers:
- Include `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) in the HMAC-signable string, or
- Independently verify `request.shop` against Shopify's known registration (e.g., cross-check `webhook_id` against the shop it was registered for via a stored mapping) before invoking the handler, and
- Document clearly that `WebhookMetadata#shop` is not currently cryptographically authenticated, so consuming applications do not treat it as a trusted tenant identifier.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and triggers a webhook whose body content they can fully control/predict (e.g. a webhook subscribed with `fields` limited to attacker-supplied text fields).
2. Shopify delivers the webhook with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body>`.
3. Attacker replays the identical POST body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds (body unchanged, so HMAC recomputation matches) as shown in: [5](#0-4) 
5. `handler.handle` is invoked with `WebhookMetadata#shop == "victim.myshopify.com"`, even though the request was neither sent by Shopify for that shop nor authorized by that shop.
