## Analysis

The CVE describes a DNS resolver caching answers to crafted queries **before** those answers are validated/finalized, letting an attacker pollute data other clients later read from the cache. The closest analog in this codebase is the intents-coprocessor's `BidCache`, which caches `place_bid` bids straight out of the **transaction pool** — before they are ever included in a block or their on-chain effects (deposit reservation) are validated — and serves that unconfirmed data to any RPC caller and to the SDK's phantom-order price aggregation.

### Root cause

`BidCache` is populated by `run_bid_watcher`, which subscribes to the pool's `import_notification_stream` and extracts bid data from any transaction the pool considers "ready" (i.e., signature/nonce valid, not yet executed or finalized): [1](#0-0) 

The cache itself is an unbounded `HashMap<H256, OrderBids>` keyed by order commitment, with no bound on the number of distinct commitments or the number of fillers per commitment: [2](#0-1) 

`get_bids_for_order` merges these unconfirmed mempool entries with genuine on-chain/offchain bids and returns them to any caller of `intents_getBidsForOrder`, with no distinction flagging which entries are still unconfirmed mempool data versus finalized bids: [3](#0-2) 

That RPC is exactly what the SDK's phantom bid aggregation (used to compute published liquidity-pool exchange rates from a weighted median of solver quotes) reads from: [4](#0-3) 
and the indexer's documented flow confirms every bid for a commitment (mempool + finalized) feeds `aggregatePhantomBids`, whose `weightedMedian` selection publishes one bidder's exact quote as the on-chain rate: [5](#0-4) 

### Why this matters

A `place_bid` extrinsic only needs to pass the pool's admission checks (valid signature/nonce) to be cached and broadcast — it does **not** need to ever land in a finalized block, and its on-chain deposit/execution effects (visible via `getBidStorageEntries`, which reports "filler addresses and deposits") are never checked before the bid is exposed. An attacker who is (or controls) a legitimately EIP-7702-delegated solver account can submit a mempool-only `place_bid` with an inflated `user_op` amount, have it observed and cached/broadcast by `run_bid_watcher`, let the price-snapshot window aggregate it into the weighted median, and then let the transaction be dropped/evicted from the pool without ever confirming — so the published rate reflects a bid nobody actually backed. Because `weightedMedian` selects one bidder's exact integer as the rate (not a blend), a single such phantom, never-executed bid can set the on-chain liquidity-pool price other solvers and users rely on.

This is analogous to CVE-2018-14626's core defect: a cache populated from unauthenticated/unvalidated input, served onward as if authoritative, allowing an attacker to corrupt the view other parties act on.

I was unable to confirm from the index the exact TTL value passed to `BidCache::new` in production (`parachain/node/src/service.rs`), nor whether pool eviction/replacement policies (e.g., minimum bond to enter the pool) meaningfully restrict how long a phantom bid can remain visible before the price-snapshot window closes — these would materially affect exploitability and should be checked in a live session before treating this as fully proven.

### Title
Unvalidated Mempool Bids Cached and Served as Authoritative — Phantom Bid Cache Poisoning ([File: modules/pallets/intents-coprocessor/rpc/src/lib.rs])

### Summary
`BidCache`, populated purely from transactions observed in the node's transaction pool (not yet included in a block or executed), is merged indistinguishably with confirmed on-chain bids and exposed via the `intents_getBidsForOrder` RPC, which the SDK's phantom-order price aggregation consumes to compute published liquidity-pool exchange rates.

### Finding Description
`run_bid_watcher` extracts `place_bid` calls from any "ready" pool transaction and inserts them into `BidCache` without waiting for block inclusion or verifying the bid's on-chain deposit/execution succeeds [6](#0-5) . `get_bids_for_order` merges these transient, unconfirmed entries with genuine on-chain bids with no marker distinguishing the two [3](#0-2) . Downstream, `aggregatePhantomBids` fetches "every bid for the commitment" through this same RPC path and computes a `weightedMedian` that is published verbatim as a pool's exchange rate [7](#0-6) .

### Impact Explanation
A solver with a genuine EIP-7702 delegation can submit a signed `place_bid` extrinsic with an attractive quote, have it cached/served by the RPC while still unconfirmed, and let it be dropped from the pool before ever executing on-chain. If aggregation runs while the phantom bid is visible, it can set the published `sellRate`/`buyRate` for a token pair from a bid that was never economically backed, since `weightedMedian` selects one bidder's exact figure as the rate rather than a blend.

### Likelihood Explanation
Requires the attacker to control (or be) a delegated solver account and time submission relative to the price-snapshot window (`PhantomBidWindowExhausted`), but no special privilege beyond that of any intent solver — the codebase's own comments show this cache accepts data straight out of the mempool.

### Recommendation
Do not serve or aggregate mempool-only bid entries as equivalent to confirmed on-chain bids: either exclude `BidCache` entries from price aggregation entirely, or clearly flag them as unconfirmed and require aggregation to wait for finality before including a filler's quote in `weightedMedian`.

### Proof of Concept
Conceptual: (1) attacker's delegated solver account signs a `place_bid` extrinsic with a large `user_op` amount for a target commitment; (2) submits it to the node's pool via `author_submitExtrinsic`; (3) `run_bid_watcher` observes it as "ready" and caches/broadcasts it before block inclusion, as shown by the existing `test_bid_discovery_via_rpc` test confirming mempool-only bids are returned by `intents_getBidsForOrder` [8](#0-7) ; (4) if aggregation runs in this window, the phantom bid is priced into the published rate; (5) the extrinsic is allowed to be dropped from the pool without ever executing, so no funds actually backed the published quote.

/// In-memory bid cache.
pub struct BidCache {
	bids: RwLock<HashMap<H256, OrderBids>>,
	ttl: Duration,
}

impl BidCache {
	pub fn new(ttl: Duration) -> Self {
		Self { bids: RwLock::new(HashMap::new()), ttl }
	}

	pub fn insert(
		&self,
		commitment: H256,
		filler: Vec<u8>,
		user_op: Vec<u8>,
	) -> Result<(), String> {
		let entry = BidEntry { filler: filler.clone(), user_op };

		let mut bids = self.bids.write().map_err(|e| format!("BidCache lock poisoned: {e}"))?;
		let order = bids
			.entry(commitment)
			.or_insert_with(|| OrderBids { first_seen: Instant::now(), entries: Vec::new() });
		if let Some(existing) = order.entries.iter_mut().find(|e| e.filler == filler) {
			*existing = entry;
		} else {
			order.entries.push(entry);
		}
		Ok(())
	}

	fn get_bids_for_order(&self, commitment: H256) -> RpcResult<Vec<RpcBidInfo>> {
		// Get mempool bids from in-memory cache
		let mut bids =
			self.bid_cache.get_bids(&commitment).map_err(runtime_error_into_rpc_error)?;

		// Query on-chain bids via StorageProvider and read bid data from offchain storage.
		let best_hash = self.client.info().best_hash;
		let prefix = bids_storage_prefix(&commitment);
		let prefix_key = sp_core::storage::StorageKey(prefix.clone());

		let keys = self
			.client
			.storage_keys(best_hash, Some(&prefix_key), None)
			.map_err(runtime_error_into_rpc_error)?;

		const MAX_ON_CHAIN_BIDS: usize = 30;

		for key in keys.take(MAX_ON_CHAIN_BIDS) {
			// Key layout after prefix: blake2_128(filler) ++ filler_encoded
			let filler_start = prefix.len() + 16;
			if key.0.len() > filler_start {
				let filler_encoded = &key.0[filler_start..];

				let offchain_key =
					pallet_intents_coprocessor::offchain_bid_key_raw(&commitment, filler_encoded);

				if let Some(data) = self.offchain_storage.get(STORAGE_PREFIX, &offchain_key) {
					// Bid encoding: filler.encode() ++ user_op.encode()
					if data.len() > filler_encoded.len() {
						if let Ok(user_op) = Vec::<u8>::decode(&mut &data[filler_encoded.len()..]) {
							bids.insert(RpcBidInfo {
								commitment,
								filler: filler_encoded.to_vec(),
								user_op,
							});
						}
					}
				}
			}
		}

		Ok(bids.into_iter().collect())
	}
