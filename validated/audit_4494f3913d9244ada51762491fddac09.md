Confirmed: the webhook `hmac` is computed only over `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are pulled directly from HTTP headers with no cryptographic binding to the signature [2](#0-1) . `Registry.process` validates only `Utils::HmacValidator.validate(request)` (which in turn calls `to_signable_string`, i.e., body-only) and then forwards `request.shop`/`request.topic` straight to the handler as trusted tenant identity [3](#0-2) .

### Title
Webhook shop-domain header not covered by HMAC allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `Utils::HmacValidator.validate` verifies the HMAC exclusively against that body [1](#0-0) [4](#0-3) . The `shop`, `topic`, `webhook_id`, and `api_version` values used downstream by `Registry.process` and passed into `WebhookMetadata` come from unauthenticated HTTP headers (`x-shopify-shop-domain`, etc.) that are never included in the signed payload [5](#0-4) [3](#0-2) .

### Finding Description
The equality broken is: `hmac_valid(raw_body) == hmac_valid(shop_header)`. Since the app's `api_secret_key` is shared across every merchant/tenant that has the app installed, any user who legitimately controls one shop (an "unprivileged" tenant relative to other merchants) can capture a valid `(raw_body, hmac)` pair for a webhook topic whose body content is generic or shop-independent (e.g., `app/uninstalled` with an empty `{}` body, or any topic where the payload doesn't embed shop-specific identifiers checked by the handler). That attacker can then replay the exact same raw body and HMAC value to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` will pass, because the shop header plays no role in `to_signable_string`, and `Registry.process` will hand the handler a `WebhookMetadata` claiming `shop: <victim>` with attacker-chosen body content [6](#0-5) .

### Impact Explanation
If a host application trusts `WebhookMetadata#shop` (as documented/intended usage) to select which tenant's data/session to act on, this allows cross-tenant confusion: an attacker-controlled shop can trigger a webhook handler under the identity of another merchant. Depending on the handler (e.g., data sync, deprovisioning on `app/uninstalled`, billing state updates), this can lead to cross-tenant data corruption or unauthorized state changes, satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Requires the attacker to already be a legitimate app-installing merchant (to capture one valid `(body, hmac)` pair) and a webhook topic whose payload is generic/shop-independent, so exploitability is topic-dependent, but the endpoint is otherwise unauthenticated and internet-reachable, and no secret material is required to construct the forged request — only replay of previously-observed bytes with a different header.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string (or otherwise cryptographically bind the header-provided identity to the signed payload) in `ShopifyAPI::Webhooks::Request#to_signable_string`, or require host applications to independently verify that `shop` matches an expected/registered value before trusting `WebhookMetadata`.

### Proof of Concept
1. App installs on Shop A; attacker controls Shop A and receives a legitimate webhook, e.g. `app/uninstalled` with body `{}` and header `X-Shopify-Hmac-Sha256: <valid-hmac-of-"{}">`.
2. Attacker POSTs to the app's webhook endpoint with body `{}`, the same valid HMAC header, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and `X-Shopify-Topic: app/uninstalled`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(api_secret_key, "{}")` — this succeeds [7](#0-6) .
4. The registered handler receives `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", ...)` and performs its `app/uninstalled` logic (e.g., revoking access, deleting data) against the victim shop, even though the request never originated from Shopify for that shop [6](#0-5) .
