### Title
Unfunded `recapitalize` pays a "refund" out of supplier custody without receiving any deposit - (File: contracts/pool/src/ops/recapitalize.rs)

### Summary
`Pool::recapitalize(hub_asset, payer, amount)` credits up to the market's backing shortfall to `cash` and then transfers `amount - applied` back to `payer` — but it never measures or requires that `payer` actually sent `amount` tokens to the pool first. Unlike every other inbound flow (supply/repay use measured receipts), `accounting` is executed before any tokens move, so an unprivileged caller can pass an `amount` up to the pool's entire token balance, have `applied == 0` when the market is solvent, and receive the full `refund` out of supplier custody.

### Finding Description
In `contracts/pool/src/ops/recapitalize.rs`, `apply` runs `accounting` first and then calls `outcome.cache.transfer_out(&payer, outcome.refund)` (lines 32–34). `accounting` computes `applied = amount.min(backing_shortfall)` and `refund = amount - applied`, credits `cash`, and commits (lines 52–58). There is no balance-delta measurement of the inbound transfer — the doc comment says "The controller transfers `amount` into the pool before this call," but nothing on-chain enforces that.

The analog to the kernel bug is a resource acquired without ownership verification on the non-error path: `of_iomap` leaked a mapping; here the refund leg "leaks" custody — value is released against a deposit that was never received. The in-repo test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` in `contracts/pool/tests/flows.rs:3408-3483` demonstrates exactly this: it calls `client().recapitalize(&hub, &payer, &custody)` with `payer` an unfunded `Address::generate`, the pool balance goes to 0, and the cash book still overstates custody, so a supplier's later `withdraw` passes the book-based liquidity guard (`require_reserves`) and then fails inside the SAC transfer with `BalanceError = 10`.

### Impact Explanation
Permanent freezing of user funds / direct theft, protocol insolvency:

- If `recapitalize` is permissionless on the pool (the in-repo test calls it directly on the pool client with an arbitrary `payer`, and `permissionless_entrypoints.txt` lists it), any address can drain the full token balance of every market as "refund" without depositing anything — direct theft of all supplier custody.
- Even if reached only via `Controller::recapitalize` after a bad-debt write-down, the refund-to-`payer` semantics let a caller underfund and still extract pool balance.
- After the drain, `cash` still claims the funds exist (the book credited `applied` without real inflow, or stayed ≥ deposit per the test), so honest suppliers' `withdraw`/`borrow` reverts inside the SAC transfer — permanent freeze until governance manually recapitalizes.

### Likelihood Explanation
High if the entrypoint is permissionless: a single `recapitalize(hub, attacker, pool_balance)` call with `amount` ≥ `backing_shortfall + balance` refunds the whole balance; no collateral, oracle, or auth setup needed. If routed through `Controller::recapitalize`, the controller presumably transfers in first — I could not fully verify the controller-side call and the exact auth/permission surface of the pool entrypoint within the available iterations, which is the main residual uncertainty. The demonstrated test path calls the pool directly and succeeds, so the missing inbound measurement is confirmed regardless.

### Recommendation
Measure the deposit, don't trust it: snapshot the pool's token balance before crediting, compute `received = balance_after_in - balance_before` (as `payments::transfer_amount_measured` does for supply/repay in `strategies/legs.rs:50-57`), and cap `applied`/`refund` to `received`. Alternatively, require the `payer`/`caller` auth and pull `amount` into the pool inside `recapitalize` itself via `token.transfer`, then compute the refund from actual received funds.

### Proof of Concept
Existing in-repo demonstration, `contracts/pool/tests/flows.rs:3408-3483`: mint 10_000_000_000 to the pool via `supply`, call `recapitalize(hub, unfunded_payer, custody)` — `token.balance(pool) == 0` while `cash` book ≥ deposit; a subsequent full `withdraw` fails with SAC `BalanceError = 10`, proving custody left without a corresponding deposit.
