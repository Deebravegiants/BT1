### Title
Supply-index accrual overflow permanently freezes a saturated market - ([File: common/src/rates/index.rs])

### Summary
A user can deposit up to the validated supply-cap domain so that total scaled supply approaches `i128::MAX`, after which even modest supply-index growth makes `supplied * supply_index / RAY` unrepresentable. Every later mutation path accrues through `global_sync` and reverts in `update_supply_index`, permanently freezing withdrawals, repayments, liquidations, recapitalization, and revenue claims while any borrow keeps producing supplier rewards.

### Finding Description
`Controller::supply` is permissionless for the caller’s own account and transfers an attacker-selected positive amount into the pool before minting scaled shares. [1](#0-0) [2](#0-1) 

Listing validation permits a cap as large as `floor(i128::MAX / 10^(27-decimals))`, and spoke usage admits scaled supply up to the cap converted at the current index. [3](#0-2) [4](#0-3) [5](#0-4) 

At the initial `RAY` index, `calculate_scaled_supply` returns the token amount rescaled to RAY, so a maximum-cap deposit can put `supplied` within a small margin of `i128::MAX`. [6](#0-5) [7](#0-6) 

`Controller::update_indexes` is permissionless and drives pool accrual; each accrual chunk calls `update_supply_index` when supplier rewards are nonzero. [8](#0-7) [9](#0-8) [10](#0-9) 

`update_supply_index` computes `supplied.mul(old_index)`, where `Ray::mul` evaluates `supplied * old_index / RAY`; once `supplied > floor(i128::MAX * RAY / old_index)`, the exact widened quotient cannot fit `i128` and panics with `MathOverflow`. [11](#0-10) [12](#0-11) [13](#0-12) 

All normal pool legs load a synced market before checking or mutating the position, so the panic occurs before repayment, withdrawal, or other recovery accounting can reduce `supplied`. [14](#0-13) [15](#0-14) [16](#0-15) 

### Impact Explanation
Once the committed supply index crosses the representability threshold and ledger time advances again, every operation that accrues that market traps before it can burn supply or debt. This permanently freezes supplier funds and prevents borrower repayment, liquidation, bad-debt cleanup, flash operations, and protocol-revenue settlement for that market, satisfying the permanent-freezing impact class. [17](#0-16) [18](#0-17) 

The deposit itself remains trapped because the attacker's near-maximum position also fails `unscale_supply` once the index exceeds the same threshold. [19](#0-18) [20](#0-19) 

### Likelihood Explanation
The attack requires an asset listed with a supply cap close to `max_cap_for_decimals`, enough attacker-held tokens to reach that cap, and nonzero borrow outstanding with less than a 100% reserve factor so supplier rewards continue growing the index. Those conditions use only accepted configuration bounds and permissionless `supply`, `borrow`, and `update_indexes` calls; no privileged action, oracle manipulation, invalid parameter, or reentrancy is required.

For a three-decimal asset, the configured cap can be `floor(i128::MAX / 10^24) = 170141` base units, producing `170141 * 10^24` shares and requiring supply-index growth of only about `i128::MAX / supplied - 1 ≈ 0.00000108` before the next valuation overflows. [3](#0-2) [6](#0-5) 

### Recommendation
Bound total scaled supply against the worst-case index, not merely `i128::MAX`: enforce `supplied <= i128::MAX / (MAX_SUPPLY_INDEX_RAY / RAY)` on supply mints and revenue-share mints, or redesign index updates and valuations to preserve exact `I256` totals without converting an unrepresentable market value back to `i128`. Also add a regression test that deposits at `max_cap_for_decimals`, accrues positive supplier rewards twice, and then successfully withdraws or repays. [21](#0-20) [22](#0-21) 

### Proof of Concept
```rust
// Market: asset_decimals = 3, positive borrow rate, reserve_factor < BPS.
let cap = i128::MAX / 10i128.pow(24); // 170141 base units.
let market = HubAssetKey { hub_id, asset };

// Attacker creates an account and supplies the maximum representable cap.
controller.supply(
    attacker,
    0,
    spoke_id,
    vec![env, (market.clone(), cap)],
);

// Attacker keeps a positive borrow open, or another borrower supplies debt.
// Once a successful accrual pushes supply_index above
// floor(i128::MAX * RAY / supplied), wait for a later ledger timestamp.
controller.update_indexes(attacker, vec![env, market.clone()]);

// Every subsequent state-changing call that reaches this market reverts in
// global_sync -> update_supply_index before user accounting runs.
controller.update_indexes(attacker, vec![env, market.clone()]); // MathOverflow
controller.withdraw(victim, victim_id, vec![env, (market.clone(), 0)], None); // reverts
controller.repay(payer, borrower_id, vec![env, (market.clone(), 1)]); // reverts
```

The first accrual is safe at the old index, but after it commits an index above `i128::MAX * RAY / supplied`, the next accrual computes an unrepresentable supplied value and the typed panic aborts the entire transaction. [23](#0-22) [24](#0-23)

```rust
pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))
```

```rust
pub fn try_mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> Option<i128> {
    if x < 0 || y < 0 || d <= 0 {
        return None;
    }
    let half = d / 2;

    // Fast path: the biased product fits `i128`, so the whole computation is
    // native. `x * y + half` is non-negative here, so `/` is the floor the
    // widened path would produce.
    if let Some(biased) = x
        .checked_mul(y)
        .and_then(|product| product.checked_add(half))
    {
        return Some(biased / d);
    }

    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    x256.mul(&y256)
        .add(&I256::from_i128(env, half))
        .div(&d256)
        .to_i128()
}
```
