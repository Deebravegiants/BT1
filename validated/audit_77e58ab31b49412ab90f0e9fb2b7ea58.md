### Title
Malicious order input token permanently freezes escrow via unbounded revert in `IntentGatewayV2.withdraw()` - (File: `evm/src/apps/IntentGatewayV2.sol` / `evm/tron/contracts/apps/IntentGatewayV2.sol` / `IntentsBase.sol`)

### Summary
`IntentGatewayV2`'s escrow release path loops over every token in an order and transfers it to the beneficiary in a single atomic call. Because the order creator freely chooses the `input`/`output` token addresses at `placeOrder` time, a malicious user can include a token contract that reverts only when `transfer`'s `to` is the solver/beneficiary address determined at fill/redemption time. When the `RedeemEscrow`/`RefundEscrow` message is later delivered through Hyperbridge, the entire `withdraw()` call reverts, permanently freezing every escrowed token in that order — including the legitimate ones — mirroring the C4 M-17 pattern where one poisoned reward token blocks withdrawal of all taxes.

### Finding Description
`IntentGatewayV2.withdraw()` iterates the token list of a `WithdrawalRequest` and transfers each one to the `beneficiary` before finalizing the order: [1](#0-0) 

Each transfer uses a raw `.call` to `IERC20.transfer`, and `if (!success) revert TransferFailed();` — a single failing token aborts the whole function, including the fee-token transfer and the `_filled` bookkeeping that happens in the same call: [2](#0-1) 

The same pattern exists in the sibling implementation `IntentsBase._withdraw()`, which is also called with attacker-influenced token lists from order inputs/outputs: [3](#0-2) 

`withdraw()` is invoked from `onAccept`/`onGetResponse` when Hyperbridge delivers a `RedeemEscrow`/`RefundEscrow` request or a cancellation GET response: [4](#0-3) [5](#0-4) 

The order creator controls the input token addresses supplied at `placeOrder`, and these same addresses flow unchanged into the `WithdrawalRequest.tokens` used by `withdraw()` when the order is later redeemed/refunded/cancelled. A token that reverts conditionally (e.g., only when `to == <solver address>`, or only after a delay/blacklist toggle) will cause `withdraw()` to revert deterministically every time it is retried with the same beneficiary, since the transfer arguments (`token`, `beneficiary`) are fixed by the immutable order data.

This differs from the ordinary `EvmHost.dispatchIncoming` retry-safety net: while `dispatchIncoming` catches the `onAccept`/`onGetResponse` low-level call failure and deletes the request/response receipt so delivery "can be retried" (`evm/src/core/EvmHost.sol:809-818`), that only prevents *permanent* rejection at the host layer — it does not help here because the malicious token's revert condition is deterministic and tied to the fixed beneficiary address baked into the order, so every retry fails identically. The result is that the escrowed tokens (all of them, not just the malicious one) can never be released: [6](#0-5) 

### Impact Explanation
This is a permanent freezing-of-funds bug reachable by a single unprivileged `placeOrder` transaction plus normal solver/relayer activity — no privileged role is required. A malicious order creator can:
- Place a cross-chain or same-chain order whose input token list includes one poisoned ERC-20 alongside legitimate assets (e.g., USDC/DAI).
- After a solver fills the order (escrowing solver capital / advancing output assets) and the redemption/refund message is delivered, `withdraw()` reverts unconditionally because the poisoned token's transfer to the fixed beneficiary always fails.
- All escrowed tokens for that order (the legitimate ones too), plus any accumulated transaction fees for that commitment, become permanently locked in the `IntentGatewayV2` contract, since there is no fallback path to skip a single failing token or to withdraw remaining sound tokens individually.

This can be weaponized to grief solvers: a solver who fills such an order believing they will be paid the escrowed input in return never receives it, since the escrow release call always reverts, while the solver's genuine payout to the order's beneficiary/order-owner was already made in `_fillCrossChain`/`_fillSameChain`. This is value leakage and fund freezing of the same class as the reported M-17 (Medium severity), not theft or unbacked mint.

### Likelihood Explanation
Likelihood is moderate-to-high: placing an order with an arbitrary ERC-20 address is a normal, permissionless action (`placeOrder`), and crafting a token that conditionally reverts on `transfer` to a specific address is a well-known, cheap attack primitive (analogous to malicious/blacklisting tokens seen across DeFi). The attacker needs no special privileges — only the ability to deploy a token contract and place an order using it as an input asset. The only constraint is convincing a solver to fill the order, which is economically plausible since the order can otherwise appear profitable.

### Recommendation
- In `withdraw()` / `_withdraw()`, wrap each token transfer in a try/catch (or a low-level call check) that does not propagate a revert for the whole function; on failure, either (a) skip that token and re-credit/carry over its escrowed balance so it can be withdrawn separately later, or (b) require finalize/`_filled` bookkeping and fee transfer to happen independently of any single token's transfer outcome.
- Consider decoupling per-token withdrawal from the batch (e.g., an explicit `withdrawToken(commitment, tokenIndex)` entry point) so a single poisoned token cannot block release of the rest of the escrow.
- Alternatively/additionally, maintain an allowlist of tokens usable in `Order.input`/`Order.output`, or require a minimum "sanity transfer" test at `placeOrder` time so poisoned tokens are rejected before escrow occurs.

### Proof of Concept
1. Deploy `EvilToken`, an ERC-20 whose `transfer(to, amount)` succeeds normally but `revert()`s specifically when `to == solverAddress` (the address the attacker expects to fill the order), e.g. keyed on a hardcoded/attacker-chosen address or toggled via a flag the attacker controls before redemption.
2. Attacker calls `IntentGatewayV2.placeOrder` with `order.inputs` = `[EvilToken (amount X), DAI (amount Y)]`, escrowing both tokens in the gateway (`_orders[commitment][token] += amount`).
3. A solver calls `fillOrder`, providing the required outputs and thereby becoming the intended beneficiary of the input escrow release.
4. The fill dispatches a `RedeemEscrow` request cross-chain (or resolves same-chain), eventually invoking `withdraw(body, false)` with `body.beneficiary == solver`.
5. Inside `withdraw()`, the loop reaches `EvilToken.transfer(solver, X)`, which reverts. `if (!success) revert TransferFailed();` aborts the entire call — the DAI transfer, the fee-token transfer, and the `_filled` write never happen.
6. Every retry of the delivery (via `EvmHost.dispatchIncoming`'s retry path) hits the same deterministic revert, since `beneficiary` (the solver) never changes. The DAI and any transaction fees remain permanently locked in `IntentGatewayV2`, and the solver never receives their entitled escrow despite having already paid out the order's outputs.

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
