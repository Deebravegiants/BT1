### Title
Webhook shop-domain identity spoofing due to HMAC covering only the request body, not the shop header - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating an HMAC computed over the raw request body only, then hands the caller-supplied `shop`, `topic`, `webhook_id`, and `api_version` headers to the app's handler unverified. Because the shop identity is never covered by the signature, any party who can obtain one legitimately-signed `(body, hmac)` pair for the app's shared `api_secret_key` can replay it to the app's webhook endpoint while swapping the `x-shopify-shop-domain` (and `x-shopify-topic`) header, causing the host app to attribute attacker-controlled data to a different, victim tenant.

### Finding Description
`Utils::HmacValidator.validate` verifies the signature against `verifiable_query.to_signable_string`, and for webhooks that string is defined as just the raw body: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from HTTP headers with no cryptographic binding to the body or the HMAC: [2](#0-1) 

`Registry.process` validates only that HMAC-over-body check and then dispatches the header-derived `shop` directly into `WebhookMetadata`, which app code uses to determine which tenant the event belongs to: [3](#0-2) 

The broken identity binding is:
`HMAC_valid(body, secret) == HMAC_valid(body, secret)` for **any** value of `shop` header, i.e. `shop_header ⊄ signed_bytes`. The gem treats "HMAC over body verified" as equivalent to "this event is authentically from `shop_header`," but those are not the same claim since `shop_header` is never part of the signed material.

### Impact Explanation
An app's `api_secret_key` is shared across every shop that has installed the app (multi-tenant), and Shopify's webhook signature is computed the same way for every shop using that one secret. A user who controls (or has previously observed) a legitimately-signed webhook body/HMAC pair for the app — e.g. from their own shop's real webhook delivery, since the webhook endpoint is a single public URL shared by all tenants — can POST that exact `(body, hmac)` pair to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` will pass (it only checks the body), and `Registry.process` will call the handler with `WebhookMetadata#shop` set to the victim's domain, causing the host application to process attacker-supplied data as if it originated from the victim's store — a cross-tenant data-integrity/spoofing issue.

### Likelihood Explanation
Requires the attacker to be able to reach the app's single shared webhook endpoint (typically internet-reachable) and to possess at least one valid `(body, hmac)` pair signed with the app's secret — obtainable simply by being a merchant who installed the target app themselves (no privileged access, no leaked secret, no TLS interception needed). This is a realistic, low-effort scenario for any SaaS app built on this gem.

### Recommendation
Bind the shop (and ideally topic) identity into the verified material: either include `shop`/`topic` in the signable string used by `HmacValidator`, or after HMAC validation, cross-check the `shop` header against an out-of-band trusted value (e.g., re-derive/verify the shop against a signed webhook subscription record) rather than trusting the header verbatim once body-only HMAC passes.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`; Shopify delivers a real webhook to `POST /webhooks` with body `B` and header `x-shopify-hmac-sha256: H = HMAC(secret, B)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures `(B, H)`.
3. Attacker sends `POST /webhooks` with the same body `B`, the same header `x-shopify-hmac-sha256: H`, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` passes because it only checks `H == HMAC(secret, B)`, independent of the shop header.
5. `ShopifyAPI::Webhooks::Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, so the host app processes attacker-controlled data under the victim shop's identity.
