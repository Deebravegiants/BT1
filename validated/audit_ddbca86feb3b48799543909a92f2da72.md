### Title
Unchecked ERC20 `transfer` return value in `IntentGatewayV2.placeOrder` predispatch flow lets escrow accounting be credited without tokens actually moving - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
In the Tron variant of `IntentGatewayV2.placeOrder`, when an order carries a `predispatch` call, the contract moves input tokens from the `CallDispatcher` back to the gateway using a raw, low-level encoded `IERC20.transfer` call, and relies solely on the low-level call's `success` boolean (i.e., "did not revert") rather than verifying the actual post-transfer balance or the ERC20 return value. Non-reverting-on-failure tokens (the classic `ZRX`-style tokens that return `false` instead of reverting) will make this call report success while moving zero tokens, yet the gateway still credits the order's escrow (`_orders[commitment][token]`) with the full `reducedInputs[i].amount`.

### Finding Description
In `placeOrder`, when `order.predispatch.call.length > 0`, the contract builds `transferCalls` to pull tokens from the `dispatcher` back to `address(this)` using: [1](#0-0) 

This `Call` is then executed through `ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls))`: [2](#0-1) 

`CallDispatcher.dispatch` only checks whether the raw `.call` reverted; it never inspects or requires the ABI-encoded boolean returned by `IERC20.transfer`: [3](#0-2) 

Meanwhile, the escrow bookkeeping for that same loop is computed from the *pre-transfer* `balance` on the dispatcher and the order's declared `reducedInputs[i].amount`, not from any post-transfer balance check on the gateway: [4](#0-3) 

If the input token is a non-reverting ERC20 (returns `false` on failed transfer instead of reverting — e.g., `ZRX`, or any token that can be paused/blacklisted and returns `false`), the `transfer` call to move tokens from the `dispatcher` to the gateway will silently fail (`success = true` at the low level, actual balance unchanged), yet `_orders[commitment][token] += reducedInputs[i].amount` still records the order as fully escrowed. The gateway will believe it holds tokens it does not actually hold.

This contrasts directly with the sibling function in the primary EVM implementation, `evm/src/apps/IntentGatewayV2.sol`, which snapshots gateway balances before the sweep and computes `received` from actual post-transfer balance deltas rather than trusting the call's success flag or the declared order amount: [5](#0-4) 

The Tron fork lacks this balance-diff verification for the predispatch path, reintroducing exactly the "deprecated/unsafe transfer usage" class of bug: trusting a transfer occurred based on call success rather than verified effect.

### Impact Explanation
Because `_orders[commitment][token]` is the escrow ledger used to pay out fillers/relayers upon proof of fulfillment, crediting escrow without a matching real token balance creates an unbacked liability. This can lead to insolvency of the gateway's token holdings — legitimate orders funded with normal (reverting) ERC20s can find their claims unpayable because the contract's actual balance is short by the amount phantom-credited via a failing non-standard token, or a malicious order creator can exploit a failing-transfer token to appear to fund an order at zero real cost, defrauding whichever party (filler) later relies on that escrow being genuinely available. This is a fund-loss/insolvency vector directly reachable by any unprivileged user calling `placeOrder` with a `predispatch` call and a non-compliant ERC20 as an input token.

### Likelihood Explanation
`placeOrder` is a fully permissionless, user-facing entry point; the `predispatch` call/assets path is a standard order flow, not a rare configuration. The only precondition is that one of the order's `inputs`/`predispatch.assets` tokens is an ERC20 that returns `false` rather than reverting on failed transfer (well known real-world tokens fit this profile, and the surface also covers any token temporarily returning `false` due to pausing/blacklisting/insufficient allowance edge cases at the dispatcher). No privileged role or unusual conditions are required, so likelihood is moderate-to-high whenever such tokens are permitted as intent inputs.

### Recommendation
Mirror the verification approach already used in `evm/src/apps/IntentGatewayV2.sol`: snapshot the gateway's token balance before invoking the sweep `dispatch` call and compute the actually-received amount from the balance delta after the call, using that verified amount (not the pre-transfer `balance`/declared `reducedInputs[i].amount`) to credit `_orders[commitment][token]`. Alternatively/additionally, switch the encoded call from `IERC20.transfer.selector` to `SafeERC20.safeTransfer` semantics (checking the returned boolean via `abi.decode` when return data is present) so that a `false` return causes `CallDispatcher.dispatch` to revert instead of silently succeeding.

### Proof of Concept
1. Deploy an ERC20 whose `transfer` returns `false` on failure without reverting (e.g., simulate an allowance/blacklist condition on the `dispatcher`'s balance, or an ERC20 modeled on `ZRX`).
2. Call `placeOrder` with `order.predispatch.call` and `order.predispatch.assets` set so this token is pulled into the `dispatcher`, and include the same token as an `order.inputs[i]` entry.
3. Arrange for the encoded sweep `IERC20.transfer(address(this), balance)` call from the `dispatcher` to the gateway to return `false` (e.g., token enforces a transfer restriction on the dispatcher) while not reverting.
4. Observe: `CallDispatcher.dispatch` does not revert (`success == true` since the call itself didn't revert) at [6](#0-5) 
   yet the gateway's actual token balance for that token is unchanged, while `_orders[commitment][token] += reducedInputs[i].amount` at [7](#0-6) 
   still records the order as escrowed for the full amount — an unbacked escrow entry.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
