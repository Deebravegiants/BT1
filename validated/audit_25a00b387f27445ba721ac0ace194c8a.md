### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, but the `shop` value it then hands to the app's handler is read from an unauthenticated HTTP header. The identity binding the gem implicitly promises — "the `shop` passed to the handler equals the shop the HMAC actually vouches for" — does not hold, because the signable string never includes the shop domain.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor is read from a separate, unauthenticated header (`shopify-shop-domain` / `x-shopify-shop-domain`): [2](#0-1) 

`HmacValidator.validate` only verifies `to_signable_string` (i.e., the raw body) against the HMAC using the app's shared `client_secret`: [3](#0-2) 

`Registry.process` accepts the request once that body-only HMAC check passes, then forwards the *unauthenticated* `request.shop` straight into `WebhookMetadata` given to the app's handler: [4](#0-3) 

The documented usage pattern confirms `data.shop` is meant to be trusted as the tenant identifier by the host app (e.g., used to route/store per-shop data): [5](#0-4) 

Because the `client_secret` used to sign webhooks is the same for every shop that installs the app (it is not shop-specific), any merchant who has installed the app can obtain a validly-signed `(raw_body, hmac)` pair by triggering a webhook event in their own store. That attacker can then POST directly to the app's public webhook endpoint, keeping the genuine `raw_body`/`hmac` pair but substituting an arbitrary `shopify-shop-domain` header value (e.g. a victim shop's domain). `HmacValidator.validate` still succeeds because the header is not part of the signed content, and `Registry.process` will invoke the handler with `shop` set to the attacker-chosen value.

The identity binding that breaks, as an equality:
`shop authenticated by HMAC` (nothing — the domain is unsigned) ≠ `shop delivered to the handler as request.shop`.

### Impact Explanation
If the host application uses `data.shop` from the webhook handler to look up or mutate per-tenant state (session/access-token lookup, order/customer records, billing, etc.) — which is exactly the pattern the gem's own documentation recommends — an attacker who controls one shop can inject webhook payloads that the app processes under a different, victim shop's identity. This is a cross-tenant access primitive achieved purely by exploiting how this gem authenticates and threads the shop identity through `Webhooks::Request` and `Webhooks::Registry`, not by any misuse of the gem's public API by the host app.

### Likelihood Explanation
Any user who can install the app on their own store (a normal unprivileged flow for public/embedded apps) can generate a fresh, validly-HMAC'd webhook body/signature pair at will (e.g., by updating a product/order in their own shop to fire a registered topic). Forging the HTTP request to the app's public webhook endpoint with a modified `shop-domain` header requires no secrets, no TLS interception, and no privileged access — only knowledge of the app's public webhook URL, which is normally public/predictable.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed content verified against the HMAC, or independently verify that the `shop` header value corresponds to a shop with an active, registered subscription/session known to the app before trusting it as the tenant identifier. At minimum, the gem should document prominently that `data.shop` is not itself authenticated by the HMAC and must be independently validated (e.g., cross-checked against a known/installed shop list) before being used for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and has a webhook topic (e.g. `orders/create`) registered.
2. Attacker creates an order in their store; Shopify sends a webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw body>`, and the JSON body.
3. Attacker captures this exact `raw_body` + `hmac` value (network log, browser devtools proxy on their own traffic, or replaying via their own server) and replays a new HTTP POST straight to the app's public webhook route, keeping `raw_body`/`hmac` identical but changing the header to `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this header as `shop` [2](#0-1) ; `HmacValidator.validate` still passes because only `raw_body` is checked [6](#0-5) .
5. `Registry.process` invokes the app's handler with `shop: "victim.myshopify.com"` [7](#0-6) , causing the app to process attacker-controlled webhook content as if it originated from the victim's store.

```ruby
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
```

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```
