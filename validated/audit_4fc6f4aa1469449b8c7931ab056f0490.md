### Title
Fee-on-transfer input tokens cause escrow over-accounting and cross-order fund drain in Tron `IntentGatewayV2.placeOrder` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` credits `_orders[commitment][token]` using the user-requested (fee-reduced-by-protocol-fee only) amount instead of the amount actually received by the contract via `transferFrom`/`transfer`. Unlike the canonical EVM `IntentGatewayV2.sol`, which explicitly measures `balanceOf(address(this))` before and after each transfer to account for fee-on-transfer (FOT) tokens, the Tron port never performs this check for the direct-escrow path, causing an accounting mismatch identical in class to the referenced Cooler.sol fee-on-transfer bug.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`, the non-predispatch escrow path: [1](#0-0) 
performs `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally credits `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` is derived only from the user-declared `order.inputs[i].amount` minus the protocol fee — it never reflects the token's actual behavior during transfer: [2](#0-1) 

The predispatch path has the same flaw: it computes `dust = balance - requiredAmount` from the dispatcher's pre-sweep balance, sweeps the entire `balance` via `token.transfer(address(this), balance)`, but never checks what the gateway's balance actually became after that (potentially fee-charging) transfer, then still credits `reducedInputs[i].amount`: [3](#0-2) 

By contrast, the canonical EVM `IntentGatewayV2.sol` explicitly guards against this by snapshotting balances before and after each transfer and mutating `order.inputs[i].amount` to the actual delta received, so the commitment and escrow always match what the contract actually holds: [4](#0-3) 
This defense — and dedicated tests for it — exists only in the main EVM contract: [5](#0-4) 

Because the Tron `_orders` mapping is a *shared pool per token* across all commitments (the gateway holds a single aggregate balance per ERC20, not per-order segregated custody), any FOT/deflationary input token inflates the sum of all `_orders[commitment][token]` entries beyond the contract's actual token balance.

### Impact Explanation
When `withdraw()` is later invoked — either by a solver claiming the escrow on fill (`RedeemEscrow`) or by the user on cancel/refund (`RefundEscrow`) — it transfers out the recorded `amount` from `_orders[body.commitment][token]` regardless of the contract's real balance: [6](#0-5) 
Since `_orders` values in aggregate exceed the true on-chain balance of the FOT token, this either:
1. Causes `token.call(...transfer...)` to revert/fail once the deficit is reached — permanently freezing legitimate withdrawals for later orders using that token (a route unable to deliver funds), or
2. Allows earlier claimants to be paid in full from the shared pool while later, legitimate order owners/solvers find the pool depleted, effectively draining other users' escrowed collateral of the same token — concrete theft/loss of funds for unrelated order participants.

This is directly reachable by any unprivileged user calling `placeOrder` with an FOT token as input — no privileged role is required.

### Likelihood Explanation
High. Any user can select an arbitrary ERC20 as `order.inputs[i].token`; deflationary/fee-on-transfer tokens (e.g., certain deployments of USDT-like custom tokens, RFI-style tokens) are common enough on EVM-compatible chains including Tron/TRC20 tokens that implement transfer fees. No special conditions or races are needed — a single `placeOrder` call with a FOT token immediately creates the accounting mismatch, and the pool-drain effect naturally manifests as more orders using that token are placed and settled.

### Recommendation
Mirror the fix already present in the canonical `evm/src/apps/IntentGatewayV2.sol`: measure `IERC20(token).balanceOf(address(this))` immediately before and after every `transferFrom`/sweep operation in `placeOrder`, and use the actual received delta (not the user-declared or fee-derived amount) both for the commitment hash and for the `_orders[commitment][token]` credit. Apply the identical fix to the predispatch sweep path (checking the gateway's balance delta after the final `transfer` call from the dispatcher, not just the dispatcher's pre-sweep balance).

### Proof of Concept
1. Deploy a 1%-fee ERC20/TRC20 token `FOT` and mint 10,000 to `user`.
2. `user` calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000}` and no protocol fee (`protocolFeeBps == 0`), so `reducedInputs[0].amount == 1000`.
3. `safeTransferFrom(user, gateway, 1000)` executes; due to the 1% fee, gateway's actual `FOT.balanceOf(gateway)` increases by only 990.
4. `_orders[commitment][FOT] += 1000` is recorded — 10 more than the contract's true balance of that token.
5. Repeat with a second, independent order (different commitment) also using `FOT` as input, e.g., another 1000 requested / 990 received, recording another 1000 in `_orders`.
6. Total `_orders[...][FOT]` book value across both commitments now exceeds the gateway's real `FOT` balance by 20 tokens.
7. When both orders are filled/cancelled and `withdraw()` attempts to pay out the recorded amounts sequentially, the second `token.call(transfer, amount)` either fails (permanently stranding that order's escrow, `TransferFailed()`), or — if amounts are structured so the first payout is partially reduced by rounding — the last claimant to withdraw receives less than entitled while an earlier claimant received the shortfall, demonstrating fund drain from one order's escrow to cover another's inflated accounting.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
