### Title
Unvalidated attacker-controlled scrypt KDF parameters (`n`/`r`/`p`) enable downgrade of blobKey derivation cost - (File: `libraries/secure-container/src/crypto.js`)

### Summary
`stretchPassphrase`/`boxDecrypt` in `libraries/secure-container/src/crypto.js` derive the AES key straight from the `n`, `r`, `p` scrypt cost parameters found in `metadata.scrypt` with no minimum-bound validation, and `metadata.decryptBlobKey` passes these values through unchecked. Because the container's `checksum` is a plain unkeyed `sha256` over `metadata`+`blob` (not a MAC bound to the passphrase or any secret), an attacker who can influence a secure-container file in transit/at rest (deeplink import, backup restore, cloud sync, MITM) can rewrite `metadata.scrypt.n/r/p` to trivial values and recompute a valid checksum, permanently downgrading the KDF work factor applied whenever that file is later decrypted.

### Finding Description
The reachable path is `index.js:decrypt()` → `conFile.decode` → checksum check → `conMetadata.decode` → `conMetadata.decryptBlobKey` → `conBlob.decrypt`, exactly as described in the question: [1](#0-0) 

`decryptBlobKey` forwards `metadata.scrypt` (attacker-controlled after decode) directly into `boxDecrypt`: [2](#0-1) 

`boxDecrypt`/`stretchPassphrase` perform no validation of `n`, `r`, `p` before calling the underlying `scrypt()` primitive — any values decoded from the file (including degenerate ones such as `n=1`) are used as-is, only merged with defaults for *missing* keys, not clamped for *present* ones: [3](#0-2) [4](#0-3) 

The `scrypt`/`n`/`r`/`p` fields are plain `UInt32BE` fields inside the metadata struct with no additional integrity binding beyond the unkeyed checksum described in the README: [5](#0-4) 

Because `file.decode`'s checksum is just `sha256(metadata || blobLength || blob)` (no secret/passphrase/key material involved), anyone able to tamper with the container bytes before they reach `decrypt()` (e.g. a compromised backup/sync channel, a malicious deeplink payload, or an MITM'd import file) can freely rewrite `scrypt.n/r/p` to weak values and simply recompute a matching checksum — the checksum provides only corruption detection, not tamper-evidence against a network/storage-level attacker.

The stated invariant — "locked/derivation parameters cannot be attacker-weakened to enable brute force of passphrase-protected blobKey" — is violated: nothing in `crypto.js` or `metadata.js` enforces a minimum `n`/`r`/`p`, so the cost of a subsequent offline brute-force against the true passphrase (if the ciphertext is later exfiltrated) can be reduced to near-zero by the attacker who controls the metadata bytes.

### Impact Explanation
This does not directly disclose secrets to the network attacker (AES-GCM auth-tag verification still requires the correct passphrase-derived key for decryption to succeed), but it degrades the KDF work factor that is supposed to protect the passphrase/blobKey against offline brute force once the ciphertext is obtained through any other means (lost backup, device compromise, stolen file). This maps to the "passphrase/blobKey brute-forcing feasibility, secret exposure" impact category — a downgrade-KDF vulnerability that removes the intended computational cost barrier protecting the wallet's blobKey.

### Likelihood Explanation
Requires an attacker capable of tampering with a secure-container file before it is decoded by `index.js:decrypt()` — e.g., a MITM'd backup-restore blob, a malicious deeplink/QR import payload, or compromised sync storage. Because the file's checksum is an unkeyed `sha256` (not bound to the passphrase), such tampering is trivially detectable-free (i.e., undetected) by the decode/checksum logic, making the downgrade reproducible and low-effort once the attacker has any channel to modify container bytes in flight or at rest.

### Recommendation
- Enforce minimum/maximum bounds for `n`, `r`, `p` (and validate `n` is a power of two, `p*r < 2^30`, etc.) inside `stretchPassphrase`/`boxDecrypt` in `libraries/secure-container/src/crypto.js`, rejecting metadata with out-of-policy scrypt parameters instead of silently deriving with them.
- Consider binding the metadata's scrypt parameters into an authenticated structure (e.g., include them in the AAD of `blobKey`'s AES-GCM tag) so any parameter tampering causes decryption to fail rather than silently using attacker-chosen weak parameters.

A companion integration test can craft a full secure-container file (using `metadata.create({ n: 1, r: 1, p: 1, salt })`, `metadata.encryptBlobKey`, `blob.encrypt`, `file.encode` with a freshly recomputed checksum) and confirm `index.js:decrypt()` accepts and processes it without rejecting the weak KDF parameters.

export async function decrypt(encryptedData, passphrase) {
  const fileObj = conFile.decode(encryptedData)

  const checksum = await conFile.computeChecksum(fileObj.metadata, fileObj.blob)
  if (!fileObj.checksum.equals(checksum))
    throw new Error('seco checksum does not match; data may be corrupted')

  const metadata = conMetadata.decode(fileObj.metadata)
  const blobKey = await conMetadata.decryptBlobKey(metadata, passphrase)
  const header = conHeader.decode(fileObj.header)
  const data = await conBlob.decrypt(fileObj.blob, metadata, blobKey)

  return { data, blobKey, metadata, header }
}
