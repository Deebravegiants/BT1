## Title
Webhook tenant identity (`shop`, `topic`) not covered by HMAC verification, enabling cross-tenant webhook spoofing — (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the shop, topic, and webhook-id attribution that `Registry.process` trusts to dispatch and identify the tenant come from unauthenticated HTTP headers that are never part of the signed message.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by comparing the HMAC over `verifiable_query.to_signable_string` against the value returned by `verifiable_query.hmac`: [1](#0-0) 

For webhooks, `Request` implements `to_signable_string` to be exactly `@raw_body`, and nothing else: [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read directly from attacker-reachable HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) and are **not** part of the signed payload: [3](#0-2) 

`Registry.process` validates only the HMAC over the body, then unconditionally trusts `request.shop` and `request.topic` from the headers to build `WebhookMetadata` and to select/dispatch the handler: [4](#0-3) 

The identity binding that should hold is: `shop attributed to the event == shop that actually produced the signed body`. Because the HMAC only covers `@raw_body`, this equality is never checked — `request.shop` is fully independent of the cryptographic proof. Critically, the signing secret (`Context.api_secret_key`, the app's `client_secret`) is the **same for every shop that installs the app** — it is not shop-specific. So:

- **Before the attack**: Attacker installs the app on their own (legitimately owned) shop `attacker.myshopify.com`. Shopify sends the attacker a real webhook: body `B`, headers `shop-domain: attacker.myshopify.com`, `hmac-sha256: HMAC(secret, B)`.
- **Attacker's request sequence**: Attacker replays the exact same `raw_body` (`B`) and `hmac-sha256` value to the app's public webhook endpoint, but substitutes the `shopify-shop-domain` (and optionally `shopify-topic`) header with `victim.myshopify.com` (or any other shop using the same app).
- **After the attack**: `HmacValidator.validate` recomputes `HMAC(secret, B)` — identical to the received value — so validation succeeds. `Registry.process` then calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, i.e., the app processes an event as if it legitimately originated from the victim shop, despite the cryptographic proof only certifying "this body was signed by the app's secret," not "this event is about this shop."

This breaks the intended binding `verified_bytes == attributed_tenant`, matching the "field acted on but not covered by the HMAC" class called out in scope.

### Impact Explanation
This allows an attacker who controls just one shop where the app is installed (a normal, unprivileged action) to forge webhook events attributed to any other shop of the same app — a cross-tenant identity confusion. Depending on how the host app uses `WebhookMetadata.shop` (commonly used as the key to look up/update per-tenant sessions or state, per the docs' guidance to key data by `shop`), an attacker can inject spoofed events for topics whose body shape is shop-agnostic (e.g., generic status/lifecycle topics), causing state to be created, corrupted, or deleted under another tenant's identity. This is a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires only that the attacker legitimately install the target app on any shop (self-service, unprivileged) to obtain one valid `(body, hmac)` pair, and then send a forged HTTP request to the app's public webhook endpoint with a different `shop-domain`/`topic` header — no secret, token, or privileged access is required. The webhook endpoint is public by design (that's the point of webhooks), so likelihood is high for apps that trust `WebhookMetadata.shop` for tenant-keyed actions.

### Recommendation
Bind the header-derived identity fields (`shop`, `topic`, `webhook_id`, `api_version`) into the signed message, or otherwise validate that the header-provided shop matches an expected/registered value before trusting it, e.g. include the shop domain and topic in `to_signable_string` (matching what is verifiable) or independently cross-check `request.shop` against the shop associated with the resolved session/registration before dispatching, rather than trusting `request.shop`/`request.topic` derived purely from unauthenticated headers once the body-only HMAC passes.

### Proof of Concept
```ruby
# 1. Attacker installs target app on their own shop and receives a legitimate webhook:
raw_body = '{"id":123}'
secret   = ShopifyAPI::Context.api_secret_key # same secret for every shop of this app
hmac = Base64.encode64(OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, raw_body))

# Real headers received by attacker for their OWN shop:
# "shopify-shop-domain" => "attacker.myshopify.com"
# "shopify-hmac-sha256" => hmac
# "shopify-topic"       => "app/uninstalled"

# 2. Attacker replays identical body+hmac but swaps the shop header to the victim:
forged_headers = {
  "shopify-topic" => "app/uninstalled",
  "shopify-hmac-sha256" => hmac,                    # unchanged, still valid for raw_body
  "shopify-shop-domain" => "victim.myshopify.com",  # forged tenant
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate passes (it only checks raw_body against hmac),
#    handler.handle is invoked with WebhookMetadata(shop: "victim.myshopify.com", topic: "app/uninstalled", ...)
```

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
