### Title
Webhook `shop-domain` and `topic` identifiers are not covered by the HMAC signature, allowing cross-tenant impersonation via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, then trusts the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` headers verbatim to build the tenant identity and dispatch routing passed to the app's handler. Because these headers are not part of the signed bytes, an attacker who can obtain any one valid `(raw_body, hmac)` pair signed with the app's `api_secret_key` can substitute an arbitrary `shop-domain` header while keeping the original body and HMAC, and the signature check still passes.

### Finding Description
`Utils::VerifiableQuery` requires only `hmac` and `to_signable_string` [1](#0-0) . For webhooks, `Webhooks::Request#to_signable_string` returns just `@raw_body`, while `shop`, `topic`, `api_version`, and `webhook_id` are read straight from HTTP headers, entirely outside of what is signed: [2](#0-1) .

`HmacValidator.validate` computes the HMAC over `to_signable_string` (the body only) and compares it to the `hmac-sha256` header [3](#0-2) .

`Registry.process` performs exactly this check and, once it passes, unconditionally trusts `request.shop` and `request.topic` to look up the handler and build the `WebhookMetadata` delivered to the app: [4](#0-3) . The resulting `WebhookMetadata#shop` field is a plain, unauthenticated string field consumed as the tenant identity by the app's `WebhookHandler#handle` [5](#0-4) .

This reproduces the report's bug class exactly: two correlated values are transmitted together (body vs. shop/topic headers, analogous to `data` vs. `sessionMerkleRoot`), but only one of them (the body) is cryptographically bound by the signature. The equality that should hold — `shop header used for identity == shop that the HMAC-signed payload actually originated from` — is never checked; only `hmac == HMAC(raw_body, api_secret_key)` is verified, independent of the headers.

Because `api_secret_key` is the app's single client secret shared across every merchant installation (not a per-shop secret), any user who installs the app on their own store is an "unprivileged internet user" with respect to other tenants, yet can generate a body/HMAC pair that is valid under the app's global secret. They can then replay that exact `(raw_body, hmac-sha256)` pair to the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) headers to name a victim shop, and `Registry.process` will accept it as an authentic webhook for the victim shop.

### Impact Explanation
This crosses the tenant boundary explicitly called out in scope: cross-tenant access. A merchant/attacker who legitimately installs the app can forge webhook deliveries that the app processes as if they originated from an arbitrary victim shop domain, corrupting per-shop state, triggering shop-scoped side effects, or spoofing sensitive mandatory GDPR topics (`shop/redact`, `customers/redact`, `customers/data_request`) against a victim's data, since the mandatory topics constant in `Registry` shows these are the very topics the library expects apps to handle [6](#0-5) . Any app that uses `WebhookMetadata#shop` to select which merchant record to update/delete (the documented and only intended use of that field) is directly exposed.

### Likelihood Explanation
Exploitation requires no privileged access to Shopify or the app's secrets — only the ability to install the app on an attacker-controlled shop (or otherwise obtain one legitimate webhook delivery, which Shopify itself will readily provide for any topic the attacker triggers on their own store) and the ability to POST to the app's public webhook endpoint with modified headers. No TLS interception, leaked credentials, or social engineering is needed, satisfying the "unprivileged internet user" constraint.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed material, or otherwise cryptographically bind them to the verified payload (e.g., verify the HMAC over `headers + body`, or reject/re-derive the shop identity from a separately verified, per-installation source rather than the raw header) before constructing `WebhookMetadata` in `Registry.process`.

### Proof of Concept
1. Install the app on attacker's own shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) and capture the raw POST: body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC_SHA256(api_secret_key, B)`, and `api_secret_key` is the same for all installs of this app).
2. Replay the exact same request to the app's webhook endpoint, keeping body `B` and `X-Shopify-Hmac-Sha256: H` unchanged, but set `X-Shopify-Shop-Domain: victim.myshopify.com` (and, if desired, `X-Shopify-Topic: shop/redact`).
3. `Utils::HmacValidator.validate(request)` recomputes the HMAC over `B` only, matches `H`, and returns `true` [7](#0-6) .
4. `Registry.process` proceeds, builds `WebhookMetadata.new(topic: "shop/redact", shop: "victim.myshopify.com", ...)`, and invokes the app's handler as if the event genuinely originated from `victim.myshopify.com` [8](#0-7) .
