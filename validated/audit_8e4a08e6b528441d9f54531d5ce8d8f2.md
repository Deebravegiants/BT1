Unconditional FIFO eviction of `BoundedStateCommitments` can permanently strand requests/timeouts awaiting proof at an evicted height - ([File: modules/pallets/ismp/src/lib.rs])

### Summary
`pallet-ismp` keeps a **capped, per-chain FIFO queue** (`StateCommitmentQueue` / `CommitmentQueueStates`) of verified state-machine heights. Every time a new consensus update stores a fresh height (`store_state_machine_commitment`), the queue evicts the **oldest** entry once the per-chain cap (`StateMachineCommitmentCap`, default `MAX_STATE_MACHINE_COMMITMENTS`) is reached, deleting the corresponding `BoundedStateCommitments`/`BoundedStateMachineUpdateTime` rows. This is structurally the same defect class as the reported bug: a piece of state that gates a user-facing action (here, the ability to submit a valid inclusion/non-membership proof against a still-relevant height) is only ever cleaned up/advanced as a **side effect of one specific unrelated trigger** (a fresh consensus update landing for that same chain), with **no external, demand-aware function** to protect or extend a height that a pending request/timeout still needs proof against.

### Finding Description
`modules/pallets/ismp/src/lib.rs` documents the queue: [1](#0-0) 

Insertion (a consensus update landing) is the *only* place the queue is mutated forward — there is no separate, callable path that lets relayers or applications ensure a height with a pending request/timeout is retained before it ages out. The test suite confirms the eviction is unconditional on insertion and purely FIFO-by-insertion-index, regardless of whether the evicted height is still needed for a live proof: [2](#0-1) 

This mirrors the original bug's root cause exactly: `_updateWithdrawalQueue()` in the PolicyBook contract was only reachable from `_addLiquidityFor`, so the queue could only ever be drained by a liquidity deposit — never on demand when policies expired and collateral became free. Here, `BoundedStateCommitments` for a given `(chain, height)` can only be *retained* by consensus updates continuing to arrive slowly enough, and can only be *pruned* as a byproduct of the next consensus update for that chain landing — there is no external/administrative function to widen the cap on demand or to protect a height a pending message still needs, analogous to the missing "process the queue without adding new liquidity" entry point flagged in the report.

### Impact Explanation
Every inbound POST/GET request or timeout message is checked against `host.state_machine_commitment(height)` (EVM equivalent) or the pallet's `BoundedStateCommitments` storage before being routed to a destination module: [3](#0-2) 

If a relayer is slow to submit the requisite proof — because it is waiting out the challenge period, batching, or simply delayed — and enough fresh consensus updates land for that same source chain in the meantime, the height the pending message/timeout was anchored to is silently evicted from the bounded map. Any later attempt to deliver that message then fails with a state-commitment-not-found condition, permanently preventing that specific request/timeout from ever being delivered (its proof can never be re-verified against a height that no longer exists in storage), i.e. a "route unable to deliver messages" outcome, with associated relayer fee loss and, for time-locked funds routed through the request (e.g. bridged token mints, intent escrow releases, relayer-fee withdrawals), a permanent freeze of those funds pending only on a timeout that itself may be unprovable for the same reason.

### Likelihood Explanation
No admin/malicious-node assumption is required: a single stream of legitimate consensus updates for a fast-finality counterparty chain (which anyone can submit permissionlessly, since consensus message submission is unsigned/`ensure_none`) can advance the FIFO tail past a cap-width window while a normal request/timeout proof is still in flight for an older height. The smaller the per-chain `StateMachineCommitmentCap`, and the faster/greater the volume of finality updates for that chain, the narrower the window in which a legitimate proof must land before its anchor height is evicted — a condition that is easy to trigger unintentionally in production and trivially reproducible/acceleratable by any relayer racing to push consensus updates ahead of a competitor's pending request delivery.

### Recommendation
Add an external, demand-aware safeguard analogous to the recommended fix in the report (an explicit function to progress state independent of the triggering event): before evicting the oldest `StateCommitmentQueue` entry, check whether any known-pending request/timeout commitment still references that height (or expose a governance/relayer-callable extension of the per-chain cap), and skip/defer eviction in that case, or require destinations to be proven within a window enforced independently of the insertion-triggered eviction rather than coupling proof validity purely to how many *unrelated* consensus updates have since landed.

	/// Per-chain FIFO queue of heights retained in [`BoundedStateCommitments`]
	/// and [`BoundedStateMachineUpdateTime`], keyed by a monotonically
	/// increasing insertion index. Insertion order matches height order because
	/// consensus updates only ever advance a state machine, so evicting at the
	/// head removes the oldest height. Entries whose height was vetoed via
	/// `delete_state_commitment` are left in place and become harmless no-ops
	/// when their index is evicted.
	///
	/// Each insertion touches O(1) small storage items, so the per-chain cap
	/// can grow without adding I/O or PoV weight to the insert path.
	#[pallet::storage]
	pub type StateCommitmentQueue<T: Config> = StorageDoubleMap<
		_,
		Blake2_128Concat,
		StateMachineId,
		Twox64Concat,
		u64,
		u64,
		OptionQuery,

// A height below the latest can never be resubmitted — the consensus handler skips
// anything at or below `previous_latest_height` — so its stale queue entry has no
// live twin and evicting it touches nothing.
#[test]
fn vetoed_height_that_cannot_be_resubmitted_evicts_as_a_noop() {
	let mut ext = new_test_ext();
	ext.execute_with(|| {
		let host = Ismp::default();
		let id = queue_test_state_machine();
		let store = |height: u64| {
			host.store_state_machine_commitment(
				StateMachineHeight { id, height },
				queue_test_commitment(),
			)
			.unwrap();
			host.store_latest_commitment_height(StateMachineHeight { id, height }).unwrap();
		};

		pallet_ismp::Pallet::<Test>::update_commitment_caps(
			RuntimeOrigin::root(),
			BTreeMap::from([(id, 2)]),
		)
		.unwrap();

		store(10);
		store(11);

		// Veto a height below the latest: the commitment goes away immediately while
		// its queue entry stays behind as a stale index. The latest height is
		// untouched, so 10 stays permanently unsubmittable.
		host.delete_state_commitment(StateMachineHeight { id, height: 10 }).unwrap();
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 10 }).is_err());
		assert_eq!(host.latest_commitment_height(id).unwrap(), 11);
		assert_eq!(
			CommitmentQueueStates::<Test>::get(id),
			CommitmentQueueState { head: 0, tail: 2 }
		);
		assert_eq!(StateCommitmentQueue::<Test>::get(id, 0), Some(10));

		// The stale index is evicted as a no-op on the next insertion.
		store(12);
		assert_eq!(
			CommitmentQueueStates::<Test>::get(id),
			CommitmentQueueState { head: 1, tail: 3 }
		);
		assert!(StateCommitmentQueue::<Test>::get(id, 0).is_none());
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 11 }).is_ok());
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 12 }).is_ok());
	})
}
