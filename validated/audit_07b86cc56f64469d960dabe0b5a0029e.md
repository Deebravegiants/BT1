### Title
Webhook shop-domain identity spoofing via HMAC that only covers the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, while the `shop` (tenant identity) is read from a separate, unsigned header. `Registry.process` validates only that HMAC and then hands the unauthenticated `shop` value straight to the app's handler as if it were verified. This breaks the intended identity binding `hmac == HMAC(secret, body ⊕ shop)`, actually enforced as `hmac == HMAC(secret, body)` with `shop` taken on faith.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed content at all: [2](#0-1) 

`HmacValidator.validate` verifies the signature against `verifiable_query.to_signable_string` (the body) only: [3](#0-2) 

`Registry.process` raises `InvalidWebhookError` only if the HMAC check fails, and otherwise forwards `request.shop` unchanged into `WebhookMetadata`, which is passed to the app's handler as authenticated tenant context: [4](#0-3) 

Because the `api_secret_key` is shared across every shop that has the app installed, any unprivileged internet user who can install the app on their own (attacker-controlled) shop receives genuine webhook deliveries with a valid HMAC computed over a body they control. Nothing in this library ties that HMAC to the `shop` header, so the attacker can replay the same body/HMAC pair while substituting an arbitrary `shopify-shop-domain` value (e.g., a victim merchant's domain). `Registry.process` will accept it as valid and dispatch it to the handler with the forged `shop`, since the equality the library actually enforces is:

`hmac_received == HMAC(api_secret_key, raw_body)`

instead of the intended:

`hmac_received == HMAC(api_secret_key, raw_body) AND shop_header == shop_that_the_HMAC_was_issued_for`

### Impact Explanation
Any app that uses `WebhookMetadata#shop` (i.e., `data.shop`, the value the library itself hands the developer as the verified webhook source) to key session lookups, run tenant-scoped business logic, or gate access will process an attacker-forged event under an arbitrary victim shop identity — a cross-tenant boundary violation. Because the same shared `api_secret_key` signs webhooks for every installed shop, the attacker only needs the app installed on a shop they control (an unprivileged, non-credentialed action) to obtain a valid signature usable against a spoofed identity header. This meets the Critical bar of cross-tenant access enabled purely by this gem's webhook verification API.

### Likelihood Explanation
Likelihood is high for any consumer of this library that follows the documented pattern of trusting `ShopifyAPI::Webhooks::Registry.process` / `WebhookMetadata#shop` as an authenticated tenant identifier, since the library's own `process` method performs no binding between the verified body and the shop header — it is the sole "identity" surface the gem exposes for webhooks, and its interface gives no indication that `shop` is unauthenticated relative to the signature.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed material verified by `HmacValidator`, or explicitly cross-check the header-derived `shop` against a value independently known to belong to the shop whose secret produced the HMAC (e.g., validate the shop domain against the session/shop registered at install time) before constructing `WebhookMetadata`. At minimum, document clearly that `Request#shop` is unauthenticated and must not be used for tenant-identity decisions without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` (a shop they control) and receives a legitimate webhook with body `B` and header `x-shopify-shop-domain: attacker.myshopify.com`, HMAC `H = HMAC(secret, B)`.
2. Attacker resends the identical body `B` and HMAC `H` to the app's webhook endpoint, replacing the header with `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` computes `HmacValidator.validate` on `request.to_signable_string` (`B` only) — it matches, since `H` was legitimately computed over `B`. [5](#0-4) 
4. The handler receives `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, and any app logic keyed by `data.shop` now runs as though the event genuinely originated from `victim.myshopify.com`.
