### Title
Webhook shop/topic/id identity fields are unauthenticated header data, not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely via `Utils::HmacValidator.validate(request)`, but the HMAC is only computed over the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values that the gem then hands to the host application's handler are read straight from unauthenticated HTTP headers.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate_signature` computes the HMAC exclusively over that signable string (`verifiable_query.to_signable_string`) and compares it to the `hmac` value: [2](#0-1) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all sourced from HTTP headers that are never included in the signable string: [3](#0-2) 

`Registry.process` validates only the HMAC (i.e., only the body) and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to construct the `WebhookMetadata` that is dispatched to the app's registered handler: [4](#0-3) 

This breaks the intended identity binding: `shop authenticated-by-HMAC == shop attributed to the request`. In reality, the equality that holds is only `body authenticated-by-HMAC == body`; the `shop` (and `topic`/`webhook_id`) values are attacker-influenceable header fields that ride along unauthenticated. Since the app's HMAC secret (`Context.api_secret_key`) is shared across all shops that install the app — it is not shop-specific — any party capable of producing one validly-HMAC-signed body for the app (e.g., a merchant who has installed the app on their own store and can capture/replay/relay the webhook delivery, or any party able to intercept/forge the request to the app's webhook endpoint before it reaches the gem) can pair that valid body+HMAC with an arbitrary `shop-domain`, `topic`, or `webhook-id` header. The gem will report this to the handler as authenticated data belonging to whatever shop the header claims, without any secondary check that the header's shop matches a shop actually entitled to send that body.

### Impact Explanation
This matches the "High" tier: a field acted upon (the shop identity used to scope the webhook’s effect within a multi-tenant app) is not covered by the same cryptographic proof (HMAC) that validates the payload. Host applications that trust `WebhookMetadata#shop` to select which tenant's data to mutate (the gem's own documented usage pattern — the gem is the one constructing and delivering this struct as the "verified" webhook context) can be made to process data under the wrong tenant's identity, i.e., cross-tenant data confusion, if any request path exists between the sender and the app's endpoint where headers can be altered independently of the body (e.g., a reverse proxy, load balancer, or a malicious middle-tier the merchant themselves controls when relaying their own shop's genuine webhook). The vulnerability is squarely inside the gem's own `HmacValidator`/`Webhooks::Request` design, not a misuse of a documented API by the host: the gem presents `WebhookMetadata.shop` as reliable, verified data once `HmacValidator.validate` succeeds, but only the body is actually authenticated.

### Likelihood Explanation
Exploitation likelihood is constrained: an attacker must be able to independently manipulate transport-layer headers apart from the signed body en route to the app's webhook endpoint (e.g., control over a proxy in the delivery path, or possession of a captured valid body+HMAC pair from one shop that can be replayed with modified headers to the same endpoint). It does not require the `api_secret_key` itself, an access token, or any Shopify-side privilege beyond the ability to install the app on an attacker-controlled shop and manipulate the resulting request headers before they reach the app.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable string used for HMAC computation, or otherwise cryptographically bind them to the validated payload, so that `HmacValidator.validate` provides an integrity guarantee over the full set of fields that `WebhookMetadata` exposes to handlers — not just the raw body.

### Proof of Concept
1. App is installed on Shop A (attacker-controlled). Shopify delivers a genuine webhook to the app's endpoint with body `B`, `x-shopify-hmac-sha256: HMAC(secret, B)`, and `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker intercepts/relays this request before it reaches the gem's `Registry.process` (e.g., via a proxy they control in front of the app, or by replaying a captured request through a channel where they can rewrite headers independently of body), changing `x-shopify-shop-domain` to `shop-b.myshopify.com` (a victim tenant) while leaving `B` and the HMAC header untouched.
3. `Utils::HmacValidator.validate` succeeds because it only checks `HMAC(secret, B)` against the untouched header value [2](#0-1) .
4. `Registry.process` builds `WebhookMetadata.new(shop: request.shop, ...)` with `shop == "shop-b.myshopify.com"` and dispatches it to the handler as though it were an authenticated event for Shop B [5](#0-4) .
