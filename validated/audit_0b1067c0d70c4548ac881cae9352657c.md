### Title
`request.shop` is not covered by the webhook HMAC, letting a forged `shop-domain` header retarget mandatory GDPR topics to an arbitrary victim shop - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC that `Registry.process` validates authenticates the JSON body but never the `shopify-shop-domain` header. Any actor who has obtained one genuine `(body, hmac)` pair for their own shop (including for a mandatory topic like `customers/redact`) can replay it against the app's public webhook endpoint with the `shop-domain` header swapped to an arbitrary victim shop, and `handler.handle` will be invoked with `WebhookMetadata.shop` equal to the forged value.

### Finding Description
The binding that should hold is: `WebhookMetadata.shop` (the shop whose data the handler acts on) == the shop that the HMAC-authenticated request body actually originated from. This binding is false.

- `Request#to_signable_string` returns just the raw body: `lib/shopify_api/webhooks/request.rb:35-38`.
- `HmacValidator.validate_signature` computes the signature purely from `verifiable_query.to_signable_string` (the body) and compares it to the `hmac-sha256` header: `lib/shopify_api/utils/hmac_validator.rb:26-31`.
- `Request#shop` simply reads the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the body or the HMAC: `lib/shopify_api/webhooks/request.rb:20-23`, `67-70`.
- `Registry.process` only checks `Utils::HmacValidator.validate(request)` and then builds `WebhookMetadata` directly from `request.shop`: `lib/shopify_api/webhooks/registry.rb:189-199`.

Attack flow: the attacker creates their own development shop, installs the app, and lets it register the `customers/redact` (or `shop/redact`/`customers/data_request`) webhook. Shopify sends the attacker a legitimately signed callback with body `B` and header `shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)`. The attacker then crafts their own POST directly to the app's public webhook endpoint using the same `B` and `H`, but sets `shopify-shop-domain: victim-shop.myshopify.com` and `shopify-topic: customers/redact`. `HmacValidator.validate` recomputes `HMAC-SHA256(secret, B)`, which still equals `H` because the header is not part of the signed content, so validation succeeds. `Registry.process` then calls `handler.handle` with `WebhookMetadata.new(topic: "customers/redact", shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`. If the host app's mandatory-topic handler deletes/redacts data keyed by `WebhookMetadata#shop` (as the mandatory-webhook contract intends), it will destroy data belonging to a shop that never requested it.

The `register()`/`mandatory_registration_result` short-circuit at `lib/shopify_api/webhooks/registry.rb:58-59` is unrelated to this path — it only affects outbound registration calls made by the host app via the Admin API and is never reached by attacker-supplied HTTP requests. `process()` is the only code path that consumes attacker-supplied webhook data, and it is here that the shop identity is unauthenticated.

### Impact Explanation
Any handler registered for `customers/redact`, `shop/redact`, or `customers/data_request` (or any other topic) receives a `shop` value that is fully attacker-controlled while still passing HMAC validation, because the signature only covers the JSON body, not the headers. This is a cross-tenant integrity issue: an attacker who legitimately received one webhook for their own shop can trigger the same handler logic against any shop-domain string of their choosing, repeatably, for every future webhook they receive. If the host app follows Shopify's documented mandatory-webhook contract (delete/redact data for `WebhookMetadata#shop`), this leads to destructive cross-tenant actions.

### Likelihood Explanation
The precondition is trivial: the attacker only needs to be an app installer on their own shop (no elevated privilege), and must be able to obtain one valid `(body, hmac)` pair, which they get for free the moment their own shop receives any webhook (including the mandatory ones, once uninstalled/redacted, or by triggering a `customers/redact` GDPR request against their own shop). No secret key, MITM, or victim cooperation is required. Cost to the attacker is a single legitimate webhook receipt plus one forged HTTP POST to the app's public endpoint.

### Recommendation
Bind the shop identity to the signed content, e.g. include the relevant Shopify headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC computation, or cross-check `request.shop` against a shop known to be associated with the specific `webhook_id`/subscription server-side before invoking `handler.handle`. At minimum, document and enforce that host apps must independently verify `request.shop` is a shop actually installed on their app before performing any destructive action, and consider validating the request source is Shopify's known webhook infrastructure.

### Proof of Concept
```ruby
# test/webhooks/registry_test.rb (new test)
def test_process_accepts_forged_shop_domain_with_valid_body_hmac
  topic = "customers/redact"
  body = "{}"
  hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)

  redacted_shop = nil
  handler = Class.new do
    define_method(:handle) { |data:| redacted_shop = data.shop }
  end.new

  ShopifyAPI::Webhooks::Registry.add_registration(
    topic: topic, path: "path", delivery_method: :http, handler: handler,
  )

  forged_headers = {
    "shopify-topic" => topic,
    "shopify-hmac-sha256" => Base64.encode64(hmac), # same body/hmac pair attacker legitimately received for their OWN shop
    "shopify-shop-domain" => "victim-shop.myshopify.com", # forged, never authenticated by Shopify for this body
    "shopify-webhook-id" => "attacker-controlled-id",
    "shopify-api-version" => "2024-01",
  }

  request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)
  ShopifyAPI::Webhooks::Registry.process(request) # does not raise InvalidWebhookError

  assert_equal("victim-shop.myshopify.com", redacted_shop) # handler ran with forged, unauthenticated shop identity
end
```
