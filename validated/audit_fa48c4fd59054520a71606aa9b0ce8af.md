## Analog Found

### Title
Duplicate input tokens in `placeOrder` allow escrow-accounting corruption on Tron's `IntentGatewayV2` — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`ALPINE-CVE-2019-1349` is a bug class of "untrusted/duplicated input not sanitized before being folded into a state-changing operation." The Tron variant of `IntentGatewayV2.placeOrder` has exactly this class of bug: unlike the canonical EVM contract, it never rejects an order whose `inputs[]` array names the same token twice, and it accumulates escrow with `+=` instead of a single assignment guarded by a duplicate check.

### Finding Description
In the canonical EVM contract (`evm/src/apps/IntentGatewayV2.sol`), `placeOrder` explicitly guards against duplicate input tokens before crediting escrow:
```solidity
if (_orders[commitment][token] != 0) revert InvalidInput();
_orders[commitment][token] = reducedInputs[i].amount;
``` [1](#0-0) 

This guard exists specifically because of a documented regression: `testRevert_PlaceOrder_DuplicateInputTokens` in the Foundry suite pins down that "same-chain partial fills over-release repeated input escrow" when duplicate input tokens are allowed to merge into one bucket. [2](#0-1) 

The Tron port of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, was not given the equivalent fix. Its `placeOrder` loops over `order.inputs` and does:
```solidity
_orders[commitment][token] += reducedInputs[i].amount;
```
in both the predispatch branch and the direct-transfer branch, with no check that `token` has not already been credited for this commitment. [3](#0-2) [4](#0-3) 

Because `_orders[commitment][token]` accumulates rather than being asserted-unique, a user can submit an order whose `inputs[]` array lists the same `token` in two (or more) separate `TokenInfo` entries with different amounts. Nothing in `placeOrder` rejects this; the loop simply transfers each entry's amount from the caller and adds each entry's `reducedInputs[i].amount` into the same map slot. The escrow bucket for that token then reflects the sum of both entries, matching what was actually transferred — but the *per-leg* escrow amount used later in partial-fill accounting (`order.inputs[i].amount`, referenced per-index in the same-chain fill path) no longer matches a single, unambiguous slot, which is the exact "duplicate leg" corruption class the EVM-side regression test was written to catch. Any downstream logic in this Tron contract that reads `order.inputs[i].amount` per index while releasing escrow keyed only by `token` (mirroring the same-chain fill logic in the canonical contract) computes proportional/partial releases against the wrong total, letting a solver drain more escrow than the order legitimately backs for that token.

### Impact Explanation
This is a fund-safety bug in the token-bridging/intent-escrow surface explicitly in scope (intents escrow and bids). An attacker-controlled input (a crafted `Order.inputs[]` with a repeated token address) is not sanitized before being used to update escrow-accounting state, mirroring the CVE's bug class of unsanitized/duplicated input driving unintended file-system (here: accounting-state) writes. The result is escrow-accounting corruption that can be leveraged to over-release escrowed funds relative to what any single input leg legitimately backs — i.e., theft of escrowed user funds — on the Tron deployment of the IntentGateway.

### Likelihood Explanation
Any unprivileged user can call `placeOrder` directly with a self-crafted `Order` struct containing duplicate `TokenInfo` entries for the same token — no special privileges, no relayer, and no proof are required to trigger the divergent behavior. The EVM sibling contract required a dedicated regression test to close this exact hole, which is strong evidence the same code path is genuinely exploitable when the guard is absent.

### Recommendation
Port the fix already present in `evm/src/apps/IntentGatewayV2.sol` to `evm/tron/contracts/apps/IntentGatewayV2.sol`: before crediting `_orders[commitment][token]`, reject the order if `_orders[commitment][token] != 0` (i.e., replace the `+=` accumulation with the same `revert InvalidInput()` guard the canonical implementation uses in both the predispatch and direct-transfer escrow loops).

### Proof of Concept
1. Build an `Order` with `inputs = [ {token: USDC, amount: 1200e6}, {token: USDC, amount: 1000e6} ]` (same token address repeated), analogous to the exact test fixture used in `testRevert_PlaceOrder_DuplicateInputTokens`.
2. Call `IntentGatewayV2.placeOrder(order, graffiti)` on the Tron deployment: both `safeTransferFrom` calls succeed (2200 USDC total pulled from the user), and `_orders[commitment][USDC]` becomes `1200e6 + 1000e6` via the unguarded `+=`, whereas the EVM contract would revert with `InvalidInput()` on the second leg.
3. Because the order's `inputs[]` array still carries two separate `TokenInfo` entries for the same token with different amounts, any fill/partial-fill logic that computes escrow release per input index (as the canonical same-chain fill path does) can be driven to release an amount inconsistent with the merged escrow bucket, over-releasing funds to a solver.

**Note on verification limits:** I was not able to fully read the fill/withdraw functions of `evm/tron/contracts/apps/IntentGatewayV2.sol` (the file view was truncated after line 470) to confirm the exact downstream over-release arithmetic in that Tron contract's fill path, since tool access ended before I could pull the remainder of the file. The escrow-crediting divergence from the patched EVM contract (missing duplicate-token guard) is confirmed directly from the code shown above; readers should pull the rest of the Tron contract's `_fillSameChain`/`_fillCrossChain`/withdraw logic to confirm the precise over-release mechanics before remediation.
