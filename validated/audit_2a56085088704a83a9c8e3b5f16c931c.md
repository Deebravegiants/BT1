### Title
Webhook `shop`, `topic`, and `webhook_id` Are Not Covered by the HMAC, Allowing Cross-Tenant Replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Webhooks::Registry.process` validates the HMAC solely against that body before trusting `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` passed to the host app's handler.

### Finding Description
The equality the HMAC is supposed to enforce is:
`verified(bytes) == bytes_the_handler_acts_on`

Here that equality is broken. `to_signable_string` binds the signature to `@raw_body` only: [1](#0-0) 

But `shop`, `topic`, and `webhook_id` — which are read straight from unauthenticated HTTP headers — are never part of the signed material: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately forwards these unverified header-derived fields to the app's handler as trusted tenant/routing identifiers: [3](#0-2) 

`HmacValidator.validate` confirms the check only covers `verifiable_query.to_signable_string` (i.e., the body), never the headers: [4](#0-3) 

Because Shopify computes the HMAC over the JSON body and the secret only, any two webhook deliveries that happen to carry byte-identical bodies (this is common for low-cardinality/minimal-payload topics such as `app/uninstalled`, `shop/redact`, or other privacy/compliance webhooks with sparse bodies) will have **the same valid `hmac`**, regardless of which shop or topic header accompanies them. An unprivileged user who operates their own Shopify store with the app installed can legitimately receive such a webhook (with a valid signature over that particular body), then replay the identical `(raw_body, x-shopify-hmac-sha256)` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` and/or `x-shopify-topic` headers to name a victim shop or a different topic. `HmacValidator.validate` still succeeds because it only checks `raw_body` against the secret, and `Registry.process` and `WebhookMetadata` then hand the forged `shop`/`topic` straight to the host app's `handle` method as if Shopify had produced them.

### Impact Explanation
This crosses a tenant boundary: the shop identifier used by the host application to attribute a webhook event (e.g. to deactivate a subscription, delete a merchant's data, or trigger de-provisioning logic on `shop/redact` / `app/uninstalled`) is not bound to the value Shopify actually signed. An attacker with any Shopify store can trigger app-side state changes or data operations attributed to a shop they do not own, which is a cross-tenant integrity violation stemming directly from this gem's webhook verification primitive.

### Likelihood Explanation
Exploitability depends on finding (or crafting) topics whose bodies are constant or attacker-predictable across shops — realistic for several compliance/lifecycle webhooks (e.g., `app/uninstalled` bodies can be minimal `{}`/near-static JSON). No access token, `client_secret`, or privileged account is required; only the ability to install the app on an attacker-controlled shop and to send arbitrary HTTP requests to the app's public webhook endpoint.

### Recommendation
Bind the routing metadata to the same authenticated bytes the HMAC covers: include `shop`, `topic`, and `webhook_id` in the canonical signed string this gem verifies (or require the host app to separately confirm they match a currently-registered subscription/shop before invoking `handle`). At minimum, `ShopifyAPI::Webhooks::Request#to_signable_string` should incorporate the shop-domain and topic headers, so a valid signature can no longer be replayed across shops or topics.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and triggers a webhook with a minimal/static body, e.g. `app/uninstalled` with body `{}`.
2. Shopify sends headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: app/uninstalled`, `x-shopify-hmac-sha256: <valid-hmac-of-"{}">`.
3. Attacker replays the exact same body and `hmac` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13-22`) recomputes HMAC over `"{}"` and matches, since the shop header is never part of the signed input.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) builds `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "app/uninstalled", ...)` and invokes the host app's handler as though Shopify itself reported `victim.myshopify.com` uninstalled the app.
