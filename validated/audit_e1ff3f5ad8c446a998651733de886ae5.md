### Title
Address cache trusts stored/synced address without re-deriving or verifying it against the wallet's key material - (File: features/address-provider/module/address-cache/index.js, features/address-provider/module/address-provider.js)

### Summary
`AddressProvider.getAddress` (and its callers `getDefaultAddress`, `getChangeAddress`, `getUnusedAddress`, `getReceiveAddresses`) will, on a cache hit, return the cached `address` string as-is without ever re-deriving it from the wallet account's key material and comparing it. The cache itself is populated both from on-disk storage (`features/address-provider/module/address-cache/index.js`) and from data pushed through a fusion sync channel, and neither path validates that the `address` corresponds to the `walletAccountName`/`derivationPath` it is keyed under before it can be served back to callers. This mirrors the reported KeyFile issue where a persisted `address` field is trusted without being re-derived/sanitized from the underlying secret.

### Finding Description
`AddressProvider.getAddress` looks up the address cache and, if present, returns it directly: [1](#0-0) 

The cache is backed by on-disk storage (`this.#cachesStorage`, a `storage.namespace('caches')`) that is loaded at startup and merged into the in-memory atom without any check that the stored `address` matches what would actually be derived for that `derivationPath`/`walletAccountName`: [2](#0-1) 

The cache is also updated from a fusion sync channel (`processBatch`), which merges externally-supplied address data directly into the atom, again marking it `synced: true` without re-derivation: [3](#0-2) 

The only place a derived address is ever compared to the cached one is in `set()`, and only opportunistically — a mismatch is merely logged and recorded under `mismatches`, but the (correctly re-derived) value is still what gets written going forward; nothing revalidates or purges a maliciously injected cache entry before it is served by `get()`: [4](#0-3) 

The underlying desktop storage adapter persists this data as plaintext JSON on disk with no integrity protection: [5](#0-4) 

This is the same root-cause pattern as the reported issue: a persisted `address` value (analogous to `KeyFile.address`) is deserialized from storage/sync and handed back to the caller (and ultimately shown in the UI as a receive/change address) without being sanitized — i.e., without verifying it against the value that would actually be derived from the wallet's key for that derivation path.

### Impact Explanation
If an attacker can modify the on-disk `caches` storage namespace (e.g., local filesystem access, the same threat model as the original report) or inject data through the fusion sync channel, they can substitute an attacker-controlled address for a given `walletAccountName`/`derivationPath`. Any subsequent call to `getAddress`/`getDefaultAddress`/`getChangeAddress` with `useCache` true (the default in `getAddress`) will silently return the attacker's address as the user's own receive/change address. A user relying on this address to receive funds (or as their own change address in a transaction) would have funds diverted to the attacker — a direct wallet-compromise-level impact matching the original bug's exploit scenario.

### Likelihood Explanation
Exploitation requires local write access to the wallet's storage (or compromise of the fusion sync data path), which is the same precondition the original report itself relies on ("malicious actor with filesystem access"). It does not require any peer/operator/mocked component and is reachable through code paths used by default (`getAddress` defaults `useCache = true`).

### Recommendation
Do not trust cached/synced `address` values for return without validation. On cache read (`get`), when serving a cached address, revalidate it lazily against a freshly-derived address (or at minimum on load from disk/sync, mark all incoming cache data as unverified and require re-derivation once per session before trusting it for display), and purge/quarantine entries recorded under `mismatches` rather than only logging them.

### Proof of Concept
1. Note the on-disk storage path used by `storage.namespace('caches')` (via `adapters/storage-unsafe-desktop`), keyed by wallet account name, mapping `derivationPath -> { address, synced }`.
2. With local filesystem access, edit the stored entry for `exodus_0`'s `bitcoin` `m/84'/0'/0'/0/0` entry, replacing `address` with an attacker-controlled Bitcoin address.
3. Restart the application; `AddressCache#load` merges the tampered file content into `addressCacheAtom` (`features/address-provider/module/address-cache/index.js:177-202`) without re-derivation.
4. Call `addressProvider.getDefaultAddress({ walletAccount, assetName: 'bitcoin' })` (or trigger the receive-address UI); `getAddress` finds the cache hit and returns the tampered address (`features/address-provider/module/address-provider.js:104-128`) as the user's receive address.
5. A user sending funds to "their own" displayed change/receive address, or a counterparty sending to the displayed receive address, sends funds to the attacker instead.
