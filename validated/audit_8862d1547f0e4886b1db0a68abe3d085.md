### Title
Excess native token sent to `EvmHost.dispatch`/`fundRequest` is trapped in the Host contract instead of being refunded to the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` all accept native-token payment and swap the *entire* `msg.value` through Uniswap V2's `swapETHForExactTokens` for an *exact* output amount (`post.fee`, `get.fee`, or `amount`). Any unspent ETH from an over-estimated `msg.value` is never returned to the original caller.

### Finding Description
In `dispatch(DispatchPost)`:
```solidity
if (msg.value > 0) {
    address[] memory path = new address[](2);
    address uniswapV2 = _hostParams.uniswapV2;
    path[0] = IUniswapV2Router02(uniswapV2).WETH();
    path[1] = feeToken();
    IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
        post.fee, path, address(this), block.timestamp
    );
}
``` [1](#0-0) 

The same pattern is repeated in `dispatch(DispatchGet)` and `fundRequest`: [2](#0-1) [3](#0-2) 

`IUniswapV2Router02.swapETHForExactTokens` is an exact-output swap: any leftover ETH not consumed by the swap (`msg.value - amountIn`) is refunded by the router to its immediate caller, which is `EvmHost` itself (since `EvmHost` is the one invoking the router with `{value: msg.value}`), not to `_msgSender()`/`post.payer`/the end user who sent the transaction. `EvmHost` has no code path after the swap call that captures this refund and forwards it back to the caller - there is no `_sendValue`/refund logic analogous to what exists elsewhere in the repo (e.g. `IntentGatewayV2.sol` and `ExtrinsicIntents.sol`/`IntrinsicIntents.sol`, which explicitly track `msgValue` and call `_sendValue(msg.sender, msgValue)` for any unspent native token after a swap): [4](#0-3) 

Because `EvmHost` accepts arbitrary refunded ETH from the router (it must have a `receive()`/payable fallback to even accept the router's refund transfer), any overpayment simply accumulates as unallocated ETH balance on the `EvmHost` contract with no accounting entry, no event, and no user-facing withdrawal mechanism tied to that specific overpayment. This is the exact bug class described in the reference report: any user who slightly overestimates the required native amount for `msg.value` (a normal client-side estimation practice, since exact swap output pricing can shift between quote-time and execution-time due to slippage) permanently loses the excess.

This is directly reachable by any unprivileged relayer, app, or end user dispatching a POST/GET request or funding a pending request through `IDispatcher.dispatch`/`fundRequest`, which are the primary permissionless entry points for message dispatch documented in `docs/content/developers/evm/messaging/post-requests.mdx` and `docs/content/developers/evm/api/idispatcher.mdx`. [5](#0-4) 

### Impact Explanation
Users sending native token to pay dispatch/relayer fees permanently lose any amount above what the swap actually consumes. This is a direct, unrecoverable loss of user funds (native token) on every dispatch call where the caller doesn't send the exact minimal `msg.value` needed for the swap — which in practice is nearly always, since callers must overestimate to account for price movement/slippage between fee quoting and transaction execution. Given `dispatch` and `fundRequest` are core, high-frequency entry points of the entire Hyperbridge messaging protocol, this represents a systemic, protocol-wide fund-loss issue rather than an edge case.

### Likelihood Explanation
High likelihood: any client that follows the documented usage pattern (`IDispatcher(host()).dispatch{value: msg.value}(post)`) and provides a safety margin on `msg.value` (as recommended practice for AMM-based fee swaps subject to slippage) triggers the loss on every call. No malicious actor or special conditions are required — normal, honest usage of the protocol's primary dispatch functions results in fund loss.

### Recommendation
Track the router-returned `amounts[0]` (actual ETH spent) from `swapETHForExactTokens`, compute `refund = msg.value - amounts[0]`, and immediately forward `refund` back to `_msgSender()` (or `post.payer`) in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, mirroring the refund pattern already implemented in `IntentGatewayV2.sol`/`ExtrinsicIntents.sol` (`_sendValue(msg.sender, msgValue)` after the swap).

### Proof of Concept
1. Caller `A` invokes `EvmHost.dispatch(DispatchPost{ ..., fee: 100 feeTokenUnits })` with `msg.value = 1 ether` to be safe against price slippage.
2. `EvmHost.dispatch` calls `IUniswapV2Router02.swapETHForExactTokens{value: 1 ether}(100, path, address(this), block.timestamp)`.
3. Suppose only `0.05 ether` is actually required to obtain 100 `feeToken` units; the Uniswap router refunds `0.95 ether` to `msg.sender` of the swap call, which is `EvmHost` (not caller `A`).
4. `EvmHost.dispatch` completes normally, emitting `PostRequestEvent`, with no code path returning the `0.95 ether` to `A`.
5. `A`'s `0.95 ether` is now stranded as an unaccounted balance inside `EvmHost`, permanently lost from `A`'s perspective, exactly as in the referenced Allo.sol `_createPool` bug where excess native tokens sent above `baseFee + amount` were never refunded. [1](#0-0)

### Native Token Payment

For native token payments, dispatch directly and let the Host handle the Uniswap swap:

```solidity lineNumbers title="MyApp.sol"
contract MyApp is HyperApp {
    function sendMessageWithNative(
        bytes memory message,
        bytes memory dest,
        uint64 timeout,
        address to,
        uint256 relayerFee
    ) public payable returns (bytes32) {
        DispatchPost memory post = DispatchPost({
            body: message,
            dest: dest,
            timeout: timeout,
            to: abi.encode(to),
            fee: relayerFee,
            payer: msg.sender
        });
        
        // User must send enough native tokens to cover fees
        // The Host will swap native -> feeToken via Uniswap
        return IDispatcher(host()).dispatch{value: msg.value}(post);
    }
```
