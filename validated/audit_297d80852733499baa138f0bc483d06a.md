### Title
Unauthenticated MessageID collision in the gateway's WebAPI capability handler overwrites another user's pending callback, causing cross-user response confusion / request-hijack denial of service - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` stores an in-flight caller's callback in a shared `map[string]*savedCallback` keyed only by the client-supplied `msg.Body.MessageID`, with no check that the key is already in use before overwriting it. This mirrors the reported `addCollateralToken` bug class: a mapping is written unconditionally by index/key without an existence check, so a second write silently clobbers state tied to the first.

### Finding Description
`HandleLegacyUserMessage` is the gateway-side entry point that accepts unauthenticated `web_api_trigger` messages from external HTTP clients and dispatches them to DON nodes. After minimal validation (payload decode, timestamp freshness), it takes the request's `MessageID` — a value fully controlled by the calling client, not a server-generated nonce — and unconditionally overwrites the `savedCallbacks` map entry for that ID: [1](#0-0) 

There is no lookup/existence check analogous to what `addCollateralToken` should have had for `collateralAddress`. If two different unprivileged clients (or one client racing itself, or an attacker who observes/guesses another user's `MessageID`) submit `web_api_trigger` requests with the same `MessageID` while the first is still in flight, the second write replaces the first caller's stored `*savedCallback` in place, silently dropping the reference to the original caller's `Callback`.

Later, when a DON node responds with that `MessageID`, `handleWebAPITriggerMessage` looks the ID up once, deletes it, and routes the (single) result to whichever callback is currently stored — the second, attacker/second-user's callback, not the first caller's: [2](#0-1) 

The insertion itself has no guard: [1](#0-0) 

whereas the comparable vault gateway handler, which faces the same "unprivileged caller supplies request ID" problem, does perform the existence check before writing: [3](#0-2) 

This confirms the codebase already treats "check-before-insert on caller-supplied ID keyed maps" as the correct pattern elsewhere, making its absence in `capabilities/handler.go` a genuine, addressable analog of the reported class of bug (mapping write without existence check leading to overwrite/data inconsistency).

### Impact Explanation
- The original caller whose callback was overwritten never receives a response for their in-flight request (their HTTP/websocket request hangs until any outer timeout, if one exists) — a denial of service against a specific in-flight request.
- The attacker/second caller's callback instead receives the DON's response to the *original* caller's `web_api_trigger` request — cross-user response confusion, potentially leaking response content associated with another user's triggered request/execution to an unrelated caller.
- Because `MessageID` is attacker-controlled and there's no per-key uniqueness enforcement, this is directly reachable by any unprivileged client hitting the internet-facing gateway endpoint that accepts legacy user messages — no privileged access is required.

### Likelihood Explanation
Exploitability depends on the attacker being able to submit (or guess/observe) a `MessageID` that collides with another concurrently in-flight legitimate request. If `MessageID`s are client-chosen (rather than gateway-generated, unpredictable UUIDs), an attacker can trivially force a collision by choosing the same value used by a victim (e.g., if IDs are predictable, sequential, or reused by client SDKs) or by simply resending the same ID they used previously while the first is still pending (self-collision, causing loss of the earlier response) — this alone demonstrates the missing check is reachable and has a concrete, reproducible effect. Whether real-world `MessageID` generation practices (e.g., random UUID per request from official SDKs) make third-party collisions likely is not fully verifiable from the available code, but the bug is present regardless — the map write should never blindly overwrite an active entry, since the class of the reported issue (`addCollateralToken`) is exactly "we didn't check, so we silently clobbered".

### Recommendation
In `HandleLegacyUserMessage`, before inserting into `h.savedCallbacks`, check whether an entry already exists for `msg.Body.MessageID`, mirroring the guard already used in `vault/handler.go`'s `newActiveRequest`:
```go
h.mu.Lock()
if _, exists := h.savedCallbacks[msg.Body.MessageID]; exists {
    h.mu.Unlock()
    return callback.SendResponse(handlers.UserCallbackPayload{
        RawResponse: codec.EncodeNewErrorResponse(msg.Body.MessageID, api.ToJSONRPCErrorCode(api.HandlerError), "duplicate message ID", nil),
        ErrorCode: api.HandlerError,
    })
}
h.savedCallbacks[msg.Body.MessageID] = &savedCallback{...}
h.mu.Unlock()
```
Additionally, consider deriving `MessageID` uniqueness scope per requesting session/connection (or generating it server-side) rather than trusting the raw client-supplied value as a global map key.

### Proof of Concept
1. Client A sends a `web_api_trigger` legacy message to the gateway with `MessageID = "X"`. The gateway calls `HandleLegacyUserMessage`, which stores Client A's callback at `savedCallbacks["X"]` and forwards the request to DON nodes.
2. Before any node responds, Client B (or Client A again) sends a second `web_api_trigger` message reusing `MessageID = "X"`. `HandleLegacyUserMessage` overwrites `savedCallbacks["X"]` with Client B's callback — no existence check exists to reject or reroute this.
3. A DON node eventually responds with `MessageID = "X"` for Client A's original request. `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds Client B's callback (since it replaced Client A's), deletes the entry, and delivers the response to Client B.
4. Client A's request hangs indefinitely (its callback reference was discarded), while Client B receives a response to a request it never made — demonstrating both denial-of-service against Client A and cross-user response confusion for Client B.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
