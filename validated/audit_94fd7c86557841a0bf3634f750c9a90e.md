### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, allowing cross-tenant webhook forgery via replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` and `topic` values used to route and act on that webhook come from separate, unauthenticated HTTP headers. This breaks the binding `HMAC-verified bytes == bytes acted upon`, allowing a captured, validly-signed webhook body to be replayed with forged `shop-domain`/`topic` headers and processed as if it belonged to a different tenant.

### Finding Description
`Registry.process` verifies authenticity with: [1](#0-0) 

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [2](#0-1) 

`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method returns only the raw body: [3](#0-2) 

Meanwhile `topic` and `shop` — the exact fields used to select the handler and to identify which tenant the webhook is *for* — are pulled straight from HTTP headers with no cryptographic linkage to the body or its HMAC: [4](#0-3) 

So the equality that should hold — `hmac_signed(shop, topic, body) == (shop, topic, body) acted upon` — does not: only `body` is signed, while `shop` and `topic` are trusted from headers verbatim.

### Impact Explanation
Because a Shopify app typically uses a single `client_secret` (`api_secret_key`) shared across every installed shop, any merchant (an unprivileged actor with respect to other tenants of the same app) who receives legitimate webhooks to their own store obtains valid `(raw_body, hmac)` pairs signed with that same app-wide secret. Since `shop-domain` and `topic` headers are not part of the signed content, that same `raw_body`/`hmac` pair can be replayed against the app's webhook endpoint with a different `X-Shopify-Shop-Domain` (or `X-Shopify-Topic`) header. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` then dispatches the handler using the attacker-forged `request.shop`/`request.topic`, causing the app to act on another tenant's data using attacker-influenced payload content (e.g., triggering `customers/redact`/`shop/redact`-style handling, or updating/deleting records) attributed to a shop the attacker does not control. This is a cross-tenant integrity/authorization violation stemming directly from an identity field not being covered by the HMAC.

### Likelihood Explanation
Exploitation requires the attacker to be a legitimate (even trial) merchant of the target app to obtain valid signed webhook deliveries, then relay a crafted HTTP request to the app's webhook endpoint with altered `shop-domain`/`topic` headers and the previously captured body/hmac — no possession of `api_secret_key` or an access token for the *victim* shop is needed. The library itself performs no cross-check between the header-derived `shop`/`topic` and the HMAC-covered content, so any host application that follows the library's documented usage of `Registry.process`/`HmacValidator` inherits this gap.

### Recommendation
Include `shop`, `topic`, and `api_version` in the HMAC-signable content for webhook requests (e.g., by binding them into `to_signable_string` or requiring the host app to independently correlate `shop-domain` with the session/tenant that requested webhook registration) rather than trusting them from unauthenticated headers. At minimum, document that `request.shop`/`request.topic` are unauthenticated and must be cross-validated by the host application against known/expected tenants before use.

### Proof of Concept
1. App has shops `A.myshopify.com` and `B.myshopify.com` installed, both signed with the same `client_secret`.
2. Attacker controls (or trials) shop `A` and captures a legitimate webhook delivery: `raw_body`, and header `X-Shopify-Hmac-Sha256: <hmac>` (valid because `HmacValidator` only signs `raw_body`) — see [3](#0-2) .
3. Attacker replays this exact `raw_body` + `hmac` header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: B.myshopify.com` and/or `X-Shopify-Topic: customers/redact`.
4. `Registry.process` calls `HmacValidator.validate(request)`, which passes because only the body is checked — [5](#0-4) .
5. The handler is dispatched with `shop: "B.myshopify.com"`, `topic: "customers/redact"`, and attacker-controlled body content, even though this data never originated from shop `B` — [6](#0-5) .
