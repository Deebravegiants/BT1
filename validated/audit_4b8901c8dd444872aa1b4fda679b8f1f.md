### Title
LP graduation seeding can open the HyperSwap V2 pair materially off the bonding-curve close price under an extreme LT-rich pre-seed ("M-02 regime") - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding.finalizeGraduation` seeds the HyperSwap V2 `TOKEN/LT` pair via `_seedUniswapV2Direct` / `_seedRebalancing` / `_pairRebalance`, which is designed to neutralize a front-run pre-seed of the pair (the same bug class as the four.meme incident referenced in the codebase's own `AGENTS.md`). The rebalance mechanism computes a swap to push the pool back to the curve-close ratio, but the swap input is capped at a fixed per-side budget (~99% of `tokensForLP`). When an attacker front-runs `factory.createPair`/`pair.mint` with an extreme LT-rich ratio, the optimal rebalancing swap exceeds this budget, the cap binds, and the pool is deposited while still materially off the curve-close price — a condition the protocol's own regression test explicitly reproduces and labels "accepted residual."

### Finding Description
`finalizeGraduation` (phase 2 of graduation) calls `_ensureUniswapV2Pair` and `_seedUniswapV2Direct` to deposit the curve-frozen `(tokensForLP, ltFromPair)` inventory into the HyperSwap `TOKEN/LT` pair and lock the resulting LP in `LPLock` [1](#0-0) .

`_ensureUniswapV2Pair` reuses any pre-existing pair via `factory.getPair`, which is exploitable because `factory.createPair(token, lt)` is permissionless and an attacker can pre-mint LP into that pair at a hostile ratio before `finalizeGraduation` runs [2](#0-1) . The defense against this (documented extensively in `AGENTS.md`) branches into three regimes; "Regime 3" rebalances a hostile mint pre-seed via a direct `pair.swap` toward the curve-close ratio before depositing the remaining inventory through `router.addLiquidity` [3](#0-2) .

The rebalance swap input is explicitly capped "at our per-side budget," and when the pre-seed is extreme enough that the optimal correcting swap exceeds that budget, the cap binds and the deposit lands "materially off curve-close" — this is acknowledged directly in the natspec's brick-resistance section [4](#0-3) .

The protocol's own regression test, `test_hostilePreSeed_budgetCappedSwap_isNotProfitable` ("M-02 reproducer"), constructs exactly this scenario: an LT-rich mint pre-seed (`reserveToken = tokensForLP/100`, `reserveLt = ltFromPair*200`) whose optimal rebalance swap exceeds the ~99%-of-`tokensForLP` budget cap. The test asserts `finalizeGraduation` succeeds but the resulting pool price is `>1.2x` the curve-close price, explicitly commenting: "M-02 regime: pool opens materially off curve-close" [5](#0-4) .

### Impact Explanation
The LP minted from this seeding is permanently locked by `LPLock.recordLock` with no withdraw/rescue path [6](#0-5) . Because the pool opens materially off the curve-close price, the mispricing represents value that can be extracted by arbitrageurs directly out of this permanently-locked, protocol/community-owned liquidity — a real and unrecoverable loss to the token's LP holders (via `LPLock`) that cannot be reversed the way a normal, unlocked LP position could self-correct without loss to its owner. This directly matches the Validate criterion "an LP seeded away from the curve close price," and because the locked LP can never be withdrawn to correct the loss, the impact is a permanent, protocol-level value leak rather than a transient one.

### Likelihood Explanation
Reaching this state requires only unprivileged, permissionless actions: (1) acquire a large quantity of the external LT (freely tradable) and a modest amount of the target `TOKEN` (buyable on the curve via `Bonding.buy`/`Zap.buy`), (2) front-run the graduation by calling `factory.createPair(token, lt)` and `pair.mint(attacker)` with an extreme LT-rich ratio before `finalizeGraduation` executes, and (3) let the permissionless `finalizeGraduation(tokenAddress)` run (callable by anyone, including the attacker) [7](#0-6) . No special privilege, timing race beyond ordinary mempool front-running, or contract bug beyond the documented budget cap is required — the codebase's own test suite proves the exact ratio needed to trigger it.

### Recommendation
Increase or make dynamic the per-side rebalance-swap budget so it can always reach the curve-close ratio (or bound the acceptable pre-seed ratio at pair-creation time), and/or route any residual off-ratio inventory through a second corrective step (e.g., an additional bounded swap or partial deposit deferral) rather than accepting a single capped swap. At minimum, add a monitoring/circuit-breaker so `finalizeGraduation` can flag (not necessarily revert, to preserve brick-resistance) graduations whose post-seed price deviates beyond a safety threshold from curve-close, so the mispriced window can be economically defended (e.g., protocol-initiated counter-arbitrage) before third parties extract the locked LP's value.

### Proof of Concept
Reference `test_hostilePreSeed_budgetCappedSwap_isNotProfitable` in `packages/contracts/test/TwoPhaseGraduation.t.sol` (lines 864–900), which already reproduces the mechanics end-to-end in the existing test suite: it front-runs pair creation via `MockHyperswapFactory.createPair`, seeds `reserveToken = tokensForLP/100` and `reserveLt = ltFromPair*200` via `pair.mint(griefer)`, asserts the optimal correcting swap exceeds the 99%-of-`tokensForLP` budget, calls `bonding.finalizeGraduation(tokenAddr)`, and asserts the resulting pool price is more than 1.2x the curve-close price.     function finalizeGraduation(
```text
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
```

```text
    /// @notice M-02 reproducer. An LT-rich mint pre-seed so lopsided that the
    ///         TOKEN-side rebalance swap exhausts its full budget (~99% of
    ///         `tokensForLP`) without reaching the cached ratio, so the pool
    ///         deposits materially off curve-close. Finalize must still succeed
    ///         (no brick), the over-funded LT side must be confiscated to the
    ///         owner, and the pre-seeder must end net-negative.
    function test_hostilePreSeed_budgetCappedSwap_isNotProfitable() public {
        (address tokenAddr,) = _launchToken();
        _enterGraduating(tokenAddr);

        (uint256 tokensForLP, uint256 ltFromPair,,) = bonding.pendingGraduation(tokenAddr);

        // Extreme LT-rich shape: TOKEN side at 1% of target, LT side at 200x.
        // The optimal TOKEN-in swap to reach the cached ratio is ~1.4x
        // `tokensForLP`, so the 99%-of-`tokensForLP` budget cap binds and the
        // pool stays ~2x off curve-close after the swap.
        uint256 reserveToken = tokensForLP / 100;
        uint256 reserveLt = ltFromPair * 200;

        // M-02 precondition: the optimal swap exceeds the budget (this is the
        // budget-capped regime, distinct from the swap-rounds-to-zero fallback
        // covered by the dust tests above).
        assertGt(
            _noFeeSwapInputUncapped(reserveToken, reserveLt, tokensForLP, ltFromPair),
            (tokensForLP * 99) / 100,
            "setup: optimal rebalance swap must exceed the per-side budget (M-02 regime)"
        );

        deal(tokenAddr, griefer, reserveToken);
        address hyperPair = _grieferMintPreSeed(tokenAddr, reserveToken, reserveLt);
        uint256 grieferLp = MockHyperswapPair(hyperPair).balanceOf(griefer);
        uint256 ownerLtBefore = lt.balanceOf(bonding.owner());

        bonding.finalizeGraduation(tokenAddr);
        assertTrue(bonding.isGraduated(tokenAddr), "finalize must succeed despite an unrecoverable pre-seed");

        // The accepted residual: no bounded swap can correct a 200x LT-rich
        // pre-seed, so the pool opens materially off curve-close.
        assertGt(
            _poolPriceLtPerToken(hyperPair, tokenAddr),
            (((ltFromPair * 1e18) / tokensForLP) * 12) / 10,
            "M-02 regime: pool opens materially off curve-close"
        );
```
