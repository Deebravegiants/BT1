## Custody Analog Found

### Title
Signature replay in `usdk::transfer_from` allows unlimited draining of owner funds via a single approval - (File: `aptos-move/move-examples/fungible_asset/stablecoin/sources/usdk.move`)

### Summary
`usdk.move` implements an ERC-2612-style "permit" flow: the token owner signs an off-chain `Approval` message and any third-party `spender` submits it on-chain via `transfer_from` to move funds out of the owner's primary fungible store. This is the Aptos-native analog of the Cork `FlashSwapRouter` permit pattern from the external report — a privileged, custody-moving operation is authorized by a signature but executed by an unprivileged third party. Unlike Cork's `amountOutMin=0` MEV vector, the concrete broken invariant here is nonce handling: the "nonce" bound into the signed message is the owner's live account sequence number, which is not consumed or invalidated by `transfer_from` itself. This lets the `spender` (or anyone who obtains the proof bytes, since they are passed as a plain function argument and visible in the mempool/calldata) replay the exact same signed proof repeatedly, draining the owner's balance in `amount`-sized increments until the store is empty, entirely bypassing the intended one-time-authorization guarantee.

### Finding Description
`transfer_from` reconstructs the expected signed message as: [1](#0-0) 

The `nonce` field of `Approval` is set to `account::get_sequence_number(from)` — the **live** sequence number of the owner's account at the time `transfer_from` executes: [2](#0-1) 

`account::get_sequence_number` reflects the number of transactions `from` has personally submitted as a signer. Because `transfer_from` is submitted by `spender`, not by `from`, calling `transfer_from` does **not** advance `from`'s sequence number. Consequently, the exact same `proof` bytes continue to satisfy `verify_signed_message` on every subsequent call, as long as `from` has not independently submitted a transaction in between. There is no on-chain "used proof" table, no monotonically-incrementing allowance nonce dedicated to `transfer_from`, and no `amount`-remaining/allowance bookkeeping (unlike a standard ERC-20 `approve`/`transferFrom` allowance model) — `transfer_from` performs a direct `primary_fungible_store::transfer_with_ref` for the full signed `amount` every time it is invoked with a still-valid proof.

This breaks the custody invariant that a single owner-signed authorization should move value exactly once (or up to a bounded allowance) rather than being infinitely replayable by whoever holds the signature bytes.

### Impact Explanation
This is a critical custody-corruption bug: any party in possession of a valid `Approval` proof (the `spender` who receives it, or anyone who observes it on-chain/in the mempool once submitted) can call `transfer_from` repeatedly to drain the owner's entire USDK balance, moving value to the wrong holder without further owner consent — directly violating the "Theft ... of ... fungible assets" and "Supply or custody accounting corruption that moves value to the wrong holder" custody gates. Because `transfer_from` uses `transfer_with_ref` (bypassing normal owner-signed transfer checks other than deny-list/pause), the only backstop against draining is the owner happening to submit an unrelated transaction that bumps their sequence number before the attacker replays the proof — which is not a reliable or intentional security control.

### Likelihood Explanation
High likelihood: this is a `move-examples` reference stablecoin implementation intended to be used/forked as a production pattern (it implements mint/burn/freeze/pause/denylist — all custody-critical stablecoin controls). Any project that copies this `transfer_from`/`Approval` pattern verbatim (as is common with Aptos example code) inherits the replay flaw. Exploitation requires no special privilege: the attacker only needs to be the named `spender` in one legitimately obtained approval (e.g., a routine dApp interaction) and can then resubmit the identical transaction payload multiple times.

### Recommendation
Do not derive the anti-replay nonce from the owner's transaction sequence number when the owner is not the transaction sender. Instead:
- Maintain a dedicated per-owner (or per-owner/spender) monotonically-incrementing nonce or a `used_proofs: SimpleMap<hash, bool>` inside the `usdk` module's state, incremented/marked at the start of `transfer_from` before or atomically with the transfer, aborting on reuse.
- Alternatively, adopt an explicit allowance model (owner sets a bounded allowance for `spender`, decremented on each `transfer_from` call) so a single signature cannot be replayed beyond the granted amount.

### Proof of Concept
1. `owner` (address `from`) signs one `Approval { owner: from, to, nonce: account::get_sequence_number(from), chain_id, spender: attacker, amount }` and hands the resulting `proof` to `attacker` for a single intended payment.
2. `attacker` calls `usdk::transfer_from(attacker, proof, from, scheme, pubkey, to, amount)`. It succeeds, transferring `amount` from `from` to `to`.
3. Because `from` never submitted a transaction, `account::get_sequence_number(from)` is unchanged, so the reconstructed `expected_message` in a second call is byte-identical to the first.
4. `attacker` calls `usdk::transfer_from` again with the exact same `proof` argument bytes. `verify_signed_message` succeeds again (same message, same signature), and another `amount` is transferred from `from`.
5. Repeat until `from`'s USDK balance is exhausted, or until `from` happens to submit an unrelated transaction that changes its sequence number.

Note: I could not directly inspect the byte-level implementation of `account::verify_signed_message` / `account::get_sequence_number` in this pass (only located them via grep, not fully read) due to iteration limits, so the exact abort conditions of `verify_signed_message` (e.g., auth-key-vs-public-key binding) are asserted based on standard Aptos framework semantics rather than a direct code read in this session. Confirming the full body of `account::verify_signed_message` would further solidify this finding.
