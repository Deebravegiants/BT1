### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` (and `topic`/`api_version`/`webhook_id`) values that are handed to the merchant's webhook handler are taken from unauthenticated HTTP headers that are excluded from the signed bytes. Because a single app has one `api_secret_key` shared across every merchant that installs it, any user who installs the app on their own (attacker-controlled) store can obtain a genuinely-signed `(body, hmac)` pair and replay it to the app's webhook endpoint with a forged `shop-domain` header, making the request appear to originate from a different (victim) shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`HmacValidator.validate` verifies exactly and only `verifiable_query.to_signable_string` against `verifiable_query.hmac`: [3](#0-2) 

`Registry.process` trusts this validation, then forwards the header-derived, unauthenticated `request.shop` straight to the merchant's handler: [4](#0-3) 

The equality that should hold is: *the shop that produced the HMAC-signed bytes == the shop value the handler is told the webhook came from*. Because `shop-domain` is outside the signed string, this equality is never enforced — the library only proves "someone who knows `api_secret_key` signed this body," not "this body came from shop X." Since `api_secret_key` is identical for all merchants of a given app, an unprivileged attacker who installs the app on their own store can:
1. Trigger (or synthesize, via a legitimately-registered webhook on their own store) a real `(raw_body, hmac)` pair signed with the app's shared secret.
2. POST that exact body/HMAC to the app's public webhook endpoint while setting `x-shopify-shop-domain` (or `shopify-shop-domain`) to a victim shop's domain.
3. `Registry.process` passes HMAC validation (body untouched) and calls the handler with `shop: "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own store.

Any app logic that trusts `WebhookMetadata#shop` to scope database writes, cache invalidation, entitlement changes, or triggers per-tenant side effects (a standard pattern for Shopify apps) can be manipulated to act as if the (attacker-authored) payload belongs to another tenant.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook delivery: it lets one merchant's genuinely-signed traffic be relabeled as belonging to a different merchant, resulting in cross-tenant data confusion in any app that keys webhook handling logic off `WebhookMetadata#shop`. This matches the Critical "cross-tenant access" impact category since the shop-scoping guarantee that webhook consumers rely on from this gem is not actually cryptographically enforced.

### Likelihood Explanation
Likelihood is Medium-High: no privileged credentials, leaked secrets, or host misconfiguration are required — only that the attacker can install the target app on a store they control (trivial via a free Shopify development store) and can send arbitrary HTTP requests directly to the app's public webhook endpoint, which is by design internet-reachable.

### Recommendation
Bind the shop/topic identity into the signed payload check, or otherwise refuse to trust header-derived identity: e.g., include `shop-domain` (and other Shopify headers used for routing/business logic) as part of `to_signable_string`, or require the consuming application to independently re-validate that the webhook's shop matches a shop known to have that webhook registered (e.g., cross-check against stored per-shop webhook IDs/session records) before trusting `WebhookMetadata#shop`. Document clearly that `shop` in `WebhookMetadata` is not authenticated by the HMAC and must not be used as the sole tenant-scoping key.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and registers a webhook (e.g., `products/create`) pointing at the app's public endpoint.
2. Attacker creates a product with attacker-chosen JSON body content, causing Shopify to deliver a webhook with headers:
   - `x-shopify-hmac-sha256: <valid HMAC of body, computed with app's shared api_secret_key>`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-topic: products/create`
3. Attacker captures this raw body and HMAC value (both are visible to them since it's their own store's webhook).
4. Attacker sends a new POST directly to the app's public webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the HMAC — it succeeds because the body/HMAC pair was never modified — reference: [5](#0-4) .
6. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker-controlled body>, ...)`, letting the attacker inject attacker-chosen webhook content attributed to a different tenant.
