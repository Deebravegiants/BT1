Confirmed: `HttpClient#initialize` builds `@base_uri` directly from `session.shop` (unless `Context.api_host` override is set), so whatever `shop` value ends up in a `Session` is the exact host that receives the POST body containing `client_id` and `client_secret` at `/admin/oauth/access_token` [1](#0-0) .

Every other credential-issuing entry point in this gem — `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.exchange_token` — calls `Utils::ShopValidator.sanitize!` (or derives the shop from a JWT `dest` claim) before building the `Session` that is handed to `HttpClient` [2](#0-1) [3](#0-2) . `ShopValidator.sanitize!` restricts the host to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) [4](#0-3) .

`Oauth.begin_auth`, however, takes the caller-supplied `shop:` argument and feeds it straight into `auth_base_uri(shop)` with no call to `ShopValidator` anywhere in the method [5](#0-4) , and `auth_base_uri` simply interpolates it into `"https://#{shop}/admin"` [6](#0-5) . The gem's own documented usage pattern takes `shop` directly from an inbound request header (`request.headers["Shop"]`) and passes it unmodified into `begin_auth` [7](#0-6) .

### Title
Missing shop-domain validation in `Oauth.begin_auth` enables forced OAuth completion / session fixation - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`Oauth.begin_auth` is the one OAuth entry point in this gem that never routes the `shop` value through `Utils::ShopValidator`, breaking the identity binding "the host that receives the redirect (and holds the CSRF `state`) == a shop the app actually trusts" that every sibling method (`client_credentials`, `refresh_access_token`, `exchange_token`) enforces.

### Finding Description
`begin_auth(shop:, redirect_path:, ...)` builds the authorization redirect URL as `auth_base_uri(shop) + "/oauth/authorize?client_id=...&redirect_uri=...&state=NONCE&..."`, where `auth_base_uri` is literally `"https://#{shop}/admin"` [8](#0-7) . Unlike `client_credentials.rb`, `refresh_token.rb`, and `token_exchange.rb`, which all call `Utils::ShopValidator.sanitize!` (or take the shop from a signed JWT `dest` claim) before the value is ever used to construct a request destination, `begin_auth` performs no such check. Since `shop` here comes from the unauthenticated login-initiation request (per the gem's documented pattern, an HTTP header set by the visitor), any unprivileged internet user can supply an arbitrary host. `begin_auth` returns this attacker-chosen URL as `auth_route` together with a freshly generated CSRF `state` nonce and a `SessionCookie` that the host application is instructed to set on the visitor's browser before redirecting to `auth_route` [9](#0-8) . Because the redirect target is fully attacker-controlled, the attacker's own server receives the app's `client_id`, the callback `redirect_uri`, and the CSRF `state` value that is simultaneously written into the victim's browser cookie. The attacker can then complete a genuine OAuth grant on a shop they control and drive the victim (or replay the flow) to the app's real `/auth/callback` route using that captured `state`; `validate_auth_callback` only checks `state == cookies[SESSION_COOKIE_NAME]` and the HMAC over the query Shopify itself signed for the attacker's own shop [10](#0-9)  — it never confirms the completed grant belongs to the shop the victim originally intended to authenticate to. This is the classic forced-OAuth-completion / login-CSRF pattern, made reachable here purely because `begin_auth` skips the domain check every other credential-issuing path performs.

### Impact Explanation
This is High severity per the given impact taxonomy: "session fixation or forced OAuth completion." An attacker can fixate a victim's app session to an attacker-controlled shop/access-token grant, and additionally exfiltrate the app's `client_id` and configured `redirect_uri` to an arbitrary attacker host as a side effect of the unvalidated redirect.

### Likelihood Explanation
Likelihood is high: no credentials are required, the `shop` parameter path is exactly the one documented for app developers to wire straight from user input, and the missing check is a single line of inconsistency compared to three other methods in the same file/module that already do it correctly.

### Recommendation
Validate `shop` in `Oauth.begin_auth` using `Utils::ShopValidator.sanitize!(shop)` (the same call already used in `client_credentials.rb` and `refresh_token.rb`) before it is passed to `auth_base_uri`, so the OAuth authorize redirect can only ever target `TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
1. Attacker sends `shop=attacker-controlled.example` (any arbitrary host) to the app's login route, which per the documented pattern calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: attacker_controlled_shop, redirect_path: "/auth/callback")`.
2. `begin_auth` returns `auth_route = "https://attacker-controlled.example/admin/oauth/authorize?client_id=<APP_CLIENT_ID>&scope=...&redirect_uri=https://app.example/auth/callback&state=<NONCE>&grant_options[]=..."` and a `SessionCookie` whose value is `<NONCE>` [11](#0-10) .
3. The host app sets the `<NONCE>` as the victim's session cookie and 307-redirects the victim's browser to the attacker's server, leaking `client_id`, `redirect_uri`, and `<NONCE>` to the attacker.
4. The attacker independently completes a real OAuth grant for a shop they control, obtaining a validly Shopify-HMAC-signed callback (`code`, `shop=attacker.myshopify.com`, `hmac`), then gets the victim to hit `/auth/callback?...&state=<NONCE>` (the same nonce still present as the victim's cookie).
5. `validate_auth_callback` passes state and HMAC checks (both are self-consistent for the attacker's shop) and completes the OAuth flow, binding the victim's app session to the attacker's shop/access token — forced OAuth completion / session fixation.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

class ShopifyAuthController < ApplicationController
  def login
    shop = request.headers["Shop"]

    # Builds the authorization URL route to redirect the user to
    auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")

    # Store the authorization cookie
    cookies[auth_response[:cookie].name] = {
      expires: auth_response[:cookie].expires,
      secure: true,
      http_only: true,
      value: auth_response[:cookie].value
    }

    # Redirect the user to "auth_response[:auth_route]" to allow user to grant the app permission
    # This will lead the user to the Shopify Authorization page
    head 307
    response.set_header("Location", auth_response[:auth_route])
  end
