### Title
Webhook shop-domain/topic/webhook-id headers are trusted for tenant routing while only the raw body is HMAC-verified - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then hands the *unauthenticated* `shop-domain`, `topic`, `webhook-id`, and `api-version` headers straight to the handler as trusted tenant-identifying metadata. This is the same class of bug as the reported issue: a value that is consumed as an identity/completeness signal (`global_cumulative_sum`) is never included in the check that is supposed to guarantee integrity (`assert_deferred_digest_complete`). Here, the "shop" field that downstream handler code treats as the source-of-truth tenant identifier is never part of the signed material the HMAC covers.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes and compares the HMAC purely over that signable string: [2](#0-1) 

`Registry.process` uses this single check as the entire authentication gate for the request, and then reads `request.shop`, `request.topic`, and `request.webhook_id` - all sourced from HTTP headers that were never part of the HMAC input - and forwards them to the app's handler as trusted values: [3](#0-2) 

`Request#shop`, `#topic`, and `#webhook_id` are all plain header reads with no cross-check against the HMAC-verified body: [4](#0-3) 

The identity equality that should hold is:
`shop_used_by_handler (request.shop, from header) == shop_that_the_HMAC_actually_authenticates`

But the HMAC authenticates only "this body+signature pair was produced with our `api_secret_key`" - it says nothing about which shop the payload is for. Since a Shopify app's `client_secret`/`api_secret_key` is shared across **all** shops that install the app (it is not per-shop), any actor who controls a shop that has legitimately installed the target app can capture one genuine webhook delivery for their own shop (valid `raw_body` + valid `hmac-sha256` for that body, since it is genuinely computed by Shopify with the shared app secret). That captured `(raw_body, hmac)` pair remains valid forever for `HmacValidator.validate`, regardless of which `shop-domain`, `topic`, or `webhook-id` header accompanies it, because those headers are excluded from `to_signable_string`.

### Impact Explanation
An attacker who runs their own shop with the target app installed can replay a self-obtained, HMAC-valid webhook body while substituting an arbitrary `shopify-shop-domain` header (a victim shop), an arbitrary `shopify-topic` header, and an arbitrary `shopify-webhook-id`. `Registry.process` will accept it as authentic (HMAC passes) and dispatch it to the registered handler tagged with the attacker-chosen `shop`/`topic`/`webhook_id`. Any host application that uses `WebhookMetadata.shop` to select which tenant's record to update (the documented, expected usage pattern for this gem) will act on forged tenant data, enabling cross-tenant state corruption/spoofing keyed off a value this gem presents as trustworthy but never authenticates. This crosses a tenant boundary using only the shared, unprivileged capability of "having one's own shop install the app" - no leaked credentials, access tokens, or `api_secret_key` disclosure required.

### Likelihood Explanation
Requires only that the attacker's own store has the target app installed (a normal, unprivileged action any internet user/merchant can take) and that they capture at least one webhook delivery to their own endpoint - both trivially satisfied by any app developer/tester or malicious merchant. No secret material needs to be extracted; the attacker uses their own legitimately-signed traffic and merely edits unauthenticated headers.

### Recommendation
Bind the tenant-identifying and routing fields into the HMAC-covered material, or otherwise cryptographically tie `shop`, `topic`, and `webhook_id` to the signature before trusting them, e.g. by including them in `to_signable_string`/`VerifiableQuery` (mirroring how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop`, `state`, `host`, etc.) rather than exposing them as independently-read, unauthenticated header accessors on `ShopifyAPI::Webhooks::Request`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and registers a webhook subscription for topic `orders/create`, receiving a genuine delivery: body `B`, header `shopify-hmac-sha256: H` (valid, since `H = HMAC-SHA256(api_secret_key, B)` and `api_secret_key` is shared across all installs of the app).
2. Attacker crafts a new HTTP POST to the target app's webhook endpoint using the same `raw_body: B` and `shopify-hmac-sha256: H`, but sets:
   - `shopify-shop-domain: victim-shop.myshopify.com`
   - `shopify-topic: orders/create` (or any registered topic)
   - `shopify-webhook-id: <arbitrary>`
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully (only presence of headers is checked, per lines 46-59).
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(B) == H`.
5. `handler.handle(data: WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...))` is invoked - the host application's handler now believes this authentic-body webhook belongs to `victim-shop.myshopify.com`, even though it was never sent by or for that shop. module ShopifyAPI

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

module ShopifyAPI
  module Utils
    module HmacValidator
      extend T::Sig

      class << self
        extend T::Sig

        sig { params(verifiable_query: VerifiableQuery).returns(T::Boolean) }
        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
