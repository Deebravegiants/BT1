### Title
Bad-debt socialization shrinks `assets` without burning vault shares, allowing the share/asset ratio to inflate toward a `uint128` overflow and permanently freeze deposits/redeems - (File: `mainnet/contracts/vault/v0-vault-usdc.clar`, and equivalently `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdh.clar`)

### Summary
Each Zest lending vault mints/burns its `zft` share token using a plain `totalShares/totalAssets` ratio with no floor or dampening. When a position defaults and `socialize-debt` is invoked, it directly decrements the vault's `assets` variable to absorb the loss, but it never burns any of the outstanding `zft` shares that represented that lost value. Repeated bad-debt events therefore compound the share/asset ratio upward without bound, exactly mirroring the Sentiment `SuperPool` bug in the referenced report, except here Clarity's `uint` is bounded to 128 bits (`MAX-U128`), a much smaller ceiling than Solidity's 256-bit `uint256`, making the overflow reachable far sooner.

### Finding Description
`convert-to-shares-preview` / `convert-to-assets-preview` compute the exchange rate as a raw ratio with no smoothing: [1](#0-0) 

`socialize-debt` is the vault-side hook the market calls to write off uncollateralized debt. It reduces `total-borrowed` and, critically, reduces the vault's `assets` variable to reflect the loss, while writing down `lindex` proportionally - but it never touches `total-supply` (the `zft` share supply): [2](#0-1) 

Since `total-assets` = `assets` + accrued interest, and `total-supply` is unaffected, each bad-debt socialization strictly increases `total-supply / total-assets`. `deposit` mints shares via `convert-to-shares-preview` (`mul-div-down amount ts ta`) and `redeem` computes payout via `convert-to-assets-preview` (`mul-div-down amount ta ts`): [3](#0-2) [4](#0-3) 

Because `mul-div-down`/`mul-div-up` compute `amount * ts` (or `* ta`) before dividing, and Clarity's `uint` is bounded by `MAX-U128` (`u340282366920938463463374607431768211455`, ~3.4e38): [5](#0-4) 

repeated write-downs of `assets` via `socialize-debt` (triggered from `liquidate` in the market contract when a position has no remaining collateral, per `bad-debt-socialized`/`socialize-debt-asset` in `v0-4-market.clar`) drive `ts/ta` up geometrically each time, just as demonstrated in the referenced Sentinel PoC. Once the ratio grows large enough that `amount * ts` (in `deposit`) or `amount * ta` (in `redeem`) exceeds `MAX-U128` for any economically meaningful `amount`, Clarity's arithmetic will trap/abort the transaction, permanently reverting `deposit` and `redeem` for that vault.

The market-side flow that drives this is the bad-debt socialization path in the liquidation function: [6](#0-5) 

The identity broken is: `total-assets(vault) / total-shares(vault)` should track redeemable value per share; instead, bad debt reduces the numerator (`assets`) without any corresponding reduction of `total-shares`, so the per-share backing is silently and repeatedly diluted in the wrong direction (ratio inflation) with no upper bound or corrective mechanism.

### Impact Explanation
Once the ratio is inflated enough (a handful of large, or many small, bad-debt liquidations against a given vault, which is plausible over the vault's lifetime given borrower assets can be volatile), all `deposit` and `redeem` calls on that vault begin reverting due to arithmetic overflow inside `convert-to-shares-preview`/`convert-to-assets-preview` (and the `accrue` function's treasury-fee minting path, which uses the same `mul-div-down ... (total-supply) (- ta-preview reserve-inc)` pattern). This permanently freezes all depositors' principal and unclaimed yield in that vault - no admin function exists to reset or rebase the ratio. This matches the "permanent freezing of funds" impact bucket.

### Likelihood Explanation
This requires the market's liquidation flow to hit the `no-collateral-left` / bad-debt-socialization branch multiple times (or with a large enough magnitude) against a single vault - the same precondition accepted as valid Medium severity in the referenced Sherlock judgment. Since Clarity's arithmetic ceiling (`u128`) is dramatically smaller than Solidity's `u256`, fewer/smaller bad-debt events are needed here to reach the overflow point, making the likelihood at least as high as in the original finding, if not higher.

### Recommendation
When socializing bad debt in the vault (`socialize-debt`), burn a proportional amount of outstanding `zft` shares (equal to the shares representing the written-down `assets`) so the `total-shares/total-assets` ratio is preserved rather than inflated, mirroring how `redeem` burns shares alongside asset withdrawal. Alternatively, clamp/normalize the ratio (e.g., periodically rebase using a scaling factor) so `mul-div-down`/`mul-div-up` operands stay well below `MAX-U128`, and add explicit bounds checks before minting/redeeming that revert with a descriptive error rather than silently trapping on overflow.

### Proof of Concept
Conceptual sequence (Clarity, per vault e.g. `v0-vault-usdc.clar`):
1. Vault starts with `assets = A0`, `total-supply = S0` (e.g., 1:1 from an initial deposit).
2. A borrower takes on debt from the paired market, collateral price drops, and `liquidate` in `v0-4-market.clar` hits the `no-collateral-left` branch, calling into `socialize-debt-asset` → vault's `socialize-debt`, which reduces `assets` by `principal-reduction` while `total-supply` (zft) stays at `S0`.
3. `total-assets/total-supply` ratio (`ts/ta`) has now increased. Repeat step 2 across several bad-debt events (or one very large one) so `ts/ta` grows geometrically, following the same math as the referenced Sentiment `SuperPool` PoC.
4. Eventually a normal-sized `deposit(amount, ...)` call computes `mul-div-down amount ts ta`; because `amount * ts` exceeds `MAX-U128`, the Clarity runtime aborts the transaction (analogous to Solidity's `Math: mulDiv overflow`).
5. From this point on, `deposit` and `redeem` on the vault permanently revert, freezing all existing depositors' funds and unclaimed yield in that vault with no recovery path.

Note: I could not fully trace the exact numeric thresholds or confirm whether an off-chain liquidation bot / initial `MINIMUM-LIQUIDITY` lock (referenced in the constants but whose usage I did not locate in the deposit/init flow within the available context) provides any additional mitigation; a Devin session with full repository access would be needed to verify the exact initialization flow and any additional safeguards not surfaced by the index.
