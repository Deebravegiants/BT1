### Title
User-centric signup path bypasses backend enrollment verification and locally-run fraud detection is a permanent no-op, allowing unauthorized/unverified signup success declarations - (File: src/plans/mod.rs)

### Summary
The Balancer report describes a class of bug where a critical authorization/state check (pool `finalized`) is missing, letting an unprivileged caller reach a code path that performs a sensitive state transition (fund transfer) that should have been gated. The analogous condition in `orb-core` is in `MasterPlan::do_signup`: when a QR-code-supplied flag `user_centric_signup` is set, the Orb determines signup **success locally** without ever calling the backend's authoritative `signup_post`/`signup_poll` enrollment check, and the only local gating check (`detect_fraud`) is hard-coded to always return `false` because "FOSS: WE HAVE DELETED ALL FRAUD CHECKS."

### Finding Description
In `do_signup`, after biometric capture and pipeline processing, the code computes `signup_reason` from `fraud_detected`: [1](#0-0) 

`fraud_detected` comes from `detect_fraud`, which — for any successful pipeline — unconditionally returns `Ok(false)`: [2](#0-1) 

This means `signup_reason` is always `SignupReason::Normal` whenever the biometric pipeline itself did not crash, regardless of duplicate-iris/liveness/fraud conditions that a real deployment would rely on the (deleted) fraud engine to catch. This is confirmed by an explicit comment in `fraud_check.rs`: [3](#0-2) 

Separately, when `user_centric_signup` (a boolean carried in the cryptographically-authenticated `UserData` returned from `backend::user_status::request`) is `true` and the orb has not been configured to `ignore_user_centric_signups`, the enrollment "success" status is derived **entirely locally** from `signup_reason`, bypassing the call to `enroll_user` (which is the only code path that contacts the backend's `signup_post`/`signup_poll` endpoints to get an authoritative accept/reject decision, including backend-side duplicate/fraud detection): [4](#0-3) 

Compare this to the `else` branch, which is the only branch that actually asks the backend to confirm enrollment via `enroll_user::Plan::run`, which polls `signup_poll` for a `Completed`/`success` response before declaring `Status::Success`: [5](#0-4) 

So for `user_centric_signup == true` orbs (a state that is decided by data returned to the orb during the user QR-code validation flow and travels forward as part of the current `QrCodes` state), a full biometric pipeline success is treated as "signup success" without ever confirming with the backend that the identity is unique, not previously enrolled, or not flagged, and without going through the backend fraud/duplicate check that `enroll_user::Plan::run` would otherwise perform. This is structurally the same defect as the Balancer bug: a required authoritative check (`finalized` state check → `signup_post`/`signup_poll` backend confirmation) is skipped on a reachable code path, and the local stand-in check (`_publicSwap` → `detect_fraud`) is a no-op/insufficient guard.

### Impact Explanation
Because `detect_fraud` never flags anything and the user-centric branch never calls the backend enrollment endpoint, an attacker who can influence pipeline outcome (e.g., replaying previously captured/duplicate biometrics, or exploiting any weakness in the biometric capture path) can have the Orb locally declare `SignupSuccess` and issue a personal-custody package upload for the associated `user_id`/identity commitment, without the backend's own duplicate-detection or fraud-detection systems ever getting a chance to reject the signup. This is a fraud/liveness-bypass and cross-signup state-bleed risk: the local, unprivileged-reachable signup flow can produce a "successful signup" state that was never verified/attested by the backend, potentially binding an identity commitment or issuing tier0/1/2 PCP data for an unauthorized or duplicate signup.

### Likelihood Explanation
- `detect_fraud`'s no-op behavior is unconditional in this build and requires no attacker action beyond a successful pipeline run — this significantly raises likelihood since the primary local defense is entirely absent.
- `user_centric_signup` is not attacker-arbitrary (it is bound into signed/verified `UserData` per `user_data.verify(user_data_hash)` in `src/backend/user_status.rs:166-179`), so triggering the vulnerable branch specifically requires either a user-centric-signup-configured app/backend flow or a compromise of that verification/trust boundary; this is a moderating factor on likelihood but the underlying no-op fraud check applies to every signup path (including the traditional `enroll_user` branch's `SignupReason` tagging that is sent to the backend), amplifying overall exposure.
- The condition can also occur legitimately in production whenever `user_centric_signup` mode is enabled and not overridden by `ignore_user_centric_signups`, meaning this is a normal, always-reachable code path rather than a rare edge case.

### Recommendation
- Never allow a local success determination to substitute for backend enrollment confirmation. Require `enroll_user`-style backend confirmation (`signup_post` + `signup_poll`) even in the `user_centric_signup` branch, or explicitly document/require that the backend independently performs full fraud/dedup checks before this code path can be trusted, and add that dependency verification into this code.
- Restore/replace the deleted fraud-check logic in `detect_fraud`/`fraud_check.rs`, or explicitly require `skip_fraud_checks` style flags to be disabled in production builds and ensure the "FOSS" no-op path cannot silently ship a security-relevant no-op into a production decision (rename/guard it so it is not compiled into `v2_x_x`+`stage`/prod feature combinations, or make its absence loudly fail if it's relied upon for a security decision).
- Treat this as a state-machine gap analogous to the Balancer "finalized" check: define explicit states (e.g., `PipelineSucceeded`, `BackendConfirmed`, `EnrollmentFinal`) and require every branch that reports `SignupSuccess` to pass through `BackendConfirmed`.

### Proof of Concept
Not directly executable without live backend/hardware access; the control-flow proof is the code path itself: with `user_centric_signup = true` and `ignore_user_centric_signups = false` (default in `Config::default()`, see `src/config.rs:436`), a successful biometric pipeline run leads to:
1. `detect_fraud` → always `Ok(false)` (`src/plans/mod.rs:1390-1406`, `src/plans/fraud_check.rs:10-12`)
2. `signup_reason = SignupReason::Normal`
3. `success = signup_reason == SignupReason::Normal` → `true`, computed purely locally at `src/plans/mod.rs:639-645`, with **no call** to `enroll_user`/`signup_post`/`signup_poll`. [6](#0-5)
