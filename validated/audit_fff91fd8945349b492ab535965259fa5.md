### Title
Truncating decimal-down conversion in `pallet-hyper-fungible-token::convert_to_balance` permanently burns dust on every cross-chain HFT/BridgeToken transfer to Substrate - (File: modules/pallets/hyper-fungible-token/src/impls.rs)

### Summary
`convert_to_balance` performs an unchecked integer division when scaling an incoming ERC20 amount (higher decimals, e.g. 18) down to the pallet's local asset decimals (e.g. 12). Any remainder below the scale factor is silently truncated. Because the corresponding EVM-side `HyperFungibleToken.send()` burns the *full* ERC20 amount from the sender before dispatch, while the destination pallet only mints/releases the *floor-divided* amount on `on_accept` (and equivalently on `on_timeout` refunds), any amount that is not an exact multiple of `10^(erc_decimals - local_decimals)` results in a permanent, unrecoverable loss of the truncated remainder for the user, with no accounting for or recovery of the dust.

### Finding Description
`convert_to_balance` in `modules/pallets/hyper-fungible-token/src/impls.rs` computes: [1](#0-0) 

This is invoked from the ISMP module's `on_accept` handler when a post request arrives from an EVM `HyperFungibleToken`/`BridgeToken` contract: [2](#0-1) 

and again in `on_timeout` when refunding the original sender: [3](#0-2) 

On the EVM side, `HyperFungibleToken.send()` (reachable by any unprivileged ERC20 holder) burns the caller's ERC20 balance for the *exact* `amount` requested before dispatching the cross-chain message — there is no rounding of the ERC20 amount down to a multiple of the destination's decimal granularity prior to burn. The pallet's `BridgeToken` contract documents that BRIDGE is 12 decimals on nexus while the ERC20 representation uses 18 decimals, i.e. the pallet scales by `10^6` in both directions: [4](#0-3) 

Because ERC20 balances on the EVM side are tracked at 18-decimal (wei) granularity, a holder can hold or send arbitrary amounts down to 1 wei — none of which are guaranteed to be a multiple of `10^6`. When such an amount is bridged to nexus, the full ERC20 amount is burned on the EVM side, but `convert_to_balance` floors the division, and the pallet mints/transfers only the truncated amount to the beneficiary. The difference (up to `10^(erc_decimals - local_decimals) - 1`, i.e. up to `999,999` wei = `0.999999` BRIDGE units per transfer in the 18→12 example) is not credited to anyone, not returned to the sender, and not tracked by any accounting mechanism — it is permanently lost. Because `pallet_account()` custodies escrowed native BRIDGE 1:1 with the ERC20 supply (per the escrow-model docstring on `BridgeToken`), the truncated remainder becomes escrow value that can never be released to any beneficiary, effectively a stranded/burned amount.

This is a structural analog of the reported `WithdrawRequest.amount` precision-loss bug: full value is debited (burned/escrowed) upstream while a smaller, floor-rounded value is credited downstream, with the delta permanently lost due to integer division truncation.

### Impact Explanation
Every unprivileged bridging transaction whose ERC20 amount is not an exact multiple of the decimal scale factor loses value up to `10^(erc_decimals - local_decimals) - 1` base units. While each individual loss may look like "dust," this reachable from any EVM `send()` call by any token holder, occurs on every mismatched transfer, and accumulates across high transaction volume — a systemic, protocol-wide loss of user funds with no recovery path (matching the report's "loss of Equity"/"accumulate rapidly" impact framing). It also creates a permanent supply/escrow imbalance: BRIDGE minted-vs-escrowed accounting on the EVM/nexus sides can drift because burned ERC20 supply does not match minted/released native supply.

### Likelihood Explanation
High likelihood: any user bridging BRIDGE (or any HFT-registered token with `erc_decimals > local_decimals`) from EVM to nexus with a non-round amount (which is the common case, since ERC20 amounts are freely chosen at wei granularity while the local asset is 6 decimal places coarser) triggers this truncation on every single transfer. No special privileges, timing, or attacker coordination are required — it is a routine user-triggered code path (`HyperFungibleToken.send()` → ISMP dispatch → `on_accept`/`convert_to_balance`).

### Recommendation
Enforce dust-free amounts at the point of burn on the EVM side: require `amount % (10 ** (erc_decimals - local_decimals)) == 0` before burning/dispatching (or round the amount down to the nearest representable unit *before* burning, refunding any truncated remainder to the sender instead of burning it). Alternatively, have `convert_to_balance` return the truncated remainder alongside the converted balance so the pallet can either reject transfers that don't cleanly convert, or credit the remainder back to the sender/beneficiary rather than silently discarding it.

### Proof of Concept
1. Register `BRIDGE` with `erc_decimals = 18` and `local_decimals (Decimals::get()) = 12`, matching the documented `BridgeToken` configuration.
2. On an EVM chain, a user holds `1_000_000_000_500` wei of BRIDGE (i.e., `1000.0000000005` tokens at 18 decimals) — not a multiple of `10^6`.
3. User calls `HyperFungibleToken.send()` with `amount = 1_000_000_000_500`; the ERC20 contract burns the full `1_000_000_000_500` wei from the sender: [5](#0-4) 
4. The pallet receives the post request and calls `convert_to_balance(1_000_000_000_500, 18, 12)`, which computes `1_000_000_000_500 / 10^6 = 1_000_000` (floor), discarding the `500` remainder: [6](#0-5) 
5. The beneficiary is minted/transferred `1_000_000` local units (equivalent to `1_000_000_000_000` wei), losing `500` wei worth of value that is neither returned to the sender nor credited anywhere — permanently stranded in/lost from the escrow.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
