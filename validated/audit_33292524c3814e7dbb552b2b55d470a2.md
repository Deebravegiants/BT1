### Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) identity fields are trusted by handlers without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by checking `Utils::HmacValidator.validate(request)` and then forwards `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` to the app's `WebhookHandler` inside a `WebhookMetadata` struct. The HMAC, however, is computed only over the raw request body, never over these header-derived identity fields, so the equality "HMAC-authenticated bytes == the bytes the handler trusts as the tenant identity" does not hold.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, and `to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) with no cryptographic binding to them: [2](#0-1) 

`Utils::HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the `hmac` from the (also header-derived, but not otherwise verified) `hmac-sha256` header: [3](#0-2) 

`Registry.process` accepts the request once the body's HMAC checks out, then builds `WebhookMetadata` directly from the unauthenticated `request.shop`/`request.topic`/`request.webhook_id`/`request.api_version` and passes it to the app's handler: [4](#0-3) [5](#0-4) 

Because the app's `client_secret` used to sign webhooks is shared across every shop that has the app installed (it is not per-shop), any merchant who has the app installed can legitimately receive a genuinely-HMAC-signed webhook for their own shop, capture the raw body and the `x-shopify-hmac-sha256` value, and then resend that exact `(body, hmac)` pair to the app's webhook endpoint while substituting a different value in `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`). `Utils::HmacValidator.validate` still succeeds because it only checks the body bytes against the secret; `Registry.process` never validates that the `shop` header actually corresponds to a shop entitled to send that payload. The forged `shop` value is handed to the handler as trusted `WebhookMetadata#shop`.

This breaks the required identity binding: `shop asserted in the unauthenticated header` should equal `shop the HMAC actually authenticates`, but the gem authenticates only the body, not the shop/topic/webhook-id metadata that callers use to route/attribute the event to a tenant.

### Impact Explanation
Any app built on top of `ShopifyAPI::Webhooks::Registry` that uses `WebhookMetadata#shop` (as documented/intended, see the field's presence in the struct and its use by `WebhookHandler#handle`) to look up the tenant, session, or access token to act on will process an attacker-controlled `shop` value paired with a genuinely-signed body from a different (attacker-controlled) shop. This is a cross-tenant confusion: a malicious merchant can make the app believe another arbitrary shop identifier sent a specific payload, potentially causing the app to perform actions, write data, or issue API calls scoped to a shop record that never actually sent this webhook. This matches the "cross-tenant access" class of impact.

### Likelihood Explanation
The prerequisites are minimal and available to any unprivileged internet user who can install the target app on their own store (a normal, permission-less action for a public/embedded app): capture one legitimately delivered webhook (body + `x-shopify-hmac-sha256`) for their own shop, then replay it to the app's registered webhook endpoint with a different `x-shopify-shop-domain` header. No access to `api_secret_key`, access tokens, or any privileged credential is required — the entire attack works because the identity headers are not part of the signed content.

### Recommendation
Bind the identity fields into the signed content, or otherwise cryptographically/authoritatively re-verify `shop` before trusting it:
- Include `shop`, `topic`, and `webhook_id` in the HMAC-signable string (this requires a change on Shopify's signing side, so as a library-side mitigation) or
- Have `Registry.process` cross-check `request.shop` against an expected/registered shop for the session/handler context rather than trusting the header verbatim, and document to consumers that `WebhookMetadata#shop` must not be used as the sole tenant identifier without additional verification (e.g., correlating with an existing, previously-established session for that shop).
- At minimum, reject requests where the raw body's shop domain (if embedded in the JSON payload, e.g., `myshopify_domain`) does not match the header-derived `shop`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, triggering a legitimate webhook delivery to the app's endpoint with a valid `x-shopify-hmac-sha256` computed over the JSON body using the app's `client_secret`.
2. Attacker captures the raw POST body `B` and header value `H = x-shopify-hmac-sha256`.
3. Attacker replays a POST to the same endpoint with the same body `B` and header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers and body (`lib/shopify_api/webhooks/request.rb`); `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` (`to_signable_string`) and succeeds because `B` and `H` are unmodified and genuinely matched.
5. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)` and invokes `handler.handle(data:)`, causing the app to process an event attributed to `victim-shop.myshopify.com` that `victim-shop.myshopify.com` never sent.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
