### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from unauthenticated HTTP headers [2](#0-1) . `HmacValidator.validate` only verifies the HMAC of `to_signable_string` (the body) against `Context.api_secret_key` [3](#0-2) . `Registry.process` accepts the request once this body-only HMAC check passes and then dispatches `request.shop` straight to the application's webhook handler [4](#0-3) .

### Finding Description
The identity binding that should hold is:
`shop header value == shop that produced/authorized the signed body`

This binding is never enforced. The HMAC only authenticates the byte content of `@raw_body`; it says nothing about which shop the header claims the event came from. Because a single app shares one `api_secret_key` (client secret) across every shop that installs it, the HMAC computed by Shopify for a webhook body from Shop A is bit-for-bit identical to what would be computed for the same body content from Shop B — the signature is a function of `(body, secret)` only, never `(shop, body, secret)`.

An attacker who controls their own shop installation of the app (a low-privilege, standard app-install relationship — not requiring any of the app's secrets) can:
1. Trigger a webhook delivery from their own shop with an attacker-chosen body (e.g., by creating/editing a resource that matches a webhook topic they control, or by simply capturing a delivery Shopify sends them). Shopify signs this body with the shared `client_secret`, producing a genuine, valid `X-Shopify-Hmac-SHA256` value for that exact body.
2. Replay that request payload and its valid HMAC to the app's webhook endpoint, but modify the `X-Shopify-Shop-Domain` header to name a different shop (e.g., a victim tenant using the same app).
3. `HmacValidator.validate` still returns `true`, because it only checks the body/HMAC pair, which the attacker captured unmodified.
4. `Registry.process` proceeds to call `handler.handle(data: WebhookMetadata.new(... shop: request.shop ...))` with the forged shop value [4](#0-3) .

Any host application that uses the `shop` field to select which tenant's `Session`/access token to load or to attribute data changes is therefore fed an unauthenticated, attacker-controlled tenant identifier that this gem itself asserts is HMAC-verified (the whole point of `Utils::HmacValidator.validate(request)` is to establish trust in the request, including the header data it exposes as part of the verified `Request` object).

### Impact Explanation
This breaks the shop-authenticated-vs-shop-acted-upon binding across tenant boundaries, matching the "Cross-tenant access" Critical-impact class: an attacker with only their own low-privilege shop install can cause the app to process forged webhook events attributed to an arbitrary victim shop, potentially triggering session lookups, data writes, or business logic keyed on `request.shop` for a tenant the attacker does not control and never authenticated as.

### Likelihood Explanation
Likelihood is high for any app that trusts `WebhookMetadata#shop` (the value this gem hands back after "validating" the webhook) to select the tenant context, since:
- No secret material is needed — only a working install on an attacker-owned shop, which is the normal barrier to entry for any public app.
- Capturing a self-generated, validly-signed body and modifying only headers is trivial (headers are not part of `to_signable_string`).
- The vulnerable code path (`Registry.process`) is the gem's own documented, first-class mechanism for handling webhooks.

### Recommendation
Include the shop domain (and ideally the topic and API version) inside the signed payload used for verification, or otherwise cryptographically or out-of-band bind the header-derived `shop` to the specific installation the delivery HMAC was generated for (e.g., verify the shop against the known set of shops with an active session/access token for this app before trusting `request.shop`, and document that consumers must not use `request.shop` as a sole tenant-selection key without additional verification). At minimum, update `to_signable_string` in `lib/shopify_api/webhooks/request.rb` so it incorporates the shop domain, and add a check in `Registry.process` that rejects/flags cross-tenant mismatches.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has the app installed there.
raw_body = '{"id":1,"note":"hi"}'
valid_hmac_from_attackers_own_shop = Base64.strict_encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)
# Same api_secret_key is shared across all shops using this app,
# so this HMAC is valid for the body regardless of the shop header.

forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac_from_attackers_own_shop,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # spoofed tenant
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Utils::HmacValidator.validate(request) # => true, HMAC only covers raw_body
ShopifyAPI::Webhooks::Registry.process(request)
# handler receives WebhookMetadata with shop: "victim-shop.myshopify.com"
# even though the HMAC was produced for the attacker's own shop delivery.
```
