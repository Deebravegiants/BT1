### Title
HostManager permanently locks any native token sent to it, with no rescue path - (File: evm/src/core/HostManager.sol)

### Summary
`HostManager` implements a payable `receive()` but has no function — governance-gated or otherwise — capable of transferring out its own native-token balance. Native tokens sent to the contract (accidentally, via a misconfigured integration, or via `params.host_manager` being used as a payment/beneficiary target) are permanently frozen.

### Finding Description
`HostManager.sol` declares: [1](#0-0) 
which accepts arbitrary native-token transfers from anyone. The contract's only value-moving logic is inside `onAccept`, where the `Withdraw` action calls `IHostManager(_params.host).withdraw(withdrawParams)`: [2](#0-1) 
`EvmHost.withdraw` explicitly disburses from `EvmHost`'s own balance (`address(this).balance`, i.e. the host contract), not `HostManager`'s: [3](#0-2) 
There is no code path in `HostManager` — no `OnAcceptActions` variant, no admin function — that calls `.call{value: ...}` or otherwise empties `address(this).balance` for the `HostManager` contract itself. Once native tokens land on `HostManager`, they are permanently stuck.

This is reachable by any unprivileged account, since `receive()` has no access control and the contract address is a real, on-chain, discoverable address (used as the `to` field target for cross-chain governance withdrawal messages and referenced as `params.host_manager` in the relayer fee-accounting flow).

### Impact Explanation
Any native token sent to `HostManager` (by mistake, by a naive integrator who confuses it with `EvmHost`, or through an operational error in a relayer/fee flow that targets the wrong contract) is permanently and irrecoverably locked — a straightforward loss-of-funds/freezing-of-funds condition with no mitigation available to governance, admin, or the sender.

### Likelihood Explanation
The likelihood of accidental transfers is non-trivial: the contract's own comment ("Do not send any tokens directly to this contract") signals developer awareness that misdirected transfers are a realistic occurrence, yet no recovery mechanism was implemented. `HostManager`'s address is also structurally similar in role/naming to `EvmHost` (which does support native rescue via governance `withdraw`), increasing the chance of confusion by relayers, users, or scripts across many deployed chains.

### Recommendation
Add a governance-gated (`restrict`/`onAccept`-routed) rescue function to `HostManager` that transfers out `address(this).balance` (and optionally arbitrary ERC-20 balances) to a specified beneficiary, mirroring the pattern already used in `EvmHost.withdraw` for its own funds.

### Proof of Concept
1. Any account sends native ETH directly to the deployed `HostManager` contract address (`receive()` accepts it unconditionally, line 86).
2. Inspect `HostManager`'s complete function surface (`init`, `onAccept`, `params`, `host`, `relayer`, `supportsInterface`) — none of them transfer `address(this).balance` anywhere.
3. `onAccept`'s only value-related action, `Withdraw`, calls `EvmHost.withdraw`, which operates strictly on `EvmHost`'s own balance, confirmed at `evm/src/core/EvmHost.sol` lines 651-660.
4. The ETH sent in step 1 remains locked in `HostManager` forever, with no admin, governance, or user recourse.
