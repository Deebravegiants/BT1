### Title
Webhook `shop` and `webhook_id` are not covered by the HMAC signature, allowing cross-tenant event forgery - (File: lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Utils::HmacValidator.validate` only verifies the HMAC over `request.to_signable_string`, which for `Webhooks::Request` is exactly `@raw_body`, and never includes the `shop-domain` or `webhook-id` headers. `Registry.process` then trusts `request.shop` and `request.webhook_id` verbatim when building the `WebhookMetadata` passed to the app's handler, so any attacker holding one validly-signed `(raw_body, hmac)` pair for the app (from their own shop) can replay it with arbitrary `shop-domain`/`webhook-id` headers and have it accepted as an event for any victim shop.

### Finding Description
The binding the API implicitly promises is:

`HmacValidator.validate(request) == true` implies `request.shop` and `request.webhook_id`, as delivered to the handler in `WebhookMetadata`, are the shop and webhook identifiers that Shopify actually signed for this event.

Tracing the code shows this binding does not hold:

- `Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `shop` and `webhook_id` are read straight from attacker-controllable HTTP headers with no cryptographic tie to the body: [2](#0-1) 
- `HmacValidator.validate_signature` recomputes the HMAC only over `verifiable_query.to_signable_string` (i.e. the raw body) and compares it to the `hmac-sha256` header, never touching `shop-domain` or `webhook-id`: [3](#0-2) 
- `Registry.process` raises only if the HMAC check fails, then constructs `WebhookMetadata` directly from `request.shop` and `request.webhook_id`, which the handler receives as if authenticated: [4](#0-3) 
- `WebhookMetadata` is a plain `T::Struct` with no additional validation of `shop`/`webhook_id` against the signed payload: [5](#0-4) 

Because the HMAC secret (`Context.api_secret_key`) is the app's single client secret shared across every shop that installs the app, any `(raw_body, hmac)` pair the attacker legitimately obtains for one topic (e.g. by subscribing their own dev-shop installation's access token to a `webhookSubscriptionCreate` pointing at a server they control) remains a valid signature regardless of which shop it is replayed against. The attacker then POSTs that identical `raw_body` and `hmac-sha256` value to the target app's real webhook endpoint, but with `shop-domain: victim-shop.myshopify.com` and `webhook-id: <attacker-chosen>`. `HmacValidator.validate` passes because it never inspected those headers, and `Registry.process` calls the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", webhook_id: <attacker-chosen>)`.

No existing guard closes this gap: `ShopValidator.sanitize!`, `state` comparisons, and JWT `aud` checks are unrelated code paths for OAuth/session-token flows and are never invoked in `Registry.process`; there is no Sorbet check that could enforce a semantic binding between header values and signed bytes.

### Impact Explanation
Any handler logic that trusts `data.shop` (e.g. to select which merchant's DB row to update) or `data.webhook_id` (e.g. for idempotency/deduplication keyed by `webhook_id` + `shop`) can be fed attacker-chosen values while still passing signature verification, letting one merchant's webhook traffic be relabeled as belonging to an arbitrary victim shop. This is repeatable for every captured `(raw_body, hmac)` pair and against any victim shop name the attacker chooses, since the shop identifier is just a header string with no server-side existence check performed by the gem. This matches the "cross-tenant access" Critical category, since one tenant's request can trigger event handling attributed to another tenant's data.

### Likelihood Explanation
The attacker only needs to be a legitimate (even free/dev-store) merchant who has installed the target app once, giving them an access token they can use to create a webhook subscription pointed at their own server, or simply observe traffic delivered to any endpoint they control. From there, forging headers on a replayed HTTP POST is trivial and requires no secrets, no TLS interception, and no privileged access — fully within the stated unprivileged-attacker threat model.

### Recommendation
Do not treat `request.shop` / `request.webhook_id` as authenticated identifiers derived from HMAC verification alone. At minimum, document (and ideally enforce in the gem) that host apps must independently verify `request.shop` against their own list of shops that currently have this specific webhook topic subscribed (e.g. cross-check against stored shop/session records) before trusting `WebhookMetadata.shop` for any per-tenant action, since Shopify's webhook HMAC scheme signs only the body. If feasible, `Registry.process` could optionally accept a caller-supplied set of expected/known shop domains to check `request.shop` against before invoking the handler.

### Proof of Concept
```ruby
# test/webhooks/registry_forgery_test.rb
require "test_helper"

class RegistryForgeryTest < Test::Unit::TestCase
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret",
      host_name: "app.com", api_version: "unstable", is_private: false,
      is_embedded: true, session_storage: nil)
    ShopifyAPI::Webhooks::Registry.clear
  end

  def test_hmac_valid_with_attacker_chosen_shop_and_webhook_id
    raw_body = '{"id":1}'
    hmac_bytes = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"),
      ShopifyAPI::Context.api_secret_key, raw_body)

    # This is the pair the attacker legitimately obtained from their own shop's
    # orders/create webhook.
    attacker_headers = {
      "x-shopify-topic" => "orders/create",
      "x-shopify-hmac-sha256" => Base64.encode64(hmac_bytes),
      "x-shopify-shop-domain" => "victim-shop.myshopify.com", # swapped
      "x-shopify-webhook-id" => "attacker-chosen-id",          # swapped
      "x-shopify-api-version" => "2024-01",
    }

    request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: attacker_headers)

    # Binding under test: HMAC validity must NOT be independent of shop/webhook_id.
    assert(ShopifyAPI::Utils::HmacValidator.validate(request))
    assert_equal("victim-shop.myshopify.com", request.shop)
    assert_equal("attacker-chosen-id", request.webhook_id)

    handled = nil
    handler = TestHelpers::FakeWebhookHandler.new(lambda { |data| handled = data })
    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "orders/create", path: "path", delivery_method: :http, handler: handler,
    )

    ShopifyAPI::Webhooks::Registry.process(request)

    assert_equal("victim-shop.myshopify.com", handled.shop)
    assert_equal("attacker-chosen-id", handled.webhook_id)
  end
end
```
