### Title
Premature reset of persistent upload-queue index causes silent overwrite/loss of pending biometric personal-custody packages - (File: `src/agents/data_uploader.rs`)

### Summary
The `Persistent` variant of the data-uploader's on-disk `Queue` assigns each personal-custody package (PCP) a monotonically increasing directory index `next_id` [1](#0-0) . In `commit()`, this counter is reset back to `0` whenever the number of in-flight uploads (`in_progress`) reaches zero, without verifying that the queue's own backlog of not-yet-popped, not-yet-uploaded entries is also empty [2](#0-1) . This is the same bug class as the reported "first deposits lost" issue: a counter is reset/initialized to a base value that does not account for already-reserved indices belonging to unprocessed entries, so a subsequent `push()` reuses an index still in use and silently overwrites the existing entry.

### Finding Description
Each tier of the data uploader (tier 1 / tier 2, `TIERS_COUNT = 2`) has its own `Queue`, either `Memory` or `Persistent` [1](#0-0) . For `Persistent` queues, `push()` writes the PCP to `path.join(next_id.to_string())` and then increments `next_id`; the id is also appended to the in-memory `queue: VecDeque<u64>` of pending entries [3](#0-2) . `pop()` removes an id from the front of `queue` and marks it in-flight by incrementing `in_progress` [4](#0-3) . `commit()` decrements `in_progress` and, critically, resets `next_id = 0` solely based on `in_progress == 0`:

```rust
Some(()) => {
    if *in_progress == 0 {
        *next_id = 0;
    }
}
``` [5](#0-4) 

This condition does not check whether `queue` (the deque of items that have been pushed/written to disk but not yet popped for upload) is empty. Because the main event loop only pops a single item per completed upload, and does so via a round-robin scan across tiers that `break`s after the first non-empty queue found rather than always refilling the tier whose slot just freed [6](#0-5) , a given tier's `in_progress` counter can drop to `0` while that same tier's `queue` deque still holds an un-popped, un-uploaded entry (e.g., because that entry was written while all `PARALLEL_UPLOAD_STREAMS` slots were occupied by other tiers, see the push handler at lines 137-153, and it hasn't been picked up by the round-robin yet). When this happens, `next_id` is reset to `0` even though a higher-indexed directory (e.g., `1`) still holds valid, not-yet-uploaded PCP data. A subsequent `push()` for that tier then reuses the recycled low indices and, once it reaches the still-pending index, calls `fs::create_dir_all` / `fs::write` on that same directory, overwriting the pending package's `meta.json`/`data.bin` on disk before it was ever uploaded [7](#0-6) .

### Impact Explanation
The overwritten package (`Pcp`) contains biometric personal-custody data — iris code images/data intended for backend upload as part of a completed signup, keyed by `signup_id` and `user_id` [8](#0-7) . If the pending package is overwritten before being uploaded, that signup's custody package is silently and permanently lost — it is neither uploaded nor retried, and no error is raised, since the code path treats this as a normal, successful push. This falls squarely into the biometric upload/retention category: a legitimate signup's biometric enrollment data can be irrecoverably dropped without any operator or user-visible failure indication.

### Likelihood Explanation
Triggering requires: (1) a `Persistent` queue mode (enabled only under certain configurations/feature paths, `#[allow(dead_code)]` on the variant suggests it may not be the default active path), (2) sustained throughput such that `PARALLEL_UPLOAD_STREAMS` (4) concurrent uploads are saturated by one tier while another tier's item is pushed without an available slot, and (3) that tier's `in_progress` counter subsequently drops to zero (via the round-robin pop favoring other tiers) while its own backlog is non-empty. This is a legitimate concurrency/ordering condition reachable purely through normal Orb operation (multiple signups queued for upload under network delay or backlog), not requiring any privileged, malicious-peer, or hardware-tampering access — consistent with an "unprivileged" reachable condition, though it depends on specific timing/load conditions that make it intermittent rather than trivially reproducible on every run.

### Recommendation
In `Queue::commit`, reset `next_id` to `0` only when both `in_progress == 0` AND `queue.is_empty()` (i.e., there is truly no outstanding work — nothing in flight and nothing pending on disk). Alternatively, avoid recycling `next_id` back to `0` altogether and instead let it monotonically increase for the lifetime of the process (matching the on-disk scan-based recovery already done in `Queue::new`, which computes `next_id` from the maximum existing directory name + 1) [9](#0-8) . This removes the possibility of a new `push()` reusing an index still associated with unprocessed, on-disk data.

### Proof of Concept
Conceptual reproduction (from code inspection, matching the reported bug class):
1. Configure/exercise the `Persistent` queue path for the data-uploader agent.
2. Drive tier 2 traffic to occupy all `PARALLEL_UPLOAD_STREAMS` (4) upload slots.
3. While busy, push two PCPs for tier 1 (`push()` writes them to directories `0` and `1`, appends both ids to `queue`, `next_id` becomes `2`); neither is popped because `uploaders.len() < PARALLEL_UPLOAD_STREAMS` is false at push time [10](#0-9) .
4. A tier-2 upload completes, freeing a slot; the round-robin loop pops tier 1's id `0` (queue now `[1]`, `in_progress = 1`) [11](#0-10) .
5. The upload for id `0` completes; `commit(0)` runs, `in_progress` becomes `0`, and — because the check only looks at `in_progress`, not `queue` — `next_id` is reset to `0`, even though `queue` still contains pending id `1` (directory `1` still has unuploaded data on disk) [2](#0-1) .
6. Two new tier-1 PCPs are pushed: the first writes to directory `0` (safe, since `0` was already removed by commit), `next_id` becomes `1`; the second writes to directory `1`, **overwriting** the still-pending, not-yet-uploaded package from step 3 [12](#0-11) .
7. That overwritten package's original biometric data is never uploaded to the backend and is unrecoverable.

    async fn push(&mut self, pcp: Pcp) {
        match self {
            Self::Memory { queue } => {
                queue.push_back(pcp);
            }
            Self::Persistent { path, queue, next_id, .. } => {
                let ssd_perform = ssd::perform_async(async {
                    let path = path.join(next_id.to_string());
                    let meta = serde_json::to_string(&pcp)?;
                    fs::create_dir_all(&path).await?;
                    fs::write(path.join("meta.json"), meta).await?;
                    fs::write(path.join("data.bin"), &pcp.data).await?;
                    Ok(())
                });
                match ssd_perform.await {
                    None => {
                        tracing::error!(
                            "Persistent queue is failed during push, switching to memory"
                        );
                        *self = Self::Memory { queue: vec![pcp].into() };
                    }
                    Some(()) => {
                        queue.push_back(*next_id);
                        *next_id = next_id.checked_add(1).expect("shouldn't grow so fast");
                    }
                }
            }
        }
    }
