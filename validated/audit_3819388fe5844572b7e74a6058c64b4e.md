### Title
Victim self-custody EmporiumStack (`signerAddress == address(0)`) forces every op into CASE 2, causing externally-created positions to be owned by the shared `Emporium` contract and stealable by any subsequent caller - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
When a victim builds an `EmporiumStack` with `stack.signerAddress == address(0)` (self-custody, no dedicated `HinkalWallet`), `verifyWallet` returns immediately without any signature check, and every operation unconditionally falls into "CASE 2: Stateless Interaction," where `op.endpoint.call{value: op.value}(op.callData)` executes with `msg.sender == address(Emporium)`. Any DeFi position (e.g. an NFT-based LP or lending position) whose ownership defaults to `msg.sender` is therefore owned by the single, shared `Emporium` contract rather than by the victim, and because `Emporium.runAction` is reachable by *any* unprivileged account that submits its own valid ZK proof, an attacker can submit a follow-up transaction whose own CASE-2 op calls `transferFrom`/`safeTransferFrom` on that same asset contract with `from = Emporium`, succeeding because `Emporium` itself is both the ERC721 owner and the `msg.sender` performing the transfer.

### Finding Description
The equality that should hold is: *"asset created by a victim's protocol call is owned by an address only the victim controls (their stealth address or their own dedicated `HinkalWallet`)."* This equality is broken whenever `stack.signerAddress == address(0)`:

- `verifyWallet` (contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:302-316) returns early for `signerAddress == address(0)`, skipping the EIP-712 signature check entirely — but this is by design for self-custody transactions, not a signature-forging bug.
- In `runAction` (contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:91-113), the branch condition `op.invokeWallet && stack.signerAddress != address(0)` means CASE 1 (`IHinkalWallet(stack.signerAddress).callHinkalWallet(...)`) is *unreachable* whenever `signerAddress == address(0)`, regardless of the value of `op.invokeWallet` that was included in the EIP-712 typed struct. Every op instead executes via `op.endpoint.call{value: op.value}(op.callData)` directly from the `Emporium` contract's own address.
- `Emporium.runAction` is gated only by `onlyAllowedRecipient`, i.e. `msg.sender == Hinkal` [1](#0-0) , reachable by any unprivileged account through `Hinkal.transact` → `_externalTransact` with a self-generated valid proof for the caller's own UTXOs [2](#0-1) . There is no check that binds who is allowed to call which `op.endpoint`/`op.callData` combination — it is entirely attacker/victim controlled `externalActionMetadata`.
- Consequently, when a protocol's position-creating function defaults its owner/recipient to `msg.sender` (a common pattern, e.g. `mint`/`open` functions that mint an NFT to the caller), that NFT/position ends up owned by `address(Emporium)` — a single contract shared by every Hinkal user, not by the victim's stealth address or a per-user `HinkalWallet`.
- No subsequent Hinkal invariant protects this asset: the UTXO/nullifier/tree system (`insertNullifiers`, `rootHashExists`, balance-diff checks in `Hinkal.transact`) only tracks `circomData.erc20TokenAddresses` balances, not arbitrary external-protocol state such as ERC721 ownership sitting on `Emporium`. `getBalancesForArray`/slippage checks never observe or constrain this NFT.
- An attacker (any unprivileged address able to deposit their own funds and generate their own proof) can now submit their own `Hinkal.transact` with a new `EmporiumStack` (also `signerAddress == address(0)` is not even required — CASE 2 for the attacker's own op is enough) whose `op.callData` calls `transferFrom(address(Emporium), attacker, tokenId)` (or the position-specific withdraw/close function) on the same asset contract. Since that call also originates with `msg.sender == address(Emporium)`, and `Emporium` is the actual owner of the asset, the transfer succeeds with no additional authorization needed.
- The `UnauthorizedWalletCall` guard only blocks the `callHinkalWallet`/`doSendToRelay` selectors; it does nothing to prevent arbitrary calls to arbitrary third-party asset contracts.

### Impact Explanation
This is direct theft of a victim's DeFi position/asset that was created through Hinkal — funds/positions that would otherwise belong to the victim end up permanently reachable and stealable by any other, unrelated user of the protocol. This matches "Critical - direct theft of shielded or in-flight user funds" since the position was created using the victim's own withdrawn/shielded balance and is fully drainable by an attacker with no special privilege, and the exploit is repeatable against any other user who uses the self-custody (`signerAddress == 0`) path for a position-creating call.

### Likelihood Explanation
- Preconditions: a victim must use the self-custody EmporiumStack path (`signerAddress == address(0)`) for an operation whose target protocol defaults ownership/recipient to `msg.sender`. This is a supported, first-class usage mode of `EmporiumStack` (not a misuse) since `verifyWallet` explicitly special-cases it.
- Attacker cost: one additional `Hinkal.transact` call with a self-generated proof over the attacker's own UTXOs (even a zero/negligible value transaction) and a crafted `EmporiumStack`/`op.callData` targeting the same external asset contract.
- No relayer, admin, or victim key is needed; the attack is fully reachable by an unprivileged actor as defined in scope.
- Repeatable against every victim who used this configuration and every asset type whose ownership model defaults to `msg.sender`.

### Recommendation
Do not allow `EmporiumOperation` calls to execute with `msg.sender == address(Emporium)` for self-custody (`signerAddress == address(0)`) flows when the operation can result in asset custody outside Hinkal's UTXO accounting. Options:
1. Require every self-custody position-creating operation to be routed through a per-transaction/per-user isolated proxy (e.g. a minimal, single-use `HinkalWallet`-like contract deployed deterministically from `originalSender`/stealth address) rather than executing directly from the shared `Emporium` address.
2. Alternatively, forbid CASE-2 execution paths whose `op.callData` targets functions that can leave persistent, transferable state (NFTs, positions) owned by `msg.sender`, and require an explicit recipient parameter verified on-chain to equal the victim's own stealth address / dedicated wallet, never `address(Emporium)`.
3. At minimum, disallow reentry into `Emporium.runAction`-callable operations from calling `transferFrom`/`safeTransferFrom`-style functions where `from == address(Emporium)` unless authorized by the original creator, similar to the existing `UnauthorizedWalletCall` selector guard, generalized to protect any asset held in `Emporium`'s name.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, and a mock "PositionManager" contract whose `mint()` function mints an ERC721 position NFT to `msg.sender`.
2. Victim flow: victim performs `Hinkal.transact` with `externalActionData` pointing at `Emporium`, `externalActionMetadata` = ABI-encoded `EmporiumStack{signerAddress: address(0), ops: [{endpoint: PositionManager, invokeWallet: true, callData: abi.encodeCall(PositionManager.mint, ())}]}`. Assert `PositionManager.ownerOf(tokenId) == address(Emporium)` (not the victim's stealth address, not a `HinkalWallet`).
3. Compare against a control run where `stack.signerAddress` = victim's `HinkalWallet` address with a valid EIP-712 signature over the same ops (CASE 1 path): assert `PositionManager.ownerOf(tokenId) == address(HinkalWallet)`, confirming the divergence between the two configurations.
4. Attacker flow: attacker (unrelated address, own funds/UTXOs, own valid proof) calls `Hinkal.transact` with an `EmporiumStack` whose op calls `PositionManager.transferFrom(address(Emporium), attacker, tokenId)`. Assert the call succeeds and `PositionManager.ownerOf(tokenId) == attacker`, proving theft of the victim's position with no signature, key, or privilege belonging to the victim.
