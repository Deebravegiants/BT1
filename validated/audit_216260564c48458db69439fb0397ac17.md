## Title
Webhook `shop` identity is taken from an unauthenticated HTTP header while the HMAC only signs the raw body, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that is handed to application webhook handlers from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature that `Utils::HmacValidator` verifies is computed over the raw request body only. The header carrying the tenant identity is never covered by the signature check, so anyone who can obtain one valid `(body, hmac)` pair signed with the app's shared `client_secret` can replay it with a different `shop-domain` header and have it accepted as an authentic webhook for an arbitrary shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight out of the (attacker-controlled, since it arrives over plain HTTP headers) `shopify-shop-domain` header, with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates the request using `HmacValidator.validate`, which checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` — i.e., only the body bytes — and then immediately forwards `request.shop` (the unauthenticated header) to the app's handler as trusted tenant identity: [3](#0-2) 

The HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is shared across every shop that has the app installed. Because the signature never covers `shop`, `topic`, or `webhook_id`, any party who has legitimately installed the app on their own store (an ordinary, unprivileged action) can capture a real, validly-signed webhook delivery for their own shop and replay it against the app's webhook endpoint with the `shop-domain` header rewritten to a different, victim shop. `HmacValidator.validate` still passes because it only re-computes the HMAC over the unchanged body, and the gem hands the forged `shop` value straight to `WebhookMetadata`: [4](#0-3) 

This breaks the identity binding `shop authenticated == shop the app acts on` — the shop that is cryptographically proven (the body/HMAC pair, tied only to the shared secret) is not equal to the shop value the library actually reports to the handler.

### Impact Explanation
Applications built on this gem's documented webhook API receive `WebhookMetadata#shop` as the trusted tenant identifier once `Utils::HmacValidator.validate` succeeds. Since that identifier is not part of what is signed, an attacker who is merely another merchant of the same app can forge webhook deliveries that are misattributed to a victim shop, producing cross-tenant data confusion/corruption (e.g., a forged `app/uninstalled`, `customers/data_request`, or order/inventory webhook processed as if it came from a different merchant). This matches the Critical "cross-tenant access" impact category, since the gem's own signature-verification primitive does not protect the very field (`shop`) applications rely on to isolate tenants.

### Likelihood Explanation
Exploitation requires no special privilege beyond installing the app on one's own shop (a normal, self-service action open to any internet user for public apps), capturing one legitimate webhook delivery, and replaying it with a modified header — no access to the app's `client_secret`, no TLS interception, and no social engineering needed. The `HmacValidator`/`Request` code path is exercised on every webhook the app processes, so likelihood is high wherever an app trusts `WebhookMetadata#shop` for tenant-scoped actions, which is the documented usage pattern.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed payload, or otherwise cryptographically verify that the `shop-domain` header matches the shop context under which the webhook subscription was created (e.g., cross-check against the shop that a stored, previously-registered `webhook_id`/subscription belongs to) before handing `WebhookMetadata` to the handler. At minimum, document prominently that `request.shop` is unauthenticated and must not be trusted as a tenant boundary without additional verification by the host app.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, obtaining valid webhook deliveries such as:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw body>`, body `B`.
2. Attacker recomputes nothing — they simply replay the same body `B` and same HMAC header, but change `x-shopify-shop-domain` to `victim.myshopify.com`, and POST it to the app's webhook endpoint.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (= raw body `B` only) using the app's shared `Context.api_secret_key`; validation succeeds because `B` and the secret are unchanged. [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"`, even though the victim shop never sent this webhook — the shop value is fully attacker-controlled.
