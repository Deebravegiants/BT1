### Title
Webhook HMAC only signs the request body, not the `shop`/`topic` identity headers - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` verifies the HMAC exclusively against `@raw_body`. The `shop-domain`, `topic`, `api-version`, and `webhook-id` values are read straight from unauthenticated HTTP headers and are never part of the HMAC-covered bytes. `Registry.process` trusts these header-derived values and passes them into `WebhookMetadata`, which host applications use to identify which tenant/shop the webhook belongs to.

### Finding Description
The identity binding that should hold is:
`HMAC-signed bytes == bytes used to determine which shop/topic this webhook is for`

Instead, the code implements:
`HMAC-signed bytes == raw_body only`, while `shop`, `topic`, `api_version`, and `webhook_id` come from headers that are excluded from the signable string. [1](#0-0) 

`Registry.process` validates the HMAC and then unconditionally trusts `request.shop`/`request.topic` from headers when building `WebhookMetadata`: [2](#0-1) 

`WebhookMetadata.shop` is the field host applications rely on to route/scoping per-tenant processing (e.g., looking up the session/store for that shop): [3](#0-2) 

Because the app's `client_secret` (the HMAC key) is the same for every shop that installs a given Shopify app, any merchant who installs the app receives genuine webhook deliveries for their own shop with a valid HMAC computed by Shopify over their own body. Nothing in this gem's verification stops that same requester from replaying the exact HTTP request to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header for an arbitrary victim shop domain — the HMAC still validates because it only covers the (unchanged) body.

### Impact Explanation
This breaks the cross-tenant boundary the gem is supposed to enforce for webhook processing: a request whose "shop" identity is attacker-controlled and unauthenticated is delivered to the app's handler as if Shopify vouched for the `(shop, body)` pairing. Depending on how the host app implements its `WebhookHandler#handle`, this can result in state changes, deletions, or data writes attributed to/executed against a victim shop chosen by the attacker (cross-tenant access), satisfying the Critical impact bar for cross-tenant access.

### Likelihood Explanation
Exploitability requires only that the attacker be able to install the target app on any shop they control (a normal, unprivileged action available to any merchant) and be able to send arbitrary HTTP requests to the app's public webhook endpoint — no leaked secrets, tokens, or elevated privileges are required. This is a realistic, moderate-likelihood scenario for any multi-tenant Shopify app built on this gem.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signable string, or otherwise cryptographically bind them to the body before trusting them in `WebhookMetadata`, so a valid HMAC can only ever be presented together with the exact shop/topic Shopify originally signed for.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, receiving a legitimately signed webhook (e.g., `orders/create`) with header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` and a valid `X-Shopify-Hmac-Sha256` computed over the JSON body using the app's shared `client_secret`.
2. Attacker replays the identical HTTP request to the app's webhook endpoint but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and/or the topic header), leaving body and HMAC header untouched.
3. `ShopifyAPI::Webhooks::Request#hmac`/`#to_signable_string` only look at the (unchanged) body and headers unrelated to `shop`, so `Utils::HmacValidator.validate` returns `true`.
4. `Registry.process` builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and invokes the host app's handler, which processes the request as if it legitimately originated from the victim shop. [4](#0-3) [5](#0-4)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
