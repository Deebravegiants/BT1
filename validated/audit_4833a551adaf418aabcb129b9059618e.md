### Title
Accumulated `need_take_pnl_pc`/`need_take_pnl_coin` can exceed live vault balances, causing permanent `CheckedSubOverflow` denial-of-service on swap/deposit/withdraw - (File: `program/src/math.rs`)

### Summary
The external report's root cause is a checked subtraction (`size.sub(_curStake)`) that reverts once an accumulator (`_curStake`) legitimately grows past a fixed threshold (`size`), permanently bricking all future contributions. Raydium AMM has an analogous accumulator/threshold subtraction pattern in `Calculator::calc_total_without_take_pnl_no_orderbook`, which is invoked on every swap/deposit/withdraw path to compute the pool's real reserves net of unswept PnL.

### Finding Description
`Calculator::calc_total_without_take_pnl_no_orderbook` computes the tradable reserves by subtracting the accumulated-but-unswept PnL counters (`need_take_pnl_pc`, `need_take_pnl_coin`) from the raw vault balances: [1](#0-0) 

These counters are monotonically incremented inside `calc_take_pnl` every time a deposit or withdrawal triggers a PnL-taking event (when `pool_pc_amount * pool_coin_amount >= calc_pc_amount * calc_coin_amount`): [2](#0-1) 

`need_take_pnl_pc`/`need_take_pnl_coin` are only ever decreased by an explicit, separate PnL-collection instruction; they are not automatically kept below the actual vault balance by any invariant check in the deposit/withdraw code that calls `calc_take_pnl` and then updates `target_orders.calc_pnl_x`/`calc_pnl_y`: [3](#0-2) [4](#0-3) 

Because `calc_total_without_take_pnl_no_orderbook` is the entry point used to derive the pool's tradable reserves for every swap (and for deposit/withdraw pricing), if `need_take_pnl_pc` or `need_take_pnl_coin` is ever equal to or greater than the corresponding vault's raw token balance, the `checked_sub` returns `None` and the call bubbles up `AmmError::CheckedSubOverflow`: [5](#0-4) 

This is structurally identical to the reported bug class: an accumulator that is expected to stay strictly below a bound, subtracted via a hard-reverting operation, with no fallback/overload path once the bound is crossed — except here the impact is on the AMM's core swap/deposit/withdraw path rather than a dispute crowdsourcer.

### Impact Explanation
If `need_take_pnl_pc`/`need_take_pnl_coin` reaches or exceeds the live vault balance (e.g., through successive withdrawals draining the vault toward the outstanding PnL watermark, or PnL accruing faster than the vault balance due to repeated deposit/withdraw price-divergence events before an admin sweeps PnL out), every subsequent call to `calc_total_without_take_pnl_no_orderbook` — and therefore every swap, deposit, and withdraw depending on it — reverts. This permanently freezes the pool for all users, halting the ability to swap or withdraw remaining LP funds through the normal instruction path, which is a permanent freezing-of-funds condition (High impact) analogous to the disclosed report.

### Likelihood Explanation
Reaching this state requires the PnL accounting invariant (`need_take_pnl_{pc,coin} < vault balance`) to be violated purely through normal, permissionless interactions (swap/deposit/withdraw), without any privileged action. I was not able to fully verify within the available exploration whether the AMM's PnL math (`calc_take_pnl`, `calc_pnl_x`/`calc_pnl_y` bookkeeping) is unconditionally sound enough to prevent this drift under adversarial sequences of deposits/withdrawals/swaps at extreme ratios or with repeated small dust operations — this would require deeper arithmetic analysis of `calc_take_pnl`'s use of `x2_power.integer_sqrt()` and the `pnl_numerator`/`pnl_denominator` fee split across many iterations, which I could not complete with the remaining tool budget. Given this uncertainty, I present this as a credible but not fully proven analog.

### Recommendation
Replace the unconditional `checked_sub`/`.ok_or(CheckedSubOverflow)` calls in `calc_total_without_take_pnl_no_orderbook` with a saturating computation and clamp the PnL counters (`need_take_pnl_pc`/`need_take_pnl_coin`) so that they can never be recorded above the corresponding vault balance in `calc_take_pnl`. Add either a runtime invariant check when incrementing the counters, or a defensive `saturating_sub`/min-clamp at read time, so that a full pool balance is never irrecoverably locked out of the swap/deposit/withdraw code paths once PnL bookkeeping exceeds actual custody.

### Proof of Concept
Not independently reproduced; a concrete PoC would need to demonstrate a sequence of permissionless deposit/withdraw/swap instructions that drives `amm.state_data.need_take_pnl_pc` (or `_coin`) to equal or exceed the corresponding vault's real balance, at which point any subsequent `process_swap_base_in`/`process_swap_base_out`/`process_deposit`/`process_withdraw` call that reaches `Calculator::calc_total_without_take_pnl_no_orderbook` [1](#0-0)  would revert with `AmmError::CheckedSubOverflow`, permanently freezing the pool.

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
