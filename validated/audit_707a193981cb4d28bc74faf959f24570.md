Based on my investigation, I found a concrete analog in the webhook processing path.

### Title
Webhook shop-domain header is not covered by HMAC, enabling cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, so the HMAC verified in `Registry.process` binds solely to the body bytes. The `shop` field that the gem hands to the app's webhook handler as the tenant identifier is read straight from the `shopify-shop-domain` header, which is never included in the signed material.

### Finding Description
`Request#to_signable_string` is defined as just `@raw_body` [1](#0-0) , and `shop` is parsed from an unauthenticated header with no cryptographic binding to the signature: `T.cast(shopify_header("shop-domain"), String)` [2](#0-1) . `Registry.process` validates only `Utils::HmacValidator.validate(request)`, which calls `to_signable_string` (the body) — it never validates `shop` — and then forwards `request.shop` straight into `WebhookMetadata` passed to the app's handler [3](#0-2) . `HmacValidator.validate_signature` computes the HMAC purely over `verifiable_query.to_signable_string` [4](#0-3) .

This breaks the identity binding `shop_verified_by_signature == shop_used_for_tenant_identification`: the signature only proves "this body was signed with the app's shared `api_secret_key`" — it says nothing about which shop the body belongs to. Since the app's `api_secret_key` is shared across *all* shops/tenants that install the app (it is not shop-specific), any unprivileged user who installs the app on their own shop legitimately receives a genuine `(body, hmac)` pair from Shopify. That same attacker can then POST the identical body/hmac to the app's webhook endpoint while substituting `shopify-shop-domain` (or `x-shopify-shop-domain`) with a victim shop's domain. `HmacValidator.validate` still returns true (only body is checked), and the handler is invoked with `WebhookMetadata#shop` set to the spoofed victim domain — the app has no signal that this is a lie, since the docs explicitly instruct handlers to trust `data.shop` for tenant identification (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [5](#0-4) .

By contrast, the OAuth callback path in this same gem does this correctly: `AuthQuery#to_signable_string` includes `shop` (along with `code`, `host`, `state`, `timestamp`) in the signed payload [6](#0-5) , so `shop` cannot be swapped post-signature there. The webhook path lacks this same protection for the `shop` field.

### Impact Explanation
This allows cross-tenant confusion: an attacker-controlled shop can cause the host application to process webhook data while believing it originated from an arbitrary victim shop domain. Depending on how the host app's handler uses `data.shop` (e.g., to look up that shop's session/access token and perform side effects, write to the wrong tenant's records, or trigger app logic keyed by tenant), this can lead to cross-tenant data corruption or actions being attributed to the wrong merchant — squarely in the "cross-tenant access" impact category, since the gem provides no way for the handler to know the `shop` value is untrustworthy.

### Likelihood Explanation
Any user can sign up for a Shopify development/trial store and install a public app to legitimately receive genuine `(body, hmac)` webhook pairs signed with the app's shared secret, then replay them against the app's webhook endpoint with a forged shop header — no access token, `client_secret`, or privileged access is required, only the ability to install the app once on a store the attacker controls.

### Recommendation
Include the `shop` (and ideally `topic`) header values in the HMAC-signed material for webhooks, or otherwise cryptographically bind them to the body signature, so `Registry.process` can reject requests where the claimed shop was not the one for which the body was actually signed. At minimum, document prominently that `data.shop` from `WebhookMetadata` is not authenticated by the HMAC and must be cross-checked by the host application against a known/installed shop list before being trusted for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a store they own) and legitimately receives a webhook, e.g. `orders/create`, with headers `x-shopify-hmac-sha256: <validHmac>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, and some JSON body `B`.
2. Attacker resends the exact same body `B` and the exact same `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (== `B`) using the app's `api_secret_key` — this matches, since `B` and its HMAC are unchanged [7](#0-6) .
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, and the host app processes/acts on data it believes came from `victim-shop.myshopify.com`, even though it was fabricated by the attacker.
