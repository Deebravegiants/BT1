### Title
Webhook Shop/Topic Identity Confusion via Unauthenticated Headers Not Covered by HMAC - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable string from the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers that are never included in the HMAC computation. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then unconditionally trusts these header-derived fields when dispatching to the handler, breaking the binding "shop authenticated == shop the HMAC covers."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from the (attacker-controllable) request headers, with no cryptographic tie to the HMAC: [2](#0-1) 

`HmacValidator.validate` only recomputes the HMAC over `verifiable_query.to_signable_string` (the raw body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` relies on this validation, then immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` when building the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because the HMAC is only a function of the body, any request whose body+HMAC pair was legitimately generated by Shopify for one shop (e.g., an attacker's own store, on which the attacker can install the target app and receive real webhooks addressed to themselves) remains valid when replayed with a different `shop-domain`, `topic`, or `webhook-id` header. The equality the library should enforce — "shop bound in the verified signature == shop attributed to the event" — is never checked; only "HMAC(body) is valid for *some* shop" is checked.

### Impact Explanation
An app built on this gem that keys per-shop session/config lookup or authorization decisions off `WebhookMetadata#shop` (as the library's own `Registry.process` passes through unchanged) can be made to process a webhook body under the identity of a different (victim) shop than the one that actually produced it, since the shop header is never bound to the signature. This is a cross-tenant identity confusion at the point where the gem hands verified-but-mislabeled data to the host application, matching the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be able to legitimately receive at least one real webhook from Shopify (trivially achievable by installing the target app on any store the attacker controls, including a free development store) and then replay that exact body/HMAC pair to the app's webhook endpoint with modified `shop-domain`/`topic`/`webhook-id` headers. No access to `api_secret_key`, access tokens, or other credentials is required, and no interaction with a victim is needed — only crafting a raw HTTP POST, which is well within reach of an unprivileged internet user.

### Recommendation
Bind the shop/topic/webhook identity fields into the HMAC-verified data (e.g., derive `to_signable_string` from the header set plus body, or otherwise cryptographically bind the headers to the payload before dispatch), so verification failure results whenever any of these metadata fields is altered independently of the body.

### Proof of Concept
1. Install the target app on an attacker-controlled store `attacker.myshopify.com` and capture a legitimate webhook delivery (raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC(api_secret_key, B)`).
2. Replay an HTTP POST to the target app's webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim.myshopify.com` (and/or a different `x-shopify-topic`/`x-shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(api_secret_key, B) == H` — this succeeds because `B` and `H` are unmodified.
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-supplied data under the victim shop's identity.

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
