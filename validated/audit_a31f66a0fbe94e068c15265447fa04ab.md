## Finding: Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing

### Title
Webhook shop attribution is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header, while the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body. Any actor who can obtain one validly-signed webhook payload (e.g. by triggering a webhook on their own installed shop) can replay that same body/HMAC pair while swapping the `shop-domain` header to a different shop, and `ShopifyAPI::Webhooks::Registry.process` will accept it as valid and hand the payload to the app's handler attributed to the attacker-chosen shop.

### Finding Description
`HmacValidator.validate` verifies the signature by calling `verifiable_query.to_signable_string` and comparing it against the HMAC header: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw body — it excludes every header, including `shop`: [2](#0-1) [3](#0-2) 

`Registry.process` validates only this body-based HMAC and then dispatches the handler using `request.shop`, which is read straight from the unauthenticated header: [4](#0-3) 

This is the same identity-binding break described in the report's bug class: the byte range that is cryptographically verified (the JSON body) is not the same byte range that determines the tenant the data is attributed to (the `shop-domain` header). A merchant who has legitimately installed the app on their own store can generate a validly HMAC-signed webhook for that store (e.g. by updating a product), capture the raw body + `x-shopify-hmac-sha256` value, and then submit a forged HTTP request to the app's webhook endpoint with the same body/HMAC but an arbitrary `x-shopify-shop-domain` header value pointing at a different installed shop. `HmacValidator.validate` still succeeds because it only checks the body against the secret, and `Registry.process` will call the app's handler with `WebhookMetadata(shop: <attacker-chosen shop>, body: <attacker's own data>)`.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: the shop that is cryptographically authenticated (implicitly, via body/secret) and the shop attributed to the processed data are not the same identity. Depending on how the consuming app persists webhook data keyed by `shop`, this can let one tenant inject or overwrite data attributed to another tenant — a cross-tenant access issue.

### Likelihood Explanation
The prerequisite is only a legitimate (even free/trial) install of the target app on an attacker-controlled shop, which triggers webhooks with valid Shopify-issued HMACs. No possession of `api_secret_key`, access tokens, or any privileged credential is required — the attacker simply replays a legitimately-obtained signed body with a modified header field that the gem never binds to the signature.

### Recommendation
Bind the `shop-domain` header into the signed material verified for webhooks, or independently verify that the `shop-domain` header corresponds to a shop the app has installed/tracks a valid session for before dispatching to handlers. At minimum, `Request#to_signable_string` (or the validation path in `Registry.process`) should incorporate the shop domain so that mutating that header invalidates the signature, matching how Shopify's own webhook verification is documented to be scoped to a specific shop.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger any webhook topic the app subscribes to (e.g. `products/update`).
2. Capture the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent for that webhook.
3. Replay the request to the app's webhook endpoint, keeping the body and HMAC header identical, but replace `x-shopify-shop-domain` with `victim.myshopify.com`.
4. `HmacValidator.validate` (checking only the body) succeeds; `Registry.process` invokes the registered handler with `WebhookMetadata(shop: "victim.myshopify.com", body: <attacker's body>)`, causing the app to process attacker-controlled data as if it originated from the victim shop.
