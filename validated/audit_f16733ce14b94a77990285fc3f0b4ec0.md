### Title
Webhook `shop-domain` header is trusted for tenant identity but is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity using only the raw request body, then dispatches the handler using the `shop` value taken from the unauthenticated `X-Shopify-Shop-Domain` header. Because the tenant-identifying field is not part of the HMAC-covered data, an attacker can produce a request whose body+HMAC pair is valid (for their own shop/app installation) but whose `shop` claim points at a different shop, causing the receiving app to process attacker-controlled webhook data under a victim shop's identity.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC exclusively over `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` values are all read straight from HTTP headers, which are entirely outside the HMAC's scope: [2](#0-1) 

`HmacValidator.validate` only ever checks the signable string (body) against the secret; it never incorporates the headers: [3](#0-2) 

`Registry.process` performs the HMAC check and then immediately trusts `request.shop` as the tenant identifier passed to the app's handler: [4](#0-3) 

The library's own documentation and `WebhookMetadata` struct establish `shop` as the authoritative tenant identity handed to app code (used for tenant-scoped job dispatch, e.g. `shop_domain: data.shop`): [5](#0-4) [6](#0-5) 

The broken identity binding, stated as an equality that the gem fails to enforce:
`shop authenticated by HMAC` (i.e., "the shop whose secret produced this signature over this body") ≠ `shop used as session/tenant key` (`request.shop`, read from an unauthenticated header). The gem verifies bytes of the body, then parses tenant identity from bytes (headers) it never verified.

### Impact Explanation
Any actor able to install the app on a shop they control (a normal, unprivileged action any merchant/developer can perform) can capture a legitimately-signed webhook body+HMAC pair for their own shop, then replay it to the app's webhook endpoint with `X-Shopify-Shop-Domain` swapped to a victim shop's domain. Because the gem's `process` method only verifies the body and never binds the header-derived `shop` to the HMAC, the forged request passes verification and the app's handler executes with `data.shop` set to the victim's shop domain. Any app that uses `data.shop` from `WebhookMetadata` to select which tenant's session/data record to update (as the gem's own documented usage pattern suggests) is exposed to a cross-tenant write/read — this maps to the Critical "cross-tenant access" impact category, entirely within logic the gem itself controls (the HMAC scope and the trust placed on `request.shop` by `Registry.process`).

### Likelihood Explanation
High feasibility: obtaining a valid HMAC for a self-controlled shop requires no privileged access — installing a test/development app and receiving a real webhook is standard, unprivileged usage. Forging the `X-Shopify-Shop-Domain` header on the replayed HTTP POST requires only basic HTTP tooling. The vulnerability is triggered purely by calling `ShopifyAPI::Webhooks::Registry.process` as documented; no misuse or divergence from the documented API is needed by the host application.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) claim into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived shop to the specific webhook subscription that produced the body (e.g., look up the webhook by its Shopify-issued `webhook_id`/subscription and cross-check the header `shop` against the shop the subscription belongs to, rather than trusting the header directly). At minimum, document prominently that `data.shop` from `WebhookMetadata` is unauthenticated and must not be used as a tenant key without independent verification (e.g., confirming an existing active session/installation for that shop before trusting webhook content tied to it).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets Shopify deliver a real webhook (e.g., `orders/create`) to the app's endpoint, capturing the raw body `B` and the resulting `X-Shopify-Hmac-Sha256` header value `H` (valid because `H = HMAC-SHA256(client_secret, B)`, and `client_secret` is the same shared app secret for all shops).
2. Attacker crafts a new HTTP POST to the same webhook endpoint with:
 - Body: `B` (unchanged, or a body they still control for their shop)
 - Headers: `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Topic: orders/create`, `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
3. `Webhooks::Request.new` parses these headers, and `Registry.process` calls `Utils::HmacValidator.validate`, which recomputes HMAC over `B` only — succeeds, since `B` and secret are unchanged. [7](#0-6) 
4. The handler is invoked with `WebhookMetadata` where `shop == "victim-shop.myshopify.com"`, even though the payload/HMAC was never produced by or for that shop, letting the app record/process attacker-controlled webhook content as if it belonged to the victim shop.
