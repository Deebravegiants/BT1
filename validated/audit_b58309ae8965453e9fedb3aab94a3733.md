### Title
Webhook shop-domain header is trusted as tenant identity but is excluded from the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) authenticates the JSON body alone. `request.shop` (the `X-Shopify-Shop-Domain` / `shopify-shop-domain` header) is never part of the signed material, yet `Registry.process` forwards it unchanged as the tenant identifier to the app's handler via `WebhookMetadata.new(... shop: request.shop ...)`. The binding the app relies on — "the `shop` value the handler trusts equals the shop that actually generated this body" — is not enforced by this gem.

### Finding Description [1](#0-0) 

`hmac`, `to_signable_string`, and `shop` are all derived independently from headers/body, but only `@raw_body` feeds the signature: [2](#0-1) 

`HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header value using `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` gates only on this body-only HMAC, then dispatches using `request.shop` as the trusted tenant identity, with no independent check that `shop` corresponds to the body that was actually signed: [4](#0-3) 

The identity binding that should hold is:
`HMAC-authenticated data == data the handler attributes to shop`
but in this implementation the equation actually enforced is only:
`HMAC-authenticated data == raw_body`
while `shop` (the value used for per-tenant routing/lookup) is carried outside that boundary. This is structurally the same class of bug as the report's "field acted on but not covered by the HMAC/binding" — the multisender bridged funds using a peer/receiver value that was never bound to the verified message; here, the webhook handler attributes verified body content to a shop value that was never bound to that body by the signature.

Because any Shopify merchant can install the app on their own store (an unprivileged action requiring no special credential), they can generate arbitrary bodies with genuinely valid HMACs for their own shop's webhooks. Nothing in this gem prevents replaying that same `(raw_body, hmac)` pair to the app's webhook endpoint with a different `X-Shopify-Shop-Domain` header naming a different, victim merchant. `HmacValidator.validate` will still succeed (it only checks the body), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the (attacker-supplied) body belongs to the victim shop.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` (as the gem's own API encourages — it is the only shop identifier `Registry.process` supplies to handlers) to look up/update per-tenant records, this allows an attacker (an unprivileged merchant with the app installed on their own store, no stolen credentials required) to inject attacker-controlled data into another tenant's records — a cross-tenant data confusion/injection primitive. This falls under the accepted "cross-tenant access" impact category, since it lets one tenant's forged event be attributed to and processed under a different tenant's identity.

### Likelihood Explanation
Low-to-medium: it requires the attacker to install the target app on their own shop (trivial, unprivileged) to obtain a genuinely-signed body/HMAC pair for arbitrary content they choose (e.g., an `orders/create` payload with attacker-chosen fields), then replay it against the public webhook endpoint with a spoofed `shop` header. It does not require the `api_secret_key`, a stolen access token, or any privileged account — only the ability to run the flow through a normal merchant install, which is available to any internet user.

### Recommendation
Bind `shop` into the authenticated material, or otherwise verify it independently before trusting it:
- Have `Request#to_signable_string` (or a new signature scope) incorporate the `shop` header alongside the body, if that is compatible with Shopify's webhook signing (Shopify itself only signs the body, so this may require the gem to separately verify `shop` against the topic/registration source, e.g., cross-check against a known/expected shop, or require the host app to pass the expected shop explicitly to `Registry.process` and reject mismatches).
- At minimum, update documentation/API to make explicit that `request.shop`/`WebhookMetadata#shop` is **not** authenticated by `HmacValidator.validate`, and that host apps must not use it as a sole tenant-identity input without additional validation (e.g. cross-referencing against the shop that installed/registered the specific webhook subscription).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, completing normal OAuth (no special privileges beyond a free merchant account).
2. Attacker triggers a webhook (e.g. `orders/create`) with a body they fully control content-wise (order fields, customer info, etc., depending on topic). Shopify signs and delivers:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid HMAC over raw_body>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   Body: <attacker-chosen JSON, still a legitimate Shopify payload for attacker's own shop>
   ```
3. Attacker replays the identical `Body` and `X-Shopify-Hmac-Sha256` value to the same webhook endpoint, but rewrites:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Registry.process` computes:
   ```ruby
   Utils::HmacValidator.validate(request) # => true, since HMAC only covers @raw_body
   ``` [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, and — if it uses `shop` to route/update per-tenant state — processes attacker data under the victim's tenant context.

**Uncertainty note**: I could not directly inspect an app-level webhook handler implementation in this repo (host apps implement `WebhookHandler#handle` themselves), so the concrete data-corruption outcome depends on how a consuming app uses `WebhookMetadata#shop`. The gem's own code, however, confirms the `shop` value is passed through unauthenticated relative to the HMAC, matching the report's identified bug class.
