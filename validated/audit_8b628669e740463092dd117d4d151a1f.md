### Title
Vetoing the latest state commitment resets the height floor to a hardcoded `1` instead of the true previous height, allowing re-acceptance of stale/lower state commitments - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.deleteStateMachineCommitmentInternal` resets `_latestStateMachineHeight[stateMachineId]` to the hardcoded value `1` when the vetoed height was the current latest height, instead of restoring it to the actual previous verified height (as the Substrate `pallet-ismp` implementation correctly does via `PreviousStateMachineHeight`). This is the same bug *class* as the reported finding: an incorrect hardcoded/derived initialization value silently breaks a height/counter invariant that a downstream boundary check (`height > latestHeight`) relies on.

### Finding Description
In the reference report, `GovernorBravoDelegate._initiate` incorrectly sets `initialProposalId = proposalCount`, breaking the invariant `proposalCount >= proposalId > initialProposalId` that `state()` depends on.

The same class of bug exists in `EvmHost.sol`: [1](#0-0) 

```solidity
function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
    StateCommitment memory stateCommitment = _stateCommitments[height.stateMachineId][height.height];
    delete _stateCommitments[height.stateMachineId][height.height];
    delete _stateCommitmentsUpdateTime[height.stateMachineId][height.height];
    // technically any state commitment can be vetoed, safety check that it's the latest before resetting it.
    if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
        _latestStateMachineHeight[height.stateMachineId] = 1;
    }
    ...
}
```

Compare this to the correct pattern used on the Substrate side, which restores the *actual* previous height rather than a magic constant: [2](#0-1) 

The `_latestStateMachineHeight` value is the sole gatekeeper used by `HandlerV2.handleConsensus` to decide whether an incoming `IntermediateState` proof is allowed to overwrite the stored commitment for a state machine: [3](#0-2) 

```solidity
for (uint256 i = 0; i < intermediatesLen; i++) {
    IntermediateState memory intermediate = intermediates[i];
    uint256 latestHeight = host.latestStateMachineHeight(intermediate.stateMachineId);
    if (latestHeight != 0 && intermediate.height > latestHeight) {
        StateMachineHeight memory stateMachineHeight =
            StateMachineHeight({stateMachineId: intermediate.stateMachineId, height: intermediate.height});
        host.storeStateMachineCommitment(stateMachineHeight, intermediate.commitment);
    }
}
```

Once a fisherman vetoes the current latest height (e.g. a legitimately high height `H`, say `H = 5000`), `_latestStateMachineHeight` collapses to `1`. This means:
- Any subsequent consensus update whose `intermediate.height` is between `2` and `H-1` (heights that were previously *below* the latest and therefore correctly rejected as stale) will now pass the `intermediate.height > latestHeight` check and be accepted as a fresh, trusted `storeStateMachineCommitment`.
- This reopens a wide window of previously-superseded/stale heights for which the relayer set, validator set, or state content may have since rotated or been compromised, letting a malicious or colluding relayer resubmit an old/incorrect `StateCommitment` for any height `> 1` and have it treated as authoritative for verifying POST/GET requests, responses, and timeouts (`stateMachineCommitment(height)` is used directly for MMR-proof verification in `HandlerV2.handlePostRequests`/`handleGetResponses`/timeout handlers).

### Impact Explanation
This breaks the monotonic "latest height" invariant that HandlerV2 depends on to prevent replay/rollback of state commitments. After any veto of the current latest height (a normal, expected fisherman operation, not an attack), the protocol's floor drops to `1`, re-opening acceptance of arbitrary lower heights as "new." An attacker (or colluding relayer) can then submit a forged/stale `StateCommitment` for an old height whose MMR root supports request/response/timeout membership or non-membership proofs that should no longer be valid, potentially enabling forged message delivery or bypass of already-superseded proofs. This can lead to unauthorized dispatch of app requests/responses or malicious timeout processing against the sequencer's true state, i.e. forged message delivery / unsound state commitment acceptance.

### Likelihood Explanation
Triggering the bug requires only a single, expected, permissionless-adjacent event: a fisherman successfully vetoing the current latest state commitment (this is a supported normal-operation path of the protocol, not a privileged-admin misconfiguration). Once triggered, exploitation only requires a relayer to submit a further consensus update whose intermediate height is anywhere in `(1, H)` — a very large exploitable window — through the ordinary `handleConsensus` path. No governance or admin misconfiguration is needed; it is a direct consequence of the fisherman-veto feature working as designed.

### Recommendation
Track and restore the true previous verified height (mirroring `PreviousStateMachineHeight` in `modules/pallets/ismp/src/host.rs`) instead of hardcoding `1` in `deleteStateMachineCommitmentInternal`. Concretely, maintain a `_previousStateMachineHeight` mapping updated alongside `storeStateMachineCommitment`, and on veto of the latest height, reset `_latestStateMachineHeight` to that recorded previous height rather than `1`.

### Proof of Concept
1. Chain X's state machine is bridged via `EvmHost`; heights `1..5000` have been verified and committed, with `_latestStateMachineHeight[X] = 5000`.
2. A fisherman detects that the commitment at height `5000` is fraudulent and calls the veto path, which invokes `deleteStateMachineCommitmentInternal(height=5000, fisherman)`.
3. Since `_latestStateMachineHeight[X] == 5000 == height.height`, the height floor is reset to `_latestStateMachineHeight[X] = 1` (not to `4999` or whatever the true prior verified height was).
4. A relayer now submits a consensus update via `HandlerV2.handleConsensus` containing an `IntermediateState` for height `3000` (a height that was already correctly superseded/committed and is now stale relative to the chain's real progress).
5. `HandlerV2` checks `latestHeight != 0 && intermediate.height > latestHeight` → `1 != 0 && 3000 > 1` → true, so `host.storeStateMachineCommitment` overwrites the commitment for height 3000 with new (potentially forged) data, and `_latestStateMachineHeight[X]` becomes `3000`.
6. Downstream `HandlerV2.handlePostRequests`/`handleGetResponses`/timeout handlers now treat this attacker-influenced height-3000 `StateCommitment` as valid, verifying request/response/timeout MMR proofs and non-membership proofs against it — enabling forged message delivery or an invalid timeout/duplicate acceptance that should have been prevented by the monotonic height invariant.

	fn delete_state_commitment(&self, height: StateMachineHeight) -> Result<(), Error> {
		// The height's entry in the state commitment queue is deliberately left
		// behind; locating it would mean scanning the queue, which is the per-insert
		// cost the queue exists to avoid. Usually its eviction is a no-op, but when
		// the vetoed height is the latest the reset below re-opens it for honest
		// resubmission, and the resubmitted height gets a *second* queue entry. The
		// stale entry then evicts the live commitment when it reaches the head —
		// one insertion before the live entry would have, since the resubmission
		// lands directly behind its stale twin. So a veto costs that height one
		// insertion of retention and permanently burns one queue slot. Both are
		// negligible against the configured caps; making it exact would need a
		// height -> index map on the insert path.
		BoundedStateCommitments::<T>::remove(height.id, height.height);
		BoundedStateMachineUpdateTime::<T>::remove(height.id, height.height);

		// technically any state commitment can be vetoed,
		// safety check that it's the latest before resetting it.
		if let Some(latest) = LatestStateMachineHeight::<T>::get(height.id) {
			if latest == height.height {
				// Reset back to the initial height to allow for honest updates
				let prev_height =
					PreviousStateMachineHeight::<T>::get(height.id).ok_or_else(|| {
						Error::Custom("Previous state machine height should exist".to_string())
					})?;
				LatestStateMachineHeight::<T>::insert(height.id, prev_height);
			}
		}
		Ok(())
	}
