This confirms the finding. The gem's documentation explicitly states `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" (`docs/usage/webhooks.md` line 125), and `data.shop` is documented as "The shop domain of the webhook" (line 14) — implying it is authenticated. But the HMAC only covers `@raw_body` [1](#0-0) , while `shop` is read verbatim from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header [2](#0-1) .

### Title
Webhook shop-domain header is not covered by the HMAC, allowing cross-tenant webhook identity spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to verify "the request did indeed come from Shopify" before dispatching to the app's handler with a `shop` identity [3](#0-2) . In reality, `Utils::HmacValidator.validate` only checks the HMAC against `Request#to_signable_string`, which returns solely the raw request body [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` fields are all read straight from HTTP headers that are never included in the signed data [4](#0-3) .

### Finding Description
`Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header value using `OpenSSL.secure_compare` [5](#0-4) . For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns `@raw_body` only [6](#0-5) , so the signature binds only the body bytes.

`Registry.process` raises `InvalidWebhookError` unless `HmacValidator.validate(request)` succeeds, then immediately builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` and dispatches it to the app's handler [7](#0-6) . `request.shop` is `shopify_header("shop-domain")`, read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header with no cryptographic binding to the HMAC-verified body [2](#0-1) .

Because a single app-wide `api_secret_key` is used to compute/verify every shop's webhook HMAC (the same key is used across all tenants of the app — see `Context.api_secret_key` used uniformly in `HmacValidator`), any unprivileged party who can obtain one valid `(raw_body, hmac)` pair for the app — e.g., a merchant who installed the app on their own store and can observe the legitimate webhook their store receives, or anyone who intercepts a single webhook delivery to any endpoint of this app — can replay that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary value in the `x-shopify-shop-domain` header. `HmacValidator.validate` will still return `true` (the body/HMAC pair is legitimate), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the forged `shop`, `topic` is likewise unauthenticated (an attacker could not fully control `topic` since a `(body, hmac)` pair is topic-agnostic in the signature, but they can freely swap `shop`).

This breaks the identity binding the documentation promises:
`hmac-verified(raw_body) == "request came from Shopify for `shop`"`
when in truth:
`hmac-verified(raw_body) != f(shop_header)` — the `shop` field is never an input to the signature.

### Impact Explanation
This is a cross-tenant identity-confusion vector reachable purely over the internet with no privileged credentials: an attacker only needs to have obtained (via any legitimate route, e.g. as a merchant/user of the app on their own store, or via passive interception of one webhook call) a single valid `(raw_body, hmac)` pair for the shared app secret. They can then submit that unmodified pair to the app's public webhook endpoint with a spoofed `shop` header naming a victim tenant. Applications following the gem's documented contract (treating `data.shop` from `WebhookHandler#handle` as an authenticated tenant identifier, exactly as the docs instruct: "The shop domain of the webhook") will process, store, or act on attacker-supplied body content attributed to a shop the attacker doesn't own — a cross-tenant data/identity confusion.

### Likelihood Explanation
Any current or former merchant of the app already possesses one valid `(body, hmac)` pair from their own legitimate webhook traffic (webhooks are delivered over plain HTTPS to the app's own endpoint, and merchants/anyone monitoring that endpoint's traffic can observe the pair). No secret key, access token, or elevated privilege is required to mount the replay — only the ability to send an HTTP POST with a swapped header value.

### Recommendation
Include the tenant/topic-identifying headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signed material, or otherwise cryptographically bind them to the HMAC before trusting `request.shop` as a webhook's authenticated origin. At minimum, document clearly that `data.shop` is not authenticated by the HMAC and must not be used as a trust boundary without additional verification (e.g., cross-checking against a shop for which the app holds an active, verified session/access token).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (or otherwise observes any single legitimate webhook delivery for the app).
2. Attacker captures one legitimate webhook POST: `raw_body = B`, header `x-shopify-hmac-sha256 = H` (valid because `H = HMAC-SHA256(api_secret_key, B)`), and `x-shopify-shop-domain = attacker-shop.myshopify.com`.
3. Attacker resends the exact same POST to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim-shop.myshopify.com", "x-shopify-hmac-sha256" => H})` is constructed.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which computes `HMAC-SHA256(api_secret_key, B)` and compares to `H` — this still matches, since `to_signable_string` returns `B` alone [6](#0-5) .
6. The registered handler is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: ..., body: JSON.parse(B), ...)` [8](#0-7) , causing the app to process attacker-supplied content as if it were an authenticated webhook from `victim-shop.myshopify.com`.
