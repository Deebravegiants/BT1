This confirms the pattern: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely outside the HMAC-covered bytes [2](#0-1) . `Registry.process` validates only `Utils::HmacValidator.validate(request)` (which checks the HMAC over `to_signable_string`, i.e., the body) and then hands `request.shop` straight to the handler as trusted tenant identity [3](#0-2) . The documentation explicitly tells integrators to trust `data.shop` as "The shop domain of the webhook" [4](#0-3) .

### Title
Webhook shop identity is not bound to the HMAC-verified payload, allowing cross-tenant webhook shop-spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` (and `topic`/`webhook_id`/`api_version`) values are taken unauthenticated from HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then passes the header-derived `shop` value directly to the app's webhook handler as trusted tenant identity, without any binding between the verified bytes and the claimed shop.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only [1](#0-0) . `Request#shop` is derived from `shopify-shop-domain`/`x-shopify-shop-domain` headers [2](#0-1) , which are never included in the signable string that `HmacValidator` verifies [5](#0-4) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (body-only) before dispatching `request.shop` to the handler as an authenticated field: [3](#0-2) 

The binding the gem implicitly claims to enforce is: `hmac_valid(body) == true` implies `shop header == the shop that produced body`. In reality the equality that actually holds is only `hmac(body, api_secret_key) == received_hmac`; there is no cryptographic tie between `body` and `shop`. Because a single app-wide `api_secret_key` is used to sign webhooks for *every* installed shop, any valid `(body, hmac)` pair captured from one shop's legitimate webhook delivery remains valid HMAC-wise when replayed with a different `shop-domain` header value, since the header is not part of the signed content.

### Impact Explanation
This breaks the tenant-identity binding that host applications are told to rely on (`docs/usage/webhooks.md` explicitly instructs apps to key work off `data.shop`). An app that trusts `data.shop` to select which merchant record to update, delete customer data for, or authorize an action against (e.g., GDPR redaction handlers, order sync, inventory updates) can be made to apply another shop's payload under an attacker-chosen shop identity — a cross-tenant data-integrity/confusion issue, which matches the Critical "cross-tenant access" impact category, since it lets one tenant's verified webhook content be attributed to a different tenant.

### Likelihood Explanation
Requires the attacker to have obtained one legitimately signed `(raw_body, hmac)` pair (e.g., via a compromised/observable webhook delivery, non-TLS relay, logging leakage, or being a legitimate merchant of the same app receiving webhooks for their own shop) and to be able to POST to the app's public webhook endpoint with a forged shop header — both of which are within reach of an unprivileged internet user/merchant, without needing `api_secret_key` or any access token.

### Recommendation
Include the shop domain (and topic/webhook id) in the HMAC-signed content, or otherwise cryptographically bind the header-derived `shop` to the verified body before handing it to `WebhookMetadata`/handlers. At minimum, `Registry.process` should not treat `request.shop` as trusted unless it is corroborated by shop-scoped session/storage lookups on the host application side, and this should be a documented requirement rather than an implicit trust of `data.shop`.

### Proof of Concept
1. App registers a webhook handler `WebhookHandler#handle` that uses `data.shop` to look up/update tenant records (as shown in `docs/usage/webhooks.md`).
2. Attacker (or a merchant installing the same app on their own store) captures a legitimate webhook `(raw_body, X-Shopify-Hmac-Sha256)` pair delivered by Shopify for shop `A.myshopify.com`.
3. Attacker POSTs the identical `raw_body` and `hmac` to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: B.myshopify.com`.
4. `HmacValidator.validate` succeeds because it only checks `body` against the secret [6](#0-5) .
5. `Registry.process` calls the handler with `shop: "B.myshopify.com"` and the body originally produced for shop `A`, causing the app to process/attribute shop A's data under shop B's identity [7](#0-6) .
