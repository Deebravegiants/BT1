### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing in `ShopifyAPI::Webhooks::Registry.process` - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , so `Utils::HmacValidator.validate` only proves the *body* bytes are authentic — it never authenticates the `shop-domain` header, which is exposed via `Request#shop` and used downstream as the tenant identifier [2](#0-1) . This mirrors the report's bug class: a field that is *acted on* (`shop`, used to route/attribute webhook data to a tenant) is not covered by the cryptographic binding (`hmac`) that is checked before trusting the request.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates the request purely by HMAC of the body, then immediately trusts `request.shop` (parsed from the `X-Shopify-Shop-Domain` header) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The binding that should hold is:
`hmac_valid(body, secret) ⇒ shop_header == shop_that_produced(body)`

But the actual binding enforced is only:
`hmac_valid(body, secret)`

Since `to_signable_string` = `@raw_body` only [1](#0-0) , and `shop` is read from a header that is never mixed into the signed string [2](#0-1) , the equality above does not hold. `HmacValidator.validate` merely recomputes `HMAC(secret, body)` and compares it to the `hmac-sha256` header [4](#0-3) ; the `shop-domain` header can be swapped freely without invalidating the signature.

Critically, the HMAC secret (`api_secret_key`) is the app's single client secret shared across **every shop** that installs the app — it is not shop-specific. An unprivileged user who has installed the app on their own (attacker-controlled) shop legitimately receives real, correctly-signed webhooks from Shopify for that shop. Nothing in this gem prevents them from re-sending that exact `(body, hmac-sha256)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still returns `true` (the body/HMAC pair is genuine), and `Registry.process` forwards `shop: request.shop` = the victim's domain to the app's handler [5](#0-4) , per the gem's own documented contract that `data.shop` is "The shop domain of the webhook" [6](#0-5) .

### Impact Explanation
This is a cross-tenant confusion: an attacker who has any legitimate install of the target app (even a free/dev shop) can produce a validly-HMAC'd payload and relabel it as belonging to any other shop of their choosing. Host applications that trust the gem's `data.shop` value (as documented and shown in the gem's own webhooks.md example) to select which tenant's records to create/update/delete will act on the victim tenant using attacker-supplied body content — e.g. spoofing `customers/redact`, `app/uninstalled`, `shop/redact`, or business-data webhooks (`orders/create`, `products/update`) as if they originated from a shop the attacker does not control. This crosses the tenant boundary purely through data the gem is responsible for authenticating, matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Always reachable: any entity that can install the app once (a public app, or a free/dev-store install) can capture one legitimate webhook body+HMAC pair and replay it with an arbitrary `shop-domain` header value to the same webhook endpoint. No secret, access token, or privileged credential is required — only observation of one's own legitimate webhook traffic, which is trivial for any app installer.

### Recommendation
Bind the shop identity into the value that is cryptographically checked before it is trusted, e.g. include the `shop-domain` (and/or `topic`/`webhook-id`) header bytes in `to_signable_string`, or independently verify that `request.shop` corresponds to a shop with an active session/install known to the host app before processing, rather than trusting the raw header once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Shopify sends a legitimate webhook to the app's callback endpoint with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same `B` and `X-Shopify-Hmac-Sha256` value to the same endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` — matches, since `to_signable_string` never includes the header — validation passes.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-controlled webhook content attributed to the victim tenant.
