Based on my investigation, this analysis confirms a valid identity-binding break in the webhook processing path.

### Title
Webhook `shop` identity is trusted from an unauthenticated header while only the raw body is HMAC-verified, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` (and `topic`, `webhook_id`, `api_version`) from HTTP headers that are excluded from the HMAC signature, while `Utils::HmacValidator.validate` only checks `to_signable_string`, which returns the raw JSON body alone.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` authorizes a webhook purely via `Utils::HmacValidator.validate(request)`, which computes the signature only over `request.to_signable_string` — the raw body: [1](#0-0) [2](#0-1) 

The `shop` value that is subsequently handed to the handler (`WebhookMetadata.shop`) comes exclusively from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed content at all: [3](#0-2) 

The identity binding that should hold is: `shop authenticated by HMAC == shop acted on by the handler`. Because the HMAC is computed only over `@raw_body` and never incorporates the `shop-domain` header, this equality does not hold — the header can be swapped for any value while the signature remains valid for the same body, since the app's `client_secret`/webhook signing key is shared across all shops using the app (it is not shop-specific).

### Impact Explanation
This breaks the tenant boundary the library is documented to provide via `Registry.process`, described as verifying "the request did indeed come from Shopify" before invoking the handler with `data.shop`: [4](#0-3) 

Handlers are documented to key application-side logic (e.g. job enqueuing, data writes) directly off `data.shop` without any additional verification, per the library's own example: [5](#0-4) 

An unprivileged holder of a valid app installation (any developer can install a public/dev app on their own free store) can capture one of their own legitimately signed webhook body/HMAC pairs, then replay it against the same endpoint with the `shopify-shop-domain` header rewritten to a victim shop that also has the app installed. `Utils::HmacValidator.validate` accepts it because the signature only ever validated the body, and `Registry.process` forwards the attacker-chosen `shop` value straight into `WebhookMetadata` used by the handler, resulting in cross-tenant data confusion/injection under another merchant's identity.

### Likelihood Explanation
Any legitimate installer of the target app already possesses a valid signed body for at least one topic (e.g., a low-value topic like `app/uninstalled` whose body content doesn't depend on shop-specific secrets), and the API secret used for webhook signing is shared across the whole app rather than per-shop, so no secret material needs to be stolen — only a header needs to be changed on replay.

### Recommendation
Bind the header-derived `shop` (and `topic`/`webhook_id`) into the signed material verified by `HmacValidator`, or otherwise cross-check the header `shop` against a shop known to be associated with the specific signed payload (e.g., require the caller to supply the expected shop and compare it against a shop resolved independently of the header) before constructing `WebhookMetadata`.

### Proof of Concept
1. Install the target app on an attacker-controlled dev store `attacker.myshopify.com`; trigger any subscribed webhook topic to capture `raw_body` and the resulting `shopify-hmac-sha256` header — this HMAC is valid because it is computed only over `raw_body` with the app's shared secret: [6](#0-5) 
2. Replay a POST to the same webhook endpoint using the identical `raw_body` and `shopify-hmac-sha256` header, but set `shopify-shop-domain: victim.myshopify.com` (a real installer of the app).
3. `Utils::HmacValidator.validate(request)` returns `true` because it only re-derives the signature from `raw_body`: [7](#0-6) 
4. `Registry.process` invokes the handler with `WebhookMetadata.shop == "victim.myshopify.com"`, even though the payload was never produced by, or signed for, that shop: [1](#0-0)

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
