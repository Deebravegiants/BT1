## Title
Webhook HMAC does not cover the `shop-domain` header, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, never the `shopify-shop-domain` header value. `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` — an unauthenticated header — to attribute the incoming payload to a specific merchant, even though the HMAC that gates processing only proves the integrity of the body, not of the shop attribution.

### Finding Description
The equality the HMAC is supposed to guarantee is:
`bytes verified by HMAC == bytes acted upon (topic, body, and the shop they are attributed to)`

In this gem that equality is broken. `Utils::HmacValidator.validate` computes and compares the signature purely from `verifiable_query.to_signable_string`, and for webhooks this is defined as: [1](#0-0) 

only `@raw_body` — the `shopify-shop-domain` header is excluded. `Registry.process` then validates the HMAC and, on success, immediately reads `request.shop` from that unauthenticated header to build the data handed to the app's handler: [2](#0-1) 

The secret used for the HMAC is the app-wide `Context.api_secret_key` — the same key is used for every shop that installs the app, not a per-shop secret: [3](#0-2) 

Because the signature is a function of `(body, app_secret)` only, and the same `app_secret` is shared across all merchants of the app, a valid `(body, hmac)` pair obtained from one shop's genuine webhook delivery remains valid when replayed with a different `shopify-shop-domain` header. The `Registry.process` code has no way to detect this since it never checks that the `shop` header was part of what was signed.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing (cross-tenant access), a Critical-impact category per this assessment's scope. An attacker who controls one shop that has installed the vulnerable app can capture any of their own legitimately-signed webhook deliveries (e.g. `orders/create`, `customers/redact`, `app/uninstalled`) and resend the exact same body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` because the signature check never looked at that header, and the app's registered handler receives `WebhookMetadata` claiming the data originated from the victim shop. Depending on the handler's logic, this can be used to inject fabricated data attributed to another tenant, or to trigger destructive/administrative flows (e.g., simulating `app/uninstalled` or a GDPR `shop/redact` webhook) against a shop the attacker does not control and never sent that event.

### Likelihood Explanation
Any user who can install the target app on their own store (a normal, unprivileged action) automatically receives genuinely HMAC-signed webhook deliveries from Shopify for topics registered by the app. Replaying that captured body+HMAC to the app's public webhook endpoint with a different shop header requires no secret knowledge and no privileged access — it is directly reachable via the gem's documented `Registry.process` entry point.

### Recommendation
Include the shop domain (and ideally the topic and webhook id) inside the HMAC-covered signable content, or otherwise independently authenticate the shop attribution before trusting `request.shop` — e.g., verify the `shop-domain` header against a session/shop record the app already knows is legitimately installed, or bind the header value into `to_signable_string` if Shopify's webhook signing scheme is extended to support it. At minimum, document that `request.shop` is unauthenticated and must not be trusted for authorization decisions without additional server-side verification.

### Proof of Concept
1. App receives a legitimate webhook for shop A: body `B`, header `x-shopify-shop-domain: shop-a.myshopify.com`, header `x-shopify-hmac-sha256: H` (computed by Shopify over `B` using the app's shared secret).
2. Attacker (owner/operator of shop A) resends the exact same `B` and `H` to the app's webhook endpoint, changing only the header to `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request#hmac` decodes the same `H`; `Utils::HmacValidator.validate` recomputes the signature over `B` with `Context.api_secret_key` and it matches, since `to_signable_string` never included the shop header.
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: parsed(B) ...)`, causing the app to process attacker-controlled data as if it came from the victim shop.
