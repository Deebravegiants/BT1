### Title
Solver-relay `intent_hash` in `getStatus`/`waitForIntentSettlement` response is trusted without verifying it matches the requested pinned hash - (File: packages/internal-utils/src/solverRelay/waitForIntentSettlement.ts)

### Summary
`waitForIntentSettlement` polls `getStatus` with a caller-pinned `intent_hash`, but when a `SETTLED` response arrives it returns `intentHash: res.intent_hash` (server-supplied value) instead of the originally requested `intentHash`, with no equality check between the two. The same pattern exists in `getStatus.ts`, which forwards `response.intent_hash` from the relay as-is. This mirrors the regclient class of bug: a caller pins an identifier (digest/hash) it expects back, but the client accepts whatever identifier the untrusted server echoes without confirming it matches what was requested.

### Finding Description
`sdk.processWithdrawal` in `packages/intents-sdk/src/sdk.ts` (lines 815-829) signs and publishes an intent, obtains `intentHash` from the publish step, then calls `waitForIntentSettlement({ intentHash, ... })` to await settlement, and finally passes the returned `intentTx` (built from `res.data.hash` / `res.intent_hash`) into `waitForWithdrawalCompletion`.

Inside `waitForIntentSettlement` (packages/internal-utils/src/solverRelay/waitForIntentSettlement.ts, lines 56-83):
```
const res = await solverRelayClient.getStatus({ intent_hash: intentHash }, ...);
...
if (res.status === "SETTLED") {
    return {
        txHash: res.data.hash,
        intentHash: res.intent_hash,
    };
}
```
The function requests status for a specific `intentHash` (the pinned value the caller cares about) but the return value uses `res.intent_hash` and `res.data.hash` taken directly from the relay's JSON-RPC response, with no assertion that `res.intent_hash === intentHash`. `getStatus.ts` (lines 20-43) has the identical pattern: it returns `response.intent_hash` from the untrusted HTTP response body rather than the value that was sent in the request.

This breaks the equality "hash reported == hash requested/pinned." A relay that returns a `SETTLED` status with a *different* `intent_hash`/`data.hash` than the one queried would have that mismatched value silently accepted and propagated up through `sdk.processWithdrawal`, into `intentTx` and ultimately into downstream logic (e.g., `waitForWithdrawalCompletion`, which uses `intentTx` to correlate/derive withdrawal identifiers) and into logs/return values (`args.logger?.info("Intent settled", { txHash: intentTx.hash })`).

### Impact Explanation
If the solver relay is compromised, buggy, or MITM'd, it could report settlement/tx-hash data for a different intent than the one the integrator is polling for. Because no consuming code checks `res.intent_hash === intentHash` before trusting `data.hash`, an integrator relying on `waitForIntentSettlement`/`processWithdrawal` could be told the wrong intent settled with a given transaction hash — a status/hash misreport that could cause an integrator to credit/refund based on the wrong intent, or bind subsequent withdrawal-completion polling to an incorrect transaction. This falls under the "status or hash misreport" High-impact category from the rules, since it can make an integrator credit/refund incorrectly.

### Likelihood Explanation
Requires a malicious or compromised solver-relay response — the relay is explicitly called out in scope rules as an entity whose malicious behavior is out of scope ("trust assumptions about ... the relayer" are excluded per the prompt's rules). This significantly limits the standalone severity/validity of this finding under the stated scope rules, since the relayer is a trusted external component in this SDK's threat model, similar to how regclient's registry is normally semi-trusted but the CVE treats it as adversarial. The finding is a defense-in-depth gap (missing equality check) rather than a bug reachable purely by an unprivileged end-user without relay cooperation.

### Recommendation
In `getStatus.ts` and `waitForIntentSettlement.ts`, after receiving the relay response, assert that `response.intent_hash === requestedIntentHash` (the value sent in `{ intent_hash: intentHash }`) before accepting `status`/`data.hash`/`intent_hash` from the response. Throw or treat as a transient/invalid response if the hashes don't match, mirroring `regclient`'s patch of comparing the returned digest to the requested digest.

### Proof of Concept
1. Attacker controls or MITMs the solver-relay endpoint (`https://solver-relay-v2.chaindefuser.com/rpc` or configured `baseURL`).
2. Client calls `waitForIntentSettlement({ intentHash: "intentA" })`, which sends `get_status` with `intent_hash: "intentA"`.
3. Malicious relay responds with `{ status: "SETTLED", intent_hash: "intentB", data: { hash: "txForIntentB" } }`.
4. `waitForIntentSettlement` returns `{ txHash: "txForIntentB", intentHash: "intentB" }` without ever checking that `"intentB" !== "intentA"`.
5. `sdk.processWithdrawal` logs and proceeds with `intentTx` built from the mismatched data, potentially crediting/reporting settlement for the wrong intent. [1](#0-0) [2](#0-1) [3](#0-2)

```typescript
export async function getStatus(
	...args: Parameters<typeof solverRelayClient.getStatus>
): Promise<GetStatusReturnType> {
	return solverRelayClient.getStatus(...args).then((response) => {
		const status = response.status;
		switch (status) {
			case "SETTLED":
			case "TX_BROADCASTED":
				return {
					status,
					intentHash: response.intent_hash,
					txHash: response.data.hash,
				};
			case "PENDING":
			case "NOT_FOUND_OR_NOT_VALID":
				return {
					status,
					intentHash: response.intent_hash,
				};
			default:
				status satisfies never;
				assert(false, `Unexpected intent status = ${status}`);
		}
	});
```
