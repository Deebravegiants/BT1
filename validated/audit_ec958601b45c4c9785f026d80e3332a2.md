### Title
Untrusted predispatch/postdispatch calldata can strand tokens in the shared `CallDispatcher`, which are later swept wholesale into an unrelated order's escrow — ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.placeOrder`'s predispatch flow and `IntentsBase._execute`'s postdispatch flow both route funds through a single, stateless, shared `CallDispatcher` contract, execute fully attacker-controlled calldata against it, and then credit whatever token balance is subsequently observed on the dispatcher (`IERC20(token).balanceOf(dispatcher)`) as the legitimately "received" amount for the current order — exactly the "trust `balanceOf(address(this))` after an untrusted external call" pattern flagged in the Dodo `MarginTrading` report. Because the sweep-back logic only ever checks the token(s) explicitly declared in `order.inputs` (predispatch) or `order.output.assets` (postdispatch), any *other* token that the attacker-authored calldata leaves behind on the dispatcher is never returned to its rightful owner and instead sits available to be claimed, in full, by whichever order next targets that token.

### Finding Description
In `placeOrder`, when `order.predispatch.call` is non-empty, the flow is:
1. Transfer `order.predispatch.assets` into the `dispatcher`.
2. Execute the fully user-supplied `order.predispatch.call` via `ICallDispatcher(dispatcher).dispatch(...)` [1](#0-0) .
3. For each token in `order.inputs`, read `balance = IERC20(token).balanceOf(dispatcher)`, require `balance >= requiredAmount`, and sweep the **entire current balance** back to the gateway [2](#0-1) .
4. Credit `received = balanceOf(this) - balancesBefore` directly as `order.inputs[i].amount` [3](#0-2) .

The `balance >= requiredAmount` check only proves the dispatcher currently holds enough of that token — it does not prove that balance was actually produced by *this* predispatch call. Analogously, in `IntentsBase._execute` (postdispatch, run when a solver fills an order carrying `order.output.call`), the dispatcher executes attacker/order-creator-supplied calldata and then sweeps back only the tokens listed in `order.output.assets`, emitting any leftover as `DustCollected` [4](#0-3) .

Because the sweep in both flows is scoped only to the *declared* token list, a malicious `order.output.call` can route a filler's delivered output tokens through an unrelated intermediate token (e.g., a multi-hop swap or DeFi interaction) that is *not* one of `order.output.assets`. That intermediate token is left stranded on the shared `CallDispatcher` — a singleton contract used by every order in the protocol, with no per-order balance accounting of its own (see `CallDispatcher.dispatch`, which just executes calls with no bookkeeping) [5](#0-4) . The same order creator (or anyone) can subsequently place a new order whose `predispatch.assets`/`predispatch.call` is a no-op for the stranded token, and whose `order.inputs` targets that token: the `balance >= requiredAmount` check passes purely because the dispatcher already holds the stranded balance, and the full balance is swept and credited as this new order's escrowed input — with no contribution of the attacker's own funds.

This mirrors the Dodo root cause precisely: `_tradeAmounts[i] = IERC20(_tradeAssets[i]).balanceOf(address(this))` trusted the post-swap balance without validating it came from the specific swap that just ran; here, `balanceOf(dispatcher)` is trusted the same way, letting an attacker-crafted call divert value into a token outside the declared list and later claim it as their own escrow deposit.

### Impact Explanation
This allows permanent misappropriation of another party's tokens (the filler's delivered output assets, diverted via a malicious `order.output.call`) with no economic contribution from the attacker on the follow-up order. Funds legitimately owed to a solver/filler (or to the protocol as declared dust) are instead captured by whoever next happens to reference the stranded token in a predispatch flow, resulting in concrete theft of funds routed through the intent gateway's shared dispatcher.

### Likelihood Explanation
The order creator fully controls `order.output.call` (postdispatch calldata) at order-placement time, and any account can subsequently call `placeOrder` with an arbitrary `predispatch.call`/`order.inputs` combination. No privileged role or governance action is required — a single attacker acting as both the order creator (to strand funds) and predispatch-order placer (to reclaim them) can execute the whole attack across two ordinary, permissionless transactions.

### Recommendation
Track and sweep based on *actual balance deltas measured immediately around the untrusted call*, and scope the sweep to only the tokens the untrusted calldata was authorized to touch, rather than trusting the dispatcher's ambient balance. Concretely: snapshot the dispatcher's balance for a token before dispatching predispatch/postdispatch calldata (not just before the swap output) and require any surplus/residual balance for tokens outside the declared list to be swept back to a safe, permissioned destination (e.g., the order's own beneficiary/creator) rather than left claimable by any future caller. Consider giving each order an isolated escrow/dispatcher context instead of a single global stateless `CallDispatcher` shared across all orders.

### Proof of Concept
1. Attacker (as order creator) places an order with `order.output.call` set to calldata that, upon receiving the filler's `order.output.assets` tokens, swaps them into an unrelated token `X` not present in `order.output.assets`, and does not forward `X` anywhere.
2. A solver fills this order; `_execute` dispatches the calldata, then sweeps only the declared output tokens (now empty balance) — `X` remains stranded on the shared `CallDispatcher`.
3. Attacker calls `placeOrder` again with `predispatch.call` a no-op (or minimal call) and `order.inputs = [{token: X, amount: strandedAmount}]`.
4. The `balance >= requiredAmount` check at `evm/src/apps/IntentGatewayV2.sol:274-275` passes because the dispatcher already holds `strandedAmount` of `X` from step 2; the full balance is swept and credited as the attacker's escrowed input, without the attacker having contributed any `X` themselves — completing the theft of the filler's funds.

        if (order.output.call.length == 0) return;

        address dispatcher = _params.dispatcher;
        ICallDispatcher(dispatcher).dispatch(order.output.call);

        Call[] memory sweepCalls = new Call[](outputsLen);
        uint256 sweepCount = 0;

        for (uint256 i; i < outputsLen;) {
            address token = address(uint160(uint256(order.output.assets[i].token)));

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
