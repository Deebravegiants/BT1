### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authentic once `Utils::HmacValidator.validate(request)` succeeds, but the HMAC signature only covers the raw request body, not the `shop-domain` (or `x-shopify-shop-domain`) header. This breaks the intended identity binding `HMAC == f(body, shop)`; in reality `HMAC == f(body)` only. An attacker who is able to obtain any one genuine `(raw_body, hmac)` pair signed by the app's `api_secret_key` (e.g., from a webhook delivered to their own, attacker-controlled shop) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value, causing the handler to process the attacker's payload as if it originated from a different (victim) shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body`, so `shop` (parsed from the `shopify-shop-domain`/`x-shopify-shop-domain` header) is never part of the signed material: [3](#0-2) 

`HmacValidator.validate` computes the HMAC purely from `to_signable_string`, i.e. the body: [4](#0-3) 

`Registry.process` accepts the request once this body-only HMAC check passes, then dispatches the handler using the unauthenticated `request.shop` value directly, with no cross-check that the shop is consistent with anything the signature covers: [5](#0-4) 

This reproduces the reported bug class: a field that is *acted on* (`shop`, used as the tenant identity for the webhook handler) but *not covered* by the authentication mechanism (`hmac`, computed over `raw_body` only). The equality that should hold — "the shop this webhook is attributed to" == "the shop Shopify actually generated this signed payload for" — does not hold, because the signature makes no statement about `shop` at all.

### Impact Explanation
Any handler that trusts `WebhookMetadata#shop` (built directly from `request.shop`) to select or scope merchant data — the documented and expected usage pattern, e.g. `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` — can be tricked into applying a genuinely-signed payload to the wrong tenant. Since the attacker only needs one valid `(raw_body, hmac)` pair from *any* shop (including their own store where the app is installed) to forge the shop attribution for arbitrary other shops, this is a cross-tenant data confusion / spoofing primitive reachable by an unprivileged internet user who merely has (or can trigger) one legitimate webhook delivery for their own store.

### Likelihood Explanation
Likelihood is high for any integrator following the documented webhook flow: register a handler, call `Registry.process`, and use `data.shop` from `WebhookMetadata`. Obtaining one genuine `(body, hmac)` pair requires nothing more than installing the app on an attacker-owned/free development store and capturing a legitimate webhook delivery — well within reach of an unprivileged internet user, no `api_secret_key` or stolen credentials needed.

### Recommendation
Bind `shop` into the signed material, or otherwise cryptographically tie the shop identity to the payload before handler dispatch:
- Include the `shop-domain` header value in `to_signable_string` (this deviates from Shopify's on-the-wire HMAC scheme, so instead prefer validating shop authenticity out-of-band), or
- Require callers to supply the expected shop (e.g., from the already-authenticated session/install record) and have `Registry.process` reject the request if it disagrees with `request.shop`, rather than trusting the header verbatim.
- Document clearly (and enforce in the library where possible) that `request.shop` is unauthenticated header data and must never be used alone to select tenant-scoped resources without an independent binding (e.g., matching against a known/installed shop list) to prevent replay-based cross-tenant spoofing.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers/receives a legitimate webhook, capturing the raw POST body `B` and its valid `x-shopify-hmac-sha256` header `H` (computed by Shopify over `B` using the app's real `api_secret_key`).
2. Attacker sends a new HTTP request directly to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256`: `H` (unchanged, still valid since HMAC only covers `B`)
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com` (attacker-chosen, arbitrary)
   - Header `x-shopify-topic`: matching a topic the app has registered a handler for.
3. `ShopifyAPI::Webhooks::Request.new` parses this successfully; `Utils::HmacValidator.validate` returns `true` because it only checks `B` against `H`.
4. `Registry.process` invokes the registered handler with `WebhookMetadata` where `shop == "victim-shop.myshopify.com"` and `body` is the attacker's captured payload — the app now processes attacker-controlled data as if it came from the victim shop.
