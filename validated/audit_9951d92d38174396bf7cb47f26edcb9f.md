### Title
Missing contract-existence check before `EvmHost.dispatchIncoming(GetResponse)`'s low-level `call` to the requesting module lets the relayer fee be paid and a delivery receipt be finalized without the callback ever executing - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatchIncoming(PostRequest, address)` explicitly checks `extcodesize(destination)` before making its low-level call to the destination module, returning early (no receipt, no call) when the target has no code [1](#0-0) . The sibling function `dispatchIncoming(GetResponse, address)`, which the handler invokes on `handleGetResponses` to deliver a GET response back to the module that originated the request, has no such check: it records the response receipt, then issues a bare `.call()` to `_bytesToAddress(response.request.from)` [2](#0-1) .

### Finding Description
Per the Solidity semantics cited in the external report, a low-level `call` to an address with no deployed code returns `success == true` with empty return data — the EVM does not distinguish "call succeeded" from "no code existed at that address." `dispatchIncoming(GetResponse, address)` relies on this `success` boolean to decide whether the delivery worked:

```solidity
function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
    // replay protection
    bytes32 commitment = response.request.hash();
    _responseReceipts[commitment] = ResponseReceipt({...});

    (bool success,) = _bytesToAddress(response.request.from)
        .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

    if (!success) {
        delete _responseReceipts[commitment];
        return;
    }

    // reward the relayer fee
    uint256 fee = _requestCommitments[commitment].fee;
    if (fee != 0) {
        IERC20(feeToken()).safeTransfer(relayer, fee);
    }
    emit GetRequestHandled({commitment: commitment, relayer: relayer});
}
``` [2](#0-1) 

If `response.request.from` is an address with no code — e.g., the originating app module was later destroyed, or a self-destructing/never-deployed contract address is used as the `from` — the `.call()` still returns `success == true`. The host then treats the callback as having succeeded: it keeps the `_responseReceipts` entry (permanently marking the message as delivered, so it can never be retried through the normal "delete receipt and retry" path used for genuine failures), and pays the full relayer fee out of the fee-token balance via `safeTransfer`, even though `onGetResponse` never actually ran. This is the exact bug class from the external report (`StaticHyVM.doDelegateCall`): a low-level call to a possibly-non-existent contract is trusted as proof that logic executed, with fee/state consequences based on that false signal.

By contrast, the POST path (`dispatchIncoming(PostRequest, ...)`) and the `CallDispatcher` utility both explicitly guard against this with an `extcodesize` check [3](#0-2) [4](#0-3) , showing the codebase is aware of this hazard elsewhere but omitted it here.

### Impact Explanation
This finding permanently drains relayer-fee funds from the fee-token balance the host holds for relayer rewards, on any relayed GET response whose originating module address has no code at delivery time (destroyed, self-destructed, or an address that was never a deployed contract). Because `_responseReceipts` is written unconditionally and never rolled back when `success` is a false positive, the message is marked as permanently delivered — the genuine app callback can never be retried, silently breaking the "retryable delivery" invariant the rest of the host relies on (as documented for the POST path and exercised by `testRejectedDeliveryStaysRetryableThroughHost`). This is a concrete loss of relayer reward accounting integrity and a permanent inability to redeliver the message, meeting the Medium-severity bar for token/fee-accounting and message-delivery-soundness issues.

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires a module that has previously dispatched a GET request (so `request.from` is on record and reachable to relayers) to subsequently lose its code (e.g., via `SELFDESTRUCT`, though largely deprecated post-Cancun, or an intentionally-non-contract `from` value if that path is otherwise reachable) before the response is relayed back. The report's own precedent (Nested Finance TOB-NESTED-1) establishes this risk is non-null in practice for adjacent systems using similar patterns.

### Recommendation
- **Short term**: Add the same `extcodesize`/`code.length` guard used in `dispatchIncoming(PostRequest, ...)` to `dispatchIncoming(GetResponse, ...)` before the low-level `.call()`, treating a code-less target the same as a failed call (skip fee payment, roll back / never persist the receipt as a false "success").
- **Long term**: Audit all remaining low-level `.call()` / `.delegatecall()` sites in `EvmHost.sol` and `HandlerV2.sol` (e.g., `dispatchTimeOut`) for the same missing-existence-check pattern, and standardize on a single internal helper that always checks code existence before treating a low-level call's `success` flag as authoritative.

### Proof of Concept
1. Module `M` dispatches a `GetRequest` via `EvmHost.dispatch(DispatchGet)`, recording `from = M`.
2. `M` is later destroyed (code removed) before the corresponding `GetResponse` is relayed back.
3. A relayer submits a valid proof for the `GetResponse` through `HandlerV2.handleGetResponses`, which calls `host.dispatchIncoming(response, relayer)`.
4. Inside `dispatchIncoming(GetResponse, ...)`, `_bytesToAddress(response.request.from).call(...)` targets the now-code-less `M` and returns `success == true` with empty return data.
5. The host keeps `_responseReceipts[commitment]` set (the message can never be redelivered even though `onGetResponse` never ran) and transfers the relayer fee via `safeTransfer(relayer, fee)`, and emits `GetRequestHandled` — all without any actual application logic having executed.
