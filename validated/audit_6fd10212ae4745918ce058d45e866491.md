If `exchangeRate` is large enough that integer division rounds `virtualLtReserve` down to `0`, `Router.addInitialLiquidity` calls `Pair.mint(totalSupply, 0)`, which sets `_pool.k = totalSupply * 0 = 0`.

### Title
Zero-reserve mint degrades `Pair`'s K-invariant guard to a no-op, letting a created LT's exchange-rate value bypass the curve's swap-correctness check - ([File: packages/contracts/src/Bonding.sol], [File: packages/contracts/src/Pair.sol])

### Summary
`Bonding._deployAndSeed` guards only against `exchangeRate() == 0`, not against the *derived* `virtualLtReserve` rounding to `0`. `Pair.mint` accepts a `0` reserve with no floor check and stores `_pool.k = tokenReserve * assetReserve`. When `assetReserve == 0`, `k == 0`. This is the direct analog of the py_ecc bug: a boundary/degenerate value (the AMM's "point at infinity", `k == 0`) is not rejected, and once it exists every subsequent arithmetic check that is supposed to be a meaningful constraint becomes trivially satisfied.

### Finding Description
`Pair.swap`'s only correctness check is:
```
if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated(); [1](#0-0) 
```
If `_pool.k == 0` (from a zero-reserve mint), the left side is always ≥ 1, so this check can never revert — it becomes unconditionally true for any `tokenIn/tokenOut/assetIn/assetOut` the router passes, exactly like the py_ecc case where `x·O = O` made verification trivially satisfied regardless of the signature.

`_deployAndSeed` computes the seed asset reserve as:
```
uint256 exchangeRate = IBounceLeveragedToken(ltAddress).exchangeRate();
if (exchangeRate == 0) revert ZeroExchangeRate();
uint256 virtualLtReserve = (VIRTUAL_LIQUIDITY_USD * 1e18) / exchangeRate;
if (virtualLtReserve > type(uint112).max / 4) revert ExchangeRateTooLow();
...
$.router.addInitialLiquidity(tokenAddr, totalSupply, curveSupply, virtualLtReserve); [2](#0-1) 
```
Only an upper bound (`ExchangeRateTooLow`) is enforced; there is no lower-bound / non-zero check on `virtualLtReserve` itself. If `exchangeRate` is large enough that `(VIRTUAL_LIQUIDITY_USD * 1e18) / exchangeRate` truncates to `0` (e.g. `exchangeRate > VIRTUAL_LIQUIDITY_USD * 1e18`), `virtualLtReserve = 0` passes both checks and reaches `Router.addInitialLiquidity`, which calls:
```
IPair(pairAddr).mint(virtualReserveToken, reserveAsset); [3](#0-2) 
```
`Pair.mint` performs no non-zero validation on either reserve:
```
function mint(uint256 tokenReserve, uint256 assetReserve) external onlyRouter returns (bool) {
    if (_pool.k != 0) revert AlreadyMinted();
    _pool = Pool({tokenReserve: tokenReserve, assetReserve: assetReserve, k: tokenReserve * assetReserve}); [4](#0-3) 
```
With `k == 0`, `AlreadyMinted` will also never trigger again (since the guard is `_pool.k != 0`), so the pair is left in a permanently degenerate, always-mintable, always-swappable state. Every buy/sell then routes through `Router._computeBuy`/`_computeSell`, both of which derive amounts from `pair.k()` — with `k == 0` these produce degenerate/zero outputs and the pair-level K-check that's supposed to police them never fires.

While this requires a specific reserve-asset LT whose `exchangeRate()` is attacker/creator-influenced high enough to zero out `virtualLtReserve`, the reserve asset is explicitly an *external* BounceTech LT chosen by the token creator at `Zap.createToken` time — the creator picks `ltAddress` from any LT registered in `Factory.ltExists`, and BounceTech LTs are rebasing/leveraged tokens whose `exchangeRate()` legitimately grows over the LT's lifetime (documented in `docs/contracts-scope.md`'s "Exchange-rate freshness" section). A sufficiently mature/high-rate LT crossing the truncation boundary reaches this path through the fully permissionless `Zap.createToken` entry point with no privileged role required.

### Impact Explanation
A `k == 0` pair permanently breaks the AMM invariant for that token's curve. Once minted this way, `Router.buy`/`Router.sell` compute nonsensical `tokensOut`/`assetOut` (division by/of zero-derived `k`), and `Pair.swap`'s invariant check can never reject an incorrect trade. This can be exploited to drain the pair's real token/LT balances for free or mint unbacked amounts, directly threatening trader/LP funds on that specific launched token — a concrete theft/freezing vector as required by the validation criteria.

### Likelihood Explanation
Requires the creator to pair a token against an LT whose current `exchangeRate()` is high enough that `(VIRTUAL_LIQUIDITY_USD * 1e18) / exchangeRate` truncates to `0` — i.e. `exchangeRate() > VIRTUAL_LIQUIDITY_USD * 1e18`. Given `VIRTUAL_LIQUIDITY_USD` is a fixed protocol constant (documented as ~$3K-equivalent) and BounceTech LTs are leveraged/rebasing tokens whose rate compounds over time, this boundary is reachable as LTs mature, without needing any privileged action beyond a normal `Zap.createToken` call. I could not fully verify the exact numeric value of `VIRTUAL_LIQUIDITY_USD` or find an explicit test exercising this truncation boundary in the indexed code, so I can't confirm today's exact distance to the boundary for a real deployed LT — this is a gap in what I could verify from the index.

### Recommendation
Add an explicit `if (virtualLtReserve == 0) revert ZeroExchangeRate();` (or a dedicated error) immediately after computing `virtualLtReserve` in `_deployAndSeed`, and additionally harden `Pair.mint` to revert on `tokenReserve == 0 || assetReserve == 0` as a defense-in-depth floor, independent of what the caller passes.

### Proof of Concept
1. BounceTech's LT `L` reaches (or a malicious/attacker-deployed mock/compromised LT reports) `exchangeRate() > VIRTUAL_LIQUIDITY_USD * 1e18`.
2. Creator calls `Zap.createToken({..., ltAddress: L, ...}, seedUsdcAmount)` (≥ `MIN_SEED_USDC`, fully permissionless).
3. `Bonding.launch` → `_deployAndSeed` computes `virtualLtReserve = (VIRTUAL_LIQUIDITY_USD * 1e18) / exchangeRate() == 0`; passes the `ExchangeRateTooLow` upper-bound check (0 is not `> type(uint112).max/4`); reaches `router.addInitialLiquidity(tokenAddr, totalSupply, curveSupply, 0)`.
4. `Pair.mint(totalSupply, 0)` sets `_pool.k = 0`.
5. Any subsequent `Zap.buy`/`Zap.sell` on this token routes through `Router._computeBuy`/`_computeSell` against a pair whose `k == 0` and whose `swap` K-check `(newTokenReserve+1)*(newAssetReserve+1) < 0` never reverts, allowing extraction of the pair's real token/LT balances at economically incorrect (effectively free) prices.
