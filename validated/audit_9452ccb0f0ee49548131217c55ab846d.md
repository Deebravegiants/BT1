### Title
Authorization bypass for `blockOwnerDeletion` via UID-only indexing in `newBlockingOwnerDeletionRefs`/`indexByUID` - ([File: plugin/pkg/admission/gc/gc_admission.go])

### Summary
`indexByUID` builds a map of old owner references keyed solely on `types.UID`, ignoring `Kind`/`Name`. Because `metav1.OwnerReference.UID` is a user-supplied, unvalidated string (not verified against a real object's UID at admission time), an attacker who once legitimately obtained a blocking owner reference to an authorized owner can later reuse that same UID value on a distinct, unauthorized owner reference and have `newBlockingOwnerDeletionRefs` treat it as a pre-existing (already-authorized) ref, skipping the per-owner delete/finalizer authorization check entirely.

### Finding Description
`gcPermissionsEnforcement.Validate` (plugin/pkg/admission/gc/gc_admission.go:89) computes `newBlockingOwnerDeletionRefs(attributes.GetObject(), attributes.GetOldObject())` to determine which `ownerReferences` entries are newly set to `blockOwnerDeletion=true`, and only those newly-blocking refs go through the per-owner authorization loop at lines 138-152 (`ownerRefToDeleteAttributeRecords` + `a.authorizer.Authorize`).

`newBlockingOwnerDeletionRefs` (lines 258-294) determines "new" by looking up each new blocking ref in `indexedOldRefs := indexByUID(oldMeta.GetOwnerReferences())` (line 280). `indexByUID` (lines 248-254) builds `map[types.UID]metav1.OwnerReference` keyed **only** by `ref.UID`, silently overwriting/matching regardless of `Kind`/`Name`. If a lookup by UID succeeds and the previously found old ref already had `BlockOwnerDeletion=true`, the code treats the new ref as *not newly blocking* (`wasNotBlocking == false`) and does **not** add it to the returned list — meaning it is never passed to the authorization check.

`ownerReference.UID` is not cross-validated against the actual UID of the referenced object at admission time; `ValidateOwnerReferences` (staging/src/k8s.io/apimachinery/pkg/api/validation/objectmeta.go:97-114) only checks that `UID` is non-empty, not that it corresponds to a real object of the stated `Kind`/`Name`. This lets an attacker fully control the `UID` string on an owner reference.

Exploit flow against a resource the attacker can update (e.g. a CSR they own):
1. Attacker legitimately adds ownerReference `{UID: X, Kind: A, Name: authorized, blockOwnerDeletion: true}` where they hold delete/finalizer permission on `A/authorized`. This passes admission normally.
2. Attacker issues a second update replacing that reference with `{UID: X, Kind: B, Name: unauthorized, blockOwnerDeletion: true}`, keeping the same UID value `X` but pointing at a different, unauthorized owner.
3. `isChangingOwnerReference` detects the change (Kind/Name differ), so the blocking-ref check runs.
4. `indexByUID(oldRefs)[X]` returns the *old* Kind-A ref (which was already blocking), so `wasNotBlocking` is `false`, and the new Kind-B ref is dropped from `newBlockingRefs`.
5. The authorization loop at lines 138-152 never evaluates the Kind-B owner, so the update succeeds without the attacker ever proving delete/finalizer permission on `B/unauthorized`.

### Impact Explanation
This is an authorization-check bypass in the `OwnerReferencesPermissionEnforcement` admission plugin. `blockOwnerDeletion=true` causes the referenced owner's deletion to be blocked (via a foreground-deletion finalizer) until the dependent is removed — a capability normally gated on the requester having delete/finalizer permission on that owner. Exploiting this lets an unprivileged user attach an un-authorized blocking reference to an arbitrary owner object (of any kind/namespace they can name), potentially blocking or interfering with deletion of resources they have no rights over — a control-plane authorization bypass (RBAC/authorizer bypass class).

### Likelihood Explanation
Requires only: (1) create/update rights on some resource supporting ownerReferences (e.g., CSR) and (2) at some point having (or being granted) legitimate blockOwnerDeletion authorization to any one object — a very low bar, and often already true for a user's own resources. The rest of the exploit is a simple two-step API update sequence, fully reproducible and deterministic.

### Recommendation
Change `indexByUID` (and its use in `newBlockingOwnerDeletionRefs`) to index/compare on the full owner identity (`APIVersion`, `Kind`, `Name`, `UID`) rather than `UID` alone, e.g. use a struct key of `{APIVersion, Kind, Name, UID}` so that a UID collision across distinct owner kinds/names cannot be conflated with an already-authorized reference.

### Proof of Concept
Unit test in `plugin/pkg/admission/gc/gc_admission_test.go`:
1. Construct `oldObj` metadata with `OwnerReferences: [{UID: "X", Kind: "A", Name: "authorized", BlockOwnerDeletion: true}]`.
2. Construct `newObj` metadata with `OwnerReferences: [{UID: "X", Kind: "B", Name: "unauthorized", BlockOwnerDeletion: true}]`.
3. Call `newBlockingOwnerDeletionRefs(newObj, oldObj)` and assert it currently returns an empty slice (bug) instead of `[{UID:"X", Kind:"B", Name:"unauthorized", ...}]` (expected/fixed behavior).
4. End-to-end: run `gcPermissionsEnforcement.Validate` with a fake authorizer that denies delete/finalizers on Kind B but allows on Kind A, over the old→new update above, and assert it currently returns `nil` (bypass) instead of `admission.NewForbidden(...)`.
