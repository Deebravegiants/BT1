This confirms the vulnerability. No index/destination-based disambiguation exists anywhere in the call chain — `createWithdrawalIdentifiers` assigns a per-bridge sequential `index` to each `WithdrawalIdentifier`, but that `index` is never used in `describeWithdrawal`. `watchWithdrawal` polls each `WithdrawalIdentifier` independently, calling `bridge.describeWithdrawal({...wid})` for each one, so with two same-token withdrawals in a batch, both `watchWithdrawal` calls hit `poaBridge.httpClient.getWithdrawalStatus` with the *same* `tx.hash`, get the *same* `response.withdrawals` array, and both go through `findMatchingWithdrawal` which does `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)` — always returning the *first* array entry matching that token, for both identifiers.

### Title
`findMatchingWithdrawal` in PoaBridge matches only by assetId, causing both withdrawals in a same-token batch to report the first one's status/txHash - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves per-withdrawal status via `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which uses `Array.prototype.find` keyed solely on `nep141:<near_token_id> === assetId`. When a batch contains two withdrawals of the same PoA token to two different destination addresses/amounts, both `WithdrawalIdentifier`s (index 0 and index 1) produce identical `poaBridge.httpClient.getWithdrawalStatus({withdrawal_hash: tx.hash})` responses, and both resolve to the same (first-matched) entry — misreporting the second withdrawal's status/txHash as the first one's.

### Finding Description
The broken equality: the code assumes `withdrawal.destinationAddress/amount == args.withdrawalParams.destinationAddress/amount` for the matched entry, but the match key is only `assetId`, so for two withdrawals of the same token this equality can fail silently while the code still returns a "completed" status with a `txHash`.

Path:
1. User (or integrator on user's behalf) calls `sdk.processWithdrawal` / `signAndSendWithdrawalIntent` with `withdrawalParams: [ {assetId: "nep141:arb-0xaf88d...omft.near", destinationAddress: A, amount: X}, {assetId: "nep141:arb-0xaf88d...omft.near", destinationAddress: B, amount: Y} ]` (same token, two different destinations — e.g., a "split withdrawal" or two unrelated users' withdrawals batched by an integrator's backend). [1](#0-0) 
2. `createWithdrawalIdentifiers` assigns `index: 0` and `index: 1` (per-bridge counter) to each `WithdrawalIdentifier`, but `index` is never propagated into the POA HTTP request or into the matching logic. [2](#0-1) 
3. `watchWithdrawal` polls `bridge.describeWithdrawal({...wid})` independently for each identifier. [3](#0-2) 
4. `describeWithdrawal` calls `getWithdrawalStatusWithRetry` keyed by `args.tx.hash` — identical for both identifiers since they share the same batch intent tx — returning the same `response.withdrawals` array for both calls. [4](#0-3) 
5. `findMatchingWithdrawal` matches only by `nep141:<near_token_id> === assetId` via `.find()`, so it returns the *same first* array entry for both identifiers when the assetId is identical. The comment in the code explicitly acknowledges this: "multiple withdrawals of the same token in a single transaction are not supported." [5](#0-4) 
6. When the API returns `COMPLETED` with a `transfer_tx_hash` for that first entry, `describeWithdrawal` returns `{status: "completed", txHash: withdrawal.data.transfer_tx_hash}` for *both* identifiers, even though the second withdrawal's actual on-chain destination/status is different (or still pending). [6](#0-5) 

No guard exists: `validateAddress`/`compareAddresses` only run at withdrawal-creation time and don't touch status matching; `supports()` ordering is irrelevant here; there is no `assert` in `findMatchingWithdrawal` preventing duplicate assetId batches; the intents contract's own nonce/signature checks don't detect this because the mis-happens entirely client-side after settlement, in status querying.

### Impact Explanation
An integrator that batches multiple withdrawals of the same PoA token (e.g., paying out several users' balances of the same token in one intent, or a single user's split withdrawal to two addresses) will have `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` resolve **both** promises as `completed` with the **same** `txHash`, even though only one destination actually received funds. This causes the integrator to incorrectly credit or mark-as-paid the second (still-pending or differently-destined) withdrawal based on the first's proof, which is a status/hash misreport that can lead to double-crediting or a stuck/incorrectly-reconciled payout — matching the "High" impact category ("a status or hash misreport making an integrator credit or refund twice"). This is repeatable on every batch containing duplicate-assetId PoA withdrawals.

### Likelihood Explanation
Precondition: the attacker/integrator only needs to construct a batch (`WithdrawalParams[]`) containing two or more entries with the same PoA `assetId` (same token) but different destination addresses/amounts — this is fully within normal SDK usage, not a documented escape hatch, and nothing in `supports()`, `validateWithdrawal()`, or `createWithdrawalIdentifiers()` rejects or dedups such batches. Cost is a single normal withdrawal intent; feasible for any ordinary caller of `processWithdrawal`/`waitForWithdrawalCompletion`; fully repeatable per batch.

### Recommendation
Disambiguate `findMatchingWithdrawal` beyond `assetId` — e.g. use the `index` already computed in `createWithdrawalIdentifiers` combined with sorting both the API's `withdrawals` list and the corresponding `withdrawalParams` by amount (as the existing code comment suggests) for same-token entries, or reject/throw when a batch contains duplicate-assetId POA withdrawals until the POA API supports disambiguation, so `describeWithdrawal` never silently attaches one withdrawal's result to another's identifier.

The correct/expected behavior (equality that should hold) is that each `WithdrawalIdentifier` resolves to a status/txHash tied to its own `destinationAddress`/`amount`, which this test demonstrates is violated.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
