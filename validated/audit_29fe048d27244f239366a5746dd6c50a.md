### Title
User-controlled route pool addresses can inject unauthorized token transfers into the caller’s signed authorization tree - (File: contracts/swap-aggregator/src/execute/mod.rs)

### Summary
The router interprets the caller-supplied route payload as an executable instruction stream and uses registry entries as pool contract addresses without restricting them to known DEX venues. During a controller strategy such as `swap_collateral`, a malicious route can therefore place arbitrary contract code below the caller’s authorized invocation. That code may perform token transfers from the caller which Soroban records as children of the caller’s authorization tree; if the caller signs the simulated tree containing that child, unrelated wallet assets can be transferred to an attacker even though the lending operation itself settles correctly. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_collateral(caller, account_id, current, amount, new, swap)` accepts caller-controlled route bytes and requires authorization from the account owner or delegate. [3](#0-2) [4](#0-3)  The controller passes those bytes to the configured aggregator and authorizes only the expected input-token transfer from the controller to the router. [5](#0-4) 

Inside the aggregator, each swap instruction resolves `pool`, `token_in`, and `token_out` directly from the attacker-controlled `assets` registry. [6](#0-5)  Route validation checks index bounds, token-chain structure, and split-weight ranges, but does not check that `idx_a` names a deployed venue owned by the claimed DEX or appear on an allowlist. [7](#0-6)  Venue adapters then invoke methods on the supplied pool address; for example, the Phoenix adapter calls that address’s `swap` function, while Aquarius calls `swap` on the supplied pool. [8](#0-7) [9](#0-8) 

Because the route selects the invoked contract, it can select a malicious contract whose ABI satisfies the adapter. That contract executes while the original user’s authorization context is active. A malicious pool can call an unrelated token’s `transfer(victim, attacker, amount)`. Soroban simulation records that transfer under the caller’s strategy authorization, and enforced authorization accepts it when the signed tree contains the recorded child. [10](#0-9) 

### Impact Explanation
The measured-output checks protect only the routed input and output balances; they do not prevent route-selected code from invoking other contracts beneath the user’s authorization. The test demonstrates that a rogue pool can drain a wallet token that the lending protocol never listed, while the swap still produces the expected collateral output. [11](#0-10) 

The impact is theft of user funds beyond the strategy input amount. The attacker’s loss is bounded neither by the route minimum output nor by the controller’s final account-risk checks. The transaction can leave the victim’s lending position solvent and correctly swapped while simultaneously transferring unrelated wallet assets to the attacker.

### Likelihood Explanation
An unprivileged user can submit the affected controller strategy with arbitrary route bytes, and a route can name any contract address through the payload registry. [12](#0-11) [13](#0-12)  Exploitation requires the victim to authorize the invocation tree containing the malicious child transfer. A malicious quote-generation path or compromised route source can cause an ordinary client to present that tree for signing; the test confirms that signing the simulated child authorizes the theft. [2](#0-1) 

This is a real authorization-scope weakness rather than merely poor route pricing: the unauthorized call is introduced through an input interpreted as a contract target, analogous to untrusted input reaching a command interpreter.

### Recommendation
Restrict executable route targets before dispatch:

- Maintain an allowlist or registry of approved venue pool contracts, or bind each route operation to a verified pool identity rather than accepting an arbitrary registry address.
- Reject any `Swap`, `Mint`, or `Burn` operation whose pool address is not an expected venue deployment.
- Where practical, validate pool metadata such as token addresses through trusted venue factories instead of asking the untrusted pool itself.
- On the controller boundary, reject route encodings that can invoke addresses outside the configured route universe.
- As defense in depth, clients should simulate and reject authorization trees containing children other than the expected strategy input transfer, but contract-level pool validation is the protocol-side fix.

### Proof of Concept
The repository contains a reproducer using a malicious pool and a strategy route:

1. Alice has supplied `10_000 USDC` and holds `77_770_000_000` units of an unrelated wallet token.
2. A route supplied to `swap_collateral` names a deployed `RogueHopPool`.
3. During simulation, the rogue pool executes `token.transfer(alice, attacker, WALLET_BALANCE)`.
4. The unauthorized transfer is recorded as a child beneath Alice’s `swap_collateral` authorization, and Alice’s wallet balance is reduced to zero while the attacker receives the tokens.
5. With an honest authorization tree, the same transfer is rejected; when Alice signs the recorded poisoned tree, it succeeds.

The relevant test demonstrates the malicious pool call and its authorization behavior. [14](#0-13) [15](#0-14) [16](#0-15)

#[test]
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    let stolen_transfer = MockAuthInvoke {

        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
