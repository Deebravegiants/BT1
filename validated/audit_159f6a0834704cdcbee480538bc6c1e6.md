Analog identified in the relayer-fee withdrawal flow, matching the original "unvalidated receiver, funds already burned upfront" bug class.

### Title
Unvalidated relayer withdrawal beneficiary permanently forfeits accrued fees - (File: modules/pallets/relayer/src/withdrawal.rs)

### Summary
`pallet-relayer`'s `Pallet::withdraw` lets any relayer sign a cross-chain withdrawal message for their accrued fees and specify an arbitrary destination `beneficiary` address. This address is never validated (no non-zero check, no length/format check beyond what ABI packing tolerates) before the pallet permanently commits to the withdrawal: it increments the relayer's nonce and dispatches an irrevocable ISMP POST request instructing the destination chain to pay out `available_amount` to that address.

### Finding Description
`WithdrawalInputData.beneficiary` is an optional, freely chosen `Vec<u8>` supplied by the relayer when signing the withdrawal message: [1](#0-0) 

`Pallet::withdraw` uses this value directly as `beneficiary_address` with no sanity check (e.g. rejecting the zero address or malformed byte length) before it:
1. Reads and does not yet clear `available_amount`,
2. Irreversibly increments `Nonce` for the relayer (making the same claim non-repeatable),
3. Builds the ABI-encoded `WithdrawalParams` (for EVM destinations) or `WithdrawalRequest` (for substrate destinations) using the unchecked beneficiary, and
4. Dispatches an ISMP POST request to the destination host/pallet to execute the payout: [2](#0-1) 

On the EVM side, the payload is the `WithdrawalParams` struct (`beneficiary_address`, `amount`, `token`), which is ABI-encoded and dispatched to the destination `HostManager` with no additional receiver validation performed on that side either: [3](#0-2) 

The test suite exercises this path by constructing a `WithdrawParams` with a randomly generated `beneficiary_address` and calling `HostManager.onAccept` to confirm the fee-token balance is decremented and paid out to that address — with no validation step demonstrated anywhere in the flow: [4](#0-3) 

Because the relayer's nonce is bumped and the ISMP request is dispatched irrevocably once `withdraw` is called, there is no mechanism to cancel, edit, or retry with a corrected beneficiary if the supplied address is wrong (e.g. the zero address, a malformed 20-byte value, or a typo'd address the relayer does not control). This is the same root cause as the referenced report: the receiver is unvalidated and the underlying claim/commitment is consumed upfront with no reversibility.

### Impact Explanation
If a relayer signs a withdrawal with an incorrect or zero beneficiary address, the entire accrued relayer-fee balance for that (relayer, dest_chain) pair is permanently and unrecoverably lost once the cross-chain message settles — either burned to the zero address on the EVM destination, or (for a malformed non-20-byte value) potentially causing decode/ABI issues at the destination that could still leave `Fees` state inconsistent while the nonce has already advanced, blocking any retried claim. This is a permanent freezing/loss of legitimately earned relayer funds, which are a scarce, real economic asset tracked by the Hyperbridge protocol's fee-accounting pallet — reachable directly and unprivilegedly by any relayer calling `withdraw`.

### Likelihood Explanation
Likelihood is driven by user/relayer error rather than malice, but it requires no special privilege, no governance action, and no unusual conditions — any relayer with `Fees` above the minimum withdrawal threshold can trigger the vulnerable path via a single signed extrinsic. Given this is a routine, frequently-used self-service operation (relayers withdraw earned fees regularly), the probability of an eventual fat-fingered or malformed beneficiary is non-trivial, and the consequence is total, irreversible loss of the withdrawn balance.

### Recommendation
- Reject withdrawals where `beneficiary` decodes to the zero address (or the chain-appropriate "burn"/invalid sentinel) for both EVM (20-byte) and substrate (32-byte `AccountId32`) destinations, before incrementing `Nonce` or dispatching the ISMP request.
- Enforce strict length validation on `beneficiary: Option<Vec<u8>>` matching the destination chain's expected address width (20 bytes for EVM `H160`, 32 bytes for `AccountId32`) instead of relying on best-effort conversions downstream.
- Consider defaulting to the relayer's own on-chain address when no beneficiary is supplied (already done), and requiring an explicit re-confirmation step or a short timelock before dispatch when a non-default beneficiary is used, so mistakes can be caught before the nonce/commitment becomes irreversible.

### Proof of Concept
1. A relayer accrues fees for `dest_chain = Evm(1)` via `pallet-relayer`'s fee-accumulation flow (`Fees::<T>::get`).
2. The relayer calls `Pallet::withdraw` with a `WithdrawalInputData` whose `beneficiary = Some(vec![0u8; 20])` (the zero address) — see `WithdrawalInputData` and `withdraw` in [5](#0-4) . No check rejects this value.
3. `Nonce` is incremented (line 127-131) and a `WithdrawalParams { beneficiary_address: [0u8;20], amount, token }` is ABI-encoded and dispatched via ISMP to the EVM `HostManager` (mirrors the flow validated in `evm/tests/rust/src/tests/host_manager.rs::test_host_manager_withdraw`, lines 81-118, which shows `HostManager.onAccept` unconditionally transferring `amount` to whatever `beneficiary_address` was supplied).
4. Once the ISMP request is delivered and processed, `available_amount` of the fee token is sent to the zero address on the destination chain and is permanently lost; the relayer's nonce has already advanced, so the same claim cannot be reissued and no corrective action is possible.

	/// Signature data to prove account ownership

	/// Chain to withdraw funds from
	pub dest_chain: StateMachine,
	/// The withdrawal beneficiary
	pub beneficiary: Option<Vec<u8>>,

impl<T: Config> Pallet<T>
where
	<T as frame_system::Config>::Hash: From<H256>,
	<T as frame_system::Config>::AccountId: From<[u8; 32]>,
	T::Balance: Into<u128>,
{
	pub fn withdraw(withdrawal_data: WithdrawalInputData) -> DispatchResult {
		let address = match &withdrawal_data.signature {
			Signature::Evm { address, .. } => address.clone(),
			Signature::Sr25519 { public_key, .. } => public_key.clone(),
			Signature::Ed25519 { public_key, .. } => public_key.clone(),
		};

		let nonce = Nonce::<T>::get(address.clone(), withdrawal_data.dest_chain);
		let msg = message(nonce, withdrawal_data.dest_chain, withdrawal_data.beneficiary.clone());

		match &withdrawal_data.signature {
			Signature::Evm { address, .. } => {
				let eth_address = withdrawal_data
					.signature
					.verify(&msg, None)
					.map_err(|_| Error::<T>::InvalidSignature)?;
				if &eth_address != address {
					Err(Error::<T>::InvalidPublicKey)?
				}
			},
			Signature::Sr25519 { .. } => {
				// Verify signature with public key provided in signature enum
				withdrawal_data
					.signature
					.verify(&msg, None)
					.map_err(|_| Error::<T>::InvalidSignature)?;
			},
			Signature::Ed25519 { .. } => {
				// Verify signature with public key provided in signature enum
				withdrawal_data
					.signature
					.verify(&msg, None)
					.map_err(|_| Error::<T>::InvalidSignature)?;
			},
		};
		let available_amount = Fees::<T>::get(withdrawal_data.dest_chain, address.clone());

		if available_amount <
			Self::min_withdrawal_amount(withdrawal_data.dest_chain)
				.unwrap_or(MinWithdrawal::get())
		{
			Err(Error::<T>::NotEnoughBalance)?
		}

		let dispatcher = <T as Config>::IsmpHost::default();

		Nonce::<T>::try_mutate(address.clone(), withdrawal_data.dest_chain, |value| {
			*value += 1;
			Ok::<(), ()>(())
		})
		.map_err(|_| Error::<T>::ErrorCompletingCall)?;

		let beneficiary_address = withdrawal_data.beneficiary.clone().unwrap_or(address.clone());
		let (to, body) = match withdrawal_data.dest_chain {
			s if s.is_substrate() => (
				HYPERBRIDGE_MODULE_ID.to_vec(),
				Message::WithdrawRelayerFees(WithdrawalRequest {
					amount: available_amount.low_u128(),
					account: AccountId32::try_from(&beneficiary_address[..])
						.map_err(|_| Error::<T>::InvalidPublicKey)?,
				})
				.encode(),
			),
			_ => {
				let HostParam::EvmHostParam(params) =
					HostParams::<T>::get(withdrawal_data.dest_chain)
						.ok_or_else(|| Error::<T>::MissingMangerAddress)?;

				let body = WithdrawalParams {
					beneficiary_address: beneficiary_address.clone(),
					amount: available_amount.into(),
					token: params.fee_token,
				}
				.abi_encode()
				.map_err(|_| Error::<T>::InvalidPublicKey)?;

				(params.host_manager.0.to_vec(), body)
			},
		};

pub struct WithdrawalParams {
	/// 20-byte EVM beneficiary address. Stored as a `Vec<u8>` so the SCALE
	/// extrinsic input doesn't have to pre-validate the length.
	pub beneficiary_address: Vec<u8>,
	/// Amount to withdraw, in the token's smallest unit.
	pub amount: U256,
	/// ERC20 token contract to withdraw. The EVM host treats the zero address
	/// as the chain's native asset.
	pub token: H160,
}

impl WithdrawalParams {
	/// Encode the withdrawal request as the EVM host expects: a single action
	/// byte (`0`) followed by the ABI-encoded `WithdrawParams` tuple.
	pub fn abi_encode(&self) -> Result<Vec<u8>, anyhow::Error> {
		let abi: WithdrawParamsAbi = self.try_into()?;
		let variant = vec![0u8]; // host manager action: withdraw
		Ok([variant, abi.abi_encode()].concat())
	}
}
