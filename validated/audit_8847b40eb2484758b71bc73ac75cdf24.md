### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header is trusted for tenant identity but not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from the `X-Shopify-Shop-Domain` header, but the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` verifies is computed only over the raw request body. The shop-domain header (along with `topic` and `webhook-id`) is never part of the signed material, so an attacker who possesses one *validly signed* webhook payload can replay it with a different `X-Shopify-Shop-Domain` header and have the app attribute that body to an arbitrary shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header: [2](#0-1) 

`Registry.process` validates the HMAC over that same `to_signable_string` (body-only) and, once it passes, hands `request.shop` straight to the app's handler as the authoritative tenant identity for the webhook: [3](#0-2) 

`HmacValidator.validate` simply recomputes the HMAC over `verifiable_query.to_signable_string` and compares it to the supplied `hmac`: [4](#0-3) 

This reproduces the report's bug class exactly: a field that is *acted on* (the `shop` used to route/attribute the webhook to a tenant) is not covered by the cryptographic check (the HMAC only binds the body bytes). The equality the gem implicitly assumes but never enforces is:
`hmac == HMAC(secret, body)` implies `shop_header == shop_that_actually_sent(body)`

That implication is false: `hmac` only proves the body came from Shopify for *some* shop that owns that body — it says nothing about which shop-domain header accompanies it.

### Impact Explanation
An unprivileged actor who legitimately operates their own Shopify store (Shop A) and therefore legitimately receives real, validly-HMAC-signed webhook deliveries for Shop A, can capture one such delivery (body + valid HMAC) and resend it to the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` header to Shop B (a victim tenant). The HMAC check still passes because it only checks the body, and `Registry.process` forwards `shop: "shop-b.myshopify.com"` (attacker-chosen) together with Shop A's real body to the handler. Any host app that uses `WebhookMetadata#shop` (the gem's documented API surface, see `docs/usage/webhooks.md`) to select which shop's session/data to update will now write/act on Shop A's payload under Shop B's tenant context — a cross-tenant data-confusion/injection primitive achievable without ever needing `api_secret_key` or a stolen access token.

### Likelihood Explanation
The prerequisite is only that the attacker owns/controls at least one shop that has the app installed (a normal, unprivileged merchant) and can capture their own webhook traffic and issue a raw HTTP POST to the app's public webhook route with modified headers — no credentials, TLS interception, or app secret needed. This is a realistic, moderately easy attack for any customer of a multi-tenant app.

### Recommendation
Include the identity-critical headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the signed body (e.g., verify the shop domain against a separately stored per-shop secret/session before trusting it), so that the shop attribution cannot be altered independently of the signed payload.

### Proof of Concept
1. App has two installed shops: `shop-a.myshopify.com` (attacker-controlled) and `shop-b.myshopify.com` (victim).
2. Shopify delivers a legitimate webhook to the app for `shop-a`: body `B`, header `X-Shopify-Shop-Domain: shop-a.myshopify.com`, header `X-Shopify-Hmac-Sha256: H` where `H = HMAC_SHA256(secret, B)`.
3. Attacker (who received this webhook because it is theirs) resends an HTTP POST to the same webhook endpoint with the identical body `B` and identical `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC_SHA256(secret, B)` and matches `H` — validation **passes** because the domain header was never part of the signed string (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
5. `Registry.process` invokes the app handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to process/attribute shop A's data as belonging to shop B.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
