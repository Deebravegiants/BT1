### Title
Webhook `shop-domain` header (and `topic`, `webhook-id`, `api-version`) is verified against a different byte-string than the HMAC covers, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` from HTTP headers, but `Utils::HmacValidator.validate` only checks the HMAC signature over `@raw_body` (`to_signable_string`). None of the identity-carrying headers are covered by the signature, so the "bytes verified" and "bytes acted on" diverge — an attacker who has (or observes) any single genuine `(raw_body, hmac)` pair for one shop can replay it to the app's webhook endpoint while substituting the `shop-domain` header for a different tenant, and the signature check still passes.

### Finding Description
`Registry.process` gates all webhook handling on a single call: [1](#0-0) 

The HMAC check only validates `request.hmac` against `Utils::HmacValidator.validate(request)`, which computes the signature over `to_signable_string`: [2](#0-1) 

`to_signable_string` returns only `@raw_body` — none of the shop, topic, webhook-id, or api-version headers are part of the signed payload: [3](#0-2) 

Yet `shop`, `topic`, `api_version`, and `webhook_id` — all read straight from attacker-controlled request headers — are exactly the fields the gem hands to the host application's handler as trusted, authenticated metadata: [4](#0-3) 

This is precisely the bug class described in the external report: a value acted upon downstream (`finalBonus`/`schnibblesTotal` there; `shop`/`topic`/`webhook_id` here) is not actually protected by the integrity check that is assumed to bind it (`schnibblesTotal` cast vs. actual sign; here, HMAC-signed bytes vs. header bytes). The equality the gem implicitly assumes but does not enforce is:

`bytes_verified_by_HMAC == bytes_the_handler_trusts_as_the_shop/topic/webhook_id`

but in reality `bytes_verified_by_HMAC = raw_body` while `bytes_the_handler_trusts = headers`, which are disjoint and independently attacker-controllable at the HTTP layer, since HTTP headers are not part of the signed message.

### Impact Explanation
Any party who can capture one legitimate `(body, x-shopify-hmac-sha256)` pair — for example by receiving a real webhook to a shop they control, or intercepting one over an unencrypted/misconfigured link, or via a genuine webhook the app already delivered publicly — can POST that same body+HMAC to the app's webhook endpoint while setting `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) to a **different, victim shop**. `Registry.process` will accept it because `HmacValidator.validate` only checks the body bytes, and will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop. If the host application uses that `shop` value to look up a session/access token and act on the merchant's data (a documented, expected usage pattern for `WebhookHandler#handle`), this causes cross-tenant data confusion/injection: data or actions belonging to one merchant get attributed to another merchant's session. This satisfies the Critical "cross-tenant access" impact category, since it breaks the tenant isolation boundary that the HMAC is supposed to enforce.

### Likelihood Explanation
No `api_secret_key`, access token, or privileged access is required — the attacker only needs one previously-observed valid webhook payload+HMAC pair (trivially obtainable by operating their own free development store subscribed to the same app, since HMAC replay does not require secret knowledge, only a captured signed body). The webhook endpoint is a public, unauthenticated HTTP endpoint by design. The only gem-side check (`Registry.process` → `HmacValidator.validate`) is bypassed because it never covers the header fields being spoofed.

### Recommendation
Include the security-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signed/verified payload, or otherwise cryptographically bind them to the body before trusting them:
- Change `Webhooks::Request#to_signable_string` to build the same string Shopify signs (i.e. confirm Shopify's HMAC actually only signs the body — if so, the gem must not expose `shop`/`topic`/`webhook_id` as trusted fields without additional binding), or
- At minimum, document/enforce that consuming apps must treat `WebhookMetadata#shop` as merely a routing hint and re-derive the authoritative shop identity from a source that is covered by the signature (e.g., validate that the resource referenced in `body` actually belongs to the claimed shop before acting), and add replay protection (e.g., dedupe on `webhook_id` plus a freshness/timestamp check) since currently nothing prevents byte-for-byte replay of an old, validly-signed webhook under a different shop header.

### Proof of Concept
```ruby
require "shopify_api"

ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", host: "example.com",
  scope: "read_products", is_embedded: false, api_version: "2024-01", is_private: false)

# 1. Attacker legitimately receives (or otherwise obtains) ONE real webhook for shop-a.myshopify.com
raw_body = '{"id":1,"note":"hello"}'
real_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# 2. Attacker replays the EXACT same body+hmac to the app's webhook endpoint,
#    but swaps the shop-domain header to a victim shop the attacker does not control.
spoofed_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => real_hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled value
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: spoofed_headers)

# HmacValidator.validate only checks raw_body against real_hmac -> passes,
# even though shop/topic/webhook_id are unauthenticated attacker input.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
```
