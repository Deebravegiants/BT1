### Title
Signature Replay via Nonce-Incremented-After-Dispatch in `pallet-hyper-fungible-token` Calldata Execution - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
The `on_accept` handler in `pallet-hyper-fungible-token` executes an attacker-controlled cross-chain `runtime_call` under a signature that is bound only to `(account_nonce, runtime_call)`, but increments the account nonce only **after** the arbitrary call has been dispatched. This mirrors the reported bug class: a privileged, signature-gated operation is executed before its replay-protection nonce is advanced, so if execution can be re-entered (or the dispatched call otherwise interleaves further processing) before the increment happens, the same signed calldata can be replayed to repeat the privileged action.

### Finding Description
In `on_accept`, when an incoming cross-chain message carries `call_data`, the pallet:
1. Reads the beneficiary's current nonce: [1](#0-0) 
2. Verifies a signature over `(nonce, runtime_call)` for Ed25519/Sr25519/ECDSA schemes: [2](#0-1) 
3. Dispatches the arbitrary, attacker-supplied `runtime_call` as `origin`: [3](#0-2) 
4. Only **after** the dispatch succeeds does it increment the nonce: [4](#0-3) 

Because `runtime_call` is fully attacker-controlled (subject only to `BaseCallFilter`), and the signature check is bound solely to `(nonce, runtime_call)` rather than to the specific incoming message/commitment, any execution path that allows a second `on_accept` invocation carrying the identical `(nonce, runtime_call, signature)` triple to run before line 202 executes for the first invocation will pass signature verification a second time and re-dispatch the privileged call. This is architecturally the same flaw as the reported wallet bug: "the nonce is checked prior to calling `performOperation()`... but incremented after external calls are made," enabling reentrant replay.

Notably, the pallet-ismp request handler itself is aware of and defends against exactly this class of reentrancy for the *request receipt* — it explicitly stores the receipt **before** invoking `on_accept` and re-checks it immediately before dispatch to block reentrant re-delivery of the same request: [5](#0-4) . However, that protection only prevents replaying the *same* ISMP message commitment — it does not protect the HFT pallet's independent, weaker nonce scheme, which is bound to `(nonce, runtime_call)` and not to the message commitment at all. An attacker can therefore embed the identical `SubstrateCalldata{signature, runtime_call}` payload inside two or more distinct PostRequest messages (different bodies/commitments, so the request-receipt anti-replay does not block them), and if the first message's dispatched `runtime_call` can trigger processing of the second message before its own `inc_account_nonce` call executes, the same signature validates twice.

### Impact Explanation
If exploited, an attacker can cause a single valid off-chain signature over a privileged runtime call (e.g., a transfer, mint-adjacent, or governance-adjacent extrinsic permitted by `BaseCallFilter`) to be executed multiple times under the victim's identity, since the nonce that is supposed to bound the signature to a single use is not advanced until after dispatch. This can result in unauthorized repeated execution of privileged actions and, depending on the chosen `runtime_call`, theft/duplication of funds attributable to the signing account — a concrete impact matching "unauthorized app action" / "concrete theft of funds."

### Likelihood Explanation
Exploitation requires the attacker to control both the `runtime_call` payload and get it embedded in two distinguishable messages that route through `on_accept` before the nonce increment for the first completes. This requires a reachable reentry/interleaving path back into the HFT pallet's message handling from within a dispatched runtime call (e.g., via a call that itself triggers further ISMP request processing in the same call stack/batch). I was not able to fully confirm the exact interleaving primitive within the remaining investigation budget (the pallet-ismp dispatchable/extrinsic entry points were not located in the indexed content), so likelihood is assessed as **Medium** pending confirmation of a concrete reentry trigger, but the root-cause ordering flaw (privileged dispatch before nonce increment) is unambiguous and directly analogous to the reported bug class.

### Recommendation
Move `frame_system::Pallet::<T>::inc_account_nonce(origin)` to execute immediately after the signature is verified and before `runtime_call.dispatch(...)` is invoked, mirroring the report's suggested fix of incrementing the nonce before performing the operation. Additionally, consider binding the signature to the specific incoming message commitment (not just `(nonce, runtime_call)`) so that even parallel/duplicate messages cannot be crafted to reuse a signature.

### Proof of Concept
Conceptual PoC (exact reentry vector unverified due to indexing limits):
1. Attacker crafts a cross-chain message `M1` whose `call_data` contains `SubstrateCalldata { signature: sig, runtime_call: RC }`, where `sig` is a valid signature over `(N, RC)` for beneficiary account with current nonce `N`.
2. Attacker crafts a second message `M2` (different body/commitment) with the identical `SubstrateCalldata { signature: sig, runtime_call: RC }`.
3. `RC` is chosen such that, when dispatched by `M1`'s `on_accept`, it triggers processing of `M2` before `M1`'s `inc_account_nonce(origin)` call executes (line 202).
4. `M2`'s `on_accept` reads the beneficiary's nonce (still `N`, unincremented), re-verifies `sig` over `(N, RC)` successfully, and re-dispatches `RC`.
5. `RC` executes twice for one signature; repeat via further nested messages to multiply the effect. [6](#0-5)
