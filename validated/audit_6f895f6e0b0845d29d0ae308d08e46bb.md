### Title
Double-entry token lets one real deposit satisfy Hinkal's balance check at two `erc20TokenAddresses` indices, minting shielded UTXOs without backing - (File: contracts/Hinkal.sol)

### Summary
`Hinkal.transact` verifies solvency per index of `circomData.erc20TokenAddresses` by diffing `getBalancesForArray` snapshots taken via `balanceOf(address(this))` on the address stored at that index. Nothing in `dimensionsCheck`/`checkOnchainCreation` (contracts/HinkalHelper.sol) or in `Hinkal.transact` enforces that the addresses in `erc20TokenAddresses` are distinct, independent tokens, so an attacker can insert a second, attacker-deployed "mirror" token whose `balanceOf` reflects the real token's balance while its `transferFrom` is a no-op. A single real deposit then satisfies the per-index balance equality twice, letting the transaction mint shielded UTXO value for a token that never actually entered the vault.

### Finding Description
The invariant the code is meant to enforce, per index `i`, is:
```
balanceDif[i] == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount[i]
``` [1](#0-0) 

For an internal transact (`externalActionId == 0`), `_internalTransact` never populates `utxoSet` (that variable is only assigned in `_externalTransact`), so `utxoAmount` is always `0` for every index, reducing the check to `balanceDif[i] == amountChanges[i]`. [2](#0-1) [3](#0-2) 

`balanceDif[i]` is computed purely from `getBalancesForArray` snapshots, i.e. `IERC20(erc20TokenAddresses[i]).balanceOf(address(this))` taken before and after the transfers: [4](#0-3) 

Neither `dimensionsCheck` nor `checkOnchainCreation` in `HinkalHelper.sol` enforce uniqueness of `erc20TokenAddresses` entries — they only check array lengths and the `onChainCreation`/internal-transaction relationship: [5](#0-4) [6](#0-5) 

**Exploit:**
1. Attacker deploys a real (or wrapped) token `A` and a malicious "mirror" token `B` whose `balanceOf(vault)` is wired to return the same value as `A.balanceOf(vault)` (e.g. `B` simply forwards `balanceOf` calls to `A`, or both read a shared external ledger), but whose `transferFrom` is a no-op that always returns `true` without moving any value.
2. Attacker builds `circomData.erc20TokenAddresses = [A, B]`, `amountChanges = [X, X]`, `onChainCreation = [false, false]`, and crafts a valid proof (since the SNARK only constrains internal witness arithmetic such as `inTotal + amountChanges === outTotal` per its own tree bookkeeping, it does not verify real reserves) producing new off-chain UTXOs of value `X` for token `A` and value `X` for token `B`.
3. In `Hinkal.transact`: `oldBalances = [A.balanceOf(vault), B.balanceOf(vault)] = [b, b]` (both equal because `B` mirrors `A`).
4. `_internalTransact` runs: for index 0 (`A`), `deltaAmountChange = X > 0`, so it performs a real `safeTransferFrom` moving `X` real tokens `A` into the vault. For index 1 (`B`), `deltaAmountChange = X > 0`, so it calls `transferERC20TokenFromOrCheckETH(B, ...)`, which calls `B.transferFrom(...)`, a no-op that returns `true` without moving anything. [7](#0-6) 
5. `newBalances = [A.balanceOf(vault), B.balanceOf(vault)] = [b+X, b+X]` — because `B`'s balance mirrors `A`, it also shows `+X`, even though no real transfer occurred through `B`.
6. `balanceDif[A] = X == amountChanges[A]` ✓ and `balanceDif[B] = X == amountChanges[B]` ✓ — both checks pass, even though the vault only ever received `X` of real value once.
7. Off-chain UTXO commitments worth `X` (token `A`) + `X` (token `B`) are inserted into the tree, i.e. `2X` of shielded value is minted for only `X` of real backing.

The same mirroring trick also works on the withdrawal side (`deltaAmountChange < 0`), including through the relay branch with `variableRate`/`flatFee` set so `relayFee == 0`: a withdrawal of `X` real tokens via `A` (moving real value out) simultaneously depresses `B`'s mirrored balance, letting a fabricated withdrawal UTXO for `B` also satisfy `balanceDif[B] == amountChanges[B]` without any actual token `B` leaving the vault — draining value while the accounting believes it is balanced. Because the relay-fee split only affects how much of `sumAbs` goes to the relay vs. `externalActionData.externalAddress`, it does not change the fact that `balanceDif` for the mirrored index is derived from a `balanceOf` value that never independently reflects a distinct real transfer.

None of `performHinkalChecks`, `verifyProof`, `rootHashExists`, `insertNullifiers`, or `checkOnchainCreation` prevent this because: (a) they operate on the SNARK's own internal amount/nullifier/commitment consistency, not on real external balances; (b) the SNARK trusts `amountChanges`/`erc20TokenAddresses` as public inputs supplied by the attacker-prover and has no way to know that two addresses are economically the same underlying asset; (c) the only real-balance guard, the `balanceDif` check in `Hinkal.transact`, is evaluated independently per array index using `balanceOf`, which is exactly the value the attacker's mirror token is designed to corrupt.

### Impact Explanation
The attacker mints shielded UTXO value with no matching on-chain backing (deposit side) or drains real token value while accounting shows balance (withdrawal side). This is direct protocol insolvency: shielded balances tracked by Hinkal's Merkle tree no longer correspond to real reserves held by the contract, and other users' later withdrawals of legitimately-backed UTXOs can fail or be front-run to drain the shared pool. This matches the "Critical: minting shielded value without backing (protocol insolvency)" category. The attack is repeatable for every real deposit the attacker makes, doubling (or multiplying, with more mirror addresses) the shielded credit obtained per unit of real value.

### Likelihood Explanation
Preconditions: attacker must deploy their own `B` token contract (fully within attacker capability, no privileged role needed) and be able to generate a valid proof for their own UTXOs (also explicitly within the allowed attacker capabilities in this exercise). There is no admin/whitelist restriction on `erc20TokenAddresses` — any address can be used. The attack costs only gas plus the cost of the single genuine deposit `X`, and can be repeated at will, scaling the insolvency with each transaction.

### Recommendation
Enforce uniqueness of `erc20TokenAddresses` entries in `dimensionsCheck` (or in `Hinkal.transact` before computing balances), rejecting any transaction whose token address array contains duplicates or addresses that alias one another. More robustly, don't rely solely on `balanceOf` snapshots per declared address; require that the balance-diff check be tied to a canonical, immutable identity of the token (e.g., verified against a registry, or by transferring and checking balance change atomically per index using `SafeERC20`'s pre/post pattern anchored to a specific token identity that cannot be shared across two entries). At minimum, add an explicit `require` that all elements of `circomData.erc20TokenAddresses` are pairwise distinct.

### Proof of Concept
Foundry test plan:
1. Deploy `RealToken` (`A`) as a standard ERC20 and `MirrorToken` (`B`) whose `balanceOf(addr)` returns `RealToken.balanceOf(addr)` and whose `transferFrom`/`transfer` are no-ops returning `true`.
2. Fund attacker with `X` of `RealToken`; approve Hinkal.
3. Locally generate a valid proof for a `CircomData` with `erc20TokenAddresses = [A, B]`, `amountChanges = [X, X]`, `onChainCreation = [false, false]`, `externalActionData.externalActionId = 0`, `externalActionData.externalAddress = attacker`, matching output commitments for `X` under both token slots.
4. Call `Hinkal.transact(...)`.
5. Assert: `RealToken.balanceOf(vault)` increased by exactly `X` (one real transfer), while two output commitments of value `X` each (for `A` and `B`) were inserted into the tree — i.e. total credited shielded UTXO value (`2X`) exceeds the real token inflow (`X`), and both `balanceDif == amountChanges[i]` require statements in `Hinkal.transact` passed without reverting.

    function _internalTransact(CircomData calldata circomData) private {
        bool hasPaidToRelay = false;
        for (uint64 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            int256 deltaAmountChange = _calculateDeltaAmount(circomData, i);

            if (deltaAmountChange > 0) {
                require(
                    circomData.externalActionData.externalAddress == msg.sender,
                    "Deposit should come from the sender"
                );
                transferERC20TokenFromOrCheckETH(
                    circomData.erc20TokenAddresses[i],
                    circomData.externalActionData.externalAddress,
                    address(this),
                    uint256(circomData.amountChanges[i])
                );
            } else {
                uint256 sumAbs = uint256(-deltaAmountChange);
                uint256 relayFee = 0;
                if (circomData.relay != address(0)) {
                    uint256 flatFee = circomData.feeStructure.feeToken ==
                        circomData.erc20TokenAddresses[i]
                        ? circomData.feeStructure.flatFee
                        : 0;

                    require(
                        sumAbs >= flatFee,
                        "Relay Fee is over withdraw amount"
                    );

                    uint256 recipientAmount = ((10000 -
                        circomData.feeStructure.variableRate) *
                        (sumAbs - flatFee)) / 10000;

                    relayFee = sumAbs - recipientAmount;

                    if (relayFee > 0) {
                        transferERC20TokenOrETH(
                            circomData.erc20TokenAddresses[i],
                            circomData.relay,
                            relayFee
                        );
                    }
                    hasPaidToRelay = true;
                }
                if (sumAbs - relayFee > 0) {
                    transferERC20TokenOrETH(
                        circomData.erc20TokenAddresses[i],
                        circomData.externalActionData.externalAddress,
                        sumAbs - relayFee
                    );
                }
            }
        }
        require(
            circomData.relay == address(0) || hasPaidToRelay,
            "relay not paid"
        );
    }
