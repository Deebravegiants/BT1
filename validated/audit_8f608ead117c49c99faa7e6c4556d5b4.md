The gem's documented API explicitly promotes `data.shop` as the trusted tenant identifier for downstream use (`docs/usage/webhooks.md` line 26: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), while the HMAC verification only covers the raw body bytes.

### Title
Webhook HMAC verification does not bind the `shop` (or `topic`/`webhook_id`) header, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `ShopifyAPI::Utils::HmacValidator.validate` / `ShopifyAPI::Webhooks::Registry.process` verify the HMAC solely over that raw body. The `shop` (and `topic`, `api_version`, `webhook_id`) values are taken directly from unauthenticated HTTP headers and passed into `WebhookMetadata`, which the gem's own documentation instructs consuming apps to trust as the tenant identifier.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` are read straight from HTTP headers without any cryptographic binding: [2](#0-1) 

`HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` (i.e., the raw body bytes) and compares against the `hmac-sha256` header value: [3](#0-2) 

`Registry.process` validates only this body-bound HMAC, then forwards the unauthenticated `request.shop` header straight into `WebhookMetadata`, which is handed to the app's handler: [4](#0-3) 

The equality the gem implicitly claims to guarantee is: `shop_the_handler_receives == shop_that_Shopify_actually_sent_the_webhook_for`. In reality the gem only guarantees `hmac_header == HMAC(secret, raw_body)`; it says nothing about which shop produced that body. Any attacker who can obtain one genuine `(raw_body, hmac)` pair signed with the app's secret — trivially achievable by installing the app on their own store and triggering an event (e.g., `orders/create`) — can replay that exact body+HMAC to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) with an arbitrary victim shop domain. `Registry.process` will accept it as valid because the HMAC check only inspects the body, and the handler will receive `data.shop` = the attacker-chosen victim domain paired with attacker-controlled body content, breaking the shop↔body binding.

The gem's own documentation instructs implementers to key downstream work off `data.shop` directly (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), so this is not merely a "host application ignores the documented API" issue — it's the documented, intended usage pattern that is unsafe because the library provides no way to bind `shop` to the signature. [5](#0-4) 

### Impact Explanation
This enables cross-tenant access/confusion: an attacker who has legitimately installed the app on their own shop can forge webhook deliveries that the app attributes to a victim shop, using the same secret that Shopify uses for HMAC signing of every install of that app (since `api_secret_key` is per-app, not per-shop). Applications following the documented pattern (persisting/queuing work keyed by `data.shop`) can be tricked into writing attacker-controlled body data into a victim shop's records, or into desynchronizing state for shops the attacker doesn't control — a cross-tenant boundary violation.

### Likelihood Explanation
Requires only that the attacker install the app on their own shop (a normal, low-privilege action for any Shopify merchant/public app installer) and trigger an event to capture one valid `(raw_body, hmac)` pair, then replay it with a modified `shop` header to the app's public webhook endpoint. No access to `api_secret_key`, tokens, or Shopify infrastructure is needed.

### Recommendation
Include the `shop` (and ideally `topic`, `api_version`, `webhook_id`) header values in the HMAC-signed material verified by the library, or otherwise cryptographically bind them (e.g., by validating them out-of-band against the shop's registered webhook subscription/session), rather than relying solely on body-only HMAC verification. At minimum, document prominently that `data.shop` is not authenticated by the HMAC check and must be independently cross-checked (e.g., against an active, known session/installation for that shop) before being trusted for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers `orders/create`, capturing the genuine webhook request: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H == HMAC-SHA256(api_secret_key, B)`).
2. Attacker replays this exact body `B` and header `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a request object where `shop` returns `"victim-shop.myshopify.com"`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `raw_body` (`B`) — this passes since `H` is genuinely valid for `B`.
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and `body` from the attacker's own shop event, despite the webhook never having originated from or being authorized for that victim shop.
