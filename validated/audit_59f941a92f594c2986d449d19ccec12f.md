## Title
Webhook `shop` (and `topic`/`api-version`/`webhook-id`) header values are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authentic for a given shop once `Utils::HmacValidator.validate(request)` succeeds, and then hands the host application `request.shop` as the trusted tenant identifier. However, the HMAC is computed only over the raw request body — the `shop`, `topic`, `webhook-id`, and `api-version` headers are read directly from unauthenticated HTTP headers and are never part of the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate_signature` computes the HMAC purely from that signable string and compares it against the `hmac` value, again derived only from a header: [2](#0-1) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, completely outside the signed content: [3](#0-2) 

`Registry.process` validates the HMAC, then immediately constructs `WebhookMetadata` using `request.shop` and hands it to the host app's handler as the authenticated tenant identity, with no cross-check that the shop is consistent with anything cryptographically bound to the signature: [4](#0-3) 

The broken identity binding as an equality: the gem asserts `hmac_valid(body, secret) == true` implies `shop_header == authentic_source_shop`, but the actual equality that holds is only `hmac(body, secret) == received_hmac`; `shop_header` is disjoint from `body` and can be set to any value. Because `api_secret_key` is a single shared app secret used for every shop that installs the app (not a per-shop secret), any merchant who has installed the app can legitimately receive a validly-signed webhook (valid body + hmac) for their own shop's events, then replay that exact body/hmac pair to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop. `HmacValidator.validate` will still return `true` because it only checks the body signature, and `Registry.process` will dispatch the handler with `request.shop` set to the victim's domain — a cross-tenant identity confusion inside the gem's own documented processing path (`docs/usage/webhooks.md`): [5](#0-4) 

This mirrors the reported bug class: a value (the WOPI/file identity) is trusted by the receiving endpoint while an unrelated value (the access token) is the only thing actually verified — here, `shop` is trusted by the handler while only `raw_body` is actually verified by HMAC.

### Impact Explanation
This enables cross-tenant access/confusion: an attacker who has installed the vulnerable app on any store (a normal, unprivileged self-service action, not requiring `api_secret_key`, a leaked token, or the target's credentials) can cause the app to process forged webhook events attributed to an arbitrary target shop domain, as long as they can produce a validly-signed body/hmac pair from their own installation. Depending on how the host app uses `WebhookMetadata#shop` (e.g., looking up the target's stored session/access token to react to the "webhook"), this can lead to actions being taken against, or data leaking to, the wrong tenant.

### Likelihood Explanation
Requires only that the attacker install the target app on a store they control (freely available to any developer/merchant) and be able to send HTTP requests to the app's webhook endpoint with attacker-controlled headers — no secrets, tokens, or victim interaction needed. The `shop` header is fully attacker-controlled at the HTTP layer and the gem performs no validation of it.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook-id`, `api-version`) values into the HMAC-signed material verified by `Utils::HmacValidator`, or have `Registry.process`/`WebhookMetadata` cross-validate the `shop` header against a value derived from an authenticated source (e.g., verify the shop is one with an active, stored session/installation, and document that host apps must not treat `request.shop` as authenticated by HMAC alone).

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`; trigger an event so Shopify sends a legitimately signed webhook with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for the app's shared `api_secret_key`).
2. Replay the captured request to the app's webhook endpoint, keeping body `B` and `X-Shopify-Hmac-Sha256: H` unchanged, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` returns `true` (only `B` and `H` are checked) — `Registry.process` dispatches the handler with `WebhookMetadata#shop == "victim.myshopify.com"`, per: [6](#0-5)

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
