### Title
Webhook shop-domain header is not bound to the HMAC signature, allowing cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate(request)`. The `shop` value handed to the app's `WebhookHandler` is taken from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, which is never included in the signed payload. Because the identity binding "HMAC-authenticated request" == "shop attributed to the request" does not hold, any party capable of reaching the app's public webhook endpoint with a valid `(body, hmac)` pair — e.g. a legitimate, unprivileged merchant of the same multi-tenant app who receives real webhooks for their own store — can replay that same body/HMAC pair while substituting an arbitrary `shop-domain` header for a victim shop.

### Finding Description
- `HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` and compares it to the received `hmac` [4](#0-3) .
- For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [2](#0-1) ; `topic`, `shop`, `api_version`, and `webhook_id` are all read from headers that are completely outside the signed data [5](#0-4) .
- `Registry.process` raises only if the HMAC on the body fails, then immediately builds `WebhookMetadata` using `request.shop` (the unauthenticated header) as the tenant identity passed to the app's handler [3](#0-2) .
- The documented contract explicitly tells host apps that `data.shop` is "The shop domain of the webhook" and to use it to key their tenant-scoped work (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [6](#0-5) , so the gem's own documented API is what turns this unauthenticated header into a trusted tenant key — this is not a case of the host ignoring the gem's contract.

The broken identity binding is: `shop that HMAC(body) authenticates` == `shop stored in WebhookMetadata used by the host app for tenant-scoped processing`. Since the HMAC never covers `shop`, an attacker who legitimately controls one shop in a multi-tenant app can obtain a valid `(body, hmac)` pair from their own real webhook deliveries and resend it to the app's endpoint with the `shop-domain` header rewritten to a victim's `myshopify.com` domain. `Utils::HmacValidator.validate` still returns `true` (the body and its HMAC still match), so `Registry.process` invokes the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker's body, ...)`.

### Impact Explanation
This is a cross-tenant identity-binding break: an unprivileged actor (a shop merchant of the same app) can make the host app process attacker-controlled event content while attributing it to an arbitrary victim shop. Depending on how the host application consumes `WebhookMetadata#shop` (session/tenant lookups, database writes keyed by shop, order/customer state changes), this enables cross-tenant data injection/corruption without ever needing the app's `api_secret_key`, an access token, or the victim's credentials — matching the High-impact "cross-tenant access" criterion.

### Likelihood Explanation
Exploitation requires only: (1) being any merchant that installs the app (unprivileged, ordinary usage) and thus legitimately receiving real webhook `(body, hmac)` pairs for their own store, and (2) sending an HTTP POST to the app's public webhook endpoint with the same body/HMAC but a forged `shop-domain` header. No secret material or elevated privilege is required, and the webhook endpoint is inherently internet-reachable by design.

### Recommendation
Bind the shop domain (and ideally topic/api-version/webhook-id) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived `shop` to the same secret used for body verification, e.g. by including the header values in `to_signable_string`/the computed digest, or by requiring `Registry.process` to independently verify that the `shop` matches an active, previously-established session/webhook registration before invoking the handler.

### Proof of Concept
1. App merchant "attacker-shop.myshopify.com" installs the target app and receives a legitimate webhook delivery: body `{"id":1}` with header `x-shopify-shop-domain: attacker-shop.myshopify.com` and a valid `x-shopify-hmac-sha256` computed over that body using the app's `api_secret_key` (known only to Shopify, but the attacker passively observes the resulting valid pair from their own webhook traffic).
2. Attacker POSTs to the app's webhook endpoint with the identical body and HMAC header, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(body)`, and it passes [7](#0-6) .
4. `WebhookMetadata.new(shop: request.shop, body: request.parsed_body, ...)` is constructed with `shop == "victim-shop.myshopify.com"` and the attacker's body, and passed to the host app's handler [8](#0-7) , causing the app to process attacker-controlled data under the victim's tenant identity.
