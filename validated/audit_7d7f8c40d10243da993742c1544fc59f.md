### Title
Webhook `topic` and `shop-domain` are dispatched to handlers without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body, so the HMAC that `Registry.process` validates authenticates the body bytes alone. The `topic`, `shop-domain`, `webhook-id`, and `api-version` values are taken from unauthenticated HTTP headers and are handed straight to the app's `WebhookHandler`, breaking the intended binding `hmac == HMAC(secret, body + shop + topic)`.

### Finding Description
`Webhooks::Request` reads `shop`, `topic`, `api_version`, and `webhook_id` directly from HTTP headers with no cryptographic protection: [1](#0-0) 

`Utils::HmacValidator.validate` verifies the HMAC using `verifiable_query.to_signable_string`, and for `Request` that method returns only `@raw_body`: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC and then dispatches to a handler using the unauthenticated `request.topic` and passes the unauthenticated `request.shop` straight into `WebhookMetadata`, which the handler trusts as the origin shop: [4](#0-3) [5](#0-4) 

Crucially, the HMAC secret (`Context.api_secret_key`) is the **app's** secret, shared across every merchant that installs the app — it is not shop-specific. That means a `(raw_body, hmac)` pair that Shopify legitimately generates for webhooks delivered to Shop A's URL is cryptographically valid for **any** shop and **any** topic, since the shop/topic are never mixed into the signed data.

**Broken identity binding (equality that should hold but doesn't):**
`hmac == HMAC(secret, body)` is verified, but the app relies on `hmac` to also vouch for `shop == request.shop` and `topic == request.topic`. Those two fields are parsed from headers but never verified.

### Impact Explanation
An unprivileged internet user who has installed the app on their own store (no `api_secret_key`, no access token, no privileged account required) receives a normal, validly-signed webhook for their own shop/topic. They can replay that exact raw body + HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim's shop and/or the `shopify-topic` header for any topic registered by the app. `Registry.process` will accept the forged HMAC (since it only checks the body) and invoke the handler with `WebhookMetadata.shop` set to the victim's domain and/or a spurious topic, e.g. triggering `app/uninstalled`, `customers/redact`, `shop/redact`, or any custom order/customer handler logic for a shop the attacker does not own. Any host application that keys persistence, entitlement changes, or data deletion by `data.shop` from this metadata is exposed to cross-tenant action forgery — satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high once an attacker has any single legitimate webhook delivery to inspect (trivial to obtain by installing the app on a shop they control, or from access to webhook logs/proxies). No secret material is required; only observation of one valid `(body, hmac)` pair from any tenant of the same app, since the secret is shared app-wide rather than per-shop.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the signed material, or otherwise re-derive them from Shopify's Admin API using the delivered `webhook_id` rather than trusting client-supplied headers. At minimum, `to_signable_string` should incorporate the shop domain and topic so the HMAC cryptographically vouches for them, e.g.:
```ruby
def to_signable_string
  "#{shop}|#{topic}|#{@raw_body}"
end
```
and Shopify's webhook signing scheme would need to match (this requires coordination with Shopify's delivery format, since today's HMAC is computed by Shopify over the body only) — alternatively, the gem should treat `shop`/`topic` as advisory only and require host apps to cross-check them against an out-of-band source of truth (e.g., a lookup keyed by `webhook_id` via GraphQL) before trusting them for any privileged action.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers any registered webhook topic (e.g. `orders/create`), capturing the raw POST body `B` and header `x-shopify-hmac-sha256: H` that Shopify sends to the app's webhook endpoint.
2. Attacker replays this HTTP POST to the same webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: customers/redact` (or `app/uninstalled`, or any other registered topic)
3. `Utils::HmacValidator.validate` computes `HMAC(secret, B)` and compares to `H` — this succeeds because the signature was never bound to shop/topic: [6](#0-5) 
4. `Registry.process` looks up the handler for the forged topic and invokes it with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "customers/redact", ...)`, causing the host application to perform whatever action that handler implements (e.g., data deletion, deactivation, entitlement update) against a shop the attacker does not control.
