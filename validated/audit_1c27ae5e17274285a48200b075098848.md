## Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC that `Registry.process` validates covers **only** `@raw_body`. All other attacker-supplied headers used later by the handler — most importantly `shop`, but also `topic`, `webhook_id`, and `api_version` — are never part of the signed material. Because `Registry.process` trusts `request.shop` when building the `WebhookMetadata` passed to the app's handler, an attacker who can obtain any one genuinely-signed `(body, hmac)` pair for a topic (e.g. from their own store, which they control and can trigger events in) can replay that exact body/HMAC pair while swapping the `x-shopify-shop-domain` header to a victim shop's domain. The signature still validates because it only checks the body bytes, but the handler now believes the payload originated from the victim tenant.

### Finding Description
The identity binding that should hold is:

`HMAC-verified bytes == bytes the handler treats as authoritative for shop attribution`

In this gem that equality is broken:

- `Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 
- `Request#shop` is read straight from the (unauthenticated, attacker-controlled at the transport layer) `shopify-shop-domain`/`x-shopify-shop-domain` header, with no relation to the signed bytes: [2](#0-1) 
- `Registry.process` validates only the HMAC over the request, then immediately forwards `request.shop` (and other unsigned headers) to the app's handler as trusted tenant metadata: [3](#0-2) 
- `HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`, i.e. the body: [4](#0-3) 

Because `shop` never enters `to_signable_string`, any valid `(raw_body, hmac)` pair the attacker previously obtained — by legitimately triggering a webhook on **their own** store, which is a store they control and for which they can freely generate topic events — remains valid for the same raw body regardless of which shop domain header accompanies it. The gem hands this forged `shop` value straight to the app's webhook handler as the tenant identity: [5](#0-4) 

This is exactly the class of bug in the external report: a field consumed for security-relevant identity decisions (`shop`) is not covered by the same authentication check (`HMAC`) that gates acceptance of the message, letting the attacker present two different values (their own signed body vs. a victim's shop identity) and having the trusted side pick the wrong one.

### Impact Explanation
An attacker who owns/operates a legitimately-installed shop of the target app can capture a real webhook `(body, hmac)` for a topic they control (e.g. `orders/create`, `app/uninstalled`, or any topic with attacker-influenced body content), then replay it to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim merchant's shop. The app, relying on this gem's `Registry.process`, will accept the HMAC as valid and dispatch the handler believing the event came from the victim's shop — i.e. cross-tenant data injection into the victim's tenant context (e.g. triggering the victim's order-processing logic, uninstall cleanup, or GDPR redaction flows with attacker-controlled body content attributed to the wrong shop). This is a cross-tenant access impact.

### Likelihood Explanation
Any internet-accessible app using this gem's documented `Registry.process` flow is affected without any special privileges: the attacker needs only their own working store (which any developer can obtain for free) to harvest one valid signed body/HMAC pair per topic of interest, then can freely relabel the shop header on replay. No access token, `client_secret`, or leaked credential is required.

### Recommendation
Include the shop domain (and ideally the topic/webhook id) in the signed material checked against the HMAC, or otherwise cryptographically/contextually bind the `shop-domain` header to the specific signed body before trusting it in `WebhookMetadata`. At minimum, `Registry.process`/`Request` should require the app to independently verify that `request.shop` corresponds to a shop that actually has this webhook topic registered/installed before dispatching to the handler, rather than trusting the header purely because the (shop-independent) body HMAC passed.

### Proof of Concept
1. Attacker registers/owns `attacker-shop.myshopify.com` with the target app and triggers a webhook event (e.g. `orders/create`) — Shopify sends a legitimate request with `raw_body = B`, `x-shopify-hmac-sha256 = HMAC(secret, B)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays this exact `raw_body = B` and the same `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and finds it matches — validation passes because `shop` was never part of the signed string (`lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` with `shop == "victim-shop.myshopify.com"` even though the request never actually originated from Shopify for that shop (`lib/shopify_api/webhooks/registry.rb:198-199`).
5. The app's handler processes attacker-supplied body `B` under the victim shop's tenant context.
