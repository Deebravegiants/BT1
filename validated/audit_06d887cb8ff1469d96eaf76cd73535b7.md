## Title
Signed-to-unsigned integer conversion in gateway staleness check allows bypass of message-age validation - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
`handler.HandleLegacyUserMessage` enforces a "not stale" guard by comparing `uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec` against `uint(payload.Timestamp)`, where `payload.Timestamp` is an attacker-controlled `int64` field of `webapicap.TriggerRequestPayload`. A negative timestamp passes the preceding `payload.Timestamp == 0` check but wraps to a near-`MaxUint64` value under the `uint()` cast, making the staleness comparison always evaluate false and silently bypassing the intended freshness check. [1](#0-0) 

## Finding Description
The handler decodes the JSON payload into `webapicap.TriggerRequestPayload`, whose `Timestamp` field is a signed `int64` (confirmed by the test helper constructing it via `strconv.ParseInt(timestamp, 10, 64)`). [2](#0-1) 

It then checks `payload.Timestamp == 0` (rejecting only exact zero) and subsequently performs the staleness check entirely in unsigned arithmetic: `uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp)`. [1](#0-0) 

A negative `Timestamp` (e.g., `-1`) is nonzero, so it passes the first check, but `uint(payload.Timestamp)` wraps around to a value near `math.MaxUint64`, which is always greater than `uint(time.Now().Unix()) - MaxAllowedMessageAgeSec`. The comparison then evaluates to `false`, so the "stale message" rejection path is never taken, and the request proceeds. Immediately after this check, only a method-name check and `common.ValidatedRequestFromMessage` (structural/signature transformation, not further timestamp validation) gate the request before it is forwarded unmodified to every DON member via `don.SendToNode`. [3](#0-2) 

The existing test suite explicitly documents that sender/rate-limit validation is not yet implemented at this layer (`// TODO: Validate Senders and rate limit check, pending question in trigger about where senders and rate limits are validated`), and the code itself contains `// TODO: apply allowlist and rate-limiting here` right after the staleness check, confirming the `MaxAllowedMessageAgeSec` check is the only freshness/anti-replay-style defense present in this codepath. [4](#0-3) [5](#0-4) 

`msg.Sign`/`msg.Validate` (used in tests to construct valid messages) verify message integrity/signature and structural correctness but do not perform any bounds check on the `Timestamp` field inside the JSON payload, since that field is opaque application payload, not part of the envelope validated by the message signature scheme.

## Impact Explanation
Any client capable of submitting an HTTP trigger request through the gateway fully controls `TriggerRequestPayload.Timestamp`. By supplying a negative value, the intended "message not stale" check is defeated, allowing forged-timestamp trigger payloads to be forwarded to all DON member nodes as if they were fresh. This undermines the integrity guarantee that `MaxAllowedMessageAgeSec` is supposed to provide against outdated or replayed webapi trigger requests reaching the workflow pipeline — a logic bypass of an intended validity guard, mapping to a gateway request/validation-bypass class issue. The actual downstream severity is bounded by what a DON node does with a maliciously-aged (but otherwise well-formed) trigger message, which is not itself an authentication or fund-movement bypass; the check bypassed here is a freshness/staleness guard, not an authentication or allowlist gate (allowlisting is explicitly not yet implemented at this layer per the TODOs, independent of this bug).

## Likelihood Explanation
`Timestamp` is fully attacker-controlled JSON input in an unprivileged, internet-facing HTTP trigger request handled by `HandleLegacyUserMessage`. No additional privilege beyond forming a correctly structured (and node-key-signed per existing message envelope requirements) request is needed to set a negative value — the test helper demonstrates the payload is constructed directly from an arbitrary `int64`. The bypass is deterministic and trivially repeatable.

## Recommendation
Validate that `payload.Timestamp` is non-negative (and within a sane upper bound) before any unsigned conversion, or perform the entire freshness comparison in signed 64-bit arithmetic, e.g.:
```go
if payload.Timestamp < 0 || time.Now().Unix()-payload.Timestamp > int64(h.config.MaxAllowedMessageAgeSec) {
    // reject as stale/invalid
}
```

## Proof of Concept
1. Using the existing `triggerRequest` test helper pattern in `core/services/gateway/handlers/capabilities/handler_test.go:193-234`, construct a `TriggerRequestPayload` with `Timestamp: -1` instead of a valid Unix timestamp string.
2. Sign the message and call `handler.HandleLegacyUserMessage(ctx, msg, cb)`.
3. Observe that the "stale message" error path (`api.HandlerError`, `"stale message"`) is never returned, and instead `don.SendToNode` is invoked for each DON member, confirming the check at `handler.go:372` is bypassed for negative timestamps.
