### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, so the HMAC signature that `HmacValidator.validate` checks binds nothing but the JSON payload. The `shop-domain`, `topic`, `webhook-id` and `api-version` headers are read directly off the unauthenticated request and forwarded to the handler untouched. Because every shop installed on the same app shares the same `api_secret_key`, any tenant who can trigger one genuine webhook delivery to the app can replay that exact (body, hmac) pair while swapping the `shop-domain` header to a victim tenant's domain, and the gem will report the forged shop as verified.

### Finding Description
The binding that should hold is:
`shop asserted in WebhookMetadata.shop == shop actually authenticated by the HMAC signature`

In `lib/shopify_api/webhooks/request.rb`:
```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

only `@raw_body` is signed. The `shop` accessor is read straight from the header with no cryptographic tie to the signature:
```ruby
sig { returns(String) }
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [2](#0-1) 

`HmacValidator.validate` only recomputes the HMAC over `to_signable_string`, i.e. the body:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [3](#0-2) 

`Registry.process` trusts this same unauthenticated `shop` field once the (body-only) HMAC check passes, and hands it to the app's handler as verified metadata:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

Because the `api_secret_key` used to compute the HMAC is a single app-wide secret shared across every shop that has installed the app (not a per-shop secret), a genuine webhook delivered to the app for shop A produces a (body, hmac) pair that remains cryptographically valid for the exact same body/secret combination *regardless of which shop-domain header accompanies the request*. Any tenant is therefore able to capture one legitimate webhook their own store received, then resend that identical body+hmac to the app's endpoint while substituting the `x-shopify-shop-domain` header for a different, victim tenant. `HmacValidator.validate` still returns `true` because it never inspected the shop field, and `Registry.process` passes the attacker's forged shop identity straight through to the handler as `WebhookMetadata#shop`, which is the field host applications are documented and expected to key their per-tenant persistence on (see `test/webhooks/registry_test.rb` assertions on `data.shop`). [5](#0-4) 

This is a direct instance of the "field acted on but not covered by the HMAC" bug class: the `shop` identity is used for tenant attribution but is excluded from the cryptographic binding, exactly analogous to the Wildcat report's unaccounted state (`state.timeDelinquent`) being excluded from the debt calculation it should have gated.

### Impact Explanation
This breaks the tenant isolation the gem is supposed to provide via `Utils::HmacValidator` + `Webhooks::Registry`: a malicious or compromised merchant who has installed the same app can inject arbitrary attacker-chosen payloads that are attributed to any other merchant's shop domain into the app's webhook processing pipeline, with the gem itself certifying the request as HMAC-validated. Any host application that trusts `WebhookMetadata#shop` (the field this gem exposes specifically for that purpose) to select which tenant's data store to write into will suffer cross-tenant data corruption/injection — satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high: the only prerequisite is that the attacker controls, or can trigger events on, one shop that has the target app installed — a normal unprivileged capability (e.g. a free/dev store install) — and can then issue a direct HTTP POST to the app's public webhook endpoint with modified headers, which requires no secret knowledge beyond capturing one legitimately delivered webhook.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) values in the signable string used by `HmacValidator`, or independently verify the `shop-domain` header against the shop the caller is authorized to act as (e.g., cross-check against a known/allow-listed shop for that specific webhook subscription/session) before constructing `WebhookMetadata`. At minimum, `to_signable_string` for `Webhooks::Request` should incorporate the shop domain so that forging it invalidates the signature.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Attacker triggers the event; Shopify delivers a genuine webhook with headers `x-shopify-topic`, `x-shopify-hmac-sha256`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, and a JSON body signed with the app's shared `api_secret_key`.
3. Attacker captures the raw body and the `x-shopify-hmac-sha256` value.
4. Attacker sends a new POST directly to the app's webhook endpoint with the identical raw body and `x-shopify-hmac-sha256` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (the unchanged raw body) — validation succeeds.
6. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker JSON>, ...)`, i.e., attacker-controlled data marked as verified and attributed to the victim tenant.
