### Title
Bandwidth gate silently truncates the attacker-controlled `request.from` identifier before its allowlist/subscription check, enabling identity-collision ACL bypass and subscription drain - (File: modules/pallets/bandwidth/src/lib.rs)

### Summary
`pallet-bandwidth`'s `BandwidthGate::try_consume` and `on_accept` key every allowlist and subscription lookup on `AppKey = BoundedVec<u8, ConstU32<32>>`, built via `AppKey::truncate_from(app.to_vec())`. `app` is `request.from`, an arbitrary-length, fully attacker-controlled byte string set by whatever untrusted dispatcher sent the message on the source chain. `truncate_from` silently drops everything past 32 bytes rather than rejecting the input, so any two distinct `from` identifiers that share the same first 32 bytes collapse onto the same `AppKey`, exactly the class of bug in CVE-2019-13164 where `qemu-bridge-helper.c` truncated a network interface name to `IFNAMSIZ` before an ACL comparison, letting a crafted long name collide with an allowed short one.

### Finding Description
`AppKey` is defined as: [1](#0-0) 

The gate that every non-purchase inbound POST request must pass through truncates the caller-supplied `app` bytes into this bound before doing the security-relevant lookups (allowlist bypass check, then FIFO subscription drain): [2](#0-1) 

`try_consume` is invoked directly from the runtime's ISMP router with the raw, unvalidated `request.from` field, *before* any module-id format check is applied (contrast with `request.to`, which is parsed via `ModuleId::from_bytes` and must be exactly 8, 20, or 32 bytes): [3](#0-2) [4](#0-3) 

`request.from` is an opaque identifier chosen by whatever entity dispatches the message on the *source* chain (any EVM contract calling the ISMP dispatcher, any pallet, etc.) — it is not constrained to the 8/20/32-byte `ModuleId` shapes, so nothing stops an attacker from submitting a `from` field of, say, 40 bytes whose first 32 bytes are identical to a legitimate, already-allowlisted or already-subscribed app's identifier.

Notably, the team already recognized this exact failure mode on the *purchase* path and fixed it there by rejecting rather than truncating: [5](#0-4) 
confirmed by a regression test: [6](#0-5) 

However, `try_consume` — the gate that runs on *every* metered inbound message, called straight from `ProxyModule::on_accept` — was never given the same “reject-over-bound” treatment; it still calls `AppKey::truncate_from` unconditionally.

### Impact Explanation
Because `try_consume` truncates instead of rejecting, an unprivileged attacker able to dispatch a message from any source chain can craft `from = <32-byte-prefix-matching-a-victim-app><arbitrary-suffix>` and have it collide with the victim's `AppKey`:
- If the victim app is on the governance `Allowlist` (a "protocol-sponsored, gate-bypass" entry, e.g. TokenGateway), the attacker's unrelated messages get the free bypass reserved for that sponsored app.
- If the victim app instead holds a paid `Allowance` (a real `BandwidthManager.purchase()` subscription), the attacker's messages silently drain the victim's paid `remaining_bytes` via the same FIFO consumption path, emitting `BandwidthConsumed` against the victim's key. This is a direct theft of a purchased resource and results in denial-of-service for the victim once the drained subscription hits `NoAllowance`/`Insufficient`, blocking the victim's own legitimate ISMP messages.

This satisfies the "concrete theft ... or permanent freezing of funds" bar: the victim paid real fee-tokens for bandwidth (`BandwidthManager.purchase()`), and that paid-for resource can be consumed by an attacker who never paid, with no way for the victim to recover the lost bytes.

### Likelihood Explanation
Reachable from a single, completely permissionless, attacker-dispatched message: any contract on any EVM chain (or any pallet on a substrate chain) that has a connection to Hyperbridge can call the ISMP dispatcher with a crafted `from` field of arbitrary length. No relayer collusion, no governance/admin compromise, and no consensus-proof forgery is required — the request simply needs to be relayed normally, which any of the many permissionless relayers will do. The only requirement is knowing the 32-byte (or shorter) identifier of a currently allowlisted or actively-subscribed victim app, which is public on-chain information (`Allowlist`/`Allowance` storage and `AllowlistChanged`/`BandwidthCredited` events).

### Recommendation
Mirror the purchase-path fix in the gate path: reject (rather than silently truncate) any `app`/`request.from` whose length exceeds `AppKey::bound()` before it is used to key `Allowlist`/`Allowance` lookups in `try_consume` (and in `is_purchase_message`/`allowances`/`remaining` for consistency). Concretely, replace `AppKey::truncate_from(app.to_vec())` in `try_consume` (modules/pallets/bandwidth/src/lib.rs:515) with a fallible `AppKey::try_from(app.to_vec())` that returns a distinguishing error (e.g. treat over-length identifiers as simply having no allowance, the same "fail closed" outcome `PurchaseMessage::try_from` already applies), so two different over-bound identifiers can never be coerced into colliding on the same bounded key.

### Proof of Concept
1. Governance allowlists TokenGateway on `EVM-1`: `AppKey::truncate_from(token_gateway_20_byte_address)` → stored as a 20-byte `AppKey` (no truncation occurs here since it's under the bound).
2. To exploit the *subscription-drain* variant (not the 20-byte allowlist case, which needs an exact-length collision), consider a victim app whose identifier is exactly 32 bytes (e.g. a `Contract(AccountId32)` module id) with an active paid subscription created via `BandwidthManager.purchase()` — `on_accept` stores it under `AppKey::truncate_from(victim_32_bytes)` = the full 32 bytes.
3. Attacker dispatches an ISMP POST from `EVM-1` with `from = victim_32_bytes || <any_extra_bytes>` (e.g. 40 bytes total). Solidity/ISMP places no length restriction on the `from` field of a dispatched request.
4. On delivery, `ProxyModule::on_accept` calls `BandwidthGate::try_consume(EVM(1), &request.from /* 40 bytes */, bytes)`. `AppKey::truncate_from` drops the last 8 bytes, producing exactly `victim_32_bytes` — the same key the victim's paid subscription lives under.
5. `try_consume` finds the victim's live `Allowance` list, drains `bytes` from it, and emits `BandwidthConsumed { source: EVM(1), app: victim_32_bytes, ... }` — deducting from the victim's paid balance even though the message actually originated from the attacker's unrelated contract.
6. Repeating this exhausts the victim's `remaining_bytes`; the victim's own subsequent legitimate messages from the real 32-byte identifier then fail with `GateError::Insufficient`/`NoAllowance`, confirming the drained/stolen state.
