### Title
Webhook `shop`/`topic`/`webhook_id` identity fields are not covered by the HMAC signature, enabling a confused-deputy cross-tenant replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from HTTP headers to build the `WebhookMetadata` passed to the app's handler. Those header fields are never included in the signed payload, so the binding "HMAC-verified bytes == identity used by the handler" does not hold.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`, and for a webhook `Request`, `to_signable_string` returns only `@raw_body`: [1](#0-0) 
Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from attacker-suppliable headers with no cryptographic tie to the body: [2](#0-1) 
`Registry.process` validates the HMAC and, if it matches, immediately hands the *header-derived* `shop`/`topic`/`webhook_id` to the developer's handler as trusted metadata: [3](#0-2) 

The identity equality the library implicitly claims to guarantee is:
`HMAC-verified(raw_body) == (shop, topic, webhook_id used by handler)`

In reality only `raw_body` is bound by the signature; `shop` (and `topic`, `webhook_id`) are unauthenticated. Any unprivileged internet user who legitimately receives one genuine webhook delivery for their own shop (e.g., by installing the target app on a shop they control, which is a normal unprivileged action) obtains a `(raw_body, hmac)` pair valid under the app's `client_secret`. Because the signature never binds `shop`, that exact `(raw_body, hmac)` pair remains valid if resent directly to the app's public webhook endpoint with the `x-shopify-shop-domain` header (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) rewritten to name a different, victim shop. `HmacValidator.validate` will still return `true` since it never inspects those headers, and `Registry.process` will invoke the handler believing the event pertains to the victim shop.

### Impact Explanation
This is a confused-deputy / tenant-binding break: an attacker who can obtain any one genuine webhook signature for their own tenant can forge events "on behalf of" an arbitrary other shop as far as this library's contract is concerned, because the shop identity is not part of what was actually verified. Any host application that follows the documented pattern (trust `WebhookMetadata#shop`/`#topic` returned by `Registry.process` to decide which tenant's data to update, e.g., billing status changes, `app/uninstalled`, `shop/redact`, GDPR webhooks, order/customer state) can be made to apply attacker-chosen body content to a victim shop's record, i.e., cross-tenant access/write via a forged but "validly HMAC'd" webhook. This matches the Critical "cross-tenant access" impact category, since the library-level authentication check gives false assurance about which tenant a signed payload belongs to.

### Likelihood Explanation
Likelihood is high for any app builder who follows the library's documented usage exactly (`docs/usage/webhooks.md` shows handlers keyed only off `Registry.process`'s validated request) and trusts the resulting `WebhookMetadata#shop` as an authenticated tenant identifier, which is the natural reading of "this request passed HMAC validation." Obtaining a genuine `(body, hmac)` pair requires nothing more than installing the target app on any shop (a normal unprivileged action for any Shopify merchant/developer), then replaying that raw POST to the app's own public webhook endpoint with a modified shop header — no access to `client_secret`, tokens, or privileged credentials is required.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the verified signable string, or otherwise cryptographically tie header identity claims to the payload before trusting them: e.g., require and independently reverify that the `shop` header is present as part of a canonical string included in `to_signable_string`, or reject/ignore the header-provided `shop` and instead only use identity data that is derivable from an out-of-band verified channel (mTLS/IP allow-list is not sufficient at the library level). At minimum, `docs/usage/webhooks.md` and the `Registry.process`/`WebhookMetadata` API should explicitly document that `shop`/`topic`/`webhook_id` are *not* covered by the HMAC and must not be used as an authorization boundary without additional verification (e.g., checking against a shop the app knows it installed for).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, triggering a genuine webhook delivery with body `B` and header `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: H` where `H = HMAC_SHA256(client_secret, B)`.
2. Attacker captures `(B, H)` (their own webhook, no special access needed).
3. Attacker POSTs directly to the target app's public webhook endpoint with the same raw body `B` and the same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in `hmac_validator.rb` recomputes the HMAC over `request.to_signable_string` (`= B`) and finds it matches `H`, per `lib/shopify_api/webhooks/request.rb#L35-38` and `lib/shopify_api/utils/hmac_validator.rb#L26-31` — validation passes.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb#L188-200`) builds `WebhookMetadata` using `shop: request.shop` = `"victim-shop.myshopify.com"` and dispatches to the app handler, which now acts on `victim-shop` using attacker-controlled body content, despite the signature never having verified anything about `victim-shop`.
