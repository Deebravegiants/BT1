This is exactly the "front-run to deny" bug class: the AllowListBasedAuth path derives a global `RequestReplayGuard` key purely from the request digest (a deterministic hash of method+params+ID), and that digest is public on-chain data (`WorkflowRegistryOwnerAllowlistedRequest.RequestDigest`, visible in `workflowRegistrySyncer.GetAllowlistedRequests`). Since the digest for a not-yet-submitted, already-allowlisted request is fully known and reproducible by anyone who can read the chain state, an unprivileged actor can front-run the legitimate submission of the exact same request to the gateway/node. ### Title
Unprivileged attacker can deny a legitimate Vault request by front-running with a duplicate digest into the replay guard - (File: core/capabilities/vault/authorizer.go)

### Summary
`allowListBasedAuth.AuthorizeRequest` computes authorization purely from a deterministic `req.Digest()` matched against on-chain allowlisted request digests, and the outer `authorizer.AuthorizeRequest` consumes a single shared, node-local `RequestReplayGuard` keyed only by that digest before checking any binding to a specific caller/connection. Because the allowlisted digest is published on-chain and is not bound to who submits it, anyone observing the allowlist entry can replay the identical JSON-RPC request to the gateway ahead of the legitimate submitter.

### Finding Description
`allowListBasedAuth.AuthorizeRequest` derives `requestDigest` from the request body and looks it up against `workflowRegistrySyncer.GetAllowlistedRequests`, which returns publicly-known on-chain `WorkflowRegistryOwnerAllowlistedRequest` entries (owner, digest, expiry) [4](#0-3) . This digest, together with the owner and expiry, is exactly the pre-image an attacker needs: to compute the same digest, the attacker only needs the exact same JSON-RPC method/ID/params that the legitimate workflow submitter will use, which for allowlisted vault operations (e.g. `secrets/create`, `secrets/update`) is fixed ahead of time and derivable from public workflow metadata/on-chain registration flow (as demonstrated by `allowlistRequest` test helper computing `input.Request.Digest()` before it's ever sent to the gateway) [5](#0-4) .

Once authorized via the allowlist, the shared `authorizer.AuthorizeRequest` immediately calls `a.replayGuard.CheckAndRecord(authResult.Digest(), ...)`, which records the digest in a single in-memory map (`seen[digest]`) shared across all requests to that node/gateway instance, and any subsequent request bearing the same digest is rejected with `ErrRequestAlreadySeen` until the entry expires [6](#0-5) . There is no verification that the digest is being consumed by the actual intended party (no signature/auth binding tying the digest-claim to the workflow owner's connection) at this stage — for the allowlist path, `req.Auth == ""` is the branch taken, and authorization relies solely on the request digest matching the on-chain allowlist entry [7](#0-6) .

This closely mirrors the H-7 pattern: the legitimate, intended operation (claiming reward tokens / here, submitting the allowlisted vault operation) is guarded by a check-then-act pattern (`balanceAfter - balanceBefore` / `CheckAndRecord`) that any unprivileged party can trigger first using publicly-derivable inputs (external `getReward` call / publicly-known request digest), permanently consuming the one-shot resource (reward delta / allowlist digest slot) before the legitimate actor's request arrives, causing the legitimate operation to be denied.

### Impact Explanation
An attacker who front-runs the gateway with a replayed request bearing the same digest as an about-to-be-submitted allowlisted vault operation causes the real node-side handler (`GatewayVaultRequestProcessor` → `authorizeAndStamp`) to reject the legitimate submitter's identical request as `ErrRequestAlreadySeen`, since the digest is now already recorded [8](#0-7) . Because the allowlist entry is single-use per digest (no re-authorization possible once consumed and no distinguishing of "which caller" submitted first), the workflow owner's actual `secrets/create`, `secrets/update`, `secrets/delete`, or `secrets/list` call can be permanently blocked until a new allowlist entry with a new digest/expiry is registered on-chain — a real operational denial-of-service against a specific, targeted user, analogous to the loss of reward tokens in the source report.

### Likelihood Explanation
This requires no special privilege: an attacker only needs to read on-chain allowlist state (public) and know/guess the exact request body a legitimate submitter will send, which is realistic for on-chain-published `AllowlistRequest` entries used to pre-authorize a specific workflow action's payload/digest ahead of submission. The retry/window mechanics (`allowListBasedAuthRetryCount`/`retryInterval`) even give an attacker a generous ~30s propagation window to win the race after observing the on-chain allowlist event [9](#0-8) .

### Recommendation
Bind the replay-guard/allowlist consumption to caller identity (e.g., require request signing/auth that ties the digest to the specific submitting party) rather than allowing anyone who reproduces the exact digest to consume the one-shot allowlist entry. Alternatively, allow the legitimate owner to invalidate/reset a consumed-but-illegitimate digest claim, or bind allowlist consumption transactionally to on-chain confirmation of the actual submitter rather than a purely off-chain, unauthenticated digest match.

### Proof of Concept
1. Workflow owner registers an on-chain `AllowlistRequest` for a specific vault JSON-RPC request (method, params, ID) with digest `D` and expiry `E` (public on-chain event/state, as constructed in `allowlistRequest`) [5](#0-4) .
2. Attacker observes the on-chain allowlist entry (owner, digest `D`, expiry `E`) via `workflowRegistrySyncer.GetAllowlistedRequests` (readable by any node/observer) and reconstructs (or already has, since it's application-public) the exact same JSON-RPC request body that will produce digest `D`.
3. Attacker submits that identical request to the gateway before the legitimate workflow owner does. `allowListBasedAuth.AuthorizeRequest` matches digest `D` against the allowlist and returns success [10](#0-9) ; `authorizer.AuthorizeRequest` then calls `replayGuard.CheckAndRecord(D, E)`, recording `D` as seen [11](#0-10) .
4. When the legitimate workflow owner submits the same request (same digest `D`), `replayGuard.CheckAndRecord` finds `D` already in `seen` and returns `ErrRequestAlreadySeen`, so `authorizer.AuthorizeRequest` rejects the legitimate request until the allowlist entry expires and a new one is registered [3](#0-2) .

var ErrRequestAlreadySeen = errors.New("request was already authorized previously")

// RequestReplayGuard prevents replay of already-processed requests by tracking
// request digests with expiry timestamps. It is safe for concurrent use.
//
// Used by both the AllowListBasedAuth flow and the JWTBasedAuth flow to ensure
// that a given request digest is only accepted once.
type RequestReplayGuard struct {
	mu      sync.Mutex
	seen    map[string]int64 // digest → unix expiry timestamp
	nowFunc func() time.Time // injectable for testing
}

// NewRequestReplayGuard creates a replay guard for authorized Vault requests.
func NewRequestReplayGuard() *RequestReplayGuard {
	return &RequestReplayGuard{
		seen:    make(map[string]int64),
		nowFunc: time.Now,
	}
}

// CheckAndRecord returns ErrRequestAlreadySeen if the digest was previously
// recorded and has not yet expired. Otherwise it records the digest with
// the given expiry timestamp (unix seconds, UTC).
//
// Expired entries are cleaned up on every call.
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
