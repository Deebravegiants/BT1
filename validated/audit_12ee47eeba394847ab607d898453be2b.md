### Title
Webhook shop-domain header is not covered by HMAC, allowing cross-tenant identity spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` identity used for tenant dispatch is read from an unauthenticated header. This breaks the binding `hmac_signed_bytes == identity_used_for_dispatch`, allowing a valid-signature webhook captured from one tenant to be replayed with a forged shop identity for another tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `#shop` is derived purely from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, with no cross-check against the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC using `verifiable_query.to_signable_string`, i.e. only the body: [3](#0-2) 

`Registry.process` trusts this HMAC check and then constructs `WebhookMetadata` directly from `request.shop`, which is the unauthenticated header value: [4](#0-3) 

Because Shopify signs webhooks using the app's single shared `api_secret_key` (the same secret is used for every merchant that has the app installed — this is not a per-tenant secret), any merchant who has legitimately installed the app can capture one of their own genuinely-signed webhook deliveries (valid `raw_body` + valid `hmac-sha256` header, since the secret matches). That merchant can then replay the exact same body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still returns `true` (only the body is checked), and `Registry.process` dispatches the request to the handler with `shop: "victim-shop.myshopify.com"` even though the payload actually originated from the attacker's own shop.

This is the "field acted on but not covered by the HMAC" bug class: the field that binds a webhook to a merchant tenant (`shop`) is exactly the field excluded from the cryptographic integrity check, while the field that is checked (`body`) carries no tenant binding of its own.

### Impact Explanation
Host applications built on this gem are expected to use `WebhookMetadata#shop` as the tenant key to route/store webhook data (e.g., to look up which merchant's session/data record to update), since that is the only identity information this gem exposes to the webhook handler after "verified" processing. An attacker with a legitimate (even free/trial) install of the app can inject data under an arbitrary victim shop's identity into any application logic keyed off `WebhookMetadata#shop`, since the gem tells the host that the request has passed authenticity verification (`Registry.process` doesn't raise) even though the identity binding was never actually verified. This is a cross-tenant boundary crossing achievable by an unprivileged actor who only needs to install the app on their own store — no access token, `client_secret`, or credential leak of the target’s is required.

### Likelihood Explanation
Any developer or malicious actor can freely install a public/free Shopify app to obtain a real merchant account, and legitimate webhook deliveries (with correctly computed HMACs) are automatically sent to the app's registered endpoint. Capturing and replaying an HTTP request with a modified header is trivial. The only constraint is that the app must expose a reachable webhook endpoint (a standard requirement for any working integration), making this readily reachable without any special privilege beyond ordinary app installation.

### Recommendation
Bind the shop identity to the HMAC verification: either
- include the shop domain (and ideally topic) in the signed payload used by `to_signable_string` (not currently possible with Shopify's HMAC scheme, since Shopify only signs the body), or
- require the host application to additionally verify that `request.shop` corresponds to a shop for which a session/access token was actually provisioned by this app (i.e., cross-check against known installed shops before trusting `WebhookMetadata#shop`), and clearly document in this gem's webhook processing API that `shop` is unauthenticated header data that must be independently validated by the caller before being used as a tenant key.
- Optionally, expose a stricter helper (e.g., `Registry.process(request, expected_shop:)`) so integrators are not implicitly encouraged to trust `request.shop` on its own.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, and receives a legitimate webhook delivery, e.g. `orders/create`, with headers:
   - `X-Shopify-Topic: orders/create`
   - `X-Shopify-Hmac-Sha256: <valid HMAC of raw_body using the shared app secret>`
   - `X-Shopify-Shop-Domain: attacker.myshopify.com`
   - body: `{...attacker's own order json...}`
2. Attacker resends the exact same body and the exact same `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but changes the header to:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
3. The host app calls `ShopifyAPI::Webhooks::Registry.process(request)`.
4. `Utils::HmacValidator.validate(request)` passes because `to_signable_string` only checks `raw_body`, which is unchanged [1](#0-0) .
5. `Registry.process` builds `WebhookMetadata.new(shop: request.shop, ...)` with `shop == "victim-shop.myshopify.com"` [5](#0-4) , and invokes the registered handler as if this were a genuine event for the victim tenant, despite the gem having reported the request as HMAC-validated/authentic.
