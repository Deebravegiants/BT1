### Title
Webhook `shop`/`topic`/`webhook_id` headers are trusted for tenant/event identity but are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
The webhook signature verification in this gem authenticates only the raw request body, while the shop domain, topic, webhook id and API version — the fields the registry uses to route and act on a webhook — are taken from unauthenticated HTTP headers. This breaks the identity binding `hmac_valid(body) ⟹ authentic(shop, topic)` that `Registry.process` implicitly relies on.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all read straight from HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC solely over `verifiable_query.to_signable_string`, i.e. the body, and compares it with the `hmac` header: [3](#0-2) 

`Registry.process` only checks that this body-only HMAC is valid, then unconditionally trusts `request.topic` and `request.shop` from headers to dispatch and construct the metadata passed to the app's handler: [4](#0-3) 

Because the signature never covers the header fields, any HTTP client capable of producing a `(body, hmac)` pair that Shopify itself once generated (for example, a merchant who installs the app on their own store and observes/replays the webhook delivered to the app's public endpoint) can resend that exact body with an arbitrary `shop-domain`, `topic`, and `webhook-id` header. The HMAC check still passes because it never inspected those headers, yet the handler receives attacker-chosen `shop` and `topic` values as if Shopify had asserted them.

### Impact Explanation
This crosses the tenant boundary the gem is supposed to enforce: an app relies on `WebhookMetadata#shop` to know which merchant's data to act on. An attacker who can obtain any one valid `(body, hmac)` pair — trivial for topics with empty/near-empty JSON bodies (e.g. `app/uninstalled` typically delivers `{}`) — can present it under a different `shop-domain` and a different `topic` header, causing the handler to process an action against a shop it never actually occurred for. Depending on how the consuming application uses `WebhookMetadata#topic`/`shop` (uninstall cleanup, GDPR redact handlers, entitlement changes), this enables cross-tenant state corruption/access, which falls into the Critical "cross-tenant access" impact category defined in scope.

### Likelihood Explanation
Any internet-reachable actor who can install the app on a shop they control (a normal, unprivileged action available to any merchant) can obtain a legitimately-signed `(body, hmac)` pair for a webhook delivered to the app's endpoint and then directly POST it to that same public endpoint with modified headers. No secret, access token, or privileged account is required beyond the ordinary ability to install a public app — this is a realistic, low-effort attack path through the gem's own verification logic.

### Recommendation
Include the security-relevant header fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used by `Utils::HmacValidator`, or otherwise cryptographically bind them to the verified payload before they are trusted in `Registry.process`/`WebhookMetadata`. At minimum, cross-check the `shop-domain` header against a known/expected shop for the installation before acting on the webhook.

### Proof of Concept
1. Install the app on shop `attacker.myshopify.com`. Capture a real webhook delivery to the app's public webhook endpoint, e.g. topic `app/uninstalled` with body `{}` and its valid `X-Shopify-Hmac-Sha256` value `H` (computed by Shopify over `{}` using the app's secret, which the attacker never needs to know).
2. Replay the identical body `{}` and identical `hmac` header `H` to the same endpoint, but set:
   - `X-Shopify-Shop-Domain: victim.myshopify.com`
   - `X-Shopify-Topic: shop/redact` (or any topic already registered by the app)
   - `X-Shopify-Webhook-Id: <arbitrary>`
3. `Utils::HmacValidator.validate` recomputes HMAC over `{}` only, matches `H`, and returns `true` (`lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. `Registry.process` proceeds to dispatch to the handler registered for `shop/redact` with `shop: "victim.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:188-199`), even though the actual event never happened for that shop.
