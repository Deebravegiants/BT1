### Title
Fee token in `EmporiumUpgradeable.payRelayFees` is unauthorised by the wallet signer's EIP-712 signature - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` pulls a "relay fee" directly from a user's persistent `HinkalWallet` via `IHinkalWallet.doSendToRelay`, using `circomData.feeStructure.feeToken` and `circomData.feeStructure.flatFee`. The wallet owner's EIP-712 signature (`EMPORIUM_SIGNATURE_TYPEHASH`) only commits to `emporiumMessage`, the hash of `ops`, `maxFee`, and `deadline` — it never commits to `feeStructure.feeToken`. The code only checks that `flatFee <= maxFee` numerically [1](#0-0) , but the token that `flatFee` is denominated in is left completely unconstrained by the signature.

### Finding Description
`verifyWallet` recovers the signer from a typed-data hash built solely from `circomData.emporiumMessage`, `_hashEmporiumOps(stack.ops)`, `stack.maxFee`, and `stack.deadline` [2](#0-1) . `feeStructure` (which carries `feeToken`, `flatFee`, `variableRate`) is a separate field of `CircomData` that is only bound to the ZK-proof's `calldataHash`/`signedMessageHash`, i.e. authorised by the *note owner's* spending key, not by the *wallet signer's* EIP-712 key [3](#0-2) . These are two different principals: the wallet's persistent balance belongs to `stack.signerAddress`, while the calldata/proof is produced by whoever is proving ownership of an unrelated shielded note (potentially a completely different, unprivileged party who is simply relaying a previously-signed `EmporiumStack` payload).

In `payRelayFees`, when `signerAddress != address(0)` the code sets `relayFee = flatFee` (unbounded by any check that `feeStructure.feeToken` matches what the signer expected) and calls `payRelay` → `sendToRelayFromWallet` → `IHinkalWallet(signerAddress).doSendToRelay(relay, relayFee, feeToken)` [4](#0-3) . `HinkalWallet.doSendToRelay` is guarded only by `onlyEmporium`, so it will execute for any caller that is the Emporium contract, with whatever `erc20TokenAddress` the Emporium instructs [5](#0-4) .

Because `feeToken` is not part of the signed `EMPORIUM_SIGNATURE_TYPEHASH` domain, whoever assembles the on-chain `CircomData` (which only needs *their own* valid ZK proof over *their own* shielded funds/notes, entirely unrelated to the wallet) can attach a previously-issued, still-unused, validly-signed `EmporiumStack` (same `ops`, `maxFee`, `deadline`, `emporiumMessage`) but substitute `feeStructure.feeToken` with any ERC-20 the wallet happens to hold, as long as `flatFee <= maxFee` numerically. This drains `flatFee` units of an attacker-chosen, arbitrarily valuable token from the victim's `HinkalWallet` to `circomData.relay` (attacker-controlled), which breaks the equality that value moved out of the wallet must be exactly what the wallet owner authorised.

### Impact Explanation
This is theft of protocol/user funds held in the persistent `HinkalWallet`: the actual amount extracted is bounded numerically by `maxFee`, but the *denomination* is not, so an attacker can redirect the fee extraction to a token with far higher value than the fee token the signer intended, or to a token the signer never intended to spend at all. This is unauthorised asset movement from a wallet whose owner never approved that specific token being debited — matching the "High: executing calls or moving assets a wallet owner or prover never authorised" impact bucket.

### Likelihood Explanation
Requires possession of any previously-signed, unused `EmporiumStack`/`emporiumMessage` (which is off-chain data the signer necessarily hands to *someone* to submit, since `HinkalWallet`-based stateful ops are explicitly designed for third-party relaying) plus the attacker's own unrelated valid ZK proof to satisfy `performHinkalChecks`. No admin, relayer-trust, or manager privilege is required — any holder of a shielded note can act as the transaction submitter. The main uncertainty is how signed `EmporiumStack` payloads are normally distributed/consumed off-chain (this repo does not include that off-chain flow), so likelihood depends on that distribution channel being reachable to an unprivileged party, which is plausible given the stated purpose of `signerAddress`-based relaying.

### Recommendation
Include `feeStructure.feeToken` (and ideally `flatFee`/`variableRate`) inside the `EMPORIUM_SIGNATURE_TYPEHASH` domain that `stack.signerAddress` signs, so the wallet owner explicitly authorises which token and how much of it can be pulled via `doSendToRelay`, instead of only bounding `flatFee` numerically against `maxFee` while leaving `feeToken` unconstrained.

### Proof of Concept
1. Wallet owner `W` (using `HinkalWallet` at `signerAddress`) signs an `EmporiumStack` for some legitimate operation with `maxFee = 10 (in USDC, 6 decimals => 10e6)`, expecting the flat fee to be paid in USDC.
2. This signed payload (`v,r,s`, `ops`, `maxFee`, `deadline`, `emporiumMessage`) is handed to a third-party submitter (as intended by the stateful-interaction design).
3. Attacker `A`, holding an unrelated valid shielded note of their own, builds `CircomData` with `circomData.emporiumMessage` matching `W`'s signed message, `circomData.feeStructure = {feeToken: WBTC, flatFee: 10e6 (raw units of WBTC, still <= numeric maxFee), variableRate: 0}`, and a valid proof for their own note/erc20TokenAddresses/amountChanges (unrelated to `W`'s wallet).
4. `A` calls `Hinkal.transact(...)` → `_externalTransact` → `EmporiumUpgradeable.runAction` → `verifyWallet` passes (signature only checks `ops`/`maxFee`/`deadline`, and `flatFee(10e6) <= maxFee(10e6)` numerically) → `payRelayFees` → `sendToRelayFromWallet(relay, W, 10e6, WBTC)` → `HinkalWallet(W).doSendToRelay(relay, 10e6, WBTC)` transfers `10e6` raw units of WBTC (worth vastly more than 10 USDC) from `W`'s wallet to `A`-controlled `relay`.
5. `W` never authorised paying fees in WBTC; funds are moved without the wallet owner's consent.

    function verifyWallet(
        EmporiumStack memory stack,
        CircomData calldata circomData
    ) internal {
        EmporiumStorageVars storage $ = _getEmporiumStorage();

        if ($.usedMessages[circomData.emporiumMessage]) {
            revert UsedMessage();
        }

        $.usedMessages[circomData.emporiumMessage] = true;

        if (stack.signerAddress == address(0)) {
            return;
        }

        bytes32 hashedMessage = _hashTypedDataV4(
            keccak256(
                abi.encode(
                    EMPORIUM_SIGNATURE_TYPEHASH,
                    circomData.emporiumMessage,
                    _hashEmporiumOps(stack.ops),
                    stack.maxFee,
                    stack.deadline
                )
            )
        );

        (address recoveredAddress, ECDSA.RecoverError err) = ECDSA.tryRecover(
            hashedMessage,
            stack.v,
            stack.r,
            stack.s
        );
        bool verified = err == ECDSA.RecoverError.NoError &&
            recoveredAddress == stack.signerAddress;
        if (!verified) {
            revert InvalidSignature();
        }
