Webhook `shop` attribution is not covered by the HMAC signature, enabling cross-tenant shop-header spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by HMAC-validating only the raw JSON body, then dispatches to the host application's handler using a `shop` value taken from an HTTP header that is never covered by that signature. This breaks the identity binding `shop authenticated-by-HMAC == shop delivered-to-handler`, mirroring the reported "dual mapping" class of bug: one identity source (the cryptographically verified body) diverges from the identity source actually acted upon (the unauthenticated `shop-domain` header).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes/compares the HMAC exclusively over that signable string: [2](#0-1) 

But `Request#shop` (and `#topic`, `#webhook_id`, `#api_version`) are read straight from HTTP headers, entirely outside the signed payload: [3](#0-2) 

`Registry.process` validates the HMAC (body only) and then builds `WebhookMetadata` — the object handed to the host app's `WebhookHandler#handle` — using `request.shop` from the unauthenticated header: [4](#0-3) 

`WebhookMetadata.shop` is a plain, unauthenticated `String` field consumed directly by handler implementations for per-tenant routing/attribution (e.g., looking up which merchant's session/data to act on): [5](#0-4) 

The equality that should hold is: `shop bound by HMAC(payload) == shop used by handler`. Because the HMAC only binds the body bytes and not the `shop-domain` header, an attacker who can obtain one validly-signed webhook body (e.g., a legitimate webhook delivered to their own store for this app, or any topic whose body is shop-independent/replayable) can resend that exact signed body to the app's webhook endpoint while substituting the `shopify-shop-domain` (or `x-shopify-shop-domain`) header for a different (victim) shop. `HmacValidator.validate` will still pass because it never inspects the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from the victim shop.

### Impact Explanation
This crosses a tenant boundary: the gem allows an attacker to make the host application's webhook handler believe a request is authoritatively "from" a shop it never actually originated from. If the host application, as documented/intended, uses `WebhookMetadata#shop` to select which merchant's session/access token/data to update or act on (the standard use of this field per this gem's own webhook contract), an attacker can inject or corrupt state attributed to an arbitrary victim shop using only a signature computed by Shopify for a different shop (or a generic empty-body payload the attacker's own shop legitimately received). This matches the "cross-tenant access" Critical-impact category: the identity used for authorization/attribution (`shop`) is decoupled from the identity actually covered by the cryptographic proof.

### Likelihood Explanation
Exploitation requires the attacker to have installed the app on at least one shop they control (to receive at least one genuinely-signed webhook body, e.g., an `app/uninstalled` or any topic delivering a `{}`/predictable body) — no `api_secret_key` or leaked credentials are required, satisfying the unprivileged-internet-user threat model. Because `hmac-sha256` only signs the body and Shopify's own webhook payloads for many topics are shop-independent in content (or attacker can trigger a webhook whose body they fully control indirectly, e.g. via their own store metadata), a header-substitution replay is straightforward once the attacker has any one valid `(body, hmac)` pair for this app.

### Recommendation
Bind the `shop` (and ideally `topic`, `api_version`, `webhook_id`) into the signable string, or otherwise cryptographically authenticate the header before using it for handler dispatch — e.g., require the host application to independently verify that `shop-domain` corresponds to a shop with an active, previously-established session/installation rather than trusting the header verbatim after only a body-HMAC check. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used for tenant selection without additional verification (e.g., cross-checking against a stored session for that shop).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives (or synthesizes, for a topic with a fixed/empty body) a legitimately Shopify-signed webhook: body `{}` with header `x-shopify-hmac-sha256: <valid HMAC over "{}">`.
2. Attacker replays this exact `(body, hmac)` pair to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `Digest.hexencode(...)` against `HMAC(secret, "{}")` — this passes because the body and secret are unchanged.
4. `WebhookMetadata.new(..., shop: request.shop, ...)` is built with `shop == "victim-shop.myshopify.com"`, and the host app's registered handler is invoked believing the event is authoritatively for the victim shop: [4](#0-3)
