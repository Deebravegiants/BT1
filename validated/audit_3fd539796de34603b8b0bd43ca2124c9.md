### Title
Webhook shop-domain identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, but the `shop` identity that is subsequently trusted and handed to the app's webhook handler is taken from an HTTP header that is never included in the signed material. This breaks the equality "shop verified by HMAC == shop acted upon by the handler," letting any holder of a validly-signed webhook body (e.g., an attacker who owns their own shop installed on the same app) relabel that payload as belonging to a different, victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop`, `topic`, `api-version`, and `webhook-id` values are all read directly from HTTP headers and are not part of the signed string: [2](#0-1) .

`Utils::HmacValidator.validate` computes the HMAC over exactly `to_signable_string` (the body) using the app's single `Context.api_secret_key`, which is shared by every shop that has installed the app — it is not shop-specific: [3](#0-2) .

`Registry.process` treats a passing HMAC check as authenticating the whole request, then builds `WebhookMetadata` directly from the unauthenticated `shop` header and dispatches it to the app's handler: [4](#0-3) .

Because the same `api_secret_key` is used to validate webhooks for every shop on the app, an attacker who controls their own shop instance of the app can:
1. Trigger a legitimate webhook from their own shop (any topic the app subscribes to), obtaining a body + valid HMAC pair signed with the shared app secret.
2. Replay that exact `raw_body`/HMAC pair to the app's webhook endpoint, but substitute the `X-Shopify-Shop-Domain` header with a victim shop's domain.
3. `HmacValidator.validate` still succeeds because it only checks the body against the secret, which is unchanged — the header is not covered.
4. `Registry.process` raises no error and constructs `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: request.parsed_body, ...)`, feeding attacker-controlled data into the handler under the identity of the victim shop: [5](#0-4) .

This is the direct code-level analog of the reported bug class: a field that is *acted upon* (the `shop` identity used to route/attribute the webhook) is not covered by the authentication primitive (the HMAC) that is supposed to bind the whole message to its source. Exactly as the initial-mint report allowed an attacker to substitute deposit ownership while bypassing the mint's implicit invariant, here an attacker substitutes shop ownership while bypassing the webhook's implicit "HMAC == authenticated request" invariant.

### Impact Explanation
Any host application that relies on `WebhookMetadata#shop` (as returned by this gem) to determine which merchant/tenant a webhook body belongs to — e.g., to update that shop's local records, revoke/rotate credentials on `shop/redact`, act on `app/uninstalled`, or process `customers/data_request`/`customers/redact` GDPR webhooks — can be made to apply attacker-supplied data to a different tenant's records. This is a cross-tenant integrity/confidentiality break attributable to the gem's own authentication primitive (`HmacValidator` + `Webhooks::Request`/`Registry`), matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires: (a) the attacker be a legitimate merchant with the target app installed on their own store (trivial for any public app), and (b) the ability to send an arbitrary HTTP request with a custom `X-Shopify-Shop-Domain` header to the app's webhook endpoint (also trivial, since webhook receivers are unauthenticated HTTP endpoints by design). No access to `api_secret_key`, tokens, or any privileged account is needed — the attacker only needs a validly-signed body they legitimately received via their own shop's webhook deliveries.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) header values into the signed material that `HmacValidator` verifies, e.g., have `Webhooks::Request#to_signable_string` incorporate the `shop-domain`, `topic`, and `webhook-id` headers alongside the raw body (matching how a MAC should cover the full authenticated context), or otherwise cryptographically bind these headers to the payload before trusting them. At minimum, document and enforce that the shop identity used for handler dispatch must be independently cross-checked against session/store state maintained by the host app, since the header alone provides no authenticated binding.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and on `victim-shop.myshopify.com` (attacker only needs their own store; victim just needs to be another installed shop of the same app).
2. Attacker triggers any subscribed webhook topic on their own shop, capturing the raw POST body `B` and the resulting `X-Shopify-Hmac-Sha256: H` header Shopify sent (computed as `HMAC-SHA256(api_secret_key, B)`), per `Webhooks::Request#hmac`/`to_signable_string`: [6](#0-5) .
3. Attacker replays the request to the app's webhook endpoint with the same body `B` and same `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)` and compares to `H` — it matches because the body is unchanged: [7](#0-6) .
5. `Registry.process` proceeds and calls the app's handler with `shop: "victim-shop.myshopify.com"` and the attacker's body content, as if Shopify itself had sent this webhook for the victim's store: [4](#0-3) .

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
