### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authenticated once the HMAC check passes, but the HMAC only covers the raw request body — not the `shop` (or `topic`/`webhook_id`) header that identifies which tenant the event belongs to. This breaks the intended binding `hmac == HMAC(secret, body + shop)`; in reality it is only `hmac == HMAC(secret, body)`, with `shop` trusted unauthenticated.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC over `verifiable_query.to_signable_string`, i.e. only the body: [3](#0-2) 

`Registry.process` gates on this HMAC check and then constructs `WebhookMetadata` directly from the unauthenticated `request.shop` header, handing it to the app-provided handler as the trusted tenant identifier: [4](#0-3) 

Because the app's `client_secret`/webhook signing secret is shared across every shop that has the app installed (it is not per-shop), any merchant who has the app installed can capture one legitimate webhook (valid body + valid HMAC, both computed with the shared secret) delivered to their own shop, and replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value (e.g. a victim shop). `Registry.process` will still find `Utils::HmacValidator.validate` returns `true` (the body/HMAC pair is legitimately signed), and will dispatch the handler with `WebhookMetadata#shop` set to the attacker-chosen shop domain instead of the shop that actually generated the event.

The gem's own documentation confirms this field is expected to be relied upon by host applications as the tenant key, without additional verification, once `Registry.process` is called: "This will verify the request did indeed come from Shopify" then dispatch using `data.shop` (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`). [5](#0-4) [6](#0-5) 

### Impact Explanation
This is a cross-tenant boundary break: an attacker who is a legitimate, unprivileged user of the app on their own store can cause the gem to report webhook events (body content) as originating from an arbitrary other shop domain, because the identity field (`shop`) that downstream code uses to select which tenant's data/session to act on is never covered by the signature that the gem validates. Any host application following the gem's documented pattern (dispatching background work keyed by `data.shop`) inherits this cross-tenant confusion directly from the gem's `Registry.process`/`WebhookMetadata` contract.

### Likelihood Explanation
Requires only that the attacker be a merchant with the app legitimately installed on their own store (an "unprivileged internet user" relative to other tenants) — no access token, secret, or privileged account for the victim shop is needed. Capturing one's own valid webhook body+HMAC pair and replaying it with a different `shop` header is trivial once the app is installed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) header into the HMAC-verified signable string, or independently verify that the `shop` header corresponds to a shop with an active, previously-established session/subscription for that specific `webhook_id`/topic before trusting it in `WebhookMetadata`. At minimum, document that `data.shop` from `WebhookMetadata` must be cross-checked against known installed shops before being used as a tenant key.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook: body `B`, headers include `X-Shopify-Hmac-Sha256: HMAC(secret, B)` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same body `B` and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body successfully (`lib/shopify_api/webhooks/request.rb:45-63`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches the shared secret → returns `true` (`lib/shopify_api/webhooks/registry.rb:190`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `WebhookMetadata.new(shop: request.shop, ...)` is built with `shop: "victim-shop.myshopify.com"` even though the body actually originated from the attacker's own shop, and this is handed to the app's webhook handler as if it were an authentic event for the victim shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
