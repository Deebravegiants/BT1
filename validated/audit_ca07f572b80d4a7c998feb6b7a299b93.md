### Title
Unauthenticated arbitrary call execution from `EmporiumUpgradeable` via zero-dimension `MainEVMCircuitMin` path drains Emporium's held funds - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
When `Dimensions.tokenNumber == 0`, `CircomDataBuilder.formInputForCircom` routes to `formInputEmporiumMin`, which only requires a proof that `message == Poseidon(1)([messageSeed])` with no nullifier, spending-key, or signature constraints. In `EmporiumUpgradeable.runAction`, this combines with `verifyWallet` skipping ECDSA verification entirely when `stack.signerAddress == address(0)`, and with the per-token balance-diff safety check being bypassed because its loop bound (`circomData.erc20TokenAddresses.length`) is zero. The result is that an attacker with zero shielded UTXOs and zero private-key knowledge can force `EmporiumUpgradeable` to execute an arbitrary `endpoint.call{value: op.value}(op.callData)` from its own address, with no accounting check on the resulting balance change, draining any ETH/ERC20 balance currently held by the contract.

### Finding Description
The broken equality is: **"every op.endpoint.call executed by EmporiumUpgradeable was authorized by a party who proved knowledge of a shielded identity (spendingPublicKey/nullifyingPrivateKey) or provided a valid ECDSA signature over that exact op set"** vs. what actually happens when `dimensions.tokenNumber == 0`: **no such authorization is checked at all**.

Trace:
1. `CircomDataBuilder.formInputForCircom` selects `formInputEmporiumMin` when `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`: [1](#0-0) 
2. `MainEVMCircuitMin` only constrains `message <== Poseidon(1)([messageSeed])` — no `spendingPublicKey`, `nullifyingPrivateKey`, or signature verification exists in this circuit: [2](#0-1) 
3. `HinkalHelper.dimensionsCheck` accepts `tokenNumber:0` and simply requires all array lengths (erc20TokenAddresses, amountChanges, inputNullifiers, outCommitments, encryptedOutputs) to equal 0 — nothing prevents this combination for an Emporium action: [3](#0-2) 
4. `Hinkal.transact`'s post-call balance/slippage-diff check loop is bounded by `circomData.erc20TokenAddresses.length`, which is 0, so it never executes: [4](#0-3) 
5. `Hinkal._externalTransact` calls `EmporiumUpgradeable.runAction` (allowed via `onlyAllowedRecipient` because Hinkal itself is the registered recipient): [5](#0-4) [6](#0-5) 
6. Inside `runAction`, `stack` (containing arbitrary `ops`, `signerAddress`, `v/r/s`) is fully attacker-controlled via `externalActionData.externalActionMetadata`. `verifyWallet` marks the message used and **returns immediately without any signature check** when `stack.signerAddress == address(0)`: [7](#0-6) 
7. The stateless branch then executes `op.endpoint.call{value: op.value}(op.callData)` directly from `EmporiumUpgradeable`'s address for every attacker-chosen op: [8](#0-7) 
8. The only guard meant to catch unauthorized fund movement — `balanceChange < 0 revert BalanceChangeShouldBePositive()` — is inside a loop bounded by `circomData.erc20TokenAddresses.length`, which is 0, so it never runs: [9](#0-8) 

The only remaining gate is `HinkalHelper.getHashedCalldata` matching `circomData.calldataHash`, but that is a plain on-chain hash computed by pure Solidity over attacker-supplied calldata fields — it requires no secret and is trivially satisfiable by the attacker who controls every field. `checkOnchainCreation` is a no-op for zero-length arrays. `rootHashExists`/`verifyProof` succeed because the Min circuit and its dedicated verifier (`mainEVMCircuitMin0v4.sol`, 3 public signals matching `formInputEmporiumMin`) impose no identity or fund-custody constraint. Consequently, `AUTHORITY` is broken: the `from` of the call executed against real token/ETH balances (`EmporiumUpgradeable`'s own balance) was never tied to any proven identity.

### Impact Explanation
An unprivileged attacker can drain any ETH or ERC20 balance currently sitting in `EmporiumUpgradeable` (e.g. leftover dust, in-flight funds from other users' concurrent Emporium operations, or any pre-funded balance) to an address of their choosing, using a single `transact` call with a trivially-generated proof and zero cost beyond gas. This is direct, repeatable theft of protocol/user funds parked at a core contract — matching the **Critical** severity bar (direct theft of shielded/in-flight funds, proof/authorization bypass).

### Likelihood Explanation
Preconditions: `EmporiumUpgradeable` must hold a nonzero ETH/ERC20 balance at call time (realistic since it is a shared pot used across users' Emporium interactions, and funds can transiently or persistently sit there between the deposit leg and op-execution leg, or as dust left over from prior operations with balance mismatches). No privileged role, whitelisted relay, or victim key material is required — the attacker only needs to generate a snarkjs proof for `MainEVMCircuitMin` (public and freely compilable) and craft `circomData`/`Dimensions`/`EmporiumStack` fields, all of which are attacker-controlled inputs to `transact`. This is fully repeatable each time Emporium holds a balance.

### Recommendation
- Do not allow `verifyWallet` to skip signature verification when `stack.ops.length > 0`; require a valid signature (or an explicit, separately-authorized "no funds move" mode) regardless of `erc20TokenAddresses.length`.
- Remove the ability to bypass the `runAction` balance-accounting loop by tying it to `stack.ops`/values touched rather than `circomData.erc20TokenAddresses.length`; ensure ETH moved via `op.value` and any ERC20 transfers from arbitrary `op.callData` are always reconciled against a declared, circuit-committed amount.
- Reject the `tokenNumber == 0` / Min-circuit path for the Emporium action entirely, or require it to prove at least the identity constraints (`spendingPublicKey`, `nullifyingPrivateKey`, signature) currently only present in the full `MainEVMCircuit`.

### Proof of Concept
Foundry fork test plan:
1. Deploy/fork with `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` wired as in production; register `EmporiumUpgradeable` as `onlyAllowedRecipient` for itself via Hinkal (as in normal deployment).
2. Seed `EmporiumUpgradeable` with ETH (e.g. `vm.deal(address(emporium), 10 ether)` simulating leftover balance from a legitimate prior `runAction`).
3. Generate a Groth16 proof for `MainEVMCircuitMin` with an arbitrary `messageSeed` using snarkjs, matching `outTimeStamp`/`calldataHash` public inputs.
4. Build `Dimensions{tokenNumber:0, nullifierAmount:0, outputAmount:0}`, `circomData` with `erc20TokenAddresses=[]`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalActionMetadata` = ABI-encoded `EmporiumStack{signerAddress: address(0), ops: [{endpoint: attacker, invokeWallet:false, value:10 ether, callData: ""}], maxFee:0, deadline: type(uint256).max}`.
5. Call `Hinkal.transact(a,b,c,dimensions,circomData)` from an attacker EOA with no prior deposits/UTXOs.
6. Assert: `address(emporium).balance` decreases by 10 ether and `attacker.balance` increases by 10 ether, while `verifyWallet`'s signature branch was never entered (`stack.signerAddress == address(0)`), demonstrating `AUTHORITY` was never checked on both sides of the (broken) equality.
