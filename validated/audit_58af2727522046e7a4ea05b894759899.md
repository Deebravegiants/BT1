## Title
Webhook shop-domain identity spoofing due to unauthenticated `shop` header — cross-tenant webhook confusion ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from only the raw request body, while the `shop` (and `topic`/`webhook_id`/`api_version`) values are read from unauthenticated HTTP headers that are never included in the signed content. This breaks the identity binding `HMAC-verified(raw_body) ⇒ shop-domain-in-headers is authentic`, letting anyone who can trigger a genuinely-signed webhook for their own store (any ordinary merchant installing the app) replay that body+HMAC pair while attaching an arbitrary `shopify-shop-domain` header, causing the host application's webhook handler to process attacker-supplied data under a victim shop's identity.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` verifies a signature by recomputing the HMAC over `verifiable_query.to_signable_string` and comparing it to `verifiable_query.hmac`: [1](#0-0) 

For webhooks, `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` — none of the Shopify-provided headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`) participate in the signed content: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates the HMAC using this body-only signable string, and then — separately and without any additional binding — trusts `request.shop` (sourced from the unauthenticated `shopify-shop-domain` header) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

Because the app's `api_secret_key` is a single shared secret used for HMAC-signing webhooks for *every* shop that installs the app (not a per-shop secret), an unprivileged merchant who installs the app on their own store receives genuinely-signed webhook deliveries (body + valid HMAC) for events they themselves trigger. Since the HMAC never binds the body to the `shop` header, that merchant can capture a legitimate `(raw_body, hmac)` pair from their own shop and replay it to the app's public webhook endpoint with the `shopify-shop-domain` header changed to any other installed shop's domain. `HmacValidator.validate` still succeeds (it only checks the body/HMAC relationship), and `Registry.process` hands the handler a `WebhookMetadata` claiming the (attacker-chosen) victim shop, with attacker-controlled body content.

This is exactly the bug class in the reference report: an authorization/identity check ("is this HMAC valid for this payload") is applied to a narrower scope than the field the application actually acts on (`shop`), letting a value outside the checked scope be forged.

### Impact Explanation
Any downstream consumer that keys tenant state, authorization decisions, or data storage off `WebhookMetadata#shop` (as the gem's own documentation instructs apps to do, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be made to associate attacker-controlled webhook bodies with an arbitrary victim shop domain — a cross-tenant data-integrity/confusion issue. This meets the "cross-tenant access" criteria for Critical impact since the host app has no way, using only what this gem verifies, to know the `shop` field is untrustworthy.

### Likelihood Explanation
Exploitation only requires being a legitimate merchant of the app (no special privilege, no leaked secrets) able to trigger an event that fires a webhook for their own store, plus the ability to send an HTTP POST to the app's public webhook callback URL with modified headers. No access token, `client_secret`, or TLS interception is required.

### Recommendation
Bind the shop identity to the HMAC-verified content, e.g. include the shop domain (and ideally topic/webhook id) in `to_signable_string`, or have the host-facing API require the application to cross-check `request.shop` against the shop of the storage/session it is about to act on, and document that `WebhookMetadata#shop` must never be trusted for tenant selection without an out-of-band binding (e.g. matching against a known, already-authenticated shop record) since it is not covered by the webhook HMAC.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (ordinary, unprivileged merchant action).
2. Attacker triggers any subscribed event (e.g. `orders/create`) on their own shop, causing Shopify to POST a genuinely HMAC-signed webhook to the app's callback URL:
   - `shopify-shop-domain: attacker-shop.myshopify.com`
   - `shopify-hmac-sha256: <valid HMAC over raw_body>`
   - body: attacker-controlled order JSON (attacker fully controls order contents on their own shop).
3. Attacker captures this exact `(raw_body, hmac)` pair and resends it directly to the app's webhook endpoint, only changing the header:
   - `shopify-shop-domain: victim-shop.myshopify.com`
4. `ShopifyAPI::Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only — it matches, since the header change never entered the signed content [4](#0-3) .
5. `ShopifyAPI::Webhooks::Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker JSON>, ...)` [5](#0-4) , and the app processes attacker-controlled data as if it originated from the victim shop.
