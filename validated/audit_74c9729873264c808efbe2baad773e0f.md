## Analog Found

### Title
Tron `IntentGatewayV2.onAccept`/`onGetResponse` never enforce `_checkRelayer`, letting any relayer drain escrow - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The GitLab report describes a control (2FA) that is required on one code path (web) but silently not enforced on an equivalent path (git). The Hyperbridge analog is the Tron `IntentGatewayV2` app: the canonical EVM implementation (`ExtrinsicIntents.sol`) gates *every* `onAccept`/`onGetResponse` delivery behind `_checkRelayer(incoming.relayer)` before any state-changing logic runs, but the Tron variant of the same contract omits that check entirely on both entry points, even though it otherwise mirrors the same `RequestKind`/`withdraw` flow.

### Finding Description
On the reference EVM path, every delivery into the intents app is required to pass an authorised-relayer gate before the request body is even decoded: [1](#0-0) [2](#0-1) 
and this is documented as the deliberate defense against a forged/malicious relayer forging escrow settlement: [3](#0-2) 

The Tron port of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, implements the identical `RequestKind`/`withdraw` logic but never calls `_checkRelayer` (there is no such function or `_relayer` state variable at all in this file): [4](#0-3) [5](#0-4) 

Both functions are gated only by `onlyHost` (i.e., `msg.sender == host`), which any relayer can satisfy simply by delivering a message through the permissionless `HandlerV2`/`EvmHost.dispatchIncoming` pipeline — the relayer address passed into `onAccept`/`onGetResponse` is attacker-controlled `msg.sender` from step 1 of the delivery flow: [6](#0-5) 

So exactly like the GitLab bug — a security control (2FA / relayer authorisation) enforced on one access path but silently skipped on an equivalent one — the Tron gateway drops the relayer-authorisation requirement that the rest of the protocol treats as load-bearing for escrow settlement.

### Impact Explanation
Because `_checkRelayer` is absent, `RedeemEscrow`/`RefundEscrow` requests and GET-response-driven refunds can be delivered by any relayer that can get a request/response through the (permissionless) handler and consensus-proof pipeline, not just the relayer the gateway's governance authorised. Combined with the documented attack model (a forged consensus proof letting an attacker's own relayer report itself as the deliverer), this removes a second layer of defense specifically built to stop an unauthorized relayer from triggering escrow withdrawal — i.e., concrete theft/permanent freezing risk for escrowed funds on the Tron deployment of the intents gateway.

### Likelihood Explanation
Reaching `onAccept`/`onGetResponse` still requires a valid consensus/state proof to be accepted by `EvmHost`/handler, so this is not trivially triggerable by an arbitrary third party under normal, uncompromised consensus. However, the missing check removes the second independent gate that the EVM implementation relies on precisely for the scenario where the first gate (consensus verification) is compromised or where governance intends to restrict delivery to a specific relayer for economic/ordering reasons. Given the code parity between the EVM and Tron contracts elsewhere, and that the design doc explicitly frames `_checkRelayer` as necessary defense-in-depth, its total absence in the Tron contract is a clear regression rather than a deliberate design choice.

### Recommendation
Add the same `_checkRelayer(incoming.relayer)` gate (and a `_relayer`/`setRelayer` mechanism mirroring `ExtrinsicIntents.sol`) to `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `onAccept` and `onGetResponse`, so escrow redemption/refund on Tron enforces the same relayer-authorisation invariant as the canonical EVM gateway.

### Proof of Concept
I could not fully verify a complete end-to-end PoC (e.g., confirming there is no relayer check enforced elsewhere in the Tron contract's constructor/initializer, since I did not see the full file beyond line 744, nor confirm whether this Tron contract is actually deployed/wired to a live `EvmHost`). Based on the visible code:
1. Attacker relays (or colludes with a relayer of) a valid `RedeemEscrow`/`RefundEscrow` `PostRequest`, or the GET response for a cancelled order, through `HandlerV2` with a valid proof.
2. `EvmHost.dispatchIncoming` calls `IntentGatewayV2.onAccept`/`onGetResponse` with `incoming.relayer = msg.sender` of the handler call (attacker-controlled).
3. Unlike `ExtrinsicIntents.sol`, no `_checkRelayer` runs, so `withdraw(...)` executes regardless of which relayer submitted it, releasing escrowed tokens to the beneficiary named in the request/response body.

Given the uncertainty about deployment scope, I recommend this be validated further in a live/full-repo review before treating it as fully confirmed exploitable in production.
