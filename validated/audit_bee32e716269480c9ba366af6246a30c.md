### Title
Relayer fee withdrawal zeroes internal `Fees` accounting before destination-chain disbursement is confirmed, with no reconciliation path if delivery never succeeds - (File: `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
The `FSDVesting` report's root cause is a claim function that mutates internal accounting for a reward *before/without* the corresponding external settlement being guaranteed to occur, permanently losing the user's entitlement if the settlement never happens. `pallet-ismp-relayer`'s `Pallet::withdraw` has the same structural flaw: it zeroes the relayer's `Fees` storage entry immediately after *dispatching* a cross-chain POST request that is supposed to trigger the actual token disbursement on the destination chain, with no callback wired up to restore the fee if that dispatched message is never successfully delivered/executed.

### Finding Description
`Pallet::withdraw` in `modules/pallets/relayer/src/withdrawal.rs` reads the relayer's `available_amount` from `Fees::<T>`, dispatches a `DispatchPost` to the destination chain instructing it to pay out that amount, and then unconditionally zeroes the `Fees` entry: [1](#0-0) 

The module's own doc comment confirms the design intent — that the on-chain effect on Hyperbridge is merely dispatching a message, and actual settlement is deferred entirely to delivery on the destination chain: [2](#0-1) 

Crucially, this dispatched `DispatchPost` is built with `timeout: 0` (no timeout), so if delivery to the destination is never completed — because the destination host manager reverts on `WithdrawalParams` decoding, the manager lacks funds/is misconfigured, the encoded `beneficiary_address`/`account` is malformed, or the relayer network simply never delivers it — the request sits permanently undelivered. Unlike `pallet-ismp`'s own request-timeout path, which does restore escrowed relayer *protocol* fees via `on_request_timeout` (`modules/pallets/ismp/src/host.rs:322-335`), there is no `IsmpModule` implementation in `modules/pallets/relayer/src/lib.rs` for `MODULE_ID = b"ISMP-RLYR"` that handles an `on_timeout`/failure callback to credit the `Fees::<T>` entry back to the relayer. The `Fees::<T>::insert(..., U256::zero())` at line 177 has already executed by the time any of these failure modes can occur, so the relayer's internal accounting shows the fee as withdrawn while the actual token transfer on the destination chain may never happen.

This is the same bug class as the `FSDVesting` report: internal state is debited to reflect a claim, while the actual value transfer is delegated to a downstream call/message that can fail independently, with no mechanism to keep the two in sync or reverse the internal debit on failure.

### Impact Explanation
A relayer's accumulated cross-chain delivery fees (`Fees::<T>` balance, in the fee token/`U256` amount) can be permanently and unrecoverably zeroed on Hyperbridge without the relayer ever receiving the corresponding payout on the destination chain, if the destination-side settlement of the `WithdrawalRequest`/`WithdrawalParams` message fails or is never delivered. Because `Fees` is zeroed synchronously in the same extrinsic that only *dispatches* the message, there is no compensating control (no timeout refund, no manual retry-with-restored-balance path) once that zeroing occurs. This is a straightforward loss-of-funds condition for relayers, who are the actors expected to reach this exact code path via a single signed `withdraw_fees` unsigned-origin extrinsic.

### Likelihood Explanation
Likelihood is moderate: it requires either (a) an EVM `HostManager`/params misconfiguration or transient failure on the destination side (e.g., `MissingMangerAddress`-adjacent misconfig fixed after zeroing, or the destination manager reverting on `WithdrawalParams.abi_encode()` decoding), or (b) the relayer's own delivery client failing to ever submit `handlePostRequests` for this particular commitment (no automatic retry is guaranteed since the request never times out). Given any relayer routinely calls `withdraw_fees` and the destination delivery is an entirely separate, asynchronous, permissionless step performed later by a relayer client, any interruption between the two irrecoverably burns the relayer's fee balance.

### Recommendation
Do not zero `Fees::<T>` until destination-side disbursement is confirmed (e.g., via an `on_response`/delivery-confirmation callback wired into an `IsmpModule` implementation for `MODULE_ID`), or alternatively add a timeout on the dispatched `DispatchPost` together with an `on_timeout` handler in the relayer pallet that credits `Fees::<T>` back to `address` for the given `dest_chain`, mirroring the pattern already used for `pallet-ismp`'s own protocol-fee refund in `modules/pallets/ismp/src/host.rs::on_request_timeout`.

### Proof of Concept
1. A relayer accrues `available_amount` in `Fees::<T>::get(dest_chain, relayer_address)` via `accumulate_fees`.
2. Relayer calls `withdraw_fees` (unsigned, `Pallet::withdraw`): this builds a `DispatchPost` to `HYPERBRIDGE_MODULE_ID`/host manager with `timeout: 0`, dispatches it, and immediately executes `Fees::<T>::insert(dest_chain, address, U256::zero())` — [3](#0-2) .
3. Suppose the destination host manager's `WithdrawalParams` handling reverts (e.g., manager under-funded, or governance changes `host_manager`/`fee_token` between dispatch and delivery) or no relayer ever submits the proof to complete delivery (no timeout exists to force resolution).
4. The relayer's `Fees` entry remains `0` forever; the destination-side payout never lands; there is no code path in the relayer pallet (`modules/pallets/relayer/src/lib.rs`) that restores the balance, since no `IsmpModule`/timeout callback exists for `MODULE_ID`.
5. Result: permanent loss of the relayer's accrued fee, confirmed by the absence of any Fees-crediting callback in the relayer pallet source.

```rust
//! Relayer fee withdrawal.
//!
//! Once fees have been accumulated into [`crate::pallet::Fees`] by
//! [`crate::accumulate`], relayers withdraw them via [`Pallet::withdraw`].
//! The flow:
//!
//! 1. The relayer signs a `(nonce, dest_chain, beneficiary?)` payload with their per-chain key (EVM
//!    secp256k1 / sr25519 / ed25519).
//! 2. The pallet verifies the signature, increments the per-relayer nonce, and dispatches an ISMP
//!    POST request to the destination's host manager (EVM) or `HYPERBRIDGE_MODULE_ID` (substrate)
//!    instructing it to disburse `available_amount` of the fee token to the beneficiary.
//! 3. The `Fees` entry is zeroed so the same balance cannot be withdrawn twice.
//!
//! The on-chain effect is just dispatching the message; the destination chain settles the
//! payout when the ISMP request is delivered there.
```
