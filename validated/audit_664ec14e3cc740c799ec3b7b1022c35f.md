### Title
Webhook `shop` domain is trusted for tenant routing but is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates a webhook by HMAC-verifying only the raw request body, while the `shop` (and `topic`/`webhook_id`/`api_version`) values used to route and attribute the webhook to a tenant come from unauthenticated HTTP headers. Any party that possesses one valid `(raw_body, hmac)` pair for their own shop can replay it while substituting an arbitrary `shop-domain` header, and the registry will process it as if it originated from the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` — the value the HMAC is computed and verified over — returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the signed body: [2](#0-1) 

`ShopifyAPI::Utils::HmacValidator.validate` (used by the registry) confirms only that the HMAC over `to_signable_string` (the body) matches: [3](#0-2) 

`Webhooks::Registry.process` performs exactly that check and then forwards `request.shop` — unauthenticated header data — directly into `WebhookMetadata`, which is handed to the app's handler as the tenant identifier for the event: [4](#0-3) [5](#0-4) 

This is the equality that should hold but does not:
`bytes_verified_by_HMAC (raw_body)` ≠ `bytes_relied_on_for_tenant_identity (shop header, topic header, webhook_id header)`.

Documentation confirms `data.shop` is the field host applications are expected to use to attribute/enqueue per-tenant work: [6](#0-5) 

### Impact Explanation
Because `shop` is not part of the signed payload, anyone who can obtain a single valid `(raw_body, hmac)` pair — e.g., a person who installs the app on their own store (an ordinary, unprivileged action) and receives a legitimate webhook for that store — can replay that exact body/HMAC to the app's webhook endpoint while forging the `shop-domain` header to name a different, victim tenant. `HmacValidator.validate` still passes because it only checks the body, and the registry dispatches the event to the handler labeled with the attacker-chosen shop. Any app logic keyed off `data.shop` (session lookup, per-shop database writes, order/inventory updates, enqueuing background jobs "for shop X") is misattributed to the wrong tenant — a cross-tenant data integrity/isolation break, which is listed as Critical impact in scope.

### Likelihood Explanation
Exploitation only requires: (1) the ability to become an authentic sender of at least one valid webhook (trivial — install the app on a shop the attacker controls, which is a normal unprivileged workflow), and (2) posting an HTTP request to the app's public webhook endpoint with a modified `shop-domain` header alongside the replayed, still-valid body+HMAC. No secrets, tokens, or privileged access are required, making this straightforward for any external actor with a shop of their own using the same app.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the authenticated material before trusting them: either include the shop domain in the HMAC signing computation and re-derive/verify it in `HmacValidator`, or require the caller to independently confirm that the `shop` in the webhook maps to an app installation whose offline access token/session actually exists and is consistent with other side channels (e.g., only accept it after confirming the shop's known install state) rather than trusting the raw header value implicitly. At minimum, document/require host applications to not rely on `data.shop` as an unforgeable identity claim, and make `Request#shop` derivation part of the signed payload contract with Shopify.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering a legitimate webhook delivery with body `B` and a valid `hmac-sha256` header `H = HMAC(secret, B)`.
2. Attacker captures `(B, H)` (they legitimately received this since it was addressed to their own shop).
3. Attacker POSTs to the app's webhook endpoint with:
   - body: `B` (unchanged)
   - `x-shopify-hmac-sha256: H` (unchanged, still valid since only body is signed)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(secret, B) == H`.
5. The handler receives `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, ...)` and performs shop-scoped work attributing `attacker`-shop's webhook payload to `victim-shop`, corrupting or misdirecting victim tenant data/processing.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
