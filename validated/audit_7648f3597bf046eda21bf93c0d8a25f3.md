### Title
Missing re-initialization guard in `LockupContract::new` allows re-initialization of an already-deployed lockup contract - (File: `lockup/src/lib.rs`)

### Summary
The `LockupContract::new` initializer in `lockup/src/lib.rs` is the only production `#[init]` constructor in this repository that does not assert `!env::state_exists()` before writing contract state, unlike every other production contract's initializer.

### Finding Description
Every other production contract in this repo that exposes an `#[init]` constructor explicitly guards against re-initialization by asserting the contract state does not already exist:
- `whitelist/src/lib.rs`: `assert!(!env::state_exists(), "Already initialized");` [1](#0-0) 
- `staking-pool/src/lib.rs`: `assert!(!env::state_exists(), "Already initialized");` [2](#0-1) 
- `staking-pool-factory/src/lib.rs`: `assert!(!env::state_exists(), "The contract is already initialized");` [3](#0-2) 
- `multisig/src/lib.rs`: `assert!(!env::state_exists(), "Already initialized");` [4](#0-3) 
- `voting/src/lib.rs`: `assert!(!env::state_exists(), "The contract is already initialized");` [5](#0-4) 
- `lockup-factory/src/lib.rs`: `assert!(!env::state_exists(), "The contract is already initialized");` [6](#0-5) 

`LockupContract::new` in `lockup/src/lib.rs`, however, has no such check — it only validates account-ID formats and vesting/foundation-account consistency before unconditionally returning a fresh `Self`: [7](#0-6) 

Because every sibling contract in this same codebase adds this guard explicitly (rather than relying purely on the `#[init]` macro), the consistent convention across the repo indicates the `#[init]` attribute itself does not automatically prevent re-invocation of the constructor as a regular function call once state exists — the guard is expected to be added manually in each initializer. `LockupContract::new` breaks this pattern, leaving the lockup contract's initializer callable again on an already-initialized contract account.

An unprivileged caller who can invoke `new` again on an already-deployed and funded lockup contract account (e.g., via a direct function call, or as an unintended path during the lockup-factory's deploy-then-initialize flow in `lockup-factory/src/lib.rs`) could overwrite `owner_account_id`, `lockup_information`, `vesting_information`, `staking_information`, and `foundation_account_id` with attacker-supplied values, since `lockup_information.lockup_amount` is recomputed from `env::account_balance()` at call time. Because `owner_account_id` is fully attacker-controlled on re-init, a successful re-initialization would let the caller reset themselves as the lockup owner, wipe out an in-progress vesting/termination state, and gain the ability to invoke owner-only functions (e.g., `transfer`, `select_staking_pool`, `add_full_access_key`) to move the locked NEAR balance to themselves once the (attacker-controlled) unlock conditions are met.

### Impact Explanation
If the initializer can be called a second time by an unprivileged party, it maps to: (1) unauthorized transfer/withdrawal of locked NEAR through an authorization bypass in the lockup flow (owner reassignment), and (2) state-transition bypass allowing an unprivileged user to seize owner privileges over the lockup contract — both in the Critical/High allowed-impact categories for lockup release flows.

### Likelihood Explanation
Likelihood depends on whether an attacker-controlled entry path actually exists to call `new` a second time against an already-initialized lockup account. This requires either: the underlying NEAR runtime/near-sdk version in use not rejecting a second call to an `#[init]`-marked method once state exists, or some flow that permits calling `new` directly against the deployed lockup account as a plain function call (which any account can attempt, since lockup contracts have no access keys and calls are permissionless function calls). I was not able to fully confirm from the repository content alone whether the specific near-sdk-rs version vendored/used here enforces the "reject `#[init]` call if state exists" behavior at the macro level independent of an explicit `assert!(!env::state_exists())` — the `Cargo.lock`/`Cargo.toml` dependency resolution and near-sdk macro source were not fully inspectable within this session. Given that all other in-repo initializers add this assertion explicitly despite already using `#[init]`, the repo's own convention strongly suggests the macro does **not** provide this guarantee unconditionally, making the missing check in `lockup/src/lib.rs` a genuine root-cause gap rather than defense-in-depth.

### Recommendation
Add the same guard used in every other contract's initializer to `LockupContract::new` in `lockup/src/lib.rs`, immediately as the first statement of the function:
```rust
assert!(!env::state_exists(), "The contract is already initialized");
```
This aligns `lockup/src/lib.rs` with the established initializer pattern already present in `whitelist/src/lib.rs`, `staking-pool/src/lib.rs`, `staking-pool-factory/src/lib.rs`, `multisig/src/lib.rs`, `voting/src/lib.rs`, and `lockup-factory/src/lib.rs`.

### Proof of Concept
1. Deploy the lockup contract WASM to an account and call `new(...)` once to initialize it normally (owner = `victim.near`, some vesting schedule, funded with locked NEAR).
2. As an unprivileged attacker, submit a `FunctionCall` action to the same lockup account invoking `new(...)` again with `owner_account_id = attacker.near` and no vesting schedule.
3. Because `LockupContract::new` never checks `env::state_exists()` (unlike all sibling initializers in this repo), the call succeeds if the runtime/SDK does not independently block re-invocation of `#[init]` methods, overwriting the contract's `owner_account_id` and vesting/termination state.
4. `attacker.near` then calls owner-only methods (e.g., `transfer`) to move the locked NEAR balance out once any unlock condition it now controls is satisfied.

    #[init]
    pub fn new(
        owner_account_id: AccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        transfers_information: TransfersInformation,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        staking_pool_whitelist_account_id: AccountId,
        foundation_account_id: Option<AccountId>,
    ) -> Self {
        assert!(
            env::is_valid_account_id(owner_account_id.as_bytes()),
            "The account ID of the owner is invalid"
        );
        assert!(
            env::is_valid_account_id(staking_pool_whitelist_account_id.as_bytes()),
            "The staking pool whitelist account ID is invalid"
        );
        if let TransfersInformation::TransfersDisabled {
            transfer_poll_account_id,
        } = &transfers_information
        {
            assert!(
                env::is_valid_account_id(transfer_poll_account_id.as_bytes()),
                "The transfer poll account ID is invalid"
            );
        }
        let lockup_information = LockupInformation {
            lockup_amount: env::account_balance(),
            termination_withdrawn_tokens: 0,
            lockup_duration: lockup_duration.0,
            release_duration: release_duration.map(|d| d.0),
            lockup_timestamp: lockup_timestamp.map(|d| d.0),
            transfers_information,
        };
        let vesting_information = match vesting_schedule {
            None => {
                assert!(
                    foundation_account_id.is_none(),
                    "Foundation account can't be added without vesting schedule"
                );
                VestingInformation::None
            }
            Some(VestingScheduleOrHash::VestingHash(hash)) => VestingInformation::VestingHash(hash),
            Some(VestingScheduleOrHash::VestingSchedule(vs)) => {
                VestingInformation::VestingSchedule(vs)
            }
        };
        assert!(
            vesting_information == VestingInformation::None ||
                env::is_valid_account_id(foundation_account_id.as_ref().unwrap().as_bytes()),
            "Foundation account should be added for vesting schedule"
        );

        Self {
            owner_account_id,
            lockup_information,
            vesting_information,
            staking_information: None,
            staking_pool_whitelist_account_id,
            foundation_account_id,
        }
    }
