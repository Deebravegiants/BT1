### Title
`PoaBridge.describeWithdrawal()` matches withdrawals by `assetId` alone, misreporting `(status, txHash)` when a batch contains two withdrawals of the same asset - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal()` calls `findMatchingWithdrawal()`, which selects an entry from the unsorted `response.withdrawals` array purely by comparing `nep141:${w.data.near_token_id}` to `args.withdrawalParams.assetId`. If a batch withdrawal contains two entries with the same `assetId` but different `destinationAddress`/`amount`, both indices resolve to the *same* (arbitrarily chosen, `Array.find` first-match) entry, so the `(status, txHash)` reported for withdrawal `i` can equal the outcome of withdrawal `j`.

### Finding Description
The broken equality is: for withdrawal index `i` in a batch, `describeWithdrawal({index: i, withdrawalParams: paramsᵢ, ...}).txHash` must equal the transfer hash of the on-chain withdrawal that actually corresponds to `paramsᵢ` (i.e., its own `destinationAddress`/`amount`), not the hash of any other withdrawal `j` in the batch.

Code path: `PoaBridge.describeWithdrawal()` [1](#0-0)  calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which is implemented as: [2](#0-1) 

The function's own doc comment acknowledges the limitation: "Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported." [3](#0-2) 

Root cause: the PoA indexer's `getWithdrawalStatus` response returns an unsorted `withdrawals` array keyed by `withdrawal_hash` (the shared NEAR intent tx hash), and `Array.prototype.find` picks the first array element whose `near_token_id` matches, ignoring `destinationAddress`/`amount`/`index`. Nothing in `WithdrawalIdentifier` (`landingChain`, `index`, `withdrawalParams`, `tx`) is used to disambiguate beyond `assetId` — the `index` field on `WithdrawalIdentifier` is never consulted inside `findMatchingWithdrawal`. There is no `validateWithdrawal`, `supports()`, or contract-level check that rejects two withdrawals of the same `assetId` within a single batched intent — `IntentsSDK.createWithdrawalIntents` and `signAndSendWithdrawalIntent` process each entry of `withdrawalParams[]` independently and impose no uniqueness constraint on `assetId` across the batch. Any caller/integrator can freely construct a batch with `withdrawalParams: [{assetId: "nep141:x", destinationAddress: A, amount: 1}, {assetId: "nep141:x", destinationAddress: B, amount: 2}]`.

Exploit flow:
1. Attacker (an ordinary user or a counterparty whose addresses/amounts an integrator forwards) submits a batch withdrawal with two entries sharing the same `assetId` but distinct `destinationAddress`/`amount`.
2. Both withdrawals settle on-chain via the same NEAR intents tx (`withdrawal_hash`), and the PoA indexer returns both entries in `response.withdrawals` in indexer-determined (unsorted) order.
3. When the integrator polls `describeWithdrawal` for index 0 and index 1, both calls query the same `withdrawal_hash` and both use `findMatchingWithdrawal` with the identical `assetId`, so `Array.find` returns the same entry (the first match) for both indices.
4. The integrator sees withdrawal 0 reported "completed" with withdrawal 1's `transfer_tx_hash` (or vice versa), even though the two withdrawals go to different addresses/amounts.

### Impact Explanation
This is a status/hash misreport (not a fund misdirection at the protocol level — the actual on-chain PoA transfers still go to their correct destinations/amounts as encoded in the intents). However, the SDK-facing consumer (an integrator relying on `describeWithdrawal`/`waitForWithdrawalCompletion` per index) can be told that withdrawal `i` completed with withdrawal `j`'s `txHash`. This matches the "status or hash misreport making an integrator credit or refund twice" category (High): an integrator could credit/mark-complete the wrong internal ledger entry, or double-credit if it later also matches the correct entry through some other path, or fail to detect that withdrawal `i` actually failed while `j` succeeded (or vice versa). This is repeatable on every batch containing duplicate `assetId` entries, and is fully attacker-controlled since the attacker can pick which `assetId`, `destinationAddress`, and `amount` to combine into one batch (any user can create their own batch withdrawals with duplicate assetIds).

### Likelihood Explanation
Preconditions: a batch withdrawal (`withdrawalParams` array) with ≥2 entries sharing the same `assetId` on the PoA bridge route, and the PoA bridge's indexer returning an unsorted list containing all withdrawals under one `withdrawal_hash`. No special permissions, contract admin, or malicious infrastructure are required — an ordinary user constructing their own batch withdrawal (or a counterparty supplying `destinationAddress`/`assetId` values that an integrator forwards) can trigger it directly through the public `signAndSendWithdrawalIntent`/`processWithdrawal`/`createWithdrawalCompletionPromises` APIs. This is a straightforward, repeatable condition, not requiring any race or timing since indexing order is not attacker-controlled but sameness of `assetId` is. Confidence in root cause is high given the explicit acknowledging code comment; verifying the actual indexer response shape/ordering (`packages/internal-utils/src/poaBridge/poaBridgeHttpClient`) would further confirm behavior but the match-by-assetId-only logic itself is the confirmed root cause in-repo.

### Recommendation
Disambiguate matches using more than `assetId`: match by `assetId` **and** `destinationAddress` (and optionally `amount`) from `args.withdrawalParams`, or track per-entry state (e.g., mark matched indices as consumed so subsequent calls in the same batch cannot re-match an already-claimed indexer entry). Where the PoA API cannot support the necessary uniqueness, sort candidates deterministically by `amount` for same-`assetId` entries (as hinted in the existing comment) and pair them with withdrawal params sorted the same way, rather than returning the first `Array.find` match to every duplicate-`assetId` index. Additionally, consider adding a `validateWithdrawal`/batch-level check that rejects (or explicitly documents as unsupported) duplicate `assetId` entries within a single POA-bridge batch until proper disambiguation is implemented.

```ts
import { describe, it, expect, vi } from "vitest";
import { poaBridge } from "@defuse-protocol/internal-utils";
import { PoaBridge } from "./poa-bridge";

describe("PoaBridge.describeWithdrawal - duplicate assetId in batch", () => {
  it("misreports txHash when two withdrawals share assetId", async () => {
    const bridge = new PoaBridge({ envConfig: /* mock env with poaTokenFactoryContractID */, xrplRpcUrls: [] });

    const sharedAssetId = "nep141:usdt.omft.near";
    const withdrawalA = {
      status: "COMPLETED",
      data: { near_token_id: "usdt.omft.near", transfer_tx_hash: "0xAAA", /* destination A, amount 1 */ },
    };
    const withdrawalB = {
      status: "COMPLETED",
      data: { near_token_id: "usdt.omft.near", transfer_tx_hash: "0xBBB", /* destination B, amount 2 */ },
    };

    vi.spyOn(poaBridge.httpClient, "getWithdrawalStatus").mockResolvedValue({
      withdrawals: [withdrawalA, withdrawalB],
    });

    const tx = { hash: "sharedNearTxHash", accountId: "user.near" };

    const result0 = await bridge.describeWithdrawal({
      index: 0,
      landingChain: "near:mainnet",
      withdrawalParams: { assetId: sharedAssetId, destinationAddress: "addrA", amount: 1n } as any,
      tx,
    });

    const result1 = await bridge.describeWithdrawal({
      index: 1,
      landingChain: "near:mainnet",
      withdrawalParams: { assetId: sharedAssetId, destinationAddress: "addrB", amount: 2n } as any,
      tx,
    });

    // BUG: both resolve to the same first-matched entry (0xAAA) instead of
    // result0.txHash === "0xAAA" (its own) and result1.txHash === "0xBBB" (its own).
    expect(result0).toEqual({ status: "completed", txHash: "0xAAA" });
    expect(result1).toEqual({ status: "completed", txHash: "0xAAA" }); // should be "0xBBB", proving misreport
  });
});
```

Both sides of the claimed equality (`describeWithdrawal(0).txHash === withdrawal_for_index_0.txHash` and `describeWithdrawal(1).txHash === withdrawal_for_index_1.txHash`) diverge: index 1 incorrectly receives index 0's `txHash`, confirming the STATUS TRUTH violation.

```typescript
/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
```
