### Title
Malicious HyperApp `from` contract can permanently freeze another user's relayer fee by always reverting `onPostRequestTimeout`/`onGetTimeout` - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch()` fixes `PostRequest.from`/`GetRequest.from` to the calling app contract, but allows the fee `payer` to be an arbitrary, different address. On timeout, `dispatchTimeOut()` invokes the timeout callback on `from` and only refunds the fee to `payer` if that callback succeeds; if it reverts, the `FeeMetadata` is restored for a retry rather than refunded. A malicious or buggy `from` app that unconditionally reverts its timeout callback can therefore permanently block fee refunds owed to unrelated `payer` addresses, exactly mirroring the Cooler `onRepay`-revert pattern where a privileged callback owner (lender/app) can force a bad outcome (default/permanent loss) on an unprivileged counterparty (borrower/payer).

### Finding Description
`dispatch(DispatchPost)` sets `from: abi.encodePacked(_msgSender())` (the calling app) while `payer` (stored in `FeeMetadata.sender`) can be any address supplied by the app, e.g. via `HyperApp.dispatchWithFeeToken()`, which pulls fee tokens from `request.payer` — a caller-supplied address, not necessarily `from` itself. This means a single deployed "app" contract can act as `from` for many different users who each supply themselves as `payer` and have their tokens pulled to fund the dispatch fee. On timeout, `dispatchTimeOut(PostRequestTimeout)`/`dispatchTimeOut(GetRequestTimeout)` call the fixed `from` address's `onPostRequestTimeout`/`onGetTimeout`; only on success is `meta.fee` refunded to `meta.sender` (the payer). If the call fails, the code deliberately re-stores the commitment "so that it can be retried" instead of refunding — with no bound on retries or fallback refund path. A malicious `from` contract with a callback that always reverts (e.g., `revert()` unconditionally, or a condition it fully controls) guarantees the refund branch is never reached, permanently trapping the payer's fee tokens inside the Host contract.

### Impact Explanation
Any payer who funds a dispatch fee through a third-party/shared app contract is exposed to permanent freezing of their relayer fee if that app's request later times out and the app's owner (or an exploited/compromised app) chooses to never let the timeout callback succeed. This is a permanent freezing-of-funds condition reachable purely through normal dispatch/timeout flows — no privileged role is required by the attacker beyond deploying/controlling the `from` application contract that other users are induced to route fee-paying dispatches through.

### Likelihood Explanation
Likelihood is significant because: (1) the `payer`/`from` separation is a first-class, documented feature (`dispatchWithFeeToken`, `post.payer`), actively encouraging multi-tenant apps where the payer differs from the dispatching contract; (2) the timeout-message submission is fully permissionless, so anyone (including the malicious app owner) can trigger `dispatchTimeOut` repeatedly with no effect other than re-confirming the fee stays stuck; (3) no protocol-level fallback (e.g., time-boxed forced refund, or refund independent of the app-callback outcome) exists to recover the payer's funds.

### Proof of Concept
1. Attacker deploys `EvilApp` implementing `IApp`/`HyperApp` whose `onPostRequestTimeout` (and/or `onGetTimeout`) unconditionally reverts.
2. Attacker exposes a public function that lets any user (Victim) call `dispatchWithFeeToken` with `request.payer = Victim`, pulling `Victim`'s fee tokens via `safeTransferFrom` and dispatching with `request.from = address(EvilApp)`.
3. `EvmHost.dispatch()` stores `_requestCommitments[commitment] = FeeMetadata({sender: Victim, fee: fee})` per `evm/src/core/EvmHost.sol:948`.
4. The request times out on the destination (never delivered, or destination never processes it).
5. Anyone submits a valid timeout proof to `handlePostRequestTimeouts`, which calls `EvmHost.dispatchTimeOut(PostRequestTimeout, meta, commitment)`.
6. `EvmHost` calls `EvilApp.onPostRequestTimeout(...)`, which reverts; per `evm/src/core/EvmHost.sol:895-899`, the commitment is restored and no refund is issued.
7. Step 5–6 can be repeated indefinitely; `Victim`'s fee tokens remain permanently locked in the Host contract, with no path to recovery.

### Recommendation
Decouple the fee refund from the success of the application's timeout callback: refund `meta.sender` unconditionally (or via a pull-based claim) once the timeout proof is verified, and treat the app callback invocation as best-effort (e.g., wrap in try/catch and proceed regardless of its outcome), similar to the Cooler audit's recommendation to isolate lender-callback failures from the borrower's ability to complete their action.

    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));
