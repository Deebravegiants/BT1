### Title
Fixed, unbenchmarked `{1_000_000}` weight on `pallet-ismp-relayer`'s unsigned proof-verification extrinsics enables denial-of-service via unbounded state-proof batches - (File: `modules/pallets/relayer/src/lib.rs`)

### Summary
`pallet-ismp-relayer` dispatches four unsigned extrinsics — `accumulate_fees`, `withdraw_fees`, `claim_outbound_consensus_delivery_reward`, and `claim_outbound_request_delivery_reward` — each annotated with a hardcoded, unbenchmarked weight literal of `{1_000_000}` picoseconds of ref-time, regardless of the size or complexity of the payload they process. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`accumulate_fees` in particular takes an unbounded `WithdrawalProof` whose `commitments: Vec<H256>` field has no declared size limit, and for every commitment it performs Merkle/state-trie membership verification against both a source-chain proof and a destination-chain proof (`verify_withdrawal_proof`, called twice), decodes and validates fee metadata (RLP for EVM, SCALE for substrate), and performs signature recovery for the beneficiary redirect path. [4](#0-3) [5](#0-4) 

None of this cost scales with the declared weight — the extrinsic is charged a flat `1_000_000` (≈1 microsecond of ref-time, negligible compared to real trie-proof verification and cryptographic signature recovery), independent of `n` = number of commitments in the batch or the size of the supplied Merkle proof. This is the same root cause as the referenced SORA report: a dispatchable whose declared weight does not reflect (or under-reflects) its actual execution cost, allowing an attacker to consume disproportionate block execution time relative to the weight fee/block-weight budget it's charged against.

Critically, all four calls are dispatched via `ensure_none(origin)` — they are **unsigned extrinsics** reachable by anyone, gated only by `validate_unsigned`/`pre_dispatch` checks (which for this pallet largely just re-run parts of the same expensive verification or dedupe via `provides` tags), not by a fee-paying signed origin. [6](#0-5) [7](#0-6) 

Because `Fees`, `Nonce`, `OutboundConsensusRotationsClaimed`, and `OutboundRequestsClaimed` maps are keyed such that malformed/never-going-to-validate but structurally valid `WithdrawalProof`/claim payloads can still be constructed with arbitrarily large `commitments` vectors or large trie proofs, an attacker can submit unsigned transactions that force the node to perform large amounts of trie-proof verification and signature-recovery work while being priced (for weight/block-fullness accounting purposes) as if it cost 1,000,000 ref-time units flat — the same class of "zero/flat weight lets you buy far more execution than you pay for" issue flagged in the SORA report for `BridgeMultisig`/`PswapDistribution` extrinsics.

### Impact Explanation
This is a Medium/High severity issue: an attacker able to submit unsigned extrinsics can repeatedly call `accumulate_fees` with large `commitments` vectors and correspondingly sized (even if ultimately invalid) Merkle proofs. Each call is billed only `1_000_000` weight units against the block's weight limit, letting an attacker pack many such calls into a single block far beyond what the flat weight accounting assumes, consuming actual CPU time disproportionately and potentially causing block production delays or denial of service for legitimate relayer traffic and other transactions competing for block weight. Because these are unsigned extrinsics with no direct fee cost to the sender, the attack is also economically cheap relative to a signed-and-fee-metered equivalent.

### Likelihood Explanation
Likelihood is High for the mechanism (constructing and submitting `accumulate_fees`/withdrawal/claim payloads with large-but-invalid commitment/proof data requires no special privilege — it is a `ensure_none` origin, callable by any actor who can get a transaction into the pool) — though the size of `validate_unsigned` filtering (dedup by `provides` tag, membership pre-checks in `pre_dispatch`/`validate_unsigned` for related calls) may reduce the effective spam surface if that logic runs cheaply and quickly rejects unbounded batches before extrinsic execution. This detail could not be fully confirmed for `accumulate_fees`/`withdraw_fees` specifically within the available index (their `ValidateUnsigned` implementation was not located in the search results), so the exact mempool-level cost-to-reject cannot be verified here — this uncertainty should be resolved by inspecting `modules/pallets/relayer/src/lib.rs`'s `ValidateUnsigned` impl (or wherever it is defined) in a full checkout.

### Recommendation
Short term: benchmark `accumulate_fees`, `withdraw_fees`, `claim_outbound_consensus_delivery_reward`, and `claim_outbound_request_delivery_reward` using `frame-benchmarking`, with weight scaling as a function of the number of commitments/proof size (`n: Linear<...>`), replacing the flat `{1_000_000}` literals with proper `T::WeightInfo::*()` calls (as is already done correctly elsewhere in this codebase, e.g. `parachain/runtimes/*/src/weights/pallet_utility.rs`, `modules/ismp/clients/parachain/client/src/weights.rs`). Additionally, bound `WithdrawalProof::commitments` and the `OutboundConsensusDeliveryClaim`/`OutboundRequestDeliveryClaim` proof payload sizes with `BoundedVec` types so the worst-case benchmarked weight has a fixed upper bound, and ensure `validate_unsigned`/`pre_dispatch` for these calls perform lightweight, O(1) rejection of oversized payloads before falling through to the expensive verification path.

### Proof of Concept
Not independently executed; the vulnerability is demonstrated statically by the code paths cited above:
1. `Pallet::accumulate_fees` is `ensure_none`-gated and declared `#[pallet::weight({1_000_000})]`. [6](#0-5) 
2. Its handler `Pallet::accumulate` accepts an unbounded `Vec<H256>` of commitments and performs two full state-trie proof verifications plus signature recovery per call, with cost scaling in the number of commitments/proof size. [4](#0-3) 
3. No `WeightInfo::accumulate_fees(n)`-style component-based weight function exists for this pallet (unlike other pallets in this repo, e.g. `modules/ismp/clients/parachain/client/src/weights.rs`, which correctly parameterize weight by batch size `n`). [8](#0-7) 

A full PoC (constructing an actual oversized `WithdrawalProof` and measuring execution time vs. charged weight) would require running the runtime locally and is not verifiable from static indexing alone.

```rust
	pub fn accumulate(mut withdrawal_proof: WithdrawalProof) -> DispatchResult {
		// Reject duplicate commitments within the batch. The wire format is a
		// `Vec` and this extrinsic is unsigned, so this is the line of defence
		// against an attacker padding the batch with identical commitments to
		// double-claim fees.
		let mut seen = alloc::collections::BTreeSet::new();
		for key in withdrawal_proof.commitments.iter() {
			ensure!(seen.insert(key.encode()), Error::<T>::DuplicateCommitment);
		}

		// Filter out already-claimed / missing commitments
		withdrawal_proof.commitments = withdrawal_proof
			.commitments
			.into_iter()
			.filter(|req| match RequestCommitments::<T>::get(*req) {
				Some(leaf_meta) => !leaf_meta.claimed,
				// If request commitment does not exist in storage which should not be
				// possible, we skip it
				None => false,
			})
			.collect();
		ensure!(!withdrawal_proof.commitments.is_empty(), Error::<T>::MissingCommitments);
		let host = <T as Config>::IsmpHost::default();
		let source_sm = validate_state_machine(&host, withdrawal_proof.source_proof.height)
			.map_err(|_| Error::<T>::ProofValidationError)?;
		let dest_sm = validate_state_machine(&host, withdrawal_proof.dest_proof.height)
			.map_err(|_| Error::<T>::ProofValidationError)?;
		let state_machine = withdrawal_proof.source_proof.height.id.state_id;
		let source_keys = Self::source_fee_commitment_keys(
			state_machine,
			&*source_sm,
			&withdrawal_proof.commitments,
		);
		let dest_keys = dest_sm.receipts_state_trie_key(withdrawal_proof.commitments.clone());

		let source_result = Self::verify_withdrawal_proof(
			&*source_sm,
			&withdrawal_proof.source_proof,
			source_keys.clone(),
		)?;
		let dest_result = Self::verify_withdrawal_proof(
			&*dest_sm,
			&withdrawal_proof.dest_proof,
			dest_keys.clone(),
		)?;
		let (result, claimed_commitments) = Self::validate_results(
			&withdrawal_proof,
			source_keys,
			dest_keys,
			source_result,
			dest_result,
		)?;
```

```rust
	pub fn verify_withdrawal_proof(
		state_machine: &dyn ismp::consensus::StateMachineClient,
		proof: &Proof,
		keys: Vec<Vec<u8>>,
	) -> Result<BTreeMap<Vec<u8>, Option<Vec<u8>>>, DispatchError> {
		let host = <T as Config>::IsmpHost::default();
		let state = host
			.state_machine_commitment(proof.height)
			.map_err(|_| Error::<T>::ProofValidationError)?;
		// Select the trie root explicitly instead of letting the relayer-supplied proof choose
		// it. Fee accumulation reads ISMP request/receipt metadata, which lives in the global
		// state trie on EVM chains and in the ISMP child trie (overlay root) on substrate
		// chains.
		let root = if proof.height.id.state_id.is_evm() {
			state.state_root
		} else {
			state.overlay_root.ok_or(Error::<T>::ProofValidationError)?
		};
		let result = state_machine
			.verify_state_proof(&host, keys, root, proof)
			.map_err(|_| Error::<T>::ProofValidationError)?;

		Ok(result)
	}
```
