## Title
CallDispatcher.dispatch() has no caller restriction, allowing anyone to seize funds transiently held by the dispatcher - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch()` is a public, unauthenticated entry point that executes an arbitrary array of `{to, value, data}` calls using whatever native ETH/ERC20 balance the `CallDispatcher` contract currently holds. This is structurally identical to the `MulticallWithoutCheck` bug class: a shared "multicall"-style executor that performs privileged fund movements without verifying that the caller is the authorized orchestrator (e.g. `IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`).

### Finding Description
`CallDispatcher` is a single shared, stateless contract used by multiple apps (`IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`) to perform "predispatch"/"postdispatch" calldata execution against tokens that are transferred to it beforehand: [1](#0-0) 

The `dispatch` function has **no access-control modifier** restricting `msg.sender` — any address can call it directly with any `Call[]`, and it will happily forward `call.value` (native ETH) and execute arbitrary calldata against any contract, using the balance currently sitting in the `CallDispatcher`:

```solidity
function dispatch(bytes memory encoded) external {
    Call[] memory calls = abi.decode(encoded, (Call[]));
    ...
    (bool success, bytes memory result) = to.call{value: call.value}(call.data);
    if (!success) revert CallFailed(to, result);
}
```

The dispatcher is also designed to hold value transiently: it has a permissionless `receive()` function and is the target of token/ETH transfers from `IntentGatewayV2.placeOrder` before the predispatch call executes: [2](#0-1) 

After the predispatch call runs, `IntentGatewayV2` only sweeps back the specific tokens declared in `order.inputs` — any other token or native balance left in the dispatcher (e.g. an intermediate-hop token from a multi-hop swap route, leftover slippage residue, referral/reward tokens paid out by the target protocol, or ETH sent to it directly via `receive()`) is **not** accounted for or swept: [3](#0-2) 

The same unrestricted-dispatch pattern is used by `IntentsBase._execute` (postdispatch) and by `HyperFungibleToken`/`WrappedHyperFungibleToken` `onAccept`, all of which transfer funds into the dispatcher and then call `dispatch()`: [4](#0-3) [5](#0-4) 

Because `dispatch()` itself enforces no caller check and no notion of "whose funds these are," any balance the `CallDispatcher` holds at any point — whether from an in-flight legitimate flow (front-runnable within the mempool before the gateway's own sweep transaction lands, since these are two separate top-level calls that any user could interleave against via a different transaction if timing allows) or from unswept dust left after a predispatch/postdispatch call — is directly claimable by an unrelated third party simply by calling `CallDispatcher.dispatch()` themselves with a `Call` that transfers the balance to their own address.

### Impact Explanation
Any ERC20 or native token balance transiently or persistently held by the shared `CallDispatcher` is stealable by an arbitrary unprivileged caller, since `dispatch()` performs no authorization check on `msg.sender` and simply executes whatever `Call[]` is supplied against the contract's own funds. Given `CallDispatcher` is shared across `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken`, and routinely receives ERC20/ETH transfers ahead of executing solver-/user-supplied swap or DeFi calldata, dust or race-window balances represent theftable funds — this is a direct fund-theft primitive, matching the "concrete theft of funds" bar.

### Likelihood Explanation
Exploitation requires no special privilege: any address can call `CallDispatcher.dispatch(bytes)` directly. The main precondition is that the dispatcher hold a nonzero balance at the moment of the attacker's call — which can occur from unswept residual tokens after a predispatch/postdispatch execution (e.g., a multi-hop swap route producing an intermediate token not listed in `order.inputs`/`order.output.assets`, or slippage remnants), or from a race against the two sequential `dispatch()` calls inside `placeOrder`/`_execute` within the same block via mempool observation.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by the set of authorized caller contracts (e.g., `IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`) via an `onlyAuthorized`/`onlyOwner`-style modifier, or make `CallDispatcher` deploy per-order/per-flow (ephemeral, single-use) so it never accumulates externally-drainable residual balance. Additionally, ensure sweep logic in `IntentGatewayV2`/`IntentsBase` accounts for all tokens the predispatch/postdispatch call could plausibly touch, not just the declared `inputs`/`output.assets`.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
