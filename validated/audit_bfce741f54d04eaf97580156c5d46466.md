### Title
Webhook Shop-Domain Header Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) from the unauthenticated `x-shopify-shop-domain` HTTP header, while the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` validates only covers the raw request body. This breaks the identity binding `shop authenticated by HMAC == shop acted upon by the handler`, allowing a malicious but legitimate app-installer (a merchant who installed the app on their own shop) to relabel a webhook payload as belonging to a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from an HTTP header, entirely outside the signed material: [2](#0-1) 

`Registry.process` validates the HMAC over that signable string (i.e., body only) and, on success, immediately forwards `request.shop` — the unauthenticated header value — to the app's handler as the trusted tenant identifier: [3](#0-2) 

Crucially, the HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is **shared across every shop that has installed the app** — it is not shop-specific: [4](#0-3) 

Because the signature only binds the body and not the shop, and the secret is shared app-wide, a valid `(body, hmac)` pair generated for one shop's webhook remains valid when replayed with a different `x-shopify-shop-domain` header. The equality that should hold — `shop cryptographically bound in signed material == shop passed to WebhookHandler#handle` — does not hold; the gem trusts an out-of-band, attacker-controllable header for tenant attribution.

### Impact Explanation
This is a cross-tenant confusion vulnerability (High/Critical depending on handler logic): an attacker who is a legitimate installer of the target app on their own shop (an "unprivileged" tenant with no special access, no leaked secrets, and no MITM) can trigger a webhook with attacker-chosen body content (e.g., `products/update`, `orders/create` topics carry attacker-editable data on their own store), capture the genuine `(body, x-shopify-hmac-sha256)` pair Shopify computed with the app's shared `client_secret`, and replay it directly to the app's webhook endpoint with the `x-shopify-shop-domain` header swapped to a victim shop. `Registry.process` will validate successfully (HMAC only checks body) and dispatch `WebhookMetadata` claiming the victim's shop with attacker-controlled body data, causing the host app to act on another tenant's data/session — i.e., cross-tenant access via credential/identity confusion.

### Likelihood Explanation
Medium-High: exploitation requires only that the attacker be a normal user who has installed the target app on any shop (a low bar for public/embedded apps), the ability to trigger a webhook topic whose payload they control (many topics reflect merchant-editable data), and a way to capture and replay the raw webhook POST to the app's public callback URL. No secrets, tokens, or privileged access are required.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-covered signable string, or otherwise cryptographically bind `shop` to the signature (e.g., derive it from a per-shop-scoped verification, or require the host app to cross-check `request.shop` against an independently-stored, already-authenticated shop record before trusting it). At minimum, document prominently that `request.shop` is unauthenticated and must not be used as a sole tenant-selection key by consuming applications.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`.
2. Attacker triggers `products/update` (or any topic with attacker-controlled body) on their shop.
3. Shopify sends: `POST /webhook` with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <hmac(body, app_client_secret)>`, and attacker-controlled `body`.
4. Attacker captures `body` and the HMAC value (network log on their own infra, or by controlling body content that itself carries a payload useful against another shop).
5. Attacker resends the identical `body`/HMAC pair to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
6. `HmacValidator.validate` in `Registry.process` recomputes HMAC over `body` only (`request.rb:36`) — it matches because the secret is app-wide, not shop-specific.
7. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: attacker_body, ...))`, causing the host application to process attacker-supplied data under `victim-shop`'s identity.
