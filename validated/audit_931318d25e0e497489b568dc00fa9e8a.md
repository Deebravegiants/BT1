### Title
Webhook topic/shop/webhook-id headers are unsigned, allowing HMAC-valid payload relabeling and handler misdispatch - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `HmacValidator.validate` never covers `topic`, `shop`, `webhook_id`, or `api_version`, all of which are read straight from attacker-controllable HTTP headers. `Registry.process` then dispatches to a handler solely based on the unsigned `request.topic`, so a resent body with a swapped topic header still passes HMAC validation and gets routed to an arbitrary registered handler.

### Finding Description
The broken binding: `HmacValidator.validate(request) == true` should imply `request.topic (and shop/webhook_id) are also authenticated`, but in fact `HmacValidator.validate(request) == true` only implies `request.raw_body is authenticated`.

- `HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field via `OpenSSL.secure_compare`: [1](#0-0) 
- `Webhooks::Request#to_signable_string` returns `@raw_body` only, excluding all headers: [2](#0-1) 
- `topic`, `shop`, `webhook_id`, and `api_version` are all derived purely from headers, none of which feed into the signable string: [3](#0-2) 
- `Registry.process` validates HMAC first, then looks up and invokes the handler keyed on the unsigned `request.topic`, and constructs `WebhookMetadata` using the equally unsigned `request.shop`, `request.webhook_id`, `request.api_version`: [4](#0-3) 

Exploit flow: the attacker installs the app on their own development shop, registers a webhook (e.g. `orders/create`), and receives one genuinely-signed callback (`raw_body`, `X-Shopify-Hmac-Sha256`). They then resend the identical `raw_body`+HMAC to their app's webhook endpoint with `X-Shopify-Topic` changed to `shop/redact` (or any other registered topic) and/or `X-Shopify-Webhook-Id`/`X-Shopify-Shop-Domain` changed arbitrarily. `HmacValidator.validate` recomputes HMAC over `@raw_body` only — unaffected by the header changes — and returns `true`. `Registry.process` then dispatches the relabeled payload to whichever handler is registered for the forged topic, with a forged `shop` claim in `WebhookMetadata`.

No existing guard closes this gap: there is no cross-check that the body's expected schema matches the claimed topic, and no comparison of the header-derived `shop` against a known/expected session or registration. This is corroborated by the test suite itself, which builds `Webhooks::Request` instances purely from headers plus body and never asserts a binding between them: [5](#0-4) 

### Impact Explanation
An attacker who possesses any one validly-signed webhook body (trivially obtainable by installing the app on their own shop and triggering any topic they registered) can get that body dispatched, with an arbitrary chosen `topic` and `shop`, to any handler registered in the host app's `Registry`, including mandatory/sensitive handlers (e.g. `shop/redact`, `customers/redact`, `customers/data_request`) if the host app maps handlers generically off `request.topic`. Because `shop` is also unsigned, the dispatched `WebhookMetadata.shop` can be forged to any value, letting the attacker's own signed traffic masquerade as originating from a different shop identifier inside the handler's view of the data — a cross-tenant confusion vector at the handler-input level. This matches the Critical category: authentication bypass, where a forged/relabeled webhook payload is accepted and routed as if genuine for a different topic/shop.

### Likelihood Explanation
The attacker only needs: (1) their own dev/test shop with the app installed, (2) permission to register at least one webhook topic and observe the raw signed callback, (3) the ability to POST to their own app's webhook endpoint with modified headers — all attainable by an unprivileged app installer with no leaked secrets. The main constraint is host-app design: exploitability requires the host to use a shared endpoint/registry (as this gem's `Registry.process` model does) that trusts `request.topic`/`request.shop` without independent verification — which is exactly the documented usage pattern in `docs/usage/webhooks.md`. This is fully repeatable per request and does not require rediscovering any secret.

### Recommendation
Include `topic`, `shop`, and ideally `webhook_id`/`api_version` in the value that gets HMAC-verified (or otherwise cryptographically bind them to the body), e.g., by having `to_signable_string` concatenate a canonical representation of these headers with `@raw_body`, or by requiring the host app to independently verify that the `topic` used for dispatch matches the URL path/registration the request was received on, and that `shop` matches an authenticated/known session for that installation.

### Proof of Concept
```ruby
# test/webhooks/topic_forgery_test.rb
require "test_helper"

class TopicForgeryTest < Test::Unit::TestCase
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
    @raw_body = '{"id":1}'
    @hmac = Base64.encode64(
      OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "secret", @raw_body)
    )
  end

  def test_topic_is_unsigned
    headers_orders = {
      "x-shopify-topic" => "orders/create",
      "x-shopify-hmac-sha256" => @hmac,
      "x-shopify-shop-domain" => "attacker.myshopify.com",
    }
    headers_redact = headers_orders.merge("x-shopify-topic" => "shop/redact")

    req_orders = ShopifyAPI::Webhooks::Request.new(raw_body: @raw_body, headers: headers_orders)
    req_redact = ShopifyAPI::Webhooks::Request.new(raw_body: @raw_body, headers: headers_redact)

    assert ShopifyAPI::Utils::HmacValidator.validate(req_orders)
    assert ShopifyAPI::Utils::HmacValidator.validate(req_redact)
    refute_equal req_orders.topic, req_redact.topic
    # Same raw_body+hmac validate under two different topics -> topic is not signed,
    # so Registry.process would dispatch the identical payload to different handlers.
  end
end
```
