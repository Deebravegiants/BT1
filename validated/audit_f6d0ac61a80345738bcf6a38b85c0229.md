Based on the codebase, `EvmHost.sol`'s `dispatch`, and `fundRequest` functions perform on-chain swaps against a Uniswap V2 pool to convert native token payments into the fee token, and this price is derived live from the pool's current reserves with no TWAP or slippage-bound refund path back to the caller.

### Title
Unprotected on-chain Uniswap V2 spot-price swap in `EvmHost.dispatch`/`fundRequest` is manipulable and traps excess native value - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest` swap the caller's native token for the fee token via `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` [1](#0-0) [2](#0-1) [3](#0-2) . The recipient of the swap output is `address(this)` (the `Host`), so the router's excess-ETH refund is sent back to the `Host` contract, not to the transaction's original caller, and none of the three functions track or return this leftover value to `_msgSender()`.

### Finding Description
Unlike `IntentGatewayV2.placeOrder`, which explicitly computes `msgValue -= amounts[0]` after the swap to account for and refund any unused native value [4](#0-3) , `EvmHost.dispatch` and `EvmHost.fundRequest` never subtract or reconcile the amount actually spent (`amounts[0]`) against `msg.value`. The entire `msg.value` is handed to the router as `amountInMax`, and whatever change the router refunds lands in the `Host` contract's own balance rather than being forwarded to the caller [1](#0-0) .

Because the swap price is read live from the configured `_hostParams.uniswapV2` pool's spot reserves (documented explicitly as vulnerable to sandwiching: "Do not call `quote()` in smart contract transactions... it uses Uniswap's `getAmountsIn`, making it vulnerable to sandwich attacks" [5](#0-4) ), an attacker can manipulate a thin-liquidity fee-token/WETH pool in the same block as a victim's `dispatch`/`fundRequest` call (front-run/sandwich or flash-loan-funded swap) to inflate the ETH cost required to fill `post.fee`/`amount` fee tokens. This forces a larger fraction — potentially nearly all — of the victim's supplied `msg.value` to be consumed by the manipulated swap and irretrievably absorbed by the `Host` contract, since the contract exposes no path for depositors to reclaim native ETH sitting in its balance. `EvmHost` only supports governance-gated withdrawal of the ERC-20 `feeToken()` revenue, not stray native ETH.

### Impact Explanation
Any unprivileged caller of `IDispatcher.dispatch`/`fundRequest` who overestimates their `msg.value` (which is unavoidable off-chain, since the SDK's own `quote()`/`quoteNative()` helpers read the same manipulable spot price [6](#0-5) ) can have the delta between the true fee-token cost and their supplied `msg.value` permanently captured by the `Host` contract instead of refunded, and an attacker can amplify this loss on demand by manipulating the pool's reserves immediately before the victim's transaction executes. This is a direct loss of user funds reachable from a single unprivileged dispatch transaction.

### Likelihood Explanation
Likelihood is elevated on any EVM deployment where the configured `uniswapV2` fee-token/WETH pool has low liquidity (mirroring the WBGL/WETH pool cited in the source report), which the repository's own fork tests acknowledge as a real deployment risk ("This validates that the configured wrapper is wired to a pool with real liquidity" [7](#0-6) ). No special privileges are required — only the ability to submit a swap transaction against the same pool and time it around a victim's `dispatch`/`fundRequest` call.

### Recommendation
Mirror `IntentGatewayV2.placeOrder`'s pattern in `EvmHost.dispatch`, `dispatch(DispatchGet)`, and `fundRequest`: track `amounts[0]` returned by `swapETHForExactTokens` and refund `msg.value - amounts[0]` back to `_msgSender()`, or swap with `to` set to the caller. Additionally consider bounding the acceptable swap price (e.g., a caller-supplied `amountInMax` and/or TWAP-based sanity check) rather than relying solely on spot reserves.

### Proof of Concept
1. Attacker identifies a low-liquidity `feeToken`/`WETH` Uniswap V2 pool configured as `_hostParams.uniswapV2` on a target `EvmHost` deployment.
2. Attacker front-runs a victim's `dispatch(DispatchPost)` (or `fundRequest`) call by swapping a large amount of WETH into the pool, sharply raising the WETH price relative to `feeToken`.
3. Victim's `dispatch` call executes `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`; the manipulated pool now requires far more ETH to produce `post.fee` fee tokens than under normal conditions.
4. The additional ETH consumed (up to the victim's full `msg.value`) is taken from the victim, and any unspent portion refunded by the router is credited to `EvmHost`'s own balance rather than back to the victim, since `dispatch`/`fundRequest` contain no logic to forward or reclaim it — see the swap call sites [1](#0-0) [3](#0-2)  contrasted with `IntentGatewayV2`'s explicit `msgValue -= amounts[0]` refund tracking [8](#0-7) .
5. Attacker back-runs by reversing the initial swap, recovering their capital while the victim's overpaid ETH remains trapped in the `Host` contract with no user-facing withdrawal mechanism.
