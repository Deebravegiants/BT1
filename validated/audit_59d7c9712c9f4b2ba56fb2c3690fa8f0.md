The `ShopifyAPI::Webhooks::Request#hmac` is validated only against `@raw_body` via `to_signable_string` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` trusts these header-derived fields to route to a handler and to build the `WebhookMetadata` passed into merchant-facing business logic, without the HMAC binding them to the body [3](#0-2) .

### Title
Webhook shop/topic identity spoofing via unauthenticated headers not covered by HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` and routing-critical `topic`/`webhook_id`/`api_version` fields from raw HTTP headers, but the HMAC signature verified by `Utils::HmacValidator` only covers the request body (`to_signable_string` returns `@raw_body`). This breaks the intended binding `HMAC(body) == HMAC(body, shop, topic)` that a webhook consumer must rely on to trust which merchant/topic a payload belongs to.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` recomputes an HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field using a constant-time comparison [4](#0-3) . For webhooks, `Request#to_signable_string` returns only `@raw_body` — the raw JSON payload bytes [1](#0-0) . Meanwhile `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all parsed straight from the `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, and `shopify-api-version` HTTP headers via `shopify_header` [2](#0-1) , none of which are included in the signed message.

`Registry.process` validates the HMAC once, then unconditionally trusts `request.topic` to select the handler and `request.shop` to build the `WebhookMetadata` delivered to the handler's business logic [3](#0-2) . Because the signature check never binds `shop`/`topic`/`webhook_id` to the body, a valid `(raw_body, hmac)` pair generated for one shop/topic remains fully valid when replayed with those headers swapped for a different shop or topic — the app has no way to detect the substitution.

An unprivileged attacker who legitimately installs the app on their own shop (a normal, unprivileged action requiring no special credentials) will receive genuine Shopify webhooks for that shop, each with a body and a valid HMAC signed by the app's `client_secret`. The attacker can then replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`) to name a different, victim shop. `HmacValidator.validate` still passes because the body bytes and HMAC are untouched, and `Registry.process` hands the forged `shop`/`topic` straight to the handler as if Shopify itself had certified that binding.

### Impact Explanation
This breaks the identity binding `shop authenticated by HMAC == shop acted upon by the handler`, which is exactly the class of bug the report describes (a field acted on but not covered by the authenticity check). Any host application that uses `WebhookMetadata#shop`/`#topic` to decide which tenant's records to create, update, or delete is exposed to cross-tenant data injection/corruption — e.g., spoofing an `app/uninstalled` or `orders/create` event against a shop the attacker does not own, using data controlled by a shop they do own. This matches the "cross-tenant access" criteria for Critical impact.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the app on a shop they control (an ordinary, unprivileged action for any merchant) and be able to send an HTTP POST to the app's public webhook endpoint, which is inherently internet-reachable. No secret, token, or elevated privilege is needed beyond what any app-installing merchant already has.

### Recommendation
Include the shop domain, topic, webhook id, and API version in the signed message (`to_signable_string`) so `HmacValidator` binds them cryptographically to the payload, or otherwise verify that `request.shop` corresponds to a shop that actually has this webhook/topic registered (e.g., cross-check against the app's own webhook registration/session store) before dispatching to a handler.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`. Shopify sends a genuine webhook: body `B`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, and a valid `x-shopify-hmac-sha256` computed as `HMAC-SHA256(client_secret, B)`.
2. Attacker captures `(B, hmac)`.
3. Attacker sends a new POST to the app's webhook endpoint with the identical body `B` and `hmac`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
4. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks `B` against `hmac` [5](#0-4) .
5. `Registry.process` dispatches the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: parsed B, ...)` [6](#0-5) , causing the host application to act on attacker-controlled payload `B` as if it were an authentic event for `victim-shop.myshopify.com`.
