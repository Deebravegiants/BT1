### Title
Webhook shop identity spoofing via replay - shop-domain header is not covered by the HMAC signature ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then hands the tenant identity (`shop`) to the application handler from an unauthenticated header. Because the signature only covers the body bytes and not the `shop-domain` (or `topic`/`api-version`/`webhook-id`) header, the equality "the shop the HMAC authenticates" == "the shop the app acts on" does not hold.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `HmacValidator.validate`/`validate_signature` compute/compare the HMAC exclusively against `to_signable_string`: [2](#0-1) 

`Registry.process` only checks this body HMAC before dispatching, and then builds `WebhookMetadata` using `request.shop`, which is read straight from the `shop-domain` header without any cryptographic binding to the signed body: [3](#0-2) [4](#0-3) 

The app's `api_secret_key`/HMAC key is the same for every shop that installs the app — it is not per-tenant. Any merchant who has installed the app receives genuine webhook deliveries for their own shop, each with a valid `x-shopify-hmac-sha256` computed over the body using this shared secret. Because the header carrying the tenant identity (`x-shopify-shop-domain`) is excluded from the signed bytes, that merchant can resend the exact same body+HMAC pair while substituting an arbitrary `x-shopify-shop-domain` (and `topic`) header value naming a different (victim) shop. `Registry.process` will accept the HMAC (it was never tied to the shop) and invoke the registered handler with `WebhookMetadata.new(shop: <spoofed shop>, body: <attacker-controlled body from their own real webhook>, ...)`.

This breaks the intended identity binding: `hmac-authenticated bytes == bytes acted upon` holds for the body, but `shop presented == shop authenticated` does not, since `shop` is parsed, not verified.

### Impact Explanation
Host applications built on this gem rely on `WebhookMetadata#shop` to determine which tenant's data to update (e.g., writing order/product/customer state keyed by shop). An attacker who legitimately controls one installed shop can forge webhook deliveries that the receiving application will process as belonging to a different, victim shop — a cross-tenant data-integrity/write primitive achieved without ever needing the victim's or the app's `client_secret` beyond what any installed merchant already possesses for their own tenant.

### Likelihood Explanation
Medium/High: an attacker needs only to install (or already have installed) the target app on some shop they control — an unprivileged, ordinary flow — capture one of their own genuine webhook deliveries, and replay it with a modified `shop-domain` header value to the same public webhook endpoint. No secrets belonging to the app owner or the victim shop are required.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC validation, or otherwise cryptographically bind the shop domain to the signed payload before dispatching to handlers, so that spoofing the header alone cannot change the trusted tenant identity.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; Shopify sends a genuine webhook with body `B` and header `x-shopify-hmac-sha256: H = HMAC(secret, B)`, `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the identical `raw_body` `B` and `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `HmacValidator.validate` recomputes `HMAC(secret, B)` and it matches `H` (body untouched), so `Registry.process` proceeds.
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)` and processes attacker-controlled data under the victim tenant's identity. [3](#0-2)
