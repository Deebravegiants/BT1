### Title
Strict `pool_k >= last_recorded_k` check in `calc_take_pnl` permanently reverts Deposit/Withdraw/WithdrawPnl on any single-wei loss - (File: program/src/processor.rs)

### Summary
`Processor::calc_take_pnl` is the pnl-accounting routine invoked from `process_deposit`, `process_withdraw`, and `process_withdrawpnl`. It gates all pnl extraction (and, by extension, the deposit/withdraw flows that call it) behind a hard invariant check that the current pool value must be `>=` the previously recorded `calc_pnl_x * calc_pnl_y` point, with zero tolerance for any decrease, mirroring the `ADAPTER_BREAKS_LOSS_POINT`-less pattern flagged in the external report.

### Finding Description
`calc_take_pnl` compares the current product of pool reserves against the last recorded pnl checkpoint with no margin: [1](#0-0) 
If the pool's `pool_pc_amount * pool_coin_amount` is even one unit below `calc_pnl_x * calc_pnl_y`, the function unconditionally errors out: [2](#0-1) 

This function is called from `process_deposit`: [3](#0-2) 
from `process_withdraw` (unless the pool is `WithdrawOnly`): [4](#0-3) 
and from `process_withdrawpnl`: [5](#0-4) 

Because integer division/rounding in fee and decimal-normalization math (`restore_decimal`, `normalize_decimal_v2`, `checked_div`) can shave off small remainders, the recorded `calc_pnl_x`/`calc_pnl_y` checkpoint can end up marginally larger than the actual current reserve product after a sequence of ordinary swaps (which do not call `calc_take_pnl` at all — see `process_swap_base_in`/`process_swap_base_out`, which never invoke it). Any unprivileged swapper submitting a single transaction that nudges the pool state into this off-by-one-wei condition (via normal swap fee rounding, no special privilege required) will cause every subsequent `Deposit`, `Withdraw`, or `WithdrawPnl` instruction to hit the `AmmError::CalcPnlError` branch and revert, since `calc_pnl_x`/`calc_pnl_y` are never adjusted downward when the check fails — the checkpoint is "stuck" above the real value.

### Impact Explanation
`process_withdraw` is the sole unprivileged path for an LP to redeem shares for underlying tokens outside of `WithdrawOnly` mode. Once `calc_take_pnl` starts failing, `Withdraw` reverts, permanently freezing LP funds in the pool (LPs cannot exit) and blocking `Deposit` as well, since both depend on the same non-recoverable revert. There is no unprivileged instruction that can correct/reset `calc_pnl_x`/`calc_pnl_y` back down after such a drift; only an admin/owner path outside the reachable unprivileged surface can act. This matches the "permanent freezing of user or LP funds" impact category.

### Likelihood Explanation
Likelihood is moderate-to-high: no privileged action is needed, only ordinary swap traffic across `process_swap_base_in`/`process_swap_base_out`, which never call `calc_take_pnl` and thus never reconcile the checkpoint, combined with the deterministic floor/ceiling rounding used throughout `Calculator` (`checked_div`, `restore_decimal`) in `calc_take_pnl` itself. An attacker could specifically target this by executing swaps engineered to minimize `total_pc_without_take_pnl * total_coin_without_take_pnl` by a small margin relative to the stored checkpoint, then any subsequent Deposit/Withdraw/WithdrawPnl by anyone reverts.

### Recommendation
Introduce a tolerance/margin (analogous to the recommended `ADAPTER_BREAKS_LOSS_POINT`) in the `calc_take_pnl` comparison at [6](#0-5) , so that only losses exceeding a defined basis-point threshold trigger `AmmError::CalcPnlError`, and/or provide an unprivileged/self-healing mechanism to reconcile `target.calc_pnl_x`/`calc_pnl_y` downward when reserves have organically drifted below the checkpoint due to rounding, rather than reverting Deposit/Withdraw indefinitely.

### Proof of Concept
1. Pool is initialized normally via `Initialize2`; `TargetOrders.calc_pnl_x/calc_pnl_y` set to the initial normalized reserves [7](#0-6) .
2. An unprivileged user repeatedly calls `SwapBaseIn`/`SwapBaseOut` (small amounts back and forth) — these instructions compute `total_pc_without_take_pnl`/`total_coin_without_take_pnl` directly from vault balances and swap math without ever calling `calc_take_pnl` or updating `calc_pnl_x`/`calc_pnl_y` [8](#0-7) . Fee/decimal rounding (`restore_decimal`, `swap_token_amount_base_in`) can leave the true reserve product marginally below the stale `calc_pnl_x * calc_pnl_y` checkpoint.
3. Any subsequent unprivileged `Withdraw` (or `Deposit`/`WithdrawPnl`) call reaches `calc_take_pnl`, which evaluates `pool_pc_amount * pool_coin_amount < calc_pc_amount * calc_coin_amount` and returns `AmmError::CalcPnlError` [2](#0-1) , reverting the transaction.
4. Because no unprivileged instruction lowers `calc_pnl_x`/`calc_pnl_y` back to match the real (lower) reserve product, every future `Withdraw`/`Deposit`/`WithdrawPnl` continues to revert, freezing LP funds in the pool.

Note: I was not able to execute this scenario end-to-end (no test harness run), so the precision/rounding magnitude needed to trigger the off-by-one condition in practice is asserted from the code paths shown rather than empirically measured; a Devin session with build/test tooling would be needed to quantify the exact rounding drift.
