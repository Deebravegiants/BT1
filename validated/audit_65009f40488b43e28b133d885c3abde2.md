### Title
Webhook `shop-domain` (and topic/webhook-id) header is not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, while the `shop` (and `topic`/`webhook_id`) values used to build the `WebhookMetadata` passed to the app's handler come from HTTP headers that are never included in the signed payload. Since the same `api_secret_key` is shared by every shop that has installed the app, any merchant that has legitimately installed the app can capture one of their own genuine (validly-HMAC-signed) webhook deliveries and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header swapped for a victim shop's domain. The HMAC check still passes (it only covers the body, which is unmodified), so the app's handler is invoked believing the webhook belongs to the victim shop.

### Finding Description
`HmacValidator.validate` computes the HMAC only over `verifiable_query.to_signable_string`, which for `Webhooks::Request` is defined as the raw body: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all read directly from unauthenticated headers: [2](#0-1) 

`Registry.process` validates only the HMAC of the request and then dispatches to the handler using `request.shop` (and other header-derived fields) with no separate binding between the signed body and the claimed shop: [3](#0-2) 

This is exactly the "field acted on but not covered by the HMAC" pattern: the identity binding that should hold is `hmac_signed_bytes == (body, shop)`, but in reality `hmac_signed_bytes == body` only, while `shop` is trusted independently. Because `api_secret_key` is a single shared secret across all shops that install a given app (not a per-shop secret), any attacker who is a legitimate (if unprivileged) merchant of the app can:
1. Receive a real webhook from Shopify for their own shop, which includes a valid `x-shopify-hmac-sha256` value computed over the raw body with the app's shared secret.
2. Replay that exact raw body and HMAC to the app's webhook endpoint, but substitute `x-shopify-shop-domain` (and optionally `x-shopify-topic`) with a victim shop's domain.
3. `HmacValidator.validate` still succeeds because the body and HMAC pair are untouched and valid.
4. The handler receives `WebhookMetadata` claiming the data belongs to the victim shop, even though the body content was authored/controlled by the attacker.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook authenticity: an app relying on `request.shop`/`WebhookMetadata#shop` to scope data writes, cache invalidation, or state changes per merchant can be made to apply attacker-controlled webhook payloads to another merchant's tenant context. This is a cross-tenant data-integrity/spoofing issue (Critical bucket: "cross-tenant access") introduced by the gem's webhook verification not binding the header-derived identity to the HMAC-protected bytes.

### Likelihood Explanation
Likelihood is realistic but bounded: exploitation requires the attacker to be an installed merchant of the target app (to obtain one genuine signed webhook body/HMAC pair) and to know or guess a valid webhook topic/body shape that the host app's handler will act on for the victim shop. No access token, `client_secret`, or privileged account is required — only the ability to install the app as any tenant and to send an HTTP POST to the app's public webhook endpoint with forged headers.

### Recommendation
Include the identity fields (`shop-domain`, and ideally `topic`, `api-version`, `webhook-id`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the body before dispatch — e.g., verify the signature over a canonical string that concatenates the raw body with the shop domain, or require host applications to separately confirm the webhook's `shop` header against a known/expected shop for that endpoint/session before trusting `WebhookMetadata#shop`. At minimum, document prominently that `Registry.process`'s HMAC check does not authenticate the `shop`, `topic`, or `webhook_id` headers so integrators are not misled into treating `WebhookMetadata#shop` as verified.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker-shop.myshopify.com` and triggers/receives a webhook (e.g. `orders/create`) at the app's registered endpoint. They capture the raw POST body `B` and the header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker crafts a new HTTP POST to the same webhook endpoint containing the identical body `B` and header `H`, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: orders/create` (unchanged, or any registered topic)
3. `Registry.process` calls `HmacValidator.validate(request)`, which computes `HMAC-SHA256(api_secret_key, B)` and compares to `H` — this matches, since `B` and `H` are untouched, per [4](#0-3) .
4. `handler.handle` is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, per [5](#0-4) , causing the app to process attacker-supplied data as if it originated from the victim's shop.
