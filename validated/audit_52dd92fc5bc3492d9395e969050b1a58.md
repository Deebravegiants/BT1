### Title
Webhook shop/topic identity spoofing via unsigned headers - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (tenant) and `topic` values from raw, unauthenticated HTTP headers, while the HMAC signature that `Registry.process` verifies covers only the raw request body. Because the tenant-identifying header is not bound to the signature, any actor capable of obtaining one valid `(body, hmac)` pair for the app (e.g., by installing the app on their own store) can replay that exact body/HMAC pair while substituting the `X-Shopify-Shop-Domain` (and/or topic) header for an arbitrary shop, and the signature check will still pass.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` and `topic` are read straight from headers that are never fed into the signable string: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then immediately trusts `request.shop`/`request.topic` to build the `WebhookMetadata` passed to the host app's handler: [3](#0-2) 

`HmacValidator.validate` recomputes the HMAC purely from `to_signable_string` (i.e., the body) and the app's `api_secret_key`, with no dependency on the shop/topic headers: [4](#0-3) 

The identity binding that should hold is:
`hmac == HMAC(api_secret_key, body || shop || topic)`

but the gem only enforces:
`hmac == HMAC(api_secret_key, body)`

while separately trusting `shop`/`topic` from headers that carry no cryptographic binding to that HMAC. The documentation explicitly promises the opposite guarantee — that `Registry.process` "will verify the request did indeed come from Shopify" as a whole (implying the shop identity is verified too), which is not actually the case for the shop/topic fields: [5](#0-4) 

Because the app's `api_secret_key` is shared across all shops that install the app, any merchant who installs the app on their own store receives genuine `(body, hmac)` pairs delivered to the app's registered webhook endpoint. That merchant can capture such a delivery and resend the identical body and `hmac-sha256` header to the same endpoint with the `shop-domain` header changed to a different, victim shop's domain (a value that is easily guessable — myshopify.com domains are public information). `HmacValidator.validate` will still succeed because it never inspected the header, and the host application's handler — which trusts `data.shop` per the documented contract — will process attacker-controlled body content as if it came from the victim tenant.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: an unprivileged app installer (attacker in their own store) can forge webhook events attributed to any other shop using the app, without ever needing that shop's credentials, access token, or `client_secret`. Depending on how the host app's webhook handler uses `data.shop` (e.g., to look up or update per-shop records, trigger fulfillment, or reflect order/customer data), this enables cross-tenant data injection/corruption — matching the "cross-tenant access" Critical impact category, since data intended for tenant A is misattributed to tenant B purely because the identity header is unsigned.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on an attacker-owned development/free Shopify store — a normal, unprivileged action any internet user can perform, and (2) capturing one legitimate webhook HTTP request sent to the app's public callback endpoint, then replaying it with a modified `shop-domain` (and/or `topic`) header. No access to the app's `api_secret_key`, any access token, or the victim shop is required. The only gate is discoverability of the app's public webhook callback URL, which per the docs is a fixed, non-secret path the app owner exposes.

### Recommendation
Bind the identity-bearing fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) into the value that is HMAC-verified, or otherwise cryptographically correlate them with the signed body (e.g., include them in `to_signable_string`, or require the host app to independently confirm that `shop` corresponds to a shop with an active, matching subscription/session before trusting the payload). At minimum, update `docs/usage/webhooks.md` to clarify that `Registry.process` only authenticates the body, not the shop/topic headers, so host applications are not misled into skipping their own tenant verification.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (free/unprivileged action) and lets the app register an `orders/create` webhook to the app's public callback URL.
2. Attacker triggers a real order creation event on their own store, capturing the resulting webhook HTTP request: raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker replays the identical request to the same callback URL, keeping `raw_body = B` and `X-Shopify-Hmac-Sha256 = H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `victim-shop.myshopify.com`
   ( [6](#0-5) ), while `to_signable_string` is unchanged (`B`).
5. `Registry.process` calls `HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B) == H` — validation succeeds
   ( [7](#0-6) ).
6. The handler is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker order data>, ...)`, causing the host app to process attacker-controlled data as belonging to `victim-shop`, despite `victim-shop` never having installed the app or authorized this event.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
