## Title
Webhook `shop-domain` (and other identity headers) are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the shop identity for an incoming webhook from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature that `Utils::HmacValidator` verifies is computed over the raw request body only. The header is never part of the signed bytes, so the "shop this webhook belongs to" is not cryptographically bound to the HMAC that authenticates the request.

### Finding Description
`Webhooks::Registry#process` authenticates an inbound webhook solely via: [1](#0-0) 

which calls `Utils::HmacValidator.validate(request)`. That validator computes the expected signature from `request.to_signable_string` and compares it (timing-safe) against `request.hmac`: [2](#0-1) 

But `Webhooks::Request#to_signable_string` returns **only the raw body**: [3](#0-2) 

while `#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read straight out of unauthenticated HTTP headers: [4](#0-3) 

The identity binding the app relies on is:
`bytes verified (raw_body) == bytes the shop attribution is derived from (shop-domain header)`

This equality does not hold — the HMAC only proves the body was produced with the app's secret for *some* legitimately-triggered webhook, it says nothing about which shop the caller is now claiming that body belongs to. After `process` validates the HMAC, it forwards `request.shop` (unverified) straight into the handler: [5](#0-4) 

### Impact Explanation
Any unprivileged user who can install the app on their own store (a normal, un-elevated tenant) will receive genuine, correctly-signed webhooks from Shopify for events they themselves trigger (e.g., creating an order/product/customer with attacker-chosen content). Because the header carrying the shop identity is excluded from the signed bytes, that same attacker can replay the intercepted `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. The HMAC check still passes (it only checks the body), so the host application's webhook handler will process attacker-controlled body content under the identity of a different, victim tenant — a cross-tenant data/event injection. This satisfies the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
The only prerequisite is the ability to install the app as a normal merchant (an unprivileged, no-special-access action) and to send an arbitrary HTTP POST to the app's public webhook endpoint — no access token, `client_secret`, or other privileged credential is required. This makes the attack straightforward for anyone who can create a Shopify dev store and install the target app.

### Recommendation
Bind the shop (and ideally topic/api_version) into the signed material, e.g. by including the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` header values in `to_signable_string`, or by independently verifying that the shop the webhook claims to be from matches a shop the app has an active session/installation for before dispatching to handlers.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers an event (e.g., creates a product) so Shopify sends a legitimately HMAC-signed webhook to the app's endpoint, with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `B`).
2. Attacker captures this request and resends it to the same endpoint, keeping body `B` and header `H` unchanged, but replacing `X-Shopify-Shop-Domain: attacker.myshopify.com` with `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Registry#process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC from `request.to_signable_string` (= `B` only) and successfully matches `H`.
4. The app then invokes the webhook handler with `shop: "victim.myshopify.com"` and the attacker-controlled body `B`, causing the host application to process/store attacker-chosen data as belonging to the victim tenant.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
