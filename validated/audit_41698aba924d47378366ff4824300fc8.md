### Title
Webhook processing trusts unauthenticated `shop`/`topic` headers, enabling cross-tenant webhook spoofing via HMAC replay - (File: lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but the `shop` and `topic` values that are subsequently trusted and handed to the app's handler are taken from HTTP headers that are never covered by that HMAC.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes and compares an HMAC using `verifiable_query.to_signable_string` as the signed payload [1](#0-0) . For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only `@raw_body`, while `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers set outside the HMAC-signed content [2](#0-1) .

`Registry.process` validates the HMAC and, once it passes, unconditionally trusts `request.shop` and `request.topic` to look up the handler and build `WebhookMetadata` that is passed to app code: [3](#0-2) 

The binding this breaks is: `shop_bound_by_HMAC == shop_delivered_in_header` should hold, but it does not — the HMAC only certifies `raw_body`; it makes no statement about which shop, topic, or webhook the body belongs to.

Critically, the HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`/webhook secret shared across **every** shop that has installed the app, not a per-tenant secret [4](#0-3) . Any unprivileged internet user can install a public app on their own (free/dev) store and thereby legitimately receive real Shopify webhooks whose body+HMAC pairs are valid under that shared secret. Because the `shop`/`topic` headers are not bound into the signature, that attacker can replay the exact same `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header for a victim shop. `HmacValidator.validate` will still return `true` (it only checks the body), and `Registry.process` will happily dispatch the forged data as if it originated from the victim shop [5](#0-4) .

### Impact Explanation
This allows an attacker who controls their own shop installation to inject data that the host application will process as belonging to a different, victim tenant (spoofed `shop` in `WebhookMetadata`). Depending on how the host app keys behavior off `data.shop` (e.g., looking up a session/access token for that shop, updating per-shop records, triggering redact/data flows), this is a cross-tenant access/data-integrity issue — the impact bucket explicitly listed as Critical ("cross-tenant access"). The gem provides no built-in defense (e.g., binding shop/topic into the signed payload, or requiring the caller to independently correlate `webhook_id`/shop against known installed sessions) and the documentation does not warn app developers that `data.shop`/`data.topic` are unauthenticated [6](#0-5) .

### Likelihood Explanation
Exploitation requires only: (1) installing the target public app on an attacker-owned shop (trivial, no privilege needed), (2) capturing one legitimate webhook delivery (body + `hmac-sha256` header) from Shopify to that attacker-controlled endpoint, and (3) replaying it to the same app's webhook receiver with a different `shop`/`topic` header value. No secrets, tokens, or social engineering are required, and the HMAC check will pass unchanged.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise independently authenticate the shop after HMAC validation, e.g.:
- Include the shop domain from `X-Shopify-Shop-Domain` in the signable string only if it can also be verified against a known/expected shop, or
- After HMAC success, cross-check `request.shop` against a shop for which the app currently holds an active session before dispatching to the handler, and reject shops that are unknown/uninstalled.
- Document explicitly that `data.shop`/`data.topic` in `WebhookMetadata` are unauthenticated headers and must not be trusted for tenant selection without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (self-service, no privilege required).
2. Attacker subscribes/receives a legitimate webhook (e.g. `orders/create`) at the app's webhook endpoint; captures the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` (valid because `H = HMAC_SHA256(app_secret, B)`).
3. Attacker resends the identical body `B` and header `H` to the same webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`).
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds a request whose `hmac` still equals `H`, and `to_signable_string` still equals `B` [7](#0-6) .
5. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC_SHA256(app_secret, B)` and matches `H` — validation succeeds [8](#0-7) .
6. The handler is invoked with `WebhookMetadata.new(topic: forged_topic, shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-controlled webhook content attributed to the victim tenant [9](#0-8) .

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
