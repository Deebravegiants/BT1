## Root cause found

`convert_to_balance` and `convert_to_erc20` in the `hyper-fungible-token` pallet scale amounts between an ERC20's decimals and a local Substrate asset's decimals using `erc_decimals.saturating_sub(local_decimals)` as the exponent — in **both** directions: [1](#0-0) 

- `convert_to_balance` divides the incoming U256 by `10^(erc_decimals.saturating_sub(local_decimals))`.
- `convert_to_erc20` multiplies by the same `10^(erc_decimals.saturating_sub(local_decimals))`.

`saturating_sub` clamps to `0` whenever `local_decimals > erc_decimals`. In that case both functions compute `10^0 = 1`, i.e. **no scaling is applied at all**, when the correct behavior is to *multiply* by `10^(local_decimals - erc_decimals)` in `convert_to_balance` (scale up) — the exact mirror of the reported `SingleSidedLiquidityVault.getMaxDeposit()` bug, which used the wrong decimal base and silently produced a wrong conversion factor instead of reverting or computing the correct exponent.

## Reachability

`convert_to_balance` is called directly from `on_accept` (minting/crediting funds on message delivery from an unsigned ISMP dispatch) and from `on_timeout` (refunding escrowed native currency), both of which are triggered by relayed/dispatched cross-chain messages that any relayer can deliver once the underlying consensus proof is valid: [2](#0-1) [3](#0-2) 

This is a token-bridge mint/burn path, explicitly in-scope per the rules.

### Title
Incorrect decimal-scaling exponent in `hyper-fungible-token`'s `convert_to_balance`/`convert_to_erc20` mints/refunds wrong amounts when local asset decimals exceed ERC20 decimals - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`convert_to_balance` and `convert_to_erc20` both compute the same scaling exponent, `erc_decimals.saturating_sub(local_decimals)`, regardless of direction. When `local_decimals > erc_decimals` (e.g. an ERC20 with 6 decimals bridged to a Substrate asset configured with 12 or 18 decimals), the subtraction saturates to `0`, so `10^0 = 1` is used — the function performs **no scaling** instead of multiplying the credited amount by `10^(local_decimals - erc_decimals)`.

### Finding Description
`convert_to_balance` is documented and intended to "Divide by `10^(erc_decimals - local_decimals)` to scale down from ERC20 precision" — but this formula is only correct when `erc_decimals >= local_decimals`. The reverse case (a common configuration, since many local Substrate assets use 12 or 18 decimals while ERC20 tokens often use 6) is silently mishandled: `saturating_sub` returns 0, and the amount is divided by 1, i.e. passed through unchanged. This under-credits recipients by a factor of `10^(local_decimals - erc_decimals)` (e.g. minting 1,000,000x too few tokens for a 6-decimal ERC20 bridged into an 18-decimal asset) instead of correctly scaling the value up.

Symmetrically, `convert_to_erc20` (used to encode outbound send amounts) multiplies by the same clamped exponent, so in the same decimal configuration it fails to divide down the amount when converting from local to ERC20 representation — over-representing the burn amount by orders of magnitude on outbound `send()`.

This directly parallels the `SingleSidedLiquidityVault.getMaxDeposit()` report: a decimals value is fed into a scale-factor computation using the wrong basis/direction, producing a systematically wrong multiplier rather than the intended conversion, silently corrupting all amounts under that configuration.

### Impact Explanation
Every `on_accept` (mint credit for an inbound bridge message) and `on_timeout` (refund of escrowed native currency) call goes through `convert_to_balance` using the on-chain configured `Precisions` value for `erc_decimals` and the local asset's actual `decimals`. If a local asset is configured with more decimals than its remote ERC20 counterpart, every inbound mint/credit and every refund silently mints/returns far less than what was locked/burned on the source chain — a systemic under-mint of user funds (and analogous over/under-representation on the ERC20-encoding side for outbound transfers). This is a direct funds-loss bug in the token bridge's mint/burn accounting, reachable by any relayer delivering an otherwise valid cross-chain message once decimals for a token pair are configured in this direction.

### Likelihood Explanation
No malicious actor is required — this triggers on completely legitimate transfers as soon as any token pair is configured where the local Substrate asset decimals exceed the source ERC20's decimals, which is a normal, foreseeable configuration (Substrate assets commonly use 12 or 18 decimals; many ERC20s use 6). Every relayed message for that asset from that source chain deterministically produces the wrong amount.

### Recommendation
Compute the exponent and direction explicitly instead of relying on `saturating_sub` to silently zero out the "wrong" direction:
```rust
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256,
    erc_decimals: u8,
    local_decimals: u8,
) -> Result<B, B::Err> {
    let scaled = if erc_decimals >= local_decimals {
        value / U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        value * U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    };
    scaled.to_string().parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```

### Proof of Concept
Configure a token pair where the local Substrate asset has 18 decimals and the remote ERC20 has 6 decimals (`Precisions::<T>::get(local_asset_id, source) == 6`, `decimals == 18`). A user bridges `1,000,000` units (i.e. 1 whole token, `1_000_000` base units at 6 decimals) from the EVM side.

1. `on_accept` computes `erc_decimals.saturating_sub(local_decimals) = 6u8.saturating_sub(18u8) = 0`.
2. `convert_to_balance` divides `value` (1,000,000) by `10^0 = 1`, yielding `1,000,000` — but the correct 18-decimal-equivalent amount should be `1,000,000 * 10^12 = 1,000,000,000,000,000,000` (1 whole token at 18 decimals).
3. The beneficiary is credited `1,000,000` base units on an 18-decimal asset — effectively `0.000000000001` tokens instead of `1` token, a 10¹²-factor loss of funds for the recipient, while the source chain correctly locked/burned the full amount.
