### Title
Inverted fallback ratio grants nested EVM call frame full parent weight/deposit budget instead of none when `remaining_gas` rounds to zero - ([File: substrate/frame/revive/src/metering/math.rs])

### Summary
In `substrate_execution::new_nested_meter`, when the computed `remaining_gas` (the gas-equivalent of the parent's leftover weight+deposit) evaluates to zero, the code sets `ratio = FixedU128::one()` instead of `FixedU128::zero()`. Because `ratio` scales both `weight_left` and `deposit_left` when producing `nested_weight_limit`/`nested_deposit_limit`, this fallback grants the nested frame the parent's *entire* remaining weight and deposit budget, completely decoupled from the caller-requested `gas` value in `CallResources::Ethereum { gas, .. }`.

### Finding Description
The nested-meter derivation logic is: [1](#0-0) 

`weight_gas_left` and `deposit_gas_left` are gas-equivalent *conversions* of the parent's actual `weight_left`/`deposit_left` (native units), via `SignedGas::from_weight_fee` and `SignedGas::from_adjusted_deposit_charge`: [2](#0-1) 

`from_adjusted_deposit_charge` multiplies the deposit amount by `next_fee_multiplier_reciprocal()` (a `FixedU128` that can be less than 1), and `from_weight_fee` simply wraps `weight_to_fee_average`'s output, which itself performs a linear/polynomial fee computation on weight — both operations are integer-truncating. This means it is arithmetically possible for `weight_left` and/or `deposit_left` to be strictly positive in native units, yet their *fee/gas-equivalent* projection rounds down to `0`, making `remaining_gas.is_zero()` true even though real, spendable resources remain in the parent frame.

When that happens, the code takes the `ratio = FixedU128::one()` branch: [3](#0-2) 

With `ratio == 1`, `weight_limit = weight_left` and `deposit_limit = deposit_left` verbatim — i.e., the *entire* remaining parent budget — regardless of how small the caller's requested `gas` was (`gas_limit = remaining_gas.min(*gas)` is `0.min(*gas) = 0`, but `gas_limit` is never actually used again once `ratio` takes the `is_zero()` branch). The comment/intent for the `remaining_gas.is_zero()` branch appears to be a guard against `FixedU128::from_rational(_, 0)` panicking/dividing by zero, but the chosen fallback (`one()`, i.e. 100%) is the *opposite* of the safe default (`zero()`, i.e. 0%), inverting the intended semantics: "no gas left to allocate" should yield "allocate nothing", not "allocate everything remaining".

This directly violates the stated invariant that a nested frame's granted deposit/weight budget must be proportional to (and never exceed what is justified by) the gas it was charged for.

### Impact Explanation
Any unprivileged contract-to-contract call routed through `CallResources::Ethereum { gas, .. }` in Substrate-style (non-EVM-native) execution can, upon hitting the `remaining_gas == 0` rounding edge case, receive a nested frame whose `nested_weight_limit`/`nested_deposit_limit` equal the parent's full remaining weight and storage-deposit allowance — an unbounded amount relative to the tiny `gas` value actually specified in the call. This is a bookkeeping asymmetry: the nested frame can consume up to the parent's full remaining native weight/deposit while the caller's intent (and any gas-based fee reservation semantics associated with the `gas` argument) only accounted for a minuscule amount. This is scoped strictly to storage-metering/gas accounting over-allocation as described; it does not itself cause fund theft, but it breaks the gas-to-resource proportionality invariant and can let a nested frame consume disproportionately more storage deposit/weight than its nominal gas allotment implies.

### Likelihood Explanation
Triggering this precisely requires the parent's remaining weight and remaining deposit to *both* convert to zero gas-equivalent under `weight_to_fee_average` and `next_fee_multiplier_reciprocal` while still being nonzero in native units — a state reachable only near resource exhaustion combined with specific fee-conversion rounding behavior (dependent on the configured `FeeInfo`/`WeightToFee` and current fee multiplier). Whether this is reachable with materially "large" leftover weight/deposit (making the bug impactful) versus only negligible leftover amounts (making the bug practically harmless) depends on the concrete `T::FeeInfo` implementation and multiplier state at call time, which could not be fully confirmed from the code inspected. The logic inversion itself, however, is unconditionally present in the code regardless of how easy it is to hit in practice.

### Recommendation
Fix the fallback branch so that `remaining_gas.is_zero()` yields `ratio = FixedU128::zero()` (deny further nested allocation) rather than `FixedU128::one()`, or alternatively short-circuit and return `Err(Error::OutOfGas)` when `remaining_gas` is zero, consistent with the "no gas left" semantics used elsewhere in the same file (e.g., the `to_ethereum_gas()` conversion failure path at line 122-126).

### Proof of Concept
Rust unit test plan (to be added near `substrate/frame/revive/src/metering/tests.rs`):
1. Construct a `ResourceMeter` (parent) with `weight_limit`/`deposit_limit` such that `weight_left` and `deposit_left` are both nonzero, but crafted so that `SignedGas::from_weight_fee(weight_to_fee_average(weight_left))` and `SignedGas::from_adjusted_deposit_charge(deposit_left)` both truncate to `0` under the configured mock `FeeInfo` (e.g., set a `next_fee_multiplier_reciprocal` close to `0` and a `weight_to_fee_average` returning `0` for the chosen small `weight_left`).
2. Call `substrate_execution::new_nested_meter(&meter, &CallResources::Ethereum { gas: 1, add_stipend: false })`.
3. Assert that `nested_deposit_limit` (the `deposit.limit` on the returned `FrameMeter`) and `nested_weight_limit` do **not** equal the parent's full `deposit_left`/`weight_left`, but instead are bounded proportionally to `gas_limit = min(remaining_gas, 1) = 0` (i.e., expect `nested_weight_limit == Weight::zero()` and `nested_deposit_limit == 0`, or an `Err(Error::OutOfGas)`).
4. Current behavior: the test would show `nested_deposit_limit == deposit_left` and `nested_weight_limit == weight_left` (full parent budget), failing the proportionality assertion — demonstrating the bug.

	pub fn from_weight_fee(weight_fee: BalanceOf<T>) -> Self {
		Self::Positive(weight_fee)
	}

	/// Transform an Ethereum gas amount coming from outside the metering system and transform into
	/// the internally used SignedGas.
	pub fn from_ethereum_gas(gas: BalanceOf<T>) -> Self {
		let gas_scale = <T as Config>::GasScale::get();
		Self::Positive(gas.saturating_mul(gas_scale.into()))
	}

	/// Transform a storage deposit into a gas value. The value will be adjusted by dividing it
	/// through the next fee multiplier. Charges are treated as a positive numbers and refunds as
	/// negative numbers.
	pub fn from_adjusted_deposit_charge(deposit: &StorageDeposit<BalanceOf<T>>) -> Self {
		let multiplier = T::FeeInfo::next_fee_multiplier_reciprocal();

		match deposit {
			StorageDeposit::Charge(amount) => Positive(multiplier.saturating_mul_int(*amount)),
			StorageDeposit::Refund(amount) => {
				Self::safe_new_negative(multiplier.saturating_mul_int(*amount))
			},
		}
	}
