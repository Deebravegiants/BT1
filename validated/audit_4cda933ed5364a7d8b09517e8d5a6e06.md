## Analysis

This is a genuine custody-analog to the reported bridgeFunds issue: no slippage protection on a swap.

### Title
No slippage protection on `bonding_curve_launchpad::swap` allows sandwich-attack value extraction from the FA/APT liquidity pair - (File: `aptos-move/move-examples/bonding_curve_launchpad/sources/bonding_curve_launchpad.move`)

### Summary
`bonding_curve_launchpad::swap` (and the underlying `liquidity_pairs::swap_fa_to_apt` / `swap_apt_to_fa`) accepts only `amount_in`, with no caller-supplied minimum-output parameter. [1](#0-0)  The constant-product `get_amount_out` computation determines the output purely from the current on-chain reserves at execution time, and neither `swap_fa_to_apt` nor `swap_apt_to_fa` check the output against any user-provided floor before transferring funds. [2](#0-1) [3](#0-2) 

This is exactly the same bug class as the external report: a swap function with a hardcoded/absent minimum-output guarantee, exposing users to sandwich attacks and value misalignment. For comparison, the codebase's own `move-examples/swap/router.move` demonstrates the correct pattern with an explicit `amount_out_min` check: [4](#0-3) 

### Finding Description
`swap` is a public entry function reachable by any unprivileged account, taking only `swap_to_apt` and `amount_in`. [5](#0-4)  It dispatches into `liquidity_pairs::swap_fa_to_apt`/`swap_apt_to_fa`, both of which compute the output via `get_amount_out` from live pool reserves and immediately execute the transfer with no assertion that the amount received meets any caller expectation. [6](#0-5) [7](#0-6) 

Because Aptos uses a public mempool, an attacker (or MEV-capable validator/block-builder) can observe a pending `swap` transaction and front-run it with their own swap in the same direction to shift `fa_reserves`/`apt_reserves`, then back-run it after the victim's transaction executes, extracting value from the victim's execution price — a classic sandwich attack. The custody invariant broken here is: *swap-triggered custody transfers (FA and APT balances moving between the swapper's primary store, the liquidity pair's `fa_store`, and the swapper's APT balance) must reflect the value the user consented to at submission time.* Since no `amount_out_min`/`amount_in_max` is enforced, the corrupted value is the actual `apt_gained` or `fa_gained` transferred to the swapper — it can be driven arbitrarily low (down to `> 0`, per the `ELIQUIDITY_PAIR_SWAP_AMOUNTOUT_INSIGNIFICANT` check) while the attacker captures the difference, and it also permanently and asymmetrically corrupts the liquidity pair's `fa_reserves`/`apt_reserves` state to the attacker's benefit.

### Impact Explanation
This directly moves value (APT and FA custody) from a legitimate swapper to a malicious actor, satisfying the custody-impact gate ("theft ... of APT, fungible assets, token objects ... tied to asset and ownership control" and "supply or custody accounting corruption that moves value to the wrong holder"). Because the liquidity pair also gatekeeps FA graduation to a public DEX once `apt_reserves` crosses `APT_LIQUIDITY_THRESHOLD`, manipulated reserves can also distort graduation timing/amounts, propagating the corrupted state to `router::create_pool_coin`/`add_liquidity_coin_entry_transfer_ref` at graduation. [8](#0-7)  Given the FA is frozen for all external transfers prior to graduation (only tradeable through this `swap`), users have no way to protect themselves except by using this vulnerable code path, making the impact high for any active user of this module.

### Likelihood Explanation
Likelihood is high in any environment with visible pending transactions/mempool ordering flexibility (validators, or any adversary capable of transaction ordering), since it requires no privileged capability — just capital and the ability to observe/precede the victim's transaction. The bonding curve's constant-product formula with a fixed, non-configurable slippage tolerance (there is none) makes exploitation straightforward with standard sandwich-bot tooling.

### Recommendation
Add a caller-supplied `min_output` (or `max_input`) parameter to `bonding_curve_launchpad::swap`, `liquidity_pairs::swap_fa_to_apt`, and `liquidity_pairs::swap_apt_to_fa`, and assert the actual `apt_gained`/`fa_gained` (or `apt_given`/`fa_given` for max-input protection) satisfies the caller's bound before executing the transfer — mirroring the pattern already used in `move-examples/swap/router.move`'s `swap` function (`EINSUFFICIENT_OUTPUT_AMOUNT` check).

### Proof of Concept
1. Victim submits `bonding_curve_launchpad::swap(victim, name, symbol, /*swap_to_apt=*/false, amount_in=1000_APT)` expecting FA output based on current reserves.
2. Attacker observes this pending transaction and front-runs with their own `swap(attacker, name, symbol, false, amount_in=large_APT)`, shifting `apt_reserves` up and `fa_reserves` down (per `get_amount_out`'s constant-product formula, lines 104-111 of `liquidity_pairs.move`).
3. Victim's transaction executes at the now-worse price, receiving far fewer FA tokens than expected, with no `min_amount_out` check to abort the trade.
4. Attacker back-runs with `swap(attacker, name, symbol, true, ...)` to sell the FA back to APT, capturing the price difference extracted from the victim — all state transitions succeed because neither `swap_fa_to_apt` nor `swap_apt_to_fa` validate output against caller-supplied floors.

**Note on scope/limitation:** This is an example/demo Move package (`move-examples/bonding_curve_launchpad`), not core `aptos-framework` production code; its custody-relevance depends on whether it is deployed as-is on mainnet by third parties. I was not able to fully verify deployment status or confirm whether this package has already been flagged/patched upstream given index limitations — a full repository session would be needed to check its Git history/CHANGELOG for prior remediation status.

    public entry fun swap(
        account: &signer,
        name: String,
        symbol: String,
        swap_to_apt: bool,
        amount_in: u64

            liquidity_pairs::swap_apt_to_fa(name, symbol, transfer_ref, account, fa_metadata_obj, amount_in);
        };

    /// Facilitate swapping between a given FA to APT.
    public(friend) fun swap_fa_to_apt(
        name: String,
        symbol: String,
        transfer_ref: &TransferRef,
        swapper_account: &signer,
        fa_object_metadata: Object<Metadata>,
        amount_in: u64
    ) acquires Pairs, LiquidityPair {
        // Verify the liquidity pair exists and is enabled for trading.
        assert_liquidity_pair_exists(name, symbol);
        let liquidity_pair = borrow_global_mut<LiquidityPair>(get_pair_obj_address(name, symbol));
        assert!(liquidity_pair.is_enabled, ELIQUIDITY_PAIR_DISABLED);
        // Determine the amount received of APT, when given swapper-supplied amount_in of FA.
        let (fa_given, apt_gained, fa_updated_reserves, apt_updated_reserves) = get_amount_out(
            liquidity_pair.fa_reserves,
            liquidity_pair.apt_reserves,
            true,
            amount_in
        );
        // Verify the swapper holds the FA.
        let swapper_address = signer::address_of(swapper_account);
        let does_primary_store_exist_for_swapper = primary_fungible_store::primary_store_exists(
            swapper_address,
            fa_object_metadata
        );
        assert!(does_primary_store_exist_for_swapper, EFA_PRIMARY_STORE_DOES_NOT_EXIST);
        // Perform the swap.
        // Swapper sends FA to the liquidity pair object. The liquidity pair object sends APT to the swapper, in return.
        let liquidity_pair_signer = object::generate_signer_for_extending(&liquidity_pair.extend_ref);
        let from_swapper_store = primary_fungible_store::ensure_primary_store_exists(
            swapper_address,
            fungible_asset::transfer_ref_metadata(transfer_ref)
        );
        fungible_asset::transfer_with_ref(transfer_ref, from_swapper_store, liquidity_pair.fa_store, fa_given);
        aptos_account::transfer(&liquidity_pair_signer, swapper_address, apt_gained);
        // Record state changes to the liquidity pair's reserves, and emit changes as events.
        let former_fa_reserves = liquidity_pair.fa_reserves;
        let former_apt_reserves = liquidity_pair.apt_reserves;
        liquidity_pair.fa_reserves = fa_updated_reserves;
        liquidity_pair.apt_reserves = apt_updated_reserves;
        event::emit(
            LiquidityPairReservesUpdated {
                former_fa_reserves,
                former_apt_reserves,
                new_fa_reserves: fa_updated_reserves,
                new_apt_reserves: apt_updated_reserves
            }
        );
        event::emit(
            LiquidityPairSwap {
                is_fa_else_apt: false,
                gained: (apt_gained as u128),
                swapper_address
            }
        );
    }

    public(friend) fun swap_apt_to_fa(
        name: String,
        symbol: String,
        transfer_ref: &TransferRef,
        swapper_account: &signer,
        fa_object_metadata: Object<Metadata>,
        amount_in: u64
    ) acquires Pairs, LiquidityPair {
        // Verify the liquidity pair exists and is enabled for trading.
        assert_liquidity_pair_exists(name, symbol);
        let liquidity_pair = borrow_global_mut<LiquidityPair>(get_pair_obj_address(name, symbol));
        assert!(liquidity_pair.is_enabled, ELIQUIDITY_PAIR_DISABLED);
        // Determine the amount received of FA, when given swapper-supplied amount_in of APT.
        let (fa_gained, apt_given, fa_updated_reserves, apt_updated_reserves) = get_amount_out(
            liquidity_pair.fa_reserves,
            liquidity_pair.apt_reserves,
            false,
            amount_in
        );
        // Perform the swap.
        // Swapper sends APT to the liquidity pair object. The liquidity pair object sends FA to the swapper, in return.
        // Requires the liquidity pair object's address, which is retrieved using the stored extend_ref.
        let swapper_address = signer::address_of(swapper_account);
        let liquidity_pair_address = object::address_from_extend_ref(&liquidity_pair.extend_ref);
        let to_swapper_store = primary_fungible_store::ensure_primary_store_exists(
            swapper_address,
            fungible_asset::transfer_ref_metadata(transfer_ref)
        );
        aptos_account::transfer(swapper_account, liquidity_pair_address, apt_given);
        fungible_asset::transfer_with_ref(transfer_ref, liquidity_pair.fa_store, to_swapper_store, fa_gained);
        // Record state changes to the liquidity pair's reserves, and emit changes as events.
        let former_fa_reserves = liquidity_pair.fa_reserves;
        let former_apt_reserves = liquidity_pair.apt_reserves;
        liquidity_pair.fa_reserves = fa_updated_reserves;
        liquidity_pair.apt_reserves = apt_updated_reserves;
        event::emit(
            LiquidityPairReservesUpdated {
                former_fa_reserves,
                former_apt_reserves,
                new_fa_reserves: fa_updated_reserves,
                new_apt_reserves: apt_updated_reserves
            }
        );
        event::emit(
            LiquidityPairSwap {
                is_fa_else_apt: true,
                gained: (fa_gained as u128),
                swapper_address
            }
        );
        // Check for graduation requirements. The APT reserves must be above the pre-defined
        // threshold to allow for graduation.
        if (liquidity_pair.is_enabled && apt_updated_reserves > APT_LIQUIDITY_THRESHOLD) {
            graduate(liquidity_pair, fa_object_metadata, transfer_ref, apt_updated_reserves, fa_updated_reserves);
        }
    }

    /// Moves the reserves of a liquidity pair on the `liquidity_pair` module to a newly created liquidity pair
    /// on an external DEX (`swap`). The resulting liquidity provider tokens are thrown away.
    /// Both of the FA's original liquidity pair and frozen status are disabled.
    /// From here, participants are free to use their FA as they'd like, because the custom `withdraw` function is no
    /// longer frozen for `transfer`.
    fun graduate(
        liquidity_pair: &mut LiquidityPair,
        fa_object_metadata: Object<Metadata>,
        transfer_ref: &TransferRef,
        apt_updated_reserves: u128,
        fa_updated_reserves: u128
    ) {
        // Disable Bonding Curve Launchpad pair and remove global freeze on FA.
        liquidity_pair.is_enabled = false;
        liquidity_pair.is_frozen = false;
        // Offload onto third party, public DEX.
        router::create_pool_coin<AptosCoin>(fa_object_metadata, false);
        let liquidity_pair_signer = object::generate_signer_for_extending(&liquidity_pair.extend_ref);
        add_liquidity_coin_entry_transfer_ref<AptosCoin>(
            transfer_ref,
            &liquidity_pair_signer,
            liquidity_pair.fa_store,
            fa_object_metadata,
            false,
            ((apt_updated_reserves - (apt_updated_reserves / 10)) as u64),
            ((fa_updated_reserves - (fa_updated_reserves / 10)) as u64),
            0,
            0
        );

    /// Swap an amount of fungible assets for another fungible asset. User can specifies the minimum amount they
    /// expect to receive. If the actual amount received is less than the minimum amount, the transaction will fail.
    public entry fun swap_entry(
        user: &signer,
        amount_in: u64,
        amount_out_min: u64,
        from_token: Object<Metadata>,
        to_token: Object<Metadata>,
        is_stable: bool,
        recipient: address,
    ) {
        let in = primary_fungible_store::withdraw(user, from_token, amount_in);
        let out = swap(in, amount_out_min, to_token, is_stable);
        primary_fungible_store::deposit(recipient, out);
    }

    /// Similar to swap_entry but returns the fungible asset received for composability with other modules.
    public fun swap(
        in: FungibleAsset,
        amount_out_min: u64,
        to_token: Object<Metadata>,
        is_stable: bool,
    ): FungibleAsset {
        let from_token = fungible_asset::asset_metadata(&in);
        let pool = liquidity_pool::liquidity_pool(from_token, to_token, is_stable);
        let out = liquidity_pool::swap(pool, in);
        assert!(fungible_asset::amount(&out) >= amount_out_min, EINSUFFICIENT_OUTPUT_AMOUNT);
        out
    }
