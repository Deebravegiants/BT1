### Title
Webhook shop-domain header not bound to HMAC signature allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/registry.rb, lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates only the HMAC over the raw request body, then forwards the unauthenticated `shop-domain` header value to the application's webhook handler as the trusted shop identity. Because the HMAC never covers the shop header, an attacker who obtains one valid `(body, hmac)` pair — trivially available by installing the target app on their own shop — can replay that exact body/HMAC pair while substituting an arbitrary `X-Shopify-Shop-Domain` header naming a victim shop, and the library will accept it as an authentic webhook "from" the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header, completely outside of what is signed: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which in turn calls `verifiable_query.to_signable_string` (the raw body only) and compares it against `verifiable_query.hmac`: [3](#0-2) [4](#0-3) 

Because Shopify computes the webhook HMAC using the app's single, shop-independent `client_secret` (the same `Context.api_secret_key` used for every merchant installing the app), the resulting `(body, hmac)` pair is not bound to any particular shop. The identity binding that should hold is:

`shop_that_hmac_authenticates == shop_attributed_to_the_webhook_data`

but the actual binding enforced by this gem is only:

`hmac_valid_for(body) == true`, with `shop` taken verbatim from an unauthenticated header.

An unprivileged attacker can:
1. Install the target app on their own (attacker-controlled) development/test shop — an ordinary, unprivileged action.
2. Capture a legitimate webhook delivery (`raw_body`, `x-shopify-hmac-sha256`) sent by Shopify to the app's webhook endpoint for their own shop (e.g. `app/uninstalled`, `shop/redact`, `customers/data_request`, or any topic with attacker-controllable/generic body content).
3. Replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint, but swap the `X-Shopify-Shop-Domain` header to name a victim shop.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the HMAC only covers `raw_body`, which the attacker did not modify.
5. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` — where `request.shop` is the attacker-supplied victim domain, now treated by the app as an authenticated fact: [5](#0-4) 

The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" and describes `data.shop` as "The shop domain of the webhook" — implying to any consumer of this documented API that the shop attribution is authenticated along with the payload, when in fact only the body bytes are authenticated.

### Impact Explanation
This breaks the tenant identity binding the gem is documented to enforce, letting an attacker impersonate any shop domain for HMAC-authenticated webhook deliveries of their choosing. Depending on the topic and how the host app's handler consumes `data.shop` (e.g. mandatory GDPR topics `shop/redact`, `customers/redact`, `customers/data_request`, or app lifecycle topics like `app/uninstalled`), this can trigger cross-tenant data deletion, uninstall/cleanup logic, or other shop-scoped side effects against a victim shop's tenant record, without ever compromising that shop's credentials — a cross-tenant access vulnerability rooted entirely in this gem's webhook processing path.

### Likelihood Explanation
Likelihood is bounded by the attacker needing at least one genuine `(body, hmac)` pair, which is freely obtainable by installing the target app on an attacker-controlled shop (an unprivileged, self-service action for any public Shopify app) and capturing the resulting webhook delivery. No access token, `client_secret`, or victim credentials are required at any point.

### Recommendation
Bind the shop identity to the authenticated payload before trusting it: either include the `shop-domain` header in the signable string covered by the HMAC comparison, or require the host application to cross-check `request.shop` against the app's own record of shops for which webhooks were registered/expected, and document this requirement prominently. At minimum, `Registry.process`/`WebhookMetadata` should not present `shop` as if it were authenticated alongside `body`.

### Proof of Concept
```ruby
# 1. Attacker installs the app on their own shop "attacker.myshopify.com"
#    and captures a legitimate webhook delivery for topic "app/uninstalled":
raw_body = "{}"  # or any topic whose body is attacker-influenced/generic
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_client_secret, raw_body)
hmac_b64 = Base64.encode64(hmac)  # attacker captured this from Shopify's real request

# 2. Attacker replays it against the app's webhook endpoint, spoofing the shop header:
headers = {
  "x-shopify-topic" => "app/uninstalled",
  "x-shopify-hmac-sha256" => hmac_b64,       # valid - body untouched
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # attacker-controlled, unauthenticated
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC validation succeeds (Utils::HmacValidator.validate only checks raw_body),
#    handler.handle is invoked with data.shop == "victim-shop.myshopify.com",
#    even though the webhook never originated from victim-shop.
```
