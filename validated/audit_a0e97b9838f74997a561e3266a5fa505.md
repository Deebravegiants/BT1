The strongest reachable analog in orb-core is the operator-QR validity caching in `MasterPlan::scan_remaining_qr_codes`, which mirrors the root cause of the Merkl H-03 bug: a security-critical validity decision is made purely from a **local time-window check**, without re-querying the backend for the operator's current (possibly since-revoked) status.

### Title
Operator authorization cached and reused past backend re-validation, allowing signups under a revoked operator ID - (File: `src/plans/mod.rs`)

### Summary
`OperatorData` stores a `timestamp` taken at the moment the operator QR code was validated against the backend via `backend::operator_status::request` [1](#0-0) . Later, `scan_remaining_qr_codes` (and `scan_initial_qr_codes`) decide whether to trust this already-validated `operator_data` purely by comparing `operator_data.timestamp.elapsed()` against `operator_qr_expiration_time`, without any additional call back to the backend to confirm the operator is still authorized [2](#0-1) .

### Finding Description
This is structurally analogous to the Merkl `Distributor.getMerkleRoot` bug: that function used only a time-window condition (`block.timestamp >= endOfDisputePeriod`) to decide which Merkle root to trust, ignoring the independently-knowable `disputer` state that should have invalidated the tree regardless of the time window. Here, the orb performs an equivalent shortcut: `operator_data.timestamp.elapsed() < operator_qr_expiration_time` is treated as sufficient proof of continued operator authorization [3](#0-2) , even though the backend is the actual source of truth for whether that operator ID has since been revoked/disputed (e.g., for fraud, distributor suspension, etc.), as exposed via `operator_status::Status.valid`/`reason` [4](#0-3) . Within the caching window (default `operator_qr_expiration_time` = 23 hours per `Config::default`) [5](#0-4) , an operator whose authorization has just been revoked can continue to be treated as validated for every subsequent signup attempt, because the code path only re-calls `verify_operator_qr_code`/backend when the cached timestamp has expired, not when authorization state might have changed server-side [6](#0-5) .

### Impact Explanation
If a distributor/operator's authorization is revoked by the backend (fraud, account compromise, policy violation) while that operator's QR-derived `OperatorData` is still cached on the orb (up to the full expiration window), the orb will keep accepting that operator as valid for starting new signups and attaching operator location/authorization context to Personal Custody Packages, without re-checking the backend. This is an unauthorized-signup-continuation scenario: signups proceed under an operator identity/authorization that the backend no longer considers valid, similar in class to claiming from a disputed Merkle tree that should have been treated as invalid.

### Likelihood Explanation
Likelihood is moderate: it requires (a) an operator being actively revoked by the backend while (b) the orb already holds a live, unexpired cached `OperatorData` for that operator (which happens routinely in `self_serve` flows where `scan_initial_qr_codes` caches the operator across many signups) [7](#0-6) . The longer the configured `operator_qr_expiration_time`, the larger this window; the default is 23 hours [5](#0-4) .

### Recommendation
Do not rely solely on the local timestamp to decide operator validity for reuse. Either shorten the reuse window drastically and/or re-validate against the backend (`backend::operator_status::request`) on every signup start rather than only after the cached timestamp expires, especially before performing sensitive operations (starting biometric capture, attaching operator identity to the PCP).

### Proof of Concept
1. Operator scans their QR code; `verify_operator_qr_code` succeeds and `OperatorData { timestamp: Instant::now(), .. }` is cached [8](#0-7) .
2. Backend operator/distributor status is revoked (e.g., `valid: false` would now be returned by `operator_status::request`) [9](#0-8) .
3. Within `operator_qr_expiration_time` (up to 23h by default), further signups reuse the cached `operator_data` in `scan_remaining_qr_codes`'s `QrCodes::Both`/`QrCodes::Operator` branches without calling the backend again, since the branch guard only checks `operator_data.timestamp.elapsed() < operator_qr_expiration_time` [10](#0-9) .
4. Signups proceed and are recorded/attributed under the now-revoked operator, despite the backend no longer authorizing that operator.

/// Makes a validation request.
pub async fn request(qr_code: &qr_scan::user::Data) -> Result<Status> {
    let request = super::client()?
        .get(format!(
            "{}/api/v1/distributor/{}/orb/{}/status",
            *SIGNUP_BACKEND_URL, qr_code.user_id, *ORB_ID
        ))
        .basic_auth(&*ORB_ID, Some(get_orb_token()?));
    let status: Status = match request.send().await?.error_for_status() {
        Ok(response) => response.json().await?,
        Err(err) => {
            tracing::error!("Received error response {err:?}");
            return Err(err.into());
        }
    };
    if !status.valid {
        tracing::info!(
            "Operator QR-code invalid: {qr_code:?}, reason: {:?}",
            status.reason.as_deref().unwrap_or("<empty>")
        );
        return Ok(status);
    }
