### Title
Webhook `shop-domain` Header Is Excluded From HMAC Signature, Allowing Cross-Tenant Event Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content solely from the raw request body, while the `shop`, `topic`, and `webhook_id` values are read from unauthenticated HTTP headers. `Registry.process` trusts `request.shop` to attribute the webhook payload to a tenant without that value ever being covered by the signature check.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [3](#0-2) 

`Utils::HmacValidator.validate` verifies the HMAC exclusively over that signable string: [4](#0-3) 

Meanwhile `Request#shop` is derived directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed payload: [5](#0-4) 

`Registry.process` validates the HMAC and then immediately hands `request.shop` (the unauthenticated header) to the app's webhook handler as the tenant identity for the event: [2](#0-1) 

This breaks the identity binding `shop authenticated == shop acted on`: the HMAC only proves "Shopify (or a holder of the app's `client_secret`) produced this exact body," it does not prove which shop that body belongs to. A merchant who installs the app on their own shop legitimately receives webhooks whose bodies are HMAC-signed with the app's shared secret. If that merchant (an unprivileged app user, not requiring the app's secret) captures one such request and replays it against the app's webhook endpoint while substituting the `shop-domain` header for a victim shop's domain, `Utils::HmacValidator.validate` still succeeds (it never inspects headers), and `Registry.process` passes the victim's shop identity to the handler along with the attacker's chosen body content — cross-tenant data injection/spoofing without needing the victim's credentials or the app's secret.

### Impact Explanation
This lets one tenant (merchant) of a multi-tenant Shopify app inject or spoof webhook events attributed to a different tenant's shop, since the `shop` field the handler trusts for tenant scoping is never bound by the cryptographic signature. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to look up per-shop data, write to per-shop stores, or trigger shop-specific side effects such as data deletion via `shop/redact`), this enables cross-tenant access or corruption — matching the "cross-tenant access" high/critical impact category.

### Likelihood Explanation
Exploitation requires only: (1) installing the app on an attacker-controlled shop (a normal unprivileged action), (2) capturing one legitimately signed webhook body for a topic the attacker cares about, and (3) resending it directly to the app's public webhook endpoint with a modified `shop-domain` header. No access to `api_secret_key`, access tokens, or the victim's credentials is needed, since the HMAC check never touches the header.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable content, or otherwise validate that the resolved `shop` header value matches an expected/allow-listed tenant registered for the current handler before dispatching to `handler.handle`. Alternatively, mirror Shopify's actual behaviour by treating the header-derived `shop` as authenticated only in combination with source verification (e.g., matching against the session/shop that originally registered the specific webhook), rather than trusting it directly from the request.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers an event (e.g., `orders/create`) so Shopify sends a webhook POST with:
   - Header `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - Header `x-shopify-hmac-sha256: <valid HMAC over raw_body>`
   - Body: `{...attacker-controlled order data...}`
2. Attacker resends the exact same request to the app's webhook endpoint, changing only the header to `x-shopify-shop-domain: victim-shop.myshopify.com` (the body and HMAC header are untouched).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` (`lib/shopify_api/webhooks/registry.rb:190`), which succeeds because it only checks `raw_body` against the HMAC — the modified `shop-domain` header is never part of the check.
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker data>, ...)` at `lib/shopify_api/webhooks/registry.rb:198-199`, causing the host app to process attacker-supplied data under the victim shop's identity.
