### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) are trusted by the handler dispatch without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by HMAC-validating the raw request body, then hands the handler a `WebhookMetadata` built from HTTP headers (`shop`, `topic`, `api_version`, `webhook_id`) that are never part of the signed material. Because the signing secret (`api_secret_key`) is the same for every shop that has installed the app, any shop can produce a validly-signed body and then have that body delivered under a different `shop` (and/or `topic`) header, causing the app's webhook handler to act on the wrong tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`hmac` is computed from the `hmac-sha256` header, and `to_signable_string` returns only `@raw_body` — the `shop-domain`, `topic`, `api-version`, and `webhook-id` headers are read via `shopify_header` but are **not** included in `to_signable_string`.

`HmacValidator.validate` only checks that the received HMAC matches `HMAC(api_secret_key, to_signable_string)`: [2](#0-1) 

`Registry.process` uses this validation result as the sole authentication gate, then dispatches using the unauthenticated header values: [3](#0-2) 

The identity binding that should hold is: `shop header == shop that the signed body actually originated from`. Because the signature only covers `@raw_body`, and `api_secret_key` is a single app-wide secret shared across every merchant shop that installed the app (not a per-shop secret), that binding does not hold: `HMAC(api_secret_key, body)` is valid for the same `body` regardless of which shop header accompanies it.

### Impact Explanation
Any shop that has the app installed can trigger a legitimate webhook delivery for itself (a normal, unprivileged action — e.g., creating an order or updating a product), capture the resulting `(raw_body, X-Shopify-Hmac-Sha256)` pair, and resend it to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop that also uses the app. `HmacValidator.validate` still passes because it only checks the body signature against the shared `api_secret_key`. `Registry.process` then builds `WebhookMetadata` with `shop: request.shop` taken straight from the (forged) header and invokes the merchant's/app's webhook handler as if the event legitimately came from the victim shop.

Any app whose webhook handler uses the `shop` field to select which tenant's database record to update (the intended and documented use of `WebhookMetadata#shop`) is exposed to cross-tenant data corruption/injection: an attacker-controlled shop can inject fabricated "events" attributed to a different, victim tenant. This crosses a tenant boundary using only an unprivileged action (installing/interacting with the app as a normal shop), matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any shop that has installed the app can generate this at will (no special access needed beyond normal shop activity that fires a webhook, which is standard merchant behavior), and the app's webhook endpoint is by definition a public HTTP endpoint. The `topic` header is equally unauthenticated, so the same technique also allows a shop to relabel its own event as any other topic the app has registered a handler for.

### Recommendation
Do not trust `request.shop`, `request.topic`, `request.api_version`, or `request.webhook_id` as authenticated data. At minimum:
- Require callers to independently confirm the `shop` from the webhook belongs to a session/shop record that the app actually has an active installation/access token for, and reject events for shops that are not currently authorized.
- Where possible, bind the expected shop/topic into the verification step (e.g., by requiring the caller to pass the expected shop and comparing it against a shop-specific stored secret/session rather than a single shared `api_secret_key`), so that a body signed by shop A cannot be replayed as an event for shop B.
- Document prominently that `WebhookMetadata#shop`/`#topic` are not cryptographically bound to the HMAC and must not be used as the sole tenant-selection key without additional verification.

### Proof of Concept
1. App is installed on Shop A and Shop B (both share the app's single `api_secret_key`).
2. Trigger any webhook-producing action on Shop A; capture the POST body and its `X-Shopify-Hmac-Sha256` header from the delivery to the app's webhook endpoint.
3. Replay the exact same body and HMAC header to the same endpoint, but set `X-Shopify-Shop-Domain: shop-b.myshopify.com` (Shop B's domain).
4. `Utils::HmacValidator.validate` in `lib/shopify_api/webhooks/registry.rb` returns `true` because it only checks `HMAC(api_secret_key, raw_body)`, which is unchanged.
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: <Shop A's body>, ...)`, causing the app to process Shop A's event data under Shop B's tenant context.
