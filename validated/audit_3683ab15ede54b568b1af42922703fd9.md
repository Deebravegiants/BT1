### Title
Webhook shop-domain spoofing via HMAC that only covers the request body, not headers - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook by validating the HMAC of the raw request body only, then trusts the `shop` (and `topic`/`webhook_id`) values taken from unauthenticated HTTP headers when building the `WebhookMetadata` passed to the app's handler. Because the HMAC signature never covers these header fields, the tenant identity (`shop`) acted upon by the handler is not bound to the value that was cryptographically verified.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all read straight from HTTP headers, none of which are part of the signed string: [2](#0-1) 

`Registry.process` validates only the HMAC of the body via `Utils::HmacValidator.validate`, and if it passes, immediately constructs `WebhookMetadata` using `request.shop` — the unauthenticated header value — and dispatches it to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string` (the raw body) using `Context.api_secret_key`: [4](#0-3) 

The identity binding that should hold is: `shop_header == shop_bound_by(hmac_signature)`. In this implementation that equality never actually holds — the HMAC binds only the body bytes, and `shop` is a disjoint, unauthenticated header. Any request whose body matches a previously-observed, genuinely-signed body (e.g., replaying/relaying a real webhook delivery that the attacker's own shop received) will pass `HmacValidator.validate` regardless of what `x-shopify-shop-domain` header is attached, since that header plays no role in the signature computation.

This is exactly the "field acted on but not covered by the HMAC" analog: the code verifies bytes (`@raw_body`) but acts on a different, unverified value (`shop`) for tenant attribution.

### Impact Explanation
An attacker who is a legitimate (but malicious) merchant with the app installed on their own store receives real, correctly-HMAC-signed webhook deliveries from Shopify for their own shop. They can replay that exact body to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. The signature check still passes because it only ever validated the body, so the app's registered handler executes `handler.handle` believing the event originated from the victim tenant. Depending on how the host application uses `WebhookMetadata#shop` (e.g., to key data writes, trigger tenant-specific business logic, or drive session/state lookups), this enables cross-tenant data corruption or cross-tenant action execution — a tenant-isolation break driven entirely by this gem's own webhook verification code.

### Likelihood Explanation
Likelihood is High: no secret material is required beyond what any merchant already legitimately possesses (a genuine webhook delivery to their own store), and no privileged access, TLS interception, or social engineering is needed — only the ability to add/modify a header when re-sending a captured HTTP request to the app's public webhook endpoint.

### Recommendation
- Include the identity-relevant headers (`shop`, `topic`, `webhook_id`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the signed payload, so that a valid signature can only be produced for the exact `(body, shop, topic)` tuple that Shopify actually sent.
- Alternatively/additionally, cross-check `request.shop` against the shop the webhook subscription was registered for (or an independently trusted source) before dispatching to the handler, rather than trusting the header value outright.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and lets Shopify deliver a legitimate webhook (e.g. `orders/create`) to the app's endpoint; this request has a valid `x-shopify-hmac-sha256` computed over the JSON body using the app's real `api_secret_key`.
2. Attacker captures this request (body + headers) and resends it to the same endpoint, changing only `x-shopify-shop-domain` (or `shopify-shop-domain`) to `victim-shop.myshopify.com`, leaving the body and HMAC header untouched.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (== unchanged `@raw_body`) and it matches, so validation succeeds: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` now returns `"victim-shop.myshopify.com"`, even though no cryptographic material tied to `victim-shop.myshopify.com` was ever verified: [6](#0-5)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
