### Title
Unallowlisted route venues let arbitrary pool code run under the caller's signed auth tree, draining unrelated wallet tokens - ([File: contracts/swap-aggregator/src/venues/mod.rs](contracts/swap-aggregator/src/venues/mod.rs))

### Summary
The swap router invokes whatever `pool` address the payload names and keeps no allowlist of venue contracts. A malicious "pool" called inside a route hop can invoke `token.transfer(victim, attacker, amount)` for any token; because the call sits below the caller's `require_auth` entry, an honest simulation records it as a child of the caller's authorization, and the transfer executes if the caller signs that tree. This is the on-chain analogue of SSRF: the router is tricked into reaching arbitrary, attacker-chosen code (an arbitrary "URL"), which then acts with the caller's authority far beyond the routed funds.

### Finding Description
`dispatch_hop` in `contracts/swap-aggregator/src/venues/mod.rs` matches on `hop.venue` and calls the adapter with `ctx.hop.pool` taken verbatim from the decoded payload; there is no venue/pool allowlist anywhere [1](#0-0) . The Soroswap adapter transfers `amount_in` to the payload's pool and invokes `swap` on it [2](#0-1) ; the Aquarius adapter similarly invokes `swap` on the payload's pool [3](#0-2) . The threat model itself states the router "keeps no allowlist" and that a route "can put third-party code on the call stack below the caller's authorization", with the resulting loss being "the caller's wallet, not the routed amount" [4](#0-3) . The harness test `rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates a `RogueHopPool` whose `swap` steals an unrelated token from the victim while the route pays fair output and passes all risk gates [5](#0-4) .

Entrypoints an attacker can weaponize for a victim to sign: `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, and `flash_position` callbacks that embed a route, plus direct `execute_strategy` on the router — all take an attacker-crafted `swap_xdr` naming the rogue pool.

### Impact Explanation
Theft of user funds. The stolen amount is unrelated to the swap: any token the victim holds can be transferred to the attacker inside the hop, bounded only by the victim's wallet balance — the test steals 77,770 units of a token the protocol never listed while routing only 5,000 USDC [6](#0-5) . Neither the payload `min_out`, the controller's final risk gate, nor the router's measured balance deltas bound the loss, since the theft is a side transfer under the victim's own auth [7](#0-6) .

### Likelihood Explanation
Exploitation requires the victim to sign an authorization tree containing the rogue child transfer (UI:R, matching the reference CVE). Clients that blindly sign the simulated auth tree — the common pattern for Soroban dApps — expose users fully; the threat model acknowledges an honest strategy produces no child entry and puts the burden on every client to decode and reject extra children [8](#0-7) . Any user of `execute_strategy` or route-bearing controller strategies is a target, and the attacker needs no privileges, only a deployed rogue contract and a crafted `swap_xdr`.

### Recommendation
Enforce a venue/pool allowlist in the router: maintain an owner-managed registry of approved pool addresses (or venue-pinned pool factories and derive/verify pools) and reject hops whose `hop.pool` is not registered, so payload data can no longer place arbitrary contracts on the call stack below the caller's auth. Until then, clients must decode `swap_xdr` and refuse any simulated authorization tree containing children beyond the single input `transfer`.

### Proof of Concept
1. Attacker deploys `RogueHopPool` configured with `(victim, wallet_token, attacker, amount)` and crafts a route whose hop pool is that contract, with `token_in`/`token_out`/`min_out` set to a fair-looking swap.
2. Victim calls `ctrl.swap_collateral(alice, account_id, usdc_key, 50_000_000_000, eth_key, route)` (or `router.execute_strategy` directly).
3. During the hop, the rogue pool executes `token::Client::new(&env, &wallet_token).transfer(&victim, &attacker, &amount)` [5](#0-4) ; simulation attaches this transfer as a child of the victim's auth entry.
4. If the victim signs that tree, the unrelated wallet tokens move to the attacker while the swap itself settles fairly and the account remains healthy — the full scenario is exercised in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` [9](#0-8) .
