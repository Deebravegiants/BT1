### Title
Webhook `shop-domain` header is not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable string solely from the raw request body, never including the `shop-domain` header, yet `Registry.process` trusts `request.shop` as the authenticated tenant identifier passed to the app's `WebhookHandler`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [3](#0-2) . The `hmac`, `topic`, `shop`, `api_version`, and `webhook_id` accessors are all pulled from HTTP headers that are never part of the signed material [4](#0-3) .

`Registry.process` validates only that `HmacValidator.validate(request)` succeeds — i.e., that the body's HMAC matches — then immediately forwards `request.shop` (the unauthenticated header) into `WebhookMetadata` and on to the app's handler: [2](#0-1) . `HmacValidator.validate_signature` confirms this — it computes the signature purely from `verifiable_query.to_signable_string` (the body) against `Context.api_secret_key`: [5](#0-4) .

The identity binding that should hold is: `shop header used by handler == shop for which the HMAC-covered body was actually issued`. Because the header is outside the signed scope, this equality is never enforced. Since the HMAC key (`Context.api_secret_key`, the app's client secret) is identical for every merchant that installs the app, any merchant who installs the app can trigger a real webhook delivery for their own shop with attacker-chosen body content (e.g., create an order with arbitrary line items on their own store to trigger `orders/create`). Shopify will sign that specific body with a valid HMAC and deliver it with a `x-shopify-shop-domain` header equal to the attacker's own shop. The attacker — an unprivileged internet user with direct HTTP access to the app's public webhook endpoint — can then replay that exact `(raw_body, hmac)` pair to the same endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with an arbitrary victim shop domain. `Utils::HmacValidator.validate` still succeeds (it never looks at the header), and `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, even though that body was never actually generated for, or delivered by, the victim's shop.

### Impact Explanation
This breaks the tenant boundary the whole webhook system is meant to enforce: an app relying on `WebhookMetadata#shop` to select which merchant's stored session/access token to use, which merchant's database row to update, or which merchant-scoped side effect to trigger, can be made to attribute attacker-controlled data to an arbitrary victim shop. This is a cross-tenant access primitive — the strongest applicable impact category (Critical) — since it lets one merchant forge events "from" any other merchant of the same app without ever compromising that merchant's credentials.

### Likelihood Explanation
Any merchant that installs the target app (a normal, unprivileged action) can obtain at least one legitimately HMAC-signed `(body, signature)` pair for content they fully control, and the webhook endpoint is by design internet-facing and unauthenticated aside from the HMAC. No access token, `api_secret_key`, or privileged access is required — only ordinary HTTP requests to the public webhook route, matching the "unprivileged internet user" threat model.

### Recommendation
Extend the webhook-signing binding so the `shop` (and ideally `topic`/`webhook-id`) header is verified against the same trust root as the body — e.g., have `Request#to_signable_string` incorporate the shop domain, or separately validate the `shop-domain` header against the shop tied to the session/registration the app expects for that HMAC, before handing it to the handler. Document clearly that `request.shop` is currently unauthenticated and must not be treated as trusted tenant input.

### Proof of Concept
1. App merchant A installs the target Shopify app; app registers an `orders/create` webhook.
2. Merchant A creates an order in their own shop containing attacker-controlled data, triggering Shopify to POST the webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: H` (valid signature of `B` under the shared `client_secret`) and `x-shopify-shop-domain: shop-a.myshopify.com`.
3. Attacker (merchant A) intercepts/replays this request directly to the app's public webhook URL, keeping body `B` and header `H` unchanged but replacing `x-shopify-shop-domain` with `shop-victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which passes because it only checks `B` against `H` [6](#0-5) .
5. The app's `WebhookHandler#handle` receives `WebhookMetadata.new(shop: "shop-victim.myshopify.com", body: B, ...)` [7](#0-6) , processing attacker-supplied data as if it originated from the victim's shop.
