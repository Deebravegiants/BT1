## Title
Webhook `shop` domain is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only signs the raw HTTP body, while the `shop` (and `topic`/`webhook_id`) values consumed by `ShopifyAPI::Webhooks::Registry.process` come from unauthenticated headers. Anyone who can obtain one valid `(raw_body, hmac)` pair for their own shop can replay it with a different `shopify-shop-domain` header and have the host application process/act on that webhook as if it came from an arbitrary victim shop.

### Finding Description
`Utils::HmacValidator.validate` verifies a signature by recomputing it over `verifiable_query.to_signable_string` and comparing to the received `hmac`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw body — none of the Shopify headers are part of the signed material: [2](#0-1) 

Yet `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from unauthenticated request headers: [3](#0-2) 

`Registry.process` validates only the body-derived HMAC, then immediately trusts `request.shop` (and `request.topic`) as the tenant identity that is handed to the app's handler: [4](#0-3) 

This is the same class of bug as the referenced report: a value that determines *who the operation applies to* (there: the royalty/seller recipient; here: the `shop` tenant) is not covered by the cryptographic check that is supposed to bind the message to its owner. The equality the gem should guarantee is:
`hmac_signed_bytes == bytes_that_determine_the_tenant`
but instead:
`hmac_signed_bytes == raw_body_only` while `tenant == unauthenticated_header`.

Because the digest is computed purely over the body, two requests with identical bodies but different `shopify-shop-domain` headers produce the exact same valid HMAC. Any actor who can observe one legitimate webhook delivery for their own shop (e.g., an attacker who installs the app on a shop they control and inspects the webhook their own server receives) can capture a valid `(body, hmac)` pair and resend it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop. `Registry.process` will accept it as authentic and dispatch it to the handler tagged with the victim's shop, since only the body — not the shop header — is checked.

### Impact Explanation
This breaks the tenant/shop authentication boundary the HMAC is meant to enforce, letting an unprivileged actor (any merchant that has installed the app) forge webhook events attributed to a shop they do not own. Depending on how the host application's `WebhookHandler` uses `data.shop`, this can lead to cross-tenant data corruption, forging mandatory compliance events (`shop/redact`, `customers/redact`, `customers/data_request`) for a victim shop, or triggering shop-scoped business logic (e.g. `app/uninstalled`) against another tenant — i.e. cross-tenant access, which is a Critical-class impact under the given criteria.

### Likelihood Explanation
Reasonably likely: exploitation requires no secrets, tokens, or privileged access — only the ability to send an HTTP POST to the app's public webhook endpoint with attacker-controlled headers and a previously-observed valid `(body, hmac)` pair from any shop that installed the app (including the attacker's own shop). No interaction with `api_secret_key` is needed because the signature check never involves the header value being forged.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the signed material, or otherwise authenticate them against out-of-band knowledge (e.g., verify `shopify-shop-domain` matches a shop for which the app holds a valid, previously-established session/installation, not merely trusting the header value once the body-only HMAC passes). At minimum, document and enforce that `request.shop` must be cross-checked against the app's known set of installed shops before being trusted as the operation's tenant.

### Proof of Concept
1. App has two merchants installed: `attacker.myshopify.com` and `victim.myshopify.com`.
2. Attacker's own shop receives a legitimate webhook delivery, e.g. `orders/create`, with body `B` and header `shopify-hmac-sha256: H`, where `H = HMAC(secret, B)`.
3. Attacker resends the identical request to the app's public webhook endpoint, but sets `shopify-shop-domain: victim.myshopify.com` while keeping body `B` and header `H` unchanged.
4. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)`, which equals `H`, so validation succeeds: [5](#0-4) 
5. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built using `shop = "victim.myshopify.com"` from the attacker-controlled header, and the handler executes as if the event genuinely originated from the victim's shop: [6](#0-5)
