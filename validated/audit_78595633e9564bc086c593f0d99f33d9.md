### Title
Emporium CASE 2 stateless ops allow any unprivileged caller to drain assets held by Emporium that are not declared in their own `erc20TokenAddresses` array (e.g. NFTs deposited by other users) - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` only reconciles Emporium's balance for tokens explicitly listed in the caller-supplied `circomData.erc20TokenAddresses`, but CASE 2 ("stateless") ops execute arbitrary `op.endpoint.call(op.callData)` from Emporium itself, with no restriction on which contract/asset is touched. Because Emporium is the `msg.sender`/owner when it calls out, and `onERC721Received`/`onERC1155Received` in `Transferer.sol` unconditionally accept any NFT, an unrelated NFT/ERC1155 (or any token not listed by the attacker) parked in Emporium can be moved out with `transferFrom(emporium, attacker, tokenId)` and the accounting loop never notices, since that token address is absent from the attacker's own `erc20TokenAddresses` array.

### Finding Description
The claimed equality is: *"assets held by Emporium are only released to the stealthAddress/claimant who funded/owns that position."* In `EmporiumUpgradeable.runAction` (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:76-160`), accounting is performed only over `circomData.erc20TokenAddresses`: [1](#0-0) [2](#0-1) 

CASE 2 ops are executed with **no restriction on target contract or calldata content** beyond blocking the `callHinkalWallet`/`doSendToRelay` selectors: [3](#0-2) 

`performHinkalChecks`/`getHashedCalldata` only verify that the metadata blob (containing the `EmporiumStack`, hence `op.callData`) matches the `calldataHash` public input the prover chose — it does not constrain *what* that calldata may target: [4](#0-3) 

Any NFT sent to Emporium is accepted unconditionally: [5](#0-4) 

**Exploit flow:** Attacker A gets an NFT into Emporium's custody (via a CASE 2 op calling `mint(emporium, tokenId)` or `safeTransferFrom(..., emporium, tokenId)`, or simply because leftover assets from any prior interaction remain in Emporium). A does not need to declare the NFT contract in `erc20TokenAddresses`, so no UTXO/claim is created for it — it is simply unaccounted balance sitting on Emporium.

In a later, unrelated `transact()` call, attacker B (any unprivileged EOA who can deposit their own funds and build their own valid `CircomData`/proof) submits an `EmporiumStack` with a CASE 2 op whose `callData` is `NFT.transferFrom(emporium, B, tokenId)`, targeting the same NFT contract. Since `op.endpoint.call(op.callData)` runs with Emporium as `msg.sender`, and Emporium is the current owner of `tokenId`, ERC-721's `transferFrom` succeeds without any approval (owner-initiated transfer). Because B never listed the NFT contract in their own `circomData.erc20TokenAddresses`, the before/after balance-diff loop in `runAction` (lines 132-151) never inspects that token at all, so the theft leaves the balance-conservation checks (`BalanceChangeShouldBePositive`) and the ZK circuit's `amountChanges`/UTXO conservation entirely untouched. No nullifier, root, or `stealthAddress` field is involved in gating this call, so `insertNullifiers`, `rootHashExists`, and the circuit's `inTotal + amountChanges === outTotal` constraint provide no protection — they only bind the fungible-token public inputs B *chose to declare*, not the arbitrary side-effects of the CASE 2 external call.

### Impact Explanation
Direct theft of assets held on Emporium that belong to another user (or protocol) — here an ERC721/ERC1155 position — by any unprivileged party, with no proof ever authorizing the transfer to the thief. This matches the "Critical - direct theft of shielded or in-flight user funds" category. The same mechanism also permits draining any ERC20/ETH dust left in Emporium by simply omitting it from `erc20TokenAddresses`. The attack is repeatable against any leftover/parked assets and costs the attacker only their own valid Hinkal proof/gas.

### Likelihood Explanation
Preconditions: some asset (NFT, or unclaimed ERC20/ETH) must be resting in Emporium's custody, which is entirely plausible given CASE 2 ops can move assets into Emporium as an intermediate step of any composed action (e.g., NFT marketplace/bridge/mint flows), and dust routinely remains uncaptured since `handleOut` only creates UTXOs for tokens in the caller-chosen list. Attacker B needs no special privileges — only the ability to run `transact()` with a self-generated proof, which every user has by design (`onlyAllowedRecipient` only restricts `msg.sender` to Emporium itself, not the prover's identity). This is highly feasible and repeatable.

### Recommendation
Track and enforce ownership of any asset transferred through Emporium (e.g., record depositor's `stealthAddress`/owner mapping for non-fungible or off-list assets, or forbid arbitrary CASE 2 calls to contracts/selectors that move assets already resident in Emporium unless they are listed and accounted for in `circomData.erc20TokenAddresses`). At minimum, require that any token/NFT contract touched by an op's `callData` be included in `erc20TokenAddresses` so its balance delta is checked, and reject stateless CASE 2 calls whose calldata invokes `transferFrom`/`safeTransferFrom` moving assets *out* of Emporium unless backed by a corresponding declared, ZK-verified negative balance change.

### Proof of Concept
Hardhat fork test:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, an ERC721 mock, and register Emporium as allowed recipient.
2. As attacker A, call `transact()` with a valid proof and `CircomData` whose `externalActionMetadata` decodes to an `EmporiumStack` containing a CASE 2 op calling `NFT.mint(emporium, tokenId)` (NFT contract not present in `erc20TokenAddresses`). Assert `NFT.ownerOf(tokenId) == emporium` and A's own UTXO set contains no claim referencing `tokenId`.
3. As attacker B (different EOA, independent Hinkal deposit/proof), call `transact()` with a new `CircomData`/`EmporiumStack` whose CASE 2 op's `callData` is `NFT.transferFrom(emporium, B, tokenId)`; `erc20TokenAddresses` does not include the NFT contract.
4. Assert the call succeeds (no `BalanceChangeShouldBePositive` revert) and `NFT.ownerOf(tokenId) == B`.
5. Assert the equality is broken: no nullifier/root/stealthAddress from A's original deposit was ever consumed or referenced by B's proof, yet ownership of `tokenId` moved from Emporium (holding it for A) to B.
