### Title
Unchecked ERC20 boolean return value in Tron `IntentGatewayV2.withdraw()` / dust-sweep leads to silent transfer failure and fund loss - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed order funds and swept dust using a raw low-level `.call` to the token's `transfer` selector, checking only that the call did not revert — it never decodes/validates the boolean return value that `transfer` is supposed to return. This is the exact bug class from the reported `CollateralEscrowV1` finding (unchecked `transferFrom`/`transfer` return value), reachable by any relayer delivering a `RedeemEscrow`/`RefundEscrow` message or a `GET` response, and by the Hyperbridge-authorized `SweepDust` path.

### Finding Description
In `withdraw()`, which is invoked from `onAccept` for `RequestKind.RedeemEscrow` / `RequestKind.RefundEscrow` and from `onGetResponse` after order cancellation, ERC20 payouts to the beneficiary are done like this: [1](#0-0) 

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```

Only `success` (whether the low-level call reverted) is checked; the ABI-encoded boolean return data from `transfer` is discarded. Any ERC20/TRC20 token that follows the common non-reverting pattern of returning `false` on a failed transfer (rather than reverting) will make this call return `success = true` with a `false` payload that is never inspected. The escrow accounting (`_orders[body.commitment][token] -= amount`) and the `_filled[body.commitment] = beneficiary` finalization proceed as if the transfer succeeded, even though the beneficiary received nothing.

The same unchecked pattern is used for fee token payout in the same function: [2](#0-1) 

and for the Hyperbridge-governance-triggered dust sweep: [3](#0-2) 

This is notably a regression relative to the canonical EVM `IntentsBase.sol`, which performs the equivalent release using `SafeERC20.safeTransfer`, which does validate the returned boolean: [4](#0-3) 

### Impact Explanation
If the output/fee token used in an order is a non-reverting ERC20 (a known real-world pattern, and specifically the norm for TRC20 USDT on Tron, which this contract is explicitly deployed to support per its `IntentGatewayV2` header comment), a failed `transfer` call (e.g., due to a blacklist, paused state, or insufficient contract balance edge cases) will be silently accepted:
- The escrow balance is decremented and the order is marked filled/refunded even though the beneficiary never received funds — the tokens remain stranded in the `IntentGatewayV2` contract with no accounting path to recover them (permanent loss of user/solver funds).
- Because `withdraw` is reachable via relayer-delivered `RedeemEscrow`/`RefundEscrow` messages (`onAccept`) and via `onGetResponse` (unprivileged relayer submits a valid state proof), any relayer can trigger this path once the underlying token misbehaves, and the false accounting is baked into on-chain state irreversibly.

### Likelihood Explanation
This bug only manifests for tokens that return `false` rather than reverting on failed transfer. Given the file is Tron-specific and Tron's dominant token (USDT-TRC20) is well known for non-standard, often silently-failing ERC20 semantics, the likelihood of encountering such a token in production on this specific deployment target is materially higher than for a generic EVM chain, making this a realistic Medium-severity issue rather than a purely theoretical one.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` handling with OpenZeppelin's `SafeERC20.safeTransfer`, which is already imported and used elsewhere in this same contract (`safeTransferFrom` in `placeOrder`). `SafeERC20` correctly reverts both when the call reverts and when it succeeds but returns `false` (or non-boolean-decodable data), eliminating the unchecked-return-value class of bug while preserving compatibility with tokens that don't return a value at all.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with a mock ERC20 whose `transfer` returns `false` on failure instead of reverting (mirrors real TRC20 USDT behavior in failure paths, e.g. blacklisted recipient).
2. Place and fill an order so that `_orders[commitment][token] = escrowedAmount` is populated.
3. Trigger the mock token's failure condition for the beneficiary address, then deliver a `RedeemEscrow` message (or drive `cancelOrder` → `onGetResponse`) so `withdraw()` executes.
4. Observe: `token.call(...)` returns `success = true` (the call didn't revert) with return data encoding `false`; the `if (!success) revert TransferFailed();` check passes, `_orders[commitment][token] -= amount` executes, and `_filled[commitment]` is set — despite the beneficiary balance being unchanged, i.e. tokens are permanently stuck in the gateway with no accounting record left to reclaim them.
