### Title
Permanent market freeze: `scaled_to_original` overflows i128 before the borrow-index cap engages, bricking repay/withdraw/liquidate - (File: contracts/pool/src/interest.rs, common/src/rates/scaling.rs)

### Summary
CVE-2019-8783's class is "maliciously crafted input drives state into memory corruption." The XOXNO Lending analog is unchecked-range arithmetic: a market whose scaled debt times borrow index exceeds `i128` makes every subsequent accrual panic with `MathOverflow`. Because `interest::global_sync` runs before every pool mutation, the market becomes permanently un-operable — suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate. The `MAX_BORROW_INDEX_RAY` cap was intended to bound the index, but the value computation `borrowed * borrow_index / RAY` overflows before the cap can take effect, so the guard never engages.

### Finding Description
`global_sync` (`contracts/pool/src/interest.rs:20-33`) calls `accrue_chunk` → `accrue_step`, which computes interest as `half_up(borrowed * borrow_index' / RAY) − half_up(borrowed * borrow_index / RAY)`. `calculate_utilization` (`contracts/pool/src/cache/scale.rs:23-26`) likewise calls `scaled_to_original(borrowed, borrow_index)`. Both go through `mul_div_half_up`/`mul_div` in `common/src/math/fp_core.rs`, which widens intermediates to `I256` but still requires the *result* to fit `i128` (`to_i128()` returns `None` → `MathOverflow` panic).

`borrowed` is RAY-scaled shares and `borrow_index` is up to `MAX_BORROW_INDEX_RAY` (10^36). For a large market (e.g., ~10^9 tokens at 18 decimals → `supplied`/`borrowed` on the order of 10^54 RAY), `borrowed * index / RAY` exceeds `i128::MAX ≈ 1.7e38` long before `index` reaches the 10^36 cap. `update_borrow_index` multiplies *then* clamps (per the test comment in `common/tests/rates/index.rs:497-512`), so the index cap cannot save the value-side multiplication.

The codebase's own harness proves reachability and permanence: `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361` supplies ~10^27 base units to an 18-decimal market, borrows to 98% utilization on the XLM curve, advances time, and observes `update_indexes` fail with `MATH_OVERFLOW` within the loop bound — after which both `withdraw` and `repay` fail with the same error. Since every verb accrues first (`entrypoint → Cache::load → global_sync → mutate`), there is no path that skips the panicking computation; `clean_bad_debt`/`seize_positions`/`recapitalize` also accrue on the same cache path, so the market cannot even be wound down.

### Impact Explanation
Permanent freezing of funds: all supplier principal and yield in the affected market is locked forever — withdraw, repay, liquidate, seize, and recapitalize all revert in `global_sync`. No privileged recovery exists short of a contract upgrade.

### Likelihood Explanation
Medium. The trigger needs no privilege — `supply`, `borrow`, and `update_indexes` are reachable by any address (pool ops go through the controller's public entrypoints, and `update_indexes`/`claim_revenue` are public on the controller). However it requires a whale-scale market (≈10^9 whole tokens of an 18-decimal asset, or proportionally less for low-decimal/high-price assets where caps are lifted), sustained near-max utilization, and enough elapsed accrual chunks for the index to grow into the overflow region (the test reaches it within tens of simulated years at steep-curve rates). It is a real code path, not hypothetical — the project maintains a dedicated regression test for it — but capital and time requirements keep it below high likelihood.

### Recommendation
In `accrue_step`/`update_borrow_index`, clamp the index **before** using it in value computations: compute `new_index = min(index * factor / RAY, MAX_BORROW_INDEX_RAY)` and detect the overflow via `try_mul_div_half_up`, falling back to the cap instead of panicking. Additionally, make `scaled_to_original`-based accrual use a saturating or short-circuit path once `borrowed * index` leaves `i128` — e.g., cap accrued interest to a representable bound and mark the market accrued so subsequent verbs can proceed. Indexers should never be able to push a market into a state where the only recovery is `upgrade`.

### Proof of Concept
The repository already contains the PoC: `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs::a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (lines 320-361). Steps:

1. Create market `BIG18` (18 decimals) with `xlm_curve()`; lift supply/borrow caps.
2. `supply` 10^9 × 10^18 base units (BOB).
3. ALICE supplies collateral and `borrow`s 98% of `BIG18`.
4. Advance ledger time in 1-year steps calling `update_indexes`.
5. Result: `update_indexes` returns `Error(Contract, MATH_OVERFLOW)` with `borrow_index < MAX_BORROW_INDEX_RAY` (cap never engaged); subsequent `withdraw(BOB, BIG18, 1)` and `repay(ALICE, BIG18, …)` both revert with `MATH_OVERFLOW`. The market, including all supplier funds, is frozen permanently.

Note on verification limits: I confirmed the panic path through `interest.rs`, `cache/scale.rs`, `fp_core.rs`, and the failing-mutation assertions in the harness test, but did not fully trace `clean_bad_debt`/`seize_positions` line-by-line to confirm they also cannot bypass accrual; the pool README's uniform flow (`every mutation runs global_sync`) supports that they cannot.
