### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from the unauthenticated `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature that `Utils::HmacValidator` checks is computed only over the raw request body. An attacker who owns any shop that has the vulnerable app installed can capture a genuinely-signed webhook payload from their own store and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop, causing the app to process attacker-controlled data as if it originated from the victim tenant — while the HMAC check still passes.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are all read straight from HTTP headers, which are never included in the signed bytes: [2](#0-1) 

`Registry.process` verifies the request purely via `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (i.e. the body only) and compares it to the `hmac-sha256` header: [3](#0-2) [4](#0-3) 

After a successful HMAC check, the unauthenticated `shop` header value is forwarded, unmodified, into `WebhookMetadata` and handed to the host app's handler as the trusted tenant identifier: [5](#0-4) [6](#0-5) 

The gem's own documentation instructs developers to build the `Request` directly from `request.raw_post` and `request.headers.to_h` and states that `Registry.process` "will verify the request did indeed come from Shopify," implying the whole request (including the shop attribution) is authenticated: [7](#0-6) 

This is the exact bug class described in the report: a field that is *acted on* (here, the `shop` used as the tenant key passed to the handler) is not covered by the cryptographic binding (HMAC) that is supposed to authenticate the whole message. The equality that should hold — `hmac_signed_shop == shop_used_by_handler` — does not, because the signature never includes the shop at all. Any raw body/HMAC pair that Shopify issues for *shop A* remains valid for *any* `shop-domain` header value an attacker chooses, including *shop B*.

### Impact Explanation
This breaks the tenant boundary the webhook mechanism is supposed to enforce (cross-tenant access), which is Critical severity per the rubric. Because a merchant can freely install a developer's public app on their own (attacker-controlled) store, they can legitimately receive a real Shopify webhook — with a body and HMAC that Shopify computed correctly — and then replay that exact `raw_body` + `hmac-sha256` value to the app's public webhook endpoint while substituting a victim's `shop-domain` (and `webhook-id`/`topic`, which are equally unauthenticated). The receiving app has no way, using this gem, to detect the mismatch: `HmacValidator.validate` returns `true`, and `WebhookMetadata.shop` reports the attacker-chosen value. Depending on how the host app uses `data.shop` (e.g., looking up/mutating per-shop records, honoring `shop/redact` or `customers/redact` mandatory compliance webhooks, gating multi-tenant business logic), this can lead to writing attacker-controlled data into another tenant's records, triggering redaction/deletion flows against the wrong shop, or otherwise confusing tenant-scoped state — a direct violation of the tenant isolation the HMAC check is meant to guarantee.

### Likelihood Explanation
High. The only prerequisite is the ability to install the app on any (even a free/dev) store to receive one legitimately signed webhook — no leaked secrets, no privileged account, and no dependence on the host app deviating from the documented integration pattern shown in `docs/usage/webhooks.md`. The attack is a straightforward HTTP replay with one header rewritten (`X-Shopify-Shop-Domain`), requiring no cryptographic work since the original HMAC remains valid (it never covered the header in the first place).

### Recommendation
- Bind the `shop`, `topic`, and `webhook_id` values into the HMAC computation (or otherwise cryptographically bind the headers to the payload) so that the verified signature covers everything the handler relies on, not just the body.
- At minimum, document prominently that `Request#shop`/`#topic`/`#webhook_id` are NOT covered by `HmacValidator.validate` and that host applications must independently corroborate the shop (e.g., cross-check against a known installed-shop list) before trusting `WebhookMetadata.shop` for any tenant-scoped operation.
- Consider rejecting/flagging webhook headers that are inconsistent with any additional integrity signal Shopify provides (if available) rather than relying on the body-only HMAC as an implicit "whole request is authentic" guarantee.

### Proof of Concept
1. Attacker installs the vulnerable app on their own store `attacker-shop.myshopify.com` and lets it register a webhook (e.g., `orders/create`).
2. Shopify sends the app a legitimate webhook request:
   - Headers: `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid HMAC of raw body>`, `X-Shopify-Topic: orders/create`.
   - Body: `{"id": 1, ...attacker-controlled order fields...}`.
3. Attacker captures this exact `raw_body` and `X-Shopify-Hmac-Sha256` value (they own this store, so this is trivially observable, e.g., from their own callback logs).
4. Attacker sends a new HTTP POST directly to the target app's public webhook callback URL, reusing the captured `raw_body` and `X-Shopify-Hmac-Sha256`, but replacing `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
5. The app constructs `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` and calls `ShopifyAPI::Webhooks::Registry.process(request)` exactly as documented.
6. `Utils::HmacValidator.validate(request)` recomputes the HMAC over `raw_body` only, which still matches — passing verification.
7. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's order data>, ...)`, causing the app to process attacker-controlled data attributed to the victim tenant.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
