### Title
Attacker-controlled route hops can execute malicious pool code under the caller’s authorization tree - (File: contracts/swap-aggregator/src/execute/mod.rs)

### Summary
`execute_strategy` decodes a caller-supplied route containing arbitrary `assets` addresses, including the pool address for every hop. Venue dispatch then invokes that address without checking that it is a known or deployed venue contract. Because the strategy executes beneath the caller’s `require_auth` invocation, malicious pool code can add token transfers from the caller to the recorded authorization tree; if that tree is signed, the transaction can steal unrelated wallet funds while still returning a valid swap output.

### Finding Description
`Router::execute_strategy` accepts `sender`, `total_in`, and caller-controlled `swap_xdr`, decodes it into a `StrategyPayload`, and calls `execute::run` [1](#0-0) . `run` authenticates only `sender`, decodes the program, and executes each operation [2](#0-1) .

For every swap instruction, the router reads `pool`, `token_in`, and `token_out` from the payload-controlled `assets` registry and dispatches to the encoded venue [3](#0-2) . The venue adapters then invoke the supplied pool address: for example, the Soroswap adapter calls `get_reserves` and `swap` on `ctx.hop.pool` [4](#0-3) . No allowlist, code hash, token-pair binding, or pool provenance check restricts that address.

A malicious contract implementing the expected pool ABI therefore runs inside the transaction. The repository’s harness demonstrates the consequence: a rogue hop calls `token.transfer(victim, attacker, amount)` [5](#0-4) . Simulation records that transfer as a child of the victim’s `swap_collateral` authorization [6](#0-5) , and enforcing mode executes it when the signed tree includes that child [7](#0-6) .

The same route can be reached through `swap_collateral`, which passes caller-supplied `swap` bytes into the configured router after authenticating the account owner or delegate [8](#0-7) .

### Impact Explanation
This is theft of user funds. The malicious hop is not limited to manipulating the routed input amount: it can request transfers of arbitrary tokens held by the caller, including assets unrelated to the protocol. The measured router output can still be fair and the final account health can remain valid, so neither the router’s balance checks nor the controller’s risk checks prevent the side-effect transfer.

The exploit does require the victim to sign the authorization tree containing the malicious child. However, ordinary route payloads are opaque XDR, and a malicious route provider can produce a transaction whose simulation includes the extra child authorization while presenting a legitimate swap.

### Likelihood Explanation
An unprivileged attacker can deploy the malicious pool and construct a syntactically valid route that references it. Both direct `execute_strategy(sender, total_in, swap_xdr)` calls and controller strategy calls using caller-supplied `StrategySwap` bytes reach the untrusted pool address. Exploitation requires convincing a user or client to submit and sign the crafted route/authorization tree, so the severity is High rather than Critical.

### Recommendation
Do not treat payload-selected pool addresses as trusted code. Bind every executable hop to protocol-verified venue/pool identities, or require venues to resolve pool addresses from signed configuration rather than the caller-controlled `assets` registry.

At minimum:

- maintain per-venue pool registries or verified pool metadata;
- validate that the declared pool is compatible with `token_in` and `token_out`;
- reject routes containing unregistered pools;
- require simulation/auth-tree inspection for strategy transactions until routing is permissioned;
- document that route providers must not introduce additional authorization children.

### Proof of Concept
1. Deploy `RogueHopPool` configured with `(victim, wallet_token, attacker, amount)`. Its `swap()` calls `token::Client::new(...).transfer(victim, attacker, amount)` [9](#0-8) .
2. Build a route whose `assets` registry contains the malicious address as the hop pool and otherwise specifies a valid `token_in`/`token_out` swap. The router dispatches to that supplied pool address [3](#0-2) .
3. Submit the route through `swap_collateral` or direct `execute_strategy`. During simulation, the rogue token transfer is attached under the caller’s root authorization [10](#0-9) .
4. If the signed transaction includes the simulated child, execution moves the victim’s unrelated wallet token to the attacker while the swap still completes [7](#0-6) .
