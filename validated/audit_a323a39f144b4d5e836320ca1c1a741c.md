### Title
Webhook shop-domain (and other metadata) is not covered by the HMAC signature, allowing a spoofed cross-tenant `shop` attribution - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` only authenticates the raw request body against the HMAC signature. It then forwards the `shop`, `topic`, `webhook_id`, and `api_version` values — all parsed straight from unauthenticated HTTP headers — to the app's webhook handler as if they were verified. This breaks the identity binding: **bytes verified (body) ≠ bytes parsed (headers, including `shop`)**, exactly the class of accounting/binding mismatch described in the referenced report (a value used downstream is not covered by the same check that "authorizes" the operation).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from the (attacker controllable at the HTTP layer) request headers: [2](#0-1) 

`Registry.process` validates only this body-derived HMAC and then immediately trusts `request.shop`/`request.topic`/`request.webhook_id` to build `WebhookMetadata`, handing it to the app's handler: [3](#0-2) 

Because the api_secret_key is shared across *all* shops that have installed a given app (it is per-app, not per-tenant), any unprivileged merchant who installs the app receives legitimately-signed webhooks for their **own** shop. The HMAC for that request depends only on `raw_body`; nothing binds the signature to the `X-Shopify-Shop-Domain` header. That merchant can therefore replay the exact `(raw_body, hmac)` pair they legitimately received, but substitute an arbitrary victim `shop` domain header, and `HmacValidator.validate` will still return `true` because it never inspects the `shop` header. The handler then executes with `WebhookMetadata#shop` pointing at the victim tenant, even though the body content is the attacker's own.

The gem's own documentation reinforces the false sense of full-request authentication, stating that `Registry.process` "will verify the request did indeed come from Shopify" — implying the whole request, not merely the body, is authenticated: [4](#0-3) 

### Impact Explanation
An unprivileged internet user who can install the target app on any shop (a normal, unprivileged self-service action) obtains at least one legitimately HMAC-signed webhook body. They can replay it against the app's public webhook endpoint with the `shop` (and `topic`/`webhook_id`) header changed to a victim tenant's domain. `Registry.process` will accept it as authentic and the host app's handler will process/attribute data under the wrong tenant identity — a cross-tenant integrity/confusion issue (Critical: cross-tenant access), since the library asserts full "came from Shopify" verification while only binding the body.

### Likelihood Explanation
Likelihood is limited by the fact that the attacker still needs one legitimate `(body, hmac)` pair (trivially available by installing the app themselves) and the host app must key any tenant-sensitive action off `WebhookMetadata#shop`/`#topic` without independent verification — which is exactly the documented, expected usage pattern shown in the gem's own docs (`data.shop`, `data.topic` used directly). Because this usage is the sanctioned pattern, not a misuse of the API, the likelihood of real-world exposure across integrating apps is meaningful.

### Recommendation
Bind the header-derived identity fields into the signed payload verification, or explicitly document/enforce that `shop`, `topic`, and `webhook_id` are unauthenticated and must be cross-checked by the caller (e.g., against the shop's known registered webhook subscriptions) before being trusted. At minimum, update `Utils::HmacValidator`/`Webhooks::Request` so that the signable string incorporates the shop-domain and topic headers (mirroring how `AuthQuery#to_signable_string` binds `shop`, `host`, `code`, `state`, `timestamp` together), removing the asymmetry between what is verified and what is acted upon.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a normal, unprivileged flow) and registers for e.g. `orders/create` webhooks.
2. Shopify sends a legitimately signed webhook to the app's endpoint:
   - `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - `raw_body: {"id": 1, ...}`
3. Attacker replays the identical `raw_body` and `X-Shopify-Hmac-Sha256` value to the same endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, raw_body)` — unaffected by the header change — and returns `true`.
5. `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` is built and passed to the app's handler, which now processes attacker-controlled data under the victim tenant's identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
