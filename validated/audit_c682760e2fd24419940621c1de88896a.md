Webhook `shop` identity is not covered by the HMAC, enabling cross-tenant webhook spoofing via replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body [1](#0-0) . The signable string used for that HMAC is only the raw body [2](#0-1) , while the `shop` (and `topic`, `webhook_id`, `api_version`) values that get handed to the app's handler come from unauthenticated HTTP headers that are never mixed into the signed material [3](#0-2) . This breaks the intended binding of `hmac == HMAC(secret, body)` ⇒ `shop == the header value`, since the header can be swapped without invalidating the HMAC.

### Finding Description
`Webhooks::Request` includes `Utils::VerifiableQuery` and defines `to_signable_string` to return only `@raw_body`: [2](#0-1) . `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (the body) and compares it to the `hmac` header [4](#0-3) . Once that check passes, `Registry.process` builds a `WebhookMetadata` struct using `request.shop`, which is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the signed body [5](#0-4) [6](#0-5) . `WebhookMetadata#shop` is a plain, trusted field passed straight to the app-supplied `WebhookHandler#handle` [7](#0-6) .

Because only the body is signed, an attacker who has legitimately received one genuine webhook (e.g., by installing the app on their own store, or capturing any webhook delivery for shop A) can resend the exact same `raw_body` + `hmac-sha256` value to the app's webhook endpoint while substituting the `shopify-shop-domain` header for shop B. The HMAC check still succeeds (it only verifies the body, not the header), so `Registry.process` will happily dispatch the handler with `WebhookMetadata.shop == "B"` even though the payload was never generated for shop B. This is the exact analog called out by the rule set: "a field acted on but not covered by the HMAC" — here it is the tenant identifier (`shop`) itself.

### Impact Explanation
Any app that trusts `WebhookMetadata#shop` (as documented and expected — see docs/usage/webhooks.md) to route data updates, cache invalidation, credential/session lookups, or authorization decisions per-tenant can be tricked into applying shop-A's webhook body under shop-B's identity, or vice versa. This is a cross-tenant confusion: the gem asserts a shop binding that the cryptographic check does not actually enforce, giving an attacker (any actor capable of triggering or capturing one real webhook delivery to the app, e.g., a low-privilege merchant on any shop with the app installed) the ability to make the host application process arbitrary already-signed bodies under a different shop's identity. Depending on how the host app scopes its per-shop state from that field, this can lead to cross-tenant data corruption or disclosure.

### Likelihood Explanation
Exploitability requires an attacker to obtain at least one valid `(raw_body, hmac)` pair — trivially available to anyone who installs the app on their own store and receives a real webhook (no `client_secret` or access token needed) — and to be able to POST to the app's public webhook endpoint with a modified `shop-domain` header, which is normal HTTP client capability. No secret material is needed to perform the replay. The likelihood is therefore not trivial to dismiss, though it does depend on the host application actually branching business logic on `WebhookMetadata#shop` without independently re-validating that the shop is one the app has an active installation/session for — a reasonably common pattern this gem's own docs encourage (`ShopifyAPI::Webhooks::Registry.process` → handler keyed by `data.shop`).

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the material that is authenticated, or otherwise assert that the header-derived `shop` matches an expectation established by the caller (e.g., require the host app to pass the expected shop and compare it explicitly, or refuse to trust `request.shop` for authorization decisions and document that callers must independently verify shop context, such as by matching against the shop of an active, looked-up session). At minimum, the gem should stop presenting `WebhookMetadata#shop` as an authenticated field when only the body is HMAC-protected.

### Proof of Concept
1. Install the app on attacker-controlled store `evil.myshopify.com`; trigger any subscribed webhook topic (e.g., `orders/create`) to capture a real delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (valid for `B` under the app's secret).
2. Replay the captured request to the app's public webhook endpoint, keeping `raw_body = B` and `x-shopify-hmac-sha256 = H` unchanged, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` computes `HmacValidator.validate(request)` over `to_signable_string` (`= B`) — validation succeeds because `B` and `H` are unchanged [2](#0-1) [8](#0-7) .
4. The handler is invoked with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed(B), ...)` [9](#0-8) , causing the host app to process attacker-controlled webhook content under the victim shop's identity.
