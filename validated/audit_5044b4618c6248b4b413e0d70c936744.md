## Analysis

The `CallDispatcher` contract that Hyperbridge's `IntentGatewayV2`/`IntentsBase` apps use for predispatch (swap-then-escrow) and postdispatch (fill-then-act) calldata is a single, stateless, permissionless singleton shared across every order and every app on a chain [1](#0-0) . It has an open `receive() external payable {}` and no access control on the ERC20 side either — anyone can send it ETH or tokens at any time [2](#0-1) .

`IntentGatewayV2.placeOrder`'s predispatch phase treats the dispatcher's *raw balance* as ground truth for how much was produced by the swap: it reads `address(dispatcher).balance` / `IERC20(token).balanceOf(dispatcher)`, only checks `balance < requiredAmount`, and sweeps that entire ambient balance back to the gateway:

```solidity
if (token == address(0)) {
    uint256 balance = address(dispatcher).balance;
    if (balance < requiredAmount) revert InsufficientNativeToken();
    transferCalls[i] = Call({to: address(this), value: balance, data: ""});
    balancesBefore[i] = address(this).balance;
} else {
    uint256 balance = IERC20(token).balanceOf(dispatcher);
    if (balance < requiredAmount) revert InvalidInput();
    ...
}
``` [3](#0-2) 

The same pattern exists in the TRON deployment, which credits escrow directly from that ambient balance check rather than from what the order's own predispatch call actually produced [4](#0-3) . The postdispatch sweep in `_execute` has the identical shape: it sweeps `dispatcher.balance` / `IERC20(token).balanceOf(dispatcher)` for whichever tokens the caller (solver, at fill time) lists in `outputsLen`, with no check that the swept balance actually originated from *this* call's calldata execution [5](#0-4) .

Because `_params.dispatcher` is one shared address reused across orders (and across `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata execution as well) [6](#0-5) , and the postdispatch sweep only sweeps the tokens *declared* in `output.assets` [7](#0-6) , any token produced as an unlisted byproduct of a multi-hop calldata call (or simply donated directly to the dispatcher by anyone) is left stranded in the dispatcher with no per-order accounting. This ambient balance is then indistinguishable from "genuinely produced by my predispatch call" the next time any order's predispatch sweep runs for that same token — exactly the `getTVLForAsset`-style flaw in the report, where a directly-transferable/attacker-influenceable raw balance stands in for tracked internal accounting.

### Title
Escrow/dust accounting in `IntentGatewayV2`/`IntentsBase` trusts the shared `CallDispatcher`'s raw balance instead of per-order tracked amounts - (File: `evm/src/apps/IntentGatewayV2.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/src/utils/CallDispatcher.sol`)

### Summary
`IntentGatewayV2.placeOrder`'s predispatch flow and `IntentsBase._execute`'s postdispatch flow both determine "how much was produced by this order's calldata" by reading `address(dispatcher).balance` / `IERC20(token).balanceOf(dispatcher)` on the single, permissionless, shared `CallDispatcher` contract, rather than tracking amounts specific to the current call. Since the dispatcher accepts arbitrary ETH/ERC20 transfers from anyone and only sweeps tokens explicitly declared by the caller, ambient/stranded balances left by unrelated calldata execution (or deliberately donated by an attacker) get silently pooled and can be swept into whichever order next happens to reference that token, with no ownership check tying the swept balance to the order that supposedly produced it.

### Finding Description
`CallDispatcher` is a bare relay contract with a public `receive()` and no state isolation between calls [8](#0-7) . It is used as `_params.dispatcher`, one address shared by every order placed through `IntentGatewayV2` (and reused by `HyperFungibleToken`/`WrappedHyperFungibleToken` for their own calldata execution).

In `placeOrder`'s predispatch branch, after the user's `predispatch.call` executes on the dispatcher, the code measures "how much came out" purely from the dispatcher's current balance:
```solidity
uint256 balance = IERC20(token).balanceOf(dispatcher);
if (balance < requiredAmount) revert InvalidInput();
transferCalls[i] = Call({ to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance) });
``` [9](#0-8) 

This balance is not scoped to the current transaction's calldata output — it is whatever happens to sit in the dispatcher at that moment. In `IntentsBase._execute` (used for postdispatch calldata at fill time), the same ambient-balance sweep occurs, restricted only to the token addresses the caller lists in `order.output.assets`:
```solidity
uint256 balance = IERC20(token).balanceOf(dispatcher);
if (balance > 0) {
    sweepCalls[sweepCount] = Call({ to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance) });
    ...
}
``` [10](#0-9) 

Because the sweep in `_execute` only iterates over the declared `outputsLen` tokens, any token produced as a byproduct of a multi-step swap/call (e.g., an intermediate hop token, rounding remainder, or a token the caller simply forgot/chose not to declare) is left behind in the dispatcher indefinitely — there is no mechanism forcing full drainage or attributing the residual to the order that created it. The same applies in reverse to `placeOrder`'s predispatch sweep: it happily accepts whatever balance is present regardless of whether it was produced by *this* order's `predispatch.call` or exists for any other reason (stranded dust from an earlier order's calldata, or an attacker directly transferring tokens to the well-known, permissionless dispatcher address).

This is the same root-cause pattern as the reported `RioLRTAssetRegistry.removeAsset` bug: a security/accounting decision (`balance < requiredAmount` gating escrow credit and sweep amount) is derived from a directly-transferable contract balance on a shared, unrestricted-deposit contract, rather than from state tracked exclusively for the operation in question.

### Impact Explanation
An order placer can satisfy the `requiredAmount` check for a predispatch-escrowed input using tokens that were never actually produced by their own `predispatch.call` — for example stranded dust left in the dispatcher by a previous order's incomplete/multi-hop calldata sweep, or tokens they pre-fund into the dispatcher themselves through a trivial transfer immediately before invoking `placeOrder` with a nominal/no-op predispatch call. Because the sweep is not scoped to the current call, whichever party's tokens happen to be sitting in the shared dispatcher get pulled into an unrelated order's escrow (or accounted as protocol dust), and a solver can subsequently be induced to release genuine output assets in `fillOrder` against escrow that was never actually backed by the placer's own predispatch execution. This is a fund-accounting/fund-loss vector rather than a pure availability issue: value that should belong to whichever transaction/party actually deposited it into the dispatcher can end up credited to a different, unrelated order.

### Likelihood Explanation
Reachability requires no privilege: any address can call `placeOrder` with a `predispatch` section, and any address can send ETH/ERC20 tokens directly to the publicly known, permissionless `CallDispatcher` address at any time via `receive()`/`transfer`. The precondition of "residual/stranded balance in the dispatcher" is realistic given that `_execute`'s postdispatch sweep only drains tokens explicitly declared in `order.output.assets`, and complex calldata (multi-hop swaps, DeFi composability the docs explicitly advertise) commonly produces intermediate or byproduct token balances that are easy to omit from that list.

### Recommendation
Do not use `address(dispatcher).balance` / `IERC20(token).balanceOf(dispatcher)` as the escrow/sweep source of truth. Instead, snapshot the dispatcher's balance for each relevant token immediately before dispatching the order's own calldata and use only the *delta* produced by that specific call (the codebase already does this correctly elsewhere, e.g. `balancesBefore[i] = address(this).balance` pattern in the gateway sweep loop, but it needs to be applied consistently to the dispatcher-side balance too, not just the gateway-side receiving balance). Additionally, consider making the postdispatch/predispatch sweep exhaustive (sweep and refuse to leave any nonzero balance of any token touched by the call) or reject calldata that leaves unexpected token balances behind, so stranded residue can never accumulate and be claimed by an unrelated order.

### Proof of Concept
1. Attacker/observer notices (or engineers, via their own crafted `predispatch.call`/`output.call`) that the shared `CallDispatcher` at `_params.dispatcher` holds a stranded balance of token `T` (e.g., left over from a prior order's multi-hop postdispatch call that only declared a subset of output tokens in `output.assets`, per `IntentsBase._execute` lines 504-533).
2. Attacker calls `placeOrder` with `order.inputs[i] = {token: T, amount: requiredAmount}` and a `predispatch.call`/`predispatch.assets` that transfers a negligible amount to the dispatcher and performs a trivial/no-op call (satisfying `order.predispatch.call.length > 0 && order.predispatch.assets.length > 0`).
3. In `IntentGatewayV2.placeOrder`, `balance = IERC20(T).balanceOf(dispatcher)` reads the pre-existing stranded balance, which already exceeds `requiredAmount`, so the `InvalidInput` check passes and the full balance is swept to the gateway and escrowed against attacker's order commitment (`evm/src/apps/IntentGatewayV2.sol` lines 268-282, `_orders[commitment][token] += reducedInputs[i].amount` in the TRON variant at lines 437-441).
4. Attacker's order now holds legitimate-looking escrow of token `T` that was never actually backed by value the attacker contributed via their own predispatch execution.
5. A solver fills the order in `fillOrder`, releasing genuine output assets to the attacker's beneficiary in exchange for escrow that was effectively "free" to the attacker.

contract CallDispatcher is ICallDispatcher {
    /**
     * @dev error thrown when the target is not a contract.
     */
    error NotContract(address target);

    /**
     * @dev error thrown when a call fails.
     */
    error CallFailed(address target, bytes result);

    /**
     * @dev Receive function to accept ETH transfers
     */
    receive() external payable {}

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
}
```

    function _execute(Order calldata order, uint256 outputsLen) internal {
        if (order.output.call.length == 0) return;

        address dispatcher = _params.dispatcher;
        ICallDispatcher(dispatcher).dispatch(order.output.call);

        Call[] memory sweepCalls = new Call[](outputsLen);
        uint256 sweepCount = 0;

        for (uint256 i; i < outputsLen;) {
            address token = address(uint160(uint256(order.output.assets[i].token)));

            if (token == address(0)) {
