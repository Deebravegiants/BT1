### Title
`erc20TokenAddresses=[]` fully disables the Emporium solvency check, letting `stack.ops` drain co-mingled funds with no `BalanceChangeShouldBePositive` guard - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` only checks solvency (`balancesAfter[i] - balancesBefore[i] + deltaAmountChanges[i] >= 0`) for tokens listed in `circomData.erc20TokenAddresses`, iterating strictly over that array's indices. The `stack.ops` loop that actually executes arbitrary calls (`op.endpoint.call{value: op.value}(op.callData)`) is decoded independently from `externalActionMetadata` and is never bounded by or tied to `erc20TokenAddresses`, so an attacker can submit a proof with `erc20TokenAddresses = []` (which is not rejected by `dimensionsCheck`, since there is no minimum-length requirement) while crafting `ops` that move real ETH/ERC20 balances out of the Emporium contract, with zero on-chain solvency enforcement.

### Finding Description
The intended equality per token `i` is:
`balancesAfter[i] - balancesBefore[i] + (deltaAmountChanges[i] < 0 ? -deltaAmountChanges[i] : 0) >= 0`

which is meant to hold for every token actually touched by `stack.ops` [1](#0-0) .

Trace:
- `Hinkal.transact` calls `hinkalHelper.performHinkalChecks`, which calls `dimensionsCheck` [2](#0-1)  — this only requires `erc20TokenAddresses.length == dimensions.tokenNumber` and the same for `amountChanges`, `onChainCreation`, `slippageValues`, `inputNullifiers`; there is **no minimum on `tokenNumber`**, so `tokenNumber = 0` passes.
- `Hinkal._externalTransact` allocates `deltaAmountChanges` with length `circomData.erc20TokenAddresses.length` [3](#0-2) , so with `erc20TokenAddresses=[]`, `deltaAmountChanges=[]` too, confirming the premise.
- `EmporiumUpgradeable.runAction` computes `balancesBefore`/`balancesAfter` only over `circomData.erc20TokenAddresses` [4](#0-3) , and the `stack.ops` execution loop is completely independent of that array's contents or length [5](#0-4) . `stack` (including `ops`, `endpoint`, `callData`, `value`) is decoded from attacker-supplied `circomData.externalActionData.externalActionMetadata` and is only integrity-checked via `calldataHash`/`getHashedCalldata`, never cross-checked against `erc20TokenAddresses`.
- The solvency loop that would revert with `BalanceChangeShouldBePositive` iterates `i < circomData.erc20TokenAddresses.length` [6](#0-5) . With an empty array this loop body never executes for any token, including `address(0)`/ETH.

Root cause: the circuit and `dimensionsCheck` never constrain `erc20TokenAddresses` to contain every token/ETH actually touched by `stack.ops`; the on-chain balance-diff loop is the only mechanism meant to catch unaccounted movement, and it is keyed exclusively off the attacker-chosen `erc20TokenAddresses` array length/content, which the attacker fully controls and can set to `[]`.

Attacker call: submit `transact(a,b,c, dimensions{tokenNumber:0,...}, circomData)` with `circomData.erc20TokenAddresses = []`, `externalActionData.externalActionId` set to Emporium, and `externalActionMetadata` encoding an `EmporiumStack` whose `ops` array contains a stateless op (`invokeWallet=false`, `stack.signerAddress=address(0)` to skip `verifyWallet`'s signature branch) with `op.endpoint` = attacker EOA/contract and `op.value` = Emporium's full ETH balance (or an ERC20 `transfer` call moving Emporium's token balance to the attacker). Since `erc20TokenAddresses=[]`, `balancesBefore`/`balancesAfter` are empty arrays, the loop at lines 132–151 never runs, `handleOut` is never called for the drained asset, and `runAction` returns an empty `UTXO[]` without reverting.

### Impact Explanation
This bypasses the sole on-chain solvency guard (`BalanceChangeShouldBePositive`) that protects other users' co-mingled funds held by the Emporium contract. An attacker can direct arbitrary `op.value`/`callData` at any `op.endpoint` using Emporium's real balance, with no post-condition check catching the resulting negative balance for the drained token/ETH. This is direct theft of shielded/co-mingled user funds held by Emporium — Critical severity, and repeatable per valid proof/`emporiumMessage` (each `emporiumMessage` can only be used once, but an attacker can generate new messages/proofs repeatedly as long as they can construct a valid Hinkal proof, which only requires their own UTXOs/leaves for the internal balance bookkeeping of the (empty) token list).

### Likelihood Explanation
Preconditions: attacker needs (1) ability to submit a valid Hinkal proof matching `tokenNumber=0` dimensions (should be feasible for the min/zero-token circuit variant referenced), (2) Emporium must hold drainable ETH/token balance from other users' deposits, (3) `stack.signerAddress=address(0)` (stateless path, no wallet signature needed) or a compromised/attacker-controlled wallet for the `invokeWallet` path. No privileged role is required — only an unprivileged prover/EOA that can call `transact`. The main uncertainty is whether the deployed verifier set actually includes a working zero-token-count circuit/verifier registered via `buildVerifierId`; this repo snapshot did not let me fully confirm the verifier registration table (`VerifierFacade.sol`), so this should be validated against the actual deployed verifier IDs before treating it as fully proven, though nothing in `dimensionsCheck` or `HinkalHelper` blocks `tokenNumber=0`.

### Recommendation
In `EmporiumUpgradeable.runAction`, do not gate the solvency check on `circomData.erc20TokenAddresses`. Either (a) require `dimensionsCheck`/the circuit to enforce `tokenNumber >= 1` and that `erc20TokenAddresses` includes every distinct `endpoint`/token address that can appear in `stack.ops` (cross-checked on-chain), or (b) independent of the declared token list, snapshot and diff Emporium's full relevant balance set (native ETH balance always, plus any token addresses referenced by `stack.ops`' `callData`/`endpoint`) before/after the `ops` loop and revert if any of them goes negative relative to `deltaAmountChanges`. The safer minimal fix is to require `erc20TokenAddresses.length > 0` whenever `externalActionId` targets Emporium, and to derive the token set to check directly from `stack.ops` rather than trusting the attacker-supplied `erc20TokenAddresses`.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, register Emporium as external action, whitelist Emporium as `_isAllowedRecipient`.
2. Fund Emporium with ETH (simulate co-mingled deposits from a victim, e.g., via a legitimate deposit flow or `vm.deal`).
3. Craft `CircomData` with `erc20TokenAddresses = []`, `amountChanges = []`, `slippageValues = []`, `onChainCreation = []`, `inputNullifiers = []`, matching `Dimensions{tokenNumber:0, nullifierAmount:0, outputAmount:0}`.
4. Encode `externalActionData.externalActionMetadata` as an `EmporiumStack` with `signerAddress = address(0)`, `ops = [{endpoint: attacker, invokeWallet:false, value: <Emporium ETH balance>, callData: ""}]`.
5. Generate a valid proof for this zero-token-dimension circuit variant (locally via snarkjs) satisfying `calldataHash`/`signedMessageHash` constraints.
6. Call `Hinkal.transact(a,b,c,dimensions,circomData)` from the attacker EOA.
7. Assert: `address(emporium).balance` before minus after equals the drained amount, attacker's ETH balance increased by that amount, and the transaction did **not** revert with `BalanceChangeShouldBePositive` — proving `balancesAfter[i]-balancesBefore[i]+...>=0` was never evaluated for ETH despite Emporium's balance having gone strictly down (violating the intended invariant for the token actually touched by `ops`).
