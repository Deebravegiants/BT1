### Title
Webhook shop-domain identity is trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the caller-supplied `shop-domain` header straight through to the app's handler as the trusted tenant identifier. Because the `shop` (and `topic`/`webhook_id`/`api_version`) header values are never part of the signed material, an attacker who can obtain one valid `(raw_body, hmac)` pair — e.g. by owning a shop that installs the app and thus receiving genuine, correctly-signed webhooks for their own store — can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header. The signature check still passes because it never covered that header, so the app is misled into processing attacker-controlled webhook content under a victim shop's identity.

### Finding Description
`HmacValidator.validate` computes and compares the HMAC only against `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be nothing but the raw HTTP body: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers with no cryptographic binding to the signature: [3](#0-2) 

`Registry.process` accepts the request once `HmacValidator.validate(request)` succeeds, and immediately forwards the unauthenticated `request.shop` value to the app's handler as the tenant identity: [4](#0-3) 

This is the exact bug class named in the rules: **"a field acted on but not covered by the HMAC."** The equality the gem implicitly claims to guarantee is:

```
shop the app trusts (WebhookMetadata#shop, used to route/attribute the webhook)
   ==
shop that actually produced/signed the body
```

But the code only proves:

```
HMAC-SHA256(client_secret, raw_body) == received_signature
```

which says nothing about which shop's header accompanied that body. Before the attacker's request: a genuine webhook for Shop A arrives with `(raw_body_A, hmac_A, shop-domain: A)` — all three consistent, signature valid. After the attacker's request: the attacker resends `(raw_body_A, hmac_A, shop-domain: B)` — the signature is still valid (it only checks `raw_body_A` against `hmac_A`), but the shop field the app receives is now `B`, a shop the attacker does not own or control.

### Impact Explanation
Any app built on this gem that uses the `shop` field from `WebhookMetadata` to key per-tenant state (order/inventory sync, GDPR/compliance webhook handling, billing, uninstall cleanup, etc.) can be made to apply attacker-supplied body content under a different, victim merchant's identity. This is a cross-tenant confusion/write primitive: data belonging to shop A can be injected/attributed to shop B purely by relabeling a header, without any knowledge of shop B's credentials or the app's `client_secret`. This matches the "cross-tenant access" Critical impact category, since the tenant boundary (`shop`) that downstream app logic relies on is not authenticated by this gem despite being exposed as if it were.

### Likelihood Explanation
Exploitation requires only that the attacker be able to trigger at least one legitimate webhook delivery for a shop they control (trivial — installing the app or performing any action that fires a subscribed webhook topic) and be able to POST arbitrary headers/body to the app's public webhook endpoint (also trivial, since webhook endpoints are unauthenticated HTTP endpoints by design). No access token, `client_secret`, or privileged account is needed. The only gating factor is whether a given host app's business logic actually trusts `WebhookMetadata#shop` for tenant-sensitive operations, which is the documented and expected usage pattern of this API.

### Recommendation
- Include the shop domain (and ideally topic/webhook id) in the signed material, or independently verify that the `shop-domain` header value corresponds to a shop with an active session/installation known to the app before trusting it.
- At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must be cross-checked against the app's session store (e.g., confirm an existing installed session exists for that shop) before being used for tenant-scoped operations.
- Consider having `Webhooks::Request#to_signable_string` incorporate the shop/topic headers if compatible with Shopify's signing scheme, or expose a method that flags shop-domain header trustworthiness relative to signature coverage.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers any subscribed webhook topic (e.g., `app/uninstalled` or `orders/create`), causing Shopify to deliver a legitimately signed webhook:
   - Headers: `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid_hmac>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`
   - Body: `raw_body` (attacker fully controls the content of orders they create in their own shop).
2. Attacker captures this `(raw_body, valid_hmac)` pair (trivially available to them since it's their own store's traffic).
3. Attacker replays a POST to the app's webhook endpoint with the same `raw_body` and `X-Shopify-Hmac-Sha256: <valid_hmac>`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Webhooks::Request.new` parses headers, `Utils::HmacValidator.validate(request)` succeeds because it only hashes `raw_body` against the secret [5](#0-4) .
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: attacker's parsed JSON, ...)` [6](#0-5) , causing the victim shop's tenant record to be updated with attacker-controlled data.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
