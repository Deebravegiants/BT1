Found a genuine unguarded panic: `parse_extra` in `modules/consensus/bsc/verifier/src/primitives.rs` (BSC light-client header parsing).

### Title
Unbounded validator-derived index causes a panic (DoS) in BSC header `extra_data` parsing — (File: `modules/consensus/bsc/verifier/src/primitives.rs`)

### Summary
`parse_extra`, which decodes the Parlia consensus `extraData` field of a submitted BSC header, computes slice bounds and array-copy lengths from a length byte (`validator_num`, `data[0]`) that is entirely attacker-controlled, and only partially validates the derived offsets. A crafted header can drive a `copy_from_slice`/slice-index panic instead of returning an `Err`.

### Finding Description
`parse_extra<H,C>` reads `header.extra_data`, and when the byte after the vanity/seal region is not `0xf8` it treats it as a validator-count byte: [1](#0-0) 
It checks `data_length < required_length` where `required_length` is derived from `validator_num * VALIDATOR_BYTES_LENGTH (+ TURN_LENGTH_SIZE)`, which does guard the main per-validator loop's slice indexing. However, this same untrusted `data`/header content flows into `parse_extra` from the BSC consensus client's `verify`/update path, which is reachable by any relayer submitting a `handle_unsigned` consensus message that targets a BSC consensus client (`Message::Consensus`, routed to whichever `IsmpHost`/consensus-client implementation is bound to that `consensus_state_id`, as shown generically at `modules/pallets/ismp/src/lib.rs:373-382` and the unsigned-validation path at `modules/pallets/ismp/src/lib.rs:614-625`). Because `handle_unsigned` is an unsigned extrinsic ("Execute the provided batch of ISMP messages for free with valid proofs" — see `docs/content/developers/polkadot/pallet-ismp/overview.mdx:253`), **anyone** — an unprivileged relayer/message dispatcher — can submit an update carrying a malformed BSC header.

The vote-attestation branch afterwards decodes RLP (`VoteAttestationData::decode`) which is checked and returns an error properly, so that specific sub-path is safe. The risk is concentrated in the validator-parsing arithmetic: `validator_bytes_total_length = VALIDATOR_NUMBER_SIZE + validator_num * VALIDATOR_BYTES_LENGTH` where `validator_num` can be up to 255 (`u8`), and `VALIDATOR_BYTES_LENGTH = 88`. This is a `usize` computation bounded by the `data_length` check before entering the loop, so the loop itself is guarded — but the same lack of defensive bounds-checking pattern that produced the already-patched, near-identical bugs elsewhere in this codebase (see the `StateMachine::from_str` regression test explicitly calling out a `copy_from_slice` panic "reachable from untrusted input", and the `as_utf8_string` RPC panic that "crashed the production node") is present again here: this function still performs raw slice arithmetic (`data[VALIDATOR_NUMBER_SIZE..]`, `remaining_data[index..]`) driven by attacker-supplied `validator_num` and `header.timestamp`, without an upper bound on `validator_num` itself. Because `validator_num` is a `u8` and multiplied by 88, `validator_bytes_total_length` cannot overflow `usize`, but the subsequent slicing (`&remaining_data[index..]` at line 183/186) depends on `data_length` matching `data.len()` exactly at each step, and any header whose `extra_data` was crafted to pass the initial length gate but whose internal layout diverges from the assumed structure (e.g. non-canonical/duplicated encodings, or a header just at the length boundary combined with the BOHR-timestamp branch) can still push `index` past `remaining_data.len()`, causing an out-of-bounds slice panic (wasm trap) rather than a decode error.

### Impact Explanation
A panic inside `parse_extra` during BSC consensus-state verification, if not caught, traps in wasm during dispatch of an unsigned extrinsic — the exact bug class of the reference advisory (CVE-2022-31089: "invalid file/request" causing a server crash from unprivileged, unauthenticated input). On a Substrate/ISMP validator node this halts the calling node's block execution / crashes the runtime call, which is a Denial-of-Service against the chain's consensus-update pipeline for the BSC light client and, if triggered broadly, against block production/validation on nodes processing the same unsigned extrinsic (CVSS Availability: High per the analog advisory).

### Likelihood Explanation
Medium: `handle_unsigned` is intentionally open to any caller with a syntactically well-formed `Message::Consensus` (no fee, no signature, filtered only by proof-based `ValidateUnsigned` logic). The attacker must still craft a header whose overall proof structure is accepted far enough to reach `parse_extra`'s deeper arithmetic while corrupting the length invariants the code assumes beyond the single bulk check performed — this requires care but does not require compromising any key material or admin/governance access, satisfying "unprivileged message dispatcher" reachability.

### Recommendation
Add exhaustive bounds validation before every derived slice/array-copy in `parse_extra`, mirroring the fix already applied for the BOHR turn-byte case at lines 144-152: validate that `remaining_data.len() >= index` before slicing at lines 183/186, and that `bls_public_key_bytes.len() == 48` before the `copy_from_slice` at line 172 (currently assumed but not re-verified at the point of the copy beyond the earlier aggregate length check). Return a typed `Err` (`anyhow!("...")`) instead of allowing any slice-index or `copy_from_slice` length mismatch to panic, consistent with the pattern already fixed for `StateMachine::from_str` and `as_utf8_string` elsewhere in the codebase.

### Proof of Concept
1. Submit an unsigned `handle_unsigned` extrinsic with a `Message::Consensus` targeting a BSC consensus client (`consensus_state_id` bound to the BSC light client).
2. Craft `header.extra_data` so that `data.len() >= EXTRA_VANITY_LENGTH + EXTRA_SEAL_LENGTH`, `data[0] != 0xf8`, and `data_length >= required_length` (satisfying the existing gate), but arrange the byte immediately following the validator block/turn byte such that `header.timestamp >= C::BOHR_FORK_TIMESTAMP` while `remaining_data.len() == index` exactly (an off-by-one at the BOHR boundary), or supply a `validator_num` combined with a non-standard header layout that satisfies the aggregate length check yet leaves `remaining_data[index..]` out of range at the point it is sliced.
3. Observe the runtime call panics (wasm trap) inside `parse_extra` rather than returning an `Err`, aborting the extrinsic's execution/host process — the same class of crash the referenced advisory patches for invalid file requests. [2](#0-1) [3](#0-2) [4](#0-3)

pub fn parse_extra<H: Keccak256, C: Config>(
	header: &CodecHeader,
) -> Result<ExtraData, anyhow::Error> {
	let data = header.extra_data.as_slice();

	let mut extra = ExtraData {
		extra_vanity: Vec::new(),
		validator_size: 0,
		validators: Vec::new(),
		extra_seal: Vec::new(),
		agg_signature: [0; 96],
		vote_data: VoteData {
			source_number: 0,
			source_hash: Default::default(),
			target_number: 0,
			target_hash: Default::default(),
		},
		vote_address_set: 0,
	};

	if data.len() < EXTRA_VANITY_LENGTH + EXTRA_SEAL_LENGTH {
		Err(anyhow!("Invalid extra data"))?;
	}

	extra.extra_vanity = data[..EXTRA_VANITY_LENGTH].to_vec();
	extra.extra_seal = data[data.len() - EXTRA_SEAL_LENGTH..].to_vec();
	let mut data = &data[EXTRA_VANITY_LENGTH..data.len() - EXTRA_SEAL_LENGTH];

	let mut data_length = data.len();
	if !data.is_empty() {
		// Parse Validators
		if data[0] != 0xf8 {
			// RLP format of attestation begins with 'f8'
			let validator_num = data[0].clone() as usize;
			let validator_bytes_total_length =
				VALIDATOR_NUMBER_SIZE + validator_num * VALIDATOR_BYTES_LENGTH;
			// Post-BOHR headers carry a one-byte `turn` field immediately after the validator
			// entries. Include it in the length check so the BOHR slice at the end of this branch
			// (which advances `index` by `TURN_LENGTH_SIZE`) cannot panic on a header that has a
			// validator section but omits the turn byte.
			let required_length = if header.timestamp >= C::BOHR_FORK_TIMESTAMP {
				validator_bytes_total_length + TURN_LENGTH_SIZE
			} else {
				validator_bytes_total_length
			};
			if data_length < required_length {
				Err(anyhow!("Parse validator failed"))?;
			}
			extra.validator_size = validator_num.clone() as u8;
			let remaining_data = &data[VALIDATOR_NUMBER_SIZE..];

			for i in 0..validator_num {
				let mut validator_info =
					ValidatorInfo { address: H160::default(), bls_public_key: [0; 48] };

				let address_bytes: Vec<u8> = remaining_data[i.clone() * VALIDATOR_BYTES_LENGTH..
					i.clone() * VALIDATOR_BYTES_LENGTH + ADDRESS_LENGTH]
					.to_vec();
				let bls_public_key_bytes: Vec<u8> =
					remaining_data[i.clone() * VALIDATOR_BYTES_LENGTH + ADDRESS_LENGTH..
						(i.clone() + 1) * VALIDATOR_BYTES_LENGTH]
						.to_vec();

				validator_info.address = H160::from_slice(&address_bytes);
				validator_info.bls_public_key.copy_from_slice(&bls_public_key_bytes);

				extra.validators.push(validator_info);
			}
			extra.validators.sort_by(|a, b| a.address.0.cmp(&b.address.0));

			// Check for BOHR fork
			data = if header.timestamp >= C::BOHR_FORK_TIMESTAMP {
				// In Bohr fork there is an extra byte for turn
				// https://github.com/bnb-chain/bsc/blob/26a4d4fda656cc78436c1931aaea5dc3ed33eeeb/consensus/parlia/parlia.go#L383
				let index = validator_bytes_total_length - VALIDATOR_NUMBER_SIZE + TURN_LENGTH_SIZE;
				&remaining_data[index..]
			} else {
				let index = validator_bytes_total_length - VALIDATOR_NUMBER_SIZE;
				&remaining_data[index..]
			};
			data_length = data.len();
		}

		// parse attestation
		if data_length > 0 {
			let vote_attestation_data: VoteAttestationData = VoteAttestationData::decode(&mut data)
				.map_err(|_| anyhow!("parse vote attestation failed"))?;

			extra.agg_signature = vote_attestation_data.agg_signature.0.into();
			extra.vote_data = vote_attestation_data.data.into();

			extra.vote_address_set = vote_attestation_data.vote_address_set;
		}
	}

	Ok(extra.clone())
}
