### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant shop-attribution spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while `#shop` is read directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) . `Registry.process` validates the HMAC against the body only, then passes `request.shop` straight into `WebhookMetadata` handed to the app's handler without any further check that the shop matches the body/signature [3](#0-2) .

### Finding Description
The binding that should hold is: `shop (used to attribute the webhook payload to a tenant) == shop bound by the HMAC signature`. In this gem it instead holds: `shop == arbitrary unauthenticated header value`, while the HMAC only certifies the byte-integrity of `raw_body` [4](#0-3) , computed with `verifiable_query.to_signable_string`, which for webhooks is exactly `@raw_body` and nothing else [1](#0-0) .

Compare this to the OAuth `AuthQuery`, where the analogous "identity" field `shop` IS included in `to_signable_string` and therefore is cryptographically bound to the HMAC: `code, host, shop, state, timestamp` are all url-encoded and signed [5](#0-4) . The webhook `Request` class breaks this same pattern: the `shop` field that downstream code trusts for tenant attribution is excluded from the signed data.

Because the shop-domain header is never part of the signable string, an attacker who can obtain one genuinely-HMAC-signed webhook body+signature pair for their own shop (trivial: install the app on a normal, unprivileged Shopify dev/trial store and trigger any webhook-eligible event) can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value naming a different, victim shop. `Utils::HmacValidator.validate` will still pass, because it only recomputes the HMAC over `raw_body` [6](#0-5) , and `Registry.process` will dispatch to the handler with `shop: request.shop` set to the victim's domain [3](#0-2) .

### Impact Explanation
This produces cross-tenant data confusion: application logic that keys off `WebhookMetadata#shop` (e.g., to look up which merchant's records to create/update/delete) will act on the wrong tenant's account using data that was never actually sent by Shopify for that tenant. Since host applications are expected to trust `Registry.process`'s HMAC validation as the authenticity guarantee for the webhook as a whole (including the shop identity, mirroring how `AuthQuery` binds `shop` into its signature), this is a cross-tenant access vulnerability rooted entirely in this gem's `Request`/`Registry` implementation, not a misuse of a documented gem contract.

### Likelihood Explanation
High: no privileged credentials, TLS interception, or leaked secrets are required. Any actor can register a free/trial Shopify store, install a target app, trigger a real webhook to capture one legitimate `(body, hmac)` pair for their own shop, and replay it with a forged shop-domain header to the app's publicly reachable webhook endpoint.

### Recommendation
Bind the shop (and topic/webhook-id, if used for attribution) into the signed material, or otherwise cryptographically tie the header-derived shop to the payload before exposing it via `WebhookMetadata`. At minimum, `Registry.process`/`Request` should not allow the caller to trust `request.shop` as authenticated unless it is verified against something the HMAC actually covers.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (no special privilege needed) and triggers a webhook-eligible action (e.g. `orders/create`). Their own server (or a captured relay) records the exact `raw_body` and the `X-Shopify-Hmac-Sha256` value Shopify sent, both valid under the app's `api_secret_key`.
2. Attacker POSTs the identical `raw_body` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and any topic still registered).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` only [7](#0-6)  — validation succeeds because the body/signature pair is unmodified.
4. The handler receives `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim-shop.myshopify.com"` [8](#0-7) , even though the payload actually originated from and describes `attacker-shop.myshopify.com`'s data — a cross-tenant identity binding break.
