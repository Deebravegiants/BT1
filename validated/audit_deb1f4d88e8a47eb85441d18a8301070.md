## Finding

### Title
Panic-Induced DoS via Unchecked Length Slicing of Attacker-Controlled `message.from` in `pallet-hyper-fungible-token` - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
The CVE-2025-8183 bug class is a remote, unauthenticated crash triggered by a malformed field in an inbound message that the receiving node fails to validate before dereferencing/indexing it. The same bug class exists in `pallet-hyper-fungible-token`'s `on_accept` handler: the ABI-decoded `message.from` field is sliced/copied with lengths assumed to be exactly 20 or 32 bytes, but no length check is performed before the operation, so a malicious `from` value of any other length causes an unconditional Rust panic while processing an unsigned, permissionless `handle_unsigned` extrinsic.

### Finding Description
`IsmpModule::on_accept` for the fungible token pallet decodes an ABI-encoded `Message { from, to, amount, data }` from the incoming `PostRequest.body`: [1](#0-0) 

When `message.data` is non-empty and no signature is supplied in the accompanying `SubstrateCalldata`, the code falls into the `else` branch that derives a dispatch origin directly from `message.from`: [2](#0-1) 

- If `source.is_evm()` is true, it computes `&from_bytes[from_bytes.len() - 20..]`. Since `from_bytes.len()` is a `usize` derived from attacker-controlled ABI bytes, if `from_bytes.len() < 20`, the subtraction underflows. In a release build this wraps to a huge index, producing an out-of-bounds slice panic; in a debug build the subtraction itself panics on overflow.
- If `source.is_evm()` is false, `account.copy_from_slice(from_bytes)` is called against a fixed `[0u8; 32]` buffer — `copy_from_slice` panics whenever `from_bytes.len() != 32`.

Contrast this with the length-checked pattern used just a few lines earlier for the `to`/recipient field, which explicitly validates length and returns a typed error instead of panicking: [3](#0-2) 

The same unchecked pattern is repeated in `on_timeout`'s length check for `from_bytes`, which *does* validate — showing the module.rs author was aware of the need to validate lengths elsewhere but missed it in the no-signature calldata-origin branch: [4](#0-3) 

The `message.from` field is a Solidity `bytes` type with no length constraint on the sending side, so any account able to call `send()`/dispatch a POST request through the paired HFT contract (an ordinary, unprivileged user) can set `from` to any byte length. On the receiving substrate chain, this request is delivered via `handle_unsigned`, which is explicitly designed to be callable by anyone, for free, as an unsigned extrinsic: [5](#0-4) 

Because `ValidateUnsigned::validate_unsigned` for `pallet-ismp` actually executes the message (`Self::execute(messages.clone())`) to determine transaction validity, the panic is hit during transaction-pool validation / block execution itself, not just at the final commit step: [6](#0-5) 

A panic inside `on_accept`, called from the ISMP message-handling pipeline invoked by `handle_unsigned`, unwinds through runtime/consensus code that is not designed to tolerate panics from application-level callbacks — this is the same class of remote-triggerable "malformed field → crash" issue described in the µD3TN advisory (CVE-2025-8183), where a non-singleton destination EID caused an unguarded null-pointer dereference during message dispatch.

### Impact Explanation
Any node (validator/collator) that processes an inbound HFT POST request with a crafted `message.from` (wrong length) while `message.data` is non-empty and unsigned will panic during extrinsic validation/execution. Since `handle_unsigned` extrinsics are gossiped/validated by every full node in the network before block inclusion, and the panic occurs deterministically for a given malformed message, this is a reliable, remotely triggerable denial-of-service against nodes running `pallet-hyper-fungible-token` — capable of halting block production or crashing collators processing the message, mirroring the "High" severity DoS class of CVE-2025-8183.

### Likelihood Explanation
Likelihood is high: the attacker only needs to call the ordinary `send()` function on the paired EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contract (any unprivileged user can do this) with a `Message.from` value that is neither 20 nor 32 bytes and non-empty `data`, and no signature in the substrate calldata payload. No governance, admin, or consensus-manipulation access is required — only a standard cross-chain token send with a malformed sender field, i.e., exactly the "single relayed message from an unprivileged path" pattern this scan targets.

### Recommendation
Add explicit length validation for `message.from` in the no-signature branch of `on_accept`, mirroring the checked pattern already used for `to` (lines 61-71) and in `on_timeout` (lines 224-232), returning a typed `HftError` (e.g. `InvalidSenderLength`) instead of panicking when the length is not exactly 20 (EVM) or 32 (substrate) bytes.

### Proof of Concept
1. On the EVM chain, call `HyperFungibleToken.send(SendParams{ dest: <substrate-chain>, to: <beneficiary>, amount: X, data: abi.encode(SubstrateCalldata{ signature: None, runtime_call: <any allowed call> }), ... })` where the outgoing wire `Message.from` (populated by the contract from `msg.sender`/from field with attacker-controlled override where applicable) is crafted/replaced to a length other than 20 bytes (e.g., 5 bytes) — or directly craft the raw ISMP `PostRequest.body` bytes off-chain to encode `Message{ from: <5 bytes>, to: <32 bytes>, amount, data: <non-empty SubstrateCalldata with signature=None> }`.
2. Submit this as an unsigned `Ismp::handle_unsigned` extrinsic (as any relayer/attacker may, since it's callable by anyone) carrying the crafted `RequestMessage`.
3. During `validate_unsigned`/`execute`, the router dispatches to `pallet_hyper_fungible_token::on_accept`, which reaches `&from_bytes[from_bytes.len() - 20..]` with `from_bytes.len() == 5`, causing an arithmetic-underflow/out-of-bounds-slice panic that crashes the executing node process.
