Webhook `shop-domain` header is trusted for tenant identification but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, but the `shop` value handed to the app's webhook handler for tenant identification is read from an HTTP header that is completely outside the HMAC's coverage. An attacker who possesses one validly-signed webhook body/HMAC pair (trivially obtainable by installing the app on an attacker-controlled development store and triggering a webhook) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value. The request passes HMAC validation, and the handler receives attacker-chosen `shop` metadata bound to genuine, signature-verified `body` bytes — breaking the equality `shop_bound_by_hmac == shop_used_for_tenant_routing`.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes and compares the signature against `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as only `@raw_body`: [2](#0-1) 

But the `shop` accessor used downstream for tenant identification is pulled straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never part of `to_signable_string` and therefore never covered by the HMAC: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately forwards `request.shop` (the unauthenticated header value) into `WebhookMetadata`, which is passed to the app's handler as the authoritative tenant identifier: [4](#0-3) 

`WebhookMetadata.shop` is documented and consumed by host apps as "The shop domain of the webhook" for routing/attribution of the payload: [5](#0-4) [6](#0-5) 

Before/after comparison of the identity binding:
- **Before (intended invariant):** the `shop` value delivered to the handler should be cryptographically bound to the same request that Shopify signed, i.e. `HMAC-verified(shop, body) == true` before trusting `shop` for tenant routing.
- **After (actual behavior):** `HMAC-verified(body) == true` says nothing about `shop`; `shop` is taken from an arbitrary, attacker-controllable header on any request whose raw body happens to match one that was legitimately signed.

Root cause: `to_signable_string` (line 37 of `request.rb`) omits the `shop-domain` header from the signed material, while `Registry.process` (line 190, `registry.rb`) trusts `request.shop` (header, line 21-23 of `request.rb`) as though it were authenticated.

### Impact Explanation
This is a cross-tenant identity-confusion vector: an unprivileged internet user can obtain one legitimately signed `(raw_body, hmac)` pair for their own (attacker-controlled) shop — e.g. by installing the target app on a free development store and triggering any webhook topic — and then replay that exact body and HMAC to the target app's public webhook endpoint while spoofing the `shop-domain` header to a victim merchant's domain. Any host application that follows this gem's own documented contract (treat `data.shop` as the shop the webhook is for, e.g. to key job queues, look up per-shop sessions/access tokens, or write to per-tenant storage as shown in the gem's own `docs/usage/webhooks.md` example `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) will process attacker-supplied body content under the identity of a shop the attacker does not control. This can lead to cross-tenant data injection/corruption or misattributed processing without requiring the app's `client_secret`, an access token, or any privileged credential — matching the Critical "cross-tenant access" impact category via a broken shop/HMAC binding, analogous to the unbound Transceiver-instruction ordering in the source report where a field acted upon downstream was never validated at the point of trust establishment.

### Likelihood Explanation
Likelihood is high: no credentials are required beyond the ability to install the target app on any store (including a free development store) to harvest one valid `(body, hmac)` pair, and HTTP headers are trivially forged by any client sending requests to the app's public webhook URL. The gem provides no warning or mechanism binding `shop` to the signature, and its own documentation instructs developers to trust `data.shop` directly.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-covered signable string for webhook requests, or otherwise independently verify that the `shop-domain` header corresponds to the shop associated with the signed payload (e.g., have `to_signable_string` incorporate the normalized `shop`, `topic`, and `webhook-id` headers alongside the raw body, matching what is actually delivered by Shopify's signing scheme) before exposing `request.shop` to `WebhookMetadata`. At minimum, document prominently that `data.shop` in `WebhookMetadata` is not cryptographically authenticated and must not be used for tenant-sensitive lookups without additional verification (e.g., cross-checking against a shop domain obtained through an authenticated session).

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com` and capture a real webhook delivery for any subscribed topic, noting the exact `raw_body`, `x-shopify-hmac-sha256`, and other headers Shopify sent.
2. Replay an HTTP POST to the app's webhook endpoint using the identical `raw_body` and `x-shopify-hmac-sha256` value, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. Server-side, `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` is constructed and passed to `ShopifyAPI::Webhooks::Registry.process`:
   ```ruby
   ShopifyAPI::Webhooks::Registry.process(
     ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
   )
   ```
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks `raw_body` against the HMAC [7](#0-6) .
5. The app's registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's original body>, ...)` — attacker-controlled body content is now attributed to the victim shop, even though the victim never sent this webhook and the attacker never possessed the victim's credentials.
