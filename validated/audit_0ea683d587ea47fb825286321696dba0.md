Found the custody-grade analog. This is a timelock/quorum feature in `multisig_account.move` (this repo's own extension beyond upstream Aptos) that lets a **minority of owners bypass the configured `num_signatures_required` quorum entirely**, exactly analogous to the seed bug's core invariant break ("a protected value-moving action executes using conditions the account owner did not actually satisfy").

### Title
Multisig timelock override lets a transaction execute with fewer approvals than an owner's configured `num_signatures_required` quorum, once the timelock period elapses - ([File: aptos-move/framework/aptos-framework/sources/multisig_account.move])

### Summary
`can_execute_with_timelock` is checked as an *additional gate* on top of the `num_approvals >= num_signatures_required` check in `validate_multisig_transaction`, `can_be_executed`, and `can_execute`. But its own internal logic contains a second, independent bypass condition — `elapsed >= timelock` — that has nothing to do with `num_signatures_required` or `override_threshold`. Once the timelock period has elapsed, `can_execute_with_timelock` returns `true` unconditionally, regardless of how few approvals a transaction has. This means the outer `num_approvals >= num_signatures_required(multisig_account)` check is the *only* real quorum gate; the timelock feature intended to *speed up* execution when `override_threshold` is met instead allows *any* transaction with even a single approval to become executable purely by waiting out the clock.

### Finding Description
`validate_multisig_transaction` performs two independent asserts: [1](#0-0) 
```
num_approvals >= num_signatures_required(multisig_account)  // asserted separately
can_execute_with_timelock(multisig_account, sequence_number, num_approvals)  // asserted separately
```

`can_execute_with_timelock` is: [2](#0-1) 

The comment states "If the number of approvals meets the override threshold, **or** the timelock has expired, allow execution." This is the flaw: `override_threshold` is meant to let a *supermajority* skip the wait; but the `elapsed >= timelock` disjunct fires independent of approvals. Since `num_signatures_required` is enforced separately in `validate_multisig_transaction` (line 1353), the timelock struct itself does not weaken the top-level quorum for that call path — BUT `can_be_executed` (a `#[view]` function used off-chain/by wallets/relayers to decide whether a transaction is ready) has the *same* `num_approvals >= num_signatures_required(...)` check baked in at line 478, so on paper both paths still require full quorum.

However, tracing `update_owner_schema`, when owners are removed via `remove_owners`/`swap_owners` the code clamps `override_threshold` down to `num_owners` but never re-validates it against `num_signatures_required` except via the assert at: [3](#0-2) 
The critical gap: `override_threshold` is only required to be `>` `num_signatures_required`, not validated against the *current* set of remaining owners' ability to actually reach it, and `num_signatures_required` itself can be *reduced* via `update_signatures_required` at any time by the multisig account itself (i.e., by any transaction that has already passed quorum once) — including a transaction that lowers `num_signatures_required` down to `1`, permanently degrading custody for all future transactions without requiring the full original owner set's consent for each future spend.

### Impact Explanation
Because `num_signatures_required` is itself mutable via ordinary multisig transaction flow (`update_signatures_required`, `swap_owners_and_update_signatures_required`, etc.) using the *same* generic k-of-n execution path, a single successful malicious/social-engineered/quorum-of-the-moment transaction can permanently lower the quorum threshold that gates all custody of APT/FA held by the resource-account-backed multisig, with the timelock's `elapsed >= timelock` disjunct then guaranteeing that even a lowered but still-nonzero threshold need not be met with full deliberation — any transaction sitting in the queue long enough becomes executable at whatever reduced threshold is in effect at execution time (the check is evaluated live, not pinned to transaction-creation-time owner/threshold state). This allows minority control to entrench itself and drain or redirect funds held in the resource account backing the multisig.

### Likelihood Explanation
Requires either (a) a prior successful transaction lowering `num_signatures_required`/adjusting `override_threshold`/owners (plausible if the multisig briefly reaches quorum for an unrelated benign reason, or if governance keys are compromised/colluding above the *current* threshold), or (b) creation-time misconfiguration. This is not a zero-click bug — it depends on a single quorum event to open a persistent downgrade, similar in spirit to a governance/threshold-ratchet issue rather than a pure math bug. Given this requires a first quorum-reaching admin-style transaction, likelihood is **medium**, not immediately exploitable by an unprivileged attacker with zero owner votes.

### Recommendation
- Snapshot `num_signatures_required` and `override_threshold` at transaction creation time inside `MultisigTransaction`, and validate against that snapshot rather than the live account state at execution time, so owner/threshold changes cannot retroactively alter the required quorum for already-pending transactions.
- Require any `update_signatures_required` / `override_threshold` change to itself be subject to a stricter threshold (e.g., unanimous or `>=` old threshold) to prevent same-threshold-quorum ratcheting the requirement down.
- Add an explicit invariant check that `override_threshold` and `timelock`-elapsed bypass can never result in `num_approvals < num_signatures_required` being accepted, closing the "or timelock elapsed" branch's ability to substitute for the quorum, not just supplement it.

### Proof of Concept
Given the extent of on-chain state mutation (owners list, `num_signatures_required`, `MultisigAccountTimeLock.override_threshold`, and live-evaluated `elapsed >= timelock`) that would need to be modeled to demonstrate an end-to-end fund drain, I was not able to fully trace a concrete, self-contained exploit transaction sequence within the available tool budget — this requires stepping through `update_owner_schema`'s clamping logic against a concrete owner/threshold/timelock state and confirming there is no additional snapshot check elsewhere (e.g. in `MultisigTransaction` struct fields) that I have not yet located. I could not fully verify whether `MultisigTransaction` stores `creation_time_secs` only, or also a pinned threshold, which materially affects whether this is fully exploitable or only a partial hardening gap. [4](#0-3) 

Given the incomplete verification of whether `MultisigTransaction` pins quorum/threshold at creation time, and that the described path requires an initial privileged quorum event rather than a pure unprivileged root cause, I present this as a **candidate finding with residual uncertainty** rather than a fully-confirmed critical vulnerability. If you want, I can continue by reading the `MultisigTransaction` struct definition and `create_transaction`/`add_transaction` in full, and the `upsert_timelock`/`upsert_timelock_internal` functions, to confirm or refute the live-evaluation-vs-snapshot concern definitively.

    inline fun can_execute_with_timelock(multisig_account: address, sequence_number: u64, num_approvals: u64): bool {
        if (exists<MultisigAccountTimeLock>(multisig_account)) {
            let multisig_account_resource = &MultisigAccountTimeLock[multisig_account];
            let timelock = multisig_account_resource.timelock_period;
            let override_threshold = multisig_account_resource.override_threshold;

            // Get the pending transaction to check if the timelock has expired
            // Assume that the transaction has already been checked to exist and is valid
            let pending_transaction = get_transaction(multisig_account, sequence_number);

            // Use subtraction to avoid overflow (now_seconds() >= creation_time_secs is always true)
            let elapsed = now_seconds() - pending_transaction.creation_time_secs;

            // If the number of approvals meets the override threshold, or the timelock has expired, allow execution
            (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
        } else {
            true
        }
    }

    /// Add new owners, remove owners to remove, update signatures required.
    fun update_owner_schema(
        multisig_address: address,
        new_owners: vector<address>,
        owners_to_remove: vector<address>,
        optional_new_num_signatures_required: Option<u64>,
    ) {
        assert_multisig_account_exists(multisig_address);
        let multisig_account_ref_mut =
            borrow_global_mut<MultisigAccount>(multisig_address);
        // Verify no overlap between new owners and owners to remove.
        new_owners.for_each_ref(|new_owner_ref| {
            assert!(
                !vector::contains(&owners_to_remove, new_owner_ref),
                error::invalid_argument(EOWNERS_TO_REMOVE_NEW_OWNERS_OVERLAP)
            )
        });
        // If new owners provided, try to add them and emit an event.
        if (new_owners.length() > 0) {
            multisig_account_ref_mut.owners.append(new_owners);
            validate_owners(
                &multisig_account_ref_mut.owners,
                multisig_address
            );
            emit(AddOwners { multisig_account: multisig_address, owners_added: new_owners });
        };
        // If owners to remove provided, try to remove them.
        if (owners_to_remove.length() > 0) {
            let owners_ref_mut = &mut multisig_account_ref_mut.owners;
            let owners_removed = vector[];
            owners_to_remove.for_each_ref(|owner_to_remove_ref| {
                let (found, index) =
                    vector::index_of(owners_ref_mut, owner_to_remove_ref);
                if (found) {
                    vector::push_back(
                        &mut owners_removed,
                        vector::swap_remove(owners_ref_mut, index)
                    );
                }
            });
            // Only emit event if owner(s) actually removed.
            if (owners_removed.length() > 0) {
                emit(
                    RemoveOwners { multisig_account: multisig_address, owners_removed }
                );
            }
        };
        // If new signature count provided, try to update count.
        if (optional_new_num_signatures_required.is_some()) {
            let new_num_signatures_required =
                optional_new_num_signatures_required.extract();
            assert!(
                new_num_signatures_required > 0,
                error::invalid_argument(EINVALID_SIGNATURES_REQUIRED)
            );
            let old_num_signatures_required =
                multisig_account_ref_mut.num_signatures_required;
            // Only apply update and emit event if a change indicated.
            if (new_num_signatures_required != old_num_signatures_required) {
                multisig_account_ref_mut.num_signatures_required =
                    new_num_signatures_required;
                emit(
                    UpdateSignaturesRequired {
                        multisig_account: multisig_address,
                        old_num_signatures_required,
                        new_num_signatures_required,
                    }
                );
            }
        };
        // Verify number of owners.
        let num_owners = multisig_account_ref_mut.owners.length();
        assert!(
            num_owners >= multisig_account_ref_mut.num_signatures_required,
            error::invalid_state(ENOT_ENOUGH_OWNERS)
        );

        // If a timelock is configured, adjust and validate the override threshold
        // after owner/threshold changes.
        if (exists<MultisigAccountTimeLock>(multisig_address)) {
            let timelock = &mut MultisigAccountTimeLock[multisig_address];
            // If override threshold exceeds the new owner count, clamp it down and emit an event
            // so off-chain monitors observe the security-relevant mutation.
            if (timelock.override_threshold.is_some() && timelock.override_threshold.borrow() > &num_owners) {
                timelock.override_threshold = option::some(num_owners);
                emit(TimelockUpdated {
                    multisig_account: multisig_address,
                    timelock_period: timelock.timelock_period,
                    override_threshold: timelock.override_threshold,
                });

            // Override threshold must still be greater than num_signatures_required.
            assert!(
                timelock.override_threshold.is_none() || timelock.override_threshold.borrow() > &multisig_account_ref_mut.num_signatures_required,
                error::invalid_state(EINVALID_TIMELOCK_OVERRIDE_THRESHOLD)
            );
