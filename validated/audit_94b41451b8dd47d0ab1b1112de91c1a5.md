### Title
Batch withdrawals with duplicate `assetId` cause `describeWithdrawal()` to misreport withdrawal status/txHash across indices, defeating per-withdrawal amount tracking - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal()` calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which matches purely on `assetId` (via `near_token_id`) with no discriminator for `amount`, `destinationAddress`, or withdrawal index. When `sdk.createWithdrawalCompletionPromises()`/`waitForWithdrawalCompletion()` polls per-index for a batch that contains two withdrawals of the same `assetId` (e.g., same-asset different-amount refund + payout to the same or different address), both indices resolve against the *same* first matching record from `Array.prototype.find`, so `promises[i]` and `promises[j]` can both report the other withdrawal's `status`/`txHash`.

### Finding Description
The broken equality: for withdrawal index `i` with amount `amount_i`, the resolved `(status, txHash)` must correspond to the API's status record whose `data.amount` equals `amount_i` (and ideally whose position in the response corresponds to index `i`). Instead, `findMatchingWithdrawal` only checks `` `nep141:${w.data.near_token_id}` === assetId ``: [1](#0-0) 

`describeWithdrawal()` uses this to resolve status per call, and the caller comment even documents the limitation: [2](#0-1) 

Code path: `sdk.ts#createWithdrawalCompletionPromises` builds one promise per input index via `createWithdrawalIdentifiers` (which assigns a running `index` per bridge route, but that index is never used for matching) and calls `watchWithdrawal` for each: [3](#0-2) [4](#0-3) 

`watchWithdrawal` calls `bridge.describeWithdrawal({...args.wid, ...})` per index, but `describeWithdrawal` discards `args.index` for matching purposes and only uses `args.withdrawalParams.assetId`: [5](#0-4) 

Attacker input: an ordinary user submits `withdrawalParams = [{assetId: X, amount: 100}, {assetId: X, amount: 200}]` (same `assetId`, possibly same or different `destinationAddress`) in one `processWithdrawal`/`signAndSendWithdrawalIntent` call, producing a single `MultiPayload` with two `nep141` withdraw intents. Once the intent settles and both withdrawals execute, the PoA indexer's `getWithdrawalStatus` response contains two records for the same `near_token_id` with different `amount`/`transfer_tx_hash` values. When `describeWithdrawal` is invoked twice (once per index, both carrying the same `assetId`), `withdrawals.find(...)` returns the **same first-matching record** both times, so both promises can resolve `completed` with the same `txHash`, or one resolves with the wrong counterpart's `txHash`/status entirely, independent of which `amount_i` the index actually represents.

Existing guards do not prevent this: `validateWithdrawal` in the PoA bridge validates address/amount thresholds per single withdrawal and does not check for duplicate `assetId` across a batch; `supports()` ordering and `FeeExceedsAmountError` are unrelated to result matching; there is no `WithdrawalIdentifier.index`-based or amount-based disambiguation anywhere in `findMatchingWithdrawal` (confirmed identically in both `poa-bridge.ts` and `internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`, both carrying the same explicit code comment acknowledging the limitation).

### Impact Explanation
An integrator relying on `promises[i]` (or the return array of `waitForWithdrawalCompletion`) to represent withdrawal `i`'s specific outcome can receive a `txHash`/`status` that actually belongs to a different withdrawal amount in the same batch. This is a status/hash misreport that can cause an integrator to mark a smaller withdrawal "completed" using a larger withdrawal's `txHash` (or vice versa), leading to double-credit or double-refund bookkeeping decisions never authorized by the on-chain execution mapping. This matches the **High** severity category: "a status or hash misreport making an integrator credit or refund twice." It is repeatable on every batch call containing two-or-more same-`assetId` withdrawals.

### Likelihood Explanation
Preconditions: PoA-bridge-routed batch withdrawal (multiple `nep141:` withdraw intents in one signed payload) where two or more entries share the same `assetId`. This requires no privileged access — any ordinary user calling `processWithdrawal`/`signAndSendWithdrawalIntent`/`createWithdrawalCompletionPromises` with attacker-controlled `withdrawalParams` array can trigger it. Feasibility is high: it only requires constructing a batch with duplicate `assetId` entries, something the SDK's public API and documented "Batch Withdrawals" feature explicitly allow, with no validation rejecting duplicate assets. Cost to the attacker is a single normal batch withdrawal transaction fee.

### Recommendation
Disambiguate `findMatchingWithdrawal` beyond `assetId`: incorporate `amount` (and `destinationAddress`/`near_token_id`) matching, or (as the code's own comment suggests) sort both the withdrawal-params list and the API's `withdrawals` list per-`assetId` group by amount and match by relative position, removing matched entries from the candidate pool so the same record cannot satisfy two different indices in one batch. Additionally, consider rejecting/warning on batches with duplicate `assetId` entries until index-safe matching is implemented, or require the indexer to return withdrawal-level identifiers (e.g., NEAR intent output index) so batch entries can be matched deterministically.

### Proof of Concept
Vitest test in `poa-bridge.test.ts` / `sdk.createWithdrawalCompletionPromises.test.ts` style:
1. Mock `poaBridge.httpClient.getWithdrawalStatus` to return a single `COMPLETED` withdrawal record for `assetId = "nep141:btc.omft.near"` with `amount: 100000`, `transfer_tx_hash: "btc-tx-hash"`.
2. Call `bridge.describeWithdrawal` twice: once with `withdrawalParams.amount = 100000n` (index 0) and once with `withdrawalParams.amount = 200000n` (index 1), same `assetId`/`destinationAddress` and same `tx`.
3. Assert both calls return `{ status: "completed", txHash: "btc-tx-hash" }` — i.e., assert `result0.txHash === result1.txHash` despite `withdrawalParams[0].amount !== withdrawalParams[1].amount`, proving no per-amount equality check exists between the requested amount and the matched record's `data.amount`.
4. Equivalently at the SDK layer: call `sdk.createWithdrawalCompletionPromises({ withdrawalParams: [{...assetId, amount:100n}, {...assetId, amount:200n}], intentTx })` with `mockBridge.describeWithdrawal` resolving the same single record for both index calls, and assert `await promises[0]` and `await promises[1]` both equal `{ hash: "btc-tx-hash" }`.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
