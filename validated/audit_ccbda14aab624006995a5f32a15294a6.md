### Title
CallDispatcher.dispatch() is unrestricted, letting anyone drain funds it transiently or residually custodies from bridge/intent flows - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher.dispatch()` executes an attacker-controllable list of arbitrary `(to, value, data)` calls "as itself," with **no caller restriction whatsoever**. This mirrors the UnistreetLaunchpad root cause: a privileged, asset-custodying contract permissionlessly forwards externally-supplied calldata and executes it with its own identity, so anyone can command it to move out any assets it happens to hold. Hyperbridge's cross-chain token-bridge (`HyperFungibleToken`/`WrappedHyperFungibleToken`) and Intent Gateway (`IntentGatewayV2`/`IntentsBase`) apps are explicitly designed to route real bridged/escrowed user funds *through* this same `CallDispatcher` instance before/while executing swap-style calldata, so it is not merely a stateless utility — it is a shared, momentarily/residually funded custodian, exactly like the factory-owned V4 positions in the external report.

### Finding Description
`CallDispatcher.dispatch(bytes memory encoded)` is `external` with no modifier, ownership check, or allow-list of callers: [1](#0-0) 

Any address can call it directly (it is a standalone, separately deployed contract at a known address — see `evm/script/DeployHFT.s.sol`, `DeployWrappedHFT.s.sol`, `DeployIntentGateway.s.sol`, `evm/tron/migrations/2_deploy_ismp.js`) with an arbitrary ABI-encoded `Call[]`, and it will execute each entry with `to.call{value: call.value}(call.data)` using its own balance and identity — including plain `IERC20.transfer` pushes, which need no prior approval at all. [2](#0-1) 

Both `HyperFungibleToken`/`WrappedHyperFungibleToken` and `IntentGatewayV2`/`ExtrinsicIntents` are documented and implemented to route real, valuable bridged/escrowed tokens *into* this same dispatcher before executing user-supplied calldata:

- Token bridge "transfer-and-swap": destination-chain tokens are minted/unlocked directly to the `CallDispatcher` address, then the message's `data` (an attacker/user-controlled `Call[]`) is executed by it: [3](#0-2) [4](#0-3) 

- Intent Gateway predispatch: input assets are transferred to the dispatcher, arbitrary calldata is executed, and only the *balance* of the dispatcher is swept back afterward: [5](#0-4) 

- Intent Gateway postdispatch also leaves the dispatcher briefly holding output funds before sweeping dust: [6](#0-5) 

Critically, `HyperFungibleToken.onAccept`/`WrappedHyperFungibleToken.onAccept` mint/unlock tokens to the dispatcher and invoke `dispatch(message.data)` with **no subsequent sweep step** at all: [7](#0-6) 

The docs themselves acknowledge that the dispatcher can be left holding real balances after execution ("the dispatcher contract holds tokens temporarily during execution"), but the only mitigation offered is advising integrators to use exact-amount approvals to third-party routers — nothing stops an unrelated third party from calling `dispatch()` directly: [8](#0-7) 

Because `dispatch()` has no `onlyHost`/`onlyApp`/`msg.sender` restriction, any leftover balance — dust from an incomplete swap, a partially consumed cross-chain calldata sequence, or tokens mistakenly delivered to that well-known address — is directly drainable by any unprivileged caller via a plain `Call({to: token, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, balance)})`, requiring no approval, no proof, and no relaying: exactly the same "permissionless forwarding of attacker calldata executed as the custodian's own identity" root cause as the Unistreet `launch()`/`multicall` bug, just via a directly callable function instead of a wrapped `launch()`.

### Impact Explanation
Any token balance the `CallDispatcher` holds — whether from the documented mint/unlock-to-dispatcher swap pattern, from predispatch/postdispatch escrow routing in `IntentGatewayV2`, or from operator/integrator error — is a public, permanent bounty for any attacker who calls `dispatch()` first. Since this contract is shared across the HFT/WrappedHFT bridge and the Intent Gateway on a given chain (deployed once, address referenced by `configure()`/`setParams()` in multiple apps), the blast radius spans concrete theft of user bridge and intent funds, satisfying the "concrete theft of funds" bar.

### Likelihood Explanation
High: the attack requires only a single, unprivileged transaction calling the public `dispatch()` function once residue exists — no signature, no proof, no governance, no admin compromise. Any imperfect Call[] consumption (slippage, partial swaps, staking flows that don't forward 100% of proceeds, or accidental direct transfers to the well-known dispatcher address) creates an exploitable window, and integrators are explicitly told this residue can occur.

### Recommendation
Restrict `CallDispatcher.dispatch()` to a caller allow-list (e.g., an `onlyAuthorizedCaller` modifier configured per deploying app, or make each app deploy/own its own dispatcher and gate calls to `msg.sender == owner`). Additionally, ensure every app that routes funds through the dispatcher (`HyperFungibleToken`, `WrappedHyperFungibleToken`) sweeps any residual balance back to a safe recipient at the end of `onAccept`, matching the sweep-and-dust-collect pattern already used in `IntentsBase._execute`.

### Proof of Concept
1. On any chain, note the publicly known `CallDispatcher` address (published on the contract-addresses page and reused by `configure()`/`setParams()` across HFT/WrappedHFT/IntentGatewayV2 deployments).
2. Wait for (or trigger via normal usage) any legitimate cross-chain "transfer-and-swap" `HyperFungibleToken`/`WrappedHyperFungibleToken` message whose `Call[]` leaves any dust (e.g., an exact-output swap, or any partial failure that does not fully drain the minted/unlocked balance) — per `HyperFungibleToken.onAccept`, there is no post-dispatch sweep, so this balance persists indefinitely. [7](#0-6) 
3. Call `CallDispatcher.dispatch(abi.encode([Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, IERC20(token).balanceOf(dispatcher))})]))` directly — no approval, no privilege required, per the unrestricted `dispatch` implementation. [1](#0-0) 
4. The dust/residual balance is transferred to the attacker.

```text
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```

```text
## Calldata Execution

Both contracts support optional calldata execution on the destination chain via the `CallDispatcher`. By passing a non-empty `data` field in `SendParams`, the sender can trigger arbitrary contract calls on the destination chain immediately after tokens are minted or unlocked. This enables composable cross-chain workflows like transfer-and-swap (e.g., bridge USDC then swap to WETH via UniswapV2), transfer-and-stake, or transfer-and-deposit into a lending protocol — all in a single cross-chain operation.

The `data` field is an ABI-encoded `Call[]` array, where each `Call` specifies a target contract, a native value to forward, and the calldata to execute. On the destination chain, the HFT contract mints or unlocks tokens to the `to` address, then forwards the entire `data` payload to the `CallDispatcher`, which executes each call sequentially. If the calls need to spend the bridged tokens (e.g., approve then swap), set `to` to the `CallDispatcher` address so tokens are delivered directly to it.

For code examples, see the [HyperFungibleToken](/developers/evm/hyper-fungible-token/hyper-fungible-token#calldata-execution) and [WrappedHyperFungibleToken](/developers/evm/hyper-fungible-token/wrapped-hyper-fungible-token#calldata-execution) pages.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
```

```text
    /**
     * @dev Executes arbitrary calldata attached to an order's output via the CallDispatcher.
     * After dispatching the calls, any residual token balances left on the dispatcher
     * are swept back to this contract and accounted for as protocol dust.
     *
     * This enables composable order fulfillment — solvers can route through DEXes,
     * lending protocols, or other DeFi primitives as part of filling an order.
     *
     * @param order The order containing the output calldata to execute.
     * @param outputsLen The number of output assets to sweep after execution.
     */
    function _execute(Order calldata order, uint256 outputsLen) internal {
        if (order.output.call.length == 0) return;

        address dispatcher = _params.dispatcher;
        ICallDispatcher(dispatcher).dispatch(order.output.call);

        Call[] memory sweepCalls = new Call[](outputsLen);
        uint256 sweepCount = 0;

        for (uint256 i; i < outputsLen;) {
            address token = address(uint160(uint256(order.output.assets[i].token)));

            if (token == address(0)) {
                uint256 balance = dispatcher.balance;
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({to: address(this), value: balance, data: ""});
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            } else {
                uint256 balance = IERC20(token).balanceOf(dispatcher);
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({
                        to: token,
                        value: 0,
                        data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
                    });
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            }

            unchecked {
                ++i;
            }
        }
```
