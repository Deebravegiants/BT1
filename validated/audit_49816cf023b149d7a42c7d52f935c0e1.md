### Title
Interest accrual overflows and permanently bricks a near-limit market - (File: common/src/rates/index.rs)

### Summary
`update_supply_index` calculates `supplied * supply_index` before distributing newly accrued supplier rewards. Once a market’s scaled supply approaches `i128::MAX` and the supply index rises above `RAY`, that multiplication cannot be represented, causing every subsequent market operation to revert during mandatory accrual.

### Finding Description
All market mutations execute `global_sync` before changing market state, and `global_sync` calls `accrue_step` for each elapsed interval. [1](#0-0) 

During accrual, `update_supply_index` evaluates the total supplied value as `supplied.mul(env, old_index)` before adding `rewards_increase`. [2](#0-1) 

Although the fixed-point helper widens the intermediate product to `I256`, it panics with `MathOverflow` when the resulting quotient cannot fit in `i128`. [3](#0-2) 

A market can legally reach this state because deposits are converted into RAY-scaled supply using token amounts up to approximately `i128::MAX / 10^(27-decimals)`, while the resulting share total is only checked against `i128::MAX`, not against the smaller bound needed for multiplication by an index above `RAY`. [4](#0-3) 

Once the supply index rises even one raw unit above `RAY` while `supplied` is sufficiently close to `i128::MAX`, the next accrual panics before `last_timestamp` or any balances can be updated. [5](#0-4) 

### Impact Explanation
The affected market becomes permanently unable to process supply, withdrawal, repayment, borrowing, liquidation, flash loans, revenue claims, or recapitalization because those paths all perform interest accrual before their state transition. [6](#0-5) 

This permanently freezes supplier collateral and prevents borrowers from repaying or liquidators from resolving positions, satisfying the permanent-freezing and contract-unable-to-operate impact criteria. [7](#0-6) 

### Likelihood Explanation
An unprivileged user can reach the condition in a market whose configured supply and borrow caps admit near-maximum representable balances. For an 18-decimal asset, RAY conversion uses a factor of `10^9`, allowing the scaled supply to be brought within less than `10^9` of `i128::MAX`; consequently, an index increase of even one raw unit can overflow the total-value calculation. [8](#0-7) 

The attacker only needs to supply near the admitted cap, borrow enough to produce nonzero supplier rewards, wait for accrual to increase the supply index, and then invoke any market operation. [9](#0-8) 

Likelihood depends on a listed market permitting balances near the protocol’s arithmetic ceiling, so it is not universally reachable in low-cap markets. When such exposure is admitted, the attack requires no privileged role, malformed parameters, oracle manipulation, or control over another account. [10](#0-9) 

### Recommendation
Avoid materializing `supplied * supply_index` as an `i128` when distributing rewards. Algebraically, the index increment can be computed as `rewards_increase * RAY / supplied` and added to the current index, or the calculation can use `I256` throughout and clamp only the final supply index. [11](#0-10) 

`supply_index_reward_shortfall` likewise needs an overflow-safe path for `supplied * (new_index - old_index)` so that saturated or capped index growth can continue without reverting the entire market. [12](#0-11) 

Add a regression test that supplies a value within one raw RAY increment of the representable ceiling, accrues nonzero rewards, then verifies that withdrawal and repayment remain executable. [13](#0-12) 

### Proof of Concept
Assume an 18-decimal asset `A`, hub asset `H`, attacker account ID `0`, and a market whose caps admit the documented maximum representable token amount.

```rust
// Initial indexes are RAY.
let max_supply = max_cap_for_decimals(18); // token base units
let debt_amount = 10i128.pow(18);          // enough to produce nonzero accrual

// Attacker-controlled calls.
controller.supply(
    attacker,
    0,
    spoke_id,
    vec![HubPayment { hub_asset: H, amount: max_supply }],
);
controller.borrow(
    attacker,
    0,
    vec![HubPayment { hub_asset: H, amount: debt_amount }],
    None,
);

// Advance ledger time enough for nonzero supplier rewards.
set_timestamp(ledger_timestamp() + 1_000);

// This call succeeds and stores supply_index > RAY.
controller.update_indexes(/* account_id / hub assets for market H */);

// Every later market mutation reverts before reaching withdrawal logic:
// supplied * supply_index / RAY > i128::MAX.
controller.withdraw(
    attacker,
    0,
    vec![HubPayment { hub_asset: H, amount: 0 }],
);
```

The second accrual fails at `supplied.mul(env, old_index)` inside `update_supply_index`, so `global_sync` never reaches `mark_accrued`; because the same overflow is encountered on every retry, the market cannot recover through ordinary user or liquidation paths. [14](#0-13)

/// Grows `old_index` by distributing `rewards_increase` over the total value
/// currently supplied (`supplied * old_index`). The division rounds down.
///
/// Returns `old_index` unchanged if `supplied` or `rewards_increase` is zero,
/// or if the total supplied value is zero. Clamps the result between
/// `old_index` (itself capped at `MAX_SUPPLY_INDEX_RAY`) and
/// `MAX_SUPPLY_INDEX_RAY`, so the returned index never decreases and never
/// exceeds the cap.
pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))
}

/// Computes the portion of `rewards_increase` not reflected by the change in
/// supplied value implied by moving from `old_index` to `new_index` over
/// `supplied` (i.e. `supplied * new_index - supplied * old_index`).
///
/// Panics if `new_index` implies less supplied value than `old_index`, or if
/// the distributed value exceeds `rewards_increase`.
pub fn supply_index_reward_shortfall(
    env: &Env,
    supplied: Ray,
    old_index: Ray,
    new_index: Ray,
    rewards_increase: Ray,
) -> Ray {
    let distributed = supplied
        .mul(env, new_index)
        .checked_sub(env, supplied.mul(env, old_index));
    rewards_increase.checked_sub(env, distributed)
}

pub fn mul_div_floor(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    require_nonzero_divisor(env, d);
    if let Some(quotient) = x
        .checked_mul(y)
        .and_then(|product| div_floor_i128(product, d))
    {
        return quotient;
    }
    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    let nonneg = quotient_is_nonnegative(x, y, d);
    to_i128(env, &div_floor_i256(env, &x256.mul(&y256), &d256, nonneg))
}

/// Converts an asset-unit `cap` to a scaled `Ray` value, rounding down.
///
/// The division saturates at `i128::MAX` instead of panicking, so the cap check
/// fails open rather than trapping an entry path. The asset-to-RAY
/// rescale still panics on overflow; listings validate caps with
/// [`crate::validation::require_cap_within_asset_domain`]. Position accounting
/// uses [`calculate_scaled_supply`] and [`calculate_scaled_borrow`], which panic
/// on overflow.
pub fn calculate_scaled_cap(env: &Env, cap: i128, decimals: u32, index: Ray) -> Ray {
    Ray::from(fp_core::mul_div_floor_saturating(
        env,
        Ray::from_asset(env, cap, decimals).raw(),
        RAY,
        index.raw(),
    ))
}

/// Converts an asset-unit `amount` to a scaled supply `Ray` using floor
/// rounding relative to `supply_index`.
pub fn calculate_scaled_supply(env: &Env, amount: i128, decimals: u32, supply_index: Ray) -> Ray {
    Ray::from_asset(env, amount, decimals).div_floor(env, supply_index)
}

pub fn accrue_step(
    env: &Env,
    params: &MarketParams,
    borrowed: Ray,
    supplied: Ray,
    borrow_index: Ray,
    supply_index: Ray,
    delta_ms: u64,
) -> AccrualStep {
    let borrowed_original = scaled_to_original(env, borrowed, borrow_index);
    let supplied_original = scaled_to_original(env, supplied, supply_index);
    let util = utilization(env, borrowed_original, supplied_original);
    let borrow_rate = calculate_borrow_rate(env, util, params);
    let interest_factor = compound_interest(env, borrow_rate, delta_ms);

    let new_borrow_index = update_borrow_index(env, borrow_index, interest_factor);

    let (supplier_rewards, protocol_fee) =
        calculate_supplier_rewards(env, params, borrowed, new_borrow_index, borrow_index);

    let new_supply_index = update_supply_index(env, supplied, supply_index, supplier_rewards);
    let supplier_shortfall = supply_index_reward_shortfall(
        env,
        supplied,
        supply_index,
        new_supply_index,
        supplier_rewards,
    );

    let protocol_reward = protocol_fee.checked_add(env, supplier_shortfall);
    // Shares are valued at the new supply index, which the caller stores for
    // this step.
    let revenue_shares = if protocol_reward == Ray::ZERO {
        Ray::ZERO
    } else {
        protocol_fee_shares(env, protocol_reward, new_supply_index, supplied)
    };

    AccrualStep {
        borrow_index: new_borrow_index,
        supply_index: new_supply_index,
        revenue_shares,
    }
