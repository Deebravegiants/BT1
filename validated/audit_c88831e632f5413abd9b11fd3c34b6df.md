### Title
Priority admission plugin fails to guard `spec.Priority`/`spec.PriorityClassName`/`spec.PreemptionPolicy` on Update for `PodGroup` and `CompositePodGroup`, allowing unprivileged priority escalation - (File: `plugin/pkg/admission/priority/admission.go`)

### Summary
The `Admit` function only invokes `admitPodGroup`/`admitCompositePodGroup` when `operation == admission.Create`, so on `Update` requests these resources' `Spec.Priority`, `Spec.PriorityClassName`, and `Spec.PreemptionPolicy` fields are never re-resolved or checked against the referenced `PriorityClass`. Unlike Pods, whose immutability of these same fields is enforced separately by core object validation (as the code comment for `admitPod` states), `ValidatePodGroupUpdate` and `ValidateCompositePodGroupUpdate` only validate `ObjectMeta`, leaving the priority-related spec fields completely unguarded on update.

### Finding Description
`Admit` dispatches based on resource and operation: [1](#0-0) 
For `podGroupResource` and `compositePodGroupResource`, `admitPodGroup`/`admitCompositePodGroup` are called **only** on `admission.Create`; any `Update` operation falls through to `return nil`, performing no priority validation or resolution at all.

Contrast this with `admitPod`, where the comment explicitly documents the design assumption that other layers (core API validation) enforce immutability of `Spec.Priority`/`Spec.PriorityClassName` for Pods: [2](#0-1) 

However, the equivalent scheduling API validation for `PodGroup` and `CompositePodGroup` does **not** enforce this invariant — it only validates `ObjectMeta`: [3](#0-2) [4](#0-3) 

So neither the admission plugin (which is Create-only for these resources) nor the object validation package (which only checks `ObjectMeta` on update) protects `Spec.Priority`, `Spec.PriorityClassName`, or `Spec.PreemptionPolicy` from being freely set on `Update`/`Patch` of a `PodGroup` or `CompositePodGroup`. An attacker with only `update`/`patch` RBAC on `podgroups`/`compositepodgroups` in their namespace can directly set an arbitrary `Spec.Priority` integer (e.g., `math.MaxInt32`) and an arbitrary `Spec.PriorityClassName` (including referencing a `system-*` critical priority class they have no rights to "use"), completely bypassing the `establishPriority` resolution/consistency check that is enforced only at create time.

### Impact Explanation
This breaks the invariant that a workload's effective scheduling priority must be derived from (and match) an authorized `PriorityClass`. By exploiting the update path, an unprivileged tenant can grant their own `PodGroup`/`CompositePodGroup` an arbitrarily high scheduling priority and preemption behavior, letting it preempt higher-value or system-critical workloads. This matches the Kubernetes bounty "Admission bypass -> control of a protected field/identity (privilege escalation)" class, since priority/preemption directly controls scheduling precedence and resource contention across tenants — a workload isolation/priority-based DoS and privilege escalation vector.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs ordinary namespace-scoped RBAC granting `update`/`patch` on `podgroups` or `compositepodgroups` (a `GenericWorkload`/`CompositePodGroup` feature-gated resource that a normal workload-owning user would plausibly have permission to modify), and the relevant feature gates (`GenericWorkload`, `CompositePodGroup`) enabled. No cluster-admin, node, or webhook access is required. The bypass is deterministic and repeatable via a simple `Update`/`Patch` call once the object exists.

### Recommendation
Extend `Admit` to invoke `admitPodGroup`/`admitCompositePodGroup` (or an update-specific variant) on `admission.Update` as well as `admission.Create`, re-resolving/validating `Spec.Priority`, `Spec.PriorityClassName`, and `Spec.PreemptionPolicy` against the old object (mirroring the `admitPod` pattern of preserving `Spec.Priority`/`Spec.PreemptionPolicy` from `oldPod`), and/or add explicit immutability checks for these fields in `ValidatePodGroupUpdate`/`ValidateCompositePodGroupUpdate` in `pkg/apis/scheduling/validation/validation.go`.

### Proof of Concept
Unit test plan (admission unit test in `plugin/pkg/admission/priority/admission_test.go`):
1. Enable `GenericWorkload` feature gate; create a `PriorityClass` "low" (value 100) and one system-critical class "system-cluster-critical".
2. Create a `PodGroup` via `Admit` with `Create` operation and `PriorityClassName: "low"` — assert `Spec.Priority == 100`.
3. Build an `Update` attributes object: `oldObject` = the created PodGroup, `object` = a copy with `Spec.PriorityClassName` set to `"system-cluster-critical"` and `Spec.Priority` set to e.g. `2000000000`.
4. Call `plugin.Admit(ctx, updateAttrs, ...)` and observe it returns `nil` (no error) and leaves the attacker-supplied `Spec.Priority`/`Spec.PriorityClassName` untouched — expected/vulnerable behavior: fields pass through unchanged since `admitPodGroup` is never called for `Update`.
5. Additionally call `ValidatePodGroupUpdate(newPG, oldPG)` and assert it returns no errors for the changed `Spec.Priority`/`Spec.PriorityClassName`/`Spec.PreemptionPolicy`, confirming no downstream validation catches the mutation either.

Expected assertion for a fixed implementation: `Admit`/`Validate` should reject or overwrite the update so that `Spec.Priority`/`Spec.PriorityClassName`/`Spec.PreemptionPolicy` cannot diverge from the original resolved value without going through `establishPriority` again.
