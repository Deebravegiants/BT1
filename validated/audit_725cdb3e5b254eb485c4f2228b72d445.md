## Title
Stale `cachedSodiumEncryptor` key cache and one-shot `storage-encrypted` unlock allow cross-wallet decryption of WALLET_INFO secrets after `wallet.clear()` + re-import in the same process - ([File: sdks/headless/src/unlock-encrypted-storage.js])

## Summary
`CachedSodiumEncryptor#cache` (features/cached-sodium-encryptor/module/cached-sodium-encryptor.ts) is never invalidated on `wallet.clear()`/`wallet.lock()`, and the general-purpose encrypted storage used for `WALLET_INFO` (`adapters/storage-encrypted/src/storage.ts`) binds its `encrypt`/`decrypt` functions via a one-shot `pDefer` that can only be resolved once. Because `unlockEncryptedStorage` (sdks/headless/src/unlock-encrypted-storage.js) captures `seedId` at call time and calls `encryptedStorage.unlock(...)` on every `unlock` hook, the *second* call (after a `clear()`+`import()` cycle in the same runtime) silently no-ops, leaving the storage's crypto functions permanently bound to the **old** seed's derived key.

## Finding Description
- `wallet.clear()` (features/wallet/module/wallet.js:261-272) only deletes `SEED_KEY`/`EXTRA_SEEDS_KEY`/passphrase flags in the wallet-specific seed storage and calls `lock()` → `keychain.removeAllSeeds()`. It does **not** touch the general `WALLET_INFO` encrypted storage (a separate namespace holding tx history, addresses, etc.), nor does it clear `CachedSodiumEncryptor`'s in-memory `#cache` [1](#0-0) .
- `CachedSodiumEncryptor` derives and permanently caches private key material keyed only by `getCacheKey({seedId, keyId})`, with no eviction API tied to lock/clear [2](#0-1) . Once a `WALLET_INFO` key for `oldSeedId` has been derived, it stays resident in the `Map` for the lifetime of the process, decryptable via `decryptSecretBox({seedId: oldSeedId, keyId: WALLET_INFO, data})` regardless of whether the seed has since been removed from the keychain.
- `unlockEncryptedStorage` (sdks/headless/src/unlock-encrypted-storage.js:12-21) captures `seedId = await wallet.getPrimarySeedId()` once per call and passes closures bound to that seedId into `encryptedStorage.unlock(...)`.
- `adapters/storage-encrypted/src/storage.ts` resolves `cryptoFunctionsPromise` from a promise that is only ever settled once (the caller wiring uses a one-shot `pDefer`, see libraries/browser-extension-adapters/encrypted-storage/encrypted-storage.js and sdks/headless test adapters, both of which expose `unlock: resolve` from `pDefer()`). Calling `resolve()` a second time on an already-settled promise is a JS no-op.
- The application hook wiring in sdks/headless/src/index.js:153-160 calls `unlockEncryptedStorage(storage)` on **every** `unlock` hook fire, including the one triggered after a `clear()`+`import()` cycle without a full process restart. On this second call, the new-seedId closures are constructed and passed to `encryptedStorage.unlock(...)`, but because the underlying promise is already resolved from the first unlock, this second `unlock()` call is silently ignored — the storage instance keeps using the stale closures bound to `oldSeedId`.
- Net effect: after `clear()` + `import(attackerMnemonic)` in the same runtime process, the `WALLET_INFO` encrypted storage keeps encrypting/decrypting using the **old** wallet's seed-derived key (served from `CachedSodiumEncryptor`'s stale cache entry), not the new wallet's key. Any leftover `WALLET_INFO` ciphertext from the previous wallet remains transparently decryptable, and any new data written by the new (attacker) wallet gets encrypted under the destroyed wallet's key — producing exactly the crossover/leak the invariant "cleared/replaced wallet secrets must not remain reachable after clear" is meant to prevent.

## Impact Explanation
This breaks the confidentiality guarantee of `wallet.clear()`: previous-wallet `WALLET_INFO` secrets (tx history, cached account/address data, and anything else stored via the general encrypted storage) remain both derivable (via the un-evicted `CachedSodiumEncryptor` cache) and reachable in practice (via the storage instance still bound to the old key) after a supposed full wallet wipe and reimport in the same session — a session-scoped secret-disclosure / wrong-account data crossover matching Hydra's "secret disclosure" / "wrong-account access" impact class. It also means the newly imported wallet's own `WALLET_INFO` writes are silently encrypted under the old, destroyed wallet's key material, which is a correctness/security regression independent of any attacker action.

## Likelihood Explanation
Preconditions are directly reachable without any elevated privilege: an unprivileged user/attacker who can invoke ordinary wallet lifecycle calls (`wallet.clear()` then `wallet.import()`) in the same running process — a supported and documented flow (browser extension / persistent background process not restarted between operations) — triggers this automatically; no social engineering or privileged state is required. The bug is deterministic given the one-shot `pDefer` semantics and the absence of cache invalidation, so it reproduces every time `clear()`+`import()` happen without an intervening process restart.

## Recommendation
1. Invalidate `CachedSodiumEncryptor`'s `#cache` (all entries, or at least entries for the affected `seedId`) whenever `wallet.lock()`/`wallet.clear()` runs — expose a `clear()`/`evict(seedId)` method on `CachedSodiumEncryptor` and call it from `wallet.lock()`/`wallet.clear()`.
2. Make encrypted-storage "unlock" rebindable rather than a single-resolution `pDefer`: use a mutable reference (e.g., a `{current: cryptoFunctions}` cell) that `unlock()` overwrites each call, instead of a promise that can only settle once, so that `unlockEncryptedStorage(storage)` calls after `clear()`+`import()` actually rebind to the new seed's key.
3. As defense-in-depth, have `wallet.clear()` also purge/re-key the `WALLET_INFO` encrypted storage namespace (or at minimum assert re-unlock actually changed the bound seedId) so residual ciphertext from a cleared wallet can never be transparently decrypted by a subsequent wallet in the same process.

## Proof of Concept
Integration test (Node, using the headless SDK test harness under `sdks/headless/__tests__/`):
1. `exodus.application.start()`.
2. `await exodus.application.create({ passphrase: 'p1' })`; `await exodus.application.unlock({ passphrase: 'p1' })`.
3. `await adapters.storage.set('secret', 'wallet-1-data')` (goes through `WALLET_INFO` encrypted storage) and capture the raw ciphertext from `adapters.unsafeStorage`.
4. `await exodus.wallet.clear()`.
5. `await exodus.wallet.import({ mnemonic: attackerMnemonic })` (no process restart) then `await exodus.application.unlock({})`.
6. Assert: `await exodus.wallet.getPrimarySeedId()` returns a seedId different from step 2's.
7. Assert (failure condition demonstrating the bug): `await adapters.storage.get('secret')` still successfully returns `'wallet-1-data'` (i.e., decrypted using the old key), **and/or** a new write `await adapters.storage.set('secret2', 'wallet-2-data')` followed by manually decrypting the resulting ciphertext with `cachedSodiumEncryptor.decryptSecretBox({ seedId: oldSeedId, keyId: EXODUS_KEY_IDS.WALLET_INFO, data })` succeeds — proving both directions of crossover (old data still readable; new data encrypted under old key).
8. Expected secure behavior: after step 5, `adapters.storage.get('secret')` should fail/throw a decryption error (data encrypted under the new key context is not decryptable with the old key, and vice versa), and `cachedSodiumEncryptor`'s cache entry for `oldSeedId`/`WALLET_INFO` should no longer exist.

export class CachedSodiumEncryptor {
  readonly #keychain: Keychain
  readonly #cache = new Map<string, Buffer>()

  constructor({ keychain }: Dependencies) {
    this.#keychain = keychain
  }

  async #derivePrivateKey({ keyId, seedId }: KeySource) {
    const { privateKey } = await this.#keychain.exportKey({ keyId, seedId, exportPrivate: true })
    return privateKey
  }

  #checkIfAllowed = ({ keyId }: KeySource) => {
    return ALLOWED_KEY_IDS.some((allowedKeyId) => KeyIdentifier.compare(allowedKeyId, keyId))
  }

  #getPrivateKey = restrictConcurrency(async (params: KeySource) => {
    assert(this.#checkIfAllowed(params), 'Key source not allowed for caching.')

    const cacheKey = getCacheKey(params)
    if (!this.#cache.has(cacheKey)) {
      this.#cache.set(cacheKey, await this.#derivePrivateKey(params))
    }

    return this.#cache.get(cacheKey)
  }) as (keySource: KeySource) => Promise<Buffer>
