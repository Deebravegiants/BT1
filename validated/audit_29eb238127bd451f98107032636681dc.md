### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the raw body against `X-Shopify-Hmac-SHA256` using the app's shared `api_secret_key`. The `shop` identity forwarded to the handler is read from the `X-Shopify-Shop-Domain` header, which is never included in the signed payload. Any principal who can obtain one valid `(body, hmac)` pair for the app's secret (e.g., by installing the app on their own store and capturing a legitimate webhook delivery) can replay that exact body/hmac while substituting an arbitrary `shop-domain` header, and the signature will still verify. This breaks the equality the app relies on: `shop delivering the signed body == shop passed to WebhookMetadata`.

### Finding Description
`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received HMAC. [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw request body — no shop, topic, or webhook id is part of the signed content: [2](#0-1) 

The `shop`, `topic`, and `webhook_id` accessors are instead read directly from unauthenticated HTTP headers: [3](#0-2) 

`Registry.process` validates only the HMAC over the body, then immediately trusts `request.shop` (and `request.topic`) to build the identity handed to the app's handler: [4](#0-3) 

Because every shop that installs the app shares the same app-level `api_secret_key`, the HMAC only proves "this body was signed with this app's secret" — it does **not** prove "this body originated from shop X." An attacker who installs the target app on their own store can trigger a real webhook (e.g. `orders/create`) and capture its `(raw_body, hmac)` pair from their own delivery. They can then send that identical body and HMAC directly to the app's webhook endpoint while setting `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) to a victim shop's domain. `HmacValidator.validate` still passes because it never inspects the shop header, and `Registry.process` forwards the forged `shop` value into `WebhookMetadata`, which the app's `WebhookHandler#handle` implementation typically uses as the tenant key to look up data/session and act on the payload for "that shop."

This is the same class of bug as the reported analog: a field that is acted upon (the tenant/shop identity) is not covered by the authentication check (the HMAC), so the binding `shop authenticated == shop the code acts on` does not hold.

### Impact Explanation
If a host application uses `request.shop`/`WebhookMetadata#shop` as the tenant key to fetch a session/store record and perform actions (a documented, intended usage pattern of this gem's webhook API), an attacker can inject events under an arbitrary victim shop identity while only needing to be a legitimate (even free/trial) installer of the same app on their own store. This crosses a tenant boundary using only the gem's own verification logic — no access token, leaked secret, or privileged account is required — matching the "cross-tenant access" High/Critical impact category.

### Likelihood Explanation
Likelihood is realistic but requires: (1) the target app to be installable by the attacker (common for public/multi-tenant Shopify apps), (2) the app's webhook handler to trust `data.shop` for tenant identification without independently verifying shop ownership of the entity IDs contained in the body (a common pattern, since the gem's own `WebhookMetadata` API surfaces `shop` as if it were an authenticated field). The gem does nothing to prevent or warn against this trust, and provides no API to cryptographically bind body content to the shop header.

### Recommendation
Bind the shop identity to the authenticated payload before trusting it:
- Cross-check `request.shop` against a shop/session already known to be associated with the resource IDs in the parsed body, or
- Extend `to_signable_string`/verification to require the app to independently verify shop ownership (e.g., look up an active session for `request.shop` and reconcile against resource ownership) before invoking the handler, and document this requirement prominently in `WebhookHandler`/`Registry.process` so integrators do not treat `data.shop` as authenticated.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, triggering a legitimate webhook delivery for, e.g., `orders/create`.
2. Attacker captures the raw POST body and the `X-Shopify-Hmac-SHA256` header from that delivery (a valid `(body, hmac)` pair signed with the app's `api_secret_key`).
3. Attacker replays the identical body and HMAC to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` → `Utils::HmacValidator.validate` succeeds because it only checks the body against the HMAC: [5](#0-4) 
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body, ...)`, so any downstream logic keyed on `shop` now operates as if it received a genuine webhook from the victim. [6](#0-5)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
