### Title
Webhook `shop`/`topic`/`webhook_id` headers are trusted without HMAC coverage, breaking the shop-identity binding - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook using `Utils::HmacValidator.validate(request)`, but the signable content for a webhook `Request` is only the raw HTTP body [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to the app's handler as the authenticated identity of the event are read straight from HTTP headers and are never included in the HMAC-signed material [2](#0-1) . This breaks the identity binding: `shop verified by HMAC == shop acted upon by the handler`.

### Finding Description
`HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` field of the same object [3](#0-2) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from separate, unsigned HTTP headers [2](#0-1) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the handler with the raw header-derived `shop`, `topic`, and `webhook_id`: [4](#0-3) 

The `WebhookMetadata` struct that is passed to app handler code carries these unauthenticated fields as if they were verified: [5](#0-4) 

The gem's own documentation instructs app developers to trust this data completely, explicitly stating that `Registry.process` "will verify the request did indeed come from Shopify," and shows a sample handler that uses `data.shop` as the tenant identity to enqueue background work (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [6](#0-5) [7](#0-6) 

Because the `api_secret_key` used for HMAC computation is a single shared secret for the whole app (not per-shop), any merchant who legitimately installs the app receives real webhook deliveries with a valid `(raw_body, hmac)` pair signed by that shared secret. Since the header fields (`shop-domain`, `topic`, `webhook-id`) are not part of the signed content, that same valid `(raw_body, hmac)` pair can be replayed to the app's webhook endpoint with attacker-chosen header values (e.g., a different `shop-domain`) and it will still pass `HmacValidator.validate`. `Registry.process` will then dispatch the (attacker-supplied) `shop` value to the handler as if it were Shopify-attested, exactly the "shop authenticated vs. shop acted upon" binding break called out in the rules.

### Impact Explanation
This is a cross-tenant identity spoofing primitive built into the gem's webhook verification API: a low-privilege actor (any merchant/user who can install the app and thus receive at least one real, validly-signed webhook for their own store) can forge the `shop`/`topic`/`webhook_id` attribution of a webhook event delivered to the app's endpoint, causing the app to process/act on data (or enqueue jobs, invalidate caches, trigger business logic) under another tenant's identity. Given the library’s own doc claims HMAC verification proves Shopify origin and correctness of the `shop`, apps built exactly per the documented pattern inherit this cross-tenant confusion, which maps to the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation only requires: (1) being a merchant able to install the target app and observe at least one legitimate webhook delivery (a normal, unprivileged action), and (2) the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with custom headers (also unprivileged, no special network position or credentials needed) — the endpoint is a normal HTTP webhook receiver by design. No access token, `api_secret_key`, or privileged account is required.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values in the HMAC-signed material (or otherwise cryptographically bind them, e.g., have `Webhooks::Request#to_signable_string` combine headers and body, matching what Shopify actually signs), and have `Registry.process` reject/require agreement between any externally-supplied identity fields and values it can independently verify. At minimum, the documentation should not claim the process "verifies the request did indeed come from Shopify" for header-derived fields that are unauthenticated.

### Proof of Concept
1. App merchant "Attacker Shop" installs the target Shopify app and legitimately receives a real webhook, e.g. `orders/create`, giving them body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC_SHA256(api_secret_key, B)` (the app's shared secret).
2. Attacker crafts a new HTTP POST to the same public webhook endpoint, reusing `body = B` and `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Webhook-Id: <arbitrary>`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` parses these headers [8](#0-7) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only checks `B` against `H` [9](#0-8) .
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload actually originated from the attacker's own store, and the app processes it as a legitimate event for the victim tenant [10](#0-9) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
