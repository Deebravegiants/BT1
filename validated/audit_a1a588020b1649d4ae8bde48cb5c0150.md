### Title
Webhook HMAC Verification Does Not Bind the `shop`/`topic`/`webhook-id` Headers, Enabling Cross-Tenant Webhook Forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` directly from unauthenticated HTTP headers, while the HMAC signature that `Utils::HmacValidator` verifies is computed only over the raw request body. Because the app's `api_secret_key` is a single, shared secret across every shop/tenant that has installed the app, a valid HMAC for one shop's webhook body remains valid when the `shop-domain` header is swapped for a different shop, letting an attacker who controls one tenant forge webhook events attributed to another tenant.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are parsed straight from headers with no cryptographic binding: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` only recomputes the HMAC over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it to the supplied `hmac`, never incorporating the shop, topic, or webhook id: [3](#0-2) 

`Registry.process` trusts this validation and then dispatches to the handler using the unauthenticated `request.shop` and `request.topic` values: [4](#0-3) 

This breaks the identity binding: `shop authenticated (implied by a valid HMAC) == shop attached to and processed with the webhook payload`. Since the HMAC is computed with a single, per-app `api_secret_key` shared by every merchant that installs the app (not a per-shop secret), any tenant that can trigger a genuinely-signed webhook for their own shop can capture that request and replay it against the same endpoint with the `shop-domain` (and/or `topic`/`webhook-id`) header rewritten to a victim shop, while the raw body — and therefore the HMAC — stays valid.

### Impact Explanation
This is a cross-tenant vulnerability: an attacker who is an unprivileged legitimate user of the app for their own shop can cause the app to process forged webhook data (order/product/customer content of the attacker's choosing) under a victim shop's identity, since `WebhookMetadata.shop` used by all downstream handler logic is taken directly from the attacker-controlled header. Depending on what the host app's webhook handlers do (sync orders, update records, trigger emails, write to per-shop storage), this can result in data corruption, unauthorized actions, or information disclosure scoped to a shop the attacker does not control — meeting the "cross-tenant access" Critical impact bar.

### Likelihood Explanation
Exploitation requires only that the attacker control (or observe traffic from) one shop that has the app installed — a normal, unprivileged capability — and be able to send an HTTP request to the app's public webhook endpoint with a modified `x-shopify-shop-domain`/`shopify-shop-domain` (or `-topic`/`-webhook-id`) header while keeping the raw body byte-identical to a webhook they legitimately received. No knowledge of `api_secret_key` or any credential belonging to the victim shop is needed.

### Recommendation
Bind the identity fields to the signature. At minimum, include `shop`, `topic`, and `webhook_id` (in addition to the body) in the string that is HMAC-signed/verified, or independently verify that the shop domain in the request matches an expected/registered shop for the delivered webhook subscription before dispatching to a handler. Do not treat header-derived `shop`/`topic`/`webhook_id` as trusted metadata once only the body has been authenticated.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a real event (e.g., creates an order), causing Shopify to send a legitimately-signed webhook to the app's endpoint:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid HMAC over body, computed with the app's shared api_secret_key>
x-shopify-shop-domain: attacker-shop.myshopify.com
x-shopify-webhook-id: wh_1
Body: {"id":1,"note":"..."}
```
2. Attacker captures this request and resends it to the same endpoint, changing only the shop header (body untouched, so the HMAC is unchanged and still valid):
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <same, still valid HMAC>
x-shopify-shop-domain: victim-shop.myshopify.com
x-shopify-webhook-id: wh_1
Body: {"id":1,"note":"..."}
```
3. `Utils::HmacValidator.validate` returns `true` because it only checks the body signature (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:188-200`), causing attacker-supplied data to be processed as if it originated from the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
