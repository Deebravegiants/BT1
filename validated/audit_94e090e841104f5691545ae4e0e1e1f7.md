### Title
PoA Bridge `describeWithdrawal` misreports completion status/tx hash across multiple same-asset withdrawals in a batch - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`createWithdrawalIdentifiers` assigns a per-bridge `index` to each withdrawal in a batch [1](#0-0) , but `PoaBridge.describeWithdrawal` never uses that `index` to disambiguate withdrawals — it matches purely by `assetId` via `findMatchingWithdrawal` [2](#0-1) [3](#0-2) . When a single intent transaction contains two or more PoA withdrawals of the same token (e.g., to two different destination addresses), `describeWithdrawal` for index 0 and index 1 both resolve to the *same* first-matching API entry, so the reported `status`/`txHash` for the second withdrawal is actually the outcome of the first one.

### Finding Description
The SDK supports batching multiple withdrawals in a single signed intent (`processWithdrawal`/`signAndSendWithdrawalIntent` accept `WithdrawalParams[]`) [4](#0-3) . `createWithdrawalIdentifiers` correctly tracks a distinct `index` per bridge route for each withdrawal in the batch so bridges can disambiguate multiple withdrawals routed through the same bridge [5](#0-4) .

However, `PoaBridge.describeWithdrawal` ignores `args.index` entirely and looks up the withdrawal solely by `assetId`:
```
const withdrawal = findMatchingWithdrawal(
    response.withdrawals,
    args.withdrawalParams.assetId,
);
```
`findMatchingWithdrawal` returns the *first* array element whose `near_token_id` matches, regardless of which of possibly several same-asset withdrawals in the transaction it actually corresponds to [6](#0-5) . The code comment explicitly acknowledges this: "multiple withdrawals of the same token in a single transaction are not supported" — but this limitation is silently accepted rather than rejected/guarded against; the SDK does not prevent building a batch with duplicate assetIds, and callers of `watchWithdrawal`/`waitForWithdrawalCompletion` receive a `WithdrawalStatus` per index that can silently be wrong [7](#0-6) .

This breaks the equality "status/txHash reported for withdrawal N == on-chain outcome of withdrawal N." Concretely: if withdrawal[0] sends 100 USDT to address A and withdrawal[1] sends 100 USDT to address B in the same batch, and the POA relayer processes withdrawal[1] to B first (completing it) while withdrawal[0] to A is still pending, `describeWithdrawal({index:0})` and `describeWithdrawal({index:1})` will both match the same underlying API record (B's completed entry) — reporting both as `completed` with B's `transfer_tx_hash`, even though A's withdrawal has not actually landed on-chain.

### Impact Explanation
An integrator relying on `waitForWithdrawalCompletion`/`watchWithdrawal` output to mark a specific withdrawal (identified by destination/index) as settled and to credit/refund a user, or to display/store the destination tx hash for that specific withdrawal, would attribute a completed status and an unrelated transaction hash to a withdrawal that either hasn't completed or completed differently. This matches the "status or hash misreport making an integrator credit or refund twice" category — an integrator could prematurely treat a still-pending withdrawal as settled and release additional off-chain credit, or record the wrong destination tx hash against the wrong recipient's withdrawal record.

### Likelihood Explanation
This requires no privileged access — any external caller of the SDK who batches ≥2 withdrawals of the same PoA-bridged asset (a legitimate, documented use case via `processWithdrawal`/`signAndSendWithdrawalIntent` with `WithdrawalParams[]`) triggers this on every status check while both withdrawals are in flight simultaneously. The SDK does not validate/reject duplicate-asset batches, and the bug is deterministic (not timing-dependent for triggering, only the specific misreported values depend on relayer processing order).

### Recommendation
`findMatchingWithdrawal` should disambiguate using additional withdrawal-identifying fields beyond `assetId` — e.g. match on `assetId` **and** `destinationAddress`/`amount`/order, or have the POA API return/accept a client-supplied identifier per withdrawal so the SDK can look up the exact entry by `index`. Until the POA API supports this, the SDK should detect duplicate-asset withdrawals within a batch at `createWithdrawalIntents`/`createWithdrawalIdentifiers` time and either reject them or clearly surface an "ambiguous status" result instead of silently returning a matched-by-luck status for the wrong index.

### Proof of Concept
1. Call `sdk.signAndSendWithdrawalIntent` with `withdrawalParams: [{assetId: "nep141:usdt.omft.near", amount: 100n, destinationAddress: "A"}, {assetId: "nep141:usdt.omft.near", amount: 100n, destinationAddress: "B"}]` (batched in one NEAR tx).
2. `createWithdrawalIdentifiers` produces `wid[0]` (index 0, destination A) and `wid[1]` (index 1, destination B), both routed to `PoaBridge` [8](#0-7) .
3. Suppose the POA relayer completes the withdrawal to B first while A is still pending; `poaBridge.httpClient.getWithdrawalStatus` returns one `COMPLETED` entry with `near_token_id: usdt.omft.near, transfer_tx_hash: <B's hash>` and no entry (or a pending one) for A.
4. Calling `bridge.describeWithdrawal(wid[0])` and `bridge.describeWithdrawal(wid[1])` both execute `findMatchingWithdrawal(response.withdrawals, "nep141:usdt.omft.near")`, which returns the same first match — B's completed record — for **both** indices, so `watchWithdrawal` resolves `{hash: <B's hash>}` for withdrawal[0] (destination A) even though A's transfer has not occurred on-chain.

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
