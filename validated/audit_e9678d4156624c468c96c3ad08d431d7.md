### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, allowing shop-identity spoofing in `ShopifyAPI::Webhooks::Registry.process` - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature only over the raw request body (`to_signable_string` returns `@raw_body`), while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers. `Registry.process` validates the HMAC against the body, but then trusts `request.shop` and `request.topic` — fields that are never part of the signed data — to dispatch the webhook and populate `WebhookMetadata` passed to the host app's handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are pulled straight from HTTP headers with no cryptographic binding to the body or the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which internally calls `verifiable_query.to_signable_string` (i.e., only the body) and `verifiable_query.hmac`: [3](#0-2) 

After the HMAC check passes, `Registry.process` uses `request.topic` (unauthenticated) to look up the handler, and forwards `request.shop` (also unauthenticated) into `WebhookMetadata`, which is delivered to the app's business logic as the tenant identity for this webhook: [4](#0-3) 

`WebhookMetadata.shop` is a plain `String` const with no verification step of its own — it is exactly what `request.shop` returned: [5](#0-4) 

**Root cause / broken binding:** the equality the code implicitly assumes is:
`shop authenticated by HMAC == shop delivered to the handler`

but in reality:
`bytes verified by HMAC (raw_body only) != identity fields consumed by the handler (shop-domain, topic headers)`

Because the app's `client_secret` (used to key the HMAC) is a single secret shared across *all* shops that install the app, any merchant who installs the app on their own store legitimately receives Shopify-issued webhooks with a valid `(body, hmac)` pair signed under that same shared secret. An unprivileged internet user who controls a shop that has installed the target app can capture one such legitimate `(raw_body, x-shopify-hmac-sha256)` pair from their own webhook deliveries, then replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header (e.g., a victim shop) and/or a different `x-shopify-topic`. `HmacValidator.validate` will still pass because it only checks the body bytes, and `Registry.process` will hand the forged shop identity straight to the app's webhook handler.

### Impact Explanation
This breaks the tenant/shop identity binding that host applications rely on when processing webhooks — the whole reason the HMAC exists is to let the app trust the `shop`/`topic` metadata that accompanies a webhook. An attacker who legitimately possesses one valid signed webhook body can forge the shop-domain (and topic) associated with that payload, enabling cross-tenant data injection into another merchant's records inside the host app (e.g., a `customers/data_request`/`shop/redact` handler acting on the wrong shop, or business data being attributed to a different tenant). This matches the "cross-tenant access" impact class, since a merchant of one tenant can cause a fabricated webhook to be processed as if it belonged to a different tenant.

### Likelihood Explanation
Requires only:
1. The attacker owns/controls a shop that has the target app installed (an ordinary unprivileged merchant action, no special access needed).
2. The attacker replays a body+HMAC combination they legitimately received, substituting headers, which the gem does nothing to prevent — the vulnerability is directly reachable through the gem's own `Webhooks::Request`/`Registry.process` API with no privileged credentials required from the attacker's side.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the verified payload (e.g., HMAC over a canonicalized concatenation of headers + body) so that a valid signature can only be produced for the specific shop/topic combination it was issued for. At minimum, document this limitation prominently so host apps do not treat `WebhookMetadata.shop`/`topic` as authenticated without additional verification (e.g., checking `shop` against the app's own session store before trusting it).

### Proof of Concept
```ruby
# 1. Attacker installs the app on their own shop "attacker-shop.myshopify.com"
#    and receives a legitimate webhook delivery from Shopify:
raw_body = '{"id":123,"note":"legit payload from attacker-shop"}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# 2. Attacker replays the same body+hmac to the app's webhook endpoint,
#    but swaps the shop-domain header to a victim shop:
forged_headers = {
  "x-shopify-topic" => "customers/data_request", # or any registered topic
  "x-shopify-hmac-sha256" => valid_hmac,          # still valid: HMAC never covered shop/topic
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",
}

req = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(req)
# => HmacValidator.validate(req) succeeds (only checks raw_body),
#    handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)) is invoked,
#    delivering attacker-controlled data under a spoofed shop identity.
```
