### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header is trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from unauthenticated HTTP headers to build the `WebhookMetadata` passed to the app's handler. Because the signed bytes (`raw_body`) and the trusted identity field (`shop`) are disjoint, an attacker who can obtain one validly-signed webhook body (e.g., by triggering a webhook to their own store, where the app is installed under the same shared `api_secret_key`) can replay that body with a forged `shopify-shop-domain` header to make the handler believe the event originated from a different merchant.

### Finding Description
The equality that should hold, but does not, is:

`bytes verified by HMAC == bytes the handler treats as authenticated (topic + shop + webhook_id)`

`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from HTTP headers with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then forwards the header-derived `shop` (and `topic`, `webhook_id`) unchecked into `WebhookMetadata`, which is delivered to the app's business logic: [3](#0-2) 

`HmacValidator.validate` only ever signs/compares `verifiable_query.to_signable_string`, so for webhooks it is exclusively `raw_body`; none of the identifying headers are part of the signable string: [4](#0-3) 

Because the app's `api_secret_key` is shared across every shop that has the app installed (it's an app-level secret, not merchant-specific), any merchant who installs the app — including an attacker — can legitimately trigger a webhook to their own endpoint and thereby obtain a `(raw_body, hmac)` pair that is valid under the app's secret. Since the HMAC never covers `shop-domain`, `topic`, or `webhook-id`, the attacker can replay that exact body/HMAC pair while substituting the `shopify-shop-domain` (and/or `topic`, `webhook-id`) header to point at a victim shop. `Registry.process` will accept it as authentic and hand the handler a `WebhookMetadata` claiming the event came from the victim shop.

### Impact Explanation
This breaks the tenant boundary the library is supposed to enforce for webhook delivery: an unprivileged app-installer can make the host application process attacker-controlled data while impersonating a completely different merchant. Any handler logic keyed off `WebhookMetadata#shop` (e.g., updating per-shop caches, flags, entitlements, deleting or reconciling data "for that shop", triggering downstream authenticated actions) can be driven for a target shop the attacker does not control — a cross-tenant access primitive.

### Likelihood Explanation
Exploitation requires no leaked credentials or special access — only that the attacker be a genuine, unprivileged installer of the same app (a normal internet user installing a public app). They can generate their own signed webhook trivially (e.g., by making an update in their own store that triggers the subscribed topic), then replay the captured body/HMAC to the app's public webhook endpoint with a modified shop header. No interaction with Shopify's private signing key is needed since the attacker legitimately receives one instance signed with that key.

### Recommendation
- Bind the identifying fields into the signable payload, or otherwise cryptographically verify that the `shop-domain`/`topic`/`webhook-id` headers match the shop/topic the raw body actually describes (e.g., by cross-checking the `shop`/`topic` fields embedded inside the parsed body against the headers) before constructing `WebhookMetadata`.
- At minimum, document and enforce that host applications must independently verify `request.shop` corresponds to a shop actually known to have installed the app before trusting it, and consider having `Registry.process` accept a caller-supplied allow-list of expected shops.
- Long term, treat `Request` header-derived identity fields as untrusted until validated against the HMAC-covered body content, following the same principle used elsewhere in the library for the OAuth `AuthQuery`, where every field used post-validation is part of the signed string (`code`, `host`, `shop`, `state`, `timestamp`): [5](#0-4) .

### Proof of Concept
1. Attacker installs the target app on their own development store `attacker-shop.myshopify.com` (the app's `api_secret_key` is shared across all installs).
2. Attacker triggers a subscribed webhook topic (e.g., `orders/create`) on their own store; Shopify sends a POST with:
   - `raw_body` = attacker-controlled JSON payload
   - `X-Shopify-Hmac-Sha256` = valid HMAC of `raw_body` under the shared `api_secret_key`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
3. Attacker replays the identical `raw_body`/HMAC to the app's webhook endpoint, but changes the header to `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks `raw_body` against the HMAC: [6](#0-5) 
5. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: attacker_json, ...)` and invokes the app's handler, which now believes the attacker's payload originated from the victim shop: [7](#0-6)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
