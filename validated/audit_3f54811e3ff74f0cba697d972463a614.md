## Analog Found

The Sherlock report's bug class — an external call that returns *successfully* while silently failing to deliver funds, causing the caller to proceed with irreversible state changes (marking an operation complete, decrementing escrow) — has a direct structural analog in Hyperbridge's Tron `IntentGatewayV2` contract.

### Title
Unchecked ERC20/TRC20 `.call` return-data in `IntentGatewayV2.withdraw()` lets escrow be marked filled/refunded while beneficiary receives nothing - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw()` (Tron variant) releases escrowed ERC20/TRC20 tokens using a raw low-level `.call()` to the token's `transfer` selector, and only checks that the *call itself* did not revert (`success`) — it never decodes/validates the returned boolean. Any token that returns `false` on a failed transfer instead of reverting (a well-known TRC20/ERC20 quirk) will cause the function to treat the transfer as successful, permanently finalizing the order (`_filled[commitment] = beneficiary`) and decrementing escrow accounting, while the beneficiary never actually receives the funds.

### Finding Description
`withdraw()` is the internal handler invoked from `onAccept()` when a `RedeemEscrow` or `RefundEscrow` request is delivered by any relayer, and from `onGetResponse()` during source-chain cancellation — both paths are reachable by any unprivileged relayer/message deliverer, exactly the class of caller in scope. [1](#0-0) 

The relevant code:
```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;
    ...
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
    ...
    _orders[body.commitment][token] -= amount;
``` [2](#0-1) 

`success` here only reflects that the external call did not revert — it does not verify the ABI-encoded boolean return value that `transfer()` is supposed to produce. Many TRC20/ERC20-style tokens (and TRC20 in particular has known non-standard/loosely-enforced return behavior) return `false` on failure (e.g., due to an internal balance/allowance/blacklist/pause condition) instead of reverting. In that case `success == true`, so the function proceeds exactly as if the transfer had succeeded: it finalizes `_filled[commitment]`, decrements `_orders[commitment][token]`, and emits `EscrowReleased`/`EscrowRefunded` — all before or without any actual token movement.

This is the same root-cause shape as the Convex report: a downstream external dependency silently fails to deliver the expected value while returning a "success" signal, and the caller's bookkeeping (finalize/mark-complete) is unconditionally advanced on that false signal. Notably, the same `withdraw`/`_withdraw` logic in the non-Tron `IntentGatewayV2.sol` and `IntentsBase.sol` correctly uses OpenZeppelin's `SafeERC20.safeTransfer`, which decodes and enforces the boolean return value — confirming this is a regression/deviation specific to the Tron contract rather than the intended design. [3](#0-2) 

### Impact Explanation
Once `_filled[commitment]` is set and `_orders[commitment][token]` is decremented, the order can never be retried or re-withdrawn (subsequent calls hit `UnknownOrder()`/already-filled checks), while the intended beneficiary (the user being refunded, or the solver being paid) never receives the underlying tokens. This is a permanent freezing/loss of escrowed user or solver funds — tokens remain stuck in the `IntentGatewayV2` contract with no path to recovery, since the accounting no longer reflects them as owed to anyone.

### Likelihood Explanation
Triggering requires only that the escrowed token behaves non-standardly on a failed transfer (returns `false` instead of reverting) under some realistic condition — e.g., a paused/blacklist-style TRC20 token, or any token with balance/allowance edge cases that don't revert. Given Tron/TRC20's well-documented looser adherence to the ERC20 return-value convention, and that the vulnerable path is reachable by any relayer delivering a `RedeemEscrow`/`RefundEscrow` message (no privileged role required), the likelihood is non-trivial for any order that escrows such a token.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` (and the analogous `SweepDust` handling) with OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom`, matching the implementation already used in `evm/src/apps/intentsv2/IntentsBase.sol` and `evm/src/apps/IntentGatewayV2.sol`, so that a `false` return value reverts the transaction instead of being silently accepted as success.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with an escrowed token `T` that returns `false` (rather than reverting) on `transfer()` failure — e.g., simulate `T` becoming unable to fulfill the transfer (internal cap, paused state, or blacklisted beneficiary) while still returning `false` from a successful low-level call.
2. Place an order with input token `T`; have a relayer deliver a `RedeemEscrow` (or `RefundEscrow`) request for that order's commitment.
3. `withdraw()` executes `token.call(...)`, which returns `(true, abi.encode(false))` (call succeeds, but the encoded boolean is `false`).
4. Because only `success` is checked, `_filled[commitment]` is set and `_orders[commitment][token]` is decremented, while `T.balanceOf(beneficiary)` remains unchanged — the beneficiary's escrowed tokens are lost with no remaining code path to reclaim them.

    /**
     * @notice Withdraws the escrowed tokens for a request body.
     * @dev This function is marked as internal.
     * @param body The request body containing commitment, tokens, and beneficiary.
     * @param isRefund Whether this is a refund (true) or a successful fill (false).
     */
    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
