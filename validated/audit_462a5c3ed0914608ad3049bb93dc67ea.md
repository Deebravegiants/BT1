### Title
Cross-chain escrow withdrawal is authorized by *any* registered IntentGateway instance, not by the specific destination chain the order designated - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`ExtrinsicIntents.onAccept` authenticates incoming `RedeemEscrow`/`RefundEscrow` requests only by checking that the request came from *some* registered IntentGateway instance (`instance(request.source) == request.from`), never by checking that `request.source` equals the specific `order.destination` chain that the original order committed to. This is the same bug class as the Gitea advisory: an object (an attachment / here, escrowed funds keyed only by `commitment`) can be released/linked by any authorized peer, instead of being checked against the specific owning relationship (the release's repo / here, the order's declared destination chain) it was scoped to.

### Finding Description
When a user places a cross-chain order via `IntentGatewayV2.placeOrder` / `ExtrinsicIntents`, the order struct fixes `order.source` and `order.destination`, and escrow is credited under `_orders[commitment][token]` where `commitment = keccak256(abi.encode(order))` [1](#0-0) .

The only chain permitted to eventually release that escrow (via `RedeemEscrow`) is supposed to be `order.destination`'s gateway instance, once a solver fills the order there. However, `onAccept` dispatches `RedeemEscrow`/`RefundEscrow` handling straight to `_authenticate(incoming.request)` and then `_withdraw`, without ever comparing `incoming.request.source` to the specific `order.destination` recorded for that commitment: [2](#0-1) 

`_authenticate`/`authenticate` only verifies that the message is from *a* known IntentGateway instance address for *whatever* `request.source` chain the message claims, via the generic `_instances` registry: [3](#0-2) [4](#0-3) 

`_withdraw` then only checks that the `commitment`+`token` slot in `_orders` is non-zero — it never checks that `body`/`request.source` corresponds to the chain the order actually specified as `destination`: [5](#0-4) 

Because `_instances` is a flat map of `keccak256(stateMachineId) → gateway address` populated by governance via `NewDeployment` for every supported chain [6](#0-5) , *any* of these registered peer chains can produce a valid, authenticated `RedeemEscrow`/`RefundEscrow` request for *any* commitment that has non-zero escrow on the source chain — not just the one chain named in `order.destination` when the order was placed. The relationship between "this specific escrow" and "the one chain authorized to release it" is never re-validated at withdrawal time, exactly mirroring the Gitea flaw where an attachment could be linked to a release in a different repository because ownership of the specific parent object was never re-checked.

### Impact Explanation
If a state machine other than the order's declared `order.destination` is compromised (its consensus client subverted, or its registered IntentGateway module address/ownership compromised — a scenario explicitly in scope, since IntentGateway instances are governance-registered per chain and many chains are integrated), an attacker there can forge a `RedeemEscrow` (or `RefundEscrow`) message carrying a real, previously-observed `commitment` value (commitments and their orders are public — emitted in `OrderPlaced`) for tokens escrowed on a *different, honest* source chain, for orders whose true destination was some other legitimate chain. Because `_withdraw` checks only `_orders[commitment][token] != 0`, not "this commitment's order.destination equals request.source", the forged message passes and the attacker drains the real escrowed input tokens to a beneficiary of their choosing before the legitimate solver ever fills the order on the correct destination chain. This is a direct theft of escrowed user funds across the multi-chain deployment, satisfying "concrete theft ... of funds."

### Likelihood Explanation
Exploitation requires control (compromise) of the ISMP/dispatch path for one of the *other* legitimately registered IntentGateway destination chains — not the order's real destination — a bar comparable to "unauthorized app action" reachable by a malicious module/dispatcher on any one of the many chains IntentGateway is deployed to, which is a broad attack surface given IntentGateway supports many EVM chains simultaneously through the shared `_instances` registry. It does not require privileged access to the specific victim chain, governance keys, or the honest destination chain — only to any single registered peer, which is a materially weaker precondition than compromising the correct chain, making this a meaningfully increased likelihood over a properly-scoped design.

### Recommendation
Bind escrow release authorization to the order's actual `destination` field, not merely to "any known instance." Concretely: derive/store `order.destination` (or a hash of it) alongside the `_orders[commitment]` escrow entry at `placeOrder` time, and in `_withdraw`/`onAccept`, assert `keccak256(incoming.request.source) == keccak256(storedDestinationForCommitment)` before releasing funds for `RedeemEscrow`. For `RefundEscrow` from the destination chain, the analogous check should assert the same binding. This closes the gap the same way Gitea's fix required verifying an attachment's owning repository matches the release's repository before linking.

### Proof of Concept
1. Governance registers legitimate IntentGateway instances on Chain A (source), Chain B (order's real destination), and Chain C (an unrelated but registered destination), via `NewDeployment`, populating `_instances` on Chain A for both B and C [6](#0-5) .
2. A user places a cross-chain order on Chain A with `order.destination = Chain B`; escrow is credited under `_orders[commitment][token]` on Chain A [1](#0-0) . `commitment` and the order details are public via `OrderPlaced`.
3. Before any solver fills on Chain B, an attacker who has compromised the consensus/relayer path for Chain C's registered IntentGateway module crafts a `PostRequest` with `source = Chain C`, `from = <Chain C's registered gateway address>`, body = `RequestKind.RedeemEscrow` with `WithdrawalRequest{commitment, tokens: order.inputs, beneficiary: attacker}`.
4. This request passes ISMP delivery to Chain A and reaches `ExtrinsicIntents.onAccept` → `_authenticate` succeeds because `instance(Chain C) == from` (a legitimate, if different, gateway registration) [3](#0-2) .
5. `_withdraw` finds `_orders[commitment][token] != 0` (real escrow from step 2) and releases the tokens to the attacker's `beneficiary`, without ever checking that `Chain C == order.destination (Chain B)` [5](#0-4) .

Note: I could not fully trace whether `_authenticate`'s implementation in `ExtrinsicIntents.sol` (as opposed to the `tron` contracts variant shown) contains any additional destination-binding check beyond what's shown in `IntentsBase._instance`/`authenticate`; the index did not surface the exact body of `_authenticate` in `ExtrinsicIntents.sol` separately from `IntentsBase.sol`, so this should be verified directly in the full file before remediation.

    function _instance(bytes calldata stateMachineId) internal view returns (address) {
        address gateway = _instances[keccak256(stateMachineId)];
        if (gateway == address(0)) revert UnknownInstance();

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        address module = address(bytes20(request.from));
        // IntentGateway only accepts incoming assets from itself or known instances
