### Title
Webhook Shop-Domain Spoofing via HMAC Scope Mismatch in `ShopifyAPI::Webhooks::Request` — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` proves nothing about the `shop`, `topic`, `webhook_id`, or `api_version` values, which are read verbatim from unauthenticated HTTP headers and forwarded to the app's webhook handler as trusted tenant identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#shop` reads directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cryptographic binding: [1](#0-0) 

The signable content used for HMAC verification is the raw body only: [2](#0-1) 

`Utils::HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it against the `hmac-sha256` header — i.e. it authenticates only the body bytes, never the `shop` (or `topic`/`webhook_id`/`api_version`) headers: [3](#0-2) 

`Registry.process` performs exactly that body-only HMAC check and then unconditionally forwards the unauthenticated `request.shop` into `WebhookMetadata`, which the host app's handler treats as the trusted tenant identifier: [4](#0-3) 

The identity binding that should hold is: `shop reported to handler == shop that actually produced/authorizes the signed body`. Because `shop` is excluded from the signable string, this equality is never checked — only `HMAC(secret, raw_body) == received_hmac` is checked, and that check is satisfied by *any* body that was ever legitimately signed with the app's single, shared `api_secret_key`, regardless of which shop it was originally sent for.

The gem's own documentation instructs developers to trust `data.shop` as the tenant identity without any additional verification, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`: [5](#0-4) 

### Impact Explanation
`api_secret_key` is shared across all shops using the app — Shopify signs every shop's webhook body with the same per-app secret. An attacker who has legitimately installed the app on their own shop (a normal, unprivileged action available to any internet user via the App Store or a dev store) can capture one of their own shop's genuinely signed webhook deliveries (raw body + valid `hmac-sha256`), then replay that exact body/HMAC pair to the app's public webhook endpoint while only changing the `X-Shopify-Shop-Domain` header to name a victim shop. `HmacValidator.validate` still passes because it only checks the body, and `Registry.process` hands the handler a `WebhookMetadata` claiming the (attacker-controlled) body belongs to the victim shop. Any host application that keys shop-scoped state (order records, customer PII, GDPR/compliance actions, billing state, session lookups) off `data.shop` as documented can have attacker-controlled data cross-attributed to another tenant — a cross-tenant data injection/confusion vulnerability.

### Likelihood Explanation
The only prerequisite is being able to install the app on a shop the attacker controls (freely available to any developer/merchant) and being able to send arbitrary HTTP requests to the app's public webhook endpoint (also freely available to any internet user, since these are unauthenticated public callback URLs by design). No access token, `client_secret`, or privileged credential is required — only reuse of a legitimately-signed payload the attacker already possesses from their own shop.

### Recommendation
Include the shop domain (and ideally topic/webhook_id/api_version) in the signable content used for HMAC verification, or otherwise cryptographically bind the reported `shop` to the specific signed payload (e.g., have `HmacValidator`/`Registry.process` reconcile `request.shop` against a shop known to have a valid, non-replayed webhook subscription/session, and reject if unmatched). At minimum, document that `data.shop` from `WebhookMetadata` is not covered by the HMAC and must be independently corroborated against the app's known/installed shop list before being used for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook: `raw_body = '{"id":1,...}'`, `X-Shopify-Hmac-Sha256: <valid HMAC of raw_body with the app's api_secret_key>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker POSTs the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses this; `HmacValidator.validate(request)` computes `HMAC(secret, raw_body)` — identical to the original — and passes.
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: request.parsed_body, ...))`, causing the host app to process attacker-controlled data under the victim's tenant identity.
