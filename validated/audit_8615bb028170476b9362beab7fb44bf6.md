### Title
Unrestricted `fungible_asset::deposit` to `swap::liquidity_pool` reserve stores allows a donation attack that permanently DoSes `mint()` and corrupts LP share accounting - (File: aptos-move/move-examples/swap/sources/liquidity_pool.move)

### Summary
The Uniswap-v3 report's core custody invariant is: *a state value used to gate a critical, capital-affecting operation (launch/price check) must not be derivable from a balance that can be mutated by an unprivileged party outside the normal accounted flow.* In `swap::liquidity_pool`, reserve amounts used for LP-share minting, swap pricing, and the `k` invariant are read directly from the live balances of the pool's internal `FungibleStore`s via `fungible_asset::balance(...)`, and any account can deposit into those stores directly (bypassing `mint`/`swap`) because `fungible_asset::deposit`/`unchecked_deposit` performs no ownership check — only a frozen-flag check.

### Finding Description
`LiquidityPool.token_store_1` / `token_store_2` are ordinary `FungibleStore` objects created with `fungible_asset::create_store` inside `create_token_store` [1](#0-0) . Their owner is the pool's object signer, so only the module can `withdraw` from them (owner-checked) — but **deposit is unauthenticated**. `fungible_asset::deposit_sanity_check` only checks a dispatch flag and the `frozen` bit, never the caller's identity or their relation to the store [2](#0-1) . Because `deposit`/`unchecked_deposit` are `public`, any address holding some of token_1 or token_2 can call `fungible_asset::deposit(token_store_1_or_2, fa)` directly (the store address is readable on-chain from the `LiquidityPool` resource), donating tokens into the pool's reserves without going through `swap` or `mint` — exactly analogous to injecting single-sided liquidity into the Uniswap v3 pool in the source report, bypassing the protocol's intended accounting path.

Every reserve-dependent computation in this module trusts that live balance:
- `get_amount_out` reads `fungible_asset::balance(token_store_1/2)` directly as `reserve_in`/`reserve_out` [3](#0-2) .
- `mint` computes the LP-share ratio from `fungible_asset::balance(store_1)` / `balance(store_2)` as `reserve_1`/`reserve_2`, with `token_1_liquidity = math64::mul_div(amount_1, lp_token_supply, reserve_1)` [4](#0-3) .
- `calculate_constant_k` also reads live balances of the same stores [5](#0-4) .

Attack sequence (classic "donation/inflation attack", enabled here specifically because deposit is un-owner-gated):
1. Attacker creates the pool (or targets a freshly created, near-empty one) and calls `mint` with the minimum amount needed to clear the `MINIMUM_LIQUIDITY` lock, e.g. `amount_1 = amount_2 = 1001`. `lp_token_supply` becomes `1` (attacker LP token), and `1000` MINIMUM_LIQUIDITY LP tokens are permanently locked to the pool object, per the standard first-mint protection [6](#0-5) .
2. Attacker directly calls `fungible_asset::deposit` (or `dispatchable_fungible_asset::deposit`) on `token_store_1` and `token_store_2` with a large amount of token_1/token_2 — no `mint`/`swap` call, no LP tokens issued, no ownership check blocks this.
3. This inflates `reserve_1`/`reserve_2` while `lp_token_supply` stays at `1`.
4. A legitimate LP then calls `mint` with real funds; `math64::mul_div(amount_1, 1, reserve_1_inflated)` rounds down to `0` for any realistic deposit size, tripping `assert!(liquidity_token_amount > 0, EINSUFFICIENT_LIQUIDITY_MINTED)` and reverting [7](#0-6) . If the ratio is instead engineered to survive the assert (attacker donates a smaller multiple), the victim receives a share of LP tokens far below their contribution — real fungible assets they deposit are merged into `store_1`/`store_2` (custody-corrupting: their value effectively becomes redeemable disproportionately by the attacker's `1` LP token) while they receive a negligible or zero LP token balance.

This mirrors H-03's mechanic precisely: a cheap, unprivileged, out-of-band manipulation of a balance that a critical custody/allocation function trusts as ground truth, causing either (a) a persistent DoS of the intended operation (mint reverts for anyone attempting to join the pool), or (b) misallocation of deposited value to the wrong holder (donation attack / LP inflation), both of which are non-recoverable for the affected user since they cannot later reclaim their share once merged into the pool's stores that only the module signer can withdraw from.

### Impact Explanation
- Any user attempting to add liquidity to an attacker-poisoned pool can be permanently blocked (`EINSUFFICIENT_LIQUIDITY_MINTED` DoS), or worse, can have their deposited fungible assets absorbed into the pool while receiving a corrupted (near-zero) LP token allocation — a direct transfer of custody value to the attacker's existing LP position. This satisfies "Supply or custody accounting corruption that moves value to the wrong holder" and "Permanent lock or non-recoverable loss of object-held ... value" from the impact gate, because deposited funds sit in stores that only the pool's own signer (via `withdraw`) can move, and the victim's under-minted LP tokens can never recover the deposited share.
- The attack cost is limited to the amount donated (which is not returned to the attacker, similar to how H-03's attacker sacrifices a swap/mint cost), but it can be executed against any freshly created pool for negligible capital relative to the damage caused to subsequent depositors.

### Likelihood Explanation
This is a well-known "vault/AMM donation/inflation" pattern (same family as ERC-4626 inflation attacks), and here it is directly enabled because `fungible_asset::deposit`/`unchecked_deposit` in `aptos_framework::fungible_asset` [8](#0-7)  impose no caller/ownership restriction — any signer or module holding the relevant FA can call it on any store address. Because `swap::liquidity_pool` reads reserves straight from `fungible_asset::balance` rather than maintaining an internally-tracked reserve counter (as, notably, `bonding_curve_launchpad::liquidity_pairs` correctly does via its own `fa_reserves`/`apt_reserves` fields [9](#0-8) ), it is directly exposed. Note this module lives under `aptos-move/move-examples/`, i.e. reference/example code rather than `aptos-framework` core, which lowers direct mainnet blast radius but the pattern is a genuine, reusable example that downstream protocols may adopt as-is.

### Recommendation
- Do not derive LP-share ratios or swap pricing from live `fungible_asset::balance` of stores that any external caller can deposit into unauthenticated. Track reserves in an internal, mint/swap-only-updated counter (as `liquidity_pairs::LiquidityPair.fa_reserves/apt_reserves` already does), and reconcile against actual balance only defensively (e.g., sweep excess donations into fees rather than letting them corrupt the pricing/ratio math).
- Alternatively, add a minimum acceptable LP-token-per-deposit check (slippage protection) enforced at the protocol level so a mint that would yield disproportionately low LP tokens reverts loudly instead of silently accepting the donation-skewed ratio, and provide a permissioned or otherwise reserve-gated way to sweep unauthorized excess deposits.

### Proof of Concept
Conceptual PoC (Move pseudocode) building on `create`/`mint` in `liquidity_pool.move`:
```
// 1. Create pool between FA_A and FA_B (attacker or existing pool).
let pool = liquidity_pool::create(fa_a_metadata, fa_b_metadata, false);

// 2. Attacker becomes the first LP with the minimal amount to clear MINIMUM_LIQUIDITY.
liquidity_pool::mint(attacker, fa_a(1001), fa_b(1001), false); // lp_token_supply == 1

// 3. Attacker reads token_store_1/token_store_2 addresses from the on-chain
//    LiquidityPool resource, then donates directly, bypassing mint/swap:
fungible_asset::deposit(token_store_1, attacker_owned_fa_a(1_000_000_000));
fungible_asset::deposit(token_store_2, attacker_owned_fa_b(1_000_000_000));

// 4. Victim LP attempts to add proportional liquidity with real funds:
liquidity_pool::mint(victim, fa_a(1_000), fa_b(1_000), false);
// token_1_liquidity = mul_div(1000, 1, ~1_000_001_001) == 0
// -> aborts with EINSUFFICIENT_LIQUIDITY_MINTED, or if amounts are tuned to
//    avoid the abort, victim receives a disproportionately small (or zero)
//    LP allocation relative to the real value they deposited into
//    token_store_1/token_store_2.
```
This cannot be directly executed/verified against a live network from this analysis (no test harness run), so the exact numeric thresholds for triggering the assert vs. silently under-minting should be confirmed with a Move unit test in `aptos-move/move-examples/swap/sources/tests/liquidity_pool_tests.move` before relying on this finding for a fix.

```text
    inline fun calculate_constant_k(pool: &LiquidityPool): u256 {
        let r1 = (fungible_asset::balance(pool.token_store_1) as u256);
        let r2 = (fungible_asset::balance(pool.token_store_2) as u256);
        if (pool.is_stable) {
            // k = x^3 * y + y^3 * x. This is a modified constant for stable pairs.
            r1 * r1 * r1 * r2 + r2 * r2 * r2 * r1
        } else {
            // k = x * y. This is standard constant product for volatile asset pairs.
            r1 * r2
        }
    }
```
