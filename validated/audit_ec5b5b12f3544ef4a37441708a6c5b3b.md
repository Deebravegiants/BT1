## Finding

### Title
Unsafe low-level ERC20 `transfer` calls in Tron IntentGatewayV2 ignore return value, allowing escrow accounting to be finalized without tokens actually moving - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron fork of `IntentGatewayV2` uses raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` for outbound escrow payouts in `withdraw()` and dust sweeping, checking only that the call didn't revert (`success`) but never decoding/validating the returned boolean. This is the exact "unsafe ERC20 transfer" pattern flagged in the referenced report, and is especially dangerous here because the mainline EVM contract at `evm/src/apps/intentsv2/IntentsBase.sol` correctly uses `SafeERC20.safeTransfer`, while this Tron variant regresses to the unsafe pattern despite also importing `SafeERC20` and using `safeTransferFrom` for inbound transfers.

### Finding Description
In `withdraw()`: [1](#0-0) 
```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```
and for the fee-token payout in the same function: [2](#0-1) 
```solidity
uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
if (fees > 0) {
    address feeToken = IDispatcher(host()).feeToken();
    (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
    if (!success) revert TransferFailed();
    delete _orders[body.commitment][TRANSACTION_FEES];
}
```
and in the `SweepDust` handler: [3](#0-2) 
```solidity
if (token == address(0)) {
    (bool sent,) = req.beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, req.beneficiary, amount));
    if (!success) revert TransferFailed();
}
```

None of these calls check the ABI-decoded `bool` returned by `transfer()`. Per the ERC20/TRC20 spec (and multiple real-world non-compliant tokens on Tron and other chains), a `transfer()` call can return `false` on failure without reverting. A low-level `.call` in that case still reports `success == true` since the call itself did not revert — only the encoded return data (which this code never reads) signals the failure. Consequently the contract proceeds to decrement `_orders[body.commitment][token]` and finalize/emit `EscrowReleased`/`EscrowRefunded`/`DustSwept` even though the beneficiary never received the tokens.

This directly contrasts with the same logic in the non-Tron contract, `evm/src/apps/intentsv2/IntentsBase.sol`, which correctly uses `SafeERC20.safeTransfer`: [4](#0-3) 
```solidity
_orders[body.commitment][token] = escrowed - amount;
if (token == address(0)) {
    _sendValue(beneficiary, amount);
} else {
    IERC20(token).safeTransfer(beneficiary, amount);
}
```

### Impact Explanation
When escrowed tokens on Tron are non-compliant (return `false` instead of reverting on failure — a known behavior class for several TRC20 tokens), a solver's legitimate `RedeemEscrow`/`RefundEscrow` settlement message delivered by any relayer will cause the contract to mark the escrow as released and zero out `_orders[commitment][token]` without the beneficiary actually receiving funds. Because the escrow balance is deleted, the tokens become permanently stuck in the `IntentGatewayV2` contract with no accounting path left to reclaim them — a full loss of user/solver funds. The same applies to the `SweepDust` governance path and the transaction-fee payout, which can silently "burn" tracked fees while funds remain trapped in the contract.

### Likelihood Explanation
This does not require any privileged or malicious actor — it triggers under ordinary operation whenever the escrowed or fee token used with the Tron `IntentGatewayV2` deployment doesn't strictly follow the ERC20 return-value convention (a common occurrence among TRC20 tokens on Tron, historically exemplified by USDT-style tokens). Any relayer delivering a normal, honestly-proven settlement message for such a token reaches this vulnerable code path.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` payout sites in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw()` for both escrow and fee payouts, and the `SweepDust` branch in `onAccept`) with `SafeERC20.safeTransfer`, consistent with the already-imported `SafeERC20` library and with the equivalent logic in `evm/src/apps/intentsv2/IntentsBase.sol`.

### Proof of Concept
1. Deploy a TRC20-style token whose `transfer()` returns `false` on failure (e.g., insufficient balance/blacklist) instead of reverting, and use it as an order's input token in `IntentGatewayV2` on Tron.
2. User calls `placeOrder`, escrowing `amount` of this token (`_orders[commitment][token] = amount`).
3. Solver fills the order on the destination chain; a `RedeemEscrow` `WithdrawalRequest` is relayed back and delivered via `onAccept` → `withdraw()`.
4. If the token's `transfer(beneficiary, amount)` call returns `false` (e.g., contract-level pause, blacklist, or insufficient contract balance due to an unrelated bug) without reverting, `token.call(...)` still returns `success == true`.
5. `withdraw()` proceeds to `_orders[body.commitment][token] -= amount` and emits `EscrowReleased`, permanently finalizing the order despite the beneficiary receiving zero tokens — the tokens remain stuck in the `IntentGatewayV2` contract with no recovery path.
