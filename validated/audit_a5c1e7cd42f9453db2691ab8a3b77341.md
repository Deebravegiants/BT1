### Title
Backend admin config changes (fraud/liveness/QR-validation flags) apply mid-signup with no timelock, isolation, or consistency guarantee - (File: src/brokers/observer.rs, src/config.rs)

### Summary
The management backend acts as an unconstrained "administrator" over orb-core's runtime behavior: it can push a new `Config` at any time, and the orb applies it immediately and globally, with no staging, no timelock, and no isolation from signups that are already in progress. This mirrors the report's bug class ("administrators of contracts can update or upgrade things in the system without warning" / "fee changes take effect immediately") — except here the mutable parameters directly gate fraud detection, age/liveness classification, and QR/identity validation for a specific human signup, not just a numeric fee.

### Finding Description
Every `CONFIG_UPDATE_INTERVAL` (10 seconds), the `Observer` broker's `config_update` spawns a task that downloads the latest backend config and **atomically overwrites** the entire shared `Config` object behind an `Arc<Mutex<Config>>`, with no versioning, no gradual rollout, and no check for whether a signup is currently mid-flight: [1](#0-0) 

This config includes fields that directly control fraud/identity-authorization decisions for a signup, e.g. `fraud_check_engine_config`, `child_threshold` (under-age classification), `ignore_user_centric_signups`, `user_qr_validation_use_full_operator_qr`, and `user_qr_validation_use_only_operator_location`: [2](#0-1) [3](#0-2) 

There is no locking/snapshotting of config for the duration of a single signup pipeline. Different phases of the same signup (`check_signup_conditions`, `proceed_with_biometric_capture`, fraud detection, PCP building) each independently call `orb.config.lock().await` and read whatever value is current at that instant: [4](#0-3) 

Because the biometric pipeline (iris/face capture → fraud check → PCP build → upload) spans multiple seconds and crosses multiple `await` points, and the background config-refresh task can complete and replace the shared `Config` object at any point during that window, a signup that started under one fraud/validation policy can finish under a different one, entirely from the backend operator's unilateral, un-timelocked action — exactly the "bad timing"/"front-running by admin" scenario described in the report (`setOperatorFee`/`setGlobalFee` taking effect immediately, no window for notice).

The comparable code region cited in the report ("Fee changes take effect immediately" — `setOperatorFee`/`setGlobalFee`) has a direct structural analog here: `Config::download_and_store` / `config_update` unconditionally replaces the live config with no two-step/timelocked mechanism, just like the report's flagged setters lacking any staged-commit pattern: [5](#0-4) 

### Impact Explanation
An operator (or a compromised/malicious management-backend session) can change `fraud_check_engine_config`, `child_threshold`, or the QR-validation flags at the exact moment a specific orb is mid-signup for a specific person, causing that in-flight signup to be evaluated under an unintended policy: a signup started while the fraud engine or age check was in a stricter mode could complete after the pipeline reads the freshly downloaded relaxed configuration (or vice versa), producing an unpredictable, non-reproducible fraud/liveness enforcement outcome and inconsistent signup authorization. Because no two orb-core signups execute against a guaranteed-consistent config snapshot, forensic/audit conclusions about "was fraud enforcement active for this signup" become unreliable, and a signup can bypass intended enforcement purely due to unfortunate timing of a backend push — the same "no assurance about the behavior of the action they're about to take" issue flagged in the report.

### Likelihood Explanation
The config refresh happens automatically every 10 seconds for every deployed orb (`CONFIG_UPDATE_INTERVAL`), so the race window recurs constantly and needs no attacker skill beyond controlling (or compromising) the management backend's config API — the same trust level as the "administrator" role in the reference report. No additional user interaction or hardware access is required; this is a pure timing/consistency defect in production code paths reachable on every signup.

### Recommendation
Snapshot (clone) the `Config` once at the start of a signup pipeline and use that fixed snapshot for the entire duration of that signup (fraud checks, QR validation, PCP tiering, age classification), rather than re-reading the shared `Arc<Mutex<Config>>` at each phase. If backend-driven config changes must apply to already-completed downloads immediately, introduce a staged/timelocked rollout for security/fraud-relevant fields (e.g., version the config and only allow orbs to switch to a new fraud/validation policy version at pipeline boundaries, never mid-signup), and log/attach the config version used to the signup's audit record so enforcement state is verifiable after the fact.

### Proof of Concept
1. Orb boots and begins a signup; `orb.config.lock().await` is read in `check_signup_conditions` with `fraud_check_engine_config`/`child_threshold` set to strict values. [6](#0-5) 
2. While the biometric pipeline for this same signup is still running (multiple seconds, several `await` points), the backend pushes an updated config (e.g., relaxes `fraud_check_engine_config` or raises `child_threshold`) via the management API.
3. `Observer::config_update` fires on its 10-second interval, downloads the new config, and replaces the entire shared `Config` object in place with no synchronization with the in-flight signup. [1](#0-0) 
4. A later stage of the *same* signup (e.g., `detect_fraud`/PCP build) re-locks `orb.config` and observes the newly relaxed policy, so the signup completes under a policy that never existed at signup start and that the user/operator had no way to anticipate — reproducing the "administrator changes take effect immediately, no assurance of consistent behavior" bug class from the report.

    /// Downloads the latest configuration from the backend and updates the
    /// shared configuration object.
    pub async fn download() -> Result<Config> {
        let res = backend::config::request().await.map_err(|e| {
            tracing::error!("Config request failed: {:?}", e);
            dd_incr!("main.count.http.config_update.error");
            e
        })?;

        if let Some(config) = Config::from_backend(res) {
            dd_incr!("main.count.http.config_update.success");
            Ok(config)
        } else {
            dd_incr!("main.count.http.config_parse.error");
            Err(eyre!("invalid config"))
        }
    }

    /// Downloads the latest configuration from the backend, updates the shared
    /// configuration object, and stores the updated configuration to the file
    /// system.
    pub async fn download_and_store(config: Arc<Mutex<Config>>) -> Result<()> {
        *config.lock().await = Self::download().await.map_err(|e| {
            tracing::error!("Failed to download config: {:?}", e);
            e
        })?;
        let config_to_store = config.lock().await;
        tracing::info!("Downloaded latest config: {:?}", config_to_store);
        config_to_store.store().await.map_err(|e| {
            tracing::error!("Config downloaded but failed to be stored: {:?}", e);
            e
        })
    }

async fn check_signup_conditions(orb: &mut Orb) -> Result<bool> {
    if let Some(report) = orb.net_monitor.last_report()? {
        // Drop the mutex lock fast.
        let Config { block_signup_when_no_internet, .. } = *orb.config.lock().await;
        if block_signup_when_no_internet && report.is_no_internet() {
            orb.ui.no_internet_for_signup();
            dd_incr!("main.count.signup.result.failure.internet_check", "type:too_slow_to_start");
            return Ok(false);
        }
        if report.is_slow_internet() {
            orb.ui.slow_internet_for_signup();
            dd_incr!("main.count.signup.result.failure.internet_check", "type:too_slow_to_start");
            return Ok(true);
        }
    }
    Ok(true)
}
