### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, `webhook_id`, and `api_version` as trusted attributes taken directly from HTTP headers, but the HMAC signature that `Registry.process` verifies only covers the raw request body. `shop` is therefore never bound to the signature that authenticates the request, breaking the identity binding: `shop attributed to a verified webhook == shop that actually produced the signed body`.

### Finding Description
`Request#hmac` reads the signature from the `hmac-sha256` header, and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated headers with no cryptographic tie to the body or the HMAC: [3](#0-2) 

`Registry.process` validates the HMAC of the body via `Utils::HmacValidator.validate(request)`, and if it passes, immediately forwards `request.shop` (and `request.topic`, `request.body`) to the app's registered handler as trusted `WebhookMetadata`, with no additional check that the `shop` header matches the tenant the body/signature actually originated from: [4](#0-3) 

`HmacValidator.validate` and `validate_signature` compute and compare the HMAC purely against `verifiable_query.to_signable_string` (the raw body) and the secret key — the `shop` header plays no role in the computation or comparison: [5](#0-4) 

Because the signature is computed only over the JSON body, any request with a valid `(body, hmac)` pair for the app's secret is accepted as authentic regardless of what `shop-domain` header accompanies it. This is the exact bug class described in the report: a field acted upon (`shop`, used by the host app to attribute the webhook to a tenant) is not covered by the value that is cryptographically verified (the HMAC only binds the body).

### Impact Explanation
An unprivileged internet user who has legitimate access to one tenant (e.g., installs the app on their own store) can capture a validly-signed webhook `(raw_body, hmac)` pair delivered to the app for their own shop, then replay that exact body+HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it never inspects the header), and `Registry.process` calls the handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain and the attacker-controlled body content. Any host app that uses this gem's documented `shop` field to select which tenant's data to create/update/delete (the intended and expected use per `WebhookMetadata`) will apply attacker-controlled webhook data to another merchant's tenant — a cross-tenant data injection/spoofing condition that meets the "cross-tenant access" impact bar.

### Likelihood Explanation
Likelihood is high for any deployment that follows this gem's documented flow of trusting `Registry.process` + `WebhookMetadata.shop` without independently re-verifying the shop domain against a signed value: an attacker only needs to be a legitimate app-installing merchant on any shop to obtain a valid signed webhook, then can freely swap the `shop-domain` header when replaying it, since the gem provides no protection against this and does not document that `shop` is unauthenticated relative to the HMAC.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the HMAC-verified material, or otherwise cryptographically tie them to the signed body — for example, include the shop domain in the signable string computed by `Utils::HmacValidator`, or independently verify that the `shop-domain` header matches a shop the running process/session is currently authorized to act on before dispatching to the handler. At minimum, document prominently that `shop` in `WebhookMetadata` is not covered by HMAC verification and must not be trusted for tenant attribution without additional validation.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook delivery with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)`.
2. Attacker resends an HTTP request to the app's webhook endpoint with the identical raw body `B` and identical `x-shopify-hmac-sha256: H`, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the headers (`shop` now returns `victim.myshopify.com`) — see `Request#initialize`/`#shop`: [6](#0-5) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (`B`) and compares to `H` — this still succeeds because `B` and `H` are unchanged: [4](#0-3) 
5. The handler is invoked with `WebhookMetadata.shop == "victim.myshopify.com"` and body `B` originally generated for the attacker's own shop, causing the host app to apply attacker-controlled data under the victim shop's identity.
