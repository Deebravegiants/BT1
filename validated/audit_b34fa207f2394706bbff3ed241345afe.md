### Title
Iris eye-side assignment relies on process-channel identity, not on any validated eye-side field in the estimate output - ([File: src/plans/biometric_pipeline/mod.rs])

### Summary
The bug class in the external report is: a value is assigned to a "slot" (wethReserve/tokenReserve) based on an assumed/positional mapping instead of validating the actual returned identity against the expected one. In `biometric_pipeline::Plan::run`, the same pattern occurs: the left/right iris result is assigned to `iris_left`/`iris_right` purely based on which python-agent channel the message arrived on (`MegaAgentOne` vs `MegaAgentTwo`), with no field in `iris::EstimateOutput` that is checked to confirm the result actually corresponds to the eye that was requested.

### Finding Description
`Plan::run_iris_left` sends an `Iris::Estimate { frame: self.eye_left.clone(), left_eye: true }` to `mega_agent_one`, and `Plan::run_iris_right` sends an `Iris::Estimate { frame: self.eye_right.clone(), left_eye: false }` to `mega_agent_two`: [1](#0-0) 

When results are polled, the code assigns `iris_left` whenever a `mega_agent_one::Output::Iris(iris::Output::Estimate(...))` arrives, and `iris_right` whenever a `mega_agent_two::Output::Iris(iris::Output::Estimate(...))` arrives — i.e., the eye label is derived solely from which channel produced the message, not from any eye-identifying field carried in the output itself: [2](#0-1) 

Unlike the analogous IR-Net capture path, which explicitly validates the model's `perceived_side` against the `target_left_eye` before accepting the frame (`if perceived_side != i32::from(!self.target_left_eye) { ... skip frame ... }`): [3](#0-2) 

the iris pipeline's `EstimateOutput` carries no equivalent `eye_side`/`perceived_side` field that is validated on return: [4](#0-3) 

The `eye_side` string passed into the python `estimate()` call is used only to build the input kwargs; it is never echoed back or cross-checked in the resulting `EstimateOutput`: [5](#0-4) 

This mirrors the reported Uniswap bug class: reserves (here, iris codes) are attributed to a slot (left/right) based on an implicit, unvalidated ordering assumption (which agent channel replied) rather than a value that is actually verified to correspond to that slot.

### Impact Explanation
If `mega_agent_one` and `mega_agent_two` ever mis-route a response (e.g. due to an agent restart/respawn, message reordering, a bug in the IPC dispatch, or a future refactor that changes which agent handles which eye), `iris_left` could silently be populated with the iris template of the right eye and vice versa. Since these templates flow directly into the signup payload (`format_pipeline`/`log_iris_data`) and into the Personal Custody Package, an eye-swap would corrupt the biometric identity being enrolled/matched under the `eye_left`/`eye_right` slots without any error being raised, since there is no independent validation step (unlike the IR-Net capture code) to catch the mismatch before it's committed.

### Likelihood Explanation
Likelihood is low under current, static wiring, since `run_iris_left` always targets `mega_agent_one` and `run_iris_right` always targets `mega_agent_two`, and this is compile-time fixed in this file. The vulnerability is a missing defense-in-depth check (the code trusts channel identity as a proxy for eye identity) rather than an actively exploitable path in the current code, so it would only manifest through an internal agent/IPC defect, not through any external/unprivileged-user-controlled input.

### Recommendation
Add a validated eye-side identifier to `iris::EstimateOutput` (mirroring `ir_net::EstimateOutput::perceived_side`) and check it against the requested `left_eye` before assigning to `iris_left`/`iris_right` in `biometric_pipeline::Plan::run`, so eye attribution depends on a value actually returned/verified by the model rather than solely on which process channel delivered the message.

### Proof of Concept
Not applicable as a runnable exploit: no external/unprivileged-user input can currently redirect a response from `mega_agent_two` into the `MegaAgentOne` match arm (or vice versa) in this codebase; the risk is structural/defense-in-depth (analogous to the reserve-order issue: the value used to determine "which side" is implicit/positional rather than validated), and further verification would require access to the agent dispatch/IPC internals not present in the indexed code.

impl Environment<'_> {
    #[allow(clippy::cast_possible_truncation, clippy::cast_sign_loss)]
    fn estimate(
        &self,
        py: Python,
        frame: &camera::ir::ArchivedFrame,
        left_eye: bool,
    ) -> Result<EstimateOutput> {
        let image = PyArray2::from_owned_array(py, frame.into_ndarray());

        let kwargs = PyDict::new(py);
        if left_eye {
            kwargs.set_item("eye_side", "left")?;
        } else {
            kwargs.set_item("eye_side", "right")?;
        };

        let output: EstimateOutput = self
            .agent
            .call_method("estimate", (image,), Some(kwargs))?
            .extract::<PipelineOutput>()?
            .try_into()?;

        log_iris_data(
            &output.iris_code_shares,
            &output.mask_code_shares,
            &output.iris_code,
            &output.mask_code,
            &output.iris_code_version,
            left_eye,
            "iris agent",
        );
        Ok(output)
    }
