Batch withdrawals with duplicate `assetId` cause `PoaBridge.describeWithdrawal` to misreport the same (status, txHash) for two distinct withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` matches a withdrawal purely by `assetId` via `findMatchingWithdrawal` (`Array.prototype.find`), never using the `WithdrawalIdentifier.index` or `destinationAddress`/`amount` to disambiguate. If a single signed intent contains two PoA withdrawals of the same `assetId` to different `destinationAddress`es, both `WithdrawalIdentifier`s (index 0 and index 1) resolve to the identical matched record, so an integrator polling both via `watchWithdrawal`/`createWithdrawalCompletionPromises` receives the same `txHash` for both, even though only one on-chain transfer occurred for that hash.

### Finding Description
The broken equality is: `describeWithdrawal({index:0, assetId:A, destinationAddress:X}) .txHash` should differ from `describeWithdrawal({index:1, assetId:A, destinationAddress:Y}) .txHash` when X ≠ Y are distinct on-chain transfers, but the code makes them equal.

Code path:
- `PoaBridge.createWithdrawalIdentifier` (poa-bridge.ts:295-311) builds a `WithdrawalIdentifier` per withdrawal, carrying `index`, `withdrawalParams` (including `assetId`/`destinationAddress`), and shared `tx` (the single NEAR intent tx hash for the whole batch).
- `createWithdrawalIdentifiers` (`withdrawal-watcher.ts:80-107`) assigns per-route `index` values (0, 1, ...) but this index is **never propagated to or consumed by** the POA status lookup.
- `describeWithdrawal` (poa-bridge.ts:313-343) calls `getWithdrawalStatusWithRetry` with only `args.tx.hash` (the shared intent tx hash) to fetch `response.withdrawals` (an array, since POA supports multiple withdrawals per tx), then calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` (poa-bridge.ts:319-322).
- `findMatchingWithdrawal` (poa-bridge.ts:418-427) does `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)` — returning the **first** array element whose token matches, regardless of `destinationAddress`, `amount`, or `index`.
- The code's own comment (poa-bridge.ts:409-416) explicitly acknowledges: *"multiple withdrawals of the same token in a single transaction are not supported"* and that the POA API itself doesn't currently support disambiguating them either.

Nothing in `PoaBridge.supports` (poa-bridge.ts:81-106), `validateWithdrawal` (poa-bridge.ts:170-259), or `createWithdrawalIdentifiers` (withdrawal-watcher.ts:80-107) rejects or deduplicates withdrawal batches containing two entries with identical `assetId`. An unprivileged user (or a solver whose params get forwarded by an integrator) can freely construct `withdrawalParams: WithdrawalParams[]` with two entries sharing `assetId: "nep141:zec.omft.near"` but different `destinationAddress`/`amount`, sign it as one `MultiPayload`, and submit it via `sendSignedIntents`/`signAndSendIntent`. Both resulting `WithdrawalIdentifier`s (index 0, index 1) will, when polled through `watchWithdrawal`/`createWithdrawalCompletionPromises`, invoke `describeWithdrawal` and receive the identical matched withdrawal object (and thus identical `status`/`txHash`) as long as `response.withdrawals` contains fewer matching entries than requested indices (e.g., only one entry indexed by the API, or the API returns entries not one-to-one orderable) — which is the exact scenario the code comment admits is unhandled.

### Impact Explanation
An integrator polling per-withdrawal-index status (as encouraged by `createWithdrawalCompletionPromises`, see `sdk.ts:557-609`, and the batch-withdrawal design doc) will observe both index 0 and index 1 report `status: "completed"` with the same `txHash`, attributing the same on-chain transfer to two different destination addresses/amounts. This causes the integrator to credit or refund the second destination based on the first withdrawal's actual on-chain outcome — a status/hash misreport that leads to double-crediting or misattribution of funds to the wrong destination, matching the **High** impact category ("a status or hash misreport making an integrator credit or refund twice"). This is repeatable on every batch withdrawal containing duplicate `assetId`s.

### Likelihood Explanation
Preconditions: attacker (or counterparty whose withdrawalParams an integrator forwards) needs only to submit a single signed intent with ≥2 withdrawal legs sharing the same `assetId` but different `destinationAddress`/`amount`, routed through POA bridge (e.g., `nep141:zec.omft.near`). No special privileges, no admin access, and no reliance on a malicious relayer/RPC — it purely depends on the ability to construct arbitrary multi-leg withdrawal intents, which is a standard, documented SDK capability (batch withdrawals, e.g. "USDC to Solana + BTC refund"). Cost is a single normal transaction; the divergence is deterministic given the current matching logic and reproducible every time an integrator polls two same-asset legs of one batch.

### Recommendation
In `findMatchingWithdrawal`/`describeWithdrawal`, disambiguate matches within `response.withdrawals` using more than `assetId` — e.g., additionally filter/sort by `destinationAddress` and `amount` (fees are equal for same token, preserving relative amount ordering, as the existing comment suggests), and correlate using the `WithdrawalIdentifier.index` positionally against the sorted candidate list, only returning a match when it can be uniquely attributed; otherwise return `status: "pending"` (or a distinct "ambiguous/unsupported" status) rather than silently returning a possibly-wrong match. Alternatively, proactively reject (in `createWithdrawalIntents`/`validateWithdrawal`) batches with duplicate `assetId` on the POA route until the API supports disambiguation, closing the gap entirely rather than leaving it to reporting-time guesswork.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
	}
