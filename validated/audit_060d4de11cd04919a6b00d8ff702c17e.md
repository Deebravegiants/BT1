### Title
Silent u128→u64 truncation in `swap_base_out` amount-in calculation allows attacker to underpay for swap output - (File: `program/src/processor.rs` / `program/src/math.rs`)

### Summary
The `SwapBaseOut` instruction path computes the required input amount as a `U128` value and converts it to `u64` using the raw `.as_u64()` method, which silently truncates to the low 64 bits instead of returning an error when the value exceeds `u64::MAX`. This is analogous to the reported `uint256 -> uint64` unsafe cast: an oversized intermediate value is coerced into a smaller type without a bounds check, corrupting the computed amount.

### Finding Description
In `process_swap_base_out` the amount the user must pay is derived from `Calculator::swap_token_amount_base_out`, which returns a `U128`: [1](#0-0) 

That value is then scaled up to account for fees and coerced to `u64` with `.as_u64()`, which is the raw `uint`-crate accessor that truncates rather than checking bounds (unlike `Calculator::to_u64`, which uses a safe `try_into`): [2](#0-1) 

The truncated `swap_in_after_add_fee` is then used for both the balance/slippage checks and the actual transfer amount, while the full, untruncated `swap.amount_out` is paid out to the user: [3](#0-2) 

Because `swap_token_amount_base_out` computes `amount_in = coin * amount_out / (pc - amount_out)` using `U128` arithmetic with no upper bound enforced before the `.as_u64()` cast, an attacker who controls the pool's reserve ratio (e.g., by creating the pool via `Initialize2` with a very large `coin` reserve and a very small `pc` reserve, or by skewing it there through prior swaps/deposits) can choose `amount_out` close to `total_pc_without_take_pnl` so the denominator is minimal (as low as `1`). This inflates `amount_in` far past `u64::MAX` while staying within `U128` bounds (no `checked_mul`/`checked_ceil_div` panic occurs), and the subsequent `.as_u64()` silently wraps the value down to an attacker-predictable small number. The attacker can then pass the `user_source.amount < swap_in_after_add_fee` and `swap.max_amount_in < swap_in_after_add_fee` checks with a token balance far smaller than economically required, pay only the truncated (tiny) amount into the vault, and still receive the full `swap.amount_out` tokens from the opposite vault.

This differs from the `SwapBaseIn` path, where the analogous `.as_u64()` call in `Calculator::swap_token_amount_base_in` is mathematically bounded (`amount_out < total_pc_without_take_pnl`, guaranteeing the result always fits in `u64`): [4](#0-3) 
`SwapBaseOut`'s amount-in formula has no such bound and is the vulnerable path.

### Impact Explanation
An attacker who can create or skew a pool to an extreme coin/pc ratio can drain pool reserves via `SwapBaseOut` by paying a wrapped/truncated (attacker-selectable, potentially near-zero) input amount while extracting the full intended output amount, resulting in direct theft of pool/LP funds and insolvent pool accounting (vault balances no longer match the constant-product invariant assumed by `AmmInfo`/`state_data.need_take_pnl_*`).

### Likelihood Explanation
Reachable from a single transaction with attacker-chosen `amount_out`/`max_amount_in` calling the public `SwapBaseOut`/`SwapBaseOut2` instruction, and the required extreme reserve ratio can be attacker-engineered at pool creation time (`Initialize2` allows arbitrary initial `coin_amount`/`pc_amount`) or reached via legitimate deposits, both of which are in the unprivileged, in-scope surface. No privileged signer or off-chain component is required.

### Recommendation
Replace the raw `.as_u64()` truncating cast in the `swap_base_out` computation with a checked conversion (e.g. `Calculator::to_u64`, mirroring the safe pattern already used elsewhere in `math.rs`) so that any intermediate `amount_in` exceeding `u64::MAX` causes the instruction to fail with `AmmError::ConversionFailure` instead of silently wrapping. Additionally consider bounding the constant-product `amount_in` formula (or rejecting `amount_out` values that push the denominator below a safe minimum) to prevent pathological reserve ratios from producing oversized intermediate values in the first place.

### Proof of Concept
1. Attacker calls `Initialize2` to create a pool with `coin_amount` near `u64::MAX` (e.g. ~1.8e19) and `pc_amount` small (e.g. 1,000,000), satisfying minimum-liquidity checks.
2. Attacker calls `SwapBaseOut` (PC2Coin or Coin2PC direction depending on which side is skewed) with `swap.amount_out` chosen so `total_pc_without_take_pnl - amount_out == 1` (minimal denominator), computed at: [5](#0-4) 
3. This produces `swap_in_before_add_fee ≈ coin * amount_out` (order of 1e25, ~2^84), which after fee-scaling still exceeds `u64::MAX` but stays under `U128::MAX`, avoiding any `checked_mul`/`unwrap` panic: [6](#0-5) 
4. `.as_u64()` truncates this to its low 64 bits. Attacker precomputes (off-chain) an `amount_out` value whose resulting truncated `swap_in_after_add_fee` is minimal (near 0), then sets `swap.max_amount_in` to that small value and ensures `user_source.amount` covers only that small amount.
5. Both the `InsufficientFunds` and `ExceededSlippage` checks pass with the truncated tiny value: [7](#0-6) 
6. The transfer moves only the tiny truncated amount into the pool vault while the full `swap.amount_out` is paid out to the attacker from the opposite vault: [8](#0-7)

    pub fn swap_token_amount_base_in(
        amount_in: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_out;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_out = pc - coin * pc / (coin + amount_in)
                // => amount_out = ((pc * coin + pc * amount_in) - coin * pc) / (coin + amount_in)
                // => amount_out =  pc * amount_in / (coin + amount_in)
                let denominator = total_coin_without_take_pnl.checked_add(amount_in).unwrap();
                amount_out = total_pc_without_take_pnl
                    .checked_mul(amount_in)
                    .unwrap()
                    .checked_div(denominator)
                    .unwrap();
            }
            SwapDirection::PC2Coin => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)
                // => amount_out = coin * amount_in / (pc + amount_in)
                let denominator = total_pc_without_take_pnl.checked_add(amount_in).unwrap();
                amount_out = total_coin_without_take_pnl
                    .checked_mul(amount_in)
                    .unwrap()
                    .checked_div(denominator)
                    .unwrap();
            }
        }
        return amount_out;
    }
