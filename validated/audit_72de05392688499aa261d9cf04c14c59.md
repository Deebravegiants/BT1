This confirms the finding: the docs explicitly state `Registry.process` "will verify the request did indeed come from Shopify" (`docs/usage/webhooks.md:125`), yet `shop` is read straight from the unauthenticated `shopify-shop-domain` header and handed to the app's handler as authoritative tenant identity.

### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only signs the raw request body, while `ShopifyAPI::Webhooks::Registry.process` treats the caller-supplied `shopify-shop-domain` (or `x-shopify-shop-domain`) header as the authenticated tenant identity and passes it straight to the app's handler. Because the header is not part of the HMAC-verified data, any party who can produce (or capture) one valid `(raw_body, hmac)` pair can replay it with an arbitrary `shop` header value and have it accepted as a legitimately-authenticated webhook for a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` computes `hmac` from the `hmac-sha256` header and validates it via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string`: [1](#0-0) 

`to_signable_string` returns only `@raw_body`: [1](#0-0) 

However, the tenant identity used downstream, `shop`, is parsed from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never mixed into the signed bytes: [2](#0-1) 

`Registry.process` validates only the HMAC of the request, then immediately forwards `request.shop` (attacker-controlled) to the app's registered handler as authoritative shop context: [3](#0-2) 

The `topic`, `webhook-id`, and `api-version` headers have the exact same problem, but `shop` is the security-critical one because it is the tenant/session-lookup key the host application is instructed to trust. The gem's own documentation tells integrators that `Registry.process` "will verify the request did indeed come from Shopify," and that `data.shop` is "The shop domain of the webhook" to be used directly (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [4](#0-3) [5](#0-4) 

This breaks the intended binding `shop-authenticated-by-hmac == shop-used-by-handler`. The HMAC only proves "this body was signed by someone holding `api_secret_key`," not "this body was signed *for shop X*." An attacker who obtains one valid `(raw_body, hmac)` pair — for example, a webhook delivered to their own shop's endpoint, since any merchant installing the app is a legitimate recipient of signed webhooks for their own store — can resend that exact body/HMAC pair to the app's shared webhook endpoint while substituting a different, victim shop's domain in the header. `HmacValidator.validate` will still pass because it only checks the body against the secret, and the handler will process the payload under the victim's identity.

### Impact Explanation
This is a scope/identity check that answers permissively: the HMAC validation is treated as validating shop identity when it does not. Depending on how the host app's handler uses `data.shop` (as documented, to key session/store lookups, enqueue background jobs, or write data), a malicious existing merchant of the app can cause the app to process attacker-supplied webhook bodies under another tenant's identity — a cross-tenant integrity issue. This matches the report's "Critical - cross-tenant access" category, since the vulnerability crosses a tenant boundary using only a captured signature that was never bound to shop identity.

### Likelihood Explanation
Exploitation requires no access to `api_secret_key`: any user who installs the app (a normal, unprivileged flow) will receive legitimately signed webhooks for their own shop and can capture the `raw_body` + `hmac-sha256` value from any webhook topic. They can then replay it to the same public webhook endpoint with a forged `shopify-shop-domain` header. The header-controlled fields are never covered by `to_signable_string`, so this is a deterministic bypass, not a probabilistic one.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, and ideally `topic`, `webhook-id`, `api-version`) in the HMAC-signed material used for verification, or otherwise cryptographically bind them to the signed payload before trusting `request.shop` in `Registry.process`. At minimum, document and enforce that `data.shop` must be cross-checked against a shop that the app has actually installed/registered a webhook for with a matching `webhook_id`/subscription, rather than trusting the header outright.

### Proof of Concept
1. App merchant A installs the app; Shopify sends a legitimately signed webhook to the app's shared endpoint:
   - Headers: `X-Shopify-Hmac-Sha256: <valid HMAC over raw_body>`, `X-Shopify-Shop-Domain: shopA.myshopify.com`, `X-Shopify-Topic: orders/create`
   - Body: `raw_body` (arbitrary order JSON)
2. Merchant A (or anyone who can observe this request, e.g. via their own logging middleware) captures `raw_body` and the `X-Shopify-Hmac-Sha256` value.
3. Merchant A resends the identical `raw_body` and `X-Shopify-Hmac-Sha256` to the same endpoint, but sets `X-Shopify-Shop-Domain: shopB.myshopify.com` (a victim shop).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` — validation succeeds.
5. The handler receives `WebhookMetadata.new(shop: "shopB.myshopify.com", body: <attacker-chosen order data>, ...)` and performs its documented action (e.g. `perform_later(shop_domain: data.shop, webhook: data.body)`) under shop B's identity, even though shop B never sent or authorized this webhook.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
