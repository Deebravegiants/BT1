### Title
Webhook HMAC only covers the raw body, not the `X-Shopify-Shop-Domain` header, allowing cross-tenant shop impersonation - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then trusts the `shop` value taken from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header — a field that is never included in the HMAC-signed data — to identify the tenant passed to the application's webhook handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes/compares the HMAC exclusively against that signable string [2](#0-1) . `Registry.process` then does:
```
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [3](#0-2) 

`request.shop` is read straight from the header without any cryptographic binding to that header: `T.cast(shopify_header("shop-domain"), String)` [4](#0-3) .

The identity binding that should hold is: `shop_bound_by_hmac == shop_delivered_to_handler`. In this gem, only the raw body is bound by the HMAC; `shop`, `topic`, `webhook-id`, and `api-version` headers are unauthenticated inputs that flow directly into `WebhookMetadata` and are used by application code (per the gem's own documented handler contract) to key subsequent authorized actions such as `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [5](#0-4) .

Because a single `api_secret_key` is shared across every shop/tenant that installs the app, any shop that legitimately receives a webhook (i.e., any merchant who installs the app) also legitimately possesses a body + valid HMAC pair signed with that same secret. Since the header carrying the tenant identity is outside the signed data, that same (body, HMAC) pair remains "valid" per `HmacValidator.validate` regardless of which `shop-domain` header accompanies it.

### Impact Explanation
An attacker who controls one shop (or captured one authentic webhook delivery from their own store) can replay that authentic body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value. `Registry.process` will pass HMAC validation (body-only check) and deliver `WebhookMetadata` claiming to be from the spoofed shop to the application's handler, since `request.shop` is trusted without being covered by the signature. Any host application that follows the documented pattern of keying tenant-scoped operations (e.g. looking up/associating data, triggering `shop_domain`-scoped jobs) off `data.shop` is exposed to cross-tenant data confusion/write — matching the "Critical: cross-tenant access" impact bucket, since the tenant boundary (`shop`) is not authenticated by this gem despite being the field used for authorization decisions in its own documented handler contract.

### Likelihood Explanation
Exploitation requires only: (1) installing the app as any shop (an unprivileged, self-service action any merchant/attacker can perform for public/embedded apps), and (2) triggering one webhook delivery for that shop to capture a valid `(raw_body, hmac)` pair, then (3) POSTing that same pair to the target application's webhook route with a forged `shop-domain` header. No access to `api_secret_key`, access tokens, or any other shop's credentials is needed — the vulnerability is entirely in the gem's `Request`/`Registry` design of what the HMAC covers versus what it is subsequently used to authorize.

### Recommendation
Bind the `shop`, `topic`, and `webhook_id` header values into the signed data used for HMAC verification (or otherwise cryptographically tie the header-derived tenant identity to the request), so that `Utils::HmacValidator.validate` fails if any of these values are altered independently of the body. At minimum, document/emit a warning that `request.shop` is unauthenticated and must not be used by consuming applications to make tenant-authorization decisions without an additional out-of-band check (e.g., cross-referencing against a `webhook_id` fetched via an authenticated GraphQL call for that shop).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, obtaining `access_token` and receiving a genuine webhook (e.g. `orders/create`) at the app's registered callback URL, with body `B` and header `X-Shopify-Hmac-Sha256: H` (computed by Shopify over `B` using the shared `api_secret_key`).
2. Attacker crafts a new HTTP POST to the same app webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256: H` (unchanged, still valid because it's still `HMAC(secret, B)`)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - Header `x-shopify-topic`, `x-shopify-webhook-id` optionally forged too.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully [6](#0-5) .
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and matches `H` — validation passes [7](#0-6) .
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` — the app now believes this webhook (and its body content) legitimately originated from `victim-shop.myshopify.com`, even though it never occurred there [8](#0-7) .

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
