### Title
Post-request timeout processing is permanently blocked once the source chain's consensus client is frozen, locking escrowed relayer fees forever - (File: modules/ismp/core/src/handlers/timeout.rs, modules/ismp/core/src/handlers.rs)

### Summary
`pallet-ismp`'s `timeout::handle` reuses the same "consensus client frozen" gate that protects against processing new/malicious requests to also gate the timeout-refund path, which is a permissionless recovery mechanism unrelated to admitting new incoming state.

### Finding Description
When a `PostRequest` dispatched by a user times out, anyone can submit a `TimeoutMessage::Post` with a non-membership proof so the router invokes the module's `on_timeout` and the escrowed relayer fee/state is released back to the sender. Before doing so, `timeout::handle` calls `validate_state_machine(host, timeout_proof.height)` [1](#0-0) . `validate_state_machine` unconditionally asserts the source state machine's consensus client is not frozen via `host.is_consensus_client_frozen(...)` [2](#0-1) .

This check exists to stop a compromised/faulty consensus client from getting new (potentially forged) state commitments accepted, per the documented purpose: "It ensures the consensus client is not frozen" for "preliminary checks for a request or response message" [3](#0-2) . However, `timeout::handle` reuses the exact same gate for the timeout/refund path, which does not admit any new state — it only proves *non*-membership of a request against a state commitment that was already accepted and finalized before the freeze occurred. Freezing is described as irreversible: "The consensus client after successfully verifying the validity of the conflicting views of the network will go into a frozen state... Frozen consensus clients cannot be unfrozen and a new consensus client must be initialized through the `create_client` method instead" [4](#0-3) .

The consequence: any `PostRequest` dispatched from (or destined through) a state machine whose consensus client later gets frozen, and which subsequently times out, can never have its timeout processed — `handle` will revert on the `validate_state_machine` check for that state machine forever, since a frozen client is never un-frozen and its `consensus_state_id` cannot be reused (`create_client` establishes a new one). The escrowed relayer fee (and, in EVM deployments, the payer's locked fee sitting in `EvmHost`'s `_requestCommitments`, released only via `dispatchTimeOut`) is left permanently unreclaimable through the intended timeout-refund path.

This directly parallels the referenced Opus bug: a check meant only to gate *new entries* (new consensus proofs / new incoming requests) is accidentally also applied to the *exit/recovery* path (timeout refunds), and here the freeze is explicitly documented as unrecoverable, making the fund lock permanent rather than merely temporary.

### Impact Explanation
Any user who dispatched a `PostRequest` whose source or destination state machine's consensus client is later frozen by a fraud-proof (`freeze_client`), and whose request subsequently times out, permanently loses access to their escrowed relayer fee/refund. Since freezing a consensus client is explicitly irreversible in this codebase, this is a genuine permanent freezing-of-funds bug rather than a transient DoS, warranting at least medium severity — consistent with the judged severity of the analogous Opus finding, which was rated medium precisely because "it relates to misbehaviour that will arise during an emergency scenario" (here: a fraud-proof freeze event).

### Likelihood Explanation
Freezing of a consensus client via `freeze_client`/fraud-proof is a designed emergency mechanism intended to occur when consensus faults (e.g. double-signing, eclipse attacks) are detected — not a purely theoretical event, and one Hyperbridge explicitly builds tooling (fishermen) to trigger. Any `PostRequest` in flight at that time, or dispatched shortly before the freeze with a timeout that elapses afterward, is very likely to be affected, since request timeout windows are commonly configured in the range of hours to days.

### Recommendation
Split the `validate_state_machine` preliminary check so timeout processing does not require the consensus client to be live. Specifically, in `timeout::handle`, avoid calling the full `validate_state_machine` (which asserts `is_consensus_client_frozen`) for `TimeoutMessage::Post`; instead, fetch the already-stored `state_machine_commitment`/`StateMachineClient` needed only for `verify_non_membership` without re-validating consensus liveness, since the state commitment used for the timeout proof was already accepted (and possibly challenge-period-cleared) prior to any freeze. If some validation is still desired, gate only genuinely new incoming information (new consensus updates / new requests) on `is_consensus_client_frozen`, and let timeouts proceed against previously accepted, un-vetoed state commitments regardless of a later freeze.

### Proof of Concept
1. Dispatch a `PostRequest` from state machine `A` to state machine `B` with `timeout_timestamp = now + 1 hour`, locking a relayer fee in escrow (or in `EvmHost._requestCommitments` on the EVM side).
2. Before the request is delivered or the timeout elapses, an offchain fisherman submits a valid `FraudProofMessage` for `A`'s consensus client; `consensus::freeze_client` marks the consensus client frozen (`host.is_consensus_client_frozen` now returns frozen for that `consensus_state_id`) — see `docs/content/protocol/ismp/consensus.mdx:191-200`.
3. Wait for the request's `timeout_timestamp` to elapse.
4. Submit `TimeoutMessage::Post { requests: [request], timeout_proof }` to `timeout::handle`.
5. Execution reaches `validate_state_machine(host, timeout_proof.height)` at `modules/ismp/core/src/handlers/timeout.rs:50`, which calls `host.is_consensus_client_frozen(...)` in `modules/ismp/core/src/handlers.rs:136` and reverts (frozen client), regardless of the timeout proof's validity.
6. Because the frozen consensus client can never be unfrozen (per the docs), this call will always revert for this state machine going forward, and the sender's escrowed relayer fee is permanently unrecoverable through this path.
