### Title
`Ismp::handle_unsigned` charges a fixed, batch-size-independent weight while looping over an unbounded `Vec<Message>`/`Vec<PostRequest>`, breaking Substrate's weight accounting and enabling block/PoV overload - (File: modules/pallets/ismp/src/lib.rs)

### Summary
`pallet_ismp::Pallet::handle_unsigned` is declared with a static weight of `300_000_000` regardless of how many messages (or how many `PostRequest`s inside a single `RequestMessage`) are submitted, while its execution path (`execute()` → `handle_incoming_message` → `handlers::request::handle`) loops over the entire unbounded batch, performing a storage read/write and an arbitrary module `on_accept` callback per request. This is the same bug class as Sherlock H-9 (unbounded loop that can exceed the resource ceiling of the environment it executes in) — here the ceiling is Substrate block weight/PoV instead of EVM gas.

### Finding Description
`handle_unsigned` is an unsigned, feeless, unprivileged extrinsic: [1](#0-0) 

Its declared weight is a hard-coded constant independent of `messages.len()` or the size of any nested `Vec<PostRequest>`: [2](#0-1) 

The actual execution, `Pallet::execute`, iterates over the full `messages` vector with no cap: [3](#0-2) 

For a `Message::Request`, the request handler further loops over `msg.requests` (a plain, unbounded `Vec<PostRequest>`), doing a receipt lookup, a receipt write, and dispatching to an arbitrary registered module's `on_accept` per request: [4](#0-3) 

Crucially, this same unbounded execution also runs inside `validate_unsigned`, which is invoked by every peer node on every gossiped submission before the extrinsic is even included in a block: [5](#0-4) 

There is no bound anywhere in the call path on the number of `Message`s or the number of `PostRequest`s per `RequestMessage`/`ResponseMessage`/`TimeoutMessage` (the only practical ceiling is the generic Substrate max-extrinsic/max-block-length limit on the SCALE-encoded call, which constrains payload bytes, not execution cost). Because the weight annotation does not scale with batch size, `frame_system::CheckWeight` and the block builder will always account only `300_000_000` weight for this call, no matter how many requests it actually processes and how much real computation (storage accesses, hashing, and arbitrary downstream `on_accept`/`on_timeout`/`on_response` module callbacks) it performs.

### Impact Explanation
Any unprivileged party can submit a single `handle_unsigned` extrinsic containing a `RequestMessage`/`ResponseMessage`/`TimeoutMessage` with a very large number of entries (bounded only by the runtime's max extrinsic/block length, typically several MB, which can still encode thousands of compact `PostRequest`/`GetResponse` entries). Because the pallet reports only a fixed 300M weight for this call:
- The block author's weight accounting under-estimates the true cost of including the extrinsic, allowing it (possibly together with other transactions) to push actual block execution time/PoV far past the intended block weight limit — the direct parachain analog of exceeding the "block gas limit" in the original report, which can stall or degrade block production/import across the network.
- Every honest node performs the same unbounded work again during `validate_unsigned` on receipt/gossip of the extrinsic (before any block inclusion, and for free since it is unsigned/feeless), amplifying the DoS surface to the entire p2p tx-pool layer, not just the block producer.
- Since this call routes into arbitrary registered ISMP modules' `on_accept`/`on_timeout`/`on_response` callbacks per-item, the attacker also controls how expensive each iteration can be made by targeting modules with heavier callback logic.

This directly threatens the availability of message delivery on Hyperbridge/pallet-ismp — the equivalent of "protection buyers won't be covered" in the original report, here "in-flight cross-chain messages cannot be reliably delivered/finalized" if block production/tx validation is degraded by feeless, unbounded batches.

### Likelihood Explanation
High reachability: `handle_unsigned` is explicitly designed to be callable by anyone with no signature and no fee, and accepts a caller-supplied `Vec<Message>` with no length/size validation before or during weight computation. No special privilege, governance, or off-chain component is required — a single crafted extrinsic submitted by any user/relayer triggers the unbounded loop both at gossip/mempool time (via `validate_unsigned`) and at inclusion time (via `handle_unsigned`/`execute`).

### Recommendation
- Replace the static `weight()` function with a `WeightInfo`-benchmarked weight that scales with `messages.len()` and, ideally, the total number of nested requests/responses/timeouts across the batch (similar to how `T::FeeHandler` post-computes actual weight, but that correction happens only after dispatch and cannot inform pre-dispatch weight reservation or transaction-pool validation cost).
- Enforce an explicit, governance-configurable maximum on the number of `Message`s per `handle_unsigned` call and on the number of items (`PostRequest`/`GetResponse`) per individual message, rejecting oversized batches in `validate_unsigned` before any expensive processing occurs.
- Consider making `validate_unsigned` perform cheap structural/size checks (and signature/proof format checks) before invoking full `execute()`, so gossip-time validation cost is bounded independent of the eventual weight charged at inclusion.

### Proof of Concept
1. Construct a single `Message::Request(RequestMessage { requests: <N very small PostRequests>, proof, signer })` where `N` is chosen so the SCALE-encoded call stays under the node's max-extrinsic-length limit but is large enough (e.g., several thousand entries) that processing time/PoV vastly exceeds what `300_000_000` weight represents.
2. Submit it as an unsigned extrinsic via `Ismp::handle_unsigned` (e.g., using the same pattern as `parachain/simtests/src/pallet_ismp.rs`, replacing the single request with a large vector): [6](#0-5) 
3. Observe that `validate_unsigned` executes the full batch (`Self::execute(messages.clone())`) for free on every receiving node, and that once included, `CheckWeight`/block accounting only reserves the fixed 300M weight declared by `weight()`, regardless of the batch's real cost — demonstrating the accounting mismatch that allows resource-limit bypass.

	let commitments = msg

		.iter()
		.map(|post| hash_request::<H>(&Request::Post(post.clone())))
		.collect();
	state_machine.verify_membership(host, commitments, state, &msg.proof)?;

	let mut total_weights = Weight::zero();
	let result = msg
		.requests
		.into_iter()
		.map(|request| {
			let wrapped_req = Request::Post(request.clone());
			let mut lambda = || {
				let cb = router.module_for_id(request.to.clone())?;
				// Re-check the receipt right before dispatch. The up-front pass above
				// runs before any callback executes; a prior request's on_accept in
				// this same batch could have stored a receipt for this request
				// (directly or by re-entering the handler), and we must not invoke
				// on_accept a second time.
				if host.request_receipt(&wrapped_req).is_some() {
					Err(Error::DuplicateRequest { meta: wrapped_req.clone().into() })?
				}
				// Store request receipt to prevent reentrancy attack
				let signer = host.store_request_receipt(&wrapped_req, &msg.signer)?;
				let res = cb.on_accept(request.clone()).map(|weight| {
					total_weights.saturating_accrue(weight);

					let commitment = hash_request::<H>(&wrapped_req);
					Event::PostRequestHandled(RequestResponseHandled {
						commitment,
						relayer: signer,
					})
				});
				// Delete receipt if module callback failed so it can be timed out
				if res.is_err() {
					host.delete_request_receipt(&wrapped_req)?;
				}
				Ok(res)
			};

			let res = lambda().and_then(|res| res);
			res
		})
		.collect::<Vec<_>>();
