### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is trusted from unauthenticated headers while the HMAC only signs the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers that are never included in the HMAC computation. `Registry.process` validates the HMAC and then unconditionally trusts these header-derived fields (in particular `shop`) to build the `WebhookMetadata` passed to the host application's handler, so the tenant identity is not actually bound to the cryptographic signature.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers, which are completely outside the HMAC input: [2](#0-1) 

`Utils::HmacValidator.validate` only ever compares the body signature computed via `to_signable_string` against the `hmac` header, using the single, app-wide `Context.api_secret_key`: [3](#0-2) 

`Registry.process` gates purely on this body HMAC check and then forwards the unauthenticated `request.shop` value straight into `WebhookMetadata`, which the host application uses as the tenant/session key to process the event: [4](#0-3) 

Because `Context.api_secret_key` (the app's `client_secret`) is a single value shared across every shop that has the app installed, any unprivileged internet user who installs the app on their own store can capture a legitimate webhook (or otherwise obtain a body + valid HMAC pair, since the secret is app-wide, not shop-specific) and then replay that exact `raw_body`/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with a victim shop's domain. The HMAC validates successfully because it never covered the shop header in the first place, and the handler receives forged tenant identity (`data.shop`) bound to attacker-chosen body content.

Root cause equality broken: `shop_authenticated_by_hmac == ""` (nothing) vs. `shop_used_as_tenant_key == request.header["shop-domain"]` — the two are never equal/bound, yet the header value is trusted.

### Impact Explanation
This is a cross-tenant identity-binding break: an attacker-controlled `shop` value (unauthenticated) is delivered to the host application as if it were verified, enabling cross-tenant webhook injection/spoofing against any shop, using only knowledge of the shared, app-wide `client_secret`-derived signature obtainable from the attacker's own legitimate install. This matches the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Any user who can install the app to their own store (a normal, unprivileged action for any Shopify merchant) can trivially capture a body+HMAC pair signed with the app's `client_secret` and replay it with a forged `shop` header value, since the header is not covered by the signature. No secret material beyond what a legitimate installer already legitimately possesses (their own webhook deliveries) is required.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed material, or otherwise cryptographically bind the header-derived `shop` to the signed payload (e.g., re-deriving/confirming shop identity from data embedded in the signed JSON body rather than trusting the `x-shopify-shop-domain` header verbatim) before constructing `WebhookMetadata` in `Registry.process`.

### Proof of Concept
1. Attacker installs the app on their own store `attacker-shop.myshopify.com`, receiving genuine webhooks signed with the app's single `client_secret`.
2. Attacker captures a valid `(raw_body, x-shopify-hmac-sha256)` pair from one of their own webhook deliveries.
3. Attacker sends this same `raw_body` and `hmac` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks the body's HMAC.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and dispatches it to the handler, which processes it as an authenticated event for the victim tenant.
