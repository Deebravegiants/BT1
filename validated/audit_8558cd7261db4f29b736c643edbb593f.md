### Title
Batch withdrawal status reported for the wrong leg when multiple withdrawals share the same `assetId` in `PoaBridge.describeWithdrawal` - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal()` resolves the on-chain status of a specific withdrawal leg by matching the POA Bridge API response only on `assetId`, ignoring the leg's `index`/amount/destination. When a single NEAR transaction contains multiple withdrawal legs of the same token (a legitimate use of the SDK's batch withdrawal support), every leg's status query resolves to the *same* matched withdrawal record, so a "completed" status (and its `transfer_tx_hash`) for one leg gets reported for a different, unrelated leg.

### Finding Description
`IntentsSDK.signAndSendWithdrawalIntent`/`createWithdrawalCompletionPromises` support batching multiple `WithdrawalParams` into a single NEAR transaction [1](#0-0) , and `createWithdrawalIdentifiers` assigns each leg an `index` and a `Bridge` instance, then `watchWithdrawal` polls `bridge.describeWithdrawal({...wid})` independently per leg [2](#0-1) .

For `PoaBridge`, `describeWithdrawal` fetches all withdrawals for the shared `tx.hash` and then calls `findMatchingWithdrawal`, which matches purely by `assetId` (`nep141:${w.data.near_token_id}`), never using `index`, `amount`, or `destinationAddress`: [3](#0-2) [4](#0-3) 

The code comment explicitly acknowledges the limitation: "multiple withdrawals of the same token in a single transaction are not supported." [5](#0-4)  The same pattern (and same disclaimer) is duplicated in `internal-utils`'s `waitForWithdrawalCompletion` helper: [6](#0-5) 

This breaks the equality "status/hash reported == the on-chain outcome for *that specific* withdrawal leg." If two legs of a batch withdrawal use the same `assetId` (e.g., two different amounts/destinations of the same token in one transaction — a scenario the batching API otherwise permits), the first matched `withdrawals[]` entry returned by the POA Bridge API will be reported as the status/txHash for *both* legs' `describeWithdrawal` calls, regardless of which leg actually completed.

### Impact Explanation
This maps to the "status or hash misreport making an integrator credit or refund twice" High-impact category. An integrator relying on `waitForWithdrawalCompletion`/`watchWithdrawal` per leg could:
- Observe both legs reported "completed" with the identical `txHash`, even though only one on-chain transfer actually happened — leading to a double credit/settlement on the integrator side for what is actually a single transfer.
- Or have the wrong leg's completion (wrong amount) attributed to a different leg, causing incorrect reconciliation.

### Likelihood Explanation
Likelihood depends on how often a caller submits a batch withdrawal with two+ legs of the exact same `assetId` in one call. The SDK's public batch API (`signAndSendWithdrawalIntent` with an array of `WithdrawalParams`) does not prevent or warn against this, and nothing in `createWithdrawalIntents`/`estimateWithdrawalFee` rejects duplicate-`assetId` legs for the PoA bridge route. The condition is caller-controlled input (no malicious relayer/bridge required) — an integrator just needs to withdraw the same PoA-bridged token twice in one batch, which is a normal, foreseeable usage pattern rather than an adversarial one.

### Recommendation
Disambiguate withdrawals within the same transaction beyond `assetId` — e.g., match by `(assetId, amount)` pairs sorted consistently between the SDK-side `withdrawalParams` list and the API's `withdrawals` list (as the existing comment suggests), or have the POA Bridge API return/accept an explicit index/ordinal so each `describeWithdrawal` call can bind to the correct on-chain leg. At minimum, `PoaBridge.supports`/`validateWithdrawal`/`createWithdrawalIntents` should detect and reject (or explicitly warn about) batches containing duplicate `assetId` legs until proper disambiguation is implemented, to avoid silently misreporting completion status.

### Proof of Concept
1. Caller invokes `sdk.signAndSendWithdrawalIntent({ withdrawalParams: [ {assetId: "nep141:usdt.omft.near", amount: 100n, destinationAddress: A}, {assetId: "nep141:usdt.omft.near", amount: 200n, destinationAddress: B} ], feeEstimation: [...] })`, producing one NEAR tx with two `ft_withdraw` legs for the same token.
2. `createWithdrawalIdentifiers` creates two `WithdrawalIdentifier`s, index 0 and 1, both routed to `PoaBridge`, sharing `tx.hash`.
3. `watchWithdrawal` polls `PoaBridge.describeWithdrawal` independently for each `wid`. Internally, `getWithdrawalStatusWithRetry` fetches all withdrawals under `tx.hash`; `findMatchingWithdrawal(response.withdrawals, "nep141:usdt.omft.near")` returns the same array element (e.g., the first `COMPLETED` one with `transfer_tx_hash = "0xLegA"`) for both calls, regardless of `index`.
4. Both `watchWithdrawal` promises resolve to `{status: "completed", txHash: "0xLegA"}`, even though only leg targeting `A` for `amount=100` actually completed while leg targeting `B` for `amount=200` may still be pending or use a different destination tx hash.

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

/**

function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,

	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
