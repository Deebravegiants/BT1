### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, while the `shop` (and `topic`/`api-version`/`webhook-id`) values are read from separate, unsigned HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then forwards the unauthenticated `shop` header value straight into `WebhookMetadata`, which host applications use to attribute the webhook to a specific merchant/tenant. Because the app's `client_secret` (the HMAC key) is identical for every shop that installs the app, any merchant who has legitimately received one authentic webhook (valid body + HMAC) can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header, and the signature check still passes. This breaks the intended binding `hmac_valid(body) == shop_authenticated(shop_header)`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from a header that plays no part in that signable string: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` and then trusts `request.shop` (and other headers) to build the metadata handed to the app's webhook handler: [3](#0-2) 

`HmacValidator.validate` only ever checks `verifiable_query.hmac` against `verifiable_query.to_signable_string`, i.e. the body — never the shop, topic, or webhook-id headers: [4](#0-3) [5](#0-4) 

Because the same app-level `client_secret` HMAC key is shared across every shop that installs the app, a merchant (an "unprivileged internet user" relative to any other tenant of the same app) who has captured one genuine webhook delivery for their own shop can resend that identical body with the same valid `x-shopify-hmac-sha256` value, but with `x-shopify-shop-domain` changed to point at a victim shop. `HmacValidator.validate` will still return `true` because it never inspects the `shop` header, so `Registry.process` will dispatch the handler with `WebhookMetadata#shop` set to the victim's domain while the signature only proves the body's authenticity, not the shop attribution.

The equality that should hold but doesn't: `shop_header == shop_bound_by_hmac`. In reality, `shop_header` is fully attacker-controlled while `shop_bound_by_hmac` doesn't exist — the HMAC binds only the body bytes.

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata#shop` (as documented/intended) to select per-tenant state — e.g., looking up the session/access token for that shop, updating that shop's order/inventory records, or deciding which tenant's data the webhook body applies to — can be made to process a validly-signed payload under the wrong tenant's identity. This is a cross-tenant confusion: a low-privilege actor (any merchant who installed the app) can inject webhook events attributed to a different merchant's store, since the shop identity is trusted without being part of the cryptographic proof. This matches the Critical "cross-tenant access" impact class.

### Likelihood Explanation
Exploitation requires only: (1) installing the app as an ordinary merchant (no elevated privilege), (2) triggering or capturing one legitimate webhook delivery for one's own store, and (3) resending that exact body/HMAC with a modified `shop-domain` header to the app's public webhook endpoint. No access to `api_secret_key`, tokens, or any other tenant's credentials is required — the attacker only ever uses their own valid signature.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-covered signable content, or otherwise cryptographically bind the `shop` header to the signed body (e.g., require the caller to pass the expected shop and compare it against a shop value carried inside the signed payload rather than a bare header). At minimum, `Registry.process`/`Request` should not treat the `shop-domain` header as trustworthy on its own for tenant-sensitive operations; document that host applications must independently verify shop ownership (e.g., against a known list of installed shops) before using `WebhookMetadata#shop`.

### Proof of Concept
1. App merchant A installs the app; Shopify sends a webhook to the app's endpoint with headers `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw body B>`, and body `B`.
2. Attacker (merchant A) captures this exact `(headers, body)` pair.
3. Attacker resends the same body `B` and the same `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` (`Request#to_signable_string`) and compares it to the header value — this succeeds because the body and HMAC are unchanged.
5. `Registry.process` dispatches the registered handler with `WebhookMetadata.new(..., shop: "shop-victim.myshopify.com", body: parsed_body, ...)`, causing the app to process/attribute the payload as if it legitimately came from `shop-victim`, despite the signature never having certified that binding.
