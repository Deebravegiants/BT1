### Title
Webhook shop-domain (and topic/webhook-id) headers are trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes/verifies the HMAC over the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers and passed straight through to the app's webhook handler. Because Shopify signs webhooks with the app's single shared `client_secret` (not a per-shop secret), a valid `(body, hmac)` pair from one tenant can be replayed with a forged `shop` header claiming to be a different tenant, and `HmacValidator.validate` will still return true.

### Finding Description
`HmacValidator.validate` verifies `verifiable_query.to_signable_string` against the HMAC header: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only the raw body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are parsed straight from headers and are not part of the signed string at all: [3](#0-2) 

`Registry.process` validates only the HMAC and then dispatches the handler using the unauthenticated `request.shop`/`request.topic`/`request.webhook_id` fields as-is: [4](#0-3) 

This breaks the identity binding `hmac_signed_bytes == authenticated_shop`. The HMAC only proves "this body was produced with knowledge of the app's `client_secret`" — it does not prove "this body originated from shop X." Since Shopify uses one `client_secret` per app shared across every installed shop, any tenant that has the app installed can legitimately obtain a valid `(raw_body, x-shopify-hmac-sha256)` pair for their own store's webhook traffic (by simply receiving a real webhook), then replay that exact body/HMAC pair to the app's webhook endpoint while substituting `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` hands the handler a `WebhookMetadata` claiming `shop: <victim-shop>` with attacker-controlled body content.

### Impact Explanation
This is a cross-tenant identity-binding failure: `desc.effectiveOutputAmount`-style acceptance of an unchecked field is analogous here — the `shop` field acted upon by the handler is not covered by the same integrity check (HMAC) that gates acceptance of the request. Any app built on this gem that trusts `WebhookMetadata#shop` from a webhook handler to select per-shop state (e.g., look up/delete a `Session` for that shop, apply `orders/create`, `app/uninstalled`, or GDPR redact events to that shop's data) can be made to act on forged data attributed to a shop the attacker does not control — an attacker with only their own legitimate app installation (a merchant/unprivileged relative to other tenants) can inject events "as" another shop. This is a cross-tenant boundary violation reachable purely by an attacker who has (or once had) the app installed on any single shop; no leaked credentials or access tokens from the victim are required.

### Likelihood Explanation
Requires only that the attacker have (or has previously had) the app installed on one shop to obtain one valid `(body, HMAC)` pair from real Shopify webhook traffic, and the ability to POST to the app's public webhook endpoint with modified headers — both are within reach of an ordinary unprivileged app user. Exploitability further depends on the specific app's webhook handler trusting the `shop` field for tenant-scoped actions, which is the documented/expected usage pattern of `WebhookMetadata`.

### Recommendation
Bind the tenant/topic identity into the signed payload verification: include `shop`, `topic`, and `webhook_id` in the signable string (mirroring what Shopify actually signs, if it does not already), or otherwise cryptographically bind the header values before they are trusted, rather than only checking body bytes. At minimum, document that `WebhookMetadata#shop`/`#topic` are unauthenticated headers and instruct implementers to cross-check them against a shop known to have that specific `webhook_id` registered (which would require session/webhook_id state, not header trust alone).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, or otherwise triggers a webhook delivery to their own endpoint (or intercepts one, e.g. via a proxy they control that also serves as the app's webhook receiver in a multi-tenant deployment).
2. Attacker captures a legitimate webhook POST: raw body `B`, and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)` — verifiable via `Request#to_signable_string`/`HmacValidator.validate_signature` logic in [2](#0-1)  and [5](#0-4) .
3. Attacker replays the exact same body `B` and `hmac` header `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com` (and, if desired, a different `x-shopify-topic`/`x-shopify-webhook-id`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H` using the shared `client_secret` — see [6](#0-5) .
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: <attacker-controlled parsed body>, ...)`, causing the app to process attacker-controlled data as if it came from `victim.myshopify.com`.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
