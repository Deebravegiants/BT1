Target: `IntentsSDK.signAndSendIntent` and `IntentPayloadBuilder.buildWithSalt`'s `nonce = this.customNonce ?? VersionedNonceBuilder.encodeNonce(salt, deadline, this.customRandomBytes)`. Attacker input: a caller-supplied `args.payload` (an `IntentPayloadFactory`) or a pre-signed `args.signedIntents` array where the same underlying intent primitives are signed twice with a deliberately reused `customNonce` string (via `setNonce`) across two separate `signAndSendIntent` calls before the first is confirmed. Preconditions: same `customNonce` used in both calls, no dedup check for pending nonces in `IntentsSDK`. Call sequence: call 1 `signAndSendIntent({intents, payload: factoryUsingSetNonce('fixedNonce')})` publishes P1; before P1 confirms, call 2 with the same `fixedNonce` (or a factory clone) builds P2 with the same `(nonce, verifying_contract)` pair but different `intents` content (e.g., a different `receiver_id`/amount) and publishes it too; the relayer accepts both since it only rejects duplicate nonces at the contract level, and if P1's transaction hasn't landed yet both may be broadcast, with only one succeeding on-chain but the SDK/caller having no synchronization to know which. Equality broken: SIGNED == BUILT holds per-call, but SINGLE EXECUTION and STATUS TRUTH break at the caller level: the caller cannot know from `IntentPublishResult.intentHash` alone which of the two conflicting payloads with reused nonce actually executed, and may believe both were separately authorized/executed distinct actions. Impact: Critical — one of two materially different signed payloads silently fails on-chain due to nonce reuse while the SDK reports a ticket/hash for both as if both were independently valid publish attempts, risking the caller crediting or refunding both. Proof idea: vitest test mocking relay `publishIntents` to accept both calls (returning two tickets) and NEAR RPC settlement query to show only one nonce-consuming transaction actually succeeded; assert `waitForIntentSettlement` for the losing ticket either hangs or returns a status that the caller could misinterpret as success given the SDK does not cross-check nonce reuse before signing via `setNonce`.
