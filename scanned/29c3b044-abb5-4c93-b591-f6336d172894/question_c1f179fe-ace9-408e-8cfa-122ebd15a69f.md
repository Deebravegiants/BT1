Attacker input: a caller passes to `invalidateNonces({nonces: [...]})` a base64 nonce string crafted so that `bytes.length === 32`, the first 4 bytes equal `VERSIONED_MAGIC_PREFIX`, but `bytes[4]` (version) is a non-zero unrecognized value while the remaining 27 bytes still `deserialize` successfully against `SALTED_NONCE_BORSH_SCHEMA` (schema is version-agnostic, so any 27-byte payload after the prefix+version deserializes as if it were the latest format). Preconditions: none beyond calling the public `invalidateNonces` method with attacker-controlled nonce strings (e.g. a nonce forwarded from an untrusted counterparty for invalidation on the caller's behalf). Equality broken: SINGLE EXECUTION — version byte is never checked against `LATEST_VERSION`, so a differently-versioned/format nonce is silently treated as v0, producing an invalidation transaction whose deadline semantics do not match what the true nonce format intended, allowing an original signed intent under that nonce to remain executable when the caller believed it was properly time-bound for invalidation. Impact: High — malformed deadline computation from an unchecked version byte causes wrong invalidation timing, a signature bound to a nonce is treated inconsistently across encode/decode. Proof idea: vitest test constructing a 32-byte buffer with correct magic prefix, `version=1`, and 27 bytes that happen to validate under `saltedNonceSchema`, calling `decodeNonce` and asserting no error is thrown despite `version !== LATEST_VERSION`, then feeding that nonce through `invalidateNonces` and asserting the computed `deadline` used doesn't match the true intended value.
