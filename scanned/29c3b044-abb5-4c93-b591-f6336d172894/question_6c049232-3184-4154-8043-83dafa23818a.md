Target: `IntentPayloadBuilder.setNonce` (accepts any string) combined with `IntentsSDK.invalidateNonces`'s `builder.setNonce(nonce)` call path. Attacker input: a nonce string supplied to `invalidateNonces` that was never actually derived via `VersionedNonceBuilder.encodeNonce` but is any attacker-chosen base64/opaque string (e.g., a nonce copied from a different signer's prior real transaction, obtained because a counterparty's forwarded `signedIntents` exposed it). Preconditions: caller has their own signer configured; no ownership check exists on `setNonce`'s string value — `IntentPayloadBuilder` never verifies the nonce was generated for `this.signerId`. Call sequence: `sdk.invalidateNonces({nonces: [foreignNonce]})` builds `builder.setNonce(foreignNonce).setDeadline(...)`, signs with the caller's own key via `buildAndSign(intentSigner)`, and publishes an empty intent using someone else's nonce value under the caller's own `signer_id`/`verifying_contract`. Equality broken: SIGNED == BUILT is technically satisfied (payload matches builder state), but SINGLE EXECUTION's binding (nonce, verifying_contract, signer) is violated in effect for the *original* nonce owner: since nonce validity/uniqueness is scoped per signer on the contract, this call is a no-op against the real owner's intent, but the attacker can be misled by the SDK into believing invalidation worked (no error thrown) for a nonce string they don't have signing rights over the correct account for. Impact: High — status/success misreport: `invalidateNonces` resolves without error even though the invalidation had no real effect on the targeted (foreign) nonce, letting an integrator wrongly credit the invalidation as successful.
