### Title
Directory Traversal in `CRE.WorkflowFetcher` HTTP mode allows escaping the configured base path via workflow-owner-controlled `BinaryURL`/`ConfigURL` - (File: `core/services/workflows/syncer/v2/fetcher.go`)

### Summary
`newHTTPFetcher` in `core/services/workflows/syncer/v2/fetcher.go` builds the artifact-fetch URL by joining the operator-configured `CRE.WorkflowFetcher` base URL path with a path derived from the workflow's registered `BinaryURL`/`ConfigURL`. The join uses `filepath.Join`, which normalizes `../` sequences and can walk the resulting path above the intended base path prefix, unlike the sibling `newFileFetcher` function which explicitly validates the final path stays under `basePath`.

### Finding Description
`NewFetcherFunc` selects `newHTTPFetcher` when the operator-configured `CRE.WorkflowFetcher.URL` uses an `http`/`https` scheme [1](#0-0) . Inside `newHTTPFetcher`, the request-supplied `req.URL` is cleaned and joined onto the base URL's path with no post-join boundary check:

```
cleanPath := strings.TrimPrefix(filepath.Clean(req.URL), "/")
...
u.Path = filepath.Join(u.Path, cleanPath)
``` [2](#0-1) 

`filepath.Join` calls `filepath.Clean` on the combined string, which resolves `..` components against the joined result. If `cleanPath` contains enough `..` segments, the resulting path is emptied of the base path's own segments entirely (e.g. base `/base/path` + `../../../etc/passwd` → `/etc/passwd`), so the outgoing HTTP request no longer targets anything under the intended `basePath`. This is the same bug class as CVE-2025-46559 (Misskey `Mk:api`): a `../`-based path is not validated to stay under the intended URL prefix, letting a request reach unintended endpoints on the target host.

By contrast, the file-scheme variant `newFileFetcher` (used for `file://` base URLs) explicitly guards against this by checking the fully resolved path is still prefixed by `basePath` and rejecting it otherwise:
```
if !strings.HasPrefix(fullPath, basePath+string(filepath.Separator)) && fullPath != basePath {
    return nil, fmt.Errorf("request URL %s is not within the basePath %s", fullPath, basePath)
}
``` [3](#0-2) 

This equivalent check is absent from `newHTTPFetcher`, and its comment ("Clean the path to prevent directory traversal") is misleading — cleaning alone does not enforce a boundary.

**Reachability from an unprivileged actor:** `req.URL` is not operator-supplied; it originates from the workflow owner's on-chain registration event and is passed through unchanged:
- `eventHandler.createWorkflowSpec` calls `h.workflowArtifactsStore.FetchWorkflowArtifacts(ctx, wfID, payload.BinaryURL, payload.ConfigURL)` where `payload.BinaryURL`/`payload.ConfigURL` come directly from the `WorkflowRegisteredEvent` [4](#0-3) .
- `Store.FetchWorkflowArtifacts` forwards these URLs into a `ghcapabilities.Request{URL: binaryURL, ...}` and calls `h.fetchFn(...)` [5](#0-4) .
- When the node is configured with `[CRE.WorkflowFetcher] URL = "http://..."` (a supported, documented production configuration — see `docs/CONFIG.md` and `testdata/config-full.toml` showing `URL = 'https://workflow.fetcher.url'`) [6](#0-5) , `fetchFn` resolves to `newHTTPFetcher`'s closure, and `req.URL` (the workflow owner's `BinaryURL`/`ConfigURL`) is what gets joined against the configured base path.

Since any address can register a workflow on the on-chain `WorkflowRegistry` with an arbitrary `BinaryURL`/`ConfigURL`, this is attacker/unprivileged-actor-controlled input reaching the vulnerable join.

### Impact Explanation
An unprivileged workflow-registering actor can craft `BinaryURL`/`ConfigURL` values containing `../` sequences to make the node's outbound artifact-fetch request target paths outside the operator-intended base path on the configured fetch host (e.g. reaching other endpoints/paths hosted on the same host as the workflow-artifact server, rather than the intended `/workflows/...` prefix). This can be used to probe or retrieve content the operator did not intend to expose through this path, or to coerce the node into issuing crafted-path requests to a third-party host if the configured base host serves multiple purposes at different paths. The severity depends heavily on what else is co-located on the configured `WorkflowFetcher` host/port; at minimum it is a boundary-bypass of the developer's explicitly intended "stay under basePath" guarantee (evidenced by the parallel, correctly implemented check in `newFileFetcher` for the `file://` case, and by the test comment "Clean the path to prevent directory traversal" that the http fetcher fails to actually enforce).

### Likelihood Explanation
Likelihood is moderate: it requires (1) the node operator to configure `CRE.WorkflowFetcher.URL` with an `http`/`https` scheme (a supported, documented config, not merely a test-only path), and (2) a workflow registration transaction with a crafted `BinaryURL`/`ConfigURL` containing `../`. Registering a workflow is an unprivileged, permissionless on-chain action for any workflow owner, so the trigger condition (2) is trivially satisfiable by an attacker; condition (1) depends on deployment choice.

### Recommendation
Add the same base-path containment check used in `newFileFetcher` to `newHTTPFetcher`: after computing the joined `u.Path`, verify it is still prefixed by the original base path (`strings.HasPrefix(u.Path, originalBasePath+"/") || u.Path == originalBasePath`) and reject the request otherwise, mirroring the logic at `core/services/workflows/syncer/v2/fetcher.go:229`.

### Proof of Concept
1. Configure a node with:
```
[CRE.WorkflowFetcher]
URL = "http://artifact-host.example.com/workflows"
```
2. As an unprivileged actor, register a workflow on the `WorkflowRegistry` contract with:
```
BinaryURL = "http://artifact-host.example.com/workflows/../../admin/secret"
```
3. When the syncer processes the `WorkflowRegistered` event, `newHTTPFetcher` computes:
```
cleanPath = "../../admin/secret"
u.Path = filepath.Join("/workflows", "../../admin/secret") // => "/admin/secret"
```
4. The node issues `GET http://artifact-host.example.com/admin/secret` instead of a request confined to `/workflows/...`, unlike `newFileFetcher`, which would reject the equivalent traversal with `"is not within the basePath"` (as shown at `core/services/workflows/syncer/v2/fetcher_test.go:443-448`).
