### Title
Unbounded, un-evicted `RequestReplayGuard.seen` map with full-scan cleanup causes linear-cost DoS on every Vault gateway request - (File: core/capabilities/vault/request_replay_guard.go)

### Summary
The Vault gateway/node authorization path uses a single shared `RequestReplayGuard` per `authorizer` instance to prevent replay of authorized requests. Its internal map (`seen map[string]int64`) has no maximum size, and entries are only removed lazily by iterating the *entire* map on every call to `CheckAndRecord`. An attacker who can get arbitrarily many distinct request digests recorded with long expiries can grow this map without bound, forcing every subsequent request (from any caller) through the same authorizer to pay an ever-increasing, unbounded cost to authorize — directly analogous to the `withdrawExcessRewards()` DoS, where cheap attacker-created entries must all be processed/scanned before the shared, gated operation can proceed cheaply.

### Finding Description
`RequestReplayGuard.CheckAndRecord` is called on every authorized Vault request, both for the allowlist-based auth flow and the JWT-based auth flow, from `authorizer.AuthorizeRequest`: [1](#0-0) 

Each call unconditionally does a full linear scan of the `seen` map to purge expired entries before inserting the new digest: [2](#0-1) [3](#0-2) 

The map is keyed by request digest and stores an attacker/caller-influenced expiry timestamp (`expiresAtUnix`) supplied via `authResult.ExpiresAt()`, which originates from the allowlist-based or JWT-based auth result computed per request: [4](#0-3) [5](#0-4) 

There is no cap on `len(seen)` and no eager, independent reaper guaranteed to run frequently enough to offset a sustained flood of unique digests with long-lived expiries — `ClearExpired` exists but is only useful if invoked out-of-band on a schedule, and even then only removes entries whose `expiresAtUnix` has already passed: [6](#0-5) 

Each distinct request the attacker submits (varying any field that changes its digest — e.g., request ID, params, or nonce) creates one more permanent-until-expiry entry. As with the `withdrawExcessRewards()` receipts pattern — where the owner is forced to pay unbounded gas to walk every cheap attacker-created receipt before the privileged operation proceeds — here every unrelated future caller through the shared `authorizer`/`RequestReplayGuard` pays an unbounded, linearly-growing cost (a full map scan) on the hot authorization path, because the attacker's cheap entries must all be iterated (even though only expired ones are deleted) before any request — theirs or anyone else's — can be authorized.

### Impact Explanation
This directly degrades a security-critical, internet/gateway-facing hot path (`HandleJSONRPCUserMessage` → `ProcessRequest` → `AuthorizeRequest` → `CheckAndRecord`) used by the Vault gateway handler: [7](#0-6) 

As the map grows, CPU time and lock hold time (a single `sync.Mutex` guards the whole map) for every legitimate request increases, eventually causing request timeouts/latency spikes or full denial of service for all Vault gateway users on that node, not merely a privileged owner operation as in the original report — an even broader impact surface since the cost is paid on every unprivileged client request rather than a single administrative call.

### Likelihood Explanation
Likelihood depends on whether an unprivileged caller can (a) generate many distinct request digests cheaply and (b) obtain expiries that persist for a meaningful window. Both allowlist-based and JWT-based auth flows compute per-request digests and independently-supplied expiries, and nothing in `CheckAndRecord`/`authorizer.go` rate-limits or bounds the number of distinct digests a single caller can register. Exact bounds on `ExpiresAt()` derivation in `jwt_based_auth.go` / `allow_list_based_auth.go` could not be fully confirmed from the available index; if expiry windows are short (seconds), the practical severity is reduced (bursty but self-clearing), but sustained flooding just below the expiry window still produces a persistently large map and a real DoS risk even in that case.

### Recommendation
- Bound `RequestReplayGuard`'s map size (reject/evict oldest when a cap is exceeded) similar to `maxCacheSize` in `core/services/gateway/handlers/common/requestcache.go`.
- Replace the O(n) full-map scan on every `CheckAndRecord` call with a time-bucketed or heap/TTL-cache based structure so cleanup cost doesn't scale with total accumulated (non-expired) entries.
- Cap the maximum allowed `expiresAtUnix` distance from "now" so a caller cannot keep entries alive indefinitely.
- Consider per-owner/per-caller rate limiting before a request reaches the replay guard, consistent with the pattern already used for other gateway maps (e.g., `checkRateLimit` in the HTTP trigger handler).

### Proof of Concept
1. An attacker with valid (or even minimal) auth capability submits many Vault requests, each with a unique digest (e.g., differing `req.ID`/params) and with `AuthResult.expiresAt` set far in the future (bounded only by whatever validation exists in the JWT/allowlist auth path, which was not found to cap it in `authorizer.go`).
2. Each call to `authorizer.AuthorizeRequest` → `replayGuard.CheckAndRecord` inserts a new, non-expiring entry into `seen`.
3. As `len(seen)` grows unboundedly, every subsequent call — from any user — pays the cost of `clearExpiredLocked`'s full map iteration under the same mutex, degrading latency/throughput for the entire node's Vault gateway traffic.

```go
func (a *authorizer) AuthorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	authResult, err := a.authorizeRequest(ctx, req)
	if err != nil {
		return nil, err
	}
	if authResult == nil {
		err = errors.New("auth mechanism returned nil auth result")
		a.lggr.Errorw("auth mechanism returned nil auth result", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "")
		return nil, err
	}
	if err := a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt()); err != nil {
		a.lggr.Debugw("replay guard rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "", "error", err)
		return nil, err
	}
	if ownerErr := validateSecretOwnersMatchAuthorized(req, authResult.AuthorizedOwner()); ownerErr != nil {
		a.lggr.Errorw("owner binding rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "hasAuth", req.Auth != "", "error", ownerErr)
		return nil, ownerErr
	}
	a.lggr.Debugw("request authorized", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "")
	return authResult, nil
}
```

```go
func (a *authorizer) authorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	// Requests without req.Auth continue using the allowlist-based path for backwards compatibility.
	// Existing clients do not populate the auth field yet, so treating an empty value as JWT would break them.
	if req.Auth == "" {
		return a.authorizeAllowListBasedAuth(ctx, req)
	}
	return a.authorizeJWTBasedAuth(ctx, req)
}

func (a *authorizer) authorizeAllowListBasedAuth(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	if a.allowListBasedAuth == nil {
		err := errors.New("AllowListBasedAuth authorizer is nil")
		a.lggr.Errorw("AllowListBasedAuth unavailable", "method", req.Method, "requestID", req.ID, "error", err)
		return nil, err
	}
	return a.allowListBasedAuth.AuthorizeRequest(ctx, req)
}
```

```go
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
```

```go
func (g *RequestReplayGuard) clearExpiredLocked() {
	now := g.nowFunc().UTC().Unix()
	for digest, expiry := range g.seen {
		if now > expiry {
			delete(g.seen, digest)
		}
	}
}
```

```go
	}

		// Public key requests don't require authorization,

		// Note we cache this value quite aggressively so don't need to worry about DoS.

			ar, err := h.newActiveRequest(req, callback)
			if err != nil {
```
