Attacker action: none needed beyond triggering any of the unsanitized-shop call sites above (webhook header spoof, OAuth callback, JWT dest) - the point is structural. Preconditions: any caller of `Session.new`/`Session.from`. Call sequence: neither constructor calls `ShopValidator.sanitize!` or `sanitize_shop_domain` on `shop`; `@id` is built purely from whatever `shop`/`id` was passed, and `@shop` is stored verbatim as the attr_accessor used later by `HttpClient`. Binding: `shop stored in every Session == shop that was authenticated at the point of creation`, which the gem provides no mechanism to verify, since `Session` itself performs zero validation and trusts every caller equally whether or not that caller sanitized. Scoped impact: Critical - because there is no single choke point, any future or existing caller (webhook handler storing a session per shop, JWT-based lookup, custom app session per `docs/usage/custom_apps.md`) can silently store a `Session` object keyed to and pointed at an unauthenticated shop string, and no other part of the gem (not `HttpClient`, not `SessionUtils`) will ever detect the divergence. Proof idea: minitest asserting `ShopifyAPI::Auth::Session.new(shop: 'anything-not-a-real-shop').shop` succeeds with no exception and no call to `ShopValidator`, contrasted with `ClientCredentials.client_credentials` which does raise `InvalidShopError` for the same string.
