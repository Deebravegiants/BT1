### Title
Unconditional Debug-level logging of the full JSON-RPC request — including the raw JWT bearer credential (`req.Auth`) — before authentication/validation completes ([File: core/services/gateway/handlers/vault/handler.go])

### Summary
The Vault gateway handler logs the entire incoming JSON-RPC request object at `Debug` level immediately upon receipt, before any authentication or parameter validation is performed. Because the JSON-RPC request struct carries the caller's bearer JWT in its `Auth` field, this credential is captured verbatim in application logs for every request that reaches the handler — valid or malformed, authorized or not. This mirrors the root cause of CVE-2019-14858: sensitive data that should only ever be exposed after validation/redaction logic runs is instead emitted unconditionally at the top of request handling, before the code paths that are supposed to guard it (authorization, later-added redaction) get a chance to execute.

### Finding Description
`HandleJSONRPCUserMessage` in `core/services/gateway/handlers/vault/handler.go` performs a small amount of ID sanity-checking, then immediately logs: [1](#0-0) 

```go
func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 { ... }

	h.lggr.Debugw("handling vault request", "method", req.Method, "requestID", req.ID, "request", req)
```

`req` is a `jsonrpc.Request[json.RawMessage]`, which carries an `Auth` field populated with the caller-supplied JWT bearer token (used for `vault.secrets.*` JWT-based authorization), as shown throughout the JWT auth code paths: [2](#0-1) , and in test helpers that explicitly set `req.Auth = jwtToken` before this token is ever validated: [3](#0-2) .

Authentication/authorization and structural validation only happen afterwards, inside `h.requestProcessor.ProcessRequest(...)`: [4](#0-3) . This is the same ordering problem as the Ansible CVE: the "sensitive" field (there, `no_log` sub-parameters; here, the bearer JWT) is logged/emitted before the validation logic that is supposed to gate or redact it has run — so an attacker sending intentionally malformed params, or an operator simply running with `Debug` logging enabled (a common production/troubleshooting configuration), captures the caller's live authentication token in the log stream regardless of whether the request is ultimately authorized.

The codebase clearly recognizes this bug class elsewhere and has taken remedial action for a narrower case — the "invalid params" error path was explicitly hardened and tested to *not* leak raw params: [5](#0-4) 
and the error-response logger for `InvalidParamsError` deliberately logs only `err.Error()`, not the full request: [6](#0-5) .

However, the pre-authorization `Debugw("handling vault request", ..., "request", req)` call at line 403 is not covered by that test (which only observes `zapcore.InfoLevel` and above) and still logs the complete request object — including the still-unvalidated `req.Auth` JWT — for every single inbound request.

Note: `jsonrpc.Request` is defined in the external `chainlink-common` module (`github.com/smartcontractkit/chainlink-common/pkg/jsonrpc2`), which is not indexed in this repo, so it was not possible to confirm from this codebase whether that type implements a custom `String()`/`MarshalLogObject()` that redacts the `Auth` field before it reaches the zap sink. If no such redaction exists in that struct (the JWT test helpers treat `Auth` as a plain string field), the token is logged in the clear.

### Impact Explanation
A leaked JWT bearer token for the Vault gateway allows request impersonation: any actor who can read the gateway's application logs (log aggregation systems, sidecar log shippers, support/debug tooling, or an attacker with read access to node logs) can replay the captured token to authorize `vault.secrets.create/update/delete/list` operations as the original caller, within the token's validity window and the digest binding it carries. This is a credential/secret disclosure that can lead to unauthorized secret creation, mutation, deletion, or enumeration for the impersonated workflow owner/organization — squarely within the "concrete authentication bypass / key-secret disclosure / request impersonation" acceptance criteria.

### Likelihood Explanation
The log statement executes unconditionally on every request that reaches `HandleJSONRPCUserMessage`, with no dependency on the request being malformed, unauthorized, or otherwise anomalous — it fires before any gating logic. The only precondition for exploitation is that `Debug`-level logging is enabled for the gateway/vault handler (a very common operational setting for a service that is still under active hardening, as evidenced by the adjacent redaction tests), and that the attacker has some means of reading logs (log-shipping misconfiguration, compromised log storage, or insider access). This is a lower bar than exploiting cryptographic or authorization logic directly, making it a realistic and often-overlooked leakage vector, consistent with the "Medium" severity of the underlying CVE-2019-14858 analog.

### Recommendation
Move or remove the unconditional pre-authorization `Debugw("handling vault request", ..., "request", req)` log call so that it no longer serializes the entire request object (and thus the JWT in `req.Auth`). At minimum: log only non-sensitive fields (`method`, `requestID`, `hasAuth: req.Auth != ""`), matching the pattern already used correctly elsewhere in the same package (e.g. `"hasAuth", req.Auth != ""` in `core/capabilities/vault/authorizer.go`). If full-request debug logging is needed for troubleshooting, redact/zero the `Auth` field (and any raw ciphertext params) before logging, and extend the existing `TestVaultHandler_InvalidParamsDoesNotLogRawParams`-style test to also assert no JWT/Auth material appears in logs at `Debug` level for both valid and invalid requests.

### Proof of Concept
1. Enable `Debug` level logging for the gateway/Vault handler (a supported, non-privileged operational configuration).
2. Send any JSON-RPC request to `vault.secrets.create` (or any gateway secrets method) with `Authorization: Bearer <jwt>` set, using a validly-formed or even a soon-to-be-rejected `req.Auth` token.
3. Observe that `handler.HandleJSONRPCUserMessage` logs `"handling vault request", "request", req` at line 403 — before `ProcessRequest` performs authorization — capturing the full `req` struct including the caller's `Auth` JWT into the log stream, regardless of whether the request later fails authorization or validation.
4. Anyone able to read this log line can replay the captured JWT (subject to its expiry/digest binding) to impersonate the original caller for Vault secret operations.

func TestVaultHandler_InvalidParamsDoesNotLogRawParams(t *testing.T) {
	t.Parallel()

	// Observed at Info level so the pre-existing whole-request Debug log is excluded.
	lggr, logs := logger.TestObserved(t, zapcore.InfoLevel)
	h, callback, don, _ := setupHandlerWithLogger(t, lggr, limits.Factory{Settings: cresettings.DefaultGetter})
	// Don't expect SendToNode to be called for invalid params
	don.AssertNotCalled(t, "SendToNode")

	const marker = "SENSITIVE_MARKER_123"
	invalidParams := json.RawMessage(`{"request_id":"req-1","injected":"` + marker + `"}`)
	req := jsonrpc.Request[json.RawMessage]{
		ID:     "invalid-params-logs",
		Method: vaulttypes.MethodSecretsCreate,
		Params: &invalidParams,
	}

	// The invalid-params response is sent synchronously, so no goroutine is needed.
	err := h.HandleJSONRPCUserMessage(t.Context(), req, callback)
	require.NoError(t, err)

	resp, err := callback.Wait(t.Context())
	require.NoError(t, err)
	var secretsResponse jsonrpc.Response[vaultcommon.CreateSecretsResponse]
	require.NoError(t, json.Unmarshal(resp.RawResponse, &secretsResponse))
	assert.Equal(t, req.ID, secretsResponse.ID, "Request ID should match")
	assert.Equal(t, api.ToJSONRPCErrorCode(api.InvalidParamsError), secretsResponse.Error.Code, "Error code should match")

	invalidParamsLogs := logs.FilterMessage("invalid params")
	entries := invalidParamsLogs.All()
	require.Len(t, entries, 1, "expected exactly one 'invalid params' log entry")
	assert.Equal(t, zapcore.ErrorLevel, entries[0].Level)
	assert.Equal(t, req.ID, entries[0].ContextMap()["requestID"])
	assert.NotContains(t, entries[0].ContextMap(), "params", "raw params must not be logged")

	for _, e := range logs.All() {
		assert.NotContains(t, e.Message, marker)
		for k, v := range e.ContextMap() {
			if s, ok := v.(string); ok {
				assert.NotContains(t, s, marker, "log field %q must not contain raw request params", k)
			}
		}
	}
