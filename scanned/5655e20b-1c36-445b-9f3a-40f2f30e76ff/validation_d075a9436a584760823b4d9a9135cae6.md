### Title
Unauthenticated `/v2/resume/:runID` endpoint allows any unprivileged client to inject arbitrary results into another job's pending pipeline task - (File: core/web/router.go, core/web/pipeline_runs_controller.go)

### Summary
The Chainlink node exposes `PATCH /v2/resume/:runID` completely outside of the authenticated route group. Anyone who can reach the node's HTTP API and knows/obtains a pending task's UUID can call this endpoint to supply an arbitrary result (or error) that gets fed directly into a running pipeline, with no proof that the caller is the legitimate external adapter/bridge that was supposed to answer that specific async task.

### Finding Description
In `core/web/router.go`, the resume route is registered on the *unauthenticated* router group, in contrast to virtually every other mutating endpoint which is wrapped in `auth.Authenticate(...)`: [1](#0-0) 

```go
func v2Routes(app chainlink.Application, r *gin.RouterGroup) {
	unauthedv2 := r.Group("/v2")

	prc := PipelineRunsController{app}
	psec := PipelineJobSpecErrorsController{app}
	unauthedv2.PATCH("/resume/:runID", prc.Resume)

	authv2 := r.Group("/v2", auth.Authenticate(app.AuthenticationProvider(), ...))
```

The handler itself performs no authentication or authorization check — it only validates that `runID` parses as a UUID and that the JSON body contains either a `value` or an `error`: [2](#0-1) 

The only thing that stands between an unprivileged caller and hijacking a pending pipeline task is the secrecy of the `taskID` UUID, which is generated when an async `BridgeTask` builds its `responseURL` (`.../v2/resume/<uuid>`) to hand to the external adapter: [3](#0-2) 

This is structurally the same bug class as the reported H‑01: the protocol assumes a piece of ambient/observable state (there, the vToken balance; here, the resumable task's UUID/URL) uniquely identifies "my" deposit/response, and lets *any* caller who learns that value act on it — instead of requiring the caller to prove they are the entity authorized to supply that value (there, via `transferFrom`; here, via a bearer credential tied to the specific external-initiator/bridge that issued the async request). The audit log entry itself documents that this action is explicitly unauthenticated: `audit.UnauthedRunResumed`.

Any attacker who can observe network traffic to the external adapter (the URL is sent in plaintext over HTTP unless TLS + strict egress controls are enforced), guess/enumerate low-entropy or leaked UUIDs, or otherwise learn a pending run's UUID (e.g. via logs, error messages, monitoring tools, or a compromised/curious external adapter operator) can PATCH that endpoint with attacker-chosen `value`/`error` and have it injected as the result of that specific pipeline task — for any job on the node, without any credential belonging to that job's configured bridge/EI.

### Impact Explanation
An attacker who obtains a valid pending `runID` can:
- Complete (or force-error) another job's pipeline run with attacker-controlled data, poisoning downstream task inputs (e.g., a `jsonparse`/`multiply`/median stage) that may feed on-chain report submissions, VRF/Automation/OCR jobs, or other automated fund-moving actions.
- Cause denial of service by resuming pending tasks with error values, corrupting job results node-wide.

This maps onto the "unauthorized job run" / "cross-user response confusion" category: an unprivileged party can complete a job run belonging to another party/job without holding that job's authentication (bridge incoming token or external-initiator secret), analogous to attacker minting tokens against another user's already-placed deposit in H‑01.

### Likelihood Explanation
Likelihood is bounded by the difficulty of obtaining a valid pending `runID`. Chainlink core relies on the UUID's unguessability as the sole authorization mechanism for this endpoint (no rate limiting, IP allowlisting, or secondary secret is enforced by the handler itself). Any leak of the URL (network capture, external-adapter-side logging, browser history if reused over plain HTTP, monitoring/proxy logs, or a malicious/compromised third-party adapter) is sufficient — no cryptographic bypass is required, since the endpoint is unauthenticated by design and only relies on UUID secrecy rather than a proper signed/authenticated response protocol.

### Recommendation
- Require the responding party to authenticate the resume call (e.g., a per-run HMAC/token bound to the specific bridge/external-initiator credential that initiated the async request, verified server-side, similar to `AuthenticateBridgeType`/`AuthenticateExternalInitiator`), rather than relying solely on UUID secrecy.
- Bind the resume payload to the originating bridge (verify that the resumer's credential matches the bridge configured for that specific pipeline task) before calling `App.ResumeJobV2`.
- Ensure `BridgeResponseURL` traffic is always sent over TLS, and consider short random-lived, single-use, cryptographically strong tokens instead of only the task UUID, with rate limiting/logging on repeated resume attempts against the same runID.

### Proof of Concept
1. Configure a job with an `async=true` `BridgeTask`; the node computes a `responseURL` of the form `https://<node>/v2/resume/<uuid>` and sends it to the configured external adapter (`core/services/pipeline/task.bridge.go:364-374`).
2. An attacker who learns this `<uuid>` (e.g., by sniffing the request to the external adapter, or via a compromised/curious adapter) sends, without any credentials:
   ```
   PATCH /v2/resume/<uuid>
   Content-Type: application/json

   {"value": "<attacker-controlled-json>"}
   ```
3. `PipelineRunsController.Resume` (`core/web/pipeline_runs_controller.go:134-161`) accepts the request with no auth check (route is registered on `unauthedv2`, `core/web/router.go:243`), decodes it, and calls `prc.App.ResumeJobV2(ctx, taskID, result)`, completing the pending pipeline task with attacker-supplied data instead of the legitimate external adapter's response.

```go
// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
}
```
