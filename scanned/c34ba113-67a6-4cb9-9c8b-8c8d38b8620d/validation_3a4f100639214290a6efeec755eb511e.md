## Title
Username Enumeration via Authentication Timing Side-Channel in Local Session Authentication - (File: `core/sessions/localauth/orm.go`)

### Summary
The `POST /sessions` login endpoint, backed by `orm.CreateSession`, performs a fast-failing database lookup for the supplied email before doing any password verification. When the email does not exist, the function returns immediately with an error. When the email exists, the function proceeds to a bcrypt password comparison (`utils.CheckPasswordHash`), which is intentionally computationally expensive. This produces a measurable timing difference between requests for valid vs. invalid emails, allowing an unauthenticated attacker to enumerate valid Chainlink node user accounts — the same bug class as GHSA-7789-65hx-f26w (FileBrowser Quantum `/api/auth/login` timing side-channel).

### Finding Description
`SessionsController.Create` in [1](#0-0)  is an unauthenticated endpoint that binds a `SessionRequest` (email + password) from the request body and calls `AuthenticationProvider().CreateSession(ctx, sr)`.

The default (local) authentication provider's `CreateSession` implementation looks up the user first and returns immediately on lookup failure, before any cryptographic comparison occurs: [2](#0-1) 

Specifically:
```go
func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	...
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		...
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		...
		return "", pkgerrors.New("Invalid password")
	}
	...
```

- If `sr.Email` does not match any row, `FindUser` (a single indexed SQL lookup, `core/sessions/localauth/orm.go:55-59`) returns an error and the function exits immediately — a fast path.
- If `sr.Email` matches an existing user, execution proceeds to `utils.CheckPasswordHash`, which wraps `bcrypt.CompareHashAndPassword` [3](#0-2)  — a deliberately slow, computationally expensive operation (tens of milliseconds by design).

This is the exact root cause pattern described in the advisory: DB lookup occurs before password validation, and the expensive `bcrypt` comparison is only reached when the account exists, creating an observable timing gap between the "user not found" and "user found, password checked" code paths.

Additionally, before `CreateSession` is even invoked, `SessionsController.Create` performs a separate unauthenticated DB query via `GetUserWebAuthn(ctx, sr.Email)` [4](#0-3) , which itself could add to observable timing variance depending on whether WebAuthn credentials exist for the account, compounding the side channel.

The same pattern (`localLoginFallback` querying the user then calling `constantTimeEmailCompare` and `utils.CheckPasswordHash`) also exists in the LDAP and OIDC fallback authenticators [5](#0-4) [6](#0-5) , but the default/local authenticator's `CreateSession` is the primary unauthenticated-reachable analog since it's the standard login path for a Chainlink node's operator UI/API.

### Impact Explanation
An unauthenticated network attacker can send crafted `POST /sessions` requests with candidate email addresses and measure response latency to distinguish valid Chainlink node operator accounts from invalid ones, exactly as demonstrated in the referenced PoC. This is a confidentiality-impacting information disclosure (CWE-208) that facilitates follow-on credential-stuffing or brute-force attacks against the node's admin/API authentication, since operator emails/usernames are otherwise not meant to be discoverable by unauthenticated third parties.

### Likelihood Explanation
The `/sessions` endpoint is unauthenticated by design (it's the login endpoint) and reachable directly by any network client with access to the node's web/API server. The timing gap is caused by an inherently slow cryptographic primitive (bcrypt) being conditionally invoked only on the "found" path, making the signal reliable and reproducible with a small number of samples for baseline calibration, similar to the original report's methodology.

### Recommendation
Ensure constant-time behavior regardless of whether the email exists:
- Always perform a bcrypt comparison (e.g., against a fixed dummy hash) even when the user lookup fails, so the response time is equalized between "user not found" and "user found, wrong password" cases.
- Alternatively, introduce a randomized or fixed artificial delay for the "not found" path to match the expected bcrypt cost.
- Apply the same fix to the LDAP (`localLoginFallback`) and OIDC (`localLoginFallback`) fallback paths, which share the identical vulnerable structure.
- Consider also normalizing the `GetUserWebAuthn` unauthenticated pre-check timing in `SessionsController.Create`.

### Proof of Concept
Using the same approach as the original advisory PoC, against a Chainlink node's login endpoint:
```python
import requests, time, statistics

TARGET_URL = "http://<node>/sessions"

def measure(email):
    start = time.perf_counter()
    requests.post(TARGET_URL, json={"email": email, "password": "wrong-password"})
    return time.perf_counter() - start

baselines = [measure(f"nonexistent_{i}@example.com") for i in range(20)]
threshold = statistics.mean(baselines) + statistics.stdev(baselines) * 5

for email in ["admin@node.example", "operator@node.example", "nonexistent_test@example.com"]:
    t = measure(email)
    print(email, t, "VALID" if t > threshold else "invalid")
```
Requests for existing emails incur the additional `bcrypt.CompareHashAndPassword` cost inside `utils.CheckPasswordHash` [3](#0-2) , while requests for non-existent emails return immediately from `FindUser` in `CreateSession` [7](#0-6) , producing a measurable and distinguishable timing difference.

func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}

func CheckPasswordHash(password, hash string) bool {
	err := bcrypt.CompareHashAndPassword([]byte(hash), []byte(password))
	return err == nil
}

func (l *ldapAuthenticator) localLoginFallback(ctx context.Context, sr sessions.SessionRequest) (sessions.User, error) {
	var user sessions.User
	sql := "SELECT * FROM users WHERE lower(email) = lower($1)"
	err := l.ds.GetContext(ctx, &user, sql, sr.Email)
	if err != nil {
		return user, err
	}

		l.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})

	}
