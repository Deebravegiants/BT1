### Title
Cross-User Response Hijacking via Unscoped, Attacker-Controlled `MessageID` in Web API Gateway Handler - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
The Web API capabilities gateway handler keys its pending-callback table (`savedCallbacks`) solely by the client-supplied `MessageID` field, with no uniqueness enforcement and no binding to the sender's identity. Because `MessageID` is fully attacker-chosen (only length/null-byte checks are applied) and unprivileged users route requests through the same shared `handler` instance per DON, one unprivileged caller can overwrite another caller's pending callback entry by submitting a request using the same `MessageID`, causing the eventual node response to be delivered to the wrong requester.

### Finding Description
`api.Message.Validate()` only enforces that `MessageID` is non-empty, ≤128 bytes, and does not end in a null byte — it never enforces uniqueness or scoping to the sender: [1](#0-0) 

In the capabilities handler's legacy flow, the gateway stores a callback in a shared, DON-wide map keyed purely by `msg.Body.MessageID`, without checking whether that key is already occupied by a different (still pending) caller's callback, and without ever recording which sender owns the slot: [2](#0-1) 

When a node later responds, the handler looks up and deletes the callback purely by `MessageID` and hands the response to whatever callback currently occupies that key: [3](#0-2) 

The only identity check performed on the node response path is that the node's address matches the expected sender of the *node* message, not any binding of the `MessageID` slot back to the original requesting user: [4](#0-3) 

This mirrors the reported bug class: an unprivileged actor abuses a caller-controlled identifier over a shared, un-partitioned resource (here, the `savedCallbacks` map) to disrupt or redirect outcomes intended for other participants — analogous to how `depositETHIntoMultipleRounds` let an attacker pollute a shared round state using attacker-controlled inputs with no per-depositor isolation.

### Impact Explanation
If two different unprivileged users' requests use (or collide on, e.g. via predictable/sequential/fixed ID schemes used by some SDKs, or an attacker deliberately choosing a `MessageID` they can guess or observe in flight) the same `MessageID` while both are pending, the later `HandleLegacyUserMessage` call silently overwrites the earlier caller's `savedCallback` entry. The node's eventual response — potentially containing another user's HTTP trigger result — is then delivered to the attacker's callback instead of the legitimate requester, and the legitimate requester's original callback is orphaned (never resolved, eventually times out or is pruned). This is a concrete cross-user response confusion condition: an unprivileged attacker can intercept response data intended for another workflow/user by racing or predicting `MessageID` values, and simultaneously deny that response to the rightful caller.

### Likelihood Explanation
Exploitability depends on the attacker's ability to predict or race a `MessageID` that collides with a legitimate concurrent request on the same DON/handler. Since `MessageID` is entirely attacker-chosen (subject only to length/format checks) and multiple distinct users' requests are multiplexed through the same `handler` instance and shared `savedCallbacks` map, any client library or workflow that uses non-random/sequential/timestamp-derived or otherwise low-entropy `MessageID`s materially increases likelihood; even with random IDs, an attacker who can observe or influence another party's ID scheme (e.g., a shared frontend, retried IDs, or IDs derived from public workflow parameters) can still collide deliberately.

### Recommendation
Scope the `savedCallbacks` key to `(sender, MessageID)` rather than `MessageID` alone, and reject/log new registrations that would overwrite an existing unexpired entry for a different sender rather than silently replacing it. Additionally, consider binding the callback entry to the authenticated sender identity extracted during `Validate()`/`ExtractSigner()` so a response can only be routed to the callback that matches the original requester.

### Proof of Concept
1. Attacker crafts and signs a `web_api_trigger` legacy message with `MessageID = "X"` (any string they choose) — signature validity only requires internal self-consistency, not global uniqueness.
2. Concurrently, victim submits a legitimate `web_api_trigger` request that happens to use (or is made to use, e.g., via a predictable/replayed ID) the same `MessageID = "X"`.
3. Whichever call to `HandleLegacyUserMessage` executes second overwrites `h.savedCallbacks["X"]`, discarding the first caller's `Callback` reference.
4. When a DON node responds with `MessageID = "X"`, `handleWebAPITriggerMessage` looks up `h.savedCallbacks["X"]`, finds the surviving (attacker's) callback, and delivers the response to the attacker — regardless of which original request the node was actually answering.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

func (h *handler) HandleNodeMessage(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	msg, err := common.ValidatedMessageFromResp(resp)
	if err != nil {
		return err
	}
	if msg.Body.Sender != nodeAddr {
		return errors.New("message sender mismatch when reading from node ")
	}
	start := time.Now()
	switch msg.Body.Method {
	case MethodWebAPITrigger:
		err = h.handleWebAPITriggerMessage(ctx, msg, nodeAddr)
	case MethodWebAPITarget, MethodComputeAction, MethodWorkflowSyncer:
		err = h.handleWebAPIOutgoingMessage(ctx, msg, nodeAddr)
	default:
		err = fmt.Errorf("unsupported method: %s", msg.Body.Method)
	}
	h.metrics.recordHandleDuration(ctx, time.Since(start), msg.Body.Method, err == nil)
	return err
}
