### Title
Bridge `OutgoingToken` credentials stored unencrypted in the database and exposed unmasked via REST/GraphQL APIs - (File: `core/bridges/bridge_type.go`)

### Summary
Chainlink's `BridgeType` model stores the external-adapter `OutgoingToken` in plaintext in the database and returns it unmasked to any authenticated caller through both the REST bridge-types API and the GraphQL `Bridge` resolver. This mirrors the Jenkins ReadyAPI advisory's bug class (CWE-256/CWE-522): a credential meant to authenticate the node's own outbound requests to an external adapter is persisted without encryption and is not masked in API/UI responses, so any user who can reach the bridges query/mutation surface can read it.

### Finding Description
`BridgeType.OutgoingToken` is a `string` DB column (`outgoing_token`) populated in cleartext when a bridge is created: [1](#0-0) 

By contrast, the *incoming* token is properly protected — only a salted hash (`IncomingTokenHash`) is stored, and comparisons are done via `AuthenticateBridgeType` with `subtle.ConstantTimeCompare`: [2](#0-1) 

The `OutgoingToken`, however, has no such protection. It is returned directly by the GraphQL resolver: [3](#0-2) 

and is explicitly queried/returned in the GraphQL schema/tests (`outgoingToken` field on `Bridge`, `CreateBridge`, `UpdateBridge`): [4](#0-3) 

This stands in sharp contrast to the rest of the node's secrets architecture, which deliberately redacts all other sensitive config/secrets values (`models.Secret`, `TOMLString()`, `readSanitizedJSON`, `redact()`): [5](#0-4) [6](#0-5) 

The `OutgoingToken` was evidently never added to this redaction path, similar to how the Jenkins plugin's job config form failed to mask SLM keys/secrets/passwords.

### Impact Explanation
Any authenticated node-API user able to query the `bridges`/`bridge` GraphQL queries or the REST `bridge_types` endpoints can read the plaintext `OutgoingToken` for every configured bridge. Since this token is used to authenticate the Chainlink node to its own external adapters (per `BridgeTypeAuthentication`), disclosure lets a lower-privileged/observer-level user impersonate the node to the adapter, or reuse the credential outside of intended job-run flows. This maps to "key/secret disclosure" and potential "request impersonation" in the same way the Jenkins credentials could be read by any Item/Extended-Read user and reused.

### Likelihood Explanation
No special access beyond an authenticated session/API token to the node's web/GraphQL API is required — no admin-only gating was found on the `Bridge`/`bridges` GraphQL query path in the portion of `core/web/router.go` I was able to inspect. I could not fully confirm the exact role-check (e.g., whether "view" role vs. "admin" role is required) for the bridge_types REST controller before running out of investigation budget, so likelihood should be validated against the actual role-check middleware for `/v2/bridge_types` and the GraphQL `bridges`/`bridge` resolvers.

### Recommendation
- Wrap `BridgeType.OutgoingToken` (and `BridgeTypeAuthentication.OutgoingToken`) in the same `models.Secret`/redaction pattern used elsewhere (`config.SecretString`), or omit it entirely from read-path GraphQL/REST responses, only returning it once at creation time (similar to how `IncomingToken` plaintext is only returned once via `BridgeTypeAuthentication` on creation).
- Store `OutgoingToken` encrypted at rest (e.g., via the node's keystore encryption) rather than as a raw DB column, consistent with `IncomingTokenHash`'s hashed storage.
- Audit the role-based access control on the bridges REST/GraphQL endpoints to confirm whether "view"-only roles can read this field, and restrict to admin/edit roles if so.

### Proof of Concept
1. As an authenticated node user (any role with bridge read access), issue the GraphQL query:
```graphql
query {
  bridge(id: "my-bridge") {
    ... on Bridge {
      outgoingToken
    }
  }
}
```
2. Per `BridgeResolver.OutgoingToken()`, the server returns the raw plaintext token stored in `bridge_types.outgoing_token`: [3](#0-2) 
3. This token can now be reused to authenticate as the node against the configured external adapter, without ever having created the bridge or possessing admin privileges — analogous to viewing unmasked SLM License Access Keys/client secrets in a Jenkins job's `config.xml`.

**Note on investigation limits:** I was unable to fully trace the precise role/permission gate applied to the `/v2/bridge_types` REST routes and the GraphQL `bridges`/`bridge` queries before the iteration budget was exhausted; this should be verified in a follow-up session to confirm the exact privilege level needed to trigger disclosure.

// AuthenticateBridgeType returns true if the passed token matches its
// IncomingToken, or returns false with an error.
func AuthenticateBridgeType(bt *BridgeType, token string) (bool, error) {
	hash, err := incomingTokenHash(token, bt.Salt)
	if err != nil {
		return false, err
	}
	return subtle.ConstantTimeCompare([]byte(hash), []byte(bt.IncomingTokenHash)) == 1, nil
}

func incomingTokenHash(token, salt string) (string, error) {
	input := fmt.Sprintf("%s-%s", token, salt)
	hash, err := utils.Sha256(input)
	if err != nil {
		return "", err
	}
	return hash, nil
}

func readSanitizedJSON(buf *bytes.Buffer) (string, error) {
	var dst map[string]any
	err := json.Unmarshal(buf.Bytes(), &dst)
	if err != nil {
		return "", err
	}

	cleaned := map[string]any{}
	for k, v := range dst {
		if isBlacklisted(k) {
			cleaned[k] = "*REDACTED*"
			continue
		}
		cleaned[k] = v
	}

	b, err := json.Marshal(cleaned)
	if err != nil {
		return "", err
	}
	return string(b), err
}
