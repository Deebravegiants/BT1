Target: ShopifyAPI::Auth::JwtPayload#shopify_user_id vs #sub trust for session id uniqueness. Attacker action: present a validly signed token from their own install where sub is a non-numeric string (own dev shop can produce arbitrary sub only if Shopify issues it that way - test the code path where user_id_sub? is false). Preconditions: online session flow. Call sequence: session_id_from_shopify_id_token calls jwt_session_id(shop, T.must(payload.sub)) unconditionally, regardless of user_id_sub?/admin_session_token? checks which only gate shopify_user_id, not jwt_session_id. Binding that breaks: session_id derived from sub == session_id derived only from a validated numeric user id is false; jwt_session_id accepts any sub string including one containing the '_' separator or empty string. Scoped impact: Critical, session id collision across users when sub is attacker-influenceable format (e.g., alternates in future token formats) causing (shop_A, sub_X) to collide with (shop_B, sub_Y) session ids. Proof idea: minitest calling SessionUtils.jwt_session_id('a.myshopify.com', '') and SessionUtils.jwt_session_id('a.myshopify.com_', '') asserting identical output strings, proving no delimiter-injection guard exists.
