Target: ShopifyAPI::Utils::SessionUtils.session_id_from_shopify_id_token and .jwt_session_id. Attacker action: obtain (via their own dev shop) a validly signed shopify_id_token where they control the shop's myshopify domain string, e.g. registering a shop literally named 'victim-shop.myshopify.com_1' is not possible, but attacker can present Authorization: Bearer <own valid JWT> where payload.sub is '1_victim-shop.myshopify.com' is also not achievable since sub is Shopify-assigned; instead attacker manipulates payload.shop via 'dest' claim boundary. Preconditions: Context.embedded? true, online session flow. Call sequence: JwtPayload.new(token) sets @dest from signed payload, shop = @dest.gsub('https://', ''); jwt_session_id(shop, T.must(payload.sub)) builds "#{shop}_#{user_id}" via string interpolation with '_' separator not escaped. Binding that breaks: session_id decomposition into (shop, user_id) is unambiguous == false when either shop or sub itself contains '_', so two distinct (shop, sub) pairs can collide on the same session_id string used as storage key. Scoped impact: Critical, cross-tenant/cross-user session collision - session belonging to user A of shop X can be loaded under the id intended for user B of shop Y if the constructed strings collide. Proof idea: minitest constructing two JwtPayload-like stubs with dest 'https://a_b.myshopify.com', sub '1' and dest 'https://a.myshopify.com', sub '1_1' with same JWT_LEEWAY, assert jwt_session_id produces identical output 'a_b.myshopify.com_1' for both, violating SHOP_BINDING equality (shop_authenticated_by_jwt != shop componentized safely from session id).
