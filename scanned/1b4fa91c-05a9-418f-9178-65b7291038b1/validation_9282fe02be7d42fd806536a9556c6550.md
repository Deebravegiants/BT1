The relevant bug-class analog exists in the CORS origin-matching logic of chainlink's Gateway HTTP server, which handles unprivileged internet-facing requests.

### Title
CORS Wildcard Origin Bypass via Suffix Matching Without Domain Boundary Check - (File: core/services/gateway/network/httpserver.go)

### Summary
The Gateway `httpServer.isAllowedOrigin` function, used to validate the `Origin` header before setting CORS response headers, implements wildcard host matching (`*.example.com`) using a raw string-suffix comparison instead of a proper subdomain/domain-boundary check. This allows an attacker-registered domain that merely ends with the same characters as the allowed suffix (e.g. `evilremix.com` matching an allowlist entry `*.remix.com`) to be treated as an authorized cross-origin caller, mirroring the CVE's root cause of mishandling origin validation (Same-Origin-Policy equivalent) for a browser-reachable interface.

### Finding Description
`isAllowedOrigin` splits both the incoming request `Origin` and each configured allowed origin into scheme/host/port, then for wildcard entries strips the `"*."` prefix and does a pure suffix check: [1](#0-0) 

Because `strings.HasSuffix(originHost, allowedHost)` is used without requiring a preceding `.` (dot) boundary, any origin host string that happens to terminate with the same characters as the configured suffix satisfies the check — not just genuine subdomains. For example, configuring `CORSAllowedOrigins = ["https://*.remix.com"]` is intended to allow only `*.remix.com` subdomains, but a completely unrelated attacker-controlled domain such as `https://evilremix.com` or `https://notremix.com` will also pass the check, because `"evilremix.com"` and `"notremix.com"` both end with the literal substring `"remix.com"`.

This function backs `handleRequest`, which reflects the caller-supplied `Origin` value into `Access-Control-Allow-Origin` once `isAllowedOrigin` returns true: [2](#0-1) 

This HTTP server is the Gateway's user-facing entrypoint (`UserServerConfig`, exercised in tests with browser-style origins like `https://remix.ethereum.org`) that accepts JSON-RPC requests from unauthenticated web clients and forwards them to the node/DON handlers (e.g. Vault secrets operations processed via `GatewayHandler.HandleGatewayMessage`). A misconfigured or attacker-abused wildcard allowlist entry therefore results in an incorrect Same-Origin-style trust decision at the gateway boundary, analogous to the CVE's mishandling of origin checks for `setPermissionRequestHandler`.

### Impact Explanation
If an operator configures a wildcard `CORSAllowedOrigins` entry (a documented, supported feature per the sample configs and tests), any attacker who registers a domain ending in the same suffix — with no actual subdomain relationship — can have their web page's cross-origin requests to the Gateway succeed with `Access-Control-Allow-Origin` reflecting their origin. A victim browsing the attacker's site would then have their browser permitted to read JSON-RPC responses from the Gateway (potentially including responses tied to Vault secrets flows or other user-scoped operations), enabling cross-origin response disclosure that the CORS allowlist was meant to prevent.

### Likelihood Explanation
Exploitability depends on an operator using a wildcard CORS entry (e.g. `*.remix.com`) and an attacker being able to register/host a domain string ending in the same suffix without a dot boundary (e.g. `evilremix.com`). This is a realistic and low-cost attack for a determined adversary (domain registration is cheap and does not require compromising the legitimate domain), and no authentication or privileged access is needed — it is purely a client/browser-side interaction with the public Gateway endpoint.

### Recommendation
Fix `isAllowedOrigin` to require a domain-boundary match for wildcard entries, e.g. check `originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost)` instead of a bare `strings.HasSuffix`, ensuring only genuine subdomains of the allowed root domain match.

### Proof of Concept
1. Configure the Gateway's `UserServerConfig` with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.remix.com"]`.
2. From an attacker-controlled site hosted at `https://evilremix.com`, send a cross-origin `fetch` request to the Gateway's user endpoint.
3. Observe that `isAllowedOrigin("https://evilremix.com")` returns `true` because `"evilremix.com"` has the suffix `"remix.com"`, and the server responds with `Access-Control-Allow-Origin: https://evilremix.com`, allowing the attacker's page to read the JSON-RPC response — despite `evilremix.com` never being an intended subdomain of `remix.com`. func (s *httpServer) isAllowedOrigin(origin string) bool {
	originScheme, originHost, originPort, err := s.splitURL(origin)
	if err != nil {
		s.lggr.Debug("error parsing origin URL", err)
		return false
	}
	for _, allowed := range s.config.CORSAllowedOrigins {
		// probably better to do this once when server starts and store it in a map
		// this is an easier solution so we don't have to apply more changes to the code
		// just need to be careful when specifying allowed origins in the config file
		allowedScheme, allowedHost, allowedPort, err := s.splitURL(allowed)
		if err != nil {
			s.lggr.Debug("error parsing allowed origin URL", err)
			continue
		}
		// skip if the scheme doesn't match at all
		if originScheme != allowedScheme {
			continue
		}
		// skip if the port doesn't match at all
		if originPort != allowedPort {
			continue
		}
		// check for exact host match (e.g., remix.com)
		if originHost == allowedHost {
			return true
		}
		// check for wildcard host match (e.g., *.remix.com)
		if strings.HasPrefix(allowedHost, "*.") {
			allowedHost = allowedHost[2:]
			if strings.HasSuffix(originHost, allowedHost) {
				return true
			}
		}
	}
	return false
}

func (s *httpServer) handleRequest(w http.ResponseWriter, r *http.Request) {
	if s.config.CORSEnabled {
		origin := r.Header.Get("Origin")
		if s.isAllowedOrigin(origin) {
			w.Header().Set("Access-Control-Allow-Origin", origin)
			w.Header().Set("Access-Control-Allow-Methods", "GET, POST, OPTIONS")
			w.Header().Set("Access-Control-Allow-Headers", "Content-Type")
		}

		// handle preflight requests
		if r.Method == http.MethodOptions {
			w.WriteHeader(http.StatusNoContent)
			return
		}
	}
