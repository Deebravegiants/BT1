### Title
JWT replay-protection check-then-act race allows the same trigger JWT to be replayed multiple times before `jti` is recorded - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
`WorkflowMetadataHandler.Authorize` checks a JWT's `jti` against the replay cache and only marks it as used *after* all other authorization checks succeed. Because `isReplay` and `recordUsage` are two separate, independently-locked operations rather than one atomic check-and-set, concurrent requests carrying the identical signed JWT can all pass the replay check before any of them records usage — the same bypass pattern as the yVault "cache-then-external-call" reentrancy: a security decision is made from state that is read once and committed later, leaving a window in which the same stale "not yet used" state can be exploited multiple times.

### Finding Description
The HTTP Trigger gateway path (fully unprivileged/internet-facing) authenticates each `HandleUserTriggerRequest` via `authorizeRequest` -> `WorkflowMetadataHandler.Authorize`: [1](#0-0) 

The sequence is:
1. Verify JWT signature (`utils.VerifyRequestJWT`).
2. `h.jwtCache.isReplay(claims.ID)` — read-check whether this `jti` was already used.
3. Look up authorized signer for the workflow and verify the key.
4. Only *after* all of that succeeds, `h.jwtCache.recordUsage(claims.ID)` — the write that actually marks the `jti` as spent. [2](#0-1) [3](#0-2) 

The replay cache itself is a plain map guarded by its own `sync.RWMutex`: [4](#0-3) 

`isReplay` and `recordUsage` are called as two distinct, separately-locked operations rather than being combined into one atomic "check-and-mark-used" critical section spanning the entire `Authorize` call. This mirrors the root cause in the H-04 report: a value/condition is read and cached, an intervening operation is performed, and only afterward is the authoritative state updated — anything that can be triggered in that window sees the pre-update state.

### Impact Explanation
An unprivileged external client that possesses one valid signed HTTP-trigger JWT (e.g., captured off the wire, or a legitimate caller replaying its own request) can fire multiple concurrent requests with the same token before the first one finishes recording its `jti` as used. Each concurrent request independently observes `isReplay == false`, passes authorization, and is forwarded to the DON to execute the workflow via `sendWithRetries` — defeating the anti-replay guarantee that is supposed to bound each signed request to exactly one execution. This can cause duplicate/unintended workflow executions (job runs) triggered by a single signed authorization, which is a concrete "unauthorized job run" outcome for CRE HTTP-triggered workflows.

### Likelihood Explanation
The race requires the attacker/caller to send the same JWT concurrently (multiple parallel HTTP POSTs to the gateway before the first completes `Authorize`), which is trivial for any external client to script — no special network position, no operator/node privilege, and no dependency-only conditions are required. This qualifies as a valid unprivileged-actor analog in "session/token/external-initiator handling" on the internet-facing gateway.

### Recommendation
Make the JWT replay check-and-mark operation atomic: hold the `jwtReplayCache` lock across both the "already used" check and the "record used" write (i.e., a single `CheckAndSet`/`ClaimOnce(jti)` method), and reject the request if the `jti` was already claimed by a concurrent caller, instead of calling `isReplay()` and `recordUsage()` as two separate calls.

### Proof of Concept
1. Attacker (or a legitimate caller) obtains one validly-signed HTTP trigger JWT for a workflow (`req.Auth`).
2. Attacker fires N concurrent POSTs to the gateway's HTTP trigger endpoint using the identical JWT/`jti` before the first request's `Authorize` call reaches `recordUsage`.
3. Each concurrent goroutine's call to `h.jwtCache.isReplay(claims.ID)` at [5](#0-4)  returns `false` because none has yet reached `recordUsage` at [6](#0-5) .
4. All N requests pass authorization and are forwarded via `HandleUserTriggerRequest` -> `sendWithRetries` to the workflow DON, causing N workflow executions from a single signed, supposedly single-use JWT.

Note: I was unable to retrieve the concrete implementation bodies of `jwtReplayCache.isReplay` and `recordUsage` (they are defined outside the range of file content available to me), so the exact locking granularity inside those two methods is inferred from the struct definition and call-site ordering rather than directly observed; this should be verified by a follow-up review of their implementation before treating this as fully confirmed.

```go
func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
```
