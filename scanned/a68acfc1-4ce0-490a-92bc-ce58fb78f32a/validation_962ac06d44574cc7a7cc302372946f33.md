### Title
Unsynchronized read of `authorizedKeys` in `WorkflowMetadataHandler.Authorize` races with `syncMetadata`'s lock-protected writes - (File: `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go`)

### Summary
The external report describes a class of bug where two components maintain related state that must stay synchronized, but one side is mutated without the corresponding safety mechanism used by the other side, breaking the invariant that keeps both in a consistent state. In `WorkflowMetadataHandler`, the same class of bug appears: `syncMetadata` replaces the `authorizedKeys`/`workflowIDToRef`/`workflowRefToID`/`workflowShards` maps under `h.mu.Lock()`, but `Authorize` — the function that performs signer authentication for every inbound HTTP Trigger request from an unprivileged external caller — reads `h.authorizedKeys` without acquiring `h.mu` at all.

### Finding Description
`WorkflowMetadataHandler` declares `mu sync.RWMutex` specifically to guard `authorizedKeys`, `workflowRefToID`, `workflowIDToRef`, and `workflowShards`: [1](#0-0) 

Every other accessor correctly takes the lock, e.g. `WorkflowShards`, `GetWorkflowID`, and `GetWorkflowReference`: [2](#0-1) [3](#0-2) 

However, `Authorize` — the function responsible for verifying that the JWT signer is an authorized key for the target workflow — indexes into `h.authorizedKeys` directly with no `h.mu.RLock()`/`RUnlock()`: [4](#0-3) 

Meanwhile, `syncMetadata` runs on a periodic ticker (`MetadataAggregationIntervalMs`) and reassigns the entire map value under `h.mu.Lock()`: [5](#0-4) [6](#0-5) 

`Authorize` is invoked directly from the HTTP trigger request path (`HandleUserTriggerRequest` → `Authorize`), which is reachable by any unprivileged external caller sending an `HTTPTriggerRequest` with a JWT to the gateway. Because `Authorize` never takes `h.mu`, it can run concurrently with `syncMetadata`'s unguarded write to `h.authorizedKeys` (a plain Go map field reassignment, not protected on the reader side). This is a classic unsynchronized concurrent map read/write in Go: at best it results in an inconsistent/stale authorization decision (reading a map about to be replaced with a different set of authorized keys for a workflow — e.g., a key that was just revoked and removed by `syncMetadata` may still be treated as valid mid-swap, or vice versa a newly authorized key may be transiently rejected), and at worst (per Go's memory model) it can trigger a runtime "fatal error: concurrent map read and map write" panic in the gateway process — a DoS reachable purely by normal HTTP trigger traffic timed against the periodic metadata sync.

### Impact Explanation
`Authorize` is the sole ECDSA-signature authorization check standing between an inbound `HTTPTriggerRequest` and workflow execution. A race here can:
- Crash the gateway service (`fatal error: concurrent map read and map write` is unrecoverable and not caught by `recover()`), causing denial of service triggerable by unprivileged, internet-facing HTTP trigger traffic.
- Produce inconsistent authorization outcomes during the race window (a revoked/rotated key transiently still validated, or a currently-valid key transiently rejected), undermining the JWT-based authentication guarantee described in the module's own documentation (`Authentication: Verifies JWT token (ECDSA signature) and checks authorized keys`).

### Likelihood Explanation
`syncMetadata` runs on every tick of `MetadataAggregationIntervalMs` (default configurable, on the order of a minute) for the lifetime of the gateway process, and `Authorize` runs on every single inbound HTTP trigger request. Given continuous request traffic, the race window is hit repeatedly over time, not as a rare edge case — this is a structural, always-reachable synchronization gap, not a corner case requiring a malicious actor with special access. Any external, unprivileged client issuing normal HTTP trigger requests is sufficient to exercise the racing code path.

### Recommendation
Acquire `h.mu.RLock()`/`RUnlock()` around the reads of `h.authorizedKeys` in `Authorize`, mirroring the pattern already used in `WorkflowShards`, `GetWorkflowID`, and `GetWorkflowReference`. If per-call lock overhead is a concern, capture the map reference under the lock at the top of `Authorize` and operate on the local copy for the remainder of the function.

### Proof of Concept
1. Start a `WorkflowMetadataHandler` with `MetadataAggregationIntervalMs` set very small (e.g., 1ms) and register a workflow with authorized key `K1`.
2. Spawn goroutine A that repeatedly calls `Authorize(workflowID, jwt, req)` with a valid JWT signed by `K1`.
3. Spawn goroutine B that repeatedly calls `syncMetadata(ctx)` (simulating the ticker), each time supplying aggregator observations that replace the authorized key set for `workflowID` (e.g., alternating between `K1` and `K2`).
4. Run under `go test -race`; the race detector reports a data race on `h.authorizedKeys` between the unguarded read in `Authorize` (line 92) and the lock-guarded write in `syncMetadata` (line 178). Running the equivalent under high concurrency without `-race` can surface `fatal error: concurrent map read and map write`, crashing the process.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (h *WorkflowMetadataHandler) WorkflowShards(workflowID string) []*shardEndpoint {
	h.mu.RLock()
	defer h.mu.RUnlock()
	shards := h.workflowShards[workflowID]
	out := make([]*shardEndpoint, len(shards))

	return out
}

func (h *WorkflowMetadataHandler) GetWorkflowID(workflowOwner, workflowName, workflowTag string) (string, bool) {
	h.mu.RLock()
	defer h.mu.RUnlock()
	workflowRef := workflowReference{
		workflowOwner: workflowOwner,
		workflowName:  workflowName,
		workflowTag:   workflowTag,
	}
	workflowID, exists := h.workflowRefToID[workflowRef]
	if !exists {
		return "", false
	}
	return workflowID, true
}

func (h *WorkflowMetadataHandler) GetWorkflowReference(workflowID string) (workflowReference, bool) {
	h.mu.RLock()
	defer h.mu.RUnlock()
	workflowRef, exists := h.workflowIDToRef[workflowID]
	return workflowRef, exists
}
