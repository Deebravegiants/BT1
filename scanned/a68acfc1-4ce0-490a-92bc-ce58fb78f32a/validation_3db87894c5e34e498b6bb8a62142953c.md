## #Vulnerability found for this question.

### Title
Missing role-based authorization on node pprof/debug profiling endpoints allows any authenticated (view-role) user to dump process memory, goroutines, and command-line, exposing secrets - (File: core/web/router.go)

### Summary
The Chainlink node's HTTP router exposes Go's `net/http/pprof` debugging endpoints (heap, goroutine, cmdline, trace, profile, symbol) under `/v2/debug/pprof/*`. These are registered via `metricRoutes(authv2)`, which is nested inside the `authv2` group that only requires a valid session/API token (`auth.AuthenticateByToken` or `auth.AuthenticateBySession`) but applies **no role check** (`auth.RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole`), unlike almost every other sensitive route in the same function (key export/import, user management, transfers, etc.) which are explicitly gated with `auth.RequiresAdminRole` or `auth.RequiresEditRole`.

### Finding Description
`metricRoutes` registers the full stdlib pprof handler set with no additional authorization: [1](#0-0) 

It is mounted directly under the token/session-authenticated `authv2` group with a comment implying this is intentional, but without any privilege check: [2](#0-1) [3](#0-2) 

Compare this to the rest of `v2Routes`, where every operation that reads/exports secret material or performs privileged operations is explicitly wrapped with a role guard, e.g. key export/import/delete require admin, bridge/job mutation requires edit: [4](#0-3) [5](#0-4) 

The role hierarchy itself (`View < Run < Edit < Admin`) is enforced elsewhere via `RequiresRunRole`, `RequiresEditRole`, and `RequiresAdminRole`, which explicitly reject the lowest `UserRoleView`: [6](#0-5) 

Because `metricRoutes` has none of these guards, any authenticated user — including one with the read-only `view` role, which is otherwise blocked from editing/running/administering anything — can hit `/v2/debug/pprof/heap`, `/v2/debug/pprof/goroutine?debug=2`, `/v2/debug/pprof/cmdline`, and `/v2/debug/pprof/profile|trace`. Heap and goroutine dumps can contain in-memory secrets (decrypted ETH/OCR/CSA/VRF/P2P private keys, session cookies, DB DSNs, API tokens) that the node holds during normal operation, and `cmdline` can reveal secrets passed via process arguments. This is analogous to the RaspAP CVE-2020-24572 pattern: an authenticated but under-privileged actor is able to reach a diagnostic/administrative surface that was not intended to be reachable at their privilege level, enabling disclosure of data that should require elevated (admin) access.

### Impact Explanation
A low-privileged (`view`-role) authenticated user or a compromised low-privilege API token could extract heap/goroutine memory dumps of the running node process. Given the node holds decrypted private keys and other secrets in memory during signing/operation, this creates a path to key/secret disclosure, which could subsequently enable unauthorized fund movement or full node compromise — well beyond what a `view` role is supposed to permit. This satisfies the "key/secret disclosure" and "authentication/role bypass" criteria.

### Likelihood Explanation
Likelihood is high for any deployment that grants `view`-level API tokens/sessions to less-trusted operators, dashboards, or automation (a common pattern precisely because `view` is documented as the safe, read-only role). No special network position or extra credentials are needed beyond a valid low-privilege session/token — exactly the CVSS AV:N/PR:L profile of the referenced advisory.

### Recommendation
Gate `metricRoutes` (and the `/debug/vars` route in `debugRoutes`) with `auth.RequiresAdminRole` (or at minimum `RequiresEditRole`) consistent with how other sensitive/diagnostic endpoints are protected in `v2Routes`, so that only trusted, elevated roles can access process-level profiling data.

### Proof of Concept
1. Create or obtain a Chainlink node user/API token with role `view` (the lowest privilege, e.g. via `authv2.POST("/users", auth.RequiresAdminRole(uc.Create))` performed by an admin for a read-only account).
2. Authenticate as that `view` user (`chainlink admin login` or `POST /sessions`) to obtain a valid session cookie.
3. Issue `GET /v2/debug/pprof/heap?debug=1` (or `cmdline`, `goroutine?debug=2`, `profile?seconds=30`) using that session cookie.
4. Observe the request succeeds (HTTP 200) despite the account lacking `run`/`edit`/`admin` privileges, and the response contains full process memory/goroutine/command-line data that a `view`-role account should not be able to access.

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
