## Analysis

The Kintsu bug is a classic **check-then-act state inconsistency**: a single boolean condition (`staked == 0`) is used to decide whether an action can proceed, but the code path that clears/sets that condition is split across two different functions (`start_unbond` decrements it, `withdraw_unbonded` does not), creating a window where the guard doesn't reflect the true state and a legitimate call is denied unpredictably.

The closest reachable analog in the unprivileged HTTP-trigger gateway path is the **JWT replay-protection cache** in `WorkflowMetadataHandler`, which has the same check-then-act structure but split across an `RLock`/`Lock` pair instead of a single atomic operation. [1](#0-0) 

`isReplay(claims.ID)` is checked under a read lock, and only afterward — after signature verification and authorized-key lookup — is `recordUsage(claims.ID)` called under a separate write lock: [2](#0-1) 

Because the "has this JWT already been used" check and the "mark this JWT as used" mutation are two independent, non-atomic critical sections (mirroring the Kintsu pattern of `staked` being read in one function and only mutated in another), concurrent requests carrying the same JWT (`jti`) can both pass `isReplay` before either calls `recordUsage`, defeating the one-time-use replay guard.

### Title
Non-atomic check-then-act in JWT replay cache allows replay of the same authorization token - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
`WorkflowMetadataHandler.Authorize` checks JWT replay status via `jwtCache.isReplay` and only records usage via `jwtCache.recordUsage` after several more steps complete. The read and write to the replay-tracking map are performed in separate, non-atomic critical sections, so concurrent requests using the identical JWT can both pass the replay check.

### Finding Description
`Authorize` is the authentication gate for unprivileged HTTP-trigger workflow requests entering the gateway. It verifies the JWT signature, then calls `h.jwtCache.isReplay(claims.ID)` (acquiring `RLock`, checking map membership, releasing the lock), and only at the very end of the function calls `h.jwtCache.recordUsage(claims.ID)` (acquiring a separate `Lock`). Between the `isReplay` check and the `recordUsage` write there is no held lock spanning both operations, so two goroutines processing requests with the same `jti` concurrently can both observe `isReplay == false` and both proceed to the authorized-key check, then both call `recordUsage`. This is structurally identical to the Kintsu bug: a guard condition (`staked == 0` / "already used") is read in one place and mutated in a separate, non-atomic step, so the intended one-time semantics are not actually enforced across concurrent/rapid calls.

### Impact Explanation
The JWT replay cache exists specifically to prevent a captured/observed token from being reused (see comment `errors.New("JWT token has already been used. Please generate a new one with new id (jti)")`). If a valid signed token (e.g., captured via logs, a compromised transport hop, or replayed by the legitimate holder for load) is submitted twice at nearly the same time, both requests can be authorized and dispatched to the DON, bypassing the intended single-use guarantee. This allows unintended duplicate execution of a workflow trigger using a token that should only authorize a single request — a request-impersonation/replay class bypass, though it requires racing two submissions of the same token within the same instant, and does not defeat the JWT signature or authorized-key checks themselves.

### Likelihood Explanation
Likelihood is limited: the race window is narrow (microseconds between the two lock acquisitions), and it requires possession of a validly-signed JWT that has not yet been recorded, plus the ability to send two copies of the exact same request concurrently to the gateway (or to two different gateway node instances if replicated, where the cache is not shared at all — see below). It is more of a robustness/consistency gap than an easily exploitable bypass, but it is a genuine, provable inconsistency in the intended one-time-use invariant.

### Recommendation
Perform the replay check and usage recording as a single atomic operation, e.g. add a `checkAndRecordJWTUsed(jti string) bool` method that acquires one write lock, checks and inserts into the map, and returns whether the token was already present — eliminating the separate `isReplay`/`recordUsage` calls in `Authorize`. Additionally, note that `jwtReplayCache` is in-memory and per-instance; if multiple gateway replicas exist, replay protection is not shared across instances regardless of the atomicity fix, which is a separate scope concern for a distributed deployment.

### Proof of Concept
1. Obtain (or observe) a validly signed JWT for a registered workflow, with `jti = "X"`.
2. Fire two HTTP trigger requests carrying this identical JWT to the gateway at effectively the same time.
3. Both goroutines execute `Authorize`: both call `h.jwtCache.isReplay("X")` before either calls `h.jwtCache.recordUsage("X")`, both observe `false`.
4. Both requests pass the authorized-key check and are dispatched to the workflow DON — the token is used twice despite the intended one-time-use enforcement. [1](#0-0) [2](#0-1)

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
