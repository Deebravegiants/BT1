### Title
Workflow reference deduplication in `syncMetadata` allows cross-owner workflow ID collision/confusion in the Gateway HTTP Trigger authorization cache - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
The external report describes a root cause pattern where an authorization/ownership mapping is maintained in a secondary registry that is not authoritative and can silently diverge from the true, current ownership state, letting stale or attacker-influenced records grant/deny access incorrectly. The closest reachable analog in this codebase is the Gateway's `WorkflowMetadataHandler.syncMetadata`, which builds an in-memory `workflowID -> workflowReference` / `workflowReference -> workflowID` cache used later to authorize and route unprivileged, internet-facing HTTP trigger requests.

### Finding Description
`WorkflowMetadataHandler.syncMetadata` aggregates per-shard observations and builds the `workflowIDToRef`, `workflowRefToID`, and `authorizedKeys` maps that `httpTriggerHandler.authorizeRequest` / `resolveWorkflowID` later rely on to authenticate and route unprivileged user trigger requests (`core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go`, `authorizeRequest` at lines 368-376, using `h.workflowMetadataHandler.Authorize`). [1](#0-0) 

`syncMetadata` explicitly performs "first-wins" deduplication when two different `workflowID`s report the same `workflowReference` (owner+name+tag): only the reference observed with the highest sequence counter is kept, and the other workflowID's mapping is silently dropped, with no re-validation against a single authoritative on-chain source at resolution time: [2](#0-1) 

This cache is rebuilt periodically (`MetadataAggregationIntervalMs`, default 60s) from node-reported observations, and old observations are only reaped after `CleanUpPeriodMs`: [3](#0-2) 

The associated test (`TestSyncMetadataMultipleWorkflows`) confirms the exact non-deterministic-looking "first observed wins" behavior for colliding `workflowReference`s across different `workflowID`s: [4](#0-3) 

This mirrors the MIMO bug class: a secondary data store (here, the Gateway's local metadata cache) is treated as authoritative for authorization/routing decisions reachable from unprivileged, internet-facing requests (`HandleUserTriggerRequest` → `resolveWorkflowID` → `authorizeRequest`), but it is populated by best-effort node observations and resolved with "last/first writer wins" semantics rather than a single canonical, always-current source of truth — exactly the class of bug the MIMO report flags ("Registry tracks last deployments and does not guarantee ownership").

### Impact Explanation
If two workflow registrations (potentially owned by different, unrelated parties) ever produce colliding `workflowReference` tuples (owner+name+tag) — whether through node/DON disagreement, replay of stale on-chain events, or a race during workflow re-registration/rotation — an unprivileged caller's HTTP trigger request resolved by name/owner/tag could be routed and authorized against the wrong `workflowID`, and the wrong workflow could be executed on behalf of a request intended for a different workflow. Because the comment explicitly assumes on-chain uniqueness of the reference ("workflow reference is unique (enforced by the on-chain registry)"), any window where that invariant is violated (e.g., during workflow deletion/re-registration by different owners reusing name/tag, or transient node disagreement before the periodic aggregation converges) causes silent mis-routing rather than an explicit failure.

### Likelihood Explanation
Likelihood is moderate-to-low without further evidence: the dedup path is a defensive fallback that assumes on-chain enforcement of reference uniqueness, and exploiting it from an unprivileged actor would require inducing a genuine collision (e.g., quickly re-registering a workflow with the same name/tag under a different owner within one aggregation cycle, or causing byzantine/stale observations from capability nodes) — this could not be fully confirmed from the indexed code alone, since the on-chain registry's guarantees around name/tag reuse across owners were not inspected in this pass.

### Recommendation
- Re-validate the resolved `workflowID`'s current owner/reference against the authoritative on-chain workflow registry at authorization time (not just against the locally cached, periodically-rebuilt map), analogous to how the MIMO fix moved to a single source of truth (`MIMOProxyFactory`) instead of a derived registry.
- On reference collision, fail closed (reject the request) rather than silently picking a "winner," and emit an alerting metric so collisions are visible operationally.
- Reduce `MetadataAggregationIntervalMs`/`CleanUpPeriodMs` risk window for stale entries during workflow re-registration, or invalidate cache entries immediately on workflow deletion/registration events rather than waiting for the next periodic sync.

### Proof of Concept
Not independently reproducible from the indexed code alone. The existing unit test `TestSyncMetadataMultipleWorkflows` in `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler_test.go` (lines 124-185) already demonstrates the exact mechanism: two distinct `workflowID`s sharing the same `workflowReference` are collected, and `syncMetadata` deterministically keeps only one (`"workflow2"`), dropping `"workflow1"`'s mapping — showing that the cache can and does silently arbitrate between competing workflow identities based on internal sequence ordering rather than authoritative on-chain state at request-resolution time. Full exploitability (i.e., whether an unprivileged actor can force such a collision against a victim owner's workflow) depends on on-chain registry invariants not covered in the indexed files and would need verification in a live/test environment.

// Start begins the periodic pull loop.
func (h *WorkflowMetadataHandler) Start(ctx context.Context) error {
	return h.StartOnce("WorkflowMetadataHandler", func() error {
		h.lggr.Info("Starting HTTP Trigger Metadata Handler")
		h.startTime = time.Now()
		for _, shard := range h.shards {
			if err := h.aggs[shard.donID].Start(ctx); err != nil {
				return fmt.Errorf("failed to start aggregator for shard %s: %w", shard.donID, err)
			}
		}
		h.runTicker(time.Duration(h.config.MetadataPullIntervalMs)*time.Millisecond, func(ctx context.Context) {
			err2 := h.sendMetadataPullRequest()
			if err2 != nil {
				h.lggr.Errorw("Failed to send pull request", "error", err2)
			}
		})
		h.runTicker(time.Duration(h.config.MetadataAggregationIntervalMs)*time.Millisecond, h.syncMetadata)
