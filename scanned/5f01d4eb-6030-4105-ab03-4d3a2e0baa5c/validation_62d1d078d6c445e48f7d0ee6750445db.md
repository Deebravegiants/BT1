### Title
JWT replay-check TOCTOU allows concurrent replay of the same HTTP-trigger JWT - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
The reported Vault bug is a classic check-effects-interactions violation: a "remaining" balance is decremented only *after* an external call returns, letting a reentrant caller repeat the withdrawal before the state is updated. The reachable analog in this Go codebase is the JWT replay-protection cache used to authorize unprivileged HTTP Trigger requests to workflows: the "check" (`isReplay`) and the "effect" (`recordUsage`) are two separate, non-atomic critical sections separated by additional authorization work, so two concurrent requests carrying the same JWT `jti` can both pass the replay check before either records it as used.

### Finding Description
`WorkflowMetadataHandler.Authorize` is the authentication entry point for `MethodWorkflowExecute` (HTTP Trigger) requests coming from arbitrary, unprivileged external clients through the CRE Gateway: [1](#0-0) 

The flow is:
1. `h.jwtCache.isReplay(claims.ID)` — takes an `RLock`, checks the map, releases the lock.
2. Workflow ID lookup and signer/authorized-key lookup (no locking, but real work/time).
3. `h.jwtCache.recordUsage(claims.ID)` — takes a `Lock`, writes the map, releases the lock.

The underlying cache implementation confirms the check and the write are two independent, separately-locked operations rather than one atomic "check-and-record": [2](#0-1) 

Because `isReplay` (read) and `recordUsage` (write) are not combined into a single critical section, if two goroutines call `Authorize` concurrently with the same JWT `jti` (e.g., the same signed token replayed twice at nearly the same time, or one legitimate request racing with a maliciously duplicated one), both can observe `isReplay == false` before either calls `recordUsage`. This is directly analogous to `Vault.sol`'s `remaining -= amount` being updated only after the external call: the state mutation that is supposed to prevent repeat use happens too late relative to the check, opening a window for a second "call" to slip through under the same state.

Notably, this codebase already has a *correct* pattern for the same problem elsewhere — `RequestReplayGuard.CheckAndRecord` in the Vault package combines the check and the write under a single mutex acquisition, closing the TOCTOU window: [3](#0-2) 

The HTTP Trigger handler's `jwtReplayCache`, by contrast, does not use this atomic pattern, showing the split-check-and-record here is a real inconsistency/regression relative to the safe pattern used for Vault.

`Authorize` is invoked from `HTTPTriggerHandler.HandleUserTriggerRequest` for `gateway_common.MethodWorkflowExecute`, which is the entry point for JSON-RPC requests from ordinary (unprivileged) callers reaching the gateway: [4](#0-3) 

(Exact line range for the call to `Authorize` inside `HandleUserTriggerRequest` could not be pinpointed further due to index truncation of that file; this should be verified directly in the file before remediation.)

### Impact Explanation
If a client (or an attacker who has legitimately obtained/observed a single JWT authorizing a workflow-execute request) sends the same token concurrently, the replay guard can be bypassed, letting the same authorization succeed twice. Depending on downstream logic (rate limiting, dedup on request ID, idempotency at the workflow-execution layer), this can result in duplicate/unauthorized re-triggering of a workflow execution using a token that should be single-use, which is the direct analog of "impersonation/replay bypass" called out as an acceptable analog class in the validation rules. The blast radius is limited by the fact that the attacker must already possess a validly signed JWT and by any additional request-ID/dedup checks noted in the test suite (`duplicate request ID`), but the specific replay-guard invariant ("token has already been used") itself can be violated under concurrency, weakening the security guarantee it's meant to provide.

### Likelihood Explanation
Medium. Exploiting the race requires firing two requests with the identical JWT within the small window between the `RLock`/`RUnlock` of `isReplay` and the `Lock` of `recordUsage` (which also includes an intervening map lookup and key comparison). This is a realistic race under load or with deliberately synchronized concurrent requests (e.g., sending the same signed JWT twice in parallel), similar in spirit to how reentrancy exploits require a callback but are fully attacker-controlled once the contract is malicious. Here, no attacker-controlled callback is needed — just concurrent delivery of the same token — making it arguably easier to trigger than a Solidity reentrancy bug, though the actual security value of a successful bypass depends on what else guards workflow execution (e.g., duplicate request-ID detection also present in the same handler).

### Recommendation
Merge `isReplay` and `recordUsage` into a single atomic check-and-record operation guarded by one lock acquisition, mirroring the `RequestReplayGuard.CheckAndRecord` pattern already used for Vault:
```go
func (cache *jwtReplayCache) checkAndRecord(jti string) error {
    cache.mu.Lock()
    defer cache.mu.Unlock()
    if _, exists := cache.cache[jti]; exists {
        return ErrRequestAlreadySeen // or equivalent
    }
    cache.cache[jti] = time.Now()
    return nil
}
```
Then call this single atomic method from `Authorize` instead of the separate `isReplay`/`recordUsage` pair, so that the "effect" (marking the token used) happens as part of the same locked "check," eliminating the race window — analogous to updating `remaining` before performing the external call in the original Vault finding.

### Proof of Concept
Not executed against a live system (no filesystem/terminal access in this mode); conceptually:
1. Register a workflow and authorized signer as in `TestWorkflowMetadataHandler_Authorize`.
2. Create one signed JWT (`tokenString`) for a `MethodWorkflowExecute` request.
3. Spin up two goroutines that both call `handler.Authorize(workflowID, tokenString, req)` at (nearly) the same time, synchronized so both pass `isReplay` before either calls `recordUsage` (e.g., inject a small sleep between the two calls inside `Authorize`, or race via `t.Parallel()`/tight loop under `go test -race`).
4. Observe that both calls can return success (no `ErrRequestAlreadySeen`/"token has already been used" error), rather than exactly one succeeding — demonstrating the replay guard's check-then-act gap, analogous to the Vault `_ensureLinkAmount` reentrancy issue where the state update lags behind the externally-observable action.

```go
func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}
```

```go
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
```
