Target: VersionedNonceBuilder.createTimestampedNonceBytes (packages/intents-sdk/src/intents/expirable-nonce.ts). Attacker input: an integrator forwards a caller-supplied startTime (Date) into IntentPayloadBuilder.setNonceRandomBytes(VersionedNonceBuilder.createTimestampedNonceBytes(startTime)) for many withdrawals issued in the same second, which is a documented, non-escape-hatch usage pattern. Preconditions: same salt, same startTime granularity (ms), only 7 bytes (bytes[8:15]) are actually random per createTimestampedNonceBytes's crypto.getRandomValues(bytes.subarray(8)) call. Call sequence: two calls to createTimestampedNonceBytes(startTime) with identical startTime feed encodeNonce(salt, deadline, bytes) -> two IntentPayloadBuilder.buildWithSalt(salt) payloads -> two signIntent + publishIntent calls. Equality broken: (nonce, verifying_contract) binds to exactly one execution; with only 2^56 space and repeated startTime, birthday-bound collision probability is far higher than the nominal 15-byte space, so two distinct signed intents can carry the same nonce bytes, and the contract's nonce-uniqueness check will accept only one, silently voiding the other even though it was fully signed and published. Impact: Critical, a fully signed withdrawal payload is silently dropped (executes zero times) although the caller believes it was submitted, and any balance debited in a batched intent tied to that nonce is not settled leaving the withdrawal stuck. Whose funds: the calling user's.
