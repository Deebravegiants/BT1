### Title
Missing memory-expansion gas surcharge in EVM `Memory::resize` allows disproportionately cheap large memory allocation/zeroing via `MSTORE`/`MLOAD`/`MSTORE8` - ([File: substrate/frame/revive/src/vm/evm/memory.rs])

### Summary
`Memory::resize` grows the interpreter's backing `Vec<u8>` up to the hard cap `EVM_MEMORY_BYTES` (1 MiB) and zero-fills every newly added byte, but the opcodes that trigger it (`mload`, `mstore`, `mstore8` in `substrate/frame/revive/src/vm/evm/instructions/memory.rs`) only charge the fixed `EVMGas(VERYLOW)`/`EVMGas(BASE)` opcode cost, with no memory-expansion surcharge as real EVMs apply (`3*words + words²/512`). A single crafted `MSTORE` at an offset near the 1 MiB ceiling can force a ~1 MiB `Vec::resize`/zero-fill for the price of one `VERYLOW` (3-gas) opcode.

### Finding Description
- `Memory::resize` at [1](#0-0)  computes `target_len` from the requested `offset`/`len`, rejects it only if it exceeds `EVM_MEMORY_BYTES`, and otherwise unconditionally does `self.data.resize(target_len, 0)` — an O(target_len - current_len) memzero/allocation — with no gas or weight charge tied to the number of bytes actually being expanded.
- The only cost paid by `mload`/`mstore`/`mstore8` is the fixed per-opcode `EVMGas(VERYLOW)`/`EVMGas(BASE)` charged via `interpreter.ext.charge_or_halt(...)` before calling `resize`, as seen at [2](#0-1) . This is a flat weight (`T::WeightInfo::evm_opcode(1) - evm_opcode(0)` per gas unit, see [3](#0-2) ) that does not scale with `offset`/`len`.
- Real EVM semantics intentionally charge a growing (linear-then-quadratic) memory-expansion gas precisely to prevent an attacker from forcing large memory allocation/zeroing for near-zero gas; that surcharge is entirely absent here. `Memory::resize` is a straight cap-check + `Vec::resize`, nothing more.
- Attacker path: an unprivileged EOA/contract caller submits an `eth_transact`/EVM-call extrinsic whose bytecode executes `PUSH offset; PUSH value; MSTORE` with `offset` chosen close to `EVM_MEMORY_BYTES - 32`. This single instruction pays fixed `VERYLOW` gas/weight yet forces the interpreter to allocate and zero close to 1 MiB. Because `CALL`/`DELEGATECALL` create fresh per-frame `Memory<T>` instances, this can be repeated once per call frame up to `CALL_STACK_DEPTH` (25, see [4](#0-3) ), and across many separate top-level transactions within the same block, each declaring only the trivial per-opcode weight.
- No other check compensates: `charge_or_halt` only enforces the flat `EVMGas` token cost; there is no `adjust_weight`/surcharge call analogous to the pattern used elsewhere in the codebase for other under-priced operations (e.g. the `sload`/`GetStorage` fix referenced in `prdoc/pr_12387.prdoc`, which explicitly charges/adjusts weight proportional to actual bytes touched). No equivalent exists for EVM memory expansion.

### Impact Explanation
Weight/gas charged for `MSTORE`/`MLOAD`/`MSTORE8` does not reflect the real computational cost of the memory expansion they trigger. An attacker can craft transactions where the declared/charged weight is minimal (a handful of `VERYLOW`/`BASE` opcode charges) while the actual work performed by the node (allocation + zero-fill of up to ~1 MiB per call frame, repeatable across call depth and across many extrinsics in a block) is far larger. This is a gas-metering/weight-accounting bypass: the block weight limit, which is supposed to bound actual per-block computation, systematically undercounts the CPU/memory-bandwidth cost of contracts that abuse large-offset memory opcodes, enabling a cheaper-than-intended computational DoS vector within block execution.

### Likelihood Explanation
Trivial to trigger: any unprivileged account can deploy or call an EVM contract compiled from a few opcodes (`PUSH2 0xFFFE0` / `MSTORE`) reachable through the ordinary `pallet-revive` EVM-call extrinsic path — no special privileges, proxy, or governance access required. It is fully deterministic and repeatable each block, bounded only by `EVM_MEMORY_BYTES` (1 MiB) per frame and `CALL_STACK_DEPTH` (25) per call chain, and by however many such transactions fit under the (mis-metered) block weight limit.

### Recommendation
Introduce an explicit memory-expansion charge in `Memory::resize` (or immediately before calling it in the `mload`/`mstore`/`mstore8`/`mcopy`/`calldatacopy` handlers), mirroring the EVM's memory-expansion gas formula (`3*Δwords + Δwords²/512`, or a weight-equivalent), charged via `charge_or_halt`/`adjust_weight` proportional to `target_len - current_len` before performing `self.data.resize(...)`, so the weight consumed accurately reflects the actual allocation/zero-fill work rather than only the fixed opcode base cost.

### Proof of Concept
Rust unit/benchmark-style test in `substrate/frame/revive/src/vm/evm/memory.rs` or an integration test in `substrate/frame/revive/src/tests`:
1. Deploy two EVM bytecodes: (a) `PUSH1 0; MSTORE` (offset 0, minimal expansion) and (b) `PUSH3 0xFFFE0; PUSH1 0; MSTORE` (offset near `EVM_MEMORY_BYTES - 32`, near-max expansion).
2. Execute both via the interpreter with equal starting gas, and using `FrameMeter`/`WeightMeter::weight_consumed()` assert that the two calls consume the **same** charged weight (proving no expansion surcharge exists today).
3. Additionally assert via `Instant::now()`/allocation counting (or a `#[bench]`) that wall-clock/allocated bytes for case (b) is orders of magnitude larger than case (a) despite equal charged gas — demonstrating the gas/weight vs. actual-cost mismatch.
4. Expected result after fix: weight consumed for case (b) should scale with the memory delta and be measurably larger than case (a).

	pub fn resize(&mut self, offset: usize, len: usize) -> ControlFlow<Halt> {
		let current_len = self.data.len();
		let target_len = revm::interpreter::num_words(offset.saturating_add(len)) * 32;
		if target_len > crate::limits::EVM_MEMORY_BYTES as usize {
			log::debug!(target: crate::LOG_TARGET, "check memory bounds failed: offset={offset} target_len={target_len} current_len={current_len}");
			return ControlFlow::Break(Error::<T>::OutOfGas.into());
		}

		if target_len > current_len {
			self.data.resize(target_len, 0);
		}

		ControlFlow::Continue(())
	}

pub fn mload<E: Ext>(interpreter: &mut Interpreter<E>) -> ControlFlow<Halt> {
	interpreter.ext.charge_or_halt(EVMGas(VERYLOW))?;
	let ([], top) = interpreter.stack.popn_top()?;
	let offset = as_usize_or_halt::<E::T>(*top)?;
	interpreter.memory.resize(offset, 32)?;
	*top = U256::from_big_endian(interpreter.memory.slice_len(offset, 32));
	ControlFlow::Continue(())
}

/// Implements the MSTORE instruction.
///
/// Stores a 32-byte word to memory.
pub fn mstore<E: Ext>(interpreter: &mut Interpreter<E>) -> ControlFlow<Halt> {
	interpreter.ext.charge_or_halt(EVMGas(VERYLOW))?;
	let [offset, value] = interpreter.stack.popn()?;
	let offset = as_usize_or_halt::<E::T>(offset)?;
	interpreter.memory.resize(offset, 32)?;
	interpreter.memory.set(offset, &value.to_big_endian());
	ControlFlow::Continue(())
}

/// Implements the MSTORE8 instruction.
///
/// Stores a single byte to memory.
pub fn mstore8<E: Ext>(interpreter: &mut Interpreter<E>) -> ControlFlow<Halt> {
	interpreter.ext.charge_or_halt(EVMGas(VERYLOW))?;
	let [offset, value] = interpreter.stack.popn()?;
	let offset = as_usize_or_halt::<E::T>(offset)?;
	interpreter.memory.resize(offset, 1)?;
	interpreter.memory.set(offset, &[value.byte(0)]);
	ControlFlow::Continue(())
}

/// Cost  for a single unit of EVM gas.
#[derive(Eq, PartialEq, Debug, Clone, Copy)]
pub struct EVMGas(pub u64);

impl<T: Config> Token<T> for EVMGas {
	fn weight(&self) -> Weight {
		let base_cost = T::WeightInfo::evm_opcode(1).saturating_sub(T::WeightInfo::evm_opcode(0));
		base_cost.saturating_mul(self.0)
	}
}
