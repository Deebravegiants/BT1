### Title
`NonFungiblesTransferAdapter::transfer_asset` never verifies `from` owns the NFT before delegating to `Assets::transfer`, and the underlying `Transfer` impls provide no ownership witness - ([File: polkadot/xcm/xcm-builder/src/nonfungibles_adapter.rs])

### Summary
`NonFungiblesTransferAdapter::transfer_asset` resolves `(class, instance)` via `Matcher::matches_nonfungibles` and calls `Assets::transfer(&class, &instance, &destination)` without ever checking that the XCM `from` Location (converted to an account) is the actual `Assets::owner(&class, &instance)`. The concrete `nonfungibles::Transfer` implementations for `pallet_uniques` and `pallet_assets`' nonfungibles adapters call `do_transfer(.., |_, _| Ok(()))`, a no-op ownership witness, meaning nothing downstream checks `from` either — the item is moved from whoever the storage says is the *current owner* to `destination`, regardless of `from`.

### Finding Description
In `transfer_asset` [1](#0-0) , `from` is used only to compute nothing — it is not passed to `Assets::transfer` at all, and there is no `ensure!(Assets::owner(&class, &instance) == Some(resolved_from))` check. The call only uses `class`, `instance`, and `destination`.

The concrete `Transfer::transfer` implementation for `pallet_uniques` confirms there is no ownership witness closure: [2](#0-1) 

That delegates to `Pallet::do_transfer`, which reads the *actual current owner* straight from storage (`Item::<T, I>::get`) and moves the item to `dest` — it never compares against any externally supplied `from`: [3](#0-2) 

So functionally, calling `NonFungiblesTransferAdapter::transfer_asset(what, from, to, ctx)` for a `(class, instance)` pair does **not** transfer "from `from`'s holdings to `to`" — it always moves whatever the pallet's storage currently says is owned by *whoever the real owner is*, to `to`, irrespective of `from`. This is different from the fungible-asset case where balances are debited from the specific account.

However, examining the actual reachable path in the XCM executor is essential to determine exploitability. `TransferAsset`/`TransferReserveAsset` always pass `origin_ref()` — the XCM message's cryptographically/structurally established origin (via `DescendOrigin`, sovereign-account conversion, `UniversalOrigin`, etc.) — as `from`: [4](#0-3) [5](#0-4) 

Since `from`/`origin_ref()` is entirely ignored by `transfer_asset` and by `Assets::transfer`, an attacker with **any** valid XCM origin (their own account, their own sovereign/descended account, etc.) can craft `TransferAsset { assets: <arbitrary class/instance>, beneficiary: <attacker-controlled account> }` and have the item moved to the beneficiary **even though the origin account never owned that item**. The only "check" that exists is the pallet-level `NoPermission` gate used by signed extrinsics like `pallet_uniques::transfer` / `pallet_nfts::transfer` — but that gate lives in the closure supplied by the **extrinsic call site**, not in the `nonfungibles::Transfer` trait implementation used by the XCM adapter. The XCM path calls `Pallet::do_transfer(.., |_, _| Ok(()))` directly, bypassing that permission closure entirely.

This confirms the audit's core claim: `transfer_asset` relies on no ownership check at all (not even indirectly through the pallet), because the `nonfungibles::Transfer::transfer` trait method used by the adapter is implemented with an always-`Ok` closure in `pallet_uniques`. There is no `NoPermission`-style rejection anywhere in this call chain for the adapter's use case.

### Impact Explanation
Any account capable of getting an XCM program executed with any origin (its own signed account executing `pallet_xcm::execute`, or a sovereign/reserve-transfer flow) can move an arbitrary NFT `(class, instance)` — one it does not own — to any destination account, as long as:
1. The runtime configures `NonFungiblesTransferAdapter`/`NonFungiblesAdapter` backed by `pallet_uniques`'s `nonfungibles::Transfer` impl (or any other impl using a no-op ownership closure) as (part of) its `AssetTransactor`, and
2. `Matcher::matches_nonfungibles` can resolve the targeted `(class, instance)` from an attacker-supplied `Asset` in the XCM message.

This is unauthorized theft/relocation of NFTs — the scoped impact matches exactly.

### Likelihood Explanation
Feasibility depends entirely on runtime configuration: this is exploitable only where the local chain's `AssetTransactor` uses this non-owner-checking adapter for local `TransferAsset`/`TransferReserveAsset` instructions against `pallet_uniques`-managed collections (or any `Transfer` impl lacking an ownership closure). `pallet_nfts`'s `Transfer` impl was not fully confirmed in this session (index did not return its exact closure), so it is uncertain whether `pallet_nfts` collections are similarly exposed — this should be verified directly. For `pallet_uniques`, the vulnerable code path is unambiguous and directly reachable through standard, unprivileged XCM execution (e.g., a signed user calling `pallet_xcm::execute` with a `TransferAsset` instruction, no special permissions required).

### Recommendation
In `NonFungiblesTransferAdapter::transfer_asset`, add an explicit ownership check before calling `Assets::transfer`:
```rust
let from_account = AccountIdConverter::convert_location(from)
    .ok_or(MatchError::AccountIdConversionFailed)?;
ensure!(Assets::owner(&class, &instance) == Some(from_account.clone()), XcmError::NoPermission);
```
Alternatively, extend the `nonfungibles::Transfer` trait to accept a `from` witness parameter (analogous to `ChangeOwnerFrom` used in `substrate/frame/uniques/src/asset_ops/item.rs`) and require all implementations, including `pallet_uniques`'s and `pallet_nfts`'s default `Transfer` impls, to verify the current owner matches `from` before performing the move.

### Proof of Concept
Integration test plan (xcm-executor level, using `pallet_uniques`):
1. Mint an NFT `(class=0, instance=0)` to account `OWNER`.
2. Configure XCM executor with `NonFungiblesAdapter`/`NonFungiblesTransferAdapter<Uniques, Matcher, AccountIdConverter, AccountId>` as `AssetTransactor`.
3. Execute an XCM program with origin resolving to `ATTACKER` (not `OWNER`), containing `TransferAsset { assets: [nft(class=0, instance=0)], beneficiary: ATTACKER_LOCATION }`.
4. Assert the instruction succeeds (`process_instruction` returns `Ok(())`) and `Uniques::owner(0, 0) == Some(ATTACKER)`, despite `ATTACKER` never having owned the item and `from` (origin) ≠ the previous owner.
5. Contrast with the signed-extrinsic path `pallet_uniques::Call::transfer` from `ATTACKER` for the same item, which correctly returns `Error::NoPermission`, proving the XCM adapter path bypasses the permission check that the extrinsic enforces.
