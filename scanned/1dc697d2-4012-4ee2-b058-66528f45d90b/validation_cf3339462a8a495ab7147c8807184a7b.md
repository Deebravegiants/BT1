Precision-loss griefing in `pallet-asset-rewards`'s `reward_per_token` leads to zero/reduced reward accrual for all stakers - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet-asset-rewards` (`substrate/frame/asset-rewards/src/lib.rs`) implements a staking-rewards accounting scheme that the pallet's own doc comment states is explicitly modeled on the Synthetix `StakingRewards.sol` design — the same lineage as the `MultiRewards.sol` contract in the external report. It computes a shared `reward_per_token_stored` accumulator using integer division scaled by a constant `PRECISION_SCALING_FACTOR = 4096` instead of Solidity's `1e18`. This much smaller scaling factor makes the truncation-to-zero griefing condition dramatically easier to trigger than in the original report, and any staker in a pool (even one holding a trivial or zero stake) can permissionlessly force reward-state updates on a per-block cadence via `stake`, `unstake`, or `harvest_rewards`, degrading rewards for every other staker in the same pool. [1](#0-0) [2](#0-1) 

### Finding Description
`reward_per_token` computes the incremental accrual since the last update using truncating integer division: [3](#0-2) 

```rust
Ok(pool_info.reward_per_token_stored.ensure_add(
    pool_info
        .reward_rate_per_block
        .ensure_mul(rewardable_blocks_elapsed.into())?
        .ensure_mul(PRECISION_SCALING_FACTOR.into())?
        .ensure_div(pool_info.total_tokens_staked)?,
)?)
```

This is structurally identical to the vulnerable pattern in `MultiRewards.sol`'s `rewardPerToken()`: `dt * rewardRate * SCALE / totalSupply`. Whenever `rewardable_blocks_elapsed * reward_rate_per_block * PRECISION_SCALING_FACTOR < total_tokens_staked`, `ensure_div` truncates the result to `0`, leaving `reward_per_token_stored` unchanged for that pool while `last_update_block` (via `update_pool_rewards`) still advances to the current block: [4](#0-3) 

Because `PRECISION_SCALING_FACTOR` is only `4096` (vs. `1e18` in the Solidity original), this zero-truncation condition is reachable with far more realistic pool parameters (e.g., `total_tokens_staked = 10_000_000`, `reward_rate_per_block = 1`: `1 * 1 * 4096 = 4096 < 10_000_000`).

The update path is triggered from every state-changing extrinsic (`stake`, `unstake`, `harvest_rewards`), all of which call the shared, pool-wide `update_pool_and_staker_rewards` / `update_pool_rewards` before doing anything else: [5](#0-4) [6](#0-5) 

Critically, `reward_per_token_stored` and `last_update_block` are pool-global state, not per-staker. Any account that is (or becomes) a staker in the pool — including one that stakes a trivial amount via `stake` — can call `stake`/`unstake` on itself every block (`caller == staker` bypasses the `BadOrigin` check in `unstake`/`harvest_rewards`) to keep `rewardable_blocks_elapsed` at `1` continuously, repeatedly hitting the truncation-to-zero branch and freezing `reward_per_token_stored` advancement for the whole pool, at the cost of ordinary transaction fees.

This differs from the original report's `getRewardForUser(address(0))` in one respect: `pallet-asset-rewards` extrinsics require the caller to be a staker (or the pool must be expired) rather than being fully open to any address regardless of stake. However, becoming "a staker" only requires calling `stake` once, so the barrier to executing the griefing loop is minimal and does not require any privileged role.

Separately from the full-zero griefing case, every single invocation of `update_pool_and_staker_rewards`/`reward_per_token` — even outside the zero-truncation edge case — discards the division remainder `(rewardable_blocks_elapsed * reward_rate_per_block * PRECISION_SCALING_FACTOR) % total_tokens_staked` with no carry-forward mechanism, causing a permanent, continuously-accumulating precision loss identical in nature to the one described in the external report.

### Impact Explanation
Medium. In the general case, this results in a slow, continuous, unrecoverable precision loss of reward tokens for every pool using this pallet (dust that is never distributed to any staker, permanently idle in the pool's reward account until an admin eventually reclaims it via `cleanup_pool`, which itself requires the pool to be fully empty of stakers). In the worst case — pools with high `total_tokens_staked` relative to `reward_rate_per_block * PRECISION_SCALING_FACTOR` — an unprivileged staker can drive `reward_per_token_stored` to a standstill for an arbitrary duration by repeatedly calling `stake`/`unstake`/`harvest_rewards` with a 1-block cadence, denying honest stakers rewards they are otherwise entitled to for that period. Funds are not permanently lost from the chain (reward assets remain recoverable by the admin through `cleanup_pool` once the pool empties), but legitimate stakers are deprived of expected yield, which is an economic griefing/DoS on the reward-distribution mechanism.

### Likelihood Explanation
Medium. It requires specific but realistic pool configurations (large `total_tokens_staked` and/or small `reward_rate_per_block`) relative to the small `PRECISION_SCALING_FACTOR = 4096`, which is far less forgiving than Solidity's `1e18` and makes the exploitable condition more attainable in practice. Since `pallet-asset-rewards` pool creation is currently permissioned (`CreatePoolOrigin`), the pool's parameters are chosen by a trusted party, but stakers who then join a pool with unfavorable parameters are ordinary, unprivileged accounts, and the griefing loop (`stake`/`unstake`/`harvest_rewards` every block) requires no special privilege, only standard transaction fees. [7](#0-6) 

### Recommendation
Track the truncated remainder from `reward_per_token`'s division and carry it forward to the next `update_pool_rewards` invocation (analogous to the mitigation suggested in the external report), so no accrual is silently dropped regardless of how frequently the update path is invoked. Additionally, consider increasing `PRECISION_SCALING_FACTOR` (e.g., using a `u128`/fixed-point representation with much higher precision, similar in spirit to `pallet-nomination-pools`'s `FixedU128`-based `RewardCounter`, which was deliberately designed with accuracy-notes to avoid this class of truncation, see `current_reward_counter`) to shrink the practical window in which `rewardable_blocks_elapsed * reward_rate_per_block * PRECISION_SCALING_FACTOR < total_tokens_staked` can occur. [8](#0-7) 

### Proof of Concept
Given a pool with `total_tokens_staked = T` and `reward_rate_per_block = R` such that `R * PRECISION_SCALING_FACTOR < T` (e.g., `T = 10_000_000`, `R = 1`, `PRECISION_SCALING_FACTOR = 4096`):

1. Attacker (or any existing staker) calls `stake(pool_id, small_amount)` once to register as a `PoolStaker`.
2. In every subsequent block, the attacker calls `stake(pool_id, 0)` (or `unstake`/`harvest_rewards` on themselves), which invokes `update_pool_and_staker_rewards` → `reward_per_token`:
   - `rewardable_blocks_elapsed = 1`
   - `1 * R * 4096 = 4096 < T = 10_000_000` → `ensure_div` truncates to `0`
   - `reward_per_token_stored` unchanged, but `last_update_block` advances to `now`.
3. Repeating this every block for the duration of interest means `reward_per_token_stored` never advances, so `derive_rewards` for all other stakers in the pool computes zero additional reward for that entire period, even though `reward_rate_per_block` continued to notionally accrue. [9](#0-8) 

This mirrors the PoC pattern in the external report (`dt = totalSupply / (rewardRate * SCALE)`, then repeatedly invoking the permissionless update path for `dt`-sized intervals across the whole reward duration).

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
