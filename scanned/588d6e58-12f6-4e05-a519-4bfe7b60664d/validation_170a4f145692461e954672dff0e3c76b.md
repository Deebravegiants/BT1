### Title
Stale `PendingSwap` entries survive `deregister`, allowing an unrelated para (after ParaId reuse) to complete a swap and trigger unintended `OnSwap::on_swap` fund/deposit reassignment - (File: polkadot/runtime/common/src/paras_registrar/mod.rs)

### Summary
`Pallet::deregister` / `do_deregister` only clears `PendingSwap::<T>::remove(id)` for the entry keyed by the deregistering `id`, but never scans for or removes entries where `id` appears as the *value* (i.e., where another para previously called `swap(other_key, id)`). Because `ParaId`s are freely reused after deregistration/re-reservation, a completely unrelated future para that is assigned the same numeric id can satisfy the stale `PendingSwap::get(other) == Some(id)` match check in `swap`, causing `Pallet::swap`/`do_thread_and_chain_swap` to execute `T::OnSwap::on_swap` against a para that the original initiator never intended to swap with.

### Finding Description
In `swap` (`polkadot/runtime/common/src/paras_registrar/mod.rs:326-370`), the two-step confirmation protocol works as follows:
1. First caller `A` calls `swap(A, B)`. Since `PendingSwap::get(B) != Some(A)`, the `else` branch executes `PendingSwap::insert(A, B)` (line 366) — i.e., stores key=`A` -> value=`B`.
2. Second caller (owning `B`) calls `swap(B, A)`. The check `PendingSwap::get(A) == Some(B)` (line 340) succeeds, matching the entry stored in step 1, and the swap proceeds via `do_thread_and_chain_swap` (line 704) or directly `T::OnSwap::on_swap` (line 359), followed by `PendingSwap::remove(other)` (line 364) — note this only clears the *other* key, not the initiator's key `A`, but that's a separate minor issue.

The critical defect is in `do_deregister` (`polkadot/runtime/common/src/paras_registrar/mod.rs:660-676`):
```rust
PendingSwap::<T>::remove(id);
```
This only removes the map entry keyed by the deregistering `id`. If `id` was instead the *target* (`other`) of someone else's still-pending swap (i.e., some other key `K` maps to `id`), that stale entry `K -> id` is **not** removed when `id` deregisters.

Exploit flow:
1. Para `A` (lease-holding Parachain) calls `swap(A, B)` where `B` is a Parathread it wishes to swap with. This inserts `PendingSwap: A -> B`.
2. `B` deregisters (permitted since `deregister` only requires the para be a Parathread and caller be Root/owner/self, per `do_deregister` lines 660-665) before ever confirming the swap. `do_deregister(B)` removes `PendingSwap::remove(B)` (a no-op, since the stale entry is keyed by `A`, not `B`), leaving `PendingSwap: A -> B` intact.
3. The numeric id `B` becomes free and is reserved/registered again by an attacker as an entirely new, unrelated Parathread (id reuse is expected/observed behavior, e.g., per the `end_to_end_scenario_works` test pattern).
4. The attacker, controlling the new para at id `B`, calls `swap(B, A)`. `Pallet::swap`'s permission check `ensure_root_para_or_owner(origin, id=B)` passes trivially since the attacker legitimately owns the new para at id `B`. The match check `PendingSwap::get(A) == Some(B)` (line 340) evaluates true because the stale entry `A -> B` from step 1 is still present and numerically matches the reused id.
5. This satisfies the "opposite swap pending" condition and executes `do_thread_and_chain_swap`/`T::OnSwap::on_swap(A, B)`, even though `A`'s original counterparty no longer exists and the current owner of `B` never coordinated with `A`.

The `swap` extrinsic's only authorization check is on the `id` parameter (the caller's own para); it inherently trusts the `PendingSwap` map as evidence of a prior, still-valid consent from the counterpart. That trust is broken because the map is not invalidated when the counterpart para is destroyed and its numeric id recycled.

### Impact Explanation
`T::OnSwap::on_swap` is wired to the crowdloan pallet's `on_swap`, which swaps per-para records (crowdloan fund/lease deposit associations) between the two para ids. If an unrelated, attacker-controlled para is substituted for the originally-intended counterpart via id reuse, the crowdloan/deposit state for para `A` can be reassigned to the attacker's para without `A`'s knowledge or a genuine confirming action from the real intended counterpart, which is a deposit/fund-reassignment vulnerability matching the scoped impact (unauthorized parachain manager/fund reassignment via stale swap state).

### Likelihood Explanation
This requires: (a) an initiator to call `swap` and never receive a genuine confirmation, (b) the counterpart para to be deregistered before confirming, and (c) an attacker to acquire the freed numeric id and call the confirming `swap`. All three steps use ordinary signed extrinsics (`swap`, `deregister`, `reserve`/`register`) available to any para manager; no privileged access is required. ParaId reuse after deregistration is an established, expected system behavior. The main uncertainty is timing — the attacker must win the race to reserve the freed id before anyone else, and `A`'s manager must not clear its own stale pending entry (e.g., via `swap(A, A)` to reset) before the attacker acts — but there is no code-enforced protection against this window; it is purely opportunistic/race-dependent, not prevented by any check.

### Recommendation
When deregistering a para (`do_deregister`), scan for and remove any `PendingSwap` entry whose *value* equals the deregistering `id` (not just the entry keyed by `id`), or better, maintain a reverse index so that both directions of a pending swap are invalidated atomically whenever either counterpart's para is deregistered. Additionally, consider requiring that `PendingSwap::insert` also be cleared automatically whenever the lifecycle of either para in the pair changes, so stale pairings can never be resurrected via id reuse.

### Proof of Concept

#[test]
fn stale_pending_swap_survives_deregister_and_matches_unrelated_para() {
    new_test_ext().execute_with(|| {
        // 1. Register para A as a Parachain (lease-holding) and para B as a Parathread.
        run_to_block(1);
        register_para(A); // ... upgrade A to Parachain via existing helpers
        register_para(B); // Parathread

        // 2. A initiates swap(A, B).
        assert_ok!(Registrar::swap(para_origin(A), A, B));
        assert_eq!(PendingSwap::<Test>::get(A), Some(B));

        // 3. B deregisters without ever confirming.
        assert_ok!(Registrar::deregister(para_origin(B), B));
        // Assert the stale entry keyed by A is NOT cleared (demonstrating the bug):
        assert_eq!(PendingSwap::<Test>::get(A), Some(B));

        // 4. Attacker reserves/registers a brand-new, unrelated para reusing id B.
        assert_ok!(Registrar::reserve(RuntimeOrigin::signed(ATTACKER)));
        // ensure reused id equals old B numeric value (force via force_register if needed)
        assert_ok!(Registrar::register(RuntimeOrigin::signed(ATTACKER), B, genesis_head, validation_code));

        // 5. Attacker completes the "swap" against A, without A's fresh consent.
        assert_ok!(Registrar::swap(para_origin(B), B, A));

        // Assertion: swap succeeded and OnSwap fired for A <-> attacker's new B,
        // even though A never coordinated with the new owner of B.
        System::assert_has_event(Event::<Test>::Swapped { para_id: B, other_id: A }.into());
        // Verify crowdloan fund/deposit records for A were reassigned to attacker's para B.
    });
}

			Self::ensure_root_para_or_owner(origin, id)?;

			// If `id` and `other` is the same id, we treat this as a "clear" function, and exit
			// early, since swapping the same id would otherwise be a noop.
			if id == other {
				PendingSwap::<T>::remove(id);
				return Ok(());
			}

			// Sanity check that `id` is even a para.
			let id_lifecycle =
				paras::Pallet::<T>::lifecycle(id).ok_or(Error::<T>::NotRegistered)?;

			if PendingSwap::<T>::get(other) == Some(id) {
				let other_lifecycle =
					paras::Pallet::<T>::lifecycle(other).ok_or(Error::<T>::NotRegistered)?;
				// identify which is a lease holding parachain and which is a parathread (on-demand
				// parachain)
				if id_lifecycle == ParaLifecycle::Parachain &&
					other_lifecycle == ParaLifecycle::Parathread
				{
					Self::do_thread_and_chain_swap(id, other);
				} else if id_lifecycle == ParaLifecycle::Parathread &&
					other_lifecycle == ParaLifecycle::Parachain
				{
					Self::do_thread_and_chain_swap(other, id);
				} else if id_lifecycle == ParaLifecycle::Parachain &&
					other_lifecycle == ParaLifecycle::Parachain

					// If both chains are currently parachains, there is nothing funny we
					// need to do for their lifecycle management, just swap the underlying

	fn do_deregister(id: ParaId) -> DispatchResult {
		match paras::Pallet::<T>::lifecycle(id) {
			// Para must be a parathread (on-demand parachain), or not exist at all.
			Some(ParaLifecycle::Parathread) | None => {},
			_ => return Err(Error::<T>::NotParathread.into()),
		}
		polkadot_runtime_parachains::schedule_para_cleanup::<T>(id)
			.map_err(|_| Error::<T>::CannotDeregister)?;

		if let Some(info) = Paras::<T>::take(&id) {
			<T as Config>::Currency::unreserve(&info.manager, info.deposit);
		}

		PendingSwap::<T>::remove(id);
		Self::deposit_event(Event::<T>::Deregistered { para_id: id });
		Ok(())
	}
