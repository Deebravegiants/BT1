### Title
pallet-psm treats external "stablecoins" as unconditionally worth 1:1 with the internal stablecoin — no on-chain price check, only reactive/manual circuit breakers - (File: substrate/frame/psm/src/lib.rs)

### Summary
`pallet-psm` implements a Peg Stability Module that mints/burns an internal stablecoin against approved external assets (e.g. USDC, USDT) at a hard-coded 1:1 rate, adjusted only for decimals — never for actual market price. This is the same root-cause pattern as the Blueberry `ChainlinkAdapterOracle` finding: an asset that is assumed to track a peg (WBTC≈BTC, or here external stablecoin≈$1/internal) is priced without any live on-chain price verification. If any approved external asset depegs, the pallet keeps minting/redeeming it at par, letting anyone extract "good" reserve assets from the shared per-instance reserve using freshly minted internal tokens backed by the depegged (now worthless) collateral.

### Finding Description
`mint()` converts `external_amount` to the internal asset purely via decimal scaling (`external_to_internal`/`internal_to_external`), with no reference to any market or oracle price: [1](#0-0) 

`redeem()` similarly burns the internal asset and pays out the external asset 1:1 (minus fee), again using only decimal conversion: [2](#0-1) 

Both externals for a given `internal_asset` are held in the **same shared reserve account** (`psm_account`), derived once per internal asset: [3](#0-2) 

Because the internal asset minted from *any* approved external is fungible, a user who mints internal tokens using a depegged/near-worthless external asset can immediately redeem those same internal tokens for a *different, healthy* external asset in the same PSM instance (as long as that other external's own `PsmDebt` ceiling allows it, which is populated by other users' legitimate deposits over time): [4](#0-3) [5](#0-4) 

The only defense against a depegging external is a **manually operated** circuit breaker (`set_asset_status`), which must be triggered by the `full_admin` or `emergency_admin`, not an automatic, price-driven halt: [6](#0-5) 

The README explicitly documents this as reactive governance tooling ("Level | Minting | Redemption | Use Case"), confirming there is no automated on-chain price feed gating mint/redeem: [7](#0-6) 

This is corroborated by the runtime's own `MonetaryGuard` governance track, added specifically to allow "fast PSM circuit breaker activation in case of a depeg or exploit" — i.e. the protocol authors are aware that depeg is only handled by out-of-band governance reaction, not by an automated oracle safeguard, exactly the gap the Blueberry report calls out: [8](#0-7) 

### Impact Explanation
If any approved external asset (e.g. USDC) depegs below $1 (as happened during the March 2023 USDC/SVB event), any unprivileged, signed user can:
1. Buy the depegged external asset cheaply off-chain/on a DEX.
2. Call `mint` to deposit it into the PSM and receive internal stablecoin at the assumed 1:1 par rate.
3. Call `redeem` against a *different*, still-healthy external asset held in the same shared reserve, extracting real value.

This drains the PSM's healthy collateral, leaving the protocol holding the depegged/worthless asset while genuine users redeeming internal stablecoin against healthy assets find the reserve depleted — i.e., the protocol accrues real bad debt equal to the depeg gap × amount minted, exactly analogous to the WBTC/BTC oracle bad-debt scenario. Given the PSM's core purpose is to guarantee the internal stablecoin's peg, this can also propagate a run on the internal stablecoin itself.

### Likelihood Explanation
Likelihood is realistic and does not require any privileged role: `mint`/`redeem` are public, signed-origin extrinsics reachable by anyone. Stablecoin depegs are a known, recurring real-world event (USDC/SVB 2023, USDT historical dips, algorithmic stablecoin failures). Response depends entirely on governance/admin latency to call `set_asset_status`, during which the exploit window is open. The attack requires only capital to acquire depegged assets and knowledge of the PSM's mint/redeem mechanics — no special access or race condition needed.

### Recommendation
- Integrate an on-chain price reference (e.g. `pallet-oracle`, already present in this repository) to validate that an external asset's live price is within an acceptable band of its peg before allowing `mint`, and consider disabling `redeem` for other externals once a depeg is detected.
- Add an automatic, price-driven circuit breaker (analogous to the report's recommendation of a liquidity/oracle threshold trigger) rather than relying solely on manual `set_asset_status` calls from `full_admin`/`emergency_admin`.
- Consider isolating reserves per external asset (rather than a single shared reserve account) so that a depeg in one external cannot be used to drain reserves backing a different, healthy external.

### Proof of Concept
Given a PSM instance for internal asset `pUSD` with two approved externals, USDC and USDT, both funded through normal usage so that `PsmDebt[pUSD, USDT] > 0`:
1. USDC depegs to $0.50 on secondary markets.
2. Attacker buys 1,000,000 USDC for $500,000.
3. Attacker calls `Psm::mint(origin, pUSD, USDC, 1_000_000, max_fee)` — receives ~995,000 pUSD (minus 0.5% fee), per: [9](#0-8) 
4. Attacker calls `Psm::redeem(origin, pUSD, USDT, 995_000, max_fee)` — as long as `PsmDebt[pUSD, USDT] >= 995_000` (built from legitimate prior USDT deposits) and reserve holds sufficient USDT, the call succeeds per: [5](#0-4) 
5. Attacker walks away with ~$990,000 worth of real USDT for a $500,000 outlay in depegged USDC, leaving the PSM insolvent by the depeg gap; no admin action is needed to allow this transaction sequence since the circuit breaker defaults to `AllEnabled` and must be manually flipped.

## Circuit Breaker

Each approved external on each instance has an independent circuit breaker
with three levels:

| Level             | Minting | Redemption | Use Case                          |
| ----------------- | ------- | ---------- | --------------------------------- |
| `AllEnabled`      | Allowed | Allowed    | Normal operation                  |
| `MintingDisabled` | Blocked | Allowed    | Drain debt from a problematic external |
| `AllDisabled`     | Blocked | Blocked    | Full emergency halt of an external |

`set_asset_status` is callable at both the `Full` (`full_admin`) and
`Emergency` (`emergency_admin`) levels.
