## Analog Vulnerability Found

### Title
Unchecked/panicking ABI-decode of ERC20 `transfer` boolean return value causes runtime panic on non-compliant contracts - (File: `substrate/frame/revive/src/impl_fungibles.rs`)

### Summary
`pallet-revive`'s `fungibles::Mutate` implementation treats any PolkaVM contract address as an ERC-20 asset and calls the Solidity `transfer(address,uint256)` selector to move funds during `mint_into`/`burn_from`. Unlike the sibling implementation in `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`, which decodes the boolean return value defensively via `abi_decode_returns_validate` with proper error propagation, this code path uses `.expect("Failed to ABI decode")`, which panics the runtime if the callee returns anything other than a well-formed `bool`.

### Finding Description
In `substrate/frame/revive/src/impl_fungibles.rs`, both `burn_from` and `mint_into` perform an ERC20-style `transfer` call and then decode the result: [1](#0-0) [2](#0-1) 

Both call sites use `bool::abi_decode_validate(&return_value.data).expect("Failed to ABI decode")`. If the target contract does not revert but returns data that cannot be decoded as a `bool` (e.g., it returns a `uint256`, empty bytes, or any other non-boolean payload — exactly the "inconsistent ERC20 implementation" scenario described in the external report), this `.expect()` will panic instead of gracefully erroring out.

By contrast, the equivalent logic in the asset-hub `ERC20Transactor` correctly treats this exact scenario as a recoverable error: [3](#0-2) 

The existing test suite even documents that this exact behavior (a contract that "doesn't return bool" instead reverting) is expected to fail gracefully, not panic: [4](#0-3) 

The comment above the `fungibles::Mutate` impl in `impl_fungibles.rs` states these functions are consumed by `xcm_builder::FungiblesAdapter`: [5](#0-4) 

Because the asset id for this implementation is defined to be an arbitrary contract address (`type AssetId = H160`, "the asset id of an ERC20 is its origin contract's address"): [6](#0-5) 

any user who can deploy a PolkaVM/Solidity contract can craft a "fake ERC20" whose `transfer` selector returns malformed data instead of reverting or returning a proper `bool`, and if a runtime wires `pallet_revive::Pallet<T>` as the `Assets` type of a generic `xcm_builder::FungiblesAdapter` (as opposed to the safer, purpose-built `ERC20Transactor`), triggering a `mint_into`/`burn_from` against that contract will panic instead of returning an `Err`.

### Impact Explanation
A panic during on-chain STF execution is far more severe than the "false instead of revert" issue from the original report: while the original ERC20 bug can lead to accounting inconsistencies if callers don't check the boolean, this analog can cause a runtime panic during block execution, which is a defensive-programming violation that risks halting block production/import (a chain-halt/DoS class issue) rather than merely a logic bug.

### Likelihood Explanation
Likelihood depends on whether any shipped runtime actually wires `pallet_revive::Pallet<T>` as the `Assets` generic parameter of the plain `xcm_builder::FungiblesAdapter` (which invokes `mint_into`/`burn_from`), as opposed to using the hardened `ERC20Transactor` exclusively. I was only able to confirm that `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs` (the safe path) is referenced from `asset-hub-westend`'s `xcm_config.rs`; I could not fully verify, within the remaining tool budget, whether the generic/unsafe `fungibles::Mutate` impl in `impl_fungibles.rs` is also reachable from a live runtime's XCM configuration versus being dead code retained only to satisfy the trait bound. This reachability question is the key uncertainty that would need to be resolved (e.g., by grepping all `AssetTransactors`/`FungiblesAdapter<pallet_revive::Pallet<Runtime>, ...>` instantiations across all in-scope runtimes) before this could be escalated with full confidence.

### Recommendation
Replace the `.expect("Failed to ABI decode")` calls in `burn_from`/`mint_into` (`substrate/frame/revive/src/impl_fungibles.rs`, lines ~191-192 and ~229-230) with the same defensive pattern already used in `erc20_transactor.rs` (`IERC20::transferCall::abi_decode_returns_validate(...).map_err(...)`), returning a clean `DispatchError` instead of panicking when the callee returns malformed data.

### Proof of Concept
1. Deploy a PolkaVM contract whose `transfer(address,uint256)` selector does not revert and returns non-boolean data (e.g., a `uint256` value), analogous to the `MyTokenFake` fixture used in `asset-hub-westend`'s test suite [7](#0-6) .
2. If a runtime's XCM `Config::AssetTransactor` uses `xcm_builder::FungiblesAdapter<pallet_revive::Pallet<Runtime>, ...>` (rather than the dedicated `ERC20Transactor`), submit an XCM `WithdrawAsset`/`DepositAsset` instruction referencing that contract's address as the asset id.
3. `mint_into`/`burn_from` in `impl_fungibles.rs` calls `bool::abi_decode_validate(...).expect(...)`, which panics because the returned data isn't a valid `bool`, instead of returning a graceful `XcmError`/`DispatchError`.
