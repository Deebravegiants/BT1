Target: ShopifyAPI::Auth::Oauth::AuthQuery#to_signable_string. Attacker action: send a callback where the `code` query parameter contains a value that, once run through Rack's `application/x-www-form-urlencoded` parsing, decodes to a string containing a literal `+` character (e.g. raw bytes `code=abc%2Bdef`), so `auth_query.code == \"abc+def\"`. Preconditions: none beyond a normally embedded app. Call sequence: `AuthQuery.new(code: \"abc+def\", ...)` -> `to_signable_string` -> `URI.encode_www_form({code: \"abc+def\", ...})`, which re-encodes the `+` back to `%2B`. Binding: bytes signed by Shopify (raw query bytes Shopify used to compute `hmac`) == bytes `HmacValidator` recomputes over via `to_signable_string`. Since `URI.encode_www_form` always canonically percent-encodes, this specific case round-trips correctly, but the same mechanism means any value containing characters with multiple valid percent-encodings (e.g. `%2B` vs `+` vs raw `+`) is normalized before signing, so the assumption 'the string Shopify signed' and 'the string HmacValidator recomputes' are byte-identical only if Shopify used the same canonicalization. Impact: Critical, authentication bypass if a crafted encoding causes the recomputed signable string to differ from what Shopify actually hashed while still matching an attacker-obtainable HMAC for a different value. Proof idea: minitest asserting `AuthQuery.new(code: \"abc+def\", ...).to_signable_string` produces `code=abc%2Bdef...` and comparing against a `hmac` computed by the test over the *raw* pre-decode query string to show any divergence.
