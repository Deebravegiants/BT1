Target: ShopifyAPI::Utils::HmacValidator.validate + ShopifyAPI::Auth::Oauth::AuthQuery#to_signable_string. Attacker action: an attacker who installs the app on their own dev shop receives a genuine callback GET /auth/callback?code=X&host=H&shop=S&state=T&timestamp=NOW&hmac=VALID, then also appends an extra query key `shop[]=other-shop.myshopify.com` or a duplicate `shop=other-shop.myshopify.com` before Rack/`request.parameters.symbolize_keys` builds the hash passed into `AuthQuery.new`. Preconditions: host app builds `AuthQuery.new(request.parameters.symbolize_keys.except(:controller, :action))` as documented in docs/usage/oauth.md. Call sequence: `Oauth.validate_auth_callback` -> `HmacValidator.validate(auth_query)` -> `auth_query.to_signable_string` (only reads the five ivars set at construction). Binding that breaks: set(fields read by Rack into the AuthQuery ivars) == set(fields inside `to_signable_string`) is assumed by the caller, but if Rack collapses duplicate/array keys before `AuthQuery.new` runs, the ivar value used for `Session.new(shop: auth_query.shop)` may not equal the single `shop` value Shopify actually signed. Impact: Critical, cross-tenant access - the token exchange in `Oauth.validate_auth_callback` line `null_session = Auth::Session.new(shop: auth_query.shop)` could bind an access token to a shop value never covered by the HMAC that was actually validated. Proof idea: minitest constructing `AuthQuery.new` directly with a `shop` value the mock HMAC was computed over, then asserting `HmacValidator.validate` still returns true if `auth_query.shop` is swapped for a different string post-construction (proving the validator never re-derives the five fields from a canonical source, only from whatever ivars were passed to it, unvalidated).
