Target: ShopifyAPI::Utils::HmacValidator.validate + OpenSSL.secure_compare. Attacker action: send a callback with `hmac` set to an empty string or a string of a different, non-hex length than a real SHA256 hex digest. Preconditions: standard embedded app. Call sequence: `validate(verifiable_query)` -> `return false unless verifiable_query.hmac` (empty string is truthy in Ruby, not nil, so this guard doesn't stop it) -> `validate_signature` -> `OpenSSL.secure_compare(computed_signature, T.must(received_signature))`. Binding: `received_signature` (`auth_query.hmac`) must be a value Shopify actually computed with `Context.api_secret_key` over exactly `to_signable_string`; `secure_compare` correctly returns false for any mismatch length/content, so this specific call is safe, but the guard `return false unless verifiable_query.hmac` only defends against `nil`/`false`, not an empty string, meaning any downstream code path relying on 'hmac was present' rather than 'hmac was valid' could be misled. Impact: High, authentication-bypass risk only if any caller checks `auth_query.hmac.present?` instead of the boolean result of `HmacValidator.validate` before acting - a caller misuse edge, included here strictly to test the boundary of the guard itself. Proof idea: minitest calling `HmacValidator.validate` with a crafted `AuthQuery` whose `hmac` is `\"\"` and asserting the method still correctly returns `false` (defending the binding rather than breaking it) — used as a boundary/regression check.
