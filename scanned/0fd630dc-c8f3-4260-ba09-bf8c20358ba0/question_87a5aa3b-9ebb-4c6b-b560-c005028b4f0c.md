Target: ShopifyAPI::Webhooks::Request#to_signable_string / #hmac (contrast case for the same root cause as HmacValidator, since both implement `Utils::VerifiableQuery`). Attacker action: POST a webhook body plus a duplicated `X-Shopify-Shop-Domain` header set to the attacker's own shop, but craft the raw body's `id` field (or any body field the app acts on) to reference another merchant's resource id, since `to_signable_string` returns only `@raw_body` verbatim and `shop` is read from a header never included in that signed string. Preconditions: app has a webhook handler that trusts `Webhooks::Request#shop` (from `shopify_header(\"shop-domain\")`) to route to a per-shop record. Call sequence: `Request.new(raw_body:, headers:)` -> `HmacValidator.validate` on a `VerifiableQuery` whose `hmac` reads `shopify-hmac-sha256` header and whose `to_signable_string` returns `@raw_body` only, never the `shop-domain` header. Binding: SIGNATURE COVERAGE fails - `shop`, `topic`, `webhook_id`, `api_version` are all read from headers that are entirely outside `to_signable_string`, so the equality set(fields acted on) == set(fields inside `to_signable_string`) is violated for every webhook, not just this scope's five OAuth fields. Impact: Critical, cross-tenant access - since the attacker owns a valid webhook subscription (their own shop) with a genuinely Shopify-signed body+hmac, they can potentially cause the header `shopify-shop-domain` to be manipulated by any intermediary/proxy in the host app's stack without invalidating the signature, letting one shop's payload be attributed to another shop.
