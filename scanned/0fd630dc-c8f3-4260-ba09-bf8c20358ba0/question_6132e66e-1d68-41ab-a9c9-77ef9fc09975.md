Target: ShopifyAPI::Webhooks::Request#shopify_header case/prefix normalization (contrast with `AuthQuery`'s lack of normalization). Attacker action: register the attacker's own webhook endpoint on their own dev shop (as permitted), and send a forged HTTP POST directly to the app's webhook endpoint (not through Shopify) with headers `HTTP_X_SHOPIFY_SHOP_DOMAIN: victim-shop.myshopify.com`, `HTTP_X_SHOPIFY_HMAC_SHA256: <attacker's own valid hmac for their own raw_body>`, and a `raw_body` referencing the attacker's own resource, attempting to get the app to process it as belonging to `victim-shop`. Preconditions: app passes raw Rack env headers straight into `Webhooks::Request.new(headers: ...)` per the documented normalization (`sub(\"http_\", \"\").gsub(\"_\", \"-\")`). Call sequence: `Request.new` normalizes headers -> `hmac` reads `shopify-hmac-sha256` -> `HmacValidator.validate(request)` computes HMAC over `to_signable_string == @raw_body` using `Context.api_secret_key`; since the attacker doesn't know `api_secret_key`, they cannot forge a valid `hmac` for this body regardless of the `shop-domain` header value. Binding: SIGNATURE COVERAGE fails specifically for `shop` in webhooks (it is read from a header entirely outside `to_signable_string`, i.e. `@raw_body`), but this particular attack still requires attacker to already possess a valid `hmac`-covering signature for the body, which they can only get from Shopify signing their own shop's webhook - meaning the header can be swapped post-signature without invalidating HMAC. Impact: Critical, cross-tenant access - a webhook genuinely signed by Shopify for the attacker's own shop can have its `shop-domain` header rewritten (e.g. by a malicious/compromised intermediary the attacker controls, or the attacker's own webhook receiver forwarding logic) to any string, and `HmacValidator.validate` will still return true because `shop` never entered `to_signable_string`. Proof idea: minitest building `Webhooks::Request.new(raw_body: real_body, headers: headers_with_shop_A)`, computing a real HMAC over `real_body` with the test's `Context.api_secret_key`, confirming `HmacValidator.validate` returns true, then swapping `headers[\"x-shopify-shop-domain\"]` to shop B and asserting validation still returns true - proving `request.shop` is unauthenticated relative to the impact scope named in this file's Critical finding.
