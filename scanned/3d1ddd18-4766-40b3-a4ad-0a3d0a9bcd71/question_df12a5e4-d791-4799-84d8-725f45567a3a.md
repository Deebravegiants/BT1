Target: authHandleToIntentsUserId case 'tron' via tronAddressToHex. Attacker input: a base58 string decoding to exactly 21 bytes (version 0x41 + 20-byte hash) with no 4-byte checksum appended, i.e. any base58 encoding of raw 21 bytes. Preconditions: tronAddressToHex only checks payload.length >= 21 and payload[0] === 0x41, never validating a checksum (tronAddressToHex.ts:9-19). Call sequence: attacker crafts base58(21-byte payload) which is NOT a valid Tron address (fails validateTronBase58Address's sha256d checksum check in validateAddress.ts), submits it as their auth identifier, integrator calls authHandleToIntentsUserId(identifier, 'tron') to derive signer_id, then signs and submits an intent with that signer_id. Equality that breaks: DESTINATION TRUTH / identity truth — the tron address used to derive signer_id was never validated as a real, checksummed Tron account, so signer_id in the signed payload may not equal any account a real private key controls. Scoped impact: High — a malformed identifier is silently accepted as a valid signer identity, letting an attacker mint an intents user id from junk bytes that could collide with or spoof another format. Whose funds: any counterparty relying on this identity being a genuine Tron account. Proof idea: vitest test constructing base58.encode(new Uint8Array([0x41, ...20 random bytes])) (21 bytes, no checksum), calling tronAddressToHex and authHandleToIntentsUserId(..., 'tron'), asserting no exception is thrown despite validateTronBase58Address(address) returning false for the same string.
