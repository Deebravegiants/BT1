### Title
Response cache key omits `WorkflowID`, causing cross-workflow cached HTTP response reuse for the same workflow owner - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
The gateway's `responseCache` for the HTTP Action capability keys cached responses by `OutboundHTTPRequest.Hash()`, which (per `TestRequestHash`) intentionally excludes `WorkflowID` while including `WorkflowOwner`, method, URL, headers and body. The component's own README states the cache is "scoped by workflow ID to prevent cross-workflow data leakage," but the implementation does not honor that guarantee — the cache key is not actually workflow-scoped at the workflow-instance level, only at the owner level. Like the TWAP staleness bug (where a cached/derived value is treated as fresh/correctly-scoped without validating the actual freshness window), here a cached value computed in the context of one workflow is served to a different workflow under the same owner without any workflow-identity check, because the "freshness/identity" check the code relies on (the hash) omits a field that the documentation claims is used for isolation.

### Finding Description
`responseCache.Fetch`/`Set`/`isExpiredOrNotCached` all key entries by `req.Hash()`: [1](#0-0) [2](#0-1) 

The struct comment says the hash is derived from "method, URL, headers, body, workflowOwner" — `WorkflowID` is not part of the key: [3](#0-2) 

This is confirmed by the unit test, which explicitly asserts that differing `WorkflowID` values produce the *same* hash, while differing `WorkflowOwner` values produce different hashes: [4](#0-3) [5](#0-4) 

Yet the component's README explicitly documents workflow-ID-level isolation as a security property of the cache: [6](#0-5) 

The cache is populated/read from `makeOutgoingRequest`, driven directly by attacker/customer-controlled `OutboundHTTPRequest` fields (`Method`, `URL`, `Headers`/`MultiHeaders`, `Body`, `CacheSettings`) that are unmarshalled from node/workflow JSON-RPC messages without any per-workflow-instance scoping check: [7](#0-6) 

Consequently, two different workflows deployed by the same `WorkflowOwner` (which is a realistic condition — one owner can operate many workflows) that happen to issue an outbound HTTP request with the same method/URL/headers/body will collide on the same cache entry. This breaks the "Workflow Isolation" guarantee stated in the README and can result in one workflow instance receiving a cached HTTP response (potentially containing another workflow's request-specific secrets templated into the URL/body/headers matching by coincidence, or simply stale/incorrect business data) that was actually fetched for a different workflow context. This is directly analogous to the TWAP bug: a value is served as if it reflects the current/authorized context, but the mechanism meant to validate that context (the cache key / "consult" check) omits the discriminating dimension (`WorkflowID` vs. block timestamp elapsed), so a stale/mis-scoped value is silently reused.

### Impact Explanation
Impact is bounded by the owner boundary: an unprivileged workflow author can only collide with other workflows they themselves own (since `WorkflowOwner` is part of the key), so this is not a direct cross-tenant secret leak between different owners. However, it does violate the explicitly documented workflow-level isolation, and for owners running multiple workflows sharing similar outbound HTTP call shapes, one workflow's cached HTTP response (which may embed workflow-specific dynamic query parameters/body baked from that workflow's own confidential inputs) can be served to a sibling workflow. It also means `CacheSettings.MaxAgeMs`/`Store` interplay between unrelated workflow instances of the same owner is unpredictable, undermining the correctness guarantee developers reasonably rely on based on the README. This is a functional/data-integrity issue rather than a full authentication/session bypass.

### Likelihood Explanation
High likelihood of accidental triggering: any owner running more than one workflow that calls the same external `URL`/`Method` with identical (or templated-to-identical) headers/body will silently share cache entries whenever `CacheSettings.MaxAgeMs > 0`. No special attacker action is required beyond normal workflow deployment behavior available to any unprivileged workflow owner.

### Recommendation
Include `WorkflowID` (or another workflow-instance-scoping identifier) in `OutboundHTTPRequest.Hash()`'s input, so cached entries are truly scoped to the workflow instance as documented, not just to the workflow owner. Update `TestRequestHash`'s "having different workflowID results in same Hash" test to reflect the corrected, workflow-scoped behavior instead of asserting the current (incorrect) behavior.

### Proof of Concept
1. Deploy two workflows under the same `WorkflowOwner`, Workflow A and Workflow B, where both call the HTTP Action capability with identical `Method`, `URL`, and (post-templating) `Headers`/`Body`, and set `CacheSettings.Store = true`, `CacheSettings.MaxAgeMs = <nonzero>`.
2. Workflow A's request runs first via `gatewayHandler.makeOutgoingRequest` → `responseCache.Fetch`, fetches the live response, and stores it keyed by `req.Hash()`.
3. Workflow B issues the "same" request (different `WorkflowID`, same `WorkflowOwner`/method/URL/headers/body). Per `TestRequestHash` ("having different workflowID results in same Hash"), `req.Hash()` is identical to Workflow A's, so `Fetch`'s fast path (`response_cache.go` lines 71-77) returns Workflow A's cached response to Workflow B without making a new outbound call — even though the README promises workflow-scoped isolation.

// isExpiredOrNotCached returns true if the cached response is expired or not cached.
// IMPORTANT: this method does not lock the cache map. MUST be called with cacheMu write-locked.
func (rc *responseCache) isExpiredOrNotCached(req gateway.OutboundHTTPRequest) bool {
	cachedResp, exists := rc.cache[req.Hash()]
	if !exists || time.Now().After(cachedResp.storedAt.Add(rc.ttl)) {
		return true
	}
	return false
}

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	// Slow path: singleflight deduplicates concurrent fetches per key.
	// Cache check + store happen inside the flight so the key isn't released
	// until the result is cached, closing the race window between singleflight
	// completion and cache write.
	result, _, _ := rc.flight.Do(cacheKey, func() (any, error) {
		// Re-check cache: a previous flight may have just stored the result.
		rc.cacheMu.RLock()
		cachedResp, exists := rc.cache[cacheKey]
		rc.cacheMu.RUnlock()
		if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
			rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
			return cachedResp.response, nil
		}

		response := fetchFn()

		if storeOnFetch && isCacheableStatusCode(response.StatusCode) {
			rc.cacheMu.Lock()
			rc.cache[cacheKey] = &cachedResponse{
				response: response,
				storedAt: time.Now(),
			}
			rc.cacheMu.Unlock()
		}

		return response, nil
	})

	return result.(gateway.OutboundHTTPResponse)
}

	requestID := resp.ID
	h.lggr.Debugw("handling outgoing message", "requestID", requestID, "nodeAddr", nodeAddr)
	var req gateway_common.OutboundHTTPRequest
	err := json.Unmarshal(*resp.Result, &req)
	if err != nil {
		return fmt.Errorf("failed to unmarshal HTTP request from node %s: %w", nodeAddr, err)
	}
	timeout := time.Duration(req.TimeoutMs) * time.Millisecond
	httpReq := network.HTTPRequest{
		Method:           req.Method,
		URL:              req.URL,
		Headers:          req.Headers, //nolint:staticcheck // forward deprecated Headers for backward compatibility; request uses MultiHeaders when set
		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}

	sendResponseTimeout := time.Duration(defaultSendResponseTimeoutMs) * time.Millisecond

	// send response to node async
	h.wg.Go(func() {
		// not cancelled when parent is cancelled to ensure the goroutine can finish
		baseCtx := context.WithoutCancel(ctx)
		httpCtx, httpCancel := context.WithTimeout(baseCtx, timeout)
		defer httpCancel()
		l := logger.With(h.lggr, "requestID", requestID, "method", req.Method, "timeout", req.TimeoutMs)
		var outboundResp gateway_common.OutboundHTTPResponse
		callback := h.createHTTPRequestCallback(httpCtx, requestID, httpReq, req)
		if req.CacheSettings.MaxAgeMs > 0 {
			h.metrics.IncrementCacheReadCount(ctx, h.lggr)
			outboundResp = h.responseCache.Fetch(httpCtx, req, callback, req.CacheSettings.Store)
		} else {
			outboundResp = callback()
			if req.CacheSettings.Store {
				h.responseCache.Set(req, outboundResp)
