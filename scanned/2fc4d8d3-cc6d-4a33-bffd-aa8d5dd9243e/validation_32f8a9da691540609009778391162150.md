### Title
User enumeration via distinguishable login error messages on `/sessions` endpoint - (File: `core/sessions/localauth/orm.go`)

### Summary
The unauthenticated `POST /sessions` login endpoint returns different, verbatim error messages depending on whether the submitted email exists in the `users` table versus whether the email exists but the password is wrong. Because the raw error is serialized back to the client in the JSON API error body, an unauthenticated caller can distinguish "unknown email" from "known email, wrong password," enabling user enumeration — the same bug class as CVE-2023-38871 (Economizzer).

### Finding Description
The login flow is:
1. `SessionsController.Create` binds the request and calls `AuthenticationProvider().CreateSession(ctx, sr)`. [1](#0-0) 

2. `CreateSession` (local auth ORM) first looks up the user by email. If the email is not found, the raw DB/driver error (e.g. `sql.ErrNoRows`) is returned immediately. If the email is found but the password check fails, a distinct hardcoded error `"Invalid password"` is returned instead: [2](#0-1) 

3. Back in the controller, any error from `CreateSession` is passed straight into `jsonAPIError`, which serializes `err.Error()` into the JSON response body sent to the client: [3](#0-2) [1](#0-0) 

This means the HTTP response body content differs based on whether the email exists (`"sql: no rows in result set"`/DB-specific not-found text) versus whether it exists with a bad password (`"Invalid password"`), directly leaking account existence to an unauthenticated caller. The route is registered without authentication, only rate-limiting: [4](#0-3) 

The existing test suite only asserts on status codes for the negative cases, not on response body content, so this behavioral difference is not currently caught by tests: [5](#0-4) 

The same pattern (distinct "Invalid email" vs "Invalid password" error paths) also exists in the OIDC and LDAP local-fallback login paths: [6](#0-5) [7](#0-6) 

### Impact Explanation
An unauthenticated attacker can enumerate valid Chainlink node operator/admin email addresses by observing the distinct error text returned from `POST /sessions`. This is low-direct-impact on its own (CWE-203, information disclosure) but materially assists credential-stuffing or targeted password-guessing/brute-force attacks against node admin accounts, and is the same class of vulnerability as the referenced advisory.

### Likelihood Explanation
The endpoint is internet-facing (subject only to rate limiting, no authentication) and requires only a single POST request per probed email, so exploitation is straightforward for any unprivileged network client that can reach the node's web server.

### Recommendation
Normalize the error returned to the client for both the "email not found" and "wrong password" cases in `CreateSession` (all three authenticator implementations) to a single generic message (e.g., `"invalid email or password"`), and ensure `jsonAPIError` does not leak the underlying DB/driver error text to the client for this path. Additionally, consider adding a constant-time delay (already partially mitigated by password hashing cost) so the unknown-email path takes comparable time to the wrong-password path.

### Proof of Concept
```
# Case 1: unknown email
curl -i -X POST https://node/sessions \
  -H 'Content-Type: application/json' \
  -d '{"email":"doesnotexist@example.com","password":"whatever"}'
# -> body contains raw DB error, e.g. "sql: no rows in result set"

# Case 2: known email, wrong password
curl -i -X POST https://node/sessions \
  -H 'Content-Type: application/json' \
  -d '{"email":"knownadmin@example.com","password":"wrongpassword"}'
# -> body contains "Invalid password"
```
The differing response bodies allow an attacker to confirm which of the two probed emails is a registered node user.

func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}

// jsonAPIError adds an error to the gin context and sets
// the JSON value of errors.
func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}

// localLoginFallback tests the credentials provided against the 'local' authentication method
// This covers the case of local CLI API calls requiring local login separate from the OIDC server
func (oi *oidcAuthenticator) localLoginFallback(ctx context.Context, sr clsessions.SessionRequest) (clsessions.User, error) {
	var user clsessions.User
	err := oi.ds.GetContext(ctx, &user, SQLSelectUserbyEmail, sr.Email)
	if err != nil {
		return user, err
	}
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		oi.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return user, errors.New("invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		oi.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return user, errors.New("invalid password")
	}

	return user, nil
}

func (l *ldapAuthenticator) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	conn, err := l.ldapClient.CreateEphemeralConnection()
	if err != nil {
		return "", errors.New("unable to establish connection to LDAP server with provided URL and credentials")
	}
	defer conn.Close()

	var returnErr error

	// Attempt to LDAP Bind with user provided credentials
	escapedEmail := ldap.EscapeFilter(strings.ToLower(sr.Email))
	searchBaseDN := fmt.Sprintf("%s=%s,%s,%s", l.config.BaseUserAttr(), escapedEmail, l.config.UsersDN(), l.config.BaseDN())
	if err = conn.Bind(searchBaseDN, sr.Password); err != nil {
		l.lggr.Infof("Error binding user authentication request in LDAP Bind: %v", err)
		returnErr = errors.New("unable to log in with LDAP server. Check credentials")
	}

	// Bind was successful meaning user and credentials are present in LDAP directory
	// Reuse FindUser functionality to fetch user roles used to create ldap_session entry
	// with cached user email and role
	foundUser, err := l.FindUser(ctx, escapedEmail)
	if err != nil {
		l.lggr.Infof("Successful user login, but error querying for user groups: user: %s, error %v", escapedEmail, err)
		returnErr = errors.New("log in successful, but no assigned groups to assume role")
	}

	isLocalUser := false
	if returnErr != nil {
		// Unable to log in against LDAP server, attempt fallback local auth with credentials, case of local CLI Admin account
		// Successful local user sessions can not be managed by the upstream server and have expiration handled by the reaper sync module
		foundUser, returnErr = l.localLoginFallback(ctx, sr)
		isLocalUser = true
	}

	// If err is still populated, return
	if returnErr != nil {
		return "", returnErr
	}
