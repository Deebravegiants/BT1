### Title
Unbounded metric label cardinality via attacker-controlled JSON-RPC `method` field in Gateway user-message handler - ([File: core/services/gateway/gateway.go])

### Summary
The Gateway's public HTTP user-facing endpoint decodes an incoming JSON-RPC request and, without any allowlist validation, uses the attacker-supplied `method` string as a metric attribute value on every request. This mirrors the disclosed timestamp-authority bug class (CWE-770: unbounded resource consumption from unvalidated metric label values), except here the unbounded value is the JSON-RPC `method` field rather than the HTTP path.

### Finding Description
In `gateway.ProcessRequest`, the gateway decodes the raw request body via `jsonrpc2.DecodeRequest` and `g.codec.DecodeJSONRequest`, then sets: [1](#0-0) 
```
	var method string
	...
	if isLegacyRequest {
		method = msg.Body.Method
		err = h.HandleLegacyUserMessage(ctx, msg, callback)
	} else {
		method = jsonRequest.Method
		err = h.HandleJSONRPCUserMessage(ctx, jsonRequest, callback)
	}
```
This `method` value — taken directly from the client-supplied JSON-RPC request without any allowlist or normalization — is then recorded as a metric attribute on every request outcome path: [2](#0-1) 
```
		g.gMetrics.RecordUserMsgHandlerDuration(ctx, method, response.String(), duration)
		g.gMetrics.RecordUserMsgHandlerInvocation(ctx, method, response.String())
		return newError(jsonRequest.ID, response, "handler timeout: "+err.Error())
	}
	g.gMetrics.RecordUserMsgHandlerDuration(ctx, method, response.ErrorCode.String(), duration)
	g.gMetrics.RecordUserMsgHandlerInvocation(ctx, method, response.ErrorCode.String())
```
These calls feed into `GatewayMetrics.RecordUserMsgHandlerDuration`/`RecordUserMsgHandlerInvocation`, which attach the raw `method` string directly as an OpenTelemetry attribute with no allowlist or normalization step: [3](#0-2) 
```
func (m *GatewayMetrics) RecordUserMsgHandlerDuration(ctx context.Context, method string, responseCode string, duration time.Duration) {
	m.userMsgHandleDuration.Record(ctx, duration.Milliseconds(), metric.WithAttributes(
		attribute.String("method", method),
		attribute.String("responseCode", responseCode),
	))
}

func (m *GatewayMetrics) RecordUserMsgHandlerInvocation(ctx context.Context, method string, responseCode string) {
	m.userMsgHandleCount.Add(ctx, 1, metric.WithAttributes(
		attribute.String("method", method),
		attribute.String("responseCode", responseCode),
	))
}
```
The gateway's user-facing HTTP server (`httpServer.handleRequest`) accepts unauthenticated public requests, reads the raw body, and forwards it directly into `ProcessRequest` for processing before any handler-level validation of the `method` field occurs: [4](#0-3) 
This is structurally identical to the disclosed bug class: a globally-registered metrics recording path executes on every incoming request using an attacker-controlled, high-cardinality string as a label/attribute value, with no allowlist of expected values and no normalization to a static placeholder for unrecognized values.

### Impact Explanation
An unauthenticated external caller can send an arbitrary, unique `method` value (or JSON-RPC `Method` in the legacy path) on every request to the gateway's public user endpoint. Because the metric backend (OpenTelemetry meter / beholder exporter, potentially Prometheus-compatible) allocates a persistent time series per unique attribute combination, an attacker can drive unbounded memory growth in the gateway process purely by varying the `method` string across requests, resulting in denial of service (CWE-770, matching CVSS impact profile of the referenced advisory: availability impact, no confidentiality/integrity impact, no privileges required).

### Likelihood Explanation
The `ProcessRequest` function is the primary entry point for all incoming JSON-RPC gateway requests and is reachable by any unauthenticated client that can reach the gateway's user port; the `method` field is fully attacker-controlled JSON content, requiring no valid DON ID, no valid service name, and no successful handler dispatch to trigger the metric recording (the metric is recorded regardless of whether the handler ultimately succeeds, times out, or the service/DON lookup fails earlier — though note: if `serviceName`/`donID` lookup fails, the function returns before reaching the metric-recording lines, so the attacker must supply a valid service name/DON ID to reach this code path, which is a mild but not blocking constraint since ShardedDON/service names are typically documented/discoverable).

### Recommendation
Restrict the `method` value recorded as a metric attribute to a fixed allowlist of expected/known method names (mirroring the upstream patch's approach of allowlisting paths/methods and mapping anything else to a static `"unrecognized"`/`"unknown"` value) before passing it to `RecordUserMsgHandlerDuration`/`RecordUserMsgHandlerInvocation` in `core/services/gateway/gateway.go`. Alternatively, cap/validate the length and character set of `method` and bucket unrecognized values into a single static label.

### Proof of Concept
1. Send repeated POST requests to the gateway's public user HTTP endpoint with a valid `serviceName`/DON ID but a distinct, randomly generated `method` string in the JSON-RPC payload on each request (e.g., `method: "x-<uuid>"`).
2. Each unique `method` value causes `gateway.ProcessRequest` (`core/services/gateway/gateway.go:267-290`) to record a new OTel metric series via `GatewayMetrics.RecordUserMsgHandlerDuration`/`RecordUserMsgHandlerInvocation` (`core/services/gateway/monitoring/metrics.go:51-63`) with `method` as an unbounded-cardinality attribute.
3. Repeating this at volume causes continuous growth of the underlying metric time-series store in the exporter/registry, exhausting memory over time — an unauthenticated remote DoS.
