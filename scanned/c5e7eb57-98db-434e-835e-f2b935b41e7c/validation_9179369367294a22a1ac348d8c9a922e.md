Based on my investigation, I found a genuine, concretely reachable analog in the gateway's internet-facing HTTP entrypoint.

### Title
Unauthenticated Amplification / Resource-Exhaustion via Missing Allowlist-Rate-Limiting in Gateway `HandleLegacyUserMessage` - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
Any unprivileged client that can reach the Gateway's public HTTP endpoint can submit signed but otherwise unauthenticated `web_api_trigger` messages. The receiving handler explicitly skips allowlist/rate-limit checks (a `TODO` in the code) before fanning each request out to every member of the DON and inserting an entry into a shared, mutex-guarded `savedCallbacks` map. This mirrors the Solana bug class from the report: unthrottled, high-volume client-originated messages fan out and pile up server-side state/work faster than it can be reclaimed, degrading or exhausting node resources.

### Finding Description
The Gateway HTTP server passes every incoming request straight to `gateway.ProcessRequest` with no authentication/authorization gate: [1](#0-0) . `ProcessRequest` only validates message structure/signature format and dispatches based on method/DON ID to the target handler's `HandleLegacyUserMessage`: [2](#0-1) .

For the WebAPI capabilities handler, `HandleLegacyUserMessage` performs basic payload/staleness checks but explicitly has **no allowlist or rate-limiting** before accepting the request, as marked by its own `TODO`: [3](#0-2) . Every accepted request is stored into `h.savedCallbacks` (a shared map protected by a single mutex) and then fanned out with `don.SendToNode` calls to **every member of the DON**: [4](#0-3) .

The map is only bounded/reclaimed on a periodic timer (`defaultCallbackPruneIntervalSec = 30`), and the code comment itself concedes it "could briefly exceed" the configured cap under load: [5](#0-4) , with pruning logic only running on tick: [6](#0-5) .

Because there is no per-sender/per-IP throttling on this path (unlike the sibling `nodeRateLimiter` used for node-originated traffic in `handleWebAPIOutgoingMessage`), an unprivileged client can submit a high volume of distinct `web_api_trigger` messages (varying `MessageID`) faster than the 30-second prune cycle can reclaim them. Each accepted message also triggers `len(donConfig.Members)` outbound `SendToNode` calls, amplifying a single client request into N node-directed messages — directly analogous to the Solana incident where unthrottled transactions were amplified into resource pressure that crashed validating nodes.

### Impact Explanation
An unprivileged actor with network access to the Gateway's HTTP listener can:
- Grow `savedCallbacks` and hold the handler's mutex repeatedly, contending with legitimate node-response processing (`HandleNodeMessage` also takes the same mutex).
- Multiply load onto every DON member via the fan-out `SendToNode` loop, amplifying a single cheap client request into DON-wide traffic.
- Sustain this for the full 30-second prune window before any eviction occurs, and the comment acknowledges the cap can be transiently exceeded.

This is a Medium-severity denial-of-service/resource-exhaustion risk on the internet-facing Gateway component, consistent with the "Medium" severity of the cited Solana DDoS analog.

### Likelihood Explanation
High-likelihood: the vulnerable code path is reachable by any client capable of POSTing a validly-signed legacy JSON-RPC message to the Gateway HTTP endpoint — no session, API key, or allowlist membership is required for this specific handler, and the missing control is explicitly flagged as a `TODO` in the source rather than an oversight requiring deep exploitation.

### Recommendation
Implement the allowlist/rate-limiting the code's own `TODO` calls for in `HandleLegacyUserMessage` (and analogous `HandleJSONRPCUserMessage` paths) before accepting into `savedCallbacks` or fanning out to `donConfig.Members` — e.g., reuse the existing `ratelimit.RateLimiter` pattern already applied to node-originated traffic (`nodeRateLimiter`) for per-sender/per-IP throttling of user-originated messages, and consider bounding/rejecting inserts synchronously (not just via periodic pruning) once `MaxSavedCallbacks` is reached.

### Proof of Concept
1. Identify a Gateway HTTP endpoint hosting a DON configured with the `capabilities` `WebAPIHandler`.
2. Script repeated `POST` requests of legacy `web_api_trigger` messages, each with a unique `MessageID`, valid signature, and current timestamp (satisfying `payload.Timestamp` and `MaxAllowedMessageAgeSec` checks) — see `triggerRequest` test helper for the exact shape required: [7](#0-6) .
3. Send these at a rate exceeding what the 30-second prune cycle can reclaim, with no credentials beyond a valid signing key.
4. Observe growth of `savedCallbacks`, mutex contention with `HandleNodeMessage`, and amplified `SendToNode` traffic to every DON member per accepted request.

func triggerRequest(t *testing.T, key *ecdsa.PrivateKey, topics []string, methodName, timestamp, payload string) *api.Message {
	messageID := "12345"
	if methodName == "" {
		methodName = MethodWebAPITrigger
	}
	if timestamp == "" {
		timestamp = strconv.FormatInt(time.Now().Unix(), 10)
	}
	donID := "workflow_don_1"
	var payloadJSON []byte
	if payload == "" {
		ts, err := strconv.ParseInt(timestamp, 10, 64)
		require.NoError(t, err)
		reqPayload := webapicap.TriggerRequestPayload{
			TriggerId:      "web-api-trigger@1.0.0",
			TriggerEventId: "action_1234567890",
			Timestamp:      ts,
			Topics:         topics,
			Params: webapicap.TriggerRequestPayloadParams(map[string]any{
				"bid": "101",
				"ask": "102",
			}),
		}
		payloadJSON, err = json.Marshal(reqPayload)
		require.NoError(t, err)
	} else {
		payloadJSON = []byte(payload)
	}
	msg := &api.Message{
		Body: api.MessageBody{
			MessageID: messageID,
			Method:    methodName,
			DonID:     donID,
			Payload:   json.RawMessage(payloadJSON),
		},
	}
	err := msg.Sign(key)
	require.NoError(t, err)
	err = msg.Validate()
	require.NoError(t, err)
	return msg
}
