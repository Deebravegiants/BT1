### Title
Unvalidated nil `req.Params` dereference in Vault gateway `PublicKeyGet` path causes node-crashing panic - (File: core/capabilities/vault/gw_handler.go)

### Summary
`GatewayHandler.HandleGatewayMessage` dispatches `vaulttypes.MethodPublicKeyGet` directly to `handlePublicKeyGet` without first running it through `GatewayVaultRequestProcessor.ProcessRequest`/`ValidateStructureBeforeAuth`, unlike the `SecretsCreate`/`SecretsUpdate`/`SecretsDelete`/`SecretsList` methods. [1](#0-0)  `handlePublicKeyGet` immediately dereferences `*req.Params` with no nil check, unlike the request-processor methods that explicitly guard `req.Params == nil` before unmarshalling. [2](#0-1) 

### Finding Description
On the node side, `gatewayConnector.readLoop` reads raw JSON-RPC messages arriving over the websocket from the Gateway, decodes them into `jsonrpc.Request[json.RawMessage]`, looks up the registered handler for `req.Method`, and calls `handler.HandleGatewayMessage` synchronously inside that goroutine — with no `recover()` wrapping. [3](#0-2) 

For the Vault capability, `HandleGatewayMessage` routes `MethodPublicKeyGet` straight to `handlePublicKeyGet(ctx, gatewayID, req)` without any authorization or structural validation step (contrast with the `SecretsCreate/Update/Delete/List` branches, which call `h.requestProcessor.ProcessRequest(...)` first). [1](#0-0)  `handlePublicKeyGet` then does `json.Unmarshal(*req.Params, r)` — dereferencing `req.Params` without checking it for `nil`. [2](#0-1)  If a `PublicKeyGet` JSON-RPC request arrives with `"params"` omitted or `null`, `req.Params` will be a nil `*json.RawMessage`, and dereferencing it panics with a nil pointer dereference — the exact bug class in CVE-2017-1000200 (externally triggered NULL pointer dereference in a message-handling callback).

Because this panic occurs inside the connector's `readLoop` goroutine with no recovery, an unrecovered panic in Go terminates the entire process, not just the goroutine — turning a malformed message into a full node crash (DoS), matching the CVE's "daemon crash via malformed message" pattern rather than a benign per-request error.

This is distinct from `handleSecretsDelete`/`handleSecretsList`, which are only reached after `ProcessRequest` has already validated and re-marshalled `req.Params` (so by the time those functions dereference `*req.Params` it is guaranteed non-nil) [4](#0-3) ; `handlePublicKeyGet` has no equivalent guard anywhere in its call path.

### Impact Explanation
An external, unauthenticated party able to reach the Gateway's public vault endpoint (or any node relay path that ultimately forwards a `MethodPublicKeyGet` JSON-RPC message to a node) can crash a node's process by sending a request with a null/absent `params` field. This is a remote, pre-authentication denial-of-service against node availability — no valid allowlist membership, JWT, or workflow ownership is required for `MethodPublicKeyGet`, since it's the only Vault method dispatched without going through the `Authorizer`/`GatewayVaultRequestProcessor` pipeline.

### Likelihood Explanation
Reaching this code only requires being able to submit a `PublicKeyGet` JSON-RPC request with missing/null `params` to a node via the gateway relay. Since `PublicKeyGet` is intentionally unauthenticated (it just returns the node's public key), this is a very low-effort trigger for any party who can talk to the gateway's public HTTP endpoint. I was not able to fully trace whether the gateway-side handler (`core/services/gateway/handlers/vault/handler.go`) performs any pre-forwarding validation that guarantees non-nil `params` before relaying the message to nodes — that would need to be checked in `newHandlerWithAuthorizer`/`HandleJSONRPCUserMessage` in that file to fully confirm end-to-end unauthenticated-client reachability. If the gateway does perform such validation, the practical attacker would need to be a Gateway (or someone who can forge a Gateway-to-node websocket message), which is a higher-privilege actor.

### Recommendation
Add a `req.Params == nil` guard in `handlePublicKeyGet` (and audit all other `GatewayHandler` methods dispatched outside `GatewayVaultRequestProcessor.ProcessRequest` for the same class of bug), returning a `UserMessageParseError` response instead of dereferencing a nil pointer. Additionally, wrap `gatewayConnector.readLoop`'s per-message handler dispatch in `core/services/gateway/connector/connector.go` with `recover()` so a panic in any single handler cannot bring down the entire node process.

### Proof of Concept
1. As an external client, send a JSON-RPC request routed to a node's Vault gateway handler with:
```json
{"jsonrpc":"2.0","id":"1","method":"vault_publicKeyGet"}
```
(no `"params"` key, or `"params": null`).
2. The message is decoded on the node side into `jsonrpc.Request[json.RawMessage]{Method: "vault_publicKeyGet", Params: nil}` and dispatched via `readLoop` → `HandleGatewayMessage` → `handlePublicKeyGet`.
3. `json.Unmarshal(*req.Params, r)` dereferences a nil `*json.RawMessage`, panicking; because this happens in the un-recovered `readLoop` goroutine, the panic propagates and crashes the node process.

Note: full confirmation of unauthenticated end-to-end reachability requires reviewing whether `core/services/gateway/handlers/vault/handler.go` validates/rejects nil `params` for `MethodPublicKeyGet` before relaying to nodes, which I could not fully verify within available context.

func (c *gatewayConnector) readLoop(gatewayState *gatewayState) {
	defer c.closeWait.Done()
	ctx, cancel := c.shutdownCh.NewCtx()
	defer cancel()

	for {
		select {
		case <-c.shutdownCh:
			return
		case item := <-gatewayState.conn.ReadChannel():
			var req jsonrpc.Request[json.RawMessage]
			err := json.Unmarshal(item.Data, &req)
			if err != nil {
				c.lggr.Errorw("parse error when reading from Gateway", "id", gatewayState.config.ID, "err", err)
				break
			}
			c.handlersMu.RLock()
			handler, exists := c.handlers[req.Method]
			c.handlersMu.RUnlock()
			if !exists {
				c.lggr.Errorw("no handler for method", "id", gatewayState.config.ID, "method", req.Method)
				break
			}
			// do not break on error. HandleGatewayMessage handles errors
			// by sending a response back to the Gateway.
			err = handler.HandleGatewayMessage(ctx, gatewayState.config.ID, &req)
			if err != nil {
				c.lggr.Warnw("failed to handle message from Gateway", "id", gatewayState.config.ID, "method", req.Method, "err", err)
			}
		}
	}
