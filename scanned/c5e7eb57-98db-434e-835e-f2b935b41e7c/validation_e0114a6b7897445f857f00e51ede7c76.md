### Title
Sensitive credentials (passwords) bypass log redaction and are disclosed in plaintext web request debug logs due to shallow top-level-only JSON key matching - (File: core/web/router.go)

### Summary
The Chainlink node's HTTP request logging middleware (`loggerFunc`) logs the request body for every API call at Debug level, applying a "redaction" pass (`readSanitizedJSON`) intended to mask sensitive fields such as passwords. However, this redaction only inspects the top-level keys of the parsed JSON object, not nested objects. All GraphQL mutations (served at `/query`) wrap their real arguments inside a nested `variables.input` object, so fields like `oldPassword`, `newPassword`, and `password` never appear as top-level keys and are therefore logged in plaintext whenever Debug-level logging is enabled — directly analogous to the Elasticsearch `emit_request_body` audit logging issue where sensitive request content (passwords/tokens) ends up unredacted in logs.

### Finding Description
The middleware reads and logs the raw request body for every request through the gin router: [3](#0-2) 

The sanitization function only walks the first level of the JSON map: [4](#0-3) 

The blacklist matching only redacts a key if it matches (or contains) `password` at that top level: [5](#0-4) 

This works correctly for REST endpoints where the request body has flat JSON, e.g. `UpdatePasswordRequest{OldPassword, NewPassword}` bound directly at top level [6](#0-5) , or `ChangeAuthTokenRequest{Password}` used by `NewAPIToken`/`DeleteAPIToken` [7](#0-6) .

However, all GraphQL mutations are sent as `POST /query` with a body shaped `{"query": "...", "variables": {"input": {...}}}` [8](#0-7) . Password-bearing mutations such as `UpdateUserPassword` (`Input.OldPassword`, `Input.NewPassword`) [9](#0-8)  and `CreateAPIToken` (`Input.Password`) [2](#0-1)  place the sensitive value two levels deep (`variables.input.password`). Since `readSanitizedJSON` never recurses into nested `map[string]any` values, these fields are logged verbatim whenever the node logs at Debug level.

### Impact Explanation
If the node operator raises log level to Debug (a supported, documented configuration, not a misconfiguration bypass) — the same class of "verbose/debug logging enabled" precondition as the original Elasticsearch `emit_request_body` audit setting — an authenticated GUI/API user's plaintext password (old and new) is written into the node's log stream. Because Chainlink node logs are frequently shipped to centralized log aggregation systems, this creates a path for anyone with read access to node logs (which may be a broader set of people/systems than those with database or admin credential access) to obtain user passwords, mirroring the disclosure vector described in the Elasticsearch CVE.

### Likelihood Explanation
Likelihood depends on the operator enabling Debug-level logging, which is a documented and reasonably common operational setting for troubleshooting, not a rare or exotic configuration. Any authenticated GraphQL user's own password-change action, or an admin's `CreateAPIToken`/password-reset actions performed via the GraphQL API, would trigger this exposure automatically — no additional attacker action beyond using the API's normal password-change/token-creation flow is required.

### Recommendation
Make `readSanitizedJSON` recursively sanitize nested maps/arrays (not just the top-level object) so that any key matching the blacklist at any nesting depth is redacted, matching the intent already expressed by `isBlacklisted`.

### Proof of Concept
1. Set node log level to `debug`.
2. As an authenticated user, send a GraphQL mutation to `/query`:
```json
{
  "query": "mutation($input: UpdatePasswordInput!) { updateUserPassword(input: $input) { ... } }",
  "variables": { "input": { "oldPassword": "CurrentSecret123!", "newPassword": "NewSecret456!" } }
}
```
3. Inspect the node's Debug logs emitted by `loggerFunc` for this request; the `body` field will contain the full `variables` object including `oldPassword` and `newPassword` in plaintext, because `readSanitizedJSON` only redacts the top-level keys `query`/`variables`, not the nested `input.oldPassword`/`input.newPassword`.

func readSanitizedJSON(buf *bytes.Buffer) (string, error) {
	var dst map[string]any
	err := json.Unmarshal(buf.Bytes(), &dst)
	if err != nil {
		return "", err
	}

	cleaned := map[string]any{}
	for k, v := range dst {
		if isBlacklisted(k) {
			cleaned[k] = "*REDACTED*"
			continue
		}
		cleaned[k] = v
	}

	b, err := json.Marshal(cleaned)
	if err != nil {
		return "", err
	}
	return string(b), err
}
