### Title
Unsynchronized concurrent map access in workflow JWT authorization (data race enabling authorization bypass/crash) - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` reads the `authorizedKeys` map without holding `h.mu`, while the periodic `syncMetadata` goroutine replaces that same map under `h.mu.Lock()`. This is the same bug class as CVE-2022-3567 (a race condition between two code paths accessing shared state without proper synchronization), here occurring on the gateway's request-authorization path that is reachable by any external caller sending an HTTP-trigger workflow request.

### Finding Description
`Authorize` is invoked per incoming request to validate the JWT signer against the workflow's `authorizedKeys`: [1](#0-0) 

Note it accesses `h.authorizedKeys[workflowID]` directly with no `h.mu.RLock()`/`RUnlock()` around the read.

Meanwhile, `syncMetadata` runs on a background ticker (`h.runTicker(...)` started in `Start`) and replaces the entire `authorizedKeys` map under the write lock: [2](#0-1) [3](#0-2) 

All other accessors of shared handler state (`WorkflowShards`, `GetWorkflowID`, `GetWorkflowReference`) correctly take `h.mu.RLock()`, confirming that `Authorize` is missing the required lock: [4](#0-3) [5](#0-4) 

`Authorize` is called from the HTTP trigger request handling path, which processes requests originating from unprivileged, internet-facing clients hitting the gateway: [6](#0-5) 

Because Go's built-in `map` type is not safe for concurrent read/write, a concurrent `Authorize` (unlocked read) and `syncMetadata` (locked write, but that doesn't protect the reader) constitutes a data race. In the Go runtime, a concurrent unsynchronized map read during a write can either: (a) return a stale or partially-updated map reference/value producing an incorrect authorization decision (e.g., authorizing against an about-to-be-replaced key set, or looking up in a workflow-ID entry deleted by a metadata resync), or (b) trigger the runtime's "concurrent map read and map write" fatal error, crashing the node process (denial of service). Unlike the kernel CVE, which is a race in socket state teardown reachable from local processes, this is a race in request-authorization state reachable from any client issuing HTTP trigger requests to the gateway while the DON is actively resyncing workflow metadata (a periodic, always-running background process).

### Impact Explanation
- Availability: an unprivileged remote caller can send trigger requests during metadata resync windows, increasing the likelihood of hitting Go's concurrent map access fatal error and crashing the gateway node handler process — a real, low-cost DoS vector, especially given `syncMetadata` runs on every `MetadataAggregationIntervalMs` tick indefinitely.
- Integrity of authorization: because the read side is unsynchronized, there is a window where an authorization decision could be computed against an inconsistent/half-swapped `authorizedKeys` reference, which could affect correctness of the JWT-signer-to-workflow authorization check.

### Likelihood Explanation
`syncMetadata` runs continuously on a fixed interval as part of normal operation (`h.runTicker(...MetadataAggregationIntervalMs..., h.syncMetadata)`), and `Authorize` is invoked on every incoming trigger request from any client able to reach the gateway's HTTP trigger endpoint. No special privilege is required to trigger `Authorize`; the race window opens on every metadata sync cycle, making the race easily reproducible under load/fuzzing (e.g. with Go's race detector or repeated concurrent requests timed against the sync interval).

### Recommendation
Acquire `h.mu.RLock()`/`defer h.mu.RUnlock()` at the start of `Authorize` before reading `h.authorizedKeys`, mirroring the pattern already used in `WorkflowShards`, `GetWorkflowID`, and `GetWorkflowReference`. Run the package's tests with `-race` to confirm the fix, and add a concurrency test that calls `Authorize` in a loop while `syncMetadata` runs concurrently.

### Proof of Concept
1. Start a `WorkflowMetadataHandler` with a short `MetadataAggregationIntervalMs`.
2. In one goroutine, repeatedly call `syncMetadata(ctx)` (simulating the background ticker) to continuously replace `h.authorizedKeys`.
3. In parallel goroutines, repeatedly call `h.Authorize(workflowID, token, req)` for a valid workflow/signer.
4. Run under `go test -race`; the race detector will report a data race between the unsynchronized read at `workflow_metadata_handler.go:92` and the locked write at `workflow_metadata_handler.go:178`. Under sufficient load without `-race` this can also surface as a runtime `fatal error: concurrent map read and map write`, crashing the process.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}

// Start begins the periodic pull loop.
func (h *WorkflowMetadataHandler) Start(ctx context.Context) error {
	return h.StartOnce("WorkflowMetadataHandler", func() error {
		h.lggr.Info("Starting HTTP Trigger Metadata Handler")
		h.startTime = time.Now()
		for _, shard := range h.shards {
			if err := h.aggs[shard.donID].Start(ctx); err != nil {
				return fmt.Errorf("failed to start aggregator for shard %s: %w", shard.donID, err)
			}
		}
		h.runTicker(time.Duration(h.config.MetadataPullIntervalMs)*time.Millisecond, func(ctx context.Context) {
			err2 := h.sendMetadataPullRequest()
			if err2 != nil {
				h.lggr.Errorw("Failed to send pull request", "error", err2)
			}
		})
		h.runTicker(time.Duration(h.config.MetadataAggregationIntervalMs)*time.Millisecond, h.syncMetadata)

func (h *WorkflowMetadataHandler) GetWorkflowID(workflowOwner, workflowName, workflowTag string) (string, bool) {

	defer h.mu.RUnlock()

		workflowOwner: workflowOwner,
		workflowName:  workflowName,
		workflowTag:   workflowTag,
