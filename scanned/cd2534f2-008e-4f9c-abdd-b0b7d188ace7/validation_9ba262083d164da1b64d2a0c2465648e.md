## Analog Found: Unbounded `activeRequests` map growth in gateway relay handlers

### Title
Unbounded growth of `activeRequests` map allows unauthenticated/unprivileged users to exhaust gateway memory and degrade the periodic sweep loop - ([File: core/services/gateway/handlers/confidentialrelay/handler.go], [File: core/services/gateway/handlers/vault/handler.go])

### Summary
The OpenQ bug is a classic "unbounded collection populated by unprivileged actors, later iterated in a loop" DoS. The chainlink gateway `confidentialrelay` and `vault` handlers have the same structural pattern: every incoming JSON-RPC user request creates an entry in an in-memory `activeRequests` map keyed by a caller-supplied request ID, with **no cap on the number of concurrent entries** — unlike the sibling `requestCache` type in `core/services/gateway/handlers/common/requestcache.go`, which explicitly enforces `maxCacheSize`.

### Finding Description
In `HandleJSONRPCUserMessage`, both handlers only validate that `req.ID` is non-empty and ≤200 characters, then unconditionally call `newActiveRequest`, which inserts the request into `h.activeRequests` if the ID hasn't been used yet: [1](#0-0) [2](#0-1) 

There is no limit on `len(h.activeRequests)` anywhere in `newActiveRequest` for either handler — compare with `vault/handler.go`: [3](#0-2) 

Entries are only removed either when the DON responds/aggregation completes, or by the periodic `removeExpiredRequests` sweep, which runs on a timer (`defaultCleanUpPeriod` = 1s for confidentialrelay, 5s for vault) and always waits the full `requestTimeout` (default 30s) before evicting an entry: [4](#0-3) [5](#0-4) 

This sweep loops over the *entire* map under a lock every tick, so the cost of `removeExpiredRequests` — and of every other operation that takes `h.mu` (all read/write access to `activeRequests`) — scales with however many entries an attacker has managed to insert.

For the vault handler specifically, `MethodPublicKeyGet` is explicitly exempted from authorization ("Public key requests don't require authorization"): [6](#0-5) 
so, whenever the public key cache is not yet warm (startup, cache miss, or after a fetch failure), an unauthenticated caller can submit an unbounded number of `vault_publicKeyGet` requests with distinct request IDs, each one adding an entry to `activeRequests` that survives for up to `requestTimeout` (30s) before being reaped.

The `confidentialrelay` handler's `HandleJSONRPCUserMessage` shows no visible authorization/authentication check before `newActiveRequest` at all in this handler file — every accepted method (`MethodSecretsGet`, `MethodCapabilityExec`) creates an entry unconditionally. I was not able to confirm within this investigation whether authentication/authorization is enforced upstream (e.g. in the gateway's HTTP layer or connection manager) before `HandleJSONRPCUserMessage` is invoked; this is the key uncertainty and should be verified, since if no upstream auth gate exists, this handler is directly exploitable by any client that can reach the gateway's public HTTP/WS listener.

### Impact Explanation
An attacker who can reach the gateway endpoint (unauthenticated for vault's public-key path, or any client able to invoke the confidentialrelay handler if it lacks upstream auth) can flood `activeRequests` with a large number of live entries within the `requestTimeout` window. This:
- Increases memory usage (each entry holds a full request + a `responses` map + timers/logging labels).
- Increases the O(n) cost of the periodic `removeExpiredRequests` sweep, run under `h.mu.RLock()`, contending with legitimate request handling on the same mutex.
- Can generally degrade gateway availability/latency for all legitimate users of that handler (fanOutToNodes/fanOutToVaultNodes work is also multiplied), which is a DoS analogous to (though not identical to; there is no literal EVM gas limit here) the OpenQ `OUT_OF_GAS`-via-unbounded-array pattern.

This does not directly expose secrets or bypass authorization on write paths (write operations are still gated by `writeMethodsEnabled`/`ProcessRequest`), so the impact is availability degradation rather than fund loss or secret disclosure.

### Likelihood Explanation
Medium. The vault public-key path is reachable without authorization by design, but is normally short-lived because of aggressive public-key caching ("we cache this value quite aggressively so don't need to worry about DoS" per the code comment) — this natural mitigation reduces (but does not eliminate, e.g. during startup or after cache invalidation) the exploitable window. Whether the confidentialrelay handler is reachable without authentication depends on gateway-level wiring that could not be confirmed from the files reviewed.

### Recommendation
- Add an explicit cap on `len(h.activeRequests)` in both `vault/handler.go` and `confidentialrelay/handler.go`'s `newActiveRequest`, rejecting new requests once a configurable maximum is reached (mirroring the `maxCacheSize` pattern already used by `core/services/gateway/handlers/common/requestcache.go`).
- Consider per-caller/per-IP rate limiting for the unauthenticated `MethodPublicKeyGet` path specifically, since it bypasses the normal authorization gate.
- Reduce `defaultCleanUpPeriod`/`requestTimeout` exposure or add early eviction under memory pressure to shrink the exploitable window.

### Proof of Concept
Not independently reproducible from the indexed code alone (no test harness for flooding `activeRequests` was found), but the vulnerable path is:
1. Attacker sends many `vault_publicKeyGet` (or, if reachable unauthenticated, confidentialrelay) JSON-RPC requests, each with a distinct `req.ID` (up to 200 chars, e.g. random UUIDs), faster than the DON can respond and faster than `requestTimeout` (30s default) elapses.
2. Each request passes the only two checks (`req.ID != ""`, `len(req.ID) <= 200`) and calls `newActiveRequest`, unconditionally growing `h.activeRequests` — [3](#0-2) .
3. Repeated over the 30-second window, the map grows to the number of requests sent; `removeExpiredRequests`'s O(n) scan and the shared `h.mu` lock degrade concurrently-served legitimate traffic — [5](#0-4) .

```go
func (h *handler) removeExpiredRequests(ctx context.Context) {
	h.mu.RLock()
	var expiredRequests []*activeRequest
	now := h.clock.Now()
	for _, userRequest := range h.activeRequests {
		if now.Sub(userRequest.createdAt) > h.requestTimeout {
			expiredRequests = append(expiredRequests, userRequest)
		}
	}
	h.mu.RUnlock()
```

```go
func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	labels := h.extractRequestLabels(req)
	l := h.requestLogger(req, labels)
	l.Debugw("handling confidential relay request", "nodes", len(h.donConfig.Members), "f", h.donConfig.F)

	ar, err := h.newActiveRequest(req, labels, callback)
	if err != nil {
		return err
	}

	return h.fanOutToNodes(ctx, l, ar)
```

```go
func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], labels requestLabels, callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID, "executionID", labels.ExecutionID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		labels:    labels,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}
```
