### Title
Vault allowlist authorization (single-use replay-guard digest) is permanently consumed before the guarded secrets operation is confirmed to succeed - ([File: core/capabilities/vault/authorizer.go])

### Summary
The `SolverVault` report describes a pattern where an irreversible state change (burning vault tokens) is committed before the operation it protects (fund withdrawal) is confirmed to succeed, leaving the user with neither the token nor the funds if the later step reverts. The `Vault` capability's gateway request pipeline has the same structural flaw: the one-time-use allowlist authorization digest is marked "consumed" via the replay guard immediately upon authorization, before the actual secrets operation (create/update/delete) that the authorization exists to gate has been validated or executed. If any later step in the pipeline fails for reasons outside the authorizer's control, the client's single-use, on-chain-registered authorization is burned with no corresponding action ever completing.

### Finding Description
`authorizer.AuthorizeRequest` calls `a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt())` immediately after the digest is found in the on-chain allowlist, and before any of the downstream request-specific validation or secret-service execution occurs: [1](#0-0) 

`RequestReplayGuard.CheckAndRecord` records the digest unconditionally on first sight; there is no mechanism to release/un-consume a digest if the caller later fails downstream — the digest simply expires naturally at `expiresAtUnix`: [2](#0-1) 

This "consume-then-validate" ordering is visible in `GatewayVaultRequestProcessor.processCreateSecretsRequest` (and the update path): `p.authorizeAndStamp` — which calls `p.authorizer.AuthorizeRequest` and thus burns the replay-guard digest — runs, and only *afterwards* does `p.validator.ValidateCiphertextSizes` run, which can still fail and abort the whole request: [3](#0-2) 

The comment in the file even documents that owner-scoped limit validation is deliberately deferred until *after* authorization, but doesn't account for the fact that authorization already irreversibly consumes the one-time allowlist grant: [4](#0-3) 

Even if all in-process validation passes, `handler.HandleJSONRPCUserMessage` only dispatches to `h.handleSecretsCreate`/`handleSecretsUpdate`/etc. *after* `h.requestProcessor.ProcessRequest` (which performs the authorization/replay-guard consumption) has already returned success: [5](#0-4) 

Since each allowlisted request digest is a single-use, time-bound on-chain grant created by the workflow owner via the `WorkflowRegistry` (`workflowRegistrySyncer.GetAllowlistedRequests`), an unprivileged client whose legitimate, correctly-authorized request fails for any downstream reason (oversized ciphertext, DON/secrets-service execution failure, stamping failure, etc.) permanently loses that one-time authorization. There is no code path that "un-burns" or restores the digest to the allowlist on downstream failure — the user is left with neither the secret operation completed nor a usable authorization, mirroring the reported bug class exactly (burn happens before success is confirmed).

### Impact Explanation
Each on-chain allowlist entry is scarce (the workflow owner must submit a new on-chain transaction to allowlist a new digest+expiry). A legitimate unprivileged caller whose secrets-create/update/delete request is authorized but subsequently fails validation (e.g. `ValidateCiphertextSizes`) or execution (e.g. secrets-service/DON failure) cannot retry with the same authorization even though the underlying vault operation never took effect. This is a denial-of-service/loss-of-authorization impact on the legitimate owner of the allowlisted request, forcing costly on-chain re-authorization for something that was never their fault.

### Likelihood Explanation
This is reachable by any unprivileged client that has a valid, correctly-signed allowlist entry and sends a request whose payload happens to trip a downstream check (e.g. oversized encrypted secret payload, stamping/marshal error, or secrets-service/DON execution failure) — no malicious behavior is required, just an otherwise normal request that fails after authorization succeeds.

### Recommendation
Defer replay-guard consumption (`CheckAndRecord`) until after the full request has been validated and the underlying secrets operation has been confirmed to succeed (or at minimum, roll back / release the recorded digest if any step after `AuthorizeRequest` fails). This mirrors the report's suggested fix of burning the SolverVault token only after `acceptWithdrawRequest` succeeds rather than at request time.

### Proof of Concept
1. Workflow owner allowlists a `SecretsCreate` request digest on-chain via `WorkflowRegistry`.
2. Client sends the corresponding `SecretsCreate` JSON-RPC request to the gateway, but with an encrypted-secret payload that is valid enough to pass structural validation but exceeds the ciphertext size limit enforced by `ValidateCiphertextSizes`.
3. `GatewayVaultRequestProcessor.processCreateSecretsRequest` calls `authorizeAndStamp` → `authorizer.AuthorizeRequest` → `replayGuard.CheckAndRecord(digest, expiry)` succeeds, consuming the digest.
4. `p.validator.ValidateCiphertextSizes` then fails, and `processCreateSecretsRequest` returns an error; the secret is never created.
5. Client retries the exact same (still on-chain, still unexpired) allowlisted request; `authorizer.AuthorizeRequest` now returns `ErrRequestAlreadySeen` from the replay guard, permanently blocking any retry until the owner submits a brand-new on-chain allowlist entry — despite no secret ever having been created.

```go
func (a *authorizer) AuthorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	authResult, err := a.authorizeRequest(ctx, req)
	if err != nil {
		return nil, err
	}
	if authResult == nil {
		err = errors.New("auth mechanism returned nil auth result")
		a.lggr.Errorw("auth mechanism returned nil auth result", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "")
		return nil, err
	}
	if err := a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt()); err != nil {
		a.lggr.Debugw("replay guard rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "", "error", err)
		return nil, err
	}
	if ownerErr := validateSecretOwnersMatchAuthorized(req, authResult.AuthorizedOwner()); ownerErr != nil {
		a.lggr.Errorw("owner binding rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "hasAuth", req.Auth != "", "error", ownerErr)
		return nil, ownerErr
	}
	a.lggr.Debugw("request authorized", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "")
	return authResult, nil
```

```go
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
```
