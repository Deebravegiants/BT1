### Title
Bridge `OutgoingToken` credential exposed in cleartext to low-privilege (View-role) API users - (File: core/web/presenters/bridges.go)

### Summary
`GET /v2/bridge_types` and `GET /v2/bridge_types/:name` return the bridge's `OutgoingToken` in plaintext in the JSON response body. This endpoint is reachable by users holding only the `View` role, which is intended to be a read-only, low-privilege role.

### Finding Description
`BridgeType.OutgoingToken` is a plaintext secret stored in the DB and used by the node to authenticate to the external adapter (the analog of the "credential" in the NeoLoad advisory, which is stored/exposed in cleartext to users who should not have that level of access). [1](#0-0) [2](#0-1) 

The presenter that serializes bridge data for the `/v2/bridge_types` API always includes this token, with no redaction and only the (unrelated) `IncomingToken` field marked `omitempty`: [3](#0-2) 

The route-role test matrix confirms `GET /v2/bridge_types` and `GET /v2/bridge_types/MOCK` are marked `viewOnlyAllowed: true`, i.e. reachable by the lowest-privileged authenticated role: [4](#0-3) 

This is corroborated by the GraphQL resolver test which shows `outgoingToken` returned as a normal queryable field for the `bridges` query with only generic authentication (not elevated role) required: [5](#0-4) 

By contrast, the codebase demonstrates elsewhere that the project has a clear pattern of secret redaction (e.g. `config.SecretString`/`"xxxxx"` masking for TOML secrets, and the `password`-field blacklist redaction on request/response logging in `core/web/router.go`), showing this bridge outgoing-token field was simply never wired into that redaction path: [6](#0-5) [7](#0-6) 

### Impact Explanation
`OutgoingToken` is the credential the Chainlink node uses to authenticate itself to configured external adapters/bridges. A `View`-role user — who is only supposed to have read-only observability into the node — can retrieve this token via a simple `GET` and then use it to impersonate the node when calling the external adapter, or replay/misuse the token against systems that trust it as proof the request came from the legitimate Chainlink node. This is a direct analog of the NeoLoad plugin issue (credentials readable by users who only have "Extended Read"/view-level access), constituting unauthorized secret disclosure across a role boundary.

### Likelihood Explanation
High likelihood of exploitation: no special conditions are required beyond having any authenticated View-role API user or session (the lowest privilege tier), and the token is returned by design (not a bug requiring a race condition or edge case) on a standard, commonly-used GET endpoint.

### Recommendation
- Remove `OutgoingToken` from `BridgeResource` for read (`GET`) operations, or mark it `omitempty`/redact it entirely except at creation time (mirroring how `IncomingToken` is already only surfaced on creation).
- If clients need to know a token exists, return a boolean/hash indicator instead of the raw secret.
- Apply the same fix to the GraphQL `bridges`/`bridge` resolvers, which expose `outgoingToken` identically.
- Audit other presenters (e.g., External Initiator) for the same over-exposure pattern, since `ExternalInitiatorResource` similarly returns `OutgoingToken`.

### Proof of Concept
1. Create an API user with `View` role only.
2. Authenticate as that user and call `GET /v2/bridge_types/<bridge-name>`.
3. Observe the JSON response contains `"outgoingToken": "<plaintext secret>"`, per `NewBridgeResource` in [8](#0-7)  and the permitted route mapping in [4](#0-3) .
4. Use the retrieved token to authenticate as the node against the configured external adapter.
