### Title
Missing `return` after failed `email` claim assertion allows OIDC session creation with empty/wrong email and DB write error swallowed - ([File: core/sessions/oidcauth/oidc.go])

### Summary
In `handleTokenExchange`, the type assertion of the `email` claim checks its `ok` return value and logs/writes an HTTP error response, but does not `return` — execution falls through and continues to create and persist an authenticated session using the empty `email` string. A second identical pattern occurs where the error from `oi.ds.ExecContext` (session insert) is also swallowed without returning, after which the code still sets the session cookie and reports success.

### Finding Description
`handleTokenExchange` extracts the `email` claim via a type assertion: [1](#0-0) 

Unlike every other validation branch in this function (id_token extraction, token verification, claims parsing, claim extraction, role mapping), which all `return` on failure, this branch only logs and writes an HTTP body — it never calls `return`. Execution continues to compute `role` from `idClaims` (which does not depend on `email`) and then inserts a new row into `oidc_sessions` using the empty `email` string: [2](#0-1) 

The session ID is then set on the user's cookie and `ExchangeTokenResponse{Success: true}` is returned to the client: [3](#0-2) 

This mirrors the reported bug class ("return value is not used / not acted upon") — here the boolean `ok` from the claim assertion, and separately the `err` from `ExecContext`, are checked but their failure paths do not halt request processing, so the code proceeds to authenticate the OIDC-attested user with an empty or already-written-but-corrupted `user_email`, while the client still receives an HTTP 200 `Success: true` (the earlier `c.String(http.StatusInternalServerError, ...)` write does not stop request handling in gin, and no `c.Abort()`/`return` is issued).

Once a session is created with an empty `email`, `AuthorizedUserWithSession` looks up `user_email` for the stored session and returns a `clsessions.User{Email: "", Role: ...}` for any subsequent request bearing that cookie, since the lookup is by session ID, not email: [4](#0-3) 

### Impact Explanation
An externally authenticated (but claim-malformed) OIDC user ends up with a valid, functioning session cookie tied to a role derived from group claims, but with a blank/incorrect `user_email` persisted in `oidc_sessions`. This breaks the assumption that every session row has a valid attested email, corrupting audit logs (`audit.AuthLoginSuccessNo2FA` is emitted with the empty email) and any authorization/audit code that keys off `user_email`. It also silently masks a legitimate error condition (missing `email` claim) from the client (who gets `Success: true`) and from operational error tracking, since the internal error write does not actually stop or fail the request. This is a logic/authentication-integrity flaw rather than a direct fund-movement bug, but it undermines the correctness of the audit trail and session-to-identity binding for an unprivileged, externally-triggered login flow.

### Likelihood Explanation
This path triggers whenever an IdP response's ID token claims lack an `email` field (or it's not a string) — a condition reachable by any actor able to complete the OAuth2/OIDC code exchange with the configured provider (which depends on IdP behavior/config, e.g. misconfigured claim mapping or a provider that omits `email` for certain accounts). It does not require any special node/DON privilege — it's part of the public-facing web session controller flow.

### Recommendation
Add `return` immediately after the `c.String(http.StatusInternalServerError, "Failed to get email from claims")` call at line 229, matching the pattern used by all other validation branches in this function. Likewise add `return` after the `ExecContext` error branch at lines 257-260 so a failed session insert does not proceed to set the session cookie and report `Success: true`.

### Proof of Concept
1. Configure OIDC login against an identity provider (or a malicious/compromised one) that returns valid, verifiable claims (satisfying `oi.provider.Verifier(...).Verify` and `ExtractIDClaimValues`/`IDClaimsToUserRole`) but omits the `email` claim or returns a non-string value for it.
2. Complete `/oidc-login` flow and call the token exchange endpoint (`handleTokenExchange`) with a valid `code`/`state`.
3. Observe: `claims["email"].(string)` assertion fails, `ok=false`; the internal error is logged and `c.String(...)` writes a 500 body, but execution continues.
4. `role` is computed successfully from `idClaims`, a new row is inserted into `oidc_sessions` with `user_email = ''`, the session cookie is set, and the handler responds `200 {"success": true}`.
5. The client now holds a valid session cookie whose backing DB row has an empty `user_email`, granting API access under the mapped `role` despite the claimed authentication failure.

// AuthorizedUserWithSession will return the API user associated with the Session ID if it
// exists and hasn't expired
func (oi *oidcAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (clsessions.User, error) {
	if len(sessionID) == 0 {
		return clsessions.User{}, errors.New("session ID cannot be empty")
	}
	var foundUser clsessions.User
	err := sqlutil.TransactDataSource(ctx, oi.ds, nil, func(tx sqlutil.DataSource) error {
		// Query the oidc_sessions table for given session ID, user role and email are saved after the id claims is provided and validated
		var foundSession struct {
			UserEmail string
			UserRole  clsessions.UserRole
			Valid     bool
		}
		if err := tx.GetContext(ctx, &foundSession,
			"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM oidc_sessions WHERE id = $1",
			sessionID, oi.config.SessionTimeout().Duration(),
		); err != nil {
			if errors.Is(err, sql.ErrNoRows) {
				return clsessions.ErrUserSessionExpired
			}
			return err
		}
		if !foundSession.Valid {
			// Sessions expired, purge
			return clsessions.ErrUserSessionExpired
		}
		foundUser = clsessions.User{
			Email: foundSession.UserEmail,
			Role:  foundSession.UserRole,
		}
		return nil
	})
	if err != nil {
		if errors.Is(err, clsessions.ErrUserSessionExpired) {
			if _, execErr := oi.ds.ExecContext(ctx, "DELETE FROM oidc_sessions WHERE id = $1", sessionID); execErr != nil {
				oi.lggr.Errorf("error purging stale OIDC session: %v", execErr)
			}
		}
		return clsessions.User{}, err
	}
	return foundUser, nil
}
