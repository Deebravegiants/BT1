## Analysis Result

Chainlink's local-auth login flow leaks whether an email address is a registered user by returning a different, distinguishable error message compared to a wrong-password attempt — directly analogous to CVE-2019-16394 (SPIP password-reminder page leaking account existence via differing error messages).

### Title
Login endpoint leaks user-account existence via distinct error messages for unknown-email vs. wrong-password - (File: core/web/sessions_controller.go, core/sessions/localauth/orm.go)

### Summary
The `/sessions` login endpoint returns the raw, unmodified error from the authentication provider directly to the unauthenticated caller. For local auth, a nonexistent email produces a raw SQL "no rows" error while an existing email with a wrong password produces the distinct string `"Invalid password"`. This lets any unauthenticated caller enumerate valid Chainlink node operator/API accounts.

### Finding Description
`SessionsController.Create` forwards the authentication error verbatim to the HTTP response body without normalization: [1](#0-0) 

The local auth ORM's `CreateSession` first looks up the user by email; if the lookup fails (email not registered), the raw error is returned immediately — before any password check occurs: [2](#0-1) 

`findUser` performs no error wrapping, so a nonexistent email surfaces the underlying SQL driver error (e.g. `sql: no rows in result set`): [3](#0-2) 

In contrast, when the email exists but the password is wrong, a distinctly different, deliberately worded error is returned: [4](#0-3) 

Because `jsonAPIError` passes this error text straight to the client, the two failure paths ("email not found" vs. `"Invalid password"`) are trivially distinguishable by an unauthenticated caller, exactly matching the CVE-2019-16394 bug class (different error messages reveal whether an account/email exists). The same pattern (`"invalid email"` vs `"invalid password"`) is also present in the LDAP and OIDC local-fallback authenticators: [5](#0-4) [6](#0-5) 

### Impact Explanation
This allows an unprivileged, unauthenticated network client to enumerate valid API user emails on a Chainlink node's admin/operator API. Combined with the rate-limiting on `/sessions` (which only throttles by request volume, not by information leaked per request), an attacker can build a list of valid operator accounts to target with credential stuffing, password spraying, or social engineering — a legitimate low-severity confidentiality impact consistent with the "C:L" rating of the original CVE.

### Likelihood Explanation
Likelihood is high for exploitation given the endpoint is unauthenticated and internet-facing (`unauth.POST("/sessions", sc.Create)`): [7](#0-6) 

No special privileges, tooling, or timing side-channel is required — the distinguishing information is present directly in the JSON error body of the HTTP response.

### Recommendation
Normalize the error returned from `AuthenticationProvider().CreateSession` in `SessionsController.Create` to a single generic message (e.g., "invalid email or password") regardless of whether the email was found or the password was wrong, for all three auth providers (local, LDAP, OIDC). Keep the specific `AuthLoginFailedEmail` / `AuthLoginFailedPassword` distinction only in the internal audit log, not in the HTTP response body.

### Proof of Concept
1. `POST /sessions` with `{"email":"admin@example.com","password":"wrong"}` where `admin@example.com` is a real account → response body contains error text derived from `"Invalid password"`.
2. `POST /sessions` with `{"email":"doesnotexist@example.com","password":"wrong"}` → response body contains a different error text derived from the raw SQL "no rows" error.
3. Comparing the two response bodies lets the caller determine which candidate emails correspond to real accounts on the node, without needing valid credentials.
