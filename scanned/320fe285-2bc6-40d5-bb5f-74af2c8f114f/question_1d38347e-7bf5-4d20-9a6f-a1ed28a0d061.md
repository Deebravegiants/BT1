VersionedNonceBuilder.decodeNonce(encoded) throws 'Nonce too short' whenever `bytes.length !== 32`, and throws 'Invalid magic prefix' when the first 4 bytes don't equal VERSIONED_MAGIC_PREFIX — but IntentPayloadBuilder.setNonce(nonce) never calls decodeNonce or otherwise validates the string before storing it as `customNonce`, and buildWithSalt only calls encodeNonce when `customNonce` is undefined. Can a caller supply, via setNonce, a base64 string that decodes to something OTHER than 32 bytes (e.g., a legacy 32-BYTE RAW nonce format some other NEAR NEP-413 flow uses, or a 44-byte garbage string), producing a signed MultiPayload whose `payload.nonce` field is accepted by the outer signing flow (since setNonce/buildWithSalt never call decodeNonce) yet is uninterpretable or misinterpreted as 'legacy' by any downstream consumer expecting the VersionedNonceBuilder format? Equality broken: the (nonce, verifying_contract) identity is meant to be unambiguous, but an unvalidated custom nonce can be format-ambiguous, letting one binary string be interpreted as two different logical nonces (versioned vs legacy) by different consumers of the same signed payload. Impact: High, ambiguous nonce interpretation can let a contract-side legacy nonce-replay-protection path treat the payload differently from what the SDK's own invalidateNonces/decodeNonce logic assumes, risking a stuck withdrawal or a nonce the caller thinks is invalidated remaining valid under the alternate interpretation.
