IntentPayloadBuilder.buildAndSign(signer) does `const payload = await this.build(); const signed = await signer.signIntent(payload); return { signed, payload };` with no verification AFTER signing that `signed`'s embedded fields (verifying_contract, nonce, deadline, intents) still equal the `payload` object that was passed in — it trusts the IIntentSigner implementation completely. If a caller supplies a custom IIntentSigner (a legitimate, permissionless integration point, e.g., a hardware-wallet or remote-signing bridge that an ordinary user configures with their own keys) whose signIntent(payload) implementation has a bug or a bridging layer that mutates fields (e.g., re-serializes `payload.deadline` with reduced precision, or substitutes a cached verifying_contract from a prior call), does buildAndSign() detect the divergence between the returned `signed.payload` and the original `payload`, or does it blindly return both as if they matched? Equality broken: SIGNED == BUILT — every field of the returned `signed` MultiPayload must equal what `payload` specified, and buildAndSign() performs zero such assertion. Impact: Critical, buildAndSign()'s two-tuple return `{ signed, payload }` can silently diverge, and any integrator code that displays/confirms `payload` to the user while actually publishing `signed` will publish a materially different intent than what was shown/approved. Proof idea: vitest test with a mock IIntentSigner.signIntent that returns a MultiPayload whose payload.deadline differs from the input payload.deadline, calling buildAndSign(), and asserting buildAndSign() does not throw or flag signed.payload.deadline !== payload.deadline before returning both.
