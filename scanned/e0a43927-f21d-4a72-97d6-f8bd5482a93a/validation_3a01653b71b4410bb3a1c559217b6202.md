Based on the investigation, there is a plausible in-scope analog to the Airflow trigger-kwargs disclosure: unmasked secret exposure through the pipeline/job-run read endpoints.

### Title
Pipeline run "inputs" are returned to any authenticated node user without secret redaction - ([File: core/web/presenters/pipeline_run.go])

### Summary
The Airflow CVE describes a REST endpoint that returns deferred-task trigger kwargs (which can contain secrets) to any authenticated user with DAG-scoped read access, without masking. The Chainlink node has a structurally identical pattern: `PipelineRunsController.Show`/`Index` return raw pipeline run `Inputs` with no redaction of sensitive values.

### Finding Description
`NewPipelineRunResource` builds the API response by copying `pr.Inputs` verbatim into the JSON payload with no filtering or masking: [1](#0-0) 

These `Inputs` are the raw pipeline task run inputs computed at execution time (`Vars` built from job/task parameters), which can include values resolved from job specs, bridge responses, or task parameters — some of which are secret-like (API keys/tokens configured for bridges or HTTP tasks). Unlike the request/response logging path used elsewhere in the web layer, which explicitly redacts blacklisted keys via `isBlacklisted`/`readSanitizedJSON`/`redact`, no equivalent redaction is applied to the `PipelineRunResource.Inputs` field before it is serialized to the API response: [2](#0-1) 

The endpoints that expose this are registered without any elevated-role gate — just plain `authv2.GET`, unlike job mutation endpoints which require `auth.RequiresEditRole`/`auth.RequiresAdminRole`: [3](#0-2) 

This means any authenticated session user (any role able to reach `authv2`) can call `GET /v2/jobs/:ID/runs` or `GET /v2/jobs/:ID/runs/:runID` and receive the unredacted `inputs` field, mirroring the Airflow bug class: an authenticated but otherwise low-privilege caller reading detail/list endpoints and getting back sensitive values that were never masked.

### Impact Explanation
If a pipeline task's resolved input values include credentials or tokens (e.g., values pulled from bridge configs, HTTP headers, or job spec parameters treated as vars), those values are disclosed in plaintext to any user who can read job runs for that job, not just admins. This is a secret-disclosure issue analogous to the Airflow advisory: authenticated cross-privilege read exposing embedded secrets via a task/run detail API.

### Likelihood Explanation
This requires only session authentication and the ability to call an existing, unauthenticated-by-role endpoint (`/v2/jobs/:ID/runs...`); no additional privilege escalation is needed. Likelihood depends on whether operators actually place secret values into task inputs/vars reachable during pipeline execution — this is plausible for HTTP/bridge tasks but I could not verify from the index whether the toolchain's normal secret injection paths (e.g. `$JOB_SPEC_ID`) route secrets through fields that end up in `run.Inputs` versus being injected only at the bridge/HTTP call layer, so it is uncertain how frequently exploitable secret material actually lands in `Inputs` in practice.

### Recommendation
Apply the same blacklist/redaction logic already used for HTTP request logging (`isBlacklisted`, `readSanitizedJSON` in `core/web/router.go`) to `PipelineRunResource.Inputs`/`Outputs` (and the GraphQL `JobRunResolver.Inputs`/`Outputs` equivalents in `core/web/resolver/job_run.go`) before serialization, and/or restrict `GET /v2/jobs/:ID/runs*` to `auth.RequiresEditRole` or add a dedicated view-role check, consistent with mutation routes.

### Proof of Concept
1. As a low-privilege authenticated node user, create/observe a job whose pipeline task inputs resolve to include a secret-like value (e.g., an API key passed as a task parameter).
2. Call `GET /v2/jobs/{ID}/runs/{runID}` or `GET /v2/jobs/{ID}/runs`.
3. Observe the `inputs` field in the JSON response contains the raw, unredacted value, per `NewPipelineRunResource` ( [4](#0-3) ), confirming disclosure through an endpoint gated only by session auth ( [5](#0-4) ).

**Caveat:** I could not fully confirm within the indexed code whether real operator secrets (as opposed to only ordinary business data) commonly flow into `pipeline.Run.Inputs`, since that depends on how individual task adapters (bridge/HTTP) populate `Vars`. This limits certainty on real-world severity; a Devin session with full repo access could trace `Vars`/`TaskRun.Input` population across all task types (`core/services/pipeline/task.*.go`) to confirm concretely which secret sources are reachable here.

func readSanitizedJSON(buf *bytes.Buffer) (string, error) {
	var dst map[string]any
	err := json.Unmarshal(buf.Bytes(), &dst)
	if err != nil {
		return "", err
	}

	cleaned := map[string]any{}
	for k, v := range dst {
		if isBlacklisted(k) {
			cleaned[k] = "*REDACTED*"
			continue
		}
		cleaned[k] = v
	}

	b, err := json.Marshal(cleaned)
	if err != nil {
		return "", err
	}
	return string(b), err
}
