Target: Webhooks::Request#shop equality with Auth::Session#shop elsewhere in the gem (SHOP BINDING core binding). Attacker action: attacker triggers a webhook-driven code path in the host app that looks up an existing ShopifyAPI::Auth::Session for WebhookMetadata#shop (a header-derived, unsigned string) and then issues an authenticated Admin API call using that session's access token on behalf of 'victim_shop.myshopify.com', purely because the attacker put that string in a header of their own signed request. Preconditions: host app pattern (per docs) is 'load session by webhook shop, then call Admin API'. Call sequence: Registry.process -> WebhookMetadata.new(shop: attacker-chosen victim domain) -> host app's Session lookup keyed by that string -> outbound Admin API call authenticated as the victim. Binding: shop string driving which stored access token is used == shop authenticated by any signature this gem verified — never enforced, since only @raw_body is signed. Impact: Critical, cross-tenant use of a merchant's real access token triggered by an attacker who never touched that token. Proof idea: minitest with a fake session store keyed by shop domain, asserting that Registry.process's WebhookMetadata#shop can be set to any string the attacker chooses independent of HMAC validity.
