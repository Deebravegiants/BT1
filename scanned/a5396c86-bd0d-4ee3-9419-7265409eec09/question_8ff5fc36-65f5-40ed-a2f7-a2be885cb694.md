Target: IntentSignerViem.signIntent (packages/intents-sdk/src/intents/intent-signer-impl/intent-signer-viem.ts). Attacker input: an IntentPayload with intent.signer_id explicitly set to victim's EVM address (lowercased), while this.config.signer is the attacker's own viem Account with a different address. Preconditions: attacker constructs the IntentPayload directly (public API allows arbitrary signer_id field) and calls signIntent with their own IntentSignerViemConfig. Call sequence: signIntent builds payload JSON using `signer_id: intent.signer_id ?? this.config.accountId ?? utils.authHandleToIntentsUserId(...)` — since intent.signer_id is non-null it is used verbatim; signRaw then has config.signer (attacker's key) call signMessage on that payload and returns MultiPayloadErc191 with payload.signer_id === victim address but signature produced by attacker's key. Equality broken: signer_id in the signed payload == the intents user id derived from the public key that produced signature — here signer_id names victim's account but the ERC191 signature recovers to the attacker's address, a mismatch the SDK does not detect before returning the MultiPayload. Impact: Critical, intent manipulation moving funds the user did not authorise, if any downstream consumer (contract or relay) does not itself re-derive and check signer against the recovered ECDSA address — this is a construction-time equality violation entirely reproducible inside the SDK without any external service. Impact scope: the account whose address is used as intent.signer_id could have a plausible-looking but improperly-authorised MultiPayload minted against it. Proof idea: vitest test calling IntentSignerViem.signIntent with intent.signer_id set to a different address than config.signer.address, then asserting the returned payload's parsed signer_id !== the address recoverable from the returned ERC191 signature via viem's recoverMessageAddress, proving SIGNED_EQUALS_BUILT (signer identity) breaks.
