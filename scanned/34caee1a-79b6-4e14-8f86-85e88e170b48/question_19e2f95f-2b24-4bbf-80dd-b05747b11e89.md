Target: `ShopifyAPI::Auth::Oauth.validate_auth_callback` HMAC-then-shop-trust ordering. Attacker action: attacker who has NOT installed any app (fully unprivileged, no dev shop) attempts to forge a callback wholesale by guessing/brute-forcing an HMAC for an arbitrary `shop` value without knowing `Context.api_secret_key`. Preconditions: none - standard threat model. Call sequence: `Utils::HmacValidator.validate(auth_query)` computes `OpenSSL::HMAC.hexdigest` with `Context.api_secret_key` and compares via `OpenSSL.secure_compare`; attacker cannot produce a matching hmac without the secret. Binding: SIGNATURE COVERAGE holds correctly for the HMAC-secret aspect - this question is a negative control validating that the actual exploitable gap is specifically the *unsanitized-but-authenticated* shop string (from a self-owned shop, i.e., attacker CAN get one authentic signature for a shop string they choose to author, since Shopify signs whatever `shop`/`code`/`host`/`timestamp`/`state` the real OAuth server sends back for the attacker's own store), not a raw HMAC forgery. Scoped impact: Critical (isolates real bug from a false lead). Proof idea: minitest asserting `HmacValidator.validate` correctly rejects a callback with a tampered `shop` field when the hmac was computed over the original untampered `shop` (using `OpenSSL.secure_compare`), confirming tampering-after-signing is blocked, while a self-authored-before-signing malicious shop string is not - i.e., the vulnerability requires an attacker who controls their own shop identity end-to-end, exactly matching the documented unprivileged-attacker capability of registering their own dev shop.
