Target: `ShopifyAPI::Auth::Oauth.begin_auth` `redirect_uri` construction vs `Context.host`. Attacker action: attacker cannot control `Context.host` (developer-configured), but can control `shop`; the question tests whether `shop` leaks into `redirect_uri` anywhere it shouldn't via query-string smuggling, e.g. `shop=real-shop.myshopify.com&extra=` type parameter pollution at the app layer. Preconditions: app passes raw `params[:shop]` straight through as documented. Call sequence: `query[:redirect_uri]` uses only `Context.host` + `redirect_path`, unaffected by `shop` - but `auth_route` itself embeds `shop` unsanitized via `auth_base_uri(shop)`. Binding: `host_of_authorize_redirect == ShopValidator.TRUSTED_SHOPIFY_DOMAINS-accepted_host`. Scoped impact: Critical - browser is redirected to `https://<attacker_shop>/admin/oauth/authorize?...&client_id=<real client_id>`, exposing the app's `client_id` (and enabling a phishing/consent-capture chain that can yield the authorization `code` to the attacker's own server) since the authorize destination host was never checked against trusted domains. Proof idea: minitest asserting `URI(begin_auth(shop: 'attacker.example', redirect_path: '/cb')[:auth_route]).host == 'attacker.example'`, i.e., not confined to `*.myshopify.com`.
