### Title
Cross-Chain Bridge DoS via Sovereign Account Drain — Shared Fee Pool Pattern in `SovereignPaidRemoteExporter` / `pallet-xcm-bridge-hub-router` (File: `polkadot/xcm/xcm-builder/src/universal_exports.rs`)

### Summary
The reported LayerZero bug is a classic "shared gas-pool DoS": a contract pre-funds ETH to pay for every outbound cross-chain message, and any unprivileged user can drain that shared balance with cheap/dust messages, halting all cross-chain operations. The Polkadot SDK has an architecturally analogous pattern in its bridging stack: XCM `ExportMessage` fees, when routed through `SovereignPaidRemoteExporter`, are paid out of a parachain's **sovereign account balance held on the Bridge Hub** — a shared pool that is not automatically replenished per-message by the actual message sender.

### Finding Description
`SovereignPaidRemoteExporter::validate` builds an XCM of the form `WithdrawAsset(fees) -> BuyExecution -> SetAppendix(refund) -> ExportMessage`, and this program is forwarded to and executed **on the Bridge Hub**, in the origin context of the sending parachain (e.g. Asset Hub): [1](#0-0) [2](#0-1) 

Because `WithdrawAsset` executes at the Bridge Hub under the sending parachain's sovereign origin, the fee is drawn from that parachain's real balance held at the Bridge Hub — not from the individual end-user account that triggered the transfer at the source chain. This requires the parachain's operators to pre-fund (and periodically top up) that sovereign account, exactly like the LayerZero router being pre-funded with ETH: [3](#0-2) [4](#0-3) 

`pallet-xcm-bridge-hub-router` explicitly supports toggling between the two exporter modes via `T::UnpaidExport`, meaning any runtime that keeps the paid mode (`SovereignPaidRemoteExporter`) is exposed to this shared-pool design: [5](#0-4) 

Any unprivileged user of the sending parachain who triggers a cross-chain send that gets routed through this exporter (e.g. a reserve transfer, teleport, or any XCM ending in `ExportMessage`) causes the *shared* sovereign-account balance to be debited — dust-value or minimal-cost messages are sufficient, since the fee is a fixed per-message price from `ExporterFor`, not scaled to be economically prohibitive for spam relative to account depletion. Once the sovereign account is drained, ALL further outbound bridge messages from that parachain fail (`Unroutable`/insufficient-balance failure at the Bridge Hub), a full DoS of the bridge for every user of that parachain — the same "loss of core feature" impact described in M-7.

### Impact Explanation
If the sovereign account is exhausted, all bridged operations from the affected parachain (asset transfers, token registrations, remote calls via the bridge) fail, denying service to every legitimate user of that chain's bridge. Depending on the specific bridge (e.g. Snowbridge to Ethereum, or the Polkadot↔Kusama bridge), this can delay or block cross-chain asset transfers, similarly to how the LayerZero report describes stalled liquidation/repayment flows.

### Likelihood Explanation
The Polkadot SDK team has already identified and mitigated this exact risk for the currently-deployed Asset Hub ↔ Bridge Hub paths: `prdoc/stable2606/pr_11694.prdoc` explicitly switched Asset Hub runtimes to `UnpaidRemoteExporter` specifically to avoid "the need to manage/top-up AH sov account on BH," and `prdoc/stable2506/pr_8599.prdoc` (Snowbridge V2) states the same goal "to avoid maintaining the Asset Hub's sovereign account on the Bridge Hub": [6](#0-5) [7](#0-6) 

The Snowbridge design docs also independently note the spam risk and recommend charging a minimum relayer-reward/router fee specifically "to prevent spamming BH with bridge messages": [8](#0-7) 

However, I could not fully confirm from the index whether the current in-repo `asset-hub-westend`/`asset-hub-rococo` `xcm_config.rs` still reference `SovereignPaidRemoteExporter` anywhere (e.g. for other bridge lanes) or exclusively `UnpaidRemoteExporter` — the grep only returned match counts, not content, so this is an open item that would need direct file inspection to close out. The underlying `SovereignPaidRemoteExporter` type and the paid mode of `pallet-xcm-bridge-hub-router` remain present and usable in the codebase, so any *other* runtime (present or future) that configures paid export without an accompanying minimum-fee/spam-guard would inherit this exact DoS class. Given that the SDK team already treated this as a real operational/security concern worth architectural mitigation, likelihood for any runtime still using the paid configuration is credible, but for the currently shipped Asset Hub configs specifically it appears to already be mitigated by design (default = unpaid).

### Recommendation
- Confirm no production runtime in this repo still routes bridge exports through `SovereignPaidRemoteExporter`/paid `pallet-xcm-bridge-hub-router` without a compensating minimum fee that scales with the cost of draining the sovereign account.
- Where paid export must be retained (e.g. lanes where `UnpaidRemoteExporter` is not applicable), enforce a minimum per-message fee/reward that is not economically negligible relative to the sovereign account's replenishment rate, and/or require the parachain to reload its own sovereign account 1:1 as part of the same XCM program rather than relying on a persistent shared balance.
- Add monitoring/alerting and possibly a low-balance circuit breaker on bridge sovereign accounts to fail safe rather than silently DoS the lane.

### Proof of Concept
Not applicable in a testable form from static analysis alone — the exploit would require deploying/emulating a parachain configured with `SovereignPaidRemoteExporter` (paid mode) and repeatedly sending minimal-cost XCM messages ending in `ExportMessage` until the sovereign account balance at the Bridge Hub is exhausted, then demonstrating that subsequent legitimate bridge transfers fail with `Unroutable`/`FundsUnavailable`. This mirrors the integration test scaffolding already present (e.g. `bridges/snowbridge/runtime/test-common/src/lib.rs::initial_fund`, `bridges_rococo_westend.sh` sovereign-account funding), which could be adapted into a draining PoC.
