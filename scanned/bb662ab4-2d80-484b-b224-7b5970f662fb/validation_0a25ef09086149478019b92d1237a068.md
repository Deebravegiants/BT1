## Analog Found

### Title
`pallet-revive`'s ERC20 `fungibles::Mutate` adapter returns the account's post-operation balance instead of the actual minted/burned amount, breaking the return-value contract relied on by `xcm_builder::FungiblesAdapter` - (File: `substrate/frame/revive/src/impl_fungibles.rs`)

### Summary
The Tapioca report's root cause is that a "wrap" operation which can be affected by a fee (`mTOFT::wrap`) returns the *actual* amount obtained, but the caller ignored the return value and kept using the pre-fee `_amount`, causing downstream accounting to overestimate the received balance. The same shape of bug — a mint/burn primitive returning a value that does not represent "the amount actually moved", consumed by code that assumes it does — exists in `pallet-revive`'s `fungibles::Mutate` implementation for ERC20 tokens, which is explicitly built to be consumed by `xcm_builder::FungiblesAdapter`.

### Finding Description
`pallet-revive` exposes ERC20 contracts as `fungibles::Inspect`/`fungibles::Mutate` assets (asset ID = contract address) so they can be used as XCM-transactable assets. The overridden `mint_into` and `burn_from` do not return the delta actually transferred; they return the account's *current total balance* after the call: [1](#0-0) [2](#0-1) 

Both functions perform an `IERC20::transferCall` for `amount`, and on success return `Self::balance(asset_id, who)` — i.e. the recipient's/burner's whole post-call balance — rather than the amount actually moved. This directly violates the documented contract of the underlying `Unbalanced::increase_balance`/`decrease_balance` primitives that `Mutate::mint_into`/`burn_from` are supposed to honor ("the returned amount [is] the amount by which it was reduced/increased"): [3](#0-2) 

The pallet-revive source itself states the purpose of these overrides is XCM asset transacting: [4](#0-3) 

`xcm_builder::FungiblesAdapter` is the standard `AssetTransactor` used by parachain/asset-hub XCM configs to call `mint_into`/`burn_from` when depositing/withdrawing fungible assets during XCM execution (teleports, reserve transfers, `PayFees`, etc.). If any code path in the adapter (or any other consumer of this `fungibles::Mutate` impl, e.g. `pallet-asset-conversion`, `SwapCredit`, or transaction-payment adapters that this repo shows relying on the *returned amount* rather than the *requested amount* — see `substrate/frame/asset-conversion/src/lib.rs` and `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs`, both of which trust returned balances/credits as authoritative) is composed on top of pallet-revive ERC20 assets, it will receive a grossly incorrect "amount transacted" value whenever:
- `who` already held a non-zero balance before the mint/burn (the return value is `old_balance + minted`, not `minted`), or
- the target ERC20 is a fee-on-transfer/deflationary/rebasing token (any user-deployed contract, since ERC20 assets on `pallet-revive` are permissionlessly created), causing the amount actually transferred to differ from the requested `amount`.

This is structurally identical to the Tapioca bug: a token-movement primitive that can silently return/actually-move an amount different from the requested one, combined with a caller that is not designed to reconcile the discrepancy.

I could not fully re-verify within this pass the exact line-by-line body of `xcm_builder/src/fungibles_adapter.rs`'s `deposit_asset`/`withdraw_asset` to confirm whether it discards the return value entirely (in which case the impact is limited to over/under-crediting relative to the caller's own separately-computed `AssetsInHolding`, not to the value returned by `mint_into`/`burn_from` itself) or whether the amount is derived from it. This should be verified before filing, since it determines whether the corruption reaches the XCM holding register (accounting/inflation issue) or is merely internal to `pallet-revive` bookkeeping.

### Impact Explanation
If `xcm_builder::FungiblesAdapter` (or any other adapter/pallet that treats the `Ok(x)` of `mint_into`/`burn_from` as "amount minted/burned") is configured with `pallet-revive`'s ERC20 fungibles implementation as its asset registry, XCM asset accounting (the in-flight `AssetsInHolding` register) can diverge from the real on-chain ERC20 balances. Depending on how the value is consumed, this can manifest as: (a) asset creation/inflation in the XCM holding register beyond what was actually transferred, or (b) downstream `ensure!`/balance checks failing unexpectedly, causing legitimate XCM programs (e.g., reserve transfers or `PayFees` involving revive ERC20 assets) to always revert — a Denial of Service for any XCM operation touching such assets, mirroring the "leverage executor always fails" impact in the original report.

### Likelihood Explanation
Reachability depends entirely on whether a `pallet-revive`-based ERC20 asset is wired into an XCM `AssetTransactor` (e.g., `FungiblesAdapter`) in a live runtime, and any account interacting with it having a pre-existing balance (the common case) or the ERC20 contract having non-standard transfer semantics (permissionless, attacker-deployable). No privileged role is required to trigger it — this is an unprivileged-user-reachable defect if the wiring exists, but I could not confirm from the index whether any current production runtime actually configures `FungiblesAdapter` over `pallet-revive`'s ERC20 fungibles impl in this snapshot of the codebase.

### Recommendation
- Change `burn_from`/`mint_into` in `substrate/frame/revive/src/impl_fungibles.rs` to compute and return the actual delta transferred (e.g., diff of `balance()` before/after the ERC20 call, or decode the ERC20 event/return data), rather than the account's absolute post-call balance.
- Audit every consumer of `fungibles::Mutate::mint_into`/`burn_from` (in particular `xcm_builder::FungiblesAdapter`) to confirm whether the returned value is used to construct XCM holding assets, and if so, ensure it is reconciled against the requested amount (fail/trap on mismatch) rather than silently trusted.

### Proof of Concept
Conceptual PoC (not executed, since confirming it requires wiring `pallet-revive` ERC20 fungibles into an XCM `AssetTransactor`, which I could not fully verify is done in this repo snapshot):
1. Deploy an ERC20 contract via `pallet-revive` and register it as an XCM-transactable asset through `FungiblesAdapter`.
2. Have account `A`, which already holds balance `B > 0` of the ERC20, receive an XCM `ReceiveTeleportedAsset`/`DepositAsset` for amount `X`.
3. `FungiblesAdapter::deposit_asset` calls `mint_into(asset_id, A, X)`, which internally performs the ERC20 transfer of `X` but returns `B + X` (A's total balance) instead of `X`.
4. If any code depends on the returned value as "amount deposited" (rather than the caller's already-known `X`), it will treat `B + X` as the deposited amount — corrupting holdings/state. [2](#0-1)

// We implement `fungibles::Mutate` to override `burn_from` and `mint_to`.
//
// These functions are used in [`xcm_builder::FungiblesAdapter`].
impl<T: Config> fungibles::Mutate<<T as frame_system::Config>::AccountId> for Pallet<T> {
	fn burn_from(
		asset_id: Self::AssetId,
		who: &T::AccountId,
		amount: Self::Balance,
		_: Preservation,
		_: Precision,
		_: Fortitude,
	) -> Result<Self::Balance, DispatchError> {
		let checking_account_eth = T::AddressMapper::to_address(&Self::checking_account());
		let checking_address = Address::from(Into::<[u8; 20]>::into(checking_account_eth));
		let data =
			IERC20::transferCall { to: checking_address, value: EU256::from(amount) }.abi_encode();
		let ContractResult { result, weight_consumed, .. } = Self::bare_call(
			OriginFor::<T>::signed(who.clone()),
			asset_id,
			U256::zero(),
			TransactionLimits::WeightAndDeposit {
				weight_limit: WEIGHT_LIMIT,
				deposit_limit:
					<<T as pallet::Config>::Currency as fungible::Inspect<_>>::total_issuance(),
			},
			data,
			&ExecConfig::new_substrate_tx(),
		);
		log::trace!(target: "whatiwant", "{weight_consumed}");
		if let Ok(return_value) = result {
			if return_value.did_revert() {
				Err("Contract reverted".into())
			} else {
				let is_success =
					bool::abi_decode_validate(&return_value.data).expect("Failed to ABI decode");
				if is_success {
					let balance = <Self as fungibles::Inspect<_>>::balance(asset_id, who);
					Ok(balance)
				} else {
					Err("Contract transfer failed".into())
				}
			}
		} else {
			Err("Contract out of gas".into())
		}
	}

	/// Reduce the balance of `who` by `amount`.
	///
	/// If `precision` is `Exact` and it cannot be reduced by that amount for
	/// some reason, return `Err` and don't reduce it at all. If `precision` is `BestEffort`, then
	/// reduce the balance of `who` by the most that is possible, up to `amount`.
	///
	/// In either case, if `Ok` is returned then the inner is the amount by which is was reduced.
	/// Minimum balance will be respected and thus the returned amount may be up to
	/// `Self::minimum_balance() - 1` greater than `amount` in the case that the reduction caused
	/// the account to be deleted.
	fn decrease_balance(
		asset: Self::AssetId,
		who: &AccountId,
		mut amount: Self::Balance,
		precision: Precision,
		preservation: Preservation,
		force: Fortitude,
	) -> Result<Self::Balance, DispatchError> {
		let old_balance = Self::balance(asset.clone(), who);
		let reducible = Self::reducible_balance(asset.clone(), who, preservation, force);
		match precision {
			BestEffort => amount = amount.min(reducible),
			Exact => ensure!(reducible >= amount, TokenError::FundsUnavailable),
		}
		let new_balance = old_balance.checked_sub(&amount).ok_or(TokenError::FundsUnavailable)?;
		if let Some(dust) = Self::write_balance(asset.clone(), who, new_balance)? {
			Self::handle_dust(Dust(asset, dust));
		}
		Ok(old_balance.saturating_sub(new_balance))
	}

	/// Increase the balance of `who` by `amount`.
	///
	/// If it cannot be increased by that amount for some reason, return `Err` and don't increase
	/// it at all. If Ok, return the imbalance.
	/// Minimum balance will be respected and an error will be returned if
	/// `amount < Self::minimum_balance()` when the account of `who` is zero.
	fn increase_balance(
		asset: Self::AssetId,
		who: &AccountId,
		amount: Self::Balance,
		precision: Precision,
	) -> Result<Self::Balance, DispatchError> {
		let old_balance = Self::balance(asset.clone(), who);
		let new_balance = if let BestEffort = precision {
			old_balance.saturating_add(amount)
		} else {
			old_balance.checked_add(&amount).ok_or(ArithmeticError::Overflow)?
		};
		if new_balance < Self::minimum_balance(asset.clone()) {
			// Attempt to increase from 0 to below minimum -> stays at zero.
			if let BestEffort = precision {
				Ok(Self::Balance::default())
			} else {
				Err(TokenError::BelowMinimum.into())
			}
		} else {
			if new_balance == old_balance {
				Ok(Self::Balance::default())
			} else {
				if let Some(dust) = Self::write_balance(asset.clone(), who, new_balance)? {
					Self::handle_dust(Dust(asset, dust));
				}
				Ok(new_balance.saturating_sub(old_balance))
			}
		}
	}
