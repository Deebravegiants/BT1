### Title
Revoked LDAP users/roles retain elevated access until the next upstream sync tick, because session/token authorization only checks expiry, not upstream role freshness - ([File: core/sessions/ldapauth/ldap.go], [File: core/sessions/ldapauth/sync.go])

### Summary
The LDAP authentication provider caches a user's role in the `ldap_sessions` and `ldap_user_api_tokens` tables at login time and serves every subsequent authenticated request from that cached role with no check for staleness against the upstream LDAP directory. Reconciliation with the LDAP server (removal or role downgrade) is performed asynchronously by `LDAPServerStateSyncer.Work` and is only guaranteed to run on the configured `UpstreamSyncInterval`/`UpstreamSyncRateLimit` timer. This mirrors the WrappedIbbtcEth pattern: a periodically-refreshed value (`pricePerShare` / here, `user_role`) is trusted by consumer functions without any check that the refresh actually ran recently, creating a window in which a stale, more-privileged cached value can be exploited.

### Finding Description
`AuthorizedUserWithSession` and `FindUserByAPIToken` in `core/sessions/ldapauth/ldap.go` authorize a request purely by looking up the cached `user_role` column and checking only time-based *expiry* (`created_at + duration >= now()`), never re-validating against the upstream LDAP group membership: [1](#0-0) [2](#0-1) 

The only mechanism that reconciles cached roles/removed users with the upstream source of truth is `LDAPServerStateSyncer.Work`, which re-queries LDAP group membership and only then purges revoked sessions/tokens or downgrades cached roles: [3](#0-2) [4](#0-3) 

This reconciliation is gated by two independent timers, both attacker/administrator-uncontrollable from the unprivileged actor's perspective, but capable of leaving a large window open: [5](#0-4) [6](#0-5) 

Critically, if `UpstreamSyncInterval` is configured as instant/zero, `Work()` is invoked only once at node startup and the periodic goroutine (`go l.run()`) is never started at all, meaning no further upstream reconciliation happens automatically for the lifetime of the process unless something else triggers it: [5](#0-4) 

The package-level documentation explicitly claims sync happens "for every auth endpoint hit", but no code path in `ldap.go`'s `AuthorizedUserWithSession`/`FindUserByAPIToken`/`FindUser` (the actual per-request authorization functions) invokes `LDAPServerStateSyncer.Work` or any upstream re-check — only `SessionsController.Create`/`Destroy` call `sc.App.WakeSessionReaper()` on login/logout, which is unrelated to per-request re-validation of an *existing* session's role: [7](#0-6) [8](#0-7) 

This exactly parallels the reported bug class: a contract-level cached value (`pricePerShare`) is trusted between costly refreshes with no staleness guard, letting an actor exploit the gap between the cached value and the true upstream state.

### Impact Explanation
A user demoted or removed from an admin/edit LDAP group (e.g., after being fired, having privileges revoked, or being caught misbehaving) retains their previously-cached elevated role for their existing session cookie or API token until the next successful `Work()` sync cycle completes — which can be delayed by `UpstreamSyncInterval`, throttled further by `UpstreamSyncRateLimit`, or (if intervals are misconfigured to instant/zero) never re-run automatically after node startup. During this window the still-valid session/API token continues to authorize privileged actions (bridge/job management, key operations, fund-moving job runs) as if the user still held the old role — a direct authorization-bypass analog to minting/burning against a stalled price.

### Likelihood Explanation
Exploitability depends on operator misconfiguration or normal operational timing (a revoked user simply continuing to use an already-authenticated session/token before the next sync fires), not on any special attacker capability — the "attacker" is simply a legitimate but recently-revoked LDAP-authenticated user who keeps using already-issued credentials. This is a realistic, unprivileged/low-privilege actor path (an authenticated user retaining authorization past revocation) rather than a purely theoretical one, and the risk window size is fully a function of operator-controlled sync interval config, matching the "market volatility during threshold time" caveat in the reference report.

### Recommendation
Add a role/session freshness check analogous to the suggested `priceUpdateThreshold` pattern:
- Track `last_upstream_sync_at` per `ldap_sessions`/`ldap_user_api_tokens` row (or globally on the syncer).
- In `AuthorizedUserWithSession` and `FindUserByAPIToken`, in addition to the expiry check, verify `now() - last_upstream_sync_at < maxStalenessThreshold`; if stale, either reject the request or force a synchronous re-validation against LDAP for that specific user before granting access.
- Ensure `LDAPServerStateSyncer.run()` is started unconditionally (or provide an explicit periodic fallback) even when `UpstreamSyncInterval` is configured to instant/zero, so revocations are guaranteed to propagate within a bounded, auditable window rather than only at startup.

### Proof of Concept
1. Configure LDAP auth with a nonzero `UpstreamSyncInterval`/`UpstreamSyncRateLimit` (or zero, the worst case).
2. User `alice@example.com` is a member of the LDAP Admin group; she logs in via `CreateSession`, which calls `FindUser` and caches `user_role = Admin` in `ldap_sessions` [9](#0-8) .
3. An operator removes alice from the Admin group upstream in LDAP (revocation).
4. Before the next `LDAPServerStateSyncer.Work()` tick reconciles the `ldap_sessions` table (per the interval/rate-limit gating shown above), alice continues to send requests with her existing session cookie; `AuthorizedUserWithSession` returns the stale cached `Admin` role straight from the DB without any upstream check [10](#0-9) .
5. Alice performs admin-only actions (e.g., managing bridges/jobs) using the stale elevated role until the next sync cycle purges/downgrades her session — an unbounded or configuration-dependent privilege-retention window.

func (l *ldapAuthenticator) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	conn, err := l.ldapClient.CreateEphemeralConnection()
	if err != nil {
		return "", errors.New("unable to establish connection to LDAP server with provided URL and credentials")
	}
	defer conn.Close()

	var returnErr error

	// Attempt to LDAP Bind with user provided credentials
	escapedEmail := ldap.EscapeFilter(strings.ToLower(sr.Email))
	searchBaseDN := fmt.Sprintf("%s=%s,%s,%s", l.config.BaseUserAttr(), escapedEmail, l.config.UsersDN(), l.config.BaseDN())
	if err = conn.Bind(searchBaseDN, sr.Password); err != nil {
		l.lggr.Infof("Error binding user authentication request in LDAP Bind: %v", err)
		returnErr = errors.New("unable to log in with LDAP server. Check credentials")
	}

	// Bind was successful meaning user and credentials are present in LDAP directory
	// Reuse FindUser functionality to fetch user roles used to create ldap_session entry
	// with cached user email and role
	foundUser, err := l.FindUser(ctx, escapedEmail)
	if err != nil {
		l.lggr.Infof("Successful user login, but error querying for user groups: user: %s, error %v", escapedEmail, err)
		returnErr = errors.New("log in successful, but no assigned groups to assume role")
	}

	isLocalUser := false
	if returnErr != nil {
		// Unable to log in against LDAP server, attempt fallback local auth with credentials, case of local CLI Admin account
		// Successful local user sessions can not be managed by the upstream server and have expiration handled by the reaper sync module
		foundUser, returnErr = l.localLoginFallback(ctx, sr)
		isLocalUser = true
	}

	// If err is still populated, return
	if returnErr != nil {
		return "", returnErr
	}

	l.lggr.Infof("Successful LDAP login request for user %s - %s", sr.Email, foundUser.Role)

	// Save session, user, and role to database. Given a session ID for future queries, the LDAP server will not be queried
	// Sessions are set to expire after the duration + creation date elapsed, and are synced on an interval against the upstream
	// LDAP server
	session := sessions.NewSession()
	_, err = l.ds.ExecContext(
		ctx,
		"INSERT INTO ldap_sessions (id, user_email, user_role, localauth_user, created_at) VALUES ($1, $2, $3, $4, now())",
		session.ID,
		strings.ToLower(sr.Email),
		foundUser.Role,
		isLocalUser,
	)
	if err != nil {
		l.lggr.Errorf("unable to create new session in ldap_sessions table %v", err)
		return "", fmt.Errorf("error creating local LDAP session: %w", err)
	}

	l.auditLogger.Audit(audit.AuthLoginSuccessNo2FA, map[string]any{"email": sr.Email})

	return session.ID, nil
}

func (l *LDAPServerStateSyncer) Start(ctx context.Context) error {
	// If enabled, start a background task that calls the Sync/Work function on an
	// interval without needing an auth event to trigger it
	// Use IsInstant to check 0 value to omit functionality.
	if !l.config.UpstreamSyncInterval().IsInstant() {
		l.lggr.Info("LDAP Config UpstreamSyncInterval is non-zero, sync functionality will be called on a timer, respecting the UpstreamSyncRateLimit value")
		go l.run()
	} else {
		// Ensure upstream server state is synced on startup manually if interval check not set
		l.Work(ctx)
	}
	return nil
}

func (sc *SessionsController) Create(c *gin.Context) {
	defer sc.App.WakeSessionReaper()
	ctx := c.Request.Context()
	sc.App.GetLogger().Debugf("TRACE: Starting Session Creation")

	session := sessions.Default(c)
	var sr clsessions.SessionRequest
	if err := c.ShouldBindJSON(&sr); err != nil {
		jsonAPIError(c, http.StatusBadRequest, fmt.Errorf("error binding json %w", err))
		return
	}

	// Does this user have 2FA enabled?
	userWebAuthnTokens, err := sc.App.AuthenticationProvider().GetUserWebAuthn(ctx, sr.Email)
	if err != nil {
		sc.App.GetLogger().Errorf("Error loading user WebAuthn data: %s", err)
		jsonAPIError(c, http.StatusInternalServerError, errors.New("internal Server Error"))
		return
	}

	// If the user has registered MFA tokens, then populate our session store and context
	// required for successful WebAuthn authentication
	if len(userWebAuthnTokens) > 0 {
		sr.SessionStore = sc.sessions
		sr.WebAuthnConfig = sc.App.GetWebAuthnConfiguration()
	}

	sid, err := sc.App.AuthenticationProvider().CreateSession(ctx, sr)
	if err != nil {
		jsonAPIError(c, http.StatusUnauthorized, err)
		return
	}

	if err := saveSessionID(session, sid); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, errors.Join(errors.New("unable to save session id"), err))
		return
	}

	jsonAPIResponse(c, Session{Authenticated: true}, "session")
}
