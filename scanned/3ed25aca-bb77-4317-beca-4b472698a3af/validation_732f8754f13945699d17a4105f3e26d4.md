### Title
Cached role in LDAP/OIDC-issued API tokens and sessions is not revoked immediately when upstream privilege is reduced or revoked - ([File: core/sessions/ldapauth/sync.go])

### Summary
CVE-2020-24330 is a "fails to drop privilege when no longer needed" bug class: `tcsd` keeps a privileged (root) group membership active long after it should have dropped it. The analogous pattern in this codebase is that `ldap_sessions` / `ldap_user_api_tokens` (and the OIDC equivalents `oidc_sessions` / `oidc_user_api_tokens`) cache a user's `user_role` at authentication time, and that cached, privileged role is only re-validated/revoked against the upstream identity source on a *periodic* background sync (`UpstreamSyncInterval`) rather than on each request. Until that sync runs, a user whose upstream group membership (privilege) has been reduced or removed continues to be authenticated locally with the old, more privileged role.

### Finding Description
`FindUserByAPIToken` in `core/sessions/ldapauth/ldap.go` (lines 204-236) and `core/sessions/oidcauth/oidc.go` (lines 297-338) authorize each incoming API request purely from the locally cached `user_role` column in `ldap_user_api_tokens` / `oidc_user_api_tokens`. Likewise `AuthorizedUserWithSession` in `core/sessions/oidcauth/oidc.go` (lines 349-391) reads the cached `user_role` from `oidc_sessions` for every session-authenticated request. No call is made to the upstream LDAP/OIDC provider during request authentication — the comments explicitly say "user role and email are cached so no further upstream query is performed." [1](#0-0) [2](#0-1) 

The only mechanism that reconciles these cached roles against the source of truth is `LDAPServerStateSyncer.Work`, which runs on a configurable timer (`UpstreamSyncInterval`) or once at startup, and updates `ldap_sessions`/`ldap_user_api_tokens` rows via a batched `CASE WHEN` update: [3](#0-2) 

If `UpstreamSyncInterval` is configured with any meaningful delay (or is misconfigured/large), a user demoted from `admin` to `view` in the upstream LDAP/OIDC directory (or fully deactivated) retains their previously-granted elevated role in the local cache for the entire interval — i.e., excess privilege that should have been dropped is retained "when no longer needed," exactly the CVE-2020-24330 bug class, just realized through a stale-privilege cache instead of an un-dropped process gid.

### Impact Explanation
An unprivileged/downgraded actor (a node API user whose admin/edit rights were revoked upstream) can continue to exercise the previously granted role — including `RequiresAdminRole`-gated endpoints (`core/web/auth/auth.go` lines 236-253) — for up to the full `UpstreamSyncInterval` window after revocation, because role enforcement in `RequiresAdminRole`/`RequiresEditRole`/`RequiresRunRole` trusts whatever role is attached to the `clsessions.User` object populated from the stale cache. This is a genuine authorization/role-bypass window (unauthorized privileged API access), not merely a cosmetic issue.

### Likelihood Explanation
Requires the node operator to run LDAP or OIDC auth (not local auth, which reads role live from the `users` table on every request) and to have a nonzero `UpstreamSyncInterval`. This is a realistic and documented supported configuration (the package doc in `core/sessions/ldapauth/ldap.go` explicitly describes this caching/interval-sync design), so the likelihood of the misconfiguration/timing window existing in production is moderate — it's a designed trade-off, but one that silently retains privilege longer than the operator intends when revoking access.

### Recommendation
- Re-validate the cached role against the upstream provider (or at minimum re-check an "active/deactivated" flag) synchronously on sensitive/privileged actions, not only on the periodic sync interval, or drastically shrink the effective staleness window for privilege downgrades.
- Add an explicit "force revoke now" administrative action that immediately purges `ldap_sessions`/`ldap_user_api_tokens` (and OIDC equivalents) for a given user, rather than relying solely on the timer-driven `Work()` sync.
- Document/enforce a maximum safe `UpstreamSyncInterval` value to bound the privilege-retention window.

### Proof of Concept
1. Configure node with LDAP (or OIDC) auth and `UpstreamSyncInterval = 24h`.
2. User `alice` is a member of the LDAP Admin group; she logs in and receives an API token/session cached with `user_role = admin` in `ldap_user_api_tokens` / `ldap_sessions` (`core/sessions/ldapauth/ldap.go:204-236`, `sync.go` insert path).
3. Administrator removes `alice` from the Admin group upstream (revokes privilege).
4. Before the next `UpstreamSyncInterval` tick (up to 24h later), `alice` continues to call admin-gated endpoints; `FindUserByAPIToken`/`AuthorizedUserWithSession` return the stale cached `user_role = admin`, and `RequiresAdminRole` (`core/web/auth/auth.go:236-253`) grants access.
5. Only after `LDAPServerStateSyncer.Work` executes and rewrites `ldap_user_api_tokens.user_role` does `alice` lose admin access. [4](#0-3)
