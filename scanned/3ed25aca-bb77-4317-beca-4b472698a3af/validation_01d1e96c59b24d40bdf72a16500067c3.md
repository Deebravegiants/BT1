### Title
Unprivileged authenticated user can dump heap/goroutine memory via `/v2/debug/pprof/heap` exposing sensitive in-process data - (File: core/web/router.go)

### Summary
The CVE describes a Linux debugfs handler leaking sensitive kernel address information to any local unprivileged reader. The closest reachable analog in this codebase is the standard `net/http/pprof` handlers mounted by `metricRoutes` and reachable at `/v2/debug/pprof/*`, which are gated only by session/token authentication (`auth.AuthenticateByToken`/`auth.AuthenticateBySession`) and carry no role check, unlike nearly every other sensitive endpoint in the router (which uses `auth.RequiresEditRole`/`auth.RequiresAdminRole`).

### Finding Description
`metricRoutes` registers the full set of Go `pprof` handlers, including `/heap`, `/goroutine`, `/allocs`, and `/profile`, on the `authv2` group: [1](#0-0) 
This group is only wrapped with `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateByToken, auth.AuthenticateBySession)` and then `metricRoutes(authv2)` is invoked directly with no role guard: [2](#0-1) [3](#0-2) 
By contrast, virtually every other sensitive resource in this same group (keys export/import/delete, users, vault operations) is additionally wrapped with `auth.RequiresEditRole` or `auth.RequiresAdminRole`, e.g.: [4](#0-3) [5](#0-4) 
The project's own documentation explicitly acknowledges that pprof heap dumps "may potentially expose sensitive data e.g. private key components": [6](#0-5) [7](#0-6) 
Yet the `InsecurePPROFHeap` config flag documented as controlling this exposure has "no effect. Always enabled," meaning the heap dump is unconditionally reachable to anyone who can authenticate — including a low-privilege "run"-role or "view"-role API token holder, since there is no `RequiresAdminRole`/`RequiresEditRole` wrapper on `metricRoutes`.

### Impact Explanation
A heap dump (`/debug/pprof/heap?debug=1`) or full goroutine dump can capture in-memory secrets such as decrypted private keys, session tokens, database credentials, or vault key material that transiently reside in process memory, directly matching the CVE's "sensitive address information" disclosure class. Any authenticated node API user — regardless of role — can trigger this, which is a confidentiality violation reachable by a comparatively low-privilege client, analogous to the "local unprivileged user" actor in the CVE.

### Likelihood Explanation
Exploitation only requires a valid session cookie or API token for the node (not necessarily an admin), and a single unauthenticated-but-valid GET request to `/v2/debug/pprof/heap?debug=1`; no race condition or timing constraint is needed, making this reliably reproducible by any authenticated caller, including tokens intended only for job-run or read-only access.

### Recommendation
Restrict `metricRoutes` to `auth.RequiresAdminRole` (or a dedicated operator-only role) rather than plain session/token authentication, and honor `InsecurePPROFHeap` (or a similar gate) to disable heap/goroutine/profile endpoints by default in production, consistent with the documented security intent in `core.toml`/`CONFIG.md`.

### Proof of Concept
1. Obtain any valid Chainlink node API session cookie or API token with only `run`/`view` role (not admin) via `POST /sessions` or `/v2/user/token`.
2. Send `GET /v2/debug/pprof/heap?debug=1` with that credential.
3. Observe a full heap dump returned without any role check, potentially containing decrypted keys or secrets resident in memory at time of capture.
