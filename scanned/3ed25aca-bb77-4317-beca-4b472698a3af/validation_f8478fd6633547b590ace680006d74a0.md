Confirmed root cause: the JWT replay check in `WorkflowMetadataHandler.Authorize` performs a non-atomic check-then-act sequence — `isReplay` acquires an `RLock`, returns, releases the lock, and only *after* the rest of the authorization logic succeeds does `recordUsage` acquire a separate `Lock` to mark the JTI as used. [1](#0-0)  The `isReplay`/`recordUsage` pair are two independently-locked critical sections rather than one atomic "check-and-set" operation. [2](#0-1)  This is the same bug class as the reported "missing nonReentrant" issue: a state check (has this been used already?) is separated from the state mutation (mark as used) by externally-callable logic in between, so two concurrent requests carrying the identical signed JWT can both pass the `isReplay` check before either calls `recordUsage`, defeating the single-use guarantee that the JWT-replay mechanism is supposed to provide.

This differs from the analogous `RequestReplayGuard` used for allowlist-based Vault auth, whose `CheckAndRecord` correctly holds a single mutex for the entire check-and-record operation, making it atomic and race-free. [3](#0-2)  The HTTP-trigger JWT path does not use this pattern.

### Title
Non-atomic JWT replay check-and-record in HTTP Trigger authorization allows concurrent JWT replay (workflow re-execution) - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
`WorkflowMetadataHandler.Authorize`, which authenticates every inbound HTTP trigger request that initiates a CRE workflow execution, checks whether a JWT's `jti` claim has already been used (`isReplay`) and only records that usage (`recordUsage`) after further processing succeeds — using two separate mutex-protected sections rather than one atomic operation.

### Finding Description
`Authorize` calls `h.jwtCache.isReplay(claims.ID)` under an `RLock`, and if it returns `false`, proceeds to look up authorized keys for the workflow and only calls `h.jwtCache.recordUsage(claims.ID)` (a separate `Lock`) at the very end of the function. [1](#0-0)  Because these are two distinct locked sections with unrelated business logic (workflow key lookup) executed in between, this is a classic TOCTOU (time-of-check-to-time-of-use) race: if two requests bearing the identical signed JWT arrive concurrently, both can call `isReplay` and observe `false` before either calls `recordUsage`. Both will then be treated as valid, authorized requests. This is the direct analog of the "missing nonReentrant" bug class described in the external report — the vulnerable code performs an external-facing state check, allows re-entry through concurrent invocation before the internal state is updated, and the single-use invariant is broken.

### Impact Explanation
A user (workflow owner) or anyone who captures a single valid signed JWT for an HTTP trigger request can, by firing multiple concurrent requests with the same token, cause the same trigger payload to be authorized and dispatched to the DON more than once, triggering duplicate workflow executions. Depending on what the workflow does downstream (e.g., a workflow that moves funds, submits an on-chain transaction, or performs an idempotent-assumed action per request), this can result in duplicate/unintended execution of actions that the JWT-replay-protection mechanism was specifically designed to prevent exactly once.

### Likelihood Explanation
Exploitation requires only the ability to send two or more concurrent HTTP requests to the gateway with the same previously-obtained signed JWT — no privileged access is required, since this is exactly the internet-facing HTTP trigger endpoint. The race window is the time between JWT signature verification and `recordUsage`, which includes workflow key lookup; this is a reasonably exploitable window especially if `authorizedKeys` lookups or additional work introduce latency.

### Recommendation
Merge the read-check and write-record into a single atomic critical section (a single lock held for the full duration of "check-if-seen, then mark-seen"), analogous to `RequestReplayGuard.CheckAndRecord` [3](#0-2) . E.g., add a `checkAndRecord(jti)` method on `jwtReplayCache` that takes the write lock once, checks for existence, and inserts atomically, returning early if already present, and use that in place of the separate `isReplay`/`recordUsage` calls in `Authorize`.

### Proof of Concept
1. Obtain one valid, correctly-signed JWT for an authorized workflow's HTTP trigger request (as in the existing test `TestWorkflowMetadataHandler_Authorize`/"JWT replay protection"). [4](#0-3) 
2. Fire two (or more) concurrent goroutines calling `HandleUserTriggerRequest` (or directly `WorkflowMetadataHandler.Authorize`) with the identical JWT/request.
3. Because `isReplay` and `recordUsage` are not executed under one held lock, both goroutines can pass the `isReplay(claims.ID)` check (each sees `false`) before either calls `recordUsage`, resulting in both requests being authorized and dispatched — bypassing the intended single-use enforcement demonstrated by the sequential test at [5](#0-4) , which only proves sequential (non-concurrent) replay is blocked.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
