### Title
User Enumeration via Distinct Authentication Error Messages - ([File: core/web/sessions_controller.go])

### Summary
The `/sessions` login endpoint returns the underlying authenticator error message verbatim to unauthenticated clients. The local, LDAP, and OIDC authentication providers each return distinct, differently-worded errors for "email/user not found" versus "wrong password", allowing an attacker to enumerate valid Chainlink node user accounts, analogous to the CVE-2025-65899 Kalmia CMS user-enumeration flaw.

### Finding Description
`SessionsController.Create` calls `sc.App.AuthenticationProvider().CreateSession(ctx, sr)` and, on failure, forwards the raw `err` directly into the HTTP response body via `jsonAPIError(c, http.StatusUnauthorized, err)`: [1](#0-0) 

The underlying `CreateSession` implementations produce different error strings depending on whether the email was found or not versus whether the password matched:

- Local auth ORM: returns `"Invalid email"` when the email doesn't match, and `"Invalid password"` when the password check fails: [2](#0-1) 

- LDAP auth's local-login fallback: returns `"invalid email"` vs `"invalid password"` distinctly: [3](#0-2) 

- OIDC auth's local-login fallback: same pattern, `"invalid email"` vs `"invalid password"`: [4](#0-3) 

Because `Create` propagates whichever specific error string was returned straight to the unauthenticated caller, the HTTP response body differs observably between a nonexistent email (`"Invalid email"` / `"invalid email"`) and a valid email with a wrong password (`"Invalid password"` / `"invalid password"`). This exactly matches the bug class in the reference CVE: distinguishable authentication responses (`user_not_found` vs `invalid_password`) that leak account existence.

### Impact Explanation
An unauthenticated attacker submitting `POST /sessions` with candidate email/password pairs can use the response text to determine whether a given email address corresponds to an existing node user account. This does not by itself grant access, but it materially aids credential-stuffing/brute-force campaigns against the Chainlink node operator UI/API by narrowing the target set to confirmed valid usernames, and can leak organizational information (which operator/admin emails are provisioned on the node).

### Likelihood Explanation
The `/sessions` endpoint is reachable by any unauthenticated network client with access to the node's Operator UI/API port; no privileges or prior authentication are required, and the differing error text is returned directly and reliably for every request, making exploitation straightforward and automatable.

### Recommendation
In `SessionsController.Create` (and the `TestPassword`/`localLoginFallback` code paths across `localauth`, `ldapauth`, and `oidcauth`), avoid propagating the specific internal error string to the client. Return a single generic message (e.g., `"invalid credentials"`) with `401 Unauthorized` for all authentication failures, and only log the detailed reason (email not found vs. password mismatch) server-side/audit log, matching the existing constant-time email comparison intent already present in the code (`constantTimeEmailCompare`).

### Proof of Concept
1. `POST /sessions` with `{"email":"nonexistent@test.net","password":"anything"}` → response body error is `"Invalid email"` (local auth) / `"invalid email"` (LDAP/OIDC fallback), HTTP 401.
2. `POST /sessions` with `{"email":"<valid_admin_email>","password":"wrongpassword"}` → response body error is `"Invalid password"` (local auth) / `"invalid password"` (LDAP/OIDC fallback), HTTP 401.
3. Comparing the two response bodies reveals whether `<valid_admin_email>` exists as a provisioned user, confirming the enumeration. [5](#0-4)

func (l *ldapAuthenticator) localLoginFallback(ctx context.Context, sr sessions.SessionRequest) (sessions.User, error) {
	var user sessions.User
	sql := "SELECT * FROM users WHERE lower(email) = lower($1)"
	err := l.ds.GetContext(ctx, &user, sql, sr.Email)
	if err != nil {
		return user, err
	}
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		l.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return user, errors.New("invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		l.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return user, errors.New("invalid password")
	}

	return user, nil
}
