## Title
Unbounded per-request iteration over all registered web-api triggers causes linear cost growth and DoS risk - (File: `core/capabilities/webapi/trigger/trigger.go`)

## Summary
`triggerConnectorHandler.processTrigger` iterates over **every** workflow currently registered for the web-api trigger capability, and for each registered workflow, over every topic in the incoming request, on **every single incoming trigger message**. The set of registered workflows only grows over the life of the DON (there is no eviction other than explicit `UnregisterTrigger`), so the per-message cost scales linearly (and in the worst case, quadratically with topics) with the total number of workflows ever registered for this trigger — mirroring the reported bug class where per-user operation cost grows unboundedly with global historical state rather than with the caller's own footprint.

## Finding Description
`RegisterTrigger` adds an entry to `h.registeredWorkflows` for each workflow that subscribes to the web-api trigger capability, with no bound on the number of entries: [1](#0-0) 

Every incoming trigger message — which originates from an unauthenticated-until-this-point HTTP call routed through the Gateway and delivered to the node via `HandleGatewayMessage` — invokes `processTrigger`, which snapshots and then iterates the **entire** `registeredWorkflows` map, and for each entry iterates all `topics` supplied in the request payload: [2](#0-1) 

This is the same structural flaw as the M-18 root cause: a per-request operation is required to walk the *entire* accumulated history/state of the system (there, all liquidations since deposit; here, all registered trigger workflows) instead of doing bounded, targeted work (e.g., a map lookup keyed by topic or workflow selector). As more workflows are onboarded to the platform over time, `len(h.registeredWorkflows)` grows without bound, and the cost of handling *each* incoming HTTP-triggered gateway message grows proportionally, even though each individual caller is only trying to reach a small number of specific workflows.

The entry point, `HandleGatewayMessage`, is reachable from unprivileged, internet-facing traffic: any external caller can hit the Gateway's web-api-trigger endpoint, and the message is forwarded to the node's handler without any bound related to number of registered workflows: [3](#0-2) 

## Impact Explanation
As the number of workflows registered for the web-api trigger grows (a normal, expected growth pattern for a production DON, analogous to "many liquidations occur over time" in the original report), the cost of processing *every subsequent* incoming trigger request increases linearly. Because this loop holds no bound and executes under a request-processing path fed directly by external HTTP submissions via the Gateway, a sufficiently large number of registered workflows turns ordinary trigger traffic into a resource-exhaustion vector: legitimate requests degrade in latency/CPU cost for the whole DON, and an attacker who can drive workflow registration growth (or simply waits for organic growth) can amplify the cost of each of their own trigger submissions to slow down or starve the shared per-message processing loop (note `processTrigger` runs while holding no lock during the loop, but is still on the critical path of every gateway message dispatch for this handler). This is a DoS-class impact analogous to the M-18 finding, though the specific mechanism is CPU/latency exhaustion rather than block-gas-limit exhaustion.

## Likelihood Explanation
Likelihood is moderate: the vulnerable code path is exercised on every legitimate web-api-trigger message, so no attacker action beyond normal usage is required to reach the code. The severity scales with the number of registered workflows, which is expected to grow over the platform's lifetime; there is no cap, decay, or indexing by topic/workflow to bound the iteration, so the degradation is a function of time/adoption rather than requiring an unusual attack precondition.

## Recommendation
Index `registeredWorkflows` by topic (e.g., `map[topic]map[triggerID]*webapiTrigger`) so that `processTrigger` only visits triggers relevant to the topics present in the incoming request, instead of scanning the full set of registered workflows on every message. Additionally, consider bounding/monitoring the total number of concurrently registered triggers per DON to avoid unbounded growth.

## Proof of Concept
Not applicable (off-chain Go service logic, no on-chain PoC). The unbounded scan can be demonstrated by registering N workflows via `RegisterTrigger` with distinct `allowedTopics`, then measuring that `processTrigger`'s execution time for a single incoming message grows linearly with N regardless of how many of those N workflows are actually targeted by the message's topics, per [2](#0-1) .

func (h *triggerConnectorHandler) HandleGatewayMessage(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) error {
	msg, err := hc.ValidatedMessageFromReq(req)
	if err != nil {
		h.lggr.Errorw("error validating message from request", "err", err, "request", req)
		return nil
	}
	body := &msg.Body
	sender := ethCommon.HexToAddress(body.Sender)
	var payload webapicap.TriggerRequestPayload
	err = json.Unmarshal(body.Payload, &payload)
	if err != nil {
		h.lggr.Errorw("error decoding payload", "err", err)
		err = h.sendResponse(ctx, gatewayID, body, ghcapabilities.TriggerResponsePayload{Status: "ERROR", ErrorMessage: fmt.Errorf("error %s decoding payload", err.Error()).Error()})
		if err != nil {
			h.lggr.Errorw("error sending response", "err", err)
		}
		return nil
	}

	switch body.Method {
	case ghcapabilities.MethodWebAPITrigger:
		resp := h.processTrigger(ctx, gatewayID, body, sender, payload)
		var response ghcapabilities.TriggerResponsePayload
		if resp == nil {
			response = ghcapabilities.TriggerResponsePayload{Status: "ACCEPTED"}
		} else {
			response = ghcapabilities.TriggerResponsePayload{Status: "ERROR", ErrorMessage: resp.Error()}
			h.lggr.Errorw("Error processing trigger", "gatewayID", gatewayID, "body", body, "response", resp)
		}
		err = h.sendResponse(ctx, gatewayID, body, response)
		if err != nil {
			h.lggr.Errorw("Error sending response", "body", body, "response", response, "err", err)
		}
		return nil

func (h *triggerConnectorHandler) RegisterTrigger(ctx context.Context, req capabilities.TriggerRegistrationRequest) (<-chan capabilities.TriggerResponse, error) {
	cfg := req.Config
	if cfg == nil {
		return nil, errors.New("config is required to register a web api trigger")
	}

	reqConfig, err := h.ValidateConfig(cfg)
	if err != nil {
		return nil, err
	}

	if len(reqConfig.AllowedSenders) == 0 {
		return nil, errors.New("allowedSenders must have at least 1 entry")
	}

	h.mu.Lock()
	defer h.mu.Unlock()
	_, errBool := h.registeredWorkflows[req.TriggerID]
	if errBool {
		return nil, fmt.Errorf("triggerId %s already registered", req.TriggerID)
	}

	rateLimiterConfig := reqConfig.RateLimiter
	commonRateLimiter := ratelimit.RateLimiterConfig{
		GlobalRPS:      rateLimiterConfig.GlobalRPS,
		GlobalBurst:    int(rateLimiterConfig.GlobalBurst),
		PerSenderRPS:   rateLimiterConfig.PerSenderRPS,
		PerSenderBurst: int(rateLimiterConfig.PerSenderBurst),
	}

	rateLimiter, err := ratelimit.NewRateLimiter(commonRateLimiter)
	if err != nil {
		return nil, err
	}

	allowedSendersMap := map[string]bool{}
	for _, k := range reqConfig.AllowedSenders {
		allowedSendersMap[k] = true
	}

	allowedTopicsMap := map[string]bool{}
	for _, k := range reqConfig.AllowedTopics {
		allowedTopicsMap[k] = true
	}

	ch := make(chan capabilities.TriggerResponse, defaultSendChannelBufferSize)

	h.registeredWorkflows[req.TriggerID] = &webapiTrigger{
		workflowID:     req.Metadata.WorkflowID,
		allowedTopics:  allowedTopicsMap,
		allowedSenders: allowedSendersMap,
		ch:             ch,
		config:         *reqConfig,
		rateLimiter:    rateLimiter,
	}

	return ch, nil
}
