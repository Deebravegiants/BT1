Target: EmporiumUpgradeable.runAction CASE 2 selector guard (`selector == IHinkalWallet.callHinkalWallet.selector || selector == IHinkalWallet.doSendToRelay.selector`) versus HinkalWallet.onlyEmporium. Attacker action: attacker's own op.endpoint is set to a HinkalWallet belonging to a DIFFERENT user (obtained e.g. by observing it on-chain), and callData is crafted for a function on that wallet OTHER than callHinkalWallet/doSendToRelay, such as isValidSignature or the wallet's `receive()`. Precondition: attacker knows victim's HinkalWallet address (public), the selector guard only blocks two specific selectors. Sequence: attacker sets op.endpoint = victimWallet, op.callData = abi.encodeWithSelector(bytes4(keccak256('isValidSignature(bytes32,bytes)')), ...) or simply sends ETH via op.value with empty calldata triggering receive(); this is allowed because onlyEmporium only restricts callHinkalWallet/doSendToRelay, not arbitrary read/receive functions, and CASE 2 calls op.endpoint.call{value: op.value}(op.callData) with emporium as msg.sender regardless of whose wallet it targets. While isValidSignature itself is view-only and harmless, the equality this exposes is: any op whose endpoint is an address the attacker does not own can still be executed with emporium's ETH/gas paid for by the current caller's op.value, and any ETH sent via op.value to victimWallet.receive() becomes irretrievably owned by the victim's wallet contract with the attacker unable to reclaim it if op.value came from attacker's own delta funds mistakenly routed. Equality broken: `from` of every value-bearing call within an attacker's own signed ops must equal an endpoint the attacker controls or intends, but stack.signerAddress verification (verifyWallet) never restricts op.endpoint choice at all -- only the ops array hash, so a compromised or careless off-chain signer could target ANY address. Impact: High, temporary freezing of an attacker's own routed value into a third party wallet is out of scope (self-harm), but Critical when combined with case where op.value is sourced from `deltaAmountChanges` funded by the relay/protocol fee rather than the attacker, causing protocol fee funds to be sent to an arbitrary third-party HinkalWallet. Proof: Foundry test crafting an EmporiumStack whose op.endpoint is a third party's HinkalWallet with op.value > 0 funded from relayFee-adjacent deltaAmountChanges, asserting the fee/relay balance ends up donated to an uninvolved wallet instead of being paid to circomData.relay.
