### Title
Session Fixation in OIDC Login Flow — Pre-Auth Session Cookie Reused as Authenticated Session - ([File: core/sessions/oidcauth/oidc.go])

### Summary
The OIDC authentication flow reuses the same gin session cookie (managed by `github.com/gin-contrib/sessions`) across the entire pre-authentication and post-authentication lifecycle. `handleSignIn` writes an OAuth `state` value into the pre-auth session and then redirects to the identity provider; on callback, `handleTokenExchange` validates the `state` and, on success, sets the authenticated `SessionIDKey` value onto **the same session object** rather than issuing a newly generated session cookie. There is no session ID/cookie regeneration at the authentication boundary, which is the exact bug class described in CVE-2018-1000173 (Jenkins Google Login Plugin session fixation).

### Finding Description
`NewRouter` wires a single cookie-backed session store (`cookie.NewStore`) for all routes via `sessions.Sessions(auth.SessionName, sessionStore)` [1](#0-0) . This is the same "gin session" object used both before and after login.

In the OIDC flow:
- `handleSignIn` retrieves the current (possibly pre-existing/unauthenticated) session via `sessions.Default(c)`, sets a `state` value on it, and saves it before redirecting the browser to the identity provider: [2](#0-1) .
- `handleTokenExchange` later retrieves the *same* default session, validates `state`, performs the OAuth code exchange and ID token verification, computes the user's role, inserts a new row into `oidc_sessions`, and then calls `ginSession.Set(webauth.SessionIDKey, clSession.ID)` followed by `ginSession.Save()` — i.e., it writes the newly authenticated session identifier into the existing gin session object rather than creating a fresh cookie/session container: [3](#0-2) .

Because the underlying gin session (identified by the cookie set by the `cookie.NewStore`) is never regenerated/rotated at the moment privilege is elevated from "unauthenticated" to "authenticated", an attacker who can fix (pre-set) the value of that session cookie in a victim's browser prior to login can predict/control the container that will later hold the victim's authenticated `SessionIDKey`. This mirrors the underlying weakness of CVE-2018-1000173: pre-auth session material controlled by an attacker survives the authentication ceremony and gets promoted to an authenticated session.

Note: because the store is `cookie.NewStore` (client-side encrypted cookie, not a server-side session ID lookup), the practical fixation vector depends on whether an attacker can plant a full cookie value the client will present at login and that persists through the exchange (e.g., via subdomain cookie injection, response splitting, or environments where cookies aren't scoped/regenerated per authentication). Regardless of the exact attacker delivery vector, the root cause — failure to regenerate/rotate the session container across the authentication boundary — is present in code and is the same class of bug as the CVE.

### Impact Explanation
If an attacker can fix a pre-authentication session value in a victim's browser (e.g. cross-subdomain cookie planting, shared network/proxy setups, or a future backend change to the session store that makes IDs attacker-visible/predictable), the victim's subsequent OIDC login would populate the attacker's known session container with the victim's authenticated `SessionIDKey` and role. The attacker could then present the same fixed cookie to impersonate the victim, gaining access at the victim's mapped RBAC role (Admin/Edit/Run/Read) as defined in `IDClaimsToUserRole` [4](#0-3) .

### Likelihood Explanation
Exploitation requires the attacker to first establish control over a pre-authentication session value the victim will use during OIDC login, which is non-trivial with the current cookie-based store but is the structural weakness the CVE targets. The likelihood is elevated by the fact that no session regeneration occurs at the trust-boundary crossing (unauthenticated → authenticated), which is the standard mitigation for this bug class and is absent here.

### Recommendation
Regenerate the session container (issue a brand-new gin session, or explicitly clear and re-create the cookie) immediately after successful OIDC authentication in `handleTokenExchange`, instead of writing `SessionIDKey` into the pre-existing session object with `ginSession.Set`/`ginSession.Save`. The same review should be applied to `SessionsController.Create` (local auth) which similarly reuses `sessions.Default(c)` and calls `saveSessionID` on the existing session [5](#0-4) .

### Proof of Concept
1. Attacker obtains/sets a session cookie value for the node's session store on a victim's browser (fixation delivery vector-dependent).
2. Attacker tricks victim into visiting `/oidc-login` (`handleSignIn`), which reuses/saves `state` on that same fixed session [2](#0-1) .
3. Victim completes OIDC login at the IdP and is redirected back; `handleTokenExchange` validates `state`, authenticates the victim, and sets `webauth.SessionIDKey` on the same fixed session object [6](#0-5) .
4. Attacker replays the known fixed cookie value against the node and is treated as the authenticated victim by `AuthenticateBySession`/`AuthenticateGQL`, which trust whatever `SessionIDKey` is present in the session [7](#0-6) .

func (oi *oidcAuthenticator) handleSignIn(c *gin.Context) {
	// generate state and store on session
	state := oi.generateState()
	session := sessions.Default(c)
	session.Set("state", state)
	err := session.Save()
	if err != nil {
		c.JSON(http.StatusInternalServerError, gin.H{"error": "Failed to save session"})
		return
	}

	// redirect to provider
	url := oi.oauth2Config.AuthCodeURL(state, oauth2.AccessTypeOffline)
	c.Redirect(http.StatusFound, url)
}

func (sc *SessionsController) Create(c *gin.Context) {
	defer sc.App.WakeSessionReaper()
	ctx := c.Request.Context()
	sc.App.GetLogger().Debugf("TRACE: Starting Session Creation")

	session := sessions.Default(c)
	var sr clsessions.SessionRequest
	if err := c.ShouldBindJSON(&sr); err != nil {
		jsonAPIError(c, http.StatusBadRequest, fmt.Errorf("error binding json %w", err))
		return
	}

	// Does this user have 2FA enabled?
	userWebAuthnTokens, err := sc.App.AuthenticationProvider().GetUserWebAuthn(ctx, sr.Email)
	if err != nil {
		sc.App.GetLogger().Errorf("Error loading user WebAuthn data: %s", err)
		jsonAPIError(c, http.StatusInternalServerError, errors.New("internal Server Error"))
		return
	}

	// If the user has registered MFA tokens, then populate our session store and context
	// required for successful WebAuthn authentication
	if len(userWebAuthnTokens) > 0 {
		sr.SessionStore = sc.sessions
		sr.WebAuthnConfig = sc.App.GetWebAuthnConfiguration()
	}

	sid, err := sc.App.AuthenticationProvider().CreateSession(ctx, sr)
	if err != nil {
		jsonAPIError(c, http.StatusUnauthorized, err)
		return
	}

	if err := saveSessionID(session, sid); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, errors.Join(errors.New("unable to save session id"), err))
		return
	}

	jsonAPIResponse(c, Session{Authenticated: true}, "session")
}

// AuthenticateBySession authenticates the request by the session cookie.
//
// Implements authMethod
func AuthenticateBySession(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	session := sessions.Default(c)
	sessionID, ok := session.Get(SessionIDKey).(string)
	if !ok {
		return auth.ErrorAuthFailed
	}

	user, err := authr.AuthorizedUserWithSession(ctx, sessionID)
	if err != nil {
		return err
	}

	c.Set(SessionUserKey, &user)

	return nil
}
