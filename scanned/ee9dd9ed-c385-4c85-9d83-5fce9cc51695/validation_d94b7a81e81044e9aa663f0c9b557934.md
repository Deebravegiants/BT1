### Title
Symlink traversal in local file fetcher allows escaping the configured basePath sandbox - (File: `core/services/workflows/syncer/v2/fetcher.go`)

### Summary
The local `file://` fetcher used by the workflow artifact syncer (`newFileFetcher`) enforces a "must stay within basePath" restriction using only string-prefix checks on a cleaned path, without resolving symlinks. This mirrors the n8n `Read/Write File` symlink traversal bug class (CWE-59/CWE-61): a path can textually satisfy the sandbox check while a symlink component silently redirects the actual open target outside the intended directory.

### Finding Description
`newFileFetcher` builds `fullPath` from the caller-supplied `req.URL`, using `filepath.Clean` and `filepath.Join(basePath, fullPath)`, then verifies containment with a plain string prefix comparison: [1](#0-0) 

It then calls `os.ReadFile(fullPath)` directly: [2](#0-1) 

This check only validates the lexical path string — it never calls `filepath.EvalSymlinks` (or equivalently opens with `O_NOFOLLOW`) to confirm the resolved, real path also stays under `basePath`. If any path component under `basePath` is (or later becomes) a symlink pointing outside of it, `fullPath` will still start with the `basePath` prefix and pass the check, but `os.ReadFile` will follow the symlink and read the linked target file — exactly the pattern described in the n8n advisory (GHSA-ggjm-f3g4-rwmm / CVE-2025-57749), where symlink presence bypasses a textual directory restriction.

`fullPath` is derived from `req.URL`, which is populated from workflow-supplied `binaryURL`/`configURL` values passed through `Store.FetchWorkflowArtifacts`: [3](#0-2) [4](#0-3) 

This confirms the URL value reaching the fetcher's containment check originates from workflow registry/spec data rather than from a fully trusted, static, operator-only source, which is the intended "unprivileged-actor" surface in scope.

### Impact Explanation
If a symlink exists (or can be created) anywhere inside the fetcher's `basePath` tree — e.g., a directory shared with another writable process/component, a leftover from artifact extraction, or a race during artifact staging — a crafted `binaryURL`/`configURL` value that lexically resolves under `basePath` can cause the fetcher to read and return the contents of an arbitrary file reachable via that symlink target. Because `Fetch`/`FetchWorkflowArtifacts` treats the returned bytes as the workflow binary/config (base64-decoded and eventually executed as WASM or used as workflow config), this is not merely an information leak — it can also result in unintended file disclosure of files outside the intended workflow-artifact directory (`C:H` per the referenced advisory's CVSS vector).

### Likelihood Explanation
Exploitability strictly depends on an attacker's ability to place a symlink inside `basePath` (or on a pre-existing symlink there). Nothing in this fetcher path itself creates such a symlink — this is purely a missing-defense-in-depth issue in the containment check, not a directly attacker-triggerable primitive on its own. Given the tool's read-only, no-terminal constraints, I could not fully verify whether any other component (e.g., artifact extraction/module caching logic) writes into this same `basePath` in a way an unprivileged workflow author could influence to plant a symlink; this would need further investigation in a live session.

### Recommendation
Resolve symlinks before/while performing the containment check — e.g., call `filepath.EvalSymlinks(fullPath)` (falling back gracefully if the file doesn't yet exist, resolving the parent directory instead) and re-verify the resolved path is still prefixed by the resolved, absolute `basePath`. Alternatively, open the file with `os.OpenFile` using `syscall.O_NOFOLLOW` (via `os.O_NOFOLLOW` where available) or use `os.Root`/`os.OpenInRoot` (Go 1.24+) to constrain all file operations to the `basePath` tree at the OS level, rather than relying solely on string-prefix matching of a cleaned path.

### Proof of Concept
1. Suppose `basePath = /var/chainlink/artifacts`.
2. Inside `/var/chainlink/artifacts`, a symlink `escape -> /etc/passwd` exists (planted by any process capable of writing to that directory, e.g., a shared volume, extraction bug elsewhere, or misconfiguration).
3. A workflow spec sets `binaryURL = "file:///var/chainlink/artifacts/escape"`.
4. `newFileFetcher`: `fullPath = filepath.Clean("/var/chainlink/artifacts/escape")` → passes the `strings.HasPrefix(fullPath, basePath+separator)` check because the *lexical* path is inside `basePath`.
5. `os.ReadFile(fullPath)` follows the symlink and returns the contents of `/etc/passwd` instead of the intended artifact, demonstrating the missing-symlink-resolution containment bypass.
