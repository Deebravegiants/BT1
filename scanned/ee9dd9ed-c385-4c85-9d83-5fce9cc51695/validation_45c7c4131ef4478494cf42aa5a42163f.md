### Title
Shared global outbound-request quota in `OutgoingConnectorHandler` can be exhausted by a single unprivileged workflow owner, causing DoS to all other workflows on the node - (File: core/capabilities/webapi/outgoing_connector_handler.go)

### Summary
The `OutgoingConnectorHandler`, which brokers all outbound Gateway traffic for WebAPI Target, Compute Action, and Workflow Syncer capabilities, enforces rate limiting via a two-tier token-bucket scheme: a per-workflow bucket and a single, shared global bucket. Because the global bucket is shared across every workflow running on the node with no per-owner allocation, an unprivileged user who can register multiple workflows can, while staying within their own per-workflow limits, collectively drain the shared global budget and deny outbound Gateway requests for every other tenant's workflow on that node. This mirrors the reported PSM `TimeBasedRateLimiter` bug class: a single actor exhausting a shared window/bucket to lock out all other legitimate users.

### Finding Description
`NewOutgoingConnectorHandler` builds two `ratelimit.RateLimiter` instances from `outgoingRateLimiterConfigDefaults`/`incomingRateLimiterConfigDefaults`, both of which combine an independent per-key bucket with one shared global bucket: [1](#0-0) 

The outgoing (request-sending) path keys the per-sender bucket by `req.WorkflowID`, defaulting to `DefaultWorkflowRPS=5`/`DefaultWorkflowBurst=50`, while the global bucket defaults to `DefaultGlobalRPS=100`/`DefaultGlobalBurst=100`, shared by every workflow on the node: [2](#0-1) [3](#0-2) 

The underlying `RateLimiter.Allow` unconditionally evaluates and consumes tokens from *both* the per-sender and the global limiter on every call: [4](#0-3) 

Because `WorkflowID` is attacker-controlled (any user with permission to register workflows can create an arbitrary number of distinct workflow IDs), an attacker can spread their outbound-request traffic across many workflow IDs, each individually staying under the 5 RPS / 50-burst per-workflow cap, while in aggregate exceeding the shared 100 RPS / 100-burst global cap. Once the global bucket is empty, `globalAllow` is `false` for every subsequent caller regardless of workflow, and the request is rejected: [5](#0-4) 

The same shared-global-bucket pattern also governs inbound Gateway responses via `incomingRateLimiter`, keyed by `body.Sender`: [6](#0-5) 

### Impact Explanation
Once the shared global bucket is exhausted, all other workflows on the node - regardless of owner - are denied WebAPI Target/Compute Action/Workflow Syncer outbound Gateway requests until the bucket refills (`errorOutgoingRatelimitGlobal`/`errorIncomingRatelimitGlobal`). This is a availability/DoS impact affecting every tenant sharing that node, triggered entirely by an unprivileged actor able to register workflows - no special node or operator privileges are required, unlike the excluded "malicious-node/operator-only" categories.

### Likelihood Explanation
Exploitation only requires the ability to create multiple workflows and drive outbound capability calls (WebAPI target fetches or Compute actions) from each, which is a normal, unprivileged user capability in the workflow platform. No cryptographic or authentication bypass is needed - just distributing load across several workflow IDs to stay under each per-workflow cap while breaching the shared global cap.

### Recommendation
Replace the single shared global bucket with per-owner (not just per-workflow) quotas, or size the global bucket so that it cannot be starved by many workflows belonging to a single owner (e.g., aggregate per-owner limiting across all of an owner's workflow IDs, similar to `syncerlimiter`'s `PerOwner`/`Global` scheme). Additionally consider fairness/backpressure (e.g., per-owner fair queuing) rather than a single FIFO global token bucket so one tenant cannot starve others.

### Proof of Concept
1. As an unprivileged user, register N workflows (`workflowID_1 … workflowID_N`), each performing WebAPI Target / Compute Action outbound calls.
2. Drive each workflow's outbound request rate at or below `DefaultWorkflowRPS=5` (staying under the per-workflow limit), but with enough concurrent workflow IDs that aggregate throughput exceeds `DefaultGlobalRPS=100`/burst `100`.
3. Observe that `handleSingleNodeRequest` starts returning `errorOutgoingRatelimitGlobal` for requests from *other, legitimate* workflows (owned by other users) on the same node, even though those workflows never exceeded their own per-workflow quota. [2](#0-1)

```go
func (c *OutgoingConnectorHandler) handleSingleNodeRequest(ctx context.Context, messageID string, req capabilities.Request) (*api.Message, error) {
	lggr := logger.With(c.lggr, "messageID", messageID, "workflowID", req.WorkflowID)
	workflowAllow, globalAllow := c.outgoingRateLimiter.AllowVerbose(req.WorkflowID)
	if !workflowAllow {
		return nil, errors.New(errorOutgoingRatelimitWorkflow)
	}
	if !globalAllow {
		return nil, errors.New(errorOutgoingRatelimitGlobal)
	}
```

```go
func (rl *RateLimiter) Allow(sender string) (senderAllow bool, globalAllow bool) {
	rl.mu.Lock()
	senderLimiter, ok := rl.perSender[sender]
	if !ok {
		senderLimiter = rate.NewLimiter(rate.Limit(rl.config.PerSenderRPS), rl.config.PerSenderBurst)
		rl.perSender[sender] = senderLimiter
	}
	rl.mu.Unlock()

	senderAllow = senderLimiter.Allow()
	globalAllow = rl.global.Allow()
	return senderAllow, globalAllow
}
```
