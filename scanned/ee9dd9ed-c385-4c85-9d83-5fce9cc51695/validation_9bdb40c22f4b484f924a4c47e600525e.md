### Title
External Initiators can trigger job runs even when the `ExternalInitiatorsEnabled` feature flag is disabled - ([File: core/web/auth/auth.go])

### Summary
`AuthenticateExternalInitiator` (the middleware that authenticates the `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers and grants an unprivileged caller the "Run" role) never checks the node's `JobPipeline.ExternalInitiatorsEnabled` configuration flag. Only the initiator-creation endpoint checks this flag. This mirrors the Neutrl `_deposit()` bug pattern: one access-restriction check (creation-time feature gate) is enforced, but a second, equally-required restriction (the same gate at authentication/use time) is silently skipped, letting a previously-created, unprivileged credential keep working after the feature is disabled.

### Finding Description
The feature flag is enforced only in `ExternalInitiatorsController.Create`: [1](#0-0) 

But the authentication path that actually uses external-initiator credentials to trigger job runs, `AuthenticateExternalInitiator`, performs no such check — it only validates the access key/secret against the stored `bridges.ExternalInitiator` record and then grants the caller the `UserRoleRun` role: [2](#0-1) 

`ExternalInitiator` records have no "enabled/disabled" state field at all: [3](#0-2) 

Compare this to the sherlock finding: `_deposit()` checked `SOFT_RESTRICTED_STAKER_ROLE` but omitted `FULL_RESTRICTED_STAKER_ROLE`, letting a fully-blacklisted user keep depositing. Here, the equivalent restriction (`ExternalInitiatorsEnabled`) is checked at one entry point (creation) but omitted at the other entry point (authentication/use), letting an external, unprivileged caller keep triggering job runs via a previously-issued credential even after an operator disables the feature.

### Impact Explanation
An operator who disables `JobPipeline.ExternalInitiatorsEnabled` (e.g., in response to a security incident, to停止 remote job triggering, or as a compliance/config control) expects that external initiators can no longer submit run requests. Because `AuthenticateExternalInitiator` doesn't re-check the flag, any previously created initiator credential remains fully functional for authenticating requests and triggering webhook job runs through `/v2/jobs/:jobID/runs` and related run-submission endpoints, defeating the operator's intended control. This is a request-impersonation/authorization-bypass issue reachable by an unprivileged external client holding a valid (but supposedly deactivated-by-policy) EI credential, on the node's internet-facing HTTP API.

### Likelihood Explanation
Likelihood is moderate: it requires (1) an external initiator to have been created at some point (a legitimate, supported feature) and (2) the operator later toggling `ExternalInitiatorsEnabled` to `false` expecting that this immediately revokes external-initiator-triggered runs. Since there is no code path that revokes or checks state at authentication time, the bypass is deterministic and requires no attacker sophistication — merely continuing to use previously-obtained valid credentials.

### Recommendation
Add the same `ExternalInitiatorsEnabled` check inside `AuthenticateExternalInitiator` (or in the routes/middleware chain that wraps it) so that authentication fails when the feature is disabled, mirroring the fix pattern of adding the missing restriction check symmetrically wherever the credential/session can be used, not just where it is created:
```go
func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
    if !cfg.JobPipeline().ExternalInitiatorsEnabled() {
        return auth.ErrorAuthFailed
    }
    ...
}
```

### Proof of Concept
1. Enable `JobPipeline.ExternalInitiatorsEnabled = true`, create an external initiator via `POST /v2/external_initiators`, capturing `AccessKey`/`Secret` (`core/web/external_initiators_controller.go:62-70`).
2. Operator sets `JobPipeline.ExternalInitiatorsEnabled = false` and restarts/reloads the node config, believing external-initiator-triggered runs are now blocked.
3. Attacker (or the still-valid EI) sends a request to a webhook job run endpoint with the captured `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` headers.
4. `AuthenticateExternalInitiator` (`core/web/auth/auth.go:119-149`) validates the credential successfully (no flag check) and sets `SessionUserKey` to a `UserRoleRun` user, allowing the job run to be triggered despite the feature being disabled.

Note: I was not able to fully verify, within tool budget, every router path wiring `AuthenticateExternalInitiator` to the job-run trigger endpoint (`core/web/router.go` was only partially read before the iteration limit); this should be confirmed by a full read of `core/web/router.go` and the job-runs controller to ensure the exact route configuration during a deeper investigation.

```go
// AuthenticateExternalInitiator authenticates an external initiator request.

// Implements authMethod
func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}
```
