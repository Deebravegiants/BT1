Target: `VersionedNonceBuilder.decodeNonce` (packages/intents-sdk/src/intents/expirable-nonce.ts) which reads `bytes[4]` into `version` and passes it straight into `new VersionedNonce(version, value)` without validating `version === LATEST_VERSION`. Attacker input: a caller-supplied nonce string passed to `IntentPayloadBuilder.setNonce(nonce)` where the base64-decoded bytes have `VERSIONED_MAGIC_PREFIX` intact but `bytes[4]` set to e.g. 255. Preconditions: nonce length must decode to exactly 32 bytes to pass the length check in `decodeNonce`. Call sequence: build payload with `IntentPayloadBuilder.setNonce(customNonce).build()`, sign via `IIntentSigner.signIntent`, submit through relay to intents.near. Equality that breaks: SINGLE EXECUTION / nonce binding — `decodeNonce` must map exactly one version byte to exactly one interpretation of the 27-byte body, but no check enforces `version === LATEST_VERSION`, so a caller can craft a nonce whose fields (salt/deadline/random split) are reinterpreted inconsistently between SDK-side decode and any future/legacy contract-side decode, breaking the (nonce, verifying_contract) binding to exactly one execution semantics. Impact: High — an intent believed dead by the SDK (decoded with unknown version) may still be accepted on-chain under a different interpretation, or vice versa, causing the caller to believe a payload will not execute when it can. Proof idea: vitest test constructing bytes with `VERSIONED_MAGIC_PREFIX`, a bogus version byte, and a valid 27-byte borsh body; call `decodeNonce` and assert it returns a `VersionedNonce` object instead of throwing, proving no version guard exists.
