### Title
ERC20Transactor credits full nominal amount to XCM holding without verifying actual balance change on the checking account, enabling fee-on-transfer / deflationary ERC20 tokens to mint phantom XCM asset credit - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` calls an arbitrary ERC20 contract's `transfer()` to move `amount` from a user to the `TransfersCheckingAccount`, and treats the operation as fully successful — crediting `amount` into the XCM `AssetsInHolding` register — based solely on the boolean return value of `transfer()`, never checking the actual balance delta received by the checking account. [1](#0-0) 

### Finding Description
This mirrors the Burve/Sherlock H-1 root cause: the protocol assumes the nominal transferred amount equals the amount actually received by the destination, when the underlying asset can silently take a cut during transfer.

In Burve, `ValueFacet.addValue` transfers `realNeeded` tokens into an ERC4626 vault and credits the user with `value` worth of shares, without accounting for the vault's deposit fee, so fewer real assets end up backing the credited value.

`ERC20Transactor::withdraw_asset_with_surplus` has the same shape: it invokes `IERC20::transferCall{ to: checking_address, value: amount }` on an arbitrary contract selected via `Matcher::matches_fungibles` (an `AccountKey20`-keyed asset id, i.e. any deployed `pallet-revive` contract implementing the ERC20 ABI can be registered/used as an XCM asset kind) and only inspects `IERC20::transferCall::abi_decode_returns_validate` for `true`/`false`: [2](#0-1) 

If that ERC20 contract implements fee-on-transfer / deflationary / rebasing semantics (a legal ERC20 pattern that still returns `true` from `transfer()` while delivering less than `value` to the recipient), the `TransfersCheckingAccount` actually receives `amount - fee`, but the transactor still mints `Erc20Credit(amount)` — the full nominal amount — into the XCM holding register: [3](#0-2) 

This phantom credit is fungible within the XCM executor exactly like a real asset (it can be `DepositAsset`'d to a beneficiary, used for reserve transfers, etc.), while the checking account backing it is short by the fee amount. Repeating this process drains the real/accounted ratio: the checking account's ERC20 balance becomes less than the sum of all outstanding XCM-registered claims against it.

The symmetric `deposit_asset_with_surplus` path has the analogous problem in reverse (transferring from checking account to beneficiary), compounding the insolvency, since it also only checks the boolean return value rather than the beneficiary's realized balance change: [4](#0-3) 

The transactor is wired into Asset Hub Westend's `AssetTransactors` tuple, making it a live, reachable XCM asset backend: [5](#0-4) 

### Impact Explanation
Because `pallet-revive` allows permissionless contract deployment, any unprivileged user can deploy a custom ERC20 contract with fee-on-transfer logic and use it as an XCM asset (identified by its contract address via `AccountKey20`). Every `withdraw_asset` call against such a token mints more XCM-accounted value than actually lands in the checking account. This can be leveraged to:
- Repeatedly manufacture "extra" asset credit relative to what the checking account actually holds, and move/deposit that excess elsewhere (e.g., to a different beneficiary or cross-chain via reserve transfer), effectively creating value out of thin air relative to the real ERC20 reserve.
- Eventually cause the checking account's real balance to be insufficient to honor legitimate `deposit_asset` calls for that token, causing `ERC20 contract transfer failed` / reverts and denial-of-service or fund lock-up for other, honest holders of the same asset — the same "last users suffer" pattern as the original report.

### Likelihood Explanation
Likelihood is high for a determined attacker: no privileged role is needed. The attacker (1) deploys a fee-on-transfer ERC20 contract via `pallet-revive`, (2) references it as an `AccountKey20` XCM asset in a `WithdrawAsset`/`DepositAsset` sequence, and (3) exploits the mismatch. The only precondition is registering/using a self-controlled malicious ERC20 as the asset kind — entirely within an unprivileged user's control, unlike the disqualifying "trusted-role compromise" or "mocked path" scenarios.

### Recommendation
Do not trust the ERC20 `transfer()` boolean return value alone. In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read the checking/beneficiary account's ERC20 balance immediately before and after the `bare_call`, and credit/rely on the *actual observed delta* rather than the requested nominal `amount`. If the delta is less than requested, either fail the operation (safest) or credit only the actually-received amount into `AssetsInHolding`.

### Proof of Concept
1. Deploy a malicious `EvilERC20` contract via `pallet-revive` implementing `IERC20`, where `transfer()` deducts e.g. 5% and burns/redirects it, but still returns `true`.
2. Register/reference `EvilERC20`'s address as an `AccountKey20` XCM asset (matched by `assets_common::ERC20Matcher`).
3. Submit an XCM program with `WithdrawAsset { EvilERC20, amount: 1000 }` from the attacker's own account followed by `DepositAsset` to a second attacker-controlled account (or a cross-chain reserve transfer).
4. Observe: `ERC20Transactor::withdraw_asset_with_surplus` credits `Erc20Credit(1000)` into holding (per line 200 of `erc20_transactor.rs`), even though `TransfersCheckingAccount`'s real `EvilERC20` balance only increased by 950.
5. Repeat; the checking account's actual `EvilERC20` balance falls further behind the aggregate amount "logically" available to depositors of that asset kind, eventually causing `deposit_asset_with_surplus` calls for other, honest users to fail (`ERC20 contract transfer failed`) since the checking account cannot cover the promised amount — demonstrating both the phantom-credit accounting break and its downstream DoS/loss impact.
