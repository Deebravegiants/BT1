### Title
Truncated division in `reward_per_token` causes permanent loss of staking rewards - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet-asset-rewards`'s reward accrual formula performs a single integer division scaled only by a small constant (`4096`), the same reward-per-token-per-interval accounting pattern flagged as vulnerable in the external Locke.sol report. When `reward_rate_per_block * elapsed_blocks * 4096 < total_tokens_staked`, the per-interval reward increment truncates to zero and is permanently lost rather than deferred, because `reward_per_token_stored` only accumulates the already-rounded increment for each interval.

### Finding Description
`reward_per_token` computes the increment added to `reward_per_token_stored` as: [1](#0-0) 
This is `reward_rate_per_block * rewardable_blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked`, where `PRECISION_SCALING_FACTOR` is a fixed `u16` value of `4096`: [2](#0-1) 
Because `reward_per_token_stored` is a running cumulative value that only ever adds the result of this single division for each interval between updates, any interval whose numerator (`reward_rate_per_block * elapsed_blocks * 4096`) is smaller than `total_tokens_staked` contributes exactly `0` to `reward_per_token_stored`, permanently losing that interval's rewards for all stakers.

This is invoked on every `stake` and `unstake` call — both callable by any signed account with no minimum-interval throttling: [3](#0-2) [4](#0-3) 
So an attacker can force `rewardable_blocks_elapsed = 1` on (almost) every block by repeatedly staking/unstaking a trivial amount, converting what would otherwise be one large, non-truncating computation over many blocks into many single-block computations that each round down to zero — exactly the "reward updated too frequently" failure mode described in the external report.

### Impact Explanation
When triggered, all rewards that should have accrued to `total_tokens_staked` during the griefed blocks are permanently lost (not merely delayed) because `reward_per_token_stored` has already "consumed" that interval with a zero contribution; there is no remainder carry-over mechanism. Legitimate stakers in the pool receive less than the reward rate the admin configured, and the surplus reward tokens become stranded in the pool account (recoverable only by the admin via `cleanup_pool`, which requires the pool to be fully empty of stakers).

### Likelihood Explanation
Likelihood is highest exactly when `total_tokens_staked` is large relative to `reward_rate_per_block * 4096` — e.g. a popular pool with many staked tokens (assets can have many decimals) paired with a modest reward rate (reward asset may have few decimals, e.g. 6). Triggering repeated `stake`/`unstake` calls requires no special privilege, only a signed account and gas/fee budget, and `unstake` even allows a caller to act on any `staker` after pool expiry, but the griefing itself only needs the attacker's own stake/unstake cycle (fees are the only cost, and dust amounts can be used). Given `PRECISION_SCALING_FACTOR` is a fixed, small constant (4096, i.e. ~12 bits of extra precision) rather than a per-pool configurable or large (e.g. 1e18-like) value, realistic asset/rate combinations across the target chain's supported assets can plausibly hit the zero-rounding condition.

### Recommendation
- Increase `PRECISION_SCALING_FACTOR` substantially (e.g. to a value proportional to `T::Balance`'s bit width, akin to `1e18` fixed-point scaling used elsewhere in the runtime) to shrink the rounding error, and/or
- Track and carry over the fractional remainder from each `reward_per_token` computation across updates (e.g. store remainder alongside `reward_per_token_stored`) so that no reward is discarded, only deferred, and/or
- Impose a minimum interval between reward-affecting operations per staker, or batch reward accrual independent of `stake`/`unstake` call frequency.

### Proof of Concept
1. Admin creates a pool with `reward_rate_per_block = R` and stakers eventually bring `total_tokens_staked = S` such that `R * 4096 < S`.
2. Attacker calls `stake(pool_id, 1)` then `unstake(pool_id, 1, None)` every block (or every few blocks), each time forcing `rewardable_blocks_elapsed = 1` (or small) in `reward_per_token`.
3. Each call computes `R * elapsed * 4096 / S = 0` (integer division), so `reward_per_token_stored` never increases across these blocks despite `R` tokens/block being nominally due to the pool.
4. Over many such griefed blocks, the cumulative reward paid out to legitimate stakers via `harvest_rewards` is measurably less than `R * total_blocks_elapsed`, with the shortfall left stranded in the pool's reward account, unrecoverable by stakers. [5](#0-4)

		pub fn unstake(
			origin: OriginFor<T>,
			pool_id: PoolId,
			amount: T::Balance,
			staker: Option<T::AccountId>,
		) -> DispatchResult {
			let caller = ensure_signed(origin)?;
			let staker = staker.unwrap_or(caller.clone());

			// Always start by updating the pool rewards.
			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			let now = T::BlockNumberProvider::current_block_number();
			ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin);

			let staker_info = PoolStakers::<T>::get(pool_id, &staker).unwrap_or_default();
			let (mut pool_info, mut staker_info) =
				Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

			// Check the staker has enough staked tokens.
			ensure!(staker_info.amount >= amount, Error::<T>::NotEnoughTokens);

			// Unfreeze staker assets.
			T::AssetsFreezer::decrease_frozen(
				pool_info.staked_asset_id.clone(),
				&FreezeReason::Staked.into(),
				&staker,
				amount,
			)?;

			// Update Pools.
			pool_info.total_tokens_staked.ensure_sub_assign(amount)?;
			Pools::<T>::insert(pool_id, pool_info);

			// Update PoolStakers.
			staker_info.amount.ensure_sub_assign(amount)?;

			if staker_info.amount.is_zero() && staker_info.rewards.is_zero() {
				PoolStakers::<T>::remove(&pool_id, &staker);
			} else {
				PoolStakers::<T>::insert(&pool_id, &staker, staker_info);
			}

			// Emit event.
			Self::deposit_event(Event::Unstaked { caller, staker, pool_id, amount });

			Ok(())
		}

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}

		/// Derives the amount of rewards earned by a staker.
		///
		/// This is a helper function for `update_pool_rewards` and should not be called directly.

			staker_info: &PoolStakerInfo<T::Balance>,
			reward_per_token: &T::Balance,
		) -> Result<T::Balance, DispatchError> {
			Ok(staker_info
				.amount
				.ensure_mul(reward_per_token.ensure_sub(staker_info.reward_per_token_paid)?)?
				.ensure_div(PRECISION_SCALING_FACTOR.into())?
				.ensure_add(staker_info.rewards)?)
		}
