### Title
Front-runnable, user-chosen `AssetId` in `pallet-assets::create` enables permanent griefing of asset creation - (File: `substrate/frame/assets/src/lib.rs`)

### Summary
The Folks-Finance report describes a griefing DoS: a user must supply an attacker-observable, arbitrary identifier (`accountId`) when creating an on-chain resource, and the create function unconditionally reverts if that identifier is already taken. An attacker can watch the pending transaction and front-run it with the identical identifier, permanently blocking the victim from ever using that identifier. The same *pattern* — user-supplied unique identifier + hard revert on collision + no fallback allocation — exists in `pallet-assets`.

### Finding Description
`Pallet::create` in `substrate/frame/assets/src/lib.rs` takes an `id: T::AssetIdParameter` chosen by the caller: [1](#0-0) 

```
pub fn create(
    origin: OriginFor<T>,
    id: T::AssetIdParameter,
    admin: AccountIdLookupOf<T>,
    min_balance: T::Balance,
) -> DispatchResult {
    let id: T::AssetId = id.into();
    let owner = T::CreateOrigin::ensure_origin(origin, &id)?;
    let admin = T::Lookup::lookup(admin)?;

    ensure!(!Asset::<T, I>::contains_key(&id), Error::<T, I>::InUse);
    ...
    if let Some(next_id) = T::AssetIdAllocator::next() {
        ensure!(id == next_id, Error::<T, I>::BadAssetId);
    }
```

The collision check `ensure!(!Asset::<T, I>::contains_key(&id), Error::<T, I>::InUse)` mirrors exactly the vulnerable line in the report (`AccountManager.createAccount`'s `isAccountCreated` check). Whether the id can be *targeted* by an attacker depends entirely on `Config::AssetIdAllocator`:

- When `AssetIdAllocator = ()` (the "no allocation policy" implementation), `next()` always returns `None` [2](#0-1) , so the `ensure!(id == next_id, …)` guard is skipped entirely and the caller may pick **any** unused id. This is functionally identical to `SpokeCommon.createAccount(accountId, …)` — free choice of a globally unique identifier, with a hard revert (`InUse`/`AccountAlreadyCreated`) on collision.
- Even when `AutoIncAssetId` is configured, the id must equal the current `NextAssetId`, which is public state readable by anyone; an attacker can still race to consume the *next slot* before the intended creator's extrinsic executes, forcing perpetual `BadAssetId` failures for every subsequent legitimate creator until they resubmit.

This is precisely the "user-chooses-identifier, first-to-land wins, loser reverts" class described in the report, now generalized to any pallet consumer configuring `AssetIdAllocator = ()` for an asset-id namespace where callers care about specific ids (e.g. registries mirroring external/bridged asset ids, or ids with semantic meaning to integrators).

### Impact Explanation
An attacker who observes a pending `Assets::create` extrinsic in the transaction pool (or simply predicts a commonly-desired id, e.g. a well-known/foreign asset id) can submit a competing `create` call with the same `id` and a higher tip/priority, landing first. The victim's extrinsic then fails with `Error::<T, I>::InUse`, and the attacker's own throwaway asset now permanently occupies that id (subject only to `AssetDeposit`, which they can reclaim later via `start_destroy`/removal, or simply accept as a cheap griefing cost). This can be repeated indefinitely to deny any particular id to any user — a genuine griefing/DoS with no profit motive required, matching the report's "Griefing" impact category.

### Likelihood Explanation
Likelihood is conditional and not universal:
- It requires a runtime to configure `Config::AssetIdAllocator = ()` for a `pallet-assets` instance that is reachable by ordinary signed users via `T::CreateOrigin` (i.e., permissionless or semi-permissionless asset creation), and for callers to actually care about specific ids rather than accepting any.
- Production chains such as Asset Hub configure `AssetIdAllocator`/`CreateOrigin` per instance (local `Assets`, `ForeignAssets`, `PoolAssets`), and I was not able to fully confirm from the indexed code within the remaining tool budget whether any of these instances are both (a) open to unprivileged signed callers and (b) configured with `AssetIdAllocator = ()` rather than `AutoIncAssetId`/an origin-gated allocator. This is a material open question that determines whether the finding is exploitable on a live, in-scope runtime today, versus being a latent risk only if a runtime is misconfigured.
- Substrate/Cumulus transaction pools and block-authoring (tip-based prioritization, collator-controlled ordering) make front-running feasible in the same way as an Ethereum public mempool, so the mechanics of the attack transfer directly once the configuration precondition is met.

### Recommendation
- For any `pallet-assets` instance (or similar pallet using `AssetIdAllocator`) exposed to permissionless/semi-permissionless signed origins, do not use `AssetIdAllocator = ()`; always enforce `AutoIncAssetId` (or another allocator that removes attacker choice of the exact id) so `create` cannot be targeted at a specific id chosen by the caller.
- Where callers genuinely need a specific id (e.g., mirroring an externally defined asset id), gate `create`/`force_create` behind `ForceOrigin` or another privileged/permissioned origin rather than a public `Signed` origin, consistent with how `force_create` already documents the "arbitrary id" capability as privileged-only.
- Consider adding a per-account reservation/commit-reveal step (analogous to name-service style protections) before allowing arbitrary-id creation from a public origin, if arbitrary ids must remain permissionless.

### Proof of Concept
Given a runtime configuring a `pallet-assets` instance with `type AssetIdAllocator = ();` and `type CreateOrigin = AsEnsureOriginWithArg<EnsureSigned<AccountId>>` (or similarly permissive):

1. Victim (Bob) submits `Assets::create(origin=Bob, id=42, admin=Bob, min_balance=1)`.
2. Attacker (Alice) observes this in the pool and submits `Assets::create(origin=Alice, id=42, admin=Alice, min_balance=1)` with a higher tip, landing in an earlier position in the same or an earlier block.
3. Alice's call succeeds: `Asset::<T, I>::insert(42, …)` (`substrate/frame/assets/src/functions.rs` `do_force_create`-equivalent path via the `create` extrinsic) executes, and the `ensure!(!Asset::<T, I>::contains_key(&id), Error::<T, I>::InUse)` check at [3](#0-2)  now finds `id = 42` occupied.
4. Bob's `create` call is included afterward and reverts with `Error::<T, I>::InUse`, exactly mirroring the reference PoC's `AccountAlreadyCreated`/`InUse` revert pattern. Alice can repeat this for any id Bob (or any user) attempts to claim.

This confirms the root-cause pattern is present in `pallet-assets::create`, though real-world exploitability on any specific shipped runtime (e.g. Asset Hub) depends on that runtime's `AssetIdAllocator`/`CreateOrigin` configuration, which I could not fully verify within the available indexing/tool budget — a Devin session with full repository access would be needed to check the concrete `Config` impls in `cumulus/parachains/runtimes/assets/asset-hub-*/src/lib.rs` to determine live exploitability.
