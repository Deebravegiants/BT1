### Title
`ResourceMeter::charge_deposit`'s exhaustion-triggered `deposit.reset()` discards already-absorbed sibling-frame charges, causing storage-deposit under-collection - (File: substrate/frame/revive/src/metering/mod.rs)

### Summary
`ResourceMeter::charge_deposit` (metering/mod.rs:330-356) resets the *entire* root deposit meter (`self.deposit.reset()`) whenever a single charge pushes `deposit_left()` to `None`, wiping `total_deposit`, `charges`, and `max_charged` for the whole transaction, not just the failing charge. Because this method is called directly on the shared root `TransactionMeter` from `Contracts::transfer`/`do_terminate` (exec.rs:1723-1866) *after* prior call frames have already merged their charges into that same meter via `absorb`/`absorb_all_meters`, an exhaustion at this late point erases previously legitimate, already-recorded deposit charges from earlier frames, causing `execute_postponed_deposits` to under-collect (or fail to refund) storage deposits.

### Finding Description
`RawMeter<T, E, Root>::is_root` is only `true` for the transaction-level meter (`storage.rs:373-380`); nested `FrameMeter`s default to `is_root = false` via `#[derive(DefaultNoBound)]`. `ResourceMeter::charge_deposit` (metering/mod.rs:330-356) is a generic method over `S: State`, so it can be invoked on either a `FrameMeter` or the root `TransactionMeter`. In practice it is invoked directly on the root `TransactionMeter` in `Contracts::transfer` (exec.rs:1729,1763) and `Contracts::do_terminate` (exec.rs:1793,1826-1846) for endowment (ED) transfers, which run *after* the calling contract's frame has already returned and had its charges merged into the transaction meter via `absorb`/`absorb_all_meters` (`storage.rs:278-310`, `metering/mod.rs:261-262`).

Because `absorb` merges a nested frame's `total_deposit` and `charges` Vec directly into the parent meter's own fields (`self.total_deposit = ...saturating_add...`, `self.charges.extend_from_slice(&absorbed.charges)` at `storage.rs:296-309`), by the time a later root-level `charge_deposit` call happens, the parent (root) meter's `charges`/`total_deposit` already contain contributions from all previously-executed sibling/child frames.

If this later root-level charge (e.g., the ED transfer during `SELFDESTRUCT`/`terminate`) causes `deposit_left()` to become `None`, `charge_deposit` calls `self.deposit.reset()` (`storage.rs:255-261`) which unconditionally zeroes `own_contribution`, `total_deposit`, `charges`, and `max_charged` — for the whole root meter, not just the failing charge. This is a plain in-memory Rust struct mutation, **not** a storage write, so it is not rolled back by the surrounding `with_transaction` block in `transfer` (exec.rs:1745-1768) even though that block rolls back the actual balance transfer on `Err`. The `Err(StorageDepositLimitExhausted)` return from `charge_deposit` then propagates from `do_terminate`, whose caller explicitly treats such failures as a soft, swallowed rollback ("we cannot fail here ... we simply roll back the termination so that nothing happened", exec.rs:1851-1853) — i.e., the failure of the terminate/ED-transfer does not necessarily abort the whole extrinsic.

Consequently the transaction can continue to `TransactionMeter::execute_postponed_deposits` (`storage.rs:385-444`) with an already-wiped `charges` Vec/`total_deposit`, meaning none of the storage deposits legitimately accrued by earlier, successfully-absorbed frames get actually charged to (or refunded from) the origin.

### Impact Explanation
This causes storage-deposit accounting corruption: an unprivileged contract caller can cause storage deposits that should have been collected from (or refunded to) the origin for prior, already-committed nested calls to silently vanish, because the root meter's bookkeeping (`total_deposit`, `charges`) is wiped by a later, unrelated exhaustion event. This is a concrete violation of the invariant that "storage deposit accounting must stay consistent" and directly leads to under-collection of storage rent (origin pays less than the storage it actually occupies) or lost refunds.

### Likelihood Explanation
Reachable purely through normal, unprivileged `pallet-revive` `call`/`eth_transact` extrinsics: an attacker deploys/controls a contract that performs several nested calls accumulating storage charges close to the transaction's deposit limit, then triggers `SELFDESTRUCT` with a balance transfer to a fresh beneficiary account whose ED charge (`Contracts::transfer` -> `meter.charge_deposit`) tips the root meter's `deposit_left()` to `None`. This requires only carefully sized storage writes and a `SELFDESTRUCT` call within one gas-limited transaction — no privileged origin, no governance, and it is fully reproducible/deterministic given fixed deposit and weight limits.

### Recommendation
`ResourceMeter::charge_deposit`'s exhaustion branch should not call `self.deposit.reset()` on the whole meter. Instead it should either: (a) only roll back the specific charge that was just applied (undo the `record_charge` delta) rather than clearing `charges`/`total_deposit` for the entire meter, or (b) avoid mutating the root meter's already-absorbed accounting at all when the failing charge is a one-off ED/transfer charge unrelated to child-frame contributions — e.g., perform this deposit_left check before merging the charge into the shared meter state, using a local/uncommitted delta that is discarded on failure without touching previously absorbed data.

### Proof of Concept
Rust integration test in `substrate/frame/revive/src/tests` (or `metering/tests.rs`) plan:
1. Build a `TransactionMeter` with a fixed `deposit_limit` close to the sum of two planned charges.
2. Simulate `frame1`: create a nested `FrameMeter`, call `record_contract_storage_changes`/`charge_contract_deposit_and_transfer` to accrue a charge just under the limit, then `absorb_all_meters` into the root meter (mirroring normal call-stack unwinding) and assert `root.deposit_consumed()` and root's internal `charges` reflect frame1's charge.
3. Directly call `root.charge_deposit(&StorageDeposit::Charge(extra))` with an `extra` amount that pushes `deposit_left()` to `None` (mirroring the ED-transfer path in `do_terminate`/`transfer`), and assert it returns `Err(StorageDepositLimitExhausted)`.
4. Assert (this should fail, proving the bug) that `root.deposit_consumed()` / the pending `charges` still contain frame1's previously-absorbed charge instead of being reset to zero.
5. Call `root.execute_postponed_deposits(&origin, &exec_config)` and assert the returned total equals frame1's original `record_charge` amount — currently it will return zero/less, proving under-collection.
