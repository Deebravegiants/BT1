### Title
Unfair reward distribution due to MEV front-running of signed `report_equivocation` extrinsics - (File: `substrate/frame/grandpa/src/lib.rs`, `substrate/frame/babe/src/lib.rs`, `substrate/frame/beefy/src/lib.rs`)

### Summary
The signed, permissionless `report_equivocation` (and BEEFY's `report_double_voting`/`report_fork_voting`/`report_future_block_voting`) extrinsics pay the transaction's signer a slashing-derived reward for being the first to submit a valid equivocation proof. Because the equivocation proof and key-ownership proof are supplied as public call arguments in a signed, network-propagated transaction, any observer of the transaction pool can copy the data, resubmit it under their own account with a higher tip/priority, and steal the reward intended for the original detector — the same "first come, first served" MEV pattern described in the external Ajna report.

### Finding Description
`report_equivocation` in GRANDPA [1](#0-0)  and BABE [2](#0-1) , as well as `report_double_voting`/`report_fork_voting`/`report_future_block_voting` in BEEFY [3](#0-2) , accept `ensure_signed(origin)` and pass the caller as `reporter` into `process_evidence`, which reports the offence and ultimately pays the reporter a share of the slashed stake via `pay_reporters` [4](#0-3) . The fee for a successful call is waived (`Pays::No`), which is itself an incentive to submit the tx.

Unlike the unsigned variant, which is restricted to `TransactionSource::Local | TransactionSource::InBlock` and never propagated over the network (`.propagate(false)`), the signed variant has no such restriction and is broadcast like any ordinary transaction [5](#0-4) . Since the entire `equivocation_proof` and `key_owner_proof` are included as plaintext call arguments, once the honest reporter's signed transaction enters the public mempool, any bot can extract this data, wrap it in its own signed call (with a higher tip to win block-inclusion priority), and claim the `reporter` slot and associated reward instead of the original submitter. The duplicate-check (`is_known_offence`) only prevents the same offence being rewarded twice — it does not protect the original submitter's claim to the reward once the raw proof is visible on the wire.

### Impact Explanation
The protocol's core security property (slashing the equivocator) is unaffected — the offender is always slashed regardless of who claims the reward. The impact is limited to unfair reward reallocation: the party that expended effort to detect and construct/verify the equivocation proof can be systematically front-run by generic "proof-copying" bots, and never actually receives the intended incentive. This mirrors exactly the "unfair distribution of rewards due to MEV" class described in the external report, applied here to consensus equivocation-reporting incentives instead of DeFi bucket-reward incentives.

### Likelihood Explanation
Likelihood is moderate: equivocation events are rare in practice, and the primary/expected reporting path is the unsigned, non-propagated variant driven by validators' own off-chain workers [6](#0-5) , which is not exploitable this way. The signed path exists as a fallback/manual reporting mechanism for arbitrary accounts, and is only exploitable when a non-validator user manually submits a signed report through the public mempool rather than relying on the built-in unsigned flow.

### Recommendation
For the signed reporting path, consider a commit-reveal scheme (submit a hash/commitment of the proof first, then reveal), or bind reward eligibility to the account that can prove exclusive prior knowledge (e.g., via a locally-only submission channel similar to the unsigned variant), or simply document/deprecate the signed variant in favor of the unsigned, non-propagated flow to avoid incentivizing manual public submission.

### Proof of Concept
1. A user (Alice) detects a GRANDPA/BABE/BEEFY equivocation and constructs a valid `equivocation_proof` + `key_owner_proof`.
2. Alice submits a signed `report_equivocation` extrinsic; it propagates through the p2p transaction pool since no `propagate(false)`/local-only restriction applies to the signed call.
3. A bot monitoring the mempool decodes Alice's call arguments (public plaintext), repackages them into its own signed `report_equivocation` call with a higher tip.
4. The bot's transaction is prioritized and included first; `is_known_offence` marks the offence as reported, `reporter` is set to the bot's account, and `pay_reporters` deposits the reward to the bot instead of Alice [7](#0-6) .
5. Alice's subsequent (now duplicate) transaction fails with `Error::<T>::DuplicateOffenceReport`, and she loses both the reward and the transaction fee she would have otherwise had waived.

fn pay_reporters<T: Config>(
	reward_payout: BalanceOf<T>,
	slashed_imbalance: NegativeImbalanceOf<T>,
	reporters: &[T::AccountId],
) {
	if reward_payout.is_zero() || reporters.is_empty() {
		// nobody to pay out to or nothing to pay;
		// just treat the whole value as slashed.
		T::Slash::on_unbalanced(slashed_imbalance);
		return;
	}

	// take rewards out of the slashed imbalance.
	let reward_payout = reward_payout.min(slashed_imbalance.peek());
	let (mut reward_payout, mut value_slashed) = slashed_imbalance.split(reward_payout);

	let per_reporter = reward_payout.peek() / (reporters.len() as u32).into();
	for reporter in reporters {
		let (reporter_reward, rest) = reward_payout.split(per_reporter);
		reward_payout = rest;

		// this cancels out the reporter reward imbalance internally, leading
		// to no change in total issuance.
		asset::deposit_slashed::<T>(reporter, reporter_reward);
	}
