### Title
Delivery fee for UMP is computed on the pre-`wrap_version` message, allowing under-payment when version conversion inflates the encoded size - (File: cumulus/primitives/utility/src/lib.rs)

### Summary
`ParentAsUmp::validate` (and the structurally identical `ChildParachainRouter::validate` in `polkadot/runtime/common/src/xcm_sender.rs`) computes the delivery price via `P::price_for_delivery((), &xcm)` **before** calling `W::wrap_version(&d, xcm)`, but the bytes that are actually checked for size/decodability and queued/delivered are the *post*-wrap `versioned_xcm.encode()`. If converting the message to the destination's supported XCM version increases its encoded size, the fee is computed on the smaller pre-conversion size while the relay chain (or DMP queue) bears the cost of the larger, post-conversion message.

### Finding Description
In `cumulus/primitives/utility/src/lib.rs` lines 71-95: [1](#0-0) 

the sequence is:
1. `let xcm = msg.take()...` — the message, already in the pallet's internal latest `Xcm<()>` representation (built by `pallet_xcm::send` after `VersionedXcm::try_into()` — see `polkadot/xcm/pallet-xcm/src/lib.rs:405-451` where the caller's arbitrary `VersionedXcm` argument is converted into the latest `Xcm<()>` before being handed to the router).
2. `let price = P::price_for_delivery((), &xcm);` — price computed on this internal-latest-version message.
3. `let versioned_xcm = W::wrap_version(&d, xcm)...` — the message is then re-encoded into whatever version the destination (`Parent`) is recorded as supporting (`SupportedVersion` storage, defaulting to `SafeXcmVersion`) via `pallet_xcm`'s `WrapVersion` impl at `polkadot/xcm/pallet-xcm/src/lib.rs:3826-3844`, which calls `xcm.into().into_version(v.min(XCM_VERSION))`.
4. `let data = versioned_xcm.encode();` — this is the actual byte blob checked by `T::can_send_upward_message(&data)` and later delivered via `T::send_upward_message(data)` in `deliver`.

`ExponentialPrice::price_for_delivery` (`polkadot/runtime/common/src/xcm_sender.rs:83-95`) is defined as `F * (B + encoded_msg_len * M)` where `encoded_msg_len = msg.encoded_size()` — i.e., the size of the pre-wrap `Xcm<()>`, not the size of the bytes that will be queued/delivered. The doc comment states the fee is meant to be for "each and every byte of the message after encoding it," but the implementation encodes/prices the wrong (pre-version-conversion) artifact.

Because `into_version` conversions between XCM versions are not guaranteed to be size-preserving (different versions can encode instructions, `Location`/`Junctions`, or asset representations with different byte layouts, and downgrade conversions can require splitting semantics into different structures), the post-wrap `versioned_xcm.encode().len()` can exceed the pre-wrap `xcm.encoded_size()`. No re-pricing or size-delta check occurs after `wrap_version`; only `check_is_decodable()` and `can_send_upward_message` enforce decode-depth and hard size caps (the guard added for message-size DoS per `prdoc/stable2506/pr_8409.prdoc`), not fee correctness. Thus an unprivileged caller of `pallet_xcm::send`/`execute` targeting `Parent` can pay a fee sized for the smaller pre-wrap message while the network absorbs the larger post-wrap message.

The identical pattern also exists in `ChildParachainRouter::validate` (`polkadot/runtime/common/src/xcm_sender.rs:107-131`) and `XcmpQueue::validate` (`cumulus/pallets/xcmp-queue/src/lib.rs:1242-1269`), confirming this is a systemic ordering issue in the `SendXcm` implementations rather than an isolated typo.

### Impact Explanation
Underpriced UMP delivery: the attacker pays a byte-fee based on a smaller message than what is actually placed in the upward message queue and processed by the relay chain, producing a fee-accounting asymmetry between charged and actual delivery cost (`ExponentialPrice`'s stated purpose of charging per-byte-after-encoding is violated). This is scoped strictly to fee/weight accounting mismatch for UMP delivery pricing, not asset theft or duplication.

### Likelihood Explanation
Reachable by any signed account permitted to call `pallet_xcm::send` or `execute` with `dest = Parent` — no special privilege required. Exploitability depends on the magnitude of size growth achievable through legitimate `into_version` conversions between the internal latest version and the relay's `SupportedVersion`/`SafeXcmVersion`; I could not conclusively quantify how large a growth is achievable for a given `TryFrom`/`into_version` implementation without deeper inspection of every version's `TryFrom` instruction-conversion code (not fully available in the indexed context), so the *existence* of the ordering flaw is confirmed, but the *magnitude* of exploitable under-payment is not fully verified here.

### Recommendation
Compute (or re-validate) `price_for_delivery` using the final `versioned_xcm.encode()` bytes (post-`wrap_version`) rather than the pre-wrap `Xcm<()>`, in `ParentAsUmp::validate`, `ChildParachainRouter::validate`, and `XcmpQueue::validate`. At minimum, price should be computed after `wrap_version` and before/alongside the `check_is_decodable`/size checks, ensuring `M::get()` is multiplied against `data.len()` (the actually-queued byte length) instead of `msg.encoded_size()`.
