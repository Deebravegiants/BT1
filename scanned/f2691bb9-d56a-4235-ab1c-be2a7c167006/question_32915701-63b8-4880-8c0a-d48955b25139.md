Target: computeSignedTonConnectHash / computeTonConnectHash address handling via parseTonAddress. Attacker input: payload.address is a TON address string in one valid textual form (e.g. raw '0:hex'), while the actual signed TonConnect payload displayed to / approved by the wallet used a different but 'equal' friendly-form address; or conversely an attacker supplies a payload.address that tryParseTonAddress accepts but that does not correspond to the wallet key that produced signature. Preconditions: computeTonConnectHash trusts payload.address purely as data to hash (workchainId + 32-byte address bytes baked into the SHA-256 preimage) with no validation that address is owned by the key behind signature — ownership is asserted entirely by whichever TON wallet extension produced the signature externally, outside this file. Call sequence: caller builds a ton_connect MultiPayload with address = victim's TON account string and obtains any 64-byte ed25519 signature (even from an unrelated key) over the resulting hash; computeSignedTonConnectHash(signedPayload) recomputes the same hash deterministically from address, domain, timestamp, and payload text, without ever checking that the ed25519 signature verifies against a public key controlled by that address. Equality that breaks: signer_id (the TON account named by address) == intents user id of the key that produced signature — this file only computes a hash for later verification elsewhere, but never itself enforces or exposes that check, so a caller relying on computeSignedTonConnectHash's success as proof of authorization is misled. Scoped impact: High — the hash-computation function's success/failure carries no signal about signer authenticity, and any SDK code path treating a successfully recomputed hash as sufficient to accept the payload (without separately verifying the ed25519 signature against address's public key) would authorize an intent signed_id mismatched to the actual signer. Whose funds: the TON account named by payload.address. Proof idea: vitest test calling computeTonConnectHash and computeSignedTonConnectHash with the same TON Connect payload object using an address for account A but a signature field (attached alongside, in the broader MultiPayload) produced by unrelated key B, asserting computeSignedTonConnectHash returns identically regardless of which key produced the accompanying signature, i.e. the hash equality it guarantees says nothing about signer identity equality.
