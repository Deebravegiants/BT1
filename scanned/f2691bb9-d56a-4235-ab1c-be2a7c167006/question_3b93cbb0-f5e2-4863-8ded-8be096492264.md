Target: IntentSignerViem.signIntent fallback via authHandleToIntentsUserId({identifier: this.config.signer.address, method:'evm'}). Attacker input: none beyond normal construction, but config.accountId is set to a NEAR-style or arbitrary string unrelated to config.signer.address, and intent.signer_id is left undefined. Preconditions: IntentSignerViemConfig.accountId is optional and, per its own doc comment, only meant as a signer_id override — yet it silently supersedes the address-derived id with no validation that accountId corresponds to any account the viem key controls. Call sequence: integrator constructs IntentSignerViem({signer: attackerAccount, accountId: 'victim.near'}) (a config an ordinary user could set on their own instance) and calls signIntent(intentWithNoSignerId); the resulting signer_id becomes 'victim.near' while the ERC-191 signature is produced by attacker's viem key. Equality that breaks: signer_id ('victim.near') == intents user id of the key that produced signature (attacker's EVM address) — false. Scoped impact: High — a caller can programmatically mint valid signed intents naming any accountId string as signer_id while signing with an unrelated key, independent of any real credential compromise. Whose funds: whichever balance is tracked under 'victim.near'. Proof idea: vitest test instantiating IntentSignerViem with accountId='someone-elses.near', calling signIntent on an intent with signer_id undefined, and asserting JSON.parse(result.payload).signer_id !== authHandleToIntentsUserId({identifier: signerAccount.address, method:'evm'}).
