Attacker input: userInfo.userAddress set to an address the caller does not hold the private key for, while signature.signatureData is a genuine ed25519 signature produced by the attacker's own different Solana key. Preconditions: prepareSwapSignedData derives public_key as `ed25519:${userInfo.userAddress}` directly from userInfo rather than recovering it from signature.signatureData (prepareBroadcastRequest.ts:45-51); the assert only checks userChainType === 'solana', not that userAddress matches the key that produced the signature. Equality that breaks: public_key embedded in the signed MultiPayload == the key that actually produced signature — the SDK trusts the caller-supplied address instead of the signature itself, so signer_id (derived from userAddress) need not equal the intents user id of the key that produced signature. Scoped impact: Critical — if intents.near's own signature verification is bypassed anywhere downstream that trusts this public_key field as authoritative rather than re-deriving from the raw signature, an attacker's signature could be attributed to (and debit) an account they do not control. Whose funds: the account named by userAddress.
