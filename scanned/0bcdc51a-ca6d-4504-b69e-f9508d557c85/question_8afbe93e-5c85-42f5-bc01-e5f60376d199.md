checkOnchainCreation in HinkalHelper.sol iterates `for (uint j = 0; j < circomData.inputNullifiers[i].length; j++) require(circomData.inputNullifiers[i][j] == 0, ...)` only when onChainCreation[i] is true, meaning input nullifiers for that index must all be zero. But nowhere in HinkalHelper.sol or Hinkal.sol is there a check that inputNullifiers[i][j]==0 entries (the placeholder for 'no spend') are excluded from insertNullifiers's actual nullifier-marking; insertNullifiers in HinkalBase.sol does check `if (inputNullifiers[i][j] != 0)` before marking, so zero nullifiers are correctly skipped. Does this hold even when onChainCreation[i] is false for some other index k that legitimately spends a real nullifier equal to 0 by construction (i.e., a poseidon hash that happens to equal exactly integer 0 — cryptographically implausible but worth confirming there's no explicit floor check `circomData.inputNullifiers[i][j] != 0` required at the proof-input level distinguishing 'null' from 'a real nullifier whose value is 0')? Since a same real nullifier value of 0 would be silently skipped by insertNullifiers's `if (inputNullifiers[i][j] != 0)` guard, could an attacker's circuit produce a genuine spend commitment whose nullifier hash is forced to literal 0 (by choosing inputs that make Poseidon output 0, which is a manipulable choice since inputs are attacker's own UTXO secrets), causing that real leaf to be spendable again later since its nullifier was never recorded in the `nullifiers` mapping? Equality broken: SINGLE SPEND, one value-bearing leaf == one nullifier ever accepted for it; a nullifier literal-0 collision with the 'unused slot' sentinel breaks this globally, not just for the attacker's own leaf, since the '0' sentinel value is shared code across all users. Impact: Critical, double-spend of a real leaf, direct theft/insolvency. Proof idea: Circom/snarkjs test attempting to brute-force or algebraically construct UTXO secret inputs whose Poseidon-based nullifier hash equals exactly 0, then submit two transact calls spending the same leaf, the second with the same forced-zero nullifier, and check whether insertNullifiers's mapping write is skipped both times, allowing the leaf's value to be withdrawn twice.
