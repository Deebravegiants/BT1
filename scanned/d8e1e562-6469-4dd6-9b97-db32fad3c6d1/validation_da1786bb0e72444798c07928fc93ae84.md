### Title
Missing Allowlist/Authorization Check Before Fan-out of Legacy Web API Trigger Requests to All DON Nodes - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The Gateway's legacy user-message path for the WebAPI capabilities handler forwards any signed (but not otherwise authorized) `web_api_trigger` request to every node in the DON without checking a workflow/sender allowlist, despite an explicit `// TODO: apply allowlist and rate-limiting here` marker in the code.

### Finding Description
`gateway.ProcessRequest` (`core/services/gateway/gateway.go:220-295`) accepts an inbound HTTP JSON-RPC request from any unprivileged client, decodes it into a legacy `api.Message`, and — as long as `msg.Validate()` succeeds — dispatches it to the target DON's handler via `h.HandleLegacyUserMessage`. [1](#0-0) 

`api.Message.Validate()` only checks field-length constraints and that a valid ECDSA signature is present; it recovers the signer address from that signature but does not check the signer/sender against any allowlist or role. [2](#0-1) 

In `HandleLegacyUserMessage`, after checking payload decoding, a non-zero timestamp, and message staleness, the code explicitly notes the missing control and then proceeds to accept any `MethodWebAPITrigger` message and fan it out to all `h.donConfig.Members`: [3](#0-2) 

This mirrors the audited `USSDRebalancer.BuyUSSDSellCollateral` pattern: a privileged/side-effecting operation (there, an arbitrary token swap; here, a DON-wide capability trigger fan-out) is executed on attacker-influenced input without validating that the request originates from an authorized party, relying only on superficial structural checks (signature format/freshness) rather than actual authorization.

### Impact Explanation
Any party able to produce a validly signed (self-signed, any keypair) `api.Message` can cause the Gateway to broadcast a `web_api_trigger`-method message to every node of a target DON. Depending on downstream node-side handling (workflow trigger dispatch), this could result in unauthorized or spurious workflow trigger events being processed by capability nodes, resource exhaustion via unbounded triggering, or reaching workflows that the sender is not entitled to invoke — since the allowlist check that would normally scope which senders/workflows may trigger which DON is not yet implemented at this layer.

### Likelihood Explanation
High from a reachability standpoint: the vulnerable code path is reached by any external, unauthenticated caller who can reach the Gateway's public user-facing HTTP endpoint and supply a self-generated signature — no pre-existing credential, session, or allowlist membership is required to reach the DON fan-out logic, only the ability to craft a validly-formatted, self-signed message with a fresh timestamp.

### Recommendation
Implement the allowlist/authorization check referenced by the TODO comment before forwarding requests to DON members — verify the recovered `msg.Body.Sender` (or associated workflow/owner) against a configured or on-chain allowlist for the target DON/method, and add rate-limiting per sender, mirroring the model already used elsewhere in the gateway (e.g., the `Authorizer`/allowlist pattern in `core/capabilities/vault/gw_handler.go` and `NewAllowListBasedAuth`). [4](#0-3) 

### Proof of Concept
1. Generate any ECDSA keypair (does not need to be pre-registered anywhere).
2. Construct an `api.Message` with `Body.Method = "web_api_trigger"`, a valid `webapicap.TriggerRequestPayload` (with non-zero, fresh `Timestamp`), and `Body.DonID` set to a known target DON ID.
3. Sign the message with the generated key (`msg.Sign(key)`), producing a message that passes `msg.Validate()`.
4. POST the JSON-RPC-wrapped message to the Gateway's public `/user` HTTP endpoint (see `core/services/gateway/integration_tests/gateway_integration_test.go:196` for the endpoint shape).
5. Observe that `gateway.ProcessRequest` routes it to `HandleLegacyUserMessage`, which — absent any allowlist check — forwards the request to `don.SendToNode` for every member in `donConfig.Members`, as demonstrated by the existing unit test `TestHandlerReceiveHTTPMessageFromClient` "happy case" which asserts `SendToNode` is called for all DON members using only a locally-generated key. [5](#0-4)

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageID) == 0 || len(m.Body.MessageID) > MessageIDMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageID, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonID) == 0 || len(m.Body.DonID) > MessageDonIDMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonID, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
