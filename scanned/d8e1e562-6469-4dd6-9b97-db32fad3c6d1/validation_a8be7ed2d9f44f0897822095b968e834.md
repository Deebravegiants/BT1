### Title
API token validity is recomputed from the live `UserAPITokenDuration` config at check-time instead of the value in effect at issuance, allowing retroactive extension of expired/stale tokens - ([File: core/sessions/oidcauth/oidc.go], [File: core/sessions/ldapauth/ldap.go])

### Summary
Both the OIDC and LDAP authentication providers implement `FindUserByAPIToken` by storing only `created_at` for an issued API token and then validating it with `created_at + $2 >= now()`, where `$2` is the *current* value of `config.UserAPITokenDuration()` fetched live at request-validation time rather than the duration that was configured when the token was minted. This mirrors the reported bug class exactly: a "staked"/committed value (here, the token's validity window) is not persisted per-request at creation time, but is instead recomputed using a mutable global setting at settlement (here, authentication) time.

### Finding Description
`SetAuthToken` in `core/sessions/oidcauth/oidc.go` inserts a row into `oidc_user_api_tokens` with only `created_at` and no independent expiry value: [1](#0-0) 

Similarly, `SetAuthToken` in `core/sessions/ldapauth/ldap.go` inserts into `ldap_user_api_tokens` with only `created_at`: [2](#0-1) 

Validation for both providers computes token validity by re-reading the operator-configurable `UserAPITokenDuration()` at the moment of the incoming, unprivileged authentication request, rather than using a value fixed at issuance: [3](#0-2) [4](#0-3) 

This is invoked directly from the unprivileged, internet-facing request-authentication path `AuthenticateByToken`, which reads the `X-API-KEY`/`X-API-SECRET` headers from an arbitrary incoming HTTP request and calls `FindUserByAPIToken` to decide whether the token is still valid before granting the caller the associated user's role: [5](#0-4) 

Because the expiry check is `created_at + <current config value> >= now()` instead of `created_at + <duration in effect at issuance> >= now()`, any change to `WebServer.OIDC.UserAPITokenDuration` or `WebServer.LDAP.UserAPITokenDuration` retroactively re-evaluates the validity of *every* previously issued token still present in the table, exactly like the reported `WITHDRAWAL_STAKE` bug where the "settlement" step uses the live config instead of the value committed at "submission" time.

### Impact Explanation
- If an operator increases `UserAPITokenDuration` (e.g., to accommodate a legitimate long-lived automation use case), tokens that had already exceeded their originally-intended lifetime — including ones a client may have assumed were expired/rotated, or ones that leaked and were expected to become useless after the original window — become valid again and continue to authenticate as the owning user with full role privileges. This is an unauthenticated-request-turned-authenticated scenario driven purely by an admin-side config change, i.e., unintended authentication bypass/extension for a token an attacker (or former holder) still possesses.
- If an operator decreases `UserAPITokenDuration`, tokens that legitimate users still expect to be valid (per the duration promised at creation) are invalidated early, forcing unexpected re-authentication (availability/DoS-style impact for the affected users).
- Because the purge/reaper logic (`deleteStaleAPITokens` in the LDAP `sync.go`) also derives its threshold from the current config, tokens are not eagerly deleted at their original expiry, so the window in which a "since-expired-but-not-yet-purged" token can be revived by a config bump is real, not merely theoretical.

### Likelihood Explanation
Requires an operator to change `UserAPITokenDuration` while old, otherwise-expired tokens still exist in `oidc_user_api_tokens`/`ldap_user_api_tokens` (they are only purged lazily on lookup or by the periodic reaper/sync, not immediately at nominal expiry). This is analogous to the original report's "Low likelihood, but High impact" characterization — it is not an everyday event, but nothing prevents it, and no validation exists to reject the config change or to pin already-issued tokens to their original duration.

### Recommendation
Persist an explicit expiry timestamp (or the duration value) alongside `created_at` at the time the token is created (`SetAuthToken`/`INSERT INTO oidc_user_api_tokens` / `ldap_user_api_tokens`), and compare against that stored value in `FindUserByAPIToken`, rather than re-deriving the window from the live, mutable `UserAPITokenDuration()` config at each authentication attempt. This ensures configuration changes only affect newly issued tokens, matching option (1) from the original report ("store staked value per user or per request").

### Proof of Concept
1. Operator enables `UserAPITokenEnabled` with `UserAPITokenDuration = '1h'`; a user calls `NewAPIToken` (`core/web/user_controller.go`, `SetAuthToken`) and receives a token whose row has `created_at = T0`. [6](#0-5) 
2. More than 1 hour elapses (`now() > T0 + 1h`); per the original config, the token should be rejected on the next `AuthenticateByToken` call, but suppose it has not yet been looked up/purged.
3. The operator changes `UserAPITokenDuration` to `'240h'` (e.g., a legitimate ops change for another user/service).
4. The old (holder-abandoned or leaked) token is now presented in `X-API-KEY`/`X-API-SECRET` headers by an unprivileged client; `FindUserByAPIToken` evaluates `created_at + 240h >= now()`, which is now true, so `AuthenticateByToken` succeeds and grants the caller the original user's session/role — even though the token should have been dead under the policy that was in force when it was issued.
