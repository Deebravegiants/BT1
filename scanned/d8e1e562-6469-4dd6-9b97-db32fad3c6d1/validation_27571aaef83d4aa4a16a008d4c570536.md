## Analysis Result

I found a valid analog to CVE-2021-3563 (bcrypt silent-truncation leading to weakened password verification) in the chainlink codebase's password-change flow.

### Title
Password-change flow allows unbounded password length, causing silent bcrypt truncation and inconsistent authentication - (File: core/sessions/localauth/orm.go)

### Summary
Chainlink caps passwords at `MaxBcryptPasswordLength = 50` characters only in the account-creation path (`sessions.NewUser` → `ValidateAndHashPassword`), explicitly to stay under bcrypt's hard 72-byte truncation limit. However, the password-change paths (`UserController.UpdatePassword` over REST, and the `UpdateUserPassword` GraphQL mutation) bypass this check entirely and hash the new password directly via `SetPassword`, which calls `utils.HashPassword` (a thin wrapper over `bcrypt.GenerateFromPassword`) with no length limit.

### Finding Description
`sessions.ValidateAndHashPassword` is the single point of logic intended to enforce password constraints before hashing, including the bcrypt-safe length cap: [1](#0-0) 

But this function is only used by the user-creation flow. The password-change (reset) flow instead calls `utils.VerifyPasswordComplexity`, which enforces only a *minimum* length (16 chars), leading/trailing whitespace, and disallowed substrings — it does **not** enforce any maximum length despite the accompanying doc string claiming "16-50 characters": [2](#0-1) 

The REST handler for password change performs only this complexity check, then proceeds straight to hashing: [3](#0-2) 

That call chain reaches `orm.SetPassword`, which hashes the raw password with bcrypt with no length guard at all: [4](#0-3) 

`utils.HashPassword` is a direct passthrough to `bcrypt.GenerateFromPassword`, which silently truncates any input beyond 72 bytes — this is the exact root cause described in CVE-2021-3563: [5](#0-4) 

The GraphQL mutation path (`UpdateUserPassword`) exhibits the same gap — it goes straight from old-password verification to `SetPassword` without calling `VerifyPasswordComplexity` or any length check at all: [6](#0-5) 

The account-creation test explicitly demonstrates the intended safeguard (`MaxBcryptPasswordLength`) that the change-password path lacks: [7](#0-6) 

### Impact Explanation
Because bcrypt only hashes/verifies the first 72 bytes of input, a user (or an operator resetting a password through the same code path) can set a password far longer than 72 bytes believing the full string participates in complexity and matching. In reality, only the first 72 bytes are cryptographically meaningful. This is a **CWE-863 (Incorrect Authorization)**-class weakness: any bytes past position 72 are silently ignored both at set-time and verify-time, so the perceived password strength/uniqueness advertised to the user (up to 50+ chars, no upper bound enforced) is inconsistent with what is actually enforced by bcrypt. An attacker who obtains or brute-forces the first 72 bytes of a long password (e.g., via credential stuffing lists, phishing partial capture, or a compromised password manager entry) can authenticate successfully even without knowing the full string the user believes they set.

### Likelihood Explanation
Exploitation requires an attacker to already know or guess the first 72 bytes of a user's password, which is a nontrivial precondition (the same caveat noted in the original CVE-2021-3563 advisory). The likelihood is moderate: it requires no privilege escalation to trigger (any authenticated user changing their own password is silently affected), and administrators/users relying on very long passphrases for "extra" entropy get a false sense of security since only the first 72 bytes matter.

### Recommendation
Route the password-change code paths (`UserController.UpdatePassword` in `core/web/user_controller.go` and `Resolver.UpdateUserPassword` in `core/web/resolver/mutation.go`) through the same `sessions.ValidateAndHashPassword`/`MaxBcryptPasswordLength` enforcement used at account creation, or add an explicit max-length check inside `orm.SetPassword` (and the equivalent `oidcauth`/`ldapauth` `SetPassword` implementations) before calling `utils.HashPassword`, so no path can silently truncate secrets during bcrypt hashing.

### Proof of Concept
1. Authenticate as any user and call `PATCH /v2/user` (or the `updateUserPassword` GraphQL mutation) with `newPassword` set to a string of e.g. 200 characters where the first 72 bytes are `AAAA...A` (72 A's) followed by 128 arbitrary characters.
2. `VerifyPasswordComplexity` passes (only checks min length 16, whitespace, disallowed substrings) — no rejection for length.
3. `orm.SetPassword` → `utils.HashPassword` → `bcrypt.GenerateFromPassword` truncates input to the first 72 bytes before hashing.
4. Subsequent login attempts using just the 72 `A` characters (ignoring the remaining 128 arbitrary characters) succeed via `utils.CheckPasswordHash`, confirming the tail of the password is functionally meaningless despite the user believing the full 200-character string constitutes their credential.

func ValidateAndHashPassword(plainPwd string) (string, error) {
	if err := utils.VerifyPasswordComplexity(plainPwd); err != nil {
		return "", pkgerrors.Wrapf(err, "password insufficiently complex:\n%s", utils.PasswordComplexityRequirements)
	}
	if len(plainPwd) > MaxBcryptPasswordLength {
		return "", pkgerrors.Errorf("must enter a password less than %v characters", MaxBcryptPasswordLength)
	}

	pwd, err := utils.HashPassword(plainPwd)
	if err != nil {
		return "", err
	}

	return pwd, nil
}

const PasswordComplexityRequirements = `
Must have a length of 16-50 characters
Must not comprise:
	Leading or trailing whitespace (note that a trailing newline in the password file, if present, will be ignored)
`

const MinRequiredLen = 16

var LeadingWhitespace = regexp.MustCompile(`^\s+`)
var TrailingWhitespace = regexp.MustCompile(`\s+$`)

var (
	ErrMsgHeader = fmt.Sprintf(`
Expected password complexity:
Must be at least %d characters long
Must not comprise:
	Leading or trailing whitespace
	A user's API email

Faults:
`, MinRequiredLen)
	ErrWhitespace = errors.New("password contains a leading or trailing whitespace")
)

func VerifyPasswordComplexity(password string, disallowedStrings ...string) (merr error) {
	errMsg := ErrMsgHeader
	var stringErrs []string

	if LeadingWhitespace.MatchString(password) || TrailingWhitespace.MatchString(password) {
		stringErrs = append(stringErrs, ErrWhitespace.Error())
	}

	if len(password) < MinRequiredLen {
		stringErrs = append(stringErrs, fmt.Sprintf("password is less than %d characters long", MinRequiredLen))
	}

	for _, s := range disallowedStrings {
		if strings.Contains(strings.ToLower(password), strings.ToLower(s)) {
			stringErrs = append(stringErrs, fmt.Sprintf("password may not contain: %q", s))
		}
	}

	if len(stringErrs) > 0 {
		for _, stringErr := range stringErrs {
			errMsg = fmt.Sprintf("%s	%s\n", errMsg, stringErr)
		}
		merr = errors.New(errMsg)
	}

	return
}

// HashPassword wraps around bcrypt.GenerateFromPassword for a friendlier API.
func HashPassword(password string) (string, error) {
	bytes, err := bcrypt.GenerateFromPassword([]byte(password), bcrypt.DefaultCost)
	return string(bytes), err
}

func (r *Resolver) UpdateUserPassword(ctx context.Context, args struct {
	Input UpdatePasswordInput
}) (*UpdatePasswordPayloadResolver, error) {
	if err := authenticateUser(ctx); err != nil {
		return nil, err
	}

	session, ok := webauth.GetGQLAuthenticatedSession(ctx)
	if !ok {
		return nil, errors.New("couldn't retrieve user session")
	}

	dbUser, err := r.App.AuthenticationProvider().FindUser(ctx, session.User.Email)
	if err != nil {
		return nil, err
	}

	if !utils.CheckPasswordHash(args.Input.OldPassword, string(dbUser.HashedPassword)) {
		r.App.GetAuditLogger().Audit(audit.PasswordResetAttemptFailedMismatch, map[string]any{"user": dbUser.Email})

		return NewUpdatePasswordPayload(nil, map[string]string{
			"oldPassword": "old password does not match",
		}), nil
	}

	if err = r.App.AuthenticationProvider().ClearNonCurrentSessions(ctx, session.SessionID); err != nil {
		return nil, clearSessionsError{}
	}

	err = r.App.AuthenticationProvider().SetPassword(ctx, &dbUser, args.Input.NewPassword)
	if err != nil {
		return nil, failedPasswordUpdateError{}
	}

	r.App.GetAuditLogger().Audit(audit.PasswordResetSuccess, map[string]any{"user": dbUser.Email})
	return NewUpdatePasswordPayload(session.User, nil), nil
}
