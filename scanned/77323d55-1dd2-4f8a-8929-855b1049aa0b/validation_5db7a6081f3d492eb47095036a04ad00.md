### Title
Nil-Pointer Dereference in Gateway JSON-RPC Request Decoding via Missing `params` Field - ([File: core/services/gateway/api/jsonrpccodec.go])

### Summary
The Gateway's JSON-RPC request decoder dereferences `request.Params` without a nil check before unmarshaling it into a `Message`. An unauthenticated, unprivileged HTTP client can send a request to the internet-facing Gateway with the `params` field omitted (or explicitly `null`), causing a nil-pointer dereference and a runtime panic. This is functionally analogous to CVE-2016-7131, where PHP's `wddx_deserialize` crashed on malformed/incomplete input that bypassed an implicit assumption about tag structure — here, the Gateway's decoder assumes `Params` is always non-nil.

### Finding Description
`(*JSONRPCCodec).DecodeJSONRequest` does: [1](#0-0) 

```go
func (*JSONRPCCodec) DecodeJSONRequest(request jsonrpc2.Request[json.RawMessage]) (*Message, error) {
	var msg Message
	err := json.Unmarshal(*request.Params, &msg)
	...
```

`request.Params` is a pointer type (`*json.RawMessage`) populated from the incoming JSON-RPC envelope. If the client omits the `"params"` key, or sends `"params": null`, the field decodes to a nil pointer. `*request.Params` then dereferences a nil pointer, panicking.

This function is called directly from the Gateway's request-processing entrypoint, which is reachable by any unauthenticated HTTP client hitting the Gateway's public endpoint: [2](#0-1) 

```go
func (g *gateway) ProcessRequest(ctx context.Context, rawRequest []byte, auth string) (rawResponse []byte, httpStatusCode int) {
	// decode
	jsonRequest, err := jsonrpc2.DecodeRequest[json.RawMessage](rawRequest, auth)
	if err != nil {
		return newError("", api.UserMessageParseError, err.Error())
	}
	msg, err := g.codec.DecodeJSONRequest(jsonRequest)
	if err != nil {
		return newError(jsonRequest.ID, api.UserMessageParseError, err.Error())
	}
```

Note that `jsonrpc2.DecodeRequest` (from the external `chainlink-common` package) succeeds first — it only validates the JSON-RPC envelope structure (version, method, id), not that `params` is present — before `DecodeJSONRequest` unconditionally dereferences `Params`. There is no guard comparable to the one seen in the legacy path (`core/services/gateway/handlers/common/message_util.go`'s `ValidatedMessageFromReq`, which explicitly checks `if req.Params == nil` before use): [3](#0-2) 

That nil check exists on the legacy DON-routed path but is missing on the JSON-RPC service-name-routed path that `ProcessRequest` uses when `msg == nil || msg.Body.DonID == ""` (i.e., the new/default routing branch), meaning the vulnerable `DecodeJSONRequest` call executes before the routing decision that would otherwise validate the message.

### Impact Explanation
A single crafted, unauthenticated HTTP request to the Gateway's public endpoint (no API key, no signature, no DON membership required) can crash the Gateway process via a Go runtime panic, resulting in denial of service for all nodes and clients relying on that Gateway instance. This matches the "Service unavailability" impact class explicitly permitted by the ruleset and is a direct root-cause analog of CVE-2016-7131 (NULL pointer dereference from malformed/incomplete input in a deserialization function).

### Likelihood Explanation
High likelihood: the Gateway's HTTP endpoint is explicitly internet-facing and designed to accept unauthenticated/unprivileged client requests; triggering the bug requires only a valid JSON-RPC envelope (`{"jsonrpc":"2.0","id":"x","method":"y"}`) with `params` omitted or `null` — no cryptographic material, valid signature, or allowlisted identity is needed.

### Recommendation
Add an explicit nil check on `request.Params` in `DecodeJSONRequest` (mirroring the check already present in `ValidatedMessageFromReq`) and return a structured `UserMessageParseError` instead of dereferencing a nil pointer. Additionally, ensure a panic-recovery/middleware wrapper exists around `ProcessRequest` so that any future missed nil-check does not crash the whole Gateway process.

### Proof of Concept
Send the following HTTP request body to the Gateway's user-facing endpoint (no auth/signature needed):
```json
{"jsonrpc":"2.0","id":"abc","method":"some_method"}
```
(i.e., `params` key entirely omitted, or set to `null`.) This reaches `gateway.ProcessRequest` → `jsonrpc2.DecodeRequest` (succeeds, since `params` isn't required by the envelope decoder) → `g.codec.DecodeJSONRequest(jsonRequest)` → `json.Unmarshal(*request.Params, &msg)` with `request.Params == nil`, causing a nil-pointer dereference panic in the Gateway process.

**Caveat**: I was unable to inspect the source of `jsonrpc2.Request[T]` and `jsonrpc2.DecodeRequest` (defined in the external `github.com/smartcontractkit/chainlink-common/pkg/jsonrpc2` module, not part of this repo's index), so I could not directly confirm from that package's code whether `Params` can in fact be left as a nil `*json.RawMessage` when the field is absent/null, nor whether that package's `DecodeRequest` performs any implicit validation that would prevent this state. This assessment is based on the call-site behavior and Go's standard `encoding/json` semantics for pointer fields, plus the corroborating nil-check pattern found elsewhere in this codebase's legacy message-validation path. A Devin session with access to the `chainlink-common` module source would be needed to fully confirm this root cause end-to-end.

func (*JSONRPCCodec) DecodeJSONRequest(request jsonrpc2.Request[json.RawMessage]) (*Message, error) {
	var msg Message
	err := json.Unmarshal(*request.Params, &msg)
	if err != nil {
		return nil, err
	}
	msg.Body.MessageID = request.ID
	msg.Body.Method = request.Method
	return &msg, nil
}

	if req.Version != "2.0" {
		return nil, errors.New("incorrect jsonrpc version")
	}
	if req.Method == "" {
		return nil, errors.New("empty method field")
	}
	if req.Params == nil {
		return nil, errors.New("missing params attribute")
