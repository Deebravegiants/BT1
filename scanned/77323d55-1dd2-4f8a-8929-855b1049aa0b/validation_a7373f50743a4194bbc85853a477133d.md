### Title
Node-side Vault `GatewayHandler` permanently caches the master public key with no refresh, so ciphertext-ownership verification silently uses a stale key after rotation - ([File: core/capabilities/vault/gw_handler.go])

### Summary
`GatewayHandler.getMasterPublicKey` in `core/capabilities/vault/gw_handler.go` fetches the vault master public key from the `SecretsService` once and stores it forever in `cachedMasterPublicKey`, with no TTL, invalidation, or refresh mechanism [1](#0-0) . This is the same bug class as the reported `decimalPad` issue: a value that is computed/fetched once from an authoritative, mutable source and then relied upon indefinitely, becoming silently incorrect if the source ever changes.

### Finding Description
`NewGatewayHandler` builds a `GatewayHandler` with a `sync.RWMutex`-guarded `cachedMasterPublicKey` field, initially `nil` [2](#0-1) . On the first `SecretsCreate`/`SecretsUpdate` request, `getMasterPublicKey` fetches the key via `MasterPublicKeyFromSecretsService` and caches it permanently: once `h.cachedMasterPublicKey != nil`, every subsequent call just returns a copy of the cached value and never re-queries `secretsService.GetPublicKey` again [1](#0-0) .

This public key is then passed into `h.requestProcessor.ProcessRequest(ctx, req, publicKey)` for `MethodSecretsCreate`/`MethodSecretsUpdate` [3](#0-2) , where it is used to validate that the client-supplied encrypted secret's ciphertext actually matches the claimed owner label (ciphertext-ownership verification), analogous to a decrypt/verify-with-public-key step gating whether the request is trusted.

By contrast, the separate gateway-side handler (`core/services/gateway/handlers/vault/handler.go`) explicitly acknowledges that this key can change and refreshes it on a `1 * time.Minute` ticker via `fetchVaultPublicKey` [4](#0-3) . The node-side `GatewayHandler` has no equivalent refresh logic — it is a "fetch-once-and-freeze" cache, exactly the same anti-pattern as the reported `decimalPad`: a scaling/verification parameter is captured once from an external, mutable source (token decimals / vault master key) and never revisited, so if the source rotates, all downstream calculations/verifications silently use outdated data.

### Impact Explanation
If the vault master key is ever rotated (e.g., via DKG re-key/re-share, which the surrounding code treats as a real possibility — hence the gateway-side periodic refresh and the `handlePublicKeyGet`/`tryCachePublicKeyResponse` machinery), the node's `GatewayHandler` will keep using the old, now-incorrect public key for validating every subsequent `SecretsCreate`/`SecretsUpdate` request from unprivileged clients. This can cause:
- Legitimate requests encrypted under the new master key to be rejected as invalid (denial of service for secret creation/update), or
- Ciphertext-ownership verification to be performed against the wrong key entirely, undermining the guarantee that the request's ciphertext label matches the claimed owner.

This is reachable purely from the internet-facing gateway → node message-handling path for `MethodSecretsCreate`/`MethodSecretsUpdate`, i.e., from unprivileged workflow-owner requests, with no operator or privileged action required to trigger the mismatch (only a legitimate key-rotation event on the vault side).

### Likelihood Explanation
Master-key rotation is an expected, designed-for event in this system (the gateway-side handler explicitly polls for it every minute), so the mismatch window is not a hypothetical edge case — it is the normal operating mode whenever a rotation occurs. Because the node-side handler never re-fetches after its first successful read, every node that has already cached the key will diverge from the new authoritative key until the process restarts, which for a long-running node service could be indefinite.

### Recommendation
Add the same kind of periodic refresh/invalidation to `GatewayHandler.cachedMasterPublicKey` that already exists in `core/services/gateway/handlers/vault/handler.go` (`fetchVaultPublicKey` ticker), or fetch the key fresh (or with a bounded TTL) on each `SecretsCreate`/`SecretsUpdate` request instead of caching it for the lifetime of the process. At minimum, expose an explicit invalidation hook that is called whenever the vault master key changes.

### Proof of Concept
1. Start a node with `GatewayHandler` wired to a `SecretsService` backed by vault master key `K1`.
2. Send a `SecretsCreate` request; `getMasterPublicKey` fetches `K1` and caches it in `h.cachedMasterPublicKey` [1](#0-0) .
3. Rotate the vault master key on the backing `SecretsService` to `K2` (a supported, expected operation given the gateway-side refresh logic).
4. Send another `SecretsCreate`/`SecretsUpdate` request encrypted against `K2`. `getMasterPublicKey` still returns cached `K1` because `h.cachedMasterPublicKey != nil` [5](#0-4) , so `requestProcessor.ProcessRequest` validates the new ciphertext against the stale `K1`, producing an incorrect verification result instead of the correct one against `K2`.

func (h *GatewayHandler) getMasterPublicKey(ctx context.Context) (*tdh2easy.PublicKey, error) {
	h.mu.RLock()
	if h.cachedMasterPublicKey != nil {
		cachedCopy := *h.cachedMasterPublicKey
		h.mu.RUnlock()
		return &cachedCopy, nil
	}
	h.mu.RUnlock()

	publicKey, err := MasterPublicKeyFromSecretsService(ctx, h.secretsService)
	if err != nil {
		return nil, err
	}

	h.mu.Lock()
	defer h.mu.Unlock()
	if h.cachedMasterPublicKey != nil {
		cachedCopy := *h.cachedMasterPublicKey
		return &cachedCopy, nil
	}
	h.cachedMasterPublicKey = publicKey
	cachedCopy := *publicKey
	return &cachedCopy, nil
}
