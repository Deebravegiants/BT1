### Title
Potential nil pointer dereference panic when handling `vault.publicKey.get` Gateway message without a `params` field - (File: `core/capabilities/vault/gw_handler.go`)

### Summary
`GatewayHandler.handlePublicKeyGet` in [1](#0-0) dereferences `*req.Params` directly without checking for `nil`, unlike other paths in the same file. `req.Params` is a `*json.RawMessage` populated from data read off the Gateway connector's websocket connection in `readLoop`, which unmarshals into a generic `jsonrpc.Request[json.RawMessage]` without validating that `Params` is non-nil before dispatching to the registered handler.

### Finding Description
`GatewayHandler.HandleGatewayMessage` [2](#0-1)  routes `vaulttypes.MethodPublicKeyGet` requests to `handlePublicKeyGet`, which does:
```go
r := &vaultcommon.GetPublicKeyRequest{}
if err := json.Unmarshal(*req.Params, r); err != nil {
``` [1](#0-0) 
This directly dereferences `req.Params` with no nil check, in contrast to `common.ValidatedMessageFromReq`, which explicitly guards `if req.Params == nil` before use [3](#0-2) . The connector's `readLoop`, which reads raw bytes off the wire from the Gateway and unmarshals them into a `jsonrpc.Request[json.RawMessage]` before dispatching to the handler, performs no such nil check either [4](#0-3) . If a request for method `MethodPublicKeyGet` is relayed with an absent/null `params` field, `req.Params` will be `nil`, and `*req.Params` will panic with a nil pointer dereference (matching CWE-476), crashing the node process — directly analogous to the ULNASTransport CVE-2026-33283 pattern (crash caused by dereferencing/accessing a field that wasn't validated as present).

### Impact Explanation
I could not fully confirm whether an external, unprivileged client's request can actually reach this code path with a nil `Params`, because I was unable to inspect: (1) the upstream Gateway-side handler (`core/services/gateway/handlers/vault/handler.go`, specifically `newActiveRequest`/`handlePublicKeyGet` forwarding logic) to see if it validates/repopulates `Params` before relaying to the node, and (2) the `jsonrpc2.DecodeRequest` implementation to see if it enforces `Params` non-nil for all methods. If either of those layers guarantees `Params != nil` before it reaches the node's `GatewayHandler.HandleGatewayMessage`, then this is not exploitable. If they don't (e.g., `MethodPublicKeyGet` requires no `params` object from the user's perspective, so a client could legitimately omit it), then this is a real crash-on-malformed-input DoS vector on the node process, reachable without authorization since `MethodPublicKeyGet` explicitly bypasses the authorization pipeline in `HandleGatewayMessage`.

### Likelihood Explanation
Uncertain — I did not confirm whether the Gateway-side relay path preserves a nil `Params` through to the node's `GatewayHandler`, or if `jsonrpc2` request decoding enforces non-nil params universally. This requires further verification with the actual repo files (`core/services/gateway/handlers/vault/handler.go`'s `newActiveRequest`, and the `jsonrpc2` package's `DecodeRequest`), which I was not able to load in the remaining iterations.

### Recommendation
Given the uncertainty, I recommend explicitly adding a nil-check guard in `handlePublicKeyGet` (mirroring the pattern used in `common.ValidatedMessageFromReq`) before dereferencing `req.Params`, regardless of whether the upstream layers currently prevent it — defense-in-depth against exactly this bug class (crash on missing required field with no upstream guard), consistent with the fix pattern in GHSA-3366-gw57-fcm5.

### Proof of Concept
Not verified end-to-end due to incomplete visibility into the Gateway-to-node relay path and the `jsonrpc2` decode logic within the available tool budget. The local trigger, if reachable, would be: send a Gateway `vault.publicKey.get` message with `"params": null` (or the field omitted) to a node's Gateway connector; `handlePublicKeyGet` would then panic on `*req.Params`.

Given the significant unresolved uncertainty about reachability from an unprivileged actor, I cannot assert this as a confirmed vulnerability with the evidence gathered — flagging it as a plausible but **unconfirmed** analog rather than a validated finding.
