Target: `ShopifyAPI::Auth::Oauth::AuthQuery#to_signable_string` (lib/shopify_api/auth/oauth/auth_query.rb) and `ShopifyAPI::Utils::HmacValidator.validate`. Attacker action: send a callback to the host app's OAuth callback route with query string `code=X&host=H&shop=S&state=T&timestamp=TS&hmac=VALID&extra_param=malicious` where `extra_param` is never included in `to_signable_string`'s five-key hash (code, host, shop, state, timestamp). Preconditions: attacker has a validly signed callback from their own dev shop install. Call sequence: host app builds `AuthQuery.new(request.parameters...)`, calls `Oauth.validate_auth_callback`, which calls `Utils::HmacValidator.validate(auth_query)` -> `auth_query.to_signable_string` -> `URI.encode_www_form({code,host,shop,state,timestamp})`. Binding that breaks: set(fields host app acted on) == set(fields inside to_signable_string) is false because `extra_param` is acted on by the app but absent from the signed set. Impact: Critical only if the host app trusts `extra_param` for authorization decisions derived from this gem's validated object — state the gem provides no protection for any field beyond the five. Proof idea: minitest asserting `AuthQuery.new(..., extra: 'x').to_signable_string` is unaffected by `extra`, and `HmacValidator.validate` returns true regardless of `extra`, showing SIGNATURE_COVERAGE fails for any field outside `to_signable_string`.
