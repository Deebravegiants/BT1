Target: ShopifyAPI::Auth::Session#expired? and #refresh_token_expired?. Attacker action: send a request carrying a Session (via cookie/session token) whose 'expires' Time was set from a value the attacker influenced through a replayed/old but HMAC-valid OAuth callback (since timestamp isn't checked, per this target's Scope, an old code exchange could still produce a session with an expires field computed from Time.now at exchange time, not from the original signed timestamp). Preconditions: expires = Time.now + access_token_response.expires_in.to_i is computed at exchange time, not tied to the original signed 'timestamp'. Call sequence: replay of old signed callback (see replay question above) -> Oauth.validate_auth_callback proceeds -> Session.from sets expires freshly -> Session#expired? returns false for a session whose authorizing signature is stale. Binding: the freshness bound checked by expired? (Time.now vs expires) == the freshness of the original signed 'timestamp' the HMAC covers; the two are never reconciled. Impact: Critical - authentication bypass via replay producing a 'fresh-looking' but illegitimately re-derived session for a merchant. Proof: minitest freezing time, replaying an old AuthQuery with valid HMAC and ancient timestamp, asserting the resulting Session#expired? is false despite auth_query.timestamp being far in the past.
