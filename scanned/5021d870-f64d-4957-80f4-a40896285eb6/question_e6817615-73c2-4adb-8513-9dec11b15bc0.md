Target: `AuthQuery#to_signable_string`. Attacker action: send a callback where `host` value is percent-encoded differently than Shopify's own encoding (e.g., using lowercase vs uppercase hex escapes, or `+` vs `%20`) such that the byte string reconstructed by `URI.encode_www_form(params)` inside `to_signable_string` differs from the exact byte string Shopify signed over on the wire. Preconditions: victim's real callback from Shopify had `host` containing a base64 sequence with `=` padding or `/` characters requiring percent-encoding. Call sequence: `AuthQuery.new(host: decoded_value)` stores the URL-decoded string; `to_signable_string` re-encodes via `URI.encode_www_form`. Binding that breaks: bytes verified by HMAC (gem's re-encoded form) == bytes Shopify actually signed over (its own encoding) — if `URI.encode_www_form`'s canonicalization differs from Shopify's original encoding for any value, the computed signature diverges from what Shopify intended to authenticate, potentially causing either false rejects (availability, out of scope) or, if two different raw query strings decode to the same stored field values, HMAC validating for content that didn't match the literal signed bytes. Impact: High — SSRF-adjacent risk is not applicable here; scoped to auth bypass reasoning only if attacker can find two distinct `host` byte sequences producing identical `to_signable_string` output while still being treated as different downstream. Proof idea: minitest building two headers with different percent-encodings decoding to the same `host` string, confirming `to_signable_string` output is identical for both and that HmacValidator cannot distinguish origin encoding, illustrating SIGNATURE_COVERAGE is over normalized fields, not raw bytes.
