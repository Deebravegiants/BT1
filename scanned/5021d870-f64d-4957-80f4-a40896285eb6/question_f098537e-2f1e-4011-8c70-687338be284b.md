Target: `AuthQuery#to_signable_string` vs `URI.encode_www_form`. Attacker action: submit a callback query with a duplicated key, e.g., `shop=attacker-shop.myshopify.com&shop=victim-shop.myshopify.com&code=...&host=...&state=...&timestamp=...&hmac=VALID_FOR_FIRST_SHOP`, where the host app's request-parsing library (e.g., Rack) takes the last occurrence of a duplicate query key while `AuthQuery.new` is constructed from parameters that took the first. Preconditions: host app builds `AuthQuery` from `request.parameters` per docs/usage/oauth.md, and any downstream logic (host app's own routing/logging) that also reads `params[:shop]` could disagree with what `AuthQuery` used. Call sequence: `AuthQuery.new(shop: parsed_shop)` -> `to_signable_string` uses only the shop value baked into the struct at construction time. Binding that breaks: shop signed by Shopify (first occurrence) == shop acted on downstream by any code re-reading raw params (potentially the last occurrence) is not guaranteed by this gem. Impact: Critical — cross-tenant confusion if any code path in the gem's documented flow re-derives shop from raw query rather than from `auth_query.shop`. Proof idea: minitest constructing two `AuthQuery` objects with different shop values but identical hmac computed for one of them; assert `HmacValidator.validate` only succeeds for the shop it was computed for, and demonstrate `auth_query.shop` is a single fixed string independent of duplicate-key ambiguity, so any caller reading `shop` from a different source violates SHOP_BINDING.
