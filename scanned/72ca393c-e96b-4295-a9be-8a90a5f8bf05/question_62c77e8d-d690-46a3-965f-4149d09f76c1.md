[computeSignedErc191Hash / computeSignedTip191Hash] Can an unprivileged counterparty supply an erc191 or tip191 `payload` string containing multi-byte UTF-8 characters such that `data.length` used in the prefix (`\x19Ethereum Signed Message:\n${data.length}`) is computed AFTER `TextEncoder().encode(payload)` (so data.length is byte length, correct) — but if instead the wallet/signer that produced the original signature used the JS string `.length` (UTF-16 units) for the prefix during actual signing, the locally recomputed hash via computeSignedErc191Hash diverges from the hash that was actually signed and from the intent_hash the relay returns after `viem`/wallet's `signRaw` re-encodes it? Preconditions: erc191 or tip191 standard, payload string with non-ASCII/multi-byte characters (e.g., emoji), signer implementation using string.length instead of byte length for the prefix. Call sequence: intent-signer-viem signRaw signs prefixed message -> multiPayload built -> computeIntentHash(multiPayload) recomputes via computeSignedErc191Hash -> publishIntent posts payload to relay -> relay recovers signer from signature over relay's own prefix computation and returns intent_hash. Equality broken: computeIntentHash(multiPayload) == intent_hash returned by publishIntent. Impact: Critical — a hash mismatch on a signed, fund-moving intent means the integrator loses the ability to match settlement to the exact signed payload, risking duplicate submission of the same withdrawal/swap intent by the same user. Proof idea: vitest test with payload='🚀' (4-byte UTF-8, 2 UTF-16 units), compute hash both ways, mock publishIntent HTTP response using the byte-length variant, assert computeIntentHash output equals the UTF-16 length variant's hash only if code paths are consistent — demonstrating the divergence.
