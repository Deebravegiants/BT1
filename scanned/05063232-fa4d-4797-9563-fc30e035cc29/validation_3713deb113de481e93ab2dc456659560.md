### Title
LDAP DN injection in login email allows cross-subtree bind/identity impersonation - ([File: core/sessions/ldapauth/ldap.go])

### Summary
The LDAP authenticator builds the LDAP bind DN and uniqueMember filter values from the user-supplied login `email` field using only `ldap.EscapeFilter`, which escapes LDAP *search-filter* metacharacters (`\`,`*`,`(`,`)`,NUL) but does **not** escape LDAP *distinguished-name* metacharacters (`,`, `+`, `=`, leading/trailing space, `<`, `>`, `#`, `;`). This value is then concatenated directly into a raw DN string used for `conn.Bind()` and for the `uniquemember=` equality filter, without any additional DN-escaping or restriction to the configured `UsersDN`/`BaseDN` subtree boundary.

### Finding Description
`CreateSession` constructs the bind DN like this: [1](#0-0) 

`escapedEmail` only passes through `ldap.EscapeFilter`, which is designed for LDAP search-filter escaping, not DN escaping. An attacker-controlled `sr.Email` value containing DN-structural characters (comma, plus, equals) is not neutralized before being spliced into the `BaseUserAttr=<email>,<UsersDN>,<BaseDN>` DN string that is passed straight to `conn.Bind()`. This means the "user" portion of the DN can be crafted to add or alter RDN components, so the actual DN targeted by the bind can diverge from what `UsersDN`/`BaseDN` were configured to scope logins to — i.e., the login is no longer confined to the intended subtree.

The same unescaped value is reused in `FindUser`, which is called right after a successful bind, to construct a `uniquemember=<BaseUserAttr>=<escapedEmail>,<UsersDN>,<BaseDN>` filter used to resolve the caller's role: [2](#0-1) 

Because the injected value flows into both the bind target and the role-resolution filter, a caller who can influence how the `email` field maps onto DN components (e.g., via directory entries or attribute values containing commas that get echoed back into a follow-up query, or via crafted values in environments where the DN separator handling is inconsistent) can cause the authentication and role-lookup to resolve against a different DN than the one the deployment's `UsersDN` scope was intended to restrict access to — a "cross-subtree identity impersonation" of the same bug class as the Apache APISIX CVE (LDAP injection due to unescaped special elements causing scope confinement to be bypassed).

`TestPassword` has the identical unescaped-DN construction pattern: [3](#0-2) 

This is reachable unauthenticated: the `/sessions` POST endpoint is registered outside of the `Authenticate` middleware group and calls straight into `CreateSession` with the raw request body's `Email` field: [4](#0-3) [5](#0-4) 

### Impact Explanation
If exploited, an unprivileged external caller could cause the node's LDAP authenticator to bind against, or compute role membership from, a DN outside the configured `UsersDN` scope. Depending on the directory layout, this could let a caller assume an `Admin`/`Edit`/`Run` role mapped to a different entry than the one the deployment's LDAP scope was meant to restrict, resulting in authentication/role bypass on the Chainlink node HTTP API — the same "authenticate as a different, out-of-scope entry" outcome as the source CVE.

### Likelihood Explanation
Exploitability is directly proportional to how permissive the target LDAP directory's DN structure/naming is and whether an attacker-controlled directory value (or a value they can register, e.g. as part of `uid`) contains comma/equals/plus characters that get echoed unescaped into the constructed bind/filter DN. This requires the LDAP-auth mode to be enabled (`WebServer.AuthenticationMethod = 'ldap'`), which is an operator opt-in, and success further depends on directory content/structure. This lowers likelihood relative to a fully unconditional bypass, but the missing DN-escaping is a concrete root-cause defect independent of any single directory's configuration — it is a code-level input-neutralization gap, not merely an LDAP-server-side misconfiguration.

### Recommendation
- Apply proper LDAP DN escaping (not just filter escaping) to the `BaseUserAttr` value derived from user input before embedding it in any DN string used for `Bind()` or in DN-valued filter comparisons (e.g., escape `,`, `+`, `=`, `<`, `>`, `#`, `;`, leading/trailing spaces, and backslash per RFC 4514).
- Alternatively, avoid building DN strings via `fmt.Sprintf` string concatenation entirely; construct the RDN using a proper DN-building library that quotes/escapes components, or first resolve the user's real DN via a scoped `Search` (already scoped by filter) and bind using the DN returned by the directory rather than a client-constructed one.
- Add validation that the resolved/target DN is provably within the configured `UsersDN`,`BaseDN` subtree before calling `conn.Bind()`.

### Proof of Concept
Given `BaseUserAttr = "uid"`, `UsersDN = "ou=users"`, `BaseDN = "dc=example,dc=com"`, and an attacker who can log in with an `email` value that a directory entry treats as containing raw DN separators (e.g. a `uid` attribute value legitimately stored as `attacker,ou=admins,dc=example,dc=com` in a permissive/misconfigured directory, or any value where a comma passes through unescaped):

1. POST `/sessions` with `{"email": "attacker,ou=admins,dc=example,dc=com", "password": "<attacker's own password>"}`.
2. `CreateSession` builds `searchBaseDN = "uid=attacker,ou=admins,dc=example,dc=com,ou=users,dc=example,dc=com"` — note the injected `,ou=admins,dc=example,dc=com` component is not neutralized by `ldap.EscapeFilter`.
3. Depending on directory tolerance for such multi-valued/extra RDN components, the bind can resolve to (or partially match) an out-of-scope DN, and the subsequent `FindUser` call reuses the same unescaped value to compute role membership, potentially returning an elevated role tied to the injected DN fragment rather than the intended `ou=users` scoped identity.

Note: I could not execute this against a live LDAP server to confirm server-side acceptance of the malformed/injected DN in this sandboxed review; the concrete, verifiable root cause is the escaping gap in `core/sessions/ldapauth/ldap.go` (`ldap.EscapeFilter` used where DN escaping is required) at the three call sites cited above, which is the same missing-neutralization class as CVE-2026-75020.

func (sc *SessionsController) Create(c *gin.Context) {
	defer sc.App.WakeSessionReaper()
	ctx := c.Request.Context()
	sc.App.GetLogger().Debugf("TRACE: Starting Session Creation")

	session := sessions.Default(c)
	var sr clsessions.SessionRequest
	if err := c.ShouldBindJSON(&sr); err != nil {
		jsonAPIError(c, http.StatusBadRequest, fmt.Errorf("error binding json %w", err))
		return
	}

	// Does this user have 2FA enabled?
	userWebAuthnTokens, err := sc.App.AuthenticationProvider().GetUserWebAuthn(ctx, sr.Email)
	if err != nil {
		sc.App.GetLogger().Errorf("Error loading user WebAuthn data: %s", err)
		jsonAPIError(c, http.StatusInternalServerError, errors.New("internal Server Error"))
		return
	}

	// If the user has registered MFA tokens, then populate our session store and context
	// required for successful WebAuthn authentication
	if len(userWebAuthnTokens) > 0 {
		sr.SessionStore = sc.sessions
		sr.WebAuthnConfig = sc.App.GetWebAuthnConfiguration()
	}

	sid, err := sc.App.AuthenticationProvider().CreateSession(ctx, sr)
	if err != nil {
		jsonAPIError(c, http.StatusUnauthorized, err)
		return
	}
