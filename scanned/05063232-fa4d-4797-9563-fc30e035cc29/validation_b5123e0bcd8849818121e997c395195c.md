### Title
Edit-role users can achieve arbitrary OS command execution via `standardcapabilities` job spec `command` field - (File: core/services/standardcapabilities/delegate.go)

### Summary
Authenticated Chainlink node users holding the `edit` role (a mid-tier, non-admin RBAC role, analogous to CVE-2021-23258's "Developer" role) can create a job of type `standardcapabilities` through the standard job-creation API and set the `command` field to an arbitrary filesystem path. That path is passed unmodified to `os/exec.Command` and executed as a subprocess by the node process, with no allowlist enforcement by default.

### Finding Description
Chainlink's RBAC defines four roles: `admin`, `edit`, `run`, `view` [1](#0-0) . The job-creation route only requires the `edit` role, not `admin`: [2](#0-1) 

When the submitted job TOML has `type = "standardcapabilities"`, the controller calls `standardcapabilities.ValidatedStandardCapabilitiesSpec`, whose only validation on the `command` field is that it is non-empty — there is no allowlist, path restriction, or admin-only gate at this layer: [3](#0-2) [4](#0-3) 

Once the job is created, `Delegate.ServicesForSpec` reads `spec.StandardCapabilitiesSpec.Command` and, when no local allowlist config (`localCfg`) is present, passes the command straight through with no restriction (confirmed in delegate tests: `"nil localCfg allows all capabilities"`): [5](#0-4) [6](#0-5) 

The command ultimately reaches `plugins.NewCmdFactory`, which builds an `exec.Cmd` directly from the attacker-supplied string: [7](#0-6) 

This is functionally equivalent to CVE-2021-23258's bug class: a sub-admin, authenticated role (Developer/Edit) can supply an expression/command that the server executes as an OS-level process without additional privilege checks or restriction, resulting in remote code execution on the node host.

### Impact Explanation
An `edit`-role user — a role explicitly designed to be less privileged than `admin` and intended only to create/manage jobs, bridges, and external initiators — can execute an arbitrary binary/script on the Chainlink node's host operating system. Because the LOOP plugin subprocess runs with the same OS privileges as the Chainlink node process, this grants full RCE capability: reading secrets, keystore material, environment variables, and potentially pivoting to other infrastructure reachable from the node. This is a full compromise of confidentiality, integrity, and availability of the node, matching the High severity of the reference CVE.

### Likelihood Explanation
Likelihood is high for any deployment that grants `edit` (or higher) role API tokens to users who should not have OS-level access — a very common operational pattern (e.g., delegating job management to a junior operator or automation account). The attack requires only a valid session/API token with `edit` role and one authenticated `POST /v2/jobs` call; no additional bypass is needed since the role gate for job creation is `RequiresEditRole`, not `RequiresAdminRole`.

### Recommendation
- Restrict creation of `standardcapabilities` job specs (and any other job type that accepts a raw `command` binary path) to `admin`-role users only, via `auth.RequiresAdminRole` in `core/web/router.go`.
- Enforce a server-side allowlist of permitted capability binaries/paths (similar to the existing `RegistryBasedLaunchAllowlist` check) unconditionally, rather than only when `localCfg` happens to be configured.
- Consider sandboxing or otherwise constraining subprocess execution paths (e.g., restricting to a fixed, non-writable capabilities directory) rather than trusting a user-supplied path verbatim.

### Proof of Concept
1. Obtain a session or API token for a user with the `edit` role (not `admin`).
2. Submit:
```
POST /v2/jobs
Content-Type: application/json

{
  "toml": "type = \"standardcapabilities\"\nschemaVersion = 1\nname = \"poc\"\nexternalJobID = \"11111111-1111-1111-1111-111111111111\"\nforwardingAllowed = false\ncommand = \"/tmp/attacker_binary\"\nconfig = \"\"\"\"\"\""
}
```
3. Once the job is created and started, the node process invokes `exec.Command("/tmp/attacker_binary")` (via `plugins.NewCmdFactory`), executing the attacker-supplied binary with the node's OS privileges — achieving RCE without ever needing `admin` role.

func (d *Delegate) ServicesForSpec(ctx context.Context, spec job.Job) ([]job.ServiceCtx, error) {
	command := spec.StandardCapabilitiesSpec.Command
	configJSON := spec.StandardCapabilitiesSpec.Config

	if d.localCfg != nil {
		capabilityID := conversions.GetCapabilityIDFromCommand(command, configJSON)
		if capabilityID != "" && d.localCfg.IsAllowlisted(capabilityID) {
			return nil, fmt.Errorf(
				"capability %q is in the RegistryBasedLaunchAllowlist and will be started from the on-chain registry; "+
					"remove the job spec and let the LocalCapabilityManager handle it via [Capabilities.Local] TOML config",
				capabilityID,
			)
		}
	}

	// Job-spec boot path: capability DON ID is not carried in the spec, so the
	// host best-effort resolves it from the capability registry inside NewServices.
	// On a node that belongs to multiple DONs running the same capability, the
	// registry lookup cannot disambiguate which DON this plugin serves, so it
	// resolves to 0 and the plugin falls back to the consumer workflow's DON ID
	// for event labeling. Carrying the DON ID in the job spec would close that
	// gap; tracked as a follow-up. See CRE-4409.
	// The job-spec launch path has no registry OCR3 config to thread; NewServices falls
	// back to the cached OCRConfigService when available.
	return d.NewServices(ctx, command, configJSON, spec.ID, spec.Name.ValueOrZero(), spec.ExternalJobID, &spec.StandardCapabilitiesSpec.OracleFactory, 0, nil)

func ValidatedStandardCapabilitiesSpec(tomlString string) (job.Job, error) {
	jb := job.Job{ExternalJobID: uuid.New()}

	tree, err := toml.Load(tomlString)
	if err != nil {
		return jb, errors.Wrap(err, "toml error on load standard capabilities")
	}

	err = tree.Unmarshal(&jb)
	if err != nil {
		return jb, errors.Wrap(err, "toml unmarshal error on standard capabilities spec")
	}

	var spec job.StandardCapabilitiesSpec
	err = tree.Unmarshal(&spec)
	if err != nil {
		return jb, errors.Wrap(err, "toml unmarshal error on standard capabilities job")
	}

	jb.StandardCapabilitiesSpec = &spec
	if jb.Type != job.StandardCapabilities {
		return jb, errors.Errorf("standard capabilities unsupported job type %s", jb.Type)
	}

	if len(jb.StandardCapabilitiesSpec.Command) == 0 {
		return jb, errors.Errorf("standard capabilities command must be set")
	}

// NewCmdFactory is helper to ensure synchronization between the loop registry and os cmd to exec the LOOP
func NewCmdFactory(register func(id string) (*RegisteredLoop, error), lcfg CmdConfig) (func() *exec.Cmd, error) {
	registeredLoop, err := register(lcfg.ID)
	if err != nil {
		return nil, fmt.Errorf("failed to register %s LOOP plugin: %w", lcfg.ID, err)
	}
	return func() *exec.Cmd {
		cmd := exec.Command(lcfg.Cmd) //#nosec G204 -- we control the value of the cmd so the lint/sec error is a false positive
		cmd.Env = append(cmd.Env, lcfg.Env...)
		cmd.Env = append(cmd.Env, registeredLoop.EnvCfg.AsCmdEnv()...)
		return cmd
	}, nil
