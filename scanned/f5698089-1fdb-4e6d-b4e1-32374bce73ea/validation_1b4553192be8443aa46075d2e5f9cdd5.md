### Title
Missing role-based access control on External Initiator listing endpoint discloses initiator credentials to view-only users - (File: core/web/router.go)

### Summary
The `GET /v2/external_initiators` endpoint, which returns each configured External Initiator's `AccessKey` and `OutgoingToken`, is registered without any role gate, while every other mutating operation on the same resource (`Create`, `Destroy`) explicitly requires `auth.RequiresEditRole`. Any authenticated node API user — including the lowest-privilege `view` role — can therefore read these initiator credentials, which is the closest reachable analog in this codebase to the reported bug class of "state-changing/sensitive function reachable without proper role/owner check."

### Finding Description
In `core/web/router.go`, the `v2Routes` function wires up the External Initiators controller as follows: [1](#0-0) 

`Index` is mounted directly on `authv2` (which only requires the generic `auth.Authenticate` session/token check) with no `auth.RequiresEditRole`/`RequiresAdminRole` wrapper, unlike `Create` and `Destroy`, which are explicitly wrapped in `auth.RequiresEditRole`. This means any of the four defined roles (`view`, `run`, `edit`, `admin`) can call this endpoint.

The handler itself performs no additional authorization check: [2](#0-1) 

The returned resource includes the initiator's `AccessKey` and `OutgoingToken`: [3](#0-2) 

`AccessKey` is one half of the credential pair used by an External Initiator to authenticate incoming requests to the node (paired with a `Secret`, verified via `AuthenticateExternalInitiator`): [4](#0-3) 

The role-enforcement middleware itself is defined here, showing `view` is the lowest role and is exactly the role excluded from `RequiresRunRole`/`RequiresEditRole`, yet `Index` bypasses these checks entirely: [5](#0-4) 

### Impact Explanation
A user provisioned with only `view`-level node API access (intended for read-only dashboards/monitoring) can enumerate all configured External Initiators and obtain their `AccessKey` and `OutgoingToken` values. `AccessKey` is required (together with the initiator's `Secret`, which is not returned) to authenticate as that initiator against node endpoints such as `/v2/ping` and job-run trigger endpoints; disclosure of `AccessKey` reduces the search space for an attacker and confirms live initiator identities, and `OutgoingToken` is used to validate webhook callbacks originating from the node to the initiator's URL, so its disclosure undermines the integrity of that outbound trust relationship. This is inconsistent with the project's own intended privilege model, where `Create`/`Destroy` of the same resource require `edit` role — read access to the resulting secrets should be at least as restricted.

### Likelihood Explanation
Likelihood is high for any deployment that provisions `view`-role API users (a supported, documented role) alongside External Initiators (a supported, though optionally-enabled, feature via `ExternalInitiatorsEnabled` config). No additional bypass or race condition is required — a simple authenticated `GET` request suffices.

### Recommendation
Wrap `Index` with the same minimum role required for managing External Initiators (`auth.RequiresEditRole`, matching `Create`/`Destroy`), or at minimum `auth.RequiresRunRole`, and consider whether `AccessKey`/`OutgoingToken` should be redacted for lower-privilege roles regardless:
```diff
- authv2.GET("/external_initiators", paginatedRequest(eia.Index))
+ authv2.GET("/external_initiators", auth.RequiresEditRole(paginatedRequest(eia.Index)))
```

### Proof of Concept
1. Create a node API user with role `view` (e.g., via `POST /v2/users` as admin with `"role":"view"`).
2. Authenticate as that `view` user (`POST /v2/sessions`).
3. As that session, call `GET /v2/external_initiators`.
4. Observe the response includes `accessKey` and `outgoingToken` for every configured External Initiator, despite the `view` role being unable to create, modify, or delete anything else in the system (confirmed by `TestRBAC_Routemap_Edit`/`TestRBAC_Routemap_Admin` test expectations in `core/web/auth/auth_test.go`, which don't cover `GET /v2/external_initiators` at all — it's absent from `routesRolesMap`, indicating it was never brought under the RBAC test matrix). [6](#0-5)

func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)

// Implements authMethod
func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
