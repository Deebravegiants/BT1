### Title
Increasing `WebServer.LDAP.UserAPITokenDuration` / `WebServer.OIDC.UserAPITokenDuration` retroactively revives already-issued (and possibly compromised/expired) API tokens - (File: core/sessions/ldapauth/ldap.go, core/sessions/oidcauth/oidc.go)

### Summary
`FindUserByAPIToken` in both the LDAP and OIDC authentication providers validates an API token's expiry by comparing `created_at + <current UserAPITokenDuration>` against `now()`, where `UserAPITokenDuration` is read live from the node's mutable config at request time rather than being fixed at the time the token was minted. This is structurally identical to the Footium bug: a mutable global "limit" (`maxGenerationId` / `UserAPITokenDuration`) is applied retroactively to already-created historical records (previously-minted academy players / previously-issued API tokens) instead of the value that was in force when those records were created, allowing state that should be permanently "closed" (an expired token, a past season) to become valid again.

### Finding Description
`FindUserByAPIToken` for LDAP: [1](#0-0) 

and for OIDC: [2](#0-1) 

both issue a query of the form:
```sql
SELECT ... , created_at + $2 >= now() as valid FROM ..._user_api_tokens WHERE token_key = $1
```
with `$2` bound to `config.UserAPITokenDuration().Duration()` fetched fresh on every call, instead of an absolute expiry timestamp recorded at token-creation time (`SetAuthToken`/token insert only stores `created_at`, see `core/sessions/ldapauth/ldap.go:571-583`). There is no `expires_at` column or duration snapshot stored per token.

The background reaper/sync jobs (`core/sessions/ldapauth/sync.go:100-104`, `core/sessions/oidcauth/reaper.go:37-44`) purge stale rows using the *same currently configured* duration, so purging (deletion) of an already-expired token is lazy and itself depends on the current live config value — a token is only actually deleted once a reap cycle or a failed lookup runs against it while the duration is still short.

Consequently, if an operator increases `WebServer.LDAP.UserAPITokenDuration` or `WebServer.OIDC.UserAPITokenDuration` (e.g. via a config reload) for any reason, every previously-issued token whose row has not yet been purged — including tokens that were already expired and that a client should no longer be able to use — instantly becomes valid again for a fresh `created_at + newDuration` window. This mirrors the Footium root cause exactly: the check enforces a *currently configured* limit against records created under a *different, expected* limit, with no per-record snapshot of the limit that applied at creation time.

### Impact Explanation
This is a concrete authentication bypass: any party holding an old/previously expired API access key + secret pair (e.g., a leaked credential from a departed employee, a rotated integration, or an incident-response revocation scenario) is unprivileged with respect to the current system state, since their token is supposed to be expired/purged. If the duration is subsequently raised, that unprivileged holder regains full authenticated access via `AuthenticateByToken` → `FindUserByAPIToken`: [3](#0-2) 
with the role the token was originally granted, without re-issuance or re-authentication.

### Likelihood Explanation
Requires only a legitimate, plausible administrative action (raising `UserAPITokenDuration`, e.g., to extend session length for current users) combined with the presence of unreaped old token rows in `ldap_user_api_tokens` / `oidc_user_api_tokens` — there is no requirement that the config change be malicious. Reaping is lazy/interval based (`UpstreamSyncInterval`, background sleeper tasks), so stale rows can persist for a meaningful window before the increased duration takes effect. Likelihood is moderate: it depends on an operator changing the duration setting, but no code defect prevents it, and nothing forces re-authentication or explicit expiry-stamping on tokens.

### Recommendation
Store an absolute `expires_at` (or the duration value) at token-creation time and compare against that stored value rather than re-deriving expiry from the live config on every lookup. This ensures a config change to `UserAPITokenDuration` only affects newly issued tokens, matching the documented intent ("UserAPITokenDuration is the duration of time an API token is active for before expiring") and preventing retroactive revival of already-expired tokens.

### Proof of Concept
1. Configure `WebServer.LDAP.UserAPITokenDuration = '1h'` (or the OIDC equivalent) and issue an API token for a user (`SetAuthToken` inserts a row with `created_at = now()`). [4](#0-3) 
2. Wait/simulate more than 1 hour passing without the token being queried or reaped (e.g., `UpstreamSyncInterval` disabled or long).
3. An attacker holding the leaked access key/secret calls the token-authenticated API; `FindUserByAPIToken` returns `Valid = false` since `created_at + 1h < now()`, and the row is purged — attack fails as expected.
4. Instead, before the attacker's request/any reap cycle runs, the operator raises `UserAPITokenDuration` to `'240h'` for legitimate reasons (extending active users' sessions).
5. The attacker replays the same old (previously invalid) key/secret pair to `AuthenticateByToken`; the query now evaluates `created_at + 240h >= now()` as true, `FindUserByAPIToken` returns the user successfully, and `AuthenticateUserByToken` succeeds — the attacker gains authenticated access using a token that should have remained permanently expired. 		}
		return sessions.User{}, sessions.ErrUserSessionExpired
	}

func (oi *oidcAuthenticator) FindUserByAPIToken(ctx context.Context, apiToken string) (clsessions.User, error) {
	if !oi.config.UserAPITokenEnabled() {
		return clsessions.User{}, errors.New("API token is not enabled")
	}

	var foundUser clsessions.User
	err := sqlutil.TransactDataSource(ctx, oi.ds, nil, func(tx sqlutil.DataSource) error {
		// Query the oidc user API token table for given token, user role and email are cached so
		// no further upstream OIDC query is performed, sessions and tokens are synced against the upstream server
		// via the UpstreamSyncInterval config and reaper.go sync implementation
		var foundUserToken struct {
			UserEmail string
			UserRole  clsessions.UserRole
			Valid     bool
		}
		if err := tx.GetContext(ctx, &foundUserToken,
			"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM oidc_user_api_tokens WHERE token_key = $1",
			apiToken, oi.config.UserAPITokenDuration().Duration(),
		); err != nil {
			return err
		}
		if !foundUserToken.Valid {
			return clsessions.ErrUserSessionExpired
		}
		foundUser = clsessions.User{
			Email: foundUserToken.UserEmail,
			Role:  foundUserToken.UserRole,
		}
		return nil
	})
	if err != nil {
		if errors.Is(err, clsessions.ErrUserSessionExpired) {
			// API Token expired, purge
			if _, execErr := oi.ds.ExecContext(ctx, "DELETE FROM oidc_user_api_tokens WHERE token_key = $1", apiToken); execErr != nil {
				oi.lggr.Errorf("error purging stale oidc API token session: %v", execErr)
			}
		}
		return clsessions.User{}, err
	}
	return foundUser, nil
}

func AuthenticateByToken(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	token := &auth.Token{
		AccessKey: c.GetHeader(APIKey),
		Secret:    c.GetHeader(APISecret),
	}
	if token.AccessKey == "" {
		return auth.ErrorAuthFailed
	}

	if token.Secret == "" {
		return auth.ErrorAuthFailed
	}

	// We need to first load the user row so we can compare tokens using the stored salt
	user, err := authr.FindUserByAPIToken(ctx, token.AccessKey)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) || errors.Is(err, clsessions.ErrUserSessionExpired) {
			return auth.ErrorAuthFailed
		}
		return err
	}

	ok, err := clsessions.AuthenticateUserByToken(token, &user)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionUserKey, &user)

	return nil
}
