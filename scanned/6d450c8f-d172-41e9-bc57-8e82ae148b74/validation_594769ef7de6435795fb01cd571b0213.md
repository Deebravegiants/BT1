### Title
Unbounded GraphQL pagination `limit` argument allows authenticated read-only user to trigger large-memory-allocation DoS - ([File: core/web/resolver/helpers.go])

### Summary
The MongoDB advisory describes a DoS where a user with read access can craft a query whose evaluation builds very large intermediate in-memory objects, exhausting RAM and crashing the server. The Chainlink node GraphQL API (`/query`) has a directly analogous pattern: several read queries accept a client-supplied `Limit` argument that is passed to `pageLimit()` and then straight into the ORM query without any upper bound, letting an authenticated (any-role) API user request an arbitrarily large result set that must be materialized in memory.

### Finding Description
`pageLimit` simply returns the caller-supplied limit, or a small default if none is given, with no maximum cap: [1](#0-0) 

This helper is used unguarded (i.e., not passed through `min(..., someCap)`) by multiple `Resolver` query methods that only require a valid authenticated session, not any special role:

- `Bridges` — passes `limit` straight to `r.App.BridgeORM().BridgeTypes(ctx, offset, limit)`: [2](#0-1) 
- `Jobs` — passes `limit` straight to `r.App.JobORM().FindJobs(ctx, offset, limit)`: [3](#0-2) 
- `Nodes`, `JobRuns` — same unguarded pattern: [4](#0-3) 
- `EthTransactions`, `EthTransactionsAttempts` — same unguarded pattern: [5](#0-4) 

By contrast, `JobResolver.Runs` (a nested field resolver) is explicitly capped: `limit := min(pageLimit(args.Limit), 100)`: [6](#0-5) 

This shows the codebase is aware that limits must be bounded in at least one place, but the top-level `Resolver` query methods for bridges, jobs, nodes, job runs, and ETH transactions/attempts were not given the same treatment. The only authorization gate on these queries is `authenticateUser(ctx)`, which merely checks that the caller is a logged-in API user — it does not restrict the `Limit` value: [7](#0-6) 

The GraphQL endpoint itself only enforces a query-depth limit (`graphql.MaxDepth(10)`), not a result-size/complexity limit, and there is no per-request response-size cap: [8](#0-7) 

An authenticated user (any role with API access, since `authenticateUser` does not check for a specific privilege level here) can send a single GraphQL query such as `{ ethTransactionsAttempts(limit: 2147483647) { results { hex } } }` or `{ jobRuns(limit: 2147483647) { results { id } } }`. Because `int32GQLID`/`pageLimit` do not cap the value, this is forwarded to the ORM layer (`TxmStorageService().TxAttempts`, `JobORM().PipelineRuns`, etc.), which will attempt to load and materialize that many rows (transaction attempts, pipeline runs, ETH transactions) into memory as Go structs before the resolver even returns, and then the GraphQL layer will build the full JSON response tree for all of them in memory as well.

### Impact Explanation
This is directly analogous to the MongoDB bug class: a query built by a read-privileged actor forces the server to allocate an unbounded/very large amount of memory, resulting in denial of service (OOM crash) of the Chainlink node's core process — the same process that runs job execution, key management, and transaction management. Because the node process is monolithic, an OOM crash here takes down all node functions, not just the API.

### Likelihood Explanation
Any user with a valid Chainlink node API session (any role able to reach the GraphQL `/query` endpoint, gated only by `AuthenticateGQL`) can send this request with no special privilege elevation. It is a single HTTP request, trivial to reproduce, and requires no cooperation from other nodes/peers — this matches "unprivileged-actor... read access" from the report, satisfying the requested scope (node API authentication path, internet/API-facing handler with no request quota/size validation).

### Recommendation
Cap all top-level pagination `Limit` arguments in `core/web/resolver/query.go` (Bridges, Jobs, Nodes, JobRuns, EthTransactions, EthTransactionsAttempts, and any others using `pageLimit`) the same way `JobResolver.Runs` does, e.g. `limit := min(pageLimit(args.Limit), 100)`, or enforce the cap centrally inside `pageLimit` itself in `core/web/resolver/helpers.go`. Additionally, consider adding a GraphQL query cost/complexity limit at the schema level (`core/web/router.go`) in addition to the existing `MaxDepth(10)`.

### Proof of Concept
1. Log in with any valid Chainlink node API user session (any role that passes `AuthenticateGQL`).
2. Send a POST to `/query` with body:
```graphql
{
  ethTransactionsAttempts(limit: 2147483647) {
    results { hash hex gasPrice }
    metadata { total }
  }
}
```
3. Observe the node ORM attempting to load and serialize an unbounded number of `TxAttempt` records into memory, causing excessive memory growth / OOM depending on database size, because `pageLimit` (`core/web/resolver/helpers.go:45-51`) and the corresponding resolver (`core/web/resolver/query.go:555-572`) apply no upper bound on the client-supplied `Limit`.

// Nodes retrieves a paginated list of nodes.
func (r *Resolver) Nodes(ctx context.Context, args struct {
	Offset *int32
	Limit  *int32
}) (*NodesPayloadResolver, error) {
	if err := authenticateUser(ctx); err != nil {
		return nil, err
	}

	offset := pageOffset(args.Offset)
	limit := pageLimit(args.Limit)
	r.App.GetLogger().Debugw("resolver Nodes query", "offset", offset, "limit", limit)
	allNodes, total, err := r.App.GetRelayers().NodeStatuses(ctx, offset, limit)
	r.App.GetLogger().Debugw("resolver Nodes query result", "nodes", allNodes, "total", total, "err", err)

	if err != nil {
		r.App.GetLogger().Errorw("Error creating get nodes status from app", "err", err)
		return nil, err
	}
	npr, warn := NewNodesPayload(allNodes, safeInt32(total))
	if warn != nil {
		r.App.GetLogger().Warnw("Error creating NodesPayloadResolver", "err", warn)
	}
	return npr, nil
}
