### Title
Global, unscoped `requestID` keyspace in the HTTP-trigger gateway handler lets any authenticated caller DoS another workflow's in-flight request - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

### Summary
The Dinari bug class is: an order/request identifier is derived only from client-supplied, non-secret data, so any actor who knows/guesses that value can create a colliding identifier and disrupt the legitimate requester's operation (here, causing the victim's `requestOrder` to be treated as a duplicate and effectively rejected/cancelled). The chainlink analog is the CRE gateway's `httpTriggerHandler`, where the request ID used to key the in-flight-callback map is taken verbatim from the client-controlled JSON-RPC `id` field and is **not namespaced by workflow, workflow owner, or caller**. Any caller who is able to authenticate a JSON-RPC request for *any* workflow (their own) can pick the same `id` string as another user's in-flight request for a *different* workflow, causing the second request to be rejected with a conflict error.

### Finding Description
`HandleUserTriggerRequest` validates and authorizes the request, then calls `setupCallback`, which stores the pending callback keyed solely by the client-supplied `req.ID`: [1](#0-0) [2](#0-1) 

The only validation performed on the ID is that it is non-empty and does not contain `/`: [3](#0-2) 

Because `h.callbacks` is a single flat `map[string]savedCallback` (`requestID -> savedCallback`) shared across all workflows served by the handler instance, the uniqueness check `if _, found := h.callbacks[requestID]; found` at line 423 has no workflow/owner scoping. JWT authorization (`authorizeRequest`) only verifies that a given signed JWT for a workflow hasn't been replayed; it does not tie the plaintext `id` string to a particular workflow or requester, so two entirely different, independently authorized workflows can legitimately submit requests bearing the same `id` value. Whichever request reaches `setupCallback` first wins; the second is rejected with `ErrConflict` and the user sees "requestID: X has already been used": [4](#0-3) 

This mirrors the reported Solidity issue: the collision is enforced on a *value that is not treated as sensitive but happens to be shared/knowable across principals* (there, the order-request hash from public mempool params; here, a bare user-supplied string with no namespacing), and it can be used to force a legitimate operation to fail for someone else. Existing tests explicitly document only the same-workflow duplicate behavior: [5](#0-4) 

but nothing in the code prevents the identical race/collision from being triggered cross-workflow, since the map key carries no workflow/owner context.

### Impact Explanation
Any authenticated CRE workflow owner (an "unprivileged" actor relative to other workflows) can deny service to another workflow's HTTP-triggered execution by front-running with the same request ID, causing the victim's legitimate `workflows.execute` call to be rejected (`ErrConflict`, "in-flight request"). This is a direct availability/DoS impact on the internet-facing gateway's request handling, analogous to the victim's buy order being blocked/cancelled in the original report. It does not require compromising the victim's signing key — only knowledge or a lucky/guessed match of the `id` string, which callers frequently choose from small, low-entropy, or externally observable spaces (sequential counters, timestamps, fixed test strings, or values leaked through logs/support channels).

### Likelihood Explanation
Likelihood is moderate: the attacker needs the JSON-RPC `id` the victim intends to use. Many client SDK/test implementations use predictable or externally-visible IDs (as seen in the repo's own test helpers, e.g. `requestID + uuid.New().String()[0:8]` prefixes, or fixed literals like `"test-request-id"`), and gateways are internet-facing, so a malicious/careless third-party workflow operator racing the same ID string is plausible without any privileged access.

### Recommendation
Scope the in-flight request map (and the duplicate/conflict check) by `(workflowID, requestID)` or `(workflowOwner, requestID)` rather than by the bare client-supplied `requestID`, e.g., use a composite key such as `workflowID + "/" + requestID` (already reserved via the `/` restriction) when indexing `h.callbacks`. This mirrors the report's own recommendation of binding the identifier to the requester (`msg.sender`) rather than relying purely on client-controlled, unscoped values.

### Proof of Concept
1. Workflow A (owned by attacker) and Workflow B (owned by victim) are both registered and reachable via the same gateway HTTP-trigger handler instance.
2. Attacker learns/guesses that the victim's client will send a request with `id = "X"` (e.g., because the victim's SDK uses low-entropy or externally observable IDs).
3. Attacker submits a valid, correctly signed `workflows.execute` request for Workflow A with `id = "X"` just before the victim's request for Workflow B arrives.
4. `setupCallback` stores the attacker's entry under key `"X"` in the shared `h.callbacks` map.
5. The victim's request for Workflow B with the same `id = "X"` arrives and is rejected in `setupCallback` with `jsonrpc.ErrConflict`: "requestID: X has already been used. Ensure the requestID is unique for each request," even though it is unique from the victim's own workflow's perspective — demonstrating the cross-workflow DoS.

func (h *httpTriggerHandler) validateRequestID(ctx context.Context, requestID string, callback handlers.Callback) error {
	if requestID == "" {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "'id' field is required and cannot be empty. Use a new unique request 'id' for each request", callback)
		return errors.New("empty request ID")
	}
	// Request IDs from users must not contain "/", since this character is reserved
	// for internal node-to-node message routing (e.g., "http_action/{workflowID}/{uuid}").
	if strings.Contains(requestID, "/") {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "request ID must not contain '/'", callback)
		return errors.New("request ID must not contain '/'")
	}
	return nil
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
