## Analog Found

### Title
Integer underflow in gateway staleness check allows bypass of message freshness validation - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The NEAR report describes an overflow in unsigned integer horizon arithmetic (`height_within_front_horizon`/`height_within_rear_horizon`) that could wrap around near `u64::MAX`. The chainlink analog is an unsigned-integer arithmetic bug in the gateway's `HandleLegacyUserMessage` staleness check, where an attacker-controlled `int64` timestamp is cast to `uint` and compared against another unsigned subtraction, allowing the freshness check to be defeated via integer wraparound.

### Finding Description
`HandleLegacyUserMessage` performs a staleness check on the incoming `TriggerRequestPayload.Timestamp` field: [1](#0-0) 

```go
if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) { //nolint:gosec // G115...
    ... return "stale message" error ...
}
```

`payload.Timestamp` is a signed `int64` field fully controlled by the caller: [2](#0-1) . The only validation performed before this check is `payload.Timestamp == 0`: [3](#0-2) . Negative values are never rejected.

Because Go's `uint` is unsigned, `uint(payload.Timestamp)` on a negative `int64` wraps around to a value near `math.MaxUint64` (on 64-bit platforms). The comparison `now - maxAge > uint(timestamp)` then evaluates false for any negative timestamp, since the wrapped value is enormous — the staleness check silently passes instead of rejecting the message.

This function is reachable directly from the gateway's public, unauthenticated HTTP user port: `gateway.ProcessRequest` decodes the raw HTTP request, and for legacy requests only calls `msg.Validate()` (structural validation) before dispatching straight into `h.HandleLegacyUserMessage`: [4](#0-3) . There is no cryptographic sender/allowlist check on this legacy path — the code even has a TODO acknowledging this: [5](#0-4) .

After the (bypassable) staleness check, the message is forwarded unmodified to every DON member: [6](#0-5) .

### Impact Explanation
The staleness/freshness check exists specifically to prevent replay of old or malformed trigger messages ("needs to be within certain freshness to be processed" per the schema: [7](#0-6) ). By supplying a negative timestamp, an unprivileged/unauthenticated caller can defeat this replay/staleness protection entirely and have their message forwarded to all DON nodes regardless of freshness intent. This is a concrete bypass of a security control (freshness/anti-replay gate) on an internet-facing gateway handler, matching the "allowlist/quota bypass" and "request impersonation via stale/replayed message" categories.

### Likelihood Explanation
High reachability: this code path is hit by any unauthenticated HTTP client that can reach the gateway's user-facing port and submit a `web_api_trigger` legacy message with a crafted negative `timestamp` field, with no signature or allowlist gate preventing it beforehand on the legacy path.

### Recommendation
Reject negative `payload.Timestamp` values explicitly (in addition to the `== 0` check), and perform the staleness comparison entirely in signed 64-bit arithmetic (`int64`) rather than casting to `uint`, to avoid wraparound for out-of-range attacker-supplied values — mirroring the nearcore fix pattern of avoiding subtraction/casts that can wrap near integer boundaries.

### Proof of Concept
1. Send a JSON-RPC request to the gateway user HTTP port with method `web_api_trigger` and a legacy `api.Message` body whose `TriggerRequestPayload.Timestamp` is set to a negative value (e.g. `-1`).
2. `HandleLegacyUserMessage` only checks `payload.Timestamp == 0` before the staleness check, so `-1` passes that gate: [3](#0-2) .
3. `uint(-1)` becomes `math.MaxUint64` (or `math.MaxUint32` on 32-bit), which is always `>=` the left-hand side, so `now - maxAge > uint(timestamp)` is false and the "stale message" branch is skipped: [8](#0-7) .
4. The message is forwarded to all DON members despite having an invalid/out-of-range timestamp, bypassing the intended freshness/anti-replay control: [9](#0-8) .
