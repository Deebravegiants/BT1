### Title
Stale error variable returned as `nil` on empty WebSocket challenge causes silent connection-establishment failure to be reported as success - ([File: core/services/gateway/network/wsclient.go])

### Summary
`webSocketClient.Connect` in `core/services/gateway/network/wsclient.go` reuses the `err` variable across multiple independent operations (`DialContext`, header inspection, challenge decode, challenge response) without resetting it before each new check, mirroring the CVE-2016-10130 root cause in libgit2's `http_connect` (a stale error value from a *prior successful* operation is returned as the result of a *later* failure branch).

### Finding Description
In `Connect`, after a successful `DialContext` call (`err == nil`), the code checks whether the server-supplied challenge header is empty: [1](#0-0) 

When `challengeStr == ""`, the function logs `"empty challenge"`, closes the connection, and executes `return nil, err` — but `err` at this point is still the `nil` value left over from the earlier successful `DialContext` call at line 51, not a new error describing the empty-challenge condition. This is the same bug class as CVE-2016-10130: an error-handling branch returns a clobbered/stale error variable instead of a fresh one representing the actual failure, so callers see `(nil, nil)` for what is really a failure.

### Impact Explanation
The immediate, concretely observable defect is that `Connect` returns a `nil` connection together with a `nil` error when the gateway/server fails to supply an auth challenge header. Any caller written in the conventional Go idiom (`if err != nil { ... }` to detect failure) will not detect the failure and may proceed to use a `nil *websocket.Conn`, producing at minimum a nil-pointer panic on the connector node, and at worst causing failure/success confusion for the connection-authentication handshake between a chainlink node connector and its gateway. This affects the trust decision at the core of node ↔ gateway session/authentication handling.

### Likelihood Explanation
Triggering this path only requires an entity able to respond to the WebSocket upgrade handshake without setting the `WsServerHandshakeChallengeHeaderName` header — i.e., a gateway endpoint (or anything positioned to answer at the configured gateway URL) that completes the HTTP upgrade but omits/strips the challenge header. This is a straightforward response-shaping action, not a deep network-layer or timing exploit, making it reasonably reachable by whatever entity accepts the WS connection from the node connector.

### Recommendation
In the `challengeStr == ""` branch, construct and return a new, descriptive error instead of reusing the (nil) `err` variable, e.g. `return nil, errors.New("WebSocketClient: empty challenge header")`, or explicitly assign a fresh error before the log/return. More generally, avoid reusing a single `err` variable across sequential, independently-fallible operations in this function; scope each check with its own error variable or ensure the value is explicitly reset immediately before each new fallible call to prevent silent success/failure confusion.

### Proof of Concept
1. Stand up (or compromise) a WebSocket endpoint at the URL the connector dials.
2. Respond to the upgrade request with a normal `101 Switching Protocols` response, but omit the `WsServerHandshakeChallengeHeaderName` header (or ensure it is empty).
3. Have `webSocketClient.Connect` (as invoked from `core/services/gateway/connector/connector.go`) attempt the connection: `DialContext` succeeds (`err == nil`), then `resp.Header.Get(WsServerHandshakeChallengeHeaderName)` returns `""`, and the function returns `nil, nil` (see [2](#0-1) ).
4. A caller checking only `if err != nil` will treat this as connection success while holding a `nil` `*websocket.Conn`, leading to a nil-pointer dereference or unhandled failure state instead of a clear, reportable authentication error.
