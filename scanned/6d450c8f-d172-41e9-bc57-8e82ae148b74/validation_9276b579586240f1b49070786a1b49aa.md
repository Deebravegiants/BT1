### Title
Gateway vault response aggregator silently tolerates missing `requestId` in signed OCR payload, bypassing the request-ID match check - ([File: core/services/gateway/handlers/vault/aggregator.go])

### Summary
The gateway's vault response aggregator verifies OCR signatures on a vault node response, then attempts to bind that signed response to the specific client `requestID` it is currently waiting on by comparing an embedded `payloadRequestID`. When the embedded ID is empty, the comparison is skipped entirely and the response is accepted as valid for the pending request — mirroring the "assume success on failure" pattern from the reported Cooler.sol bug, where an unchecked/failed operation is silently treated as if it had succeeded, letting the caller proceed on invalid state.

### Finding Description
`validateUsingSignatures` in `core/services/gateway/handlers/vault/aggregator.go` performs OCR signature verification and then extracts the request ID embedded in the signed payload: [1](#0-0) 

Immediately after, the binding check that is supposed to guarantee the signed payload actually corresponds to the request the gateway is waiting on is conditioned on the extracted ID being non-empty: [2](#0-1) 

The comment explains the intent — "Temporarily tolerate signed OCR reports from vault nodes that have not upgraded to include requestId in the signed payload" — but the effect is that whenever `payloadRequestID == ""`, the code takes the same "success" path as when the IDs genuinely match, exactly analogous to the reported pattern where a transfer's return value/failure is not checked and the caller proceeds as though the operation succeeded. Here, instead of an ERC20 `transferFrom` return value being ignored, it is the request-ID binding check that is ignored/short-circuited whenever the embedded ID happens to be empty. Because signature verification alone (`vaultcommon.ValidateSignatures`) does not assert which specific client request the OCR report was produced for, an empty `payloadRequestID` collapses the identity check to a no-op, and the aggregator returns the response as authoritative for the caller's currently pending `requestID`: [3](#0-2) 

`HandleNodeMessage` in `core/services/gateway/handlers/vault/handler.go` calls this aggregator path and, on success, forwards the resulting response straight to the waiting user callback for `ar.req.ID` without any additional binding of the payload to that specific request: [4](#0-3) 

This is reachable purely from the unprivileged gateway-facing user request path: any user submitting a vault secrets request (`SecretsCreate`/`Update`/`Delete`/`List`) via `HandleJSONRPCUserMessage` creates an `activeRequest` keyed by their own `req.ID`, and any signed node response that lands on that exact `req.ID` bucket with a signature-valid but requestId-empty payload will be accepted: [5](#0-4) 

### Impact Explanation
If the embedded requestId can legitimately be empty (per the comment, for "vault nodes that have not upgraded"), the gateway loses its cross-request binding guarantee for that class of responses. A signed OCR response intended for a different request/owner, or replayed from a prior response, could be matched to an unrelated pending request bucket as long as the outer envelope `ID` used by `HandleNodeMessage`/`getActiveRequest` lines up — collapsing the defense-in-depth check that was specifically added (per the `errSignedPayloadRequestIDMismatch` mechanism and metric `signed_payload_request_id_mismatch`) to catch this exact class of cross-request/cross-user response confusion. This weakens the vault gateway's guarantee that a given user only receives responses to their own secrets requests.

### Likelihood Explanation
Likelihood depends entirely on whether any node in the DON set can currently produce (or be coerced/downgraded to produce) a signed payload with an empty requestId — the code comment states this is an accepted/expected transitional state ("vault nodes that have not upgraded"), meaning the bypass condition is not theoretical but an actively-tolerated production configuration per the linked ticket (CRE-4875). As long as such nodes exist in a DON, every signed response from them silently skips the requestId binding check.

### Recommendation
Do not treat an empty `payloadRequestID` as "match anything." Either:
1. Reject (or route to a stricter path/quorum-only validation) any signed response whose payload lacks a requestId, rather than accepting it as bound to the current request, or
2. Track an explicit allowlist/expiry for the "legacy unupgraded node" tolerance (e.g., a feature flag scoped to specific, verified node addresses) instead of a blanket string-emptiness check that any signer can trigger.
Once all vault nodes are confirmed upgraded (per the CRE-4875 ticket referenced in the code), remove the tolerance entirely so the check in `aggregator.go` lines 277-281 is unconditional.

### Proof of Concept
1. A user submits a `vaulttypes.MethodSecretsCreate` request with `req.ID = "victim-req"` through `handler.HandleJSONRPCUserMessage`, creating an `activeRequest` keyed by `"victim-req"`.
2. A DON node (any node not yet upgraded to embed `requestId`, per the code's stated tolerance) returns a validly-signed `SignedOCRResponse` whose envelope `ID` is `"victim-req"` but whose embedded payload was actually produced/signed for a different request, resulting in `payloadRequestID == ""` after decoding via `vaultutils.SignedPayloadRequestID`.
3. In `validateUsingSignatures`, signature verification (`vaulttypes.ValidateSignatures`) passes because the signature itself is valid for that node; then `payloadRequestID != "" && payloadRequestID != requestID` evaluates to `false` (since `payloadRequestID == ""`), skipping `errSignedPayloadRequestIDMismatch` and returning `resp` as valid for `"victim-req"`.
4. `HandleNodeMessage` forwards this response — whose content is not verifiably bound to `"victim-req"` — to the user's callback as the definitive response for their request: [2](#0-1) [6](#0-5)

	err := a.unmarshal(bytes.NewReader(*resp.Result), r)

		return nil, err
	}

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		// Arbitrary limit to prevent abuse
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	h.lggr.Debugw("handling vault request", "method", req.Method, "requestID", req.ID, "request", req)
	if req.Method == vaulttypes.MethodPublicKeyGet {
		// Public key requests don't require authorization,
		// Let's process this request right away.
		// Note we cache this value quite aggressively so don't need to worry about DoS.
		publicKeyResponseBytes, cachedPublicKey := h.getCachedPublicKey()
		if cachedPublicKey == nil {
			// Not found in cache. Fetch from nodes.
			ar, err := h.newActiveRequest(req, callback)
			if err != nil {
				h.lggr.Errorw("failed to create new activeRequest", "error", err)
				return err
			}
			return h.handlePublicKeyGet(ctx, ar)
		}
		h.lggr.Debugw("returning cached public key response")
		return h.handlePublicKeyGetSynchronously(ctx, req, publicKeyResponseBytes, callback)
	}

	if !vaulttypes.IsGatewaySecretsMethod(req.Method) {
		return h.sendImmediateUserResponse(ctx, req, callback, api.UnsupportedMethodError, errors.New("this method is unsupported: "+req.Method))
	}

	_, cachedPublicKey := h.getCachedPublicKey()
	authorized, err := h.requestProcessor.ProcessRequest(ctx, &req, cachedPublicKey)
	if err != nil {
		if vaultcap.IsInvalidVaultParamsError(err) {
			return h.sendImmediateUserResponse(ctx, req, callback, api.InvalidParamsError, err)
		}
		h.lggr.Errorw("request not authorized", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "", "error", err)
		return errors.New("request not authorized: " + err.Error())
	}
	authorizedOwner := authorized.AuthResult.AuthorizedOwner()

	h.lggr.Debugw("handling authorized vault request", "method", req.Method, "requestID", req.ID, "authorizedOwner", authorizedOwner)
	ar, activeRequestErr := h.newActiveRequest(req, callback)
	if activeRequestErr != nil {
		return activeRequestErr
	}

	switch req.Method {
	case vaulttypes.MethodSecretsCreate:
		return h.handleSecretsCreate(ctx, ar)
	case vaulttypes.MethodSecretsUpdate:
		return h.handleSecretsUpdate(ctx, ar)
	case vaulttypes.MethodSecretsDelete:
		return h.handleSecretsDelete(ctx, ar)
	case vaulttypes.MethodSecretsList:
		return h.handleSecretsList(ctx, ar)
	default:
		return h.sendResponse(ctx, ar, h.errorResponse(req, api.UnsupportedMethodError, errors.New("this method is unsupported: "+req.Method), nil))
	}
