Confirmed: the `MessageID` (`req.ID` in the JSON-RPC request, mapped to `m.Body.MessageID`) is fully client-controlled — `ValidatedMessageFromReq` at [1](#0-0)  takes it straight from the incoming JSON-RPC request without any uniqueness enforcement, and `Message.Validate()` only checks length/format, not uniqueness [2](#0-1) .

### Title
Unprivileged client can overwrite an in-flight `web_api_trigger` callback by MessageID collision, orphaning the earlier request - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`HandleLegacyUserMessage` stores the caller's callback in `h.savedCallbacks` keyed only by the client-supplied `MessageID`, without checking whether an entry already exists for that key. A second request using the same `MessageID` silently overwrites the first request's saved callback before the first has been answered, exactly mirroring the Derby `MainVault.withdrawalRequest` pattern where `user.withdrawalAllowance = value` (assignment, not accumulation) let a later request silently destroy the state of an earlier one while work/resources for both had already been committed.

### Finding Description
In `handler.HandleLegacyUserMessage`, the gateway unconditionally writes:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageID] = &savedCallback{id: msg.Body.MessageID, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [3](#0-2) 

There is no `if _, exists := h.savedCallbacks[msg.Body.MessageID]; exists { return error }` guard here (unlike the sibling `RequestCache.NewRequest`, which explicitly rejects a duplicate key with `"request already exists"` [4](#0-3) , and unlike `confidentialrelay`'s `newActiveRequest`, which also rejects duplicate IDs [5](#0-4) ).

Because `MessageID` is entirely attacker-controlled (`ValidatedMessageFromReq` copies `req.ID` directly into `m.Body.MessageID` with only a length/format check) [1](#0-0) [2](#0-1) , an unprivileged client can:
1. Send request A with `message_id = "X"`. The gateway saves `callback A` under key `"X"` and fans the request out to all DON members: `for _, member := range h.donConfig.Members { don.SendToNode(ctx, member.Address, req) }` [6](#0-5) .
2. Before any DON node responds, send request B, also with `message_id = "X"`. This overwrites `h.savedCallbacks["X"]` with `callback B`, discarding the reference to `callback A` — exactly like the vault's `user.withdrawalAllowance = value` overwrite, which discarded the first withdrawal's redeemable value while the burn (here: the DON-side work/fan-out for request A) had already happened.
3. When any node later responds to `MessageID = "X"` via `handleWebAPITriggerMessage`, only the surviving callback (B) is looked up and served: `savedCb, found := h.savedCallbacks[msg.Body.MessageID]` [7](#0-6) . Caller A's callback reference is gone; caller A never receives a response and hangs until whatever request-level timeout the caller enforces (there is no timeout tracked per-request here, only the periodic `pruneCallbacks` eviction based on `createdAt`, which just silently drops it without ever notifying the caller) [8](#0-7) .

This is a direct structural analog to the reported bug class: a later unprivileged request before the first is resolved overwrites per-key state (the "allowance"/callback) rather than being rejected or queued, while the cost/side effect of the first request (LP-token burn / DON fan-out) has already been paid — producing a permanently unserved/dropped first request.

### Impact Explanation
An unprivileged user of the gateway (any signer allowed to call `HandleLegacyUserMessage`, i.e. any DON-authorized caller sending `web_api_trigger` messages) can cause legitimate concurrent requests from itself (or, if `MessageID` namespacing is not otherwise scoped per-sender at this layer, potentially collide across callers depending on deployment) to be silently dropped/orphaned — the caller's HTTP/RPC connection hangs and never gets a response, while DON compute resources are consumed processing the now-orphaned request. This is a denial-of-service / response-loss condition analogous to "funds locked forever" in the original report — here it's "the response is dropped forever," not returned to the correct caller, and DON-side work is wasted for the abandoned request. It does not directly cause fund loss in Chainlink, so severity is capped at a response-integrity / availability issue rather than fund theft.

### Likelihood Explanation
Any unprivileged party able to send two `HandleLegacyUserMessage` gateway requests in quick succession with the same `message_id` before the first is answered can trigger this deterministically — no special timing or race beyond "send B before A's DON response arrives," which is trivially achievable for a malicious/misbehaving client and easily reproducible in tests.

### Recommendation
Add a duplicate-key guard to `HandleLegacyUserMessage`, symmetric with `RequestCache.NewRequest`'s protection, e.g. reject (or queue instead of overwrite) when `h.savedCallbacks[msg.Body.MessageID]` already exists:
```go
h.mu.Lock()
if _, exists := h.savedCallbacks[msg.Body.MessageID]; exists {
    h.mu.Unlock()
    return callback.SendResponse(handlers.UserCallbackPayload{...duplicate MessageID error...})
}
h.savedCallbacks[msg.Body.MessageID] = &savedCallback{...}
h.mu.Unlock()
```

### Proof of Concept
1. Client sends `HandleLegacyUserMessage` request with `msg.Body.MessageID = "X"`, `method = web_api_trigger`. Gateway stores `callback A` at key `"X"` and forwards to all DON members.
2. Before any node responds, client sends a second request with the same `MessageID = "X"`. Gateway overwrites `h.savedCallbacks["X"]` with `callback B` (see the unconditional map write at [3](#0-2) ).
3. A DON node eventually responds for `MessageID = "X"` (either in response to request A's or B's fan-out, since both share the ID once forwarded). `handleWebAPITriggerMessage` looks up and deletes `h.savedCallbacks["X"]`, finds only `callback B`, and answers B only [9](#0-8) .
4. Caller A's `callback.SendResponse` is never invoked; its request hangs indefinitely (until an external timeout on the caller's side or `pruneCallbacks`, which does not invoke the callback at all when evicting) [10](#0-9) .

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]

func (h *handler) pruneCallbacks() {
	h.mu.Lock()
	defer h.mu.Unlock()

	// First, remove expired callbacks.
	maxAge := time.Duration(h.config.CallbackMaxAgeSec) * time.Second
	now := time.Now()
	var expired int
	for id, cb := range h.savedCallbacks {
		if now.Sub(cb.createdAt) > maxAge {
			delete(h.savedCallbacks, id)
			expired++
		}
	}

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}

	if expired > 0 || evicted > 0 {
		h.lggr.Infow("Pruned savedCallbacks", "expired", expired, "evicted", evicted, "remaining", len(h.savedCallbacks))
	}
```
