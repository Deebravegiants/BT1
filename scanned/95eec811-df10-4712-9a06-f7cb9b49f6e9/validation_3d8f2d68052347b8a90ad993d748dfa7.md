### Title
Login Endpoint Leaks Distinct "Invalid Email" vs "Invalid Password" Errors, Enabling Username Enumeration - (File: core/web/sessions_controller.go)

### Summary
The `/sessions` login endpoint returns different, verbatim error messages depending on whether the submitted email exists or the password is wrong, allowing an unauthenticated attacker to enumerate valid Chainlink node user accounts — the same bug class as CVE-2019-15162 (libpcap's `rpcapd` leaking whether a username was valid via differing auth-failure responses).

### Finding Description
`SessionsController.Create` calls `sc.App.AuthenticationProvider().CreateSession(ctx, sr)` and, on failure, forwards the raw error directly to the client: [1](#0-0) 

The local authentication ORM's `CreateSession` produces two distinguishable errors depending on which check fails: [2](#0-1) 

The same email-vs-password distinction is repeated in the LDAP and OIDC local-login fallback paths: [3](#0-2) [4](#0-3) 

`jsonAPIError` then serializes `err.Error()` straight into the HTTP JSON response body without normalizing or genericizing the message: [5](#0-4) 

As a result, an unauthenticated request to `POST /sessions` with a guessed email returns "Invalid email" if the account doesn't exist, but "Invalid password" if it does — directly revealing valid usernames to any unprivileged network client, mirroring the libpcap `rpcapd` authentication-failure disclosure described in the CVE.

### Impact Explanation
This is a concrete authentication-related information disclosure: an unauthenticated attacker can enumerate valid operator/admin usernames (emails) on an internet-facing Chainlink node, narrowing subsequent credential-stuffing or brute-force attacks against the `/sessions` endpoint and increasing the risk of account takeover for node operator accounts.

### Likelihood Explanation
The `/sessions` endpoint is reachable pre-authentication by any client that can reach the node's API surface, and the request/response flow requires no special conditions — merely submitting arbitrary email/password pairs and observing the returned error text.

### Recommendation
Return a single generic error message (e.g., "invalid credentials") for all `CreateSession` failure paths in `core/web/sessions_controller.go`, regardless of whether the failure originated from an unknown email or an incorrect password, and avoid propagating internal error strings from `AuthenticationProvider().CreateSession` verbatim to the HTTP client.

### Proof of Concept
1. `POST /sessions` with `{"email":"nonexistent@example.com","password":"anything"}` → response body contains `"Invalid email"` (per `core/sessions/localauth/orm.go:156`).
2. `POST /sessions` with `{"email":"<a known valid admin email>","password":"wrongpassword"}` → response body contains `"Invalid password"` (per `core/sessions/localauth/orm.go:161`).
3. The differing text ("Invalid email" vs "Invalid password") in the JSON body returned by `jsonAPIError` lets the attacker distinguish valid from invalid emails, confirming username enumeration.

func jsonAPIError(c *gin.Context, statusCode int, err error) {
