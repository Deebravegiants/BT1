### Title
Bridge `OutgoingToken` Credential Disclosed in Plaintext to Any Authenticated (View-Role) User - (File: `core/web/resolver/bridge.go`)

### Summary
The Chainlink node's Bridge GraphQL query (and the equivalent REST `bridge_types` endpoints) return the bridge's `OutgoingToken` — a credential used to authenticate outbound webhook calls to an external adapter — to any authenticated user, regardless of role. There is no `authenticateUserCanEdit`/`authenticateUserIsAdmin` gate on read access to this secret, unlike write-role protections elsewhere in the resolver package (`core/web/resolver/auth.go:31-43`). This closely parallels the underlying bug class of GHSA-7h99-vjmf-5pg8 (CVE-2019-1003068): a credential intended to be write-only/creation-time-only is instead persistently exposed to lower-privileged, non-admin viewers through a standard read/list API.

### Finding Description
`BridgeType.OutgoingToken` (`core/bridges/bridge_type.go:57-68`) is a durable secret token that the Chainlink node presents when calling out to the configured bridge adapter URL. Unlike `IncomingToken`, which is intentionally `omitempty` and only returned once at creation time (`core/web/presenters/bridges.go:16-17`, `core/web/bridge_types_controller.go:98-99`), `OutgoingToken` has no `omitempty` tag and is unconditionally serialized on every read: [1](#0-0) 

The GraphQL resolvers for both single-bridge and list queries gate access only via `authenticateUser`, which merely checks that a session exists — it explicitly does not check role: [2](#0-1) 

Contrast this with the stricter helpers used elsewhere for write operations: [3](#0-2) 

The `Bridge`/`Bridges` resolvers use only the weakest check and then return the resolver type exposing `OutgoingToken()`: [4](#0-3) [5](#0-4) 

The REST `Index`/`Show` handlers exhibit the identical pattern, unconditionally embedding `OutgoingToken` in the JSON:API response: [6](#0-5) 

### Impact Explanation
An authenticated node-UI/API user holding only the lowest privilege role (`UserRoleView`, which per `core/sessions/authentication.go` and `core/web/resolver/auth.go:25-27` is explicitly barred from mutating jobs/bridges) can nonetheless read every configured bridge's `OutgoingToken`. Because this token is the credential the Chainlink node uses to authenticate to the external adapter service, its disclosure lets a low-privilege internal user impersonate the node to the external adapter (submit spoofed responses, replay/forge webhook calls, or pivot to attack the adapter infrastructure), which is a direct secret/credential disclosure and potential request-impersonation vector — matching the "Accept: concrete... key/secret disclosure, request impersonation" bar in the validation rules. It does not, however, allow privilege escalation within Chainlink itself, and depending on deployment, the "view" role may already be considered a trusted operator seat — this is the main mitigating uncertainty.

### Likelihood Explanation
Likelihood is moderate-to-high for any deployment where view-only credentials are handed to less-trusted internal users (a common Jenkins-analog scenario — "Extended Read"-style users). No additional exploitation steps beyond an authenticated GraphQL/REST call are required; there is no rate limiting or extra authorization step (`authenticateUser` only checks session existence).

### Recommendation
Gate bridge read access (both GraphQL `Bridge`/`Bridges` resolvers and REST `Index`/`Show`) behind at least `authenticateUserCanEdit` (or a new "admin/secret-view" check), and/or redact `OutgoingToken` from list/show responses the same way `IncomingToken` is already handled (`omitempty`, only returned at creation), requiring an explicit "reveal" action gated by re-authentication (as done for `NewAPIToken`, which requires password confirmation — `core/web/user_controller.go:267-273`).

### Proof of Concept
1. Create a user with `UserRoleView` (`core/sessions/session.go`, `core/sessions`).
2. Log in and obtain a session cookie via `/sessions`.
3. Issue the GraphQL query:
```graphql
query { bridges { results { name outgoingToken } } }
```
or `GET /v2/bridge_types` — the response includes the plaintext `outgoingToken` for every bridge, confirmed by test fixtures showing the field always populated in list/show responses (`core/web/resolver/bridge_test.go:22-38`, `core/web/presenters/bridges_test.go:39-58`).

// Index lists Bridges, one page at a time.
func (btc *BridgeTypesController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	bridges, count, err := btc.App.BridgeORM().BridgeTypes(ctx, offset, size)

	resources := make([]presenters.BridgeResource, 0, len(bridges))

func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)

		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}
