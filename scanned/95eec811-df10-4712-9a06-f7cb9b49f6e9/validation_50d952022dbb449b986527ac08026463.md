### Title
Session fixation in OIDC login flow allows an attacker's pre-authentication session cookie to be upgraded into an authenticated session - ([File: core/sessions/oidcauth/oidc.go])

### Summary
The OIDC authentication driver reuses the same gin-contrib/sessions cookie-store session across the entire login flow — before, during, and after authentication — instead of issuing a fresh session identifier once the user is actually authenticated. This mirrors the root cause of CVE-2018-1000173 (Jenkins Google Login Plugin session fixation): a pre-authentication session is "promoted" to an authenticated session rather than being replaced.

### Finding Description
The gin session store used by the whole web router is a single cookie-based store (`cookie.NewStore`), shared for every request via `sessions.Sessions(auth.SessionName, sessionStore)`: [1](#0-0) [2](#0-1) 

When a user begins the OIDC login flow, `handleSignIn` takes whatever session is already active for the browser (pre-authentication) and simply writes a `state` value into it: [3](#0-2) 

After the OAuth provider redirects back, `handleTokenExchange` verifies the `state` against that same pre-existing session, creates a new backend `oidc_sessions` row, and then sets the authenticated `SessionIDKey` directly onto the **same** gin session object used for the pre-auth step, saving it back to the browser: [4](#0-3) [5](#0-4) 

At no point in this flow is a brand-new gin session (i.e., a fresh cookie value) generated after successful authentication — the code only calls `Set`/`Save` on the `sessions.Default(c)` instance that was already present when `handleSignIn` was invoked. If an attacker can get a victim to load the application with an attacker-known/attacker-set session cookie (e.g. by planting the `clsession`-style cookie through a shared/misconfigured cookie scope, XSS elsewhere, or a captured pre-auth response), and the victim then completes the OIDC login using that fixed session, the attacker's browser session becomes authenticated as the victim, because the session identifier itself was never rotated at the authentication boundary. This is the same bug class as the Jenkins Google Login Plugin issue, where `GoogleOAuth2SecurityRealm.java` upgraded a pre-auth session to an authenticated one without regenerating it.

By contrast, the local/LDAP login path via `SessionsController.Create` (`core/web/sessions_controller.go`) also calls `saveSessionID(session, sid)` on the existing gin `Default(c)` session, but that endpoint requires POSTing valid credentials directly and is not preceded by an unauthenticated redirect/callback round trip controlled partly by an external IdP, so the practical fixation window is narrower there. The OIDC callback path is the closest analog to the Jenkins plugin flow because it involves a pre-auth redirect step (`state` set on session) followed by a callback that finalizes authentication on the identical session object.

### Impact Explanation
If exploitable, this allows a network-adjacent/unprivileged attacker to hijack another user's authenticated Chainlink node web session (GUI/API), gaining that user's RBAC role (potentially Admin) without needing to compromise credentials or the OIDC provider — a request/session impersonation issue.

### Likelihood Explanation
Likelihood depends on whether an attacker can actually fix/set the victim's session cookie before the OIDC flow starts (e.g., cookie not marked `secure`/`HttpOnly` in some deployment, subdomain cookie injection, or an attacker-supplied link that causes the browser to adopt a specific session before visiting `/sessions/oidc-login` — this repo does configure `SecureCookies` via `config.WebServer().SessionOptions()`, which reduces but does not eliminate all fixation vectors, e.g. cross-subdomain or older-browser scenarios). This is a Medium-likelihood, environment-dependent issue, consistent with the CVSS 5.9 (AC:H) rating of the original CVE.

### Recommendation
Regenerate the gin session (clear and reissue a new session ID/cookie) at the point authentication succeeds in `handleTokenExchange` (and equally in `SessionsController.Create` for defense in depth), rather than reusing the pre-authentication session object. Concretely, call `session.Clear()` (or generate a new session via the store) before setting `webauth.SessionIDKey` and saving, so any pre-existing (potentially attacker-fixed) session cookie value is discarded and replaced post-authentication.

### Proof of Concept
1. Attacker visits the target Chainlink node and obtains an unauthenticated session cookie (`state` not yet set), or otherwise plants a chosen session cookie value in the victim's browser (via a shared subdomain, an open redirect, or a similar cookie-fixation vector allowed by the deployment).
2. Attacker sends the victim a link to `GET /sessions/oidc-login` (this initiates `handleSignIn`) using the fixed session cookie.
3. Victim authenticates with the OIDC provider; the provider redirects back to `handleTokenExchange`.
4. `handleTokenExchange` validates `state` against the fixed session, creates the `oidc_sessions` row, and sets `SessionIDKey` on the *same* fixed session, then calls `ginSession.Save()` — reusing the attacker-known cookie.
5. Attacker reuses that same (never-rotated) session cookie to access the application as the victim's authenticated user.

```go
func (oi *oidcAuthenticator) handleSignIn(c *gin.Context) {
	// generate state and store on session
	state := oi.generateState()
	session := sessions.Default(c)
	session.Set("state", state)
	err := session.Save()
	if err != nil {
		c.JSON(http.StatusInternalServerError, gin.H{"error": "Failed to save session"})
		return
	}

	// redirect to provider
	url := oi.oauth2Config.AuthCodeURL(state, oauth2.AccessTypeOffline)
	c.Redirect(http.StatusFound, url)
}
```
