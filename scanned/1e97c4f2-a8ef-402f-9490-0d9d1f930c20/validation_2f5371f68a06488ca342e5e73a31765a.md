### Title
Double-application of a frame's pending storage diff to `ContractInfo` breaks storage-deposit accounting invariant - ([File: substrate/frame/revive/src/metering/storage.rs])

### Summary
`FrameMeter::apply_pending_storage_changes` (wrapping `RawMeter::apply_pending_changes_to_contract`) mutates the shared, persistent `ContractInfo` (`storage_bytes`, `storage_items`, `storage_byte_deposit`, `storage_item_deposit`) using the frame's still-`Alive` `own_contribution` diff, but does **not** consume/reset that diff or transition it to `Checked`. When the frame later calls `finalize` (`finalize_own_contributions`), the exact same diff is applied to `ContractInfo` a second time, now against an already-mutated baseline. This violates the single-application invariant that every other path in the meter (`bank_pending_changes`, `absorb`, `finalize_own_contributions` alone) relies on.

### Finding Description
`RawMeter::apply_pending_changes_to_contract` explicitly documents that it "does not consume the pending diff, allowing the meter to continue tracking changes after the nested call returns": [1](#0-0) 

Compare this to `bank_pending_changes`, which is the "safe" sibling that resets `own_contribution` to `Alive(Default::default())` after applying it, precisely to avoid double counting when a subsequent `finalize_own_contributions` runs: [2](#0-1) 

`finalize_own_contributions`, however, is unconditionally applied on `own_contribution` whenever a frame finalizes, regardless of whether `apply_pending_changes_to_contract` already mutated `info` for the same diff: [3](#0-2) 

Both call sites route through the same `Diff::update_contract`, which mutates `info.storage_bytes`/`storage_items`/`storage_byte_deposit`/`storage_item_deposit` as a side effect and computes a pro-rata refund based on the *current* value of those fields: [4](#0-3) 

The wrapper `FrameMeter::apply_pending_storage_changes` / `bank_pending_storage_changes` in `metering/mod.rs` confirms the two are meant to be alternatives, but nothing in the type system prevents `apply_pending_storage_changes` from being followed by a normal `finalize()` on the same frame instead of `bank_pending_storage_changes`: [5](#0-4) 

Because `Diff::update_contract` both (a) permanently mutates `ContractInfo` fields and (b) computes a refund/charge proportionally to the *current* `storage_bytes`/`storage_byte_deposit` at call time, applying the identical diff twice against two different intermediate states of `info` means the pro-rata refund math is evaluated against a baseline that has already partially absorbed the very diff being processed. Depending on whether the pending diff was a net-charge or net-refund, and on what the nested frame does to `info` in between the two applications, this can either inflate `info.storage_bytes`/`storage_byte_deposit` (leading to future under-refunds/stuck deposits) or, in the reversed ordering (pending delete previewed, nested frame re-adds equivalent bytes, then the stale delete diff is re-applied against the now-restored `info`), produce a second, unearned refund/charge event that does not correspond to any additional real storage change. In all cases the core invariant — each logical storage diff must be reflected in `ContractInfo` and in money movement exactly once — is broken.

The design intent for the sequence (write K → nested call deletes K → nested returns → parent finalizes) is exactly the "before creating a nested frame" pattern described in the PR that introduced `apply_pending_storage_changes` (issue paritytech/contract-issues#213), so the attacker-reachable path is straightforward: any contract that writes storage, then performs a nested call (to itself or another contract) that touches the same key, exercises this exact code path via ordinary `call`/`instantiate` execution — no privileged origin required.

### Impact Explanation
`ContractInfo.storage_bytes`/`storage_items`/`storage_byte_deposit`/`storage_item_deposit` are persistent on-chain state used by every subsequent storage-deposit calculation for that contract (via `Diff::update_contract`'s pro-rata refund ratio). A double application of the same diff desynchronizes these fields from the contract's real trie usage, which corrupts every future refund/charge computation for that contract's storage deposit and can allow the deposit accounting to diverge from the real backing byte/item count — the scoped invariant ("net storage deposit refunded across the whole call stack must equal exactly the net delta actually persisted") is violated. Because `StorageDeposit` amounts are ultimately transferred via `ReservingExt::charge` (real balance holds/refunds), a persistent accounting drift is a real fund-safety issue, not merely a bookkeeping cosmetic bug.

### Likelihood Explanation
Fully reachable by an ordinary, unprivileged contract call: write a storage key, then perform any nested `call`/`delegate_call` (even to itself) that touches the same key, then let the outer frame return normally so its `finalize()` runs. No admin/governance/node privilege is needed, and the sequence is a common contract pattern (re-entrant self-calls, proxy patterns), making it easily and repeatably triggerable by any contract deployer.

### Recommendation
Make `apply_pending_storage_changes` idempotent with respect to `finalize`: either (a) always route through `bank_pending_storage_changes` instead of the raw preview (i.e., remove `apply_pending_changes_to_contract`/`apply_pending_storage_changes` and replace all call sites with the "bank" variant so `own_contribution` is reset after every application), or (b) have `finalize_own_contributions` detect that a pending preview was already applied (e.g., track an explicit "already-previewed" diff baseline) and only apply the delta accumulated since the preview, never reapplying the previously-previewed portion.

	pub fn update_contract<T: Config>(&self, info: Option<&mut ContractInfo<T>>) -> DepositOf<T> {
		let per_byte = T::DepositPerByte::get();
		let per_item = T::DepositPerChildTrieItem::get();
		let bytes_added = self.bytes_added.saturating_sub(self.bytes_removed);
		let items_added = self.items_added.saturating_sub(self.items_removed);
		let mut bytes_deposit = Deposit::Charge(per_byte.saturating_mul((bytes_added).into()));
		let mut items_deposit = Deposit::Charge(per_item.saturating_mul((items_added).into()));

		// Without any contract info we can only calculate diffs which add storage
		let info = if let Some(info) = info {
			info
		} else {
			return bytes_deposit.saturating_add(&items_deposit);
		};

		// Refunds are calculated pro rata based on the accumulated storage within the contract
		let bytes_removed = self.bytes_removed.saturating_sub(self.bytes_added);
		let items_removed = self.items_removed.saturating_sub(self.items_added);
		let ratio = FixedU128::checked_from_rational(bytes_removed, info.storage_bytes)
			.unwrap_or_default()
			.min(FixedU128::from_u32(1));
		bytes_deposit = bytes_deposit
			.saturating_add(&Deposit::Refund(ratio.saturating_mul_int(info.storage_byte_deposit)));
		let ratio = FixedU128::checked_from_rational(items_removed, info.storage_items)
			.unwrap_or_default()
			.min(FixedU128::from_u32(1));
		items_deposit = items_deposit
			.saturating_add(&Deposit::Refund(ratio.saturating_mul_int(info.storage_item_deposit)));

		// We need to update the contract info structure with the new deposits
		info.storage_bytes =
			info.storage_bytes.saturating_add(bytes_added).saturating_sub(bytes_removed);
		info.storage_items =
			info.storage_items.saturating_add(items_added).saturating_sub(items_removed);
		match &bytes_deposit {
			Deposit::Charge(amount) => {
				info.storage_byte_deposit = info.storage_byte_deposit.saturating_add(*amount)
			},
			Deposit::Refund(amount) => {
				info.storage_byte_deposit = info.storage_byte_deposit.saturating_sub(*amount)
			},
		}
		match &items_deposit {
			Deposit::Charge(amount) => {
				info.storage_item_deposit = info.storage_item_deposit.saturating_add(*amount)
			},
			Deposit::Refund(amount) => {
				info.storage_item_deposit = info.storage_item_deposit.saturating_sub(*amount)
			},
		}

		bytes_deposit.saturating_add(&items_deposit)
	}

	/// Apply pending storage changes to a ContractInfo without finalizing the meter.
	///
	/// This is used before creating a nested frame to ensure the child frame can see
	/// the parent's pending storage changes when calculating refunds.
	///
	/// Unlike [`Self::finalize_own_contributions`], this does not consume the pending diff,
	/// allowing the meter to continue tracking changes after the nested call returns.
	pub fn apply_pending_changes_to_contract(&self, info: &mut ContractInfo<T>) {
		if let Contribution::Alive(diff) = &self.own_contribution {
			// Apply the diff to update the ContractInfo's storage deposit fields.
			// We don't care about the return value (the deposit amount) here,
			// we just want to update the ContractInfo so child frames can see it.
			let _ = diff.update_contract::<T>(Some(info));
		}
	}

	/// Apply the pending diff to `info` and push its deposit as a final charge, then reset
	/// `own_contribution` so finalize does not apply it a second time.
	pub fn bank_pending_changes(&mut self, contract: T::AccountId, info: &mut ContractInfo<T>) {
		if let Contribution::Alive(_) = &self.own_contribution {
			let deposit = self.own_contribution.update_contract(Some(info));
			self.own_contribution = Contribution::Alive(Default::default());
			if !deposit.is_zero() {
				self.charge_deposit(contract, deposit);
			}
		} else {
			debug_assert!(
				false,
				"on-stack ancestor frames have not finalized yet, so own_contribution \
				 should be Alive when banked; qed",
			);
		}
	}

	/// Apply pending storage changes to a ContractInfo without finalizing the meter.
	///
	/// This is used before creating a nested frame to ensure the child frame can see
	/// the parent's pending storage changes when calculating refunds. This fixes the issue
	/// where storage deposit refunds fail in subframes because the parent's pending

	pub fn apply_pending_storage_changes(&self, info: &mut ContractInfo<T>) {
