## Finding: Missing slippage protection on internal swap during XCM fee refund

### Title
Missing slippage parameter (`amount_out_min = None`) in `SwapFirstAssetTrader::refund_weight` swap - (File: `cumulus/primitives/utility/src/lib.rs`)

### Summary
`SwapFirstAssetTrader` is a `WeightTrader` implementation used to pay XCM execution fees by automatically swapping a user's asset into a `Target` fee asset via `pallet_asset_conversion`'s `SwapCredit`. When refunding unused weight back to the original asset, it calls `SwapCredit::swap_exact_tokens_for_tokens` and passes `None` for the `amount_out_min` parameter, meaning the swap accepts any output amount, no matter how unfavorable, exactly analogous to the Dopex `reLP()` bug of passing `0`/no slippage bound into an AMM's liquidity/swap function.

### Finding Description
`buy_weight` swaps a user's asset into `Target` with an explicit exact-output amount (`fee`), bounding the input amount implicitly via `swap_tokens_for_exact_tokens`. However, `refund_weight` swaps unused `Target` fee credit back into the original asset with no minimum-output bound: [1](#0-0) 

```rust
let refund = self.total_fee.extract(refund_amount);
let refund = match SwapCredit::swap_exact_tokens_for_tokens(
    vec![Target::get(), refund_swap_asset],
    refund,
    None,
) {
```

This mirrors `pallet_asset_conversion::Swap::swap_exact_tokens_for_tokens`, whose `amount_out_min: Option<Self::Balance>` is explicitly designed to protect against unfavorable pool state at execution time: [2](#0-1) 

By passing `None`, the caller of the pallet disables that protection entirely for this internal, automatic swap — the pallet itself will accept whatever `amount_out` the pool state produces at execution time, since `do_swap_exact_tokens_for_tokens` only checks the minimum `if let Some(amount_out_min) = amount_out_min`: [3](#0-2) 

Compare with `SingleAssetExchangeAdapter::exchange_asset`, which correctly bounds the maximal-swap branch with `Some(want_amount)`: [4](#0-3) 

### Impact Explanation
The swap in `refund_weight` executes atomically as part of XCM message processing inside a block. A block-producing collator (or anyone able to influence transaction ordering within the same block/extrinsic batch, e.g. via other pool-affecting extrinsics processed earlier in the same block) can manipulate the `Target`/refund-asset pool's reserves immediately before this swap executes, causing the user to receive a refund amount below fair value. Because there is no `amount_out_min`, the swap cannot fail — it simply returns whatever (possibly minimal) amount the manipulated pool state yields, and the difference is effectively captured by whoever manipulated the reserves.

### Likelihood Explanation
Exploitation requires the ability to influence ordering/state of the asset-conversion pool before this specific refund executes within the same block — realistically only a block-producing collator (or a bridge of same-block extrinsics) can reliably pull this off, since ordinary "front-running the mempool" is not straightforward in Substrate's block production model. The value at stake is also bounded to the refunded fee amount (residual weight not consumed), which is typically small relative to a full swap. This limits both the realistic attacker set (largely privileged/trusted block producers) and the magnitude of extractable value.

### Recommendation
Compute an `amount_out_min` for the refund swap based on a fair-value quote (e.g. via `QuotePrice::quote_price_exact_tokens_for_tokens`) before calling `swap_exact_tokens_for_tokens`, similar to how `quote_weight` already uses `QuotePrice` elsewhere in the same file, and treat a swap that cannot meet this minimum as "no refund" rather than accepting an unbounded loss.

### Proof of Concept
Not applicable as a standalone PoC beyond the code path: the refund is only reachable inside XCM `BuyExecution`/weight-refund logic, and demonstrating the value-extraction requires controlling block-level extrinsic ordering relative to the asset-conversion pool, which is a collator-level capability rather than an ordinary unprivileged-user-reachable exploit in isolation. [5](#0-4) 

Note on confidence: this analog is weaker than the original Dopex finding because (a) the affected value is limited to fee refunds rather than full liquidity/swap amounts, and (b) exploitation realistically requires block-producer-level control over extrinsic ordering rather than being reachable by an arbitrary unprivileged user via a simple transaction. All other `add_liquidity`/`swap_*` call sites in this repository (pallet extrinsics, precompiles, `SingleAssetExchangeAdapter`, benchmarks, and integration tests) either require callers to explicitly supply `amount*_min`/`amount*_max` (enforced via `ensure!` checks in `do_add_liquidity`/`do_swap_exact_tokens_for_tokens`/`do_swap_tokens_for_exact_tokens`) or pass explicit non-`None` bounds, matching intended usage rather than a code-level defect.

		log::trace!(
			target: "xcm::weight",
			"SwapFirstAssetTrader::refund_weight weight: {:?}, self.total_fee: {:?}",
			weight,
			self.total_fee,
		);
		if weight.is_zero() || self.total_fee.peek().is_zero() {
			// noting to refund.
			return None;
		}
		let refund_asset = if let Some(asset) = &self.last_fee_asset {
			// create an initial zero refund in the asset used in the last `buy_weight`.
			(asset.clone(), Fungible(0)).into()
		} else {
			return None;
		};
		let refund_amount = WeightToFee::weight_to_fee(&weight);
		if refund_amount >= self.total_fee.peek() {
			// not enough was paid to refund the `weight`.
			return None;
		}

		let refund_swap_asset = FungiblesAssetMatcher::matches_fungibles(&refund_asset)
			.map(|(a, _)| a.into())
			.ok()?;

		let refund = self.total_fee.extract(refund_amount);
		let refund = match SwapCredit::swap_exact_tokens_for_tokens(
			vec![Target::get(), refund_swap_asset],
			refund,
			None,
		) {
			Ok(refund_in_target) => refund_in_target,
			Err((refund, _)) => {
				// return an attempted refund back to the `total_fee`.
				let _ = self.total_fee.subsume(refund).map_err(|refund| {
					// error may occur if `total_fee.asset` differs from `refund.asset`, which does
					// not apply in this context.
					defensive!(
						"`total_fee.asset` must be equal to `refund.asset`",
						(self.total_fee.asset(), refund.asset())
					);
				});
				return None;
			},
		};

		let refund = AssetsInHolding::new_from_fungible_credit(refund_asset.id, Box::new(refund));
		Some(refund)
	}
