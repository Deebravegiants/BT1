Target: computeErc191Prehash's length prefix in packages/intents-sdk/src/intents/intent-hashes/erc191.ts (data.length used inside the \x19Ethereum Signed Message:\n${data.length} template). Attacker input: any erc191 payload whose JSON stringification includes multi-byte UTF-8 characters (e.g. an emoji in memo). Preconditions: signer (intent-signer-viem) signs the exact same string that computeIntentHash re-hashes locally; if the signer path uses a different serialization (e.g. Buffer.byteLength vs data.length after re-parsing/re-stringifying JSON) than computeIntentHash's fresh TextEncoder call. Call sequence: sdk.signAndSendIntent -> intentSigner.signIntent produces multiPayload.payload as a string -> IntentExecuter calls computeIntentHash(multiPayload) using that exact stored string -> intentRelayer.publishIntent posts the same string over HTTP -> contract recomputes hash from the received string bytes. Equality that breaks: SIGNED == BUILT is preserved only if no re-serialization occurs between signing and hashing; if any intermediate step (e.g. a custom intentPayloadFactory merging fields via mergeIntentPayloads) re-stringifies the JSON with different key ordering or whitespace before it reaches computeIntentHash, then computeIntentHash(multiPayload) != intent_hash returned by publishIntent for the string actually signed. Impact: Critical - the persisted intentHash tracked by an integrator no longer identifies the transaction actually executed on-chain, so waitForIntentSettlement times out against the wrong hash and integrator logic re-issues the withdrawal. Whose funds: the signing user's withdrawal funds. Proof idea: vitest test with a custom intentPayloadFactory that merges an intent but is proven to preserve field order (documented invariant), followed by a fuzz case that deliberately reorders keys, and assert computeIntentHash diverges from the relay's fixture intent_hash for the reordered case.
