[Function: scale-debt-for-liquidation (private)] Precondition: borrower's curr-scaled (from get-account-scaled-debt) is less than scaled-debt computed from debt-final (i.e. debt-final overshoots the borrower's remaining scaled debt, which can occur if a second liquidator front-runs in the same block via liquidate-multi or if the borrower's debt was partially repaid by another actor in a prior transaction within the same block). Attacker action: liquidator A calls liquidate on a borrower whose remaining debt is thin, immediately followed (same block, via liquidate-multi or sequential calls) by liquidator B calling liquidate on the same borrower/debt-aid before caches update. Call sequence: first liquidate call reduces curr-scaled via debt-remove-scaled; second call's scale-debt-for-liquidation caps scaled-to-remove at the now-smaller curr-scaled, then computes coll-final = mul-div-down(coll-actual, scaled-to-remove, scaled-debt) proportionally reduced -- but coll-actual itself was already computed by process-collateral-asset from a stale user-coll-balance (post first liquidation, if pos-full was fetched before the first call's collateral-remove committed). Identity: sum of (coll-final across both liquidate calls) must equal user-coll-balance-before-any-liquidation converted at coll-price, but with stale reads the sum can exceed the borrower's actual collateral. Scoped impact: Critical, theft of borrower funds / protocol insolvency if collateral-remove underflows are silently avoided by clamping. Proof idea: Clarinet test issuing two liquidate calls in the same block against the same undercollateralized position and asserting CUSTODY (.v0-market-vault balance for coll-aid) never goes negative and equals initial balance minus sum of both coll-final values exactly.
