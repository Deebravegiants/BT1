Target: ShopifyAPI::Auth::JwtPayload#shop and ShopifyAPI::Auth::TokenExchange.exchange_token. Attacker action: an attacker who has installed the app on their own dev shop obtains a validly-signed session token (their JWT, signed by the real Shopify STS but decodable with this app's Context.api_secret_key per the app's own key) whose `dest` claim is `https://attacker-controlled.example.com` instead of a `*.myshopify.com` host, then calls the app endpoint that invokes `exchange_token(session_token: token, requested_token_type: ...)`. Preconditions: app configured embedded, Context.api_secret_key set, no shop param passed. Call sequence: JwtPayload.new(token) -> decode_token succeeds since signature is genuinely valid -> shop returns dest_shop = 'attacker-controlled.example.com' unchecked -> Session.new(shop: dest_shop) -> Clients::HttpClient.new(session: shop_session) sets @base_uri = 'https://attacker-controlled.example.com' -> client.request posts client_id/client_secret to that host. Binding that breaks: host receiving client_secret ∈ TRUSTED_SHOPIFY_DOMAINS is false. Impact: Critical - theft/exfiltration of client_secret to an attacker-controlled host. Proof idea: minitest + WebMock stubbing a JWT with dest set to a non-myshopify host, assert HttpClient posts to that host and that ShopValidator.sanitize! is never called in exchange_token.
