Attacker input: an integrator/user opts into `setNonceRandomBytes(VersionedNonceBuilder.createTimestampedNonceBytes(startTime))` to embed a timestamp, leaving only 7 random bytes (`bytes.subarray(8)`) instead of the normal 15. Preconditions: multiple withdrawals are built with the same `startTime` (e.g. batched or rapid calls) and the same cached salt from `SaltManager`. Call sequence: `builder.setDeadline(d).setNonceRandomBytes(createTimestampedNonceBytes(startTime)).buildWithSalt(salt)` invoked twice with identical `startTime`. Equality to test: SINGLE EXECUTION - two distinct signed `MultiPayload`s must have distinct `nonce` values so each executes independently exactly once; with only 2^56 space and the birthday bound, collisions become practically reachable in a moderate-size batch. Scoped impact: High - a nonce collision between two of the user's own intents let the intents.near contract treat the second submission as an already-used nonce, silently dropping/rejecting one of the user's own withdrawals leaving it stuck pending manual re-sign. Proof idea: vitest test generating `createTimestampedNonceBytes` for a fixed `startTime` across a large batch (e.g. 200k), asserting no duplicate 7-byte tails, then a smaller-scale statistical check flagging non-uniform distribution against the 2^56 bound.
