In `HotBridge.describeWithdrawal` (packages/intents-sdk/src/bridges/hot-bridge/hot-bridge.ts:375-404), the reported `status`/`txHash` is derived from `this.hotSdk.getGaslessWithdrawStatus(nonce)` where `nonce` is looked up from a cache keyed by `this.getNoncesCacheKey(args.tx)` and indexed by `args.index`, with no check that the returned txHash's destination address/amount matches `args.withdrawalParams.destinationAddress`/`amount`. Attacker input: none required from the attacker directly - a permissionless solver or the HOT relay (excluded as attacker) could serve a status for a different nonce at the same index if `nonces[args.index]` is stale/reused across a caller-triggered batch re-run. Preconditions: caller calls `describeWithdrawal` twice for the same `tx`/`index` after cache eviction/refetch. Call sequence: `sdk` internal orchestration -> `waitForWithdrawalCompletion` -> `HotBridge.describeWithdrawal`. Equality that breaks: STATUS TRUTH - `(status, txHash)` reported for withdrawal `i` must equal the on-chain outcome of the withdrawal actually signed at index `i`, but no field ties the returned hash back to `args.withdrawalParams.destinationAddress`/`amount` signed for that index. Impact: High - an integrator relying on `describeWithdrawal` to credit an off-chain balance could credit against a txHash that does not correspond to the destination/amount originally signed. Proof idea: vitest test asserting the destination/amount encoded in the tx fetched at `txHash` equals `args.withdrawalParams.destinationAddress`/`amount`, mocking `hotSdk.getGaslessWithdrawStatus` to return a mismatched hash.
