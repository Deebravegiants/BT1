### Title
Bridge and Bridges GraphQL queries leak the `OutgoingToken` credential to any authenticated "View"-role user - ([File: core/web/resolver/bridge.go])

### Summary
The `OrderListInitial` report describes a GraphQL over-fetch/under-authorization bug class: a resolver enforces only a coarse, low-privilege authentication check while returning object fields that should require a higher privilege level, allowing an under-privileged staff account to read sensitive data by simply requesting more fields in the same query. Chainlink's GraphQL API has an analogous pattern in the `Bridge`/`Bridges` queries: the role gate is the same coarse `authenticateUser` check used for read-only data, yet the returned `Bridge` object exposes `OutgoingToken`, a live credential used by the node to authenticate to the external bridge adapter.

### Finding Description
Chainlink's GraphQL layer authenticates via a session cookie and stores a `GQLSession{User}` in context [1](#0-0) . Each resolver is individually responsible for deciding what role is required, via helper functions in `core/web/resolver/auth.go`: `authenticateUser` only checks that *any* authenticated session exists (i.e. it accepts the lowest role, `UserRoleView`), while `authenticateUserCanRun`/`authenticateUserCanEdit`/`authenticateUserIsAdmin` require successively higher roles [2](#0-1) .

The `Bridges` query (list of bridges) and `Bridge` query (single bridge lookup) both call the minimal `authenticateUser` check only: [3](#0-2)  and [4](#0-3) .

The `BridgeResolver` returned from these queries exposes an `OutgoingToken()` field that returns the raw bridge credential (`r.bridge.OutgoingToken`), used by the Chainlink node to authenticate outbound requests to the external bridge adapter: [5](#0-4) . Because the `Bridge`/`Bridges` resolvers only require `authenticateUser` (View role, the lowest privilege tier — comparable to Shopify's "Customer"-only permission staff account), any authenticated GraphQL client, regardless of role, can query this field and read a live outbound secret credential that should reasonably be restricted to Edit/Admin-level operators who manage bridge configuration.

This mirrors the reported bug class exactly: the authorization boundary is enforced at a coarse level (session exists / minimal role) rather than per-sensitive-field, so a low-privilege but authenticated caller can broaden its GraphQL selection set to retrieve fields intended for higher-privileged operations — in Shopify's case order PII, here a bridge outbound secret token.

### Impact Explanation
`OutgoingToken` is a secret used by the node to authenticate itself to external bridge/adapter services. Disclosure to any authenticated user regardless of role (including read-only `View` users) allows credential theft that could be replayed against the external adapter, potentially enabling request forgery against systems the bridge integrates with. This satisfies the "concrete... key/secret disclosure" acceptance criterion.

### Likelihood Explanation
The chainlink GraphQL server documented in `core/web/router.go` mounts the `authv2`/GraphQL routes behind session authentication only, and role enforcement is delegated entirely to per-resolver logic (as seen consistently across `query.go` for keys, jobs, and bridges) [6](#0-5) . Any operator who provisions a low-privilege ("View") user account for read-only dashboard access would unknowingly grant that account the ability to fetch the `outgoingToken` value simply by issuing a `bridges` or `bridge` GraphQL query including that field — no additional exploitation steps are required beyond crafting the query, making this readily reachable by any authenticated but low-privileged client.

### Recommendation
Gate the `OutgoingToken` field (and any other bridge credential fields) behind `authenticateUserCanEdit` or `authenticateUserIsAdmin` instead of the coarse `authenticateUser` check used for the parent query, or omit `OutgoingToken` from the `Bridge` GraphQL type entirely for non-privileged roles, following the same pattern already used elsewhere for admin-only mutations (`authenticateUserIsAdmin`) [7](#0-6) .

### Proof of Concept
1. Create a Chainlink node user with role `view` (the lowest privilege role, analogous to Shopify's "Customer"-only staff permission) via the admin API/CLI.
2. Log in as this `view` user to obtain a GraphQL session cookie.
3. Issue the following GraphQL query against `/query` (or equivalent GraphQL endpoint):
```graphql
query {
  bridges(limit: 10) {
    results {
      name
      url
      outgoingToken
    }
  }
}
```
4. Because `Bridges`/`Bridge` resolvers only call `authenticateUser` (which accepts any authenticated session including `view`) [8](#0-7) , and `BridgeResolver.OutgoingToken()` unconditionally returns the raw token [5](#0-4) , the response discloses the live `outgoingToken` secret to the low-privilege `view` user.

// on the request context if it exists. It is the responsibility of each resolver

// We currently only support GQL authentication by session cookie.
func AuthenticateGQL(authenticator Authenticator, lggr logger.Logger) gin.HandlerFunc {
	return func(c *gin.Context) {
		ctx := c.Request.Context()
		session := sessions.Default(c)
		sessionID, ok := session.Get(SessionIDKey).(string)
		if !ok {
			return
		}

		user, err := authenticator.AuthorizedUserWithSession(ctx, sessionID)
		if err != nil {
			if errors.Is(err, clsessions.ErrUserSessionExpired) {
				lggr.Warnw("Failed to authenticate session", "err", err)
			} else {
				lggr.Errorw("Failed call to AuthorizedUserWithSession, unable to get user", "err", err)
			}
			return
		}

		ctx = WithGQLAuthenticatedSession(c.Request.Context(), user, sessionID)

		c.Request = c.Request.WithContext(ctx)
	}
}

// Authenticates the user from the session cookie, presence of user inherently provides 'view' access.
func authenticateUser(ctx context.Context) error {
	if _, ok := auth.GetGQLAuthenticatedSession(ctx); !ok {
		return unauthorizedError{}
	}
	return nil
}

// Authenticates the user from the session cookie and asserts at least 'run' role.
func authenticateUserCanRun(ctx context.Context) error {
	session, ok := auth.GetGQLAuthenticatedSession(ctx)
	if !ok {
		return unauthorizedError{}
	}
	if session.User.Role == sessions.UserRoleView {
		return RoleNotPermittedError{session.User.Role}
	}
	return nil
}

// Authenticates the user from the session cookie and asserts at least 'edit' role.
func authenticateUserCanEdit(ctx context.Context) error {
	session, ok := auth.GetGQLAuthenticatedSession(ctx)
	if !ok {
		return unauthorizedError{}
	}
	switch session.User.Role {
	case sessions.UserRoleView, sessions.UserRoleRun:
		return RoleNotPermittedError{session.User.Role}
	default:
	}
	return nil
}

// Authenticates the user from the session cookie and asserts has 'admin' role
func authenticateUserIsAdmin(ctx context.Context) error {
	session, ok := auth.GetGQLAuthenticatedSession(ctx)
	if !ok {
		return unauthorizedError{}
	}
	if session.User.Role != sessions.UserRoleAdmin {
		return RoleNotPermittedError{session.User.Role}
	}
	return nil
}

// Bridge retrieves a bridges by name.
func (r *Resolver) Bridge(ctx context.Context, args struct{ ID graphql.ID }) (*BridgePayloadResolver, error) {
	if err := authenticateUser(ctx); err != nil {
		return nil, err
	}

	name, err := bridges.ParseBridgeName(string(args.ID))
	if err != nil {
		return nil, err
	}

	bridge, err := r.App.BridgeORM().FindBridge(ctx, name)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return NewBridgePayload(bridge, err), nil
		}

		return nil, err
	}

	return NewBridgePayload(bridge, nil), nil
}
