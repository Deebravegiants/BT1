Based on my research, I found a concrete analog of the missing-domain-separator bug class in the JWT/digest-based signature verification used for gateway HTTP-trigger authorization.

### Title
JWT-based request authorization lacks binding between the signed digest and the workflow/audience it is authorizing, enabling signature replay across workflows - (File: core/utils/jwt.go, core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
`CreateRequestJWT`/`VerifyRequestJWT` sign and verify a JSON-RPC request purely by hashing the request body (`req.Digest()`) and wrapping it in a JWT whose only bound claims that are actually checked are `jti` (replay id), `exp`/`iat` (expiry), and the `digest` itself.

### Finding Description
The JWT payload structure includes an optional `aud` (audience) claim [1](#0-0) , but `VerifyRequestJWT` never validates the `Audience` claim against the workflow, gateway, or DON the caller is targeting — it only checks `ID`, `ExpiresAt`, `IssuedAt`, and that `Digest` matches the recomputed request digest [2](#0-1) . The digest itself is derived solely from the JSON-RPC `Request` payload via `req.Digest()`, with no domain-separating context such as the target workflow ID, DON/gateway identity, or chain scope folded into the signed material at the JWT layer. Authorization in `WorkflowMetadataHandler.Authorize` then verifies this JWT and, only after verification, separately checks whether the recovered signer key is present in `authorizedKeys[workflowID]` — the `workflowID` binding is enforced purely as an out-of-band lookup key, not something the signature itself commits to [3](#0-2) . This mirrors the report's root cause: the signed payload's digest is missing a domain separator that ties the authorization to the specific execution context (here, workflow/audience) it is meant to be scoped to, relying instead on incidental request-content matching plus a separate map lookup for authorization boundary enforcement.

### Impact Explanation
If the same signer (an authorized key holder) has requests routed against multiple workflows or the request body used to construct the digest doesn't include workflow-scoping fields, a validly-signed JWT+request pair intended for one workflow/audience could be revalidated against a different workflow lookup path, since the cryptographic digest never commits to the workflow/audience context and the `aud` claim designed for this purpose is silently ignored during verification.

### Likelihood Explanation
Exploitability depends on whether the JSON-RPC request body passed into `Authorize` (params) already embeds workflow-identifying fields that would naturally prevent cross-workflow replay; I could not fully verify this from the code available to me, since I don't have visibility into the exact request payload construction at the `http_trigger_handler.go` call site content. This is a genuine gap in the verification logic (unused `aud` claim) grounded in the same code, but I cannot confirm end-to-end exploitability without further inspection of that handler.

### Recommendation
Bind the JWT digest (or a required, validated claim) to the full authorization context — workflow ID, DON/gateway identity — and enforce the `Audience` claim check in `VerifyRequestJWT` rather than leaving it unvalidated, so a signature cannot be considered valid outside the exact scope it was issued for.

### Proof of Concept
Not constructed — requires confirming, from `http_trigger_handler.go` and the underlying HTTP trigger request schema (not fully available in the index), whether the signed request body already embeds the workflow ID/audience such that cross-workflow digest collision is actually reachable by an unprivileged client.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}
