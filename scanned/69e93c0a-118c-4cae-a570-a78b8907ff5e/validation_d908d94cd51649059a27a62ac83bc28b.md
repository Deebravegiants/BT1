## Analysis

The reported bug class (log injection via unsanitized CRLF-containing user input, as in `Rack::CommonLogger`/`Rack::Auth::Basic`) has a direct analog in Chainlink's Operator UI/API session (login) flow.

`core/web/sessions_controller.go`'s `Create` handler binds the `email`/`password` fields straight from the unauthenticated `POST /sessions` JSON body into a `clsessions.SessionRequest` and passes it to the configured `AuthenticationProvider().CreateSession(ctx, sr)` [1](#0-0) . This session-request struct's `Email` field is fully attacker-controlled and is never checked for control characters before use.

In the LDAP authentication backend, `ldapAuthenticator.CreateSession` logs the raw, unsanitized `sr.Email` directly into a formatted log line at `Info` level: [2](#0-1) 
```go
l.lggr.Infof("Successful LDAP login request for user %s - %s", sr.Email, foundUser.Role)
```
Note that `escapedEmail` (the `ldap.EscapeFilter`-sanitized value) is used only for the LDAP bind DN construction, not for this log statement — the raw `sr.Email` is what's interpolated into the log message [3](#0-2) . Other failed-login paths in the same file also format `sr.Email`/`escapedEmail` straight into `Infof` calls [4](#0-3) , and the group-membership lookup path logs unescaped LDAP attribute values the same way [5](#0-4) .

By contrast, the OIDC backend's equivalent local-admin login path explicitly strips `\n`/`\r` before logging the email, showing the project is aware of this exact risk elsewhere but did not apply the same fix to the LDAP backend: [6](#0-5) 
```go
sanitizedEmail := strings.ReplaceAll(sr.Email, "\n", "")
sanitizedEmail = strings.ReplaceAll(sanitizedEmail, "\r", "")
oi.lggr.Infof("Successful local admin login request for user %s - %s", sanitizedEmail, foundUser.Role)
```
The zap-based `SugaredLogger.Infof` used here performs no CRLF/control-character escaping of its own — it just formats the string into the log message, so any newline/carriage-return characters submitted in the `email` JSON field pass straight through into the log stream.

### Title
Log Injection via Unsanitized `email` Field in LDAP Login Logging - (File: core/sessions/ldapauth/ldap.go)

### Summary
`ldapAuthenticator.CreateSession` (and related LDAP login/failure paths) log the raw, client-supplied `SessionRequest.Email` value using `Infof`-style string formatting without stripping CRLF or other control characters, allowing an unauthenticated caller of `POST /sessions` to inject forged log lines or corrupt the Chainlink node's log stream — the same bug class as `Rack::CommonLogger`/CVE-2025-25184.

### Finding Description
The `/sessions` HTTP endpoint (`SessionsController.Create`) accepts an unauthenticated JSON body and forwards its `Email` field unmodified to the configured `AuthenticationProvider.CreateSession` [7](#0-6) . When the LDAP authentication backend is configured, `ldapAuthenticator.CreateSession` calls:
```go
l.lggr.Infof("Successful LDAP login request for user %s - %s", sr.Email, foundUser.Role)
``` [2](#0-1) 
and earlier failure-path logging:
```go
l.lggr.Infof("Error binding user authentication request in LDAP Bind: %v", err)
...
l.lggr.Infof("Successful user login, but error querying for user groups: user: %s, error %v", escapedEmail, err)
``` [4](#0-3) 
None of these strip `\n`/`\r`/other control characters from the email value before interpolating it into a single log line. The value only gets `ldap.EscapeFilter`-escaped for use in the LDAP search filter/bind DN (a separate variable, `escapedEmail`), not for logging purposes at line 435, where the raw `sr.Email` is used. Since login is unauthenticated by definition, any external, unprivileged client can trigger this code path simply by POSTing a crafted `email` value containing newline characters.

### Impact Explanation
An attacker who does not need any credentials can inject arbitrary fabricated log lines (including fake success/failure entries, spoofed usernames, or injected structured-looking text) into the node operator's log files. This can be used to: obscure genuine malicious login attempts, frame other users, pollute log-based alerting/SIEM pipelines with fabricated entries, or (depending on downstream log consumers) attempt secondary injection (e.g., log-forging that mimics other subsystems' output). This matches CWE-117 (Log Injection) / CWE-93 (CRLF Injection) as described in the advisory, scoped to Chainlink's own authentication logging rather than Rack.

### Likelihood Explanation
High reachability: the vulnerable code executes on every login attempt against an LDAP-backed node, triggered by an unauthenticated `POST /sessions` request with no prerequisites other than the operator having LDAP auth configured. No valid credentials are required to reach the vulnerable `Infof` calls (the bind-failure and lookup-failure paths execute before/regardless of successful authentication).

### Recommendation
Sanitize (strip or escape `\n`/`\r`/other control characters) any user-controlled value — especially `sr.Email` — before interpolating it into free-form log messages in `core/sessions/ldapauth/ldap.go`, mirroring the sanitization already applied in `core/sessions/oidcauth/oidc.go`'s `CreateSession` (`sanitizedEmail := strings.ReplaceAll(sr.Email, "\n", ""); ...`). Prefer switching these `Infof`/`Errorf`-style calls to structured logging (`lggr.Infow("...", "email", sr.Email, ...)`) with a logger that treats field values as data rather than format-string content, consistent with the existing `remote.SanitizeLogString` helper used elsewhere in the codebase [8](#0-7) .

### Proof of Concept
1. Configure a Chainlink node with LDAP authentication enabled.
2. Send an unauthenticated request:
```
POST /sessions
Content-Type: application/json

{"email":"attacker@example.com\nINFO: Successful LDAP login request for user admin@example.com - admin","password":"anything"}
```
3. The LDAP bind fails (or falls back to local auth failure), but before/while doing so, `ldapAuthenticator.CreateSession`/`localLoginFallback` logs the raw `sr.Email` value via `Infof`, injecting a forged, attacker-controlled log line (e.g., fabricating a fake "admin" success entry) into the node's log output.

func (l *ldapAuthenticator) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	conn, err := l.ldapClient.CreateEphemeralConnection()
	if err != nil {
		return "", errors.New("unable to establish connection to LDAP server with provided URL and credentials")
	}
	defer conn.Close()

	var returnErr error

	// Attempt to LDAP Bind with user provided credentials
	escapedEmail := ldap.EscapeFilter(strings.ToLower(sr.Email))
	searchBaseDN := fmt.Sprintf("%s=%s,%s,%s", l.config.BaseUserAttr(), escapedEmail, l.config.UsersDN(), l.config.BaseDN())
	if err = conn.Bind(searchBaseDN, sr.Password); err != nil {
		l.lggr.Infof("Error binding user authentication request in LDAP Bind: %v", err)
		returnErr = errors.New("unable to log in with LDAP server. Check credentials")
	}

	// Bind was successful meaning user and credentials are present in LDAP directory
	// Reuse FindUser functionality to fetch user roles used to create ldap_session entry
	// with cached user email and role
	foundUser, err := l.FindUser(ctx, escapedEmail)
	if err != nil {
		l.lggr.Infof("Successful user login, but error querying for user groups: user: %s, error %v", escapedEmail, err)
		returnErr = errors.New("log in successful, but no assigned groups to assume role")
	}
