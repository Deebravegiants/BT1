### Title
Under-protected Bridge Show endpoint leaks the bridge's `OutgoingToken` secret to view-only users - ([File: core/web/router.go], [File: core/web/presenters/bridges.go])

### Summary
The GitLab CVE describes "Incorrect Access Control" — a case where an authenticated but lower-privileged actor can reach data/actions that should require a higher privilege level. The chainlink node HTTP API has an analogous route-level authorization gap: `GET /v2/bridge_types/:BridgeName` is registered without any role check, so any authenticated user (including the lowest `view` role) can retrieve a bridge's `OutgoingToken`, a credential that is otherwise treated as write/edit-restricted for creation and modification.

### Finding Description
In `core/web/router.go`, the bridge routes are registered as: [1](#0-0) 

```go
bt := BridgeTypesController{app}
authv2.GET("/bridge_types", paginatedRequest(bt.Index))
authv2.POST("/bridge_types", auth.RequiresEditRole(bt.Create))
authv2.GET("/bridge_types/:BridgeName", bt.Show)
authv2.PATCH("/bridge_types/:BridgeName", auth.RequiresEditRole(bt.Update))
authv2.DELETE("/bridge_types/:BridgeName", auth.RequiresEditRole(bt.Destroy))
```

Note that `Create`, `Update`, and `Destroy` are wrapped in `auth.RequiresEditRole`, requiring at least the `edit` role — but `bt.Show` is registered bare, requiring only that the request pass the generic `Authenticate` middleware (session or API token), with no role check at all [2](#0-1) .

The handler returns a `BridgeResource` presenter that includes `OutgoingToken` unconditionally: [3](#0-2) 

```go
type BridgeResource struct {
	JAID
	Name          string `json:"name"`
	URL           string `json:"url"`
	Confirmations uint32 `json:"confirmations"`
	// The IncomingToken is only provided when creating a Bridge
	IncomingToken          string       `json:"incomingToken,omitempty"`
	OutgoingToken          string       `json:"outgoingToken"`
	...
}
```

`OutgoingToken` is a secret bearer credential the node presents to the external bridge adapter (comparable in sensitivity to an API secret) — it is not marked `omitempty` and is not redacted for lower-privilege roles. The role-based access control (RBAC) middleware (`RequiresRunRole`, `RequiresEditRole`, `RequiresAdminRole`) defined in `core/web/auth/auth.go` [4](#0-3)  exists precisely to gate this kind of sensitive data/action by role, but it was not applied to the `Show` route, meaning the `view` role — whose entire purpose is read-only, non-sensitive access — can retrieve this secret token for any bridge whose name it knows or can guess/enumerate.

The project's own RBAC route map test documents (but does not flag as wrong) this gap: `{"GET", "/v2/bridge_types/MOCK", true, true, true}` [5](#0-4)  shows `viewOnlyAllowed: true` for this route, confirming `view`-role users pass this endpoint successfully in the test suite, while `POST`/`PATCH`/`DELETE` bridge_types routes correctly disallow `view` and `run` roles.

### Impact Explanation
An attacker who compromises or is issued a `view`-role API token/session (the lowest privilege tier, intended for read-only dashboards/monitoring) can enumerate bridge names via `GET /v2/bridge_types` (also viewable at `view` role) and then fetch each bridge's `OutgoingToken` via `GET /v2/bridge_types/:BridgeName`. This token authenticates the node to the external bridge adapter; obtaining it allows an attacker to impersonate the node when calling the adapter, or to use it to determine trust boundaries and pivot into external systems the operator did not intend `view` users to reach. This is a genuine broken/incorrect access control issue reachable from an authenticated but minimally-privileged unprivileged actor.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment that issues `view`-role credentials to lower-trust users (e.g., read-only dashboards, external monitoring integrations, junior operators) — a common practice specifically because `view` is supposed to be safe for such use. No additional exploitation complexity is required beyond having a valid `view` session/token and knowing (or listing) a bridge name.

### Recommendation
- Wrap `GET /v2/bridge_types/:BridgeName` with `auth.RequiresEditRole` (or at minimum `auth.RequiresRunRole`) so `view`-role users cannot retrieve `OutgoingToken`.
- Alternatively, keep the route open to all authenticated roles but redact `OutgoingToken` from the presenter output unless the requesting user has `edit`/`admin` role (mirroring how `IncomingToken` is already only returned at creation time).
- Extend the RBAC route-map test (`core/web/auth/auth_test.go`) to assert `viewOnlyAllowed: false` (and ideally `editMinimalAllowed: false`) for this route once fixed, so future regressions are caught.

### Proof of Concept
1. Create a bridge as an admin/edit user (`POST /v2/bridge_types`), noting the returned `outgoingToken`.
2. Create or use a `view`-role user/API token (`sessions.UserRoleView`).
3. As the `view` user, call `GET /v2/bridge_types` to enumerate bridge names, then `GET /v2/bridge_types/<BridgeName>`.
4. Observe the JSON response includes `"outgoingToken": "<secret>"` despite the requester having only `view` privileges, and despite `POST`/`PATCH`/`DELETE` on the same resource correctly returning `403 Forbidden` for this role (as validated by `TestRBAC_Routemap_ViewOnly` in `core/web/auth/auth_test.go`).

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
