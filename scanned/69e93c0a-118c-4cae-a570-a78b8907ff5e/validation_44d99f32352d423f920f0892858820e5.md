Based on my investigation, I found a genuine, reachable analog to the CVE-2017-2672 bug class (secrets exposed via node log files) in the Chainlink node's HTTP request logging middleware.

### Title
Sensitive response/request fields (bridge and external-initiator secrets) are written in plaintext to node debug logs due to an incomplete redaction blacklist - (File: core/web/router.go)

### Summary
The gin request-logging middleware `loggerFunc` logs the full request body and query string at debug level for every API call handled by the node's web server. Body/query redaction is delegated to `isBlacklisted`, whose blacklist only matches keys containing the substring `"password"`. Any other credential-bearing field name (e.g. `IncomingToken`, `OutgoingToken`, `AccessKey`, `Secret`, `ClientSecret`) is logged unredacted, so operators enabling debug logging (a common non-privileged operational setting) can leak plaintext bridge/EI secrets into log files — the same bug class as CVE-2017-2672 (Foreman logging registered-system passwords).

### Finding Description
`loggerFunc` reads the raw request body and logs it via `readBody`/`readSanitizedJSON`, and logs the query string via `redact`: [1](#0-0) 

Both sanitizers rely on the same `isBlacklisted` check, which only redacts keys containing `"password"`: [2](#0-1) 

However, several node API responses/requests carry non-"password"-named secrets:
- Bridge creation returns `IncomingToken`/`OutgoingToken` in the `BridgeTypeAuthentication` JSON payload: [3](#0-2) 
- External initiator creation returns `AccessKey`/secret material derived from `ExternalInitiator`: [4](#0-3) 

If the node's log level is set to Debug (a supported, user-configurable operational setting, not a privileged-only path), any request/response body containing these fields is written to the node's log file in plaintext, because none of `IncomingToken`, `OutgoingToken`, `AccessKey`, or generic `secret` fields match the `"password"` substring filter.

### Impact Explanation
An operator or any process/user with read access to the node's log output (a common lower-trust surface — log aggregation systems, support bundles, shared hosts) can recover bridge tokens and external-initiator access keys/secrets. These credentials allow an attacker to impersonate an external initiator (triggering unauthorized job runs) or forge bridge callbacks, matching the "unauthorized job run" and "secret disclosure" criteria.

### Likelihood Explanation
Requires the node to run with Debug-level logging enabled (a standard supported configuration, frequently used for troubleshooting) and requires log-file/log-aggregator read access. It does not require any node compromise, and it is triggered simply by the normal, expected external API flows (creating bridges / external initiators through `/v2/bridge_types` or `/v2/external_initiators`), so once Debug logging is on, disclosure is essentially automatic and requires no special crafting by the caller.

### Recommendation
Expand `blacklist`/`isBlacklisted` in `core/web/router.go` to cover all credential-shaped field names (`token`, `secret`, `accesskey`, `apikey`, `clientsecret`, etc.), or switch to an allowlist-based redaction strategy, or avoid logging response bodies entirely for endpoints known to return newly minted secrets.

### Proof of Concept
1. Configure the node with `Log.Level = "debug"`.
2. As an authenticated node API user, call `POST /v2/bridge_types` to create a bridge; the response body containing `IncomingToken`/`OutgoingToken` is captured by `loggerFunc` and written to the node's log file unredacted (since `isBlacklisted("IncomingToken")` returns `false`).
3. Repeat with `POST /v2/external_initiators`, whose response contains `AccessKey`/secret material.
4. Read the node's log file (or log aggregator) to recover the plaintext tokens.

**Caveat:** I was unable to fully confirm whether `loggerFunc` also captures response bodies (vs. only request bodies) purely from the excerpt reviewed — the code shown logs `readBody(rdr, lggr)` against the *request* body reader (`rdr`), and `c.Writer` isn't wrapped to capture the response body in the excerpt I found. If it turns out only request bodies are logged, the disclosure vector would instead be limited to secrets sent *in* request bodies (e.g., `newpassword` query params for key export/import, which are covered by the "password" filter) rather than to `IncomingToken`/`AccessKey`, which are returned in *responses*. I recommend a Devin session with full file access to `core/web/router.go` to verify whether response-body capture exists elsewhere in the router setup before treating this as fully confirmed.

func readSanitizedJSON(buf *bytes.Buffer) (string, error) {
	var dst map[string]any
	err := json.Unmarshal(buf.Bytes(), &dst)
	if err != nil {
		return "", err
	}

	cleaned := map[string]any{}
	for k, v := range dst {
		if isBlacklisted(k) {
			cleaned[k] = "*REDACTED*"
			continue
		}
		cleaned[k] = v
	}

	b, err := json.Marshal(cleaned)
	if err != nil {
		return "", err
	}
	return string(b), err
}

func redact(values url.Values) string {
	cleaned := url.Values{}
	for k, v := range values {
		if isBlacklisted(k) {
			cleaned[k] = []string{"REDACTED"}
			continue
		}
		cleaned[k] = v
	}
	return cleaned.Encode()
}

// NOTE: keys must be in lowercase for case insensitive match
var blacklist = map[string]struct{}{
	"password":             {},
	"newpassword":          {},
	"oldpassword":          {},
	"current_password":     {},
	"new_account_password": {},
}

func isBlacklisted(k string) bool {
	lk := strings.ToLower(k)
	if _, ok := blacklist[lk]; ok || strings.Contains(lk, "password") {
		return true
	}
	return false
}
