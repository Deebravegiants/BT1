### Title
Username Enumeration via Distinguishable Login Error Responses in `/sessions` Endpoint - (File: core/web/sessions_controller.go)

### Summary
The unauthenticated `POST /sessions` login endpoint returns different, distinguishable error messages depending on whether a submitted email corresponds to an existing account or not, allowing an unauthenticated attacker to enumerate valid usernames (emails) on a Chainlink node — the same bug class as CVE-2022-41414 (insecure default disclosing valid usernames through login behavior).

### Finding Description
The login flow is: `SessionsController.Create` binds the request, calls `AuthenticationProvider().CreateSession(ctx, sr)`, and on error forwards the raw error straight to the client via `jsonAPIError(c, http.StatusUnauthorized, err)`. [1](#0-0) 

`jsonAPIError` serializes `err.Error()` directly into the JSON response when the error isn't a `*models.JSONAPIErrors`: [2](#0-1) 

In the local auth provider, `CreateSession` calls `FindUser`, and if the email doesn't exist, the raw database error (`sql: no rows in result set`) is propagated unchanged: [3](#0-2) 

By contrast, if the email exists but the password is wrong, a distinct message `"Invalid password"` is returned, and if the (already looked-up) email fails a constant-time compare, `"Invalid email"` is returned: [4](#0-3) 

The result: an unauthenticated client posting to `/sessions` with a non-existent email sees `sql: no rows in result set`, while a request with a valid, existing email and a wrong password sees `"Invalid password"`. This distinguishable response pair leaks whether a given email is a registered Chainlink node user/admin account — directly mirroring the Liferay `auth.login.prompt.enabled` finding, which also allowed unprivileged actors to enumerate valid usernames via login-flow response differences.

### Impact Explanation
An unauthenticated network attacker can enumerate valid admin/API user emails on a Chainlink node by observing whether the login endpoint returns the SQL "no rows" error versus "Invalid password"/"Invalid email". This information supports targeted credential-stuffing, phishing, or brute-force attacks against confirmed accounts, and discloses account existence information that should remain private (CWE-276 class: insecure default / information disclosure via authentication flow). It does not, on its own, bypass authentication or leak secrets/keys, keeping the severity at the "confidentiality: low" tier, consistent with the referenced advisory's CVSS (`C:L/I:N/A:N`).

### Likelihood Explanation
High likelihood of exploitability: the `/sessions` endpoint is reachable by any unauthenticated client (only rate-limited, not blocked) as wired in `sessionRoutes`: [5](#0-4) 
No privileged access or special conditions are required — just two POST requests with different emails.

### Recommendation
Normalize authentication failure responses so that unknown-email and wrong-password cases are indistinguishable to the client (e.g., always return a single generic message such as `"invalid email or password"` with the same status code and, ideally, comparable timing), and ensure `FindUser`'s `sql.ErrNoRows` is translated to that generic error before being returned from `CreateSession`, rather than letting the raw database error propagate through `jsonAPIError`.

### Proof of Concept
```
POST /sessions {"email":"nonexistent@x.com","password":"whatever"}
-> 401 {"errors":[{"detail":"sql: no rows in result set"}]}

POST /sessions {"email":"real-admin@company.com","password":"wrongpass"}
-> 401 {"errors":[{"detail":"Invalid password"}]}
```
The differing `detail` field allows an attacker to confirm `real-admin@company.com` is a valid, registered account while `nonexistent@x.com` is not.

func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
