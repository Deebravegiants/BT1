### Title
External initiator feature-disable flag is not enforced at authentication time, only at creation time - (File: core/web/external_initiators_controller.go, core/web/auth/auth.go)

### Summary
The `ExternalInitiatorsEnabled` configuration flag is checked only when an external initiator (EI) is *created* via `ExternalInitiatorsController.Create`, but the actual authentication/authorization path that grants the privileged `run` role to a caller — `AuthenticateExternalInitiator` — never re-checks this flag. This mirrors the reported Neptune Mutual bug class: a security-relevant requirement ("NPM must be staked" / "the EI feature must be enabled") is enforced on one code path (deposit / creation) but is not enforced on the path that actually grants the sensitive capability (liquidity provision / job-run triggering), so the requirement can be trivially bypassed by using the other path.

### Finding Description
`ExternalInitiatorsController.Create` gates the creation of a new external initiator behind the `JobPipeline().ExternalInitiatorsEnabled()` config flag: [1](#0-0) 

However, the function that actually authenticates an external initiator's HTTP request and elevates it to the privileged `UserRoleRun` role — `AuthenticateExternalInitiator` — performs no equivalent check of this flag. It only validates the access-key/secret pair against the stored record and then unconditionally sets the run role: [2](#0-1) 

Because the enable/disable check lives solely in the creation controller, any external initiator record that already exists in the database (created while the feature was enabled) continues to authenticate successfully and continues to be granted `UserRoleRun` even after an operator disables the feature via config (`ExternalInitiatorsEnabled = false`). The authentication/authorization enforcement point (`AuthenticateExternalInitiator`) and the feature-gate enforcement point (`Create`) are decoupled, exactly as in the Neptune Mutual report where the staking check is enforced at `addLiquidity` but bypassable via `removeLiquidity`'s `exit` path.

### Impact Explanation
An operator who disables the External Initiator feature (e.g., in response to abuse or a security incident) expects that external initiators can no longer trigger job runs. Because `AuthenticateExternalInitiator` does not consult the `ExternalInitiatorsEnabled` flag, any previously-created external initiator credentials remain fully functional and can continue to authenticate and trigger job runs (`UserRoleRun`) against the node, defeating the intended kill-switch. This is a role/authorization bypass of an admin-configured control, not merely a cosmetic gap: it results in unauthorized job-run triggering via credentials that the operator believed were revoked in effect.

### Likelihood Explanation
Any deployment that has ever created an external initiator and later disables the feature (a documented, supported operational action) is affected. No attacker-side sophistication is required — an existing EI's already-issued `AccessKey`/`Secret` continue to work unchanged; the only precondition is that the flag was toggled off after EI creation, which is a normal operational/incident-response scenario.

### Recommendation
Move the `ExternalInitiatorsEnabled` check into `AuthenticateExternalInitiator` (or a shared checkpoint reached by every authenticated EI request) so that disabling the feature also disables authentication/execution for any pre-existing external initiator records, not just future creation of new ones.

### Proof of Concept
1. Ensure `JobPipeline.ExternalInitiatorsEnabled = true`; call `POST /v2/external_initiators` to create an EI (`ExternalInitiatorsController.Create`), obtaining `AccessKey`/`Secret`.
2. Operator sets `JobPipeline.ExternalInitiatorsEnabled = false` and restarts/reconfigures the node.
3. Using the previously obtained `AccessKey`/`Secret`, send an authenticated request routed through `AuthenticateExternalInitiator` (e.g., a job-run trigger endpoint guarded by this auth method).
4. Observe the request is authenticated and granted `UserRoleRun` — as shown by [3](#0-2)  — with no check against `ExternalInitiatorsEnabled`, demonstrating the disabled feature is not actually enforced for existing credentials.

// AuthenticateExternalInitiator authenticates an external initiator request.
//
// Implements authMethod
func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}
