### Title
Authenticated SQL Injection via unsanitized `taskName` in `FindTaskResultByRunIDAndTaskName` - (File: core/services/job/orm.go)

### Summary
`orm.FindTaskResultByRunIDAndTaskName` builds a SQL query by directly interpolating the `taskName` parameter into the query string with `fmt.Sprintf`, rather than passing it as a bound parameter, mirroring the classic string-concatenation SQL injection pattern in the referenced GLPI Fields CVE-2024-45600.

### Finding Description
The function constructs its query as: [1](#0-0) 

Only `runID` is passed as a bound `$1` parameter; `taskName` is spliced directly into the SQL text via `%s` inside a single-quoted string literal, with no escaping or parameterization. If `taskName` were reachable from any external, less-trusted input, an attacker could break out of the string literal (e.g. `' OR '1'='1`, or subqueries/UNION) to alter query semantics or exfiltrate data from other tables.

However, unlike the GLPI case (attacker-controlled custom field values processed by any authenticated user), I could not find any live caller of `FindTaskResultByRunIDAndTaskName` anywhere in the codebase outside of the interface declaration and its generated mock (`core/services/job/mocks/orm.go`). No controller, GraphQL resolver, or gateway handler in this repository invokes this method, so there is no currently reachable path from an unprivileged (or even privileged) client request into this code.

### Impact Explanation
As written, if this method were wired into any handler that accepts `taskName` from a request (e.g., a future pipeline-run task-result lookup endpoint), it would allow full SQL injection with the privileges of the node's database user — potentially reading/modifying unrelated tables (session tokens, API keys, job specs) or affecting availability. This would be a High severity issue analogous to CVE-2024-45600.

### Likelihood Explanation
Currently low/unproven: the method appears unreachable from any documented API path in this snapshot of the codebase. Exploitability depends entirely on some caller (not present here) passing externally-controlled `taskName` into it. Without a live call site, this cannot be confirmed as an active, exploitable vulnerability from an unprivileged actor today — only as a latent bug-class instance (unsafe string interpolation into SQL) that should be fixed defensively before any new caller is added.

### Recommendation
Regardless of current reachability, fix the query to use a bound parameter instead of string interpolation:
```go
stmt := "SELECT * FROM pipeline_task_runs WHERE pipeline_run_id = $1 AND dot_id = $2;"
...
o.ds.SelectContext(ctx, &taskRuns, stmt, runID, taskName)
```
Audit the codebase for any other `fmt.Sprintf`/string-concatenation based SQL construction that mixes non-numeric, potentially externally influenced values directly into query text (the `filter` variable built with `fmt.Sprintf("... = %d AND ", *jobID)` in `loadPipelineRunIDs` is safe since `jobID` is a strictly-typed `int32`, but should still be reviewed for consistency).

### Proof of Concept
Not applicable — no reachable caller/endpoint exists in the current codebase to demonstrate end-to-end exploitation. The vulnerable pattern itself is demonstrable in isolation: a `taskName` value such as `foo' OR '1'='1` would produce the query:
```sql
SELECT * FROM pipeline_task_runs WHERE pipeline_run_id = $1 AND dot_id = 'foo' OR '1'='1';
```
which returns all task runs regardless of `pipeline_run_id`, illustrating the injection primitive if this function is ever exposed to caller-supplied input.
