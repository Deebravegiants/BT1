### Title
Debug-level HTTP request logging writes cleartext passwords to log file/output because sanitization only redacts top-level JSON keys - ([File: core/web/router.go])

### Summary
When `Log.Level = 'debug'` (and optionally `Log.File` is configured), every incoming HTTP request body to the Chainlink node's API is logged via `loggerFunc`, which calls `readBody`/`readSanitizedJSON` to redact sensitive fields before logging. [1](#0-0)  However, the redaction logic only inspects the **top-level keys** of the parsed JSON body and matches on a small hardcoded blacklist (`password`, `newpassword`, `oldpassword`, `current_password`, `new_account_password`, or any key containing the substring "password"). [2](#0-1) 

### Finding Description
`readSanitizedJSON` unmarshals the request body into a flat `map[string]any` and redacts only keys at the top level:
```go
cleaned := map[string]any{}
for k, v := range dst {
    if isBlacklisted(k) {
        cleaned[k] = "*REDACTED*"
        continue
    }
    cleaned[k] = v
}
``` [3](#0-2) 

This is directly analogous to the referenced CVE-2024-53979 class of bug: password-like input fields are written in clear text to a log file (and here also potentially returned/echoed via debug logs) because the redaction/blacklist mechanism does not comprehensively cover all paths where the secret value flows into logging. In this codebase, any endpoint whose password-bearing field is nested (not a top-level JSON key) will bypass the blacklist entirely. For example, `UserController.UpdatePassword` binds a top-level `{"oldPassword":"...","newPassword":"..."}` payload, which the blacklist substring match (`strings.Contains(lk, "password")`) does catch. But any JSONAPI-style request body that wraps password fields under `data.attributes.*` (a pattern used elsewhere in this API, e.g. `keysController.Import`/`Export`, `BridgeTypeRequest`) — or any nested object containing a `password` field — would have only the top-level key (`data`) checked, not the nested attribute. Since `isBlacklisted` never recurses into nested maps/arrays, such nested secrets are logged in cleartext whenever `loggerFunc` fires. [4](#0-3) 

This is a genuine reachable path from any unprivileged/authenticated API client: simply issuing a request that includes a password-like field nested under a wrapper object (not literally a top-level key) while the node has `Log.Level = 'debug'` configured causes the plaintext secret to be written into the node's log stream (console and, if `Log.File` is configured, to disk), where it can later be read by anyone with log access (which is a broader, less-privileged audience than the API itself, e.g. log aggregation systems, support staff, or a `view`-role operator with log access but not API password-change rights).

### Impact Explanation
Passwords or other secrets that bypass the shallow top-level redaction are persisted in cleartext in the node's structured logs. Given that the node's log file/stream is often shipped to log aggregators or accessible to more parties than the admin who owns the credential, this can lead to unauthorized account takeover (via disclosed passwords), matching the "High" severity rationale of the underlying CVE (local, low-complexity, high-privilege-required-to-view-logs, high confidentiality/integrity impact).

### Likelihood Explanation
Likelihood is contingent on: (1) the operator having enabled `Log.Level = 'debug'` (not default; default is `info`), and (2) a request containing a nested password-bearing payload being made. Since `debug` logging is a documented, supported configuration (and is even exercised in test fixtures such as `testdata/scripts/node/validate/disk-based-logging.txtar`), and API clients regularly submit structured/nested JSON bodies, this is plausible in real deployments that enable verbose logging for troubleshooting. [5](#0-4) 

### Recommendation
Make `readSanitizedJSON`/`isBlacklisted` recurse into nested maps and arrays instead of only checking top-level keys, so that any field name matching the blacklist (at any nesting depth) is redacted before being logged. Additionally, expand the blacklist to cover other well-known secret field names (e.g. `token`, `secret`, `apiKey`, `bindPassword`, etc.) used across the API's request DTOs (bridges, keys import/export, LDAP config, etc.).

### Proof of Concept
1. Configure the node with `Log.Level = 'debug'` (optionally with `Log.File` enabled to persist to disk).
2. Send an authenticated API request whose JSON body wraps a password-bearing field inside a nested object, e.g.:
```json
{
  "data": {
    "type": "someResource",
    "attributes": {
      "password": "SuperSecretPass123!"
    }
  }
}
```
3. Observe the resulting debug log line produced by `loggerFunc` (`core/web/router.go:556-567`): because `readSanitizedJSON` only redacts the top-level key `data`, the nested `attributes.password` value is logged verbatim in the `"body"` field of the log entry, exposing the cleartext secret in the log stream/log file.

func readSanitizedJSON(buf *bytes.Buffer) (string, error) {
	var dst map[string]any
	err := json.Unmarshal(buf.Bytes(), &dst)
	if err != nil {
		return "", err
	}

	cleaned := map[string]any{}
	for k, v := range dst {
		if isBlacklisted(k) {
			cleaned[k] = "*REDACTED*"
			continue
		}
		cleaned[k] = v
	}

	b, err := json.Marshal(cleaned)
	if err != nil {
		return "", err
	}
	return string(b), err
}

func redact(values url.Values) string {
	cleaned := url.Values{}
	for k, v := range values {
		if isBlacklisted(k) {
			cleaned[k] = []string{"REDACTED"}
			continue
		}
		cleaned[k] = v
	}
	return cleaned.Encode()
}

// NOTE: keys must be in lowercase for case insensitive match
var blacklist = map[string]struct{}{
	"password":             {},
	"newpassword":          {},
	"oldpassword":          {},
	"current_password":     {},
	"new_account_password": {},
}

func isBlacklisted(k string) bool {
	lk := strings.ToLower(k)
	if _, ok := blacklist[lk]; ok || strings.Contains(lk, "password") {
		return true
	}
	return false
}
