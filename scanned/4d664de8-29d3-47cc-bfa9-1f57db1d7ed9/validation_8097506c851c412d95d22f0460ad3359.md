### Title
Persistent Secret Token Disclosure via External Initiator List/Read API - ([File: core/web/presenters/external_initiators.go])

### Summary
The `GET /v2/external_initiators` endpoint (and single-record reads) returns the `OutgoingToken` secret for every registered External Initiator to any authenticated node user who can reach that endpoint, on every subsequent read — not only at creation time. This mirrors the reported bug class (CVE-2020-13444): an API meant to expose only non-sensitive metadata instead returns a live credential to callers who are not the original creator/owner of the resource.

### Finding Description
When an External Initiator (EI) is created, the node generates two secrets: an `OutgoingToken` and an `OutgoingSecret`, plus an incoming `AccessKey`/hashed `Secret` pair used to authenticate calls *from* the EI to the node. [1](#0-0) 

The incoming credential (`Secret`) is correctly never persisted in plaintext (`HashedSecret`) and is excluded from list/read presenters — it is only returned once, at creation, via `ExternalInitiatorAuthentication`. [2](#0-1) 

However, `OutgoingToken` — a plaintext secret persisted in the `external_initiators` table and used by the node to authenticate itself when calling out to the initiator's webhook — is embedded directly in `ExternalInitiatorResource`, the presenter used for both `Index` (list) and individual reads: [3](#0-2) 

The controller's `Index` handler loads all External Initiators from the ORM and serializes each one through this presenter on every call, re-disclosing the live secret on every list request rather than only once at provisioning time: [4](#0-3) 

This is corroborated by the endpoint test, which asserts `OutgoingToken` is present in the plain `Index` response body for pre-existing (not just newly-created) initiators: [5](#0-4) 

The same pattern exists for Bridge Types, where `BridgeType.OutgoingToken` is likewise a stored plaintext field alongside the (properly hashed) `IncomingTokenHash`: [6](#0-5) 

This directly parallels the Liferay flaw: a data-provider-style read API (`DDMDataProvider`/here, the EI/bridge list API) fails to sanitize/redact a credential field before returning it, allowing any authenticated caller with read access to obtain a password/token belonging to a resource they did not necessarily create.

### Impact Explanation
`OutgoingToken` is a bearer-style secret the Chainlink node presents to the External Initiator's own service when triggering it. Any authenticated node user able to call `GET /v2/external_initiators` (or `/v2/bridge_types`) obtains this secret for *every* configured initiator/bridge, not just ones they created. Since this credential is used to authenticate the node's own outbound calls to third-party EI services, its disclosure lets a lower-privileged internal user impersonate the node's calls to that EI endpoint, potentially triggering unauthorized job runs or interfering with the initiator's trust boundary — this maps to CWE-200 (information exposure) with request-impersonation impact, consistent with the CVSS vector of the source report (`AC:L/PR:L/UI:N/C:H`).

### Likelihood Explanation
Any actor holding a valid node session/API token that can reach standard `/v2/external_initiators` or `/v2/bridge_types` routes can trigger this with a single unauthenticated-to-the-secret GET request; no special privilege beyond basic authenticated access is exercised in the code path itself (the exact RBAC role required for `Index` could not be conclusively confirmed from the available router configuration in this session, but Chainlink's convention typically grants read/list routes to the lowest authenticated role tier).

### Recommendation
- Exclude `OutgoingToken` (and any other live secret) from `ExternalInitiatorResource` and equivalent bridge-type list/read presenters; return it only once, at creation, the same way `Secret`/`AccessKey` (incoming) are already handled.
- If the outgoing token must be verifiable later, store and expose only a hash or truncated/masked representation, requiring re-issuance for full disclosure.
- Apply the same treatment to `core/web/presenters/bridges.go`'s `OutgoingToken` field.

### Proof of Concept
1. Authenticate as any node user with access to list-level routes.
2. Call `GET /v2/external_initiators` (as exercised by `TestExternalInitiatorsController_Index`).
3. Observe that the JSON response includes `outgoingToken` for pre-existing initiators created by others, per [5](#0-4) , confirming the secret is disclosed on every read, not solely at creation.

func NewExternalInitiator(
	eia *auth.Token,
	eir *ExternalInitiatorRequest,
) (*ExternalInitiator, error) {
	salt := utils.NewSecret(utils.DefaultSecretSize)
	hashedSecret, err := auth.HashedSecret(eia, salt)
	if err != nil {
		return nil, pkgerrors.Wrap(err, "error hashing secret for external initiator")
	}

	return &ExternalInitiator{
		Name:           strings.ToLower(eir.Name),
		URL:            eir.URL,
		AccessKey:      eia.AccessKey,
		HashedSecret:   hashedSecret,
		Salt:           salt,
		OutgoingToken:  utils.NewSecret(utils.DefaultSecretSize),
		OutgoingSecret: utils.NewSecret(utils.DefaultSecretSize),
	}, nil
}

type ExternalInitiatorAuthentication struct {
	Name           string        `json:"name,omitempty"`
	URL            models.WebURL `json:"url"`
	AccessKey      string        `json:"incomingAccessKey,omitempty"`
	Secret         string        `json:"incomingSecret,omitempty"`
	OutgoingToken  string        `json:"outgoingToken,omitempty"`
	OutgoingSecret string        `json:"outgoingSecret,omitempty"`
}

// NewExternalInitiatorAuthentication creates an instance of ExternalInitiatorAuthentication.
func NewExternalInitiatorAuthentication(
	ei bridges.ExternalInitiator,
	eia auth.Token,
) *ExternalInitiatorAuthentication {
	var result = &ExternalInitiatorAuthentication{
		Name:           ei.Name,
		AccessKey:      ei.AccessKey,
		Secret:         eia.Secret,
		OutgoingToken:  ei.OutgoingToken,
		OutgoingSecret: ei.OutgoingSecret,
	}
	if ei.URL != nil {
		result.URL = *ei.URL
	}
	return result
}

func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}
