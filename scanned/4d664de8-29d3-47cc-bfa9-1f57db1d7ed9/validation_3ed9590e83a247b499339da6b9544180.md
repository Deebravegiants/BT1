### Title
Missing `return` after failed OIDC email-claim extraction allows session creation to proceed on error path - (File: core/sessions/oidcauth/oidc.go)

### Summary
In `handleTokenExchange`, the OIDC email-claim type assertion failure path writes an HTTP error response but does not `return`, so execution falls through and creates an authenticated session anyway, using an empty/zero-value `email`. This mirrors the reported bug class (a failure signal is generated but not acted upon, so the caller proceeds as if the operation succeeded).

### Finding Description
`handleTokenExchange` extracts the email claim from the verified ID token claims map: [1](#0-0) 

```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims. error: %v", err)
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
}
```

Unlike every other error-handling branch in this same function (missing `id_token`, verify failure, claims parse failure, role-mapping failure — each of which correctly calls `return` after writing the error response), this branch omits the `return`. Execution continues past this check into the rest of the handler, which:

1. Maps the (still valid) OIDC group claims to an RBAC role via `IDClaimsToUserRole`. [2](#0-1) 
2. Inserts a new row into `oidc_sessions` with the empty-string `email` and the resolved role: [3](#0-2) 
3. Emits an audit log entry `AuthLoginSuccessNo2FA` claiming a successful login for that (empty) email: [4](#0-3) 
4. Sets the session cookie and returns HTTP 200 `Success: true` to the client, i.e. the client thinks the login is a full success even though a `StatusInternalServerError` body was already written earlier in the same handler: [5](#0-4) 

The resulting session row is subsequently trusted by `AuthorizedUserWithSession`, which reads `user_email`/`user_role` directly from `oidc_sessions` without any additional validation of the email value: [6](#0-5) 

Note: a second, analogous missing-`return` exists a few lines later after the `INSERT INTO oidc_sessions` error branch (lines 257–260) — on DB insert failure it also writes an error response but falls through to audit-log "success" and set the session cookie, even though no session row exists in the database. [7](#0-6) 

### Impact Explanation
This is reachable by any unprivileged client that can drive the OIDC callback flow (`/oidc-login` → `/exchangeToken`), i.e. anyone who can complete the OAuth2 code exchange against the configured IdP but whose ID token happens to lack an `email` claim (or where the claim isn't a string) — a condition an attacker can influence if they control or can manipulate the identity provider's claim set (e.g. a mis-configured or attacker-influenced upstream IdP, or a race/config bug causing claims to omit `email`). The practical result is:
- A valid, cookie-backed session record is created and returned to the client with `Role` derived from real group claims but tied to an empty-string user identity, and the client is told the login "Succeeded" despite the server having already emitted an internal error.
- The audit trail (`AuthLoginSuccessNo2FA`) is falsified, recording a successful login for an empty email — undermining forensic/audit reliability.
- In the DB-insert-failure variant, the client is issued a session cookie referencing a session ID that does not exist in `oidc_sessions`, producing inconsistent state (though `AuthorizedUserWithSession` will subsequently reject it as `sql.ErrNoRows`/expired, limiting exploitability of that specific sub-case to a confusing-but-not-directly-exploitable state).

This does not directly bypass authentication of a specific victim account (role still derives from genuine IdP group claims, and email is empty rather than attacker-chosen), but it constitutes unauthorized state creation from a failure path and audit-log falsification, which is the exact bug class described in the report (a failure is not checked/acted upon, so the operation is treated as a success with unintended side effects).

### Likelihood Explanation
Requires a specific, less-common IdP misconfiguration (missing/malformed `email` claim) but is triggerable by any client completing the OAuth2 exchange step; no privileged access is needed. Likelihood is moderate — it depends on IdP claim behavior rather than a universally reachable path.

### Recommendation
Add `return` immediately after both error-response blocks so the handler halts on failure:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims")
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
```
and similarly after the `oidc_sessions` INSERT error block (line 257-260), add `return` before the audit log / session-save code executes.

### Proof of Concept
1. Configure/point the OIDC provider (or intercept the exchange) such that the verified ID token's claims map does not include an `email` key (or `email` is a non-string type), while still including valid group claims mapping to some role via `IDClaimsToUserRole`.
2. Complete `/oidc-login` and POST the resulting `code`/`state` to the `/exchangeToken` endpoint (`handleTokenExchange`).
3. Observe: server writes `500 Failed to get email from claims` to the response writer, but processing continues; a row is inserted into `oidc_sessions` with `user_email = ''`; `AuthLoginSuccessNo2FA` is audited; the session cookie (`SessionIDKey`) is set; and the client ultimately receives `ExchangeTokenResponse{Success: true}` (HTTP 200), i.e. a functioning session despite the earlier failure — because ` [1](#0-0) ` lacks the `return` present in every sibling error branch of the same function.
