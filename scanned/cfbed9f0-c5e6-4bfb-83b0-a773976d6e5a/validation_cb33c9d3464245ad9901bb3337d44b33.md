### Title
`responseCache` key omits `WorkflowID` — cross-workflow cached HTTP response confusion despite documented "workflow isolation" - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
`responseCache` in the gateway's HTTP-action handler stores every outbound HTTP response in a single map keyed solely by `req.Hash()` — a hash over method, URL, headers, body, and `WorkflowOwner`. `WorkflowID` and `CacheSettings` are deliberately excluded from the key, contradicting the component's own documented guarantee that cache entries are "workflow-scoped" and isolated "to prevent cross-workflow data leakage."

### Finding Description
`responseCache.Fetch` and `responseCache.Set` use `req.Hash()` as the sole cache key: [1](#0-0) 

The package comment is explicit about which fields participate in the key: "method, URL, headers, body, workflowOwner" — `WorkflowID` is not listed. This is confirmed by the test suite, which documents the behavior as intentional: [2](#0-1) 

Yet the component's own `README.md` states the opposite guarantee for the exact same cache: [3](#0-2) 

Both `Fetch` and `Set` are invoked directly from `makeOutgoingRequest`, which builds `req` straight from an unmarshaled node message and forwards it to the shared cache with no additional scoping by `WorkflowID`: [4](#0-3) 

This is structurally identical to the reported bug class: a mapping/cache key that omits a discriminator field the system's own design assumes is present (here `WorkflowID`, in the report `interval`), causing distinct logical entries — different workflows' HTTP action calls — to collide into the same cache slot whenever method, URL, headers, and body happen to match for the same `WorkflowOwner`. This is a common and easily-triggered scenario for an owner who runs multiple workflows hitting the same shared/public API endpoint with identical parameters (e.g., a price feed, a health check, a static reference API).

### Impact Explanation
When two different workflows belonging to the same `WorkflowOwner` issue outbound HTTP action requests with identical method/URL/headers/body, one workflow's response — including its full body and headers — will be silently served to the other workflow via the shared cache, regardless of the two workflows' distinct identities, intents, or freshness requirements (`CacheSettings` is also excluded from the key). Because the README's "Workflow Isolation" claim leads operators/integrators to trust that this cannot happen, downstream workflow logic that assumes each workflow only ever sees responses to its own requests can silently consume another workflow's response. This is a cross-workflow response confusion vector: an unprivileged workflow author (any owner can author multiple workflows) can unintentionally or intentionally influence what data reaches a sibling workflow through shared cache poisoning, and workflow authors relying on the documented isolation guarantee have no way to detect the collision from their side.

### Likelihood Explanation
Likelihood is moderate-to-high for the "unintentional collision" case: any owner operating more than one workflow that calls the same external endpoint with the same static request parameters (a common pattern — health checks, shared price/reference data, shared health/status endpoints) will hit this by default whenever `CacheSettings.MaxAgeMs > 0` on at least one of the requests. It requires no privilege escalation — it is triggered purely by normal, unprivileged use of the HTTP action capability with `CacheSettings.Store`/`MaxAgeMs` set, which is fully controlled by the workflow author.

### Recommendation
Include `WorkflowID` (and/or `WorkflowExecutionID`, if per-execution isolation is desired) in the cache key, e.g., extend `req.Hash()` upstream (in `chainlink-common`'s `gateway` package) to incorporate `WorkflowID`, or have `responseCache` compose the key as `workflowID + req.Hash()` locally in `response_cache.go`/`isExpiredOrNotCached`. Update the `README.md` claim to match the actual, corrected scoping, and add a regression test analogous to `TestRequestHash`'s "different workflowID" case that asserts the hash *differs* when `WorkflowID` differs, to catch any future regression of this invariant.

### Proof of Concept
1. Deploy two workflows, `wf-A` and `wf-B`, both owned by the same `WorkflowOwner`.
2. Both workflows issue an HTTP action request with identical `Method`, `URL`, `MultiHeaders`, and `Body`, but `wf-A` sets `CacheSettings.Store = true` while `wf-B` sets `CacheSettings.MaxAgeMs > 0` (relying on a fresh cache read).
3. `wf-A`'s request executes first; `makeOutgoingRequest` calls `responseCache.Set`/`Fetch`, storing the response under `req.Hash()` [5](#0-4)  using only method/URL/headers/body/`WorkflowOwner`.
4. `wf-B` subsequently issues its request; because `WorkflowID` is excluded from `Hash()`, `responseCache.Fetch` computes the same `cacheKey` as `wf-A`'s and returns `wf-A`'s cached response to `wf-B` without ever contacting the real endpoint, as demonstrated directly by the "having different workflowID results in same Hash" test [2](#0-1) .
5. `wf-B` receives `wf-A`'s response data, violating the documented "Workflow Isolation" / "prevent cross-workflow data leakage" guarantee in the README.

func (h *gatewayHandler) makeOutgoingRequest(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	requestID := resp.ID
	h.lggr.Debugw("handling outgoing message", "requestID", requestID, "nodeAddr", nodeAddr)
	var req gateway_common.OutboundHTTPRequest
	err := json.Unmarshal(*resp.Result, &req)
	if err != nil {
		return fmt.Errorf("failed to unmarshal HTTP request from node %s: %w", nodeAddr, err)
	}
	timeout := time.Duration(req.TimeoutMs) * time.Millisecond
	httpReq := network.HTTPRequest{
		Method:           req.Method,
		URL:              req.URL,
		Headers:          req.Headers, //nolint:staticcheck // forward deprecated Headers for backward compatibility; request uses MultiHeaders when set
		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}

	sendResponseTimeout := time.Duration(defaultSendResponseTimeoutMs) * time.Millisecond

	// send response to node async
	h.wg.Go(func() {
		// not cancelled when parent is cancelled to ensure the goroutine can finish
		baseCtx := context.WithoutCancel(ctx)
		httpCtx, httpCancel := context.WithTimeout(baseCtx, timeout)
		defer httpCancel()
		l := logger.With(h.lggr, "requestID", requestID, "method", req.Method, "timeout", req.TimeoutMs)
		var outboundResp gateway_common.OutboundHTTPResponse
		callback := h.createHTTPRequestCallback(httpCtx, requestID, httpReq, req)
		if req.CacheSettings.MaxAgeMs > 0 {
			h.metrics.IncrementCacheReadCount(ctx, h.lggr)
			outboundResp = h.responseCache.Fetch(httpCtx, req, callback, req.CacheSettings.Store)
		} else {
			outboundResp = callback()
			if req.CacheSettings.Store {
				h.responseCache.Set(req, outboundResp)
			}
		}
