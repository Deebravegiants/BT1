### Title
CORS wildcard-origin check in Gateway HTTP server uses unanchored suffix match, allowing spoofed subdomains to bypass allowlist - (File: core/services/gateway/network/httpserver.go)

### Summary
`httpServer.isAllowedOrigin` implements wildcard-origin matching for the internet-facing Gateway HTTP server's CORS allowlist. For entries like `*.example.com`, it strips the `*.` and compares the request's `Origin` host using `strings.HasSuffix`, without requiring a `.` boundary before the matched suffix. Any origin host that merely ends with the configured suffix — including one with no dot separator such as `evilexample.com` — passes the check.

### Finding Description
`isAllowedOrigin` parses the incoming `Origin` header and each configured allowed origin into scheme/host/port, then for wildcard entries does: [1](#0-0) 
`allowedHost[2:]` strips `*.` from e.g. `*.example.com`, leaving `example.com`. `strings.HasSuffix(originHost, allowedHost)` then returns `true` for any `originHost` ending in that literal string — this includes `evilexample.com`, `notexample.com`, or any concatenation that happens to end with `example.com`, not just genuine subdomains like `sub.example.com`. This mirrors the DNSSEC report's root cause: comparing/covering names by raw substring/suffix containment instead of verifying a proper label (here, host-segment) boundary.

The scheme and port are correctly compared for exact equality earlier in the function, but the host wildcard branch omits an equivalent boundary check (e.g., requiring `originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost)`).

### Impact Explanation
This function directly governs `Access-Control-Allow-Origin` responses in `handleRequest`: [2](#0-1) 
Because the Gateway HTTP server is an internet-facing endpoint reachable by unprivileged/unauthenticated clients (browsers), an attacker who registers or controls a domain ending in the configured wildcard suffix (e.g. `evilremix.ethereum.org`-style host without the required dot, or more realistically a domain whose registrable name happens to end in the operator's suffix) can have the server echo back `Access-Control-Allow-Origin: <attacker origin>` with `Access-Control-Allow-Credentials`-style trust implied by the allowlist design. This enables browser-based cross-origin requests from a domain the operator never intended to trust, potentially allowing response/data exposure or forged requests against the Gateway from a page hosted on the attacker's look-alike domain.

### Likelihood Explanation
Exploitability depends on the operator actually configuring a wildcard entry (e.g., `*.example.com`) in `CORSAllowedOrigins`, and on an attacker being able to register or serve content from a domain string that ends with the same suffix without a preceding dot (e.g. `notexample.com`, `evilexample.com`). Since domain registration is unprivileged and cheap, and wildcard CORS entries are a documented/expected configuration pattern for this server, this is realistically reachable — unlike the original DNSSEC finding, which required exploiting DNS label-length constraints (noted by the ENS team as impractical), here any attacker who can register a similarly-suffixed domain and serve a page can trigger the bypass.

### Recommendation
Anchor the suffix match to the host-label boundary: after stripping `*.`, require either an exact match or that the origin host ends with `"." + allowedHost`, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
        return true
    }
}
```

### Proof of Concept
1. Configure the Gateway HTTP server with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.example.com"]`.
2. Attacker serves a page from `https://evilexample.com` (no subdomain of `example.com`) and sends a cross-origin `fetch`/XHR request to the Gateway with `Origin: https://evilexample.com`.
3. In `isAllowedOrigin`: `originHost = "evilexample.com"`, `allowedHost` after stripping `*.` = `"example.com"`. `strings.HasSuffix("evilexample.com", "example.com")` evaluates to `true`, so the function returns `true`.
4. `handleRequest` sets `Access-Control-Allow-Origin: https://evilexample.com` and permits the request, even though `evilexample.com` is not a subdomain of `example.com`. [3](#0-2)

func (s *httpServer) isAllowedOrigin(origin string) bool {
	originScheme, originHost, originPort, err := s.splitURL(origin)
	if err != nil {
		s.lggr.Debug("error parsing origin URL", err)
		return false
	}
	for _, allowed := range s.config.CORSAllowedOrigins {
		// probably better to do this once when server starts and store it in a map
		// this is an easier solution so we don't have to apply more changes to the code
		// just need to be careful when specifying allowed origins in the config file
		allowedScheme, allowedHost, allowedPort, err := s.splitURL(allowed)
		if err != nil {
			s.lggr.Debug("error parsing allowed origin URL", err)
			continue
		}
		// skip if the scheme doesn't match at all
		if originScheme != allowedScheme {
			continue
		}
		// skip if the port doesn't match at all
		if originPort != allowedPort {
			continue
		}
		// check for exact host match (e.g., remix.com)
		if originHost == allowedHost {
			return true
		}
		// check for wildcard host match (e.g., *.remix.com)
		if strings.HasPrefix(allowedHost, "*.") {
			allowedHost = allowedHost[2:]
			if strings.HasSuffix(originHost, allowedHost) {
				return true
			}
		}
	}
	return false
}
