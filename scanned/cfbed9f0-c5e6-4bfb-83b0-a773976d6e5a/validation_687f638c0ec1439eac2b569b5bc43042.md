### Title
Unbounded nested loop in web-API trigger processing allows unauthenticated DoS via attacker-controlled `topics` array - (File: core/capabilities/webapi/trigger/trigger.go)

### Summary
`triggerConnectorHandler.processTrigger` iterates over every registered workflow trigger and, for each trigger, iterates over the full `payload.Topics` slice supplied in the incoming Gateway message body. The `Topics` field is fully attacker-controlled (arbitrary JSON array of strings) and has no upper bound, mirroring the `FCNProduct.processDepositQueue`/`processWithdrawalQueue` pattern where a loop's iteration count is driven entirely by attacker-supplied input with no cap, allowing resource exhaustion.

### Finding Description
`HandleGatewayMessage` accepts any JSON-RPC request received by the Gateway connector's `readLoop` and unmarshals the body into a `webapicap.TriggerRequestPayload` [1](#0-0) . It performs no signature/sender-authorization gate before calling `processTrigger` — the sender allowlist check happens *inside* the nested loop, not before it [2](#0-1) .

`processTrigger` builds `triggers := slices.Collect(maps.Values(h.registeredWorkflows))` and then runs a nested loop `for _, trigger := range triggers { for _, topic := range topics { ... } }` [3](#0-2) . The `topics` variable is `payload.Topics`, taken directly and unbounded from the JSON body [4](#0-3) . Neither the JSON Schema definition of `TriggerRequestPayload` nor the generated Go struct impose a maximum array length on `topics` [5](#0-4) [6](#0-5) .

The Gateway connector's `readLoop` processes each incoming message from a gateway connection synchronously, in-order, on a single goroutine, calling `handler.HandleGatewayMessage(ctx, ...)` directly without dispatching to a separate worker [7](#0-6) . This means the total work of `processTrigger` (registered-workflows × topics) directly blocks the processing of all subsequent messages from that gateway connection while it runs.

This is directly analogous to the `FCNProduct` bug class: an unbounded loop whose iteration count is controlled by an unprivileged party (`processDepositQueue`/`processWithdrawalQueue`, driven by queue length), except here the driving factor is the size of an attacker-supplied JSON array rather than an on-chain queue.

### Impact Explanation
A single unauthenticated (or minimally authenticated — the trigger source only needs to be a valid Gateway client capable of sending JSON-RPC messages, not an `allowedSender` of any trigger) actor can submit a `web_api_trigger` message with an arbitrarily large `Topics` array (e.g. hundreds of thousands of unique strings). Because the sender/allowlist check occurs only after a topic match inside the loop, and the loop cost scales with `len(registeredWorkflows) * len(topics)`, this can consume significant CPU on the node's Gateway connector read loop, stalling processing of legitimate trigger/gateway traffic for that connection and delaying workflow triggers node-wide for that DON. In a sufficiently large registered-workflow set, this becomes a meaningful denial-of-service vector against the CRE web-API trigger delivery path.

### Likelihood Explanation
Likelihood is moderate-to-high in environments where the web-API trigger capability is enabled and reachable by external Gateway clients, since no authentication or size validation gates the `Topics` field before the loop executes, and the attack requires only a single well-formed (but oversized) JSON-RPC message with a valid signature format expected by `hc.ValidatedMessageFromReq` — no special privilege over any specific workflow is required to trigger the cost, only to reach the Gateway's webapi trigger handler at all.

### Recommendation
Enforce a maximum length on `TriggerRequestPayload.Topics` (and reject the request early if exceeded, before entering the nested loop), similar to the `MaxBatchSize` checks used elsewhere in the vault capability's request validators (e.g. `ValidateGetSecretsRequest` in `core/capabilities/vault/validator.go`). Additionally, consider restructuring `processTrigger` to build a set-based lookup keyed by topic so the cost is bounded by O(topics + registeredWorkflows) rather than O(topics × registeredWorkflows), and move the sender-authorization check ahead of the expensive per-topic work where feasible.

### Proof of Concept
1. Register at least one workflow trigger via `RegisterTrigger` with any `allowedTopics`/`allowedSenders` config (per `core/capabilities/webapi/trigger/trigger.go`, lines 212-269).
2. Craft a Gateway JSON-RPC request with method `web_api_trigger` whose body is a `TriggerRequestPayload` containing a `topics` array with a very large number of entries (e.g. 500,000 unique strings), signed as required by `hc.ValidatedMessageFromReq`.
3. Send this message through the Gateway connector; `readLoop` will invoke `HandleGatewayMessage` → `processTrigger`, which iterates `len(registeredWorkflows) * len(topics)` times synchronously on the connector's single read goroutine, as shown in `core/capabilities/webapi/trigger/trigger.go` lines 98-118, blocking subsequent message processing on that connection for the duration.

func (h *triggerConnectorHandler) HandleGatewayMessage(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) error {
	msg, err := hc.ValidatedMessageFromReq(req)
	if err != nil {
		h.lggr.Errorw("error validating message from request", "err", err, "request", req)
		return nil
	}
	body := &msg.Body
	sender := ethCommon.HexToAddress(body.Sender)
	var payload webapicap.TriggerRequestPayload
	err = json.Unmarshal(body.Payload, &payload)
	if err != nil {
		h.lggr.Errorw("error decoding payload", "err", err)
		err = h.sendResponse(ctx, gatewayID, body, ghcapabilities.TriggerResponsePayload{Status: "ERROR", ErrorMessage: fmt.Errorf("error %s decoding payload", err.Error()).Error()})
		if err != nil {
			h.lggr.Errorw("error sending response", "err", err)
		}
		return nil
	}

func (c *gatewayConnector) readLoop(gatewayState *gatewayState) {
	defer c.closeWait.Done()
	ctx, cancel := c.shutdownCh.NewCtx()
	defer cancel()

	for {
		select {
		case <-c.shutdownCh:
			return
		case item := <-gatewayState.conn.ReadChannel():
			var req jsonrpc.Request[json.RawMessage]
			err := json.Unmarshal(item.Data, &req)
			if err != nil {
				c.lggr.Errorw("parse error when reading from Gateway", "id", gatewayState.config.ID, "err", err)
				break
			}
			c.handlersMu.RLock()
			handler, exists := c.handlers[req.Method]
			c.handlersMu.RUnlock()
			if !exists {
				c.lggr.Errorw("no handler for method", "id", gatewayState.config.ID, "method", req.Method)
				break
			}
			// do not break on error. HandleGatewayMessage handles errors
			// by sending a response back to the Gateway.
			err = handler.HandleGatewayMessage(ctx, gatewayState.config.ID, &req)
			if err != nil {
				c.lggr.Warnw("failed to handle message from Gateway", "id", gatewayState.config.ID, "method", req.Method, "err", err)
			}
		}
	}
