## Title
Rate limiting bypass via unvalidated `body.Sender` field instead of cryptographically verified sender in `webapiTrigger` allowlist check - (File: core/capabilities/webapi/trigger/trigger.go)

## Summary
In `triggerConnectorHandler.processTrigger`, the authorization check (`allowedSenders`) uses the cryptographically-verified `sender` address derived from message signature validation, but the subsequent rate-limit check uses the raw, attacker-controlled `body.Sender` string field from the message payload. This is directly analogous to the Sherlock M-2 finding: two checks that should operate on the same identity value instead use two different variables, one authoritative and one not, letting an unprivileged caller bypass the intended per-sender protection.

## Finding Description
`processTrigger` receives both a verified `sender ethCommon.Address` (presumably derived from `ValidatedMessageFromReq`/signature recovery) and the raw `body *api.MessageBody`, which contains a `Sender` string field populated directly from the JSON payload sent by the caller: [1](#0-0) 

The allowlist check correctly uses the verified `sender`: [2](#0-1) 

But the very next check — the per-sender rate limiter, which is meant to throttle the same authorized/verified sender — uses `body.Sender` instead of `sender.String()`: [3](#0-2) 

Because `body.Sender` is a plain string field carried in the message body (as opposed to `sender`, which is checked against `allowedSenders`), an attacker who is a legitimately allowlisted sender (passes the `allowedSenders` check with their real, signature-verified address) can freely vary the `body.Sender` value in each request payload. Since the rate limiter keys its per-sender bucket off `body.Sender` (an unvalidated, attacker-supplied string) rather than the verified signer address, the caller can trivially defeat the per-sender rate limit by rotating the `Sender` field value on every request, while the signature-based identity (and thus the allowlist decision) stays constant.

This mirrors the root cause of the Sherlock report: the intended protection mechanism (`blockClaim`/rate limiter) is checked against the wrong identity value (`address(this)`/`body.Sender`) instead of the value that was actually authenticated (`msg.sender`/verified `sender`).

## Impact Explanation
An allowlisted-but-malicious workflow trigger sender can bypass the per-sender rate limiter entirely by supplying an arbitrary/rotating `Sender` value in the trigger payload for each request, defeating the intended DoS/anti-abuse protection (`PerSenderRPS`/`PerSenderBurst`) on the `web_api_trigger` gateway path. This can lead to excessive trigger execution volume, execution ID collisions/log confusion (since `TriggerEventID := body.Sender + payload.TriggerEventId` also derives from the same unvalidated field), and resource exhaustion of the workflow engine, while only the (weaker) global rate limit still applies.

## Likelihood Explanation
Medium-to-low confidence: this requires the caller to already be an allowlisted sender able to pass the signature-based `allowedSenders` check, so it is not an unauthenticated bypass, but rather a rate-limit-evasion bug within an already-permitted (unprivileged relative to the node) client. I was unable to fully confirm within the available tool calls whether `sender` and `body.Sender` are enforced to be identical elsewhere (e.g., in `ValidatedMessageFromReq`/message validation prior to `processTrigger` being called), which would need to be checked to determine whether this is fully exploitable or only a latent inconsistency. This uncertainty should be verified in a Devin session with full file access.

## Recommendation
Use the verified `sender` (the cryptographically authenticated address) consistently for both the allowlist and rate-limiter checks, e.g.:
```go
if !trigger.rateLimiter.Allow(sender.String()) {
```
instead of `trigger.rateLimiter.Allow(body.Sender)`. Additionally, consider deriving `TriggerEventID` from the verified `sender` rather than from the unvalidated `body.Sender` field to avoid any cross-user event ID confusion.

## Proof of Concept
1. An allowlisted signer submits a `web_api_trigger` gateway message that is correctly signed (so `sender` == an allowlisted address and passes `trigger.allowedSenders[sender.String()]`).
2. The message payload's `body.Sender` field (part of `api.MessageBody`, populated by the client) is set to a distinct/random value on each request.
3. Because `trigger.rateLimiter.Allow(body.Sender)` keys the per-sender token bucket off this attacker-controlled string rather than the verified `sender.String()`, each request appears to originate from a "new" sender for rate-limiting purposes and is granted a fresh bucket, allowing unlimited request throughput despite `PerSenderRPS`/`PerSenderBurst` configuration.
