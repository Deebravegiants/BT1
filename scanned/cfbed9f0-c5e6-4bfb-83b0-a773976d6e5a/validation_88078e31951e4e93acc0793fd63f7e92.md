### Title
CORS wildcard-origin matching in the Gateway HTTP server accepts non-subdomain hosts sharing a suffix, allowing Origin allowlist bypass - (File: `core/services/gateway/network/httpserver.go`)

### Summary
The reported `python-cryptography` bug is a class of "over-broad wildcard matching that lets an attacker escape an intended name constraint." The Chainlink Gateway's CORS origin allowlist implements the exact same bug class: when an operator configures a wildcard entry like `https://*.example.com` in `CORSAllowedOrigins`, the matching code strips the `*.` prefix and then does a raw `strings.HasSuffix` comparison against the caller-supplied `Origin` header, with no check that the match boundary is a domain label (i.e., preceded by a `.`). This lets an unprivileged, internet-facing client craft an `Origin` header such as `https://evilexample.com` that is treated as if it belonged to `*.example.com`, bypassing the intended origin allowlist.

### Finding Description
The vulnerable logic is `isAllowedOrigin` in `core/services/gateway/network/httpserver.go`: [1](#0-0) 

```go
func (s *httpServer) isAllowedOrigin(origin string) bool {
	...
	for _, allowed := range s.config.CORSAllowedOrigins {
		allowedScheme, allowedHost, allowedPort, err := s.splitURL(allowed)
		...
		if originScheme != allowedScheme { continue }
		if originPort != allowedPort { continue }
		if originHost == allowedHost { return true }
		// check for wildcard host match (e.g., *.remix.com)
		if strings.HasPrefix(allowedHost, "*.") {
			allowedHost = allowedHost[2:]
			if strings.HasSuffix(originHost, allowedHost) {
				return true
			}
		}
	}
	return false
}
```

Once `*.` is stripped, `allowedHost` becomes a bare suffix string (e.g. `example.com`), and the check becomes `strings.HasSuffix(originHost, "example.com")`. This is true for `notexample.com`, `myevilexample.com`, or `xexample.com` — none of which are subdomains of `example.com`. A proper wildcard-subdomain check must additionally ensure `originHost` ends with `"."+allowedHost` (i.e. there's a `.` label boundary), which is exactly what's missing here — mirroring the pyca bug where a wildcard SAN (`*.example.com`) was accepted for a hostname outside its intended constrained scope (`foo.example.com`) because the matching logic omitted the correct DNS-label boundary semantics.

This function gates `Access-Control-Allow-Origin`/`Access-Control-Allow-Methods`/`Access-Control-Allow-Headers` response headers in the internet-facing Gateway HTTP handler: [2](#0-1) [3](#0-2) 

The `origin` value comes directly and unvalidated from the client-controlled `Origin` request header.

### Impact Explanation
An operator who intends to scope CORS access to `*.example.com` (e.g., to allow only their own subdomains to call the Gateway API from a browser) will unintentionally also allow any domain that merely ends with the string `example.com` as a raw suffix, including attacker-registered domains like `evilexample.com`. A malicious website hosted on such a domain can then issue credentialed cross-origin requests against the Gateway's HTTP endpoint, with the browser accepting the reflected `Access-Control-Allow-Origin` value as authorization — enabling cross-user response confusion / allowlist bypass for whatever the browser-based caller is entitled to (reading data, submitting requests through the origin-restricted API) that should have been restricted to the operator's own legitimate subdomains.

### Likelihood Explanation
Exploitability only requires: (1) `CORSEnabled: true` and a wildcard entry configured in `CORSAllowedOrigins` (a documented, supported configuration pattern per `sample_config.toml`), and (2) an attacker registering or controlling any domain that shares the same trailing character sequence as the allowed suffix. No privileged access or node compromise is needed — this is reachable by any unprivileged web client sending a crafted `Origin` header, matching the "unprivileged-actor" scope of this analysis.

### Recommendation
Fix the wildcard match in `isAllowedOrigin` to require a proper label boundary, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    suffix := allowedHost[1:] // ".example.com" (keep the leading dot)
    if originHost == suffix[1:] || strings.HasSuffix(originHost, suffix) {
        return true
    }
}
```
This ensures only `example.com` itself or `*.example.com` (an actual subdomain, delimited by a dot) matches, not any host that happens to share the trailing bytes.

### Proof of Concept
1. Configure the Gateway with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.example.com"]`.
2. From an attacker-controlled site at `https://evilexample.com`, send a `POST` request to the Gateway's configured `Path` with header `Origin: https://evilexample.com`.
3. `isAllowedOrigin` strips `*.` to get `allowedHost = "example.com"`, then `strings.HasSuffix("evilexample.com", "example.com")` returns `true`.
4. The server responds with `Access-Control-Allow-Origin: https://evilexample.com`, and the browser treats the cross-origin request as authorized, despite `evilexample.com` not being a subdomain of `example.com`.
