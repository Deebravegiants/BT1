### Title
Cache key omits WorkflowID, causing cross-workflow HTTP response confusion in the gateway's outbound response cache - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
The gateway's HTTP Action response cache is documented to provide "Workflow Isolation" ("Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" per `core/services/gateway/handlers/capabilities/v2/README.md:72`), but the cache key is derived solely from `req.Hash()`, and the request's own test suite proves `Hash()` deliberately ignores `WorkflowID` while only `WorkflowOwner` affects the hash.

### Finding Description
The `responseCache` in `core/services/gateway/handlers/capabilities/v2/response_cache.go` stores and retrieves cached HTTP responses keyed exclusively by `req.Hash()`: [1](#0-0) [2](#0-1) 

The struct's own doc comment states the hash is built from "method, URL, headers, body, workflowOwner" — `WorkflowID` is not part of the key: [3](#0-2) 

This is confirmed directly by the test suite for `Hash()`, which explicitly asserts that varying `WorkflowID` alone produces the *same* hash, while `WorkflowOwner` is what differentiates entries: [4](#0-3) [5](#0-4) 

However, the module's design documentation explicitly promises per-workflow isolation and states the cache key is "Generated from workflow ID and request hash": [6](#0-5) 

Because the actual implementation contradicts the documented design, any two workflows run by the same owner (a very common scenario — e.g., a user running multiple workflow versions, or several workflows that call the same third‑party API with identical method/URL/headers/body) will collide on the same cache entry in `rc.cache`. A response fetched for workflow A's outbound HTTP Action request can be transparently served to workflow B's identical-looking request via `Fetch()`, and `singleflight.Group.Do` further coalesces concurrent in-flight requests from different workflows under the same cache key: [7](#0-6) 

This is reachable from a workflow-node-triggered HTTP Action request path handled in `makeOutgoingRequest`, which passes the parsed `OutboundHTTPRequest` (including `WorkflowOwner`/`WorkflowID` fields) directly into the shared `responseCache`: [8](#0-7) 

### Impact Explanation
This is a cross-workflow response confusion bug in the gateway, the internet-facing component that brokers HTTP Action results between external endpoints and DON workflow nodes. Practical impact:
- A workflow can receive an HTTP response body that was actually fetched on behalf of a *different* workflow (same owner, same request shape), even if the two workflows expect different results or have different trust/authorization contexts for that response.
- Response bodies may embed request-context-specific data (tokens, correlation IDs, personalized payloads) that leaks across workflow boundaries, undermining the "Workflow Isolation" guarantee that operators and downstream workflow logic rely on.
- Because the response is served without a fresh HTTP call, this could also be leveraged to keep serving a stale/attacker-influenced response to a victim workflow if the underlying endpoint's response for that colliding key was set up favorably by another workflow under the same owner.

The severity is bounded by the fact that isolation is only broken within the same `WorkflowOwner`, and only when requests coincidentally have identical method/URL/headers/body — but this is a realistic occurrence (identical shared API integrations across a user's several workflows).

### Likelihood Explanation
High likelihood of occurrence in normal operation (no attacker action needed at all — accidental collision between an owner's own workflows), and a motivated owner could deliberately craft two workflows with identical outbound request shapes to intentionally cause response reuse or to probe/exploit cache timing (singleflight coalescing) for cross-workflow effects. No authentication bypass is needed; this triggers purely through normal, unprivileged workflow-node-originated HTTP Action requests reaching the gateway's shared cache.

### Recommendation
Include `WorkflowID` (in addition to `WorkflowOwner`) in the value hashed by `OutboundHTTPRequest.Hash()` so `responseCache` keys are truly scoped per-workflow, matching the documented behavior. Add a regression test asserting that varying `WorkflowID` alone changes `Hash()`'s output (inverse of the current test at `response_cache_test.go:139-149`), and update/verify all cache read/write paths (`Fetch`, `Set`, `isExpiredOrNotCached`) continue to key off the corrected hash.

### Proof of Concept
1. Owner `X` runs Workflow `A` and Workflow `B`, both of which issue an HTTP Action request with identical `Method`, `URL`, `MultiHeaders`, and `Body` (e.g., both call `GET https://api.example.com/data`), with `CacheSettings.Store = true` and `CacheSettings.MaxAgeMs > 0`.
2. Workflow `A`'s request reaches `gatewayHandler.makeOutgoingRequest` → `responseCache.Fetch`, which executes the real HTTP call and stores the 200 response under `cacheKey := req.Hash()`.
3. Workflow `B` issues the same-shaped request. Because `Hash()` does not incorporate `WorkflowID` (only `WorkflowOwner`, per `response_cache_test.go:139-149`), `cacheKey` is identical to Workflow `A`'s, so `Fetch` returns Workflow `A`'s previously cached response to Workflow `B` without making a new HTTP call — demonstrated directly by the existing test `response_cache_test.go` showing identical hashes for differing `WorkflowID` values.

// IMPORTANT: this method does not lock the cache map. MUST be called with cacheMu write-locked.
func (rc *responseCache) isExpiredOrNotCached(req gateway.OutboundHTTPRequest) bool {
	cachedResp, exists := rc.cache[req.Hash()]
	if !exists || time.Now().After(cachedResp.storedAt.Add(rc.ttl)) {

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

### 3.2 Caching Behavior

- **Cacheable Responses**: 2xx (success) and 4xx (client error) status codes.
- **Cache TTL**: Configurable, default 10 minutes
- **Cache Key**: Generated from workflow ID and request hash
- **Cache Invalidation**: Time-based expiration with periodic cleanup
- **Cache Strategy**: All cacheable responses are cached; Non-zero `CacheSettings.MaxAgeMs` determines whether to return a cached value or make a fresh request

func (h *gatewayHandler) makeOutgoingRequest(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	requestID := resp.ID
	h.lggr.Debugw("handling outgoing message", "requestID", requestID, "nodeAddr", nodeAddr)
	var req gateway_common.OutboundHTTPRequest
	err := json.Unmarshal(*resp.Result, &req)
	if err != nil {
		return fmt.Errorf("failed to unmarshal HTTP request from node %s: %w", nodeAddr, err)
	}
	timeout := time.Duration(req.TimeoutMs) * time.Millisecond
	httpReq := network.HTTPRequest{
		Method:           req.Method,
		URL:              req.URL,
		Headers:          req.Headers, //nolint:staticcheck // forward deprecated Headers for backward compatibility; request uses MultiHeaders when set
		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}

	sendResponseTimeout := time.Duration(defaultSendResponseTimeoutMs) * time.Millisecond

	// send response to node async
	h.wg.Go(func() {
		// not cancelled when parent is cancelled to ensure the goroutine can finish
		baseCtx := context.WithoutCancel(ctx)
		httpCtx, httpCancel := context.WithTimeout(baseCtx, timeout)
		defer httpCancel()
		l := logger.With(h.lggr, "requestID", requestID, "method", req.Method, "timeout", req.TimeoutMs)
		var outboundResp gateway_common.OutboundHTTPResponse
		callback := h.createHTTPRequestCallback(httpCtx, requestID, httpReq, req)
		if req.CacheSettings.MaxAgeMs > 0 {
			h.metrics.IncrementCacheReadCount(ctx, h.lggr)
			outboundResp = h.responseCache.Fetch(httpCtx, req, callback, req.CacheSettings.Store)
		} else {
			outboundResp = callback()
			if req.CacheSettings.Store {
				h.responseCache.Set(req, outboundResp)
			}
