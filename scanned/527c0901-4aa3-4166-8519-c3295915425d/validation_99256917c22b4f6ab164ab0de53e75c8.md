## Analysis

The reported bug class (unchecked arithmetic that can under/overflow) has a concrete analog in the gateway's staleness check for trigger messages.

### Title
Unsigned integer underflow in message-staleness check allows anti-replay bypass via negative timestamp - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
`handler.HandleLegacyUserMessage` validates the freshness of an incoming `TriggerRequestPayload` by comparing an unsigned-integer-cast timestamp against the current time, but never rejects negative `Timestamp` values. Casting a negative `int64` to `uint` wraps around to a value near `math.MaxUint64`, which always satisfies the "not stale" branch of the comparison, completely defeating the staleness/anti-replay check for any attacker-supplied negative timestamp.

### Finding Description
`HandleLegacyUserMessage` only special-cases a `Timestamp == 0` payload as invalid: [1](#0-0) 

It then performs the staleness comparison using unchecked unsigned casts: [2](#0-1) 

`payload.Timestamp` is declared as a signed `int64` (`webapicap.TriggerRequestPayload.Timestamp`), and it is fully attacker-controlled: it originates from the JSON payload of an `api.Message` sent to the gateway's user-facing endpoint. Critically, `Message.Validate()` (which runs before this handler) only verifies the signature is *internally consistent* — it recovers whatever address signed the message and stores it as `Sender`; it does **not** check that the signer is a member of an allowlist of legitimate DON nodes: [3](#0-2) 

This means any unprivileged client can generate a throwaway ECDSA key, sign an arbitrary `MessageBody` (including a negative `Timestamp` in the payload), and have it pass `Validate()`. Because `uint(payload.Timestamp)` wraps to a huge value when `Timestamp` is negative, the condition `uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp)` is always false, so the "stale message" rejection at line 373 can never trigger, regardless of how the config's `MaxAllowedMessageAgeSec` is set.

### Impact Explanation
The staleness check is the sole defense against replaying previously captured, validly signed trigger messages. By supplying (or forging) a message with a negative timestamp, an attacker defeats this anti-replay control entirely, allowing indefinitely delayed or repeated processing of a captured request as if newly issued. Combined with the fact that message validation performs no sender allowlist check at this stage, this weakens a layered defense that is otherwise relied on to bound the freshness/authenticity window of trigger requests dispatched to DON nodes — enabling unauthorized re-triggering of workflow execution requests outside the intended freshness window.

### Likelihood Explanation
High. No special access is required: the request is sent by an ordinary caller of the gateway's user-facing HTTP/message endpoint, `Message.Validate()` does not reject arbitrary signers, and only a single crafted negative-integer field is needed to bypass the check.

### Recommendation
Reject any `payload.Timestamp <= 0` (not just `== 0`), or better, perform the freshness comparison using signed arithmetic on `time.Time`/`time.Duration` (e.g., `time.Now().Sub(time.Unix(payload.Timestamp, 0)) > maxAge`) instead of casting to `uint` and subtracting, so that negative or out-of-range values cannot wrap around.

### Proof of Concept
1. Generate an arbitrary ECDSA keypair (no registration/allowlisting required).
2. Construct a `webapicap.TriggerRequestPayload` with `Timestamp: -1` (or any negative int64).
3. Sign the resulting `api.Message` with the throwaway key via `Message.Sign()`.
4. Submit the message to the gateway; `Message.Validate()` succeeds (it only checks the signature is self-consistent, not that the signer is authorized).
5. In `HandleLegacyUserMessage`, `uint(-1)` wraps to `18446744073709551615`, which is always greater than `uint(time.Now().Unix()) - MaxAllowedMessageAgeSec`, so the "stale message" branch never executes and the (arbitrarily old or replayed) message is forwarded to DON nodes. [4](#0-3)

	}
	if strings.HasSuffix(m.Body.MessageID, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonID) == 0 || len(m.Body.DonID) > MessageDonIDMaxLen {
		return errors.New("invalid DON ID length")
	}
