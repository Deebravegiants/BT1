## Analysis

The Sherlock report describes a **data mismatch between the value used for an authorization/emission decision and the value actually emitted/used downstream**: `footiumClub.ownerOf(tokenId)` is used to mint players, but the *stale* `to` parameter is used in the emitted event, which can diverge if the token was transferred in between.

The closest reachable analog in this codebase is in the gateway's web-API trigger handler, where the sender address is validated/normalized once but a *different, unnormalized* representation of the same field is used for a security-relevant per-sender rate-limit key — enabling a quota bypass by an unprivileged, unauthenticated web-API client. ### Title
Per-sender rate limit keyed on unnormalized address string allows quota bypass - (File: core/capabilities/webapi/trigger/trigger.go)

### Summary
`triggerConnectorHandler.processTrigger` validates the sender's allowlist membership using a normalized `common.Address` (`sender.String()`), but enforces the per-sender rate limit using the raw, attacker-controlled `body.Sender` string. Because Ethereum hex addresses are case-insensitive, an unprivileged web-API client can submit the same underlying address in many different letter-case permutations, each treated as a distinct rate-limiter key, defeating the `PerSenderRPS`/`PerSenderBurst` quota entirely.

### Finding Description
`HandleGatewayMessage` normalizes the incoming `body.Sender` into a canonical address once: `sender := ethCommon.HexToAddress(body.Sender)` [2](#0-1) . This normalized `sender` is correctly used for the allowlist check `trigger.allowedSenders[sender.String()]` [5](#0-4) . Immediately after, however, the rate limiter check uses the original, unnormalized field: `trigger.rateLimiter.Allow(body.Sender)` [6](#0-5) .

Since `body.Sender` is a plain string taken directly from the inbound message body and hex addresses are case-insensitive, an attacker who controls the exact casing of the address string in the JSON-RPC/gateway message can present the same allowlisted address as many distinct strings (e.g. `0xABCDEF...`, `0xabcdef...`, `0xAbCdEf...`), all of which pass the allowlist check (because that check normalizes through `common.Address`) but each of which is treated as a brand-new, distinct bucket by the rate limiter (because it does no normalization). This defeats the `PerSenderRPS`/`PerSenderBurst` limits configured at `RegisterTrigger` [7](#0-6) .

This is structurally analogous to the original bug class: a security-relevant decision is made using a *different representation of the identity* than the one that was actually authenticated/normalized, letting the same real-world actor be treated as many different logical actors.

### Impact Explanation
An unprivileged, unauthenticated caller of the gateway's web API trigger endpoint can flood a registered workflow trigger far beyond its configured per-sender rate limit just by varying address casing, causing excessive workflow executions, resource exhaustion, and potential downstream cost/DoS impact on the DON, while circumventing an explicit anti-abuse control that operators rely on.

### Likelihood Explanation
Likelihood is high: exploitation requires no special privileges beyond being an already-allowlisted sender (which is the expected caller for this endpoint), and only requires trivial string manipulation of the address casing in the request body — no cryptographic or protocol-level trickery needed.

### Recommendation
Use the normalized `sender.String()` (or `sender` bytes) consistently for both the allowlist check and the rate limiter key, e.g. change `trigger.rateLimiter.Allow(body.Sender)` to `trigger.rateLimiter.Allow(sender.String())`, ensuring both checks operate on the same canonical identity representation.

### Proof of Concept
1. Register a trigger with `AllowedSenders: ["0xAbCdEf0123456789..."]` and `PerSenderRPS`/`PerSenderBurst` configured to a low value.
2. From an allowlisted address, send repeated `web_api_trigger` gateway messages with `body.Sender` values that are case-permutations of the same address (`0xabcdef...`, `0xABCDEF...`, `0xAbCdEf...`, etc.).
3. Observe that `sender.String()` normalizes each to the identical checksummed address, so the allowlist check in `processTrigger` passes every time [3](#0-2) .
4. Observe that `trigger.rateLimiter.Allow(body.Sender)` is called with a distinct string each time [6](#0-5) , so the configured per-sender quota is never actually enforced against the single real sender, allowing unlimited trigger throughput.

	msg, err := hc.ValidatedMessageFromReq(req)
	if err != nil {
		h.lggr.Errorw("error validating message from request", "err", err, "request", req)
		return nil
	}
	body := &msg.Body
	sender := ethCommon.HexToAddress(body.Sender)
