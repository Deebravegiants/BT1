### Title
Authentication response leaks user existence via differing error messages - (File: core/sessions/localauth/orm.go)

### Summary
The local-auth login endpoint (`POST /sessions`) returns different, distinguishable error messages depending on whether the supplied email corresponds to an existing user, allowing an unauthenticated remote caller to enumerate valid Chainlink node user accounts. This is a direct analog to CVE-2016-20012, where an SSH server's differing challenge behavior let a remote attacker confirm whether a username/key combination was valid.

### Finding Description
`SessionsController.Create` calls `AuthenticationProvider().CreateSession(ctx, sr)` and, on any error, forwards that error unmodified to the client via `jsonAPIError`, which serializes `err.Error()` straight into the JSON response body. [2](#0-1) [1](#0-0) 

In `localauth/orm.go`'s `CreateSession`, the very first step is `FindUser`, whose error (the raw DB lookup error, e.g. `sql.ErrNoRows`/"no rows in result set") is returned immediately and verbatim if the email doesn't match any row. Only *after* a user is found does the code produce the generic, deliberately uniform `"Invalid email"` / `"Invalid password"` errors: [3](#0-2) 

The comment right above the email/password check even states the intent to avoid a *different* kind of leak (MFA existence) by doing email/password checks before hitting the WebAuthn table — showing the authors were aware of enumeration-style leaks in this exact function, yet the preceding `FindUser` error path was left unguarded: [4](#0-3) 

The same unmasked-error-on-missing-user pattern exists in the LDAP and OIDC authenticators' local-admin fallback paths as well, though those wrap the `FindUser`/lookup error before the email/password comparison: [5](#0-4) [6](#0-5) 

As a result, an unauthenticated client can send a login request with a candidate email and observe:
- Existing email + wrong password → HTTP 401 body containing `"Invalid password"`.
- Non-existent email → HTTP 401 body containing the raw SQL "no rows" error string.

This distinction is exactly the "known-vs-unknown identity" signal that CVE-2016-20012 flags: an unprivileged, unauthenticated network actor can reliably determine whether a given email/username is a registered Chainlink node account, without needing valid credentials.

### Impact Explanation
This is an information-disclosure / user-enumeration issue reachable by any unauthenticated network client hitting `/sessions`. It doesn't grant authentication bypass or credential compromise directly, but it lets an attacker build a list of valid node operator emails for targeted credential-stuffing, phishing, or brute-force campaigns against the Chainlink node's admin UI/API — consistent with the "Medium" severity of the underlying CVE class (CVSS 5.3, confidentiality-only impact, no authentication required).

### Likelihood Explanation
High likelihood of exploitability: the endpoint is unauthenticated by design (it's the login endpoint), requires no special network position, and the differing error text is returned synchronously in every response — no timing side-channel or race condition needed, just literal response-body comparison.

### Recommendation
In `orm.go`'s `CreateSession` (and the LDAP/OIDC local-fallback equivalents), normalize all failure paths — including the initial `FindUser` lookup failure — to return the same generic error (e.g., `"Invalid email or password"`) with the same HTTP status, before any user-existence-dependent branching, and avoid propagating raw DB errors into `jsonAPIError`.

### Proof of Concept
1. `POST /sessions` with `{"email":"knownadmin@node.com","password":"wrong"}` → response body contains `"Invalid password"`.
2. `POST /sessions` with `{"email":"doesnotexist@node.com","password":"wrong"}` → response body contains a different message derived from the raw `FindUser` DB error (e.g. containing "no rows").
3. Comparing the two distinct response bodies lets the attacker confirm which target emails correspond to real accounts on the node, without any valid credentials.

```go
func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}
```
