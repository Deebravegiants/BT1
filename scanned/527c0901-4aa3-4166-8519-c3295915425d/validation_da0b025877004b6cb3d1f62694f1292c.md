Based on my investigation, I found a concrete unprivileged-actor rate-limiting gap: the `PATCH /v2/resume/:runID` endpoint is registered entirely unauthenticated (no session, no token, no external-initiator check) yet it inherits the **authenticated** rate-limit tier (default 1000 req/min) rather than the much stricter unauthenticated tier (default 5 req/20s), because it is mounted directly on the `api` group in `NewRouter` before any auth middleware is applied.

### Title
Unauthenticated pipeline-run resume endpoint inherits the high "authenticated" rate limit instead of the strict "unauthenticated" limit - (File: core/web/router.go)

### Summary
`v2Routes` registers `PATCH /v2/resume/:runID` on `unauthedv2 := r.Group("/v2")` with no authentication middleware at all [1](#0-0) . The parent `api` group in `NewRouter` only applies the "Authenticated" rate limiter (`rl.Authenticated()` / `rl.AuthenticatedPeriod()`, default 1000 requests/min) to every route mounted under it, including this unauthenticated one [2](#0-1) . By contrast, the `/sessions` login endpoint — the only other unauthenticated write route — is explicitly wrapped in a separate sub-group using the much stricter "Unauthenticated" limiter (default 5 requests/20s) [3](#0-2) . `/v2/resume/:runID` receives no such treatment, so it is rate-limited as if it were an authenticated route even though anyone can call it without credentials.

### Finding Description
`PipelineRunsController.Resume` accepts a `runID` (UUID) and a JSON body, then calls `prc.App.ResumeJobV2`, which triggers `ResumeRun` in the pipeline runner — this performs a database update (`UpdateTaskRunResult`) and, if applicable, spawns a goroutine to restart pipeline execution (`r.Run`) [4](#0-3) [5](#0-4) . This is intentionally unauthenticated because it's the callback target for external resumable tasks (e.g., bridge adapters completing async work), but that design choice means it is the only unauthenticated *mutating* endpoint on the API besides `/sessions`. Unlike `/sessions`, it is not scoped under the stricter unauthenticated rate limiter, so an unprivileged remote attacker can send up to the "authenticated" quota (1000/min by default) of resume requests, each of which does a DB write and can spawn a new goroutine plus a pipeline re-execution, consuming CPU, DB connections, and memory. Because `runID` values are guessable/enumerable at scale (or simply brute forced against valid UUIDs seen elsewhere), this creates a straightforward resource-exhaustion vector consistent with the reported "lack of resources / rate limiting" issue: an attacker without any credential can multiply request volume nearly 200x compared to the deliberately stricter unauthenticated tier used for `/sessions`.

### Impact Explanation
An unauthenticated caller can drive substantially higher request volume against a DB-writing, goroutine-spawning endpoint than the node's own unauthenticated rate-limit policy intends, degrading node responsiveness and consuming pipeline/DB resources — matching the reported impact of API unavailability from resource exhaustion (Impact: 3/5 per the report).

### Likelihood Explanation
No credentials, tokens, or session are required to reach the endpoint; the only barrier is guessing a valid `runID` UUID, and even invalid/nonexistent IDs still consume request-handling and DB-lookup resources before erroring. Rate limiting exists but is misconfigured to the lenient tier, meaning normal production defaults (1000/min) do not meaningfully throttle abuse (Likelihood: 4/5 per the report).

### Recommendation
Move `PATCH /v2/resume/:runID` into its own sub-group (mirroring the `/sessions` pattern) that applies `rl.UnauthenticatedPeriod()` / `rl.Unauthenticated()`, or introduce a dedicated, more conservative rate-limit tier for this callback endpoint. Consider additionally rate-limiting per-`runID`/per-IP and validating that the referenced run/task is in a resumable state before performing any DB write.

### Proof of Concept
1. Start a node with default `WebServer.RateLimit` config (`Authenticated=1000/1m`, `Unauthenticated=5/20s`).
2. Without any auth headers/cookies, send `PATCH /v2/resume/<any-uuid>` with a valid/garbage JSON body repeatedly.
3. Observe that requests are only rejected with HTTP 429 after ~1000 requests/minute (matching the authenticated limiter in `rateLimiter(rl.AuthenticatedPeriod(), rl.Authenticated())` applied to the parent `api` group), rather than after 5 requests/20s as intended for unauthenticated traffic — confirmed by contrast with `TestSessions_RateLimited`, which shows the `/sessions` unauthenticated endpoint being blocked after only 5 attempts [6](#0-5) .

// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
}

func (r *runner) ResumeRun(ctx context.Context, taskID uuid.UUID, value any, err error) error {
	run, start, err := r.orm.UpdateTaskRunResult(ctx, taskID, Result{
		Value: value,
		Error: err,
	})
	if err != nil {
		return fmt.Errorf("failed to update task run result: %w", err)
	}

	// TODO: Should probably replace this with a listener to update events
	// which allows to pass in a transactionalised database to this function
	if start {
		// start the runner again
		go func() {
			ctx, cancel := r.chStop.NewCtx()
			defer cancel()
			if _, err := r.Run(ctx, &run, false, nil); err != nil {
				r.lggr.Errorw("Resume run failure", "err", err)
			}
			r.lggr.Debug("Resume run success")
		}()
	}
	return nil
}
