### Title
Cross-user response hijacking via un-scoped `savedCallbacks` map keyed only by client-supplied `MessageID` - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`handler.HandleLegacyUserMessage` (the entry point for unprivileged clients invoking `web_api_trigger`/webhook-style workflow triggers through the Gateway) stores the caller's response callback in a shared map keyed solely by the client-supplied `msg.Body.MessageID`, with no binding to the caller/session identity. A second, unrelated caller who submits a request carrying the same `MessageID` before the first request's DON response arrives will silently overwrite the first caller's stored callback, causing the first caller's eventual response to be delivered to the second caller instead. This mirrors the root cause of the reported Carousel bug: a shared identity→slot mapping (`ownerToRollOverQueueIndex` there, `savedCallbacks[MessageID]` here) is updated unconditionally on every "enlist"/request call rather than only when a slot doesn't already belong to someone else, allowing one caller's action to silently take over another caller's tracked state/response.

### Finding Description
`HandleLegacyUserMessage` is called for every incoming legacy user message dispatched via the Gateway's `ProcessRequest` path in `core/services/gateway/gateway.go`, which is reachable from any unprivileged client that can reach the Gateway's HTTP endpoint [1](#0-0) .

Inside the handler, the callback for the request is stored keyed only by `msg.Body.MessageID`: [2](#0-1) 

There is no check whether an entry for that key already exists and belongs to a different, still-pending request — the assignment always overwrites whatever was previously stored under that key, exactly analogous to line 268 of `Carousel.sol` unconditionally rewriting `ownerToRollOverQueueIndex[_receiver]` regardless of whether the entry already belonged to someone else.

When a DON node later responds with the matching `MessageID`, the handler looks up and deletes whatever callback currently sits at that key and delivers the response to it: [3](#0-2) 

Because `MessageID` is client/request-controlled (propagated from the inbound JSON-RPC/legacy message) and the map is not scoped by sender or session, two different unprivileged callers who happen to use (or deliberately choose) the same `MessageID` value produce a direct collision: whichever request is stored second in `savedCallbacks` "wins" the slot, and the response for the first request — originally sent to the DON nodes under that ID — gets delivered to the second caller's callback instead of the first caller's.

### Impact Explanation
This is a concrete cross-user response confusion: an unprivileged attacker who can guess or brute-force/collide a `MessageID` in flight can receive another user's workflow-trigger response (which may contain data returned by the invoked capability/workflow), while the legitimate caller either receives no response (timing out) or the attacker's unrelated response. This satisfies the "cross-user response confusion" acceptance criterion — one unprivileged actor's request silently redirects/consumes state (the response channel) that logically belongs to another user, without any privilege escalation needed.

### Likelihood Explanation
Exploitability depends on the attacker being able to submit a request with a colliding `MessageID` while the victim's request is still pending (a window bounded by `CallbackMaxAgeSec`, default 120s per `defaultCallbackMaxAgeSec` [4](#0-3) ). If `MessageID` values are attacker-choosable (e.g., taken directly from the inbound JSON-RPC request `id` field) rather than server-generated with high entropy, collision is trivial to force deliberately; if IDs are server-generated with sufficient entropy, likelihood is lower but the underlying missing ownership check is a latent defect regardless. I was not able to fully trace, within the available context, the exact code path that assigns `msg.Body.MessageID` for legacy inbound requests to confirm whether it is fully attacker-controlled or partially server-derived — this should be verified before drawing final conclusions on exploit likelihood.

### Recommendation
Scope `savedCallbacks` by both `MessageID` and the caller/sender identity (e.g., `(sender, MessageID)` as already done correctly in the sibling `RequestCache` implementation, which keys by `globalID{sender, id}` [5](#0-4) ), and reject/error on collision with an existing pending entry for a different sender rather than silently overwriting it — mirroring the fix recommended for the Carousel bug (only assign a new slot when one doesn't already exist for a different owner).

### Proof of Concept
1. Victim submits a `web_api_trigger` legacy request through the Gateway with `MessageID = "X"`; `HandleLegacyUserMessage` stores victim's callback at `savedCallbacks["X"]` and forwards the request to DON nodes.
2. Before any DON node responds, Attacker submits their own legacy request also carrying `MessageID = "X"` (self-chosen or colliding value); `HandleLegacyUserMessage` overwrites `savedCallbacks["X"]` with Attacker's callback.
3. A DON node eventually responds for message `"X"` (the response that was meant for Victim's forwarded request). `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds Attacker's callback, deletes the entry, and delivers the response to Attacker instead of Victim.
4. Victim's original request now never receives a response (or later receives Attacker's own DON response if Attacker's request also completes), demonstrating cross-user response hijacking caused by the unconditional overwrite of a shared identity-keyed map, structurally identical to the reported `ownerToRollOverQueueIndex` overwrite bug.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
