### Title
CORS wildcard-origin allowlist bypass via improper suffix matching - (File: core/services/gateway/network/httpserver.go)

### Summary
The Chainlink Gateway's CORS origin check (`isAllowedOrigin`) validates wildcard-allowed origins (e.g. `*.example.com`) using a plain `strings.HasSuffix` comparison without requiring a `.` boundary before the matched suffix. This is the same bug class as CVE-2024-2419 (Keycloak): an allowlist check meant to restrict access to a specific host (or its subdomains) can be bypassed by an attacker who registers a similarly-suffixed but unrelated domain, causing the server to treat an untrusted origin as trusted.

### Finding Description
`isAllowedOrigin` parses the request `Origin` header and each configured allowed origin into scheme/host/port via `splitURL`, then for wildcard entries strips the `*.` prefix and does: [1](#0-0) 

There is no check that the character immediately preceding the matched suffix in `originHost` is a `.` (i.e., that `originHost` is actually a subdomain of `allowedHost`, or equal to it). Because of this, for an allowed entry `*.ethereum.org` (allowedHost becomes `ethereum.org`), an attacker-registered domain such as `evil-ethereum.org` or `notethereum.org` will pass `strings.HasSuffix(originHost, "ethereum.org")` even though it shares no subdomain relationship with `ethereum.org`.

This logic is invoked directly from the unauthenticated, internet-facing gateway HTTP handler: [2](#0-1) 

If the check passes, the server reflects the attacker's `Origin` value back in `Access-Control-Allow-Origin` and permits credentialed cross-origin requests to succeed, exactly mirroring the root cause pattern in the Keycloak advisory: a "hostname allowlist" that is bypassed due to insufficient boundary validation of the matching logic.

### Impact Explanation
If a Gateway operator configures a wildcard CORS allow-list (e.g., `*.mycompany.com`) intending to scope trusted origins to their own subdomains, an unrelated attacker-controlled site whose registered domain happens to end with the same suffix (`evilmycompany.com`) can pass the origin check. Combined with the CORS headers set by `handleRequest`, a browser running attacker JavaScript from that spoofed origin can make cross-origin, credentialed calls to the Gateway API and read the responses, enabling request impersonation / token or data exfiltration from other users' sessions that rely on this Gateway endpoint — a cross-user response confusion analogous to the referenced CVE's "theft of access token" impact.

### Likelihood Explanation
Exploitation requires: (1) `CORSEnabled = true` with at least one wildcard entry configured in `CORSAllowedOrigins`, and (2) an attacker able to register/host a domain with the matching suffix and lure/host malicious JS causing a victim client to include the Gateway's cookies/tokens in the request (or that the gateway performs an unauthenticated but sensitive operation). This is a config-dependent condition, but wildcard entries are a documented supported feature, and the bypass requires no privileged access — only a purchasable domain name — making this a reasonably likely misconfiguration abuse scenario for internet-facing gateway deployments using wildcard CORS.

### Recommendation
Fix `isAllowedOrigin`'s wildcard match to enforce a proper subdomain boundary, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    suffix := allowedHost[1:] // ".example.com"
    if originHost == allowedHost[2:] || strings.HasSuffix(originHost, suffix) {
        return true
    }
}
```
i.e., require the suffix to include the leading dot (`.ethereum.org`) so `evil-ethereum.org` no longer matches, while `foo.ethereum.org` still does. Add regression tests covering domains that share a suffix but are not true subdomains (e.g., `evil-ethereum.org`, `notethereum.org`).

### Proof of Concept
1. Configure the Gateway with `CORSEnabled = true` and `CORSAllowedOrigins = []string{"*.ethereum.org"}`.
2. From a browser page hosted on `https://evil-ethereum.org`, send a `fetch()` request to the Gateway endpoint with credentials included.
3. The Gateway's `isAllowedOrigin` computes `allowedHost = "ethereum.org"` and `originHost = "evil-ethereum.org"`; `strings.HasSuffix("evil-ethereum.org", "ethereum.org")` returns `true`.
4. The server responds with `Access-Control-Allow-Origin: https://evil-ethereum.org`, allowing the attacker's page to read the cross-origin response despite not being a genuine subdomain of `ethereum.org`. [3](#0-2)
