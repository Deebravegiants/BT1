### Title
Unsigned Integer Underflow in Stale-Message Timestamp Check Allows Replay of Arbitrarily Old Gateway Trigger Messages - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The internet-facing gateway's legacy user-message handler validates message freshness using raw unsigned subtraction `uint(time.Now().Unix()) - h.config.MaxAllowedMessageAgeSec`. Because `MaxAllowedMessageAgeSec` is attacker-independent but the comparison itself uses unchecked `uint` arithmetic, and because `payload.Timestamp` is fully attacker-controlled, the freshness check can be trivially bypassed or produce wraparound results — directly mirroring the reported bug class of unsafe raw arithmetic used to gate acceptance/rejection of a request.

### Finding Description
In `HandleLegacyUserMessage`: [1](#0-0) 

```go
if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) {
    h.lggr.Errorw("stale message")
    ...
}
```

`payload.Timestamp` originates from `webapicap.TriggerRequestPayload`, which is fully controlled by the unprivileged HTTP client submitting the legacy trigger message (decoded directly from `body.Payload` at [2](#0-1) ). The only validation performed is `payload.Timestamp == 0` at [3](#0-2) ; there is no upper-bound / future-timestamp check.

The freshness check is the mirror image of the reported "unsafe arithmetic" class: instead of a multiplication overflowing to make a purchase amount wrongly "sold out"/"bought out", here the subtraction can wrap or the comparison can be satisfied for values that should have been rejected, wrongly marking a message as "fresh" (or, in edge conditions near process start / clock skew, wrongly "stale"). Specifically:
- `uint(payload.Timestamp)` — since `Timestamp` is a signed field decoded from attacker JSON, a large or negative value cast to `uint` produces an arbitrarily large unsigned number, trivially satisfying `> uint(time.Now().Unix()) - MaxAllowedMessageAgeSec` and passing the "not stale" check regardless of the real age of the message.
- There is no check that `payload.Timestamp` is not in the future, so a caller can set an arbitrarily large future timestamp to always pass this check on any subsequent replay of the same signed payload, as long as the DON-side signature/replay logic (handled elsewhere) does not itself catch it.

This directly parallels the audited bug: a raw, unchecked arithmetic comparison on an attacker-influenced numeric input is used to gate a security-relevant decision (accept vs. reject a request) at the internet-facing gateway boundary, instead of using safe/bounded comparisons.

### Impact Explanation
An unprivileged caller of the gateway's legacy user-message HTTP endpoint can craft a `TriggerRequestPayload` with a manipulated `Timestamp` value that defeats the staleness check, causing the gateway to forward a "stale" (or otherwise invalid-timestamp) trigger message to DON nodes as if it were fresh. Depending on downstream replay protections in `common.ValidatedRequestFromMessage` and DON-side handling, this can enable acceptance of old/replayed workflow trigger requests via the gateway's `handleWebAPITriggerMessage`/`handleWebAPIOutgoingMessage` flow, undermining the intended anti-replay/staleness guarantee that `MaxAllowedMessageAgeSec` is meant to enforce.

### Likelihood Explanation
The `HandleLegacyUserMessage` path is exposed to any unprivileged client able to submit "legacy" gateway messages, and `payload.Timestamp` is fully attacker-supplied with only a `== 0` guard. No signature or cryptographic binding of `Timestamp` to the freshness check is shown in this function, so exploitation only requires crafting the JSON payload — no privileged access needed.

### Recommendation
Replace the raw unsigned subtraction/comparison with signed, bounds-checked time arithmetic, e.g. compute `age := time.Now().Unix() - payload.Timestamp` using `int64` and explicitly reject `age < 0` (future timestamp) and `age > int64(h.config.MaxAllowedMessageAgeSec)` (stale), rather than subtracting into `uint` and comparing unsigned values. Additionally, bind `Timestamp` into any signature/digest that protects the message body so that it cannot be altered independently of the rest of the payload.

### Proof of Concept
1. Submit a legacy gateway message with `Method = MethodWebAPITrigger` and `Payload.Timestamp` set to a very large value (e.g., `math.MaxInt64` or a large future value) or a negative value that, when cast to `uint`, becomes larger than `uint(time.Now().Unix()) - MaxAllowedMessageAgeSec`.
2. Observe that the check at [4](#0-3)  passes regardless of the actual age of the message, since only unsigned arithmetic on attacker-supplied `Timestamp` is used and no future-timestamp bound exists.
3. The message proceeds to `common.ValidatedRequestFromMessage` and is fanned out to all DON members via `don.SendToNode`, bypassing the intended staleness gate.
