### Title
Match-arm ordering in `run_call`'s reentrancy heuristic defeats the stipend-based reentrancy guard for nonzero-value calls, enabling classic `.transfer()`/`.send()`-style reentrancy - (File: substrate/frame/revive/src/vm/evm/instructions/contract.rs)

### Summary
`run_call` classifies the reentrancy level for a `CALL` based on `(value.is_zero(), gas_limit == CALL_STIPEND)`, but because Rust `match` evaluates arms top-down and the first arm is `(false, _)`, any nonzero-value call — including the canonical Solidity `.transfer()`/`.send()` pattern (`value != 0`, `gas_limit == 2300`) — is unconditionally routed to `ReentrancyProtection::AllowReentry` instead of the intended `AllowNext`. This is precisely the opposite of the stated purpose of the heuristic (protecting stipend-limited calls from reentrancy on revive's different gas scale), leaving `.transfer()`/`.send()`-based withdraw patterns fully reentrant.

### Finding Description
In `run_call`: [1](#0-0) 

```rust
let (add_stipend, reentracy) =
    match (value.is_zero(), gas_limit.try_into().is_ok_and(|limit: u64| limit == CALL_STIPEND))
    {
        (false, _) => (true, ReentrancyProtection::AllowReentry),
        // Heuristic: detect when solc passes `gas_limit = 2300` (the call stipend).
        // For zero-value transfer/send, solc injects `gas_limit = 2300` explicitly.
        // We apply `AllowNext` reentrancy protection and set `add_stipend = true` since the
        // raw 2300 gas value is only meaningful at Ethereum's gas scale.
        (_, true) => (true, ReentrancyProtection::AllowNext),
        (_, _) => (false, ReentrancyProtection::AllowReentry),
    };
```

Solidity's `.transfer(amount)`/`.send(amount)` always compile to a low-level `CALL` with `value = amount` (nonzero) and `gas_limit = 2300` (the stipend), specifically because on real Ethereum 2300 gas is insufficient for the callee to make a further state-changing call, which is what makes the checks-effects-interactions-violating `withdraw() { transfer(); balance = 0; }` pattern safe on mainnet. The code comment acknowledges revive's gas scale differs and that this guarantee "does not automatically hold in revive," which is why the `AllowNext` branch exists at all.

However, because the first match arm is `(false, _)`, any call with `value != 0` — regardless of `gas_limit` — matches that arm first and is unconditionally assigned `ReentrancyProtection::AllowReentry`. The second arm `(_, true)`, which grants `AllowNext`, is only reachable when `value.is_zero()` is `true`, i.e., only for zero-value calls with `gas_limit == 2300`. That is not the pattern solc actually emits for `.transfer()`/`.send()`. As a result, the explicit protection the code claims to add is dead for its actual intended use case, and every `.transfer()`/`.send()` call compiled from Solidity is executed with full `AllowReentry` semantics in `Stack::call`: [2](#0-1) 

With `AllowReentry`, `self.top_frame_mut().allows_reentry` is never set to `false`, so `allows_reentry(&dest)` checks impose no restriction and the callee (and its recursive callees) can freely call back into the caller contract before the caller's post-call state update executes — exactly the classic reentrancy pattern.

### Impact Explanation
Any Solidity contract deployed on `pallet-revive` that uses the standard (and historically common) pattern `balances[msg.sender] = 0; ... msg.sender.transfer(amount);` reversed order (`transfer` before zeroing balance) — code that would be non-reentrant on real Ethereum precisely because of the 2300-gas stipend — is fully reentrant here. An attacker-controlled contract can, in its fallback triggered by the `transfer`/`send`, re-enter the vulnerable contract's withdrawal function before the balance is debited, draining/double-spending the victim contract's held funds. This matches the scoped impact: cross-contract reentrancy drain via a value-bearing stipend call.

### Likelihood Explanation
This is trivially and deterministically reachable by any unprivileged EVM contract caller: deploy a victim contract using the common (and, on real Ethereum, considered safe due to gas-stipend semantics) `.transfer()`-based withdrawal pattern, deploy an attacker contract whose `receive`/fallback re-enters `withdraw()`, and invoke `withdraw()` — no special origin, proxy, or governance access needed. It requires no fuzzing to hit; the value/gas combination used by the Solidity compiler for `.transfer()`/`.send()` deterministically triggers the mis-branch every time.

### Recommendation
Change the classification so the stipend/gas check is evaluated independently of the value-zero check, i.e., first check `gas_limit == CALL_STIPEND` and grant `AllowNext` for that case regardless of value, only falling back to `AllowReentry` for other nonzero-value/non-stipend calls:
```rust
let (add_stipend, reentracy) = if gas_limit_is_stipend {
    (true, ReentrancyProtection::AllowNext)
} else if !value.is_zero() {
    (true, ReentrancyProtection::AllowReentry)
} else {
    (false, ReentrancyProtection::AllowReentry)
};
```
i.e., reorder so `(_, true)` (stipend match) is checked before `(false, _)` (nonzero value).
