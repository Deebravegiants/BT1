### Title
Storage-deposit charge coalescing in `execute_postponed_deposits` merges charges purely by contract address, silently discarding legitimate deposit charges of a contract re-deployed at a terminated contract's address within the same call stack - (`substrate/frame/revive/src/metering/storage.rs`)

### Summary
`RawMeter<T,E,Root>::execute_postponed_deposits` coalesces `Charge` entries solely by `T::AccountId` (contract address), with no notion of contract "incarnation". If a `Terminated` entry and a later `Alive{amount}` entry for the *same address* both land in `self.charges` within one call stack, the coalescing code treats the second entry as belonging to the same (now-dead) contract, reverses its deposit out of `self.total_deposit`, and drops it from the final charge/refund application loops.

### Finding Description
`execute_postponed_deposits` sorts `self.charges` by `contract` and stable-merges consecutive entries with the same address [1](#0-0) . The merge logic for `(Terminated, Alive{amount})` (regardless of order) always does:
```
self.total_deposit = self.total_deposit.saturating_sub(&amount);
last.state = ContractState::Terminated;
``` [2](#0-1) 

This is designed for the case of a *single* contract instance that accrued a deposit and then self-destructed in the same call stack (the deposit must be reversed because the contract no longer exists to hold it). It assumes one `Terminated` charge per address, enforced only via a `debug_assert!` (which is a no-op in release builds) [3](#0-2) . The `Charge` struct is keyed only by `contract: T::AccountId` [4](#0-3) , with no generation/incarnation counter distinguishing a terminated contract from a brand-new contract that is later deployed to the same address within the same transaction (e.g., via `CREATE2`-style deterministic address derivation combined with self-destruct-then-redeploy in one call stack).

If such an address reuse occurs, the sequence of pushed charges (Terminated for the old incarnation, then Alive{amount} for the new incarnation's genuine deposit) survives the stable sort in original relative order, hits the `(Terminated, Alive)` branch, and the new contract's deposit is subtracted from `total_deposit` and dropped from both the refund loop and the charge loop [5](#0-4) . The net effect is that the origin is never actually charged for storage the live, still-existing contract occupies, and `total_deposit` (the value asserted by the invariant to match real balance deltas) becomes wrong by exactly that amount.

### Impact Explanation
If contract address reuse within a single call stack is achievable, an attacker can obtain "free" storage deposit for a freshly (re)deployed contract: the accounting subtracts the new contract's charge instead of applying it, so the origin's balance is never debited for storage that is actually held on-chain. This is a real accounting-integrity bug in the deposit coalescing logic, matching the "avoid a charge that should have applied" branch of the scoped impact (rather than a double-refund, since a `Refund` merged against a prior `Alive` amount is bounded by that prior charge and cannot manufacture value that was never charged in the first case; the exploitable direction is charge-avoidance for the second incarnation).

### Likelihood Explanation
The bug in the merge arithmetic itself is unconditionally present in the code as written. However, real-world exploitability hinges entirely on whether `pallet_revive`'s contract-address derivation and instantiation checks actually permit a *new, distinct* contract to be deployed to the exact same account address as a contract that was terminated earlier in the same transaction/call stack (e.g., `CREATE2` with identical salt+code after `seal_terminate`, with the dead account's storage cleared synchronously). I was not able to confirm within the available investigation whether same-transaction address reuse of this kind is permitted by the current address-derivation and instantiation-existence checks in this codebase (this would require deeper review of `substrate/frame/revive/src/address.rs` and the instantiate/terminate paths in `exec.rs`, which I could not complete before running out of tool budget). Absent confirmed address reuse in one call stack, normal usage cannot trigger the `(Terminated, Alive)` merge path for a second, legitimately-charged contract, since a terminated contract's frame ends and no further storage charges for that exact address are recorded.

### Recommendation
Do not rely solely on `T::AccountId` to identify which `Charge` entries belong to the same contract "incarnation." Either (a) reject/short-circuit any further charge accumulation for an address once it has been marked `Terminated` within the same root meter's `self.charges` (turning the current `debug_assert!` into an enforced invariant, e.g. by rejecting instantiation at addresses that have a pending `Terminated` charge in the current meter), or (b) tag `Charge` with an incarnation identifier (e.g., a monotonically increasing per-address counter incremented on each instantiate) and only coalesce charges sharing the same `(contract, incarnation)` key, treating cross-incarnation charges as fully independent charge/refund pairs rather than merging them.

### Proof of Concept
Unit test in `substrate/frame/revive/src/metering/storage/tests.rs` (or a new test module) constructing a `RawMeter<Root>` with `charges = vec![Charge{contract: ADDR, state: Terminated}, Charge{contract: ADDR, state: Alive{amount: Deposit::Charge(100)}}]` and a nonzero `total_deposit`:
- Assert that after `execute_postponed_deposits`, the returned `total_deposit` equals `original_total_deposit - 100` (demonstrating the charge for the second incarnation is silently voided) instead of the expected value if the two incarnations were accounted independently (i.e., `original_total_deposit + 0` net plus a real 100-unit charge applied to `origin`).
- Assert that no `E::charge(origin, ADDR, Deposit::Charge(100), _)` call is recorded by a mock `Ext` implementation, proving the deposit for the live contract is never actually collected.

Full end-to-end confirmation additionally requires an integration/contract test that (1) deploys contract `X` via `CREATE2` with salt `S`, (2) has `X` call `seal_terminate`, (3) within the same transaction deploys contract `Y` via `CREATE2` with the same salt `S` (yielding the same address as `X`) and non-zero storage writes, and (4) checks the origin's post-transaction balance/held deposit does not reflect `Y`'s actual storage deposit — this part depends on confirming that same-transaction address reuse via `CREATE2` is actually permitted by `pallet_revive`'s instantiation/address-derivation logic, which was not verified in this review.
