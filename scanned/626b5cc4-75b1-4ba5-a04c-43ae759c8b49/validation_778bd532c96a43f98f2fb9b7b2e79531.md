### Title
OIDC login trusts unverified `email` claim to establish session identity, enabling identity/audit spoofing - ([File: core/sessions/oidcauth/oidc.go])

### Summary
The chainlink node's OIDC authentication strategy (`core/sessions/oidcauth/oidc.go`) establishes an authenticated session's identity purely from the OIDC provider's `email` claim, without checking `email_verified` or binding identity to the stable `iss`/`sub` claim pair. This mirrors the root cause of GHSA-777c-2fxx-qr28 (AshAuthentication): trusting a mutable, self-asserted email claim as the unique user identifier instead of the OIDC-spec-mandated `iss`+`sub` combination.

### Finding Description
In `handleTokenExchange` (`core/sessions/oidcauth/oidc.go:163-276`), after verifying the ID token's signature, the code extracts the `email` claim directly: [1](#0-0) 

There is no check of `email_verified`, and no use of the token's `sub`/`iss` claims anywhere in this flow. The role for the session is derived independently from a separate group claim (`IDClaimsToUserRole`), but the **identity** of the session — the value that flows through the rest of the application as the authenticated user's email — is this raw, unverified claim: [2](#0-1) 

This `user_email` is persisted into `oidc_sessions` and later resolved by `AuthorizedUserWithSession` (`core/sessions/oidcauth/oidc.go:349-391`) into a `clsessions.User{Email: ..., Role: ...}` object that is set as `SessionUserKey` in `AuthenticateBySession` (`core/web/auth/auth.go:52-71`) and used throughout GraphQL/REST resolvers, audit logging (`audit.AuthLoginSuccessNo2FA`), and identity-based access checks such as the "can't edit/delete self" guard in `UserController.UpdateRole`/`Delete` (`core/web/user_controller.go:122-131`, `177-186`), which compares `sessionUser.Email` (attacker-controlled) against a target email using `strings.EqualFold`.

Because the email is never validated as verified by the IdP, and because AshAuthentication-style upstream OIDC/OAuth providers commonly allow unverified or attacker-chosen `email` values (per the same precondition documented in the referenced advisory), an unauthenticated actor who can register/authenticate with any accepted OIDC provider using an arbitrary or reused email can cause the chainlink node to create a session whose recorded identity is that arbitrary email — including an email belonging to another real local/OIDC user.

### Impact Explanation
The role granted to the attacker's session still comes from *their own* group-claim mapping (`IDClaimsToUserRole`), so this does not directly escalate the attacker to another user's role/privilege level the way the original AshAuthentication bug allowed full account takeover via upsert. However, it does allow:
- Audit log poisoning / cross-user identity confusion: actions performed by the attacker are recorded under a spoofed victim email (`audit.AuthLoginSuccessNo2FA`, and every subsequent audit event keyed by `sessionUser.Email`).
- Self-protection bypass side effects in `UserController.UpdateRole`/`Delete`, where the "don't allow editing/deleting yourself" check is keyed only on the spoofed email string, so an attacker impersonating an admin's email would be incorrectly treated as that admin for these guard checks.
- Any downstream logic that treats `sessionUser.Email` as an authoritative, unique account identifier is subject to confusion between the OIDC session's asserted identity and the real local `users` table records, since `FindUser` for the OIDC driver separately queries the local `users` table by that same unverified email (`core/sessions/oidcauth/oidc.go:278-295`).

Endpoints that additionally re-verify a password (`NewAPIToken`, `DeleteAPIToken`, `UpdatePassword` in `core/web/user_controller.go`) are not directly exploitable for privilege escalation because they require knowledge of the real local admin's password in addition to the spoofed session email — this limits the severity compared to the original critical account-takeover advisory.

### Likelihood Explanation
Exploitability depends entirely on operator configuration: it requires `WebServer.AuthenticationMethod = 'oidc'` and an upstream OIDC/OAuth provider that does not strictly verify email ownership (the same precondition called out in the original advisory). Given that dependency, the exploit path from an unprivileged, unauthenticated external actor is straightforward (standard OIDC login flow), requiring no application misconfiguration beyond selecting OIDC auth with a permissive provider.

### Recommendation
- Verify the `email_verified` claim is `true` before trusting the `email` claim for session identity.
- Prefer binding session identity to the stable `iss` + `sub` claim pair rather than (or in addition to) email, and reject/flag mismatches.
- Ensure any self-identity comparisons (`UpdateRole`, `Delete` "self" checks) and audit logging use a claim value that cannot be spoofed by an unverified provider.

### Proof of Concept
1. Configure the chainlink node with `WebServer.AuthenticationMethod = 'oidc'` pointed at an OIDC/OAuth provider that does not enforce email verification (or one that allows email reuse/reclamation).
2. Register/authenticate on that provider using the email address of a legitimate local user, e.g. `admin@example.com`.
3. Complete the `/oidc-login` → `/oidc-exchange` flow against the chainlink node (`core/sessions/oidcauth/oidc.go:163`); the resulting `oidc_sessions` row and audit log entries will show `user_email = admin@example.com`, even though the "role" is derived from the attacker's own IdP group membership rather than `admin@example.com`'s actual privileges.
4. Observe that `sessionUser.Email` throughout the web layer (audit events, self-protection checks in `UserController`) reflects the spoofed identity rather than the attacker's true identity.
