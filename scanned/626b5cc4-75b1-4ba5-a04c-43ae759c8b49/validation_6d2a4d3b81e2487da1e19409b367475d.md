### Title
Vault allowlist authorization performs unbounded linear scans and retries over an attacker-inflatable, chain-synced request list - ([File: core/capabilities/vault/allow_list_based_auth.go])

### Summary
`AllowListBasedAuth.AuthorizeRequest`, used to authorize every Vault (secrets) request coming through the Gateway's node-side handler when the caller doesn't use JWT auth, resolves the caller's authorization by linearly scanning the entire in-memory list of on-chain "allowlisted requests" synced from the workflow registry, and it repeats this scan up to 11 times (once per retry) for every single Vault request. This list has no upper bound and is populated purely from chain state that any workflow owner can grow by registering additional allowlisted requests. [1](#0-0) [2](#0-1) 

### Finding Description
`AuthorizeRequest` calls `findAllowlistedItemWithRetry`, which loops up to `retryCount+1` (11) times. On every attempt it calls `r.workflowRegistrySyncer.GetAllowlistedRequests(ctx)` to obtain the full slice of allowlisted requests, builds a debug string for every element, and calls `fetchAllowlistedItem`, which does a plain `for _, item := range allowListedRequests` linear search for a matching digest: [1](#0-0) [2](#0-1) 

The backing list is maintained by `workflowRegistry.syncAllowlistedRequests`, which appends newly observed on-chain allowlisted requests to the existing slice, pruning only entries whose `ExpiryTimestamp` has passed: [3](#0-2) 

Because `ExpiryTimestamp` is attacker-controlled (set when the workflow owner registers the allowlisted request on-chain), a workflow owner (an "unprivileged" tenant relative to Vault/Gateway internals — no special node/operator role required) can register a very large number of distinct allowlisted requests with far-future expiries. This directly grows `w.allowListedRequests` without bound, exactly as the original report describes an adversary inflating `bounty`'s deposit list with many small, cheap entries.

This is structurally the same bug class as the report: an unprivileged actor can cheaply create many "entries" (deposits → allowlisted requests) that are unconditionally iterated in full on every subsequent, unrelated request from any user, turning a hot authorization path into an O(n) (here, effectively O(11·n) due to retries) operation that scales with attacker-controlled state rather than the size of the current request.

### Impact Explanation
Every Vault request authorized via the allowlist path (used by all non-JWT clients, i.e. the default/legacy Vault gateway path per the code comment "Requests without req.Auth continue using the allowlist-based path for backwards compatibility") pays the cost of this scan. If the list grows large enough, this authorization step becomes slow enough to:
- Blow through per-request timeouts in the Gateway/node request pipeline (`GatewayHandler`/`GatewayVaultRequestProcessor`), causing legitimate users' secrets create/update/delete/list requests to fail.
- Degrade node CPU/goroutine time across all DON members handling Vault traffic, since every node independently runs this authorization logic.
- Because the list is retried up to 11 times with `allowListBasedAuthRetryInterval` (3s) sleeps between attempts when a digest isn't found, a request for an as-yet-unregistered or invalid digest triggers 10 additional full re-scans plus ~30 seconds of wall time, compounding the cost under load.

This does not directly move funds, but it can deny service to the entire Vault allowlist-authorization path for all tenants, similar in kind to the reported "adversary can brick refunds" finding (a shared unbounded loop over attacker-inflatable state breaks a critical operation for everyone).

### Likelihood Explanation
Likelihood is moderate: exploitation requires the ability to register on-chain allowlisted requests, which likely costs gas per entry (similar to the "many small deposits" cost in the original report) and is not fully free, but nothing in the reviewed code caps the number of live allowlisted entries a single owner (or many owners) can create, nor the total in-memory list size that `workflowRegistry` will hold in `w.allowListedRequests`. Because expiries are attacker-chosen, entries can be kept alive indefinitely, so the list can grow monotonically over time even from many small/cheap registrations.

### Recommendation
- Replace the linear scan with an indexed/keyed lookup (e.g., a `map[[32]byte]WorkflowRegistryOwnerAllowlistedRequest`) built and maintained by `workflowRegistry` for O(1) digest lookups instead of exposing/iterating a flat slice.
- Cap the number of allowlisted requests tracked in memory (globally and/or per owner) and enforce an equivalent cap on-chain in the workflow registry contract, or evict oldest/lowest-priority entries once a limit is reached.
- Avoid rebuilding the full debug log string (`allowedRequestsStrs`) for the entire list on every authorization attempt — this makes the cost of the scan even higher and should at minimum be gated behind a debug flag.
- Reconsider the 11x retry multiplier interacting with the full-list scan; the retry loop should not re-fetch/re-scan the entire list if the underlying syncer can support a targeted digest lookup.

### Proof of Concept
1. Deploy/own a workflow and repeatedly call the workflow registry's allowlist function to register a very large number (e.g., hundreds of thousands) of distinct `RequestDigest` values with expiry timestamps far in the future, at whatever gas cost is required (this is the analog of "a large number of small deposits").
2. Wait for `workflowRegistry.syncAllowlistedRequests` to pick these up; per the sync loop, they are appended into `w.allowListedRequests` and never pruned before expiry ( [4](#0-3) ).
3. As a normal user, send a legitimate Vault request through the Gateway without a JWT (using the allowlist path). Each node calls `AllowListBasedAuth.AuthorizeRequest` → `findAllowlistedItemWithRetry` → `fetchAllowlistedItem`, which now must scan the inflated list on every request and retry, up to 11 times, each iterating the full slice ( [5](#0-4) ).
4. As the list size grows, measure increasing latency/CPU cost per Vault authorization; beyond a threshold, requests begin to time out at the Gateway/handler layer, denying Vault operations to all users relying on the allowlist path.

func (r *allowListBasedAuth) findAllowlistedItemWithRetry(ctx context.Context, req jsonrpc.Request[json.RawMessage], requestDigest string, requestDigestBytes32 [32]byte) (*workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest, []string, error) {
	for attempt := 0; attempt <= r.retryCount; attempt++ {
		allowedRequests := r.workflowRegistrySyncer.GetAllowlistedRequests(ctx)
		allowedRequestsStrs := make([]string, 0, len(allowedRequests))
		for _, rr := range allowedRequests {
			allowedReqStr := fmt.Sprintf("AuthorizedOwner: %s, RequestDigest: %s, ExpiryTimestamp: %d", rr.Owner.Hex(), hex.EncodeToString(rr.RequestDigest[:]), rr.ExpiryTimestamp)
			allowedRequestsStrs = append(allowedRequestsStrs, allowedReqStr)
		}
		r.lggr.Debugw("AllowListBasedAuth loaded allowlisted requests", "method", req.Method, "requestID", req.ID, "attempt", attempt+1, "allowedRequests", allowedRequestsStrs)

		allowlistedRequest := r.fetchAllowlistedItem(allowedRequests, requestDigestBytes32)
		if allowlistedRequest != nil {
			return allowlistedRequest, allowedRequestsStrs, nil
		}
		if attempt == r.retryCount {
			return nil, allowedRequestsStrs, nil
		}

		r.lggr.Debugw("AllowListBasedAuth request digest not yet allowlisted, retrying",
			"method", req.Method,
			"requestID", req.ID,
			"digestHexStr", requestDigest,
			"attempt", attempt+1,
			"maxAttempts", r.retryCount+1,
			"retryInterval", r.retryInterval)
		if err := sleepWithContext(ctx, r.retryInterval); err != nil {
			r.lggr.Debugw("AllowListBasedAuth retry canceled", "method", req.Method, "requestID", req.ID, "error", err)
			return nil, nil, err
		}
	}

	return nil, nil, nil // unreachable: loop always returns
}

func (r *allowListBasedAuth) fetchAllowlistedItem(allowListedRequests []workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest, digest [32]byte) *workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest {
	for _, item := range allowListedRequests {
		if item.RequestDigest == digest {
			return &item
		}
	}
	return nil
}

func (w *workflowRegistry) syncAllowlistedRequests(ctx context.Context) {
	ticker := w.getTicker(defaultTickIntervalForAllowlistedRequests)
	w.lggr.Debug("starting syncAllowlistedRequests")
	for {
		select {
		case <-ctx.Done():
			w.lggr.Debug("shutting down syncAllowlistedRequests, %s", ctx.Err())
			return
		case <-ticker:
			newAllowListedRequests, totalAllowlistedRequests, head, err := w.getAllowlistedRequests(ctx, w.contractReader)
			if err != nil {
				w.lggr.Errorw("failed to call getAllowlistedRequests", "err", err)
				continue
			}
			w.allowListedMu.Lock()
			// Prune expired requests
			activeAllowlistedRequests := []workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest{}
			expiredRequestsCount := 0
			for _, request := range w.allowListedRequests {
				if int64(request.ExpiryTimestamp) > time.Now().Unix() {
					activeAllowlistedRequests = append(activeAllowlistedRequests, request)
				} else {
					expiredRequestsCount++
				}
			}

			// Add new requests
			activeAllowlistedRequests = append(activeAllowlistedRequests, newAllowListedRequests...)
			w.allowListedRequests = activeAllowlistedRequests
			w.lastSeenAllowlistedRequestsCount = totalAllowlistedRequests
			w.lggr.Debugw("synced allowlisted requests",
				"newRequestsNum", len(newAllowListedRequests),
				"expiredRequestsNum", expiredRequestsCount,
				"activeRequestsNum", len(w.allowListedRequests),
				"lastSeenOnchainRequestsNum", w.lastSeenAllowlistedRequestsCount,
				"blockHeight", head.Height,
			)
			w.allowListedMu.Unlock()
		}
	}
}
