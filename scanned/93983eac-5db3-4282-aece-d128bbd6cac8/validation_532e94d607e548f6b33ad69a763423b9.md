This confirms the vulnerability pattern: `ldap.EscapeFilter` is a filter-escaping function (escapes `*`, `(`, `)`, `\`, NUL for LDAP search-filter syntax) but is being reused to sanitize input that gets embedded directly into a Distinguished Name (DN) string used for LDAP `Bind()` calls, not into a search filter. DN escaping requires different rules (escaping `,`, `+`, `"`, `\`, `<`, `>`, `;`, leading/trailing spaces, leading `#`), which `EscapeFilter` does not provide.

### Title
LDAP DN Injection in CreateSession/TestPassword Bind via Filter-Escaped (Not DN-Escaped) Email - ([File: core/sessions/ldapauth/ldap.go])

### Summary
The LDAP authentication provider's login path (`CreateSession`) and credential-test path (`TestPassword`) build the LDAP Bind DN by concatenating a user-supplied, unauthenticated `email` value into a DN string, sanitized only with `ldap.EscapeFilter`. `EscapeFilter` is designed to neutralize LDAP *search-filter* metacharacters (`*`, `(`, `)`, `\`, NUL) — it does not escape DN metacharacters such as `,`, `+`, `"`, `<`, `>`, `;`, or leading `#`/space. Since the sanitized value is placed directly into a DN (not a filter) that is passed to `conn.Bind()`, an unauthenticated caller can supply an `email` containing unescaped commas/other DN separators to alter the RDN sequence of the DN being bound against.

### Finding Description
In `core/sessions/ldapauth/ldap.go`, `CreateSession` (the unauthenticated login handler invoked from the Session API) does: [1](#0-0) 
and `TestPassword` (invoked for local admin/API credential checks) does the identical construction: [2](#0-1) 

Both build `searchBaseDN` via `fmt.Sprintf("%s=%s,%s,%s", l.config.BaseUserAttr(), escapedEmail, l.config.UsersDN(), l.config.BaseDN())` where `escapedEmail` was produced by `ldap.EscapeFilter`. `EscapeFilter` only escapes filter metacharacters used inside `(attr=value)` search filters; it is not a DN escaper. RFC 4514 DN escaping requires escaping `,`, `+`, `"`, `\`, `<`, `>`, `;`, and leading `#`/space and trailing space — none of which `EscapeFilter` handles. Because the `sr.Email` field of `sessions.SessionRequest` originates directly from the unauthenticated login HTTP request body, an attacker controls this string end-to-end before it is spliced into the DN passed to `conn.Bind(searchBaseDN, sr.Password)`.

This mirrors the CWE-90 LDAP injection class in the reported Apache CXF advisory: user input is embedded into an LDAP query/DN construct using the wrong (or insufficient) escaping mechanism, allowing structural manipulation of the LDAP operation.

### Impact Explanation
Because the Bind DN's structure can be altered by injecting unescaped comma-delimited components, an attacker may be able to influence which DN the ephemeral connection actually attempts to bind as. In many LDAP topologies this class of bug enables authentication confusion/bypass (binding against or probing for the existence of arbitrary DNs) — an unprivileged actor manipulating a node's authentication process, which is a critical operation since a success path leads directly to session issuance (`session := sessions.NewSession()` → `INSERT INTO ldap_sessions ...`) and role assignment via `FindUser`.

### Likelihood Explanation
Likelihood is high for exposure: `CreateSession` is reachable by any unauthenticated client hitting the login endpoint with attacker-controlled `Email`/`Password` fields — no prior authentication is required to reach the vulnerable code path. `TestPassword` is used in credential verification flows with the same escaping mistake. Exploitability depends on the specific upstream LDAP server's tolerance of malformed/attacker-crafted DNs during `Bind`, but the sanitization is objectively the wrong function for this sink, which is the same root cause as the referenced advisory.

### Recommendation
Do not reuse `ldap.EscapeFilter` for values embedded in DN strings. Instead:
- Use a proper DN-component escaper for `escapedEmail` wherever it's placed into a DN (`ldap.EscapeDN` if available in the go-ldap version used, or an RFC 4514-compliant escape function), applied to `CreateSession` (line 406-407) and `TestPassword` (line 512-513).
- Alternatively, avoid constructing bind DNs from user input entirely: perform a filter-based Search (using `ldap.EscapeFilter` correctly, as done elsewhere in `FindUser`) with the service/read-only account to resolve the user's actual DN first, then Bind using that resolved, trusted DN and the user-supplied password.
- Add regression tests supplying emails containing `,`, `+`, `"`, `<`, `>`, `;` to confirm the resulting Bind DN cannot be manipulated to reference an unintended entry.

### Proof of Concept
1. Submit a login request to the Session API (`POST` to the login endpoint that maps to `CreateSession`) with `sr.Email` set to a value containing an unescaped comma sequence designed to append or override RDN components, e.g. `"attacker@example.com,ou=Admins,dc=example,dc=com"` combined with a crafted password.
2. `ldap.EscapeFilter` passes commas through unescaped (it only escapes `*()\` and NUL), so `escapedEmail` retains the injected `,ou=Admins,dc=example,dc=com` segment.
3. The resulting `searchBaseDN` fed to `conn.Bind(searchBaseDN, sr.Password)` at [3](#0-2)  no longer represents the DN the application intended (`uid=<email>,ou=Users,dc=...`), demonstrating the DN can be structurally altered by attacker input — confirming the injection primitive exists at the sink, independent of any specific downstream LDAP server behavior.
