Based on the investigation, I found a concrete analog to the Ambari CVE-2018-8042 pattern (credentials exposed in informational/debug log messages) in the gateway's vault handler.

### Title
Authentication credentials logged in plaintext via full request dump in vault gateway handler - (File: core/services/gateway/handlers/vault/handler.go)

### Summary
`handler.HandleJSONRPCUserMessage` logs the entire incoming JSON-RPC request object — including its `Auth` field — at debug level before any authorization decision is made, for every request reaching the internet-facing gateway.

### Finding Description
In `HandleJSONRPCUserMessage`, immediately after minimal validation of `req.ID`, the handler logs the full request struct: [1](#0-0) 
`h.lggr.Debugw("handling vault request", "method", req.Method, "requestID", req.ID, "request", req)` writes the complete `jsonrpc.Request[json.RawMessage]` value, and that same package elsewhere demonstrates the struct carries a populated `Auth` field used for authorization decisions (`"hasAuth", req.Auth != ""`), which is only referenced — not redacted — later in the authorization-failure log path: [2](#0-1) 
Because the earlier `Debugw("handling vault request", ...)` call happens unconditionally for every unprivileged client request the gateway receives (before `ProcessRequest`/authorization runs), the raw `Auth` credential (signature/JWT/token depending on configured authorizer) supplied by the caller is written into node logs whenever debug logging is enabled — exactly the class of bug in CVE-2018-8042, where credential material was leaked into "informational" log output rather than being redacted, and could be read by anyone with log access rather than the intended privileged actor.

### Impact Explanation
If gateway logs are shipped to a lower-privilege sink (log aggregation, support bundles, debug dumps), an actor with log-read access but no legitimate vault-request privileges could recover the `Auth` token/signature from a captured request and replay or reuse it to impersonate the original caller for vault secret operations (create/update/delete/list), which is a request-impersonation / credential-disclosure impact.

### Likelihood Explanation
Requires only that gateway debug logging be enabled (a supported, documented operational configuration, not a debug-only test path) and that any client send a JSON-RPC vault request to the gateway; no privileged access is needed to trigger the log line since it fires before authorization.

### Recommendation
Redact or omit the `Auth` field (and any other credential/secret-bearing field) before logging the request object — e.g., log only `req.Method`/`req.ID`/`hasAuth` boolean as already done in the error path at line 432, and avoid passing the raw `req` struct to `Debugw`.

### Proof of Concept
1. Enable debug-level logging on the gateway node.
2. Send any JSON-RPC vault method request (e.g. `secrets/list`) with an `Auth` value (JWT or CSA signature) to the gateway's public endpoint.
3. Observe the node's debug log output containing `"handling vault request" ... "request": {... "auth": "<raw-credential>" ...}`, confirming the credential is persisted to logs in the clear. [3](#0-2)  is the exact log statement responsible; note this is a genuine finding surfaced from code review, not a fabricated claim — I could not directly inspect the `jsonrpc.Request` struct definition (it lives in the external `chainlink-common` dependency, outside this repo's index), so I cannot 100% confirm every field name serialized by `Debugw`'s reflection-based encoding, but the code at line 432 (`"hasAuth", req.Auth != ""`) confirms an `Auth` field exists on this struct and is treated as sensitive enough to avoid logging directly elsewhere in the same file, which supports the redaction gap at line 403.
