### Title
`AllowNext` reentrancy heuristic never triggers for real value-transferring calls, leaving classic reentrancy protection disabled - ([File: substrate/frame/revive/src/vm/evm/instructions/contract.rs])

### Summary
The `run_call` helper in `substrate/frame/revive/src/vm/evm/instructions/contract.rs` selects `ReentrancyProtection` based on a `match` over `(value.is_zero(), gas_limit == CALL_STIPEND)`, but the arm ordering makes any nonzero-value call fall into `ReentrancyProtection::AllowReentry` before the gas-stipend check is even evaluated. Since real Solidity `.transfer(amount)`/`.send(amount)` calls with `amount > 0` are exactly the scenario `AllowNext` was designed to protect (per the doc comment on `ReentrancyProtection::AllowNext`), this means the protection is effectively dead code for the only case that matters in practice, permitting unrestricted reentrancy on value-transfer callbacks.

### Finding Description
`ReentrancyProtection::AllowNext` is documented in `substrate/frame/revive/src/exec.rs` (lines 122-142) as existing specifically "for calls that transfer value but restrict gas so that the callee only has a stipend gas amount... we enforce it explicitly here." [1](#0-0) 

The heuristic that is supposed to detect this case lives in `run_call`:
```rust
let (add_stipend, reentracy) =
    match (value.is_zero(), gas_limit.try_into().is_ok_and(|limit: u64| limit == CALL_STIPEND))
    {
        (false, _) => (true, ReentrancyProtection::AllowReentry),
        (_, true) => (true, ReentrancyProtection::AllowNext),
        (_, _) => (false, ReentrancyProtection::AllowReentry),
    };
``` [2](#0-1) 

Per `prdoc/stable2603/pr_11227.prdoc`, the real EVM/solc semantics are:
| Solidity call | value | gas passed | stipend source |
|---|---|---|---|
| `target.transfer(amount)` (amount>0) | >0 | 0 | EVM adds 2300 automatically |
| `target.send(amount)` (amount>0) | >0 | 0 | EVM adds 2300 automatically |
| `target.transfer(0)` / `send(0)` | 0 | 2300 | compiler injects explicitly | [3](#0-2) 

This means the realistic, dangerous reentrancy vector — `.transfer(amount)`/`.send(amount)` with a nonzero `amount` — arrives at `run_call` with `value.is_zero() == false`. The first match arm `(false, _)` matches unconditionally on this and returns `ReentrancyProtection::AllowReentry`, completely bypassing the gas-stipend check and disabling any reentrancy protection. Only the practically meaningless `transfer(0)`/`send(0)` case (value is zero, gas is exactly 2300) reaches the `AllowNext` arm, which is exactly what `pr_11227` tests confirm were added — tests only cover the zero-value edge case, not the actual value-transfer scenario the mechanism claims to defend.

Once `AllowReentry` is selected, `PrecompileExt::call` in `substrate/frame/revive/src/exec.rs` never sets `self.top_frame_mut().allows_reentry = false` for either `Strict` or `AllowNext` branches: [4](#0-3)  Consequently `allows_reentry(&dest)` — which scans the whole frame stack for a `false` flag — never rejects the reentrant call back into the victim's frame: [5](#0-4) 

### Impact Explanation
Any PVM/EVM contract deployed on `pallet_revive` that relies on the intended reentrancy protection for value transfers (or that has the classic "transfer funds, then update state" bug pattern that Ethereum's 2300-gas stipend and `AllowNext` are supposed to mitigate) is fully exploitable via standard cross-contract reentrancy. An attacker contract can re-enter the victim's withdrawal function during the stipend-limited callback triggered by `.transfer()`/`.send()`, executing the withdrawal logic multiple times before the victim's balance/accounting is updated, resulting in fund double-spend/theft — exactly the scoped impact.

### Likelihood Explanation
- Preconditions: a victim PVM/EVM contract using `.transfer()`/`.send()` (or Solidity's low-level `call` with an explicit 2300 gas value and nonzero value) to send funds to `msg.sender`, with state updates occurring after the external call.
- Feasibility: fully reachable through the standard `eth_call`/`call_evm` extrinsic path used by any unprivileged signed account; no admin/governance access required.
- Repeatability: deterministic — every nonzero-value transfer through this code path resolves to `AllowReentry`, so the bug triggers on every such call, not just under specific timing/race conditions.

### Recommendation
Fix the match ordering so that the stipend/gas check is evaluated regardless of whether value is zero, i.e., treat any call at `gas_limit == CALL_STIPEND` with `AllowNext`, and only fall back to `AllowReentry` when the gas limit is not the stipend value:
```rust
let is_stipend = gas_limit.try_into().is_ok_and(|limit: u64| limit == CALL_STIPEND);
let (add_stipend, reentracy) = match (value.is_zero(), is_stipend) {
    (_, true) => (true, ReentrancyProtection::AllowNext),
    (false, false) => (true, ReentrancyProtection::AllowReentry), // or Strict, revisit intent
    (true, false) => (false, ReentrancyProtection::AllowReentry),
};
```
Add integration tests exercising nonzero-value `.transfer()`/`.send()` reentrancy (not just the zero-value edge case covered by `pr_11227`), asserting that a reentrant callback during the stipend-limited transfer is rejected with `Error::ReentranceDenied`.

### Proof of Concept
Rust integration test plan (in `substrate/frame/revive/src/tests.rs` or fixtures used by `pr_11227`):
1. Deploy `Victim` fixture contract with `withdraw()`: reads caller's recorded balance, calls `msg.sender.transfer(balance)` (or `call{value: balance, gas: 2300}("")`), then zeroes the balance record.
2. Deploy `Attacker` fixture contract whose `receive()`/fallback calls back into `Victim.withdraw()`.
3. Fund `Victim` with `N` tokens credited to `Attacker`. Call `Victim.withdraw()` from `Attacker`.
4. Assert: without the fix, `Attacker`'s reentrant `withdraw()` call succeeds (no `ReentranceDenied` error) and `Victim`'s total balance decreases by more than `N` (double withdrawal) — reproducing the reentrancy drain.
5. Assert: with the fix applied, the reentrant call inside `receive()` fails with `Error::<T>::ReentranceDenied`, and `Victim`'s balance decreases by exactly `N`.
