### Title
Liquidity withdrawal fee is bypassable by splitting `remove_liquidity` into minimum-unit lp-token burns - ([File: substrate/frame/asset-conversion/src/lib.rs])

### Summary
`do_remove_liquidity` computes `withdrawal_fee_amount = T::LiquidityWithdrawalFee::get() * lp_token_burn` using `Permill` truncating multiplication, then sets `lp_redeem_amount = lp_token_burn.saturating_sub(withdrawal_fee_amount)`. For any `lp_token_burn` small enough that `Permill * lp_token_burn` rounds down to `0` (e.g. `lp_token_burn = 1` for any fee below 100%), the fee is entirely skipped for that call, so a user can fragment a large withdrawal into many minimal-unit withdrawals and pay zero cumulative fee instead of the fee that would apply to a single large withdrawal.

### Finding Description
The fee is computed per-call on the `lp_token_burn` argument passed to `remove_liquidity`/`do_remove_liquidity`, with no floor/minimum-fee enforcement and no tracking of cumulative burned/redeemed amounts across multiple calls by the same account. Because `Permill` multiplication (`value * parts_per_million / 1_000_000`) truncates towards zero, any `lp_token_burn` value below the reciprocal threshold of the configured fee produces `withdrawal_fee_amount = 0`, making `lp_redeem_amount == lp_token_burn`. Since the reserves/asset amounts returned to the withdrawer are computed from `lp_redeem_amount` relative to `total_supply`, calling `remove_liquidity(1)` N times yields the same aggregate redeemed reserves as `remove_liquidity(N)` would without any fee applied, whereas a single `remove_liquidity(N)` call would apply the fee to the whole amount. No check in the pallet enforces a minimum fee per call, aggregates fee across calls per account, or rejects sub-fee-granularity `lp_token_burn` values (other than the pallet's standard existential/zero-amount checks unrelated to fee granularity). ### Impact Explanation
The withdrawal fee in this pallet functions as a disincentive/redistribution mechanism: lp tokens burned but not redeemed (`lp_token_burn - lp_redeem_amount`) effectively increase the value-per-share for remaining LPs. By fragmenting withdrawals to always hit the zero-fee rounding case, an attacker withdraws their full proportional share without contributing this redistribution amount, extracting more value relative to remaining LPs than an equivalent single large withdrawal would, and reducing protocol/LP fee revenue to zero regardless of total withdrawal size. This is an accounting/economic-invariant violation (fee should be invariant to fragmentation) rather than a fund-freezing or double-spend bug — no assets outside the attacker's own lp-token backing are misappropriated.

### Likelihood Explanation
Fully reachable by any unprivileged signed account holding LP tokens through the standard `remove_liquidity` extrinsic — no special origin, proxy, or privileged path is required. The only cost to the attacker is per-extrinsic transaction/weight fees, which bound the practical scale of exploitation (splitting into thousands of `lp_token_burn = 1` calls incurs proportional transaction overhead), but for any `LiquidityWithdrawalFee` configuration and moderate withdrawal sizes, the fee bypass is deterministic and repeatable, not probabilistic.

### Recommendation
Enforce a fee that does not vanish under fragmentation, e.g. by rounding the fee up (`Permill::mul_ceil` or equivalent) instead of truncating down, and/or enforce a minimum non-zero fee whenever `lp_token_burn > 0` and `LiquidityWithdrawalFee` is non-zero, so that `withdrawal_fee_amount >= 1` for any burn above zero once the fee rate is non-zero.

### Proof of Concept
Rust unit test in `substrate/frame/asset-conversion/src/tests.rs`:
1. Configure a pool and mint LP tokens such that the account holds `N` lp tokens (`N` large enough that `LiquidityWithdrawalFee * N > 0`).
2. Path A: call `AssetConversion::remove_liquidity(origin, pool_id, N, ...)` once; record total assets received (`assets_A`).
3. Path B: reset state, call `remove_liquidity(origin, pool_id, 1, ...)` N times; record cumulative assets received (`assets_B`).
4. Assert `assets_B - assets_A` scales with `N` (fee-bypass amount grows linearly), violating the invariant that fee collected should be independent of fragmentation — expected assertion: `assets_B > assets_A` and the difference approximately equals `LiquidityWithdrawalFee * N` worth of reserves, demonstrating the fee is fully bypassed in Path B.
