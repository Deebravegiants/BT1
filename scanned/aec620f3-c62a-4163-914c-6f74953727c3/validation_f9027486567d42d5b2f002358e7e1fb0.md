## Title
Unauthenticated `/v2/resume/:runID` callback allows state-confusion replay of already-resolved async task results and duplicate pipeline continuation - (File: core/services/pipeline/orm.go)

### Summary
The C4 finding shows that SIZE's `finalize()`/`cancelAuction()`/`cancelBid()` state machine inferred "is this auction finalized" purely from a mutable, attacker-influenced field (`lowestQuote == type(uint128).max`) instead of a dedicated, monotonic state flag, letting an attacker resurrect a "not-yet-finalized" state after funds had already moved. Chainlink's async pipeline "resume" callback exhibits the same class of bug: whether a specific `pipeline_task_runs` row may still be written is inferred from the *pipeline_run's* coarse state (`running`/`suspended`) rather than from that individual task run's own completion status, and the callback endpoint that triggers this write is completely unauthenticated.

### Finding Description
`core/web/router.go` registers the resume endpoint outside of any auth middleware: [1](#0-0) 

`PipelineRunsController.Resume` accepts an arbitrary `taskID` UUID and result body from any caller and forwards it straight into the pipeline runner with no additional authorization check: [2](#0-1) 

`runner.ResumeRun` calls `UpdateTaskRunResult`, and only decides whether to re-launch pipeline execution (`start=true`) based on the *pipeline_run's* `State` field, not on whether this particular task run had already produced a result: [3](#0-2) 

`UpdateTaskRunResult` in the ORM selects the parent run using only a coarse guard (`pipeline_runs.state in ('running','suspended')`) and then unconditionally overwrites the task run's `output`/`error`/`finished_at`, with no check that the specific `pipeline_task_runs.id` had not already been resolved: [4](#0-3) 

Because the guard is at the run level and not the task level, and the `FOR UPDATE` lock is only held for the duration of a single transaction on the `pipeline_runs` row, this creates a state-confusion window analogous to the SIZE bug:
- Any holder of a resume URL (an external adapter, or anyone who intercepted/replayed it) can call `PATCH /v2/resume/:runID` for a task whose result has already been consumed by pipeline scheduling logic, since the `UPDATE pipeline_task_runs ... WHERE id = $1` has no `finished_at IS NULL` precondition.
- For pipelines with multiple concurrent async tasks, a resume call for task B that arrives while the run is already `running` (because task A's resume just flipped the state from `suspended` to `running`) is accepted and silently rewrites B's row, but does **not** re-trigger `r.Run` (since `run.State != RunStatusSuspended` by the time B's resume executes) — orphaning B's result or causing the concurrently-running goroutine (which still holds a stale in-memory `run.PipelineTaskRuns` snapshot) to treat B as still pending and re-invoke the downstream task, including tasks with side effects (e.g. `ETHTx`).
- Conversely, an attacker who simply replays/resends a resume request for a task that already has `finished_at` set can overwrite the recorded output/error while the run is still `running`/`suspended`, corrupting values already consumed by the DAG or feeding poisoned data into subsequent fund-moving tasks.

This mirrors the SIZE root cause precisely: state ("has this unit of work already been settled?") is derived from a broader, overwritable field rather than a dedicated per-unit completion guard, and the endpoint that can trigger the confusing transition requires no privileged credential — it is guarded only by the entropy of the UUID that is unrelated to any actual state-check.

### Impact Explanation
An unprivileged holder of a resume callback URL can:
- Corrupt/overwrite already-persisted async task results after they have already been consumed by the pipeline, without any authentication beyond knowledge of the task UUID.
- Trigger duplicate concurrent execution paths for the same pipeline run, which can lead to duplicate invocation of side-effecting tasks (e.g., `ETHTx`, on-chain writes), i.e., duplicate/unauthorized job runs or fund movement — the impact category explicitly called out as acceptable for this analog exercise.

### Likelihood Explanation
Likelihood is moderate-to-low in practice because it requires: (1) a job pipeline with concurrent/multiple async tasks, and (2) the resume URL(s) being available to more than one truly trusted party, or a caller re-sending a resume request outside the normal single-fire adapter callback. However, no authentication or freshness check exists to prevent it — the endpoint is intentionally unauthenticated (`unauthedv2`), and the missing per-task-run completion guard makes the race exploitable by any party that can send an HTTP PATCH with a valid UUID, including a misbehaving/compromised external adapter.

### Recommendation
- Add a `finished_at IS NULL` (or equivalent "not yet resolved") condition to the `UPDATE pipeline_task_runs` statement in `UpdateTaskRunResult`, so a task run can only be resolved once.
- Decide whether to restart the run (`start`) based on whether *all* pending task runs for that pipeline run are now resolved (re-querying task-level state within the same transaction), not solely on the previously-read `pipeline_runs.state`.
- Consider binding resume tokens to a one-time-use secret independent of predictable UUID reuse, and rejecting resume calls for task runs that are already terminal.

### Proof of Concept
1. Create a job whose pipeline has two independent `async=true` tasks (A and B) feeding into a downstream `ETHTx`/fund-moving task, so the run suspends waiting on both.
2. Have the bridge for A respond immediately, calling `PATCH /v2/resume/:taskA_UUID` — this flips `pipeline_runs.state` from `suspended` to `running` and spawns a goroutine `G1` using an in-memory snapshot of `run` where B is still pending.
3. Before `G1` re-derives B's true DB state, call `PATCH /v2/resume/:taskB_UUID` with a crafted result — this is accepted (`pipeline_runs.state` is `running`, which passes the `WHERE` filter) and persists B's row, but does **not** spawn a new goroutine (`run.State != Suspended`).
4. `G1`, still holding stale in-memory data for B, treats B as pending and re-invokes the downstream async bridge task / re-schedules dependents, producing duplicate execution and/or feeding the downstream `ETHTx` task with inconsistent state — all without ever authenticating past the two PATCH calls to `/v2/resume/:runID`.

// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
}

	}
	return nil
}

func (o *orm) UpdateTaskRunResult(ctx context.Context, taskID uuid.UUID, result Result) (run Run, start bool, err error) {
	if result.OutputDB().Valid && result.ErrorDB().Valid {
		panic("run result must specify either output or error, not both")
	}
	err = o.transact(ctx, func(tx *orm) error {
		sql := `
		SELECT pipeline_runs.*, pipeline_specs.dot_dag_source "pipeline_spec.dot_dag_source", job_pipeline_specs.job_id "job_id"
		FROM pipeline_runs
		JOIN pipeline_task_runs ON (pipeline_task_runs.pipeline_run_id = pipeline_runs.id)
		JOIN pipeline_specs ON (pipeline_specs.id = pipeline_runs.pipeline_spec_id)
		JOIN job_pipeline_specs ON (job_pipeline_specs.pipeline_spec_id = pipeline_specs.id)
		WHERE pipeline_task_runs.id = $1 AND pipeline_runs.state in ('running', 'suspended')
		FOR UPDATE`
		if err = tx.ds.GetContext(ctx, &run, sql, taskID); err != nil {
			return fmt.Errorf("failed to find pipeline run for task ID %s: %w", taskID.String(), err)
		}

		// Update the task with result
		sql = `UPDATE pipeline_task_runs SET output = $2, error = $3, finished_at = $4 WHERE id = $1`
		if _, err = tx.ds.ExecContext(ctx, sql, taskID, result.OutputDB(), result.ErrorDB(), time.Now()); err != nil {
			return fmt.Errorf("failed to update pipeline task run: %w", err)
		}

		if run.State == RunStatusSuspended {
			start = true
			run.State = RunStatusRunning

			sql = `UPDATE pipeline_runs SET state = $2 WHERE id = $1`
			if _, err = tx.ds.ExecContext(ctx, sql, run.ID, run.State); err != nil {
				return fmt.Errorf("failed to update pipeline run state: %w", err)
			}
		}

		return loadAssociations(ctx, tx.ds, []*Run{&run})
	})

	return run, start, err
}
