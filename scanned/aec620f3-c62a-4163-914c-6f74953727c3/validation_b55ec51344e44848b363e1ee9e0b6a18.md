### Title
Password/secret disclosure via URL query parameters in key export/import and CLI login endpoints - (File: core/web/keys_controller.go)

### Summary
CVE-2018-20243 describes credentials sent as URL query parameters in a POST request, exposing them via proxy/access logs, browser history, and Referer headers. The Chainlink node exhibits the identical bug-class pattern: the `oldpassword` and `newpassword` secrets used to decrypt/re-encrypt exported key material are transmitted as HTTP query-string parameters on `POST` requests, both on the client (CLI) side and the server (controller) side.

### Finding Description
Across every key-management CLI command (CSA, ETH/EVM, OCR, OCR2, P2P, VRF), the shell builds an export/import URL with the password appended to the query string rather than the request body: [1](#0-0) [2](#0-1) [3](#0-2) 

On the server side, the corresponding controllers read these secrets directly out of the query string via `c.Query(...)`: [4](#0-3) [5](#0-4) [6](#0-5) 

Because these are query parameters (not headers or body), they are:
- Logged by the Gin request logger middleware (`loggerFunc`) registered on the router, which typically logs the full request path including the query string, unless explicitly redacted.
- Recorded in HTTP access logs of any reverse proxy or load balancer placed in front of the node.
- Persisted in shell history / process listings when constructed via the CLI (`ps aux` exposure), and stored in browser history if triggered from a UI/tool that hits the URL directly.
- Potentially leaked via the `Referer` header if any redirect or resource load originates from a page containing this URL.

This exactly matches the root cause of CVE-2018-20243: "POST with username/password in URL parameters exposes credentials," just applied to the node's key-encryption passwords instead of login credentials.

### Impact Explanation
The exposed value is the encryption/decryption password (`oldpassword`/`newpassword`) used to protect exported private key material (CSA, ETH/EVM, OCR, OCR2, P2P, VRF keys). If this password leaks via logs/proxies/history, and an attacker also obtains the corresponding encrypted key export file (which may be stored, backed up, or transmitted separately), they can decrypt sensitive node keys — potentially leading to fund loss (ETH keys), impersonation (P2P/CSA keys), or unauthorized OCR round participation. This is a genuine secret-disclosure class issue, matching the "key/secret disclosure" acceptance criterion, though it requires an authenticated session to reach these endpoints (Import/Export require an existing admin/API session per `sessionRoutes`/`v2Routes` wiring in `core/web/router.go`), so it is not a fully unauthenticated bypass — the primary risk is secondary disclosure of a secret that should never be logged or appear in a URL, not a direct authentication bypass.

### Likelihood Explanation
Any operator or automation script invoking key export/import via the CLI (`chainlink keys ... export/import`) will transmit the password in the URL by default — this is not an edge case, it's the standard code path for every key type. Any environment with a logging proxy, HTTP access logs, or shared shell history in front of the node will passively capture the secret without any additional attacker action, making exploitation likelihood high once any log/proxy access is obtained.

### Recommendation
Move `oldpassword`/`newpassword` out of the URL query string and into the request body (or an HTTP header) for all key `Import`/`Export` endpoints and their corresponding CLI callers (`core/web/keys_controller.go`, `core/web/ocr_keys_controller.go`, `core/web/ocr2_keys_controller.go`, `core/web/p2p_keys_controller.go`, `core/web/vrf_keys_controller.go`, `core/web/csa_keys_controller.go`, and all `core/cmd/*_keys_commands.go` shell counterparts). Ensure the Gin access logger (`loggerFunc`) redacts query strings for these routes, and audit any reverse-proxy configuration to confirm query strings are not persisted in access logs.

### Proof of Concept
1. Run `chainlink keys eth export <address> --new-password=pwfile.txt --output=key.json`.
2. Observe the CLI issue `POST /v2/keys/evm/export/<address>?newpassword=<PLAINTEXT_PASSWORD>` as built in [7](#0-6) .
3. On the server, `core/web/eth_keys_controller.go`/`vrf_keys_controller.go` reads `c.Query("newpassword")` and the Gin access-log middleware records the full request line including the query string, exposing the plaintext password in the node's log files/any intermediary proxy logs.
