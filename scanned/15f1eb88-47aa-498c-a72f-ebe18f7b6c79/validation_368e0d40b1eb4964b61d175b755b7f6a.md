### Title
Cross-workflow HTTP response cache poisoning/leakage due to WorkflowID being excluded from the cache key - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
The analog to the Insurance Fund bug ("a shared, mutable resource used to compute a value/response for one user can be altered by another unprivileged user's action, causing cross-user value/response confusion") is present in the Gateway's HTTP Action `responseCache`. The cache is documented as being workflow-scoped ("Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage") but the actual cache key computed by `req.Hash()` is explicitly confirmed by tests to be **independent of `WorkflowID`** — two different workflows issuing the same HTTP action request receive/share the same cache entry.

### Finding Description
`responseCache` stores and retrieves cached HTTP responses keyed solely by `req.Hash()`: [1](#0-0) [2](#0-1) 

The struct comment states the key is derived from "method, URL, headers, body, workflowOwner" — notably `workflowID` is not part of the key: [3](#0-2) 

This is confirmed directly by the test suite for `req.Hash()`, which explicitly asserts that differing `WorkflowID` values produce the **same** hash, while differing `WorkflowOwner` values produce different hashes: [4](#0-3) [5](#0-4) 

Yet the module's own documentation explicitly claims per-workflow isolation for cache entries: [6](#0-5) 

This means the actual guarantee is only per-owner (any two workflows belonging to the same owner share cache entries), not per-workflow as documented. The `Fetch`/`Set` methods operate purely on this hash-derived key, so a response cached on behalf of one workflow (e.g., containing that workflow's request-specific but owner-shared HTTP call result) can be served to a different workflow under the same owner, and a malicious/compromised workflow under that owner can pre-populate (poison) the cache to control the response another sibling workflow later receives on its next `MethodHTTPAction` call — analogous to how a bad-debt settlement in the Insurance Fund could be triggered by one actor to alter the value another actor's withdrawal computation returns from a shared underlying resource.

### Impact Explanation
Within a single workflow owner's account (an unprivileged actor relative to other owners, but who may run multiple workflows with differing trust boundaries/logic), one workflow can observe or manipulate the cached HTTP action response consumed by a sibling workflow of the same owner, since the cache key does not disambiguate by `WorkflowID`. This breaks the "Workflow Isolation" guarantee documented for the gateway's response cache and can lead to cross-workflow response confusion (stale/incorrect/attacker-influenced data being fed into a different workflow's execution) purely from normal, unprivileged HTTP-action traffic — no privileged access or node compromise required.

### Likelihood Explanation
Any owner running more than one HTTP-action-capable workflow that issue outbound HTTP requests to the same method/URL/headers/body combination will hit this shared cache key by default. Since `CacheSettings.Store=true` is the trigger for caching (set by the workflow author, not the gateway), and `MaxAgeMs`/TTL windows exist for up to 10 minutes by default, cross-workflow reuse is straightforward to trigger deliberately or observe accidentally.

### Recommendation
Include `WorkflowID` in the cache key computation (`req.Hash()`) in addition to `WorkflowOwner`, method, URL, headers, and body, so that cache entries are truly scoped per workflow as documented, or explicitly document/enforce that isolation is only per-owner and update all callers/consumers accordingly if per-owner sharing is the intended behavior.

### Proof of Concept
1. Owner `O` operates two workflows `W1` and `W2`, both configured with an HTTP Action to `GET https://api.example.com/data` with `CacheSettings.Store = true`.
2. `W1` executes first; `gatewayHandler` fetches the response and calls `responseCache.Set`/`Fetch`, storing the result keyed by `req.Hash()` (method+URL+headers+body+`WorkflowOwner`, excluding `WorkflowID`), as shown in `response_cache.go` lines 46-120.
3. `W2` (different `WorkflowID`, same `WorkflowOwner`) issues the identical outbound HTTP request within the TTL window; because `req.Hash()` does not vary by `WorkflowID` (proven by `response_cache_test.go` lines 139-149), `W2` receives `W1`'s cached response without a fresh outbound fetch — even though the README documents per-workflow cache isolation.
4. If `W1` is compromised/malicious or intentionally crafted to poison the shared endpoint's response (e.g., by controlling the target URL/mocked response upstream), it can influence the data consumed by `W2`, demonstrating cross-workflow response confusion.

```go
// isExpiredOrNotCached returns true if the cached response is expired or not cached.
// IMPORTANT: this method does not lock the cache map. MUST be called with cacheMu write-locked.
func (rc *responseCache) isExpiredOrNotCached(req gateway.OutboundHTTPRequest) bool {
	cachedResp, exists := rc.cache[req.Hash()]
	if !exists || time.Now().After(cachedResp.storedAt.Add(rc.ttl)) {
		return true
	}
	return false
}
```

```go
// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}
```

```markdown
### 3.2 Caching Behavior

- **Cacheable Responses**: 2xx (success) and 4xx (client error) status codes.
- **Cache TTL**: Configurable, default 10 minutes
- **Cache Key**: Generated from workflow ID and request hash
- **Cache Invalidation**: Time-based expiration with periodic cleanup
- **Cache Strategy**: All cacheable responses are cached; Non-zero `CacheSettings.MaxAgeMs` determines whether to return a cached value or make a fresh request
- **Workflow Isolation**: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage
```
