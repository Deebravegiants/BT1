Confirmed: `/sessions` login endpoint (`core/web/sessions_controller.go` `Create`) is unauthenticated and passes attacker-controlled `sr.Email` directly into `AuthenticationProvider().CreateSession`, which for LDAP-mode nodes is `ldapAuthenticator.CreateSession` in `core/sessions/ldapauth/ldap.go`.

### Title
LDAP DN injection via filter-escaping used in bind DN construction - (File: core/sessions/ldapauth/ldap.go)

### Summary
`ldapAuthenticator.CreateSession` and `TestPassword` build an LDAP **bind DN** by concatenating an attacker-supplied, unauthenticated `email` value that has only been passed through `ldap.EscapeFilter`, which is designed for LDAP *search filter* escaping, not *Distinguished Name* escaping.

### Finding Description
In `core/sessions/ldapauth/ldap.go`, `CreateSession` does: [1](#0-0) 
and `TestPassword` does the same pattern: [2](#0-1) 

`escapedEmail := ldap.EscapeFilter(...)` only escapes filter metacharacters (`*`, `(`, `)`, `\`, NUL) as documented by the go-ldap library. It does **not** escape DN-reserved characters such as `,`, `+`, `"`, `<`, `>`, `;`, `=`, or leading/trailing spaces. The resulting `searchBaseDN` string, however, is used as a **Bind DN** (`conn.Bind(searchBaseDN, sr.Password)`), a DN context — not a filter context. This mirrors the referenced CVE-2026-33609 pattern: escaping intended for one LDAP syntax context (filters) is incompletely applied and reused in a different context (DN), permitting structural injection of extra RDN components (e.g. `ou=`, `dc=`) via a value like `x,ou=OtherGroup,dc=corp,dc=com` in the `email` field of the login request, letting the constructed DN target a different or internal directory subtree than intended.

This request path is fully unauthenticated: `SessionsController.Create` reads `sr.Email` straight from the request body and forwards it to `CreateSession` before any authentication has succeeded. [3](#0-2) 

### Impact Explanation
An unauthenticated client can manipulate the DN used for the LDAP bind/search, causing the node to query or bind against unintended DNs/subtrees within the configured LDAP directory (matches the CVE's "queries of internal domain subtrees" impact). Because a valid bind still requires a matching password for the resulting DN, this is not an outright authentication bypass by itself, but it does allow probing/targeting of arbitrary DNs under the LDAP tree and violates the intended containment of `UsersDN`/`BaseDN` scoping — a legitimate confidentiality/boundary issue for the LDAP-authenticated node API, consistent with CVSS 5.3/Medium.

### Likelihood Explanation
Requires the node to be configured with `WebServer.AuthenticationMethod = 'ldap'`. Any unauthenticated caller can reach `POST /sessions` and control the `email` field, making the trigger trivial once LDAP auth is enabled.

### Recommendation
Use proper DN escaping (e.g., a DN-escaping routine, or validate `email` against a strict allow-list of characters such as `^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+$` before use) when constructing `searchBaseDN` for `conn.Bind` in `CreateSession` and `TestPassword`. `ldap.EscapeFilter` should be reserved only for values placed inside filter expressions (as already done correctly in `FindUser` and `validateUsersActive`).

### Proof of Concept
1. Configure a chainlink node with `WebServer.AuthenticationMethod = 'ldap'`.
2. Send `POST /sessions` with body `{"email": "victim,ou=Admins,dc=corp,dc=com", "password": "anything"}`.
3. `CreateSession` builds `searchBaseDN = "uid=victim,ou=Admins,dc=corp,dc=com,ou=users,dc=custom,dc=example,dc=com"` (or similar depending on config), altering the target DN structure away from the intended `UsersDN` scope, and attempts a bind against it — demonstrating the injected DN reaches the upstream LDAP server outside the originally scoped subtree. 	session := sessions.Default(c)
	var sr clsessions.SessionRequest
	if err := c.ShouldBindJSON(&sr); err != nil {
		jsonAPIError(c, http.StatusBadRequest, fmt.Errorf("error binding json %w", err))
		return
	}

	// Does this user have 2FA enabled?
	userWebAuthnTokens, err := sc.App.AuthenticationProvider().GetUserWebAuthn(ctx, sr.Email)
	if err != nil {
		sc.App.GetLogger().Errorf("Error loading user WebAuthn data: %s", err)
		jsonAPIError(c, http.StatusInternalServerError, errors.New("internal Server Error"))
		return
	}

	// If the user has registered MFA tokens, then populate our session store and context
	// required for successful WebAuthn authentication
	if len(userWebAuthnTokens) > 0 {
		sr.SessionStore = sc.sessions
		sr.WebAuthnConfig = sc.App.GetWebAuthnConfiguration()
	}

	sid, err := sc.App.AuthenticationProvider().CreateSession(ctx, sr)
	if err != nil {
		jsonAPIError(c, http.StatusUnauthorized, err)
		return
	}
