Confirmed: the `isAllowedOrigin` wildcard check in `core/services/gateway/network/httpserver.go` performs the same class of bug as the reported MaxKey CVE — a hostname suffix comparison without dot-boundary anchoring.

### Title
CORS wildcard origin allowlist bypass via unanchored hostname suffix match - (File: `core/services/gateway/network/httpserver.go`)

### Summary
The gateway's user-facing HTTP server (`httpServer.handleRequest`) reflects the request's `Origin` header into `Access-Control-Allow-Origin` whenever `isAllowedOrigin` returns true [1](#0-0) . For wildcard-configured entries (`*.example.com`), the match is performed with `strings.HasSuffix(originHost, allowedHost)` after stripping the `*.` prefix, with no check that the character preceding the suffix in `originHost` is a `.` [2](#0-1) .

### Finding Description
`isAllowedOrigin` splits both the incoming `Origin` header and each configured `CORSAllowedOrigins` entry into scheme/host/port [3](#0-2) . For a wildcard allowlist entry such as `https://*.remix.com`, the code strips `*.` to get `remix.com` and then does a bare suffix comparison:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if strings.HasSuffix(originHost, allowedHost) {
        return true
    }
}
```
This is exactly the "hostname suffix matches a registered value without proper dot-boundary anchoring" pattern described in the MaxKey `DefaultRedirectResolver.hostMatches()` advisory: any attacker-registered domain that merely *ends with* the allowed suffix — e.g. `evilremix.com` or `notremix.com` — satisfies `strings.HasSuffix("evilremix.com", "remix.com")` even though it is not a subdomain of `remix.com`. There is no dot-boundary check (`originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost)`).

### Impact Explanation
When `CORSEnabled = true` and a wildcard entry is configured (a supported, documented pattern exercised in `httpserver_test.go`, e.g. `https://*.ethereum.org` [4](#0-3) ), an unprivileged remote attacker who registers a domain ending in the same suffix (e.g. `evilethereum.org`) can host a page there. A victim visiting that page will have their browser send a cross-origin request to the gateway's user-facing HTTP server; `isAllowedOrigin` incorrectly returns `true`, causing the server to reflect `Access-Control-Allow-Origin: https://evilethereum.org` [1](#0-0) . This lets the attacker-controlled origin read cross-origin JSON-RPC responses from the gateway (which is the internet-facing entry point handling JWT-bearer requests forwarded to `ProcessRequest` [5](#0-4) ), i.e. an allowlist bypass leading to cross-origin response disclosure/confusion for the user server.

### Likelihood Explanation
Exploitability requires only that the gateway operator configure `CORSEnabled = true` with at least one wildcard entry in `CORSAllowedOrigins` — a normal, supported configuration shape (tested explicitly in `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards` [6](#0-5) ). No privileged access, node/peer trust, or mocked-only path is needed; any external attacker able to register a suffix-colliding domain and lure a victim browser can trigger it.

### Recommendation
Fix the wildcard comparison to require a dot boundary, e.g.:
```go
if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
    return true
}
```
in `isAllowedOrigin` at [2](#0-1) .

### Proof of Concept
1. Configure the gateway user server with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.remix.com"]`.
2. Register (or simulate via `/etc/hosts`) the attacker domain `https://evilremix.com`.
3. Send a request to the gateway user endpoint with header `Origin: https://evilremix.com`.
4. Observe the response includes `Access-Control-Allow-Origin: https://evilremix.com`, because `strings.HasSuffix("evilremix.com", "remix.com")` is `true`, matching the vulnerable code path at [7](#0-6) .
