### Title
Single para can monopolize entire on-demand order queue via repeated `place_order_with_credits`/`place_order_allow_death` calls, denying `QueueFull` to all other paras - ([File: polkadot/runtime/parachains/src/on_demand/mod.rs])

### Summary
`Pallet::do_place_order` enforces a global queue-length check (`order_status.queue.len() < on_demand_queue_max_size`) before pushing a new `EnqueuedOrder`, but it never checks whether the `para_id` already has an outstanding, un-assigned order in the queue. Any unprivileged signed account with enough balance or `Credits::<T>` can repeatedly call `place_order_with_credits`/`place_order_allow_death` for one target `para_id`, filling the entire `OrderQueue` with entries for that single para and causing every other para's order to fail with `Error::QueueFull`.

### Finding Description
`OrderQueue::try_push` (`polkadot/runtime/parachains/src/on_demand/mod.rs:140-144`) unconditionally pushes an `EnqueuedOrder { para_id, ordered_at }` as long as the `BoundedVec` has spare capacity - there is no dedup or per-`para_id` admission limit. `do_place_order` (`polkadot/runtime/parachains/src/on_demand/mod.rs:471-558`) gates admission only by:
- the *global* queue length vs `on_demand_queue_max_size` (line 492-496), and
- the spot price vs the caller-supplied `max_amount` (line 490).

Neither check inspects existing entries for the same `para_id`. By contrast, the dequeue path `OrderQueue::pop_assignment_for_cores` (`polkadot/runtime/parachains/src/on_demand/mod.rs:108-131`) *does* dedup per round via a `BTreeSet`, matching the module doc's claim that "only one order per ParaId can be assigned in each scheduling round" (lines 23-27). That guarantee applies only to assignment, not to queue admission - so the admission and assignment invariants are inconsistent, and nothing stops one para's backlog from crowding out the shared queue capacity used by all paras.

Exploit flow: an attacker with a signed account calls `place_order_with_credits(max_amount, attacker_para_id)` (or `place_order_allow_death`) in a loop. Each call succeeds as long as `spot_price <= max_amount` and `queue.len() < on_demand_queue_max_size`, pushing another entry for the same `para_id`. Once the queue reaches `on_demand_queue_max_size`, every other account's `place_order_*` call for a different `para_id` fails with `Error::<T>::QueueFull` (line 495), even though the attacker's para can only ever be assigned once per scheduling round.

### Impact Explanation
While the queue remains saturated with the attacker's redundant orders, no other on-demand parachain can enqueue a new order - `place_order_*` unconditionally reverts with `QueueFull` regardless of the caller's willingness to pay. This is a resource-seizure/griefing DoS against every other on-demand parathread's access to blockspace, matching the scoped impact.

### Likelihood Explanation
The attack requires only a signed account and enough `Currency`/`Credits` to pay `on_demand_queue_max_size` spot-price charges (each order is a normal extrinsic call, no special origin needed). The queue's spot-price mechanism (`update_spot_traffic`/`calculate_spot_traffic`, lines 560-665) raises price with utilization and is the codebase's documented mitigation for exactly this class of spam (see `prdoc/1.10.0/pr_3190.prdoc`: "the spot price for on-demand is now checked prior to every order, ensuring that economic backpressure will be applied"). This bounds but does not eliminate the attack: for a moderately sized `on_demand_queue_max_size`, or if traffic decays between attacker transactions (e.g., spread across blocks, since traffic decreases when the queue is below target on idle blocks per `spot_traffic_decreases_over_time`/`spot_traffic_decreases_between_idle_blocks` tests), a well-funded attacker can sustain queue saturation by re-filling drained slots (one attacker order is popped per round via `pop_assignment_for_cores`) faster than legitimate paras can react, at a real but bounded economic cost (excess orders beyond one-per-round are wasted spend by design).

### Recommendation
Add a per-`para_id` admission control to `OrderQueue`/`do_place_order`, e.g., reject or defer new orders for a `para_id` that already has an outstanding un-assigned entry in the queue, or bound the number of concurrently queued orders per `para_id` (independent of the global `on_demand_queue_max_size`), so that the admission invariant matches the "one order per ParaId assigned per round" assignment invariant already enforced in `pop_assignment_for_cores`.

### Proof of Concept
Integration test (in `polkadot/runtime/parachains/src/on_demand/tests.rs` style, using the existing mock runtime):
1. Configure `on_demand_queue_max_size = N` (small, e.g. 20) and fund attacker account with enough balance/credits to cover N spot-price payments (mint credits via `credit_account`).
2. In a loop, call `OnDemand::place_order_with_credits(attacker_origin, max_amount, attacker_para_id)` until it returns `Err(Error::QueueFull)`; assert the loop succeeds `N` times before failing.
3. Assert `OnDemand::get_order_status().queue.len() == N` and every entry's `para_id == attacker_para_id`.
4. As a distinct honest account, call `OnDemand::place_order_with_credits(honest_origin, max_amount, other_para_id)` and assert it returns `Err(Error::<T>::QueueFull)`.
5. Advance one scheduling round (`OnDemand::pop_assignment_for_cores`) and assert only 1 entry for `attacker_para_id` is popped, `N-1` entries remain, confirming other paras still cannot place any order while attacker's excess orders sit unassigned. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

	pub fn pop_assignment_for_cores<T: Config>(
		&mut self,
		now: N,
		mut num_cores: u32,
	) -> impl Iterator<Item = ParaId>
	where
		N: Saturating + Ord + One + Copy,
	{
		let mut popped = BTreeSet::new();
		let mut remaining_orders = Vec::with_capacity(self.queue.len());
		for order in mem::take(&mut self.queue) {
			// Order is ready 2 blocks later (asynchronous backing):
			let ready_at = order.ordered_at.saturating_plus_one().saturating_plus_one();
			let is_ready = ready_at <= now;

			if num_cores > 0 && is_ready && popped.insert(order.para_id) {
				num_cores -= 1;
			} else {
				remaining_orders.push(order);
			}
		}
		self.queue = BoundedVec::truncate_from(remaining_orders);
		popped.into_iter()
	}
