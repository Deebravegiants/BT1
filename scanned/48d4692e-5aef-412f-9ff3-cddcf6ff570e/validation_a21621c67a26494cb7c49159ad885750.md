## Analog Assessment: On-Demand Queue Rewrite in `polkadot-runtime-parachains::on_demand`

### Title
Unbounded per-block queue rewrite when popping on-demand assignments — `polkadot/runtime/parachains/src/on_demand/mod.rs`

### Summary
The external report describes `_removeFromQueue` rewriting the entire remaining array to storage on every removal, an O(n) operation for what should be O(k). The closest structural analog in this codebase is `OrderQueue::pop_assignment_for_cores` in the on-demand (parathread) assignment pallet, which similarly reconstructs and rewrites the **entire** queue on every invocation instead of only removing the popped entries.

### Finding Description
`OrderQueue::pop_assignment_for_cores` drains the whole `BoundedVec` via `mem::take`, iterates every element, and rebuilds a new `remaining_orders` vector that is written back wholesale: [1](#0-0) 

This is called every time cores need on-demand assignments, once per relevant scheduling step, via `Pallet::<T>::pop_assignment_for_cores`: [2](#0-1) 

which is itself invoked from `advance_assignments_single_impl` in the coretime scheduler on essentially every block (both for the "pop" and "peek" access modes): [3](#0-2) [4](#0-3) 

The code even documents the inefficiency explicitly: [5](#0-4) 

The queue can be grown up to a configurable maximum (`on_demand_queue_max_size`, bounded by `ON_DEMAND_MAX_QUEUE_MAX_SIZE`) simply by any signed account calling the permissionless `place_order_allow_death` / `place_order_keep_alive` / `place_order_with_credits` extrinsics: [6](#0-5) 

### Impact Explanation
Unlike the Solidity case, this is **not** an unbounded gas-griefing vector: the queue length is capped by `on_demand_queue_max_size` (default derived from `ON_DEMAND_DEFAULT_QUEUE_MAX_SIZE`, hard-capped at `ON_DEMAND_MAX_QUEUE_MAX_SIZE`), and the `place_order_*` extrinsics are metered with weight/fees per the pallet's `WeightInfo`. The `pop_assignment_for_cores` rewrite cost is O(queue length), so a full queue makes every subsequent scheduling step do bounded, but non-trivial, work (up to thousands of `EnqueuedOrder` entries reconstructed every block). This is a performance/efficiency concern rather than an unbounded-cost or fund-draining vulnerability, since:
- the growth is capped by a governance-configured constant,
- placing orders costs real balance/credits (spot price), which is an economic disincentive against spamming the queue, and
- the operation runs inside pallet-internal scheduling logic invoked from block processing, not as a directly user-priced dispatchable whose cost the attacker controls arbitrarily.

### Likelihood Explanation
Low-to-moderate. An attacker would need to pay the on-demand spot price repeatedly to keep the queue near its maximum size to sustain the worst-case per-block cost, and the resulting overhead is bounded by a known constant rather than growing without limit. I was not able to fully verify (within the tool budget) whether the benchmarked weight for the block-processing path that invokes `advance_assignments`/`pop_assignment_for_cores` (e.g., `paras_inherent::enter`) scales with the on-demand queue length; if it does not, sustained queue-filling could cause the mandatory inherent's actual execution time to exceed its benchmarked weight, which would be a genuine (if narrow) weight-accounting concern. This last point remains unconfirmed.

### Recommendation
If verified, the recommendation mirrors the original report's fix: replace the "rebuild whole vector on pop" pattern with a true FIFO structure indexed by monotonically increasing `first`/`last` cursors (similar to the pattern already used elsewhere in this codebase, e.g. `InboundDownwardQueue`'s `first_full`/`first_free` metadata with per-page `StorageMap` entries, see `polkadot/runtime/parachains/src/dmp/inbound_downward_queue.rs`), so that popping `k` entries only touches `k` storage/vector positions instead of the whole remaining queue. Additionally, confirm that the weight charged for the block-processing path calling `pop_assignment_for_cores` (via `paras_inherent::enter`) scales with, or is bounded independently of, the current on-demand queue length.

### Proof of Concept
Not applicable as a standalone exploit — this requires runtime-level benchmarking (comparing measured `paras_inherent::enter` execution time at low vs. near-maximum on-demand queue occupancy) to confirm whether real-world weight exceeds benchmarked weight. I could not perform or verify this within the current investigation.

impl<N> OrderQueue<N> {
	/// Pop `num_cores` from the queue, assuming `now` as the current block number.
	pub fn pop_assignment_for_cores<T: Config>(
		&mut self,
		now: N,
		mut num_cores: u32,
	) -> impl Iterator<Item = ParaId>
	where
		N: Saturating + Ord + One + Copy,
	{
		let mut popped = BTreeSet::new();
		let mut remaining_orders = Vec::with_capacity(self.queue.len());
		for order in mem::take(&mut self.queue) {
			// Order is ready 2 blocks later (asynchronous backing):
			let ready_at = order.ordered_at.saturating_plus_one().saturating_plus_one();
			let is_ready = ready_at <= now;

			if num_cores > 0 && is_ready && popped.insert(order.para_id) {
				num_cores -= 1;
			} else {
				remaining_orders.push(order);
			}
		}
		self.queue = BoundedVec::truncate_from(remaining_orders);
		popped.into_iter()
	}

/// Pop assignments for `now`.
fn advance_assignments_single_impl<T: Config>(
	now: BlockNumberFor<T>,
	core_states: &mut BTreeMap<CoreIndex, CoreDescriptor<BlockNumberFor<T>>>,
	mut mode: AccessMode<T>,
) -> AdvancedAssignments {
	let mut bulk_assignments = Vec::with_capacity(num_coretime_cores::<T>() as _);
	let mut pool_cores = Vec::with_capacity(num_coretime_cores::<T>() as _);
	for (core_idx, core_state) in core_states.iter_mut() {
		ensure_workload::<T>(now, *core_idx, core_state, &mode);

		let Some(work_state) = core_state.current_work.as_mut() else { continue };

		// Wrap around:
		work_state.pos = work_state.pos % work_state.assignments.len() as u16;
		let (a_type, a_state) = &mut work_state
			.assignments
			.get_mut(work_state.pos as usize)
			.expect("We limited pos to the size of the vec one line above. qed");

		// advance for next pop:
		a_state.remaining = a_state.remaining.saturating_sub(work_state.step);
		if a_state.remaining < work_state.step {
			// Assignment exhausted, need to move to the next and credit remaining for
			// next round.
			work_state.pos += 1;
			// Reset to ratio + still remaining "credits":
			a_state.remaining = a_state.remaining.saturating_add(a_state.ratio);
		}
		match *a_type {
			CoreAssignment::Pool => pool_cores.push(*core_idx),
			CoreAssignment::Task(para_id) => bulk_assignments.push((*core_idx, para_id.into())),
			CoreAssignment::Idle => {},
		}
	}

	let pool_assignments = mode.pop_assignment_for_ondemand_cores(now, pool_cores.len() as _);
	let pool_assignments = pool_cores.into_iter().zip(pool_assignments).collect();

	AdvancedAssignments { bulk_assignments, pool_assignments }
