### Title
Storage-deposit coalescing in `execute_postponed_deposits` merges charges by contract address only, letting a same-tx terminate+redeploy sequence erase a legitimate deposit charge and create an unbacked refund - (File: substrate/frame/revive/src/metering/storage.rs)

### Summary
`RawMeter::execute_postponed_deposits` coalesces the transaction-wide `charges: Vec<Charge<T>>` purely by `contract: T::AccountId` [1](#0-0) . If the same address is terminated and then redeployed within the same transaction, the second, legitimate `Alive` charge for the *new* contract instance is merged into the earlier `Terminated` marker and silently dropped from both the actual `E::charge` transfer and the running `total_deposit` accounting [2](#0-1) . This produces a `ContractInfo` whose `storage_byte_deposit`/`storage_item_deposit` fields claim a deposit that was never actually reserved from `origin`, which becomes real, unbacked balance in a later legitimate termination refund.

### Finding Description
`execute_postponed_deposits` sorts `self.charges` by contract address (a stable sort, so relative order per-address is preserved) and then coalesces consecutive entries for the same address in a single pass: [3](#0-2) 

The merge rule for `(Alive, Terminated)` or `(Terminated, Alive)` unconditionally treats the encounter as "undo all deposits made by a terminated contract": it subtracts the `Alive` amount from `self.total_deposit` and forces the coalesced entry to stay `Terminated` — regardless of whether the `Alive` entry temporally precedes or follows the `Terminated` marker [4](#0-3) .

The `Charge` struct only carries `contract: T::AccountId` and a `ContractState`, with no generation/instance identifier [5](#0-4) . Consequently the coalescing logic cannot distinguish "the terminated instance's own charge" from "a brand-new instance's charge at the same address, deployed later in the same call stack."

Exploit flow:
1. Attacker deploys contract at address `X` (e.g. via CREATE2 with attacker-chosen salt/init-code, giving deterministic, reusable address semantics typical of EVM-compatible pallets).
2. `X` performs a storage write, which upon frame return is `absorb`ed into the root meter, updating `X`'s `ContractInfo` fields and pushing `Charge{X, Alive{C1}}` [6](#0-5) .
3. `X` self-terminates in the same transaction; `RawMeter::terminate` adds the real termination refund to `total_deposit` and pushes `Charge{X, Terminated}` [7](#0-6) .
4. Still within the same transaction, the attacker redeploys a new contract instance at the same address `X` (CREATE2 with identical salt/init-code, now legal because the account was vacated by termination) and has it perform a fresh storage write, producing `Charge{X, Alive{C2}}` for the *new* instance, whose `ContractInfo` fields were already updated to reflect `C2` via `Contribution::update_contract(info)` at `absorb` time.
5. At the end of the transaction, `execute_postponed_deposits` sorts/coalesces `[Alive{C1}, Terminated, Alive{C2}]` (order preserved by stable sort) into a single `Terminated` entry, subtracting **both** `C1` and `C2` from `total_deposit` and never calling `E::charge` for either amount.

Result: the new (still alive, not terminated) contract's `ContractInfo.storage_byte_deposit`/`storage_item_deposit` fields say a deposit of `C2` is held, but no hold/reserve was ever placed on `origin`'s balance for `C2` — the charge was erased by the coalescing bug. If that new contract is legitimately terminated afterwards (a different transaction), the real termination refund path pays out `C2` (plus whatever other deposit fields the contract has) as if it were backed, but it never was. This is a genuine mismatch between recorded deposit and actually-held balance, i.e. the invariant "total deposit charged/refunded must equal the net real storage change" is violated, and it is reachable purely via ordinary contract calls (instantiate/call/terminate), with no privileged access required.

### Impact Explanation
The bug lets an unprivileged attacker cause the storage-deposit ledger (`ContractInfo` fields) to diverge from actually-held funds: a contract can accrue a "backed" deposit balance in its `ContractInfo` without the corresponding amount ever being reserved from `origin`. A subsequent, ordinary termination of that contract pays out this un-backed amount as a real balance refund, i.e., value is created out of thin air and paid to whichever beneficiary receives the termination refund — a concrete instance of the scoped "fund theft via storage deposit refund inflation" impact.

### Likelihood Explanation
Feasibility hinges on being able to deploy a new contract at the exact same address as a just-terminated contract within a single transaction/call stack. In EVM-compatible environments (which `pallet-revive` targets), this is a well-known and intentionally supported pattern via `CREATE2` with attacker-chosen salt and init code ("metamorphic contract" pattern): terminate at address `X`, then re-`CREATE2` with the same salt/init-code hash to redeploy at the same `X`, all inside one transaction/call stack. Given that, the sequence (charge, terminate, redeploy, charge) is fully attacker-controlled and repeatable in every transaction, with no signature/origin/proxy/fee check intervening (the entire flaw is downstream, purely in the deposit-accounting merge). I was not able to fully trace the exact CREATE2/address-derivation code path within the available tool budget to conclusively confirm same-block redeploy is unconditionally permitted (e.g., whether nonce/account-existence checks in `exec.rs` add additional friction), so this should be verified with a concrete integration test before treating it as fully proven.

### Recommendation
Track charges by a `(contract, generation)` key instead of `contract` alone (e.g. bump a generation counter on every `instantiate`, and store it in `Charge`), so that a `Terminated` marker from an earlier instance can never coalesce with an `Alive` charge belonging to a later instance redeployed at the same address in the same transaction. Alternatively, flush/finalize `self.charges` for a given address at the moment `terminate` is recorded, so no further charges for that address can be appended to the same coalescing bucket within the transaction.

### Proof of Concept
Rust integration test in `substrate/frame/revive/src/exec/tests.rs` (or a `metering/storage/tests.rs` unit test at the `RawMeter` level, escalated to a full exec-level integration test for realism):
1. Deploy contract `A` via CREATE2 with salt `S` and init code `I`, whose constructor writes storage causing charge `C1`.
2. From `A`, call `terminate`/`seal_terminate` to self-destruct within the same transaction.
3. Still within the same transaction (e.g. from the caller/origin's follow-up call in the same extrinsic execution), redeploy a contract via CREATE2 with the same salt `S` and init code `I`, landing at the same address, whose constructor writes storage causing charge `C2`.
4. Call `execute_postponed_deposits` (end of the top-level call) and assert:
   - The final `ContractInfo` for the redeployed contract has `storage_byte_deposit + storage_item_deposit == C2` (deposit believed to be backed).
   - The actual `Held`/reserved balance under `HoldReason::StorageDepositReserve` for `origin` attributable to this contract is `0` (no hold was placed for `C2`), i.e. `origin`'s balance decreased by less than the sum of the diffs actually applied to storage.
   - Terminate the redeployed contract in a later transaction and assert the refund paid out exceeds what was ever actually reserved from `origin`, demonstrating a net balance surplus, i.e. `origin`/beneficiary balance delta != net real storage change (`Diff`) of the transaction.
