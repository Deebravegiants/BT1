### Title
Repeated re-application of un-consumed storage `Diff` via `apply_pending_changes_to_contract` allows a contract to over-refund its own storage deposit across multiple nested calls - (File: substrate/frame/revive/src/metering/storage.rs)

### Finding Description
`Diff::update_contract` (`substrate/frame/revive/src/metering/storage.rs:121-173`) both **computes** a charge/refund for the current in-memory `Diff` *and* **mutates** `info.storage_bytes` / `info.storage_byte_deposit` (and the items equivalents) as a side effect [1](#0-0) . Any code path that calls `update_contract` therefore permanently commits the diff into `ContractInfo`, even if the `Diff` itself is not cleared afterwards.

`RawMeter::apply_pending_changes_to_contract` is documented to intentionally *not* reset `own_contribution` after applying it, explicitly so the meter can "continue tracking changes after the nested call returns": [2](#0-1) 

Contrast this with `bank_pending_changes`, which does the equivalent commit but explicitly resets `own_contribution` back to `Contribution::Alive(Default::default())` right after applying it to prevent re-application: [3](#0-2) 

Because `apply_pending_changes_to_contract` never clears `own_contribution`, if it is invoked more than once for the same accumulated `Diff` (e.g. once before each of several nested sub-calls made from the same call frame, per its own doc comment: "This is used before creating a nested frame … "), the *same* `bytes_removed`/`items_removed` values get subtracted from the already-shrunk `info.storage_bytes`/`info.storage_items`, and a *new* refund ratio (`FixedU128::checked_from_rational(bytes_removed, info.storage_bytes)`, line 139) gets computed and applied against the already-shrunk `info.storage_byte_deposit` each time.

Mathematically, if a contract has `S0` bytes recorded with deposit `Dep0 = per_byte * S0`, and it actually removes `R` bytes once, the correct one-time refund is `per_byte * R`. But because `update_contract` is idempotent-looking yet stateful (it both reads and writes `info`), calling it `N` times with the *unchanged* `Diff{bytes_removed: R}` produces a *geometric* refund: each call computes `ratio_i = R / S_{i-1}` and refunds `ratio_i * Dep_{i-1}`, then shrinks `S` and `Dep` again by the same `R`. Since `S_{i-1}` shrinks every call while the `Diff`'s `R` stays constant, `ratio_i` grows toward `1` on subsequent calls and each call keeps re-refunding roughly `per_byte * R` again — repeating the refund for storage that was only physically removed once — until `S` saturates to `0` (u32 saturating_sub), at which point the deposit for that storage has been drained by a multiple of the true entitled refund rather than exactly once.

### Impact Explanation
This lets an attacker-controlled contract obtain a storage-deposit refund larger than what was actually charged for the bytes/items it removed, by simply making several nested sub-calls (e.g. calling itself or a no-op callee in a loop) after performing a storage removal within the same call frame, so that `apply_pending_changes_to_contract` is invoked multiple times against the same un-cleared `Diff`. The excess is paid out of the `HoldReason::StorageDepositReserve` hold via `ReservingExt::charge`/`Pallet::refund_deposit`, effectively over-crediting the caller/contract account at the expense of correctly-accounted balances — a direct violation of the "refund must never exceed the amount charged" invariant.

### Likelihood Explanation
The precondition is a normal, permissionless contract execution path: a contract makes ordinary storage writes/removals and then issues multiple nested calls from the same execution frame — nothing here requires privileged origins, and both storage mutation and nested calls are standard contract capabilities exposed through `pallet_revive`'s hostcalls. The only uncertainty (which I could not fully verify given tool-call limits) is the exact call site in `substrate/frame/revive/src/exec.rs` that invokes `apply_pending_changes_to_contract` — specifically whether it is called once per call-stack-frame lifetime or once per nested sub-call issued from that frame. The design/doc comment on `apply_pending_changes_to_contract` strongly implies the latter ("used before creating a nested frame"), and the fact that `bank_pending_changes` needed an explicit reset (while this function deliberately omits one) indicates the authors were aware repeated application is possible and chose not to guard against it here.

### Recommendation
- Either make `apply_pending_changes_to_contract` idempotent with respect to `info` (e.g., only apply the *delta* since the last application, or track and subtract an "already-applied" baseline), or
- Reset/checkpoint `own_contribution` similarly to `bank_pending_changes` after each application while still allowing later increments to be tracked separately from what has already been committed to `info`, or
- Store a snapshot of `info`'s pre-frame state and always recompute the diff-to-apply as `current_accumulated_diff - previously_applied_diff` rather than re-feeding the full accumulated `Diff` into `update_contract` every time.

### Proof of Concept
Rust unit test (in `substrate/frame/revive/src/metering/storage/tests.rs` style) plan:
1. Construct a `ContractInfo` with `storage_bytes = S0`, `storage_byte_deposit = per_byte * S0`.
2. Build a nested `RawMeter`, call `.charge(&Diff { bytes_removed: R, .. })` where `R < S0`.
3. Call `apply_pending_changes_to_contract(&mut info)` twice (or N times) without any reset in between, mirroring two nested sub-calls issued from the same frame.
4. Assert the sum of refunds computed by each `update_contract` invocation exceeds `per_byte * R` (the true one-time entitlement), and that `info.storage_byte_deposit` has been reduced by more than `per_byte * R` in total.
5. Extend to a fuzz/invariant test that randomizes `S0`, `R`, and number of `apply_pending_changes_to_contract` calls, asserting `total_refund <= per_byte * R` (expected to fail, proving the bug) versus the actual (larger) accumulated refund.

	/// Apply pending storage changes to a ContractInfo without finalizing the meter.
	///
	/// This is used before creating a nested frame to ensure the child frame can see
	/// the parent's pending storage changes when calculating refunds.
	///
	/// Unlike [`Self::finalize_own_contributions`], this does not consume the pending diff,
	/// allowing the meter to continue tracking changes after the nested call returns.
	pub fn apply_pending_changes_to_contract(&self, info: &mut ContractInfo<T>) {
		if let Contribution::Alive(diff) = &self.own_contribution {
			// Apply the diff to update the ContractInfo's storage deposit fields.
			// We don't care about the return value (the deposit amount) here,
			// we just want to update the ContractInfo so child frames can see it.
			let _ = diff.update_contract::<T>(Some(info));
		}
	}
