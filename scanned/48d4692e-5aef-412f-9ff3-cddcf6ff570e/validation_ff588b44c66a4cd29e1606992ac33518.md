### Title
Stale `PendingSwap` entry survives `deregister` and can be completed against a re-registered ParaId, hijacking a lease-holding parachain's slot - (File: polkadot/runtime/common/src/paras_registrar/mod.rs)

### Summary
`Pallet::swap` stores pending swap intents keyed by the *initiating* `id` (`PendingSwap::<T>::insert(id, other)`), but `Pallet::do_deregister` only clears the entry keyed by the deregistered para itself (`PendingSwap::<T>::remove(id)`), not entries where that para is the *value* pointed to by another key. Consequently, if para_2 is deregistered while it is the "other" side of a still-pending `swap(para_1, para_2)` request, the stale mapping `PendingSwap[para_1] = para_2` survives, and can later be matched and executed against a completely different para that is subsequently registered under the same freed ParaId `para_2`.

### Finding Description
In `swap` (lines 326-370), when a swap request does not yet have a reciprocal pending entry, the code executes the `else` branch and does `PendingSwap::<T>::insert(id, other)` [1](#0-0) , storing the intent keyed by `id` (e.g. `PendingSwap[para_1] = para_2`).

`do_deregister` only removes the entry keyed by the para being deregistered: `PendingSwap::<T>::remove(id)` [2](#0-1) . When `para_2`'s manager calls `deregister(para_2)`, this call removes `PendingSwap[para_2]` (which never existed in this scenario), but it does **not** touch `PendingSwap[para_1] = para_2`, which remains in storage. `do_deregister` also fully removes `para_2`'s `ParaInfo` via `Paras::<T>::take(&id)` and unreserves its deposit, freeing the ParaId for future reservation/registration by anyone.

Because ParaIds can be re-reserved and re-registered by any signed account (via `reserve`/`register`, `do_reserve`/`do_register` at lines 604-657), an attacker can subsequently reserve and register a brand-new, unrelated on-demand parachain under the exact same ParaId `para_2`. As the new manager, the attacker can then call `swap(id=para_2, other=para_1)`. This passes `ensure_root_para_or_owner` because the attacker is now the legitimate manager of the (new) `para_2` `ParaInfo` entry [3](#0-2) . Inside `swap`, the match check `PendingSwap::<T>::get(other) == Some(id)` — i.e. `PendingSwap::get(para_1) == Some(para_2)` — is still `true` because the stale entry was never purged, so `do_thread_and_chain_swap`/`T::OnSwap::on_swap` executes between the legitimate, unrelated `para_1` (lease-holding parachain) and the attacker's freshly registered, entirely different `para_2` para [4](#0-3) .

None of the existing checks prevent this: `ensure_root_para_or_owner` only validates current ownership of the ParaId, not registration continuity/identity; and the `swap` matching logic correlates purely by `ParaId` value with no registration epoch/nonce to detect that the para behind `id`/`other` has changed since the original pending intent was created.

### Impact Explanation
Para_1's manager, who consented only to swap with the original (now-deregistered) `para_2` on-demand parachain, ends up having their lease-holding parachain's slot/lifecycle unexpectedly swapped with an attacker-controlled, freshly-registered, unrelated para under the reused ParaId. This is an unauthorized state transition affecting parachain slot ownership and deposit/lifecycle accounting without the victim's actual consent to swap with this specific new entity, and it can leave the deposit/lease accounting inconsistent with the original swap intent.

### Likelihood Explanation
This requires: (1) a lease-holding parachain manager to initiate `swap(para_1, para_2)` and leave it pending (a legitimate, common workflow while waiting for the counterparty), (2) para_2's manager to deregister para_2 before completing the swap (also plausible/legitimate independent action), and (3) an attacker to notice the stale `PendingSwap[para_1] = para_2` entry (publicly readable on-chain storage) and race to reserve/register the now-free ParaId `para_2` before para_1's manager clears the pending swap (e.g. via `swap(para_1, para_1)`) or someone else claims it. All steps use ordinary signed extrinsics (`register`, `reserve`, `swap`, `deregister`) with no privileged origin required, making this fully reachable by unprivileged users, though it is a timing-dependent race requiring the victim to leave the pending swap unresolved.

### Recommendation
In `do_deregister`, in addition to `PendingSwap::<T>::remove(id)`, also remove any reverse-referencing pending swap entries — e.g., iterate/check if any `PendingSwap` key maps its value to `id` and remove that key too, or better, store pending swaps symmetrically/bidirectionally so a single removal by either party's `ParaId` fully invalidates the pending intent. Alternatively, bind pending swap entries to a registration nonce/epoch (incremented on every `register`) so that a stale intent referencing a since-removed-and-recreated ParaId can never match a newer registration.

### Proof of Concept
Rust integration test in `polkadot/runtime/common/src/paras_registrar/tests.rs`:
1. Register `para_1` as a lease-holding parachain (`Parachain` lifecycle) and `para_2` as an on-demand parathread, both under distinct managers `alice` (para_1) and `bob` (para_2).
2. `alice` calls `Registrar::swap(para_1, para_2)` — assert `PendingSwap::<Test>::get(para_1) == Some(para_2)`.
3. `bob` calls `Registrar::deregister(para_2)` — assert `Paras::<Test>::get(para_2).is_none()` and deposit unreserved, but observe `PendingSwap::<Test>::get(para_1)` is still `Some(para_2)` (bug reproduction point).
4. Attacker `eve` calls `reserve()` then `register(para_2_new_id_same_value, ...)` reusing the freed `para_2` ParaId, becoming its manager, and progresses lifecycle to `Parathread`.
5. `eve` calls `Registrar::swap(para_2, para_1)`.
6. Assert either the call is rejected (expected fix: `Error::CannotSwap`/`NotRegistered` due to stale-intent detection), or, demonstrating the bug, assert that it **succeeds** and `para_1` is downgraded to a parathread while `eve`'s new `para_2` registration is upgraded to lease-holding parachain status — proving the unauthorized slot transfer occurred without `alice`'s consent to swap with this new entity.

	/// Deregister a Para Id, freeing all data returning any deposit.
	fn do_deregister(id: ParaId) -> DispatchResult {
		match paras::Pallet::<T>::lifecycle(id) {
			// Para must be a parathread (on-demand parachain), or not exist at all.
			Some(ParaLifecycle::Parathread) | None => {},
			_ => return Err(Error::<T>::NotParathread.into()),
		}
		polkadot_runtime_parachains::schedule_para_cleanup::<T>(id)
			.map_err(|_| Error::<T>::CannotDeregister)?;

		if let Some(info) = Paras::<T>::take(&id) {
			<T as Config>::Currency::unreserve(&info.manager, info.deposit);
		}

		PendingSwap::<T>::remove(id);
		Self::deposit_event(Event::<T>::Deregistered { para_id: id });
		Ok(())
	}
