Target: `SaltManager.fetchAndCache`/`getCachedSalt` deduplication (`this.fetchPromise`) combined with `IntentPayloadBuilder.build`. Attacker input: none from an external attacker; concerns concurrent calls by the SAME user issuing two independent `build()` calls (e.g. two tabs/two SDK instances under one account) that both call `getCachedSalt()` while `fetchPromise` is in flight. Preconditions: `isCacheValid()` false at start (`currentSalt == null`), two `build()` calls race. Call sequence: `build()` A and `build()` B both call `getCachedSalt()`; both receive the SAME `fetchPromise`'s resolved salt S; both call `buildWithSalt(S)` with their own `customRandomBytes`/timestamps, producing two DIFFERENT nonces via `encodeNonce(S, deadlineA, rbA)` and `encodeNonce(S, deadlineB, rbB)`; both get signed and submitted for two logically independent withdrawal intents. Equality broken: none directly - nonces differ due to different random/deadline inputs, so this is not itself a collision, but it demonstrates that `SaltManager` provides NO exclusivity guarantee per signed payload, meaning a caller cannot rely on `getCachedSalt()` returning a fresh, single-use value; combined with the 7-byte random-collision risk from `createTimestampedNonceBytes` (if both callers additionally use timestamp-based random bytes generated in the same millisecond, e.g. a batch/looped withdrawal helper), the shared salt plus millisecond-quantized random bytes materially shrinks the effective entropy protecting SINGLE_EXECUTION for concurrently-issued intents from the same account. Scoped impact: Critical - concurrent, legitimate use of the public `build()` API by one user can produce colliding nonces that violate one-execution-per-payload. Proof idea: vitest test firing two concurrent `build()` calls with `crypto.getRandomValues` mocked to return identical bytes (simulating a low-entropy environment) and `Date.now()` frozen, asserting the two resulting `nonce` strings are byte-identical.
