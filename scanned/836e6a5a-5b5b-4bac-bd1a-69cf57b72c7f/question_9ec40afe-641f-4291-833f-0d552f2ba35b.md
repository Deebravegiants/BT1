Target: `IntentSignerNEP413.signRaw` (intent-signer-nep413.ts), the underlying primitive `signIntent` calls. Attacker input: an integrator-forwarded `Nep413RawPayload` object (e.g. reconstructed from a cached/relayed quote payload) whose `payload.recipient` differs from the `payload.message`'s JSON content (the JSON message contains only `deadline, intents, signer_id` - it never embeds `verifying_contract`). Preconditions: nothing in `hashNEP413Message`/`signRaw` cross-checks that `recipient` matches any field inside `message`. Call sequence: caller invokes `signer.signRaw({ payload: { message, nonce, recipient: attackerRecipient, callbackUrl } })` directly (a legitimate public method on `IIntentSigner`), obtains a validly-signed `MultiPayloadNep413`. Equality broken: SIGNED == BUILT - the message body (intents/deadline/signer_id) the user reviewed/authorized has no cryptographic link to which contract (`recipient`) will execute it, so the same signed `message` bytes could be wrapped with a different `recipient` in a different `Nep413RawPayload` without invalidating the signature check on the message hash structure used by `hashNEP413Message` (recipient is part of the hashed struct, but the SDK never re-derives/validates recipient against the caller's original intended contract post-hoc). Scoped impact: Critical - because `signRaw` is a lower-level exported primitive with no invariant checking `recipient` against the caller's intended `verifying_contract`, an integrator wiring a solver-supplied raw payload through `signRaw` can produce a validly signed payload for a contract the end user never approved. Proof idea: vitest test calling `signRaw` twice with the same `message`/`nonce` but different `recipient` values, mocking `signMessageFn`, asserting both signatures verify successfully with no SDK-side rejection despite the differing contract binding.
