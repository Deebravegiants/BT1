### Title
Missing allowlist/authorization enforcement on gateway legacy user-triggered messages allows unauthorized DON job triggering - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The CVE describes an unprivileged/remote actor being able to invoke a dangerous, unauthenticated interface (Electron's exposed `ipcRenderer` → `openExternal`) because the receiving side performed no authorization check on the incoming message before acting on it. The closest reachable analog in this codebase is the Gateway's user-facing legacy message handler, `handleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go`, which accepts a `web_api_trigger` message straight from the internet-facing HTTP endpoint and forwards it to every node in the DON — with an explicit `// TODO: apply allowlist and rate-limiting here` marking the missing authorization check.

### Finding Description
The Gateway's public HTTP entry point (`gateway.ProcessRequest` in `core/services/gateway/gateway.go`) routes any legacy (DonID-bearing) JSON-RPC request straight to `handler.HandleLegacyUserMessage`: [1](#0-0) 

Inside `HandleLegacyUserMessage`, the handler validates the payload's structure, timestamp and method name, but explicitly skips authorization/allowlist checks before broadcasting the message to every node of the DON: [2](#0-1) 

Compare this to the node-side outgoing message path (`handleWebAPIOutgoingMessage`), which at least enforces a per-node rate limiter before acting on incoming node responses: [3](#0-2) 

and to the sibling Vault gateway path, which performs full `AuthorizeRequest`/allowlist checks before any privileged action is taken: [4](#0-3) 

The `HandleLegacyUserMessage` code path has no equivalent authorization gate — any caller reaching the Gateway's public user port with a syntactically valid `web_api_trigger` message and a known `DonID` can cause the Gateway to broadcast the request to `don.SendToNode` for every DON member: [5](#0-4) 

This mirrors the CVE's root cause: a message interface reachable by an untrusted party that dispatches directly to a sensitive downstream action without checking whether the caller is permitted to invoke it.

### Impact Explanation
An unprivileged, unauthenticated remote client can trigger `web_api_trigger` workflow executions on all nodes of a targeted DON without being on any allowlist, since the code path bypasses authorization entirely (as the TODO comment concedes). This can cause unauthorized workflow/job execution, resource exhaustion of DON nodes (since every member node is contacted per request with no allowlist-based quota), and potential downstream side effects if the triggered workflow performs privileged or fund-moving actions.

### Likelihood Explanation
Likelihood is high for reachability: the Gateway's HTTP user port is explicitly the internet-facing entry point, and the legacy path is selected purely based on the presence of `msg.Body.DonID` in the request — no credential, signature, or allowlist membership is required to hit `HandleLegacyUserMessage`. The only mitigations present (timestamp freshness check, method name check, per-node rate limiting on the return path) do not perform any actor-authorization.

### Recommendation
Implement the allowlist/rate-limiting check referenced by the TODO in `handleLegacyUserMessage` before broadcasting to `don.SendToNode`, mirroring the `Authorizer`/`AllowListBasedAuth` pattern already used in `core/capabilities/vault/gw_handler.go` and `core/capabilities/vault/allow_list_based_auth.go`. Reject or rate-limit requests from callers/workflow owners not present in the DON's allowlist prior to fan-out to nodes.

### Proof of Concept
1. Identify a Gateway's public HTTP user port and a valid `DonID` for a target DON (from `config.DONConfig`).
2. Send a legacy JSON-RPC request with `Method: "web_api_trigger"`, a valid `Timestamp`, and the target `DonID`, without any prior allowlisting or credential setup.
3. `gateway.ProcessRequest` routes it to `HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:341`), which — absent the allowlist check flagged by the TODO at line 384 — proceeds to call `don.SendToNode` for every member of the DON, triggering workflow execution on all nodes despite the caller having no authorization.

func (h *GatewayHandler) HandleGatewayMessage(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) (err error) {
	reqLggr := h.requestLogger(req, gatewayID)
	reqLggr.Debugw("received message from gateway", "req", req)

	var response *jsonrpc.Response[json.RawMessage]
	var authResult *AuthResult

	switch req.Method {
	case vaulttypes.MethodSecretsCreate, vaulttypes.MethodSecretsUpdate:
		publicKey, pkErr := h.getMasterPublicKey(ctx)
		if pkErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pkErr)
			break
		}
		authorized, pipelineErr := h.requestProcessor.ProcessRequest(ctx, req, publicKey)
		if pipelineErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pipelineErr)
			break
		}
		authResult = authorized.AuthResult
	case vaulttypes.MethodSecretsDelete, vaulttypes.MethodSecretsList:
		authorized, pipelineErr := h.requestProcessor.ProcessRequest(ctx, req, nil)
		if pipelineErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pipelineErr)
			break
		}
		authResult = authorized.AuthResult
	case vaulttypes.MethodPublicKeyGet:
		response = h.handlePublicKeyGet(ctx, gatewayID, req)
	default:
		response = h.errorResponse(ctx, gatewayID, req, api.UnsupportedMethodError, errors.New("unsupported method: "+req.Method))
	}
