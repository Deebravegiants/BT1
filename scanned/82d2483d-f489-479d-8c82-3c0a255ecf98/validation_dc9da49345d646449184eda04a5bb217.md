### Title
Revoked LDAP user role remains valid for the full sync interval because `AuthorizedUserWithSession` trusts a locally cached role instead of the live LDAP group membership - (File: core/sessions/ldapauth/ldap.go)

### Summary
The Palmera `isSafeLead` bug is a class of "authorization decision based on stale/cached state instead of the current source of truth for roles." The Chainlink node's LDAP authenticator has the same bug class: per-request authorization reads a role value cached in the local `ldap_sessions` table rather than checking current LDAP group membership, and that cache is only refreshed by a periodic background sync job.

### Finding Description
`ldapAuthenticator.AuthorizedUserWithSession` is the per-request authorization check used to authenticate an already-logged-in user for every subsequent API call. It queries only the local `ldap_sessions` table for the cached `user_role` and never re-checks the upstream LDAP directory (the actual source of truth for group membership/roles): [1](#0-0) 

The role stored in that row is set at login time in `CreateSession` (`foundUser.Role` from the LDAP group lookup) and is only ever corrected by a separate background reconciliation job, `LDAPServerStateSyncer.Work`, which re-queries the upstream LDAP groups and issues bulk `UPDATE ldap_sessions SET user_role = CASE ...` statements: [2](#0-1) 

This mirrors the `isSafeLead` flaw exactly: the authorization check (`AuthorizedUserWithSession`, analogous to `isSafeLead`) consults a locally stored flag (`_safe.lead` / `ldap_sessions.user_role`) instead of querying the authoritative role source (`RolesAuthority` / the LDAP server) at decision time. If an admin removes a user from the `Admin`/`Edit`/`Run` LDAP group (the equivalent of calling `disableSafeLeadRoles`), that revocation is not reflected until the next `LDAPServerStateSyncer.Work` tick.

### Impact Explanation
Between the moment a user's LDAP group membership is revoked and the next sync cycle, any existing session for that user continues to be authorized with the old (higher) role by `AuthorizedUserWithSession`, since role checks such as `RequiresAdminRole`/`RequiresEditRole` operate purely on the cached `clsessions.User.Role` value set from this stale row: [3](#0-2) 

A de-provisioned/demoted user can therefore continue to perform admin/edit-level actions (creating jobs, managing bridges/keys, etc.) on the Chainlink node for the entire sync interval, which is an unauthorized-access / privilege-persistence issue directly analogous to the reported finding.

### Likelihood Explanation
This requires only normal, unprivileged operational conditions: a previously valid, logged-in LDAP user whose role changes upstream (revocation/demotion) while their local session remains active. No malicious node/peer, network-layer exploit, or gateway component is involved — it is a standard authenticated-user role check inside the node's own web/API authentication layer, which fits the "unprivileged-actor... node API authentication and roles" scope. Likelihood is bounded by how frequently the periodic LDAP sync job runs (not fully confirmed from available context — I could not locate the exact configured/default sync interval value within the tool budget), but the window is inherent to the design regardless of interval length.

### Recommendation
Perform authoritative role verification (or at minimum a short-TTL cache with forced invalidation on role-affecting events) at request time rather than relying solely on the cached `ldap_sessions.user_role`, or trigger an immediate sync/session-role-invalidation whenever the upstream state changes, instead of waiting for the next scheduled `LDAPServerStateSyncer.Work` run.

### Proof of Concept
1. User `X` logs in via LDAP; `CreateSession` stores `user_role = 'admin'` in `ldap_sessions` for their session ID (see `core/sessions/ldapauth/ldap.go` `CreateSession`).
2. An LDAP administrator removes `X` from the Admin group upstream (their local `disableSafeLeadRoles` analog).
3. Before the next `LDAPServerStateSyncer.Work` tick runs, `X` continues to call authenticated node API endpoints using their existing session cookie.
4. `AuthenticateBySession` → `AuthorizedUserWithSession` reads the stale `admin` role from `ldap_sessions` (core/sessions/ldapauth/ldap.go:345-373) and `RequiresAdminRole` (core/web/auth/auth.go:237-253) grants access, allowing `X` to perform admin-only actions despite the revoked role.

func (l *ldapAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (sessions.User, error) {
	if len(sessionID) == 0 {
		return sessions.User{}, errors.New("session ID cannot be empty")
	}
	// Query the ldap_sessions table for given session ID, user role and email are cached so
	// no further upstream LDAP query is performed
	var foundSession struct {
		UserEmail string
		UserRole  sessions.UserRole
		Valid     bool
	}
	if err := l.ds.GetContext(ctx, &foundSession,
		"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM ldap_sessions WHERE id = $1",
		sessionID, l.config.SessionTimeout().Duration(),
	); err != nil {
		return sessions.User{}, sessions.ErrUserSessionExpired
	}
	if !foundSession.Valid {
		// Sessions expired, purge
		if _, execErr := l.ds.ExecContext(ctx, "DELETE FROM ldap_sessions WHERE id = $1", sessionID); execErr != nil {
			l.lggr.Errorf("error purging stale ldap session: %v", execErr)
		}
		return sessions.User{}, sessions.ErrUserSessionExpired
	}
	return sessions.User{
		Email: foundSession.UserEmail,
		Role:  foundSession.UserRole,
	}, nil
}

// RequiresAdminRole extracts the user object from the context, and asserts the user's role is 'admin'
func RequiresAdminRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role != clsessions.UserRoleAdmin {
			c.Abort()
			addForbiddenErrorHeaders(c, "admin", string(user.Role), user.Email)
			jsonAPIError(c, http.StatusForbidden, errors.New("Forbidden"))
			return
		}
		handler(c)
	}
}
