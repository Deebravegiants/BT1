In `core/web/resolver/query.go`, `ParsePaginatedRequest` in `core/web/api.go` validates its inputs (`size < 1`), but `pageOffset`/`pageLimit` in `core/web/resolver/helpers.go` do not validate negative `*int32` GraphQL arguments before casting to `int` and slicing.### Title
Negative GraphQL `offset`/`limit` bypasses bounds validation and reaches raw SQL `LIMIT`/`OFFSET` in `Bridges`, `JobRuns`, `EthTransactions` resolvers - ([File: core/web/resolver/helpers.go])

### Summary
The chainlink node's GraphQL API exposes several paginated list resolvers (`Bridges`, `JobRuns`, `EthTransactions`, `EthTransactionsAttempts`, etc.) that accept client-supplied `*int32 Offset`/`*int32 Limit` arguments. Unlike the REST pagination path (`core/web/api.go`'s `ParsePaginatedRequest`, which explicitly rejects `size < 1` / `page < 1`), the GraphQL helpers `pageOffset`/`pageLimit` perform no such validation before the values are passed straight into SQL `LIMIT`/`OFFSET` clauses. This is analogous to the reported imagecli bug class: an unvalidated numeric input (there, a `ratio`; here, `offset`/`limit`) that is trusted and forwarded into a lower-level primitive (there, `imageproc::shrink_width`; here, raw SQL parameter binding) without a sanity/bounds check.

### Finding Description
`pageOffset` and `pageLimit` in `core/web/resolver/helpers.go` cast the client-provided `*int32` directly to `int` with no negativity or bounds check: [1](#0-0) 

These are used by multiple authenticated resolvers, e.g. `Bridges`: [2](#0-1) 

and `JobRuns` / `EthTransactions`: [3](#0-2) [4](#0-3) 

The `offset`/`limit` values flow unchecked into `bridges.orm.BridgeTypes`, which interpolates them directly as SQL parameters: [5](#0-4) 

By contrast, the equivalent REST controller path validates size/page are `>= 1` before computing offset: [6](#0-5) 

The `Chains` resolver is the only one in this file that additionally checks `offset >= count` and bounds `end`, showing the codebase is aware such checks are needed but did not apply them uniformly across all paginated resolvers/ORM calls: [7](#0-6) 

### Impact Explanation
A negative `limit` passed to PostgreSQL's `LIMIT` clause is normally interpreted by Postgres as "no limit" (it does not error), and a negative `OFFSET` is rejected by Postgres with an error (`OFFSET must not be negative`), which the resolver would propagate as a raw internal error rather than a controlled 4xx. This does not directly evidence a Rust-style reachable panic/process crash as in the CVE, but it is the same bug class — unvalidated numeric input from an unprivileged (any authenticated, low-privilege "view" role) actor reaching a data-layer primitive without the same validation applied elsewhere in the same file (`Chains`) and in the REST equivalent (`ParsePaginatedRequest`). Confirmed impact is limited to unhandled DB errors / inconsistent behavior rather than a proven crash or data exposure; I could not confirm from static analysis whether Postgres's LIMIT/OFFSET behavior on negative values in this exact configuration causes a full internal-server error or a panic in `sqlx`/`sqlutil` code paths — that requires runtime verification.

### Likelihood Explanation
Any user who can authenticate to the GraphQL API with the lowest privilege role (`view`, checked only via `authenticateUser`, not `authenticateUserCanEdit`/`authenticateUserIsAdmin`) can trivially set `Offset: -1` or `Limit: -1` in a query — this requires no special role or admin access, matching the "unprivileged-actor" scope of this analog. It is a low-effort request-crafting issue, not a network/malicious-node scenario.

### Recommendation
Add explicit validation in `pageOffset`/`pageLimit` (or at each call site) rejecting negative `Offset`/`Limit` values, mirroring the checks already present in `ParsePaginatedRequest` (`core/web/api.go`) and in the `Chains` resolver's `offset >= count` bound. Return a clear `GraphQL` user error instead of allowing negative values to reach `bridges.orm.BridgeTypes`, `JobORM().PipelineRuns`, `TxmStorageService().Transactions`, etc.

### Proof of Concept
Send an authenticated GraphQL query:
```graphql
query {
  bridges(offset: -100, limit: -1) {
    results { name }
    metadata { total }
  }
}
```
`pageOffset(-100)` and `pageLimit(-1)` return `-100` and `-1` unchanged (per [1](#0-0) ), which are passed to `r.App.BridgeORM().BridgeTypes(ctx, -100, -1)` → `SELECT * FROM bridge_types ORDER BY name asc LIMIT -1 OFFSET -100` (per [8](#0-7) ), producing an unvalidated/unexpected database-layer response instead of a clean input-validation error.

// Chains retrieves a paginated list of chains.
func (r *Resolver) Chains(ctx context.Context, args struct {
	Offset *int32
	Limit  *int32
}) (*ChainsPayloadResolver, error) {
	if err := authenticateUser(ctx); err != nil {
		return nil, err
	}

	offset := pageOffset(args.Offset)
	limit := pageLimit(args.Limit)

	relayersMap := r.App.GetRelayers().GetIDToRelayerMap()

	chains := make([]chainlink.NetworkChainStatus, 0, len(relayersMap))
	for k, v := range relayersMap {
		s, err := v.GetChainStatus(ctx)
		if err != nil {
			return nil, err
		}

		chains = append(chains, chainlink.NetworkChainStatus{
			ChainStatus: s,
			Network:     k.Network,
		})
	}

	count := len(chains)
	if count == 0 {
		// No chains are configured, return an empty ChainsPayload, so we don't break the UI
		return NewChainsPayload(nil, 0), nil
	}

	// bound the chain results
	if offset >= count {
		return nil, fmt.Errorf("offset %d out of range", offset)
	}
	end := count
	if limit > 0 && offset+limit < end {
		end = offset + limit
	}

	sortByNetworkAndID(chains)
	return NewChainsPayload(chains[offset:end], safeInt32(count)), nil
}

// BridgeTypes returns bridge types ordered by name filtered limited by the
// passed params.
func (o *orm) BridgeTypes(ctx context.Context, offset int, limit int) (bridges []BridgeType, count int, err error) {
	err = o.transact(ctx, true, func(tx *orm) error {
		if err = tx.ds.GetContext(ctx, &count, "SELECT COUNT(*) FROM bridge_types"); err != nil {
			return pkgerrors.Wrap(err, "BridgeTypes failed to get count")
		}
		sql := `SELECT * FROM bridge_types ORDER BY name asc LIMIT $1 OFFSET $2;`
		if err = tx.ds.SelectContext(ctx, &bridges, sql, limit, offset); err != nil {
			return pkgerrors.Wrap(err, "BridgeTypes failed to load bridge_types")
		}
		return nil
	})

	return
}

// ParsePaginatedRequest parses the parameters that control pagination for a
// collection request, returning the size and offset if specified, or a
// sensible default.
func ParsePaginatedRequest(sizeParam, pageParam string) (int, int, int, error) {
	var err error
	page := 1
	size := PaginationDefault

	if sizeParam != "" {
		if size, err = strconv.Atoi(sizeParam); err != nil || size < 1 {
			return 0, 0, 0, fmt.Errorf("invalid size param, error: %w", err)
		}
	}

	if pageParam != "" {
		if page, err = strconv.Atoi(pageParam); err != nil || page < 1 {
			return 0, 0, 0, fmt.Errorf("invalid page param, error: %w", err)
		}
	}

	offset := (page - 1) * size
	return size, page, offset, nil
}
