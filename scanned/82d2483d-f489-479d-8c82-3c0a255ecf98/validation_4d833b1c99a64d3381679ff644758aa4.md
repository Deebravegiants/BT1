### Title
Gateway Legacy User Trigger Messages Broadcast to All DON Nodes Without Allowlist Authorization - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The BabySwap report shows a router trusting an unvalidated, caller-supplied parameter (a `factories` address) as if it were a pre-authorized/trusted value, letting an unprivileged caller substitute a malicious contract and manipulate protocol logic. The analogous root cause in this codebase is a gateway path that accepts an unauthenticated, caller-supplied message and forwards it to privileged downstream execution (triggering a workflow run on every DON node) without ever checking it against an allowlist — the check is explicitly marked as not implemented.

### Finding Description
`gateway.ProcessRequest` is the entry point invoked directly for incoming user HTTP requests [1](#0-0) . For legacy requests (those carrying a `DonID`), it looks up the handler and calls `h.HandleLegacyUserMessage(ctx, msg, callback)` with no prior authorization step other than message shape validation [2](#0-1) .

Inside `handler.HandleLegacyUserMessage`, the code decodes the payload, checks the timestamp isn't stale, and then reaches a method check that is explicitly preceded by an unimplemented control:

```
// TODO: apply allowlist and rate-limiting here
if msg.Body.Method != MethodWebAPITrigger {
``` [3](#0-2) 

After this, the request is transformed and sent to **every** DON member node with no owner/allowlist check at all:
```go
for _, member := range h.donConfig.Members {
    err = errors.Join(err, don.SendToNode(ctx, member.Address, req))
}
``` [4](#0-3) 

This mirrors the BabySwap parameter-trust issue: a caller-controlled request (analogous to the attacker-supplied `factories` array) is accepted and used to drive privileged execution (triggering a workflow on all DON nodes) without validating it against the trusted/allowlisted set of callers, unlike the newer JSON-RPC vault/gateway path which does enforce `AllowListBasedAuth`/`Authorizer.AuthorizeRequest` before processing [5](#0-4) [6](#0-5) .

### Impact Explanation
If this legacy (`web_api_trigger`) path is reachable and enabled in a deployed configuration, any unprivileged network client able to reach the gateway's user-facing HTTP port could submit a message with an arbitrary `DonID`/payload and cause the gateway to broadcast a trigger message to every node of that DON — i.e., an unauthorized job/workflow run — because there is no allowlist enforcement gating which callers/owners may trigger workflows on a given DON, unlike the newer vault gateway flow.

### Likelihood Explanation
This depends entirely on whether the legacy `capabilities` handler and the `web_api_trigger` method are still wired up/enabled in production DON configurations, versus superseded by the newer v2 HTTP trigger handler (`core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go`), which does perform explicit request validation (e.g., `workflowOwner` hex checks seen in its tests) [7](#0-6) . The explicit `// TODO: apply allowlist and rate-limiting here` comment strongly suggests the legacy path was known to be missing this control at the time it was written, but I could not fully verify from the index whether this legacy handler is still actively deployed/reachable in current production gateway configs or has been fully deprecated in favor of the v2/JSON-RPC paths.

### Recommendation
Add allowlist/authorization enforcement in `HandleLegacyUserMessage` before dispatching to DON members — mirroring the `Authorizer`/`AllowListBasedAuth` pattern already used by the vault gateway handler — so that only requests from owners/callers authorized for the target DON/workflow can trigger a broadcast, and remove or gate the legacy path if it is no longer intended for production use.

### Proof of Concept
Not independently reproducible from the indexed codebase alone (no test harness proving the legacy handler is live end-to-end with a real DON in current configs was found). A background Devin session with full repo/build access would be needed to confirm whether `web_api_trigger`/`HandleLegacyUserMessage` is still routed to from a running gateway configuration and to construct a request exercising the missing-allowlist gap.

func (g *gateway) ProcessRequest(ctx context.Context, rawRequest []byte, auth string) (rawResponse []byte, httpStatusCode int) {
	// decode
	jsonRequest, err := jsonrpc2.DecodeRequest[json.RawMessage](rawRequest, auth)
	if err != nil {
		return newError("", api.UserMessageParseError, err.Error())
	}
	msg, err := g.codec.DecodeJSONRequest(jsonRequest)
	if err != nil {
		return newError(jsonRequest.ID, api.UserMessageParseError, err.Error())
	}
	if len(jsonRequest.ID) > 200 {
		// Arbitrary limit to prevent abuse
		return newError(jsonRequest.ID, api.UserMessageParseError, "request ID is too long: "+strconv.Itoa(len(jsonRequest.ID))+". max is 200 characters")
	}
```
