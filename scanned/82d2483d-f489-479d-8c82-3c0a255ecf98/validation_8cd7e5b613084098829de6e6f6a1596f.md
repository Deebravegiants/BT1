### Title
Cross-Workflow HTTP Response Cache Collision Due to Missing WorkflowID in Cache Key - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
The gateway's outbound HTTP action response cache is keyed only by `OutboundHTTPRequest.Hash()`, which the codebase's own tests confirm deliberately excludes `WorkflowID` from the hash while including `WorkflowOwner`. Despite the package README explicitly promising "Cache Key: Generated from workflow ID and request hash" and "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage," the actual `Hash()` implementation does not bind the cache entry to the requesting workflow. This is analogous to the reported Move `lending.move` bug: a caller-supplied identifier (there, `CoinType`/pool; here, `WorkflowID`) is not verified/bound against the resource actually used to satisfy the request, so a request "labeled" for one resource is silently serviced/stored using the identity of a different one.

### Finding Description
`responseCache.Fetch` and `responseCache.Set` in `core/services/gateway/handlers/capabilities/v2/response_cache.go` use `req.Hash()` as the sole cache key: [1](#0-0) [2](#0-1) 

The struct comment states the hash is derived from "method, URL, headers, body, workflowOwner" — `WorkflowID` is not part of the key: [3](#0-2) 

The package's own test suite proves this explicitly: setting different `WorkflowID` values on otherwise identical requests produces the **same** hash, while different `WorkflowOwner` values produce different hashes: [4](#0-3) [5](#0-4) 

This directly contradicts the documented invariant in the handler's own README: [6](#0-5) 

The cache is populated/consumed from `gatewayHandler.makeOutgoingRequest`, which is invoked for every inbound outbound-HTTP-action message from a workflow node (an unprivileged, internet/DON-facing path): [7](#0-6) 

Because `Method`, `URL`, `Headers`/`MultiHeaders`, and `Body` are attacker/workflow-controlled fields of `OutboundHTTPRequest`, any two workflows belonging to the same `WorkflowOwner` that issue HTTP action requests with identical method/URL/headers/body but different `WorkflowID` will collide on the same cache key. The second workflow's request will be served the first workflow's cached response (or vice versa) without re-executing the HTTP call, i.e., cross-workflow response confusion — the exact "identifier not verified against the resource actually used" bug class described in the analog report.

### Impact Explanation
An owner running multiple workflows (or a single owner reusing the same webhook/API call shape across workflow versions/tags) can have HTTP action results improperly shared across workflow executions. This can leak one workflow's fetched data (e.g., API responses containing execution-specific or environment-specific content) into a different workflow's execution context, or cause a workflow to act on stale/foreign data returned from another workflow's request, undermining the "Workflow Isolation" guarantee the caching subsystem is documented to provide. Because HTTP action data can feed subsequent on-chain reports/transactions initiated by the workflow, cross-workflow data leakage can translate into incorrect downstream capability execution.

### Likelihood Explanation
Reachable directly from the outbound HTTP action path taken by any workflow node message (an unprivileged/DON-side but non-operator, internet-facing message path within `gatewayHandler.HandleNodeMessage` → `makeOutgoingRequest`). It requires no privilege escalation — only that two workflows under the same owner (or crafted to match on relevant fields) issue outbound HTTP requests with identical method/URL/headers/body and caching enabled (`CacheSettings.MaxAgeMs > 0` or `Store: true`), which is a normal, expected configuration for HTTP action nodes using caching.

### Recommendation
Include `WorkflowID` (and ideally `WorkflowExecutionID`/`ReferenceID` if response scoping should be per-execution rather than per-workflow) in the `OutboundHTTPRequest.Hash()` computation used as the cache key, so that the documented "workflow-scoped caching" / "Workflow Isolation" behavior actually holds. At minimum, update the cache key or the documentation so the implementation matches the stated isolation guarantee, and add a regression test asserting that identical requests with different `WorkflowID` produce different cache keys (the inverse of the current `response_cache_test.go` assertion).

### Proof of Concept
1. Workflow A (owner `0xabc`, `WorkflowID = wf-A`) issues an `OutboundHTTPAction` request: `GET https://api.example.com/data`, no auth headers, with `CacheSettings{MaxAgeMs: 60000, Store: true}`. The gateway fetches and caches the response keyed by `Hash()` (method+URL+headers+body+workflowOwner — no workflowID).
2. Workflow B (same owner `0xabc`, different `WorkflowID = wf-B`) issues the identical `OutboundHTTPAction` request (`GET https://api.example.com/data`, same headers/body, same `CacheSettings.MaxAgeMs > 0`).
3. Because `Hash()` ignores `WorkflowID`, `responseCache.Fetch` for Workflow B's request hits the cache entry stored for Workflow A and returns Workflow A's cached response to Workflow B without making a fresh HTTP call — demonstrated directly by the existing test `TestRequestHash`'s "having different workflowID results in same Hash" subtest. func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}

func (h *gatewayHandler) makeOutgoingRequest(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	requestID := resp.ID
	h.lggr.Debugw("handling outgoing message", "requestID", requestID, "nodeAddr", nodeAddr)
	var req gateway_common.OutboundHTTPRequest
	err := json.Unmarshal(*resp.Result, &req)
	if err != nil {
		return fmt.Errorf("failed to unmarshal HTTP request from node %s: %w", nodeAddr, err)
	}
	timeout := time.Duration(req.TimeoutMs) * time.Millisecond
	httpReq := network.HTTPRequest{
		Method:           req.Method,
		URL:              req.URL,
		Headers:          req.Headers, //nolint:staticcheck // forward deprecated Headers for backward compatibility; request uses MultiHeaders when set
		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}

	sendResponseTimeout := time.Duration(defaultSendResponseTimeoutMs) * time.Millisecond

	// send response to node async
	h.wg.Go(func() {
		// not cancelled when parent is cancelled to ensure the goroutine can finish
		baseCtx := context.WithoutCancel(ctx)
		httpCtx, httpCancel := context.WithTimeout(baseCtx, timeout)
		defer httpCancel()
		l := logger.With(h.lggr, "requestID", requestID, "method", req.Method, "timeout", req.TimeoutMs)
		var outboundResp gateway_common.OutboundHTTPResponse
		callback := h.createHTTPRequestCallback(httpCtx, requestID, httpReq, req)
		if req.CacheSettings.MaxAgeMs > 0 {
			h.metrics.IncrementCacheReadCount(ctx, h.lggr)
			outboundResp = h.responseCache.Fetch(httpCtx, req, callback, req.CacheSettings.Store)
		} else {
			outboundResp = callback()
			if req.CacheSettings.Store {
				h.responseCache.Set(req, outboundResp)
			}
		}
