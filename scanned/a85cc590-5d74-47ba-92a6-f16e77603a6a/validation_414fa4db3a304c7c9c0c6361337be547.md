### Title
Legacy gateway user message handler allows request-ID collision to hijack or deny another user's saved callback - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The Sherlock report describes a low-cost, reversible reservation of a shared, limited resource (Queue's `maxTVL`) that lets an unprivileged actor block other legitimate users from using that resource, at essentially no risk to themselves. The closest reachable analog in this codebase is in the gateway's legacy user-message path: `handler.HandleLegacyUserMessage` stores an in-flight callback keyed only by the caller-supplied `MessageID`, with no check for collision against another still-pending request, unlike the newer v2 trigger handler which explicitly guards against this.

### Finding Description
`ProcessRequest` in `core/services/gateway/gateway.go` accepts JSON-RPC requests from unprivileged external users, validates the embedded legacy `Message` via `msg.Validate()`, and dispatches to `h.HandleLegacyUserMessage(ctx, msg, callback)`. [1](#0-0) 

`Message.Validate()` only checks the `MessageID`'s length (1–128 bytes) and that it doesn't end in a null byte — it never checks that the ID is unique or unpredictable, and the ID is fully attacker-chosen. [2](#0-1) 

In `HandleLegacyUserMessage`, the handler stores the pending callback keyed by `msg.Body.MessageID` with a plain map write, with no existence check:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageID] = &savedCallback{id: msg.Body.MessageID, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [3](#0-2) 

Because the map key comes straight from the user-controlled `MessageID`, if an unprivileged attacker sends a second legacy request re-using the exact `MessageID` of another user's still-in-flight request, the attacker's own callback silently overwrites the legitimate one in `savedCallbacks`. When the DON member's response for that `MessageID` later arrives, `HandleNodeMessage` looks the entry up by ID and delivers the response to whichever callback is currently stored — i.e., to the attacker, not the original requester (cross-user response confusion), while the original caller's HTTP request simply times out.

This is directly analogous to the reported bug class: a single, low-cost, unprivileged action (sending one crafted request) lets an attacker occupy/overwrite a slot in a shared, capacity-bounded resource (`savedCallbacks`, bounded by `MaxSavedCallbacks`) to deny or hijack another user's outcome, with no meaningful cost or risk to the attacker (they can always guess/predict `MessageID`s since the DON's or user's client typically chooses simple, sometimes sequential or user-supplied values, and there is no server-side randomness requirement enforced by `Validate()`).

Notably, the newer v2 implementation of the same concept (`httpTriggerHandler.setupCallback`) explicitly defends against this exact scenario by rejecting a request whose ID is already in use:
```go
if _, found := h.callbacks[requestID]; found {
    h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, ...)
    return nil, fmt.Errorf("in-flight request ID: %s", requestID)
}
``` [4](#0-3) 
This confirms the legacy handler's lack of the same guard is a real gap rather than intended behavior.

### Impact Explanation
An unprivileged remote caller of the gateway's `/user` endpoint can:
1. Deny another legitimate user their response (their pending callback is overwritten and they will time out), and/or
2. Receive the response payload intended for another user's request if it correlates with sensitive data, achieving cross-user response confusion.

This is a legitimate node-API/gateway-facing denial-of-service and confidentiality-adjacent issue reachable by any external, unauthenticated-to-the-DON caller who only needs to guess or observe another in-flight `MessageID`.

### Likelihood Explanation
Exploitability depends on the attacker knowing or guessing a victim's in-flight `MessageID` within the short callback window (`CallbackMaxAgeSec`, default 120s). If client-generated `MessageID`s are predictable, sequential, or otherwise observable (e.g., echoed by client-side apps, logs, or timing side channels), likelihood is meaningful; if IDs are always cryptographically random and never exposed before the response, exploitability is lower. Because the codebase does not enforce ID unpredictability at the protocol layer (`Validate()` has no uniqueness/entropy requirement), this remains a real defense-in-depth gap regardless of current client behavior.

### Recommendation
In `handler.HandleLegacyUserMessage` (core/services/gateway/handlers/capabilities/handler.go), before inserting into `savedCallbacks`, check for an existing, non-expired entry for the same `MessageID` and reject the request (mirroring the `ErrConflict` behavior already implemented in `httpTriggerHandler.setupCallback`) rather than silently overwriting it.

### Proof of Concept
1. User A sends a valid signed legacy `Message` with `MessageID = "shared-id"` to the gateway's `/user` endpoint; the gateway stores `savedCallbacks["shared-id"] = <A's callback>` and forwards to DON members.
2. Before a DON response for `"shared-id"` arrives, attacker B sends their own valid signed legacy `Message` also using `MessageID = "shared-id"`. This overwrites the map entry: `savedCallbacks["shared-id"] = <B's callback>`.
3. When a DON node responds with `resp.ID == "shared-id"`, `HandleNodeMessage` looks up `savedCallbacks["shared-id"]` and delivers the result to B's callback, not A's; A's original HTTP request eventually times out with no response. [3](#0-2)

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
