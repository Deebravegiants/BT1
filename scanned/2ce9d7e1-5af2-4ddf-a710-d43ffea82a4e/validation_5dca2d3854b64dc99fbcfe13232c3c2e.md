### Title
Partial storage-deposit refund on contract termination can permanently strand `StorageDepositReserve` hold when a competing freeze reduces the account's polite-liquid balance - (File: substrate/frame/contracts/src/storage/meter.rs)

### Summary
`ReservingExt::charge`'s `Deposit::Refund` branch calls `T::Currency::transfer_on_hold(..., Precision::BestEffort, ..., Fortitude::Polite, ...)` and only logs an error if `transferred < *amount`, then unconditionally proceeds to `System::<T>::dec_consumers(&contract)` and sweeps the remaining `reducible_balance` to the beneficiary. If the contract's account has a competing freeze/lock that reduces `reducible_total_balance_on_hold(..., Polite)` below the full `StorageDepositReserve` hold amount, the refund silently under-delivers, and the leftover hold is stranded on the (now consumer-decremented, potentially reapable) contract account forever, with no path to reclaim it.

### Finding Description
`fungible::hold::Mutate::transfer_on_hold` (`substrate/frame/support/src/traits/tokens/fungible/hold.rs:346-378`) computes `liquid = Self::reducible_total_balance_on_hold(source, force)`, and under `Precision::BestEffort` it clamps `amount = amount.min(liquid).min(have)` rather than erroring. `reducible_total_balance_on_hold` with `Fortitude::Polite` respects other freeze/lock mechanisms on the account (as directly demonstrated by the codebase's own test `frozen_hold_balance_best_effort_transfer_works`, `substrate/frame/balances/src/tests/fungible_tests.rs:427-448`, which freezes 5 and holds 9, then a `BestEffort`/`Polite` `transfer_on_hold` of 10 only actually moves 5, silently leaving 4 stuck on hold).

`ReservingExt::charge`'s refund path (`substrate/frame/contracts/src/storage/meter.rs:567-593`) invokes exactly this call with `Precision::BestEffort` and `Fortitude::Polite`. If `transferred < *amount`, it only does `log::error!` — it does not return an `Err`, does not retry with `Force`, and does not abort. Execution then falls through unconditionally to:
```rust
if let ContractState::<T>::Terminated { beneficiary } = state {
    System::<T>::dec_consumers(&contract);
    T::Currency::transfer(&contract, &beneficiary, T::Currency::reducible_balance(&contract, Preservation::Expendable, Polite), Preservation::Expendable)?;
}
```
(`substrate/frame/contracts/src/storage/meter.rs:596-605`). This decrements the consumer ref and sweeps the free/expendable-reducible balance to the beneficiary, while the un-refunded portion of the `StorageDepositReserve` hold remains on the (now-orphaned, non-consumer-protected) contract account, with no remaining code path in the contracts pallet that will ever revisit or release it.

The precondition is that the contract account must have a competing freeze/lock/hold recognized by `reducible_total_balance_on_hold(..., Polite)` at the moment of `terminate`. I was not able to fully verify, within the available tool budget, a concrete unprivileged extrinsic/XCM/contract-call path that lets an attacker place such a freeze on the *contract's own account* (as opposed to the caller's/origin's account) before invoking `terminate`. Candidate vectors (not confirmed) would require the contract itself, acting as its own signed origin (e.g., via `seal_call_runtime`/`call_runtime` host functions subject to `CallFilter`), to dispatch a call that places a `fungible::MutateFreeze` lock or another pallet's `hold` reason on itself (e.g., vesting, staking bonding, NFT reserve) prior to self-terminating. I could not confirm within the available budget whether the default `CallFilter` in the reference runtimes permits such calls from contract-origin dispatch, nor whether contracts pallet's `terminate` performs any pre-check against `reducible_total_balance_on_hold` before allowing termination to proceed — I did not get to inspect `exec.rs`'s `terminate` implementation before running out of iterations. This is the critical unresolved piece: if `terminate` (or the runtime's call filter) already forbids acquiring other holds/freezes on contract accounts, this finding is not exploitable in practice, even though the `ReservingExt::charge` logic itself contains the accounting gap described.

### Impact Explanation
If reachable, the impact is a "stranded" residual `StorageDepositReserve` hold on a terminated, consumer-decremented contract account. The user who paid the deposit does not get a full refund, and the funds are not recoverable through any documented contracts-pallet flow, breaking the invariant that the storage deposit is a temporary, fully-recoverable hold. However, the funds are not "lost" from total issuance — they are diverted from the depositor to being stuck in the residual account under a hold, which is a stranding/accounting-correctness bug rather than an ability to mint or steal foreign assets.

### Likelihood Explanation
Likelihood hinges entirely on the unconfirmed precondition: whether an attacker (as the contract, via a permitted `call_runtime`/chain-extension dispatch, or via some other pallet interaction) can place a freeze/hold on the contract's own account that is recognized by `reducible_total_balance_on_hold` under `Fortitude::Polite`, and whether `terminate` lacks a guard against this. Without confirming this reachability, the likelihood cannot be assessed as concrete/high; the vulnerable *accounting logic* in `ReservingExt::charge` exists and is real, but the missing piece is a demonstrated attacker-controlled trigger for the precondition.

### Recommendation
- In `ReservingExt::charge`'s refund branch, treat `transferred < *amount` as a hard failure (return `Error::<T>::StorageRefundNotEnoughFunds`/`StorageRefundLocked`) instead of only logging, so that termination aborts (or is rolled back) rather than proceeding to `dec_consumers` and sweeping the account.
- Alternatively/additionally, have `terminate` (in `exec.rs`) proactively check `reducible_total_balance_on_hold(contract, Polite) >= info.total_deposit()` before allowing termination, or use `Fortitude::Force` for the refund `transfer_on_hold` for the specific `StorageDepositReserve` reason so it is not blocked by unrelated freezes, since this hold is a contracts-pallet-internal accounting mechanism, not a user-imposed lock that should block refunds.
- Confirm and, if necessary, restrict via `CallFilter`/config whether a contract's own account can acquire other pallets' freezes/holds while it is an active contract, to preserve the assumption that `ContractInfo.total_deposit()` fully characterizes the account's held balance.

### Proof of Concept
Rust unit/integration test plan (in `substrate/frame/contracts/src/tests.rs` or a new `storage/meter.rs` test using the real `Balances` pallet instead of `TestExt`):
1. Instantiate a contract `C` with `Alice` as depositor; storage deposit reserved under `HoldReason::StorageDepositReserve` on `C`'s account.
2. Externally (or via a confirmed contract-callable dispatch, if one is found) place a `Balances::set_freeze`/other-hold on `C`'s account for an amount that reduces `reducible_total_balance_on_hold(C, Polite)` below `info.total_deposit()`.
3. Call `terminate` on `C` (contract self-destructs to `beneficiary`).
4. Assert:
   - Either the call fails with `Error::<T>::StorageRefundNotEnoughFunds` (expected fix), OR
   - Under current code: `Balances::balance_on_hold(&HoldReason::StorageDepositReserve.into(), &C) > 0` after termination (bug reproduced — stranded hold), together with `System::consumers(&C) == 0` (consumer already decremented) and `C`'s account no longer tracked by the contracts pallet, proving the residual hold is now orphaned and unrecoverable through any contracts extrinsic.
