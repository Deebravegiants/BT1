## Finding: Vault request-authorization can be permanently "burned" via the replay guard before owner-binding validation completes

This maps cleanly onto the reported bug class: a piece of persistent state (`inAuction` in the Arcadia report; here, the replay-guard's "seen" map) is written as a side effect of an operation that can still fail a later validation step, and that state is never rolled back on failure — permanently blocking the legitimate operation identified by that state key.

### Title
Replay guard records a request digest as "seen" before owner-ownership validation completes, permanently burning that digest on failure - (File: `core/capabilities/vault/authorizer.go`)

### Summary
`authorizer.AuthorizeRequest` records a request's digest in the `RequestReplayGuard` immediately after the underlying auth mechanism (allowlist or JWT) succeeds, but *before* it validates that the request's payload owner actually matches the authorized owner. If that later owner-binding check fails, the function returns an error, but the digest has already been permanently recorded as "seen" for the duration of `authResult.ExpiresAt()`.

### Finding Description [1](#0-0) 

The sequence is:
1. `authorizeRequest` succeeds and returns an `AuthResult` (owner + digest + expiry) — this only proves the *caller* is authorized for that digest, not that the *request content* belongs to that caller.
2. `a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt())` unconditionally records the digest as seen.
3. `validateSecretOwnersMatchAuthorized(req, authResult.AuthorizedOwner())` is only checked *after* step 2, and can fail (e.g., request params reference a different owner than the one just authorized). [2](#0-1) 

`validateSecretOwnersMatchAuthorized` compares the `Owner` field embedded in the request params (`CreateSecretsRequest`, `UpdateSecretsRequest`, `DeleteSecretsRequest`, `ListSecretIdentifiersRequest`) against `authResult.AuthorizedOwner()`. This is exactly the "solvent-check revert" analog: the state-mutating step (`CheckAndRecord`) happens unconditionally, while the correctness check that can revert the whole operation happens afterward, with no rollback of the already-recorded state. [3](#0-2) 

`RequestReplayGuard.CheckAndRecord` has no corresponding "unrecord"/rollback method — once a digest is recorded, it stays recorded until its expiry elapses, unconditionally.

Because the digest is a `req.Digest()` derived purely from method/params/id — not tied to the caller's identity — any unprivileged caller who can obtain *any* valid authorization for a chosen digest (e.g., by self-registering an on-chain `WorkflowRegistryOwnerAllowlistedRequest` entry, or minting a JWT with an `authorization_details` digest claim for their own org) can pre-record that exact digest in the shared replay guard by submitting a request whose payload params intentionally target a different (victim) owner. The request will fail the owner-binding check and return an error to the caller, but the digest is already burned. If a legitimate workflow later issues that same request content (same method/params/id — which is realistic for idempotent, deterministically-derived request IDs used by CRE workflows, as reflected in the codebase's own replay-guard/idempotency test comments), it is rejected with `ErrRequestAlreadySeen`, even though it was never actually processed.

### Impact Explanation
An unprivileged actor can grief a specific vault request identity (secrets create/update/delete/list for a particular owner+namespace+key) by pre-consuming its replay-guard slot with a request engineered to fail owner validation. The victim's subsequent legitimate call for that same request digest is rejected as a "replay" and never executed, for up to the attacker-chosen expiry window. This is a request/fund-flow denial-of-service against a specific caller's vault operation, directly analogous to the "user can prevent liquidation" pattern: a security-relevant state flag is set unconditionally before a subsequent validity check that can revert, and there is no cleanup path.

### Likelihood Explanation
Requires the attacker to know or predict the exact request digest (method + params + id) that a target workflow will eventually submit, and to be able to obtain their own valid authorization for that same digest (self-registered allowlist entry or self-minted JWT claim referencing that digest). This is plausible where request IDs are deterministic/idempotent per workflow execution (a documented design goal in this codebase), lowering the bar significantly for a targeted griefing attack, though it is not a fully generic every-request DoS.

### Recommendation
Perform `validateSecretOwnersMatchAuthorized` (and any other request-content validation that can fail) *before* calling `replayGuard.CheckAndRecord`, so the replay guard is only updated once the request is fully validated and about to be treated as authorized. Alternatively, add a rollback/`Unrecord` path in `RequestReplayGuard` that is invoked whenever a post-record validation step fails.

### Proof of Concept
1. Attacker crafts a `vault.secrets.list` (or create/update/delete) JSON-RPC request whose `params` field sets `Owner` to a known victim workflow owner address, using a request `id`/content identical to what the victim's workflow will deterministically submit.
2. Attacker obtains their own valid authorization for this exact digest — e.g., by calling the on-chain `WorkflowRegistry` to add a `WorkflowRegistryOwnerAllowlistedRequest{RequestDigest: Digest(maliciousReq), Owner: attacker, ExpiryTimestamp: farFuture}` [4](#0-3) , or by minting a JWT with an `authorization_details` claim referencing that digest for their own org.
3. Attacker sends the crafted request through the gateway. `authorizeRequest` succeeds (attacker's own authorization is valid for that digest); `replayGuard.CheckAndRecord` records the digest as seen; `validateSecretOwnersMatchAuthorized` then fails because `listReq.Owner` (victim) != `authResult.AuthorizedOwner()` (attacker), and the request is rejected with an owner-mismatch error — but the digest is now burned.
4. When the victim's workflow later submits the legitimate identical request, `replayGuard.CheckAndRecord` returns `ErrRequestAlreadySeen` [5](#0-4) , and the victim's genuine vault operation is denied until the attacker-controlled expiry passes.

```go
func (a *authorizer) AuthorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	authResult, err := a.authorizeRequest(ctx, req)
	if err != nil {
		return nil, err
	}
	if authResult == nil {
		err = errors.New("auth mechanism returned nil auth result")
		a.lggr.Errorw("auth mechanism returned nil auth result", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "")
		return nil, err
	}
	if err := a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt()); err != nil {
		a.lggr.Debugw("replay guard rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "", "error", err)
		return nil, err
	}
	if ownerErr := validateSecretOwnersMatchAuthorized(req, authResult.AuthorizedOwner()); ownerErr != nil {
		a.lggr.Errorw("owner binding rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "hasAuth", req.Auth != "", "error", ownerErr)
		return nil, ownerErr
	}
	a.lggr.Debugw("request authorized", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "")
	return authResult, nil
}
```

```go
// validateSecretOwnersMatchAuthorized checks that secret identifiers in the request payload
// match the authorized workflow owner. This is read-only validation; owner prefixing and
// param stamping happen later in GatewayVaultRequestProcessor.
func validateSecretOwnersMatchAuthorized(req jsonrpc.Request[json.RawMessage], workflowOwner string) error {
	switch req.Method {
	case vaulttypes.MethodPublicKeyGet:
		return nil
	case vaulttypes.MethodSecretsCreate:
		if req.Params == nil {
			return errors.New("request params must not be nil")
		}
		var createReq vaultcommon.CreateSecretsRequest
		if err := json.Unmarshal(*req.Params, &createReq); err != nil {
			return err
		}
		return validateEncryptedSecretOwnerMismatch(createReq.EncryptedSecrets, workflowOwner)
	case vaulttypes.MethodSecretsUpdate:
		if req.Params == nil {
			return errors.New("request params must not be nil")
		}
		var updateReq vaultcommon.UpdateSecretsRequest
		if err := json.Unmarshal(*req.Params, &updateReq); err != nil {
			return err
		}
		return validateEncryptedSecretOwnerMismatch(updateReq.EncryptedSecrets, workflowOwner)
	case vaulttypes.MethodSecretsDelete:
		if req.Params == nil {
			return errors.New("request params must not be nil")
		}
		var deleteReq vaultcommon.DeleteSecretsRequest
		if err := json.Unmarshal(*req.Params, &deleteReq); err != nil {
			return err
		}
		return validateSecretIdentifierOwnerMismatch(deleteReq.Ids, workflowOwner)
	case vaulttypes.MethodSecretsList:
		if req.Params == nil {
			return errors.New("request params must not be nil")
		}
		var listReq vaultcommon.ListSecretIdentifiersRequest
		if err := json.Unmarshal(*req.Params, &listReq); err != nil {
			return err
		}
		if vaultutils.NormalizeOwner(listReq.Owner) != vaultutils.NormalizeOwner(workflowOwner) {
			return fmt.Errorf("list secrets owner %q does not match authorized workflow owner %q", listReq.Owner, workflowOwner)
		}
		return nil
	default:
		return fmt.Errorf("owner validation not implemented for method %q", req.Method)
	}
```

```go
// CheckAndRecord returns ErrRequestAlreadySeen if the digest was previously
// recorded and has not yet expired. Otherwise it records the digest with
// the given expiry timestamp (unix seconds, UTC).
//
// Expired entries are cleaned up on every call.
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
```

```go
func TestAuthorizer_RejectsAllowListBasedAuthReplay(t *testing.T) {
	allowListBasedAuth := vaultmocks.NewAuthorizer(t)
	// Use a method without secret identifiers so the owner-binding check is a no-op.
	req := jsonrpc.Request[json.RawMessage]{ID: "1", Method: vaulttypes.MethodPublicKeyGet}
	allowListBasedAuth.EXPECT().AuthorizeRequest(mock.Anything, req).Return(vault.NewAuthResult("", "0xabc", "digest-1", time.Now().Add(time.Minute).Unix()), nil).Twice()

	a := vault.NewAuthorizer(allowListBasedAuth, nil, logger.TestLogger(t))

	authResult, err := a.AuthorizeRequest(t.Context(), req)
	require.NoError(t, err)
	require.Empty(t, authResult.OrgID())
	require.Equal(t, "0xabc", authResult.WorkflowOwner())
	require.Equal(t, "0xabc", authResult.AuthorizedOwner())

	authResult, err = a.AuthorizeRequest(t.Context(), req)
	require.Nil(t, authResult)
	require.ErrorIs(t, err, vault.ErrRequestAlreadySeen)
}
```
