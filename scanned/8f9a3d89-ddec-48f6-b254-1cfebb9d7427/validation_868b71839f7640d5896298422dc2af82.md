### Title
Fixed compile-time ChainId in EIP-712 domain separator for ERC20 permit precompile enables signature replay across chain forks/renumbering - (File: substrate/frame/assets/precompiles/src/permit.rs)

### Summary
The `pallet-assets-precompiles` EIP-2612 permit implementation computes its EIP-712 domain separator using `T::ChainId::get()`, a `#[pallet::constant]` fixed at compile/config time, exactly mirroring the vulnerable pattern in the EQLC/Blacksmith report where `chainId_` is baked into the domain separator at construction and can never be updated if the chain's actual identity changes.

### Finding Description
`compute_domain_separator` builds the EIP-712 domain separator using a chain ID pulled from `T::ChainId: Get<u64>`, a pallet-level constant: [1](#0-0) [2](#0-1) 

This value is not derived dynamically from the live runtime/chain state (e.g. from `frame_system` genesis hash, spec version, or an actual EVM `chain_id` opcode/host function analog) — it is a static constant configured once in the runtime's `impl permit::Config for Runtime` block. Once deployed, this constant cannot be changed without a runtime upgrade, and there is no on-chain mechanism (analogous to Substrate's `frame_system::CheckGenesis`/`CheckSpecVersion` transaction extensions, which regenerate replay-protection material from live chain state on every extrinsic) that ties the permit's chain identity to the chain's current state.

This is structurally identical to the reported EQLC/Blacksmith issue: `DOMAIN_SEPARATOR` is computed once from a `chainId_` value fixed at deployment time (`constructor(uint256 chainId_)`), and if the chain undergoes a hard fork (or, in the Substrate/parachain analog, if a chain is spun off, renumbered, or two networks end up sharing the same configured `ChainId` constant — e.g. via a testnet/mainnet template reuse, chain fork, or migration), signatures for `permit()` remain valid and replayable on both resulting chains because the domain separator baked into the pallet never changes.

Note: standard Substrate extrinsics are properly protected against this class of replay via `frame_system::CheckGenesis` and `frame_system::CheckSpecVersion` transaction extensions, which bind every signed extrinsic to the live genesis hash and spec version: [3](#0-2) 
However, the EIP-2612 `permit()` precompile path bypasses this protection entirely — it is a self-contained EIP-712/ECDSA verification scheme with its own domain separator that does not consult `frame_system`'s genesis hash or any dynamically-updatable chain identifier.

### Impact Explanation
If two chains ever end up configured with (or diverge while retaining) the same `permit::Config::ChainId` value and the same verifying-contract address/asset ID/token name — a realistic scenario for parachain forks, testnet forks, chain migrations, or genesis config reuse across networks — a previously-issued `permit` signature authorizing a spender to move a user's asset allowance is valid and replayable on both chains. An attacker (the `spender` from an old permit) can call `permit()` and then `transferFrom` on both chains to drain the owner's approved allowance twice, effectively doubling the value extracted from a single signature.

### Likelihood Explanation
Likelihood is contingent on an actual chain-identity-changing event (fork, network split, or runtime/config reuse across networks) occurring after deployment, which is not routine for Polkadot/Kusama-style relay chains but is a real risk in parachain ecosystems (testnets frequently reset/fork, and runtimes/configs are commonly cloned across chains for new parachain launches). This matches the original report's classification as informational/configuration risk of "High" difficulty rather than a directly exploitable bug under normal operation — it requires an external chain-identity event, not attacker-controlled input alone, to become exploitable.

### Recommendation
Either (a) detect the live chain identity dynamically (e.g., derive from `frame_system::block_hash(0)` genesis hash instead of, or in addition to, a static `Get<u64>` constant, and cache/regenerate the domain separator when it changes), or (b) include the dynamic chain identifier directly in the EIP-712 struct hash passed into `permit()` rather than folding it only into a cached domain separator. Document the chain-fork/config-reuse risk for parachain teams deploying `pallet-assets-precompiles` and provide guidance on assigning globally unique `ChainId` constants per network.

### Proof of Concept
1. Deploy Runtime A with `impl permit::Config for RuntimeA { type ChainId = ConstU64<1000>; ... }`.
2. Alice signs a permit approving Bob to spend her ERC-20 asset balance; the digest is computed via `permit_digest` using `compute_domain_separator` bound to `ChainId = 1000`: [4](#0-3) 
3. A second chain (Runtime B — e.g., a forked testnet, or a new parachain that copied the runtime config without changing `ChainId`) is deployed with the same `ChainId = 1000` constant and the same verifying-contract address/asset ID/name.
4. Bob submits Alice's original signature to Runtime B's `permit()` precompile call; `use_permit`/`do_verify_permit` recomputes the identical digest (since `ChainId`, `verifying_contract`, and `name` all match) and the signature verifies successfully, letting Bob obtain approval and drain Alice's balance on Runtime B as well: [5](#0-4)

		/// Compute the EIP-712 domain separator for a given verifying contract.
		///
		/// DOMAIN_SEPARATOR = keccak256(abi.encode(
		///   keccak256("EIP712Domain(string name,string version,uint256 chainId,address
		/// verifyingContract)"),
		///   keccak256(name),
		///   keccak256("1"),
		///   chainId,
		///   verifyingContract
		/// ))
		///
		/// The `name` parameter should be the token name per EIP-2612 specification.
		pub fn compute_domain_separator(verifying_contract: &H160, name: &[u8]) -> H256 {
			let name_hash = keccak_256(name);
			let version_hash = keccak_256(b"1");
			let chain_id = T::ChainId::get();

			// Encode: typehash || name_hash || version_hash || chainId || verifyingContract
			let mut data = Vec::with_capacity(DOMAIN_SEPARATOR_ENCODED_LEN);
			data.extend_from_slice(&DOMAIN_TYPEHASH);
			data.extend_from_slice(&name_hash);
			data.extend_from_slice(&version_hash);
			// Pad chain_id to 32 bytes (big-endian)
			data.extend_from_slice(&[0u8; 24]);
			data.extend_from_slice(&chain_id.to_be_bytes());
			// Pad address to 32 bytes
			data.extend_from_slice(&[0u8; 12]);
			data.extend_from_slice(verifying_contract.as_bytes());

			H256(keccak_256(&data))

			name: &[u8],

			nonce: &U256,

			data.extend_from_slice(struct_hash.as_bytes());

		}
