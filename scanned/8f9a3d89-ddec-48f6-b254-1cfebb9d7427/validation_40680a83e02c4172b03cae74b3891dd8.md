### Title
Deployment nonce is rolled back on constructor revert in `pallet-revive`, diverging from real EVM CREATE nonce semantics - (`substrate/frame/revive/src/exec.rs`)

### Summary
`pallet-revive` implements EVM-compatible contract creation (`CREATE`/`CREATE2`) with `create1`/`create2` address derivation identical to Ethereum's. However, its handling of the deployer's nonce on a failed/reverted child-contract constructor mirrors the zkSync Era model described in the report rather than genuine EVM behavior: the nonce increment is undone when the instantiation frame fails, whereas on real Ethereum the nonce increments permanently as soon as `CREATE` begins, regardless of whether the child constructor succeeds.

### Finding Description
In `execute_top_frame`/`run_instantiate` (`substrate/frame/revive/src/exec.rs:1355-1363`), the nonce of both the new contract account and (for `bump_nonce`/nested frames) the caller is incremented via `<System<T>>::inc_account_nonce(...)` **before** the constructor code is executed: [1](#0-0) 

This looks superficially like the EVM model (increment at CREATE start), but the whole instantiate/call execution runs inside a nested storage transaction that is rolled back on frame failure (`with_transient_storage_mut`/transactional frame handling around lines 1319-1330, and the broader `run_instantiate` transactional wrapper), so any storage write performed inside a failed frame — including the `inc_account_nonce` call — is undone.

This is confirmed directly by the pallet's own unit test `nonce()`: [2](#0-1) 

The comment "fail should not increment" and the assertion `System::account_nonce(&ALICE) == 0` after a failed instantiate prove that a reverted child-contract constructor rolls back the deployer's nonce — exactly the zkSync Era behavior criticized in the report as diverging from real EVM/Geth semantics (where `CREATE` bumps the nonce before the snapshot, and the increment survives a revert).

Address derivation for `CREATE` (`create1`) uses this same nonce and is EVM-bytecode-compatible: [3](#0-2) [4](#0-3) 

And the EVM `CREATE`/`CREATE2` opcode handler in the interpreter falls through to the same `instantiate` path, so a reverted child constructor (`did_revert()`) simply returns `0` on the stack without any special-case nonce handling to emulate persistent EVM nonce bump: [5](#0-4) 

So a Solidity/EVM factory contract deployed on a `pallet-revive` chain that does low-level `create`/`create2` and predicts child addresses via `nonce`/`keccak256(rlp(deployer, nonce))` will observe non-EVM-equivalent behavior: after a failed child deployment, the "next" predicted address (computed assuming EVM's persisting nonce bump) will not match the actually deployed address, and instead the previously-predicted (but unused) address will be reused for the next successful deployment — the same address-collision/desync pattern demonstrated in the zkSync PoC.

### Impact Explanation
Any EVM-ported factory contract (proxy factories, CREATE2 deployers that track/predict nonces manually, deterministic multi-chain deployment tooling) ported to `pallet-revive` under the assumption of full EVM CREATE-nonce equivalence will get incorrect address predictions after a failed child instantiation. This can lead to:
- Reused/aliased addresses for unrelated child contracts (address collision between the "intended next deployment" and an unrelated failed one), potentially allowing the deployer or an attacker who can force a revert in someone else's factory-driven deployment sequence to redirect a predicted proxy address to a different contract than intended.
- Cross-chain address desynchronization for CREATE2/CREATE-based deterministic deployment systems that assume identical nonce progression between real Ethereum and revive-based chains.

This matches the "Medium, implementation-reliant, high impact in specific factory-pattern scenarios" categorization given to the original zkSync finding.

### Likelihood Explanation
Any unprivileged user can trigger this by simply causing a child constructor to revert (e.g., insufficient value, a `require` failure, out-of-gas child constructor) inside a factory's `CREATE`/`CREATE2` sequence — no privileged role or trusted party is needed. The bug is deterministic and reachable from ordinary contract calls, but only manifests as an exploitable issue for contracts that specifically rely on EVM-consistent, persisting nonce increments for address prediction (a known but not universal factory pattern), which is why the severity is scenario-dependent rather than universally critical, consistent with the judge's Medium rating in the original report.

### Recommendation
Decide and document explicit EVM-compatibility semantics for `pallet-revive`'s deployer nonce on constructor revert:
- Either persist the nonce increment outside of the reverted storage transaction (e.g., perform `inc_account_nonce` in a scope that is not rolled back with the rest of the failed frame, similar to how real EVM snapshots exclude the nonce bump), to match Ethereum's actual `CREATE` semantics, or
- Clearly document in `pallet-revive`'s EVM-compatibility notes that nonce-based address prediction across a failed child deployment is **not** EVM-equivalent, so factory-contract authors/tooling authors are aware and can avoid relying on it.
Given `ExecConfig::bump_nonce`'s existing nuanced handling of nonce semantics (`substrate/frame/revive/src/primitives.rs:428-447`), this would fit naturally as an additional documented deviation, but if true EVM parity is a design goal for `pallet-revive`, the rollback-on-revert of the nonce increment should be fixed to increment-and-persist regardless of the frame's outcome.

### Proof of Concept
The existing unit test in the repo itself demonstrates the divergence: [6](#0-5) 

Specifically:
1. `fail_code` constructor always traps (`exec_trapped()`).
2. `MockStack::run_instantiate(ALICE, fail_executable, ...)` is called and fails.
3. `assert_eq!(System::account_nonce(&ALICE), 0)` — the nonce remains unchanged after the failed instantiate, confirming the rollback behavior described above, which is the same behavior flagged as a medium-severity EVM-non-equivalence issue in the zkSync Era report.

Note: I was unable to fully trace the exact `with_transaction`/`TransactionOutcome` call site in `exec.rs` that performs the rollback (search matched but I couldn't retrieve the specific line numbers before running out of tool calls), so the precise mechanism of the rollback (frame-level transactional wrapper vs. `frame_support::storage::with_transaction`) should be verified by a follow-up read of `substrate/frame/revive/src/exec.rs` around the `run_instantiate`/frame execution functions; the *effect* (nonce rollback on failure) is however conclusively demonstrated by the cited test.

/// Determine the address of a contract using CREATE semantics.
pub fn create1(deployer: &H160, nonce: u64) -> H160 {
	let mut list = rlp::RlpStream::new_list(2);
	list.append(&deployer.as_bytes());
	list.append(&nonce);
	let hash = keccak_256(&list.out());
	H160::from_slice(&hash[12..])
}
