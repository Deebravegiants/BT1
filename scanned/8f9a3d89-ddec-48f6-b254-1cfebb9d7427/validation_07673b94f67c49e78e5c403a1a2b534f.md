Explanation: The reported issue is specific to OpenZeppelin's `safeApprove`, which reverts if the current allowance is non-zero when setting a new non-zero value. In this codebase, the equivalent ERC-20 precompile `approve`/`permit` logic in [1](#0-0)  explicitly calls `do_cancel_approval` to clear any existing non-zero allowance before setting a new one, avoiding the exact "increment on top of nonzero allowance reverts" failure mode described in the Tapioca report. There is also no `convertRate`-style rounding-down step between approval and consumption in the `pallet-assets` approval/transfer path — `do_transfer_approved` in [2](#0-1)  deducts the exact `amount` from the approved amount via `checked_sub`, with no rate conversion or rounding that could leave an un-consumable remainder in the allowance itself. The vendored `ERC20.sol` fixture in [3](#0-2)  also uses direct overwrite semantics (`_allowances[owner][spender] = value`) rather than `safeApprove`'s revert-on-nonzero pattern. No reachable attacker-controlled path reproduces the Balancer `_routerSwap` root cause (approve-without-clearing + rate-based rounding leaving a nonzero remainder that blocks the next `safeApprove`) in this repository's in-scope FRAME/precompile code.
