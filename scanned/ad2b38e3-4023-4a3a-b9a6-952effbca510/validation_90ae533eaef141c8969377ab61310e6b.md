### Title
Nonzero-value `CALL`/`transfer()`/`send()` bypasses the stipend reentrancy guard (`AllowNext`), always downgrading to `AllowReentry` - (File: `substrate/frame/revive/src/vm/evm/instructions/contract.rs`)

### Summary
In `run_call`, the match that selects the reentrancy mode is ordered so that **any** call with `value != 0` is unconditionally routed to `ReentrancyProtection::AllowReentry`, regardless of `gas_limit`. This means the classic Solidity `.transfer(amount)`/`.send(amount)` reentrancy guard — which relies on the callee receiving only the 2300-gas stipend and therefore being unable to perform meaningful state-changing reentrant calls — never receives the `AllowNext` protection that pallet-revive itself created specifically to compensate for "gas scale differences" between EVM gas and revive weight.

### Finding Description
`run_call` computes `(add_stipend, reentrancy)` via: [1](#0-0) 

The match arms are evaluated top-down against `(value.is_zero(), gas_limit == CALL_STIPEND)`:
- `(false, _) => AllowReentry` — this arm matches **every** call where `value != 0`, irrespective of the second tuple element (i.e., irrespective of `gas_limit`).
- `(_, true) => AllowNext` — only reachable when `value.is_zero() == true`.
- `(_, _) => AllowReentry` — zero-value, non-stipend gas.

Because arm 1 is matched first and ignores `gas_limit` entirely, the `AllowNext` branch is structurally unreachable for any nonzero-value call — including the exact case the developers documented as needing it. Per `prdoc/stable2603/pr_11227.prdoc`, solc's `target.transfer(amount)`/`target.send(amount)` with `amount > 0` emit `gas_limit = 0` on the stack (the EVM runtime itself adds the 2300 stipend), while only the *zero*-value variants (`transfer(0)`/`send(0)`) explicitly push `gas_limit = 2300`. The `AllowNext` heuristic in this code only recognizes the latter (`value.is_zero() && gas_limit == 2300`), so the real, common `.transfer(amount>0)` pattern falls into `AllowReentry`.

`add_stipend = true` does cap the requested Ethereum gas by adding only the stipend-equivalent weight (see `substrate/frame/revive/src/metering/math.rs`, `ethereum_execution::new_nested_meter`, `CallResources::Ethereum { gas, add_stipend }` branch — `gas_limit = SignedGas::from_ethereum_gas(*gas) + stipend_weight` when `*gas` is 0). This does limit compute budget somewhat, but the `AllowReentry` mode never sets `self.top_frame_mut().allows_reentry = false` in `Stack::call` (`substrate/frame/revive/src/exec.rs:2167-2192`), so the caller's frame remains fully open to reentry by the callee. Additionally, an attacker who issues the raw `CALL` opcode directly (rather than through solc's `.transfer`) can pass an arbitrary `gas_limit` (not 0, not 2300) together with `value != 0`; since arm 1 does not condition on `gas_limit` at all, the callee then receives `min(remaining_gas, gas_limit + stipend)` — potentially close to the caller's entire remaining gas budget — while still getting the fully-open `AllowReentry` mode. There is no code path that forces `AllowNext` for any nonzero-value transfer.

The `AllowNext` design itself exists precisely because "due to gas scale differences that guarantee does not automatically hold in revive and we enforce it explicitly here" (comment on `ReentrancyProtection::AllowNext`, `substrate/frame/revive/src/exec.rs:134-141`) — i.e., the developers recognized that stipend-sized weight in revive might still be enough for a callee to make a further state-changing call, unlike genuine EVM gas. That explicit enforcement is missing for the value-transfer case.

### Impact Explanation
Any Solidity contract compiled to pallet-revive's EVM bytecode target that uses `.transfer(amount)` or `.send(amount)` for its reentrancy defense (an extremely common pattern for withdrawal-style logic) does not get the intended stipend-based reentrancy lockout. If the callee (an attacker-controlled contract or EOA-fallback) can, within stipend-equivalent revive weight, execute a `CALL` back into the caller, it can reenter the caller mid-execution — before the caller's own storage/state updates (e.g., balance zeroing) are finalized — enabling double-spend/drain-style reentrancy against contracts that assumed `.transfer`/`.send` semantics carried over from Ethereum. This is a contract-execution/accounting integrity issue reachable purely from attacker-controlled contract code, matching the "contract call context must only execute through intended routes with correct accounting" invariant.

### Likelihood Explanation
- Preconditions: a victim contract deployed under pallet-revive's EVM-bytecode mode (`Code::Upload`, gated by `AllowEVMBytecode`) uses `.transfer(amount)`/`.send(amount)` to pay out to a caller-supplied/attacker-controlled address, and does not additionally follow the checks-effects-interactions pattern.
- Attacker action: deploy a malicious receiving contract whose fallback/`receive()` performs a reentrant call back into the victim; trigger the victim's payout path (e.g., a withdrawal function) as an ordinary externally-owned account transaction.
- No signature/origin/proxy/multisig checks are relevant or bypassed — the exploit occurs entirely within the EVM interpreter's reentrancy-mode selection, which is a design/logic gap, not an authorization bypass. It is reachable with any account able to submit a normal `eth_call`-style transaction. Whether it is *practically* exploitable per-victim-contract depends on whether the stipend-equivalent weight the callee is granted happens to be enough to perform a state-mutating call in that specific victim's function; this needs a repeatable weight-budget measurement, which the analysis could not fully quantify from static code alone (would require running the fixture-based test harness).

### Recommendation
Change the `run_call` heuristic so that the stipend/`AllowNext` classification is based on whether the *actual* gas granted to the callee is stipend-limited, not on `value.is_zero()`. Concretely, detect the stipend pattern independent of `value`: if `gas_limit == 0` (EVM's implicit-stipend convention for value transfers) or `gas_limit == CALL_STIPEND` (explicit convention for zero-value transfer/send), apply `ReentrancyProtection::AllowNext` and `add_stipend = true`, regardless of whether `value` is zero. Only route to `AllowReentry` when the caller genuinely forwards more than the stipend amount of gas.

### Proof of Concept
Rust integration test (extending `substrate/frame/revive/src/tests/stipends.rs`):
1. Deploy a `Victim` EVM contract with a `withdraw()` function that: reads `balances[msg.sender]`, calls `msg.sender.transfer(balances[msg.sender])`, then sets `balances[msg.sender] = 0` (classic vulnerable ordering).
2. Deploy an `Attacker` EVM contract whose `receive()`/fallback calls back into `Victim.withdraw()`.
3. Fund `Victim` with more than one `Attacker` balance entry's worth of ETH-equivalent; credit `Attacker` a balance in `Victim`.
4. Call `Attacker.attack()` which calls `Victim.withdraw()`.
5. Assert that `Victim`'s balance-mapping is *not* re-read/reentered more than once before it is zeroed (i.e., assert final Victim on-chain balance == expected single-withdrawal balance, not drained multiple times), and instrument/assert that during the nested `run_call`, `reentrancy == ReentrancyProtection::AllowNext` (not `AllowReentry`) whenever `gas_limit == 0 && value != 0`.
6. Expected (post-fix) assertion: reentrant `Victim.withdraw()` call from `Attacker.receive()` fails with `Error::ReentranceDenied`; expected (current/bug) result: reentrant call succeeds, draining more than the credited balance.
