### Title
Verifier-signature replay across re-created crowdloans for the same ParaId due to missing fund-instance binding in signed payload - (File: polkadot/runtime/common/src/crowdloan/mod.rs)

### Summary
`Pallet::do_contribute` builds the verifier-signature payload as `(index, &who, old_balance, value)` [1](#0-0) , where `index` is the `ParaId` and `old_balance` is read live from the child-trie contribution storage. Because the payload contains no fund-instance identifier (`fund.fund_index`), a signature captured for one crowdloan campaign on a `ParaId` remains valid for a *later, independently created* crowdloan on the same `ParaId` once the contributor's on-chain balance is reset to the same value (e.g. `0`) via `withdraw`/`dissolve`+`create`.

### Finding Description
The permissioned-crowdloan gate only checks that `signature.verify(payload, verifier)` succeeds, where `payload = (index, who, old_balance, value)` and `old_balance` is fetched fresh from `contribution_get(fund.fund_index, &who)` at call time [2](#0-1) . The child-trie key used for contribution storage is derived from `fund.fund_index` (an internal monotonically-increasing counter in `NextFundIndex`) [3](#0-2) , not from the `ParaId` itself. The signed payload, however, only binds to `index` (the `ParaId`), not to `fund.fund_index`.

Exploit flow:
1. Attacker is an allowed contributor for fund #1 on `ParaId = P` and obtains a verifier signature for `(P, who, old_balance=0, value=V)`, then calls `contribute(P, V, sig)` — succeeds, `contribution_get(fund1_index, who) == V`.
2. After the fund ends (`now >= fund.end`), attacker calls `withdraw(who, P)` — permissionless, callable by anyone [4](#0-3) . This kills the child-trie entry, resetting `contribution_get(fund1_index, who)` back to default `0`.
3. Once `fund.raised == 0`, the fund is dissolved via `dissolve` (called by depositor or after `end`) [5](#0-4) , removing the `Funds` entry for `P`.
4. The parachain manager creates a *new* crowdloan for the same `P` via `create`, which allocates a new `fund.fund_index` and (commonly) reuses the same off-chain `verifier` public key [6](#0-5) . `contribution_get(new_fund_index, who)` starts at `0` again since the child-trie key changed.
5. Attacker replays the *originally captured* signature for `(P, who, old_balance=0, value=V)` in `contribute` against the new fund. Since payload verification only checks `(index=P, who, old_balance=0, value=V)` — all of which now match the fresh state — `signature.verify` succeeds and the contribution is accepted **without the verifier ever approving the new campaign**.

This works because the signature is not bound to the specific fund instance (no `fund.fund_index`, fund creation block, or other per-campaign nonce in the payload), only to a `(ParaId, account, current-balance, value)` tuple that can recur once contributions are reset via legitimate `withdraw`/`dissolve`/`create` lifecycle calls. Note that within a single, still-active fund this replay is blocked, because `do_contribute` requires `now < fund.end` [7](#0-6) , while `withdraw` requires the fund to have already ended [8](#0-7)  — so the exploit only manifests across fund re-creation for the same `ParaId`, not within one fund's lifetime.

### Impact Explanation
An attacker whose participation was approved (signed) for one crowdloan campaign can force acceptance of a contribution to a subsequent, unrelated campaign on the same `ParaId` without the off-chain verifier ever approving them for that campaign — bypassing the permissioned allowlist gate that `fund.verifier` is meant to enforce. This is an unauthorized state change (an unapproved contribution is recorded and funds move into the new fund's pot), matching the scoped impact of "bypassing the permissioned crowdloan allowlist."

### Likelihood Explanation
Requires: (a) `fund.verifier` set (permissioned crowdloan), (b) attacker previously a valid, signed contributor who retains the signature bytes, (c) the crowdloan for the same `ParaId` is later withdrawn-from, dissolved and re-created (a normal, expected lifecycle for parachains that run multiple crowdloan rounds), and (d) the new campaign's verifier key coincidentally/intentionally matches the old one (common in practice, since the same project/off-chain infra typically backs the verifier across rounds) and the replayed `value` happens to not exceed the new fund's cap. All of steps (contribute, withdraw, dissolve, create, contribute) are reachable via plain signed extrinsics with no special privilege beyond being a parachain manager for the `create` step, which is a normal, expected actor in this flow, not an attacker-controlled privileged action. This makes the scenario realistic in real-world serial-crowdloan setups.

### Recommendation
Bind the verifier signature to the specific fund instance rather than just the `ParaId`, e.g. include `fund.fund_index` (and/or fund creation block number) in the signed payload: `(fund.fund_index, index, &who, old_balance, value)`. This ensures a signature is scoped to exactly one crowdloan campaign and cannot be replayed after that fund is dissolved and a new one created for the same `ParaId`.

### Proof of Concept
Rust unit test (extend `polkadot/runtime/common/src/crowdloan/mod.rs` test module):
1. Create fund #1 for `ParaId(1)` with `verifier = V`.
2. Sign payload `(ParaId(1), who, 0, value)` with `V`'s private key -> `sig`.
3. `contribute(ParaId(1), value, Some(sig))` from `who` -> assert `Ok`.
4. Advance blocks past `fund.end`; call `withdraw(who, ParaId(1))` -> assert `Ok`, contribution reset to 0.
5. Ensure `fund.raised == 0`; call `dissolve(ParaId(1))` -> assert `Ok`, fund removed.
6. Recreate fund for `ParaId(1)` with the **same** `verifier = V` (new `fund_index` allocated internally).
7. Replay the same captured `sig` via `contribute(ParaId(1), value, Some(sig))` -> assert this call **succeeds** (`Ok(())`) instead of returning `Error::<T>::InvalidSignature`, demonstrating the bypass. Also assert `Funds::<Test>::get(ParaId(1)).raised == value` to confirm the unauthorized contribution was recorded in the new campaign without a fresh verifier signature.

		pub fn withdraw(
			origin: OriginFor<T>,
			who: T::AccountId,
			#[pallet::compact] index: ParaId,
		) -> DispatchResult {
			ensure_signed(origin)?;

			let mut fund = Funds::<T>::get(index).ok_or(Error::<T>::InvalidParaId)?;
			let now = frame_system::Pallet::<T>::block_number();
			let fund_account = Self::fund_account_id(fund.fund_index);
			Self::ensure_crowdloan_ended(now, &fund_account, &fund)?;

			let (balance, _) = Self::contribution_get(fund.fund_index, &who);
			ensure!(balance > Zero::zero(), Error::<T>::NoContributions);

			CurrencyOf::<T>::transfer(&fund_account, &who, balance, AllowDeath)?;
			CurrencyOf::<T>::reactivate(balance);

			Self::contribution_kill(fund.fund_index, &who);
			fund.raised = fund.raised.saturating_sub(balance);

			Funds::<T>::insert(index, &fund);

			Self::deposit_event(Event::<T>::Withdrew { who, fund_index: index, amount: balance });
			Ok(())
		}

		pub fn dissolve(origin: OriginFor<T>, #[pallet::compact] index: ParaId) -> DispatchResult {
			let who = ensure_signed(origin)?;

			let fund = Funds::<T>::get(index).ok_or(Error::<T>::InvalidParaId)?;
			let pot = Self::fund_account_id(fund.fund_index);
			let now = frame_system::Pallet::<T>::block_number();

			// Only allow dissolution when the raised funds goes to zero,
			// and the caller is the fund creator or we are past the end date.
			let permitted = who == fund.depositor || now >= fund.end;
			let can_dissolve = permitted && fund.raised.is_zero();
			ensure!(can_dissolve, Error::<T>::NotReadyToDissolve);

			// Assuming state is not corrupted, the child trie should already be cleaned up
			// and all funds in the crowdloan account have been returned. If not, governance
			// can take care of that.
			debug_assert!(Self::contribution_iterator(fund.fund_index).count().is_zero());

			// Crowdloan over, burn all funds.
			let _imba = CurrencyOf::<T>::make_free_balance_be(&pot, Zero::zero());
			let _ = frame_system::Pallet::<T>::dec_providers(&pot).defensive();

			CurrencyOf::<T>::unreserve(&fund.depositor, fund.deposit);
			Funds::<T>::remove(index);
			Self::deposit_event(Event::<T>::Dissolved { para_id: index });
			Ok(())
		}
