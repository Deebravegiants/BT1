#No Vulnerability found for this question.

**Analysis summary:**

The described exploit path does not hold up under detailed tracing of `GasMeter::nested`/`absorb_nested` in [1](#0-0) .

Key facts that disprove the claim:

1. **Note the file mismatch**: the question cites `polkadot/xcm/src/v4/traits.rs` as scope, but the function in question (`pallet_contracts::gas::GasMeter`) actually lives in `substrate/frame/contracts/src/gas.rs`, unrelated to XCM v4 traits.

2. **`absorb_nested` runs unconditionally, even on revert.** In `Stack::run` / `pop_frame`, the line `prev.nested_gas.absorb_nested(frame.nested_gas);` executes before the `if !persist { return; }` check [2](#0-1) . This means gas consumed by a reverted nested frame is still charged to the parent — reverting a call does NOT let the caller avoid paying for the work already performed.

3. **`gas_left_lowest()` getter self-corrects via `min(field, gas_left)`.** Since `gas_left` only decreases through `charge` (barring explicit `adjust_gas` refunds), and the getter takes `self.gas_left_lowest.min(self.gas_left)`, the "lowest ever" value is tracked correctly across nested calls without needing an explicit update on every `charge` call.

4. **Manual trace of the exact attack pattern** (repeated `nested(0)` → revert, at various depths, with and without intermediate `charge` calls) shows that `gas_consumed()` at the root after unwinding equals exactly the sum of real `charge` calls performed at any depth — e.g., a 100-unit charge at depth 1 followed by an all-remaining-gas `nested(0)`/immediate-revert at depth 2 yields `gas_consumed() == 100` at the root, with zero drift.

5. There is an existing regression/linearity test confirming this exact scenario is monotonic and bounded by `CallStack` depth: `weight_consumed_is_linear_for_nested_calls` [3](#0-2) , which asserts `gas_max == gas_0 + gas_per_recursion * CALL_STACK_DEPTH`, i.e., gas consumption scales linearly with recursion depth with no drift, exactly contradicting the hypothesized bookkeeping-drift bug.

Because `absorb_nested` always executes (independent of `persist`) and its lowest-gas bookkeeping formula `(self.gas_left + nested.gas_limit).saturating_sub(nested.gas_required())` provably reconstructs the correct pre-call state after unwinding (verified above), there is no mechanism by which nested `weight=0` calls followed by early reverts can inflate reported available gas or let the caller under-report consumed gas. The scoped impact (gas/weight metering bypass) is not realized.

	/// Create a new gas meter by removing gas from the current meter.
	///
	/// # Note
	///
	/// Passing `0` as amount is interpreted as "all remaining gas".
	pub fn nested(&mut self, amount: Weight) -> Self {
		let amount = Weight::from_parts(
			if amount.ref_time().is_zero() {
				self.gas_left().ref_time()
			} else {
				amount.ref_time()
			},
			if amount.proof_size().is_zero() {
				self.gas_left().proof_size()
			} else {
				amount.proof_size()
			},
		)
		.min(self.gas_left);
		self.gas_left -= amount;
		GasMeter::new(amount)
	}

	/// Absorb the remaining gas of a nested meter after we are done using it.
	pub fn absorb_nested(&mut self, nested: Self) {
		self.gas_left_lowest = (self.gas_left + nested.gas_limit)
			.saturating_sub(nested.gas_required())
			.min(self.gas_left_lowest);
		self.gas_left += nested.gas_left;
	}

fn weight_consumed_is_linear_for_nested_calls() {
	let (code, _code_hash) = compile_module("recurse").unwrap();

		let [gas_0, gas_1, gas_2, gas_max] = {

				.map(|i| {

					assert_eq!(
