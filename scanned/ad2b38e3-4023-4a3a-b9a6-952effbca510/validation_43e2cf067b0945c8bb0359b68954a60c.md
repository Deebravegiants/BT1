Based on my investigation, I could not find a valid analog to this vulnerability pattern in the polkadot-sdk codebase.

The Notional Finance bug is rooted in a very specific Solidity design: an array (`trades`) that must be strictly ordered and indexed to match a pool's token index (`trades[i].buyToken == address(tokens[i])`), combined with a separate hardcoded denylist (`_isInvalidRewardToken`) that unconditionally rejects any reward token matching a pool token. This creates a structural conflict when a reward token happens to coincide with a pool constituent token.

I checked the closest architectural analogs in this repo:

- `pallet_asset_rewards` (staking/reward pools) — explicitly supports and tests the case where the staked asset and reward asset are identical (`success_same_assets` test), so there's no equivalent "index-ordered trade array vs. denylist" conflict. [1](#0-0) 

- `pallet_nomination_pools` — reward pool accounting uses a single native currency for both staking and rewards, with no token-index-ordered trade arrays or reward/pool-token overlap logic. [2](#0-1) 

- `pallet_asset_conversion` (AMM/DEX pallet) — swaps operate on an explicit `path: Vec<AssetKind>` supplied by the caller per-call, not on a fixed reward-token reinvestment structure with a hardcoded index-to-pool-token mapping and a separate denylist function that could revert on legitimate overlapping tokens.

		let (mut member, mut bonded_pool, mut reward_pool) =

	}
