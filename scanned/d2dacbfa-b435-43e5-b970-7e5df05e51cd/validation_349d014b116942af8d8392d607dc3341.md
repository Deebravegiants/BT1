Based on my investigation, I found a concrete cross-workflow data leakage bug in the gateway's HTTP action response cache, which is a legitimate analog to the "insufficient policy enforcement... allowed leak of cross-origin data" pattern from CVE-2021-30583 (data intended for one isolation boundary leaking to another).

### Title
Cross-Workflow HTTP Response Cache Data Leakage via Workflow-Owner-Only Cache Key - (File: core/services/gateway/handlers/capabilities/v2/response_cache.go)

### Summary
The gateway's `responseCache` is documented and intended to provide "Workflow Isolation" ("Cache entries are scoped by workflow ID to prevent cross-workflow data leakage") [1](#0-0) , but the actual cache key computed by `OutboundHTTPRequest.Hash()` deliberately excludes `WorkflowID` and keys only on method/URL/headers/body/`WorkflowOwner` [2](#0-1) . This is confirmed by the test explicitly asserting that differing `WorkflowID` values still produce the *same* hash [3](#0-2) .

### Finding Description
`responseCache.Fetch` and `responseCache.Set` both key the cache map by `req.Hash()` [4](#0-3) [5](#0-4) [6](#0-5) . In `makeOutgoingRequest`, the gateway calls `h.responseCache.Fetch(httpCtx, req, callback, req.CacheSettings.Store)` when `MaxAgeMs > 0`, and returns whatever is cached under that hash directly to the requesting node in the response [7](#0-6) . Since the hash does not incorporate `WorkflowID` (only `WorkflowOwner`), any two different workflows belonging to the *same owner address* that issue an identical HTTP action request (same method/URL/headers/body) will read and write the same cache entry. A response fetched and cached on behalf of Workflow A (which could include sensitive response bodies/headers, e.g., `Set-Cookie` tokens as seen being propagated through `MultiHeaders` in the response path [8](#0-7) ) will subsequently be served to Workflow B under that owner without re-fetching, even though the workflows are logically distinct execution contexts with potentially different secrets/credentials embedded in headers.

### Impact Explanation
An owner running multiple workflows can have one workflow's cached HTTP response (potentially containing session tokens, auth headers, or other sensitive response data returned by the external endpoint) served transparently to a different workflow under the same owner. This breaks the documented per-workflow isolation guarantee and can lead to unintended data exposure across workflow boundaries, stale/incorrect data being used by a workflow expecting a fresh response, or a workflow indirectly obtaining response data associated with another workflow's credentials/headers.

### Likelihood Explanation
Medium: the requestor must control (or influence) a workflow under the same owner and know that the responseCache's key omits WorkflowID; since `MaxAgeMs > 0` cache reads are triggered whenever a workflow sets caching, any workflow owner running two workflows that call the same URL/method/headers/body will trigger the collision without any attacker action beyond normal workflow configuration.

### Recommendation
Include `WorkflowID` (in addition to `WorkflowOwner`) in the `OutboundHTTPRequest.Hash()` computation used as the cache key, matching the documented behavior in the README, and update/add tests asserting that different `WorkflowID` values produce different hashes.

### Proof of Concept
1. Owner `0xabc` deploys Workflow A (`WorkflowID = "workflow-123"`) and Workflow B (`WorkflowID = "workflow-456"`), both configured to make an HTTP action `GET https://api.example.com/data` with `CacheSettings.Store=true` and `MaxAgeMs>0`.
2. Workflow A's request executes first; the gateway fetches the response and stores it in `responseCache` keyed by `req.Hash()`, which (per [3](#0-2) ) is identical regardless of `WorkflowID`.
3. Workflow B issues the same request shape; `responseCache.Fetch` finds the existing entry (same hash, since only method/URL/headers/body/owner matter) and returns Workflow A's cached response directly to Workflow B's node — without contacting the external endpoint again — demonstrating cross-workflow response leakage.

func (rc *responseCache) isExpiredOrNotCached(req gateway.OutboundHTTPRequest) bool {
	cachedResp, exists := rc.cache[req.Hash()]
	if !exists || time.Now().After(cachedResp.storedAt.Add(rc.ttl)) {
		return true
	}
	return false
}
