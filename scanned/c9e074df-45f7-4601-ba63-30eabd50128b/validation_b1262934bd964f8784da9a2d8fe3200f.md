### Title
Missing rate limiting/allowlist on user-initiated WebAPI trigger requests enables client-side DoS via unbounded DON fan-out - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The `handler.HandleLegacyUserMessage` function in the WebAPI capabilities gateway handler accepts any correctly-signed trigger request and forwards it to **every member of the DON** without any per-client rate limiting or allowlist check, despite an explicit `// TODO: apply allowlist and rate-limiting here` comment marking the gap.

### Finding Description
`HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go` validates message decoding, checks payload timestamp staleness (`MaxAllowedMessageAgeSec`), and validates the method name, but performs **no rate limiting and no allowlist check** before fanning the request out to `h.donConfig.Members`: [1](#0-0) 

```go
if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) { ... }
// TODO: apply allowlist and rate-limiting here
if msg.Body.Method != MethodWebAPITrigger { ... }
req, err := common.ValidatedRequestFromMessage(msg)
...
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageID] = &savedCallback{...}
don := h.don
h.mu.Unlock()

// Send original request to all nodes
for _, member := range h.donConfig.Members {
	err = errors.Join(err, don.SendToNode(ctx, member.Address, req))
}
```

By contrast, the sibling `handleWebAPIOutgoingMessage` path (node→gateway direction) does enforce a per-node rate limiter: [2](#0-1) 

The `HandlerConfig` struct only exposes a `NodeRateLimiter`, which is applied to node-originated messages, not to `HandleLegacyUserMessage` (the user-facing entry point): [3](#0-2) 

The message-validation logic (`api.Message.Validate`/`ExtractSigner`) only checks that the message is signed by *some* valid ECDSA key and recovers the sender address — it does not check that the sender is a member of an authorized allowlist: [4](#0-3) 

The handler's own test suite acknowledges the gap is untested/unresolved: [5](#0-4) 

This is a direct analog of the reported in3-server issue: a single client-controlled message causes the gateway to perform *N* downstream operations (one `SendToNode` RPC per DON member), and there is no throttling to bound how often a client can trigger this fan-out.

### Impact Explanation
Because the amplification factor is `len(h.donConfig.Members)` per user request and there is no per-sender or global rate limit at this call site, a client capable of producing validly-signed messages (e.g., a compromised or malicious external initiator key, or any key accepted by the deployment's trust model for this handler) can repeatedly submit trigger requests to consume:
- Gateway CPU/memory (`savedCallbacks` map growth, mitigated only by a periodic prune, not by admission control)
- Network/CPU on every DON node (each fan-out message must be processed and validated by every member)

This matches the audited vulnerability class: an unprivileged/low-cost client action produces an outsized amount of downstream node work, and there is no request-throttling mechanism to prevent it — precisely the DoS concern raised in the original in3-server finding and explicitly still marked TODO in this codebase.

### Likelihood Explanation
The vulnerability is directly reachable through the standard external entry point `gateway.ProcessRequest` → `Handler.HandleLegacyUserMessage`, requires no privileged access beyond a valid signature over the message (the same requirement any legitimate caller must meet), and the missing-mitigation TODO comment confirms the gap is a known, unaddressed omission rather than a defense implemented elsewhere. Exploitability depends on how sender authorization/allowlisting is enforced upstream (at the connection or auth-token layer) before reaching this handler — I could not fully verify from the indexed code whether an additional allowlist check occurs earlier in the request path (e.g., in the HTTP server or connection manager) that would restrict which signers can reach this method at all. This uncertainty should be resolved by a Devin session with full repository access before treating likelihood as "confirmed high."

### Recommendation
Add a per-sender (and/or global) rate limiter — analogous to the existing `nodeRateLimiter` used for `handleWebAPIOutgoingMessage` — to `HandleLegacyUserMessage`, keyed on `msg.Body.Sender`, and reject/throttle requests before the fan-out loop over `h.donConfig.Members`. Additionally, replace the TODO with an actual allowlist check restricting which signer addresses may submit `MethodWebAPITrigger` requests for a given DON/topic, consistent with the mitigation pattern already implemented in the newer `v2` HTTP gateway handler (`globalNodeRateLimiter`, `perNodeRateLimiters`, `userRateLimiter` in `core/services/gateway/handlers/capabilities/v2/http_handler.go`).

### Proof of Concept
1. Obtain (or compromise) any ECDSA key accepted as a valid signer for a `MethodWebAPITrigger` message (per `api.Message.Sign`/`Validate`, any key producing a valid signature over the message body passes).
2. Repeatedly construct and sign `api.Message` bodies with unique `MessageID` values and a fresh timestamp (to bypass the staleness check), method `MethodWebAPITrigger`.
3. Submit these via the gateway's legacy request path in rapid succession.
4. Observe: each call reaches `HandleLegacyUserMessage`, is accepted (no rate limit/allowlist check exists at line 384 as shown), stored in `savedCallbacks`, and fanned out via `don.SendToNode` to **every** DON member — with no upper bound on request frequency from this handler itself, unlike the `nodeRateLimiter`-protected `handleWebAPIOutgoingMessage` path. func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageID) == 0 || len(m.Body.MessageID) > MessageIDMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageID, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonID) == 0 || len(m.Body.DonID) > MessageDonIDMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonID, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
