## Finding

### Title
Missing `return` after failed claim extraction allows an authenticated session to be created despite the error response - ([File: core/sessions/oidcauth/oidc.go])

### Summary
`handleTokenExchange` in `core/sessions/oidcauth/oidc.go` follows a consistent pattern of validating a step, writing an HTTP error response, and calling `return` to halt processing on failure — mirroring the audit's "missing `revert`" bug class where a guard check exists syntactically but fails to actually stop execution. One of these guards is missing its `return`, letting execution fall through and complete the login flow anyway.

### Finding Description
Throughout `handleTokenExchange`, every failed precondition is handled with the pattern `c.JSON/c.String(...); return` (e.g. bad JSON body, invalid state, failed token exchange, missing `id_token`, failed token verification, failed claims parsing, failed claim mapping — all correctly `return` after writing the error). [1](#0-0) [2](#0-1) 

However, the email-claim check breaks this pattern — it writes the error response but omits `return`: [3](#0-2) 

Because the function keeps running after this check "fails," it proceeds to:
1. Map group claims to an RBAC role via `IDClaimsToUserRole`. [4](#0-3) 
2. Insert a new row into `oidc_sessions` keyed by the (empty) `email` and the resolved role — and here too, an insert error is only logged to the response body without `return`, compounding the same missing-halt bug: [5](#0-4) 
3. Set the session cookie (`SessionIDKey`) and save the Gin session. [6](#0-5) 
4. Finally overwrite whatever error status/body was written earlier with `c.JSON(http.StatusOK, ExchangeTokenResponse{Success: true})`. [7](#0-6) 

The net effect: an ID token that verifies successfully (passes signature/issuer/audience checks) but lacks an `email` claim — or whose DB insert fails — still results in a valid, cookie-backed authenticated session being created and a final `200 { success: true }` response being sent to the client, exactly as if nothing had gone wrong. This is functionally identical to the reported Solidity bug: a safety check (`if (!isContract(target)) Errors.AddressNotContract;`) exists in source but, because the halting keyword (`revert` in Solidity, `return` here) is missing, the check becomes a no-op and execution proceeds past the intended failure point.

### Impact Explanation
An unprivileged client completing the OIDC handshake can end up with a legitimate, cookie-backed session (`AuthenticateGQL`/`AuthenticateBySession` will accept this session ID going forward) tied to a role derived purely from IdP group claims, with an empty/incorrect `email` recorded in `oidc_sessions`. This undermines the intended email-identity binding of the session and can produce sessions whose identity attribute doesn't match what downstream code (e.g. audit logging, per-user authorization or the `users` table cross-reference) expects. It also masks genuine failures (DB insert errors) as successes to the caller, which can mislead operators and hide broken state.

### Likelihood Explanation
Reaching this code path requires only a successful OIDC round trip against the configured identity provider (an unprivileged but otherwise legitimate flow through the standard `/oidc` token-exchange endpoint) combined with an ID token/claims payload that omits the `email` claim, or a transient database failure on the `INSERT INTO oidc_sessions` statement. No special privilege is needed to trigger it beyond normal OIDC login capability.

### Recommendation
Add `return` immediately after both error branches, matching the pattern used everywhere else in the function:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims")
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
...
_, err = oi.ds.ExecContext(ctx, "INSERT INTO oidc_sessions ...", clSession.ID, strings.ToLower(email), role)
if err != nil {
    oi.lggr.Errorf("unable to create new session in oidc_sessions table %v", err)
    c.String(http.StatusInternalServerError, "Error creating session")
    return
}
```

### Proof of Concept
1. Configure the OIDC provider so the ID token's claims map does not include an `email` field (or intercept/craft an IdP response without it, while all signature/issuer checks still pass).
2. Complete the normal `/oidc` sign-in flow through `handleSignIn` and hit the token-exchange endpoint that invokes `handleTokenExchange`.
3. Observe that despite `claims["email"].(string)` failing (`ok == false`) and an HTTP 500 body being written at line 229, execution continues: `IDClaimsToUserRole` runs, a row is inserted into `oidc_sessions`, `ginSession.Set(webauth.SessionIDKey, clSession.ID)` + `ginSession.Save()` run, and the handler ultimately emits `200 {"success":true}` with a valid session cookie set in the response headers.
4. Use the resulting session cookie against a session-protected endpoint (e.g. via `AuthenticateBySession`) to confirm it is accepted as a valid authenticated session. [8](#0-7)

func AuthenticateBySession(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	session := sessions.Default(c)
	sessionID, ok := session.Get(SessionIDKey).(string)
	if !ok {
		return auth.ErrorAuthFailed
	}

	user, err := authr.AuthorizedUserWithSession(ctx, sessionID)
	if err != nil {
		return err
	}

	c.Set(SessionUserKey, &user)

	return nil
}
