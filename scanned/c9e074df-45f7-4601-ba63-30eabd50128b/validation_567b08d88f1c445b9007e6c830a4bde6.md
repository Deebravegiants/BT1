Based on my investigation, I found a concrete authorization gap analogous to the reported issue: while `handleSecretsList` explicitly re-stamps the request with the authorized owner (`r.Owner = authResult.AuthorizedOwner()`), `handleSecretsDelete` does **not** perform the equivalent enforcement before invoking the privileged mutation `h.secretsService.DeleteSecrets`.

### Title
Missing owner-binding enforcement in Vault gateway secrets-delete path allows cross-owner secret deletion - ([File: core/capabilities/vault/gw_handler.go])

### Summary
The Vault `GatewayHandler.handleSecretsDelete` function unmarshals the caller-supplied `DeleteSecretsRequest` and forwards it directly to `h.secretsService.DeleteSecrets` without overwriting/binding the request's owner-scoped identifiers to the authenticated caller's `AuthorizedOwner()`, unlike its sibling `handleSecretsList`, which explicitly does `r.Owner = authResult.AuthorizedOwner()` before calling the underlying service.

### Finding Description
`HandleGatewayMessage` routes `MethodSecretsDelete` requests through `GatewayVaultRequestProcessor.ProcessRequest` → `processDeleteSecretsRequest`, which authorizes the request and stamps the request ID with the authorized owner via `authorizeAndStamp` [1](#0-0) . However, this stamping only rewrites `req.ID`/`RequestId`; it does not rewrite the `Ids` (each a `SecretIdentifier` presumably carrying its own `Owner` field, mirroring `EncryptedSecret.Id.Owner` used elsewhere in the file) inside the delete payload.

Downstream, `handleSecretsDelete` unmarshals the request and calls `h.secretsService.DeleteSecrets(ctx, r)` directly, passing through whatever owner-scoped identifiers the caller supplied in the JSON-RPC params [2](#0-1) . Compare this to `handleSecretsList`, which explicitly forces `r.Owner = authResult.AuthorizedOwner()` before calling the service, preventing a caller from listing another owner's secrets [3](#0-2) .

This is structurally the same class of bug as the `USSD.sol` report: a privileged/state-mutating operation (`mintRebalance`/`burnRebalancer` there; `DeleteSecrets` here) is reachable without the access-control check (owner-scope binding) that its sibling read operation enforces. If `vaultcommon.SecretIdentifier` carries an `Owner` field (as it does for `EncryptedSecret.Id.Owner`, confirmed used in `processCreateSecretsRequest`/tests), an authenticated-but-unprivileged workflow could authorize successfully for its own owner scope, then supply `Ids` referencing a different owner's secrets in the delete params, deleting secrets it does not own.

### Impact Explanation
If exploitable, this allows any authenticated (allowlisted/JWT) workflow caller to delete secrets belonging to another owner/workflow, causing unauthorized data loss/denial-of-service for other tenants of the shared Vault capability — a cross-user integrity violation analogous to unauthorized fund movement in the original report, though scoped to secrets rather than tokens.

### Likelihood Explanation
Reaching this path only requires being an authorized (allowlisted or JWT-authenticated) gateway caller — not a privileged operator — matching the "unprivileged client request" threat model. The likelihood of successful exploitation depends on whether `p.validator.ValidateDeleteSecretsRequest` (in `validator.go`) independently checks/rejects mismatched owners in `Ids` before this point; I was unable to fully confirm the internals of `ValidateDeleteSecretsRequest` or the exact shape of `vaultcommon.DeleteSecretsRequest`/`SecretIdentifier` within the indexed content, so I cannot confirm with certainty whether validation elsewhere closes this gap.

### Recommendation
In `handleSecretsDelete` (and in `processDeleteSecretsRequest`'s stamping closure), explicitly overwrite/validate that every `Ids[i].Owner` in the delete request matches `authResult.AuthorizedOwner()`, mirroring the pattern already used in `handleSecretsList`, before calling `h.secretsService.DeleteSecrets`.

func (p *GatewayVaultRequestProcessor) processDeleteSecretsRequest(
	ctx context.Context,
	req *jsonrpc.Request[json.RawMessage],
) (*AuthorizedGatewayVaultRequest, error) {
	if req.Params == nil {
		return nil, InvalidVaultParamsError{Method: req.Method, Err: errors.New("request params must not be nil")}
	}

	var deleteReq vaultcommon.DeleteSecretsRequest
	if err := json.Unmarshal(*req.Params, &deleteReq); err != nil {
		return nil, InvalidVaultParamsError{Method: req.Method, Err: err}
	}
	if p.stripOwnerPrefixForAuth {
		deleteReq.RequestId = req.ID
		if err := marshalVaultParams(req, &deleteReq); err != nil {
			return nil, InvalidVaultParamsError{Method: req.Method, Err: err}
		}
	} else {
		deleteReq.RequestId = coalesceRequestID(deleteReq.RequestId, req.ID)
	}

	if err := p.validator.ValidateDeleteSecretsRequest(ctx, &deleteReq); err != nil {
		return nil, p.validationError(req, err)
	}

	return p.authorizeAndStamp(ctx, req, func(prefixedRequestID string) error {
		deleteReq.RequestId = prefixedRequestID
		vaultutils.ApplySecretIdentifierNamespaceDefaults(deleteReq.Ids)
		return marshalVaultParams(req, &deleteReq)
	})
}

func (h *GatewayHandler) handleSecretsDelete(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) *jsonrpc.Response[json.RawMessage] {
	r := &vaultcommon.DeleteSecretsRequest{}
	if err := json.Unmarshal(*req.Params, r); err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.UserMessageParseError, err)
	}

	h.lggr.Debugw("Processing authorized delete secrets request", "request", r.String())
	resp, err := h.secretsService.DeleteSecrets(ctx, r)
	if err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.HandlerError, fmt.Errorf("failed to delete secrets: %w", err))
	}

	resultBytes, err := resp.ToJSONRPCResult()
	if err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.NodeReponseEncodingError, err)
	}

	return &jsonrpc.Response[json.RawMessage]{
		Version: jsonrpc.JsonRpcVersion,
		ID:      req.ID,
		Method:  req.Method,
		Result:  (*json.RawMessage)(&resultBytes),
	}
}
