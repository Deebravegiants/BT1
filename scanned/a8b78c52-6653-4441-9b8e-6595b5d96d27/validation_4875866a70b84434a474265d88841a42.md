### Title
Unauthenticated-role disclosure of External Initiator credentials via unauthenticated-role `/v2/external_initiators` index endpoint - (File: core/web/router.go)

### Summary
The GitLab CVE describes a lower-privileged user being able to disclose information (email addresses) belonging to a resource scope they don't have the role/maintainer access for. The chainlink analog is the `/v2/external_initiators` index route, which is reachable by any authenticated user regardless of role — including the lowest-privileged `UserRoleView` — and returns the `AccessKey` and `OutgoingToken` credentials of every External Initiator registered on the node, not just resources the requester created or is entitled to manage.

### Finding Description
In `core/web/router.go`, the `/v2/external_initiators` routes are registered as: [1](#0-0) 

Note that `GET /v2/external_initiators` (`eia.Index`) has **no** role-gating wrapper (`auth.RequiresEditRole`/`RequiresRunRole`/`RequiresAdminRole`), unlike the `POST` (create) and `DELETE` (destroy) routes on the same resource, which are wrapped in `auth.RequiresEditRole`. This is confirmed by the RBAC route map test, which explicitly marks the index route as accessible to view-only, run, and edit roles alike: [2](#0-1) 

The handler returns `ExternalInitiatorResource`, which includes the `AccessKey` and `OutgoingToken` fields for every initiator in the system (paginated, not filtered by owner/creator): [3](#0-2) 

The integration test for this endpoint confirms both `AccessKey` and `OutgoingToken` are exposed in the list response for initiators the requesting client did not create: [4](#0-3) 

`AccessKey` is one half of the credential pair used to authenticate incoming External Initiator job-run requests (paired with a secret that is only shown once, at creation time) — see `ExternalInitiator` struct and `AuthenticateExternalInitiator`: [5](#0-4) [6](#0-5) 

Compare this to every other credential-bearing resource in the router (CSA keys, ETH keys, OCR keys, etc.), which uniformly require at least an Edit role for creation and Admin role for export/delete — the External Initiator index is the outlier that leaks credential material to any authenticated session, including `UserRoleView`.

### Impact Explanation
A user provisioned only with `UserRoleView` (meant for read-only dashboard access, explicitly denied access to run/edit/admin actions elsewhere in the API per `RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole` in `core/web/auth/auth.go`) can enumerate every External Initiator's `AccessKey` and `OutgoingToken` on the node — including ones created by other operators/administrators. While the paired `Secret`/`OutgoingSecret` are not returned by Index (only shown once at `Create`), the `AccessKey` disclosure still meaningfully aids credential-guessing/replay attacks against the node's external-initiator-triggered job runs, and `OutgoingToken` disclosure exposes the token the node itself uses when calling out to the external initiator's URL, which could be replayed against that third-party endpoint if it accepts the token as a bearer/auth credential. This is a horizontal/vertical privilege boundary violation: a low-privileged, unprivileged-role client can access sensitive configuration belonging to higher-privileged operators.

### Likelihood Explanation
High likelihood of exploitation if `ExternalInitiatorsEnabled` is turned on and any `UserRoleView` accounts exist (a common practice for granting read-only dashboard access to less-trusted operators/auditors). The endpoint requires only a valid authenticated session (any role) — `auth.Authenticate(... AuthenticateByToken, AuthenticateBySession)` — with no additional role check, so exploitation is a single unauthenticated-role authenticated `GET` request.

### Recommendation
Wrap `GET /v2/external_initiators` with `auth.RequiresEditRole` (or at minimum `auth.RequiresRunRole`) to match the access level required for `POST`/`DELETE` on the same resource, consistent with how every other credential-bearing resource (CSA/ETH/OCR/P2P/VRF keys) restricts read access. Additionally consider omitting `AccessKey`/`OutgoingToken` from the list/index presenter entirely, only surfacing them on the one-time `Create` response (`ExternalInitiatorAuthentication`), and scoping visibility so operators only see the credentials for their own resources if per-user ownership is later introduced.

### Proof of Concept
1. Enable External Initiators: `JobPipeline.ExternalInitiatorsEnabled = true`.
2. Provision a session/API token for a user with `UserRoleView`.
3. As an admin/edit-role user, create an External Initiator: `POST /v2/external_initiators {"name":"foo"}` — records an `AccessKey`, `OutgoingToken`, and secrets server-side.
4. As the `UserRoleView` user, call `GET /v2/external_initiators?size=50`.
5. Observe the response includes `accessKey` and `outgoingToken` for the initiator created in step 3, despite the requester holding only view privileges — mirrored by the assertions in `TestExternalInitiatorsController_Index` at [4](#0-3) , run without any role restriction on the client.

// AuthenticateExternalInitiator compares an auth against an initiator and
// returns true if the password hashes match
func AuthenticateExternalInitiator(eia *auth.Token, ea *ExternalInitiator) (bool, error) {
	hashedSecret, err := auth.HashedSecret(eia, ea.Salt)
	if err != nil {
		return false, err
	}
	return subtle.ConstantTimeCompare([]byte(hashedSecret), []byte(ea.HashedSecret)) == 1, nil
}
