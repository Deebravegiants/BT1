### Title
Unauthenticated LDAP login response messages allow user/group enumeration and connection-state probing - (File: core/sessions/ldapauth/ldap.go)

### Summary
The Zammad CVE-2021-35299 root cause is that an unauthenticated user can send probe requests and infer sensitive backend configuration/state from differentiated response messages. Chainlink's LDAP authentication path exhibits the same bug class: the `CreateSession` function returns distinct, verbatim error strings depending on internal state (LDAP server unreachable, bind failure, user found but no role, local-fallback path), and these are passed straight to the unauthenticated caller.

### Finding Description
`ldapAuthenticator.CreateSession` returns different literal error messages for different internal states:
- `"unable to establish connection to LDAP server with provided URL and credentials"` when the ephemeral LDAP connection cannot be established [4](#0-3) 
- `"unable to log in with LDAP server. Check credentials"` on a bind failure [5](#0-4) 
- `"log in successful, but no assigned groups to assume role"` when the bind succeeds but `FindUser` cannot resolve a role [6](#0-5) 
- Local-fallback specific errors such as `"invalid credentials"` returned by `TestPassword`/`localLoginFallback` [7](#0-6) 

These distinct strings are propagated unmodified to the HTTP client: `SessionsController.Create` calls `sc.App.AuthenticationProvider().CreateSession(ctx, sr)` and on error immediately does `jsonAPIError(c, http.StatusUnauthorized, err)` [2](#0-1) , and `jsonAPIError` serializes `err.Error()` directly into the JSON response body [1](#0-0) . The `/sessions` POST route requires no authentication, only rate limiting [8](#0-7) .

An unauthenticated attacker submitting arbitrary emails/passwords can therefore distinguish:
1. Whether the node's upstream LDAP server is reachable/misconfigured (infra probing, matching the CVE's "email connection configuration probing" class — the LDAP connectivity string leaks backend configuration health).
2. Whether a given email exists in the directory and is bound successfully but lacks group-role mapping ("log in successful, but no assigned groups") vs. simply wrong credentials — enabling account/user enumeration.

### Impact Explanation
This differs from the plain "wrong password" bug class in that it discloses internal state (backend LDAP connectivity, existence of specific accounts, role misconfiguration) to any unauthenticated network client hitting the login endpoint, which is directly analogous to Zammad's incorrect access control disclosing email connection configuration to unprivileged probing. It does not allow direct credential/session bypass, but it materially aids an attacker in enumerating valid Chainlink node operator emails and diagnosing/troubleshooting LDAP misconfiguration remotely (useful for a follow-on credential-stuffing/spray or social-engineering attack against a specific node operator).

### Likelihood Explanation
The LDAP driver is optional (`WebServer.AuthenticationMethod = 'ldap'`), so this only affects nodes configured to use LDAP auth [9](#0-8) . When enabled, the `/sessions` endpoint is internet-facing and unauthenticated by design, and the differentiated error strings are always returned as-is with no generic "invalid credentials" normalization across all failure branches, so exploitation only requires network access to the node's login endpoint.

### Recommendation
Normalize all `CreateSession`/LDAP-related authentication failures returned to the HTTP client into a single generic message (e.g., "invalid credentials") regardless of whether the failure is due to LDAP connectivity, bind failure, or missing role mapping, and log the detailed distinguishing error only server-side (as is already partially done via `l.lggr.Infof`). Apply the same normalization to the local-auth fallback path.

### Proof of Concept
1. Configure a Chainlink node with `WebServer.AuthenticationMethod = 'ldap'`.
2. Send `POST /sessions` with a random nonexistent email/password — observe response error text (e.g., "unable to log in with LDAP server. Check credentials" or an LDAP connectivity error).
3. Send `POST /sessions` with a known/guessed valid organizational email and a wrong password — observe whether the response differs (e.g., "log in successful, but no assigned groups to assume role" if the account exists but the LDAP group mapping is misconfigured, vs. the generic bind failure for nonexistent accounts).
4. Compare response strings across many guessed emails to enumerate valid accounts and probe LDAP backend connectivity state, all without authentication.

Note: I could not execute this against a live instance (no filesystem/runtime access in this environment); the PoC steps are derived from static analysis of the cited code paths and would need to be verified by running the node. If deeper verification against an actual running node/database state is needed, that requires a full Devin session with code execution access.

func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
