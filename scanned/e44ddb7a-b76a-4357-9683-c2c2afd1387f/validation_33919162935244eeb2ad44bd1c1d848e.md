## Title
Username enumeration via distinguishable login error messages on `/sessions` endpoint - (File: `core/sessions/localauth/orm.go`)

## Summary
The `POST /sessions` login endpoint returns different error message text depending on whether the submitted email exists in the system, allowing an unauthenticated attacker to enumerate valid usernames — the same bug class as CVE-2021-46434 (EMQ X username enumeration).

## Finding Description
`SessionsController.Create` calls `AuthenticationProvider().CreateSession(ctx, sr)` and, on any failure, forwards the raw Go `error` value straight into the JSON response body via `jsonAPIError`: [1](#0-0) 

`jsonAPIError` serializes `err.Error()` verbatim into the client-visible JSON API error response: [2](#0-1) 

In the default local authentication provider, `CreateSession` first looks up the user by email. If the email does not exist, the raw database error (e.g. `sql: no rows in result set`) is returned unmodified. If the email exists but the password is wrong, a distinct, explicit `"Invalid password"` error is returned instead: [3](#0-2) 

`FindUser`/`findUser` performs a direct `SELECT ... WHERE lower(email) = lower($1)` and propagates `sql.ErrNoRows` untouched when no match is found: [4](#0-3) 

Both the "unknown email" and "wrong password" cases return HTTP 401 (`http.StatusUnauthorized`), so the status code alone doesn't leak anything — but the body text differs ("sql: no rows in result set" vs "Invalid password"), letting an attacker distinguish valid accounts from invalid ones purely from response content, exactly mirroring the EMQ X dashboard bug class.

The route is reachable by any unauthenticated client, gated only by a rate limiter, not by authentication: [5](#0-4) 

The existing test suite only asserts a generic "should not be able to create session" status-code check and does not assert on error-message equivalence between the two failure cases, so this behavior is not caught by tests: [6](#0-5) 

## Impact Explanation
An unauthenticated network attacker can send crafted email/password pairs to `POST /sessions` and, by inspecting the returned error string, determine whether a given email/username is a registered Chainlink node operator account. This enables targeted credential-stuffing, phishing, or brute-force campaigns against confirmed valid accounts, and reduces the overall security posture of the node's admin API authentication.

## Likelihood Explanation
Likelihood is high: the endpoint is unauthenticated and internet-facing by design (it exists specifically to allow login), requires no special privileges to reach, and the differing error text is deterministic and always present in the response body. The only mitigating control is a configurable rate limiter, which slows but does not prevent enumeration.

## Recommendation
Ensure `CreateSession` (and its `AuthenticationProvider` implementations) return a single, generic, constant-time error (e.g. `"invalid email or password"`) regardless of whether the email lookup fails or the password check fails, and avoid propagating raw driver/database errors (e.g. `sql.ErrNoRows`) up to the HTTP response. Apply the same generic handling in the LDAP/OIDC local-fallback paths (`localLoginFallback` in `core/sessions/ldapauth/ldap.go` and `core/sessions/oidcauth/oidc.go`), which currently also differentiate "invalid email" vs "invalid password" in returned errors.

## Proof of Concept
1. `POST /sessions` with `{"email":"nonexistent@test.com","password":"anything"}` → HTTP 401, body contains database-level error text (e.g. `sql: no rows in result set`).
2. `POST /sessions` with `{"email":"<known-valid-email>","password":"wrongpassword"}` → HTTP 401, body contains `"Invalid password"`.
3. Compare the two response bodies: the differing content confirms which email is a valid, registered account, without needing the correct password.

func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}

func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}

func sessionRoutes(app chainlink.Application, r *gin.RouterGroup) {
	config := app.GetConfig()
	rl := config.WebServer().RateLimit()
	unauth := r.Group("/", rateLimiter(
		rl.UnauthenticatedPeriod(),
		rl.Unauthenticated(),
	))
	sc := NewSessionsController(app)
	unauth.POST("/sessions", sc.Create)
	auth := r.Group("/", auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession))
	auth.DELETE("/sessions", sc.Destroy)
}
