### Title
Missing Future-Timestamp Validation in Gateway `HandleLegacyUserMessage` Allows Indefinite Staleness-Check Bypass - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The internet-facing gateway's `HandleLegacyUserMessage` function validates that a client-supplied `payload.Timestamp` is not too old (the "stale message" check), but never validates that it is not set in the future. This mirrors the reported bug class: a timestamp/duration field accepted by an unprivileged-user-triggered `request()`-like entrypoint is only checked in one temporal direction, letting a caller set it to an out-of-bounds value that defeats the intended time-based control.

### Finding Description
`HandleLegacyUserMessage` is reachable from any unprivileged client sending a message (a "web api trigger") to the DON via the gateway. It unmarshals `webapicap.TriggerRequestPayload`, requires `payload.Timestamp != 0`, and rejects the message only if it is *too old*: [1](#0-0) 

There is no corresponding upper-bound check ensuring `payload.Timestamp` is not set arbitrarily far in the future. Since the timestamp is attacker-controlled input embedded in the message payload (not derived from the gateway's own receipt time), a caller can set it to any future value. The staleness formula `uint(time.Now().Unix()) - h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp)` will then never trigger for that message, effectively disabling the anti-replay/staleness protection that `MaxAllowedMessageAgeSec` is meant to enforce, analogous to the reported issue where a `duration`/date field is accepted without bounds validation, corrupting a time-based business rule (there: "loan overdue before disbursed"; here: "message never becomes stale").

### Impact Explanation
`MaxAllowedMessageAgeSec` exists specifically to bound the freshness window of user-submitted trigger messages before they are forwarded to every DON node (`don.SendToNode` for all `h.donConfig.Members`) and before a callback is registered (`h.savedCallbacks`). By supplying a future timestamp, an unprivileged external caller can render this freshness control moot, allowing messages to remain "fresh" indefinitely from the gateway's perspective. This weakens the staleness/replay defense on the internet-facing gateway path and can be combined with other conditions (e.g., message-ID reuse, callback caching behavior) to widen the acceptance window for otherwise-expired requests being routed to the DON.

### Likelihood Explanation
Likelihood is high for triggering the bug itself: `Timestamp` is a plain field on the JSON payload of `TriggerRequestPayload` supplied entirely by the calling client, requires no privileges, and the check is a simple `if` with no future-bound clause. However, the severity of the resulting impact depends on what downstream systems otherwise rely on `MaxAllowedMessageAgeSec`-derived freshness guarantees; the code notes at line 384 that allowlist/rate-limiting enforcement is still a `TODO`, further indicating this path has weaker validation maturity overall.

### Recommendation
Add an upper-bound check in `HandleLegacyUserMessage` immediately alongside the existing staleness check, rejecting messages whose `payload.Timestamp` is more than a small allowed clock-skew tolerance ahead of `time.Now().Unix()`, e.g.:
```go
if uint(payload.Timestamp) > uint(time.Now().Unix())+allowedClockSkewSec {
    // reject: timestamp in the future
}
```
This closes the gap and ensures the timestamp is bounded on both sides, consistent with how other time-bounded checks in the codebase (e.g., JWT `iat`/`exp` validation in `core/utils/jwt.go`) validate both past and future bounds.

### Proof of Concept
1. Craft a `webapicap.TriggerRequestPayload` with `Timestamp` set to, e.g., `time.Now().Unix() + 10_000_000` (far future).
2. Submit it as a `web_api_trigger` message to the gateway's `HandleLegacyUserMessage` entrypoint.
3. Observe that the `payload.Timestamp == 0` check passes (non-zero) and the staleness check `uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp)` evaluates false for any realistic `MaxAllowedMessageAgeSec`, since `payload.Timestamp` is far larger than `time.Now().Unix()`.
4. The message proceeds to be forwarded to all DON members via `don.SendToNode`, with no future-timestamp rejection ever occurring, confirmed by inspecting [2](#0-1)  and the absence of any complementary "future timestamp" test case in [3](#0-2) .
