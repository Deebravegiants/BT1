## Finding: View-role users can read bridge outgoing credentials via GraphQL/REST bridge queries

### Title
Sensitive bridge credential (`OutgoingToken`) exposed to view-only role users - ([File: core/web/resolver/query.go])

### Summary
The GLPI CVE describes a low-privileged, read-only authenticated user retrieving sensitive/secret fields of an item through a listing-style query, because the field-level sensitivity was not checked separately from the item-level read permission. The chainlink analog is the `Bridge`/`Bridges` GraphQL queries and the corresponding `/v2/bridge_types` REST endpoints, which only enforce the lowest role tier (`view`) yet return the bridge's `OutgoingToken` — a credential Chainlink attaches as an authentication header when calling out to the external adapter.

### Finding Description
`Resolver.Bridge` and `Resolver.Bridges` gate access with `authenticateUser(ctx)`, which only requires a valid session and permits the `UserRoleView` role (the least privileged role): [1](#0-0) 

`authenticateUser` is explicitly documented as granting "view" access with no further restriction: [2](#0-1) 

The `BridgeResolver.OutgoingToken()` method returns the bridge's live outgoing credential as part of the `Bridge` GraphQL type with no field-level authorization check: [3](#0-2) 

The REST equivalents (`GET /v2/bridge_types` and `GET /v2/bridge_types/:BridgeName`) serialize the same `OutgoingToken` field via `presenters.NewBridgeResource`, and per the RBAC route table, these endpoints are marked `viewOnlyAllowed: true`, meaning a `view`-role user is not rejected: [4](#0-3) [5](#0-4) [6](#0-5) 

This is structurally the same bug class as CVE-2024-27930: an item-level read permission (view a bridge's existence/config) is conflated with permission to see a sensitive field (`OutgoingToken`, a real credential used to authenticate node → external-adapter calls) that should logically require at least `edit`/`admin` privileges, consistent with how `IncomingToken` is deliberately withheld outside of bridge creation (`omitempty`, only returned once): [7](#0-6) 

### Impact Explanation
Any authenticated Chainlink node UI/API user provisioned with only the `view` role — the tier intended for read-only observability, not credential management — can retrieve the `OutgoingToken` for every configured bridge. This token is used by the node to authenticate itself to external adapters; disclosure allows the view-role user (or anyone who compromises their session/API key) to impersonate the node when calling the external adapter, or replay/misuse the credential outside the intended trust boundary. This is a concrete "key/secret disclosure" and "cross-user response confusion" style issue matching the required impact categories.

### Likelihood Explanation
High likelihood of exploitation: no special conditions are needed beyond having any valid `view`-role session or API token, which is the lowest privilege tier explicitly designed for read-only access. A single `bridges`/`bridge` GraphQL query or a plain `GET /v2/bridge_types` REST call suffices — no additional gating exists on this field.

### Recommendation
Restrict the `OutgoingToken` field (and any other bridge secret material) so it is only returned to users with at least `edit`/`admin` role, mirroring the treatment of `IncomingToken`. Concretely: add a role check within `BridgeResolver.OutgoingToken()` (or filter it before constructing the resolver for `view`-role callers) and add the analogous field-level gating in `presenters.NewBridgeResource`/`BridgeTypesController`, rather than relying solely on the coarse-grained `authenticateUser`/`viewOnlyAllowed` route-level check.

### Proof of Concept
1. Create a Chainlink node API user with role `view` (`chainlink admin users create --role=view`).
2. Authenticate as that user and issue:
   - GraphQL: `query { bridges { results { name outgoingToken } } }`
   - or REST: `GET /v2/bridge_types`
3. Observe that `outgoingToken` for existing bridges is returned in the response, despite the user holding only the lowest, read-only role.

// Bridge retrieves a bridges by name.
func (r *Resolver) Bridge(ctx context.Context, args struct{ ID graphql.ID }) (*BridgePayloadResolver, error) {
	if err := authenticateUser(ctx); err != nil {
		return nil, err
	}

	name, err := bridges.ParseBridgeName(string(args.ID))
	if err != nil {
		return nil, err
	}

	bridge, err := r.App.BridgeORM().FindBridge(ctx, name)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return NewBridgePayload(bridge, err), nil
		}

		return nil, err
	}

	return NewBridgePayload(bridge, nil), nil
}

// Bridges retrieves a paginated list of bridges.
func (r *Resolver) Bridges(ctx context.Context, args struct {
	Offset *int32
	Limit  *int32
}) (*BridgesPayloadResolver, error) {
	if err := authenticateUser(ctx); err != nil {
		return nil, err
	}

	offset := pageOffset(args.Offset)
	limit := pageLimit(args.Limit)

	brdgs, count, err := r.App.BridgeORM().BridgeTypes(ctx, offset, limit)
	if err != nil {
		return nil, err
	}

	return NewBridgesPayload(brdgs, safeInt32(count)), nil
}

// Index lists Bridges, one page at a time.
func (btc *BridgeTypesController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	bridges, count, err := btc.App.BridgeORM().BridgeTypes(ctx, offset, size)

	resources := make([]presenters.BridgeResource, 0, len(bridges))
	for _, bridge := range bridges {
		resources = append(resources, *presenters.NewBridgeResource(bridge))
	}

	paginatedResponse(c, "Bridges", size, page, resources, count, err)
}

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
