## Title
External Initiator authentication and job-run triggering is not gated by the `ExternalInitiatorsEnabled` feature flag - (`File: core/web/auth/auth.go`)

### Summary
The audit finding describes a class of bug where a resource's "active/enabled" state flag is enforced in only some code paths (e.g., creation) but not in the core operational paths that actually use the resource (allocate, registerRecipient, increasePoolAmount). The analogous pattern exists in the External Initiator (EI) feature: the `ExternalInitiatorsEnabled` config flag gates creation of new external initiators, but not the authentication/execution path that lets an already-registered external initiator trigger job runs.

### Finding Description
`ExternalInitiatorsController.Create` explicitly checks the feature flag before allowing a new external initiator to be registered: [1](#0-0) 

However, the actual authentication method used to let an external initiator make authenticated requests (which grants the `run` role used to trigger job runs) does not check this flag at all: [2](#0-1) 

This `AuthenticateExternalInitiator` method only verifies the access key/secret against the `bridges.ExternalInitiator` record and, on success, sets the requester's role to `UserRoleRun`: [3](#0-2) 

Nothing in this path calls `App.GetConfig().JobPipeline().ExternalInitiatorsEnabled()`. As a result, if the feature is disabled after some external initiators were already created (or if the flag is later flipped off as an operational kill switch), those pre-existing external initiator credentials remain fully functional for authenticating requests and triggering job runs — the "disabled" state of the feature is not enforced at the point where it matters (request authentication / run execution), only at the point of creation.

This exactly mirrors the reported analog: `increasePoolAmount()`/`registerRecipient()`/`allocate()` check state where creation/registration happens but skip the `onlyActivePool` gate in the functions that actually move funds/trigger effects.

### Impact Explanation
An operator who disables `ExternalInitiatorsEnabled` (intending to shut down external-initiator-triggered job runs, e.g., in response to abuse, a compromised initiator, or a security policy change) would reasonably expect that no external initiator can start job runs any more. In reality, any previously-issued external initiator access key/secret pair continues to authenticate and can still call the "run" role endpoints (e.g., `POST /v2/jobs/:JobID/runs` and similar) because `AuthenticateExternalInitiator` never checks the flag. This is an unauthorized-run/fund-movement-adjacent bypass of an intended access control gate — the flag is a security control that is silently ineffective for already-existing credentials.

### Likelihood Explanation
High: no attacker sophistication is required. It happens automatically for any existing external initiator once the operator disables the feature but the initiator's credentials were not separately revoked/deleted. Since deleting existing initiators is a separate, manual step (`DeleteExternalInitiator`), and the flag is documented/intended as a way to control the entire feature, this gap is very likely to be hit in normal operational use.

### Recommendation
Add an `ExternalInitiatorsEnabled()` check inside `AuthenticateExternalInitiator` (core/web/auth/auth.go) so that authentication fails (e.g., returns `auth.ErrorAuthFailed`) whenever the feature flag is disabled, regardless of whether the initiator record still exists. This aligns the enforcement of the "enabled" state across both the registration and the execution paths, consistent with the requested fix pattern in the original report (apply the state guard uniformly to all core functions, not just creation).

### Proof of Concept
1. Enable `ExternalInitiatorsEnabled` and create an external initiator via `POST /v2/external_initiators`, obtaining `AccessKey`/`Secret`.
2. Disable `ExternalInitiatorsEnabled` in the node config (operator intends to shut off the feature).
3. Using the previously obtained `AccessKey`/`Secret` headers (`X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret`), call an endpoint protected by `Authenticate(..., AuthenticateExternalInitiator)` (e.g., trigger a job run).
4. Observe the request succeeds and is granted the `run` role — despite the feature being disabled — because `core/web/auth/auth.go`'s `AuthenticateExternalInitiator` never consults `ExternalInitiatorsEnabled()`. [1](#0-0) [4](#0-3)

// AuthenticateExternalInitiator authenticates an external initiator request.
//
// Implements authMethod
func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}
