Based on my investigation, I found a plausible analog to CVE-2024-49201 (Keyfactor's "sensitive information exposed at the debug logging level") in the chainlink Vault capability's gateway-facing code.

## Title
Full JSON-RPC request (including raw, unvalidated `Params`) logged at Debug level exposes sensitive request data — (`File: core/capabilities/vault/gw_handler.go`, `core/services/gateway/handlers/vault/handler.go`)

### Summary
The Vault capability's gateway-side and node-side handlers log the entire inbound JSON-RPC request object — including the raw `Params` field — at `Debug` log level before/alongside validation. This is the same bug class as CVE-2024-49201: sensitive information disclosure gated only by log verbosity (turning on Debug logging exposes data that should be redacted or excluded).

### Finding Description
In `core/capabilities/vault/gw_handler.go`, `HandleGatewayMessage` logs the complete incoming request object as soon as it is received, before any authorization or secrets-specific redaction is applied: [1](#0-0) 

Separately, the vault gateway handler test suite explicitly acknowledges the existence of a "pre-existing whole-request Debug log" that must be excluded from assertions checking that raw/invalid request parameters are not logged: [2](#0-1) 

That same test (`TestVaultHandler_InvalidParamsDoesNotLogRawParams`) only guards the `Error`-level "invalid params" log path against leaking raw params — it explicitly does *not* cover the Debug-level whole-request log, meaning at Debug verbosity the full, unfiltered request (including `Params`) is written to logs: [3](#0-2) 

This is consistent with the general pattern seen elsewhere in the codebase where Debug-level gateway/handler logs routinely serialize entire request/response objects (e.g. `core/services/gateway/gateway.go:292` logs the full `response` object, and `core/services/gateway/handlers/capabilities/handler.go:182` logs `msg.Body`), rather than a small set of whitelisted fields, unlike the more careful redaction implemented for the HTTP web-server layer (`core/web/router.go` `isBlacklisted`/`redact`). [4](#0-3) 

### Impact Explanation
If operators enable Debug logging (a supported, documented log level, not a developer-only mode), the Vault gateway handler and capability code will write complete JSON-RPC requests — including `Params` for methods such as `MethodSecretsCreate`/`MethodSecretsUpdate`/`MethodSecretsDelete`/`MethodSecretsList` — into logs that are typically less access-controlled than the primary secret store (log aggregation systems, disk files, log shipping pipelines). Depending on payload contents this can leak secret identifiers, owner/namespace metadata, or other caller-supplied data that the system otherwise takes care to redact in error paths, matching the "information disclosure at debug logging level" bug class from the CVE.

### Likelihood Explanation
Likelihood is moderate: Debug logging is an operator-controlled but ordinary/supported configuration, not an attacker-controlled setting, so exploitation requires an operator to have Debug enabled (common in troubleshooting/staging, sometimes production). No authentication bypass or code execution is needed — any request routed through the gateway (including from unprivileged/external clients) will be captured verbatim.

### Recommendation
Apply the same redaction discipline already used in the Error-level "invalid params" path (`entries[0].ContextMap()` excludes `params`) to the Debug-level whole-request logs in `core/capabilities/vault/gw_handler.go` and `core/services/gateway/handlers/vault/handler.go`: log only non-sensitive metadata (method, request ID, gateway ID) and avoid serializing `req`/`Params` wholesale, or explicitly redact known-sensitive sub-fields before logging.

### Proof of Concept
1. Configure a chainlink node acting as gateway/vault-DON member with `Log.Level = 'debug'`.
2. Send a JSON-RPC request to the gateway for `secrets_create`/`secrets_update`/`secrets_delete` (or any Vault method).
3. Observe the node's Debug logs: the full request object, produced by `reqLggr.Debugw("received message from gateway", "req", req)` in `core/capabilities/vault/gw_handler.go:182`, is written verbatim, including the raw `Params` payload — the same pattern the test at `core/services/gateway/handlers/vault/handler_test.go:1016-1059` acknowledges exists but does not cover.

**Caveat / uncertainty**: I could not pinpoint the exact line number of the "pre-existing whole-request Debug log" inside `core/services/gateway/handlers/vault/handler.go` referenced by the test comment (search matches were found but the surrounding `HandleJSONRPCUserMessage` body wasn't fully read before the tool budget ran out) — a Devin session with full file access should confirm the exact statement and whether the logged `Params` for valid Create/Update requests contain only ciphertext (lower severity) or any plaintext identifiers/metadata (higher severity) before finalizing severity/priority.
