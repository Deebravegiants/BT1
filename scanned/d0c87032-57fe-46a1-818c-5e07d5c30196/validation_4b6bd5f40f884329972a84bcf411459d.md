### Title
Potential cross-owner secret-identifier disclosure via unvalidated `Owner` field in gateway-routed `secrets/list` request - ([File: core/capabilities/vault/gateway_vault_request_processor.go])

### Summary
The internet-facing Gateway's vault JSON-RPC handler (`core/services/gateway/handlers/vault/handler.go`) processes `secrets/list` requests through the shared `GatewayVaultRequestProcessor.processListSecretIdentifiersRequest` [1](#0-0) . Unlike the node-side `GatewayHandler.handleSecretsList`, which explicitly overwrites the request's `Owner` field with the cryptographically authorized owner before querying the secrets service (`r.Owner = authResult.AuthorizedOwner()`) [2](#0-1) , the shared gateway-side processor never performs this override for the `ListSecretIdentifiersRequest.Owner` field [3](#0-2) .

### Finding Description
`authorizeAndStamp` computes `authorizedOwner` from the `AuthResult` and uses it only to prefix the JSON-RPC request ID (`prefixedRequestID := authorizedOwner + vaulttypes.RequestIDSeparator + originalRequestID`), not to rewrite the `Owner` field inside the request body [4](#0-3) . For `secrets/list`, the `stamp` callback only sets `listReq.RequestId` and defaults `listReq.Namespace`; it never sets `listReq.Owner` [5](#0-4) . The public Gateway's `handleSecretsList` then simply fans the (potentially client-supplied) request out to vault DON nodes without any additional owner substitution [6](#0-5) .

This differs from the node-side capability handler in `core/capabilities/vault/gw_handler.go`, which is defensive and explicitly re-derives `Owner` from the authorization result immediately before calling the local `SecretsService` [2](#0-1) . That inconsistency between the two code paths handling the same JSON-RPC method suggests the gateway-side path is missing an equivalent safeguard.

### Impact Explanation
If the vault DON's OCR reporting plugin trusts the `Owner` field embedded in the JSON-RPC request body (rather than independently deriving the owner from the authenticated request signature/JWT claims) when servicing `ListSecretIdentifiers`, an unprivileged client could specify an arbitrary `Owner` value in their request and receive secret identifiers (namespace/key names) belonging to another tenant — an excessive-data-exposure / cross-user response confusion, analogous to CVE-2024-49827.

### Likelihood Explanation
I could **not confirm** whether this is actually exploitable, because I was unable to verify, within the available iterations, whether the vault OCR plugin (`core/services/ocr2/plugins/vault/plugin.go`) or `RequestValidator.ValidateListSecretIdentifiersRequest` independently re-derives/validates `Owner` against the authenticated signer before answering `ListSecretIdentifiers` at the DON layer. If the DON-side plugin ignores the client-supplied `Owner` and instead derives it from the signed request digest/authorization context (similar to how `ValidateCiphertextSizes` uses `authorized.AuthResult.AuthorizedOwner()` rather than the request body for create/update), this finding would be a false positive. This distinction was not resolved with the tools/iterations available.

### Recommendation
Have a Devin session verify:
1. Whether `core/services/ocr2/plugins/vault/plugin.go`'s handling of `ListSecretIdentifiers`/`GetSecrets` derives the owner from the authenticated request (signature/JWT) or trusts the `Owner` field in the request body.
2. If the DON trusts the client-supplied `Owner`, add the same explicit override (`listReq.Owner = authResult.AuthorizedOwner()`) in `GatewayVaultRequestProcessor.processListSecretIdentifiersRequest` / `authorizeAndStamp` as is already done in `core/capabilities/vault/gw_handler.go`, so the gateway-routed path cannot be used to query another owner's secret identifiers.

### Proof of Concept
Not able to construct a concrete working PoC without confirming DON-side owner enforcement (see Likelihood Explanation). Conceptually: an authorized-but-unprivileged client sends a `secrets/list` JSON-RPC request through the public Gateway with `params.owner` set to a different tenant's address; if the DON trusts this field, the response would leak that tenant's secret identifiers.

func (p *GatewayVaultRequestProcessor) processListSecretIdentifiersRequest(
	ctx context.Context,
	req *jsonrpc.Request[json.RawMessage],
) (*AuthorizedGatewayVaultRequest, error) {
	if req.Params == nil {
		return nil, InvalidVaultParamsError{Method: req.Method, Err: errors.New("request params must not be nil")}
	}

	var listReq vaultcommon.ListSecretIdentifiersRequest
	if err := json.Unmarshal(*req.Params, &listReq); err != nil {
		return nil, InvalidVaultParamsError{Method: req.Method, Err: err}
	}
	if p.stripOwnerPrefixForAuth {
		listReq.RequestId = req.ID
		if err := marshalVaultParams(req, &listReq); err != nil {
			return nil, InvalidVaultParamsError{Method: req.Method, Err: err}
		}
	} else {
		listReq.RequestId = coalesceRequestID(listReq.RequestId, req.ID)
	}

	if err := p.validator.ValidateListSecretIdentifiersRequest(ctx, &listReq); err != nil {
		return nil, p.validationError(req, err)
	}

	return p.authorizeAndStamp(ctx, req, func(prefixedRequestID string) error {
		listReq.RequestId = prefixedRequestID
		if listReq.Namespace == "" {
			listReq.Namespace = vaulttypes.DefaultNamespace
		}
		return marshalVaultParams(req, &listReq)
	})
}

func (h *GatewayHandler) handleSecretsList(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage], authResult *AuthResult) *jsonrpc.Response[json.RawMessage] {
	r := &vaultcommon.ListSecretIdentifiersRequest{}
	if err := json.Unmarshal(*req.Params, r); err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.UserMessageParseError, err)
	}
	r.Owner = authResult.AuthorizedOwner()

	h.lggr.Debugw("Processing authorized list secrets request", "request", r.String())
	resp, err := h.secretsService.ListSecretIdentifiers(ctx, r)
	if err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.HandlerError, fmt.Errorf("failed to list secret identifiers: %w", err))
	}
