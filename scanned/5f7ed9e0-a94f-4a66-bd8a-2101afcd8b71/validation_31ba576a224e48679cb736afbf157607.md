### Title
HTTP capability response cache is not scoped by workflow ID, only workflow owner, enabling cross-workflow response confusion - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
The Gondi finding shows that a permissionless action (`mergeTranches`) altered an identifier (`loanId`) that a downstream accounting routine (`_loanTermination`) implicitly trusted to correctly bucket state, causing funds/accounting destined for one recipient (a withdrawal queue) to be silently misattributed to another (the pool). The analogous root cause here is an identifier that downstream logic *documents and is expected* to scope isolation (`WorkflowID`), but which is silently excluded from the actual cache key used to bucket cached HTTP responses, so responses can be served across boundaries they were not intended to cross.

### Finding Description
The HTTP capability gateway handler (v2) caches outbound HTTP action responses so that repeated identical requests do not re-hit the external endpoint. The `responseCache` type is documented as keying entries "by a hash of the request (method, URL, headers, body, workflowOwner)" [1](#0-0)  and the package README explicitly states "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" [2](#0-1) .

However, the actual `Hash()` implementation used as the cache key (`req.Hash()`) does not include `WorkflowID` in the computed hash — verified directly by the test suite: `TestRequestHash` asserts that two requests with different `WorkflowID` values (`"workflow-123"` vs `"workflow-456"`) but identical method/URL produce **the same hash**, while only a differing `WorkflowOwner` changes the hash [3](#0-2) . The cache lookup (`Fetch`) and write (`Set`) both key purely off `req.Hash()` [4](#0-3) , meaning any workflow sharing the same `WorkflowOwner` (e.g. a customer running multiple distinct workflows under one owner address, or workflows that reuse the same identity/owner across tags) but different `WorkflowID`/`WorkflowExecutionID` and issuing a matching HTTP action request (same method/URL/headers/body) will read or poison the same cache slot as another, unrelated workflow.

This is directly reachable from workflow authors submitting HTTP action requests through the internet-facing gateway handler (`gatewayHandler.HandleJSONRPCUserMessage` → node dispatch → `makeOutgoingRequest` → `responseCache.Fetch`/`Set`) [5](#0-4) , with no privileged/operator access required — an unprivileged workflow owner controls the `OutboundHTTPRequest` fields (method, URL, headers, body, cache settings) that determine the hash.

### Impact Explanation
If two logically distinct workflows (different `WorkflowID`/`WorkflowExecutionID`) execute under the same `WorkflowOwner` and happen to construct an HTTP action request with an identical method/URL/headers/body, one workflow's cached response (which may contain sensitive external-endpoint data, e.g., API responses containing per-workflow secrets, tokens, or business data returned from a customer's own endpoint) can be transparently served to the other workflow. This is a cross-workflow response confusion / data leakage bug that violates the documented workflow-level isolation guarantee, even though it does not cross owner boundaries. Given that a single owner can operate many concurrent workflows (e.g. via workflow tags, multiple deployments, or CI/CD test vs prod workflows) that legitimately hit the same third-party endpoint with the same parameters, stale/wrong-workflow data being returned is a realistic and non-benign correctness/leakage issue — directly parallel to the Gondi report's core lesson: an identifier assumed by downstream logic to enforce isolation was not actually load-bearing in the code path that mattered.

### Likelihood Explanation
Likelihood is moderate: it requires two workflows sharing the same `WorkflowOwner` to issue byte-for-byte identical cacheable requests (same method, URL, headers, body) with `CacheSettings.Store`/`MaxAgeMs` set — a plausible occurrence for common integration patterns (e.g., polling the same public API endpoint, or a workflow owner running staging/prod copies of the same workflow). No malicious intent is needed to trigger accidental cross-workflow leakage; a workflow owner could also deliberately craft two workflows to probe/exfiltrate another of their own workflow's cached responses, but true cross-*owner* leakage is not possible since `WorkflowOwner` is included in the hash.

### Recommendation
Include `WorkflowID` (and/or `WorkflowExecutionID`) in `OutboundHTTPRequest.Hash()` so the response cache key matches the documented workflow-scoped isolation guarantee, or explicitly and permanently document/remove the "Workflow Isolation" claim in the README if owner-level scoping is the intended (weaker) guarantee. At minimum, align the code comment in `response_cache.go` (which already omits WorkflowID) with the README to avoid the mismatch, and add a regression test asserting `WorkflowID` inclusion in the hash if isolation-per-workflow is the intended security property.

### Proof of Concept
1. Workflow A (`WorkflowID = "wf-A"`, `WorkflowOwner = "0xOwner"`) issues an HTTP action: `GET https://api.example.com/data` with `CacheSettings{MaxAgeMs: 60000, Store: true}`. The external endpoint returns `{"secret":"A-data"}`, which gets cached under `req.Hash()` (owner+method+URL, no workflow ID) — see `Fetch`/`Set` in [4](#0-3) .
2. Workflow B (`WorkflowID = "wf-B"`, same `WorkflowOwner = "0xOwner"`) issues the identical HTTP action `GET https://api.example.com/data` with `MaxAgeMs > 0`.
3. Because `Hash()` ignores `WorkflowID` (confirmed by `TestRequestHash`'s "having different workflowID results in same Hash" case [6](#0-5) ), workflow B's `Fetch` call hits the cache entry populated by workflow A and returns `{"secret":"A-data"}` without ever contacting the external endpoint — violating the documented per-workflow isolation.

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	// Slow path: singleflight deduplicates concurrent fetches per key.
	// Cache check + store happen inside the flight so the key isn't released
	// until the result is cached, closing the race window between singleflight
	// completion and cache write.
	result, _, _ := rc.flight.Do(cacheKey, func() (any, error) {
		// Re-check cache: a previous flight may have just stored the result.
		rc.cacheMu.RLock()
		cachedResp, exists := rc.cache[cacheKey]
		rc.cacheMu.RUnlock()
		if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
			rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
			return cachedResp.response, nil
		}

		response := fetchFn()

		if storeOnFetch && isCacheableStatusCode(response.StatusCode) {
			rc.cacheMu.Lock()
			rc.cache[cacheKey] = &cachedResponse{
				response: response,
				storedAt: time.Now(),
			}
			rc.cacheMu.Unlock()
		}

		return response, nil
	})

	return result.(gateway.OutboundHTTPResponse)
}

// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}

		URL:              req.URL,

		Body:             req.Body,
