## Analysis

The reachable analog to CVE-2016-0762 is in the local authentication provider's `CreateSession`, which backs the unauthenticated `POST /sessions` login endpoint.

### Title
Username Enumeration via Timing Discrepancy in Local Login Password Verification - (File: core/sessions/localauth/orm.go)

### Summary
`orm.CreateSession` (the login handler invoked by `SessionsController.Create`) looks up the user by email first and returns an error immediately if no matching user is found — *before* any bcrypt password verification is performed. If the email does exist, the request continues on to perform a bcrypt hash comparison (`utils.CheckPasswordHash`), which is deliberately expensive (bcrypt cost factor). This produces two distinguishable response-time classes for an unauthenticated attacker: "fast" (email unknown) vs. "slow" (email known, bcrypt executed), directly mirroring the Tomcat Realm bug class described in CVE-2016-0762/GHSA-wxcp-f2c8-x6xv, where "the supplied password" is "not processed if the supplied user name did not exist."

### Finding Description
`SessionsController.Create` in [1](#0-0)  accepts an unauthenticated `SessionRequest{Email, Password}` and forwards it to `AuthenticationProvider().CreateSession`.

The local ORM implementation does: [2](#0-1) 

```go

	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err

	...
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		...
		return "", pkgerrors.New("Invalid email")

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
```

`FindUser` performs a single indexed SQL lookup [3](#0-2)  that returns quickly whether or not the email exists. If it returns `sql.ErrNoRows` (unknown email), the function returns immediately at line 147 — no bcrypt work is ever performed. Only if the email *does* exist does execution reach `utils.CheckPasswordHash`, which wraps `bcrypt.CompareHashAndPassword` [4](#0-3) . Bcrypt is intentionally slow (typically tens of milliseconds at `bcrypt.DefaultCost`), so the "email exists" path takes measurably longer than the "email does not exist" path — the same "password not processed if the username does not exist" pattern from the reported Tomcat advisory.

Note that the equivalent `TestPassword` methods used for re-authentication on already-authenticated endpoints (`CreateAPIToken`/`DeleteAPIToken`) have this same short-circuit pattern ( [5](#0-4) ), but those require an existing valid session, so they are not reachable by a fully unprivileged caller and don't disclose unauthenticated-caller-relevant secrets — the `CreateSession`/login path is the higher-impact, pre-authentication analog.

### Impact Explanation
An unauthenticated network client can send repeated `POST /sessions` requests with different candidate emails and measure response latency to determine which emails correspond to registered Chainlink node users/admins. This is user/email enumeration — useful reconnaissance for follow-on credential-stuffing, phishing, or brute-force attacks against the node's admin/API-key/edit/run accounts. It does not itself grant authentication or role bypass, matching the "Medium"/"Observable Discrepancy" (CWE-203) classification of the original Tomcat advisory rather than a critical vulnerability.

### Likelihood Explanation
Exploitation only requires network access to the node's HTTP API `/sessions` endpoint and the ability to send repeated timed requests (no credentials or special privileges needed), which is consistent with the CVSS vector in the advisory (`AV:N/AC:H/PR:N/UI:N`). The `AC:H` reflects that reliable timing measurement over a network typically requires statistical sampling to overcome jitter, but is a well-established class of attack (similar to bcrypt-based login timing attacks generally).

### Recommendation
Perform a constant-time-equivalent operation regardless of whether the email exists — e.g., always run `bcrypt.CompareHashAndPassword` against either the real hash (if found) or a fixed dummy/precomputed hash (if not found) before returning any authentication result, so response timing does not depend on whether the account exists. Alternatively, add a randomized or fixed artificial delay to the "not found" path to approximate the cost of a bcrypt comparison, and ensure `constantTimeEmailCompare` is checked using the same code path timing in both branches.

### Proof of Concept
1. Identify a Chainlink node's `/sessions` endpoint (unauthenticated).
2. Send `POST /sessions` with `{"email":"known_admin@example.com","password":"wrong"}` and record response time (bcrypt executed → slower).
3. Send `POST /sessions` with `{"email":"nonexistent@example.com","password":"wrong"}` and record response time (`FindUser` fails immediately, no bcrypt → faster).
4. Repeat over many samples/candidate emails; statistically distinguish existing vs. non-existing accounts by latency, enumerating valid node user emails. [2](#0-1) [1](#0-0) [4](#0-3)

```go
func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}
```

```go
// CheckPasswordHash wraps around bcrypt.CompareHashAndPassword for a friendlier API.
func CheckPasswordHash(password, hash string) bool {
	err := bcrypt.CompareHashAndPassword([]byte(hash), []byte(password))
	return err == nil
}
```
