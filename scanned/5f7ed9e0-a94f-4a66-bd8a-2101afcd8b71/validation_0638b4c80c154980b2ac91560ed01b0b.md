### Title
Full JSON-RPC User Request (Including Auth Token) Logged at Debug Level in Vault Gateway Handler - ([File: core/services/gateway/handlers/vault/handler.go])

### Summary
The chainlink gateway's Vault handler logs the entire, unfiltered `jsonrpc.Request` object — including its `Auth` field and raw `Params` — at Debug level for every user request, before any redaction is applied. This mirrors the Apache NiFi CWE-532 pattern: an operator who raises the log level to Debug (a legitimate, non-privileged-code-path operation) causes sensitive request material (bearer/JWT auth tokens and raw request parameters) to be written to disk in plaintext.

### Finding Description
`HandleJSONRPCUserMessage` unconditionally logs the full inbound request object: [1](#0-0) 

```go
func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	...
	h.lggr.Debugw("handling vault request", "method", req.Method, "requestID", req.ID, "request", req)
```

`req` is the whole `jsonrpc.Request[json.RawMessage]` struct, which carries the `Auth` field used for request authorization — evidenced a few lines later where the code explicitly checks its presence for a separate error log: [2](#0-1) 

```go
	authorized, err := h.requestProcessor.ProcessRequest(ctx, &req, cachedPublicKey)
	if err != nil {
		if vaultcap.IsInvalidVaultParamsError(err) {
			return h.sendImmediateUserResponse(ctx, req, callback, api.InvalidParamsError, err)
		}
		h.lggr.Errorw("request not authorized", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "", "error", err)
```

The `"request", req` field at line 403 logs the object before that authorization check, meaning `req.Auth` (and the raw, unvalidated `Params`) is written to the Debug log for every method — including `MethodSecretsCreate`/`MethodSecretsUpdate`/`MethodSecretsList` requests, before the request has even been validated or redacted.

The project itself is aware this is a live gap: a dedicated regression test explicitly documents and works around the fact that this whole-request Debug log is *not* covered by sanitization, and only tests the separate "invalid params" Error-level log path: [3](#0-2) 

```go
func TestVaultHandler_InvalidParamsDoesNotLogRawParams(t *testing.T) {
	t.Parallel()

	// Observed at Info level so the pre-existing whole-request Debug log is excluded.
	lggr, logs := logger.TestObserved(t, zapcore.InfoLevel)
```

The test comment itself is the strongest confirmation that this is a known, unresolved issue: the harness must filter to Info level specifically to avoid triggering the pre-existing whole-request Debug log, rather than asserting that log is safe.

### Impact Explanation
Chainlink's Vault gateway is an internet-facing entry point that authenticates and authorizes unprivileged client requests (`AuthResult`/`Auth` header/JWT). If Debug logging is enabled — a routine operational action taken by any node operator or administrator with log-level control, not requiring source code access or elevated application privileges — every vault request's authentication material and parameters are persisted to the log file. This can lead to:
- Disclosure of the caller's `Auth` token/JWT used to authorize vault operations, enabling request impersonation/replay against the vault DON.
- Disclosure of raw request parameters for `SecretsCreate`/`SecretsUpdate`/`SecretsList` before validation, which may include owner/namespace identifiers and any other caller-supplied metadata not otherwise redacted.

This matches the CWE-532 class in the referenced advisory: optional, admin-enabled debug logging exposing sensitive request-scoped values that a default (non-debug) configuration would not expose.

### Likelihood Explanation
Debug-level logging is a common, low-friction operational toggle used for troubleshooting on gateway/node deployments. No attacker code execution or bypass of any control is needed — an operator (or automated logging misconfiguration) merely needs to raise the log verbosity, at which point every subsequent vault request from any unprivileged client is captured in full, including its auth field. This is analogous to the NiFi advisory's own likelihood framing ("An authorized administrator with access to change logging levels...").

### Recommendation
- Remove the `"request", req` field from the Debug log at `core/services/gateway/handlers/vault/handler.go:403`, or replace it with a sanitized/redacted projection that excludes `req.Auth` and raw `Params` (similar to the redaction already applied to the "invalid params" Error-level log path).
- Apply the same review to other Debug logs that pass the raw `req`/`getPublicKeyRequest` object, e.g. lines 333, 342, 347, 357 in the same file, to ensure no `Auth`/secret-bearing fields are captured even for public-key fetch flows.
- Add a regression test (extending the pattern already used for `TestVaultHandler_InvalidParamsDoesNotLogRawParams`) that explicitly asserts the whole-request Debug log line does not contain the `Auth` field or raw params, rather than filtering it out of scope.

### Proof of Concept
1. Deploy a Chainlink gateway node with `Log.Level = 'debug'`.
2. Submit any authenticated Vault JSON-RPC request (e.g., `secrets_create`) through the gateway's public HTTP endpoint, including a valid `Auth` token/JWT in the request envelope.
3. Inspect the node's application log: the line `"handling vault request" method=... requestID=... request={... Auth: "<token>", Params: {...}}"` (emitted at `core/services/gateway/handlers/vault/handler.go:403`) contains the full request object, including the caller's `Auth` value, in plaintext. [1](#0-0)
