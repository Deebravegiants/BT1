### Title
Malicious ERC20-Backed Foreign Asset Can Block/Grief Multi-Asset XCM `DepositAsset`/`TransferAsset` Batches - (File: `polkadot/xcm/xcm-executor/src/lib.rs`, `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
The external Putty report describes a Solidity contract where a single malicious token contract embedded among several assets in one bundled operation (`exercise()`/`withdraw()`) can revert on-demand and block the entire multi-asset transfer, denying counterparties their legitimate assets. I looked for an analogous pattern in this repo: a case where multiple heterogeneous assets are transferred/deposited in a single atomic operation, and one asset backed by attacker-controlled, Turing-complete code can fail on demand and abort the whole operation.

### Finding Description
`ERC20Transactor::withdraw_asset_with_surplus` / `deposit_asset_with_surplus` in `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs` (lines 150-306) implement `TransactAsset` for ERC20 tokens by making a `pallet_revive::Pallet::<T>::bare_call` into an arbitrary Solidity contract address resolved via `Matcher::matches_fungibles`. Just like Putty's ERC20/ERC721 calls, this is a call into attacker-influenceable, Turing-complete code that can be made to unconditionally revert (`return_value.did_revert()` → `Err(XcmError::FailedToTransactAsset(...))`), exactly mirroring Putty's "malicious token contract fails under attacker-controlled conditions" pattern [1](#0-0) .

The XCM executor's `DepositAsset`/`TransferAsset`/`InitiateTransfer` instructions batch multiple assets together and process the whole instruction inside `Config::TransactionalProcessor::process`/`self.transactional_process`. `deposit_assets_with_retry` iterates assets and, on a retry-pass failure of any single asset, propagates the error with `?`, causing the surrounding transactional wrapper to roll back the entire instruction (all previously-succeeded per-asset deposits in that instruction are undone) [2](#0-1) . Likewise `TransferAsset` loops over `assets.inner()` calling `transfer_asset_with_surplus` per asset inside one `TransactionalProcessor::process` closure, so one asset's failure aborts the whole `TransferAsset` instruction [3](#0-2) .

This is the structural analog of Putty's bug: several assets bundled for a single atomic transfer, one of which is backed by attacker-controlled code that can revert on demand, causing the whole bundle's transfer to fail.

### Impact Explanation
Unlike Putty, the polkadot-sdk XCM executor already has a mitigating design: on instruction failure, `post_process` traps the entire pre-instruction holding via `Config::AssetTrap::drop_assets`, and the assets are recoverable by the original owner via a subsequent `ClaimAsset` XCM instruction, as demonstrated in the codebase's own tests (`deposit_assets_with_retry_aborts_on_failure_and_post_process_traps`, `partial_deposit_failure_aborts_instruction_and_traps_full_holding`) [4](#0-3) [5](#0-4) . So funds are not permanently locked as in Putty's worst case — they are trapped and recoverable, at the cost of an extra `ClaimAsset` XCM round-trip and gas.

The residual impact is therefore a griefing/DoS: a malicious asset bundled alongside legitimate assets in one XCM `DepositAsset`/`TransferAsset`/`InitiateTransfer` instruction can cause that entire instruction to fail (`Outcome::Incomplete`), delaying/blocking delivery of the co-bundled legitimate assets until the trapped holding is manually reclaimed.

### Likelihood Explanation
Exploitability depends on whether an attacker can get an arbitrary, attacker-controlled ERC20 contract recognized as a valid fungible asset that a victim would unknowingly bundle with their own legitimate assets in the same XCM instruction. From what I could inspect, `asset-hub-westend`'s `ForeignAssets` creation is gated by `ForeignCreators` (restricted to sibling parachains, specific networks, and bridging paths — not fully permissionless) [6](#0-5) , and I was not able to fully confirm within the available context whether the `ERC20Transactor`/its `Matcher` is wired into asset-hub-westend's production `AssetTransactor` tuple with a permissionless mapping from arbitrary `pallet_revive` contract addresses to XCM-recognized assets, or whether such registration is governance-gated. This is a material open question: if registration requires governance/root, the attacker precondition becomes a "trusted-role" barrier that would disqualify this as a high-likelihood, unprivileged-user-exploitable issue. I could not locate the exact `xcm_config.rs` wiring of `ERC20Transactor` within the remaining research budget.

Additionally, even where the failure mode is reachable, the trap/`ClaimAsset` recovery path significantly reduces severity compared to Putty's un-recoverable lock, making this at most a availability/griefing issue rather than a fund-loss issue.

### Recommendation
- Confirm (via a Devin session with full repo access) whether `ERC20Transactor` is included in any production runtime's `AssetTransactor` and whether the underlying `Matcher`/foreign-asset registration is permissionless for arbitrary `pallet_revive` contracts; if so, treat unregistered/foreign ERC20-backed assets with the same caution UIs apply per the Putty acknowledgement (warn users, mark unverified tokens).
- Consider isolating per-asset transactor calls in `TransferAsset`/`InitiateTransfer` similarly to how `deposit_assets_with_retry` already isolates deposits per-asset on the first pass, so that a single malicious/reverting asset transfer doesn't force rollback of already-completed transfers for co-bundled legitimate assets, reducing reliance on the trap-and-reclaim fallback.
- Document clearly (as Putty ultimately did at the UI/DB level) that bundling arbitrary/foreign-asset-backed tokens with trusted assets in one XCM instruction carries availability risk if any bundled asset's execution can be made to revert.

### Proof of Concept
Not applicable as a standalone runnable PoC — this analysis is based on static code review of `deposit_assets_with_retry`, `TransferAsset` instruction handling in `xcm-executor/src/lib.rs`, and `ERC20Transactor` in `erc20_transactor.rs`, combined with existing repo unit tests (`deposit_assets_with_retry_aborts_on_failure_and_post_process_traps`, `partial_deposit_failure_aborts_instruction_and_traps_full_holding`) that already demonstrate the "one failing asset aborts the whole batched instruction, and the whole pre-instruction holding is trapped" behavior [4](#0-3) . I was unable, within the remaining tool budget, to confirm the exact production wiring (registration permissionlessness) needed to fully validate unprivileged-attacker reachability against the `ERC20Transactor` specifically — this should be verified with full repository access before treating this as a confirmed, in-scope finding.

	fn deposit_assets_with_retry(
		to_deposit: AssetsInHolding,
		beneficiary: &Location,
		context: Option<&XcmContext>,
	) -> Result<Weight, XcmError> {
		let mut total_surplus = Weight::zero();
		let mut failed_deposits = AssetsInHolding::new();

		// First pass: try to deposit each asset; failures go to retry.
		for single in to_deposit.into_per_asset_holdings() {
			match Config::AssetTransactor::deposit_asset_with_surplus(single, beneficiary, context)
			{
				Ok(surplus) => total_surplus.saturating_accrue(surplus),
				Err((unspent, _)) => {
					// First-pass failure: keep for retry. A subsequent deposit in the same
					// pass may create the destination account (by satisfying ED), allowing
					// the retry pass to succeed for assets that fall here.
					failed_deposits.subsume_assets(unspent);
				},
			}
		}

		// Retry previously failed deposits, this time short-circuiting on any error.
		for single in failed_deposits.into_per_asset_holdings() {
			let surplus =
				Config::AssetTransactor::deposit_asset_with_surplus(single, beneficiary, context)
					.map_err(|(unspent, error)| {
					tracing::debug!(
						target: "xcm::deposit_assets_with_retry",
						?error,
						?unspent,
						"Retry-pass deposit failed"
					);
					error
				})?;
			total_surplus.saturating_accrue(surplus);
		}

		Ok(total_surplus)
	}

#[test]
fn deposit_assets_with_retry_aborts_on_failure_and_post_process_traps() {
	// fund sender
	add_asset(SENDER, (Here, 200u128));

	// sub-ED amount (< ED=2): this `DepositAsset` will fail and abort the program.
	let dust: Asset = (Here, 1u128).into();

	// ≥ED amount: would succeed on its own — but the program aborts at the first error,
	// so this instruction never runs.
	let legit: Asset = (Here, 100u128).into();

	let xcm = Xcm::<TestCall>(vec![
		WithdrawAsset((Here, 101u128).into()),
		DepositAsset { assets: Definite(Assets::from(vec![dust])), beneficiary: RECIPIENT.into() },
		DepositAsset { assets: Definite(Assets::from(vec![legit])), beneficiary: RECIPIENT.into() },
	]);

	let (mut vm, weight) = instantiate_executor(SENDER, xcm.clone());

	let err = vm
		.bench_process(xcm)
		.expect_err("a sub-ED `DepositAsset` must error out and abort the rest of the XCM");
	vm.set_error(Some((err.index, err.xcm_error)));

	let outcome = vm.bench_post_process(weight);
	assert!(
		matches!(outcome, Outcome::Incomplete { .. }),
		"Expected Incomplete, got {:?}",
		outcome
	);

	// Nothing reached the recipient: the failing `DepositAsset` rolled back its own take,
	// and the subsequent `DepositAsset(legit)` was never executed because the program is
	// already in error state.
	let here_assets = asset_list(RECIPIENT);
	assert!(here_assets.is_empty(), "no deposit should reach recipient when program aborts");

	// `post_process` trapped the leftover holding — the full 101 originally withdrawn.
	let trapped = asset_list(TRAPPED_ASSETS);
	assert_eq!(
		trapped,
		vec![(Here, 101u128).into()],
		"the entire pre-instruction holding must be trapped (claimable later), not silently lost"
	);
}

#[test]
fn partial_deposit_failure_aborts_instruction_and_traps_full_holding() {
	add_asset(SENDER, (Here, 5u128)); // ≥ ED on its own
	add_asset(SENDER, (Parent, 1u128)); // < ED — will fail on retry

	let xcm = Xcm::<TestCall>(vec![
		WithdrawAsset(vec![(Here, 5u128).into(), (Parent, 1u128).into()].into()),
		DepositAsset {
			assets: AssetFilter::Wild(WildAsset::All),
			beneficiary: Location::from(AccountId32 { id: RECIPIENT, network: None }),
		},
	]);

	let (mut vm, weight) = instantiate_executor(SENDER, xcm.clone());

	let err = vm.bench_process(xcm).expect_err(
		"any per-asset deposit failure on the retry pass must abort the whole DepositAsset",
	);
	vm.set_error(Some((err.index, err.xcm_error)));

	let outcome = vm.bench_post_process(weight);
	assert!(
		matches!(outcome, Outcome::Incomplete { .. }),
		"expected Outcome::Incomplete, got {outcome:?}"
	);

	// `post_process` trapped the holding that `transactional_process` restored from the
	// pre-instruction backup — both assets are present.
	assert_eq!(asset_list(TRAPPED_ASSETS), vec![(Here, 5u128).into(), (Parent, 1u128).into()]);
}
