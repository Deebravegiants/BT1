### Title
Fee-on-transfer / non-standard ERC20 tokens break custody accounting in `ERC20Transactor` - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` move ERC20 tokens by calling `IERC20::transfer()` against the token contract and only inspect the boolean success return value; the requested `amount` (not the balance actually moved) is what gets credited into/removed from the XCM `AssetsInHolding` register. This reproduces exactly the "weird-erc20" class of bug from the referenced report (unchecked actual transferred amount for deflationary/fee-on-transfer/rebasing tokens), but here the matcher is fully permissionless.

### Finding Description
`withdraw_asset_with_surplus` withdraws by transferring `amount` from the user to `TransfersCheckingAccount` via a bare EVM call, then, if the call didn't revert and the ABI-decoded return is `true`, unconditionally mints `Erc20Credit(amount)` into the XCM holding register: [1](#0-0) 

`deposit_asset_with_surplus` mirrors this on the way out — it transfers `amount` from the checking account to the beneficiary and, as long as the call succeeds/returns `true`, treats the deposit as fully successful: [2](#0-1) 

Neither path checks the actual balance delta (`balance_after - balance_before`) of the checking account or beneficiary; both simply trust the ERC20 contract's boolean return combined with the pre-computed `amount`. For a standards-compliant ERC20 this is safe, but for fee-on-transfer, deflationary, or rebasing tokens, the amount that actually lands in the checking account (on withdraw) or in the beneficiary (on deposit) can be strictly less than `amount`, while the code still records/releases the full requested `amount` in the XCM holding.

Crucially, matching for this transactor is unrestricted: `ERC20Matcher` matches **any** location of the form `(0, [AccountKey20{ key }])`, i.e. any deployed contract address, with no allow-list or governance-gated registration step: [3](#0-2) 

This is confirmed by the feature's own PRDoc, which states any `AccountKey20` location is matched and its `transfer` function invoked — this is by design meant to let users reference *any* deployed ERC20 contract, not a curated set: [4](#0-3) 

`ERC20Transactor` is wired into the live `AssetTransactors` tuple on Asset Hub Westend, so it is reachable through any regular unprivileged XCM entry point (e.g. `pallet_xcm::execute`, `transfer_assets`) that references an `AccountKey20` asset id: [5](#0-4) 

### Impact Explanation
Because any user can deploy an arbitrary `pallet-revive` contract implementing `IERC20` (including one with transfer fees, deflation, or rebasing behavior) and immediately have it recognized by this transactor with zero registration, a caller can construct an XCM program (`WithdrawAsset` followed by e.g. `DepositAsset`/`BuyExecution`/further hops) where:
- `withdraw_asset_with_surplus` moves less than `amount` into the real checking-account ERC20 balance, yet the executor's in-memory holding is credited with the full requested `amount`.
- That inflated holding amount can then be consumed downstream within the same XCM program (e.g. used to pay execution weight via `TakeFirstAssetTrader::buy_weight`, or deposited onward) as if it were fully-collateralized value, when the real custody balance backing it is smaller.

This is an accounting/state-transition bug: the transactor's bookkeeping is decoupled from the ERC20 contract's real balance movement, letting an attacker extract more XCM-recognized value (or pay less in fees) than what was actually placed into custody.

### Likelihood Explanation
High for an unprivileged attacker: no special permission or asset registration is required — deploying a custom ERC20 via `pallet-revive` and referencing its address as an `AccountKey20` XCM asset id is available to any account, and fee-on-transfer/deflationary/rebasing ERC20 patterns are common and trivial to implement.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, measure the actual balance delta of the checking account / beneficiary (via a `balanceOf` call before and after the `transfer`) and use that measured delta — not the requested `amount` — when constructing/releasing the `Erc20Credit`, mirroring the OpenZeppelin "check balance before/after" mitigation from the referenced report. Alternatively, explicitly document and enforce (e.g. via an allow-list `Matcher`) that only standards-compliant, non-fee-on-transfer, non-rebasing ERC20 contracts may be used with this transactor.

### Proof of Concept
1. Deploy an ERC20 contract via `pallet-revive` whose `transfer` function burns/withholds e.g. 5% of `value` on every call (fee-on-transfer), otherwise ABI-compliant and returns `true`.
2. From an unprivileged account, submit an XCM program via `pallet_xcm::execute` (or `transfer_assets`) with asset id `Location(0, [AccountKey20{ key: <contract_address> }])` and `amount = 1000`, containing `WithdrawAsset` followed by an instruction that consumes the resulting holding (e.g. `BuyExecution` or `DepositAsset` to another account/pallet).
3. Observe: `withdraw_asset_with_surplus` (`erc20_transactor.rs:166-203`) only moves 950 real tokens into `ERC20TransfersCheckingAccount`, but credits `Erc20Credit(1000)` into `AssetsInHolding`.
4. The downstream instruction consuming the holding treats it as 1000 units of fully-custodied value, even though only 950 are actually held in escrow — demonstrating the accounting desync.
