### Title
Missing `para_id` validity check in `do_place_order` allows credit-burning and potential permanent `OrderQueue` exhaustion (`Error::QueueFull` DoS) - (File: polkadot/runtime/parachains/src/on_demand/mod.rs)

### Summary
`Pallet::do_place_order` (invoked by the public extrinsics `place_order_allow_death`, `place_order_keep_alive`, and `place_order_with_credits`) never validates that `para_id` is a registered/onboarded parathread before charging the caller and pushing the order into `OrderStatus::queue`. An unprivileged signed account can therefore place unlimited orders for a bogus `para_id`, burning `Credits::<T>` (or balance) and inflating `Revenue::<T>` for a chain slot that can never consume the purchased core time, and can fill the queue up to `config.scheduler_params.on_demand_queue_max_size`, causing `Error::QueueFull` for legitimate orderers.

### Finding Description
`do_place_order` (`polkadot/runtime/parachains/src/on_demand/mod.rs`, lines 471-558) performs only these checks before enqueuing an order:
- spot price vs. `max_amount` (`Error::SpotPriceHigherThanMaxAmount`)
- queue length vs. `config.scheduler_params.on_demand_queue_max_size` (`Error::QueueFull`)
- balance/credit sufficiency (`Currency::withdraw` or `Credits::<T>` subtraction) [1](#0-0) 

There is no call to `paras::Pallet::<T>::is_parathread`, `is_parachain`, or any check that `para_id` is a lifecycle-valid, onboarded para. `para_id` is pushed unconditionally into the queue: [2](#0-1) 

Since the `paras` module import is only used for the `configuration` type in this file's context and not for validity checks, an attacker holding pre-funded `Credits::<T>` (from a legitimate top-up) can call `place_order_with_credits(max_amount, bogus_para_id)` repeatedly. Each call:
1. Debits `Credits::<T>` for `sender` by the current spot price.
2. Adds `spot_price` to `Revenue::<T>` — attributing revenue to a `para_id` that will never actually receive/consume the coretime, corrupting the accounting the Broker chain later uses to distribute revenue.
3. Pushes `para_id` into `OrderStatus::queue`.

The dequeue side, `pop_assignment_for_cores`, is a generic pop operation with no knowledge of para validity: [3](#0-2) 

The pallet exposes `push_back_order`, explicitly documented for the case "the order could not be served for some reason, give it another chance": [4](#0-3) 

This is the mechanism used by the scheduler/assignment-provider layer when a popped assignment cannot actually be scheduled (e.g., because the para is not a valid parathread with available cores). If the assignment provider re-queues an unserviceable bogus-`para_id` order instead of dropping it, that order will cycle indefinitely between "popped" and "pushed back," continuously occupying a queue slot without ever completing — meaning an attacker filling the queue with such orders can hold the queue at `on_demand_queue_max_size` capacity indefinitely.

### Impact Explanation
- **Credit/balance waste**: Every call to `place_order_with_credits`/`place_order_allow_death`/`place_order_keep_alive` for an invalid `para_id` permanently burns the caller's own credits/balance for blockspace that can never be delivered, since no valid para exists to receive the assignment. (This part self-harms the caller, so its severity alone is limited, but it corrupts `Revenue::<T>` accounting attributed to a nonexistent/invalid para.)
- **Queue DoS**: If unserviceable orders are recycled via `push_back_order` rather than dropped (which the code's own doc-comments imply is the intended behavior for unserved orders), an attacker can occupy some or all of the `on_demand_queue_max_size` slots with bogus, permanently-cycling entries, causing legitimate `place_order_*` callers to receive `Error::QueueFull` — a concrete denial-of-service against the on-demand order queue.
- Revenue misattribution could also cause funds to be teleported/claimed against a broker-chain lease that has no legitimate corresponding para, corrupting cross-chain revenue accounting.

### Likelihood Explanation
- Preconditions are trivial: any account can acquire `Credits::<T>` through the normal legitimate crediting flow (`credit_account`, exposed via configured extrinsic/governance-controlled crediting mechanism, or simply using the `Balance` payment path via `place_order_allow_death`/`place_order_keep_alive`, which requires no special credits at all — just a funded account).
- The call sequence is a single repeated extrinsic call (`place_order_with_credits` or `place_order_allow_death`) with an attacker-chosen `para_id` that was never onboarded (e.g., `ParaId::from(9999999)`), fully reachable via normal signed extrinsic dispatch — no privileged origin needed.
- Reproducibility is deterministic and requires no race conditions; it only depends on `config.scheduler_params.on_demand_queue_max_size` being reasonably small (a known, governance-set configuration value).

### Recommendation
In `do_place_order`, before charging the sender and pushing to the queue, validate that `para_id` refers to a currently onboarded parathread eligible for on-demand assignment, e.g.:
```rust
ensure!(paras::Pallet::<T>::is_parathread(para_id), Error::<T>::InvalidParaId);
```
Additionally, ensure the scheduler/assignment-provider path drops (rather than indefinitely requeues via `push_back_order`) orders whose `para_id` is no longer a valid parathread at assignment time, to prevent stale/invalid entries from permanently occupying queue capacity.

### Proof of Concept
Extend `polkadot/runtime/parachains/src/on_demand/tests.rs`:
1. Set up test config with a small `on_demand_queue_max_size` (e.g., 5).
2. `credit_account(attacker, large_amount)`.
3. Choose `bogus_para_id` that is never passed through `schedule_blank_para` (i.e., not onboarded).
4. Loop calling `OnDemandAssigner::place_order_with_credits(RuntimeOrigin::signed(attacker), max_amount, bogus_para_id)` `on_demand_queue_max_size` times.
   - Assert each call succeeds (`Ok(())`), `Credits::<T>::get(attacker)` decreases each time, and `Revenue::<T>` increases, despite `bogus_para_id` never being validated.
5. Call `OnDemandAssigner::place_order_with_credits(RuntimeOrigin::signed(legit_user), max_amount, valid_para_id)` and assert it returns `Err(Error::<T>::QueueFull)`.
6. Advance blocks and call `pop_assignment_for_cores` to confirm whether entries for `bogus_para_id` are dropped or (per `push_back_order` semantics) re-queued, and assert whether the queue remains permanently full — confirming the DoS condition described.
