## Analysis Result

**Valid analog exists** — the same vulnerability class (spot balance/reserve manipulation via direct token transfer, exposed as an oracle-like price function) exists in `pallet-asset-conversion`.

### Title
Manipulable spot price/reserves via direct-transfer donation to pool account, exposed as an oracle interface without TWAP protection - (File: `substrate/frame/asset-conversion/src/lib.rs`)

### Summary
`pallet-asset-conversion` (explicitly modeled on Uniswap V2) computes pool "reserves" by reading the pool account's *live* token balances on every call, rather than maintaining Uniswap-V2-style cached `reserve0`/`reserve1` state variables updated through `_update` with cumulative TWAP accounting. These live-balance reserves back `get_reserves()`, `quote_price_exact_tokens_for_tokens()`, and `quote_price_tokens_for_exact_tokens()`, which are exposed via the `AssetConversionApi` runtime API and, more recently, via an EVM/PVM precompile (`getReserves`, `quoteExactTokensForTokens`, `quoteTokensForExactTokens`) explicitly intended for third-party contract consumption.

### Finding Description
`get_reserves()` derives the deterministic pool account address and reads its current asset balances directly: [1](#0-0) 

These live balances feed the price-quoting functions used both for actual swaps and for external price queries: [2](#0-1) [3](#0-2) 

The same `get_reserves` and quote logic is exposed through `AssetConversionApi`, documented as the mechanism to "query for an exchange price" and "query the size of a liquidity pool": [4](#0-3) 

It is also exposed to smart contracts via a dedicated precompile, whose `getReserves` implementation calls `pallet_asset_conversion::Pallet::get_reserves()` directly: [5](#0-4) 

The precompile's own PR description states the explicit intent for this to serve as a Uniswap-V2-style oracle for contracts: "Contracts to make routing decisions based on actual liquidity" and "Parity with Uniswap V2's `getReserves` interface that Solidity developers expect." [6](#0-5) 

The pallet's own documentation confirms the Uniswap V2 lineage: [7](#0-6) 

Critically, unlike genuine Uniswap V2 (which pairs its live-balance-derived reserves with `price0CumulativeLast`/`price1CumulativeLast` accumulators for TWAP-safe external consumption — the very mitigation cited in the original report), `pallet-asset-conversion` has **no cumulative/time-weighted price mechanism at all**. Any account can transfer assets or native currency directly to the pool's deterministic account (computed via `T::PoolLocator`) using ordinary `pallet_balances::transfer`/`pallet_assets::transfer` calls — there is nothing pool-account-specific preventing inbound transfers. This directly and instantaneously inflates the value returned by `get_reserves()`/`quote_price_*` and the precompile's `getReserves`/`quoteExactTokensForTokens`/`quoteTokensForExactTokens`.

### Impact Explanation
Any downstream integration — particularly a `pallet-revive` smart contract — that treats the precompile's `getReserves`/quote functions as a reliable spot-price oracle can be fed a manipulated price within a single transaction: an attacker transfers assets into the pool account to skew the balance ratio, triggers the victim contract's price-dependent logic (e.g., collateral valuation, liquidation threshold, swap-routing decision), and then reverses the position via a swap in the same or a follow-up transaction, extracting value from the victim protocol. This mirrors exactly the Caviar `Pair.sol` scenario: the underlying AMM math is fine for direct swaps, but the *exposed price/reserve view is trivially manipulable and unsuitable as an oracle* because it is not decoupled from instantaneous balance and carries no time-weighting.

### Likelihood Explanation
Fully reachable by an unprivileged user: no special origin or privileged role is required to transfer assets to a known/derivable `AccountId`, and the pool address is deterministically computable off-chain via `T::PoolLocator`. The precompile and runtime API are both intentionally public-facing "price/reserve" interfaces, actively documented for external contract/frontend consumption, which is exactly the misuse scenario the original Caviar finding described. Likelihood of *some* integration relying on this as a spot oracle (rather than performing its own TWAP or slippage-checked quote) is realistic given the precompile's stated purpose ("routing decisions based on actual liquidity").

### Recommendation
- Do not present `get_reserves()`/precompile `getReserves` or the raw spot `quote_price_*` outputs as safe price-oracle primitives; documentation should explicitly warn that these reflect instantaneous, donation-manipulable balances.
- Consider adding a Uniswap-V2-style cumulative/time-weighted price mechanism (analogous to `price0CumulativeLast`/`price1CumulativeLast` and `_update`) if this pallet or its precompile is meant to serve as an oracle for other pallets/contracts.
- At minimum, harden any *internal* Polkadot SDK/Cumulus usage of `AssetConversion::get_reserves`/`quote_price_*` (e.g., the XCM fee trader observed using `get_reserves` for refund calculations) to ensure it is never used as a security-critical price source without additional TWAP or bounds checks.

### Proof of Concept
1. Pool exists for `(Native, AssetX)` with reserves `(R1, R2)` via `create_pool`/`add_liquidity`.
2. Attacker computes the deterministic pool account via `T::PoolLocator::pool_address(asset1, asset2)`.
3. Attacker calls `pallet_balances::transfer` (or `pallet_assets::transfer`) to send a large amount of `Native` directly to the pool account — no pallet-asset-conversion extrinsic involved, no LP tokens minted.
4. Any subsequent call to `AssetConversion::get_reserves`, `quote_price_exact_tokens_for_tokens`, or the precompile's `getReserves`/`quoteExactTokensForTokens` now reflects the inflated, attacker-controlled ratio, as demonstrated by the pallet's own reserve/price test pattern reading live pool-account balances directly: [8](#0-7) 
5. A third-party contract or integration consuming this value as an oracle acts on the skewed price; attacker reverses via a swap to recover capital (minus swap fee), completing the manipulation.
