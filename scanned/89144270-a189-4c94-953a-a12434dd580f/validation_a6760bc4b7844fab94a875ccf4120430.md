## Finding

### Title
Missing slippage protection in `SwapFirstAssetTrader::refund_weight` enables MEV-style value extraction during fee refunds - (File: `cumulus/primitives/utility/src/lib.rs`)

### Summary
The external report concerns Uniswap's `Fees::sellProfits()` calling `exactInputSingle` with both `deadline: block.timestamp` (meaningless) and `amountOutMinimum: 0` (no slippage protection), letting a malicious miner/validator manipulate the pool price before the swap executes and capture value from the contract. Polkadot SDK has no "deadline" concept for extrinsics/XCM execution (blocks execute deterministically), so the deadline half of this bug class is not applicable. However, the `amountOutMinimum: 0` half — an unprotected AMM swap executed as part of protocol logic, exploitable by whoever controls transaction/message ordering — has a direct analog in `pallet_asset_conversion`-backed swap helpers.

### Finding Description
`SwapFirstAssetTrader` is a `WeightTrader` used to let XCM messages pay fees in a non-native asset by swapping it into a `Target` fee asset via `SwapCredit`. Its `buy_weight` swap is properly protected (`swap_tokens_for_exact_tokens` targets an exact fee amount). But its `refund_weight` performs the reverse swap — converting unused `Target` fee back into the user's original asset — with **no minimum output specified**: [1](#0-0) 

```rust
let refund = self.total_fee.extract(refund_amount);
let refund = match SwapCredit::swap_exact_tokens_for_tokens(
    vec![Target::get(), refund_swap_asset],
    refund,
    None,   // <-- no amount_out_min, analogous to amountOutMinimum: 0
) { ... }
```

Inside `pallet_asset_conversion`, when `amount_out_min` is `None`, the minimum-output check is skipped entirely: [2](#0-1) 

This mirrors the root cause of the reported Solidity bug: a swap is executed against an AMM pool with zero slippage protection, so whoever controls the ordering of transactions/messages within the block (a collator, in the Cumulus/parachain block-authoring model) can manipulate the relevant pool's reserves immediately before this refund swap executes (e.g., via a sandwich: trade against the pool, let the refund swap execute at a bad price, trade back), extracting value that should have gone back to the fee payer.

### Impact Explanation
Value that should be refunded to whichever account paid XCM execution fees in a non-`Target` asset can be reduced arbitrarily (down to whatever dust the manipulated pool returns), with the difference captured by whoever manipulated the pool price around the refund. This is a direct funds-loss impact analogous to the original report, though the impact is bounded by the size of the `total_fee` outstanding credit (i.e., unspent weight fee) at time of refund, not the whole contract/pallet balance.

### Likelihood Explanation
Exploitation requires the ability to influence transaction/message ordering relative to the pool state at the moment `refund_weight` executes — i.e., control over block construction (a collator/block-builder), the same threat actor explicitly named in the original report ("a malicious miner/validator can hold a transaction until they favor it"). This is a realistic, unprivileged-from-the-user's-perspective threat model in permissionless collator sets, and the `Swap`/`SwapCredit`-based fee mechanisms (`SwapFirstAssetTrader`, and generally any `WeightTrader`/fee-payment integration using `pallet_asset_conversion`) are reachable any time a chain configures non-native asset fee payment for XCM execution.

### Recommendation
Compute and pass a non-`None` `amount_out_min` to `swap_exact_tokens_for_tokens` in `refund_weight`, derived via `QuotePrice::quote_price_exact_tokens_for_tokens` (already used elsewhere in the same file for `quote_weight`) with an acceptable slippage tolerance, and treat a failed/insufficient-output swap as "no refund" (fall back to keeping the credit in `Target`) rather than accepting any price.

### Proof of Concept
1. Configure a parachain runtime with `SwapFirstAssetTrader` as (or among) its `WeightTrader`s, backed by `pallet_asset_conversion`.
2. A user sends an XCM message paying weight fees in asset `X` (not `Target`); `buy_weight` swaps `X` → `Target` for the exact estimated fee.
3. Actual weight consumed is less than estimated, so `refund_weight` triggers, swapping leftover `Target` back to `X` via `swap_exact_tokens_for_tokens(..., None)` at line 540-544.
4. A block-producing collator, prior to including/executing this refund in the block, inserts trades against the `X`/`Target` pool (e.g., via `pallet_asset_conversion::swap_*` extrinsics or other XCM `AssetExchange` calls) to skew the pool's reserves unfavorably for the refund swap, then reverses the trade afterward — a standard sandwich — extracting the difference between the fair refund and the manipulated one. 	fn refund_weight(&mut self, weight: Weight, _context: &XcmContext) -> Option<AssetsInHolding> {
		log::trace!(
			target: "xcm::weight",
			"SwapFirstAssetTrader::refund_weight weight: {:?}, self.total_fee: {:?}",
			weight,
			self.total_fee,
		);
		if weight.is_zero() || self.total_fee.peek().is_zero() {
			// noting to refund.
			return None;
		}
		let refund_asset = if let Some(asset) = &self.last_fee_asset {
			// create an initial zero refund in the asset used in the last `buy_weight`.
			(asset.clone(), Fungible(0)).into()
		} else {
			return None;
		};
		let refund_amount = WeightToFee::weight_to_fee(&weight);
		if refund_amount >= self.total_fee.peek() {
			// not enough was paid to refund the `weight`.
			return None;
		}

		let refund_swap_asset = FungiblesAssetMatcher::matches_fungibles(&refund_asset)
			.map(|(a, _)| a.into())
			.ok()?;

		let refund = self.total_fee.extract(refund_amount);
		let refund = match SwapCredit::swap_exact_tokens_for_tokens(
			vec![Target::get(), refund_swap_asset],
			refund,
			None,
		) {
			Ok(refund_in_target) => refund_in_target,
			Err((refund, _)) => {
				// return an attempted refund back to the `total_fee`.
				let _ = self.total_fee.subsume(refund).map_err(|refund| {
					// error may occur if `total_fee.asset` differs from `refund.asset`, which does
					// not apply in this context.
					defensive!(
						"`total_fee.asset` must be equal to `refund.asset`",
						(self.total_fee.asset(), refund.asset())
					);
				});
				return None;
			},
		};

		let refund = AssetsInHolding::new_from_fungible_credit(refund_asset.id, Box::new(refund));
		Some(refund)
	}
