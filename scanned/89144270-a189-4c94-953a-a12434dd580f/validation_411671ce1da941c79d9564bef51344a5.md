### Title
Ethereum claim signatures are replayable across independent `mint_claim` cycles, allowing redirection of a newly re-minted claim to a stale `dest` - (File: polkadot/runtime/common/src/claims/mod.rs)

### Summary
The `claim`/`claim_attest` unsigned extrinsics are validated by recovering an Ethereum address from a signature over only `prefix || dest` (and optionally a statement), with no nonce, claim-instance identifier, or amount bound into the signed payload. Because `validate_unsigned` only checks `Claims::<T>::contains_key(&signer)` and the storage entry is keyed purely by `EthereumAddress`, a previously broadcast/valid `claim` extrinsic remains fully replayable against any *later*, independent `mint_claim` for the same Ethereum address, redirecting the newly minted funds to the stale `dest` without any new signature from the Ethereum key holder.

### Finding Description
`Pallet::claim` and `Pallet::claim_attest` recover the Ethereum signer via `Self::eth_recover(&ethereum_signature, &data, ...)` where `data = dest.using_encoded(to_ascii_hex)` [1](#0-0) . The signed message is simply `keccak256("\x19Ethereum Signed Message:\n" + len + prefix + dest [+ statement])` [2](#0-1) . There is no nonce, claim value, block number, or mint-cycle identifier included anywhere in the signed payload.

`validate_unsigned` for `Call::claim`/`Call::claim_attest` re-derives the same signer and only asserts `Claims::<T>::contains_key(&signer)` before accepting the extrinsic [3](#0-2) . `Claims` is a flat `StorageMap<EthereumAddress, BalanceOf<T>>` [4](#0-3) , so it carries no information distinguishing one `mint_claim` "cycle" from another for the same address.

`process_claim` pays out the currently-stored balance for `signer` to whatever `dest` is passed in the call, then removes `Claims`, `Vesting`, and `Signing` entries for that signer [5](#0-4) .

Exploit flow:
1. `mint_claim(eth_addr, v1)` is called (root) — `Claims[eth_addr] = v1` [6](#0-5) .
2. The Ethereum key holder signs `prefix || dest_A` and submits `claim(dest_A, sig)`. This passes `validate_unsigned` and `process_claim` pays `v1` to `dest_A`, then deletes `Claims[eth_addr]` [7](#0-6) . The extrinsic (with `dest_A` and `sig`) is now permanently visible on-chain/in history.
3. Later, root calls `mint_claim(eth_addr, v2)` again for the same Ethereum address — e.g. topping up, re-issuing, or correcting a prior claim, with the expectation that a *new* signature over the intended new destination will be produced.
4. Any unprivileged actor resubmits the exact same, previously-successful `claim(dest_A, sig)` extrinsic (no new signing required — it's just the old bytes). `validate_unsigned` recovers the same `eth_addr` from `sig`/`dest_A`, finds `Claims::contains_key(eth_addr) == true` (because of step 3), and the transaction is accepted and included.
5. `process_claim` executes again, paying `v2` to `dest_A`, even though the second mint was intended to require a fresh signature/destination.

No check ties the signature to a specific minting instance, amount, or block, so the "destination binding" is only as fresh as the *first* claim ever made for that address — any subsequent independent mint for the same address inherits the old binding for free.

### Impact Explanation
Funds newly minted via a second, independent `mint_claim` for an Ethereum address that was previously fully claimed and paid out can be automatically and unconditionally redirected to the original `dest` from the first claim cycle, without any consent or fresh signature from the Ethereum key holder or governance's intended recipient. This is an unauthorized redirection of claim funds, matching the scoped impact exactly.

### Likelihood Explanation
The preconditions require governance to `mint_claim` twice for the same Ethereum address across the address's lifetime (once, fully claimed/removed, then again later) — a plausible administrative action (e.g., correcting an error, re-issuing a claim, or crediting more DOTs to the same known Ethereum address). Once that happens, exploitation is trivial and fully realizable by any unprivileged actor: simply resubmit the historical `claim` extrinsic bytes (publicly available from chain history/explorers) to the transaction pool. No new cryptographic material, privileged origin, or interaction with the Ethereum key is needed.

### Recommendation
Bind the signed message to the specific claim instance rather than only to `dest`. For example, include a per-address "claim epoch"/nonce (incremented on every `mint_claim` for that address) or the claim `value`/mint block number in the signed payload (`ethereum_signable_message`), and validate that nonce in `validate_unsigned` and `process_claim`. Alternatively, require `mint_claim` to reject re-minting for an address that has an entry already fully claimed unless it also resets/increments an associated nonce that is mixed into the expected signed message, invalidating any previously valid signature.

### Proof of Concept
Rust unit test in `polkadot/runtime/common/src/claims/tests.rs`:
1. `mint_claim(RuntimeOrigin::root(), eth(&alice_secret()), 100, None, None)`.
2. Build `sig = sig::<Test>(&alice_secret(), &42u64.encode(), &[])` for `dest = 42` (AccountId), call `Claims::claim(RuntimeOrigin::none(), 42, sig.clone())`; assert `Ok(())`, assert `Balances::free_balance(42) == 100`, assert `Claims::claims(eth(&alice_secret())).is_none()`.
3. `mint_claim(RuntimeOrigin::root(), eth(&alice_secret()), 200, None, None)` (simulating a legitimate second mint intended for a different destination, e.g. `dest = 99`, requiring a fresh signature that has not yet been produced).
4. Replay the *original* extrinsic: `Claims::validate_unsigned(TransactionSource::External, &Call::claim { dest: 42, ethereum_signature: sig.clone() })` — assert it returns `Ok(ValidTransaction { .. })` (currently succeeds, demonstrating the bug), then dispatch `Claims::claim(RuntimeOrigin::none(), 42, sig)` and assert `Balances::free_balance(42) == 300` (100 + replayed 200), i.e., the second mint's funds went to the stale `dest = 42` instead of the intended `dest = 99`, with no new signature ever produced for `dest = 99`.

	// Constructs the message that Ethereum RPC's `personal_sign` and `eth_sign` would sign.
	fn ethereum_signable_message(what: &[u8], extra: &[u8]) -> Vec<u8> {
		let prefix = T::Prefix::get();
		let mut l = prefix.len() + what.len() + extra.len();
		let mut rev = Vec::new();
		while l > 0 {
			rev.push(b'0' + (l % 10) as u8);
			l /= 10;
		}
		let mut v = b"\x19Ethereum Signed Message:\n".to_vec();
		v.extend(rev.into_iter().rev());
		v.extend_from_slice(prefix);
		v.extend_from_slice(what);
		v.extend_from_slice(extra);
		v
	}

	// Attempts to recover the Ethereum address from a message signature signed by using
	// the Ethereum RPC's `personal_sign` and `eth_sign`.
	fn eth_recover(s: &EcdsaSignature, what: &[u8], extra: &[u8]) -> Option<EthereumAddress> {
		let msg = keccak_256(&Self::ethereum_signable_message(what, extra));
		let mut res = EthereumAddress::default();
		res.0
			.copy_from_slice(&keccak_256(&secp256k1_ecdsa_recover(&s.0, &msg).ok()?[..])[12..]);
		Some(res)
	}

	fn process_claim(signer: EthereumAddress, dest: T::AccountId) -> sp_runtime::DispatchResult {
		let balance_due = Claims::<T>::get(&signer).ok_or(Error::<T>::SignerHasNoClaim)?;

		let new_total =
			Total::<T>::get().checked_sub(&balance_due).ok_or(Error::<T>::PotUnderflow)?;

		let vesting = Vesting::<T>::get(&signer);
		if let Some(_) = vesting {
			if T::VestingSchedule::vesting_balance(&dest).is_some() {
				return Err(Error::<T>::VestedBalanceExists.into());
			}

			// A vesting schedule installs a balance lock, which requires the account to stay alive,
			// otherwise it is dusted and the lock placed on a non-existent account. The `dest` may
			// already hold funds, so a small claim that tops an existing account over the ED is
			// valid.
			let free_after = CurrencyOf::<T>::free_balance(&dest).saturating_add(balance_due);
			ensure!(
				free_after >= CurrencyOf::<T>::minimum_balance(),
				Error::<T>::ClaimBelowExistentialDeposit,
			);
		}

		// We first need to deposit the balance to ensure that the account exists.
		let _ = CurrencyOf::<T>::deposit_creating(&dest, balance_due);

		// Check if this claim should have a vesting schedule.
		if let Some(vs) = vesting {
			// This can only fail if the account already has a vesting schedule or its balance is
			// below the existential deposit, both of which are checked above.
			T::VestingSchedule::add_vesting_schedule(&dest, vs.0, vs.1, vs.2)
				.map_err(|_| Error::<T>::VestedBalanceExists)?;
		}

		Total::<T>::put(new_total);
		Claims::<T>::remove(&signer);
		Vesting::<T>::remove(&signer);
		Signing::<T>::remove(&signer);

		// Let's deposit an event to let the outside world know this happened.
		Self::deposit_event(Event::<T>::Claimed {
			who: dest,
			ethereum_address: signer,
			amount: balance_due,
		});

		Ok(())
	}
