Target: ShopifyAPI::Clients::HttpClient#initialize `@headers['X-Shopify-Access-Token']` assignment guarded only by `session.access_token.nil? || ... .empty?`. Attacker action: attacker forges the Cookie-derived session id to point at a SessionStorage record for 'offline_victim.myshopify.com' that a legitimate merchant installed earlier and whose access_token is present in storage. Preconditions: SessionStorage#load_session keyed purely by the string returned from current_session_id, as documented in getting_started.md. Call sequence: current_session_id (unauthenticated cookie) -> host's SessionStorage.load_session(id) -> returns victim's real Session with real access_token -> HttpClient.new(session: victim_session) attaches victim's real X-Shopify-Access-Token to an attacker-triggered outbound request whose response body may be reflected back to the attacker by the vulnerable host endpoint. Binding: SESSION_DERIVATION and CREDENTIAL DESTINATION combined - the access token attached to a request must belong to the shop that authenticated THIS request; here it belongs to whichever shop's cookie string the attacker guessed. Impact: Critical, direct theft/use of a victim merchant's access token to perform authenticated Admin API calls on their behalf. Proof: minitest with a stub SessionStorage returning a Session(shop: 'victim.myshopify.com', access_token: 'victim-token') keyed by the exact string SessionUtils.current_session_id produces for a forged cookie, then WebMock-asserting the outbound request's X-Shopify-Access-Token header equals 'victim-token' even though the request's origin never presented any bytes authenticated under Context.api_secret_key.
