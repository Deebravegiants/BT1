Target: ShopifyAPI::Clients::HttpClient#initialize `session ||= Context.active_session`. Attacker action: attacker sends two rapid concurrent requests to the same app process: request A carries their own valid shopify_id_token (activating Context.active_session for the attacker's shop), request B (racing, same worker thread pool member if Context.active_session is stored in a thread-unsafe global rather than Fiber/thread-local) carries a forged Cookie: shopify_app_session=offline_victim.myshopify.com. Preconditions: Context.active_session implemented as a class-level mutable global rather than a strictly per-request Thread.current value (must be confirmed against Context source, but SessionUtils itself provides no isolation). Call sequence: HttpClient.new(base_path: ...) with session: nil resolves session via Context.active_session, which if set by a different concurrent request due to a race, is used to build @headers['X-Shopify-Access-Token']. Binding: SHOP BINDING - the shop whose token is attached to a given outbound request must equal the shop authenticated for that specific request, not whichever request last wrote the global. Impact: Critical, cross-tenant token leakage across concurrent requests. Proof: minitest is limited to single-threaded verification that Context.active_session is not reset per call to current_session_id/activate_session unless explicitly invoked, flagging the absence of any per-call isolation guarantee inside SessionUtils itself (documented as a call-sequence gap, not a full race demo).
