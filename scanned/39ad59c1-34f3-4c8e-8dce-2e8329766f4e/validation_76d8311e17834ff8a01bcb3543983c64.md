### Title
Unauthenticated Job Run Resumption via `PATCH /v2/resume/:runID` - ([File: core/web/router.go])

### Summary
The `/v2/resume/:runID` endpoint is registered on the *unauthenticated* router group and lets any network caller inject an arbitrary result (value or error) into a pipeline task run and force resumption of the associated job run, with no session, API token, or external-initiator credential required.

### Finding Description
`v2Routes` explicitly creates an unauthenticated group and attaches the resume handler to it, in contrast to every other mutating route which is wrapped in `auth.Authenticate(...)`: [1](#0-0) 

The handler itself performs no authentication or authorization check on the caller — it only parses `runID` (actually a `pipeline.TaskRun` UUID) from the path and a JSON body, then forwards directly to the application layer: [2](#0-1) 

`ResumeJobV2` → `runner.ResumeRun` then unconditionally updates the task run's output/error in the DB and, if the parent run was `suspended`, flips it back to `running` and restarts pipeline execution with the attacker-supplied value: [3](#0-2) [4](#0-3) [5](#0-4) 

Unlike other authenticated endpoints, there is no verification tying the caller to the job/run owner, no external-initiator authentication (`auth.AuthenticateExternalInitiator`), and no session/token check (`auth.AuthenticateByToken`/`auth.AuthenticateBySession`) as used elsewhere in the same file for comparable operations (e.g. `authv2.POST("/jobs/:ID/runs", ...)` requires `auth.RequiresRunRole`). The only "secret" gating this call is knowledge of the task-run UUID, which is not treated as a credential anywhere else in the codebase (no rate limiting, no expiry, no scoping to a particular caller/bridge).

The code path is knowingly unauthenticated — it logs via `audit.UnauthedRunResumed` — but this is architecturally identical to the reported bug class: a state-mutating operation is exposed with no authorization boundary, and any party that obtains the identifier (leaked via logs, error messages, monitoring, or a compromised low-privilege viewer session that can read run/task details) can freely rewrite pipeline state.

### Impact Explanation
An unauthenticated caller who obtains or guesses a task-run UUID can:
- Inject arbitrary attacker-controlled data as the "output" of an async task (e.g., a pending bridge/external-adapter response), which then flows into downstream tasks such as `ETHTx` — i.e., attacker-controlled data can influence values used to build and broadcast on-chain transactions.
- Force premature/duplicate resumption of a suspended job run, corrupting job state or triggering side effects (transactions, external calls) that were only meant to be triggered by the legitimate external adapter/bridge that owns that pending task.

This matches "unauthorized job run" impact and can lead to fund-movement-adjacent impact if the resumed run drives an on-chain transaction task with attacker data.

### Likelihood Explanation
Likelihood depends on the task-run UUID being disclosed or predictable. Chainlink's task-run IDs are randomly generated UUIDs and are not directly returned in current presenters, which somewhat limits blind exploitation. However, the fundamental design flaw remains: the endpoint enforces zero authentication and relies entirely on ID secrecy as an implicit bearer token — a pattern with a demonstrated history of leaking through logs, error messages, or monitoring dashboards, and one that provides no defense-in-depth (no rate limiting, no expiry enforcement beyond the run being in `suspended` state, no per-caller scoping).

### Recommendation
- Require authentication for `/v2/resume/:runID` scoped to a role capable of resuming runs (e.g., `Run` role) or, if external callback support is required, authenticate via the existing External Initiator mechanism (`auth.AuthenticateExternalInitiator`) bound to the specific bridge that owns the pending task.
- Alternatively/additionally, bind the task UUID to a per-bridge secret (e.g., HMAC-signed callback token) rather than relying on UUID secrecy alone, and add rate limiting/expiry to the resume endpoint.

### Proof of Concept
1. Configure a job with an async/bridge task that suspends the pipeline run awaiting an external callback (task run created with a UUID `taskID`).
2. Any external network entity that obtains `taskID` sends: `PATCH /v2/resume/<taskID>` with body `{"data": {"result": "<attacker-controlled>"}}` and no auth headers.
3. `PipelineRunsController.Resume` (`core/web/pipeline_runs_controller.go:134-161`) accepts the request unauthenticated, calls `app.ResumeJobV2`, which updates the task run's output and restarts the run — completing the job with attacker-supplied data, exactly analogous to calling an unrestricted `initialize`/state-setter function with no access control.

// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
}

func (r *runner) ResumeRun(ctx context.Context, taskID uuid.UUID, value any, err error) error {
	run, start, err := r.orm.UpdateTaskRunResult(ctx, taskID, Result{
		Value: value,
		Error: err,
	})
	if err != nil {
		return fmt.Errorf("failed to update task run result: %w", err)
	}

	// TODO: Should probably replace this with a listener to update events
	// which allows to pass in a transactionalised database to this function
	if start {
		// start the runner again
		go func() {
			ctx, cancel := r.chStop.NewCtx()
			defer cancel()
			if _, err := r.Run(ctx, &run, false, nil); err != nil {
				r.lggr.Errorw("Resume run failure", "err", err)
			}
			r.lggr.Debug("Resume run success")
		}()
	}
	return nil
}

func (o *orm) UpdateTaskRunResult(ctx context.Context, taskID uuid.UUID, result Result) (run Run, start bool, err error) {
	if result.OutputDB().Valid && result.ErrorDB().Valid {
		panic("run result must specify either output or error, not both")
	}
	err = o.transact(ctx, func(tx *orm) error {
		sql := `
		SELECT pipeline_runs.*, pipeline_specs.dot_dag_source "pipeline_spec.dot_dag_source", job_pipeline_specs.job_id "job_id"
		FROM pipeline_runs
		JOIN pipeline_task_runs ON (pipeline_task_runs.pipeline_run_id = pipeline_runs.id)
		JOIN pipeline_specs ON (pipeline_specs.id = pipeline_runs.pipeline_spec_id)
		JOIN job_pipeline_specs ON (job_pipeline_specs.pipeline_spec_id = pipeline_specs.id)
		WHERE pipeline_task_runs.id = $1 AND pipeline_runs.state in ('running', 'suspended')
		FOR UPDATE`
		if err = tx.ds.GetContext(ctx, &run, sql, taskID); err != nil {
			return fmt.Errorf("failed to find pipeline run for task ID %s: %w", taskID.String(), err)
		}

		// Update the task with result
		sql = `UPDATE pipeline_task_runs SET output = $2, error = $3, finished_at = $4 WHERE id = $1`
		if _, err = tx.ds.ExecContext(ctx, sql, taskID, result.OutputDB(), result.ErrorDB(), time.Now()); err != nil {
			return fmt.Errorf("failed to update pipeline task run: %w", err)
		}

		if run.State == RunStatusSuspended {
			start = true
			run.State = RunStatusRunning

			sql = `UPDATE pipeline_runs SET state = $2 WHERE id = $1`
			if _, err = tx.ds.ExecContext(ctx, sql, run.ID, run.State); err != nil {
				return fmt.Errorf("failed to update pipeline run state: %w", err)
			}
		}

		return loadAssociations(ctx, tx.ds, []*Run{&run})
	})

	return run, start, err
}
