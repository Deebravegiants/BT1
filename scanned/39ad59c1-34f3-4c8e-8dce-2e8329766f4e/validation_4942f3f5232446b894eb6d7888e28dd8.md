### Title
Off-by-one boundary in allowlist request expiry check permits authorization exactly at expiry — ([File: core/capabilities/vault/allow_list_based_auth.go])

### Summary
The Kairos report describes a boundary comparison bug where an operator uses a strict `<` check for a time boundary meant to be inclusive, causing an action (liquidation) to become valid one instant earlier than documented. The Chainlink Vault capability's allowlist-based request authorizer has the analogous boundary defect in the opposite direction: it uses a strict `>` comparison to decide when an allowlisted request's authorization has expired, so a request digest with `ExpiryTimestamp = X` is still treated as valid authorization during the entire second `X`, one second past its intended validity window.

### Finding Description
`allowListBasedAuth.AuthorizeRequest` validates that a client-supplied JSON-RPC request's digest is present in the on-chain allowlist and has not expired: [1](#0-0) 

```go
if time.Now().UTC().Unix() > int64(allowlistedRequest.ExpiryTimestamp) {
    ...
    return nil, errors.New("request authorization expired")
}
```

`ExpiryTimestamp` is documented (and used elsewhere in the same package, e.g. `RequestReplayGuard.clearExpiredLocked`) as the boundary after which the authorization should no longer be honored: [2](#0-1)  also uses the same strict-`>` pattern (`if now > expiry { delete(...) }`), consistently treating the exact expiry second as still valid rather than expired.

This is directly analogous to the reported Kairos bug: the boundary timestamp is being evaluated with the wrong inequality operator relative to its documented semantics, extending the validity window by one second beyond what was intended.

This authorization path is reachable by an unprivileged/external client: allowlist-based auth is the default authentication mechanism used by `Authorizer.authorizeRequest` for any Vault gateway request that does not carry a JWT (`req.Auth == ""`), which is explicitly kept for backwards compatibility with existing clients: [3](#0-2) . Requests arrive from the internet-facing gateway and are dispatched into `AuthorizeRequest` by the Vault gateway handler.

### Impact Explanation
The practical security impact is limited: the extension of the authorization validity window is bounded to under one second (the difference between the `ExpiryTimestamp` integer second and the actual expiry instant), since Unix-second timestamps quantize time and `time.Now().UTC().Unix()` truncates sub-second precision. Within that narrow window, a request digest that has technically reached its intended expiry could still be replayed/accepted as authorized (subject to `RequestReplayGuard` digest-based replay protection, which independently prevents the *same* digest from being reused once seen). There is no cross-user impersonation, secret disclosure, or unbounded time extension — the window is at most ~1 second and depends on the allowlisted requester having a valid digest and being the legitimate owner of the workflow, since the authorized owner is still bound to the on-chain allowlist entry's `Owner` field.

### Likelihood Explanation
Low. Exploiting this requires an attacker (or an otherwise-authorized client) to submit their already-authorized request within the same wall-clock second as `ExpiryTimestamp`, which is a narrow timing window and does not by itself grant access to secrets or owners the caller wasn't already authorized for. It is best characterized as a spec/boundary correctness bug rather than a privilege-escalation vector.

### Recommendation
Change the comparison in `allowListBasedAuth.AuthorizeRequest` (and the equivalent check in `RequestReplayGuard.clearExpiredLocked`) from `>` to `>=` so that the exact `ExpiryTimestamp` second is treated as expired, matching the documented "authorization no longer valid after this timestamp" semantics:

```go
if time.Now().UTC().Unix() >= int64(allowlistedRequest.ExpiryTimestamp) {
    return nil, errors.New("request authorization expired")
}
```

### Proof of Concept
1. An allowlisted request is recorded on-chain with `ExpiryTimestamp = T`.
2. A client submits the corresponding JSON-RPC request to the gateway at wall-clock time `T` (i.e., `time.Now().UTC().Unix() == T`).
3. `AuthorizeRequest` evaluates `T > T` → `false`, so the request is treated as authorized even though `T` is meant to be the expiry boundary.
4. The request proceeds to `RequestReplayGuard.CheckAndRecord` and, if not previously seen, is processed as a valid authorized Vault operation — one second beyond the intended expiry.
