### Title
Unrestricted server-side URL fetch in workflow artifact `newHTTPFetcher` bypasses gateway SSRF protections - ([File: core/services/workflows/syncer/v2/fetcher.go])

### Summary
`core/services/workflows/syncer/v2/fetcher.go`'s `newHTTPFetcher` builds an outbound `http.Client` with no IP/port/scheme allowlisting and issues GET requests to a URL derived by joining a configured `baseURL` with an operator/workflow-supplied path fragment (`req.URL`), unlike the gateway's HTTP client path which enforces `safeurl`-based blocking of private/loopback/link-local IPs, disallowed ports, and disallowed schemes.

### Finding Description
`NewFetcherFunc` (`core/services/workflows/syncer/v2/fetcher.go:172-196`) returns either a file-based fetcher or, for `http`/`https` base URLs, `newHTTPFetcher` (`fetcher.go:243-289`). `newHTTPFetcher` constructs a bare `&http.Client{Timeout: 30 * time.Second}` [1](#0-0)  and performs the fetch by joining `baseURL` with a cleaned `req.URL` path and calling `client.Do` directly [2](#0-1) , returning the raw response body content to the caller [3](#0-2) .

This contrasts with the gateway's hardened HTTP client (`core/services/gateway/network/httpclient.go`), which by default blocks loopback/private/link-local IPs, restricts schemes to `http`/`https`, restricts ports to `80`/`443`, and blocks dangerous headers via `safeurl` [4](#0-3) , and which is exercised extensively in tests blocking SSRF-style targets (loopback, `169.254.0.1`, IPv6 loopback, octal/hex/decimal-encoded loopback, etc.) [5](#0-4) . The comment on `NewFetcherFunc` explicitly states this path "bypasses the gateway" [6](#0-5) , meaning none of those SSRF protections apply when this fetcher variant is used to retrieve workflow binary/config artifacts (the same purpose served, elsewhere, by the properly-restricted gateway path in `FetcherService.Fetch` at `fetcher.go:135-170`, which routes through `OutgoingConnectorHandler`/gateway instead of a raw client).

`FetchWorkflowArtifacts` in `core/services/workflows/artifacts/v2/store.go:131-229` calls whichever `FetcherFunc` is configured to retrieve `binaryURL`/`configURL` supplied as part of workflow registration, and returns the fetched bytes (decoded and included) to be stored/used as the workflow's binary and config artifacts [7](#0-6) . If a deployment is configured to use the `newHTTPFetcher`-backed `FetcherFunc` instead of the gateway-routed `FetcherService.Fetch`, an unprivileged workflow owner who controls the artifact URL path component processed by this fetcher could cause the node to make unrestricted server-side HTTP requests and have the response content embedded back into artifact retrieval flows/errors.

### Impact Explanation
If exploitable in a given deployment configuration, this allows an unprivileged actor (a workflow registrant) to cause the node to issue outbound requests to internal-only endpoints reachable from the node's network position, with response bytes and status codes surfaced back through error messages/logs or artifact content — a response-disclosure SSRF matching the CVE-2026-65842 bug class (fetch attacker-influenced URL server-side, disclose fetched content).

### Likelihood Explanation
This is contingent on which `FetcherFunc` implementation is wired up for a given node/environment — the primary production path (`FetcherService.Fetch`) correctly routes through the gateway/`OutgoingConnectorHandler`, which is subject to the gateway's `safeurl`-restricted HTTP client. I could not fully verify, within available tool budget, which deployment paths/configuration select `NewFetcherFunc`/`newHTTPFetcher` over `FetcherService.Fetch` versus the file-based fetcher, nor confirm how attacker-controlled `req.URL` path segments are in the fields referencing this fetcher (`core/services/workflows/syncer/v2/types.go`, `core/services/cre/cre.go`, `core/cmd/shell.go`) — these references exist per `grep_search` but their content was not retrieved in this session due to iteration limits.

### Recommendation
Route all HTTP-based workflow artifact fetching (including `newHTTPFetcher`) through the same SSRF-hardened HTTP client used by the gateway (`core/services/gateway/network/httpclient.go`'s allowlist-based client) rather than a bare `&http.Client{}`, and ensure `baseURL`/`req.URL` composition cannot be steered to arbitrary hosts by workflow-controlled input in any deployment mode that exposes this fetcher path.

### Proof of Concept
Not independently confirmed executable within this session — reachability depends on which fetcher implementation (`newHTTPFetcher` vs. gateway-routed `FetcherService.Fetch`) is active in a given node configuration, which I was unable to fully trace (`core/services/workflows/syncer/v2/types.go`, `core/services/cre/cre.go`, `core/cmd/shell.go` reference `NewFetcherFunc`/`FetcherFunc` but were not read in full before the session ended). A Devin session with fuller access should verify this wiring end-to-end before treating this as confirmed-exploitable.

// NewFetcher creates a new FetcherFunc based on the provided URL configuration
// The implementation supports both file and HTTP(S) URLs and bypasses the gateway
func NewFetcherFunc(baseURL string, lggr logger.Logger) (types.FetcherFunc, error) {
	if baseURL == "" {
		return nil, errors.New("baseURL cannot be empty")
	}

	u, err := url.Parse(baseURL)
	if err != nil {
		return nil, fmt.Errorf("invalid URL: %w", err)
	}

	switch u.Scheme {
	case "file":
		// Ensure the basePath is absolute
		if !filepath.IsAbs(u.Path) {
			return nil, fmt.Errorf("basePath must be an absolute path, got: %s", u.Path)
		}
		return newFileFetcher(u.Path, lggr), nil
	case "http", "https":
		return newHTTPFetcher(baseURL, lggr), nil
	default:
		return nil, fmt.Errorf("unsupported URL scheme: %s", u.Scheme)
	}
}
