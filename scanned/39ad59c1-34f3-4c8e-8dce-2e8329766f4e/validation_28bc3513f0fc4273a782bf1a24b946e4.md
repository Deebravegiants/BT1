### Title
Bridge `OutgoingToken` secret is stored and served in plaintext to any authenticated user regardless of role - ([File: core/web/bridge_types_controller.go], [File: core/web/presenters/bridges.go], [File: core/web/router.go])

### Summary
Chainlink's bridge (external adapter) subsystem stores an `OutgoingToken` — a secret used by the node to authenticate its outbound requests to the configured external adapter — as plaintext in the database, and exposes it unredacted through `GET /v2/bridge_types` and `GET /v2/bridge_types/:BridgeName`, routes that are registered with no role restriction, unlike the mutating bridge routes.

### Finding Description
`BridgeType.OutgoingToken` is stored as a plain DB column (`db:"outgoing_token"`), unlike `IncomingTokenHash`/`Salt`, which are hashed: [1](#0-0) 

The presenter that serializes bridges for the API always includes this value with no redaction and no `omitempty`, in contrast to `IncomingToken` which is explicitly marked "only provided when creating a Bridge": [2](#0-1) 

`BridgeTypesController.Show` and `.Index` return this presenter directly for any request that reaches these handlers: [3](#0-2) 

Route registration shows the asymmetry: mutating bridge endpoints require the `RequiresEditRole` guard, but the read endpoints (`Index`, `Show`) that leak `OutgoingToken` have no role guard at all — only the general authenticated-session/token middleware applies: [4](#0-3) 

This mirrors the reported bug class: a secret (there, a plugin-managed password; here, the bridge's outgoing authentication token) is persisted without protecting its confidentiality and is disclosed to users who hold a lesser privilege level than the one required to create/manage the secret in the first place (there: "Extended Read" users; here: any authenticated node user without the Edit role).

### Impact Explanation
`OutgoingToken` is the credential the Chainlink node uses to authenticate itself to the external adapter it calls. An authenticated but non-privileged Chainlink node user (any role that can reach `/v2/bridge_types` but lacks Edit rights) can read this token in plaintext and use it to impersonate the node when calling the external adapter directly, potentially manipulating adapter behavior, exhausting adapter quotas, or accessing adapter-side functionality gated by that token. This satisfies the "concrete secret disclosure" / "request impersonation" bar from the validation criteria.

### Likelihood Explanation
Any account with basic node API access (a valid session or API token, without Edit privileges) can trigger this by issuing a single unauthenticated-role GET request to `/v2/bridge_types` or `/v2/bridge_types/:BridgeName`. No special conditions, race, or additional privilege escalation is required — the disclosure happens on every normal listing/show call.

### Recommendation
- Redact `OutgoingToken` from `BridgeResource`/`Index`/`Show` responses by default (similar to how `IncomingToken` is only surfaced once, at creation time), or gate its exposure behind `auth.RequiresEditRole`/`RequiresAdminRole` consistent with the mutating routes.
- Consider hashing/encrypting `OutgoingToken` at rest, or providing a one-time reveal / rotate mechanism instead of persistent plaintext retrieval.

### Proof of Concept
1. Create a Chainlink node user with a role that lacks Edit permission but can authenticate to the node's API.
2. As that user, call `GET /v2/bridge_types/<bridgeName>` (or `GET /v2/bridge_types` for all bridges).
3. Observe the JSON response includes `attributes.outgoingToken` in plaintext, e.g. as demonstrated in the existing test asserting `outgoingToken` is always present in the response body: [5](#0-4) 

Note: I was unable to fully verify the exact node user role hierarchy (e.g., whether a distinct "View"/read-only role exists below "Edit") within the remaining investigation budget — this would need confirmation in `core/sessions` or wherever `UserRole`/`auth.RequiresEditRole` is defined, which I could not locate via search before running out of iterations.

func (btc *BridgeTypesController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	bridges, count, err := btc.App.BridgeORM().BridgeTypes(ctx, offset, size)

	resources := make([]presenters.BridgeResource, 0, len(bridges))
	for _, bridge := range bridges {
		resources = append(resources, *presenters.NewBridgeResource(bridge))
	}

	paginatedResponse(c, "Bridges", size, page, resources, count, err)
}

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
