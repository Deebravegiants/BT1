### Title
Fee-asymmetric memory expansion pricing between `MSTORE`/`MLOAD` and `CALLDATACOPY`/`CODECOPY`/`RETURNDATACOPY` due to unmetered `Memory::resize` - ([File: substrate/frame/revive/src/vm/evm/instructions/system.rs])

### Summary
`Memory::resize` performs no gas/weight accounting for the actual heap growth it causes; it only bounds-checks against `EVM_MEMORY_BYTES` and calls `Vec::resize`. All memory-expansion cost therefore comes solely from whatever the caller charges *before* invoking `resize`, and the two families of memory-touching opcodes use incompatible pricing models for the same physical action (growing `Memory` to a target size), making `MSTORE`/`MLOAD`/`MSTORE8` systematically cheaper than `CALLDATACOPY`/`CODECOPY`/`RETURNDATACOPY` for reaching an identical memory footprint.

### Finding Description
`Memory::resize` in [1](#0-0)  only checks the target length against `EVM_MEMORY_BYTES` and grows the underlying `Vec<u8>`; it charges nothing itself, regardless of how many new bytes are allocated.

For `MLOAD`/`MSTORE`/`MSTORE8`, the charge applied before `resize` is a flat, offset-independent `EVMGas(VERYLOW)` (a legacy EVM opcode gas constant, 3 gas) converted to `Weight` at a fixed `WEIGHT_PER_GAS` ratio: [2](#0-1) .

For `CALLDATACOPY`/`CODECOPY`/`RETURNDATACOPY`, the shared helper `memory_resize` charges `RuntimeCosts::CopyToContract(len)` before calling `resize`, where `len` is the copy length (not the target offset either): [3](#0-2) . This cost resolves to `T::WeightInfo::seal_copy_to_contract(len)`, a Substrate host-function benchmark weight that bundles fixed per-call overhead (buffer bounds checks, sandbox memory read, proof-size accounting) plus a per-byte term: [4](#0-3) .

These two charging paths are structurally different pricing models applied to the same underlying resource operation (`interpreter.memory.resize(offset, len)`), and neither scales with the actual memory-growth-driving parameter (`offset`). Because `CopyToContract`'s weight includes fixed host-function-call overhead that is calibrated for the WASM/PVM contracts pallet calling convention, while `EVMGas(VERYLOW)` is a tiny fixed EVM opcode constant scaled by `WEIGHT_PER_GAS`, `seal_copy_to_contract(32)` is materially larger than `VERYLOW * WEIGHT_PER_GAS` for the same 32-byte write/resize outcome. An attacker can therefore always prefer `MSTORE`(and `MLOAD`) over `CALLDATACOPY` to reach any given `Memory` size at strictly lower charged weight, since both ultimately fall through to the same unmetered `Memory::resize`.

This is reachable by any contract deployed and called under `pallet-revive`'s EVM interpreter — no privileged origin is required, only attacker-controlled EVM bytecode executed via a normal call/instantiate extrinsic.

### Impact Explanation
This is a fee/weight-accounting inconsistency rather than an asset-theft or authorization bypass: it allows a contract to reach a given memory footprint (and therefore consume the same amount of node heap/PoV resource) while being charged less weight than the "intended"/benchmarked cost path for that resource, because `Memory::resize` itself carries no cost and the opcode dispatch layer applies two incompatible cost models to the same operation. The scoped impact is "reachable underpriced execution due to cross-opcode accounting asymmetry" for EVM memory growth inside `pallet-revive`'s interpreter — it does not expose a path to steal or duplicate user funds, forge signatures, or bypass extrinsic-level fee/weight limits; it only lets an attacker choose the cheaper of two opcode paths to grow interpreter memory relative to the other, which weakens the intended fee-parity across the EVM instruction set within a single transaction/block weight budget.

### Likelihood Explanation
Fully attacker-controlled: any deployed contract can freely choose to emit `MSTORE`/`MLOAD` instead of `CALLDATACOPY`/`CODECOPY`/`RETURNDATACOPY` to reach the same memory size, with no additional preconditions, signatures, or privileged origin needed. It is trivially repeatable in every call to the affected contract.

### Recommendation
Meter memory expansion cost inside `Memory::resize` itself (or in a single shared pre-check called by every memory-touching opcode) based on the actual growth in words/bytes (`target_len - current_len`), independent of which EVM opcode triggered it, so that `MLOAD`/`MSTORE`/`MSTORE8`/`MCOPY` and `CALLDATACOPY`/`CODECOPY`/`RETURNDATACOPY`/`EXTCODECOPY` all pay an identical, growth-proportional cost for the same resulting `Memory` size, in addition to (not instead of) their respective per-opcode/base costs.

### Proof of Concept
Rust unit test in `substrate/frame/revive/src/vm/evm/instructions/system.rs` (or a shared test module) with a mocked `Ext`/`Interpreter`:
1. Build an interpreter with empty `Memory`.
2. Execute `calldatacopy(offset=X, data_offset=0, len=32)`; record the weight charged via `charge_or_halt` (e.g. instrument a mock `Ext::charge_or_halt` to accumulate `Weight`), then assert `interpreter.memory.size() == word_align(X+32)`.
3. Reset interpreter/memory; execute `mstore(offset=X, value=0)`; record charged weight; assert same final `interpreter.memory.size()`.
4. Assert `weight_calldatacopy > weight_mstore` for equal final memory size — confirming the fee asymmetry — and flag as a bug per the invariant "cost of reaching a given memory size must not depend on which opcode was used to reach it."

	pub fn resize(&mut self, offset: usize, len: usize) -> ControlFlow<Halt> {
		let current_len = self.data.len();
		let target_len = revm::interpreter::num_words(offset.saturating_add(len)) * 32;
		if target_len > crate::limits::EVM_MEMORY_BYTES as usize {
			log::debug!(target: crate::LOG_TARGET, "check memory bounds failed: offset={offset} target_len={target_len} current_len={current_len}");
			return ControlFlow::Break(Error::<T>::OutOfGas.into());
		}

		if target_len > current_len {
			self.data.resize(target_len, 0);
		}

		ControlFlow::Continue(())
	}

pub fn mload<E: Ext>(interpreter: &mut Interpreter<E>) -> ControlFlow<Halt> {
	interpreter.ext.charge_or_halt(EVMGas(VERYLOW))?;
	let ([], top) = interpreter.stack.popn_top()?;
	let offset = as_usize_or_halt::<E::T>(*top)?;
	interpreter.memory.resize(offset, 32)?;
	*top = U256::from_big_endian(interpreter.memory.slice_len(offset, 32));
	ControlFlow::Continue(())
}

/// Implements the MSTORE instruction.
///
/// Stores a 32-byte word to memory.
pub fn mstore<E: Ext>(interpreter: &mut Interpreter<E>) -> ControlFlow<Halt> {
	interpreter.ext.charge_or_halt(EVMGas(VERYLOW))?;
	let [offset, value] = interpreter.stack.popn()?;
	let offset = as_usize_or_halt::<E::T>(offset)?;
	interpreter.memory.resize(offset, 32)?;
	interpreter.memory.set(offset, &value.to_big_endian());
	ControlFlow::Continue(())
}

/// Common logic for copying data from a source buffer to the EVM's memory.
///
/// Handles memory expansion and gas calculation for data copy operations.
pub fn memory_resize<'a, E: Ext>(
	interpreter: &mut Interpreter<'a, E>,
	memory_offset: U256,
	len: usize,
) -> ControlFlow<Halt, Option<usize>> {
	if len == 0 {
		return ControlFlow::Continue(None);
	}

	interpreter.ext.charge_or_halt(RuntimeCosts::CopyToContract(len as u32))?;
	let memory_offset = as_usize_or_halt::<E::T>(memory_offset)?;
	interpreter.memory.resize(memory_offset, len)?;
	ControlFlow::Continue(Some(memory_offset))
}
