## What I found

`substrate/frame/assets/precompiles/src/permit.rs` implements an EIP-2612 "permit" pallet — the same general pattern class as the Harpie bug (ECDSA signature-based state-changing calls). Its `ecrecover` function recovers a signer from a `(v, r, s)` secp256k1 signature via `secp256k1_ecdsa_recover` [1](#0-0) .

Unlike the vulnerable OpenZeppelin `<4.7.3` ECDSA library (which allowed both `(r,s)` and its malleable counterpart `(r, n-s)` to recover to the same signer), this pallet explicitly rejects high-`s` signatures before ever calling recovery:

```rust
fn is_s_value_valid(s: &[u8; 32]) -> bool { ... }
```
`ecrecover` calls this check first and returns `Error::SignatureSValueTooHigh` if `s` is in the upper half of the curve order [2](#0-1) . This is precisely the low-`s` normalization check that OpenZeppelin's ECDSA 4.7.3 fix added, so the malleable counterpart signature is rejected outright.

Additionally, even without that check, the replay-protection design differs fundamentally from the vulnerable Harpie pattern: the nonce is baked into the signed digest itself (`permit_digest` includes `nonce` as part of the EIP-712 struct hash) [3](#0-2) , and `use_permit` atomically verifies and increments the nonce in the same call [4](#0-3) . This means a malleable signature `(r, n-s, v')` recovers to the *same* signer for the *same* nonce value — it does not let an attacker resurrect an old/stale request, because the nonce (not the raw signature bytes) is what's checked for freshness/replay, not "has this exact signature been seen before." This is architecturally different from the Harpie bug, where the signature bytes themselves were used as the replay-protection key, so a malleable variant bypassed the "already used" check.

Tests confirm both properties are enforced: `ecrecover_rejects_high_s_value` [5](#0-4)  and replay-rejection tests like `use_permit_rejects_replay_of_consumed_permit` [6](#0-5) .

## Other ECDSA recovery sites checked

I also checked other secp256k1 recovery call sites in `pallet_revive` (EVM-compat precompiles/transactions) and `sp_io::crypto`:
- The `ecrecover` builtin precompile [7](#0-6)  and EVM transaction signature recovery [8](#0-7)  intentionally mirror Ethereum's `ecrecover` semantics (which is malleable by design, matching mainnet Ethereum behavior — this is expected/standard, not a bug, since Ethereum tooling and consensus already tolerate this at the EVM opcode level and it isn't used there for replay-protection keying).
- The raw `sp_io::crypto::secp256k1_ecdsa_recover` host function itself does not enforce low-`s`, by design, since it's a generic primitive [9](#0-8) ; it is up to callers to add malleability protection where signatures are used for state-changing authorization/replay checks, which is exactly what `permit.rs` does.

I did not find any pallet where a raw ECDSA signature (or other malleable signature scheme) is itself used as the deduplication/replay key for an unprivileged, attacker-reachable state-changing call, which is the precise root cause pattern from the Harpie report.

**Conclusion:** No valid analog vulnerability found — the one comparable code path (`pallet_assets` permit precompile) already implements low-`s` normalization plus nonce-in-digest replay protection, closing off the exact attack described in the external report.

		pub fn ecrecover(
			digest: &[u8; 32],
			v: u8,
			r: &[u8; 32],
			s: &[u8; 32],
		) -> Result<H160, Error<T>> {
			// Check signature malleability: s must be in lower half of curve order
			if !Self::is_s_value_valid(s) {
				return Err(Error::<T>::SignatureSValueTooHigh);
			}

			// Convert v to recovery_id (Ethereum v is 27 or 28, recovery_id is 0 or 1)
			let recovery_id = v.checked_sub(27).ok_or(Error::<T>::InvalidVValue)?;
			if recovery_id > 1 {
				return Err(Error::<T>::InvalidVValue);
			}

			// Build signature in format expected by secp256k1_ecdsa_recover: [r, s, recovery_id]
			let mut sig = [0u8; 65];
			sig[0..32].copy_from_slice(r);
			sig[32..64].copy_from_slice(s);
			sig[64] = recovery_id;

			// Recover uncompressed public key (64 bytes)
			let pubkey =
				secp256k1_ecdsa_recover(&sig, digest).map_err(|_| Error::<T>::InvalidSignature)?;

			// Convert public key to Ethereum address: keccak256(pubkey)[12..]
			let hash = keccak_256(&pubkey);
			let mut address = H160::zero();
			address.0.copy_from_slice(&hash[12..]);

			Ok(address)
		}

			&p.value,
			&p.deadline,
			p.v,
			&p.r,
			&p.s,

			},
			Err(_) => Vec::new(),

	fn secp256k1_ecdsa_recover(
		sig: PassPointerAndRead<&[u8; 65], 65>,
		msg: PassPointerAndRead<&[u8; 32], 32>,
	) -> AllocateAndReturnByCodec<Result<[u8; 64], EcdsaVerifyError>> {
		let rid = libsecp256k1::RecoveryId::parse(
			if sig[64] > 26 { sig[64] - 27 } else { sig[64] } as u8,
		)
		.map_err(|_| EcdsaVerifyError::BadV)?;
		let sig = libsecp256k1::Signature::parse_overflowing_slice(&sig[..64])
			.map_err(|_| EcdsaVerifyError::BadRS)?;
		let msg = libsecp256k1::Message::parse(msg);
		let pubkey =
			libsecp256k1::recover(&msg, &sig, &rid).map_err(|_| EcdsaVerifyError::BadSignature)?;
		let mut res = [0u8; 64];
		res.copy_from_slice(&pubkey.serialize()[1..65]);
		Ok(res)
	}
