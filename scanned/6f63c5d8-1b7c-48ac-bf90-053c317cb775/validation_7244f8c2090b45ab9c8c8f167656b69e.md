## Analysis

I found a valid analog to the THORChain fee-on-transfer bug in this codebase's `ERC20Transactor`, which is the XCM `TransactAsset` implementation used by Asset Hub to move value in and out of ERC20 contracts hosted on `pallet-revive`.

The `ERC20Matcher` type confirms this transactor is wired to *any* local `AccountKey20` location, i.e. any ERC20 contract address deployed via `pallet-revive`, without a permissioned allow‑list at the type level: [1](#0-0) 

### Title
Fee-on-transfer / non-standard ERC20 tokens cause XCM value inflation in `ERC20Transactor::withdraw_asset_with_surplus` and custody-account drain in `deposit_asset_with_surplus` - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Transactor` bridges XCM's `TransactAsset` interface to arbitrary ERC20 contracts on `pallet-revive` by issuing a Solidity `transfer(to, value)` call and treating a `true` return value as proof that exactly `amount` moved. It never re-reads on-chain balances to confirm the actual amount transferred. For a fee-on-transfer, rebasing, or otherwise non-standard ERC20 token, the real amount credited/debited can differ from `amount`, causing the XCM holding register to be inflated relative to what the custody (`TransfersCheckingAccount`) account actually holds.

### Finding Description
In `withdraw_asset_with_surplus`, the transactor transfers `amount` from `who` to `TransfersCheckingAccount` via a raw `IERC20::transferCall`, and on `is_success == true` unconditionally mints an `AssetsInHolding` credit of exactly `amount`: [2](#0-1) 

If the ERC20 contract implements a transfer fee, burn-on-transfer, or any other deviation from the naive balance-additivity assumption (the exact class of token used in the THORChain PoC), `TransfersCheckingAccount` receives less than `amount`, yet the XCM executor is handed a holding register that claims the full `amount` was withdrawn. That inflated holding can subsequently be deposited elsewhere in the same XCM (e.g., minted as a foreign asset on another chain, or swapped through `pallet-asset-conversion`), meaning more value leaves the system than was actually backed by the custody account.

The mirrored code path, `deposit_asset_with_surplus`, has the analogous problem in reverse: it transfers `amount` out of the custody account to the beneficiary and treats a `true` return value as full settlement, without verifying the beneficiary actually received `amount`: [3](#0-2) 

If the token takes a fee on the outbound leg, the custody account is debited by more (via the transfer call itself, from the token's internal accounting) while `what` — the XCM holding being consumed — is treated as fully spent regardless of what the beneficiary actually received; any shortfall becomes an unbacked, unrecoverable loss with no accounting adjustment or event distinguishing it, unlike `pallet-assets::do_transfer`, which returns the actual `credit` amount and is used by all internal callers: [4](#0-3) 

Contrast this with the FRAME-native `fungible`/`fungibles` `transfer` implementations, which decrease/increase balances internally under the pallet's own control and return the actual moved amount — there is no external contract call whose side effects can diverge from the requested amount: [5](#0-4) 

The `ERC20Transactor` is architecturally different: it is the one place in this codebase's in-scope XCM/Asset-Hub logic that performs an *external, arbitrary-contract* `transfer()` call and then assumes the requested amount, rather than the actual delta, was moved — exactly the root cause pattern in the THORChain finding.

### Impact Explanation
- **Withdraw path**: an attacker can deploy their own fee-on-transfer ERC20 contract via `pallet-revive` (contract deployment is permissionless), have it matched by `ERC20Matcher` (any `AccountKey20` location matches), and initiate an XCM `WithdrawAsset`/reserve-transfer using that token. Each such XCM creates holding credit for `amount` while only `amount - fee` actually reaches `TransfersCheckingAccount`. If this credit is deposited into another chain/pool as backed value, this constitutes value inflation / a violation of the backing invariant for the custody account, potentially compounding into deposit_asset shortfalls or accounting corruption of pools that use the ERC20 as an asset kind.
- **Deposit path**: repeated small transfers out of the custody account will progressively drain more of its actual token balance than the aggregate `amount`s recorded as consumed by the XCM executor, mirroring the "griefing" of the THORChain `Aggregator`, here griefing the shared `TransfersCheckingAccount`.

Both are unprivileged, permissionless, and require no trusted-role compromise — any user able to deploy a contract on `pallet-revive` and send/receive an XCM message can trigger this.

### Likelihood Explanation
Likelihood depends on whether/how Asset Hub's runtime actually wires `ERC20Transactor`/`ERC20Matcher` into its live `XcmConfig`'s `AssetTransactor` for user-reachable XCM instructions (`WithdrawAsset`, `DepositAsset`, reserve/teleport handling), and whether ERC20 tokens registered this way can be freely created by any user (rather than requiring a governance-gated registration step that could reasonably exclude non-standard tokens). I found references to `ERC20Transactor`/`ERC20Matcher` wired into `asset-hub-westend`'s `xcm_config.rs`, but could not fully confirm within the available index whether there is an additional permission gate (e.g., asset registration/whitelisting) between "any deployed contract" and "matched by the XCM executor as a transactable fungible" — this would materially affect exploitability and should be verified directly in `cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs`.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read the counterparty's on-chain balance (or use the `transfer` return delta) before and after the `bare_call`, and use the *actual* observed balance change as the credited/debited amount instead of blindly trusting the boolean return value and the requested `amount`, mirroring the general "safeTransfer" pattern recommended in the original THORChain report (check real balance delta, not just call success).

### Proof of Concept
Conceptual PoC (cannot be executed in this ask-only environment, but the mechanism is directly analogous to the ERC-4626/ERC-20 fee-on-transfer PoC in the referenced report):
1. Deploy a fee-on-transfer ERC20 contract via `pallet-revive` (e.g., a PSP22/Solidity contract charging 1% on every `transfer`).
2. Register/use this contract's `AccountKey20` location as an XCM fungible asset (matched automatically by `ERC20Matcher` since it only checks the location shape, not a registry).
3. Initiate an XCM program invoking `WithdrawAsset` for `amount` of this token from an account holding it; `ERC20Transactor::withdraw_asset_with_surplus` transfers `amount` to `TransfersCheckingAccount`, which actually receives `amount * 0.99`, but the function returns `AssetsInHolding` with `Erc20Credit(amount)` (the full, un-discounted value) — [6](#0-5) .
4. Have the XCM program `DepositAsset` this holding into a destination that mints/records `amount` (not `amount * 0.99`) as backed value, creating a 1% discrepancy between the custody account's real ERC20 balance and the system's recorded backing, repeatable to compound the shortfall.

	/// Reduces the asset `id` balance of `source` by some `amount` and increases the balance of
	/// `dest` by (similar) amount.
	///
	/// Returns the actual amount placed into `dest`. Exact semantics are determined by the flags
	/// `f`.
	///
	/// Will fail if the amount transferred is so small that it cannot create the destination due
	/// to minimum balance requirements.
	pub fn do_transfer(
		id: T::AssetId,
		source: &T::AccountId,
		dest: &T::AccountId,
		amount: T::Balance,
		maybe_need_admin: Option<T::AccountId>,
		f: TransferFlags,
	) -> Result<T::Balance, DispatchError> {
		let (balance, died) =
			Self::transfer_and_die(id.clone(), source, dest, amount, maybe_need_admin, f)?;
		if let Some(Remove) = died {
			T::Freezer::died(id.clone(), source);
			T::Holder::died(id, source);
		}
		Ok(balance)
	}
