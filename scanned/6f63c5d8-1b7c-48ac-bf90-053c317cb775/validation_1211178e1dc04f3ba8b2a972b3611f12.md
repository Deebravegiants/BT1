### Title
Stale oracle price data can be consumed indefinitely because `pallet-oracle`'s aggregated `Values` storage is never re-validated for freshness at read time - (File: `substrate/frame/honzon/oracle/src/lib.rs`)

### Summary
The external Chainlink report flags use of `latestAnswer()` without freshness/round-completeness checks, which can silently return stale price data to consumers. `pallet-oracle` in this repo exhibits an analogous pattern: staleness (`ExpiresIn`) is only checked at the moment new data is *fed*, not at the moment data is *read* by a consuming pallet, so a consumer calling `DataProvider::get()` can receive an arbitrarily old aggregated value with no on-chain signal that it is stale.

### Finding Description
`DefaultCombineData::combine_data` filters out raw feeder submissions older than `ExpiresIn` before recomputing the median, and falls back to `prev_value` if too few fresh submissions remain: [1](#0-0) 

Crucially, this staleness check only executes inside `do_feed_values`, which is only invoked when an operator calls `feed_values` (or `DataFeeder::feed_value`): [2](#0-1) 

The final aggregated value lives in the `Values` storage map, and `Pallet::get()` simply returns whatever is currently stored there with no timestamp/expiry validation at read time: [3](#0-2) 

This is exposed to consumers via the `DataProvider` trait implementation, which strips the timestamp entirely and returns only the raw value: [4](#0-3) 

and via the `DataProviderExtended::get_all_values`, and the runtime API exposed to RPC clients: [5](#0-4) 

If oracle operators stop submitting data (e.g., go offline, are slashed/removed from membership, or simply choose not to feed a particular key), `Values<T, I>` retains the last combined value forever. No re-combination is triggered by the passage of time — `combined()` is only ever called from `do_feed_values`, never from a hook like `on_finalize`. Any pallet that consumes oracle data through `T::PriceOracle: DataProvider<...>` (the common integration pattern for pallets like `pallet-psm` or a CDP/lending pallet) obtains only the bare `Value` with the timestamp discarded, so even if it wanted to enforce its own additional staleness guard, `DataProvider::get()` gives it no way to do so; it would have to bypass the trait and call `RawValues`/`Values` directly and reimplement freshness logic itself.

This mirrors the Chainlink `latestAnswer()` issue precisely: a "get current price" API exists that returns a bare value without freshness metadata, while a separate, richer API path (`latestRoundData` / `read_raw_values`+timestamp) that does carry freshness information is not the one wired into the primary consumer interface (`DataProvider`).

### Impact Explanation
Any FRAME pallet built on top of `pallet-oracle`'s `DataProvider` trait (the intended, documented consumption path per the pallet's own README: "other pallets can use the `DataProvider` trait to read the aggregated data") receives a price/value with no built-in guarantee of freshness. If oracle feeders stop reporting (voluntarily, due to a bug, network partition, or removal from the `Members` set without a corresponding governance action to also handle the stale `Values` entry), a consuming financial pallet (e.g., a stablecoin/CDP module) could use an outdated price for liquidations, collateral valuation, or minting/redemption decisions, leading to economic loss or unfair liquidations for users. Whether this rises to protocol-level impact depends entirely on which downstream pallet actually consumes `pallet-oracle` prices and whether *that* pallet independently enforces a staleness bound using the timestamp obtained via `read_raw_values`/`get` on `TimestampedValueOf` rather than the plain `DataProvider::get()`.

### Likelihood Explanation
The condition (oracle operators pausing/stopping submissions for a given key, whether due to outage, key deprecation, or malicious/negligent operator behavior) is realistic and requires no special privilege from an attacker — it is a passive/liveness failure rather than an active exploit, similar to the original Chainlink report's realistic failure mode (feed deprecation). However, I could not confirm within this repository that any in-tree consuming pallet (e.g., `pallet-psm`, referenced alongside `pallet_oracle::Config` in `substrate/bin/node/runtime/src/lib.rs`) actually calls `DataProvider::get()` on price data for a security-critical decision without its own additional staleness check — the searches for such wiring (`PriceProvider`, `OraclePriceProvider`, `Oracle::get(`) in `substrate/frame/psm` and elsewhere returned no matches. This means the vulnerable *pattern* (bare-value API lacking freshness data) exists at the pallet-oracle layer, but I cannot confirm a concrete reachable, unprivileged-user-exploitable path through an actual consumer in this codebase without further investigation of `pallet-psm` or other oracle-consuming pallets' internal implementation, which was not fully explorable within the available searches.

### Recommendation
- Add an explicit staleness check inside `pallet_oracle::Pallet::get()` (or provide a `get_no_op`/`get_checked` variant) that compares the stored `TimestampedValue::timestamp` against `T::Time::now()` and `ExpiresIn`, returning `None` if stale, rather than only filtering staleness during aggregation.
- Change `DataProvider::get()` (or add a new trait method) to surface the `TimestampedValue` (value + timestamp) instead of discarding the timestamp, so that consuming pallets can enforce their own maximum-age policy at the point of use — analogous to using `latestRoundData()` and checking `updatedAt`/`answeredInRound` instead of `latestAnswer()`.
- Audit any in-tree or downstream pallet that integrates with `pallet-oracle::DataProvider` (e.g., PSM/CDP-style pallets) to confirm they independently bound the acceptable age of the price before using it for state-changing decisions.

### Proof of Concept
1. Configure `pallet_oracle::Config::CombineData = DefaultCombineData<Runtime, MinimumCount, ExpiresIn>` as done in `substrate/bin/node/runtime/src/lib.rs` lines 3152-3165. [6](#0-5) 
2. Operators feed a value for key `K` at time `T0`, which aggregates and stores `Values[K] = (value, T0)`.
3. All operators stop calling `feed_values` for key `K` (offline, removed from `Members`, or simply idle).
4. Time advances far beyond `ExpiresIn`. `Values[K]` is never recombined/cleared because `combined()` is only invoked from `do_feed_values`.
5. A downstream pallet or off-chain consumer calls `Pallet::<Runtime, I>::get(&K)` (or the `DataProvider::get` trait method used by `PriceOracleApi`/runtime API), and receives the original stale `value` with no on-chain error, exactly as `latestAnswer()` would return the last-reported price without indicating it is stale. [4](#0-3)

	fn combine_data(
		_key: &<T as Config<I>>::OracleKey,
		mut values: Vec<TimestampedValueOf<T, I>>,
		prev_value: Option<TimestampedValueOf<T, I>>,
	) -> Option<TimestampedValueOf<T, I>> {
		let expires_in = ExpiresIn::get();
		let now = T::Time::now();

		values.retain(|x| x.timestamp.saturating_add(expires_in) > now);

		let count = values.len() as u32;
		let minimum_count = MinimumCount::get();
		if count < minimum_count || count == 0 {
			return prev_value;
		}

		let mid_index = count / 2;
		// Won't panic as `values` ensured not empty.
		let (_, value, _) =
			values.select_nth_unstable_by(mid_index as usize, |a, b| a.value.cmp(&b.value));
		Some(value.clone())
	}

	fn do_feed_values(who: T::AccountId, values: Vec<(T::OracleKey, T::OracleValue)>) {
		let now = T::Time::now();
		for (key, value) in &values {
			let timestamped = TimestampedValue { value: value.clone(), timestamp: now };
			RawValues::<T, I>::insert(&who, key, timestamped);

			// Update `Values` storage if `combined` yielded result.
			if let Some(combined) = Self::combined(key) {
				<Values<T, I>>::insert(key, combined);
			}

			T::OnNewData::on_new_data(&who, key, value);
		}
		Self::deposit_event(Event::NewFeedData { sender: who, values });
	}
