### Title
Non-atomic per-signal weight metering in XCMP `Signals` page processing can leave a channel permanently suspended - (File: cumulus/pallets/xcmp-queue/src/lib.rs)

### Summary
The `Signals` branch of the inbound XCMP message handling loop consumes weight from the `WeightMeter` on a **per-signal** basis while decoding a `Signals`-format page, rather than reserving the full worst-case weight for the page up front. If the meter runs out mid-page (e.g. after a `Suspend` signal has already been applied but before the paired `Resume` is decoded), the loop `break`s, logs a defensive message, and the function still returns as if the message were fully processed, silently discarding the remaining signal bytes. This can leave `InboundXcmpSuspended` permanently set for the affected sibling channel with no corresponding `Resume` ever being applied.

### Finding Description
Inbound XCMP messages are dispatched via the `ProcessMessage`/`XcmpMessageHandler` machinery in `cumulus/pallets/xcmp-queue/src/lib.rs`. When a page's format is `XcmpMessageFormat::Signals`, the pallet decodes a stream of `ChannelSignal` values (`Suspend`/`Resume`) out of the page body in a loop, applying each signal (`Self::suspend_channel(para)` / `Self::resume_channel(para)`) and charging `meter.try_consume(T::WeightInfo::suspend_channel())` for each iteration before/while decoding the next signal.

Because the weight check happens *incrementally inside the loop* rather than being reserved for the *whole page* before any signal is applied, the loop can process an arbitrary prefix of signals — including a `Suspend` — and then run out of weight budget before reaching a later `Resume` in the same page. When `try_consume` fails, the code logs a defensive warning/error and `break`s out of the loop instead of propagating a hard failure (e.g. `ProcessMessageError::Overweight`) that would cause the message-queue to retry the page later with a larger weight budget. The function returns as though the message was consumed, so the un-decoded trailing bytes (containing the `Resume`) are dropped forever, not requeued.

This is a partial-application bug: state mutations that already happened (the `Suspend` toggling `InboundXcmpSuspended`) are not rolled back when the remainder of the page fails to be processed, and the remainder is not retried. This violates the expected "process the page atomically or defer/retry" invariant for a critical routing control path.

Since a parachain's outbound XCMP channel signal messages are typically emitted by the parachain runtime in response to internal channel-management logic (e.g., queue growth, suspension triggers) that themselves may be reachable indirectly by a user causing enough backlog, and since the receiving side accepts *any* `Signals`-format page delivered over an established HRMP/XCMP channel from a sibling para (no additional origin filtering beyond "this came from parachain X's channel"), a sibling chain (or code running under it that a user can trigger, e.g. a parachain that echoes/forwards attacker-supplied XCM causing it to emit crafted channel signals) can construct a page with many `Suspend`/`Resume` signals crafted specifically to exhaust the meter between the `Suspend` and its paired `Resume`.

### Impact Explanation
If exploited, the victim parachain's inbound XCMP channel from the attacking sibling remains marked as suspended in `InboundXcmpSuspended` indefinitely, since the `Resume` signal that would have cleared it is silently dropped rather than retried. This halts processing of that specific inbound channel, a denial-of-service against the parachain's HRMP/XCMP queue for messages arriving over that channel, which is a critical routing path for cross-chain messaging.

### Likelihood Explanation
The precondition requires only the ability to have a sibling parachain originate XCMP channel-signal traffic pointed at the victim, and control over its exact byte layout/count of signals in a single page — both achievable by a chain operator/relay-controlled sibling parachain, or transitively by unprivileged users causing that parachain's own queue-management logic to emit such signals if the sibling runtime can be influenced to do so. The exact weight-per-signal figure (`T::WeightInfo::suspend_channel()`) is a fixed constant, making the "meter limit just under N × suspend_channel()" crafting deterministic and repeatable.

### Recommendation
Reserve the full worst-case weight for a `Signals` page (bounded by `MAX_SIGNALS_PER_PAGE`) before beginning to apply any signal in the page, so the whole page either fits entirely in the current weight budget or is deferred/failed atomically (returning `ProcessMessageError::Overweight` so the message-queue retries it later), rather than metering and applying signals one at a time and silently truncating on failure. Alternatively, buffer-decode all signals first (cheaply, without weight cost) and only then apply them transactionally after confirming sufficient weight remains for all of them.

### Proof of Concept
Add a test in `cumulus/pallets/xcmp-queue/src/tests.rs`:
1. Build a `Signals`-format page: `[Suspend, Resume, Resume, ..., Resume]` (or interleave several `Suspend`/`Resume` pairs) sized so that after decoding the `Suspend` the cumulative `suspend_channel()` weight cost equals the meter's remaining budget.
2. Call the pallet's inbound-message processing entry point (`XcmpMessageHandler::handle_xcmp_messages` / `ProcessMessage::process_message`) with a `WeightMeter::with_limit` set to `N * T::WeightInfo::suspend_channel()` where `N` is less than the number of signals in the page.
3. Assert that `InboundXcmpSuspended::<T>::get()` still contains the sibling `ParaId` after the call (channel remains suspended).
4. Assert that no further call/retry ever processes the trailing `Resume` (i.e., the bytes were dropped, not requeued), confirming the channel is permanently stuck.
