Based on the code, the described asymmetry does not exist in the conversion pipeline. Every `TryFrom` conversion of asset lists across XCM versions (v3↔v4↔v5) is implemented as an atomic operation using `.collect::<Result<Vec<_>, ()>>()?`, so a single unconvertible `AssetId`/`Fungibility` variant causes the *entire* `Assets`/`MultiAssets` conversion — and therefore the entire enclosing instruction and `Xcm` conversion — to fail with `Err(())`, propagated via `?` all the way up to the top-level `VersionedXcm` conversion. [1](#0-0) [2](#0-1) [3](#0-2) 

Crucially, this atomic conversion happens *before* weight estimation in both reachable entry paths:

1. **UMP/XCMP message queue processing** (`ProcessXcmMessage::process_message`): the raw bytes are decoded to `VersionedXcm`, then converted with `Xcm::<Call>::try_from(versioned_message)`. Only if that whole conversion succeeds does the code call `XcmExecutor::prepare(message, Weight::MAX)`, which computes `pre.weight_of()` used for the weight-meter check. If conversion fails for any single asset anywhere in the message, the function returns `ProcessMessageError::Unsupported` immediately — no `prepare`/weight computation and no execution ever occurs. [4](#0-3) 

2. **`pallet_xcm::execute` (user-callable extrinsic/precompile path)**: `(*message).try_into()` converts the full `VersionedXcm` to the active `Xcm` type before `T::XcmExecutor::prepare_and_execute` is invoked; a conversion failure yields `Error::<T>::BadVersion` and aborts before any weighing or execution. [5](#0-4) 

Additionally, individual instruction conversions (e.g. `WithdrawAsset(assets) => Self::WithdrawAsset(assets.try_into()?)`) also propagate asset-list conversion failure via `?`, so a partial failure inside one instruction's asset list aborts the whole `Xcm` conversion, not just that instruction. [6](#0-5) 

Because the `WeighedMessage`/`prepare` step (which determines the weight used for `XcmWeightInfo`-based estimation) always operates on the *same* already-converted, fully-materialized `Xcm<Call>` that is subsequently executed, there is no code path where the weight/fee estimate reflects the original (larger) asset list while execution processes a silently-truncated subset. The conversion is genuinely all-or-nothing at every layer inspected (`Asset`, `Assets`, `WildAsset`, `AssetFilter`, `Instruction`, `Xcm`). [7](#0-6)
