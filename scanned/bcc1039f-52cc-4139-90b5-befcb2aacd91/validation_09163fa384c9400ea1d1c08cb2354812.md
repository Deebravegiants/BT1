### Title
Blocked/frozen asset accounts cannot be rescued even by the Admin via `force_transfer` - (File: `substrate/frame/assets/src/functions.rs`)

### Summary
In `pallet-assets`, once an account is `Blocked` (via `Freezer::block`) or has a `Frozen` balance exceeding its spendable amount, the privileged `force_transfer` extrinsic — the pallet's designated admin/rescue mechanism — cannot move that account's funds, because it shares the same `prep_debit`/`reducible_balance` check as the permissionless `transfer` call. This mirrors the CashManager.sol pattern: a compliance/sanctions-style status (`Blocked`) locks funds so completely that even the trusted privileged role cannot intervene.

### Finding Description
`force_transfer` is documented as "Transfers between arbitrary accounts; called by the asset class's Admin" [7](#0-6) , implying it is the pallet's override mechanism analogous to a trusted admin resolving stuck/sanctioned funds. However its implementation calls the generic `do_transfer` function with no special-casing for the `Admin`/root capability beyond an admin-identity check [8](#0-7) ; it still routes through `prep_debit`, which relies entirely on `reducible_balance`, which unconditionally rejects any account whose `status.is_frozen()` is true (covers both `Frozen` and `Blocked`) [1](#0-0) [2](#0-1) . There is no `Force`/`Polite`-style fortitude parameter for `force_transfer` (unlike `pallet-balances`' `transfer_and_hold`, which explicitly supports a `Force` fortitude to override freezes/holds when strong authorization is present, see [9](#0-8) ). Consequently, once a compliance-style `Freezer` (which can be a different, potentially externally-triggered pallet/oracle implementing `FrozenBalance`) blocks or freezes an account, the `Admin` role has no dispatchable that can move funds out on the user's behalf.

### Impact Explanation
Funds in a `Blocked` or heavily `Frozen` asset account become permanently unrecoverable through any privileged pallet-assets call, since `force_transfer` is the only admin-level fund-movement primitive and it inherits the same restriction as unprivileged `transfer`. If a runtime uses the `Freezer`/`block` mechanism to represent a compliance status (e.g., sanctions, KYC revocation) — which is precisely the intended design per the pallet docs ("Disallow further transfers... to and from an account") [10](#0-9)  — there is no on-chain path for the Admin to redeem/refund that user even if the compliance concern is resolved or the protocol team wants to intervene, exactly the CashManager.sol pattern where MANAGER_ADMIN cannot service redemptions/refunds for a KYC-failed address.

### Likelihood Explanation
This requires that the runtime's `T::Freezer` implementation places accounts in `Blocked`/`Frozen` state for reasons outside the Admin's direct control (e.g., an external compliance oracle), and that recovery for those accounts is expected to go through `force_transfer`. This is a realistic configuration pattern (freeze/block for compliance, with Admin expected to be the "trusted operator" who can act on frozen funds), matching the disputed-but-accepted judge stance in the referenced report: even a fully trusted admin lacking any override results in genuinely locked funds, which is a protocol-level design gap rather than a pure "trusted role compromise."

### Recommendation
Provide an explicit override path for the Admin-only `force_transfer` (and/or a dedicated `force_transfer_blocked`) that bypasses the `AccountStatus::Blocked`/`Frozen` check — analogous to the `Force` `Fortitude` parameter already used in `pallet-balances`' hold/freeze machinery — so that funds in blocked accounts can still be rescued by a trusted Admin origin, while regular `transfer`/`transfer_approved` remain restricted.

### Proof of Concept
1. Runtime configures `pallet-assets` with `T::Freezer` such that an external process blocks account `U` via `Assets::block(freezer_origin, asset_id, U)`, setting `AccountStatus::Blocked` [11](#0-10) .
2. Admin later attempts `Assets::force_transfer(admin_origin, asset_id, U, rescue_account, amount)` to rescue `U`'s funds.
3. `do_transfer` → `transfer_and_die` → `prep_debit` → `reducible_balance` evaluates `account.status.is_frozen()` (true because `Blocked` matches) and returns `Error::<T, I>::Frozen` [1](#0-0) , so the admin call fails identically to a call from the blocked user themself, permanently locking the funds.
