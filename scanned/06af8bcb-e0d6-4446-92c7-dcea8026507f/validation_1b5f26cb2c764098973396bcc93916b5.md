### Title
LDAP DN Injection via unescaped bind-DN construction in login flow - (File: core/sessions/ldapauth/ldap.go)

### Summary
The LDAP authentication provider builds the bind DN for user login by string-concatenating attacker-controlled email input using `ldap.EscapeFilter`, a function designed to escape LDAP *search filter* metacharacters, not LDAP *Distinguished Name* metacharacters. Because DN-significant characters (comma, `+`, `"`, `<`, `>`, `;`, leading `=`, etc., per RFC 4514) are left unescaped, an unauthenticated client submitting a crafted email during login can inject additional RDN components into the bind DN sent to the upstream LDAP server. This is the same bug class as CVE-2018-12689 (LDAP injection via crafted username in the login panel).

### Finding Description
`CreateSession`, which is invoked directly from the public, unauthenticated `/sessions` endpoint (`core/web/sessions_controller.go`), constructs the bind DN like this: [1](#0-0) 

```go
escapedEmail := ldap.EscapeFilter(strings.ToLower(sr.Email))
searchBaseDN := fmt.Sprintf("%s=%s,%s,%s", l.config.BaseUserAttr(), escapedEmail, l.config.UsersDN(), l.config.BaseDN())
if err = conn.Bind(searchBaseDN, sr.Password); err != nil {
```

`TestPassword` (also reachable via password-change / admin flows) has the identical pattern: [2](#0-1) 

`ldap.EscapeFilter` only escapes the characters relevant to LDAP *search filters* (`\`, `*`, `(`, `)`, NUL). It is not the correct API to sanitize a value being embedded into a *DN string* used for `conn.Bind()`. DN syntax treats `,` as an RDN separator, `+` as a multi-valued RDN separator, and `=`/`"`/`<`/`>`/`;` as structurally significant. None of these are escaped by `EscapeFilter`.

Because `sr.Email` is fully attacker-controlled from an unauthenticated HTTP POST body (`core/web/sessions_controller.go` `Create`), a value such as `victim,dc=other,dc=example,dc=com` — or a value that closes out the intended RDN and appends new RDN components — can alter the structure of the DN that `conn.Bind()` targets, rather than being confined to the intended `uid=<value>,ou=users,dc=...` subtree. This is DN injection: the identity being authenticated against the upstream directory is no longer strictly the caller-registered account under `UsersDN`.

### Impact Explanation
This directly maps to "concrete authentication or role bypass" and "request impersonation" categories: an unprivileged, unauthenticated caller controls a structural part of the DN used for a privileged directory bind operation. Depending on the LDAP server's DN normalization/parsing behavior and directory layout, this can be leveraged to target DNs outside the intended `UsersDN` subtree, and, combined with role mapping via `FindUser`/`groupSearchResultsToUserRole`, could result in unintended role assignment or authentication behavior differing from what the application's DN-restriction design intends. It also affects `TestPassword`, which is used for password verification flows.

### Likelihood Explanation
Reachable directly from an unauthenticated POST to `/sessions` (`SessionsController.Create` → `AuthenticationProvider().CreateSession`) with no prior authentication or privilege required — only conditioned on the node being configured with `AuthenticationMethod = 'ldap'`. The only requirement is crafting an email value containing DN metacharacters (e.g., `,`), which is trivial for a remote attacker.

### Recommendation
Use a DN-specific escaping routine (e.g., `ldap.EscapeDN` from `github.com/go-ldap/ldap/v3`, or manually escape per RFC 4514) whenever a value is embedded into a DN string (as in `searchBaseDN` construction in `CreateSession` and `TestPassword`). Reserve `ldap.EscapeFilter` strictly for values embedded into filter expressions (as already correctly done in `FindUser`'s `filterQuery` and `validateUsersActive`). Additionally, validate/normalize the email format before using it in DN construction (e.g., reject characters not valid in the expected `uid`/email format) as defense in depth.

### Proof of Concept
1. Configure the node with `WebServer.AuthenticationMethod = 'ldap'` and a real LDAP backend.
2. Send `POST /sessions` with body:
```json
{"email": "victim,ou=admins,dc=example,dc=com", "password": "attacker-known-password"}
```
3. Observe that `searchBaseDN` in `CreateSession` (core/sessions/ldapauth/ldap.go:407) becomes:
```
uid=victim,ou=admins,dc=example,dc=com,ou=users,dc=example,dc=com
```
instead of the intended `uid=<escaped-victim>,ou=users,dc=example,dc=com`, demonstrating that attacker-supplied input alters the DN structure sent to `conn.Bind`, confirming the DN injection is reachable and unsanitized for DN-context use.
