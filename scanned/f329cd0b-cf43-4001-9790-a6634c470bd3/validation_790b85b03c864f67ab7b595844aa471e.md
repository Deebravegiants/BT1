### Title
Lost/misallocated rewards when `total_tokens_staked` is `0` in `pallet-asset-rewards` - (File: substrate/frame/asset-rewards/src/lib.rs)

### Summary
`pallet-asset-rewards` implements a Synthetix/MasterChef-style reward accounting scheme functionally identical to the Tokemak `AbstractRewarder` pattern described in the report. It suffers from the same root cause: when a pool's `total_tokens_staked` is `0`, `reward_per_token()` freezes the accumulator but `last_update_block` is still advanced whenever any account interacts with the pool, permanently skipping the reward accrual for that block window.

### Finding Description
`reward_per_token()` mirrors the vulnerable Solidity logic exactly: [1](#0-0) 

If `pool_info.total_tokens_staked.is_zero()`, the function returns `reward_per_token_stored` unchanged, without accounting for the blocks elapsed since `last_update_block`.

The caller, `update_pool_and_staker_rewards`, always follows this with `update_pool_rewards`, which unconditionally sets `last_update_block` to the current block: [2](#0-1) 

Every pool-mutating extrinsic (`stake`, `unstake`, `harvest_rewards`, `set_pool_reward_rate_per_block`, `set_pool_expiry_block`) calls this update path: [3](#0-2) [4](#0-3) 

`create_pool` sets `total_tokens_staked: 0`, `reward_per_token_stored: 0`, and `last_update_block: 0` while immediately configuring a non-zero `reward_rate_per_block` and a future `expiry_block`: [5](#0-4) 

There is no check anywhere (`create_pool`, `stake`, `set_pool_reward_rate_per_block`) that requires `total_tokens_staked > 0` before rewards start accruing conceptually against `reward_rate_per_block`. Consequently, any period between pool creation (or between a full unstake-to-zero and the next stake) and the first `stake()` call causes that window's intended reward emission to be silently dropped: `reward_per_token_stored` stays flat while `last_update_block` jumps forward to the block of the first `stake`, exactly like the Tokemak issue's `rewardPerTokenStored`/`lastUpdateBlock` desynchronization.

### Impact Explanation
Reward tokens corresponding to the zero-supply block window are never reflected in `reward_per_token_stored`, so no staker's `reward_per_token_paid` accounting will ever credit them. The tokens remain in the pool's pot account (`pool_info.account`) indefinitely, are not distributed to any staker, and can only be recovered by the pool admin via `cleanup_pool`, which explicitly requires the pool to have zero stakers: [6](#0-5) 

Once a first staker joins, `cleanup_pool` becomes unusable until the pool empties again, so these "orphaned" reward tokens are effectively stuck for the pool's remaining lifetime and are unfairly excluded from the reward distribution that stakers are otherwise entitled to under the advertised `reward_rate_per_block`. This is a fund-accounting/fairness defect, not a direct fund-theft primitive.

### Likelihood Explanation
This condition is not attacker-triggered — it occurs under completely normal, expected usage: any pool creator configuring `reward_rate_per_block` and `expiry_block` at `create_pool` time before the first staker joins will trigger it, and it also occurs whenever a pool's `total_tokens_staked` returns to `0` (e.g., all stakers fully unstake) before the next stake. Given `CreatePoolOrigin` is a privileged/permissioned action for pool creation, but staking is fully open to any account, the gap between pool creation and first stake is a realistic, common operational window, not a contrived edge case.

### Recommendation
Mirror the Sherlock recommendation: prevent reward emission from accruing while `total_tokens_staked == 0`. Concretely, either:
- do not advance `last_update_block` when `total_tokens_staked.is_zero()` (so the reward window is deferred, not lost), or
- require `total_tokens_staked > 0` before allowing `reward_rate_per_block` to be set/effective, and initialize/reset `last_update_block` to the block of the first stake rather than pool creation.

The former (freezing `last_update_block` together with `reward_per_token_stored` when supply is zero) is the more general fix, since it also covers the "everyone unstakes mid-pool-life" case, not just the initial-deposit case.

### Proof of Concept
1. Privileged account calls `create_pool` with `reward_rate_per_block = R` and `expiry_block = E` at block `N`. Pool state: `total_tokens_staked = 0`, `reward_per_token_stored = 0`, `last_update_block = N` (see `create_pool` in `RewardsPool` impl, lines 843-898).
2. No one stakes for `K` blocks (e.g., due to normal onboarding delay).
3. At block `N+K`, a staker calls `stake()`. Internally: `update_pool_and_staker_rewards` -> `reward_per_token()` returns unchanged `reward_per_token_stored = 0` because `total_tokens_staked.is_zero()` (lines 790-792); then `update_pool_rewards` sets `last_update_block = N+K` (line 780).
4. The `K` blocks' worth of `reward_rate_per_block * K` tokens that "should" have accrued are never reflected in `reward_per_token_stored` and can never be claimed by any staker via `harvest_rewards`; they remain stuck in `pool_info.account` and are unrecoverable by admin once any staker is present (`cleanup_pool` requires zero stakers, lines 700-704). 		pub fn cleanup_pool(origin: OriginFor<T>, pool_id: PoolId) -> DispatchResult {
			let who = ensure_signed(origin)?;

			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			ensure!(pool_info.admin == who, BadOrigin);

			let stakers = PoolStakers::<T>::iter_key_prefix(pool_id).next();
			ensure!(stakers.is_none(), Error::<T>::NonEmptyPool);

			let pool_balance = T::Assets::reducible_balance(
				pool_info.reward_asset_id.clone(),
				&pool_info.account,
				Preservation::Expendable,
				Fortitude::Polite,
			);
			T::Assets::transfer(
				pool_info.reward_asset_id,
				&pool_info.account,
				&pool_info.admin,
				pool_balance,
				Preservation::Expendable,
			)?;

			if let Some((who, cost)) = PoolCost::<T>::take(pool_id) {
				T::Consideration::drop(cost, &who)?;
			}

			Pools::<T>::remove(pool_id);

			Self::deposit_event(Event::PoolCleanedUp { pool_id });

			Ok(())
		}

		pub fn update_pool_and_staker_rewards(
			pool_info: &PoolInfoFor<T>,
			staker_info: &PoolStakerInfo<T::Balance>,
		) -> Result<(PoolInfoFor<T>, PoolStakerInfo<T::Balance>), DispatchError> {
			let reward_per_token = Self::reward_per_token(&pool_info)?;
			let pool_info = Self::update_pool_rewards(pool_info, reward_per_token)?;

			let mut new_staker_info = staker_info.clone();
			new_staker_info.rewards = Self::derive_rewards(&staker_info, &reward_per_token)?;
			new_staker_info.reward_per_token_paid = pool_info.reward_per_token_stored;
			return Ok((pool_info, new_staker_info));
		}

		/// Computes update pool reward state.
		///
		/// Should be called every time the pool is adjusted, and a staker is not involved.
		///
		/// Returns the updated pool and staker info.
		///
		/// NOTE: this function has no side-effects. Side-effects such as storage modifications are
		/// the responsibility of the caller.
		pub fn update_pool_rewards(
			pool_info: &PoolInfoFor<T>,
			reward_per_token: T::Balance,
		) -> Result<PoolInfoFor<T>, DispatchError> {
			let mut new_pool_info = pool_info.clone();
			new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number();
			new_pool_info.reward_per_token_stored = reward_per_token;

			Ok(new_pool_info)
		}

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}

	fn set_pool_reward_rate_per_block(
		admin: &T::AccountId,
		pool_id: PoolId,
		new_reward_rate_per_block: T::Balance,
	) -> DispatchResult {
		let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
		ensure!(pool_info.admin == *admin, BadOrigin);
		ensure!(
			new_reward_rate_per_block > pool_info.reward_rate_per_block,
			Error::<T>::RewardRateCut
		);

		// Always start by updating the pool rewards.
		let rewards_per_token = Self::reward_per_token(&pool_info)?;
		let mut pool_info = Self::update_pool_rewards(&pool_info, rewards_per_token)?;

		pool_info.reward_rate_per_block = new_reward_rate_per_block;
		Pools::<T>::insert(pool_id, pool_info);

		Self::deposit_event(Event::PoolRewardRateModified { pool_id, new_reward_rate_per_block });

		Ok(())
	}
