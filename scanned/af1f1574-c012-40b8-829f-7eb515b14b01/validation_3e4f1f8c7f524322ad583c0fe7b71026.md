### Title
HRMP channel closure permanently drops undelivered `HrmpChannelContents` without recovery or notification - (File: polkadot/runtime/parachains/src/hrmp.rs)

### Summary
`close_hrmp_channel` unconditionally removes `HrmpChannelContents` and refunds `sender_deposit`/`recipient_deposit` at session boundary, without checking whether any queued messages remain unpruned. Either channel party can call `hrmp_close_channel` at any time — including immediately after the counterparty commits a large in-flight message — causing that message to be permanently discarded with no error, event, or replay mechanism.

### Finding Description
`Pallet::close_channel` (the `hrmp_close_channel` extrinsic) only requires that the caller be a channel participant and that the channel exists; it does not check `msg_count`/`HrmpChannelContents` state, and simply queues the channel for closure in `HrmpCloseChannelRequestsList` (per implementers-guide description of `hrmp_close_channel`). At the next session change, `process_hrmp_close_channel_requests` iterates the close list and calls `close_hrmp_channel` unconditionally: [1](#0-0) 

`close_hrmp_channel` refunds `sender_deposit`/`recipient_deposit` and then removes `HrmpChannelContents` for that channel outright, with no check for outstanding/unpruned messages (`msg_count > 0`), no attempt to force-deliver or fail them, and no event emitted about lost messages: [2](#0-1) 

Message pruning normally happens via `prune_hrmp`, driven by the recipient parachain's own HRMP watermark advancement in its candidate commitments: [3](#0-2) 

Because channel closure processing (session change) and message pruning (per-block, driven by the recipient's own candidate) are independent, an attacker who is the recipient (or sender) of a channel can call `hrmp_close_channel` right after the counterparty commits messages within the same session, and the recipient can simply refrain from advancing its watermark to prune them before the session ends. When the session boundary triggers `process_hrmp_close_channel_requests`, `HrmpChannelContents` is wiped along with `HrmpChannels` (which tracks `msg_count`/`total_size`), discarding any messages that were never pruned — with no notification to the sender parachain beyond the earlier best-effort `HrmpChannelClosing` DMP message sent at request time, which does not indicate message loss and can arrive before the messages themselves are even sent within the same session.

### Impact Explanation
Concrete, permanent loss of committed inter-parachain messages: `HrmpChannelContents` entries corresponding to messages that were validly included in the sender's candidate commitments and accounted for in `HrmpChannels.msg_count`/`total_size` are deleted with no delivery, no replay, no explicit event describing the lost payloads, and no way for the sender parachain to detect or recover them programmatically (only the earlier generic close notification exists, unrelated to specific in-flight messages). This can cause funds/XCM instructions embedded in those HRMP messages (e.g. reserve transfers, DOT/asset messages) to silently vanish from the recipient's perspective while the sender believes the message was sent.

### Likelihood Explanation
This requires only unprivileged parachain-collator-controlled actions that are entirely within the normal call surface: any parachain (sender or recipient) can call `hrmp_close_channel` via a normal signed/root-of-parachain origin extrinsic on an open channel, and the counterparty can commit HRMP messages via ordinary block production. No governance or root privilege is needed on the relay chain; the only "privilege" involved is being one of the two parachains in the channel, which is an intended actor in this design, not an admin. The race is deterministic and repeatable: within one session, party A sends a message, party B calls `hrmp_close_channel` and simply never advances its watermark past `sent_at` before the session ends, guaranteeing the message stays in `HrmpChannelContents` at the point of removal.

### Recommendation
Before closing a channel in `close_hrmp_channel`/`process_hrmp_close_channel_requests`, check `HrmpChannels::msg_count` (or non-emptiness of `HrmpChannelContents`) for the channel; if there are unpruned messages, either defer closure until they are pruned (e.g., only allow the close request to take effect once `msg_count == 0`), or explicitly force-prune/deliver them (treating them as delivered for watermark purposes) and emit a `Pallet::Event` documenting how many messages/bytes were force-dropped, so this is at minimum an auditable, intentional, documented griefing-acceptance path rather than a silent deletion.

### Proof of Concept
Rust integration test in `polkadot/runtime/parachains/src/hrmp/tests.rs`:
1. Register `para_a`/`para_b`, open and confirm a channel `(para_a -> para_b)`.
2. Advance to a session where the channel is active; have `para_a` submit a candidate with an `OutboundHrmpMessage` to `para_b` (via the usual candidate-commitments/`queue_outbound_hrmp` path), without `para_b` advancing its HRMP watermark past `sent_at`.
3. Call `Hrmp::close_channel(para_b, HrmpChannelId{sender: para_a, recipient: para_b})` (or `para_a`) in the same session.
4. Assert before session change: `HrmpChannelContents::<Test>::get(&channel_id)` is non-empty and `HrmpChannels::<Test>::get(&channel_id).unwrap().msg_count > 0`.
5. Run to the next session (`run_to_block` past session boundary) to trigger `process_hrmp_close_channel_requests`.
6. Assert: `HrmpChannelContents::<Test>::get(&channel_id)` is now empty/removed and `HrmpChannels::<Test>::get(&channel_id)` is `None`, while no event or storage record reflects the dropped message — confirming silent, permanent message loss.

		let close_reqs = HrmpCloseChannelRequestsList::<T>::take();
		for condemned_ch_id in close_reqs {
			HrmpCloseChannelRequests::<T>::remove(&condemned_ch_id);
			Self::close_hrmp_channel(&condemned_ch_id);
		}

	/// Close and remove the designated HRMP channel.
	///
	/// This includes returning the deposits.
	///
	/// This function is idempotent, meaning that after the first application it should have no
	/// effect (i.e. it won't return the deposits twice).
	fn close_hrmp_channel(channel_id: &HrmpChannelId) {
		if let Some(HrmpChannel { sender_deposit, recipient_deposit, .. }) =
			HrmpChannels::<T>::take(channel_id)
		{
			T::Currency::unreserve(
				&channel_id.sender.into_account_truncating(),
				sender_deposit.unique_saturated_into(),
			);
			T::Currency::unreserve(
				&channel_id.recipient.into_account_truncating(),
				recipient_deposit.unique_saturated_into(),
			);
		}

		HrmpChannelContents::<T>::remove(channel_id);

		HrmpEgressChannelsIndex::<T>::mutate(&channel_id.sender, |v| {
			if let Ok(i) = v.binary_search(&channel_id.recipient) {
				v.remove(i);
			}
		});
		HrmpIngressChannelsIndex::<T>::mutate(&channel_id.recipient, |v| {
			if let Ok(i) = v.binary_search(&channel_id.sender) {
				v.remove(i);
			}
		});
	}

	pub(crate) fn prune_hrmp(recipient: ParaId, new_hrmp_watermark: BlockNumberFor<T>) {
		// sift through the incoming messages digest to collect the paras that sent at least one
		// message to this parachain between the old and new watermarks.
		let senders = HrmpChannelDigests::<T>::mutate(&recipient, |digest| {
			let mut senders = BTreeSet::new();
			let mut leftover = Vec::with_capacity(digest.len());
			for (block_no, paras_sent_msg) in mem::replace(digest, Vec::new()) {
				if block_no <= new_hrmp_watermark {
					senders.extend(paras_sent_msg);
				} else {
					leftover.push((block_no, paras_sent_msg));
				}
			}
			*digest = leftover;
			senders
		});

		// having all senders we can trivially find out the channels which we need to prune.
		let channels_to_prune =
			senders.into_iter().map(|sender| HrmpChannelId { sender, recipient });
		for channel_id in channels_to_prune {
			// prune each channel up to the new watermark keeping track how many messages we removed
			// and what is the total byte size of them.
			let (mut pruned_cnt, mut pruned_size) = (0, 0);

			let contents = HrmpChannelContents::<T>::get(&channel_id);
			let mut leftover = Vec::with_capacity(contents.len());
			for msg in contents {
				if msg.sent_at <= new_hrmp_watermark {
					pruned_cnt += 1;
					pruned_size += msg.data.len();
				} else {
					leftover.push(msg);
				}
			}
			if !leftover.is_empty() {
				HrmpChannelContents::<T>::insert(&channel_id, leftover);
			} else {
				HrmpChannelContents::<T>::remove(&channel_id);
			}

			// update the channel metadata.
			HrmpChannels::<T>::mutate(&channel_id, |channel| {
				if let Some(ref mut channel) = channel {
					channel.msg_count -= pruned_cnt as u32;
					channel.total_size -= pruned_size as u32;
				}
			});
		}

		HrmpWatermarks::<T>::insert(&recipient, new_hrmp_watermark);
	}
