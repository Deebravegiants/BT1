### Title
Charge-coalescing in `execute_postponed_deposits` can discard a legitimate post-termination `Alive` deposit when a `Terminated` marker for a contract account is followed by another `Alive` charge for the same account within one transaction - (File: substrate/frame/revive/src/metering/storage.rs)

### Summary
`execute_postponed_deposits` sorts `self.charges` by contract account and coalesces consecutive entries for the same account, treating any `(Alive, Terminated)` or `(Terminated, Alive)` pair as "undo the alive amount and mark Terminated" [1](#0-0) . This coalescing rule is only sound if a `Terminated` charge for a contract account is always the chronologically *last* charge pushed for that account. The code does not enforce or assert that invariant — it only guards against two `Terminated` entries for the same contract via a `debug_assert!` [2](#0-1) , and does nothing to prevent an `Alive` charge from being appended *after* a `Terminated` charge for the same account (e.g. from a new contract deployed to the same address later in the same transaction, or from a stray push ordering).

### Finding Description
`Charge` entries are pushed in two places: `RawMeter::absorb` pushes `ContractState::Alive { amount }` whenever a nested call ends normally with a non-zero own deposit [3](#0-2) , and `RawMeter::terminate` pushes `ContractState::Terminated` and folds the contract's `refunded` balance straight into `self.total_deposit` [4](#0-3) .

At the end of the whole call stack, `execute_postponed_deposits` sorts `charges` by `contract` (a **stable** sort, so relative order among entries with the same contract account is preserved) and then coalesces adjacent same-account entries [1](#0-0) . The merge logic is:

- `Alive + Alive` → sum the amounts (correct, order-independent).
- `Alive + Terminated` or `Terminated + Alive` → subtract the `Alive` amount from `total_deposit` and force the merged state to `Terminated`.
- `Terminated + Terminated` → `debug_assert!(false, ...)` — only defends against the double-terminate case.

The `(Terminated, Alive)` branch is written to model "a later charge for an account that was already terminated should be discarded", which is correct **only if that later `Alive` charge represents residual accounting from the *same, now-destroyed* contract** (e.g. leftover bookkeeping noise after termination). It is **not** correct if the later `Alive` charge represents a *new* contract that has been (re)instantiated at that same account after the earlier one terminated, because in that scenario the account is genuinely `Alive` with real persisted storage at the end of the transaction, yet the merge collapses the state to `Terminated` and removes the associated deposit from `total_deposit`.

Because `sort_by` is stable, the ordering of charges for a single contract account exactly reflects the order in which `terminate`/`absorb` calls happened during execution. The coalescing code implicitly assumes `Terminated` is always the terminal (last) event for an account within a transaction, but nothing in `RawMeter` enforces this — the only safeguard is a `debug_assert!` that fires solely for two consecutive `Terminated` markers, not for an `Alive` marker following a `Terminated` one.

### Impact Explanation
If an account can legitimately receive an `Alive` charge after a `Terminated` charge for the same account within one transaction (e.g. redeployment to the same address in the same tx, or any other execution path that appends charges for an already-terminated account), the coalescing logic silently subtracts that `Alive` amount from `total_deposit` and marks the account `Terminated` in the final charge list. That means:
- The corresponding `E::charge` call for that deposit is never issued in the refund/charge loops that follow (they only iterate `ContractState::Alive` entries) [5](#0-4) .
- `total_deposit`, which is returned as the net deposit charged to the origin, is reduced by an amount that corresponds to storage that is actually still persisted on-chain (belonging to the later, alive contract) [6](#0-5) .

This is a genuine violation of the stated invariant ("total_deposit charged to origin must equal the net storage delta actually persisted on-chain") *if* the precondition (post-termination reuse of the same account within the same transaction, producing an `Alive` charge after a `Terminated` charge for that account) is reachable.

### Likelihood Explanation
The vulnerable code path (the coalescing logic itself) is real and exactly as described above; I confirmed it by reading `substrate/frame/revive/src/metering/storage.rs` in full. What I was **not** able to fully verify within the available tooling/time is whether pallet-revive's `instantiate`/termination flow actually allows a *new* contract to be created at the same account address as a just-terminated contract *within the same transaction*, which is the precondition the question's proof idea and the scoped exploit require (analogous to the classic pre-EIP-6780 EVM SELFDESTRUCT+CREATE2-redeploy pattern). I found references to a `DuplicateContract`-style existence check in `substrate/frame/revive/src/exec.rs`, which suggests instantiate does check for an existing contract at the target address, but I could not confirm from the index whether that check (and the underlying `ContractInfoOf`/trie-id state) is cleared synchronously on `terminate` (making same-tx reuse possible) or only at block finalization (which would close this path). I also could not find a `terminate_if_same_tx`-named function in the indexed code, so I cannot confirm the exact helper referenced in the question's call sequence exists as named.

Absent confirmation of that redeployment precondition, the merge logic is defensible for the "normal" case (charges for one contract instance, ending in a single terminal `Terminated`), and the `debug_assert!` shows the authors were aware of ordering assumptions but only defended the double-terminate case, not the terminate-then-alive case.

### Recommendation
Regardless of whether the address-reuse-in-same-tx path is currently reachable, the coalescing logic should not rely on an unenforced ordering invariant:
- Track charges per-`(contract, instantiation-generation)` instead of per bare account, or attach a generation/trie-id to each `Charge` so that charges from a *new* instantiation at a reused address are never merged with a stale `Terminated` marker from a prior instance.
- Alternatively, explicitly forbid (with a hard error, not just `debug_assert!`) any `Alive` charge appearing after a `Terminated` charge for the same account within a transaction, and audit whether `instantiate` can actually produce this sequence; if it can, this needs a structural fix (e.g., flush/settle charges for an account at the point of termination rather than deferring coalescing to end-of-transaction).

### Proof of Concept
Because I could not conclusively confirm the same-tx address-reuse precondition, the concrete PoC below should first establish reachability, then assert the accounting bug:

```rust
// 1. Reachability check (frame/revive integration test):
//    - Instantiate contract A at address X, write storage (charge recorded via absorb -> Alive charge).
//    - Have A self-destruct/terminate within the same transaction (single extrinsic / same call stack).
//    - In the SAME transaction, attempt to instantiate a new contract at the same address X
//      (e.g. via CREATE2-equivalent salt reuse) and have it write storage (another Alive charge
//      pushed for the same account after the Terminated marker).
//    - Assert this instantiate succeeds (if it fails with DuplicateContract/AccountAlreadyExists,
//      the vulnerability is NOT reachable and the finding is moot).

// 2. If reachable, invariant test:
//    - Record on-chain storage bytes/items for address X before/after the transaction.
//    - Record origin's held/reserved balance before/after via `execute_postponed_deposits`'s
//      returned `total_deposit`.
//    - assert_eq!(net_storage_delta_deposit(X), total_deposit_returned)
//      Expect this to FAIL when the (Alive, Terminated, Alive) charge sequence is coalesced,
//      because total_deposit is under-charged by the second Alive amount.
```

If reachability in step 1 cannot be established (i.e., instantiate rejects reuse of a terminated contract's address within the same transaction), the exploit path described in the question is not currently viable, and this should be treated as a latent/defense-in-depth issue in the coalescing logic rather than a confirmed exploitable vulnerability.
