### Title
`ERC20Transactor` XCM asset transactor calls external ERC20 `transfer()` with unchecked zero amount, causing revert on "weird" tokens - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` unconditionally build and dispatch a Solidity `IERC20::transfer(to, value)` call to an arbitrary user-deployed ERC20 contract via `pallet_revive::Pallet::bare_call`, using the `amount` extracted by `Matcher::matches_fungibles(what)`, without ever checking whether `amount == 0` before making the call. [1](#0-0) [2](#0-1) 

### Finding Description
This is the same vulnerability class as the reported `Cooler.roll()` issue: an unconditional external-token `transfer()` call is made without guarding against a zero value, even though it is well known ("weird-erc20" revert-on-zero-value-transfers) that many ERC20 implementations revert when `value == 0`.

Every other transfer/withdrawal path in this codebase explicitly special-cases zero amounts as a no-op before doing any state-changing work or external call:
- `Balances::transfer` in `impl_currency.rs` returns `Ok(())` immediately if `value.is_zero()`. [3](#0-2) 
- `fungible::Inspect::can_deposit` / `can_withdraw` in `impl_fungible.rs` return `Success` immediately for zero amount. [4](#0-3) 
- `pallet-revive`'s native `Ext::transfer` explicitly documents and implements: "This is a no-op for zero `value`... avoiding events to be emitted for zero balance transfers." [5](#0-4) 
- The Snowbridge outbound-queue XCM converter explicitly rejects `Fungible(0)` assets with a dedicated `ZeroAssetTransfer` error rather than letting it propagate to an external transfer. [6](#0-5) 

`ERC20Transactor` breaks this convention: it forwards `amount` straight into an `IERC20::transferCall` payload and executes it via `bare_call` regardless of value, then only inspects the returned bool/revert flag afterward: [7](#0-6) [8](#0-7) 

If the underlying ERC20 contract that a given `asset_id`/`asset_contract_id` points to reverts on a zero-value `transfer` (a documented, common ERC20 implementation choice), any XCM instruction that ends up asking this transactor to move `0` of that token will fail with `XcmError::FailedToTransactAsset("ERC20 contract reverted")`.

### Impact Explanation
An `Asset` with `Fungible(0)` can legitimately reach `withdraw_asset_with_surplus` / `deposit_asset_with_surplus` in multiple ways: a user constructing an XCM program (e.g., via `WithdrawAsset`/`DepositAsset`/`TransferAsset`) that references the ERC20-backed asset with a zero fungible amount, or a non-zero amount that collapses to zero after intermediate processing (fee deduction, asset conversion rounding, `TeleportAsset`/reserve-transfer leftover dust). In such cases:
1. The XCM instruction fails with `FailedToTransactAsset`, aborting/erroring the message for that asset — analogous to impact #1 in the original report (revert on `newCollateral = 0`-equivalent operations).
2. Depending on how the surrounding XCM executor and barriers handle a failed `TransactAsset` (e.g., inside a `DepositAsset`/reserve-transfer flow), this can cause partial-execution/trapped-asset situations for otherwise valid messages that merely happen to reference a zero amount for one ERC20-backed asset among several, denying service to well-formed XCM programs that use "weird" reverting ERC20 tokens as XCM-registered fungibles.

This mirrors the sponsor's own characterization of the original issue: a real but "niche case", not a fund-loss or accounting bug — it is a denial-of-transaction/DoS-style correctness bug that surfaces only when the backing ERC20 contract implements revert-on-zero-value transfers.

### Likelihood Explanation
Likelihood is limited by two conditions that must both hold:
1. A runtime must actually configure `ERC20Transactor` as (part of) its `AssetTransactor` for XCM, wiring specific ERC20 contracts (deployed on `pallet-revive`) as XCM-registered fungible assets. I was not able to confirm from the indexed code whether any in-repo runtime currently wires `ERC20Transactor` into production XCM configuration — this needs verification via a Devin session with fuller build/config search, since the index used here does not conclusively show a live runtime wiring.
2. The specific ERC20 contract registered for that asset must implement revert-on-zero-value transfers (a subset, but a real and documented class, of ERC20 tokens).

Given a runtime that permissionlessly (or via governance) allows arbitrary ERC20 contracts to be registered as XCM assets, and given that XCM programs are constructible by unprivileged users/relayers, the zero-amount transfer path is reachable without any privileged role — matching the "unprivileged user" threat model of the original finding.

### Recommendation
Mirror the convention used elsewhere in the codebase (`Balances::transfer`, `fungible::Inspect`, `pallet-revive`'s `Ext::transfer`): short-circuit both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus` in `erc20_transactor.rs` to return success immediately (with an empty `AssetsInHolding`/zero surplus, as appropriate) when `amount == 0`, before constructing the `IERC20::transferCall` and invoking `bare_call`.

### Proof of Concept
1. Deploy (or use) an ERC20 contract on `pallet-revive` whose `transfer(address,uint256)` implementation includes `require(value > 0)` (a real-world "weird ERC20" pattern, revert-on-zero-value-transfers).
2. Register this contract's address as `asset_id`/`asset_contract_id` for an XCM-fungible asset handled by `ERC20Transactor::Matcher`.
3. Submit an XCM program that triggers `withdraw_asset_with_surplus` or `deposit_asset_with_surplus` for this asset with a `Fungible(0)` amount (directly, or via a fee/rounding path that reduces the transferred amount to 0).
4. Observe the `bare_call` to `IERC20::transferCall` reverting inside the ERC20 contract, `return_value.did_revert()` returning `true`, and the transactor returning `XcmError::FailedToTransactAsset("ERC20 contract reverted")` at [9](#0-8)  / [10](#0-9) , aborting the intended XCM operation.

	/// Transfer some funds from `from` to `to`.
	///
	/// This is a no-op for zero `value`, avoiding events to be emitted for zero balance transfers.
	///
	/// If the destination account does not exist, it is pulled into existence by transferring the
	/// ED from `origin` to the new account. The total amount transferred to `to` will be ED +
	/// `value`. This makes the ED fully transparent for contracts.
	/// The ED transfer is executed atomically with the actual transfer, avoiding the possibility of
	/// the ED transfer succeeding but the actual transfer failing. In other words, if the `to` does
	/// not exist, the transfer does fail and nothing will be sent to `to` if either `origin` can
	/// not provide the ED or transferring `value` from `from` to `to` fails.
	/// Note: This will also fail if `origin` is root.
	fn transfer<S: State>(
		origin: &Origin<T>,
		from: &T::AccountId,
		to: &T::AccountId,
		value: U256,
		preservation: Preservation,
		meter: &mut ResourceMeter<T, S>,
		exec_config: &ExecConfig<T>,
	) -> DispatchResult {
		let value = BalanceWithDust::<BalanceOf<T>>::from_value::<T>(value)
			.map_err(|_| Error::<T>::BalanceConversionFailed)?;
		if value.is_zero() {
			return Ok(());
		}
