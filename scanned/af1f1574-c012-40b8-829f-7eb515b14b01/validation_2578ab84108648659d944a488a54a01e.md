## Analog Vulnerability Found

### Title
Single fixed/global staleness window (`ExpiresIn`) applied uniformly to all Oracle keys, and no staleness enforcement on stored aggregated value read - (File: `substrate/frame/honzon/oracle/src/default_combine_data.rs`, `substrate/frame/honzon/oracle/src/lib.rs`)

### Summary
The `pallet-oracle` (Honzon oracle) module aggregates price/data feeds from multiple operators using `DefaultCombineData`, which is parameterized by a single, pallet-instance-wide `ExpiresIn: Get<MomentOf<T, I>>` constant used to determine data freshness for every `OracleKey` (e.g., every currency pair/asset) handled by that pallet instance [1](#0-0) . This is directly analogous to the Renzo `MAX_TIME_WINDOW` finding: one fixed heartbeat/staleness constant is used regardless of the fact that different tokens/assets naturally update at very different frequencies.

### Finding Description
`DefaultCombineData::combine_data` filters raw per-operator submissions using a single `expires_in` value shared across all `OracleKey`s configured for the pallet instance: [2](#0-1) 

If the number of "fresh" (non-expired) values falls below `MinimumCount`, the function does not invalidate the stored aggregate — it simply returns the previous combined value (`prev_value`) unchanged, with its original stale timestamp intact: [3](#0-2) 

Critically, the public read path `Pallet::get()` performs **no freshness/expiry check at all** on the value it returns — it simply returns whatever is in `Values` storage: [4](#0-3) 

The same applies to the `DataProvider::get()` trait implementation consumed by other pallets, which strips the timestamp entirely and returns only the raw value: [5](#0-4) 

This mirrors the Renzo root cause exactly: a single, non-per-asset staleness parameter (`MAX_TIME_WINDOW` in Renzo vs. `ExpiresIn` here) governs price acceptance for heterogeneous assets that update at different real-world cadences. Here the issue is compounded because:
1. `ExpiresIn` is a single configuration constant per pallet **instance**, not per `OracleKey`, so a value tuned for a slow-moving asset (e.g., a stablecoin pair) will be equally applied to a fast-moving/volatile asset pair configured on the same instance.
2. Even where `ExpiresIn` governs which raw submissions are aggregated, it does **not** invalidate the final `Values` entry once aggregated — a downstream consumer calling `DataProvider::get()` receives a value with no timestamp and no built-in staleness guarantee, since the trait signature discards the timestamp.

### Impact Explanation
Any runtime/pallet that consumes this oracle via `DataProvider::get()` (which is the primary generic integration point exposed by this pallet) receives price/data values that can be arbitrarily stale if oracle operators stop feeding fresh data for a particular key or feed at a lower cadence than assumed by a single, uniformly-configured `ExpiresIn`. A downstream pallet (e.g., a lending/CDP/liquidation module built on this oracle) that trusts `DataProvider::get()` without independently tracking/verifying timestamps has no protection against consuming outdated data for assets whose natural price update frequency diverges from the single configured `ExpiresIn`, exactly the scenario described in the Renzo report where a fixed heartbeat was too stale for some tokens/chains. This can lead to protocol logic (e.g. valuation, collateralization, liquidation triggers) operating on outdated prices.

### Likelihood Explanation
This is a design-level issue reachable in normal, unprivileged operation — no privileged role compromise is required. It manifests whenever: (a) a runtime configures a single `ExpiresIn`/`DefaultCombineData` instance to serve multiple `OracleKey`s with different real-world update cadences, or (b) oracle operators (a permissioned but externally-influenced/liveness-dependent set) fail to submit enough fresh values for a specific key within `ExpiresIn`, causing the previous (stale) aggregate to persist indefinitely and be served via `get()`/`DataProvider::get()` to any consumer with no error or staleness signal.

### Recommendation
- Track and expose per-`OracleKey` last-updated timestamps to consumers via `DataProviderExtended`/`get_all_values`, and require consuming pallets to explicitly check freshness rather than relying on a single implicit `ExpiresIn`.
- Consider allowing (or requiring) `ExpiresIn` to be a per-`OracleKey` (or per-asset-class) configurable mapping rather than a single `Get<MomentOf<T, I>>` constant, similar to the Renzo mitigation of maintaining a mapping of heartbeat/staleness periods per token/chain.
- In `Pallet::get()`, consider invalidating (returning `None`) or flagging values whose timestamp exceeds a maximum age instead of silently returning a stale `prev_value` from `combine_data` forever when insufficient fresh submissions exist.

### Proof of Concept
1. Configure `pallet-oracle` with `DefaultCombineData<T, MinimumCount, ExpiresIn, I>` where `ExpiresIn` is tuned for a slow-moving asset pair (e.g., 24h) but the same pallet instance is also used for a fast-moving asset pair (e.g., an LST/ETH exchange-rate-like feed expected to update every few hours) [6](#0-5) .
2. Oracle operators submit fewer than `MinimumCount` fresh values for the fast-moving key within a shorter real window, but `combine_data` only checks against the shared `ExpiresIn`, so the stale `prev_value` (aggregated from old submissions) keeps being returned instead of being invalidated [7](#0-6) .
3. A downstream consumer calls `Pallet::get(key)` or the `DataProvider::get(key)` trait method, receiving this stale aggregated value with no timestamp/staleness indication passed through `DataProvider::get()` [5](#0-4) , and uses it as if it were current, reproducing the Renzo "stale heartbeat" scenario at the FRAME pallet level.
