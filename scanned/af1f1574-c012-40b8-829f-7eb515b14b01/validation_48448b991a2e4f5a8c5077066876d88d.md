Found a solid analog. Both `pallet-bounties` and `pallet-child-bounties` have the exact same unchecked-transfer-result pattern as the MerkleVesting bug, but using `debug_assert!` (which is compiled out in production/release builds) instead of a real error check.### Title
Unchecked `Currency::transfer` result in bounty payout silently swallowed by `debug_assert!`, causing permanent loss of bounty/child-bounty funds - (File: `substrate/frame/bounties/src/lib.rs`, `substrate/frame/child-bounties/src/lib.rs`)

### Summary
This is the same vulnerability class as the reported MerkleVesting issue: a fund-transferring call is made and its `Result` is discarded instead of being propagated as a dispatch error, so state is committed as "successful" even though the transfer failed. In `pallet-bounties::claim_bounty` and `pallet-child-bounties::claim_child_bounty`, the payout transfers use `T::Currency::transfer(...)` whose `Result` is passed only to `debug_assert!(res.is_ok())`. Since `debug_assert!` is compiled to a no-op in release builds (the builds actually used for production runtimes), a failed transfer is never surfaced as an error, yet the bounty/child-bounty record is unconditionally deleted from storage in the very next lines. There is no way to retry the payout afterward.

### Finding Description
In `claim_bounty`, at [1](#0-0) , the curator-fee and beneficiary payouts are performed via `T::Currency::transfer(&bounty_account, &curator, final_fee, AllowDeath)` and `T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath)`. The returned `Result` (`res`) is bound to a variable and only checked with `debug_assert!(res.is_ok())` — it is never propagated with `?` or checked with `ensure!`. Immediately afterwards, regardless of whether the transfer actually succeeded, the code unconditionally clears the bounty state: [2](#0-1) .

The identical pattern exists in `claim_child_bounty`: [3](#0-2) , followed by unconditional removal of the child-bounty record: [4](#0-3) .

`debug_assert!` macros are stripped out by the Rust compiler unless `debug-assertions` is explicitly enabled (which it is not in standard release/production runtime builds used on live chains). This means the check has zero effect in production: if `T::Currency::transfer` returns an `Err` (e.g. `Error::ExistentialDeposit` from the legacy `Currency` trait when a deposit to a not-yet-existing account would leave it below the existential deposit, or any other transfer failure), the error is silently discarded, execution continues as if the transfer succeeded, and the bounty/child-bounty storage entry is deleted. This is functionally identical to the reported MerkleVesting bug: the "success" path is taken and state is finalized without actually verifying the transfer.

`claim_bounty`/`claim_child_bounty` are permissionless (`ensure_signed(origin)?; // anyone can trigger claim`), reachable by any account once the bounty enters `PendingPayout` and the unlock delay has elapsed, so there is no privileged-role barrier to reaching this code path.

### Impact Explanation
If the transfer to the beneficiary (or curator) fails for any reason after the unlock delay, the bounty/child-bounty payout is lost permanently:
- The bounty account's remaining balance is not actually delivered to the beneficiary/curator.
- The bounty (or child-bounty) storage entry is removed (`*maybe_bounty = None`), so there is no dispatchable path left to retry the payment — the funds are stranded in the bounty sub-account with no code path referencing them again.
- A `BountyClaimed`/`Claimed` event is still emitted, misleadingly indicating success.

This is a direct loss-of-funds bug affecting governance-approved bounty payouts, matching Impact severity of the original finding (funds permanently unrecoverable, state already finalized).

### Likelihood Explanation
Likelihood is lower than the original ERC20 report because Substrate's `Currency::transfer` is not an arbitrary external contract call that can "lie" about success or be malicious — it is native runtime accounting. However, realistic failure triggers exist under the legacy `Currency` trait semantics used here (`ExistenceRequirement::AllowDeath`):
- Deposit-side existential deposit failures when creating a brand-new beneficiary/curator account with a payout below `ExistentialDeposit`.
- Arithmetic overflow on the destination balance in pathological configurations.
- Any custom `T::Currency` implementation (runtimes can plug in alternative implementations) that can legitimately fail transfers under specific conditions.

Because `claim_bounty`/`claim_child_bounty` are permissionless and the failure conditions are governance/curator/beneficiary controllable (e.g., choosing a low payout amount or unfunded beneficiary account), this is a realistic, unprivileged-reachable code path — the only "trust" involved is that a bounty was already approved through governance, which is normal expected usage, not privileged compromise.

### Recommendation
Replace the `debug_assert!(res.is_ok())` pattern with proper `?`-propagation (or `ensure!`) so that transfer failures cause the dispatchable to fail atomically (returning to the `PendingPayout` state via storage transaction rollback) instead of silently deleting bounty state:
```rust
T::Currency::transfer(&bounty_account, &curator, final_fee, AllowDeath)?;
T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath)?;
```
Apply the same fix to `claim_child_bounty`'s two `T::Currency::transfer` calls, and audit other `debug_assert!`-guarded balance-affecting calls in these pallets (e.g., `unreserve` checks) for the same pattern.

### Proof of Concept
1. Governance approves and funds a bounty (`propose_bounty` → `approve_bounty` → funded) and assigns a curator (`propose_curator`/`accept_curator`).
2. Curator calls `award_bounty(bounty_id, beneficiary)` where `beneficiary` is a brand-new account with zero balance, setting status to `PendingPayout`.
3. Wait until `unlock_at` (post `BountyDepositPayoutDelay`).
4. Configure/observe a scenario where the computed `payout` to `beneficiary` is below the chain's `ExistentialDeposit` (e.g., a very small bounty value net of fees) — under `Currency::transfer` with `AllowDeath`, depositing into a non-existent account below ED returns an error rather than creating a sub-ED account.
5. Anyone calls `claim_bounty(bounty_id)`. In a release build, `T::Currency::transfer(...)` returns `Err(...)`, `debug_assert!(res.is_ok())` is compiled out and does nothing, execution proceeds, `*maybe_bounty = None` deletes the bounty, and a `BountyClaimed` event fires despite the beneficiary never receiving funds — with no remaining code path to retry the payout.
