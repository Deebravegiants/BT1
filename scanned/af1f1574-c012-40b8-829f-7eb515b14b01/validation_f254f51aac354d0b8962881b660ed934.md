### Title
Missing slippage protection in `SwapFirstAssetTrader::refund_weight` XCM fee-refund swap - (File: `cumulus/primitives/utility/src/lib.rs`)

### Summary
`SwapFirstAssetTrader` is a `WeightTrader` used in production Asset Hub runtimes (Rococo, Westend, Penpal, staking-async parachain runtimes) to let XCM message senders pay execution fees in a non-native asset that gets swapped via `pallet_asset_conversion`'s `SwapCredit` into the runtime's fee `Target` asset. Its `buy_weight` correctly bounds the swap with `swap_tokens_for_exact_tokens`. However, `refund_weight`, which swaps unused fee credit in `Target` back into the user's original asset, calls `SwapCredit::swap_exact_tokens_for_tokens` with `amount_out_min = None`, exactly mirroring the Cork Protocol pattern of calling an AMM swap/removeLiquidity with zero slippage protection.

Compare to `buy_weight`, which uses the bounded `swap_tokens_for_exact_tokens` variant with an explicit target `fee` amount: [2](#0-1) 

`pallet_asset_conversion`'s `SwapCredit::swap_exact_tokens_for_tokens` trait explicitly documents that passing `None` for `amount_out_min` disables the minimum-output check: [3](#0-2) 
and the underlying implementation only enforces `ProvidedMinimumNotSufficientForSwap` if `amount_out_min` is `Some`: [4](#0-3) 

This is a direct analog to the Cork Protocol issue: `ammRouter.swapExactTokensForTokens(ctSellAmount, 0, ...)` — both pass a "no minimum" sentinel (0 / `None`) to an exact-input AMM swap, so the swap executes against whatever pool price exists at execution time, with no protection against price manipulation between quoting and execution.

`SwapFirstAssetTrader` is wired into the `WeightTrader` tuple in shipped configs:


so `refund_weight` is reachable whenever an XCM message pays delivery/execution fees in a non-`Target` asset and consumes less weight than was bought (a very common, unprivileged, attacker-triggerable scenario — any XCM sender can construct a message that over-buys weight relative to actual execution).

### Impact Explanation
Unlike the Cork case (loss of protocol/vault funds), here the swapped credit belongs to the individual XCM message's fee payer, being refunded from the collected `total_fee`. If the pool for `Target`/`refund_swap_asset` is thin or manipulated at the moment `refund_weight` executes, the refund swap can return far less of the original asset than it should, i.e., the sender receiving a reduced refund. Because there is no deadline check either (Asset Conversion swaps use current block state directly, no explicit expiry parameter exists in this pallet at all), the same "temporal exposure" issue from the report also generically applies to all `pallet_asset_conversion` swaps, but they always allow a caller to supply an explicit `amount_out_min`/`amount_in_max` at the entrypoint level (`swap_exact_tokens_for_tokens`/`swap_tokens_for_exact_tokens` extrinsics both require non-optional min/max params) — this is the one internal call site identified where the SDK code itself, not an external caller, chooses to skip that protection.

### Likelihood Explanation
Reachability is real (production runtime config, unprivileged code path executed for any fee-paying XCM message), but the actual value at risk per triggering event is bounded by the small `refund_amount` (excess weight fee, typically a tiny fraction of a transaction's total fee) rather than an entire vault/pool balance as in the Cork case. Exploiting it profitably requires an attacker able to influence pool price at the precise point `refund_weight` executes (e.g., via transaction ordering/priority within a block, which is possible but not equivalent to Ethereum mempool front-running), making practical, profitable exploitation non-trivial and low-value per instance.

### Recommendation
Pass an explicit, non-`None` `amount_out_min` to `swap_exact_tokens_for_tokens` in `refund_weight`, derived from `QuotePrice` (already used elsewhere in this file, e.g., `quote_weight`) with an acceptable slippage tolerance, and treat a failed/unfavorable swap by returning the credit to `total_fee` (as already done for the `Err` branch) rather than silently accepting an unbounded-slippage refund.

### Proof of Concept
Not independently verified with a runnable exploit in this pass — the index shows the code path and its production wiring, but exercising a real sandwich against `refund_weight` would require constructing an XCM message that overpays weight in a swappable asset and mining/ordering a manipulating swap around the block containing that message's execution; this could not be fully validated with static code search alone. This is flagged as an uncertainty: confirm via a Devin session with test-node/emulated-chain execution (e.g., extending `cumulus/primitives/utility/src/tests/swap_first.rs`) whether a manipulated pool state at `refund_weight` time measurably reduces the refunded amount below the `QuotePrice`-based expectation.
