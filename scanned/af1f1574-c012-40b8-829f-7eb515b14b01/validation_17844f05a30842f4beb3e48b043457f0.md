### Title
Charge coalescing in `execute_postponed_deposits` conflates unrelated contract generations, allowing a redeployed contract's deposit to be silently erased - (File: substrate/frame/revive/src/metering/storage.rs)

### Summary
`RawMeter::execute_postponed_deposits` sorts and coalesces per-transaction `Charge` records solely by `T::AccountId`, with no notion of "contract instance/generation". When a contract at address `A` is terminated and a different contract is later (re)instantiated at the same address `A` within the same call stack, their charges are merged, and the `(Terminated, Alive)` coalescing branch cancels the new contract's legitimate deposit from `self.total_deposit`.

### Finding Description
`self.charges` accumulates `Charge{ contract: T::AccountId, state }` entries as sub-calls are absorbed (`RawMeter::absorb`, lines 278-310) and as terminations occur (`RawMeter::terminate`, lines 450-456). Nothing in the `Charge` type distinguishes *which instantiation* of a contract at a given address a charge belongs to - it is keyed purely by account id: [1](#0-0) 

At the end of the whole call stack, `execute_postponed_deposits` does a stable sort by `contract` and then coalesces consecutive same-address entries: [2](#0-1) 

The `(Alive, Terminated) | (Terminated, Alive)` branch is meant to "undo all deposits made by a terminated contract" for the case where *the same* contract instance is charged and then destroyed within one transaction. But because the sort key is only the account id, and the sort is stable (preserving original push order), if within a single extrinsic's call stack a contract at address `A` is instantiated and terminated first (pushing a `Terminated` charge), and later a *new, distinct* contract is instantiated at the *same address* `A` (deterministic address collision, e.g. via a fixed salt / CREATE2-style derivation as used for pallet-revive's Solidity-compatible instantiation), the new contract's `Alive{amount}` charge is coalesced right after the old `Terminated` charge for the same key. The code then executes: [3](#0-2) 

`self.total_deposit = self.total_deposit.saturating_sub(&amount)` where `amount` is bound to the *second* (redeployed, still-alive) contract's own deposit, and `last.state` is forced to `Terminated`. This erases the deposit accounting for a contract that is actually alive and holds real storage, while the coalesced entry is marked `Terminated` so no charge/refund transfer happens for it in the subsequent charge loop (lines 431-441). The check that would normally prevent double-accounting for the *same* instance (charge-then-terminate) instead fires for two *unrelated* instances that merely share an address, because there is no instance/generation identifier in `Charge` to disambiguate them.

### Impact Explanation
This breaks the deposit-accounting invariant for storage rent/deposits: the origin's `total_deposit` returned by `execute_postponed_deposits` (used to reserve/hold balance backing the contract's storage) can end up smaller than the storage genuinely consumed by the live, redeployed contract. Concretely, the attacker can get a live contract's storage deposit obligation silently dropped from `total_deposit`/held balance while the contract retains its storage, i.e., storage that is supposed to be backed by a deposit hold ends up unbacked. This is a storage-deposit accounting/under-collateralization bug scoped to `RawMeter::absorb`/`execute_postponed_deposits`.

### Likelihood Explanation
Preconditions: the attacker must (1) instantiate a contract at a deterministically-derivable address, (2) terminate it (self-destruct) within the same call stack, and (3) instantiate a new contract at the identical address again in the same call stack/extrinsic, performing storage writes there. Pallet-revive supports deterministic/salt-based address derivation for instantiation (`substrate/frame/revive/src/address.rs`), and contract termination frees the account/`ContractInfo` synchronously, which is the standard precondition for the well-known "metamorphic contract" redeploy-at-same-address pattern used in EVM-compatible chains. All of these actions (`seal_instantiate`, `seal_terminate`) are reachable from ordinary, unprivileged contract code invoked by a signed extrinsic - no admin, governance, or node-level access is required. I was not able to fully verify from the available code whether pallet-revive's nonce/salt-based address derivation makes the exact-address collision trivially reproducible in all instantiate paths (e.g., whether CREATE1-style nonce-based addressing versus CREATE2-style salt addressing is used by default), so the practical trigger condition (getting two distinct contract generations to share one address within a single call stack) carries some uncertainty, but the underlying coalescing logic bug itself is confirmed directly from the code.

### Recommendation
Disambiguate `Charge` entries by contract *instance*, not just by account id - e.g., tag each `Charge` with a generation/instantiation counter (or the `ContractInfo`'s trie id / a monotonically increasing nonce assigned at instantiation) and only coalesce/cancel charges that share both the same address *and* the same generation. Alternatively, flush/finalize a contract's charges into `total_deposit` at the point of termination (rather than deferring cancellation to a global sort-and-coalesce pass) so that charges from a subsequently redeployed contract at the same address can never be merged with a prior, unrelated termination record.

### Proof of Concept
Rust integration test in `substrate/frame/revive/src/exec/tests.rs` (or `metering/storage/tests.rs`):
1. Deploy contract `C1` via `instantiate` with a fixed salt so address `A = derive(deployer, salt, code_hash)`.
2. Inside the same call stack (e.g., driven by an outer "orchestrator" contract call), have `C1` write storage (incurring a charge), then self-destruct (`seal_terminate`) back to the deployer.
3. Still within the same outer call/extrinsic, instantiate a new contract `C2` with the same `salt`/`code_hash` so it lands at the same address `A`, and have it write real storage (incurring a fresh `Alive` charge).
4. Complete the extrinsic and inspect the root meter's `total_deposit` returned by `execute_postponed_deposits` (or the final held balance via `Pallet::<T>::deposit_reserve`/`HoldReason::StorageDepositReserve`).
5. Assert that `total_deposit` (and the actual on-chain held balance) accounts for `C2`'s live storage deposit; the bug reproduces if `total_deposit` is short by `C2`'s own deposit amount because it was incorrectly subtracted by the `(Terminated, Alive)` coalescing branch, and/or if querying `ContractInfo` of `C2` shows storage present without a corresponding deposit hold.
