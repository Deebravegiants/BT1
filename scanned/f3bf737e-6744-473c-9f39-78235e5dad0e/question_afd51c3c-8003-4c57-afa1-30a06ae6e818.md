Target: ShopifyAPI::Clients::HttpClient#initialize, @headers['Host'] assignment. Attacker action: combine an unsanitized shop from Oauth.validate_auth_callback with a host app that additionally sets Context.api_host (a common configuration to proxy all Admin API calls through a fixed reverse proxy). Preconditions: Context.api_host is set (e.g. to the app's own proxy), so @base_uri uses api_host but @headers['Host'] = session.shop is still set verbatim from the unsanitized auth_query.shop. Call sequence: validate_auth_callback -> Session.new(shop: auth_query.shop) [unsanitized] -> HttpClient.new(session:, base_path:) sets @headers['Host'] = session.shop -> the proxy at api_host routes based on that Host header to decide which merchant's credentials to attach/forward. Binding: @headers['Host'] == ShopValidator.sanitize!(session.shop); never enforced. Impact: Critical - if the host app's proxy trusts this gem's Host header to select which merchant's access token to use (a common pattern when api_host is a shared ingress), an attacker-influenced unsanitized shop string can cause the proxy to route the request such that a different tenant's access token is attached, i.e. cross-tenant access. Proof idea: minitest asserting HttpClient built from a session with shop: 'victim-shop.myshopify.com<injected>' (crafted via an unsanitized OAuth callback) produces headers['Host'] equal to that raw injected string rather than a value ShopValidator.sanitize! would have produced.
