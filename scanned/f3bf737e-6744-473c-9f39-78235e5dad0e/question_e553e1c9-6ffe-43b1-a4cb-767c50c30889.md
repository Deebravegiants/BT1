Target: ShopifyAPI::Auth::Oauth::AuthQuery#to_signable_string vs ShopifyAPI::Webhooks::Request#to_signable_string. Attacker action: register a webhook endpoint on their own app installed on their own dev shop, receive a validly HMAC-signed webhook whose body and 'X-Shopify-Hmac-Sha256' header are genuine, then re-POST that identical raw body and hmac header to the same endpoint but with the 'X-Shopify-Shop-Domain' header swapped to a victim shop's domain. Preconditions: Webhooks::Registry.process(request) is used as documented. Call sequence: Utils::HmacValidator.validate(request) computes compute_signature(request.to_signable_string, secret) where to_signable_string returns only @raw_body (webhooks/request.rb to_signable_string) - the shop header is never part of the signed bytes; validation succeeds because body+hmac are untouched -> handler.handle(data: WebhookMetadata.new(topic:, shop: request.shop, ...)) uses request.shop taken straight from the swapped header. Binding: every value acted on downstream (request.shop) must be inside the string handed to HmacValidator via to_signable_string; request.shop is not, so the SIGNATURE COVERAGE binding fails. Impact: Critical - cross-tenant webhook processing: the app's webhook handler executes business logic (e.g. order/customer data mutation) attributing it to the victim shop while it was actually attacker-controlled and only genuinely signed for the attacker's own shop. Proof idea: minitest building a Webhooks::Request with a real raw_body/hmac pair computed for shop A but headers['shopify-shop-domain'] set to shop B, asserting Utils::HmacValidator.validate(request) returns true while request.shop == 'shop-B'.
