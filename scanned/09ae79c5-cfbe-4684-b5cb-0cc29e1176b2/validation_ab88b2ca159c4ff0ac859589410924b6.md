### Title
Unauthenticated LOOP-plugin proxy endpoints allow path-traversal request forwarding to internal debug/metrics services - ([File: core/web/router.go], [File: core/web/loop_registry.go])

### Summary
The Chainlink node's HTTP router registers the LOOP plugin proxy routes (`/discovery`, `/plugins/:name/metrics`, `/plugins/:name/debug/pprof/*profile`, `/plugins/:name/debug/pprof/symbol`) on the *unauthenticated* top-level router group, and the pprof proxy handler concatenates an attacker-supplied wildcard path segment directly into the internal request URL without any cleaning or allowlisting. This mirrors the CVE-2024-46898 bug class: improper processing of a URL/path segment taken from an HTTP request allows a remote, unauthenticated actor to reach unintended internal resources.

### Finding Description
`NewRouter` builds the main route group `api` with only rate limiting and a session store attached — no authentication middleware: [1](#0-0) 

Every other sensitive group in this file explicitly wraps itself in `auth.Authenticate(...)` (e.g. `debugRoutes`): [2](#0-1) 

but `loopRoutes` does not add any auth middleware before registering its handlers on `api`: [3](#0-2) 

Inside `pluginPPROFHandler`, the gin wildcard route parameter `profile` (matched via `*profile`, which — unlike gin's `:name` params — can contain `/` and `..` segments) is spliced directly into the outbound request URL string with `fmt.Sprintf`, with no `path.Clean`, no allowlist of pprof sub-paths, and no rejection of `..`: [4](#0-3) 

The comment on this handler ("unlike discovery, this endpoint is internal btw the node and plugin") shows the intended trust model was that only the node itself would reach the plugin's debug HTTP listener; instead it is reachable by any unauthenticated client that can send an HTTP request to the node's public web server, and the destination path is attacker-controlled.

### Impact Explanation
An unauthenticated remote client can:
- Reach and control the exact path sent to the internal per-plugin HTTP listener (bound by `p.EnvCfg.PrometheusPort` on `loopHostName`), including path segments containing `..`, bypassing the intended `/debug/pprof/` restriction.
- Access plugin internal metrics/pprof endpoints, and potentially any other route hosted on that internal listener, entirely without authentication — a capability the code comments indicate should be gateway-internal only.
This is a concrete authentication bypass to an internal-only surface, matching the "unauthorized... cross-user response confusion / authentication bypass" acceptance criteria, and follows the same root-cause pattern as CVE-2024-46898 (unsanitized URL path segment used to reach unintended server-side resources).

### Likelihood Explanation
High: the routes require no credentials, no CORS/session token, and are reachable directly at the node's standard web server port with a single crafted GET request; the plugin name only needs to match a currently-registered LOOP plugin (enumerable via the also-unauthenticated `/discovery` endpoint).

### Recommendation
- Wrap `loopRoutes` in the same `auth.Authenticate(...)` requirement used by `debugRoutes`/`metricRoutes`, so these internal-only proxy endpoints require a valid session/API token.
- In `pluginPPROFHandler`, validate/clean the `profile` parameter (e.g., `path.Clean`, reject any segment containing `..`, and restrict to a fixed allowlist of known pprof sub-paths) before constructing the outbound URL.

### Proof of Concept
1. Register or wait for a LOOP plugin to be active (name discoverable via `GET /discovery`, unauthenticated).
2. As an unauthenticated client, send:
   `GET /plugins/<pluginName>/debug/pprof/../../../metrics`
   or any other traversal payload as the `*profile` wildcard segment.
3. The handler builds `http://<loopHostName>:<PrometheusPort>/debug/pprof/../../../metrics` and forwards it via `http.DefaultClient`, returning the response body to the unauthenticated caller — demonstrating that arbitrary path segments under attacker control are forwarded to an internal service with no authentication check at the node's edge. func (l *LoopRegistryServer) pluginPPROFHandler(gc *gin.Context) {
	pluginName := gc.Param("name")
	p, ok := l.registry.Get(pluginName)
	if !ok {
		gc.Data(http.StatusNotFound, "text/plain", fmt.Appendf(nil, "plugin %q does not exist", html.EscapeString(pluginName)))
		return
	}

	// unlike discovery, this endpoint is internal btw the node and plugin
	pluginURL := fmt.Sprintf("http://%s:%d/debug/pprof/"+gc.Param("profile"), l.loopHostName, p.EnvCfg.PrometheusPort)
	urlVals, timeout := pprofURLVals(gc)
	if s := urlVals.Encode(); s != "" {
		pluginURL += "?" + s
	}
	l.logger.Infow("Forwarding plugin pprof request", "plugin", pluginName, "url", pluginURL)
	l.doRequest(gc, "GET", pluginURL, nil, timeout, pluginName)
}
