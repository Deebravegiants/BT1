### Title
Authentication Bypass by Spoofing via Unverified OIDC `email` Claim - (File: core/sessions/oidcauth/oidc.go)

### Summary
The chainlink node's OIDC authenticator binds a new user session to the `email` claim taken directly from a verified-but-untrusted ID token, without checking the `email_verified` claim or anchoring identity to the immutable `sub` (subject) claim. This mirrors CVE-2023-3128 (Grafana): a signed token is cryptographically valid, but the human-readable `email` claim inside it can be set arbitrarily by the identity provider/tenant issuing that token, allowing an attacker to claim another user's email and be issued a session under that identity.

### Finding Description
In `handleTokenExchange`, after the ID token signature/issuer/audience are verified with `oi.provider.Verifier(oi.oidcConfig).Verify(...)`, the code reads the `email` claim straight out of the token payload with no additional validation: [1](#0-0) 

That value is then persisted as the durable identity key for a brand-new session row, alongside a role computed from group claims in the same token: [2](#0-1) 

Nowhere in this flow is:
- `email_verified` checked, or
- the `sub` claim (the only IdP-guaranteed-unique identifier) used to bind or cross-check the session to a specific upstream account.

The `AuthenticationProvider` interface only exposes `AuthorizedUserWithSession`/`FindUser` by e-mail string, so every downstream consumer (audit logging, session lookup, `ClearNonCurrentSessions`) treats `email` as the trusted identity anchor: [3](#0-2) [4](#0-3) 

This is architecturally identical to the Grafana bug class: OIDC identity is verified cryptographically (signature/issuer/audience), but the human-facing `email` claim used as the actual authorization/identity key is not guaranteed unique or immutable by the protocol, and the configured provider (particularly a multi-tenant OIDC/Azure-AD-style endpoint sharing one ClientID/audience across tenants) may let a low-privilege external user set their own `email` claim to match a victim's, since `oidc.NewProvider`/`Verifier` here only validate the token against `ClientID` (audience) and issuer — not tenant/directory restriction.

### Impact Explanation
If the configured OIDC identity provider is multi-tenant or otherwise allows a caller to control the value of their own `email` claim, an unprivileged external actor can authenticate through the legitimate OIDC flow, present a token whose `email` claim equals a victim node-user's email, and receive a valid chainlink `oidc_sessions` row keyed to that victim's email. Every action performed in that session — audit log entries (`audit.AuthLoginSuccessNo2FA` etc.), any code path that scopes state to `user.Email`, and `ClearNonCurrentSessions` (which deletes all other sessions matching that email) — will be attributed to/affect the victim's identity rather than the real actor's. This is a concrete authentication/identity bypass (impersonation), not merely a cosmetic issue.

### Likelihood Explanation
Exploitability depends entirely on the deployed OIDC provider's configuration (whether it is multi-tenant / allows attacker-controlled email claims), which is an operator choice, not a code guarantee. However, the vulnerable code path applies unconditionally to every OIDC deployment because there is no defensive check (`email_verified`, `sub` pinning) regardless of provider trustworthiness. Any operator who points chainlink at a multi-tenant IdP (a common configuration pattern for enterprise IdPs) is immediately exposed.

### Recommendation
- Require and check the `email_verified` claim (reject or treat as untrusted if false/absent).
- Persist and match on the IdP's immutable `sub` claim (optionally scoped by `iss`) as the primary session identity key rather than `email`; use `email` only as a display attribute.
- Document/enforce that multi-tenant OIDC endpoints must restrict issuance to a specific tenant (e.g., via `tid` claim validation) if `email` is ever used as an identity/authorization key.

### Proof of Concept
1. Configure chainlink's OIDC authenticator against a multi-tenant OIDC provider (shared `ClientID`/audience across tenants).
2. As an attacker, register/control an account in your own tenant/directory and set its `email` profile field to a target victim's chainlink-node email address.
3. Complete the normal `/oidc-login` → provider redirect → `handleTokenExchange` flow; the ID token is signature/issuer/audience-valid.
4. `handleTokenExchange` extracts `email` = victim's address from the token and inserts a new `oidc_sessions` row keyed to that email (`core/sessions/oidcauth/oidc.go` lines 247-262), with a role derived from the attacker's own group claims.
5. The attacker now holds a session cookie whose downstream identity (audit logs, `ClearNonCurrentSessions`, any email-keyed logic) is the victim's email, achieving identity spoofing/authentication bypass analogous to CVE-2023-3128.

// ClearNonCurrentSessions removes other oidc_sessions for the user tied to sessionID.
func (oi *oidcAuthenticator) ClearNonCurrentSessions(ctx context.Context, sessionID string) error {
	var email string
	if err := oi.ds.GetContext(ctx, &email, "SELECT user_email FROM oidc_sessions WHERE id = $1", sessionID); err != nil {
		return err
	}
	_, err := oi.ds.ExecContext(ctx, "DELETE FROM oidc_sessions WHERE lower(user_email) = lower($1) AND id != $2", email, sessionID)
	return err
}
