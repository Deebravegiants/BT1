### Title
Delete Operations Blocked by Global Write-Methods Kill-Switch, Preventing Removal of Already-Stored Secrets - (File: core/services/gateway/handlers/vault/handler.go)

### Summary
The `handleSecretsDelete` function in the gateway-side Vault handler applies the same `writeMethodsEnabled` gate that governs `Create`/`Update` operations to `Delete` operations as well. When operators disable vault write methods (`cresettings.Default.GatewayVaultManagementEnabled`), an already-authorized, allowlisted workflow owner is blocked from deleting their own previously stored secrets, exactly mirroring the reported Starklane pattern where a global "disabled" flag improperly blocks a withdrawal-style operation that reclaims/removes an asset the user already legitimately owns.

### Finding Description
`newHandlerWithAuthorizer` builds a single gate limiter, `writeMethodsEnabled`, keyed off the `GatewayVaultManagementEnabled` setting: [1](#0-0) 

This same limiter is checked identically in all three write handlers — `handleSecretsCreate`, `handleSecretsUpdate`, and `handleSecretsDelete` — with no distinction between "adding/mutating state" (create/update) and "removing state on the owner's request" (delete): [2](#0-1) 

Requests reach this code from `HandleJSONRPCUserMessage`, which authorizes the request via the allowlist-based `requestProcessor.ProcessRequest` (an unprivileged workflow owner whose request digest is allowlisted in the on-chain `WorkflowRegistry`) before dispatching to `handleSecretsDelete`: [3](#0-2) 

By contrast, `handleSecretsList` — a read-only operation — is not gated by `writeMethodsEnabled` at all: [4](#0-3) 

This is directly analogous to the Starklane report's bug class: a single "system enabled/disabled" toggle is used to gate both a new "deposit-like" state-changing operation (create/update of secrets) and an operation that should remain available regardless of that toggle because it only allows a user to reclaim/remove something they already control (delete of an existing, already-authorized secret). Just as blocking `withdrawTokens` under `_enabled == false` traps user assets that have already crossed the bridge, blocking `DeleteSecrets` under `writeMethodsEnabled == false` traps a user's ability to remove secrets that already exist and are already owned/authorized by them.

### Impact Explanation
When operators disable `GatewayVaultManagementEnabled` (e.g., during an incident, rollback, degraded-mode operation, or intentional lockdown of the vault write path), authorized workflow owners cannot delete secrets they already own, even though they are fully authorized and the secret already exists in the DON. This is functionally the inverse of the intended safety behavior: the moments when write methods are most likely to be disabled (incidents, suspected compromise, emergency maintenance) are exactly the moments a legitimate owner would most need to delete/rotate a secret. This can result in continued storage/availability of a secret a legitimate owner is actively trying to remove, and generally erodes the "management" guarantees the vault should provide to its (unprivileged, non-node) callers.

### Likelihood Explanation
This is not a hypothetical edge case: the gate is applied uniformly by design (`handleSecretsCreate`, `handleSecretsUpdate`, `handleSecretsDelete` all share verbatim gate-check code), so any time an operator disables `GatewayVaultManagementEnabled` for legitimate reasons (e.g. incident response), every authorized owner's delete requests are also blocked as a side effect. No malicious actor action, node compromise, or race condition is required — it is triggered by normal, expected use of the existing kill-switch.

### Recommendation
Exclude `MethodSecretsDelete` from the `writeMethodsEnabled` gate (similar to how `MethodSecretsList` is already excluded), so that disabling vault "write/management" only blocks the introduction/mutation of new secret material (`Create`/`Update`) but always allows owners to delete/reclaim secrets they already control. If a global emergency-stop of all vault mutation is truly required, consider a separate, explicit "disable delete" flag rather than reusing the same toggle for both classes of operation, so operators can consciously choose whether to also block deletion.

### Proof of Concept
1. An authorized workflow owner calls `DeleteSecrets` through the gateway; the request passes `requestProcessor.ProcessRequest` allowlist authorization successfully (owner is legitimate and the secret exists). [5](#0-4) 
2. Dispatch routes to `handleSecretsDelete`. [6](#0-5) 
3. If an operator has disabled `GatewayVaultManagementEnabled` (e.g., during an incident), `h.writeMethodsEnabled.AllowErr(ctx)` returns `limits.ErrorNotAllowed{}`, and the handler returns `UnsupportedMethodError` with message "vault write methods(create/update/delete) are disabled", never forwarding the delete request to the vault nodes. [7](#0-6) 
4. The owner's already-existing, already-authorized secret remains stored and cannot be removed until the global flag is re-enabled — mirroring the Starklane pattern of blocking withdrawal of already-received assets while the system-wide toggle is off.

```go
func (h *handler) handleSecretsDelete(ctx context.Context, ar *activeRequest) error {
	l := logger.With(h.lggr, "method", ar.req.Method, "requestID", ar.req.ID)

	err := h.writeMethodsEnabled.AllowErr(ctx)
	if errors.Is(err, limits.ErrorNotAllowed{}) {
		l.Warnw("secrets write method called but write methods are disabled", "error", err)
		return h.sendResponse(ctx, ar, h.errorResponse(ar.req, api.UnsupportedMethodError, errors.New("vault write methods(create/update/delete) are disabled: "+err.Error()), nil))
	} else if err != nil {
		l.Errorw("error checking if write methods are enabled", "error", err)
		return h.sendResponse(ctx, ar, h.errorResponse(ar.req, api.FatalError, errors.New("error checking if write methods are enabled: "+err.Error()), nil))
	}

	return h.fanOutToVaultNodes(ctx, l, ar)
}
```
