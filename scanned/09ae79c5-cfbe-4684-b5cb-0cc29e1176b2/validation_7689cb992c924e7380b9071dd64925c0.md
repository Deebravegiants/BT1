## Title
Missing domain-boundary anchor in gateway CORS wildcard origin matching allows origin bypass - (File: core/services/gateway/network/httpserver.go)

### Summary
The Chainlink Gateway's internet-facing HTTP server implements a custom CORS allow-listing function, `isAllowedOrigin`, that supports wildcard subdomain patterns such as `*.remix.com`. When checking the wildcard case, it strips the `*.` prefix and then tests whether the incoming request's `Origin` host merely ends with the resulting suffix, using `strings.HasSuffix`, without requiring a `.` (or any other domain-boundary character) immediately before the matched suffix. This is the same bug class as CVE-2017-11173 in `rack-cors`: unanchored suffix/substring matching of hostnames lets an attacker register a domain that textually ends with the allowed suffix (e.g. `evilremix.com` for an allowlist entry `*.remix.com`) and be treated as an allowed origin, even though it is not a true subdomain.

### Finding Description
In `core/services/gateway/network/httpserver.go`, `isAllowedOrigin` handles wildcard allow-list entries like this: [1](#0-0) 

```go
// check for wildcard host match (e.g., *.remix.com)
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if strings.HasSuffix(originHost, allowedHost) {
        return true
    }
}
```

After stripping the `*.` prefix, `allowedHost` becomes the bare domain (e.g. `remix.com`), and the check becomes a plain suffix test on the origin host. There is no requirement that the character preceding the matched suffix in `originHost` be a `.`. Consequently, a host like `evilremix.com` (or `attacker-remix.com`) satisfies `strings.HasSuffix("evilremix.com", "remix.com")`, and the function returns `true` even though `evilremix.com` is not a subdomain of `remix.com` at all — it merely shares a trailing string. This is functionally identical to the rack-cors flaw where `example.com.example.net` or `example.com-example.net` bypassed a regex intended to match only `example.com`, because the anchor/boundary check was missing.

This `isAllowedOrigin` result directly drives the CORS response in `handleRequest`: [2](#0-1) 

When `isAllowedOrigin` returns true, the server sets `Access-Control-Allow-Origin` to the attacker's exact `Origin` value and also allows credentials-adjacent behavior via `Access-Control-Allow-Headers`/`Methods`, enabling a browser at `evilremix.com` to make cross-origin requests to the Gateway's user-facing endpoint and read the JSON-RPC response.

### Impact Explanation
The Gateway HTTP server is an internet-facing endpoint that forwards node/DON communication (`ProcessRequest`) and returns responses containing potentially sensitive data (job/workflow results, authenticated request/response payloads) to whatever origin passes the CORS check. An operator who configures a legitimate wildcard allowlist entry such as `*.mycompany.com` (intending to permit only subdomains of `mycompany.com`) unintentionally also permits any attacker-registered domain ending in that literal string, e.g. `evilmycompany.com`, `attacker-mycompany.com`. A malicious site under attacker control can then issue authenticated/CORS-enabled requests against the Gateway on behalf of an unsuspecting victim's browser and read cross-origin responses that should have been restricted to the operator's trusted subdomains — a cross-user/cross-origin response confusion analogous to the CORS bypass in the reported CVE.

### Likelihood Explanation
Exploitation requires only that: (1) the Gateway operator configures a wildcard `CORSAllowedOrigins` entry (a documented, supported feature — see the passing test cases at [3](#0-2) ), and (2) an attacker registers a domain that textually ends with the allowed suffix and lures a victim's browser to it. Domain registration matching an arbitrary suffix is trivial and cheap for an attacker (e.g., buying `evil-remix.com`), and no interaction beyond visiting a malicious page is required from the victim. This is an unprivileged, purely client-side/network-reachable bypass with no dependency on any special access.

### Recommendation
Anchor the wildcard suffix match to a domain boundary: require that the character immediately preceding the matched suffix in `originHost` is a literal `.`, i.e. check `originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost)` instead of the current unanchored `strings.HasSuffix(originHost, allowedHost)`. Add regression tests covering hosts like `evil<allowed>` / `attacker-<allowed>` to confirm they are rejected.

### Proof of Concept
1. Configure the Gateway with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.remix.com"]`.
2. From a browser hosted at `https://evilremix.com`, send a request to the Gateway's configured `Path` with header `Origin: https://evilremix.com`.
3. `isAllowedOrigin` strips `*.` to get `allowedHost = "remix.com"`, then evaluates `strings.HasSuffix("evilremix.com", "remix.com")`, which is `true`.
4. The server responds with `Access-Control-Allow-Origin: https://evilremix.com`, allowing the attacker page's JavaScript to read the JSON-RPC response cross-origin, even though `evilremix.com` is not a subdomain of `remix.com`.

```go
func (s *httpServer) handleRequest(w http.ResponseWriter, r *http.Request) {
	if s.config.CORSEnabled {
		origin := r.Header.Get("Origin")
		if s.isAllowedOrigin(origin) {
			w.Header().Set("Access-Control-Allow-Origin", origin)
			w.Header().Set("Access-Control-Allow-Methods", "GET, POST, OPTIONS")
			w.Header().Set("Access-Control-Allow-Headers", "Content-Type")
		}

		// handle preflight requests
		if r.Method == http.MethodOptions {
			w.WriteHeader(http.StatusNoContent)
			return
		}
	}
```
