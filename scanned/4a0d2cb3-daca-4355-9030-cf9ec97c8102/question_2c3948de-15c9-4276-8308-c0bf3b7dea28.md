HinkalBase.insertCommitments' `emit NewCommitment(leaves[index], -1 * int256(insertedIndexes[index++]), ...)` for on-chain commitments casts `insertedIndexes[index]` (a `uint256` tree position that can be as large as `2**LEVELS - 1`) into `int256` then negates it, while off-chain commitments emit `int256(insertedIndexes[index])` positively — the sign is the ONLY on-chain signal distinguishing on-chain vs off-chain leaves for indexers, yet nothing in HinkalBase constrains `insertedIndexes[index] < 2**255` before this cast. Given `LEVELS` is set at Merkle construction and could be configured (or grow via future upgrades) such that `2**LEVELS - 1 >= 2**255`, can a leaf's tree index alias between the on-chain-negative and off-chain-positive encodings, causing an indexer (and, more critically, any on-chain logic that re-derives commitment/nullifier state from these indices) to misclassify a spent on-chain UTXO as an unspent off-chain one? State the equality: `int256(insertedIndexes[index])` must recover the same magnitude as the uint256 `insertedIndexes[index]` for both sign branches, which fails once the index reaches `2**255`. Impact: Critical, misattribution of leaf provenance that could be leveraged with a crafted proof to double-insert or double-nullify a leaf whose event-derived merkle path an off-chain relay trusts. Proof idea: Foundry test with `LEVELS` set high enough that `m_index` can exceed `2**255` (or a mock override), confirming the `NewCommitment` event's signed index collides between an on-chain and off-chain leaf at the same tree position.
