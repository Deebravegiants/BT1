Found it: `/v2/resume/:runID` is intentionally mounted on the `unauthedv2` route group (no `Authenticate` middleware at all) and dispatches to `PipelineRunsController.Resume`, which resumes a suspended pipeline run with attacker-supplied JSON body content.

### Title
Unauthenticated `/v2/resume/:runID` endpoint allows anyone to resume/inject results into a suspended pipeline run - (File: `core/web/router.go`, `core/web/pipeline_runs_controller.go`)

### Summary
The Chainlink node HTTP API exposes `PATCH /v2/resume/:runID` completely outside of any authentication group. Anyone able to reach the node's HTTP port (in many deployments this port is reachable from adapters/bridges or, if misconfigured, from the wider network) can call this endpoint with an arbitrary `runID` and an arbitrary `pipeline.ResumeRequest` JSON payload to resume a suspended pipeline task and inject the result value used downstream.

### Finding Description
`v2Routes` creates an `unauthedv2` group with no `auth.Authenticate(...)` middleware and mounts `Resume` directly on it: [1](#0-0) 

`PipelineRunsController.Resume` parses the `runID` path parameter and an unauthenticated JSON body into a `pipeline.ResumeRequest`, then calls `App.ResumeJobV2` to inject the result and resume the run — with no caller identity or authorization check of any kind: [2](#0-1) 

The audit log entry name itself, `audit.UnauthedRunResumed`, documents that this action is explicitly unauthenticated by design — it is meant to let external task adapters (which receive a callback/run ID out-of-band as a bearer-like secret) resume async bridge tasks. This is directly analogous to the `ReserveFund.pause()`/`unpause()` bug: a state-mutating operation that should only be triggered by a trusted, identified caller is instead reachable by anyone who can guess or intercept the identifying value (`runID`), because there is no access-control check on the endpoint itself — authorization is implicitly and solely delegated to the secrecy of the `runID` UUID.

### Impact Explanation
If a `runID` (a UUID, but potentially observable via logs, monitoring systems, error messages, or a race with the legitimate external adapter callback) is obtained by an unprivileged actor, that actor can:
- Submit an arbitrary result value for the pending task, poisoning the pipeline computation (similar in spirit to forcing "improper calculations" as in the original report, since downstream tasks/consumers trust the injected result).
- Repeatedly or prematurely resume runs, potentially causing double-processing, denial-of-service of the run, or corrupting job pipeline state that feeds on-chain transactions (e.g., a Direct Request / Bridge job whose result is later submitted on-chain).

The severity depends on `runID` unpredictability (UUIDv4, so brute force is infeasible) and network exposure of the node's core HTTP API, but the control itself is architecturally identical to the reported bug: a state-changing function with **zero** access-control gate, relying entirely on an opaque identifier rather than an explicit authentication/authorization check.

### Likelihood Explanation
Likelihood is moderate: exploitation requires knowledge of a valid, in-flight `runID`. This can leak through logs, monitoring dashboards, or through race conditions with the legitimate external initiator's own resume call (there is no idempotency/ownership check preventing a second, different caller from resuming/overwriting the same run before the legitimate one completes). Because the route bypasses `auth.Authenticate` entirely (unlike the `AuthenticateExternalInitiator` mechanism used elsewhere, e.g. `core/web/auth/auth.go` lines 119-149, which validates an access-key/secret pair), there is no cryptographic secret gating the call at all — only the runID.

### Recommendation
Require verification of a caller-held secret before permitting resume, e.g., validate the request against the external-initiator's `OutgoingToken`/`OutgoingSecret` bound to the specific run/task (similar to how `AuthenticateExternalInitiator` validates access key/secret pairs), or otherwise bind the resume call to a per-run unguessable, single-use token that is invalidated after first use, rather than relying on the run UUID alone as the only credential.

### Proof of Concept
1. Obtain (via log exposure, timing, or a race with the legitimate external adapter) the `runID` of a suspended pipeline run created by a bridge/webhook task.
2. Send `PATCH /v2/resume/<runID>` with a crafted JSON body matching `pipeline.ResumeRequest` (see `core/web/pipeline_runs_controller.go` lines 134-148) to the node's HTTP endpoint — no `X-Chainlink-EA-AccessKey`/`Secret` or session cookie is required, since the route is registered on `unauthedv2` (`core/web/router.go` line 239, 243).
3. Observe that `App.ResumeJobV2` executes with attacker-supplied results, and an audit-log entry `UnauthedRunResumed` confirms the unauthenticated resume occurred.

// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
}
