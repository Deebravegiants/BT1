### Title
View-role users can read a Bridge's `OutgoingToken` authentication secret via `GET /v2/bridge_types` and `GET /v2/bridge_types/:BridgeName` - (File: core/web/presenters/bridges.go)

### Summary
The `basic-user`/`view`-role RBAC in the OpenShift CVE fails to strip a sensitive backend secret (`restuserkey`) from a resource that low-privilege users are allowed to read. The chainlink node has an analogous pattern in its own RBAC: bridge listing/show endpoints are explicitly marked `viewOnlyAllowed: true` in the RBAC route tests, yet the resource returned to those requests includes the bridge's `OutgoingToken`, which is the credential Chainlink uses to authenticate outbound calls to the external adapter.

### Finding Description
`BridgeResource` (used for all bridge JSONAPI responses) unconditionally serializes `OutgoingToken` with no `omitempty`/redaction: [1](#0-0) 

`NewBridgeResource` copies `OutgoingToken` straight from the DB model into every response, including `Index` (list) and `Show` (single bridge): [2](#0-1) 

The controller uses this presenter for both `Index` and `Show`, with no additional filtering of fields based on caller role: [3](#0-2) 

The RBAC test suite for the HTTP API explicitly documents that `GET /v2/bridge_types` and `GET /v2/bridge_types/MOCK` are allowed for `view`-role users (`viewOnlyAllowed: true`), the lowest privilege tier: [4](#0-3) 

Role-check middleware (`RequiresViewRole`, implied by the absence of any higher role requirement on these two routes) is enforced elsewhere consistently for admin/edit-only routes, e.g. `RequiresEditRole`/`RequiresAdminRole`: [5](#0-4) 

`OutgoingToken` is the actual bearer credential the Chainlink node sends to the external adapter for outbound bridge calls (`AuthenticateBridgeType` only validates the separate `IncomingToken`/hash used by the adapter calling back into the node; `OutgoingToken` is the node's own outbound secret used by adapters to trust callbacks from Chainlink): [6](#0-5) [7](#0-6) 

This mirrors the CVE's root cause exactly: a low-privilege, authenticated role (`basic-user` in OpenShift / `view` in Chainlink) is granted read access to a resource whose RBAC-intended scope is "view metadata" but which leaks a credential secret (`restuserkey` / `OutgoingToken`) usable to impersonate/authenticate against an external system on the node's behalf.

### Impact Explanation
Any user provisioned with the lowest `view` role (created via `chainlink admin users create --role=view`, LDAP `NodeReadOnlyGroupCN`, or OIDC read claim) can call `GET /v2/bridge_types` or `GET /v2/bridge_types/:BridgeName` and obtain every configured bridge's `OutgoingToken`. Because this token is the secret Chainlink presents to the external adapter, an attacker holding it can potentially impersonate the node when interacting with, or being trusted by, that external adapter — a concrete secret-disclosure / impersonation vector consistent with the "Validate" criteria (key/secret disclosure, request impersonation) requested by the task. Severity is bounded by the fact that exploitation still requires a legitimate (if minimally privileged) authenticated API user/session.

### Likelihood Explanation
High likelihood of reachability: `view` is the default lowest role explicitly intended for read-only dashboards/monitoring accounts, and the bridge list/show endpoints are core, always-enabled API surface with no additional gating beyond `authenticateUser`/basic session check. No special conditions, race, or malicious-node/operator access is required — a normal authenticated low-privilege user triggers this by design intent (the route is deliberately "view-allowed").

### Recommendation
- Omit `OutgoingToken` (and any other outbound secret) from `BridgeResource` for `Index`/`Show` responses served to non-`admin`/`edit` roles, or redact it entirely from read paths and only reveal it on `Create`/`Update` responses to the requesting privileged user (mirroring how `IncomingToken` is already `omitempty` and only populated on creation).
- Alternatively, restrict `GET /v2/bridge_types` and `GET /v2/bridge_types/:BridgeName` to `edit`/`admin` roles, consistent with how bridge mutation (`POST`, `PATCH`, `DELETE`) is already gated to `edit`+ in the RBAC route map.
- Add/extend the RBAC route tests (`core/web/auth/auth_test.go`) to assert that sensitive fields are absent from `view`-role responses, not just that the route returns 200.

### Proof of Concept
1. Create a `view`-role API user: `chainlink admin users create --email=readonly@test.com --role=view`.
2. Log in as that user and call `GET /v2/bridge_types` (or `GET /v2/bridge_types/<bridge_name>`).
3. Observe the JSON response's `data.attributes.outgoingToken` field contains the bridge's live outbound authentication secret, confirmed by the presenter serialization test showing `outgoingToken` always present in the response body: [8](#0-7)

// Index lists Bridges, one page at a time.
func (btc *BridgeTypesController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	bridges, count, err := btc.App.BridgeORM().BridgeTypes(ctx, offset, size)

	resources := make([]presenters.BridgeResource, 0, len(bridges))
	for _, bridge := range bridges {
		resources = append(resources, *presenters.NewBridgeResource(bridge))
	}

	paginatedResponse(c, "Bridges", size, page, resources, count, err)
}

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresAdminRole extracts the user object from the context, and asserts the user's role is 'admin'
func RequiresAdminRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role != clsessions.UserRoleAdmin {
			c.Abort()
			addForbiddenErrorHeaders(c, "admin", string(user.Role), user.Email)
			jsonAPIError(c, http.StatusForbidden, errors.New("Forbidden"))
			return
		}
		handler(c)
	}
}

// AuthenticateBridgeType returns true if the passed token matches its
// IncomingToken, or returns false with an error.
func AuthenticateBridgeType(bt *BridgeType, token string) (bool, error) {
	hash, err := incomingTokenHash(token, bt.Salt)
	if err != nil {
		return false, err
	}
	return subtle.ConstantTimeCompare([]byte(hash), []byte(bt.IncomingTokenHash)) == 1, nil
}
