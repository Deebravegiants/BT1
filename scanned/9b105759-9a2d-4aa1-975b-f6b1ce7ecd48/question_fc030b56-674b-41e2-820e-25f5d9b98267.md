Target: ShopifyAPI::Clients::HttpClient @headers['Host'] vs @base_uri when Context.api_host is set. Preconditions: multi-tenant app uses a single Context.api_host with per-request Host header for routing (documented pattern for Plus/enterprise proxies). Call sequence: HttpClient#initialize sets @headers['Host'] = session.shop unconditionally whenever api_host present, independent of whether session.shop was itself validated. Binding: SHOP BINDING requires the Host header shop equal the shop whose access token is attached; if session.shop was fixated cross-tenant (see earlier findings) this pairing becomes (attacker session, victim shop) sent with (attacker's own access_token). Impact: Critical, cross-tenant request smuggling - a reverse proxy keyed on Host header could deliver the attacker's authenticated request, with the attacker's access token, into the victim shop's context. Proof idea: minitest constructing HttpClient with Context.api_host set and a session.shop equal to an attacker-fixated victim domain, asserting @headers['Host'] equals that unvalidated value alongside X-Shopify-Access-Token from the attacker's own session.
