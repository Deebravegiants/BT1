### Title
Unbounded `Addresses` (and `Topics` values) in `eth_getLogs` RPC filter enables JSON-RPC DoS - (File: `substrate/frame/revive/rpc/src/receipt_provider.rs`)

### Summary
`pallet-revive-eth-rpc`'s `eth_getLogs` implementation accepts an `alloy_rpc_types::Filter` with no server-side bound on the number of addresses (or per-topic values) a caller may supply. `ReceiptProvider::logs()` iterates every entry in `filter.address` and every entry inside each topic slot, binding one SQL parameter per value with no cap, mirroring the exact `minievm` `FilterCriteria.Addresses` unbound-DoS pattern described in the reference report.

### Finding Description
`EthRpcServerImpl::get_logs` forwards the caller-supplied `Filter` straight to the receipt provider without any validation: [1](#0-0) 

`ReceiptProvider::logs()` then builds a SQL query by looping over every address and every topic value with no upper bound check, in contrast with the length-checked query result set (`MAX_LOG_RESULTS`): [2](#0-1) 

Notably, this codebase already recognizes the need for such a bound elsewhere: the `eth_subscribe("logs", …)` filter explicitly caps addresses and topic values to 1000 entries via `BoundedOneOrMany<Address, 1000>` / `BoundedVec<..., ConstU32<4>>`: [3](#0-2) 

But the same bound was never applied to the `eth_getLogs` (`Filter`) path, which uses the unbounded `alloy_rpc_types::Filter` type directly (confirmed by the type migration in `prdoc/pr_12037.prdoc`, which replaced the pallet's own `AddressOrAddresses`/`Addresses`/`FilterTopic` types with the alloy `Filter`/`FilterSet` types without adding any length guard).

The only mitigating control is the general JSON-RPC request body size limit (`--rpc-max-request-size`, default configurable in MB via `RpcParams::rpc_max_request_size`): [4](#0-3) 
As demonstrated in the original report, this byte-size limit is not an effective bound — hundreds of thousands of 20-byte addresses can be packed well within default MB-scale limits, and processing them (looping to build a dynamic SQL query with one bound parameter per address/topic entry) consumes disproportionate CPU/time per request.

### Impact Explanation
An unauthenticated JSON-RPC client can send a single `eth_getLogs` request with a very large `address` array (and/or many topic values), forcing the eth-rpc node to construct a huge dynamic `QueryBuilder` (looping and calling `push_bind` per element) and execute the resulting SQL statement. Repeated requests can degrade or exhaust worker threads on the JSON-RPC server, denying service to other legitimate RPC users of that node. This does not affect on-chain consensus/state, but it is a real availability risk for `pallet-revive`'s Ethereum-compatible RPC endpoint, analogous in root cause and severity class to the confirmed medium/high-severity finding in the referenced report.

### Likelihood Explanation
High for anyone with network access to a public `pallet-revive-eth-rpc` endpoint (the standard Ethereum-compatible RPC front-end for parachains using `pallet-revive`). No special privileges or trusted role are required — the `eth_getLogs` method is a "safe" method typically exposed for all users, and the request is a single unauthenticated JSON-RPC call. The attack cost is low (a handful of HTTP requests), while the existing byte-size request limit is easily satisfied given how compact hex-encoded addresses are.

### Recommendation
Enforce a maximum number of addresses (and cap per-topic-slot value counts) in `EthRpcServerImpl::get_logs` / `ReceiptProvider::logs()`, mirroring the bound already applied to the `eth_subscribe("logs", …)` path (e.g., reuse `BoundedOneOrMany<_, N>`-style limits or a constant `MAX_FILTER_ADDRESSES`), and return a clear RPC error when exceeded, before the query builder loop runs.

### Proof of Concept
Send `eth_getLogs` with a `Filter` populated with a very large `address` array, e.g. via the `alloy_rpc_types::Filter::address(vec![...])` builder used in `ReceiptProvider::logs` tests: [5](#0-4) 
Scaling this from 2 addresses to hundreds of thousands (as in the original minievm PoC) drives `ReceiptProvider::logs()` into building/binding a correspondingly large SQL query with no bound check at `receipt_provider.rs:776-798`, reproducing the same class of CPU/time blow-up demonstrated in the external report's `Test_GetLogs` benchmark.
