### Title
Inbound XCMP messages are silently and permanently dropped when `WeightMeter` capacity is exceeded, independent of `suspend_threshold` backpressure - (File: cumulus/pallets/xcmp-queue/src/lib.rs)

### Summary
`Pallet::enqueue_xcmp_messages` enqueues only as many XCMs from an inbound HRMP page as `search_best_by` determines fit the remaining `WeightMeter` budget, and permanently discards the rest of that batch when `best_batch_footprint.msgs_count < xcms.len()`. This drop path is entirely decoupled from the `suspend_threshold`/`drop_threshold` congestion-control mechanism, which only reacts to backlog depth in the destination `pallet_message_queue`, not to weight-exhaustion drops that occur before messages ever reach that queue.

### Finding Description
`enqueue_xcmp_messages` computes footprints via `T::XcmpQueue::get_batches_footprints(sender, xcms.iter().copied(), drop_threshold)`, then picks the largest batch that still satisfies `meter.can_consume(required_weight)` using `search_best_by`: [1](#0-0) 

If the chosen `best_batch_footprint.msgs_count` is smaller than `xcms.len()`, the tail messages of that HRMP page are never enqueued into `T::XcmpQueue` and the function logs an error and returns `Err(())`; the caller (`handle_xcmp_messages`) has no retry mechanism for the discarded tail — inbound HRMP pages are consumed from the relay-chain-delivered batch once processed and are not re-delivered, so this is an unrecoverable drop for that block's page content.

The congestion-control primitives (`QueueConfigData::suspend_threshold`/`drop_threshold`, enforced via `on_queue_changed` and `QueuePausedQuery::is_paused`) operate on the *count of ready pages already enqueued* in `pallet_message_queue` for the sending para, i.e., backlog depth after successful enqueue. Because weight-exhaustion drops happen *before* messages are counted as enqueued pages, they structurally never contribute to `ready_pages`, so `suspend_threshold` cannot be tripped by this failure mode — the very drop mechanism prevents backlog accumulation that would otherwise trigger suspension.

The `WeightMeter` budget passed into `handle_xcmp_messages` derives from a fixed, publicly known reserved-XCMP-weight configuration value (a constant proportion of block weight dedicated to inbound XCMP processing), not from unpredictable per-block extrinsic activity. This makes the available enqueue budget deterministically computable off-chain by any actor that knows the runtime's weight configuration and the per-message enqueue weight function (`T::WeightInfo::enqueue_xcmp_messages`).

### Impact Explanation
An attacker with an open sibling HRMP channel (precondition, no receiving-chain privilege required beyond an already-established channel) can size batches so that every call to `handle_xcmp_messages` yields `best_batch_footprint.msgs_count < xcms.len()`, causing chronic tail-message drops each block while `ready_pages` for that channel never crosses `suspend_threshold`. Because the drop occurs at the shared-page/batch level, any legitimate messages from unrelated senders sharing the same HRMP page/processing pass can be collaterally dropped, griefing XCM delivery for the parachain's cross-chain message pipeline without paying any delivery-fee penalty (the fee-factor mechanism reacts to outbound queued-byte totals, not to inbound drop events).

### Likelihood Explanation
Feasibility depends on the attacker being able to reliably predict and exceed the fixed enqueue-weight budget per block, which is plausible since the reserved weight and per-message weight functions are public runtime configuration/benchmarked constants. The attack is repeatable every block at low cost (only requires sending XCMP messages through an already-open channel) and requires no privileged action on the receiving chain. The exact numeric window (message/page size just under meter capacity) requires runtime-specific tuning but is a deterministic computation, not guesswork.

### Recommendation
Tie congestion-control signaling to drop events, not only to enqueued backlog depth: increment a per-channel drop counter/metric when `enqueue_xcmp_messages` returns `Err(())`, and factor that into `suspend_channel` decisions (e.g., trigger suspension if drops occur for N consecutive blocks even if `ready_pages < suspend_threshold`). Additionally, consider treating partial-batch drops as a defensive/incident condition that also increases the sender's effective backpressure (e.g., forcing a signal to the sender to slow down), rather than silently discarding trailing messages with only a log entry.

### Proof of Concept
Extend `test_xcm_enqueueing_starts_dropping_on_out_of_weight` in `cumulus/pallets/xcmp-queue/src/tests.rs`:
1. Configure `QueueConfigData` with default (high) `suspend_threshold`/`drop_threshold`.
2. Construct a sequence of inbound HRMP pages whose per-message weight, multiplied by message count, exceeds the `WeightMeter` limit passed to `handle_xcmp_messages` (mirroring `T::WeightInfo::enqueue_xcmp_messages` cost), while page byte-size stays under `MaxPageSize`.
3. Call `handle_xcmp_messages` repeatedly across many simulated blocks.
4. Assert: (a) `enqueue_xcmp_messages` returns `Err(())` on every call (tail messages dropped), (b) cumulative dropped-message count grows unboundedly across blocks, (c) the channel's `OutboundXcmpStatus`/`ready_pages` (queried via `on_queue_changed`) never reaches `suspend_threshold`, confirming suspension never engages despite chronic drops.

	fn enqueue_xcmp_messages<'a>(
		sender: ParaId,
		xcms: &[BoundedSlice<'a, u8, MaxXcmpMessageLenOf<T>>],
		is_first_sender_batch: bool,
		meter: &mut WeightMeter,
	) -> Result<(), ()> {
		let QueueConfigData { drop_threshold, .. } = <QueueConfig<T>>::get();
		let batches_footprints =
			T::XcmpQueue::get_batches_footprints(sender, xcms.iter().copied(), drop_threshold);

		let best_batch_footprint = batches_footprints.search_best_by(|batch_info| {
			let required_weight = T::WeightInfo::enqueue_xcmp_messages(
				batches_footprints.first_page_pos.saturated_into(),
				batch_info,
				is_first_sender_batch,
			);

			match meter.can_consume(required_weight) {
				true => core::cmp::Ordering::Less,
				false => core::cmp::Ordering::Greater,
			}
		});

		meter.consume(T::WeightInfo::enqueue_xcmp_messages(
			batches_footprints.first_page_pos.saturated_into(),
			best_batch_footprint,
			is_first_sender_batch,
		));
		T::XcmpQueue::enqueue_messages(
			xcms.iter().take(best_batch_footprint.msgs_count).copied(),
			sender,
		);

		if best_batch_footprint.msgs_count < xcms.len() {
			tracing::error!(
				target: LOG_TARGET,
				used_weight=?meter.consumed_ratio(),
				"Out of weight: cannot enqueue entire XCMP messages batch; \
				dropped some or all messages in batch."
			);
			return Err(());
		}
		Ok(())
	}
