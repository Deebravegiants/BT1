## Analysis: ERC20/ERC777-style token interface mismatch analog

The external report's vulnerability class ("a token that doesn't implement the expected ERC20 interface causes the assumed transfer call to fail, leaving user funds stranded") has a direct structural analog in this repo's `ERC20Transactor` used to bridge XCM and `pallet-revive` (EVM) contracts.

### Title
Non-standard ERC20-compatible contracts (missing/non-conforming `transfer`) can strand XCM-transferred value in the checking account - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Finding Description
`ERC20Transactor::withdraw_asset_with_surplus` moves a user's tokens by ABI-encoding a hardcoded Solidity `IERC20.transfer(address,uint256)` call and executing it via `pallet_revive::Pallet::<T>::bare_call` against the user-supplied `asset_id` contract: [1](#0-0) 

Similarly, `deposit_asset_with_surplus` re-delivers the held credit to the beneficiary by calling `IERC20.transfer` from the `TransfersCheckingAccount` on the same contract address: [2](#0-1) 

Both functions assume the target contract strictly implements the standard ERC20 `transfer` ABI (fixed selector, `bool` return, `abi_decode_returns_validate`). If the contract at `asset_id` is a token that does not conform to this exact interface — e.g., an ERC777-style token without a compatible `transfer`, a non-standard/fee-on-transfer token, or a contract that reverts, has no fallback, or returns a different encoding — the `bare_call` either errors, reverts, or fails to decode, and the transactor returns `XcmError::FailedToTransactAsset` in every branch: [3](#0-2) [4](#0-3) 

This mirrors the reported pattern exactly: the protocol hardcodes a call to a single, assumed-standard token function (`transfer`) with no fallback or alternate path (e.g., no equivalent of ERC777 `send`), and no on-chain vetting of the token's actual ABI before it's registered as a fungible asset via `Matcher: MatchesFungibles`.

The critical asymmetry, unlike the withdraw path (which fails atomically before user balance changes, since `bare_call` failures don't commit state), is in the **deposit path when reached via `transfer_asset`**. `TransactAsset::transfer_asset`'s default implementation performs `withdraw_asset` then `deposit_asset`, and on deposit failure it makes only a **best-effort** attempt to return funds to the original owner — that reversal itself uses the same non-conforming `deposit_asset` call and can fail identically: [5](#0-4) 

If both the forward deposit and the best-effort reversal fail (same broken contract interface in both directions), the previously-withdrawn tokens remain held by `TransfersCheckingAccount` inside the ERC20/ERC777 contract with no other code path in this transactor to recover them — there is no `send`-based fallback and no governance/vetting gate visible in this file.

### Impact Explanation
If an asset (an EVM/`pallet-revive` contract address) that does not correctly implement the assumed ERC20 `transfer` ABI is registered as a fungible asset matched by `Matcher`, any XCM transfer/deposit of that asset can permanently fail. Combined with the best-effort-only reversal in `transfer_asset`, funds already moved into `TransfersCheckingAccount` can become stranded there, unrecoverable through the transactor's normal paths — functionally identical to the original report's "user cannot withdraw" outcome, but here manifesting as XCM-level fund immobilization inside a system checking account rather than a user-facing escrow contract.

### Likelihood Explanation
Likelihood hinges entirely on how `Matcher: MatchesFungibles<H160, u128>` is configured for the deployed runtime — i.e., whether arbitrary/unvetted contract addresses can be matched as transactable fungible assets, or whether only a governance-curated allowlist is used. I was not able to fully verify the concrete `Matcher` and registration/governance process wired into `asset-hub-westend`'s `xcm_config.rs` within the remaining investigation budget (the file was found to reference `ERC20Transactor`/`Erc20`/`TransfersCheckingAccount` but its `Matcher` implementation details weren't retrieved). If asset registration for this transactor requires privileged/governance vetting of the ERC20 contract's interface, this significantly reduces likelihood for an unprivileged attacker and would disqualify the finding under the program's "trusted-role compromise required" exclusion. If registration is permissionless or under-vetted, the likelihood is realistic since any user can deploy a non-conforming ERC20-like contract on `pallet-revive` and trigger the failure path via a normal XCM transfer.

### Recommendation
- Vet any contract before it can be matched/registered as a transactable fungible asset in `ERC20Transactor`, confirming it implements the standard ERC20 `transfer`/`transferFrom` ABI (selector and return-type checks, e.g., via a dry-run/static check at registration time).
- Make the best-effort reversal in `TransactAsset::transfer_asset` (`polkadot/xcm/xcm-executor/src/traits/transact_asset.rs`) more robust for this transactor specifically — e.g., detect deposit failure to the checking account and surface it distinctly, or add a recovery/claim mechanism for stuck `TransfersCheckingAccount` balances.
- Consider avoiding the withdraw-to-checking-account/deposit-from-checking-account round trip pattern in favor of a single atomic operation where possible, so a failed deposit does not leave value already extracted from the source.

### Proof of Concept
Conceptual (could not be fully validated against the live `Matcher`/registration logic due to tool-call budget):
1. Deploy an EVM contract via `pallet_revive` that does not implement a standards-conformant ERC20 `transfer(address,uint256) returns (bool)` — e.g., only implements a custom `send` method, or reverts unconditionally on `transfer`.
2. Have this contract registered/matched as a fungible asset id via the configured `Matcher: MatchesFungibles<H160, u128>` for `ERC20Transactor`.
3. Initiate an XCM `TransferAsset`/`ReserveAssetTransfer` instruction moving this asset from account A to account B via `ERC20Transactor::transfer_asset`.
4. `withdraw_asset_with_surplus` succeeds (moves the balance to `TransfersCheckingAccount` inside the contract, assuming the contract's non-standard transfer still moves funds to a plain transfer-like call, or fails atomically leaving A's funds intact).
5. `deposit_asset_with_surplus` fails because the contract's `transfer` doesn't conform to the ABI expected by `IERC20::transferCall::abi_decode_returns_validate` [6](#0-5) .
6. `transfer_asset`'s best-effort reversal to account A also calls `deposit_asset` on the same non-conforming contract and fails identically [7](#0-6) , leaving the withdrawn balance stuck in `TransfersCheckingAccount` with no recovery path in this transactor.

	fn transfer_asset(
		asset: &Asset,
		from: &Location,
		to: &Location,
		context: &XcmContext,
	) -> Result<Asset, XcmError> {
		match Self::internal_transfer_asset(asset, from, to, context) {
			Err(XcmError::AssetNotFound | XcmError::Unimplemented) => {
				let credit = Self::withdraw_asset(asset, from, Some(context))?;
				Self::deposit_asset(credit, to, Some(context)).map_err(|(unspent, error)| {
					// best effort try to return the assets to original owner
					let _ = Self::deposit_asset(unspent, from, Some(context));
					error
				})?;
				Ok(asset.clone())
			},
			result => result,
		}
	}
