### Title
Permissionless `pallet-asset-conversion` pool creation with arbitrary `pallet-assets` tokens enables freezer-based DoS / fund-lockup on liquidity pools - (File: `substrate/frame/asset-conversion/src/lib.rs`, `substrate/frame/assets/src/lib.rs`)

### Summary
The Solana report's root cause — trusting an arbitrary, attacker-supplied token mint that carries a freeze authority, allowing the attacker to freeze the pool's token vault and DoS/lock funds — has a structural analog in `pallet-asset-conversion`. Pools can be created permissionlessly for any two `AssetKind`s [1](#0-0) , and the underlying `pallet-assets` supports a per-asset `Freezer` role that can freeze any account (including the pool's account) for that specific asset [2](#0-1) . Asset creation itself is permissionless in the reference runtimes via `CreateOrigin = AsEnsureOriginWithArg<EnsureSigned<AccountId>>` [3](#0-2) .

### Finding Description
1. Any signed account can create a "trust backed" asset in the reference asset-hub runtimes since `CreateOrigin` is `AsEnsureOriginWithArg<EnsureSigned<AccountId>>` [3](#0-2) . The creator becomes (by default) the asset's admin/freezer.
2. `pallet-assets` exposes a `freeze` extrinsic that any account holding the asset's `freezer` role can call against **any** account holding that asset, setting `AccountStatus::Frozen`, which blocks unprivileged transfers from that account [4](#0-3) . This is functionally the direct analog of Solana's "freeze authority."
3. `pallet-asset-conversion::create_pool` performs no validation of the trustworthiness of the paired `AssetKind` — it is callable by any signed origin for any two assets that satisfy `PoolLocator` [1](#0-0) .
4. `add_liquidity`/`remove_liquidity`/swaps move funds into and out of a deterministic pool account (`T::PoolLocator::address`) via `T::Assets::transfer` [5](#0-4) [6](#0-5) . If the malicious asset's freezer freezes the pool account, subsequent transfers of that asset out of the pool fail, causing `do_remove_liquidity`/swap calls to revert (they are marked `#[transactional]`, see `MutateLiquidity` impl) [7](#0-6) , thereby locking both the malicious asset and the paired legitimate asset (e.g., native token) inside the pool for as long as the attacker keeps the freeze in place.

### Impact Explanation
An attacker can: (a) permissionlessly create a token with themselves as freezer, (b) create a pool pairing it with a legitimate asset (native token, DOT, USDC, etc.), (c) lure/incentivize liquidity providers to add liquidity, (d) freeze the pool account for their malicious asset. This blocks `remove_liquidity` and any swap route touching that pool, permanently locking the paired legitimate funds contributed by other LPs unless/until the attacker voluntarily thaws — a direct DoS and potential permanent loss of funds for third-party liquidity providers, matching the impact class of the original Solana report.

### Likelihood Explanation
Likelihood is significant but conditioned on ecosystem trust assumptions: `pallet-asset-conversion` and `pallet-assets` are generic, reusable pallets — whether a deployed runtime treats them as permissionless (as in the reference asset-hub configs shown here, where `CreateOrigin = EnsureSigned`) is a runtime-integration decision. In the actual Polkadot/Kusama Asset Hub runtimes, UI/documentation and community norms discourage interacting with unvetted assets, similar to the Solana team's stated mitigation ("we recommend users only interact with official/reviewed pools"). No on-chain enforcement in `pallet-asset-conversion` itself prevents pairing with a freezable/malicious asset — the protection, if any, is purely a runtime-configuration or off-chain-trust matter, not a code-level guarantee.

### Recommendation
- In `pallet-asset-conversion::do_create_pool`, optionally support a configurable "allowed asset" check (e.g., a trait bound like `T::PoolCreationValidator` or restricting `AssetKind` to assets without an active `Freezer`/with `Freezer = ()`), analogous to the Solana report's recommendation to validate absence of freeze authority.
- For asset-hub–style deployments, consider distinguishing "sufficient"/vetted assets from freely mintable ones when whitelisting valid pool pairs, and/or emit a warning/flag in metadata for assets that have a non-trivial `Freezer`.
- Document clearly (as the Solana team did) that LPs bear counterparty risk from the freezer authority of paired assets, and that only pools using assets without freeze capability (or from vetted/sufficient asset lists) should be considered safe.

### Proof of Concept
Conceptual reproduction using existing test scaffolding in `substrate/frame/asset-conversion/src/tests.rs`:
1. `Assets::force_create`/`Assets::create` a new asset `X` with `freezer = ATTACKER` (in the runtime's actual permissionless config, `Assets::create` signed by ATTACKER suffices) — see `pallet_assets::Config::Freezer = AssetsFreezer` wiring in asset-hub configs [8](#0-7) .
2. `AssetConversion::create_pool(ATTACKER, Native, X)` then `AssetConversion::add_liquidity(VICTIM, Native, X, ...)` to have a victim LP contribute native funds, using the same call pattern shown in `can_add_liquidity`/`can_remove_liquidity` tests [9](#0-8) [10](#0-9) .
3. ATTACKER calls `Assets::freeze(ATTACKER_origin, X, pool_account)`, which is permitted since `origin == d.freezer` [11](#0-10) .
4. VICTIM's subsequent `AssetConversion::remove_liquidity` call fails because the pool account is frozen for asset `X`, and the transactional wrapper reverts the whole operation, leaving VICTIM's native-side liquidity trapped as well.

**Uncertainty**: I could not directly view `do_create_pool`'s full body (only excerpts around it) or `functions.rs`'s exact `can_withdraw`/frozen-status enforcement code within this session, so the precise line ranges enforcing the frozen-account transfer rejection in `pallet-assets` were not fully confirmed by direct citation. The behavioral claim is based on the pallet's documented account `AccountStatus::Frozen` semantics and the `freeze`/`thaw` dispatchables' doc comments [12](#0-11) .

		/// Disallow further unprivileged transfers of an asset `id` from an account `who`. `who`
		/// must already exist as an entry in `Account`s of the asset. If you want to freeze an
		/// account that does not have an entry, use `touch_other` first.
		///
		/// Origin must be Signed and the sender should be the Freezer of the asset `id`.
		///
		/// - `id`: The identifier of the asset to be frozen.
		/// - `who`: The account to be frozen.
		///
		/// Emits `Frozen`.
		///
		/// Weight: `O(1)`
		#[pallet::call_index(11)]
		pub fn freeze(
			origin: OriginFor<T>,
			id: T::AssetIdParameter,
			who: AccountIdLookupOf<T>,
		) -> DispatchResult {
			let origin = ensure_signed(origin)?;
			let id: T::AssetId = id.into();

			let d = Asset::<T, I>::get(&id).ok_or(Error::<T, I>::Unknown)?;
			ensure!(
				d.status == AssetStatus::Live || d.status == AssetStatus::Frozen,
				Error::<T, I>::IncorrectStatus
			);
			ensure!(origin == d.freezer, Error::<T, I>::NoPermission);
			let who = T::Lookup::lookup(who)?;

			Account::<T, I>::try_mutate(&id, &who, |maybe_account| -> DispatchResult {
				maybe_account.as_mut().ok_or(Error::<T, I>::NoAccount)?.status =
					AccountStatus::Frozen;
				Ok(())
			})?;

			Self::deposit_event(Event::<T, I>::Frozen { asset_id: id, who });
			Ok(())

#[test]
fn can_remove_liquidity() {
	new_test_ext().execute_with(|| {
		let user = 1;
		let token_1 = NativeOrWithId::Native;
		let token_2 = NativeOrWithId::WithId(2);
		let pool_id = (token_1.clone(), token_2.clone());

		create_tokens(user, vec![token_2.clone()]);
		let lp_token = AssetConversion::get_next_pool_asset_id();
		assert_ok!(AssetConversion::create_pool(
			RuntimeOrigin::signed(user),
			Box::new(token_1.clone()),
			Box::new(token_2.clone())
		));

		let ed_token_1 = <Balances as fungible::Inspect<_>>::minimum_balance();
		let ed_token_2 = <Assets as fungibles::Inspect<_>>::minimum_balance(2);
		assert_ok!(Balances::force_set_balance(
			RuntimeOrigin::root(),
			user,
			10000000000 + ed_token_1
		));
		assert_ok!(Assets::mint(RuntimeOrigin::signed(user), 2, user, 100000 + ed_token_2));

		assert_ok!(AssetConversion::add_liquidity(
			RuntimeOrigin::signed(user),
			Box::new(token_1.clone()),
			Box::new(token_2.clone()),
			1000000000,
			100000,
			1000000000,
			100000,
			user,
		));

		let total_lp_received = pool_balance(user, lp_token);
		LiquidityWithdrawalFee::set(&Permill::from_percent(10));

		assert_ok!(AssetConversion::remove_liquidity(
			RuntimeOrigin::signed(user),
			Box::new(token_1.clone()),
			Box::new(token_2.clone()),
			total_lp_received,
			0,
			0,
			user,
		));
