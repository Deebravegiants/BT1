## Title
Vault request replay guard is permanently consumed for legitimate requests whose owner-binding validation fails, causing denial of legitimate retries - (File: `core/capabilities/vault/authorizer.go`)

## Summary
In `authorizer.AuthorizeRequest`, the request replay guard records the request digest via `a.replayGuard.CheckAndRecord(...)` immediately after JWT/allowlist authorization succeeds, but *before* the owner-binding check `validateSecretOwnersMatchAuthorized` is evaluated [1](#0-0) . If the owner-binding check subsequently fails, the request is ultimately rejected with no vault operation performed for the user — yet the digest has already been irrevocably marked "seen" in the replay guard, exactly mirroring the reported bug class where state (`lastRewardTime`/consumed resource) is advanced even though the caller received zero benefit.

## Finding Description
`AuthorizeRequest` runs the pipeline: authorize (JWT or allowlist) → record digest in replay guard → validate owner binding [2](#0-1) . The replay guard is a simple map of digest → expiry that rejects any later `CheckAndRecord` call for the same digest until it expires [3](#0-2) .

Because `CheckAndRecord` executes unconditionally on the success path of the underlying auth mechanism, and only *afterwards* is the owner match validated, any request that authenticates successfully (valid JWT signature/digest) but whose secret owner does not match the JWT's derived `workflowOwner` (`validateSecretOwnersMatchAuthorized`, e.g. a client-side bug, a race where the workflow owner mapping changed, or simply a legitimate retry racing with an aborted first attempt) will consume the replay-guard slot for that exact request digest and then be rejected with `owner binding rejected request`. The gateway comment for the request processor explicitly documents the pipeline order as `ValidateStructureBeforeAuth → AuthorizeRequest → Prefix ID → StampAuthorizedParams → ValidateOwnerScopedLimits` [4](#0-3) , confirming owner-scoped limit/ownership checks are deliberately deferred, but the replay-guard recording happens for both the success and the eventual-owner-failure path.

Since the request digest is derived deterministically from the JSON-RPC request contents (`req.Digest()`), any retry of the identical request (same params, same request ID) will be rejected as `ErrRequestAlreadySeen` — even though the original attempt never resulted in a secret create/update/delete/list actually being performed. The caller cannot simply "wait and resubmit" because the digest is only cleared on expiry (bound to the JWT's `exp` claim/leeway) [5](#0-4) .

This is directly analogous to the reported `_claimRewards` bug: state is mutated ("consumed") on a path that does not actually deliver the outcome (rewards / a processed secrets request) to the caller, penalizing them on the next legitimate attempt.

## Impact Explanation
Impact is medium: an unprivileged client that legitimately retries an operation whose owner-binding check fails once (e.g., benign owner metadata drift, application bug, or a race in `workflow_owner` derivation) is locked out from resubmitting the exact same vault operation (secrets create/update/delete/list) until the JWT's expiry+leeway window elapses. This can cause a denial of service on a specific vault operation for a legitimate owner, and in the worst case an attacker could deliberately craft a validly-signed-but-owner-mismatched JWT copying a victim's exact intended request digest to pre-consume the replay slot for that request, blocking the victim's legitimate follow-up attempt (a griefing/DoS vector against a specific known request).

## Likelihood Explanation
Likelihood is medium: the owner-binding failure path is reachable by any caller who can obtain a validly-signed JWT for a digest they don't fully control the ownership metadata of, or by natural client retries after partial failures. No privileged/malicious node or peer access is required — it's reachable purely through the public/unprivileged client-facing vault gateway request flow.

## Recommendation
Move the `replayGuard.CheckAndRecord` call to after `validateSecretOwnersMatchAuthorized` succeeds, so the digest is only marked "seen" once the request is fully authorized to proceed to secrets processing:

```diff

 	}

 		...
 	}

-		...
-		return nil, err
-	}

 	}
+	if err := a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt()); err != nil {

## Proof of Concept
1. Craft (or obtain) a validly signed JWT for a `vault.secrets.create` request whose `request_digest` claim matches request R, but whose derived `workflowOwner` does not match the `owner` field inside R's `EncryptedSecrets`.
2. Submit R to the gateway. `AuthorizeRequest` succeeds JWT validation, calls `CheckAndRecord(digest(R), exp)` which succeeds and records the digest, then `validateSecretOwnersMatchAuthorized` fails and the request is rejected (`owner binding rejected request`) — confirmed by code flow at `core/capabilities/vault/authorizer.go:109-116`.
3. The legitimate owner now resubmits the exact same request R (same params/ID, correct owner-context this time, or via retry after fixing metadata) with a fresh, correctly-scoped JWT whose digest still equals `digest(R)`.
4. `CheckAndRecord(digest(R), ...)` returns `ErrRequestAlreadySeen` (per `request_replay_guard.go:41-43`), and the legitimate request is rejected as a replay even though no secret was ever created for R.

	authResult, err := a.authorizeRequest(ctx, req)
	if err != nil {
		return nil, err
	}
	if authResult == nil {
		err = errors.New("auth mechanism returned nil auth result")

		return nil, err
	}
	if err := a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt()); err != nil {
		a.lggr.Debugw("replay guard rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "", "error", err)
		return nil, err
	}
	if ownerErr := validateSecretOwnersMatchAuthorized(req, authResult.AuthorizedOwner()); ownerErr != nil {

	}

	return authResult, nil
}

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
```
