Confirmed: the `httpTriggerHandler.callbacks` map in `core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go` is keyed **globally by `requestID`** — not scoped per-workflow or per-owner. Any unprivileged caller who can reach the gateway's HTTP trigger endpoint can supply an attacker-chosen `req.ID` for their *own* (attacker-owned, permissionlessly registered) workflow, and `setupCallback` will claim that ID in the shared map. If a victim later submits a legitimate request using the same `id` value (e.g. a client-generated idempotency key, timestamp, or predictable/guessable ID) for a *different* workflow, `setupCallback` rejects it with `jsonrpc.ErrConflict` ("requestID: %s has already been used") — denying the victim's request, analogous to the Connext front-running griefing pattern where an attacker uses the same identifier with different (attacker-controlled) associated data to block the legitimate operation.

### Title
Global (non-workflow-scoped) request-ID collision allows unprivileged actor to grief another user's HTTP trigger request - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

### Summary
`httpTriggerHandler.setupCallback` deduplicates in-flight HTTP trigger requests using only `requestID` as the map key, with no binding to the calling workflow or owner. Since `req.ID` is fully attacker-controlled and workflow registration/authorization is per-workflow (not globally exclusive), any unprivileged actor with their own registered workflow can pre-claim an arbitrary `requestID` and cause any other workflow's request using that same ID to be rejected.

### Finding Description
`HandleUserTriggerRequest` validates the request, resolves `workflowID`, authorizes the caller against that specific `workflowID` via `authorizeRequest`/`WorkflowMetadataHandler.Authorize` [1](#0-0) , then calls `setupCallback`, which checks/writes into `h.callbacks[requestID]`: [2](#0-1) 

Authorization only proves the caller controls a valid signer for *some* `workflowID` — it does not bind the chosen `requestID` to that workflow or to the identity of the caller. `id` is supplied by the untrusted client in the JSON-RPC request and only checked for emptiness and absence of `/`: [3](#0-2) 

Because `h.callbacks` is a single global map (not `map[workflowID]map[requestID]...`), two different workflows (owned by two different, mutually untrusted parties) cannot use the same `requestID` concurrently — the second one to arrive is rejected as a conflict, exactly mirroring the Connext bug class where an unprivileged party can use a shared identifier with different associated data to block a legitimate operation tied to that identifier.

### Impact Explanation
An attacker who can register any workflow (workflow registration is permissionless on-chain per the WorkflowRegistry reference in this file) and reach the gateway's public trigger endpoint can pre-emptively "squat" a `requestID` value that they predict or observe a target is about to use (e.g., idempotency keys derived from timestamps, sequential counters, or client-side UUIDs leaked via other channels), causing the legitimate request to fail with `ErrConflict`. This is a denial-of-service against a specific workflow execution attempt, not a fund-movement or secret-disclosure bug, but it directly matches the accepted bug class ("request impersonation" / griefing via shared identifier).

### Likelihood Explanation
Moderate-to-low: exploitation requires the attacker to predict or learn a victim's chosen `requestID` before the victim's request is processed, and workflow registration/authorization (JWT-signed, per `WorkflowMetadataHandler.Authorize`) constrains who can be "the workflow" but not what `requestID` they submit. If IDs are attacker-guessable (e.g., low-entropy or observable), the collision is trivial to trigger with a single request sent slightly earlier.

### Recommendation
Scope the in-flight-request dedup key by `(workflowID, requestID)` instead of `requestID` alone in `h.callbacks` (and correspondingly in `HandleNodeTriggerResponse` lookups), so an unrelated workflow cannot pre-claim or collide with another workflow's request ID.

### Proof of Concept
1. Attacker registers/owns Workflow A (permissionless) and obtains a valid signer key for it.
2. Attacker predicts/observes that Victim's Workflow B will soon receive a trigger request with `id = "X"`.
3. Attacker sends a `workflows.execute` JSON-RPC request to the gateway with `id: "X"`, targeting Workflow A, with a valid JWT for Workflow A — `setupCallback` inserts `h.callbacks["X"]`.
4. Victim's legitimate request with `id: "X"` for Workflow B arrives; `setupCallback` finds `h.callbacks["X"]` already present and returns `jsonrpc.ErrConflict` ("requestID: X has already been used"), denying the victim's execution request [4](#0-3) .

Note: I could not fully verify how `requestID` values are generated/communicated on the client side across the wider CRE/workflow tooling (i.e., whether IDs are ever predictable/observable enough in practice to make this exploitable at scale), since that client-side generation logic was outside the indexed scope reachable from this investigation. If precise confirmation of ID predictability in a specific client is needed, a deeper repo/session review of workflow-execution client SDKs would be required.

func (h *httpTriggerHandler) HandleUserTriggerRequest(ctx context.Context, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback, requestStartTime time.Time) error {
	triggerReq, err := h.validatedTriggerRequest(ctx, req, callback)
	if err != nil {
		return err
	}

	workflowID, err := h.resolveWorkflowID(ctx, triggerReq, req.ID, callback)
	if err != nil {
		return err
	}

	key, err := h.authorizeRequest(ctx, workflowID, req, callback)
	if err != nil {
		return err
	}

	if err = h.checkRateLimit(ctx, workflowID, req.ID, callback); err != nil {
		return err
	}

	strippedWorkflowID := strings.TrimPrefix(workflowID, "0x")
	legacyExecutionID, err := workflows.EncodeExecutionID(strippedWorkflowID, req.ID) //nolint:staticcheck // legacy ID kept for observability comparison
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID: " + err.Error())
	}
	// Workflows shouldn't use more than one HTTP trigger. If we ever need to support multiple triggers, we'd need to pass
	// trigger index to the Gateway handler and somehow allow senders to pick. For now, we use trigger index 0.
	// Execution IDs here are used only for logging.
	executionIDWithTriggerIndex, err := workflows.GenerateExecutionIDWithTriggerIndex(strippedWorkflowID, req.ID, 0)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID with trigger index: " + err.Error())
	}
	h.lggr.Debugw("processing request",
		"legacyExecutionID", legacyExecutionID,
		"executionIDWithTriggerIndex", executionIDWithTriggerIndex,
		"requestID", req.ID,
		"workflowID", workflowID)

	reqWithKey, err := reqWithAuthorizedKey(triggerReq, *key)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error marshaling trigger request: " + err.Error())
	}

	doneCh, err := h.setupCallback(ctx, req.ID, callback, requestStartTime, workflowID)
	if err != nil {
		return err
	}

	return h.sendWithRetries(ctx, legacyExecutionID, executionIDWithTriggerIndex, reqWithKey, workflowID, doneCh)

func (h *httpTriggerHandler) validateRequestID(ctx context.Context, requestID string, callback handlers.Callback) error {
	if requestID == "" {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "'id' field is required and cannot be empty. Use a new unique request 'id' for each request", callback)
		return errors.New("empty request ID")
	}
	// Request IDs from users must not contain "/", since this character is reserved
	// for internal node-to-node message routing (e.g., "http_action/{workflowID}/{uuid}").
	if strings.Contains(requestID, "/") {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "request ID must not contain '/'", callback)
		return errors.New("request ID must not contain '/'")
	}
	return nil
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
