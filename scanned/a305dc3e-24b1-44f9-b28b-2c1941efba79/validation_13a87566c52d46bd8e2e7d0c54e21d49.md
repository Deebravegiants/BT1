## Finding

### Title
LDAP Injection via Improper DN Escaping in Bind/Search Construction - (File: core/sessions/ldapauth/ldap.go)

### Summary
The `CreateSession`, `TestPassword`, and `FindUser` functions in the LDAP authentication provider build LDAP Bind DNs and search-filter DN comparisons by concatenating unprivileged, attacker-controlled input (`sr.Email` / `email` from the public, unauthenticated `/sessions` login endpoint) with `fmt.Sprintf`, after passing it only through `ldap.EscapeFilter`. `ldap.EscapeFilter` only escapes RFC 4515 filter metacharacters (`\`, `*`, `(`, `)`, NUL) — it does not perform RFC 4514 DN escaping (commas, plus signs, quotes, leading `#`/space, etc.). Because the escaped value is subsequently embedded directly into a DN string, an attacker can inject additional RDN components into the constructed Bind DN or the DN-valued attribute comparison inside a search filter.

### Finding Description
`CreateSession` builds the bind target as: [1](#0-0) 
using `ldap.EscapeFilter` (filter-context escaping) to sanitize the email, then splicing it into a DN string via `fmt.Sprintf("%s=%s,%s,%s", ...)`. The identical pattern is used in `TestPassword`: [2](#0-1) 
and in `FindUser`, where the same filter-escaped email is embedded as a DN-shaped value inside a `uniquemember` filter comparison: [3](#0-2) 

Since `sr.Email` originates from an unauthenticated, rate-limited POST body on `/sessions` [4](#0-3)  and `EscapeFilter` does not neutralize DN-structural characters (`,`, `+`, `"`, `<`, `>`, `;`, leading `#`/space), a caller can inject extra RDN components into the DN string used for `conn.Bind(searchBaseDN, sr.Password)`. This mirrors the CVE-2016-8750 bug class: usernames used to construct directory queries/binds are not encoded for the syntactic context they are placed in, enabling LDAP injection.

### Impact Explanation
Malformed or crafted DN/filter values reaching the upstream LDAP server can, depending on the server's DN-tree layout, redirect the bind target to unintended entries or corrupt the `uniquemember` comparison used to derive the user's role in `FindUser`/`CreateSession`, and can also trigger malformed LDAP protocol operations against the directory server — the same "improper encoding leading to injection/DoS" root cause identified in CVE-2016-8750. This directly affects `CreateSession` (authentication) and `TestPassword` (used to gate `NewAPIToken` issuance in `core/web/user_controller.go`), both reachable by an unprivileged, unauthenticated client.

### Likelihood Explanation
The `/sessions` endpoint is unauthenticated and only protected by a generic unauthenticated rate limit [5](#0-4) , so any external actor can submit arbitrary `Email` values with no prior privilege. Exploitation reliability depends on the target LDAP server's directory layout, which lowers likelihood of a fully deterministic authentication bypass but does not eliminate the injection primitive itself.

### Recommendation
Replace `ldap.EscapeFilter` with proper RFC 4514 DN escaping (e.g., the `go-ldap` library's `ldap.EscapeDN`/attribute-value DN-encoding equivalent) wherever the value is placed into a DN component, and continue using `EscapeFilter` only for values placed inside filter expressions. Consider validating that `sr.Email` matches an expected email/username character set before using it in any LDAP-directed string construction.

### Proof of Concept
1. Send `POST /sessions` with `{"email": "x,ou=AdminsOrOtherOU,dc=example,dc=com", "password": "<attacker-known password for that DN>"}`.
2. `CreateSession` builds `searchBaseDN = "uid=x,ou=AdminsOrOtherOU,dc=example,dc=com,ou=users,dc=custom,dc=example,dc=com"` [6](#0-5)  — the injected comma alters the DN's RDN structure prior to `conn.Bind`, rather than being treated as a literal character of the `uid` value, because `EscapeFilter` never escapes `,`.
3. Depending on directory layout this can bind against an unintended DN, or otherwise cause LDAP protocol/parse errors consistent with the injection class described in CVE-2016-8750.
