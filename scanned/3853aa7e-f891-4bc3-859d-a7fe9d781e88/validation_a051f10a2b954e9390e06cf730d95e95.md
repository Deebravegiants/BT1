### Title
Unauthenticated Pipeline Run Resume Endpoint Allows Arbitrary Job Run Manipulation - (File: core/web/router.go)

### Summary
The `PATCH /v2/resume/:runID` endpoint is registered on the `unauthedv2` route group, which has no authentication middleware attached at all, unlike every other route in the router which is gated behind `auth.Authenticate(...)` with token/session/external-initiator checks and further role checks via `auth.RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole`.

### Finding Description
In `core/web/router.go`, the route is mounted on the unauthenticated group: [1](#0-0) 

Contrast this with the sibling job-run-triggering endpoint `POST /v2/jobs/:ID/runs`, which requires authentication (`AuthenticateExternalInitiator`, `AuthenticateByToken`, `AuthenticateBySession`) plus `auth.RequiresRunRole`: [2](#0-1) 

The handler backing `/resume/:runID`, `PipelineRunsController.Resume`, accepts an arbitrary run-task UUID and an arbitrary JSON body decoded into a `pipeline.ResumeRequest`, then calls `App.ResumeJobV2(ctx, taskID, result)` to finish a pending pipeline task with attacker-supplied data/errors, with no ownership, role, or session check whatsoever: [3](#0-2) 

This is functionally analogous to the reported `mintRebalancer`/`burnRebalancer` bug class: a state-mutating operation (finishing/resuming a task, i.e., writing an arbitrary result into a job run) that is exposed without any access control to any unauthenticated caller who can guess or enumerate a `runID` (task UUID). The route is even explicitly logged via `audit.UnauthedRunResumed`, indicating this exposure is a known, intentional design choice for resuming tasks like webhook/bridge callbacks awaiting external results — but it means any unauthenticated actor who obtains/guesses the UUID can inject arbitrary task results (or force task completion/failure) for that pipeline run.

### Impact Explanation
An unauthenticated party who can guess or discover a pending task's UUID can call this endpoint to force-complete a paused pipeline task with attacker-controlled `pipeline.ResumeRequest` data. Since job pipelines can chain into contract-writing tasks (e.g., ETH transaction tasks), this could let an unauthenticated actor inject falsified data into a running job, and — depending on the specific job's pipeline logic that consumes the resumed value — potentially influence downstream on-chain writes or bridge/EA callback results. However, unlike the referenced `mintRebalancer`/`burnRebalancer` case, this is not a direct "any address can mint tokens" primitive: exploitation requires (a) knowledge of a valid, still-pending task UUID (a v4 UUID, high entropy, not guessable) and (b) a pipeline configuration where the resumed value is trusted downstream without further validation. Because task UUIDs are cryptographically random and typically only known to the legitimate external-initiator/bridge caller that is supposed to invoke resume, and the design has an explicit audit log entry (`UnauthedRunResumed`) suggesting this was a deliberate, accepted design tradeoff (this pattern is inherited from upstream chainlink and not new/introduced by this fork), the concrete unprivileged-attacker impact is limited primarily to a scenario where UUIDs leak or are otherwise obtainable.

### Likelihood Explanation
Low-to-moderate. Exploitation requires possession of a valid pending task UUID, which is high-entropy and not exposed by any of the routes examined for unauthenticated callers. This is a design-known gap (evidenced by the specific `UnauthedRunResumed` audit event name), not a newly introduced bug, and mirrors upstream Chainlink node behavior rather than a fork-specific regression.

### Recommendation
If this behavior is not strictly required to be fully unauthenticated, consider requiring the external-initiator's `OutgoingSecret`/token (already generated per `ExternalInitiator` and used for callback authentication) to be validated against the specific run/task before allowing resume, rather than relying solely on UUID secrecy. At minimum, ensure task UUIDs are never leaked via logs, error messages, or other endpoints, and consider rate-limiting/monitoring calls to `/v2/resume/:runID` to detect brute-force attempts.

### Proof of Concept
1. Obtain or guess a pending pipeline task UUID (`runID`) for a job with an external-initiator/bridge task awaiting an async callback.
2. Send `PATCH /v2/resume/<runID>` with an arbitrary JSON body shaped as a `pipeline.ResumeRequest` (e.g., `{"error": null, "value": "<attacker-controlled-value>"}`) without any authentication headers or session cookie.
3. Observe that `core/web/pipeline_runs_controller.go`'s `Resume` handler is invoked (since the route is on the `unauthedv2` group with no `auth.Authenticate` middleware) and calls `App.ResumeJobV2`, completing the task with the attacker-supplied result — confirmed by the `UnauthedRunResumed` audit log entry being emitted with no associated user/session.

// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
}
