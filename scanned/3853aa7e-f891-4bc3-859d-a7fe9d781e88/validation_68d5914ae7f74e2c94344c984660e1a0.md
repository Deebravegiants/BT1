### Title
Cross-user JSON-RPC request-ID collision allows griefing/DoS on the CRE Gateway handlers - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go], [File: core/services/gateway/handlers/confidentialrelay/handler.go])

### Summary
The `BatonLaunchpad.create` bug is a class of "attacker-controlled identifier collision" griefing: anyone who can predict or observe another user's chosen identifier (there, a CREATE2 `salt`) can front-run it and permanently occupy that slot, causing the legitimate caller's transaction to revert. The Chainlink Gateway's JSON-RPC request handlers exhibit the same pattern at the application layer: several handlers key their in-flight-request tracking map purely by the client-supplied `req.ID` string, with no per-caller/per-owner namespacing, so any client of the same DON/gateway can occupy a request ID before the legitimate owner uses it, causing the victim's real request to be rejected.

### Finding Description
In the HTTP trigger handler, `setupCallback` registers the request under the raw, attacker-controlled `requestID` global map key: [1](#0-0) 

If an entry with that `requestID` already exists, the *new* caller is rejected with `jsonrpc.ErrConflict`: [2](#0-1) 

This is confirmed by the handler's own test, which shows a second request using the same `ID` is rejected as an "in-flight request", even though it is a distinct request/callback: [3](#0-2) 

Crucially, the map key `requestID` is the value the *client itself* supplies in the JSON-RPC envelope — it is not derived from the authenticated workflow ID/owner, and different users' requests targeting different workflows still share this single flat namespace. There is no `owner`/auth-derived prefix applied before the `h.callbacks[requestID]` lookup/insert.

The same pattern exists in the confidential-relay gateway handler, where `newActiveRequest` keys `h.activeRequests` by the raw `req.ID` and rejects on collision with a plain "request ID already exists" error, again confirmed by its own duplicate-ID test: [4](#0-3) [5](#0-4) 

The vault handler follows an identical `h.activeRequests[req.ID]` collision-check pattern: [6](#0-5) 

However, for the vault handler I was not able to fully confirm whether `req.ID` is rewritten/namespaced by the authenticated owner before this check runs (the test file references an `owner + RequestIDSeparator + requestID` pattern for the *response* ID, which may or may not apply to the map key used for collision detection) — this needs further verification with a background Devin session that can trace `requestProcessor.ProcessRequest`'s mutation of `req.ID`.

Any authenticated caller able to reach the same DON/gateway handler instance (e.g., any workflow owner with valid auth for their own workflow) can send a request with a `requestID` equal to one they expect (or observe) another legitimate user to use. If they win the race, the legitimate user's subsequent identical-ID request is rejected outright with a conflict/duplicate error, denying them service for that request — directly analogous to the BatonLaunchpad `salt` front-running griefing.

### Impact Explanation
This causes a temporary denial of service to a specific user's request on the gateway: their legitimate request fails with `ErrConflict`/"already exists" instead of being processed, forcing a retry with a different ID. It does not lead to fund loss or state corruption, matching the "Medium" impact classification of the original BatonLaunchpad finding — a targeted, but recoverable, DoS.

### Likelihood Explanation
Exploitation requires an attacker to guess or observe another user's `requestID` and beat them to the gateway. If client SDKs use predictable IDs (sequence counters, timestamps, hashes of known workflow inputs), or if the attacker can observe an in-flight ID via any side channel, this is easy to execute but has limited attacker incentive (pure griefing, no economic gain) — consistent with the "Medium" likelihood in the original finding.

### Recommendation
Namespace the in-flight-request tracking key by the authenticated caller identity (e.g., workflow owner/authorized key, similar to how the original recommendation was to mix `msg.sender` into the CREATE2 `salt`) rather than relying solely on the client-supplied `req.ID`. For example, use `ownerOrAuthKey + separator + req.ID` as the map key in `setupCallback` (http_trigger_handler.go) and `newActiveRequest` (confidentialrelay/handler.go, vault/handler.go), so that request IDs from different authenticated principals cannot collide with each other.

### Proof of Concept
1. Legitimate user U plans to submit a workflow-execute request to the gateway with `requestID = "42"` for `workflowID = W`.
2. Attacker A (any authorized caller, possibly for a different/own workflow) sends a request first with the identical `ID = "42"` in the JSON-RPC envelope, which is accepted and stored at `h.callbacks["42"]` (per `setupCallback`, `core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go:419-427`).
3. When U's request with `ID = "42"` arrives, `setupCallback` finds the existing entry and rejects U's request with `jsonrpc.ErrConflict` ("requestID: 42 has already been used..."), exactly as demonstrated by the existing unit test `TestHttpTriggerHandler_HandleUserTriggerRequest/duplicate request ID` (`core/services/gateway/handlers/capabilities/v2/http_trigger_handler_test.go:320-357`), which shows the second, distinct caller's request is refused solely due to `ID` reuse.
4. U's legitimate execution is denied until they retry with a different, unpredictable ID — the same griefing pattern as the CREATE2 salt front-run in the original report.

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], labels requestLabels, callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID, "executionID", labels.ExecutionID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		labels:    labels,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}
