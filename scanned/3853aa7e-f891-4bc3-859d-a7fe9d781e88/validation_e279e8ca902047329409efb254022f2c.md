### Title
Unsynchronized concurrent map access in `WorkflowMetadataHandler.Authorize` allows data race on JWT authorization state - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` reads the `h.authorizedKeys` map without holding `h.mu`, while a background goroutine (`syncMetadata`, run on a periodic ticker started in `Start`) replaces that same map under `h.mu.Lock()`. This is a classic unsynchronized concurrent read/write of a Go map — the same bug class as the reported `lever` crate issue (shared mutable state reachable across "threads"/goroutines without proper synchronization), but manifesting in Go as a data race on the authorization data path used to gate access to a workflow's HTTP trigger.

### Finding Description
`Authorize` is invoked on every unprivileged HTTP trigger request to verify the caller's JWT signer against the set of keys authorized for a given workflow: [1](#0-0) 

Note line 92: `keys, exists := h.authorizedKeys[workflowID]` is executed with **no lock held** (`h.mu` is never acquired in `Authorize`), even though every other accessor of `h.authorizedKeys`/`h.workflowIDToRef`/`h.workflowRefToID` (`GetWorkflowID`, `GetWorkflowReference`, `WorkflowShards`) takes `h.mu.RLock()`.

Meanwhile, `syncMetadata` — run periodically via `h.runTicker(..., h.syncMetadata)` from `Start` — rebuilds fresh maps and swaps them into `h.authorizedKeys`, `h.workflowRefToID`, `h.workflowIDToRef`, `h.workflowShards` under `h.mu.Lock()`: [2](#0-1) [3](#0-2) 

`Authorize` is called directly from the HTTP trigger handler's request path, which is the entry point for unprivileged/external callers submitting a signed JWT to trigger a workflow (`core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go`, one call site found via `grep`). Because Go map reads are not safe for concurrent use while another goroutine may be writing (including whole-map reassignment, which is a plain pointer/field write in the struct but the *read* of `h.authorizedKeys[workflowID]` races with the *write* `h.authorizedKeys = authorizedKeys` at the field level), this can trigger Go's runtime race detector fault ("fatal error: concurrent map read and map write") or, under `-race`-undetected/optimized builds, an inconsistent read of the map reference/internals.

### Impact Explanation
- At minimum this is a crash/DoS vector: an unprivileged workflow-trigger caller can hit the race window during every periodic `syncMetadata` cycle (default `MetadataAggregationIntervalMs`), and Go's runtime will fatally panic the process on detecting concurrent map read/write, taking down the gateway handler goroutine (and, depending on panic recovery boundaries, the process).
- Because this data structure directly gates JWT-signer authorization for workflow HTTP triggers (`Authorize` checks `keys[key]` from `h.authorizedKeys[workflowID]`), a race that yields a stale/inconsistent snapshot of the map at the moment of concurrent reassignment could plausibly cause incorrect authorization decisions (reading from a map mid-swap), i.e. an authorization bypass or unintended failure, though the primary and most reliably reproducible consequence is a runtime fault/DoS rather than guaranteed silent bypass. Full memory-corruption-style impact (as in the Rust CVE, which involves Send/Sync unsoundness) doesn't have a direct Go equivalent, since Go is memory-safe even with data races; the meaningful production risk here is process crash (availability) and a secondary risk of authorization-logic incorrectness.

### Likelihood Explanation
High-frequency race window: `syncMetadata` runs on every `MetadataAggregationIntervalMs` tick (default 1 minute per `defaultMetadataAggregationIntervalMs`), and `Authorize` runs on every single incoming HTTP trigger request from any external/unprivileged caller. Given production traffic volume, the two goroutines will regularly execute concurrently, making the race easily triggerable without any special privilege — just normal use of the HTTP trigger capability.

### Recommendation
Acquire `h.mu.RLock()`/`h.mu.RUnlock()` around the `h.authorizedKeys[workflowID]` lookup in `Authorize`, consistent with the locking already used in `GetWorkflowID`, `GetWorkflowReference`, and `WorkflowShards`. Also audit `Authorize` for any other unsynchronized field access before merging the fix.

### Proof of Concept
1. Start a `WorkflowMetadataHandler` with a short `MetadataAggregationIntervalMs` (e.g., 10ms) so `syncMetadata` runs in a tight loop, continuously reassigning `h.authorizedKeys` under `h.mu.Lock()`.
2. Concurrently, from another goroutine simulating an unprivileged HTTP trigger caller, repeatedly call `h.Authorize(workflowID, token, req)` with a valid workflow ID/JWT in a loop.
3. Run under `go test -race` or in a build with race detection enabled — the concurrent unsynchronized read at `keys, exists := h.authorizedKeys[workflowID]` (workflow_metadata_handler.go:92) against the locked write at workflow_metadata_handler.go:178 will be flagged as a data race, and under sufficient load Go's runtime can raise `fatal error: concurrent map read and map write`, terminating the process.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}
