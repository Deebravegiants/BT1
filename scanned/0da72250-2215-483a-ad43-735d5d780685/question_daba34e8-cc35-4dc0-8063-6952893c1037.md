Attacker input: any standard's MultiPayload with a `signature` field that a custom IIntentSigner implementation re-encodes after computing the payload (e.g. signRaw normalizes a secp256k1 recovery-id byte or base58 padding), so the signature stored in the returned multiPayload differs in string form from what the relay actually verifies against. Preconditions: custom intentSigner passed via sdk.signAndSendIntent({signer: customSigner}). Call sequence: intentSigner.signIntent returns multiPayload with signature S1 -> onBeforePublishIntent computes computeIntentHash(multiPayload) (signature-independent, only payload bytes are hashed) -> intentRelayer.publishIntent submits multiPayload with signature S1 to the relay, which itself normalizes/re-encodes to S2 for on-chain submission and returns intent_hash computed from the final S2-signed transaction. Impact: Critical - if intent identity ever incorporates signature bytes anywhere downstream (e.g., duplicate-detection keyed by intent_hash), the integrator's local hash silently diverges causing a duplicate signAndSendIntent call for the same intent, resulting in two on-chain executions consuming the same funds. Whose funds: caller's signed amount, if the nonce isn't yet invalidated on the first submission's failure path.
