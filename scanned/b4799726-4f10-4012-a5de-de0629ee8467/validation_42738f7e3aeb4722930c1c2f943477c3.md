### Title
Gateway `savedCallbacks` response routing is keyed only by client-supplied `MessageID`, not bound to sender identity, enabling cross-user response misdirection - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The h2o report describes a class of bug where a resumption/session identifier is not cryptographically bound to the principal (server address/cert) it was originally established with, letting an attacker with only partial trust redirect a victim's traffic to itself. The Chainlink gateway's `WebAPIHandler` has an analogous flaw: it correlates a pending user request with the eventual DON-node response purely via the caller-supplied `MessageID` string, with no binding to the original requester's identity (signer), and no protection against a second, colliding submission overwriting the pending entry.

### Finding Description
When an external caller submits a legacy trigger request to the gateway, `HandleLegacyUserMessage` stores the caller's `Callback` in the `savedCallbacks` map keyed solely by the request's `MessageID` (client-controlled, taken directly from the request body/JSON-RPC ID): [1](#0-0) 

There is no check for whether `msg.Body.MessageID` already exists in the map — a second request with the same `MessageID` (from a different signer/sender) silently overwrites the previously registered callback for that ID. The explicit `TODO` comment confirms that no allowlist or rate-limiting is applied before this registration step: [2](#0-1) 

When a DON node later responds, the gateway looks the callback up again purely by `MessageID` and dispatches the response to whatever `Callback` is currently stored, deleting the entry: [3](#0-2) 

`Message.Validate()` only checks structural well-formedness (lengths, non-null bytes) and recovers a signer address via ECDSA signature recovery, but the recovered `Sender` is never used to scope or verify ownership of the `savedCallbacks` entry: [4](#0-3) 

Any party can generate an arbitrary ECDSA key, sign a well-formed message (`msg.Sign`), and submit it to the gateway's public HTTP endpoint via `ProcessRequest`, which only validates structure/DON existence, not sender authorization, before invoking the handler: [5](#0-4) 

If an attacker submits a request whose `MessageID` collides with a legitimate, currently in-flight request (guessed, observed, or brute-forced — nothing enforces high-entropy or per-sender uniqueness of `MessageID`), the attacker's `Callback` replaces the victim's in `savedCallbacks`. When the DON node's response for the original request arrives back at the gateway keyed by that same `MessageID`, it is delivered to the attacker's callback instead of the legitimate caller's — i.e., cross-user response confusion, structurally identical to the CVE's misdirection of a resumed session to the wrong principal because the identifier used for correlation is not bound to the originating party.

### Impact Explanation
A successful collision lets an unprivileged external caller receive a response destined for another user's web API trigger request, which can include the DON node's processed output. This is a cross-user response confusion vulnerability with the impact of unauthorized disclosure of another caller's response data via the internet-facing gateway.

### Likelihood Explanation
Exploitation requires the attacker to win a race — submitting a colliding `MessageID` request after the victim's original submission but before the DON node's response returns — and requires a `MessageID` value the attacker can predict or reuse. Since `MessageID` is entirely client-supplied and its uniqueness/entropy is not enforced or verified against the sender, and the gateway's own code documents that allowlist/rate-limiting for this path is not yet implemented (`TODO`), this is more likely to occur than typical production hardening would allow. It is still bounded by timing constraints of the race, making the overall likelihood medium.

### Recommendation
- Bind `savedCallbacks` entries to the verified `msg.Body.Sender` (already extracted during `Validate()`) in addition to `MessageID`, e.g. use a composite key `(Sender, MessageID)`.
- Reject registration of a `MessageID` that already exists in `savedCallbacks` (return an error) rather than silently overwriting it.
- Complete the pending allowlist/rate-limiting check noted in the `TODO` comment before accepting and registering a callback for a legacy user message.

### Proof of Concept
1. Legitimate user U signs and submits a `web_api_trigger` legacy message with `MessageID = "X"` to the gateway; gateway stores `savedCallbacks["X"] = U.callback` and forwards to DON members.
2. Before the DON node responds, attacker A generates their own ECDSA key, crafts and signs a structurally valid message with the same `MessageID = "X"`, and submits it to the same public gateway endpoint.
3. Gateway's `HandleLegacyUserMessage` overwrites `savedCallbacks["X"] = A.callback` (no existing-key check, no sender binding) — see [1](#0-0) .
4. The DON node responds with its result for `MessageID = "X"`; `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]` and delivers the response to A instead of U — see [3](#0-2) .

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageID) == 0 || len(m.Body.MessageID) > MessageIDMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageID, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonID) == 0 || len(m.Body.DonID) > MessageDonIDMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonID, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
