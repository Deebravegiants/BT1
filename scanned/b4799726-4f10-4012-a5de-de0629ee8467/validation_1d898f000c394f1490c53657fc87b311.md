### Title
Local-auth API tokens are not revoked on password change, allowing continued authenticated access with stale long-lived credentials - ([File: core/sessions/localauth/orm.go])

### Summary
When a local-auth user changes their password (self-service, via `PATCH /v2/user/password` or the `updateUserPassword` GraphQL mutation), only the user's web *session* is invalidated. The long-lived API token (`token_key` stored on the `users` row, functioning like an OAuth refresh token that grants full role-based access without further interactive login) is never revoked. This mirrors the Zitadel bug class: a security-sensitive credential-invalidation event (session termination / account lock) fails to also invalidate the longer-lived token that can independently re-establish full authenticated access.

### Finding Description
The password-update code path calls `ClearNonCurrentSessions` and then `SetPassword`, but never calls `DeleteAuthToken`: [1](#0-0) [2](#0-1) 

`SetPassword` in the local ORM only updates `hashed_password`; it does not touch the `token_key`/API-token columns on the `users` row: [3](#0-2) 

The API token is a persistent secondary credential, checked independently of the session/password via `FindUserByAPIToken`, which authenticates purely against `token_key` stored on the same row: [4](#0-3) [5](#0-4) 

By contrast, the LDAP and OIDC authentication providers correctly purge *both* the session table *and* the API-token table together whenever a user's trust state changes (e.g., deactivated upstream): [6](#0-5) 

The local-auth provider has no equivalent step tying `SetPassword` (or its callers) to `DeleteAuthToken`. `DeleteAuthToken` exists in the `AuthenticationProvider` interface and is presumably wired to the explicit "Delete API Token" endpoint, but it is not invoked as part of the password-change flow: [7](#0-6) 

### Impact Explanation
A password change is a security boundary — typically performed because the user suspects their credentials (and thus their browser session) have been compromised, or an admin/CLI operator has reset the password to lock out prior access. Because the API token is left untouched, anyone who previously obtained that API token (e.g., via a compromised session, leaked config file, or a malicious script that read `/v2/user/token` beforehand) retains full authenticated access to the node's HTTP API, with the current role, indefinitely — completely bypassing the intended effect of the password change. This satisfies "unauthorized continued authenticated access" analogous to the refresh-token-not-invalidated CWE-613 pattern in the report.

### Likelihood Explanation
This is reachable by any authenticated (even minimally privileged) local user simply by exercising the normal, unprivileged self-service password-change API — no special access or race condition is required. The only precondition is that an API token was previously issued for the account (a supported, common feature via `UserAPITokenEnabled`). This makes the bug straightforward to trigger and exploit whenever an attacker has captured a token before the legitimate user resets their password.

### Recommendation
In `SetPassword` (or in the two callers `UserController.updateUserPassword` and `Resolver.UpdateUserPassword`), also call `DeleteAuthToken(ctx, user)` to revoke any existing API token whenever the password is changed, matching the behavior already implemented for LDAP/OIDC session+token purging on trust-state changes.

### Proof of Concept
1. Enable `WebServer.UserAPITokenEnabled = true`.
2. As user A, log in via session, then create an API token (`CreateAndSetAuthToken`), and note `AccessKey`/`Secret`.
3. Attacker obtains the API token (e.g., captured from logs/config or a compromised session).
4. User A suspects compromise and changes their password via `PATCH /v2/user/password` (or GraphQL `updateUserPassword`), which calls `ClearNonCurrentSessions` + `SetPassword` only.
5. Attacker continues to send authenticated requests using `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers (per `AuthenticateByToken`), which still succeed because `token_key` was never revoked — confirming persistent unauthorized access despite the password reset. [8](#0-7)

func (u *UserController) updateUserPassword(c *gin.Context, user *clsession.User, newPassword string) error {
	ctx := c.Request.Context()
	sessionID, err := getCurrentSessionID(c)
	if err != nil {
		return err
	}
	orm := u.App.AuthenticationProvider()
	if err := orm.ClearNonCurrentSessions(ctx, sessionID); err != nil {
		u.App.GetLogger().Errorf("failed to clear non current user sessions: %s", err)
		return errors.New("unable to update password")
	}
	if err := orm.SetPassword(ctx, user, newPassword); err != nil {
		if errors.Is(err, clsession.ErrNotSupported) {
			return errUnsupportedForAuth
		}
		u.App.GetLogger().Errorf("failed to update current user password: %s", err)
		return errors.New("unable to update password")
	}
	return nil
}

func (r *Resolver) UpdateUserPassword(ctx context.Context, args struct {
	Input UpdatePasswordInput
}) (*UpdatePasswordPayloadResolver, error) {
	if err := authenticateUser(ctx); err != nil {
		return nil, err
	}

	session, ok := webauth.GetGQLAuthenticatedSession(ctx)
	if !ok {
		return nil, errors.New("couldn't retrieve user session")
	}

	dbUser, err := r.App.AuthenticationProvider().FindUser(ctx, session.User.Email)
	if err != nil {
		return nil, err
	}

	if !utils.CheckPasswordHash(args.Input.OldPassword, string(dbUser.HashedPassword)) {
		r.App.GetAuditLogger().Audit(audit.PasswordResetAttemptFailedMismatch, map[string]any{"user": dbUser.Email})

		return NewUpdatePasswordPayload(nil, map[string]string{
			"oldPassword": "old password does not match",
		}), nil
	}

	if err = r.App.AuthenticationProvider().ClearNonCurrentSessions(ctx, session.SessionID); err != nil {
		return nil, clearSessionsError{}
	}

	err = r.App.AuthenticationProvider().SetPassword(ctx, &dbUser, args.Input.NewPassword)
	if err != nil {
		return nil, failedPasswordUpdateError{}
	}

	r.App.GetAuditLogger().Audit(audit.PasswordResetSuccess, map[string]any{"user": dbUser.Email})
	return NewUpdatePasswordPayload(session.User, nil), nil
}

// AuthenticateByToken authenticates a User by their API token.

// Implements authMethod
func AuthenticateByToken(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	token := &auth.Token{
		AccessKey: c.GetHeader(APIKey),
		Secret:    c.GetHeader(APISecret),
	}
	if token.AccessKey == "" {
		return auth.ErrorAuthFailed
	}

	if token.Secret == "" {
		return auth.ErrorAuthFailed
	}

	// We need to first load the user row so we can compare tokens using the stored salt
	user, err := authr.FindUserByAPIToken(ctx, token.AccessKey)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) || errors.Is(err, clsessions.ErrUserSessionExpired) {
			return auth.ErrorAuthFailed
		}
		return err
	}

	ok, err := clsessions.AuthenticateUserByToken(token, &user)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionUserKey, &user)

	return nil
}
