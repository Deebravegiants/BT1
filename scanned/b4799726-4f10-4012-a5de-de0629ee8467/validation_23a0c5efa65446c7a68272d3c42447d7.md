### Title
Unbounded growth of registered web-API triggers causes O(n·m) DoS on every gateway trigger message - (File: core/capabilities/webapi/trigger/trigger.go)

### Summary
The Alchemix report describes a missing per-actor cap (`MAX_DELEGATES`) that lets an attacker cheaply grow a data structure that is then walked in a hot path (`_moveTokenDelegates`/`_moveAllDelegates`), causing gas exhaustion and DoS for anyone who has to process it. The Chainlink analog is `triggerConnectorHandler.RegisterTrigger` in the web-API trigger capability: there is no limit on the number of triggers that can be registered, nor on the size of each trigger's `AllowedSenders`/`AllowedTopics` sets, and every single incoming gateway trigger message is processed by iterating the *entire* set of registered triggers, causing unbounded linear-time growth of a shared, request-hot code path.

### Finding Description
`RegisterTrigger` inserts a new entry into the shared map `h.registeredWorkflows` for every workflow that subscribes to `web-api-trigger@1.0.0`, with no cap on the total number of registrations and no cap on `len(reqConfig.AllowedSenders)` or `len(reqConfig.AllowedTopics)`: [1](#0-0) 

The only validation is that `AllowedSenders` is non-empty; there is no upper bound check comparable to Alchemix's `MAX_DELEGATES`.

Every time an external caller sends a trigger message through the gateway (`HandleGatewayMessage` → `processTrigger`), the handler takes a snapshot of *all* registered triggers and does a nested loop over every trigger and every topic in the incoming payload, doing map lookups against `allowedTopics`/`allowedSenders` and invoking the rate limiter for each match: [2](#0-1) 

Because `registeredWorkflows` has no maximum size, any workflow owner able to register additional web-API triggers (a routine, low-privilege operation available to any workflow author) can grow this map without bound. Each subsequent trigger message from any sender then costs `O(len(triggers) × len(topics))` work on the node processing that gateway connection, exactly mirroring the Alchemix pattern where an attacker cheaply grows a delegate list that is then walked during any transfer/mint/burn.

### Impact Explanation
As the number of registered triggers grows unboundedly, processing cost for `processTrigger` — invoked for every trigger message received from the gateway, from any external sender — grows linearly with the number of registrations. This degrades trigger dispatch latency/throughput for the whole node/DON handling that capability, and in the worst case (many workflows each registering with large `AllowedTopics`) can consume enough CPU per incoming message to constitute a denial of service against the gateway trigger capability shared by all workflows, not just the party that registered the triggers. This matches the "Griefing"/DoS impact category from the source report, where an unbounded per-actor registration degrades a shared hot path for other users.

### Likelihood Explanation
Registering a web-API trigger capability config is a normal, expected workflow action and is not gated by any global or per-owner size limit in this code path (no equivalent of `MAX_DELEGATES` for `registeredWorkflows`, `AllowedSenders`, or `AllowedTopics`). Any actor able to deploy/register workflows using this trigger can trigger the growth cheaply and repeatedly, similar to how Alchemix's attacker only needed a locked NFT and a `delegate()` call.

### Recommendation
- Enforce a maximum number of concurrently registered triggers (global and/or per-owner), analogous to `MAX_DELEGATES`.
- Enforce maximum sizes for `AllowedSenders` and `AllowedTopics` per trigger registration.
- Consider indexing triggers by topic (e.g., `map[topic][]*webapiTrigger`) instead of a full linear scan in `processTrigger`, so the cost of dispatch is proportional to matches, not to the total number of registrations.

### Proof of Concept
1. Register N web-API triggers (e.g., via workflow registration) each with a large `AllowedTopics`/`AllowedSenders` list; there is no rejection since `RegisterTrigger` only requires `AllowedSenders` to be non-empty.
2. Send a trigger message through the gateway (`HandleGatewayMessage` → `MethodWebAPITrigger`).
3. Observe that `processTrigger` iterates the full `triggers` slice and, for each, the full `topics` slice from the incoming payload — CPU cost scales with `N × registered AllowedTopics × incoming topics`, degrading processing for all other trigger traffic on the same node.

func (h *triggerConnectorHandler) RegisterTrigger(ctx context.Context, req capabilities.TriggerRegistrationRequest) (<-chan capabilities.TriggerResponse, error) {
	cfg := req.Config
	if cfg == nil {
		return nil, errors.New("config is required to register a web api trigger")
	}

	reqConfig, err := h.ValidateConfig(cfg)
	if err != nil {
		return nil, err
	}

	if len(reqConfig.AllowedSenders) == 0 {
		return nil, errors.New("allowedSenders must have at least 1 entry")
	}

	h.mu.Lock()
	defer h.mu.Unlock()
	_, errBool := h.registeredWorkflows[req.TriggerID]
	if errBool {
		return nil, fmt.Errorf("triggerId %s already registered", req.TriggerID)
	}

	rateLimiterConfig := reqConfig.RateLimiter
	commonRateLimiter := ratelimit.RateLimiterConfig{
		GlobalRPS:      rateLimiterConfig.GlobalRPS,
		GlobalBurst:    int(rateLimiterConfig.GlobalBurst),
		PerSenderRPS:   rateLimiterConfig.PerSenderRPS,
		PerSenderBurst: int(rateLimiterConfig.PerSenderBurst),
	}

	rateLimiter, err := ratelimit.NewRateLimiter(commonRateLimiter)
	if err != nil {
		return nil, err
	}

	allowedSendersMap := map[string]bool{}
	for _, k := range reqConfig.AllowedSenders {
		allowedSendersMap[k] = true
	}

	allowedTopicsMap := map[string]bool{}
	for _, k := range reqConfig.AllowedTopics {
		allowedTopicsMap[k] = true
	}

	ch := make(chan capabilities.TriggerResponse, defaultSendChannelBufferSize)

	h.registeredWorkflows[req.TriggerID] = &webapiTrigger{
		workflowID:     req.Metadata.WorkflowID,
		allowedTopics:  allowedTopicsMap,
		allowedSenders: allowedSendersMap,
		ch:             ch,
		config:         *reqConfig,
		rateLimiter:    rateLimiter,
	}

	return ch, nil
}
