### Title
Unbounded per-request linear scan and log-string materialization over the on-chain allowlist in `AllowListBasedAuth.AuthorizeRequest` - (File: core/capabilities/vault/allow_list_based_auth.go)

### Summary
Every unprivileged Vault request (e.g. `CreateSecrets`/`GetSecrets`/`ListSecrets`) is authorized by scanning the *entire* in-memory `allowListedRequests` slice synced from the `WorkflowRegistry` contract. This slice grows with every on-chain `AllowlistRequest` call made by any workflow owner and is only pruned by expiry, so the per-request work is `O(n)` in the number of currently-unexpired allowlist entries across the whole DON, with no cap analogous to `SurplusGuildMinter`'s unbounded gauge loop.

### Finding Description
`AllowListBasedAuth.AuthorizeRequest` calls `findAllowlistedItemWithRetry`, which on every attempt does: [1](#0-0) 
This pulls the full snapshot via `r.workflowRegistrySyncer.GetAllowlistedRequests(ctx)`, then:
1. Iterates once to build a `allowedRequestsStrs` slice with `fmt.Sprintf` for every single entry — this happens unconditionally, before the log call is made, regardless of the configured log level: [2](#0-1) 
2. Iterates again (linear scan) in `fetchAllowlistedItem` to find a matching digest: [3](#0-2) 

This is done for **every** incoming request, up to `retryCount+1` times if not immediately found (default retry loop), so cost is `O(retries * n)` per request.

The backing list is populated by `workflowRegistry.syncAllowlistedRequests`, which appends every new active (non-expired) on-chain allowlist entry and only removes entries once their `ExpiryTimestamp` passes: [4](#0-3) 

The on-chain `AllowlistRequest` call (invoked from `deployment/cre/workflow_registry/v2/changeset/user_workflow_registry.go` / `user_workflow_registry_ops.go`) lets a workflow **owner** register an allowlist entry with an arbitrary future `ExpiryTimestamp` (up to far future) for an arbitrary digest, and the node-side syncer paginates through `getActiveAllowlistedRequestsReverse` fetching up to `MaxResultsPerQuery` (1,000) entries per page in a loop until `SearchComplete`: [5](#0-4) 

I was unable to locate the Solidity source for `WorkflowRegistry.allowlistRequest` in this repository (only Go wrapper/binding call sites were found), so I cannot confirm from code whether the contract enforces a per-owner or global cap on the number of live allowlist entries, or a minimum/maximum expiry window. Without such a cap, any workflow owner permitted to call this on-chain function (which is a normal, not necessarily privileged, workflow-registration action) can register an unbounded number of long-lived allowlist entries, each of which permanently adds to the in-memory slice scanned on every single Vault request handled by every DON node running this authorizer — directly mirroring the `SurplusGuildMinter`/`ProfitManager.claimRewards()` pattern where an unbounded, permissionlessly-grown collection is fully iterated on a hot per-user-action path.

### Impact Explanation
If the number of live allowlist entries grows large (via repeated legitimate-looking `AllowlistRequest` calls with far-future expiries), every subsequent unprivileged Vault request incurs increasing CPU/allocation cost (string formatting + linear scan, multiplied by retry attempts) on every node in the DON that runs `AllowListBasedAuth`. This degrades or denies Vault-request processing for all users, not just the one who registered many entries — a DoS on the authorization hot path, analogous to the `getReward()`/`claimRewards()` finding in the external report. Because the Sprintf loop executes unconditionally (independent of log level), this is a real avoidable per-request cost, not just diagnostic overhead.

### Likelihood Explanation
Likelihood depends on parameters I could not verify from available code: whether the on-chain contract caps allowlist entries per owner/total, and what the maximum expiry duration is. If uncapped (as the C4 finding's `setMaxGauges` was uncapped), any workflow owner could grow the list over time. This is lower likelihood than a fully-open scan (list is periodically pruned by expiry, and appending requires a signed on-chain transaction with gas cost), but the report's own precedent shows judges treat "no evidence it cannot happen" as sufficient for medium severity given the impact is a DoS affecting all users of the authorization path.

### Recommendation
- Verify/enforce an on-chain cap on the number of concurrently active allowlist entries per owner and/or globally, and/or a maximum expiry duration, on the `WorkflowRegistry.allowlistRequest` contract.
- Replace the linear scan in `fetchAllowlistedItem` with an indexed lookup (e.g., a `map[digest]entry` built once per sync cycle in `workflowRegistry.syncAllowlistedRequests`, exposed via `GetAllowlistedRequests`/a new `GetAllowlistedRequest(digest)` accessor) so `AuthorizeRequest` is O(1) instead of O(n).
- Guard the `allowedRequestsStrs` construction with `r.lggr.Level() <= zapcore.DebugLevel` (or equivalent) so the Sprintf loop over all entries is skipped entirely at non-debug log levels.

### Proof of Concept
Not independently verified with a runnable PoC due to inability to inspect the `WorkflowRegistry.sol` contract's caps/expiry limits in this index; the Go-side amplification (unconditional per-request O(n) scan + O(n) log-string build, multiplied by retry attempts) is directly demonstrated by the code cited above in `allow_list_based_auth.go` and `workflow_registry.go`.

func (r *allowListBasedAuth) findAllowlistedItemWithRetry(ctx context.Context, req jsonrpc.Request[json.RawMessage], requestDigest string, requestDigestBytes32 [32]byte) (*workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest, []string, error) {
	for attempt := 0; attempt <= r.retryCount; attempt++ {
		allowedRequests := r.workflowRegistrySyncer.GetAllowlistedRequests(ctx)
		allowedRequestsStrs := make([]string, 0, len(allowedRequests))
		for _, rr := range allowedRequests {
			allowedReqStr := fmt.Sprintf("AuthorizedOwner: %s, RequestDigest: %s, ExpiryTimestamp: %d", rr.Owner.Hex(), hex.EncodeToString(rr.RequestDigest[:]), rr.ExpiryTimestamp)
			allowedRequestsStrs = append(allowedRequestsStrs, allowedReqStr)
		}
		r.lggr.Debugw("AllowListBasedAuth loaded allowlisted requests", "method", req.Method, "requestID", req.ID, "attempt", attempt+1, "allowedRequests", allowedRequestsStrs)

		allowlistedRequest := r.fetchAllowlistedItem(allowedRequests, requestDigestBytes32)
		if allowlistedRequest != nil {
			return allowlistedRequest, allowedRequestsStrs, nil
		}

func (w *workflowRegistry) syncAllowlistedRequests(ctx context.Context) {
	ticker := w.getTicker(defaultTickIntervalForAllowlistedRequests)
	w.lggr.Debug("starting syncAllowlistedRequests")
	for {
		select {
		case <-ctx.Done():
			w.lggr.Debug("shutting down syncAllowlistedRequests, %s", ctx.Err())
			return
		case <-ticker:
			newAllowListedRequests, totalAllowlistedRequests, head, err := w.getAllowlistedRequests(ctx, w.contractReader)
			if err != nil {
				w.lggr.Errorw("failed to call getAllowlistedRequests", "err", err)
				continue
			}
			w.allowListedMu.Lock()
			// Prune expired requests
			activeAllowlistedRequests := []workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest{}
			expiredRequestsCount := 0
			for _, request := range w.allowListedRequests {
				if int64(request.ExpiryTimestamp) > time.Now().Unix() {
					activeAllowlistedRequests = append(activeAllowlistedRequests, request)
				} else {
					expiredRequestsCount++
				}
			}

			// Add new requests
			activeAllowlistedRequests = append(activeAllowlistedRequests, newAllowListedRequests...)
			w.allowListedRequests = activeAllowlistedRequests
			w.lastSeenAllowlistedRequestsCount = totalAllowlistedRequests
			w.lggr.Debugw("synced allowlisted requests",
				"newRequestsNum", len(newAllowListedRequests),
				"expiredRequestsNum", expiredRequestsCount,
				"activeRequestsNum", len(w.allowListedRequests),
				"lastSeenOnchainRequestsNum", w.lastSeenAllowlistedRequestsCount,
				"blockHeight", head.Height,
			)
			w.allowListedMu.Unlock()
