### Title
Unbounded attacker-controlled `Topics` array causes O(N×M) loop DoS in `webapiTrigger` HandleGatewayMessage - (File: core/capabilities/webapi/trigger/trigger.go)

### Summary
`triggerConnectorHandler.processTrigger` in `core/capabilities/webapi/trigger/trigger.go` iterates every registered workflow trigger against every element of an externally-supplied `payload.Topics` slice, with no upper bound on the slice size, similar to how the Canto `tickTracking_` array could be inflated by cheap external actions and then fully iterated on every mint/burn/harvest, bricking the operation for all liquidity providers. [1](#0-0) 

### Finding Description
`HandleGatewayMessage` is the entry point invoked for every JSON-RPC message the gateway forwards to a node for the `web_api_trigger` method — this is reachable by any external, unauthenticated-to-the-node caller that can reach the gateway's web API trigger endpoint (the caller only needs a valid `sender` signature checked by the gateway/DON transport layer, not node-level authorization for the specific workflow). [2](#0-1) 

The handler unmarshals `body.Payload` into `webapicap.TriggerRequestPayload`, then pulls `payload.Topics` directly and only checks that it is non-empty — there is no cap on the number of elements: [1](#0-0) 

`processTrigger` then snapshots every workflow currently registered on the node's `registeredWorkflows` map and runs a nested loop: for each registered trigger, for each attacker-supplied topic, it does a map lookup and (on match) performs signature/rate-limit checks, ID generation, and event emission: [3](#0-2) 

Because `Topics` is fully attacker-controlled and unbounded in the deserialized payload, and `triggers` scales with however many workflows are registered on the node (a multi-tenant node can have many concurrently registered `web-api-trigger` workflows), a single crafted request with a very large `Topics` array produces an O(len(triggers) × len(topics)) amount of work inside a single call to `HandleGatewayMessage`. This mirrors the root cause of the Canto finding: an attacker inflates one side of a nested-iteration structure cheaply (small swaps growing `tickTracking_`; here, a large JSON array in one HTTP-ish payload) and that inflated structure is then iterated in full on a hot path shared by many other tenants/users (mint/burn/harvest for all LPs; here, gateway message handling for every registered workflow trigger on the node).

### Impact Explanation
If `HandleGatewayMessage` for this capability is processed synchronously/serially per gateway connector message stream (as is typical for `core.GatewayConnector` handlers), a single oversized request can consume disproportionate CPU/memory processing time on the node, delaying or starving processing of legitimate trigger messages for all other workflows registered under `web-api-trigger` on that node — a cross-tenant denial-of-service analogous to bricking mint/burn for "almost all liquidity providers" in the original report. Because the loop also holds no bound tied to registered workflow count, the blast radius grows with the number of tenants on the node, which is exactly the "affects almost every user" characteristic emphasized in the source finding.

### Likelihood Explanation
Exploitation requires only that the attacker be able to submit a `web_api_trigger` message through the gateway with an arbitrarily large `Topics` array in the JSON body — there does not appear to be a length limit enforced on `Topics` prior to this loop, and the check at line 94 only rejects the empty case. This is a cheap, single-request attack (no need to grind ticks/swaps over time as in the Canto case), making it arguably easier to trigger than the original DoS.

### Recommendation
- Enforce a hard cap on `len(payload.Topics)` (and reject/bound `len(trigger.allowedTopics)` combinations) before entering the nested loop in `processTrigger`.
- Consider inverting the iteration to look up topics against a hash set keyed by topic rather than nested double iteration, and/or limit total iterations (`len(triggers) * len(topics)`) to a safe ceiling, returning an error if exceeded.
- Validate and cap the overall size of `body.Payload` / `TriggerRequestPayload` at the message deserialization boundary (`hc.ValidatedMessageFromReq` / gateway ingress) so oversized attacker payloads are rejected before reaching capability-specific handlers.

### Proof of Concept
1. Register one or more workflows with the `web-api-trigger@1.0.0` capability so `registeredWorkflows` is non-empty (`RegisterTrigger`). [4](#0-3) 
2. As an external caller, send a `web_api_trigger` JSON-RPC message through the gateway to the target node with a `TriggerRequestPayload` whose `Topics` field contains a very large number of entries (e.g., hundreds of thousands of strings), while `AllowedTopics`/registered workflow count is nonzero.
3. `HandleGatewayMessage` → `processTrigger` executes the nested loop over `len(triggers) * len(topics)`, consuming CPU proportional to the attacker-chosen size, delaying processing of subsequent gateway messages for the node's other registered workflows. [3](#0-2) 

Note: I was not able to locate an explicit request-size or field-length limit enforced earlier in the gateway ingress path (`core/services/gateway/handlers/common/message_util.go`) for this specific method/payload within the indexed content, so it is uncertain whether an overall message-size cap elsewhere in the gateway stack partially mitigates this; a full review of that file (and its size limits, if any) would be needed to confirm the exact scale required for practical exploitation.

func (h *triggerConnectorHandler) RegisterTrigger(ctx context.Context, req capabilities.TriggerRegistrationRequest) (<-chan capabilities.TriggerResponse, error) {
	cfg := req.Config
	if cfg == nil {
		return nil, errors.New("config is required to register a web api trigger")
	}

	reqConfig, err := h.ValidateConfig(cfg)
	if err != nil {
		return nil, err
	}

	if len(reqConfig.AllowedSenders) == 0 {
		return nil, errors.New("allowedSenders must have at least 1 entry")
	}

	h.mu.Lock()
	defer h.mu.Unlock()
	_, errBool := h.registeredWorkflows[req.TriggerID]
	if errBool {
		return nil, fmt.Errorf("triggerId %s already registered", req.TriggerID)
	}

	rateLimiterConfig := reqConfig.RateLimiter
	commonRateLimiter := ratelimit.RateLimiterConfig{
		GlobalRPS:      rateLimiterConfig.GlobalRPS,
		GlobalBurst:    int(rateLimiterConfig.GlobalBurst),
		PerSenderRPS:   rateLimiterConfig.PerSenderRPS,
		PerSenderBurst: int(rateLimiterConfig.PerSenderBurst),
	}

	rateLimiter, err := ratelimit.NewRateLimiter(commonRateLimiter)
	if err != nil {
		return nil, err
	}

	allowedSendersMap := map[string]bool{}
	for _, k := range reqConfig.AllowedSenders {
		allowedSendersMap[k] = true
	}

	allowedTopicsMap := map[string]bool{}
	for _, k := range reqConfig.AllowedTopics {
		allowedTopicsMap[k] = true
	}

	ch := make(chan capabilities.TriggerResponse, defaultSendChannelBufferSize)

	h.registeredWorkflows[req.TriggerID] = &webapiTrigger{
		workflowID:     req.Metadata.WorkflowID,
		allowedTopics:  allowedTopicsMap,
		allowedSenders: allowedSendersMap,
		ch:             ch,
		config:         *reqConfig,
		rateLimiter:    rateLimiter,
	}

	return ch, nil
}
