### Title
Missing Function Level Access Control in `BridgeTypesController.Show` Exposes Bridge `OutgoingToken` Secret to Any Authenticated User - ([File: core/web/bridge_types_controller.go])

### Summary
`GET /v2/bridge_types/:BridgeName` is registered without any role-based authorization check, while every other bridge-mutating route (`Create`, `Update`, `Destroy`) is wrapped in `auth.RequiresEditRole`. This inconsistency lets any authenticated user — including one with the lowest `view` role — fetch a bridge's `OutgoingToken`, which is a credential used to authenticate outbound calls to the External Adapter.

### Finding Description
In `core/web/router.go`, the bridge type routes are declared as: [1](#0-0) 
`GET /bridge_types` (Index) and `GET /bridge_types/:BridgeName` (Show) have no `auth.RequiresEditRole`/`auth.RequiresAdminRole` wrapper, unlike `POST`, `PATCH`, and `DELETE` on the same resource. Only the generic `authv2` group-level middleware `auth.Authenticate(...)` (session or token) applies, which accepts any valid user regardless of role.

`BridgeTypesController.Show` retrieves the bridge and serializes it with no additional privilege check: [2](#0-1) 

The presenter used, `presenters.NewBridgeResource`, includes the `OutgoingToken` field unconditionally in the JSON response (only `IncomingToken` is intentionally omitted after creation): [3](#0-2) 

This mirrors the reported bug class exactly: a controller (`IndexesApi`/`Cop1Api`/`TimeApi` in the Yamcs advisory) that omits the object/system privilege check that sibling controllers/endpoints correctly enforce, letting an unprivileged authenticated actor read or manipulate data it should not have access to. Here, Chainlink's own RBAC test matrix (`core/web/auth/auth_test.go`) explicitly documents that `GET /v2/bridge_types/MOCK` is expected to be `viewOnlyAllowed: true`: [4](#0-3) 
confirming this is the actual (not merely accidental) access policy — a `view`-role user is intentionally permitted to hit this endpoint, yet it returns a live outbound authentication secret.

### Impact Explanation
- **Confidentiality:** Any authenticated user with only `view` (the lowest role, intended for read-only dashboards) can retrieve `OutgoingToken` for any configured bridge. This token is the shared secret Chainlink sends to the External Adapter in the `X-Bridge-Response-URL`/outgoing auth flow, so its disclosure allows an unprivileged actor to impersonate the node when calling out to (or being called back by) the adapter, potentially manipulating job run responses.
- **Integrity:** Combined with knowledge of the bridge's expected response format, a low-privileged user obtaining this token could inject or replay responses that get accepted as legitimate bridge callbacks, corrupting pipeline run results.
- Scope is limited to `view`-role or higher authenticated node operators (not unauthenticated), same threat model as the referenced advisory (any authenticated, low-privileged user vs. admin).

### Likelihood Explanation
High for any deployment that provisions `view`-role accounts (e.g., dashboards, read-only auditors, monitoring integrations) alongside bridges with meaningful `OutgoingToken` values. The endpoint is a documented, first-class REST route reachable with a single unauthenticated-role-gated GET request; no additional preconditions are needed beyond having any valid session/API token.

### Recommendation
Wrap `GET /v2/bridge_types` and `GET /v2/bridge_types/:BridgeName` with the same `auth.RequiresEditRole` (or a new read-scoped privilege) that guards the mutating bridge routes, or strip `OutgoingToken` from the `BridgeResource` returned to non-privileged roles (similar to how `IncomingToken` is already conditionally omitted). At minimum, redact `OutgoingToken` for `view`/`run` roles in `presenters.NewBridgeResource`.

### Proof of Concept
```bash
# Login as a 'view'-role user (lowest privilege, e.g. dashboard account)
curl -s -c cookies.txt -X POST http://localhost:6688/sessions \
  -d '{"email":"viewer@example.com","password":"viewerpass"}' \
  -H "Content-Type: application/json"

# Fetch bridge details as the unprivileged view-role user
curl -s -b cookies.txt "http://localhost:6688/v2/bridge_types/my_bridge"
```
Expected/observed result: HTTP 200 with JSON body including `"outgoingToken": "<secret>"`, despite the requester holding only the `view` role — the same class of function-level access control gap as `IndexesApi`/`Cop1Api`/`TimeApi` in the referenced advisory, where sibling mutating endpoints enforce privilege checks but the read endpoint does not.

func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
