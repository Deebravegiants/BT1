Based on my research, the response cache in the gateway's HTTP capability handler exhibits the same root-cause pattern as CVE-2026-1965: a shared cache entry can be served to a different "authenticated" context (here, a different mTLS client certificate) than the one that produced it.

### Title
Cross-credential response reuse: mTLS-authenticated HTTP action responses cached by a key that excludes credentials - (File: core/services/gateway/handlers/capabilities/v2/response_cache.go)

### Summary
`responseCache` caches outbound HTTP action responses keyed by a hash of `(method, URL, headers, body, workflowOwner)`, explicitly excluding the request's `Mtls` client-certificate credentials from the cache key. When the gateway is asked to make an outbound mTLS request, a fresh, throwaway HTTP client is (correctly) instantiated per request to prevent connection-level credential leakage [1](#0-0) , but the *response* returned by that authenticated call is then cached and can be replayed to a subsequent request bearing entirely different `Mtls` credentials, as long as method/URL/headers/body/workflowOwner match.

### Finding Description
`makeOutgoingRequest` builds an `OutboundHTTPRequest` (which may carry per-request `Mtls` credentials) and, when `CacheSettings.MaxAgeMs > 0`, serves/stores the result via `h.responseCache.Fetch(httpCtx, req, callback, req.CacheSettings.Store)` [2](#0-1) . The cache key is `req.Hash()`, and the struct's own documentation states the hash covers "method, URL, headers, body, workflowOwner" [3](#0-2) . The accompanying unit tests exhaustively verify what is/is not included in the hash — confirming `CacheSettings` and `WorkflowID` do **not** affect the hash while `WorkflowOwner` does — but no test asserts that `Mtls` credentials affect the hash [4](#0-3) .

Meanwhile, the `send` function goes out of its way to avoid leaking mTLS-authenticated *connections* across users/requests by building a fresh client per call and disabling keep-alives at the transport layer [5](#0-4) , and this connection-level protection is verified by tests and hardened at the transport (`DisableKeepAlives`) [6](#0-5) . However, that hardening only addresses TCP/TLS connection reuse — it does not address the *response cache*, which sits above the HTTP client and reuses the *result* of one credential's authenticated fetch for a different credential's identical-looking request.

### Impact Explanation
An unprivileged workflow node driving the HTTP Action capability controls `Mtls`, `Method`, `URL`, `Headers`, `Body`, and `CacheSettings` on `OutboundHTTPRequest` (all attacker/user-controlled fields from an untrusted node, as the code comment on `send` itself notes: "all fields set on the request come from untrusted nodes") [7](#0-6) . If two logically distinct callers under the same `workflowOwner` issue requests with identical method/URL/headers/body but different `Mtls` client certificates, the second caller can receive a response that was in fact fetched using the first caller's private key/certificate — a direct analog to the CVE's "request impersonation"/cross-user response confusion, and it can leak data intended for a different mTLS identity.

### Likelihood Explanation
Likelihood is moderate: it requires `CacheSettings.MaxAgeMs > 0` and `Store: true` to be set (both attacker-controlled), a shared `workflowOwner`, and colliding method/URL/headers/body across two different `Mtls` credentials — a scenario plausible in multi-tenant/organization workflows sharing an owner identity but using distinct per-workflow client certificates against the same endpoint.

### Recommendation
Include a fingerprint of the `Mtls` credentials (e.g., a hash of the certificate) in the response-cache key so that responses fetched under distinct client-certificate identities are never returned across a certificate boundary. Since `Hash()` is defined on the `gateway.OutboundHTTPRequest` type in the external `chainlink-common` dependency, I could not directly inspect its full source to conclusively confirm `Mtls` is excluded — this should be verified in that package, but the in-repo struct comment and the test suite's explicit "not affecting the hash" assertions strongly indicate it is excluded today.

### Proof of Concept
1. Two capability requests share `workflowOwner="org-1"`, `Method="GET"`, `URL="https://api.example.com/data"`, no differentiating headers/body, and `CacheSettings={MaxAgeMs: 60000, Store: true}`.
2. Request A includes `Mtls{Certificate: certA, PrivateKey: keyA}`; the gateway performs the request with certA's identity and caches the (2xx) response under `req.Hash()` [8](#0-7) .
3. Request B (different tenant/workflow using certB) arrives with identical method/URL/headers/body/workflowOwner but `Mtls{Certificate: certB, PrivateKey: keyB}`.
4. Because `req.Hash()` ignores `Mtls`, `Fetch` returns the cached entry produced by certA's authenticated call to Request B, without ever making a request authenticated as certB.

func (h *gatewayHandler) send(ctx context.Context, httpReq network.HTTPRequest, req gateway_common.OutboundHTTPRequest) (*network.HTTPResponse, error) {
	if req.Mtls == nil {
		return h.httpClient.Send(ctx, httpReq)
	}

	if h.httpClientFactory == nil {
		return nil, errors.New("nil http client factory, cannot make mtls request")
	}

	// Instantiate a throwaway HTTP client with the provided Mtls client certificate provided.
	// We do this to ensure that we don't accidentally leak auth'd connections to other users.
	// Note: this isn't a DOS vector because
	// a) we have a global rate limit above which limits abuse
	// b) we apply rate limits limiting the ability of sending nodes to spam requests
	// c) we apply per-owner rate limits in the action capability in the
	// workflow node limiting the ability of users to abuse this flow by spamming Mtls requests.
	// The client enforces the mtls concurrency limit internally (on the request's
	// capped-timeout context) before delegating to the underlying transport.
	client, err := h.httpClientFactory(network.HTTPClientConfig{
		Mtls: &gateway_common.MtlsAuth{
			PrivateKey:  req.Mtls.PrivateKey,
			Certificate: req.Mtls.Certificate,
		},
		ConcurrencyLimiter: h.mtlsConcurrencyLimiter,
	})
	if err != nil {
		return nil, fmt.Errorf("failed to instantiate http client for mtls request: %w", err)
	}

	h.lggr.Debugw("handling outgoing message", "requestID", requestID, "nodeAddr", nodeAddr)
	var req gateway_common.OutboundHTTPRequest
	err := json.Unmarshal(*resp.Result, &req)
	if err != nil {
		return fmt.Errorf("failed to unmarshal HTTP request from node %s: %w", nodeAddr, err)
	}
	timeout := time.Duration(req.TimeoutMs) * time.Millisecond
	httpReq := network.HTTPRequest{
		Method:           req.Method,
		URL:              req.URL,
		Headers:          req.Headers, //nolint:staticcheck // forward deprecated Headers for backward compatibility; request uses MultiHeaders when set
		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}

	sendResponseTimeout := time.Duration(defaultSendResponseTimeoutMs) * time.Millisecond

	// send response to node async
	h.wg.Go(func() {
		// not cancelled when parent is cancelled to ensure the goroutine can finish
		baseCtx := context.WithoutCancel(ctx)
		httpCtx, httpCancel := context.WithTimeout(baseCtx, timeout)
		defer httpCancel()
		l := logger.With(h.lggr, "requestID", requestID, "method", req.Method, "timeout", req.TimeoutMs)

			if req.CacheSettings.Store {

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	// Slow path: singleflight deduplicates concurrent fetches per key.
	// Cache check + store happen inside the flight so the key isn't released
	// until the result is cached, closing the race window between singleflight
	// completion and cache write.
	result, _, _ := rc.flight.Do(cacheKey, func() (any, error) {
		// Re-check cache: a previous flight may have just stored the result.
		rc.cacheMu.RLock()
		cachedResp, exists := rc.cache[cacheKey]
		rc.cacheMu.RUnlock()
		if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
			rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
			return cachedResp.response, nil
		}

		response := fetchFn()

		if storeOnFetch && isCacheableStatusCode(response.StatusCode) {
			rc.cacheMu.Lock()
			rc.cache[cacheKey] = &cachedResponse{
				response: response,
				storedAt: time.Now(),
			}
			rc.cacheMu.Unlock()
		}

		return response, nil
	})

	return result.(gateway.OutboundHTTPResponse)
