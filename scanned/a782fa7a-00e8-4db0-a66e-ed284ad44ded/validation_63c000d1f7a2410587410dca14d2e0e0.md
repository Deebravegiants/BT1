Notably, `MessageBody.Payload` (which carries `webapicap.TriggerRequestPayload`, including the `Topics` array) has no size or element-count limit enforced in `Message.Validate()` [1](#0-0) . Only `MessageID`, `Method`, and `DonID` have length caps; the raw `Payload` is unbounded. That unbounded, externally-controlled `Topics` array is what feeds the nested-loop bug below.

### Title
Unbounded nested loop over externally supplied `Topics` array causes CPU/DoS in web API trigger handler - (File: `core/capabilities/webapi/trigger/trigger.go`)

### Summary
`triggerConnectorHandler.processTrigger` iterates every registered workflow trigger against every entry of the attacker-controlled `payload.Topics` slice in a nested `for` loop, with no upper bound on the number of topics a single gateway message may contain [2](#0-1) . This is the same bug class as the reported `D3Maker.setTokensPrice` issue: an O(n×m) loop driven by unbounded, caller-supplied array length, risking resource exhaustion / denial of service.

### Finding Description
`HandleGatewayMessage` decodes the JSON payload from an incoming gateway message and calls `processTrigger` directly, without any check on `len(payload.Topics)`: [3](#0-2) 

Inside `processTrigger`, only an empty-topics check exists (`len(topics) == 0`); there is no upper bound: [4](#0-3) 

The message envelope itself (`api.Message` / `MessageBody.Payload`) enforces length limits only on `MessageID`, `Method`, and `DonID` — the `Payload` field (which contains the JSON-encoded `Topics` array) is unbounded [5](#0-4) . Any node forwarding an external client's message (or, if reachable via the gateway's public HTTP ingress, an unprivileged client itself) can therefore submit a payload with an arbitrarily large `Topics` array. Since the outer loop ranges over every `registeredWorkflows` entry (`triggers`) and the inner loop ranges over every topic, the total work is `O(len(triggers) * len(topics))`, and it also holds `h.mu.Lock()` momentarily to snapshot triggers, and per-trigger sends are gated on channel writes — but the topic-matching work itself scales linearly with an attacker-controlled `topics` length with no cap, matching the "Gas Limitations" class of unbounded-array-iteration DoS from the source report.

### Impact Explanation
A crafted message with a very large `Topics` array (e.g., tens of thousands of strings) forces the node to perform proportionally more map lookups (`trigger.allowedTopics[topic]`) per registered workflow trigger on every gateway message received for this handler. With multiple registered triggers, this becomes a CPU amplification vector that can degrade the node's message-processing throughput or that of `HandleGatewayMessage` calls generally (since this runs synchronously in the gateway connector's read loop, per `readLoop` in `core/services/gateway/connector/connector.go`, blocking that message's processing) — a realistic availability/DoS concern for an internet-facing gateway path, consistent with the Medium severity of the source finding.

### Likelihood Explanation
Reachability depends on whether an unprivileged (non-DON-member) actor can submit `web_api_trigger` messages that reach this handler. This handler is invoked as `HandleGatewayMessage` on the connector side (the workflow node — not the gateway's own untrusted public endpoint), so the practical trust boundary is: gateway node → connector → node. Since the Rules exclude "malicious-node/malicious-peer" analogs and require an unprivileged-client-reachable path, and I could not fully confirm within available context whether the public-facing gateway HTTP ingress performs its own topic-count bound before relaying to this handler (only message ID/method/don_id length caps were found; payload size limits on the gateway's HTTP listener were referenced in `core/services/gateway/network/httpserver.go` but not inspected in depth due to remaining iteration budget), likelihood is uncertain — this is a legitimate gap but its exploitability from a fully unprivileged actor (versus a compromised/malicious gateway/DON node) is not conclusively established here.

### Recommendation
Enforce an explicit upper bound on `payload.Topics` length (and ideally on total payload size) in `HandleGatewayMessage`/`processTrigger` before entering the nested loop, similar to the `MaxBatchSize` checks used elsewhere in the vault request validator (`core/capabilities/vault/validator.go`), and confirm the gateway's HTTP ingress (`core/services/gateway/network/httpserver.go`) enforces a hard body-size/array-size limit on inbound trigger payloads from unauthenticated clients.

### Proof of Concept
1. Register at least one web-api-trigger workflow via `RegisterTrigger` with any `allowedTopics`.
2. Construct a `webapicap.TriggerRequestPayload` whose `Topics` field contains N (e.g., 1,000,000) distinct strings, none of which need to match `allowedTopics`.
3. Sign and submit this payload as the body of a `jsonrpc.Request` with `Method: ghcapabilities.MethodWebAPITrigger`, invoking `HandleGatewayMessage`.
4. Observe that `processTrigger`'s nested loop performs `len(triggers) * N` map lookups per message with no rejection, and repeat submission to degrade node responsiveness — mirroring the reported "Gas Limitations" unbounded-loop-over-array DoS pattern, now realized as unbounded CPU work per message instead of unbounded gas.

func (h *triggerConnectorHandler) HandleGatewayMessage(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) error {
	msg, err := hc.ValidatedMessageFromReq(req)
	if err != nil {
		h.lggr.Errorw("error validating message from request", "err", err, "request", req)
		return nil
	}
	body := &msg.Body
	sender := ethCommon.HexToAddress(body.Sender)
	var payload webapicap.TriggerRequestPayload
	err = json.Unmarshal(body.Payload, &payload)
	if err != nil {
		h.lggr.Errorw("error decoding payload", "err", err)
		err = h.sendResponse(ctx, gatewayID, body, ghcapabilities.TriggerResponsePayload{Status: "ERROR", ErrorMessage: fmt.Errorf("error %s decoding payload", err.Error()).Error()})
		if err != nil {
			h.lggr.Errorw("error sending response", "err", err)
		}
		return nil
	}

	switch body.Method {
	case ghcapabilities.MethodWebAPITrigger:
		resp := h.processTrigger(ctx, gatewayID, body, sender, payload)

		}
		err = h.sendResponse(ctx, gatewayID, body, response)
		if err != nil {
