### Title
Debug-level request logging in the Gin HTTP router performs only shallow (top-level) redaction, exposing credentials sent via the GraphQL `/query` endpoint - (File: `core/web/router.go`)

### Summary
Chainlink's HTTP router logs full request bodies at Debug level for every request, including the single GraphQL mutation endpoint `/query` that handles almost all sensitive node-management actions (creating API tokens, importing/exporting keys, creating bridges, external initiators, feeds managers, etc.). The redaction routine that is supposed to strip sensitive fields before logging only inspects the top-level keys of the JSON body, not nested objects — so any sensitive field nested one level deep (as all GraphQL variables are, since the body shape is always `{"query": ..., "variables": {...}}`) is logged in cleartext. This is the same bug class as GHSA-xfj7-qf8w-2gcr (Rancher audit log leaking secrets due to insufficiently strict redaction), applied to Chainlink's request-debug-logging path rather than to a dedicated audit logger.

### Finding Description
`NewRouter` installs `loggerFunc(app.GetLogger())` as a global Gin middleware applied to *every* route, including the GraphQL endpoint: [1](#0-0) 

`loggerFunc` reads the full request body and logs it at Debug level via `readBody`: [2](#0-1) 

`readBody` calls `readSanitizedJSON`, which unmarshals the body into `map[string]any` and redacts only keys that appear at the top level of that map: [3](#0-2) 

The blacklist itself is also narrow (only password-like field names): [4](#0-3) 

Nearly all Chainlink node-management mutations (`CreateAPIToken`, key import/export mutations, bridge/external-initiator/feeds-manager mutations, etc.) are dispatched through a single REST-like endpoint: [5](#0-4) 

Because GraphQL requests are always shaped as a top-level object with `query`/`operationName`/`variables` keys, any sensitive scalar submitted by the client (e.g., a password confirming an API-token creation, a key JSON/passphrase for import, or other secret-bearing arguments used across the resolvers in `core/web/resolver/mutation.go`) lives *inside* the `variables` object, not at the top level. The shallow, single-level `isBlacklisted` check in `readSanitizedJSON` never inspects `variables`, so these values pass through unredacted into the Debug log output. This is a direct structural analog to the Rancher issue: a feature intended to filter sensitive data from logs (opt-in, gated by `Log.Level = 'debug'` here vs. `AUDIT_LEVEL >= 1` in Rancher) fails to do so because the filter only checks a shallow/incomplete set of fields, and the JSON transport shape (nested `variables`) systematically evades the filter.

By contrast, the legacy REST session endpoint (`/sessions`) posts `password` as a top-level field, so it *is* caught by the blacklist: [6](#0-5) 
— which confirms the redaction was designed with only flat JSON bodies in mind and was never updated to handle the nested GraphQL variable shape that the vast majority of sensitive mutations now use.

### Impact Explanation
When node operators enable `Log.Level = 'debug'` (a supported, documented configuration, not a hidden/undocumented state), every GraphQL request body sent by any authenticated (or, for endpoints reachable pre-auth, unauthenticated) API client is written to the node's log output in near-plaintext, with only top-level password-like fields stripped. Depending on log shipping configuration (local file, syslog, or forwarded log aggregation), this can leak passwords, key-import passphrases, or other sensitive mutation arguments to anyone with read access to the logs — mirroring exactly the confidentiality impact described in CVE-2023-22649 (CWE-532: Insertion of Sensitive Information into Log File).

### Likelihood Explanation
Requires the operator to set `Log.Level = 'debug'` (an opt-in condition analogous to Rancher's `AUDIT_LEVEL >= 1`), but once that condition holds, the leak is automatic and deterministic for every GraphQL mutation carrying sensitive arguments — no additional attacker action or race condition is needed. Any authenticated GraphQL client invoking a sensitive mutation (or an unauthenticated client hitting a pre-auth mutation, if any exist) will have their arguments logged in the clear.

### Recommendation
Make `readSanitizedJSON`/`redact` recursively redact blacklisted field names at any nesting depth (not just top-level), explicitly parse and redact known-sensitive keys inside the GraphQL `variables` object, and/or exclude the `/query` GraphQL endpoint's request body from raw debug logging entirely, replacing it with a redacted summary (e.g., only log `operationName`).

### Proof of Concept
1. Set `Log.Level = 'debug'` in the node's config.
2. As an authenticated user, send a GraphQL mutation to `POST /query` that carries a sensitive scalar in `variables`, e.g. `CreateAPIToken` (`{"query":"mutation($password:String!){ createAPIToken(input:{password:$password}) { token } }","variables":{"password":"SuperSecretPass123"}}`) — resolver at: [7](#0-6) 
3. Inspect the node's debug log output for the request; the `body` field logged by `loggerFunc`/`readBody` will contain the full `variables` object including `"password":"SuperSecretPass123"` in cleartext, because `isBlacklisted` only ever inspects the top-level keys `query`, `operationName`, and `variables` — none of which match the blacklist.

**Note on completeness:** I was not able to fully enumerate every sensitive field accepted across all resolvers in `core/web/resolver/mutation.go` (the file is large) to build an exhaustive list of impacted mutations; the analysis above demonstrates the root-cause mechanism and one concrete instance (`CreateAPIToken`) but a full audit of all mutation arguments would require further review.

func loggerFunc(lggr logger.Logger) gin.HandlerFunc {
	return func(c *gin.Context) {
		buf, err := io.ReadAll(c.Request.Body)
		if err != nil {
			lggr.Error("Web request log error: ", err.Error())
			// Implicitly relies on limits.RequestSizeLimiter
			// overriding of c.Request.Body to abort gin's Context
			// inside io.ReadAll.
			// Functions as we would like, but horrible from an architecture
			// and design pattern perspective.
			if !c.IsAborted() {
				c.AbortWithStatus(http.StatusBadRequest)
			}
			return
		}
		rdr := bytes.NewBuffer(buf)
		c.Request.Body = io.NopCloser(bytes.NewBuffer(buf))

		start := time.Now()
		c.Next()
		end := time.Now()

		lggr.Debugw(fmt.Sprintf("%s %s", c.Request.Method, c.Request.URL.Path),
			"method", c.Request.Method,
			"status", c.Writer.Status(),
			"path", c.Request.URL.Path,
			"ginPath", c.FullPath(),
			"query", redact(c.Request.URL.Query()),
			"body", readBody(rdr, lggr),
			"clientIP", c.ClientIP(),
			"errors", c.Errors.String(),
			"servedAt", end.Format("2006-01-02 15:04:05"),
			"latency", fmt.Sprintf("%v", end.Sub(start)),
		)
	}

func readSanitizedJSON(buf *bytes.Buffer) (string, error) {
	var dst map[string]any
	err := json.Unmarshal(buf.Bytes(), &dst)
	if err != nil {
		return "", err
	}

	cleaned := map[string]any{}
	for k, v := range dst {
		if isBlacklisted(k) {
			cleaned[k] = "*REDACTED*"
			continue
		}
		cleaned[k] = v
	}

	b, err := json.Marshal(cleaned)
	if err != nil {
		return "", err
	}
	return string(b), err
}

var blacklist = map[string]struct{}{
	"password":             {},
	"newpassword":          {},
	"oldpassword":          {},
	"current_password":     {},
	"new_account_password": {},
}

func isBlacklisted(k string) bool {
	lk := strings.ToLower(k)
	if _, ok := blacklist[lk]; ok || strings.Contains(lk, "password") {
		return true
	}
	return false
}
