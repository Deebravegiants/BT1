### Title
User enumeration via distinct error messages on unauthenticated `/sessions` login endpoint - (File: core/sessions/localauth/orm.go)

### Summary
The Chainlink node's local session login flow returns distinct, attacker-observable error messages depending on whether the submitted email exists in the `users` table or the password was simply wrong. This is the same "Observable Response Discrepancy" bug class (CWE-204) as the reported Shopware Store API issue: an unauthenticated login endpoint leaks account existence through differentiated error text instead of a unified generic failure.

### Finding Description
`CreateSession` in `orm` first looks up the user by email, then performs a constant-time email comparison and a password hash check, returning two different Go errors: [1](#0-0) 

- If the email does not match a record, it returns `pkgerrors.New("Invalid email")`.
- If the email matches but the password is wrong, it returns `pkgerrors.New("Invalid password")`.

Both errors are returned unmodified by `SessionsController.Create`, which passes them directly to `jsonAPIError`: [2](#0-1) 

`jsonAPIError` serializes `err.Error()` verbatim into the JSON response body: [3](#0-2) 

The `/sessions` `POST` route is registered without any authentication middleware (it is the login route itself), reachable by any unauthenticated client: [4](#0-3) 

The end-to-end test confirms both cases return an error but does not verify the message content is unified — an attacker distinguishes "incorrect email" (`Invalid email`) from "incorrect pwd" (`Invalid password`) by reading the response body text: [5](#0-4) 

The same discrepancy pattern is duplicated in the LDAP and OIDC local-fallback authenticators, which return `"invalid email"` vs `"invalid password"` as distinct errors as well: [6](#0-5) [7](#0-6) 

This mirrors exactly the reported bug class: Shopware's Store API propagated `CustomerNotFoundException` vs `BadCredentialsException` distinctly to unauthenticated clients, while Shopware's storefront controller unified them. Chainlink's node API has no such unification anywhere in the local/LDAP/OIDC login code paths.

### Impact Explanation
An unauthenticated attacker probing the `/sessions` endpoint (or LDAP/OIDC local fallback logins) can determine whether a given email address corresponds to a registered node API user by inspecting the distinct `"Invalid email"` vs `"Invalid password"` message in the JSON response. Chainlink node accounts are typically few in number (node operator admin/edit/view users) but confirming which emails are valid operator accounts materially aids targeted credential-stuffing or phishing against a specific node operator's dashboard access, and reveals information about the node's user base that should not be exposed pre-authentication.

### Likelihood Explanation
The `/sessions` endpoint is public and unauthenticated by design (it is the login endpoint), requiring no privilege to reach. Exploitation is a single HTTP request with an arbitrary email/password payload, and the differentiating error text is returned directly in the JSON response body, requiring no timing side channel. Only the number of node-authenticator users limits the interesting attack surface, but this doesn't reduce the ease of exploitation.

### Recommendation
Unify the error returned to the HTTP layer for both "email not found" and "password incorrect" cases into a single generic error at the boundary where it is serialized to the client (`SessionsController.Create` / `CreateSession`), e.g., return a fixed `sessions.ErrInvalidCredentials`-style sentinel and always map it to a fixed message such as `"invalid email or password"`, regardless of which check failed. Apply the same fix to `localLoginFallback` in both `ldapauth` and `oidcauth`. Continue to log/audit the differentiated case (`AuthLoginFailedEmail` vs `AuthLoginFailedPassword`) server-side for observability, but do not let the distinct message reach the client response body.

```
Content-Type: application/json
```

```json

```

```
{"email":"knownadmin@node.local","password":"wrongpass"}
```
Response body (email registered, wrong password):
```json

```

```go
func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}
```

```go
func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
```

```go
// localLoginFallback tests the credentials provided against the 'local' authentication method
// This covers the case of local CLI API calls requiring local login separate from the LDAP server
func (l *ldapAuthenticator) localLoginFallback(ctx context.Context, sr sessions.SessionRequest) (sessions.User, error) {
	var user sessions.User
	sql := "SELECT * FROM users WHERE lower(email) = lower($1)"
	err := l.ds.GetContext(ctx, &user, sql, sr.Email)
	if err != nil {
		return user, err
	}
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		l.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return user, errors.New("invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		l.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return user, errors.New("invalid password")
	}

	return user, nil
}
```
