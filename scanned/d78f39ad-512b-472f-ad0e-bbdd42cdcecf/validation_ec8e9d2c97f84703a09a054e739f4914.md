## Title
CORS Origin Allowlist Bypass via Suffix-Only Wildcard Host Matching - (File: `core/services/gateway/network/httpserver.go`)

## Summary
The gateway HTTP server's CORS origin allowlist check uses a separator-unaware suffix comparison (`strings.HasSuffix`) to validate wildcard-configured allowed origins. Just as the OpenList advisory shows `strings.HasPrefix` matching `/base2/...` against a `/base` allowlist entry, this code matches an attacker-registered domain like `evilremix.com` against an allowed wildcard entry `*.remix.com`, because it strips the `*.` and checks only whether the origin host ends with the literal string `remix.com` — without requiring a `.` boundary.

## Finding Description
In `isAllowedOrigin`, wildcard entries are handled as: [1](#0-0) 

`allowedHost` is derived by stripping the leading `*.` (e.g. `*.remix.com` → `remix.com`), and the match is `strings.HasSuffix(originHost, allowedHost)`. This does not verify that the character preceding the match is a domain separator (`.`). Consequently, an origin host such as `evilremix.com` or `attacker-remix.com` satisfies `strings.HasSuffix("evilremix.com", "remix.com") == true`, passing the allowlist check that was intended to permit only `*.remix.com` subdomains.

This is the exact bug class from the report: a boundary-unaware string containment check (`HasPrefix`/`HasSuffix`) substituting for a proper separator-aware match, allowing an attacker-controlled value to pass validation against a scope it does not actually belong to.

## Impact Explanation
When the request origin passes this check, the gateway server reflects it back with credentialed CORS headers: [2](#0-1) 

An attacker who registers a domain merely sharing a suffix with an allowed wildcard entry (e.g. `notreallyremix.com` when `*.remix.com` is allowlisted) can have a browser send credentialed cross-origin requests to the gateway's `HTTPRequestHandler.ProcessRequest` endpoint and read the JSON-RPC response cross-origin, bypassing the operator's intended origin restriction on the internet-facing gateway. This is an authorization/allowlist bypass allowing unauthorized cross-origin access to gateway responses (message envelopes / handler results), from an unprivileged external actor.

## Likelihood Explanation
Exploitability only requires that the deployment enables CORS (`CORSEnabled: true`) with at least one wildcard entry (e.g. `*.example.com`) in `CORSAllowedOrigins`, and that the attacker can register or control a domain sharing that literal suffix (which is easy and common, e.g. registering `evilexample.com`). No credentials or special permissions are needed by the attacker to trigger the check — it fires on any incoming request's `Origin` header.

## Recommendation
Replace the suffix check with a separator-aware subdomain match, e.g.:
```go
if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
    return true
}
```
This mirrors the report's remediation of using `target == base || strings.HasPrefix(target, base+"/")` but adapted for suffix/subdomain matching (`originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost)`).

## Proof of Concept
1. Configure the gateway with `CORSEnabled: true` and `CORSAllowedOrigins: ["https://*.remix.com"]`.
2. From a browser hosted at `https://evilremix.com`, send a fetch request with credentials to the gateway's HTTP endpoint, setting `Origin: https://evilremix.com`.
3. `splitURL` extracts `originHost = "evilremix.com"`; `isAllowedOrigin` strips the wildcard entry to `allowedHost = "remix.com"` and evaluates `strings.HasSuffix("evilremix.com", "remix.com")`, which is `true`.
4. The server responds with `Access-Control-Allow-Origin: https://evilremix.com`, allowing the malicious page's script to read the gateway's JSON-RPC response cross-origin.
