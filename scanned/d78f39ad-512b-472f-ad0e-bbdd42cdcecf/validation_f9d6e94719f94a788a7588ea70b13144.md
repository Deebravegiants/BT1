### Title
Unauthenticated job-run resume endpoint allows anyone to complete/hijack another user's pending pipeline task run - (File: core/web/pipeline_runs_controller.go, core/web/router.go)

### Summary
The analog of the "stop DCA task" bug — a state-mutating operation reachable by ID alone, with no ownership/authentication check tying the caller to the resource — exists in the Chainlink node's `PATCH /v2/resume/:runID` HTTP endpoint. It is registered without any authentication middleware and forwards attacker-controlled data straight into `ResumeJobV2`, which resumes a suspended pipeline run by task-run UUID.

### Finding Description
The route is explicitly mounted in the unauthenticated router group: [1](#0-0) 

`PipelineRunsController.Resume` parses only a `runID` UUID from the URL and a JSON body, with no session, API-token, or external-initiator authentication check (unlike `Create`, which is gated behind `auth.RequiresRunRole`): [2](#0-1) 

This directly parallels `NestedDca.stopDca`: a sensitive state transition (resuming/finalizing a pending pipeline run with attacker-supplied result data) is keyed off of a bare ID (`taskID`) with no validation that the caller has any relationship to the job/run owner. Anyone who can reach the node's HTTP port and knows or guesses a task-run UUID can call this endpoint to push a `pipeline.ResumeRequest` result into the ORM via `App.ResumeJobV2`, which internally calls `runner.ResumeRun` → `orm.UpdateTaskRunResult`: [3](#0-2) 

Task-run UUIDs are used for pending/async tasks (e.g., bridge adapter callbacks) that are meant to be completed only by the intended external adapter that was given that UUID when the task was dispatched. There is no secondary secret, HMAC, or ownership check comparing the caller to the task's expected completer — only knowledge of the UUID is required.

### Impact Explanation
If an attacker obtains or brute-forces/guesses a pending run's UUID (e.g., via log leakage, error messages, or a race with a legitimate but slow external adapter), they can:
- Inject arbitrary result/error data into another job's suspended pipeline run, corrupting downstream pipeline stages (e.g., price feeds, VRF fulfillment logic, or any task chain reading `$(task.result)`).
- Force premature "completion" of a run that should have received a legitimate external adapter response, similar to how stopping the Alice's DCA task in the report caused unintended financial exposure — here, injecting wrong data into an oracle/automation pipeline can cause bad on-chain reports or fund-affecting transactions to be built and submitted.
- Because the endpoint is fully unauthenticated (not even external-initiator auth), this is reachable from any unprivileged network client that can hit the node's API port, unlike other state-mutating endpoints in the same router file, all of which require at least `RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole`.

### Likelihood Explanation
Likelihood depends on whether task-run UUIDs are otherwise treated as secrets (UUIDv4 is not guessable, but they may be logged, returned in API responses, or observable in outbound bridge HTTP request bodies sent to third-party adapters, any of which would leak them to an unprivileged party). The endpoint itself imposes zero access control by design (`unauthedv2` group), so likelihood is entirely a function of UUID confidentiality, which I could not fully verify from the indexed code — I did not find the code path that generates/dispatches these UUIDs to external bridge adapters to assess how well they are protected in transit/logs.

### Recommendation
- Require that resuming a run present some proof of authorization tied to the specific run (e.g., a per-run bridge-specific shared secret, HMAC signature, or the external-initiator/bridge credentials used to originally dispatch the async task), not just the UUID.
- Alternatively, bind the resume operation to the specific bridge/adapter that was invoked for that task, validating the caller identity against the task's `bridge_name`/expected caller before applying `UpdateTaskRunResult`.
- Audit-log and rate-limit this endpoint given it is intentionally unauthenticated.
- Document why this endpoint must remain unauthenticated (external adapters don't hold node sessions) and add compensating controls (e.g., mTLS, IP allowlisting, or bridge-specific secrets) as long as it stays open.

### Proof of Concept
Conceptually: any HTTP client that can reach the node can do
```
curl -X PATCH https://node:6688/v2/resume/<guessed-or-leaked-task-run-uuid> \
     -H "Content-Type: application/json" \
     -d '{"error": null, "value": "<attacker-controlled-value>"}'
```
This hits `PipelineRunsController.Resume` [4](#0-3)  with no auth check, and — if the UUID matches a pending task run belonging to any job on the node, regardless of who created it — completes that run with attacker-supplied data via `ResumeJobV2` → `runner.ResumeRun` [5](#0-4) .

I was unable to fully trace, within the indexed portion of the codebase, exactly how/where these run UUIDs are generated and transmitted to external adapters (`task.bridge.go` contents and `ResumeJobV2`/`UpdateTaskRunResult` implementations were not retrievable in this session), so I cannot confirm how well-protected the UUID secrecy assumption is in practice. A Devin session with full repo access would be needed to verify UUID generation/exposure paths and confirm exploitability end-to-end.

```go
// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
```

```go
func (r *runner) ResumeRun(ctx context.Context, taskID uuid.UUID, value any, err error) error {
	run, start, err := r.orm.UpdateTaskRunResult(ctx, taskID, Result{
		Value: value,
		Error: err,
	})
	if err != nil {
		return fmt.Errorf("failed to update task run result: %w", err)
	}

	// TODO: Should probably replace this with a listener to update events
	// which allows to pass in a transactionalised database to this function
	if start {
		// start the runner again
		go func() {
			ctx, cancel := r.chStop.NewCtx()
			defer cancel()
			if _, err := r.Run(ctx, &run, false, nil); err != nil {
				r.lggr.Errorw("Resume run failure", "err", err)
			}
			r.lggr.Debug("Resume run success")
		}()
	}
	return nil
}
```
