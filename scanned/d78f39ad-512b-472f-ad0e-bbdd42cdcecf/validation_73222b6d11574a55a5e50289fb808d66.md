### Title
Unauthenticated Gateway `HandleLegacyUserMessage` Path Forwards Unvetted Requests to All DON Nodes Without Allowlist Enforcement - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The Gateway's internet-facing HTTP server accepts unauthenticated JSON-RPC "legacy" requests and routes them to the capabilities `handler.HandleLegacyUserMessage`, which contains a known-incomplete authorization path: the code explicitly notes `// TODO: apply allowlist and rate-limiting here` and only checks payload shape, timestamp freshness, and method name before broadcasting the request to every node in the DON.

### Finding Description
`httpServer.handleRequest` reads the raw request body from any client reaching the Gateway's user port, optionally extracts a bearer JWT, and passes both to `gateway.ProcessRequest` without any authentication gate at the HTTP layer itself [4](#0-3) . `ProcessRequest` classifies the request as "legacy" purely based on the presence of a `DonID` field in the decoded message body and, for legacy requests, only calls `msg.Validate()` (a structural/signature check, not an authorization/allowlist check) before dispatching to the handler's `HandleLegacyUserMessage` [2](#0-1) .

Inside `capabilities/handler.go`, `HandleLegacyUserMessage` performs payload parsing, a `Timestamp` staleness check, and a method-name check for `MethodWebAPITrigger`, but the comment directly preceding those checks states `// TODO: apply allowlist and rate-limiting here`, confirming that no per-sender allowlist or rate limit is enforced on this path [5](#0-4) . Once these superficial checks pass, the handler stores a callback keyed by `MessageID` and forwards the (attacker-controlled) request verbatim to every member node in the DON via `don.SendToNode` [6](#0-5) . This contrasts with the newer HTTP handler v2 path, which documents JWT-based authentication and per-workflow rate limiting as part of its design [7](#0-6) , and with the vault/handler.go gateway handler, which enforces an `Authorizer.AuthorizeRequest` allowlist check before processing (as seen in `gw_handler_test.go`) [8](#0-7)  — showing the legacy capabilities handler is an outlier lacking the authorization layer present elsewhere in the same Gateway subsystem.

### Impact Explanation
Any unauthenticated internet client that can reach the Gateway's user-facing HTTP port can submit a `web_api_trigger` legacy request that is broadcast to every node in the DON, without being checked against any sender/workflow allowlist. This allows an unprivileged, external actor to trigger workflow execution paths on all DON nodes at will (subject only to timestamp freshness and payload well-formedness), which can lead to unauthorized job/workflow runs, resource exhaustion of DON nodes, and potential downstream side effects depending on what the triggered workflow does with attacker-supplied payload data.

### Likelihood Explanation
The Gateway's user HTTP endpoint is explicitly designed to be internet-facing (it is the ingress point for external clients per the interface `gw_net.HTTPRequestHandler` and lacks any authentication middleware at the transport layer). Triggering the vulnerable path requires only crafting a validly-signed/structured legacy JSON message with a `DonID` and `MethodWebAPITrigger`, which is well documented in the codebase's own tests (`triggerRequest` helper in `handler_test.go`). The missing-allowlist condition is self-documented via the `TODO` comment, indicating it is a known, currently-unaddressed gap rather than a speculative one.

### Recommendation
Implement the allowlist/rate-limiting check referenced by the `TODO` comment in `HandleLegacyUserMessage` before forwarding to `don.SendToNode`, mirroring the `Authorizer.AuthorizeRequest` pattern used in the vault gateway handler, and/or migrate all legacy trigger traffic to the v2 HTTP handler path which already implements JWT-based authentication and per-workflow rate limiting.

### Proof of Concept
1. Craft a legacy JSON-RPC message with `DonID` set to a valid DON ID served by the Gateway, `Method` set to `web_api_trigger`, a fresh `Timestamp`, and a valid signature satisfying `msg.Validate()`.
2. POST the raw message to the Gateway's user-facing HTTP endpoint (`config.Path`) with no `Authorization` header.
3. Observe that `gateway.ProcessRequest` routes the message to `HandleLegacyUserMessage`, which — absent any allowlist check — forwards the trigger request to every node listed in `donConfig.Members`, as shown by the loop in `core/services/gateway/handlers/capabilities/handler.go:417-419` [9](#0-8) .
