This is a genuine TOCTOU race in JWT replay protection.

### Title
JWT replay guard has a check-then-act race allowing a single JWT to be reused concurrently - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` checks JWT replay status and records usage as two separate, independently-locked operations rather than a single atomic check-and-set, unlike the properly-fixed `RequestReplayGuard.CheckAndRecord` pattern used elsewhere in the codebase (e.g. `core/capabilities/vault/request_replay_guard.go`). This mirrors the NEAR nearcore bug class: "check under lock" was not enforced atomically with the state mutation, opening a race window where the same JWT can be processed twice.

### Finding Description
`Authorize` calls `h.jwtCache.isReplay(claims.ID)` (which takes `cache.mu.RLock()`, checks, and releases the lock) and, only after several unrelated checks (workflow ID lookup, signer authorization), calls `h.jwtCache.recordUsage(claims.ID)` (a separate `Lock()`/`Unlock()`). [1](#0-0) 

The underlying cache primitives are correctly locked individually: [2](#0-1) 

But because `isReplay` and `recordUsage` are not combined under one critical section (unlike the `vault.RequestReplayGuard.CheckAndRecord`, which explicitly holds a single mutex across the "check exists" and "record" steps to close this exact race — see `core/capabilities/vault/request_replay_guard.go:35-47`), two concurrent `Authorize` calls presenting the identical JWT (same `jti`) can both pass the `isReplay` check before either calls `recordUsage`, exactly analogous to the nearcore issue where `processed_witnesses` was checked outside the lock protecting the insert. This is a classic TOCTOU: the check and the mutation are not atomic with respect to each other. [3](#0-2) 

### Impact Explanation
`Authorize` is invoked from the internet-facing gateway/HTTP-trigger path to authenticate a client-signed JWT before granting workflow metadata access; the JWT anti-replay mechanism exists specifically to prevent an unprivileged client (or an observer who has captured a token) from reusing the exact same signed JWT more than once. If two authorization attempts using the same `jti` race, both can succeed, defeating the single-use guarantee of the JWT and allowing request impersonation/replay to be accepted twice instead of rejected. This is a genuine authentication-bypass-of-replay-protection issue reachable from an unprivileged client sending concurrent duplicate requests.

### Likelihood Explanation
Triggering the race requires an attacker (or a legitimate client with a buggy retry path) to send two requests bearing the identical JWT at nearly the same time — a low-latency, easily reproducible condition for a network client, comparable to the "multiple parts delivered by multiple nodes at very low latencies" condition described in the nearcore report. No special privilege is needed; any external caller who can present a valid signed JWT with a given `jti` and issue it twice concurrently can win the race.

### Recommendation
Combine the replay check and the usage recording into one atomic operation guarded by a single lock, following the same pattern already used correctly in `vault.RequestReplayGuard.CheckAndRecord`: acquire `cache.mu.Lock()` once, check for existing `jti`, and if absent, insert it, all before releasing the lock. Replace the separate `isReplay`/`recordUsage` calls in `Authorize` with a single `checkAndRecord`-style method.

### Proof of Concept
1. Obtain (or forge, if signer key is otherwise compromised) or capture a valid signed JWT for `WorkflowMetadataHandler.Authorize` with a given `jti`.
2. Fire two concurrent requests to the gateway's workflow-metadata authorization path using the identical JWT.
3. Both goroutines call `isReplay(claims.ID)` before either calls `recordUsage(claims.ID)`, so both pass the replay check and both are authorized — the JWT is accepted twice instead of the second attempt being rejected with "JWT token has already been used." [4](#0-3)

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}

// CheckAndRecord returns ErrRequestAlreadySeen if the digest was previously
// recorded and has not yet expired. Otherwise it records the digest with
// the given expiry timestamp (unix seconds, UTC).
//
// Expired entries are cleaned up on every call.
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
