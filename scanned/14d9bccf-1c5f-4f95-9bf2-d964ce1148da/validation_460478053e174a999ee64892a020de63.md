### Title
Global (non-workflow-scoped) request-ID keyspace lets an authorized-for-any-workflow caller squat a request ID and block another workflow's legitimate execution - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

### Summary
The `httpTriggerHandler` that services the internet-facing CRE gateway's HTTP-trigger execution path stores in-flight requests in a single map keyed only by the client-supplied JSON-RPC `id` (`requestID`), with no namespacing by workflow or by caller/owner. Because the uniqueness check happens after authorization but the map itself is global, any caller who is authorized for *some* workflow can pre-register a request under an `id` that another (unrelated) legitimate caller is about to use for a *different* workflow, causing the honest request to be rejected with `ErrConflict`. This mirrors the reported Optimism bug class: a globally-unique identifier (`UUID`/`requestID`) that must be unique across all actors lets an attacker "squat" the identifier ahead of the honest party and block them, because "the requestID must be unique."

### Finding Description
`httpTriggerHandler` keeps its in-flight-callback table as: [1](#0-0) 

which is populated in `setupCallback`: [2](#0-1) 

The key is `requestID` alone — not `(workflowID, requestID)` or `(owner, requestID)`. `requestID` comes straight from the caller's JSON-RPC `id` field, validated only for non-emptiness and absence of `/`: [3](#0-2) 

The execution flow is: parse/validate → resolve workflow → `authorizeRequest` (JWT signed by the *target* workflow's own key) → rate limit → `setupCallback` (global uniqueness check): [4](#0-3) 

Authorization (`h.workflowMetadataHandler.Authorize`) only proves the caller holds a valid key for the workflow *they specified*, not that they have any relationship to whichever other workflow ends up colliding on the same `requestID`. Since `id` values are attacker-chosen strings and the map is process-wide, a caller who owns/controls Workflow A (a workflow anyone can deploy against the CRE workflow registry) can submit a trigger request for Workflow A using the exact `id` string that a victim is expected to use for Workflow B. If Workflow A's request lands first, `setupCallback` for the victim's Workflow B request with the same `id` fails with: [5](#0-4) 

The test suite explicitly documents and asserts this exact collision behavior (albeit for the same workflow/token in the test), confirming the uniqueness check is enforced purely on the bare `requestID`: [6](#0-5) 

The same architectural pattern (global request-ID map with no owner/workflow scoping) also exists in the confidentialrelay and vault gateway handlers: [7](#0-6) [8](#0-7) 

### Impact Explanation
If an attacker can predict or observe the `requestID` a victim workflow caller is about to use (e.g. deterministic/sequential IDs generated by an integration, or IDs observed via side channels, logs, or a public API/dashboard), the attacker — using their own authorized-but-unrelated workflow — can occupy that ID first. The victim's legitimate request is then rejected outright (`ErrConflict`, "requestID has already been used"), denying that specific execution. Because the block is scoped to a single `requestID` (and self-heals once the reaper expires the stale entry after `CleanUpPeriodMs`, see `reapExpiredCallbacks`), the impact per collision is a bounded denial-of-service on one execution rather than a permanent state-corruption/fund-freeze like the original Optimism report. Unlike the original bug, there is no unbounded/cheap way to block *all* future honest submissions indefinitely (each entry expires and there's no restriction preventing the honest party from retrying with a new ID next time, unless they are contractually forced to reuse a specific idempotency key).

### Likelihood Explanation
Exploitability hinges entirely on the attacker's ability to predict the victim's exact `requestID` string before it is submitted. For most integrations, request IDs are client-generated random values (UUIDs), making blind squatting impractical. The likelihood becomes meaningful only in narrower scenarios: idempotency-key reuse schemes, sequential/time-based ID generators used by some integrator, or leaked/observable IDs (e.g., from logs, webhooks, or a shared queueing system). No authentication bypass or capital/gas asymmetry protects the honest party the way bonds do in the original dispute-game report, so this is a lower-severity, narrower-window analog of the same identifier-squatting bug class.

### Recommendation
Scope the in-flight request table by `(workflowID, requestID)` or `(authorizedOwnerKey, requestID)` instead of by bare `requestID`, so that a caller authorized only for their own workflow cannot occupy the ID namespace of a different workflow. Apply the same fix to the confidentialrelay and vault gateway handlers' `activeRequests` maps, which have the identical global-keying pattern.

### Proof of Concept
1. Attacker deploys/owns Workflow A on the CRE gateway and holds a valid signing key for it.
2. Attacker learns (or guesses, e.g. via a predictable ID scheme) that a victim will soon call Workflow B's HTTP trigger with `id = "X"`.
3. Attacker sends a `workflows.execute` JSON-RPC request with `id = "X"` targeting Workflow A, using their own valid JWT — this passes `authorizeRequest` and reaches `setupCallback`, inserting `h.callbacks["X"]`.
4. Victim's legitimate request for Workflow B with `id = "X"` arrives; `setupCallback` finds `h.callbacks["X"]` already present and returns `ErrConflict`, per the exact code path validated in `TestHttpTriggerHandler_HandleUserTriggerRequest`'s "duplicate request ID" subtest.
5. Victim's execution is denied until the attacker's entry is reaped (bounded by `CleanUpPeriodMs`), after which the attacker can repeat the squat if they can still predict the ID.

func (h *httpTriggerHandler) HandleUserTriggerRequest(ctx context.Context, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback, requestStartTime time.Time) error {
	triggerReq, err := h.validatedTriggerRequest(ctx, req, callback)
	if err != nil {
		return err
	}

	workflowID, err := h.resolveWorkflowID(ctx, triggerReq, req.ID, callback)
	if err != nil {
		return err
	}

	key, err := h.authorizeRequest(ctx, workflowID, req, callback)
	if err != nil {
		return err
	}

	if err = h.checkRateLimit(ctx, workflowID, req.ID, callback); err != nil {
		return err
	}

	strippedWorkflowID := strings.TrimPrefix(workflowID, "0x")
	legacyExecutionID, err := workflows.EncodeExecutionID(strippedWorkflowID, req.ID) //nolint:staticcheck // legacy ID kept for observability comparison
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID: " + err.Error())
	}
	// Workflows shouldn't use more than one HTTP trigger. If we ever need to support multiple triggers, we'd need to pass
	// trigger index to the Gateway handler and somehow allow senders to pick. For now, we use trigger index 0.
	// Execution IDs here are used only for logging.
	executionIDWithTriggerIndex, err := workflows.GenerateExecutionIDWithTriggerIndex(strippedWorkflowID, req.ID, 0)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID with trigger index: " + err.Error())
	}
	h.lggr.Debugw("processing request",
		"legacyExecutionID", legacyExecutionID,
		"executionIDWithTriggerIndex", executionIDWithTriggerIndex,
		"requestID", req.ID,
		"workflowID", workflowID)

	reqWithKey, err := reqWithAuthorizedKey(triggerReq, *key)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error marshaling trigger request: " + err.Error())
	}

	doneCh, err := h.setupCallback(ctx, req.ID, callback, requestStartTime, workflowID)
	if err != nil {
		return err
	}

	return h.sendWithRetries(ctx, legacyExecutionID, executionIDWithTriggerIndex, reqWithKey, workflowID, doneCh)
}

func (h *httpTriggerHandler) validateRequestID(ctx context.Context, requestID string, callback handlers.Callback) error {
	if requestID == "" {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "'id' field is required and cannot be empty. Use a new unique request 'id' for each request", callback)
		return errors.New("empty request ID")
	}
	// Request IDs from users must not contain "/", since this character is reserved
	// for internal node-to-node message routing (e.g., "http_action/{workflowID}/{uuid}").
	if strings.Contains(requestID, "/") {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "request ID must not contain '/'", callback)
		return errors.New("request ID must not contain '/'")
	}
	return nil
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], labels requestLabels, callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID, "executionID", labels.ExecutionID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		labels:    labels,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}
