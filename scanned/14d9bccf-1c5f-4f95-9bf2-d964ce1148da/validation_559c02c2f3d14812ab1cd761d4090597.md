Based on my analysis, I found a concrete, provable analog to the `permit()` front-running DoS in the Vault gateway's `AllowListBasedAuth` flow.

### Title
DoS via front-running the on-chain `AllowlistRequest` commitment to consume a workflow owner's one-time Vault authorization - (File: `core/capabilities/vault/allow_list_based_auth.go`, `core/capabilities/vault/request_replay_guard.go`)

### Summary
The Vault gateway's allow-list authorization path authorizes a JSON-RPC request purely by matching a request digest against an on-chain `WorkflowRegistry.AllowlistRequest(digest, expiry)` commitment, then enforces "single use" via an in-memory `RequestReplayGuard` keyed by that same digest. Because the on-chain `AllowlistRequest` transaction (which reveals the digest) is broadcast before the actual off-chain gateway call is made, any party who can reconstruct or predict the exact request content matching that digest can submit it to the gateway first, permanently consuming the one-time authorization and causing the legitimate workflow owner's subsequent (identical) request to be rejected — the same "front-run the public commitment, burn the one-time-use grant" pattern described in the `permit()` report.

### Finding Description
The allow-list flow works as follows:
1. The workflow owner submits an on-chain transaction `AllowlistRequest(requestDigest, expiryTimestamp)` to the `WorkflowRegistry` contract, which is public in the mempool/chain, exactly like the `permit()` call in the report.
2. The workflow owner later sends the actual JSON-RPC request (e.g. `vault.secrets.delete`, `vault.secrets.list`) to the gateway.
3. `allowListBasedAuth.AuthorizeRequest` computes `req.Digest()` from the request's method/ID/params and checks it against the on-chain allowlisted digests [1](#0-0) . It does **not** verify who is submitting the request — it purely checks a digest match and expiry.
4. `authorizer.AuthorizeRequest` then calls `a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt())`, and if the digest was already recorded, it returns `ErrRequestAlreadySeen` [2](#0-1) .
5. `RequestReplayGuard.CheckAndRecord` accepts the digest exactly once until expiry — first submitter wins [3](#0-2) .

Because the digest commitment is published on-chain before the corresponding off-chain request is submitted (mirroring the `permit()` signature being visible in the mempool before `start()` executes), an attacker who is able to reconstruct the exact JSON-RPC payload that hashes to the on-chain digest (e.g. because the request content is guessable/enumerable — predictable `namespace`/`key` values, a known method with sparse parameter space, or because the payload leaked through logs/telemetry) can race the legitimate owner and submit that content to the gateway first. Since `AuthorizeRequest` does not bind the digest to the network origin or any request-time identity beyond the digest itself, the attacker's copy is authorized and immediately recorded in the replay guard, permanently burning the one-time grant. The legitimate owner's subsequent identical submission then fails with `ErrRequestAlreadySeen`, denying them access to the entitlement they on-chain paid gas to create.

### Impact Explanation
This is a denial-of-service against a legitimate workflow owner's Vault secret operation (create/update/delete/list). The owner's authorization is consumed without their consent, they must re-run the entire on-chain `AllowlistRequest` flow (new digest, new gas cost, wait for `WorkflowRegistrySyncer` propagation) to retry, and in adversarial conditions the race can be repeated indefinitely, effectively blocking the target from ever completing time-sensitive secret mutations.

### Likelihood Explanation
Exploitation requires the attacker to know/predict the exact request content (method + params + ID) that will hash to the publicly-committed digest before the owner submits it. Because the digest itself is one-way (SHA-based) and does not leak content, this is meaningfully harder than the pure `permit()` case, which lowers likelihood versus the original report, but this remains a real risk when parameters are predictable/enumerable (e.g., low-entropy `namespace`/`key` fields, or a fixed/known ID scheme) since the root design flaw — authorization by digest-match alone with no requester binding and single-use consumption of a publicly pre-committed value — is identical to the reported bug class.

### Recommendation
- Bind the on-chain `AllowlistRequest`/off-chain authorization to the requester's identity (e.g., require the off-chain call to be signed/originate from the same key that owns the allowlisted digest, verified inside `allowListBasedAuth.AuthorizeRequest`), not just digest equality.
- Consider adding an authenticated channel (e.g., mTLS/session-bound submission) so a third party cannot exercise a digest they did not compute for their own request.
- Alternatively, ensure request payload entropy (e.g., mandatory random nonce/ID field) is high enough that guessing/pre-computing the digest is infeasible, and audit for any place where request payload content could be predicted or leaked prior to submission.

### Proof of Concept
1. Owner submits `WorkflowRegistry.AllowlistRequest(digest_D, expiry)` on-chain for a `vault.secrets.delete` request they intend to send with fixed, low-entropy params (e.g., `{"ids":[{"owner":"0xOwner","namespace":"main","key":"api-key"}]}`, `id:"1"`).
2. Attacker observes the on-chain digest `digest_D` and, knowing the workflow owner's address and a small guessable parameter space (or having observed the same payload previously, e.g. via retried/cached requests), reconstructs the exact JSON-RPC request that hashes to `digest_D`.
3. Attacker submits this reconstructed request to the gateway before the real owner does. `allowListBasedAuth.AuthorizeRequest` matches the digest and expiry [4](#0-3) , and `authorizer.AuthorizeRequest` records the digest in the replay guard [5](#0-4) .
4. When the legitimate owner submits the same request, `RequestReplayGuard.CheckAndRecord` returns `ErrRequestAlreadySeen` (see `core/capabilities/vault/request_replay_guard_test.go:20-29` for the exact "duplicate rejected" behavior this relies on) [6](#0-5) , and the owner's operation is denied even though they hold the on-chain-committed entitlement.

func (r *allowListBasedAuth) AuthorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	r.lggr.Debugw("AllowListBasedAuth authorizing request", "method", req.Method, "requestID", req.ID)
	requestDigest, err := req.Digest()
	if err != nil {
		r.lggr.Debugw("AllowListBasedAuth failed to create digest", "method", req.Method, "requestID", req.ID, "error", err)
		return nil, err
	}
	requestDigestBytes, err := hex.DecodeString(requestDigest)
	if err != nil {
		r.lggr.Debugw("AllowListBasedAuth failed to decode digest", "method", req.Method, "requestID", req.ID, "requestDigest", requestDigest, "error", err)
		return nil, err
	}
	requestDigestBytes32 := [32]byte(requestDigestBytes)
	if r.workflowRegistrySyncer == nil {
		r.lggr.Errorw("AllowListBasedAuth workflowRegistrySyncer is nil", "method", req.Method, "requestID", req.ID)
		return nil, errors.New("internal error: workflowRegistrySyncer is nil")
	}
	allowlistedRequest, allowedRequestsStrs, err := r.findAllowlistedItemWithRetry(ctx, req, requestDigest, requestDigestBytes32)
	if err != nil {
		return nil, err
	}
	if allowlistedRequest == nil {
		r.lggr.Debugw("AllowListBasedAuth request digest not allowlisted",
			"method", req.Method,
			"requestID", req.ID,
			"digestHexStr", requestDigest,
			"allowedRequestsStrs", allowedRequestsStrs)
		return nil, errors.New("request not allowlisted")
	}

	if time.Now().UTC().Unix() > int64(allowlistedRequest.ExpiryTimestamp) {
		authorizedRequestStr := string(allowlistedRequest.RequestDigest[:])
		r.lggr.Debugw("AllowListBasedAuth authorization expired", "method", req.Method, "requestID", req.ID, "authorizedRequestStr", authorizedRequestStr, "expiryTimestamp", allowlistedRequest.ExpiryTimestamp)
		return nil, errors.New("request authorization expired")
	}

func (a *authorizer) AuthorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	authResult, err := a.authorizeRequest(ctx, req)
	if err != nil {
		return nil, err
	}
	if authResult == nil {
		err = errors.New("auth mechanism returned nil auth result")
		a.lggr.Errorw("auth mechanism returned nil auth result", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "")
		return nil, err
	}
	if err := a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt()); err != nil {
		a.lggr.Debugw("replay guard rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "", "error", err)
		return nil, err
	}
	if ownerErr := validateSecretOwnersMatchAuthorized(req, authResult.AuthorizedOwner()); ownerErr != nil {
		a.lggr.Errorw("owner binding rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "hasAuth", req.Auth != "", "error", ownerErr)
		return nil, ownerErr
	}
	a.lggr.Debugw("request authorized", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "")
	return authResult, nil
}

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
