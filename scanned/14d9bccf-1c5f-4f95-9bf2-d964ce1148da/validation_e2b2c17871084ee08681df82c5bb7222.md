This is exactly the bug class described in CVE-2014-7960: `max_meta_count`-style constraint (here, `MaxSecretsPerOwner`) can be bypassed by splitting a single overage across multiple concurrent requests, because each request's admission check reads a stale/pre-transaction count instead of reserving capacity atomically.

### Title
Vault `MaxSecretsPerOwner` quota can be bypassed via multiple concurrently-batched `CreateSecrets` requests - ([File: core/services/ocr2/plugins/vault/plugin.go])

### Summary
`stateTransitionCreateSecretsRequest` enforces the per-owner secret quota by reading the current count from the `KVStore` and checking `count+1` against `MaxSecretsPerOwner` for each item, one at a time, inside `stateTransitionCreateSecrets`'s loop over `chosen[0].GetCreateSecretsRequest()` responses [1](#0-0) . This mirrors the OpenStack Swift flaw where `max_meta_count` was checked per-request rather than atomically against the true cumulative total, allowing the limit to be exceeded when several requests are combined.

### Finding Description
`stateTransitionCreateSecretsRequest` calls `store.GetSecretIdentifiersCountForOwner(ctx, req.Id.Owner)` and then checks `r.cfg.MaxSecretsPerOwner.Check(ctx, count+1)` before calling `store.WriteSecret` [2](#0-1) . `GetSecretIdentifiersCountForOwner` derives its count from `GetMetadata`, which reads persisted metadata `len(md.SecretIdentifiers)` [3](#0-2) , and `WriteSecret` only updates that metadata (`addIDToMetadata`) after the write succeeds [4](#0-3) .

The batch loop in `stateTransitionCreateSecrets` processes each response entry sequentially and independently for a single `CreateSecretsRequest`, calling `stateTransitionCreateSecretsRequest` once per item [5](#0-4) . The batch-size limiter (`MaxRequestBatchSizeLimiter`) only bounds how many secrets can be requested in one `CreateSecretsRequest` call/message [6](#0-5) ; it does not bound how many *separate* `CreateSecretsRequest` calls an owner can submit concurrently within the same OCR round/outcome-processing window. Because `WriteSecret`/metadata updates for one item only happen synchronously within that item's own state-transition call, and the count check for a subsequent item re-reads the store, the ordering and freshness of that read across multiple concurrently-submitted requests (each individually valid against the currently-committed count) determines whether the aggregate check can be exceeded — precisely the "multiple crafted requests which exceed the limit when combined" pattern from CVE-2014-7960.

### Impact Explanation
An unprivileged workflow owner could exceed the configured `MaxSecretsPerOwner` limit by submitting multiple `CreateSecrets` requests (each within the per-request batch-size limit) around the same processing window, so that the per-owner cap intended to bound storage/resource consumption in the Vault capability is not correctly enforced in aggregate. This is a quota-bypass condition affecting resource limits for an internet/gateway-reachable, unprivileged-authenticated code path (Vault secrets capability reachable by workflow owners), consistent in class with the referenced advisory.

### Likelihood Explanation
Exploitability depends on timing: an attacker needs to get several `CreateSecrets` requests processed such that the count re-read for a later request does not yet reflect writes from an earlier concurrently-processed request. Whether this is actually achievable depends on the exact concurrency/ordering guarantees of the OCR3.1 `StateTransition` execution model (e.g., whether observations for the same owner within one or across sequence numbers are serialized), which I was not able to fully verify from the available code — the reviewed `stateTransitionCreateSecrets` function processes one `CreateSecretsRequest`'s items sequentially, but I could not confirm from what's indexed whether the broader OCR report/outcome pipeline guarantees strict serialization of state transitions across different `RequestId`s/rounds for the same owner, or whether it could process multiple outcomes for the same owner without an intervening committed write.

### Recommendation
Enforce the per-owner secret quota atomically with respect to the write, e.g. read-count-and-reserve inside a single atomic KV transaction/lock keyed by owner, or maintain a per-owner counter that is incremented transactionally as part of `WriteSecret`/`addIDToMetadata` rather than re-derived by a separate read-then-check. Ensure that `stateTransitionCreateSecrets` (or its caller) serializes quota checks across all pending requests for the same owner within a processing round before any writes for that owner are committed, so that concurrently-submitted requests cannot each observe a stale sub-limit count.

### Proof of Concept
Not concretely demonstrable from the indexed code alone: verifying an exploitable race requires tracing the OCR3.1 `StateTransition`/outcome-aggregation call graph to confirm whether it is possible for two distinct `CreateSecretsRequest` state transitions for the same owner to both read `GetSecretIdentifiersCountForOwner` before either commits its `WriteSecret`. I could not fully confirm this ordering guarantee (or its absence) from the code retrieved; a Devin session with full repository access would be needed to trace `ReportingPlugin.StateTransition`'s dispatch order across observations/requests to conclusively prove or disprove exploitability.

func (s *KVStore) GetSecretIdentifiersCountForOwner(ctx context.Context, owner string) (int, error) {
	defer s.trackDuration(ctx, "GetSecretIdentifiersCountForOwner", time.Now())
	md, err := s.GetMetadata(ctx, owner)
	if err != nil {
		return 0, fmt.Errorf("failed to get metadata for owner %s: %w", owner, err)
	}

	count := 0
	if md != nil {
		count = len(md.SecretIdentifiers)
	}
	return count, nil
}
