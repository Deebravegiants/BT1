## Analog Found

### Title
JWT Replay-Protection Window Not Enforced to Cover Full Token Validity Lifetime, Enabling Request Replay - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
The reported ChainLink-adjacent bug is a classic "insufficient check" pattern: a cache/record is treated as fresh/unused based on one time threshold, while the underlying data can actually remain valid under a *different*, unrelated threshold — allowing a stale/already-consumed value to be accepted. The same structural flaw exists in the gateway's JWT-based request authentication for HTTP trigger requests: replay protection is enforced by evicting a token's `jti` from an in-memory cache after `JWTReplayPeriodMs`, but the JWT's own cryptographic validity window (`exp`/`iat`) is governed by a completely separate, hardcoded constant that is never checked against, or tied to, the replay-cache TTL.

### Finding Description
`WorkflowMetadataHandler.Authorize` authenticates unprivileged, internet-facing HTTP trigger requests by verifying a signed JWT and rejecting tokens whose `jti` has already been used: [1](#0-0) 

The replay-protection cache is constructed with an operator-configured TTL, independent of anything related to the JWT's own expiry: [2](#0-1) 

Meanwhile, `VerifyRequestJWT` (the function that performs cryptographic/claims validation for these same requests) allows a token lifetime (`exp - iat`) of up to a hardcoded maximum: [3](#0-2) [4](#0-3) 

There is no code path that enforces `JWTReplayPeriodMs >= maxJWTExpiryDuration` (or any relationship between the two). This mirrors exactly the `GasTankPaymaster.updateCachedPrice()` root cause: the staleness/validity check is performed against the wrong (or an insufficient) reference threshold — here, the *replay cache TTL* — while the actual authoritative validity window — the *JWT `exp` claim* — is independently controlled and can outlive the cache entry. If `JWTReplayPeriodMs` is configured (or defaults) to a value shorter than the maximum allowed JWT lifetime, a `jti` will be evicted from `jwtCache` (via `newJWTReplayCache`'s cleanup) before the token itself has cryptographically expired. At that point, `isReplay(claims.ID)` returns `false` again, and a previously-used, still-cryptographically-valid JWT/request pair can be re-submitted and will pass `Authorize` a second time.

### Impact Explanation
Successful replay of a signed workflow-trigger request lets an unprivileged party (anyone able to observe or capture a legitimate JWT-signed request over the internet-facing gateway) re-trigger the exact same workflow execution after the replay window has elapsed but while the token is still within its `exp`. Because the digest binds the JWT to a specific JSON-RPC request payload (`verifiedClaims.Digest != "0x"+reqDigest` check at [5](#0-4) ), the attacker cannot forge new payloads, but can duplicate an already-authorized workflow execution — an unauthorized/duplicate job run, potentially causing double execution of side-effecting workflow logic (fund movement, external calls, etc., depending on what the workflow does). This is analogous in impact class to "unauthorized job run" from the rules.

### Likelihood Explanation
Exploitability is entirely dependent on the deployed value of `JWTReplayPeriodMs` relative to the (fixed, 5-minute) `maxJWTExpiryDuration`. I could not retrieve the configured/default value of `JWTReplayPeriodMs` in this pass (only that it is read from `ServiceConfig` at [6](#0-5) , and is documented as "how long JWT IDs are cached to prevent replay attacks"). If it is set at or below 5 minutes in any deployment/config, or an operator misconfigures it, replay becomes trivially possible for the remaining window of token validity. The code contains no cross-validation between these two independently-configured timing parameters, so nothing prevents this misconfiguration — the same "insufficient check" pattern flagged in the ChainLink report.

### Recommendation
Enforce that the JWT replay-cache retention window is always greater than or equal to the maximum permitted JWT lifetime (`maxJWTExpiryDuration`), either by deriving `JWTReplayPeriodMs` from that constant automatically, or by validating at startup that `JWTReplayPeriodMs >= maxJWTExpiryDuration` and refusing to start (or clamping it) otherwise. Additionally, consider basing cache eviction directly on each token's own `exp` claim rather than a fixed global TTL, so replay protection is provably tied to the actual token validity window instead of an independently configurable value.

### Proof of Concept
1. Deploy the gateway with `ServiceConfig.JWTReplayPeriodMs` set to a value less than 5 minutes (e.g., 60000 = 1 minute), while a client signs a JWT with `iat`/`exp` giving it close to the maximum allowed 5-minute lifetime.
2. Client submits a valid `HTTPTriggerRequest` with this JWT; `Authorize` succeeds, `claims.ID` is recorded in `jwtCache`, and the workflow executes [7](#0-6) .
3. Wait longer than `JWTReplayPeriodMs` (1 minute) but less than the token's remaining `exp` (up to ~4 more minutes) — `jwtCache`'s cleanup evicts the `jti`.
4. Resubmit the exact same JSON-RPC request with the exact same JWT. `VerifyRequestJWT` still succeeds (token not yet expired, digest still matches the identical payload), and `isReplay(claims.ID)` now returns `false` since the entry was evicted — the request is processed a second time, duplicating the workflow execution.
