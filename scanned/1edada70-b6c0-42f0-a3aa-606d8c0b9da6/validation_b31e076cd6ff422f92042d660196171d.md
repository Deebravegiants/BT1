### Title
Unbounded nested-loop over registered workflow triggers × attacker-controlled topics list causes CPU/DoS in the Web API trigger gateway handler - (File: `core/capabilities/webapi/trigger/trigger.go`)

### Summary
`triggerConnectorHandler.processTrigger`, invoked from `HandleGatewayMessage` for every inbound `MethodWebAPITrigger` gateway message, iterates over **all registered triggers × all topics supplied in the untrusted request payload**, doing map lookups, rate-limiter calls, execution-ID generation and event emission on each hit. Neither the number of registered triggers nor the size of the attacker-supplied `Topics` slice is bounded before the loop runs, so a single external HTTP request forwarded through the internet-facing Gateway can force the node to perform `O(triggers × topics)` work, mirroring the `calculateTVLs` quadratic-loop DoS pattern described in the report.

### Finding Description
`HandleGatewayMessage` unmarshals the untrusted `body.Payload` directly into `webapicap.TriggerRequestPayload` with no bound on `payload.Topics` length: [1](#0-0) 

`processTrigger` then snapshots **all** currently registered triggers and runs a nested loop, `for _, trigger := range triggers { for _, topic := range topics { ... } }`, doing map lookups, rate-limit checks, `events.GenerateExecutionID`, and `events.EmitTriggerExecutionStarted` on every matching pair: [2](#0-1) 

Unlike the RestakeManager `calculateTVLs` case (bounded by number of operators/tokens configured by admins), here one of the two loop dimensions — `topics` — is entirely attacker-controlled per request, and the other dimension — `triggers` — grows with the number of workflows registered across the DON (potentially many, and increasing over time as workflows are deployed). There is no cap on `len(payload.Topics)` before entering the loop, and no check limiting how many registered triggers exist for the handler.

### Impact Explanation
A malicious/unprivileged caller who can reach the Gateway's `web_api_trigger` service (the intended entry point for external HTTP-triggered workflow execution) can submit a single message whose `Topics` array contains a very large number of entries. Combined with a realistic number of registered triggers (deployed workflows) in the DON, this produces `O(triggers × topics)` iterations of map lookups, rate-limiter invocations, and event emission per request — all executed synchronously inside `HandleGatewayMessage`, which is the single-goroutine-per-connection dispatch path from the Gateway connector. This can starve CPU and delay/deny processing of legitimate trigger requests and other gateway traffic, i.e., a DoS on the node's workflow-trigger capability, analogous to the quadratic-loop exhaustion in the source report.

### Likelihood Explanation
The `web_api_trigger` method is explicitly designed to accept requests originating from external, unprivileged HTTP callers relayed through the Gateway (`AddHandler(ctx, []string{"web_api_trigger"}, h)`). The payload shape (`Topics []string`) is fully attacker-controlled and the code contains no length validation before iterating, so no privileged access or special conditions are required to trigger the pathological cost — only a modestly sized topics array and an existing population of registered triggers.

### Recommendation
- Bound `len(payload.Topics)` (and reject/error on requests exceeding a small, sane maximum) before entering the loop in `processTrigger`.
- Replace the "pull"/nested-loop approach with an indexed lookup: build/maintain a map from topic → list of triggers (updated on `RegisterTrigger`/`UnregisterTrigger`) so that matching cost is `O(topics × avg-triggers-per-topic)` rather than `O(all-triggers × topics)`.
- Move expensive per-match work (rate limiting, ID generation, event emission) out of the hot loop where possible, or short-circuit as soon as a single fully-matched trigger is found if that satisfies the intended semantics.

### Proof of Concept
1. Register a moderate number of workflows (e.g., a few thousand) as `web_api_trigger` triggers, each with distinct `AllowedTopics`, via normal `RegisterTrigger` calls — this is an expected, unprivileged-scale operation as more workflows are deployed.
2. As an external, unauthenticated HTTP caller, send a single request to the Gateway targeting `MethodWebAPITrigger` with a `TriggerRequestPayload.Topics` array containing a large number of distinct topic strings (e.g., tens of thousands), and any sender address.
3. `HandleGatewayMessage` → `processTrigger` will iterate `len(triggers) × len(topics)` times synchronously, performing map lookups and rate-limiter calls for each pairing, consuming CPU proportional to the product — a single request can be crafted to consume disproportionate processing time relative to its size, blocking the connector's dispatch goroutine for that gateway connection.

func (h *triggerConnectorHandler) HandleGatewayMessage(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) error {
	msg, err := hc.ValidatedMessageFromReq(req)
	if err != nil {
		h.lggr.Errorw("error validating message from request", "err", err, "request", req)
		return nil
	}
	body := &msg.Body
	sender := ethCommon.HexToAddress(body.Sender)
	var payload webapicap.TriggerRequestPayload
	err = json.Unmarshal(body.Payload, &payload)
	if err != nil {
		h.lggr.Errorw("error decoding payload", "err", err)
		err = h.sendResponse(ctx, gatewayID, body, ghcapabilities.TriggerResponsePayload{Status: "ERROR", ErrorMessage: fmt.Errorf("error %s decoding payload", err.Error()).Error()})
		if err != nil {
			h.lggr.Errorw("error sending response", "err", err)
		}
		return nil
	}

	case ghcapabilities.MethodWebAPITrigger:
		resp := h.processTrigger(ctx, gatewayID, body, sender, payload)
