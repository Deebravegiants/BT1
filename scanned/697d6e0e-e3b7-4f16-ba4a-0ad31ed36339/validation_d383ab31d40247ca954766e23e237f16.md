### Title
Silent, unrecoverable drop of already-delivered XCMP asset-transfer messages at `drop_threshold` causes sender/receiver asset-accounting mismatch - (File: cumulus/pallets/xcmp-queue/src/lib.rs)

### Summary
The XCMP inbound-message pipeline discards any XCM page (including genuine reserve-transfer/teleport payloads) once the receiving parachain's per-sender queue has reached `QueueConfigData::drop_threshold`, logging only via `tracing::error!`/`defensive!` with no on-chain `Event` and no state retained for recovery. Because a sender-side `pallet_xcm` transfer (`transfer_assets`) irrevocably burns/withdraws/reserves the asset locally as part of building and dispatching the outbound XCM *before* the message is even placed in the channel, a drop on the receiving side after successful, paid HRMP delivery produces a permanent, silent asset-accounting mismatch between chains.

### Finding Description
`Pallet::enqueue_xcmp_messages` reads the configured `drop_threshold` and calls `T::XcmpQueue::get_batches_footprints(sender, xcms, drop_threshold)` [1](#0-0)  . The real `pallet-message-queue` implementation of `get_batches_footprints` returns an empty/partial footprint as soon as `total_pages_count > total_pages_limit` (i.e. the existing queued page count already at/over `drop_threshold`) [2](#0-1)  . Back in the xcmp-queue pallet, only `best_batch_footprint.msgs_count` messages are actually enqueued via `T::XcmpQueue::enqueue_messages`; any remaining messages in the batch (which can be the entire XCM page, including a would-be asset-transfer payload) are never enqueued. This is reported purely with `tracing::error!` and the function returns `Err(())`, which makes the caller `break` out of processing further batches from that page/sender in `handle_xcmp_messages` [3](#0-2) [4](#0-3)  . No `Event` is deposited and no message identifier is retained anywhere for later retry or refund. The pallet's own doc comments concede the danger: `drop_threshold` "should normally not happen since the `suspend_threshold` can be used to suspend the channel" and, in `on_queue_changed`, "It will retry if `drop_threshold` is not reached, but it could be too late" / "further messages may be dropped" [5](#0-4)  . Crucially, the HRMP/relay-chain transport layer has already reliably and verifiably delivered the page into the parachain's PoV before this runtime-level drop decision is made — this is a self-inflicted, local resource-limit discard of data that was already paid for and committed on-chain, not a network-level loss. Since a sender-side reserve-transfer/teleport already executed local burn/withdraw/reserve effects (via `InitiateTeleport`/`InitiateReserveWithdraw`/`DepositReserveAsset` local program execution) before the message ever entered the channel, a drop on the receiving side after that point leaves the sender's assets gone with no corresponding credit or recoverable trace on the receiver, and no event records this fact anywhere. The reachability of the precondition (pushing the inbound queue to `drop_threshold` before the `Suspend` signal takes effect) is demonstrated directly by the pallet's own test `xcm_enqueueing_starts_dropping_on_overflow`, which fills a queue past its threshold and asserts messages beyond it are simply absent from `EnqueuedMessages` [6](#0-5)  .

### Impact Explanation
An attacker who can cheaply flood many small XCM messages from a sending parachain toward a target parachain (well within normal unprivileged XCM-send capability) can push that sibling's per-sender inbound queue to `drop_threshold` before the `ChannelSignal::Suspend` feedback loop takes effect (it requires at least one additional relay-chain round trip to reach and be processed by the sender). Any genuine asset transfer (reserve-transfer or teleport) whose XCM page lands in the channel at/above `drop_threshold` at that moment is silently discarded on the receiving parachain, while the sender chain has already irrevocably debited the sending account. This is concrete, unrecoverable fund loss for the transfer's beneficiary with zero on-chain trace (no `Event`, no `OverweightEnqueued`-style entry, nothing) to detect or remediate it.

### Likelihood Explanation
The precondition (drive one sibling's inbound queue past `drop_threshold`) is directly demonstrated by the pallet's own unit test and requires only sending many messages faster than the suspend/resume signal round-trip can react — cheap, repeatable, and does not require any privileged origin, since any account capable of triggering outbound XCM sends (e.g. via `pallet_xcm::send`/transfers) from the flooding source can produce this. Precisely timing a *real* asset transfer to land in the exact page that crosses the threshold adds some timing precision requirements but is feasible for an attacker who controls or heavily uses the sending chain and observes queue depth via public chain state before submitting the transfer.

### Recommendation
When `enqueue_xcmp_messages` determines that messages will be dropped due to `drop_threshold` (i.e. `best_batch_footprint.msgs_count < xcms.len()`), do not silently discard them: emit an on-chain `Event` (e.g. `Event::XcmpMessageDropped { sender, dropped_count, ... }`) that records the sender and the discarded message count/hashes so off-chain tooling/relayers can detect the loss, and consider gating asset-affecting outbound `pallet_xcm` transfers behind delivery-fee/queue-depth checks (e.g. rejecting `transfer_assets` sends when the destination channel's outbound state is already `Suspended`), rather than relying purely on best-effort local weight-based dropping with only a log line.

### Proof of Concept
Extend `cumulus/pallets/xcmp-queue/src/tests.rs`-style setup into an xcm-emulator integration test:
1. Configure a sibling channel with a low `drop_threshold` (e.g. via `update_drop_threshold`/genesis default).
2. From parachain A, flood parachain B's inbound queue for sender A with cheap XCM pages until `ready_pages` reaches `drop_threshold` (mirroring `xcm_enqueueing_starts_dropping_on_overflow`).
3. Submit a real `pallet_xcm::transfer_assets` from an account on A to a beneficiary on B, timed so its XCM page is processed while the queue is at/over `drop_threshold`.
4. Assert: (a) the sender's account balance on A decreased by the transferred amount (burn/withdraw executed); (b) no corresponding balance increase occurs for the beneficiary on B; (c) no `Event` was deposited on B recording the drop (`System::events()` contains no drop/refund event); failing the test demonstrates the silent, unrecoverable fund loss described.
