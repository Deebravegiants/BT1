### Title
Fee-refund path in `SwapAssetAdapter::correct_and_deposit_fee` uses a manipulable spot-price AMM quote, letting a user extract LP-pool value via same-transaction price manipulation - (File: `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs`)

### Summary
`ChargeAssetTxPayment` withdraws the fee in a non-native asset at prepare-time using a quote from the AMM pool (`quote_price_tokens_for_exact_tokens`), and refunds unspent weight at `post_dispatch_details` using a *second, independent* spot-price quote (`quote_price_exact_tokens_for_tokens`) taken after the dispatched call (and any pool-moving swaps within it) has already executed. Because the refunded native amount is fixed by weight accounting but the asset amount returned for it is priced off the *current* (attacker-controllable) pool reserves, a user can move the pool price with their own call/extrinsics between the two quotes and receive materially more asset back than the fee they actually paid, extracting value from the AMM pool.

### Finding Description
The fee lifecycle for `ChargeAssetTxPayment` is:

1. `prepare` → `SwapAssetAdapter::withdraw_fee` quotes `S::quote_price_tokens_for_exact_tokens(asset_id, A::get(), fee, true)` at the pool state *before* the call is dispatched, withdraws that quoted `asset_fee`, and swaps it into native `fee` immediately (back-to-back, same price) [1](#0-0) .
2. The wrapped call is dispatched. Nothing prevents that call itself (or any other extrinsic executed earlier in the same block) from being an `AssetConversion` swap that moves the native/asset pool reserves.
3. `post_dispatch_details` computes `actual_fee` from actual weight used, then calls `SwapAssetAdapter::correct_and_deposit_fee`, which re-quotes the refund at the *current* pool state: `S::quote_price_exact_tokens_for_tokens(A::get(), asset_id, refund_amount, true)` and then executes `S::swap_exact_tokens_for_tokens(vec![A::get(), asset_id], refund, Some(refund_asset_amount))` [2](#0-1) .

`refund_amount` (native) is derived purely from weight/fee accounting (`fee_paid.peek().saturating_sub(corrected_fee)`), independent of AMM price [3](#0-2) . The asset amount handed back for that fixed native amount is priced off whatever the pool reserves are *at that exact post-dispatch moment*. Since the dispatched call (or a sandwiching extrinsic within the same block) can shift the asset/native reserve ratio in the attacker's favor before this quote runs, the attacker receives a refund priced at a manipulated rate rather than the rate that prevailed when the fee was originally withdrawn. No slippage/TWAP protection ties the refund quote back to the original withdrawal price — the `Some(refund_asset_amount)` passed to `swap_exact_tokens_for_tokens` only protects the swap-quote/swap-execute pair against interleaving between those two calls, not against manipulation occurring before the quote itself.

The value extracted comes directly out of the AMM pool (LPs): the refund swap feeds the already-collected native fee back into the pool in exchange for asset_id at the skewed price, and the amount out scales with how far the attacker moved reserves relative to pool depth, not with the true economic size of the refund.

### Impact Explanation
This lets a signed, unprivileged account that (a) pays tx fees in a non-native asset via `ChargeAssetTxPayment`/`SwapAssetAdapter`, and (b) can include or interleave a pool-moving swap in the same extrinsic/block, extract asset value from the `pallet-asset-conversion` liquidity pool beyond what their actual fee reduction warrants. This is a fee-accounting/oracle-manipulation bug that transfers LP value to the attacker; it does not require any privileged access and is repeatable per block as long as the pool has finite depth relative to the manipulation size.

### Likelihood Explanation
Preconditions are realistic and fully attacker-controlled: a live `AssetConversion` pool for `asset_id`/native, a signed account paying fees in that asset, and the ability to submit ordinary swap extrinsics (or embed a swap as the dispatched call itself) before `post_dispatch_details` runs. No governance or privileged action is required. Profitability is bounded by pool depth vs. LP fee costs of the manipulation, but the earlier analysis (moving the pool ~50% and then reverting) shows a positive net gain is achievable, so the attack is economically viable against pools that aren't extremely deep relative to the refundable weight-fee amount, and is fully repeatable each block.

### Recommendation
Do not use a fresh spot-price AMM quote for the refund leg. Options: (1) cache/derive the refund conversion from the same price used at withdrawal (e.g., compute the refund proportionally from `fee_asset_amount`/`fee` ratio recorded at withdraw time rather than re-quoting the pool), (2) bound the refund quote by the originally-paid `fee_asset_amount` so the user can never receive back more asset than they put in, or (3) require the refund swap to use a TWAP/oracle price rather than instantaneous spot reserves, and additionally clamp `refund_asset_amount` to `min(quoted_refund, fee_asset_amount - 1)` as a hard ceiling so no price move can return more than was originally withdrawn.

### Proof of Concept
Rust integration test to add to `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/tests.rs`:
1. Set up `setup_lp(asset_id, balance_factor)` producing a pool with moderate depth.
2. `caller` calls `validate_and_prepare` for `ChargeAssetTxPayment` with `asset_id`, recording `fee_in_asset` withdrawn and the pool reserves at that point.
3. Before calling `post_dispatch_details`, execute (as the caller, using an ordinary signed `AssetConversion::swap_exact_tokens_for_tokens` extrinsic call) a large swap of `asset_id` into the pool for native, skewing reserves toward more `asset_id`/less native.
4. Call `post_dispatch_details` with a `post_info` reflecting some unused weight so `refund_amount > 0`, and record `expected_token_refund`/actual `Assets::balance` change for `caller`.
5. Compute `fair_refund` = what `quote_price_exact_tokens_for_tokens` would have returned at the *original* (step-2) reserves for the same `refund_amount`.
6. Assert `actual_token_refund > fair_refund` (proving the refund is inflated by the manipulation) and, optionally, reverse the manipulation swap and assert the caller's net asset balance (`starting_balance - fee_in_asset + actual_token_refund + reversed_swap_output - manipulation_swap_input`) is strictly greater than `starting_balance - actual_fee_at_fair_price`, demonstrating net profit extracted from the pool.
