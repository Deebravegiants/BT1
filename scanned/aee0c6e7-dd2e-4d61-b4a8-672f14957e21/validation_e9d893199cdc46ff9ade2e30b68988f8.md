### Title
Missing Duplicate-MessageID Guard Enables Cross-User Response Hijacking in Gateway WebAPI Handler - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The Otter Audits finding describes a CPI-guard bug where the Solana program indexed a paired instruction (`PreSwap`/`PostSwap`) purely by a numeric instruction index, without verifying the call was not nested/re-entered. Two logically-independent calls collided on the same index, letting a second call silently overwrite state set by the first and steal funds. The chainlink analog is in the internet-facing Gateway's `WebAPIHandler`, which stores an in-flight caller callback keyed only by a caller-supplied `MessageID` in a shared map, with no uniqueness/ownership check before the entry is overwritten [1](#0-0) . A second request using the same `MessageID` silently replaces the first caller's pending callback, so the eventual node response is routed to the wrong caller.

### Finding Description
`HandleLegacyUserMessage` stores the caller's callback in `h.savedCallbacks` keyed solely by `msg.Body.MessageID`, with no check for an existing entry: [1](#0-0) 

This is unlike the sibling v2 HTTP trigger handler, which explicitly guards against ID collisions by checking `if _, found := h.callbacks[requestID]; found` and rejecting the request with `jsonrpc.ErrConflict` before inserting [2](#0-1) . The legacy `handler.go` path lacks this same guard.

When a node later responds with `MethodWebAPITrigger`, the response is matched purely by `MessageID`, the callback is deleted and immediately sent the node's response: [3](#0-2) 

Because `MessageID` is caller-supplied and the map is a single shared table with no per-sender/per-owner scoping (unlike the vault handler's `activeRequest` model or `requestcache.go`'s `globalID{sender, id}` composite key which explicitly binds requests to their sender to avoid exactly this class of collision) [4](#0-3) , an unprivileged caller can submit a `web_api_trigger` request whose `MessageID` collides with (or is guessed/predicted to equal) another in-flight caller's `MessageID`. The second (attacker) call overwrites `h.savedCallbacks[MessageID]` with the attacker's own callback via `HandleLegacyUserMessage` [1](#0-0) . When the DON node subsequently answers the original (victim) request, `handleWebAPITriggerMessage` looks the response up by the same `MessageID`, finds the attacker's callback now installed there, and forwards the victim's response payload to the attacker [3](#0-2) . The victim's own callback reference is lost and never receives a response (denial of response) while the attacker receives data destined for another user — a cross-user response confusion, structurally identical to the “second call overwrites state set by the first” bug class in the report.

### Impact Explanation
An unprivileged actor able to submit web-API-trigger messages through the gateway can hijack another in-flight caller's response, receiving potentially sensitive trigger/workflow response payload data intended for a different user, while the legitimate caller's request silently times out. This is a concrete cross-user response confusion / request impersonation impact reachable purely through the gateway's public message-handling path.

### Likelihood Explanation
Exploitation requires the attacker to cause (or race to guess) a `MessageID` collision with an in-flight victim request before the corresponding node response arrives. Feasibility depends on how `MessageID` values are generated by legitimate callers (e.g., predictable counters or short IDs increase likelihood; cryptographically random UUIDs would reduce it). Because the vulnerable map lacks any explicit collision/ownership check — a control the codebase itself applies elsewhere (`http_trigger_handler.go`, `requestcache.go`) — the missing guard here is a genuine gap rather than defense-in-depth already covered.

### Recommendation
Add the same duplicate-ID rejection used in `http_trigger_handler.go` to `HandleLegacyUserMessage`: reject/queue instead of silently overwriting when `h.savedCallbacks[msg.Body.MessageID]` already exists, or key the callback map by a composite `{sender, MessageID}` identity (as `requestcache.go` already does) so that colliding IDs from different senders cannot overwrite one another's pending callbacks.

### Proof of Concept
1. Victim sends a `web_api_trigger` request through the gateway with `MessageID = "X"`; the gateway stores the victim's callback at `h.savedCallbacks["X"]`.
2. Before the DON node responds, attacker sends their own `web_api_trigger` request also using `MessageID = "X"`; this call overwrites `h.savedCallbacks["X"]` with the attacker's callback (no collision check exists in `HandleLegacyUserMessage`).
3. The DON node eventually responds for message ID `"X"` (intended as the victim's response). `handleWebAPITriggerMessage` looks up `h.savedCallbacks["X"]`, finds the attacker's callback, deletes the entry, and sends the victim's response payload to the attacker.
4. The victim's original callback is never invoked and receives no response.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
