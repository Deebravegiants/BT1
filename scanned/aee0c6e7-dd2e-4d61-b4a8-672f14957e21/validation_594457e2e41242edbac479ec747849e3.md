### Title
Missing role authorization on `GET /v2/external_initiators` allows any authenticated low-privilege user to read all External Initiator access keys and outgoing tokens - ([File: core/web/router.go])

### Summary
`core/web/router.go` registers the External Initiator collection endpoints with inconsistent role gating: `Create` and `Destroy` require `auth.RequiresEditRole`, but `Index` (the `GET` listing endpoint) is registered with only session/token authentication and no role check at all.

### Finding Description
In `v2Routes`, the three External Initiator endpoints are wired as: [1](#0-0) 
```go
eia := ExternalInitiatorsController{app}
authv2.GET("/external_initiators", paginatedRequest(eia.Index))
authv2.POST("/external_initiators", auth.RequiresEditRole(eia.Create))
authv2.DELETE("/external_initiators/:Name", auth.RequiresEditRole(eia.Destroy))
```
`POST` and `DELETE` are explicitly wrapped with `auth.RequiresEditRole`, matching the rest of the router's convention (bridge types, transfers, etc. all gate mutating/sensitive actions behind at least `edit` or `admin` roles, see `authv2.POST("/bridge_types", auth.RequiresEditRole(bt.Create))` at [2](#0-1) ). `GET /external_initiators`, however, sits only inside the `authv2` group, which merely requires the request to pass `auth.AuthenticateByToken` or `auth.AuthenticateBySession` — i.e., any valid session/API token regardless of role: [3](#0-2) .

`Index` then returns every External Initiator record, including the incoming `AccessKey` and `OutgoingToken`, via `presenters.NewExternalInitiatorResource`: [4](#0-3) [5](#0-4) 

This is the same bug class as the Singularity Finance root cause: a security-relevant parameter (the required role for a route) was configured inconsistently across sibling endpoints and never validated/enforced, so an operation that should be gated at "edit"-level privilege is silently left open to any authenticated caller including the lowest-privilege `view`/`run` roles — an unvalidated admin-level configuration gap directly reachable by an unprivileged authenticated user.

### Impact Explanation
A user with only `view` or `run` role (roles intended to be read-only or execution-only, explicitly denied edit/admin-level actions elsewhere, e.g. `RequiresEditRole` rejects `UserRoleView`/`UserRoleRun`, see [6](#0-5) ) can enumerate all External Initiators' `AccessKey` and `OutgoingToken` values on the node. `AccessKey` is one half of the credential pair used by `AuthenticateExternalInitiator` (paired with a `Secret` that is not returned by `Index`), so this alone doesn't grant full impersonation, but it does leak sensitive configuration/credential material to a role class that is supposed to have no edit-level visibility, violating the node's role-based access model and enabling reconnaissance for further attacks (e.g., targeted secret brute-forcing/guessing, correlating outgoing tokens with initiator infrastructure).

### Likelihood Explanation
Any low-privilege API/session user (e.g., `run` or `view` role, which many operational/CI accounts are deliberately restricted to) can trigger this with a single unauthenticated-role-check `GET` request; no special conditions are needed beyond having any valid chainlink API token or session, making this trivially and consistently reachable.

### Recommendation
Wrap the `Index` route the same way as `Create`/`Destroy`: `authv2.GET("/external_initiators", auth.RequiresEditRole(paginatedRequest(eia.Index)))` (or at minimum `RequiresRunRole` if broader read access is intentional, but then strip `AccessKey`/`OutgoingToken` from the `Index` presenter output for non-edit roles). Add an explicit test asserting `view`/`run` role users receive `401/403` on `GET /v2/external_initiators`, mirroring existing role-based route tests.

### Proof of Concept
1. Create a user with `UserRoleView` (or `UserRoleRun`).
2. Authenticate as that user (session cookie or API token) and call `GET /v2/external_initiators`.
3. Observe the response returns `200 OK` with the full list of `ExternalInitiatorResource` objects, including `AccessKey` and `OutgoingToken` for every registered External Initiator — despite the same user receiving `401 Unauthorized` if they attempt `POST /v2/external_initiators` or `DELETE /v2/external_initiators/:Name`, confirming the `Index` route is missing the intended role check.

func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
