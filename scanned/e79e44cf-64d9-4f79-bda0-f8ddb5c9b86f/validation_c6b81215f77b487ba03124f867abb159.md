### Title
Unprivileged authenticated node users (View role) can disclose RPC provider credentials embedded in node configuration via `/v2/config` - (File: core/web/config_controller.go)

### Summary
`GET /v2/config` (and `/v2/config/v2`) is registered under the authenticated route group but, unlike most other sensitive endpoints in the router, is not wrapped with any `auth.RequiresEditRole` / `auth.RequiresAdminRole` middleware. Any authenticated user — including the lowest-privilege `View` role — can call this endpoint and retrieve the node's full effective/input TOML configuration, which commonly contains RPC provider URLs (`WSURL` / `HTTPURL`) with embedded API keys (e.g., Alchemy/Infura/QuickNode style URLs), OIDC `ClientID`, and other operator-supplied configuration values that were never intended to be visible to low-privilege users.

### Finding Description
The route is registered without a role guard: [1](#0-0) 

Compare this to neighboring routes in the same file, which are explicitly wrapped with `auth.RequiresEditRole` or `auth.RequiresAdminRole` (e.g. `bridge_types`, `external_initiators`, `transfers`), confirming that role-gating is the intended pattern for sensitive configuration/management endpoints, but was omitted for `/config`.

The handler itself returns the full input/effective configuration TOML with no filtering of potentially sensitive fields such as node RPC endpoints: [2](#0-1) 

The application's config model formally separates "Secrets" (Database URL, Keystore password) from general `Config`, and only `Secrets.TOMLString()` performs redaction: [3](#0-2) 

RPC node URLs (`EVM.Nodes[].WSURL` / `HTTPURL`) are treated as ordinary `Config` fields, not `Secrets`, so they are never redacted — even though operators frequently embed provider API keys directly in these URLs (a well-known operational pattern for services like Alchemy/Infura). Because `ConfigTOML()` returns the full `Config` TOML unfiltered, and the `/v2/config` route enforces only session/token authentication with no minimum role, any authenticated user with `View`-level access (the lowest privilege tier defined in `core/web/auth/auth.go` role checks such as `RequiresEditRole`) can read these embedded credentials.

### Impact Explanation
An authenticated but unprivileged user (e.g. a `View`-role API user, who per `RequiresEditRole`/`RequiresAdminRole` logic should not have access to sensitive operational data) can extract RPC provider API keys and other operator-configured secrets embedded in the node's configuration. This enables unauthorized use of the node operator's third-party API credits, potential rate-limit exhaustion/DoS against the operator's provider account, and exposure of other configuration data (e.g. OIDC `ClientID`) not meant for low-privilege roles — directly analogous to the GitLab class of bug where a config/HTML page discloses credentials to a viewer without the appropriate privilege level.

### Likelihood Explanation
High: the endpoint requires only basic session or API-token authentication (no minimum role), as shown by the router wiring. Any created API user regardless of assigned role (`view`, `run`, `edit`, `admin`) can call `GET /v2/config` immediately after being provisioned, with no additional step, mirroring the "other administrators" pattern in the original CVE, but here even the lowest role tier is sufficient.

### Recommendation
- Wrap `authv2.GET("/config", cc.Show)` and `/config/v2` with `auth.RequiresAdminRole` (or at minimum `RequiresEditRole`) matching the sensitivity of the data returned.
- Alternatively/additionally, redact known-sensitive substrings (e.g., URL query parameters/API keys) from `WSURL`/`HTTPURL` and other externally-facing configuration values before serialization in `ConfigTOML()`.

### Proof of Concept
1. Create a chainlink node with an EVM node RPC URL containing a provider API key, e.g. `HTTPURL = 'https://eth-mainnet.g.alchemy.com/v2/<API_KEY>'`.
2. Create an API user with role `view` via the admin CLI/API (`POST /v2/users` with `role=view`).
3. Authenticate as the `view` user and call `GET /v2/config`.
4. Observe the response includes the full `[[EVM.Nodes]]` block with the RPC URL and embedded API key, confirming disclosure to a low-privilege authenticated actor: [4](#0-3) [5](#0-4) 

**Note on confidence**: I was not able to fully view the `routesRolesMap` table entries for `/v2/config` in `core/web/auth/auth_test.go` (only a partial excerpt was retrievable via search) to confirm the test suite's expected role permissions for this route, nor could I directly confirm at runtime whether `WSURL`/`HTTPURL` values in a live deployment always contain embedded credentials — this is a common but not universal operational pattern. If a Devin session is needed to inspect the full `auth_test.go` route table and confirm intended role enforcement for `/v2/config`, that would help solidify certainty on this finding.

// Show returns the whitelist of config variables
// Example:
//
//	"<application>/config"
func (cc *ConfigController) Show(c *gin.Context) {
	cfg := cc.App.GetConfig()
	var userOnly bool
	if s, has := c.GetQuery("userOnly"); has {
		var err error
		userOnly, err = strconv.ParseBool(s)
		if err != nil {
			jsonAPIError(c, http.StatusBadRequest, fmt.Errorf("invalid bool for userOnly: %w", err))
			return
		}
	}
	var toml string
	user, effective := cfg.ConfigTOML()
	if userOnly {
		toml = user
	} else {
		toml = effective
	}
	jsonAPIResponse(c, ConfigV2Resource{toml}, "config")
}

// TOMLString returns a TOML encoded string with secret values redacted.
func (s *Secrets) TOMLString() (string, error) {
	b, err := gotoml.Marshal(s)
	if err != nil {
		return "", err
	}
	return string(b), nil
}
