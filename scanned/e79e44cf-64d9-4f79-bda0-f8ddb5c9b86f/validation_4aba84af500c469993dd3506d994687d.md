# Lack of Validation in Gateway Legacy WebAPI Trigger Handler

### Title
Unvalidated/Unauthenticated Fan-out of Legacy WebAPI Trigger Messages to All DON Nodes - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
The external report describes unvalidated event-listener input (`chrome.runtime.onMessage.addListener`) that lets malicious messages manipulate internal state without sanitization. The analogous flaw in this codebase is the Gateway's `capabilities.handler.HandleLegacyUserMessage`, which is the entry point for legacy JSON-RPC "web_api_trigger" requests coming from any external, unprivileged client through `gateway.ProcessRequest`. This handler explicitly skips sender allowlisting and rate-limiting — a gap the code itself flags with `// TODO: apply allowlist and rate-limiting here` — before broadcasting the message to every member node of the DON.

### Finding Description
An external client reaches the gateway's HTTP endpoint, which decodes and structurally validates the JSON-RPC/legacy envelope and dispatches legacy requests to the target handler: [1](#0-0) 

For DON handlers built from the `capabilities` package, `HandleLegacyUserMessage` only checks that the payload decodes, that the timestamp isn't stale, and that the method equals `web_api_trigger` — it does **not** check the message sender against any allowlist and does **not** apply rate-limiting, despite an explicit TODO acknowledging this is missing: [2](#0-1) 

After these checks, the handler unconditionally fans the raw, unauthorized request out to **every** configured DON member: [3](#0-2) 

`api.Message.Validate()` (invoked from `gateway.go`) only checks structural well-formedness (non-empty IDs, valid receiver address, and that the signature is well-formed) — it does not check that the signer/sender is an authorized or allowlisted party: [4](#0-3) 

This is a materially different code path from the newer `webapicap` trigger implementation (`core/capabilities/webapi/trigger/trigger.go`), which enforces `allowedSenders`/`allowedTopics`/per-sender rate limiting on the DON-node side before honoring a trigger: [5](#0-4) 

Because the gateway-side legacy handler performs no allowlist or rate-limit check before broadcasting, any unprivileged actor who can produce a structurally valid (self-signed, not necessarily allowlisted) message can force the gateway to send an unbounded volume of messages to all DON node members, consuming node-side network/processing resources before any per-sender rate limiter or allowlist is applied downstream at the trigger capability.

### Impact Explanation
An unauthenticated, unprivileged external actor can trigger unbounded message fan-out to every node in a DON by simply crafting a self-signed legacy `web_api_trigger` message with a fresh timestamp — no allowlist membership is required to reach `don.SendToNode` for all members. This is a quota/allowlist bypass at the gateway ingress boundary that can be used to flood and degrade DON node availability (denial of service), even though the final workflow execution is gated by a separate allowlist at the node.

### Likelihood Explanation
Likelihood is significant: the vulnerable code path is directly reachable from any external HTTP client via the internet-facing Gateway's `ProcessRequest` entry point with no authentication beyond crafting a valid signature (which any actor can generate with their own key), and the missing check is explicitly acknowledged as a TODO in the shipped code rather than a latent oversight.

### Recommendation
Implement the sender allowlist and rate-limiting checks referenced in the `// TODO: apply allowlist and rate-limiting here` comment inside `HandleLegacyUserMessage` before forwarding messages to DON members — mirroring the `allowedSenders`/`rateLimiter` enforcement already present in `core/capabilities/webapi/trigger/trigger.go`. This should happen at the gateway ingress boundary, not only at the DON-node side, to prevent fan-out amplification to all nodes for unauthorized senders.

### Proof of Concept
1. Generate an arbitrary ECDSA key pair (no allowlist membership required).
2. Construct an `api.Message` with `Body.Method = "web_api_trigger"`, a fresh timestamp, and any DON ID/receiver, then sign it with the arbitrary key (per `api.Message.Sign`/`Validate` semantics shown in `message_test.go`).
3. Submit it repeatedly as a legacy JSON-RPC request to the Gateway's public HTTP endpoint (`gateway.ProcessRequest`).
4. Observe that `HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go` accepts and forwards each message to every DON member via `don.SendToNode` without any sender allowlist or rate-limit check, at `core/services/gateway/handlers/capabilities/handler.go:411-420`.

func TestMessage_Validate(t *testing.T) {
	msg := &api.Message{
		Body: api.MessageBody{
			MessageID: "abcd",
			Method:    "request",
			DonID:     "donA",
			Receiver:  "0x0000000000000000000000000000000000000000",
			Payload:   []byte("datadata"),
		},
	}
	privateKey, err := crypto.GenerateKey()
	require.NoError(t, err)
	err = msg.Sign(privateKey)
	require.NoError(t, err)

	// valid
	require.NoError(t, msg.Validate())

	// missing message ID
	msg.Body.MessageID = ""
	require.Error(t, msg.Validate())
	// message ID ending with null bytes
	msg.Body.MessageID = "myid\x00\x00"
	require.Error(t, msg.Validate())
	msg.Body.MessageID = "abcd"
	require.NoError(t, msg.Validate())

	// missing DON ID
	msg.Body.DonID = ""
	require.Error(t, msg.Validate())
	// DON ID ending with null bytes
	msg.Body.DonID = "mydon\x00\x00"
	require.Error(t, msg.Validate())
	msg.Body.DonID = "donA"
	require.NoError(t, msg.Validate())

	// method name too long
	msg.Body.Method = string(bytes.Repeat([]byte("a"), api.MessageMethodMaxLen+1))
	require.Error(t, msg.Validate())
	// empty method name
	msg.Body.Method = ""
	require.Error(t, msg.Validate())
	// method name ending with null bytes
	msg.Body.Method = "method\x00"
	require.Error(t, msg.Validate())
	msg.Body.Method = "request"
	require.NoError(t, msg.Validate())

	// incorrect receiver
	msg.Body.Receiver = "blah"
	require.Error(t, msg.Validate())
	msg.Body.Receiver = "0x0000000000000000000000000000000000000000"
	require.NoError(t, msg.Validate())

	// invalid signature
	msg.Signature = "0x00"
	require.Error(t, msg.Validate())
