Target: `ShopifyAPI::Webhooks::Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb`), which returns `@raw_body` only, and `ShopifyAPI::Utils::HmacValidator.validate`, which HMACs only that string. Attacker action: an attacker's own dev shop receives one validly-signed HTTP webhook (e.g. `orders/create` for `attacker-shop.myshopify.com` with body `{}`); the attacker replays the identical `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint but swaps the `x-shopify-topic` header to `customers/data_request` and `x-shopify-shop-domain` to `victim-shop.myshopify.com`. Preconditions: app registered a handler for `customers/data_request` via `ShopifyAPI::Webhooks::Registry.add_registration`; `victim-shop` is an existing installed tenant. Call sequence: `Registry.process(request)` -> `HmacValidator.validate(request)` recomputes HMAC over `request.to_signable_string` (== `@raw_body`, unchanged) and succeeds -> `@registry[request.topic]` selects the `customers/data_request` handler -> `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))`. Binding that breaks: `request.topic == topic authenticated by HMAC` and `request.shop == shop authenticated by HMAC` both fail because neither is inside `to_signable_string`. Impact: Critical, cross-tenant access — handler acts on `victim-shop`'s data using an attacker-controlled topic while the app believes the request is authentic. Proof idea: minitest computing a real HMAC over `'{}'` with `Context.api_secret_key`, building a `Request` with mismatched shop/topic headers vs. what was 'signed', asserting `Registry.process` invokes the handler with `WebhookMetadata#shop == 'victim-shop.myshopify.com'` despite the HMAC being computed for a different (or no) shop context.
