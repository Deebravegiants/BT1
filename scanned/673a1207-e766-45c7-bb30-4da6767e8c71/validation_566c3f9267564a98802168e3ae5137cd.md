## Analysis

**Vulnerability class**: The reported bug is a Solidity-specific pattern — a wallet contract's internal `_call()` forwards native value via `.call{value: ...}` but the wallet itself (and its modules) lacks a `payable` fallback/`receive()`, so it can never *receive* value even though it's designed to relay it.

**Mapping to polkadot-sdk**: The closest analog is `pallet-revive`, which is Polkadot's EVM-compatible contracts pallet and executes Solidity bytecode with EVM-equivalent semantics. I checked how value transfers and payability are modeled there:

1. Native balance transfers into pallet-revive are handled by the runtime's balance-transfer machinery, not gated by a "payable" Rust attribute the way Solidity gates functions. The dispatchable `call` extrinsic accepts a `value` parameter and transfers it unconditionally to `dest` via `bare_call`/`run_call`, mirroring EVM `CALL` semantics. [1](#0-0) [2](#0-1) 

2. For Solidity contracts *deployed on top of* pallet-revive, the `payable`/`receive()` requirement is faithfully preserved — pallet-revive intentionally emulates EVM call semantics, including reverting a value transfer into a contract with no matching `receive()`/`payable fallback` (or insufficient gas stipend for it), exactly like Ethereum. This is explicitly tested in the `Stipends.sol` fixture, where `ComplexReceiver` (no proper payable path with enough gas) fails to receive funds via `transfer`/`send`, while contracts with `receive() external payable` succeed. [3](#0-2) [4](#0-3) 

3. This is a deliberate design choice, not an oversight: a prior PR reworked balance transfers specifically to make the existential deposit transparent to contracts while preserving EVM-equivalent transfer semantics. [5](#0-4) 

**Conclusion**: The "missing payable/receive" bug class is inherently a Solidity application-contract design defect (the audited wallet forgot to add `payable`/`receive()` to its own contracts). In polkadot-sdk, the equivalent behavior at the pallet-revive protocol level is intentional and spec-compliant EVM emulation — pallet-revive doesn't have an analogous "wallet forgot payable" flaw because value transfers via the `call` extrinsic go through the runtime's balance/Currency system, not through a Solidity-style function-level payable gate. Any occurrence of this pattern would be confined to a *user-deployed* Solidity contract on pallet-revive (an application bug, out of scope for the SDK itself), not a defect in FRAME pallets, runtime primitives, or pallet-revive's own dispatch logic.

Given the disqualification criteria (no reachable attacker-controlled entry path into core protocol code, and the behavior is intentional EVM-equivalence rather than a flaw), there is no valid analog vulnerability to report against this codebase.

```text
title: '[pallet-revive] rework balance transfers'
doc:
- audience: Runtime Dev
  description: |-
    This PR removes the `transfer` syscall and changes balance transfers to make the existential deposit (ED) fully transparent for contracts.

    The `transfer` API is removed since there is no corresponding EVM opcode and transferring via a call introduces barely any overhead.

    We make the ED transparent to contracts by transferring the ED from the call origin to nonexistent accounts. Without this change, transfers to nonexistant accounts will transfer the supplied value minus the ED from the contracts viewpoint, and consequentially fail if the supplied value lies below the ED. Changing this behavior removes the need for contract code to handle this rather annoying corner case and aligns better with the EVM. The EVM charges a similar deposit from the gas meter, so transferring the ED from the call origin is practically the same as the call origin pays for gas.
```
