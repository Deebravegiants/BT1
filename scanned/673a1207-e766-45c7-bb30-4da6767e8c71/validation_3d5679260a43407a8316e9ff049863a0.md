### Title
Donation-based reserve manipulation allows first-LP to capture value from subsequent depositors due to missing LP-token-received slippage protection - (File: substrate/frame/asset-conversion/src/lib.rs)

### Summary
The pool's reserves used in `do_add_liquidity` are read from the *live on-chain balance* of the pool's sovereign account rather than from an internally-tracked accounting value, so anyone can inflate `reserve1`/`reserve2` by simply transferring assets directly to the pool account outside of the pallet's extrinsics. Combined with the fact that `add_liquidity` only exposes `amount1_min`/`amount2_min` (slippage bounds on the *input token amounts*) and not a minimum on the *LP tokens received*, a depositor can be tricked into contributing valuable assets while minting a rounded-down (potentially near-zero) amount of LP shares, letting an earlier/attacker-controlled LP position redeem a disproportionate share of the pool.

### Finding Description
`Pallet::do_add_liquidity` determines pool reserves via `T::Assets::balance(asset, &pool_account)` (the pool account being a deterministic, unprivileged sovereign account derived from the pool id) rather than a pallet-internal ledger. Because that account is a normal `AccountId`, any signed user can call the underlying assets pallet's `transfer` extrinsic to send `asset1`/`asset2` directly to it — completely bypassing `add_liquidity`'s accounting. This "donates" tokens to the pool without minting any LP tokens for the donor.

The LP-minting math is:
- For the first mint (`total_supply == 0`): `lp_token_amount = calc_lp_amount_for_zero_supply(amount1, amount2)`, computed only from the actually-transferred `amount1`/`amount2` in that call — it ignores any pre-existing (donated) balance sitting in the pool account.
- For subsequent mints: `lp_token_amount = min(mul_div(amount1, total_supply, reserve1), mul_div(amount2, total_supply, reserve2))`, where `reserve1`/`reserve2` include any donated balance.

An attacker who mints the first (tiny) amount of LP tokens and then front-runs/precedes a victim's `add_liquidity` call with a large direct donation to the pool account can massively inflate `reserve1`/`reserve2` relative to `total_supply`. When the victim's `add_liquidity(amount1_desired, amount2_desired, amount1_min, amount2_min, ...)` executes, `amount1_min`/`amount2_min` only bound the token amounts actually pulled from the victim — they do **not** bound the number of LP shares minted to the victim. Integer division in `mul_div` can round the victim's minted LP amount down to a negligible value even though their tokens were fully transferred into the pool, so the victim effectively donates value to the pool that the attacker (holding nearly all outstanding, non-burned LP supply) can then reclaim via `do_remove_liquidity`, which pays out `reserve * lp_token_burn / total_supply`.

The pallet's only existing defense is the one-time `MintMinLiquidity` amount permanently minted to the pallet account on the very first mint (mirroring Uniswap V2's dead-share burn), which raises the cost of a pure "self-inflate-then-withdraw" attack against the *pool itself*, but it does not protect a *second, honest* depositor from receiving disproportionately few LP shares once reserves have already been skewed by a direct donation — because there is no corresponding minimum-LP-token-out parameter checked against `lp_token_amount` for that depositor.

### Impact Explanation
An honest liquidity provider's assets can be diverted, in whole or in part, to an earlier LP position without receiving proportional LP tokens in return, because the pallet's slippage protection (`amount1_min`/`amount2_min`) only guards the deposited token amounts, not the LP shares received. This directly violates the invariant that LP token value must be proportional to contributed value and can result in a net transfer of value from a victim depositor to an attacker who has manipulated the pool's reserve ratio via a plain, unprivileged asset transfer to the pool account.

### Likelihood Explanation
The precondition (pool account is a normal, transferable `AccountId` reachable via a standard `Assets::transfer`/`transfer_keep_alive` call) is trivially satisfiable by any unprivileged signed account. The attack requires precise transaction ordering relative to a victim's `add_liquidity` call (i.e., it is a front-running/mempool-timing attack, more easily executed against the very first non-attacker depositor into a freshly created pool, or against any depositor immediately after a large unexpected reserve donation). Repeatability is limited to windows where reserves can be skewed right before a victim transaction lands, making it opportunistic rather than continuously exploitable against a mature, high-liquidity pool.

### Recommendation
- Add an explicit minimum LP-token-output parameter to `add_liquidity`/`do_add_liquidity` (analogous to `amount1_min`/`amount2_min`) and `ensure!(lp_token_amount >= lp_token_min, ...)`.
- Alternatively/additionally, track reserves internally in pallet storage instead of trusting the live balance of the pool account, so direct "donation" transfers cannot be used to manipulate the ratio used for LP minting math.

### Proof of Concept
Integration test plan (Rust, using the pallet's existing mock runtime):
1. `create_pool(attacker, asset1, asset2)`.
2. `attacker` calls `add_liquidity` with minimal `amount1_desired`/`amount2_desired` (e.g. just above `MintMinLiquidity` threshold) to become the sole LP; record `lp_token_amount_attacker` and `total_supply`.
3. `attacker` calls `Assets::transfer` to send a large amount of `asset1` and `asset2` directly to `Pallet::<T>::get_pool_account(pool_id)`, bypassing `add_liquidity`.
4. `victim` calls `add_liquidity` with a substantial `amount1_desired`/`amount2_desired` and reasonable `amount1_min`/`amount2_min` (satisfied because full token amounts are transferred); assert the resulting minted LP amount for `victim` (`Assets::balance(lp_token, victim)` delta) is disproportionately small relative to the value they contributed (e.g., near zero due to rounding).
5. `attacker` calls `remove_liquidity` burning their LP tokens; assert `attacker` receives back more `asset1`+`asset2` value than they originally deposited (donation + original stake), while `victim`'s redeemable share (`lp_token_amount_victim * reserves / total_supply`) is less than what they deposited.
