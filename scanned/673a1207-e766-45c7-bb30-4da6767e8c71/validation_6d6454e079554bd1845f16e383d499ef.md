### Title
`refund_surplus`'s holding-overflow "buy-back" fallback always fails and permanently burns the attacker's already-collected fee instead of refunding or crediting it - (File: `polkadot/xcm/xcm-executor/src/lib.rs`)

### Summary
When `RefundSurplus` cannot merge the refund into `holding` because `ensure_can_subsume_assets` fails, `XcmExecutor::refund_surplus` tries to "undo" the refund by calling `self.trader.buy_weight(...)` again to push the credit back into the trader. For `cumulus_primitives_utility::TakeFirstAssetTrader`, this call is guaranteed to fail (`XcmError::NotWithdrawable`) because `buy_weight`'s re-entrancy guard (`outstanding_credit.is_some()`) is still `true` at that point (the prior `refund_weight` call never clears `outstanding_credit`, it only `extract`s from it). The failed `Result` is discarded with `let _ = ... .defensive_proof(...)`, so the `AssetsInHolding` containing the extracted fee credit is dropped and its underlying `fungibles::Credit` imbalance is destroyed (its `OnDropCredit`/issuance-decrease path fires) instead of being returned to the user, put in holding, or forwarded to `OnUnbalanced`.

### Finding Description
- `TakeFirstAssetTrader::buy_weight` guards against double entry: [1](#0-0) 
- `TakeFirstAssetTrader::refund_weight` extracts from the existing `outstanding_credit` but never resets it to `None`: [2](#0-1) 
- `XcmExecutor::refund_surplus` checks whether the refund asset can be subsumed into `holding` via `ensure_can_subsume_assets`; if not, it attempts to "buy back" the weight to restore consistency, assuming this call cannot fail (`defensive_proof("refund_weight returned an asset capable of buying weight; qed")`): [3](#0-2) 
- `Defensive::defensive_proof` for `Result` only logs and returns the original `Err` unchanged; it does not recover or reinsert the value: [4](#0-3) 

Because `refund_weight` never sets `outstanding_credit` back to `None` (it only reduces the balance inside the `Some` via `extract`), the subsequent `buy_weight` call inside the "buy back" branch always hits the "we don't enter twice" guard and returns `Err((refund, XcmError::NotWithdrawable))`. The code binds this to `let _ = ...`, discarding the tuple — including the `AssetsInHolding` (`refund`) that carries the actual `fungibles::Credit` imbalance that had already been withdrawn from the user during the original `BuyExecution`/`PayFees`. Dropping this `AssetsInHolding` drops the boxed `ImbalanceAccounting` credit, which (per the `fungibles::Balanced` `OnDropCredit` contract used throughout this codebase, e.g. `fungibles::DecreaseIssuance`) decreases total issuance — i.e. it burns the funds rather than crediting them to the user, to holding, or to any `OnUnbalanced` fee-revenue handler.

Trigger path: an unprivileged account can call `pallet_xcm::execute` (or send a message processed by the same `XcmExecutor`) with a self-authored program that:
1. Withdraws/holds enough distinct fungible asset IDs (e.g., via multiple `WithdrawAsset`/`ReceiveTeleportedAsset` on assets the attacker owns, such as permissionlessly-created `pallet-assets` assets) to bring `holding.len()` to the point where `ensure_can_subsume_assets(1)` fails for a *new* asset ID not yet in holding.
2. Issues `BuyExecution`/`PayFees` with a *different* fee asset (not already present in holding) whose amount slightly exceeds `Fungibles::minimum_balance`, so `TakeFirstAssetTrader::buy_weight` accepts it and sets `outstanding_credit`.
3. Consumes only a fraction of the weight purchased, so `total_surplus > total_refunded` when `RefundSurplus` runs.
4. Calls `RefundSurplus`. Since the fee-asset ID is not already a key in `holding.fungible` and holding is already near `2 * holding_limit`, `ensure_can_subsume_assets(1)` fails, triggering the buy-back branch, which always fails and silently drops/burns the refund credit.

No existing check stops this: `ensure_can_subsume_assets` is only an overflow guard for holding, not a correctness check for the trader's re-entry semantics; `TakeFirstAssetTrader`'s "only called once" invariant was never intended to be violated by the executor's own recovery path, but the recovery path violates it every time it is exercised — so the fallback is effectively dead code that always discards value.

### Impact Explanation
The attacker (or any user hitting this holding-capacity edge case, even accidentally) permanently loses the fee amount corresponding to `current_surplus` weight that should have been refunded back into `holding` (and ultimately to the user via `DepositAsset`). The funds are neither returned to the user nor credited to the chain's fee-revenue account (`OnUnbalanced`); they are burned via the imbalance drop-issuance-decrease path. This is a real, un-recoverable value-destruction bug — user funds that were already debited are destroyed instead of being fully backed/returned, violating the "user-controlled assets must remain fully backed" invariant. It also causes the current instruction to fail with `XcmError::HoldingWouldOverflow`, aborting the remainder of the program (subject to error handler/appendix), compounding the unexpected loss.

### Likelihood Explanation
Reaching this requires the attacker to fill `holding` to more than `2 * MaxAssetsIntoHolding` distinct asset entries using only their own funds (feasible on chains like Asset Hub where users can permissionlessly create many distinct `pallet-assets` asset IDs with minimal balances) and to use a fee asset ID not already present in holding for `BuyExecution`/`PayFees`. This is entirely constructible by an unprivileged signed account via `pallet_xcm::execute`, with no privileged origin, proxy, or admin action needed. The complexity is moderate (crafting an XCM program with many distinct assets and precise weight bookkeeping) but fully within reach of a determined attacker or can occur unintentionally for any user with many distinct asset holdings, making it repeatable and chain-agnostic wherever `TakeFirstAssetTrader` is the configured `Trader`.

### Recommendation
Fix the "buy back" recovery path in `XcmExecutor::refund_surplus` so it does not rely on `WeightTrader::buy_weight`'s re-entrancy check. Either:
- Add a dedicated `WeightTrader` method (e.g. `restore_refund` / `un_refund`) that reinserts a previously extracted amount back into `outstanding_credit` without going through the "already bought" guard, or
- Have `TakeFirstAssetTrader::refund_weight` not mutate `outstanding_credit` until the caller confirms the refund was successfully placed into holding (i.e., make the extraction transactional/reversible), or
- In `refund_surplus`, when the buy-back fails, explicitly route the discarded `refund` assets to `Config::FeeManager::handle_fee` (or an equivalent trap/claim mechanism) instead of silently dropping them, so funds are at minimum treated as legitimate fee revenue rather than burned.

### Proof of Concept
xcm-executor integration test (in `polkadot/xcm/xcm-executor/src/tests/`) using `TakeFirstAssetTrader`:
1. Configure `MaxAssetsIntoHolding` to a small value (e.g. 2) for a fast-to-construct test.
2. Build an XCM: `WithdrawAsset` of `holding_limit` distinct asset IDs (asset A, asset B) to fill holding to `holding_limit`.
3. `BuyExecution` using asset C (not A or B) with `amount = minimum_balance(C) + X`, weight limit `W`.
4. A `Transact`/no-op instruction consuming less than `W` so `total_surplus > 0` after execution.
5. `RefundSurplus`.
6. Assertions:
   - Program instruction for `RefundSurplus` returns `Err(XcmError::HoldingWouldOverflow)`.
   - `holding` does not contain any of asset C (refund never added).
   - Total issuance of asset C after execution equals `initial_issuance - X_consumed_fee - surplus_amount` (i.e., the surplus portion has been additionally burned/decreased from issuance), proving the surplus amount vanished rather than being refunded to the user or credited via `OnUnbalanced`/`FeeManager`.
   - Compare against expected correct behavior: total issuance should only decrease by the amount of fee actually consumed (`total_surplus`-adjusted), not by the full `buy_weight` amount.

		let current_surplus = self.total_surplus.saturating_sub(self.total_refunded);
		tracing::trace!(
			target: "xcm::refund_surplus",
			total_surplus = ?self.total_surplus,
			total_refunded = ?self.total_refunded,
			?current_surplus,
			"Refunding surplus",
		);
		if current_surplus.any_gt(Weight::zero()) {
			if let Some(refund) = self.trader.refund_weight(current_surplus, &self.context) {
				// Check if adding the refund would overflow holding. This can happen if the
				// refund asset is not already in holding and holding is at max capacity.
				if refund
					.fungible
					.first_key_value()
					.map(|(id, _)| {
						!self.holding.fungible.contains_key(id) &&
							self.ensure_can_subsume_assets(1).is_err()
					})
					.unwrap_or(false)
				{
					// Can't add refund to holding - undo by buying back the weight.
					// This returns the refund credit to the trader where it will be
					// handled by OnUnbalanced when the trader is dropped.

						.trader
						.buy_weight(current_surplus, refund, &self.context)
						.defensive_proof(
							"refund_weight returned an asset capable of buying weight; qed",
						);
					tracing::error!(
						target: "xcm::refund_surplus",
						"error: HoldingWouldOverflow",
					);
					return Err(XcmError::HoldingWouldOverflow);
				}
