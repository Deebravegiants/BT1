### Title
Weight-exhausted XCMP page processing silently drops legitimate inbound HRMP messages without retry - (cumulus/pallets/xcmp-queue/src/lib.rs, cumulus/pallets/parachain-system/src/lib.rs)

### Summary
`Pallet::handle_xcmp_messages` shares one `WeightMeter` across *all* senders' inbound HRMP pages processed in a single relay-parent inherent call. If an earlier-ordered sender exhausts that meter (e.g., via a large but within-channel-limits page), any subsequent sender's page in the same call is dropped outright (`continue`/`break` on `try_consume` failure) with only a `defensive!` log and no re-enqueue. Because the parachain's own `HrmpWatermark` is advanced based on which messages were *included* in the inherent — not whether `xcmp-queue` actually enqueued them — the relay chain later prunes those messages from `HrmpChannelContents` via `prune_hrmp`, so they are never resent.

### Finding Description
`handle_xcmp_messages` creates a single `WeightMeter::with_limit(max_weight)` for the whole call [1](#0-0) , and iterates over `(sender, sent_at, data)` tuples for *every* sender that has inbound HRMP data in that relay block. When the meter runs out mid-page (`try_consume` fails for `uncached_enqueue_xcmp_messages`, `take_first_concatenated_xcm`, or inside `enqueue_xcmp_messages`), the code simply `continue`s to the next sender or stops decoding the rest of the current page, logging only a `defensive!` message: [2](#0-1) . The remaining bytes of that page — and thus the messages they encode — are never enqueued into `T::XcmpQueue`, and no backpressure (`InboundXcmpSuspended`) is triggered, because `on_queue_changed` is only invoked from a successful `enqueue_messages` call, which never happens for the dropped remainder.

Crucially, the raw page bytes are still consumed from the iterator (they were already extracted from the inherent by `enqueue_inbound_horizontal_messages`), and the watermark computation happens *before* `handle_xcmp_messages` is even called, purely from message metadata (`sent_at`), independent of the handler's success: [3](#0-2) . The relay chain's `hrmp::Pallet::prune_hrmp` then removes all `HrmpChannelContents` messages up to the submitted watermark unconditionally [4](#0-3) . Once pruned, the dropped messages cannot be resent — they are permanently lost.

Ordering of senders within a relay block is deterministic and only partially attacker-influenced: `InboundHrmpMessages::from_map` sorts messages by `(sent_at, sender ParaId ascending)` [5](#0-4) . An attacker with a numerically-lower `ParaId` than the victim, and an HRMP channel large enough (within governance-configured `max_capacity`/`max_total_size`) to submit enough messages to exhaust `ReservedXcmpWeight` in one relay block, can cause every message from higher-ParaId senders in that same relay block to be silently and permanently dropped.

### Impact Explanation
Legitimate XCM messages (including asset-transfer / DOT-moving XCMs) from a victim sibling parachain can be permanently and silently discarded without ever executing, without the sender being notified, without channel suspension/backpressure, and without any possibility of relay-chain-level retransmission (the HRMP watermark has already advanced past them). This is fund-affecting message loss triggered purely by an unprivileged sibling parachain crafting an oversized (but protocol-legal, within its own channel's configured capacity) inbound page.

### Likelihood Explanation
Preconditions are non-trivial but realistic: the attacker needs (1) an open HRMP channel to the victim parachain (or shares the same block-processing budget as one — actually the attacker only needs an HRMP channel to *this* parachain, sending in the same relay block as the victim), (2) a numerically lower `ParaId` than the intended victim, and (3) enough channel capacity/message-size budget to fill up `ReservedXcmpWeight` for that block, which is a fixed, config-driven fraction of block weight (not scaled to total inbound volume across all channels). This is fully reachable through the normal HRMP/XCMP transport (attacker just needs to actually be a registered parachain able to send HRMP messages), requiring no privileged origin — it is a standing design property of shared, per-block weight metering across senders processed in one call, and the drop path is explicitly acknowledged (but not fully mitigated) in code via `defensive!` comments like "page will be dropped".

### Recommendation
- Do not advance `HrmpWatermark` past messages that `handle_xcmp_messages` failed to fully process/enqueue due to weight exhaustion; either fail the block or persist the residual undecoded bytes so they can be retried on the next block instead of being pruned by the relay chain.
- Alternatively, make weight accounting per-sender rather than a single shared meter across the whole `iter`, so one sender's oversized page cannot cannibalize the weight budget of other senders processed in the same call.
- When a page is dropped due to `can_process_next_batch=false` or meter exhaustion, trigger inbound channel suspension (`InboundXcmpSuspended`)/signal to force the sender to resend, instead of silently continuing.

### Proof of Concept
Rust unit test in `cumulus/pallets/xcmp-queue/src/tests.rs`:
1. Configure `ReservedXcmpWeight`/mock `WeightMeter` limit to a small value.
2. Build an `iter` yielding two senders' pages in ascending ParaId order: sender A (ParaId=1, attacker) with a page containing many small XCM messages sized to consume nearly all of `max_weight`; sender B (ParaId=2, victim) with a single legitimate XCM message.
3. Call `Pallet::<Test>::handle_xcmp_messages(iter, max_weight)`.
4. Assert that sender B's message never appears in `T::XcmpQueue`'s enqueued messages (`EnqueuedMessages` mock storage), proving silent drop.
5. Assert that `InboundXcmpSuspended` does NOT contain sender B (proving no proper backpressure/retry was triggered), demonstrating the invariant violation ("no legitimate enqueued message should be silently dropped without being retried/suspended safely").

	pub(crate) fn prune_hrmp(recipient: ParaId, new_hrmp_watermark: BlockNumberFor<T>) {
		// sift through the incoming messages digest to collect the paras that sent at least one
		// message to this parachain between the old and new watermarks.
		let senders = HrmpChannelDigests::<T>::mutate(&recipient, |digest| {
			let mut senders = BTreeSet::new();
			let mut leftover = Vec::with_capacity(digest.len());
			for (block_no, paras_sent_msg) in mem::replace(digest, Vec::new()) {
				if block_no <= new_hrmp_watermark {
					senders.extend(paras_sent_msg);
				} else {
					leftover.push((block_no, paras_sent_msg));
				}
			}
			*digest = leftover;
			senders
		});

		// having all senders we can trivially find out the channels which we need to prune.
		let channels_to_prune =
			senders.into_iter().map(|sender| HrmpChannelId { sender, recipient });
		for channel_id in channels_to_prune {
			// prune each channel up to the new watermark keeping track how many messages we removed
			// and what is the total byte size of them.
			let (mut pruned_cnt, mut pruned_size) = (0, 0);

			let contents = HrmpChannelContents::<T>::get(&channel_id);
			let mut leftover = Vec::with_capacity(contents.len());
			for msg in contents {
				if msg.sent_at <= new_hrmp_watermark {
					pruned_cnt += 1;
					pruned_size += msg.data.len();
				} else {
					leftover.push(msg);
				}
			}
			if !leftover.is_empty() {
				HrmpChannelContents::<T>::insert(&channel_id, leftover);
			} else {
				HrmpChannelContents::<T>::remove(&channel_id);
			}

			// update the channel metadata.
			HrmpChannels::<T>::mutate(&channel_id, |channel| {
				if let Some(ref mut channel) = channel {
					channel.msg_count -= pruned_cnt as u32;
					channel.total_size -= pruned_size as u32;
				}
			});
		}

		HrmpWatermarks::<T>::insert(&recipient, new_hrmp_watermark);

impl InboundHrmpMessages {
	// Prepare horizontal messages for a more convenient processing:
	//
	// Instead of a mapping from a para to a list of inbound HRMP messages, we will have a
	// list of tuples `(sender, message)` first ordered by `sent_at` (the relay chain block
	// number in which the message hit the relay-chain) and second ordered by para id
	// ascending.
	pub fn from_map(messages_map: BTreeMap<ParaId, Vec<InboundHrmpMessage>>) -> Self {
		let mut messages = messages_map
			.into_iter()
			.flat_map(|(sender, channel_contents)| {
				channel_contents.into_iter().map(move |message| (sender, message))
			})
			.collect::<Vec<_>>();
		messages.sort_by(|(sender_a, msg_a), (sender_b, msg_b)| {
			// first sort by sent-at and then by the para id
			(msg_a.sent_at, sender_a).cmp(&(msg_b.sent_at, sender_b))
		});

		Self { messages }
	}
