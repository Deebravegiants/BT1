## Analysis: Fee Payment Independent of Delivery Success in Snowbridge Outbound Queue V2

### Finding

The vulnerability pattern from the report — a relayer/postman being able to claim delivery fees while the message delivery actually fails — has a direct analog in `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`.

### Title
Relayer reward paid regardless of message dispatch success on Ethereum - (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
The `DeliveryReceipt` type explicitly carries a `success: bool` field decoded from the Ethereum `InboundMessageDispatched` event, indicating whether the message was actually dispatched successfully on the destination side. [1](#0-0) 
However, `process_delivery_receipt` never reads or checks this field before paying the relayer reward — the reward is paid unconditionally as long as a `PendingOrder` exists and `order.fee > 0`. [2](#0-1) 

### Finding Description
`process_delivery_receipt` fetches the `PendingOrder` for the given `nonce` and pays `order.fee` to the reward account whenever `order.fee > 0`: [3](#0-2) 
The `receipt.success` value — which is the authoritative on-chain (Ethereum) record of whether the inbound message was actually dispatched successfully by the Gateway contract — is completely unused in this reward path. This mirrors the report's core issue exactly: a "postman" (here, the relayer submitting the delivery receipt) can collect fees/rewards for a delivery that did not actually complete successfully, because the pallet's accounting logic checks only that a receipt/proof was submitted, not that the underlying operation succeeded.

### Impact Explanation
Any relayer who submits a valid delivery receipt (proof of the `InboundMessageDispatched` event, verified via the light client/verifier) is rewarded the full `order.fee`, even in cases where `success == false` (e.g., insufficient gas or reverted execution on the destination side). This breaks the intended incentive alignment where reward should reflect successful message delivery, potentially draining reward funds for deliveries that did not actually apply the intended cross-chain effect.

### Likelihood Explanation
This does not require any privileged role compromise — any registered relayer submitting message deliveries to Ethereum can trigger this path, and the reward payment is unconditional on `order.fee > 0` in the current code. The exact conditions under which `success` can be `false` while the receipt is still valid (e.g., relayer controlling gas parameters passed to the Gateway contract on Ethereum) could not be fully verified from this repository alone, since the Ethereum-side Gateway contract logic controlling how/why `success` is set is out of scope for this Rust codebase. This is a limitation of the analysis — the Solidity Gateway contract logic that emits `InboundMessageDispatched` is not present in this repo, so I cannot confirm to what extent a relayer can deliberately induce `success=false` at will (analogous to the Linea "sub-call gas starving" scenario) versus it purely reflecting message content errors unrelated to relayer behavior.

### Recommendation
Check `receipt.success` in `process_delivery_receipt` before paying the reward (or route to a reduced/zero reward path when `success == false`), so relayer compensation is conditioned on the message actually having been dispatched successfully on the destination chain, consistent with the field's stated purpose.

### Proof of Concept
Not independently reproducible from the indexed contents of this repo — the existing integration tests (`cumulus/parachains/integration-tests/emulated/tests/bridges/bridge-hub-westend/src/tests/snowbridge_v2_outbound.rs`, lines 496–513 and 676–693) only exercise the `success: true` receipt path. [4](#0-3) 
I located references to `success: false`/edge cases in `snowbridge_v2_outbound_edge_case.rs` and `snowbridge_v2_outbound_from_rococo.rs` but was unable to read their full contents in the remaining tool budget to confirm whether they assert reward is (incorrectly) still paid on failure — this should be verified directly in a full checkout of the repository, as the wiki-indexed content may be incomplete for these files.

```rust
		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```
