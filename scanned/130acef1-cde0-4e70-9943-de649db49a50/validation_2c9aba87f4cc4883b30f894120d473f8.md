### Title
User-selected identifier allows front-running of collection/asset creation, causing griefing DoS - (File: `substrate/frame/uniques/src/lib.rs`)

### Summary
`pallet-uniques`'s public `create` extrinsic lets the caller pick an arbitrary `CollectionId`, which is only checked for prior existence (`InUse`) before insertion. Any account watching the transaction pool can observe a pending `create(collection, admin)` call and resubmit the identical `collection` id with a higher tip, causing the original submitter's transaction to fail with `Error::InUse`. This is the exact vulnerability pattern described in the external report (user-chosen `loanId` that reverts on collision), applied to a FRAME pallet whose extrinsic is reachable by any signed account.

### Finding Description
`Pallet::create` in `pallet-uniques` accepts a caller-supplied `collection: T::CollectionId` and forwards it unmodified to `do_create_collection`: [1](#0-0) 

`do_create_collection` performs only a "not currently in use" check before inserting the new collection, with no binding between `collection` and the calling account (`CreateOrigin` is only checked against the id via `ensure_origin`, which in the common permissionless configuration — `AsEnsureOriginWithArg<EnsureSigned<AccountId>>` — does not constrain which id a signed account may claim): [2](#0-1) 

This mirrors the root cause in the external report: `LoanManager.createUserLoan` also only checks `isUserLoanActive(loanId)` before insertion, with the id fully attacker-observable and attacker-selectable ahead of the victim's transaction landing.

`pallet-assets` has the equivalent structural issue in its `create` extrinsic: unless `Config::AssetIdAllocator` is configured to enforce a strict auto-increment sequence, the pallet accepts any caller-chosen `id` and only checks `InUse`: [3](#0-2) 

The pallet's own configuration trait documents that `AssetIdAllocator = ()` "leaves `create` unconstrained" — i.e. accepts any id not currently in use, which is the exact vulnerable mode: [4](#0-3) 

Note that Parity has already recognized and partially mitigated this class of issue for `pallet-assets` by introducing `AssetIdAllocator`/`AutoIncAssetId`, which — when configured (e.g. `NextAssetId` auto-increment) — removes attacker control over the id entirely: [5](#0-4) 

`pallet-uniques`, however, has no such mitigation: it has always used a purely caller-chosen `CollectionId` with no allocator abstraction, and is still present and buildable in this repo (it is a legacy/soon-to-be-deprecated pallet, but not removed, and runtimes may still include it).

### Impact Explanation
Any signed account satisfying `CreateOrigin` can grief legitimate collection creators on chains with a public mempool by monitoring for `Uniques::create` calls and resubmitting the same `collection` id with higher priority/tip, causing the victim's extrinsic to fail deterministically with `Error::<T, I>::InUse`. This is a pure griefing/DoS vector with no profit motive required from the attacker, exactly matching the "Griefing" impact category in the original report — it can be automated to block essentially all collection creation on an affected chain. The same applies to `pallet-assets::create` for any runtime that leaves `AssetIdAllocator` unconstrained (`()`).

### Likelihood Explanation
Likelihood is bounded by two factors: (1) the parachain/relay chain must expose a public mempool where the pending extrinsic and its `collection`/`id` parameter are visible before inclusion — true for most Substrate chains without private transaction pools; and (2) `CreateOrigin` must be configured permissively enough (e.g. `AsEnsureOriginWithArg<EnsureSigned<AccountId>>`) that any signed account can claim any id, which is a common test/mock configuration and plausible for some production configurations that don't tie the id to the account. Where `AssetIdAllocator` is configured with `AutoIncAssetId` (as in the newer `pallet-assets` design) or where NFT collection IDs are always chain-assigned (as in `pallet-nfts`'s default `create` using `NextCollectionId`), the analog does not apply — this narrows real-world exposure primarily to `pallet-uniques` deployments and any `pallet-assets` deployment still using `AssetIdAllocator = ()`.

### Recommendation
- For `pallet-uniques`: derive `CollectionId` from an internal auto-incrementing counter (as `pallet-nfts` already does via `NextCollectionId`) instead of accepting a fully caller-chosen id, or bind the allowed id space to the caller (e.g., a per-account namespace) so front-running cannot succeed.
- For `pallet-assets`: ensure runtime configurations always set `Config::AssetIdAllocator` to an enforcing allocator (e.g. `AutoIncAssetId`) for the permissionless `create` call rather than `()`, closing the unconstrained id-selection path.
- More generally, avoid public extrinsics that let an unprivileged caller select a shared, globally-unique identifier that is merely checked for collision at insertion time; prefer pallet-managed sequential/deterministic ids for any object created via a signed, permissionless call.

### Proof of Concept
1. Alice (attacker) monitors the transaction pool for pending `Uniques::create(collection = X, admin = Bob)` calls.
2. Alice submits `Uniques::create(collection = X, admin = Alice)` with a higher tip; it is included first, calling `do_create_collection` which succeeds because `Collection::<T,I>::contains_key(X)` is false at that point (`substrate/frame/uniques/src/functions.rs:92`).
3. Bob's original transaction is then executed and reverts with `Error::<T, I>::InUse` because `Collection::<T,I>::contains_key(X)` is now true.
4. Alice repeats this for every observed `create` call with a new user-chosen `collection` id, indefinitely denying any user the ability to create a collection with their intended id — analogous to the provided PoC against `LoanManager.createUserLoan` in the external report.
