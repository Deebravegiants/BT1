## Title
Unauthenticated Login Endpoint Leaks Distinct "Invalid email" vs "Invalid password" Errors, Enabling User Email Enumeration - (File: core/sessions/localauth/orm.go)

### Summary
The Operator UI login endpoint (`POST /sessions`, handled by `SessionsController.Create`) returns the raw error produced by `AuthenticationProvider().CreateSession`, which explicitly distinguishes between "email not registered" and "email registered but password wrong." An unauthenticated caller can submit arbitrary emails and use the differing error text to enumerate which emails have accounts on the node, the same bug class (CWE-203/204) as the referenced CI4MS advisory, just manifesting on the login flow instead of the password-reset flow.

### Finding Description
`CreateSession` in the local authentication ORM performs the checks in this explicit order and returns two different, static error strings depending on which check fails: [1](#0-0) 

- If the submitted email does not match a real user record, it returns `"Invalid email"` and logs `audit.AuthLoginFailedEmail`.
- If the email is valid but the password is wrong, it returns `"Invalid password"` and logs `audit.AuthLoginFailedPassword`.

This error is propagated verbatim to the HTTP client without normalization: [2](#0-1) 

The `jsonAPIError` call surfaces the underlying error message/detail in the JSON:API response body, so a client sees `"Invalid email"` for one class of input and `"Invalid password"` for another, both with the same `401 Unauthorized` HTTP status code — an unambiguous behavioral oracle for account existence.

The same enumeration pattern (`"invalid email"` vs `"invalid password"`, with matching distinct audit events) exists in the LDAP and OIDC local-login fallback paths as well: [3](#0-2) [4](#0-3) 

Notably, the code even contains a comment acknowledging the enumeration risk for MFA/WebAuthn state ("Do email and password check first to prevent extra database look up for MFA tokens leaking if an account has MFA tokens or not"), but no equivalent care was taken for the email-vs-password distinction itself — the exact discrepancy is preserved and returned to the caller.

### Impact Explanation
This is a direct, unauthenticated user/email enumeration vulnerability on the node's own login endpoint. It allows an attacker to build a list of valid Chainlink node operator accounts, which can be leveraged for targeted credential-stuffing, phishing, or brute-force attacks against confirmed-valid accounts — consistent with CWE-203/204 and the medium-severity classification of the referenced advisory. It does not by itself grant authentication bypass or fund movement, but it materially lowers the cost of a follow-on credential attack against the node's admin/operator accounts.

### Likelihood Explanation
The endpoint is reachable pre-authentication (`POST /sessions`) by any network client able to reach the Operator UI/API port. Exploitation requires no special privileges — only sending JSON bodies with different candidate emails and observing the returned error string. The main mitigating factor is the existing unauthenticated rate limit (`WebServer.RateLimit.Unauthenticated = 5` requests per `UnauthenticatedPeriod = '20s'` by default), which slows but does not prevent enumeration.

### Recommendation
Return a single, generic authentication failure message/response (e.g., "invalid email or password") and a single audit event category for both "unknown email" and "wrong password" cases in `CreateSession` across the local, LDAP, and OIDC providers, matching timing where feasible (e.g., always compute a password hash comparison even for unknown emails) so that response content and timing do not reveal account existence.

### Proof of Concept
1. `POST /sessions` with `{"email":"unknown@example.com","password":"x"}` → HTTP 401 with error containing `"Invalid email"`.
2. `POST /sessions` with `{"email":"<real-admin-email>","password":"wrongpass"}` → HTTP 401 with error containing `"Invalid password"`.
3. The differing error text between steps 1 and 2 confirms `<real-admin-email>` is a registered account on the node, without any valid credentials. [5](#0-4) [6](#0-5)

func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}
