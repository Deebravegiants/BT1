Based on my investigation, the strongest analog to the `AffiliateValidator` key-reuse bug (a signature scoped only to salt/operator but not to the specific contract instance, allowing cross-instance replay) is the workflow-trigger JWT authorization path in the gateway, where the signed digest binds only to the JSON-RPC *request* content and never to the specific `workflowID` being authorized against, or to any DON/shard identity.

### Title
Trigger-authorization JWT signature is not bound to the target `workflowID`, enabling cross-workflow signature reuse - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` verifies a caller-supplied JWT via `utils.VerifyRequestJWT`, which only checks that the signature covers the JSON-RPC request body/digest, replay (`jti`), and expiry [1](#0-0) . Neither the signed JWT claims nor `req.Digest()` bind the signature to the `workflowID` parameter that `Authorize` uses to look up the authorized-keys set [2](#0-1) . This mirrors the `AffiliateValidator` flaw: a signature valid for one "instance" (there: contract address; here: `workflowID`) can be replayed against a different instance as long as the underlying request body is identical or can be crafted to match.

### Finding Description
`utils.CreateRequestJWT`/`utils.VerifyRequestJWT` compute `JWTClaims.Digest` from `req.Digest()` where `req` is the generic JSON-RPC request (`Method`, `Params`, `ID`, etc.), and sign that together with `jti`, `iss`, `exp`, `iat` [3](#0-2) [4](#0-3) . The `workflowID` used to select the authorized-key set in `Authorize` comes from a separate, unsigned parameter passed by the caller/handler (`h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)` in `http_trigger_handler.go`) [5](#0-4) , and `resolveWorkflowID` derives `workflowID` from user-supplied, unsigned fields (`workflow.WorkflowID`, or the owner/name/tag triple) inside `req.Params` [6](#0-5) . Because the trigger request's `Params.Workflow` selector, `Params.Input`, `ID`, and `Method` can be identical for two different workflows that a given signer key is authorized on, or because `req.Digest()` may not cryptographically bind the resolved `workflowID` at all, a signature obtained (or intercepted) for use against workflow A's authorized key can potentially be replayed to authorize a trigger for workflow B whose authorized-key set the attacker does not otherwise control — exactly analogous to reusing an `AffiliateValidator` key signed for one contract instance against a different instance.

### Impact Explanation
If exploitable, this would let an unprivileged caller invoke `workflows.execute` triggers against a `workflowID` other than the one implicitly intended by the signer, bypassing the per-workflow `authorizedKeys` gate enforced in `Authorize` [2](#0-1) . This is an authorization-bypass / cross-workflow request impersonation on the internet-facing gateway HTTP trigger path.

### Likelihood Explanation
Exploitability depends on whether `req.Digest()` (from `jsonrpc.Request[T]`) sufficiently and uniquely commits to the resolved `workflowID` for every code path in `resolveWorkflowID`/`validatedTriggerRequest`. I could not fully verify the implementation of `req.Digest()` (it lives in the `chainlink-common` dependency, outside this repo's index) to confirm whether it already includes the workflow selector fields in a way that prevents cross-workflow reuse. This is the key uncertainty limiting confidence in this finding — without seeing `Digest()`'s exact field coverage, I cannot definitively confirm the bypass is live rather than already mitigated by construction (e.g., if `Params.Workflow` is always included in the digest, cross-workflow reuse would require an owner/name/tag collision, which is a much narrower window).

### Recommendation
Explicitly bind the JWT's signed claims to the resolved `workflowID` (and/or the gateway/DON identity), e.g., include `workflowID` as a required claim field validated in `VerifyRequestJWT`/`Authorize`, rather than relying solely on the generic JSON-RPC request digest to implicitly cover it. This directly mirrors the Augur fix pattern of embedding the target contract's address in the signed hash.

### Proof of Concept
Not independently verifiable without access to `jsonrpc.Request[T].Digest()`'s implementation (external dependency, not present in this repo's index) and without a live environment to test whether two distinct `workflowID`s can produce colliding/reusable signed digests. A Devin session with full repo/dependency access and ability to run tests would be needed to confirm whether `Digest()` covers `Params.Workflow` fields for all trigger-request shapes.

func CreateRequestJWT[T any](req jsonrpc.Request[T], opts ...Option) (*jwt.Token, error) {
	// Apply options
	options := &jwtOptions{}
	for _, opt := range opts {
		opt(options)
	}

	expiryDuration := maxJWTExpiryDuration
	if options.expiryDuration != nil {
		expiryDuration = *options.expiryDuration
	}

	digest, err := req.Digest()
	if err != nil {
		return nil, err
	}

	var issuer string
	if options.issuer != nil {
		issuer = *options.issuer
	}

	var subject string
	if options.subject != nil {
		subject = *options.subject
	}

	var audience []string
	if options.audience != nil {
		audience = options.audience
	}

	now := time.Now()
	jti := uuid.New().String()

	claims := JWTClaims{
		Digest: "0x" + digest,
		RegisteredClaims: jwt.RegisteredClaims{
			ID:        jti,
			Issuer:    issuer,
			Subject:   subject,
			Audience:  jwt.ClaimStrings(audience),
			ExpiresAt: jwt.NewNumericDate(now.Add(expiryDuration)),
			IssuedAt:  jwt.NewNumericDate(now),
		},
	}

	return jwt.NewWithClaims(&SigningMethodEth{}, claims), nil
}

func (h *httpTriggerHandler) resolveWorkflowID(ctx context.Context, triggerReq *jsonrpc.Request[gateway_common.HTTPTriggerRequest], requestID string, callback handlers.Callback) (string, error) {
	h.lggr.Debugw("resolving workflow ID", "workflowID", triggerReq.Params.Workflow.WorkflowID, "workflowOwner", triggerReq.Params.Workflow.WorkflowOwner, "workflowName", triggerReq.Params.Workflow.WorkflowName, "workflowTag", triggerReq.Params.Workflow.WorkflowTag, "requestID", requestID)
	workflowID := triggerReq.Params.Workflow.WorkflowID
	if workflowID != "" {
		workflowID = normalizeHex(workflowID, workflowIDLength)
		_, found := h.workflowMetadataHandler.GetWorkflowReference(workflowID)
		if !found {
			h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, fmt.Sprintf("Workflow not found. 'workflowID' %s is not a valid workflow ID", workflowID), callback)
			return "", errors.New("workflow not found")
		}
		return workflowID, nil
	}
	workflowOwner := normalizeHex(triggerReq.Params.Workflow.WorkflowOwner, workflowOwnerLength)
	workflowName := "0x" + hex.EncodeToString([]byte(workflows.HashTruncateName(triggerReq.Params.Workflow.WorkflowName)))
	workflowID, found := h.workflowMetadataHandler.GetWorkflowID(
		workflowOwner,
		workflowName,
		triggerReq.Params.Workflow.WorkflowTag,
	)
	if !found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "Workflow not found. Provide either a valid 'workflowID' or a valid combination of 'workflowOwner', 'workflowName', and 'workflowTag'", callback)
		return "", errors.New("workflow not found")
	}
	return workflowID, nil
}

func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}
