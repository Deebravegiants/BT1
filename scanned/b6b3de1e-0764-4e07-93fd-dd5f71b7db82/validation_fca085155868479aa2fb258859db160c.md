## Analysis

The XWiki bug is a case where a data-exposure safeguard is implemented by matching on a specific identifier (field *name*) rather than the actual data semantics, so data that should be protected slips through when the identifier doesn't match what the filter expects. Searching the gateway (internet-facing, unprivileged-workflow-reachable) code for a similar identifier-based isolation guarantee that silently fails to apply surfaces the HTTP response cache in the CRE Gateway's HTTP Handlers V2.

### Title
Outbound HTTP response cache in the CRE Gateway omits `WorkflowID` from its cache key, breaking documented workflow isolation - (File: `core/services/gateway/handlers/capabilities/v2/response_cache.go`)

### Summary
The gateway's `responseCache` is documented and intended to scope cached outbound HTTP responses by workflow, but the actual cache key (`gateway.OutboundHTTPRequest.Hash()`) does not include `WorkflowID` or `CacheSettings`, only `workflowOwner` (plus method/URL/headers/body). This means two logically distinct workflows sharing the same owner address, request method, URL, headers, and body will collide on the same cache entry and receive each other's previously cached HTTP action responses.

### Finding Description
The `v2/README.md` explicitly documents: "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" [1](#0-0) . The cache implementation itself states the key is "a hash of the request (method, URL, headers, body, workflowOwner)" [2](#0-1)  — `workflowID` is conspicuously absent from that list, despite the doc's claim.

The cache lookup/store/fetch paths (`Fetch`, `Set`, `isExpiredOrNotCached`) all key exclusively off `req.Hash()` [3](#0-2) [4](#0-3) .

The test suite directly proves the omission: identical requests with different `WorkflowID` values produce the *same* hash, while different `WorkflowOwner` values produce different hashes — and `CacheSettings` is likewise ignored by the hash: [5](#0-4) [6](#0-5) .

This is the same class of bug as the XWiki advisory: a protection is implemented as a keyed/named lookup (field name in XWiki; request-identity tuple here) instead of covering the full intended scope, so data crosses a boundary the system claims to enforce (workflow isolation vs. field-name-based redaction).

### Impact Explanation
Because the cache is reachable via the internet-facing gateway's HTTP Action message handling flow — where nodes forward `OutboundHTTPRequest`s from workflow executions and the gateway may fetch or return a cached response — a workflow response (which can contain sensitive data returned from an external HTTP endpoint, e.g. API keys, personal data, or business data specific to one workflow/tenant) can be served to a different workflow that shares the same owner but has a distinct `WorkflowID`. This is a cross-workflow ("cross-user" in the sense of cross-tenant-workflow) response confusion: one workflow's cached HTTP action output leaks into another workflow's execution context, silently, with no error surfaced to either party. It also means a `CacheSettings.Store=false` request can still be served/poisoned by data cached under `Store=true` settings from an unrelated workflow, since `CacheSettings` is likewise excluded from the hash.

### Likelihood Explanation
No special privilege beyond normal workflow-node message submission to the gateway is required to trigger a cache read/write — this happens automatically for every outbound HTTP action whose method/URL/headers/body match another workflow's prior request under the same owner. Given that owners frequently run multiple workflows against common shared endpoints (same URL/method/headers/body, e.g. price or reference-data pulls), a collision is plausible in normal operation without any adversarial action, making this a realistic and not merely theoretical exposure.

### Recommendation
Include `WorkflowID` (and ideally `CacheSettings` semantics that affect cache eligibility) in the `OutboundHTTPRequest.Hash()` computation used as the cache key, so that the implementation matches the documented workflow-scoped isolation guarantee, or explicitly document/enforce owner-level (not workflow-level) sharing if that is the intended design and update all downstream assumptions.

### Proof of Concept
The existing test already demonstrates the flaw: [7](#0-6) 
Two requests differing only in `WorkflowID` ("workflow-123" vs "workflow-456") produce an identical hash — meaning a cache entry stored while serving `workflow-123` will be transparently returned to `workflow-456` on its next matching outbound HTTP action, contradicting the documented per-workflow cache isolation.

func (rc *responseCache) isExpiredOrNotCached(req gateway.OutboundHTTPRequest) bool {
	cachedResp, exists := rc.cache[req.Hash()]
	if !exists || time.Now().After(cachedResp.storedAt.Add(rc.ttl)) {
		return true
	}
	return false
}

// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}
