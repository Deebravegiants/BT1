### Title
Observable Discrepancy Enabling Email Enumeration via Login Error Messages - (File: core/sessions/localauth/orm.go)

### Summary
The `CreateSession` login flow returns distinguishable error messages depending on whether the supplied email exists in the system versus whether the password is wrong, and these raw error strings are forwarded verbatim to the unauthenticated HTTP client. This is the same bug class as CVE-2022-22120 (NocoDB password-reset observable discrepancy): an unauthenticated endpoint reveals whether an email address is a registered user.

### Finding Description
In the local authentication provider's `CreateSession`, the user lookup happens first via `FindUser`, and if that fails (email not found or DB "no rows" error), the raw ORM error is returned directly: [1](#0-0) 

If the user *is* found but the email case-comparison or password check fails, distinct, deliberately different error strings are audited and returned: [2](#0-1) 

The `SessionsController.Create` handler (the unauthenticated `/sessions` HTTP endpoint) passes this returned error straight to the JSON API response without normalizing the message: [3](#0-2) 

The route is registered on an unauthenticated group, reachable by any unprivileged/anonymous client subject only to rate limiting: [4](#0-3) 

The same pattern (differing "invalid email" vs "invalid password" error text) is also present in the LDAP and OIDC local-fallback authenticators: [5](#0-4) [6](#0-5) 

Because `FindUser` for an unknown email returns a raw SQL "no rows" style error (from `findUser`'s `GetContext` call) rather than the deliberately-worded "Invalid email"/"Invalid password" strings, the response body/text an attacker receives for "email doesn't exist" is observably different from "email exists, wrong password." This directly mirrors the NocoDB CVE's bug class: an unauthenticated endpoint (there, password reset; here, login) leaking distinguishable output that lets an attacker enumerate valid registered emails. [7](#0-6) 

### Impact Explanation
An attacker can enumerate valid Chainlink node operator/admin email addresses by sending POST requests to `/sessions` with candidate emails and observing whether the response error text differs (DB "no rows" vs. "Invalid password"/"Invalid email"). This does not directly compromise credentials, funds, or job execution, but it materially aids credential-stuffing and targeted phishing/brute-force campaigns against a specific node's admin/API accounts, which is the same severity class as the referenced CVE (Medium, information disclosure only, no direct impact on confidentiality/integrity of secrets).

### Likelihood Explanation
High likelihood of exploitability from a purely network-reachable, unauthenticated standpoint: the `/sessions` endpoint requires no prior authentication, only email+password in the JSON body, and is rate-limited but not blocked outright. Any external client can iterate a list of candidate emails and observe the error text/format differences in `jsonAPIError` responses.

### Recommendation
Normalize the error returned from `CreateSession` (and its LDAP/OIDC counterparts) so that "user not found," "invalid email," and "invalid password" cases return an identical generic message (e.g., "invalid email or password") and identical error type before reaching `SessionsController.Create`'s `jsonAPIError` call, ideally with constant-time handling to also avoid timing-based enumeration.

### Proof of Concept
1. POST `/sessions` with `{"email":"knownadmin@example.com","password":"wrongpass"}` — response error resolves through `FindUser` success → `CheckPasswordHash` failure → error text `"Invalid password"`.
2. POST `/sessions` with `{"email":"doesnotexist@example.com","password":"wrongpass"}` — response error resolves through `FindUser` failure → raw SQL "no rows in result set" (or wrapped) error, distinguishable in content/format from case 1.
3. Compare the two HTTP 401 response bodies: the differing text confirms the target email in case 1 is a valid registered user, while case 2 is not — enabling systematic enumeration of registered emails. [8](#0-7) [9](#0-8)

func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}

// localLoginFallback tests the credentials provided against the 'local' authentication method
// This covers the case of local CLI API calls requiring local login separate from the LDAP server
func (l *ldapAuthenticator) localLoginFallback(ctx context.Context, sr sessions.SessionRequest) (sessions.User, error) {
	var user sessions.User
	sql := "SELECT * FROM users WHERE lower(email) = lower($1)"
	err := l.ds.GetContext(ctx, &user, sql, sr.Email)
	if err != nil {
		return user, err
	}
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		l.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return user, errors.New("invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		l.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return user, errors.New("invalid password")
	}

	return user, nil
}
