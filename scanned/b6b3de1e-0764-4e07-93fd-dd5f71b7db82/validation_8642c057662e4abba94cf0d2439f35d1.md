### Title
Session ID Disclosed in Plaintext in Audit Event Log on Session Destroy - (File: core/web/sessions_controller.go)

### Summary
The `Destroy` handler in `SessionsController` logs the raw, active-at-the-time session ID into the audit event stream, which can be forwarded to an external HTTP log sink. This mirrors the root cause of CVE-2018-1192 (CWE-200): a session identifier that is also the actual bearer credential for authenticating requests is written into audit/event logs, where it can be captured by anyone with access to those logs and replayed to impersonate the user.

### Finding Description
`SessionsController.Destroy` retrieves the session ID from the request's session cookie and passes it directly into the audit logger as unredacted data: [1](#0-0) 

The `sessionID` value used here is not an opaque, purpose-built log identifier — it is the same `Session.ID` (`utils.NewBytes32ID()`) that is stored server-side and used as the actual authentication credential for the session: [2](#0-1) 

This same ID is what `AuthenticateBySession` extracts from the cookie and hands to the authentication provider to authorize a request: [3](#0-2) 

and it is looked up directly (e.g., against the `sessions`/`ldap_sessions`/`oidc_sessions` tables) by the various `AuthorizedUserWithSession`/`DeleteUserSession` implementations, with no additional binding to a specific client, IP, or secondary secret: [4](#0-3) 

The audit logger, when `AUDIT_LOGGER_FORWARD_TO_URL` is configured, buffers and asynchronously POSTs every audit event — including this `sessionID` field — to an external HTTP endpoint: [5](#0-4) 

The `AuthSessionDeleted` event type and its payload are defined generically as `map[string]any`/`Data`, with no field-level redaction applied for session identifiers, unlike the deliberate password redaction implemented elsewhere in the web layer: [6](#0-5) [7](#0-6) 

Notably, the codebase already implements a request-body/query blacklist (`isBlacklisted`) to redact `password`-like fields before they reach logs, showing the project is aware of this class of leak for HTTP access logs — but this redaction is not applied to the audit-log payloads emitted by `AuditLoggerService.Audit`.

### Impact Explanation
Because the logged value is the literal session credential (not a hash or truncated identifier), anyone able to read the forwarded audit log stream (the configured `AUDIT_LOGGER_FORWARD_TO_URL` endpoint, any intermediate log aggregation/SIEM system, or log storage with broader access than the Chainlink node's admin UI) can extract a still-recently-valid session ID and use it to impersonate the node operator. This is a direct authentication/session-impersonation exposure of the CWE-200 class described in the reference CVE — the audit trail becomes a secondary channel for credential leakage independent of the primary session/cookie transport.

### Likelihood Explanation
Exploitation requires that `AUDIT_LOGGER_FORWARD_TO_URL` be configured (an operator-enabled optional feature) and that the attacker have access to the receiving log service or logging pipeline — a plausible scenario in real deployments where log aggregation services are broader-access than the admin UI itself, or where the forwarding endpoint/headers are misconfigured or compromised. This is not a network-layer or malicious-node attack; it is a logic flaw in what data the unprivileged-facing session-destroy API handler emits to the audit trail.

### Recommendation
Do not log the raw session ID value in audit events. Either omit the `sessionID` field entirely from `AuthSessionDeleted`, or replace it with a non-reusable identifier (e.g., a hash of the session ID, or an internal auto-increment session record ID that cannot be replayed as a credential). Apply the same redaction principle already used for password fields in `core/web/router.go` to all audit log payload construction, or add centralized field-level redaction in `AuditLoggerService.postLogToLogService` for known-sensitive keys such as `sessionID`.

### Proof of Concept
1. Configure `AUDIT_LOGGER_FORWARD_TO_URL` to point to an operator-controlled but broader-access log collector (a normal, documented feature).
2. Log in as a node user to obtain a valid session cookie (contains `sessionID`).
3. Call `POST /sessions` destroy endpoint (logout) while the session is still active/logged elsewhere, or observe the audit event emitted at logout time — `core/web/sessions_controller.go:87` sends `{"sessionID": "<raw-session-id>"}` to the forwarding URL before/around the point of deletion.
4. An entity with read access to the forwarded log stream captures `<raw-session-id>` and uses it as the value of the `webauth.SessionIDKey` in a forged session cookie to call `AuthorizedUserWithSession`, gaining access as the victim until the session row is actually purged/expired. [1](#0-0)

// Destroy removes the specified session ID from the database.
func (sc *SessionsController) Destroy(c *gin.Context) {
	defer sc.App.WakeSessionReaper()
	ctx := c.Request.Context()

	session := sessions.Default(c)
	defer session.Clear()
	sessionID, ok := session.Get(auth.SessionIDKey).(string)
	if !ok {
		jsonAPIResponse(c, Session{Authenticated: false}, "session")
		return
	}
	if err := sc.App.AuthenticationProvider().DeleteUserSession(ctx, sessionID); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	sc.App.GetAuditLogger().Audit(audit.AuthSessionDeleted, map[string]any{"sessionID": sessionID})
	jsonAPIResponse(c, Session{Authenticated: false}, "session")
}

//
// Implements authMethod
func AuthenticateBySession(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	session := sessions.Default(c)
	sessionID, ok := session.Get(SessionIDKey).(string)
	if !ok {
		return auth.ErrorAuthFailed
	}

	user, err := authr.AuthorizedUserWithSession(ctx, sessionID)
	if err != nil {
		return err
	}

	c.Set(SessionUserKey, &user)

	return nil
}

// Takes an EventID and associated data and sends it to the configured logging
// endpoint. This function blocks on the send by timesout after a period of
// several seconds. This helps us prevent getting stuck on a single log
// due to transient network errors.
//
// This function blocks when called.
func (l *AuditLoggerService) postLogToLogService(eventID EventID, data Data) {
	// Audit log JSON data
	logItem := map[string]any{
		"eventID":  eventID,
		"hostname": l.hostname,
		"localIP":  l.localIP,
		"env":      l.environmentName,
		"data":     data,
	}

	// Optionally wrap audit log data into JSON object to help dynamically structure for an HTTP log service call
	if l.jsonWrapperKey != "" {
		logItem = map[string]any{l.jsonWrapperKey: logItem}
	}

	serializedLog, err := json.Marshal(logItem)
	if err != nil {
		l.logger.Errorw("unable to serialize wrapped audit log item to JSON", "err", err, "logItem", logItem)
		return
	}
	ctx, cancel := l.chStop.NewCtx()
	defer cancel()

	// Send to remote service
	req, err := http.NewRequestWithContext(ctx, http.MethodPost, (*url.URL)(&l.forwardToUrl).String(), bytes.NewReader(serializedLog))
	if err != nil {
		l.logger.Error("failed to create request to remote logging service!")
	}
	for _, header := range l.headers {
		req.Header.Add(header.Header, header.Value)
	}
	resp, err := l.loggingClient.Do(req)
	if err != nil {
		l.logger.Errorw("failed to send audit log to HTTP log service", "err", err, "logItem", logItem)
		return
	}
	if resp.StatusCode != http.StatusOK {
		if resp.Body == nil {
			l.logger.Errorw("no body to read. Possibly an error occurred sending", "logItem", logItem)
			return
		}

		bodyBytes, err := io.ReadAll(resp.Body)
		if err != nil {
			l.logger.Errorw("error reading errored HTTP log service webhook response body", "err", err, "logItem", logItem)
			return
		}
		l.logger.Errorw("error sending log to HTTP log service", "statusCode", resp.StatusCode, "bodyString", string(bodyBytes))
		return
	}
}
