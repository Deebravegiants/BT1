### Title
Unbounded JWT Replay Cache Growth Enables Memory Exhaustion in Gateway HTTP Trigger Authorization - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
The gateway's HTTP-trigger JWT replay-protection cache (`jwtReplayCache`) grows unboundedly in response to attacker-controlled input (the JWT `jti` claim) with no maximum-size cap, only a time-based periodic cleanup. Any authorized workflow signer can flood this map with unique `jti` values faster than the cleanup ticker reclaims them, causing unbounded, sequential memory allocation — the same root-cause class (CWE-1325, improperly controlled sequential memory allocation) as the reported weixin4j advisory.

### Finding Description
`jwtReplayCache` is a plain `map[string]time.Time` with no size bound, keyed directly by the JWT `jti` claim, which is attacker-supplied and unique per request: [1](#0-0) 

Cache insertion happens in `Authorize`, after JWT signature verification and workflow-signer authorization succeed, but this only requires the caller to hold a private key already registered as an authorized key for *some* workflow — it does not require any operator/admin privilege, and importantly happens **before** any user-level rate limiting: [2](#0-1) 

Cleanup only occurs on a fixed periodic ticker (`JWTReplayPeriodMs`), not bounded by cache size: [3](#0-2) [4](#0-3) 

In the caller `HandleUserTriggerRequest`, `authorizeRequest` (which triggers `Authorize`/`recordUsage`) executes before `checkRateLimit`: [5](#0-4) 

Because each JWT must carry a fresh, unique `jti` to avoid immediate replay rejection, and generating a new signed JWT is cheap for the legitimate signer (no proof-of-work, no cap on requests per cleanup interval), a workflow owner (or a compromised workflow-owner key) can submit a very high volume of distinct valid JWTs within a single cleanup window, each adding a new entry to the map. There is no maximum entry count enforced anywhere in `jwtReplayCache`, `Authorize`, or `recordUsage`.

### Impact Explanation
Unbounded growth of `jwtCache.cache` consumes gateway process memory proportional to the number of unique JWTs submitted between cleanup intervals. A sustained flood from a single authorized workflow owner (which is an unprivileged, low-trust actor from the gateway's perspective — no operator/admin access required) can exhaust gateway memory, degrading or crashing the gateway node's HTTP-trigger service for all users of that DON/shard. This is a service-facing memory-exhaustion / availability issue reachable purely through the internet-facing gateway request path, consistent with the "internet-facing gateway (handlers, caches)" scope allowed by the rules.

### Likelihood Explanation
Likelihood is moderate: exploitation requires possession of a private key that is already an authorized signer for at least one registered workflow (this is not an anonymous, fully-unauthenticated caller, but it is still an untrusted, low-privilege end-user credential, not an operator/node credential). Given that workflow registration is a normal, low-barrier self-service action in this system, an attacker can register their own workflow and then flood JWTs against it, making the requirement trivial to satisfy. There is no additional cap preventing a single authorized owner from generating unlimited distinct `jti` values.

### Recommendation
Add an explicit maximum-size bound to `jwtReplayCache` (e.g., evict oldest entries or reject new insertions once a configured `MaxJWTCacheEntries` is reached), and/or move rate limiting (`checkRateLimit`) ahead of `authorizeRequest` in `HandleUserTriggerRequest` so that JWT-driven cache writes are also bounded by the per-workflow-owner request rate before they occur. Consider using an LRU or TTL-bounded cache implementation with a hard capacity limit instead of an unbounded map cleaned only on a timer.

### Proof of Concept
1. Register a workflow and obtain an authorized signer key (standard, low-privilege self-service flow).
2. Repeatedly construct and sign new JWTs (via `utils.CreateRequestJWT`) each with a unique `jti`, and submit them as HTTP trigger requests (`gateway_common.MethodWorkflowExecute`) faster than `JWTReplayPeriodMs` cleanup interval elapses.
3. Each request calls `WorkflowMetadataHandler.Authorize` → `jwtCache.recordUsage(claims.ID)` (workflow_metadata_handler.go:105), inserting a new unbounded entry into `jwtCache.cache` (workflow_metadata_handler.go:411) before any rate-limit check is applied.
4. Observe `jwtCache.cache` (and process memory) grow linearly with the number of submitted requests, unbounded by any size cap, until the next scheduled cleanup tick — which can be outrun by sustained request volume.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
