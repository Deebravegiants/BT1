## Analysis

I found a genuine analog to the CVE-2020-15132 "Response time of login gives hint if the username exists" issue in the local authentication login flow.

### Title
Login timing side-channel enables username enumeration in `CreateSession` - (File: `core/sessions/localauth/orm.go`)

### Summary
The `/sessions` login endpoint responds significantly faster for non-existent usernames than for existing ones, because the expensive bcrypt password comparison is only performed after a successful database lookup of the user record. An unauthenticated attacker can use this timing asymmetry to enumerate valid Chainlink node UI/API usernames (emails).

### Finding Description
`SessionsController.Create` accepts an unauthenticated `SessionRequest` and forwards it straight to `AuthenticationProvider().CreateSession` [1](#0-0) .

In the local authenticator, `CreateSession` first calls `FindUser`, which performs a single indexed SQL lookup (`SELECT * FROM users WHERE lower(email) = lower($1)`) and returns immediately with an error if no row is found — no cryptographic work is performed on this path: [2](#0-1) 

Only if the user is found does the code proceed to `constantTimeEmailCompare` and then `utils.CheckPasswordHash`, which wraps `bcrypt.CompareHashAndPassword` — a deliberately slow, tunable-cost hashing operation: [3](#0-2) [4](#0-3) 

Because bcrypt's cost factor is deliberately expensive (by design, to resist offline brute-force), the round-trip time for an existing-user login attempt is measurably and consistently larger than for a non-existent user, regardless of the network noise, especially over repeated/averaged sampling. This is the exact bug class described in the Sulu advisory's "Response time of login gives hint if the username exists" section — the fix in Sulu was to make the two code paths take equal time (e.g., always perform a dummy hash comparison even when the user isn't found).

The same asymmetric pattern (fast-fail on `FindUser`, then slow `CheckPasswordHash`) is also present in the LDAP and OIDC local-fallback authenticators (`localLoginFallback` in `core/sessions/ldapauth/ldap.go` and `core/sessions/oidcauth/oidc.go`), so the issue is not isolated to a single authenticator implementation.

### Impact Explanation
This is a username/email enumeration vector against an internet-facing, unauthenticated endpoint (the node's login page/API). Confirmed valid operator emails can subsequently be used for targeted credential stuffing, phishing, or brute-force/password-spray attacks against the Chainlink node's admin/operator accounts. It does not by itself grant access but materially lowers the cost of a follow-on account-takeover attack. This matches the CVSS 3.1 vector of the original advisory (confidentiality-only, no direct integrity/availability impact).

### Likelihood Explanation
Exploitation only requires an unauthenticated network client sending repeated `POST /sessions` requests with different candidate emails and measuring response latency (statistically, with averaging to reduce network jitter) — no special privileges or internal access are required. This makes it a straightforward, low-effort, unprivileged-actor attack given access to the node's HTTP login endpoint.

### Recommendation
Equalize the timing of the "user not found" and "password mismatch" code paths in `CreateSession` (and the equivalent LDAP/OIDC local fallback functions), e.g., by always performing a bcrypt comparison against a fixed/dummy hash when the user lookup fails, so that the same computational cost is incurred regardless of whether the email exists. Additionally, ensure error responses returned via `jsonAPIError` (which currently serializes `err.Error()` directly) don't leak lookup-specific details that could reinforce the enumeration signal.

### Proof of Concept
1. Send `POST /sessions` with a known-valid email and a wrong password; measure response time (dominated by bcrypt compare).
2. Send `POST /sessions` with a random/invalid email; measure response time (fails fast at `FindUser`, no bcrypt).
3. Repeat many times for statistical significance; the valid-email requests will show a consistently higher latency, allowing an attacker to distinguish valid from invalid emails without needing the correct password.

		jsonAPIError(c, http.StatusUnauthorized, err)
		return
	}

// CheckPasswordHash wraps around bcrypt.CompareHashAndPassword for a friendlier API.
func CheckPasswordHash(password, hash string) bool {
	err := bcrypt.CompareHashAndPassword([]byte(hash), []byte(password))
	return err == nil
}
