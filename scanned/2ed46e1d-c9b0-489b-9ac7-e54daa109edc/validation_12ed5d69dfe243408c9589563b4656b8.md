### Title
Terminated-contract address can be indefinitely blocked from redeployment via strict-FIFO `DeletionQueue` head-of-line blocking (`PendingDepositCleanup`) - (File: `substrate/frame/revive/src/storage.rs`)

### Summary
`ContractInfo::process_deletion_queue_batch` drains the `DeletionQueue` strictly in FIFO order using a ring-buffer `delete_counter`/`insert_counter` pair, and never advances past an entry whose `NativeDepositOf` prefix or child-trie cannot be fully drained within the current `on_idle` weight budget. An attacker can pre-populate the queue with many slow-to-drain decoy entries ahead of a victim contract's `DeletionQueueItem`, so `ContractInfo::new`'s `NativeDepositOf::iter_prefix` check keeps returning `Error::PendingDepositCleanup` for that address until every decoy ahead of it is fully processed.

### Finding Description
`ContractInfo::new` (`substrate/frame/revive/src/storage.rs:196-234`) rejects re-instantiation at address `A` while any `NativeDepositOf` row keyed by `A`'s fallback account still exists: [1](#0-0) 

Those rows are only cleared lazily via `on_idle` → `process_deletion_queue_batch`, which pulls entries from `DeletionQueueManager` using `next()` — a function that always returns the entry at the current `delete_counter` head, never any later entry: [2](#0-1) 

The batch-processing loop charges a per-entry overhead, then attempts phase 1 (`NativeDepositOf::clear_prefix`) and phase 2 (child-trie `kill_storage`) for that head entry only. If either phase cannot finish within the remaining weight (`result.maybe_cursor.is_some()` or `KillStorageResult::SomeRemaining`), the loop `break`s immediately — it does not proceed to the next queue slot in the same call, and the head entry is *not* removed, so the same entry remains at `delete_counter` for the next `on_idle` invocation: [3](#0-2) 

Because this is a strict ring-buffer FIFO (`insert()` appends at `insert_counter`, `remove()` only advances `delete_counter` by one after full completion), a queue entry can never be skipped over. An unprivileged attacker can therefore:
1. Instantiate and grow storage via many distinct contributor accounts on N decoy contracts (using the same `MultiContributorStorage`-style pattern referenced in the existing test suite, e.g. `substrate/frame/revive/src/tests/deposit_payment.rs:460-527`), each seeding a large `NativeDepositOf` prefix and/or large child trie.
2. Terminate all N decoys (each push via `queue_for_deletion`, `substrate/frame/revive/src/storage.rs:395-397`), which enqueues their `DeletionQueueItem`s ahead of the victim's.
3. Terminate the victim contract at address `A` last, so its `DeletionQueueItem` lands behind all N decoys in the FIFO.
4. Attempt to redeploy at `A` (e.g., via CREATE2/deterministic salt in `Pallet::instantiate`), which calls `ContractInfo::new` and hits `PendingDepositCleanup` because `A`'s `NativeDepositOf` rows are still present and the queue hasn't reached `A`'s entry.
5. As long as the attacker keeps at least one decoy ahead of `A` that requires more processing than a single `on_idle` weight budget allows to fully clear (e.g. a very large native-deposit prefix or trie), the queue head never advances past it, and `A` remains permanently un-drained and unusable for redeployment.

None of the existing checks (`DuplicateContract`, `MaxCallDepthReached`, weight metering) prevent this because they are unrelated to cross-entry queue ordering; the FIFO design itself has no starvation-avoidance or per-address prioritization/skip-ahead mechanism.

### Impact Explanation
This is a durable, attacker-controlled denial of service against a specific contract address: address `A` cannot be reused for redeployment for as long as the attacker sustains a backlog of slow-draining decoys ahead of it in the global `DeletionQueue`. Since the queue is shared chain-wide, this also degrades cleanup for every other terminated contract behind the same backlog, but the scoped impact here is the address-specific permanent block via `PendingDepositCleanup`.

### Likelihood Explanation
Fully reachable via ordinary unprivileged extrinsics/contract calls: instantiate, storage-growing calls, and self-terminate are all normal user-triggered paths. The attacker needs enough funds to pay the deposits for growing storage across decoy contracts/contributors and enough time to insert decoys before terminating `A`, both of which are attacker-controllable and repeatable. The only limiting factor is the economic cost of seeding large `NativeDepositOf` prefixes/child tries per decoy, which is bounded by deposit requirements but not prevented by any protocol-level cap on queue depth or drain time per address.

### Recommendation
Change the deletion-queue drain strategy so that per-entry drain progress is decoupled from strict head-of-line ordering — e.g., track and persist a resumable cursor per entry so an incomplete entry doesn't monopolize the "current position," or process entries out of order (e.g., round-robin/limit consecutive weight spent on a single entry and advance to try the next entry within the same `on_idle` call once a per-entry budget cap is hit). Alternatively, decouple the `PendingDepositCleanup` check from full completion of the deletion queue by clearing the terminated contract's `NativeDepositOf` prefix eagerly (or with a bounded first pass) at termination time rather than purely lazily via the shared FIFO queue.

### Proof of Concept
Rust integration test in `substrate/frame/revive/src/tests/deposit_payment.rs` style:
1. Instantiate decoy contracts `D_1..D_N` using `MultiContributorStorage`, have K distinct contributor accounts each call `growStorage` on each decoy to seed K `NativeDepositOf` rows per decoy.
2. Terminate `D_1..D_N` in order (each enqueues a `DeletionQueueItem`).
3. Instantiate victim contract at deterministic address `A` (fixed salt), grow storage from at least one contributor, then terminate `A` (enqueues `A`'s `DeletionQueueItem` behind all decoys).
4. Assert `DeletionQueue::<Test>::iter().count() == N + 1`.
5. Attempt to re-instantiate at `A`'s address with the same salt; assert it fails with `Error::<Test>::PendingDepositCleanup`.
6. Call `Contracts::on_idle(block, weight_bounded_below_full_backlog)` repeatedly with a weight budget insufficient to drain all N decoys in one call; after each call, re-attempt instantiation at `A` and assert it still fails with `PendingDepositCleanup` while any decoy remains in `DeletionQueue`.
7. Scale N and K and measure/assert the number of `on_idle` calls required before redeployment at `A` succeeds grows linearly with the pre-seeded backlog size, demonstrating unbounded (attacker-controlled) delay rather than a fixed bound.
