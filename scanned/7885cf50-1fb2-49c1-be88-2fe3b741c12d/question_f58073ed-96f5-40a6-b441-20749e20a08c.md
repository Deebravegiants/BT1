Target: OmniBridge.createWithdrawalIntents' use of `this.envConfig.contractID` passed into deriveOmniWithdrawIntentParams as `intentsContract`, baked into the ft_withdraw intent's `msg` (recipient/fee/external_id JSON), but never cross-checked against the `verifying_contract` actually used when IntentExecuter.signAndSendIntent signs the payload (which independently reads `this.envConfig.contractID` from the SDK instance issuing the call, not from the intent content). Attacker input: a caller instantiating IntentsSDK with a custom `env` EnvConfig whose contractID differs between the instance used to build intents (via createWithdrawalIntents) and the instance/signer actually used to sign (e.g., multi-tenant integrator code passing pre-built IntentPrimitive[] into signAndSendIntent on a differently configured SDK instance, a legitimate documented advanced use case). Preconditions: two IntentsSDK instances with different envConfig.contractID; intents built by one, signed via signAndSendIntent by the other. Call sequence: sdkA.createWithdrawalIntents(...) returns intents embedding sdkA.envConfig.contractID in msg fields -> sdkB.signAndSendIntent({intents}) signs verifying_contract = sdkB.envConfig.contractID. Equality broken: SIGNED == BUILT (every field of the signed MultiPayload's verifying_contract must equal the contract the intent content assumes) - nothing in signAndSendIntent checks that intents supplied already assume the same contractID as this.envConfig.contractID. Impact: Critical, the signed payload's verifying_contract can diverge from the contractID embedded in the bridge intent's msg, causing the intents contract execution and destination bridge contract's expectations to mismatch, which can misroute or void the withdrawal with no recovery. Proof: vitest builds intents via one EnvConfig then calls signAndSendIntent using an IntentExecuter configured with a different envConfig.contractID, mocks intentRelayer.publishIntent, and asserts no error/check occurs even though intentPayload.verifying_contract != the contractID baked into the intent's msg field.
