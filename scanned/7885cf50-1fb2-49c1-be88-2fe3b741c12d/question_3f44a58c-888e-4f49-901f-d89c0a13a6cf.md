Target: IntentsSDK.sendSignedIntents (and IntentExecuter.sendSignedIntents) which calls `intentRelayer.publishIntents({multiPayloads: args.multiPayloads, quoteHashes})` on an arbitrary caller-supplied array of MultiPayload objects with zero validation of their `standard`/contract binding fields. Attacker input: a caller passes multiPayloads containing a MultiPayload it received from a counterparty (e.g., another integrator's signed but unrelated intent) mixed with its own. Preconditions: public method sendSignedIntents callable directly per shared-types.ts's IIntentsSDK interface. Call sequence: sendSignedIntents -> intentRelayer.publishIntents -> tickets returned 1:1 with input array order assumed by caller. Equality broken: SINGLE EXECUTION / SIGNED==BUILT - nothing ties the multiPayloads passed to sendSignedIntents back to any envConfig.contractID or to intents this caller actually built, so a caller can be tricked (or trick itself) into co-publishing an unrelated already-signed payload atomically with its own, with no check that all payloads target the same contract. Impact: Critical, atomic co-publishing of unrelated signed payloads can cause one payload's nonce/nonce-nonce set to be consumed together with the caller's own withdrawal, and if the relayer's ticket-to-payload ordering assumption breaks, the caller cannot determine which ticket belongs to which payload. Proof: vitest calls sendSignedIntents with two MultiPayloads of different verifying_contract, mocks intentRelayer.publishIntents returning tickets, and asserts the SDK provides no equality check confirming both payloads share the same contractID before atomic submission.
