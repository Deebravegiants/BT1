Target: internal-utils/solverRelay/getStatus.ts getStatus(). Attacker input: none required from the caller - the vulnerability is in the trust placed on the relayer's response object; but the reachable path is when a solver/relayer-returned response.status is 'TX_BROADCASTED' or 'SETTLED' yet response.data.hash is attacker-observable/reused across two different intent_hash queries (a permissionless solver can trigger this by racing two intents whose broadcast tx happens to be reported with the same hash field due to relay bugs, or by resubmitting). Preconditions: two calls to getStatus({intent_hash: h1}) and getStatus({intent_hash: h2}) both routed through the same solverRelayClient.getStatus HTTP endpoint. Call sequence: waitForIntentSettlement polls getStatus per intentHash and trusts response.data.hash as txHash without recomputing/reconciling it against a locally computed intent hash or a locally observed NEAR tx. Equality broken: STATUS TRUTH - (status, txHash) reported for intentHash h1 is never checked to correspond uniquely to h1 versus h2; getStatus performs no reconciliation between the local computeIntentHash(multiPayload) used to build h1 and the intent_hash echoed back in the relayer response. Scoped impact: Critical - an integrator polling getStatus for two concurrent withdrawals can be handed a txHash that does not correspond to the specific signed payload it submitted, causing a double-credit or double-refund decision downstream. Proof idea: vitest test mocking the /rpc HTTP endpoint to return the same data.hash for two different intent_hash queries, call getStatus twice with different intent_hash values, and assert both callers accept the identical txHash as authoritative with no equality check against a locally recomputed hash.
