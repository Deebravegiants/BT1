This is a genuine reachable vulnerability class: unvalidated pagination `offset`/`limit` from GraphQL causing an out-of-bounds slice panic (Go's version of "crash via bad Offset/Limit before the response window was safely bounded"), reachable by any authenticated user via the `Nodes` query.

### Title
Unbounded GraphQL `offset`/`limit` in `Nodes` query causes server panic via out-of-range slice - ([File: core/services/chainlink/relayer_chain_interoperators.go])

### Summary
The `Nodes` GraphQL resolver forwards attacker-controlled `Offset`/`Limit` (`*int32`, unbounded, can be negative or larger than `int32` max abs value) directly into `CoreRelayerChainInteroperators.NodeStatuses`, which performs raw Go slice arithmetic (`result[offset:]`, `result[:limit]`) without validating that `offset`/`limit` are non-negative or within bounds of `result`.

### Finding Description
`Resolver.Nodes` only requires `authenticateUser` (any session, including the lowest `UserRoleView` role) and passes the caller-supplied `Offset`/`Limit` straight through: [1](#0-0) 

`pageOffset`/`pageLimit` merely dereference the pointer with no range validation (unlike `pageOffset`/`pageLimit` usage in `Chains`, which has an explicit `offset >= count` bound check): [2](#0-1) [3](#0-2) 

`NodeStatuses` then does unchecked slicing: [4](#0-3) 

- `result[offset:]` panics if `offset` is negative or `offset > len(result)` isn't already caught (the `len(result) < offset` check only guards the upper bound, not negative offsets).
- `result[:limit]` panics if `limit` is negative (the code only checks `len(result) > limit`, which is true for any negative `limit` too, and Go rejects negative slice bounds at runtime with `panic: runtime error: slice bounds out of range [:-N]`).

This causes an unrecovered panic in the GraphQL resolver goroutine, crashing/terminating the node process (or at minimum the request handler, depending on whether there is panic recovery middleware for GraphQL — not confirmed in the excerpts reviewed).

### Impact Explanation
Any authenticated Chainlink node operator UI user — even one restricted to the lowest `UserRoleView` role, which is intended for read-only monitoring — can crash the node process by sending a single malformed GraphQL `nodes(offset: -1, limit: -1)` query. This is a low-privilege-to-high-impact escalation: a "view-only" account can cause a denial of service against the entire node, disrupting job execution and OCR/DON participation.

### Likelihood Explanation
High likelihood: no special conditions are required beyond having any valid session cookie (any role) and issuing one GraphQL query with negative or contradictory `offset`/`limit` values. The `Chains` resolver in the same file demonstrates that the developers were aware bound checks are necessary for these pagination params, but the equivalent check was omitted for `Nodes`/`NodeStatuses`.

### Recommendation
In `NodeStatuses` (core/services/chainlink/relayer_chain_interoperators.go), and defensively in `pageOffset`/`pageLimit` (core/web/resolver/helpers.go), clamp `offset` and `limit` to non-negative values before use, and validate `offset <= len(result)` before slicing (mirroring the `Chains` resolver's `offset >= count` check). Also consider adding panic-recovery middleware around GraphQL resolver execution as defense-in-depth.

### Proof of Concept
Send an authenticated GraphQL request (any role) to the node's GraphQL endpoint:
```graphql
query {
  nodes(offset: -1, limit: -1) {
    results { id }
  }
}
```
This reaches `Resolver.Nodes` → `NodeStatuses(ctx, -1, -1)` → `result[offset:]` with `offset = -1`, panicking with `slice bounds out of range [-1:]`.

---

**Note on confidence:** I could not verify (due to index limits) whether there is global panic-recovery middleware wrapping the GraphQL handler in the `gqlgen`/`graphql-go` router setup that would turn this panic into a 500 error rather than a full process crash — this affects whether the impact is "process crash" vs. "single request 500 error." I'd recommend a Devin session with full repo access to confirm the presence/absence of such middleware (e.g., in `core/web/router.go` or wherever the GraphQL handler is mounted) before finalizing severity.

func (r *Resolver) Nodes(ctx context.Context, args struct {
	Offset *int32
	Limit  *int32
}) (*NodesPayloadResolver, error) {
	if err := authenticateUser(ctx); err != nil {
		return nil, err
	}

	offset := pageOffset(args.Offset)
	limit := pageLimit(args.Limit)
	r.App.GetLogger().Debugw("resolver Nodes query", "offset", offset, "limit", limit)
	allNodes, total, err := r.App.GetRelayers().NodeStatuses(ctx, offset, limit)
	r.App.GetLogger().Debugw("resolver Nodes query result", "nodes", allNodes, "total", total, "err", err)

	if err != nil {
		r.App.GetLogger().Errorw("Error creating get nodes status from app", "err", err)
		return nil, err

	if warn != nil {
		r.App.GetLogger().Warnw("Error creating NodesPayloadResolver", "err", warn)

}

// pageOffset returns the default page offset if nil, otherwise it returns the

func pageOffset(offset *int32) int {

	}

	return int(*offset)
