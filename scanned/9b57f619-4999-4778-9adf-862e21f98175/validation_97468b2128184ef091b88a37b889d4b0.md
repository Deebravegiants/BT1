### Title
Vault secret storage/quota keys use non-normalized owner address while authorization uses normalized owner - ([File: core/capabilities/vault/vaulttypes/types.go])

### Summary
The Vault capability's authorization layer normalizes owner addresses (lower-cases, strips `0x`) before comparing them, so a request whose secret-identifier owner is `0xAbCd` is treated as authorized for a caller whose authenticated owner is `0xabcd`. However, the storage key derivation function `KeyFor` and the per-owner secret-count/quota lookup use the *raw, non-normalized* owner string. This mirrors the reported cw20-base/cw1-whitelist bug class: one code path normalizes an address for comparison/authorization while a different, security-relevant code path (storage keying / quota accounting) does not, causing the same logical entity (one wallet address) to be treated as multiple distinct identities depending on casing.

### Finding Description
`vaultutils.NormalizeOwner` is documented as the single source of truth for owner comparisons: "All comparison sites must use this function" [1](#0-0) . It is consistently applied inside `authorizer.go` when validating that a secret identifier's `Owner` field matches the authorized workflow owner from the auth token/JWT, e.g. in `validateEncryptedSecretOwnerMismatch` and `validateSecretIdentifierOwnerMismatch` [2](#0-1) [3](#0-2) .

This authorization check only validates that the caller-supplied `Owner` field matches (case-insensitively) the caller's own authenticated owner — it never rewrites the `Owner` field on the request to the canonical/normalized form. The raw, caller-supplied `Owner` string then propagates unchanged into the persistence layer:

- `vaulttypes.KeyFor` builds the storage key directly from `id.Owner` with no normalization: `fmt.Sprintf("%s::%s::%s", id.Owner, namespace, id.Key)` [4](#0-3) .
- `KVStore.WriteSecret`, `GetSecret`, and `DeleteSecret` use this raw key to read/write the OCR key-value store [5](#0-4) [6](#0-5) .
- The per-owner quota check in `stateTransitionCreateSecretsRequest` calls `store.GetSecretIdentifiersCountForOwner(ctx, req.Id.Owner)` and `contexts.WithCRE(ctx, contexts.CRE{Owner: req.Id.Owner})` using the raw, unnormalized owner [7](#0-6) .

Because the authorization check treats `0xAbCd`, `0xabcd`, and `abcd` (with/without `0x` prefix) as the same authorized identity (see the exhaustive matching-case test table) [8](#0-7) , but the storage key and quota bucket are keyed on the literal string, a legitimate owner can pass authorization with any casing of their own address while the secret ends up filed under a *different* storage bucket/quota bucket per casing variant.

Only one call site, `secretsFetcher.GetRawSecrets` in the workflow SDK, explicitly calls a `normalizeOwner` helper before building request/keys for logging purposes [9](#0-8) , confirming that normalization is not uniformly enforced across all producers of `SecretIdentifier.Owner` that feed into `KeyFor`/count.

### Impact Explanation
- **Cross-casing secret loss / unavailability (funds-lock analog):** A create issued with owner casing A stores at key `A::ns::key`; the authorized caller can later issue a delete/get/update with a differently-cased owner B (same real address) that passes owner-match authorization (`NormalizeOwner(A) == NormalizeOwner(B)`) but resolves to a different `KeyFor` string, so the operation silently misses the existing secret (`GetSecret` returns not-found, or `WriteSecret` for "create" appears to succeed as a *new* independent entry rather than overwriting/managing the same logical secret). This can strand secrets, similarly to cw20 funds being locked when sent to a differently-cased but functionally identical address.
- **Quota/limit bypass:** `MaxSecretsPerOwner` is enforced via `GetSecretIdentifiersCountForOwner(ctx, req.Id.Owner)`, keyed on the raw owner string. A single authorized owner can create secrets under several casing variants of their own address (all of which pass the owner-match check) to accumulate more secrets than `MaxSecretsPerOwner` allows for that owner, since each variant is counted as a separate owner bucket.
- **Confusing/duplicated inventory and List inconsistency:** `ListSecretIdentifiers` is also owner-scoped; secrets created under differing raw-owner casings would not be listed together, producing operational confusion and orphaned/undiscoverable entries for the legitimate owner.

This is a functional-integrity/availability and quota-bypass issue reachable by any unprivileged, already-authorized vault client (the caller's own valid credentials are sufficient — no privileged access or malicious peer required), matching the "unauthorized... quota bypass" and "cross-user response confusion" acceptance criteria.

### Likelihood Explanation
Likelihood is moderate-to-high for the quota-bypass and self-inflicted-lock scenarios, since it only requires the legitimate, already-authorized caller to vary the case (or `0x` prefix) of their own address across `create`/`update`/`delete`/`list` requests — no cryptographic break or third-party spoofing is needed. EVM addresses are frequently rendered in checksummed (mixed-case) form by wallets/SDKs versus lower-case forms used elsewhere, making an accidental casing mismatch across a client's own requests plausible even without malicious intent, and easy to weaponize deliberately for quota evasion.

### Recommendation
Normalize `SecretIdentifier.Owner` (and any owner value used for count/limit bucketing) once, at the earliest trust boundary (e.g., immediately after `AuthorizeRequest` succeeds, in the Authorizer or GatewayVaultRequestProcessor), and canonicalize it into the request before it reaches `KeyFor`, `GetSecretIdentifiersCountForOwner`, or `contexts.WithCRE`. `vaulttypes.KeyFor` itself should call `vaultutils.NormalizeOwner(id.Owner)` rather than using `id.Owner` verbatim, ensuring storage keys, quota buckets, and list results are always consistent for a given real-world owner regardless of the casing/prefix used in any individual request.

### Proof of Concept
1. Authenticate as owner with EVM address `0xAbCdEf1234567890abcdef1234567890abcdef12` (any casing/prefix variant is accepted by the authorizer per the "matching with different casing" test case) [10](#0-9) .
2. Send `vault.secrets.create` with `SecretIdentifier{Owner: "0xAbCdEf1234567890abcdef1234567890abcdef12", Namespace: "main", Key: "secret1"}`. This passes owner-match authorization and is stored under key `KeyFor` = `"0xAbCdEf...::main::secret1"` [4](#0-3) .
3. Send another `vault.secrets.create` for the same logical secret but with `Owner: "0xabcdef1234567890abcdef1234567890abcdef12"` (all lowercase). Authorization again succeeds (owner match is case-insensitive), and since the KV store key differs (`"0xabcdef...::main::secret1"`), this is treated as a brand-new secret rather than a duplicate, incrementing the per-owner secret count under a second quota bucket [7](#0-6) .
4. Repeat with additional casing permutations of the same address to accumulate secrets beyond `MaxSecretsPerOwner` for what the authorization layer considers a single owner.
5. Issue a `vault.secrets.delete` or `vault.secrets.get` using yet another casing of the same address; authorization succeeds, but the lookup at the differently-cased `KeyFor` key returns not-found, demonstrating the secret is now unreachable via that casing (functional lock / inconsistent inventory).

```go
// NormalizeOwner lowercases an Ethereum owner address for case-insensitive comparison.
// All comparison sites must use this function. When VaultOwnerAddressCanonicalizationEnabled
// is introduced, normalization at ingress will supersede comparison-site calls here.
func NormalizeOwner(owner string) string {
	return strings.ToLower(strings.TrimPrefix(owner, "0x"))
```

```go
func validateEncryptedSecretOwnerMismatch(encryptedSecrets []*vaultcommon.EncryptedSecret, workflowOwner string) error {
	if len(encryptedSecrets) == 0 {
		return errors.New("request batch must contain at least 1 item")
	}
	for idx, encryptedSecret := range encryptedSecrets {
		if encryptedSecret == nil {
			return fmt.Errorf("encrypted secret must not be nil at index %d", idx)
		}
		if encryptedSecret.Id == nil {
			return fmt.Errorf("secret ID must not be nil at index %d", idx)
		}
		if vaultutils.NormalizeOwner(encryptedSecret.Id.Owner) != vaultutils.NormalizeOwner(workflowOwner) {
			return fmt.Errorf("encrypted secret owner at index %d %q does not match authorized workflow owner %q", idx, encryptedSecret.Id.Owner, workflowOwner)
		}
	}
	return nil
}
```

```go
func (s *KVStore) GetSecret(ctx context.Context, id *vault.SecretIdentifier) (*vault.StoredSecret, error) {
	defer s.trackDuration(ctx, "GetSecret", time.Now())
	if id == nil {
		return nil, errors.New("id cannot be nil")
	}
	found, err := s.metadataContainsID(ctx, id)
	if err != nil {
		return nil, fmt.Errorf("failed to check if metadata contains id: %w", err)
	}

	if !found {
		return nil, nil
	}

	b, err := s.reader.Read([]byte(keyPrefix + vaulttypes.KeyFor(id)))
	if err != nil {
		return nil, fmt.Errorf("failed to read secret: %w", err)
	}

	if b == nil {
		return nil, errors.New("invariant violation: metadata contains id but secret not found")
	}

	secret := &vault.StoredSecret{}
	err = proto.Unmarshal(b, secret)
	if err != nil {
		return nil, fmt.Errorf("failed to unmarshal secret: %w", err)
	}
	return secret, nil
}
```

```go
func (s *KVStore) WriteSecret(ctx context.Context, id *vault.SecretIdentifier, secret *vault.StoredSecret) error {
	defer s.trackDuration(ctx, "WriteSecret", time.Now())
	if id == nil {
		return errors.New("id cannot be nil")
	}
	b, err := proto.Marshal(secret)
	if err != nil {
		return fmt.Errorf("failed to marshal secret: %w", err)
	}

	err = s.writer.Write([]byte(keyPrefix+vaulttypes.KeyFor(id)), b)
	if err != nil {
		return fmt.Errorf("failed to write secret: %w", err)
	}

	if err := s.addIDToMetadata(ctx, id); err != nil {
		return fmt.Errorf("failed to add id to metadata: %w", err)
	}

	return nil
}
```
