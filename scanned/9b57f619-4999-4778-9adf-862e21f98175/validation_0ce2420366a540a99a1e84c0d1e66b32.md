### Title
LDAP Authentication Bypass via Unauthenticated (Empty-Password) Bind - (File: core/sessions/ldapauth/ldap.go)

### Summary
`ldapAuthenticator.CreateSession` forwards the client-supplied password directly to the LDAP `Bind` call without first rejecting an empty password. Per LDAP semantics (RFC 4513 §5.1.2), a simple bind with a non-empty DN and an *empty* password is defined as an "unauthenticated bind" and is commonly accepted by LDAP servers as a *successful* bind (no error returned), rather than a credential check failure. Because chainlink treats any successful `Bind()` as proof of valid credentials, an unauthenticated remote caller who supplies only a valid/guessable email and an empty password string can obtain a fully authenticated node session for that user, including whatever role (Admin/Edit/Run) is mapped to them in LDAP groups.

### Finding Description
`CreateSession` is reachable directly from the public, unauthenticated `POST /sessions` endpoint via `SessionsController.Create`: [1](#0-0) 

It binds the JSON body to `sessions.SessionRequest` (which has no validation requiring a non-empty `Password`): [2](#0-1) 

`CreateSession` then performs the bind directly with the attacker-controlled `sr.Password`: [3](#0-2) 

There is no check anywhere in `CreateSession`, `SessionRequest`, or the HTTP controller that rejects an empty (or otherwise degenerate) password before calling `conn.Bind(searchBaseDN, sr.Password)`. If the LDAP server treats the empty-password bind as an "unauthenticated bind" success (a documented, common LDAP server behavior for backward-compatibility/protocol conformance, unless the operator has explicitly disabled it), `err` will be `nil`, `returnErr` stays `nil`, and the flow proceeds to call `FindUser` and issue a real `ldap_sessions` row and session cookie for the targeted email/role — i.e., full authentication bypass for any known email address.

This mirrors the referenced CVE-2025-50103 bug class (a flaw specifically in the "Server: Security: LDAP Auth" component that a network-reachable actor can exploit to compromise the server), except here the analog impact in chainlink is authentication bypass/session impersonation rather than DoS, because the vulnerable code path is the LDAP bind-based login handler itself.

Compare with the local/OIDC auth providers, which explicitly hash-compare the password and never delegate raw empty strings to a third-party bind call: [4](#0-3) 

The LDAP provider's `TestPassword` function has the identical unguarded pattern: [5](#0-4) 

### Impact Explanation
An unauthenticated network client who knows (or guesses/enumerates) a valid user email registered in the upstream LDAP directory can obtain a legitimate, fully privileged Chainlink node web session (Admin/Edit/Run, per the user's LDAP group mapping) without knowing their password, by submitting an empty password to `POST /sessions`. This is a direct authentication/role bypass and session impersonation against the node's HTTP API, satisfying "concrete authentication or role bypass" and "cross-user response confusion" categories.

### Likelihood Explanation
Exploitability depends on whether the configured upstream LDAP server accepts unauthenticated binds (many servers do by default unless explicitly hardened per RFC 4513 recommendations). Given chainlink performs no client-side guard against empty passwords, any operator whose LDAP server has not disabled unauthenticated binds is exposed to this bypass from any network client that can reach the `/sessions` endpoint and knows a target's email address — a low-effort, high-impact remote condition.

### Recommendation
In `ldapAuthenticator.CreateSession` (and `TestPassword`), explicitly reject empty/blank passwords before calling `conn.Bind`, e.g. return an authentication error immediately if `sr.Password == ""` (or after trimming whitespace), regardless of LDAP server bind semantics. Additionally, consider validating `sr.Password` non-empty at the `sessions.SessionRequest` binding layer to close this class of bug for all authentication providers uniformly.

### Proof of Concept
1. Configure `WebServer.AuthenticationMethod = 'ldap'` against an upstream LDAP server that permits unauthenticated binds (default in many LDAP deployments).
2. As an unauthenticated remote client, send:
```
POST /sessions
Content-Type: application/json

{"email":"victim-admin@example.com","password":""}
```
3. `conn.Bind(searchBaseDN, "")` succeeds per RFC 4513 unauthenticated-bind semantics, `CreateSession` proceeds to `FindUser`, creates an `ldap_sessions` row, and returns a valid session cookie for `victim-admin@example.com` with their mapped role — without ever knowing the real password.
