Found a concrete replay-analog issue: the `Authorize` function in `WorkflowMetadataHandler` performs the replay check (`isReplay`) and the replay record (`recordUsage`) as two separate, non-atomic operations, with unrelated authorization work happening in between.

### Title
JWT Replay Check-Then-Act Race Allows Duplicate HTTP Trigger Requests to Bypass Replay Protection - (`core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go`)

### Summary
`WorkflowMetadataHandler.Authorize` is meant to prevent replay of a signed JWT-bound trigger request (the JWT `jti` claim is intended to be single-use, analogous to the nonce recommended in the reported `reserve()` replay bug). The check (`isReplay`) and the mark-as-used (`recordUsage`) are separated by unrelated logic and are not protected by a single atomic operation, creating a TOCTOU (time-of-check-to-time-of-use) window.

### Finding Description
`Authorize` calls `h.jwtCache.isReplay(claims.ID)` early, then does authorization key lookups, and only calls `h.jwtCache.recordUsage(claims.ID)` at the very end, right before returning success: [1](#0-0) 

`jwtReplayCache` uses a `sync.RWMutex`, but the mutex only guards each individual method call (`isReplay`, `recordUsage`); it does not span the whole "check, then eventually record" sequence in `Authorize`: [2](#0-1) 

If two concurrent HTTP trigger requests carrying the identical signed JWT/request pair arrive at the gateway node at (nearly) the same time, both can pass `isReplay` (since neither has called `recordUsage` yet), both can pass the authorized-key lookup, and both get treated as valid, freshly-authorized requests — with `recordUsage` only being called after the fact. This defeats the single-use guarantee the `jti`-based replay cache is supposed to provide, which is the same class of bug flagged in the reference report (replayable signed request without an atomic single-use guard).

### Impact Explanation
The `Authorize` function gates `HandleUserTriggerRequest` for the v2 HTTP trigger path, so a bypass here allows an attacker (or a captured/leaked signed JWT+request) to have the same signed trigger request accepted and forwarded to the workflow DON twice concurrently, instead of exactly once as intended by the anti-replay design. Depending on the downstream workflow logic (e.g., idempotency assumptions tied to "one JWT = one execution"), this can cause duplicate job/workflow executions triggered from a single signed request — directly analogous to the reported fund-misallocation risk from replayed `reserve()` calls, since duplicate triggers processed by workflows that move funds or resources would be executed more than intended.

### Likelihood Explanation
This requires an attacker to be able to send the same signed request twice, concurrently, to the same gateway node — feasible for anyone in possession of a valid signed JWT/request (including the legitimate workflow signer replaying their own already-used token, or a request being duplicated/retried at the network layer and racing with itself). No privileged access is needed; it is exploitable by any unprivileged HTTP client capable of concurrent requests. The race window is narrow (a few in-process operations), so reliable exploitation may require multiple attempts, which somewhat lowers likelihood but does not eliminate it.

### Recommendation
Make the check-and-record operation atomic: implement a single `jwtReplayCache` method (e.g. `CheckAndRecord(jti)`) that acquires the cache's write lock once, checks for prior existence, and inserts the entry before releasing the lock — mirroring the pattern already used correctly in `RequestReplayGuard.CheckAndRecord` in `core/capabilities/vault/request_replay_guard.go` [3](#0-2) . Then call this atomic method from `Authorize` immediately after JWT verification, before doing any authorization-key lookups, instead of splitting `isReplay`/`recordUsage` across the function.

### Proof of Concept
1. Sign a valid JWT-bound HTTP trigger request for an authorized workflow (`utils.CreateRequestJWT` + `SignedString`), matching the pattern used in `http_trigger_handler_test.go`'s `createTestJWTToken` helper: [4](#0-3) 
2. Fire two goroutines that both call `handler.workflowMetadataHandler.Authorize(workflowID, tokenString, req)` (or equivalently POST the same signed body twice concurrently to the gateway) at the same time.
3. Observe that both calls can return successfully (no `"JWT token has already been used"` error on either), because both pass `isReplay` before either reaches `recordUsage`, in contrast to the existing sequential test `TestWorkflowMetadataHandler_Authorize`'s "JWT replay protection" subtest, which only exercises the strictly-sequential (non-concurrent) replay case: [5](#0-4)

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
