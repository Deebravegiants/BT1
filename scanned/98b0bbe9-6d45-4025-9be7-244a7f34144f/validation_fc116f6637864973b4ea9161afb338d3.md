### Title
Unhandled nil pointer dereference in Vault node's `MethodPublicKeyGet` handler crashes the node process - (File: `core/capabilities/vault/gw_handler.go`)

### Summary
The Vault capability's node-side gateway message handler, `GatewayHandler.HandleGatewayMessage`, dispatches `vaulttypes.MethodPublicKeyGet` requests to `handlePublicKeyGet` without first checking whether `req.Params` is `nil`. `handlePublicKeyGet` then dereferences `*req.Params` directly, which panics with a nil pointer dereference if `Params` is absent. Because the public-key-get method is explicitly documented and tested to work with `Params: nil` on the gateway side, an unprivileged/unauthenticated client can trigger this code path end-to-end simply by omitting `params` in a `vault.publicKey.get` request sent to the gateway's public HTTP endpoint.

### Finding Description
On the gateway side, `MethodPublicKeyGet` is intentionally exempt from Vault authorization ("Public key requests don't require authorization") and is explicitly allowed to have `Params: nil`: [1](#0-0) 

This is directly confirmed by tests constructing `jsonrpc.Request[json.RawMessage]{Method: vaulttypes.MethodPublicKeyGet, Params: nil}` and passing them through `HandleJSONRPCUserMessage`/`handlePublicKeyGet` successfully at the gateway layer (no unmarshal of `Params` is attempted there): [2](#0-1) [3](#0-2) 

When the gateway's cache is cold, it forwards the original request object (with the untouched, possibly-nil `Params`) unchanged to every DON node via `SendToNode`: [4](#0-3) 

On the node side, the connector routes this to the registered `core.GatewayConnectorHandler`, which for Vault is `GatewayHandler.HandleGatewayMessage`. It switches on `req.Method` and, for `MethodPublicKeyGet`, calls `handlePublicKeyGet` with no prior nil-check on `req.Params`: [5](#0-4) 

`handlePublicKeyGet` then unconditionally dereferences the pointer: [6](#0-5) 

In Go, `json.Unmarshal(*req.Params, r)` where `req.Params` is a `*json.RawMessage` equal to `nil` panics with a nil pointer dereference. No `recover()` wrapping was found around the connector's dispatch to `HandleGatewayMessage` in `core/services/gateway/connector/connector.go`, meaning an unrecovered panic here will crash the node process, exactly mirroring the HAX CMS root cause of dereferencing/using unchecked, user-omittable request data (`ERR_INVALID_ARG_TYPE` there vs. nil-pointer panic here).

### Impact Explanation
A single crafted JSON-RPC request (`vault.publicKey.get` with no `params` field, or `params: null`) sent by any client capable of reaching the gateway's public HTTP endpoint — no Vault authorization or workflow-owner allowlisting required, since `MethodPublicKeyGet` explicitly skips authorization — propagates unchanged to every Vault DON node and panics the node's `GatewayHandler.HandleGatewayMessage` goroutine. If unrecovered, this crashes the node's backend process, denying service to all users of that node (and, since the request fans out to `h.donConfig.Members`, potentially to every member of the Vault DON simultaneously). This matches CWE-20/248/703 style improper exception handling leading to Denial of Service (CVSS VA:H), analogous to the referenced HAX CMS advisory.

### Likelihood Explanation
High. The trigger is a normal externally reachable JSON-RPC request with no authentication, authorization, or special conditions beyond omitting `params` (or setting it to `null`), a request shape that is explicitly supported/expected by the gateway-side code and tests. No race condition, timing, or privileged access is required.

### Recommendation
In `core/capabilities/vault/gw_handler.go`, add an explicit nil/empty check on `req.Params` before dispatching to `handlePublicKeyGet` (and any other handler branch that dereferences `*req.Params`), returning a structured `UserMessageParseError`/`InvalidParamsError` response instead of dereferencing a nil pointer — consistent with how `handleSecretsCreate`/`handleSecretsList` and the gateway-side v2 HTTP trigger handler already guard `req.Params == nil` before use (e.g., `core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go` lines 150-153). Additionally, consider adding panic recovery around `HandleGatewayMessage` dispatch in the connector as defense-in-depth against similar unchecked-dereference bugs in other capability handlers.

### Proof of Concept
1. Send an unauthenticated JSON-RPC request to the gateway's HTTP endpoint targeting the Vault DON/service:
```json
{"jsonrpc":"2.0","id":"1","method":"vault.publicKey.get","params":null}
```
(equivalently, omit the `params` field entirely).
2. The gateway's `handler.HandleJSONRPCUserMessage` (`core/services/gateway/handlers/vault/handler.go:404-420`) accepts this without requiring authorization, and (on cold cache) forwards the request as-is to Vault DON nodes via `fanOutToVaultNodes`/`SendToNode`.
3. Each node's `GatewayHandler.HandleGatewayMessage` (`core/capabilities/vault/gw_handler.go:180-211`) routes to `handlePublicKeyGet`, which executes `json.Unmarshal(*req.Params, r)` with `req.Params == nil`, causing a nil pointer dereference panic and crashing the node process (absent panic recovery in the connector dispatch path).

```go
func (h *handler) fanOutToVaultNodes(ctx context.Context, l logger.Logger, ar *activeRequest) error {
	var nodeErrors []error
	for _, node := range h.donConfig.Members {
		err := h.don.SendToNode(ctx, node.Address, &ar.req)
		if err != nil {
			nodeErrors = append(nodeErrors, err)
			l.Errorw("error sending request to node", "node", node.Address, "error", err)
		}
	}

	if len(nodeErrors) == len(h.donConfig.Members) && len(nodeErrors) > 0 {
		return h.sendResponse(ctx, ar, h.errorResponse(ar.req, api.FatalError, errors.New("failed to forward user request to nodes"), nil))
	}

	l.Debugw("successfully forwarded request to Vault nodes")
	return nil
}
```

```go
func (h *GatewayHandler) HandleGatewayMessage(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) (err error) {
	reqLggr := h.requestLogger(req, gatewayID)
	reqLggr.Debugw("received message from gateway", "req", req)

	var response *jsonrpc.Response[json.RawMessage]
	var authResult *AuthResult

	switch req.Method {
	case vaulttypes.MethodSecretsCreate, vaulttypes.MethodSecretsUpdate:
		publicKey, pkErr := h.getMasterPublicKey(ctx)
		if pkErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pkErr)
			break
		}
		authorized, pipelineErr := h.requestProcessor.ProcessRequest(ctx, req, publicKey)
		if pipelineErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pipelineErr)
			break
		}
		authResult = authorized.AuthResult
	case vaulttypes.MethodSecretsDelete, vaulttypes.MethodSecretsList:
		authorized, pipelineErr := h.requestProcessor.ProcessRequest(ctx, req, nil)
		if pipelineErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pipelineErr)
			break
		}
		authResult = authorized.AuthResult
	case vaulttypes.MethodPublicKeyGet:
		response = h.handlePublicKeyGet(ctx, gatewayID, req)
	default:
		response = h.errorResponse(ctx, gatewayID, req, api.UnsupportedMethodError, errors.New("unsupported method: "+req.Method))
	}
```

```go
func (h *GatewayHandler) handlePublicKeyGet(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) *jsonrpc.Response[json.RawMessage] {
	r := &vaultcommon.GetPublicKeyRequest{}
	if err := json.Unmarshal(*req.Params, r); err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.UserMessageParseError, err)
	}
```
