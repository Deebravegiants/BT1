Confirmed root-cause data: `TriggerRequestPayload.Timestamp` is `int64` (attacker-controlled, from an unprivileged HTTP client hitting the gateway), and `HandlerConfig.MaxAllowedMessageAgeSec` is `uint`.

### Title
Signed/unsigned comparison mismatch bypasses staleness check in gateway legacy WebAPI trigger handling - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The gateway's legacy message handler validates message freshness with a mixed signed/unsigned comparison that mirrors the CVE-2021-26713 bug class (a signedness mismatch causing incorrect bounds/comparison logic reachable by an unauthenticated/unprivileged actor sending crafted repeated requests).

### Finding Description
`HandleLegacyUserMessage` computes staleness as: [1](#0-0) 

```go
if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) { //nolint:gosec // G115
```

`payload.Timestamp` is declared as `int64` and is fully attacker-controlled JSON input [2](#0-1) . The code casts it to `uint` for the comparison. Because Go performs `uint(payload.Timestamp)` by reinterpreting the bit pattern, a negative or arbitrarily large `int64` value converts to an enormous unsigned value (near `math.MaxUint64`), which will always be *greater* than `uint(time.Now().Unix()) - MaxAllowedMessageAgeSec`, so the "stale message" branch is skipped regardless of the actual intent — this is functionally the same "signedness comparison mismatch" pattern named in the CVE (unsigned/signed cast used in a bounds check without normalizing sign first), just applied to a timestamp/freshness check instead of an RTP hold/unhold counter.

This handler is directly reachable from an unauthenticated HTTP client through the gateway's public entrypoint: `gateway.ProcessRequest` → `HandleLegacyUserMessage` for any legacy (DON-ID-based) request [3](#0-2) . On success, the handler unconditionally stores a callback keyed by `msg.Body.MessageID` in `h.savedCallbacks` and fans the message out to every DON member [4](#0-3) .

### Impact Explanation
An unprivileged client can bypass the intended message-freshness/anti-replay control by crafting `timestamp` values that wrap in the signed→unsigned cast, causing arbitrarily old or arbitrarily "future" messages to be accepted as fresh. Combined with the unbounded per-request callback insertion (bounded only by periodic pruning every `CallbackPruneIntervalSec`, default 30s, and `MaxSavedCallbacks`, default 20000) [5](#0-4) , repeated rapid submission of such requests amplifies fan-out load to every DON member without the freshness gate acting as a throttle, which is the closest analog to the "rapid repeated requests exploiting a signedness bug to overload the target" bug class in the CVE. This is a logic/availability-adjacent issue rather than memory corruption (Go has no stack buffer overflow equivalent here), so impact is limited to anti-replay/staleness-control bypass and increased DON fan-out load, not remote code execution or crash.

### Likelihood Explanation
High likelihood of reachability: the endpoint is internet-facing and requires no privileged role, only a validly-formed legacy gateway message with attacker-chosen `timestamp` [6](#0-5) . The `//nolint:gosec // G115` annotation shows the signedness issue was known and explicitly suppressed rather than fixed, which increases confidence this is a live weakness in production code rather than a hypothetical one [7](#0-6) .

### Recommendation
Reject negative `payload.Timestamp` explicitly before comparison, and perform the freshness check using signed 64-bit arithmetic (or convert `MaxAllowedMessageAgeSec` and `time.Now().Unix()` consistently to `int64`) instead of casting a signed, attacker-controlled value to `uint`. E.g.:
```go
if payload.Timestamp <= 0 || time.Now().Unix()-int64(h.config.MaxAllowedMessageAgeSec) > payload.Timestamp {
    // stale/invalid
}
```

### Proof of Concept
1. Send a legacy gateway request (`msg.Body.DonID` set) with `MethodWebAPITrigger` and payload JSON containing `"timestamp": -1` (or any negative int64).
2. `payload.Timestamp` unmarshal succeeds since `Timestamp != 0` check only excludes zero [8](#0-7) .
3. `uint(payload.Timestamp)` becomes `18446744073709551615` (for `-1`), which is always greater than `uint(time.Now().Unix()) - MaxAllowedMessageAgeSec`, so the staleness check at line 372 is bypassed.
4. The message is accepted, stored in `savedCallbacks`, and forwarded to all DON members, despite failing the intended freshness/anti-replay gate.

**Note on confidence:** I could not fully trace whether an upstream JSON-RPC decoding layer normalizes or re-validates `timestamp` before it reaches this handler for the *legacy* request path specifically (only the `Timestamp == 0` check is visible in this file); if such validation exists elsewhere in the request-decoding pipeline it could reduce or eliminate exploitability. I recommend verifying this end-to-end in a live/dynamic test given index limitations.
