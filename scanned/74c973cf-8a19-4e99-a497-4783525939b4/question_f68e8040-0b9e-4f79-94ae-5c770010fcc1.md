[File: mainnet/contracts/vault/v0-vault-sbtc.clar -> Scope: Critical] Target: `system-repay`. Precondition: `total-borrowed > 0`, debt (via `total-debt`) already includes accrued but uncollected interest so `debt > total-borrowed`. Attacker action: attacker (as any account funded with underlying, since `system-repay` is only gated by `check-caller-auth`, but the resulting state is externally observable and exploitable by any redeemer) is not required to call `system-repay` itself — instead the attacker calls `redeem` immediately after a real repay event. Call sequence: 1) borrower/system triggers `system-repay(amount)` where `capped-amount = min(amount, debt)`, `principal-repaid = mul-div-down(capped-amount, total-borrowed, debt)` (rounds down), `total-borrowed -= principal-repaid`; 2) attacker calls `redeem` in the same or next block. Identity that breaks: `principal-repaid` should reduce `principal-scaled` by the same fraction it reduces `total-borrowed`, i.e. `principal-reduction/scaled-principal == principal-repaid/total-borrowed-amount`; because both are independently rounded down via `calc-principal-ratio-reduction` and `mul-div-down`, `principal-scaled` after `system-repay` overstates true remaining debt relative to `total-borrowed`, growing the phantom-interest term `(total-debt) - total-borrowed` on every repay. Impact: Critical, protocol insolvency, absorbed by remaining suppliers. Proof idea: Clarinet test running many small `system-repay` calls and asserting the invariant `total-debt - total-borrowed == 0` holds after a full repayment (`amount >= debt`); show a nonzero residual.
