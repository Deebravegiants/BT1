## Analysis Result

This vulnerability class **does** have a valid analog in the codebase — the JIT (just-in-time) reward-per-token accounting in `pallet-asset-rewards` shares the exact same accumulator-truncation weakness as the reported Synthetix-style contract, and it is *more severe* here because a truncated update corrupts the pool-wide accumulator rather than just a single account's snapshot.

### Title
Permissionless, zero-cost griefing of `pallet-asset-rewards` reward accrual via integer-truncation of `reward_per_token` on repeated no-op `stake`/`unstake` calls - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet-asset-rewards` implements the same Synthetix-style "reward-per-token accumulator" pattern described in the external report [1](#0-0) . The accumulator update, `reward_per_token`, divides `reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR` by `total_tokens_staked` [2](#0-1) . `PRECISION_SCALING_FACTOR` is only `4096`, a far smaller scaling constant than the `1e18` WAD used in the Solidity contract, making the numerator collapse to `0` under integer division much more easily [3](#0-2) .

Crucially, `update_pool_rewards` always advances `last_update_block` to the current block regardless of whether `reward_per_token_stored` actually increased [4](#0-3) . Because this state is persisted to storage on every `stake`/`unstake` call, any truncated interval's rewards are **permanently and irrecoverably lost for the entire pool** (all stakers), not just for the caller.

### Finding Description
The extrinsic `stake` is fully permissionless and has no minimum-amount check, so `stake(pool_id, 0)` is a valid call [5](#0-4) . Each call:
1. Computes `reward_per_token` via `Self::reward_per_token(&pool_info)` (truncation-prone division) [6](#0-5) .
2. Persists the pool's `last_update_block = now` and `reward_per_token_stored = <possibly unchanged value>` via `Pools::<T>::insert(pool_id, pool_info)` [7](#0-6) .

An attacker (who need not hold any existing stake — `PoolStakers::get(...).unwrap_or_default()`) can call `stake(pool_id, 0)` on every block. If
```
reward_rate_per_block * 1 * 4096 < total_tokens_staked
```
the integer division truncates to `0`, so `reward_per_token_stored` does not increase for that block while `last_update_block` is advanced past it — permanently erasing that block's rewards for the whole pool. Because the interval can be as short as one block, and the condition only needs `total_tokens_staked` (driven by legitimate stakers, often an 18-decimal asset) to exceed `reward_rate_per_block * 4096`, this is trivially satisfiable in realistic pools (e.g., low-decimal or modest reward-rate configurations), analogous to the USDT/USDC/WBTC low-decimal scenario in the original report.

`unstake(pool_id, 0)` on one's own stake produces the same effect, but `stake(pool_id, 0)` is strictly worse since it requires no prior participation in the pool at all.

### Impact Explanation
This freezes reward accrual for **every staker in the pool simultaneously**, not merely one targeted victim as in the original report. Since `last_update_block` unconditionally advances, the lost reward period can never be recovered — it is a permanent, protocol-wide reward loss, achievable by any signed account for the cost of transaction fees only.

### Likelihood Explanation
High. No privileged role or special preconditions are needed beyond an active pool with `total_tokens_staked > 0` (the normal state of any pool with real stakers). `PRECISION_SCALING_FACTOR = 4096` is small enough that the truncation window is easy to hit repeatedly for realistic `reward_rate_per_block` / `total_tokens_staked` ratios, and the attack can be automated to fire every block.

### Recommendation
- Increase `PRECISION_SCALING_FACTOR` substantially (e.g., to a WAD-like `1e12`+ scale, accounting for `Balance` overflow headroom).
- In `reward_per_token`, detect when the computed increment truncates to zero while `total_tokens_staked > 0` and the elapsed blocks are nonzero, and either accumulate a remainder/carry instead of dropping the reward, or avoid advancing `last_update_block` past the point where meaningful accrual occurred.
- Consider requiring `amount > 0` for `stake`, though this alone does not fully close the truncation issue (an attacker with any small real stake, or via `unstake(pool_id, 0)`, can still trigger it).

### Proof of Concept
1. Admin creates a pool with `reward_rate_per_block = R` and stakers deposit tokens such that `total_tokens_staked = S` where `S > R * 4096`.
2. Attacker (any signed account, no prior stake required) calls `stake(pool_id, 0)` on this pool every single block.
3. Each call computes `rewardable_blocks_elapsed = 1`; `R * 1 * 4096 < S` truncates the reward increment to `0` in `reward_per_token` [8](#0-7) .
4. `Pools::<T>::insert` persists `last_update_block = now` with `reward_per_token_stored` unchanged [7](#0-6) .
5. Repeating every block indefinitely permanently prevents `reward_per_token_stored` from ever increasing, so no staker in the pool can ever accrue or harvest rewards, despite the reward asset balance sitting in the pool account.

		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
