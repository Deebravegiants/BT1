## Analog Found

### Title
Unbounded growth of the gateway `activeRequests` map lets an unprivileged client cause linear-time DoS sweeps and unbounded memory growth - (File: `core/services/gateway/handlers/vault/handler.go`, `core/services/gateway/handlers/confidentialrelay/handler.go`)

### Summary
Both the Vault gateway handler and the Confidential Relay gateway handler store every incoming, unprivileged, internet-facing user request in an in-memory map (`activeRequests`) keyed by request ID, with no limit on the number of concurrent entries. A background goroutine periodically walks the *entire* map to find and evict expired/graced entries. This mirrors the reported bug class (`GTL.sol`'s `_withdrawalQueue` iteration): cheap, attacker-controlled insertions into an unbounded collection followed by full-collection iteration on a hot/periodic path.

### Finding Description
`handler.newActiveRequest` in the Vault gateway handler inserts a new `activeRequest` into `h.activeRequests` for every valid `HandleJSONRPCUserMessage` call, gated only by a per-request-ID uniqueness check and a 200-character ID length cap — there is no cap on the total number of concurrently tracked requests: [1](#0-0) [2](#0-1) 

Every `defaultCleanUpPeriod` (5s), `removeExpiredRequests` acquires a lock and iterates the *entire* `activeRequests` map to find expired entries: [3](#0-2) 

The Confidential Relay handler has the identical pattern (`newActiveRequest` with no size cap, plus periodic full-map scans in both `removeExpiredRequests` and `forwardGracedRequests`, this one ticking every 1 second): [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

By contrast, the generic `RequestCache` used elsewhere in the gateway *does* enforce a `maxCacheSize` and rejects new entries once full: [8](#0-7) 

Neither the Vault nor the Confidential Relay handler applies an equivalent bound. The only rate limiting present (`nodeRateLimiter`/`perNodeRateLimiters`) throttles *node* responses, not the *user-submitted* request volume that grows the map: [9](#0-8) 

### Impact Explanation
An unprivileged client submitting JSON-RPC requests through the gateway (e.g. repeated `secrets_list`/`secrets_create` calls with distinct, well-formed request IDs) can grow `activeRequests` without bound until the request's own `requestTimeout` (default 30s) expires. Since insertion is cheap (no per-user quota) and eviction only happens on a periodic full-map sweep that both locks a shared mutex and is O(n) in the number of tracked requests, sustained submission volume degrades sweep latency and increases memory pressure on the gateway node, analogous to the reported unbounded-loop gas-DoS: cheap attacker-controlled insertions vs. expensive full-collection iteration on a critical path (here, a periodic maintenance goroutine holding `h.mu` for the duration of the scan, which also blocks `newActiveRequest`/`getActiveRequest`/`sendResponse` on the same lock).

### Likelihood Explanation
Reaching this path requires no authentication for `MethodPublicKeyGet`, and for authorized methods only requires passing the Vault allowlist/JWT `AuthorizeRequest` check — i.e., any user with valid credentials for *any* workflow can spam requests. Even unauthenticated public-key requests reach `newActiveRequest` when the cache is cold. This is directly reachable from `HandleJSONRPCUserMessage`, the gateway's primary internet-facing entrypoint.

### Recommendation
Apply the same bounded-cache pattern already used by `common.RequestCache` (an explicit `maxCacheSize` check in `newActiveRequest`, rejecting new requests once the map is full) to both `core/services/gateway/handlers/vault/handler.go` and `core/services/gateway/handlers/confidentialrelay/handler.go`. Consider also adding a per-sender/per-user quota so a single caller cannot occupy the entire budget of concurrent in-flight requests.

### Proof of Concept
1. As an authorized (or, for `MethodPublicKeyGet`, unauthenticated) client, send a burst of `HandleJSONRPCUserMessage` calls with unique `req.ID` values faster than `requestTimeout` (30s) elapses.
2. Each call succeeds in `newActiveRequest` and adds an entry to `h.activeRequests`; there is no check against total map size. [2](#0-1) 
3. Repeat continuously to keep the map larger than the rate at which `removeExpiredRequests` can evict; each 5s tick locks `h.mu` and performs an O(n) scan over the accumulated entries, growing more expensive as n grows, and blocking concurrent `newActiveRequest`/`sendResponse` calls that also take `h.mu`. [3](#0-2)

func (h *handler) removeExpiredRequests(ctx context.Context) {
	h.mu.RLock()
	var expiredRequests []*activeRequest

func (h *handler) forwardGracedRequests(ctx context.Context) {
	h.mu.RLock()
	var graced []*activeRequest
	now := h.clock.Now()
	for _, ar := range h.activeRequests {
		if ar.graceElapsed(now) {
			graced = append(graced, ar)
		}
	}
	h.mu.RUnlock()

	for _, ar := range graced {
		h.forwardAfterGrace(ctx, ar)
	}
}

func NewRequestCache[T any](timeout time.Duration, maxCacheSize uint32) RequestCache[T] {
	return &requestCache[T]{cache: make(map[globalID]*pendingRequest[T]), timeout: timeout, maxCacheSize: maxCacheSize}
}

func (c *requestCache[T]) NewRequest(lggr logger.Logger, request *api.Message, callback handlers.Callback, responseData *T) error {
	if request == nil {
		return errors.New("request is nil")
	}
	if responseData == nil {
		return errors.New("responseData is nil")
	}
	key := globalID{request.Body.Sender, request.Body.MessageID}
	c.mu.Lock()
	defer c.mu.Unlock()
	_, ok := c.cache[key]
	if ok {
		return errors.New("request already exists")
	}
	if len(c.cache) >= int(c.maxCacheSize) {
		return errors.New("request cache is full")
	}
