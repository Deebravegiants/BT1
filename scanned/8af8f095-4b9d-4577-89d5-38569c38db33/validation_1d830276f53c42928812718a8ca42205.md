## Analysis

The strongest reachable analog to the "missing access control" bug class in this codebase is the `Resume` endpoint on `PipelineRunsController`, mounted with **no authentication middleware at all**.

### Finding

`PATCH /v2/resume/:runID` is registered on `unauthedv2`, a router group that does not go through `auth.Authenticate(...)`, unlike every other `/v2/*` route which requires session/token/external-initiator auth plus role checks: [1](#0-0) 

The handler itself performs no ownership, secret, or role verification — it accepts an arbitrary `runID` (task UUID) from the path and a JSON body, and directly resumes the pipeline task: [2](#0-1) 

This mirrors the reported `SolverVaults.acceptWithdrawRequest` bug class: a state-mutating function reachable by any unprivileged caller with no `onlyRole`/session check, relying solely on the caller supplying a value (there: `providedAmount`/ratio; here: a `runID` UUID) rather than any authorization proof. The code even self-documents the gap via the audit event name `audit.UnauthedRunResumed`, confirming this route is deliberately public/unauthenticated.

Because `runID` is a UUID (task run ID), guessing it is impractical in normal operation, but the design has no defense-in-depth: any party who obtains or brute-forces/log-leaks a pending task's run ID (e.g., via logs, monitoring, error messages, or a bridge response echoed elsewhere) can inject arbitrary task results/errors into someone else's job pipeline run without any credentials, causing incorrect pipeline results, fund-moving `ETHTx` tasks to be resumed with attacker-controlled data, or DoS via forcing task completion/error states.

### Title
Unauthenticated `PATCH /v2/resume/:runID` allows unauthorized resumption of arbitrary pipeline task runs - (File: core/web/router.go, core/web/pipeline_runs_controller.go)

### Summary
The `/v2/resume/:runID` route is registered on the `unauthedv2` gin group, bypassing all of Chainlink's authentication middleware (`auth.Authenticate`) and role checks (`RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole`) that protect every other stateful `/v2` endpoint. Its handler, `PipelineRunsController.Resume`, performs no additional authorization check of its own — it trusts the caller-supplied `runID` alone to authorize completing/erroring a pipeline task, directly analogous to `acceptWithdrawRequest` lacking the `onlyRole(BALANCER_ROLE)` enforcement in the reported bug.

### Finding Description
`v2Routes` explicitly creates an unauthenticated group and binds the resume handler to it: [3](#0-2) 
Every other route in the same file is wrapped in `auth.Authenticate(...)` plus a `RequiresXRole` guard [4](#0-3) , showing this is the sole exception with no equivalent protection.

`Resume` then parses the path parameter as a UUID and calls `App.ResumeJobV2` directly, with no ownership/ACL check tying the caller to the run, bridge, or job in question: [5](#0-4) 

This endpoint exists to let bridge/external-task adapters asynchronously post back results for tasks awaiting resumption (e.g., `bridge`/`external`/`webhook`-style async tasks), but the only "secret" gating it is the task run UUID itself — there is no signature, shared secret comparison, or bridge-specific token check performed in this handler, unlike the external-initiator flow (`AuthenticateExternalInitiator`) which does a constant-time secret comparison [6](#0-5) .

### Impact Explanation
An attacker who learns or guesses a pending task run UUID (e.g., leaked via logs, external system responses, monitoring dashboards, or a compromised/malicious downstream bridge target) can:
- Force early/incorrect completion of a pipeline run with attacker-controlled data, corrupting job outputs.
- Inject an error into a run, causing denial of service for time-sensitive jobs (e.g., OCR/keeper-adjacent pipelines).
- Potentially manipulate downstream tasks (e.g., `ethtx`) that consume the resumed value, indirectly affecting on-chain transaction behavior for jobs that use async/resumable tasks.

This is high severity because it is a full authorization bypass on a state-mutating, pipeline-run-altering endpoint exposed on the node's HTTP API with zero session/token/role checks.

### Likelihood Explanation
Likelihood is moderated by the fact that `runID` is a random UUID rather than a sequential/guessable ID, so the primary attack vector is UUID leakage rather than brute force. However, the complete absence of a second authorization factor (unlike the external-initiator or API-token flows, which pair credentials with constant-time secret comparisons) means the security of the entire endpoint rests solely on UUID secrecy — a violation of defense-in-depth, and exactly the "missing access control checks" class flagged in the reference report.

### Recommendation
Require a bridge/task-specific authenticator (e.g., a per-task callback secret or HMAC signature bound to the run/task ID) similar to the external-initiator secret model in `bridges.AuthenticateExternalInitiator`, rather than relying on unauthenticated public access. At minimum, add rate limiting and audit-based anomaly detection (the code already tags this action `audit.UnauthedRunResumed`, indicating the team is aware it's intentionally unauthenticated) and consider scoping resumption to only tasks tied to the specific bridge/adapter secret used when the async task was dispatched.

### Proof of Concept
1. Enumerate or obtain a pending task's `runID` (UUID) for an async/bridge task awaiting resumption — e.g., from application logs, a compromised external adapter response, or timing/side-channel leakage.
2. Send `PATCH /v2/resume/<runID>` with an attacker-crafted JSON body matching `pipeline.ResumeRequest` (no `Content-Type`, session cookie, or API token header required, since the route is in the `unauthedv2` group in `core/web/router.go`).
3. Observe `App.ResumeJobV2` executes with the attacker-supplied result, completing or erroring the run without any authentication challenge — confirmed by the absence of `auth.Authenticate` in the route group definition and no in-handler ownership check in `PipelineRunsController.Resume`.

// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
}

// AuthenticateExternalInitiator compares an auth against an initiator and
// returns true if the password hashes match
func AuthenticateExternalInitiator(eia *auth.Token, ea *ExternalInitiator) (bool, error) {
	hashedSecret, err := auth.HashedSecret(eia, ea.Salt)
	if err != nil {
		return false, err
	}
	return subtle.ConstantTimeCompare([]byte(hashedSecret), []byte(ea.HashedSecret)) == 1, nil
}
