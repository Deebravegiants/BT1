### Title
Local-auth session renewal bypasses the operator-configured `SessionReaperExpiration` maximum session lifetime - ([File: core/sessions/localauth/orm.go])

### Summary
The Keystone advisory describes a bug class where a re-issued/rescoped credential does not inherit the constraints (expiry) of the policy that is supposed to bound it, letting a client keep renewing access indefinitely and defeat an operator-configured lifetime limit. The `localauth` session provider in this repository has the same root cause: every authenticated request silently extends the session's `last_used` timestamp with no reference to the original session's age or to any absolute cap, so an authenticated (even unprivileged/session-hijacking) actor can keep a single session alive forever by simply calling the API before each idle window (`SessionTimeout`) elapses, defeating the documented `SessionReaperExpiration` "max session lifetime" policy.

### Finding Description
`AuthorizedUserWithSession` is invoked on essentially every authenticated HTTP/GraphQL request and unconditionally bumps `last_used` to `now()` on success: [1](#0-0) 

The validity check itself is purely idle-time based (`last_used + SessionTimeout >= now()`), not tied to the session's `created_at`: [2](#0-1) 

The reaper — the only mechanism meant to enforce an absolute session lifetime cap — deletes rows only when `last_used` is older than a computed stale threshold derived from `SessionReaperExpiration` + `SessionTimeout`: [3](#0-2) 

Because `last_used` is refreshed on every legitimate request (line 102 of `orm.go`), as long as the session is used at least once within each `SessionTimeout` window (default 15m), `last_used` never falls behind the reaper's stale threshold, and the session is never purged — regardless of how long it has actually existed. The documentation, however, describes `SessionReaperExpiration` as a hard cap on total session lifetime:

> "SessionReaperExpiration represents how long an API session lasts before expiring and requiring a new login." [4](#0-3) 

This is the same root-cause pattern as the Keystone advisory: a token/session renewal path (`updateSessionLastUsed`) that fails to propagate/enforce the original issuance-time constraint (an absolute maximum age), causing the effective lifetime policy configured by the operator to be silently bypassed through routine, unprivileged use of the credential.

### Impact Explanation
Any actor in possession of a valid session cookie/ID — whether the legitimate user or an attacker who has stolen a session (e.g., via XSS, log leakage, or a compromised client) — can retain that session indefinitely by issuing periodic authenticated requests, completely bypassing the operator's configured maximum session age (`SessionReaperExpiration`, default 240h). This undermines a core security control that operators rely on to force periodic re-authentication and limit the blast radius of a leaked session token. Given Admin-role sessions grant full node control (fund movement via `/v2/transfers`, job/bridge management, user management), indefinite retention of a hijacked session is a meaningful confidentiality/integrity risk.

### Likelihood Explanation
No special privilege is required beyond already holding a valid session ID — this is triggered by completely normal, unprivileged API/GUI usage patterns (or automated periodic polling by an attacker holding a stolen cookie). It requires no error condition or race; it is the deterministic behavior of `updateSessionLastUsed` on every authorized request.

### Recommendation
Enforce an absolute session lifetime independent of activity: track and check `created_at` (or the initial-login timestamp) against `SessionReaperExpiration` in `findValidSession`/`AuthorizedUserWithSession`, so that a session cannot survive past `SessionReaperExpiration` regardless of how often `last_used` is refreshed. The reaper's stale-threshold calculation should similarly key off session age (`created_at`), not solely off `last_used`.

### Proof of Concept
1. Log in via `POST /sessions` to obtain a session cookie (`localauth`, default `SessionTimeout=15m`, `SessionReaperExpiration=240h`).
2. Every ~10 minutes (well within the 15m idle window), issue any authenticated request (e.g., `GET /v2/config`) using the same session cookie.
3. Each request calls `AuthorizedUserWithSession` → `updateSessionLastUsed`, resetting `last_used` to `now()`. [5](#0-4) 
4. Because the reaper only purges sessions whose `last_used` is older than `now - SessionTimeout - SessionReaperExpiration`, and `last_used` is continually refreshed, the session ID remains valid for weeks/months/indefinitely past the configured 240h `SessionReaperExpiration`, contradicting the documented "how long an API session lasts before expiring" guarantee.

Note: I was unable to fully trace `core/web/auth/auth.go`'s middleware wiring in this pass (tool budget exhausted) to enumerate every route that triggers `AuthorizedUserWithSession`; a Devin session with full repo access could confirm the exact set of routes and validate the fix against the LDAP/OIDC providers, which use a different (age-based, non-renewing) session-validity model and do not appear to share this specific issue.

// findValidSession finds an unexpired session by its ID and returns the associated email.
func (o *orm) findValidSession(ctx context.Context, sessionID string) (email string, err error) {
	if err := o.ds.GetContext(ctx, &email, "SELECT email FROM sessions WHERE id = $1 AND last_used + $2 >= now() FOR UPDATE", sessionID, o.sessionDuration); err != nil {
		o.lggr.Infof("query result: %v", email)
		return email, pkgerrors.Wrap(err, "no matching user for provided session token")
	}
	return email, nil
}

// updateSessionLastUsed updates a session by its ID and sets the LastUsed field to now().
func (o *orm) updateSessionLastUsed(ctx context.Context, sessionID string) error {
	_, err := o.ds.ExecContext(ctx, "UPDATE sessions SET last_used = now() WHERE id = $1", sessionID)
	return err
}

// AuthorizedUserWithSession will return the API user associated with the Session ID if it
// exists and hasn't expired, and update session's LastUsed field.
// AuthorizedUserWithSession will return the API user associated with the Session ID if it
// exists and hasn't expired, and update session's LastUsed field.
func (o *orm) AuthorizedUserWithSession(ctx context.Context, sessionID string) (user sessions.User, err error) {
	if len(sessionID) == 0 {
		return sessions.User{}, sessions.ErrEmptySessionID
	}

	email, err := o.findValidSession(ctx, sessionID)
	if err != nil {
		return sessions.User{}, sessions.ErrUserSessionExpired
	}

	user, err = o.findUser(ctx, email)
	if err != nil {
		return sessions.User{}, sessions.ErrUserSessionExpired
	}

	if err := o.updateSessionLastUsed(ctx, sessionID); err != nil {
		return sessions.User{}, err
	}

	return user, nil
}

func (sr *sessionReaper) Work(ctx context.Context) {
	recordCreationStaleThreshold := sr.config.SessionReaperExpiration().Before(
		sr.config.SessionTimeout().Before(time.Now()))
	err := sr.deleteStaleSessions(ctx, recordCreationStaleThreshold)
	if err != nil {
		sr.lggr.Error("unable to reap stale sessions: ", err)
	}
}

// DeleteStaleSessions deletes all sessions before the passed time.
func (sr *sessionReaper) deleteStaleSessions(ctx context.Context, before time.Time) error {
	_, err := sr.ds.ExecContext(ctx, "DELETE FROM sessions WHERE last_used < $1", before)
	return err
}
