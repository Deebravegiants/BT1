### Title
Unbounded allowlist growth causes gas/CPU DoS of Vault gateway authorization - ([File: core/capabilities/vault/allow_list_based_auth.go])

### Summary
The Vault gateway's allowlist-based request authorization loads and linearly scans the *entire* global on-chain allowlisted-requests list on every single incoming request. Any unprivileged workflow owner can grow this list indefinitely (by repeatedly calling `AllowlistRequest` on the `WorkflowRegistry` contract with a far-future expiry), which increases the per-request cost of `AuthorizeRequest` for *every* caller of the Vault gateway, not just the attacker — mirroring the reported `getLockedFunds`/`refundDeposit` pattern where an attacker inflates an array that a shared, unbounded loop must scan on every unrelated call.

### Finding Description
`allowListBasedAuth.AuthorizeRequest` → `findAllowlistedItemWithRetry` calls `r.workflowRegistrySyncer.GetAllowlistedRequests(ctx)` and then does a full linear scan (`fetchAllowlistedItem`) over the returned slice to find a matching digest: [1](#0-0) 

`GetAllowlistedRequests` itself allocates and copies the *entire* in-memory `allowListedRequests` slice on every call: [2](#0-1) 

That in-memory slice is populated by `syncAllowlistedRequests`, which appends every still-unexpired on-chain allowlist entry (across *all* workflow owners) into a single shared slice — there is no per-owner or global cap on how many active entries can exist: [3](#0-2) 

Any address that can link itself as a workflow owner can call the on-chain `AllowlistRequest` function repeatedly with a distant `ExpiryTimestamp` (the test harness exercises this exact call path): [4](#0-3) 

Because `findAllowlistedItemWithRetry` retries up to `retryCount+1` times (default 11 attempts, `allowListBasedAuthRetryCount = 10`) with a 3-second sleep between attempts, and each attempt performs a full slice copy + full linear scan + `fmt.Sprintf`-based string-building over every entry (for debug logging), the per-request cost scales linearly with the size of the shared allowlist: [5](#0-4) 

This is functionally analogous to the reported `BountyCore.getLockedFunds` bug: a single unbounded, globally-shared array is iterated in full on every unprivileged-triggered call path, so one actor's cheap, self-service action (adding entries) degrades performance/availability for all other callers who share the same authorization check.

### Impact Explanation
Every Vault JSON-RPC request handled through the allowlist path (`SecretsCreate`, `SecretsUpdate`, `SecretsDelete`, `SecretsList`, etc., for *all* workflow owners on the DON) pays the cost of scanning the full allowlist on every attempt. As the list grows (bounded only by how many `AllowlistRequest` transactions an attacker is willing to submit, with a long expiry keeping entries "active"), CPU time, memory churn (repeated full-slice copies), and logging overhead per request increase linearly, and with 11 retry attempts per request, that cost multiplies. This can degrade or effectively deny Vault authorization service for all legitimate workflow owners on the DON — a shared-resource availability impact caused by a single unprivileged actor, without requiring any special role.

### Likelihood Explanation
Likelihood is credible but not proven-exploitable from static reading alone: it requires (a) confirming there is no on-chain cap on `AllowlistRequest` calls per owner/globally in the `WorkflowRegistry` contract (not found in this repo's Go bindings/tests — the Solidity contract source itself was not located in this codebase to fully confirm the absence of a cap), and (b) that becoming a "workflow owner" able to call `AllowlistRequest` is a low-friction, unprivileged action (the linking flow references only a signed ownership proof, not admin approval). Given the syncer explicitly paginates by `MaxResultsPerQuery = 1000` when *reading* the list (suggesting the authors anticipated large lists) but does not cap list *size* or *scan cost* on the hot authorization path, this looks like a genuine, currently-unmitigated DoS surface rather than a hardened, bounded design.

### Recommendation
- Index the in-memory allowlist by request digest (e.g., `map[[32]byte]WorkflowRegistryOwnerAllowlistedRequest`) instead of a slice, so `fetchAllowlistedItem` is O(1) instead of O(n).
- Cap the number of active allowlisted requests retained per owner (and/or globally) and prune deterministically, rejecting new `AllowlistRequest` submissions once a per-owner ceiling is reached.
- Avoid building the full `allowedRequestsStrs` debug string list (an O(n) `fmt.Sprintf` loop) on every attempt in production paths; gate it behind a debug-level check or sample it.
- Consider reducing/making adaptive the retry count/interval so that authorization cost does not multiply the base per-request scan cost by up to 11x.

### Proof of Concept
1. An attacker links an EOA as a workflow owner (no special privilege required beyond a valid ownership-proof signature, as exercised in `TestUserWorkflowOperations`/`allowlistRequest` helpers).
2. The attacker repeatedly calls `WorkflowRegistry.AllowlistRequest(digest, farFutureExpiry)` on-chain with many distinct digests, growing `totalAllowlistedRequests` into the tens/hundreds of thousands, each with an expiry far in the future so `syncAllowlistedRequests` keeps them "active" (not pruned).
3. `syncAllowlistedRequests` on the Vault DON node syncs these into the single shared `w.allowListedRequests` slice with no cap: [6](#0-5) 
4. Any legitimate user's subsequent `AuthorizeRequest` call (e.g., a normal `SecretsList` request from a different, unrelated workflow owner) now triggers up to 11 full copies (`GetAllowlistedRequests`) and full linear scans (`fetchAllowlistedItem`) of this bloated list, each iteration also building a full-length debug string slice, materially increasing latency/CPU for every Vault request served by that node — a denial-of-service effect proportional to how many entries the attacker chooses to create.

func (r *allowListBasedAuth) findAllowlistedItemWithRetry(ctx context.Context, req jsonrpc.Request[json.RawMessage], requestDigest string, requestDigestBytes32 [32]byte) (*workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest, []string, error) {
	for attempt := 0; attempt <= r.retryCount; attempt++ {
		allowedRequests := r.workflowRegistrySyncer.GetAllowlistedRequests(ctx)
		allowedRequestsStrs := make([]string, 0, len(allowedRequests))
		for _, rr := range allowedRequests {
			allowedReqStr := fmt.Sprintf("AuthorizedOwner: %s, RequestDigest: %s, ExpiryTimestamp: %d", rr.Owner.Hex(), hex.EncodeToString(rr.RequestDigest[:]), rr.ExpiryTimestamp)
			allowedRequestsStrs = append(allowedRequestsStrs, allowedReqStr)
		}
		r.lggr.Debugw("AllowListBasedAuth loaded allowlisted requests", "method", req.Method, "requestID", req.ID, "attempt", attempt+1, "allowedRequests", allowedRequestsStrs)

		allowlistedRequest := r.fetchAllowlistedItem(allowedRequests, requestDigestBytes32)
		if allowlistedRequest != nil {
			return allowlistedRequest, allowedRequestsStrs, nil
		}
		if attempt == r.retryCount {
			return nil, allowedRequestsStrs, nil
		}

		r.lggr.Debugw("AllowListBasedAuth request digest not yet allowlisted, retrying",
			"method", req.Method,
			"requestID", req.ID,
			"digestHexStr", requestDigest,
			"attempt", attempt+1,
			"maxAttempts", r.retryCount+1,
			"retryInterval", r.retryInterval)
		if err := sleepWithContext(ctx, r.retryInterval); err != nil {
			r.lggr.Debugw("AllowListBasedAuth retry canceled", "method", req.Method, "requestID", req.ID, "error", err)
			return nil, nil, err
		}
	}

	return nil, nil, nil // unreachable: loop always returns
}

func (r *allowListBasedAuth) fetchAllowlistedItem(allowListedRequests []workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest, digest [32]byte) *workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest {
	for _, item := range allowListedRequests {
		if item.RequestDigest == digest {
			return &item
		}
	}
	return nil
}

func (w *workflowRegistry) syncAllowlistedRequests(ctx context.Context) {
	ticker := w.getTicker(defaultTickIntervalForAllowlistedRequests)
	w.lggr.Debug("starting syncAllowlistedRequests")
	for {
		select {
		case <-ctx.Done():
			w.lggr.Debug("shutting down syncAllowlistedRequests, %s", ctx.Err())
			return
		case <-ticker:
			newAllowListedRequests, totalAllowlistedRequests, head, err := w.getAllowlistedRequests(ctx, w.contractReader)
			if err != nil {
				w.lggr.Errorw("failed to call getAllowlistedRequests", "err", err)
				continue
			}
			w.allowListedMu.Lock()
			// Prune expired requests
			activeAllowlistedRequests := []workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest{}
			expiredRequestsCount := 0
			for _, request := range w.allowListedRequests {
				if int64(request.ExpiryTimestamp) > time.Now().Unix() {
					activeAllowlistedRequests = append(activeAllowlistedRequests, request)
				} else {
					expiredRequestsCount++
				}
			}

			// Add new requests
			activeAllowlistedRequests = append(activeAllowlistedRequests, newAllowListedRequests...)
			w.allowListedRequests = activeAllowlistedRequests
			w.lastSeenAllowlistedRequestsCount = totalAllowlistedRequests
			w.lggr.Debugw("synced allowlisted requests",
				"newRequestsNum", len(newAllowListedRequests),
				"expiredRequestsNum", expiredRequestsCount,
				"activeRequestsNum", len(w.allowListedRequests),
				"lastSeenOnchainRequestsNum", w.lastSeenAllowlistedRequestsCount,
				"blockHeight", head.Height,
			)
			w.allowListedMu.Unlock()
		}
	}

func (w *workflowRegistry) GetAllowlistedRequests(_ context.Context) []workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest {
	w.allowListedMu.RLock()
	defer w.allowListedMu.RUnlock()
	allowListedRequests := make([]workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest, len(w.allowListedRequests))
	copy(allowListedRequests, w.allowListedRequests)
	return allowListedRequests
}
