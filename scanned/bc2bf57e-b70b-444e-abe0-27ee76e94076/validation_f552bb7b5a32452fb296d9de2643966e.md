## Title
Unprivileged Vault client can crash the DON's allowlist authorizer via a wrong-length request digest, causing a slice-to-array conversion panic - (File: core/capabilities/vault/allow_list_based_auth.go)

## Summary
`req.Digest()` is a hash function over caller-controlled JSON-RPC request fields (`ID`, `Method`, `Params`), and `AllowListBasedAuth.AuthorizeRequest` hex-decodes that digest and immediately converts it to a fixed `[32]byte` array without validating its length first, exactly mirroring the russh `clone_from_slice` bug class (unchecked length before a fixed-size conversion of externally influenced data).

## Finding Description
In `core/capabilities/vault/allow_list_based_auth.go`, `AuthorizeRequest` computes a digest from the incoming (unprivileged, gateway-forwarded) JSON-RPC request and converts it to a fixed-size array without a length check: [1](#0-0) 

```go
requestDigest, err := req.Digest()
...
requestDigestBytes, err := hex.DecodeString(requestDigest)
...
requestDigestBytes32 := [32]byte(requestDigestBytes)
```

The Go language spec makes `[32]byte(slice)` a runtime-panicking operation ("cannot convert slice with length N to array or pointer to array with length 32") whenever `len(slice) != 32`, which is the structural analog of Rust's `clone_from_slice` panicking on a length mismatch in the russh advisory. This is the same bug class described in the report: a fixed-size conversion performed on a value whose length is not independently validated, unlike the sibling code paths that do check length explicitly — for example `system-tests/lib/cre/workflow/secrets.go` guards the identical conversion: [2](#0-1) 
```go
requestDigestBytes, err := hex.DecodeString(requestDigest)
...
if len(requestDigestBytes) != 32 {
    return errors.Errorf("invalid request digest length: got %d bytes, want 32", len(requestDigestBytes))
}
var reqDigestBytes [32]byte
copy(reqDigestBytes[:], requestDigestBytes)
```
This shows the same team is aware elsewhere that this exact conversion needs a length check — but `allow_list_based_auth.go` (the production authorizer used on the Vault DON node, reachable via Gateway → Vault handler → `AuthorizeRequest`) omits it.

**However**, I could not confirm that `req.Digest()` can actually return a value whose hex-decoded length differs from 32 bytes. Every code path I found treats `Digest()` as returning a fixed-length hash (consistent with SHA-256/Keccak output), and I was unable to inspect the `jsonrpc2.Request.Digest()` implementation itself (it lives in the external `chainlink-common` package, `github.com/smartcontractkit/chainlink-common/pkg/jsonrpc2`, which is outside this repo's indexed source). If `Digest()` is a fixed-output-size hash (e.g., always SHA-256/Keccak-256, 32 bytes), then no attacker-controlled input can ever produce a non-32-byte digest, and this code path is **not exploitable** regardless of the input's `ID`/`Method`/`Params` content — the missing check would be defensive-only, not a real vulnerability.

## Impact Explanation
If `req.Digest()`'s output length were ever non-32-bytes-when-hex-decoded (e.g., due to a future codec change, an error-swallowing bug, or an edge case in canonicalization that I could not verify from this repo), an unprivileged/unauthenticated party sending a single crafted JSON-RPC request to the Vault gateway could crash the node-side `AuthorizeRequest` call path with a runtime panic, mirroring the pre-auth DoS impact of the russh advisory (deterministic single-request crash before authorization succeeds). Given the panic's location (goroutine handling of a gateway-forwarded per-request call), if not caught by an isolating goroutine recover, it could crash the vault node process, which is more severe than russh's per-connection-only impact.

## Likelihood Explanation
Low-to-unverified. I found no evidence in this repo that `req.Digest()` (implemented in the external `chainlink-common` package) can return anything other than a fixed-length hash digest for well-formed JSON-RPC requests, which is the necessary precondition for the `[32]byte(...)` conversion to panic. Without visibility into that function's implementation, I cannot confirm a real attacker-controlled trigger exists.

## Recommendation
Regardless of confirmed exploitability, defense-in-depth suggests adding the same length check used elsewhere in this codebase (`system-tests/lib/cre/workflow/secrets.go:195-197`) before the conversion in `core/capabilities/vault/allow_list_based_auth.go:46`:
```go
if len(requestDigestBytes) != 32 {
    return nil, fmt.Errorf("invalid request digest length: got %d, want 32", len(requestDigestBytes))
}
requestDigestBytes32 := [32]byte(requestDigestBytes)
```
This would make the authorizer robust even if `Digest()`'s guarantees ever change, and is consistent with how the rest of the codebase treats this exact conversion.

## Proof of Concept
Not reproducible from the information available in this repo: I could not locate or verify the implementation of `jsonrpc2.Request.Digest()` to confirm it can emit a value that hex-decodes to something other than 32 bytes. Without that, no concrete PoC input can be constructed. If Devin (with full repository/dependency access) confirms `Digest()`'s output length is fixed and hash-based, this finding should be downgraded to **no vulnerability** (defensive-only gap).

**Overall assessment: uncertain / likely not exploitable.** Given the inability to confirm the actual root-cause precondition (variable-length digest output) from the available context, and per the strict validation requirement to prove root cause with exact file/function support, I cannot assert this is a confirmed live vulnerability. Recommend a Devin session with full dependency access (`chainlink-common/pkg/jsonrpc2`) to inspect `Request.Digest()`'s implementation and settle whether the length precondition can ever be violated by unprivileged input.
