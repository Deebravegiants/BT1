## Title
Unrecovered panic (negative-length `strings.Repeat`) from unvalidated workflow ID/owner format in HTTP trigger handler - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

## Summary
The `normalizeHex` helper in the CRE HTTP-trigger gateway path computes a padding length as `expectedHexLength - len(hexStr)` and passes it directly to `strings.Repeat`, without checking that the result is non-negative. `strings.Repeat` panics if given a negative count. The length validation performed upstream (`validateHexInput`) only checks the *total* string length against the expected length (which includes the `"0x"` prefix), but does not require the `"0x"` prefix to actually be present. An attacker-supplied `workflowID`/`workflowOwner` that is exactly `workflowIDLength` (66) or `workflowOwnerLength` (42) hex characters **without** the `0x` prefix passes validation but causes `normalizeHex` to compute a negative repeat count and panic.

## Finding Description
`normalizeHex` is:
```go
func normalizeHex(input string, length int) string {
	hexStr := strings.TrimPrefix(input, "0x")
	expectedHexLength := length - 2
	paddedHex := strings.Repeat("0", expectedHexLength-len(hexStr)) + hexStr
	return "0x" + paddedHex
}
``` [1](#0-0) 

The only validation performed before this is called is `validateHexInput`, which checks `len(input) > expectedLength` and that the string decodes as hex after `TrimPrefix(input, "0x")` — it never enforces that the `0x` prefix is present:
```go
func validateHexInput(input string, expectedLength int) error {
	...
	if len(input) > expectedLength {
		return fmt.Errorf(...)
	}
	hexStr := strings.TrimPrefix(input, "0x")
	_, err := hex.DecodeString(hexStr)
	...
}
``` [2](#0-1) 

If a client submits `workflowID` as exactly 66 lowercase hex characters with **no** `0x` prefix (e.g., `"aa...aa"` 66 chars), `validateWorkflowID`/`validateHexInput` pass (length ≤ 66, valid hex). `resolveWorkflowID` then calls `normalizeHex(workflowID, workflowIDLength)`: [3](#0-2) 
Inside `normalizeHex`, since there's no `0x` prefix, `TrimPrefix` is a no-op, so `hexStr` stays 66 chars; `expectedHexLength = 66-2 = 64`; `64 - 66 = -2`, and `strings.Repeat("0", -2)` panics with `"strings: negative Repeat count"`. The same applies to `workflowOwner` (`workflowOwnerLength = 42`).

This is reachable directly from an unauthenticated/unprivileged HTTP client request: `HandleJSONRPCUserMessage` → `HandleUserTriggerRequest` → `resolveWorkflowID` → `normalizeHex`, all before the request is authorized (`authorizeRequest` happens after `resolveWorkflowID`): [4](#0-3) [5](#0-4) 

## Impact Explanation
This mirrors the reported bug class: an unchecked subtraction that can go negative and is used to derive a length/count parameter for an operation that panics/underflows on invalid input, causing a crash. Here, the panic occurs inside `HandleJSONRPCUserMessage`, invoked synchronously from `gateway.ProcessRequest` per incoming HTTP request: [6](#0-5) 
I could not find a `recover()` in the gateway request-handling path (`gateway.go`, `http_handler.go`, `http_trigger_handler.go`); the only `recover()` hit in the whole gateway package is in a test file (`response_cache_test.go`), not production code. If the standard library's `net/http` server is used underneath (recovering per-request panics in its own goroutine), the blast radius may be limited to a single request/connection rather than crashing the whole process — I was unable to fully confirm the HTTP server setup (`httpServer`) recovers per-request panics, since that code wasn't reachable within the remaining investigation budget. At minimum this is a reliable, unauthenticated denial-of-service against a single request handler goroutine, and potentially the whole gateway service if no per-request recovery exists at the transport layer.

## Likelihood Explanation
High. The trigger path validating `workflowID`/`workflowOwner` is reachable pre-authentication by any client able to reach the gateway's HTTP trigger endpoint, and the malformed input (right length, missing `0x` prefix) is trivial to construct and requires no special privileges or node compromise.

## Recommendation
- In `validateHexInput`, require the `0x` prefix explicitly (e.g., `strings.HasPrefix(input, "0x")`) rather than only checking length/hex-decodability after an optional trim.
- In `normalizeHex`, guard against `expectedHexLength - len(hexStr) < 0` and return an error (or clamp to 0) instead of calling `strings.Repeat` with a value that can be negative.
- Add a panic-recovery wrapper around per-request handling in the gateway (`ProcessRequest`/handler dispatch) as defense-in-depth so malformed input from any handler cannot take down the process.

## Proof of Concept
Send an HTTP trigger request (`workflows.execute`) with:
```json
{
  "jsonrpc": "2.0",
  "id": "poc",
  "method": "workflows.execute",
  "params": {
    "workflow": {
      "workflowID": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
    },
    "input": {}
  }
}
```
where `workflowID` is exactly 66 lowercase hex characters with no `0x` prefix. This passes `validateWorkflowID`/`validateHexInput` (length ≤ 66, valid hex), then `resolveWorkflowID` calls `normalizeHex(workflowID, 66)`, which panics on `strings.Repeat("0", -2)`. [7](#0-6) [8](#0-7)

func validateHexInput(input string, expectedLength int) error {
	if input != strings.ToLower(input) {
		return errors.New("must be lowercase")
	}

	if len(input) > expectedLength {
		return fmt.Errorf("hex string too long: expected at most %d characters, got %d", expectedLength, len(input))
	}

	hexStr := strings.TrimPrefix(input, "0x")
	_, err := hex.DecodeString(hexStr)
	if err != nil {
		return errors.New("must be a valid hex string")
	}

	return nil
}

// normalizeHex normalizes a hex string by stripping 0x prefix, padding with leading zeros, and adding 0x prefix back
func normalizeHex(input string, length int) string {
	hexStr := strings.TrimPrefix(input, "0x")

	expectedHexLength := length - 2
