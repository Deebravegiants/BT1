### Title
Unbounded in-memory HTTP response cache in Gateway HTTP Action handler enables memory-exhaustion DoS - (File: core/services/gateway/handlers/capabilities/v2/response_cache.go)

### Summary
The Mattermost advisory (GHSA-w496-f5qq-m58j) describes an endpoint that caches arbitrary external HTTP responses without bounding total cache size, letting a client fill server memory. The Chainlink Gateway's HTTP Handlers V2 implements an analogous pattern: `responseCache` caches outbound HTTP Action responses keyed by a hash of the request, with no maximum entry count or memory bound — only time-based (TTL) expiry via a periodic sweep.

### Finding Description
`responseCache` stores every cacheable outbound HTTP response in a plain Go map with no capacity limit: [1](#0-0) 

Entries are only removed by `DeleteExpired`, which runs on a periodic timer and deletes entries strictly by TTL, never by memory pressure or entry count: [2](#0-1) 

The cache is populated from `makeOutgoingRequest`, invoked whenever a workflow node forwards an outbound HTTP Action on behalf of a workflow: if `CacheSettings.Store` is true (or `MaxAgeMs>0`, which also stores via `Fetch`), the response is written into the map keyed by `req.Hash()` (method/URL/headers/body/workflow scope, per the handler's README): [3](#0-2) [4](#0-3) 

The only mitigations present are per-node/global request-rate limiters and a per-response byte cap enforced by `http.MaxBytesReader` in the HTTP client (`MaxResponseBytes`), but neither of these bounds the aggregate size of the cache map itself: [5](#0-4) [6](#0-5) 

By contrast, another cache in the same codebase (`requestCache` in `core/services/gateway/handlers/common/requestcache.go`) explicitly enforces a `maxCacheSize` and rejects new entries once full: [7](#0-6) 

`responseCache` has no equivalent safeguard — this is the design gap that mirrors the Mattermost `/redirect_location` bug class: caching large, attacker-influenceable items without a bound on total cached memory.

### Impact Explanation
Because the cache key is derived from the full request (URL, headers, body, workflow scope) and requests are driven by workflow definitions (attacker-influenceable content within the workflow), a workflow that issues many distinct outbound HTTP Action requests with `CacheSettings.Store=true` (or `MaxAgeMs>0`) against endpoints returning large, cacheable (2xx/4xx) bodies can cause the gateway to accumulate an unbounded number of large cache entries within the TTL window (default configurable, e.g. `OutboundRequestCacheTTLMs`). Each entry can be as large as the configured `MaxResponseBytes` (seen as high as 50–100 MB in test/deployment configs). Sustained traffic within the TTL window can drive gateway memory usage far beyond intended limits, risking OOM and denial of service for the Gateway process (impacting all DONs/workflows it serves), consistent with CWE-400 in the referenced advisory.

### Likelihood Explanation
Reaching this path only requires a workflow node forwarding HTTP Action requests to the gateway on behalf of a workflow — no privileged/administrative access is required beyond what any workflow owner already has to define outbound HTTP actions with `CacheSettings.Store=true`. Per-node and global rate limiters throttle request *rate* but do not cap the *number of distinct cache keys* accumulated over the TTL window, so a moderate, sustained rate of varied requests (e.g., varying URL query parameters or headers) is sufficient to grow the cache unboundedly before the next cleanup sweep.

### Recommendation
Add a hard cap on the response cache (max entry count and/or max aggregate byte size), evicting oldest/least-recently-used entries when the limit is reached, similar to the `maxCacheSize` enforcement already present in `handlers/common/requestcache.go`. Additionally, consider capping cacheable response size independently of the general `MaxResponseBytes` request cap, and exposing/alerting on cache memory usage via `metrics.RecordCacheSize` (already tracked) with an enforced ceiling rather than pure observability.

### Proof of Concept
1. Deploy a workflow that issues HTTP Action requests with `CacheSettings.Store = true` (or `MaxAgeMs > 0`) against attacker-controlled/attacker-influenced endpoints returning large 2xx bodies close to the configured `MaxResponseBytes` limit.
2. Vary a request parameter (query string, header, or body) on each call so that `req.Hash()` produces a new cache key per call — see `Fetch`/`Set` keying by `req.Hash()`: [8](#0-7) 
3. Repeat at a rate within the per-node/global rate limiter's allowance, sustained for the duration of `OutboundRequestCacheTTLMs` (e.g. 10 minutes default).
4. Observe gateway process memory grow roughly proportional to `(sustained request rate) × TTL × MaxResponseBytes`, since `DeleteExpired` only reclaims memory after entries age out and imposes no ceiling during accumulation: [2](#0-1)

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

func (rc *responseCache) DeleteExpired(ctx context.Context) int {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	now := time.Now()
	var expiredCount int
	for key, cachedResp := range rc.cache {
		if now.After(cachedResp.storedAt.Add(rc.ttl)) {
			delete(rc.cache, key)
			expiredCount++
		}
	}
	rc.lggr.Debugw("Removed expired cached HTTP responses", "count", expiredCount, "remaining", len(rc.cache))
	rc.metrics.IncrementCacheCleanUpCount(ctx, int64(expiredCount), rc.lggr)
	rc.metrics.RecordCacheSize(ctx, int64(len(rc.cache)), rc.lggr)
	return expiredCount
}

### 3.2 Caching Behavior

- **Cacheable Responses**: 2xx (success) and 4xx (client error) status codes.
- **Cache TTL**: Configurable, default 10 minutes
