Target: IntentPayloadBuilder.setNonce. Attacker input: any string accepted as `nonce` without format validation, e.g., a nonce string previously observed by the caller from another already-published (but not yet confirmed as executed) MultiPayload's payload.nonce, reused via setNonce(observedNonce) on a *different* intents array. Preconditions: setNonce has no check against reuse, no check that it matches a currently valid VersionedNonceBuilder encoding, and takes precedence over any generated nonce (confirmed by 'setNonce takes precedence over setNonceRandomBytes' test). Call sequence: sdk.intentBuilder().setNonce(observedNonce).addIntents([...differentIntents]).buildAndSign(signer) -> sdk.sendSignedIntents(). Equality that breaks: SIGNED == BUILT identity for nonce binding - the caller intends a fresh, unique nonce per distinct intent set, but setNonce lets a caller (or code forwarding a caller-supplied nonce string) bind a completely different set of intents to a nonce identity already associated with prior intents, risking either (a) rejection as NONCE_USED after the first executes, or (b) if the first was never executed, a race where either payload could be the one that lands. Scoped impact: High - integrator code paths that let a counterparty submit a 'nonce' string for pre-signed payload construction can bind an unrelated debit to a nonce identity the caller does not control the semantics of. Proof idea: vitest constructing two IntentPayloadBuilder instances calling setNonce with the same observed nonce string but different addIntent() calls, buildAndSign both, assert both signed payloads carry identical `nonce` and `verifying_contract` yet different `intents`.
