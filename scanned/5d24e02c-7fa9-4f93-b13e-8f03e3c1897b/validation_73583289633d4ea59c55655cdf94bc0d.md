Based on my analysis, I found a concrete analog in `newHTTPFetcher`.

### Title
Percent-encoded/raw path-traversal scope bypass in workflow artifact `newHTTPFetcher` - (File: `core/services/workflows/syncer/v2/fetcher.go`)

### Summary
`newHTTPFetcher` builds an outbound artifact-fetch URL by joining a configured `baseURL` with the workflow-registry-supplied `BinaryURL`/`ConfigURL` path (`req.URL`), intending to scope all fetches under `baseURL`'s path — the same "base + wildcard suffix" scoping pattern the Nitro advisory describes for `routeRules` proxies. The path-cleaning logic does not canonicalize percent-encoded traversal sequences and, in the raw (non-encoded) `..` case, is fully bypassable, allowing the actual request to be sent outside the intended base path.

### Finding Description
`newHTTPFetcher` computes the forwarded path as: [1](#0-0) 

`filepath.Clean(req.URL)` only normalizes `.`/`..` segments that are literal path separators in the string; it does not decode `%2e%2e%2f`/`..%2f` first. If `req.URL` contains `..%2f` (a literal 5-character token, not an actual slash), `filepath.Clean` treats the whole thing as one opaque path segment (no traversal collapsing occurs, matching the Nitro bug's "Nitro sees `..%2f` as opaque characters at match time" behavior), and `filepath.Join(u.Path, cleanPath)` simply appends it as a subpath under `baseURL`. If the upstream artifact/storage host later decodes `%2F` to `/` and resolves `..`, the request resolves outside the configured base path — the exact bypass class in the advisory.

Separately, even *without* encoding, `filepath.Join` itself collapses raw `../../` sequences against the base path (e.g. `filepath.Join("/base", "../../secret")` → `/secret`), so a `BinaryURL`/`ConfigURL` value containing literal `../` can escape `baseURL` entirely at request-construction time, which is a stronger, more direct version of the same "scope fence bypass" problem.

By contrast, `newFileFetcher` correctly enforces the fence by checking `strings.HasPrefix(fullPath, basePath+separator)` *after* cleaning, which is the correct pattern; `newHTTPFetcher` lacks any equivalent post-join containment check.

### Impact Explanation
`newHTTPFetcher`/`NewFetcherFunc` is wired in as the `FetcherFunc` used by `Store.FetchWorkflowArtifacts` to download a workflow's binary/config artifacts: [2](#0-1) 
`binaryURL`/`configURL` originate from the on-chain `WorkflowRegisteredEvent.BinaryURL`/`ConfigURL` fields, which are attacker-influenced inputs supplied by whoever registers a workflow: [3](#0-2) 
If the node operator configures `NewFetcherFunc` with a fixed `baseURL` intended to fence artifact fetches to a specific storage prefix (bypassing the gateway path per the `NewFetcher` doc comment "bypasses the gateway"), a workflow owner could craft a `BinaryURL`/`ConfigURL` value to make the node issue outbound HTTP requests outside that intended prefix — potentially reaching internal endpoints reachable from the node, mirroring the Nitro advisory's "any HTTP path reachable from the [fetcher] to the upstream could be requested" impact.

### Likelihood Explanation
Likelihood is moderate: it requires (a) an operator configuring `NewFetcherFunc` with an HTTP(S) `baseURL` used as a scoping fence (rather than exclusively the gateway/storage-service flow, which is the documented primary path), and (b) an upstream host that decodes `%2F`/resolves `..` after receiving the forwarded path — same upstream-dependent caveat noted in the original advisory. The raw (non-percent-encoded) `../` variant has no such upstream dependency and is directly exploitable purely via `filepath.Join`'s traversal-collapsing behavior at request-construction time, which is more immediately triggerable by any actor able to register a workflow with a crafted `BinaryURL`/`ConfigURL`.

### Recommendation
In `newHTTPFetcher`, after computing `u.Path = filepath.Join(u.Path, cleanPath)`, verify the resulting path still has the original base path as a prefix (mirroring the containment check already used in `newFileFetcher`), and reject/percent-decode-then-recheck the request if it does not. Additionally, percent-decode `req.URL`'s path segment before cleaning (or explicitly reject encoded slash/dot sequences) so `..%2f`-style tokens cannot be forwarded as opaque literals to an upstream that may decode them.

### Proof of Concept
1. Configure `NewFetcherFunc("https://artifacts.internal/public", lggr)` as the fetcher, intending to restrict fetches to `/public/**`.
2. Register a workflow (or otherwise trigger `FetchWorkflowArtifacts`) with `BinaryURL: "../../admin/secret.json"`.
3. `newHTTPFetcher` computes `cleanPath = "../../admin/secret.json"` (no leading slash to trim), then `u.Path = filepath.Join("/public", "../../admin/secret.json")`, which `filepath.Join` collapses to `/admin/secret.json` — outside `/public`, despite the intended scoping.
4. Alternatively, with `BinaryURL: "..%2f..%2fadmin%2fsecret.json"`, `filepath.Clean` leaves the token intact (no literal `/`), and it is appended verbatim as `/public/..%2f..%2fadmin%2fsecret.json`; if `artifacts.internal` decodes `%2F` before resolving `..`, the effective fetch escapes `/public`.
