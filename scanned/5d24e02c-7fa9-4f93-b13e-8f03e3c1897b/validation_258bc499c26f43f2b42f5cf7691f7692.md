## Analysis Result



### Title
Username Enumeration via Distinguishable Login Error Messages on `/sessions` - (File: core/sessions/localauth/orm.go)

### Summary
The `/sessions` login endpoint returns different, descriptive error strings depending on whether the submitted email exists versus whether the password was wrong, across all three `AuthenticationProvider` implementations (local, LDAP, OIDC). This is forwarded verbatim to the unauthenticated caller by `SessionsController.Create`, allowing an unprivileged network client to enumerate valid Chainlink node operator usernames/emails.

### Finding Description
`SessionsController.Create` binds the login payload and calls `AuthenticationProvider().CreateSession`, then on failure returns the raw error to the client with `jsonAPIError(c, http.StatusUnauthorized, err)`: [1](#0-0) 

The local auth ORM explicitly distinguishes the two failure cases with different error text and different audit event codes: [2](#0-1) 

The same pattern (`"invalid email"` vs `"invalid password"`) is repeated in the OIDC local-login fallback: [3](#0-2) 

And in LDAP, a distinct "no assigned groups" vs "check credentials" error path exists as well: [4](#0-3) 

Both `AuthLoginFailedEmail` and `AuthLoginFailedPassword` are separate audit event constants, confirming the codebase itself treats "wrong email" and "wrong password" as semantically distinct, distinguishable outcomes: [5](#0-4) 

Since `jsonAPIError` propagates the underlying error's message into the JSON response body, an attacker submitting a candidate email with an arbitrary password can distinguish "Invalid email" (email does not exist) from "Invalid password" (email exists, wrong password), enabling systematic username/email enumeration against the node's operator UI.

Note: unlike the Kanboard CVE, the IP-spoofing brute-force bypass half of the bug class does **not** apply here — Chainlink explicitly disables trust in proxy headers via `engine.RemoteIPHeaders = nil // don't trust default headers: "X-Forwarded-For", "X-Real-IP"`, so `c.ClientIP()` used by the rate limiter falls back to the actual TCP `RemoteAddr` and cannot be spoofed by a client-controlled header: [6](#0-5) 

The unauthenticated rate limiter is still keyed per-request via this non-spoofable IP, and is applied to `/sessions`: [7](#0-6) 

### Impact Explanation
An unauthenticated attacker can enumerate valid operator/API user emails registered on a Chainlink node's `/sessions` endpoint. This narrows subsequent credential-stuffing or brute-force attacks (bounded by the rate limiter) to confirmed accounts, and can also be used for reconnaissance/targeting of specific operators. Impact is limited to information disclosure of account existence — it does not itself allow authentication bypass or fund movement, and the IP-spoofing bruteforce bypass component of the original CVE is not reproducible here due to the `RemoteIPHeaders = nil` mitigation.

### Likelihood Explanation
High likelihood of exploitability: the endpoint is unauthenticated, requires no special network position, and the distinguishing error text is returned directly to the HTTP client on every login attempt (confirmed by the existing test `TestSessionsController_Create`, which does not assert body content is generic for failure cases): [8](#0-7) 

### Recommendation
Return a single, generic "invalid email or password" error/message for all `CreateSession` failure paths (local, LDAP, OIDC) instead of distinguishing "Invalid email" from "Invalid password", and ensure `jsonAPIError` for `/sessions` failures does not leak the underlying differentiated error text to the client. Keep the differentiated audit events (`AuthLoginFailedEmail`/`AuthLoginFailedPassword`) server-side only.

### Proof of Concept
1. `POST /sessions` with `{"email":"nonexistent@node.com","password":"x"}` → response body contains `"Invalid email"`.
2. `POST /sessions` with `{"email":"<known-valid-admin-email>","password":"wrongpass"}` → response body contains `"Invalid password"`.
3. Automate step 1/2 against a wordlist of candidate emails (bounded by the `Unauthenticated`/`UnauthenticatedPeriod` rate limit) to enumerate valid accounts on the node.

```go
func sessionRoutes(app chainlink.Application, r *gin.RouterGroup) {
	config := app.GetConfig()
	rl := config.WebServer().RateLimit()
	unauth := r.Group("/", rateLimiter(
		rl.UnauthenticatedPeriod(),
		rl.Unauthenticated(),
	))
	sc := NewSessionsController(app)
	unauth.POST("/sessions", sc.Create)
	auth := r.Group("/", auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession))
	auth.DELETE("/sessions", sc.Destroy)
}
```
