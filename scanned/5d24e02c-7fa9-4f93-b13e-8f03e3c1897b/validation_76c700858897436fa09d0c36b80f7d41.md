### Title
HTTP Action response cache omits `WorkflowID` and mTLS credentials from its cache key, breaking documented workflow isolation - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
The GMGN incident describes corrupted/incorrect data being served (token details, holdings, transaction records) after a flood of crawler-style traffic — a classic symptom of a shared response cache keyed too broadly and serving one client's cached data to another. The Chainlink Runtime Environment (CRE) HTTP Action gateway handler has an analogous internal-tenancy version of this bug: the `responseCache` used to short-circuit outbound HTTP requests is documented as being workflow-isolated but its actual cache key omits `WorkflowID` entirely and does not fold in mTLS client credentials.

### Finding Description
The gateway's HTTP capability handler v2 caches outbound HTTP action responses to avoid redundant external calls, keyed by `gateway.OutboundHTTPRequest.Hash()`: [1](#0-0) 

The documentation for this component explicitly states the cache is meant to prevent cross-workflow leakage: "Cache Key: Generated from workflow ID and request hash ... Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage." [2](#0-1) 

However, the repo's own test suite proves the opposite: `Hash()` is explicitly verified to be *identical* across different `WorkflowID`s, and is only differentiated by `WorkflowOwner`: [3](#0-2) 

Because caching is done purely on request shape (method, URL, headers, body) plus `WorkflowOwner`, any two different workflows belonging to the same owner that issue the same outbound HTTP request will read/write the same cache entry, regardless of `WorkflowID`. This directly contradicts the documented workflow-level isolation guarantee, and the `Fetch`/`Set` cache logic performs no additional per-workflow segregation: [4](#0-3) 

Separately, `gateway_common.OutboundHTTPRequest.Mtls` (client certificate/private key) is used to select which throwaway mTLS-authenticated HTTP client performs the outbound call: [5](#0-4)  yet this credential material is not part of the request hash used for caching, so a cached response obtained via one workflow's mTLS-authenticated call can be replayed to a different request (with different or no mTLS credentials) for the same owner/URL/method/headers/body, as long as `CacheSettings.MaxAgeMs`/`Store` request the cache path: [6](#0-5) 

### Impact Explanation
This is a cross-workflow response confusion bug within the gateway's internet-facing HTTP capability handler. Two workflows under the same owner (a routine multi-tenant configuration for CRE users who run several workflows) that call the same endpoint can silently receive each other's cached responses, even though the code and documentation assert workflow-level cache isolation. Worse, because mTLS credential material is excluded from the hash, a response fetched using one workflow's client certificate can be served, from cache, to a subsequent request lacking that certificate — effectively bypassing the intended per-request mTLS authentication for that external endpoint and disclosing privileged response content to a caller that never supplied valid credentials for it. The severity is bounded by the requirement that `WorkflowOwner` match and the rest of the request (method/URL/headers/body) be identical, but this is a realistic condition for workflows sharing configuration templates or default headers.

### Likelihood Explanation
Likelihood is moderate: it requires two workflows under the same owner (or an owner running many workflows) to issue requests that are identical apart from `WorkflowID`/mTLS credentials, and for `CacheSettings.MaxAgeMs`/`Store` to be enabled on the request (attacker/workflow-controlled fields). Given `WorkflowOwner`-scoped rate limits and the multi-tenant CRE model where an owner may run several concurrent workflows hitting shared HTTP endpoints with default settings, this is readily reachable without any special privilege — a workflow author only needs to know they share an owner/org with another workflow calling the same endpoint.

### Recommendation
Include `WorkflowID` in the cache key (or key strictly on `WorkflowID` if that's the intended isolation boundary per the README) and include a hash/fingerprint of `Mtls` credentials (or bypass caching entirely for mTLS requests) in `gateway.OutboundHTTPRequest.Hash()` so that cached responses can never be served across workflow or credential boundaries. Add regression tests in `response_cache_test.go` asserting that different `WorkflowID`s and different `Mtls` credentials produce different hashes, matching the documented workflow-isolation guarantee.

### Proof of Concept
1. Workflow A (WorkflowID = "wf-A", WorkflowOwner = "0xOwner") issues an `OutboundHTTPRequest{Method: GET, URL: "https://api.example.com/data", CacheSettings:{MaxAgeMs: 60000, Store:true}}`; the gateway executes it and caches the response under `Hash()` (owner+method+URL+headers+body, no WorkflowID).
2. Workflow B (WorkflowID = "wf-B", same WorkflowOwner = "0xOwner") issues the identical request shape shortly after.
3. Per `responseCache.Fetch` [7](#0-6) , Workflow B receives Workflow A's cached response without a fresh outbound call, confirmed by the test harness's own assertion that differing `WorkflowID` produces the same hash [8](#0-7) , violating the documented workflow-scoped isolation.

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	// Slow path: singleflight deduplicates concurrent fetches per key.
	// Cache check + store happen inside the flight so the key isn't released
	// until the result is cached, closing the race window between singleflight
	// completion and cache write.
	result, _, _ := rc.flight.Do(cacheKey, func() (any, error) {
		// Re-check cache: a previous flight may have just stored the result.
		rc.cacheMu.RLock()
		cachedResp, exists := rc.cache[cacheKey]
		rc.cacheMu.RUnlock()
		if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
			rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
			return cachedResp.response, nil
		}

		response := fetchFn()

		if storeOnFetch && isCacheableStatusCode(response.StatusCode) {
			rc.cacheMu.Lock()
			rc.cache[cacheKey] = &cachedResponse{
				response: response,
				storedAt: time.Now(),
			}
			rc.cacheMu.Unlock()
		}

		return response, nil
	})

	return result.(gateway.OutboundHTTPResponse)
}

// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}

func (h *gatewayHandler) send(ctx context.Context, httpReq network.HTTPRequest, req gateway_common.OutboundHTTPRequest) (*network.HTTPResponse, error) {
	if req.Mtls == nil {
		return h.httpClient.Send(ctx, httpReq)
	}

	if h.httpClientFactory == nil {
		return nil, errors.New("nil http client factory, cannot make mtls request")
	}

	// Instantiate a throwaway HTTP client with the provided Mtls client certificate provided.
	// We do this to ensure that we don't accidentally leak auth'd connections to other users.
	// Note: this isn't a DOS vector because
	// a) we have a global rate limit above which limits abuse
	// b) we apply rate limits limiting the ability of sending nodes to spam requests
	// c) we apply per-owner rate limits in the action capability in the
	// workflow node limiting the ability of users to abuse this flow by spamming Mtls requests.
	// The client enforces the mtls concurrency limit internally (on the request's
	// capped-timeout context) before delegating to the underlying transport.
	client, err := h.httpClientFactory(network.HTTPClientConfig{
		Mtls: &gateway_common.MtlsAuth{
			PrivateKey:  req.Mtls.PrivateKey,
			Certificate: req.Mtls.Certificate,
		},
		ConcurrencyLimiter: h.mtlsConcurrencyLimiter,
	})
	if err != nil {
		return nil, fmt.Errorf("failed to instantiate http client for mtls request: %w", err)
	}

	// We don't have access to the org here, so this will fall back to the environment default (=false).
	// That's appropriate because all fields set on the request come from untrusted nodes.
	// The capability separately applies an org-specific check.

	// Note: we intentionally consume the rate-limit after instantiating the client so that a malicious user
	// can't send requests with invalid mtls credentials and thus cheaply consume global tokens.
	if !h.mtlsRequestRateLimiter.Allow(ctx) {
		return nil, fmt.Errorf("global mtls request rate limit exceeded: %w", network.ErrBlockedRequest)
	}

	return client.Send(ctx, httpReq)
