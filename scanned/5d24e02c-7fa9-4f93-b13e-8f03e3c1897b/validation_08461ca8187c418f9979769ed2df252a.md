### Title
Missing embedded-null-byte validation allows signature/identity canonicalization mismatch in Gateway `Message` fields - ([File: core/services/gateway/api/message.go])

### Summary
The Gateway's user-facing `Message.Validate()` only rejects `MessageID`, `Method`, and `DonID` values that *end* with a null byte, but does not reject embedded (non-trailing) null bytes anywhere in these fields. This mirrors the reported analog bug class: a value that is signed/processed as the *full* string can be re-interpreted elsewhere as a *truncated* string once null-padded/aligned buffers are decoded, letting different attacker-controlled inputs collapse to the same canonical identity/value downstream.

### Finding Description
`Message.Validate()` in `core/services/gateway/api/message.go` only checks for a trailing null byte: [1](#0-0) 

It never rejects a null byte appearing in the *middle* of `MessageID`, `Method`, or `DonID`. These raw (attacker-supplied) strings are then copied verbatim into fixed-size buffers and signed/verified as-is via `GetRawMessageBody`: [2](#0-1) 

Separately, the gateway/node "aligned" byte<->string encoding helper explicitly documents (but does not enforce) the same constraint violated in the report — that inputs must not contain null bytes — because the decode path truncates at the first null byte: [3](#0-2) 

This is used for the node/gateway handshake auth header (`DonID`, `GatewayID`): [4](#0-3) 

The structural defect is identical to the `partial_sha256_var_interstitial` bug class described in the report: a value that is fully consumed/signed in one code path (e.g., the complete raw string including bytes after an embedded null) can be silently truncated in another code path that reconstructs a canonical string from the same buffer (`AlignedBytesToString` stops at the first `0x00`). Whenever these two representations are compared for authorization/identity decisions, two semantically different inputs can be treated as equivalent, or a signed value can diverge from its "logical" (post-decode) value.

### Impact Explanation
If any authorization, routing, or allowlist decision in the gateway/node path relies on the *decoded* (`AlignedBytesToString`) form of a field while the *signed* bytes cover the untruncated raw string, an attacker could craft a `DonID`/`MessageID`/`Method` value with an embedded null byte such that:
- the bytes actually signed/verified differ from what downstream logic treats as the canonical identifier, or
- two distinct signed payloads decode to the identical canonical string, creating a cross-request/cross-identity confusion.

This falls into the same class explicitly called out as in-scope: cross-user response confusion / allowlist bypass via authentication-adjacent data handling.

### Likelihood Explanation
Exploitability depends on whether a concrete comparison point exists downstream that consumes the truncated/decoded form while the signature covers the raw form. I was only able to confirm the **structural defect** (incomplete null-byte validation in `Validate()`, and the documented-but-unenforced null-byte assumption in `StringToAlignedBytes`/`AlignedBytesToString`) using the available index; I could not fully trace every downstream consumer (e.g., DON routing table lookups, allowlist match logic in `gateway.go`) within the tool-call budget to confirm a complete, exploitable end-to-end bypass. This should be treated as **unconfirmed/likely-partial** — the missing validation is real and directly analogous to the reported bug class, but full confirmation of a concrete authorization bypass requires further tracing of every place these fields are compared or looked up after decoding (this was not completable given the remaining iteration budget).

### Recommendation
- In `Message.Validate()` (`core/services/gateway/api/message.go`), reject any embedded null byte in `MessageID`, `Method`, and `DonID` (i.e., check `strings.Contains(field, NullChar)`, not just `strings.HasSuffix`).
- In `common.StringToAlignedBytes` (`core/services/gateway/common/utils.go`), enforce the documented constraint at runtime (return an error / panic) if the input contains a `0x00` byte, instead of relying on callers to honor an unchecked comment.
- Audit all call sites that compare the raw signed bytes against the `AlignedBytesToString`-decoded value (handshake DonID/GatewayID checks, message routing, allowlist checks) to ensure they always operate on the same canonical representation.

### Proof of Concept
Not fully constructible without further tracing of downstream comparison logic (see Likelihood Explanation). The reachable structural proof is:
1. Send a Gateway message with `Body.MessageID = "abc\x00XYZ..."` (or similarly for `Method`/`DonID`) — passes `Validate()` since only the suffix is checked. [5](#0-4) 
2. The full raw bytes (including everything after the null) are what gets signed/verified via `GetRawMessageBody` + `ExtractSigner`. [6](#0-5) 
3. Any downstream code that instead reconstructs the string via `AlignedBytesToString` from an equivalent fixed-size buffer would see only `"abc"`, diverging from the signed content — the same "different-data/same-derived-value" pattern as the SHA-256 partial hash report.

func GetRawMessageBody(msgBody *MessageBody) [][]byte {

	copy(alignedMessageID, msgBody.MessageID)
	alignedMethod := make([]byte, MessageMethodMaxLen)
	copy(alignedMethod, msgBody.Method)
	alignedDonID := make([]byte, MessageDonIDMaxLen)
	copy(alignedDonID, msgBody.DonID)
	alignedReceiver := make([]byte, MessageReceiverLen)
	copy(alignedReceiver, msgBody.Receiver)
	return [][]byte{alignedMessageID, alignedMethod, alignedDonID, alignedReceiver, msgBody.Payload}

func StringToAlignedBytes(input string, size int) []byte {
	aligned := make([]byte, size)
	copy(aligned, input)
	return aligned
}

func AlignedBytesToString(data []byte) string {
	idx := slices.IndexFunc(data, func(b byte) bool { return b == 0 })
	if idx == -1 {
		return string(data)
	}
	return string(data[:idx])
}

func UnpackSignedAuthHeader(data []byte) (elems *AuthHeaderElems, signer []byte, err error) {
	if len(data) != HandshakeAuthHeaderLen {
		return nil, nil, fmt.Errorf("auth header length is invalid (expected: %d, got: %d)", HandshakeAuthHeaderLen, len(data))
	}
	elems = &AuthHeaderElems{}
	offset := 0
	elems.Timestamp = common.BytesToUint32(data[offset : offset+HandshakeTimestampLen])
	offset += HandshakeTimestampLen
	elems.DonID = common.AlignedBytesToString(data[offset : offset+HandshakeDonIDLen])
	offset += HandshakeDonIDLen
	elems.GatewayID = common.AlignedBytesToString(data[offset : offset+HandshakeGatewayURLLen])
	offset += HandshakeGatewayURLLen
	signature := data[offset:]
	signer, err = common.ExtractSigner(signature, data[:len(data)-HandshakeSignatureLen])
	return elems, signer, err
}
