Based on the investigation, there is a plausible analog: the Chainlink GraphQL API exposes multiple paginated list queries (`Jobs`, `JobRuns`, `Bridges`, `EthTransactions`, `EthTransactionsAttempts`, `Nodes`, etc.) whose `limit` argument is taken directly from client input and passed unbounded into a SQL `LIMIT` clause, with no maximum-size enforcement, mirroring the class of bug in CVE-2018-25004 where an authorized-but-not-privileged user can trigger an expensive server-side operation via a client-controlled query parameter.

### Title
Unbounded GraphQL pagination `limit` argument enables authenticated-user DoS via expensive database queries - (File: core/web/resolver/helpers.go)

### Summary
GraphQL resolvers such as `Jobs`, `JobRuns`, `Bridges`, `EthTransactions`, and `EthTransactionsAttempts` accept a client-supplied `Limit` argument that is converted via `pageLimit()` with no upper bound and forwarded straight into a SQL `LIMIT` clause. Any authenticated Chainlink node-operator UI user — including the lowest-privilege `view` role — can supply an arbitrarily large limit (e.g. `2147483647`) to force the ORM to select and marshal a very large number of rows in a single request, similarly to the MongoDB `explain` DoS class where a permitted-but-unprivileged operation is abused to consume excessive server resources.

### Finding Description
`pageLimit()` simply returns the caller-provided value with no cap: [1](#0-0)  This value flows unchecked from resolvers that only call `authenticateUser(ctx)` (any authenticated session, no role check), for example `Jobs`/`Bridges`/`EthTransactions`: [2](#0-1) [3](#0-2)  The limit is passed to raw SQL `OFFSET $1 LIMIT $2` queries in the ORM layer, e.g. `FindJobs`: [4](#0-3)  and `PipelineRuns`, which additionally recomputes `loadPipelineRunIDs` with exponential batch scanning tied to the requested `limit`: [5](#0-4) . While a GraphQL `MaxDepth` protection exists at the schema level: [6](#0-5) , there is no corresponding maximum-limit/page-size enforcement, so a single shallow query with a huge `limit` bypasses depth limiting entirely.

### Impact Explanation
A low-privilege authenticated user (any role, since only `authenticateUser` — not `authenticateUserCanRun`/`Edit`/`IsAdmin` — is checked for these queries: [7](#0-6) ) can issue a single GraphQL request that forces the node to execute a large full-table scan/fetch and marshal a huge JSON response, consuming CPU, memory, and DB connection resources, potentially degrading or crashing the node process — a denial-of-service condition consistent with the referenced CVE class (availability impact, no confidentiality/integrity impact).

### Likelihood Explanation
Likelihood is high for any environment where multiple users share node-operator UI access with differing roles (view/run/edit/admin), since the `view` role is intended to be read-only/low-trust but is fully capable of triggering this. The attack requires only a single crafted GraphQL query and standard session authentication, with no special network position or timing needed.

### Recommendation
Enforce a hard maximum on the `limit`/`Limit` argument in `pageLimit()` (and equivalent REST paginated endpoints) and reject or clamp requests exceeding it before invoking `BridgeTypes`, `FindJobs`, `PipelineRuns`, `Transactions`, `TxAttempts`, and `NodeStatuses`. Consider also enforcing per-query result-size/cost limits in the GraphQL schema alongside the existing `MaxDepth` protection.

### Proof of Concept
```graphql
query {
  jobs(limit: 2000000000) {
    results { id observationSource }
    metadata { total }
  }
}
```
Sent as an authenticated request from a `view`-role user session, this causes the server to attempt to select and serialize an unbounded number of job rows (limited only by actual table size), consuming excessive CPU/memory on the node.

func (o *orm) loadPipelineRunIDs(ctx context.Context, jobID *int32, offset, limit int) (ids []int64, err error) {
	lggr := o.lggr

	var res sql.NullInt64
	if err = o.ds.GetContext(ctx, &res, "SELECT MAX(id) FROM pipeline_runs"); err != nil {
		err = errors.Wrap(err, "error while loading runs")
		return ids, err
	} else if !res.Valid {
		// MAX() will return NULL if there are no rows in table.  This is not an error
		return ids, err
	}
	maxID := res.Int64

	var filter string
	if jobID != nil {
		filter = fmt.Sprintf("JOIN job_pipeline_specs USING(pipeline_spec_id) WHERE job_pipeline_specs.job_id = %d AND ", *jobID)
	} else {
		filter = "WHERE "
	}

	stmt := fmt.Sprintf(`SELECT p.id FROM pipeline_runs AS p %s p.id >= $3 AND p.id <= $4
			ORDER BY p.id DESC OFFSET $1 LIMIT $2`, filter)

	// Only search the most recent n pipeline runs (whether deleted or not), starting with n = 1000 and
	//  doubling only if we still need more.  Without this, large tables can result in the UI
	//  becoming unusably slow, continuously flashing, or timing out.  The ORDER BY in
	//  this query requires a sort of all runs matching jobID, so we restrict it to the
	//  range minID <-> maxID.

	for n := int64(1000); maxID > 0 && len(ids) < limit; n *= 2 {
		var batch []int64
		minID := maxID - n
		if err = o.ds.SelectContext(ctx, &batch, stmt, offset, limit-len(ids), minID, maxID); err != nil {
			err = errors.Wrap(err, "error loading runs")
			return ids, err
		}
		ids = append(ids, batch...)
		if offset > 0 {
			if len(ids) > 0 {
				// If we're already receiving rows back, then we no longer need an offset
				offset = 0
			} else {
				var skipped int
				// If no rows were returned, we need to know whether there were any ids skipped
				//  in this batch due to the offset, and reduce it for the next batch
				err = o.ds.GetContext(ctx, &skipped,
					fmt.Sprintf(
						`SELECT COUNT(p.id) FROM pipeline_runs AS p %s p.id >= $1 AND p.id <= $2`, filter,
					), minID, maxID,
				)
				if err != nil {
					err = errors.Wrap(err, "error loading from pipeline_runs")
					return ids, err
				}
				offset -= skipped
				if offset < 0 { // sanity assertion, if this ever happened it would probably mean db corruption or pg bug
					lggr.AssumptionViolationw("offset < 0 while reading pipeline_runs")
					err = errors.Wrap(err, "internal db error while reading pipeline_runs")
					return ids, err
				}
				lggr.Debugw("loadPipelineRunIDs empty batch", "minId", minID, "maxID", maxID, "n", n, "len(ids)", len(ids), "limit", limit, "offset", offset, "skipped", skipped)
			}
		}
		maxID = minID - 1
	}
	return ids, err
}
