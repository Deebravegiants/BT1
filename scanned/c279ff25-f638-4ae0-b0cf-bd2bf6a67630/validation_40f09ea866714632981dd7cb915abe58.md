## Title
Login endpoint leaks username existence via bcrypt timing side-channel — ([File: core/sessions/localauth/orm.go])

### Summary
The `/sessions` login endpoint (`SessionsController.Create` in `core/web/sessions_controller.go`) is reachable by any unauthenticated client and forwards the submitted email/password to `AuthenticationProvider().CreateSession`. In the default local authentication backend, `orm.CreateSession` performs a fast-fail DB lookup when the email doesn't exist, but performs an expensive `bcrypt.CompareHashAndPassword` call when the email does exist — creating a measurable timing discrepancy that allows an unprivileged remote attacker to enumerate valid usernames, exactly analogous to the xrdp login timing side-channel (CVE-2026-42218).

### Finding Description
`SessionsController.Create` accepts unauthenticated POST requests with `{email, password}` and calls `sc.App.AuthenticationProvider().CreateSession(ctx, sr)`: [1](#0-0) 

The local authentication provider's `CreateSession` implementation looks up the user by email first, and returns *immediately* on a DB miss (no such user): [2](#0-1) 

Only when the email *does* exist does the code proceed to `utils.CheckPasswordHash`, which wraps `bcrypt.CompareHashAndPassword` — an intentionally slow, computationally expensive hash comparison (bcrypt cost factor): [3](#0-2) [4](#0-3) 

This produces two clearly distinguishable response-time classes:
- Unknown email → fast path (single indexed SQL lookup, immediate error return).
- Known email → slow path (SQL lookup + bcrypt comparison, which typically costs tens to hundreds of milliseconds).

The same fast-fail-vs-bcrypt pattern also exists in the LDAP and OIDC local-fallback authenticators, which are structured identically: [5](#0-4) [6](#0-5) 

Additionally, before `CreateSession` is even invoked, `SessionsController.Create` calls `GetUserWebAuthn(ctx, sr.Email)` — another DB round trip whose behavior/timing may also differ based on user existence, compounding the signal: [7](#0-6) 

### Impact Explanation
An unauthenticated remote attacker can systematically probe the login endpoint with candidate emails and use response-time measurements to determine which accounts exist on the node. This is a confidentiality-only information disclosure (matches CVSS C:L/I:N/A:N in the reference CVE): it does not directly grant access, but materially aids further targeted attacks (credential stuffing, phishing, brute force focused only on confirmed real accounts) against chainlink node operator/admin accounts.

### Likelihood Explanation
The `/sessions` create endpoint is unauthenticated and internet-facing by design (it's the login form). No special privileges, prior session, or network position are required — only the ability to send HTTP requests and measure timing, which is straightforward over a low-jitter network path or with statistical averaging over many requests. This makes the likelihood of exploitation reasonably high for any exposed node.

### Recommendation
Ensure constant-time behavior regardless of whether the submitted email corresponds to an existing user, e.g.:
- Always perform a bcrypt comparison (against a fixed dummy hash) even when the user is not found, before returning any error.
- Return a generic error message and roughly equalize timing between the "unknown user" and "wrong password" code paths in `orm.CreateSession`, `ldapAuthenticator.localLoginFallback`, and `oidcAuthenticator.localLoginFallback`.
- Consider adding a fixed minimum response delay to the login handler to mask backend timing variance.

### Proof of Concept
1. Send POST `/sessions` with a known-invalid email and any password; measure response time (fast, DB miss only).
2. Send POST `/sessions` with a valid, existing admin email and a wrong password; measure response time (slow, includes bcrypt compare in `orm.CreateSession`, `core/sessions/localauth/orm.go:159`).
3. Repeat for a list of candidate emails, averaging multiple samples per candidate to reduce noise; emails producing consistently slower responses are confirmed to exist on the node.

func (sc *SessionsController) Create(c *gin.Context) {
	defer sc.App.WakeSessionReaper()
	ctx := c.Request.Context()
	sc.App.GetLogger().Debugf("TRACE: Starting Session Creation")

	session := sessions.Default(c)
	var sr clsessions.SessionRequest
	if err := c.ShouldBindJSON(&sr); err != nil {
		jsonAPIError(c, http.StatusBadRequest, fmt.Errorf("error binding json %w", err))
		return
	}

	// Does this user have 2FA enabled?
	userWebAuthnTokens, err := sc.App.AuthenticationProvider().GetUserWebAuthn(ctx, sr.Email)
	if err != nil {
		sc.App.GetLogger().Errorf("Error loading user WebAuthn data: %s", err)
		jsonAPIError(c, http.StatusInternalServerError, errors.New("internal Server Error"))
		return
	}

	// If the user has registered MFA tokens, then populate our session store and context
	// required for successful WebAuthn authentication
	if len(userWebAuthnTokens) > 0 {
		sr.SessionStore = sc.sessions
		sr.WebAuthnConfig = sc.App.GetWebAuthnConfiguration()
	}

	sid, err := sc.App.AuthenticationProvider().CreateSession(ctx, sr)
	if err != nil {
		jsonAPIError(c, http.StatusUnauthorized, err)
		return
	}

// CheckPasswordHash wraps around bcrypt.CompareHashAndPassword for a friendlier API.
func CheckPasswordHash(password, hash string) bool {
	err := bcrypt.CompareHashAndPassword([]byte(hash), []byte(password))
	return err == nil
}

		return user, err
