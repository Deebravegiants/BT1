Based on my investigation, the internet-facing gateway's `HandleLegacyUserMessage` path bypasses allowlist/authorization checks entirely, unlike the JSON-RPC vault path which is properly authorized before forwarding to nodes. This is a genuine unprivileged-actor reachable authorization gap analogous to the FileGator bug class (missing validation/authorization before a privileged action is executed).

### Title
Unauthenticated legacy gateway user messages bypass allowlist authorization before being forwarded to DON nodes - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The gateway's legacy JSON-RPC message path (`isLegacyRequest` branch in `gateway.ProcessRequest`) routes directly into `handler.HandleLegacyUserMessage`, which forwards the request to all DON nodes via `don.SendToNode` without performing any allowlist or authorization check on the caller. The code contains an explicit `// TODO: apply allowlist and rate-limiting here` marker immediately before the request is dispatched to nodes.

### Finding Description
In `core/services/gateway/gateway.go`, `ProcessRequest` decodes an incoming user HTTP request and, when the request carries a `DonID` (the "legacy" format), calls `h.HandleLegacyUserMessage(ctx, msg, callback)` directly: [1](#0-0) [2](#0-1) 

`HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go` validates message decoding, staleness, and method name, but the allowlist/authorization step is explicitly marked unimplemented, and the function proceeds to fan the request out to every DON member node: [3](#0-2) 

This contrasts sharply with the JSON-RPC (non-legacy) vault path, where `GatewayVaultRequestProcessor.ProcessRequest` always calls into an `Authorizer` (allowlist-based or JWT-based) before forwarding any request: [4](#0-3) [5](#0-4) 

The user-facing HTTP server (`core/services/gateway/network/httpserver.go`) does not perform per-caller authentication before invoking `ProcessRequest` — the `auth` string passed through is only used by `jsonrpc2.DecodeRequest` for message parsing/signature extraction, not for an allowlist check gating which DON a caller may message.

### Impact Explanation
Any unauthenticated/unprivileged external client that can reach the gateway's public user-facing HTTP endpoint can submit a legacy-format `web_api_trigger` message specifying an arbitrary `DonID`, and it will be dispatched to every node in that DON without any allowlist, workflow-ownership, or rate-limit gating at the gateway layer (only a message-age and method-name check apply). This allows an unprivileged caller to trigger workflow executions or otherwise interact with DON capabilities that should be restricted to allowlisted callers — a request-impersonation / allowlist-bypass class of bug, matching the "no validation before privileged forwarding" pattern seen in the FileGator chmod report.

### Likelihood Explanation
The vulnerable path is reached directly from the public gateway HTTP endpoint with no authentication precondition beyond basic JSON-RPC decoding, and the missing-check is explicitly flagged as a TODO in the code, indicating it is a known gap rather than a hardened, reviewed no-op.

### Recommendation
Implement the allowlist/authorization and rate-limiting check in `HandleLegacyUserMessage` before forwarding to `don.SendToNode`, mirroring the `Authorizer`/allowlist pattern already used by the vault JSON-RPC gateway path, so that unauthenticated callers cannot trigger arbitrary DON node message delivery.

### Proof of Concept
1. Identify a running gateway's public user HTTP endpoint and a valid `DonID` (e.g., from job configuration).
2. Craft a legacy-format JSON-RPC request with `Body.DonID` set to the target DON, `Body.Method = "web_api_trigger"`, and a fresh `Timestamp`, with no prior allowlisting of the caller's identity/workflow.
3. POST it to the gateway; `gateway.ProcessRequest` will route it to `HandleLegacyUserMessage`, which (absent the TODO'd allowlist check) forwards it to every member node of that DON via `don.SendToNode`, without verifying the caller is authorized for that DON/workflow. [3](#0-2)

// ProcessRequest runs validate structure → authorize → prefix ID → stamp params → validate owner-scoped limits.
// In node mode (stripOwnerPrefixForAuth), the envelope ID received from the gateway (owner::id)
// is restored on error so error responses remain matchable by the gateway, which tracks active
// requests by the exact envelope ID it forwarded to the nodes.
func (p *GatewayVaultRequestProcessor) ProcessRequest(
	ctx context.Context,
	req *jsonrpc.Request[json.RawMessage],
	publicKey *tdh2easy.PublicKey,
) (*AuthorizedGatewayVaultRequest, error) {
	if !p.stripOwnerPrefixForAuth {
		return p.processRequest(ctx, req, publicKey)
	}

	envelopeID := req.ID
	strippedID, _ := stripPrefixedVaultRequestID(req.ID)
	req.ID = strippedID
	authorized, err := p.processRequest(ctx, req, publicKey)
	if err != nil {
		req.ID = envelopeID
		return nil, err
	}
	return authorized, nil
}
