### Title
Web-API trigger accepts requests with stale/missing timestamps despite documented freshness requirement, enabling replay of external-initiator trigger events - (File: `core/capabilities/webapi/trigger/trigger.go`)

### Summary
This finding is analogous to the "Different Oracle issues can return outdated prices" report: a value that is documented to require a freshness/timestamp check (there, `latestRoundData().timeStamp`; here, `TriggerRequestPayload.Timestamp`) is either checked against a meaningless sentinel or not checked at all before the value is consumed and acted upon. In `processTrigger`/`HandleGatewayMessage` in `core/capabilities/webapi/trigger/trigger.go`, the `Timestamp` field of the incoming `webapicap.TriggerRequestPayload` is never validated for staleness, even though the schema explicitly documents that it "needs to be within certain freshness to be processed."

### Finding Description
The `TriggerRequestPayload.Timestamp` field is documented in the JSON schema as needing "certain freshness to be processed": [1](#0-0) 

However, the actual gateway-facing handler for this trigger type, `triggerConnectorHandler.HandleGatewayMessage`, unmarshals the payload and immediately dispatches it to `processTrigger` without ever inspecting `payload.Timestamp`: [2](#0-1) 

`processTrigger` itself only checks topic matching, sender allowlisting, and rate limiting — again, no timestamp/staleness check is performed before the trigger event is forwarded into the workflow engine: [3](#0-2) 

This is directly analogous to the PegOracle bug: a sibling handler for the same "web api trigger" concept, `HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go`, does perform a real staleness check (`payload.Timestamp == 0` rejected, and age compared against `MaxAllowedMessageAgeSec`): [4](#0-3) 

This shows that the "inconsistency between how price1/price2 are handled" pattern from the report — one code path validating freshness, a sibling code path skipping the check entirely — exists here between `HandleLegacyUserMessage` (validates) and the V2 `HandleGatewayMessage`/`processTrigger` path in `trigger.go` (does not validate). An unprivileged external caller reaching the gateway can submit (or capture and replay) a `web_api_trigger` request with an arbitrarily old, or even zero, `Timestamp`, and it will still be accepted, signed for, and forwarded to trigger workflow executions, as long as sender/topic/rate-limit checks pass.

### Impact Explanation
Because the timestamp of the trigger event is part of the workflow's application-level input (passed through via `wrappedPayload` into `capabilities.TriggerEvent.Outputs`) and is used to compute the deduplication `TriggerEventID` only in combination with `body.Sender` + `payload.TriggerEventId` (not timestamp), an attacker who can reach the gateway as an allowed sender could replay old captured requests (with different `TriggerEventId` values, or valid ones if replay protection is weak) to re-trigger workflow executions with stale data, bypassing the intended freshness guarantee documented in the schema. This can cause workflows to act on outdated market/price/event data supplied through the trigger payload, leading to incorrect automated decisions — the same class of economic-loss risk described in the oracle report, translated to the workflow-trigger data path.

### Likelihood Explanation
Likelihood is Medium: exploitation requires the attacker to be an "allowed sender" for at least one registered `web-api-trigger` workflow topic (per `allowedSenders`), which limits it to already-authorized external initiators/API consumers rather than fully anonymous actors. However, no additional privilege or gateway-level access is required beyond that — any authorized sender can submit or replay a request with an old timestamp and have it processed, since there is no server-side freshness enforcement in this handler path.

### Recommendation
Add an explicit freshness check for `payload.Timestamp` in `triggerConnectorHandler.HandleGatewayMessage` (or in `processTrigger`) before processing the trigger, mirroring the check already present in `HandleLegacyUserMessage`:
- Reject requests where `Timestamp == 0`.
- Reject requests where `time.Now().Unix() - payload.Timestamp` exceeds a configured maximum allowed age (e.g., a `MaxAllowedMessageAgeSec`-style config value), returning an `ERROR` `TriggerResponsePayload` in that case.
- Ensure this check is applied consistently across all trigger-handling code paths (`HandleLegacyUserMessage` and the V2 `trigger.go` path) rather than only in one.

### Proof of Concept
1. A workflow registers a `web-api-trigger` with `allowedSenders` including attacker-controlled sender address `S`, and `allowedTopics` including topic `T`.
2. Attacker (as sender `S`) sends a `web_api_trigger` gateway message with `TriggerRequestPayload{Timestamp: 0 (or very old value), Topics: ["T"], TriggerEventId: "...", Params: {...}}`.
3. `HandleGatewayMessage` in `core/capabilities/webapi/trigger/trigger.go` unmarshals the payload and calls `processTrigger` without any timestamp check.
4. `processTrigger` matches the topic, verifies `S` is an allowed sender, checks rate limiting, and forwards the (stale) event to the workflow's trigger channel — the workflow executes using stale trigger data despite the schema's documented freshness requirement, and the response returned is `{"Status": "ACCEPTED"}`.

func (h *triggerConnectorHandler) HandleGatewayMessage(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) error {
	msg, err := hc.ValidatedMessageFromReq(req)
	if err != nil {
		h.lggr.Errorw("error validating message from request", "err", err, "request", req)
		return nil
	}
	body := &msg.Body
	sender := ethCommon.HexToAddress(body.Sender)
	var payload webapicap.TriggerRequestPayload
	err = json.Unmarshal(body.Payload, &payload)
	if err != nil {
		h.lggr.Errorw("error decoding payload", "err", err)
		err = h.sendResponse(ctx, gatewayID, body, ghcapabilities.TriggerResponsePayload{Status: "ERROR", ErrorMessage: fmt.Errorf("error %s decoding payload", err.Error()).Error()})
		if err != nil {
			h.lggr.Errorw("error sending response", "err", err)
		}
		return nil
	}

	switch body.Method {
	case ghcapabilities.MethodWebAPITrigger:
		resp := h.processTrigger(ctx, gatewayID, body, sender, payload)
		var response ghcapabilities.TriggerResponsePayload
		if resp == nil {
			response = ghcapabilities.TriggerResponsePayload{Status: "ACCEPTED"}
		} else {
			response = ghcapabilities.TriggerResponsePayload{Status: "ERROR", ErrorMessage: resp.Error()}
			h.lggr.Errorw("Error processing trigger", "gatewayID", gatewayID, "body", body, "response", resp)
		}
		err = h.sendResponse(ctx, gatewayID, body, response)
		if err != nil {
			h.lggr.Errorw("Error sending response", "body", body, "response", response, "err", err)
		}
		return nil
