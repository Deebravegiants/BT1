### Title
Unauthenticated pipeline-run resume endpoint lacks the unauthenticated rate limit applied to /sessions - ([File: core/web/router.go])

### Summary
The Nextcloud CVE describes missing rate-limiting on a public, unauthenticated endpoint that lets an attacker brute-force/enumerate valid tokens. In this codebase, `v2Routes` explicitly carves out an unauthenticated route group (`unauthedv2`) that exposes `PATCH /v2/resume/:runID` with no dedicated per-route rate limiter, unlike the `/sessions` login endpoint which the code base deliberately wraps in a stricter `Unauthenticated` rate limit.

### Finding Description
In `core/web/router.go`, `NewRouter` applies a single global rate limiter to the whole `api` group keyed by the "Authenticated" limits (default 1000 req/min, `rl.Authenticated()`/`rl.AuthenticatedPeriod()`): [1](#0-0) 

By contrast, the login endpoint is deliberately given a much stricter, separate "Unauthenticated" limiter (default 5 req/20s) because it is unauthenticated and attacker-reachable: [2](#0-1) 

However, `v2Routes` creates its own unauthenticated group with no additional rate limiting at all beyond the global "Authenticated" limiter inherited from `api`: [3](#0-2) 

This means `PATCH /v2/resume/:runID` — an endpoint reachable by any unauthenticated client — is throttled only at the same generous 1000 req/min ceiling meant for logged-in, trusted API users, not the 5 req/20s ceiling the codebase itself designed for unauthenticated/public endpoints like `/sessions`. This mirrors the Nextcloud bug class: a public endpoint that accepts a token/identifier-like path parameter (`runID`) but is not subjected to the stricter unauthenticated rate limit, enabling faster enumeration than the security model intends.

I was unable to fully verify the `Resume` handler implementation in `core/web/pipeline_runs_controller.go` (its body was not returned before the search budget was exhausted), so I cannot confirm the exact behavior for invalid/mismatched `runID` values (e.g., whether it returns a distinguishing error that would allow an attacker to detect valid vs. invalid run IDs) or whether `runID` values are guessable/sequential integers. This is a factual gap that determines whether this is exploitable enumeration or just a rate-limit inconsistency.

### Impact Explanation
If `runID` is a sequential/guessable identifier (as pipeline run primary keys typically are) and the resume handler returns a different status/response for valid vs. invalid IDs, an unauthenticated attacker could enumerate valid run IDs at up to 1000/min instead of 5/20s, and if the resume action has a side effect (resuming a paused pipeline run, e.g., a webhook/resume callback), this could allow unauthorized triggering of job resumption — a request-impersonation/authorization-bypass consequence. Absent confirmation of the handler's exact logic, the confirmed, provable impact is limited to the rate-limit design inconsistency itself.

### Likelihood Explanation
Reaching this endpoint requires no authentication and no special network position — a plain HTTP client can hit `PATCH /v2/resume/:runID` directly, making the reachable-path story strong. The likelihood of the enumeration actually working depends on unverified details of `Resume`'s response behavior and `runID` predictability.

### Recommendation
- Apply the same stricter `Unauthenticated` rate limiter (via `rateLimiter(rl.UnauthenticatedPeriod(), rl.Unauthenticated())`) to the `unauthedv2` group in `v2Routes`, consistent with how `sessionRoutes` protects `/sessions`.
- Confirm and, if necessary, harden the `Resume` handler in `core/web/pipeline_runs_controller.go` to return uniform responses/timing for valid vs. invalid `runID` to prevent enumeration regardless of rate limiting.

### Proof of Concept
Not fully constructable without confirming `Resume`'s response behavior for invalid `runID`s; conceptually: send repeated unauthenticated `PATCH /v2/resume/<guessed-id>` requests and observe whether more than 5 requests per 20 seconds succeed without being rate-limited (they would be, since the endpoint only inherits the 1000/min "Authenticated" limiter), then compare response codes/timings across ID guesses to determine if valid IDs are distinguishable.

```go
func sessionRoutes(app chainlink.Application, r *gin.RouterGroup) {
	config := app.GetConfig()
	rl := config.WebServer().RateLimit()
	unauth := r.Group("/", rateLimiter(
		rl.UnauthenticatedPeriod(),
		rl.Unauthenticated(),
	))
	sc := NewSessionsController(app)
	unauth.POST("/sessions", sc.Create)
	auth := r.Group("/", auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession))
	auth.DELETE("/sessions", sc.Destroy)
}
```
