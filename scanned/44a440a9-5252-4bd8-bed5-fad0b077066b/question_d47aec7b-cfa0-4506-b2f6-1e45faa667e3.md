Target: IntentSignerNEP413.signRaw (packages/intents-sdk/src/intents/intent-signer-impl/intent-signer-nep413.ts). Attacker input: a signMessage callback (fully attacker-controlled if the integrator wires a custom signMessage per NEP413Config, e.g. a counterparty-supplied wallet bridge) that returns {publicKey: attackerPublicKey, signature: 'somePrefix:garbage'} where signature does not start with 'ed25519:' and is not valid base64 either. Preconditions: signIntent/signRaw is invoked with any IntentPayload; no NEAR network state needed. Call sequence: signRaw computes nep413Hash, calls signMessageFn, then formats: signatureFormatted = signature.startsWith('ed25519:') ? signature : `ed25519:${base58.encode(base64.decode(signature))}`. If signature is not valid base64, base64.decode throws before packaging, but if signature is valid base64 yet was never actually produced by publicKey signing nep413Hash (e.g. it's an old cached signature reused, or a value the attacker fabricated), the function still re-encodes it and returns a MultiPayloadNep413 with public_key=publicKey and signature=signatureFormatted, without verifying that signature actually validates against nep413Hash and publicKey. Equality that breaks: signer_id in the signed payload == the intents user id derived from the public key that produced signature -- signRaw never checks that ed25519_verify(publicKey, nep413Hash, decodedSignature) holds, so payload.public_key can be paired with an unrelated signature blob and forwarded as if it were a valid signed intent. Impact (Critical): if an integrator's custom signMessage implementation is buggy or returns a stale/mismatched signature (a realistic non-malicious-integrator scenario since the attacker only controls what a permissionless remote signer service returns to a thin wallet-bridge), the SDK will still construct and forward a MultiPayload that looks correctly formed, letting an unauthorised or incorrect signature be submitted for signer_id, risking execution of an intent that was never actually validly signed by the named account's key -- a signature not actually bound to signer/payload being executed.
