Target: authHandleToIntentsUserId 'stellar' case using stellarAddressToBytes (packages/internal-utils/src/utils/authIdentity.ts). Attacker input: a 56-character Stellar-shaped string ('G' + 55 chars) whose CRC16 checksum bytes are valid for the payload but whose version byte differs from the standard ED25519 public key version byte (e.g. crafted to pass CRC while encoding a different key type/version). Preconditions: stellarAddressToBytes only needs to be invoked through authHandleToIntentsUserId with method:'stellar'; no route or fee context required. Call sequence: authHandleToIntentsUserId({identifier: craftedStellarString, method:'stellar'}) -> stellarAddressToBytes(identifier) -> hex.encode(decoded) is trusted as the intents user id without confirming the decoded version byte matches the expected Ed25519-public-key version. Equality that breaks: signer_id in the signed payload == the intents user id derived from the public key that produced signature; if stellarAddressToBytes accepts a valid-CRC-but-wrong-version-byte string, the resulting hex bytes used as the intents user id are not guaranteed to be the raw ed25519 public key bytes that actually produced the SEP-53 signature, breaking the binding between signature and identity. Impact (Critical): an attacker submitting a wrong-version Stellar string could get an intents user id assigned that does not match the key that will sign, allowing a swap/withdrawal intent to be attributed to (and debit) an identity the attacker does not control the key for, i.e. intent manipulation moving funds the true keyholder did not authorise. Proof idea: vitest test crafting a base32 Stellar string with a non-standard version byte but recomputed CRC16 checksum so it decodes without throwing, feeding it to authHandleToIntentsUserId and prepareSwapSignedData's sep53 path, and asserting whether the SDK rejects it (it should, but currently does not perform version-byte validation) versus accepting it into public_key used for signature verification, showing SIGNED_EQUALS_BUILT breaks for the public_key field.
