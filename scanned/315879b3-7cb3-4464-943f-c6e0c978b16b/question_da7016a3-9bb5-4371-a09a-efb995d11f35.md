Target: `composeMultiPayloads` (packages/intents-sdk/src/intents/intent-executer-impl/intent-executer.ts). Attacker input: `signedIntents.before` containing a `MultiPayload` whose `intents` array (once decoded from `payload`) includes an intent unrelated to what the caller's top-level `intents` argument describes, obtained from an integrator-forwarded pre-signed intent supplied by another party. Preconditions: `IntentExecuter.signAndSendIntent` called with `signedIntents: { before: [foreignSignedPayload] }`. Call sequence: `composeMultiPayloads` unconditionally prepends `signedIntents.before` entries to the result array, which is submitted atomically via `intentRelayer.publishIntents({ multiPayloads: composedPayloads, quoteHashes })`. Equality broken: the set of intents executed atomically alongside the caller's own signed intent != only the intents the caller's call to `signAndSendIntent` requested (`intents` param), since arbitrary pre-signed foreign payloads are spliced in without any cross-check that they correspond to the same intended trade. Impact: Critical - an attacker who can get an integrator to forward another party's `signedIntents.before` entry (e.g. a stale/duplicate withdrawal) causes it to execute atomically bundled with the caller's fresh intent, resulting in an extra, unauthorized execution bundled under the same ticket. Proof idea: vitest test calling `signAndSendIntent` with `signedIntents: { before: [priorPayloadA, priorPayloadA] }` (duplicate reference) and asserting `intentRelayer.publishIntents` is called with a `multiPayloads` array containing `priorPayloadA` only once, which it does not - it appears twice, causing double submission of the same pre-signed payload.
