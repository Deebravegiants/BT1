Target: `IntentPayloadBuilder.setNonceRandomBytes`. Attacker input: caller supplies `customRandomBytes` of length != 15 (e.g. reused 15-byte buffer from a previous signed and settled intent, or attacker-influenced buffer sourced from a solver-provided seed). Call sequence: `buildWithSalt` calls `VersionedNonceBuilder.encodeNonce(salt, deadline, this.customRandomBytes)`; `encodeNonce` only validates `randomBytes.length !== RANDOM_BYTES_LENGTH` (throws) but performs no uniqueness/freshness check against previously used random bytes. Equality broken: none enforced - nonce uniqueness (a precondition for `SINGLE EXECUTION`: executions per signed payload == 1) is not guaranteed by this function when `customRandomBytes` is attacker/solver supplied and intentionally repeated. Impact: Critical - reusing the same 15 random bytes with the same salt and deadline produces an identical nonce, and if the previous signed intent using that nonce has not yet been consumed on-chain, a second payload signed with the same nonce becomes valid, risking double execution of a similar intent structure.
