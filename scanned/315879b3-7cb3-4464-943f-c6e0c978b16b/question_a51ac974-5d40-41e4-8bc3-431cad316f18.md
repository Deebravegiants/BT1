Target: `mergeIntentPayloads` interaction with `nonce` stripping. Attacker input: `intentPayloadFactory` returns a payload object where `customPayload` includes a `nonce` field directly (violating the documented contract but permitted by `Partial<IntentPayload>` typing). Call sequence: `mergeIntentPayloads` destructures `const { nonce: _nonce, ...basePayload } = defaultPayload` to strip only the base payload's nonce, then spreads `...customPayload` (which may itself carry a stale `nonce`) over `basePayload`, and finally calls `defaultIntentPayloadFactory(salt, { ...basePayload, ...customPayload, intents: ... })`; inside `defaultIntentPayloadFactory`, the destructured `params` retains any `nonce` from `customPayload` because only `intents` and `verifying_contract` are pulled out of the input, so `...params` at the end re-applies `customPayload.nonce`, overwriting the freshly computed `nonce: VersionedNonceBuilder.encodeNonce(...)`. Equality broken: nonce in the final signed `IntentPayload` != the freshly generated nonce bound to the current `deadline`/`salt`, but instead equals a stale nonce from `customPayload` that may already have been consumed or bound to a different, already-expired deadline. Impact: Critical - a stale/reused nonce signed into a new payload can either be rejected (stranding funds mid-flow) or, worse, collide with a previously valid unexecuted signature, breaking `SINGLE EXECUTION`. Proof idea: vitest test with `intentPayloadFactory: () => ({ nonce: staleNonceFromPreviousPayload })` asserting the final `intentPayload.nonce` passed to `intentSigner.signIntent` differs from `staleNonceFromPreviousPayload`, which it will not because the spread order lets it survive.
