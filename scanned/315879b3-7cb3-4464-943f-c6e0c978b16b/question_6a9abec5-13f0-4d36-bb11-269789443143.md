Target: `IntentPayloadBuilder.buildWithSalt`, field `signer_id` via `setSigner`. Attacker input: caller calls `.setSigner('some-account.near')` then later calls `.reset()` incorrectly assuming `signerId` is cleared, but a stale reference to the builder from a prior `.clone()` retains the original `signerId` due to the pre-reset clone sharing the same `intents` array reference (`builder.intents = [...this.intents]` is a shallow copy of array but not of nested intent objects). Call sequence: `.clone()` produces a new builder with `builder.signerId = this.signerId` (copied by value, fine for strings) but `builder.intents = [...this.intents]` shallow-copies primitive intent objects by reference; if the original builder's `addIntent` is called again after cloning with an intent object that is later mutated in place (e.g., an integrator mutates an `IntentPrimitive` object post-construction), both the original and cloned builder's `build()` outputs reflect the mutation. Equality broken: intents in the signed payload built from the CLONE != the intents the caller explicit called `.addIntent()` with, since a mutation to a shared reference can change intent contents between builder configuration time and `signIntent` time undetected. Impact: Critical - the signed intent's fields (e.g. `ft_withdraw` amount/receiver_id) can differ from what was passed to `addIntent`, moving funds to different amount/recipient than authorized. Proof idea: vitest test calling `.addIntent(intentObj)`, `.clone()`, then mutating `intentObj.amount` before calling `build()` on the clone, asserting the built payload's intent amount equals the value at `addIntent` time rather than the mutated value - it will not, since the reference is shared.
