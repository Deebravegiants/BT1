Target: `IntentExecuter.signAndSendIntent`, field `salt` reuse across `mergeIntentPayloads`. Attacker input: an integrator's `intentPayloadFactory` returns `{ intents: [...] }` without altering `salt`, but the SDK re-derives nonce inside `mergeIntentPayloads` by calling `defaultIntentPayloadFactory(salt, {...})` a second time with the SAME `salt` value used for the initial `intentPayload` build. Call sequence: first `defaultIntentPayloadFactory(salt, {...})` call at line 72 generates `nonce_1` via `VersionedNonceBuilder.encodeNonce(salt, nonceDeadline_1, undefined)` using a fresh random default; `mergeIntentPayloads` calls `defaultIntentPayloadFactory(salt, {...basePayload, ...customPayload, intents})` again, generating `nonce_2` with a NEW random default (since `randomBytes` defaults to `crypto.getRandomValues`), so the two calls with the same `salt` produce different final nonces - this is fine for uniqueness, but the intermediate `nonce_1` from the first call is discarded and never checked against `nonce_2` for the `deadline` field consistency, since `basePayload` (post nonce-strip) carries `basePayload.deadline` derived from `intentParams.deadline` possibly overridden a second time by `customPayload.deadline`. Equality broken: the final signed `deadline` != the `deadline` the caller passed to `signAndSendIntent` if `intentPayloadFactory` alters `deadline` in a way the caller (who called the top-level `signAndSendIntent({ deadline: X, ...})`) never sees reflected back before signing, since there is no post-merge check comparing final `intentPayload.deadline` to the original caller-supplied `X`. Impact: Critical - the deadline actually signed can silently diverge from what the caller specified when invoking `signAndSendIntent`, extending or shortening the effective signature validity window used for `SIGNED == BUILT` without caller confirmation. Proof idea: vitest test calling `exec.signAndSendIntent({ deadline: 'T1', salt, intentPayloadFactory-equivalent factory returning { deadline: 'T2' } })` and asserting `intentSigner.signIntent` is invoked with `deadline === 'T1'`, which fails because `customPayload.deadline` (T2) wins in the spread.
