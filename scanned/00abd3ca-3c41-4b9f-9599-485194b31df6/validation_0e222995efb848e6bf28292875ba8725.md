## Analysis: Signature Not Bound to Recipients in HOP Data Pool

The vulnerability class from the external report — a signature that authorizes an object without cryptographically binding to the *full contents* of that object, enabling replay against a different context — has a concrete analog in `substrate/client/hop` (the "Hand-Off Protocol" off-chain data pool).

### Title
Recipient list is not covered by the `hop_submit` signature, allowing signature replay to redirect/hijack pool entries to attacker-chosen recipients - (File: `substrate/client/hop/src/rpc.rs`, `substrate/client/hop/src/pool.rs`, `substrate/client/hop/src/types.rs`)

### Summary
`hop_submit` accepts `data`, `recipients`, `signature`, `signer`, and `submit_timestamp` as independent RPC parameters. The signature is verified only over `blake2_256(HOP_SUBMIT_CONTEXT || blake2_256(data) || submit_timestamp)` — it never covers `recipients`. Any party who obtains a previously-valid `(data, signer, signature, submit_timestamp)` tuple (e.g. by observing an earlier submission, or after the original entry has been fully acked/removed) can resubmit it with an arbitrary `recipients` list and have it accepted as if the original signer authorized delivery to those new recipients.

### Finding Description
The signed payload is constructed in `submit_signing_payload`: [1](#0-0) 

It hashes only the context tag, the data hash, and the timestamp. The RPC handler verifies exactly this payload and nothing else: [2](#0-1) 

`recipients` is decoded and passed straight into `HopDataPool::insert` without ever being folded into the signed message: [3](#0-2) 

`insert` accepts whatever `recipients` the RPC caller supplied, keyed only by the content hash of `data` (which is unrelated to `recipients`): [4](#0-3) [5](#0-4) 

The only replay defense that exists is domain separation between `hop_submit`/`hop_claim`/`hop_ack` and content-addressing that rejects a second insert *while an entry for the same hash still exists*: [6](#0-5) 

Nothing prevents a *second* insertion of the exact same `(data, signer, signature, submit_timestamp)` tuple once the first entry has been fully claimed/acked and removed from the index (see the removal path in `ack`): [7](#0-6) 

At that point the hash `H = blake2_256(data)` is no longer in `index`, so `DuplicateEntry` no longer fires, and an attacker who captured the original tuple can call `hop_submit` again with a `recipients` list of their choosing. The signature still verifies (it never depended on `recipients`), so the entry is accepted as authored by the original `signer`/`sender_id`, but now addressable only by the attacker's keys — a direct analog of the report's Issue 2 ("messages not validated against the object included in the payload," enabling reuse of a previously-signed message to authorize different content/state).

### Impact Explanation
- **Confidentiality/redirection**: if `data` is later resubmitted for on-chain promotion or otherwise regains relevance, an attacker who has re-registered themselves as the recipient list can `hop_claim`/`hop_ack` it, obtaining data that was never intended for them — the same "loss of confidentiality of ... encrypted message" outcome the external report describes for the analog Arweave registry bug.
- **Accounting abuse**: `entry_accounted_size` scales with `recipients.len()`, and quota/pool-size accounting in `insert` charges the *original* `sender_id`, not the resubmitter: [8](#0-7) 
An attacker can replay a captured tuple with `MAX_RECIPIENTS` (256) attacker-controlled recipients, inflating the victim's per-user quota usage and consuming shared pool capacity without the victim's consent — a resource-exhaustion/DoS vector against an unrelated account.

### Likelihood Explanation
Exploitability requires the attacker to observe a valid `(data, signer, signature, submit_timestamp)` tuple submitted by another party (e.g. via a non-TLS RPC endpoint, a malicious/compromised relay, or simply because HOP is designed as a public hand-off mechanism where `data`, `signer`, and `signature` are not secret — only knowledge of which recipient private key can `claim` is secret). Given HOP's protocol purpose (public off-chain relay of encrypted hand-off payloads to be later promoted on-chain), and that the entry needs only to have expired/been-acked before replay, this is realistically triggerable by any unprivileged RPC caller with no special role.

### Recommendation
Bind `recipients` into the signed payload, mirroring the fix pattern in the external report (verify the object matches what was signed):
```rust
pub fn submit_signing_payload(hash: &HopHash, recipients_hash: &[u8;32], submit_timestamp: u64) -> [u8; 32] {
    // include blake2_256(recipients.encode()) in the hashed buffer
}
```
and recompute/verify `recipients_hash` in `HopRpcServer::submit` before calling `pool.insert`, so a signature only ever authorizes the exact `(data, recipients, submit_timestamp)` triple it was created for.

### Proof of Concept
1. Legitimate user Alice calls `hop_submit(data, recipients=[Bob], signature=S, signer=Alice, submit_timestamp=T)`. `S` verifies over `blake2_256(HOP_SUBMIT_CONTEXT || blake2_256(data) || T)` only, per [9](#0-8) . Entry stored at `H = blake2_256(data)`.
2. Bob calls `hop_claim`/`hop_ack`; once all recipients ack, `pool.rs::ack` removes the entry from `index` (lines 636-649 above), freeing hash `H`.
3. Attacker (having observed `data, S, Alice-signer, T` from the network/logs) calls `hop_submit(data, recipients=[Attacker], signature=S, signer=Alice, submit_timestamp=T)`. `H` is no longer in `index`, so `DuplicateEntry` is not triggered; `S` still verifies (unchanged payload); the entry is re-inserted charged to Alice's `sender_id` with `recipients=[Attacker]`.
4. Attacker now calls `hop_claim`/`hop_ack` against this new entry and receives `data`, despite never being an intended recipient and never having signed anything themselves.

pub const HOP_SUBMIT_CONTEXT: &[u8] = b"hop-submit-v1:";

/// Domain-separator prefix for `hop_ack` signatures.
pub const HOP_ACK_CONTEXT: &[u8] = b"hop-ack-v1:";

/// Compute the 32-byte payload that HOP recipients / submitters sign for a given
/// operation. This is `blake2_256(context || hash)` and ensures signatures from
/// one operation cannot be replayed in another.
pub fn signing_payload(context: &[u8], hash: &HopHash) -> [u8; 32] {
	let mut buf = Vec::with_capacity(context.len() + 32);
	buf.extend_from_slice(context);
	buf.extend_from_slice(hash.as_bytes());
	blake2_256(&buf)
}

/// Compute the 32-byte payload signed at `hop_submit` time.
///
/// The runtime pallet re-derives this exact byte sequence to verify the
/// signature on-chain, so the construction must remain byte-identical to the
/// pallet's `signing_payload(data, submit_timestamp)`:
/// `blake2_256(HOP_SUBMIT_CONTEXT || blake2_256(data) || submit_timestamp.to_le_bytes())`.
pub fn submit_signing_payload(hash: &HopHash, submit_timestamp: u64) -> [u8; 32] {
	let mut buf = [0u8; HOP_SUBMIT_CONTEXT.len() + 32 + 8];
	buf[..HOP_SUBMIT_CONTEXT.len()].copy_from_slice(HOP_SUBMIT_CONTEXT);
	buf[HOP_SUBMIT_CONTEXT.len()..HOP_SUBMIT_CONTEXT.len() + 32].copy_from_slice(hash.as_bytes());
	buf[HOP_SUBMIT_CONTEXT.len() + 32..].copy_from_slice(&submit_timestamp.to_le_bytes());
	blake2_256(&buf)
}
