### Title
Unvalidated ERC20 transfer amount trusted as-is in `ERC20Transactor::withdraw_asset_with_surplus` / `deposit_asset_with_surplus` (Fee-on-transfer / non-standard ERC20 accounting bypass) - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

### Summary
`ERC20Transactor`, the XCM `TransactAsset` implementation that bridges XCM asset handling to arbitrary ERC20 contracts deployed on `pallet-revive`, credits/debits the XCM holding register with the `amount` requested in the ERC20 `transfer` call, rather than verifying the actual balance delta caused by the call. This is exactly the class of bug described in the referenced report: trusting a token's self-reported "success" instead of measuring the real balance change, which breaks under fee-on-transfer, rebasing, or otherwise non-conforming ERC20 tokens.

### Finding Description
In `withdraw_asset_with_surplus`, the transactor calls the target contract's `transfer(checking_address, amount)` via `pallet_revive::Pallet::<T>::bare_call`, and if the call doesn't revert and the ABI-decoded boolean return value is `true`, it unconditionally mints an `Erc20Credit(amount)` into the `AssetsInHolding` register: [2](#0-1) 

There is no read of the checking account's actual token balance before/after the call to confirm that `amount` (rather than some lesser amount, e.g. after a transfer fee) was actually received. The same pattern exists symmetrically in `deposit_asset_with_surplus`, which transfers `amount` from the checking account to the beneficiary and treats a `true` boolean return as proof that the beneficiary was credited `amount`: [3](#0-2) 

If the ERC20 contract implements a transfer fee (deducting tokens on transfer while still returning `true`), the checking account (the parachain's reserve/collateral account for that asset) will receive less than `amount`, but the XCM executor's internal accounting (`AssetsInHolding`) will believe the full `amount` was withdrawn and is available to deposit/teleport elsewhere.

### Impact Explanation
Because the holding register is over-credited relative to what is actually escrowed in `TransfersCheckingAccount`, repeated reserve-transfers of a fee-charging ERC20 asset would progressively drain the real token balance held in the checking account below what the XCM system (and any receiving chain crediting a wrapped/foreign representation of this asset) believes is backed. This is a reserve/collateral accounting break — the same "protocol leakage" impact called out in the original report — and could allow users to move out more real value than the checking account can back over time, or allow the checking account to become insolvent relative to outstanding foreign-asset claims on the destination side.

### Likelihood Explanation
Exploitability depends entirely on whether governance registers an ERC20 contract for this transactor whose `transfer` implementation charges a fee or otherwise transfers less than the requested `amount` while still returning `true`. This mirrors the exact mitigation stance PoolTogether took ("we don't plan to support fee on transfer tokens"), which is why the original finding was downgraded to Medium. Here likelihood is similarly conditional on asset registration policy, but unlike a permissioned single-asset system, `ERC20Transactor` is a generic matcher-driven transactor intended to support arbitrary registered ERC20 contracts on `pallet-revive`, which increases the chance that a non-conforming contract could be onboarded (accidentally or via a compromised/malicious asset issuer) and be triggered by any unprivileged user simply executing a normal reserve-transfer XCM using that asset.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, query the actual `balanceOf` of the checking/destination account before and after the `transfer` call (or use `transferFrom`-style pull with a balance-delta check as recommended in the original report), and credit/return only the observed delta into `AssetsInHolding` instead of the originally requested `amount`. Alternatively, restrict the `Matcher` configuration to a governance-curated allowlist of ERC20 contracts that are verified not to implement fee-on-transfer or rebasing semantics, and document this as a hard registration requirement.

### Proof of Concept
1. Deploy (or have registered as a foreign asset) an ERC20 contract on `pallet-revive` whose `transfer` function burns/redirects 1% of `value` to a separate address while still returning `true`.
2. Register this contract's `H160` address so that `Matcher::matches_fungibles` resolves it for `ERC20Transactor`, as done in `asset-hub-westend`'s `xcm_config.rs`.
3. A user executes a `limited_reserve_transfer_assets` (or `pallet_xcm::execute`) XCM program that includes `WithdrawAsset` for this token, driving execution into `withdraw_asset_with_surplus` at `erc20_transactor.rs:150-216`.
4. The `TransfersCheckingAccount` receives only 99% of `amount`, but `Erc20Credit(amount)` (100%) is placed into holding at line 198-201, and subsequent XCM instructions (e.g., `DepositAsset` on a remote/local chain) proceed as if the full `amount` was collateralized.
5. Repeating this creates a growing gap between the real balance in `TransfersCheckingAccount` and the total amount XCM has "moved," eventually leaving the reserve unable to back all recorded transfers.

Note: I could not find any code path in `erc20_transactor.rs` or its call sites that performs a balance-before/after check to mitigate this, and the transactor is actively wired into `asset-hub-westend`'s runtime, confirming this is live rather than dead code. I did not have access to the asset-registration governance flow for this transactor in this session, so I cannot state with certainty how strict the current onboarding requirements are for ERC20 contracts eligible for this path.
