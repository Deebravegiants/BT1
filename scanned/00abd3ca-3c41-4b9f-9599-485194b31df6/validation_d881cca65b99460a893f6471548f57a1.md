### Title
Missing slippage protection (`amount_out_min = None`) in `SwapFirstAssetTrader::refund_weight` swap - (File: `cumulus/primitives/utility/src/lib.rs`)

### Summary
`SwapFirstAssetTrader`, a `WeightTrader` used by the XCM executor to let users pay execution fees in a non-native asset (via `pallet_asset_conversion`'s `SwapCredit`), correctly enforces an exact-output swap when *buying* weight, but its `refund_weight` implementation performs the reverse swap with the `amount_out_min` slippage parameter hard-coded to `None`, mirroring the UniswapV3 `amountOutMinimum = 0` pattern from the referenced report.

### Finding Description
In `buy_weight`, the trader swaps the user's asset for the `Target` asset using `swap_tokens_for_exact_tokens`, which fixes the desired *output* amount (the fee) and only varies the input — this is slippage-safe by construction. [1](#0-0) 

However, `refund_weight` swaps the excess `Target` asset fee back into the asset the user originally paid with, using `swap_exact_tokens_for_tokens` and passing `None` as `amount_out_min`: [2](#0-1) 

`SwapCredit::swap_exact_tokens_for_tokens`'s `amount_out_min` parameter exists specifically to bound the acceptable output of a swap; the pallet's own trait doc says "If `amount_out_min` is provided and the swap can't achieve at least this amount, an error is returned," and the pallet's extrinsic-level API always enforces it via `ProvidedMinimumNotSufficientForSwap`. [3](#0-2) [4](#0-3) 

By passing `None`, `refund_weight` disables this protection entirely — the swap will accept any non-negative output amount, exactly analogous to `amountOutMinimum = 0` in the UniswapV3 report.

`SwapFirstAssetTrader` is wired into production runtime configurations, e.g. Penpal's `XcmConfig::Trader`: [5](#0-4) 

### Impact Explanation
When an XCM message pays execution fees with a non-`Target` asset and the actual weight consumed is less than the weight bought (a common case — e.g. `BuyExecution`/`PayFees` with headroom, or partial instruction execution/error handling), `refund_weight` is invoked to give back the equivalent of the unused fee, swapped back into the user's original asset. Because the swap has no minimum-output bound, a block producer or any actor able to trade against the relevant `pallet-asset-conversion` pool in the same block (sandwich pattern: front-run to move the price unfavorably, let the zero-slippage refund swap execute at a bad rate, then back-run to restore price and capture the difference) can extract value from the refund at the expense of the XCM message's fee payer, who receives a smaller refund than the fair-market amount.

### Likelihood Explanation
Exploitation requires:
- A runtime configuring `SwapFirstAssetTrader` with a liquid, permissionless `pallet-asset-conversion` pool (true for Penpal, and this pattern is promoted for Asset Hub-style fee-swap configurations).
- An attacker capable of executing trades against that pool immediately before/after the block containing the refund-triggering XCM message — feasible for anyone submitting ordinary swap extrinsics in adjacent transactions/blocks, not just a privileged or trusted role.
- The refunded amount must be non-trivial enough to be worth manipulating, which scales with the weight headroom purchased vs. consumed — attacker-influenceable to some degree by the fee payer's own `WeightLimit`/`PayFees` choices, but the swap itself is triggered automatically by ordinary, unprivileged XCM usage (no special origin or trusted role needed).

This is a reachable, un-mocked code path exercised by real runtime configuration, not merely a test helper.

### Recommendation
Compute a minimum acceptable refund amount (e.g., via `QuotePrice::quote_price_exact_tokens_for_tokens` right before the swap, with a reasonable tolerance) and pass it as `Some(min_amount)` instead of `None` in the `swap_exact_tokens_for_tokens` call inside `refund_weight`. If a suitable minimum cannot be safely computed (e.g., quote unavailable), consider skipping the refund swap and returning `None` (no refund) rather than accepting an unbounded slippage swap, consistent with how `buy_weight` already avoids this risk by using the exact-output variant.

### Proof of Concept
1. Configure a runtime with `SwapFirstAssetTrader<Target, AssetConversionSwapCredit, ...>` as in `cumulus/parachains/runtimes/testing/penpal/src/xcm_config.rs`.
2. Create a `Target`/`ClientAsset` pool via `pallet_asset_conversion` with modest liquidity.
3. Submit an XCM message that pays fees in `ClientAsset` with `WeightLimit`/`PayFees` amount noticeably larger than the weight actually consumed (so `refund_weight` is triggered with a non-trivial `refund_amount`), matching the pattern exercised in `cumulus/primitives/utility/src/tests/swap_first.rs`.
4. In the same block (or immediately preceding it), submit a large trade against the `Target`/`ClientAsset` pool to move the exchange rate unfavorably for a `Target -> ClientAsset` swap, then reverse it after the refund executes.
5. Observe that `refund_weight`'s swap at line 540-544 (`swap_exact_tokens_for_tokens(..., refund, None)`) executes without any minimum-output check, so the XCM sender receives a reduced refund while the attacker profits from the round-trip trade — reproducing the `amountOutMinimum = 0` sandwich pattern described in the source report.
