### Title
Missing `return` after email-claim validation failure allows OIDC session creation to proceed with an unvalidated/empty email - (File: core/sessions/oidcauth/oidc.go)

### Summary
`handleTokenExchange` in `core/sessions/oidcauth/oidc.go` validates several inputs during the OIDC login callback (state, exchange code, ID token signature, claim extraction) and correctly `return`s on each failure — except for the email-claim check, where the missing `return` lets execution fall through and finish authenticating the caller.

### Finding Description
In `handleTokenExchange`, after verifying the ID token and mapping claims to a role, the code attempts to read the `email` claim: [1](#0-0) 

Unlike every other validation branch in this function (state mismatch, exchange failure, missing `id_token`, verification failure, claim parsing failure, role-mapping failure — each of which correctly `return`s after writing an error response), this branch omits the `return` statement. Execution therefore continues past the failed check and reaches the role-mapping and session-creation logic: [2](#0-1) 

The session row is inserted using `strings.ToLower(email)` where `email` is the zero-value empty string (since the type assertion at line 226 failed), and a valid session cookie is then saved and a `200 OK` / `Success: true` JSON response is sent to the client: [3](#0-2) 

Session lookup later trusts whatever `user_email`/`user_role` was stored against the session ID without re-validating identity: [4](#0-3) 

### Impact Explanation
Any caller completing the OIDC callback flow whose identity token lacks a usable string `email` claim (e.g., misconfigured/permissive external IdP tenant, a claim of the wrong JSON type, or a user record at the IdP without an email attribute) still receives a fully authenticated, valid `oidc_sessions` cookie with whatever role the group claims mapped to (including potentially `admin`, since role mapping already succeeded before the email check). This is a concrete authentication-state bypass: the endpoint reports failure via `c.String(http.StatusInternalServerError, ...)` but does not actually stop request processing, so the caller ends up authenticated despite the server having flagged the input as invalid. Additionally, every such caller is persisted with the same empty-string email, creating cross-user session confusion (multiple distinct identities all keyed to `""` in `oidc_sessions`), which can affect `ClearNonCurrentSessions` and other email-keyed session operations.

### Likelihood Explanation
Reachability requires: (1) a working OIDC login flow already configured (self-hosted or attacker-influenced IdP tenant), and (2) an identity/claims response missing a string `email` value. This is plausible in real deployments where the IdP's email claim is optional, differently typed (array vs string), or intentionally omitted by an account the caller controls at the IdP. Because the OIDC flow is exposed to any unauthenticated client hitting the callback endpoint, and the bug is a simple missing `return` (not a deep exploit chain), likelihood is moderate — gated mainly by whether the configured IdP can be induced to omit/malform the email claim while still passing group/role claim mapping.

### Recommendation
Add the missing `return` immediately after the failed type assertion, exactly as done for every other validation branch in this function:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims")
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
```

### Proof of Concept
Not independently executed (index/read-only access only); the control-flow defect is directly verifiable by inspecting `core/sessions/oidcauth/oidc.go` lines 226–276: unlike the four other error branches in the same function which call `return`, the email-claim branch does not, so control falls through to `IDClaimsToUserRole`, the `INSERT INTO oidc_sessions` call, and `ginSession.Save()`, ultimately returning `http.StatusOK` with `Success: true` to the caller.

// AuthorizedUserWithSession will return the API user associated with the Session ID if it
// exists and hasn't expired
func (oi *oidcAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (clsessions.User, error) {
	if len(sessionID) == 0 {
		return clsessions.User{}, errors.New("session ID cannot be empty")
	}
	var foundUser clsessions.User
	err := sqlutil.TransactDataSource(ctx, oi.ds, nil, func(tx sqlutil.DataSource) error {
		// Query the oidc_sessions table for given session ID, user role and email are saved after the id claims is provided and validated
		var foundSession struct {
			UserEmail string
			UserRole  clsessions.UserRole
			Valid     bool
		}
		if err := tx.GetContext(ctx, &foundSession,
			"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM oidc_sessions WHERE id = $1",
			sessionID, oi.config.SessionTimeout().Duration(),
		); err != nil {
			if errors.Is(err, sql.ErrNoRows) {
				return clsessions.ErrUserSessionExpired
			}
			return err
		}
		if !foundSession.Valid {
			// Sessions expired, purge
			return clsessions.ErrUserSessionExpired
		}
		foundUser = clsessions.User{
			Email: foundSession.UserEmail,
			Role:  foundSession.UserRole,
		}
		return nil
	})
	if err != nil {
		if errors.Is(err, clsessions.ErrUserSessionExpired) {
			if _, execErr := oi.ds.ExecContext(ctx, "DELETE FROM oidc_sessions WHERE id = $1", sessionID); execErr != nil {
				oi.lggr.Errorf("error purging stale OIDC session: %v", execErr)
			}
		}
		return clsessions.User{}, err
	}
	return foundUser, nil
}
