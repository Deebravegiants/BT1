### Title
JWT replay-protection check-then-record race allows unlimited authorization-token reuse - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
`WorkflowMetadataHandler.Authorize` implements JWT replay protection for HTTP-triggered workflow-execution requests using a separate "check" step (`isReplay`) and "record" step (`recordUsage`), rather than a single atomic check-and-record operation. Between the two steps, concurrent requests carrying the identical signed JWT can each pass the replay check before either has recorded its usage, letting the same authorization token be redeemed more than once — the same bug class as the reported Apache CXF `DefaultEncryptingCodeDataProvider` flaw where `removeCodeGrant` failed to make code redemption atomic, permitting unlimited replay of a single-use credential.

### Finding Description
`Authorize` verifies the JWT, then checks for prior use, then (after further authorization checks) records usage: [1](#0-0) 

The read (`isReplay`) and write (`recordUsage`) are two independent, separately-locked operations on `jwtReplayCache`: [2](#0-1) 

Each uses its own `RLock`/`Lock`, so there is no atomicity guarantee across the read-check-then-later-write sequence in `Authorize`. If two requests carrying the same JWT (`jti`) arrive concurrently — e.g., replayed by a network intermediary or by re-submitting a captured request to the gateway HTTP trigger endpoint — both can call `isReplay(claims.ID)` and both observe "not yet used" before either calls `recordUsage(claims.ID)`, since `recordUsage` only runs after the (non-trivial) signer/authorized-keys lookup in between. This is a classic check-then-act (TOCTOU) race that defeats the intended single-use guarantee.

This contrasts with the codebase's other replay-protection mechanism, `RequestReplayGuard.CheckAndRecord`, which correctly performs the presence-check and insertion under a single mutex-held critical section, making it atomic: [3](#0-2) 

`Authorize` is reached directly from the gateway's HTTP trigger handler when processing user-submitted workflow execution requests, i.e., from an unprivileged external client hitting the internet-facing gateway. [4](#0-3) 

### Impact Explanation
A captured/observed signed JWT for a workflow-execution request can be replayed concurrently to bypass the intended one-time-use restriction, resulting in duplicate/unauthorized execution of a workflow trigger using someone else's authorization token. This is a request-impersonation / authorization-bypass condition on the internet-facing gateway trigger path, potentially causing duplicate or unauthorized workflow runs.

### Likelihood Explanation
Exploitation requires the attacker to have captured a valid signed JWT (e.g., via network observation, logging, or a legitimate but replayable client request) and then race two copies of it against the gateway within the narrow window between the `isReplay` read and the later `recordUsage` write. This window is small but real under load or with intentionally-scheduled concurrent submissions, and the codebase's own test suite documents JWT replay as an explicit security property being defended (`TestWorkflowMetadataHandler_Authorize`/"JWT replay protection" test), confirming this is a designed invariant rather than an incidental behavior — but the tests only exercise sequential (non-concurrent) replay, not the concurrent race, so the atomicity gap is untested.

### Recommendation
Make the check-and-record step atomic, mirroring `RequestReplayGuard.CheckAndRecord`: acquire a single lock, check `isReplay`, and if not already used, immediately record usage before releasing the lock and before performing (or independent of) the downstream authorized-key lookup — or perform provisional recording first and roll back on later authorization failure. At minimum, combine `isReplay` + `recordUsage` into one method executed under a single `jwtReplayCache.mu` critical section.

### Proof of Concept
1. Client obtains/derives a validly signed workflow-execution JWT (`claims.ID` = jti) for `MethodWorkflowExecute`.
2. Client (or attacker replaying a captured token) fires two concurrent `HandleUserTriggerRequest` calls to the gateway with the same JWT.
3. Both goroutines invoke `Authorize`: both call `h.jwtCache.isReplay(claims.ID)` before either calls `h.jwtCache.recordUsage(claims.ID)`, since `recordUsage` is only invoked after the signer/authorized-key lookup completes.
4. Both authorization calls succeed, and the workflow-execution request is processed twice, contradicting the single-use guarantee the cache is intended to enforce (as demonstrated conceptually by contrast with `TestRequestReplayGuard_ConcurrentAccess`, which shows the *correct* atomic pattern rejecting all but one concurrent caller with `ErrRequestAlreadySeen`) — no equivalent concurrency test exists for `jwtReplayCache`/`Authorize`. [5](#0-4)

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}

func TestRequestReplayGuard_ConcurrentAccess(t *testing.T) {
	guard := NewRequestReplayGuard()
	futureExpiry := time.Now().UTC().Unix() + 100

	const goroutines = 100
	results := make([]error, goroutines)
	var wg sync.WaitGroup
	wg.Add(goroutines)

	for i := range goroutines {
		go func(idx int) {
			defer wg.Done()
			results[idx] = guard.CheckAndRecord("same-digest", futureExpiry)
		}(i)
	}
	wg.Wait()

	successCount := 0
	duplicateCount := 0
	for _, err := range results {
		if err == nil {
			successCount++
		} else {
			require.ErrorIs(t, err, ErrRequestAlreadySeen)
			duplicateCount++
		}
	}

	assert.Equal(t, 1, successCount, "exactly one goroutine should succeed")
	assert.Equal(t, goroutines-1, duplicateCount, "all others should be rejected as duplicates")
}
