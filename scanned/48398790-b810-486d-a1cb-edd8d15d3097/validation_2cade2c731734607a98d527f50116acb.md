Based on the bug class in the report — an `initialize()`-style entry point accepting a caller-controlled configuration/parameter with no upper-bound validation, enabling resource-exhaustion — the closest reachable analog in this codebase is the GraphQL pagination `Limit` argument, which is accepted directly from an authenticated API caller and passed through without any upper bound in several resolvers, unlike the one resolver that does clamp it.

### Title
Unbounded, user-controlled `Limit` argument in GraphQL resolvers enables resource-exhaustion (DoS) - ([File: core/web/resolver/helpers.go], [File: core/web/resolver/query.go])

### Summary
`pageLimit()` only supplies a default value (50) when the caller-supplied `Limit` is `nil`; if a caller supplies any `Limit`, that raw value is returned unmodified with no upper-bound check. Multiple GraphQL resolvers (`Bridges`, `Nodes`, `JobRuns`) pass this unclamped value straight into ORM queries that fetch and materialize that many rows, so an authenticated caller can request an arbitrarily large page size on every call.

This is the same root-cause pattern as the reported issue: a caller-supplied numeric parameter (there, `ResourceMetering.ResourceConfig`; here, GraphQL `Limit`) flows into resource-consuming logic (there, gas metering; here, DB row fetch + JSON-API/GraphQL response construction) without any sanity/upper-bound check, so a caller can force the node to do unbounded work per request.

### Impact Explanation
A logged-in operator-UI/API user (any role sufficient to pass `authenticateUser`, which only requires a valid session/API token, not necessarily an edit/admin role) can repeatedly issue `bridges`, `nodes`, or `jobRuns` queries with an extremely large `Limit` (e.g. `2^31-1`). Each such request forces the ORM to fetch and the presenter layer to marshal that many rows into memory and over the wire, which can be used to degrade node responsiveness or exhaust memory/CPU — a denial-of-service condition consistent with the reported bug class, though the blast radius here is a single Chainlink node process rather than a smart contract.

### Likelihood Explanation
Any authenticated session or API-token holder can trigger this without needing edit/run privileges, since these three queries only call `authenticateUser` (not `authenticateUserCanEdit`). No special crafting beyond sending a large integer is required, making exploitation straightforward for any authenticated account (including a low-privilege "read" role).

### Recommendation
Clamp `Limit` (and any similarly caller-supplied bound) to a sane maximum in `pageLimit()` itself, mirroring what `JobResolver.Runs` already does, so all resolvers that use it are protected uniformly, e.g. `return min(int(*limit), MaxPageLimit)`.

### Proof of Concept
1. Authenticate as any user with only "read"-level API access.
2. Issue a GraphQL query: `query { nodes(limit: 2147483647) { results { id } } }` (or `bridges`, `jobRuns` similarly).
3. Observe the resolver passes `2147483647` unmodified into `NodeStatuses`/`BridgeTypes`/`PipelineRuns`, causing the node to attempt to build and serialize a response of that size, consuming excessive memory/CPU relative to a bounded request.

func pageLimit(limit *int32) int {
	if limit == nil {
		return PageDefaultLimit
	}

	return int(*limit)
}

func (r *Resolver) Bridges(ctx context.Context, args struct {
	Offset *int32
	Limit  *int32
}) (*BridgesPayloadResolver, error) {
	if err := authenticateUser(ctx); err != nil {

}

func (r *Resolver) Nodes(ctx context.Context, args struct {
	Offset *int32
	Limit  *int32
}) (*NodesPayloadResolver, error) {
	if err := authenticateUser(ctx); err != nil {
		return nil, err
	}

	offset := pageOffset(args.Offset)
	limit := pageLimit(args.Limit)
	r.App.GetLogger().Debugw("resolver Nodes query", "offset", offset, "limit", limit)
	allNodes, total, err := r.App.GetRelayers().NodeStatuses(ctx, offset, limit)
	r.App.GetLogger().Debugw("resolver Nodes query result", "nodes", allNodes, "total", total, "err", err)

	if err != nil {
		r.App.GetLogger().Errorw("Error creating get nodes status from app", "err", err)
		return nil, err
	}
	npr, warn := NewNodesPayload(allNodes, safeInt32(total))
	if warn != nil {
		r.App.GetLogger().Warnw("Error creating NodesPayloadResolver", "err", warn)
	}
	return npr, nil
}
