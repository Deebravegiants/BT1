### Title
Cross-User Response Hijack via Global `MessageID` Key in Gateway `savedCallbacks` Map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The report's core bug class is a shared, unscoped piece of state ("receiver") that is set before an asynchronous/external operation and then blindly trusted/consumed by whichever caller invokes the callback path first, without validating that the caller is entitled to claim it. The direct analog in this repo is `handler.savedCallbacks`, a map keyed only by the client-supplied `msg.Body.MessageID` — with no binding to the sender/user who created the entry — used to route trigger responses back to a specific user.

### Finding Description
In `core/services/gateway/handlers/capabilities/handler.go`, `HandleLegacyUserMessage` stores the caller's callback keyed solely by the message ID taken from the untrusted request: [1](#0-0) 

Later, when a DON node responds, `handleWebAPITriggerMessage` looks the entry up and deletes it purely by `msg.Body.MessageID`, then forwards the response to whatever callback is stored under that key: [2](#0-1) 

The lookup/deletion is not scoped by the originating client identity at all — the key is exactly `msg.Body.MessageID`, and nothing ties it to the user session that created the request. Contrast this with the more defensive pattern used elsewhere in the same package tree, `core/services/gateway/handlers/common/requestcache.go`, which deliberately composes the cache key from **both** sender and message ID to prevent exactly this kind of collision: [3](#0-2) [4](#0-3) 

Because `handler.savedCallbacks` uses only the bare `MessageID` (attacker/user-controlled input embedded in the request body), if two different users' in-flight legacy trigger requests happen to use the same `MessageID` (whether by collision, or deliberately chosen by an attacker who can predict or brute-force another user's ID scheme), the second `HandleLegacyUserMessage` call silently overwrites the first entry in the map:
```go
h.savedCallbacks[msg.Body.MessageID] = &savedCallback{...}
```
When the DON node's response for the *original* (victim's) request arrives, it is matched purely by `MessageID` and delivered to whichever callback currently occupies that slot — which may now be the attacker's callback, not the victim's. This is precisely the "unvalidated shared receiver" footgun from the report: a global/shared piece of state authorizing delivery of a result is set and later consumed without validating whose call it belongs to.

### Impact Explanation
An unprivileged client (a user submitting legacy `web_api_trigger` requests through the gateway) can potentially intercept another user's trigger response by supplying/colliding on the same `MessageID`, resulting in cross-user response confusion — the attacker receives data intended for another user's request/session. Depending on what the trigger payload response contains (e.g., HTTP responses or execution results relayed from the workflow DON), this could leak information the attacker was not authorized to see, or trick the attacker into acting on a mismatched result. This falls squarely under "cross-user response confusion" flagged as acceptable impact for this scan.

### Likelihood Explanation
Likelihood depends on whether `MessageID` values are cryptographically random/high-entropy and how they're generated by legitimate clients (this could not be fully confirmed from the available index — the definition of `api.Message.Body.MessageID` and its generation path on the client side were not found in the indexed portion of `core/services/gateway/api/message.go` beyond field references). If `MessageID` is client-chosen or low-entropy, likelihood is high since an attacker can simply reuse or brute-force IDs from another concurrent request. If it is generated server-side with strong randomness, likelihood is much lower and effectively limited to accidental collisions. This uncertainty should be resolved by inspecting the full `message.go` and any callers that populate `MessageID` for legacy trigger requests, ideally by running a Devin session against the full repository since the code index size limits may have excluded some relevant file contents.

### Recommendation
Scope the `savedCallbacks` key (and its lookup/delete) by both the message ID and an authenticated identity of the requester (e.g., session/user identifier or a server-generated correlation ID that is never attacker-influenced), analogous to the `globalID{sender, id}` pattern already used in `handlers/common/requestcache.go`. Reject or fail closed if a `MessageID` collision is detected instead of silently overwriting the existing entry.

### Proof of Concept
1. User A submits a legacy trigger request with `MessageID = "X"`; the gateway stores A's callback at `savedCallbacks["X"]` and fans it out to DON nodes.
2. Before the DON responds, Attacker B submits a legacy trigger request also using `MessageID = "X"` (reused/guessed); the gateway overwrites `savedCallbacks["X"]` with B's callback.
3. A DON node responds for the message ID `"X"` (originally A's request). `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds B's callback, deletes the entry, and delivers A's response data to B.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
