This directly matches the reported bug class: a critical post-validation step fails, but the handler does not stop/return, and execution proceeds to complete the (here) authentication/session-creation flow anyway.

### Title
Missing `return` after failed email-claim extraction and failed DB session persistence lets `handleTokenExchange` complete login with an unvalidated/unpersisted session - ([File: core/sessions/oidcauth/oidc.go])

### Summary
In `oidcAuthenticator.handleTokenExchange`, two error checks fail to halt execution: the `email` claim type-assertion failure, and the `oidc_sessions` INSERT failure. In both cases the handler logs/writes an HTTP error body but omits `return`, so the function falls through and completes the login flow — setting a valid, signed session cookie and reporting `Success: true` to the client.

### Finding Description
After verifying the ID token and extracting role claims, the handler extracts the email claim: [3](#0-2) 
If `claims["email"]` is not a string (missing/wrong type in the IdP's ID token), the code writes an HTTP 500 body via `c.String(...)` but does not `return`. Execution continues to role mapping and then to session creation using the empty-string `email`: [4](#0-3) 
The `INSERT INTO oidc_sessions` failure path has the identical bug — the error is logged and an HTTP 500 body is written, but again no `return`: [5](#0-4) 
Immediately after, the audit logger records `AuthLoginSuccessNo2FA` unconditionally [6](#0-5) , and the handler proceeds to set the session cookie and save it: [7](#0-6) 
Because Gin does not stop handler execution on `c.String`/`c.JSON` calls (unlike `c.Abort()`), both branches are pure logging with no control-flow effect, and the response is effectively overwritten by the later `200 OK` written at the end of the function.

Consequently:
- If the DB insert into `oidc_sessions` fails, the client still receives a session cookie (`ginSession.Set(webauth.SessionIDKey, clSession.ID)`) referencing a session ID that was never persisted. The audit log incorrectly records a successful login. Subsequent use of that cookie in `AuthorizedUserWithSession` will fail lookup (`sql.ErrNoRows` → `ErrUserSessionExpired`), but the immediate response to the exchange call falsely reports success and an inconsistent audit trail is created regardless of state.
- If the email claim is missing/malformed, the session is created and persisted with `user_email = ""` and whatever `role` the group claims mapped to, and the response reports `Success: true`. Any subsequent OIDC login by a different user whose IdP also omits the email claim would map to the same empty-email row space, and `ClearNonCurrentSessions` (`SELECT user_email ... WHERE id = $sessionID`, then `DELETE ... WHERE lower(user_email)=lower($email)`) would delete/collide across sessions sharing the empty email, producing cross-user session confusion — closely analogous to the "cross-user response confusion" class called out in scope.

### Impact Explanation
This is an authentication-integrity bug on a client-facing, unauthenticated endpoint (`POST /oidc-exchange`). A malformed/incomplete but signature-valid ID token response (attacker-controllable identity provider response content, or normal misconfiguration) can produce an authenticated, cookie-backed session that is either not actually persisted server-side or is persisted with an empty owner email, undermining the intended fail-closed behavior of the login flow and creating potential for session/audit inconsistency and cross-user session collisions via the shared empty-email key.

### Likelihood Explanation
Reaching this code requires only completing the standard OIDC redirect/exchange flow that any client of the deployment can trigger; no privileged access is needed. Triggering the email-claim-missing branch requires control over (or a misconfigured) upstream OIDC provider's ID token claims — a config/provider-dependent but realistic scenario. The DB-insert-failure branch can be hit by any transient database error during the login flow, which is not exceptionally rare in production. Likelihood is moderate: it is not exploitable by IdP-agnostic clients purely via forged HTTP fields (the ID token signature is still checked), but the guard-omission means the *intended* fail-closed behavior silently doesn't happen.

### Recommendation
Add `return` immediately after both error-handling blocks:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims")
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
```
and
```go
_, err = oi.ds.ExecContext(ctx, "INSERT INTO oidc_sessions ...")
if err != nil {
    oi.lggr.Errorf("unable to create new session in oidc_sessions table %v", err)
    c.String(http.StatusInternalServerError, "Error creating session")
    return
}
```
This ensures the function reverts (aborts) the login flow consistently with its error responses, matching the pattern already used correctly elsewhere in the same function (e.g., the `ginSession.Save()` error path at lines 267-271 which does `return`).

### Proof of Concept
1. Configure or intercept an OIDC provider so that its ID token claims omit the standard `email` claim but include a valid group claim matching one of `AdminClaim`/`EditClaim`/`RunClaim`/`ReadClaim`.
2. Complete the standard flow: `GET /oidc-login` → redirect to provider → provider redirects back with `code`/`state` → client calls `POST /oidc-exchange` with `{code, state}`.
3. In `handleTokenExchange`, `claims["email"].(string)` fails (`ok == false`); the `c.String(http.StatusInternalServerError, ...)` write occurs but function does not return.
4. Execution proceeds through `IDClaimsToUserRole`, inserts a row into `oidc_sessions` with `user_email = ""` and the mapped role, sets the session cookie, and returns `200 OK {"success": true}` to the client — despite the code having already signaled a hard failure.
5. The client now holds a valid, cookie-based authenticated session tied to an empty-email record with a role, which `AuthorizedUserWithSession` will happily authorize on subsequent requests [8](#0-7) .

func (oi *oidcAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (clsessions.User, error) {
	if len(sessionID) == 0 {
		return clsessions.User{}, errors.New("session ID cannot be empty")
	}
	var foundUser clsessions.User
	err := sqlutil.TransactDataSource(ctx, oi.ds, nil, func(tx sqlutil.DataSource) error {
		// Query the oidc_sessions table for given session ID, user role and email are saved after the id claims is provided and validated
		var foundSession struct {
			UserEmail string
			UserRole  clsessions.UserRole
			Valid     bool
		}
		if err := tx.GetContext(ctx, &foundSession,
			"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM oidc_sessions WHERE id = $1",
			sessionID, oi.config.SessionTimeout().Duration(),
		); err != nil {
			if errors.Is(err, sql.ErrNoRows) {
				return clsessions.ErrUserSessionExpired
			}
			return err
		}
		if !foundSession.Valid {
			// Sessions expired, purge
			return clsessions.ErrUserSessionExpired
		}
		foundUser = clsessions.User{
			Email: foundSession.UserEmail,
			Role:  foundSession.UserRole,
		}
		return nil
	})
	if err != nil {
		if errors.Is(err, clsessions.ErrUserSessionExpired) {
			if _, execErr := oi.ds.ExecContext(ctx, "DELETE FROM oidc_sessions WHERE id = $1", sessionID); execErr != nil {
				oi.lggr.Errorf("error purging stale OIDC session: %v", execErr)
			}
		}
		return clsessions.User{}, err
	}
	return foundUser, nil
}
