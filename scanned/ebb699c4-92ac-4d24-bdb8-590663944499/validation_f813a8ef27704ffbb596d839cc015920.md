### Title
Cross-user response confusion via attacker-controlled `MessageID` collision in gateway `WebAPIHandler` callback map - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
The gateway's legacy `WebAPIHandler` (used for `web_api_trigger` requests) stores the pending user callback in a single map keyed only by the client-supplied `MessageID`, with no binding to the sender's identity. Because `MessageID` is fully attacker-controlled and is not required to be unique per-sender, one unprivileged client can choose a `MessageID` that collides with another in-flight client's request. This causes the map entry (and thus the eventual node response) to be misattributed to the wrong requester — mirroring the referenced report's root cause: state tracked only by a shared/non-scoped identifier, without proper per-owner isolation, lets one party's result "leak" to or replace another party's, because the intermediate bookkeeping step isn't atomic/isolated per caller.

### Finding Description
The user-facing entry point `gateway.ProcessRequest` decodes the raw JSON-RPC request and passes `jsonRequest.ID` straight through as the message identity: [1](#0-0) 

`ValidatedMessageFromReq` sets `m.Body.MessageID = req.ID` directly from the untrusted client request, with the only sanity checks being length/null-byte checks in `Message.Validate`: [2](#0-1) 

The gateway then dispatches to `HandleLegacyUserMessage`, which stores the caller's `callback` in a package-level map `h.savedCallbacks`, keyed **solely** by `msg.Body.MessageID`, without checking whether an entry already exists for that key or binding the entry to the requester's identity/session: [3](#0-2) 

When a DON node later responds with the same `MessageID`, `handleWebAPITriggerMessage` looks up and deletes whatever callback currently occupies that key and forwards the node's payload to it — with no verification that the retrieved callback actually belongs to the request that produced this particular node response: [4](#0-3) 

Because two different unprivileged clients (or the same client, twice) can submit requests with an identical `MessageID` (limited only to ≤200 chars and non-null-terminated, per `gateway.ProcessRequest`): [5](#0-4) 

If client B's request with the same `MessageID` arrives while client A's request is still outstanding, B's `HandleLegacyUserMessage` call overwrites A's entry in `savedCallbacks` (assignment at line 412, no existence check). When the DON subsequently sends back the response correlated to A's original job (still keyed by that `MessageID`), the handler delivers A's node response to B's callback instead of A's. A's own callback reference is lost and will only resolve via timeout in `gateway.ProcessRequest`'s `callback.Wait(ctx)`.

This is precisely analogous to the referenced Sherlock finding: a piece of state (there, the still-open `OpenPositions` quote; here, the `savedCallbacks` entry) is tracked by a shared key without being properly scoped/finalized per-owner before a second, unrelated flow reuses the same key, causing one party's outcome to be attributed to another party.

### Impact Explanation
An unprivileged client can cause another concurrent client's Web API trigger response (which may include capability/job execution results, addresses, or arbitrary payload data intended only for the original caller) to be delivered to the attacker instead, and can simultaneously deny/starve the victim's own request (which will eventually only see a `handler timeout` error). This is a cross-user response confusion vulnerability reachable purely through the internet-facing gateway endpoint by an unauthenticated/unprivileged HTTP client, without requiring any special role.

### Likelihood Explanation
Exploitation requires only sending an HTTP request to the gateway's legacy JSON-RPC endpoint with a `MessageID` chosen to match a value the attacker expects (or can observe/predict, e.g. via traffic analysis, sequential IDs used by some clients, or simply racing many collisions) another client is currently using, and winning a benign race against `savedCallbacks` map writes/reads (which is not otherwise synchronized to prevent overwrite). No authentication bypass and no special privileges are needed to reach this code path; the DON-node-side signature/rate-limit checks apply to responses, not to the initial map-key collision itself.

### Recommendation
Scope `savedCallbacks` entries by more than the caller-supplied `MessageID` — e.g., generate/derive a gateway-side unique key (or combine `MessageID` with sender/session identity and a gateway-generated nonce) before storing/looking up callbacks, and reject (rather than silently overwrite) insertion attempts when a `MessageID` collision with a still-pending entry is detected in `HandleLegacyUserMessage`.

### Proof of Concept
1. Client A sends a `web_api_trigger` request to the gateway HTTP endpoint with `MessageID = "X"`; the gateway registers A's callback under `savedCallbacks["X"]` in `HandleLegacyUserMessage` [6](#0-5)  and forwards the request to DON nodes.
2. Before any node responds, client B (attacker) sends its own `web_api_trigger` request also using `MessageID = "X"`. This overwrites `savedCallbacks["X"]` with B's callback via the same unconditional assignment.
3. A DON node later replies for A's original trigger with the same `MessageID = "X"`. `handleWebAPITriggerMessage` pulls whatever callback is currently stored under `"X"` (now B's) and delivers A's response payload to B: [7](#0-6) .
4. Client A's original `callback.Wait(ctx)` in `gateway.ProcessRequest` never resolves and eventually times out [8](#0-7) , while B has received A's response data.

// ValidatedMessageFromReq validated and extracts a legacy Gateway Message
// from params field of JSON-RPC request
func ValidatedMessageFromReq(req *jsonrpc.Request[json.RawMessage]) (*api.Message, error) {
	if req.Version != "2.0" {
		return nil, errors.New("incorrect jsonrpc version")
	}
	if req.Method == "" {
		return nil, errors.New("empty method field")
	}
	if req.Params == nil {
		return nil, errors.New("missing params attribute")
	}
	var m api.Message
	err := json.Unmarshal(*req.Params, &m)
	if err != nil {
		return nil, fmt.Errorf("failed to unmarshal request params: %w", err)
	}
	m.Body.Method = req.Method
	m.Body.MessageID = req.ID
	err = m.Validate()
	if err != nil {
		return nil, err
	}
	return &m, nil
}

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageID) == 0 || len(m.Body.MessageID) > MessageIDMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageID, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonID) == 0 || len(m.Body.DonID) > MessageDonIDMaxLen {
		return errors.New("invalid DON ID length")
	}

		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
