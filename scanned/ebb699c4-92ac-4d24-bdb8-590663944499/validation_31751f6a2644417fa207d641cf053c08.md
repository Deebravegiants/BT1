### Title
Unauthenticated/unauthorized legacy Gateway user messages are fanned out to every DON node with no allowlist or rate-limiting - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The capabilities Gateway handler's legacy HTTP entrypoint, `HandleLegacyUserMessage`, forwards any structurally-valid, self-signed message to every node in the DON without checking the signer against any allowlist or applying any rate limit, as explicitly flagged by the code's own `// TODO: apply allowlist and rate-limiting here` comment. This mirrors the H-10 root cause: absence of admission-control (mempool-equivalent) validation lets any external caller cause the system to accept and propagate/store attacker-supplied payloads at scale.

### Finding Description
`ValidatedMessageFromReq` (`core/services/gateway/handlers/common/message_util.go`) and `Message.Validate()` (`core/services/gateway/api/message.go`) only verify structural constraints (field lengths, no null-byte suffixes, valid signature *format*) and recover a signer address via `ExtractSigner`. There is no check that the recovered signer belongs to any permitted/allowlisted set of senders — any party who can produce an ECDSA keypair can self-sign a message and pass validation. [1](#0-0) 

In `HandleLegacyUserMessage`, after basic decoding/staleness checks, the code proceeds directly to persisting a callback entry and fanning the request out to **every DON member**, with the allowlist/rate-limit gap called out directly in the source: [2](#0-1) 

Unlike the sibling `trigger` handler path (`core/capabilities/webapi/trigger/trigger.go`), which performs a `verify... unauthorized Sender` check before processing (per `trigger_test.go`'s "sad case Not Allowed Sender"), this legacy capabilities handler path has no equivalent sender authorization gate before forwarding to nodes. [3](#0-2) 

### Impact Explanation
An unprivileged caller can repeatedly hit the Gateway's legacy HTTP endpoint with distinct self-signed, freshly-keyed messages. Each request causes the Gateway to store a `savedCallback` entry (bounded only by `MaxSavedCallbacks`/pruning) and to broadcast an HTTP call to every node in the DON, consuming node-side bandwidth, connection slots, and processing cycles across the entire DON — an amplification of a single unauthenticated request into N node-directed messages, directly analogous to the "no mempool" bloat class (unvalidated input accepted and propagated widely with resource cost, bounded here only by best-effort pruning rather than real admission control).

### Likelihood Explanation
High: reaching this code path requires no privileged credentials — only a syntactically valid signed `Message` (`Validate()`'s checks are trivially satisfiable with a throwaway key), and the missing-allowlist gap is explicitly marked as an unresolved TODO in the shipped code.

### Recommendation
Implement sender allowlist verification for `HandleLegacyUserMessage` before persisting the callback and forwarding to DON members (mirroring the sender-allowlist check present in `core/capabilities/webapi/trigger/trigger.go`), and add per-sender/global rate limiting analogous to `nodeRateLimiter`, closing the `// TODO: apply allowlist and rate-limiting here` gap.

### Proof of Concept
1. Generate an arbitrary ECDSA keypair (no registration/permission needed).
2. Construct an `api.Message` with `Method = MethodWebAPITrigger`, a fresh `MessageID`, and a valid `Payload.Timestamp`; sign it with the throwaway key via `msg.Sign(...)`.
3. Submit it through the Gateway's legacy JSON-RPC HTTP endpoint (`gateway.ProcessRequest` → `HandleLegacyUserMessage`).
4. Observe the request passes `Validate()` (structural + signature-format only), is *not* checked against any allowlist, is stored in `savedCallbacks`, and is sent via `don.SendToNode` to every member of `donConfig.Members`.
5. Repeat at volume with new keys/message IDs each time to amplify a single unauthenticated caller into unbounded DON-wide fan-out traffic and gateway-side callback storage growth. [4](#0-3)
