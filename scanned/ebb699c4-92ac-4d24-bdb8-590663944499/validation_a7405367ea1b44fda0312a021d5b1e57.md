### Title
Stale LDAP session/role cache is never revalidated against upstream server, allowing revoked/demoted users to retain elevated privileges - (File: core/sessions/ldapauth/sync.go, core/sessions/ldapauth/ldap.go)

### Summary
The `ldapauth` authentication provider caches a user's session and role locally after login and relies exclusively on a background `LDAPServerStateSyncer.Work()` job to revalidate that cache against the upstream LDAP directory. This mirrors the Fei Protocol oracle bug class: a value (peg price / here, user role) is read and trusted by security-critical decision points without first forcing an update, so decisions are made on stale data.

### Finding Description
`AuthorizedUserWithSession` and `FindUserByAPIToken` in `core/sessions/ldapauth/ldap.go` authorize every API request purely by reading the locally cached `ldap_sessions` / `ldap_user_api_tokens` tables: [1](#0-0) [2](#0-1) 

No call to the upstream LDAP server or to the sync routine is made in either function — the cached `UserRole` and validity flag from the local DB are trusted directly.

The only mechanism that refreshes these cached roles/sessions against the upstream directory is `LDAPServerStateSyncer.Work()`, and it only runs in two cases:
- on a fixed background timer, if `UpstreamSyncInterval` is non-zero, or
- exactly once at node startup, if `UpstreamSyncInterval` is left at its default `'0s'`: [3](#0-2) 

The package-level doc comment claims "This sync happens for every auth endpoint hit, and via the defined sync interval," and `docs/CONFIG.md` states the check is "already performed during login/logout actions" — but this is not what the code does. `CreateSession` (login) calls `FindUser`, which fetches the user's *own* current role, but it never invokes `Work()` to resync *other* existing sessions, and `AuthorizedUserWithSession`/`FindUserByAPIToken` never call `Work()` or the upstream server at all: [4](#0-3) 

Consequently, with the documented default configuration (`UpstreamSyncInterval = '0s'`), the sync runs once at process start and then never again. Any existing session created by a user who is later demoted or removed from an LDAP admin/edit/run group upstream continues to be authorized with the old, stale role for the full duration of `SessionTimeout` / `UserAPITokenDuration`, since role/validity checks only compare against local creation timestamps, not upstream state.

### Impact Explanation
This is directly analogous to the reported oracle bug class: a security-relevant value (user role/permission) is read from a cache without forcing an update, and the stale value drives an authorization decision (`RequiresRunRole`/`RequiresAdminRole`-gated endpoints in `core/web/auth/auth.go`). A revoked/demoted user's existing session or long-lived API token keeps granting Admin/Edit/Run access on the Chainlink node's HTTP API for up to the full session/token TTL after upstream revocation, which can allow unauthorized job creation/mutation, key management, or other privileged node operations — a concrete role/authorization bypass reachable by any already-authenticated (formerly privileged, now revoked) client.

### Likelihood Explanation
This triggers under the documented default configuration (`UpstreamSyncInterval = '0s'`), which per `docs/CONFIG.md` is explicitly presented as an acceptable/common setting ("this check is already performed during login/logout actions"), even though the code does not perform per-request or per-login-of-other-users resync. Any deployment relying on that documented behavior (rather than configuring a short `UpstreamSyncInterval`) is silently exposed for the entire session/API-token lifetime.

### Recommendation
Ensure the sync/revalidation path is actually invoked, or documented accurately: either (a) call `LDAPServerStateSyncer.Work` (or an equivalent targeted per-user upstream lookup) inside `AuthorizedUserWithSession`/`FindUserByAPIToken` before trusting the cached role, matching what the docstring and `docs/CONFIG.md` claim, or (b) correct the documentation to state that revalidation only happens on the configured `UpstreamSyncInterval` timer/startup, and recommend operators set a short non-zero interval rather than relying on the `'0s'` default.

### Proof of Concept
1. Deploy a Chainlink node with the `ldapauth` driver and default config (`UpstreamSyncInterval = '0s'`, default `SessionTimeout`).
2. User `alice` is a member of the upstream LDAP Admin group; she logs in via `CreateSession`, receiving a session with `UserRoleAdmin` cached in `ldap_sessions`.
3. An operator removes `alice` from the upstream Admin group (revoking access) but the node process is not restarted and no `UpstreamSyncInterval` timer is configured.
4. `alice` continues to call Admin-gated endpoints; `AuthorizedUserWithSession` (`core/sessions/ldapauth/ldap.go:345-373`) only checks `created_at + SessionTimeout >= now()` from the local `ldap_sessions` row and returns the stale `UserRoleAdmin`, so `RequiresAdminRole` in `core/web/auth/auth.go` continues to authorize her requests until the session naturally expires.

// FindUserByAPIToken retrieves a possible stored user and role from the ldap_user_api_tokens table store
func (l *ldapAuthenticator) FindUserByAPIToken(ctx context.Context, apiToken string) (sessions.User, error) {
	if !l.config.UserApiTokenEnabled() {
		return sessions.User{}, errors.New("API token is not enabled ")
	}

	// Query the ldap user API token table for given token, user role and email are cached so
	// no further upstream LDAP query is performed, sessions and tokens are synced against the upstream server
	// via the UpstreamSyncInterval config and reaper.go sync implementation
	var foundUserToken struct {
		UserEmail string
		UserRole  sessions.UserRole
		Valid     bool
	}
	err := l.ds.GetContext(ctx, &foundUserToken,
		"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM ldap_user_api_tokens WHERE token_key = $1",
		apiToken, l.config.UserAPITokenDuration().Duration(),
	)
	if err != nil {
		return sessions.User{}, err
	}
	if !foundUserToken.Valid { // API Token expired, purge
		if _, execErr := l.ds.ExecContext(ctx, "DELETE FROM ldap_user_api_tokens WHERE token_key = $1", apiToken); execErr != nil {
			l.lggr.Errorf("error purging stale ldap API token session: %v", execErr)
		}
		return sessions.User{}, sessions.ErrUserSessionExpired
	}

	return sessions.User{
		Email: foundUserToken.UserEmail,
		Role:  foundUserToken.UserRole,
	}, nil
}

// AuthorizedUserWithSession will return the API user associated with the Session ID if it
// exists and hasn't expired, and update session's LastUsed field. The state of the upstream LDAP server
// is polled and synced at the defined interval via a SleeperTask
func (l *ldapAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (sessions.User, error) {
	if len(sessionID) == 0 {
		return sessions.User{}, errors.New("session ID cannot be empty")
	}
	// Query the ldap_sessions table for given session ID, user role and email are cached so
	// no further upstream LDAP query is performed
	var foundSession struct {
		UserEmail string
		UserRole  sessions.UserRole
		Valid     bool
	}
	if err := l.ds.GetContext(ctx, &foundSession,
		"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM ldap_sessions WHERE id = $1",
		sessionID, l.config.SessionTimeout().Duration(),
	); err != nil {
		return sessions.User{}, sessions.ErrUserSessionExpired
	}
	if !foundSession.Valid {
		// Sessions expired, purge
		if _, execErr := l.ds.ExecContext(ctx, "DELETE FROM ldap_sessions WHERE id = $1", sessionID); execErr != nil {
			l.lggr.Errorf("error purging stale ldap session: %v", execErr)
		}
		return sessions.User{}, sessions.ErrUserSessionExpired
	}
	return sessions.User{
		Email: foundSession.UserEmail,
		Role:  foundSession.UserRole,
	}, nil
}

func (l *LDAPServerStateSyncer) Start(ctx context.Context) error {
	// If enabled, start a background task that calls the Sync/Work function on an
	// interval without needing an auth event to trigger it
	// Use IsInstant to check 0 value to omit functionality.
	if !l.config.UpstreamSyncInterval().IsInstant() {
		l.lggr.Info("LDAP Config UpstreamSyncInterval is non-zero, sync functionality will be called on a timer, respecting the UpstreamSyncRateLimit value")
		go l.run()
	} else {
		// Ensure upstream server state is synced on startup manually if interval check not set
		l.Work(ctx)
	}
	return nil
}
