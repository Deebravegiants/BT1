Target: `ShopifyAPI::Auth::Oauth.validate_auth_callback` cookie/session issuance for non-embedded apps. Attacker action: attacker forces their own OAuth completion (installing on their own shop) and inspects the `SessionCookie.new(value: session.id, ...)` returned to the browser. Preconditions: `Context.embedded?` false. Call sequence: `session.id` is derived via `Session.from` using unsanitized `auth_query.shop` as shown above; the cookie value equals that raw session id. Binding: `session_id_stored_in_cookie == session_id_derived_only_from_HmacValidator-authenticated_bytes` - breaks because `shop` inside `session.id` was never passed through `ShopValidator.sanitize!`, only through HMAC-signature coverage of the raw string. Scoped impact: Critical - if the host app uses this cookie value directly as a lookup key without additional sanitization (as documented gem usage implies), an attacker can craft a shop string that collides with or spoofs another tenant's stored session key. Proof idea: minitest asserting `cookie.value == session.id` and that `session.id` contains the raw (non-sanitized) `auth_query.shop` substring verbatim.
