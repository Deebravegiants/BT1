Target: `ShopifyAPI::Auth::ClientCredentials.client_credentials` vs `Oauth.begin_auth`/`validate_auth_callback` - a comparative binding question. Attacker action: none directly executable server-side, but the audit compares code paths: attacker feeds `shop` to the app's OAuth install endpoint (routed to `begin_auth`) versus the app's client-credentials endpoint (routed to `client_credentials`). Preconditions: both are reachable per README-documented usage. Call sequence: `client_credentials` calls `validated_shop = Utils::ShopValidator.sanitize!(shop)` before building `Session.new` and the request host; `begin_auth`/`validate_auth_callback` never do. Binding: `sanitize!_applied_on_OAuth_path == sanitize!_applied_on_ClientCredentials_path` is false - an inconsistency proving `Oauth` module bypasses the same guard `ClientCredentials` enforces for identical downstream sinks (`HttpClient.@base_uri`, `Session.shop`). Scoped impact: Critical - confirms the asymmetry that lets OAuth-path attackers reach the unsanitized-host sink that the client-credentials path closes off, enabling `client_secret`/code exfiltration only via the OAuth flow. Proof idea: minitest with Mocha `.expects(:sanitize!)` set once for `ClientCredentials.client_credentials(shop: 'x')` (asserted called) and once for `Oauth.begin_auth(shop: 'x', redirect_path: 'y')` (asserted never called), demonstrating the divergence.
