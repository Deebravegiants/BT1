Target: authHandleToIntentsUserId (packages/internal-utils/src/utils/authIdentity.ts) case 'webauthn' with curveType 'p256' vs case 'evm'. Attacker input: an EVM address that happens to equal the last-20-bytes keccak256('p256'||pubkey) output for some P-256 public key the attacker can register as a WebAuthn credential (birthday-style construction across many registered EVM accounts, or more directly: attacker registers a WebAuthn P-256 credential whose derived '0x'+hex(last20 bytes) collides with an existing EVM-based intents account they do not control the EVM key for). Preconditions: two independent authentication methods ('evm' and 'webauthn' with p256) both funnel into the same 20-byte-hex-with-0x-prefix intents user id namespace. Call sequence: authHandleToIntentsUserId(evmAddr,'evm') -> evmAddr.toLowerCase(); authHandleToIntentsUserId(p256Credential,'webauthn') -> webAuthnIdentifierToIntentsUserId -> keccak_256('p256'+pubkey).slice(-20) formatted as '0x'+hex — if these two 20-byte values are equal, both authentication methods resolve to the identical intents user id despite being unrelated cryptographic primitives (secp256k1 ECDSA vs P-256/WebAuthn), and the intents.near contract must independently support ecrecover for evm and the WebAuthn verifier for webauthn, both being able to authorize actions on the one shared user id. Equality that breaks: signer_id (the intents user id namespace) is expected to uniquely correspond to exactly one authorizing key per credential type; the derivation scheme places EVM and WebAuthn-P256 identities in the same 20-byte address space with no domain separation beyond the keccak prefix (which is itself part of the same address space as raw EVM addresses), so a colliding WebAuthn P-256 key or intentionally chosen credential could co-authorize an existing EVM-identified account's funds. Scoped impact: High — while a literal keccak preimage collision is not attacker-computable in real time, the design flaw (two distinct credential types sharing one flat namespace with only a content-derived, not method-tagged, identifier) is the SDK-level weakness that removes any structural separation between 'evm' and 'webauthn' identities, an in-scope design defect regardless of practical collision cost. Proof idea: vitest test asserting authHandleToIntentsUserId(evmAddress,'evm') and authHandleToIntentsUserId(chosenP256Credential,'webauthn') can be made to produce the same output string by choosing evmAddress = keccak_256('p256'+pubkey).slice(-20) directly (a deterministic construction, not a preimage attack), proving the two authentication method namespaces are not disjoint.
