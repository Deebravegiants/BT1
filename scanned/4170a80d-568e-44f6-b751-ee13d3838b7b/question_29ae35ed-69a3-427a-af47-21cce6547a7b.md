authHandleToIntentsUserId (packages/internal-utils/src/utils/authIdentity.ts): attacker generates a raw 32-byte ed25519 key pair and registers it twice with the SDK: once as authMethod='solana' (identifier = base58.encode(rawPubKey)) and once as authMethod='webauthn' with an ed25519 credential whose parsePublicKey() output equals the same rawPubKey bytes. Preconditions: no cross-check between auth methods; webAuthnIdentifierToIntentsUserId returns hex.encode(publicKey) with no method-specific prefix, identical to the solana branch's hex.encode(base58.decode(identifier)). Call sequence: authHandleToIntentsUserId({identifier: base58Addr, method:'solana'}) then authHandleToIntentsUserId({identifier: webauthnCredB64, method:'webauthn'}) on the same raw bytes. Equality broken: two distinct credentials (one wallet-controlled Solana key, one WebAuthn passkey) must map to distinct intents user ids, but both resolve to the identical IntentsUserId string. Impact: Critical - intent manipulation/fund collision, an integrator crediting balances or routing withdrawals by intents-user-id will conflate a Solana-controlled account and a WebAuthn-controlled account into one signer_id, letting either keyholder authorize intents against funds the other believes only they can move. Proof idea: vitest asserting authHandleToIntentsUserId({identifier: solanaAddr, method:'solana'}) === authHandleToIntentsUserId({identifier: webauthnEd25519Cred, method:'webauthn'}) for the same raw public key bytes, i.e. SIGNED == BUILT identity check fails.
