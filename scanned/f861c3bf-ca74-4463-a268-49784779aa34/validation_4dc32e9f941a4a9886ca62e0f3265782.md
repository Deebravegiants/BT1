### Title
User enumeration via differing authentication error responses on `POST /sessions` - (File: `core/web/sessions_controller.go`)

### Summary
The unauthenticated `/sessions` login endpoint returns raw, unfiltered backend error strings to the client whenever `CreateSession` fails. Because the underlying `AuthenticationProvider` implementations return different error text depending on whether the submitted email exists or not (e.g. a raw SQL "no rows" error for unknown emails vs. `"Invalid password"`/`"invalid password"` for existing accounts with a wrong password), an unauthenticated attacker can distinguish valid from invalid accounts by inspecting the HTTP response body — the same bug class as the Kirby CMS advisory (CWE-204 response discrepancy leading to user enumeration).

### Finding Description
`SessionsController.Create` forwards any error from `CreateSession` straight to the client via `jsonAPIError`, which serializes `err.Error()` into the JSON response body: [1](#0-0) 

`jsonAPIError` puts the raw Go error string in the response body unless it is already a `*models.JSONAPIErrors`: [2](#0-1) 

For the local auth provider, `CreateSession` first calls `FindUser`, and if the user is not found the raw `sql.ErrNoRows`-derived error is returned directly to the caller (no generic wrapping), while an existing user with a wrong password produces a distinct `"Invalid password"` message: [3](#0-2)  combined with the underlying lookup at [4](#0-3) 

The same pattern exists in the OIDC and LDAP providers' local-admin fallback login path, which also returns the raw lookup error for unknown users versus a distinct `"invalid password"`/`"invalid email"` error for known users: [5](#0-4) [6](#0-5) 

Because these three distinct error strings ("sql: no rows in result set" / a not-found style error vs. `"Invalid email"` vs. `"Invalid password"`) are all surfaced verbatim in the `POST /sessions` response body under the same `401` status, an attacker submitting a login attempt can tell whether the supplied email corresponds to a registered account.

### Impact Explanation
This is a low/medium severity information-disclosure issue matching CWE-204. It does not itself grant authentication bypass, but it lets any unauthenticated network client enumerate valid operator/admin email addresses on an internet-facing Chainlink node UI/API, which can be leveraged for targeted credential-stuffing or phishing/social-engineering attacks against confirmed accounts — the same impact rationale as the referenced Kirby CMS advisory.

### Likelihood Explanation
Likelihood is high for exploitation once discovered: the `/sessions` endpoint requires no prior authentication, requests are cheap to send repeatedly, and the discriminating signal is a simple string difference in the JSON error body returned synchronously with each request — no timing side channel or special server misconfiguration is required (unlike the original Kirby report, which required a secondary error condition).

### Recommendation
Return a single generic, constant error message and status code (e.g. `401 Unauthorized: "invalid credentials"`) from `SessionsController.Create` for all authentication failures (unknown email, wrong password, wrong email casing, provider-specific "not found" errors), and log the detailed underlying error server-side only. Ensure the local, LDAP, and OIDC `CreateSession`/`localLoginFallback` implementations normalize all failure paths to the same sentinel error type before it reaches the HTTP handler, so `jsonAPIError` cannot leak provider-internal error text that varies by account existence.

### Proof of Concept
1. `POST /sessions` with `{"email":"unknown@example.com","password":"anything"}` → response body contains a distinct "no rows"/not-found style error.
2. `POST /sessions` with `{"email":"<real-admin-email>","password":"wrongpassword"}` → response body contains `"Invalid password"`.
3. Comparing the two response bodies (both `401`) reveals which email address is a registered account, without needing valid credentials.

```go
func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
```

```go
func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}
```

```go
func (l *ldapAuthenticator) localLoginFallback(ctx context.Context, sr sessions.SessionRequest) (sessions.User, error) {
	var user sessions.User
	sql := "SELECT * FROM users WHERE lower(email) = lower($1)"

		return user, err

		l.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})

		l.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
```
