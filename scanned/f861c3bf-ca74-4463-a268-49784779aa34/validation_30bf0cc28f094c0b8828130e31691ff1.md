### Title
External Initiator authentication does not check `ExternalInitiatorsEnabled` config flag - ([File: core/web/auth/auth.go])

### Summary
This is a direct analog of the JOJO `JUSDBank._borrow` bug: a feature-enable flag is checked on the "create" path but not on the corresponding "use" path. In Chainlink, `ExternalInitiatorsEnabled` is checked when a new External Initiator (EI) is created, but not when an EI authenticates a webhook run request.

### Finding Description
`ExternalInitiatorsController.Create` explicitly gates creation of new external initiators behind the config flag: [1](#0-0) 

However, the middleware that authenticates an *existing* external initiator against incoming run-trigger requests, `AuthenticateExternalInitiator`, performs no such check — it only validates the access key/secret pair against the DB record and, on success, grants the caller the `run` role: [2](#0-1) 

Because the enabled check exists solely in `Create`, any external initiator credentials that already exist in the database (created while the feature was enabled, or present from before an operator disabled the feature via config) continue to authenticate successfully and trigger webhook job runs even after `JobPipeline.ExternalInitiatorsEnabled` is turned off. `grep` confirms the flag `ExternalInitiatorsEnabled` is referenced only in `Create` and config/docs code, not in the authentication path: [3](#0-2) 

### Impact Explanation
An operator who disables the External Initiator feature (e.g., during an incident, or to lock down webhook-triggered runs) expects that no External Initiator can trigger job runs afterward. Because the disable flag is not enforced at authentication time, previously-issued EI credentials remain fully functional, allowing an external, unprivileged holder of leaked/old EI credentials to keep triggering job runs (potentially moving funds or executing pipeline tasks) despite the feature being administratively disabled. This mirrors the "borrow proceeds despite isBorrowAllowed=false" impact in the original report — a security control intended to pause a capability is silently bypassed.

### Likelihood Explanation
Any party holding valid EI `AccessKey`/`Secret` credentials (which are treated as external, unprivileged, secret-bearing tokens) can send an authenticated webhook request at any time; there is no dependency on privileged/operator actions or malicious node/peer behavior. The bypass is triggered purely by the config toggle not being consulted in the authentication middleware, which is deterministic and always reachable once such credentials exist.

### Recommendation
Add the same `ExternalInitiatorsEnabled` check inside `AuthenticateExternalInitiator` (or in the `Authenticate` chain right before/after invoking it) so that, when the feature is disabled, authentication fails with `auth.ErrorAuthFailed` regardless of whether valid EI credentials are presented.

### Proof of Concept
1. Enable `JobPipeline.ExternalInitiatorsEnabled = true`.
2. Create an external initiator via `POST /v2/external_initiators` (succeeds, per `Create` check) — record credentials (`AccessKey`, `Secret`).
3. Disable the feature: set `JobPipeline.ExternalInitiatorsEnabled = false` and restart/reconfigure the node.
4. Send a webhook run-trigger request using the previously obtained `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` headers, matching the flow exercised in [4](#0-3) .
5. Observe that `AuthenticateExternalInitiator` in `core/web/auth/auth.go` still succeeds and grants the `run` role, since it never consults `ExternalInitiatorsEnabled` — job run is triggered despite the feature being disabled.

// AuthenticateExternalInitiator authenticates an external initiator request.

// Implements authMethod
func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}
