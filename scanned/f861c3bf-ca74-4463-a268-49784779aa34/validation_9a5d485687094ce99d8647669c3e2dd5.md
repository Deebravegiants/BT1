Analog identified: `BridgeResource.OutgoingToken` (and the GraphQL `BridgeResolver.OutgoingToken()`) always includes the bridge's outgoing authentication token in read responses, unlike `IncomingToken`, which is explicitly commented as "only provided when creating a Bridge."

### Title
Bridge Show/Index/GraphQL Responses Always Disclose the Bridge Outgoing Token - (File: core/web/presenters/bridges.go)

### Summary
The `BridgeTypesController.Show` and `Index` REST endpoints, and the GraphQL `BridgeResolver`, return `OutgoingToken` unconditionally on every read of a bridge, not just on creation. This mirrors the Rocket.Chat `visitors.info` bug class: a secret/bearer-style credential is embedded in an info/read response where it serves no functional purpose and enables impersonation of the resource by anyone who can view it.

### Finding Description
`BridgeResource` marks `IncomingToken` with `omitempty` and a comment stating it is "only provided when creating a Bridge" [1](#0-0) , but `OutgoingToken` has no such gating and is populated straight from the DB-backed `BridgeType.OutgoingToken` field in `NewBridgeResource` for every call site [2](#0-1) .

This resource is used by:
- `Show` (`GET /v2/bridge_types/:BridgeName`), which fetches the bridge and serializes it via `presenters.NewBridgeResource(bt)` [3](#0-2) 
- `Index` (`GET /v2/bridge_types`), which serializes every bridge in a paginated list the same way [4](#0-3) 
- `Update` and `Destroy`, which also return the full resource including `OutgoingToken` [5](#0-4) 
- The GraphQL `BridgeResolver.OutgoingToken()` accessor, which exposes the same field to any bridge query [6](#0-5) 

The `OutgoingToken` is the credential the Chainlink node uses to authenticate itself to the external bridge/adapter when making outbound requests (`bridges.BridgeTypeAuthentication`/`BridgeType` struct) [7](#0-6) . There is no functional need for any client reading bridge metadata (list, show, update, delete) to receive this token — it is only needed internally when the node calls out to the adapter.

### Impact Explanation
Any authenticated node UI/API user with read access to bridges (the `Index`/`Show` endpoints, or GraphQL `bridge`/`bridges` queries) can retrieve the outgoing token for every configured bridge. With this token, an attacker could replay it against the external adapter to impersonate the Chainlink node's outbound authentication to that adapter — the same "credential disclosure enabling impersonation via a routine info-read response" pattern as the CVE, except here the exposure is to any node operator/read-scope role rather than an anonymous internet caller. Unlike `IncomingToken` (which the codebase already treats as sensitive and creation-only), `OutgoingToken` is treated as ordinary, always-visible metadata, which is the root-cause asymmetry.

### Likelihood Explanation
Reaching this requires only a standard authenticated `GET /v2/bridge_types` or `GET /v2/bridge_types/:name` call, or an equivalent GraphQL `bridges`/`bridge` query — no privilege escalation or additional exploitation is needed. It is limited to users who already have bridge read access, so severity is capped by the pre-existing role model, but the disclosure itself is trivial and always present in response bodies (and thus also flows into logs/caches that persist API responses).

### Recommendation
Apply the same `omitempty`/creation-only gating already used for `IncomingToken` to `OutgoingToken` in `BridgeResource` (and the GraphQL resolver): return it only from the `Create` response (and possibly a dedicated regenerate endpoint), and redact/omit it from `Show`, `Index`, `Update`, and `Destroy` responses and from the GraphQL `BridgeResolver.OutgoingToken()` field for general queries.

### Proof of Concept
1. As an authenticated node UI user with bridge read permissions, call `GET /v2/bridge_types/<bridgeName>` (see `TestBridgeController_Show`, which already asserts other fields present) [8](#0-7) .
2. Observe the response JSON contains `data.attributes.outgoingToken` populated with the live token value, sourced from `NewBridgeResource` [9](#0-8) .
3. Repeat via `GET /v2/bridge_types` (`Index`) to enumerate outgoing tokens for all configured bridges, or via the GraphQL `bridges { outgoingToken }` query.
4. Use the retrieved `OutgoingToken` to authenticate as the node when calling the external bridge/adapter, impersonating the node's outbound bridge traffic.

**Note on verification limits**: I was unable to confirm within the available index whether the `v2/bridge_types` routes require any particular RBAC role (e.g., admin vs. read-only) versus the general authenticated-session middleware, since `router.go`'s route-registration section for bridges was not fully retrievable through search. This affects only the precise privilege level required to exploit the disclosure, not the existence of the disclosure itself.

		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

}

// Destroy removes a specific Bridge.
func (btc *BridgeTypesController) Destroy(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	orm := btc.App.BridgeORM()
	bt, err := orm.FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, fmt.Errorf("error searching for bridge: %w", err))
		return
	}
	jobsUsingBridge, err := btc.App.JobORM().FindJobIDsWithBridge(ctx, name)
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, fmt.Errorf("error searching for associated v2 jobs: %w", err))
		return
	}
	if len(jobsUsingBridge) > 0 {
		jsonAPIError(c, http.StatusConflict, fmt.Errorf("can't remove the bridge because jobs %v are associated with it", jobsUsingBridge))
		return
	}
	if err = orm.DeleteBridgeType(ctx, &bt); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, fmt.Errorf("failed to delete bridge: %w", err))
		return
	}

	btc.App.GetAuditLogger().Audit(audit.BridgeDeleted, map[string]any{"name": name})

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
