## Analog Vulnerability Found

### Title
Unauthenticated `MessageID` collision allows cross-user response hijacking in the WebAPI capabilities gateway handler - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The ChainPort report highlights that signature schemes need explicit uniqueness guarantees (nonce/signature dedup) to prevent one signed operation from being confused with, or substituted for, another. The chainlink gateway's `capabilities` handler has an analogous problem: it correlates in-flight HTTP requests to their eventual DON-node responses using an unauthenticated, user-supplied `MessageID` as a map key, with no check that the ID is not already in use by another pending request.

### Finding Description
When the gateway receives a user's legacy request, `HandleLegacyUserMessage` stores the caller's HTTP callback in a shared map keyed purely by the attacker-controlled `msg.Body.MessageID`, without verifying whether an entry for that ID already exists: [1](#0-0) 

`MessageID` is a caller-supplied field in `MessageBody` — it is not derived from any session/user identity and its only validation is length/null-byte checks in `Message.Validate()`: [2](#0-1) [3](#0-2) 

Because Go map assignment (`h.savedCallbacks[msg.Body.MessageID] = &savedCallback{...}`) silently overwrites any pre-existing entry, if a second unrelated request arrives with the same `MessageID` while the first is still pending, the second caller's `Callback` (its HTTP handler/channel) replaces the first one in `h.savedCallbacks`. When the DON node eventually responds — echoing the original `MessageID` in the response body, as `handleWebAPITriggerMessage`/`HandleNodeMessage` uses to look up the callback — the response is delivered to whichever `Callback` currently occupies that map slot, not necessarily to the request that originated it: [4](#0-3) 

`pruneCallbacks` only removes entries by age/count; it does nothing to prevent a live overwrite of an in-flight entry: [5](#0-4) 

This is directly the class of bug the ChainPort report warns about: the system relies on an identifier (here `MessageID`, there "nonce"/signature) to disambiguate concurrent operations, but never enforces that the identifier is actually unique among currently-outstanding operations before using it as the sole correlation key.

### Impact Explanation
If two unprivileged callers (or an attacker racing a victim) submit `web_api_trigger` requests with the same `MessageID` while both are in flight, the gateway can deliver one user's DON response payload to the other user's HTTP connection. This is a cross-user response confusion issue: it can leak data intended for another caller, or let an attacker cause a victim's request to receive attacker-influenced output, undermining the confidentiality/integrity boundary between independent unprivileged API callers of the gateway's user-facing endpoint.

### Likelihood Explanation
Exploitability depends on being able to win a race and cause a `MessageID` collision. Because `MessageID` is entirely attacker-chosen and there is no per-caller namespacing (e.g., prefixing with session/user identity) or uniqueness check against `h.savedCallbacks`, an attacker only needs to predict or observe another caller's `MessageID` (or simply flood with common/short IDs) during the window that request is outstanding (bounded by `CallbackMaxAgeSec`, default 120s) to trigger the collision. This is feasible without any special privileges — it only requires calling the same internet-facing gateway HTTP endpoint.

### Recommendation
Enforce uniqueness of `MessageID` per outstanding request before inserting into `savedCallbacks` (reject/collide-detect instead of silently overwriting), and consider namespacing the map key with a gateway-generated, non-guessable correlation ID rather than trusting the caller-supplied `MessageID` alone. Document explicitly (per the original ChainPort recommendation) what uniqueness property `MessageID` is expected to provide and how it is enforced.

### Proof of Concept
1. Caller A sends a `web_api_trigger` legacy request with `MessageID = "X"`; gateway stores A's callback at `h.savedCallbacks["X"]` [1](#0-0) .
2. Before the DON responds, Caller B (attacker) sends its own legacy request also with `MessageID = "X"`; this silently overwrites `h.savedCallbacks["X"]` with B's callback.
3. The DON node processes A's original forwarded request and replies referencing `MessageID = "X"`.
4. `HandleNodeMessage` looks up `h.savedCallbacks["X"]`, now pointing to B's callback, and delivers A's response payload to B [4](#0-3) .

	}

	return err
}

func (h *handler) pruneCallbacks() {
	h.mu.Lock()
	defer h.mu.Unlock()

	// First, remove expired callbacks.
	maxAge := time.Duration(h.config.CallbackMaxAgeSec) * time.Second
	now := time.Now()
	var expired int
	for id, cb := range h.savedCallbacks {
		if now.Sub(cb.createdAt) > maxAge {
			delete(h.savedCallbacks, id)
			expired++
		}
	}

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}

	if expired > 0 || evicted > 0 {
		h.lggr.Infow("Pruned savedCallbacks", "expired", expired, "evicted", evicted, "remaining", len(h.savedCallbacks))
	}
}
