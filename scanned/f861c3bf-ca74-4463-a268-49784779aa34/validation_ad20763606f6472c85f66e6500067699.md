### Title
User enumeration via distinguishable login error messages - (File: core/sessions/localauth/orm.go, core/web/sessions_controller.go)

### Summary
The unauthenticated `/sessions` login endpoint (`SessionsController.Create`) surfaces the underlying authentication error returned by `AuthenticationProvider().CreateSession` directly to the HTTP client. The local authentication provider's `CreateSession` returns different, distinguishable error strings depending on whether the submitted email corresponds to an existing user or not, mirroring the CWE-209 "Generation of Error Message Containing Sensitive Information" class described in the reference advisory (user enumeration via discrepant authentication error messages).

### Finding Description
`SessionsController.Create` accepts unauthenticated POST requests to `/sessions` and forwards the raw error from the authentication provider straight into the JSON error response: [1](#0-0) 

The local ORM's `CreateSession` first looks up the user by email via `FindUser`, and returns immediately with whatever error that lookup produced if the user is not found: [2](#0-1) [3](#0-2) 

`findUser` performs a raw SQL lookup and returns the underlying `database/sql` error (e.g. `sql.ErrNoRows`, surfaced as `sql: no rows in result set`) unmodified when the email does not exist. In contrast, when the email *does* exist but the password is wrong, a distinctly different, explicit error is returned: [4](#0-3) 

This produces two observably different error payloads for "email does not exist" versus "email exists, password wrong" — the same bug class as the livehelperchat advisory (discrepancy between error responses for existing vs. non-existing users), analogous to the CVE-2022-0083 details. The router confirms this endpoint requires no authentication and is only protected by a rate limiter, not by response redaction: [5](#0-4) 

Note: I was not able to fully confirm from the index whether `jsonAPIError` serializes the raw `err.Error()` text into the HTTP response body byte-for-byte, or whether it maps to a generic message — the `jsonAPIError` implementations in `core/web/auth/helpers.go` and `core/web/helpers.go` were not retrievable in full within this session. This should be verified by reading those two files directly, since it determines whether the discrepancy is actually exposed on the wire versus only in server logs/internal error values.

### Impact Explanation
If the raw error text is reflected to the client, an unauthenticated attacker can enumerate valid Chainlink node operator/admin email addresses by observing which `/sessions` login attempts yield a "no rows" style error versus an "Invalid password" error. This does not by itself grant access, but materially aids credential-stuffing and targeted phishing/brute-force campaigns against a specific node operator's admin account, which is a higher-value target than typical web apps given Chainlink node control over jobs and potentially funds-adjacent operations.

### Likelihood Explanation
The `/sessions` endpoint is explicitly unauthenticated and internet-facing by design, protected only by a rate limiter: [6](#0-5) 
An attacker needs no prior access — only network reachability to the node's API — and can send a bounded number of requests per rate-limit window to differentiate responses. Likelihood is Medium given the rate limiting friction but a straightforward reachable path.

### Recommendation
Normalize the error returned by `CreateSession`/`findUser` so that "user not found" and "invalid password" produce an identical opaque error (e.g., always `"invalid email or password"`) before it reaches `jsonAPIError`, and ensure `jsonAPIError` does not leak internal/db error text for authentication failures on `/sessions`. Apply constant-time behavior consistently (already partially done via `constantTimeEmailCompare`) to also cover the "user not found" branch so lookup timing does not leak existence either.

### Proof of Concept
1. `POST /sessions` with `{"email":"nonexistent@test.com","password":"x"}` → local ORM's `findUser` returns `sql.ErrNoRows`-derived error, propagated via `CreateSession` → `jsonAPIError(c, 401, err)`.
2. `POST /sessions` with `{"email":"<valid-existing-email>","password":"wrongpassword"}` → `CreateSession` returns `pkgerrors.New("Invalid password")` explicitly: [7](#0-6) 
3. Compare the two 401 response bodies; a stable textual difference between them (subject to confirming `jsonAPIError`'s exact serialization behavior) allows distinguishing valid vs. invalid emails.

func sessionRoutes(app chainlink.Application, r *gin.RouterGroup) {
	config := app.GetConfig()
	rl := config.WebServer().RateLimit()
	unauth := r.Group("/", rateLimiter(
		rl.UnauthenticatedPeriod(),
		rl.Unauthenticated(),
	))
	sc := NewSessionsController(app)
	unauth.POST("/sessions", sc.Create)
	auth := r.Group("/", auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession))
	auth.DELETE("/sessions", sc.Destroy)
