## Analog Found

### Title
Debug-Level Request Logging Leaks Secrets Due to Incomplete Redaction Blacklist - ([File: core/web/router.go])

### Summary
The gin request-logging middleware installed on every authenticated API route logs the full request body (and query string) at `Debug` level. The sanitization routine only redacts top-level JSON fields whose key *contains* the substring `"password"`; it has no awareness of other sensitive field names (tokens, secrets, access keys) and does not recurse into nested objects. This is the same bug class as the external report (sensitive values written to `Debugw`/`console.log`-style logs that end up in CloudWatch/Datadog/SIEM), but reachable here through the chainlink node's own HTTP API rather than a mock auth middleware.

### Finding Description
`NewRouter` wires `loggerFunc(app.GetLogger())` into every request on the authenticated `api` group, including all of `v2Routes` (bridge types, external initiators, user/API-token endpoints, key management, etc.): [1](#0-0) 

The middleware buffers and logs the **entire request body** at Debug level on every request/response cycle: [2](#0-1) 

Sanitization is delegated to `readSanitizedJSON`/`redact`, whose blacklist is hardcoded to password-only substrings: [3](#0-2) 

Because the blacklist only matches keys containing `"password"`, any other sensitive field name in an authenticated request body — for example a bridge's `IncomingToken` (the shared secret external adapters use to authenticate resume-run callbacks) on `POST /v2/bridge_types`, or an OIDC `clientSecret` field, or key-import payload contents — passes through to the Debug log verbatim. The routine also only walks top-level map keys (`for k, v := range dst`), so any sensitive value nested inside a sub-object or array is never inspected at all, regardless of its key name.

This is functionally identical to the report's root cause: a debug-log statement fires on every request/auth check and includes fields that should be treated as secrets, with no dedicated secret-redaction logic beyond an ad-hoc keyword list.

### Impact Explanation
Any authenticated API call carrying a secret-like field in its JSON body (most notably bridge `IncomingToken`, which authenticates job-run resumption callbacks from external adapters) is written unredacted into the node's log stream at Debug level. Per the report's own threat model, these logs commonly flow to CloudWatch/Datadog, are exported to third-party SIEMs, or are read by staff with log-only access. Exposure of a bridge's `IncomingToken` lets an attacker impersonate the external adapter and forge `PATCH /v2/resume/:runID` callbacks, letting them control job-run resumption/results — an unauthorized-run-manipulation impact directly in scope of the validation criteria.

### Likelihood Explanation
Requires only that: (1) the node runs with `Log.Level = 'debug'` (a supported, non-exotic operator configuration, and the default in several of the repo's own test fixtures, e.g. `Log.Level = 'debug'` appears throughout `testdata/scripts/node/validate/*.txtar`), and (2) an authenticated user (any role capable of hitting `POST /v2/bridge_types`, which only requires the `Edit` role per [4](#0-3) ) creates or updates a bridge. No privileged/operator-only access to internals is needed to trigger the leak — only a normal authenticated API call with Debug logging enabled, matching the report's "every authentication/config check" pattern.

### Recommendation
- Replace the substring/keyword-based blacklist in `isBlacklisted` with an explicit allow-list of loggable field names, or a recursive redactor that walks nested objects/arrays.
- Add known secret field names (`incomingtoken`, `outgoingtoken`, `secret`, `clientsecret`, `accesskey`, `apikey`, `token`) to the redaction set.
- Consider removing full request-body logging from the generic access-log middleware entirely and rely on the existing `audit.AuditLogger` for security-relevant events, which already logs structured, curated fields rather than raw bodies.

### Proof of Concept
1. Start a chainlink node with `Log.Level = 'debug'`.
2. As an authenticated user with the `Edit` role, call:
```
POST /v2/bridge_types
{
  "name": "my-bridge",
  "url": "https://adapter.example.com",
  "incomingToken": "super-secret-callback-token"
}
```
3. Observe the node's Debug log line emitted by `loggerFunc` for this request — the `body` field contains `"incomingToken":"super-secret-callback-token"` in plaintext, because `isBlacklisted("incomingToken")` returns `false`.
4. Anyone with read access to the node's aggregated logs can now forge `PATCH /v2/resume/:runID` requests using this token.

**Note on confidence**: I verified that `password`/`oldPassword`/`newPassword` fields *are* correctly redacted (matches the blacklist substring), but I could not directly confirm the exact JSON field name/casing chainlink uses for bridge `IncomingToken` in the wire struct within the indexed content — the search only surfaced the router's redaction logic, not the `BridgeTypeRequest` struct definition itself. If you want certainty on the exact field name and full exploit chain, a Devin session with full repo access (to inspect `core/bridges` request/response structs) would confirm this precisely.

func readSanitizedJSON(buf *bytes.Buffer) (string, error) {
	var dst map[string]any
	err := json.Unmarshal(buf.Bytes(), &dst)
	if err != nil {
		return "", err
	}

	cleaned := map[string]any{}
	for k, v := range dst {
		if isBlacklisted(k) {
			cleaned[k] = "*REDACTED*"
			continue
		}
		cleaned[k] = v
	}

	b, err := json.Marshal(cleaned)
	if err != nil {
		return "", err
	}
	return string(b), err
}

func redact(values url.Values) string {
	cleaned := url.Values{}
	for k, v := range values {
		if isBlacklisted(k) {
			cleaned[k] = []string{"REDACTED"}
			continue
		}
		cleaned[k] = v
	}
	return cleaned.Encode()
}

// NOTE: keys must be in lowercase for case insensitive match
var blacklist = map[string]struct{}{
	"password":             {},
	"newpassword":          {},
	"oldpassword":          {},
	"current_password":     {},
	"new_account_password": {},
}

func isBlacklisted(k string) bool {
	lk := strings.ToLower(k)
	if _, ok := blacklist[lk]; ok || strings.Contains(lk, "password") {
		return true
	}
	return false
}
