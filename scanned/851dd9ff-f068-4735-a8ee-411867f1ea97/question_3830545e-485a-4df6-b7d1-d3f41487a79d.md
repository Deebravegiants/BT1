Target: prepareSwapSignedData 'STELLAR_SEP53' case (packages/internal-utils/src/utils/prepareBroadcastRequest.ts). Attacker input: userInfo.userAddress is a Stellar address string different from the key that signed signatureData, while userInfo.userChainType === 'stellar' (only chain-type is asserted, not address-to-key correspondence). Preconditions: public_key is derived via stellarAddressToBytes(userInfo.userAddress) then base58-encoded as ed25519 public key, entirely independent of signature.signatureData bytes. Call sequence: caller supplies mismatched userAddress/signature pair -> prepareSwapSignedData builds { standard: 'sep53', public_key: ed25519:base58(stellarAddressToBytes(userInfo.userAddress)), signature: transformED25519Signature(signature.signatureData) } -> resulting MultiPayload's public_key field names a principal the attacker does not control the private key for. Equality that breaks: public_key in the signed multipayload == the intents-user-id derivable from the private key that produced the ed25519 signature. Impact: Critical - the SDK layer builds and could forward a payload whose declared signer identity is decoupled from the actual signing key, and any downstream logic (e.g. UI confirmation, off-chain accounting, refund routing) trusting userInfo.userAddress as 'who signed this' is misled even before contract-level signature verification catches the mismatch.
