Target: prepareSwapSignedData 'SOLANA' case (packages/internal-utils/src/utils/prepareBroadcastRequest.ts). Attacker input: userInfo.userAddress set to a Solana address that is NOT the public key that actually produced signature.signatureData.signature (e.g. attacker's own signature but victim's Solana address as userAddress). Preconditions: userInfo.userChainType === 'solana' assertion only checks chain type equality, not that userAddress matches the key that generated the signature; public_key field is built as `ed25519:${userInfo.userAddress}` directly from caller-supplied data. Call sequence: caller invokes prepareSwapSignedData(signature, {userAddress: victimAddress, userChainType: 'solana'}) with a signature actually produced by the attacker's own Solana key -> the returned Params.signed_data has public_key bound to victimAddress while signature was made by attacker's key. Equality that breaks: public_key embedded in signed_data == the public key that actually produced signature (the signer identity claim diverges from the cryptographic signer). Impact: Critical - since intents.near will verify signature against declared public_key, this specific combination fails on-chain verification UNLESS the same raw bytes happen to also verify (unlikely) -- but the SDK-level bug is that it never cross-checks userInfo.userAddress against a recovered/derived key before constructing signed_data, letting a caller construct a MultiPayload whose public_key field claims a different principal than the actual signer, which if forwarded downstream (e.g. before submission validation) could be logged/relied upon as proof of authorization for the wrong account. Proof idea: vitest test calling prepareSwapSignedData with a SOLANA WalletSignatureResult where signatureData was produced independently of userInfo.userAddress, asserting the function does not validate consistency and returns a public_key untethered to the signature's real signer, then asserting signed payload's declared identity != recoverable signer identity.
