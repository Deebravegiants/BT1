### Title
DMP inbound messages bypass the "advancement rule" size check, enabling collator censorship of downward XCM/DMP messages - (File: cumulus/pallets/parachain-system/src/lib.rs / cumulus/pallets/parachain-system/src/parachain_inherent.rs)

### Summary
`check_enough_messages_included_advanced` — the check meant to guarantee that a collator includes as many full messages as fit in `max_full_messages_size` before hashing the rest — is only invoked for HRMP messages inside `enqueue_inbound_horizontal_messages`, not for DMP messages inside `enqueue_inbound_downward_messages`. DMP messages are only subject to `check_enough_messages_included_basic`, which merely requires "at least 1 full message" and does not compare included sizes against the available size budget at all. A malicious collator can therefore hash almost all DMP messages (leaving just one small full message) even when the budget clearly allows including many more, without triggering any panic.

while `enqueue_inbound_horizontal_messages` additionally invokes the stricter, size-aware check: [2](#0-1) 

The two checks in `cumulus/pallets/parachain-system/src/parachain_inherent.rs` differ substantially:

- `check_enough_messages_included_basic` (lines 172-184) only asserts `full_messages.len() >= 1` whenever `hashed_messages` is non-empty — it says nothing about whether the size budget could have accommodated more full messages.
- `check_enough_messages_included_advanced` (lines 186-218) asserts that `full_messages_size + first_hashed_msg_max_size > max_full_messages_size`, i.e. that hashing was actually necessary given the size budget. [3](#0-2) 

Because `enqueue_inbound_downward_messages` never calls the advanced variant, a collator building the `AbridgedInboundDownwardMessages` via `into_abridged` (`InboundMessagesCollection::into_abridged`, lines 117-142) is free to choose `size_limit` artificially small for DMQ or simply hash messages that would clearly fit inside `messages_collection_size_limit()` (PoV/6 budget, `lib.rs:1269-1277`), as long as it keeps one small full DMP message to satisfy the basic check. The runtime's only cross-check is the MQC head hash equality assertion in `enqueue_inbound_downward_messages` (line 1362), which validates that the *hashed* representation matches the relay-chain-provided MQC head — it does not validate that hashing a given message was necessary. Thus a collator can hash all subsequent DMP messages (of arbitrary legitimate origin, e.g. relay-chain-originated XCM reserve-transfer/teleport instructions) indefinitely while still producing a validly-verifiable inherent.

This matches the PR history: `prdoc/stable2603/pr_9086.prdoc` documents "Make HRMP advancement rule more restrictive," confirming the advanced rule was deliberately hardened for HRMP but the corresponding hardening was not applied to the DMP path.

### Impact Explanation
A collator that controls block production for a parachain can selectively censor/delay downward (relay-chain-to-parachain) messages — including XCM instructions carrying user funds (reserve transfers, teleports, DMP-originated calls) — by always hashing them instead of including them in full, provided it keeps at least one unrelated full DMP message present. Because `check_enough_messages_included_basic` is satisfied, no panic occurs and the block is accepted. This delays/censors DMP settlement of user assets/XCM without violating any current runtime invariant, matching the scoped impact ("censoring collator halting/delaying settlement of user-submitted DMP messages").

### Likelihood Explanation
This requires only that the block-producing collator is malicious/rational (an economically-motivated but otherwise "normal" collator role, not requiring privileged keys or governance access) and is fully reproducible every block: the collator simply builds the `ParachainInherentData`/`AbridgedInboundDownwardMessages` with a small `size_limit` for DMP (or hand-crafted hashed set) while still relaying a proper MQC head. There is no on-chain mechanism preventing this, since `check_enough_messages_included_advanced` — the only check that would catch it — is never called for the DMP path. This is a deterministic, always-reachable gap, not a probabilistic race.

### Recommendation
Invoke `check_enough_messages_included_advanced` for DMP in `enqueue_inbound_downward_messages`, mirroring the HRMP path, using `messages_collection_size_limit()` for `max_full_messages_size` and the configured max DMP message length (e.g. `MaxDmpMessageLenOf::<T>::get()`) for `first_hashed_msg_max_size`. This closes the asymmetry and enforces the "advancement rule" uniformly for both DMP and HRMP.

### Proof of Concept
Rust unit test (to be added near `parachain_inherent.rs` tests / `lib.rs` tests):
```rust
#[test]
fn dmp_advancement_rule_not_enforced_allows_censorship() {
    // Build 4 downward messages of size 100 each, size_limit large enough to fit all 4 in full.
    let msgs_vec = build_inbound_dm_vec(&[(0, 100), (0, 100), (0, 100), (0, 100)]);
    let msgs = InboundDownwardMessages::new(msgs_vec.clone());

    // Malicious collator artificially uses a tiny size_limit, hashing 3 of the 4 messages
    // even though messages_collection_size_limit() (the real on-chain budget) would allow all 4.
    let mut tiny_size_limit = 100usize; // only 1 message fits
    let abridged = msgs.into_abridged(&mut tiny_size_limit);

    assert_eq!(abridged.messages().0.len(), 1); // only 1 full message
    assert_eq!(abridged.messages().1.len(), 3); // 3 unnecessarily hashed

    // check_enough_messages_included_basic passes (>=1 full message present):
    abridged.check_enough_messages_included_basic("DMQ"); // does NOT panic

    // There is no equivalent call to check_enough_messages_included_advanced for DMP anywhere
    // in enqueue_inbound_downward_messages, so this censorship is never rejected on-chain,
    // whereas the equivalent HRMP scenario (see check_enough_messages_included_advanced_works)
    // would panic under the same size budget.
}
```

Expected assertion demonstrating the bug: for an equivalent HRMP scenario with the same size ratios, `check_enough_messages_included_advanced` panics (as shown by the existing test `check_enough_messages_included_advanced_works`), but no such panic occurs for DMP because the check is never invoked in `enqueue_inbound_downward_messages`. A full integration test would set `T::WeightInfo`/`BlockWeights` to a known `max_block` (fixing `messages_collection_size_limit()`), submit `set_validation_data` with a crafted `AbridgedInboundDownwardMessages` (1 full message + N hashed messages that would collectively still fit under the size budget), and assert the extrinsic succeeds — proving the runtime accepts unnecessary DMP censorship.

```rust
	/// Check that the current collection contains at least 1 full message if needed.
	pub fn check_enough_messages_included_basic(&self, collection_name: &str) {
		if self.hashed_messages.is_empty() {
			return;
		}

		// Here we just check that there is at least 1 full message.
		assert!(
			self.full_messages.len() >= 1,
			"[{}] Advancement rule violation: full messages missing",
			collection_name,
		);
	}

	/// Check that the current collection contains as many full messages as possible, taking into
	/// consideration the collection constraints.
	///
	/// The `AbridgedInboundMessagesCollection` is provided to the runtime by a collator.
	/// A malicious collator can provide a collection that contains no full messages or fewer
	/// full messages than possible, leading to censorship.
	pub fn check_enough_messages_included_advanced(
		&self,
		collection_name: &str,
		size_info: AbridgedInboundMessagesSizeInfo,
	) {
		// We should check that the collection contains as many full messages as possible
		// without exceeding the max expected size.
		let AbridgedInboundMessagesSizeInfo { max_full_messages_size, first_hashed_msg_max_size } =
			size_info;

		let mut full_messages_size = 0usize;
		for msg in &self.full_messages {
			full_messages_size = full_messages_size.saturating_add(msg.data().len());
		}

		// The worst case scenario is that were the first message that had to be hashed
		// is a max size message.
		assert!(
			full_messages_size.saturating_add(first_hashed_msg_max_size) > max_full_messages_size,
			"[{}] Advancement rule violation: full messages size smaller than expected. \
			full msgs size: {}, first hashed msg max size: {}, max full msgs size: {}",
			collection_name,
			full_messages_size,
			first_hashed_msg_max_size,
			max_full_messages_size
		);
	}
```
