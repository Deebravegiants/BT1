### Title
Oversized DMP messages are silently and permanently dropped during `DmpQueue`→`MessageQueue` lazy migration - (File: cumulus/pallets/dmp-queue/src/migration.rs)

### Summary
`migrate_page` and `migrate_overweight` attempt to convert legacy `Vec<u8>` DMP messages into `BoundedVec<u8, MaxDmpMessageLenOf<T>>` before forwarding them to `T::DmpSink`. If conversion fails because the message exceeds the parachain-configured `MaxDmpMessageLenOf<T>` bound, the message is only logged via `log::error!` and then dropped (`continue` in `migrate_page`, `Err(())` in `migrate_overweight`), with no storage of the raw bytes, no event, and no replay path.

### Finding Description
`migrate_page` (`cumulus/pallets/dmp-queue/src/migration.rs:77-96`) pops a page of legacy messages via `Pages::<T>::take(p)` and, for each message, tries `BoundedVec::<u8, _>::try_from(msg.clone())` (line 86). On failure it logs an error and `continue`s to the next message (lines 87-88) — the message content is gone forever since `Pages::take` already removed it from storage before the loop. `migrate_overweight` (lines 99-113) has the same pattern: `Overweight::<T>::take(i)` removes the entry, and if the bound conversion fails (line 104), the function just logs and returns `Err(())`, again with the message data lost.

These legacy `Pages`/`Overweight` entries were originally populated by the old `dmp-queue` pallet from messages the relay chain delivered to the parachain, subject only to the relay chain's `configuration.max_downward_message_size` (a relay-chain governance parameter, see `polkadot/runtime/parachains/src/dmp.rs` and `configuration.rs`). That relay-side limit is independent of, and can be larger than, the parachain's own `MaxDmpMessageLenOf<T>` constant used by `cumulus-pallet-parachain-system`/`dmp-queue` for the new `MessageQueue`-based bound. Any message that was valid and accepted at the relay-chain level but exceeds the parachain's newer, potentially stricter `MaxDmpMessageLenOf<T>` will silently fail the bound conversion during migration and be discarded with no on-chain trace beyond an off-chain log line.

An unprivileged actor does not need any special permission to get a large DMP message enqueued — DMP messages are XCM messages delivered from the relay chain (e.g., a large `Transact` payload, batched instructions, or reserve/teleport with call data) which any account able to route XCM to the relay chain (directly or via HRMP/XCM routing from another parachain/system chain) can influence in size and content, up to the relay's configured maximum. There is no code path in `migrate_page`/`migrate_overweight` that checks whether `MaxDmpMessageLenOf<T>` is at least as large as the relay's configured limit, nor any mechanism to persist or resurrect a message once it fails the bound check.

### Impact Explanation
If a message stored in the legacy `Pages` or `Overweight` maps exceeds `MaxDmpMessageLenOf<T>`, it is unconditionally and irreversibly dropped mid-migration. Because such messages can encode XCM instructions carrying asset transfers, `Transact` governance/runtime calls, or other user funds/instructions, this results in permanent loss of the encoded operation with zero on-chain accounting trail (only a debug/error log). This matches the scoped impact: accounting inconsistency and fund/instruction loss during the migration window, with no replay or recovery mechanism.

### Likelihood Explanation
Requires: (1) the parachain runs the `cumulus-pallet-dmp-queue` lazy migration (`MigrationStatus` in `StartedExport`/`StartedOverweightExport`), and (2) a pre-existing stored page/overweight message whose length exceeds `MaxDmpMessageLenOf<T>` for that runtime. Whether this condition is reachable depends on the concrete relation between the parachain's configured `MaxDmpMessageLenOf<T>` and the relay chain's `max_downward_message_size` at the time messages were originally enqueued — if the parachain's bound was always ≥ the relay's max, this specific drop path is unreachable in practice for that chain. This is a latent/config-dependent bug rather than one exploitable purely through a single attacker extrinsic; it manifests only for parachains whose historical DMP messages could exceed the newer bound, which is plausible but not universally guaranteed across all deployments.

### Recommendation
Before or during migration, either (a) assert/enforce that `MaxDmpMessageLenOf<T>` is not smaller than any historically-accepted relay-chain DMP message size for the chain, or (b) instead of dropping oversized messages, re-store them (e.g., back into an `Overweight`-like map without the bound, or a dedicated `FailedMigration` storage item) and emit an `Event` so operators/governance can detect and manually recover them, rather than only logging via `log::error!`.

### Proof of Concept
In `cumulus/pallets/dmp-queue/src/tests.rs`:
1. Seed `migration::Pages::<Test>::insert(0, vec![(1, vec![0u8; MaxDmpMessageLenOf::<Test>::get() as usize + 1])])` and `migration::PageIndex::<Test>::put(PageIndexData{begin_used:0,end_used:1,overweight_count:0})`.
2. Run `Pallet::<Test>::on_idle` (or directly invoke the migration hooks) until `MigrationStatus::get()` reaches `Completed`.
3. Assert that no corresponding message was forwarded to the mock `DmpSink`/`MessageQueue`, that `Pages`/`Overweight` no longer contain the entry, and that there is no event or storage item recording the drop for recovery — demonstrating silent, permanent loss.
