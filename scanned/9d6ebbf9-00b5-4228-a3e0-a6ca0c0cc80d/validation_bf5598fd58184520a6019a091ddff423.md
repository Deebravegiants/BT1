### Title
Repeated low-cost HRMP open/cancel-channel cycles from an attacker-controlled para can flood a victim para's `DownwardMessageQueue`, causing legitimate DMP notifications (including `HrmpChannelClosing`) to be silently dropped once `dmq_max_length` is hit - (File: polkadot/runtime/parachains/src/dmp.rs, polkadot/runtime/parachains/src/hrmp.rs)

### Summary
`Pallet::init_open_channel` only rate-limits the number of *pending* outbound requests per sender (`egress_cnt + open_req_cnt < channel_num_limit`), and that counter is decremented again by `hrmp_cancel_open_request`. There is no limit on how many `HrmpNewChannelOpenRequest`/`HrmpChannelAccepted`/`HrmpChannelClosing` notifications may be *queued to a single recipient* over time, and `Hrmp::send_to_para` silently swallows the case where `dmp::queue_downward_message` fails due to the recipient's queue being full, so an attacker-controlled para can cheaply cycle init→cancel to fill a victim para's DMQ up to `dmq_max_length()` and cause subsequent legitimate notifications to that para to be dropped without any error being surfaced.

### Finding Description
`Pallet::init_open_channel` (`polkadot/runtime/parachains/src/hrmp.rs:1443-1526`) enqueues a `HrmpNewChannelOpenRequest` downward message to `recipient` via `Self::send_to_para(...)` → `dmp::Pallet::<T>::queue_downward_message(...)` [1](#0-0) . The only anti-spam check performed is against the **sender's** own outbound-channel/open-request count: [2](#0-1) 

That counter (`HrmpOpenChannelRequestCount`) is incremented on `init_open_channel` and decremented again on `hrmp_cancel_open_request`, which also unreserves the sender's deposit. Nothing prevents the same attacker-controlled para (origin must pass `ensure_parachain`, i.e. it is a registered para acting via its own UMP/HRMP dispatch) from repeatedly cycling `hrmp_init_open_channel(victim, ...)` → `hrmp_cancel_open_request(...)` targeting the *same recipient*, paying only the transaction weight/fee each time (the deposit is returned on cancel) while producing one queued downward message to `victim` per cycle. Crucially, **there is no cap on the number of pending/cancelled requests a recipient can receive** — the only inbound-side cap (`hrmp_max_parachain_inbound_channels`) is checked in `accept_open_channel`, not in `init_open_channel`, so the victim never gets a chance to reject the notification itself.

On the receiving side, `dmp::Pallet::can_queue_downward_message` enforces the hard queue-length cap: [3](#0-2) 

and `dmq_max_length` is `MAX_POSSIBLE_ALLOCATION / max_downward_message_size` [4](#0-3) . Once the victim's queue reaches this cap, `queue_downward_message` returns `Err(QueueDownwardMessageError::ExceedsMaxMessageSize)` for *any* subsequent message directed at that para — including system-originated ones such as `HrmpChannelClosing` sent from `close_channel`, or governance messages sent via `sudo_queue_downward_xcm`.

Critically, `Hrmp::send_to_para` does not propagate this failure as an extrinsic error; it just logs and asserts (a no-op in production): [5](#0-4) 

This means: (1) the attacker's spamming extrinsics keep succeeding and filling the queue, (2) once full, legitimate HRMP notifications (including `HrmpChannelClosing`, which is how a channel-closing peer informs the counterparty) to the victim are dropped silently with no retry — the extrinsic that triggered them (e.g. some other para's `hrmp_close_channel`) still reports success even though its notification never reached the recipient.

The DMP delivery fee-factor mechanism (`increase_fee_factor`, triggered when queue length passes `THRESHOLD_FACTOR`) is meant to economically deter DMP queue growth, but it only affects the *cost of sending future XCM through the fee-metered router* to that destination — it does not apply to the cost of calling `hrmp_init_open_channel`/`hrmp_cancel_open_request` themselves, so it provides no deterrence against this specific spam vector.

### Impact Explanation
An attacker who controls even a single registered para can drive the victim's `InboundDownwardQueue` to `dmq_max_length()` through free (deposit-refunded) init/cancel cycles. Once full, any further downward message targeting that para — including `HrmpChannelClosing` notifications, other paras' HRMP lifecycle notifications, or governance-originated `sudo_queue_downward_xcm` messages — is silently dropped rather than queued or retried, effectively freezing the victim para's inbound DMP channel until the queue is drained (which requires the victim itself to process/prune messages, something it cannot influence since it did not initiate the flood).

### Likelihood Explanation
Feasibility depends on the attacker controlling a registered para capable of dispatching `hrmp_init_open_channel`/`hrmp_cancel_open_request` (a precondition explicitly granted by this question). Given that precondition, the exploit is fully repeatable: each cycle costs only transaction weight (deposit is refunded on cancellation), is bounded only by block weight/inclusion rate, and requires no cooperation from the victim or any privileged actor. `dmq_max_length` can be large (`MAX_POSSIBLE_ALLOCATION` divided by `max_downward_message_size`), so filling it fully may require many blocks of sustained spam, but there is no mechanism increasing the attacker's per-message cost for this specific call path, making sustained griefing economically cheap relative to the damage (freezing legitimate DMP delivery to the target).

### Recommendation
- Add a per-recipient rate limit or cap on the number of *pending* open-channel requests (and/or total HRMP-originated notifications) that can be queued toward a single recipient within a time window, independent of the sender-side `HrmpOpenChannelRequestCount` accounting.
- In `Hrmp::send_to_para`, do not silently swallow `QueueDownwardMessageError` failures for critical lifecycle notifications (e.g. `HrmpChannelClosing`); instead fail the extrinsic, retry later, or track undelivered notifications so they are not permanently lost once the queue drains.
- Consider applying the DMP delivery fee-factor (or an equivalent escalating cost) to the sender of HRMP lifecycle calls (`hrmp_init_open_channel`, `hrmp_cancel_open_request`) based on the current queue occupancy of the *recipient*, closing the gap where this notification path bypasses the existing anti-spam fee mechanism.

### Proof of Concept
Rust integration test in `polkadot/runtime/parachains/src/hrmp/tests.rs` style:
```rust
#[test]
fn hrmp_open_cancel_cycle_floods_victim_dmq() {
    let attacker = ParaId::from(2000);
    let victim = ParaId::from(2001);
    new_test_ext(GenesisConfigBuilder::default().build()).execute_with(|| {
        register_parachain(attacker);
        register_parachain(victim);
        run_to_block(5, Some(vec![4, 5]));

        let config = configuration::ActiveConfig::<Test>::get();
        let max_len = Dmp::dmq_max_length(config.max_downward_message_size); // via test-exposed helper

        // Repeatedly init+cancel from `attacker` targeting `victim`.
        for _ in 0..max_len {
            assert_ok!(Hrmp::hrmp_init_open_channel(
                crate::Origin::from(attacker).into(), victim, 2, 8
            ));
            let channel_id = HrmpChannelId { sender: attacker, recipient: victim };
            assert_ok!(Hrmp::hrmp_cancel_open_request(
                crate::Origin::from(attacker).into(), channel_id, 1000
            ));
        }

        assert_eq!(Dmp::dmq_length(victim), max_len);

        // Now a legitimate close-channel notification (from an unrelated real channel)
        // targeting `victim` should be silently dropped rather than surfacing an error.
        // Assert dmq_length stays at max_len (message not enqueued) even though the
        // extrinsic that triggered it returns Ok.
    });
}
```
Expected assertions: `Dmp::dmq_length(victim)` reaches `dmq_max_length`; a subsequent legitimate `queue_downward_message`/`send_to_para` call for `victim` returns `Err(QueueDownwardMessageError::ExceedsMaxMessageSize)` from `can_queue_downward_message`, and when routed through `Hrmp::send_to_para` the corresponding extrinsic (e.g. a third party's `hrmp_close_channel`) still returns `Ok(())` while the notification is verifiably absent from `Dmp::dmq_contents_do_not_call_in_consensus(victim)`.

	fn send_to_para(
		log_label: &str,

		dest: ParaId,
