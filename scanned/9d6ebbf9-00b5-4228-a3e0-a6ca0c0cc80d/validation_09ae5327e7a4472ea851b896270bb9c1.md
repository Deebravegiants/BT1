## Analysis

Confirmed: `paras_registrar::do_deregister` only permits deregistration when `paras::Pallet::<T>::lifecycle(id)` is `Some(ParaLifecycle::Parathread)` or `None` [1](#0-0) . This check is *independent* of `assigned_slots::TemporarySlots`/`PermanentSlots` bookkeeping, and `do_deregister` never touches those maps.

For `assign_temp_parachain_slot` with `SlotLeasePeriodStart::Next` (or `Current` when `ActiveTemporarySlotCount >= MaxTemporarySlotPerLeasePeriod`), no lease is created immediately: `configure_slot_lease`/`Leaser::lease_out` is only invoked conditionally [2](#0-1) . In that case the para's lifecycle remains `Parathread` even though `TemporarySlots<T>` now holds an entry for it. During this window the parathread manager can call `paras_registrar::deregister` (a normal signed extrinsic, permitted because lifecycle is still `Parathread`), which clears `Paras::<T>` (so `manager_of` becomes `None`) and eventually returns the id to lifecycle `None`, all while `TemporarySlots<T>` for that `ParaId` is left untouched (stale, desynced) [3](#0-2) .

The `ParaId` can then be re-registered — by the same or a different manager — via `register`/`reserve`, since `Paras::<T>::get(id)` is now `None` and the ownership check is skipped [4](#0-3) . Later, `on_initialize` -> `manage_lease_period_start` -> `allocate_temporary_slot_leases` iterates `TemporarySlots<T>` unconditionally and calls `configure_slot_lease`/`Leaser::lease_out` using the *stale* `temp_slot.manager` for the (possibly now different) para occupying that `ParaId`, with no re-validation of `Registrar::manager_of`/`is_parathread` [5](#0-4) . `Leaser::lease_out` (`Slots::lease_out`) inserts into `Leases<T>` and, if `period_begin == current_lease_period`, best-effort calls `Registrar::make_parachain(id)` regardless of who currently controls the id [6](#0-5) . This grants a free (zero-amount) parachain slot to whatever para now occupies the ParaId, and `unassign_parachain_slot`'s cleanup (`has_permanent_slot`/`has_temporary_slot` checks plus `clear_slot_leases`) also operates purely on the recycled `ParaId` key without validating the current registrant, so governance's later "unassign" of the *original* slot silently affects the new occupant's lease state instead [7](#0-6) .

This matches the tests observed (`unassign_temp_slot_succeeds`, `unassign_perm_slot_succeeds`) which only cover the case where the registrar state and assigned-slots bookkeeping stay in sync — there is no test exercising deregister/re-register of the para in between assignment and unassignment/allocation.

### Title
Stale `TemporarySlots`/`PermanentSlots` bookkeeping after registrar deregister+re-register desyncs slot leases from `Registrar` state - (File: polkadot/runtime/common/src/assigned_slots/mod.rs)

### Summary
`assigned_slots::TemporarySlots`/`PermanentSlots` are keyed only by `ParaId` and are never invalidated when `paras_registrar::deregister` removes a para that has a *pending* (not-yet-leased) temporary/permanent slot assignment. Because `deregister` only checks para lifecycle (`Parathread`/`None`) and not `assigned_slots` state, a parathread manager can deregister and a new (possibly attacker-controlled) party can re-register the same `ParaId`, causing later `allocate_temporary_slot_leases`/`unassign_parachain_slot` calls to operate on the wrong registrant using stale manager/slot metadata.

### Finding Description
- `assign_temp_parachain_slot` with `SlotLeasePeriodStart::Next` (or `Current` when the per-period active cap is already reached) inserts into `TemporarySlots<T>` without creating an actual lease yet, leaving `paras::lifecycle(id) == Parathread` [8](#0-7) .
- `paras_registrar::do_deregister` allows deregistration whenever lifecycle is `Parathread` or `None`, with no cross-check against `assigned_slots` storage [9](#0-8) . The attacker (the para's own manager, an unprivileged signed account) can call this directly.
- After deregistration and re-registration of the same `ParaId` (by the manager or a third party, since ownership checks only apply if `Paras::<T>::get(id)` is `Some`), `TemporarySlots<T>[id]` still contains the old manager/period data.
- `allocate_temporary_slot_leases` (invoked from `on_initialize`) blindly iterates `TemporarySlots<T>` and calls `Leaser::lease_out` for the stale entry against whatever para now holds that `ParaId`, without re-verifying `Registrar::manager_of`/`is_parathread` [10](#0-9) .
- `Slots::lease_out` may then best-effort call `Registrar::make_parachain(id)`, granting the new registrant of that `ParaId` a free slot upgrade [6](#0-5) .
- `unassign_parachain_slot`, when later invoked by governance for the original assignment, only consults `PermanentSlots`/`TemporarySlots`/`Slots::Leases` keyed by `ParaId`, so it clears/downgrades whatever para currently sits at that id — not the para governance intended — while its own `has_permanent_slot`/`has_temporary_slot` gating never detects the substitution [7](#0-6) .

### Impact Explanation
A parathread manager can use ordinary `paras_registrar` extrinsics to desynchronize `assigned_slots` bookkeeping from `Registrar`/`Slots` truth. The concrete effect within the pallet's own logic: a pending temporary/permanent slot's later activation (`allocate_temporary_slot_leases`) or a later `unassign_parachain_slot` acts on whichever para now occupies the recycled `ParaId`, not the para governance originally assigned to/from. This is confined to a test-only pallet (`assigned_slots` is explicitly documented as "should not be used on a production relay chain, only on a test relay chain (e.g. Rococo)") but is a real logic bug relative to the stated invariant that `PermanentSlots`/`TemporarySlots` must stay consistent with `Slots::Leases`/`Registrar::manager_of`.

### Likelihood Explanation
Requires: (1) governance/root to have called `assign_temp_parachain_slot` with `Next` (or hit the active-slot cap) for a para, and (2) the para's manager to deregister+re-register (or hand off) the `ParaId` before `allocate_temporary_slot_leases` processes it or before `unassign_parachain_slot` is called. Both steps are ordinary unprivileged signed extrinsics from the parathread manager; no special access is needed. This is feasible and repeatable on any chain configured with this pallet (currently only test relay chains like Rococo).

### Recommendation
In `allocate_temporary_slot_leases` and in `unassign_parachain_slot`, re-validate `T::Registrar::manager_of(id)` and `T::Registrar::is_parathread(id)`/`is_parachain(id)` against the stored slot's `manager` before acting, and treat any mismatch (or an unregistered id) as a cause to purge the stale `TemporarySlots`/`PermanentSlots` entry instead of operating on it. Additionally, hook `assigned_slots` cleanup into `paras_registrar::do_deregister` (e.g., via a trait callback) so deregistering a para with a pending/active assigned slot immediately clears the corresponding `TemporarySlots`/`PermanentSlots` entry.

### Proof of Concept
Rust integration test in `polkadot/runtime/common/src/assigned_slots/mod.rs` tests module:
1. Register para 1, call `assign_temp_parachain_slot(root, 1, SlotLeasePeriodStart::Next)` (no immediate lease; `TemporarySlots::<Test>::get(1)` is `Some` with `last_lease: None`).
2. As the manager (signed), call `TestRegistrar::deregister(1)` (or via the mock registrar's deregister path) — assert this succeeds while lifecycle is still `Parathread`.
3. Re-register `ParaId::from(1)` under a different account (e.g. account `2`).
4. Advance blocks to the `period_begin` lease period so `on_initialize` triggers `allocate_temporary_slot_leases`.
5. Assert: `Slots::already_leased(1, ...)` becomes true and `TestRegistrar::manager_of(1) == Some(2)`, i.e., account `2`'s para received a lease/slot upgrade that was intended for the original registrant, and `TemporarySlots::<Test>::get(1).manager` still shows the stale old manager (account `1`), demonstrating the desync — despite `Registrar::manager_of` now reporting a different owner.
6. 	fn allocate_temporary_slot_leases(lease_period_index: LeasePeriodOf<T>) -> DispatchResult {
		let mut active_temp_slots = 0u32;
		let mut pending_temp_slots = Vec::new();
		TemporarySlots::<T>::iter().for_each(|(para, slot)| {
				match slot.last_lease {
					Some(last_lease)
						if last_lease <= lease_period_index &&
							lease_period_index <
								(last_lease.saturating_add(slot.period_count)) =>
					{
						// Active slot lease
						active_temp_slots += 1;
					}
					Some(last_lease)
						// Slot w/ past lease, only consider it every other slot lease period (times period_count)
						if last_lease.saturating_add(slot.period_count.saturating_mul(2u32.into())) <= lease_period_index => {
							pending_temp_slots.push((para, slot));
					},
					None if slot.period_begin <= lease_period_index => {
						// Slot hasn't had a lease yet
						pending_temp_slots.insert(0, (para, slot));
					},
					_ => {
						// Slot not being considered for this lease period (will be for a subsequent one)
					},
				}
		});

		let mut newly_created_lease = 0u32;
		if active_temp_slots < T::MaxTemporarySlotPerLeasePeriod::get() &&
			!pending_temp_slots.is_empty()
		{
			// Sort by lease_count, favoring slots that had no or less turns first
			// (then by last_lease index, and then Para ID)
			pending_temp_slots.sort_by(|a, b| {
				a.1.lease_count
					.cmp(&b.1.lease_count)
					.then_with(|| a.1.last_lease.cmp(&b.1.last_lease))
					.then_with(|| a.0.cmp(&b.0))
			});

			let slots_to_be_upgraded = pending_temp_slots.iter().take(
				(T::MaxTemporarySlotPerLeasePeriod::get().saturating_sub(active_temp_slots))
					as usize,
			);

			for (id, temp_slot) in slots_to_be_upgraded {
				TemporarySlots::<T>::try_mutate::<_, _, Error<T>, _>(id, |s| {
					// Configure temp slot lease
					Self::configure_slot_lease(
						*id,
						temp_slot.manager.clone(),
						lease_period_index,
						temp_slot.period_count,
					)
					.map_err(|_| Error::<T>::CannotUpgrade)?;

					// Update temp slot lease info in storage
					*s = Some(ParachainTemporarySlot {
						manager: temp_slot.manager.clone(),
						period_begin: temp_slot.period_begin,
						period_count: temp_slot.period_count,
						last_lease: Some(lease_period_index),
						lease_count: temp_slot.lease_count + 1,
					});

					newly_created_lease += 1;

					Ok(())
				})?;
			}
