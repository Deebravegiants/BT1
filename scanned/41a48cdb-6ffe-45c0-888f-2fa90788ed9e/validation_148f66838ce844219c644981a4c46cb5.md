## Analysis Result

I investigated the closest analog to this Keycloak "stale session survives scope revocation" bug class within the chainlink node's session/authentication subsystem (LDAP and OIDC auth providers), which cache upstream role/session state locally rather than re-validating live and continuously against the identity provider.

### Title
Revoked LDAP roles/sessions remain valid indefinitely when `UpstreamSyncInterval` is left at its default disabled value - (File: core/sessions/ldapauth/sync.go)

### Summary
The LDAP authentication provider caches user sessions and roles locally in the `ldap_sessions` and `ldap_user_api_tokens` tables. Revocation propagation from the upstream LDAP directory (e.g., removing a user from an admin group) depends entirely on the periodic `LDAPServerStateSyncer.Work` job, which is only started as a recurring background task if `UpstreamSyncInterval` is configured to a non-zero value [1](#0-0) . The documented default for `UpstreamSyncInterval` is `'0s'`, which is treated as "disabled" for the recurring timer path [2](#0-1) .

### Finding Description
When `UpstreamSyncInterval` is `0s` (the shipped default), `Start` only calls `Work` a single time at node startup instead of scheduling a recurring sync goroutine [1](#0-0) . Per-request session/API-token validation (`AuthorizedUserWithSession`, `FindUserByAPIToken`) only checks the locally cached role and expiry timestamp in `ldap_sessions` / `ldap_user_api_tokens` — it never re-queries the upstream LDAP server or triggers `Work` on each request [3](#0-2) . The package-level doc comment claims "This sync happens for every auth endpoint hit" [4](#0-3) , but the actual authentication code path (`FindUserByAPIToken`/`AuthorizedUserWithSession`) does not invoke the syncer at all — only `Start()` (once, at boot) and the optional timer in `run()` do [5](#0-4) . Consequently, if an administrator removes a user from an LDAP admin/edit/run group (the direct analog of removing the `offline_access` scope from a Keycloak client), the locally cached `user_role` in `ldap_sessions`/`ldap_user_api_tokens` is not updated or purged until the next `Work` invocation — which, under default configuration, never runs again after startup.

### Impact Explanation
A user whose privileges are revoked upstream (e.g., demoted from Admin to View, or fully removed from all LDAP groups) retains their previously cached elevated role for the lifetime of their existing session cookie or API token (up to `SessionTimeout` / `UserAPITokenDuration`, default 15m and 240h respectively) as long as the operator has not explicitly configured a non-default `UpstreamSyncInterval`. This is a session/role revocation bypass analogous to the Keycloak CWE-613 finding: the administrator believes access has been removed, but the previously-issued credential continues to authorize privileged node API actions.

### Likelihood Explanation
This requires the LDAP authentication method to be enabled and `UpstreamSyncInterval` left at its documented default (`'0s'`), which is a plausible and likely operator configuration since the default disables the recurring background job. No attacker action beyond continuing to use an already-issued session/token is needed, matching the "unprivileged actor continues using previously valid credentials" pattern of the reported CVE.

### Recommendation
Re-validate role/membership against the upstream LDAP server (or at minimum consult a very recent cache) on every `AuthorizedUserWithSession`/`FindUserByAPIToken` call, or change the default so that `Work` always runs on a bounded recurring interval regardless of `UpstreamSyncInterval` being unset, and update the misleading doc comment claiming per-request sync already occurs.

### Proof of Concept
1. Deploy a chainlink node with `WebServer.AuthenticationMethod = 'ldap'` and default `WebServer.LDAP.UpstreamSyncInterval = '0s'`.
2. Log in as a user who is a member of the LDAP `AdminUserGroupCN` group; the node caches `user_role = admin` in `ldap_sessions`.
3. On the upstream LDAP server, remove the user from the admin group (or deactivate the account if `ActiveAttribute` isn't configured).
4. Continue issuing admin-level requests using the existing session cookie/API token: they remain accepted with the stale cached `admin` role, since neither `AuthorizedUserWithSession` nor `FindUserByAPIToken` re-check the upstream server and no background sync job is running to purge/update the cache.

func (l *LDAPServerStateSyncer) Start(ctx context.Context) error {
	// If enabled, start a background task that calls the Sync/Work function on an
	// interval without needing an auth event to trigger it
	// Use IsInstant to check 0 value to omit functionality.
	if !l.config.UpstreamSyncInterval().IsInstant() {
		l.lggr.Info("LDAP Config UpstreamSyncInterval is non-zero, sync functionality will be called on a timer, respecting the UpstreamSyncRateLimit value")
		go l.run()
	} else {
		// Ensure upstream server state is synced on startup manually if interval check not set
		l.Work(ctx)
	}
	return nil
}

func (l *LDAPServerStateSyncer) Work(ctx context.Context) {
	// Purge expired ldap_sessions and ldap_user_api_tokens
	recordCreationStaleThreshold := l.config.SessionTimeout().Before(time.Now())
	err := l.deleteStaleSessions(ctx, recordCreationStaleThreshold)
	if err != nil {
		l.lggr.Error("unable to expire local LDAP sessions: ", err)
	}
	recordCreationStaleThreshold = l.config.UserAPITokenDuration().Before(time.Now())
	err = l.deleteStaleAPITokens(ctx, recordCreationStaleThreshold)
	if err != nil {
		l.lggr.Error("unable to expire user API tokens: ", err)
	}

	// Optional rate limiting check to limit the amount of upstream LDAP server queries performed
	if !l.config.UpstreamSyncRateLimit().IsInstant() {
		if !time.Now().After(l.nextSyncTime) {
			return
		}

		// Enough time has elapsed to sync again, store the time for when next sync is allowed and begin sync
		l.nextSyncTime = time.Now().Add(l.config.UpstreamSyncRateLimit().Duration())
	}

	l.lggr.Info("Begin Upstream LDAP provider state sync after checking time against config UpstreamSyncInterval and UpstreamSyncRateLimit")

// FindUserByAPIToken retrieves a possible stored user and role from the ldap_user_api_tokens table store
func (l *ldapAuthenticator) FindUserByAPIToken(ctx context.Context, apiToken string) (sessions.User, error) {
	if !l.config.UserApiTokenEnabled() {
		return sessions.User{}, errors.New("API token is not enabled ")
	}

	// Query the ldap user API token table for given token, user role and email are cached so
	// no further upstream LDAP query is performed, sessions and tokens are synced against the upstream server
	// via the UpstreamSyncInterval config and reaper.go sync implementation
	var foundUserToken struct {
		UserEmail string
		UserRole  sessions.UserRole
		Valid     bool
	}
	err := l.ds.GetContext(ctx, &foundUserToken,
		"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM ldap_user_api_tokens WHERE token_key = $1",
		apiToken, l.config.UserAPITokenDuration().Duration(),
	)
	if err != nil {
		return sessions.User{}, err
	}
	if !foundUserToken.Valid { // API Token expired, purge
		if _, execErr := l.ds.ExecContext(ctx, "DELETE FROM ldap_user_api_tokens WHERE token_key = $1", apiToken); execErr != nil {
			l.lggr.Errorf("error purging stale ldap API token session: %v", execErr)
		}
		return sessions.User{}, sessions.ErrUserSessionExpired
	}

	return sessions.User{
		Email: foundUserToken.UserEmail,
		Role:  foundUserToken.UserRole,
	}, nil
}
