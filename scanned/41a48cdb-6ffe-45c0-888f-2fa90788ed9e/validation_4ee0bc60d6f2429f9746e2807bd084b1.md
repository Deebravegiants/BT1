Based on my investigation, I found a concrete role-based access control gap that is analogous to the CVE — an unprivileged authenticated user can read node configuration data (including potentially secret-bearing RPC endpoint URLs) through an endpoint that should require elevated privilege.

### Title
Low-privilege authenticated users can read the full node configuration (including RPC endpoint URLs that may embed provider API keys) via `GET /v2/config` — ([File: core/web/config_controller.go])

### Summary
The `/v2/config` and `/v2/config/v2` routes are registered in the authenticated route group but, unlike almost every other mutating/read-sensitive endpoint in the router, they are not wrapped with any role gate (`auth.RequiresEditRole`/`auth.RequiresAdminRole`). Any authenticated session — including the lowest-privilege `view` role — can call this endpoint and retrieve the node's complete effective configuration TOML.

### Finding Description
`v2Routes` mounts `ConfigController.Show` directly on the `authv2` group with no role wrapper, while sibling routes like key export, transfers, or bridge management are wrapped with `auth.RequiresEditRole`/`auth.RequiresAdminRole`: [1](#0-0) 

`ConfigController.Show` returns the full effective (or user-input) configuration as TOML to any caller who reaches it: [2](#0-1) 

The router's own RBAC test matrix confirms this endpoint is reachable by `view`, `run`, and `edit` roles alike (`viewOnlyAllowed: true`): [3](#0-2) 

The data returned is the `Config` (non-`Secrets`) TOML produced by `ConfigTOML()`, which includes chain node connection details such as `EVM.Nodes[].WSURL`/`HTTPURL`: [4](#0-3) 

Unlike the dedicated `Secrets` struct (e.g., `Database`, `Password`, `Pyroscope.AuthToken`, `Mercury.Credentials`) which is explicitly redacted before being logged/exposed: [5](#0-4) 

...RPC node URLs configured under `[[EVM.Nodes]]` are part of the non-secret `Config` struct and are not redacted at all, even though operators commonly embed RPC provider API keys/tokens directly in `WSURL`/`HTTPURL` (a widely-documented pattern for providers like Alchemy/Infura): [6](#0-5) 

This is directly analogous to the CVE's bug class: an authenticated but low-privileged principal can retrieve configuration data that contains credentials/keys intended to gate access to a privileged external resource (here, the node operator's RPC provider account), because the endpoint that serves that config lacks a role check that its sibling sensitive endpoints have.

### Impact Explanation
A `view`-role user (the lowest privilege tier, which per the RBAC design should be read-only and non-sensitive) can extract RPC provider URLs/API keys embedded in `EVM.Nodes` configuration. These keys often carry billing/quota implications and, depending on the provider, broader RPC node privileges (e.g., debug/trace methods) — resulting in unauthorized access to a resource the requesting user's role was not meant to reach, and financial/DoS impact on the operator's RPC provider account.

### Likelihood Explanation
High for any deployment where an admin has legitimately provisioned multiple user roles (a normal RBAC setup) and configured RPC endpoints with embedded credentials (a common real-world pattern). Exploitation requires only a valid low-privilege API/session token — no additional bypass technique needed, since the missing role check is the vulnerability itself.

### Recommendation
Wrap `/v2/config` and `/v2/config/v2` with `auth.RequiresAdminRole` (or at minimum `auth.RequiresEditRole`), consistent with other configuration/credential-adjacent endpoints in the router. Additionally, consider redacting URL credentials/query parameters in `EVM.Nodes[].WSURL`/`HTTPURL` (and any other externally-configured endpoint URLs) when serialized via `ConfigTOML()`, mirroring the existing `Secrets` redaction pattern, so that even privileged roles do not inadvertently leak provider credentials through logs, support tickets, or the config API.

### Proof of Concept
1. Create a Chainlink node user with role `view` (or generate a `view`-role API token via `POST /v2/user/token`) — a low-privilege authenticated principal.
2. As that user, issue: `GET /v2/config` with the token's API key/secret headers.
3. Observe the response contains the full effective configuration, including `[[EVM.Nodes]]` entries with `WSURL`/`HTTPURL`, which may contain the operator's RPC provider API key (e.g., `https://eth-mainnet.g.alchemy.com/v2/<API_KEY>`), even though this user's role should not grant access to credential-bearing infrastructure details.

```go
func (cc *ConfigController) Show(c *gin.Context) {
	cfg := cc.App.GetConfig()
	var userOnly bool
	if s, has := c.GetQuery("userOnly"); has {
		var err error
		userOnly, err = strconv.ParseBool(s)
		if err != nil {
			jsonAPIError(c, http.StatusBadRequest, fmt.Errorf("invalid bool for userOnly: %w", err))
			return
		}
	}
	var toml string
	user, effective := cfg.ConfigTOML()
	if userOnly {
		toml = user
	} else {
		toml = effective
	}
	jsonAPIResponse(c, ConfigV2Resource{toml}, "config")
}
```
