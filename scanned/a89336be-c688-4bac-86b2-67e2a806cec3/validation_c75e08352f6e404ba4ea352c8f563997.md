Based on my research, the strongest reachable analog to this Sybil/cap-bypass bug class in Chainlink is the per-owner workflow registration limit enforced by `syncerlimiter.NewWorkflowLimits`, which — exactly like the reported `CAP_PER_ADDRESS` NFT mint cap — is keyed only by a self-declared `owner` address with no additional permission or identity-cost check, so it can trivially be bypassed by registering workflows under new, freely-generated addresses.

### Title
Per-owner workflow registration limit is trivially bypassable via Sybil addresses, allowing a single actor to exhaust the node's global workflow capacity - (File: core/services/workflows/syncerlimiter/limiter.go)

### Summary
`NewWorkflowLimits` enforces two quotas for workflow registration on a Chainlink node/DON: a `Global` cap across all owners and a `PerOwner` cap per workflow owner address. [1](#0-0)  The `PerOwner` limit is keyed purely by the `Owner` value carried in the workflow registration context (`contexts.CREValue(ctx).Owner`), which is derived from the `WorkflowOwner` address emitted in the on-chain `WorkflowRegisteredEvent`. [2](#0-1)  There is no requirement that the owner address be whitelisted or tied to any real-world identity/staking cost beyond paying gas to register a new workflow — exactly analogous to the reported issue where `CAP_PER_ADDRESS` can be bypassed by minting from a new, freely-generated address because there is no whitelist or permission gate.

### Finding Description
`Engine.init` calls `e.cfg.GlobalWorkflowLimit.Use(ctx, 1)` on workflow initialization, which increments both the `Global` and `PerOwner` counters for the CRE context's `Owner`. [3](#0-2)  Because `PerOwner` is scoped strictly to the self-reported/owner-address dimension with no Sybil resistance (any new EOA can register a workflow on the WorkflowRegistry contract and become a "new owner" for the purposes of this limiter), an attacker who controls unlimited addresses can register `PerOwner` workflows under each of many addresses, consuming slots against the shared `Global` limit while never individually exceeding `PerOwner`. This mirrors the audit finding precisely: the cap-per-identity check exists, but nothing prevents cheaply minting new identities to bypass it.

### Impact Explanation
The `Global` limit exists specifically to bound total node/DON capacity consumed by workflow execution (default `200`, configurable via `Workflows.Limits.Global`/`PerOwner` in `core/config/docs/core.toml`). [4](#0-3)  A single actor rotating across Sybil owner addresses can consume the entire `Global` quota before other legitimate workflow owners get a chance to register/run workflows on that DON, resulting in denial-of-service to legitimate users sharing the same capability node/DON — the `PerOwner` control becomes ineffective as a fairness/anti-abuse mechanism.

### Likelihood Explanation
Registering a workflow under a new address only requires generating a new EOA and paying the registration gas cost on the WorkflowRegistry contract — there is no allowlist, staking, or identity verification gating who can become a "workflow owner." This makes the bypass cheap and reachable by any unprivileged actor able to submit workflow registration transactions.

### Recommendation
Since `Global` is the only real backstop, consider adding cost/reputation-based Sybil resistance for the `PerOwner` quota (e.g., requiring staked/allowlisted owner addresses, tying quota to a verified organization/owner identity via the `Org` resolver already present in `contexts.CRE`, or rate-limiting new-owner registrations per time window) so that the per-owner limit cannot be trivially circumvented by rotating addresses.

### Proof of Concept
1. Deploy `N` workflows under owner address `A`, each incrementing `Global` and `PerOwner[A]` via `syncerlimiter.Config{Global: G, PerOwner: P}` (`core/services/workflows/syncerlimiter/limiter.go` lines 48-78).
2. Once `PerOwner[A]` reaches `P`, further registrations from `A` fail with `settings.ScopeOwner` limited error, as shown in the limiter's own test. [5](#0-4) 
3. Generate a new address `B` and repeat registration; `PerOwner[B]` starts fresh at 0, allowing another `P` workflows to be registered, only bounded by the shared `Global` counter. [6](#0-5) 
4. Repeat with addresses `C, D, ...` until `Global` is exhausted — demonstrating that the `PerOwner` quota provides no real protection against a single actor monopolizing the node's total workflow capacity.

	if k.getter != nil {
		value, err = k.getter.GetScoped(ctx, scope, key)
	}
	if value != "" {
		return
	}
	if k.key != key || scope != settings.ScopeOwner {
		return "", nil
	}
	return k.vals[contexts.CREValue(ctx).Owner], nil
}
