### Title
Vault gateway handler logs the full JSON-RPC request/response, including caller-supplied JWT auth tokens, into node logs at Debug level - ([File: core/capabilities/vault/gw_handler.go])

### Summary
`GatewayHandler.HandleGatewayMessage` in the vault capability logs the entire incoming JSON-RPC request struct and the outgoing response struct as structured log fields at Debug/Info level. Because the request struct carries the raw bearer/JWT `Auth` value used to authenticate the caller, this results in insertion of sensitive authentication material into the node's on-disk log file — the same bug class as CVE-2023-22447 (insertion of sensitive information into log files), reachable from an unprivileged/external gateway client rather than a privileged local operator.

### Finding Description
`jsonrpc.Request[T]` carries an `Auth` field that holds the caller's bearer/JWT token used by `Authorizer.AuthorizeRequest` (`core/capabilities/vault/authorizer.go`) and `jwtBasedAuth.AuthorizeRequest` (`core/capabilities/vault/jwt_based_auth.go`) to authenticate vault requests forwarded from the gateway to the DON node. [1](#0-0) 

The gateway-facing handler for vault requests logs the raw request and response objects wholesale: [2](#0-1) [3](#0-2) 

Elsewhere in the same authorization pipeline, engineers were clearly aware that `req.Auth` is sensitive: most call sites deliberately log only `"hasAuth", req.Auth != ""` rather than the raw value, e.g. in `authorizer.go`: [4](#0-3) 

and in `jwt_based_auth.go`, note the token itself is never logged directly: [5](#0-4) 

However, `GatewayHandler.HandleGatewayMessage` bypasses this discipline: it logs `"req", req` (the whole `jsonrpc.Request[json.RawMessage]`, including its `Auth` field) at Debug level, and logs `"resp", response` at Info level. Because `Request.Auth` has no redaction/`MarshalLogObject` override found anywhere in the codebase (no `String()`/`MarshalLogObject` implementation for the type was found), Go's structured/reflective logging (zap `SugaredLogger.Debugw`) will serialize the struct with its exported `Auth` field intact, writing the plaintext JWT into the node's `log.jsonl` file whenever `Log.Level = 'debug'` (a supported, documented configuration option, see `docs/CONFIG.md` and `disk-based-logging-disabled.txtar`). [6](#0-5) 

There is a similar, related pattern in the confidentialrelay handler tests demonstrating awareness that raw params logging is a real risk that must be actively tested against (`TestVaultHandler_InvalidParamsDoesNotLogRawParams`), confirming this is a recognized-but-inconsistently-enforced class of bug in this code: [7](#0-6) 

### Impact Explanation
The vault JWT `Auth` token authorizes secret create/update/delete/list operations for a specific workflow owner within the vault DON. Any actor with read access to the node's log file (a privileged local user on the node host, or any process/pipeline that ships/aggregates `log.jsonl`) can extract a still-valid JWT and replay it (subject to the request-digest binding and replay guard) or otherwise gain visibility into caller identity/authorization metadata that should remain confidential. This maps to "concrete authentication/secret disclosure" under the report's acceptance criteria, since the token is exactly the unprivileged client's authentication credential for vault operations, disclosed via a log sink under privileged/local access — mirroring CVE-2023-22447 precisely.

### Likelihood Explanation
Exploitation only requires: (1) `Log.Level` set to `debug` (or the response line, which is logged at `Info`, always-on) on a node running the vault gateway handler, and (2) an actor able to read the node's log output. Debug logging is a standard, supported, non-exotic operational configuration (documented in `docs/CONFIG.md`), and any legitimate vault client request passing through the gateway will trigger this log line, so the disclosure occurs under ordinary operation, not a rare edge case. The response-object log line at Info level is emitted unconditionally on every gateway message handled.

### Recommendation
- Strip or redact `Auth` before logging the request/response objects in `GatewayHandler.HandleGatewayMessage` (e.g., log `"hasAuth", req.Auth != ""` and other non-sensitive fields, consistent with `authorizer.go`), instead of logging the raw struct.
- Add a `MarshalLogObject`/custom `String()` method on the shared `jsonrpc.Request`/`Response` types (or a redacting wrapper) so any future call site that logs these structs cannot leak `Auth` by default.
- Add a regression test analogous to `TestVaultHandler_InvalidParamsDoesNotLogRawParams` asserting that no log entry from `gw_handler.go` contains the raw `Auth` token value.

### Proof of Concept
1. Configure a chainlink node running the vault capability's gateway connector with `Log.Level = 'debug'`.
2. Send a vault JSON-RPC request (e.g., `vault.secrets.list`) through the gateway with a valid JWT in the `auth` field, per the flow exercised in `system-tests/tests/smoke/cre/vault_don_test_helpers.go` (`sendVaultSignedOCRRequestToGateway`, which sets `Authorization: Bearer <token>` and strips `Auth` only from the outbound wire payload, not from the in-process struct handled by `gw_handler.go`).
3. Inspect the node's `log.jsonl` file: the `Debugw("received message from gateway", "req", req)` call in `core/capabilities/vault/gw_handler.go:182` will contain a `req` field whose JSON representation includes the full JWT string, and the `Infow("Sent message to gateway", "resp", response)` at line 231 exposes the outgoing signed payload. func TestVaultHandler_InvalidParamsDoesNotLogRawParams(t *testing.T) {
	t.Parallel()

	// Observed at Info level so the pre-existing whole-request Debug log is excluded.
	lggr, logs := logger.TestObserved(t, zapcore.InfoLevel)
	h, callback, don, _ := setupHandlerWithLogger(t, lggr, limits.Factory{Settings: cresettings.DefaultGetter})
	// Don't expect SendToNode to be called for invalid params
	don.AssertNotCalled(t, "SendToNode")

	const marker = "SENSITIVE_MARKER_123"
	invalidParams := json.RawMessage(`{"request_id":"req-1","injected":"` + marker + `"}`)
	req := jsonrpc.Request[json.RawMessage]{
		ID:     "invalid-params-logs",
		Method: vaulttypes.MethodSecretsCreate,
		Params: &invalidParams,
	}

	// The invalid-params response is sent synchronously, so no goroutine is needed.
	err := h.HandleJSONRPCUserMessage(t.Context(), req, callback)
	require.NoError(t, err)

	resp, err := callback.Wait(t.Context())
	require.NoError(t, err)
	var secretsResponse jsonrpc.Response[vaultcommon.CreateSecretsResponse]
	require.NoError(t, json.Unmarshal(resp.RawResponse, &secretsResponse))
	assert.Equal(t, req.ID, secretsResponse.ID, "Request ID should match")
	assert.Equal(t, api.ToJSONRPCErrorCode(api.InvalidParamsError), secretsResponse.Error.Code, "Error code should match")

	invalidParamsLogs := logs.FilterMessage("invalid params")
	entries := invalidParamsLogs.All()
	require.Len(t, entries, 1, "expected exactly one 'invalid params' log entry")
	assert.Equal(t, zapcore.ErrorLevel, entries[0].Level)
	assert.Equal(t, req.ID, entries[0].ContextMap()["requestID"])
	assert.NotContains(t, entries[0].ContextMap(), "params", "raw params must not be logged")

	for _, e := range logs.All() {
		assert.NotContains(t, e.Message, marker)
		for k, v := range e.ContextMap() {
			if s, ok := v.(string); ok {
				assert.NotContains(t, s, marker, "log field %q must not contain raw request params", k)
			}
		}
	}
