### Title
Unprivileged actor can spam pending capability callbacks to evict legitimate in-flight requests via `pruneCallbacks` halving - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
The gateway's capabilities handler stores pending node/workflow requests in a bounded map (`savedCallbacks`) and enforces a cap (`MaxSavedCallbacks`) by halving the map when the cap is exceeded, keeping only the newest half of entries. This mirrors the reported Morpho Heap issue: a size-bounded, "halve on overflow" data structure lets an attacker who can cheaply generate many new entries evict the legitimate, older entries that were already waiting for a response.

### Finding Description
`pruneCallbacks` in the gateway capabilities handler removes expired entries by age (`CallbackMaxAgeSec`) and additionally enforces `MaxSavedCallbacks` by trimming the map down to `maxSize/2`, discarding the oldest surviving entries regardless of whether they are legitimately pending a response from a node. [1](#0-0) 

This is functionally identical to the reported Heap halving behavior: when the bounded structure overflows, it is trimmed to half its capacity, and whichever entries are "newest" (by insertion/creation order) survive — regardless of whether the evicted entries represent legitimate, already-in-flight work. In the audited protocol this let an attacker's newly inserted dust accounts push out legitimate suppliers; here, an attacker who can cheaply and repeatedly trigger new `savedCallback` entries (e.g. by sending many capability requests through the gateway) can force `pruneCallbacks` to run and evict older, legitimate pending callbacks before their corresponding node response arrives. [2](#0-1) 

Comparable bounded/eviction structures exist elsewhere in the gateway path but do not exhibit the same "evict existing legitimate entry to admit a cheap new one" pattern — for example, `RequestCache.NewRequest` simply rejects new requests once the cache is full rather than evicting existing ones: [3](#0-2) 
and `reapExpiredCallbacks` in the HTTP trigger handler only removes entries that are already past their TTL, not based on a size cap: [4](#0-3) 

The `savedCallbacks`/`pruneCallbacks` mechanism in `handler.go` is the one path in the reachable gateway code that reproduces the exact "size-bounded structure halves and silently drops legitimate waiting entries" bug class described in the report.

### Impact Explanation
If an unprivileged/external client (or a compromised low-trust workflow) can generate capability requests fast enough to exceed `MaxSavedCallbacks`, legitimate users' pending requests are silently evicted from `savedCallbacks` before their node response arrives. The evicted request's caller receives no aggregated response (or only a stale timeout later, if any), amounting to a denial-of-service / dropped-response condition for other users sharing the same gateway handler — a cross-user response-confusion/DoS impact consistent with the "unauthorized... cross-user response confusion" category in the validation criteria.

### Likelihood Explanation
Likelihood depends on how cheaply and quickly an actor can create `savedCallback` entries relative to `MaxSavedCallbacks`, and on the default value of that config (I was not able to fully read `handler.go`'s callback-creation path and the default `MaxSavedCallbacks`/`CallbackMaxAgeSec` values within the remaining tool budget, so exact request cost/rate needed to trigger repeated halving is unverified). The rate limiters seen elsewhere in the gateway (`ratelimit.RateLimiter`, per-sender/global) may mitigate but do not eliminate this if the cap is reachable within allowed rate limits or via many distinct senders.

### Recommendation
Replace the halve-on-overflow eviction in `pruneCallbacks` with a policy that does not penalize legitimately pending, unexpired entries — e.g., reject new callback creation once at capacity (mirroring `RequestCache.NewRequest`'s "cache is full" rejection) instead of evicting existing ones, or use strict per-sender/global rate limiting and quota enforcement before a request is allowed to occupy a `savedCallbacks` slot.

### Proof of Concept
The existing test in the repo already demonstrates the exploitable mechanics: with `MaxSavedCallbacks = 2`, inserting four callbacks (`a`,`b`,`c`,`d`) at increasing timestamps and calling `pruneCallbacks()` results in only the single newest entry (`d`) surviving — three older, still-live entries are unconditionally dropped. [1](#0-0) 
An attacker repeatedly issuing new capability requests (each allocating a new `savedCallback`) at a rate that keeps the map above `MaxSavedCallbacks` can use this mechanism to continuously evict other users'/nodes' legitimate pending callbacks.

// reapExpiredCallbacks removes callbacks that are older than the maximum age
func (h *httpTriggerHandler) reapExpiredCallbacks(ctx context.Context) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()
	now := time.Now()
	var expiredCount int
	for reqID, callback := range h.callbacks {
		if now.Sub(callback.createdAt) > time.Duration(h.config.CleanUpPeriodMs)*time.Millisecond {
			if !callback.processed {
				h.metrics.IncrementRequestErrors(ctx, jsonrpc.ErrInternal, h.lggr)
			}
			h.cleanupCallback(reqID)
			expiredCount++
		}
	}
	if expiredCount > 0 {
		h.metrics.IncrementPendingRequestsCleanUpCount(ctx, int64(expiredCount), h.lggr)
		h.lggr.Infow("Removed expired callbacks", "count", expiredCount, "remaining", len(h.callbacks))
	}
	h.metrics.RecordPendingRequestsCount(ctx, int64(len(h.callbacks)), h.lggr)
}
