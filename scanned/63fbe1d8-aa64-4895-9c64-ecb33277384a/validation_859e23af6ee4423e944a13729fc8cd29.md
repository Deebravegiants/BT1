### Title
Owner-label binding check for encrypted vault secrets can be skipped, allowing a client to submit ciphertext for one owner while declaring another owner - (File: core/capabilities/vault/gateway_vault_request_processor.go)

### Summary
`GatewayVaultRequestProcessor.processCreateSecretsRequest` / `processUpdateSecretsRequest` compute `skipLabelValidation := publicKey == nil` and pass it into `RequestValidator.ValidateEncryptedSecretsStructure`, which is the pre-authorization structural check run on every `MethodSecretsCreate`/`MethodSecretsUpdate` request coming from the public gateway. When `skipLabelValidation` is true, the validator calls `verifyEncryptedSecret` (structural-only check) instead of `EnsureRightLabelOnSecret`, which is the only routine that actually binds the ciphertext's embedded label to the `SecretIdentifier.Owner` claimed in the request. This mirrors the reported bug class: an invariant-preserving check (`_checkBalances` in the external report / `EnsureRightLabelOnSecret` here) is applied on some code paths but conditionally skipped on another, reachable, unprivileged-client path.

### Finding Description
`validateWriteRequest` in `core/capabilities/vault/validator.go` is the single choke point meant to guarantee that a caller cannot submit an `EncryptedSecret` whose embedded tdh2 label belongs to a different owner than the one declared in `SecretIdentifier.Owner`: [1](#0-0) 

The branch taken is controlled entirely by the `skipLabelValidation` flag. In the gateway-facing processor, that flag is derived solely from whether a `*tdh2easy.PublicKey` happens to be non-nil at the time of the call: [2](#0-1) [3](#0-2) 

This structural validation (`ValidateEncryptedSecretsStructure`) runs *before* authorization (`authorizeAndStamp`), i.e., on the unprivileged path directly reachable from any gateway client. The test file explicitly documents that when `publicKey` is nil, "label validation is skipped" and only structural checks apply: [4](#0-3) 

The same asymmetry is confirmed by the internal `Capability.CreateSecrets`/`UpdateSecrets` entrypoints, which hard-code `skipLabelValidation=false` regardless of whether the node's own cached public key (`s.publicKey.Get()`) is nil: [5](#0-4) 

This is precisely the pattern described in the external report: a validation routine (`_checkBalances`/`EnsureRightLabelOnSecret`) is invoked in one function (`_swap`/`Capability.CreateSecrets`) but bypassed in another reachable function (`_reserveTokenSpecified`/`GatewayVaultRequestProcessor.processCreateSecretsRequest` when `publicKey == nil`), producing an invariant violation — here, the invariant that "ciphertext label == declared owner" is not enforced.

### Impact Explanation
If the gateway-side `publicKey` cache is nil when a `SecretsCreate`/`SecretsUpdate` request arrives — the code comments call this out as a real possibility ("since it can be nil if the gateway nodes don't have the public key cached yet") — the pre-authorization structural check silently degrades to a check that no longer verifies label-to-owner binding. A caller could then submit an `EncryptedSecret` whose ciphertext label does not correspond to the `Owner` field they declare, and this decoupling passes the pre-auth gate. Because authorization for create/update is based on an allowlisted request digest tied to `Owner` (via `AllowListBasedAuth.AuthorizeRequest`), and because the label-binding check is the mechanism intended to prevent cross-owner ciphertext submission, skipping it under this condition risks cross-owner secret confusion (secrets stored/attributed under an owner whose label does not match the actual ciphertext binding).

### Likelihood Explanation
The `publicKey == nil` condition is not attacker-controlled directly, but it is a normal, documented runtime state (public key not yet cached on the gateway node) rather than a purely theoretical or operator-only condition, and the check is evaluated on every unauthenticated `SecretsCreate`/`SecretsUpdate` request before authorization. This makes the vulnerable branch reachable by any unprivileged gateway client during the window in which the node has not cached the master public key (e.g., at node startup or after key rotation).

### Recommendation
Do not tie `skipLabelValidation` to nil-ness of the public key alone. Either:
- Reject (or defer, returning a retryable error) `SecretsCreate`/`SecretsUpdate` requests when the public key is not yet available, instead of silently downgrading to structural-only validation, or
- Re-run `EnsureRightLabelOnSecret` unconditionally once the public key becomes available (e.g., inside `ValidateCiphertextSizes`, which already runs post-authorization) so that the label-to-owner binding is always enforced before a secret is persisted, regardless of the state of the pre-auth cache.

### Proof of Concept
1. Cause the gateway's cached `cachedMasterPublicKey` to be nil (e.g., node freshly started before the master public key sync completes).
2. Submit a `MethodSecretsCreate` request via `HandleGatewayMessage` with an `EncryptedSecret` whose `SecretIdentifier.Owner` is attacker-controlled but whose ciphertext label was generated for a different owner.
3. `processCreateSecretsRequest` computes `skipLabelValidation := publicKey == nil` → `true`, and `ValidateEncryptedSecretsStructure` calls `verifyEncryptedSecret` instead of `EnsureRightLabelOnSecret`, so the owner/label mismatch is not detected at this stage: [6](#0-5) 
4. The request proceeds to `authorizeAndStamp` and, if the digest is allowlisted, to `ValidateCiphertextSizes` (size-only check), with no subsequent re-check of label/owner binding.

func (p *GatewayVaultRequestProcessor) processCreateSecretsRequest(
	ctx context.Context,
	req *jsonrpc.Request[json.RawMessage],
	publicKey *tdh2easy.PublicKey,
) (*AuthorizedGatewayVaultRequest, error) {
	if req.Params == nil {
		return nil, InvalidVaultParamsError{Method: req.Method, Err: errors.New("request params must not be nil")}
	}

	var createReq vaultcommon.CreateSecretsRequest
	if err := json.Unmarshal(*req.Params, &createReq); err != nil {
		return nil, InvalidVaultParamsError{Method: req.Method, Err: err}
	}
	if p.stripOwnerPrefixForAuth {
		createReq.RequestId = req.ID
		if err := marshalVaultParams(req, &createReq); err != nil {
			return nil, InvalidVaultParamsError{Method: req.Method, Err: err}
		}
	} else {
		createReq.RequestId = coalesceRequestID(createReq.RequestId, req.ID)
	}

	skipLabelValidation := publicKey == nil
	if err := p.validator.ValidateEncryptedSecretsStructure(ctx, publicKey, createReq.RequestId, createReq.EncryptedSecrets, skipLabelValidation); err != nil {
		return nil, p.validationError(req, err)
	}

func (s *Capability) CreateSecrets(ctx context.Context, request *vaultcommon.CreateSecretsRequest) (*vaulttypes.Response, error) {
	s.lggr.Debugw("received create secrets request", "requestID", request.RequestId, "request", request.String())
	if err := validateEncryptedSecretsUniformOwners(request.EncryptedSecrets); err != nil {
		return nil, err
	}
	err := s.ValidateCreateSecretsRequest(ctx, s.publicKey.Get(), request, false)
	if err != nil {
		s.lggr.Debugw("failed validation checks", "requestID", request.RequestId, "err", err)
		return nil, err
	}
	return s.handleRequest(ctx, request.RequestId, request)
}

func (s *Capability) UpdateSecrets(ctx context.Context, request *vaultcommon.UpdateSecretsRequest) (*vaulttypes.Response, error) {
	s.lggr.Debugw("received update secrets request", "requestID", request.RequestId, "request", request.String())
	if err := validateEncryptedSecretsUniformOwners(request.EncryptedSecrets); err != nil {
		return nil, err
	}
	err := s.ValidateUpdateSecretsRequest(ctx, s.publicKey.Get(), request, false)
	if err != nil {
		s.lggr.Debugw("failed validation checks", "requestID", request.RequestId, "err", err)
		return nil, err
	}
	return s.handleRequest(ctx, request.RequestId, request)
}
