### Title
Login Endpoint Reveals Account Existence Through Differential Error Messages - (File: core/sessions/localauth/orm.go)

### Summary
The `/sessions` login endpoint (`SessionsController.Create`) forwards raw authentication error messages from the credential-check pipeline in `CreateSession` directly to unauthenticated clients. Although the HTTP status code is uniformly `401`, the *message text* differs depending on whether the supplied email is registered, allowing an unauthenticated caller to enumerate valid accounts — the same bug class as CVE-2026-24468 (differential response revealing account existence), just carried in the response body instead of the status code.

### Finding Description
`SessionsController.Create` accepts unauthenticated login attempts and passes any error from `AuthenticationProvider().CreateSession` straight through to the client via `jsonAPIError(c, http.StatusUnauthorized, err)`: [1](#0-0) 

In the local-auth implementation, `CreateSession` first resolves the user by email with `FindUser`, and if that lookup fails, returns that lookup's error unmodified — before ever reaching the "Invalid password" branch: [2](#0-1) 

The local ORM's other lookup helpers (e.g. `TestPassword`) consistently emit a distinct string, `"no matching user for provided email"`, when an email is not present in the `users` table, versus `"passwords don't match"` for existing accounts with an incorrect password: [3](#0-2) 

`CreateSession` itself emits `"Invalid email"` for a non-existent/mismatched email and `"Invalid password"` for an existing account with a wrong password: [4](#0-3) 

Because these two distinct messages are surfaced verbatim to the caller under the same `401` status code, an attacker submitting a login attempt can distinguish "email unknown" from "email known, password wrong" purely from response body content — an observable differential exactly analogous to the OpenAEV `/api/reset` enumeration bug, just implemented via message text rather than status code.

The LDAP and OIDC authenticator variants exhibit the same pattern via their own `localLoginFallback`/`CreateSession` implementations, which also emit `"invalid email"` vs `"invalid password"` distinctly: [5](#0-4) [6](#0-5) 

Notably, the code already contains a deliberate mitigation for a *related* leak — ordering the email/password check before the WebAuthn/MFA lookup specifically "to prevent extra database look up for MFA tokens leaking if an account has MFA tokens or not": [7](#0-6) 
This shows the team is aware of enumeration-style leaks in this exact code path, but the email-vs-password message distinction was not addressed.

### Impact Explanation
An unauthenticated attacker can enumerate valid node-operator/API-user email addresses registered on a Chainlink node by observing whether the login response says "Invalid email" or "Invalid password" (or "no matching user for provided email" via related surfaces). This does not itself grant access, but materially aids credential-stuffing, phishing, and targeted brute-force attacks against a Chainlink node's admin/API accounts, which control job runs, keys, and chain interactions. Impact is limited to information disclosure (no direct auth bypass or fund movement), consistent with the CVSS 5.3 "confidentiality-only" rating of the referenced CVE.

### Likelihood Explanation
The `/sessions` endpoint is unauthenticated and internet-facing by design (it is the login endpoint), requiring no privileges to reach. Exploitation only requires sending POST requests with different email guesses and inspecting the JSON error body — no timing analysis or advanced tooling needed, making likelihood high for any node with rate-limiting not otherwise deployed at the network edge.

### Recommendation
Return a single, generic error message and status code (e.g., "invalid credentials", `401`) for all authentication failure branches in `CreateSession` (local, LDAP, OIDC implementations), regardless of whether the failure occurred at email lookup, password check, or role resolution. Ensure `SessionsController.Create` does not propagate distinguishing internal error text to the HTTP response, and consider adding uniform artificial delay/timing already partially addressed for MFA lookups to also cover the FindUser-vs-password-check paths.

### Proof of Concept
1. POST to `/sessions` with `{"email": "known-admin@example.com", "password": "wrong"}` → response body contains `"Invalid password"`.
2. POST to `/sessions` with `{"email": "nonexistent@example.com", "password": "wrong"}` → response body contains `"Invalid email"` (or `"no matching user for provided email"` from related lookup paths).
3. Both requests return HTTP `401`, but the differing message text lets an attacker script account enumeration by iterating candidate emails and checking for `"Invalid password"` vs `"Invalid email"` in the JSON API error response.

```go
func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}
```

```go
// TestPassword checks plaintext user provided password with hashed database password, returns nil if matched
func (o *orm) TestPassword(ctx context.Context, email string, password string) error {
	var hashedPassword string
	if err := o.ds.GetContext(ctx, &hashedPassword, "SELECT hashed_password FROM users WHERE lower(email) = lower($1)", email); err != nil {
		return pkgerrors.New("no matching user for provided email")
	}
	if !utils.CheckPasswordHash(password, hashedPassword) {
		return pkgerrors.New("passwords don't match")
	}
	return nil
}
```

```go
func (l *ldapAuthenticator) localLoginFallback(ctx context.Context, sr sessions.SessionRequest) (sessions.User, error) {
	var user sessions.User
	sql := "SELECT * FROM users WHERE lower(email) = lower($1)"
	err := l.ds.GetContext(ctx, &user, sql, sr.Email)
	if err != nil {
		return user, err
	}
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		l.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})

	}
```
