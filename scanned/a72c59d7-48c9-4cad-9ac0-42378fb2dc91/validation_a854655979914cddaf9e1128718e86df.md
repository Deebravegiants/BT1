## Analog Found: Unauthenticated `/v2/resume/:runID` endpoint allows anyone to finalize another party's pending pipeline task

### Title
Unauthenticated pipeline task resume endpoint lets any anonymous caller inject a result/error and finalize another user's suspended job run - (File: core/web/pipeline_runs_controller.go)

### Summary
The Sherlock finding for `CrabNetting.checkOrder()` is a class of bug where a state-mutating function that should only be actionable by the resource's owner (or an internal system) is instead exposed with no access control, letting any caller consume/invalidate/finalize another party's pending state. Chainlink's `PipelineRunsController.Resume` handler exhibits the same pattern: it is deliberately mounted on the unauthenticated router group and accepts an arbitrary `runID` (task UUID) plus an arbitrary result payload from the request body, with no check that the caller is the legitimate external adapter/bridge that is supposed to complete that specific task.

### Finding Description
The route is registered without any of the auth middlewares applied to the rest of the v2 API: [1](#0-0) 

```go
unauthedv2 := r.Group("/v2")
...
unauthedv2.PATCH("/resume/:runID", prc.Resume)

authv2 := r.Group("/v2", auth.Authenticate(app.AuthenticationProvider(),
    auth.AuthenticateByToken,
    auth.AuthenticateBySession,
))
```

The handler itself performs no ownership or capability check on the supplied task UUID before mutating pipeline state: [2](#0-1) 

`Resume` parses `taskID` straight from the URL param, decodes a JSON body into a `pipeline.ResumeRequest`, and calls `prc.App.ResumeJobV2(ctx, taskID, result)` — which flows into `runner.ResumeRun`, updating the stored task-run result and restarting the suspended pipeline run: [3](#0-2) 

The only concurrency protection that exists is a DB row lock intended to prevent *races* between two resumers, not to verify *who* is allowed to resume a given task: [4](#0-3) 

This mirrors the `checkOrder()` bug exactly: a public, unauthenticated function takes an identifier (nonce/order hash in the Solidity case, task UUID here) supplied entirely by the caller and uses it to finalize/consume state that belongs to a specific, different actor (the trader who signed the order / the external adapter that owns the suspended bridge task), with no signature, API key, or external-initiator credential check tying the caller to that identifier.

### Impact Explanation
Any external caller who learns or guesses a task UUID (these are returned to the client as part of async bridge/webhook task responses handled by `pipeline` bridge tasks, and can also be observed via logs, metrics, or timing/enumeration in low-entropy deployments) can:
- Submit a fabricated result/error for that task before the legitimate external adapter's real answer arrives, causing the job run to complete with attacker-controlled data (result/error injection into an oracle pipeline).
- Cause a denial of service by "consuming" the resume slot with garbage data, since once a run is resumed (`restart = true` and result stored), the true callback from the legitimate external adapter can no longer take effect for that same task run.

This is a High-severity analog: it allows request impersonation / cross-user response confusion, and can lead to fund-relevant outcomes if the affected job feeds price data or triggers on-chain transactions, similar in class to the reported unauthorized cancellation of trading orders.

### Likelihood Explanation
Likelihood is High for guessable/leaked UUIDs and moderate in general: task IDs are UUIDv4 (128-bit), so blind guessing is infeasible, but the endpoint is reachable by anyone with network access to the node's API (no auth token, no external-initiator header needed), and the UUID is routinely transmitted to third parties (the external adapter itself, logs, and potentially exposed via response payloads/webhooks) as part of normal async task completion flow — any leak of that identifier (e.g., via a compromised/malicious adapter, log exposure, or a race with the legitimate response) is sufficient for exploitation, exactly as in the report where knowledge of a signed `Order`/nonce was sufficient to invalidate it.

### Recommendation
Add authorization to the resume flow analogous to how `AuthenticateExternalInitiator`/API-token auth is applied elsewhere in the router: require the caller to present a secret bound to the specific task (e.g., a per-task HMAC/token minted when the task is suspended and returned only to the bridge/external adapter that must complete it), and verify that secret in `Resume` before calling `ResumeJobV2`. At minimum, treat the current design as intentionally "unauthenticated but requires an unguessable random ID," and audit all code paths (logging, webhooks, bridge responses) to ensure the task UUID used for resume is never leaked to any party other than the intended external adapter.

### Proof of Concept
1. Create a job with a bridge (external adapter) task that suspends pending an async response, causing the pipeline run to persist with `state = suspended` and a `pipeline_task_runs` row keyed by a task UUID (see `StoreRun`) [5](#0-4) .
2. Obtain the task UUID for that pending run (e.g., logged output, or attacker-controlled/compromised "external adapter" endpoint that receives the callback URL containing the UUID).
3. Before the legitimate external adapter responds, send an unauthenticated request:
   ```
   PATCH /v2/resume/<task-uuid>
   Content-Type: application/json

   {"error": "malicious result injected"}
   ```
   This hits `unauthedv2.PATCH("/resume/:runID", prc.Resume)` with zero credentials [6](#0-5) .
4. `Resume` decodes the body and calls `App.ResumeJobV2` → `runner.ResumeRun` → `orm.UpdateTaskRunResult`, storing the attacker-supplied value/error and restarting the run, finalizing it with attacker-controlled data instead of the legitimate adapter's response [7](#0-6) [3](#0-2) .

// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
}

// StoreRun will persist a partially executed run before suspending, or finish a run.
// If `restart` is true, then new task run data is available and the run should be resumed immediately.
func (o *orm) StoreRun(ctx context.Context, run *Run) (restart bool, err error) {
	err = o.transact(ctx, func(tx *orm) error {
		finished := run.FinishedAt.Valid
		if !finished {
			// Lock the current run. This prevents races with /v2/resume
			sql := `SELECT id FROM pipeline_runs WHERE id = $1 FOR UPDATE;`
			if _, err = tx.ds.ExecContext(ctx, sql, run.ID); err != nil {
				return fmt.Errorf("failed to select pipeline run %d: %w", run.ID, err)
			}

			taskRuns := []TaskRun{}
			// Reload task runs, we want to check for any changes while the run was ongoing
			if err = tx.ds.SelectContext(ctx, &taskRuns, `SELECT * FROM pipeline_task_runs WHERE pipeline_run_id = $1`, run.ID); err != nil {
				return fmt.Errorf("failed to select piepline task run %d: %w", run.ID, err)
			}

			// Construct a temporary run so we can use r.ByDotID
			tempRun := Run{PipelineTaskRuns: taskRuns}

			// Diff with current state, if updated, swap run.PipelineTaskRuns and early return with restart = true
			for i, tr := range run.PipelineTaskRuns {
				if !tr.IsPending() {
					continue
				}

				// Look for new data
				if taskRun := tempRun.ByDotID(tr.DotID); taskRun != nil && !taskRun.IsPending() {
					// Swap in the latest state
					run.PipelineTaskRuns[i] = *taskRun
					restart = true
				}
			}

			if restart {
				return nil
			}

			// Suspend the run
			run.State = RunStatusSuspended
			if _, err = tx.ds.NamedExecContext(ctx, `UPDATE pipeline_runs SET state = :state WHERE id = :id`, run); err != nil {
				return fmt.Errorf("failed to update pipeline run %d to %s: %w", run.ID, run.State, err)
			}
