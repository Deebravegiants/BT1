### Title
GatewayHandler node-side vault master public key is cached permanently and never refreshed - ([File: core/capabilities/vault/gw_handler.go])

### Summary
The node-side `GatewayHandler.getMasterPublicKey` fetches the vault's master TDH2 public key from the `secretsService` exactly once and caches it forever in `h.cachedMasterPublicKey`, with no TTL, invalidation, or refresh path. This is the same bug class as the report: a value obtained from an external/authoritative source at initialization time is cached and never re-fetched even though the source can legitimately change it later, so the node keeps operating against a stale value indefinitely.

### Finding Description
`GatewayHandler.getMasterPublicKey` in `core/capabilities/vault/gw_handler.go` implements a "fetch-once, cache-forever" pattern: [1](#0-0) 

Once `h.cachedMasterPublicKey` is populated (on the first `MethodSecretsCreate`/`MethodSecretsUpdate` request), every subsequent call returns the cached copy directly under a read lock, and the underlying `MasterPublicKeyFromSecretsService` call is never invoked again for the lifetime of the process: [2](#0-1) 

This public key is used by `requestProcessor.ProcessRequest` to validate/verify the TDH2-encrypted secret payloads submitted in create/update requests, so it functions as an authoritative, security-relevant reference value that all future encrypt/decrypt operations depend on for the lifetime of the node process.

By contrast, the gateway-side vault handler (`core/services/gateway/handlers/vault/handler.go`) treats the same value as something that must be periodically re-fetched: it runs a dedicated background ticker (`tickerVaultPublicKeyRefresh`, default 1 minute) that calls `fetchVaultPublicKey` to keep the cached public key current, and it separately hardens the node-response-derived cache path against spoofed/attacker-controlled keys: [3](#0-2) [4](#0-3) 

The node-side `GatewayHandler`, in the same vault subsystem, has no equivalent refresh mechanism at all — this asymmetry is the strongest indicator that the permanent cache in `gw_handler.go` is an oversight rather than an intentional invariant (i.e., there is no code path or comment asserting the master key is immutable for the process lifetime; the sibling component explicitly assumes it can/should be refreshed).

### Impact Explanation
If the underlying secrets service ever legitimately rotates or re-derives the master public key (e.g. key backend restart, re-keying, tenant/master key regeneration performed by `secretsService`), the node's `GatewayHandler` will keep validating/encrypting all subsequent `SecretsCreate`/`SecretsUpdate` requests against the old, now-incorrect public key. Depending on how `ProcessRequest` treats a public-key mismatch, this manifests as either (a) persistent request failures (availability/DoS for legitimate create/update operations on that node) or (b) requests being processed against a public key that no longer corresponds to the DON's actual decryption key shares, corrupting stored secrets so they can never be decrypted correctly later. Both outcomes match the "Medium" severity class of the reference finding (protocol continuing to operate on stale critical state after the authoritative value changed), though here the concrete consequence is closer to secret-store corruption/availability loss for legitimate users than a straightforward authentication bypass.

### Likelihood Explanation
This is only reachable if the vault's master public key is expected to change at runtime after the node process has already served at least one create/update request. I was not able to fully confirm within the available index whether `secretsService.GetPublicKey` (backing `MasterPublicKeyFromSecretsService`) is designed to return a mutable value over the node's lifetime, or whether the master key is fixed for the life of a deployment (in which case this cache would be benign by design). The presence of an explicit, actively-maintained refresh ticker in the sibling gateway-side handler for the exact same value is circumstantial evidence that key rotation/refresh is a real operational concern in this subsystem, but I could not verify a concrete operational trigger (e.g., a documented key-rotation procedure) that would cause the master key to change while a `GatewayHandler` process is running.

### Recommendation
Mirror the gateway-side handler's approach: add a TTL-based or periodic refresh for `cachedMasterPublicKey` in `GatewayHandler` (e.g., a background ticker calling `MasterPublicKeyFromSecretsService` at a bounded interval, or invalidating the cache after a max age), instead of caching the first fetched value indefinitely. At minimum, expose an explicit invalidation hook so that if the secrets service backend is known to rotate the master key, the cached value can be forced to refresh rather than silently going stale.

### Proof of Concept
1. Start a node with `GatewayHandler` wired to a `secretsService` whose `GetPublicKey` returns public key `PK1`.
2. Issue a `MethodSecretsCreate` request; `getMasterPublicKey` fetches and caches `PK1` in `h.cachedMasterPublicKey`.
3. Rotate/replace the master key on the `secretsService` backend so subsequent `GetPublicKey` calls would return `PK2`.
4. Issue another `MethodSecretsCreate`/`MethodSecretsUpdate` request encrypted client-side against `PK2`. `getMasterPublicKey` returns the stale cached `PK1` (line 240-244 of `gw_handler.go`), causing `requestProcessor.ProcessRequest` to validate against the wrong key — request processing fails or, depending on validator behavior, produces state inconsistent with the DON's actual current key shares — with no code path in `GatewayHandler` ever re-fetching `PK2`.

func (h *GatewayHandler) getMasterPublicKey(ctx context.Context) (*tdh2easy.PublicKey, error) {
	h.mu.RLock()
	if h.cachedMasterPublicKey != nil {
		cachedCopy := *h.cachedMasterPublicKey
		h.mu.RUnlock()
		return &cachedCopy, nil
	}
	h.mu.RUnlock()

	publicKey, err := MasterPublicKeyFromSecretsService(ctx, h.secretsService)
	if err != nil {
		return nil, err
	}

	h.mu.Lock()
	defer h.mu.Unlock()
	if h.cachedMasterPublicKey != nil {
		cachedCopy := *h.cachedMasterPublicKey
		return &cachedCopy, nil
	}
	h.cachedMasterPublicKey = publicKey
	cachedCopy := *publicKey
	return &cachedCopy, nil
}

func (h *handler) fetchVaultPublicKey(ctx context.Context) {
	ctx, cancel := context.WithDeadline(ctx, h.clock.Now().Add(10*time.Second))
	defer cancel()
	param := vaultcommon.GetPublicKeyRequest{}
	paramBytes, err := json.Marshal(param)
	if err != nil {
		h.lggr.Errorw("fetchVaultPublicKey: failed to marshal get public key request", "error", err)
		return
	}
	getPublicKeyRequest := jsonrpc.Request[json.RawMessage]{
		Version: jsonrpc.JsonRpcVersion,
		ID:      uuid.New().String(),
		Method:  vaulttypes.MethodPublicKeyGet,
		Params:  (*json.RawMessage)(&paramBytes),
	}
	h.lggr.Debugw("fetchVaultPublicKey: trying to fetch vault public key", "request", getPublicKeyRequest)
	callback := handlerscommon.NewCallback()
	ar, err := h.newActiveRequest(getPublicKeyRequest, callback)
	if err != nil {
		h.lggr.Errorw("fetchVaultPublicKey: failed to create new activeRequest", "error", err)
		return
	}
	err = h.handlePublicKeyGet(ctx, ar)
	if err != nil {
		h.lggr.Errorw("fetchVaultPublicKey: failed to fetch vault public key", "request", getPublicKeyRequest, "error", err)
		return
	}
	response, err := callback.Wait(ctx)
	if err != nil {
		h.lggr.Errorw("fetchVaultPublicKey: failed to fetch vault public key", "request", getPublicKeyRequest, "error", err)
		return
	}
	httpStatus := api.ToHTTPErrorCode(response.ErrorCode)
	jsonCodec := api.JSONRPCCodec{}
	jsonResp, _ := jsonCodec.DecodeRawRequest(response.RawResponse, "")
	if httpStatus != http.StatusOK {
		h.lggr.Errorw("fetchVaultPublicKey: failed to fetch vault public key", "request", getPublicKeyRequest, "httpStatusCode", httpStatus, "rawResponse", jsonResp)
		return
	}
	h.lggr.Debugw("fetchVaultPublicKey: successfully fetched vault public key", "request", getPublicKeyRequest, "rawResponse", jsonResp)
}
