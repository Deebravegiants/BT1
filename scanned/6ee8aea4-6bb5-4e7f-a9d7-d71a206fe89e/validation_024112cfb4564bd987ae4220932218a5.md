### Title
LDAP Session/Auth Empty-Password Bind Bypass - (File: core/sessions/ldapauth/ldap.go)

### Summary
The LDAP authentication provider forwards a user-supplied `SessionRequest.Password` (and `TestPassword`'s `password` argument) directly into an LDAP Simple Bind call without ever checking that the value is non-empty. Per RFC 4513 §5.1.2, a Simple Bind performed with a non-empty DN and an empty password is defined as an "unauthenticated bind," and many LDAP servers return a success result code for it rather than rejecting it. If the configured upstream LDAP server exhibits this common behavior, `conn.Bind()` returns `nil` (no error) for any valid user DN combined with an empty password string, letting the caller obtain a fully authenticated session or pass `TestPassword` for an arbitrary known email with no real credential.

### Finding Description
`(*ldapAuthenticator).CreateSession` builds a bind DN from the attacker-controlled email and calls the bind with the attacker-controlled password verbatim: [1](#0-0) 
There is no check anywhere in this function, nor in `sessions.SessionRequest` (`Password string \`json:"password"\`` has no length/omitempty/min constraint), nor in the HTTP handler that binds the JSON body, that rejects an empty-string password before it reaches the bind call: [2](#0-1) [3](#0-2) 
The same unguarded pattern exists in `TestPassword`, used to re-verify a logged-in user before issuing a new API token: [4](#0-3) 
If the bind succeeds (empty-password unauthenticated bind accepted by the LDAP server), `CreateSession` proceeds to call `FindUser` for the role and inserts a fully valid `ldap_sessions` row, returning a session ID that the web layer sets as an authenticated cookie: [5](#0-4) 
This mirrors exactly the bug class in CVE-2026-44551: an LDAP client library performing a Simple Bind without validating that the submitted password is non-empty, relying entirely on the LDAP server to reject the bind.

### Impact Explanation
An unauthenticated network client who knows (or guesses) a valid user's email address registered in the LDAP directory can submit `POST /sessions` with that email and an empty `password` field. If the configured upstream LDAP server treats empty-password binds as unauthenticated-but-successful binds (a common, RFC-permitted, frequently-misconfigured behavior), Chainlink will issue that user a valid session cookie or API token with that user's role — including Admin, if an admin's email is known. This is a full authentication bypass leading to session/token issuance for an arbitrary account, i.e., unauthorized privilege escalation and request impersonation from an unprivileged actor.

### Likelihood Explanation
Likelihood depends entirely on the deployed LDAP server's handling of unauthenticated binds. Since Chainlink's LDAP driver does not add any password-emptiness safeguard of its own (unlike the local/OIDC drivers, which hash-compare the password and therefore inherently reject an empty string against any non-empty hash), the application places full trust in the upstream server's bind semantics. Any operator using a standard-compliant or default-configured LDAP/AD server that permits unauthenticated binds (a documented, non-exotic configuration, and one that RFC 4513 explicitly allows unless a server disables it) would be exposed. This is directly analogous, and root-caused the same way, as the reported Open WebUI CVE.

### Recommendation
Add an explicit guard in `ldapAuthenticator.CreateSession` and `TestPassword` (and ideally at the `SessionRequest` binding layer) to reject empty or whitespace-only passwords before ever calling `conn.Bind()`, e.g.:
```go
if strings.TrimSpace(sr.Password) == "" {
    return "", errors.New("password must not be empty")
}
```
Apply the same check in `TestPassword` before the bind call at `core/sessions/ldapauth/ldap.go:514`.

### Proof of Concept
1. Configure `WebServer.LDAP` against an LDAP server that permits unauthenticated binds for a bind DN with an empty password (default/permissive OpenLDAP or AD configuration).
2. As an unauthenticated client, `POST /sessions` with body `{"email":"admin@example.com","password":""}`.
3. `conn.Bind(dn, "")` at [6](#0-5)  succeeds (unauthenticated bind, no error), `FindUser` resolves the admin's role, and a valid `ldap_sessions` row/cookie is issued for the admin account without ever knowing the real password.

// TestPassword tests if an LDAP login bind can be performed with provided credentials, returns nil if success
func (l *ldapAuthenticator) TestPassword(ctx context.Context, email string, password string) error {
	conn, err := l.ldapClient.CreateEphemeralConnection()
	if err != nil {
		return errors.New("unable to establish connection to LDAP server with provided URL and credentials")
	}
	defer conn.Close()

	// Attempt to LDAP Bind with user provided credentials
	escapedEmail := ldap.EscapeFilter(strings.ToLower(email))
	searchBaseDN := fmt.Sprintf("%s=%s,%s,%s", l.config.BaseUserAttr(), escapedEmail, l.config.UsersDN(), l.config.BaseDN())
	err = conn.Bind(searchBaseDN, password)
	if err == nil {
		return nil
	}
	l.lggr.Infof("Error binding user authentication request in TestPassword call LDAP Bind: %v", err)

	// Fall back to test local users table in case of supported local CLI users as well
	var hashedPassword string
	if err := l.ds.GetContext(ctx, &hashedPassword, "SELECT hashed_password FROM users WHERE lower(email) = lower($1)", email); err != nil {
		return errors.New("invalid credentials")
	}
	if !utils.CheckPasswordHash(password, hashedPassword) {
		return errors.New("invalid credentials")
	}

	return nil
}
