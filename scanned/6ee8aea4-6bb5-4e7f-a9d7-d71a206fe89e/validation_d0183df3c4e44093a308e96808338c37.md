### Title
Global, caller-unscoped request-ID cache in the HTTP Trigger Handler lets any unprivileged workflow caller collide with and block another caller's trigger request - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

### Summary
The Sherlock finding shows that Perennial's `BalancedVault.deposit` lets *anyone* mutate state keyed only by an `account` parameter (with no check that `msg.sender == account`), so an attacker can grief a victim's deposit epoch by depositing dust "for" them. The reachable chainlink analog is the HTTP Trigger Handler's request de-duplication cache, which is keyed purely by the caller-supplied `req.ID` string with no binding to the authenticated workflow owner, so an unrelated unprivileged caller can occupy another user's request ID and force their legitimate request into the `ErrConflict` path.

### Finding Description
`httpTriggerHandler` stores in-flight/aggregated requests in a single process-wide map: [1](#0-0) 

`HandleUserTriggerRequest` validates the trigger payload, resolves the workflow, authorizes the caller, and checks rate limits, but the only constraint placed on `req.ID` before it is used as the sole dedup key is that it is non-empty and does not contain `/`: [2](#0-1) [3](#0-2) 

Authorization (`authorizeRequest`) validates that the caller's JWT is valid *for the workflow they name in the request*, but it does not tie the `req.ID` namespace to that owner/workflow — the map lookup that decides "conflict" vs "proceed" is keyed solely on the string `req.ID`, as confirmed by the existing test that reproduces the `ErrConflict` path: [4](#0-3) 

Because any authenticated (but otherwise unprivileged, unrelated) caller can trigger *some* workflow they are authorized for, they can choose an arbitrary `req.ID` value. If that value happens to coincide with (or is deliberately front-run against) another caller's chosen `req.ID` — which is entirely client-selected and commonly predictable (sequential counters, fixed strings, timestamps, etc.) — the second request to arrive is rejected with a conflict error, exactly mirroring the underlying bug class in the report: an unprivileged actor mutating/consuming a shared resource keyed by an identifier they don't own, delaying or denying processing for the rightful caller.

### Impact Explanation
A legitimate user's HTTP-triggered workflow execution can be denied service by an unrelated, unprivileged caller who merely needs a valid trigger request of their own (for any workflow) and knowledge/guess of the victim's chosen request ID. This blocks execution of that specific request (`jsonrpc.ErrConflict`), which for time-sensitive or single-shot workflow triggers is a meaningful availability/DOS impact, analogous to the "permanently delayed deposit" impact in the source report.

### Likelihood Explanation
Likelihood is moderate: the attacker must control an authorized trigger request for some workflow (a low bar — the gateway accepts JWT-signed triggers for any workflow the caller is entitled to invoke) and must guess/know the victim's `req.ID`. Many client integrations use low-entropy or predictable IDs (incrementing counters, fixed strings such as `"1"`, timestamps), which materially raises the practical likelihood of collision or targeted front-running versus a purely random-ID scenario.

### Recommendation
Scope the trigger-request dedup/callback cache key to the authenticated caller identity (e.g., combine `workflowOwner`/`workflowID` with `req.ID`, similar to how the Vault gateway handler prefixes/rewrites request IDs with the authorized owner) rather than trusting the raw, client-supplied `req.ID` as a global namespace. This closes the cross-caller collision so one unprivileged caller cannot occupy or race another caller's request identifier.

### Proof of Concept
1. Caller B has valid JWT authorization to trigger Workflow B and knows (or guesses) that Caller A commonly uses request ID `"1"` for their trigger calls to Workflow A.
2. Caller B does not need permission on Workflow A; they only need `callbacks["1"]` to be populated before Caller A's real request arrives — for instance, by targeting a shared/predictable ID scheme, or by winning a race on a commonly-used literal ID.
3. Caller A's legitimate trigger request with `req.ID == "1"` reaches `HandleUserTriggerRequest` after Caller B's entry occupies the global `callbacks` map slot for that ID.
4. `setupCallback` (keyed only by `req.ID` per the map declaration `callbacks map[string]savedCallback // requestID -> savedCallback`) rejects Caller A's request with an `ErrConflict`-style error, as demonstrated by the existing "duplicate request ID" test that reproduces this exact rejection path. [4](#0-3)

func (h *httpTriggerHandler) HandleUserTriggerRequest(ctx context.Context, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback, requestStartTime time.Time) error {
	triggerReq, err := h.validatedTriggerRequest(ctx, req, callback)
	if err != nil {
		return err
	}

	workflowID, err := h.resolveWorkflowID(ctx, triggerReq, req.ID, callback)
	if err != nil {
		return err
	}

	key, err := h.authorizeRequest(ctx, workflowID, req, callback)
	if err != nil {
		return err
	}

	if err = h.checkRateLimit(ctx, workflowID, req.ID, callback); err != nil {
		return err
	}

	strippedWorkflowID := strings.TrimPrefix(workflowID, "0x")
	legacyExecutionID, err := workflows.EncodeExecutionID(strippedWorkflowID, req.ID) //nolint:staticcheck // legacy ID kept for observability comparison
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID: " + err.Error())
	}
	// Workflows shouldn't use more than one HTTP trigger. If we ever need to support multiple triggers, we'd need to pass
	// trigger index to the Gateway handler and somehow allow senders to pick. For now, we use trigger index 0.
	// Execution IDs here are used only for logging.
	executionIDWithTriggerIndex, err := workflows.GenerateExecutionIDWithTriggerIndex(strippedWorkflowID, req.ID, 0)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID with trigger index: " + err.Error())
	}
	h.lggr.Debugw("processing request",
		"legacyExecutionID", legacyExecutionID,
		"executionIDWithTriggerIndex", executionIDWithTriggerIndex,
		"requestID", req.ID,
		"workflowID", workflowID)

	reqWithKey, err := reqWithAuthorizedKey(triggerReq, *key)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error marshaling trigger request: " + err.Error())
	}

	doneCh, err := h.setupCallback(ctx, req.ID, callback, requestStartTime, workflowID)
	if err != nil {
		return err
	}

	return h.sendWithRetries(ctx, legacyExecutionID, executionIDWithTriggerIndex, reqWithKey, workflowID, doneCh)
}

func (h *httpTriggerHandler) validateRequestID(ctx context.Context, requestID string, callback handlers.Callback) error {
	if requestID == "" {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "'id' field is required and cannot be empty. Use a new unique request 'id' for each request", callback)
		return errors.New("empty request ID")
	}
	// Request IDs from users must not contain "/", since this character is reserved
	// for internal node-to-node message routing (e.g., "http_action/{workflowID}/{uuid}").
	if strings.Contains(requestID, "/") {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "request ID must not contain '/'", callback)
		return errors.New("request ID must not contain '/'")
	}
	return nil
}
