target=ShopifyAPI::Webhooks::Registry.process; ShopifyAPI::Webhooks::Request#to_signable_string. Attacker action: attacker's own dev shop receives one legitimately signed webhook POST (body B, X-Shopify-Hmac-Sha256 valid for B) at their own registered endpoint; attacker replays the identical body+HMAC header but substitutes X-Shopify-Topic: 'app/uninstalled' -> 'customers/data_request' and X-Shopify-Shop-Domain: 'attacker-shop.myshopify.com' -> 'victim-shop.myshopify.com' to the same app endpoint. Preconditions: app uses ShopifyAPI::Webhooks::Registry.process as documented, HmacValidator configured with the real Context.api_secret_key, attacker's dev shop is a legitimate Shopify install. Call sequence: Request.new(raw_body: B, headers: forged_headers) -> Registry.process(request) -> Utils::HmacValidator.validate(request) passes because it only recomputes HMAC over @raw_body -> handler = @registry[request.topic] resolves to victim topic handler -> handler.handle(WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)). Binding that breaks: shop_and_topic_authenticated_by_hmac(over raw_body only) != shop_and_topic_acted_on_by_handler(request.topic, request.shop from unsigned headers). Impact: Critical, cross-tenant access - handler mutates records keyed to 'victim-shop.myshopify.com' using an attacker-controlled event, on the victim's tenant data. Proof idea: minitest + WebMock-free unit test constructing Request with a valid HMAC for a given raw_body computed against a stub Context.api_secret_key, then swapping only the shop-domain/topic headers and asserting HmacValidator.validate still returns true and Registry.process dispatches to the swapped topic/shop.
