OIDC callback `state` parameter compared with non-constant-time `!=` operator, enabling a timing side-channel in `handleTokenExchange` - (File: core/sessions/oidcauth/oidc.go)

### Summary
The Go implementation of the OIDC login flow in `handleTokenExchange` validates the anti-CSRF/replay `state` parameter using Go's built-in `!=` string comparison instead of a constant-time comparison, mirroring the exact bug class described in CVE-2023-50708 (yii2-authclient comparing OAuth1/2 `state`/`nonce` with regular string comparison instead of `compareString()`).

### Finding Description
`handleSignIn` generates a random `state` value and stores it server-side in the session [1](#0-0) . When the identity provider redirects back, `handleTokenExchange` reads the client-supplied `state` from the JSON body and compares it against the session-stored value using a short-circuiting, byte-by-byte `!=` operator: [2](#0-1) 

Go's native string `!=` comparison returns as soon as it finds the first mismatching byte, which is a classic variable-time comparison. This is the same root-cause pattern flagged in the external advisory for `yii2-authclient`'s OAuth1 `state`/OAuth2 `state`/OpenID Connect `nonce` checks (`OAuth1.php:158`, `OAuth2.php:121`, `OpenIdConnect.php:420`), where a plain string comparison was used instead of a constant-time helper.

Notably, this same file already defines and uses a constant-time comparison helper, `constantTimeEmailCompare`, elsewhere for email matching [3](#0-2) , showing the codebase is aware of timing-attack risk for string comparisons in this exact authentication flow but did not apply the same protection to the `state` check.

Both `/oidc-login` and `/oidc-exchange` are registered as unauthenticated endpoints via `ExtendRouter`, reachable by any unprivileged client without a prior session [4](#0-3) .

### Impact Explanation
A successful timing attack against the `state` comparison could allow an attacker to guess/forge a valid `state` value without having observed the value issued by `/oidc-login` to a victim session. If an attacker can predict/forge the `state`, and can otherwise obtain or race a valid authorization `code` (e.g., via open-redirect, log leakage, or CSRF login flow abuse), the state check ceases to be an effective anti-CSRF control, undermining the OIDC login flow's replay/CSRF protection. On its own — given `state` is 256 bits of entropy and delivered over HTTPS in a single request/response round trip — exploitability is constrained, but this is a comparison-timing weakness within an unauthenticated authentication codepath, matching the CVE's bug class precisely.

### Likelihood Explanation
Low-to-medium. Practical exploitation of a network-based byte-at-a-time timing side channel against a short server-processed string typically requires many thousands of precisely-timed measurements and a low-jitter/low-latency network path (e.g., same LAN/data-center), which is harder for a purely remote unprivileged attacker but not implausible against nodes with predictable RTT (e.g., cloud-hosted nodes on shared infrastructure). The `state` value itself is high-entropy (32 random bytes), so even if timing leakage is exploitable, the attacker must still win a race for a valid `code`/session pairing, similar to constraints acknowledged for the original CVE-2023-50708 advisory (CVSS 6.1, AC:H).

### Recommendation
Replace the `req.State != storedState.(string)` comparison in `handleTokenExchange` with `crypto/subtle.ConstantTimeCompare` (the same pattern already used by `constantTimeEmailCompare` in this file, and by `AuthenticateUserByToken`/`AuthenticateBridgeType` elsewhere in the codebase), e.g.:
```go
storedStateStr, ok := storedState.(string)
if !ok || subtle.ConstantTimeCompare([]byte(req.State), []byte(storedStateStr)) != 1 {
    // invalid state
}
```

### Proof of Concept
1. Configure the node with OIDC enabled (`config.OIDC`).
2. Call `GET /oidc-login` to obtain a session cookie with a stored `state`.
3. Send repeated `POST /oidc-exchange` requests with crafted `state` values that share increasingly longer correct prefixes, measuring server response latency for the state-check branch.
4. Because `req.State != storedState.(string)` at [5](#0-4)  exits comparison at the first differing byte, statistically significant timing differences correlate with the number of correctly-guessed leading bytes, allowing incremental byte-by-byte recovery of the session's `state` value — directly analogous to the PoC described for CVE-2023-50708 against yii2-authclient's OAuth1/OAuth2/OpenID Connect `state`/`nonce` checks.

func constantTimeEmailCompare(left, right string) bool {
	const constantTimeEmailLength = 256
	length := mathutil.Max(constantTimeEmailLength, len(left), len(right))
	leftBytes := make([]byte, length)
	rightBytes := make([]byte, length)
	copy(leftBytes, left)
	copy(rightBytes, right)
	return subtle.ConstantTimeCompare(leftBytes, rightBytes) == 1
}
