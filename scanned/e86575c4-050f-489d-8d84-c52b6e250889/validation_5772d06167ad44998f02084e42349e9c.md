## Analysis

The reported CVE (Webmin/Usermin login error-message discrepancy enabling user enumeration) has a direct analog in Chainlink's local login flow via the `/sessions` endpoint.

### Title
Login endpoint leaks distinct error messages for unknown-email vs. wrong-password, enabling user enumeration - (File: `core/sessions/localauth/orm.go`)

### Summary
`POST /sessions` (`SessionsController.Create`) calls `AuthenticationProvider().CreateSession`, which in the local-auth implementation looks up the user by email and returns different, attacker-visible error strings depending on whether the email exists.

### Finding Description
`CreateSession` first calls `FindUser` → `findUser`, which does a plain SQL lookup and returns the raw `sql.ErrNoRows` (e.g. `"sql: no rows in result set"`) when the email doesn't exist: [1](#0-0) 

If the email does exist, but the password is wrong, a different, explicit error `"Invalid password"` is returned instead: [2](#0-1) 

Both error paths propagate unmodified up through `SessionsController.Create`, which forwards `err` straight into `jsonAPIError`: [3](#0-2) 

And `jsonAPIError` serializes `err.Error()` verbatim into the HTTP JSON response body: [4](#0-3) 

This means an unauthenticated client submitting `POST /sessions` with a guessed email receives a structurally distinguishable error ("no rows"/DB-level error vs. `"Invalid password"`), letting an attacker enumerate valid admin/operator email addresses. This is confirmed by the existing test at: [5](#0-4) 
which explicitly exercises both "incorrect pwd" and "incorrect email" cases against the same live endpoint, though the test only checks status code, not response body content — the actual body differs by design of the ORM code above.

The same email/password-discrepancy pattern also exists in `ldapauth.localLoginFallback` (`"invalid email"` vs `"invalid password"`) and `oidcauth.localLoginFallback`, for the CLI-admin local-fallback login path: [6](#0-5) [7](#0-6) 

### Impact Explanation
An unprivileged, unauthenticated network attacker can enumerate valid Chainlink node operator/admin email addresses by observing the error message/text returned from `/sessions`. This is a precursor for targeted credential-stuffing, phishing, or brute-force attacks against known accounts on an internet-facing node UI/API. Impact is limited to information disclosure (account existence), not direct account takeover.

### Likelihood Explanation
High reachability: `/sessions` is an unauthenticated, internet-facing endpoint by design (used for login), so this requires no prior privilege. The discrepancy is deterministic and not timing-based, making enumeration straightforward and reliable.

### Recommendation
Normalize the error returned by `CreateSession` (and its LDAP/OIDC local-fallback counterparts) for both "user not found" and "wrong password" cases into a single generic message (e.g., `"invalid email or password"`), and ensure `findUser`'s raw `sql.ErrNoRows` is caught and remapped before it reaches `jsonAPIError`, rather than being serialized to the client verbatim.

### Proof of Concept
1. `POST /sessions` with `{"email":"nonexistent@test.net","password":"anything"}` → response body/error derived from `sql.ErrNoRows` (e.g. contains `"sql: no rows in result set"` or a DB-specific message).
2. `POST /sessions` with `{"email":"<valid-known-email>","password":"wrongpassword"}` → response body contains `"Invalid password"`.
3. Comparing these two responses allows an attacker to distinguish valid vs. invalid emails without needing any credentials, as demonstrated by the differing code paths in `core/sessions/localauth/orm.go` lines 44-59 and 144-162, both reachable from `core/web/sessions_controller.go` line 56-60.

func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}

// jsonAPIError adds an error to the gin context and sets
// the JSON value of errors.
func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}

// localLoginFallback tests the credentials provided against the 'local' authentication method
// This covers the case of local CLI API calls requiring local login separate from the LDAP server
func (l *ldapAuthenticator) localLoginFallback(ctx context.Context, sr sessions.SessionRequest) (sessions.User, error) {
	var user sessions.User
	sql := "SELECT * FROM users WHERE lower(email) = lower($1)"
	err := l.ds.GetContext(ctx, &user, sql, sr.Email)
	if err != nil {
		return user, err
	}
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		l.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return user, errors.New("invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		l.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return user, errors.New("invalid password")
	}

	return user, nil
}
