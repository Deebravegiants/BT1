### Title
JWT replay-protection check-then-act race in `WorkflowMetadataHandler.Authorize` allows request replay from an unprivileged HTTP trigger caller - (File: `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go`)

### Summary
The Compound report's root cause is a stale-value bug: a security-relevant value (`exchangeRateStored`) is read without accounting for a concurrent state update, producing an incorrect result that an unprivileged caller can exploit. The closest reachable analog in this codebase is the JWT replay guard used by the internet-facing HTTP trigger handler: the "check" (`isReplayed`) and the "act" (`recordUsage`) on the JWT-ID cache are two independently-locked operations rather than one atomic operation, so a stale read of cache state can be observed by multiple concurrent requests before either records usage.

### Finding Description
`WorkflowMetadataHandler.Authorize` is invoked by `httpTriggerHandler.authorizeRequest`, which is reached directly from an unprivileged external caller's `workflows.execute` HTTP trigger request via `HandleUserTriggerRequest`: [1](#0-0) 

Inside `Authorize`, the JWT single-use ("replay") guard performs a read (`isReplay`) and, only after several additional unrelated steps (looking up `authorizedKeys`, comparing signer), a separate write (`recordUsage`): [2](#0-1) 

`isReplay` takes an `RLock`, checks the map, and releases the lock; `recordUsage` takes a completely separate `Lock` later: [3](#0-2) 

Because the check and the write are not performed atomically (no single lock spans both, and other authorization work happens in between), two concurrent `HandleUserTriggerRequest` calls carrying the same signed JWT (same `jti`) can both call `isReplay` before either calls `recordUsage`. Both will observe the stale (not-yet-recorded) cache state and both will pass the "already used" check, exactly analogous to the Compound bug where a stale exchange-rate read let a caller act on outdated state.

### Impact Explanation
This defeats the intended one-time-use guarantee of the JWT-signed HTTP trigger request. A JWT is meant to authorize exactly one workflow execution (`workflows.execute`) per token. With the race, the same valid, previously-authorized request/JWT pair could be concurrently submitted and pass authorization twice (or more), which is a request-impersonation/replay-bypass of the JWT anti-replay control. Downstream, `setupCallback` does dedupe strictly on `requestID`, which reduces (but does not eliminate) the observable effect since a distinct requestID with a reused JWT would still slip through `Authorize`, potentially triggering the workflow execution a second time with the same signer authorization/rate-limit and cost implications not intended by the single-use JWT contract.

### Likelihood Explanation
Exploitation requires an attacker (or the legitimate caller replaying its own captured JWT for a race) to send two requests carrying the same JWT concurrently within the narrow window between `isReplay` and `recordUsage`. This window includes an authorizedKeys map lookup and comparison, which is fast in-memory work, so the race window is small but real; it is a genuine TOCTOU (check-then-act) bug rather than a purely theoretical one, and gateways are commonly hit with concurrent/duplicate client retries, increasing the odds of triggering it in production. It is reachable purely from an unprivileged external caller of the gateway's HTTP trigger endpoint, with no special privileges needed beyond possessing one previously-valid JWT.

### Recommendation
Make the replay check-and-record atomic: hold a single write lock across the "check jti not present" and "insert jti" steps (e.g., a `CompareAndSwap`-style method on `jwtReplayCache` such as `checkAndRecord(jti) bool` that returns false if already present, otherwise atomically inserts it), and call this immediately before any other authorization logic proceeds, rather than performing the read early and the write only after several additional steps.

### Proof of Concept
1. Obtain one valid JWT for a workflow trigger request (`vaulttypes`/`gateway_common.HTTPTriggerRequest`, signed, with a fixed `jti`).
2. Fire two (or more) concurrent `workflows.execute` requests to the gateway carrying this same JWT, each with the same `req.Auth` value used in `authorizeRequest`.
3. Both goroutines execute `Authorize`: both call `h.jwtCache.isReplay(claims.ID)` before either calls `h.jwtCache.recordUsage(claims.ID)`, since the two operations use independent locks with unrelated work executing between the read and the write (`workflowID` lookup, key comparison).
4. Both requests pass the "JWT already used" check and both proceed to be authorized, defeating the single-use guarantee that the JWT was intended to provide.

**Uncertainty**: I was not able to fully trace whether an additional layer (e.g. request-level `setupCallback`'s `requestID` uniqueness check) fully absorbs this in all deployment configurations, since a caller could supply a new unique `requestID` per race attempt while reusing the same JWT `jti`; this would need confirmation with a live/dynamic test that is out of scope for static code review.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
