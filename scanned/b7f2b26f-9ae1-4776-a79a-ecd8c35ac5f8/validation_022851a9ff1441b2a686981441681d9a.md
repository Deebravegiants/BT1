### Title
Unbounded `email` length on unauthenticated `/sessions` login endpoint enables memory/DB amplification DoS - (File: core/web/sessions_controller.go)

### Summary
The rdiffweb advisory describes a DoS caused by accepting an arbitrarily long `email` field with no length validation, which is then processed repeatedly (login, etc.), causing server overload. The Chainlink node has an analogous unauthenticated endpoint, `SessionsController.Create` (`POST /sessions`), which binds `sessions.SessionRequest.Email` directly from the JSON request body with no length cap, and passes it through DB queries and a length-proportional constant-time comparison buffer allocation.

### Finding Description
`SessionsController.Create` unmarshals the request body directly into `clsessions.SessionRequest` via `c.ShouldBindJSON(&sr)` with no size or length restriction on `sr.Email`: [1](#0-0) 

`sr.Email` is then used unmodified in `GetUserWebAuthn` and forwarded to `CreateSession`, both of which issue SQL queries parameterized with the raw email string: [2](#0-1) 

Inside `CreateSession`, `constantTimeEmailCompare` allocates two byte buffers sized to `max(256, len(left), len(right))` — i.e., proportional to the attacker-controlled email length, not the fixed 256-byte constant it was presumably meant to enforce: [3](#0-2) 

The same unbounded pattern exists in the LDAP and OIDC local-fallback authenticators: [4](#0-3) [5](#0-4) 

Unlike the internet-facing Gateway HTTP server, which enforces an explicit `MaxRequestBytes`/`MaxRequestBytesLimiter` on incoming payloads: [6](#0-5) 

I found no equivalent request body size limit applied to the core node web API router/middleware stack for the `/sessions` route (searches for `MaxBytesReader`, `ContentLength` checks, or body-limit middleware in `core/web/*.go` returned no matches). This means an unauthenticated client can submit an arbitrarily large `email` value in the JSON body to `POST /sessions`, which the server will fully parse, allocate `2 * len(email)` bytes for the comparison, and pass as a bound parameter to a Postgres query — all before any password check or authentication succeeds.

Also relevant: `sessions.ValidateEmail` (used at user-creation time, an admin-only path) only checks for non-empty and RFC parseable format — it does not enforce any maximum length: [7](#0-6) 

### Impact Explanation
An unauthenticated attacker can repeatedly POST to `/sessions` with multi-megabyte (or larger, up to whatever the HTTP server's/gin's default body limits allow) `email` values. Each request causes: (1) full JSON body parsing, (2) a database query with a huge bound parameter, and (3) allocation of two buffers each sized to the email length in `constantTimeEmailCompare`. Repeated concurrent requests can exhaust node memory, CPU, or database resources, resulting in denial of service for the node's API/UI — consistent with the CWE-770 "Allocation of Resources Without Limits" class in the source advisory. This does not grant authentication bypass or data disclosure; the impact is availability only.

### Likelihood Explanation
The `/sessions` endpoint is unauthenticated by design (it's the login endpoint) and reachable from any unprivileged client, so exploitation requires no prior access. The lack of an observed max-length check on `Email` in the bind/validation path and lack of a general request body size limit on the node web router (in contrast to the Gateway's `MaxRequestBytesLimiter`) makes this readily reachable, though actual severity depends on any HTTP-server-level default body caps (e.g., Go's `http.Server` has no default max header/body size unless explicitly set) which were not found configured for this router.

### Recommendation
- Enforce a maximum length (e.g., 255 or similar) for `Email` in `sessions.SessionRequest` validation on the `/sessions` login path, mirroring `MaxBcryptPasswordLength` handling for passwords.
- Add an explicit request body size limit (e.g., `http.MaxBytesReader` or gin body-limit middleware) to the core node web server, similar to the Gateway's `MaxRequestBytesLimiter`.
- Cap the buffer size in `constantTimeEmailCompare` to a fixed constant, rejecting (with an early length check) any email longer than that constant before entering the comparison, instead of sizing the buffer dynamically to the input length.

### Proof of Concept
1. Without authentication, send:
```
POST /sessions HTTP/1.1
Content-Type: application/json

{"email": "<10MB of 'a' characters>@test.com", "password": "irrelevant"}
```
2. Observe the server accepts and fully processes the body: it queries the DB with the huge email value (`FindUser`/`GetUserWebAuthn`) and allocates buffers proportional to the email length in `constantTimeEmailCompare`.
3. Repeating this concurrently from multiple connections can degrade node responsiveness/availability due to unbounded memory and DB query parameter size, with no authentication required.

func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

const constantTimeEmailLength = 256

func constantTimeEmailCompare(left, right string) bool {
	length := mathutil.Max(constantTimeEmailLength, len(left), len(right))
	leftBytes := make([]byte, length)
	rightBytes := make([]byte, length)
	copy(leftBytes, left)
	copy(rightBytes, right)
