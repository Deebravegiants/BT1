## Analysis

The bug at `core/sessions/oidcauth/oidc.go:226-230` is a genuine, real analog to the trilogy CVE's bug class (use of a variable that isn't properly validated/initialized before being used downstream in an authentication flow), reachable by an unprivileged actor via the OIDC callback endpoint.### Title
Missing return after unauthenticated email-claim extraction failure leads to session creation with empty/attacker-influenced identity - (File: core/sessions/oidcauth/oidc.go)

### Summary
In `oidcAuthenticator.handleTokenExchange`, after exchanging the OIDC authorization code and verifying the ID token, the handler extracts the `email` claim from the unauthenticated `claims` map. If the `email` claim assertion fails, the code logs an error and writes an HTTP response but **does not `return`**, so execution falls through and continues to map roles, insert an `oidc_sessions` row, and establish an authenticated Gin session using whatever `email` value is present (empty string in the failure case) [1](#0-0) .

### Finding Description
`handleTokenExchange` performs the OAuth2 code exchange, verifies the ID token, and extracts claims into a generic `map[string]any` [2](#0-1) . It then does:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims. error: %v", err)
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
}
``` [1](#0-0) 

Unlike every other error branch in this function (which all `return` after writing an error response, e.g. state mismatch, token exchange failure, ID token verification failure, claim extraction failure) [3](#0-2) , this branch is missing the `return` statement. As a result, when `!ok` (email claim absent or non-string), execution proceeds to:
- Role mapping via `IDClaimsToUserRole` using the already-validated group claims [4](#0-3) 
- Insertion of a new row into `oidc_sessions` keyed by `strings.ToLower(email)` (an empty string in the failure case) together with the resolved `role` [5](#0-4) 
- An audit log entry for `AuthLoginSuccessNo2FA` [6](#0-5) 
- Setting the Gin session's `SessionIDKey` and saving it, then returning `ExchangeTokenResponse{Success: true}` to the caller [7](#0-6) 

The response written earlier (`http.StatusInternalServerError`) is silently overwritten by the later `c.JSON(http.StatusOK, ...)` call because Gin allows multiple writes and the last one wins for the status/body in this code path, so the client actually receives a `200 Success: true` response along with a valid, authenticated session cookie, despite `email` never being validated.

This is a state/identity-confusion analog to the trilogy CVE's "use of uninitialized/unvalidated variable" bug class: a value that should have gated further authenticated-session issuance (the verified email identity) is not properly checked before being used to persist and authenticate a session, because a missing `return` allows control flow to proceed with the zero-value/uncontrolled variable.

### Impact Explanation
An authenticated session is created and returned to the caller bound to an empty-string (or otherwise invalid) email identity, with a role derived purely from OIDC group claims. Downstream, `FindUserByAPIToken`/session-consuming code and audit logs (`AuthLoginSuccessNo2FA`) will treat this as a legitimate login for user `""`, potentially colliding with or being conflated with other empty/unset email records, and granting a live, cookie-authenticated Gin session with a role (Admin/Edit/Run/Read) mapped from the OIDC provider's group claims. This is a concrete instance of cross-user response/session confusion and improper session issuance stemming from unvalidated identity data.

### Likelihood Explanation
Reaching this path requires control over, or the ability to cause, an OIDC ID token/claims response where the `email` claim is missing or non-string while the configured RBAC group claims (Admin/Edit/Run/Read) are still present — this is plausible with a misconfigured or partially-compliant OIDC provider, or an unprivileged user manipulating the provider-side profile/claims (depending on trust boundary of the configured IdP) since the endpoint is reached via the normal, unprivileged OIDC callback flow (`handleTokenExchange`) after only presenting a valid `code`/`state` pair.

### Recommendation
Add a `return` after writing the error response in the `email` claim-extraction failure branch, mirroring every other error branch in `handleTokenExchange`:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims. error: %v", err)
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
```
This prevents session/role creation and audit-success logging when the identity claim cannot be validated.

### Proof of Concept
1. Configure the OIDC provider integration such that the ID token's claims payload omits the `email` field (or returns a non-string type for it) while still containing one of the configured group claims (Admin/Edit/Run/Read).
2. Complete the normal `handleSignIn` → provider redirect → `handleTokenExchange` flow, POSTing the valid `code`/`state` to the token-exchange endpoint.
3. Observe: `claims["email"].(string)` assertion fails, the error branch executes but falls through (no `return`), `IDClaimsToUserRole` still resolves a role, a row is inserted into `oidc_sessions` with `user_email = ''` and the resolved role, `AuthLoginSuccessNo2FA` is audited, and the response is `200 {"success": true}` with a valid session cookie set — granting an authenticated session despite failed identity extraction.
