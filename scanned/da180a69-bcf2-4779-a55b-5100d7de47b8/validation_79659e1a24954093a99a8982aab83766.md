## Title
Unauthenticated pprof/metrics debug endpoints reachable via `loopRoutes`, bypassing the authentication constraints applied to the equivalent `/v2/debug/pprof` endpoints - (File: `core/web/router.go`)

### Summary
Chainlink's node HTTP router mounts the same class of sensitive debug/profiling functionality (pprof and metrics endpoints) under two different paths with inconsistent authentication: the standard pprof endpoints are gated behind session/token authentication and admin authorization via `metricRoutes(authv2)`, while the LOOP-plugin pprof/metrics forwarding endpoints registered by `loopRoutes` are mounted directly on the unauthenticated base router group and are reachable by any unprivileged client.

### Finding Description
`NewRouter` builds a base `api` group with only rate limiting and session-cookie middleware attached — no authentication requirement: [1](#0-0) 

It then calls `loopRoutes(app, api)` directly on this unauthenticated `api` group, alongside `debugRoutes`, `healthRoutes`, `sessionRoutes`, and `v2Routes` which each construct their own authenticated sub-groups internally: [2](#0-1) 

`loopRoutes` registers the discovery, plugin metrics, plugin pprof, and plugin pprof-symbol endpoints with no auth middleware at all: [3](#0-2) 

Contrast this with the standard Go pprof endpoints, which are only exposed via `metricRoutes(authv2)`, called from inside the `authv2` group that requires `auth.Authenticate(... AuthenticateByToken, AuthenticateBySession)`: [4](#0-3) [5](#0-4) [6](#0-5) 

The plugin pprof handlers themselves proxy arbitrary pprof requests (including profile duration/`seconds`, `debug`, `gc` query params) to the internal LOOP-plugin process and return the raw response body to the caller, with no ownership/role check performed anywhere in the handler chain: [7](#0-6) 

This mirrors the Tomcat CWE-288 bug class described in the report: a resource (pprof/profiling data) that is protected when reached via the "expected" path (`/v2/debug/pprof/*` under `authv2`) is reachable and unprotected via an "alternate" mounted path (`/plugins/:name/debug/pprof/*` under the base `api` group), because the security constraint (authentication middleware) was attached to the route group of the expected path rather than uniformly enforced for the resource class.

### Impact Explanation
An unprivileged, unauthenticated network client that can reach the node's web server can enumerate loaded LOOP plugins via `/discovery`, pull their runtime metrics via `/plugins/:name/metrics`, and pull full pprof profiles (heap, goroutine, CPU profile, trace) via `/plugins/:name/debug/pprof/*` and `/plugins/:name/debug/pprof/symbol`. Profiling/heap data can leak internal state, memory contents, and operational details of the node's capability plugins without any credentials, and the CPU-profile/`seconds` parameter can also be used to tie up node resources (proxied HTTP calls with attacker-controlled duration).

### Likelihood Explanation
High for any deployment where this HTTP router is exposed to the network (it's the same listener that serves the authenticated `/v2` API and operator UI), since no credentials, tokens, or session cookies are required — only knowledge of a valid plugin name (discoverable via the equally unauthenticated `/discovery` endpoint).

### Recommendation
Require the same authentication as `metricRoutes`/`authv2` for the routes registered in `loopRoutes` (or move `loopRoutes` registration inside an authenticated group), so that plugin metrics/pprof-forwarding endpoints are gated by `auth.Authenticate` (and appropriate role checks) exactly like the built-in `/v2/debug/pprof` endpoints, rather than being mounted on the unauthenticated base `api` group.

### Proof of Concept
1. Start a chainlink node with at least one LOOP plugin registered.
2. Without any session cookie or API token, issue: `curl http://<node>:<port>/discovery` — returns plugin names/ports unauthenticated.
3. Using a discovered plugin name, issue: `curl http://<node>:<port>/plugins/<name>/debug/pprof/heap?debug=1` — the handler `pluginPPROFHandler` forwards the request to the plugin's internal debug pprof endpoint and returns the profile data with no authentication check performed anywhere in the call chain (`core/web/router.go:234` → `core/web/loop_registry.go:150-166`).

func (l *LoopRegistryServer) pluginPPROFHandler(gc *gin.Context) {
	pluginName := gc.Param("name")
	p, ok := l.registry.Get(pluginName)
	if !ok {
		gc.Data(http.StatusNotFound, "text/plain", fmt.Appendf(nil, "plugin %q does not exist", html.EscapeString(pluginName)))
		return
	}

	// unlike discovery, this endpoint is internal btw the node and plugin
	pluginURL := fmt.Sprintf("http://%s:%d/debug/pprof/"+gc.Param("profile"), l.loopHostName, p.EnvCfg.PrometheusPort)
	urlVals, timeout := pprofURLVals(gc)
	if s := urlVals.Encode(); s != "" {
		pluginURL += "?" + s
	}
	l.logger.Infow("Forwarding plugin pprof request", "plugin", pluginName, "url", pluginURL)
	l.doRequest(gc, "GET", pluginURL, nil, timeout, pluginName)
}

func (l *LoopRegistryServer) pluginPPROFPOSTSymbolHandler(gc *gin.Context) {
	pluginName := gc.Param("name")
	p, ok := l.registry.Get(pluginName)
	if !ok {
		gc.Data(http.StatusNotFound, "text/plain", fmt.Appendf(nil, "plugin %q does not exist", html.EscapeString(pluginName)))
		return
	}

	// unlike discovery, this endpoint is internal btw the node and plugin
	pluginURL := fmt.Sprintf("http://%s:%d/debug/pprof/symbol", l.loopHostName, p.EnvCfg.PrometheusPort)
	urlVals, timeout := pprofURLVals(gc)
	if s := urlVals.Encode(); s != "" {
		pluginURL += "?" + s
	}
	body, err := io.ReadAll(gc.Request.Body)
	if err != nil {
		gc.Data(http.StatusInternalServerError, "text/plain", fmt.Appendf(nil, "error reading plugin pprof request body: %s", err))
		return
	}
	l.doRequest(gc, "POST", pluginURL, bytes.NewReader(body), timeout, pluginName)
}
