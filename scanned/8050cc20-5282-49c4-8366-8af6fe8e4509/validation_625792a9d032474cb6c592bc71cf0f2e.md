### Title
Pending HRMP open-channel sender deposit permanently trapped when initiating para deregisters before session-boundary channel establishment - ([File: polkadot/runtime/parachains/src/hrmp.rs])

### Summary
When a parathread manager calls `deregister` on a para that has an *unconfirmed/pending* `hrmp_init_open_channel` request, `clean_open_channel_requests` intentionally skips refunding the sender's deposit when the sender itself is in the `outgoing` list. Because the para is deregistered in the same flow (via `Pallet::do_deregister` → `schedule_para_cleanup`), no future extrinsic can ever unreserve that deposit from the para's sovereign account, since the request record is deleted and no `Origin::Parachain` can ever again be produced for a deregistered `ParaId`.

### Finding Description
`Registrar::deregister` is reachable by a signed parathread manager via `Pallet::ensure_root_para_or_owner` → `Pallet::do_deregister` [1](#0-0) . `do_deregister` calls `polkadot_runtime_parachains::schedule_para_cleanup::<T>(id)`, which only fails if the para has a PVF pre-check in progress or unprocessed UMP messages; it otherwise marks the para `OffboardingParathread` and schedules it for removal in `ActionsQueue` [2](#0-1) . Nothing in this path checks for outstanding HRMP open-channel requests or crowdloan funds.

At the next session boundary, `initializer::apply_new_session` computes `outgoing_paras` from `paras::Pallet::initializer_on_new_session` and passes it to `hrmp::Pallet::initializer_on_new_session` [3](#0-2) , which calls `perform_outgoing_para_cleanup` → `clean_open_channel_requests` for pending, not-yet-established channel requests [4](#0-3) .

The root cause is in `clean_open_channel_requests`:
```
// Return the deposit of the sender, but only if it is not the para being offboarded.
if !outgoing.contains(&req_id.sender) {
    T::Currency::unreserve(&req_id.sender.into_account_truncating(), req_data.sender_deposit...);
}
``` [5](#0-4) 

If the deregistering para is the *sender* of the pending open request (i.e. it called `hrmp_init_open_channel`), its `sender_deposit` — reserved on the para's sovereign account (`ParaId::into_account_truncating()`) at request creation — is never unreserved. The request entry itself is removed from `HrmpOpenChannelRequests`/`HrmpOpenChannelRequestsList` in the same pass, so `hrmp_cancel_open_request` can no longer find it even in principle. Moreover, `hrmp_cancel_open_request`/`hrmp_close_channel` require an `ensure_parachain` origin (`Origin::Parachain(id)`), which can only be produced by the parachain's own runtime dispatching via the relay chain while the para is a live, validating parachain [6](#0-5) . Once deregistered, that origin can never again be generated for this `ParaId`, and no signed account (manager or otherwise) can invoke it directly.

Note that for *already-established* channels (post `HrmpChannels` insertion), `close_hrmp_channel` unconditionally refunds both sender and recipient deposits regardless of outgoing status [7](#0-6) , so that path is safe. The bug is specific to the *pending, unconfirmed* open-channel-request window between `hrmp_init_open_channel` and the session boundary that would have turned it into a real channel.

The attack sequence matches exactly: `reserve` → `register` → `hrmp_init_open_channel` (reserves `sender_deposit` from the para's sovereign account, request stays unconfirmed) → `deregister` (schedules cleanup, no check for pending HRMP requests) → `run_to_session` (session boundary processes `outgoing_paras` and permanently skips the sender refund).

### Impact Explanation
The HRMP `sender_deposit` (`config.hrmp_sender_deposit`) reserved from the deregistering para's sovereign account becomes permanently locked in `Balances::reserved_balance` with no extrinsic path to release it: the para no longer exists (no manager-controlled origin can dispatch as that `ParaId`), the request record has been deleted, and unprivileged accounts cannot directly manipulate another account's reserved balance. This is a concrete instance of "permanently trapped funds," matching the scoped impact.

### Likelihood Explanation
This requires only unprivileged actions available to any parathread manager: register a parathread, initiate an HRMP open channel (no counterparty acceptance needed — the bug triggers purely from having a *pending* request), then deregister before the recipient accepts/before the next session boundary. This is fully reachable through normal extrinsics (`Registrar::reserve`, `Registrar::register`, `Hrmp::hrmp_init_open_channel`, `Registrar::deregister`) with no admin/governance action needed, and is deterministically repeatable every time a parathread manager deregisters while it has a pending outbound-initiated HRMP request.

### Recommendation
In `Pallet::do_deregister` (or `schedule_para_cleanup`), reject deregistration while the para has outstanding `HrmpOpenChannelRequests` where it is the sender/recipient (similar to the existing UMP-queue and PVF-pre-check guards), or alternatively change `clean_open_channel_requests` to always refund the sender's `sender_deposit` regardless of whether the sender is offboarding (mirroring the unconditional refund behavior already used in `close_hrmp_channel` for established channels).

### Proof of Concept
Rust integration test in `polkadot/runtime/parachains/src/hrmp/tests.rs` style, extended with the registrar:
1. Register parathread `para_a` (manager account `M`), give `M`/`para_a`'s sovereign account sufficient balance.
2. Call `Hrmp::init_open_channel(para_a, para_b, cap, size)` — assert `Balances::reserved_balance(&para_a.into_account_truncating())` increases by `hrmp_sender_deposit`.
3. Do **not** call `accept_open_channel` from `para_b` (keep request unconfirmed).
4. Call `Registrar::deregister(RuntimeOrigin::signed(M), para_a)` — assert `Ok`.
5. `run_to_session(next)` to trigger `initializer_on_new_session` / `clean_open_channel_requests`.
6. Assert: `HrmpOpenChannelRequests::<Test>::get(&HrmpChannelId{sender: para_a, recipient: para_b})` is `None` (request removed), and `Balances::reserved_balance(&para_a.into_account_truncating())` is **still equal to `hrmp_sender_deposit`** (nonzero), with `paras::Pallet::<Test>::lifecycle(para_a)` being `None` (para fully deregistered) — proving the deposit is permanently orphaned since no further extrinsic path exists to release it for a nonexistent `ParaId`.

	pub(crate) fn schedule_para_cleanup(id: ParaId) -> DispatchResult {
		// Disallow offboarding in case there is a PVF pre-checking in progress.
		//
		// This is not a fundamental limitation but rather simplification: it allows us to get
		// away without introducing additional logic for pruning and, more importantly, enacting
		// ongoing PVF pre-checking votes. It also removes some nasty edge cases.
		//
		// However, an upcoming upgrade on its own imposes no restrictions. An upgrade is enacted
		// with a new para head, so if a para never progresses we still should be able to offboard
		// it.
		//
		// This implicitly assumes that the given para exists, i.e. it's lifecycle != None.
		if let Some(future_code_hash) = FutureCodeHash::<T>::get(&id) {
			let active_prechecking = PvfActiveVoteList::<T>::get();
			if active_prechecking.contains(&future_code_hash) {
				return Err(Error::<T>::CannotOffboard.into());
			}
		}

		let lifecycle = ParaLifecycles::<T>::get(&id);
		match lifecycle {
			// If para is not registered, nothing to do!
			None => return Ok(()),
			Some(ParaLifecycle::Parathread) => {
				ParaLifecycles::<T>::insert(&id, ParaLifecycle::OffboardingParathread);
			},
			Some(ParaLifecycle::Parachain) => {
				ParaLifecycles::<T>::insert(&id, ParaLifecycle::OffboardingParachain);
			},
			_ => return Err(Error::<T>::CannotOffboard.into()),
		}

		let scheduled_session = Self::scheduled_session();
		ActionsQueue::<T>::mutate(scheduled_session, |v| {
			if let Err(i) = v.binary_search(&id) {
				v.insert(i, id);
			}
		});

		if <T as Config>::QueueFootprinter::message_count(UmpQueueId::Para(id)) != 0 {
			return Err(Error::<T>::CannotOffboard.into());
		}

		Ok(())
	}

	fn perform_outgoing_para_cleanup(
		config: &HostConfiguration<BlockNumberFor<T>>,
		outgoing: &[ParaId],
	) -> Weight {
		let mut w = Self::clean_open_channel_requests(config, outgoing);
		for outgoing_para in outgoing {
			Self::clean_hrmp_after_outgoing(outgoing_para);

			// we need a few extra bits of data to weigh this -- all of this is read internally
			// anyways, so no overhead.
			let ingress_count =
				HrmpIngressChannelsIndex::<T>::decode_len(outgoing_para).unwrap_or_default() as u32;
			let egress_count =
				HrmpEgressChannelsIndex::<T>::decode_len(outgoing_para).unwrap_or_default() as u32;
			w = w.saturating_add(<T as Config>::WeightInfo::force_clean_hrmp(
				ingress_count,
				egress_count,
			));
		}
		w
	}
