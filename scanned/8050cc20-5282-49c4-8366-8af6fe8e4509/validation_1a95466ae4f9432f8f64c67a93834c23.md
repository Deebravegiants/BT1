### Title
Unthrottled DMP queue flooding via free HRMP notifications (`hrmp_init_open_channel`/`hrmp_cancel_open_request` cycling) - ([File: polkadot/runtime/parachains/src/dmp.rs])

### Summary
`Pallet::queue_downward_message`/`can_queue_downward_message` in `dmp.rs` enforce only a hard queue-size cap (`dmq_max_length`) and no per-sender/per-message-count throttle. HRMP channel-management notifications (`HrmpNewChannelOpenRequest`, `HrmpChannelAccepted`, `HrmpChannelClosing`) are pushed into a victim para's downward queue via `hrmp.rs::send_to_para` → `dmp::Pallet::<T>::queue_downward_message` completely free of charge, bypassing the `DeliveryFeeFactor`/`ExponentialPrice` economic throttle that the module doc claims protects the queue. An attacker controlling any registered parachain can therefore repeatedly cycle `hrmp_init_open_channel`(victim)/`hrmp_cancel_open_request` to push notifications into the victim's `DownwardMessageQueuePages` up to the hard cap at essentially zero net cost (deposits are reserved then fully unreserved on cancel), degrading the victim's DMP throughput.

### Finding Description
`can_queue_downward_message` only checks message size and the hard cap `dmq_length(para) > dmq_max_length(max_downward_message_size)` [1](#0-0) . There is no check that limits how many messages a *specific unprivileged sender* can inject, and no fee is charged for HRMP-triggered notifications.

`queue_downward_message` does call `increase_fee_factor` once the queue crosses a threshold [2](#0-1) , but this fee factor is only consumed by `ExponentialPrice::price_for_delivery`, which is invoked by `ChildParachainRouter::validate` for XCM-`send`-initiated, fee-paying downward messages [3](#0-2) . HRMP protocol notifications never go through `ChildParachainRouter`/`price_for_delivery` — they call `dmp::Pallet::<T>::queue_downward_message` directly from `hrmp.rs::send_to_para` with no price computed or charged [4](#0-3) . So the rising `DeliveryFeeFactor` never makes this particular spam path more expensive for the attacker; it only raises the cost for unrelated third parties who later try to `send` XCM to the same victim para.

Exploit flow:
1. Attacker controls parachain `A` (unprivileged, reachable via `ensure_parachain` origin on `hrmp_init_open_channel`/`hrmp_cancel_open_request` extrinsics) [5](#0-4) .
2. `A` calls `hrmp_init_open_channel(victim, ...)` → `init_open_channel` reserves a deposit, records the request, and unconditionally enqueues an `HrmpNewChannelOpenRequest` downward message to `victim` via `send_to_para`/`queue_downward_message` [6](#0-5) .
3. `A` immediately calls `hrmp_cancel_open_request`, which removes the request, decrements the open-request counter, and fully unreserves the deposit [7](#0-6) .
4. Because the request/count state is fully cleared, step 2 can be repeated against the same `victim` indefinitely, each cycle appending one more message to `victim`'s `DownwardMessageQueuePages`, until `Self::dmq_length(*para) > Self::dmq_max_length(...)` is hit, after which *all* further downward messages to `victim` (including legitimate governance/XCM messages) are rejected with `ExceedsMaxMessageSize`/`ExceedsMaxQueueSize` [8](#0-7) .

The only real bottleneck is relay-chain block weight (bounding cycles per block), not any fee/queue-count throttle targeting this specific sender — contradicting the premise that `increase_fee_factor` bounds this spam economically.

### Impact Explanation
A victim parachain's downward message queue can be driven to its hard capacity by an unprivileged actor controlling any parachain, at negligible net cost (only relay-chain extrinsic weight/fees; deposits are always refunded). Once saturated, the victim stops receiving new downward messages — including legitimate governance/XCM traffic — for as long as the attacker sustains the flood, directly matching the scoped "DMP queue DoS against a victim parachain" impact.

### Likelihood Explanation
Preconditions are modest: attacker needs control of any onboarded parachain (not the victim) — a permissionless, if capital-intensive, precondition already assumed valid by the question. The attack is fully repeatable (`init`/`cancel` cycle has no cooldown or per-target rate limit) and requires no privileged origin, only `ensure_parachain` origin already reachable through normal HRMP dispatch. Feasibility is bounded only by relay-chain block weight throughput, making it a sustained but realistic multi-block DoS.

### Recommendation
Apply the delivery-fee/queue-pressure throttling (or an equivalent per-sender rate limit) to HRMP-triggered downward notifications in `hrmp.rs::send_to_para`, not just to fee-paying `ChildParachainRouter`-routed XCM sends; alternatively, impose a cooldown or dedicated quota on `hrmp_init_open_channel`/`hrmp_cancel_open_request` cycles per `(sender, recipient)` pair so free notification traffic cannot be regenerated without bound.

### Proof of Concept
Integration test in `polkadot/runtime/parachains/src/hrmp/tests.rs` style:
1. Register attacker para `A` and victim para `V`.
2. Loop N times: `Hrmp::hrmp_init_open_channel(A, V, cap, size)` then `Hrmp::hrmp_cancel_open_request(A, HrmpChannelId{A,V})`.
3. Assert `Dmp::dmq_contents_do_not_call_in_consensus(V).len()` grows by 1 each iteration and `Dmp::get_fee_factor(V)` (via `FeeTracker`) rising does **not** cause any `Err` on subsequent `hrmp_init_open_channel` calls (proving the fee factor doesn't gate this path).
4. Continue looping until `dmq_length(V) == dmq_max_length(max_downward_message_size)`; assert a subsequent legitimate `ChildParachainRouter`/`pallet_xcm::send` targeting `V` now fails with `SendError::ExceedsMaxMessageSize`, confirming the DoS on legitimate traffic.

		config: &HostConfiguration<BlockNumberFor<T>>,
		para: &ParaId,
		msg: &DownwardMessage,
	) -> Result<(), QueueDownwardMessageError> {
		let serialized_len = msg.len() as u32;
		if serialized_len > config.max_downward_message_size {
			return Err(QueueDownwardMessageError::ExceedsMaxMessageSize);
		}

		// Hard limit on Queue size

		if !paras::Heads::<T>::contains_key(para) {
			return Err(QueueDownwardMessageError::Unroutable);
		}

		Ok(())
	}

	pub fn queue_downward_message(
		config: &HostConfiguration<BlockNumberFor<T>>,
		para: ParaId,
		msg: DownwardMessage,
	) -> Result<(), QueueDownwardMessageError> {
		let serialized_len = msg.len();
		Self::can_queue_downward_message(config, &para, &msg)?;

		let inbound = InboundDownwardQueue::<T>::push_back(para, msg)
			.map_err(|_| QueueDownwardMessageError::ExceedsMaxQueueSize)?;
		let q_len = InboundDownwardQueue::<T>::len(para).unwrap_or(0);

		// obtain the new link in the MQC and update the head.
		DownwardMessageQueueHeads::<T>::mutate(para, |head| {
			let new_head =
				BlakeTwo256::hash_of(&(*head, inbound.sent_at, T::Hashing::hash_of(&inbound.msg)));
			*head = new_head;
		});

		let threshold =
			Self::dmq_max_length(config.max_downward_message_size).saturating_div(THRESHOLD_FACTOR);
		if q_len > threshold as u64 {
			Self::increase_fee_factor(para, serialized_len as u128);
		}

		Ok(())
	}

impl<A: Get<AssetId>, B: Get<u128>, M: Get<u128>, F: FeeTracker> PriceForMessageDelivery
	for ExponentialPrice<A, B, M, F>
{
	type Id = F::Id;

	fn price_for_delivery(id: Self::Id, msg: &Xcm<()>) -> Assets {
		let msg_fee = (msg.encoded_size() as u128).saturating_mul(M::get());
		let fee_sum = B::get().saturating_add(msg_fee);
		let amount = F::get_fee_factor(id).saturating_mul_int(fee_sum);
		(A::get(), amount).into()
	}
}

pub struct ChildParachainRouter<T, W, P>(PhantomData<(T, W, P)>);

impl<T: configuration::Config + dmp::Config, W: xcm::WrapVersion, P> SendXcm
	for ChildParachainRouter<T, W, P>
where
	P: PriceForMessageDelivery<Id = ParaId>,
{
	type Ticket = (HostConfiguration<BlockNumberFor<T>>, ParaId, Vec<u8>);

	fn validate(
		dest: &mut Option<Location>,
		msg: &mut Option<Xcm<()>>,
	) -> SendResult<(HostConfiguration<BlockNumberFor<T>>, ParaId, Vec<u8>)> {
		let d = dest.take().ok_or(MissingArgument)?;
		let id = if let (0, [Parachain(id)]) = d.unpack() {
			*id
		} else {
			*dest = Some(d);
			return Err(NotApplicable);
		};

		// Downward message passing.
		let xcm = msg.take().ok_or(MissingArgument)?;
		let config = configuration::ActiveConfig::<T>::get();
		let para = id.into();
		let price = P::price_for_delivery(para, &xcm);
		let versioned_xcm = W::wrap_version(&d, xcm).map_err(|()| DestinationUnsupported)?;
		versioned_xcm.check_is_decodable().map_err(|()| ExceedsMaxMessageSize)?;
		let blob = versioned_xcm.encode();
		dmp::Pallet::<T>::can_queue_downward_message(&config, &para, &blob)
			.map_err(Into::<SendError>::into)?;

		Ok(((config, para, blob), price))
	}

	pub fn init_open_channel(
		origin: ParaId,
		recipient: ParaId,
		proposed_max_capacity: u32,
		proposed_max_message_size: u32,
	) -> DispatchResult {
		ensure!(origin != recipient, Error::<T>::OpenHrmpChannelToSelf);
		ensure!(
			paras::Pallet::<T>::is_valid_para(recipient),
			Error::<T>::OpenHrmpChannelInvalidRecipient,
		);

		let config = configuration::ActiveConfig::<T>::get();
		ensure!(proposed_max_capacity > 0, Error::<T>::OpenHrmpChannelZeroCapacity);
		ensure!(
			proposed_max_capacity <= config.hrmp_channel_max_capacity,
			Error::<T>::OpenHrmpChannelCapacityExceedsLimit,
		);
		ensure!(proposed_max_message_size > 0, Error::<T>::OpenHrmpChannelZeroMessageSize);
		ensure!(
			proposed_max_message_size <= config.hrmp_channel_max_message_size,
			Error::<T>::OpenHrmpChannelMessageSizeExceedsLimit,
		);

		let channel_id = HrmpChannelId { sender: origin, recipient };
		ensure!(
			HrmpOpenChannelRequests::<T>::get(&channel_id).is_none(),
			Error::<T>::OpenHrmpChannelAlreadyRequested,
		);
		ensure!(
			HrmpChannels::<T>::get(&channel_id).is_none(),
			Error::<T>::OpenHrmpChannelAlreadyExists,
		);

		let egress_cnt = HrmpEgressChannelsIndex::<T>::decode_len(&origin).unwrap_or(0) as u32;
		let open_req_cnt = HrmpOpenChannelRequestCount::<T>::get(&origin);
		let channel_num_limit = config.hrmp_max_parachain_outbound_channels;
		ensure!(
			egress_cnt + open_req_cnt < channel_num_limit,
			Error::<T>::OpenHrmpChannelLimitExceeded,
		);

		// Do not require deposits for channels with or amongst the system.
		let is_system = origin.is_system() || recipient.is_system();
		let deposit = if is_system { 0 } else { config.hrmp_sender_deposit };
		if !deposit.is_zero() {
			T::Currency::reserve(
				&origin.into_account_truncating(),
				deposit.unique_saturated_into(),
			)?;
		}

		// mutating storage directly now -- shall not bail henceforth.

		HrmpOpenChannelRequestCount::<T>::insert(&origin, open_req_cnt + 1);
		HrmpOpenChannelRequests::<T>::insert(
			&channel_id,
			HrmpOpenChannelRequest {
				confirmed: false,
				_age: 0,
				sender_deposit: deposit,
				max_capacity: proposed_max_capacity,
				max_message_size: proposed_max_message_size,
				max_total_size: config.hrmp_channel_max_total_size,
			},
		);
		HrmpOpenChannelRequestsList::<T>::append(channel_id);

		Self::send_to_para(
			"init_open_channel",
			&config,
			recipient,
			Self::wrap_notification(|| {
				use xcm::opaque::latest::{prelude::*, Xcm};
				Xcm(vec![HrmpNewChannelOpenRequest {
					sender: origin.into(),
					max_capacity: proposed_max_capacity,
					max_message_size: proposed_max_message_size,
				}])
			}),
		);

		Ok(())
	}

	fn cancel_open_request(origin: ParaId, channel_id: HrmpChannelId) -> DispatchResult {
		// check if the origin is allowed to close the channel.
		ensure!(channel_id.is_participant(origin), Error::<T>::CancelHrmpOpenChannelUnauthorized);

		let open_channel_req = HrmpOpenChannelRequests::<T>::get(&channel_id)
			.ok_or(Error::<T>::OpenHrmpChannelDoesntExist)?;
		ensure!(!open_channel_req.confirmed, Error::<T>::OpenHrmpChannelAlreadyConfirmed);

		// Remove the request by the channel id and sync the accompanying list with the set.
		HrmpOpenChannelRequests::<T>::remove(&channel_id);
		HrmpOpenChannelRequestsList::<T>::mutate(|open_req_channels| {
			if let Some(pos) = open_req_channels.iter().position(|x| x == &channel_id) {
				open_req_channels.swap_remove(pos);
			}
		});

		Self::decrease_open_channel_request_count(channel_id.sender);
		// Don't decrease `HrmpAcceptedChannelRequestCount` because we don't consider confirmed
		// requests here.

		// Unreserve the sender's deposit. The recipient could not have left their deposit because
		// we ensured that the request is not confirmed.
		T::Currency::unreserve(
			&channel_id.sender.into_account_truncating(),
			open_channel_req.sender_deposit.unique_saturated_into(),
		);

		Ok(())
	}

	/// Sends/enqueues notification to the destination parachain.
	fn send_to_para(
		log_label: &str,
		config: &HostConfiguration<BlockNumberFor<T>>,
		dest: ParaId,
		notification_bytes_for: impl FnOnce(ParaId) -> polkadot_primitives::DownwardMessage,
	) {
		// prepare notification
		let notification_bytes = notification_bytes_for(dest);

		// try to enqueue
		if let Err(dmp::QueueDownwardMessageError::ExceedsMaxMessageSize) =
			dmp::Pallet::<T>::queue_downward_message(&config, dest, notification_bytes)
		{
			// this should never happen unless the max downward message size is configured to a
			// jokingly small number.
			log::error!(
				target: "runtime::hrmp",
				"sending '{log_label}::notification_bytes' failed."
			);
			debug_assert!(false);
		}
	}
