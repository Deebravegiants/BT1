## Finding

CVE-2019-3788 concerns Cloud Foundry UAA accepting wildcard subdomain redirect URIs, letting an attacker register a subdomain like `evil.legit-domain.com` to satisfy a `*.legit-domain.com` pattern and steal an OAuth access code. The chainlink Gateway HTTP server has a structurally identical flaw in its own wildcard-domain matching logic used for CORS origin allowlisting.

### Title
CORS wildcard-origin allowlist bypass via unanchored suffix match - (File: core/services/gateway/network/httpserver.go)

### Summary
`isAllowedOrigin` implements wildcard host matching for `CORSAllowedOrigins` (e.g. `*.example.com`) using a raw `strings.HasSuffix` check with no domain-boundary (leading-dot) validation, allowing any attacker-registered domain that merely ends with the configured suffix string to be treated as an allowed subdomain.

### Finding Description
In `isAllowedOrigin`, wildcard entries are handled by stripping the `*.` prefix and then checking suffix containment: [1](#0-0) 

There is no check that the character preceding the matched suffix in `originHost` is a `.` (i.e., a real subdomain boundary). Because of this, an allowlist entry `*.ethereum.org` matches not only `foo.ethereum.org` but also any domain an attacker can register that ends in the literal string `ethereum.org`, such as `notethereum.org` or `evilethereum.org` — these are unrelated, attacker-controlled domains, not subdomains of `ethereum.org`.

This function is invoked directly on the untrusted `Origin` request header in `handleRequest`, and when it returns true, the server reflects the attacker's origin back in `Access-Control-Allow-Origin`: [2](#0-1) 

This is the same bug class as CVE-2019-3788: a wildcard match intended to scope trust to genuine subdomains instead matches on unanchored substring/suffix, letting a remote unprivileged attacker who registers a lookalike domain bypass the intended allowlist restriction.

### Impact Explanation
`handleRequest` is the gateway's internet-facing HTTP entrypoint, processing job/DON requests including a JWT bearer token extracted from the `Authorization` header: [3](#0-2) 

If `CORSEnabled` and `CORSAllowedOrigins` contain a wildcard entry (as shown/tested with `*.ethereum.org`, `*.valid.domain.com`), an attacker who hosts a page on a domain such as `evilethereum.org` can have their browser JS make a cross-origin request to the gateway and successfully read the response body, because the reflected `Access-Control-Allow-Origin` will match their page's origin. This defeats the operator's intended origin restriction and can expose gateway response data (potentially including user/job data returned to the caller) to an unauthorized cross-origin site — a cross-user/cross-origin response confusion issue.

### Likelihood Explanation
Exploitation requires: (1) the gateway operator configuring a wildcard `CORSAllowedOrigins` entry (a documented, supported feature — the codebase's own tests use `*.ethereum.org`, `*.valid.domain.com`, `*.gov`), and (2) an attacker registering/controlling any domain ending in the same literal suffix. Domain registration is trivial and requires no privileges, so likelihood is moderate-to-high wherever wildcard CORS entries are used.

### Recommendation
Fix `isAllowedOrigin` to require a `.` boundary before the matched suffix (or compare against `"."+allowedHost` as the suffix) so that only genuine subdomains match, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    suffix := allowedHost[1:] // keep the leading dot, e.g. ".ethereum.org"
    if strings.HasSuffix(originHost, suffix) {
        return true
    }
}
```

### Proof of Concept
1. Configure the gateway with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.ethereum.org"]`.
2. Attacker registers `evilethereum.org` and hosts a page there that performs `fetch("https://<gateway-host>/<path>", {mode: "cors"})` with `Origin: https://evilethereum.org`.
3. `s.splitURL` extracts `originHost = "evilethereum.org"`; the wildcard check strips `*.` from `*.ethereum.org` to get `allowedHost = "ethereum.org"`, and `strings.HasSuffix("evilethereum.org", "ethereum.org")` returns `true`.
4. The server sets `Access-Control-Allow-Origin: https://evilethereum.org`, and the attacker's browser is permitted to read the cross-origin response, despite `evilethereum.org` never being an intended member of the `*.ethereum.org` allowlist. [4](#0-3)

```go
func (s *httpServer) isAllowedOrigin(origin string) bool {
	originScheme, originHost, originPort, err := s.splitURL(origin)
	if err != nil {
		s.lggr.Debug("error parsing origin URL", err)
		return false
	}
	for _, allowed := range s.config.CORSAllowedOrigins {
		// probably better to do this once when server starts and store it in a map
		// this is an easier solution so we don't have to apply more changes to the code
		// just need to be careful when specifying allowed origins in the config file
		allowedScheme, allowedHost, allowedPort, err := s.splitURL(allowed)
		if err != nil {
			s.lggr.Debug("error parsing allowed origin URL", err)
			continue
		}
		// skip if the scheme doesn't match at all
		if originScheme != allowedScheme {
			continue
		}
		// skip if the port doesn't match at all
		if originPort != allowedPort {
			continue
		}
		// check for exact host match (e.g., remix.com)
		if originHost == allowedHost {
			return true
		}
		// check for wildcard host match (e.g., *.remix.com)
		if strings.HasPrefix(allowedHost, "*.") {
			allowedHost = allowedHost[2:]
			if strings.HasSuffix(originHost, allowedHost) {
				return true
			}
		}
	}
	return false
}
```
