## Title
Gateway legacy message signature scheme lacks EIP-712-style domain separation and generic replay protection - (File: `core/services/gateway/api/message.go`)

### Summary
The Chainlink Gateway's legacy user-message protocol authenticates unprivileged, internet-facing client requests using an ad-hoc ECDSA signature scheme (`Message.Sign` / `Message.Validate` / `Message.ExtractSigner`) built on the raw EIP-191 "Ethereum Signed Message" prefix, exactly the anti-pattern flagged in the referenced Sherlock report on NFTPort's `Factory.sol`. The signed payload has no domain separator (contract/protocol identity, chain ID, or gateway instance ID) and no protocol-level nonce/expiry enforcement — freshness/anti-replay is left to individual downstream handlers to implement themselves, and is not uniformly enforced.

### Finding Description
`Message.Sign` in [1](#0-0)  builds the signed data by concatenating fixed-width `MessageID`, `Method`, `DonID`, `Receiver`, and `Payload` fields, then calls `gw_common.SignData`, which in turn calls `utils.GenerateEthSignature` — a plain EIP-191 personal-sign over the flattened bytes: [2](#0-1) 

There is no EIP-712 domain separator (no chain ID, no verifying-contract/gateway identity, no versioning tag). The only fields that vary per-deployment are `DonID` and `Receiver`, both of which are ordinary, often well-known configuration strings (e.g. `"workflow_don_1"`), not cryptographically bound network/domain identifiers.

`Message.Validate()` performs structural checks (lengths, non-null suffixes) and recovers the signer, but performs **no freshness or uniqueness check** at the protocol level: [3](#0-2) 

Anti-replay is therefore left entirely to individual handlers. The `capabilities` handler happens to add a staleness check, but only because the specific `webapicap.TriggerRequestPayload` it decodes carries its own `Timestamp` field: [4](#0-3) 

This staleness check is payload-specific, not part of the generic `Message` envelope, so any other handler built on the same `api.Message` type (e.g. `handlers.dummy.go`) has no built-in expiry or single-use enforcement of the signature itself — a captured, validly-signed `Message` can be replayed as long as the handler's own bookkeeping (e.g., `savedCallbacks` keyed by client-supplied `MessageID`) does not independently reject it: [5](#0-4) 

Because `MessageID` is fully attacker/client-controlled and not tied to any nonce registry, and the signature covers only the message body (no domain/context tag distinguishing it as "Chainlink Gateway" signed data), this design carries the same four risk categories called out in the report: (1) signature replay when a handler doesn't add its own freshness check, (2) reuse across different gateway/DON deployments that happen to share `DonID` naming, (3) absence of a proper EIP-712 domain/nonce scheme, and (4) phishing risk, since signing raw concatenated bytes via `personal_sign` gives the user's wallet no indication of what protocol/domain they are signing for — a malicious dApp using the same byte layout could trick a user into producing a signature usable against the Gateway, or vice versa.

### Impact Explanation
An attacker who intercepts (e.g., via a public relay, logs, or a malicious dApp reusing the same signing format) a validly signed `Message` can potentially replay it against handlers that do not implement their own staleness/uniqueness logic, causing duplicate job-run triggers or repeated `SendToNode` invocations to the DON member nodes on behalf of the original signer. Because the signed bytes carry no domain separator, this is a design-level authentication weakness across the whole legacy Gateway user-message surface, not confined to one handler.

### Likelihood Explanation
Moderate. Exploitation requires either a handler that omits payload-specific freshness checks (unlike `capabilities.handler`) or a scenario where a user is induced to sign the exact same generic byte layout for an unrelated purpose (classic EIP-191 phishing pattern). The `capabilities` handler mitigates timing replay via its own `Timestamp` field, reducing likelihood there, but the vulnerability is structural in `api.Message` and applies to any current or future handler built on it that doesn't reimplement the same protections.

### Recommendation
Adopt an EIP-712-style typed-data signing scheme for `api.Message`, including a proper domain separator (gateway/network identity, chain ID if applicable, protocol version) and a mandatory, protocol-level nonce/expiry check inside `Message.Validate()` itself (not left to individual handler payloads), so all handlers built on the `Message` envelope get uniform replay protection and unambiguous signing context for end users' wallets.

### Proof of Concept
1. Construct an `api.Message` with a given `MessageID`, `Method`, `DonID`, empty `Payload` (no `Timestamp` field required, since `Validate()` doesn't check one).
2. Sign it once with a user key via `msg.Sign(privateKey)` as shown in [6](#0-5) .
3. Submit the same signed `Message` bytes through `dummyHandler.HandleLegacyUserMessage` (or any handler lacking a payload-level timestamp) multiple times — each call passes `Validate()` identically since no protocol-level nonce/expiry is checked, only handler-specific `savedCallbacks` bookkeeping (keyed by the attacker-controlled `MessageID`) determines whether it is treated as new.

	}

const EthSignedMessagePrefix = "\x19Ethereum Signed Message:\n"

func GetSignersEthAddress(msg []byte, sig []byte) (recoveredAddr common.Address, err error) {
	if len(sig) != 65 {
		return recoveredAddr, errors.New("invalid signature: signature length must be 65 bytes")
	}

	// Adjust the V component of the signature in case it uses 27 or 28 instead of 0 or 1
	if sig[64] == 27 || sig[64] == 28 {
		sig[64] -= 27
	}
	if sig[64] != 0 && sig[64] != 1 {
		return recoveredAddr, errors.New("invalid signature: invalid V component")
	}

	prefixedMsg := fmt.Sprintf("%s%d%s", EthSignedMessagePrefix, len(msg), msg)
	hash := crypto.Keccak256Hash([]byte(prefixedMsg))

	sigPublicKey, err := crypto.SigToPub(hash[:], sig)
	if err != nil {
		return recoveredAddr, err
	}

	recoveredAddr = crypto.PubkeyToAddress(*sigPublicKey)
	return recoveredAddr, nil
}

func GenerateEthPrefixedMsgHash(msg []byte) (hash common.Hash) {
	prefixedMsg := fmt.Sprintf("%s%d%s", EthSignedMessagePrefix, len(msg), msg)
	return crypto.Keccak256Hash([]byte(prefixedMsg))
}

func GenerateEthSignature(privateKey *ecdsa.PrivateKey, msg []byte) (signature []byte, err error) {
	hash := GenerateEthPrefixedMsgHash(msg)
	return crypto.Sign(hash[:], privateKey)
}

func (d *dummyHandler) HandleLegacyUserMessage(ctx context.Context, msg *api.Message, callback Callback) error {
	d.mu.Lock()
	d.savedCallbacks[msg.Body.MessageID] = &savedCallback{msg.Body.MessageID, callback}
	don := d.don
	d.mu.Unlock()
	params, err := json.Marshal(msg)
	if err != nil {
		return err
	}
	rawParams := json.RawMessage(params)
	req := &jsonrpc.Request[json.RawMessage]{
		Version: "2.0",
		ID:      msg.Body.MessageID,
		Method:  msg.Body.Method,
		Params:  &rawParams,
	}
	for _, member := range d.donConfig.Members {
		err = errors.Join(err, don.SendToNode(ctx, member.Address, req))
	}
	return err
}
