Confirmed: no `email_verified` check exists anywhere in the codebase, in `handleTokenExchange` or elsewhere.### Title
OIDC callback trusts unverified `email` claim to create authenticated sessions with attacker-controlled role - ([File: core/sessions/oidcauth/oidc.go])

### Summary
The Chainlink OIDC authentication provider's `/oidc-exchange` handler extracts the `email` claim from an ID token returned by the configured OIDC Identity Provider and uses it verbatim — without checking an `email_verified` claim — as the identity key for a newly created, fully-authenticated session. This mirrors the root cause of CVE-2022-31107 (Grafana OAuth account takeover): trusting an identity attribute supplied by the IdP without confirming it was verified/owned by the authenticating user, allowing session/identity spoofing for arbitrary email addresses.

### Finding Description
In `handleTokenExchange`, after verifying the ID token signature, the code pulls the `email` claim directly from the token claims map with no verification step: [1](#0-0) 

This email is then used, unconditionally, to persist a new session row keyed by that email and a role computed purely from the token's *group* claims (which belong to the authenticating principal, not necessarily tied to the email's true owner): [2](#0-1) 

The rest of the OIDC authentication surface (`AuthorizedUserWithSession`, `ClearNonCurrentSessions`, audit logging) all key exclusively off this `user_email` value: [3](#0-2) [4](#0-3) 

There is no code path anywhere in the module (or repo) that checks `email_verified` on the ID token — confirmed by searching the entire codebase for that claim name, which returns zero matches. Many OIDC/OAuth providers (self-hosted Keycloak, generic/custom IdPs, some enterprise SSO setups) allow a user to register or set a profile `email` attribute that is not cryptographically or organizationally verified, or allow the `email` claim to be populated from a user-editable field. Because Chainlink performs no secondary verification (no check against a pre-existing local `users` row, no requirement that `email_verified=true`, no binding of a `sub`/subject identifier to a stable local account), any authenticated OIDC principal whose IdP will return an arbitrary/attacker-chosen `email` claim can cause Chainlink to mint a valid Chainlink session keyed to that (possibly victim's) email address.

This is analogous to the Grafana bug's root cause (CWE-863: Incorrect Authorization) — trusting an OAuth/OIDC-supplied identity attribute to determine account identity without validating it was actually verified/owned.

### Impact Explanation
An attacker who can authenticate to the configured upstream OIDC provider (an "unprivileged" actor from Chainlink's perspective — anyone able to log into the IdP) and who can influence the `email` claim returned to Chainlink (a realistic scenario with several common IdP configurations that don't enforce verified email or that permit custom claim mapping) can:
- Create Chainlink sessions/audit entries under a victim's email while retaining a role derived from the attacker's own IdP group memberships (potential privilege escalation if attacker's own groups map to `admin`/`edit`), and
- Pollute/impersonate identity in `oidc_sessions`, `oidc_user_api_tokens` and audit logs (`AuthLoginSuccessNo2FA` audited with the spoofed `email`), causing cross-user identity confusion, and
- Under `ClearNonCurrentSessions`, terminate/interfere with sessions of the real owner of that email since operations are keyed by `lower(user_email)`.

This is an authentication/identity-binding bypass reachable directly from an unprivileged actor's OAuth login request — the strongest severity bucket for this class of finding.

### Likelihood Explanation
Likelihood depends on the deployment's IdP configuration: this is exploitable whenever the configured OIDC Identity Provider does not strictly enforce that returned `email` claims are verified and unique per account (a documented, common OIDC integration pitfall, and exactly the scenario the upstream CVE targeted). Chainlink adds no defense-in-depth (no `email_verified` check, no correlation to a stable `sub` claim, no binding to pre-existing local accounts) to protect against this even when operators unknowingly use such an IdP.

### Recommendation
- Require and check the `email_verified` claim (reject authentication if `false` or absent) before using `email` as session identity.
- Bind sessions/roles to the stable, IdP-issued `sub` claim rather than (or in addition to) `email`, and treat `email` purely as a display attribute.
- Optionally require that the resolved email correspond to a pre-provisioned/expected identity rather than trusting any claim value verbatim.

### Proof of Concept
1. Configure Chainlink with an OIDC provider that does not enforce `email_verified` (or that allows a self-service/custom email attribute), or points at a provider where the profile email field is attacker-editable.
2. Attacker logs into the IdP with their own account, setting/mapping their `email` attribute to a victim's known Chainlink-associated email, and ensures their IdP group memberships map to `AdminClaim` per `IDClaimsToUserRole`.
3. Attacker completes `/oidc-login` → `/oidc-exchange` flow; `handleTokenExchange` reads `claims["email"]` as the victim's email with no `email_verified` check, computes `role=admin` from the attacker's own groups, and inserts a new `oidc_sessions` row keyed to the victim's email at: [5](#0-4) 
4. Attacker now holds a valid, admin-role session cookie associated with the victim's identity in Chainlink's audit trail and session table.

// AuthorizedUserWithSession will return the API user associated with the Session ID if it
// exists and hasn't expired
func (oi *oidcAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (clsessions.User, error) {
	if len(sessionID) == 0 {
		return clsessions.User{}, errors.New("session ID cannot be empty")
	}
	var foundUser clsessions.User
	err := sqlutil.TransactDataSource(ctx, oi.ds, nil, func(tx sqlutil.DataSource) error {
		// Query the oidc_sessions table for given session ID, user role and email are saved after the id claims is provided and validated
		var foundSession struct {
			UserEmail string
			UserRole  clsessions.UserRole
			Valid     bool
		}
		if err := tx.GetContext(ctx, &foundSession,
			"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM oidc_sessions WHERE id = $1",
			sessionID, oi.config.SessionTimeout().Duration(),
		); err != nil {
			if errors.Is(err, sql.ErrNoRows) {
				return clsessions.ErrUserSessionExpired
			}
			return err
		}
		if !foundSession.Valid {
			// Sessions expired, purge
			return clsessions.ErrUserSessionExpired
		}
		foundUser = clsessions.User{
			Email: foundSession.UserEmail,
			Role:  foundSession.UserRole,
		}
		return nil
	})
	if err != nil {
		if errors.Is(err, clsessions.ErrUserSessionExpired) {
			if _, execErr := oi.ds.ExecContext(ctx, "DELETE FROM oidc_sessions WHERE id = $1", sessionID); execErr != nil {
				oi.lggr.Errorf("error purging stale OIDC session: %v", execErr)
			}
		}
		return clsessions.User{}, err
	}
	return foundUser, nil
}

// ClearNonCurrentSessions removes other oidc_sessions for the user tied to sessionID.
func (oi *oidcAuthenticator) ClearNonCurrentSessions(ctx context.Context, sessionID string) error {
	var email string
	if err := oi.ds.GetContext(ctx, &email, "SELECT user_email FROM oidc_sessions WHERE id = $1", sessionID); err != nil {
		return err
	}
	_, err := oi.ds.ExecContext(ctx, "DELETE FROM oidc_sessions WHERE lower(user_email) = lower($1) AND id != $2", email, sessionID)
	return err
}
