### Title
User enumeration via timing side-channel on session login endpoint - (File: core/sessions/localauth/orm.go)

### Summary
The `/sessions` login endpoint (`SessionsController.Create` → `AuthenticationProvider().CreateSession`) exhibits a measurable response-time difference between requests for existing and non-existing user emails, allowing an unauthenticated attacker to enumerate valid Chainlink node usernames — the same bug class as CVE-2024-47057 (Mautic password-reset timing enumeration).

### Finding Description
`CreateSession` in `core/sessions/localauth/orm.go` first calls `FindUser`, which performs a single, fast SQL lookup (`SELECT * FROM users WHERE lower(email) = lower($1)`). If no row is found, the function returns immediately with an error and the request completes quickly. [1](#0-0) 

If the email *does* exist, execution proceeds to `constantTimeEmailCompare` and then `utils.CheckPasswordHash`, which performs a computationally expensive bcrypt comparison against the stored hash before returning an "Invalid password" error. [2](#0-1) 

The same asymmetric pattern (cheap failure for unknown identity vs. expensive bcrypt check for known identity) exists in the LDAP and OIDC local-fallback authenticators as well: [3](#0-2) [4](#0-3) 

This is invoked directly from the unauthenticated, internet-facing `POST /sessions` endpoint: [5](#0-4) 

An attacker with no credentials can measure the response latency for a batch of candidate emails; bcrypt verification (tens to hundreds of milliseconds depending on cost factor) versus a fast "row not found" SQL response creates a statistically distinguishable timing gap, exactly analogous to the Mautic "Forget your password" timing oracle described in GHSA-424x-cxvh-wq9p.

### Impact Explanation
An attacker can enumerate valid Chainlink node operator/API usernames without authentication. While this alone does not directly grant access, it materially aids follow-on attacks: targeted credential stuffing, phishing, or brute-force password guessing against confirmed valid accounts, and it discloses account existence information that should be confidential (CWE-203/204), matching the CVSS vector of the referenced advisory (network, low complexity, no privileges, confidentiality-low impact).

### Likelihood Explanation
Likelihood is moderate: the endpoint is unauthenticated and internet-reachable, and the timing gap introduced by bcrypt (which is deliberately slow) versus a single indexed SQL miss is typically significant and repeatable over many samples, making statistical timing analysis practical even over a network with jitter. No rate limiting on `/sessions` was found in the reviewed code, which increases feasibility of the timing measurement (many samples can be collected).

### Recommendation
Normalize response time for the login path regardless of whether the user exists: perform a constant-cost dummy `CheckPasswordHash` (or equivalent bcrypt operation) against a fixed/random hash when `FindUser` fails, before returning the "Invalid email"/"Invalid password" error. Apply the same fix uniformly to `core/sessions/localauth/orm.go`, `core/sessions/ldapauth/ldap.go` (`localLoginFallback`), and `core/sessions/oidcauth/oidc.go` (`localLoginFallback`). Additionally, consider adding rate limiting to the `/sessions` endpoint to reduce feasibility of timing-based enumeration.

### Proof of Concept
1. Send `POST /sessions` with `{"email":"admin@example.com","password":"wrongpass"}` (a known/likely-valid email) and measure response time — request proceeds through `FindUser` success + `CheckPasswordHash` bcrypt comparison, incurring bcrypt's cost delay.
2. Send `POST /sessions` with `{"email":"doesnotexist@example.com","password":"wrongpass"}` and measure response time — request fails fast at `FindUser` (`sql.ErrNoRows`), skipping the bcrypt step entirely.
3. Repeating each request N times and comparing median/average latencies reveals a consistent, statistically significant gap correlating with email existence, enabling enumeration of valid accounts on the node's `/sessions` endpoint. [6](#0-5)

func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}

func (l *ldapAuthenticator) localLoginFallback(ctx context.Context, sr sessions.SessionRequest) (sessions.User, error) {
	var user sessions.User
	sql := "SELECT * FROM users WHERE lower(email) = lower($1)"
	err := l.ds.GetContext(ctx, &user, sql, sr.Email)
	if err != nil {
		return user, err
	}

		l.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})

		l.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})

	}

	return user, nil

func (sc *SessionsController) Create(c *gin.Context) {
	defer sc.App.WakeSessionReaper()
	ctx := c.Request.Context()
	sc.App.GetLogger().Debugf("TRACE: Starting Session Creation")

	session := sessions.Default(c)
	var sr clsessions.SessionRequest
	if err := c.ShouldBindJSON(&sr); err != nil {
		jsonAPIError(c, http.StatusBadRequest, fmt.Errorf("error binding json %w", err))
		return
	}

	// Does this user have 2FA enabled?
	userWebAuthnTokens, err := sc.App.AuthenticationProvider().GetUserWebAuthn(ctx, sr.Email)
	if err != nil {
		sc.App.GetLogger().Errorf("Error loading user WebAuthn data: %s", err)
		jsonAPIError(c, http.StatusInternalServerError, errors.New("internal Server Error"))
		return
	}

	// If the user has registered MFA tokens, then populate our session store and context
	// required for successful WebAuthn authentication
	if len(userWebAuthnTokens) > 0 {
		sr.SessionStore = sc.sessions
		sr.WebAuthnConfig = sc.App.GetWebAuthnConfiguration()
	}

	sid, err := sc.App.AuthenticationProvider().CreateSession(ctx, sr)
	if err != nil {
		jsonAPIError(c, http.StatusUnauthorized, err)
		return
	}
