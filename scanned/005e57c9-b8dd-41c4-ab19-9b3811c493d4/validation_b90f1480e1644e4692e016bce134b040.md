### Title
Missing slippage protection in `SwapFirstAssetTrader::refund_weight` XCM asset swap - (File: cumulus/primitives/utility/src/lib.rs)

### Summary
`SwapFirstAssetTrader`, a `WeightTrader` implementation used by parachain runtimes to let users pay XCM execution fees in a non-native asset, swaps a user's overpaid fee back into their original asset during `refund_weight` without specifying a minimum output amount, mirroring the "no price limit" pattern described in the external report (a swap executed without a slippage/price bound, whose caller also does not independently verify the received amount).

### Finding Description
`SwapFirstAssetTrader::buy_weight` uses `SwapCredit::swap_tokens_for_exact_tokens` (which does enforce a bound via `amount_in_max` implicitly through the exact-output semantics) to convert a user-supplied asset into the `Target` fee asset. [1](#0-0) 

However, when refunding unused weight, `refund_weight` calls `SwapCredit::swap_exact_tokens_for_tokens(vec![Target::get(), refund_swap_asset], refund, None)`, explicitly passing `None` for `amount_out_min`: [2](#0-1) 

Because `amount_out_min` is `None`, `pallet-asset-conversion`'s `do_swap_exact_credit_tokens_for_tokens` skips the minimum-output check entirely: [3](#0-2) 

This is the same defect class as the reported `zapWETH` bug: a swap is executed with an attacker-influenceable pool price and no bound on the acceptable output, and the caller (`refund_weight`) does not perform any post-swap check on the amount received — it simply wraps whatever `credit_out` comes back into the refund asset and returns it: [4](#0-3) 

An attacker who can influence the state of the `Target`/`refund_swap_asset` pool (e.g., by executing large swaps against the same AMM pool in a preceding transaction/block, or by being a liquidity provider who withdraws liquidity right before the refund) can cause the refund swap to execute at an unfavorable price, so the value returned to the fee payer is smaller than it should be with no protection.

### Impact Explanation
The impact is a value-siphoning issue: the actual refunded value can be pushed arbitrarily lower than the fair-market value by manipulating the AMM pool used for the refund swap immediately before the refund executes. Since `pallet-asset-conversion` is a constant-product AMM whose price is fully determined by on-chain reserves, any actor able to submit a transaction (or a sequence of XCM/extrinsics) that shifts the pool's reserves just before the refund transaction is processed can extract value at the fee-payer's expense. This differs from the reported bug only in the AMM model (constant-product vs. concentrated-liquidity price-limit), but the missing bound and missing caller-side check are structurally identical.

### Likelihood Explanation
Likelihood is limited by several factors that reduce it below the original report's rating:
- The victim is the runtime's fee-refund mechanism, not a user-initiated deposit, so the "attacker" gains value from the pool/protocol side rather than directly stealing a specific victim's principal; the loss is bounded by the refund amount, which is typically small relative to the swapped principal.
- Exploiting it requires the attacker to time a pool-manipulating swap immediately before the refund transaction executes (front-running/sandwiching), which is possible for any unprivileged user submitting transactions on a chain using `SwapFirstAssetTrader`, but requires liquidity and precise timing.
- This code path (`SwapFirstAssetTrader`) must actually be wired into a runtime's `XcmWeightTrader`/`Trader` configuration; not all runtimes in this codebase use it, so the reachability depends on downstream runtime configuration (not verified in the indexed code for a specific production runtime).

### Recommendation
Pass a non-`None` `amount_out_min` (e.g., derived from `QuotePrice::quote_price_exact_tokens_for_tokens` at the time of refund, with a configurable slippage tolerance) to the `swap_exact_tokens_for_tokens` call in `refund_weight`, and treat a swap failure/below-minimum result the same way the code already handles the `Err` branch (falling back to crediting `total_fee` and skipping the refund) rather than allowing an unbounded-slippage swap to succeed silently.

### Proof of Concept
Conceptual PoC (cannot be executed without a runtime instance in this ask-only session):
1. Configure a runtime with `SwapFirstAssetTrader` as an XCM `WeightTrader`, with `Target` = native asset and a `pallet-asset-conversion` pool between `Target` and some `refund_swap_asset`.
2. An unprivileged actor with capital swaps a large amount against the `Target`/`refund_swap_asset` pool to skew reserves immediately before the victim's XCM message (which overpays fees in `refund_swap_asset`) is executed in the same block/pool state.
3. When `refund_weight` executes `swap_exact_tokens_for_tokens(..., None)`, the refund credited back to the fee-payer is computed at the skewed price, i.e., significantly less value than at the pre-manipulation price — no `ensure!` in `do_swap_exact_credit_tokens_for_tokens` rejects the trade because `amount_out_min` is `None`.
4. The attacker then reverses their pool-skewing swap, extracting the value differential from the AMM (funded by the discrepancy in the refund) minus normal AMM fees. [2](#0-1) [5](#0-4)

		pub(crate) fn do_swap_exact_credit_tokens_for_tokens(
			path: Vec<T::AssetKind>,
			credit_in: CreditOf<T>,
			amount_out_min: Option<T::Balance>,
		) -> Result<CreditOf<T>, (CreditOf<T>, DispatchError)> {
			let amount_in = credit_in.peek();
			let inspect_path = |credit_asset| {
				ensure!(
					path.first().map_or(false, |a| *a == credit_asset),
					Error::<T>::InvalidPath
				);
				ensure!(!amount_in.is_zero(), Error::<T>::ZeroAmount);
				ensure!(amount_out_min.map_or(true, |a| !a.is_zero()), Error::<T>::ZeroAmount);

				Self::validate_swap_path(&path)?;
				let path = Self::balance_path_from_amount_in(amount_in, path)?;

				let amount_out = path.last().map(|(_, a)| *a).ok_or(Error::<T>::InvalidPath)?;
				ensure!(
					amount_out_min.map_or(true, |a| amount_out >= a),
					Error::<T>::ProvidedMinimumNotSufficientForSwap
				);
				Ok((path, amount_out))
			};
			let (path, amount_out) = match inspect_path(credit_in.asset()) {
				Ok((p, a)) => (p, a),
				Err(e) => return Err((credit_in, e)),
			};

			let credit_out = Self::credit_swap(credit_in, &path)?;

			Self::deposit_event(Event::SwapCreditExecuted { amount_in, amount_out, path });

			Ok(credit_out)
		}
