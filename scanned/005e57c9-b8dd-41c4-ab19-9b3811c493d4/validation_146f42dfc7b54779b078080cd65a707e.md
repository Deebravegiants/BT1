### Title
Stale `PendingSwap` entry survives counterparty deregistration, allowing unauthorized swap with unrelated re-registered ParaId - ([File: polkadot/runtime/common/src/paras_registrar/mod.rs])

### Summary
`swap` implements a two-phase commit using the `PendingSwap` map: the initiator inserts `PendingSwap[id] = other`, and the counterparty confirms by calling `swap(other, id)`. `do_deregister` only clears the entry keyed by the deregistered para itself (`PendingSwap::<T>::remove(id)`), but never scans for or removes reverse-referencing entries where some other para's pending-swap target equals the deregistered id. This lets a stale swap "offer" persist across deregistration/re-registration of the counterparty ParaId and be completed by an unrelated new owner.

### Finding Description
In `swap` [1](#0-0) , the initiator (`ensure_root_para_or_owner` only checks authorization over `id`, not `other`) inserts `PendingSwap::<T>::insert(id, other)` when no matching reverse pending swap exists. The swap completes only when a later call to `swap(other_origin, other, id)` finds `PendingSwap::get(other_call_other=id) == Some(other_call_id=other)`.

`do_deregister` [2](#0-1)  removes only `PendingSwap::<T>::remove(id)` for the para being torn down — it does not search for any `X` such that `PendingSwap::get(X) == Some(id)`. Consequently, if `A`'s owner previously called `swap(A, B)` (creating `PendingSwap[A] = B`) and `B` is later deregistered by governance/owner before confirming, the dangling entry `PendingSwap[A] = B` is never cleared.

Exploit flow:
1. Owner of `A` calls `swap(A, B)` → `PendingSwap[A] = B` stored (unconfirmed).
2. `B` is deregistered (`deregister`/`do_deregister`) — this clears `PendingSwap[B]` (empty anyway) but leaves `PendingSwap[A] = B` intact.
3. A new, unrelated unprivileged user reserves and registers ParaId `B` again via `reserve`+`register` [3](#0-2) .
4. The new owner of `B` calls `swap(B, A)`. `ensure_root_para_or_owner` only checks the new owner controls `B`, which it does. The check `PendingSwap::get(A) == Some(B)` still evaluates true (stale entry from step 1), so the swap proceeds — potentially invoking `do_thread_and_chain_swap` [4](#0-3)  or `T::OnSwap::on_swap` [5](#0-4)  between `A` and the new, unrelated `B` — swapping lease/schedule/deposit-relevant state that `A`'s original owner never agreed to exchange with this new entity.

No check exists that binds the pending swap's validity to the specific `Paras::<T>` registration (e.g., a generation counter or manager identity) that existed when the offer was created, so the stale intent silently carries over to an unrelated new registration.

### Impact Explanation
An unprivileged new registrant of a reused/re-registered `ParaId` can trigger an unauthorized cross-swap of parachain lifecycle/scheduling state (and associated `OnSwap` hook effects such as lease/deposit records in the `slots`/`crowdloan` pallets) with an unrelated existing para, without consent from that para's current owner for this specific counterparty. This violates the invariant that `PendingSwap` entries must be invalidated when either side deregisters.

### Likelihood Explanation
Requires: (a) an initiator starts a swap that is never confirmed, (b) the counterparty ParaId is deregistered before confirmation, (c) the ParaId is re-registered later by any user (ParaId reuse is normal/expected since `NextFreeParaId` only increases for new reservations, but any deregistered id can be re-registered by anyone via `register`/`reserve` flow), and (d) lifecycle states at confirmation time satisfy one of the three permitted lifecycle combinations in `swap` (e.g., `A` remains a `Parachain` and new `B` is freshly registered as `Parathread`, which is the default state after `register`). All these steps use only standard signed extrinsics (`reserve`, `register`, `deregister`, `swap`) reachable by any account, making this practically triggerable, though it depends on a specific sequencing/timing window (swap left unconfirmed, then deregistration/re-registration of the counterparty before the entry is cleared/overwritten).

### Recommendation
When deregistering a para, also clear any pending swap that references it as the target, not just the entry keyed by its own id. Concretely, in `do_deregister`, in addition to `PendingSwap::<T>::remove(id)`, also remove the entry for the recorded counterparty: fetch `PendingSwap::<T>::get(id)` (if any) prior to removal, and if some `X` has `PendingSwap::<T>::get(X) == Some(id)`, remove `PendingSwap::<T>::remove(X)` as well. Since only one outstanding pending swap can reference a given id at a time under current call semantics, tracking/removing the reverse reference (or storing pending swaps bidirectionally/symmetrically so a single removal invalidates both sides) closes this gap.

### Proof of Concept
Extend `swap_handles_para_lifecycle`-style test in `polkadot/runtime/common/src/paras_registrar/tests.rs`:
1. Register `para_1` (owner 1) and `para_2` (owner 2); elevate `para_1` to a lease-holding `Parachain`, leave `para_2` as `Parathread`.
2. Owner of `para_1` calls `swap(para_1, para_2)` → asserts `PendingSwap::<Test>::get(para_1) == Some(para_2)`.
3. Governance/owner deregisters `para_2` via `deregister`/`do_deregister`; run to the session where cleanup completes.
4. Assert `PendingSwap::<Test>::get(para_1)` is still `Some(para_2)` (demonstrating the dangling entry — expected fix should make this `None`).
5. A different signed account (owner 3) `reserve`s and `register`s a brand-new para at the same `para_2` id.
6. Owner 3 calls `swap(para_2, para_1)`.
7. Current (buggy) behavior: call succeeds, emits `Swapped { para_id: para_2, other_id: para_1 }`, and `T::OnSwap::on_swap`/`do_thread_and_chain_swap` executes between `para_1` and owner 3's unrelated new registration.
   Expected (fixed) behavior: assert the call fails with `Error::<Test>::NotRegistered`/`CannotSwap`, or that `PendingSwap` was already cleared by step 4 so no swap occurs.

		pub fn swap(origin: OriginFor<T>, id: ParaId, other: ParaId) -> DispatchResult {
			Self::ensure_root_para_or_owner(origin, id)?;

			// If `id` and `other` is the same id, we treat this as a "clear" function, and exit
			// early, since swapping the same id would otherwise be a noop.
			if id == other {
				PendingSwap::<T>::remove(id);
				return Ok(());
			}

			// Sanity check that `id` is even a para.
			let id_lifecycle =
				paras::Pallet::<T>::lifecycle(id).ok_or(Error::<T>::NotRegistered)?;

			if PendingSwap::<T>::get(other) == Some(id) {
				let other_lifecycle =
					paras::Pallet::<T>::lifecycle(other).ok_or(Error::<T>::NotRegistered)?;
				// identify which is a lease holding parachain and which is a parathread (on-demand
				// parachain)
				if id_lifecycle == ParaLifecycle::Parachain &&
					other_lifecycle == ParaLifecycle::Parathread
				{
					Self::do_thread_and_chain_swap(id, other);
				} else if id_lifecycle == ParaLifecycle::Parathread &&
					other_lifecycle == ParaLifecycle::Parachain
				{
					Self::do_thread_and_chain_swap(other, id);
				} else if id_lifecycle == ParaLifecycle::Parachain &&
					other_lifecycle == ParaLifecycle::Parachain
				{
					// If both chains are currently parachains, there is nothing funny we
					// need to do for their lifecycle management, just swap the underlying
					// data.
					T::OnSwap::on_swap(id, other);
				} else {
					return Err(Error::<T>::CannotSwap.into());
				}
				Self::deposit_event(Event::<T>::Swapped { para_id: id, other_id: other });
				PendingSwap::<T>::remove(other);
			} else {
				PendingSwap::<T>::insert(id, other);
			}

	fn do_deregister(id: ParaId) -> DispatchResult {
		match paras::Pallet::<T>::lifecycle(id) {
			// Para must be a parathread (on-demand parachain), or not exist at all.
			Some(ParaLifecycle::Parathread) | None => {},
			_ => return Err(Error::<T>::NotParathread.into()),
		}
		polkadot_runtime_parachains::schedule_para_cleanup::<T>(id)
			.map_err(|_| Error::<T>::CannotDeregister)?;

		if let Some(info) = Paras::<T>::take(&id) {
			<T as Config>::Currency::unreserve(&info.manager, info.deposit);
		}

		PendingSwap::<T>::remove(id);
		Self::deposit_event(Event::<T>::Deregistered { para_id: id });
		Ok(())
	}
