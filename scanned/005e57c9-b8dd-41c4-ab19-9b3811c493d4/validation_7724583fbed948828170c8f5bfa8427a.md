### Title
Silent, unrecoverable loss of on-demand orders during `MigrateV3ToV4` when the on-demand `OrderQueue` is user-filled to capacity - (File: polkadot/runtime/parachains/src/scheduler/migration.rs)

### Summary
`UncheckedMigrateToV4::on_runtime_upgrade` migrates surviving V3 `Assignment::Pool` claim-queue entries by calling `on_demand::Pallet::<T>::push_back_order`, which silently drops the order if the on-demand `OrderQueue` is full. Because `push_back_order` bounds itself only against the hard-coded `ON_DEMAND_MAX_QUEUE_MAX_SIZE` constant (via the `BoundedVec` capacity) rather than the currently configured, potentially lower, `on_demand_queue_max_size`, whether an unprivileged user can actually force this drop depends on how close the chain's configured queue-size limit is to the hard cap.

### Finding Description
`on_demand::Pallet::<T>::push_back_order` calls `order_status.queue.try_push(now, para_id)` on the `BoundedVec<EnqueuedOrder<N>, ConstU32<ON_DEMAND_MAX_QUEUE_MAX_SIZE>>` and, on failure, only logs at `debug` level and drops the order — no error is propagated, no retry, no accounting adjustment. [1](#0-0) 

The user-facing entry point `do_place_order` (reached via `place_order_with_credits` / `place_order_allow_death`, both `ensure_signed` extrinsics) enforces admission using the *runtime-configured* `config.scheduler_params.on_demand_queue_max_size`, not the hard `ON_DEMAND_MAX_QUEUE_MAX_SIZE` constant: [2](#0-1) 

`configuration.rs`'s consistency check only requires `on_demand_queue_max_size <= ON_DEMAND_MAX_QUEUE_MAX_SIZE` — it permits, but does not require, the configured value to be strictly smaller: [3](#0-2) 

During `UncheckedMigrateToV4::on_runtime_upgrade`, every surviving V3 `Assignment::Pool` entry in the claim queue is re-inserted via `push_back_order` with no bound check against remaining OrderQueue capacity beyond the hard cap, and no fallback if it fails: [4](#0-3) 

Exploit flow: an unprivileged, signed attacker repeatedly calls `place_order_with_credits`/`place_order_allow_death` to fill `OrderStatus.queue` up to the chain's configured `on_demand_queue_max_size`. If that configured limit is at (or sufficiently close to) the hard `ON_DEMAND_MAX_QUEUE_MAX_SIZE` constant — which the configuration validation logic explicitly permits — the `OrderQueue`'s underlying `BoundedVec` has little or no remaining slack. When an operator then performs the V3→V4 runtime upgrade, `MigrateV3ToV4` calls `push_back_order` for each surviving Pool assignment; these calls fail against the (now nearly full) `BoundedVec` capacity, and the affected `para_id`s are permanently dropped — they never reappear in `peek_order_queue` and are never rescheduled, with only a `debug`-level log as evidence.

The check that stops normal users (`on_demand_queue_max_size` admission check in `do_place_order`) does not protect the migration path because `push_back_order` bypasses it entirely and only respects the wider hard cap; conversely, if the configured limit is meaningfully below the hard cap, the gap acts as unintended headroom that absorbs migration pushbacks, meaning the exploit is fully contingent on the specific runtime configuration chosen by governance for `on_demand_queue_max_size`.

### Impact Explanation
Confirmed pool assignments whose `push_back_order` call fails during the upgrade are permanently lost from the on-demand scheduling queue: the affected `ParaId`s are dropped without being re-queued, without event emission, and without state indicating the loss occurred (only a debug log line). Users who already paid for those orders (via balance withdrawal or credits, accounted for earlier in `do_place_order`) receive no service and no refund, and the affected parachains lose their already-purchased core assignment, causing service degradation until they re-purchase on-demand coretime.

### Likelihood Explanation
This is conditionally exploitable, not universally exploitable: it requires the chain's configured `on_demand_queue_max_size` to be set (by governance) close enough to the hard-coded `ON_DEMAND_MAX_QUEUE_MAX_SIZE` that ordinary user-driven queue filling via `place_order_*` leaves negligible spare capacity for the finite number of `Assignment::Pool` entries that `MigrateV3ToV4` needs to re-insert (bounded by `num_cores * lookahead`, typically small). Filling the on-demand queue itself is trivial and repeatable for an unprivileged, funded attacker (pay-per-order via `place_order_with_credits`/`place_order_allow_death`), and requires no elevated origin. The remaining precondition — the queue-size configuration gap being small at the time of the V3→V4 upgrade — is chain/governance-dependent and cannot be independently forced by the attacker, which limits generality but does not eliminate the bug: the migration code itself contains no defensive check or fallback (e.g., no queue-capacity reservation, no error escalation, no retry-after-migration mechanism) to guarantee lossless preservation of paid orders regardless of concurrent queue occupancy.

### Recommendation
In `UncheckedMigrateToV4::on_runtime_upgrade` (polkadot/runtime/parachains/src/scheduler/migration.rs), before dropping a failed `push_back_order` call, either (a) reserve capacity for in-flight Pool assignments ahead of the migration (e.g., temporarily raise the effective capacity check or evict least-eligible pending orders), or (b) collect failed migrations into a bounded auxiliary storage item that can be retried/drained post-upgrade, and emit a countable event/error metric instead of a silent debug log so operators can detect and remediate the loss. Additionally, consider enforcing `on_demand_queue_max_size < ON_DEMAND_MAX_QUEUE_MAX_SIZE` by some safety margin in the configuration consistency check to guarantee headroom for migrations of this kind.

### Proof of Concept
Rust unit test in `polkadot/runtime/parachains/src/scheduler/migration.rs` (`v4_tests` module):
1. Set `configuration::ActiveConfig::<Test>::mutate` so `scheduler_params.on_demand_queue_max_size == ON_DEMAND_MAX_QUEUE_MAX_SIZE` (or very close), and `num_cores = 1`.
2. Simulate the attacker filling `on_demand::pallet::OrderStatus::<Test>` to capacity by repeatedly invoking `on_demand::Pallet::<Test>::place_order_allow_death` (or directly `do_place_order`-equivalent extrinsic dispatch) with a funded signed account until `Error::QueueFull` is returned, confirming the queue is at `on_demand_queue_max_size` == hard cap.
3. Seed `v3::ClaimQueue::<Test>::put` with one or more `Assignment::Pool { para_id, core_index }` entries for a new `ParaId` (e.g., `ParaId::from(9999)`) not already in the queue.
4. Set `StorageVersion::new(3)` and call `UncheckedMigrateToV4::<Test>::on_runtime_upgrade()`.
5. Assert: `on_demand::Pallet::<Test>::peek_order_queue()` does NOT contain `ParaId::from(9999)`, and subsequent `pop_assignment_for_cores` never schedules it — proving the paid order was silently and permanently dropped despite `push_back_order` being invoked.
