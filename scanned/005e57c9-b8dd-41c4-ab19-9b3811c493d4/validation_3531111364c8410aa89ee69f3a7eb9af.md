### Title
Griefing DoS via front-run vesting schedule permanently blocks `payout` for a valid purchaser - (File: polkadot/runtime/common/src/purchase/mod.rs)

### Summary
`payout` re-checks `T::VestingSchedule::vesting_balance(&who).is_none()` before performing the transfer and setting `Completed`, but any unprivileged account can front-run this by giving `who` a vesting schedule via `pallet_vesting::vested_transfer` (or an equivalent public extrinsic), which is callable against any target `AccountId` with no consent required. This permanently blocks `payout` for that specific `who` with `Error::VestingScheduleExists`, since there is no recovery path in the `purchase` pallet.

### Finding Description
`payout` performs two checks against `who`'s vesting state: [1](#0-0) 
before entering `Accounts::<T>::try_mutate` and eventually calling `T::VestingSchedule::add_vesting_schedule` if `status.locked_balance` is non-zero: [2](#0-1) 

`pallet_vesting` exposes `vested_transfer(origin, target, schedule)` as a publicly callable, signed extrinsic that lets *any* signed account push funds and a vesting schedule onto *any* target `AccountId`, without the target's consent, subject only to `MinVestedTransfer` and `MaxVestingSchedules` (default vesting pallet allows exactly one schedule per account in the common configuration used with `pallet_vesting::Pallet<T>` as `VestingSchedule`).

Exploit flow:
1. `ValidityOrigin` calls `create_account(who, signature)` for a legitimate purchaser `who`. At this time `T::VestingSchedule::vesting_balance(&who)` is `None`, so `create_account` succeeds.
2. `ValidityOrigin` advances `who` to `ValidLow`/`ValidHigh` via `update_validity_status` and sets balances via `update_balance`.
3. An unprivileged attacker (no relation to `who`, no privilege needed) submits a normal `pallet_vesting::vested_transfer(target = who, schedule)` extrinsic, which succeeds and gives `who` a vesting schedule.
4. `PaymentAccount` calls `payout(origin, who)`. The check `T::VestingSchedule::vesting_balance(&who).is_none()` now returns `Some(_)`, so `payout` returns `Error::VestingScheduleExists` before any state mutation occurs.
5. Because `who`'s `AccountStatus` was never advanced to `Completed` (the failure occurs before `Accounts::try_mutate`), and there is no way in the `purchase` pallet to remove or bypass a pre-existing vesting schedule on `who`, every subsequent `payout(who)` call fails identically and permanently. `update_validity_status` and `update_balance` do not touch vesting state, so `ValidityOrigin` cannot self-heal the situation through this pallet either.

This is a genuine, reachable, permanent griefing/DoS vector triggered entirely through a normal, unprivileged extrinsic path (`pallet_vesting::vested_transfer`), independent of `T::ValidityOrigin`/`T::ConfigurationOrigin` privileges and independent of the `PaymentAccount`'s behavior. It does not enable fund theft — `T::Currency::transfer` never executes for the blocked `who` since the vesting check aborts before the `try_mutate` block runs — but it does permanently lock a legitimate purchaser out of their configured payout, contradicting the intended invariant that "a valid, fully-processed purchaser must eventually be payable exactly once."

### Impact Explanation
A griefer can permanently deny a specific, legitimate DOT-purchase participant their promised payout (both `free_balance` and `locked_balance`) by spending a small amount to open a vesting schedule against that participant's `AccountId` before the `PaymentAccount` executes `payout`. The purchaser's funds are never transferred and there is no extrinsic in the `purchase` pallet to clear or override the vesting-schedule pre-check, so the block is permanent absent off-chain/governance-level remediation (e.g., a storage migration or an unrelated privileged fix outside this pallet). This is a fund-lock/DoS impact on a per-victim basis, not a theft of the `PaymentAccount` balance.

### Likelihood Explanation
The attack requires no special privilege — merely a signed account with enough balance to satisfy `pallet_vesting`'s `MinVestedTransfer`, and knowledge of the target purchaser's `AccountId`, which is realistically discoverable (purchaser identities/addresses used in the sale are often known or inferable, e.g., from `AccountCreated`/`ValidityUpdated`/`BalanceUpdated` events emitted by this very pallet). The race window is between account creation/validation and the operator's `payout` call, which can span a considerable time in practice, making front-running highly feasible and fully repeatable against any number of purchasers.

### Recommendation
Do not let `payout` permanently fail due to a pre-existing vesting schedule created outside the pallet's control. Options:
- On `payout`, if `who` already has a vesting schedule, still perform the currency transfer for `free_balance`/`locked_balance` and mark the account `Completed`, deferring/skipping only the `add_vesting_schedule` call (or merging into the existing schedule) instead of aborting the whole extrinsic.
- Alternatively, perform the `VestingScheduleExists` check only once — at `create_account` time — and remove it from `payout`, since `create_account` already guards against pre-existing schedules; if a schedule appears afterward, `payout` should handle it gracefully (e.g., transfer only the free balance and record locked-balance vesting failure via an event) rather than reverting the whole call with no recovery path.
- Add a privileged/administrative extrinsic (guarded by `T::ConfigurationOrigin` or `T::ValidityOrigin`) that can force-complete or reset a stuck `who` in this exact griefed state.

### Proof of Concept
Rust unit test in `polkadot/runtime/common/src/purchase/tests.rs` mock environment:
1. Call `create_account` for `who` (ValidityOrigin) — assert success.
2. Call `update_validity_status(who, ValidHigh)` and `update_balance(who, free, locked, vat)` — assert success.
3. Before calling `payout`, directly invoke the mock `VestingSchedule::add_vesting_schedule(&who, locked_amount, per_block, starting_block)` (simulating an attacker's `pallet_vesting::vested_transfer` extrinsic reaching `who`) — assert success.
4. Call `payout(payment_account_origin, who)` — assert it returns `Err(Error::<Test>::VestingScheduleExists)`.
5. Call `payout` again — assert it still returns `Err(Error::<Test>::VestingScheduleExists)`, demonstrating the permanent block.
6. Assert `Accounts::<Test>::get(&who).validity` is still `ValidHigh` (never reaches `Completed`) and the `PaymentAccount`'s and `who`'s balances are unchanged, confirming funds are locked/stuck rather than stolen.
