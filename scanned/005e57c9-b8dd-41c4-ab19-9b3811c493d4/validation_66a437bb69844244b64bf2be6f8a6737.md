## Analog Vulnerability Confirmed

### Title
Permissioned contract deployment (`InstantiateOrigin`/`UploadOrigin`) can be bypassed via nested `CREATE`/`CREATE2` from within a contract - (File: `substrate/frame/contracts/src/lib.rs`, `substrate/frame/revive/src/lib.rs`, `substrate/frame/revive/src/exec.rs`)

### Summary
Both `pallet-contracts` and `pallet-revive` gate top-level, dispatchable-originated contract deployment (`instantiate`, `instantiate_with_code`, `upload_code`) behind configurable origin filters (`T::InstantiateOrigin`, `T::UploadOrigin`). This is exactly analogous to `minievm`'s `AllowedPublishers` mechanism referenced in the external report. Critically, the Polkadot SDK maintainers have already documented this exact bypass class themselves.

### Finding Description
`InstantiateOrigin`/`UploadOrigin` checks are enforced only in the pallet's dispatchable entry points and in `bare_instantiate`, e.g.: [1](#0-0) [2](#0-1) 

However, when a contract itself instantiates another contract (i.e., the `CREATE`/`CREATE2` EVM opcodes in `pallet-revive`'s interpreter, or the `seal_instantiate` host function path that both pallets expose to contract code), this origin check is **not** re-applied. The nested instantiate path goes through `exec.rs`'s frame-building logic: [3](#0-2) 
which is reached from the EVM `CREATE`/`CREATE2` opcode handler: [4](#0-3) 
There is no call to `T::InstantiateOrigin::ensure_origin` anywhere in this nested path — the deployer is simply "the calling contract," with no re-check against the origin filter.

This is confirmed to be a known, currently-undocumented-in-full limitation: the very PR that introduced permissioned deployment for `pallet-contracts` explicitly states the caveat: [5](#0-4) 

Existing tests (`only_instantiation_origin_can_instantiate` in both pallets) only assert that direct, dispatchable-originated instantiation by a non-whitelisted account fails — they do **not** test (and thus do not guard against) a whitelisted account first deploying a permissionless "factory" contract that any third party can then call to instantiate arbitrary child contracts: [6](#0-5) [7](#0-6) 

Instead, the test suite explicitly exercises and validates the *unrestricted* nested-instantiate path (`instantiation_from_contract`, `deploy_and_call_other_contract`, `create_works`/`create2_works` for Solidity `CREATE`/`CREATE2`), confirming that any contract — regardless of its deployer's identity — can freely instantiate new contracts with no origin gate: [8](#0-7) [9](#0-8) 

### Impact Explanation
If a runtime configures `InstantiateOrigin`/`UploadOrigin` to restrict who may deploy contracts (a legitimate, supported configuration pattern, e.g., for permissioned/consortium chains), a single whitelisted account can deploy one "factory" contract whose constructor or a callable function performs `CREATE`/`CREATE2`/`seal_instantiate`. Any unprivileged account can then call that factory to deploy arbitrary bytecode, completely bypassing the deployment restriction the runtime operator intended to enforce. This mirrors the `minievm` finding precisely, but here the SDK explicitly documents it as accepted/known behavior for `pallet-contracts`, and the same architecture exists unchanged in `pallet-revive`.

### Likelihood Explanation
Likelihood is high for any runtime that actually sets `InstantiateOrigin`/`UploadOrigin` to something other than `EnsureSigned`/permissionless (the default in `substrate/bin/node/runtime/src/lib.rs` uses `EnsureSigned`, so this is not exploitable out-of-the-box, but is exploitable in any runtime that opts into restricted deployment — which is the entire purpose of the config option). No special privilege is needed by the attacker; only one initial whitelisted deployer is required, and that deployer's factory contract need not be malicious itself for the exploit to work — it only needs to relay `CREATE`.

### Recommendation
As with the Evmos precedent cited in the original report, `pallet-contracts`/`pallet-revive` should re-check the instantiate/upload origin restriction inside the nested `Ext::instantiate` path in `exec.rs` (and the `CREATE`/`CREATE2` EVM opcode handlers in `pallet-revive`'s interpreter), not only at the dispatchable-call boundary. This would require passing origin/caller-identity context through to the check, or alternatively documenting this limitation prominently as a known-and-accepted risk (as `pallet-contracts`' prdoc already does) so that runtime operators relying on `InstantiateOrigin` restrictions are aware their guarantee does not survive nested instantiation.

### Proof of Concept
1. Runtime configures `T::InstantiateOrigin` to `EnsureSignedBy<Whitelist>` restricting deployment to a small set of addresses (per the pattern validated by `only_instantiation_origin_can_instantiate` tests).
2. A whitelisted account calls `instantiate_with_code`/`bare_instantiate` to deploy a "Factory" contract whose exported function performs `CREATE`/`CREATE2` (or `seal_instantiate`) with attacker-supplied init code, mirroring the pattern in [9](#0-8) .
3. Any non-whitelisted account calls the Factory contract, supplying arbitrary bytecode.
4. The nested `Ext::instantiate` call in `exec.rs` succeeds without checking `InstantiateOrigin`, deploying the attacker's arbitrary contract — bypassing the intended restriction entirely.

#[test]
fn only_instantiation_origin_can_instantiate() {
	let (code, code_hash) = compile_module::<Test>("dummy").unwrap();
	InstantiateAccount::set(Some(ALICE));
	ExtBuilder::default().build().execute_with(|| {
		let _ = Balances::set_balance(&ALICE, 1_000_000);
		let _ = Balances::set_balance(&BOB, 1_000_000);

		assert_err_ignore_postinfo!(
			builder::instantiate_with_code(code.clone())
				.origin(RuntimeOrigin::root())
				.build(),
			DispatchError::BadOrigin
		);

		assert_err_ignore_postinfo!(
			builder::instantiate_with_code(code.clone())
				.origin(RuntimeOrigin::signed(BOB))
				.build(),
			DispatchError::BadOrigin
		);

		// Only Alice can instantiate
		assert_ok!(builder::instantiate_with_code(code).build());

		// Bob cannot instantiate with either `instantiate_with_code` or `instantiate`.
		assert_err_ignore_postinfo!(
			builder::instantiate(code_hash).origin(RuntimeOrigin::signed(BOB)).build(),
			DispatchError::BadOrigin
		);
	});
}

#[test]
fn create_works() {
	let (caller_code, _) = compile_module_with_type("Caller", FixtureType::Solc).unwrap();
	let (callee_code, _) = compile_module_with_type("Callee", FixtureType::Solc).unwrap();

	ExtBuilder::default().build().execute_with(|| {
		let _ = <Test as Config>::Currency::set_balance(&ALICE, 1_000_000_000);

		let Contract { addr: caller_addr, .. } =
			builder::bare_instantiate(Code::Upload(caller_code)).build_and_unwrap_contract();

		let create_call_data =
			Caller::createCall { initcode: Bytes::from(callee_code.clone()) }.abi_encode();

		let result = builder::bare_call(caller_addr)
			.data(create_call_data)
			.native_value(1_000)
			.build_and_unwrap_result();

		let callee_addr = Caller::createCall::abi_decode_returns(&result.data).unwrap();
		let magic_number = 42u64;

		// Check if the created contract is working
		let echo_result = builder::bare_call(callee_addr.0.0.into())
			.data(Callee::echoCall { _data: magic_number }.abi_encode())
			.build_and_unwrap_result();

		let echo_output = Callee::echoCall::abi_decode_returns(&echo_result.data).unwrap();

		assert_eq!(magic_number, echo_output, "Callee.echo must return 42");
	});
}
