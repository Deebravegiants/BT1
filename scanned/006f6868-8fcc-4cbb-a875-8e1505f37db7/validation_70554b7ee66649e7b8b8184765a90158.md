### Title
Case-sensitive owner-label equality check in `EnsureRightLabelOnSecret` bypasses the codebase's mandated `NormalizeOwner` comparison, unlike every other owner-matching path - ([File: core/capabilities/vault/validator.go])

### Summary
`EnsureRightLabelOnSecret` computes the expected TDH2 ciphertext label from the raw `owner` string via `vaultutils.WorkflowOwnerToLabel(owner)` and compares it to the ciphertext's embedded label with a strict `==`, instead of normalizing both sides first. Every sibling owner-comparison function in the same package (`validateEncryptedSecretOwnerMismatch`, `validateSecretIdentifierOwnerMismatch`, the uniform-owner checks in `capability.go`, and the list-owner check in `authorizer.go`) explicitly calls `vaultutils.NormalizeOwner()` on both operands before comparing, because owner addresses can legitimately arrive checksummed (EIP-55, mixed case) or lower-case from different code paths (client-supplied `SecretIdentifier.Owner` vs. authorized/derived workflow owner). `EnsureRightLabelOnSecret` is the one place that skips this normalization.

### Finding Description
`WorkflowOwnerToLabel` derives a fixed-size label from the string form of the owner address (analogous to how `unstakeAndExitPool` converts ETH into WETH but leaves the *identity check* comparing raw addresses). The label embedded in an already-encrypted ciphertext was computed by the client at encryption time using whatever casing of the owner address it had on hand (commonly the checksummed EIP-55 form returned by wallets/SDKs). `EnsureRightLabelOnSecret` then recomputes the expected label from `req.Id.Owner` (the `SecretIdentifier.Owner` string from the JSON-RPC payload) without normalizing case, and does a strict `secretLabel == expected` array comparison. [1](#0-0) 

If the value supplied in `SecretIdentifier.Owner` differs only in case from the value used to derive the label at encryption time (both of which are logically "the same owner" per every other check in this codebase, since `NormalizeOwner` explicitly lower-cases and strips `0x`), the comparison fails even though `NormalizeOwner`-based checks elsewhere in the same request pipeline (`validateEncryptedSecretsUniformOwners`, `validateSecretOwnersMatchAuthorized`) would treat the identifiers as matching. [5](#0-4) [6](#0-5) 

This function is invoked from `validateWriteRequest` (used by `ValidateCreateSecretsRequest`/`ValidateUpdateSecretsRequest`) in the non-skip-label-validation branch, which is the standard path for allowlist-authenticated (non-JWT-skip) create/update requests reaching a vault node from the gateway. [4](#0-3) 

### Impact Explanation
A legitimate, correctly-authorized client whose `SecretIdentifier.Owner` string differs in case from the label baked into the ciphertext (e.g., client encrypts using a checksummed address but later — or via a different SDK/tool — submits the identifier in lower-case, or vice versa) will have valid `CreateSecrets`/`UpdateSecrets` requests rejected with "doesn't have owner as the label" even though the owner-matching logic used for authorization (`NormalizeOwner`-based) would accept the same pair as identical. This is a functional/availability defect analogous to the reported DoS: an operation that other parts of the system treat as equivalent gets rejected due to an inconsistent, stricter comparison, blocking legitimate secret creation/update for affected owners until they resubmit with exactly matching casing.

### Likelihood Explanation
Likelihood is moderate: it requires that the owner-address casing used to build the label at encryption time differ from the casing supplied in the `SecretIdentifier.Owner` field of the JSON-RPC request — a realistic scenario in a mixed-tooling ecosystem where different SDKs/wallets normalize EVM addresses differently (checksummed vs lower-case), and where the codebase's own test suite (`zone_b_restriction_test.go` MUST-4) demonstrates this exact mixed-case scenario is a real concern elsewhere in the vault stack. [7](#0-6) 

### Recommendation
Normalize both operands in `EnsureRightLabelOnSecret` the same way every other owner-comparison site does — i.e., derive the expected label from `vaultutils.NormalizeOwner(owner)` (or otherwise ensure `WorkflowOwnerToLabel` normalizes internally) so that the label check is case-insensitive and consistent with `validateEncryptedSecretOwnerMismatch`/`validateSecretIdentifiersUniformOwners`/`validateSecretOwnersMatchAuthorized`.

### Proof of Concept
1. Client encrypts a secret with `EncryptSecretWithWorkflowOwner(value, publicKey, ownerAddr)` where `ownerAddr` is the checksummed (mixed-case) EIP-55 form, e.g. `0xAbCdEf...`. The resulting TDH2 ciphertext label is derived from that mixed-case string.
2. Client (or a different tool) submits a `CreateSecretsRequest` with `SecretIdentifier{Owner: "0xabcdef..."}` (lower-cased) — a value that `NormalizeOwner` treats as identical to the mixed-case original, and which would pass `validateEncryptedSecretsUniformOwners`/`validateSecretOwnersMatchAuthorized`.
3. `validateWriteRequest` calls `EnsureRightLabelOnSecret(publicKey, req.EncryptedValue, req.Id.Owner)` with the lower-cased owner string. [8](#0-7) 
4. `WorkflowOwnerToLabel("0xabcdef...")` produces a different label than the one embedded in the ciphertext (which was derived from the mixed-case string), so `secretLabel == expected` fails and the request is rejected with `"doesn't have owner as the label"`, despite the owner being the authorized, correctly-matching owner under every other check in the system.

func EnsureRightLabelOnSecret(publicKey *tdh2easy.PublicKey, secret, owner string) error {
	cipherText, err := verifyEncryptedSecret(publicKey, secret)
	if err != nil {
		return err
	}
	if cipherText == nil {
		return nil
	}
	if owner == "" {
		return errors.New("owner must not be empty for secret label verification")
	}

	expected := vaultutils.WorkflowOwnerToLabel(owner)
	secretLabel := cipherText.Label()
	if secretLabel == expected {
		return nil
	}

	return fmt.Errorf("secret label [%s] does not match workflow owner label [%s]",
		hex.EncodeToString(secretLabel[:]), hex.EncodeToString(expected[:]))
}

	return strings.ToLower(strings.TrimPrefix(owner, "0x"))

func validateEncryptedSecretOwnerMismatch(encryptedSecrets []*vaultcommon.EncryptedSecret, workflowOwner string) error {
	if len(encryptedSecrets) == 0 {
		return errors.New("request batch must contain at least 1 item")
	}
	for idx, encryptedSecret := range encryptedSecrets {
		if encryptedSecret == nil {
			return fmt.Errorf("encrypted secret must not be nil at index %d", idx)
		}
		if encryptedSecret.Id == nil {
			return fmt.Errorf("secret ID must not be nil at index %d", idx)
		}
		if vaultutils.NormalizeOwner(encryptedSecret.Id.Owner) != vaultutils.NormalizeOwner(workflowOwner) {
			return fmt.Errorf("encrypted secret owner at index %d %q does not match authorized workflow owner %q", idx, encryptedSecret.Id.Owner, workflowOwner)
		}
	}
	return nil
}
