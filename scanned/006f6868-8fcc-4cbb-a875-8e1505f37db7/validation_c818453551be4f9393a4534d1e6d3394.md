Based on my investigation, I found a genuine analog: the HTTP action response cache's `Hash()` function excludes `WorkflowID` from its key, meaning cached HTTP responses can be served across different workflows despite the documented intent of workflow isolation.### Title
Outbound HTTP action response cache key excludes WorkflowID, causing cross-workflow response confusion - (File: core/services/gateway/handlers/capabilities/v2/response_cache.go)

### Summary
The Pendle `lend` bug is a "wrong value trusted from a shared/derived source" class of bug — the code trusts data at the wrong granularity/index, causing state or funds to be misattributed to the wrong party. The analogous pattern in this repo is the HTTP-action `responseCache`, whose cache key (`OutboundHTTPRequest.Hash()`) is computed from method/URL/headers/body/workflow owner but explicitly **excludes `WorkflowID`**, even though the component's own documentation and code comments claim "workflow-scoped caching" / "cache entries are scoped by workflow ID to prevent cross-workflow data leakage."

### Finding Description
`responseCache.Fetch` and `.Set` key cached HTTP responses using `req.Hash()`: [1](#0-0) 

The comment on the struct itself states the hash is built from "method, URL, headers, body, workflowOwner" — `workflowID` is not part of the key: [2](#0-1) 

This is confirmed by the handler's own unit test, which explicitly asserts that two requests with different `WorkflowID` values produce the **same** hash: [3](#0-2) 

Yet the component's README documents the opposite guarantee — that cache entries are workflow-ID-scoped specifically to prevent cross-workflow data leakage: [4](#0-3) 

The cache is populated and read from `makeOutgoingRequest`, which is reached whenever any workflow node sends an outbound HTTP action request through the gateway with `CacheSettings.Store`/`MaxAgeMs` set — an unprivileged-actor-reachable path from any workflow (owner) that can schedule an HTTP action capability call: [5](#0-4) 

Because the key only binds on `(method, URL, headers, body, workflowOwner)`, two different workflows belonging to the **same workflow owner** (a very common case — one org/owner can register many workflows) that issue identical HTTP requests (same method/URL/headers/body, e.g. a shared API call, mTLS-less GET to a common endpoint) will collide on the same cache entry. A response fetched and cached for Workflow A can then be served — via `Fetch`'s `MaxAgeMs`-gated cache hit — to Workflow B without ever contacting the external endpoint, and vice versa.

### Impact Explanation
This breaks the documented workflow isolation guarantee and can produce cross-workflow response confusion: a workflow legitimately entitled to fresh or workflow-specific data can receive another workflow's stale/cached response body from an external endpoint. Depending on what the HTTP action call is used for downstream (e.g., feeding pricing, authorization tokens, status codes, or business-logic branch decisions into the workflow), this can cause a workflow to act on data that was never actually returned for its own request — a form of cross-user/cross-tenant response confusion, one of the explicitly accepted impact categories. It does not require any node/peer compromise: any workflow owner running two workflows that happen to hit the same external URL with the same payload triggers the collision.

### Likelihood Explanation
Likelihood is moderate-to-high in normal operation, not just adversarial: this is a same-owner, different-workflow collision that can occur organically whenever two workflows under one owner query the same external endpoint with identical parameters — a common pattern for shared data sources (e.g., price feeds, common REST APIs). It requires no privileged access and no malicious peer/node — only that the workflow owner enables caching (`CacheSettings.Store`/`MaxAgeMs`) on the HTTP action task, which is entirely under the caller's control via workflow definition.

### Recommendation
Include `WorkflowID` in `OutboundHTTPRequest.Hash()` (or in the composed cache key used by `responseCache.Fetch`/`Set`) so cache entries are truly scoped per workflow, matching the documented isolation guarantee. Update `TestRequestHash`'s "having different workflowID results in same Hash" test, which currently locks in the incorrect behavior, to require workflow-ID differentiation instead.

### Proof of Concept
1. Workflow A (owner `0xOwner`) issues an HTTP action: `GET https://api.example.com/data`, `CacheSettings.Store=true`, `MaxAgeMs=600000`, `WorkflowID = "wfA"`. The gateway calls the external endpoint, gets response R1, and stores it in `responseCache` under `Hash(method, url, headers, body, "0xOwner")` (no `wfA` component).
2. Workflow B (same owner `0xOwner`, different `WorkflowID = "wfB"`) issues an HTTP action with identical method/URL/headers/body and `CacheSettings.MaxAgeMs>0`.
3. Because `Hash()` produces the same key for both requests (as demonstrated in `TestRequestHash`'s "different workflowID results in same Hash" subtest), `responseCache.Fetch` returns the cached R1 to Workflow B without making any external call — even though Workflow B never had its own request served, and R1 may be stale, endpoint-side-effect-bearing, or logically scoped to Workflow A's execution context.

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	requestID := resp.ID
	h.lggr.Debugw("handling outgoing message", "requestID", requestID, "nodeAddr", nodeAddr)
	var req gateway_common.OutboundHTTPRequest
	err := json.Unmarshal(*resp.Result, &req)
	if err != nil {
		return fmt.Errorf("failed to unmarshal HTTP request from node %s: %w", nodeAddr, err)
	}
	timeout := time.Duration(req.TimeoutMs) * time.Millisecond
	httpReq := network.HTTPRequest{
		Method:           req.Method,
		URL:              req.URL,
		Headers:          req.Headers, //nolint:staticcheck // forward deprecated Headers for backward compatibility; request uses MultiHeaders when set
		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}

	sendResponseTimeout := time.Duration(defaultSendResponseTimeoutMs) * time.Millisecond

	// send response to node async
	h.wg.Go(func() {
		// not cancelled when parent is cancelled to ensure the goroutine can finish
		baseCtx := context.WithoutCancel(ctx)
		httpCtx, httpCancel := context.WithTimeout(baseCtx, timeout)
		defer httpCancel()
		l := logger.With(h.lggr, "requestID", requestID, "method", req.Method, "timeout", req.TimeoutMs)
		var outboundResp gateway_common.OutboundHTTPResponse
		callback := h.createHTTPRequestCallback(httpCtx, requestID, httpReq, req)
		if req.CacheSettings.MaxAgeMs > 0 {
			h.metrics.IncrementCacheReadCount(ctx, h.lggr)
			outboundResp = h.responseCache.Fetch(httpCtx, req, callback, req.CacheSettings.Store)
		} else {
			outboundResp = callback()
			if req.CacheSettings.Store {
				h.responseCache.Set(req, outboundResp)
			}
		}
