Based on my investigation, I found a stale-cache bug in the Vault gateway/node handlers that mirrors the CVE's bug class: a cached security-relevant object (there, a cached prepared statement; here, the vault DKG master public key) is served from cache indefinitely, with the mechanism meant to refresh/invalidate it silently short-circuited.

### Title
Vault master public key is cached indefinitely with no expiry/invalidation, and the periodic "refresh" path is a no-op — ([File: core/capabilities/vault/gw_handler.go])

### Summary
Both the vault-node-side `GatewayHandler` and the gateway-side vault `handler` cache the threshold-encryption (`tdh2easy`) master public key in memory and never invalidate it once populated. On the node side there is no refresh mechanism at all; on the gateway side there is a ticker meant to refresh the cache, but the refresh call is intercepted by the same cache-hit short-circuit it is supposed to bypass, making it a no-op once the cache is warm.

### Finding Description
`GatewayHandler.getMasterPublicKey` on the vault node fetches the master public key once from `MasterPublicKeyFromSecretsService`, stores it in `h.cachedMasterPublicKey`, and forever after returns the cached copy with no TTL, no version check, and no external trigger to invalidate it: [1](#0-0) 

This cached key is fed directly into request authorization for the two write paths reachable from unprivileged workflow-owner requests: `MethodSecretsCreate` and `MethodSecretsUpdate` route through `h.requestProcessor.ProcessRequest(ctx, req, publicKey)`: [2](#0-1) 

On the gateway side, `handler.fetchVaultPublicKey` is invoked by a 1-minute ticker specifically to "periodically ... fetch vault public key, so we can cache it" — i.e., to refresh the cache: [3](#0-2) 

But that fetch flows into `handlePublicKeyGet`, whose very first branch checks `getCachedPublicKey()` and, if non-nil, returns the stale cached bytes immediately — it never reaches `fanOutToVaultNodes` to actually re-query nodes once a value is cached: [4](#0-3) 

The comment at the call site for user-facing `MethodPublicKeyGet` requests makes the same design explicit — "we cache this value quite aggressively so don't need to worry about DoS" — with no eviction/expiry logic anywhere (`cachedPublicKeyGetResponse`/`cachedPublicKeyObject` are only ever set in `tryCachePublicKeyResponse`, never cleared): [5](#0-4) [6](#0-5) 

This is structurally the same defect class as CVE-2026-58041: a cache/state-holder is supposed to be kept fresh via an explicit refresh/invalidation path, but that path is bypassed by the same "if cached, return early" logic the invalidation mechanism was meant to override — so once populated, the cached object is used forever regardless of the true, current upstream state.

### Impact Explanation
If the DKG/master key material is ever rotated on the vault nodes (e.g., due to a re-share, quorum change, or as a security response to key compromise), the node-side `GatewayHandler` and the gateway-side response cache continue trusting/serving the old public key indefinitely — there is no code path that ever clears `cachedMasterPublicKey` or `cachedPublicKeyGetResponse`. Because the cached public key is used as an authorization input for `SecretsCreate`/`SecretsUpdate` (`ProcessRequest(ctx, req, publicKey)`), and is also served directly to any caller of `MethodPublicKeyGet`, a security-motivated key rotation would not actually take effect on already-running nodes/gateways without a restart, silently defeating the intended invalidation/rotation boundary. Unprivileged users only interact with the effect (stale key served/used), not with an authentication bypass by themselves, so the severity is bounded to "key rotation doesn't take effect" rather than a direct authorization bypass I could fully confirm.

### Likelihood Explanation
The bug fires automatically on any node/gateway process that has already served one successful `MethodPublicKeyGet` — no attacker action is required to trigger the caching; it is the default steady-state behavior. It only becomes a real security incident in the event of a genuine key rotation, so likelihood of exploitation depends on operational key-rotation practices, which I could not fully verify from the code alone within the investigation budget.

### Recommendation
Add explicit invalidation to both caches: (1) in `core/capabilities/vault/gw_handler.go`, add a TTL or an explicit invalidation hook tied to `MasterPublicKeyFromSecretsService` changes so `cachedMasterPublicKey` cannot outlive a rotation; (2) in `core/services/gateway/handlers/vault/handler.go`, make `fetchVaultPublicKey`/`handlePublicKeyGet`'s periodic-refresh path bypass the cache check (i.e., always fan out to nodes on the ticker, updating the cache from the fresh response) instead of short-circuiting on `getCachedPublicKey()`.

### Proof of Concept
Not exploitable via a single external request; this is a state-machine/caching defect. Reproduction requires: (1) start a vault node and gateway, (2) trigger one successful `MethodPublicKeyGet` to warm both caches, (3) rotate/replace the underlying master key material in `SecretsService`, (4) observe that `GatewayHandler.getMasterPublicKey` (core/capabilities/vault/gw_handler.go:238-261) and the gateway's `handler.getCachedPublicKey` (core/services/gateway/handlers/vault/handler.go:680-690) continue returning the old key indefinitely, and that the 1-minute refresh ticker never issues a fresh node round-trip because `handlePublicKeyGet` (handler.go:692-708) returns on cache hit before calling `fanOutToVaultNodes`.

**Note on limitations**: I was unable to fully trace how `publicKey` is consumed inside `requestProcessor.ProcessRequest` / `validator.go` / `verify.go` (e.g., whether it verifies ciphertext-to-key binding or a signed digest) within the remaining tool budget, so the precise security consequence of using a stale key for authorization (versus merely serving stale read-only data) is not fully confirmed. A deeper look at `core/capabilities/vault/validator.go` and `core/capabilities/vault/verify.go` would be needed to state the exact authorization impact with certainty.

func (h *GatewayHandler) getMasterPublicKey(ctx context.Context) (*tdh2easy.PublicKey, error) {
	h.mu.RLock()
	if h.cachedMasterPublicKey != nil {
		cachedCopy := *h.cachedMasterPublicKey
		h.mu.RUnlock()
		return &cachedCopy, nil
	}
	h.mu.RUnlock()

	publicKey, err := MasterPublicKeyFromSecretsService(ctx, h.secretsService)
	if err != nil {
		return nil, err
	}

	h.mu.Lock()
	defer h.mu.Unlock()
	if h.cachedMasterPublicKey != nil {
		cachedCopy := *h.cachedMasterPublicKey
		return &cachedCopy, nil
	}
	h.cachedMasterPublicKey = publicKey
	cachedCopy := *publicKey
	return &cachedCopy, nil
}

func (h *handler) tryCachePublicKeyResponse(resp *jsonrpc.Response[json.RawMessage], l logger.Logger) {
	if resp.Result == nil {
		l.Debugw("no result in public key response, not caching")
		return
	}

	r := &vaultcommon.GetPublicKeyResponse{}
	err := h.unmarshal(bytes.NewReader(*resp.Result), r)
	if err != nil {
		l.Debugw("failed to unmarshal public key response, not caching", "error", err)
		return
	}

	if r.PublicKey == "" {
		l.Debugw("no public key in unmarshaled response, not caching", "response", resp, "result", r)
		return
	}
	masterPublicKey := tdh2easy.PublicKey{}
	masterPublicKeyBytes, err := hex.DecodeString(r.PublicKey)
	if err != nil {
		l.Debugw("failed to decode master public key string", "error", err)
		return
	}
	err = masterPublicKey.Unmarshal(masterPublicKeyBytes)
	if err != nil {
		l.Debugw("failed to unmarshal master public key", "error", err)
		return
	}

	h.mu.Lock()
	h.cachedPublicKeyGetResponse = *resp.Result
	h.cachedPublicKeyObject = &masterPublicKey
	h.mu.Unlock()
	l.Debugw("successfully cached public key response")
}

func (h *handler) handlePublicKeyGet(ctx context.Context, ar *activeRequest) error {
	l := logger.With(h.lggr, "method", ar.req.Method, "requestID", ar.req.ID)

	publicKeyResponseBytes, cachedPublicKey := h.getCachedPublicKey()
	if cachedPublicKey != nil {
		l.Debugw("returning cached public key response")
		return h.sendSuccessResponse(ctx, l, ar, &jsonrpc.Response[json.RawMessage]{
			Version: jsonrpc.JsonRpcVersion,
			ID:      ar.req.ID,
			Method:  ar.req.Method,
			Result:  (*json.RawMessage)(&publicKeyResponseBytes),
		})
	}

	l.Debugw("cache stale: forwarding request to nodes", "now", h.clock.Now())
	return h.fanOutToVaultNodes(ctx, l, ar)
}
