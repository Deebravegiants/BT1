## Analysis Result

A concrete, reachable timing side-channel exists in the local authentication login path.

### Title
Username/Email Enumeration via Timing Side-Channel in Login Endpoint - (File: `core/sessions/localauth/orm.go`)

### Summary
The `CreateSession` login flow performs a fast database lookup for the supplied email and returns immediately on a "user not found" error, but only invokes the expensive `bcrypt.CompareHashAndPassword` operation when the email *does* exist. This asymmetry in computation time between "email not found" and "email found, password wrong" allows an unauthenticated remote attacker to enumerate valid email addresses/usernames on the node purely by measuring response latency of the public `/sessions` login endpoint.

### Finding Description
In `orm.CreateSession`, the flow is:
1. `o.FindUser(ctx, sr.Email)` — a cheap SQL lookup. If no matching row, returns immediately with error. [1](#0-0) 
2. Only if the user is found does the code proceed to `constantTimeEmailCompare` and then `utils.CheckPasswordHash`, which internally calls `bcrypt.CompareHashAndPassword` — a deliberately slow, CPU-bound hashing operation (bcrypt default cost). [2](#0-1) [3](#0-2) 

Because bcrypt is intentionally slow (tens of milliseconds), a request for a non-existent email returns in a fraction of the time it takes for a request with a valid, existing email and an incorrect password. There is no dummy/constant-cost bcrypt comparison performed for the "user not found" branch to mask this timing difference. The same pattern is repeated identically in the LDAP and OIDC local-fallback authenticators (`localLoginFallback` in `core/sessions/ldapauth/ldap.go` and `core/sessions/oidcauth/oidc.go`), and again in `TestPassword` implementations used by the API-token creation/deletion GraphQL mutations. [4](#0-3) [5](#0-4) 

The `/sessions` HTTP endpoint that reaches this code is unauthenticated and internet-facing (subject to whatever network exposure the node operator configures), matching the same class of vulnerability described in CVE-2024-7010 (timing attack in password handling leaking whether credentials/accounts are valid). [6](#0-5) 

### Impact Explanation
An unauthenticated attacker able to reach the login endpoint can distinguish "email exists" from "email does not exist" by timing responses, enabling systematic enumeration of valid Chainlink node user accounts (email addresses). This is a reconnaissance primitive that materially aids follow-on credential-stuffing, phishing, or brute-force attacks against the node's admin/API accounts, and is consistent with the "unprivileged-actor, internet-facing gateway / authentication" analog class permitted by the rules.

### Likelihood Explanation
Exploitability is high in principle (timing side-channels are well understood and practically measurable over the network with enough samples), but likelihood of *this specific* being flagged as newly introduced is uncertain — the code already implements `constantTimeEmailCompare` for email string comparison, suggesting the team was aware of timing concerns for that specific comparison but did not extend the same mitigation to the "user not found vs. wrong password" branch (i.e., no dummy bcrypt hash comparison is performed when the user lookup fails).

### Recommendation
Perform a constant-time-equivalent operation regardless of whether the user is found: always run a bcrypt comparison against either the real stored hash or a precomputed dummy hash before returning an authentication failure, so that "no such user" and "wrong password" take statistically indistinguishable time. Apply the same fix uniformly to `orm.CreateSession`, `orm.TestPassword`, and the equivalent `localLoginFallback`/`TestPassword` methods in `ldapauth` and `oidcauth`.

### Proof of Concept
Not directly executable without network access; conceptually: send repeated POST requests to `/sessions` with a known-existing email + wrong password vs. a random non-existent email + wrong password, and measure round-trip latency distributions — the existing-email case will consistently be slower due to the bcrypt comparison being performed.

---

Note: this finding is an analog derived from the bug-class hint in the external CVE report, not a proven exploited instance — it should be validated by an engineer with the ability to run timing measurements against a live instance before being treated as confirmed.

	return err == nil
