Target: interaction between `AuthScopes#covers?` and `GraphqlProxy.proxy_query` when a host app *does* attempt a scope check but does it against the wrong object. Attacker action: attacker (their own installed dev shop, own online session) sends a proxy request; the host app, following the gem's exposed API, checks `Context.active_session.scope.covers?(...)` but `Context.active_session` was set from a *different* session than the `session:` argument actually passed into `proxy_query` (e.g. because the app resolves the proxy's session from a request parameter/shop domain while `Context.active_session` still holds a previous request's session in a shared worker). Preconditions: app is multi-tenant and reuses the `ShopifyAPI::Context` singleton across requests without resetting `active_session` per request boundary - a pattern the gem's own `Session.temp` helper exists to avoid, but is not enforced by `proxy_query` itself. Call sequence: `proxy_query(session: session_B, ...)` executes against shop B's Admin API while any scope check the app performed used `Context.active_session` (shop A's session). Binding: 'the session whose scope was checked' == 'the session whose credentials execute the GraphQL query' breaks because `proxy_query` takes an explicit `session:` argument that is never cross-checked against `Context.active_session`. Scoped impact: Critical, cross-tenant access - shop A's granted scope is validated while shop B's access token is the one that actually executes the attacker's query, if the host app's own gate is not perfectly aligned with the `session:` argument. Proof idea: minitest + WebMock setting `Context.active_session` to session A and calling `GraphqlProxy.proxy_query(session: session_B, ...)`, asserting the WebMock request goes to shop B's Admin API host, and that no code path inside `proxy_query` cross-validates `session` against `Context.active_session`.
