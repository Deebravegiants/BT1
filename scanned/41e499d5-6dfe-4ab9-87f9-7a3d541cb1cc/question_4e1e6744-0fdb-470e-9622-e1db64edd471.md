Target: `ShopifyAPI::Utils::GraphqlProxy.proxy_query`'s content-type branch (`application/json` path). Attacker action: attacker posts `body: '{"query":"{ shop { name } }", "variables": {"__proto__":"x"}}'` with `headers: {'Content-Type' => 'application/json'}`. Preconditions: app passes attacker body/headers straight through per docs/usage/graphql.md pattern. Call sequence: `JSON.parse(body)` -> `parsed_body['query']` and `parsed_body['variables']` are forwarded verbatim to `client.query(query:, variables:)` with zero validation that `query` matches any allow-list, and zero re-check of `session.scope.covers?` for the operations named inside the query string. Binding: 'GraphQL operation permitted by the scope granted at OAuth time' == 'GraphQL operation actually executed by `client.query`' does not hold - the only structural check is presence of a `query` key. Scoped impact: Critical, an attacker who can reach this endpoint at all (any request carrying a valid online session cookie for their own installed dev-shop, or - if the endpoint is not itself scope-gated - any authenticated end user of the embedded app) can execute arbitrary Admin GraphQL mutations against the merchant's store, exfiltrating or mutating customer/order/product data belonging to the merchant. Proof idea: minitest + WebMock stubbing `POST https://<shop>/admin/api/.../graphql.json` and asserting the exact attacker-supplied `query`/`variables` are relayed unmodified regardless of the session's originally granted scope set.
