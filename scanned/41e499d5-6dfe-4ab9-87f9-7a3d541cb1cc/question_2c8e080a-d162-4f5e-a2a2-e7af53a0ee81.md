Target: `ShopifyAPI::Auth::AuthScopes#store_scopes` / `SCOPE_DELIMITER`. Attacker action: attacker controls a string that ends up passed into `AuthScopes.new` as the caller-supplied scope to compare against (e.g. a host app that builds `AuthScopes.new(params[:scope])` from an untrusted request parameter to check against the session's granted scope). Preconditions: host app treats a request-supplied scope string as the AuthScopes object; gem does not validate tokens after `split(',')`. Call sequence: `scope_names.split(',')` -> `.map(&:strip).reject(&:empty?)` -> arbitrary strings (including ones shaped like `write_x`) become members of `compressed_scopes` with no whitelist against Shopify's actual scope vocabulary. Binding: 'string is a scope Shopify recognizes' == 'string accepted into `compressed_scopes`' does not hold - any token surviving strip/empty-reject is accepted. Scoped impact: High, scope check bypass - an attacker-chosen scope name can be constructed to intersect with the implied `read_*` set added by `implied_scope`, producing a `covers?` true where the app-level intent was false. Proof idea: minitest building `AuthScopes.new('write_orders')` and `AuthScopes.new(attacker_string)` where `attacker_string` is not a real Shopify scope but happens to equal the implied `read_*` token, asserting `covers?` returns true.
