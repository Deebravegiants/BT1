Target: `ShopifyAPI::Utils::GraphqlProxy.proxy_query`. Attacker action: attacker sends a request to the proxy endpoint with an offline (non-online) session id somehow reachable, OR sends a request while `Context.active_session`/passed-in `session` is any session for which `online?` is true but which was itself derived from stale/expired token state (see `expired?` finding above). Preconditions: app resolves `session` for the proxy from `SessionUtils`/cookie without also checking `session.expired?`. Call sequence: `proxy_query` gate is exactly `unless session.online?` - it never checks `session.expired?` or `session.access_token` validity. Binding: 'session is currently valid (not expired, has a live token)' == 'session accepted by proxy_query's gate' fails since only `online?` (a boolean set at token-exchange time) is checked, not expiry. Scoped impact: High, expired-session/scope-bypass - a stale online session (e.g. one whose `expires` was never set, per the `expired?` finding) is still usable to reach the merchant's live Admin GraphQL API through the proxy. Proof idea: minitest + WebMock constructing an online `Session` with `expires: nil`, calling `proxy_query`, and asserting the outbound GraphQL request was sent despite the session having no verified freshness.
