Target: `ShopifyAPI::Auth::AuthScopes#==`/`#covers?` combined with `Session#scope`. Attacker action: attacker who installs their own dev shop requests scope string `'write_customers,read_orders'`; the two literal tokens are kept in `compressed_scopes` unchanged (per `store_scopes: @compressed_scopes = scopes - implied_scopes`, and `read_orders` is not itself an implied output of `write_customers`), so nothing unusual there - but attacker then separately crafts a caller `AuthScopes` object using only the string `'read_customers'` (never granted) and calls `covers?`. Preconditions: host app authorization check is literally `granted_scope.covers?(AuthScopes.new(requested_scope_string))`. Call sequence: `implied_scope('write_customers')` returns `'read_customers'` -> `expanded_scopes` includes `'read_customers'` though it was never an OAuth-granted scope -> `covers?(AuthScopes.new('read_customers'))` -> true. Binding: 'scope string returned by Shopify's OAuth token exchange' == 'scope string treated as granted by `covers?`' fails; a derived, non-issued scope name satisfies the check. Scoped impact: High, scope check bypass letting a read-customers gated feature run for a merchant who only granted write_customers, exposing merchant customer data (PII) through a feature the app intended to gate separately. Proof idea: minitest asserting `AuthScopes.new('write_customers').covers?(AuthScopes.new('read_customers'))` is true, then asserting `'read_customers'` never appears in the original scope string used to build the grant.
