## Analog Finding

### Title
Missing maximum-length validation before address truncation in vault owner normalization - (File: `core/services/workflows/v2/secrets.go`)

### Summary
The ENS report's root cause is a `hexToAddress`-style function that checks only a *lower* bound on address length and lets `common.HexToAddress`-equivalent logic silently right-truncate an over-length value into an unrelated 20-byte address, rather than rejecting it. The same pattern exists in `normalizeOwner` in `core/services/workflows/v2/secrets.go`, which feeds the `Owner` field used to key/label secrets in the Vault capability.

### Finding Description
`normalizeOwner` only checks a minimum length before delegating to go-ethereum's `common.HexToAddress`: [1](#0-0) 

`common.HexToAddress` decodes the hex string and calls `Address.SetBytes`, which — for inputs longer than 20 bytes — silently keeps only the **rightmost** 20 bytes (exactly the "last 20 bytes from the right" truncation behavior described in the ENS report), instead of returning an error. There is no upper-bound check here (unlike, e.g., `ccipevm.AddressCodec.AddressStringToBytes`, which validates with `common.IsHexAddress` first: [2](#0-1) , or `cresettings.normalizeOwnerHex`, which enforces an exact 40-char length: [3](#0-2) ).

`normalizeOwner`'s output is used to build the `Owner` field of every `vault.SecretIdentifier` sent to the Vault capability and to build the local secret lookup key: [4](#0-3) [5](#0-4) 

Additionally, `vaultutils.WorkflowOwnerToLabel`, used to derive the TDH2 encryption label that binds a ciphertext to an owner, calls `common.HexToAddress(owner)` with **no length validation whatsoever**: [6](#0-5) 

By contrast, the owner-matching checks that gate unprivileged, gateway-facing requests (`validateSecretOwnersMatchAuthorized` / `vaultutils.NormalizeOwner`) do plain string equality after lower-casing and stripping the `0x` prefix — they never hex-decode or bound-check length: [7](#0-6) [8](#0-7) 

### Impact Explanation
If a malformed/over-length owner string reaches `normalizeOwner` or `WorkflowOwnerToLabel` (e.g., through workflow metadata that isn't itself hex-address-length-constrained before reaching these call sites), the value is silently coerced into a different, attacker-influenced 20-byte address instead of failing loudly. This mirrors the ENS finding's core defect class: "should revert rather than silently truncating." In the Vault context this could manifest as secrets being written/read under an unintended owner key (cross-owner secret confusion), rather than the DNS-ownership confusion in the original report.

### Likelihood Explanation
Low-to-moderate. The `Owner` field on gateway-facing requests is checked via `validateSecretOwnersMatchAuthorized`, which requires literal string equality (after case/`0x` normalization, no length coercion) with the JWT/allowlist-authorized owner, so a client cannot easily smuggle a malformed value past that gate for the request-processing path. The exposure is narrower: it depends on whether `workflowOwner` (passed into `NewSecretsFetcher`) can ever be a non-canonical-length string before it reaches `normalizeOwner`/`WorkflowOwnerToLabel`. I could not fully trace all upstream producers of `workflowOwner` in the time available, so I cannot confirm a concrete unprivileged trigger — this should be treated as an unverified-but-structurally-real gap rather than a proven exploit.

### Recommendation
Add strict length/format validation (reject rather than silently truncate) before any `common.HexToAddress`/`common.BytesToAddress`-style conversion of a caller- or config-derived owner string, in both `normalizeOwner` (`core/services/workflows/v2/secrets.go`) and `WorkflowOwnerToLabel` (`core/capabilities/vault/vaultutils/labels.go`) — e.g., require exactly 40 hex characters (with optional `0x`) using `common.IsHexAddress`, matching the pattern already used in `ccipevm.AddressCodec.AddressStringToBytes` and `cresettings.normalizeOwnerHex`.

### Proof of Concept
Not independently reproducible from the indexed code alone — reproducing would require confirming a concrete unprivileged path that supplies a `workflowOwner` value longer than 40 hex characters into `secretsFetcher.GetRawSecrets`/`getVaultSecretsForBatch`, which I was unable to fully trace within the available tool budget. The code-level defect (missing upper-bound check before silent truncation) is confirmed at the cited lines; full end-to-end exploitability requires further investigation of `workflowOwner`'s upstream sources.

	if len(owner) < 40 {
		return "", errors.New("invalid owner address: too short")
	}

	if owner[:2] != "0x" {
		owner = "0x" + owner
	}

	return common.HexToAddress(owner).Hex(), nil
}

func normalizeOwnerHex(s string) (string, error) {
	s = strings.TrimSpace(s)
	s = strings.TrimPrefix(s, "0x")
	s = strings.TrimPrefix(s, "0X")
	s = strings.ToLower(s)
	if len(s) != 40 {
		return "", fmt.Errorf("owner address must be 40 hex chars (20 bytes), got %d chars", len(s))
	}
	if _, err := hex.DecodeString(s); err != nil {
		return "", fmt.Errorf("owner address is not valid hex: %w", err)
	}
	return s, nil

// validateSecretOwnersMatchAuthorized checks that secret identifiers in the request payload
// match the authorized workflow owner. This is read-only validation; owner prefixing and
// param stamping happen later in GatewayVaultRequestProcessor.
func validateSecretOwnersMatchAuthorized(req jsonrpc.Request[json.RawMessage], workflowOwner string) error {
	switch req.Method {
	case vaulttypes.MethodPublicKeyGet:
		return nil
	case vaulttypes.MethodSecretsCreate:
		if req.Params == nil {
			return errors.New("request params must not be nil")
		}
		var createReq vaultcommon.CreateSecretsRequest
		if err := json.Unmarshal(*req.Params, &createReq); err != nil {
			return err
		}
		return validateEncryptedSecretOwnerMismatch(createReq.EncryptedSecrets, workflowOwner)
	case vaulttypes.MethodSecretsUpdate:
		if req.Params == nil {
			return errors.New("request params must not be nil")
		}
		var updateReq vaultcommon.UpdateSecretsRequest
		if err := json.Unmarshal(*req.Params, &updateReq); err != nil {
			return err
		}
		return validateEncryptedSecretOwnerMismatch(updateReq.EncryptedSecrets, workflowOwner)
	case vaulttypes.MethodSecretsDelete:
		if req.Params == nil {
			return errors.New("request params must not be nil")
		}
		var deleteReq vaultcommon.DeleteSecretsRequest
		if err := json.Unmarshal(*req.Params, &deleteReq); err != nil {
			return err
		}
		return validateSecretIdentifierOwnerMismatch(deleteReq.Ids, workflowOwner)
	case vaulttypes.MethodSecretsList:
		if req.Params == nil {
			return errors.New("request params must not be nil")
		}
		var listReq vaultcommon.ListSecretIdentifiersRequest
		if err := json.Unmarshal(*req.Params, &listReq); err != nil {
			return err
		}
		if vaultutils.NormalizeOwner(listReq.Owner) != vaultutils.NormalizeOwner(workflowOwner) {
			return fmt.Errorf("list secrets owner %q does not match authorized workflow owner %q", listReq.Owner, workflowOwner)
		}
		return nil
	default:
		return fmt.Errorf("owner validation not implemented for method %q", req.Method)
	}
}
