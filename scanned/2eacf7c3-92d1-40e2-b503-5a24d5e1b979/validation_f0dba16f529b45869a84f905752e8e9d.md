## Analysis

The bug class in the report is a **global, unscoped uniqueness check** on a caller-supplied value (token balance in the C4 report; here, request ID) that lets an unrelated, unprivileged actor pre-empt/collide with that value and cause a *legitimate* operation to fail — i.e., a griefing/DoS via namespace collision, not a fund-theft bug.

The closest reachable analog in this codebase is `httpTriggerHandler.setupCallback` in the internet-facing CRE gateway's HTTP trigger path.

### Finding Description

`httpTriggerHandler.HandleUserTriggerRequest` accepts a JSON-RPC request from any external, unprivileged caller and validates the request ID only for emptiness/format (`validateRequestID`), not uniqueness scoped to a workflow/owner [1](#0-0) . Authorization (`authorizeRequest`) validates only that the caller holds a valid signing key for the *targeted* `workflowID` [2](#0-1) , but does not bind the `requestID` namespace to that `workflowID` or owner.

The in-flight-request tracking map is keyed **purely by the client-supplied `requestID` string**, globally across all workflows and all callers: [3](#0-2) 

```go
callbacks map[string]savedCallback // requestID -> savedCallback
```

`setupCallback` rejects any second request with the same `requestID`, regardless of which workflow or owner it belongs to: [4](#0-3) 

Because any unprivileged party can register/own a workflow and sign valid requests for it (this is a normal, unprivileged CRE tenant capability, not an operator-only action), an attacker can:
1. Predict or observe a victim's `requestID` (client-chosen, often low-entropy or reused values such as `"1"`, `"req-1"`, idempotency keys, etc., as seen throughout the test suite), and
2. Submit their own authorized trigger request for their *own, unrelated* workflow using that same `requestID` just before or concurrently with the victim,

causing the victim's legitimate execution request to fail with `jsonrpc.ErrConflict` / "requestID: %s has already been used" [5](#0-4) , exactly mirroring the C4 pattern: an unprivileged, unrelated actor injecting a value into a shared, un-scoped equality/uniqueness check causes the legitimate transaction to fail.

The existing test suite only exercises same-workflow / same-signer collisions ("duplicate request ID", "duplicate JWT token and request ID") [6](#0-5) , and does not cover the cross-workflow/cross-owner collision case, which is the actual vulnerable path.

By contrast, the analogous vault gateway handler avoids this problem because its active-request map is keyed by an **owner-prefixed** request ID stamped only after authorization (`authorizedOwner + separator + originalRequestID`) [7](#0-6) , so collisions require sharing the same authorized owner. The HTTP trigger handler has no equivalent namespacing by workflow/owner.

### Impact Explanation

An unprivileged, arbitrary CRE user (anyone able to register or invoke any workflow through the gateway) can deny service to another unrelated user's workflow-execution request by colliding on `requestID`. This is a griefing/availability issue: it does not by itself steal funds or secrets, but it can reliably block a targeted execution, similar in kind (unprivileged party spoiling an unrelated, shared state check) to the original report even though the specific mechanism (token balance vs. request-ID map) differs.

### Likelihood Explanation

Exploitability depends on the attacker's ability to predict/observe the victim's `requestID` before the victim's request completes. Since `requestID` is entirely caller-chosen and not namespaced, low-entropy or reused IDs (which is common practice, as reflected in the tests using constants like `"1"`, `"req-1"`) make this straightforward to hit; for high-entropy random IDs, the race is harder but the underlying design flaw (missing owner/workflow scoping of the uniqueness map) remains.

### Recommendation

Scope the `callbacks` map key (and the "in-flight" uniqueness check) by `(workflowID, requestID)` or `(workflowOwner, requestID)` rather than by `requestID` alone, so that requests targeting different workflows/owners cannot collide. This mirrors the owner-prefixing approach already used by the vault gateway handler's `activeRequests` map.

### Proof of Concept

1. Victim submits `workflows.execute` with `id: "abc123"` targeting `workflowID: 0xVictim...`.
2. Attacker (owning any unrelated, self-registered workflow `0xAttacker...`) submits a validly-authorized `workflows.execute` request with the exact same `id: "abc123"`, timed to land in `setupCallback` first.
3. `setupCallback` finds `"abc123"` already present in the global `callbacks` map (regardless of workflow) and returns the conflict error for whichever request arrives second [8](#0-7) , denying that party's (potentially the victim's) execution request.

**Uncertainty**: I could not fully trace how `requestID` values are typically generated/exposed to end users in the production CRE client SDKs (i.e., whether they are always high-entropy UUIDs by convention, which would reduce practical predictability), nor whether any upstream API gateway layer imposes additional per-caller/per-workflow ID scoping before reaching this handler. This would need to be confirmed via a Devin session with fuller repository/build access.

func (h *httpTriggerHandler) validateRequestID(ctx context.Context, requestID string, callback handlers.Callback) error {
	if requestID == "" {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "'id' field is required and cannot be empty. Use a new unique request 'id' for each request", callback)
		return errors.New("empty request ID")
	}
	// Request IDs from users must not contain "/", since this character is reserved
	// for internal node-to-node message routing (e.g., "http_action/{workflowID}/{uuid}").
	if strings.Contains(requestID, "/") {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "request ID must not contain '/'", callback)
		return errors.New("request ID must not contain '/'")
	}
	return nil
}

func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
