Looking at this analog, the strongest reachable path from an unauthenticated client is the login flow: `SessionsController.Create` → `AuthenticationProvider().CreateSession` → `orm.CreateSession` in `core/sessions/localauth/orm.go`. This flow accepts an attacker-controlled `email` field with no length bound anywhere in the pipeline before it reaches `constantTimeEmailCompare`, which allocates a byte buffer sized to the input length.

### Title
Unbounded-length email field in unauthenticated login endpoint allows memory-allocation DoS - ([File: core/sessions/localauth/orm.go])

### Summary
The `/sessions` login endpoint (`SessionsController.Create` in `core/web/sessions_controller.go`) binds an arbitrary-length `email` string from the request body directly into `sessions.SessionRequest` and passes it, unvalidated for length, into `orm.CreateSession`. `constantTimeEmailCompare` (`core/sessions/localauth/orm.go:232-241`) allocates two byte slices sized `max(256, len(left), len(right))`, meaning the allocation size is directly controlled by the attacker-supplied email length, with no upper bound enforced before this point.

### Finding Description
`SessionsController.Create` (`core/web/sessions_controller.go:29-68`) does `c.ShouldBindJSON(&sr)` into `clsessions.SessionRequest` and immediately calls `sc.App.AuthenticationProvider().GetUserWebAuthn(ctx, sr.Email)` [1](#0-0) , then `CreateSession(ctx, sr)` [2](#0-1) . Neither of these paths performs any length validation on `sr.Email`. Inside `orm.CreateSession` (`core/sessions/localauth/orm.go:144-157`), after the user lookup fails to match (attacker doesn't need a valid account), the email is passed to `constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email))` [3](#0-2) . The comparison function itself:

```go
const constantTimeEmailLength = 256

func constantTimeEmailCompare(left, right string) bool {
	length := mathutil.Max(constantTimeEmailLength, len(left), len(right))
	leftBytes := make([]byte, length)
	rightBytes := make([]byte, length)
	...
}
``` [4](#0-3) 

allocates two buffers whose size is `len(sr.Email)` when that exceeds 256 bytes — entirely attacker-controlled, with no cap. This is the same bug class as the rdiffweb advisory (CVE-2022-3295): an unbounded user-supplied string field flowing into memory-affecting operations with no size limit, enabling a DoS via memory pressure/GC churn under repeated or concurrent requests. Unlike the gateway's `Message.Validate()` (`core/services/gateway/api/message.go:54-88`), which explicitly caps `MessageID`, `Method`, and `DonID` lengths, and unlike the gateway's JSON-RPC request ID check (`len(jsonRequest.ID) > 200` in `core/services/gateway/gateway.go:231-234`), there is no equivalent length cap on the `email` field anywhere in the local-auth login path. Also note `sessions.ValidateEmail` (`core/sessions/user.go:59-66`), which is used at user-creation time (an authenticated admin operation), likewise never checks length before calling `mail.ParseAddress`, but that path requires an authenticated admin, whereas login is unauthenticated.

### Impact Explanation
An unauthenticated attacker can submit oversized `email` values (e.g., megabytes long) via POST to `/sessions` repeatedly. Each request causes two allocations proportional to submitted length, imposing per-request memory/CPU cost with no gate before the allocation, on a completely unauthenticated endpoint. Under concurrent/repeated requests this results in memory pressure/GC overhead — a denial-of-service vector directly analogous to the referenced rdiffweb CVE (unbounded field length causing DoS/memory issues). Impact is limited to availability degradation of the login endpoint/node API; no direct confidentiality/integrity compromise from this specific allocation pattern is evident.

### Likelihood Explanation
High likelihood of reachability: the `/sessions` endpoint requires no prior authentication, `ShouldBindJSON` will happily bind an arbitrarily long JSON string field, and there is no request body size limit visible in this controller path (unlike gateway's `MaxRequestBytes` config seen in `deployment/cre/jobs/pkg/gateway_job_test.go`). Whether an overarching HTTP body size limit is enforced by the gin server/router setup could not be fully verified in this pass — if such a global limit exists it may bound the practical exploitability. This uncertainty should be checked directly in the router/middleware setup (`core/web/router.go`, gin engine max multipart/body size config) before finalizing severity.

### Recommendation
Add an explicit maximum length check for `SessionRequest.Email` (and ideally `Password`) at the top of `SessionsController.Create`, and/or within `ValidateEmail`/`CreateSession`, rejecting oversized inputs before any downstream allocation or lookup — mirroring the length caps already used in `core/services/gateway/api/message.go` (`MessageIDMaxLen`, etc.) and the `MaxBcryptPasswordLength` pattern in `core/sessions/user.go`. Additionally confirm/introduce a global request body size limit on the gin server used for the node API.

### Proof of Concept
```
POST /sessions HTTP/1.1
Content-Type: application/json

{"email":"AAAA...<multi-MB of 'A'>...@x.com","password":"anything"}
```
