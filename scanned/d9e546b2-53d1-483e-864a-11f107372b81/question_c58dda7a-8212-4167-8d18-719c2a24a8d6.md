`IntentPayloadBuilder.buildWithSalt` computes `nonce = this.customNonce ?? VersionedNonceBuilder.encodeNonce(salt, deadline, this.customRandomBytes)`. When `setNonce(customNonce)` is used, the returned `nonce` is fully decoupled from `deadline` — no cross-check exists between the custom nonce's embedded deadline and `payload.deadline`. Can a caller of the public `sdk.intentBuilder()` chain call `.setDeadline(D1).setNonce(nonceEncodedWithD2).buildWithSalt(salt)` and produce a signed `MultiPayload` whose `nonce`-embedded deadline (D2) differs from its own `deadline` field (D1), breaking the (deadline, nonce) coupling this system relies on for expiry? Impact: High, a stale pre-built nonce (D2 in the past) paired with a still-valid `deadline` (D1) field could make the contract treat the intent as expired via nonce and strand a fund transfer the user already signed for; or conversely, an already-consumed nonce is reused, executing the payload a second time. Proof: vitest builds a payload with `setNonce` set to a nonce encoding a different deadline than `setDeadline`, decodes both fields, asserts the coupling test used elsewhere (`extractNonceDeadlineMs(payload.nonce) === deadline.getTime()`) fails.
