Confirmed: the `readLoop` in `core/services/gateway/connector/connector.go` calls `handler.HandleGatewayMessage` synchronously, in a single goroutine per gateway connection, for every incoming message from that gateway [1](#0-0) . `triggerConnectorHandler.HandleGatewayMessage` in turn calls `processTrigger` inline (no goroutine dispatch, unlike `confidentialrelay.Handler.HandleGatewayMessage`, which explicitly spawns a goroutine per request to avoid exactly this problem) [2](#0-1) . Inside `processTrigger`, the send to a matched trigger's channel is a blocking `select` with no `default` (only `ctx.Done()` or a successful send), performed while holding `trigger.chWriteMu` [3](#0-2) .

### Title
Head-of-line blocking DoS in web-api-trigger gateway message handling halts all trigger delivery on a shared connection - (File: core/capabilities/webapi/trigger/trigger.go)

### Summary
`triggerConnectorHandler.HandleGatewayMessage` is invoked synchronously, one message at a time, from the gateway connector's single per-connection read loop. When it processes a `MethodWebAPITrigger` message whose topic matches a registered workflow trigger, it blocks indefinitely (bounded only by the message context) on writing to that workflow's bounded 1000-entry channel while holding the trigger's `chWriteMu`. If the destination workflow engine is not draining the channel fast enough (e.g., slow/paused/crashed consumer, or an authorized-but-throttled sender simply exceeding the consumer's drain rate), any single legitimate, authenticated `web_api_trigger` message can stall this blocking send. Because the handler is called synchronously from the connector's shared read loop, that block prevents `HandleGatewayMessage` from returning, which in turn prevents the read loop from processing the *next* message on the wire — including trigger messages destined for entirely unrelated, healthy workflows.

### Finding Description
Every gateway JSON-RPC message received on a connection is read and dispatched serially:
`readLoop` blocks on `handler.HandleGatewayMessage(...)` before looping back to read the next item [4](#0-3) .

`triggerConnectorHandler.HandleGatewayMessage` does not offload work to a goroutine (contrast with `confidentialrelay.Handler.HandleGatewayMessage`, which explicitly does `h.eng.GoCtx(...)` specifically to avoid head-of-line blocking, as documented in its own test comment: "The gateway connector calls HandleGatewayMessage from a single goroutine per connection and waits for it to return, so serving inline forced requests through one at a time...") [5](#0-4) [6](#0-5) . The trigger handler instead runs `processTrigger` inline on the connector's read-loop goroutine [7](#0-6) .

Inside `processTrigger`, once a message passes the `allowedTopics`, `allowedSenders`, and per-sender rate-limit checks, delivery to the registered workflow's channel is a blocking channel send guarded by a per-trigger mutex:
```
trigger.chWriteMu.Lock()
...
select {
case <-ctx.Done():
    ...
case trigger.ch <- tr:
    ...
}
``` [3](#0-2) . There is no `default:` branch, so if `trigger.ch` (buffer size 1000, `defaultSendChannelBufferSize`) [8](#0-7) [9](#0-8)  is full and the consuming workflow engine is stalled, slow, or simply outpaced by legitimate trigger volume, the send blocks for the lifetime of `ctx` (which is the connector's shutdown context, not a short per-message timeout) [10](#0-9) .

Because this call happens on the shared `readLoop` goroutine for the entire gateway connection, one blocked send effectively stalls delivery of *all* subsequent messages from that gateway to *any* handler routed on that connection, not just the offending trigger's workflow — an unbounded, cross-tenant head-of-line block reachable via a single, authorized/normal `web_api_trigger` request whose target workflow is temporarily slow to consume.

This is structurally the same bug class as the Zebra advisory: a per-connection resource (there: gossip/syncer queues; here: the read-loop goroutine and a bounded trigger channel) can be starved/blocked by ordinary, protocol-valid traffic with no independent penalty or circuit breaker, permanently degrading delivery for unrelated consumers sharing the same connection until the node/handler is restarted or the stuck consumer resumes draining.

### Impact Explanation
A stalled `trigger.ch` send blocks the connector's per-gateway read loop, which serializes handling of *all* gateway-originated messages (not just `web_api_trigger`) traveling over that connection to this node — including other workflow triggers, target responses, and any other registered `HandleGatewayMessage` handler multiplexed on the same `gatewayConnector`. This causes cross-workflow denial of service: a single slow/stuck workflow consumer can silently halt trigger delivery to unrelated workflows sharing the connection, with no logging, alerting, or automatic recovery until the blocking send's `ctx` is cancelled (connector shutdown) or the stuck consumer resumes draining its channel.

### Likelihood Explanation
No malicious or unauthenticated actor is strictly required to trigger the initial condition — an authorized sender's normal (rate-limit-compliant) traffic combined with any workflow-side slowdown (backpressure, engine restart, paused workflow) is sufficient to fill the 1000-entry buffer and block the send. Given `RegisterTrigger` enforces at least one `AllowedSender` but places no independent bound on how many distinct triggers/topics one sender can legitimately fan out to, and the per-sender/global rate limiters only throttle inbound rate rather than bound outstanding unconsumed events, this condition is plausible under ordinary operational stress (e.g., workflow engine backlog) rather than requiring a sophisticated attack chain.

### Recommendation
Make trigger delivery non-blocking and independent of the connector's read-loop goroutine:
- Dispatch `processTrigger` (or at minimum the per-trigger channel send) onto its own goroutine per message, mirroring the pattern already used in `confidentialrelay.Handler.HandleGatewayMessage`, so a slow consumer cannot stall the shared read loop.
- Replace the blocking `select` on `trigger.ch <- tr` with a bounded-wait or `default:`-drop path that increments a "trigger queue full" metric and returns an error/response to the caller instead of blocking indefinitely, consistent with the `receiver channel full, dropping message` pattern already used elsewhere in the codebase (e.g., `core/capabilities/remote/dispatcher.go`) [11](#0-10) .
- Add a short per-message timeout for the trigger delivery independent of the connector's long-lived shutdown context.

### Proof of Concept
1. Register a `web-api-trigger` workflow with a small `AllowedSenders`/`AllowedTopics` set and do not drain its returned channel (simulate a stalled workflow engine, e.g., stop reading from the channel returned by `RegisterTrigger`).
2. From an authorized sender, send `defaultSendChannelBufferSize` (1000) + 1 `MethodWebAPITrigger` gateway messages matching that trigger's topic within the configured rate limit.
3. Observe that the connector's `readLoop` goroutine for that gateway connection blocks inside `processTrigger`'s `trigger.ch <- tr` send (`core/capabilities/webapi/trigger/trigger.go:149`).
4. Send a `web_api_trigger` (or any other method routed through the same connector) message for a second, healthy, unrelated workflow over the same gateway connection.
5. Observe the second message is never processed until the stalled consumer resumes draining or the connector shuts down, demonstrating cross-workflow head-of-line blocking DoS from ordinary protocol-valid traffic.

func (c *gatewayConnector) readLoop(gatewayState *gatewayState) {
	defer c.closeWait.Done()
	ctx, cancel := c.shutdownCh.NewCtx()
	defer cancel()

	for {
		select {
		case <-c.shutdownCh:
			return
		case item := <-gatewayState.conn.ReadChannel():
			var req jsonrpc.Request[json.RawMessage]
			err := json.Unmarshal(item.Data, &req)
			if err != nil {
				c.lggr.Errorw("parse error when reading from Gateway", "id", gatewayState.config.ID, "err", err)
				break
			}
			c.handlersMu.RLock()
			handler, exists := c.handlers[req.Method]
			c.handlersMu.RUnlock()
			if !exists {
				c.lggr.Errorw("no handler for method", "id", gatewayState.config.ID, "method", req.Method)
				break
			}
			// do not break on error. HandleGatewayMessage handles errors
			// by sending a response back to the Gateway.
			err = handler.HandleGatewayMessage(ctx, gatewayState.config.ID, &req)
			if err != nil {
				c.lggr.Warnw("failed to handle message from Gateway", "id", gatewayState.config.ID, "method", req.Method, "err", err)
			}
		}
	}
}

func (h *triggerConnectorHandler) HandleGatewayMessage(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) error {
	msg, err := hc.ValidatedMessageFromReq(req)
	if err != nil {
		h.lggr.Errorw("error validating message from request", "err", err, "request", req)
		return nil
	}
	body := &msg.Body
	sender := ethCommon.HexToAddress(body.Sender)
	var payload webapicap.TriggerRequestPayload
	err = json.Unmarshal(body.Payload, &payload)
	if err != nil {
		h.lggr.Errorw("error decoding payload", "err", err)
		err = h.sendResponse(ctx, gatewayID, body, ghcapabilities.TriggerResponsePayload{Status: "ERROR", ErrorMessage: fmt.Errorf("error %s decoding payload", err.Error()).Error()})
		if err != nil {
			h.lggr.Errorw("error sending response", "err", err)
		}
		return nil
	}

	switch body.Method {
	case ghcapabilities.MethodWebAPITrigger:
		resp := h.processTrigger(ctx, gatewayID, body, sender, payload)
		var response ghcapabilities.TriggerResponsePayload
		if resp == nil {
			response = ghcapabilities.TriggerResponsePayload{Status: "ACCEPTED"}
		} else {
			response = ghcapabilities.TriggerResponsePayload{Status: "ERROR", ErrorMessage: resp.Error()}
			h.lggr.Errorw("Error processing trigger", "gatewayID", gatewayID, "body", body, "response", resp)
		}
		err = h.sendResponse(ctx, gatewayID, body, response)
		if err != nil {
			h.lggr.Errorw("Error sending response", "body", body, "response", response, "err", err)
		}
		return nil

func (h *Handler) HandleGatewayMessage(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) error {
	h.lggr.Debugw("received message from gateway", "gatewayID", gatewayID, "requestID", req.ID)

	// GoCtx ties the goroutine to the handler's service lifecycle, so Close waits
	// for in-flight requests instead of abandoning them mid-vault-call.
	h.eng.GoCtx(ctx, func(ctx context.Context) {
		ctx, done, err := h.serveTime.WithTimeout(ctx)
		if err != nil {
			h.lggr.Errorw("failed to apply serve timeout, dropping request", "gatewayID", gatewayID, "requestID", req.ID, "err", err)
			return
		}
		defer done()
		h.serveGatewayMessage(ctx, gatewayID, req)
	})

	return nil
}
