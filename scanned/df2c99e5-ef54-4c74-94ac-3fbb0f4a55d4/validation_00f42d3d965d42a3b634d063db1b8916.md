### Title
Unbounded JWT replay-cache growth allows unauthenticated-rate-limit-bypassing DoS on the HTTP Trigger gateway - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go, http_trigger_handler.go)

### Summary
The reported bug class ("unbounded array/collection growth accepted from a caller before any size guard is applied → gas/compute exhaustion / DoS") maps to the `jwtReplayCache` used by `WorkflowMetadataHandler.Authorize` in the CRE HTTP Trigger gateway path. Every trigger request that reaches the gateway inserts an entry into an in-memory map keyed by JWT `jti`, and this happens **before** the per-workflow-owner rate limiter is checked, so the map can be flooded far beyond what the rate limiter is meant to allow, only being pruned once every `JWTReplayPeriodMs` (default 24h).

### Finding Description
`httpTriggerHandler.HandleUserTriggerRequest` processes each inbound trigger request in this order:
1. `h.authorizeRequest(...)` → calls `WorkflowMetadataHandler.Authorize`
2. `h.checkRateLimit(...)` [1](#0-0) 

`Authorize` verifies the JWT and, on success, calls `h.jwtCache.recordUsage(claims.ID)` to prevent replay — this insertion into the `jwtReplayCache.cache` map happens *before* `checkRateLimit` is ever invoked: [2](#0-1) 

The cache itself is a plain `map[string]time.Time` with no upper-bound/eviction-on-insert logic — entries are only removed by a periodic ticker running every `h.jwtCache.cleanupPeriod` (`JWTReplayPeriodMs`, default 24 hours): [3](#0-2) [4](#0-3) [5](#0-4) 

Because the JWT is per-request and includes a unique `jti` (only the ECDSA signature over the request needs to be valid for a *registered* workflow key), a client already holding one authorized signing key for any workflow served by this gateway can generate an effectively unlimited stream of distinct valid JWTs, each inserted into `jwtCache.cache` before the workflow-owner rate limiter (`h.userRateLimiter.AllowErr`) has a chance to reject the request: [6](#0-5) 

This is the same root-cause pattern as the `USSD.addCollateral` finding: a caller-controlled collection (`collateral` array / `jwtCache.cache` map) grows without any per-insert bound, only capped by an out-of-band periodic sweep, so a caller can drive it to unbounded size within one cleanup window.

### Impact Explanation
An attacker who controls one authorized workflow signing key (which is not a node-operator or privileged role — any workflow developer registered on-chain can hold such a key) can flood the gateway node's memory with jwtCache entries by sending a high volume of otherwise-valid, uniquely-`jti`'d trigger requests. Because insertion happens ahead of the per-workflow rate limiter, the rate limiter does not bound cache growth — it only stops the *trigger requests themselves* from being forwarded to the DON, not the memory consumed by JWT bookkeeping. Sustained flooding for up to `JWTReplayPeriodMs` (24h default) before the next cleanup tick can grow the map to a size proportional to attacker-controlled request volume, potentially exhausting gateway node memory and causing a denial of service for legitimate HTTP-trigger workflow executions on that node.

### Likelihood Explanation
Medium. It requires possession of at least one authorized signing key for some workflow served by the gateway (a normal workflow-developer credential, not an operator/admin credential), and sustained high request volume against the internet-facing gateway HTTP endpoint. There is no additional bound (e.g., max cache size, per-key insertion cap) preventing this.

### Recommendation
- Enforce the per-workflow-owner rate limit (`checkRateLimit`) before recording JWT usage in `jwtReplayCache`, so replay-cache growth is capped by the same limiter that bounds request forwarding.
- Add an upper bound on `jwtReplayCache.cache` size (e.g., LRU eviction or per-key/global cap) independent of the time-based cleanup ticker, so a burst of requests within a single `cleanupPeriod` window cannot grow the map unbounded.
- Consider reducing `JWTReplayPeriodMs` or running cleanup more frequently if memory pressure is a concern, though this only mitigates rather than fixes the missing size bound.

### Proof of Concept
1. Obtain (or compromise) one workflow's authorized ECDSA signing key already registered with the gateway's `WorkflowMetadataHandler.authorizedKeys`.
2. Repeatedly build valid `HTTPTriggerRequest` JSON-RPC messages, each signed with a fresh JWT containing a unique `jti` claim (via `utils.CreateRequestJWT`/`VerifyRequestJWT` flow used in `workflow_metadata_handler_test.go`), and POST them to the gateway's public HTTP endpoint (`core/services/gateway/network/httpserver.go: handleRequest` → `gateway.ProcessRequest` → `httpTriggerHandler.HandleUserTriggerRequest`).
3. Each request passes `Authorize()` (JWT signature + non-replay check) and inserts a new entry into `jwtCache.cache` — this happens before `checkRateLimit`, so rate limiting does not throttle cache growth.
4. Repeat at high volume for a duration approaching `JWTReplayPeriodMs` (24h default) to grow the in-memory map to a size proportional to request volume, consuming gateway node memory.

func (h *httpTriggerHandler) checkRateLimit(ctx context.Context, workflowID, requestID string, callback handlers.Callback) error {
	workflowRef, found := h.workflowMetadataHandler.GetWorkflowReference(workflowID)
	if !found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "workflow reference not found", callback)
		return errors.New("workflow reference not found")
	}

	orgID := h.resolveOrgID(ctx, workflowRef.workflowOwner)
	ctx = contexts.WithCRE(ctx, contexts.CRE{Owner: workflowRef.workflowOwner, Org: orgID, Workflow: workflowID})
	if err := h.userRateLimiter.AllowErr(ctx); err != nil {
		lggr := logger.With(h.lggr, platform.KeyWorkflowID, workflowID, platform.KeyWorkflowOwner, workflowRef.workflowOwner, "requestID", requestID, "err", err)
		if errLimited, ok := errors.AsType[limits.ErrorRateLimited](err); ok {
			switch errLimited.Scope {
			case settings.ScopeWorkflow:
				lggr.Errorf("failed to start execution: per workflow rate limit exceeded")
				h.metrics.IncrementWorkflowThrottled(ctx, h.lggr)
			default:
				lggr.Errorf("failed to start execution: unexpected rate limit for scope %s", errLimited.Scope)
			}
			h.handleUserError(ctx, requestID, jsonrpc.ErrLimitExceeded, "rate limit exceeded", callback)
			return err
		}
		return fmt.Errorf("failed to check rate limit: %w", err)
	}
	return nil
}

```go
func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
```
