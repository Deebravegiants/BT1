### Title
Unauthenticated panic (integer-underflow-driven negative repeat count) via `normalizeHex()` in the HTTP trigger gateway handler - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

### Summary
The reported Zephyr CVE-2026-5589 is a classic "attacker-controlled length minus fixed constant, used without a lower-bound check" bug that causes an out-of-bounds write once the subtraction underflows. The closest analog reachable from an unprivileged client in this repo is `normalizeHex()`, which computes `length - 2 - len(hexStr)` and passes the (potentially negative) result straight into `strings.Repeat`, with no validation that `len(hexStr) <= length-2`.

### Finding Description
`normalizeHex` is defined as: [1](#0-0) 

```go
func normalizeHex(input string, length int) string {
	hexStr := strings.TrimPrefix(input, "0x")
	// length-2 because we'll add "0x" prefix
	expectedHexLength := length - 2
	paddedHex := strings.Repeat("0", expectedHexLength-len(hexStr)) + hexStr
	return "0x" + paddedHex
}
```

It is invoked directly on attacker-supplied strings from an incoming HTTP trigger request, with no prior length check: [2](#0-1) 

```go
workflowID := triggerReq.Params.Workflow.WorkflowID
if workflowID != "" {
    workflowID = normalizeHex(workflowID, workflowIDLength)
    ...
}
workflowOwner := normalizeHex(triggerReq.Params.Workflow.WorkflowOwner, workflowOwnerLength)
```

`workflowIDLength` (66) and `workflowOwnerLength` (42) are fixed constants: [3](#0-2) 

If a caller supplies a `WorkflowID` or `WorkflowOwner` value whose length (after stripping any `0x` prefix) exceeds `length-2`, `expectedHexLength-len(hexStr)` becomes negative. `strings.Repeat` in Go panics when given a negative count ("strings: negative Repeat count"). This is directly analogous to the Zephyr bug's root cause — a raw subtraction of an attacker-controlled length against a small constant with no `>=` guard before the result is consumed by a size-sensitive primitive. The Go runtime prevents this from becoming true memory corruption (Go slices/strings.Repeat panic instead of writing OOB), but the reachable effect is an unrecoverable panic in the gateway's request-handling goroutine.

### Impact Explanation
This is reachable from an unprivileged/unauthenticated actor: `HandleUserTriggerRequest` is the gateway's user-facing entry point for HTTP-triggered workflow execution, and `resolveWorkflowID`/`normalizeHex` run before authorization (`authorizeRequest`) is performed. A crafted `WorkflowID` (or `WorkflowOwner`) longer than the expected hex length triggers a panic. Depending on whether the calling goroutine has panic recovery, this can crash the request-handling goroutine or, if unrecovered at a higher level, the whole gateway process — a denial-of-service condition affecting all tenants sharing that gateway, without any prior authentication.

### Likelihood Explanation
High likelihood of triggering the panic: the field is a plain JSON string in the HTTP trigger request payload, fully attacker-controlled, and no length validation gate exists before `normalizeHex` is called for either `WorkflowID` or `WorkflowOwner`.

### Recommendation
In `normalizeHex`, validate that `len(hexStr) <= expectedHexLength` before calling `strings.Repeat`; return an explicit user error (e.g. "invalid workflow ID/owner length") otherwise, mirroring the length checks already used elsewhere in the codebase (e.g. `HexStringTo32Bytes`, `parseSelectorHex`). Ensure this validation happens before any auth-independent processing.

### Proof of Concept
Send an HTTP trigger request to the gateway with a `workflow.workflowId` (or `workflowOwner`) field far exceeding the expected length, e.g.:
```json
{
  "params": {
    "workflow": {
      "workflowId": "0xAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA"
    }
  }
}
```
Because `len(hexStr)` (128) > `expectedHexLength` (64), `strings.Repeat("0", 64-128)` is called with a negative count, causing an immediate panic in `normalizeHex`, before any authentication/authorization step is reached.
